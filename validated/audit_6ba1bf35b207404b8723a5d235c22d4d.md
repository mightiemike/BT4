### Title
Accrual pause freezes `last-update`, so unpausing back-charges the entire frozen span at the post-resume interest rate - ([File: mainnet/contracts/vault/v0-vault-stx.clar] and equivalent in all vault-*.clar contracts)

### Summary
When the vault's `accrue` pause flag is active, `next-index` returns the index unchanged and `last-update` is never advanced (it is only mutated when the index actually changes). When accrual is later unpaused, the next call to `accrue` computes `time-delta` as `stacks-block-time - last-update`, which now spans the pre-pause unaccrued interval **plus** the entire paused duration **plus** any time since unpause - and charges that whole span interest at whatever the *current* (post-resume) utilization-based rate is. This is the same root-cause pattern as the referenced FraxlendPair bug: a single rate is applied over an interval that actually straddles a state-boundary (there: maturity date; here: pause/unpause), instead of being split at the boundary.

### Finding Description
`last-update` is a data-var used as the anchor for interest accrual: [1](#0-0) 

`next-index` short-circuits to the current index (no accrual) while `accrue` is paused, and otherwise computes a multiplier from `interest-rate()` (driven by current utilization) over `time-delta = stacks-block-time - last-update`: [2](#0-1) 

The public `accrue` entrypoint only advances `last-update` when the computed index actually differs from the stored one: [3](#0-2) 

Because the pause check happens inside `next-index`/`next-liquidity-index` themselves (returning the unchanged index), the `if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time)` branch is never taken while paused - `last-update` is frozen for the full pause duration. When the DAO/admin later flips `accrue` back to `false` (unpausing), the very next `accrue()` call measures `time-delta` from the old, stale `last-update`, which now covers: (a) any real unaccrued interval before the pause began, (b) the entire paused window (during which zero interest should logically have accrued), and (c) time elapsed after unpausing. All of that combined interval is charged interest using the interest rate computed from utilization **at the moment of resumption**, not the rate(s) that would have applied incrementally over each sub-interval. This mirrors the FraxlendPair defect exactly: a rate that is only "correct" for the post-boundary portion of an interval gets applied to the entire interval, including a portion (the paused span) that should have been exempt or accrued differently.

### Impact Explanation
This inflates (or, depending on rate direction, distorts) the debt owed by every borrower in the vault and the yield credited to every lender, based purely on how long accrual happened to be paused and what the utilization-driven rate is at the moment of resumption - not on the actual risk/time exposure. Borrowers are charged interest for a period during which the protocol had intentionally frozen accrual, which is an unexpected, uncommunicated economic penalty analogous to the "theft of unclaimed yield" / "temporary freezing of funds"-adjacent impact called out in the reference report: value is extracted from borrowers (or under/over-credited to lenders) that does not correspond to real elapsed accrual time. This lands in the High impact bucket for "theft of unclaimed yield" since the miscalculated interest is unclaimed yield/debt that gets set incorrectly at the pause boundary.

### Likelihood Explanation
Triggering this requires only two ordinary sequential transactions: (1) an admin/DAO action to set `accrue: true` in `pause-states` (e.g., via the vault's pause-configuration entrypoint) followed later by (2) an admin action to set it back to `false`, and then any user or third party calling the public `accrue()` (or any operation that internally calls `accrue`, e.g. borrow/repay/deposit/redeem). No collusion between two users is required, and no flashloan is involved. Pausing accrual is a plausible, intended operational lever (e.g., during an oracle incident or upgrade), so this code path is realistically reachable under normal DAO operations, and the miscalculation is a mechanical, deterministic consequence of the `last-update`-freezing design rather than a rare edge case.

### Recommendation
When toggling `accrue` from paused to unpaused, snapshot/reset `last-update` to the current `stacks-block-time` at the moment of resumption (mirroring how `set-pause-liquidation` in `market.clar` explicitly manages a `grace-end` transition). This ensures that no interest accrues for the frozen span, and that only genuinely elapsed post-resume time is used in the subsequent `next-index`/`next-liquidity-index` calculations.

### Proof of Concept
1. At `t0`, someone calls `accrue()`; `last-update = t0`, `index = idx0`.
2. DAO calls the vault's pause-configuration function to set `pause-states.accrue = true` (pausing accrual) at `t1 > t0`. No `accrue()` call happens at `t1`, so `last-update` remains `t0` (per `mainnet/contracts/vault/v0-vault-stx.clar:855-866`, only updated on index change, and while paused `next-index` returns the same index, so it never updates).
3. Time passes; at `t2` (e.g., 30 days later) DAO unpauses accrual by setting `pause-states.accrue = false`.
4. Immediately at `t2`, any transaction triggers `accrue()`. `next-index` computes `time-delta = t2 - last-update = t2 - t0` (i.e., the full 30+ days spanning the entire paused period), and applies the current interest rate (from `interest-rate()`, based on utilization at `t2`) over that whole span via `calc-multiplier-delta`, as shown in `mainnet/contracts/vault/v0-vault-stx.clar:379-390`.
5. Every borrower's `total-debt` (`calc-cumulative-debt`) jumps up to reflect interest for the entire frozen interval, even though accrual was supposed to be halted for most of it - identical in mechanism to the FraxlendPair issue where the post-maturity penalty rate was applied retroactively to the pre-maturity interval.

(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta rate time-delta true))))
          (calc-index-next idx multiplier)))))
