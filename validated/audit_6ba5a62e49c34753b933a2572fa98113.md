### Title
Unbounded full-store iteration in `AssetIssueStore.getAllAssetIssues()` exposed via unpaginated `getassetissuelist` HTTP/gRPC endpoint enables CPU/memory/disk read-amplification DoS - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
`AssetIssueStore.getAllAssetIssues()` (inherited by `AssetIssueV2Store`) performs a full, unpaginated iteration of the entire asset-issue key-value store via `Streams.stream(iterator()).collect(Collectors.toList())`, and this method is reachable from the unauthenticated `GET /wallet/getassetissuelist` HTTP servlet and the corresponding gRPC call. Unlike `getAssetIssuesPaginated`, which caps results with `ASSET_ISSUE_COUNT_LIMIT_MAX`, this path has no size cap, so an attacker who inflates the number of issued assets (or simply repeatedly hits the endpoint on a chain that already has many assets) forces the node to materialize the entire asset list into memory and serialize it on every request.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` at [1](#0-0)  streams the full underlying store with no limit, in contrast to the paginated variant which explicitly bounds output using `ASSET_ISSUE_COUNT_LIMIT_MAX` at [2](#0-1) . `AssetIssueV2Store` adds no overriding behavior and simply inherits this unbounded method [3](#0-2) .

`GetAssetIssueListServlet.doGet` calls `wallet.getAssetIssueList()` directly and returns the full serialized result with no size limiting logic at the servlet layer beyond `RateLimiterServlet`'s generic rate limiting [4](#0-3) . The equivalent gRPC `getAssetIssueList` RPC in `RpcApiService` reaches the same `Wallet.getAssetIssueList()` code path. `RateLimiterServlet` only throttles request *rate*, not the *cost* of each individual request, so it does not mitigate the amplification: each allowed request still costs O(N) store iteration and full serialization where N is the total number of issued assets on chain.

Because asset issuance (`AssetIssueContract`) is a normal, low-cost transaction type available to any funded account, an attacker can grow N cheaply over time, and then repeatedly (up to whatever the rate limiter permits) invoke the unpaginated endpoint, each time forcing a full LevelDB/RocksDB iteration, full capsule deserialization, and full JSON/protobuf serialization of the entire asset-issue set — with no existing cap analogous to `ASSET_ISSUE_COUNT_LIMIT_MAX` protecting this specific path.

### Impact Explanation
This maps to **DoS via RPC-API**: sustained CPU (iteration + protobuf/JSON serialization), memory (materializing the full `List<AssetIssueCapsule>` and response payload) and disk I/O (full store scan) amplification per request, scaling linearly with the number of assets issued on the chain — a quantity influenced by any unprivileged attacker over time. Repeated requests at the maximum allowed rate multiply this cost, potentially degrading node responsiveness for all other RPC/HTTP consumers on that node.

### Likelihood Explanation
No privileged role is required: any unauthenticated client can call `GET /wallet/getassetissuelist` or the gRPC equivalent, and any funded account can broadcast ordinary `AssetIssueContract` transactions to grow the dataset over time (paying normal fees, no special conditions). The rate limiter (`RateLimiterServlet`) limits request frequency but not the cost of each request, so the amplification effect is not mitigated by existing checks. This is a low-cost, fully repeatable, unprivileged action; likelihood is moderate-to-high on any node with a nontrivial number of issued assets, and worse over time as more assets accumulate globally (since the chain-wide asset count is shared state, not attacker-local).

### Recommendation
Apply a hard cap (e.g., reuse `ASSET_ISSUE_COUNT_LIMIT_MAX`) to `getAllAssetIssues()`/`Wallet.getAssetIssueList()` or force callers to use the already-existing paginated API (`getAssetIssuesPaginated`), rejecting/redirecting the unpaginated `getassetissuelist` endpoint once the store size exceeds a safe threshold, and consider caching the full list with invalidation on writes to avoid repeated full scans for repeated read requests.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
