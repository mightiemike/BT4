### Title
Unbounded gas EVM call to attacker-controlled CEA recipient contract in `CallExecuteUniversalTx` enables free-of-charge compute griefing via gasless `MsgVoteInbound` - (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
The Vault.sol hooks bug is a case of untrusted, attacker-controlled contract logic being invoked from a privileged/claim-critical code path with no gas bound, enabling unbounded external calls that grief the caller. Push Chain has a structural analog: for `isCEA` inbounds whose `Recipient` is an attacker-deployed, non-UEA smart contract, `x/uexecutor` invokes that arbitrary contract's `executeUniversalTx` via `Keeper.CallExecuteUniversalTx` [1](#0-0) , which passes a `nil` `gasLimit` to `DerivedEVMCall` [2](#0-1) , unlike the user-derived UEA path (`CallUEAExecutePayload`) which explicitly bounds the call by the payload's declared `GasLimit` [3](#0-2) .

### Finding Description
`ExecuteInboundGasAndPayload` and `ExecuteInboundFundsAndPayload` both handle the case where an inbound's `Recipient` resolves to an attacker-deployed, non-UEA smart contract (`isSmartContract`), and both call `CallExecuteUniversalTx` with the recipient fully attacker-controlled [4](#0-3) [5](#0-4) . Because `gasLimit` is `nil`, the EVM call runs with the fork's "sensible default" rather than a value bounded by the payload's declared `GasLimit`. The declared `GasLimit` is only checked *after* execution, inside `DeductGasFeesFromReceipt`, as a post-hoc rejection (`gasUsedBig.Cmp(abiPayload.GasLimit) > 0 → error`) [6](#0-5) , and this whole EVM call + fee deduction runs inside a `CacheContext` that is discarded on fee failure, so a failing fee check leaves no lasting state change other than a "FAILED" `PCTx` record [7](#0-6) .

The inbound votes that trigger this path (`MsgVoteInbound`) are explicitly gasless — no Cosmos tx fee is charged to the submitter [8](#0-7) . An attacker can therefore:
1. Deploy a contract on Push Chain whose `executeUniversalTx` entry point consumes maximal EVM computation (loops, storage writes, etc.) up to whatever "sensible default" gas limit the fork applies when `gasLimit` is `nil`.
2. Submit/trigger an inbound (from any connected external chain) with `IsCEA=true` and `Recipient` set to that contract, with a `UniversalPayload.GasLimit` deliberately set below what the contract will actually burn.
3. Each of the (honest) Universal Validators that votes on this inbound causes Push Chain to execute the attacker's unbounded contract logic as a module-originated `DerivedEVMCall`, paying real EVM computation cost, before the post-hoc gas-limit/fee check discards the result and marks the `PCTx` as `FAILED`.

This differs from ordinary "wasted user gas" because the submitting message is gasless and the actual callee is unbounded before the check — the protocol/module absorbs the compute cost of arbitrary attacker bytecode with no upfront cap, and the same crafted inbound can be repeated cheaply.

### Impact Explanation
This is a compute-griefing/denial-of-service vector reachable by an ordinary unprivileged external actor (no relayer, validator, or governance privilege required) that forces honest validators to execute unbounded attacker-supplied EVM bytecode for free on every `MsgVoteInbound` for the crafted inbound. It does not corrupt canonical UTX/ballot state (the cache-context rollback correctly prevents the recipient from keeping unpaid state changes, and PC deposits made prior to the cached scope are unaffected), so it is a resource-consumption issue rather than a funds-loss or state-corruption issue. Per the impact gate, non-network-level DoS reachable by unprivileged users is in scope, but the severity here is limited because the guard rails (post-hoc fee/gas check + cache rollback) already prevent any permanent damage or fund loss — the residual impact is validator/node compute overhead.

### Likelihood Explanation
Reasonably likely for a determined attacker: deploying an EVM contract with expensive `executeUniversalTx` logic and getting an inbound observed with `IsCEA=true` pointing at it requires only a normal user-level cross-chain deposit/message from any connected source chain — no special permissions are needed, and it can be repeated as long as validators keep voting the inbound to completion.

### Recommendation
Pass an explicit, capped `gasLimit` (derived from `UniversalPayload.GasLimit`, symmetric to what `CallUEAExecutePayload` already does) into `CallExecuteUniversalTx`'s `DerivedEVMCall` invocation instead of `nil`, so the EVM call itself is bounded at execution time rather than only checked after the fact. Additionally consider enforcing a protocol-wide maximum gas ceiling for module-originated calls to attacker-controlled (non-UEA) recipients, independent of the caller-declared `GasLimit`, mirroring the "cap the gas used by hooks" mitigation recommended for the original Vault.sol finding.

### Proof of Concept
1. Deploy a Push Chain contract `Griefer` implementing `executeUniversalTx(...)` that performs an expensive loop (e.g., repeated `SSTORE`s) sized to consume close to the fork's default `DerivedEVMCall` gas ceiling.
2. Submit a source-chain event that Universal Validators observe as an inbound with `IsCEA=true`, `Recipient=Griefer`, and `UniversalPayload.GasLimit` set to a small value (e.g., `21000`).
3. As validators vote via `MsgVoteInbound` (gasless) to quorum, each vote triggers `ExecuteInboundGasAndPayload`/`ExecuteInboundFundsAndPayload` → `CallExecuteUniversalTx` → `DerivedEVMCall(..., gasLimit=nil, ...)`, executing `Griefer`'s expensive logic in full.
4. `DeductGasFeesFromReceipt` subsequently rejects the receipt because `GasUsed > payload.GasLimit`, the cache is discarded, and the `PCTx` is recorded as `FAILED` — but the EVM computation already happened, unpaid, as observed by `require.Greater(t, callPcTx.GasUsed, uint64(0), ...)` in the existing test for the analogous fee-failure scenario [9](#0-8) .
