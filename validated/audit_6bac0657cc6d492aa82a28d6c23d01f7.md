### Title
Attacker-grindable pubkeys force one accounts-index bin's HashMap past its configured `high_water_mark` because newly-created accounts stay "dirty" (unevictable) until their slot is rooted and flushed - `InMemAccountsIndex::get_or_create_index_entry_for_pubkey` - ([File: accounts-db/src/accounts_index/in_mem_accounts_index.rs])

### Summary
When `IndexLimit::Threshold` is configured, inline eviction in `get_or_create_index_entry_for_pubkey` and the background flush/evict path both refuse to evict `dirty` entries, and a freshly created account's entry stays dirty until it leaves the write cache via `write_through_pubkeys`/`try_write_through`, which only fires when the pubkey's slot is rooted-and-flushed or an unrooted slot is purged. An unprivileged attacker who grinds pubkeys landing in a single bin and creates many new distinct accounts inside one (or a few) un-flushed slots can make that bin's in-memory `HashMap` grow well past `high_water_mark` with zero inline or background eviction occurring, because every candidate entry is dirty.

### Finding Description
`BucketMapHolder::should_evict_based_on_count` compares `count` against `threshold_entries_per_bin.high_water_mark` [1](#0-0) . In `get_or_create_index_entry_for_pubkey`, once this condition fires for a new pubkey not already in the bin, the code searches for a clean candidate to evict via `map.iter().find(|(_, v)| !v.dirty())`; if none is found, `evict_key` is `None` and **no eviction happens at all** - the code proceeds to insert the new entry anyway [2](#0-1) .

Write-through (the only mechanism, besides periodic age-based background flush, that clears the dirty flag in `should_write_through` mode) is only invoked when a pubkey is fully removed from the accounts write cache:
- On rooted-slot flush, `do_flush_slot_cache` calls `write_through_pubkeys(pubkeys_removed)` only for pubkeys `accounts_cache.remove_slot` returns, i.e. pubkeys no longer present in *any* cached slot [3](#0-2) .
- On unrooted-slot purge, the same call pattern applies in `purge_slots_from_cache` [4](#0-3) .

Ordinary `upsert()` (the path used for normal account stores/creations) does not call `write_through` synchronously — only `replace()` and `slot_list_mut_with_entry()` do, and only when the entry's slot list already collapses to a single, uncached slot (`slot_list.len() == 1 && ref_count == 1`) [5](#0-4) [6](#0-5) . A brand-new account created and cached within the *current, unrooted* slot is therefore dirty and stays dirty until that slot is rooted and its slot cache is dropped.

The background flush path deliberately does the same thing: in `should_write_through` mode, dirty entries are explicitly skipped by the background scan/evict logic and only clean entries are evicted, as confirmed by the existing test `test_flush_internal_evicts_in_should_write_through_mode` ("dirty entries are written through inline on upsert...must NOT flush dirty entries to disk") [7](#0-6) , and `gather_possible_flush_evict_candidates` only adds non-dirty entries to the eviction-candidate list [8](#0-7) .

Bin assignment is a deterministic function of the pubkey bytes (`bin_calculator.bin_from_pubkey`, referenced at `get_bin`) [9](#0-8) , so an attacker can grind keypairs offline (no chain interaction, no privilege) until enough of them hash into one target bin, then submit account-creation transactions for those pubkeys within a short window (ideally within the same unrooted slot(s)).

Existing guards — slot/ancestor checks, zero-lamport handling, obsolete-account marking, ref-count checks — do not intervene here: ref-count checks (`entry.ref_count() != 1`) only block flush of multi-versioned entries and are irrelevant to freshly-created, single-version, dirty entries, which is exactly the case exploited.

### Impact Explanation
This is a disproportionate memory-cost issue (Agave bounty category: "unprivileged attacker forces disproportionate storage/index/memory work below true transaction cost"). While bounded by the validator's own root-advancement cadence (dirty entries eventually become evictable once their slot is rooted+flushed, typically on the order of a slot time), an attacker who concentrates enough distinct new-account creations into a single grindable bin before that flush happens can push that bin's `HashMap` len/capacity well past the configured `high_water_mark`/`target_entries_per_bin`, causing at least one unplanned capacity doubling of that bin, and correspondingly larger doublings on subsequent bursts. The `IndexLimitThreshold::num_bytes` configuration is meant to bound overall in-memory index footprint; this path lets that bound be exceeded per-bin in a way that is not proportional to the fees/rent the attacker paid for the accounts, matching the described "transient unbounded HashMap growth (capacity doubling) beyond the configured memory threshold" invariant violation.

### Likelihood Explanation
Preconditions: `IndexLimit::Threshold` must be configured (an operator choice, not attacker-controlled, but a supported and documented production configuration per the code and tests). Given that, the attack requires only: (1) offline pubkey grinding to target one bin (cheap, no chain access needed, purely local hashing), and (2) submitting enough account-creation transactions within a window before the containing slot(s) are rooted and flushed. The number of accounts creatable in that window is bounded by per-block compute-unit and account-lock limits and by the fees/rent the attacker must pay — this is the main mitigating factor limiting how far past `high_water_mark` a bin can be pushed in a single burst. The bug is deterministic and repeatable across every burst window (each new burst of un-flushed account creations targeting the same bin repeats the same unbounded-growth condition), so it is reliably reproducible in a unit-test harness that bypasses full validator/CU constraints (as most of the existing `should_write_through`-mode tests already do).

### Recommendation
In `get_or_create_index_entry_for_pubkey`'s inline-eviction path, when `should_evict_based_on_count` is true but no clean candidate exists (all entries dirty), apply a hard backstop rather than silently allowing unbounded insertion — e.g., synchronously write-through and evict a dirty, single-slot, ref-count==1 entry from the *current* write cache (not just cache-dropped pubkeys) when the bin is over threshold, or throttle/reject further mem-only growth of that bin until write-through catches up. Alternatively, extend `try_write_through`/`write_through_pubkeys` invocation to run proactively on a per-bin basis whenever `should_evict_based_on_count` trips, independent of cache-removal events, so dirty-but-single-versioned entries become eligible for inline eviction even before their containing slot is rooted.

### Proof of Concept
```rust
// accounts-db/src/accounts_index/in_mem_accounts_index.rs (add to #[cfg(test)] mod tests)

/// Demonstrates that when every candidate entry in a bin is dirty (i.e. still cached,
/// not yet write-through'd), get_or_create_index_entry_for_pubkey performs NO inline
/// eviction and the bin's HashMap grows past high_water_mark unbounded by the configured
/// threshold, violating the resource-cost invariant.
#[test]
fn test_inline_eviction_fails_when_all_entries_dirty_bin_grows_unbounded() {
    // high_water_mark=2: after inserting >2 entries we should trigger eviction attempts.
    let index = new_should_write_through_for_test(Some((2, 1)));
    let slot = 1;
    let info = 2;

    // Insert many *new* pubkeys via upsert WITHOUT calling try_write_through
    // (simulating accounts still live in the write cache, i.e. not yet flushed/rooted).
    let num_inserts = 50;
    for i in 0..num_inserts {
        let pubkey = solana_pubkey::new_rand();
        let new_value = PreAllocatedAccountMapEntry::new(slot, info + i, &index.storage, true);
        index.upsert(
            &pubkey,
            new_value,
            None,
            &mut ReclaimsSlotList::new(),
            UpsertReclaim::IgnoreReclaims,
        );
        // Note: try_write_through is intentionally NOT called here, mirroring an
        // attacker's burst of account creations within a single unrooted slot.
    }

    let len = index.map_internal.read().unwrap().len();
    let capacity = index.map_internal.read().unwrap().capacity();

    // Assert the resource-cost invariant is violated: len has grown far past
    // high_water_mark (2) with no bounded slack, because no clean candidate was
    // ever found to evict inline.
    let thresholds = index.storage.threshold_entries_per_bin.unwrap();
    assert!(
        len > thresholds.high_water_mark,
        "expected len ({len}) to exceed high_water_mark ({}) due to failed inline eviction",
        thresholds.high_water_mark
    );
    assert_eq!(len, num_inserts, "no entries were evicted because all were dirty");
    assert!(capacity >= len, "capacity doubled/grew unbounded relative to configured threshold");
}
```

Fuzz/invariant extension: parameterize `num_inserts` and burst rate (interleaving simulated `age` increments to allow the background flush to run) and assert `map_internal.len() <= high_water_mark + configured_slack` fails once inserts exceed `high_water_mark` while no `try_write_through` calls are interleaved — confirming the bin's growth is bounded only by attacker-controlled burst size, not by the configured `IndexLimitThreshold`.
