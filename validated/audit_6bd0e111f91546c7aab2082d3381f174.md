### Title
Signer's `bitcoin_block_arrival` fallback to the prior sortition's miner omits the canonical-tip check that `check_miner_inactivity` enforces, letting a signer adopt an already-orphaned miner as active - ([File: stacks-signer/src/v0/signer_state.rs])

### Summary
When a Bitcoin block arrives, `LocalStateMachine::bitcoin_block_arrival` decides who the active miner is by testing `is_tenure_valid()` on the current sortition and, if that fails, falling back to the *prior* sortition without ever checking that the prior sortition's tenure is still the one the canonical Stacks tip is built on [1](#0-0) . The sibling code path, `check_miner_inactivity`, performs the exact same "revert to prior miner" decision but explicitly guards it with a canonical-tip check before doing so, precisely because a Bitcoin reorg can orphan the prior tenure and leave its miner already stopped [2](#0-1) . That guard was added as a deliberate fix, documented in the changelog entry stating a miner must not be treated as active unless the canonical Stacks tip is in its tenure [3](#0-2) , but the equivalent check was never applied to `bitcoin_block_arrival`.

### Finding Description
`SortitionState::is_tenure_valid` only verifies two things: that the sortition chose an acceptable parent tenure (`check_parent_tenure_choice`) and that the tenure has not timed out (`is_timed_out`) [4](#0-3) . Neither check confirms that the tenure in question is the one the *canonical Stacks tip* currently descends from. `check_parent_tenure_choice` itself only validates whether a reorg away from a prior tenure was legitimate at proposal time; it does not re-derive "is this tenure still live" at the moment of evaluation [5](#0-4) .

`bitcoin_block_arrival` uses exactly this insufficient check to decide the miner view for the *whole* state machine on every new burn block:
```
let is_current_valid = cur_sortition.is_tenure_valid(...)?;
let miner_state = if is_current_valid {
    Self::make_miner_state(cur_sortition.data().clone(), ...)?
} else {
    ...
    let is_last_valid = last_sortition.is_tenure_valid(...)?;
    if is_last_valid {
        Self::make_miner_state(last_sortition.data().clone(), ...)?
    } else {
        MinerState::NoValidMiner
    }
};
``` [1](#0-0) 

Contrast this with `check_miner_inactivity`, which performs the analogous "should we revert to the prior miner" decision but adds an explicit tip check that `bitcoin_block_arrival` lacks:
```
let stacks_tip_ch = client.get_peer_info()?.stacks_tip_consensus_hash;
if sortition_data.consensus_hash != stacks_tip_ch {
    warn!("... the canonical stacks tip is not in the prior miner's tenure, so the prior miner cannot continue it. Allowing current miner to continue");
    return Ok(());
}
if !last_sortition.is_tenure_valid(...)? { ... }
``` [6](#0-5) 

This is structurally the same defect class as the reported Flayer bug: one state-check function (`Locker::isListing`) is relied upon by a critical path but fails to reflect an intermediate/invalidated state that a sibling code path (the withdraw flow) does track correctly. Here, `is_tenure_valid` is relied upon by `bitcoin_block_arrival` to decide "is this sortition's miner still the legitimate active miner," but it fails to reflect the "has the canonical tip moved off this tenure due to a reorg" state that `check_miner_inactivity` explicitly tracks via `stacks_tip_ch` comparison.

### Impact Explanation
If the current sortition is deemed invalid at the moment a new Bitcoin block arrives (e.g., it failed `check_parent_tenure_choice`), the signer falls back to the prior sortition. If a Bitcoin reorg has, in the interim, orphaned that prior sortition's tenure (the same scenario the changelog fix targets), `is_tenure_valid` on `last_sortition` can still return `true` because it never checks whether the canonical Stacks tip is actually still in that tenure. The affected signer then sets `MinerState::ActiveMiner` to a miner whose node has already stopped mining and will never propose again, rejecting valid proposals from the correct, canonical miner. Because `check_miner_inactivity` (the other code path making this same class of decision) does carry the tip check and would behave differently, signers can diverge on who the legitimate active miner is - a minority-triggerable, unprivileged validation-verdict divergence causing temporary tip/agreement disagreement among signers, consistent with the "High" impact category (signer weight/validation divergence, temporary tip disagreement).

### Likelihood Explanation
This does not require any majority or malicious collusion: a natural Bitcoin reorg orphaning the prior sortition's tenure, combined with the current sortition momentarily failing `check_parent_tenure_choice` (e.g., because of a legitimate but unusual reorg pattern), is sufficient to route a signer through the vulnerable `bitcoin_block_arrival` fallback branch instead of `check_miner_inactivity`. The bug is a straightforward inconsistency between two near-identical decision functions in the same file, not a deep economic attack, and the fix committed for `check_miner_inactivity` demonstrates the maintainers already recognize this exact failure mode is realistic.

### Recommendation
Apply the same canonical-tip check used in `check_miner_inactivity` to the fallback branch of `bitcoin_block_arrival`: before adopting `last_sortition` as `MinerState::ActiveMiner`, verify that `last_sortition.data().consensus_hash` matches the node's current `stacks_tip_consensus_hash` (or equivalent canonical-tip derivation), and only proceed with `is_tenure_valid` if that holds; otherwise set `MinerState::NoValidMiner` (or retain the invalid current miner state) as `check_miner_inactivity` does.

### Proof of Concept
1. Signer's local state machine has `cur_sortition` = tenure A, which fails `check_parent_tenure_choice` (e.g., A's committed parent tenure is disputed/invalid) at burn-block arrival time.
2. `bitcoin_block_arrival` falls into the `else` branch and evaluates `last_sortition` = tenure B (the previously-considered valid tenure).
3. Between B's original activity and this evaluation, a Bitcoin reorg has orphaned tenure B; the canonical Stacks tip is no longer inside B's tenure, and B's miner node has already stopped mining (mirroring the exact scenario in `stacks-signer/changelog.d/no-fallback-to-stopped-miner.fixed`).
4. `last_sortition.is_tenure_valid(...)` still returns `true` because `check_parent_tenure_choice`/`is_timed_out` do not check the canonical tip at all [4](#0-3) .
5. The signer sets `MinerState::ActiveMiner` to tenure B's (stopped) miner via `bitcoin_block_arrival` [7](#0-6) , while other signers (or this same signer via `check_miner_inactivity` in a different code path) would have blocked this exact fallback because tenure B's consensus hash no longer matches the canonical stacks tip [8](#0-7) . This produces a signer-level disagreement on the active miner, rejecting the legitimate current miner's proposals.

    /// check if the tenure defined by sortition state:
    ///  (1) chose an appropriate parent tenure
    ///  (2) has not "timed out"
    pub fn is_tenure_valid(
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        proposal_config: &ProposalEvalConfig,
        eval: &GlobalStateEvaluator,
    ) -> Result<bool, SignerChainstateError> {
        let data = self.data();
        let chose_good_parent = data.check_parent_tenure_choice(
            signer_db,
            client,
            &proposal_config.first_proposal_burn_block_timing,
        )?;
        if !chose_good_parent {
            return Ok(false);
        }
        Self::is_timed_out(
            &self.version(),
            &data.consensus_hash,
            signer_db,
            client.get_signer_address(),
            proposal_config,
            eval,
        )
        .map(|timed_out| !timed_out)
    }
