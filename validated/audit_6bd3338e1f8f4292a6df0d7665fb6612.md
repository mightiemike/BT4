### Title
Unauthenticated state-value ingestion during `KvOnly` backup restore corrupts pre-replay ledger state - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
The `restore` coordinator's phase-1 flow (`storage/backup/backup-cli/src/coordinators/restore.rs:242-260`) restores an early state snapshot using `StateSnapshotRestoreMode::KvOnly` before replaying transactions on top of it. In this mode, `StateSnapshotRestore::add_chunk` (`storage/aptosdb/src/state_restore/mod.rs:213-218`) calls only `kv_restore.add_chunk(chunk)` and never calls `tree_restore.verify_chunk`, so the `SparseMerkleRangeProof` shipped with the chunk is never checked against any root hash for that version.

### Finding Description
`StateSnapshotRestoreController::run_impl` (`storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs:113-230`) does verify the overall snapshot's `TransactionInfoWithProof` and `manifest.root_hash` once, up front — but that verification path is orthogonal to the per-chunk `add_chunk` calls, and in `KvOnly` mode the per-chunk proof is dropped in `StateSnapshotRestore::add_chunk` (`storage/aptosdb/src/state_restore/mod.rs:213-218`):
```rust
StateSnapshotRestoreMode::KvOnly => {
    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
},
```
Contrast this with `Default` mode, which explicitly documents "verify proof -> write state_kv_db -> write state_merkle_db" (lines 227-249) as a safety invariant. `StateValueRestore::add_chunk` itself (lines 73-112) performs zero cryptographic validation of the `(key, value)` pairs it writes — it only reads/writes a `StateSnapshotProgress` cursor for resumability and unconditionally commits `write_kv_batch`.

This `KvOnly` restore is exercised specifically at `storage/backup/backup-cli/src/coordinators/restore.rs:247-259` for the *older* `kv_snapshot.version`, which is different from `tree_snapshot.version` that later gets `TreeOnly`-verified. Because the two versions differ, the later `TreeOnly` Jellyfish Merkle verification checks leaf hashes at `tree_snapshot.version`, not the raw values written during the earlier unverifiable `KvOnly` phase. Transaction replay (`TransactionRestoreBatchController` in "only replay KV" mode, lines 289-300) then executes on top of this unverified base state to advance to `tree_snapshot.version`. Any state key present at `kv_snapshot.version` that is never subsequently touched by replayed transactions retains its unverified, potentially tampered value permanently, with no cryptographic binding ever validated against it.

### Impact Explanation
A corrupted or maliciously modified backup archive (e.g., a compromised or buggy backup storage backend, `BackupStorage` implementation, or a bit-flip/truncation in transit) can inject arbitrary state values into the restored node's `state_kv_db` for any state key not overwritten by subsequent transaction replay. This produces a node whose serving state (via `get_state_value_by_version` and downstream authenticated reads) silently diverges from the true, consensus-committed ledger state — with no error, no proof failure, and no detectable inconsistency at restore time. This is a hard state-corruption bug: the restored node's account/resource data no longer reflects the correct VM result, which is exactly the class of impact the state-integrity gate targets ("Committed state that differs from the correct VM result or corrupts durable ledger data").

### Likelihood Explanation
Exploitability requires control over, or corruption of, the backup archive content consumed by `KvOnly` restore (a `BackupStorage` implementation and its state-snapshot chunk files/manifests). This is a real, unprivileged path for anyone operating restore against an untrusted or compromised backup store (a common deployment for full-node bootstrap/DR), since the code contains no fallback validation for `KvOnly` chunks. It does not require any validator or consensus authority — only supplying a bad backup blob to a node performing this specific restore mode combination (kv snapshot version < tree snapshot version, phase 1 of `RestoreCoordinator`).

### Recommendation
In `StateSnapshotRestore::add_chunk`'s `KvOnly` branch, verify the supplied `SparseMerkleRangeProof` against the snapshot's `expected_root_hash` (the same verification `TreeOnly`/`Default` perform), even if the resulting Merkle nodes are not persisted, so that KV-only restores cannot silently ingest unauthenticated key/value data. Alternatively, refactor `KvOnly` restore to always run `verify_chunk` (discarding tree writes) before calling `kv_restore.add_chunk`.

### Proof of Concept
1. Set up a `RestoreCoordinator` restore where a state-kv snapshot exists at `kv_snapshot.version` strictly less than `tree_snapshot.version` (a normal incremental-restore scenario per `storage/backup/backup-cli/src/coordinators/restore.rs:198-210`).
2. Serve a tampered state-snapshot chunk file for `kv_snapshot.version` from the `BackupStorage` (modify one `(StateKey, StateValue)` pair on disk that is not touched by any transaction between `kv_snapshot.version` and `tree_snapshot.version`).
3. Run restore: `StateSnapshotRestoreController::run_impl` verifies only the overall `manifest.root_hash`/`TransactionInfoWithProof` for the full snapshot commitment, not the individual chunk's `SparseMerkleRangeProof`, and `StateSnapshotRestore::add_chunk` in `KvOnly` mode writes the tampered chunk directly via `StateValueRestore::add_chunk` with no cryptographic check (`storage/aptosdb/src/state_restore/mod.rs:213-218`, `73-112`).
4. After restore completes (including transaction replay to `tree_snapshot.version` and beyond), query the tampered state key: it returns the attacker-supplied value instead of the correct historical value, with the node reporting successful restore. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

struct StateValueRestore<K, V> {
    version: Version,
    db: Arc<dyn StateValueWriter<K, V>>,
}

impl<K: Key + CryptoHash + Eq + Hash, V: Value> StateValueRestore<K, V> {
    pub fn new<D: 'static + StateValueWriter<K, V>>(db: Arc<D>, version: Version) -> Self {
        Self { version, db }
    }

    pub fn add_chunk(&mut self, mut chunk: Vec<(K, V)>) -> Result<()> {
        // load progress
        let progress_opt = self.db.get_progress(self.version)?;

        // skip overlaps
        if let Some(progress) = progress_opt {
            let idx = chunk
                .iter()
                .position(|(k, _v)| CryptoHash::hash(k) > progress.key_hash)
                .unwrap_or(chunk.len());
            chunk = chunk.split_off(idx);
        }

        // quit if all skipped
        if chunk.is_empty() {
            return Ok(());
        }

        // save
        let mut usage = progress_opt.map_or(StateStorageUsage::zero(), |p| p.usage);
        let (last_key, _last_value) = chunk.last().unwrap();
        let last_key_hash = CryptoHash::hash(last_key);

        // In case of TreeOnly Restore, we only restore the usage of KV without actually writing KV into DB
        for (k, v) in chunk.iter() {
            usage.add_item(k.key_size() + v.value_size());
        }

        // prepare the sharded kv batch
        let kv_batch: StateValueBatch<K, Option<V>> = chunk
            .into_iter()
            .map(|(k, v)| ((k, self.version), Some(v)))
            .collect();

        self.db.write_kv_batch(
            self.version,
            &kv_batch,
            StateSnapshotProgress::new(last_key_hash, usage),
        )
    }

impl<K: Key + CryptoHash + Hash + Eq, V: Value> StateSnapshotReceiver<K, V>
    for StateSnapshotRestore<K, V>
{
    fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_verify_chunk"]);
                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
                }
            },
        }

        Ok(())
    }
