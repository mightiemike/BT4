### Title
Blake3-based Accounts Lattice-Hashing at `Bank::freeze()` is a Disproportionate, Non-Metered CPU Cost per Block - (File: `runtime/src/bank/accounts_lt_hash.rs`)

### Summary
The external report describes a `sequencer`/zkEVM finalization function whose gas cost scales with the number of transactions/logs in a block, but is not itself bounded by the block gas limit, risking block-finalization failure or DoS. The closest concrete analog in agave is the accounts lattice-hash (`lt_hash`) update that Solana's `Bank` computes at block finalization time (`Bank::freeze()`). This hashing work is proportional to the total bytes of every account modified in the block (including full-size, unpacked account data up to the ~10 MB account maximum), is executed with a fixed, small thread pool, and its CPU cost is not directly metered against the transaction/block compute-unit (CU) budget the way instruction execution is. This creates a mismatch between the (nominally CU-capped) block and the actual finalization-time CPU work required, mirroring the report's "gas requirement exceeds block gas limit" pattern.

### Finding Description
When a block is produced or replayed, every modified account is hashed with blake3 via `AccountsDb::lt_hash_account` / `hash_account_helper`, which hashes the account's *entire* data buffer (not a fixed-size digest of it): [1](#0-0) [2](#0-1) 

The project's own benchmark acknowledges this cost scales with account size, up to the largest permitted account (10 MB): [3](#0-2) 

During normal transaction processing, every modified account in the batch is enqueued to a small, fixed-size thread pool (`NUM_ACCOUNTS_HASHER_THREADS = 4`) for lt-hash computation: [4](#0-3) [5](#0-4) 

Critically, `finish_accounts_lt_hash_updates()` — called as part of freezing/finalizing the bank for a slot — *blocks* until all in-flight hashing jobs for that block complete, before the bank's hash/lattice state is considered final: [6](#0-5) 

This work is synchronous with respect to block finalization: a validator producing or replaying a slot cannot declare the bank "frozen" (i.e., finalize the block's state/hash) until this hashing has completed for every account touched in the block, regardless of how large those accounts were.

The Solana cost model, which is what actually gates how many transactions/how much data can go into a block, meters write-locks as a flat per-account-key cost and CU consumption tied to the VM's own accounting (`WRITE_LOCK_UNITS`, `loaded_accounts_data_size_cost`, `programs_execution_cost`), none of which are calibrated to the blake3-hashing cost incurred later at freeze time: [7](#0-6) [8](#0-7) [9](#0-8) 

The per-block cap that is explicitly tied to account *data size* only limits *growth* of accounts data within a block (new allocations), not the cost of rewriting/hashing already-existing large accounts: [10](#0-9) 

An attacker can therefore repeatedly touch multiple large, pre-existing accounts (created in earlier blocks, up to the platform's max account size) across many transactions within the same block, up to the per-writable-account and total block CU limits (`MAX_WRITABLE_ACCOUNT_UNITS`, `MAX_BLOCK_UNITS`), while imposing a blake3-hashing workload on the fixed 4-thread accounts-hasher pool that is disproportionate to the flat write-lock/CU cost actually charged for those writes, and which must complete synchronously before the block can be finalized.

### Impact Explanation
Because `finish_accounts_lt_hash_updates()` gates block finalization (bank freeze) and runs on a small fixed thread pool doing per-byte blake3 hashing of every modified account's full data, a block engineered to touch the maximum number of large, already-allocated accounts permitted by the CU-based cost model can impose CPU cost at finalization time that is disproportionate to what the cost model intended to bound. This is analogous to the reported "heavy block exceeding gas limit" scenario: the resource (CPU time for finalization) required is decoupled from the resource (CU) that is actually capped, risking delayed block finalization / slot processing on the honest-node critical path — a disproportionate CPU cost issue as permitted by the validation rules.

### Likelihood Explanation
Likelihood is moderate: reaching this path only requires an ordinary, unprivileged user submitting normal write transactions against multiple large, pre-existing accounts they control (no special role required), and the accounts-hashing code path (`enqueue_on_chain_accounts_lt_hash_updates` → `finish_accounts_lt_hash_updates`) is executed unconditionally by every bank freeze. However, the actual severity depends on cluster-wide CU limits (`MAX_BLOCK_UNITS`, `MAX_WRITABLE_ACCOUNT_UNITS`) and how many maximally-sized accounts can realistically be packed and rewritten in a single block under those limits, which was not verified end-to-end (no direct evidence in the indexed code of an existing byte-proportional charge specifically calibrated to the lt-hash CPU cost, nor conclusive proof this exceeds acceptable finalization latency in practice).

### Recommendation
Benchmark and calibrate the CU/cost-model charges for writable accounts and loaded-account-data-size to reflect the actual blake3 lattice-hashing cost incurred at `Bank::freeze()`, and/or bound the total bytes of already-existing account data that can be rewritten (not just newly allocated) within a single block, so that finalization-time hashing work is proportional to what the block's compute budget already caps.

### Proof of Concept
1. Create N accounts near the maximum account size (~10 MB each) in earlier blocks.
2. In a subsequent block, submit the maximum number of transactions permitted by `MAX_BLOCK_UNITS` / `MAX_WRITABLE_ACCOUNT_UNITS` that each rewrite one byte of a distinct large account (minimal CU cost per write-lock, per `WRITE_LOCK_UNITS`).
3. Observe that `Bank::freeze()` must, via `finish_accounts_lt_hash_updates`, wait for blake3 hashing (`lt_hash_account`/`hash_account_helper`) over the full data of every touched large account on only `NUM_ACCOUNTS_HASHER_THREADS = 4` threads before the block can be considered finalized — reproducible via the existing `bench_hash_account` benchmark showing per-byte hashing cost scaling with the 10 MB `DATA_SIZES` case: [11](#0-10) .

    pub fn enqueue_on_chain_accounts_lt_hash_updates<'a>(
        &self,
        accounts: &impl StorableAccounts<'a>,
    ) {
        if accounts.is_empty() {
            return;
        }

        let seen_accounts_freelist = seen_accounts_freelist();
        let mut seen_accounts = seen_accounts_freelist.try_pop().unwrap_or_default();
        let async_progress = &self.accounts_lt_hash_async_progress;
        let thread_pool = accounts_hasher_thread_pool();

        // process accounts in reverse because we must only count the latest version of each account
        for index in (0..accounts.len()).rev() {
            let address = accounts.pubkey(index);
            if !seen_accounts.insert(*address) {
                // we've already enqueued a newer update for the same account; skip this one
                continue;
            }
            let prev_account = self
                .rc
                .accounts
                .load_with_fixed_root_do_not_populate_read_cache(&self.ancestors, address)
                .map(|(account, _slot)| account);
            let curr_account = accounts.account(index, |account| {
                (account.lamports() != 0).then(|| account.take_account())
            });
            if prev_account.is_none() && curr_account.is_none() {
                // the account was ephemeral; skip it
            } else {
                // the account was modified; enqueue this update
                async_progress.spawn(
                    thread_pool,
                    AccountsLtHashUpdate {
                        address: *address,
                        prev_account,
                        curr_account,
                    },
                );
            }
        }

        // reclaim the seen accounts hashset
        seen_accounts_freelist.try_push(seen_accounts);
    }

    pub fn try_add(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<UpdatedCosts, CostTrackerError> {
        let cost = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // Check each account against account_cost_limit and apply the cost in
        // the same lookup. On failure, undo the applied prefix.
        let mut updated_costliest_account_cost = 0;
        for (index, account_key) in tx_cost.writable_accounts().enumerate() {
            let new_account_cost = match self.cost_by_writable_accounts.entry(*account_key) {
                Entry::Occupied(mut entry) => {
                    let new_account_cost = entry.get().saturating_add(cost);
                    if new_account_cost > self.limits.account_cost {
                        None
                    } else {
                        *entry.get_mut() = new_account_cost;
                        Some(new_account_cost)
                    }
                }
                Entry::Vacant(entry) => {
                    // `cost <= limits.account_cost` was checked above, so an
                    // account without chained cost always fits
                    entry.insert(cost);
                    Some(cost)
                }
            };
            let Some(new_account_cost) = new_account_cost else {
                // the first `index` accounts were applied before this failure
                self.roll_back_applied_costs(tx_cost, cost, index);
                return Err(CostTrackerError::WouldExceedAccountMaxLimit);
            };
            updated_costliest_account_cost = updated_costliest_account_cost.max(new_account_cost);
        }
