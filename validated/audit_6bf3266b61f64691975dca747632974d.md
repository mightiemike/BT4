### Title
`VoteWitnessActuator` allows duplicate witness entries in `AccountCapsule`/`VotesCapsule` votes list when the same witness address is voted for twice in one `VoteWitnessContract` - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
`VoteWitnessActuator.countVoteAccount()` pushes every `Vote` entry from the incoming `VoteWitnessContract` into `accountCapsule` and `votesCapsule` without checking (or merging) whether the same witness address was already added in the same list. This mirrors the reported `NestedRecords.store` bug class: an element is appended to an array without a duplicate/existence check, so the same key can appear multiple times, and downstream processing that expects one entry per key silently gets duplicated/inconsistent data instead.

### Finding Description
`VoteWitnessActuator.validate()` only checks each `Vote` entry's address validity, that `voteCount > 0`, and that the accumulated `sum` does not exceed the voter's `tronPower`. It never checks for duplicate `voteAddress` values within `contract.getVotesList()`. [1](#0-0) 

`countVoteAccount()` then iterates the raw contract vote list with `forEach` and calls `addVotes`/`addNewVotes` once per entry, with no de-duplication or merging logic: [2](#0-1) 

`AccountCapsule.addVotes()` unconditionally appends a new `Vote` proto entry to the repeated `votes` field — it does not check whether an entry for that address already exists: [3](#0-2) 

`VotesCapsule.addNewVotes()` behaves identically for the `newVotes` list: [4](#0-3) 

This is the exact analog of the reported bug: a value is pushed into an array keyed by an identifier (witness address / token) without checking for an existing entry, allowing the identifier to appear twice with two different amounts.

Notably, the TVM-native equivalent, `VoteWitnessProcessor.execute()` (used by the `voteWitness` TVM opcode), was written correctly: it explicitly merges votes for the same witness into a `Map<ByteString, Long> voteMap` before writing them, precisely to avoid this duplicate-entry problem: [5](#0-4) 

The plain (non-TVM) `VoteWitnessActuator` path used for ordinary `VoteWitnessContract` transactions lacks this merge step, so it is vulnerable to the same class of duplicate-array-entry issue that the sibling TVM code was specifically hardened against.

### Impact Explanation
Once a duplicate witness entry exists in `AccountCapsule.votes` / `VotesCapsule.newVotes`, several downstream consumers iterate the full list and sum by entry rather than by unique witness key, e.g. reward computation in `MortgageService.computeReward()` and `VoteRewardUtil.computeReward()`, both of which loop over `accountCapsule.getVotesList()`: [6](#0-5) [7](#0-6) 

Because these loops sum per-entry (not per-unique-address), a state divergence is created between the account's on-chain vote-list representation and what a single logical "one vote per witness per account" invariant assumes elsewhere in the codebase (e.g., HTTP/gRPC vote-list APIs, `VoteWitnessAccountServlet`, and any client tooling assuming one `Vote` entry per witness per account). This can produce inconsistent/duplicated vote records for a witness from a single account, complicating audits, UI display, and any external code that does a lookup-by-first-match against the votes list (as in the referenced report's root cause) — leading to state/accounting divergence rather than direct fund loss, since the `tronPower` cap still limits the total sum of vote counts.

### Likelihood Explanation
Any unprivileged account can trigger this by constructing a `VoteWitnessContract` with the same witness address listed more than once (each with a valid positive `voteCount` and combined sum ≤ tronPower) and submitting it as a normal transaction through `VoteWitnessActuator`; no special privilege is required. This is a straightforward, always-reachable transaction path.

### Recommendation
In `VoteWitnessActuator.validate()`, reject `VoteWitnessContract`s containing duplicate `voteAddress` entries, or in `countVoteAccount()`, merge votes for the same witness address into a single entry before calling `addVotes`/`addNewVotes` — matching the de-duplication logic already implemented in `VoteWitnessProcessor.execute()`.

### Proof of Concept
1. Freeze balance to obtain sufficient `tronPower`.
2. Construct a `VoteWitnessContract` with `votes = [{witnessA, 1}, {witnessA, 5}]` (same witness address twice, sum = 6 ≤ tronPower).
3. Submit via `VoteWitnessActuator`. `validate()` passes because it never checks address uniqueness (`actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java:98-121`).
4. `countVoteAccount()` calls `accountCapsule.addVotes(witnessA, 1)` then `accountCapsule.addVotes(witnessA, 5)` in the `forEach` loop, producing two separate `Vote` entries for `witnessA` in `AccountCapsule.votes` and `VotesCapsule.newVotes`, instead of one merged entry of `6`.

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
