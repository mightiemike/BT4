### Title
`GetRewardServlet`/`queryReward()` returns a nonzero reward for guard representatives who are prohibited from ever withdrawing it - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.queryReward()` (and its duplicate in `VoteRewardUtil.queryReward()`) is a pure read-only computation of a witness's outstanding reward. It is exposed unauthenticated via `GetRewardServlet`/`/wallet/getReward` and via the `withdrawReward` TVM opcode path. However, the actual withdrawal path (`WithdrawBalanceActuator.validate()`) explicitly forbids "guard representative" (genesis-block witness) accounts from ever withdrawing their allowance/reward. `queryReward()` never checks this "isGP" condition, so it reports a nonzero, seemingly withdrawable reward for accounts that can never actually withdraw it - mirroring the reported Sablier `refundableAmountOf()` bug, where the view function omits a status check (`isCancelable`) that the corresponding state-changing action enforces.

### Finding Description
`WithdrawBalanceActuator.validate()` contains an explicit, chain-enforced invariant: [1](#0-0) 

Any account matching a genesis-block witness address ("guard representative", GP) can never successfully execute a `WithdrawBalanceContract` - the transaction will always fail validation.

The reward preview function used both internally and externally, however, computes and returns the reward with no such check: [2](#0-1) 

The identical duplicate logic used by the TVM `withdrawReward`/`rewardBalance` opcodes has the same omission: [3](#0-2) 

This `queryReward()` result is exposed directly and unauthenticated to any caller through the HTTP API: [4](#0-3) 

and is even used inside `WithdrawBalanceActuator.validate()` itself as a "has any reward" pre-check that ignores the GP restriction: [5](#0-4) 

So the exact same asymmetry described in the report exists here: the "how much can I get" view function does not encode the "can I get anything at all" precondition that the corresponding mutating actuator enforces.

### Impact Explanation
Any external system (analytics dashboards, exchanges, lending/DeFi-style integrations built on top of java-tron, delegation/voting-reward aggregators) that queries `/wallet/getReward` (or the TVM `rewardBalance`/analogous opcode) to determine a witness account's claimable reward will get a nonzero, "spendable" balance for guard representative accounts that in fact can never be withdrawn on-chain. This is a state/business-logic inconsistency between a read view and the real state-transition rule, which can cause downstream financial miscalculation (e.g., an integrator crediting or collateralizing a guard-rep's "reward" balance that is permanently non-withdrawable), directly analogous to the impact described in the report (a lending protocol overestimating a liquidatable/withdrawable amount).

### Likelihood Explanation
Likelihood is limited by two factors: (1) guard representatives are a small, fixed, genesis-configured set of addresses (`CommonParameter.getInstance().getGenesisBlock().getWitnesses()`), so the affected account set is very small and known in advance; and (2) no funds are actually lost on-chain — the discrepancy only manifests in the reported/queried value, not in an exploitable state transition, since `WithdrawBalanceActuator.validate()` still correctly blocks the withdrawal. This is a read-view/business-logic-accuracy issue rather than a directly exploitable fund-drain or consensus bug, so likelihood of a real incorrect crediting event depends entirely on whether any downstream integrator trusts this reward-query value as directly withdrawable.

### Recommendation
Add the same guard-representative check used in `WithdrawBalanceActuator.validate()` to `MortgageService.queryReward()` and `VoteRewardUtil.queryReward()`, returning `0` for GP addresses (mirroring the Sablier fix that folds the `isCancelable` check into `refundableAmountOf()`):
```java
public long queryReward(byte[] address) {
  boolean isGP = CommonParameter.getInstance()
      .getGenesisBlock().getWitnesses().stream()
      .anyMatch(witness -> Arrays.equals(address, witness.getAddress()));
  if (isGP) {
    return 0;
  }
  ... // existing logic
}
```

### Proof of Concept
1. Identify a genesis-block witness address `GP` (guard representative), e.g. one of the addresses returned by `CommonParameter.getInstance().getGenesisBlock().getWitnesses()`.
2. Cause `GP` to accumulate reward/allowance (e.g. via block/transaction-fee rewards being paid to it as a witness, per `MortgageService.payBlockReward`/`payTransactionFeeReward`).
3. Call the unauthenticated HTTP API `GET/POST /wallet/getReward` with `address=GP` (`GetRewardServlet.doGet`/`doPost` → `manager.getMortgageService().queryReward(address)`); observe a nonzero reward value returned.
4. Attempt to actually withdraw by broadcasting a `WithdrawBalanceContract` transaction from `GP`; observe it is rejected in `WithdrawBalanceActuator.validate()` with `"... is a guard representative and is not allowed to withdraw Balance"`.
5. This demonstrates the view (`queryReward`) reports a withdrawable amount that the state-transition logic (`WithdrawBalanceActuator`) will never allow to be realized — the same category of bug as `refundableAmountOf()` returning nonzero for non-cancelable streams.

  public long queryReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return 0;
    }

    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (accountCapsule == null) {
      return 0;
    }
    if (beginCycle > currentCycle) {
      return accountCapsule.getAllowance();
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      return reward + accountCapsule.getAllowance();
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
    }
    return reward + accountCapsule.getAllowance();
  }
