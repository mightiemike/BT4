Investigation summary: `types/src/transaction/change_set.rs::ChangeSet::empty()` is a distinct, standalone type (a plain `write_set: WriteSet` + `events: Vec<ContractEvent>` struct) from the `VMChangeSet` used by the actual VM execution pipeline (`aptos-move/aptos-vm-types/src/change_set.rs`) [1](#0-0) . Searching the codebase, this specific `ChangeSet::empty()` constructor is called only once, in a test file (`aptos-move/e2e-testsuite/src/tests/genesis.rs`), and is not wired into any replay, restore, executor, or storage-commit code path [2](#0-1) .

The type it constructs (`types::transaction::ChangeSet`) is only consumed as the payload of `WriteSetPayload::Direct(...)`, which is exclusively used for privileged writeset/genesis transactions (`aptos-move/aptos-vm/src/aptos_vm.rs::execute_write_set`, `aptos-move/vm-genesis/src/lib.rs`) [3](#0-2) . That path is not reachable from unprivileged transaction, package, API, view, bytecode, or proof input — it requires a trusted writeset transaction constructed by governance/operators, which is out of scope per the review's decision standard (excludes trusted-operator-only paths).

The real VM execution and replay/restore pipelines use `VMChangeSet` and `VMOutput`, not this `ChangeSet` type. `VMChangeSet::empty()` is used correctly only in contexts that are genuinely empty by construction — e.g., initializing a fresh session in `PrologueSession::new` before any writes occur [4](#0-3) , `VMOutput::empty_with_status` for discarded/failed transactions where no state should be committed [5](#0-4) , and no-op block metadata/epilogue handling in the benchmark native VM [6](#0-5) . None of these substitute an empty change set for a genuinely non-trivial computed result — they are all legitimate "nothing happened" cases (discarded transactions, block metadata, or fresh session initialization before execution).

No code path was found where a transaction that legitimately produces writes falls through to `ChangeSet::empty()` (or `VMChangeSet::empty()`) and gets committed to storage or used to derive a `TransactionInfo` state root, so the proposed divergence between the VM-derived root and the committed root does not have a demonstrable trigger in this codebase.
