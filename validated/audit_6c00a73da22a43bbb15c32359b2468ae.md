### Title
L1 handler transactions marked `rejected` by `L1EventsProvider::commit_block` are permanently excluded and can never be re-processed - (File: `crates/apollo_l1_events/src/l1_events_provider.rs`)

### Summary
`L1EventsProvider::apply_commit_block` routes any L1-handler transaction whose block-level execution failed into a permanent `rejected` bucket inside `TransactionManager`. Once there, re-scraped `Event::L1HandlerTransaction` events for the same hash are silently dropped by `add_events`, and there is no code path that ever moves a transaction out of the `rejected` state back into `Pending`/proposable. This mirrors the `TelcoinDistributor::challengeTransaction()` pattern: a flag is set (`challenged` there, "rejected" here) that blocks the item forever, with no release mechanism.

### Finding Description
`apply_commit_block` computes `rejected_and_consumed` as the intersection of the batcher's `rejected_tx_hashes` (any transaction whose execution returned `Err`, see `collect_execution_results_and_stream_txs`) and `consumed_txs`, then calls `self.tx_manager.commit_txs(&committed_txs, &rejected_and_consumed)`: [1](#0-0) 

`collect_execution_results_and_stream_txs` in the batcher adds a transaction hash to `rejected_tx_hashes` whenever its execution result is `Err`, regardless of the concrete reason (this includes non-malicious execution failures, e.g. resource limits, temporary account/contract state issues, or block-full pruning at execution time): [2](#0-1) 

Once a hash lands in the provider's `rejected` bucket, `add_events` (invoked every time the scraper re-observes the same on-chain `LogMessageToL2` event, e.g. during node restart/resync) does not re-insert or reset it — confirmed by the dedicated regression test: [3](#0-2) 

The snapshot exposes a distinct terminal `rejected_transactions` set separate from `committed_transactions` and the proposable pool, confirming this is a persistent classification, not a transient status: [4](#0-3) 

No function in `L1EventsProvider` (`start_block`, `get_txs`, `validate`, `commit_block`, `apply_commit_block`) reads from or clears the `rejected` set to re-admit a transaction. The design documentation even states the intended behavior should be different ("For rejected txs: Unstage, keep as Pending"), suggesting the implementation diverges from the intended retry semantics: [5](#0-4) 

### Impact Explanation
L1-handler transactions originate from a permissionless L1 message sender (e.g., a bridge deposit or any contract call from L1 to L2 via `sendMessageToL2`). This message is not attacker-controlled by the sequencer operator — any user can trigger this path simply by sending a message that later fails execution on L2 for a reason unrelated to fund legitimacy (e.g., transient gas/resource exhaustion during block building, an account nonce race, or any other execution error). Once such a message is included in a proposed block and its execution errors, the corresponding transaction hash is permanently placed in the `rejected` bucket and will never be retried, proposed, or validated again — even though the L1 message itself was never consumed on L2. Since the L2 side of the bridging/message flow never completes and the transaction can never be resubmitted (the L1 message hash is used as the deduplication key), user funds bridged via that message are permanently frozen, matching the "permanent freezing of funds" criterion.

### Likelihood Explanation
Any transient or non-malicious execution failure of an L1-handler transaction (bouncer/resource pressure, incidental account-state race, or any other `Err` result surfaced during block building) is sufficient to trigger this path — it does not require a malicious operator, prover, or peer, only a normal execution failure for a legitimately-sent L1 message. Given that execution failures of L1-handler transactions are a foreseeable, ordinary occurrence (not necessarily attacker-induced), the likelihood of this state being reached in production is non-negligible.

### Recommendation
Add a mechanism to retry or reclassify `rejected` L1-handler transactions: either move them back into the proposable/pending pool (consistent with the documented intent in `06-l1-handler-flow.md`), or explicitly surface them so the L1 message can be legitimately cancelled/refunded via the existing cancellation timelock flow. At minimum, `add_events` should not silently discard re-scraped events for transactions sitting in the `rejected` bucket without providing any path back to execution or cancellation.

### Proof of Concept
1. An L1 message sender calls the L1 `sendMessageToL2` (or equivalent) function to bridge funds/trigger a call to L2 — this creates an `L1HandlerTransaction` picked up by the scraper and added via `L1EventsProvider::add_events`.
2. The batcher proposes a block including this L1-handler transaction. During execution, the transaction's execution returns `Err` (e.g., due to resource exhaustion or any transient failure) — `collect_execution_results_and_stream_txs` inserts its hash into `rejected_tx_hashes` (`crates/apollo_batcher/src/block_builder.rs:708-716`).
3. The batcher commits the block via `Batcher::commit_proposal_and_block`, forwarding `rejected_tx_hashes` filtered to L1-handler hashes to `L1EventsProviderClient::commit_block` (`crates/apollo_batcher/src/batcher.rs:1182-1191`).
4. `L1EventsProvider::apply_commit_block` classifies the hash as rejected and consumed, moving it permanently into `tx_manager`'s `rejected` state (`crates/apollo_l1_events/src/l1_events_provider.rs:370-381`).
5. Even if the scraper re-observes the same `LogMessageToL2` event on a later poll (e.g., after node restart), `add_events` does not restore the transaction to the proposable pool — as demonstrated by `add_new_transaction_not_added_if_rejected` (`crates/apollo_l1_events/src/l1_events_provider_tests.rs:576-598`).
6. Result: the L1 message's corresponding L2 side effect (fund credit/contract call) never executes, and no mechanism exists to retry it, permanently freezing the associated value.

Note: I was unable to directly inspect `crates/apollo_l1_events/src/transaction_manager.rs` (the `commit_txs`/`add_tx` implementation) due to running out of tool-call budget, so the exact internal state machine transitions for the `rejected` bucket are inferred from the provider-level tests and snapshot fields rather than verified line-by-line in that file. If a hidden retry path exists there, it would need to be checked to fully confirm permanence.

    /// Commit the given transactions, and increment the current height.
    fn apply_commit_block(
        &mut self,
        consumed_txs: IndexSet<TransactionHash>,
        rejected_txs: IndexSet<TransactionHash>,
    ) {
        debug!("Applying commit_block to height: {}", self.current_height);
        let (rejected_and_consumed, committed_txs): (Vec<_>, Vec<_>) =
            consumed_txs.iter().copied().partition(|tx| rejected_txs.contains(tx));
        self.tx_manager.commit_txs(&committed_txs, &rejected_and_consumed);

        self.current_height = self.current_height.unchecked_next();
    }

#[test]
fn add_new_transaction_not_added_if_rejected() {
    // Setup.
    let rejected_tx_id: TransactionHash = tx_hash!(1);
    let mut l1_events_provider = setup_rejected_transactions();

    // Add a new transaction that is already in the rejected set.
    l1_events_provider.add_events(vec![l1_handler_event(rejected_tx_id)]).unwrap();

    // Ensure that the rejected transaction is not re-added to the provider.
    let expected_l1_events_provider = L1EventsProviderContentBuilder::new()
        .with_txs([l1_handler(3)])
        .with_rejected([l1_handler(1)])
        .with_committed([l1_handler(2)])
        .with_height(BlockNumber(1))
        .build();
    expected_l1_events_provider.assert_eq(&l1_events_provider);

    // Ensure that the rejected transaction is not re-added to the provider, even if it is staged.
    l1_events_provider.validate(rejected_tx_id, BlockNumber(1)).unwrap();
    l1_events_provider.add_events(vec![l1_handler_event(rejected_tx_id)]).unwrap();
    expected_l1_events_provider.assert_eq(&l1_events_provider);
}
