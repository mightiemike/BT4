## Analysis

The requested bug class — unbounded recursion over attacker-influenced nested/chained data causing a stack overflow DoS (CVE-2022-38750 in SnakeYAML) — has a direct structural analog in nearcore's transaction-outcome assembly path, reachable by any unprivileged RPC caller.

### Title
Unbounded recursion in `get_recursive_transaction_results` causes stack-overflow crash on `tx`/`tx_status` JSON-RPC queries - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` walks the receipt-outcome DAG produced by a transaction by recursing once per `receipt_id`, with no depth limit and no iterative/queue-based fallback. [1](#0-0) 
It is invoked from both `get_final_transaction_result` and `get_partial_transaction_result_option`. [2](#0-1) [3](#0-2) 

### Finding Description
`ViewClientActor::get_tx_status` calls `get_partial_transaction_result_option` directly when the node tracks the relevant shard. [4](#0-3) 
This is wired to the `TxStatusRequest` handler and, through the JSON-RPC layer, to the public `tx` and `tx_status` (and `EXPERIMENTAL_tx_status`) methods. [5](#0-4) [6](#0-5) 

Any unprivileged RPC caller can submit a single transaction whose `FunctionCall` actions create a long, linear chain of cross-contract-call receipts (each receipt producing exactly one child `receipt_id`, e.g. a self-recursive promise/callback pattern). Since the aggregate gas across the whole receipt chain is bounded only by the 300 Tgas per-transaction cap and per-hop overhead can be a small fraction of that, the resulting chain can have many thousands of hops. Once any of these receipts execute and the node persists their outcomes, querying `tx`/`tx_status` for the *original* transaction hash causes `get_recursive_transaction_results` to recurse once per hop in the chain with no depth guard, unlike other trie-walking code in the codebase that explicitly avoids recursion "to avoid any potential stack overflows" [7](#0-6) 
or other lookup paths that enforce an explicit `MAX_DEPTH` [8](#0-7) 
This function has neither protection.

### Impact Explanation
A Rust stack overflow (as opposed to a catchable panic) triggers a guard-page fault that aborts the whole process; it cannot be caught by `catch_unwind`. `ViewClientActor` is a shared multithread actor within the node process [9](#0-8) 
so a crash here brings down the entire node — including validators that also expose or internally use the same `Chain`/view-client code paths for `tx_status` polling during transaction submission (`send_tx_commit`). [10](#0-9) 
This is a transaction-triggered halt reachable from a single unprivileged submitted transaction plus a follow-up RPC query, matching the required "Validate" bar (transaction-triggered halt / no-impact-only bugs are excluded, but this is a concrete crash primitive).

### Likelihood Explanation
Likelihood is moderate-to-high: constructing a contract that recursively calls itself via promises (well-known pattern, exercised already in `test_evil_deep_recursion` for the WASM call-stack case) [11](#0-10) 
is straightforward and only requires deploying one contract and sending one transaction with sufficient attached gas, then calling the standard `tx`/`tx_status` RPC method — no special privileges, validator status, or node cooperation needed.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative, worklist/queue-based traversal (as already done in `trie_recording.rs`'s `get_subtree_size`), and/or impose an explicit maximum depth (mirroring the `MAX_DEPTH` pattern used for `ReceiptToTx` lookups) that fails gracefully with a bounded error instead of recursing arbitrarily deep.

### Proof of Concept
1. Deploy a contract whose method `A` issues a `FunctionCall` promise back to itself (or to a chain of accounts A→B→A→B…) with the remaining attached gas, minus per-hop overhead, repeated until gas is exhausted (near the 300 Tgas cap, using minimal per-hop gas cost to maximize hop count).
2. Submit one transaction invoking `A` with `MAX_GAS`; let the resulting receipt chain execute across blocks.
3. Call the `tx` or `tx_status` JSON-RPC method with the original transaction hash and signer account id.
4. `ViewClientActor::get_tx_status` → `Chain::get_partial_transaction_result_option` → `get_recursive_transaction_results` recurses once per receipt in the chain, exhausting the actor thread's stack and aborting the node process.

    pub fn get_partial_transaction_result_option(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<Option<FinalExecutionOutcomeView>, Error> {
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));

        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, false)?;
        if outcomes.is_empty() {
            // The transaction is in the store (included in a chunk) but its execution outcome has
            // not been recorded yet, so there is no result to assemble.
            return Ok(None);
        }

        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(Some(FinalExecutionOutcomeView {
            status,
            transaction,
            transaction_outcome,
            receipts_outcome,
        }))
    }
