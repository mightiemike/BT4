### Title
Cross-tenant webhook forgery via unauthenticated `X-Shopify-Shop-Domain` header not covered by HMAC signature - (File: packages/apps/shopify-api/lib/webhooks/process.ts)

### Summary
`callWebhookHandlers` passes `webhookCheck.domain` — sourced directly from the unauthenticated `X-Shopify-Shop-Domain` header — into `handler.callback` as the `shop_domain` argument, relying solely on webhook HMAC validation as proof of authenticity. However, the HMAC computed in `validateHmacFromRequestFactory` is calculated only over `rawBody`, never over the domain header, so the header can be freely modified on any HMAC-valid request without invalidating the signature.

### Finding Description
`validateFactory` (`packages/apps/shopify-api/lib/webhooks/validate.ts`) calls `validateHmacFromRequestFactory` which computes `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — the local HMAC is derived exclusively from `rawBody` and `config.apiSecretKey`, per [1](#0-0) . No header, including `X-Shopify-Shop-Domain`, is included in the signed material. After HMAC succeeds, `checkWebhooksHeaders` simply reads the `domain` header as-is and returns it as a trusted field [2](#0-1) . `callWebhookHandlers` then forwards this unauthenticated value straight into the app-supplied `handler.callback` as `shop_domain` [3](#0-2) , with no cross-check against any session-storage record or the shop that the app secret actually belongs to.

An attacker who can obtain any single valid `(rawBody, HMAC)` pair signed with the app's shared `apiSecretKey` — which is trivial to do by installing the target app on their own store and triggering/observing one webhook delivery to themselves — can replay that exact body and HMAC header while substituting an arbitrary victim shop domain in `X-Shopify-Shop-Domain`. The HMAC check passes because it never examined that header, and `callWebhookHandlers` hands the forged domain to the app's handler as if it were verified.

### Impact Explanation
This breaks the confused-deputy boundary the library implicitly promises: passing a value literally sourced from an unauthenticated header to app code under the same trust umbrella as the HMAC-validated body invites exactly the integration pattern described (keying session-storage reads/writes by `shop_domain`). Concretely this enables cross-tenant session storage corruption/overwrite or state confusion in any app whose webhook handler uses the callback's `shop_domain` parameter to look up or write per-shop state, without the library providing any binding between the cryptographic proof and the domain claim.

### Likelihood Explanation
The attacker needs only to be an unprivileged actor able to install the target app on any store (including their own free/dev store) — no leaked secret, no MITM, no privileged role is required. Capturing one's own outbound webhook request (body + `X-Shopify-Shop-Domain-`independent HMAC) and replaying it with a modified domain header is straightforward and fully repeatable for any topic the attacker can trigger on their own shop.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` as authenticated. Either bind the domain into the signed payload before comparison, or require host apps to independently verify the domain matches an actual installed/active session for that shop (via a session-storage lookup keyed by an already-trusted identifier) before using it for any storage read/write, and document this trust boundary explicitly in `WebhookValidationValid`/`callWebhookHandlers`.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/webhooks/__tests__/process-domain-forge.test.ts
import {createSHA256HMAC} from '../../../runtime/crypto';
import {HashFormat} from '../../../runtime/crypto/types';

test('forged X-Shopify-Shop-Domain header passes HMAC validation', async () => {
  const rawBody = '{"id":123}';
  const hmac = await createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64);

  // Legit request from attacker's own shop
  const legitHeaders = {
    'X-Shopify-Hmac-Sha256': hmac,
    'X-Shopify-Topic': 'products/create',
    'X-Shopify-Shop-Domain': 'attacker-shop.myshopify.com',
    'X-Shopify-Api-Version': '2024-01',
    'X-Shopify-Webhook-Id': 'abc',
  };

  // Replay with victim domain, same body/HMAC
  const forgedHeaders = {...legitHeaders, 'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com'};

  const result = await validateFactory(config)({rawBody, headers: forgedHeaders});
  expect(result.valid).toBe(true);
  expect((result as any).domain).toBe('victim-shop.myshopify.com'); // forged domain accepted
});
```
This demonstrates that `handler.callback` in `callWebhookHandlers` will receive `victim-shop.myshopify.com` as `shop_domain` despite the request never having been sent by or on behalf of that shop.
