I have enough information now to write the final analog analysis. The confirmed root cause chain: `DelegateResourceActuator.delegateResource()` (or the TVM `DelegateResourceProcessor`) lets any account create an unbounded number of `DelegatedResourceAccountIndex` entries under a single owner address via repeated `DelegateResourceContract` broadcasts to distinct receiver addresses, and `DelegatedResourceAccountIndexStore.getWithPrefix()` / `getV2Index()` unboundedly iterates (`prefixQuery`) all such entries whenever the account's delegation index is queried via the public RPC/HTTP endpoints `getDelegatedResourceAccountIndex(V2)`.

### Title
Unbounded growth and iteration of `DelegatedResourceAccountIndex` entries enables RPC/state-read DoS - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
Any anonymous account can call `DelegateResourceContract` (via `DelegateResourceActuator`/`DelegateResourceProcessor`) repeatedly, delegating tiny amounts (≥1 TRX) to an unbounded number of distinct receiver addresses. Each delegation creates new, permanent index entries (`V2_FROM_PREFIX`/`V2_TO_PREFIX` keyed rows) with no cap on how many receivers/senders an address may accumulate. The public read APIs `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`, exposed over gRPC and HTTP without authentication, then perform an unbounded `prefixQuery` scan and sort over every entry for that address on every call.

### Finding Description
`DelegateResourceActuator.delegateResource()` calls `delegatedResourceAccountIndexStore.delegate()`/`delegateV2()` unconditionally for every unique `(owner, receiver)` pair, with no maximum on the number of distinct receivers/senders an address can accumulate. [1](#0-0) 
The equivalent TVM-reachable path, `DelegateResourceProcessor.delegateResource()`, does the same via `repo.updateDelegatedResourceAccountIndex()`. [2](#0-1) 
Each of these entries is stored as an independent key under `V2_FROM_PREFIX`/`V2_TO_PREFIX`, and `DelegatedResourceAccountIndexStore.getWithPrefix()` performs an unbounded `prefixQuery` and in-memory sort over *all* matching entries for the target address: [3](#0-2) 
This method is invoked directly from `Wallet.getDelegatedResourceAccountIndex(V2)`, which is wired into unauthenticated gRPC (`RpcApiService`) and HTTP servlets (`GetDelegatedResourceAccountIndexServlet`, `GetDelegatedResourceAccountIndexV2Servlet`) as well as their Solidity/PBFT node mirrors: [4](#0-3) [5](#0-4) [6](#0-5) 
The legacy (pre-optimization) code path is worse: while `supportAllowDelegateOptimization` is disabled, `FreezeBalanceActuator.delegateResource()` loads the entire `toAccountsList`/`fromAccountsList` array, does an O(n) `List.contains`/`add`, and rewrites the whole growing protobuf array on every single delegate/unfreeze call: [7](#0-6) 
This is the direct analog of the reported bug class: unbounded arrays/lists that grow from user-controlled input and are iterated in full on every subsequent operation or read, exactly like the `OmoVault.totalAssets()`/`removeAgent`/`_removeTokenAddress` pattern.

### Impact Explanation
An attacker who controls or funds one address can broadcast many cheap `DelegateResourceContract` transactions to distinct freshly created receiver addresses (minimum 1 TRX each), building an arbitrarily large delegation index for that single address. Subsequent calls to `getDelegatedResourceAccountIndex(V2)` for that address force the full node to scan, sort, and serialize the entire unbounded set on every RPC/HTTP request — this is reachable by any anonymous caller and can be repeated to degrade full-node/gRPC-service responsiveness (denial of service on node RPC/HTTP layer). It also increases per-block state-transition cost in `delegateResource()`/`FreezeBalanceActuator` for legacy mode, growing linearly with each new delegation.

### Likelihood Explanation
Likelihood is Medium: creating many receiver addresses and issuing many small `DelegateResourceContract`/`FreezeBalanceContract` (legacy) transactions costs only the minimum 1 TRX delegate balance and normal transaction fees/bandwidth, with no other limiting parameter (e.g., no `MAX_DELEGATE_RECEIVERS`-style cap analogous to `MAX_VOTE_NUMBER` used in `VoteWitnessActuator`). The read-side RPC/HTTP endpoints require no authentication or privilege.

### Recommendation
- Cap the number of distinct delegation relationships (`to`/`from` accounts) an address can accumulate, similar to `MAX_VOTE_NUMBER` enforced in `VoteWitnessActuator.validate()`.
- Add pagination/limit parameters to `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` and to `DelegatedResourceAccountIndexStore.getWithPrefix()`'s `prefixQuery`, instead of returning/sorting the full unbounded set.
- For the legacy non-optimized code path in `FreezeBalanceActuator.delegateResource()`, avoid loading and rewriting the entire `toAccountsList`/`fromAccountsList` on each call, or force migration to the prefix-keyed model universally.

### Proof of Concept
1. Fund an address `A`.
2. Repeat N times (N large, e.g., 100,000): generate a fresh receiver address `Ri`, fund it minimally, then broadcast `DelegateResourceContract{owner=A, receiver=Ri, balance=1_000_000 (1 TRX), resource=BANDWIDTH}` from `A` (requires `A` to have ≥1 TRX frozen V2 balance per delegation, achievable by freezing once and delegating tiny slices repeatedly if allowed, or freezing minimal amounts per iteration).
3. Each successful delegation adds a new `V2_FROM_PREFIX`/`V2_TO_PREFIX` row via `DelegatedResourceAccountIndexStore.delegateV2()`.
4. Call the public gRPC/HTTP endpoint `getDelegatedResourceAccountIndexV2(A)` (e.g., via `GetDelegatedResourceAccountIndexV2Servlet`) repeatedly.
5. Observe the full node performing an unbounded `prefixQuery` + sort over all N entries on every request, with response latency and node CPU/I/O usage growing linearly with N, degrading the shared RPC/HTTP service for all other API consumers.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
