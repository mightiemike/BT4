### Title
Webhook `domain` header is not HMAC-authenticated, enabling cross-tenant session hijack via replayed genuine webhook body - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
`validateFactory`'s `validate()` only verifies the HMAC over `rawBody` using `validateHmacFromRequestFactory`; it never binds the `X-Shopify-Shop-Domain` header (or any other header) into that signature. `checkWebhooksHeaders`/`checkEventsHeaders` then read the unauthenticated `domain` header and return it as `valid: true` output, which downstream consumers such as `authenticateWebhookFactory` use to look up the offline session/access token for API calls.

### Finding Description
In `validateFactory` (`packages/apps/shopify-api/lib/webhooks/validate.ts`, lines 46-75), the only cryptographic check performed is `validateHmacFromRequestFactory(config)({type: HmacValidationType.Webhook, rawBody, webhookType, ...adapterArgs})`, which computes an HMAC over `rawBody` and compares it to the `X-Shopify-Hmac-Sha256` header. Once that succeeds, `checkWebhookHeaders` dispatches to `checkWebhooksHeaders`/`checkEventsHeaders` (lines 99-204), which pull `domain`, `topic`, `apiVersion`, `webhookId`, etc. straight from request headers via `getRequiredHeader`/`getHeader` with zero validation against the signed body or against any known-shop allowlist, and return them as part of the `valid: true` result object (`fields.domain = domain!`). [1](#0-0) [2](#0-1) 

This unauthenticated `domain` is then consumed by `authenticateWebhookFactory` (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`), which calls `ensureValidOfflineSession(params, check.domain)` to resolve and return that shop's offline session and construct an admin API client scoped to it. [3](#0-2) 

Because a valid HMAC only proves the request body was generated with the app's shared secret at some point (i.e., it was a genuine webhook for *some* shop using this app), and does not prove which shop it was for, an attacker who owns shop A can capture a real webhook (rawBody + HMAC) delivered to their own endpoint and replay it to the app's webhook endpoint with `X-Shopify-Shop-Domain` rewritten to `victim-shop.myshopify.com`. `validate()` returns `valid:true` with `domain: 'victim-shop.myshopify.com'` because the HMAC check passes independent of the domain header. The consuming app code (`process()`/`authenticateWebhookFactory`) then attributes the payload/topic to shop B, loading shop B's session/access token and invoking the shop-B-scoped handler with attacker-controlled body content.

### Impact Explanation
This breaks tenant isolation for any app relying solely on `webhooks.validate()`/`authenticateWebhookFactory` from this library: an attacker can inject arbitrary "genuine-looking" webhook payloads (of a topic they can trigger for their own store, e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) under the identity of any other merchant shop known to the attacker, as long as the app's webhook handler trusts `domain`/`shop` for authorization or data attribution. Depending on the handler logic, this can cause cross-tenant data corruption, spoofed compliance/GDPR webhooks, or forged business events attributed to a victim shop. This matches Shopify's bounty class of cross-tenant data/state access via forged webhook acceptance.

### Likelihood Explanation
The attacker only needs to be an unprivileged merchant who owns their own shop and can install the target app on it — a routine and cheap precondition. They can capture their own legitimate webhook deliveries (body + valid HMAC) via a controlled receiving endpoint or proxy, then replay that exact body/HMAC pair to the app's public webhook URL while forging the `X-Shopify-Shop-Domain` header, which is fully attacker-controlled in the HTTP request. No secret, no privileged role, and no non-default configuration are required — this is inherent to how `validateFactory` in this library performs verification.

### Recommendation
Do not implicitly trust the `domain`/`X-Shopify-Shop-Domain` header for session or tenant attribution purely on the basis of a body-only HMAC check. At minimum, the library or consuming app should cross-check that the resolved shop from the `domain` header corresponds to a shop for which the app has legitimate installed state (which `ensureValidOfflineSession` does implicitly reject if no session exists for a domain never installed) — but for a shop that IS installed by the attacker's own store and also matches a victim domain string convincingly, this doesn't fully protect against topic-content confusion for shops both installed. Recommend documenting explicitly that `domain` is unauthenticated and that webhook handler code must not use payload content to imply trust beyond the resolved installed shop, and/or track webhook idempotency/shop binding via `webhookId` plus out-of-band verification (e.g., re-fetching the resource via the Admin API using the resolved shop's own access token rather than trusting body content for sensitive fields).

  const secret = config.apiSecretKey; // attacker does NOT know this in general,
  // but they don't need to: they reuse a genuine hmac captured from their OWN shop's webhook.
  const genuineHmac = createHmac('sha256', secret).update(rawBody).digest('base64');

        'X-Shopify-Api-Version': '2024-01',
        'X-Shopify-Webhook-Id': 'attacker-controlled-id',
      },
    }),
  });

  expect(result.valid).toBe(true);
