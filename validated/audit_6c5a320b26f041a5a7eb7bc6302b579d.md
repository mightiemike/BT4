### Title
`ExchangeInjectActuator` computes proportional deposit amounts from manipulable pool spot ratio with no slippage protection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The `ExchangeInjectActuator` calculates how much of the "other" token must be pulled from an exchange creator's balance by reading the *current* (spot) reserve ratio of the `Exchange`/`ExchangeV2` pool at execution time, with no way for the caller to bound that amount. Because the pool's spot ratio can be moved arbitrarily by any unprivileged account issuing an `ExchangeTransactionContract` swap immediately beforehand, an attacker can force a pending `ExchangeInjectContract` to debit far more of the paired token than the creator intended — the exact same "spot-price-used-for-liquidity-minting-without-slippage-check" root cause described in the Panoptic `deployNewPool` report.

### Finding Description
`ExchangeInjectActuator.doValidate`/`execute` derive `anotherTokenQuant` directly from the exchange's *live* `firstTokenBalance`/`secondTokenBalance` (the AMM's spot price), using a simple proportional formula: [1](#0-0) 

This mirrors exactly how `PanopticFactory.deployNewPool` reads `v3Pool.slot0()` spot price to size the liquidity to mint — both use an on-chain, freely-tradable spot ratio, taken at transaction-execution time, as the sole input for computing how much of a paired asset a caller must supply.

Unlike `ExchangeTransactionContract`, which includes an `expected` field acting as a slippage/minimum-output guard (checked in `ExchangeTransactionActuator`): [2](#0-1) 

`ExchangeInjectContract` (and `ExchangeWithdrawContract`) carry only `token_id` and `quant` — there is no maximum/expected bound on the computed `anotherTokenQuant`: [3](#0-2) 

The pool's reserves are freely tradable by any account through `ExchangeTransactionActuator`, which directly mutates `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction`: [4](#0-3) 

Because the ratio that `ExchangeInjectActuator` will use is only fixed at the moment the inject transaction is processed by a block-producing witness — not when the creator signs/broadcasts it — an attacker who observes a pending `ExchangeInjectContract` in the mempool can broadcast (and, given witness-controlled ordering, have included ahead of it) an `ExchangeTransactionContract` swap that skews the ratio, then reverse the swap afterward. The creator's inject transaction executes against the manipulated ratio, forcing them to debit an amount of the paired token far in excess (or deficit) of what they intended, with no `expected`/limit parameter to reject the unfavorable outcome. `ExchangeWithdrawActuator` has an analogous "Not precise enough" tolerance check but likewise no caller-supplied bound on `anotherTokenQuant`.

### Impact Explanation
This is a direct, unprivileged accounting/settlement impact: an exchange creator's `ExchangeInjectContract` can be economically sandwiched, causing them to transfer more of a paired token (TRX or TRC-10 asset) into the pool than they intended, resulting in a real balance loss enforced by on-chain state transition rules — the same class of loss described as the Panoptic finding's "sandwiched leading to a significant loss" scenario. The loss is bounded by the size of the injector's balance/exchange balance limit (`getExchangeBalanceLimit`), but is fully realizable without any privileged access, using only standard `ExchangeTransactionContract` calls available to any account.

### Likelihood Explanation
Exploitability requires only the ability to observe a pending `ExchangeInjectContract` and to get an `ExchangeTransactionContract` swap ordered immediately before it (and typically reversed after) — both are ordinary, permissionless operations already exposed via the `ExchangeCreate`/`Inject`/`Transaction` RPCs. This mirrors the real-world condition Panoptic's judges accepted as valid (Medium severity): it primarily threatens users who grant broad/implicit trust in the computed ratio and do not manually verify the resulting debit before signing, which is realistic for anyone injecting liquidity into an existing TRON internal exchange pool.

### Recommendation
Add a caller-specified bound (e.g., a `max_another_token_quant` or `expected`-style field, analogous to `ExchangeTransactionContract.expected`) to `ExchangeInjectContract` (and `ExchangeWithdrawContract`), and have `ExchangeInjectActuator`/`ExchangeWithdrawActuator` reject execution when the computed `anotherTokenQuant` exceeds (or falls below) the caller's supplied limit, instead of relying purely on the spot ratio at execution time.

### Proof of Concept
1. Attacker monitors the mempool/pending transactions for an `ExchangeInjectContract` from a known exchange creator specifying `token_id = A`, `quant = X`.
2. Attacker submits an `ExchangeTransactionContract` swap (large sell of token B for token A, or vice versa) designed to skew `firstTokenBalance`/`secondTokenBalance` unfavorably relative to what the creator expects, per [5](#0-4) .
3. This swap is ordered ahead of the creator's inject transaction; when the creator's `ExchangeInjectContract` executes, `anotherTokenQuant` is computed against the now-skewed ratio in [6](#0-5) , debiting far more of token B from the creator than intended.
4. Attacker reverses their swap afterward, restoring the pool ratio and pocketing the excess token B debited from the creator, with no on-chain check available to the creator to have prevented or bounded this outcome.

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
