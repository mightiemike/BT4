### Title
Permissionless `ExchangeTransactionContract` calls allow front-running DoS of slippage-protected AMM trades - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator` lets **any** account trade against a bancor-style TRC10 exchange pool for a fee-level cost, with the only economic floor being `tokenQuant > 0` and the standard transaction fee. This mirrors the `addCredit()` bug class: a cheap, unrestricted, state-mutating call that can be broadcast ahead of another user's transaction to make that transaction's on-chain validation fail deterministically, causing a denial of service.

### Finding Description
`ExchangeTransactionActuator.doValidate()` only requires that the caller's account exists, has enough balance/asset for `tokenQuant`, and that the resulting swap output is `>=` the caller-supplied `tokenExpected`: [1](#0-0) 

Unlike `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, which require `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`: [2](#0-1) 

`ExchangeTransactionActuator` has **no such restriction** — any address can submit a trade against any pool, for any `tokenQuant >= 1`, moving the AMM's `firstTokenBalance`/`secondTokenBalance` ratio computed in `exchangeCapsule.transaction(...)`: [3](#0-2) 

A legitimate user computes `tokenExpected` (their slippage-protection floor) from the pool state visible when they build/sign their transaction, then broadcasts it. An attacker observing the pending transaction can front-run it with a minimal-cost trade (`tokenQuant=1` in the same direction, or in whatever direction most shifts the ratio) that changes `firstTokenBalance`/`secondTokenBalance` just enough that when the victim's transaction executes, `exchangeCapsule.transaction(...)` returns an `anotherTokenQuant` that is now `< tokenExpected`, triggering: [4](#0-3) 
This throws `ContractValidateException("token required must greater than expected")`, causing the victim's transaction to fail — the same "cheap permissionless state mutation used to invalidate another user's already-signed, hash/value-dependent validation" pattern described in the `addCredit()` report, just applied to the AMM pool's balance state instead of a `keccak256(lien)` hash.

### Impact Explanation
This is a griefing/DoS vector against any TRC10↔TRX or TRC10↔TRC10 exchange trade that uses `tokenExpected` for slippage protection. Repeated front-running can force victims to either drop slippage protection (exposing themselves to sandwich losses) or repeatedly retry trades, degrading usability of the exchange feature and burning victim fees on failed transactions. No funds are directly stolen by this specific path (the attacker's own trade still costs them real token/TRX per bancor math, unlike `addCredit()` which cost `1 wei`), so this is more constrained than the original High/Medium-rated finding, but it is a genuine unprivileged availability impact reachable from any broadcast transaction.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to observe a pending `ExchangeTransactionContract` in the mempool and front-run it with a cheaper-priority transaction (achievable via bandwidth/energy fee bidding, same mechanism as generic MEV front-running on TRON). Unlike `addCredit()`, the attacker cannot manipulate the pool for near-zero cost repeatedly at scale, since injecting a directional trade still moves real value and the attacker bears bancor-formula cost; sustained DoS is more expensive than the original report's `1 wei` griefing, which somewhat limits practical exploitation.

### Recommendation
- Consider adding a deadline/expiration parameter and/or a maximum acceptable slippage percentage rather than a raw absolute `tokenExpected`, and re-derive `tokenExpected` bounds using a TWAP-like sampling instead of raw spot balances to reduce single-block manipulation impact.
- Document that `tokenExpected` alone does not protect against front-running of the *validation call itself* (as opposed to just execution price), and evaluate whether a two-phase commit (submit intent, then execute) or Merkle-committed price bound would be appropriate for high-value swaps.
- This is a lower-severity, differently-shaped analog than the original High/Medium `addCredit()` finding (no near-zero-cost DoS primitive exists here), so treat as Low/Informational unless further primitives (e.g., a cheaper state-mutating call reachable by any address) are found that can move the AMM ratio at negligible cost.

### Proof of Concept
1. User A observes pool state and constructs `ExchangeTransactionContract{exchangeId, tokenId=X, quant=Q, expected=E}` where `E` is computed from the current `firstTokenBalance`/`secondTokenBalance`, then signs and broadcasts it.
2. Attacker B, monitoring the mempool, broadcasts `ExchangeTransactionContract{exchangeId, tokenId=X, quant=1}` (or any small quantity) with higher fee/priority so it executes first.
3. B's transaction succeeds via `ExchangeTransactionActuator.execute()`, updating `exchangeCapsule`'s balances through `Commons.putExchangeCapsule(...)`. [5](#0-4) 
4. When A's transaction is then validated against the now-mutated pool, `exchangeCapsule.transaction(...)` returns a lower `anotherTokenQuant`, which is `< E`, so `doValidate()` throws and A's transaction fails/reverts, at the cost of A's transaction fee.

**Uncertainty note:** I could not fully verify the exact fee (`calcFee()`) amount charged for `ExchangeTransactionContract` within the available index (the constant/config value wasn't resolved from the snippets retrieved), so the precise economic cost of repeated front-running by B is not confirmed here. A Devin session with full repo access could confirm the fee constant and any additional guard (e.g. minimum trade size) in `AbstractExchangeActuator`/`DynamicPropertiesStore` to more precisely bound the attacker's cost per DoS attempt.
