## Analog Found

### Title
Universal ("0u") account funds can be permanently frozen with no recovery path if the state-init producer's raw-byte serialization is inconsistent with the derived account ID - (File: `core/primitives/src/universal_state_init.rs`)

### Summary
NEAR's universal account scheme (NEP for `0u` accounts) derives an account's address directly from the SHA3-256 hash of the *exact raw bytes* of a `UniversalStateInit`/`RawStateInit` payload. Any unprivileged signer can fund such an address via a plain `Transfer`, creating an uninitialized account that holds a balance but has no code, keys, or data. The account can only ever leave the `Uninitialized` state by later submitting a `UniversalStateInit` action whose attached raw bytes hash to that exact address. If the off-chain producer/tooling that generated the original raw bytes (the "creation script" analog) is buggy, non-canonical, or the exact bytes are ever lost/regenerated differently, the resulting account can never be initialized — the funds are permanently stranded, mirroring the reported Keystore.sol issue where an incorrect commitment (`rootHash`) bricks the account with no recovery mechanism.

### Finding Description
The account ID for a `0u` account is defined as `derive_universal_account_id(raw)` = SHA3-256 over the exact raw bytes supplied, not over any canonical/typed re-encoding: [1](#0-0) 

The protocol accepts non-canonical borsh encodings when decoding (`from_raw`), but re-serializing a decoded value produces different (canonical) bytes and therefore a *different* derived account ID than the original input: [2](#0-1) [3](#0-2) 

The code's own documentation explicitly states the burden of consistency is pushed onto the off-chain producer: "Producers are responsible for serializing consistently" (`core/primitives/src/universal_state_init.rs:19`). This is architecturally identical to the reported bug class: an external creation script computes a commitment (there, `rootHash`; here, the SHA3-256 digest of raw bytes) that is used to derive/authorize an on-chain identity, and if that computation is wrong or not reproducible, the resulting account becomes permanently unusable.

Any account can be brought into existence in the `Uninitialized` state purely by an ordinary `Transfer` from any signer, with no state-init required at that point: [4](#0-3) 

Once uninitialized and funded, the account is stuck rejecting essentially every state-touching action until a matching state init arrives: [5](#0-4) 

If nobody ever holds/reproduces the exact byte sequence whose hash equals that address, the account can never leave the `Uninitialized` state, as explicitly acknowledged by the codebase's own test for genesis dump behavior on such accounts: "with no known state init, so the account can never leave the uninitialized state": [6](#0-5) 

There is no on-chain recovery mechanism defined anywhere in the `UniversalStateInit` action-handling path (`runtime/runtime/src/universal_account_id.rs`) for an account that is stuck uninitialized because the bytes that would unlock it were never correctly recorded or reproducibly generated.

### Impact Explanation
Funds transferred to a `0u` address whose derivation depended on a state-init byte sequence that is subsequently lost, regenerated differently (e.g., due to a tooling/serialization bug that produces non-canonical bytes, or a wallet/relayer bug that re-encodes the state init before computing the address a user is told to fund), are permanently frozen. There is no protocol-level path to recover them — the account can never transition out of `Uninitialized`, and per NEAR's preimage-resistant hash derivation, no alternate bytes can be substituted to unlock the same address. This matches the "permanently frozen funds" impact category explicitly accepted for this analysis, and is functionally identical to the reported Keystore bricking scenario (bad commitment → unusable account, no recovery).

### Likelihood Explanation
Reaching this state requires only unprivileged, ordinary transaction capabilities: any signer can `Transfer` to an arbitrary `0u` account id before it is initialized, and no special permission is needed to attempt (and fail) a `UniversalStateInit` with mismatched bytes. The risk is entirely dependent on off-chain tooling correctness (wallets, relayers, or scripts computing/serializing `RawStateInit`), exactly as the original report's risk depended on the correctness of an off-chain creation script. Given the codebase itself documents this as a producer responsibility rather than an enforced invariant, and demonstrates via its own tests that non-canonical byte handling silently changes the derived address, the failure mode is realistic in practice (e.g., a wallet computing the address from a typed/canonical struct but a user, relayer, or older client submitting a differently-serialized payload).

### Recommendation
Consider adding a recovery mechanism for `0u` accounts that remain `Uninitialized` after holding a balance for an extended period (e.g., a governance- or protocol-level fallback allowing the funds to be reclaimed by the original sender after a timeout), and/or provide stronger canonicalization guarantees/tooling so that address derivation and state-init submission cannot diverge. At minimum, document and provide reference implementations that guarantee producers always derive `0u` addresses from bytes they will reliably reproduce later, and add wallet/RPC-level warnings before transferring to an uninitialized `0u` account whose state-init bytes are not verified to be canonical/reproducible.

### Proof of Concept
1. A wallet or relayer tool constructs a `RawStateInit` for a new `0u` account, but serializes it via a hand-rolled or buggy encoder that produces valid-but-non-canonical borsh (e.g., unsorted `BTreeMap`/`BTreeSet` entries), as demonstrated to be accepted by `from_raw` in `core/primitives/src/universal_state_init.rs:251-274` and `276-289`.
2. The tool computes the account address from these non-canonical bytes via `derive_universal_account_id` and displays it to the user as the account to fund.
3. A user submits an ordinary `Transfer` to that address; per `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:276-282`), this creates the account in the `Uninitialized` state and credits the balance.
4. The original non-canonical raw bytes are lost (e.g., the tool only persisted/reused the canonical/typed form for later re-submission, or a different tool/version re-serializes the "same" logical state canonically).
5. Submitting the canonicalized `UniversalStateInit` bytes derives a *different* account id (per `from_raw_accepts_non_canonical_order` test, `core/primitives/src/universal_state_init.rs:252-273`, showing re-encoding differs from the original input), so the `UniversalStateInit` action's receiver check fails against the originally funded account — it can never be initialized, and its balance is permanently frozen, with no on-chain recovery mechanism, exactly as in the Keystore `rootHash` bricking scenario.

/// Returns the `0u` universal account ID defined by `state_init`: SHA3-256
/// (FIPS-202) over exactly those bytes, encoded with the UAID address codec.
///
/// **Note:** This function deliberately does not take `UniversalStateInit`, but
/// `RawStateInit`, because account ID is committed to the exact user-supplied bytes.
/// Re-serializing could yield a different ID, if `state_init` contained non-canonical
/// borsh representation.
pub fn derive_universal_account_id(state_init: &RawStateInit) -> AccountId {
    use sha3::Digest;
    let hash = sha3::Sha3_256::digest(&state_init.0).into();
    encode_universal_account_id(&hash)
}

    #[test]
    fn from_raw_accepts_non_canonical_order() {
        // Hand-build V1{code: None, data: {"b","a"} out of order, access_keys: {}}.
        // borsh writes map keys sorted, so this is a non-canonical encoding. It is
        // now accepted: borsh silently re-sorts on read (`de_strict_order` is off)
        // and we no longer reject non-canonical encodings. Re-serializing yields
        // the canonical bytes, which differ, so this input hashes to a different id.
        let mut bytes = vec![0u8]; // V1 discriminant
        bytes.push(0u8); // code: None
        bytes.extend_from_slice(&2u32.to_le_bytes()); // data: 2 entries
        for key in [b'b', b'a'] {
            bytes.extend_from_slice(&1u32.to_le_bytes()); // key len
            bytes.push(key);
            bytes.extend_from_slice(&0u32.to_le_bytes()); // value len 0
        }
        bytes.extend_from_slice(&0u32.to_le_bytes()); // access_keys: empty

        let decoded = UniversalStateInit::from_raw(&RawStateInit(bytes.clone())).unwrap();
        assert_eq!(
            decoded.data().keys().cloned().collect::<Vec<_>>(),
            vec![b"a".to_vec(), b"b".to_vec()],
        );
        assert_ne!(decoded.to_raw().0, bytes, "canonical re-encoding must differ from the input");
    }

/// An uninitialized account has no access keys, code or data, so every action
/// that needs a set-up account is refused with `AccountNotInitialized`, as an
/// action error rather than anything harsher. Without this an `AddKey` would
/// silently install a key the account id does not commit to, and a `Stake` or
/// `DeployContract` would reach a setter that an uninitialized account rejects.
#[test]
fn test_uninitialized_account_rejects_actions_needing_state() {
    init_test_logger();
    let mut env = Env::setup();

    let public_key = SecretKey::from_seed(KeyType::ED25519, "uaid-uninitialized").public_key();
    let state_init = UniversalStateInit::V1(UniversalStateInitV1 {
        code: None,
        data: BTreeMap::new(),
        access_keys: BTreeSet::from([PublicKeyHandle::from(public_key.clone())]),
    });
    let account = state_init.derive_account_id();

    // Funding the `0u` id creates the account without installing its state.
    env.transfer(&account, Balance::from_near(3));
    assert!(env.view_account(&account).amount > Balance::ZERO);

    let actions = [
        Action::AddKey(Box::new(AddKeyAction {
            public_key: public_key.clone(),
            access_key: AccessKey::full_access(),
        })),
        Action::Stake(Box::new(StakeAction { stake: Balance::from_near(1), public_key })),
        Action::DeployContract(DeployContractAction {
            code: near_test_contracts::trivial_contract().to_vec(),
        }),
        Action::FunctionCall(Box::new(FunctionCallAction {
            method_name: "log_something".to_owned(),
            args: vec![],
            gas: Gas::from_teragas(100),
            deposit: Balance::ZERO,
        })),
    ];

    for action in actions {
        let signer_id = env.user_account.clone();
        let signer = create_user_test_signer(&signer_id);
        let tx = SignedTransaction::from_actions(
            env.next_nonce(),
            signer_id,
            account.clone(),
            &signer,
            vec![action.clone()],
            env.block_hash(),
        );
        let outcome = env.env.rpc_runner().execute_tx(tx, Duration::seconds(5)).unwrap();
        let FinalExecutionStatus::Failure(TxExecutionError::ActionError(err)) = outcome.status
        else {
            panic!("expected an action error for {action:?}, got {:?}", outcome.status);
        };
        assert_eq!(
            err.kind,
            ActionErrorKind::AccountNotInitialized { account_id: account.clone() },
            "unexpected error for {action:?}",
        );
    }

    // The account is untouched: still uninitialized, still holding its balance.
    let view = env.view_account(&account);
    assert_eq!(view.amount, Balance::from_near(3));
    assert_eq!(view.code_hash, CryptoHash::default());
}
