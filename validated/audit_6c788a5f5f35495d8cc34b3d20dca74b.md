### Title
Receipt size validated before mutation allows oversized receipts to bypass `max_receipt_size`, breaking size-based protocol invariants - ([File: runtime/runtime/src/lib.rs])

### Summary
Analogous to CVE-2022-42252 (Tomcat accepting a request whose declared `Content-Length` no longer matches the body actually forwarded, enabling smuggling), nearcore's runtime validates a newly-created receipt's size against `max_receipt_size` *before* the receipt is mutated by appending `output_data_receivers`, so the check is bypassed and an over-limit receipt is admitted into consensus state exactly as a stale "declared length" can smuggle extra content past a validating proxy.

### Finding Description
`validate_receipt` in `ValidateReceiptMode::NewReceipt` computes `receipt_size = borsh::object_length(receipt)` and compares it to `limit_config.max_receipt_size` [1](#0-0) . This check runs in `apply_action_receipt` immediately after each action executes, over `new_result.new_receipts` [2](#0-1) . However, immediately afterward, when `action_receipt.output_data_receivers()` is non-empty and the action returned a `ReturnData::ReceiptIndex`, the runtime mutates the already-validated new receipt in place, appending `output_data_receivers` entries onto it — after the size check has already passed [3](#0-2) . This lets a receipt's serialized size grow past `max_receipt_size` without ever being re-checked.

The `ValidateReceiptMode::ExistingReceipt` path even documents this as a known, unfixed bug that the runtime must "handle gracefully" [4](#0-3) , and `try_forward` in congestion control explicitly clamps oversized-receipt sizes to `max_receipt_size` as a workaround, citing the same tracking issue [5](#0-4) . The nearcore test suite reproduces and documents exactly this bypass via `promise_return` and large `value_return` paths, referencing `https://github.com/near/nearcore/issues/12606` [6](#0-5) [7](#0-6) .

### Impact Explanation
`max_receipt_size` (4 MiB) is a hard protocol limit that the `ChunkStateWitness` size budget depends on for consensus soundness: the size-limits doc states the overall witness budget is engineered around each of these per-item hard limits [8](#0-7) . An unprivileged contract caller (any transaction signer able to deploy/call a contract that creates a promise chain and returns a large value/receipt index) can construct a receipt that is exactly at the size limit and then have it grow unboundedly past the limit via the `output_data_receivers` append, exactly reproducing the test scenarios `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`. This breaks the invariant `ChunkStateWitness` size accounting relies on, and is explicitly acknowledged to interact with cross-shard forwarding/congestion-control size accounting (`try_forward`), where the workaround (clamping) is itself an approximation, not a fix, of the true receipt size used in bandwidth/size budgeting [5](#0-4) .

### Likelihood Explanation
High reachability: any account holder can deploy a WASM contract and issue a single top-level transaction that creates a promise DAG culminating in a `promise_return`/large value return, driving the receipt over `max_receipt_size` post-validation — no privileged role, validator, or network position is required, matching the test harness's reproduction using only `SignedTransaction::call` from a funded account [9](#0-8) .

### Recommendation
Re-run `validate_receipt` (or at minimum re-check `borsh::object_length` against `max_receipt_size`) after `output_data_receivers` are appended to a newly created receipt in the block at `runtime/runtime/src/lib.rs:1152-1170`, before the receipt is committed to state, delayed queues, or outgoing buffers, so `ValidateReceiptMode::NewReceipt`'s guarantee actually holds at the point the receipt becomes durable. Track and resolve nearcore issue #12606 rather than continuing to patch around it in `try_forward`.

### Proof of Concept
Use the existing repro in `test-loop-tests/src/tests/max_receipt_size.rs::test_max_receipt_size_promise_return` (or `test_max_receipt_size_value_return`): deploy `near_test_contracts::rs_contract()`, then call `max_receipt_size_promise_return_method1` with `args_size` computed so the intermediate receipt lands exactly at `max_receipt_size` (4 194 304 bytes) before `output_data_receivers` are appended; `assert_oversized_receipt_occurred` confirms a receipt exceeding `max_receipt_size` is subsequently persisted/forwarded on chain [10](#0-9) .

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

**File:** docs/misc/state_witness_size_limits.md (L16-24)
```markdown
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
* `max_receipt_total_input_size - 4 MiB + 640 B`
  * Hard limit on the combined size of a receipt's resolved promise inputs (the `ReceivedData` referenced by its `input_data_ids`). Receipts which exceed it fail with `TotalPromiseInputSizeExceeded` without executing their actions.
  * These inputs are read before `per_receipt_storage_proof_size_limit` starts counting, so without this limit a single receipt could pull `max_number_input_data_dependencies * max_receipt_size` (128 * 4 MiB) into the witness.
  * The limit is `max_length_returned_data` (4 MiB) plus the worst-case per-input framing overhead (128 * 5 bytes), so 4 MiB of input data always fits no matter how it's split across data receipts.
* `combined_transactions_size_limit - 4 MiB`
  * Hard limit on total size of transactions from this and previous chunk. `ChunkStateWitness` contains transactions from two chunks, this limit applies to the sum of their sizes.
```
