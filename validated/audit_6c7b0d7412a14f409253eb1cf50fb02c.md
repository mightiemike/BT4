### Title
Off-by-one in `DelegateAction` expiry boundary allows execution at `max_block_height` — (`File: runtime/runtime/src/actions.rs`)

---

### Summary

`apply_delegate_action` uses a strict `>` comparison to check whether a `DelegateAction` has expired. Both the field-level documentation and the runtime spec state the action is valid only for blocks **below** `max_block_height`, meaning it must be rejected when `block_height >= max_block_height`. The code rejects only when `block_height > max_block_height`, leaving the boundary block (`block_height == max_block_height`) as an unguarded execution window. This is the nearcore analog of the external "equal-index direction ambiguity" bug class: a boundary-equality case is silently misclassified, producing the wrong outcome.

---

### Finding Description

In `apply_delegate_action`:

```rust
if apply_state.block_height > delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
``` [1](#0-0) 

The `DelegateAction` struct documents `max_block_height` as:

> "The maximal height of the block in the blockchain **below which** the given DelegateAction is valid." [2](#0-1) 

"Below which" means the action is valid for `block_height < max_block_height` and must be rejected for `block_height >= max_block_height`. The runtime spec reinforces this:

> "If the current block is **equal or greater than** `max_block_height`" → `DelegateActionExpired` [3](#0-2) 

The code uses `>` (strict), so when `block_height == max_block_height` the condition is `false` and the action proceeds to execution. The existing test suite confirms this is the live behavior — the happy-path test explicitly passes `block_height == max_block_height` and asserts success:

```rust
let apply_state = create_apply_state(signed_delegate_action.delegate_action.max_block_height);
// ...
assert!(result.result.is_ok(), ...);
``` [4](#0-3) 

The expiry test only covers `max_block_height + 1`, never the equal case:

```rust
let apply_state = create_apply_state(signed_delegate_action.delegate_action.max_block_height + 1);
``` [5](#0-4) 

The `DelegateActionExpired` error variant's own description also says "less than actual block height", which is consistent with `>=` being the correct guard: [6](#0-5) 

---

### Impact Explanation

A user signs a `DelegateAction` and sets `max_block_height = H` to bound the window in which a relayer may submit it. Per the documented semantics, the user believes the action is invalid at block H and beyond. The relayer, however, can hold the action and submit it at exactly block H. Because `H > H` is `false`, the runtime executes the action — transferring funds, calling a contract, or performing any other delegated operation — at a block height the user did not intend to authorize.

Concrete fund-loss path:
1. User signs a `DelegateAction` (e.g., 100 NEAR transfer) with `max_block_height = H`.
2. At block `H − 1` the user decides to cancel; they wait for block H, believing the action will then be expired.
3. The relayer submits at block H.
4. Runtime evaluates `H > H` → `false` → action executes.
5. 100 NEAR is transferred without the user's current consent.

This maps to the **transaction manipulation** and **unauthorized transaction** impact categories: a relayer executes a delegated action at a block height the signer explicitly excluded per the documented contract.

---

### Likelihood Explanation

Medium. The relayer controls submission timing and can trivially target block H. No privileged access, no network-level capability, and no validator collusion is required — only the ability to submit a transaction at a chosen block height, which any RPC-connected party can do. The user must have relied on the documented `>=` semantics (reasonable given the spec and field description), and the relayer must choose to exploit the one-block window rather than submit earlier.

---

### Recommendation

Change the comparison from strict `>` to `>=` to match the documented and specified semantics:

```rust
// Before (wrong — allows execution at max_block_height)
if apply_state.block_height > delegate_action.max_block_height() {

// After (correct — rejects at max_block_height per spec)
if apply_state.block_height >= delegate_action.max_block_height() {
``` [7](#0-6) 

Update the happy-path test to use `max_block_height - 1` as the valid boundary, and add a test asserting that `block_height == max_block_height` produces `DelegateActionExpired`.
