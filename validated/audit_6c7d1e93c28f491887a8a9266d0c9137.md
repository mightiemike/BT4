### Title
Exchange (Bancor-style) liquidity Inject/Withdraw compute counterpart amount from live pool ratio with zero slippage protection, enabling MEV sandwich attacks - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` — unlike `ExchangeTransactionContract` — carry no `expected`/minimum-output field, so the counterpart token amount charged or paid out during liquidity injection/withdrawal is computed strictly from the pool's balances at execution time, with no bound the caller can enforce. This mirrors the reported `swapRaforDs`/`__provideLiquidityWithRatioGetDust` issue where liquidity is provisioned "with 0 tolerance," letting anyone sandwich the transaction to shift the ratio in their favor.

### Finding Description
`ExchangeInjectActuator.execute` computes the counterpart amount purely from the current on-chain pool ratio: [1](#0-0) 
and its validator never checks any caller-supplied minimum/maximum bound for `anotherTokenQuant` because `ExchangeInjectContract` has no such field: [2](#0-1) 

The same pattern exists in `ExchangeWithdrawActuator`, which also derives `anotherTokenQuant` from the live `firstTokenBalance`/`secondTokenBalance` ratio with no expected-amount check: [3](#0-2) [4](#0-3) 

By contrast, `ExchangeTransactionActuator` (a normal swap) was hardened with an `expected` field and a validation check comparing the computed output against it: [5](#0-4) 

Because the pool's `firstTokenBalance`/`secondTokenBalance` are ordinary chain state that is updated by any anonymous account's `ExchangeTransactionContract` (swap) broadcast into the same block, an attacker can:
1. Front-run a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` with an `ExchangeTransactionContract` swap that skews the first/second token ratio.
2. Let the victim's inject/withdraw execute at the skewed ratio, forcing them to deposit more of the counterpart asset than intended (inject) or receive less than fair share (withdraw).
3. Back-run with an opposite swap to restore the ratio and realize the extracted profit, exactly the sandwich pattern described in the report against `__provideLiquidityWithRatioGetDust`.

`ExchangeInjectActuator` and `ExchangeWithdrawActuator` restrict the caller to the exchange creator (`exchangeCapsule.getCreatorAddress()`), but the *attacker* performing the sandwich swaps is an unrelated, unprivileged, anonymous account broadcasting ordinary `ExchangeTransactionContract` transactions — this requires no special privilege, key, or node access, satisfying the "unprivileged actor" constraint.

### Impact Explanation
A successful sandwich forces the exchange-market creator to inject more value than intended or withdraw less than the fair proportional share, transferring value to the attacker performing the surrounding swaps. This is direct on-chain asset/accounting corruption of the exchange market's internal balances/creator funds, reachable purely through ordinary broadcast transactions.

### Likelihood Explanation
Any account can create an `Exchange` (via `ExchangeCreateContract`) and later inject/withdraw liquidity; the pool ratio is public chain state, and manipulating it via `ExchangeTransactionContract` swaps requires only sufficient balance and standard mempool/block-ordering visibility (validators/packers can trivially reorder transactions within a block). No special privilege is required, and the actuators contain no minimum-output or deadline/tolerance check to prevent it, making exploitation straightforward whenever profitable Inject/Withdraw transactions are visible pre-confirmation.

### Recommendation
Add an `expected`/minimum-output (and optionally maximum) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate` / `ExchangeWithdrawActuator.doValidate`, following the same pattern already implemented for `ExchangeTransactionContract`'s `expected` field.

### Proof of Concept
1. Account A creates an Exchange pool with balanced TRX/token reserves via `ExchangeCreateContract`.
2. Account A broadcasts an `ExchangeInjectContract` intending to inject at the current ratio.
3. Before it is packed, Attacker B broadcasts an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably (as computed in `ExchangeInjectActuator.execute` lines 71-83).
4. Account A's inject executes at the skewed ratio, debiting more of the counterpart token than intended, since no `expected` bound exists to abort the transaction.
5. Attacker B immediately swaps back via a second `ExchangeTransactionContract`, restoring the ratio and capturing the value difference — mirroring the sandwich PoC in the external report against `provideLiquidityWithFlashSwapFee`.
