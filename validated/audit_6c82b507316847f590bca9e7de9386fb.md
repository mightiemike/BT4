### Title
Unprivileged attacker can poison a shared SPL-token secondary-index key with fake token accounts, causing unbounded `do_load` cost amplification on `AccountsDb::index_scan_accounts` for any subsequent index-filtered RPC scan by any client - ([File: accounts-db/src/accounts_db.rs])

### Summary
An unprivileged user can create many cheap, real SPL-Token-program-owned accounts whose "mint" field bytes are forged to any pubkey of the attacker's choosing (including a mint the attacker does not own), inflating the `spl_token_mint_index` bucket for that key. Any later `getTokenAccountsByMint`/filtered `getProgramAccounts` RPC call against that mint key forces `AccountsDb::index_scan_accounts` to call `do_load` once per pubkey stored under that key, so the attacker's cheap writes impose proportionally unbounded scan cost on whoever queries that shared key.

### Finding Description
`AccountsIndex::update_spl_token_secondary_indexes` only checks that the account is owned by a real SPL-Token program (`*account_owner == *token_id`) and that the mint key passes `account_indexes.include_key(mint_key)` (which defaults to "include all" unless the operator explicitly configured an include/exclude allowlist): [1](#0-0) 

It never validates that the "mint" bytes correspond to an actually-initialized mint account — the mint pubkey is read directly out of raw account data at a fixed offset by `G::unpack_account_mint`, and `get_token_account_mint`/`Account::valid_account_data` only checks the token-account state discriminant, not that the referenced mint exists or is legitimate: [2](#0-1) 

This lets an attacker create arbitrarily many small, rent-paid, SPL-Token-owned accounts whose mint field is set to any pubkey they choose (e.g., a popular mint they don't control), inserting all of those pubkeys into the shared `spl_token_mint_index` bucket for that key via `self.spl_token_mint_index.insert(mint_key, pubkey)`.

When any client (the attacker or an unrelated third party) later performs an index-filtered scan for that key — e.g. `getTokenAccountsByMint` → `get_filtered_indexed_accounts` → `Accounts::load_by_index_key_with_filter` → `AccountsDb::index_scan_accounts` — the scan unconditionally iterates every pubkey in `get_index_key_pubkeys(&index_key)` and performs a `do_load` for each one, checking `config.is_aborted()` only between iterations: [3](#0-2) 

The only cost-limiting mechanism, `byte_limit_for_scan`/`accumulate_and_check_scan_result_size`, is opt-in (`accounts-index-scan-results-limit-mb`, defaulting to `None` unless the operator sets it): [4](#0-3) [5](#0-4) 

and even when enabled, it only aborts after accumulating that many bytes of *matching* results — since the attacker's forged accounts are crafted to pass the `TokenAccountState`/`Memcmp(mint)` RPC filters, they are counted as matches and still consume `do_load` work before the limit triggers. Without the limit configured, the cost is fully `O(M)` for attacker-controlled `M`.

### Impact Explanation
This falls under the "cheap storage/index/scan work exhaustion" bounty category: the attacker pays only ordinary rent-exempt-minimum costs for `M` small accounts, but every future index-filtered RPC scan against that shared key (by the attacker or any unrelated third party/dApp legitimately querying real holders of that mint) incurs `O(M)` `do_load` calls in `AccountsDb::index_scan_accounts`, disproportionate to the fees the attacker paid and imposed on other RPC callers/nodes rather than scoped to the attacker.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: `AccountIndex::SplTokenMint` must be enabled by the validator operator (a common RPC configuration, e.g. for `getTokenAccountsByMint`/`getProgramAccounts` support) and `account_indexes.include_key(mint_key)` must be true, which is the default state. The attacker needs no special program deployment — real SPL-Token/Token-2022 program-owned accounts can be created and initialized by anyone with data bytes at the "mint" offset set to a chosen pubkey, since neither `Account::valid_account_data` nor `update_spl_token_secondary_indexes` verify that the referenced mint is real. Poisoning is repeatable and persistent until the fake accounts are closed/cleaned, and the amplified-cost trigger requires only a single filtered RPC call.

### Recommendation
- Bound the size of a single secondary-index bucket (`spl_token_mint_index`/`spl_token_owner_index`/`program_id_index`) per key, or cap the number of `do_load` calls performed in `index_scan_accounts` regardless of `byte_limit_for_scan` configuration.
- Make `scan_results_limit_bytes` (or an equivalent do_load iteration cap) enabled by default rather than opt-in.
- Consider validating that a token account's "mint" field actually references an account owned by the same token program before indexing it under `spl_token_mint_index`.

### Proof of Concept
Rust integration test sketch (in `accounts-db/src/accounts_db/tests/impl.rs`, using existing `spl_token_mint_index_enabled()` test helper and `IndexKey::SplTokenMint`):

```rust
#[test]
fn test_secondary_index_poisoning_cost_amplification() {
    let accounts = AccountsDb {
        account_indexes: spl_token_mint_index_enabled(),
        ..AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG)
    };
    let victim_mint_key = Pubkey::new_unique(); // attacker doesn't own/control this mint

    const SPL_TOKEN_INITIALIZED_OFFSET: usize = 108;
    let make_fake_token_account = || {
        let mut data = vec![0; spl_generic_token::token::Account::get_packed_len()];
        data[..PUBKEY_BYTES].clone_from_slice(&victim_mint_key.to_bytes());
        data[SPL_TOKEN_INITIALIZED_OFFSET] = 1;
        let mut acct = AccountSharedData::new(1, data.len(), &spl_generic_token::token::id());
        acct.set_data(data);
        acct
    };

    // Attacker floods the shared index key with M cheap accounts.
    for m in [10usize, 1_000, 100_000] {
        for _ in 0..m {
            let pubkey = Pubkey::new_unique();
            accounts.store_for_tests((0, [(&pubkey, &make_fake_token_account())].as_slice()));
        }
        accounts.add_root_and_flush_write_cache(0);

        let start = std::time::Instant::now();
        let mut count = 0;
        accounts
            .index_scan_accounts(
                &Ancestors::default(),
                0,
                IndexKey::SplTokenMint(victim_mint_key),
                |_| count += 1,
                &ScanConfig::default(), // no byte_limit_for_scan configured (default behavior)
            )
            .unwrap();
        // Assert: wall time / do_load count grows linearly with M, unbounded by any
        // cost the attacker actually paid (only rent-exempt minimums for M accounts).
        println!("M={m} count={count} elapsed={:?}", start.elapsed());
    }
}
```

Expected result: scan wall-time/`do_load` count scales linearly with attacker-controlled `M`, with no cap, confirming the disproportionate cost amplification against `IndexKey::SplTokenMint(victim_mint_key)`, a key the attacker does not need to own.
