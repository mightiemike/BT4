### Title
Fold in bad-debt socialization aborts the *whole* liquidation instead of isolating the failed asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate()` calls `fold socialize-debt-asset` over a borrower's remaining debt list when their collateral is exhausted. `socialize-debt-asset` returns an accumulator `{ borrower, success }` and, once one iteration fails, propagates `success: false` through the remaining folds without reverting inside the fold itself — that part is a correct "fail fast, but continue folding" pattern. The actual defect is architectural: after the fold completes, `liquidate()` does `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)`, which reverts the *entire* liquidation (including the already-computed, already-committed `debt-remove-scaled` and `collateral-remove` calls earlier in the same function) if socialization of even one of several debt assets fails.

### Finding Description
In `liquidate()` [1](#0-0) , once `no-collateral-left` is true, the function computes `fresh-debt-list` (the borrower's remaining debt entries across possibly multiple assets) and folds `socialize-debt-asset` over it: [2](#0-1) 

`socialize-debt-asset` itself is a fold that absorbs failure of any *single* asset's socialization by short-circuiting subsequent iterations via the `success` flag, rather than reverting mid-fold: [3](#0-2) 

The bug is that the fold's absorbed failure is then converted into a hard `asserts!` failure at the call site (`ERR-BAD-DEBT-SOCIALIZATION-FAILED`), which — because Clarity rolls back *all* state changes and asset transfers for the entire top-level public-function transaction on any `(err ...)` return — undoes the liquidator's already-repaid debt (`vault-system-repay`) and the collateral already seized (`collateral-remove`) for the *first* (successfully processed) debt asset in the same call, purely because a *later*, unrelated debt asset failed to socialize (e.g. `vault-socialize-debt` or `vault-accrue` returning an error for that asset's vault). There is no way to retry or complete the liquidation with partial bad-debt socialization, and no fallback path (no "sweep"/quarantine of the good state) — the transaction is forced to strand the entire liquidation attempt for that borrower on that block, even though the failure only concerned one of several debt legs.

### Impact Explanation
This is a temporary freezing-of-funds class issue: a liquidator's transaction that would have correctly seized collateral and repaid the majority of a bad-debt position reverts entirely because one unrelated vault call inside the bad-debt socialization fold fails. The borrower's now-undercollateralized/insolvent position remains unliquidated, and the protocol's insolvency exposure (unsocialized bad debt) persists. Because `is-liquidation-paused`/vault availability can vary per asset, this makes it possible for a borrower with multi-asset debt to have their position become effectively un-liquidatable if socialization always fails on one specific debt asset (e.g., a paused or edge-case vault), freezing funds that should be recovered via liquidation.

### Likelihood Explanation
This triggers deterministically any time `no-collateral-left` is true for a multi-debt-asset borrower and one of the *other* debt assets' `vault-socialize-debt` or `vault-accrue` calls fails (e.g. that vault is paused, or hits an internal invariant/edge case). No attacker collusion or privileged access is required — it is a single-transaction, single-caller (liquidator) scenario, matching a "fold that absorbs failure" being subsequently treated as an all-or-nothing revert gate.

### Recommendation
Decouple the atomicity of collateral seizure/debt repayment from bad-debt socialization: either (a) allow `liquidate()` to succeed and record unsocialized bad debt for later retry per-asset instead of asserting on the aggregate fold result, or (b) make `socialize-debt-asset` per-asset failures non-fatal to the overall transaction (e.g., persist which assets succeeded and emit an event for manual/automated retry of the remainder), so a failure in socializing one debt asset cannot roll back an otherwise-successful liquidation of collateral and other debt assets.

### Proof of Concept
1. Borrower has debt in two assets, A and B, and zero remaining collateral value after a liquidation reduces their sole collateral to 0 (`no-collateral-left` becomes true).
2. Liquidator calls `liquidate()` targeting debt asset A; `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` succeed for A.
3. `fresh-debt-list` now contains the residual debt for asset B (and possibly A if not fully repaid). `fold socialize-debt-asset` processes B; `vault-socialize-debt` (or `vault-accrue`) for vault B returns an error (e.g., vault B is paused or hits an edge-case revert) [4](#0-3) .
4. `socialization-result` comes back with `success: false`; `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fires [5](#0-4) .
5. Because the top-level `liquidate` call returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`, Clarity rolls back the entire transaction — the liquidator's repayment of debt A and seizure of collateral are undone, even though they succeeded independently, and the borrower's insolvent position remains stuck unliquidated as long as vault B keeps failing socialization.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))

                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
