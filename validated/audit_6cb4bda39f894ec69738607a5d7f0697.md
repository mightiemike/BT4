### Title
`ExchangeInjectActuator` computes the paired token amount with floor-division instead of round-up, letting the exchange creator under-contribute liquidity every injection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` (the `ExchangeInjectContract` handler for Tron's built-in bancor-style bonding-curve DEX) computes the amount of the "other" token that must be injected alongside the user-chosen `tokenQuant` using plain `BigInteger` truncating division (equivalent to `floorDiv`). This rounds the required co-deposit down instead of up, letting the caller inject slightly less value than the exact proportional amount while still increasing the credited balance of the token they explicitly chose. This is the same class of bug as the Mellow `ratiosX96Value` finding: a value that should be rounded up to preserve invariant/solvency is instead rounded down, and the caller captures the rounding delta.

### Finding Description
In `doValidate()` and `execute()`, when the caller injects `tokenQuant` of one reserve token, the actuator computes the matching amount of the other reserve token proportionally to the existing reserve ratio: [1](#0-0) 

and in `execute()` the same computation is performed with `floorDiv`/`multiplyExact`: [2](#0-1) 

Both paths use integer division that truncates toward zero (floor, for positive operands), i.e. `anotherTokenQuant = floor(otherBalance * tokenQuant / thisBalance)`. This value is:
1. Added to the pool's reserve for the "other" token (`exchangeCapsule.setBalance(...)`), and
2. Deducted from the caller's own asset/TRX balance (`accountCapsule.reduceAssetAmountV2(...)` / balance subtraction).

Because the amount deducted from the caller is the *floor* of the proportional amount, the caller pays strictly less than the exact value required to keep the reserve ratio (and thus the bonding-curve price) unchanged. Each injection therefore leaves the pool's reserve ratio very slightly skewed in the injector's favor relative to a "round up" implementation — exactly the direction the Mellow report flags: rounding a contribution/valuation quantity down instead of up shifts value away from the shared pool and toward the actor performing the operation.

Unlike `ExchangeWithdrawActuator`, which additionally enforces a "Not precise enough" check (rejecting withdrawals whose ratio deviates by more than 0.01%) when hardening is enabled, `ExchangeInjectActuator` has no equivalent tolerance/precision check and no `RoundingMode.CEILING`/round-up option at all — the floor division is unconditional in both the legacy and any "hardened" code paths for this actuator.

### Impact Explanation
Repeated injections (only the exchange creator, per the `!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check, can call this) allow the creator to accumulate reserve-ratio distortion in the pool at negligible individual cost each time, which:
- Slowly degrades the invariant/pricing accuracy of the on-chain exchange pool used by other traders via `ExchangeTransactionActuator`, letting the creator extract value from counterparties trading against the distorted curve, and
- Constitutes accounting corruption of the exchange's reserve state relative to the amount of value actually contributed by the depositor, which is the same "vault vs. user" imbalance flagged in the source report (small, cumulative, non-reversible drift favoring the depositor).

This is lower severity than a direct vault-drain because the actor must already be the exchange's creator and the per-call skew is bounded by 1 unit of the smaller-denomination token, but it is a real, exploitable, repeatable asset-accounting rounding error in a reachable actuator invoked via ordinary broadcast transactions.

### Likelihood Explanation
Any account that creates an `Exchange` (via `ExchangeCreateContract`, which is unprivileged/anonymous) automatically becomes that exchange's creator and can call `ExchangeInjectContract` an unlimited number of times with tokenQuant values chosen to maximize the rounding remainder (e.g., picking `tokenQuant` such that `otherBalance * tokenQuant % thisBalance` is just under `thisBalance`), making exploitation straightforward and repeatable at will.

### Recommendation
Round `anotherTokenQuant` up (ceiling division) in both `doValidate()` and `execute()` of `ExchangeInjectActuator`, mirroring the direction recommended in the Mellow fix (`FullMath.mulDivRoundingUp`), e.g. using `BigInteger` ceiling division: `(numerator + denominator - 1) / denominator`, or equivalently `bigNumerator.divide(bigDenominator, RoundingMode.CEILING)` via `BigDecimal`. Additionally consider adding the same "Not precise enough" bounds check that `ExchangeWithdrawActuator` already applies, to reject injections whose computed ratio deviates from the ideal proportional value beyond a small tolerance.

### Proof of Concept
1. Attacker creates an `Exchange` with reserves `firstTokenBalance = 3`, `secondTokenBalance = 10` (becoming the exchange creator).
2. Attacker calls `ExchangeInjectContract` with `tokenID = firstTokenID`, `tokenQuant = 2`.
3. `anotherTokenQuant = floor(10 * 2 / 3) = floor(6.67) = 6` (see `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java:217-218` / `:73-74`), instead of the fair value `6.67` (which should round up to `7` to preserve/improve the pool's reserve ratio).
4. Pool reserves become `first = 5, second = 16` (ratio `3.2`) instead of the mathematically fair `first = 5, second ≈ 16.67` (ratio `≈3.33`), and the attacker paid only `6` of the second token instead of `6.67`+ needed to keep the price unchanged.
5. Repeating this injection pattern (choosing `tokenQuant` to maximize the floor remainder each time) lets the creator accumulate the rounding discount over many transactions, distorting the AMM's implied price to the detriment of subsequent traders using `ExchangeTransactionActuator` / `ExchangeWithdrawActuator` against the same pool.
