### Title
Unbounded, un-notified wait in the runtime contract-pipelining pipeline can permanently hang chunk application - ([File: runtime/runtime/src/pipelining.rs])

### Summary
`ReceiptPreparationPipeline::get_contract` blocks the apply/validation thread on a `parking_lot::Condvar` that is only ever signaled by a background worker on the shared `contract_compilation_pool()`. If that worker thread dies (panics) before it reaches the code path that flips the task status and calls `notify_all`, the waiter is left parked forever with no timeout, matching the exact bug class of the reported CVE (an operation that indefinitely awaits a signal that a broken/aborted worker will never send).

### Finding Description
When a receipt containing a `FunctionCall` action is submitted to the pipeline, a `PrepareTask` (state machine `Pending → Working → Prepared/Finished`, guarded by a `parking_lot::Mutex` + `Condvar`) is created and the actual WASM preparation work is handed off to `contract_compilation_pool()` [1](#0-0) .

The worker closure:
1. Locks `task.status`, swaps it to `Working`, and drops the lock.
2. Calls `prepare_function_call(...)` **without holding the lock**.
3. Only after `prepare_function_call` returns does it re-lock, set `Prepared(contract)`, and call `task.condvar.notify_all()` [2](#0-1) .

Meanwhile, the apply-loop thread that actually needs the result calls `get_contract`, which loops on `task.condvar.wait(&mut status_guard)` whenever it observes `PrepareTaskStatus::Working`, with **no timeout and no panic/abandonment detection** [3](#0-2) .

If step 2 above (`prepare_function_call`, which ultimately calls into the WASM prepare/compile pipeline, e.g. `runtime/near-vm-runner/src/wasmtime_runner/mod.rs`'s `compile_and_cache`/`compile_and_persist`) panics or the worker thread is otherwise terminated abnormally before re-acquiring the lock, `task.status` remains stuck at `Working` and `notify_all` is never called. The `Condvar::wait` in `get_contract` then blocks forever, because nothing else ever mutates or signals that particular `PrepareTask`. This is precisely the reported bug class ("wait for the stream/condition that never finishes because the underlying worker faulted while processing attacker-supplied input") applied to nearcore's contract-preparation pipelining rather than to a tar layer.

Because `apply_action_receipt`/`Runtime::apply` is the deterministic state-transition function executed identically by every chunk producer and — via `validate_chunk_state_witness` — by every chunk validator re-executing the same receipt, a receipt crafted (deployed contract + `FunctionCall`) so that its background preparation reliably panics the worker would deterministically wedge the apply/validation thread on **every honest node** that processes that chunk, not just one.

### Impact Explanation
A stuck `Condvar::wait` with no timeout on the deterministic runtime apply path is a transaction/receipt-triggered halt: any honest node (chunk producer or chunk validator) that reaches `get_contract` for the offending receipt would hang indefinitely on that thread, blocking chunk application/witness validation for that shard. Because the trigger is deterministic WASM-preparation input reachable from a single `DeployContract` + `FunctionCall` submitted by any unprivileged account, this can propagate network-wide and produce a chain-halting Denial of Service — squarely inside the "transaction-triggered halt" impact category.

### Likelihood Explanation
Likelihood hinges entirely on whether an attacker can make `prepare_function_call`/the underlying wasmtime compile path panic (rather than return a `CompilationError`) on attacker-controlled but protocol-valid WASM bytes. The normal error paths in `compile_and_cache`/`compile_and_persist` return `Result`, so a plain invalid-WASM deploy is handled gracefully and does not exhibit this bug. Triggering the hang additionally requires finding an actual panic path inside contract preparation (e.g., an internal `unwrap()`/`expect()`/index-out-of-bounds/arithmetic-overflow bug reachable from crafted WASM, or a debug-assertion firing in a release-with-debug-assertions build). No such concrete panic-inducing WASM input was found or verified in this investigation — this is reported as an architectural weakness (missing panic-safety / timeout around the pipelining condvar wait) rather than a proven end-to-end exploit, so likelihood should be treated as uncertain/lower-medium until a concrete panic trigger inside `prepare_function_call` is identified.

### Recommendation
- Wrap the pipelining worker's call into `prepare_function_call` with `std::panic::catch_unwind`, and on panic (or any early return) unconditionally transition the task to a terminal "Failed" state and call `condvar.notify_all()` so waiters are released instead of parked forever.
- Add a bounded timeout to `get_contract`'s `condvar.wait` (e.g., `wait_for` with a generous but finite deadline) as defense-in-depth, falling back to synchronous in-thread preparation (the same fallback already used for the "not submitted" case) if the background task does not complete in time.
- Audit `contract_compilation_pool`/`ThreadPool` (`core/async/src/thread_pool.rs`) to ensure a panicking job does not silently shrink the pool's thread count without being detected/retried.

### Proof of Concept
Not constructed: a concrete panic-inducing WASM payload for `prepare_function_call`/the wasmtime compile path was not identified during this investigation. The finding is based on static analysis of the un-timed, unlock-free `Condvar::wait` in `runtime/runtime/src/pipelining.rs` (`get_contract`, lines 375-412) combined with the worker closure (`submit`, lines 264-297) that only calls `notify_all` after successfully completing `prepare_function_call`, leaving no notification path for a worker that panics or otherwise fails to reach that line.
