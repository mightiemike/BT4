### Title
Mempool size limit (`isTooManyPending`) is bypassed for transactions received over P2P, allowing unbounded `pendingTransactions` growth - (File: framework/src/main/java/org/tron/core/net/messagehandler/TransactionsMsgHandler.java)

### Summary
`Manager.pushTransaction()` never enforces `maxTransactionPendingSize` itself; the cap is only checked by the *caller*. The gRPC/HTTP broadcast path (`Wallet.broadcastTransaction`) checks `dbManager.isTooManyPending()` before calling `pushTransaction`, but the P2P transaction-relay path (`TransactionsMsgHandler` → `TronNetDelegate.pushTransaction` → `Manager.pushTransaction`) does not, letting `pendingTransactions` grow without bound from network traffic.

### Finding Description
`Manager.pushTransaction()` unconditionally adds a validated transaction to the in-memory `pendingTransactions` queue with no size check: [1](#0-0) 

The only enforcement of the configured limit (`maxTransactionPendingSize`) is `Manager.isTooManyPending()`: [2](#0-1) 

This check is called explicitly in the gRPC/HTTP broadcast entry point before `pushTransaction` is invoked: [3](#0-2) [4](#0-3) 

However, the P2P transaction relay path does not call `isTooManyPending()` at all. `TransactionsMsgHandler.handleTransaction` submits every incoming peer transaction straight to `TronNetDelegate.pushTransaction`: [5](#0-4) 

which forwards directly into `Manager.pushTransaction` with no capacity check: [6](#0-5) 

`TransactionsMsgHandler.processMessage` also never consults `isBusy()` (which itself wraps `getCachedTransactionSize()`/`maxTrxCacheSize`) before dispatching non-smart-contract transactions to the worker pool — it is only referenced for other purposes (e.g. `InventoryMsgHandler`), not gating the transaction-processing path itself: [7](#0-6) 

This is structurally the same bug class as the sei-tendermint report: the size-limit check (`canAddTx`/`isTooManyPending`) exists but is enforced only on one insertion path, while a second path that feeds the same shared pending-transaction store (`pendingTransactions`) skips the check entirely, allowing the store to grow past its configured bound.

### Impact Explanation
Because `pendingTransactions` is shared state consumed by `PendingManager`/block production and is bounded only by JVM heap once the P2P path is used, an attacker can flood the node with distinct valid transactions relayed over the network, driving unbounded growth of `pendingTransactions` (and consequently `getCachedTransactionSize()`), causing memory pressure, GC pauses, and potential denial-of-service for block production or node stability — matching the reported "Network Shutdown Due to Transaction Limit Overflow" bug class.

### Likelihood Explanation
Any anonymous peer (or a colluding set of accounts submitting many independently valid signed transactions) can trigger this by relaying transactions through the normal P2P transaction-broadcast protocol; no privileged access or key compromise is required, since `TransactionsMsgHandler.handleTransaction` performs only signature/expiration/duplicate checks before calling `pushTransaction`, none of which are the size-limit check.

### Recommendation
Move the `isTooManyPending()` (or equivalent) check into `Manager.pushTransaction()` itself so it is enforced uniformly for both the gRPC/HTTP broadcast path and the P2P relay path, rejecting/dropping new transactions once `maxTransactionPendingSize` (and/or `maxTrxCacheSize`) is reached regardless of entry point. Additionally, `TransactionsMsgHandler.processMessage`/`handleTransaction` should check `isBusy()`/`isTooManyPending()` before submitting P2P-received transactions for processing, and consider evicting/pruning `pendingTransactions` when full rather than growing unbounded.

### Proof of Concept
1. Start a full node with default `maxTransactionPendingSize = 2000`.
2. From an attacker-controlled peer node, generate more than 2000 distinct, validly-signed transactions from various accounts.
3. Broadcast them over the P2P protocol (`TransactionsMessage`) instead of via the gRPC/HTTP `BroadcastTransaction` API.
4. Observe that `TransactionsMsgHandler.handleTransaction` → `TronNetDelegate.pushTransaction` → `Manager.pushTransaction` accepts and enqueues all of them into `pendingTransactions` without ever calling `isTooManyPending()`, exceeding the configured cap, whereas the same volume submitted via `Wallet.broadcastTransaction` would be rejected with `SERVER_BUSY` once the threshold is reached.
