### Title
Concurrent OCC re-execution ignores `compiled_class_hash_v2` reads, allowing stale hash values to be committed - ([File: crates/blockifier/src/concurrency/versioned_state.rs])

### Summary
The blockifier's parallel transaction execution engine (`VersionedState`) uses an optimistic-concurrency-control (OCC) scheme: each transaction records its "read set" (`StateMaps`) while executing speculatively, and before commit `validate_reads` re-checks that set against the latest committed values, forcing re-execution on mismatch. `StateMaps` tracks `storage`, `nonces`, `class_hashes`, `compiled_class_hashes`, and `declared_contracts` [1](#0-0) , and `validate_reads` compares exactly those five categories [2](#0-1) . However, `get_compiled_class_hash_v2` — a distinct state-reader method used to fetch the v2 compiled-class hash for a class [3](#0-2)  — is served and cached entirely through the global `ContractClassManager`/`GlobalContractCache`, bypassing `StateMaps` and the versioned per-tx-index storage that backs OCC validation [4](#0-3) , [5](#0-4) .

### Finding Description
This mirrors the structural root cause in CVE-2024-10976: PostgreSQL's plan-invalidation tracking failed to record dependencies reached through subqueries/views/functions, so a plan built and validated under one context (role) was silently reused under a different context without being told anything had changed. Here, the sequencer's OCC read-set tracking (`StateMaps`) is the analogous "dependency tracking" mechanism that decides whether a speculatively-executed transaction must be re-executed before commit. Any state that is read during execution but not represented in `StateMaps` is, by construction, invisible to `validate_reads`, so a value change to that state between speculative execution and commit will never trigger re-execution.

`compiled_class_hash_v2` is exactly such an untracked value: it is read via `StateReader::get_compiled_class_hash_v2` [3](#0-2) , and the concrete `StateReaderAndContractManager` implementation resolves it from the process-global `ContractClassManager` cache, only falling back to the underlying state reader and then writing the result into the same global cache when absent [4](#0-3) . That global cache is shared across the entire block (and across blocks), and is not versioned per transaction index the way `storage`, `nonces`, `class_hashes`, `compiled_class_hashes` and `declared_contracts` are in `VersionedState` [6](#0-5) . Consequently, `CachedState`'s read-tracking machinery, which records `initial_reads` for every other field type as demonstrated in the concurrency tests (`test_validate_reads` explicitly checks storage/nonce/class_hash/compiled_class_hash/declared_contracts tracking) [7](#0-6) , has no equivalent hook for `compiled_class_hash_v2`.

In the block-production concurrent executor (used by `apollo_batcher`'s `ConcurrentTransactionExecutor` over `ApolloStateReaderAndContractManager` [8](#0-7) ), if two transactions within the same block chunk both cause a v2-hash migration write for the same class (e.g. via the compiled-class-hash migration path that populates this cache — see `compiled_class_hash_migration.rs`), a transaction executed and speculatively "validated" earlier in program order can read a stale/absent `compiled_class_hash_v2` from the shared global cache, and because that value never enters `StateMaps`, `validate_reads` will report success (no conflict detected) and the transaction will be committed without re-execution, even though the value it based part of its execution/fee/resource accounting on differs from what a sequential (non-concurrent) execution would have produced for the same block.

### Impact Explanation
If `compiled_class_hash_v2` values feed into fee computation, resource accounting, or declared-class-hash validation for a transaction (the field exists specifically to support a v2 hashing scheme for declared classes, gated by `enable_casm_hash_migration` as seen in worker_logic tests [9](#0-8) ), a divergence between the value used during concurrent block-building and the value a sequential/consensus-honest re-execution would use can produce a different committed state diff or fee outcome for the same transaction ordering — i.e., honest-node divergence in the resulting state root, or incorrect fee/resource charges, depending on where the migration logic is invoked relative to concurrent scheduling. This is a Medium-severity correctness issue in the execution/concurrency layer reachable purely by an ordinary sequence of Declare/Invoke transactions inside one block (no privileged actor required).

### Likelihood Explanation
Triggering this requires: (1) the sequencer running with concurrency enabled for block building, (2) the `compiled_class_hash_v2` migration path being active for the relevant classes, and (3) at least two transactions in the same block whose speculative execution order causes a read of this value before the writing transaction commits. Given that block building explicitly uses the concurrent executor path (`ConcurrentTransactionExecutor`) and this hash-v2 caching is a recently-introduced migration mechanism (see the dedicated `compiled_class_hash_migration.rs` module and `enable_casm_hash_migration` feature flag), the conditions are plausible but require a specific interleaving of transactions relative to the migration; I could not fully verify in this pass whether other guardrails (e.g., forcing all v2 lookups to occur through the versioned/read-tracked path in production, or restricting migration timing to block boundaries) eliminate the practical exploitability. This should be verified by inspecting `compiled_class_hash_migration.rs` and the exact call sites of `get_compiled_class_hash_v2` within `VersionedStateProxy`/`TransactionalState`, which I did not have iterations left to fully trace.

### Recommendation
Add `compiled_class_hash_v2` as a tracked field in `StateMaps`/`StateCache` (mirroring `compiled_class_hashes`), route its reads/writes through the versioned per-tx-index storage in `VersionedState` the same way `compiled_class_hashes` is handled, and include it in `validate_reads` so that concurrent OCC validation correctly detects conflicts and forces re-execution when this value changes across transactions in the same chunk.

    fn validate_reads(&mut self, tx_index: TxIndex, reads: &StateMaps) -> bool {
        // If is the first transaction in the chunk, then the read set is valid. Since it has no
        // predecessors, there's nothing to compare it to.
        if tx_index == 0 {
            return true;
        }
        // Ignore values written by the current transaction.
        let tx_index = tx_index - 1;
        for (&(contract_address, storage_key), expected_value) in &reads.storage {
            let value =
                self.storage.read(tx_index, (contract_address, storage_key)).expect(READ_ERR);

            if &value != expected_value {
                return false;
            }
        }

        for (&contract_address, expected_value) in &reads.nonces {
            let value = self.nonces.read(tx_index, contract_address).expect(READ_ERR);

            if &value != expected_value {
                return false;
            }
        }

        for (&contract_address, expected_value) in &reads.class_hashes {
            let value = self.class_hashes.read(tx_index, contract_address).expect(READ_ERR);

            if &value != expected_value {
                return false;
            }
        }

        for (&class_hash, expected_value) in &reads.compiled_class_hashes {
            let value = self.compiled_class_hashes.read(tx_index, class_hash).expect(READ_ERR);

            if &value != expected_value {
                return false;
            }
        }

        for (&class_hash, expected_value) in &reads.declared_contracts {
            let is_declared = self.declared_contracts.read(tx_index, class_hash).expect(READ_ERR);
            assert_eq!(
                is_declared,
                self.compiled_contract_classes.read(tx_index, class_hash).is_some(),
                "The declared contracts mapping should match the compiled contract classes \
                 mapping."
            );

            if &is_declared != expected_value {
                return false;
            }
        }

    /// Returns the compiled class hash v2 for the given class hash.
    /// The function assumes that the class hash is already declared,
    /// and of cairo1 contract class.
    fn get_compiled_class_hash_v2(
        &self,
        class_hash: ClassHash,
        compiled_class: &RunnableCompiledClass,
    ) -> StateResult<CompiledClassHash> {
        // First, try getting from class manager cache.
        match self.contract_class_manager.get_compiled_class_hash_v2(&class_hash) {
            Some(compiled_class_hash) => Ok(compiled_class_hash),
            None => {
                // Not in cache → fetch from state reader.
                let compiled_class_hash =
                    self.state_reader.get_compiled_class_hash_v2(class_hash, compiled_class)?;
                // Verify that the returned compiled_class_hash_v2 is not the default value.
                // default value is used to mark classes that are not declared or cairo0 classes.
                assert_ne!(
                    compiled_class_hash,
                    CompiledClassHash::default(),
                    "Default compiled class hash is for marking classes that are not declared or \
                     cairo0 classes. class_hash: {class_hash:?}"
                );
                // Store in cache.
                self.contract_class_manager
                    .set_compiled_class_hash_v2(class_hash, compiled_class_hash);

                Ok(compiled_class_hash)
            }
        }
    }
