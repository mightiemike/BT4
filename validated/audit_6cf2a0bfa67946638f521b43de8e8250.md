## Finding

### Title
Hardcoded 5% swap slippage tolerance in module-driven PRC20→PC auto-swaps enables sandwich-attack value extraction from depositing users - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
When Push Chain executes a gas-abstraction deposit (source-chain native asset → PRC20 → auto-swapped to PC) or refunds unused destination-chain gas, the keeper fetches a spot quote from Uniswap `QuoterV2` and then immediately submits the swap with a fixed `minPCOut = quote * 95 / 100`. This 5% tolerance is hardcoded, not user-configurable, and the quote/execute pair happens inside a single Push-Chain-produced EVM transaction whose ordering relative to other transactions in the same block is controlled by the block proposer, not the depositing user. An unprivileged actor can manipulate the WPC/PRC20 pool price immediately before this module transaction lands (and reverse it afterward) to skim up to the full 5% tolerance from every gas-abstraction deposit and gas refund, exactly analogous to the Dopex bonder issue where the "discount" a user is entitled to can be moved against them between quoting and execution because no caller-supplied bound is honored.

### Finding Description
The relevant code paths are:

- `x/uexecutor/keeper/execute_inbound_gas.go:104-153` — fetches `quote` via `GetSwapQuote` then computes `minPCOut := quote*95/100` before calling `CallPRC20DepositAutoSwap`. [1](#0-0) 
- `x/uexecutor/keeper/execute_inbound_gas_and_payload.go:347-379` — same pattern in `gasAndPayloadDepositAutoSwap`. [2](#0-1) 
- `x/uexecutor/keeper/outbound.go:213-234` (`applyGasRefund`) — same pattern for the unused-gas refund swap back to PC. [3](#0-2) 

In all three cases, `GetSwapQuote` is a plain `CallEVM` (`commit=false`) reading the current Uniswap V3 `QuoterV2` state, i.e. a spot-price read of on-chain reserves at the moment the finalize/vote-triggered keeper logic executes: [4](#0-3) 

The 5% band is a fixed protocol constant, never derived from anything the depositing user specified when they made their source-chain deposit. The user has no channel to communicate an acceptable slippage bound at deposit time (unlike `DeductGasFeesFromReceipt`, which does honor a caller-supplied `maxFeePerGas`). Because the deposit-triggering event happens on a *different* chain and is only executed on Push Chain once validators reach quorum and the resulting `MsgVoteInbound`/`MsgVoteOutbound` is included in a Push Chain block, there is a real, attacker-influenceable time/ordering gap between "when the exchange rate that will apply is effectively locked in" (immediately before the module's own transaction) and "when the user's off-chain source-chain transaction was submitted." An unprivileged party who can influence transaction ordering within the same Push Chain block (e.g., via priority fee, or simply by racing to trade against the WPC/PRC20 pool right before the module's swap executes and reversing after) can move the pool price by up to just under 5% before the module's swap lands, extracting the difference as MEV at the depositing user's expense, while the module transaction itself still "succeeds" because it stays within the 5% floor.

### Impact Explanation
This falls under "corruption of PRC20 or native asset accounting … or canonical UniversalTx state" and "unauthorized … module-originated EVM execution" adjacent impact categories: the amount of PC actually credited to a user's UEA (via `depositPRC20WithAutoSwap`) or refunded to a user (via `refundUnusedGas` with `withSwap=true`) can be systematically less than the fair-market value of the swapped PRC20, with the shortfall captured by an unprivileged attacker sandwiching the trade. This is a leak of user/protocol value reachable purely from ordinary deposit/outbound flows, matching the "in scope" impact of value leakage from honest user funds without any privileged actor assumption.

### Likelihood Explanation
Likelihood is bounded by the loss being capped at ~5% per swap and requiring the attacker to have capital and the ability to trade in the same pool within the same block window as the module's swap transaction (which is influenced by, but not fully controlled by, the depositing user). This is realistically executable by any bot monitoring pending `MsgVoteInbound`/`MsgVoteOutbound` transactions that will trigger a swap, similar to how MEV searchers sandwich DEX trades on any EVM chain today.

### Recommendation
- Do not fetch the quote and execute the swap as two independent EVM calls with a fixed tolerance; instead compute `minPCOut` from a manipulation-resistant reference (e.g., a short TWAP from the pool, or an oracle price) rather than the instantaneous `QuoterV2` spot quote.
- Consider tightening the slippage bound and/or making it configurable via governance parameters rather than a hardcoded `95/100` constant, and add safeguards (e.g., per-block price-deviation checks) before committing to the swap.
- Where feasible, allow off-chain relayers/users to embed an expected minimum output in the original source-chain payload so the destination-chain module trade can enforce a caller-intended bound instead of a blanket protocol-wide 5%.

### Proof of Concept
1. An attacker monitors the Push Chain mempool/proposer queue for `MsgVoteInbound` messages that will finalize a `GAS` or `GAS_AND_PAYLOAD` inbound (i.e., quorum is about to be reached and `ExecuteInboundGas`/`ExecuteInboundGasAndPayload` will run this block).
2. Immediately before that transaction is applied, the attacker submits a swap on the WPC/PRC20 pool that pushes the PRC20→WPC price down by just under 5% (front-run).
3. The module's `GetSwapQuote` + `CallPRC20DepositAutoSwap` (with `minPCOut = quote*0.95`) executes against the now-worse price; the depositing user's UEA receives close to the 5%-discounted amount instead of the fair-market amount.
4. The attacker immediately reverses their trade (back-run), realizing the price difference as profit extracted from the value that should have gone to the depositing user.
5. Repeat for every `GAS`/`GAS_AND_PAYLOAD` inbound and every gas refund with `withSwap=true`, systematically skimming value from Push Chain users' cross-chain deposits/refunds.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
