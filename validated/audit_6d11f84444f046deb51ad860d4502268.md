## Title
Unlocked disk-index write in `write_through` lets a stale `AccountInfo` clobber a concurrent shrink's write-through, corrupting the on-disk accounts-index entry - (`accounts-db/src/accounts_index/in_mem_accounts_index.rs`)

### Summary
`InMemAccountsIndex::write_through` reads `(slot, account_info)` under the slot-list read lock, releases the lock, and only then performs the actual disk-bucket write, re-validating the in-memory state afterward only to decide whether to clear the dirty flag — not to gate the write itself. Two concurrent callers of `write_through` for the same pubkey (one from `remove_unrooted_slots`'s cache-drop write-through, one from `shrink_storage`'s `update_index_for_shrink`/`replace`) can therefore have their disk writes complete out of order relative to their slot-list mutations, leaving the on-disk index bucket holding a stale `AccountInfo` while the in-memory entry is left clean and evictable.

### Finding Description
The relevant code: [1](#0-0) 

`write_through` performs `write_to_disk` (the actual bucket write) *outside* any lock that also protects the slot-list mutation performed by a concurrent caller. Its post-write check only reads the current slot list to decide whether to `clear_dirty()`; it does not gate or retry the disk write itself.

Both `try_write_through` (used by `write_through_pubkeys`, called from `purge_slots_from_cache`/`remove_unrooted_slots`) and `replace` (used by `update_index_for_shrink`, the index-update step of `shrink_storage`) can invoke `write_through` for the same pubkey concurrently: [2](#0-1) [3](#0-2) [4](#0-3) 

Reproduction of the race, matching the attacker-controlled preconditions in the question (store P at slot 0 and slot 1, root+flush slot 0, then concurrently shrink slot 0's storage and `remove_unrooted_slots([(1, bank_id)])`):

1. Thread A (`remove_unrooted_slots(1) → purge_slots_from_cache → write_through_pubkeys → try_write_through`) reads the slot list under a read lock, capturing `(0, old_info)` — the pre-shrink `AccountInfo` for slot 0 — then drops the lock (per lines 486-498).
2. Thread B (`shrink_storage(0) → store_accounts_for_shrink → update_index_for_shrink → accounts_index.replace`) takes the write lock, swaps the slot-0 entry to `(0, new_info)` pointing at the post-shrink storage, marks dirty, then itself calls `write_through(pubkey, 0, new_info)`: it writes `new_info` to the disk bucket and, seeing the slot list still matches, clears dirty (lines 572-601, 464-481).
3. Thread A resumes and performs its own `write_to_disk` call with the now-stale `old_info`, unconditionally overwriting B's correct `new_info` in the on-disk bucket (line 467). A's post-write check then reads the slot list, sees it no longer equals `(0, old_info)` (line 473-474), and correctly skips `clear_dirty()` — but this does *not* undo the stale disk write that already landed.
4. Net state: in-memory entry has the correct `new_info` **and** `dirty == false` (cleared by B in step 2, never re-marked by A since `try_write_through` does not call `mark_dirty`). A clean entry is eligible for background eviction from memory (dirty entries are exempted from write-through-mode eviction, per the codebase's own eviction contract validated in `test_flush_internal_evicts_in_should_write_through_mode`).
5. Once evicted, any future lookup for `pubkey` (`get_internal_inner` → `load_account_entry_from_disk` → `load_from_disk`) resolves to the corrupted disk-bucket entry holding `old_info`, whose `store_id` refers to storage that shrink has already dropped via `remove_old_stores_shrink`/`mark_dirty_dead_stores`.

No existing guard prevents this: the equality check in `write_through` (lines 470-479) only protects the *dirty-clearing* decision, not the disk write ordering itself; there is no lock or generation counter serializing concurrent `write_to_disk` calls for the same pubkey.

### Impact Explanation
Once the corrupted disk-index entry is the only surviving record for the pubkey (in-mem entry evicted), subsequent reads resolve `(store_id, offset)` to storage that no longer exists. `retry_to_get_account_accessor` documents this class of failure and its retry logic: [5](#0-4) 

Under `LoadHint::FixedMaxRoot` this becomes an unbounded retry loop assuming eventual correction that, in this bug, never arrives (the corrupted disk-index entry is not self-healing unless a fresh store to that exact slot occurs). Under `LoadHint::Unspecified` (RPC path) it counts toward `ABSURD_CONSECUTIVE_FAILED_ITERATIONS`, which is documented as a failsafe against exactly this "should never happen" condition — i.e. this bug can trigger the codebase's own panic/failsafe path. This matches the requested scoped impact: reads resolving to invalid/dropped storage, producing corrupted or missing account data, and potential node panic.

### Likelihood Explanation
This requires the accounts index to be running with disk-backed write-through enabled (`IndexLimit::Threshold`, i.e. `should_write_through == true`), which is an operator-selected, supported production configuration (not the default `IndexLimit::InMemOnly`), used to bound in-memory index size. Given that configuration, the trigger requires only unprivileged actions: an attacker stores the same pubkey in a slot that will be rooted+flushed and in a sibling slot that will be dropped as unrooted (a normal fork outcome from ordinary transaction submission), while background shrink happens to run on the rooted slot at the same time — both are routine AccountsBackgroundService activities that occur under normal validator operation, not attacker-privileged actions. The race window is narrow (two lock-release/disk-write interleavings) but hits routinely under a sustained high-account-churn workload combined with the affected index configuration.

### Recommendation
Serialize `write_to_disk` calls for a given pubkey against slot-list mutations that also intend to write through — e.g., perform the disk write while still holding the slot-list lock (or a dedicated per-entry write-through lock), or attach a monotonically increasing version/generation to each `AccountMapEntry` and have `write_through` verify-and-write under a single critical section (CAS-style) rather than read-then-write-then-recheck across lock releases.

### Proof of Concept
Rust integration test plan (extends the existing `test_purge_unrooted_slot_writes_through_surviving_entry` harness in `accounts-db/src/accounts_db/tests/impl.rs`):
1. Build `AccountsDb` with `IndexLimit::Threshold` (as in the existing write-through tests) and a small `num_ages_to_distribute_flushes`/high-water-mark so evictable clean entries are actually evicted quickly.
2. `store_for_tests(0, P)`, `store_for_tests(1, P)`, `add_root_and_flush_write_cache(0)`.
3. Spawn two threads: Thread A calls `db.remove_unrooted_slots(&[(1, bank_id)])`; Thread B calls a low-level shrink trigger for slot 0 (`db.shrink_slots(vec![0])` or equivalent public shrink entrypoint) after forcing `store` to have shrinkable garbage (e.g., write then overwrite P once more before rooting, to create dead bytes).
4. Use a synchronization barrier or repeated randomized `thread::yield_now()` interleavings (loop many iterations) to increase the chance `try_write_through`'s disk write lands after `replace`'s disk write.
5. After both threads join, force in-mem eviction of the entry (advance ages / call background flush enough times), then assert `db.do_load_for_tests(&Ancestors::from(vec![0]), &P)` returns the *current* (post-shrink) account data and never panics or returns `None`/stale bytes; also assert `db.storage.get_slot_storage_entry(0)` matches the `store_id` encoded in whatever `AccountInfo` the accounts index resolves to disk after eviction.
6. Expected (buggy) outcome: assertion failure where the resolved `AccountInfo`'s `store_id` does not match any entry in `self.storage`, or `do_load_for_tests` panics via the `ABSURD_CONSECUTIVE_FAILED_ITERATIONS` failsafe.

    /// If the in-mem entry for pubkey is `slot_list.len() == 1` with `ref_count == 1` and
    /// currently dirty, write it through to disk
    pub fn try_write_through(&self, pubkey: &Pubkey) {
        let to_write = self.get_only_in_mem(pubkey, false, |entry| {
            entry.and_then(|entry| {
                if !entry.dirty() {
                    return None;
                }

                let slot_list = entry.slot_list_read_lock();
                match (entry.ref_count(), &slot_list[..]) {
                    (1, [info]) => Some(*info),
                    _ => None,
                }
            })
        });
        if let Some((slot, info)) = to_write {
            self.write_through(pubkey, slot, info);
        }
    }

    /// Replaces the slot list entry at `old_slot` with `new_item`.
    ///
    /// Panics if `old_slot` is not present in the slot list, or if more than one entry at
    /// `old_slot` is found (which would indicate prior corruption).
    pub fn replace(&self, pubkey: &Pubkey, new_item: SlotListItem<T>, old_slot: Slot) {
        let mut should_write_through = false;

        self.get_or_create_index_entry_for_pubkey(pubkey, |entry| {
            let mut slot_list = entry.slot_list_write_lock();
            let mut found_slot = false;
            let slot_list_length = slot_list.retain_and_count(|cur_item| {
                if cur_item.0 == old_slot {
                    assert!(
                        !found_slot,
                        "duplicate entry at slot {old_slot} in slot_list"
                    );
                    found_slot = true;
                    *cur_item = new_item;
                }
                true
            });
            assert!(
                found_slot,
                "Expected to find a slot to replace in the slot list"
            );
            entry.mark_dirty();

            should_write_through =
                self.should_write_through && slot_list_length == 1 && entry.ref_count() == 1;
        });
        if should_write_through {
            let (slot, account_info) = new_item;
            self.write_through(pubkey, slot, account_info);
        }
    }

    fn update_index_for_shrink<'a>(
        &self,
        infos: &[AccountInfo],
        accounts: &impl StorableAccounts<'a>,
        update_index_thread_selection: UpdateIndexThreadSelection,
        thread_pool: &ThreadPool,
    ) {
        let target_slot = accounts.target_slot();
        let len = std::cmp::min(accounts.len(), infos.len());

        let update = |start, end| {
            (start..end).for_each(|i| {
                let info: AccountInfo = infos[i];
                let old_slot = accounts.slot(i);
                let pubkey = accounts.pubkey(i);
                self.accounts_index
                    .replace(target_slot, old_slot, pubkey, info);
            });
        };

        let threshold = 1;
        if matches!(
            update_index_thread_selection,
            UpdateIndexThreadSelection::PoolWithThreshold,
        ) && len > threshold
        {
            let chunk_size = len.div_ceil(thread_pool.current_num_threads());
            let batches = 1 + len / chunk_size;
            thread_pool.install(|| {
                (0..batches).into_par_iter().for_each(|batch| {
                    let start = batch * chunk_size;
                    let end = std::cmp::min(start + chunk_size, len);
                    update(start, end)
                })
            });
        } else {
            update(0, len);
        }
    }
