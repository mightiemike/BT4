### Title
Contract owner can front-run `TriggerSmartContract` calls by instantly changing `consume_user_resource_percent` to 100 - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java`)

### Summary
The `UpdateSettingContractActuator` lets a deployed smart contract's owner (`origin_address`) change `consume_user_resource_percent` at any time, and the new value takes effect immediately for the very next transaction that hits the mempool/block, with no delay, no cap below 100%, and no check against the value a calling user expected. This mirrors the `DropEngineV2` bug: an owner-controlled fee-like parameter can be flipped to its maximum right before (front-running) a user's transaction, silently shifting cost/liability onto that unprivileged user.

### Finding Description
`consume_user_resource_percent` controls how the energy cost of a `TriggerSmartContract` call is split between the contract creator's frozen energy and the caller's own resources/TRX, as used in `VMActuator.getTotalEnergyLimitWithFixRatio` / `getTotalEnergyLimitWithFloatRatio`: [1](#0-0) 

`UpdateSettingContractActuator.execute` writes the new percent to the `ContractStore` unconditionally and immediately, and its `validate` only checks the range `[0,100]` and that the caller is the contract's `originAddress` — there is no cooldown, no timelock, and no linkage to the previously communicated/expected percent: [2](#0-1) [3](#0-2) 

Because the setting is read fresh from the `ContractStore` at execution time of each `TriggerSmartContract` call (`rootRepository.getContract(...).getConsumeUserResourcePercent(...)`), any ordinary user calling the contract has no guarantee the percent they observed off-chain (e.g. via `wallet/getcontractinfo`) still holds by the time their transaction is included. A malicious/compromised contract owner can broadcast an `UpdateSettingContract` transaction with `consume_user_resource_percent = 100` to front-run a specific victim's `TriggerSmartContract` transaction (or simply set it permanently to 100 right before mass usage), forcing the caller to pay 100% of the energy bill themselves instead of the previously-subsidized split.

### Impact Explanation
When `consumeUserResourcePercent` is pushed to 100, `creatorEnergyLimit` collapses to 0 in `getTotalEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFloatRatio`, so the caller's own `feeLimit`/frozen energy must cover the entire execution cost that they budgeted assuming creator subsidy. This can cause: (a) unexpected extra TRX burned from the caller's account to pay for energy that was expected to come from the contract owner's frozen energy, or (b) transaction failure due to insufficient energy/feeLimit despite the call being properly budgeted under the previously known percent. This is a concrete accounting/fee-shifting impact against unprivileged callers, directly analogous to the `revenueRecipient`/fee-payer being rugged in the original report.

### Likelihood Explanation
Low-to-moderate: it requires a malicious or compromised contract-owner account (same trust assumption as the original report), but no other privilege is needed — any contract owner can do this at will, and the change is applied atomically with no delay, making front-running trivial for an owner who monitors the mempool for calls to their own contract.

### Recommendation
Add a delay/cooldown (e.g., only take effect after N blocks) before a `consume_user_resource_percent` change becomes active, or require callers to specify the percent they expect and revert if it no longer matches (mirroring the report's recommendation for `DropEngineV2`). At minimum, emit clear on-chain events/logs and consider restricting how often/how drastically the percent can change per time window.

### Proof of Concept
1. Contract owner deploys a contract with `consume_user_resource_percent = 10` (caller pays only 10% of energy, creator subsidizes 90%).
2. A user submits a `TriggerSmartContract` transaction budgeting `feeLimit` for the 10% split.
3. Owner observes the pending transaction and broadcasts an `UpdateSettingContract` transaction setting `consume_user_resource_percent = 100`, which `UpdateSettingContractActuator.execute` applies immediately (subject to normal transaction ordering/block-producer inclusion): [4](#0-3) 
4. When the user's transaction executes, `VMActuator` reads the now-updated percent from the contract store and computes `creatorEnergyLimit = 0`, so the entire energy cost falls on the caller, exceeding their budgeted `feeLimit` and either burning far more TRX than expected or causing the call to fail (`OUT_OF_ENERGY`), despite the caller having correctly sized their transaction for the previously observed 10% split.

  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    ContractStore contractStore = chainBaseManager.getContractStore();
    try {
      UpdateSettingContract usContract = any.unpack(UpdateSettingContract.class);
      long newPercent = usContract.getConsumeUserResourcePercent();
      byte[] contractAddress = usContract.getContractAddress().toByteArray();
      ContractCapsule deployedContract = contractStore.get(contractAddress);

      contractStore.put(contractAddress, new ContractCapsule(
          deployedContract.getInstance().toBuilder().setConsumeUserResourcePercent(newPercent)
              .build()));
      RepositoryImpl.removeLruCache(contractAddress);

      ret.setStatus(fee, code.SUCESS);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
  }
