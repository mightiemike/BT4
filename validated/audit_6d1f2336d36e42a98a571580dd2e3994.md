## Title
Meta-transaction (`SignedDelegateAction`) signatures omit a chain-binding domain separator, enabling cross-fork replay of user-authorized value transfers - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
NEAR's meta-transaction scheme (NEP-366) lets a user sign a `DelegateAction` off-chain and hand it to an untrusted relayer, who wraps it in a transaction and submits it on-chain. Just like the EIP-2612 `permit` scheme in the report, the signed payload is only bound to `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height` and `public_key` — there is no chain/network identifier (equivalent to Ethereum's `chainId`) baked into the domain separator (`MessageDiscriminant`/`SignableMessage`). If NEAR ever undergoes a contentious hard fork that produces two chains sharing the same historical account/access-key state (analogous to the ETH/ETC split), a single user signature remains simultaneously valid on both resulting chains until consumed, letting a relayer execute the same authorized action twice — once per chain — extracting value the user only intended to authorize once.

### Finding Description
`SignedDelegateAction::verify` hashes a `SignableMessage` wrapping the `DelegateAction` with only a NEP-based discriminant prefix, with no chain identity component: [1](#0-0) [2](#0-1) 

The `MessageDiscriminant` only encodes the NEP number (366 for `DelegateAction`, 611 for `DelegateActionV2`) — it carries no genesis hash, `chain_id`, or protocol identifier: [3](#0-2) 

The replay protection that does exist — nonce strictly greater than the access key's on-chain nonce, and `max_block_height` — is enforced purely against local, per-chain state at execution time in `apply_delegate_action`/`validate_delegate_action_key`: [4](#0-3) [5](#0-4) 

Because these checks reference only the chain's own state (the access key's nonce as stored in that chain's trie), a `SignedDelegateAction` that has not yet been consumed remains independently valid on any chain that shares the same pre-fork account/access-key state — there is nothing in the signed bytes that ties the authorization to one specific chain. This mirrors exactly the report's root cause: chainID/domain data is fixed or absent at signing time and cannot distinguish between two chains that diverge after a fork.

### Impact Explanation
A relayer (or anyone who obtains a `SignedDelegateAction`, since it is transmitted off-chain to a possibly-untrusted relayer per NEP-366) can submit the identical signed payload as a transaction on both the original chain and any hard-forked chain sharing the same account state at the fork point, since neither chain's access-key nonce advances until the delegate action is actually included there. This causes the user's single authorization (e.g., a token transfer, `permit`-like approval, or fund withdrawal via a contract call) to be executed on both chains, producing unauthorized duplicate value movement that the signer only intended to happen once. This satisfies the "concrete unauthorized value movement" bar without needing any state-root divergence or malicious validator — a normal relayer replaying an off-chain-transmitted signature is sufficient.

### Likelihood Explanation
Exploitation requires a genuine contentious hard fork of NEAR that produces two live chains sharing pre-fork account state — an infrequent but historically real class of event in blockchain ecosystems (as cited in the original report's Ethereum London-fork scenario). Given such an event, exploitation is trivial and requires no privileged access: any party holding a previously-issued, unconsumed `SignedDelegateAction` (a relayer by design, or a third party if the relayer's flow leaks it) can replay it as-is. Given the "High" difficulty/low-probability-but-high-impact nature (matching the original report's own "High difficulty" rating), this is a valid medium-severity design gap rather than a routinely exploitable bug.

### Recommendation
Bind delegate-action (and any future NEP-461-style off-chain signature) signatures to the specific chain by including a persistent, chain-identifying value — e.g., the genesis hash or an explicit protocol/chain id — as part of the `SignableMessage`/`MessageDiscriminant` construction in `core/primitives/src/signable_message.rs`, so that `get_nep461_hash` in `core/primitives/src/action/delegate.rs` produces different hashes (and thus different signatures) on chains that diverge after a fork. Document this as a required field for any future off-chain signing standard (NEP-461) adopted by nearcore.

### Proof of Concept
1. Alice signs a `DelegateAction` (nonce `N`, `max_block_height` = `H`) authorizing a large token transfer, and hands the `SignedDelegateAction` to Relayer R off-chain, per the intended NEP-366 flow.
2. Before R submits it, NEAR undergoes a contentious hard fork at block `< H`, producing Chain A and Chain B, both containing Alice's account with access-key nonce `< N` at the fork point.
3. R submits the same `SignedDelegateAction` bytes as a transaction on Chain A. `apply_delegate_action`/`validate_delegate_action_key` accept it because the nonce and `max_block_height` checks pass against Chain A's state: [4](#0-3) .
4. R submits the identical bytes on Chain B. The same checks pass independently against Chain B's state, since nothing in the signed payload differentiates the two chains: [6](#0-5) .
5. Alice's single authorized transfer executes twice, once on each chain, resulting in unauthorized duplicate value movement from a signature she issued only once.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
