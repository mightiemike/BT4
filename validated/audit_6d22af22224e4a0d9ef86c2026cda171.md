### Title
OAuth callback HMAC/state validation is computed on a different `shop` value than the one used for token exchange and session creation — HTTP Parameter Pollution ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
In the OAuth `callback` handler, the `shop` query parameter is read twice, in two inconsistent ways, when a request contains **duplicate `shop` parameters**: the value that gets HMAC/state-verified is not the same value that is subsequently used to determine where the authorization code is redeemed and which shop the resulting session belongs to. This is structurally the same bug class as the HatsSignerGate finding: the security check (`checkTransaction`/`checkNSignatures` analog = `validQuery`) is applied to one representation of the input, while the privileged action (`execTransaction`/token exchange) consumes a *different* representation of the same nominally-checked input.

### Finding Description
`callback()` in <cite repo="patrichyt/shopify-app-js--020" path="packages/apps/shopify-api/lib/auth/oauth/oauth.ts" start="141="147" /> parses the URL once into a `URLSearchParams` object called `query`, then:

1. Extracts `shop` with `query.get('shop')` (returns the **first** occurrence of a duplicate key) for logging: [1](#0-0) 
2. Builds `authQuery` with `Object.fromEntries(query.entries())`, which, for duplicate keys, retains the **last** occurrence (later entries overwrite earlier ones in the object): [2](#0-1) 
3. Validates the request via `validQuery`, which calls `validateHmac(config)(query)` and compares `query.state` against the cookie-stored nonce — both against the **de-duplicated `authQuery`** (i.e., the *last* `shop` value): [3](#0-2) 
4. After validation succeeds, `cleanShop` is computed independently via `sanitizeShop(config)(query.get('shop')!, true)` — using `query.get('shop')` again, which returns the **first** occurrence: [4](#0-3) 
5. `cleanShop` is then used as the destination host for the token exchange POST (`https://${cleanShop}/admin/oauth/access_token`, which includes `client_id`/`client_secret`/`code`) and as the `shop` recorded on the resulting `Session`: [5](#0-4) 

Because `validateHmac`/`generateLocalHmac` operate on `authQuery` (built by `Object.fromEntries`, last-value-wins) via `stringifyQueryForAdmin`/`ProcessedQuery`, while the actually-used shop comes from `query.get('shop')` (first-value-wins), an attacker who supplies **two `shop` parameters** in the callback URL can make the HMAC/state check validate against one value while the token-exchange/session-creation logic consumes an entirely different value. This is the same class of defect as the HatsSignerGate finding: the code that performs signature/HMAC verification does not operate on the same data the code performs the privileged action with.

Relevant supporting code: `validateHmac`/`generateLocalHmac` normalize/stringify the already-deduplicated query object: [6](#0-5) , and `sanitizeShop` only constrains the shop to match `*.myshopify.com`/`*.shopify.com`/etc., which does not prevent an attacker from supplying any syntactically valid shop domain of their choosing (including one they control): [7](#0-6) .

### Impact Explanation
An attacker who has a validly-signed OAuth callback for their own shop (trivially obtainable by simply installing the app on any shop they own) can craft a callback URL with a second, spurious `shop` parameter placed before the real one. If ordered correctly, the HMAC/state check will pass (because it operates on the de-duplicated `authQuery`, which lands on the real, correctly-signed value), while the token exchange is issued against `https://<attacker-chosen-shop>/admin/oauth/access_token` and any resulting session would be attributed to `<attacker-chosen-shop>` rather than the shop that actually completed the check. This breaks the fundamental invariant that "the shop identified by a validated request is the shop the request is acted upon," undermining per-tenant isolation guarantees in the OAuth flow. Actual exploitation to full cross-tenant token theft further depends on whether Shopify's own `/admin/oauth/access_token` endpoint accepts a code that isn't bound to the shop in the request path, so the most reliably provable impact is a parameter-confusion/validation-bypass defect in the app's own code, with downstream severity depending on Shopify platform behavior that is outside this codebase.

### Likelihood Explanation
Exploitation requires the ability to induce a browser to visit (or an app server to process) a maliciously modified callback URL containing a duplicated `shop` parameter — reachable by any user completing (or replaying/redirecting) an OAuth install flow, i.e., an unprivileged, single-merchant/customer-controlled vector. No special access to the app's secrets or infrastructure is needed to construct the malformed URL; the attacker only needs one legitimately-issued callback (from installing the app on their own store).

### Recommendation
Use a single, consistent extraction of `shop` (and any other security-relevant parameter) throughout `callback()`. Either:
- Reject any query that contains duplicate values for `shop`, `code`, `state`, `hmac`, or `timestamp` before further processing (similar to the existing `APP_PROXY_SINGLE_VALUE_PARAMS` duplicate-rejection logic already used for app proxy requests in `normalizeQuery`), or
- Derive `authQuery` and `cleanShop`/`shop` from the exact same normalized representation (e.g., always use `Object.fromEntries(query.entries())` or always use `query.get(...)`), so that the value verified by `validQuery` is guaranteed to be identical to the value later used for the token exchange and session creation.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`, completing the normal OAuth `begin` flow and receiving a real, correctly-HMAC-signed callback redirect from Shopify: `.../auth/callback?code=C&hmac=H&host=...&shop=attacker.myshopify.com&state=S&timestamp=T`.
2. Attacker crafts a modified URL, prepending an extra `shop` parameter:
   `.../auth/callback?shop=victim.myshopify.com&code=C&hmac=H&host=...&shop=attacker.myshopify.com&state=S&timestamp=T`
3. When this URL is processed by `callback()`:
   - `authQuery = Object.fromEntries(query.entries())` → `authQuery.shop === "attacker.myshopify.com"` (last occurrence), so `validateHmac`/`state` checks succeed against the real, correctly-signed values.
   - `cleanShop = sanitizeShop(config)(query.get('shop')!, true)` → `query.get('shop') === "victim.myshopify.com"` (first occurrence).
   - The app issues `POST https://victim.myshopify.com/admin/oauth/access_token` with the app's `client_id`/`client_secret`/`code`, and (if the exchange succeeded) would create/attribute a `Session` for `victim.myshopify.com` — a shop that never actually completed or authorized this callback.

export function sanitizeShop(config: ConfigInterface) {
  return (shop: string, throwOnInvalid = false): string | null => {
    let shopUrl = shop;
    const domainsRegex = [
      'myshopify\\.com',
      'shopify\\.com',
      'myshopify\\.io',
      'shop\\.dev',
    ];

    // Add domains from transformations (both source and target)
    if (config.domainTransformations) {
      domainsRegex.push(...getTransformationDomains(config));
    }

    const shopUrlRegex = new RegExp(
      `^[a-zA-Z0-9][a-zA-Z0-9-_]*\\.(${domainsRegex.join('|')})[/]*$`,
    );

    const shopAdminRegex = new RegExp(
      `^admin\\.(${domainsRegex.join('|')})/store/([a-zA-Z0-9][a-zA-Z0-9-_]*)$`,
    );

    const isShopAdminUrl = shopAdminRegex.test(shopUrl);
    if (isShopAdminUrl) {
      shopUrl = shopAdminUrlToLegacyUrl(shopUrl) || '';
    }

    const sanitizedShop = shopUrlRegex.test(shopUrl) ? shopUrl : null;
    if (!sanitizedShop && throwOnInvalid) {
      throw new InvalidShopError('Received invalid shop argument');
    }

    if (sanitizedShop && config.domainTransformations) {
      return applyDomainTransformations(sanitizedShop, config);
    }

    return sanitizedShop;
  };
