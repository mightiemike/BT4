## Title
Unbounded `set-points-rate` interest-rate curve permits index/multiplier overflow that permanently reverts `accrue()`, bricking all vault operations - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vaults `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
`set-points-rate` lets the DAO set the interest-rate curve (`points-ir.rate`) with **no explicit interest-rate bound** — it packs values with `(pack-u16 points none)`, which only clamps to `MAX-U16` (`u65535`, i.e. up to 655.35% APY), unlike `set-points-util` which is bounded by `(some BPS)`. This is structurally the same class of bug as the reported issue: an admin-settable numeric parameter with insufficient bound checking that later interacts with fixed-precision arithmetic used by a core, always-invoked function (`accrue`/`next-index`), where an out-of-range configuration can push a checked-arithmetic operation to overflow and revert permanently.

### Finding Description
`set-points-rate` [1](#0-0)  sets `points-ir.rate` via `(pack-u16 points none)`. `pack-u16` clamps only to `MAX-U16` when `upper` is `none` [2](#0-1) , so each rate point can be as high as `u65535` (655.35% in BPS terms), whereas `set-points-util` enforces `< BPS` (100%) on utilization points [3](#0-2) . There is no analogous upper bound tied to a safe maximum rate for `set-points-rate`.

The interpolated `rate` feeds `next-index` on every accrual:
```
(multiplier (calc-multiplier-delta rate time-delta true))
(calc-index-next idx multiplier)
``` [4](#0-3) 

`calc-multiplier-delta` computes `rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS` (rounded up) [5](#0-4) , and `calc-index-next` computes `idx * multiplier / INDEX-PRECISION` [6](#0-5) . Because Clarity uses checked 128-bit unsigned arithmetic that **reverts on overflow** rather than wrapping, an extreme but DAO-permitted rate (up to `655%`) compounding over repeated accrual calls on the ever-growing `idx` (borrow index) can eventually push the `idx * multiplier` product past `MAX-U128` (`u340282366920938463463374607431768211455`) [7](#0-6) . Once that occurs, every future call to `next-index` (and therefore `accrue`) reverts.

`accrue` is invoked from every vault entry point (deposit, borrow, repay, redeem, `set-fee-reserve`, `set-points-util`, `set-points-rate` itself, etc.), so a perpetual revert in `next-index`/`accrue` bricks the vault entirely — no user can deposit, withdraw, borrow, or repay, and even the DAO cannot fix the rate curve afterward because `set-points-rate` and `set-points-util` also call `(try! (accrue))` before applying the new curve [3](#0-2) , so it too would revert, permanently locking the parameter and the funds.

### Impact Explanation
This is a permanent freezing-of-funds condition: once the compounding index overflows, `accrue()` (and therefore all deposit/withdraw/borrow/repay/parameter-update paths that call it) reverts unconditionally and irrecoverably, since the same overflowing state persists and grows every subsequent attempted accrual. All supplied liquidity and outstanding positions in the affected vault become permanently inaccessible. This matches the "permanent freezing of funds" Critical impact class.

### Likelihood Explanation
Reaching this state requires (a) the DAO/governance to set an extreme `rate` value via `set-points-rate` (permitted up to `u65535`, no BPS-style cap unlike `set-points-util`), and (b) sufficient elapsed time/compounding accruals for `idx` to grow enough that a subsequent multiplication overflows `u128`. This is not attacker-triggerable without a governance action, but it is a genuine missing-bound-check bug (the same root cause pattern as the reported analog) rather than intended DAO discretion — the surrounding code clearly intends bounded values (as shown by the `set-points-util` BPS bound) but omits the equivalent safeguard for `set-points-rate`.

### Recommendation
Bound `set-points-rate` inputs to a sane maximum APY (e.g., pass `(some MAX_SAFE_RATE)` to `pack-u16` analogous to `set-points-util`'s `(some BPS)`), and/or add an explicit `asserts!` checking each rate point against a protocol-defined ceiling before packing, so that `calc-multiplier-delta`/`calc-index-next` can never be driven into an overflow regime regardless of elapsed time between accruals.

### Proof of Concept
1. DAO calls `set-points-rate` with a rate point at `u65535` (655.35% APY, allowed since `pack-u16` only clamps to `MAX-U16`) — no revert, since no BPS bound exists for rate points [8](#0-7) .
2. Over time, borrowers keep the vault utilized near this extreme point; each `accrue`/`next-index` call compounds `idx` by `calc-index-next` using the corresponding huge `multiplier` from `calc-multiplier-delta` [9](#0-8) .
3. As accruals repeat (each accrual's `idx` becomes the base for the next), the cumulative product `idx * multiplier` eventually exceeds `MAX-U128`.
4. The next call to any function that calls `next-index`/`accrue` (deposit, borrow, repay, redeem, or even `set-points-rate`/`set-points-util` themselves, which call `(try! (accrue))` first) reverts due to Clarity's checked-arithmetic overflow.
5. Because every mutating entry point depends on `accrue`, the vault is permanently frozen — including the DAO's own path to correct the rate curve, since correcting it also requires a successful `accrue()` call first.

(define-private (calc-multiplier-delta (rate uint) (time-delta uint) (round-up bool))
  (+ INDEX-PRECISION
    (if round-up
      (mul-div-up rate
                  (* time-delta INDEX-PRECISION)
                  SECONDS-PER-YEAR-BPS)
      (mul-div-down rate
                  (* time-delta INDEX-PRECISION)
                  SECONDS-PER-YEAR-BPS))))

(define-private (calc-index-next (index-curr uint) (multiplier uint))
