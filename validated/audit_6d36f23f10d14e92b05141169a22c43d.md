### Title
Cross-Chain Replay of `SignedDelegateAction` (Meta Transactions) — (`core/primitives/src/action/delegate.rs`)

### Summary

`DelegateAction` (NEP-366 meta transactions) signs a payload that contains no chain-specific binding — no `chain_id`, no `network_id`, and no `block_hash`. The only replay guards are a per-key nonce and a `max_block_height`. Both are chain-agnostic: block heights on NEAR mainnet and testnet overlap, and accounts frequently share the same key pair across networks. A `SignedDelegateAction` created for mainnet can be submitted verbatim on testnet (or any other NEAR network) by any party who observes the signed payload, executing the inner actions against the sender's account on the unintended chain.

### Finding Description

`TransactionV0` and `TransactionV1` include a `block_hash` field in the signed body, which is chain-specific and provides cross-chain replay protection for ordinary transactions. [1](#0-0) 

`DelegateAction` (and `DelegateActionV2`) carry no equivalent field: [2](#0-1) 

The signing hash is computed by `get_nep461_hash()`, which prepends a constant NEP discriminant (`1<<30 + 366`) to the serialized payload and hashes it: [3](#0-2) 

The discriminant is a compile-time constant, not a chain identifier: [4](#0-3) 

`apply_delegate_action` verifies the signature and then checks only `max_block_height` and the nonce — neither of which is chain-specific: [5](#0-4) 

The nonce check in `validate_delegate_action_key` compares against the on-chain access key nonce for the target chain, not the originating chain: [6](#0-5) 

### Impact Explanation

An attacker who observes a `SignedDelegateAction` (e.g., from the mempool, a relayer API, or on-chain data) can submit it to any other NEAR network where:

1. The sender account exists with the same public key registered.
2. The access key nonce on the target chain is lower than the `nonce` in the delegate action.
3. The current block height on the target chain is below `max_block_height`.

All three conditions are routinely satisfied: mainnet and testnet share overlapping block heights (both in the tens-of-millions range), many users register the same key pair on both networks, and testnet accounts typically have lower nonces than their mainnet counterparts.

The inner `actions` execute with `sender_id` as the predecessor, so a `Transfer` action drains the sender's balance on the unintended chain. An `AddKey` action installs an attacker-controlled key. A `FunctionCall` action executes arbitrary contract logic. The relayer's gas cost is irrelevant to the attacker since the attacker wraps the replayed `SignedDelegateAction` in their own outer transaction.

**Corrupted invariant:** A `SignedDelegateAction` authorizes execution on exactly one chain; the missing chain binding allows it to authorize execution on every NEAR network simultaneously.

**Affected impact categories:** unauthorized transaction, stealing or loss of funds, balance manipulation, contract execution flow breakage.

### Likelihood Explanation

- Meta transactions are a live, production feature (NEP-366).
- Signed delegate actions are routinely shared with third-party relayers and are visible on-chain.
- The same key pair on mainnet and testnet is a common user pattern.
- No protocol-level guard prevents cross-chain submission.
- The attacker needs only to observe one valid `SignedDelegateAction` and submit it to a different network — no privileged access required.

### Recommendation

Include a chain-specific domain separator in the `DelegateAction` signed payload, analogous to EIP-712's `chainId`. The natural NEAR equivalent is the genesis block hash (`genesis_hash`), which is unique per network and already available in `ApplyState`. Add a `genesis_hash: CryptoHash` field to `DelegateAction` (and `DelegateActionV2`), include it in the borsh-serialized body that `get_nep461_hash()` hashes, and validate in `apply_delegate_action` that `delegate_action.genesis_hash == apply_state.genesis_hash`. This is a protocol-breaking change requiring a new protocol version gate.

Alternatively, a new `DelegateActionV3` variant can carry the genesis hash while keeping backward compatibility with existing V1/V2 actions during a transition window.

### Proof of Concept

**Setup:** Alice holds 100 NEAR on both mainnet and testnet under the same key pair. She signs a `DelegateAction` on mainnet to transfer 10 NEAR to Bob, with `nonce = 5` and `max_block_height = 140_000_000`.

**Attack:**

1. Bob (or any observer) extracts the `SignedDelegateAction` from the mainnet mempool or from the on-chain transaction that included it.
2. Bob wraps it in a new outer `SignedTransaction` addressed to Alice's account on testnet, signed with Bob's own testnet key (Bob pays the relayer gas).
3. Bob submits this to testnet via `broadcast_tx_commit`.
4. `apply_delegate_action` on testnet:
   - `signed_delegate_action.verify()` passes — the signature is over the same borsh bytes, which are chain-agnostic.
   - `apply_state.block_height (e.g. 138_000_000) <= max_block_height (140_000_000)` — passes.
   - `validate_delegate_action_key` finds Alice's key on testnet with nonce 3 < 5 — passes, advances nonce to 5.
   - The inner `Transfer { deposit: 10 NEAR }` executes, moving 10 NEAR from Alice's testnet account to Bob.
5. Alice loses 10 NEAR on testnet without having authorized any testnet transaction.

The attack is repeatable on every NEAR network where Alice's account exists with a nonce below the replayed value, until `max_block_height` is exceeded on all target chains.

    /// Delegate action hash used for NEP-461 signature scheme which tags
    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
        let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
        hash(&bytes)
    }
