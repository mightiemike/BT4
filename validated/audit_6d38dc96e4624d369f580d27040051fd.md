### No vulnerability found for this question.

**Rationale:**

The claimed broken equality is: *"the reward set (`address_weights`) node A derives for cycle N == the reward set node B derives for cycle N."* Tracing the code shows this equality is never actually violated in a way that breaks consensus:

1. `GlobalStateEvaluator::insert_update` [1](#0-0)  is purely a **local gossip-aggregation helper** used to reach soft agreement among a fixed, already-known `address_weights` set (miner viewpoint, burn view, protocol version, tx-replay set) — it is not the mechanism that determines block acceptance/signature-threshold validity on chain.

2. Both the miner side (`StackerDBListener::new`) and the signer side (`RunLoop`) construct a `GlobalStateEvaluator` **scoped to one specific reward cycle's already-finalized reward set**, derived from `reward_set.signers()` / `SignerEntries::parse` [2](#0-1) . This reward set is deterministically computed once, from a specific anchor block, via `pox_4_compute_and_update_signers` / `pox_5_compute_and_update_signers` in chainstate [3](#0-2) , and stored keyed by `StacksBlockId` [4](#0-3) . Two nodes that have processed the *same* canonical anchor block will always compute the *same* `address_weights` for cycle N — this computation is not node-dependent, it's a pure function of chainstate.

3. The signer runloop explicitly anticipates the cycle-boundary scenario the question describes by maintaining **two parallel `Signer` instances keyed by `reward_cycle % 2`** (current and next cycle), each initialized ahead of the boundary during the next cycle's prepare phase [5](#0-4) . A signer/node that hasn't yet processed the new cycle's anchor block simply has not yet initialized/activated the new-cycle `GlobalStateEvaluator` — it does not accept a block against a stale reward set; it fails closed (`ConfigurationError::StackerDBNotUpdated` [6](#0-5) ) or ignores events for a cycle it hasn't started [7](#0-6) .

4. There is no code path by which `insert_update`'s per-address-weights check causes a *canonical* block to be accepted against one reward set and rejected against a different, equally-canonical reward set for the same cycle. The lagging node is simply behind and will not sign/validate at all until caught up — this is ordinary eventual-consistency/synchronization, not a consensus divergence, chain split, or non-reproducible state root.

The scenario described is a temporary node-sync lag, not a protocol-level divergence in the canonical reward set, and does not meet the Critical/High impact bar (no chain split, no invalid-block-accepted/valid-block-rejected network-wide, no reward mispayment). It is out of scope per the rules against theoretical/non-reproducible findings absent an actual equality violation.

    fn initialize_runloop(&mut self) -> Result<(), ClientError> {
        debug!("Initializing signer runloop...");
        let reward_cycle_info = retry_with_exponential_backoff(|| {
            self.stacks_client
                .get_current_reward_cycle_info()
                .map_err(backoff::Error::transient)
        })?;
        let current_reward_cycle = reward_cycle_info.reward_cycle;
        self.refresh_signer_config(current_reward_cycle);
        // We should only attempt to initialize the next reward cycle signer if we are in the prepare phase of the next reward cycle
        if reward_cycle_info.is_in_next_prepare_phase(reward_cycle_info.last_burnchain_block_height)
        {
            self.refresh_signer_config(current_reward_cycle.saturating_add(1));
        }
        self.current_reward_cycle_info = Some(reward_cycle_info);
        if self.stacks_signers.is_empty() {
            self.state = State::NoRegisteredSigners;
        } else {
            self.state = State::RegisteredSigners;
        }
        Ok(())
    }
