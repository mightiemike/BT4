## Analysis

Confirmed flow: `FinalizeOutbound` (`x/uexecutor/keeper/outbound.go:71-97`) routes any observed outbound — regardless of `TxType`, including `INBOUND_REVERT` and `RESCUE_FUNDS` — to `handleFailedOutbound` on failure or `handleSuccessfulOutbound` on success. `handleSuccessfulOutbound` unconditionally calls `applyGasRefund` for every outbound type. `applyGasRefund` computes `refundRecipient` from `outbound.RevertInstructions.FundRecipient` (falling back to `outbound.Sender`) and feeds it directly into `common.HexToAddress(refundRecipient)` before calling `CallUniversalCoreRefundUnusedGas`, which mints/refunds real PRC20/native value on Push Chain to that address. ## Title
Unvalidated `RevertInstructions.FundRecipient` bypasses the address-format check applied to `Recipient`, causing silent fund misroute/loss - (File: `x/uexecutor/keeper/outbound.go`, `x/uexecutor/types/inbound.go`)

### Summary
This is a direct analog of the Liquorice bug class: `Inbound.ValidateForExecution()` (`x/uexecutor/types/inbound.go:126-175`) validates the primary `Recipient` field with `utils.IsValidAddress(p.Recipient, utils.HEX)` for `FUNDS`/`GAS` types, but the sibling field `RevertInstructions.FundRecipient` — which is used in the exact same fund-routing paths (`buildRevertOutbound`, `handleFailedOutbound`, `applyGasRefund`) — is never subjected to any address-format validation, anywhere in the pipeline (`Canonicalize`, `ValidateBasic`, `ValidateForExecution`).

### Finding Description
`RevertInstructions.FundRecipient` originates from attacker-controlled, ordinary user data: it is populated from the source-chain gateway event (`eventData.RevertFundRecipient` in `universalClient/chains/common/event_processor.go:301-305`), relayed by honest UVs via `MsgVoteInbound`, and also propagated into `OutboundTx.RevertInstructions` from the `UniversalGatewayPC` contract's emitted `revertRecipient` (`x/uexecutor/keeper/create_outbound.go:86-88`), which itself is populated from data an ordinary UEA-execution-triggering user can specify inside their payload.

`Canonicalize()` (`x/uexecutor/types/inbound.go:32-35`) only trims/lenient-canonicalizes `RevertInstructions.FundRecipient` — the doc comment explicitly states "unparseable values are kept trimmed, never rejected." Unlike `Recipient`, which is hard-validated for hex format in `ValidateForExecution` (`x/uexecutor/types/inbound.go:159,169`), `FundRecipient` has no equivalent check anywhere.

This unvalidated value is then fed straight into `common.HexToAddress(...)` in the fund-movement code paths:
- `x/uexecutor/keeper/outbound.go:119` (`handleFailedOutbound` → `CallPRC20Deposit`)
- `x/uexecutor/keeper/outbound.go:206` (`applyGasRefund` → `CallUniversalCoreRefundUnusedGas`)

`go-ethereum`'s `common.HexToAddress` silently converts malformed/non-hex input into the zero address or an arbitrary truncated/padded address rather than erroring. Because `applyGasRefund` is invoked unconditionally by `handleSuccessfulOutbound`/`handleFailedOutbound` from `FinalizeOutbound` for every outbound `TxType` (including `INBOUND_REVERT`), a malformed `FundRecipient` silently redirects the on-chain PRC20/native gas-refund mint to the zero address (or an unintended address) instead of erroring out or falling back safely. ### Impact Explanation
If an ordinary depositor (or a malicious depositor targeting *their own* revert flow, or one who mis-encodes/malforms this field) supplies a non-hex `FundRecipient` string, the excess-gas refund minted by `applyGasRefund` (and, in the deposit-failure re-mint path, `handleFailedOutbound`) is silently sent to the zero address instead of erroring or falling back to `Sender`. This is a **permanent loss/freezing of protocol-minted PRC20/native value** — funds that should have been returned to the user are burned to an unreachable address, matching the in-scope "permanent loss, permanent freezing... of user or protocol-controlled funds" category. Because `common.HexToAddress` never errors, there is no failure signal recorded — the `PCTx` will show `SUCCESS` with a lost-fund destination, silently corrupting refund accounting.

### Likelihood Explanation
Medium. Triggering requires only an ordinary user/depositor supplying an unvalidated string in the gateway-event's revert-recipient field (or a payload-driven outbound whose `revertRecipient` is malformed) — no privileged actor or validator misbehavior is required, since honest UVs and honest nodes faithfully relay/execute whatever value was embedded in the observed event. The trigger conditions (deposit failure, or any outbound with excess gas to refund) are common, non-adversarial execution paths.

### Recommendation
Apply the same address-format validation used for `Recipient` to `RevertInstructions.FundRecipient` in `Inbound.ValidateForExecution()` (and the analogous `OutboundTx.RevertInstructions` construction path in `create_outbound.go`), rejecting non-hex values before they reach `buildRevertOutbound`, `handleFailedOutbound`, or `applyGasRefund`. If validation fails, fall back explicitly to `Sender`/`outbound.Sender` (as already done when the field is empty) rather than allowing `common.HexToAddress` to silently substitute the zero address.

### Proof of Concept
1. An external depositor triggers a source-chain gateway deposit event carrying a `TxType_FUNDS` (or `GAS`) inbound whose `revertFundRecipient` field is a non-hex string (e.g., `"not-an-address"`).
2. UVs faithfully relay this via `MsgVoteInbound`; `Canonicalize()` and `ValidateBasic()`/`ValidateForExecution()` never reject `RevertInstructions.FundRecipient` (only `Recipient` is checked).
3. Force a deposit-step failure (e.g., missing token config, as already exercised in `test/integration/uexecutor/vote_inbound_validation_test.go:312-364`), causing `buildRevertOutbound` to set `outbound.Recipient` and (via `OutboundTx.RevertInstructions`) the eventual gas-refund recipient to the malformed string.
4. When the resulting outbound is finalized (`FinalizeOutbound` → `handleFailedOutbound`/`applyGasRefund`), `common.HexToAddress("not-an-address")` resolves to the zero address, and `CallPRC20Deposit`/`CallUniversalCoreRefundUnusedGas` mints/refunds the value to `0x000...000`, permanently losing the funds instead of returning them to `Sender`.

*Note: I was not able to fully trace whether `applyGasRefund` is reachable for `INBOUND_REVERT`-typed outbounds specifically in this session (time-limited), so the `handleFailedOutbound`/deposit re-mint path for `FUNDS`/`GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` outbound types is the most concretely verified trigger; the `INBOUND_REVERT`-refund path should be independently confirmed by a follow-up session with access to `msg_vote_outbound.go` and full outbound dispatch logic.*

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}
