### Title
Collateral balance is credited before the underlying token transfer completes, enabling reentrant double-crediting via a malicious `ft-trait` implementation - (File: `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`collateral-add` binds `result` to `(add-user-collateral user-id asset-id amount)` inside its `let`, which unconditionally executes `map-set collateral key updated-collateral-amount` at bind time — before any of the function's `asserts!` guards and before the token transfer (`receive-tokens`) that is supposed to back that credit.

### Finding Description
In `mainnet/contracts/market/v0-market-vault.clar:374-404`:
```
(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        ...
        (result (add-user-collateral user-id asset-id amount)))   ;; <- map-set already happened here

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))   ;; external call to arbitrary ft contract
    (insert updated-entry)
    ...
    (ok result)))
```
`add-user-collateral` (lines 198-203) is not a pure computation — it performs `map-set collateral key updated-collateral-amount` immediately. Because Clarity evaluates `let` bindings sequentially before the body, this map mutation is committed to contract state as soon as the `let` list is evaluated, i.e., before `check-impl-auth`, before the pause/amount checks, and before `receive-tokens` calls `(contract-call? asset transfer amount account current-contract none)` on an attacker-supplied `ft` (line 256-257, `receive-tokens`).

Because `ft` is a caller-supplied `<ft-trait>` implementation (not a fixed, trusted contract), its `transfer` function can contain arbitrary logic, including a callback into `collateral-add` (or the wrapping `market.clar` function) again before returning control. During that nested call, the outer call's `collateral` map entry for `{id: user-id, asset: asset-id}` has already been incremented by `amount`, even though the corresponding token transfer for the outer call has not yet succeeded or failed. This is the same bug class as the reported `_deposit`-before-transfer issue: a queued/credited balance is incremented ahead of the transfer that is supposed to justify it, and reentrancy through the transfer hook can compound the credit without proportional backing tokens ever moving.

This differs from the sibling vault `deposit` functions (e.g., `mainnet/contracts/vault/v0-vault-stx.clar:779-781`), which correctly call `(try! (receive-underlying amount account))` before minting shares — those are safe. `collateral-add` in the market-vault does the opposite ordering for its state mutation.

### Impact Explanation
A malicious/crafted `ft` contract passed to `collateral-add` (reachable via `market.clar`'s `collateral-add`/`supply-collateral-add` public entry points, which forward the trait argument through) can reenter and accumulate collateral credits in the `collateral` map disproportionate to tokens actually transferred to the vault. Since collateral drives borrowing capacity in the lending market, this allows a user to inflate their recorded collateral and borrow against value that was never deposited — this is direct theft of protocol funds / insolvency, landing in the Critical impact class (theft of funds / protocol insolvency).

### Likelihood Explanation
The precondition is a caller-controlled `<ft-trait>` argument whose `transfer` implementation performs a reentrant call — this is fully within a single caller-controlled transaction and does not require any privileged access, DAO compromise, or interference from a second user. The `<ft-trait>` genericity is inherent to how `collateral-add`/`market.clar` accept arbitrary supported assets, so the attack surface exists for any asset registered through this interface where the token contract itself is attacker-influenced or attacker-supplied at the trait-call site.

### Recommendation
Reorder `collateral-add` so that the state-mutating `add-user-collateral` call happens only after all guards (`check-impl-auth`, pause check, amount check) pass and after `receive-tokens` has confirmed the token transfer succeeded — mirroring the correct pattern already used in the vault `deposit` functions (transfer/receive first, state mutation last). Concretely, move the `(add-user-collateral user-id asset-id amount)` call out of the `let` bindings and into the function body, placed after `(try! (receive-tokens ft amount account))`.

### Proof of Concept
1. Attacker deploys a malicious contract implementing `ft-trait` whose `transfer` function, when invoked with `sender = account` and `recipient = current-contract` (the market-vault), calls back into `.market-vault collateral-add` with the same `account`/`asset-id` before returning `(ok true)`.
2. Attacker calls `collateral-add account amount maliciousFt asset-id`.
3. Evaluation of the `let` bindings runs `add-user-collateral user-id asset-id amount`, which does `map-set collateral {id: user-id, asset: asset-id} amount` — collateral is now credited.
4. Execution reaches `(try! (receive-tokens ft amount account))`, which calls into the malicious `ft` contract's `transfer`.
5. Inside that call, the malicious contract reenters `collateral-add account amount maliciousFt asset-id` again. The reentrant call's `let` bindings re-read `collateral-amount` (now `amount` from step 3) and add `amount` again, doubling the credited collateral to `2*amount` via a second `map-set`, all before any second token transfer has occurred (or even before the first has completed).
6. The malicious `transfer` then returns `(ok true)` without actually moving `amount` tokens (or moves a fraction of it), and the outer call proceeds to complete, leaving the attacker with `2*amount` (or more, with deeper recursion) of recorded collateral backed by only `amount` (or less) of real tokens transferred into the vault.
7. Attacker then borrows against the inflated collateral via `market.clar`'s borrow flow, extracting real assets from the protocol. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
