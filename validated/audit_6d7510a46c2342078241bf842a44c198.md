### Title
Concurrent bucket resize requests can violate the "single active reallocation" invariant and panic the validator - ([File: bucket_map/src/bucket.rs])

### Summary
`BucketApi::grow()` only acquires a **read** lock on the bucket before triggering an index/data-bucket resize, explicitly to allow it to run concurrently with other read-lock holders. However, the resize path (`Bucket::grow_index` / `Bucket::grow_data`) records the pending resize via `Reallocated::add_reallocation()`, which asserts that at most one reallocation can be in flight at a time. Because the "check that no other resize is already pending" is enforced only by an `assert_eq!` inside `add_reallocation()` and not by any lock/mutual-exclusion mechanism between concurrent `grow()` callers, two threads that both hit `BucketMapError` for the same bucket at nearly the same time can both proceed to record a reallocation, and the second one panics.

### Finding Description
`BucketApi::try_write()` takes a **write** lock via `get_write_bucket()`, which also drains any previously pending resize (`handle_delayed_grows()`) before performing the write. If the write fails with `BucketMapError::IndexNoSpace`/`DataNoSpace`, callers (e.g. `InMemAccountsIndex::write_to_disk` at [1](#0-0) ) call `disk.grow(err)` *outside* of that write lock: [2](#0-1) 

`BucketApi::grow()` deliberately takes only a **read** lock ("grows are special - they get a read lock and modify 'reallocated'; the grown changes are applied the next time there is a write lock taken"), so multiple concurrent callers can enter `Bucket::grow()`/`grow_index()`/`grow_data()` at once since `RwLock` permits multiple simultaneous readers: [3](#0-2) 

Each of `grow_index()` and `grow_data()` finishes by calling `self.reallocated.add_reallocation()`: [4](#0-3) 

`Reallocated::add_reallocation()` enforces the "only one active reallocation" invariant with a hard `assert_eq!`, not a `try_lock`/CAS retry or queuing mechanism: [5](#0-4) 

This mirrors the Delay-app bug class: an operation (`pauseExecution`) proceeded based on state that could concurrently change (`executionTime` already elapsed) without a proper guard, because the precondition check ("no pause/resize already active") is checked-then-acted in a way that isn't atomic with respect to concurrent actors. Here, two racing `grow()` calls both pass through code that computes a brand-new resized bucket (a nontrivial, unlocked amount of work) and only at the very end attempt to atomically register "I am the one active reallocation" — by which point a concurrent racer may already have registered its own, and the second call hits the assertion and panics the thread instead of failing gracefully or being naturally serialized.

### Impact Explanation
`add_reallocation()`'s failure path is `assert_eq!(0, ...)`, which panics the calling thread. This code sits on the hot path for the disk-backed accounts index (`in_mem_accounts_index.rs`), used during ordinary account writes/flushes when the index or data bucket becomes full and needs to grow — this is triggered purely by normal user activity that creates new accounts (each new pubkey is an index insertion), not by any validator/operator-only code path. A panic here would abort the validator/thread process, constituting a node panic caused by unprivileged (regular transaction) activity that increases the account/index population enough to trigger concurrent bucket growth.

### Likelihood Explanation
Triggering this requires two writers (e.g., a synchronous `write_through` call from active transaction processing and a background disk-index flush thread, or two flush workers) to independently hit `BucketMapError` for the *same* bucket bin at close to the same time — a plausible but timing-dependent race under sufficient concurrent account-creation load, since bucket bins are shared across many pubkeys and disk-index growth is not rare when the index is under memory pressure.

### Recommendation
Make the "only one active reallocation" invariant race-safe instead of assert-based: use `compare_exchange` (or a `try_lock`-style API) in `add_reallocation()` to detect an already-pending reallocation and either (a) skip performing the (now redundant) resize work and return, or (b) serialize concurrent growers with an actual lock rather than only a read lock, so a second racer waits for the first grow to be applied via `handle_delayed_grows()` before attempting its own.

### Proof of Concept
1. Populate the disk-backed accounts index bucket map so a particular bucket bin is near full (achievable purely through ordinary account creation/writes across many pubkeys hashing into the same bin).
2. From the account-store path, trigger a synchronous `try_write_through`/`write_through` call for a pubkey in that bin while the background index-flush thread (`InMemAccountsIndex` flush logic) concurrently calls `write_to_disk` for a different pubkey in the same bin.
3. Both threads observe `BucketMapError::IndexNoSpace`/`DataNoSpace` from `try_write`, and each calls `BucketApi::grow(err)`, which takes a read lock and proceeds to `Bucket::grow_index`/`grow_data`.
4. If both threads compute their resize and call `add_reallocation()` before either applies its result via a write lock (`handle_delayed_grows()`), the second call's `assert_eq!(0, self.active_reallocations.fetch_add(1, ...))` fails, panicking the thread with "Only 1 reallocation can occur at a time".

    pub fn grow_index(&self, mut current_capacity: u64) {
        if self.index.contents.capacity() == current_capacity {
            // make sure to grow to at least % more than the anticipated size
            // The indexing algorithm expects to require some over-allocation.
            let anticipated_size = self.anticipated_size * 140 / 100;
            let mut m = Measure::start("grow_index");
            //debug!("GROW_INDEX: {}", current_capacity_pow2);
            let mut count = 0;
            loop {
                count += 1;
                // grow relative to the current capacity
                let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
                let (mut index, file_name) = BucketStorage::new_with_capacity(
                    Arc::clone(&self.drives),
                    1,
                    std::mem::size_of::<IndexEntry<T>>() as u64,
                    Capacity::Actual(new_capacity),
                    self.index.max_search,
                    Arc::clone(&self.stats.index),
                    Arc::clone(&self.index.count),
                );
                // index may have allocated something larger than we asked for,
                // so, in case we fail to reindex into this larger size, grow from this size next iteration.
                current_capacity = index.capacity();
                let mut valid = true;
                for ix in 0..self.index.capacity() {
                    if !self.index.is_free(ix) {
                        let elem: &IndexEntry<T> = self.index.get(ix);
                        let new_ix =
                            Self::bucket_create_key(&mut index, &elem.key, self.random, true);
                        if new_ix.is_err() {
                            valid = false;
                            break;
                        }

                        let new_elem: &mut IndexEntry<T> = index.get_mut(new_ix);
                        *new_elem = *elem;

    /// grow a data bucket
    /// The application of the new bucket is deferred until the next write lock.
    pub fn grow_data(&self, data_index: u64, current_capacity_pow2: u8) {
        let (new_bucket, _file_name) = BucketStorage::new_resized(
            &self.drives,
            self.index.max_search,
            self.data.get(data_index as usize),
            Capacity::Pow2(std::cmp::max(
                current_capacity_pow2 + 1,
                DEFAULT_CAPACITY_POW2,
            )),
            1 << data_index,
            Self::elem_size(),
            &self.stats.data,
        );
        self.reallocated.add_reallocation();
        let mut items = self.reallocated.items.lock().unwrap();
        items.data = Some((data_index, new_bucket));
    }

    fn bucket_index_ix(key: &Pubkey, random: u64) -> u64 {
        // the locally generated random will make it hard for an attacker
        // to deterministically cause all the pubkeys to land in the same
        // location in any bucket on all validators
        let hasher_builder = ahash::RandomState::with_seeds(random, random, random, random);
        hasher_builder.hash_one(key)
    }

    /// grow the appropriate piece. Note this takes an immutable ref.
    /// The actual grow is set into self.reallocated and applied later on a write lock
    pub(crate) fn grow(&self, err: BucketMapError) {
        match err {
            BucketMapError::DataNoSpace((data_index, current_capacity_pow2)) => {
                //debug!("GROWING SPACE {:?}", (data_index, current_capacity_pow2));
                self.grow_data(data_index, current_capacity_pow2);
            }
            BucketMapError::IndexNoSpace(current_capacity) => {
                //debug!("GROWING INDEX {}", sz);
                self.grow_index(current_capacity);
            }
        }
