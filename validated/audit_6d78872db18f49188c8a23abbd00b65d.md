### Title
Unmetered ELF verification/JIT-compilation cost in `DeployWithMaxDataLen`/`Upgrade` allows CU-cheap block packing that degrades leader block-production liveness - ([File: cost-model/src/cost_tracker.rs])

### Summary
`CostTracker::would_fit`/`block_cost` gate block admission purely on `TransactionCost::sum()` (signature + write-lock + data-bytes + `programs_execution_cost` + `loaded_accounts_data_size_cost`), while the actual wall-clock-dominant work of an upgradeable-loader deploy — `Executable::load` (`load_elf_us`), `RequisiteVerifier::verify` (`verify_code_us`), and `jit_compile` (`jit_compile_us`) inside `deploy_program` — is never charged to the compute meter or folded into the cost model. An attacker can therefore submit many `DeployWithMaxDataLen`/`Upgrade` instructions in one block, each nominally costing only the fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS` (2,370 CU) plus a small requested CU limit, while consuming disproportionate real CPU time verifying/JIT-compiling large ELF payloads during block production.

### Finding Description
`would_fit` computes `let cost: u64 = tx_cost.sum();` and compares it against `self.limits.block_cost` (`MAX_BLOCK_UNITS`) [1](#0-0) . `TransactionCost::sum()` only aggregates `signature_cost`, `write_lock_cost`, `data_bytes_cost`, `programs_execution_cost`, and `loaded_accounts_data_size_cost` [2](#0-1) .

For a builtin loader instruction, `programs_execution_cost` comes from the requested/estimated compute-unit limit, not from the actual ELF size or verification complexity [3](#0-2) . When the instruction actually executes, `process_instruction_inner` charges a fixed constant, `UPGRADEABLE_LOADER_COMPUTE_UNITS = 2_370`, for *any* `bpf_loader_upgradeable` invocation regardless of program size [4](#0-3) .

The real CPU-intensive work happens inside `deploy_program`, invoked via the `deploy_program!` macro from the `DeployWithMaxDataLen` handler [5](#0-4) . `deploy_program` performs `Executable::load` (ELF parsing), `executable.verify::<RequisiteVerifier>()`, and (on x86_64) `executable.jit_compile()` — none of which consume `invoke_context.compute_meter` — and only records timing into `LoadProgramMetrics` (`load_elf_us`, `verify_code_us`, `jit_compile_us`) [6](#0-5) . These metrics feed only `ExecuteDetailsTimings`/telemetry via `submit_datapoint`, never the cost tracker or compute budget [7](#0-6) .

Consequently, an attacker who pre-stages N buffer accounts each containing a maximal-size, verification/JIT-heavy ELF (up to `MAX_PERMITTED_DATA_LENGTH`, checked only at [8](#0-7) ), and then submits N `DeployWithMaxDataLen` transactions in a single block, can make `would_fit` accept far more real CPU-seconds of verify+JIT work than `MAX_BLOCK_UNITS` was designed to bound — because none of that time is priced into `cost.sum()`.

### Impact Explanation
This is a liveness-degradation issue (Solana bounty category: DoS / validator liveness): a leader spends real wall-clock time on ELF verification and JIT compilation that is invisible to the block-cost accounting used to bound per-slot processing time, risking slot-processing overruns/slowdowns even though `cost_tracker` reports the block as well under `MAX_BLOCK_UNITS`. It does not lead to fund loss, double-spend, or consensus divergence by itself — it is scoped to processing-time/liveness impact.

### Likelihood Explanation
Preconditions are attacker-affordable but not free: N buffer/program/programdata accounts each sized near `MAX_PERMITTED_DATA_LENGTH` require substantial rent-exempt lamports and prior `Write` transactions to populate (done ahead of time, off the critical block). Given funded keypairs, the actual attack transactions (`DeployWithMaxDataLen`) are individually cheap in CU terms (~2,370 CU fixed + small requested budget), so many can be packed per block within `MAX_BLOCK_UNITS`. The attack is repeatable per slot the attacker can land transactions in, and requires no privileged access — only ordinary client transaction submission and control over ELF byte content to maximize `verify`/`jit_compile` cost.

### Recommendation
Incorporate an ELF-size/complexity-dependent cost component into the cost model and/or compute-meter accounting for `bpf_loader_upgradeable` deploy/upgrade/extend instructions, proportional to the buffer/program data length actually passed to `deploy_program`, so that `would_fit`/`block_cost` (and ideally the compute budget itself) reflect real `load_elf`/`verify`/`jit_compile` cost rather than the flat `UPGRADEABLE_LOADER_COMPUTE_UNITS` constant. Alternatively, meter `deploy_program`'s stages against `invoke_context.compute_meter` so a failed/expensive verification is charged CUs proportional to work performed, and have the cost model estimate this ahead of execution based on buffer size.

### Proof of Concept
1. Unit test in `cost-model/src/cost_tracker.rs` tests module: build several `TransactionCost` instances representing `DeployWithMaxDataLen` transactions with large `allocated_accounts_data_size`/buffer sizes but nominal `programs_execution_cost` (~2,370 + small CU), and show `would_fit` accepts many of them well under `MAX_BLOCK_UNITS`.
2. Integration test extending `core/tests/scheduler_cost_adjustment.rs`'s `deploy_with_max_data_len_ix` helper (already present) to use maximal-size adversarial ELF buffers; submit N such instructions across N transactions in one bank/block via `Consumer::process_and_record_transactions`, assert `cost_tracker.block_cost() <= block_limit` while measuring wall-clock time of `process_and_record_transactions` and asserting it is dominated by `ExecuteDetailsTimings::create_executor_verify_code_us`/`create_executor_jit_compile_us` (already exposed and asserted non-zero in `svm/tests/integration_test.rs::svm_metrics_accumulation`) rather than by CU-based expectations.
