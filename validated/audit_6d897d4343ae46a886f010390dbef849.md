**Analysis:**

The premise doesn't hold up under review of the actual code path.

1. **`ContractEventV2::size()` is deterministic and stateless.** It computes `bcs::serialized_size(&self.type_tag)? + self.event_data.len()` purely from the struct's current field values [1](#0-0) . It is not a cached flag set at construction time — it's recomputed every time `ContractEvent::size()` is called [2](#0-1) . So even if a `ContractEventV2` were constructed via `bcs::from_bytes` directly (bypassing `ContractEventV2::new`), calling `.size()` later would produce the *same* result as if `new()` had been called — either both succeed or both fail identically, since the computation only depends on `type_tag` and `event_data.len()`, not on how the struct was built.

2. **The `size()?` check in `new()` only guards against `bcs::serialized_size` erroring**, which practically only happens for pathological `TypeTag` structures (e.g. exceeding BCS's container-depth limits), not for large `String`/byte payloads — BCS byte vectors support lengths up to `u32::MAX`, so an oversized `collection`/`token` string in `MaximumMutate` would not make `bcs::serialized_size(&self.type_tag)` fail; `MaximumMutate`'s bytes live in `event_data: Vec<u8>`, whose `.len()` never errors. So the described attack input (large strings) doesn't even reach the failure mode the question assumes.

3. **No unprivileged path can inject a raw `ContractEvent::V2` into committed storage bypassing `new_v2`.** All real event producers go through `ContractEvent::new_v2`/`ContractEventV2::new`: the native event runtime [3](#0-2) , the MonoMove output path [4](#0-3) , and test/proptest generators [5](#0-4) . The storage schema's `decode_value` does call `bcs::from_bytes` directly [6](#0-5) , but this only deserializes bytes that were already committed by consensus after VM execution produced them via `new_v2` — an attacker cannot write arbitrary bytes into this column family without direct, trusted access to the RocksDB store, which is explicitly out of scope ("trusted operator mistakes").

4. **Even in the hypothetical failure case**, `ContractEvent::size()` calling `.expect(...)` would panic (fail-stop) rather than silently produce a wrong/corrupted size used downstream [2](#0-1) . A panic is not "corruption of write-set serialization, transaction info, or versioned state," it's a crash, and it can't occur from unprivileged transaction/event content since normal `TypeTag`s (bounded by the type system) always serialize successfully.

In short, deriving `Serialize`/`Deserialize` on `ContractEventV2` without calling `new()` doesn't skip any state that `new()` cached — `size()` is idempotent and content-derived, and no unprivileged path can smuggle a bypassed `ContractEvent::V2` into committed ledger state, proofs, or storage. This does not meet the bar of corrupting authenticated state, proof material, or causing divergence.
