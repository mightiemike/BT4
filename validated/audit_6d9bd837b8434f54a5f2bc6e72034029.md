### Title
Single-Asset Bad-Debt Socialization Failure Reverts Entire Liquidation - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate()` in `v0-4-market.clar` folds `socialize-debt-asset` over a borrower's remaining debt-asset list to write off bad debt when no collateral is left. If the write-down for any single debt asset in that list fails, the fold's accumulator flips to `success: false`, the subsequent `asserts!` reverts the transaction, and the entire liquidation (collateral seizure, debt repayment, obligation update) is undone. This mirrors the reported `PrimeStrategy.withdraw()` pattern: a loop over a list of external targets where one failure blocks the whole operation.

### Finding Description
`liquidate()` computes `no-collateral-left` and, when true, builds `fresh-debt-list` — the borrower's remaining debt entries across potentially multiple assets — and folds `socialize-debt-asset` over it: [1](#0-0) 

`socialize-debt-asset` itself is a fold callback with a "short-circuit on first failure" pattern: once `success` becomes `false` for any entry, it stops doing any further work but still needs the whole fold to complete, and the outer caller asserts on the aggregate `success` flag: [2](#0-1) 

Each iteration calls three external/state-changing operations that can fail: `vault-socialize-debt`, `vault-accrue`, and `.v0-market-vault debt-remove-scaled`. Any one of these failing for a single asset (e.g. that vault being paused, or a supply/precondition check failing) sets `success: false` for the whole accumulator. Because the fold has already been evaluated for all list entries by the time `asserts!` runs, and because `liquidate()` has already performed `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` earlier in the same transaction, the `asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED` at line 1548 reverts the entire multi-step liquidation, not just the failed socialization sub-step: [3](#0-2) 

This is the same bug class as the reported issue — a fold/loop over a list of external-facing targets that absorbs an individual failure into a global result, with no fallback (try/catch equivalent), so a problem localized to one asset's vault (e.g. a paused vault, as seen with `ERR-PAUSED` pause-state guards present in each vault contract) blocks the entire multi-asset operation: [4](#0-3) 

### Impact Explanation
When a borrower's position has debt spread across multiple assets and ends up with zero collateral, liquidators cannot complete the liquidation (and thus cannot seize collateral or repay debt) if even one of the borrower's debt vaults is paused or otherwise reverts on `socialize-debt`/`accrue`/`debt-remove-scaled`. This strands the position in an unliquidatable, insolvent state, freezing the collateral seizure and debt write-down until a DAO/manager action (e.g. unpausing the affected vault) is taken — a temporary freezing-of-funds condition analogous to the reported `PrimeStrategy.withdraw()` DoS, rather than a design decision (this is not a deliberate "disabled collateral" liquidation block; it is an unrelated vault's pause state stalling an otherwise-valid liquidation of a different, undercollateralized position).

### Likelihood Explanation
Requires: (1) a borrower position with debt across ≥2 assets and zero remaining collateral after a partial/full liquidation, and (2) one of those debt-asset vaults being paused (or otherwise reverting) at the moment bad-debt socialization runs. Vault pausing is an operational/administrative action that can occur at any time (e.g., incident response), so the interleaving is plausible without requiring attacker-controlled state, making this a realistic single-transaction failure mode rather than a contrived edge case.

### Recommendation
Do not let a single asset's socialization failure abort the whole `liquidate()` transaction after collateral/debt state has already been mutated. Either: (a) make `socialize-debt-asset` tolerant of individual asset failures (skip and continue, tracking which assets succeeded, rather than short-circuiting the whole fold to `false`), or (b) move bad-debt socialization out of the atomic liquidation path into a separate, retryable step so a paused/failing vault for one debt asset cannot block collateral seizure and debt repayment for the liquidation itself.

### Proof of Concept
1. Borrower has debt in `USDC` and `USDH` vaults, backed by collateral that liquidator seizes down to zero (`no-collateral-left` becomes `true`).
2. Liquidator calls `liquidate()`; contract performs `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` successfully.
3. Contract builds `fresh-debt-list` containing the remaining `USDC` and `USDH` debt entries and folds `socialize-debt-asset` over it.
4. `USDC` vault is paused (DAO/manager toggled `pause-states` for `socialize-debt`), so `vault-socialize-debt` for `USDC` fails inside the fold, setting `success: false` in the accumulator.
5. The fold completes (short-circuiting further work but still returning `success: false`); `asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED` reverts.
6. The entire `liquidate()` call reverts, undoing the otherwise-valid collateral seizure and debt repayment, leaving the insolvent position un-liquidated until the paused vault is fixed by the manager.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
