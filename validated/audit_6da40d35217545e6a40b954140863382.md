### Title
Market's per-block index cache is not invalidated when a vault's index moves via a direct vault call within the same block - (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/vault/v0-vault-*.clar`)

### Summary
`market.clar` caches each vault's `index`/`lindex` keyed only by `{ stacks-block-time, aid }` [1](#0-0) . The cache is populated the first time any market operation touches an asset in a block and is then reused for the rest of that block, on the assumption that "no manual invalidation needed... eliminates stale data risks" [2](#0-1) . However, vault contracts (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, etc.) expose public `deposit`/`redeem`/`transfer` entry points that each independently call `accrue`, mutating the vault's `index`, `lindex`, and `last-update` outside of market's control [3](#0-2) [4](#0-3) . Because the market's cache key is only `(timestamp, aid)` and does not track whether the vault's underlying index has since moved via one of these direct calls, a stale cached index can be reused for subsequent market operations in the same block.

### Finding Description
1. A user calls a market operation (e.g. borrow, health check, liquidation) that touches asset `aid`. Market's `accrue-and-cache` sees no cache entry for `{ timestamp: T, aid }`, calls the vault's `accrue`, and stores the resulting `{ index, lindex }` in `index-cache-` [5](#0-4) .
2. Within the same block `T`, the same user (or anyone) calls the vault's own public `deposit` or `redeem` directly (bypassing market). Both entry points call `(try! (accrue))` first, which recomputes `next-index`/`next-liquidity-index` from `interest-rate`, mints treasury shares, and updates `index`, `lindex`, and `last-update` in the vault's own storage [4](#0-3) . Because `time-delta` is computed from `last-update`, and utilization/rate can change due to the deposit/redeem itself, the vault's index for that same timestamp `T` can differ from what was already cached by market.
3. A further market operation in the same block `T` for the same `aid` (e.g. a second borrow, a notional/health calculation, or a liquidation check) calls `get-cached-indexes`, which returns the earlier cached (now stale) `{ index, lindex }` rather than re-querying the vault, since the cache entry for `{ timestamp: T, aid }` already exists [6](#0-5) .
4. Market then values collateral/debt notionals and evaluates health/LTV using the stale index instead of the vault's actual current index, even though the source of truth (the vault) has already moved within the same block.

### Impact Explanation
Health/LTV checks and notional valuations are core solvency guards described in `docs/market.md` ("Health = (Collateral × LTV) >= Debt") [7](#0-6) . If the cache serves a stale (lower) debt index or a stale (lower) collateral `lindex` after a same-block direct vault interaction, a borrower could pass a health check that should have failed with the updated index, allowing borrowing beyond what collateral actually supports, or letting a position dodge liquidation it should be subject to. This constitutes a protocol-solvency risk (funds freezing/insolvency), which falls in the in-scope Critical/High impact classes.

### Likelihood Explanation
This requires only a single attacker acting within a single block: no second party, no flashloan mechanics, no DAO/oracle compromise. It relies purely on the fact that vault entry points (`deposit`, `redeem`, `transfer`) are public and independently trigger `accrue`, while market's cache invalidation is coarse-grained (per timestamp only, not per actual index state). This satisfies the required "cached value not invalidated when its source moves" pattern and is reachable through vault contracts that are explicitly documented as directly callable by users, in parallel to market's rehypothecated-collateral flow [8](#0-7) .

### Recommendation
Either (a) have market always re-derive/re-verify the vault's `last-update`/index at time of use rather than trusting a timestamp-keyed cache blindly, or (b) route all vault `accrue`-triggering operations (deposit/redeem/transfer) through market so the cache and vault state can never diverge within a block, or (c) invalidate/refresh the cache entry whenever the corresponding vault's `last-update` changes, rather than relying solely on the block timestamp key.

### Proof of Concept
Not independently executed against the mainnet contract due to index-search limits on the full `v0-4-market.clar` cache-consumption call sites (only doc-level and vault-level evidence was retrievable). The mechanism is demonstrated by the documented cache-population code path and the vault `deposit`/`redeem`/`accrue` definitions cited above; a Devin session with full repository access would be needed to trace every `get-cached-indexes` consumer in `v0-4-market.clar` and confirm no additional invalidation check exists before this is treated as confirmed rather than a strong analog.

(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-read-only (get-cached-indexes (aid uint))
  (map-get? index-cache- { timestamp: stacks-block-time, aid: aid }))

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache- cache-key)))
    (match cached?
      existing existing  ;; Return cached if exists
      (let ((fresh (vault-accrue aid)))  ;; Otherwise accrue vault
        (map-set index-cache- cache-key fresh)
        fresh))))
