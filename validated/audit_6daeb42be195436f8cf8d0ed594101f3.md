Based on my investigation, I found a genuine, self-documented state-integrity gap in transaction-output verification that is structurally analogous to the reserve-factor bug: a validation routine that is supposed to bind committed output to the *correct, complete* expected state is only checking a subset of the fields, silently accepting an incorrect/incomplete result as "verified."

### Title
Chunk/replay transaction-output verification ignores state-checkpoint hashes, allowing state-root divergence to be accepted as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by the chunk executor, replay-verify tooling, and CLI replay comparisons) is the function that is supposed to bind a freshly computed/replayed `TransactionOutput` to the authenticated `TransactionInfo` carried in a verified accumulator/ledger proof. It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that summarize the resulting global/position state root at that transaction.

### Finding Description
`ensure_match_transaction_info` compares:
- execution status,
- gas used,
- write-set hash (`state_change_hash`),
- event root hash,

against the values carried in `TransactionInfo`, which is itself authenticated by an accumulator/consistency proof back to a `LedgerInfo`. [1](#0-0) 

It never checks `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the actual resulting state root computed locally. This gap is called out in the code's own comment: [2](#0-1) 

This function is the sole state-binding check used by:
- the chunk executor (`execution/executor/src/chunk_executor/mod.rs`),
- the backup/replay-verify tool `storage/db-tool/src/replay_on_archive.rs`,
- `aptos-debugger` and CLI transaction replay (`aptos-move/cli/src/commands.rs`, which materializes VM output then calls `ensure_match_transaction_info`) [3](#0-2) 

None of these callers independently re-verify the state (Merkle) root against the transaction info's `state_checkpoint_hash` when this comparator is the check being relied on. Since the write-set hash only proves the *write set itself* is unchanged, and the event-root hash only proves *events* are unchanged, neither one binds the resulting state to the correct pre-state application: a JMT/state-merkle computation bug, a hot-state divergence, or (once trading-native/position state is enabled) a diverging `position_state_checkpoint_hash` can produce a `TransactionOutput` whose write set/events serialize identically but whose materialized state root differs, and `ensure_match_transaction_info` will still report success.

### Impact Explanation
This is exactly the same *bug class* as the reserve-factor issue: a verification/commitment formula omits a term it is supposed to include (there, the reserve factor is applied to the wrong base; here, the checkpoint/root-hash terms are omitted entirely from the equality check), so an incorrect underlying computation is accepted as correct. In this codebase, that means replay-verification tooling (`db-tool replay_on_archive`) and the chunk executor's transaction-output/committed-info equivalence check can both report a "successful" match even though the authenticated state root (main state, hot state, or position state) diverges from what local execution actually produced. This directly threatens the "state that differs from correct VM result... accepted as valid" and "authenticated API or state-view output bound to the wrong version/root" impact categories, since replay tooling and archival correctness checks are precisely the safety net meant to catch state-commitment divergence (hard forks, storage corruption, non-deterministic execution bugs).

### Likelihood Explanation
The gap is unconditionally present in `ensure_match_transaction_info` for every caller — it does not require the trading-native/position feature to be enabled to be missing the ordinary `state_checkpoint_hash` check (the position-specific fields are additionally omitted once that feature ships). Because this function is a diagnostic/verification safety net rather than the primary consensus-critical proof-verification path (`TransactionAccumulatorProof::verify`, `SparseMerkleProof::verify`, etc., which I confirmed are implemented correctly and are not analogous to this bug), the practical impact is bounded to "verification tooling reports false positives," not a bypass of consensus-critical state commitment itself. I could not fully confirm within the remaining budget whether some other layer (e.g., inside the chunk executor's broader commit path) independently re-derives and compares the state-checkpoint hash before this function is invoked, which would reduce this to a pure tooling/diagnostic gap rather than an exploitable integrity bypass.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally computed state root(s) — `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when enabled) `position_state_checkpoint_hash` — against the corresponding fields in `txn_info`, mirroring how `write_set_hash` and `event_root_hash` are already checked. Until this is fixed, any tool or code path relying on this function as evidence of "the replayed/executed output matches the authenticated ledger state" should be considered as validating only write-set and event equivalence, not full state-root equivalence.

### Proof of Concept
Not independently constructible as a concrete exploit without deeper access to the chunk executor's calling context (to confirm whether an out-of-band state-root check exists elsewhere in that pipeline) — this is reported as a code-level integrity gap with exact file/function support rather than a fully demonstrated end-to-end PoC, per the stated uncertainty above.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
