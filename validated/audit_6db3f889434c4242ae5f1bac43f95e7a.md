## Analog Found: Overloaded sentinel value in `oldTronPower` field causes state ambiguity - ([File: chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java])

### Summary
The reported issue describes a boolean (`canExecute`) that is asked to represent three distinct lifecycle states (`NotReady`, `Ready`, `Executed`), so a legitimate but different condition ends up mapping to the same value as an already-processed state, causing incorrect gating logic. The same bug class — a single scalar field overloaded with disjoint sentinel meanings — exists in java-tron's `Account.old_tron_power` field, which is used to gate one-time vote-migration logic during the "new resource model" (TRON Power freeze v2) transition.

### Finding Description
`AccountCapsule` uses a single `long oldTronPower` to encode three semantically different states with magic values:
- `0` → "not yet initialized"
- `-1` → "invalid / already migrated"
- any other value → "snapshot of the owner's old TRON Power at the moment of first touch under the new model" [1](#0-0) 

The bug is in `initializeOldTronPower()`:
```java
public void initializeOldTronPower() {
  long value = getTronPower();
  if (value == 0) {
    value = -1;
  }
  setOldTronPower(value);
}
```
If an account's actual `getTronPower()` is legitimately `0` (e.g., the account has never frozen balance under the `TRON_POWER` resource type — which is entirely normal, since most accounts only freeze `BANDWIDTH`/`ENERGY`), the "not yet initialized" transition collapses directly into the same sentinel (`-1`) used for "already invalidated / migration already completed." This is structurally identical to the reported Executor.sol flaw, where a legitimate outcome (successful call) and a distinct outcome (already-executed/failed) are folded into the same boolean value, producing ambiguity for any code that branches on that single field.

This field is checked via two accessor predicates that are mutually assumed to distinguish state, but actually cannot when the snapshot value is 0: [2](#0-1) 

It gates a one-time vote migration in `updateVote()` inside both `UnfreezeBalanceV2Actuator` and `UnfreezeBalanceV2Processor` (native/TVM path): [3](#0-2) [4](#0-3) 

The intended flow is: first time this actuator touches the account after the model flips, `initializeOldTronPower()` is called first, `oldTronPowerIsInvalid()` should be `false`, and the vote-clearing branch runs once (`accountCapsule.clearVotes(); votesCapsule.clearNewVotes();`). Then `invalidateOldTronPower()` is called at the end of `execute()` to permanently set the value to `-1`, marking the one-time migration as done: [5](#0-4) 

But if `getTronPower()` returns `0` at the moment of `initializeOldTronPower()`, the field is immediately set to `-1` — the exact same value used by `invalidateOldTronPower()` to mark "migration already done." The subsequent `oldTronPowerIsInvalid()` check in `updateVote()` therefore takes the "no need to change votes" branch (for BANDWIDTH/ENERGY) instead of the intended one-time `clearVotes()`/`clearNewVotes()` branch, silently skipping the vote migration for that account. This is the exact ambiguity pattern from the bug report: a state that means "not yet processed" is indistinguishable from "already processed," and the code takes the wrong branch depending on which meaning a caller assumes.

This same pattern (`oldTronPowerIsNotInitialized()` / `initializeOldTronPower()` / `oldTronPowerIsInvalid()` / `invalidateOldTronPower()`) is reused identically across `FreezeBalanceActuator`, `FreezeBalanceV2Actuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, `FreezeBalanceV2Processor`, and `UnfreezeBalanceV2Processor`, so the ambiguity is not localized to one code path. [6](#0-5) [7](#0-6) 

### Impact Explanation
When `getTronPower()` is `0` for an account at the point its old-tron-power snapshot is first taken (a common case for accounts that only ever froze BANDWIDTH/ENERGY), the field collapses "not initialized" into the "already migrated" sentinel. This causes the vote-migration branch (`updateVote`) to permanently skip the intended one-time vote-clearing step for such accounts. The practical effect is state divergence between accounting invariants that the new resource model relies on (votes proportional to tron power) and the account's actual recorded votes — an accounting/invariant-violation class of impact, consistent with the "invalid-state/divergence" acceptance criterion. It does not directly move funds, but it silently corrupts witness-vote bookkeeping for a subset of accounts undergoing the freeze-v2 migration.

### Likelihood Explanation
Likelihood depends entirely on the reachable precondition `getTronPower() == 0`, which is not an edge case — any account that has never frozen the `TRON_POWER` resource type (the overwhelming majority of accounts, since most freeze BANDWIDTH/ENERGY) satisfies this at the time their old-tron-power value is first initialized via `initializeOldTronPower()`. This is triggered by ordinary, unprivileged calls to `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`, or `VoteWitnessActuator` — all standard user-facing transaction types, and also reachable via TVM opcodes (`freeze`/`unfreeze`/`freezeBalanceV2`/`unfreezeBalanceV2`) as shown in `Program.java`. [8](#0-7) 

### Recommendation
Replace the overloaded `long oldTronPower` sentinel encoding with an explicit tri-state representation (e.g., a dedicated `NOT_INITIALIZED` / `MIGRATED` enum-like marker distinct from the actual snapshot value range, or a separate boolean "migrated" flag alongside the snapshot value), so that a legitimate snapshot value of `0` can never be conflated with the "already migrated" marker. Add explicit unit tests exercising the case where `getTronPower() == 0` at the time of first freeze/unfreeze/vote call under the new resource model, verifying the vote-clearing migration branch still executes exactly once.

### Proof of Concept
1. Create a fresh account that has never frozen balance under `ResourceCode.TRON_POWER` (only BANDWIDTH/ENERGY), and which has existing witness votes (`accountCapsule.addVotes(...)`).
2. Enable the new resource model: `dynamicPropertiesStore.saveAllowNewResourceModel(1L)`.
3. Confirm `accountCapsule.getTronPower() == 0` (true for typical BANDWIDTH/ENERGY-only freezers) — see `getTronPowerFrozenBalance()`/related getters in `AccountCapsule.java`.
4. Call `UnfreezeBalanceV2Actuator.execute()` (or `FreezeBalanceV2Actuator`, or `VoteWitnessActuator`) for this account for the first time post-model-switch. Internally `accountCapsule.oldTronPowerIsNotInitialized()` is true, so `initializeOldTronPower()` runs and sets `oldTronPower = -1` directly (since `getTronPower() == 0`). [9](#0-8) 
5. Inside `updateVote()`, `accountCapsule.oldTronPowerIsInvalid()` now evaluates `true` on this very first call (rather than only after `invalidateOldTronPower()` runs at the end of `execute()`), so the code takes the "no need to change votes" branch and returns without clearing votes. [10](#0-9) 
6. Assert that `accountCapsule.getVotesList()` still contains the pre-migration votes untouched, whereas an account whose `getTronPower() > 0` at initialization time would have had its votes cleared as intended — demonstrating the state-ambiguity-driven divergence between otherwise-equivalent accounts.

    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,

    FreezeBalanceParam param = new FreezeBalanceParam();
    param.setOwnerAddress(owner);
    param.setReceiverAddress(receiver);
    boolean needCheckFrozenTime = CommonParameter.getInstance()
        .getCheckFrozenTime() == 1; // for test
    param.setFrozenDuration(needCheckFrozenTime
        ? repository.getDynamicPropertiesStore().getMinFrozenTime() : 0);
    param.setResourceType(parseResourceCode(resourceType));
    try {
      FreezeBalanceProcessor processor = new FreezeBalanceProcessor();
      param.setFrozenBalance(frozenBalance.sValue().longValueExact());
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;

      logger.warn("TVM Freeze: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM Freeze: frozenBalance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
