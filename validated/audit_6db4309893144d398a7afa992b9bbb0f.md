**Analysis supporting rejection:**

1. **The chain-id assertion is never skipped for simulation.** In `prologue_common`, only the auth-key check (`skip_auth_key_check`) and gas-payment check (`skip_gas_payment`) are conditioned on `is_simulation`. The chain-id assertion `assert!(chain_id::get() == chain_id, ...)` executes unconditionally, before either of those `is_simulation`-gated branches, for every invocation of `prologue_common`, regardless of the `is_simulation` flag. [1](#0-0) 

2. **`chain_id::get()` always reads from the same resolver/state view passed into the VM, not a distinct "speculative" view divorced from committed state.** For the public simulation API, that state view is `self.context.latest_state_view_poem(&ledger_info)` — a state view rooted at a specific, real, committed ledger version — and `AptosSimulationVM::create_vm_and_simulate_signed_transaction` builds its resolver directly from that state view (only patching the randomness seed resource, not chain id). So `chain_id::get()` reads the real `ChainId` resource as committed at that ledger version. [2](#0-1) [3](#0-2) [4](#0-3) 

3. **Simulated output is never mistaken for a proof-bound committed `TransactionInfo`.** The API explicitly zeroes out `state_change_hash`, `event_root_hash`, and `accumulator_root_hash` when constructing the simulated `TransactionOnChainData`/`TransactionInfo`, and the code comment states plainly "All state hashes are invalid, and will be filled with 0s." This output is never written to storage or the accumulator, and carries no real proof material that could be confused with a genuine committed transaction info. [5](#0-4) 

4. **Block execution (BlockSTM) is a separate path from user-facing simulation** and its speculative/aborted incarnations never leave the executor — only validated, committed outputs are flushed and persisted, per `flush_speculative_logs` gating in `AptosBlockExecutorWrapper::execute_block`. This has no relation to the `/transactions/simulate` prologue path described in the question. [6](#0-5) 

There is no path by which an unprivileged simulation request causes the chain-id check to run against anything other than the genuine committed `ChainId` resource at the queried ledger version, and no path by which simulated output (explicitly zero-hashed and never persisted) could be mistaken for proof-bound committed transaction info.

    pub fn create_vm_and_simulate_signed_transaction(
        transaction: &SignedTransaction,
        state_view: &impl StateView,
    ) -> (VMStatus, TransactionOutput) {
        assert_err!(
            transaction.verify_signature(),
            "Simulated transaction should not have a valid signature"
        );

        let env = AptosEnvironment::new(state_view);
        let mut vm = AptosVM::new(&env);
        vm.is_simulation = true;

        let log_context = AdapterLogSchema::new(state_view.id(), 0);
        let original_view = state_view.as_move_resolver();
        let patched_view = Self::patch_randomness_seed(&original_view);
        let resolver = vm.as_move_resolver(&patched_view);
        let code_storage = state_view.as_aptos_code_storage(&env);

        let (vm_status, vm_output) = vm.execute_user_transaction(
            &resolver,
            &code_storage,
            transaction,
            &log_context,
            &AuxiliaryInfo::new_timestamp_not_yet_assigned(0),
        );
        let txn_output = vm_output
            .into_transaction_output()
            .expect("Converting to transaction output should never fail");
        (vm_status, txn_output)
    }
