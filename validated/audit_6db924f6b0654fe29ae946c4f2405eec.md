The reentrancy pattern in the report (state update occurring after an external call that can call back into the vulnerable function) does not have a viable analog in the reachable NEAR paths. In particular, the NEAR Wallet Contract — the closest analog since it accepts an unprivileged relayer/RPC-submitted transaction and creates cross-contract promises — already implements a reentrancy guard that is checked and set *before* any external call is initiated: `rlp_execute` checks `self.has_in_flight_tx` and returns early if a transaction is already in progress, and only sets `has_in_flight_tx = true` after successfully building the promise (never leaving a window where a second call can be accepted mid-flight) [1](#0-0) . The `nonce` (which prevents transaction replay) is also incremented synchronously inside `inner_rlp_execute` before any promise/cross-contract call is dispatched, not after a callback resolves, so there is no window for double-spending or nonce reuse via a nested call [2](#0-1) .

More fundamentally, NEAR's execution model does not have synchronous callback reentrancy: cross-contract calls (`promise_batch_action_function_call`, `promise_then`, etc.) always spawn asynchronous receipts, and each receipt is processed to completion (with all state committed) before the next receipt for that account is applied by the runtime's apply loop [3](#0-2) . There is no code path where an untrusted callee can execute arbitrary logic *within the same call stack* before the caller's state (balance, nonce, minted supply, etc.) is finalized — which is the root cause that makes `_safeMint`-style reentrancy possible in Solidity. This structural difference means the bug class from the Sherlock/Carapace report does not transfer to a reachable, transaction-triggered nearcore vulnerability meeting the required impact bar (unauthorized value movement, supply inflation, fee/gas bypass, state-root divergence, receipt loss/duplication, frozen funds, or halt).

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }
