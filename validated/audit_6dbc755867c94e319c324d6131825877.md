### Title
L1Handler paid-fee validation is bypassed for consensus-replayed transactions — `paid_fee_on_l1` hardcoded to `Fee(1)` - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
The reported bug class (unvalidated/mismanaged "fee" input allowing bypass of an economic safety check) has a concrete analog in the sequencer's L1Handler transaction path. When an `L1HandlerTransaction` originates from the real L1 event scraper, its `paid_fee_on_l1` is populated with the actual fee paid on L1 [1](#0-0) . However, when the same transaction is reconstructed from a `ConsensusTransaction` (i.e., during proposal validation / re-execution by a node other than the original scraper-informed proposer), `paid_fee_on_l1` is hardcoded to `Fee(1)` regardless of what was actually paid on L1, with an explicit TODO acknowledging this is a stand-in value: [2](#0-1) 

### Finding Description
The blockifier's L1Handler execution path performs a post-execution fee check that only verifies `paid_fee_on_l1 != Fee(0)` — it does not verify the paid amount is sufficient for the actual computed fee (the comment states "For now, assert only that any amount of fee was paid"): [3](#0-2) 

Because `convert_consensus_l1_handler_to_internal_l1_handler` unconditionally substitutes `Fee(1)` for `paid_fee_on_l1` instead of propagating the real, L1-scraped fee value, any node that receives and re-executes an `L1HandlerTransaction` via the consensus/gossip path (rather than directly from its own L1 events provider) will always treat the paid fee as `Fee(1)`, satisfying the `paid_fee != Fee(0)` check unconditionally. This decouples the post-execution admission decision (accept/revert) of the L1Handler transaction from the real, on-chain L1 fee amount for any node relying on the consensus-converted representation.

### Impact Explanation
Since the check in `l1_handler_transaction.rs` is the only gate deciding whether an L1Handler transaction with an underpaid L1 fee is committed vs. reverted, and this decision now depends on which code path (`L1EventsProviderClient::get_txs` with real fee vs. `convert_consensus_l1_handler_to_internal_l1_handler` with hardcoded `Fee(1)`) is used to reconstruct the transaction, different honest nodes could, in principle, reach different accept/revert outcomes for the same L1Handler transaction depending on how they obtained the fee value used to execute it. A divergence in whether a transaction reverts or commits changes the resulting state diff and therefore the committed state root / block hash for that node, which is a critical honest-node-divergence risk category.

### Likelihood Explanation
This is a hardcoded stand-in acknowledged by the authors via a `TODO` comment, meaning the code exists but its real-value replacement was deferred. Whether this leads to actual divergence depends on whether the L1Handler fee-check bound (`Fee(0)` threshold, i.e., "any amount") is ever meaningfully exercised in practice at the resource-bound level, since the "sufficiency" comparison is coarse (`!= 0`) rather than proportional to computed gas cost — I could not fully verify within the available context whether any other stronger fee-sufficiency enforcement exists elsewhere (e.g., in the L1 core contract logic that determines how much gas/fee is provided per message, which is out of scope for this repo). The known-incomplete nature of this code path (explicit TODO, not a subtle logic bug) increases confidence this is a real gap, but I could not confirm from this codebase alone whether both code paths (`L1EventsProviderClient` real-fee path and consensus-converted hardcoded path) are ever both live for the same node in the same execution round in a way that produces a two different real block hashes — this needs runtime/integration verification beyond what the indexed code shows.

### Recommendation
Propagate the real `paid_fee_on_l1` value through the consensus transaction representation (e.g., include it as a field in `ConsensusTransaction`/`InternalConsensusTransaction` for L1Handler transactions) instead of hardcoding `Fee(1)` in `convert_consensus_l1_handler_to_internal_l1_handler`, and resolve the outstanding `TODO(Gilad)` before this path is exercised in a production or consensus-critical execution flow.

### Proof of Concept
1. A malicious or buggy proposer's L1 events provider observes a `LogMessageToL2` L1 event with a legitimate on-chain paid fee (say `Fee(1000)`) and builds a proposal containing this L1Handler transaction correctly attributed with the real fee via `Event::from_l1_event` [1](#0-0) .
2. A validating node receives this transaction as part of the `ConsensusTransaction` payload and reconstructs the executable transaction via `convert_consensus_l1_handler_to_internal_l1_handler`, which discards the real fee and substitutes `Fee(1)` [2](#0-1) .
3. During `execute_raw`, the post-execution check only verifies `paid_fee != Fee(0)` [4](#0-3)  — this passes identically for `Fee(1)` and `Fee(1000)`, so no divergence is observable with this specific weak check; however, any future stricter validation added at this checkpoint (or asymmetric usage of `paid_fee_on_l1` elsewhere, e.g. for receipts/billing) will silently diverge between the proposer (real fee) and the validator (stubbed fee) node, since one path uses actual L1 data and the other a hardcoded placeholder.
