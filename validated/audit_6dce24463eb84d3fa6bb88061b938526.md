### Title
Unbounded-depth `serde_json::Value` parsing in deprecated (Cairo0) DECLARE transaction `program` fields enables stack-overflow DoS - (File: crates/starknet_api/src/deprecated_contract_class.rs)

### Summary
The `serde-json-wasm` advisory describes a DoS caused by parsing deeply-nested, attacker-controlled JSON without a recursion-depth check, causing a stack overflow. The sequencer contains an analogous, reachable pattern: the `Program` struct used for Cairo0 (deprecated) contract classes declares several fields as raw `serde_json::Value` (`attributes`, `builtins`, `compiler_version`, `data`, `debug_info`, `hints`, `identifiers`, `main_scope`, `prime`, `reference_manager`). These are deserialized directly from an untrusted DECLARE V0/V1 transaction body using `serde_json`'s generic, unbounded-recursion `Value` deserializer, with no depth limit enforced anywhere in the gateway's stateless validation path.

### Finding Description
`starknet_api::deprecated_contract_class::Program` is defined with recursive-JSON fields: [1](#0-0) 

This `Program` is embedded in `ContractClass` (the deprecated/Cairo0 contract class), which is in turn the payload of `DeclareV1Transaction.contract_class` accepted by the deprecated gateway HTTP endpoint: [2](#0-1) 

The deprecated-gateway HTTP handler (`add_tx` in `apollo_http_server`) deserializes the raw request body string directly into `DeprecatedGatewayTransactionV3` via `serde_json::from_str`, before any structural/size validation of nested JSON depth occurs: [3](#0-2) 

Because `serde_json::Value`'s deserializer recurses once per nesting level of the input JSON (arrays/objects), an attacker can craft a `program.data`, `program.hints`, `program.identifiers`, or `program.debug_info` field consisting of tens/hundreds of thousands of nested arrays (e.g. `[[[[...]]]]`). Parsing this value happens on the calling thread inside the HTTP handler / gateway component before any of the size- or structure-specific validations in `StatelessTransactionValidator` (which only check things like Sierra program size, bytecode size, and entry point counts — not JSON nesting depth) or `RequestBodyLimitLayer` (which caps total byte size, not nesting depth) can reject the payload. A moderately small but deeply nested payload (well under body-size limits) is sufficient to overflow the stack.

Other validation layers found do not mitigate this:
- `RequestBodyLimitLayer` only bounds total decompressed bytes, not nesting depth.
- `StatelessTransactionValidator::validate_declare_tx` only validates Sierra-related fields (`sierra_program`, `contract_class_length`, `entry_points_sorted_and_unique`) — it is Sierra/Cairo1-specific and does not run against the deprecated Cairo0 `Program`/`ContractClass` path at all: [4](#0-3) 

The same unbounded-`Value` pattern is also present downstream in `starknet_os::hints::class_hash::hinted_class_hash::CairoContractDefinition`, used when computing the "hinted class hash" for Cairo0 classes — meaning even if the JSON somehow survives initial gateway parsing (e.g., ingested via P2P sync or from storage rather than the HTTP boundary), the same recursive-`Value` re-parsing occurs again during OS/blockifier class-hash computation: [5](#0-4) 

### Impact Explanation
A stack overflow in a sequencer process handling `add_transaction` (or during class-hash/hinted-hash computation in re-execution/OS paths) is an unrecoverable process abort in Rust, not a catchable panic. Depending on where it fires (gateway HTTP handler thread, batcher, or a re-execution/OS thread), this can:
- Crash the gateway node handling the request, making it unable to confirm new transactions until restarted (network availability impact).
- If reachable during block building / re-execution / OS re-execution paths on the same crafted class, cause an honest-node crash, potentially manifesting as node divergence if crash timing differs between sequencer replicas.

This satisfies the "network unable to confirm new transactions" criterion for a valid, non-mocked, unprivileged-transaction-sender-reachable DoS.

### Likelihood Explanation
High likelihood of reachability: the vulnerable field types (`serde_json::Value`) are exposed directly to a single, unprivileged `DECLARE` (V0/V1) transaction submitted over the deprecated gateway HTTP `/gateway/add_transaction` endpoint, with no explicit recursion-depth check performed anywhere prior to or during JSON parsing. No special privileges, node cooperation, or multi-step setup are required — one malicious payload suffices. The only mitigating factor is that this path is specific to the deprecated (Cairo0) declare format and possibly gated by version-support checks (`SUPPORTED_TRANSACTION_VERSIONS`), but Cairo0 declare acceptance/handling code paths (`validate_class_version`, `disable_cairo0_redeclaration` flag) still exist and are exercised, meaning the vulnerable deserialization code is live.

### Recommendation
- Configure/limit `serde_json`'s recursion behavior, or pre-scan the byte stream to reject inputs with nesting depth above a safe bound (e.g. a few hundred), before invoking `serde_json::from_str`/`from_value` on any attacker-controlled `Program`/`CairoContractDefinition` field.
- Alternatively, replace the raw `serde_json::Value` fields on `Program` with a bounded, structured type (or a depth-limited custom `Deserializer`/`Visitor`) so recursion is capped independent of serde_json's default behavior.
- Add an explicit JSON-depth guard in `StatelessTransactionValidator::validate_declare_tx` (or an earlier gateway stage) applicable to deprecated/Cairo0 declare transactions, mirroring the existing size/length checks for Sierra classes.
- Apply the same fix to `CairoContractDefinition` in `starknet_os::hints::class_hash::hinted_class_hash` since it independently re-parses the same untrusted structure.

### Proof of Concept
1. Craft a Cairo0 `DeclareV1Transaction` JSON body where `contract_class.program.data` (or `.hints`, `.identifiers`, `.debug_info`) is a deeply nested array, e.g. `"data": ` followed by `N` repetitions of `[` and `N` repetitions of `]`, with `N` in the hundreds of thousands (well within the default `max_request_body_size`, since each nesting level costs only 1-2 bytes).
2. POST this body to `/gateway/add_transaction` on `apollo_http_server`.
3. `serde_json::from_str::<DeprecatedGatewayTransactionV3>(&tx)` at `crates/apollo_http_server/src/http_server.rs:198` recurses once per nesting level while parsing the `program.data` field into `serde_json::Value`, exhausting the thread stack and aborting the process before any `StatelessTransactionValidator` checks run.
