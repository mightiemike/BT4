### Title
Unbounded-depth recursive `bytecode_hash_node` traversal of attacker-supplied `NestedIntList` causes a stack overflow when computing compiled-class hashes for declared classes - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
When a class is declared, the Sierra program is compiled to CASM in an isolated, resource-limited subprocess `crates/apollo_compilation_utils/src/compiler_utils.rs:17-50`, and CPU/memory limits are applied to that subprocess via `ResourceLimits` [1](#0-0) . However, immediately after the subprocess returns, the resulting `CasmContractClass` (deserialized in the **parent, unsandboxed** process) is hashed in-process via `executable_class.hash(&HashVersion::V2)` [2](#0-1) . This hash computation recurses over the `bytecode_segment_lengths: Option<NestedIntList>` field via `bytecode_hash_node`, with recursion depth equal to the nesting depth of that structure and **no recursion-depth bound anywhere in the call path**.

### Finding Description
`bytecode_hash_node` is a plain, unbounded recursive function: [3](#0-2) 

It is invoked from `bytecode_hash`, which is invoked from `hash_inner`, which is the implementation behind `HashableCompiledClass::hash` used by `SierraCompiler::compile`: [4](#0-3) [5](#0-4) 

The `bytecode_segment_lengths` field is a `NestedIntList`, an arbitrarily-nestable tree of `Leaf`/`Node` variants that is emitted by the Sierra→Casm compiler based on the control-flow/branch structure of the Sierra program supplied by the class declarer. While `SierraCompilationConfig::max_bytecode_size` bounds the *total* bytecode length passed with `--max-bytecode-size` to the compiler subprocess, there is no corresponding limit on the **nesting depth** of the segment-length tree that the compiler emits for that bytecode. The only size limit checked in `ClassManager::add_class` (`validate_class_length`) is applied to the serialized executable class size, not the tree depth: [6](#0-5) 

A Sierra program crafted with a deeply nested branching/control-flow structure (e.g., long chains of nested `if`/`match` blocks) can therefore cause the compiler to emit a `NestedIntList` whose nesting depth scales with the number of statements, well beyond what a typical Rust thread stack can accommodate through non-tail recursion (each level allocates iterator state, a `Vec` via `collect_vec()`, and closures). Unlike the subprocess that performs the actual Sierra→CASM compilation (which is resource-limited and isolated, so a subprocess crash does not affect the sequencer), `bytecode_hash_node` executes directly inside the `apollo_class_manager` / sierra-compiler service's own process, on the default thread stack, with no `RUST_MIN_STACK`/`stack_size` protection analogous to what is deliberately provisioned for Cairo-native recursive execution [7](#0-6)  or for VM entry-point recursion depth limits enforced by `max_recursion_depth` during transaction execution [8](#0-7) . This is structurally the same bug class as CVE-2025-70309: a recursive parser/hasher walking an attacker-controlled nested structure with no depth cap, causing a stack overflow (process abort/SIGSEGV) instead of a graceful error.

### Impact Explanation
A successful stack overflow crashes the process performing compiled-class hashing (the sierra-compiler / class-manager component) with SIGSEGV/abort. Because class declaration and compiled-class-hash computation are on the hot path for every `DECLARE` transaction, a crafted class declaration reaching this code on every full node/sequencer running this code would cause a denial of service, matching the "network unable to confirm new transactions" impact bar (all sequencers processing the same declare transaction would crash identically, since the recursive traversal is deterministic on the compiled bytecode). This is a Medium-severity honest-crash/liveness bug (matching the referenced CVE's severity and CVSS profile), not a state-corruption or fund-theft bug.

### Likelihood Explanation
Reaching this code only requires submitting a `DECLARE` transaction (or L1-equivalent path where applicable) for a class whose Sierra program is deliberately structured to produce a deeply nested bytecode-segment tree — no special privileges, no operator/proposer/prover involvement. This is directly reachable by any unprivileged contract declarer, matching the "sierra to casm compilation and class hashing" allowed analog category. The exact stack-frame cost per nesting level, and thus the number of nested statements required to overflow a specific deployment's stack size, could not be measured without executing the code; however, since `max_bytecode_size` does not constrain nesting depth, an attacker can pick sizes up to the maximum configured bytecode size (`DEFAULT_MAX_BYTECODE_SIZE`, potentially multiplied by 10x for re-execution paths, cf. `crates/blockifier_reexecution/src/compile.rs:102`) to make nesting depth as large as needed.

### Recommendation
- Add an explicit maximum recursion/nesting-depth check in `bytecode_hash_node` (or convert it to an iterative traversal using an explicit heap-allocated stack) so that malformed/deeply-nested `NestedIntList` structures produce a graceful compilation/hashing error instead of a stack overflow.
- Alternatively/additionally, validate the maximum depth of `bytecode_segment_lengths` as part of `validate_class_length`/class-declaration validation in `apollo_class_manager`, rejecting classes whose segment tree exceeds a safe bound, consistent with how `max_recursion_depth` and stack pre-allocation are handled elsewhere in the codebase for VM/Cairo-native recursion.
- Ensure this hashing step, like the Sierra→CASM compile step itself, either runs under equivalent resource isolation, or is made recursion-depth-safe by construction.

### Proof of Concept
Conceptual PoC (not executed, since the actual stack-frame-size-to-depth threshold requires running the code):
1. Craft a Cairo 1 contract whose body consists of a long chain of deeply nested conditional/branch constructs (e.g., N nested `if`/`match` arms), chosen so the Sierra→Casm compiler emits a `CasmContractClass.bytecode_segment_lengths` as a `NestedIntList::Node` tree nested N levels deep, while keeping total bytecode size under `max_bytecode_size`.
2. Submit this class via a `DECLARE` transaction (or via `ClassManager::add_class`/`SierraCompiler::compile`).
3. The Sierra→Casm compiler subprocess succeeds (bounded by CPU/memory limits only) and returns the `CasmContractClass` including the deeply nested `bytecode_segment_lengths`.
4. `SierraCompiler::compile` then calls `executable_class.hash(&HashVersion::V2)` in-process [2](#0-1) , which recurses into `bytecode_hash_node` N times [3](#0-2) , exhausting the thread stack and crashing the class-manager/sierra-compiler process.

Note: I was not able to execute the Cairo compiler in this environment to empirically determine the exact N required to overflow the default stack size, or to confirm whether any upstream limit (e.g., a Sierra statement-count cap) indirectly bounds nesting depth before it reaches this function — this should be independently verified before treating this as fully validated.

```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
```

```rust
    pub async fn add_class(&mut self, class: RawClass) -> ClassManagerResult<ClassHashes> {
        let sierra_class = SierraContractClass::try_from(&class)?;
        let class_hash = sierra_class.calculate_class_hash();
        if let Ok(Some(executable_class_hash_v2)) =
            self.classes.get_executable_class_hash_v2(class_hash)
        {
            // Class already exists.
            return Ok(ClassHashes { class_hash, executable_class_hash_v2 });
        }

        let compilation_start_time = Instant::now();
        let (raw_executable_class, executable_class_hash_v2) =
            self.compiler.compile(class.clone()).await.map_err(|err| match err {
                SierraCompilerClientError::SierraCompilerError(error) => {
                    ClassManagerError::SierraCompiler { class_hash, error }
                }
                SierraCompilerClientError::ClientError(error) => {
                    ClassManagerError::Client(error.to_string())
                }
            })?;
        debug!(
            %class_hash,
            compiled_class_hash = %executable_class_hash_v2,
            compilation_elapsed_ms = compilation_start_time.elapsed().as_millis(),
            class_size_bytes =
                class.size().map_or("Failed to get class size".to_owned(), |size| size.to_string()),
            casm_size_bytes =
                raw_executable_class.size().map_or("Failed to get casm size".to_owned(), |size| size.to_string()),
            "Finished compiling class."
        );

        self.validate_class_length(&raw_executable_class)?;
        Self::validate_class_version(&sierra_class)?;
        self.classes.set_class(
            class_hash,
            class,
            executable_class_hash_v2,
            raw_executable_class,
        )?;

        let class_hashes = ClassHashes { class_hash, executable_class_hash_v2 };
        Ok(class_hashes)
    }
```
