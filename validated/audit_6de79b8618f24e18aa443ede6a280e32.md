### Title
App Proxy signature verification collision via unescaped, undelimited key/value concatenation - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The App Proxy variant of the HMAC signature algorithm concatenates sorted `key=value` pairs directly with no separator between pairs and no escaping of `=` characters that may appear inside an (attacker-controlled) parameter name. This is the same "multiple dynamic values packed together without delimiters" bug class as the reported `abi.encodePacked` collision: two structurally different query maps can produce an identical signing input, so a signature that Shopify genuinely computed for one query can be replayed against a different, attacker-chosen query.

### Finding Description
`stringifyQueryForAppProxy` builds the string that is HMAC-signed/verified for App Proxy requests: [1](#0-0) 

Unlike `stringifyQueryForAdmin`, which uses `URLSearchParams`-based encoding with `&` separators via `ProcessedQuery` [2](#0-1) , the App Proxy path joins every `key` and `value` back-to-back with no field separator, and does not escape `=` characters embedded in the (fully attacker-controlled) key.

Only a small, fixed set of keys is protected against duplication/ambiguity: [3](#0-2) 

Note that `logged_in_customer_id` and `path_prefix` — both security-relevant fields commonly consumed by app business logic — are outside that protected set. Because arbitrary query parameter *names* are attacker-controlled (a storefront visitor can append any query string to the proxied URL, and standard percent-decoding lets a key contain a literal `=`), it is possible to construct two distinct, independently-parseable query objects whose `stringifyQueryForAppProxy` output is byte-identical:

- `Q1` (what an unauthenticated visitor actually sends, and what Shopify genuinely signs): a single custom key literally named `logged_in_customer_id=999path_prefix` with value `/apps/my_app`, plus the real `shop` and `timestamp` Shopify appends.
- `Q2` (what the attacker later submits directly to the app, without going through Shopify at all): the real 4-key map `{logged_in_customer_id: "999", path_prefix: "/apps/my_app", shop, timestamp}`.

Because `"logged_in_customer_id=999" + "path_prefix=" + "/apps/my_app"` is byte-for-byte the same string as `"logged_in_customer_id=999path_prefix" + "=" + "/apps/my_app"`, `stringifyQueryForAppProxy(Q1) === stringifyQueryForAppProxy(Q2)`, so `HMAC(Q1) === HMAC(Q2)`. The `normalizeQuery`/`validateHmac` logic only re-derives the HMAC from whatever query object it is given and compares it via `safeCompare` [4](#0-3) ; it has no way to detect that the signature was actually produced for a structurally different query.

The request never needs to be re-proxied through Shopify — App Proxy authentication in the framework packages is transport-independent and only checks the signature/timestamp, e.g. in the Remix/React Router `authenticateAppProxyFactory`, which calls `api.utils.validateHmac(searchParams, {signator: 'appProxy'})` directly on whatever `URLSearchParams` it is handed [5](#0-4) .

### Impact Explanation
An unauthenticated attacker who can make one legitimate, unauthenticated visit through a merchant's App Proxy (something any storefront visitor can do) can harvest a validly-signed `(query, signature, timestamp)` tuple and then directly POST/GET a differently-shaped, forged query to the app's App Proxy endpoint that reuses that same signature but sets a security-sensitive field such as `logged_in_customer_id` to an arbitrary value. Apps that trust `logged_in_customer_id` from a signature-verified App Proxy request (a documented, common pattern for authorizing "my orders"/"my account" style storefront features) would then act as if the request came from an authenticated customer of the attacker's choosing — a cross-tenant/cross-customer authentication bypass on the App Proxy channel. This matches the "accepted forged Shopify request" / "cross-tenant access" bar for a valid finding.

### Likelihood Explanation
Exploitation requires only unauthenticated interaction with the App Proxy endpoint (no privileged access, no secret leakage, no MITM) and standard percent-encoding support that virtually all HTTP clients/servers provide. The attacker fully controls the crafted key names and values in both the "signed" request and the "forged" replay, and the reserved-key protection set does not cover `logged_in_customer_id`/`path_prefix`, making the specific collision above directly constructible. The only constraint is the 90-second timestamp tolerance enforced by `validateHmacTimestamp`, which is easily satisfied by an automated attacker replaying immediately after harvesting the signature.

### Recommendation
Do not build the App Proxy signing base string via raw, unescaped, undelimited `key`+`value` concatenation. At minimum:
- Escape/encode `=` (and any separator characters) inside both keys and values before concatenation, or
- Insert an unambiguous separator between `key=value` pairs (as Shopify's algorithm is inherently ambiguous, the app should additionally reject query keys containing raw `=`/control characters before verification), and
- Extend `APP_PROXY_SINGLE_VALUE_PARAMS`-style protections to reject any parameter name that collides with (or is a superstring/prefix concatenation of) reserved names like `logged_in_customer_id`, `path_prefix`, `shop`, `timestamp` before computing/verifying the HMAC.

### Proof of Concept
1. As an anonymous visitor, request the App Proxy URL with a crafted query parameter name containing a percent-encoded `=`:
   `https://{shop}.myshopify.com/apps/my_app?logged_in_customer_id%3D999path_prefix=%2Fapps%2Fmy_app`
   Shopify appends its own real `shop` and `timestamp`, computes `signature` over `stringifyQueryForAppProxy`, and forwards the request to the app (which will pass validation normally, since it truthfully reflects what Shopify signed).
2. Capture the resulting `shop`, `timestamp`, and `signature` values from this legitimate exchange.
3. Send a new request directly to the app's App Proxy authentication endpoint (bypassing Shopify) with the real 4-key query:
   `?logged_in_customer_id=999&path_prefix=/apps/my_app&shop={shop}&timestamp={timestamp}&signature={captured_signature}`
4. `stringifyQueryForAppProxy` produces the identical string in both cases, so `validateHmac` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` returns `true`, and the app treats the request as though it were signed for `logged_in_customer_id=999`, even though Shopify never actually authenticated that customer ID.

function stringifyQueryForAdmin(query: AuthQuery): string {
  const processedQuery = new ProcessedQuery();
  Object.keys(query)
    .sort((val1, val2) => val1.localeCompare(val2))
    .forEach((key: string) => processedQuery.put(key, query[key]));

  return processedQuery.stringify(true);
}

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}
