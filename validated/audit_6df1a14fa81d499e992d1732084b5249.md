### Title
Duplicate pubkey within a single slot's storage causes `generate_index` to unconditionally panic during index (re)generation - ([File: accounts-db/src/accounts_index.rs])

### Summary
`AccountsIndex::insert_new_if_missing_into_primary_index` — the function used by `AccountsDb::generate_index_for_slot` to build the accounts index from on-disk account storages at validator startup/fastboot — asserts that no two items being inserted for the same slot share a pubkey. If a slot's storage ever legitimately contains two records for the same pubkey (e.g. produced by a bug in shrink/ancient-append-vec combining, or a race that writes the same pubkey twice into one append vec before the entry is added to the index), the assertion fires unconditionally and crashes the validator instead of gracefully deduplicating.

### Finding Description
`insert_new_if_missing_into_primary_index` sorts the batch of `(pubkey, account_info)` items collected from a single slot's storage and then walks it looking for entries that share the same bin. While doing so it asserts that consecutive same-bin items never carry an identical pubkey: [1](#0-0) 

This is called from `AccountsDb::generate_index_for_slot`, which is exercised both by the disk-index startup path (`use_disk` → `startup_insert_only`) and — as shown by the existing unit tests — reachable directly with duplicate entries for one pubkey within one slot's append vec: [2](#0-1) 

The comment in the test acknowledges the *intent* is for "the last one of each pubkey" to end up in the index (i.e., graceful last-write-wins deduplication), but the actual code path panics instead of deduplicating — this is precisely the pattern in the referenced report: unexpected/extra data (a second record for a pubkey that the code assumed would be unique within a slot) is present at the moment a structural invariant is checked, and instead of being filtered out it causes the check to fail permanently. In the original Notional bug, the check was `onERC1155Received` verifying the asset list length is exactly 1; here the analogous check is that a slot's account list contains no duplicate pubkeys. In both cases, once the "before" state (an asset/record placed early) collides with the expected structural invariant, the guarded operation (minting / accounts-index generation) is permanently blocked rather than being resolved.

### Impact Explanation
If any account storage the validator loads (from its own local `accounts` directory or via fastboot storage list) ends up with two entries for the same pubkey inside a single slot's append vec — which can happen from bugs in the shrink/ancient-combine write paths that write alive accounts back into a single storage (`store_accounts_for_shrink`, `write_ancient_accounts`), or from any accidental double-write into one AppendVec before it's registered with the index — `generate_index` will panic on the next startup/fastboot reload. This is a validator node panic (crash) rather than silent data loss, matching the "node panic" impact category, and it occurs specifically before/during index construction, i.e. before the accounts index (the "deployed contract" analog) is fully materialized.

### Likelihood Explanation
Likelihood is low-to-moderate: normal transaction flow deduplicates writes to a given pubkey within a slot before they reach a storage file (writes accumulate in the per-slot write cache keyed by pubkey), so under correct operation a slot's append vec should never contain two records for the same pubkey. However, any latent bug in the shrink or ancient-append-vec-combining paths (which directly write `alive_accounts` collections into new storages) that lets the same pubkey appear twice for one target slot would turn into a guaranteed, deterministic startup panic on the next restart/fastboot load — an availability-only failure with no direct fund loss, consistent with the Medium-severity characterization in the referenced report.

### Recommendation
Make `insert_new_if_missing_into_primary_index` (and `generate_index_for_slot`) tolerant of duplicate pubkeys within a single slot's storage by deduplicating (keeping the last occurrence, as the code comments already assume) instead of asserting/panicking. At minimum, downgrade the hard `assert_ne!` to a recoverable error path with logging, so a corrupted or unexpectedly duplicated storage does not prevent the validator from starting.

### Proof of Concept
The existing repository tests already demonstrate the crash deterministically: [3](#0-2) 
Both `test_generate_index_duplicates_within_slot` and its `_reverse` variant construct a single append vec containing two records for the same pubkey (different data/lamports) within slot 0, call `generate_index_for_slot`, and assert the process panics with `"Accounts may only be stored once per slot:"`. Any real-world code path (e.g. a shrink/ancient-combine defect) that produces such a storage file would reproduce this panic on the next `generate_index` call during validator startup.

fn run_generate_index_duplicates_within_slot_test(db: AccountsDb, reverse: bool) {
    let slot0 = 0;

    let pubkey = Pubkey::from([1; 32]);

    let append_vec = db.create_store(slot0, 1000);

    let mut account_small = AccountSharedData::default();
    account_small.set_data(vec![1]);
    account_small.set_lamports(1);
    let mut account_big = AccountSharedData::default();
    account_big.set_data(vec![5; 10]);
    account_big.set_lamports(2);
    assert_ne!(
        AppendVec::calculate_stored_size(account_big.data().len()),
        AppendVec::calculate_stored_size(account_small.data().len()),
    );
    // same account twice with different data lens
    // Rules are the last one of each pubkey is the one that ends up in the index.
    let mut data = vec![(&pubkey, &account_big), (&pubkey, &account_small)];
    if reverse {
        data = data.into_iter().rev().collect();
    }
    let storable_accounts = (slot0, &data[..]);

    // construct append vec with account to generate an index from
    append_vec.accounts.write_accounts(&storable_accounts);
    db.storage.insert(Arc::new(append_vec));

    assert!(!db.accounts_index.contains(&pubkey));
    let storage = db.get_storage_for_slot(slot0).unwrap();
    let mut reader = crate::append_vec::new_scan_accounts_reader();
    let mut accum = IndexGenerationAccumulator::with_slots_capacity(1);
    db.generate_index_for_slot(&mut reader, &mut accum, 0, &storage);
}
