Based on the investigation, I found a valid analog in java-tron's standby-witness reward distribution logic, which mirrors the MultiRewards precision-loss pattern: a shared reward amount is split proportionally using floating-point division, and the truncation from the per-recipient division is never accounted for or carried forward, so a fraction of the reward pool is silently under-distributed on every invocation.

### Title
Precision loss in standby witness reward distribution leads to systematic under-payment of rewards - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payStandbyWitness()` distributes a fixed total reward (`totalPay`) among all standby witnesses proportionally to their vote counts. It computes a floating-point `eachVotePay` and then truncates each witness's share to a `long` via `(long) (w.getVoteCount() * eachVotePay)`. The individual truncation losses are never tracked or redistributed, so the sum of all witnesses' payouts is always ≤ `totalPay`, with the difference simply disappearing rather than being accounted for anywhere.

### Finding Description
`totalPay` is read from `dynamicPropertiesStore.getWitness127PayPerBlock()`, and `eachVotePay = (double) totalPay / voteSum` is computed once. Each witness is then paid `pay = (long) (w.getVoteCount() * eachVotePay)`: [1](#0-0) 

This is functionally identical to the MultiRewards.sol bug class: a shared rate is computed once and then applied to each recipient's share, with every individual multiplication/truncation losing a fractional remainder that is never captured as a "residual" to be redistributed in a later cycle (unlike the VI-based new reward algorithm, which uses `BigInteger` arithmetic specifically to avoid this class of loss, see `RewardViCalService.accumulateWitnessVi` / `DelegationStore.accumulateWitnessVi`): [2](#0-1) 

The same unaccounted-truncation pattern also appears in `IncentiveManager.reward()`, which pays standby witnesses in the legacy (pre-`allowChangeDelegation`) code path using the same `(long) (voteCount * (double) totalPay / voteSum)` computation: [3](#0-2) 

In both cases, because `totalPay` is a fixed per-block constant (not drawn down from a ledger balance that must reconcile), the sum of truncated per-witness payouts is silently less than the intended `totalPay`; the shortfall is not recorded, tracked, or carried into the next block's distribution.

### Impact Explanation
Low-to-moderate: each individual truncation loss is at most a few units of the smallest reward denomination (sun) per witness per block/maintenance cycle, since `voteCount * eachVotePay` truncation loses at most `< 1` unit per witness. This causes standby witnesses (and, via `IncentiveManager`, the broader active witness set on the older, non-`allowChangeDelegation` reward path) to be systematically underpaid relative to the intended `totalPay` budget.

### Likelihood Explanation
High: `payStandbyWitness()` is invoked on every block via `Manager.payReward()` for up to 127 standby witnesses, and `IncentiveManager.reward()` runs on every maintenance cycle, so the unaccounted truncation loss accumulates continuously and indefinitely for the life of the chain.

### Recommendation
Track the truncation remainder (`totalPay - sum(individual payouts)`) explicitly, similar to the `rewardResidual` fix recommended for MultiRewards, and either (a) carry it forward into the next block/cycle's `totalPay`, or (b) use integer-exact proportional allocation (e.g., largest-remainder method or `BigInteger`-based division as already done in the VI reward algorithm) so that the sum of payouts always equals `totalPay` exactly.

### Proof of Concept
For `payStandbyWitness()`: with `totalPay = 16000000` and 127 witnesses each with `voteCount = 100000000 + i` (as used in the existing test `DelegationServiceTest.testPay`), `eachVotePay = totalPay / voteSum` is a repeating (non-terminating) fraction. Each witness's `pay = (long)(voteCount * eachVotePay)` truncates a fractional sun; summing all 127 truncated payouts yields strictly less than `16000000`, and the shortfall is neither logged nor stored anywhere, repeating identically every block: [4](#0-3)

  public void payStandbyWitness() {
    List<WitnessCapsule> witnessStandbys = witnessStore.getWitnessStandby(
        dynamicPropertiesStore.allowWitnessSortOptimization());
    long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
    if (voteSum < 1) {
      return;
    }
    long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
    double eachVotePay = (double) totalPay / voteSum;
    for (WitnessCapsule w : witnessStandbys) {
      long pay = (long) (w.getVoteCount() * eachVotePay);
      payReward(w.getAddress().toByteArray(), pay);
      logger.debug("Pay {} stand reward {}.", Hex.toHexString(w.getAddress().toByteArray()), pay);
    }
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
