### Title
Panic on missing `class_hash` during Starknet OS re-execution of `get_execution_info` for constructor calls - ([File: crates/starknet_os/src/hint_processor/snos_syscall_executor.rs])

### Summary
The Starknet OS's implementation of the `get_execution_info` syscall unconditionally unwraps the `class_hash` field of the currently-executing `CallEntryPoint` with `.expect("No class hash was set.")`. However, blockifier deliberately constructs `CallEntryPoint` with `class_hash: None` for constructor invocations (and for internal view-only calls). Any contract deployer can write a constructor that invokes the `get_execution_info` syscall, which executes successfully in blockifier (whose syscall handlers do not need `class_hash` to answer `get_execution_info`) but panics deterministically when the Starknet OS re-executes/proves the same block.

### Finding Description
`execute_constructor_entry_point` in blockifier builds the constructor's `CallEntryPoint` with `class_hash: None`: [1](#0-0) 

This `CallEntryPoint` (with `class_hash: None`) is what ends up stored as `CallInfo.call` and is later replayed by the Starknet OS during re-execution/proving. The OS's `get_execution_info` syscall handler reads the class hash directly off that stored `CallEntryPoint` and unwraps it unconditionally: [2](#0-1) 

The same unguarded `.expect("No class hash was set.")` pattern also exists in the deprecated (Cairo0) syscall path for the same reason: [3](#0-2) 

During ordinary blockifier execution, `get_execution_info` does not need `CallEntryPoint::class_hash` at all — the VM/native syscall handlers build the response purely from `block_info`, `tx_info`, `caller_address`, and `storage_address`: [4](#0-3) 
So a transaction whose constructor calls `get_execution_info` is accepted by the gateway, admitted to the mempool, and executes successfully in blockifier with no error. It only fails later, when the Starknet OS replays the same call info during re-execution/proving, because the OS's syscall handler additionally depends on `class_hash` being present, which it never is for constructor calls.

This is directly analogous to the reported bug class: `GetMagickProperty` in ImageMagick dereferences a property value without validating it is actually set, causing a NULL pointer dereference crash. Here, the OS handler dereferences (`.expect`s) an `Option<ClassHash>` field that the execution layer guarantees is `None` for a specific, externally-reachable call type (constructor calls), causing a deterministic panic.

### Impact Explanation
Any unprivileged account can declare and deploy a contract whose `constructor` calls `starknet::get_execution_info_syscall()` (or the equivalent low-level `get_execution_info`/`get_execution_info_v2`/`get_execution_info_v3` selector). The deploying transaction executes and commits normally in the sequencer's blockifier pipeline, so the block is built and includes this transaction. When the Starknet OS re-executes this block — a required step for proving/validation — it panics on the `.expect("No class hash was set.")` call. Since all conforming nodes/provers run the same OS logic on the same execution trace, this is a deterministic, network-wide failure to produce a proof/re-execute the block, which prevents block confirmation/finalization for any block containing such a transaction — this is a "network unable to confirm new transactions" condition rather than a single-node crash.

### Likelihood Explanation
High. The trigger requires only a single declare + deploy transaction (or invoke through a deployer/UDC) containing a constructor with one syscall call — no special privileges, no race conditions, no complex preconditions. It is fully reachable by any transaction sender/contract deployer.

### Recommendation
- In `crates/starknet_os/src/hint_processor/snos_syscall_executor.rs::get_execution_info` (and the corresponding deprecated path in `snos_deprecated_syscall_executor.rs`), do not require `CallEntryPoint::class_hash` to be `Some` for the `data_gas_accounts`/`v1_bound_accounts` checks. When `class_hash` is `None` (e.g., constructor calls, view calls), fall back to a defined default behavior (e.g., treat the account as neither a v1-bound nor data-gas-excluded account) instead of panicking.
- Alternatively, ensure `CallEntryPoint::class_hash` is always populated (e.g., using `ctor_context.class_hash`) before the `CallInfo` is persisted for OS consumption, since the class hash is in fact known at constructor-invocation time in `execute_constructor_entry_point`.
- Add a regression test that deploys a contract whose constructor invokes `get_execution_info` and asserts OS re-execution completes without panicking.

### Proof of Concept
1. Write and declare a Cairo1 contract whose `constructor` function calls `starknet::get_execution_info_syscall()` (this compiles and is permitted — no restriction bars syscalls from being called in a constructor).
2. Submit a `DEPLOY_ACCOUNT`/`INVOKE` (via UDC) transaction that deploys this contract; blockifier executes it successfully, since `execute_constructor_entry_point` builds the `CallEntryPoint` with `class_hash: None` (`crates/blockifier/src/execution/entry_point.rs:602-612`), and the blockifier's own `get_execution_info` handler does not consult that field.
3. Feed the resulting block to the Starknet OS for re-execution/proving. When the OS reaches the constructor's `get_execution_info` syscall, `snos_syscall_executor.rs::get_execution_info` executes `call_info_tracker.call_info.call.class_hash.expect("No class hash was set.")` (`crates/starknet_os/src/hint_processor/snos_syscall_executor.rs:272-273`), which panics because `class_hash` is `None`, halting re-execution of that block.

Note: I was not able to fully trace whether any later step in the execution pipeline back-fills `CallEntryPoint::class_hash` after constructor execution before the `CallInfo` is serialized for the OS (the search tool coverage of `entry_point.rs`'s full execution flow was incomplete). If such back-filling does occur elsewhere, this reduces to the `call_view_entry_point` path only, which is not part of consensus re-execution and would not qualify. A Devin session with full repository access should verify the final state of `CallEntryPoint::class_hash` on constructor `CallInfo` objects before this is treated as confirmed.
