### Title
Unbounded recursion in JSON-RPC request body parsing causes stack-overflow crash of the RPC server - ([File: chain/jsonrpc/src/lib.rs])

### Summary
The nearcore JSON-RPC entry point deserializes every incoming HTTP body directly into a `serde_json::Value` / `near_jsonrpc_primitives::message::Message` (which itself is `#[serde(untagged)]` over `Value`), with only a **byte-size** limit (`RpcLimitsConfig::json_payload_max_size`, default 10 MiB) enforced before parsing. There is no check on JSON *nesting depth*. `serde_json`'s `Value` deserializer is a classic recursive-descent parser: parsing `[[[[…]]]]` recurses once per nesting level with no built-in depth cap. A single unauthenticated POST to the RPC endpoint containing a few megabytes of nested arrays/objects (well under the 10 MiB size limit) is enough to exceed the parser thread's stack and trigger a Rust stack overflow, which aborts the process (stack overflows are not catchable via `catch_unwind`). This is the same bug class as CVE-2026-62296 (HAPI FHIR `XhtmlParser` unbounded recursion): a size-only limit substitutes for a depth limit, and a document/payload with unbounded nesting still triggers unbounded recursion between the parser's element/value functions.

### Finding Description
- `RpcLimitsConfig` only bounds the JSON payload by *byte count*, not nesting depth: [1](#0-0) 
- The wire message type used for all RPC requests is deserialized as an untagged `serde_json::Value`-backed enum with no custom depth-limiting deserializer: [2](#0-1) [3](#0-2) 
- Downstream parameter parsing (`Params::parse`) also uses plain `serde_json::from_value`, again with no depth restriction, only a generic parse-error path: [4](#0-3) 

Nowhere in the RPC ingestion path (`chain/jsonrpc/src/lib.rs`, `chain/jsonrpc-primitives/src/message.rs`, `chain/jsonrpc/src/api/mod.rs`) is there a recursion/depth guard analogous to what exists elsewhere in the codebase for genuinely untrusted recursive structures — e.g. the trie printer explicitly caps `max_depth` to avoid unbounded recursion (`core/store/src/trie/mod.rs:1045-1060`), and `get_subtree_size` was deliberately rewritten as an iterative BFS "to avoid any potential stack overflows" (`core/store/src/trie/trie_recording.rs:302`). The RPC JSON body path lacks the equivalent safeguard.

### Impact Explanation
`serde_json`'s recursive `Value` parser has no depth cap; a stack overflow while parsing terminates the offending thread via a Rust abort (stack overflows cannot be caught with `catch_unwind`), which in a `tokio`/`axum` process typically aborts the whole process rather than degrading gracefully. Because the JSON-RPC endpoint is reachable by any unauthenticated network caller (no signature, staking, or gas requirement — this is pre-transaction, at the HTTP/JSON layer), a single crafted request can crash a validator's or RPC node's JSON-RPC service, denying service to transaction submission (`send_tx`), view calls, and query endpoints. If deployed broadly (validators exposing the same code path), this is a low-cost repeatable denial-of-service against block-producing or RPC infrastructure.

### Likelihood Explanation
High. The payload-size limit (10 MiB by default) is far larger than what is needed to reach thousands of nesting levels (`[[[[…]]]]` costs 2 bytes per level, so even a payload of tens of KB is enough to reach nesting depths that overflow a typical 1–8 MiB thread stack, well within limits accepted by both `RequestBodyLimitLayer` and `json_payload_max_size`). No authentication, signature, or on-chain state is required — it is a pure network-facing HTTP POST to the standard RPC port.

### Recommendation
- Enforce an explicit maximum JSON nesting depth when parsing RPC request bodies (e.g., using a bounded/depth-checked JSON parser, or a pre-pass that rejects payloads exceeding a small depth threshold such as 64–128 levels) before or during deserialization in `chain/jsonrpc-primitives/src/message.rs::from_slice`/`from_str` and in `chain/jsonrpc/src/api/mod.rs::Params::parse`.
- Consider running JSON parsing inside a resource/stack-limited context, or use a `serde_json` deserializer configuration/wrapper that tracks depth and errors out (`serde_json` supports custom `Deserializer` wrapping to track recursion depth).
- Add fuzz/regression tests that submit deeply nested JSON payloads (arrays and objects) to the RPC server and assert the server returns a parse error instead of crashing.

### Proof of Concept
1. Start a nearcore node with the JSON-RPC server enabled (default `RpcLimitsConfig::json_payload_max_size = 10 MiB`).
2. Construct a payload consisting of a JSON-RPC request whose `params` field is `N` nested arrays, e.g. programmatically generate `"[".repeat(N) + "]".repeat(N)` for `N` on the order of 100,000–1,000,000 (well under 10 MiB: `2*N` bytes).
3. POST this payload as the body of a standard JSON-RPC request to the node's RPC endpoint (`Content-Type: application/json`).
4. Observe that the worker thread parsing the body via `serde_json`/`near_jsonrpc_primitives::message::from_slice` overflows its stack; the resulting Rust abort crashes the RPC-serving process, denying service to all subsequent RPC calls.

*(Note: verifying the exact stack-overflow depth threshold and confirming there is no additional depth guard further upstream, e.g. inside `axum`'s `Json` extractor configuration, would require running the node locally; this could not be confirmed purely via static code search within the available indexing.)*
