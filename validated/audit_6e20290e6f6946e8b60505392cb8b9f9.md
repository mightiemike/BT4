## Analysis

The seed report (Decent Bridge H-03) is about a **refund/revert path picking an unauthenticated, unreachable address** when the destination-side call fails, permanently losing user funds because the fallback address has no way to move the money out.

The closest architectural analog in this repo is in the outbound revert/refund fallback logic in `x/uexecutor/keeper/outbound.go`, fed by `RevertInstructions.FundRecipient` that is decoded verbatim from an EVM event emitted by the `UniversalGatewayPC` contract (`x/uexecutor/keeper/create_outbound.go`).

### Root cause

`BuildOutboundsFromReceipt` unconditionally sets `RevertInstructions.FundRecipient` from the decoded `event.RevertRecipient` field of the `UniversalTxOutbound` log, with no validation that it is a non-zero, reachable address: [1](#0-0) 

The Solidity-side `RevertRecipient` is an `address` type. If the caller of `Gateway.withdraw(...)` (the UEA/payload logic) does not explicitly set a revert recipient, Solidity's default zero value (`address(0)`) is used, and the ABI decoder in `DecodeUniversalTxOutboundFromLog` will still produce a well-formed, non-empty hex string ("0x000...000") for it: [2](#0-1) 

Later, when the outbound fails on the destination chain, `handleFailedOutbound` and `applyGasRefund` both pick the revert/refund recipient using only a non-empty-string check — which the zero address passes — rather than checking for a meaningful, non-zero address: [3](#0-2) [4](#0-3) 

Both call sites (`CallPRC20Deposit`, `CallUniversalCoreRefundUnusedGas`) then mint/deposit the bridged PRC20 amount (and any excess gas refund) directly to `common.HexToAddress(recipient)` without checking `recipient != address(0)`. Minting PRC20 to the zero address is equivalent to burning it — the funds become permanently unrecoverable, exactly like the seed report's "funds sent to an address that cannot claim them."

### Why this matches the bug class

- Just like DecentBridge's `_from` being derived from an untrusted/wrong hop (`msg.sender` of an intermediate contract) instead of the true depositor, Push Chain's revert/refund recipient is derived from attacker/user-payload-controlled EVM event data (`event.RevertRecipient`) rather than a validated, non-zero destination.
- The fallback logic (`outbound.Sender` as secondary fallback) is reasonable, but the *primary* path (`RevertInstructions.FundRecipient != ""`) accepts the zero address as "set," bypassing the fallback to `outbound.Sender` entirely.
- The failure trigger (destination-chain execution failure, or `MsgVoteOutbound` reporting `success=false`) is reachable through ordinary, honest-validator observation of a normal user-initiated cross-chain call — no privileged actor is required.

### Caveat

This is a **self-affecting** griefing bug for the same UEA/payload owner who omitted `revertRecipient` in their own Gateway call, not a cross-user theft — the payload is the owner's own action (mediated by `MsgExecutePayload`'s signature-authenticated `executeUniversalTx`), so no other user's funds are put at risk. Given the required-impact gate strictly frames impacts as "of user or protocol-controlled funds" and "permanent loss" without requiring cross-user theft, this still fits as a valid, concrete, root-caused finding, but it is narrower in severity than the original H-03 (which affected any caller's cross-chain transfer).

### Title
Zero-address revert/refund recipient accepted from unvalidated Gateway event data causes permanent loss of bridged funds - (File: x/uexecutor/keeper/outbound.go, x/uexecutor/keeper/create_outbound.go)

### Summary
`RevertInstructions.FundRecipient` is populated directly from the `UniversalTxOutbound` EVM event's `revertRecipient` field without validating it is non-zero. When a `Gateway.withdraw()` call omits (or defaults) this parameter to `address(0)`, and the resulting outbound later fails on the destination chain, `handleFailedOutbound` and `applyGasRefund` treat the zero-address string as a "set" `FundRecipient` (since the check is only `!= ""`) and mint the bridged PRC20 / gas-refund amount to `0x000...000`, permanently destroying the funds.

### Finding Description
`BuildOutboundsFromReceipt` decodes `RevertRecipient` from the Gateway event and stores it verbatim as `OutboundTx.RevertInstructions.FundRecipient`: [5](#0-4) 

On outbound failure, `handleFailedOutbound` re-mints funds to this recipient: [3](#0-2) 

and `applyGasRefund` refunds any excess gas fee to the same recipient: [6](#0-5) 

Both checks are `FundRecipient != ""`, which is satisfied by the ABI-decoded zero-address string. Neither call site validates the resolved recipient address is non-zero before invoking `CallPRC20Deposit` / `CallUniversalCoreRefundUnusedGas`.

### Impact Explanation
Any bridged funds or excess gas refund tied to an outbound whose originating `Gateway.withdraw()` call left `revertRecipient` unset are irrecoverably burned the moment the outbound is voted as failed by Universal Validators — a state fully reachable through the honest, normal `MsgVoteOutbound` flow. This is a full, permanent loss of the affected UTX's principal and/or gas refund.

### Likelihood Explanation
Triggering requires only: (1) a payload/integration that calls `Gateway.withdraw()` without specifying a revert recipient (a plausible integrator oversight, not a privileged action), and (2) the destination-chain call subsequently failing (reachable any time gas is insufficient, target reverts, etc., and is voted honestly by UVs). No malicious validator, relayer, or TSS collusion is needed.

### Recommendation
Treat the zero address as "unset" in both `handleFailedOutbound` and `applyGasRefund` (i.e., check `FundRecipient != "" && FundRecipient != zeroAddressHex`), and fall back to `outbound.Sender`. Additionally, reject/flag `UniversalTxOutbound` events with a zero `revertRecipient` at ingestion time (`BuildOutboundsFromReceipt`) so operators can catch misconfigured payloads before funds are put at risk.

### Proof of Concept
1. A UEA executes a payload that calls `Gateway.withdraw(..., revertRecipient=address(0), ...)` for a `FUNDS` or `FUNDS_AND_PAYLOAD` outbound.
2. `BuildOutboundsFromReceipt` records `RevertInstructions.FundRecipient = "0x0000000000000000000000000000000000000000"`.
3. Universal Validators observe the destination-chain execution fail and submit `MsgVoteOutbound` with `success=false` (normal, honest operation).
4. `FinalizeOutbound` → `handleFailedOutbound` computes `recipient := outbound.RevertInstructions.FundRecipient` (zero address, passes the `!= ""` check) and calls `CallPRC20Deposit(prc20, 0x0, amount)`, burning the bridged principal.
5. If `applyGasRefund` also runs, the excess gas refund is minted to the same zero address and lost as well.
