### Title
Sandwiching `UnDelegateResourceContract` via `TotalNetWeight`/`TotalEnergyWeight` manipulation forces resource-usage loss on the delegator - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.execute` caps the amount of bandwidth/energy usage returned to the delegator (`transferUsage`) by a value (`unDelegateMaxUsage`) that is computed from the chain-wide `TotalNetWeight`/`TotalEnergyWeight` counters at the moment the transaction executes. These counters can be atomically inflated and deflated within the same block by any unprivileged account issuing `FreezeBalanceV2Contract`/`UnfreezeBalanceV2Contract` transactions, letting an attacker sandwich a victim's un-delegate transaction to force a lower usage-transfer cap, exactly mirroring the Beanstalk report's pattern of manipulating a shared, block-local pricing/ratio variable (deltaB) to force an unwanted "penalty" onto an honest user's transaction.

### Finding Description
`UnDelegateResourceActuator.execute` computes, for BANDWIDTH: [1](#0-0) 
and for ENERGY: [2](#0-1) 

The cap `unDelegateMaxUsage` is inversely proportional to `dynamicStore.getTotalNetWeight()` / `dynamicStore.getTotalEnergyWeight()`:
```
unDelegateMaxUsage = (unDelegateBalance / TRX_PRECISION) * (totalNetLimit / totalNetWeight)
transferUsage = min(unDelegateMaxUsage, proportionalUsage)
```
The larger `totalNetWeight`/`totalEnergyWeight` is at execution time, the smaller the cap, and the less bandwidth/energy usage is transferred from the receiver back to the owner when un-delegating. This transferred usage is later applied to the owner's account via `BandwidthProcessor.unDelegateIncrease` / `EnergyProcessor.unDelegateIncrease`: [3](#0-2) 

`TotalNetWeight`/`TotalEnergyWeight` are global counters that any unprivileged account can move up or down within the same block via `FreezeBalanceV2Actuator` (freeze increases the weight instantly): [4](#0-3) 
and via `UnfreezeBalanceV2Processor`/`UnfreezeBalanceV2Actuator` (unfreeze decreases it), e.g.: [5](#0-4) 

This is the exact analog of the Beanstalk bug class: a shared, in-block-mutable state variable (deltaB in Beanstalk; `TotalNetWeight`/`TotalEnergyWeight` in java-tron) is read by a victim's transaction to compute a punitive adjustment (stalk penalty in Beanstalk; usage-transfer cap here), and an unprivileged attacker can move that variable before the victim's transaction and move it back after, at low cost, to force an unfavorable outcome onto the victim. Unlike `ExchangeTransactionActuator`, which already implements a user-supplied minimum-output ("expected") protection against exactly this class of sandwich manipulation, `UnDelegateResourceActuator` has no analogous tolerance parameter — the owner cannot specify a minimum acceptable `transferUsage`, so the actuator silently accepts whatever value the current, attacker-influenced global weight produces.

### Impact Explanation
An attacker can broadcast a `FreezeBalanceV2Contract` transaction (BANDWIDTH or ENERGY) immediately before a targeted victim's `UnDelegateResourceContract` transaction in the same block, then broadcast an `UnfreezeBalanceV2Contract`/`CancelAllUnfreezeV2Contract` transaction immediately after, to temporarily inflate `TotalNetWeight`/`TotalEnergyWeight`. This lowers `unDelegateMaxUsage` for the victim's un-delegation, causing the victim's account to receive less bandwidth/energy usage credit back than it is legitimately owed (the "used" resource stays attributed to the receiver rather than returning proportionally to the delegator). This is an accounting-corruption / unfair-usage-transfer impact on the resource/reward accounting system, imposed on an honest user without their consent, with no way for the user to bound the loss (no equivalent of a "maximum tolerable penalty").

### Likelihood Explanation
The precondition set is low: any account can send `FreezeBalanceV2Contract` requiring only ≥1 TRX and `supportUnfreezeDelay()` (post `ALLOW_UNFREEZE_DELAY`-equivalent hardfork) already enabled — both `FreezeBalanceV2Actuator` and `UnDelegateResourceActuator` require this same flag (`dynamicStore.supportUnfreezeDelay()`), so if un-delegate is enabled, freeze v2/unfreeze v2 are also enabled. The attack requires transaction-ordering control within a block (a capability commonly available to block producers/witnesses, or approximated by fee/ordering games by any broadcaster), which is the same assumption underlying the original Beanstalk sandwich report. The magnitude of the effect scales with how large a freeze the attacker can afford relative to the existing `TotalNetWeight`/`TotalEnergyWeight`, which can be sizeable on chains/side-chains with lower total staked weight.

### Recommendation
- Avoid using a global, easily-and-cheaply-movable state (`TotalNetWeight`/`TotalEnergyWeight`) as a hard cap on a specific user's resource-usage transfer within a single atomic actuator; instead, snapshot/checkpoint the ratio at delegation time, or use a time-weighted/period-averaged weight so a single-block spike cannot dominate the computation.
- Add a user-specified minimum acceptable `transferUsage` (a "maximum tolerable penalty"/minimum-received parameter) to `UnDelegateResourceContract`, mirroring the `expected` field already present in `ExchangeTransactionContract`, and revert the transaction if the computed `transferUsage` falls below the caller's tolerance.
- Consider disallowing/delaying same-block freeze-then-unfreeze roundtrips that materially move `TotalNetWeight`/`TotalEnergyWeight`, or rate-limit how much a single transaction can change these global counters relative to recent history.

### Proof of Concept
1. Attacker prepares a large idle TRX balance.
2. Victim broadcasts `UnDelegateResourceContract` (BANDWIDTH) to reclaim delegated resource from a receiver.
3. Attacker front-runs with `FreezeBalanceV2Contract` (resource=BANDWIDTH) freezing a large amount of TRX, calling `FreezeBalanceV2Actuator.execute`, which immediately increases `dynamicStore.addTotalNetWeight(...)` (lines 62-65 above) before the victim's transaction executes in the same block.
4. Victim's `UnDelegateResourceActuator.execute` runs; `unDelegateMaxUsage` is computed with the now-inflated `dynamicStore.getTotalNetWeight()`, producing a smaller cap than would have existed absent the attack, reducing `transferUsage` returned to the victim (lines 79-88 above).
5. Attacker back-runs with `UnfreezeBalanceV2Contract` for the same BANDWIDTH amount, restoring `TotalNetWeight` to its prior value and recovering their TRX (subject to any unfreeze delay/withdraw timing rules).
6. Net effect: the victim's un-delegate transaction returns less usable bandwidth usage than it would have without the sandwich, while the attacker's TRX is only temporarily locked/moved, at comparatively low cost.
