### Title
Boundary block for a PoisonMicroblock report matures before the report is written, letting a valid last-block report be silently ignored - (File: `stackslib/src/chainstate/stacks/db/transactions.rs::handle_poison_microblock`, `stackslib/src/chainstate/stacks/db/accounts.rs::find_mature_miner_rewards`)

### Summary
`handle_poison_microblock` accepts a report as long as `current_height <= height + MINER_REWARD_MATURITY`, but the reward for `height` is computed by `find_mature_miner_rewards`/`calculate_matured_miner_rewards` **before** the current block's own transactions (including the just-submitted poison report) are applied. A report filed in exactly the boundary block (`current_height == height + MINER_REWARD_MATURITY`) is accepted and recorded, but the coinbase for `height` has already been paid out in full to the miner in that same block, so the report has no effect.

### Finding Description
The claimed equality is: the commission-eligible report must be visible to `find_mature_miner_rewards` at the moment `reward_height == height` is evaluated, i.e. `poison_reward_paid == earned_by_reporter`.

- `handle_poison_microblock` in `stackslib/src/chainstate/stacks/db/transactions.rs:783-803` only rejects when `height + MINER_REWARD_MATURITY < current_height`; equality (`current_height == height + MINER_REWARD_MATURITY`) is accepted, and the report is written via `insert_microblock_poison` keyed by `mblock_pubk_height` (= `height`).
- `find_mature_miner_rewards` in `stackslib/src/chainstate/stacks/db/accounts.rs:993-1031` computes `reward_height = tip_stacks_height - MINER_REWARD_MATURITY` and looks up `get_poison_microblock_report(clarity_tx, reward_height)`. Because `tip_stacks_height` for the maturation event equals `height + MINER_REWARD_MATURITY`, `reward_height` is exactly `height` — so on paper the keys line up.
- The bug is in **when** this lookup happens relative to the block's own transaction processing. In the epoch2x path (`stackslib/src/chainstate/stacks/db/blocks.rs:5101-5107`), `find_mature_miner_rewards` is called right after `chainstate_block_begin`/`reset_cost`, **before** `process_block_transactions` (`blocks.rs:5595-5598`) runs. In the Nakamoto path, `calculate_matured_miner_rewards` is likewise invoked inside `inner_setup_block` (`stackslib/src/chainstate/nakamoto/mod.rs:4671-4682`) before the block's transactions execute.
- Consequently, a `PoisonMicroblock` transaction included in the *same block* that matures `height`'s reward (the boundary block, `current_height == height + MINER_REWARD_MATURITY`) is validated and accepted by `handle_poison_microblock` (no error, report written to the DB), but `find_mature_miner_rewards` for that block already ran against the pre-transaction Clarity state, which has no report yet. `calculate_miner_reward` (`accounts.rs:804-905`) therefore pays the miner's full, unslashed coinbase. Since each height's reward matures exactly once (in exactly that one block), the freshly-written report is permanently orphaned — no later block will ever query `reward_height == height` again.
- No existing guard closes this gap: `handle_poison_microblock`'s maturity check is strictly about whether the report is *too late*, not about whether it is still processed *before* the payout snapshot is taken; there is no cross-check against the coinbase-height parity used by `find_mature_miner_rewards`.

### Impact Explanation
This is a poison-report/reward mis-payment: the honest reporter's rightful `POISON_MICROBLOCK_COMMISSION_FRACTION` share of the coinbase is never paid, and the microblock-forking miner keeps the full, un-slashed coinbase for that block despite a report being filed within the nominally valid window and successfully recorded on-chain. This matches the rules' High-severity category "a poison or reward mis-payment bounded to fees" (poison/reward mis-payment), not a chain split or state-root divergence — all nodes agree on the (wrong) payout deterministically, so there is no fork. Impact is scoped to the single miner/reporter pair at the affected height and is repeatable whenever a report lands in the exact boundary block.

### Likelihood Explanation
No special stake or privilege is needed. The condition requires only that a valid `PoisonMicroblock` report tx be included in the block at `height + MINER_REWARD_MATURITY` rather than any earlier block — e.g., a miner who wants to protect themselves or an ally from the slash need only win (or otherwise arrange for) the sortition at that specific height and delay/withhold the mempool report until then, or the report may simply arrive late from network propagation and get picked up only by that final eligible block. This is fully within reach of a single unprivileged miner slot and requires no majority stake; it is deterministic once the timing condition is met and reproducible on demand in a local chainstate test.

### Recommendation
Tighten the acceptance window in `handle_poison_microblock` so that the report must be included strictly before the block that matures the reward, i.e. reject when `height + MINER_REWARD_MATURITY <= current_height` (not just `<`), ensuring reports cannot be filed in the block that performs the maturity payout. Alternatively, move the `find_mature_miner_rewards` lookup to occur after the current block's own transactions (including any PoisonMicroblock report) have been applied, so the report is visible to the same-block maturation check.

### Proof of Concept
Rust integration test outline (using the existing test harness in `stackslib/src/chainstate/stacks/tests/block_construction.rs`):
1. Mine a tenure at height `H` with a microblock stream that forks (as in `test_build_microblock_stream_forks_...`), producing a poisonable `microblock_pubkey_hash` at height `H`.
2. Advance the chain for `MINER_REWARD_MATURITY - 1` further tenures without ever submitting the `PoisonMicroblock` report.
3. At tenure height `H + MINER_REWARD_MATURITY` (the boundary block), include a valid `PoisonMicroblock` transaction from a reporter address in that block's transaction set.
4. Assert:
   - `StacksChainState::process_transaction`/block processing succeeds without error (the report is "accepted").
   - `StacksChainState::get_poison_microblock_report(clarity_tx, H)` returns `Some((reporter_addr, seq))` after the block commits (proving the report was written).
   - `StacksChainState::get_matured_miner_payment(...)` for the block at height `H`'s reward shows the **miner's** address (`earned_by_reporter` side) received the full, un-slashed coinbase rather than the reporter receiving `POISON_MICROBLOCK_COMMISSION_FRACTION` of it — i.e. `poison_reward_paid != earned_by_reporter`, breaking the intended equality and showing `TENURE_REWARD` was paid to the cheating miner in full.
