**Analysis:**

The path requires calling `chunky_dkg_config_seqnum::set_for_next_epoch`, which is gated by `system_addresses::assert_aptos_framework(framework)` [1](#0-0) . This function can only be invoked with the `@aptos_framework` signer, reachable only through governance proposals or the framework-internal `reconfiguration_with_dkg` module, not from unprivileged transactions, packages, or API/view/bytecode entry points as required by the scope rules.

Even setting aside the privilege requirement, the buffering mechanism itself is not vulnerable to double-buffering or staleness from repeated calls. `config_buffer::upsert` stores at most one entry per config type in a `SimpleMap` keyed by `type_info::type_name<T>()`, and calling `upsert` again with the same type simply replaces the prior value via `configs.upsert(key, value)` [2](#0-1) . There is no way for two pending values to coexist — the second `set_for_next_epoch` call always overwrites the first. When `on_new_epoch` later runs, `extract_v2` removes and returns exactly the single most-recently-buffered value and clears the entry [3](#0-2) , then `on_new_epoch` writes that value into the global resource [4](#0-3) . This is deterministic "last write wins" semantics, which is exactly the intended design of `config_buffer` for async config updates under DKG, and matches every other config module using the same pattern (e.g. `randomness_config_seqnum.move`) [5](#0-4) .

The monotonicity check (`assert!(seq_num > current, ...)`) compares against the currently *committed* on-chain value, not the pending buffered value, so a sequence of calls like `set(5)` then `set(3)` is legal if the on-chain value is still `0`, and the final buffered/applied value is simply whatever the last call set — this is the correct, intended VM result for the last authorized call, not a stale or double-buffered write. There is no divergence between the VM's correct result and what gets committed; both are the value from the final `set_for_next_epoch` call prior to `on_new_epoch`.

Since (1) the entry point is privileged/governance-gated rather than reachable from unprivileged input, and (2) the buffer/extract logic produces no state divergent from the correctly intended last-call value, this does not meet the State-Integrity Gate criteria.
