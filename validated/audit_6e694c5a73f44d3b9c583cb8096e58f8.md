### Title
Missing negative-value validation in `extractDestGasAmountFromMap` allows int64→uint32 sign-wraparound corruption of `DestGasAmount` - ([File: core/capabilities/ccip/ccipsolana/executecodec.go])

### Summary
`extractDestGasAmountFromMap` accepts an `int64`-typed `destgasamount` value from a decoded `DestExecData` map and only rejects values `> math.MaxUint32`, but never rejects negative values, unlike the sibling field-parsing code in the same package (`parseExtraDataMap`'s `computeunits`/`accountiswritablebitmap` handling) which explicitly checks `v < 0`. A negative `int64` therefore passes validation and is silently converted with `uint32(v)`, wrapping around to a large unsigned value that is folded directly into `ccip_offramp.Any2SVMTokenTransfer.DestGasAmount`, which is consensus-critical hash/report input.

### Finding Description
`extractDestGasAmountFromMap` in `core/capabilities/ccip/ccipsolana/executecodec.go` handles the `int64` branch (representing the LOOP gRPC-converted form of a `uint32`) as follows: [1](#0-0) 

```go
case "destgasamount":
    switch v := fieldValue.(type) {
    case uint32:
        return v, nil
    case int64: // LOOP converts expected uint32 to int64
        if v > math.MaxUint32 {
            return 0, fmt.Errorf("destGasAmount exceeds uint32 max, got %d", v)
        }
        return uint32(v), nil //nolint:gosec // G115: validated to be within uint32 max above
    default:
        return 0, errors.New("invalid type for destgasamount, expected uint32 or int64")
    }
```

Only the upper bound (`v > math.MaxUint32`) is checked; there is no `v < 0` check. Contrast this with the analogous field handling in the same file's neighbor `parseExtraDataMap` (`core/capabilities/ccip/ccipsolana/msghasher.go`), which correctly validates both bounds: [2](#0-1) 

The `//nolint:gosec // G115: validated to be within uint32 max above` comment asserts full validation occurred, but this claim is false — only half the range check is present, so it's a real logic gap, not just a suppressed lint.

This function is called from two consensus-relevant paths:
- `MessageHasherV1.Hash` builds `ccip_offramp.Any2SVMTokenTransfer.DestGasAmount` directly from its return value, which feeds `ccip.HashAnyToSVMMessage` — the OCR commit message hash. [3](#0-2) 
- `ExecutePluginCodecV1.Encode` similarly uses it to build the execute report's `Any2SVMTokenTransfer.DestGasAmount`. [4](#0-3) 

If a negative `int64` (e.g. `-1`) reaches this switch, `uint32(-1)` silently wraps to `4294967295`, corrupting the `DestGasAmount` field used both when hashing (potential mismatch relative to other nodes/implementations that do not hit this code path, e.g. a peer running native `uint32` decoding) and when constructing the on-chain execution report (over-committing gas / passing an unintended value into `Any2SVMTokenTransfer`).

### Impact Explanation
A corrupted `DestGasAmount` flows into the message hash computed for OCR commit/consensus (`MessageHasherV1.Hash`) and into the encoded execute report sent to the Solana `ccip_offramp` program (`ExecutePluginCodecV1.Encode`). This can cause hash mismatches between honest nodes that decode the same underlying data differently (e.g., LOOP-relayed `int64` path vs. native `uint32` path), or produce a materially wrong (very large) gas amount baked into a signed report, matching the "misreporting/data tampering" and "hash mismatch enabling message forgery" impact class described in the question.

### Likelihood Explanation
The bug is unconditionally reachable any time the `ExtraDataCodecBundle.DecodeTokenAmountDestExecData` output map contains a `destgasamount` key with an `int64` value that happens to be negative. This depends on the LOOP/protobuf-based codec's encoding path (out of scope of this file) potentially producing a negative `int64` for what should be an unsigned 32-bit quantity (e.g., via a signed 32-bit wire type or sign-extension bug upstream). Within the file audited, there is no defense-in-depth: the function itself provides no lower-bound check, unlike its sibling parser in `parseExtraDataMap`, making this a straightforward, directly-testable logic defect independent of how likely the upstream codec is to actually emit a negative value.

### Recommendation
Add the missing lower-bound check, consistent with `parseExtraDataMap`:
```go
case int64:
    if v < 0 || v > math.MaxUint32 {
        return 0, fmt.Errorf("destGasAmount out of uint32 range: %d", v)
    }
    return uint32(v), nil
```
Apply the same fix to every other `extractDestGasAmountFromMap` implementation with the identical pattern (`ccipevm/msghasher.go`, `ccipsui/msghasher.go`, `ccipaptos/msghasher.go`) if they share this gap.

### Proof of Concept
Unit/fuzz test directly against `extractDestGasAmountFromMap` in `core/capabilities/ccip/ccipsolana`:

```go
func TestExtractDestGasAmountFromMap_NegativeInt64(t *testing.T) {
    m := map[string]any{"destGasAmount": int64(-1)}
    got, err := extractDestGasAmountFromMap(m)
    // Current behavior: err == nil, got == 4294967295 (wraparound) -- BUG
    require.Error(t, err, "negative destGasAmount must be rejected")
}

func FuzzExtractDestGasAmountFromMap(f *testing.F) {
    f.Add(int64(-1))
    f.Add(int64(0))
    f.Add(int64(math.MaxUint32))
    f.Add(int64(math.MaxUint32) + 1)
    f.Fuzz(func(t *testing.T, v int64) {
        m := map[string]any{"destGasAmount": v}
        got, err := extractDestGasAmountFromMap(m)
        if v < 0 || v > math.MaxUint32 {
            require.Error(t, err)
        } else {
            require.NoError(t, err)
            require.Equal(t, uint32(v), got)
        }
    })
}
```
Expected assertion: negative values must return an error rather than silently wrapping into an unrelated large `uint32`.
