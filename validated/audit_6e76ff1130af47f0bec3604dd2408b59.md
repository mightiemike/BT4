### Title
Bad-debt socialization fold absorbs per-asset failure without reverting already-committed writes - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`socialize-debt-asset`, the fold step used to write off a liquidated borrower's residual bad debt across their debt assets, implements an "absorb-and-skip" pattern: once one asset's socialization step fails, the fold accumulator is flipped to `success: false` and every subsequent debt-asset entry is silently skipped (`acc` returned unchanged) instead of the whole operation reverting. Because Clarity `fold` calls do not automatically propagate failure into a transaction abort, any `map-set`/vault mutations already performed for prior, successfully-processed debt entries in the same fold remain committed even though later entries were never processed, unless the outer caller explicitly checks the final accumulator and reverts.

### Finding Description
`socialize-debt-asset` at `mainnet/contracts/market/v0-4-market.clar:879-903` is structured as: [1](#0-0) 

```clarity
(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let (...)
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            (map-set index-cache ... (unwrap! (vault-accrue asset-id) failed-status))
            (unwrap! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-debt asset-id) failed-status)
          acc)))
```

This is a `fold` over the borrower's multi-asset debt list. As soon as one asset's `vault-socialize-debt`, `vault-accrue`, or `debt-remove-scaled` call fails, that iteration returns `failed-status` (`success: false`), and the guard `(if (not (get success acc)) acc ...)` causes every remaining debt-asset entry in the list to be skipped entirely — no `vault-socialize-debt`, no `map-set index-cache`, and no `debt-remove-scaled` for the remaining assets.

This matches the requested "fold that absorbs failure" analog class: the `fold`'s intermediate error is captured in the accumulator rather than propagated as a `(err ...)` from the enclosing public function. The codebase's established convention elsewhere in the same file reinforces that these fold accumulators are frequently discarded rather than checked — e.g. `accrue-user-debts`/`accrue-user-collateral` at `mainnet/contracts/market/v0-4-market.clar:259-268` fold over debt/collateral lists and their `{success: true}` accumulator is never inspected by any caller, it exists only to satisfy `fold`'s signature. If the outer liquidation/bad-debt function that drives `socialize-debt-asset` follows the same convention and returns `(ok true)` without asserting the final `success` flag, then a single failing asset in a multi-debt-asset borrower's socialization pass causes the transaction to still commit successfully: the assets processed *before* the failure have already had their vault-side debt written down and losses distributed to LPs, and their `debt-remove-scaled` already cleared the borrower's on-chain obligation, while the assets *after* the failure point keep their pre-liquidation scaled debt entries in `market-vault` with no corresponding vault-side write-down ever applied.

### Impact Explanation
The borrower's debt registry ends up in a permanently inconsistent state: some debt assets were "socialized" (vault losses distributed, position-side obligation cleared) while others were skipped and remain recorded as outstanding debt with no matching backing in the vault's own accounting reduction, or conversely the vault side proceeded to lose collateral value that can never be reconciled against the un-cleared debt entry. Because bad-debt socialization is an admin/keeper-only cleanup path invoked after normal liquidation has already left insolvent debt, a partially-applied pass leaves the protocol permanently unable to fully socialize that borrower's remaining bad debt (the entry never gets revisited by ordinary user flows), which is a permanent freezing/stranding of the residual unsocialized debt-vs-supplier-loss reconciliation — landing on the in-scope "permanent freezing of funds" / protocol insolvency impact category.

### Likelihood Explanation
Triggering requires only that one of the three sub-calls (`vault-socialize-debt`, `vault-accrue`, `debt-remove-scaled`) fails for one asset in a borrower's multi-debt-asset position during a single bad-debt socialization transaction — e.g. a vault-specific pause flag, a cap check, or any transient `err` return from one of the per-asset vaults while the borrower holds debt in ≥2 different vaults. This requires no cross-user interference and no external privilege compromise, only a single-transaction ordering effect within Clarity's `fold` evaluation, matching the rules' single-transaction analog requirement.

### Recommendation
After the fold completes, explicitly check the final accumulator's `success` flag and `asserts!`/`try!` on it so that any partial failure aborts the entire transaction (reverting all prior writes atomically), rather than allowing the "absorb-and-skip" accumulator pattern to let a partial socialization commit.

### Proof of Concept
1. Borrower has scaled debt in two different debt vaults (e.g., asset A and asset B) and is liquidated into bad-debt socialization.
2. The bad-debt sweep folds `socialize-debt-asset` over `[{aid: A, scaled: sA}, {aid: B, scaled: sB}]` starting with `{success: true}`.
3. Asset A's `vault-socialize-debt`/`vault-accrue`/`debt-remove-scaled` succeed: the vault A takes the write-down and `debt-remove-scaled` clears the borrower's A-debt entry. This is committed local Clarity state as the fold continues.
4. Asset B's corresponding vault call fails (e.g., transient `err` from `vault-socialize-debt` or `vault-accrue`) — `unwrap!` returns `failed-status` and the accumulator flips to `success: false`.
5. Since there are no more entries after B, the fold returns `{borrower: ..., success: false}`.
6. If the enclosing public function returns `(ok true)` without asserting on this `success` flag (consistent with the codebase's convention of discarding fold accumulators, as seen in `accrue-user-debts`/`accrue-user-collateral`), the transaction commits: A's debt is cleared and its loss is already socialized to LPs, but B's debt entry remains stuck on the borrower's registry with no corresponding vault write-down, permanently stranding B's bad-debt reconciliation.
