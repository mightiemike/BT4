## Title
Deeply nested Cairo0 contract ABI/identifiers JSON causes unbounded-recursion StackOverflow in deprecated class-hash computation - (File: crates/starknet_os/src/hints/class_hash/hinted_class_hash.rs)

### Summary
`compute_cairo_hinted_class_hash` and `compute_deprecated_class_hash` deserialize an attacker-supplied Cairo0 `ContractClass` into `CairoContractDefinition`, which stores the `abi`, `identifiers`, and `reference_manager` fields as raw, unconstrained `serde_json::Value` trees [1](#0-0) . The function then recursively walks these JSON values with `sort_json_value`, which has no depth bound and recurses once per nesting level [2](#0-1) .

### Finding Description
`compute_cairo_hinted_class_hash` first serializes the whole `ContractClass` to a `serde_json::Value`, then calls `sort_json_value` on it before re-parsing it into `CairoContractDefinition` and re-serializing it for hashing [3](#0-2) . `sort_json_value` recurses into every nested `Object`/`Array` node without any recursion-depth check, exactly the bug class described in the jackson-databind advisory (unbounded native-stack recursion while walking a JSON-derived tree built from attacker-controlled deep nesting). In addition, `serde_json::from_slice` itself is a recursive-descent parser with no depth limit, so a deeply-nested `abi` (an arbitrary, schema-less `serde_json::Value`, per the doc comment "Contract ABI, which has no schema definition") can already overflow the stack during deserialization, before `sort_json_value` is even reached [4](#0-3) .

This code path is invoked from `compute_deprecated_class_hash`, which recomputes the class hash for deprecated (Cairo0) declared classes, re-deriving `CairoContractDefinition` from the same untrusted `ContractClass` [5](#0-4) . `ContractClass::abi` for deprecated classes is explicitly documented as unverified attacker content: "Starknet does not verify the abi. If we can't parse it, we set it to None" [6](#0-5) , but that fallback only applies to the strongly-typed `ContractClassAbiEntry` vector used at the API layer — the `CairoContractDefinition::abi` field in `hinted_class_hash.rs` is a raw, unrestricted `serde_json::Value`, so an attacker can submit any deeply nested JSON structure (or nested `identifiers`/`reference_manager`/`hints` values, which are also raw `serde_json::Value`s) inside a Cairo0 declare transaction's contract class.

This class-hash recomputation is used by the Starknet OS during (re-)execution of declared classes to verify the declared class hash matches the submitted contract, i.e. it is reachable directly from a `DECLARE` transaction (V0/V1) submitted by any unprivileged sender through the gateway, or indirectly whenever the sequencer/OS re-executes/re-hashes such a class.

### Impact Explanation
A single Declare transaction (V0/V1, Cairo0) with a deeply nested JSON value in `abi`, `program.identifiers`, `program.reference_manager`, or `program.hints` can crash the process computing the class hash with a native `StackOverflowError`-equivalent abort in Rust (stack overflow → process abort, not a catchable `Result::Err`). Because class-hash computation happens as part of transaction/class processing in the sequencer and the Starknet OS re-execution path, this can crash the sequencer process handling the transaction (denial of service), and if triggered during OS re-execution, it can prevent block/state re-verification from completing — a chain-halting DoS rather than a mere resource-consumption issue, satisfying "network unable to confirm new transactions."

### Likelihood Explanation
Likelihood is high for any unprivileged actor: only crafting a Cairo0 declare transaction with deeply nested JSON in one of these unconstrained value fields is required; no special privileges, size limits specific to nesting depth, or race conditions are needed. Existing size validators (e.g., `max_contract_class_object_size`, `max_contract_bytecode_size` in the gateway config) bound total payload size but do not bound JSON structural nesting depth — a 2KB payload can already encode 1000s of nesting levels, well under any byte-size cap [7](#0-6) .

### Recommendation
- Enforce an explicit maximum nesting-depth check on the raw `abi`, `identifiers`, `reference_manager`, and `hints` JSON values before/while parsing (reject with a normal validation error rather than allowing unbounded recursion), or use an iterative (stack-based, non-recursive) implementation for `sort_json_value` and JSON tree traversal.
- Consider using a depth-limited JSON parser/deserializer or apply `serde_json`'s workaround pattern (bounded manual recursion counter) at the point where `CairoContractDefinition` is deserialized from untrusted input.
- Add a stateless validator step in the gateway (similar to `max_contract_class_object_size`) that rejects Cairo0 declare transactions whose ABI/program JSON exceeds a safe nesting depth, run before the class ever reaches OS re-execution / hash computation.

### Proof of Concept
1. Craft a Cairo0 `DECLARE` transaction (V0 or V1) whose `contract_class.abi` field is a deeply nested JSON array/object, e.g. `[[[[...]]]]` nested ~50,000+ levels deep (still only a few hundred KB, well under `max_contract_class_object_size`).
2. Submit the transaction via the gateway HTTP endpoint (`/gateway/add_transaction`).
3. When the sequencer/OS calls `compute_deprecated_class_hash` → `compute_cairo_hinted_class_hash`, either the initial `serde_json::from_slice::<CairoContractDefinition>` parse or the subsequent `sort_json_value` recursive walk will exhaust the native call stack, aborting the process [8](#0-7) .

Note: I could not fully trace every call site that reaches `compute_deprecated_class_hash`/`compute_cairo_hinted_class_hash` during normal gateway validation vs. OS re-execution only (the search results show it wired into `deprecated_compiled_class` hint implementation and OS-side class-hash cairo code, but the exact real-time trigger point in the stateful gateway validator was not confirmed within the available index). A Devin session with full repository access would be needed to confirm whether this path is exercised synchronously during gateway `add_transaction` handling versus only during batch/OS re-execution.

/// Recursively sorts all JSON objects by their keys.
/// This ensures deterministic serialization regardless of the `preserve_order` feature in
/// serde_json.
fn sort_json_value(value: serde_json::Value) -> serde_json::Value {
    match value {
        serde_json::Value::Object(map) => {
            let sorted: BTreeMap<String, serde_json::Value> =
                map.into_iter().map(|(k, v)| (k, sort_json_value(v))).collect();
            serde_json::Value::Object(sorted.into_iter().collect())
        }
        serde_json::Value::Array(arr) => {
            serde_json::Value::Array(arr.into_iter().map(sort_json_value).collect())
        }
        other => other,
    }
}

pub fn compute_cairo_hinted_class_hash(
    contract_class: &ContractClass,
) -> Result<Felt, HintedClassHashError> {
    // Serialize to Value, sort all objects by keys for deterministic output, then to bytes.
    // The sorting is necessary because serde_json with `preserve_order` feature enabled
    // maintains insertion order instead of sorting keys.
    // TODO(Meshi): Compute hinted hashes when loading serialized contracts from storage, before
    // deserializing, to avoid back-and-forth serde.
    let contract_value = serde_json::to_value(contract_class)?;
    let sorted_contract_value = sort_json_value(contract_value);
    let contract_definition_vec = serde_json::to_vec(&sorted_contract_value)?;
    let contract_definition: CairoContractDefinition<'_> =
        serde_json::from_slice(&contract_definition_vec)?;

    let mut string_buffer = vec![];

    let mut ser = serde_json::Serializer::with_formatter(&mut string_buffer, PythonJsonFormatter);
    contract_definition.serialize(&mut ser)?;
