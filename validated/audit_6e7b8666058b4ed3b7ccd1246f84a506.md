### Title
Token-Name Front-Running in `AssetIssueActuator` Permanently Blocks Legitimate Token Issuance - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
When the chain parameter `AllowSameTokenName` is disabled (`0`), `AssetIssueActuator` enforces global uniqueness of TRC10 token names via a check-then-set pattern on `AssetIssueStore`, keyed by the attacker-guessable, mempool-visible `name` field. This mirrors the `CredibleAccountModule.enableSessionKey` bug class: any unprivileged account can observe a pending, legitimate `AssetIssueContract` transaction in the mempool and front-run it with their own transaction using the same `name`, permanently occupying that name and causing the legitimate issuer's transaction to fail with `"Token exists"`.

### Finding Description
In `validate()`, uniqueness is checked with a simple existence lookup that is not bound to the intended issuer in any way: [1](#0-0) 
The `name` used as the lookup/storage key is fully attacker-controlled and visible in the mempool before the legitimate transaction is confirmed, since the actuator reads `assetIssueContract.getName()` directly from an unsigned, publicly broadcast contract: [2](#0-1) 
On `execute()`, the token is stored under `assetIssueCapsule.createDbKey()` (derived from `name`) with no relation to who "reserved" it beforehand: [3](#0-2) 
There is no per-account reservation, commit-reveal, or nonce/signature binding tying a specific `name` to the specific sender who intends to use it — exactly the missing "SCW -> sessionKey" binding described in the external report for `CredibleAccountModule`.

Additionally, the actuator enforces a stronger invariant that an account may issue only one asset ever: [4](#0-3) 
This is confirmed by the existing test `assetIssueNameTest`/`IssueSameTokenNameAssert`, which shows that once a name is claimed the legitimate owner permanently loses the ability to issue that (or any) asset: [5](#0-4) 

### Impact Explanation
Since each account is limited to issuing exactly one asset for its lifetime (`"An account can only issue one asset"`), a griefing front-run permanently denies the victim's ability to ever issue a TRC10 token under the intended name (they would need to either abandon that name or, since the one-asset-per-account check already fired only on the same account collision — but the *name* squat by attacker's own account causes `Token exists` for the honest issuer regardless of which account tries the same name next). This is a concrete denial-of-service / griefing on public state that blocks legitimate token issuance, directly analogous to the "attacker griefs SCW's session key enablement" impact in the report.

### Likelihood Explanation
This requires only mempool visibility and the ability to submit a competing transaction with higher fee/priority — no privileged role is needed. This is realistic on any account-based, mempool-visible blockchain and is the same threat model as the original report (front-running via mempool observation). The main mitigating factor is that `AllowSameTokenName` is a committee-controlled chain parameter (`ProposalUtil`/`DynamicPropertiesStore`) that, once set to `1`, disables this check path; however, the vulnerable code remains reachable whenever the parameter is `0`, and the check-then-set race condition itself is a genuine logic flaw independent of the parameter's current mainnet setting.

### Recommendation
Do not allow a bare, attacker-controlled string comparison to gate a global, non-reversible resource claim. Options:
- Bind the reservation to `ownerAddress` (e.g., require the name to be pre-registered/committed by the owner in a separate step with a nonce/hash commit-reveal), or
- Require the `AssetIssueContract` to include a signature/commitment created ahead of time so front-runners cannot simply copy the visible `name` field, or
- If same-token-name mode is to remain supported, consider deprecating the exclusive one-time reservation semantics so a squatted name does not permanently exhaust the victim's one-time issuance right.

### Proof of Concept
1. Attacker monitors the mempool/API and sees an `AssetIssueContract` transaction from victim `V` with `name = "MYTOKEN"`, `AllowSameTokenName == 0`.
2. Attacker immediately broadcasts their own `AssetIssueContract` with `name = "MYTOKEN"` and a higher energy/fee bid so it is packed first.
3. Attacker's actuator `execute()` succeeds, calling `assetIssueStore.put(assetIssueCapsule.createDbKey(), ...)` for key `"MYTOKEN"`. [3](#0-2) 
4. Victim `V`'s transaction is then validated and hits the existence check, throwing `ContractValidateException("Token exists")`. [1](#0-0) 
5. Because an account can only issue one asset for its entire lifetime, `V` cannot retry with the same or a different name once flagged/attempted appropriately (per the one-asset-per-account invariant), demonstrating a permanent griefing outcome analogous to the session-key front-running report. [4](#0-3)
