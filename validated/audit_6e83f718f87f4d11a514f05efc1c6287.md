### Title
Stale per-timestamp `index-cache` allows a within-transaction ztoken price to diverge from the vault's actual liquidity index after accrual - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`accrue-and-cache` caches vault `{index, lindex}` keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . Because the key is time-based rather than state-based, once a vault's indexes are cached for the current block, `resolve-ztoken` will keep using that same cached `lindex` to price a ztoken for the rest of the transaction/block, even if the underlying vault's real index has since moved due to further vault mutation in the same execution.

### Finding Description
`accrue-and-cache` is a classic "cache a value keyed by something coarser than its true invalidation trigger" pattern: the correct invalidation trigger is "the vault's index changed," but the actual invalidation trigger implemented is "the block timestamp changed" [2](#0-1) . Within one block, `accrue-and-cache` is called repeatedly from `accrue-collateral-asset`/`accrue-debt-asset` (during position accrual) and again from `resolve-ztoken` while resolving oracle prices for ztoken collateral [3](#0-2) . On a cache hit it simply returns the previously stored `{index, lindex}` without re-checking the vault [4](#0-3) .

The notional-value evaluation used for health checks calls `accrue-and-cache` again to fetch the debt index for computing debt notional [5](#0-4) , and `resolve-ztoken` calls `get-cached-indexes` to price ztoken collateral [3](#0-2) . If any vault-mutating call (e.g., `vault-deposit`, `vault-redeem`, `system-borrow`, `system-repay`, or an ERC4626-style `convert-to-assets` change) happens in the same block after the index was first cached, the vault's real `lindex` moves, but `index-cache` still returns the earlier snapshot for any subsequent read in that same block/timestamp — because the cache key never changes within a block.

I was not able to fully verify, within the remaining budget, the precise ordering of oracle price resolution relative to vault mutation inside the top-level public entry points (e.g., a combined "deposit collateral + borrow" or "repay + withdraw" flow), so I cannot state with certainty that a single public function reaches this stale-read in one transaction without an intervening call boundary. This should be confirmed by reading the full bodies of the public entry points in `mainnet/contracts/market/v0-4-market.clar` (borrow, withdraw, deposit-collateral, liquidate) to see whether `accrue-and-cache`/`resolve-ztoken` is invoked before and after a vault-mutating sub-call within the same transaction.

### Impact Explanation
If reachable in a single transaction, a stale cached `lindex` would let the market misprice ztoken collateral relative to the vault's true share value at the point of the health check — either overvaluing collateral (letting a user borrow more than actually collateralized, i.e. temporary/permanent freezing or shortfall of protocol funds) or undervaluing it (unfairly triggering liquidation). This lands in the "temporary freezing of funds" / protocol insolvency impact category if the divergence is large enough to move a position across the liquidation threshold using a stale, rather than current, index.

### Likelihood Explanation
Likelihood is **not confirmed** — this write-up is based on the caching mechanism's design combined with the report's bug class ("cached value not invalidated when its source moves"), but I could not verify an actual reachable multi-step call path in the current tool budget where a vault mutation and a stale-cache price read occur in the same transaction after the cache is first populated. This needs direct code confirmation before being treated as validated.

### Recommendation
Invalidate/refresh `index-cache` on any vault state-mutating call within the same transaction (e.g., clear or overwrite the cache entry for that `aid` immediately after `vault-deposit`, `vault-redeem`, `system-borrow`, `system-repay`, `socialize-debt` execute), rather than relying solely on the block timestamp as the cache key.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
