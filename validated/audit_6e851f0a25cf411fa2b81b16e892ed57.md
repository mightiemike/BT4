### Title
Front-runnable, permanent, zero-cost griefing of `SetAccountIdContract` allows an attacker to steal a victim's chosen account ID from the mempool - (`actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`)

### Summary
Analogous to the reported Folks-Finance bug (an attacker monitoring the mempool front-runs a victim's account-registration call to steal the victim's chosen identifier), java-tron's `SetAccountIdActuator` lets any account bind a unique, human-readable `accountId` to its address. This binding is first-come-first-served, globally unique, permanent (can only be set once per account), and costs zero fee, making it trivially front-runnable by an unprivileged attacker watching the public mempool.

### Finding Description
When a user broadcasts a `SetAccountIdContract` to claim a desired `accountId` (e.g. a vanity name), the transaction is visible in the public mempool before being packed into a block. `SetAccountIdActuator.validate()` rejects the operation if the `accountId` is already registered in `AccountIdIndexStore`: [1](#0-0) 

and `execute()` unconditionally writes the caller's own address as the owner of that `accountId`: [2](#0-1) 

Because the check-then-set is racey at the mempool/block-packing level (not because of any single-actuator logic bug, but because any node can observe a pending transaction and submit a copycat with the same `accountId` and higher energy/bandwidth priority or simply earlier broadcast/better connectivity), an attacker can copy the `accountId` bytes from the victim's pending transaction and submit their own `SetAccountIdContract` with the identical `accountId` but their own `ownerAddress`. If the attacker's transaction gets included first, `accountIdIndexStore.put()` binds the name to the attacker's address: [3](#0-2) 

The victim's original transaction then fails validation with `"This id has existed"`: [4](#0-3) 

Additionally, because each account may only call `SetAccountIdContract` successfully once (`"This account id already set"`): [5](#0-4) 

the victim is not merely delayed — they permanently lose the ability to ever claim that specific `accountId` string with a different attempt on that address (the ID stays squatted by the attacker forever, since there's no release/transfer path for `accountId`). This mirrors the Folks-Finance report exactly: a unique, user-chosen identifier is claimed via a public, unprivileged, cheap transaction that can be observed and front-run, permanently denying the intended registrant that identifier.

The attack is compounded by `calcFee()` returning `0`, meaning the attacker's front-running transaction costs nothing beyond ordinary bandwidth, just like the report's "attacker can do this repeatedly as the fee is very low": [6](#0-5) 

### Impact Explanation
This is a griefing vulnerability: no profit motive is required for the attacker, but it inflicts real, permanent damage on the targeted user, who loses forever the ability to bind their desired `accountId` to their address (accounts cannot re-attempt once `SetAccountIdContract` has been consumed, and `accountId` values are globally unique via `AccountIdIndexStore`). Any anonymous actor observing the public mempool for pending `SetAccountIdContract` transactions can carry out this griefing at essentially zero cost, repeatedly, against any target of their choosing.

### Likelihood Explanation
Likelihood is high for a determined attacker: mempool transactions (including `SetAccountIdContract`) are broadcast publicly before confirmation, `accountId` bytes are visible in plaintext in the unpacked contract, the fee is zero, and no special privilege, staking, or witness role is required — only the ability to broadcast a transaction with better propagation/priority than the victim's.

### Recommendation
- Introduce a commit-reveal scheme for `SetAccountIdContract` (commit a hash of `accountId + salt + ownerAddress`, then reveal after a delay) to prevent front-running of the plaintext identifier.
- Alternatively, bind the `accountId` claim to the account's nonce/creation transaction atomically instead of allowing it as a separate, independently front-runnable contract, or require it to be set during account activation in the same transaction that funds/creates the account.
- Consider allowing an already-set `accountId` dispute/rebind mechanism with cooldown, or requiring a stake that can be slashed for provably malicious squatting, to reduce the incentive/impact of griefing.

### Proof of Concept
1. Victim broadcasts `SetAccountIdContract{ownerAddress: victim, accountId: "myvanityid"}`.
2. Attacker observes this pending transaction in the mempool and extracts `accountId = "myvanityid"`.
3. Attacker immediately broadcasts `SetAccountIdContract{ownerAddress: attacker, accountId: "myvanityid"}` with equal or higher fee/priority so it is packed first.
4. In `SetAccountIdActuator.execute()`, `accountIdIndexStore.put()` binds `"myvanityid"` to the attacker's address [2](#0-1) .
5. Victim's transaction is then processed and `validate()` throws `"This id has existed"` [4](#0-3) , permanently denying the victim that `accountId` since a second attempt from the same address is blocked by `"This account id already set"` [5](#0-4) .
