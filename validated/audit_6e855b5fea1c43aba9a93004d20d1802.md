## Finding

### Title
Replay-verify silently accepts a wrong state-checkpoint root because `TransactionOutput::ensure_match_transaction_info` never checks the checkpoint hash fields - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-comparison routine used by replay/verification tooling to confirm that a locally re-executed transaction output matches the `TransactionInfo` recorded (and Merkle-accumulator-committed) on chain. It verifies status, gas, write-set hash, and event-root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed state root, even though these fields exist on `TransactionInfo` and are part of the value that is hashed into the transaction accumulator.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  compares only `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`. It ends with an explicit acknowledged gap: [2](#0-1) 

This comment confirms the state-integrity gap: the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", so replay-verify tooling can report success even when the authenticated state root diverges from local re-execution.

This function is consumed by the production replay/verification path in `storage/db-tool/src/replay_on_archive.rs`, where re-executed outputs are checked against expected `TransactionInfo`s pulled from a backup/archive: [3](#0-2) 

and is also used by `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` for similar auditing/debugging purposes.

Because `state_checkpoint_hash` is the Sparse-Merkle/Jellyfish state root committed at checkpoint boundaries (part of `TransactionInfo`, which is itself a leaf hashed into the transaction accumulator whose root is bound in `LedgerInfo`), skipping this comparison means the tool cannot detect a divergence between the *actual* committed state root and the root that would result from correct VM execution of the same inputs, as long as write-set/event/status/gas all happen to match. In particular, a state-checkpoint hash corruption or a discrepancy introduced by a different but write-set-equivalent execution path would go undetected by `ensure_match_transaction_info`, silently passing replay verification.

### Impact Explanation
Replay-verify / debugger-based re-execution is the mechanism operators and auditors rely on to confirm that historical (or archived) mainnet ledger state was produced correctly by the VM. If the checkpoint state root is never actually validated by this comparator, a state root that differs from the correct VM result can be accepted as "verified" by these tools, undermining the guarantee that state-commitment matches VM execution — directly matching the "Committed state that differs from the correct VM result" and "state proof accepted as valid" criteria in the State-Integrity Gate. This is a real gap in the authenticated-comparison logic, not a hypothetical: it is explicitly acknowledged by the `TODO(trading-native)` comment in the code, and the missing checks are unconditional (not behind any flag) for `state_checkpoint_hash`.

### Likelihood Explanation
The gap is unconditionally present in shipped code (no feature flag guards it) and is exercised any time replay-verify, the debugger, or CLI trace/verify commands call `ensure_match_transaction_info`. It requires no adversarial network behavior — it's a straightforward logic gap in an audit/verification utility that silently under-verifies state integrity on every invocation.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally computed state-checkpoint hash (and, once available/applicable, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against `txn_info.state_checkpoint_hash()` (and the corresponding accessors), returning an error on mismatch just as is done for `state_change_hash` and `event_root_hash`.

### Proof of Concept
Not applicable as an on-chain exploit; the issue is demonstrated purely by code inspection: `ensure_match_transaction_info` ( [4](#0-3) ) has no assertion referencing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, while `TransactionInfo` exposes these fields (see the `TransactionInfo` accumulator construction at [5](#0-4) , which does include and hash these fields when building the leaf that goes into the transaction accumulator). Any test constructing a `TransactionOutput`/`TransactionInfo` pair with identical write-set/event/status/gas but a different `state_checkpoint_hash` will pass `ensure_match_transaction_info` without error.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
