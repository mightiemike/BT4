### Title
Backup restore accepts unverified epoch-ending ledger infos for "too new" epochs, allowing state/transaction/epoch data restore to proceed without proof verification - (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
`EpochHistory::verify_ledger_info` is the function used by the transaction and state-snapshot restore controllers to validate `LedgerInfoWithSignatures` fetched from an (untrusted) backup storage source against the previously verified epoch-ending chain before accepting the associated proof (`transaction/restore.rs`, `state_snapshot/restore.rs`). When the ledger info's epoch is *greater* than the number of epoch-ending ledger infos loaded (`epoch > self.epoch_endings.len()`), the function logs a warning and returns `Ok(())` — i.e. it treats the verification as *passed* without ever validating the ledger info's signatures/validator set. [1](#0-0) 

### Finding Description
`verify_ledger_info` is called from `StateSnapshotRestoreController::run_impl` (via `self.epoch_history.as_ref().verify_ledger_info(&li)`) and from `transaction/restore.rs`'s chunk verification path to authenticate the `LedgerInfoWithSignatures` that accompanies a `TransactionInfoWithProof`/`TransactionInfoListWithProof` before that proof's root hash is trusted and applied to the restore. [2](#0-1) 

The normal verification path checks:
1. epoch 0 against the known genesis ledger info,
2. a manually-trusted waypoint if one is configured for that version, or
3. the previous epoch's `next_epoch_state().verify(...)` (the standard validator-signature chained verification). [3](#0-2) 

However, if the epoch claimed by the ledger info exceeds `self.epoch_endings.len()` (i.e., it is an epoch for which the `EpochHistoryRestoreController` has not (yet) loaded/verified an epoch-ending record), the function short-circuits and returns `Ok(())` treating it as verified, with only a warning log ("Epoch is too new and can't be verified... won't be able to start if this data is malicious"). This is exactly the same bug class as the referenced report: consuming/accepting an item associated with a future/not-yet-verified epoch marks it as "processed"/"trusted" prematurely — except here the consequence is a proof-integrity break rather than a reward-accounting break. A backup storage provider (which is explicitly an untrusted input per Aptos's own threat model for restore — that's why waypoints/epoch chains are verified at all) can supply an unsigned-by-real-validators or forged `LedgerInfoWithSignatures` for a "future" epoch that the restoring node hasn't cross-checked yet, and the restore code will accept the associated root hash/state-checkpoint hash as authentic, feeding it straight into `state_root_hash == manifest.root_hash` checks and subsequent tree/KV restoration. [4](#0-3) 

### Impact Explanation
If exploited by a compromised/malicious backup storage backend (the exact adversary model backup verification is designed to defend against), this allows corrupting a freshly-restored node's ledger/state database with data that was never actually certified by validator signatures for the given epoch, since the accompanying `LedgerInfoWithSignatures` is accepted unchecked. This directly violates the "Committed state that differs from correct result / wrong proof accepted as valid" and "restore paths must not reinterpret committed data into a different ledger state" invariants called out in the gate. Because full/archival nodes and disaster-recovery flows rely on this restore path, a successful attack could silently seed a node with an incorrect ledger state that is indistinguishable from a legitimate one to the operator (only a warning log is emitted).

### Likelihood Explanation
I could not fully confirm, within the available tool budget, whether in practice `EpochHistoryRestoreController::run_impl` (the code that populates `epoch_endings`) always loads epoch-ending manifests up to (and including) the epoch of every ledger info subsequently checked, which would make the `epoch > epoch_endings.len()` branch unreachable in normal correct operation. The code's own comment ("TODO(aldenhu): fix this from upper level" and "Epoch is too new and can't be verified") strongly suggests the Aptos developers are aware this branch is reachable under some conditions and consider it a known gap, but I was not able to fully trace `preheat_impl`/`run_impl` bodies of `EpochEndingRestoreController` (lines 74–267 were not available through the indexed tools) to determine exactly when/why this condition triggers, nor to confirm whether callers always pass consistent/complete epoch histories. This limits my confidence that this is exploitable rather than a defense-in-depth log-only branch for a state that never occurs in well-formed backups.

### Recommendation
Do not return `Ok(())` when `epoch > self.epoch_endings.len()`. Instead, either (a) fail closed by returning an error until the corresponding epoch-ending ledger info has been loaded and verified, or (b) restructure the restore pipeline so epoch-ending data is always fully loaded/verified up to the target epoch before any transaction/state-snapshot ledger info at that epoch is trusted, removing the possibility of the "too new to verify" case ever being reached without a fallback that silently succeeds.

### Proof of Concept
Not fully constructible from the indexed code alone. A conceptual PoC: an attacker in control of the backup storage endpoint (S3 bucket/GCS/etc.) crafts a `TransactionInfoWithProof`/`TransactionInfoListWithProof` file paired with a `LedgerInfoWithSignatures` claiming an epoch number higher than the epoch-ending manifests the restoring node has loaded so far (`epoch > epoch_endings.len()`), with a bogus/self-signed signature set and an attacker-chosen `transaction_accumulator_hash`/root hash. When `StateSnapshotRestoreController::run_impl` or the transaction-restore verification path calls `epoch_history.verify_ledger_info(&li)`, the check returns `Ok(())` without verifying signatures, after which `manifest.root_hash`/state data are accepted as authentic and restored into the DB.

**Caveat:** due to indexer limits I was unable to view the full body of `EpochEndingRestoreController::preheat_impl`/`run_impl` (the section populating `epoch_endings`), so I cannot definitively confirm the exact preconditions under which the vulnerable branch is reached in a production restore run. I recommend starting a full Devin session with complete repository access to trace this path end-to-end and confirm exploitability before treating this as a confirmed high/critical finding.

impl EpochHistory {
    pub fn verify_ledger_info(&self, li_with_sigs: &LedgerInfoWithSignatures) -> Result<()> {
        let epoch = li_with_sigs.ledger_info().epoch();
        ensure!(!self.epoch_endings.is_empty(), "Empty epoch history.",);
        if epoch > self.epoch_endings.len() as u64 {
            // TODO(aldenhu): fix this from upper level
            warn!(
                epoch = epoch,
                epoch_history_until = self.epoch_endings.len(),
                "Epoch is too new and can't be verified. Previous chunks are verified and node \
                won't be able to start if this data is malicious."
            );
            return Ok(());
        }
