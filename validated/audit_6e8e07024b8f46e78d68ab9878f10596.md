### Title
Hardcoded, immutable address-registrar account ID in the ETH-Wallet global contract can permanently break ETH-implicit account transfers - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract`, which is deployed as a single shared global contract to **every** ETH-implicit account on the network, references the account ID of its companion "address registrar" contract not as a configurable/settable value, but as a compile-time constant baked into the WASM binary via `include_str!`.

### Finding Description
The wallet contract hardcodes the address registrar's account id as a compiled-in string constant: [1](#0-0) 
The literal value shipped in the repository is `address-map.near`: [2](#0-1) 

This constant is parsed and used to construct a cross-contract call every time an EOA-style base-token transfer needs an address-to-account lookup: [3](#0-2) 

Unlike the Aave incentives controller in the external report — which is at least an `immutable` set once per lending-pool deployment — this NEAR analog is worse: the address is a **build-time literal string** shared by one single global contract deployment (`AccountContract::Global(global_contract_hash)`) that every ETH-implicit account on the chain points to: [4](#0-3) [5](#0-4) 

Because the value is compiled into the contract's WASM bytes rather than stored as mutable contract state, there is no owner/admin function in `WalletContract` to update it if the registrar contract is ever redeployed, migrated to a new account, or upgraded to a different address — exactly the "lending pool changes the incentives address via governance" scenario in the original report, but transposed to "the address-map/registrar operator has to redeploy or move accounts". The only way to fix a stale registrar reference is to publish an entirely new global contract WASM with the corrected string and get every network participant onto new code, since the constant cannot be patched per-account.

### Impact Explanation
Any unprivileged caller submitting an `EOABaseTokenTransfer { address_check: Some(address), .. }` RLP-encoded Ethereum-style transaction to any ETH-implicit account will have the wallet contract schedule a cross-contract `lookup` call to whatever account is baked into `ADDRESS_REGISTRAR_ACCOUNT_ID`: [6](#0-5) 
If the real registrar has moved to a new account id (e.g. re-deployment, key rotation to a new namespace, or a NEP upgrade), this call fails or returns wrong data for the life of that global contract's deployment. Since a huge (potentially unbounded) set of accounts share the same global contract, this can permanently break the address-check path for every ETH-implicit account network-wide, until governance ships and every validator applies a new global contract WASM. Funds deposited toward an unregistered/incorrectly-resolved counter-party can also get mis-routed or refunded unpredictably depending on how the callback handles the registrar's failure.

### Likelihood Explanation
This is only triggered by normal transaction flow — no privileged or malicious actor is required. The precondition is entirely operational: the real `eth-address-registrar` account changes address after the wallet contract's global code has already been deployed and adopted network-wide. Given that the registrar id is embedded as a literal string in a globally-shared contract binary rather than mutable state, any future migration of the registrar account (routine key/account management, disaster recovery, or a NEP-driven redesign) would trigger this class of failure for the entire fleet of ETH-implicit accounts simultaneously.

### Recommendation
Store the address registrar's account id as mutable contract state (e.g., initialized via `#[init]` and updatable through a privileged/governance-gated method, or supplied per-call/queried dynamically), instead of hardcoding it into the compiled WASM via `include_str!`. This allows the registrar to be migrated without requiring a full re-deploy-and-adopt cycle of the shared global wallet contract across every ETH-implicit account.

### Proof of Concept
1. Deploy the `near-wallet-contract` WASM as the global contract used by `EthImplicitGlobalContract` (as done in `test_eth_implicit_accounts`): [7](#0-6) 
2. Note the address registrar id baked into the WASM at build time is fixed at `runtime/near-wallet-contract/implementation/wallet-contract/src/ADDRESS_REGISTRAR_ACCOUNT_ID`.
3. Redeploy/migrate the real address-registrar contract to a different account id (simulating an operational migration), without redeploying the wallet contract's global code.
4. Submit an unprivileged `rlp_execute` transaction encoding `EOABaseTokenTransfer { address_check: Some(address), .. }` from any ETH-implicit account.
5. Observe the wallet contract's cross-contract `lookup` call targets the stale (now-incorrect) registrar account id, causing the address-check flow to fail or resolve incorrectly for every ETH-implicit account sharing that global contract, with no on-chain mechanism to correct it short of shipping new global contract code.
