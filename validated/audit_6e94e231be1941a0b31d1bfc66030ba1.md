### Title
Lite-node history-query restriction bypass via gRPC `GetTransactionInfoByBlockNum` — ([File: framework/src/main/java/org/tron/core/services/filter/LiteFnQueryGrpcInterceptor.java])

### Summary
`LiteFnQueryHttpFilter` blocks `/wallet/gettransactioninfobyblocknum` and `/walletsolidity/gettransactioninfobyblocknum` on lite fullnodes, but `LiteFnQueryGrpcInterceptor.filterMethods` never lists `protocol.Wallet/GetTransactionInfoByBlockNum` (nor a WalletSolidity equivalent). The underlying handler is implemented as a real gRPC method in `RpcApiService`, so an unprivileged gRPC client can call it directly on a lite fullnode and force full historical iteration that the HTTP transport correctly blocks.

### Finding Description
`LiteFnQueryHttpFilter` maintains `filterPaths` [1](#0-0)  including `/wallet/gettransactioninfobyblocknum` and `/walletsolidity/gettransactioninfobyblocknum`, and enforces the lite-node block only for requests whose path is in this set [2](#0-1) .

`LiteFnQueryGrpcInterceptor.filterMethods`, which is supposed to mirror the same restriction policy for gRPC, is missing `protocol.Wallet/GetTransactionInfoByBlockNum` and any `protocol.WalletSolidity/GetTransactionInfoByBlockNum` entry entirely [3](#0-2) . The interceptor only blocks calls whose full method name is in this incomplete set [4](#0-3) .

The HTTP servlet `GetTransactionInfoByBlockNumServlet` calls `wallet.getTransactionInfoByBlockNum(num)` [5](#0-4) , and the same underlying `Wallet` method is exposed as a gRPC RPC in `RpcApiService`, confirmed by matches for `GetTransactionInfoByBlockNum` in `framework/src/main/java/org/tron/core/services/RpcApiService.java`. Because this gRPC method name is absent from `filterMethods`, an attacker's gRPC call bypasses the lite-node guard and reaches `Wallet.getTransactionInfoByBlockNum`, which iterates over all transactions of the requested block and performs per-transaction index/history lookups that a lite fullnode (`openHistoryQueryWhenLiteFN=false`) is not provisioned to serve efficiently — the exact case the filter set exists to prevent.

By contrast, `GetTransactionReceiptById` (HTTP-only path `/wallet/gettransactionreceiptbyid`) internally reuses `wallet.getTransactionInfoById(...)`, whose gRPC equivalent `protocol.Wallet/GetTransactionInfoById` is present in `filterMethods`, so that particular HTTP-only alias does not constitute an independent bypass — it does not need its own gRPC filter entry because no separate unguarded gRPC surface exists for it.

### Impact Explanation
An anonymous gRPC client (no signed transaction, no privileged role required) can repeatedly invoke `protocol.Wallet/GetTransactionInfoByBlockNum` (and its WalletSolidity counterpart, if similarly exposed) against a lite fullnode configured with `openHistoryQueryWhenLiteFN=false`, forcing repeated full-block transaction-info iteration and index lookups the operator explicitly intended to disable. This matches the "DoS via RPC-API" bounty class: sustained calls can exhaust CPU/I-O resources and degrade RPC-API availability for legitimate users on that node, and repeated invalid/failed lookups can generate exception storms in node logs.

### Likelihood Explanation
Precondition is simply operating (or targeting) a lite fullnode with default lite-node history restriction enabled and gRPC access exposed — a common, non-exotic deployment. The attacker needs no special privileges, keys, or funds; a bare gRPC client call suffices, and it is trivially repeatable at will, making this a low-cost, high-repeatability availability issue against any lite fullnode exposing gRPC.

### Recommendation
Keep `filterPaths` and `filterMethods` programmatically derived from a single source of truth (e.g., a shared list of blocked API names with a per-transport mapping to HTTP path and gRPC full method name), and add a build-time/unit test that asserts one-to-one coverage between the two sets. As an immediate fix, add `"protocol.Wallet/GetTransactionInfoByBlockNum"` and the corresponding `WalletSolidity` full method name to `LiteFnQueryGrpcInterceptor.filterMethods`.

### Proof of Concept
```java
// JUnit: prove filterMethods is missing an entry that filterPaths has
@Test
public void testLiteFnFilterCoverageGap() {
  Set<String> httpPaths = LiteFnQueryHttpFilter.getFilterPaths();
  Set<String> grpcMethods = LiteFnQueryGrpcInterceptor.getFilterMethods();

  assertTrue(httpPaths.contains("/wallet/gettransactioninfobyblocknum"));
  // Fails today: no matching entry in filterMethods
  assertFalse(grpcMethods.contains("protocol.Wallet/GetTransactionInfoByBlockNum"));
}
```
Request-level PoC on a running lite fullnode (openHistoryQueryWhenLiteFN=false):
1. HTTP: `POST /wallet/gettransactioninfobyblocknum {"num": 1000}` → returns `"this API is closed because this node is a lite fullnode"` (blocked as expected).
2. gRPC: call `Wallet.GetTransactionInfoByBlockNum(NumberMessage{num=1000})` via any gRPC client → call succeeds and returns full `TransactionInfoList`, proving the restriction is bypassed on the gRPC transport.
