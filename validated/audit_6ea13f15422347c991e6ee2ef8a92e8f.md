### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting a divergent state root pass replay/authenticated verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` verifies status, gas, write-set hash, and event root hash against a `TransactionInfo`, but does not compare `state_checkpoint_hash()` / `position_state_checkpoint_hash()`. This function is the sole match check used by `db-tool replay_on_archive` and the chunk executor's `verify_execution` path, so a locally-computed state (or hot-state / position-state) root that diverges from the authenticated `TransactionInfo` in the accumulator is never detected by this check.

### Finding Description
`ensure_match_transaction_info` ( [1](#0-0) ) checks four things — execution status, gas used, write-set hash (`state_change_hash`), and event root hash — but the function's own trailing comment documents that it intentionally omits comparing the state checkpoint hash and `position_state_checkpoint_hash` carried in `TransactionInfo` against the locally computed values: [2](#0-1) 

This function is called from two integrity-sensitive call sites that are supposed to catch state divergence between VM execution and the authenticated ledger record:
- `storage/db-tool/src/replay_on_archive.rs`, where `executed_outputs[idx].ensure_match_transaction_info(...)` is the terminal correctness check of the replay-verify tool [3](#0-2) .
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`, which re-executes a chunk and calls `ensure_match_transaction_info` per transaction to validate state-sync-received data before treating it as verified [4](#0-3) .

Because the state checkpoint / position checkpoint comparison is absent, if the locally re-executed state root (main state or the "trading-native" position state) differs from what is committed in the persisted `TransactionInfo`, neither `replay_on_archive` nor chunk-executor's `verify_execution` will flag it — the function returns `Ok(())` regardless.

### Impact Explanation
This is a proof/authenticity binding gap: the `TransactionInfo`'s `state_checkpoint_hash` is exactly the root that downstream Merkle-proof verification (`SparseMerkleProof::verify`, state-restore, and other proof consumers) trusts as authoritative. `ensure_match_transaction_info` is the mechanism meant to independently confirm that this trusted root actually matches VM re-execution. Skipping it means a state root corruption (introduced anywhere between VM output and committed `TransactionInfo` — e.g. a bug in `do_state_checkpoint`/JMT materialization, or a maliciously altered archive/backup) can pass both the offline replay-verify tool and the chunk-executor's execution-verification path undetected. Any client relying on `replay_on_archive` or chunk-executor verification for the guarantee "the committed ledger state matches independent re-execution" gets a false positive on exactly the invariant that gate is asking us to protect (committed state that differs from correct VM result, silently accepted). This satisfies the "Wrong ... state proof accepted as valid" and "hard-fork-only divergence during commit/replay" criteria in the gate.

### Likelihood Explanation
This is gated: the comment states the checkpoint-hash validation must be added "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the feature (and by extension the reliance on this comparator for position/trading-native state) is not yet fully active in production, which lowers immediate exploitability. However, the gap in `ensure_match_transaction_info` is unconditional and always compiled in — it silently omits verification of the main `state_checkpoint_hash` too, not just the position-state one, for every caller regardless of feature flags. I was not able to fully verify from local code whether some other independent path (outside this function) revalidates the main state_checkpoint_hash during `replay_on_archive`'s or chunk-executor's verification flow; if no such secondary check exists, the main-state gap is live today, not merely gated by the future feature.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally computed state checkpoint hash (and, when applicable, `position_state_checkpoint_hash`) against `txn_info.state_checkpoint_hash()` / `txn_info.position_state_checkpoint_hash()`, returning an error on mismatch, before any code path relies on this function as an authoritative "output matches ledger record" check.

### Proof of Concept
Not applicable as a runnable exploit — this is a code-inspection finding based on the function's documented omission and its two real call sites (`replay_on_archive.rs`, `chunk_executor/mod.rs::verify_execution`), both of which only call `ensure_match_transaction_info` and would treat a checkpoint-hash mismatch as a passing verification.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
