### Title
Mutable `AccountId`-mode global contracts let a contract owner silently backdoor every account that references them - ([File: runtime/runtime/src/contract_code.rs])

### Summary
`DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` publishes a "global contract" that is looked up by the *deploying account's id* rather than by code hash. Any account that later opts in via `UseGlobalContractAction` (`GlobalContractIdentifier::AccountId(owner)`) or `DeterministicStateInitAction` binds its execution to whatever code currently lives under that owner's identifier. Because code resolution (`RuntimeContractIdentifier::resolve` / `GlobalContractAccessExt::hash`/`code`) always re-reads the current trie value for `TrieKey::GlobalContractCode { identifier: AccountId(owner) }` at call time, the owner can redeploy a new `DeployGlobalContractAction` (same `AccountId` mode) at any later block and instantly change the code executed on behalf of every referencing account, with no consent, notification, or re-approval from those accounts. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`GlobalContractDeployMode::AccountId` is explicitly documented as mutable: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users." [4](#0-3) 

`action_deploy_global_contract` → `initiate_distribution` computes the storage key purely from the mode: for `AccountId` mode the identifier is always `GlobalContractIdentifier::AccountId(account_id)`, independent of the code being deployed, and the distribution receipt simply overwrites `TrieKey::GlobalContractCode` for that identifier once the nonce check passes. [5](#0-4) 

Any account that has previously called `UseGlobalContract` with `GlobalContractIdentifier::AccountId(owner)` (or created a `DeterministicStateInitAction`/`sub-account` state whose `code` field is that same identifier) stores only `AccountContract::GlobalByAccount(owner)` — a reference, not a snapshot. Every subsequent `FunctionCall` resolves the *current* code for that identifier via `RuntimeContractIdentifier::resolve`, which calls `GlobalContractIdentifier::hash`/`code`, both of which look up the live trie value rather than any value pinned at `UseGlobalContract` time. [6](#0-5) [3](#0-2) 

Tests in the repo confirm this exact update-in-place behavior: `test_global_contract_update` shows that once accounts reference an `AccountId`-mode contract, a fresh `DeployGlobalContract` from the owner immediately changes what those referencing accounts execute, without those accounts taking any new action. [7](#0-6) 

This is structurally the same bug class as the reported "governance can backdoor new Safes via malicious upgrade" issue: a party controlling a mutable "singleton"/shared implementation (there: `AddressProvider`-governed Safe singleton/factory; here: the `AccountId`-keyed global contract) can publish benign code first, get users/accounts to bind to it, and later swap in malicious code that silently takes effect for all bound accounts — including the "sandwich" obfuscation pattern the original report warns about (deploy malicious code, let a victim's `UseGlobalContract`/`DeterministicStateInit` execute against it in a later block, then redeploy the benign code again), since queries of "what code do I use" only reveal the identifier, not the (mutable) code behind it.

### Impact Explanation
Any account bound to an `AccountId`-mode global contract (via `UseGlobalContract`, `DeterministicStateInitAction`, or as the deterministic/ETH-implicit wallet code target) executes fully-privileged WASM code on behalf of that account (its balance, storage, and any keys/permissions it holds) whose content is entirely at the discretion of a third-party owner account, at any point in time, without any interaction from the bound account. A malicious or compromised owner account can therefore drain balances, corrupt state, or otherwise act as an unauthorized executor for every account referencing it — i.e., concrete unauthorized value movement — reachable purely through ordinary transactions (`DeployGlobalContract`, `UseGlobalContract`, `DeterministicStateInit`) sent by unprivileged signers.

### Likelihood Explanation
Likelihood is low-to-medium: the mutability is an intentional, documented protocol feature (not a bug in the state-transition logic itself), and any account choosing to reference a contract "by AccountId" is implicitly trusting the owner to keep the deployed code benign — analogous to the audited report where governance's control was "acknowledged, within the trust scope." However, unlike governance (a protocol-level, semi-trusted role), the "owner" here is an ordinary, unprivileged account that anyone can control, and nothing in the protocol prevents a bait-and-switch: deploy trusted-looking code, wait for adoption via `UseGlobalContract`/`DeterministicStateInit`, then redeploy malicious code. There is no timelock, freeze, or hash-pinning mechanism for `AccountId`-mode contracts, so exploitation requires only ordinary signed transactions.

### Recommendation
- Encourage/require consumers that need security guarantees to use `GlobalContractDeployMode::CodeHash` (immutable) rather than `AccountId` mode, and make this trade-off explicit wherever `UseGlobalContract`/`DeterministicStateInit` accept a `GlobalContractIdentifier::AccountId`.
- Consider adding an opt-in "pin to code hash at time of use" mode for `UseGlobalContractAction`/`DeterministicStateInitAction` so that binding to a mutable identifier still commits to specific code unless the referencing account explicitly opts into "always track latest," decoupling delegated trust from silent mutability.
- Surface the current code hash behind an `AccountId` identifier prominently in RPC/view responses so wallets and auditors can detect changes, and consider a mandatory delay/notification window between a `DeployGlobalContract` (AccountId mode) redeploy and it taking effect for already-bound accounts, mirroring the "sandwich attack" mitigation the original report recommends (avoid instantaneous, unannounced swaps of code trusted by dependents).

### Proof of Concept
1. Attacker account `owner.near` calls `DeployGlobalContractAction{ code: benign_code, deploy_mode: AccountId }`. Code is distributed and stored at `TrieKey::GlobalContractCode{ identifier: AccountId(owner.near) }`. [8](#0-7) 
2. Victim account `victim.near` calls `UseGlobalContractAction{ contract_identifier: GlobalContractIdentifier::AccountId(owner.near) }`. `victim.near`'s `AccountContract` is set to `GlobalByAccount(owner.near)` — a live reference, not a hash pin. [9](#0-8) 
3. `victim.near` operates normally for some time; every `FunctionCall` to it resolves code via `RuntimeContractIdentifier::resolve` → `GlobalContractIdentifier::code`/`hash`, which fetches whatever is currently at that trie key. [6](#0-5) 
4. `owner.near` submits a new `DeployGlobalContractAction{ code: malicious_code, deploy_mode: AccountId }`. Once the higher-nonce distribution receipt lands on `victim.near`'s shard, the stored code for identifier `AccountId(owner.near)` is overwritten in place. [5](#0-4) 
5. The very next `FunctionCall` to `victim.near` executes `malicious_code` with full access to `victim.near`'s balance/state, with `victim.near` never having signed any new transaction — demonstrated by the existing test harness pattern in `test_global_contract_update`, which shows the same redeploy-then-call sequence changing the executed code for already-bound accounts. [7](#0-6)

    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }

    fn code(self, store: &TrieUpdate) -> Result<Option<ContractCode>, StorageError> {
        let key = TrieKey::GlobalContractCode { identifier: self.clone().into() };
        let code_hash = match self {
            GlobalContractIdentifier::AccountId(_) => None,
            GlobalContractIdentifier::CodeHash(hash) => Some(hash),
        };
        let code = store.get(&key, AccessOptions::DEFAULT)?;
        Ok(code.map(|code| ContractCode::new(code, code_hash)))
    }

fn test_global_contract_update() {
    let mut env = GlobalContractsTestEnv::setup(Balance::from_near(1000));
    let use_accounts = [env.account_shard_0.clone(), env.account_shard_1.clone()];

    env.deploy_trivial_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        env.use_global_contract(
            account,
            GlobalContractIdentifier::AccountId(env.deploy_account.clone()),
        );

        // Currently deployed trivial contract doesn't have any methods,
        // so we expect any function call to fail with MethodNotFound error
        let call_tx = env.call_global_contract_tx(account.clone(), account.clone());
        let call_outcome = env.execute_tx(call_tx);
        assert_matches!(
            call_outcome.status,
            FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
                kind: ActionErrorKind::FunctionCallError(FunctionCallError::MethodResolveError(
                    MethodResolveError::MethodNotFound
                )),
                index: _
            }))
        );
    }

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        // Function call should be successful after deploying rs contract
        // containing the function we call here
        env.assert_call_global_contract_success(account.clone(), account.clone());
    }
}
