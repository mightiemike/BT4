### Title
Protocol-relative URL bypasses `isSafe()` origin check in `sanitizeRedirectUrl`, allowing open redirect to attacker-controlled host - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts])

### Summary
`isSafe()` in `validate-redirect-url.ts` only blocks 3+ consecutive slashes (`FILE_URI_MATCH = /\/\/\//`) and checks `INVALID_RELATIVE_URL` against `url.pathname` only, never against the resolved `url.host`. A protocol-relative input such as `//attacker.com` has exactly two slashes, so it passes both regex checks, and `new URL('//attacker.com', domain)` resolves per WHATWG URL rules to `https://attacker.com/`, replacing the intended app host while keeping the base scheme. The function then reports the URL as "safe" even though its origin is entirely attacker-controlled.

### Finding Description
`isSafe()` runs three checks before accepting a redirect target: `FILE_URI_MATCH` (blocks `///`), `WHITESPACE_CHARACTER`, and after parsing with `new URL(redirectUrl, domain)`, `INVALID_RELATIVE_URL` against `url.pathname`, plus a protocol allow-list (`http:`/`https:`). [1](#0-0) 

None of these checks constrain `url.host`/`url.origin` to match `domain`. For input `redirectUrl = '//attacker.com'`:
- `FILE_URI_MATCH.test('//attacker.com')` is `false` (only 2 slashes).
- `WHITESPACE_CHARACTER.test(...)` is `false`.
- `new URL('//attacker.com', 'https://my-app.com')` evaluates, per the WHATWG URL spec, to `https://attacker.com/` (protocol-relative resolution replaces the authority component but inherits the base scheme).
- `INVALID_RELATIVE_URL.test(url.pathname)` checks `'/'`, which does not match `/[/\\][/\\]/`.
- `url.protocol` is `'https:'`, which is in `VALID_PROTOCOLS`, and satisfies `requireSSL`.

So `isSafe` returns `true`, and `sanitizeRedirectUrl` returns `new URL('//attacker.com', domain)`, whose host is `attacker.com`, not the app's own domain — defeating the stated purpose of the function (`throw new ShopifyError('Invalid URL. Refusing to redirect')` is meant to guard against exactly this). [2](#0-1) 

This function is the security boundary used by `renderAppBridge` to decide the destination injected into an embedded admin `window.open(...)` script, and by `redirectFactory`/`redirect()` for OAuth-related and app-navigation redirects. [3](#0-2) [4](#0-3) 

I was not able to fully confirm, within the available exploration, a route in this library where an unprivileged, un-authenticated caller directly supplies a raw `redirect`-style query parameter that flows into `sanitizeRedirectUrl` without any app-developer code choosing/constructing the URL string first (e.g., `redirect(url)` in `redirect.ts` is invoked by host application loader/action code with a URL string the developer supplies, not automatically bound to a request query parameter). This makes the full end-to-end attacker reachability dependent on how a specific host app wires user input into the exported `redirect()`/`sanitizeRedirectUrl()` API. The underlying validation logic flaw itself, however, is confirmed and reproducible independent of caller.

### Impact Explanation
If any code path (in this library's OAuth/App Bridge flow or in a consuming app) passes a request-influenced value into `sanitizeRedirectUrl`, an attacker can force the returned URL's origin to be `attacker.com` instead of the app's own domain. Since these helpers are used to construct `window.open(...)` targets and redirect responses during the embedded/OAuth flow, this can send an authenticated admin browser to an attacker-controlled origin — a classic open-redirect primitive that can be leveraged for phishing, App Bridge/session-token exfiltration via a lookalike page, or OAuth flow hijacking, matching Shopify's "Open Redirect with real consequence" bounty class.

### Likelihood Explanation
The bypass itself requires no privilege — any value string reaching `sanitizeRedirectUrl` (`//attacker.com`, or variants) triggers it deterministically; this is 100% reproducible via unit test. The remaining uncertainty is purely whether a given deployment/library code path feeds unprivileged attacker input into this function without host-app validation of its own; I could not fully verify a built-in, always-present request-to-`sanitizeRedirectUrl` path in the reviewed files within the exploration budget.

### Recommendation
Fix `isSafe()` to compare the resolved URL's origin/host against the trusted `domain`'s origin/host, not just its `pathname`/protocol, e.g.:
```ts
const base = new URL(domain);
if (url.host !== base.host) return false;
```
Additionally, reject any redirect string that begins with `//` (or `\\`, or mixed-case scheme variants like `HTTPS:`) before calling `new URL(redirectUrl, domain)`, since protocol-relative/backslash inputs are never valid same-app relative paths.

const FILE_URI_MATCH = /\/\/\//;
const INVALID_RELATIVE_URL = /[/\\][/\\]/;
const WHITESPACE_CHARACTER = /\s/;
const VALID_PROTOCOLS = ['https:', 'http:'];

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}

export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}

export function redirectFactory(
  params: BasicParams,
  request: Request,
  shop: string,
): RedirectFunction {
  const {config, logger} = params;

  return function redirect(url, init: RedirectInit) {
    const {searchParams} = new URL(request.url);
    const {url: parsedUrl, target} = parseURL({
      params,
      url,
      base: config.appUrl,
      shop,
      init,
    });

    logger.debug('Redirecting', {shop, url: parsedUrl.toString()});

    const isSameOrigin = parsedUrl.origin === new URL(config.appUrl).origin;
    if (isSameOrigin) {
      searchParams.forEach((value, key) => {
        if (!parsedUrl.searchParams.has(key)) {
          parsedUrl.searchParams.set(key, value);
        }
      });
    }

    if (target === '_self') {
      if (isBounceRequest(request)) {
        throw renderAppBridge(params, request, {
          url: parsedUrl.toString(),
          target,
        });
      } else {
        return remixRedirect(parsedUrl.toString(), init);
      }
    } else if (isDataRequest(request)) {
      throw redirectWithAppBridgeHeaders(parsedUrl.toString());
    } else if (isEmbeddedRequest(request)) {
      throw renderAppBridge(params, request, {
        url: parsedUrl.toString(),
        target,
      });
    }
    return remixRedirect(url, init);
  };
}
