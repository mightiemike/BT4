### Title
Withdrawal health-check values zToken collateral via oracle liquidity-index price while actual redemption pays out via vault share-ratio, letting the two diverge within one transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`collateral-remove-redeem` gates a withdrawal's health check using a zToken "price" derived from the market's cached liquidity index (`lindex`), then in the very same call redeems the zToken through the vault's own `redeem` function, which computes the payout from a completely different internal ratio (`total-assets-preview()/total-supply-preview()`, driven by the borrow index and accrued debt/reserve accounting). These two valuations of "1 zToken" are not the same number and are not reconciled, so the amount of collateral value the health check assumed the user removed is not the amount of underlying value the user actually receives.

### Finding Description
`collateral-remove-redeem` is a two-step, single-transaction entry point:

1. `collateral-remove` validates the withdrawal is safe using `get-notional-evaluation`/`find-and-resolve-asset-value`, which price zTokens through `price-resolve` → `resolve-callcode` → `resolve-ztoken`: [1](#0-0) 
This multiplies the underlying oracle price by the cached `lindex` (liquidity index) pulled from `index-cache`, which was populated earlier in the same call via `accrue-and-cache`/`accrue-user-collateral`: [2](#0-1) [3](#0-2) 

2. Immediately after `collateral-remove` succeeds, the same function calls `vault-redeem`, which forwards to the vault's own `redeem`: [4](#0-3) 
Inside the vault, `redeem` computes the actual payout with `convert-to-assets-preview`, which is driven by `total-assets-preview()`/`total-supply-preview()` — a ratio computed from the vault's borrow index and accrued interest/reserve mechanics, not from `lindex`: [5](#0-4) [6](#0-5) 

So within one atomic transaction, the health-check step bound the value of the zToken being removed to `underlying_price * lindex / PRECISION` (a value read from a market-level cache), while the actual token transfer step pays out `amount * total_assets_preview / total_supply_preview` (a value computed independently inside the vault contract). Nothing in `collateral-remove-redeem` reconciles these two numbers or re-checks health against the true redemption amount. The "price paid" (i.e., the valuation used to authorize/limit the withdrawal) is not the "price" actually realized at settlement — the same root-cause shape as the referenced Unlock finding, where a refund used a differently-sourced current price instead of the price that was actually used/paid.

### Impact Explanation
If `lindex` and the vault's `total-assets/total-supply` ratio drift apart (e.g., due to reserve-factor treasury minting, socialized bad debt write-downs that only update `lindex`/`index` in the market's cache path, or accrual timing differences between the two computations), a user's withdrawal can be authorized by the health check using one valuation of their zToken collateral but be executed for a materially different amount of underlying assets. This can let a borrower strand more collateral value than the health check accounted for (freezing funds relative to what should have been withdrawable) or, in the reverse direction, let a user extract more underlying value than their post-withdrawal health check assumed remained backing their debt, weakening solvency guarantees for the vault. This lands on temporary freezing of user funds / degradation of the collateral-accounting invariant that liquidation and health checks depend on.

### Likelihood Explanation
This triggers on every `collateral-remove-redeem` call for any zToken collateral whenever the market's `lindex`-based zToken price and the vault's own share-conversion ratio are not exactly equal, which is plausible any time the two accounting paths (market-level oracle callcode using `lindex`, versus vault-level `total-assets-preview`/`total-supply-preview` using the borrow index and reserve mints) advance independently — no privileged action or external oracle manipulation is required, only ordinary vault operation.

### Recommendation
Make `collateral-remove-redeem` use one authoritative valuation for both the health check and the payout: either (a) compute the health check using the vault's own `convert-to-assets-preview` ratio for the zToken (so the checked value equals the actual redeemable value), or (b) after `vault-redeem` returns the actual underlying amount, re-run/verify the health check against that realized amount instead of the pre-computed oracle-based notional value.

### Proof of Concept
1. User calls `collateral-remove-redeem` for a zToken (e.g., zUSDC) as their sole/primary collateral, with `amount` sized so the health check in `collateral-remove` barely passes using the `lindex`-derived valuation (`mainnet/contracts/market/v0-4-market.clar:1211-1234`, `343-347`).
2. `collateral-remove` succeeds because `get-notional-evaluation` values the removed zUSDC at `usdc_price * lindex / PRECISION` (cached value from `accrue-and-cache`).
3. In the same transaction, `vault-redeem` is invoked, calling `v0-vault-usdc`'s `redeem`, which computes `inkind = convert-to-assets-preview(amount)` using `total-assets-preview()/total-supply-preview()` (`mainnet/contracts/vault/v0-vault-sbtc.clar:306-344, 799-833`), a ratio independently derived from the borrow index/interest/reserve mint accounting rather than `lindex`.
4. Because the two ratios are computed from different state (`lindex` vs. `total-assets/total-supply`), the underlying amount actually sent to the user differs from the amount the health check assumed was removed, without any re-validation of health against the real payout — the position's health status printed/relied upon in step 2 no longer matches the true post-withdrawal state.

(define-public (collateral-remove-redeem (ft <ft-trait>) (amount uint) (min-underlying uint) (receiver (optional principal)) (price-feeds (optional (list 3 (buff 8192)))))
  (let ((ft-address (contract-of ft))
        (asset (try! (get-asset ft-address)))
        (ztoken-id (get id asset))
        (underlying-id (if (is-eq ztoken-id zSTX) STX
                       (if (is-eq ztoken-id zsBTC) sBTC
                       (if (is-eq ztoken-id zstSTX) stSTX
                       (if (is-eq ztoken-id zUSDC) USDC
                       (if (is-eq ztoken-id zUSDH) USDH
                       (if (is-eq ztoken-id zstSTXbtc) stSTXbtc
                       u100)))))))  ;; invalid sentinel for non-ztoken
        (funds-receiver (match receiver recv recv contract-caller)))

    (asserts! (<= underlying-id stSTXbtc) ERR-UNKNOWN-VAULT)
    
    ;; Step 1: Remove collateral - sends zTokens to THIS contract (market)
    ;; receiver=current-contract so market holds the zTokens
    (try! (collateral-remove ft amount (some current-contract) price-feeds))
    
    ;; Step 2: Redeem zTokens for underlying
    ;; vault-redeem calls vault.redeem which burns shares from contract-caller (market)
    ;; Since market now holds the zTokens, this succeeds
    ;; Underlying tokens are sent to the specified receiver
    (vault-redeem underlying-id amount min-underlying funds-receiver)))
