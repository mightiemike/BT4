### Title
Premature/reversed division-before-multiplication in reward payout math causes systematic reward underpayment/rounding loss - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The reported bug class is: a reward calculation performs division before the final multiplication, truncating intermediate fractional values and causing systematically reduced payouts. The same bug class is reachable in java-tron in the block-reward/vote-reward distribution logic in `MortgageService`, where several reward computations divide first (using `double`, which itself is imprecise) and then multiply, instead of multiplying first and dividing once at the end with exact integer/BigInteger arithmetic.

### Finding Description
Three code paths in `MortgageService` compute a payout by dividing before multiplying:

1. `payStandbyWitness()` computes `eachVotePay = (double) totalPay / voteSum` first, then multiplies per witness: `pay = (long) (w.getVoteCount() * eachVotePay)`. [1](#0-0) 

2. `payReward()` computes `brokerageRate = (double) brokerage / 100` first, then multiplies: `brokerageAmount = (long) (brokerageRate * value)`. [2](#0-1) 

3. The legacy per-cycle reward algorithm `computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes `voteRate = (double) userVote / totalVote` first, then multiplies by `totalReward`: `reward += voteRate * totalReward`. [3](#0-2) 

This is the exact bug class described in the report: dividing (`X/Y`) before multiplying by a third factor truncates fractional value before the final scaling multiplication is applied, amplifying rounding error compared to computing `(A * B) / C` in one step. All three cases additionally use IEEE-754 `double` instead of exact integer/`BigInteger` math, which is strictly worse than the Solidity example (which at least used exact integer division), compounding the precision loss with floating-point rounding error.

By contrast, the *new* reward algorithm in the same class and in `VoteRewardUtil` correctly multiplies first, then divides once using `BigInteger`: [4](#0-3) 
This shows the codebase authors already recognize and fixed this exact pattern for the delta-Vi reward path, but the legacy code path (`computeReward(cycle, votes)`, used for `beginCycle < newAlgorithmCycle`) and the standby-witness/brokerage payment paths in `payStandbyWitness`/`payReward` still use the vulnerable pattern.

`computeReward(beginCycle, endCycle, accountCapsule)` — which internally calls the legacy `getOldReward`/`computeReward(cycle, votes)` for cycles prior to `newAlgorithmCycle` — is invoked from `MortgageService.withdrawReward(address)` and `queryReward(address)`, which are called by `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `VoteWitnessActuator` — all reachable via ordinary broadcast transactions from any account. [5](#0-4) 

`payStandbyWitness()` and `payReward()` are invoked as part of consensus block production/maintenance (not directly by a user transaction), so those two specifically are protocol-internal reward-accounting logic rather than user-triggered, but they still directly determine on-chain balances credited to witness accounts every block/maintenance cycle.

### Impact Explanation
Underpayment of standby-witness rewards, brokerage commissions, and legacy-cycle voter rewards reduces the amounts credited to witness and voter accounts network-wide. Because `double` division/multiplication is used (rather than integer/BigInteger), the error is not a bounded one-unit truncation as in the Solidity report, but a floating-point rounding error whose magnitude depends on operand size — over many witnesses/cycles/blocks this compounds into a nontrivial, systematic loss of TRX that should have been distributed to witnesses and voters. This is a resource/reward-accounting correctness issue affecting protocol-level economic accuracy, not a memory-safety or authentication issue.

### Likelihood Explanation
`payReward` and `payStandbyWitness` execute on every block/maintenance cycle unconditionally as part of consensus reward distribution, so the underpayment occurs continuously and automatically without any special attacker action — it is a deterministic, always-triggered miscalculation rather than an exploit requiring adversarial input. The legacy `computeReward(cycle, votes)` path is only exercised for cycles before `newAlgorithmCycle` (i.e., historical/pre-upgrade cycles), so its practical exposure on current networks is lower but still present for withdrawal/query of rewards spanning that period.

### Recommendation
Replace the divide-then-multiply `double` arithmetic with multiply-then-divide integer/BigInteger arithmetic, mirroring the fix already applied to the delta-Vi reward path:

- In `payStandbyWitness`, compute `pay = totalPay * w.getVoteCount() / voteSum` using `long`/`BigInteger` (with overflow-safe multiplication, e.g. `Math.multiplyHigh`/`BigInteger`) instead of `eachVotePay = totalPay / voteSum` followed by multiplication.
- In `payReward`, compute `brokerageAmount = value * brokerage / 100` using integer arithmetic instead of `brokerageRate = brokerage/100.0` followed by multiplication.
- In the legacy `computeReward(cycle, votes)`, compute `reward += userVote * totalReward / totalVote` using `BigInteger` (to avoid overflow) instead of computing `voteRate` as a `double` first.

### Proof of Concept
Using the same style of example as the report, with integer inputs `totalPay = 123456789`, `voteSum = 5555`, `voteCount = 1234`:

- Current (`payStandbyWitness`): `eachVotePay = 123456789.0 / 5555 = 22226.010...`; `pay = (long)(1234 * 22226.010...) = 27,426,905` (floating point rounding truncates before final multiply).
- Correct order: `pay = (123456789 * 1234) / 5555 = 27,426,907` (multiply first, divide once).

The discrepancy (here on the order of a few units per witness per payout, scaling with values and repeated every payout) demonstrates the same class of systematic underpayment described in the report, reproduced with integer inputs run through `payStandbyWitness`'s actual `double`-based formula versus multiply-then-divide integer formula.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
