Found it. `UnDelegateResourceActuator` modifies the **receiver's** account state (bandwidth/energy usage, `AcquiredDelegatedFrozenV2Balance`) purely on the `owner`'s signature, with no consent or authorization check from the receiver — directly analogous to Gondi's `addNewTranche()` where the lender's signature alone was sufficient to mutate the borrower's loan state.

### Title
Unauthorized modification of receiver account resource/usage state via `UnDelegateResourceActuator` without receiver consent - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator.execute()` mutates the **receiver's** `AccountCapsule` (bandwidth/energy usage counters and `AcquiredDelegatedFrozenV2Balance`) whenever the resource `owner` broadcasts an `UnDelegateResourceContract`. Only the `owner`'s transaction signature is checked in `validate()`; the receiver is never required to sign or approve, exactly mirroring the Gondi finding where only the lender's signature was checked while the borrower's loan was mutated without consent.

### Finding Description
`validate()` checks only that `ownerAddress` and `receiverAddress` are valid, distinct addresses and that the owner has sufficient delegated balance to reclaim: [1](#0-0) 
There is no check tying `receiverAddress` to the transaction signer, nor any receiver approval mechanism — the receiver's consent is never required because the contract is authorized solely by the owner (as `getOwnerAddress()` returns the owner field used for the standard single-signature `validateSignature` check performed in `Manager.pushTransaction` / `TransactionCapsule.validateSignature`).

In `execute()`, the actuator directly rewrites the receiver's live usage counters and consumption timestamps: [2](#0-1) 
Specifically, it recomputes `transferUsage` from the receiver's *current* bandwidth/energy usage ratio and unconditionally overwrites `receiverCapsule.setNetUsage(...)` / `setEnergyUsage(...)` and `setLatestConsumeTime(...)` / `setLatestConsumeTimeForEnergy(...)`, then persists the mutated receiver account: [3](#0-2) [4](#0-3) 

This differs qualitatively from `TransferAssetActuator`/`TransferContract`, where the receiver's balance is only ever *increased* (a benign, expected on-chain behavior for token transfers). Here the owner can unilaterally strip resource usage windows and acquired balances from the receiver's account state at any time the owner chooses, with the outcome depending on the receiver's *current* usage at the moment the owner submits the transaction — a value the owner can observe on-chain and time adversarially.

### Impact Explanation
An owner who previously delegated bandwidth/energy to a receiver can call `UnDelegateResourceContract` at will to reclaim the resource and simultaneously force a recalculation of the receiver's `NetUsage`/`EnergyUsage` and `LatestConsumeTime`. Because this happens without the receiver's authorization, a receiver actively relying on delegated resource (e.g., a smart contract or dApp backend counting on available bandwidth/energy for a batch of pending operations) can have that resource silently revoked and its usage state altered mid-flight, causing unexpected `OUT_OF_ENERGY`/bandwidth-exhaustion failures for the receiver's own subsequent transactions. This is an asset/resource-accounting corruption from the receiver's perspective, reachable by any account via a normal broadcast transaction (`UnDelegateResourceContract`) requiring only the owner's own signature.

### Likelihood Explanation
High likelihood of reachability: `UnDelegateResourceContract` is a standard, publicly broadcastable transaction type processed by `Manager.pushTransaction` after ordinary single-signer signature validation; no special privilege is required beyond being the original resource-delegating account, which any account can become simply by delegating resource to an arbitrary victim address first (`DelegateResourceActuator` likewise requires no receiver consent to originate the delegation, since the receiver only ever gains resource there). Thus an attacker can delegate a small amount to a victim, then repeatedly undelegate at chosen times to manipulate the victim's usage counters.

### Recommendation
Since resource delegation lifecycle is owner-controlled by design (owner froze the TRX, so owner should be able to reclaim it), the concrete fix is not to require receiver co-signature (that would break the intended UX), but to eliminate receiver-side side effects that depend on data the receiver did not consent to have recomputed adversarially — specifically, avoid mutating `NetUsage`/`EnergyUsage`/`LatestConsumeTime` based on the *current* live usage ratio captured at an owner-chosen time, or clearly document/bound this as intentional (matching Gondi's approach of documenting it as accepted design) rather than an authorization gap. If receiver-side usage/resource guarantees are meant to be protected, add validation ensuring the recalculated usage transfer cannot push the receiver below zero or otherwise cause immediate resource starvation without receiver opt-in.

### Proof of Concept
1. Attacker account A delegates a small amount of BANDWIDTH/ENERGY to victim account B via `DelegateResourceActuator` (`DelegateResourceContract`), which succeeds without any signature or consent from B. [5](#0-4) 
2. B begins actively using the delegated bandwidth/energy for its own operations, increasing its `NetUsage`/`EnergyUsage`.
3. A observes B's on-chain usage and broadcasts `UnDelegateResourceContract` (signed only by A) at a moment chosen to maximize disruption to B.
4. `UnDelegateResourceActuator.execute()` recomputes and overwrites B's `NetUsage`/`EnergyUsage`/`LatestConsumeTime` fields based on B's current usage ratio, purely from A's unilateral, single-signature transaction, with no participation or consent from B. [6](#0-5)

  @Override
  public boolean execute(Object result) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) result;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    final DelegateResourceContract delegateResourceContract;
    AccountStore accountStore = chainBaseManager.getAccountStore();
    byte[] ownerAddress;
    try {
      delegateResourceContract = this.any.unpack(DelegateResourceContract.class);
      ownerAddress = getOwnerAddress().toByteArray();
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    AccountCapsule ownerCapsule = accountStore
        .get(delegateResourceContract.getOwnerAddress().toByteArray());
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    long delegateBalance = delegateResourceContract.getBalance();
    boolean lock = delegateResourceContract.getLock();
    long lockPeriod = getLockPeriod(dynamicStore.supportMaxDelegateLockPeriod(),
            delegateResourceContract);
    byte[] receiverAddress = delegateResourceContract.getReceiverAddress().toByteArray();

    // delegate resource to receiver
    switch (delegateResourceContract.getResource()) {
      case BANDWIDTH:
        delegateResource(ownerAddress, receiverAddress, true,
            delegateBalance, lock, lockPeriod);

        ownerCapsule.addDelegatedFrozenV2BalanceForBandwidth(delegateBalance);
        ownerCapsule.addFrozenBalanceForBandwidthV2(-delegateBalance);
        break;
      case ENERGY:
        delegateResource(ownerAddress, receiverAddress, false,
            delegateBalance, lock, lockPeriod);

        ownerCapsule.addDelegatedFrozenV2BalanceForEnergy(delegateBalance);
        ownerCapsule.addFrozenBalanceForEnergyV2(-delegateBalance);
        break;
      default:
        logger.debug("Resource Code Error.");
    }

    accountStore.put(ownerCapsule.createDbKey(), ownerCapsule);

    ret.setStatus(fee, code.SUCESS);

    return true;
  }
