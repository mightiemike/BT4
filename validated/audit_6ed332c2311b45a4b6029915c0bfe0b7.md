### Title
L1 handler transaction can be reopened into a validatable state after reaching `CancelledOnL2`/`Rejected` via a repeated cancellation-start event - (File: crates/apollo_l1_events/src/transaction_record.rs)

### Summary
`TransactionRecord::mark_cancellation_request` unconditionally sets `state = TransactionState::CancellationStartedOnL2` whenever the record is not `committed`, without checking whether the record has already reached a terminal, non-validatable state (`CancelledOnL2`, `Rejected`, or even `Consumed`/`CancellationFinalizedOnL1`). This mirrors the reported TON bug class: one code path (`mark_committed`/`mark_rejected`) asserts the current state before transitioning, while a different path that reaches the same kind of transition (`mark_cancellation_request`) fails to validate the pre-condition, allowing a "closed" (terminal) L1 handler transaction record to be reopened into a state that `is_validatable()` treats as active again.

### Finding Description
`is_validatable()` only excludes `Committed`, `CancelledOnL2`, and `Consumed` states: [1](#0-0) 

`CancellationStartedOnL2` and `Rejected` are *not* excluded, so a record in either state is still considered validatable/stageable by `validate_tx`: [2](#0-1) 

However, `mark_cancellation_request` only guards against the `Committed` case; it does not check for `CancelledOnL2` (timelock already expired, meant to be a durable terminal state) or `Rejected`: [3](#0-2) 

By contrast, sibling transition functions in the same struct do defend their pre-conditions with hard assertions, e.g. `mark_committed` asserts `!self.committed` and `mark_rejected` asserts `!self.committed`: [4](#0-3) 

The caller in `TransactionManager::request_cancellation` passes the event through unconditionally as well, with no state check beyond existence of the record: [5](#0-4) 

And the L1 event dispatcher only checks that the tx exists in the provider before forwarding a `TransactionCancellationStarted` event to `request_cancellation` — it performs no check on the transaction's current lifecycle state: [6](#0-5) 

Because `update_time_based_state` moves `CancellationStartedOnL2` → `CancelledOnL2` only after the timelock expires (and this is meant to be the permanently-terminal, non-validatable end state for that tx), receiving a second `TransactionCancellationStarted` L1 event for the same `tx_hash` after it already reached `CancelledOnL2` (or `Rejected`, which also has no explicit terminal guard) resets `state` back to `CancellationStartedOnL2` — a state that `is_validatable()` treats as active/stageable, effectively "reopening" a transaction that was supposed to be permanently excluded from proposal/validation.

### Impact Explanation
An L1 handler transaction that has already been rejected on L2, or whose cancellation timelock has already elapsed (`CancelledOnL2`), can be forced back into a validatable (`CancellationStartedOnL2`) state simply by a subsequent `MessageToL2CancellationStarted` L1 event for the same message (which any L1 account controlling the original message's sender/nonce can trigger, or which can occur as a duplicate/late-arriving scrape of the same underlying L1 call). Once reopened, the transaction can again be selected via `get_txs`/`validate_tx` and proposed/validated for inclusion in a block, contradicting the intended semantics that a cancelled or rejected L1→L2 message must never again be sequenced. This can lead to unauthorized re-processing of an L1 message the protocol had already treated as finalized-out, i.e., unauthorized transaction execution / inconsistent transaction admission across the fleet (nodes that saw the events in different orders/timings could disagree on whether the tx is currently validatable), risking state divergence between proposer and validators or wasted/duplicate consumption semantics for a message meant to be dead.

### Likelihood Explanation
Triggering `TransactionCancellationStarted` a second time for the same `tx_hash` is possible through ordinary externally-observable L1 activity (the L1 `startL1ToL2MessageCancellation` call can be invoked more than once by the same sender/nonce owner, or the scraper could relay a duplicate event in edge/reorg scenarios), and requires no special sequencer privilege — the reachable path is a normal L1 event processed by `add_events`, which any L1 message sender indirectly controls by (re-)issuing the cancellation-start call for their own message. No additional guard exists at any layer (`l1_events_provider::add_events`, `TransactionManager::request_cancellation`, or `TransactionRecord::mark_cancellation_request`) to reject the request once the record is already `Rejected` or `CancelledOnL2`.

### Recommendation
- **Short term:** In `TransactionRecord::mark_cancellation_request`, throw/return an error (or make it a no-op, consistent with how `finalize_cancellation` warns and still proceeds only for state maintenance) if `self.state` is already `CancelledOnL2`, `Rejected`, `Consumed`, or `CancellationFinalizedOnL1`, mirroring the existing guard against `Committed`.
- **Long term:** Ensure every state-transition function in `TransactionRecord` validates the full set of terminal states before mutating `state`, rather than checking only one condition (`committed`). Add unit tests exercising "second cancellation-start event after `CancelledOnL2`/`Rejected`" to lock in the guard.

### Proof of Concept
1. Provider processes `LogMessageToL2` for `tx_hash`, creating a `TransactionRecord` in `Pending` state.
2. Provider processes `TransactionCancellationStarted { tx_hash, cancellation_request_timestamp: t0 }` → `request_cancellation` → `mark_cancellation_request` sets `state = CancellationStartedOnL2`, `cancellation_requested_at = Some(t0)`.
3. Time passes beyond `cancellation_timelock`; on the next `validate_tx`/`update_time_based_state` call, `state` transitions to `CancelledOnL2` (now `is_validatable() == false`, effectively "closed").
4. Attacker/legitimate L1 sender re-issues (or a duplicate/replayed) `startL1ToL2MessageCancellation` call for the same message, producing another `TransactionCancellationStarted` event with a new timestamp `t1`.
5. Provider's `add_events` forwards this to `request_cancellation` → `mark_cancellation_request`: since `self.committed == false`, it unconditionally sets `state = CancellationStartedOnL2` again (note: `cancellation_requested_at` stays at `t0` because of the `match self.cancellation_requested_at { Some(existing) => Some(existing) ... }` branch, but `state` is still overwritten).
6. `is_validatable()` now returns `true` for this record (state is `CancellationStartedOnL2`, not `CancelledOnL2`), so subsequent `validate_tx`/`get_txs` calls treat the previously-cancelled transaction as active again, allowing it to be proposed/validated into a block.

    /// Mark a cancellation request for this transaction.
    /// Returns the existing cancellation timestamp if one exists, `None` if this is the first
    /// request.
    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }
