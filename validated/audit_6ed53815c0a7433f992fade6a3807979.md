### Title
Bad-debt write-down runs *before* interest accrual in `socialize-debt-asset`, causing suppliers/treasury to lose interest that had already accrued on the socialized principal - (`mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/vault/v0-vault-ststxbtc.clar`)

### Summary
`socialize-debt-asset` calls `vault-socialize-debt` (→ vault's `socialize-debt`) *before* calling `vault-accrue` (→ vault's `accrue`) for the same asset in the same fold iteration. Unlike every other state-mutating vault entry point (`deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`), `socialize-debt` does not call `accrue` first, so the write-down is applied against the stale `index`/`lindex` from `last-update`, and the subsequent `accrue` call computes interest for that whole elapsed interval over the already-shrunk `principal-scaled`/`total-borrowed`.

### Finding Description
Sequence inside `socialize-debt-asset` (`mainnet/contracts/market/v0-4-market.clar` lines 879-903):

1. `(unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)` — routes to `.v0-vault-ststxbtc socialize-debt` [1](#0-0) [2](#0-1) .
2. Inside `socialize-debt` (`mainnet/contracts/vault/v0-vault-ststxbtc.clar` lines 944-984), all bindings (`idx`, `current-assets`, `current-lindex`, `old-total-assets`) are read from `var-get index`/`var-get lindex` etc. **without calling `accrue` first**, unlike `deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`, which all begin their `let` with `(u (try! (accrue)))` [3](#0-2) . So `principal-scaled`, `total-borrowed`, `assets`, and `lindex` are all written down using the index as of `last-update`, ignoring interest that accrued since then.
3. Back in `socialize-debt-asset`, `(map-set index-cache ... (unwrap! (vault-accrue asset-id) failed-status))` immediately calls `accrue` on the same vault [4](#0-3) .
4. `accrue` (`mainnet/contracts/vault/v0-vault-ststxbtc.clar` lines 835-863) computes `next-index`/`next-liquidity-index` using `time-delta = stacks-block-time - last-update` (still the full pre-write-down interval, since `socialize-debt` never touched `last-update`), but `debt-delta`, `reserve-inc`, and `treasury-lp` (the treasury's minted share) are computed from `(var-get principal-scaled)` — which is now the *post-write-down*, smaller value [5](#0-4) . Likewise `next-liquidity-index` depends on `utilization()`/`interest-rate()`, which are recomputed from the already-shrunk `total-borrowed`/`assets`, understating the rate that actually applied while the now-socialized debt was still outstanding for most of that interval.

Root cause: the write-down and the interest accrual for the same elapsed interval are applied in the wrong order. The correct order (used everywhere else in the vault) is accrue-then-mutate; here it is mutate(write-down)-then-accrue. As a result, the interest that had economically accrued on the pre-write-down (larger) `principal-scaled`/`total-assets` during `[last-update, now]` is never captured — the `old-total-assets` used inside `socialize-debt` to size the `lindex` write-down also excludes that interval's accrued interest, so depositors absorb the bad-debt loss as a larger fraction of a smaller (stale) asset base, and the treasury's `reserve-inc`/`treasury-lp` mint in the following `accrue` call is computed on the diminished post-write-down principal rather than the true pre-write-down principal that was actually outstanding and accruing interest up to the moment of liquidation.

No caller-controlled input is needed beyond triggering a normal bad-debt-socializing liquidation; there is no assertion, cap, or later step in `socialize-debt-asset` or `accrue` that reconciles or backfills the lost interest — the transaction does not revert, it simply mis-accounts state permanently for that interval.

### Impact Explanation
Unclaimed yield (both the liquidity-index growth owed to zft-share holders and the treasury's reserve-factor cut minted via `treasury-lp`) that had already economically accrued between `last-update` and the liquidation block on the debt portion being socialized is permanently lost/never minted — it is silently absorbed into the write-down instead of being credited first. This is a permanent under-crediting of already-earned yield (not a revert/temporary freeze), matching the in-scope category "High – theft of unclaimed yield ... or permanent freezing of unclaimed yield or royalties." Magnitude scales with elapsed time since `last-update` and the size of the socialized debt relative to `total-assets`.

### Likelihood Explanation
This triggers on every ordinary bad-debt socialization event (any liquidation that leaves under-collateralized residual debt), which is a normal, expected, unprivileged flow (any liquidator can cause it by liquidating an eligible position — no special access needed). The interleaving is not attacker-chosen for profit extraction; it is an incidental, deterministic consequence of the contract's fixed call order inside `socialize-debt-asset`, so it fires every single time bad debt is socialized on this vault, with no extra capital cost to the ordinary liquidator triggering it.

### Recommendation
In `socialize-debt-asset`, call `vault-accrue` **before** `vault-socialize-debt` for the asset (mirroring the accrue-then-mutate pattern used by `deposit`/`redeem`/`system-borrow`/`system-repay`), or equivalently make the vault's `socialize-debt` call `accrue` internally as its first step so the write-down operates on freshly-accrued `index`/`lindex`/`principal-scaled` values, then drop the redundant post-write-down `vault-accrue` call (or keep it as a no-op cache refresh since state won't have moved).

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy full protocol; initialize `.v0-vault-ststxbtc`; set a non-zero `fee-reserve` and interest-rate curve with `points-util`/`points-rate` producing a nonzero rate at moderate utilization.
2. Have a supplier deposit stSTXbtc into the vault (mint zft shares), and have a borrower system-borrow against collateral, until utilization is significant and `total-borrowed`/`principal-scaled` are set.
3. Advance the simnet chain time (e.g. `mineEmptyBlocks`/timestamp advance) by a meaningful interval (e.g. days) without calling `accrue`, so unclaimed interest exists (`next-index()` and `next-liquidity-index()` diverge from stored `index`/`lindex`).
4. Snapshot `get-total-supply`, `dao-treasury` zft balance, and `get-liquidity-index` immediately before triggering socialization.
5. Trigger a liquidation on the market that leaves bad debt for `stSTXbtc`, causing `.v0-4-market` to invoke `socialize-debt-asset` for `stSTXbtc` in its fold.
6. Inside the same transaction, record (via `print` events or exposed getters) the `old-total-assets`/`current-lindex` used inside `socialize-debt` (post- but stale-index) versus what `total-assets-preview()`/`next-liquidity-index()` would have produced if `accrue` had run first.
7. Compare `dao-treasury`'s zft balance and `get-liquidity-index` after the transaction against a modified control run where `accrue` is called manually right before triggering the liquidation (simulating the "should be" order) — the control run should show a strictly larger `treasury-lp` mint and a smaller proportional `lindex` write-down than the actual (buggy) order, confirming the immediate-write-down-then-accrue path permanently drops treasury/supplier yield for that interval.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
