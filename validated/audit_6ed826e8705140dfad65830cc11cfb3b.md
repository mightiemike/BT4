### Title
Fixed static gas budget for `rlp_execute_callback` can be under-priced relative to actual execution cost, permanently freezing the ETH-implicit Wallet Contract account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (the code deployed on every ETH‑implicit account to emulate Ethereum transactions, per NEP‑518) gates all further `rlp_execute` calls behind an in‑flight flag, `has_in_flight_tx`, that is only supposed to be cleared by the promise callback that finishes execution. The gas attached to that callback is a hard‑coded constant rather than an amount validated against the actual cost of running it. If the callback's real gas cost ever exceeds this fixed budget, the callback receipt fails, and — because a failed receipt is rolled back atomically in nearcore — the flag that was already committed as `true` never gets reset. This is the same failure class as the reported "use of `transfer()` with a fixed gas stipend": a hard-coded gas amount for a value/state-critical step that can become insufficient and permanently strand funds/state.

### Finding Description
`WalletContract::rlp_execute` sets `has_in_flight_tx = true` and commits that state change in the transaction/receipt that creates the outbound promise chain: [1](#0-0) [2](#0-1) 

The gas that will be given to the eventual `rlp_execute_callback` (the only place expected to flip `has_in_flight_tx` back to `false`) is computed from hard-coded constants, not from any measured/validated cost of the callback logic: [3](#0-2) 

These fixed budgets (5 Tgas plus small additions) are then attached via `with_static_gas` when scheduling the callback for every transaction kind (address-check flow, NEP‑141 storage-deposit flow, self-transfer flow, and the default flow): [4](#0-3) 

nearcore's runtime guarantees that a receipt which fails (including with `GasExceeded`/"Exceeded the prepaid gas") is rolled back except for outcome/gas accounting — no state change from that receipt is persisted: [5](#0-4) 

Because `has_in_flight_tx = true` was already durably committed by the earlier, successful `rlp_execute` receipt, a subsequent callback failure due to insufficient attached gas leaves the flag permanently stuck at `true`. Every future call to `rlp_execute` on that account short-circuits with the "transaction already in progress" error, since the check happens unconditionally at the top of the method: [6](#0-5) 

Unlike Solidity's `transfer()` 2300-gas stipend (which is fixed by the EVM itself and can't track increases in opcode costs), here the wallet contract's own author chose a fixed constant for the callback rather than deriving/validating it against the actual, possibly-growing cost of the callback logic (which parses execution results, may issue further refund logic, NEP-141 handling, etc.). Any future increase in the underlying gas cost model (e.g., WASM cost table updates, new per-byte or per-op charges introduced by a protocol upgrade) or any code change to the callback that increases its instruction count can push the real cost above the hard-coded budget.

### Impact Explanation
If the fixed callback gas ever becomes insufficient, the ETH-implicit account's Wallet Contract instance becomes permanently unusable: `has_in_flight_tx` stays `true` forever, and every subsequent `rlp_execute` call — the only entry point for that ETH-implicit account to send funds, call other contracts, or manage its access keys — is rejected. Because ETH-implicit accounts cannot be deleted and cannot receive a full-access key by any means other than the Wallet Contract's own actions, this constitutes a permanent freeze of the account and of any funds already held by it (they can never be moved out through the wallet's normal transaction path again). This matches the report's "fund can get stuck" impact, but here it is amplified to a full account freeze rather than a single failed transfer.

### Likelihood Explanation
Triggering this requires only:
1. A protocol-level (or contract-level, since the Wallet Contract's code itself could be redeployed with more complex callback logic) increase in the real gas cost of executing `rlp_execute_callback`/`address_check_callback`/`nep_141_storage_balance_callback` relative to their hard-coded budgets (5 Tgas class), or
2. Any legitimate cross-shard/receipt delay or congestion scenario that causes extra gas to be burnt inside the callback logic before it finishes clearing the flag.

Since the constants are static and not derived from measured worst-case execution cost, and NEAR's cost tables are periodically revised by protocol upgrades (see the various `ProtocolFeature` gas-cost changes such as `AccountCostIncrease`), the risk is not purely theoretical — it depends only on chain-level parameter changes outliving the currently-deployed Wallet Contract binary, which is realistic given how infrequently on-chain contracts are redeployed compared to how often protocol gas parameters are revisited.

### Recommendation
- Avoid gating a critical liveness/state-recovery mutation (`has_in_flight_tx = false`) behind a fixed, hard-coded gas budget for the callback. Instead:
  - Attach enough gas to the callback using the "unspent gas" / weight-based mechanism (`promise_batch_action_function_call_weight` / `GasWeight`), which automatically claims all remaining prepaid gas rather than a static amount, matching NEAR's recommended pattern for cross-contract callbacks (see `docs/architecture/how/gas.md`'s discussion of NEP‑264 weighted gas).
  - Add an explicit recovery path (e.g., a privileged/self-call cleanup method, or a timeout-based reset) that lets the account clear `has_in_flight_tx` even if the original callback never completes successfully.
  - Add a regression test that artificially reduces available gas for the callback path and asserts the contract remains recoverable rather than permanently locked.

### Proof of Concept
1. Deploy the Wallet Contract on an ETH-implicit account (as already done by `action_implicit_account_creation_transfer`, see `runtime/runtime/src/actions.rs:255-269`, which sets `AccountContract::Global(global_contract_hash)` to the shared wallet code).
2. Submit an `rlp_execute` transaction that reaches any of the callback-scheduling branches in `inner_rlp_execute` (lines 412–472 above), causing `has_in_flight_tx` to be committed as `true`.
3. Ensure the actual gas needed to run the scheduled callback (`rlp_execute_callback`/`address_check_callback`/`nep_141_storage_balance_callback`) exceeds the hard-coded budget — reproducible today in a test harness by monkey-patching/forking the contract to inflate work done in the callback (simulating a future gas-cost-table increase), or by waiting for a live protocol gas-cost upgrade that raises the relevant opcode/host-function costs beyond the ~5–15 Tgas static budgets.
4. Observe the callback receipt fails with `GasExceeded`ish error ("Exceeded the prepaid gas"), and per nearcore's failed-receipt rollback guarantee, no state update clears `has_in_flight_tx`.
5. Any subsequent `rlp_execute` call to the same account now unconditionally returns `"Error: transaction already in progress, please try again later."` forever, confirming the permanent freeze.

Note: I was not able to fully read the body of `rlp_execute_callback` (the function that resets `has_in_flight_tx`) within the available tool budget to confirm there is no alternate/manual recovery branch inside it; this should be verified directly in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` (the callback implementations) before treating this as fully proven.
