### Title
Unprivileged RPC scan callers can indefinitely pin `AccountsDb` clean/shrink progress, causing unbounded storage and CPU growth - (File: `accounts-db/src/accounts_db.rs`, `accounts-db/src/accounts_scan.rs`)

### Summary
Any unauthenticated RPC client can invoke a scan-backed RPC method (`getProgramAccounts`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, `getLargestAccounts`, `getSupply`, etc.), which internally calls `AccountsDb::scan_accounts`. This registers a `ScanGuard` that pins the scan's `max_root` in the global `ScanTracker::ongoing_scan_roots` map for the entire duration of the scan. `clean_accounts`/`flush_rooted_accounts_cache_with_clean` compute `max_clean_root` bounded by the minimum ongoing scan root, so cleaning cannot advance past a slow/long-running scan. A caller who keeps a single scan open (e.g., by requesting a large `getProgramAccounts` result and reading the HTTP response slowly, or targeting a program with many accounts) can hold this pin open far longer than intended, blocking `clean`/`shrink` for the whole node with only a single RPC call.

### Finding Description
`scan_accounts` (analogous in spirit to Llama's unprivileged `validateActionCreation`, which let anyone mutate a value meant to be fixed "at creation time") lets any unprivileged caller mutate shared, globally-consequential AccountsDb state — the `ongoing_scan_roots` pin — for as long as their single RPC call/scan is alive: [1](#0-0) 

The pin is registered via `ScanGuard::try_new`, which locks `ongoing_scan_roots` and increments the count for the caller-determined `max_root`, tracking `max_distance_to_min_scan_slot` as a symptom metric: [2](#0-1) 

`flush_rooted_accounts_cache_with_clean` explicitly bounds the cleanable root by the oldest ongoing scan root, meaning a stalled scan blocks cleaning of every newer root: [3](#0-2) 

This is not merely theoretical — it is a known internal effect documented and exercised in tests, confirming a single external RPC scan is capable of preventing cache cleaning and immediate purge of zero-lamport single-ref accounts: [4](#0-3) [5](#0-4) 

`test_scan_flush_accounts_cache_then_clean_drop` demonstrates directly that a live scan on an unrooted/rooted slot prevents `clean_accounts` from purging accounts that would otherwise be reclaimed: [6](#0-5) 

The scan-backed RPC endpoints (`getProgramAccounts`, `getSupply`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, `getLargestAccounts`) are part of the standard, unauthenticated `rpc_accounts_scan` module exposed to any client: [7](#0-6) 

### Impact Explanation
While a scan is pinned, `clean_accounts` cannot advance the clean root past the pinned slot, so obsolete/zero-lamport account versions across many newer rooted slots accumulate instead of being reclaimed, and shrink candidates are not resolved. This causes disproportionate growth of on-disk `AccountStorageEntry` data and increases the CPU/I/O cost of subsequent cleans/shrinks/scans once the pin is released, since more work has piled up. A caller can trigger and sustain this state with a single unauthenticated RPC call (no special role required), by simply not finishing consumption of a large/slow scan.

### Likelihood Explanation
Moderate. It requires an API node with `getProgramAccounts`/scan RPC enabled (which is common for public RPC nodes) and a client that issues one scan request and keeps it open (e.g., a large program-account set combined with a slow/throttled reader, or repeatedly starting new scans in quick succession to keep `min_ongoing_scan_root` pinned near the oldest slot). This matches the "single call" boundary called out in scope rules, since it does not require more than one call per slot to sustain the effect once initiated, though a persistent effect benefits from re-issuing the scan.

### Recommendation
Bound the maximum duration/size of a single RPC scan (timeout the scan and release the `ScanGuard` if the client does not consume results promptly, decoupling internal cleaning progress from external I/O pace), and/or decouple `clean_accounts`'s bound from `min_ongoing_scan_root` when the gap (`max_distance_to_min_scan_slot`) exceeds a safety threshold, allowing clean to proceed and instead serve slow scans from a consistent snapshot/copy rather than blocking global cleanup.

### Proof of Concept
Not independently reproduced in this analysis; the described mechanism is directly evidenced by the existing unit tests `test_scan_flush_accounts_cache_then_clean_drop` [8](#0-7)  and the explicit comment in `test_remove_zero_lamport_single_ref_accounts_after_shrink` acknowledging "flush_write_cache doesn't clean if there is an ongoing RPC scan" [5](#0-4) , which simulate the exact externally-triggerable condition (a long-lived scan pinning the clean root) using the same `AccountsDb::scan_accounts`/`ScanGuard` path that unauthenticated `getProgramAccounts` RPC calls exercise.

    /// the newest version of any given account when flushing multiple rooted slots. This reduces
    /// storage space and speeds up background account cleaning. If an ongoing scan is occurring,
    /// cleaning can only be done up to the minimum scan root to avoid cleaning accounts that may

        &self,
        requested_flush_root: Option<Slot>,
    ) -> (usize, usize, FlushStats) {

        self.flush_rooted_accounts_cache(
            requested_flush_root,
            FlushShouldClean::Yes { max_clean_root },

impl<'a> ScanGuard<'a> {
    /// Begin a scan: checks the bank hasn't been removed and pins `max_root` in
    /// `ongoing_scan_roots`.
    ///
    /// Returns `None` if the bank has already been removed.
    ///
    /// `max_root_inclusive_fn` is called while holding the `ongoing_scan_roots` write lock.
    pub(crate) fn try_new(
        scan_tracker: &'a ScanTracker,
        scan_bank_id: BankId,
        max_root_inclusive_fn: impl FnOnce() -> Slot,
    ) -> Option<Self> {
        {
            let locked_removed_bank_ids = scan_tracker.removed_bank_ids.lock().unwrap();
            if locked_removed_bank_ids.contains(&scan_bank_id) {
                return None;
            }
        }

        let max_root_inclusive = {
            let mut w_ongoing_scan_roots = scan_tracker
                // This lock is also grabbed by clean_accounts(), so clean
                // has at most cleaned up to the current `max_root` (since
                // clean only happens *after* BankForks::set_root() which sets
                // the `max_root`)
                .ongoing_scan_roots
                .write()
                .unwrap();
            // `max_root()` grabs a lock while
            // the `ongoing_scan_roots` lock is held,
            // make sure inverse doesn't happen to avoid
            // deadlock
            let max_root_inclusive = max_root_inclusive_fn();
            if let Some(min_ongoing_scan_root) =
                ScanTracker::min_ongoing_scan_root_from_btree(&w_ongoing_scan_roots)
                && min_ongoing_scan_root < max_root_inclusive
            {
                let current = max_root_inclusive - min_ongoing_scan_root;
                scan_tracker
                    .max_distance_to_min_scan_slot
                    .fetch_max(current, Ordering::Relaxed);
            }
            *w_ongoing_scan_roots.entry(max_root_inclusive).or_default() += 1;
            max_root_inclusive
        };

        scan_tracker.active_scans.fetch_add(1, Ordering::Relaxed);
        Some(Self {
            scan_tracker,
            max_root: max_root_inclusive,
            scan_bank_id,
        })

#[test]
fn test_scan_flush_accounts_cache_then_clean_drop() {
    let db = Arc::new(AccountsDb::new_for_tests_with_config(
        Vec::new(),
        DEFAULT_ACCOUNTS_DB_CONFIG,
    ));
    let account_key = Pubkey::new_unique();
    let account_key2 = Pubkey::new_unique();
    let slot0_account = AccountSharedData::new(1, 0, AccountSharedData::default().owner());
    let slot1_account = AccountSharedData::new(2, 1, AccountSharedData::default().owner());
    let slot2_account = AccountSharedData::new(3, 1, AccountSharedData::default().owner());

    /*
        Store account into slots 0, 1, 2 where
        root slots are 0, 2, and slot 1 is unrooted.
                                0 (root)
                            /        \
                          1            2 (root)
    */
    db.store_for_tests((0, &[(&account_key, &slot0_account)][..]));
    db.store_for_tests((1, &[(&account_key, &slot1_account)][..]));
    // Fodder for the scan so that the lock on `account_key` is not held
    db.store_for_tests((1, &[(&account_key2, &slot1_account)][..]));
    db.store_for_tests((2, &[(&account_key, &slot2_account)][..]));

    let max_scan_root = 0;
    db.add_root(max_scan_root);
    let scan_ancestors: Arc<Ancestors> = Arc::new(Ancestors::from(vec![0, 1]));
    let bank_id = 0;
    let scan_tracker = setup_scan(db.clone(), scan_ancestors.clone(), bank_id, account_key2);

    // Add a new root 2
    let new_root = 2;
    db.add_root(new_root);

    // Check that the scan is properly set up
    assert_eq!(
        db.scan_tracker.min_ongoing_scan_root().unwrap(),
        max_scan_root
    );

    // If we specify a requested_flush_root == 2, then `slot 2 <= max_flush_slot` will
    // be flushed even though `slot 2 > max_scan_root`. The unrooted slot 1 should
    // remain in the cache
    db.flush_accounts_cache(true, Some(new_root));
    assert_eq!(db.accounts_cache.num_slots(), 1);
    assert!(db.accounts_cache.slot_cache(1).is_some());

    // Intra cache cleaning should not clean the entry for `account_key` from slot 0,
    // even though it was updated in slot `2` because of the ongoing scan
    let account = db
        .get_account_at_slot(&account_key, 0)
        .expect("account should exist");
    assert_eq!(account.lamports(), slot0_account.lamports());

    // Run clean, unrooted slot 1 should not be purged, and still readable from the cache,
    // because we're still doing a scan on it.
    db.clean_accounts_for_tests();
    let account = db
        .get_account_at_slot(&account_key, 1)
        .expect("account should exist");
    assert_eq!(account.lamports(), slot1_account.lamports());

    // When the scan is over, clean should not panic and should not purge something
    // still in the cache.
    scan_tracker.exit().unwrap();
    db.clean_accounts_for_tests();
    let account = db
        .get_account_at_slot(&account_key, 1)
        .expect("account should exist");
    assert_eq!(account.lamports(), slot1_account.lamports());

    // Simulate dropping the bank, which finally removes the slot from the cache
    let bank_id = 1;
    db.purge_slot(1, bank_id, false);
    assert!(db.get_account_at_slot(&account_key, 1).is_none());
}
