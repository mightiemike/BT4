### Title
`isSafe()` in `validate-redirect-url.ts` fails to detect protocol-relative redirect URLs (`//evil.com/...`), allowing `sanitizeRedirectUrl` to return a URL pointing to an attacker-controlled origin - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts])

### Summary
`sanitizeRedirectUrl`/`isSafe` are supposed to guarantee that any accepted `redirectUrl` resolves to the app's own origin, but the `INVALID_RELATIVE_URL` check is applied to `url.pathname` *after* `new URL(redirectUrl, domain)` has already resolved the URL, not to the raw `redirectUrl` string. A protocol-relative input like `//attacker.com/path` is parsed by the WHATWG `URL` constructor as `https://attacker.com/path` (host taken from the "authority" part of the input, ignoring the supplied base's host), and its resulting `pathname` is just `/path` — containing no double slash — so the double-slash guard never fires. `isSafe` therefore returns `true` for a URL whose origin differs entirely from `domain`.

### Finding Description
`isSafe()` performs these checks, in order, on `redirectUrl`/its parsed form: [1](#0-0) 

1. `FILE_URI_MATCH` (`///`) and `WHITESPACE_CHARACTER` are tested against the **raw** `redirectUrl` string.
2. `redirectUrl` is parsed with `new URL(redirectUrl, domain)`.
3. `INVALID_RELATIVE_URL` (`[/\\][/\\]`) is tested against **`url.pathname`**, i.e. the *already-resolved* pathname, not the original input.
4. Protocol and SSL requirements are checked against the resolved `url.protocol`.

For input `redirectUrl = "//attacker.com/path"` and `domain = APP_URL` (e.g. `https://app.example.com`):
- `FILE_URI_MATCH` (`///`) does not match (only two slashes).
- `new URL("//attacker.com/path", "https://app.example.com")` follows the WHATWG URL spec's "special authority ignore slashes" state and resolves to `https://attacker.com/path` — the host component is taken entirely from the input, not from `domain`.
- `url.pathname` for this resolved URL is `/path`, which does **not** match `INVALID_RELATIVE_URL`, so the double-slash guard is defeated because it inspects the post-resolution pathname rather than the pre-resolution string.
- `url.protocol` is `https:`, which passes `VALID_PROTOCOLS` and the SSL requirement.

`isSafe` therefore returns `true`, and `sanitizeRedirectUrl` returns `new URL("//attacker.com/path", domain)` whose `.origin` is `https://attacker.com`, not the app's origin — even though the entire purpose of this helper is to enforce a same-origin allowlist for redirect destinations. [2](#0-1) 

This same code exists verbatim in the `shopify-app-react-router` package. [3](#0-2) 

The result is consumed by `renderAppBridge`, which trusts the returned URL to be same-origin and injects it verbatim into a `<script>window.open(...)</script>` payload rendered in an HTML response, and used more generally for top-level/exit-iframe redirects: [4](#0-3) 

Because `sanitizeRedirectUrl` is the sole gate used before trusting a "relative" redirect target as being confined to the app's own domain, any code path that forwards attacker-influenced request data (e.g., the incoming request's own `pathname`/`search`, as is a common pattern for post-auth "return to where you were" redirects) into this helper is vulnerable to an open redirect to an arbitrary external origin whenever that value begins with `//` or contains a backslash-based authority-like prefix that the `URL` parser treats as protocol-relative.

### Impact Explanation
This is an open redirect vulnerability in an authentication-adjacent helper used to gate destinations for app-bridge/top-level navigation. An attacker who can influence the value passed as `redirectUrl` (e.g., via the request path/query that a login/exit-iframe flow echoes back) can cause the app to emit a `window.open()`/redirect script pointing at an attacker-controlled domain, defeating the intended "must stay on app origin" invariant. Depending on how a specific host app wires this in its OAuth begin/callback or exit-iframe logic, this can be leveraged for phishing (redirecting a merchant out of the legitimate embedded app context to a lookalike site) — matching Shopify's open-redirect impact class.

### Likelihood Explanation
The flaw is triggerable with a single crafted string and requires no privileges: `isSafe(domain, "//attacker.com/path")` returns `true` for any `domain`. It is fully deterministic and repeatable. The remaining uncertainty for full end-to-end exploitation is which specific caller feeds attacker-controlled data into `sanitizeRedirectUrl`'s `redirectUrl` parameter in a given host app; within this repository the only in-repo caller is `renderAppBridge`'s `redirectTo.url`, and the vulnerability is confirmed to reside squarely in the `isSafe` logic itself rather than in caller-side sanitization.

### Recommendation
Validate the *resolved* URL's origin against `domain`'s origin directly, e.g. `if (url.origin !== new URL(domain).origin) return false;`, rather than relying on regex heuristics against `pathname`. Additionally, run `INVALID_RELATIVE_URL`/`FILE_URI_MATCH` against the raw `redirectUrl` string (as already done for `FILE_URI_MATCH`) rather than the post-parse `pathname`, and explicitly reject inputs beginning with `//` or `\\` before calling `new URL()`.

import {ShopifyError} from '@shopify/shopify-api';

interface Options {
  requireSSL?: boolean;
  throwOnInvalid?: boolean;
}

type SanitizedRedirectUrl<OptionsArg extends Options> =
  OptionsArg['throwOnInvalid'] extends false ? URL | undefined : URL;

const FILE_URI_MATCH = /\/\/\//;
const INVALID_RELATIVE_URL = /[/\\][/\\]/;
const WHITESPACE_CHARACTER = /\s/;
const VALID_PROTOCOLS = ['https:', 'http:'];

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}

export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}
