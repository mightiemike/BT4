Analysis of `applyGasRefund` in `x/uexecutor/keeper/outbound.go` shows that when the excess-gas refund fails (both the swap-refund attempt and the no-swap fallback attempt), the code only records `refundPcTx.Status = "FAILED"` and `outbound.RefundSwapError`, then returns — there is no retry mechanism, no admin-triggered re-drive, and no separate claimable-balance accounting for the recipient.### Title
Failed excess-gas refunds are permanently written off with no retry, abort, or reclaim path - ([File: x/uexecutor/keeper/outbound.go])

### Summary
`applyGasRefund` in `x/uexecutor/keeper/outbound.go` computes an excess-gas amount (`gasFee - gasFeeUsed`) owed back to the outbound sender/fund recipient and attempts to pay it out via two on-chain calls to `UniversalCore.refundUnusedGas`. If both attempts fail, the function only records `PcRefundExecution.Status = "FAILED"` and `RefundSwapError` on the `OutboundTx`, then returns normally — the outbound itself is finalized as `OBSERVED`/`REVERTED` regardless. There is no retry mechanism, no `ABORTED` marking, and no admin/user-facing message to reclaim the unrefunded excess. This mirrors the reported bug class: a fee/balance amount is computed and recorded in state, but the actual transfer can silently fail with the record becoming a dead end rather than a claimable balance.

### Finding Description
`FinalizeOutbound` calls `handleFailedOutbound` or `handleSuccessfulOutbound`, both of which call `k.applyGasRefund(ctx, &outbound, obs)` unconditionally as part of finalizing the outbound [1](#0-0) .

Inside `applyGasRefund`, the refund is attempted in two steps: first a swap-based refund via `CallUniversalCoreRefundUnusedGas(..., withSwap=true, ...)`, and if any step in that path fails (fee-tier lookup, quote fetch, or the EVM call itself), a fallback no-swap call is attempted [2](#0-1) . If the fallback call also fails, the code does:
```go
resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, false, big.NewInt(0), big.NewInt(0))
if err != nil {
    refundPcTx.Status = "FAILED"
    refundPcTx.ErrorMsg = err.Error()
} else { ... }
outbound.PcRefundExecution = refundPcTx
outbound.RefundSwapError = swapFallbackReason
``` [3](#0-2) 

Crucially, this failure path does not call `AbortOutbound` (which is used elsewhere in the same file, e.g. when the revert re-mint fails, to flag the outbound for manual intervention) [4](#0-3) . Instead, both `handleFailedOutbound` and `handleSuccessfulOutbound` proceed to call `k.UpdateOutbound(ctx, utxId, outbound)` and return `nil` — the outbound is finalized as `REVERTED` or left `OBSERVED` with a `Status: FAILED` refund record baked in, with no state machine path back to it [5](#0-4) .

The excess amount (`gasFee - gasFeeUsed`) is a real value tracked in `outbound.GasFee`/`observed_tx.gas_fee_used`, computed from validator-observed data [6](#0-5) . Once `refundUnusedGas` fails on both the swap and no-swap attempts (e.g., due to insufficient PRC20 liquidity in the swap pool, a stale/incorrect fee tier, or any transient EVM failure), that amount is never retried and there is no `MsgClaimRefund`-style message or rescue message that lets the intended recipient (or an operator) pull the recorded amount later. Grepping the codebase for a retry/claim path (`RetryRefund`, `MsgClaimRefund`) found none; the only related recovery message class is `RESCUE_FUNDS`, which is a distinct, unrelated flow for stuck principal funds, not for gas-refund excess.

### Impact Explanation
Whenever the two on-chain refund attempts both fail — which is plausible under normal, unprivileged conditions (e.g., insufficient swap liquidity for the gas token/PC pair, a misconfigured fee tier, or the PRC20 gas token temporarily lacking balance in `UniversalCore`) — the excess gas amount that was rightfully owed to an ordinary user (the outbound sender or configured fund recipient) becomes permanently unrecoverable through any on-chain path in scope. This is a fund-freezing/loss condition reachable purely from ordinary relayer/UV observation of gas usage on the destination chain; no privileged actor is required to trigger it, satisfying the "permanent freezing... of user or protocol-controlled funds" allowed-impact category.

### Likelihood Explanation
The refund path runs on every successful and every failed outbound whenever `gasFee > gasFeeUsed` (the common case, since `gasFee` is a conservative pre-funded estimate and `gasFeeUsed` is the actual consumption) [7](#0-6) . The double-failure condition (swap AND no-swap both failing) depends on the state of `UniversalCore`'s liquidity/fee-tier configuration for the specific `gasToken`, which is plausible in production for less-liquid gas tokens or during pool imbalance — it is not an attacker-controlled trigger, but it is an ordinary operational condition, not a privileged-actor scenario, making this a realistically reachable, medium-to-high likelihood gap rather than a purely theoretical one.

### Recommendation
When both refund attempts fail, do not simply record `Status = "FAILED"` and move on. Either:
1. Call `AbortOutbound` (as is already done for failed revert re-mints) so the outbound is flagged `ABORTED` for manual/operator intervention, or
2. Introduce a persistent, per-recipient "pending refund" accounting entry (keyed by recipient + gas token + amount) together with a dedicated `MsgClaimGasRefund`-style message (or a keeper-driven retry in a future block) that allows the amount to actually be paid out later, mirroring the recommendation in the source report to add global accounting plus an access-controlled claim path.

### Proof of Concept
1. Configure (or let organically arise) a `UniversalCore` state where the gas-token/PC swap pool for a given `gasToken` has insufficient liquidity or an invalid default fee tier, so `GetDefaultFeeTierForToken`/`getSwapQuoteForRefund`/`CallUniversalCoreRefundUnusedGas(withSwap=true)` fails.
2. Simultaneously have the raw PRC20 `refundUnusedGas(withSwap=false)` fallback also fail (e.g., transient EVM revert, or the `UniversalCore` contract's PRC20 balance for that token being temporarily exhausted).
3. Submit `MsgVoteOutbound` observations from validators reaching quorum for an outbound where `outbound.GasFee > obs.GasFeeUsed`, triggering `handleSuccessfulOutbound`/`handleFailedOutbound` → `applyGasRefund`.
4. Observe: `outbound.PcRefundExecution.Status == "FAILED"`, `outbound.RefundSwapError` is populated, but `k.UpdateOutbound` still commits the outbound as finalized (`OBSERVED` or `REVERTED`) with no `ABORTED` status and no further code path ever re-attempts or exposes a claim for `refundAmount`. This mirrors the existing test `swap fallback reason stored when swap refund fails` in `test/integration/uexecutor/gas_fee_refund_test.go`, which explicitly documents that "the outbound status stays OBSERVED (refund failure does not revert the outbound)" [8](#0-7)  — confirming the recorded failure is terminal with no downstream recovery.

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}

	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return

		return

		return

	// No excess gas to refund

		return
	}
