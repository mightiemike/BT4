## Title
Uncapped `updateAdaptiveTotalEnergyLimit()` overflow can throw an uncaught `ArithmeticException` inside `Manager.processBlock`, halting block processing - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
The Sherlock report describes a class of bug where a periodic on-chain accounting update (minting emissions once a month) performs unbounded arithmetic before any cap/bound check, and the unchecked result later triggers an explicit error path that "compromises" the block that computes it. The closest analog in java-tron is `EnergyProcessor.updateAdaptiveTotalEnergyLimit()`, which recomputes the network's adaptive energy limit on every block (when adaptive energy is enabled) using multiplication that can overflow, and is invoked directly and unconditionally from `Manager.processBlock()` with no surrounding exception handling for the resulting `ArithmeticException`.

### Finding Description
`EnergyProcessor.updateAdaptiveTotalEnergyLimit()` computes a new `totalEnergyCurrentLimit` by scaling the current limit up or down and then clamping it against an `upperBound` computed as `totalEnergyLimit * adaptiveResourceLimitMultiplier`: [1](#0-0) 

When the "harden calculation" fork (`hardenCalculation()`) is active, the upper bound and the internal `scaleByRate` helper use `BigInteger` arithmetic with `.longValueExact()`, which throws `ArithmeticException` on overflow instead of silently wrapping: [2](#0-1) [3](#0-2) 

This exact overflow behavior is confirmed by the project's own regression tests, which assert that large `TOTAL_ENERGY_LIMIT`/`ADAPTIVE_RESOURCE_LIMIT_MULTIPLIER` combinations deliberately throw `ArithmeticException`: [4](#0-3) 

Crucially, `updateAdaptiveTotalEnergyLimit()` is called unconditionally at the end of every block's processing whenever adaptive energy is enabled, with no cap/bound validation of the inputs (`totalEnergyLimit`, `adaptiveResourceLimitMultiplier`) beforehand, and no `try/catch` around the call in `Manager.processBlock()`: [5](#0-4) 

Both `totalEnergyLimit` (`TOTAL_ENERGY_LIMIT`/`TOTAL_CURRENT_ENERGY_LIMIT`) and `adaptiveResourceLimitMultiplier` (`ADAPTIVE_RESOURCE_LIMIT_MULTIPLIER`) are governance-controlled parameters set via `ProposalService`/committee proposals, not bounded at write time relative to each other for overflow safety: [6](#0-5) [7](#0-6) 

This mirrors the Allora bug class precisely: a periodic (per-block/per-cycle) arithmetic update runs without pre-validating that its inputs stay within safe bounds, and the resulting overflow surfaces as an explicit runtime error deep in the call chain (here `ArithmeticException` from `longValueExact()`, there `ErrNegativeTargetEmissionPerToken`), which is thrown from inside block processing rather than being pre-empted by a cap check.

### Impact Explanation
If committee-approved parameter combinations (or their accumulation via repeated `EXPAND_RATE`/`CONTRACT_RATE` scaling over many blocks) push `totalEnergyCurrentLimit * multiplier` past `Long.MAX_VALUE`, `updateAdaptiveTotalEnergyLimit()` throws an uncaught `ArithmeticException` from within `Manager.processBlock()`. Since this call sits in the mainline block-processing path (after `payReward`, before consensus apply), an uncaught exception here propagates up through block application, causing that node to fail to process/apply the block — a liveness/consensus-halt risk analogous to the "one block ... will be compromised" impact in the original report. This is a state-machine/liveness risk (Medium-class), not a direct fund-loss bug, matching the original's own Medium classification.

### Likelihood Explanation
Triggering this requires the network's governance-controlled `TOTAL_ENERGY_LIMIT` and `ADAPTIVE_RESOURCE_LIMIT_MULTIPLIER` parameters (or their drift via the adaptive expand-rate over time) to reach magnitudes near `Long.MAX_VALUE / multiplier`. These are committee-controlled parameters bounded by `ProposalUtil.ProposalType` ranges (e.g., `TOTAL_ENERGY_LIMIT` documented range up to `100000000000000000`), so a malicious or careless committee proposal, or long-term unchecked adaptive expansion, could realistically approach the overflow boundary — the project's own tests demonstrate the exact overflow trigger values are within the nominally allowed configuration space.

### Recommendation
Validate/clamp `totalEnergyLimit * adaptiveResourceLimitMultiplier` (and any other multiplicative bound computations in `EnergyProcessor`/`ResourceProcessor`) against safe limits before use, either by using saturating arithmetic (clamp to `Long.MAX_VALUE`) instead of throwing, or by rejecting proposal values for `TOTAL_ENERGY_LIMIT`/`ADAPTIVE_RESOURCE_LIMIT_MULTIPLIER` that could cause the product to overflow, and by wrapping `updateAdaptiveTotalEnergyLimit()`'s call site in `Manager.processBlock()` with defensive handling so a single bad parameter combination cannot halt block processing.

### Proof of Concept
The project's own test `testUpdateAdaptiveTotalEnergyLimitOverflowDetected` demonstrates the overflow trigger directly: [8](#0-7) 
Setting `TOTAL_ENERGY_LIMIT`/`TOTAL_ENERGY_CURRENT_LIMIT` to `10_000_000_000_000_000L` with `ADAPTIVE_RESOURCE_LIMIT_MULTIPLIER = 1000` and harden calculation enabled causes `updateAdaptiveTotalEnergyLimit()` to throw `ArithmeticException` — the same call made unconditionally from `Manager.processBlock()` on every block once adaptive energy is enabled and harden calculation is active, with no surrounding exception handling.

  public void updateAdaptiveTotalEnergyLimit() {
    long totalEnergyAverageUsage = dynamicPropertiesStore
        .getTotalEnergyAverageUsage();
    long targetTotalEnergyLimit = dynamicPropertiesStore.getTotalEnergyTargetLimit();
    long totalEnergyCurrentLimit = dynamicPropertiesStore
        .getTotalEnergyCurrentLimit();
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyLimit();

    long result;
    if (totalEnergyAverageUsage > targetTotalEnergyLimit) {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_DENOMINATOR);
    } else {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.EXPAND_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.EXPAND_RATE_DENOMINATOR);
    }
    long upperBound = hardenCalculation()
        ? BigInteger.valueOf(totalEnergyLimit).multiply(BigInteger.valueOf(
            dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier())).longValueExact()
        : totalEnergyLimit * dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier();
    result = min(max(result, totalEnergyLimit, this.disableJavaLangMath()),
        upperBound, this.disableJavaLangMath());

    dynamicPropertiesStore.saveTotalEnergyCurrentLimit(result);
    logger.debug("Adjust totalEnergyCurrentLimit, old: {}, new: {}.",
        totalEnergyCurrentLimit, result);
  }

  private long scaleByRate(long value, long numerator, long denominator) {
    if (hardenCalculation()) {
      return BigInteger.valueOf(value)
          .multiply(BigInteger.valueOf(numerator))
          .divide(BigInteger.valueOf(denominator))
          .longValueExact();
    }
    return value * numerator / denominator;
  }
