### Title
Replay-verification comparator `TransactionOutput::ensure_match_transaction_info` omits state/hot-state/position checkpoint hashes, allowing corrupted state roots to pass chunk-replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the single integrity gate used by the chunk executor's `verify_execution` path (state-sync replay verification) and by the standalone `db-tool replay_on_archive` verifier to confirm that a locally re-executed transaction matches the transaction info recorded in a backup/archive (and thus proven under the accumulator). This comparator checks status, gas used, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, per the TODO left in the code itself.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  validates:
- execution status,
- gas used,
- write-set hash (`state_change_hash`),
- event root hash.

It does not compare `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against anything derived from local re-execution. The comment embedded in the function makes this explicit: [2](#0-1) 

This comparator is the sole verification primitive used in two proof-integrity-sensitive call sites:
1. `ChunkExecutorInner::verify_execution`, which drives `TransactionReplayer::enqueue_chunks` and is used by state-sync's "restore + verify" and general chunk-replay verification path: [3](#0-2) 
2. `storage/db-tool`'s `replay_on_archive` verifier, whose entire purpose is to detect execution/state divergence between archived transaction infos and locally re-executed results: [4](#0-3) 

Because a `TransactionOutput`'s state updates (the actual key/value writes going into the Jellyfish Merkle Tree / state summary / hot-state / native position tree) are not hashed and compared against the recorded `state_checkpoint_hash` (and related checkpoint hashes) by this function, a transaction that produces the correct events, correct gas usage, correct execution status, and even the correct write-set hash, but whose committed *state root derivation* diverges (e.g. due to a bug in state-checkpoint construction, position-state SMT extension logic in `do_state_checkpoint.rs`, or hot-state promotion logic) will still pass `ensure_match_transaction_info`. Note that `state_change_hash` only covers the hash of the write set (the raw key/value diffs of that single transaction) — it does not cover the checkpoint/root-hash fields that summarize accumulated state at a checkpoint boundary, which are produced by a separate, more complex pipeline (`DoStateCheckpoint`, position-state SMT, hot-state SMT) that this comparator never touches.

### Impact Explanation
Both call sites of this function exist specifically to detect state-commitment divergence between an authenticated/backed-up ledger and a freshly re-executed one — i.e., they are the last line of defense for catching non-determinism or storage-schema/replay bugs that would otherwise silently corrupt the durable state root. Because the checkpoint-hash fields are excluded, `replay_on_archive` (used to audit mainnet archives) and the chunk-executor's `verify_execution_mode` (used during full-node/validator chunk replay and restore) can both report a **successful, matching replay** even though the authenticated state root (state summary / hot-state / native-position state) computed locally differs from what is recorded on-chain. This is a proof-integrity/authenticated-response-binding failure: the very tool meant to bind replayed state to the correct root can accept a wrong root as "verified." This meets the "wrong accumulator/proof accepted as valid" and "authenticated API output bound to the wrong … root" criteria in the gate, since a downstream consumer of `replay_on_archive`'s "no errors" result, or of state-sync's chunk-replay-verify success, would trust a state root that has not actually been checked.

### Likelihood Explanation
Likelihood is Medium: it requires an actual local divergence in state-checkpoint/state-root computation (e.g., a bug in `do_state_checkpoint.rs`'s position-state SMT extension logic, hot-state processing, or JMT construction) to exist independently for this gap to matter. The gap itself does not directly cause corruption; it removes the detection mechanism, i.e., it converts a would-be-caught state-integrity bug into an undetected, silently accepted one during replay/restore verification, which is why the code explicitly flags this as a known-unfixed TODO ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS").

### Recommendation
Extend `ensure_match_transaction_info` to also compute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) against values derived from the transaction's/chunk's actual resulting state, before it is considered a match. At minimum, `replay_on_archive` and chunk-executor's `verify_execution` should not report success on any transaction whose checkpoint hashes were skipped, and this should be resolved prior to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production as the existing TODO already indicates.

### Proof of Concept
1. `ChunkExecutorInner::verify_execution` calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` for every replayed transaction: [5](#0-4) .
2. `ensure_match_transaction_info`'s body only asserts on status, gas_used, write_set_hash, and event_root_hash, explicitly skipping checkpoint hashes per its own inline TODO: [6](#0-5) .
3. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` uses the identical comparator as its only pass/fail criterion for archive replay verification: [7](#0-6) .
4. Therefore, given a locally re-executed transaction with correct write-set/events/gas/status but a state-checkpoint/hot-state/position-state root that diverges from what is recorded in the corresponding `TransactionInfo`, both verification tools will report success rather than failure, confirming the comparator's blind spot as an exploitable/undetectable-divergence path rather than a mere style issue.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
