### Title
Division-by-zero DoS in TVM energy-limit accounting due to unguarded `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()` computes a per-account energy limit by dividing by the network-wide `totalEnergyWeight` value read directly from the dynamic-properties store, guarding the zero case only with a Java `assert` statement instead of a real runtime check. Because JVM assertions are disabled by default in production, this "guard" is a no-op, so if `totalEnergyWeight` is ever zero when this TVM-side code path is invoked, the subsequent division throws an `ArithmeticException`, matching the reported bug class of "directly accessing an accounting value assumed to be populated/cached, without a fallback, leading to division by zero."

### Finding Description
Compare the two implementations of the same calculation that exist in the codebase:

- The chain-level `EnergyProcessor.calculateGlobalEnergyLimit()` defensively checks the value before dividing: [1](#0-0) 

- The TVM/actuator-level `RepositoryImpl.calculateGlobalEnergyLimit()`, used during contract execution, only protects the divide with an `assert`, which is stripped/disabled unless the JVM is started with `-ea`: [2](#0-1) 

The pattern is directly analogous to the Suzaku report: a critical accounting divisor (`totalEnergyWeight`, functionally the "total stake"/cache used to compute an operator's/account's share) is read from a store and used in a division without a real fallback path, unlike the sibling implementation (`EnergyProcessor`) that already has the `<= 0` fallback (`return 0`). The `RepositoryImpl` variant is reachable from TVM execution (`ContractState.java`, `VMActuator.java`) which is triggered by ordinary, unprivileged `TriggerSmartContract` transactions broadcast to the network.

### Impact Explanation
If `totalEnergyWeight` is zero at the time a smart-contract execution path invokes `RepositoryImpl.calculateGlobalEnergyLimit()` (e.g., very early after genesis before any account has frozen TRX for energy, or in a private/test network configuration where all energy-frozen balances have been unfrozen), the division throws an uncaught `ArithmeticException`. This would cause the transaction execution (and potentially block processing, since VM execution happens as part of block application) to fail unexpectedly, resulting in a denial-of-service for any transaction path that reaches this energy-limit calculation, until `totalEnergyWeight` becomes non-zero again.

### Likelihood Explanation
Likelihood is low-to-moderate: on established mainnet, `totalEnergyWeight` is virtually always positive because many accounts hold frozen-for-energy balances, so the zero-division condition is unlikely under normal mainnet operation. However, the code contains no defensive check comparable to `EnergyProcessor`'s guard, so the correctness of this path relies entirely on an assumption that is not enforced at runtime (assertions are disabled by default), making it a latent DoS risk analogous to the reported "uncached secondary asset class" issue, particularly for private networks, early-genesis states, or future configuration changes that could zero out `totalEnergyWeight`.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit()` with an explicit runtime check mirroring `EnergyProcessor`'s guarded implementation, returning `0` (or another safe fallback) when `totalEnergyWeight <= 0`, so that the TVM-side and chain-side implementations behave consistently and neither can throw `ArithmeticException` from unprivileged transaction execution.

### Proof of Concept
1. Configure/observe a state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., fresh network state or after all energy-frozen balances are withdrawn).
2. Submit any `TriggerSmartContract` transaction whose execution path invokes `Repository.calculateGlobalEnergyLimit()` (reached via `ContractState`/`VMActuator` during normal TVM energy accounting for the calling account).
3. Since `frozeBalance >= TRX_PRECISION` for that account, execution proceeds past the early return and reaches the division `totalEnergyLimit / totalEnergyWeight` (or `BigInteger` divide) with `totalEnergyWeight == 0`.
4. Because assertions are disabled in the production JVM, the `assert totalEnergyWeight > 0;` check does not fire, and the subsequent division throws `ArithmeticException`, aborting the calculation and the enclosing transaction/block execution flow. [2](#0-1)

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
