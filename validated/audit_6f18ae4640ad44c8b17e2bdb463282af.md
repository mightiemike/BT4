### Title
`assert_eq!` panic in `inner_insert_matured_miner_reward` when two sibling forks mature the same ancestor block with differing poison-microblock reports - ([File: stackslib/src/chainstate/stacks/db/accounts.rs])

### Summary
`StacksChainState::inner_insert_matured_miner_reward` deduplicates matured-reward inserts for a `(parent_block_id, child_block_id)` pair under the assumption that any two forks maturing the same ancestor block must compute an identical `MinerReward`, enforced via `assert_eq!`. This assumption is false because the reward computation in `find_mature_miner_rewards` depends on `get_poison_microblock_report`, which reads fork-scoped Clarity/MARF state that can legitimately differ between two forks sharing the same common-ancestor block.

### Finding Description
The equality the code implicitly relies on is:

`MinerReward(parent_block_id, child_block_id)` computed on fork A == `MinerReward(parent_block_id, child_block_id)` computed on fork B, whenever both forks share the identical ancestor block (same `parent_block_id`/`child_block_id`, i.e. literally the same historical block by hash).

In `inner_insert_matured_miner_reward` [1](#0-0) , when a reward already exists for that key and the newly computed reward is also a "child" reward, the code asserts strict equality: [2](#0-1) 

The reward is computed by `find_mature_miner_rewards`, which calls `get_poison_microblock_report(clarity_tx, reward_height)` [3](#0-2)  and feeds the result into `calculate_miner_reward`, which changes the reward recipient/amount whenever a poison reporter is present [4](#0-3) . `get_poison_microblock_report` reads `db.get_microblock_poison_report(height)` through `clarity_tx.with_clarity_db_readonly`, i.e. fork-scoped Clarity/MARF state tied to the *current* tip being processed [5](#0-4) , not to the ancestor block whose reward is maturing.

Exploit flow:
1. An attacker (unprivileged, single miner/reporter) builds two sibling tenures/forks that share a common ancestor block `B` at depth `MINER_REWARD_MATURITY`.
2. On fork A, the attacker (or anyone) submits a valid `PoisonMicroblock` transaction reporting a microblock fork attributable to `B`'s tenure height, which sets `microblock_poison_report` in fork A's Clarity/MARF state only.
3. Fork B never receives/includes that poison report.
4. When the honest node processes both forks up to the maturation point (a routine occurrence while following competing tips or during a reorg), `find_mature_miner_rewards` computes different `MinerReward` values for the identical `(parent_block_id, child_block_id)` pair: one crediting the original miner, the other crediting the poison reporter with a different `address`/`coinbase` amount.
5. Both computations funnel into `inner_insert_matured_miner_reward` against the shared (non-fork-scoped) `matured_rewards` sqlite table. The second insert attempt finds an existing conflicting child reward and hits `assert_eq!`, panicking and crashing the node process.

Existing guards do not prevent this: the dedup logic in `inner_insert_matured_miner_reward` was designed around the (false) assumption that reward computation for a given ancestor block is fork-independent; `get_poison_microblock_report`/`calculate_miner_reward` are exactly the fork-dependent inputs that break that assumption. No check cross-validates that the poison report is unique/canonical for a given matured block across concurrently tracked forks. Because the assert always either matches or panics (it never allows a divergent record to be silently inserted), the outcome is not a silent double-payment — it is a deterministic crash.

### Impact Explanation
The panic occurs during normal block-processing/reorg-following logic (`inner_insert_matured_miner_reward` is called from `insert_matured_child_miner_reward`/`insert_matured_parent_miner_reward`/`insert_matured_child_user_reward` during block acceptance). Since it is a hard Rust panic, it crashes the node process handling the reward maturation. Any full node that processes both the poisoned and non-poisoned sibling forks for the same ancestor block will hit the identical panic, so the effect is a uniform node crash/halt for every node that observes both branches — not an actual divergent double payment, because the code path never lets two conflicting child rewards coexist silently. This is a liveness-impacting correctness bug in reward bookkeeping, reachable without majority stake, though it manifests as a deterministic crash rather than a state-divergent chain split.

### Likelihood Explanation
Preconditions are attacker-accessible: any participant can mine/extend two sibling tenures forking below `MINER_REWARD_MATURITY` blocks (100 blocks in epoch2.x context) and can submit a legitimate `PoisonMicroblock` transaction to only one of the branches. No signer majority, no privileged role, and no majority hash power is required — only the ability to author two competing tenures off a shared parent and a valid poison-microblock proof (which any node can construct if a miner's own microblock stream forks, including the attacker acting as their own miner). The main cost is normal BTC block-commit fees for the two competing tenures. This is realistically triggerable by a single actor controlling one miner slot who deliberately forks their own microblocks to generate a legitimate poison report on one branch only.

### Recommendation
Do not use `assert_eq!` to hard-fail on divergent matured rewards for the same `(parent_block_id, child_block_id)` key. Instead:
- Make the poison-microblock report keyed/validated against the specific ancestor block being matured (not just fork-local Clarity state at a height), so the same historical block always yields the same poison determination regardless of which descendant fork is currently being processed.
- Alternatively, treat a mismatch as an expected-but-rare event: log an error, prefer the canonical/heaviest fork's computed reward, and skip inserting the conflicting one rather than panicking.

### Proof of Concept
Rust integration test plan (using `TestPeer`/two-fork harness):
1. Build a common tenure ending in block `B` at height `H`.
2. Fork the chain into branch A and branch B at `B`.
3. On branch A, include a valid `PoisonMicroblock` transaction reporting a fork for the microblock stream at `B`'s tenure height.
4. On branch B, do not include any poison report.
5. Advance both branches past `H + MINER_REWARD_MATURITY` so each independently triggers `find_mature_miner_rewards`/`inner_insert_matured_miner_reward` for the same `(parent_block_id, child_block_id)` pair derived from `B`.
6. Assert the equality under test: compute `MinerReward` for branch A vs `MinerReward` for branch B for the same key and show `reward_A.address != reward_B.address` (or `reward_A.coinbase != reward_B.coinbase`) — i.e., the equality `MinerReward(A) == MinerReward(B)` fails.
7. Process both forks against the same underlying chainstate DB and confirm this triggers a panic inside `inner_insert_matured_miner_reward`'s `assert_eq!` (catch via `std::panic::catch_unwind` to assert the panic message contains "FATAL: tried to insert multiple distinct matured parent block reward records").
8. As a secondary check, confirm that absent the bug (i.e., no poison report on either branch), `get_matured_miner_payment` returns exactly one consistent reward for the canonical fork with no panic.
