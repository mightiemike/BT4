### Title
Insufficient base64 length validation in `sanitizeHost` causes uncaught `atob()` exception (`decodeHost`) reachable from unauthenticated request parameters - ([File: packages/apps/shopify-api/lib/auth/decode-host.ts])

### Summary
`sanitizeHost` validates the `host` query parameter with a regex that only checks the base64 character set and trailing `=` padding, but does not enforce that the string length is a multiple of 4 (accounting for padding), as required by the WHATWG `atob()` / forgiving-base64 decode algorithm. A crafted `host` value that satisfies the regex but has invalid length/padding (e.g. `"AAAAA"`) causes `decodeHost` → `atob()` to throw synchronously, and this exception is not caught anywhere in `sanitizeHost` or `decodeHost`.

### Finding Description
`decodeHost` is a one-line wrapper around the platform `atob`: [1](#0-0) 

`sanitizeHost` gates the call to `decodeHost` with only a charset/padding-shape regex, `^[0-9a-zA-Z+/]+={0,2}$`, which accepts strings of any length as long as they end in 0-2 `=` characters — it never checks that `length % 4 === 0`: [2](#0-1) 

Per the WHATWG forgiving-base64 decode algorithm implemented by Node's/browser's `atob`, a string whose length is not a multiple of 4 (after removing padding) throws an `InvalidCharacterError`/`DOMException`. Strings like `"A"`, `"AAAAA"`, or `"AAAAAAA="` pass the `base64regex` test but are invalid base64 length, and will make `atob()` throw. Since `sanitizeHost` calls `decodeHost(sanitizedHost)` with no `try/catch`, and `decodeHost` itself has no error handling, this exception propagates synchronously out of `sanitizeHost`.

This function is reachable directly from unauthenticated request parameters in multiple entry points that are part of the auth/embedded bootstrap flow: `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` [3](#0-2) , the Remix `validateShopAndHostParams` helper used in every `authenticate.admin()` call [4](#0-3) , and the Express `redirectToAuth`/`clientSideRedirect` path used when `embedded=1` [5](#0-4) . None of these call sites wrap `sanitizeHost` in a try/catch, and `sanitizeHost`'s own `throwOnInvalid` mechanism only produces the intended `InvalidHostError` for the "regex doesn't match" case — it does not protect against the `atob` throw, which happens on the line before that check would run.

### Impact Explanation
An attacker can send a single crafted `host` query parameter (no auth required) that passes the char/padding regex but has invalid base64 length, causing an unhandled `DOMException`/`TypeError` to be thrown from deep inside a library utility used on the authentication/embedded-bootstrap path, instead of the expected `InvalidHostError`. Depending on how the surrounding framework (Remix loader, Express async handler) handles synchronous throws vs. rejected promises in async call chains, this can surface as an unhandled promise rejection rather than a normal 500 response, which in Node ≥15 defaults to terminating the process on an unhandled rejection. This corresponds to a DoS-in-auth-handler class impact, though the exact blast radius (single request 500 vs. process crash) depends on the specific caller's error-handling wrapper, which is outside this library's file.

### Likelihood Explanation
Trivial to trigger: no authentication, no secrets, and no non-default configuration are required — a single crafted HTTP GET with `?host=AAAAA` (or any base64-charset string whose length is not a multiple of 4) to any endpoint that calls `sanitizeHost`/`buildEmbeddedAppUrl` will reach the vulnerable code. It is fully repeatable and requires no race conditions or timing.

### Recommendation
Fix the `base64regex` in `sanitizeHost` to also enforce valid base64 length (`length % 4 === 0`), and/or wrap the `decodeHost` call in `sanitizeHost` in a `try/catch` that treats a decode failure the same as a regex mismatch (returning `null` or throwing the typed `InvalidHostError`), so malformed input can never escape as an unhandled low-level exception.

```ts
describe('sanitizeHost malformed base64', () => {
  it('does not throw an uncaught exception for regex-valid but malformed base64', () => {
    const config = testConfig();
    // "AAAAA" matches /^[0-9a-zA-Z+/]+={0,2}$/ but has invalid base64 length
    expect(() => sanitizeHost(config)('AAAAA', true)).not.toThrow(TypeError);
    // Expected: should throw ShopifyErrors.InvalidHostError or return null,
    // not an unhandled DOMException/TypeError from atob().
  });
});
```
Equivalent HTTP-level PoC: `GET /apps/exitiframe?host=AAAAA` (or any Remix/Express route using `validateShopAndHostParams`/`redirectToAuth` with `embedded=1`) — expected: a graceful `InvalidHostError`-driven redirect/400; observed: an uncaught exception from `atob()` inside `decodeHost`.
