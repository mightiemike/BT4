### Title
Missing shop/session-token binding check in `tokenExchange` allows cross-tenant session-storage confusion - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`tokenExchange()` verifies only the cryptographic validity of the session token (signature, `exp`/`nbf`, and optionally `aud`) via `decodeSessionToken`, but it never checks that the token's `dest` claim matches the `shop` parameter supplied by the caller. Both values are attacker-influenced through independent, unrelated channels (`shop` from a query string, `sessionToken` from an `Authorization` header or `id_token` param), and the function's own documentation instructs implementers to source them separately.

### Finding Description
In `tokenExchange` [1](#0-0) , the function calls `decodeSessionToken(config)(sessionToken)` which only validates the JWT signature, expiry window, and (optionally) the `aud` (API key) claim [2](#0-1) . It discards the returned payload entirely and never compares the token's `dest`/`iss` (the shop origin the token was minted for) to the `shop` argument. The `shop` value used to build the token endpoint URL (`https://${cleanShop}/admin/oauth/access_token`) and to construct the returned `Session` object comes solely from the caller-supplied `shop` parameter, sanitized only for format via `sanitizeShop` [3](#0-2) .

The public documentation for this API instructs implementers to derive `shop` from `req.query.shop` and `sessionToken` independently from the `Authorization` header or `id_token` URL param [4](#0-3) , meaning nothing in the documented, intended usage pattern ties the two values together. This mirrors the reported bug class: a security-relevant computation (which shop's OAuth endpoint to call and which shop the resulting `Session` is stamped with) is derived from an unvalidated combination of inputs, without a consistency check tying the "expected" value (the shop bound to the verified credential) to the value actually used.

### Impact Explanation
If a host application follows the documented pattern and does not itself re-derive/validate `shop` from the verified token's `dest`, an app endpoint that accepts a `shop` query parameter and an `Authorization`-header session token from an anonymous/merchant-controlled request could be induced to call the token exchange endpoint for a `shop` that does not match the session token's true origin. Depending on how the resulting `Session` (stamped with the caller-chosen `shop`) is subsequently persisted via `SessionStorage.storeSession`, this can pollute session storage with a session keyed to the wrong shop, or cause an app to associate a valid credential/access token exchange with an unintended tenant, leading to cross-tenant session confusion in the session-storage layer.

### Likelihood Explanation
The frameworks in this repo (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) that call the underlying `tokenExchange` internally always derive `shop` from the verified token's `dest` claim rather than from an untrusted query parameter [5](#0-4) [6](#0-5) , so the built-in integrations are not directly exploitable through this path. However, the underlying `shopify-api` library function itself performs no defense-in-depth check, and its own reference documentation explicitly demonstrates the vulnerable pattern of sourcing `shop` and `sessionToken` from unrelated, independently-controlled request fields, making misuse plausible for any app built directly against `shopify.auth.tokenExchange` following the documented example.

### Recommendation
In `tokenExchange`, after decoding and verifying the session token, parse the `dest` (or `iss`) claim and assert that its hostname matches the sanitized `shop` parameter before proceeding to call the token exchange endpoint or before stamping the returned `Session`; throw an `InvalidJwtError`/similar if they diverge. Update the reference documentation to derive `shop` from the verified token payload rather than from `req.query.shop` directly.

### Proof of Concept
1. App exposes a token-exchange endpoint following the documented pattern:
```ts
app.get('/auth', async (req, res) => {
  const shop = shopify.utils.sanitizeShop(req.query.shop, true);
  const sessionToken = getSessionTokenHeader(req); // Authorization: Bearer <token>
  const {session} = await shopify.auth.tokenExchange({sessionToken, shop, requestedTokenType: RequestedTokenType.OfflineAccessToken});
  await sessionStorage.storeSession(session);
});
```
2. A user with a legitimately-issued session token for `attacker-shop.myshopify.com` requests `GET /auth?shop=victim-shop.myshopify.com` with `Authorization: Bearer <attacker-shop-token>`.
3. `decodeSessionToken` only validates signature/expiry/audience of the token — it never checks that the token's `dest` (`attacker-shop.myshopify.com`) matches the supplied `shop` (`victim-shop.myshopify.com`) — so `tokenExchange` proceeds to call `https://victim-shop.myshopify.com/admin/oauth/access_token` with the attacker's subject_token and, if this call is accepted by Shopify's token endpoint, returns/stores a `Session` object stamped `shop: 'victim-shop.myshopify.com'` in the app's session storage, causing cross-tenant session-storage confusion. export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
