### Title
Unbounded single-threaded BN128Pairing precompile execution (no in-loop CPU-time checks) allows CPU-bound DoS via rate-limit-compliant `triggerConstantContract`/`eth_call` requests - (File: `crypto/src/main/java/org/tron/common/crypto/zksnark/PairingCheck.java`)

### Summary
The `BN128Pairing` precompile's `execute()` runs a synchronous, unbounded-duration loop calling `PairingCheck.run()` (Miller loop + final exponentiation over `Fp2`/`Fp12` `BigInteger` arithmetic) for every pair in the input, with no CPU-time check anywhere inside that loop. Because TRON's only CPU-time enforcement (`Program.checkCPUTimeLimit`) is invoked once per top-level EVM opcode — before, not during, a precompiled-contract call — a single `CALL` into address `0x8` can consume the full deadline-unconstrained wall-clock time to process up to the energy-bounded number of pairs, letting an unauthenticated caller tie up an RPC worker thread with pure CPU work for seconds, and do so repeatedly at a rate the count-based rate limiter permits.

### Finding Description
`triggerConstantContract` (HTTP `TriggerConstantContractServlet`, gRPC `RpcApiService.WalletApi#triggerConstantContract`) reaches `Wallet.callConstantContract` → `VMActuator` → `Program.callToPrecompiledAddress`, which for the `BN128Pairing` address (`0x8`) simply calls: [1](#0-0) 

Inside `PrecompiledContracts.BN128Pairing.execute()`, the number of pairs is derived purely from the input length (`data.length / 192`), and every pair is added and processed synchronously: [2](#0-1) 

`PairingCheck.run()` then executes a `millerLoop()` (a 254-bit-loop of `Fp12`/`Fp6`/`Fp2` `BigInteger` field arithmetic) per pair plus a `finalExponentiation()`, with zero interruption points: [3](#0-2) 

The only CPU-time guard in the VM, `Program.checkCPUTimeLimit`, is invoked exclusively in the opcode dispatch loop, **before** `op.execute(program)` runs — i.e., before the `CALL` opcode is even dispatched to the precompile, never during it: [4](#0-3) 

So once `BN128Pairing.execute()` starts, `constantCallTimeoutMs`/`vmShouldEndInUs` cannot abort it mid-flight. Other precompiles are aware of this class of problem and defend against it explicitly — `ValidateMultiSign` calls `MUtil.checkCPUTime()` inside its per-signature loop — but `BN128Pairing` has no equivalent check, showing the gap is a real oversight rather than an accepted design constraint.

The only bound on the loop's size is energy: for constant calls, `energyLimit = maxEnergyLimit` (default `100_000_000`, see `CommonParameter.maxEnergyLimitForConstant`), and Istanbul pricing charges `34000` energy per pair plus a `45000` base: [5](#0-4) [6](#0-5) 

This allows roughly ⌊(100,000,000−45,000)/34,000⌋ ≈ 2,939 pairs per single constant call, i.e. an input of ≈564 KB (192 bytes/pair), well within the default HTTP (`maxMessageSize=4194304`) and gRPC (`maxMessageSize=4194304`) body-size limits: [7](#0-6) [8](#0-7) 

The rate limiters guarding these endpoints are strictly request-count-based (token-bucket QPS via Guava `RateLimiter`, or concurrency-permit based), with no notion of CPU cost per request: [9](#0-8) [10](#0-9) 

Thus, an attacker who stays under the configured/default QPS ceiling (`global.qps=50000`, `global.ip.qps=10000`, default per-endpoint `qps=1000`) can still send N parallel maximum-pair-count `triggerConstantContract`/`eth_call` requests, each occupying a worker thread (gRPC executor pool sized `availableProcessors/2` by default, or the HTTP servlet container thread pool) for a substantial, uninterruptible CPU-bound duration, none of which is charged to any account balance since constant calls never broadcast/consume TRX resources.

### Impact Explanation
This maps to the "DoS via RPC-API" bounty class: sustained saturation of RPC/HTTP worker threads with CPU-bound, non-preemptible work degrades or starves other legitimate RPC handling (and, if gRPC/HTTP threads compete for CPU with the block-processing/witness thread, potentially block production latency) — all while the attacker's request rate stays within any configured count-based rate limit and costs the attacker nothing (constant calls are free of TRX fees/energy debits).

### Likelihood Explanation
- No privileged role required: any anonymous HTTP/gRPC/JSON-RPC client can call `triggerconstantcontract`/`eth_call` if `supportConstant`/`estimateEnergy` is enabled (the intended, documented purpose of these APIs).
- No fee is paid, no signature or funded account is required for `triggerConstantContract` (it does not need to be broadcast).
- The request stays within default size limits (≈564 KB, within the 4 MB HTTP/gRPC body caps) and within default rate limits (a handful of concurrent requests per second is far below the default 1000 qps per-endpoint / 50000 global qps).
- Feasibility depends on how much wall-clock time this unoptimized, pure-`BigInteger` pairing implementation (ported from ethereumJ) actually takes for ~2,939 pairs; this needs to be empirically measured on target hardware, but the code path itself is confirmed uninterruptible regardless of the measured duration.
- Repeatable indefinitely; each request is independent and stateless.

### Recommendation
Add periodic CPU-time/deadline checks inside `PairingCheck.run()` (and ideally inside `millerLoop()`/`calcEllCoeffs()`) similar to the `MUtil.checkCPUTime()` pattern already used in `ValidateMultiSign`, so that a long-running precompile call can be aborted once `vmShouldEndInUs` is exceeded rather than only being checked between whole opcodes. Additionally, consider capping the maximum number of pairs accepted by `BN128Pairing` for constant/view calls independent of the energy budget, and/or making rate limiters CPU-time-aware (e.g., a global concurrency/CPU-budget semaphore for constant-call execution) rather than purely count-based.

### Proof of Concept

```
  "fee_limit": 1000000000

```
Expected observation to confirm: measure wall-clock time of the VM execution for this single request (e.g., via `result.getEnergyUsed()`/server logs) and confirm it consumes CPU on the handling thread continuously without any `OutOfTimeException` being thrown mid-execution even when `constantCallTimeoutMs` is configured to a low value (e.g. 50 ms) — demonstrating the deadline is not enforced inside `BN128Pairing.execute()`/`PairingCheck.run()`. A JUnit test can invoke `PrecompiledContracts.BN128Pairing.execute()` directly with a large multiple-of-192-byte input and assert on elapsed `System.nanoTime()` versus `CommonParameter.getInstance().getConstantCallTimeoutMs()` to show no exception is thrown despite exceeding the configured deadline.

```java
    @Override
    public Pair<Boolean, byte[]> execute(byte[] data) {

      if (data == null) {
        data = EMPTY_BYTE_ARRAY;
      }

      // fail if input len is not a multiple of PAIR_SIZE
      if (data.length % PAIR_SIZE > 0) {
        return Pair.of(false, EMPTY_BYTE_ARRAY);
      }

      PairingCheck check = PairingCheck.create();

      // iterating over all pairs
      for (int offset = 0; offset < data.length; offset += PAIR_SIZE) {

        Pair<BN128G1, BN128G2> pair = decodePair(data, offset);

        // fail if decoding has failed
        if (pair == null) {
          return Pair.of(false, EMPTY_BYTE_ARRAY);
        }

        check.addPair(pair.getLeft(), pair.getRight());
      }

      check.run();
      int result = check.result();

      return Pair.of(true, new DataWord(result).getData());
    }
```
