## Title
Unbounded full-table scan of `PendingInbounds` on every inbound ballot terminal transition enables an unprivileged deposit-flood DoS - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
`afterInboundBallotTerminal` performs a full, unindexed `Walk` over the entire `PendingInbounds` collection on **every** inbound ballot terminal transition (PASSED/REJECTED/EXPIRED), just to find the one entry whose variant carries the finalizing `ballotID`. This is the same bug class as the reported `runExecutionHooks`/`runValidationHooks` issue: an attacker-growable set is iterated in full inside a hot, consensus-critical path, with cost scaling linearly (and, across many concurrent finalizations, effectively quadratically) with the number of pending entries. Because any unprivileged external-chain user can cheaply create new distinct inbound deposit events, an attacker can inflate `PendingInbounds` and make every subsequent `MsgVoteInbound` finalization progressively more expensive for honest Universal Validators.

### Finding Description
`x/uexecutor/keeper/msg_vote_inbound.go`'s `VoteInbound` records every voter's vote in a per-utx `PendingInbounds` entry via `RecordInboundVote` [1](#0-0) , then calls `VoteOnInboundBallot`, which ultimately calls into `x/uvalidator`'s `VoteOnBallot` → `CheckIfFinalizingVote` → `MarkBallotFinalized`, firing the registered `BallotHooks.AfterBallotTerminal` callback [2](#0-1) .

The `x/uexecutor` implementation of that hook, `afterInboundBallotTerminal`, cannot reverse the one-way ballot ID hash back to a UTX key, so it scans **every** entry in `PendingInbounds` (an `sdk.collections.Map`) with `Walk`, checking each variant's `BallotId`:

```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [3](#0-2) 

The code comment explicitly assumes "the pending set is small and transient" [4](#0-3) , but nothing enforces that assumption. `PendingInbounds` entries are created purely from unprivileged, source-chain inbound events observed and voted on by UVs — any external user can submit an arbitrary number of distinct low-value/dust deposits on a connected external chain (bounded only by that chain's own gas cost, which can be negligible on cheap L2s/testnets), each producing a new `PendingInboundEntry` key (`GetInboundUniversalTxKey`) that persists until its ballot reaches a terminal state (finalized or expired after `DefaultExpiryAfterBlocks`).

If the attacker submits inbound events faster than UVs can drive them to quorum/expiry, `PendingInbounds` grows unbounded, and **every** terminal transition thereafter (which fires on the normal, honest-validator vote path) pays an O(n) full-map scan. With many concurrently open ballots this becomes effectively O(n²) work across a burst of finalizations, all executed synchronously inside `MsgVoteInbound` transaction processing on every honest node.

This mirrors the reported bug class precisely: an `EnumerableSet`/collection whose size is attacker-controlled is iterated in full inside a state-changing, consensus-critical code path, with no upper bound on the set size and no indexed lookup structure (e.g., a secondary `ballotID -> utxKey` index) to avoid the scan.

### Impact Explanation
This is a compute-amplification / node-performance denial-of-service vector reachable by any unprivileged external-chain user without needing malicious validators, malicious relayers, or any privileged role. As `PendingInbounds` grows, ordinary honest-UV `MsgVoteInbound` processing (which is gasless per `app/txpolicy/gasless.go`'s allowlist [5](#0-4) ) becomes increasingly expensive to execute for every node, since the hook fires synchronously in-block for every terminal ballot. This degrades block processing time/throughput chain-wide and can materially slow or stall UV consensus on inbound processing — a legitimate in-scope, non-network-level DoS per the allowed-impact gate (reachable via ordinary user deposit submission alone, with honest validators/nodes).

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs to sustain enough distinct pending inbound events to grow the set faster than UVs finalize/expire them, which costs real (if potentially small) gas/fees on the external source chain per event, and is bounded further by chain-level enablement/config (`IsChainInboundEnabled`, `GetTokenConfig`) which must exist for a chain/asset pair. However, no protocol-side rate limit, cap, or fee is imposed on the number of distinct pending inbound entries, so a moderately funded attacker on a cheap external chain can realistically inflate this set.

### Recommendation
Avoid the full-collection scan in `afterInboundBallotTerminal`. Maintain a secondary index mapping `ballotID -> utxKey` (populated in `RecordInboundVote` alongside `PendingInbounds`) so the hook can do an O(1) lookup instead of `Walk`-ing the entire `PendingInbounds` map. Additionally consider bounding the maximum number of concurrently tracked `PendingInbounds`/variants (e.g., per source chain) or tightening ballot expiry to limit worst-case set growth.

### Proof of Concept
1. An external, unprivileged attacker submits N distinct low-value deposit transactions on an enabled source chain (distinct `tx_hash`/`log_index` pairs), each observable and vote-able by UVs, faster than existing ballots reach quorum/expiry.
2. Each deposit causes `RecordInboundVote`/`VoteOnInboundBallot` to create a new `PendingInboundEntry` in `PendingInbounds` [1](#0-0) , growing the collection to size N.
3. As honest UVs continue voting normally and any ballot reaches a terminal state (PASSED/REJECTED/EXPIRED), `MarkBallotFinalized`/`MarkBallotExpired` fires `AfterBallotTerminal` → `afterInboundBallotTerminal`, which performs a full `Walk` over all N `PendingInbounds` entries [6](#0-5) .
4. Repeat for every subsequent terminal event while N remains large: each `MsgVoteInbound` that happens to finalize a ballot now costs O(N) work purely from this hook, degrading per-tx and per-block processing time chain-wide, with no admin/validator misbehavior required.

func (k Keeper) MarkBallotFinalized(ctx context.Context, id string, status types.BallotStatus) error {
	if status != types.BallotStatus_BALLOT_STATUS_PASSED && status != types.BallotStatus_BALLOT_STATUS_REJECTED {
		return fmt.Errorf("invalid finalization status: %v", status)
	}

	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as finalized",
		"ballot_id", id,
		"final_status", status.String(),
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.FinalizedBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = status
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, status)
	return nil
}

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
```
