## Finding

### Title
Unbounded mmap write in append-only storage backend can exceed grown file region and corrupt/crash node storage - (File: crates/apollo_storage/src/mmap_file/mod.rs)

### Summary
`apollo_storage`'s `MMapFile`/`FileHandler` backend maps a file with a virtual mapping size of `config.max_size` (default 1 TB) up front, but only physically grows (`set_len`) the underlying file lazily, in `growth_step` increments, whenever the tracked logical `offset` gets within `max_object_size` of the currently grown `size`. The `Writer::append` implementation writes serialized bytes directly into the mmap'd region via a raw slice `mmap_file.mmap[offset..]` / `mmap_slice[..len]` **before** any bound is enforced against `len`, relying entirely on an undocumented, code-unchecked precondition stated only in a doc comment: "the serialized data is not larger than the maximum object size." [1](#0-0) [2](#0-1) 

This mirrors the CVE-2021-28026 bug class: a size/count value derived from input data is used to index/write into a buffer without validating it fits inside the region that was actually reserved/backed, relying on an implicit invariant rather than an explicit check.

### Finding Description
- The mmap is created with a fixed virtual length of `config.max_size`, decoupled from the file's real backing size: [3](#0-2) 
- The real file size is grown only by `growth_step`, and only when `mmap_file.size < offset + mmap_file.config.max_object_size`: [4](#0-3) 
- `append()` computes `serialized`/`len` from caller-supplied data, slices `mmap_file.mmap[offset..]` (bounded only by the 1 TB virtual mapping, so it will *not* panic), and copies `len` bytes into it, then only afterwards calls `grow_file_if_needed` for the *next* write: [5](#0-4) 

If any single serialized value (`len`) written through this path exceeds `max_object_size` (the only bound the growth logic assumes), the write can land past the currently `set_len`-grown, physically-backed portion of the file while still being inside the mmap's virtual `max_size` window. On Linux, writing into an mmap'd region beyond the actual file length raises `SIGBUS`, crashing the process — the memory-safety-adjacent equivalent of the heap-buffer-overflow behavior in the reported CVE (an out-of-bounds write caused by an unchecked, attacker-influenced size value).

The values persisted through this generic `FileHandler<V>::append` path include block bodies/transaction outputs (events, messages, calldata echoes) and contract classes, whose serialized sizes are a function of data ultimately derived from submitted transactions (e.g., number/size of emitted events, L2-to-L1 messages, or declared class payloads). Contract-class size is bounded by `ClassManagerConfig::max_compiled_contract_class_object_size` (default ~3.9 MB) which is comfortably below the mmap default `max_object_size` (256 MB), so classes are unlikely to trigger this in default configuration. However, the guarantee that *every* value type stored via this generic append path (in particular full transaction outputs, which aggregate potentially many events/messages from a single transaction) never exceeds `max_object_size` is not enforced in `mmap_file/mod.rs` itself — it is purely a documented caller obligation, which is a fragile invariant to maintain across all current and future callers of `Writer<V>`.

### Impact Explanation
If any writer of this generic append path is fed a value whose serialization exceeds `max_object_size`, the store can write past the physically backed file region into an mmap-only-virtual area, causing a `SIGBUS` crash (or, at minimum, corruption) on every honest node that persists the corresponding block via this storage layer. Because this triggers deterministically for any node running the identical storage code against the identical block/data, this is not a single-node DoS but a class of bug that can produce a synchronized halt across honest nodes trying to confirm/persist the block — i.e., "a network unable to confirm new transactions."

### Likelihood Explanation
Exploitability depends on whether any concrete caller of `Writer<V>::append` can be driven, by a single submitted transaction/declared class, to produce a serialized value whose length exceeds the configured `max_object_size` (256 MB by default) without that being rejected earlier by a stricter per-type limit (as is the case for contract classes today). This requires confirming, for the specific value types stored this way (e.g., full transaction outputs including events, per the `StorageSerde` implementations near `apollo_storage/src/serialization`), that no other admission-time limit already caps their size below `max_object_size`. The report should be treated as a structural/precondition-enforcement gap rather than confirmed with a concrete end-to-end trigger, since the exact enforcement chain for every `V` type going through this path was not fully traced.

### Recommendation
- Enforce `len <= config.max_object_size` explicitly inside `FileHandler::append` (returning an error rather than silently writing) instead of relying on an undocumented caller invariant. [2](#0-1) 
- Ensure the mmap's growth check accounts for the actual `len` of the object about to be written, not just a fixed assumed upper bound (`max_object_size`), e.g., grow before writing based on the real serialized length.
- Audit all `StorageSerde`/`ValueSerde` implementations used with this backend (transaction outputs, events, classes, state diffs) to confirm each is bounded, at gateway/blockifier admission time, strictly below `max_object_size`.

### Proof of Concept
Conceptual reproduction (requires confirming a concrete unbounded `V` type in this storage path):
1. Construct/submit a transaction (or sequence of transactions in a block) that maximizes serialized `TransactionOutput` size (e.g., via many emitted events/L2-to-L1 messages) up to whatever resource/fee limits allow.
2. If the resulting serialized object size for that value exceeds `MmapFileConfig::max_object_size` (default 256 MB) while the storage layer's `growth_step`/`size` bookkeeping has only pre-grown for a `max_object_size`-sized write, `FileHandler::append` writes past the physically backed file region within the virtual `max_size` mmap window.
3. On Linux, this triggers `SIGBUS`, crashing the process for any honest node persisting this block through this code path.

impl<V: ValueSerde> FileHandler<V, RW> {
    fn grow_file_if_needed(&mut self, offset: usize) {
        let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
        if mmap_file.size < offset + mmap_file.config.max_object_size {
            debug!(
                "Attempting to grow file. File size: {}, offset: {}, max_object_size: {}",
                mmap_file.size, offset, mmap_file.config.max_object_size
            );
            mmap_file.grow();
        }
    }
}

impl<V: ValueSerde + Debug> Writer<V> for FileHandler<V, RW> {
    fn append(&mut self, val: &V::Value) -> LocationInFile {
        trace!("Inserting object: {:?}", val);
        let serialized = V::serialize(val).expect("Should be able to serialize");
        let len = serialized.len();
        let offset;
        {
            let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
            offset = mmap_file.offset;
            trace!("Inserting object at offset: {}", offset);
            let mmap_slice = &mut mmap_file.mmap[offset..];
            mmap_slice[..len].copy_from_slice(&serialized);
            mmap_file
                .mmap
                .flush_async_range(offset, len)
                .expect("Failed to asynchronously flush the mmap after inserting");
            mmap_file.offset += len;
            mmap_file.should_flush = true;
        }
        let location = LocationInFile { offset, len };
        self.grow_file_if_needed(location.next_offset());
        location
    }
