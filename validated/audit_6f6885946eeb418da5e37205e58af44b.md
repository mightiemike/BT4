## Finding: `save_transactions_impl` in the backup/kv-replay path never identifies checkpoint boundaries, silently corrupting the state-usage/index split used to compute state during restore

### Summary
`storage/aptosdb/src/backup/restore_utils.rs::save_transactions_impl` (used by `RestoreHandler::save_transactions_and_replay_kv`, exercised by `TransactionRestoreBatchController::replay_kv` in `storage/backup/backup-cli/src/backup_types/transaction/restore.rs:604`) always passes an empty `all_checkpoint_indices: vec![]` to `StateUpdateRefs::index_write_sets`, instead of computing it from the `TransactionInfo`s' `has_state_checkpoint_hash()` the way the equivalent, "correct" call site (`replay_write_sets_after_snapshot` in `storage/aptosdb/src/state_store/mod.rs:936-948`) does.

### Finding Description
`StateUpdateRefs::index_write_sets`/`::index` (`storage/storage-interface/src/state_store/state_update_refs.rs:156-233`) splits the incoming per-version write-set updates into two batches based on `all_checkpoint_indices`:
- `for_last_checkpoint` — updates up to and including the last checkpoint version in the chunk,
- `for_latest` — updates after the last checkpoint to the end of the chunk. [1](#0-0) 

This split matters: `for_last_checkpoint_batched()` is treated as the state as-of a durable state-checkpoint version (used for usage accounting/state-summary snapshotting at that version), while `for_latest_batched()` represents un-checkpointed in-flight state. The correct restore code path, `replay_write_sets_after_snapshot`, computes `all_checkpoint_indices` by scanning the actual `TransactionInfo`s for `has_state_checkpoint_hash()`: [2](#0-1) 

But the backup/restore `kv_replay` code path (`save_transactions_impl`) hard-codes `vec![]` regardless of what the actual `txn_infos` for that chunk say: [3](#0-2) 

`txn_infos` (which do carry `state_checkpoint_hash()`, see `TransactionInfoListWithProof::state_checkpoint_hashes` at `types/src/proof/definition.rs:901-906`) is available in this same function but is never consulted for this purpose — it's only used to save transaction-info records and populate the accumulator.

As a direct consequence, every chunk replayed through `save_transactions_and_replay_kv` (used by `backup-cli`'s `replay_kv`, which is the code path used to fast-forward the KV DB during backup restore, `storage/backup/backup-cli/src/backup_types/transaction/restore.rs:553-618`) is treated by `StateUpdateRefs::index` as if it contains **no checkpoint at all** — i.e. it always goes down the `for_latest`-only branch (`state_update_refs.rs:207-219`), even when a checkpoint transaction is actually within the chunk. This shifts the boundary between "checkpointed"/"latest" version windows that downstream logic (`state_store.calculate_state_and_put_updates` → `put_stats_and_indices` → stale-index/usage accounting) relies on for computing per-version state usage and stale-index entries.

### Impact Explanation
The versioned usage/state-summary numbers that are calculated and persisted for a given checkpoint version (via `for_last_checkpoint_batched()`) are the numbers used later for state-storage-usage accounting (`get_state_storage_usage`) and hot-state/LRU indexing at restart. If those numbers are computed with the wrong batching boundary during a `kv_replay`-based restore, the restored node's derived committed-state bookkeeping (usage stats, stale-index attribution) for the affected versions diverges from what a node that executed the transactions live would have computed — a state-integrity divergence localized to nodes doing backup-restore with `kv_replay`/`replay_kv`. Because this affects the deterministic state derived at commit/restore time (not just an in-memory cache), it is a genuine state-integrity concern rather than a display-only bug.

### Likelihood Explanation
This code path (`kv_replay=true`) is only reachable via the backup-restore tooling's `replay_kv` mode (`storage/backup/backup-cli/.../restore.rs`), which is invoked deliberately by an operator restoring a node/backup, not by mainnet consensus execution. It requires the restore to include a chunk that spans an actual checkpoint boundary for the divergence to manifest (which is common for larger backup chunks). I could not fully verify within the available tool budget whether the resulting usage/stale-index divergence is later caught by a root-hash/consistency check during restore (e.g., JMT restore chunk verification against `expected_root_hash`) that would abort the restore, which would reduce this to a restore-only correctness bug rather than a silently-accepted wrong committed state. This uncertainty means I cannot confirm end-to-end high/critical impact with confidence.

### Recommendation
In `storage/aptosdb/src/backup/restore_utils.rs::save_transactions_impl`, compute `all_checkpoint_indices` from `txn_infos` (mirroring `replay_write_sets_after_snapshot`) via `txn_infos.iter().positions(TransactionInfo::has_state_checkpoint_hash).collect()`, and pass that into `StateUpdateRefs::index_write_sets` instead of the hard-coded `vec![]`.

### Proof of Concept
Not independently verified end-to-end (would require constructing a restore chunk containing a checkpoint transaction, running `save_transactions_and_replay_kv`, and diffing resulting `StateStorageUsage`/stale-index records against a live-executed equivalent) — flagging this as the strongest candidate found, but noting the verification gap above regarding whether a later root-hash check masks the effect.
