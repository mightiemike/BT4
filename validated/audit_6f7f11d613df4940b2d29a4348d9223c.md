### Title
Missing frozenDuration bounds/overflow check in TVM native FreezeBalanceProcessor allows expireTime overflow - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java)

### Summary
The reported Aragon bug is a `uint64` overflow in an unvalidated duration parameter (`_period`) used to compute a future timestamp (`openDate + _period`) without `SafeMath`. The strongest analog in java-tron is `FreezeBalanceProcessor`, the native-contract implementation of `freezeBalance` reachable from unprivileged TVM contract execution via `PrecompiledContracts.java`. Unlike its legacy actuator counterpart `FreezeBalanceActuator`, this processor never bounds-checks the caller-supplied `frozenDuration`, and computes `expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD` with plain `long` arithmetic that silently overflows/wraps, exactly the bug class described in the report.

### Finding Description
`FreezeBalanceProcessor.validate()` checks `frozenBalance`, `frozenCount`, `resourceType`, and the receiver address, but contains no check at all on `frozenDuration`: [1](#0-0) 

`execute()` then computes the expire time by multiplying the unchecked, caller-controlled `frozenDuration` by `FROZEN_PERIOD` and adding it to the current block timestamp: [2](#0-1) 

This `expireTime` is then persisted into account frozen state via `setFrozenForBandwidth`/`setFrozenForEnergy`: [3](#0-2) 

Compare this to the legacy (non-TVM) `FreezeBalanceActuator.validate()`, which explicitly bounds `frozenDuration` between `minFrozenTime` and `maxFrozenTime` before allowing the freeze: [4](#0-3) 

The codebase is also aware of exactly this overflow class and has already patched it elsewhere: `AssetIssueActuator` explicitly guards `startTime + frozenDays * FROZEN_PERIOD` against overflow using `StrictMathWrapper.addExact` (post fork `VERSION_4_8_1`), throwing `"Start time and frozen days would cause expire time overflow"` if the addition would overflow: [5](#0-4) 

`FreezeBalanceProcessor` received no equivalent hardening. Because Java `long` arithmetic wraps silently on overflow (analogous to pre-SafeMath Solidity `uint` behavior in the original report), a sufficiently large `frozenDuration` supplied through the TVM precompile can cause `nowInMs + frozenDuration * FROZEN_PERIOD` to overflow, yielding an `expireTime` that is arbitrary (including negative or far in the past), which corrupts the account's frozen/expire-time invariant used for resource accounting.

`FreezeBalanceProcessor` is confirmed to be wired into the TVM precompiled-contract dispatch (6 references in `PrecompiledContracts.java`), meaning it is reachable from ordinary, unprivileged smart-contract execution — not a privileged/administrative code path. [6](#0-5) 

### Impact Explanation
An `expireTime` corrupted by overflow directly affects on-chain resource accounting: `setFrozenForBandwidth`/`setFrozenForEnergy` store the (wrapped) expire time, and total network/energy weight is updated based on the frozen amount: [7](#0-6) 
An attacker-controlled wraparound could set an expire time in the past, allowing immediate unfreeze/withdraw of resources that should be time-locked, or could set an expire time far beyond intended bounds, effectively locking funds/resources indefinitely. Since frozen balances feed into total bandwidth/energy weight (a shared, chain-wide accounting metric used for resource pricing across all accounts), state divergence here has a network-wide accounting impact, not just a per-account one.

### Likelihood Explanation
Reachability requires only an ordinary account/contract able to invoke the TVM `freezeBalance` precompile with an attacker-chosen `frozenDuration`; no privileged role is needed, matching the "unprivileged-user analog" requirement. The only mitigating factor is uncertainty (not fully verified within available tool calls) about whether this specific `freezeBalance` native contract path is still an actively enabled feature versus one gated behind `supportUnfreezeDelay`/freeze-v2 flags (the standalone `FreezeBalanceActuator` explicitly rejects freeze v1 once freeze-v2/`supportUnfreezeDelay` is enabled — see line 271-274 of `FreezeBalanceActuator.java`, code not fully shown above). If the TVM-callable `FreezeBalanceProcessor` path is likewise gated off on current networks where freeze-v2 is active, exploitability would be reduced to legacy/older chain configurations only. This gating status could not be conclusively confirmed with the remaining tool budget.

### Recommendation
Add an explicit bounds check on `frozenDuration` in `FreezeBalanceProcessor.validate()` (mirroring `FreezeBalanceActuator`'s `minFrozenTime`/`maxFrozenTime` check), and/or use overflow-safe arithmetic (e.g. `Math.addExact`/`LongMath.checkedAdd`, as already used in `WithdrawExpireUnfreezeProcessor` and `AssetIssueActuator`) when computing `expireTime = nowInMs + frozenDuration * FROZEN_PERIOD`, throwing `ContractValidateException` on overflow instead of silently wrapping.

### Proof of Concept
1. Deploy/invoke a smart contract that calls the TVM `freezeBalance` precompile (dispatched to `FreezeBalanceProcessor`) with `frozenBalance` set to the minimum allowed (≥ 1 TRX) and `frozenDuration` set to a very large value such that `frozenDuration * FROZEN_PERIOD` overflows `Long.MAX_VALUE` when added to `nowInMs` (e.g. `frozenDuration ≈ Long.MAX_VALUE / FROZEN_PERIOD`).
2. `FreezeBalanceProcessor.validate()` performs no check that would reject this value (contrast with `FreezeBalanceActuator.validate()` lines 203-214, which is bypassed since this is the TVM-native code path).
3. `FreezeBalanceProcessor.execute()` computes `expireTime = nowInMs + frozenDuration * FROZEN_PERIOD` (line 77), which overflows/wraps to an unintended value (e.g., negative or small), and persists it via `accountCapsule.setFrozenForBandwidth(...)`/`setFrozenForEnergy(...)`.
4. The account's frozen balance now carries a corrupted `expireTime`, which can be immediately eligible for unfreeze (if wrapped to a value ≤ current time) despite intent to lock for a long duration, or conversely lock the balance for an unintended duration — demonstrating the same overflow-driven invalid-state root cause as the original Aragon `setPeriod` finding.

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(

    }
