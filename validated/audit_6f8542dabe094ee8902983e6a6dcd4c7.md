### Title
Webhook HMAC validation does not bind the signature to the claimed shop domain, allowing cross-tenant webhook forgery - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`validateHmacFromRequestFactory` computes and checks the webhook HMAC using only the raw request body, never the `X-Shopify-Shop-Domain` (or `shopify-domain`) header that identifies which shop the webhook is supposedly for. Because the same `apiSecretKey` is shared across every shop that installs a given app, an attacker who controls any shop where the app is installed can obtain a validly HMAC-signed webhook body from Shopify and then replay it to the app's webhook endpoint while substituting the `domain` header for a victim shop that also has the app installed. The HMAC check will still pass because the domain is never part of the signed material, so the request is accepted as if it genuinely originated from the victim shop.

### Finding Description
`validateHmacString` verifies the signature by comparing `hmac` against a locally computed HMAC over `rawBody` only: [1](#0-0) 

`validateHmacFromRequestFactory` extracts the `hmac` header and validates it against `rawBody`, but the `domain`, `topic`, and `webhookId` headers are pulled directly from the (unauthenticated) request headers without being included in the signed payload: [2](#0-1) 

`checkWebhooksHeaders` simply reads the `domain` header verbatim and returns it as trusted `WebhookValidationValid.domain` once the (domain-independent) HMAC check succeeds: [3](#0-2) 

That unauthenticated `domain` is then used directly to look up/refresh the shop's offline session and to build an authenticated Admin/Storefront API client for that shop, both in `shopify-app-remix` and `shopify-app-react-router`: [4](#0-3) [5](#0-4) 

This is the direct analog to H-15: the HMAC/"signature" only proves that the payload was produced by an entity that possesses the app's shared secret (i.e. some shop that installed the app) — exactly like the Allora `Validate()` check proving a bundle was signed by *some* private key without confirming that key belongs to the actor named in the payload. Here, nothing ties the verified signature to the specific shop domain the request claims to be from.

### Impact Explanation
Because `apiSecretKey` is a single value shared by the app across all installing shops, any merchant who installs the app on a shop they control can capture a real, validly-HMAC-signed webhook body from Shopify (e.g. by triggering `products/create` in their own store) and then send that body directly to the app's public webhook endpoint with the `domain` header rewritten to a victim shop that also uses the app. `authenticateWebhookFactory` will accept it as valid, load the victim's offline session/access token, hand the attacker-controlled body to the app's webhook handler as if it were the victim's data, and build an Admin API client authenticated as the victim shop. Depending on the app's webhook handlers, this can lead to processing of forged data attributed to another tenant, unwanted mutations performed with the victim's access token, or state corruption/cross-tenant data leakage — a single lower-privilege merchant can attack any other tenant of the same app.

### Likelihood Explanation
Any user of the app can self-install it on their own shop (many apps are free to install or have dev-store trial periods), giving them the ability to receive legitimately signed webhook bodies at will for topics they trigger themselves. Forging the `domain` header on the replayed HTTP request requires no cryptographic material beyond the header value itself (unlike the HMAC, it's not signed). This makes the attack straightforward to mount from an anonymous/unprivileged actor's own store against another shop that has the same app installed.

### Recommendation
Do not treat the `domain` (and ideally `topic`/`webhookId`) header as trusted purely because the request-body HMAC validated. Options:
- Include the shop domain (and other identifying headers) in the HMAC-signed material, or
- Cross-check the claimed `domain` against an authenticated/known value (e.g. verify it corresponds to a shop with an active, previously stored session created via a real OAuth/token-exchange flow tied to that same domain, and reject if the shop was never legitimately established), and
- Consider per-shop signing where feasible, so a signature produced for shop A cannot be replayed and accepted for shop B.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. creates a product), capturing the raw POST body and the resulting `X-Shopify-Hmac-Sha256` value that Shopify computed with the app's shared secret.
2. Attacker replays that exact body/HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop that also installed the app).
3. `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts`) validates only `rawBody` against the HMAC and returns `valid: true`.
4. `checkWebhooksHeaders` returns `domain: 'victim.myshopify.com'` unchanged.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim.myshopify.com')`, loading/refreshing the victim's offline session and access token, then invokes the app's webhook handler with the attacker's forged payload attributed to the victim shop.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
