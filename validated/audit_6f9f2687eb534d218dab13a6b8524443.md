### Title
Missing feature-toggle check (`supportUnfreezeDelay`) in `WithdrawExpireUnfreezeProcessor` allows TVM contracts to withdraw expired unfrozen TRX before the feature is enabled - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java])

### Summary
The `WITHDRAWEXPIREUNFREEZE` TVM opcode is gated only by the `allowTvmFreezeV2` proposal flag [1](#0-0) , and its actual balance-withdrawal logic delegates to `WithdrawExpireUnfreezeProcessor.validate()`/`execute()` [2](#0-1) . Unlike its sibling, ordinary-transaction actuator `WithdrawExpireUnfreezeActuator`, which explicitly requires the committee-controlled `supportUnfreezeDelay()` flag to be enabled before allowing the withdrawal [3](#0-2) , the TVM-reachable `WithdrawExpireUnfreezeProcessor.validate()` never checks `dynamicStore.supportUnfreezeDelay()` at all [4](#0-3) .

### Finding Description
This mirrors the C4 finding: a state-changing withdrawal function is missing a mandatory governance/feature-gate check ("unpaused(p)") that its sibling entry point enforces. Here, the "pause"-equivalent guard is the `UNFREEZE_DELAY` (`supportUnfreezeDelay`) committee-controlled dynamic parameter, which is meant to gate whether the delayed-unfreeze-withdraw feature is active on chain. The regular contract-broadcast path (`WithdrawExpireUnfreezeContract` → `WithdrawExpireUnfreezeActuator.validate()`) enforces this check, throwing `"Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee"` if it is not enabled [3](#0-2) . However, the equivalent operation reachable from inside a smart contract via the `WITHDRAWEXPIREUNFREEZE` TVM opcode uses a completely separate code path — `Program.withdrawExpireUnfreeze()` → `WithdrawExpireUnfreezeProcessor` — that never consults `supportUnfreezeDelay()` [4](#0-3) .

The only guard on the TVM opcode is the unrelated `allowTvmFreezeV2` fork/proposal flag applied uniformly to the whole freeze-v2 opcode group [1](#0-0) , which governs whether TVM freeze-v2 opcodes exist at all, not whether the delayed-unfreeze feature specifically has been separately activated. Since `allowTvmFreezeV2` and `UNFREEZE_DELAY`/`supportUnfreezeDelay` are distinct, independently-toggleable committee proposals, it is architecturally possible for `allowTvmFreezeV2` to be enabled while `supportUnfreezeDelay` remains disabled — a state the actuator path correctly rejects but the TVM native-contract path does not.

### Impact Explanation
If the network operator/committee enables `ALLOW_TVM_FREEZE_V2` before enabling `UNFREEZE_DELAY`, any smart contract could invoke `WITHDRAWEXPIREUNFREEZE` and successfully withdraw "expired" unfrozen balances via `WithdrawExpireUnfreezeProcessor.execute()` even though the feature has not been formally activated by governance, bypassing the intended activation gate for this consensus-affecting balance-mutation feature. This is an unauthorized state-transition/feature-bypass issue consistent with "asset or accounting corruption" / bypass of a protocol-level governance gate.

### Likelihood Explanation
Exploitability depends on the specific sequencing/state of the two independent committee proposals (`ALLOW_TVM_FREEZE_V2` vs `UNFREEZE_DELAY`) at any point in the chain's history or on private/test networks that configure these flags independently. I was not able to confirm from the indexed code whether current mainnet genesis/proposal ordering makes this window unreachable in practice (e.g., whether one flag can only be enabled after the other) — I found no explicit dependency check enforcing `UNFREEZE_DELAY` as a precondition for `ALLOW_TVM_FREEZE_V2` in `ProposalUtil.java`.

### Recommendation
Add an explicit `supportUnfreezeDelay()` check to `WithdrawExpireUnfreezeProcessor.validate()`, mirroring `WithdrawExpireUnfreezeActuator.validate()`, so both entry points enforce the same governance gate:
```java
if (!dynamicStore.supportUnfreezeDelay()) {
  throw new ContractValidateException("Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee");
}
```

### Proof of Concept
1. On a network/testnet where `ALLOW_TVM_FREEZE_V2` is enabled (via committee proposal) but `UNFREEZE_DELAY` (`supportUnfreezeDelay`) is not yet enabled.
2. A regular account attempts `WithdrawExpireUnfreezeContract` — rejected by `WithdrawExpireUnfreezeActuator.validate()` with `"Not support WithdrawExpireUnfreeze transaction..."` [3](#0-2) .
3. The same account instead deploys/calls a smart contract that executes the `WITHDRAWEXPIREUNFREEZE` opcode, which routes to `Program.withdrawExpireUnfreeze()` and `WithdrawExpireUnfreezeProcessor.validate()`/`execute()` [2](#0-1)  — succeeding despite the feature being disabled, because the flag check is absent there [4](#0-3) .

  public long withdrawExpireUnfreeze() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawExpireUnfreeze", nonce, null);

    try {
      WithdrawExpireUnfreezeParam param = new WithdrawExpireUnfreezeParam();
      param.setOwnerAddress(owner);

      WithdrawExpireUnfreezeProcessor processor = new WithdrawExpireUnfreezeProcessor();
      processor.validate(param, repository);
      long expireUnfreezeBalance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(expireUnfreezeBalance);
      }
      return expireUnfreezeBalance;
    } catch (ContractValidateException e) {
      logger.warn("TVM WithdrawExpireUnfreeze: validate failure. Reason: {}", e.getMessage());
    } catch (ContractExeException e) {
      logger.warn("TVM WithdrawExpireUnfreeze: execute failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
  }

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
  }
