### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify accept a diverged state/hot-state/native-position root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (the function used by both `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` to check re-executed output against the backup/archive-recorded `TransactionInfo`) checks status, gas used, write-set hash, event root hash, and transaction hash — but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is called out by the code's own comment as a known gap.

### Finding Description
`ensure_match_transaction_info` validates several fields between a freshly-computed `TransactionOutput` and the authenticated `TransactionInfo` read from an archive/backup: [1](#0-0) 

It checks status, gas, the write-set hash against `state_change_hash`, and the event root hash, but the comment right before returning `Ok(())` states plainly: [2](#0-1) 

i.e. "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole per-transaction correctness check in the replay-verify tool's execution loop: [3](#0-2) 

and in `aptos-debugger`'s `execute_and_verify` (via the same `ensure_match_transaction_info` call, confirmed by the grep hit in `aptos-move/aptos-debugger/src/aptos_debugger.rs`). Both tools are the primary mechanisms operators and Aptos Labs use to confirm that re-execution of historical/mainnet transactions from cold storage reproduces the exact ledger state that was originally committed and signed by validators, including the `state_checkpoint_hash` field embedded in the consensus-signed `TransactionInfo`/accumulator leaf. Because the comparator never compares `state_checkpoint_hash` (Sparse Merkle Tree root of the *whole* world state at a checkpoint), `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` (native trading position state root, gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), the checkpoint-level state root is the one authenticated-by-consensus value that replay-verify does *not* actually re-derive-and-compare in this code path.

### Impact Explanation
If a locally re-executed block produces state values whose per-write-set hash and event hash coincidentally match the archived `TransactionInfo` (e.g. two writes cancel out to the same combined write-set hash, or a bug only manifests in state not touched by this particular write set but visible only in the aggregate checkpoint root/hot-state root/position-state root), replay-verify will report success even though the actual state tree at the checkpoint boundary has diverged from the one validators signed. Since replay-verify (and the debugger) is the tool relied on to catch consensus/state divergence bugs (hard forks, non-determinism, storage corruption) before/after they reach production, a gap here means such a divergence in checkpoint-level state can go undetected — directly undermining the "proof-integrity" guarantee that replay of committed state faithfully reproduces the authenticated ledger. This matches the state-commitment/proof-integrity impact class ("committed state that differs from correct VM result... accepted as valid", "hard-fork-only divergence during commit, replay... verification").

### Likelihood Explanation
This is a real, currently-shipping gap (not a hypothetical): the code comment itself flags it as a known omission ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), meaning as of this commit the feature that would make `position_state_checkpoint_hash` meaningful is presumably not yet safe to turn on specifically because of this gap. For the already-active `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields, the comparator's silence means any bug that corrupts checkpoint-level SMT root computation while leaving per-transaction write-set/event hashes intact would not be caught by replay-verify today. I was not able to fully verify within this session whether some other, separate consistency check elsewhere in the executor (e.g. `do_state_checkpoint.rs`'s `known_state_checkpoints` comparison against `computed_last_checkpoint_hash`) independently closes this gap in production execution/commit paths outside of these two specific offline replay tools; that comparison operates on `known_state_checkpoints` passed in during normal execution/commit, not in the `replay_on_archive`/`aptos-debugger` code paths shown above, which construct outputs via `AptosVMBlockExecutor::execute_block` and only call `ensure_match_transaction_info`.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) `position_state_checkpoint_hash` against the values in the supplied `TransactionInfo`, as the existing TODO comment already instructs, before allowing `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any reliance on this function for full replay integrity) to be treated as trustworthy.

### Proof of Concept
Not independently executable within this session (would require constructing a replay-verify run against an archived backup where a locally re-executed block reproduces the same per-transaction write-set hash and event root hash as the archive but a different aggregate state-checkpoint SMT root, and observing that `replay_on_archive`/`aptos-debugger` report success). The root cause is demonstrated structurally by the cited code: the comparator's `Ok(())` return path is reached without ever reading `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, confirmed by the function body at [4](#0-3)  and the explicit acknowledging comment at lines 2196-2202.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
