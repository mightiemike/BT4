### Title
Unchecked gas-underflow panic in `GasCounter::spend` can halt transaction execution — ([File: crates/blockifier/src/context.rs])

### Summary
`GasCounter::spend` subtracts a call's reported `gas_consumed` from the tracked `remaining_gas` using `checked_sub(...).expect("Overuse of gas; should have been caught earlier")`. This mirrors the reported bug class: an accounting invariant (`consumed <= remaining`) is *assumed* to always hold rather than being defensively handled, and if any execution path ever reports `gas_consumed` larger than the tracked remaining gas, the transaction-processing thread panics instead of gracefully erroring.

### Finding Description
`GasCounter` tracks `spent_gas`/`remaining_gas` for an entire account transaction (validate + execute phases): [1](#0-0) 

`spend()` is invoked via `subtract_used_gas()` after both the `validate` call and the `execute` call of every account transaction: [2](#0-1) [3](#0-2) 

`gas_consumed` on the resulting `CallInfo` is computed independently, per execution backend (VM/Cairo0, Native), from lower-level counters — e.g. in the raw VM path, `execution_utils::update_remaining_gas` performs an unchecked, non-`checked_sub` subtraction directly on a `u64`: [4](#0-3) 

and in the Native path `gas_consumed` is derived from `initial_gas - remaining_gas` with only a sanity check that `remaining_gas <= initial_gas` for that specific call, not against the transaction-level counter: [5](#0-4) 

Because the value ultimately fed into `GasCounter::spend` is reconstructed via several independent, backend-specific computations (VM step/gas conversion, Sierra gas tracking, syscall gas refunds, revert-gas tracking via `SierraGasRevertTracker`), any divergence between these layers — analogous to the Velocimeter bug's mismatch between `_flow.totalSupply()` and `_ve.totalSupply()` — causes the top-level invariant `remaining_gas >= amount` to be violated, and `.expect(...)` panics rather than returning a `Result`.

### Impact Explanation
A panic inside `AccountTransaction::run_execute`/`validate_tx` occurs synchronously during block building/execution for a single submitted transaction. Since this is deterministic logic executed identically by every honest sequencer/validator re-executing the same transaction (including in the Starknet OS re-execution flow), a triggering transaction would cause every node to panic while processing that block, halting block production/confirmation — a systemic DoS matching the "network unable to confirm new transactions" impact bar, directly analogous to the reported Minter DoS where a periodic, unconditional operation reverts due to an unguarded arithmetic assumption.

### Likelihood Explanation
Likelihood is **uncertain/low-to-medium**: the code explicitly acknowledges this is a defensive backstop ("should have been caught earlier"), implying upstream logic is intended to guarantee `gas_consumed <= remaining_gas`. I was not able to trace, within the available tooling, a concrete execution path (e.g., a specific interaction between syscall gas refunds, revert-gas tracking, and cross-call aggregation) that provably desynchronizes the counters for an attacker-controlled contract. This is analogous to the original report in structure (unchecked subtraction on values from independently-computed accounting) but I could not confirm a concrete divergence trigger analogous to the "high liquidity + high price" precondition in the original bug.

### Recommendation
- Replace `.expect(...)` panics in `GasCounter::spend` (and the raw `-=` in `execution_utils::update_remaining_gas`) with saturating arithmetic or a propagated `Result`/error, consistent with the codebase's own stated style guideline to "prefer saturating_sub … over raw arithmetic that could underflow."
- Add explicit cross-checks/tests validating that `gas_consumed` reported by VM, Native, and Sierra-gas-revert-tracking paths can never exceed the gas budget granted to a call under all documented interaction sequences (syscall refunds, reverts, library/nested calls).

### Proof of Concept
Not available — I could not construct a concrete transaction/contract sequence that provably causes `call_info.execution.gas_consumed` to exceed `GasCounter::remaining_gas` using the tools at my disposal (this would require deeper tracing across the Cairo0/VM, Cairo1/Sierra, and Native execution paths, plus the `SierraGasRevertTracker` interplay, than the available search tooling could confirm). This should be verified by a background engineering session with full build/test access before treating it as a confirmed, exploitable finding.
