### Title
Sequencer removes ALL fetched deposits from `DepositDataMempool` regardless of real execution success, silently dropping deposits that fail at actual execution time - ([File: crates/sequencer/src/runner.rs])

### Summary
`crates/sequencer/src/runner.rs` fetches a batch of deposits (`deposit_data`) and passes it into `produce_and_run_system_transactions` → `process_sys_txs`, which correctly reverts and *skips* any individual deposit that fails at real execution time (`EvmSystemTransactionNotSuccessful`) without including it in the returned `all_txs`. However, after the block is committed, the caller unconditionally calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the *original, unfiltered* `deposit_data` list instead of the subset that actually succeeded, so a deposit that diverges from its earlier `eth_call` simulation is purged from the retry queue even though it was never applied.

### Finding Description
The binding that should hold is: `deposit ∈ removed_from_mempool ⇔ deposit ∈ successfully_applied_txs (all_txs returned by process_sys_txs)`.

Trace:
1. `citrea_sendRawDepositTransaction` (`crates/sequencer/src/rpc.rs:330-388`) simulates the deposit with `evm.get_call(dep_tx, Some(BlockId::pending()), ...)` against pending state, and on `Ok`, calls `deposit_mempool.add_deposit_tx(...)` and returns `Ok(())` to the caller immediately. No further confirmation is ever sent to the depositor. [1](#0-0) 
2. Later (potentially several L2 blocks later, per FIFO batching in `fetch_deposits`), the block-production loop fetches a batch `deposit_data` and hands it to `produce_and_run_system_transactions`, which builds `SystemEvent::BridgeDeposit` events from `deposit_data` and passes them to `process_sys_txs`. [2](#0-1) 
3. Inside `process_sys_txs`, each deposit is executed as a system transaction inside a checkpoint. If it fails with `EvmSystemTransactionNotSuccessful`, the working set is reverted, the nonce is decremented, and the loop `continue`s — the deposit is **not** added to `all_txs` (the return value used to build the actual block). [3](#0-2) 
4. Back in the block-commit path, the sequencer unconditionally removes the **entire original `deposit_data` slice** — not `all_txs` — from `DepositDataMempool`: [4](#0-3) 
5. `DepositDataMempool::remove_deposits` matches purely by `calc_tx_id` derived from the deposit bytes and removes both from `accepted_deposit_txs` and `pending_deposits`, with no notion of "was this one actually applied". [5](#0-4) 

Because step 4 uses `deposit_data` (the fetched batch) instead of deriving the removal set from `all_txs` (the batch that was actually applied per step 3), **any deposit whose real execution outcome diverges from its earlier `eth_call` simulation and fails is silently dropped from the mempool forever**, with no error surfaced to the RPC caller (who already got `Ok(())` at submission time) and no automatic retry, since it's gone from `accepted_deposit_txs`.

This directly answers the audit question: `process_sys_txs`'s revert-and-continue logic correctly protects state-root integrity (no double mint, no corrupted state), but the higher-level mempool bookkeeping in `runner.rs` does **not** correctly handle the divergence — it drops the deposit regardless of whether it succeeded. The depositor's BTC lock is never credited with cBTC, and unless an out-of-band operator/aggregator manually notices and re-submits the exact deposit bytes (which is possible since `pending_deposits` is also cleared, but nothing in the protocol prompts anyone to do so), the deposit is effectively orphaned.

### Impact Explanation
A real Bitcoin deposit (BTC locked in the Clementine vault) whose corresponding system deposit transaction fails at actual execution time (due to any state change between simulation and execution — e.g., `processedTxIds[txId]` becoming true from another deposit processed first, contract logic changes, or any other revert condition) is permanently removed from the sequencer's retry queue without minting cBTC and without notifying the depositor. This matches "funds permanently frozen (BTC locked, cBTC never minted, no retry surfaced)" — Critical severity. The bug is systemic (affects every batch containing a failing deposit, on every node running this sequencer code) rather than a single one-off race, and is repeatable for every sequencer restart/batch cycle where a deposit fails at real-execution time after passing simulation.

### Likelihood Explanation
No privileged access is required to trigger the divergence itself in the general case — it merely requires the simulated state (at submission time, against `BlockId::pending()`) to differ from the state at actual execution time, which can happen naturally across the block-gap between `fetch_deposits` batching and the deposit's turn in `process_sys_txs` (multiple deposits queued, unrelated state changes, or contention over the same `moveTx`/txId as described in the question). Because deposit RPC submission is unauthenticated for any client of the sequencer's JSON-RPC (typically used by Clementine but not access-controlled at the protocol level per the question's threat model), and the mempool-removal bug is unconditional, this is a deterministic bug rather than a probabilistic one — every case where a deposit fails after being simulated as valid will silently vanish, 100% of the time.

### Recommendation
Change the block-commit path to only remove deposits that were actually applied. Have `process_sys_txs` / `produce_and_run_system_transactions` return the subset of `deposit_data` that succeeded (or, conversely, the subset that failed) instead of relying on the caller to remove the entire originally-fetched batch. Use that success-only set in the `remove_deposits` call at `crates/sequencer/src/runner.rs:636-643`. Additionally, consider surfacing/logging failed deposits distinctly (e.g., a dead-letter list or metric) so an aggregator/operator can detect and manually resubmit them, since the depositor already received `Ok(())` from `citrea_sendRawDepositTransaction`.

    #[instrument(level = "trace", skip_all, ret)]
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
