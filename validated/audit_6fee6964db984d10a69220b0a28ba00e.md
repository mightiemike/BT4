### Title
Signer v1's tenure-change duplicate-block check ignores locally-accepted blocks, allowing an equivocating signature - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The `Bera_Module` bug class is an asymmetric validation defect: one code path checks both sides of a state transition while a structurally identical sibling path checks only one side, letting an unchecked value slip through and become "stuck"/inconsistent. The same asymmetry pattern exists between the v1 and v2 tenure-change validators in the stacks-signer, where the "duplicate block in tenure" guard checks a narrower state set in v1 than in v2.

### Finding Description
`validate_tenure_change_payload` exists in two protocol-version implementations that are supposed to enforce the same invariant — "a signer must not approve a second, competing tenure-start block once it has already committed to one for that tenure":

- v1: `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0) 
- v2: `signer_db.get_last_signed_block(&block.header.consensus_hash)` [2](#0-1) 

`get_last_signed_block` covers blocks that are either locally accepted or globally accepted (i.e., anything the signer has actually signed), whereas `get_last_globally_accepted_block` only covers blocks confirmed accepted by the network — a strictly narrower set. This asymmetry is explicitly called out in the design notes: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)." [3](#0-2) 

Consequently, a v1 signer that has already locally accepted (signed) a tenure-change block for a given tenure — but that block has not yet reached global acceptance (e.g., it stalled below the 70% signature threshold, was slow to propagate, or a Bitcoin/network delay prevented confirmation) — will not find any "last globally accepted block" for that tenure and will therefore proceed to validate and potentially sign a second, competing tenure-change block for the same tenure. This is exactly analogous to the reported Kodiak bug: the "output side" of the check (locally-accepted, not-yet-globalized commitments) is silently skipped in one branch of otherwise-parallel logic, while the parallel branch handles it correctly.

### Impact Explanation
A signer producing two valid signatures for two different, competing tenure-change (or tenure-start) blocks at the same height/tenure is a minority-triggerable equivocation. If enough v1-protocol signers hit this narrow race (their own previously signed block not yet globally accepted) they can help gather signatures on a second conflicting block, creating a genuine fork/tip disagreement at the miner-signer boundary. This maps to the "temporary tip disagreement" / "minority-triggerable... divergence" High-impact category: nodes/miners can observe two differently-signed candidate blocks for the same tenure, and honest peers following v1 vs v2 protocol logic can disagree on the accepted tip until reconciliation.

Note this is a real timing-window bug in the v1 code path but is more narrow than a full chain split, since v2 (the documented current) protocol has the correct, wider check, and eventual node-side reconciliation (`check_latest_block_in_tenure`, node's own chain view) still bounds the damage.

### Likelihood Explanation
Likelihood depends on how commonly v1-signers still run in the network and how often the timing window (signed-but-not-yet-globally-accepted) is hit — this can occur naturally under normal network latency during pre-commit/threshold gathering, so it is not a contrived edge case. Because v1 is explicitly documented as the older/legacy code path (v2 is the "global signer state" successor referenced throughout `docs/signer-flows.md`), the residual risk is bounded by v1 deployment prevalence, which I cannot confirm from the available code/docs alone.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (matching v2) instead of `get_last_globally_accepted_block`, so that the duplicate-block guard considers any block this signer has already committed a signature to (locally or globally accepted), not just network-confirmed ones.

### Proof of Concept
Conceptual reproduction (cannot be executed without a running signer/test harness, but the code paths are directly comparable):
1. A v1-protocol signer receives tenure-change block `A` for tenure `T`, validates it, and signs it (`mark_locally_accepted`), but block `A` does not reach the 70% global-acceptance threshold in time (e.g., due to network partition/slow propagation among signers).
2. The miner (or a different miner in a fork) proposes a second tenure-change block `B` for the same tenure `T`.
3. `validate_tenure_change_payload` in v1 calls `get_last_globally_accepted_block(T)`, which returns `None` because `A` was never globally accepted.
4. The duplicate check at [4](#0-3)  passes, and the signer proceeds to sign `B` as well — producing two signed, competing tenure-start blocks for tenure `T` from the same signer.
5. Compare with v2's equivalent path at [5](#0-4) , which would correctly find `A` via `get_last_signed_block` and reject `B` with `RejectReason::DuplicateBlockFound`.
