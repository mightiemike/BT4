### Title
Cross-DON WorkflowDonID spoofing bypasses owner-scoping when `workflowDONBindingGate` is disabled - ([File: core/capabilities/remote/executable/request/server_request.go])

### Summary
In `executeCapabilityRequest`, the check that binds `CapabilityRequest.Metadata.WorkflowDonID` to the authenticated `callingDonID` is only enforced when `workflowDONBindingGate.Limit(ctx)` returns `enabled=true`. When the gate returns `enabled=false` (an intended transitional/rollout state), the code skips validation entirely and forwards the unauthenticated, attacker-supplied `WorkflowDonID` straight into `capability.Execute(ctx, capabilityRequest)`.

### Finding Description
`callingDonID` is derived from the authenticated p2p sender: `server.Receive` looks up `cfg.workflowDONs[msg.CallerDonId]` [1](#0-0)  and `ServerRequest.addRequester` further verifies the sending peer is a member of that DON [2](#0-1) . This makes `callingDonID` trustworthy.

By contrast, `capabilityRequest.Metadata.WorkflowDonID` comes from `pb.UnmarshalCapabilityRequest(payload)`, i.e., attacker-controlled request payload content sent by a legitimate member of *some* workflow DON [3](#0-2) . The binding check that ties these two together is conditioned on the gate:

```go
enabled, gerr := workflowDONBindingGate.Limit(ctx)
...
if enabled && capabilityRequest.Metadata.WorkflowDonID != callingDonID {
    ... return error
}
``` [4](#0-3) 

When `enabled` is `false`, the mismatch check is entirely skipped and execution proceeds unconditionally: `capResponse, err := capability.Execute(ctx, capabilityRequest)` [5](#0-4) . The comment above the check explicitly documents the intended invariant ("bind the caller-supplied WorkflowDonID to the authenticated calling DON so it cannot be spoofed") [6](#0-5) , confirming that spoofing is the exact threat this check is meant to close — and that threat is realized whenever the gate reports disabled.

The `NewServerRequest`/`NewServer` constructors only guard against a `nil` gate [7](#0-6) ; there is no fallback enforcement, no default-deny, and no independent verification elsewhere in the call path (`server.Receive`, `ServerRequest.OnMessage`, `executeRequest`) that cross-checks `Metadata.WorkflowDonID` against `callingDon.ID`.

### Impact Explanation
A member of a legitimate (but attacker-influenced) workflow DON can forge `Metadata.WorkflowDonID` to reference a different DON. Since the capability layer downstream attributes the executed action's ownership/billing/authorization metadata to the value in `capabilityRequest.Metadata`, this permits misattribution of privileged workflow actions to an owner/DON that did not actually initiate them — an owner-scoping/authorization bypass affecting capability execution accounting and any downstream logic keyed on `WorkflowDonID` (e.g., rate limiting, billing, secret/zone scoping). This matches "unauthorized privileged workflow action attribution" impact.

### Likelihood Explanation
The precondition — `workflowDONBindingGate.Limit(ctx)` returning `enabled=false` — is explicitly designed to be reachable as a normal, non-misconfigured operating state during gradual rollout, per the code's own comments. Any node that is a legitimate member of a workflow DON (an ordinary workflow submitter, not requiring node-operator/admin privilege) can trigger this by simply setting `Metadata.WorkflowDonID` in its own outgoing `CapabilityRequest` to an arbitrary DON ID. The exploit is fully reproducible whenever the gate is off, with no additional bypass required.

### Recommendation
Remove the feature-flag conditionality from the security-relevant identity binding, or invert the default so the binding check is enforced unconditionally (fail-closed) and the gate only controls a temporary allow-list/monitoring mode rather than disabling the check outright. At minimum, ensure the gate cannot be left in `enabled=false` state in production and add a hard invariant test that fails the build if `WorkflowDonID != callingDonID` is ever forwarded to `capability.Execute`, regardless of gate state.

### Proof of Concept
Unit test in `server_request_test.go`/`server_request_binding_test.go`:
1. Construct a `capabilities.ExecutableCapability` mock that records the `Metadata.WorkflowDonID` it receives in `Execute`.
2. Build a fake `limits.GateLimiter` whose `Limit(ctx)` returns `(false, nil)`.
3. Call `executeCapabilityRequest` with a `CapabilityRequest` whose `Metadata.WorkflowDonID = 999` while `callingDonID = 1`.
4. Assert: no error is returned, and the mock capability's `Execute` was invoked with `Metadata.WorkflowDonID == 999` (i.e., spoofed value passed through unchecked).
5. Repeat with gate returning `(true, nil)` and assert the same input now returns an error and `Execute` is never called — demonstrating the check is present but bypassable purely based on gate state, confirming the vulnerability window.

func (e *ServerRequest) addRequester(from p2ptypes.PeerID) error {
	fromPeerInCallingDon := slices.Contains(e.callingDon.Members, from)

	if !fromPeerInCallingDon {
		return fmt.Errorf("request received from peer %s not in calling don", from)
	}

	if e.requesters[from] {
		return fmt.Errorf("request already received from peer %s", from)
	}

	e.requesters[from] = true

	return nil
}
```
