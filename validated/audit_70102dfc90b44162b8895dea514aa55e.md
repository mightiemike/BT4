## Analysis

This is a valid analog. The Push Chain `x/uexecutor` module deliberately mirrors the "module-issues-EVM-call → contract can call back into the withdrawal gateway → log must be scanned for a new outbound" pattern described in the ZetaChain report, via `DerivedEVMCall` [1](#0-0) . Every place that issues such a call and where the callee can trigger `UniversalGatewayPC` withdrawal logic is expected to feed the resulting receipt into `CreateUniversalTxFromReceiptIfOutbound`/`AttachOutboundsToExistingUniversalTx`, e.g. the normal UEA-payload path does this explicitly [2](#0-1)  and [3](#0-2) .

However, the **CEA smart-contract-recipient branch** of both `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload` calls `CallExecuteUniversalTx` on the recipient contract and only extracts the tx hash/gas for bookkeeping — it never scans `contractReceipt.Logs` for `UniversalTxOutboundEventSig`/`RescueFundsOnSourceChainEventSig`: [4](#0-3)  and [5](#0-4) . `CallExecuteUniversalTx` is a module-as-sender `DerivedEVMCall` into an attacker-controlled contract [6](#0-5) , and outbound creation elsewhere is driven purely by scanning `receipt.Logs` for the gateway address/topic [7](#0-6) .

### Title
Burned PRC20 funds with no outbound created when a CEA smart-contract recipient calls the gateway from within `executeUniversalTx` - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go)

### Summary
For `isCEA` inbounds whose recipient is a deployed smart contract (not a UEA), `x/uexecutor` deposits PRC20 tokens to the recipient and then invokes `executeUniversalTx` on it via `CallExecuteUniversalTx`. If that call causes the recipient contract to call `UniversalGatewayPC`'s withdraw path (burning the just-deposited PRC20 and emitting `UniversalTxOutboundEventSig`), the emitted log is discarded: the smart-contract branch never runs `BuildOutboundsFromReceipt`/`CreateUniversalTxFromReceiptIfOutbound` on `contractReceipt`.

### Finding Description
`ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload` both route `isCEA` inbounds whose recipient has contract code (but is not a recognized UEA) through a dedicated "smart contract path": the module deposits PRC20 to the recipient [8](#0-7) , then calls `CallExecuteUniversalTx(cacheCtx, ueaAddr, ...)` [9](#0-8) .

`CallExecuteUniversalTx` is a real, committed `DerivedEVMCall` from the module account into the recipient contract [10](#0-9) . Because the recipient is attacker-controlled bytecode, its `executeUniversalTx` implementation can itself call `UniversalGatewayPC`'s withdraw entry point using the PRC20 balance it just received, burning tokens and emitting the same `UniversalTxOutboundEventSig` log that `BuildOutboundsFromReceipt` normally parses to create a `PENDING` outbound [7](#0-6) .

The code after the call only records `contractReceipt.Hash`/`GasUsed` into a `PCTx` and returns — it never calls `CreateUniversalTxFromReceiptIfOutbound`, `AttachOutboundsToExistingUniversalTx`, or `AttachRescueOutboundFromReceipt` on `contractReceipt` [11](#0-10) . The identical gap exists in the gas-and-payload variant [12](#0-11) .

This contrasts directly with the sibling UEA-execution path in the same file, where `receipt` from `ExecutePayloadV2` is explicitly passed to `AttachOutboundsToExistingUniversalTx` [3](#0-2) , and with `ExecutePayload`'s direct-msg flow, which explicitly checks the receipt for outbound and rescue events [2](#0-1) . The smart-contract branch is the only module-originated-EVM-call site whose receipt is dropped without a log scan — the same root cause as ZetaChain's `HandleEVMDeposit()`/`processFailedZETAOutboundOnZEVM()` bug, where a module-invoked EVM call reaches a target contract capable of triggering the withdrawal gateway, but the resulting log is never processed.

### Impact Explanation
An unprivileged attacker who is a `Sender`/contract-deployer on any supported external chain can craft an `isCEA` inbound whose `Recipient` is a smart contract they control (not a UEA). Once validators finalize the inbound with quorum (an ordinary, honest-validator vote on user-submitted data), `x/uexecutor` deposits PRC20 into the attacker's contract and then calls `executeUniversalTx` on it. The attacker's contract code, inside that call, invokes the gateway's withdraw function to burn the PRC20 for an "outbound" to a destination chain. Because the log from this call is never scanned, no `OutboundTx`/`PendingOutboundEntry` is ever created — TSS never signs anything, and the destination chain never receives funds. The PRC20 is burned on Push Chain with no compensating outbound, permanently destroying user/protocol-controlled value. This matches the "in scope" impact category of permanent loss/unauthorized burn of user funds.

### Likelihood Explanation
High reachability: this is a standard, unprivileged user flow (`isCEA` inbound to a smart-contract recipient), requires no privileged actor, validator collusion, or external-chain compromise — only an ordinary honest-validator-finalized inbound vote and a malicious recipient contract the attacker deploys and controls. The `isSmartContract` branch is a first-class, documented code path (three-way check: UEA / smart contract / EOA), not an edge case.

### Recommendation
In both `ExecuteInboundFundsAndPayload`'s and `ExecuteInboundGasAndPayload`'s smart-contract branches, after a successful `CallExecuteUniversalTx` (and gas-fee deduction / `writeCache()`), scan `contractReceipt.Logs` the same way the UEA path does — call `CreateUniversalTxFromReceiptIfOutbound`/`AttachOutboundsToExistingUniversalTx` and `AttachRescueOutboundFromReceipt` on `contractReceipt` before returning, so any gateway withdraw triggered from within the recipient's `executeUniversalTx` call is captured as a proper pending outbound.

### Proof of Concept
1. Attacker deploys a contract `C` on Push Chain whose `executeUniversalTx(...)` implementation calls `UniversalGatewayPC`'s withdraw function using the PRC20 balance `C` holds, specifying itself/attacker as beneficiary on a destination chain.
2. Attacker sends funds from an external chain with an `isCEA` inbound where `Recipient = C.address`, `Amount > 0`.
3. Universal Validators vote and finalize the inbound normally (honest validators, honest process).
4. `ExecuteInboundFundsAndPayload` detects `C` is a smart contract (not UEA), deposits PRC20 to `C` [8](#0-7) , then calls `CallExecuteUniversalTx` [9](#0-8) .
5. Inside that call, `C` burns its PRC20 balance via the gateway withdraw path, emitting `UniversalTxOutboundEventSig` in `contractReceipt.Logs`.
6. `ExecuteInboundFundsAndPayload` records only a `SUCCESS` `PCTx` and returns [13](#0-12)  — no outbound is ever attached to the UTX, and querying `AllUniversalTx`/`PendingOutbounds` shows no corresponding entry, while the PRC20 balance is confirmed burned.

// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
}
