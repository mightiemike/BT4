### Title
`sanitizeHost` accepts malformed base64 host values that pass `base64regex` but crash `atob()` in `decodeHost`, causing an unhandled exception in `shopify-app-express` auth handlers - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the `host` query parameter using `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/`, which does not enforce that the base64 string length is a multiple of 4. Values such as `host=A` pass this regex but cause `decodeHost(host)` → `atob(sanitizedHost)` to throw a `DOMException`/`InvalidCharacterError`, which is not caught anywhere inside `sanitizeHost` and propagates to the caller.

### Finding Description
`sanitizeHost` in [1](#0-0)  only checks the character set/padding-marker shape of `host` via `base64regex`, not its length modulo 4, then immediately calls `decodeHost(sanitizedHost)` which is a bare `atob()` call with no try/catch: [2](#0-1) . A single character such as `"A"` (or any base64 payload whose length mod 4 is 1) satisfies the regex but is invalid per the WHATWG forgiving-base64 algorithm that `atob` implements, so it throws.

Reachable, unauthenticated callers of `sanitizeHost` include:
- `redirectToShopifyOrAppRoot` in shopify-app-express, an `async` middleware that calls `api.utils.sanitizeHost(req.query.host as string)!` synchronously with no try/catch: [3](#0-2) .
- `clientSideRedirect` inside `redirectToAuth`, called from an `async function redirectToAuth` with `await redirectToAuth(...)` at the route level, also without a try/catch around the `sanitizeHost` call: [4](#0-3) .

Because these are `async` functions invoked from Express route handlers (Express 4 does not automatically catch rejected promises thrown inside `async` handlers), an uncaught synchronous throw inside them becomes an unhandled promise rejection at the process level rather than a clean HTTP error response. The library's own existing test coverage only verifies the "missing/empty host" case returns a 500 via the `!host` null check [5](#0-4) , and does not cover the malformed-base64-that-throws case, so this gap in the regex is not otherwise mitigated.

`buildEmbeddedAppUrl`/`getEmbeddedAppUrl` also call `sanitizeHost(config)(host, true)` expecting a controlled `InvalidHostError` on invalid input, but a length-invalid base64 host bypasses that controlled path and throws a raw `DOMException` instead: [6](#0-5) .

### Impact Explanation
An anonymous, unauthenticated attacker can send a crafted `host` query parameter (e.g. `?host=A`) to any endpoint that calls `sanitizeHost` without its own surrounding try/catch (`shopify.auth.callback()` → `redirectToShopifyOrAppRoot()`, or `redirectToAuth` with `embedded=1`). This throws an uncaught exception instead of the intended graceful `null`/400 response. In `shopify-app-express`, because the call sites are `async` route handlers without try/catch, this manifests as an unhandled promise rejection, which by default terminates the Node process on modern Node versions (`--unhandled-rejections=throw` is default since Node 15) — a denial-of-service against the app's authentication/callback endpoint.

### Likelihood Explanation
Trivially reachable and repeatable: no authentication, secrets, or special configuration are required — just a single crafted GET request to the OAuth callback or redirect-to-auth route with an invalid-length base64 `host` value. The regex flaw is in the default library code and default `shopify-app-express` wiring, not app-developer misconfiguration.

### Recommendation
Harden `sanitizeHost`/`decodeHost`: (1) make `base64regex` correctly enforce standard base64 length rules (length % 4 === 0 including padding, and reject lengths with remainder 1), and/or (2) wrap the `decodeHost` call in `sanitizeHost` in a try/catch that returns `null` (or throws the controlled `InvalidHostError` when `throwOnInvalid` is set) instead of letting the raw `DOMException` propagate. Additionally, wrap `sanitizeHost`/`sanitizeShop` usage in `shopify-app-express`'s async middlewares (`redirect-to-shopify-or-app-root.ts`, `redirect-to-auth.ts`) in try/catch to guarantee a clean error response regardless of upstream validation gaps.

// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost throws uncaught DOMException for malformed base64 length', () => {
  const shopify = shopifyApi(testConfig());

  // 'A' passes base64regex (/^[0-9a-zA-Z+/]+={0,2}$/) but is an invalid
  // base64 length (1 char), so atob() throws instead of sanitizeHost
  // returning null.
  expect(() => shopify.utils.sanitizeHost('A')).toThrow(); // throws DOMException, not InvalidHostError, and with throwOnInvalid=false it should have returned null instead
});
