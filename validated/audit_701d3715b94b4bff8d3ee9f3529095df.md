### Title
DeleteAccount's beneficiary balance refund is permanently burned when `beneficiary_id` is a non-existent account - ([File: runtime/runtime/src/actions.rs])

### Summary
The external report describes `BasePool#claimRewards` allowing a user to burn their own rewards by passing `_receiver = address(0)`, because the contract never checks that the receiver is valid before sending value to it. The analogous pattern exists in nearcore's `DeleteAccountAction`: an account owner supplies a `beneficiary_id` to receive their remaining balance when the account is deleted, but the runtime only validates that `beneficiary_id` is a *syntactically* valid account id, not that the account actually exists. If it does not exist, the balance transfer is issued as a refund receipt, refund receipts to non-existent accounts fail, and because refund receipts never spawn a further refund, the entire balance is irrecoverably burned.

### Finding Description
`action_delete_account` computes the account's current balance and, if positive, unconditionally pushes a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` into `new_receipts`, then deletes the account: [1](#0-0) 

The only validation performed on `beneficiary_id` is that it is a well-formed `AccountId` string (`InvalidAccountId`), documented in the action spec; there is no check that the beneficiary account actually exists on-chain: [2](#0-1) 

The balance transfer is created via `Receipt::new_balance_refund`, which builds a refund receipt (`predecessor_id == "system"`). Refund receipts are special: `apply_action_receipt` never generates a further refund for a failed refund receipt — instead the deposit is burned into `other_burnt_amount`: [3](#0-2) 

The runtime's own regression test confirms both halves of this chain:
- A refund receipt sent to a non-existent account fails with `AccountDoesNotExist` and the receiving account is never created: [4](#0-3) 
- An equivalent case for ordinary transfers, `test_refund_on_send_money_to_non_existent_account`, shows that when the initial send fails because the receiver doesn't exist, the follow-up *deposit refund* correctly goes back to the sender (because it is a refund of a non-refund receipt). But `DeleteAccountAction`'s beneficiary transfer is *itself* already the refund, so this "refund-of-a-refund" safety net does not apply and the tokens are burned outright: [5](#0-4) 

The runtime engineers are aware that `beneficiary_id` must exist for correct behavior — this is explicitly called out in an internal test comment: [6](#0-5) 

### Impact Explanation
Any account owner (holder of a full-access key) who submits a `DeleteAccount` action with a `beneficiary_id` pointing to an account that does not exist (e.g. a typo'd account name, or a name that was never registered, or a previously-existing account that has since been deleted) permanently and irrecoverably burns their entire remaining account balance. This reduces total token supply (`stats.balance.other_burnt_amount`) with no path to recovery — a "permanently frozen/destroyed funds" outcome triggered entirely by a single, ordinary transaction from an unprivileged signer. It is a self-inflicted, user-triggered fund loss exactly analogous to `claimRewards(address(0))` burning a user's own rewards due to missing receiver validation.

### Likelihood Explanation
Likelihood is low-to-moderate: this requires the account owner to specify a bad `beneficiary_id` (typo, non-existent account, or relying on the beneficiary to be created later), which is a user/wallet-integration mistake rather than an externally exploitable attack on a victim's funds — the actor can only destroy their own balance, not someone else's. It could also be hit accidentally by wallets/tooling that don't pre-validate beneficiary existence before submitting the delete transaction.

### Recommendation
Before creating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or, more practically, warn/require verification at the RPC/wallet layer before submission). Alternatively, change the refund semantics for `DeleteAccountAction`'s beneficiary transfer so that on `AccountDoesNotExist` failure the funds are routed to a safe fallback (e.g., burned funds tracked distinctly and reported, or rejected at validation time by requiring the runtime to check account existence for the beneficiary prior to executing the delete, failing the whole action instead of silently burning funds).

### Proof of Concept
1. Create account `alice.near` with a full access key and a positive balance.
2. Ensure `bob.near` (chosen as beneficiary) does not exist on-chain.
3. Submit `SignedTransaction` with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "bob.near".parse().unwrap() })` signed by `alice.near`'s full access key, following the same pattern as: [7](#0-6) 
4. Observe: `alice.near` is deleted, a `Receipt::new_balance_refund(bob.near, alice_balance)` is produced, this refund receipt fails execution with `ActionErrorKind::AccountDoesNotExist` (as shown in `refund_may_not_create_universal_account`), and because it is a refund receipt no secondary refund is generated — `alice_balance` is added to `stats.balance.other_burnt_amount` and permanently lost from total supply.

pub fn test_refund_on_send_money_to_non_existent_account(node: impl Node) {
    let account_id = &node.account_id().unwrap();
    let node_user = node.user();
    let root = node_user.get_state_root();
    let money_used = Balance::from_yoctonear(10);
    // Successful atomic transfer has the same cost as failed atomic transfer.
    let fee_helper = fee_helper(&node);
    let transfer_cost = fee_helper.transfer_cost();
    let transaction_result =
        node_user.send_money(account_id.clone(), eve_dot_alice_account(), money_used).unwrap();
    assert_eq!(
        transaction_result.status,
        FinalExecutionStatus::Failure(
            ActionError {
                index: Some(0),
                kind: ActionErrorKind::AccountDoesNotExist { account_id: eve_dot_alice_account() }
            }
            .into()
        )
    );
    assert_eq!(transaction_result.receipts_outcome.len(), 2 + extra_refund_outcomes());
    let new_root = node_user.get_state_root();
    assert_ne!(root, new_root);
    let result1 = node_user.view_account(account_id).unwrap();
    assert_eq!(
        (result1.amount, result1.locked),
        (
            TESTING_INIT_BALANCE
                .checked_sub(TESTING_INIT_STAKE)
                .unwrap()
                .checked_sub(transfer_cost)
                .unwrap(),
            TESTING_INIT_STAKE
        )
    );
    assert_eq!(node_user.get_access_key_nonce_for_signer(account_id).unwrap(), 1);
    let result2 = node_user.view_account(&eve_dot_alice_account());
    assert!(result2.is_err());
}
