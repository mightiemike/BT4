### Title
Method-ID upgrade canonicality is determined by first-inscribed activation height, not council intent — allows permanent censorship of the true upgrade - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`run_l1_block`'s `DataOnDa::BatchProofMethodId` handler accepts *any* blob (no `blob.sender()` check) whose body carries a valid 3-of-5 council signature, and only requires `activation_l2_height` to be strictly greater than the *last accepted* entry's height. Because acceptance is judged against insertion order rather than the council's real chronological intent, a signed-but-unpublished alternate body with a higher activation height, once inscribed first by anyone, permanently blocks the later, lower/equal-height "real" upgrade from ever being applied.

### Finding Description
The binding that should hold is: `BatchProofMethodIdAccessor::get(H)` for any L2 height `H` == the method id the council most recently, in intended chronological order, designated canonical for `H`. What the code actually enforces is a strictly different binding: `BatchProofMethodIdAccessor::last().0 == max(activation_l2_height of all previously *accepted* DA inscriptions)`, and any new candidate is accepted iff `candidate.activation_l2_height > last_activation_height`: [1](#0-0) 

Two facts make this exploitable:
1. Unlike the `Complete`, `Aggregate` and `SequencerCommitment` branches, the `BatchProofMethodId` branch performs **no `blob.sender()` check** — any Bitcoin transaction, from any address, carrying a body with valid signatures is accepted: [2](#0-1) 
compare to the unguarded `BatchProofMethodId` arm at lines 529-566, which has no equivalent sender check.
2. `verify_method_id_security_council` only checks signature validity/threshold (3-of-5, ascending non-duplicate indices) — it has no notion of "latest intended" body, timestamp, or nonce that ties a signed body to a specific point in council decision-making: [3](#0-2) 

`BatchProofMethodIdAccessor::insert` simply appends to the end of the vector without re-sorting or validating global height ordering beyond what the caller already checked: [4](#0-3) 

Exploit flow: the council genuinely produces and signs two bodies during contingency planning — body `A` (the real, intended upgrade) at height `H_real`, and body `B` (a contingency/alternate body, never meant to be inscribed) at height `H_alt > H_real`. If the attacker observes body `B` (e.g., leaked from council coordination channels, as granted by the question's precondition) before the council inscribes `A`, they craft a Bitcoin transaction embedding `DataOnDa::BatchProofMethodId(B)` from an address of their choosing (no DA public key required, since there is no sender check) and inscribe it, paying only ordinary Bitcoin fees. The circuit accepts it because verification only checks signature validity, and `H_alt` is greater than the previous `last_activation_height`. `BatchProofMethodIdAccessor` now has `last().0 == H_alt`. When the council later inscribes the real body `A` with `H_real < H_alt` (or `H_real <= H_alt`), line 539's guard `activation_l2_height <= last_activation_height { continue; }` silently drops it — logged only, with no error surfaced anywhere in `run_l1_block`'s return value.

None of the existing guards (`verify_method_id_security_council`, sender checks elsewhere, chain-id check) catch this, because the vulnerability is not about signature forgery or cross-network replay — it's about the *absence* of any binding between DA-inscription order and council intent, and the *absence* of a sender restriction on this specific variant.

### Impact Explanation
The real, intended `BatchProofMethodId` upgrade is permanently and silently skipped in the light-client-prover's JMT state — the accessor never records it, and no error is surfaced to operators beyond a log line. All batch proofs submitted after `H_real` that were generated against the intended (correct) circuit ID will fail `Z::verify` in `process_complete_proof` (since the LCP will instead attempt to verify them against `B`'s stale/wrong method id), permanently halting proof acceptance for the affected L2 range — or, if the attacker's alternate circuit happens to accept a different state transition, honest provers/proof consumers can diverge on what proof output is considered valid. This is a Critical impact: "a batch or light client proof accepted for a state transition that did not happen or a true one made unprovable" / "a method-id upgrade accepted that was never authorised" (for the specific height/purpose it activates). The attack is a one-shot, irreversible poisoning of the light-client proof's method-id list for the rest of the chain's life (or until a further, even-higher-height override is separately signed and inscribed), affecting every node and prover that ingests this L1 block.

### Likelihood Explanation
Preconditions: the attacker must observe a genuinely 3-of-5-signed alternate body with an activation height greater than the real upgrade's — this is explicitly granted as the scenario's premise (e.g., leaked during council's own contingency-planning coordination, which routinely happens over less-than-airtight channels). Given that, the attacker's cost is only the price of inscribing one Bitcoin transaction (P2A/reveal fees), well within reach of any unprivileged actor, and no council key, DA key, or race against the sequencer/prover is required. The attack is deterministic once the precondition is met and is repeatable for any future alternate signed body an attacker can obtain.

### Recommendation
Bind the accepted `BatchProofMethodId` to actual council intent rather than DA-arrival order: e.g., include a strictly increasing nonce/sequence number or explicit "supersedes" reference inside the signed body that the council increments only when publishing the body they intend to be canonical, and validate that nonce (not just `activation_l2_height`) monotonically in `run_l1_block`. Additionally, restrict the `BatchProofMethodId` DA blob to a designated sender key (mirroring the `sequencer_da_public_key`/`batch_prover_da_public_key` checks) so arbitrary third parties cannot front-run inscription of validly-signed-but-unpublished bodies.

### Proof of Concept
```rust
// crates/light-client-prover/src/circuit/tests -- illustrative
#[test]
fn attacker_can_preempt_real_upgrade_with_higher_activation_height() {
    // council signs body_real at H_real=100 (intended) and body_alt at H_alt=200 (never meant to be inscribed)
    let body_real = BatchProofMethodIdBody { method_id: REAL_ID, activation_l2_height: 100, chain_id };
    let body_alt  = BatchProofMethodIdBody { method_id: ALT_ID,  activation_l2_height: 200, chain_id };
    let sig_real = create_valid_signatures(&signers, &eip191_hash_message(body_real.serialize()));
    let sig_alt  = create_valid_signatures(&signers, &eip191_hash_message(body_alt.serialize()));

    // attacker inscribes body_alt FIRST (from an arbitrary, non-council DA address)
    run_l1_block_with_blob(DataOnDa::BatchProofMethodId(BatchProofMethodId{body: body_alt, signatures_with_index: sig_alt}), /* sender = attacker key */);
    // council later inscribes the real, intended body
    run_l1_block_with_blob(DataOnDa::BatchProofMethodId(BatchProofMethodId{body: body_real, signatures_with_index: sig_real}), /* sender = council key */);

    let ids = BatchProofMethodIdAccessor::<S>::get(&mut working_set).unwrap();
    // BINDING VIOLATION: the intended, later-inscribed real upgrade is missing entirely
    assert!(!ids.contains(&(100, REAL_ID)), "real upgrade was silently dropped");
    assert_eq!(ids.last().unwrap(), &(200, ALT_ID), "attacker-inscribed alt body wins solely due to inscription order");
}
```
This demonstrates that acceptance is governed purely by first-observed inscription order relative to `activation_l2_height`, not by which body the council actually intended to be canonical, confirming the binding violation.
