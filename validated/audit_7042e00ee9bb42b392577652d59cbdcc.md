### Title
Unbounded per-block `GetAllBalances` iteration on FeeCollector in `AllocateTokens` enables a fee-denom-flooding DoS of `uvalidator` `BeginBlocker` - (File: `x/uvalidator/abci.go`)

### Summary
`x/uvalidator/abci.go`'s `AllocateTokens`, which runs unconditionally in every block's `BeginBlocker`, calls `k.BankKeeper.GetAllBalances(ctx, feeCollector.GetAddress())` and subsequently iterates/moves the *entire* set of denoms held by `FeeCollector` with no bound on the number of distinct denoms. This mirrors the Canto coinswap finding: an unprivileged actor who can cause a module-controlled account to accumulate an unbounded number of coin denoms can turn a routine, per-block, "iterate-all-balances" keeper call into a computational-DoS vector against block production.

### Finding Description
`AllocateTokens` is invoked from `BeginBlocker` on every block after height 1: [1](#0-0) 

Inside it, the FeeCollector's balance is read in full and then converted/split/transferred with no cap on the number of denoms processed: [2](#0-1) [3](#0-2) 

Every distinct denom present in `feesCollectedInt` is: (1) converted into `DecCoins`, (2) iterated per UV vote to compute a truncated share, (3) moved via `SendCoinsFromModuleToModule` to `distribution`, and (4) the remainder moved back to `FeeCollector` — all inside `BeginBlocker`, which (unlike a metered SDK transaction) is not subject to a per-transaction gas limit the same way, so an inflated denom set does not fail with "insufficient gas" the way the original coinswap bug did, but instead directly inflates the wall-clock/computation cost of block production for every validator, every block.

The precondition for exploitation is that `FeeCollector` accumulates many distinct denoms. Fees are moved into `FeeCollector` via `SendCoinsFromAccountToModule` inside the ante fee-deduction path, which — unlike the bank module's `MsgSend` handler — does not go through the `BlockedAddr` check, so a module account being "blocked" for ordinary `MsgSend` does not prevent it from receiving many-denom fee payments through the ante pipeline. If a transaction's `Fee` field can legally contain many distinct coin denoms (in addition to whatever the required gas denom is), and the account holds those denoms (which, given the presence of a `tokenfactory` module in this app — see `scripts/test_node.sh` genesis wiring — can be minted cheaply/for free by any user), an attacker can inflate the number of unique denoms deposited into `FeeCollector` in a single block, causing that block's `AllocateTokens` execution to iterate over an attacker-chosen number of denoms.

### Impact Explanation
If exploitable, this is a network-level-adjacent but code-reachable computational DoS on the `uvalidator` module's mandatory `BeginBlocker`, executed by every honest validator node on every block. A sufficiently large number of distinct denoms in `FeeCollector` would materially slow or stall block production chain-wide — a consensus-availability impact reachable purely from unprivileged user transaction submission, matching the "denial of service ... reachable without privileged control" and "state-machine divergence/halt reachable from ordinary user ... default transaction submission paths" categories in scope.

### Likelihood Explanation
Likelihood is uncertain and depends on two facts I could not fully verify with the available tooling:
1. Whether the ante fee-deduction/fee-checking logic in this repo permits a transaction's `Fee` coins to include arbitrary extra denoms beyond the required gas-price denom (standard Cosmos SDK `checkTxFeeWithValidatorMinGasPrices`-style logic only strictly validates denoms present in `minGasPrices`, and typically does not forbid additional junk denoms in the `Fee` field, but this repo's custom `DeductFeeDecorator` in `app/ante/fee.go` was not fully inspected for this constraint).
2. The production (non-test) `tokenfactory` `denom_creation_fee` — I only confirmed it is set to `[]` (free) in the local test genesis script (`scripts/test_node.sh`), not in the actual mainnet/testnet parameter set, so the practical cost of minting thousands of distinct denoms in production is unknown.

Because the reachability hinges on these two unverified preconditions, actual likelihood ranges from Medium (if extra fee denoms are unrestricted and denom creation is cheap) to Low/Not-exploitable (if the ante handler strictly rejects unrecognized fee denoms, or governance sets a meaningful `denom_creation_fee`).

### Recommendation
- Bound `AllocateTokens`' work to the chain's canonical fee/gas denom(s) instead of iterating `GetAllBalances` over the entire `FeeCollector` account, e.g., only process `BaseDenom` (and any explicitly whitelisted fee denoms), and either ignore or periodically sweep any other stray denom via a separate, rate-limited/administrative path.
- In the ante `DeductFeeDecorator` (`app/ante/fee.go`), explicitly reject transactions whose `Fee` coins contain denoms outside an allow-list (e.g., only `BaseDenom`), preventing arbitrary denom injection into `FeeCollector` in the first place.
- Add a cap on the number of denoms processed per `BeginBlocker` invocation, logging/skipping (or deferring) any excess so block production time stays bounded regardless of how many unique denoms a malicious actor manages to inject.

### Proof of Concept
Conceptual (blocked from full construction because I could not verify the two preconditions above in the ante handler and mainnet tokenfactory params):
1. Attacker uses `tokenfactory` to mint `N` distinct sub-denoms to their own address (cost depends on production `denom_creation_fee`, confirmed `[]`/free only in the local test genesis).
2. Attacker submits an ordinary transaction whose `Fee` field includes the mandatory `upc` gas amount plus `N` additional 1-unit coins of the attacker's custom denoms (feasibility depends on whether `app/ante/fee.go`'s `DeductFeeDecorator` accepts non-whitelisted extra fee denoms).
3. `SendCoinsFromAccountToModule` in the fee-deduction path (which bypasses the `BlockedAddr` check used only by `MsgSend`) deposits all `N+1` denoms into `FeeCollector`.
4. On the next block, `x/uvalidator/abci.go`'s `BeginBlocker` → `AllocateTokens` calls `GetAllBalances` on `FeeCollector` and performs `O(N)` `DecCoins` conversions and `SendCoinsFromModuleToModule` operations, inflating that block's processing time proportionally to `N`, repeatable every block the attacker chooses to submit such a transaction.

func AllocateTokens(ctx context.Context, totalPreviousPower int64, bondedVotes []abci.VoteInfo, k keeper.Keeper) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// fetch and clear the collected fees for distribution, since this is
	// called in BeginBlock, collected fees will be from the previous block
	// (and distributed to the previous proposer)
	feeCollector := k.AuthKeeper.GetModuleAccount(ctx, authtypes.FeeCollectorName)
	feesCollectedInt := k.BankKeeper.GetAllBalances(ctx, feeCollector.GetAddress())
	if feesCollectedInt.IsZero() {
		k.Logger().Debug("AllocateTokens: no fees collected, skipping", "block_height", sdkCtx.BlockHeight())
		return nil
	}
	feesCollected := sdk.NewDecCoinsFromCoins(feesCollectedInt...)

	k.Logger().Debug("AllocateTokens: fees collected",
		"block_height", sdkCtx.BlockHeight(),
		"fees", feesCollectedInt.String(),
		"bonded_votes", len(bondedVotes),
	)

	// transfer collected fees to the uvalidator module account
	err := k.BankKeeper.SendCoinsFromModuleToModule(ctx, authtypes.FeeCollectorName, types.ModuleName, feesCollectedInt)
	if err != nil {
		return err
	}
