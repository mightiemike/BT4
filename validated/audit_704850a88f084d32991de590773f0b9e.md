Confirmed: there is no interface-support gate (no `supportsInterface`/ERC165-style opt-in check) anywhere in the codebase before the CEA "smart contract" path decides to invoke `executeUniversalTx` on a recipient. The only gate is `codeHash != EmptyCodeHash`. [1](#0-0) [2](#0-1) 

### Title
Module-originated `executeUniversalTx` call is dispatched to any code-bearing recipient without an interface-support check, mirroring the unsafe-ERC721-receiver defect - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/evm.go`)

### Summary
For `isCEA` inbounds whose explicit `Recipient` is not a UEA, Push Chain's `x/uexecutor` module decides whether to treat the recipient as a "smart contract" purely by checking that its code hash is non-empty (`codeHash != types.EmptyCodeHash`), then unconditionally invokes `executeUniversalTx(sourceChain, ceaAddress, payload, amount, prc20AssetAddr, txId)` on it via `CallExecuteUniversalTx`, using the `uexecutor` module account as the EVM `msg.sender`. There is no analog of ERC721's `IERC721Receiver` check — no `supportsInterface`/opt-in flag confirms the target contract actually implements or expects this callback before the module blindly calls into it with attacker-controlled `sourceChain`, `ceaAddress`, `payload`, and `amount` fields sourced from the observed inbound. [3](#0-2) [4](#0-3) 

### Finding Description
The `Recipient` field of an `Inbound` is populated from source-chain event data that an unprivileged attacker fully controls (the attacker initiates the deposit/gateway event on the external chain and chooses the recipient/payload contents). `ValidateForExecution` only requires `Recipient` to be a syntactically valid hex address when `IsCEA` is true — it does not restrict `Recipient` to contracts that intentionally implement the CEA-receiver interface. [5](#0-4) 

Once quorum of honest validators votes the inbound in, execution branches: if `Recipient` is not a deployed UEA, the keeper checks only `GetCodeHash(recipient) != EmptyCodeHash` to decide it is a "smart contract," then always attempts `CallExecuteUniversalTx`, which performs a `DerivedEVMCall` from the `uexecutor` module account into that contract with the ABI-encoded `executeUniversalTx(string,bytes,bytes,uint256,address,bytes32)` selector and attacker-supplied `payload`/`ceaAddress`/`amount` bytes. [2](#0-1) [6](#0-5) 

This is the direct analog of the ERC721 `safeTransferFrom` defect: the protocol treats "has bytecode" as equivalent to "consents to and correctly handles this specific inbound callback," exactly as `RCNftHubL2.safeTransferFrom` treated "any address" as an acceptable receiver without checking `IERC721Receiver`. No `supportsInterface`, allow-list, or explicit registration step exists anywhere in the codebase to confirm a target contract has opted in to being called this way. [7](#0-6) 

### Impact Explanation
The `uexecutor` module account is a privileged, protocol-controlled EVM sender used elsewhere for mint/deposit/refund/chain-meta operations. Forcing it to make an unsolicited call — with attacker-chosen `payload` bytes forwarded verbatim, and other attacker-influenced fields — into any code-bearing address on Push Chain (including contracts never designed to receive this callback) means:
- Any deployed contract on Push Chain can be made to receive an unrequested, module-authenticated call with attacker-supplied calldata parameters, with no opt-in mechanism, purely because it happens to have bytecode.
- If any current or future contract on Push Chain exposes a function whose selector coincides with `executeUniversalTx(string,bytes,bytes,uint256,address,bytes32)`, or relies on a fallback that trusts `msg.sender == uexecutor module account` for privileged behavior, this path lets an unprivileged attacker trigger that function/fallback with attacker-chosen arguments and no consent from the contract's owner. This directly matches the in-scope impact category of "unauthorized module-originated EVM execution."
- Because the deposit into the recipient happens before/around this call and there is no interface confirmation, a mismatched or malicious deployment relationship could result in funds being deposited to and calls being routed into a contract that has no code path expecting or safely handling this deposit+callback, resulting in stuck/mishandled protocol-minted PRC20 balances or unintended contract state transitions attributable to the module's identity.

### Likelihood Explanation
An unprivileged attacker fully controls the source-chain inbound event that becomes `Recipient`, `payload`, `ceaAddress`, `amount`, and `sourceChain`; honest validators only need to observe and vote the real on-chain event, which the attacker triggers themselves by depositing to the gateway. No special privilege, TSS key compromise, or validator collusion is needed — an ordinary user submitting a normal cross-chain deposit with `isCEA=true` and `Recipient` set to any contract address of their choosing reaches this code path. The main mitigating factor is that Solidity's 4-byte selector must collide with the exact `executeUniversalTx(string,bytes,bytes,uint256,address,bytes32)` signature (or the target's fallback must accept arbitrary calls), which lowers exploitation likelihood against arbitrary already-deployed third-party contracts, but does not lower it against the attacker's own maliciously deployed "recipient" contract crafted to exploit any implicit trust in the module-account caller identity that other Push Chain infrastructure might place on it.

### Recommendation
Add an explicit opt-in/consent mechanism before treating any code-bearing address as a valid CEA recipient, analogous to the ERC721 `IERC721Receiver` check:
- Require recipient contracts to implement and pass a `supportsInterface`-style (or dedicated marker function) check confirming they explicitly support the `executeUniversalTx` CEA callback before `CallExecuteUniversalTx` is invoked.
- Alternatively, maintain an explicit registry/allow-list of CEA-aware recipient contracts (similar in spirit to the existing chain/token registry pattern) rather than inferring "callable" from `GetCodeHash != EmptyCodeHash`.
- Wrap the interface-check call itself in error handling so that a revert/mismatch is treated identically to "recipient is not CEA-aware" (deposit-only, no call), preventing any unsolicited call to non-consenting contracts.

### Proof of Concept
1. Attacker deploys (or targets) a contract `C` on Push Chain.
2. Attacker performs a normal external-chain deposit to the Push Chain gateway with `isCEA=true`, `TxType=FUNDS_AND_PAYLOAD` (or `GAS_AND_PAYLOAD`), `Recipient=address(C)`, and attacker-chosen `UniversalPayload.Data`/`amount`.
3. Honest Universal Validators observe this real deposit and vote `MsgVoteInbound` as usual; quorum is reached honestly.
4. `ExecuteInboundFundsAndPayload` resolves `Recipient` is not a UEA, sees `GetCodeHash(C) != EmptyCodeHash`, sets `isSmartContract = true`.
5. `CallExecuteUniversalTx` is invoked from `ueModuleAccAddress` into `C` with `executeUniversalTx(sourceChain, ceaAddress, payload, amount, prc20AssetAddr, txId)`, all attacker-influenced parameters, with **no** prior check that `C` ever declared support for or expects this call. [8](#0-7)

// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
}
