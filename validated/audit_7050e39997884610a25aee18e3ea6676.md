### Title
Account owner permission can be bricked by setting Owner-permission keys to an unrecoverable/burn address - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` lets an account holder replace its `Owner` (and `Active`/`Witness`) permission key set via `AccountPermissionUpdateContract`. The only address-format check performed is `DecodeUtil.addressValid`, which only verifies address length and network prefix, never that the address is a valid, controllable (non-zero/non-burn) address.

### Finding Description
`checkPermission()` validates key count, weight, threshold sum, and address *format* via `DecodeUtil.addressValid(key.getAddress().toByteArray())`, but this function only checks byte length (21) and the `0x41` prefix byte — it does not reject the all-zero address or any other address without a known private key. [2](#0-1)  `validate()` then calls `checkPermission(owner)` on the submitted `Owner` permission with no additional restriction on the key addresses used to satisfy the threshold. [3](#0-2)  In `execute()`, the new permissions (including `Owner`) are written to the account unconditionally via `account.updatePermissions(...)`. [4](#0-3) 

This is a direct analog of the reported bug class: a privileged role (the current `Owner`-permission signer(s)) can set the new "admin" key(s) to an address with no associated private key (e.g., the zero address), which — like the `newAdmin != 0` check missing in the reported protocol — permanently and irreversibly disables that account's ability to satisfy the `Owner` permission threshold, since no one can ever produce a valid signature for the zero address.

Notably, the codebase is aware that the zero address permanently disables owner-permission control: `Manager.resetBlackholeAccountPermission()` deliberately sets the blackhole account's owner permission to a synthetic zero address specifically to lock it out. [5](#0-4)  However, this same "unspendable" property is not blocked when applied by a normal (non-blackhole) account's own `AccountPermissionUpdateContract`.

### Impact Explanation
If the sole/threshold-reaching Owner-permission key(s) are set to a zero or otherwise unrecoverable address, the account permanently loses the ability to authorize any Owner-permission-gated action — including further `AccountPermissionUpdateContract` transactions to fix the misconfiguration. For a witness account this also can leave the `Witness` permission (bound to be updated together per the `hasWitness()` requirement) in the same state, cutting off future permission repair. This matches the "invalid-state/halt" impact category: irreversible loss of account control equivalent to admin-control loss in the reported bug.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the current Owner-permission signer(s) to submit a malformed or malicious permission update (accidental misconfiguration, or a malicious co-signer in a multisig scenario deliberately assigning threshold-satisfying weight to a burn address). There is no on-chain incentive check preventing it, and the actuator performs no "reachable/spendable address" validation, so it is fully triggerable by the actuator's normal, unprivileged-relative-to-itself transaction flow (any TRON account with multisig enabled can trigger this on itself).

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, reject known unrecoverable addresses (e.g., the all-zero address / burn address) for `Key` entries, at minimum for `Owner` permission keys, e.g.:
```java
if (Arrays.equals(key.getAddress().toByteArray(), new byte[21])) {
  throw new ContractValidateException("key address cannot be the zero/burn address");
}
```
placed inside the loop in `checkPermission()` alongside the existing `DecodeUtil.addressValid` check. [6](#0-5) 

### Proof of Concept
1. Attacker/careless owner controls the current `Owner` permission of account `A` (threshold=1, single key = `A`'s own address).
2. Submit `AccountPermissionUpdateContract` with `owner_address = A`, and `owner` Permission containing a single `Key{address=0x410000000000000000000000000000000000000000, weight=1}`, threshold=1.
3. `validate()` passes: `DecodeUtil.addressValid` accepts the zero address (correct prefix/length), weight > 0, threshold ≤ weight sum. [7](#0-6) 
4. `execute()` commits the new Owner permission to the account. [8](#0-7) 
5. Account `A` can never again produce a valid Owner-permission signature (no private key exists for the zero address), permanently disabling any future `AccountPermissionUpdateContract`, `WitnessUpdateContract` (if governed by Owner), or other Owner-gated action for account `A`.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
