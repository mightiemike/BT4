Confirmed: the `ExchangeCreateActuator` never scales `firstTokenBalance`/`secondTokenBalance` for asset `precision` before storing the pool ratio, and all downstream actuators (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) operate purely on these raw, unscaled long balances.

### Title
Bancor-style Exchange pool ratio/slippage math uses raw unscaled TRC10 balances that ignore token `precision`, enabling swap/inject/withdraw pricing corruption between differently-scaled assets - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`, `ExchangeInjectActuator.java`, `ExchangeWithdrawActuator.java`, `ExchangeTransactionActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
TRON's on-chain Bancor-like `Exchange` feature stores pool balances as raw `firstTokenBalance`/`secondTokenBalance` `long` values and computes trade/inject/withdraw ratios directly from these raw integers, without ever consulting each TRC10 asset's `precision` field (`0`–`6` decimals, `AssetIssueContract.precision`). This mirrors the reported bug class: summing/ratioing unscaled amounts across assets with different decimal precisions invalidates the pool-ratio math.

### Finding Description
Every TRC10 asset carries an independent `precision` (decimals) value set at issuance and validated to be in `[0, PRECISION_DECIMAL]` (6) in `AssetIssueActuator`: [1](#0-0) 
and stored per-asset: [2](#0-1) 

The `ExchangeCreateActuator` takes the raw `firstTokenBalance`/`secondTokenBalance` amounts supplied by the pool creator and stores them directly as the pool state, with no scaling by each token's `precision`: [3](#0-2) [4](#0-3) 

`ExchangeCapsule.transaction()` (invoked by `ExchangeTransactionActuator` on every swap) feeds these raw balances straight into `ExchangeProcessor`/`SafeExchangeProcessor`, which perform a Bancor relay-token computation purely on the unscaled `long` values: [5](#0-4) [6](#0-5) 

Similarly, `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the "matching" amount of the other token using a simple cross-multiplication of raw balances (`anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance`), again with no decimal normalization: [7](#0-6) [8](#0-7) 

This is the exact class of bug described in the report: two tokens with different decimal precision are treated as if 1 raw unit of token A equals 1 raw unit of token B when computing pool ratios, deposit/withdraw ratios, and swap prices.

### Impact Explanation
Because `precision` is an issuer-chosen, per-asset value (0–6) and is never factored into `ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, or `ExchangeCapsule.transaction`, a pool created from a 0-decimal token and a 6-decimal token will price trades as if raw integer units were of equal value. An attacker can create or use such a pool, or inject/withdraw liquidity, to skew the effective exchange rate far from the tokens' actual intended value ratio and extract value from other participants (arbitrage against the mispriced pool, or draining counter-party liquidity through injects/withdrawals whose "matching" quantity is computed on the wrong scale). This is reachable by any account via the standard `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` transactions — no privileged access required — and results in asset/accounting corruption for exchange participants.

### Likelihood Explanation
High likelihood: any user can freely choose `precision` when issuing a TRC10 asset (subject only to the 0–6 bound) and then create or interact with an `Exchange` pairing that asset against TRX or another asset with a different precision, via a normal broadcast transaction (`exchangecreate`, `exchangeinject`, `exchangewithdraw`, `exchangetransaction`). No special permissions, timing, or race conditions are required — the flaw is in the deterministic math of the actuators themselves.

### Recommendation
Before computing pool ratios, injected/withdrawn matching amounts, or swap outputs, scale each token amount to a common decimal base using the corresponding `AssetIssueContract.precision` (treating TRX as a fixed reference precision, e.g. 6). This affects `ExchangeCreateActuator.execute/doValidate`, `ExchangeInjectActuator.execute/doValidate`, `ExchangeWithdrawActuator.execute/doValidate`, and `ExchangeCapsule.transaction`/`ExchangeProcessor`/`SafeExchangeProcessor`, all of which currently operate on raw unscaled balances.

### Proof of Concept
1. Issue token `A` with `precision = 0` and token `B` with `precision = 6`, each with total supply `1_000_000`.
2. Call `ExchangeCreateContract` to create a pool with `firstTokenBalance = 1_000_000` (token A, effectively "1,000,000.000000" of the smaller-precision token when compared value-for-value against B's 1e6 scale) and `secondTokenBalance = 1_000_000` (token B, which given precision 6 represents only `1.000000` B in real terms) — see `ExchangeCreateActuator.execute` at lines 55-58/90, which stores these raw amounts as the 1:1 pool ratio.
3. Call `ExchangeTransactionContract` selling a small amount of token A; `ExchangeCapsule.transaction` (`chainbase/.../ExchangeCapsule.java:124-158`) and `ExchangeProcessor.exchange` (`chainbase/.../ExchangeProcessor.java:41-45`) compute the received amount of B using the raw 1:1 balance ratio, ignoring that B is actually worth 1,000,000x more per raw unit than intended, letting the attacker extract B tokens far below their real value.
4. Repeat with `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (`actuator/.../ExchangeInjectActuator.java:71-83`, `actuator/.../ExchangeWithdrawActuator.java:74-89`) to show the "matching" quantity computation is likewise skewed by the unaccounted precision difference, allowing further extraction during liquidity provisioning/removal.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
