### Title
Unchecked subtraction on accumulated `accounts_data_len` can underflow and panic during startup index generation - ([File: accounts-db/src/accounts_db.rs])

### Summary
During `generate_index()` (invoked when Agave reconstructs the accounts index from on-disk storages — e.g. at snapshot load / startup), the code subtracts the data length contributed by duplicate pubkeys from a running total using a plain, unchecked subtraction, immediately next to a sibling field (`capitalization`) that performs the *same kind* of subtraction but with a proper `checked_sub().expect(...)` guard. [1](#0-0) 

### Finding Description
`total_accum.capitalization` and `total_accum.accounts_data_len` are both running accumulators built in parallel over all account-storage bins during index generation, and both are later reduced by subtracting out contributions computed from "duplicate" pubkeys found across slots (`capitalization_from_duplicates`, `accounts_data_len_from_duplicates`), which are themselves parallel-reduced sums from `visit_duplicate_pubkeys_during_startup`.

For `capitalization`, the developers were careful to guard against underflow: `checked_sub(capitalization_from_duplicates).expect("capitalization cannot underflow")` [2](#0-1) . The very next line, doing the analogous operation for `accounts_data_len`, uses an ordinary `-=` with no overflow/underflow check: `total_accum.accounts_data_len -= accounts_data_len_from_duplicates;` [3](#0-2) .

This mirrors the reported bug class exactly: a derived quantity is computed via subtraction without validating that the subtrahend cannot exceed the minuend, in a code path with a sibling calculation that *does* perform this validation correctly — indicating the unguarded one is an oversight rather than an intentional design choice. If duplicate-key visitation ever computes a per-duplicate data length sum (`accounts_data_len_from_duplicates`) that exceeds the total accumulated `accounts_data_len` (e.g., due to a bug in how `visit_duplicate_pubkeys_during_startup` computes deltas for overlapping/duplicate accounts across many storages, or due to malformed/legacy account storages with duplicate pubkeys whose sizes don't reduce cleanly), the subtraction underflows.

### Impact Explanation
`accounts_data_len` is a `u64`; in debug builds an underflow triggers an explicit `attempt to subtract with overflow` panic, and in release builds it silently wraps to a huge value. Either outcome is undesirable on this specific path:
- A panic during `generate_index()` halts the validator/tool during startup or snapshot rebuild — a node-panic / availability impact reachable purely through account/storage data, not through any privileged operator action.
- A silent wraparound corrupts `calculated_accounts_data_len`, which propagates into `ReconstructedAccountsDbInfo` and is used to validate/report the bank's accounts data size after snapshot load [4](#0-3) , i.e., a silent divergence between the node's internal accounting and the true state — analogous to the "silent balance/hash divergence" class called out in scope.

### Likelihood Explanation
This code only executes during `generate_index` at startup/snapshot reconstruction — a legitimate reachable path for every validator (not just a mocked or test-only condition), and is over accounts-db storage/index data as required by the analog rules. Triggering the underflow requires the duplicate-pubkey accounting to produce a data-length sum larger than the total, which depends on the specifics of how duplicates are resolved across slots; I could not fully verify all code paths that populate `accounts_data_len_from_duplicates` within the remaining search budget, so I cannot confirm a concrete account/storage layout that forces the underflow deterministically. The structural asymmetry with the neighboring, properly-checked `capitalization` subtraction is nonetheless a strong signal of a missed bounds check on the same class of operation.

### Recommendation
Replace the unchecked `-=` with a checked or saturating operation and treat an underflow as a bug to be surfaced explicitly, consistent with the neighboring `capitalization` handling, e.g.:
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```
This preserves detection of a genuine invariant violation (as a controlled panic with a clear message) while making the intent explicit and consistent, rather than relying on implicit debug-only overflow checks or silently wrapping in release builds.

### Proof of Concept
Not independently reproduced; this is a static-analysis-based structural finding derived from comparing the two adjacent accumulator-reduction statements:
```rust
// accounts-db/src/accounts_db.rs
total_accum.capitalization = total_accum
    .capitalization
    .checked_sub(capitalization_from_duplicates)
    .expect("capitalization cannot underflow");     // guarded
total_accum.accounts_data_len -= accounts_data_len_from_duplicates; // unguarded
```
A full PoC would require constructing on-disk account storages with duplicate pubkeys across slots such that `visit_duplicate_pubkeys_during_startup`'s summed `accounts_data_len_from_duplicates` exceeds `total_accum.accounts_data_len`; verifying this requires deeper tracing of `visit_duplicate_pubkeys_during_startup` and the per-bin accumulation logic than was completed here, so this should be validated further by a background engineering session with full repository access.
