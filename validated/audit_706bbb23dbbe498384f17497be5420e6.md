### Title
Unbounded/negative `TotalEnergyWeight` and `TotalNetWeight` from mismatched unfreeze accounting causes chain-wide, permanent mis-pricing (and possible ArithmeticException/consensus divergence) of energy/bandwidth for all accounts - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java`)

### Summary
The external report describes a Curve-style `GaugeController` bug: a global aggregate value (`pt.slope`/`pt.bias`) is decremented by an amount that assumes it was tracked consistently with prior increments, but a manual/administrative reduction of a single gauge's weight desynchronizes the aggregate from the delta table, causing `pt.slope -= d_slope` to underflow and permanently brick weight-reading functions for that gauge.

java-tron has a structurally analogous pattern: a chain-wide aggregate counter (`TotalNetWeight` / `TotalEnergyWeight` / `TotalTronPowerWeight`, tracked in `DynamicPropertiesStore`) is incremented when accounts freeze TRX and decremented when they unfreeze, via multiple independent code paths (`UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `UnfreezeBalanceProcessor`/`UnfreezeBalanceV2Processor` for TVM-triggered unfreezes, `CancelAllUnfreezeV2Actuator`, and self-destruct resource transfer in `Program.transferDelegatedResourceToInheritor`). These paths do not all recompute the delta the same way, and the explicit comment `// adjust total resource, used to be a bug here` in `UnfreezeBalanceProcessor.java:190` documents that this exact class of accounting-drift bug has occurred before in this codebase.

### Finding Description
`TotalNetWeight`/`TotalEnergyWeight` are global divisors used in every account's resource limit calculation: [1](#0-0) [2](#0-1) 

These totals are maintained purely by additive/subtractive updates spread across several independent actuators/processors, each computing the delta from local, per-path state rather than from a single canonical source of truth:
- `UnfreezeBalanceActuator.execute` computes `decrease` from before/after per-account weight snapshots and applies it via `dynamicStore.addTotalNetWeight(weight)` [3](#0-2) 
- `UnfreezeBalanceV2Actuator.updateTotalResourceWeight` computes its own before/after delta and calls `dynamicStore.addTotalNetWeight(newNetWeight - oldNetWeight)` [4](#0-3) 
- The TVM-native `UnfreezeBalanceProcessor.execute` instead subtracts the raw unfrozen amount directly: `repo.addTotalNetWeight(-unfreezeBalance / TRX_PRECISION)` with the comment `// adjust total resource, used to be a bug here` acknowledging this is a historically fragile spot [5](#0-4) 
- `Program.transferDelegatedResourceToInheritor` (invoked on contract `SUICIDE`) independently subtracts frozen balances from the totals when transferring resources to an inheritor: `repo.addTotalNetWeight(-frozenBalanceForBandwidthOfOwner / TRX_PRECISION)` [6](#0-5) 

There is no invariant check anywhere that clamps `TotalNetWeight`/`TotalEnergyWeight` to non-negative, nor any reconciliation between these independently-computed deltas and the true sum of all accounts' frozen balances. Just as the external report's `pt.slope` can drift out of sync with the sum of individual gauge slopes due to a governance action (`change_gauge_weight`) bypassing the delta bookkeeping, java-tron's global totals can drift due to multiple divergent, independently-maintained subtraction paths that were already flagged once as buggy (see the comment above), rounding-precision differences between the double-based legacy formula and `BigInteger`-based hardened formula, or any code path that decrements the total by more than what was actually added for a given account.

The consequence of the totals going negative or drifting incorrect is visible directly in the consumers:
- `EnergyProcessor.calculateGlobalEnergyLimit` performs `assert totalEnergyWeight > 0;` (a no-op unless `-ea` is enabled) and then divides `totalEnergyLimit / totalEnergyWeight` — a negative or zero value here produces either an `ArithmeticException` (divide-by-zero) or a silently wrong (potentially negative) `energyLimit` for every account on the network. [7](#0-6) 
- `RepositoryImpl.calculateGlobalEnergyLimit` has the identical `assert totalEnergyWeight > 0;` pattern, used by the TVM execution path (called on every energy-consuming contract call). [1](#0-0) 
- `UnDelegateResourceActuator` divides by `dynamicStore.getTotalNetWeight()` / `dynamicStore.getTotalEnergyWeight()` directly with no zero/negative guard at all, so a corrupted total there is an unguarded division. [8](#0-7) 

Because `assert` statements are disabled by default in production JVMs, the "safety check" in the energy-limit calculation is not actually enforced at runtime; a negative `totalEnergyWeight`/`totalNetWeight` will flow straight into the division. If the hardened, `BigInteger`-based calculation path is enabled (`allowHardenResourceCalculation`), a zero divisor throws `ArithmeticException` from every energy-consuming transaction — this is validated by the project's own tests expecting `ArithmeticException` on such division. [9](#0-8) 

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight` are consensus-critical, block-processing state read by every account's bandwidth/energy consumption calculation on every transaction — not a single gauge affecting a single user, but a global divisor affecting the entire network's resource pricing. If any of the divergent update paths cause these totals to become zero or negative (or to drift so that they no longer reflect the true sum of frozen balances):
- With the hardened/BigInteger calculation path enabled, every subsequent energy-consuming transaction across the whole chain throws an `ArithmeticException`, since block processing must be deterministic and exception-safe, a persistent divide-by-zero here would either halt processing of any transaction that hits this code path or, if inconsistently thrown across nodes (e.g., due to differing hardening flags on different node versions), cause a chain split/consensus divergence.
- With the legacy double-based path, a negative or wrong total silently mis-prices every account's available energy/bandwidth (analogous to the underlying report's "entire gauge is useless... impact is high"), permanently corrupting resource accounting network-wide until a hard fork/manual state repair, since there is no self-healing mechanism that recomputes the totals from the sum of individual account balances.

This matches the required "invalid-state/divergence/halt" impact category, and is strictly worse in scope than the original per-gauge DoS because the corrupted value is global and consensus-relevant rather than scoped to a single gauge/market.

### Likelihood Explanation
This is a real design-level fragility rather than a hypothetical, evidenced by the explicit historical-bug comment left in the code (`// adjust total resource, used to be a bug here`) and by the fact that at least four structurally different, independently-derived subtraction paths (`UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `UnfreezeBalanceProcessor`, `Program.transferDelegatedResourceToInheritor`) all mutate the same shared global counters with no cross-validation or floor-at-zero clamp. Any future edge case in one of these paths (partial unfreeze ordering, contract suicide combined with delegation, rounding differences between the legacy/hardened formulas) can desynchronize the totals from reality, exactly as a single admin call desynchronizes `pt.slope` from `changes_weight` in the original report. I could not, within the scope of static code reading, construct or verify a fully concrete transaction sequence that forces the total to go negative in the current build (this would require deeper cross-actuator interaction tracing/dynamic testing that a background Devin session could perform), so likelihood should be treated as "plausible/needs dynamic verification" rather than confirmed-exploitable.

### Recommendation
- Clamp `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` to a minimum of `0` inside `DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` (the java-tron analog of the report's suggested `pt.slope = 0` floor), rather than allowing them to go negative.
- Replace the disabled `assert totalEnergyWeight > 0;` checks in `EnergyProcessor.calculateGlobalEnergyLimit` / `RepositoryImpl.calculateGlobalEnergyLimit` with real runtime guards (`if (totalEnergyWeight <= 0) return 0;`, matching the pattern already used in `calculateGlobalEnergyLimitV2`), since Java assertions are not enabled by default and provide no real protection.
- Consolidate the total-weight bookkeeping into a single reviewed helper used by all unfreeze/suicide/delegate paths instead of four independently-computed deltas, to eliminate the class of drift bug already flagged by the `// used to be a bug here` comment.

### Proof of Concept
Not independently reproduced; would require a background Devin session to construct a concrete transaction sequence (e.g., interleaving freeze/unfreeze, delegate/undelegate, and contract self-destruct across the different actuators/processors identified above) and confirm on a running node whether `TotalNetWeight`/`TotalEnergyWeight` can be driven to ≤0, and what the resulting behavior is under both the legacy and hardened (`allowHardenResourceCalculation`) code paths.

          .divide(BigInteger.valueOf(totalEnergyWeight))

  private void transferDelegatedResourceToInheritor(byte[] ownerAddr, byte[] inheritorAddr, Repository repo) {

    // delegated resource from sender to owner, just abandon
    // in order to making that sender can unfreeze their balance in future
    // nothing will be deleted

    // delegated resource from owner to receiver
    // there cannot be any resource when suicide

    AccountCapsule ownerCapsule = repo.getAccount(ownerAddr);

    // transfer owner`s frozen balance for bandwidth to inheritor
    long frozenBalanceForBandwidthOfOwner = 0;
    // check if frozen for bandwidth exists
    if (ownerCapsule.getFrozenCount() != 0) {
      frozenBalanceForBandwidthOfOwner = ownerCapsule.getFrozenList().get(0).getFrozenBalance();
    }
    repo.addTotalNetWeight(-frozenBalanceForBandwidthOfOwner / TRX_PRECISION);

    long frozenBalanceForEnergyOfOwner =
        ownerCapsule.getAccountResource().getFrozenBalanceForEnergy().getFrozenBalance();
    repo.addTotalEnergyWeight(-frozenBalanceForEnergyOfOwner / TRX_PRECISION);

    // transfer all kinds of frozen balance to BlackHole
    repo.addBalance(inheritorAddr, frozenBalanceForBandwidthOfOwner + frozenBalanceForEnergyOfOwner);

    if (VMConfig.allowTvmSelfdestructRestriction()) {
      clearOwnerFreeze(ownerCapsule);
      repo.updateAccount(ownerAddr, ownerCapsule);
    }
  }
