### Title
Gateway heartbeat requests lack message-level replay/freshness enforcement, relying only on ephemeral in-memory `pendingRequests` map - ([File: core/services/gateway/handlers/functions/handler.functions.go])

### Summary
The `functionsHandler.HandleLegacyUserMessage` / `handleRequest` path (invoked for `MethodHeartbeat`) validates only the message signature, sender allowlist, and per-sender rate limit before forwarding the request to every DON member via `h.don.SendToNode`. Deduplication is performed solely by `hc.RequestCache.NewRequest`, keyed on `{Sender, MessageId}` [1](#0-0) , and that entry is deleted as soon as the request completes or times out [2](#0-1) . Once removed, the exact same signed `api.Message` (same `MessageId`, same `Signature`) can be resubmitted and will pass `NewRequest` again, re-triggering `SendToNode` to all DON members.

### Finding Description
`handleRequest` performs no timestamp/expiration/nonce check on the outer `api.Message`; `api.Message.Validate()` only checks signature length, ID length/format, method/DonId length, and Receiver format — it has no freshness field at all [3](#0-2) . The gateway's only anti-replay mechanism is the transient `pendingRequests` cache keyed by `{Sender, MessageId}`, which exists only while a request is in flight and is deleted on completion/timeout [4](#0-3) [5](#0-4) . Because this is purely an in-flight uniqueness check and not a persisted replay-window/freshness check, resending the same signed bytes after the entry is gone succeeds and re-forwards the identical heartbeat request to all `h.donConfig.Members` [6](#0-5) .

Downstream, the node-side `functionsConnectorHandler.handleHeartbeat` does apply a freshness check on the payload's `request.Timestamp` field (`request.Timestamp < now - requestTimeoutSec` → "Request is too old") and an `internalId`-keyed cache (`heartbeatRequests`, capacity-bounded by `HeartbeatCacheSize`, not time-bounded) [7](#0-6) . This mitigates *late* replays (beyond `requestTimeoutSec`) but does not prevent replay within that window, and it is enforced independently per node, not at the gateway. The gateway itself never checks this inner payload timestamp before broadcasting to all members.

### Impact Explanation
An attacker who has obtained a previously valid, signed heartbeat message (via network capture or otherwise, per the stated precondition) can resend the identical message once the original gateway-side `pendingRequests` entry has been cleared, causing the gateway to re-broadcast the request to every DON node again. This is a duplicate-broadcast / minor resource-amplification issue rather than a full DoS or state-tampering primitive, because: (1) the sender is still subject to `userRateLimiter.Allow(msg.Body.Sender)` before dispatch, capping the achievable replay rate to what the legitimate allowed initiator could already generate [8](#0-7) ; and (2) node-level timestamp/`internalId` checks reject or de-duplicate replays that fall outside the freshness window. The concrete impact is limited to unnecessary heartbeat broadcast/processing cycles within the request's freshness window using rate-limit-bounded traffic — not unbounded DoS, and not unauthorized state manipulation, since the aggregated result still reflects genuine node responses (potentially error responses if nodes reject stale timestamps).

### Likelihood Explanation
Requires the attacker to already possess a validly-signed heartbeat message from an allowed initiator's traffic and to resend it before its embedded `Timestamp` exceeds `requestTimeoutSec`, and after the gateway's own `pendingRequests` entry for that MessageId has been cleaned up (which happens quickly, as soon as the original request is completed/timed out). This is feasible but yields effects bounded by pre-existing per-sender rate limiting.

### Recommendation
Bind gateway-side replay protection to a persistent (not purely in-flight) MessageId/timestamp record with an explicit freshness/expiration window (independent of `pendingRequests` cache lifetime), and reject requests whose payload timestamp is stale or whose `MessageId` was already fully processed within a configurable replay window, before forwarding to DON members in `handleRequest`.

### Proof of Concept
Integration test in `core/services/gateway/handlers/functions/handler.functions_test.go`:
1. Construct and sign a heartbeat `api.Message` from an allowed initiator; call `handler.HandleLegacyUserMessage` and drive it to completion (simulate node responses via `sendNodeReponse` until F+1 responses are collected and the callback resolves), so the `pendingRequests` entry is deleted.
2. Resend the exact same `api.Message` (same `MessageId`/`Signature`) via `handler.HandleLegacyUserMessage` again.
3. Assert current behavior: `NewRequest` succeeds and `don.SendToNode` is invoked again for all members (no rejection) — demonstrating the replay is accepted with no freshness/expiration check at the gateway layer, contrary to the expected invariant that already-fulfilled `MessageId`s be rejected within a replay window rather than merely deduped while in-flight.

func (c *requestCache[T]) deleteAndSendOnce(key globalId, callbackResponse handlers.UserCallbackPayload) error {
	c.mu.Lock()
	entry, deleted := c.cache[key]
	delete(c.cache, key)
	c.mu.Unlock()
	if deleted {
		entry.timeoutTimer.Stop()
		return entry.SendResponse(callbackResponse)
	}

	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *functionsHandler) handleRequest(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	h.lggr.Debugw("handleRequest: processing message", "sender", msg.Body.Sender, "messageId", msg.Body.MessageId)
	err := h.pendingRequests.NewRequest(h.lggr, msg, callback, &PendingRequest{request: msg, responses: make(map[string]*api.Message)})
	if err != nil {
		h.lggr.Warnw("handleRequest: error adding new request", "sender", msg.Body.Sender, "err", err)
		promHandlerError.WithLabelValues(h.donConfig.DonId, err.Error()).Inc()
		return err
	}
	req, err := hc.ValidatedRequestFromMessage(msg)
	if err != nil {
		h.lggr.Debugw("handleRequest: failed to validate message", "sender", msg.Body.Sender, "err", err)
		promHandlerError.WithLabelValues(h.donConfig.DonId, err.Error()).Inc()
		return err
	}
	// Send to all nodes.
	for _, member := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, member.Address, req)
		if err != nil {
			h.lggr.Debugw("handleRequest: failed to send to a node", "node", member.Address, "err", err)
		}
	}
	return nil
}
