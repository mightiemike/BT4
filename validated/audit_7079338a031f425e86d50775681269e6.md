Confirmed: any regular account can call `ExchangeCreateActuator` to create a Bancor-style pool (no privileged role required), and that same account is later the only one permitted to call `ExchangeInjectActuator`/`ExchangeWithdrawActuator` on it. ### Title
Missing slippage protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` allows creator to receive/pay an unexpected counter-token amount - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` let the exchange creator add or remove liquidity from a Bancor-style TRX/TRC10 pool by specifying only a single-sided `quant`; the paired `anotherTokenQuant` is computed at execution time from the pool's *then-current* balances, with no user-supplied minimum/maximum bound. This mirrors the reported `ERC4626DepositOnly.deposit`/`mint` issue where no slippage control exists for the derived output/input amount.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` [1](#0-0) , and `ExchangeWithdrawContract` is identical in shape [2](#0-1) . Neither has an `expected`/minimum-output or maximum-input field, unlike `ExchangeTransactionContract`, which explicitly carries an `expected` field used to bound slippage [3](#0-2)  and is enforced in `ExchangeTransactionActuator.doValidate` via `if (anotherTokenQuant < tokenExpected) throw ...` [4](#0-3) .

In `ExchangeInjectActuator.execute`, `anotherTokenQuant` is derived from the pool's current `firstTokenBalance`/`secondTokenBalance` at the moment the transaction is applied — `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` — and this exact value is then pulled from the creator's balance via `reduceAssetAmountV2`/`setBalance`, with no cap supplied by the creator [5](#0-4) . `doValidate` recomputes the same ratio-based amount and only checks that the creator's balance is sufficient — never that it stays under a user-specified ceiling [6](#0-5) .

Symmetrically, `ExchangeWithdrawActuator.execute` computes `anotherTokenQuant` from the live pool ratio and credits exactly that amount to the withdrawer, with no user-specified floor on the amount received [7](#0-6) .

Because Tron transactions are broadcast to the mempool and can sit for multiple blocks before being packed, other participants can execute `ExchangeTransactionContract` swaps (which do have slippage-protected pricing via `ExchangeCapsule.transaction`, see `ExchangeCapsule.java:119-169`) against the same pool between when the creator signs an inject/withdraw transaction and when it's actually processed, shifting `firstTokenBalance`/`secondTokenBalance` [8](#0-7) . This changes the ratio used to compute `anotherTokenQuant` at execution time versus what the creator expected when signing, exactly analogous to the `previewDeposit`/`previewMint` value drifting between call construction and execution in the reported ERC-4626 issue.

### Impact Explanation
An exchange creator injecting liquidity can be forced to pay more of the counter-token than they intended for the same primary-token `quant`, or a creator withdrawing liquidity can receive less of the counter-token than expected, with no on-chain mechanism to bound or revert the transaction. This is asset/accounting corruption from the creator's perspective — value loss without any way to specify a floor/ceiling, unlike the equivalent swap path (`ExchangeTransactionContract`) which already implements this protection.

### Likelihood Explanation
Likelihood is moderate: it requires (a) pending inject/withdraw transactions in the mempool and (b) another party (or the creator's own bot, or unrelated market activity) trading against the same pool before the inject/withdraw is included. Given TRX/TRC10 Bancor pools are public and any account can execute `ExchangeTransactionContract` trades that shift `firstTokenBalance`/`secondTokenBalance`, this is a reachable and reproducible scenario, not a contrived edge case, though it requires multi-block timing that an attacker or normal market volatility can produce.

### Recommendation
Add an `expected`-style bound to `ExchangeInjectContract` (e.g., `max_another_token_quant`) and `ExchangeWithdrawContract` (e.g., `min_another_token_quant`), and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `doValidate`/`execute`, mirroring the existing `expected` check already implemented in `ExchangeTransactionActuator` [4](#0-3) .

### Proof of Concept
1. Creator C owns a TRX/TOKEN Bancor pool with balances `firstTokenBalance = 1_000_000`, `secondTokenBalance = 1_200_000`.
2. C constructs and signs an `ExchangeInjectContract` with `token_id = firstTokenID`, `quant = 100_000`, expecting `anotherTokenQuant ≈ 120_000` based on the current ratio.
3. Before C's transaction is packed into a block, another account submits an `ExchangeTransactionContract` swap that shifts the ratio so `secondTokenBalance/firstTokenBalance` increases significantly.
4. C's `ExchangeInjectContract` is then processed by `ExchangeInjectActuator.execute`, which recomputes `anotherTokenQuant` using the new, worse ratio (`floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)`), causing C to pay substantially more of the second token than anticipated — with no field in `ExchangeInjectContract` to cap this, and no validation rejecting the transaction [9](#0-8) .

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
