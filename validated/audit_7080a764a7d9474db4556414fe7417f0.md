## Title
`ensure_match_transaction_info` omits hot/position state-checkpoint hash validation, allowing replay-verify to accept a `TransactionInfo` whose accumulator-bound hash diverges from the recomputed one - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` (called from replay-verify tooling, e.g. `aptos-move/cli/src/commands.rs`) checks status, gas used, write-set hash, and event root hash against a `TransactionInfo`, but explicitly does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The code itself flags this with a `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` validates only status/gas/write-set-hash/event-root-hash and returns `Ok(())` without comparing `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`: [1](#0-0) 

These checkpoint hash fields are populated at ledger-update time from `DoStateCheckpoint`/execution-config-derived flags (`hotness_in_epilogue`, `transaction_info_v1`, `hot_state_root_in_txn_info`) and are embedded in `TransactionInfoV1`, which participates in `TransactionInfo::hash()` and therefore in the transaction accumulator leaf hash: [2](#0-1) [3](#0-2) [4](#0-3) 

Because two `TransactionInfoV1` instances that differ only in `hot_state_checkpoint_hash` produce different `TransactionInfo::hash()` values (needed for accumulator-proof and range-proof verification, as seen in `verify_transaction_info` and `TransactionInfoListWithProof::verify`), while `ensure_match_transaction_info` is blind to that field, a caller can pass an incorrect/malicious `hot_state_checkpoint_hash` alongside an otherwise-correct output and have the check succeed: [5](#0-4) [6](#0-5) 

The comment in the code confirms the developers are aware: “this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution.” [7](#0-6) 

### Impact Explanation
As of this reviewed commit, `HOT_STATE_ROOT_IN_TXN_INFO` requires `TRANSACTION_INFO_V1` to be enabled, and per `hot_state.rs`'s own comments, on **testnet and mainnet these hot-state-root feature flags are currently off** (`hot_state_checkpoint_hashes` is `None` in production configuration): [8](#0-7) 

This means today, on mainnet, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` are always `None` in the actual committed ledger — there is no live divergence to exploit because the field simply isn't populated/consensus-verified yet. The gap is a real latent defect (acknowledged by the inline TODO) that would become exploitable the moment `HOT_STATE_ROOT_IN_TXN_INFO` or `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on, since replay-verify would then silently accept a wrong hot/position state root while claiming a match. But under current production feature-flag configuration, this does not corrupt authenticated mainnet state today — it is a tooling gap for a not-yet-enabled feature, not an active state-commitment corruption path.

### Likelihood Explanation
Low under present mainnet configuration, since the relevant fields are unpopulated (`None`) in production and the accumulator computation for `TransactionInfoV1.hot_state_checkpoint_hash` is not yet consensus-verified anywhere in the block/executor pipeline. It requires a future feature activation (`HOT_STATE_ROOT_IN_TXN_INFO` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) to become a live gap, and even then, replay-verify accepting a mismatched replay result is a detection-tooling failure, not itself a mechanism for an unprivileged attacker to corrupt consensus-committed state (validators/full-nodes independently execute and their own accumulator hash still must match the authenticated `LedgerInfo`).

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the recomputed values before enabling `HOT_STATE_ROOT_IN_TXN_INFO` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production, as the existing TODO comment already recommends.

### Proof of Concept
Construct two `TransactionOutput`/`TransactionInfoV1` pairs identical in status, gas, write set, and events, but differing only in `hot_state_checkpoint_hash`:
```rust
let txn_info_a = TransactionInfo::builder_v1()
    .transaction_hash(h).state_change_hash(wsh).event_root_hash(erh)
    .maybe_hot_state_checkpoint_hash(Some(hash_a))
    .gas_used(g).status(s.clone()).build();
let txn_info_b = TransactionInfo::builder_v1()
    .transaction_hash(h).state_change_hash(wsh).event_root_hash(erh)
    .maybe_hot_state_checkpoint_hash(Some(hash_b))  // hash_a != hash_b
    .gas_used(g).status(s).build();

assert_ne!(txn_info_a.hash(), txn_info_b.hash());
assert!(output.ensure_match_transaction_info(v, &txn_info_a, None, None).is_ok());
assert!(output.ensure_match_transaction_info(v, &txn_info_b, None, None).is_ok()); // both pass
```
This demonstrates the check's blindness to the hot-state field, matching the code's own acknowledged TODO, though it is not currently exploitable against mainnet state because the field is unset there.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
