### Title
Unbounded recursion in `get_final_transaction_result` when walking an attacker-built receipt chain can crash a node servicing an RPC transaction-status query - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` recurses once per receipt in the outcome tree with no depth limit, unlike the newer `receipt_to_tx` resolver which explicitly caps traversal at `MAX_DEPTH = 1000` and returns `GetReceiptToTxError::DepthExceeded` instead of recursing further.

### Finding Description
`get_recursive_transaction_results` walks the `receipt_ids` produced by each execution outcome and calls itself once per child receipt, with no bound on recursion depth: [1](#0-0) . It is the core of `get_final_transaction_result`, which is used to answer transaction-status queries (`tx`, `EXPERIMENTAL_tx_status`, etc.) served by the RPC/view layer [2](#0-1) .

The depth of this recursion is controlled by whoever built the receipt chain: any account can submit a contract that repeatedly issues `promise_create`/`promise_then`, producing a long chain of `SuccessReceiptId` outcomes, each of which is itself an entry point for the next recursive call in `get_recursive_transaction_results`. Because chained function calls can be spread over many blocks (each hop bounded only by per-block gas, not by any global depth cap), an attacker can accumulate a chain many thousands of receipts long over time at moderate gas cost.

This is directly analogous to the reference issue: Exim's BDAT path used unbounded recursion in an alternate code path that the DATA path's stack-usage assumptions didn't cover, leading to stack exhaustion. Here, `nearcore` has already recognized and fixed exactly this recursion class in one code path — the `receipt_to_tx` hint resolver enforces `MAX_DEPTH = 1000` and fails cleanly rather than recursing unbounded, as shown by the dedicated regression test constructing a 1002-hop chain [3](#0-2)  — but the older `get_recursive_transaction_results` path used by `get_final_transaction_result` has no equivalent guard.

### Impact Explanation
An unbounded, attacker-controlled recursion depth on a hot RPC path (transaction-status lookup) risks a stack overflow that aborts the serving process. Because view/RPC handling frequently runs in the same process as validator/chunk-producing logic (or on nodes whose availability matters for the network), a transaction-triggered crash here is a potential chunk-producer/RPC-node halt vector, which is high severity for availability even though it does not directly move funds.

### Likelihood Explanation
Exploitability requires only an ability to submit contract calls that create chained promises (a standard, unprivileged capability of any transaction sender) and to eventually have any node execute a `tx`/`EXPERIMENTAL_tx_status`-style query against the resulting transaction hash. Building a sufficiently deep chain costs gas over multiple blocks but is otherwise not access-restricted. I could not fully verify from the available index whether newer code paths (`resolve_receipt_via_hint` / `receipt_to_tx`) have already fully superseded `get_final_transaction_result` for all RPC status queries, or whether it remains reachable in the current wiring of `view_client_actor.rs`; the tool budget was exhausted before confirming which RPC handler(s) still call `Chain::get_final_transaction_result` versus the newer hint-based resolver. This should be verified before treating the finding as fully confirmed.

### Recommendation
Bound `get_recursive_transaction_results` the same way `receipt_to_tx`'s resolver is bounded: convert it to an iterative worklist (e.g., a `VecDeque`/stack loop instead of recursive calls) and/or enforce an explicit `MAX_DEPTH`/max-outcome-count that returns a typed error instead of recursing indefinitely, mirroring `GetReceiptToTxError::DepthExceeded`.

### Proof of Concept
1. Deploy a contract whose method recursively self-calls via `promise_create`/`promise_then` (or chains distinct contracts), sending enough separate transactions/blocks to build a receipt chain of, e.g., 100k+ hops, gas cost permitting over time.
2. Submit the initiating transaction and record its hash.
3. Call the JSON-RPC `tx` (or `EXPERIMENTAL_tx_status`) method with that transaction hash on a node whose view/RPC layer still calls `Chain::get_final_transaction_result`.
4. Observe whether the resulting deep, unbounded recursion in `get_recursive_transaction_results` exhausts the call stack and crashes/aborts the serving process — confirming the analog to CVE-2020-28019's recursion-based stack consumption.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Returns FinalExecutionOutcomeView for the given transaction.
    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }
