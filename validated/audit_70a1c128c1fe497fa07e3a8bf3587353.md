### Title
Failed precompiled-contract calls burn the caller's entire allocated energy instead of only the actual computed cost - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress` computes a fixed "requiredEnergy" for a precompiled-contract call, refunds `msg.getEnergy() - requiredEnergy` on success, but on failure refunds `0`, i.e. burns the caller's *entire* energy stipend for that call regardless of how small `requiredEnergy` actually was. This is the same bug class as the zkSync `L1->L2` finding: a failed sub-execution consumes far more of the caller's resource budget than the work it actually performed, instead of capping the cost at the (already-known) actual/expected computation cost.

### Finding Description
When a contract issues `CALL`/`STATICCALL`/`DELEGATECALL`/`CALLCODE` to a precompiled contract address, `Program.callToPrecompiledAddress` is invoked: [1](#0-0) 

```
long requiredEnergy = contract.getEnergyForData(data);
if (requiredEnergy > msg.getEnergy().longValue()) {
  this.refundEnergy(0, CALL_PRE_COMPILED);
  this.stackPushZero();
} else {
  ...
  Pair<Boolean, byte[]> out = contract.execute(data);
  if (out.getLeft()) { // success
    this.refundEnergy(msg.getEnergy().longValue() - requiredEnergy, CALL_PRE_COMPILED);
    ...
  } else {
    // spend all energy on failure, push zero and revert state changes
    this.refundEnergy(0, CALL_PRE_COMPILED);
    this.stackPushZero();
    ...
  }
}
```

`requiredEnergy` is the deterministic, precomputed cost for the call (`contract.getEnergyForData(data)`), analogous to zkSync's `gasLimitForTx`/known execution cost. On success the caller is charged exactly `requiredEnergy` and the remainder of `msg.getEnergy()` (the energy the calling contract chose to forward with the `CALL`) is refunded. On failure — even though the exact cost of the (aborted) precompiled execution is the same `requiredEnergy` value already computed — the code discards the entire `msg.getEnergy()` stipend (`refundEnergy(0, ...)`), i.e. it charges however much energy the caller forwarded to the call, not the actual/known cost of the operation.

This mirrors the root cause identified in the zkSync report: a design decision that treats "failure" as "consume the whole budget" rather than "consume only what was actually used/known", which is inconsistent with the surrounding code's own accounting (`requiredEnergy` is already known) and inconsistent with the refund-on-success path in the very same function.

By contrast, ordinary internal calls to non-precompiled contracts (`Program.callToAddress`) refund based on the sub-call's *actual* `callResult.getEnergyUsed()` even when that sub-call reverts or throws: [2](#0-1) 

This makes the precompiled-contract-call path an outlier: it is the only common call path where failure causes energy loss disproportionate to the actual/known cost of the operation.

### Impact Explanation
A contract author (or a user interacting with an unaware smart contract) that forwards a large energy stipend to a precompiled-contract call (e.g. `ecrecover`, TVM-specific precompiles such as batch signature validation, zk-SNARK verification, `p256Verify`, etc.) and supplies input that causes the precompile to fail (`execute()` returns `false`, e.g. malformed signature, invalid curve point, malformed proof) will have the *entire forwarded energy* burned rather than just `requiredEnergy`. Since `CALL` semantics let a caller forward an arbitrary amount of the caller's remaining energy, this can silently consume a large multiple of the actual/known cost of the call on every failed precompile invocation — an unintended, disproportionate loss of the transaction sender's energy/TRX for a class of calls where the true cost is already computed and known by the VM itself.

### Likelihood Explanation
This path is reachable unprivileged by any account through a normal `TriggerSmartContract` that performs a low-level `call`/`staticcall` to one of the precompiled addresses with energy forwarded and with an input that fails validation inside the precompile (a very common, easily triggerable condition — e.g., supplying a malformed public key/signature to a verification precompile). No special privileges, node control, or malicious peer/consensus behavior are required; it happens purely from contract-level and RPC-submitted transaction execution in `VMActuator`/`Program`.

### Recommendation
On the failure branch of `callToPrecompiledAddress`, refund `msg.getEnergy() - requiredEnergy` (the same amount that would be charged on success) instead of `0`, so that the caller is only charged the known/actual cost of the precompiled operation regardless of success or failure, consistent with the accounting already performed for the success case and consistent with `callToAddress`'s use of actual energy used.

### Proof of Concept
Not independently executed against a running node; the analysis is based on static code review of `Program.callToPrecompiledAddress` in [3](#0-2) , comparing the `refundEnergy` value used in the success branch (`msg.getEnergy().longValue() - requiredEnergy`) against the failure branch (`refundEnergy(0, ...)`). A concrete PoC would deploy a contract that performs a low-level `call` to a precompiled address (e.g. a signature/proof-verification precompile) with a large `gas(...)` stipend and a deliberately invalid input, then observe that all forwarded energy is consumed on failure versus only `requiredEnergy` consumed on an equivalent successful call with the same input size. I was unable to run this PoC in the current environment (no code-execution tooling available in ask-only mode); this would need to be validated with an actual TVM test (e.g. extending the existing `framework/src/test/java/org/tron/common/runtime/vm/*PrecompiledContract*Test.java` suite) to confirm exact energy deltas.
