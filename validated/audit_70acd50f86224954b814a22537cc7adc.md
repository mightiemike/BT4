### Title
Recursion-depth reset in repeated/legacy `group` field decoding allows unbounded stack growth and stack-overflow crash - ([File: internal/impl/codec_field.go])

### Summary
The fast-path decoder for proto2 `group`-kind fields (`consumeGroupSlice` / `consumeGroupSliceValue` in `internal/impl/codec_field.go`) delegates to `opts.Options().UnmarshalState(...)` without carrying over the current recursion depth. `unmarshalOptions.Options()` builds a fresh `proto.UnmarshalOptions{}` that never copies `o.depth` into `RecursionLimit` [1](#0-0) , so `RecursionLimit` is left at its Go zero value (`0`). `proto.UnmarshalOptions.UnmarshalState` treats `0` as "unset" and resets it back to `protowire.DefaultRecursionLimit` [2](#0-1) . Every nested `group` field therefore restarts a brand-new, full recursion budget instead of continuing to decrement from the caller's remaining depth, defeating the recursion-depth defense that is otherwise consistently enforced everywhere else in the codebase (`internal/impl/decode.go:103-107`, `proto/decode.go:124-126`, `internal/impl/codec_map.go:176-178`, `encoding/prototext/decode.go:117-119`, `encoding/protojson/decode.go:125-128`).

### Finding Description
`protowire.DefaultRecursionLimit`-based checks are the codebase's designated mitigation against unbounded recursive descent while parsing attacker-controlled, length-prefixed/nested wire data — the same bug class as the reported Traffic Server `regex_remap` stack overflow (uncontrolled recursion/stack growth from substitution/input data leading to worker-thread crash).

For ordinary nested messages, this defense works: `mi.unmarshalPointer` decrements `opts.depth` and aborts once it goes negative [3](#0-2) , and `proto.UnmarshalOptions.unmarshal`/`unmarshalMap` do the analogous check [4](#0-3) [5](#0-4) .

However, `group`-kind fields (a still-supported legacy proto2 wire feature, `protowire.StartGroupType`) go through a different path:
- `consumeGroupSliceValue` (message-set/opaque style) and `consumeGroupSlice` (pointer-slice style) each call `opts.Options().UnmarshalState(...)` to decode the group's contents into a brand-new sub-message [6](#0-5) [7](#0-6) .
- Neither function checks or decrements `opts.depth` itself before recursing.
- `opts.Options()` produces a `proto.UnmarshalOptions` struct that omits `RecursionLimit` entirely [1](#0-0) , so it is `0`.
- `UnmarshalState` (and `Unmarshal`) treat `RecursionLimit == 0` as "use the default", resetting the remaining budget to the full `protowire.DefaultRecursionLimit` on every group entered [2](#0-1) .

The net effect: if a self-referential proto2 message type has a repeated `group` field pointing back to itself, an attacker can nest `N` groups, each level resetting the logical depth counter back to `DefaultRecursionLimit`. Only the innermost normal (non-group) message recursion inside each group level is actually depth-limited; the *group* nesting itself is unbounded because each `UnmarshalState` call is a genuine new Go function-call frame (`unmarshalPointer` → `unmarshalPointerEager`/`Lazy` → field coder → `consumeGroupSlice*` → `UnmarshalState` → `unmarshal` → `mi.unmarshal` → `unmarshalPointer` …), consuming real Go call stack with no cap on the number of group levels traversed. This produces uncontrolled, attacker-controlled stack growth — a Go stack overflow is an unrecoverable fatal error (`runtime: goroutine stack exceeds ... - fatal error: stack overflow`), directly crashing the process, analogous to the reported ATS stack overflow from attacker-controlled recursive input.

### Impact Explanation
On a fully trusted-schema, default binary `proto.Unmarshal`/`proto.UnmarshalOptions.Unmarshal` path — i.e., no attacker-supplied descriptor, no custom resolver, just a service that unmarshals untrusted bytes into a known proto2 message type containing a self-referential (directly or mutually) repeated `group` field — a remote, unauthenticated caller can trigger this by sending a small, deeply group-nested payload, causing an unrecoverable process crash (`SA:H`/availability impact), matching a critical-severity uncontrolled-recursion/stack-exhaustion DoS class similar to CVE-2026-58179.

### Likelihood Explanation
`group` fields are a legacy but still fully supported proto2 wire feature; generated code for any `.proto` schema using `group` (or repeated group) automatically wires into `makeGroupSliceFieldCoder` / `coderGroupSliceValue`, which is the default marshal/unmarshal codec table entry for such fields — no special configuration or opt-in flag is required. Any service accepting untrusted binary protobuf input against a schema containing a recursive `group` field is exposed by default.

### Recommendation
Propagate the caller's remaining `opts.depth` into the `proto.UnmarshalOptions` (or equivalent `protoiface.UnmarshalInput.Depth`) passed to `UnmarshalState` in `consumeGroupSlice` and `consumeGroupSliceValue`, and have `unmarshalOptions.Options()` set `RecursionLimit` from `o.depth` instead of leaving it at zero, so recursion budget is consistently decremented and enforced across group nesting exactly as it is for ordinary nested messages and maps.

### Proof of Concept
Given a proto2 schema with a self-referential `group` field, e.g. (conceptually):
```proto
syntax = "proto2";
message Recursive {
  repeated group G = 1 {
    optional Recursive inner = 2;
  }
}
```
An attacker constructs a payload that nests the `group` (tag `1`, `StartGroupType` / `EndGroupType`) inside itself thousands of times (each level trivially small on the wire: a start-group tag + inner-message tag + nested start-group … + matching end-group tags), for example generated in Go:
```go
var buf []byte
const N = 200000 // deep enough to exceed the real Go goroutine stack
for i := 0; i < N; i++ {
    buf = protowire.AppendVarint(buf, protowire.EncodeTag(1, protowire.StartGroupType))
}
for i := 0; i < N; i++ {
    buf = protowire.AppendVarint(buf, protowire.EncodeTag(1, protowire.EndGroupType))
}
var m Recursive
err := proto.Unmarshal(buf, &m) // crashes with fatal stack overflow before returning
```
Because each `group` level resets the logical recursion counter back to `protowire.DefaultRecursionLimit` via `UnmarshalState`'s zero-value reset (`internal/impl/decode.go:31-40`, `proto/decode.go:80-85`), the intended `RecursionLimit` never actually bounds the number of `group` levels traversed, and the real Go call stack grows without the intended limit, leading to a fatal, unrecoverable stack overflow.

**Note on verification limits**: I was not able to fully trace whether `unmarshalPointerLazy` (the lazy-decode path referenced at `internal/impl/decode.go:112-117`) exhibits the identical gap, nor confirm the exact numeric value of `protowire.DefaultRecursionLimit` in this build, due to index scope; a Devin session with full repo access would be needed to pin down the precise minimal `N` and confirm lazy-decode behavior.

		return protoreflect.Value{}, out, errDecode
	}

		Buf:     b,
		Message: m.Message(),

	}

	out.initialized = o.Flags&protoiface.UnmarshalInitialized != 0

func consumeGroupSlice(b []byte, p pointer, num protowire.Number, wtyp protowire.Type, goType reflect.Type, opts unmarshalOptions) (out unmarshalOutput, err error) {

		return out, errUnknown

		return out, errDecode

		Buf:     b,

		return out, err
	}
	p.AppendPointerSlice(pointerOfValue(mp))
	out.n = n
	out.initialized = o.Flags&protoiface.UnmarshalInitialized != 0
	return out, nil
