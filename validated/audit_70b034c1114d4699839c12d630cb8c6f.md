### Title
Malicious witness can max out `brokerage` via `UpdateBrokerageContract` to seize nearly all vote-reward yield from delegating accounts - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
java-tron's SR (witness) vote-reward system contains the same fee-manipulation pattern flagged in the BoostAggregator report: an account that controls a reward-sharing pool (there, the `BoostAggregator` owner; here, a witness/SR) can unilaterally push its cut of the shared yield up to the maximum allowed value via a simple setter, with no rate-lock tied to when voters delegated to it.

### Finding Description
`UpdateBrokerageActuator.execute()` lets any registered witness set its `brokerage` (its cut of block/tx-fee rewards) up to `ActuatorConstant.ONE_HUNDRED` (100%) with a single transaction: [1](#0-0) , validated only by a simple bound check [2](#0-1) . This is functionally identical to `BoostAggregator.setProtocolFee`, which was flagged for allowing the pool owner to raise its cut to 100% and take all depositor rewards.

The new brokerage value is written to a "pending" slot (`cycle = REMARK = -1`) via `DelegationStore.setBrokerage(byte[] address, int brokerage)` [3](#0-2) . On every maintenance cycle boundary, `MaintenanceManager.doMaintenance()` unconditionally copies this pending value into the *next* cycle's brokerage record for every witness, with no check on whether voters have had a chance to react: [4](#0-3) .

Reward splitting itself happens in `MortgageService.payReward()`, which reads the *current cycle's* brokerage and immediately siphons `brokerageAmount` to the witness's allowance before crediting the remainder to the shared reward pool that voters draw from: [5](#0-4) . Because a witness's brokerage change takes effect starting the very next maintenance cycle (a fixed, automatic interval — `MAINTENANCE_TIME_INTERVAL`, default 6 hours), voters who have already delegated votes to that witness have no on-chain lock or per-voter fee snapshot protecting the reward split they implicitly agreed to when voting; the split for their existing delegated votes changes at the very next cycle rollover, exactly the "no snapshot at deposit time" root cause the BoostAggregator finding cites.

### Impact Explanation
A witness that attracts votes at a low/attractive brokerage (e.g., the `DEFAULT_BROKERAGE = 20%`) [6](#0-5)  can later call `UpdateBrokerage` to set brokerage to 100%. From the next maintenance cycle onward, `payReward` sends the *entire* block/fee reward for that witness to the witness's own allowance, leaving nothing for the reward pool that voters' `computeReward`/`withdrawReward` draw from [7](#0-6) . Voters who have delegated TRX-power votes to that witness, expecting a favorable split, lose essentially all future yield without any ability to prevent it once the change lands at the next cycle boundary — they can only un-vote for future cycles, not recover the impacted cycle's split.

### Likelihood Explanation
This requires a witness (an on-chain role obtainable by anyone via `WitnessCreateContract` plus sufficient votes) to act maliciously against its own voters — a similar trust assumption to the original finding's "malicious aggregator owner," which the C4 judge still rated Medium severity due to the concrete, uncapped, unilateral loss of yield it causes. No additional privilege beyond being a registered witness is required, and the actuator itself performs no rate-of-change limiting or per-voter fee locking.

### Recommendation
Introduce a brokerage-change delay/notice period longer than one maintenance cycle (or require multiple cycles before a change takes effect), and/or snapshot the brokerage rate applicable to already-delegated votes so that a rate increase only applies to newly cast votes, analogous to the mapping-based fix Maia adopted for `BoostAggregator`.

### Proof of Concept
1. Witness `W` registers and keeps the default 20% brokerage; voters delegate votes to `W` across several cycles, accruing pool rewards via `MortgageService.payReward` (`brokerage=20`).
2. `W` submits `UpdateBrokerageContract{ownerAddress=W, brokerage=100}`; `UpdateBrokerageActuator.execute()` accepts it since `100 <= ActuatorConstant.ONE_HUNDRED` and stores it at `DelegationStore` key `(REMARK, W)`.
3. At the next `MaintenanceManager.doMaintenance()` run, `delegationStore.setBrokerage(nextCycle, W, 100)` is written unconditionally for the upcoming cycle.
4. From that cycle forward, `payReward` computes `brokerageAmount = value` (100%) and credits it entirely to `W`'s allowance, while `delegationStore.addReward(cycle, W, 0)` leaves zero for delegating voters, who receive `0` reward when calling `withdrawReward`/`queryReward` despite still having votes locked on `W`.

    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);

    delegationStore.addReward(cycle, witnessAddress, value);

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
