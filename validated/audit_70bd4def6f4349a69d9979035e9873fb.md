### Title
Unauthenticated `/wallet/getassetissuebyaccount` triggers full O(N) table scan of all asset issues - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueByAccountServlet.java])

### Finding Description
The HTTP endpoint is served by `GetAssetIssueByAccountServlet.doGet`/`doPost`, which take an arbitrary, attacker-supplied `address` parameter (no authentication, no ownership check) and pass it straight to `wallet.getAssetIssueByAccount(address)` [1](#0-0) . Inside `Wallet.getAssetIssueByAccount`, when the chain parameter `AllowSameTokenName` is enabled, the implementation does not perform an indexed lookup keyed by owner address; instead it calls the asset-issue store's `getAllAssetIssues()`-style full iteration and then applies a `filter(... ownerAddress ...)` in-memory over every asset issue record before returning matches. The underlying store method backing that full-table scan is `AssetIssueStore.getAllAssetIssues()`, which iterates the entire underlying RocksDB column via `Streams.stream(iterator())` and materializes every `AssetIssueCapsule` in the database into a `List` [2](#0-1) . Because there is no secondary index on `ownerAddress`, this account-scoped query is implemented as a full linear scan of the entire asset-issue table for every single API call, regardless of caller identity or the target account.

### Impact Explanation
Any unprivileged client can invoke this HTTP endpoint with an arbitrary address (including non-issuer/non-existent addresses) and force the node to deserialize and filter every asset-issue record in the database on each call. As the total number of issued assets (N) on the network grows, per-request cost scales linearly (O(N)) with global chain state rather than being bounded by the requester's own account data, violating the invariant that account-scoped queries use indexed lookups. Repeated requests amplify CPU/I/O load on full nodes serving the HTTP API, degrading availability for other API consumers (a public-API resource-exhaustion / underpriced-work condition), though it does not by itself corrupt consensus state or steal funds.

### Likelihood Explanation
The endpoint is reachable without authentication over the public HTTP API (`FullNodeHttpApiService`) and is rate-limited only by `RateLimiterServlet`'s generic request-rate throttling, not by per-request computational cost [3](#0-2) . No special privileges, on-chain transaction, or contract call are required — a simple repeated GET/POST with arbitrary addresses is sufficient, and the cost scales automatically as the network's asset-issue table grows over time, making this fully repeatable.

### Recommendation
Add a secondary index keyed by `ownerAddress -> assetIssueId` (or store asset-issue references directly on the `AccountCapsule`) so that `getAssetIssueByAccount` performs a bounded, indexed lookup instead of `getAllAssetIssues()` plus an in-memory filter. Alternatively, cap/paginate the scan and apply per-endpoint cost-based rate limiting distinct from generic request-count throttling.

### Proof of Concept
Integration test plan:
1. Populate `AssetIssueStore` with a large number (e.g., 100k) of `AssetIssueCapsule` entries with distinct owner addresses via a test fixture.
2. Enable `AllowSameTokenName` in `DynamicPropertiesStore`.
3. Instrument/spy `AssetIssueStore.getAllAssetIssues()` (or measure iterator invocation count) and call `wallet.getAssetIssueByAccount(nonIssuerAddress)` for an address that owns zero assets.
4. Assert that `getAllAssetIssues()` is invoked and that it returns/iterates all N records (i.e., iterator count == total DB size), demonstrating the scan is not bounded by the queried account.
5. Measure wall-clock time for increasing N (e.g., 10k, 50k, 100k asset issues) and assert near-linear growth, confirming O(N) cost per request regardless of caller-supplied address.
