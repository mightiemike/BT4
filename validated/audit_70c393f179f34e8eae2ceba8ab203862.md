### Title
Missing declaration re-verification for cached Cairo0 classes in `StateReaderAndContractManager::get_compiled_from_class_manager` - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
`get_compiled_from_class_manager` re-validates that a cached class is still declared on-chain (`is_declared`) only for Cairo1 classes. Cairo0 (`RunnableCompiledClass::V0`) cache hits are returned unconditionally, without checking against the authoritative state whether the class hash is currently declared.

### Finding Description
The global `ContractClassManager` (`class_cache`/`GlobalContractCache`) is a long-lived, process-wide cache shared across proposal attempts (`propose_block`, `validate_block`, and view calls all construct `StateReaderAndContractManager` instances over the *same* `ContractClassManager` — see `StorageViewStateReaderFactory::create` at [1](#0-0) , and `NativeClassManager`/`TrivialClassManager::set_and_compile` populate this cache unconditionally as classes are executed [2](#0-1) ).

When resolving `get_compiled_class`, cache hits are handled asymmetrically:

```rust
if let Some(runnable_class) =
    self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
{
    match &runnable_class {
        RunnableCompiledClass::V0(_) => {}
        _ => {
            // The Cairo1 class is cached; verify it is declared,
            // since existence in the cache does not guarantee that
            // (it might contain a declared class from a reverted block, for example).
            if !self.state_reader.is_declared(class_hash)? {
                return Err(StateError::UndeclaredClassHash(class_hash));
            }
        }
    }
    ...
    return Ok(runnable_class);
}
``` [3](#0-2) 

The code comment itself acknowledges the exact bug class described in the report: a cache entry can persist from a state that never became canonical ("a declared class from a reverted block"), and the snapshot must be re-validated against the current authoritative state before being trusted. This re-validation (`is_declared`) is only performed for the `_` (Cairo1) branch; the `RunnableCompiledClass::V0(_)` branch is a no-op. This is directly analogous to the Arbitrum finding: a cached snapshot (`honestBlockChalLevelZeroEdge`/here, the cached `RunnableCompiledClass`) is not refreshed/re-validated against the authoritative source (`RefreshEdgesFromChain`/here, `state_reader.is_declared`) before being used to make a decision (`findAncestorInChallenge`/here, treating the class hash as validly declared).

The associated regression test suite (`state_reader_and_contract_manager_test.rs`) explicitly exercises this scenario for Cairo1 (`cairo_1_declared_then_verification_failed_after_reorg`) but has no equivalent Cairo0 case, confirming the gap is untested [4](#0-3) [5](#0-4) .

### Impact Explanation
If a Cairo0 class hash is executed/cached by the shared `ContractClassManager` during a proposal or view-call attempt that is subsequently discarded (e.g. an aborted/failed proposal, or a proposal built by this node that loses to another proposer, or a validated-but-unaccepted block) — a scenario the file's own comment says is possible ("a declared class from a reverted block") — a later `get_compiled_class` call on that class hash by any unprivileged caller (e.g. a `DEPLOY`/library-call referencing that class hash, or the gateway/batcher servicing subsequent transactions) will return the stale Cairo0 class as if it were currently declared, with no check against the node's actual, authoritative declared-class state. Since resolving whether a class is declared gates contract deployment and class-hash validation, this can let a class hash be treated as declared on one node (which still has the stale cache entry) while another honest node without that cache entry correctly rejects it as `UndeclaredClassHash`. That produces honest-node divergence in transaction execution results (differing state diffs / commitments) for the same block content — a wrong committed root/block-hash class of impact.

### Likelihood Explanation
The condition requires the shared, process-lifetime `ContractClassManager` cache to have been populated by execution of a Cairo0 declare/deploy in a proposal/validation attempt that did not end up committed, and for that class hash to then be referenced again by a transaction before the node restarts or the LRU entry is evicted. Given that `propose_block`/`validate_block` reuse one `ContractClassManager` across many proposal attempts per height (as seen in `Batcher`/`StorageViewStateReaderFactory`), and non-committed proposal attempts are a routine and frequent part of consensus (competing proposers, reproposals, view calls), this is readily reachable without any privileged access — it only requires normal declare/deploy transactions from ordinary senders across the sequence of proposal attempts.

### Recommendation
Apply the same re-validation performed for Cairo1 classes to the `RunnableCompiledClass::V0(_)` branch: call `self.state_reader.is_declared(class_hash)` (or an equivalent authoritative check) before returning a cached Cairo0 class, returning `StateError::UndeclaredClassHash` if it is no longer declared in the current state. Add a regression test mirroring `cairo_1_declared_then_verification_failed_after_reorg` for the Cairo0 (`V0`) case.

### Proof of Concept
1. Node builds/validates a proposal at height `N` that includes a `DECLARE` of a Cairo0 class `C` with hash `H`. During execution, `StateReaderAndContractManager::get_compiled_from_class_manager` is invoked, calling `contract_class_manager.set_and_compile(H, ...)`, populating the shared, process-wide `class_cache`.
2. This proposal is discarded (not committed) — e.g., a competing proposer's block wins consensus for height `N`, or the local proposal fails/aborts. The class `H` is *not* declared in the finally-committed state.
3. A subsequent transaction (from any unprivileged sender) references class hash `H` (e.g., attempts a `DEPLOY`/replace-class referencing `H`, or another declare/redeclare flow that queries `get_compiled_class`).
4. `get_compiled_from_class_manager` finds `H` in `contract_class_manager` (still cached from step 1) as `RunnableCompiledClass::V0`, hits the no-op match arm, and returns `Ok(runnable_class)` without ever calling `is_declared`, unlike the Cairo1 path.
5. A peer node that never built/validated the discarded proposal (and thus never cached `H`) correctly returns `UndeclaredClassHash` for the same transaction, producing divergent execution results/state diffs between honest nodes for identical block content.

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
