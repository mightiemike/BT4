### Title
Unbounded Request Body Buffering Before HMAC Validation in Webhook/Flow/Fulfillment-Service Authenticate Handlers Enables DoS - (File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts)

### Summary
The `authenticateWebhookFactory`, `authenticateFlowFactory`, and `authenticateFulfillmentServiceFactory` handlers in both `@shopify/shopify-app-remix` and `@shopify/shopify-app-react-router` all read the full request body into memory via `await request.text()` before performing any HMAC/signature validation on it. No maximum body size is enforced at this layer.

### Finding Description
In `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`, the handler checks only that the HTTP method is `POST`, then immediately does `const rawBody = await request.text();` and only afterward calls `api.webhooks.validate({rawBody, rawRequest: request})` to check the HMAC. [1](#0-0) 

The identical pattern (unbounded `request.text()` read prior to signature validation) exists in the react-router equivalent. [2](#0-1) 

The same unbounded-read-before-validation pattern also appears in the Flow and Fulfillment Service authenticate factories. [3](#0-2) [4](#0-3) 

By contrast, the Express package explicitly caps the body size to 500kb via `express.text({type: '*/*', limit: '500kb'})` before its equivalent webhook `process` handler runs. [5](#0-4) 

These `authenticate.public.*` / `authenticate.webhooks` / `authenticate.flow` / `authenticate.fulfillmentService` endpoints are reachable by any anonymous, unauthenticated HTTP POST request to the app's configured route — there is no prior authentication gate before the body is fully buffered into a JS string in server memory.

### Impact Explanation
Because `request.text()` has no size ceiling in these Remix/React Router adapters, an attacker who discovers or guesses the webhook/flow/fulfillment-service callback URL (these are typically public, predictable paths like `/webhooks`) can send arbitrarily large POST bodies. Each such request forces the Node process to buffer the entire payload into memory before any cryptographic validation rejects it. Repeated or concurrent large-payload requests can exhaust process memory or CPU (string concatenation/GC pressure), degrading or crashing the app server — a Denial of Service condition, directly analogous to the WASM-file-size DoS pattern in the reference report (processing large/unbounded input before any validity/size check is applied).

### Likelihood Explanation
The affected routes are unauthenticated by design (they must accept unauthenticated webhook calls from Shopify), and their paths are typically fixed/well-known (`/webhooks`, flow/fulfillment paths configured by the app). No credentials, session, or prior trust relationship is needed to reach the vulnerable code path — only network access to the app's public endpoint is required, making this practically exploitable by any anonymous actor.

### Recommendation
Impose an explicit maximum body size before or during `request.text()` in the Remix and React Router `authenticate.webhooks`, `authenticate.flow`, and `authenticate.fulfillmentService` factories — mirroring the 500kb limit already used in `shopify-app-express`'s `processWebhooks` middleware. This can be done by checking `Content-Length` up front and rejecting oversized requests, or by wrapping the body stream read with a byte-count cap that aborts once exceeded, prior to buffering the full payload into memory.

### Proof of Concept
```ts
// Any anonymous client can POST an arbitrarily large body to the app's
// webhook/flow/fulfillment-service route, e.g.:
fetch('https://merchant-app.example.com/webhooks', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: 'A'.repeat(500 * 1024 * 1024), // 500MB payload, no size limit enforced
});
// authenticateWebhookFactory's `await request.text()` will attempt to
// buffer the entire 500MB body into memory before the HMAC check in
// api.webhooks.validate() ever runs and rejects it as invalid.
```
