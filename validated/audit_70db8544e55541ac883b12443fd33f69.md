### Title
Stale zToken price/index cache after in-batch bad-debt socialization causes mispriced collateral in `liquidate-multi` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` caches each vault's borrow index and liquidity index (`lindex`) per block in the `index-cache` map, keyed only by `{timestamp: stacks-block-time, aid: aid}`, and reuses that cached value for every subsequent price/valuation lookup of the same asset within the same block [1](#0-0) . This cache is treated as authoritative for zToken price resolution during liquidation ("accrue FIRST - populates cache for zToken price resolution", "NOW safe to resolve prices (cache is populated)") [2](#0-1) . However, when a liquidated position has no collateral left, `liquidate` writes off the remaining debt by calling into the vault's `socialize-debt`, which mutates `lindex` directly with `var-set` rather than through the normal accrual path the cache assumes [3](#0-2) . Nothing purges or refreshes the `index-cache` entry for that asset id when this happens.

### Finding Description
The root cause is a per-block cache that is never invalidated when its underlying source (`lindex`, which determines zToken/share value) is mutated by a non-accrual code path:

1. `accrue-and-cache` is the single gate for zToken pricing: on a cache MISS it calls `vault-accrue`, stores `{index, lindex}` in the persistent `index-cache` map under key `{timestamp: stacks-block-time, aid}`, and on a cache HIT it simply returns the stored value with no re-validation against current vault state [1](#0-0) .
2. `liquidate` explicitly relies on this cache being fresh: it calls `accrue-user-debts`/`accrue-user-collateral` (which populate the cache) before resolving any USD notional values, with the comment "NOW safe to resolve prices (cache is populated)" [2](#0-1) .
3. Later in the same `liquidate` call, if the borrower's collateral is exhausted, the function socializes any remaining debt by folding `socialize-debt-asset` over the debt list, which invokes the vault's public `socialize-debt` [4](#0-3) .
4. The vault's `socialize-debt` directly overwrites `lindex` (and `principal-scaled`, `total-borrowed`, `assets`) with `var-set` to reflect the write-off — this is a state mutation to the exact value (`lindex`) that market's `index-cache` had already snapshotted for that block [3](#0-2) .
5. `liquidate-multi` batches up to 64 independent `(borrower, collateral-ft, debt-ft, debt-amount)` liquidations inside one atomic transaction, explicitly noting that "failed liquidations return error codes but don't revert entire batch" — i.e., multiple positions are processed sequentially in the same call and same block [5](#0-4) .
6. Because the `index-cache` key only depends on `(timestamp, aid)` and not on any "generation"/"dirty" marker tied to `socialize-debt`, any position processed later in the same `liquidate-multi` batch (or any other call in the same block) that shares the same ztoken asset id as collateral or debt will hit the now-stale cache entry from step 2, re-using the pre-socialization `lindex` instead of the just-written post-loss `lindex`.

This is the "cached value not invalidated when its source moves" pattern applied within Clarity's deterministic, sequential fold/let evaluation inside a single transaction: the cache-write (step 2) and the source-mutation (step 4) both occur before the cache-read (step 6) in program order, but only the mutation updates ground truth — the cache is never told to refresh.

### Impact Explanation
Because `lindex` determines how much underlying value each zToken share represents, using a stale (pre-write-off) `lindex` for a later position in the same batch causes that position's zToken collateral or debt to be misvalued in USD. Overvaluing collateral could let liquidations under-seize or a position wrongly stay outside the liquidation threshold, temporarily freezing bad debt that should have been recognized/liquidated, or lead to incorrect debt-repaid/collateral-seized amounts being executed and locked in during that atomic call — this is a temporary freezing of funds impact, and if the direction of the mispricing lets a party extract more collateral than the true state supports, it edges toward theft of protocol funds/insolvency. Given the batching design's explicit purpose ("prevents front-running attacks that prevent bad debt socialization"), it is realistic for a `liquidate-multi` call to touch multiple positions that share ztoken debt/collateral, especially in a market with limited underlying assets (STX, sBTC, stSTX, USDC, USDH, stSTXbtc) shared across many egroups.

### Likelihood Explanation
The trigger requires no special privileges: any liquidator can submit a `liquidate-multi` transaction ordering multiple eligible liquidatable positions such that a position whose debt gets fully socialized (no remaining collateral) is processed before another position sharing the same asset id. This is fully attacker-controlled ordering within a single transaction and requires only that bad debt socialization occurs for at least one position in the batch — a condition the protocol explicitly anticipates and handles (bad-debt-socialized event, `filter-out-debt-asset`, etc.) [4](#0-3) .

### Recommendation
Invalidate or bypass the `index-cache` entry for an asset id immediately after any direct mutation of that vault's `index`/`lindex` outside of the standard accrual path (e.g., in `socialize-debt`), or fold a monotonically increasing "generation" counter into the cache key that is bumped whenever `socialize-debt` runs, forcing subsequent `accrue-and-cache` calls in the same block to re-query the vault rather than trusting the stale snapshot.

### Proof of Concept
1. Liquidator submits a single `liquidate-multi` transaction with two entries: Position A (borrower whose collateral will be fully exhausted by this liquidation, triggering bad-debt socialization on debt asset `X`) and Position B (a different borrower holding zToken collateral or debt also keyed to asset `X`).
2. During processing of Position A: `accrue-and-cache(X)` runs (cache MISS), storing `{index, lindex}` for asset `X` at the current `stacks-block-time` [1](#0-0) ; the liquidation completes and, because no collateral remains, `socialize-debt-asset` calls the vault's `socialize-debt`, which `var-set`s `lindex` to a new (loss-adjusted) value [3](#0-2) .
3. During processing of Position B (same transaction, same `stacks-block-time`): `accrue-and-cache(X)` is called again for pricing Position B's collateral/debt in asset `X`; this hits the `index-cache` entry written in step 2 and returns the pre-socialization `lindex`, not the vault's true post-socialization `lindex`.
4. Position B's collateral/debt USD valuation, and consequently its liquidation eligibility and seized/repaid amounts, are computed against a stale share value, producing an incorrect liquidation outcome for Position B within the very same atomic transaction.

Note: I was not able to fully read the complete body of `liquidate-multi` and the private `socialize-debt-asset` fold helper before the tool budget was exhausted, so I could not verify from source whether any additional cross-position cache-clearing logic exists inside `liquidate-multi` that might mitigate this. The finding is based on the confirmed cache design in `accrue-and-cache`, the confirmed direct `lindex` mutation in `socialize-debt`, and the confirmed atomic multi-position nature of `liquidate-multi`; a full review of `liquidate-multi`'s implementation is recommended to conclusively confirm exploitability across positions in the same batch.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
