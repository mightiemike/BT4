## Finding: `TransactionOutput::ensure_match_transaction_info` never checks the state-checkpoint (JMT) root hash, letting replay-verify tooling accept a diverged state root as a passing replay

### Title
Replay-verify comparator skips state/hot-state/position checkpoint hash validation, causing state-root divergence to go undetected - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used by replay/debug tooling to decide whether a locally re-executed transaction "matches" the authenticated on-chain `TransactionInfo`. It validates status, gas, write-set hash, and event root hash, but it never validates `state_checkpoint_hash` (the Jellyfish Merkle state root), `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The gap is self-documented in the code itself as a known TODO, but is already live and is the sole verification used by `storage/db-tool/src/replay_on_archive.rs`.

### Finding Description
`ensure_match_transaction_info` checks status, gas, write-set hash, and event root hash, but explicitly stops short of validating the checkpoint hash fields: [1](#0-0) 

The comment at the end of the function admits the gap directly: [2](#0-1) 

This function is used as the sole per-transaction acceptance check in the archive replay-verification tool `replay_on_archive`, which compares VM-executed outputs against the `expected_txn_infos` pulled from a backup/archive and reports "failed txns" only for mismatches this function detects: [3](#0-2) 

Because `state_checkpoint_hash` (the JMT state root committed in every `TransactionInfo`, gated by no feature flag) is never compared, a divergence between the locally computed state root and the authenticated on-chain state root at that version is silently accepted as a passing replay, regardless of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. The same weak comparator is also referenced from `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`, spreading the blind spot to other operator-facing debug/replay flows.

For contrast, the actual consensus/state-sync commit paths use a stricter, whole-`TransactionInfo` hash comparison (`ensure_transaction_infos_match` in `execution/executor-types/src/ledger_update_output.rs`, invoked from `execution/executor/src/chunk_executor/chunk_result_verifier.rs`), which does implicitly cover the checkpoint hashes since they are part of the hashed `TransactionInfo`. So the live commit/sync path is not affected — the break is isolated to the archive replay-verify/debug tooling that relies specifically on `ensure_match_transaction_info`.

### Impact Explanation
Replay-verify tooling exists precisely to catch state-commitment divergence (e.g., a non-determinism bug in the VM or in state-checkpoint/JMT construction) between archived, already-committed ledger data and a fresh local re-execution. Because the comparator never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a real state-root divergence introduced by a bug elsewhere in the stack (e.g., in `DoStateCheckpoint`, hot-state merge logic, or sharded state-merkle commit) would not be flagged by `replay_on_archive`, `aptos-debugger`, or the CLI replay commands. Operators, auditors, or automated CI relying on this tool for confidence that historical execution reproduces the authenticated ledger state would get false-positive "replay succeeded" results even though the durable state root differs from the correct VM/state result — a direct violation of the "committed state must not differ from correct VM result, and this must be detectable via proof/replay tooling" invariant.

### Likelihood Explanation
Low likelihood of triggering by itself (it requires an independent state-root-affecting bug to exist elsewhere), but the *masking* condition itself is unconditional and always present today wherever `ensure_match_transaction_info` is called — it is not behind any feature flag for the `state_checkpoint_hash`/`hot_state_checkpoint_hash` checks (only the TODO calls out `position_state_checkpoint_hash` as tied to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`). This means the replay-verify safety net is silently degraded on every invocation, which is a systemic tooling-integrity gap rather than a one-off edge case.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values (recomputing them from the post-transaction state view where the caller has access to it, as `DoStateCheckpoint` does), and fail loudly on mismatch, before any code path that gates on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Proof of Concept
Not independently reproducible as an on-chain exploit — the gap is a tooling/detection blind spot, not a consensus-path bug. Conceptual PoC:
1. Suppose any bug elsewhere (e.g. a JMT commit path or hot-state merge bug) causes locally re-executed state to hash to a different `state_checkpoint_hash` than the one recorded in the archived `TransactionInfo`, while `write_set`, `events`, `gas_used`, and `status` still match.
2. Run `replay_on_archive` (`storage/db-tool/src/replay_on_archive.rs::execute_and_verify`) over the affected version range.
3. `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) returns `Ok(())` because it never inspects `state_checkpoint_hash`.
4. `replay_on_archive` reports zero failed transactions — a "clean" replay — despite the underlying state root diverging from the authenticated ledger.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
