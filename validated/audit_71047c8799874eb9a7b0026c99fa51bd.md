### Title
Meta-transaction (`DelegateAction`) signatures omit any chain/network-binding value, enabling cross-network replay of signed delegate actions - (File: `core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

### Summary
`DelegateAction`/`DelegateActionV2` (NEP‑366 meta transactions) are signed via `get_nep461_hash()`, which hashes a `SignableMessage` consisting only of a NEP discriminant plus the `DelegateAction` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). Unlike ordinary `SignedTransaction`s, which are bound to a specific chain via a recent `block_hash` field, the delegate-action signing payload contains no chain-identifying value (no genesis hash, no chain/network id, no live block hash) — only a bare `BlockHeight` integer used purely as an expiry threshold.

### Finding Description
`SignedDelegateAction::verify()` and `VersionedSignedDelegateAction::verify()` check the signature over `delegate_action.get_nep461_hash()`: [1](#0-0) [2](#0-1) 

The hashed `SignableMessage` is simply a NEP discriminant tag concatenated with the borsh-serialized `DelegateAction`/`DelegateActionV2` struct: [3](#0-2) [4](#0-3) 

None of `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, or `public_key` identify which chain/network the signer intended the message for — `max_block_height` is only a plain integer height acting as an expiry ceiling, not a hash of a specific block/chain history. This is analogous to the reported Opyn bug: EIP-712's `domainSeparator` binds a signature to a specific `chainId` to stop replay across forks/other chains; NEP‑366's scheme has no equivalent binding.

On-chain replay validation in `apply_delegate_action` / `validate_delegate_action_key` only checks (1) signature validity, (2) `max_block_height` vs current height, (3) `sender_id` matches receiver, and (4) access-key nonce monotonicity — none of these are chain-specific: [5](#0-4) [6](#0-5) 

Because NEAR runs multiple networks that can share account/key state (e.g., a network fork, a state-cloned shadow/testnet, or any future chain sharing genesis state with mainnet), a `SignedDelegateAction` produced by a user for one network can be replayed verbatim on another network as long as: the target network's block height is still below `max_block_height`, and the sender's access key nonce on that network has not yet advanced past `nonce`. Both conditions are commonly true right after a fork/clone, since heights and nonces start identical on both chains.

### Impact Explanation
A relayer that submits a `SignedDelegateAction` obtained off-chain from a user has no protocol-level guarantee that the signature is scoped to the network it is submitting to. If the same account and access key exist on a second network (fork, testnet clone with copied mainnet state, or a future hard-fork producing two live chains), an attacker or a malicious/compromised relayer can replay the identical `SignedDelegateAction` on the second network to execute the delegated actions (e.g., transfers, key additions, function calls) there without the user's fresh consent for that network — causing unauthorized value movement or unauthorized state changes on the other chain, funded/paid for by whichever relayer submits it there. This satisfies "concrete unauthorized value movement" / "invalid state transition acceptance" criteria, since the action executes exactly as originally authorized but on an unintended chain.

### Likelihood Explanation
Requires two live NEAR networks/chains that share enough account state (account existing with the same access key and nonce, e.g. right after a network fork or a state-cloned deployment) for the nonce/height checks to still pass on both sides. This is a realistic scenario for chain forks, disaster-recovery/backup chains restored from mainnet state, or testnets that periodically re-sync from mainnet snapshots — all legitimate NEAR-ecosystem operational patterns, not a purely theoretical assumption. It does not require any malicious validator, peer, or privileged party — only a signed `DelegateAction` obtained by any party able to observe it (e.g., a relayer, or anyone the user shared it with) and access to submit it as a transaction on the second network.

### Recommendation
Include a chain-binding value in the NEP-461/NEP-366 signable payload for delegate actions — e.g., the genesis hash or a `ChainId`/`network_id` string — analogous to how `SignedTransaction` binds to a recent `block_hash`. Concretely, add a chain-identifying field to `DelegateAction`/`DelegateActionV2` (or embed it into the `SignableMessage` discriminant/context in `signable_message.rs`) and verify it against the current chain's genesis/network id in `apply_delegate_action`/`validate_delegate_action_key` before accepting the delegate action.

### Proof of Concept
1. On Network A (e.g. mainnet), user Alice signs `DelegateAction { sender_id: "alice.near", receiver_id: "ft.near", actions: [transfer_action], nonce: N, max_block_height: H, public_key: Alice_key }` producing `SignedDelegateAction` via `SignedDelegateAction::sign` (`core/primitives/src/action/delegate.rs:92-95`).
2. Network B is a fork/clone of Network A's state at a height below `H`, where `alice.near`'s access key for `Alice_key` still has nonce `< N` (true immediately after any fork/state-clone).
3. Submit the identical `SignedDelegateAction` bytes as a transaction's `Action::Delegate` on Network B. `apply_delegate_action` verifies the signature successfully (`runtime/runtime/src/actions.rs:474-477`), height check passes (`:479-482`), sender match passes (`:483-490`), and nonce check in `validate_delegate_action_key` passes since Network B's stored nonce is still below `N` (`runtime/runtime/src/actions.rs:602-646`).
4. The delegated transfer action executes on Network B exactly as authorized only for Network A, without Alice's intent or fresh signature for Network B.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

    /// Delegate action hash used for NEP-461 signature scheme which tags
    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
        let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
        hash(&bytes)
    }

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
