## Analysis

The Cooler bug class is: a counter-party fully controls the code/response inside a callback, and can make that callback fail in a way that blocks the legitimate account holder from ever completing a state-changing action again, effectively freezing their assets. The closest reachable analog in this nearcore checkout is in the **NEAR Wallet Contract** (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`), which is the account contract every ETH-implicit account runs, and which any signer/RPC caller reaches directly via `rlp_execute`.

### Title
Untrusted NEP-141 token response can permanently lock the ETH-implicit Wallet Contract via `has_in_flight_tx` rollback - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`WalletContract` guards every mutating call behind a single in-flight flag, `has_in_flight_tx`, which is reset to `false` as the *first statement* of each promise callback and set back to `true` only after a new promise is successfully scheduled. [1](#0-0)  If the callback function body panics for any reason after that reset line runs, the entire receipt (and therefore all of its state writes, including the `has_in_flight_tx = false` write) is rolled back atomically, leaving the flag stuck at `true` forever.

### Finding Description
`rlp_execute` refuses to start any new transaction while `has_in_flight_tx` is `true`: [2](#0-1) 

For an emulated ERC-20 transfer, the contract schedules a call to `storage_balance_of` on the attacker-influenceable `target` token account, and its response is consumed inside `nep_141_storage_balance_callback`, whose very first line resets the flag: [3](#0-2) 

The value returned by the (attacker-controlled) `target` account is deserialized with `serde_json::from_slice(&value)` inside this same receipt, whose wasm execution has only the residual gas left over from `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (a small fixed 15 Tgas budget shared with two forwarded sub-calls) after the deposit/transfer/callback sub-promises are scheduled: [4](#0-3) 

Because `target` is chosen by the signer of the RLP-encoded Ethereum transaction and can be any account (there is no allow-list requiring a real, honest NEP-141 contract), an attacker can point an `ERC20Transfer` action at their own malicious contract that returns an oversized or deeply-nested JSON blob from `storage_balance_of`. Deserializing that payload consumes the small residual gas budget of the `nep_141_storage_balance_callback` receipt and causes a `GasExceeded` panic. Because NEAR receipt execution is all-or-nothing, this panic reverts every state write already made in that receipt — including the `self.has_in_flight_tx = false` line executed at the top of the function. The flag remains permanently `true`.

The identical structural pattern exists in `address_check_callback`, which also resets the flag first and later deserializes an externally supplied `Option<AccountId>` payload from the address-registrar response before doing further work: [5](#0-4) 

Once `has_in_flight_tx` is stuck at `true`, every subsequent call to `rlp_execute` — the only entry point for using this account, since ETH-implicit accounts cannot have a full-access key or be deleted, per the docs — is rejected forever: [6](#0-5) 

This mirrors the Cooler pattern exactly: an external party the victim is forced to interact with (a token/registrar contract chosen as `target`) controls data that flows into a privileged callback, and can weaponize it to make that callback fail, permanently denying the victim the ability to complete their own future legitimate actions (in Cooler: repay; here: any future `rlp_execute`).

### Impact Explanation
An ETH-implicit account can only be operated through `WalletContract::rlp_execute`. If `has_in_flight_tx` is stuck `true`, the account is permanently unable to transfer NEAR/tokens, call contracts, add relayer keys, or otherwise move funds ever again through this contract — a state-transition-triggered permanent freeze of funds, satisfying the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Reachable by a single unprivileged transaction/RPC caller: the attacker only needs to be the signer of the Ethereum-style transaction (or convince a victim/relayer to route through a malicious token) so that `target` in `rlp_execute` points to attacker-deployed contract code returning an oversized/malformed `storage_balance_of` response (or, via `address_check_callback`, a malformed registrar `lookup` response). No validator/network/operator privilege is required.

### Recommendation
Do not perform gas-sensitive external-data deserialization before persisting `has_in_flight_tx = false`, or better, persist the flag reset in a way that is not tied to the same all-or-nothing receipt that also parses attacker-controlled payloads (e.g. write the flag via a separate low-risk promise/action, or bound/validate the size of `promise_result` payloads before deserializing them, or reserve sufficient dedicated gas independent of forwarded sub-call gas for the parsing logic so a crafted payload cannot exhaust it).

### Proof of Concept
1. Attacker deploys a NEAR contract implementing `storage_balance_of` that returns a very large/deeply nested JSON payload (sized to exhaust the residual gas left in the `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget after sub-promise gas is reserved).
2. Attacker (or a victim tricked into using this token as an ERC-20 target) submits an RLP-encoded `ERC20Transfer` through `rlp_execute` with `target` = attacker's malicious contract.
3. `inner_rlp_execute` schedules `storage_balance_of` → `nep_141_storage_balance_callback`; `has_in_flight_tx` is set `true` before returning the promise. [7](#0-6) 
4. When the callback executes, it resets `has_in_flight_tx = false`, then attempts to deserialize the oversized payload and panics with `GasExceeded`.
5. The whole receipt (including the flag reset) is rolled back; `has_in_flight_tx` remains `true` in persisted state.
6. Any future `rlp_execute` call from the legitimate account owner is rejected with "transaction already in progress", permanently, since no code path exists to clear the flag once stuck.
