### Title
VRF v2 fee estimation uses stale Chainlink price feed data without freshness validation - (File: core/services/vrf/v2/listener_v2_log_processor.go)

### Summary
The VRF v2 listener's `estimateFee` function reads the LINK/ETH price from a Chainlink `AggregatorV3Interface`-style feed via `LatestRoundData()` and uses the returned `Answer` directly to compute the LINK cost of fulfilling a VRF request, without validating the freshness (`UpdatedAt`) or completeness (`AnsweredInRound`) of the round data, mirroring the exact bug class described in the external report for `JBChainlinkV3PriceFeed.currentPrice()`.

### Finding Description
In `estimateFee`, when a VRF request is paid for in LINK (i.e., not `NativePayment()`), the code queries the price aggregator and passes only `roundData.Answer` into `EstimateFeeJuels`, ignoring `roundData.UpdatedAt`, `roundData.StartedAt`, and `roundData.AnsweredInRound`: [1](#0-0) 

`EstimateFeeJuels` then divides the estimated wei cost by this unchecked `weiPerUnitLink` value to compute the juels cost of fulfillment: [2](#0-1) 

There is no comparison of `updatedAt` against `block.timestamp`/current time, no round-completeness check (`answeredInRound >= roundId`), and no fallback/circuit-breaker logic if the aggregator returns a stale or zero price — exactly the missing controls Chainlink's own documentation (and the referenced report) recommend.

### Impact Explanation
This fee estimate feeds into `simulateFulfillment`, which decides the maximum LINK cost the node is willing to accept for fulfilling a randomness request (used to validate `req.SubID`/wallet balance against the estimated cost) as part of the VRF v2 pipeline invoked from `runPipelines`. If the LINK/ETH aggregator becomes stale (e.g., during high volatility, an outage, or a compromised/paused feed) the computed `weiPerUnitLink` could diverge significantly from the true market price. This can cause:
- The node to underestimate the LINK cost of fulfillment, potentially causing the VRF request to revert on-chain due to insufficient LINK, or
- The node to overestimate cost and refuse to service requests that should be fulfillable, or
- In coordinator contracts that trust off-chain-estimated pricing for gas/fee bookkeeping, systematic misreporting of the VRF fulfillment cost.

Because this only affects the off-chain fee estimate used to decide whether/how to simulate and submit a fulfillment transaction (the actual charge is ultimately enforced on-chain by the VRFCoordinator contract), the direct fund-loss impact is bounded, but it can still cause denial-of-service (spurious pipeline failures) or economically incorrect fulfillment decisions by the node operator.

### Likelihood Explanation
Likelihood is moderate: it requires the configured LINK/ETH price aggregator feed to become stale or return outdated data (an external dependency failure, not attacker-controlled on the Chainlink node itself), which Chainlink's own guidance highlights as a plausible real-world occurrence (feed heartbeat delays, outages, deviation thresholds not met). No malicious node/operator action is required — it's a data-consumption gap in the node's own fee-estimation logic.

### Recommendation
- Validate `roundData.UpdatedAt` against a configurable staleness threshold (heartbeat) before using `roundData.Answer` in `estimateFee`.
- Reject non-positive (`Answer <= 0`) or incomplete rounds (`AnsweredInRound < RoundId`).
- On staleness/invalidity, fall back to a safe default price, skip fee estimation gracefully, or surface an error/alert rather than silently using potentially incorrect pricing.
- Consider consistency with the staleness-threshold patterns already used elsewhere in the codebase (e.g., Automation/Keeper `StalenessSeconds`/`FallbackLinkPrice` and CCIP `TokenPriceStalenessThreshold`), which explicitly implement exactly this kind of check but is absent in the VRF v2 `estimateFee` path.

### Proof of Concept
1. Configure a VRF v2 job with a LINK/ETH price aggregator whose underlying feed stops updating (simulate via a mock aggregator that returns a fixed old `UpdatedAt` timestamp).
2. Trigger a `RandomWordsRequested` event with LINK payment (`NativePayment() == false`).
3. Observe that `lsn.aggregator.LatestRoundData()` in `estimateFee` (`core/services/vrf/v2/listener_v2_log_processor.go:1079`) returns stale `Answer`/`UpdatedAt` values, yet the code proceeds directly to `EstimateFeeJuels` without any check, producing a juels cost estimate based on out-of-date market pricing — with no logged warning or fallback distinguishing this from a fresh, valid price.

func (lsn *listenerV2) estimateFee(
	ctx context.Context,
	req RandomWordsRequested,
	maxGasPriceWei *assets.Wei,
) (*big.Int, error) {
	// NativePayment() returns true if and only if the version is V2+ and the
	// request was made in ETH.
	if req.NativePayment() {
		return EstimateFeeWei(req.CallbackGasLimit(), maxGasPriceWei.ToInt())
	}

	// In the event we are using LINK we need to estimate the fee in juels
	// Don't use up too much time to get this info, it's not critical for operating vrf.
	callCtx, cancel := context.WithTimeout(ctx, 1*time.Second)
	defer cancel()
	roundData, err := lsn.aggregator.LatestRoundData(&bind.CallOpts{Context: callCtx})
	if err != nil {
		return nil, fmt.Errorf("get aggregator latestAnswer: %w", err)
	}

	return EstimateFeeJuels(
		req.CallbackGasLimit(),
		maxGasPriceWei.ToInt(),
		roundData.Answer,
	)
}

// EstimateFeeJuels estimates the amount of link needed to fulfill a request
// given the callback gas limit, the gas price, and the wei per unit link.
// An error is returned if the wei per unit link provided is zero.
func EstimateFeeJuels(callbackGasLimit uint32, maxGasPriceWei, weiPerUnitLink *big.Int) (*big.Int, error) {
	if weiPerUnitLink.Cmp(big.NewInt(0)) == 0 {
		return nil, errors.New("wei per unit link is zero")
	}
	maxGasUsed := big.NewInt(int64(callbackGasLimit + GasProofVerification))
	costWei := maxGasUsed.Mul(maxGasUsed, maxGasPriceWei)
	// Multiply by 1e18 first so that we don't lose a ton of digits due to truncation when we divide
	// by weiPerUnitLink
	numerator := costWei.Mul(costWei, big.NewInt(1e18))
	costJuels := numerator.Quo(numerator, weiPerUnitLink)
	return costJuels, nil
}
