### Title
`liquidate-multi()` masks a mid-flow `liquidate()` failure as success, leaving partially executed debt/collateral state committed - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi()` calls `liquidate()` through the private helper `call-liquidate()` using a plain (same-contract) function application inside `map`, not `contract-call?`. In Clarity, automatic state-rollback-on-error is scoped to `contract-call?` invocation boundaries, not to plain in-contract function calls. `liquidate()` performs several state-mutating `contract-call?`s to `.v0-market-vault` (`debt-remove-scaled`, `collateral-remove`) *before* a later guard (`asserts! (get success socialization-result) ...`) can fail. Because `call-liquidate` invokes `liquidate` directly and `liquidate-multi` wraps every element's `Response` (ok or err) into a `map` result that itself always returns `(ok (list ...))`, the top-level transaction commits successfully even when an individual position's `liquidate()` call errors out partway through. The debt-removal and collateral-removal that already ran as their own successful `contract-call?`s stay committed, while the bad-debt-socialization step (and the reporting of that position as failed) is the only part that is "rolled back"/skipped.

### Finding Description
`liquidate()` in `mainnet/contracts/market/v0-4-market.clar` executes in this order: [1](#0-0) 
1. `vault-system-repay` (liquidator repays the vault) — `try!`'d, own `contract-call?` boundary.
2. `debt-remove-scaled` on `.v0-market-vault` — `try!`'d, own `contract-call?` boundary, commits borrower's debt reduction.
3. `collateral-remove` on `.v0-market-vault` — `try!`'d, own `contract-call?` boundary, commits collateral transfer to the liquidator. [2](#0-1) 

Only *after* these three commits does the function evaluate the "bad debt socialization" branch, which can fail via: [3](#0-2) 

That `asserts!` failure makes `liquidate()` itself return `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`. When `liquidate()` is called directly at the top level (via `contract-call?` from a transaction), Clarity's checkpoint semantics roll back everything committed during that top-level call, so `liquidate()` used stand-alone is safe.

`liquidate-multi()`, however, invokes `liquidate` through `call-liquidate`, a plain in-contract helper function, inside `map`: [4](#0-3) [5](#0-4) 

Because `call-liquidate` → `liquidate` is a same-contract function application (not `contract-call?`), no rollback checkpoint is created for that individual `liquidate` invocation. The `map`/`liquidate-multi` combinator only ever produces `(ok (list of Response values))` — the outer public-function boundary that Clarity *does* checkpoint always evaluates to `ok`. As a result:
- The successful `contract-call?`s made *inside* the failing `liquidate` call (`debt-remove-scaled`, `collateral-remove`) are individually committed and are never unwound, since the enclosing `liquidate-multi` transaction commits as `ok`.
- The one thing that is "aborted" is only the final socialization/print step of that specific position and its outward-facing `Response`, which the caller sees as `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)` in the returned list — misleadingly suggesting nothing happened for that position.

This is the direct Clarity analog of the H-22 pattern: a multi-step entry point (`liquidate` invoked through `liquidate-multi`) moves value/state in early sub-steps (debt cleared, collateral seized) and then hits a later guard failure, but because the failure is absorbed by the batch wrapper instead of reverting the whole call, the already-moved value/state is stranded in an inconsistent, partially-executed condition rather than being unwound or fully completed.

### Impact Explanation
A borrower's debt obligation can be reduced and their collateral seized and sent to the liquidator via committed `contract-call?`s, while the corresponding bad-debt socialization (writing down the vault's liquidity index to account for the loss) never executes and the batch caller is told this specific position "failed." This leaves the vault's internal accounting inconsistent — debt was cleared and collateral removed without the compensating write-down that keeps liquidity-index accounting solvent, i.e., a temporary freezing/mis-accounting of protocol assets. This is a fund-safety issue affecting the vault's collective backing (protocol insolvency risk category), not merely a UX inconvenience, since it can be triggered by any liquidator submitting a position designed to hit the socialization-failure branch inside a `liquidate-multi()` call.

### Likelihood Explanation
Triggering this requires crafting a `liquidate-multi()` batch containing a position that ends up with `no-collateral-left = true` and where the subsequent `fold socialize-debt-asset` fails (e.g., `vault-socialize-debt` or `debt-remove-scaled` inside `socialize-debt-asset` returning an error for some reason, such as the debt list becoming inconsistent). This is a specific, engineered corner case rather than something hit in every liquidation, so likelihood is moderate — it requires an attacker/liquidator to deliberately construct or discover a socialization-failure condition, but it is reachable purely through public, permissionless liquidation calls without any privileged access.

### Recommendation
Route `call-liquidate`/`liquidate` invocations inside `liquidate-multi()` through an actual `contract-call?` boundary (e.g., by wrapping the per-position call so that Clarity's checkpoint mechanism applies per position), or restructure `liquidate()` so the bad-debt-socialization guard is evaluated and asserted *before* any of the state-mutating `debt-remove-scaled`/`collateral-remove` calls commit. Alternatively, make `liquidate-multi()` itself assert on and abort entirely if a position's socialization fails rather than swallowing the error into a list, or use `contract-call?` explicitly for each `liquidate` sub-call so each position's checkpoint is independent and correctly rolled back on failure.

### Proof of Concept
1. Construct a borrower position that will be fully liquidated (`no-collateral-left = true` after `collateral-remove`).
2. Ensure the subsequent `fold socialize-debt-asset` over the borrower's remaining debt list fails for at least one asset entry (e.g., by having `vault-socialize-debt` or the nested `debt-remove-scaled` on `.v0-market-vault` return an error for that asset ID — achievable by racing/state manipulation on the target debt asset such that its scaled amount check in `vault-socialize-debt` fails at fold time).
3. Call `liquidate-multi()` with this position included in the `positions` list, per [5](#0-4) .
4. Observe that:
   - The transaction as a whole succeeds (`ok`).
   - The returned list contains `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)` for that position.
   - Querying the borrower's position afterward shows debt already reduced (`debt-remove-scaled` committed) and collateral already removed (`collateral-remove` committed), per [2](#0-1) , even though the reported result for the position was an error and the compensating socialization never ran.

*Note: full confirmation of this finding depends on Clarity's documented per-`contract-call?` rollback-checkpoint semantics (rollback is scoped to `contract-call?` invocations, not same-contract plain function calls used by `call-liquidate`/`map`). This is standard, well-documented Clarity VM behavior, but it was not independently re-verified against a live Clarity VM trace in this session; a Devin session with tool/test access could confirm this precisely via the local-testing harness.*
