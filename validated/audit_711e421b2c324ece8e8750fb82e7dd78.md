### Title
Webhook shop-domain header is not bound to the HMAC-signed body, allowing cross-tenant webhook context forgery - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
The vulnerability report describes a Solidity contract that trusts a user-controlled `amount`/action combination without verifying that a corresponding real asset transfer occurred, letting one user manipulate balances belonging to other users. The analogous flaw here is a **binding gap** between what is cryptographically verified (the raw webhook body) and what is trusted unverified (the `X-Shopify-Shop-Domain` header), which is then used to select which tenant's session/access token gets attached to the payload.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` validates a webhook by computing an HMAC only over `rawBody` [1](#0-0) , and then separately reads unauthenticated headers — including the shop `domain` — via `checkWebhooksHeaders`/`checkEventsHeaders` [2](#0-1) . The HMAC signature never covers the `domain`, `topic`, `webhookId`, or other headers — only the body bytes. This means a request whose body carries a valid HMAC for the app's secret can be paired with **any** attacker-chosen `domain` header, and the check will still return `valid: true` with that forged `domain` [3](#0-2) .

Downstream, `authenticateWebhookFactory` (shopify-app-remix and shopify-app-react-router) takes `check.domain` at face value to look up/create the **offline session** for that shop and attach an authenticated `admin` client to the webhook context, while `payload` is the attacker-controlled JSON body: [4](#0-3) . `ensureValidOfflineSession` loads/creates a session strictly keyed by the `shop` string passed in [5](#0-4) .

Any actor who can obtain one genuine (body, HMAC) pair from Shopify — e.g., a merchant who has installed the app on their own store and receives real webhooks signed with the app's shared secret (the same secret is used for HMAC across all shops using the app) — can replay that request to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (also serviced by the same app). Because the HMAC only signs the body, the forged request still validates, and the webhook handler executes with `shop: <victim>`, `session`/`admin` scoped to the victim's offline access token, but `payload` fully controlled by the attacker.

### Impact Explanation
This breaks tenant isolation between shops that share the same app installation. An attacker-controlled payload gets processed under a victim shop's authenticated admin session, letting the attacker's webhook handler code act (create/update/delete resources, trigger business logic) against the victim's store using the victim's access token, while attributing the event data to the wrong tenant. This matches the "cross-tenant access" acceptance criterion, analogous to the Hub contract crediting a user's vault without verifying the underlying asset actually moved for that specific account.

### Likelihood Explanation
Exploitability requires: (1) the attacker to be an app user/merchant able to trigger at least one real webhook delivery for their own shop (a normal, unprivileged capability of any merchant installing a public app), and (2) the target victim shop to also have the app installed (so an offline session exists). No secret material or MITM position is required — only replaying an unmodified body with a different header value, which any HTTP client can do since HMAC validation never inspects headers.

### Recommendation
Bind identity-critical fields (`domain`/`shop`) into the value that is cryptographically authenticated, or independently cross-check the header-provided `domain` against shop identity encoded in the payload (where available) before attaching a session/admin client. At minimum, apps and this library should not implicitly trust `X-Shopify-Shop-Domain` as authoritative for session lookup without further binding to the signed content, and should treat mismatches as invalid.

### Proof of Concept
1. Merchant M installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `PRODUCTS_CREATE`), capturing the POST body and its valid `X-Shopify-Hmac-Sha256` header.
2. M resends the exact same body/HMAC to the app's `/webhooks` endpoint but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (a shop where the app is also installed).
3. `validateFactory` HMAC-validates the (unchanged) body successfully and returns `domain: 'victim-shop.myshopify.com'` from the forged header [6](#0-5) .
4. `authenticateWebhookFactory` loads the victim's offline session and admin client, then invokes the app's webhook handler with `payload` controlled by M but `admin`/`session` authenticated as the victim shop [4](#0-3) .

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}
