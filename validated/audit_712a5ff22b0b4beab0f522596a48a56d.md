### Title
Cross-tenant unauthorized job run triggering via EI-to-job ownership bypass in PipelineRunsController.Create - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Create` (core/web/pipeline_runs_controller.go:109-125) gates integer-ID job runs solely on whether `auth.GetAuthenticatedUser(c)` returns an authenticated user object, but `AuthenticateExternalInitiator` (core/web/auth/auth.go:143-148) unconditionally injects a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` into the same `SessionUserKey` context slot used by real logged-in users. As a result, the `isUser` check cannot distinguish a legitimate session/token user from any authenticated External Initiator, and the handler never verifies that the target job's `ExternalInitiatorWebhookSpec` (core/services/job/models.go:462-468) actually names the calling EI.

### Finding Description
The code path is:
1. `AuthenticateExternalInitiator` validates the EI's access key/secret against `bridges.ExternalInitiator` records via `FindExternalInitiator` and `bridges.AuthenticateExternalInitiator` [1](#0-0) , then sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` — identical regardless of which EI authenticated [2](#0-1) .
2. `PipelineRunsController.Create` retrieves `_, isUser := auth.GetAuthenticatedUser(c)` and, if `isUser` is true, parses the URL `:ID` param as an int32 and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly, with no ownership or EI-to-job binding check whatsoever [3](#0-2) .
3. The inline comment "`only users are allowed to run jobs using int IDs - EIs not allowed`" documents the intended invariant, but the implementation only checks for presence of *any* `SessionUserKey` value — which `AuthenticateExternalInitiator` always populates — so the intended EI exclusion is not actually enforced in code; both real users and any authenticated EI satisfy `isUser`.
4. There is no code in `Create` that loads `job.ExternalInitiatorWebhookSpec` for the target job ID and cross-checks it against `auth.GetAuthenticatedExternalInitiator(c)`'s identity, meaning any EI credential — valid for job A's webhook spec — can supply an arbitrary integer job ID for job B and have `RunJobV2` execute it.

### Impact Explanation
An attacker holding legitimate EI credentials issued for one webhook job (job A) can trigger pipeline runs for any other webhook or non-webhook job on the same node by integer ID, causing unauthorized execution of pipelines belonging to other job configurations/tenants sharing the node. This can cause unwanted external HTTP calls, bridge invocations, on-chain transaction attempts, or resource exhaustion tied to jobs the attacker has no legitimate relationship to — a cross-tenant/cross-job authorization bypass ("unauthorized workflow execution" class impact).

### Likelihood Explanation
Preconditions are exactly as attacker-scoped: possession of one valid EI access key/secret pair (obtained legitimately for job A) and knowledge/guessing of another job's small monotonically-increasing integer ID. Job IDs are sequential integers exposed via job listing (`GET /v2/jobs`) or events, making enumeration straightforward. The exploit requires only a single unauthenticated-adjacent HTTP POST once EI credentials are held, so it is trivially repeatable.

### Recommendation
In `PipelineRunsController.Create`, when the request is authenticated as an External Initiator (`auth.GetAuthenticatedExternalInitiator(c)`), look up the target job's `WebhookSpec.ExternalInitiatorWebhookSpecs` and verify the authenticated EI's ID is present among them before calling `RunJobV2`; reject with 401/403 otherwise. Additionally, stop conflating EI identity with generic user identity in `SessionUserKey` — use a distinct marker/role or carry EI-specific authorization context through to the controller so `isUser` checks cannot be satisfied by EI auth alone.

### Proof of Concept
Integration test (extending `core/web/pipeline_runs_controller_test.go` patterns):
1. Create two External Initiators, `eiA` and `eiB`, via `cltest.CreateExternalInitiatorViaWeb`.
2. Create webhook job A with `externalInitiators = [{name = eiA.Name, ...}]`, and webhook job B with `externalInitiators = [{name = eiB.Name, ...}]`.
3. Authenticate as `eiA` (using its access key/secret headers) and POST to `/v2/jobs/<jobB.ID>/runs` (job B's integer ID, not job A's).
4. Assert expectation: request should be rejected (401/403) since `eiA` is not part of job B's `ExternalInitiatorWebhookSpecs`.
5. Current behavior (bug): `isUser` is true because `AuthenticateExternalInitiator` sets `SessionUserKey`, so `RunJobV2` executes job B's pipeline and returns 200 with a `pipelineRun` resource, proving unauthorized cross-tenant execution — assert `cltest.AssertCountStays` fails to hold i.e. `pipeline_runs` count for job B increases despite `eiA` having no association with it.
