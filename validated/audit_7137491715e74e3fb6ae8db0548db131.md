### Title
Constant calls default to full block-processing CPU deadline instead of a bounded constant-call limit when `vm.constantCallTimeoutMs=0` (default) - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.calculateCpuLimitInUs` only applies the dedicated constant-call timeout when `constantCallTimeoutMs > 0`; with the shipped default of `0` (`common/src/main/resources/reference.conf` line 815, `VmConfig.constantCallTimeoutMs = 0L`), every `TriggerConstantContract`/`eth_call` invocation instead falls through to `maxCpuTimeOfOneTxMs * 1000 * cpuLimitInUsRatio`, i.e. the same CPU budget used for real block-processing transactions. This lets an unprivileged caller run a maximal-cost precompile workload (e.g. BN128 pairing) inside a free, feeless-to-broadcast constant call for as long as a full transaction is allowed to run.

### Impact Explanation
This is a query-path DoS: an anonymous, unprivileged RPC/HTTP caller (no funded account, no signed broadcast transaction needed) can invoke `TriggerConstantContract` against any deployed contract containing a maximal-cost BN128 pairing loop and consume CPU time up to the full `maxCpuTimeOfOneTx` block-processing deadline per call, repeatable at will and in parallel across many RPC connections. Because constant calls are execute-only (no block inclusion, no fee payment enforced unless the node operator opts into throttling), this allows cheap/free repeated CPU exhaustion of the FullNode/SolidityNode process, degrading availability for all API consumers — matching the "DoS via RPC-API" bounty impact class.

### Likelihood Explanation
Preconditions are exactly the shipped defaults: `vm.constantCallTimeoutMs` unset (`= 0`) as in `common/src/main/resources/reference.conf`, and `vm.supportConstant`/HTTP or gRPC APIs enabled (also common production configuration, since constant calls are a core, widely-used feature). No privileged role, no fee payment, and no special network access is required — only a standard `TriggerConstantContract`/`eth_call` request against a contract exercising BN128 pairing (or any other CPU-heavy precompile/opcode sequence). This is fully attacker-controlled and trivially repeatable.

### Recommendation
Set a materially tighter default for `vm.constantCallTimeoutMs` (nonzero) so constant/query calls are always bounded well below `maxCpuTimeOfOneTx`, rather than defaulting to "share the block-processing deadline." Alternatively, change `calculateCpuLimitInUs` to apply a hardcoded conservative ceiling for `isConstantCall` even when `constantCallTimeoutMs == 0`, so operators who don't explicitly configure the value are not silently exposed to the same CPU budget as full transaction execution.

@Test
public void constantCallDefaultsToFullBlockDeadline() {
  long maxCpuTimeOfOneTxMs = 50; // e.g. node's configured block-processing CPU limit
  double ratio = 1.0;            // ET_PRE_TYPE always uses ratio 1.0 for constant calls
  long constantCallTimeoutMs = 0; // shipped default from reference.conf

  long limit = VMActuator.calculateCpuLimitInUs(
      true, maxCpuTimeOfOneTxMs, ratio, constantCallTimeoutMs);

  // Fails to demonstrate a bounded constant-call limit:
  // constant call gets the same deadline as a full transaction.
  assertEquals(maxCpuTimeOfOneTxMs * 1000L, limit);
}

  static long calculateCpuLimitInUs(boolean isConstantCall, long maxCpuTimeOfOneTxMs,
      double cpuLimitInUsRatio, long constantCallTimeoutMs) {
    if (isConstantCall && constantCallTimeoutMs > 0L) {
      return constantCallTimeoutMs * VMConstant.ONE_THOUSAND;
