### Title
Receipt Size Limit Bypassed via `promise_return` and `value_return` Paths, Allowing Oversized Receipts to Enter the System — (`runtime/runtime/src/lib.rs`)

---

### Summary

The `max_receipt_size` hard limit (4 MiB) can be bypassed through two distinct execution paths in the nearcore runtime. A contract can produce receipts that exceed `max_receipt_size` without triggering `ReceiptValidationError::ReceiptSizeExceeded`. These oversized receipts are forwarded across shards, violating the `ChunkStateWitness` size invariant. The codebase acknowledges this as a live bug (issue #12606) and has added workarounds to prevent permanent sticking, but the root invariant — that no receipt may exceed `max_receipt_size` — remains broken and reachable by any unprivileged user.

---

### Finding Description

**Path 1 — `promise_return` with post-validation `output_data_receivers` injection**

In `apply_action_receipt`, each new receipt created by an action is validated with `validate_receipt(..., NewReceipt)` at line ~871 (per the spec anchor at `runtime/runtime/src/lib.rs:848`). This check measures the receipt's borsh size and rejects it if it exceeds `max_receipt_size`.

However, at lines 1031–1049, *after all actions have been validated*, the runtime checks whether the parent receipt has `output_data_receivers`. If the contract called `promise_return(C)`, the parent's `output_data_receivers` are appended directly to receipt C's `output_data_receivers` field without re-running `validate_receipt`:

```rust
// runtime/runtime/src/lib.rs:1040-1047
ReceiptEnum::Action(new_action_receipt)
| ReceiptEnum::PromiseYield(new_action_receipt) => new_action_receipt
    .output_data_receivers
    .extend_from_slice(&action_receipt.output_data_receivers()),
```

A contract can craft receipt C to be exactly `max_receipt_size` bytes (passing validation), then call `promise_return(C)` from a context where the parent has one or more `output_data_receivers`. Each `DataReceiver` is ~70 bytes (account ID + data ID). The final receipt C exceeds `max_receipt_size` with no error.

**Path 2 — `value_return` with data at `max_length_returned_data`**

`value_return` in `logic.rs:3934` checks only `max_length_returned_data` (also 4,194,304 bytes). A contract returning exactly 4,194,304 bytes passes this check. The runtime then wraps the return value in a `Data` receipt at lines 1056–1068:

```rust
Receipt::V0(ReceiptV0 {
    predecessor_id: account_id.clone(),
    receiver_id: data_receiver.receiver_id.clone(),
    receipt_id: CryptoHash::default(),
    receipt: ReceiptEnum::Data(DataReceipt {
        data_id: data_receiver.data_id,
        data: data.clone(),
    }),
})
```

The borsh-serialized `Data` receipt includes `predecessor_id`, `receiver_id`, `receipt_id`, `data_id`, and the data payload. With 4,194,304 bytes of data plus ~200 bytes of envelope, the total receipt size exceeds `max_receipt_size = 4,194,304`. This `Data` receipt is never passed through `validate_receipt(..., NewReceipt)` — it is created directly and pushed to `result.new_receipts`.

**Workarounds present but invariant still broken**

The codebase has two mitigations that prevent permanent sticking:

1. `try_forward` clamps oversized receipt sizes to `max_receipt_size` for forwarding limit comparisons (line 418–426).
2. `generate_bandwidth_request` applies the same clamp (line 562).
3. `ValidateReceiptMode::ExistingReceipt` skips the size check when processing receipts already in state.

These workarounds allow the oversized receipts to be forwarded and processed, but they do not prevent the invariant violation.

---

### Impact Explanation

The `max_receipt_size` limit exists to keep `ChunkStateWitness` under 17 MiB. A single oversized receipt can be up to ~8 MiB (4 MiB data + envelope), consuming nearly half the total witness budget for one receipt. With multiple such receipts in a chunk, the witness can exceed 17 MiB, potentially causing stateless validators to reject the chunk or diverge from the chunk producer's result. The `per_receipt_storage_proof_size_limit` (4 MB hard limit) can also be hit during execution of these oversized receipts, causing them to fail with a storage proof error rather than a clean `ReceiptSizeExceeded` error — a different failure mode than intended.

The broken invariant is: **no receipt produced by contract execution may exceed `max_receipt_size`**. Both paths violate this invariant from ordinary user-submitted transactions.

---

### Likelihood Explanation

Any unprivileged user can deploy a contract using the standard NEAR SDK and trigger either path:
- Path 1: create a near-maximum-size receipt and call `promise_return` from a chained promise context.
- Path 2: call `value_return` with exactly `max_length_returned_data` bytes from a contract that has `output_data_receivers`.

No special permissions, validator access, or privileged keys are required. The test contracts in `near_test_contracts::rs_contract()` already implement both triggering methods (`max_receipt_size_promise_return_method2`, `max_receipt_size_value_return_method`).

---

### Recommendation

1. **Re-validate after `output_data_receivers` injection**: After appending `output_data_receivers` to receipt C at `runtime/runtime/src/lib.rs:1040–1047`, call `validate_receipt(..., NewReceipt)` again on the modified receipt. If it now exceeds `max_receipt_size`, return a `NewReceiptValidationError`.

2. **Account for `Data` receipt envelope in `max_length_returned_data`**: Set `max_length_returned_data` to `max_receipt_size - DATA_RECEIPT_OVERHEAD` (where `DATA_RECEIPT_OVERHEAD` is the borsh size of a `Data` receipt with empty data, approximately 200 bytes), so that a maximum-size return value still produces a receipt within the limit.

3. **Remove the workarounds once the root cause is fixed**: The size-clamping in `try_forward` and `generate_bandwidth_request` can be removed after the above fixes are deployed via protocol upgrade.

---

### Proof of Concept

The bug is demonstrated by two existing tests in `test-loop-tests/src/tests/max_receipt_size.rs`:

- `test_max_receipt_size_promise_return` (line 130): deploys a contract, calls `max_receipt_size_promise_return_method1` which chains `promise_return` with a near-maximum-size receipt, then asserts via `assert_oversized_receipt_occurred` that a receipt above `max_receipt_size` was forwarded on-chain.

- `test_max_receipt_size_value_return` (line 216): calls `max_receipt_size_value_return_method` which returns exactly `max_receipt_size` bytes, then asserts an oversized receipt was forwarded.
