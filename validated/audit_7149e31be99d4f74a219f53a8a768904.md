## Finding

### Title
L1 handler messages are marked consumed even when execution hard-fails, permanently freezing bridged funds - (File: `crates/apollo_batcher/src/block_builder.rs`)

### Summary
The Alchemix bug pattern is: an entity (the `from` veNFT) is irrevocably destroyed (`_burn`) before the value it still holds (unclaimed ALCX rewards) is settled, so the reward becomes permanently unreachable. The sequencer analog is in the batcher's block-building loop, where an `L1Handler` transaction's hash is unconditionally added to the "consumed" set *before* the code even inspects whether execution actually succeeded, reverted, or hard-failed with an executor error.

### Finding Description
In `collect_execution_results_and_stream_txs`, for every `InternalConsensusTransaction::L1Handler`, the transaction hash is inserted into `execution_data.consumed_l1_handler_tx_hashes` unconditionally, prior to the `match result { Ok(..) => .., Err(..) => .. }` branch that determines whether the transaction actually executed: [1](#0-0) 

The subsequent `match result` only distinguishes `Ok`/`Err` for bookkeeping of `execution_infos_and_signatures` vs. `rejected_tx_hashes`, but the hash is already committed to `consumed_l1_handler_tx_hashes` regardless of the branch taken: [2](#0-1) 

This is explicitly validated by a unit test, `failed_l1_handler_transaction_consumed`, which feeds the executor a hard `TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress)` for one L1 handler transaction and a normal success for another, and then asserts that **both** transaction hashes end up in `consumed_l1_handler_tx_hashes`: [3](#0-2) 

Once a hash reaches the L1 events provider's `TransactionManager` as consumed, `mark_consumed` permanently transitions the record to `TransactionState::Consumed`, which is documented as an irreversible terminal state removing the transaction from the proposable index (i.e., it can never be retried again): [4](#0-3) [5](#0-4) 

This mirrors the reported bug class exactly: an irreversible state transition (`Consumed`/burn) is performed on the basis of the transaction merely being *processed* by the executor, rather than on the basis of its value-bearing effects (the L1→L2 message payload, e.g. a bridged deposit) having actually been credited to the target contract's storage. A hard executor error (distinct from a normal Cairo-level "reverted" L1 handler, which is expected and handled) means the transaction's state changes were never applied at all — yet the L1 message is treated identically to a successfully executed one.

### Impact Explanation
If an `L1Handler` transaction returns `Err(..)` from the executor (e.g., due to `StateError::OutOfRangeContractAddress`, or any other executor-level error that is possible only transiently — for instance because the target contract has not yet been deployed in this block's state view, or due to another state-dependent condition that could clear in a later block), the batcher still records the tx hash as consumed. This hash flows to the `apollo_l1_events` `TransactionManager`, which removes the record from the proposable set once consumption is committed. The L1→L2 message can never be re-included in any future block. Any funds or state changes that message was supposed to deliver (e.g., a bridged token deposit credited via the L1 handler's `execute_call_info`) are permanently and irrecoverably lost, matching the "Permanent freezing of unclaimed/bridged funds" impact category from a single, unprivileged L1 message — no operator or validator misbehavior is required.

### Likelihood Explanation
This path is reachable purely from the content of a single L1→L2 message chosen by any unprivileged L1 sender (e.g., a token/message bridge call), combined with any condition that makes the corresponding L1 handler transaction fail hard at the executor level rather than producing a normal Cairo revert (which is the only failure mode intentionally accounted for in the OS/blockifier, per `execute_l1_handler_transaction`'s `is_reverted` handling). The dedicated regression test proves this is current, unmitigated behavior of the batcher rather than a hypothetical corner case.

### Recommendation
Do not add an `L1Handler` transaction hash to `consumed_l1_handler_tx_hashes` when its executor result is `Err`. Only transactions that returned `Ok(..)` (whether reverted or successfully executed, per protocol) — meaning the OS successfully processed the consumption of the L1→L2 message as part of the transaction — should be treated as consumed. Hard executor errors should route the transaction through the same path as `rejected_tx_hashes`, so the underlying L1 message stays `Pending` and can be retried in a subsequent block/proposal, exactly as intended by the transaction-manager's `Pending`/`Consumed` state machine.

### Proof of Concept
The existing test `failed_l1_handler_transaction_consumed` in `crates/apollo_batcher/src/block_builder_test.rs` (lines 1064–1111) is itself the proof of concept: it constructs two L1 handler transactions, makes the executor return `Err(TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress))` for the first and a normal `Ok` result for the second, then asserts that `result_block_artifacts.execution_data.consumed_l1_handler_tx_hashes` contains **both** hashes — demonstrating that the failed (never-applied) L1 handler transaction is nonetheless marked consumed and will subsequently be permanently removed from the retry-eligible pool via `TransactionManager::mark_consumed`.

*Note: due to tool-call limits I was unable to fully trace whether `apollo_batcher/src/batcher.rs` (which also references `rejected_l1_handler_tx_hashes` / `consumed_l1_handler_tx_hashes`, per grep matches) performs any reconciliation/filtering between the two sets before calling `L1EventsProvider::commit_block`. If such filtering exists and correctly excludes hard-failed L1 handler transactions from the consumed set sent to the L1 provider, the practical exploitability of this issue would be mitigated at that later stage; this should be verified directly in `crates/apollo_batcher/src/batcher.rs`.*

    /// Mark a transaction as consumed on L1.
    /// The timestamp is the L1 block timestamp where this tx was marked consumed.
    /// If tx was not already consumed (expected result), return None.
    /// If tx was already consumed (double consumption), return the time when it was previously
    /// consumed. Note that double consumption is a bug.
    pub fn mark_consumed(&mut self, timestamp: BlockTimestamp) -> Option<BlockTimestamp> {
        if self.is_committed() {
            debug!("Marking a committed transaction {} as consumed.", self.tx.tx_hash());
        } else {
            // TODO(guyn): check if this situation should be an error.
            // TODO(guyn): check other state combinations that may be worth an error/warning/debug
            // log.
            debug!(
                "Marking a non-committed transaction {} as consumed. Previous state: {:?}",
                self.tx.tx_hash(),
                self.state
            );
        }
        self.state = TransactionState::Consumed;
        // First check if the tx was already consumed. Double consumption is a bug!
        // If None, it wasn't previously consumed: mark the time and return None to signal
        // everything is ok. If Some, it was already consumed: report the time when it was
        // previously consumed, the caller decides what to do.
        match self.consumed_at {
            Some(existing) => Some(existing),
            None => {
                self.consumed_at = Some(timestamp);
                None
            }
        }
    }

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct TransactionManager {
    /// Storage of all l1 handler transactions --- keeps transactions until they can be safely
    /// removed, like when they are consumed on L1, or fully cancelled on L1.
    pub records: Records,
    pub config: TransactionManagerConfig,
    /// Ordered lexicographically by scraping moment timestamp, then order-of-arrival for
    /// identical timestamps, also at any point the staged transactions are a prefix of the
    /// structure under this order.
    /// Invariant: contains all hashes of transactions that are proposable, and only them.
    /// Invarariant 2: Once removed from this index, a transaction will never be proposed again.
    proposable_index: BTreeMap<UnixTimestamp, Vec<TransactionHash>>,
    /// Generation counter used to prevent double usage of an l1 handler transaction in a single
    /// block.
    /// Calling `get_txs` or `validate_tx` tags the touched transactions with the current block
    /// counter, so that further calls will know not to touch them again.
    /// At the start and end (commit) of every block, the counter is incremented, thus "unstaging"
    /// all tagged transactions from the previous block attempt.
    // TODO(Gilad): remove "for rejected" from name when uncommitted is migrated to records DS.
    current_staging_epoch: StagingEpoch,
    /// All consumed transactions that are waiting to be removed from the transaction manager.
    /// Invariant: Ordered lexicographically by the block timestamp where they were marked as
    /// consumed, then order-of-arrival for identical timestamps.
    /// Invariant 2: A transaction is in the queue iff it is in the records and marked as consumed.
    consumed_queue: BTreeMap<BlockTimestamp, Vec<TransactionHash>>,
}
