### Title
`socialize-debt` write-down of the liquidity index uses stale, un-accrued vault state instead of normalized/current values - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
Every state-mutating vault entrypoint (`deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`) calls `(accrue)` first so that `index`, `lindex`, `total-borrowed` and `assets` reflect interest accrued up to the current block before any further math is performed. `socialize-debt` is the one exception: it computes the bad-debt write-down of `lindex` directly from the raw, un-accrued `index`/`assets`/`total-borrowed` variables, then the caller in the market contract triggers accrual only *after* the write-down has already been committed.

### Finding Description
`socialize-debt` reads the debt index and asset totals directly from storage without first calling `accrue`: [1](#0-0) 

`idx` is `(var-get index)` — the index as of `last-update`, not the current block. `old-total-assets` is `(total-assets)`, which itself is built from `total-debt` using that same stale `idx`: [2](#0-1) 

Both `debt-reduction` (the USD-equivalent of the bad debt being written off) and `old-total-assets` (the base the write-down ratio is applied against) are therefore computed from values that omit every second of interest accrued since `last-update`. `new-lindex` — the value every depositor's shares are valued against going forward — is then derived from this understated ratio:
```
new-lindex = current-lindex * (old-total-assets - debt-reduction) / old-total-assets
```
Compare this to `accrue`, which is the only place `index`/`lindex` are normally advanced, and which every other public entrypoint calls before touching reserve state: [3](#0-2) 

The caller of `socialize-debt` (the market's liquidation flow) makes the ordering bug explicit: it calls `vault-socialize-debt` (the write-down) *first*, and only afterward calls `vault-accrue` to "refresh the cache with new indexes post-write-down": [4](#0-3) 

So within the single liquidation transaction:
1. `index`/`assets`/`total-borrowed` are a cached snapshot from `last-update`, which "moves" (accrues) continuously as blocks pass.
2. `socialize-debt` consumes that stale snapshot to compute `debt-reduction` and `old-total-assets`, and permanently commits `lindex = new-lindex` using this un-normalized base.
3. Only after `lindex` has already been mutated does `vault-accrue` run, applying the pending interest to the *already-shrunk* `principal-scaled` and against the *already-corrupted* `lindex`.

The interest that accrued between `last-update` and the liquidation block is never factored into the write-down ratio, so the fraction of the loss socialized onto depositors is computed against an artificially low `old-total-assets`/`debt-reduction` pair rather than the true, currently-accrued reserve state — exactly the "raw vs normalized values" class of bug from the report, applied to `lindex` instead of the borrow/liquidity rate.

### Impact Explanation
`lindex` is the sole conversion factor between zToken shares and underlying assets for every depositor in the vault (`get-liquidity-index`, `convert-to-assets-preview`, `total-supply-preview`, etc. all derive from it). A single miscalculated write-down permanently mis-prices `lindex` for all subsequent redemptions/deposits in that vault:
- If `old-total-assets` is understated relative to the true, accrued value, the write-down fraction `(old-total-assets - debt-reduction) / old-total-assets` is more punitive than warranted, permanently destroying value for every depositor's shares beyond the actual bad debt — a permanent freezing/loss of depositor funds.
- Because the subsequent `vault-accrue` call re-applies interest on top of an already-corrupted `lindex`/`principal-scaled` base, the reserve's asset/liability accounting can also drift the other way over repeated socialization events, risking protocol insolvency (redemptions paying out more than the vault actually holds).

This satisfies the Critical impact bar (protocol insolvency / permanent freezing of funds at rest).

### Likelihood Explanation
`socialize-debt` is reached deterministically whenever a liquidation fully exhausts a borrower's collateral with debt remaining (`no-collateral-left` in `liquidate`) — a normal, expected occurrence in an undercollateralized-position liquidation, not requiring any privileged compromise, oracle manipulation, or multi-block timing. Any real-world period of elapsed time (any nonzero `time-delta` since `last-update`) between the vault's last accrual and the liquidation triggers the discrepancy, so the bug fires on essentially every socialization event where time has passed since the vault was last touched.

### Recommendation
Call `(try! (accrue))` at the top of `socialize-debt`, before reading `index`, `lindex`, `assets`, or `total-borrowed`, so that `debt-reduction` and `old-total-assets` are computed from the normalized, currently-accrued state — mirroring the pattern already used in `deposit`, `redeem`, `system-borrow`, and `system-repay`. Update the market's `socialize-debt-asset` caller accordingly so it no longer needs to re-accrue after the fact.

### Proof of Concept
1. Vault V has an outstanding borrow; time passes (e.g. one or more blocks) after `last-update` without any accrual-triggering call, so unrealized interest has accrued but `index`/`lindex`/`assets` remain at their stale, pre-accrual values.
2. A borrower's collateral price crashes; `liquidate()` in `v0-4-market.clar` seizes all collateral, leaving residual debt and setting `no-collateral-left`, which triggers `socialize-debt-asset` → `vault-socialize-debt` (the vault's `socialize-debt` in step 3 below).
3. `socialize-debt` computes `idx = (var-get index)` and `old-total-assets = (total-assets)` — both derived from the pre-liquidation, un-accrued `index`, omitting the interest that accrued since `last-update`. It computes `debt-reduction` from this stale `idx` and derives `new-lindex` from the understated `old-total-assets`, then commits `(var-set lindex new-lindex)`.
4. Immediately afterward, `socialize-debt-asset` calls `vault-accrue`, which advances `index`/`lindex` to reflect the interest that should have been included in step 3's math, but is now applied on top of the already-write-down-corrupted `lindex` and reduced `principal-scaled`.
5. All depositors' shares are now permanently valued against the corrupted `lindex`, producing systematically wrong payouts on every subsequent `redeem`/`convert-to-assets` call for that vault.
