Based on my research, I found a solid analog: java-tron's TRC10 Exchange (Bancor-style AMM) mixes raw token amounts of different decimal `precision` without any decimal normalization, mirroring the Zaros Vault decimal-scaling bug class.

### Title
TRC10 Exchange (Bancor relay) mixes raw balances of tokens with different `precision` without decimal normalization - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`, `ExchangeInjectActuator.java`, `ExchangeWithdrawActuator.java`, `ExchangeTransactionActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
TRC10 assets can be issued with a configurable `precision` field from 0 to 6 decimals [1](#0-0) , while TRX always implicitly uses 6 decimals (`sun`). The Exchange feature (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) implements a Bancor-relay-style AMM that pools a `firstTokenBalance`/`secondTokenBalance` pair and computes swap/inject/withdraw amounts purely from these raw `long` quantities, with no reference anywhere to each token's `precision` [2](#0-1) . This is directly analogous to the reported Zaros bug where `IERC4626(self.indexToken).totalAssets()` (native token decimals) was mixed into 18-decimal (`UD60x18`) math without scaling, corrupting USD accounting for low-decimal collateral.

### Finding Description
The `AssetIssueContract.precision` field (0–6) governs how many decimal places a TRC10 token's raw integer amount represents [3](#0-2) , and is validated to not exceed `ActuatorConstant.PRECISION_DECIMAL` (6) once the `AllowSameTokenName` proposal is active [1](#0-0) .

However, `ExchangeCreateActuator.execute`/`doValidate` take `firstTokenBalance`/`secondTokenBalance` directly as raw `long` quantities and store them into the `ExchangeCapsule` pool with no scaling factor applied based on each token's precision [4](#0-3) .

The core AMM logic in `ExchangeCapsule.transaction` (and the underlying `ExchangeProcessor`/`SafeExchangeProcessor` Bancor relay math) operates purely on these raw balances [2](#0-1) , and `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` similarly compute proportional amounts using raw integer balance ratios (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`) with no decimal normalization [5](#0-4) .

This means a "1 unit" difference is treated identically by the constant-product/relay math regardless of whether that unit represents `10^-6` of a token (precision=6) or a whole unit of a token (precision=0) or 1 sun of TRX (which is inherently `10^-6` TRX). Pools pairing tokens of different `precision` (or a precision>0 token against TRX or a precision=0 token) will have an effective exchange rate skewed by a factor of up to `10^6`, exactly the same class of bug as the reported Vault `totalAssets()` issue — raw native-precision amounts fed into value/ratio math that implicitly assumes a uniform unit scale.

### Impact Explanation
An attacker (any unprivileged TRON account holder — no special role required to call `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`/`ExchangeWithdrawContract`) can create or exploit an Exchange pool pairing a high-precision TRC10 token against a low-precision TRC10 token or TRX. Because the AMM math ignores `precision`, the effective price is mispriced by up to `10^6`, allowing systematic underpricing/overpricing of trades and extraction of value from counterparties or from a pool the attacker itself seeded, at the expense of other participants trading against that pool. This is a concrete accounting/mispricing impact directly reachable by unprivileged users through the public actuator API, matching the reported bug class (decimal-scaling omission corrupting value accounting).

### Likelihood Explanation
High. Creating an `ExchangeCreateContract` pairing tokens of arbitrary precision (0–6) is a normal, unprivileged, low-fee operation available to any account [6](#0-5) . No special conditions are needed beyond issuing/holding two TRC10 tokens (or one TRC10 + TRX) with differing decimal precision, which is a normal and expected configuration under the protocol's own precision rules.

### Recommendation
Normalize token amounts to a common internal scale (e.g., 6 decimals matching TRX/sun, or a fixed 18-decimal internal representation) before they enter the Exchange's Bancor relay / constant-ratio math in `ExchangeCapsule.transaction`, `ExchangeCreateActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, converting back to native precision only when crediting/debiting account balances. This mirrors the suggested Zaros fix of using a `convertTokenAmountToUd60x18`-style conversion before performing value/ratio math.

### Proof of Concept
1. Issue TRC10 token `A` with `precision = 0` (raw units = whole tokens) and TRC10 token `B` with `precision = 6` (raw units = micro-tokens), both permitted by `AssetIssueActuator.doValidate` [1](#0-0) .
2. Call `ExchangeCreateContract` to create a pool with `firstTokenBalance` = 1,000,000 units of `A` and `secondTokenBalance` = 1,000,000 units of `B` [4](#0-3) . Nominally this looks like a 1:1 pool, but economically it is 1,000,000 whole `A` tokens against 1 whole `B` token (since `B` has 6 decimals) — a 1,000,000x mispricing baked in at creation, undetected because no precision-based validation or scaling exists anywhere in the create/validate path.
3. Call `ExchangeTransactionContract` to swap a small amount of `B` for `A` using `ExchangeCapsule.transaction` [7](#0-6)  — the attacker receives `A` tokens at a rate reflecting the mispriced raw-integer pool ratio rather than true economic value, extracting value disproportionate to what was deposited.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
