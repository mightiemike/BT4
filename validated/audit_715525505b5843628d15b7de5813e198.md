### Title
Ancient-squash tombstone invariant is only enforced by a `debug_assert!`, not by code — silent loss of zero-lamport deletion markers in release builds - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
The report's bug class is "an invariant that documentation/one code path assumes is enforced elsewhere is never actually enforced in code," letting a privileged bypass slip through silently. The Agave analog is in `finish_combine_ancient_slots_packed_internal`, which assumes ancient squashing only ever touches slots that are older than `latest_full_snapshot_slot` (so `tombstones_to_carry_forward` is always empty), but this assumption is checked only with a `debug_assert!`, which compiles to a no-op in release builds.

### Finding Description
`shrink_collect` populates `tombstones_to_carry_forward` whenever a slot's zero-lamport single-ref accounts cannot yet be purged, i.e., when `can_purge_zero_lamport_single_ref_after_shrink(slot)` is false (the slot is newer than `latest_full_snapshot_slot`): [1](#0-0) 

The ancient-append-vec squash path (`combine_ancient_slots_packed_internal` → `calc_accounts_to_combine` → `shrink_collect`) reuses this same `shrink_collect` function, but its write-back path (`write_packed_storages`/`write_ancient_accounts`) only ever writes `alive_accounts`, never `tombstones_to_carry_forward`. The code documents and *assumes* this never matters because ancient squash "only runs on slots far older than the latest full snapshot," and enforces that assumption solely with a `debug_assert!`: [2](#0-1) 

If that assumption is ever violated — i.e., a slot processed by ancient squash is newer than `latest_full_snapshot_slot` — `shrink_collect` will populate `tombstones_to_carry_forward` for that slot, but `finish_combine_ancient_slots_packed_internal` proceeds to call `remove_old_stores_shrink`, which drops the original storage (and therefore the tombstone bytes) without ever writing the tombstones anywhere: [3](#0-2) 

In a debug build this would panic (`debug_assert!` fires); in a release build (the build used by validators) the assertion is compiled out, so the tombstone accounts are silently dropped and the old storage is removed. The slot selection for ancient squash is driven by `get_sorted_potential_ancient_slots`, whose `oldest_non_ancient_slot` boundary depends on the epoch schedule and the operator-configurable `ancient_append_vec_offset`, which the code comment explicitly says can be tuned ("offset is used to combine newer slots than we normally would. This is designed to be used for testing"): [4](#0-3) 

Unlike the analogous, and correctly enforced, `latest_full_snapshot_slot` gate used everywhere else in clean and normal shrink (`filter_zero_lamport_clean_for_incremental_snapshots`, `load_accounts_index_for_shrink`, `can_purge_zero_lamport_single_ref_after_shrink`), the ancient-squash write path has no runtime check that actually prevents processing a too-new slot or that carries the tombstone bytes forward — it only "documents" the invariant and validates it with a debug-only assertion, exactly mirroring the proxy-admin report's pattern of an invariant that is claimed/assumed in one place but not actually enforced by the code that matters.

### Impact Explanation
If a slot that is newer than `latest_full_snapshot_slot` is ever squashed into an ancient append vec (e.g. via a smaller `ancient_append_vec_offset`, or any future scheduling change that lets ancient-slot selection drift closer to the current slot), the zero-lamport "tombstone" marker for an account is permanently lost from storage in release builds. A subsequent incremental snapshot taken relative to the still-unadvanced full snapshot would then fail to propagate that account's deletion. On restart/rebuild from that full + incremental snapshot pair, the account would be restored with its old, non-zero balance from the full snapshot — a concrete stale/incorrect account balance and a snapshot-vs-replay divergence, exactly the kind of "silent balance change" / "honest-node snapshot-vs-replay mismatch" this analog analysis targets.

### Likelihood Explanation
Under default validator parameters, ancient-slot selection is bounded far enough in the past (roughly one epoch) that it is very unlikely to overlap with `latest_full_snapshot_slot`, so the condition is not hit in normal operation. However, the enforcement of the invariant relies entirely on scheduling behavior and a debug-only assertion rather than an actual runtime guard, so any change to ancient-slot selection logic, `ancient_append_vec_offset` tuning, or future refactors that alter timing between full-snapshot cadence and ancient-slot boundaries can silently violate the invariant in production (release) builds with no panic and no log to indicate corruption occurred.

### Recommendation
Add an explicit, non-debug runtime check in the ancient-squash write path (e.g., in `shrink_collect` when called for ancient squashing, or in `finish_combine_ancient_slots_packed_internal`) that either (a) refuses/defers squashing any slot for which `tombstones_to_carry_forward` is non-empty, or (b) writes the tombstones forward into the packed ancient storage just as normal shrink does, rather than relying on a `debug_assert!` that is compiled out in release builds.

    /// finish shrink operation on slots where a new storage was created
    /// drop root and storage for all original slots whose contents were combined into other storages
    fn finish_combine_ancient_slots_packed_internal(
        &self,
        accounts_to_combine: AccountsToCombine<'_>,
        mut write_ancient_accounts: WriteAncientAccounts,
        metrics: &mut SquashStatsSub,
    ) {
        let mut dropped_roots = Vec::with_capacity(accounts_to_combine.accounts_to_combine.len());
        for shrink_collect in accounts_to_combine.accounts_to_combine {
            let slot = shrink_collect.slot;

            // Ancient squash only runs on slots far older than the latest full snapshot, where
            // tombstones are purgeable and `shrink_collect` drops them rather than carrying them
            // forward. The squash write path has no tombstone handling, so a non-empty list here
            // would be silently lost; assert the invariant at the point that loss would occur.
            debug_assert!(
                shrink_collect.tombstones_to_carry_forward.is_empty(),
                "ancient squash reached a carry-forward tombstone at slot {slot}",
            );

            let shrink_in_progress = write_ancient_accounts.shrinks_in_progress.remove(&slot);

            let mut reopen = false;
            if shrink_in_progress.is_none() {
                dropped_roots.push(slot);
            } else {
                // Remember that we need to 'reopen' the storage for this
                // 'slot'. Note that it is not *safe* to reopen the storage for
                // the 'slot' here, because 'shrink_in_progress' is still alive.
                // Storage map may still point to the old storage and will be
                // updated to point to the new storage, after we drop
                // 'shrink_in_progress'.
                reopen = true;
            }

            self.remove_old_stores_shrink(
                &shrink_collect,
                &self.shrink_ancient_stats.shrink_stats,
                shrink_in_progress,
                true,
            );
