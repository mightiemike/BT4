### Title
Unbounded growth of per-shop session-ID list in `KVSessionStorage` causes DoS of `findSessionsByShop` (used by the `app/uninstalled` handler and installation checks) - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds()` appends a session ID to the per-shop index array on every `storeSession()` call without checking whether the ID is already present, unlike the equivalent Redis implementation. Because `storeSession` is re-invoked every time an offline/online session is (re-)created via OAuth or token exchange (using a deterministic ID such as `offline_<shop>` or `<shop>_<userId>`), the array backing `shop:${shop}` grows without bound as sessions expire and are refreshed. `findSessionsByShop()` and `deleteSessions()` then iterate/`Promise.all` over this ever-growing, duplicate-laden array, which is on the auth path (`AppInstallations.includes/delete`, called from webhook and installation-check handlers).

### Finding Description
`addShopIds` simply concatenates new IDs onto the existing list with no de-duplication: [1](#0-0) 

Compare this with the Redis adapter's equivalent function, which explicitly checks `includes()` before pushing: [2](#0-1) 

`storeSession` calls `addShopIds` unconditionally on every store, including re-stores of a session whose ID already exists in the list (offline sessions use the fixed ID `offline_<shop>`; online sessions use `<shop>_<userId>`): [3](#0-2) 

This function is reached from normal, unprivileged auth flows: every time a merchant's OAuth or token-exchange flow re-stores the offline/online session (e.g. on token refresh, re-auth, or repeated `ensureInstalledOnShop`/`token-exchange` invocations when no active session is found), the same ID is appended again: [4](#0-3) [5](#0-4) 

Once the array grows, every call to `findSessionsByShop` (which fetches and `Promise.all`s a `loadSession` per stored ID, including duplicates) becomes progressively more expensive: [6](#0-5) 

`findSessionsByShop`/`deleteSessions` are used by `AppInstallations`, which is invoked from the `app/uninstalled` webhook handler and installation checks — both part of the app's auth/installation-lifecycle machinery: [7](#0-6) [8](#0-7) 

### Impact Explanation
Over the lifetime of a single shop's installation, the KV value at `shop:${shop}` grows unbounded as sessions are refreshed (which happens routinely — offline tokens are re-exchanged when missing/expired, online per-user tokens are re-minted hourly/per session-token refresh). A merchant/user who can trigger repeated re-authentication (e.g., by forcing session invalidation, using multiple staff accounts with `useOnlineTokens`, or simply over normal long-term usage) causes:
- Unbounded growth of a single KV value, eventually risking the KV value-size limit.
- Increasingly slow and resource-intensive `findSessionsByShop` calls (fetching and loading every duplicate ID), which are invoked on the uninstall webhook path and installation checks — degrading or effectively DoS'ing that auth-adjacent handler for the affected shop over time.

This is a genuine denial-of-service risk for a specific shop's session-management path, though it requires sustained/repeated triggering rather than a single request, so severity is moderate.

### Likelihood Explanation
Likelihood is moderate-to-high in deployments using `@shopify/shopify-app-session-storage-kv`: no attacker sophistication is needed since the bug is triggered by ordinary session refresh/re-auth flows that any merchant/app installation naturally exercises over time, and can be accelerated by a malicious/curious merchant deliberately invalidating sessions or using many staff logins with online tokens enabled.

### Recommendation
Update `KVSessionStorage.addShopIds` (and `removeShopIds`) to de-duplicate before storing, mirroring the Redis adapter's `includes()` check, e.g.:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```
Additionally, consider pruning expired session IDs from the list during `findSessionsByShop`/`storeSession`, and enforcing a maximum list size with periodic cleanup to bound worst-case iteration cost.

### Proof of Concept
1. Configure an app with `KVSessionStorage` and `useOnlineTokens: true`.
2. Repeatedly force the offline/online session to be considered inactive (e.g., wait for natural expiry or manipulate the stored `expires` field) and re-trigger the token-exchange/OAuth flow for the same shop (`GET /auth?shop=...` or the embedded token-exchange path).
3. Observe that each re-store call appends a duplicate entry to the `shop:${shop}` KV list without removing prior (possibly duplicate/expired) entries.
4. After N re-auth cycles, call `findSessionsByShop(shop)` (e.g., via the `app/uninstalled` webhook handler) and observe that the number of `loadSession` calls performed grows linearly with N, unboundedly increasing latency/resource usage for that shop's session lookups.

    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }
