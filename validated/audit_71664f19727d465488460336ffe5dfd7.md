### Title
Missing slippage protection on the auto-calculated counter-asset amount in `ExchangeInjectContract`/`ExchangeWithdrawContract` - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeTransactionContract` (the trade-execution path) has an on-chain slippage guard via the `expected` field, checked in `ExchangeTransactionActuator.doValidate()` [1](#0-0) . However, `ExchangeInjectContract` and `ExchangeWithdrawContract` — the two-sided liquidity operations on the same TRX/TRC10 bancor-style `Exchange` pool — have no equivalent bound. Their protobuf messages only carry `owner_address, exchange_id, token_id, quant` [2](#0-1) , with no user-supplied min/max for the automatically-computed `anotherTokenQuant`. This is the same bug class as Sherlock M-5: an operation that touches two amounts has slippage protection on one side only (here, none at all on the derived side).

### Finding Description
`ExchangeInjectActuator` lets the exchange pool's creator inject `quant` of `token_id`; the actuator computes the required `anotherTokenQuant` of the paired asset from the *current* pool ratio and force-debits it from the caller's account, with no way for the caller to cap it: [3](#0-2) 
Execution recomputes the same ratio-dependent value again at execute() time from the (potentially already-mutated) `ExchangeCapsule` balances and immediately deducts it from the account, with no ceiling check: [4](#0-3) 

`ExchangeWithdrawActuator` has the symmetric problem on the receiving side: the amount of the paired asset returned to the withdrawer is derived from the live pool ratio, with no minimum-received guard supplied by the caller: [5](#0-4) 

Because the `Exchange` pool's `firstTokenBalance`/`secondTokenBalance` (the "price") can be moved by any anonymous account issuing an `ExchangeTransactionContract` trade against the pool earlier in the same block, a pending `ExchangeInject`/`ExchangeWithdraw` transaction — submitted by the exchange creator based on an off-chain simulation of the ratio — can execute against a materially different ratio by the time it lands. For inject, this means the creator can be forced to debit far more of the counter-asset than expected/available-for-risk; for withdraw, the creator can receive far less of the counter-asset than expected. This mirrors the reported `MetapoolRouter.addLiquidityOneETHKeepYt` issue: liquidity/asset-pair operations lack a slippage bound on the derived leg, even though the code already demonstrates the pattern for doing so (`ExchangeTransactionContract.expected`).

### Impact Explanation
This can cause unintended asset loss for the party performing the liquidity operation: over-deduction of the counter-asset on inject, or under-receipt of the counter-asset on withdraw, both driven by ratio manipulation from ordinary, permissionless trade transactions against the same pool within the same block/transaction ordering window. This is an accounting/asset-loss issue in the actuator layer reachable via ordinary broadcast transactions (`ExchangeTransactionContract` + `ExchangeInjectContract`/`ExchangeWithdrawContract`), not requiring any privileged/witness/node access.

### Likelihood Explanation
Moderate. Exploitation requires the attacker to be able to sequence an `ExchangeTransactionContract` trade ahead of the victim's `ExchangeInject`/`ExchangeWithdraw` transaction within the same block (e.g., via block-producer collusion, mempool visibility, or simply racing transactions targeting the same low-liquidity/legacy TRC10 `Exchange` pool). The `Exchange`/bancor mechanism is a legacy feature with generally low usage today, which reduces real-world likelihood relative to an actively used DeFi router, but the code-level absence of any slippage parameter is a genuine gap.

### Recommendation
Add an optional caller-specified bound to `ExchangeInjectContract` (e.g., `max_another_token_quant`) and `ExchangeWithdrawContract` (e.g., `min_another_token_quant`), and validate them in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()` against the freshly computed `anotherTokenQuant`, analogous to the existing `tokenExpected` check in `ExchangeTransactionActuator.doValidate()` [1](#0-0) .

### Proof of Concept
1. Exchange creator plans to inject `tokenQuant` of `firstTokenID` into their pool, expecting `anotherTokenQuant ≈ secondTokenBalance * tokenQuant / firstTokenBalance` based on the pool state they queried off-chain, and broadcasts `ExchangeInjectContract`.
2. Before this transaction is packed/executed, any account broadcasts an `ExchangeTransactionContract` trade against the same `exchange_id`, shifting `firstTokenBalance`/`secondTokenBalance` (permitted, no special role required, only requires `tokenExpected` slippage on the trader's own side) [6](#0-5) .
3. The victim's `ExchangeInjectActuator.execute()` then recomputes `anotherTokenQuant` from the now-shifted balances and unconditionally debits that amount from the creator's account [4](#0-3) , with no field in `ExchangeInjectContract` to cap this debit [7](#0-6) , resulting in the creator depositing more (or, in the withdraw case, receiving less) of the counter-asset than their off-chain simulation predicted.

Note: I was unable to independently verify the exact ordering/inclusion semantics that determine whether an attacker can reliably front-run a given transaction within the same block in this fork (that logic lives in block-production/`TransactionCapsule` ordering code, which was not part of this scan). This assessment is based on the actuator/validate logic alone.
