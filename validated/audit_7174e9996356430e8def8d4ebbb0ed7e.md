### Title
Missing slippage protection in `ExchangeInjectContract` allows liquidity providers to be forced into unfavorable token ratios - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeTransactionContract` (a swap) includes an `expected` field that lets a caller bound the minimum output they will accept, and `ExchangeTransactionActuator.doValidate()` enforces `anotherTokenQuant < tokenExpected` at validation time [1](#0-0) . By contrast, `ExchangeInjectContract` — which lets a liquidity provider deposit into a bancor-style token pair pool — has no such bound: its protobuf message only carries `owner_address`, `exchange_id`, `token_id`, and `quant`, with no minimum/maximum for the paired token [2](#0-1) .

### Finding Description
In `ExchangeInjectActuator.doValidate()`, the amount of the "other" token the depositor must simultaneously contribute is computed purely from the exchange pool's current on-chain balances at validation time, using the constant-ratio formula:
```
anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance
``` [3](#0-2) 

This mirrors the Ajna vulnerability class exactly: a user signs a transaction expecting a certain deposit ratio/price (analogous to LUP), but the pool state (`firstTokenBalance`/`secondTokenBalance`, analogous to `deposits_`/`poolState_.debt`) used to compute the ratio is read fresh at validation, which happens immediately before execution in block processing — not at signing time. Any `ExchangeTransactionContract` swap that executes against the same exchange pair before the victim's inject transaction (ordered by the block-producing witness, or simply preceding transactions in the same block) shifts `firstTokenBalance`/`secondTokenBalance`, and therefore shifts `anotherTokenQuant` the victim is forced to pay, with no cap:
```java
if (Arrays.equals(anotherTokenID, TRX_SYMBOL_BYTES)) {
  if (accountCapsule.getBalance() < addExact(anotherTokenQuant, calcFee())) {
    throw new ContractValidateException("balance is not enough");
  }
} else {
  if (!accountCapsule.assetBalanceEnoughV2(anotherTokenID, anotherTokenQuant, dynamicStore)) {
    throw new ContractValidateException("another token balance is not enough");
  }
}
``` [4](#0-3) 
The only checks are that the resulting quantity is `> 0`, within the exchange balance limit, and that the account can afford it — there is no way for the depositor to specify a minimum or maximum acceptable ratio, unlike the `expected` protection that already exists for swaps.

### Impact Explanation
A liquidity provider calling `injectExchangeToken` can be forced to contribute a materially different (larger) amount of the second token than intended when they signed the transaction, if the pool ratio moves due to preceding swap transactions in the same or an adjacent block — whether by ordinary trading activity or by a block-producing witness/attacker deliberately reordering a swap ahead of the inject transaction. This is a direct economic-loss analog of the Ajna `addQuoteToken` slippage issue: value is extracted from the depositor without their consent, through legitimate on-chain state changes they did not anticipate and had no mechanism to bound.

### Likelihood Explanation
Reachable by any account via a normal broadcast `ExchangeInjectContract` transaction against any TRC10/TRX exchange pair; requires only that another party (or the depositor's own unlucky timing) submits a swap transaction against the same pair before the inject is processed. Given java-tron block producers control transaction ordering within a block, front-running/back-running by a witness is straightforward and requires no special privilege beyond normal transaction submission — comparable to standard AMM sandwich conditions.

### Recommendation
Add a caller-specified bound (e.g., `expected_min` / `expected_max` for the second token quantity, or a `slippage_bps` parameter) to `ExchangeInjectContract`, and enforce it in `ExchangeInjectActuator.doValidate()` the same way `tokenExpected` is enforced in `ExchangeTransactionActuator`, rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller's specified bound.

### Proof of Concept
1. Exchange pair pool has balances `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Victim signs `ExchangeInjectContract` with `token_id = first`, `quant = q`, expecting to pay `B*q/A` of the second token.
3. Before the victim's transaction is included, an attacker submits `ExchangeTransactionContract` swaps against the same pair, shifting the ratio to `A'`, `B'`.
4. Victim's inject transaction is validated/executed against the new ratio: `anotherTokenQuant = B'*q/A'`, computed in `ExchangeInjectActuator.doValidate()`/`execute()` [3](#0-2) , which can require the victim to pay significantly more of the second token than originally anticipated, with the only protections being non-zero output and sufficient balance — no slippage bound exists to reject the deposit.
