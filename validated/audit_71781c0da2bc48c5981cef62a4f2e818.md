### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, letting replay/verify tooling accept divergent state, hot-state, and trading-position roots - (`File: types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used across replay and verification tooling to confirm that a locally re-executed transaction output matches an authenticated `TransactionInfo` pulled from a proof or backup. It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The code itself documents this gap with a `TODO(trading-native)` comment, but the gap is unconditional today — it applies to the ordinary state-checkpoint hash as well, not only the new trading-native fields.

### Finding Description
`ensure_match_transaction_info` builds its comparison from only four fields: [1](#0-0) 

Specifically it verifies `status`, `gas_used`, `write_set_hash == txn_info.state_change_hash()`, and `event_root_hash == txn_info.event_root_hash()`, then returns `Ok(())` — it never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The function's own trailing comment acknowledges this: [2](#0-1) 

This function is the sole comparator used by several verification/replay entry points that are supposed to detect state divergence:
- Chunk-executor replay verification (`verify_execution`), used by the replay-verify tool that compares locally re-executed history against backed-up/authenticated `TransactionInfo`s: [3](#0-2) 
- The `aptos-debugger` mismatch printer: [4](#0-3) 
- The CLI replay command, which explicitly treats a `ensure_match_transaction_info` success as proof the replayed output matches the authenticated transaction info: [5](#0-4) 

Note that this is distinct from the primary in-protocol consensus/commit path (`DoStateCheckpoint`/`chunk_result_verifier.rs`), which does separately validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against known values via `get_state_checkpoint_hashes`: [6](#0-5) 
So live block execution/commit is protected. The gap is confined to the tooling path that uses `ensure_match_transaction_info` directly (replay-verify, CLI replay, debugger), which is exactly the kind of "authenticated data → local re-computation" comparison meant to catch state-commitment divergence during replay.

### Impact Explanation
Because `ensure_match_transaction_info` silently ignores `state_checkpoint_hash` (used at every reconfiguration/checkpoint boundary for ordinary accounts state, not just trading-native), a corrupted or forked state root at a checkpoint boundary would not be caught by replay-verify, `aptos-debugger`, or the CLI replay command even though the write-set/event/gas/status all matched. This matches the in-scope impact category "Hard-fork-only divergence during commit, replay, restore, or proof verification": a divergence in the authenticated state root can pass replay-verify tooling as if it were consistent, defeating the purpose of these tools as an integrity backstop against silent state corruption (e.g. after a JMT bug, state-sync corruption, or hard-fork mismatch). For the trading-native fields specifically, the code comment states this directly for `position_state_checkpoint_hash`.

### Likelihood Explanation
This triggers deterministically any time these tools are used on a chunk whose write-set/events/gas/status are unaffected by a divergence but whose committed state root (state checkpoint, hot-state checkpoint, or position-state checkpoint) differs — e.g., non-deterministic downstream commitment computation, a bug in the JMT/hot-state/position accumulator, or corrupted backup data. It requires no attacker action; it's a silent verification gap in a safety-net tool. This is why the developers already left the TODO note for the trading-native part, but the omission is broader (it also applies to the base `state_checkpoint_hash`).

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally-computed checkpoint output and `txn_info`, when these values are known/applicable (i.e., when the transaction is a checkpoint boundary and the caller can supply the locally computed root). This likely requires threading the checkpoint output (or its computed roots) into `ensure_match_transaction_info`'s call sites (`chunk_executor::verify_execution`, `aptos-debugger`, CLI replay, `replay_on_archive`) since the function currently only has access to `TransactionOutput`, not the state-checkpoint root computed by `DoStateCheckpoint`.

### Proof of Concept
Not applicable as a runnable exploit — this is a static code-review finding based on tracing all call sites of `ensure_match_transaction_info` and confirming, by direct code inspection, that the comparison omits three of the seven fields present on `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), while the corresponding in-protocol commit path (`do_state_checkpoint.rs::get_state_checkpoint_hashes`) does check them. I was unable to fully verify within the available iterations whether `compute_trading_native_state_roots` is currently enabled on mainnet (feature flag status in `types/src/on_chain_config/aptos_features.rs`), which would affect the severity of the `position_state_checkpoint_hash` portion specifically; the `state_checkpoint_hash` omission, however, applies unconditionally regardless of that flag.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
