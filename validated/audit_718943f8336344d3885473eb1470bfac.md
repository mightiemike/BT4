Found the analog: `add_chunk_transactions` in `chain/client/src/pending_transaction_queue.rs` silently discards the return-value error from `tx_cost()` instead of rejecting/handling it in a way that keeps the pending-balance accounting consistent — directly mirroring the sudoswap bug class ("Quote"-style function whose error code is unchecked before being used for downstream accounting).

### Title
Unchecked `tx_cost()` error silently drops pending-balance accounting for a certified-but-uncharged transaction - (File: chain/client/src/pending_transaction_queue.rs)

### Summary
`tx_cost()` is the NEAR equivalent of `LSSVMPair.getBuyNFTQuote()`/`getSellNFTQuote()`: it is the authoritative "quote" function that computes the balance/gas cost that must be reserved against an account for a transaction included in an uncertified chunk. In `PendingTransactionQueue::add_chunk_transactions`, when `tx_cost()` returns an `Err`, the code logs a warning and does `continue`, skipping that transaction entirely for accounting purposes, exactly like `LSSVMRouter.sol` skipping the error check on `getBuyNFTQuote()`/`getSellNFTQuote()` and using the (possibly wrong/absent) result anyway. [1](#0-0) 

### Finding Description
The pending transaction queue tracks per-account and per-gas-key balance commitments (`paid_from_balance`, `pending_gas_key_costs`) for transactions that have been included in a block's chunk but not yet certified/executed. These aggregates are later used by `get_pending_constraints` to compute `available_balance` in `verify_and_charge_transaction` (`available_balance = account.amount().saturating_sub(pending.paid_from_balance)`) — this is the actual admission-control gate that prevents a signer from submitting more transactions/deposits than their balance can support while prior chunks are still uncertified. [2](#0-1) 

In `add_chunk_transactions`, `tx_cost(config, tx, gas_price)` is called for every transaction in an already-included chunk in order to compute `cost.deposit_cost`, `cost.total_cost`, and `cost.gas_cost` that get folded into `chunk_account.paid_from_balance` and `chunk_data.gas_key_costs`. If `tx_cost` returns `Err`, the code does not check/propagate this error meaningfully — it just logs and `continue`s to the next transaction: [3](#0-2) 

But the transaction itself has already been included in the chunk and will be executed/certified by the runtime regardless (this queue is purely an admission-control bookkeeping structure, not the runtime's own validation). If a transaction can be constructed such that `tx_cost` fails while `verify_and_charge_transaction`/the runtime's own cost computation for the *same* transaction still succeeds (e.g., because the pending-queue's `tx_cost` call happens with a different/stale `RuntimeConfig` or `gas_price` snapshot than the one used at actual execution, or a code path where the two cost functions diverge on an edge case such as overflow boundaries), then:
- The transaction is silently dropped from `chunk_account.paid_from_balance` and `chunk_data.gas_key_costs`.
- Every subsequent `get_pending_constraints`/admission check for that signer in the same uncertified window under-counts the balance already committed by prior in-flight transactions.
- A malicious signer can exploit the resulting slack to get additional conflicting transactions admitted into further chunks that, combined with the "invisible" transaction, exceed the account's real spendable balance, mirroring the LSSVMRouter class of bug where an unchecked quote error lets the caller proceed with stale/incorrect cost data instead of rejecting.

This is architecturally identical to the reported Sudoswap issue: a downstream module (`LSSVMRouter`/`PendingTransactionQueue`) consumes a cost/quote-producing function (`getBuyNFTQuote`/`getSellNFTQuote` vs `tx_cost`) without checking/handling its error path consistently with how the "quote" function is used elsewhere (`LSSVMPair.swapTokenForAnyNFTs` checks `error == CurveErrorCodes.Error.OK` vs `verify_and_charge_transaction` fully computing and charging cost with `?`).

### Impact Explanation
This is an in-runtime-reachable admission-control accounting bug: if a signer can trigger `tx_cost` failure in the pending-queue path while the runtime's real charge succeeds, they can under-report their committed pending balance, allowing extra transactions to be admitted into subsequent chunks that reference balance already spent by an in-flight transaction. Depending on chunk ordering this can let a single account get transactions certified whose combined cost exceeds its actual balance for the certification window, i.e., an unauthorized-value/fee-bypass style admission failure at the RPC/chunk-producer admission layer, which is one of the accepted impact categories (fee/gas bypass, invalid-state-transition-adjacent admission bypass reachable purely from a submitted transaction).

### Likelihood Explanation
Medium: this requires crafting a transaction that makes `tx_cost` fail in the pending-queue call (which is a best-effort/RPC-side computation, distinct from the authoritative runtime charge in `verifier.rs`), which is a narrower trigger surface than the original Sudoswap report (any curve error), but the pattern — silently discarding an error from a cost/quote function without any fallback accounting or correctness guarantee — is present and directly reachable by any transaction submitter.

### Recommendation
Do not silently `continue` on `tx_cost` failure inside `add_chunk_transactions`. Either treat the transaction as consuming a conservative/maximum possible cost (fail-safe over-approximation) for pending accounting purposes, or ensure `tx_cost` cannot diverge from the runtime's authoritative charge function for any transaction that reaches this code path (i.e., prove the error paths of both functions are exactly aligned), and add an explicit invariant/test asserting this alignment, consistent with how `verify_and_charge_transaction` propagates cost errors via `?` rather than dropping them.

### Proof of Concept
Not independently reproducible with the current tools (no execution environment); the analysis is based on static code reading of `add_chunk_transactions` (`chain/client/src/pending_transaction_queue.rs:266-284`) versus `verify_and_charge_transaction`'s cost handling (`runtime/runtime/src/verifier.rs:594-657`), and `get_pending_constraints`'s consumption of the aggregated `paid_from_balance` (`chain/client/src/pending_transaction_queue.rs:407-416`). Confirming actual exploitability requires demonstrating a concrete transaction for which `tx_cost` fails in the pending-queue context but the runtime's own cost/charge computation for the identical transaction succeeds — this divergence was not verified against `node_runtime::config::tx_cost`'s implementation within the available indexed context, so likelihood should be treated as conditional on that divergence existing.
