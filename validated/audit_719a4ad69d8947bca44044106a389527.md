## Analysis: Hard-coded 5% Slippage Tolerance in GAS-type Autoswaps

The Sherlock report's core defect is a **hard-coded slippage tolerance applied by the protocol on the user's behalf**, rather than a user-specified slippage bound, which lets an MEV actor consistently extract value on every use of the vulnerable code path at essentially zero attacker cost. Push Chain's `x/uexecutor` keeper reproduces the identical pattern in its inbound-gas autoswap and gas-refund logic.

### Title
Hard-coded 5% slippage tolerance in `ExecuteInboundGas`/`gasAndPayloadDepositAutoSwap`/`applyGasRefund` autoswaps lets an MEV sandwicher extract value from every GAS/GAS_AND_PAYLOAD inbound and every outbound gas refund - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
For every `GAS`/`GAS_AND_PAYLOAD` inbound deposit, and for every outbound gas-fee refund, the `uexecutor` module fetches a Uniswap V3 `QuoterV2` quote and then unconditionally computes `minPCOut = quote * 95 / 100` before executing the actual swap via `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas`. This 5% tolerance is not derived from any user input or market-volatility parameter — it is a fixed constant baked into every code path that performs a swap on behalf of the user. ### Finding Description
In `ExecuteInboundGas`, the flow is: get quote from `GetSwapQuote` → immediately compute `minPCOut` as 95% of quote → call `CallPRC20DepositAutoSwap` with that `minPCOut`: [4](#0-3) 

The same 95%-of-quote pattern recurs in `gasAndPayloadDepositAutoSwap` (used by `ExecuteInboundGasAndPayload`) and in `applyGasRefund` (used by both `handleFailedOutbound` and `handleSuccessfulOutbound` to refund excess relayer gas via a PRC20→WPC swap): [5](#0-4) [6](#0-5) 

Because these swaps execute on Push Chain's own Cosmos-EVM engine against an on-chain Uniswap V3-style pool (via `UniversalCore.depositPRC20WithAutoSwap` / `refundUnusedGas`), and because the module's swap-triggering transaction (a `MsgVoteInbound` reaching quorum, or an outbound-observation vote reaching quorum) is a normal, publicly-visible transaction submitted through the same mempool as any other user transaction, an attacker can:
1. Observe the pending vote transaction that will trigger the module's swap (the swap parameters — quote and `minPCOut` — are computed and consumed within the same transaction execution, but the *pool price* at execution time can be manipulated by transactions ordered immediately before it in the same block).
2. Submit a large swap against the same PRC20/WPC Uniswap V3 pool immediately before the module's transaction to push the price down by up to just under 5%.
3. Let the module's autoswap execute at the manipulated price — it will still succeed because `minPCOut` tolerates a full 5% deviation.
4. Reverse the manipulation afterward (sell back), capturing the difference between the fair quote and the worse execution price that the module actually paid — extracted directly from either the depositing user's converted PC (in the `GAS`/`GAS_AND_PAYLOAD` inbound path) or the relayer's excess-gas refund (in `applyGasRefund`).

This is architecturally identical to the ERC5095 bug: the protocol itself imposes slippage on the user's/relayer's behalf using a hard-coded percentage rather than letting the actual value owner (or an external check) bound the acceptable output, and the amount is fixed for every invocation, making the attack repeatable and low-cost for every deposit that goes through the autoswap path.

### Impact Explanation
Every `GAS` and `GAS_AND_PAYLOAD` inbound deposit, and every outbound observation that triggers an excess-gas refund, is exposed to up to 5% value extraction by an MEV actor sandwiching the module's swap transaction. Because the tolerance is hard-coded and applies unconditionally (there is no way for the depositing user to specify a tighter bound, nor any circuit breaker comparing against a recent TWAP), this is a systemic, per-transaction fund loss affecting the user's converted native-PC balance (`GAS`/`GAS_AND_PAYLOAD` deposit path) or the relayer's gas refund (`applyGasRefund` path) — falling under "corruption of ... gas fee accounting, refund accounting ... " and unauthorized draining of user/protocol-controlled funds in the allowed impact gate.

### Likelihood Explanation
The attack requires no privileged role — any unprivileged actor able to submit ordinary EVM transactions against the Push Chain PRC20/WPC pool can attempt the sandwich whenever a `GAS`/`GAS_AND_PAYLOAD` inbound vote or outbound-refund vote is about to reach quorum (these are visible on-chain/in the mempool as ordinary `MsgVoteInbound`/`MsgVoteOutbound` transactions). Since the slippage tolerance is fixed at 5% for every single occurrence rather than being an edge case, the exploit is reproducible on essentially every relevant transaction, mirroring the original report's rationale for treating this as systemic rather than a one-off issue.

### Recommendation
Do not use a fixed 95%/5% constant for `minPCOut`. Instead, derive the acceptable slippage from a manipulation-resistant reference (e.g., a TWAP-based quote, or a maximum bound configured per-token in `uregistry` and periodically updated), and/or perform the quote and the swap atomically within the same block using a price that cannot be moved by an attacker-controlled transaction ordered immediately before it (e.g., using the pool's TWAP oracle instead of `quoteExactInputSingle`'s spot-based quote). Additionally consider capping how much value a single swap can extract relative to trade size, and emitting alerts/reverting when computed slippage would exceed a much tighter default (e.g., 0.5–1%).

### Proof of Concept
1. Attacker monitors the Push Chain mempool for a pending `MsgVoteInbound` (or `MsgVoteOutbound`) transaction from the last required validator that will push a `GAS`/`GAS_AND_PAYLOAD` inbound (or an outbound requiring a gas refund) to quorum.
2. Attacker submits (with higher gas/priority so it lands first in the same block) a swap on the PRC20↔WPC Uniswap V3 pool used by `GetSwapQuote`/`CallPRC20DepositAutoSwap`, pushing the pool price down by just under 5%.
3. The validator's vote transaction executes in the same block, calling `GetSwapQuote` (reflecting the manipulated price) then `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` with `minPCOut = quote*95/100`, which the manipulated pool state still satisfies.
4. Attacker submits a follow-up transaction reversing the initial swap, extracting the value pushed out of the pool by the module's underpriced swap — the difference below fair value that `minPCOut`'s 5% tolerance allowed.
5. Repeat for every subsequent `GAS`/`GAS_AND_PAYLOAD` inbound or gas-refund event, since the 5% constant is hard-coded at [7](#0-6)  , [8](#0-7)  , and [9](#0-8) .

// gasAndPayloadDepositAutoSwap handles the swap quote + deposit autoswap for GAS_AND_PAYLOAD.
func (k Keeper) gasAndPayloadDepositAutoSwap(
	sdkCtx sdk.Context,
	prc20AddressHex common.Address,
	ueaAddr common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	quoterAddr, err := k.GetUniversalCoreQuoterAddress(sdkCtx)
	if err != nil {
		return nil, err
	}

	wpcAddr, err := k.GetUniversalCoreWPCAddress(sdkCtx)
	if err != nil {
		return nil, err
	}

	fee, err := k.GetDefaultFeeTierForToken(sdkCtx, prc20AddressHex)
	if err != nil {
		return nil, err
	}

	quote, err := k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)
	if err != nil {
		return nil, err
	}

	// 5% slippage: minPCOut = quote * 95 / 100
	minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
	minPCOut.Div(minPCOut, big.NewInt(100))

	return k.CallPRC20DepositAutoSwap(sdkCtx, prc20AddressHex, ueaAddr, amount, fee, minPCOut)
}
