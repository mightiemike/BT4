## Title
Metering `Settle()` fails to cap capability-reported spend against the reserved deduction, allowing over-billing of workflow credits - (File: `core/services/workflows/metering/metering.go`)

## Summary
The Datatrust.vy bug describes a system that lets an untrusted reporter (the Backend) submit a consumption value that is applied to a user's balance without being capped to what was actually paid/reserved, letting reported usage exceed the authorized amount and drain funds meant for other purchases. The Chainlink CRE workflow metering package has the same structural flaw: `Report.Settle` trusts capability-reported `SpendValue` figures from `capabilities.ResponseMetadata.Metering` and adds them to the billed total (`spent`) without ever capping them to the amount that was `Deduct`-ed (reserved) for that step.

## Finding Description
When a workflow step invokes a capability, the engine first earmarks (`Deduct`s) a maximum spend via `ByResource`/`ByDerivedAvailability`, which calls `balanceStore.Minus` to remove that amount from the local in-execution credit balance. [1](#0-0) 

After the capability responds, `Report.Settle` aggregates the node-reported `SpendValue` fields from `metadata.Metering` (data returned by the invoked capability/DON, analogous to the "Backend" in the Vyper report) into `spentCredits`, without ever checking that `spentCredits` does not exceed the previously earmarked `step.Deduction`: [2](#0-1) 

The only place this mismatch is checked is here:
```go
// Refund the difference between what local balance had been earmarked and the actual spend
if err := r.balance.Add(step.Deduction.Sub(spentCredits)); err != nil {
    // invariant: capability should not let spend exceed reserve
    r.lggr.Info("invariant: spend exceeded reserve")
}

r.balance.AddSpent(spentCredits)
``` [3](#0-2) 

`balanceStore.Add` rejects negative amounts (`amount.LessThan(decimal.Zero)` → `ErrInvalidAmount`), so when `spentCredits > step.Deduction` the refund call simply fails and is swallowed via an info-level log — the local balance is **not** further debited for the excess. [4](#0-3)  However, `AddSpent(spentCredits)` unconditionally records the **full, uncapped** reported spend into the running `spent` total, which is exactly what gets reported to the remote billing service.

This uncapped `spent` total is submitted as `CreditsConsumed` in `SendReceipt`:
```go
req := billing.SubmitWorkflowReceiptRequest{
    ...
    CreditsConsumed: r.balance.GetSpent().String(),
}
``` [5](#0-4) 

So while the local in-memory guard prevents the *local* balance from going negative, the amount actually billed to the workflow owner's account (via `SubmitWorkflowReceipt`) reflects the inflated, unbounded capability-reported value rather than the amount that was reserved/authorized for that step (`ReserveCredits`/`Deduct`). This is the direct analog of the Datatrust.vy flaw: `bytes_purchased`/cost accounting is decremented by an externally-reported amount that is never validated to be ≤ what was paid for, and the discrepancy is only logged, not prevented.

## Impact Explanation
A capability (or the DON responding to a capability call) that reports an inflated `SpendValue` in `capabilities.ResponseMetadata.Metering` can cause the workflow owner to be billed for `CreditsConsumed` that exceeds what was reserved for that step and possibly what was reserved for the whole execution (`ReserveCredits`). Because the discrepancy is only surfaced through an `Info`-level log line ("invariant: spend exceeded reserve") and never blocks execution or the receipt submission, downstream billing settlement can silently overcharge the workflow owner's credit account, mirroring the original report's "excess cost taken from the user's pool" impact, where legitimate future spend (other workflow executions/steps for the same owner) can be starved because more credits than authorized were consumed by one step.

## Likelihood Explanation
This does not require compromising a majority of a DON — it only requires one capability response to carry an inflated `SpendValue` string for at least one resource dimension not classified as `RPC_EVM`; for single-node/non-BFT capability responses (or gas-spend types which explicitly disallow more than one report and instead just fail open into metering mode) there is no cross-validation against the reserved `Deduction` at all before the value is folded into the billed total. The check exists only as an unenforced log statement.

## Recommendation
- In `Report.Settle`, when `spentCredits` exceeds `step.Deduction`, either clamp the value that is added to `spent`/billed to the reserved amount, or treat it as an error condition that reverts/aborts the step's contribution to `CreditsConsumed` rather than merely logging.
- Ensure `AddSpent` is only ever called with a value bounded by what was actually reserved (`step.Deduction`), consistent with the intent already expressed in the code comment "invariant: capability should not let spend exceed reserve".
- Add explicit test coverage asserting `CreditsConsumed` submitted to the billing service never exceeds the sum of `Deduction` values across steps.

## Proof of Concept
1. Call `report.Deduct("step1", ByResource(unit, "", decimal.NewFromInt(2)))` to reserve 2 units (worth 1 credit given the test rate cards).
2. Call `report.Settle("step1", capabilities.ResponseMetadata{Metering: []capabilities.MeteringNodeDetail{{Peer2PeerID: "xyz", SpendUnit: unit, SpendValue: "20"}}})` — i.e., the capability reports 20 units consumed instead of the 2 reserved.
3. Observe (as already exercised by the existing test `Test_Report_Settle/does_not_error_when_spend_exceeds_reservation`) that `Settle` returns `nil` (no error) and only logs one info-level line. [6](#0-5) 
4. Call `report.SendReceipt(ctx)` and inspect the `CreditsConsumed` field of the submitted `SubmitWorkflowReceiptRequest` — it reflects the full inflated spend (`r.balance.GetSpent()`), not the amount actually reserved via `Deduct`/`ReserveCredits`. [5](#0-4)

// ByResource returns a DeductOpt that earmarks a specified amount of local universal credit balance for a given spend
// type.
func ByResource(
	spendType, capabilityID string,
	amount decimal.Decimal,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     capabilityID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		bal, err := r.balance.ConvertToBalance(spendType, amount)
		if err != nil {
			// Fail open, continue optimistically
			r.switchToMeteringMode(fmt.Errorf("failed to convert to balance [%s]: %w", spendType, err))
		}

		step.Deduction = bal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return []capabilities.SpendLimit{}, r.balance.Minus(bal)
	}

// Minus lowers the current credit balance.
func (bs *balanceStore) Minus(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	if amount.GreaterThan(bs.balance) {
		return ErrInsufficientBalance
	}

	bs.balance = bs.balance.Sub(amount)

	return nil
}
