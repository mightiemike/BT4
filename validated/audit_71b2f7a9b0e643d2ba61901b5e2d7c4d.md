### Title
Unhandled `ArithmeticException` from division by zero `totalEnergyWeight`/`totalNetWeight` in resource-limit calculation - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` divides by `totalEnergyWeight` guarded only by a Java `assert` statement, which is a no-op in production JVMs (run without `-ea`). When the hardened calculation path is enabled, the actual division is performed via `BigInteger.divide()`, which throws `ArithmeticException` on division by zero instead of silently continuing like double arithmetic would.

### Finding Description
This mirrors the Notional Finance "Handle division by 0" bug class: a denominator (`totalWeight`/`totalEnergyWeight`) that is assumed to always be non-zero (enforced only by a comment/assert) is used directly as a BigInteger divisor with no runtime guard. [1](#0-0) 

```
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    ...
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    ...
```

The zero-guard (`allowNewReward() && totalEnergyWeight <= 0`) only applies when the `allowNewReward` fork is active. If that fork flag is not set (e.g., older config or specific chain parameters) and `totalEnergyWeight` is legitimately `0` (for example, right after genesis before any account has frozen TRX for energy, or immediately after all energy weight has been unfrozen network-wide), execution falls to the `assert`, which does nothing in a production JVM, and then to: [2](#0-1) 

```
protected long calculateGlobalLimitV1(long frozeBalance,
    long totalLimit, long totalWeight) {
  long weight = frozeBalance / TRX_PRECISION;
  return BigInteger.valueOf(weight)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(totalWeight))
      .longValueExact();
}
```

`BigInteger.divide(BigInteger.ZERO)` throws an `ArithmeticException: BigInteger divide by zero`. The same pattern with the identical unguarded `assert` exists in the sibling `RepositoryImpl.calculateGlobalEnergyLimit()` used inside TVM native contract execution: [3](#0-2) 

```
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

Here there is no `allowNewReward` guard at all — only the unenforced `assert`. If `totalEnergyWeight` is `0` when this path is hit during TVM execution (e.g. a native contract for delegate/undelegate energy resource, invoked from any broadcast transaction that triggers energy accounting), the hardened branch throws an uncaught `ArithmeticException`.

### Impact Explanation
An uncaught `ArithmeticException` inside transaction processing/TVM execution logic that is not wrapped in a catch block specific to that exception type can propagate up through block processing, causing consensus-critical logic to fail unpredictably (nodes may either all fail identically — halting the chain — or diverge if the divide-by-zero condition is reached inconsistently, e.g., due to differing internal float/BigInteger code paths across the hardened/legacy toggle). At minimum it represents a transaction-processing DoS: an attacker able to drive `totalEnergyWeight` to `0` (or catch the brief window where it legitimately is) can cause any subsequent resource-limit calculation to throw, potentially reverting/breaking normal execution for well-formed transactions.

### Likelihood Explanation
Likelihood is moderate-to-low: `totalEnergyWeight` is a global chain state variable summing all frozen-for-energy balances across the network, which on a live mainnet with any activity is very unlikely to be exactly `0`. However, on new networks, test/private chains, sidechains, or during specific migration/config states before the `allowNewReward` fork is active, `totalEnergyWeight == 0` is a realistic startup condition, and this code executes on every transaction that computes account energy limits.

### Recommendation
Add an explicit, always-enforced runtime check (not a Java `assert`) for `totalEnergyWeight <= 0` (and the analogous `totalNetWeight` in `BandwidthProcessor`) before performing the `BigInteger` division in both `EnergyProcessor.calculateGlobalEnergyLimit()` / `calculateGlobalLimitV1()`/`calculateGlobalLimitV2()` and the duplicate logic in `RepositoryImpl.calculateGlobalEnergyLimit()`, returning `0` (or another safe default) instead of dividing when the denominator is non-positive, consistent with the guard already present in `calculateGlobalEnergyLimitV2()`.

### Proof of Concept
Not independently executable from the available index (would require constructing a node/chain state with `totalEnergyWeight == 0`, `allowHardenResourceCalculation` enabled, and `allowNewReward` disabled, then broadcasting a transaction that triggers `calculateGlobalEnergyLimit`, e.g. a `DelegateResourceContract`/`UnDelegateResourceContract` or TVM energy accounting call). This condition and reachability should be validated in a live/test node by a background agent, since it depends on runtime dynamic-properties state not fully inspectable via static code search alone.
