Based on the codebase analysis, I found a strong structural analog to the StRSR issue in java-tron's `Exchange` market feature (TRC10 bancor-style AMM pools). Both bugs share the same root pattern: a pool/balance can be driven to exactly zero through a legitimate value-transfer path, and once that happens, the system enters a permanently-frozen state with no recovery mechanism (no analog of `beginEra()`), locking whatever remains in the pool.

### Title
Exchange pool balance can be driven to exactly zero, permanently locking remaining pooled TRX/TRC10 funds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The `Exchange` feature (`ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeTransactionActuator`/`ExchangeWithdrawActuator`) implements bonding-curve token pools stored in `ExchangeCapsule`. All four actuators independently guard against operating on an exchange whose `firstTokenBalance` or `secondTokenBalance` is already `0` by throwing `"Token balance in exchange is equal with 0, the exchange has been closed"`. However, nothing prevents a normal `ExchangeTransactionContract` from mutating a pool's balance down to *exactly* zero (as opposed to becoming negative, which the hardened path checks for). Once either side reaches zero, every actuator that touches that exchange — inject, transaction, and withdraw — is unconditionally blocked by that same zero-balance guard, leaving any remaining balance on the other token side permanently unwithdrawable. This mirrors the StRSR bug class: a legitimate value-transfer operation drains a pool to zero without any "re-initialization"/"era reset" step, and the missing recovery path leaves user funds trapped.

### Finding Description
`ExchangeCapsule.transaction()` computes a new pair of balances using the bonding-curve `ExchangeProcessor`/`SafeExchangeProcessor` math and writes them back via `setBalance(...)`: [1](#0-0) 

The only safety check applied to the resulting balances is the *hardened* path's `< 0` check: [2](#0-1) 

Nothing rejects a resulting balance of exactly `0`. `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)` directly against the persisted `ExchangeCapsule` and writes it back to the store: [3](#0-2) 

Meanwhile, every actuator that can act on an exchange enforces the *pre-condition* check that both balances must be non-zero, else it treats the exchange as permanently closed: [4](#0-3) 

The identical zero-balance guard exists in `ExchangeInjectActuator` and `ExchangeWithdrawActuator`, confirmed by their respective tests asserting `"Token balance in exchange is equal with 0,the exchange has been closed"`: [5](#0-4) 

Because the bonding-curve `exchangeFromSupply` computation in `ExchangeProcessor` truncates a `double` result to a `long` (`(long) exchangeBalance`), a sufficiently large `sellTokenQuant` can drive the computed `buyTokenQuant` to be exactly equal to `buyTokenBalance`, producing a new balance of `0` on that side: [6](#0-5) 

Once this occurs, there is no equivalent of StRSR's `beginEra()` to reset/re-open the exchange. Every subsequent `ExchangeInjectContract`, `ExchangeTransactionContract`, and `ExchangeWithdrawContract` targeting that exchange ID is rejected in `doValidate()` because the balance-zero guard treats the pool as "closed" — with no code path to reopen it or to withdraw the stranded remaining balance of the non-zero token side.

### Impact Explanation
Any TRX/TRC10 balance remaining on the non-zero side of the exchange pool becomes permanently locked in the `Exchange`/`ExchangeV2` account (owned by the exchange creator internally, but inaccessible via any actuator). This is an asset/accounting corruption and denial-of-service against the exchange owner's and any liquidity participants' funds, reachable purely through normal broadcast `ExchangeTransactionContract` transactions from any account — no privileged role is required to trigger the drain.

### Likelihood Explanation
Reaching exact-zero requires a sell quantity large enough that the bonding-curve computation's floating-point truncation collapses the result to precisely `buyTokenBalance`. This is plausible for large trades against thinly-capitalized exchange pools (which are user-created and can have arbitrary, small `firstTokenBalance`/`secondTokenBalance`), but requires favorable rounding conditions, so it is not trivially reproducible on every pool/trade size — it depends on specific balance/quantity ratios.

### Recommendation
- Short term: After computing the new balances in `ExchangeCapsule.transaction()` (and in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`), explicitly reject transactions that would set either resulting balance to `0` (require `> 0`), the same way negative balances are already rejected in the hardened path, rather than allowing zero and only detecting it defensively on the next unrelated call.
- Long term: Add a recovery/close-out actuator so that if an exchange pool's balance legitimately reaches zero, the remaining side's balance can still be withdrawn by whoever is entitled to it (analogous to `beginEra()` resetting StRSR state instead of leaving it stuck).

### Proof of Concept
1. Create an exchange (`ExchangeCreateActuator`) with a small `secondTokenBalance` (e.g., TRX side) and a large enough `firstTokenBalance`.
2. Submit an `ExchangeTransactionContract` selling the first token with a `tokenQuant` calibrated so that `ExchangeProcessor.exchange()`'s floating point/long-truncation math (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:31-45`) returns `buyTokenQuant == secondTokenBalance` exactly.
3. `ExchangeTransactionActuator.execute()` persists `secondTokenBalance = 0` via `Commons.putExchangeCapsule(...)`.
4. Any subsequent `ExchangeWithdrawContract`, `ExchangeInjectContract`, or `ExchangeTransactionContract` against this exchange ID is rejected with `"Token balance in exchange is equal with 0,the exchange has been closed"`, permanently trapping the remaining `firstTokenBalance`.

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
