### Title
Unbounded recursion in compiled-class bytecode-segment hashing enables a crash-inducing declare transaction - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recursively walks the `NestedIntList` bytecode-segment structure of a declared class with no depth limit, mirroring the CVE-2022-37050 bug class: a recursive/nested data structure derived from attacker-controlled input is processed without bounds checking, and can crash the process. [1](#0-0) 

### Finding Description
When the gateway receives a Declare V3 transaction, it forwards the submitted Sierra program to the class manager/compiler, which produces a `CasmContractClass` including a `bytecode_segment_lengths: NestedIntList` field, and then computes the executable/compiled class hash in-process via `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash` → `bytecode_hash_node`, comparing it against the caller-supplied `compiled_class_hash` field. [2](#0-1) 

`bytecode_hash_node` recurses once per nesting level of the segment tree with no maximum-depth guard, unlike other recursive/user-reachable paths in the codebase (entry-point call recursion is explicitly bounded by `RecursionDepthGuard`/`max_recursion_depth`). [3](#0-2) [4](#0-3) 

The equivalent structure-building routine used elsewhere in the stack, `create_bytecode_segment_structure_inner`, is likewise unbounded recursion over the same nested list. [5](#0-4) 

Because the Sierra→CASM compilation itself runs in a resource-limited subprocess (`compile_with_args` with `ResourceLimits`) but the subsequent compiled-class-hash computation over the resulting `CasmContractClass` runs directly on the gateway/sequencer process, an attacker who can shape the compiler's segment output to be deeply nested (e.g., via deeply nested function/branch structure in a large but within-limits Sierra program) can trigger unbounded native-stack recursion in `bytecode_hash_node` on the trusted sequencer process itself, outside of the sandboxed compiler subprocess. [6](#0-5) 

This mirrors the CVE's root cause pattern — mishandled nested/recursive structures without depth limits during processing of attacker-supplied structured data, leading to a crash — but here the analog is a Rust native stack overflow triggered outside of the isolated compilation subprocess, in the size-validation/hashing code path that every declare transaction goes through.

### Impact Explanation
A stack overflow in `bytecode_hash_node` on the gateway or class-manager process is not caught by Rust's panic machinery (`catch_unwind` cannot catch stack overflows); it aborts the process. If this executes in-process on the gateway/sequencer (not inside the isolated compiler subprocess), it can crash the node servicing declare transactions, causing denial of service for new transaction submissions from that node — matching "a network unable to confirm new transactions" if this path is on a critical, non-isolated component.

### Likelihood Explanation
Medium: the size and object-size limits on declared classes (`max_contract_bytecode_size`, `max_contract_class_object_size`) constrain the *bytecode* length, but do not appear to directly bound the *nesting depth* of the `bytecode_segment_lengths` tree produced by the compiler, so it is unclear from static inspection whether the resulting nesting depth is inherently capped by the bytecode-size limit (in which case the practical achievable recursion depth may be too shallow to overflow a default stack) or can be made deep independent of overall size. This significantly affects exploitability and I could not verify the segment-lengths generation logic inside the vendored `cairo_lang_starknet_classes` compiler (out of this repo's index) to confirm whether nesting depth is naturally bounded by bytecode size or by a fixed segmentation depth (note `NestedFeltCounts::new_inner` elsewhere asserts `segmentation_depth <= 1`, suggesting CASM segments may in practice be shallow) — [7](#0-6)  — which would substantially reduce or negate the practical risk of this specific path.

### Recommendation
- Add an explicit maximum-depth check to `bytecode_hash_node` (and `create_bytecode_segment_structure_inner`) analogous to `RecursionDepthGuard`, rejecting/erroring out on `NestedIntList` structures deeper than a configured bound before recursing.
- Convert both functions to iterative (worklist/stack-based) traversal to remove reliance on native call-stack depth entirely.
- Confirm whether the vendored Sierra→CASM compiler bounds segment nesting depth as a function of bytecode length; if not, add a depth cap in the deserialization/validation of `CasmContractClass.bytecode_segment_lengths` at the gateway boundary.

### Proof of Concept
Not constructible with available tooling/index access: exploitation requires crafting a Sierra program whose compiled CASM `bytecode_segment_lengths` nests to a stack-overflow-triggering depth, which depends on internals of the vendored `cairo_lang_starknet_classes`/Sierra-to-CASM compiler that are not present in this repository's index. A background Devin session with full filesystem/compiler access would be needed to determine the actual achievable nesting depth for a given bytecode-size budget and to empirically verify whether the recursion reaches native stack-overflow thresholds.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
