### Title
Reentrant `collateral-add` call before outer `insert` commits causes duplicate obligation `id` creation, stranding collateral under an orphaned id - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
In `collateral-add`, the `let`-bound `entry`/`updated-entry` (via `resolve-or-create`) is computed and `add-user-collateral` writes the `collateral` map *before* the token transfer (`receive-tokens`) executes, but the corresponding `reverse`/`registry` write (`insert`) happens only *after* the transfer returns. A malicious `<ft-trait>` implementation whose `transfer` re-enters the deposit flow for the same `account` (via the registered market impl, so `check-impl-auth` still passes) causes a second `resolve-or-create` to run while `reverse` still shows no entry for `account`, minting a second obligation `id` via `create`. The two `insert` calls (inner then outer) each set `reverse account` to their own id, so the later (outer) `insert` overwrites `reverse` to point at only one id, permanently orphaning the collateral recorded under the other id.

### Finding Description
Sequence for outer call `collateral-add(account=A, amount, ft, asset-id)` (first-ever deposit for `A`):
1. `let` binding `entry = (resolve-or-create A)` — `map-get? reverse A` is `none` -> `create A` is called: `id = (increment)` bumps `nonce` from `0`→`1` and returns `id=1`, but `create` does **not** write `registry`/`reverse`; those are only written later by `insert`. [1](#0-0) 
2. `updated-entry` derived from `entry` (still unwritten to `registry`/`reverse`).
3. `result = (add-user-collateral user-id=1 asset-id amount)` — this **immediately** `map-set`s `collateral {id:1,asset}` to `amount`. [2](#0-1) 
4. Body executes `check-impl-auth` (passes, `contract-caller` = registered market impl), pause/amount asserts, then `try! (receive-tokens ft amount A)`, i.e. `contract-call? ft transfer amount A current-contract none`. [3](#0-2) [4](#0-3) 
5. Inside the attacker's `transfer`, the attacker re-enters the market impl's deposit entrypoint for the same `A`, which calls `market-vault.collateral-add` again. Because this reentrant call still routes through the registered impl, `check-impl-auth` passes again.
6. Inner call's `resolve-or-create A` again sees `reverse A = none` (outer `insert` has not run yet) and calls `create` again: `nonce` bumps `1`→`2`, new `id=2`. `add-user-collateral(2, asset-id, amount2)` writes `collateral {id:2,asset}=amount2`. The inner call finishes normally and calls `insert` for `id=2`: `registry[2]=...`, `reverse[A]=2`.
7. Control returns to the outer `receive-tokens` call, which completes; the outer call then executes `(insert updated-entry)` for `id=1`: `registry[1]=...`, `reverse[A]=1`, **overwriting** `reverse[A]` from `2` back to `1`.

Root cause: `resolve-or-create`/`create` (lines [1](#0-0) ) and `insert` (lines [5](#0-4) ) are split across a re-entrant boundary: the id-lookup source (`reverse`) is only updated at the very end of the public function, after an external, attacker-controllable `transfer` call. Nothing in `collateral-add` re-validates `reverse` after the transfer returns, so the stale pre-transfer `entry`/`updated-entry` is blindly inserted, clobbering whatever the reentrant call wrote.

After the transaction commits, `reverse[A] = 1`, and `collateral {id:2, asset}` (holding `amount2`) is unreachable from any getter that resolves through `reverse` (`resolve`, `resolve-safe`, `get-position`, `lookup-collateral` reached via those paths) since only `id=1`'s obligation is referenced going forward. `get-nr` reflects two increments (nonce = 2) though only one id is reachable.

### Impact Explanation
The `amount2` collateral recorded under the orphaned `id=2` becomes permanently unreachable by the account, since all future `debt-add`, `collateral-remove`, and position-health logic resolve the account exclusively through `reverse[A]`, which now points only at `id=1`. This is a permanent freezing of user funds (the deposited `amount2` collateral can never be withdrawn or counted toward the user's position), matching the Critical severity bucket ("permanent freezing of funds").

### Likelihood Explanation
This requires: (a) the attacker's chosen `<ft-trait>` implementation for `asset-id` to actually be accepted as the transfer asset for that deposit (a market-vault-internal condition this file does not itself validate — `collateral-add` performs no check that `ft`'s principal matches a registered asset contract), and (b) the market implementation's own deposit entrypoint to allow reentrant invocation without a reentrancy guard. `check-impl-auth` in `v0-market-vault.clar` specifically blocks a *direct* reentrant call from the malicious `ft` contract into `market-vault.collateral-add` (since `contract-caller` would then be the `ft` contract, not `impl`), so the callback must be routed back through the registered market impl's own public entrypoint. I was unable to fully verify within available iterations whether `v0-4-market.clar`'s deposit entrypoint enforces a reentrancy lock or independently validates `ft` against the asset registry before delegating to `collateral-add` — this is a real gap in verification and materially affects whether the described interleaving is reachable in practice. If no such guard/validation exists, the attack is attacker-chosen, single-transaction, requires only capital equal to their own fabricated token amounts, and is fully repeatable.

### Recommendation
Make obligation-id resolution and the collateral map write atomic with the `registry`/`reverse` commit: call `insert updated-entry` immediately after computing it (before invoking `receive-tokens`), or restructure `collateral-add` to re-resolve/re-validate the obligation id after the token transfer completes and merge collateral deltas rather than relying on a pre-transfer snapshot. Additionally, add a reentrancy guard (e.g., an "in-progress" flag per account or globally) around `collateral-add`/`debt-add-scaled` so a nested call for the same account cannot execute between the token transfer and the final `insert`.

### Proof of Concept
1. Deploy a malicious contract implementing `<ft-trait>` whose `transfer` function, on its first invocation, calls back into the market implementation's deposit-collateral entrypoint for the same `account` and `asset-id` before returning `(ok true)`.
2. In a Clarinet simnet test: register this malicious ft (bypassing any asset-registry validation, or using an `asset-id` the test controls) and call the market impl's deposit-collateral function once with `account=wallet_1`, `amount=100`.
3. Assert `get-nr` (nonce) increased by 2 in that single transaction (proving two `create` calls occurred for one account).
4. Assert `resolve wallet_1` now returns only one `id`, and `lookup-collateral` for that id does not include the `amount` deposited during the inner (reentrant) call — while `collateral {id: orphaned-id, asset: asset-id}` still holds that amount in the raw map, unreachable via `reverse`.
5. Confirm the transaction as a whole succeeds (does not abort), demonstrating the state is not rolled back and the orphaned collateral is permanently stranded.

    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
