#No Vulnerability found for this question.

The `PackedAncientStorage::pack` algorithm's worst-case fragmentation is bounded by a small constant factor, not unbounded, and several existing guards limit the attacker's ability to force disproportionate work:

1. **Bin-packing overhead is inherently bounded.** In `pack` (accounts-db/src/ancient_append_vecs.rs:1012-1094), the first account added to a new storage is always accepted regardless of size (`bytes_total > 0` guard at line 1057 only rejects subsequent accounts), so a storage can be at most "1 account short of full." For accounts sized just over half of `ideal_size`, each storage ends up ~50%+ full holding one account. This yields at most a 2x storage-count overhead versus optimal packing — a classic, well-understood greedy bin-packing bound, not "near-maximal" fragmentation. [1](#0-0) 

2. **The algorithm and its bounded behavior are explicitly tested.** `test_pack_ancient_storages_varying` asserts that `packed.bytes >= ideal_size - largest_account_size` for all but the last storage, confirming the tight-packing guarantee holds except for a bounded slack equal to one account's size. [2](#0-1) 

3. **Hard caps limit total work regardless of fragmentation.** `combine_ancient_slots_packed` sets `max_resulting_storages: NonZeroU64::new(10)` and `max_ancient_slots: self.max_ancient_storages`, and `truncate_to_max_storages`/`filter_by_smallest_capacity` explicitly cut off processing once the required ancient storage count would exceed these caps, preventing pack from ever producing runaway numbers of storages in a single pass. [3](#0-2) [4](#0-3) 

4. **`ideal_storage_size` is not attacker-fixed.** It is recomputed dynamically each pass from `total_alive_bytes / (max_ancient_slots / 2)` (accounts-db/src/ancient_append_vecs.rs:530-534), a value in the hundreds-of-MB to GB range, floored at `self.ancient_storage_ideal_size`. An attacker would need to precisely straddle this dynamically shifting boundary across many future re-pack invocations, which is not something they can reliably target since it depends on aggregate cluster-wide alive-byte totals, not just their own accounts. [5](#0-4) 

Given the bounded (≤2x) worst-case overhead inherent to the greedy packing design, the hard caps on storage counts, and the non-attacker-controlled dynamic sizing of `ideal_storage_size`, this does not constitute a disproportionate, unbounded resource-exhaustion vulnerability — it is a known, tested, and capped algorithmic tradeoff rather than an exploitable flaw.
