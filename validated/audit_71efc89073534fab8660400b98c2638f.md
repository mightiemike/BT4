### Title
Missing audit-log entry for privileged `ReplayFromBlock` action allows unattributed replay requests - ([File: core/web/replay_controller.go])

### Summary
`ReplayController` is constructed with only an `App chainlink.Application` field and no `audit.AuditLogger`, and `ReplayFromBlock` never emits an audit event, unlike comparable state-changing controllers (e.g. `keys_controller.go`) that call `auditLogger.Audit(...)` on privileged mutations. As a result, a run-role-authenticated user who triggers a chain replay leaves no audit trail identifying who initiated it.

### Finding Description
`ReplayController` is defined as: [1](#0-0) 

and is wired up in the router with no audit logger dependency at all, unlike `NewChainsController`, which explicitly accepts and stores an `audit.AuditLogger`: [2](#0-1) 

`ReplayFromBlock` performs full request validation (block number, force flag, chain family, chain ID) and then directly calls `bdc.App.ReplayFromBlock(ctx, chainFamily, chainID, uint64(blockNumber), force)`, returning a success/error response — at no point is any audit event recorded: [3](#0-2) 

Other controllers that perform privileged/state-changing actions (e.g. key management in `keys_controller.go`) call `auditLogger.Audit(...)` to record the acting principal and action type for the audit trail. `ReplayController` has no such mechanism — there is no field to hold an `AuditLogger`, and none is invoked, so a chain replay (which forces the node to reprocess and potentially re-report on-chain state) is unattributable to the session/user that triggered it. The `auth.RequiresRunRole` middleware only performs authorization (role check) — it does not itself record any audit entry — so nothing else in the request path fills this gap.

### Impact Explanation
Replay actions can affect log/event reprocessing and downstream on-chain reporting for OCR/CCIP-adjacent flows. Because no audit entry ties a specific authenticated principal to the replay action, an incident responder investigating anomalous or unauthorized replay usage (e.g. by a run-role user misusing their access, or a compromised run-role session) has no forensic record identifying who issued the request, when, or with what parameters, unlike equivalent operations on other controllers. This undermines the "privileged actions must be attributable" invariant and weakens incident response/detection capability for cross-chain misreporting scenarios triggered via replay.

### Likelihood Explanation
Any user holding a valid run-role (or higher) authenticated session can trigger this path via `POST /v2/replay_from_block/:number`; no additional privilege, key leakage, or social engineering is required beyond the documented run-role precondition. The gap is deterministic and 100% reproducible on every call — it does not depend on race conditions or unusual configuration.

### Recommendation
Add an `AuditLogger` field to `ReplayController` (mirroring `chainsController`), inject it at construction time in `router.go`, and call `auditLogger.Audit(...)` with a dedicated audit event type (e.g. `ReplayRequested`) including the acting user, chain family, chain ID, block number, and `force` flag before/after invoking `bdc.App.ReplayFromBlock`.

### Proof of Concept
Integration test plan:
1. Set up a test node with an in-memory/mock `audit.AuditLogger` capturing all `Audit(...)` calls, similar to existing controller tests for `keys_controller.go`.
2. Authenticate as a run-role user and issue `POST /v2/replay_from_block/:number?family=<family>&ChainID=<id>`.
3. Assert `App.ReplayFromBlock` was invoked (request succeeded, 200 response with `ReplayResponse`).
4. Assert the mock `AuditLogger.Audit` was **not** called with any replay-related event — demonstrating the missing audit trail.
5. Contrast with an equivalent test against a mutating audited controller (e.g., triggering a key deletion via `keys_controller.go`) where `AuditLogger.Audit` **is** called, confirming the asymmetry described in the finding.
