### Title
gRPC lite-node filter omits `GetTransactionInfoByBlockNum` (and `GetTransactionReceiptById`), unlike the HTTP filter, allowing bypass of the disabled-history-query restriction - (File: framework/src/main/java/org/tron/core/services/filter/LiteFnQueryGrpcInterceptor.java)

### Summary
The gRPC lite-fullnode filter (`filterMethods` in `LiteFnQueryGrpcInterceptor`) and the HTTP lite-fullnode filter (`filterPaths` in `LiteFnQueryHttpFilter`) are supposed to guard an identical set of history-dependent endpoints when a node is running as a lite fullnode with `openHistoryQueryWhenLiteFN=false`. They are not identical: the HTTP filter blocks `gettransactioninfobyblocknum` (and `gettransactionreceiptbyid` on `/wallet`), but the gRPC `filterMethods` set never adds `protocol.Wallet/GetTransactionInfoByBlockNum`, `protocol.WalletSolidity/GetTransactionInfoByBlockNum`, or any `GetTransactionReceiptById` entry at all.

### Finding Description
`LiteFnQueryGrpcInterceptor.interceptCall` rejects a gRPC call only if `filterMethods.contains(call.getMethodDescriptor().getFullMethodName())`, and `filterMethods` is populated in a static block enumerating 23 `protocol.Wallet`/`protocol.WalletSolidity` methods plus `protocol.Database/GetBlockByNum`. [1](#0-0) [2](#0-1) 

The equivalent HTTP filter, `LiteFnQueryHttpFilter.doFilter`, blocks requests whose `requestPath` is in `filterPaths`, and `filterPaths` additionally includes `/wallet/gettransactioninfobyblocknum`, `/walletsolidity/gettransactioninfobyblocknum`, and `/wallet/gettransactionreceiptbyid`: [3](#0-2) [4](#0-3) 

None of these two method names appear anywhere in the gRPC `filterMethods` static initializer. Yet `GetTransactionInfoByBlockNum` is a real RPC handler implemented in `RpcApiService.java` (served for both `protocol.Wallet` and, via `RpcApiServiceOnSolidity`, for `protocol.WalletSolidity`), and it walks a full block range collecting all transaction receipts/logs — an operation the operator explicitly intended to disable on a history-pruned lite node (which is exactly why it is HTTP-blocked). Because the gRPC path performs no such check, a client can call the gRPC method directly and reach the handler, which will either error deep inside store access on missing historical data or, worse, consume CPU/IO scanning ranges of blocks — the exact unbounded/expensive handler the config flag is meant to shut off.

The root cause is that the two allow/deny lists are maintained independently as hard-coded string sets with no shared source of truth (e.g., generated from `api.proto` method descriptors), so they can silently drift out of sync.

### Impact Explanation
This maps to "DoS via RPC-API": an operator who sets `openHistoryQueryWhenLiteFN=false` believes both HTTP and gRPC transports are equally restricted, but an unprivileged gRPC client can still invoke `protocol.Wallet/GetTransactionInfoByBlockNum` and `protocol.WalletSolidity/GetTransactionInfoByBlockNum` (also `GetTransactionReceiptById`), causing the lite node to perform history-store range work it was configured to avoid — either erroring on missing pruned data repeatedly or consuming resources, contrary to the operator's configured restriction.

### Likelihood Explanation
Preconditions match the question's scenario exactly: lite fullnode with `openHistoryQueryWhenLiteFN=false` and the gRPC port exposed (default configuration for a lite node exporting gRPC). No authentication, fee, or special privilege is required — any gRPC client can call the method directly and repeatedly at no cost, making this trivially and repeatedly exploitable.

### Recommendation
Add the missing entries to `LiteFnQueryGrpcInterceptor.filterMethods`: `protocol.Wallet/GetTransactionInfoByBlockNum`, `protocol.WalletSolidity/GetTransactionInfoByBlockNum`, `protocol.Wallet/GetTransactionReceiptById`, and any other HTTP-only guarded path not mirrored in gRPC. Better, derive both `filterMethods` and `filterPaths` from a single shared list (or from `api.proto` annotations) at build/init time, and add an automated test asserting a 1:1 correspondence between the two sets so future additions cannot drift apart.

### Proof of Concept
```java
// JUnit-style differential test demonstrating the asymmetry
@Test
public void testFilterMethodsMissingGetTransactionInfoByBlockNum() {
  Set<String> grpcMethods = LiteFnQueryGrpcInterceptor.getFilterMethods();
  Set<String> httpPaths = LiteFnQueryHttpFilter.getFilterPaths();

  // HTTP explicitly disables this endpoint on a lite node
  assertTrue(httpPaths.contains("/wallet/gettransactioninfobyblocknum"));
  assertTrue(httpPaths.contains("/walletsolidity/gettransactioninfobyblocknum"));

  // gRPC equivalent is NOT guarded -> asymmetry / bypass
  assertFalse(grpcMethods.contains("protocol.Wallet/GetTransactionInfoByBlockNum"));
  assertFalse(grpcMethods.contains("protocol.WalletSolidity/GetTransactionInfoByBlockNum"));
}
```
Request-level reproduction: on a lite fullnode configured with `openHistoryQueryWhenLiteFN=false`,
1. `curl -X POST http://<node>:8090/wallet/gettransactioninfobyblocknum -d '{"num":100}'` → returns "this API is closed because this node is a lite fullnode" (blocked, confirming HTTP filter works).
2. Issue the equivalent gRPC call `protocol.Wallet/GetTransactionInfoByBlockNum` (e.g. via `grpcurl -plaintext <node>:50051 protocol.Wallet/GetTransactionInfoByBlockNum -d '{"num":100}'`) → call is forwarded to the real handler instead of being rejected with `UNAVAILABLE`, proving the restriction is bypassed via gRPC.

  @Override
  public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(ServerCall<ReqT, RespT> call,
      Metadata headers, ServerCallHandler<ReqT, RespT> next) {
    if (chainBaseManager.isLiteNode()
            && !CommonParameter.getInstance().openHistoryQueryWhenLiteFN
            && filterMethods.contains(call.getMethodDescriptor().getFullMethodName())) {
      call.close(Status.UNAVAILABLE
              .withDescription("this API is closed because this node is a lite fullnode"), headers);
      return new ServerCall.Listener<ReqT>() {};
    } else {
      return next.startCall(call, headers);
    }
  }

  @Override
  public void doFilter(ServletRequest servletRequest, ServletResponse servletResponse,
                       FilterChain filterChain) throws IOException, ServletException {
    String contextPath = ((HttpServletRequest) servletRequest).getContextPath();
    String requestPath = contextPath + ((HttpServletRequest) servletRequest).getServletPath();
    if (chainBaseManager.isLiteNode()
            && !CommonParameter.getInstance().openHistoryQueryWhenLiteFN
            && filterPaths.contains(requestPath)) {
      servletResponse.setContentType("application/json; charset=utf-8");
      servletResponse.getWriter().write("this API is closed because this node is a lite fullnode");
    } else {
      filterChain.doFilter(servletRequest, servletResponse);
    }
  }
