Found a strong analog matching the "pause that passes through instead of reverting" mechanism, explicitly labeled `PAUSED: Pass-through without reverting` in the vault `accrue` function, and reused identically across all six vaults.

### Title
Pausing `accrue` silently freezes interest indexes instead of reverting, allowing debt/collateral valuation to desync from real accrual state - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`accrue` in every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) is designed so that when `accrue` is paused via `pause-states`, the function does not revert - it returns the **current, stale** `index`/`lindex` as an `ok` response instead of an error. [1](#0-0) 

This "pass-through instead of revert" is deliberate for the case where the DAO explicitly toggles the `accrue` pause flag (and `set-pause-states` calls `accrue` once right before pausing to flush pending interest, then jumps `last-update` forward on unpause to skip the paused window): [2](#0-1) 

However, `market.clar`'s `accrue-and-cache` treats **any** successful (`ok`) response from `vault-accrue` as a legitimate, freshly-accrued index and unconditionally caches it for the rest of the block: [3](#0-2) 

### Finding Description
The health/interest model of the protocol assumes `index`/`lindex` monotonically reflect real accrued interest since `last-update`. When accrual is paused, `accrue` in the vault does not error out to the caller (`market.clar`) - it silently returns the pre-pause `index`/`lindex` values wrapped in `ok`, indistinguishable from a "no time has passed" result: [4](#0-3) 

`market.clar`'s `borrow`, `repay`, and `liquidate` flows all call `accrue-and-cache`/`vault-accrue` and then compute debt/collateral notional values, LTV, and health directly from whatever index is returned, without ever checking whether the vault is in a paused-accrue state: [5](#0-4) 

Since `set-pause-states` only realigns `last-update` (via `var-set last-update stacks-block-time`) at the moment accrual is un-paused, any period the DAO leaves `accrue` paused causes the vault's `index`/`lindex` to freeze while the protocol continues to treat scaled debt/collateral values as accurate using that frozen index. `market.clar`'s comment block documents the caching model as timestamp-invalidated per block, with no awareness of the pause flag: [6](#0-5) 

This is the same root-cause shape as the Rubicon `[H-10]` bug: one code path (`accrue` under pause) returns a value through the "happy path" `ok` type that a downstream consumer (`market.clar`'s health/liquidation math) treats as fully valid and authoritative, without the invalidation/guard that the design otherwise relies on (timestamp-based cache invalidation, index freshness). Just as Rubicon's `cancel` trusted `isOfferSorted`/`_hide` to always reflect true sort-list membership, Zest's borrow/repay/liquidate math trusts `vault-accrue`'s `ok` result to always reflect true elapsed-time accrual.

### Impact Explanation
While the DAO's decision to pause is itself a "deliberate safety design decision" and out of scope on its own, the concrete mechanism - a guarded state transition (`accrue`) whose guard (`pause`) is bypassed by returning success with stale data rather than reverting - creates a genuine single-transaction risk: within the same paused window, `borrow`, `repay`, and `liquidate` in `v0-4-market.clar` combine the frozen index with live oracle prices to compute LTV/health. If oracle prices move during the pause (or a user manipulates price feeds via `write-feeds` while accrual is frozen), a position's collateral/debt USD valuation is computed off a stale index, potentially permitting under-collateralized borrows or `liquidate` to compute incorrect final debt/collateral amounts - a temporary freezing/mis-valuation of user funds until un-pause realigns `last-update`. This lands in the **High** impact bucket: temporary freezing/mispricing of funds tied to the interest-accrual invariant, not a permanent loss.

### Likelihood Explanation
Likelihood is **low-to-medium**: it requires the DAO to actually toggle `accrue` pause (an operational, intended control) and a user to transact against `borrow`/`repay`/`liquidate` during that specific window while oracle prices diverge from the frozen index basis. It is a single-transaction/single-block class of issue (the interleaving of a frozen accrual index with live-but-independent price resolution within one call), not a multi-block or cross-user race.

### Recommendation
Have `accrue` return an explicit "paused" indicator (or a distinct error) rather than an `ok` with stale index/lindex, and have `market.clar`'s `accrue-and-cache`/borrow/repay/liquidate paths check for that indicator and either revert or treat the position as frozen (skip health mutation) rather than treating the stale return as fresh. Alternatively, ensure any caller that depends on `index`/`lindex` for economic calculations refuses to proceed when the corresponding vault's `accrue` pause flag is set.

### Proof of Concept
1. DAO calls `set-pause-states` on `v0-vault-usdc.clar` with `accrue: true` (this internally calls `accrue()` once to flush pending interest, then sets the pause flag) — [7](#0-6) .
2. Time passes; real interest would have accrued, but `index`/`lindex` remain frozen because every subsequent call to `accrue()` hits the `(get accrue states)` branch and returns the old `{index, lindex}` as `ok` — [4](#0-3) .
3. A user calls `market.clar`'s `borrow`/`repay`/`liquidate` for USDC; `accrue-and-cache` calls `vault-accrue`, receives the frozen `ok` result, and caches it as the block's authoritative index — [3](#0-2) .
4. Debt/collateral USD valuation and LTV/health checks proceed using this stale index combined with live oracle prices, with no check that accrual is paused — [5](#0-4) .
5. If oracle price movement during the pause window makes the frozen-index-based valuation inconsistent with true economic state, borrow/repay/liquidate outcomes are computed on incorrect debt/collateral figures until the DAO un-pauses and `last-update` is jumped forward.

**Uncertainty note:** I could not find any explicit guard in `market.clar` that checks a vault's `accrue` pause state before using `accrue-and-cache`/`get-cached-indexes` results, based on the indexed content available. Given index-size limits on the codebase index, I recommend a full review of `v0-4-market.clar`'s complete `borrow`/`repay`/`liquidate` bodies and all vault `set-pause-states`/`accrue` implementations in a Devin session to confirm there is no compensating check elsewhere (e.g., in `write-feeds` or a separate pause-state read) that mitigates this before treating it as conclusively exploitable.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

        (ok indexes)))))
