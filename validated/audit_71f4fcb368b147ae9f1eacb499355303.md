**Reasoning:**

`get_all_checkpoint_indices` treats a transaction as a checkpoint boundary if either `txn.is_non_reconfig_block_ending()` is true or `output.has_new_epoch_event()` is true [1](#0-0) . `has_new_epoch_event` is implemented purely by checking whether any emitted event's `type_tag` equals the `NewEpochEvent`/`NewEpoch` struct type defined by the `0x1::reconfiguration` module [2](#0-1) [3](#0-2) , with the type tags themselves being `Lazy` statics pinned to `0x1::reconfiguration::NewEpochEvent`/`NewEpoch` [4](#0-3) .

The attack premise requires an attacker-controlled, non-reconfiguration user transaction to emit a `ContractEvent` whose `type_tag` matches this exact struct type. That is not possible under Move's module encapsulation model: a struct value of type `0x1::reconfiguration::NewEpochEvent` (or the V2 `NewEpoch` struct) can only ever be constructed/packed by bytecode belonging to the `reconfiguration` module itself, since Move's verifier restricts struct-pack operations to the module that declares the struct. An arbitrary user transaction (unprivileged Move script/entry function) cannot fabricate a `ContractEvent` carrying that specific type tag unless it actually invokes code inside the `reconfiguration` module that performs a genuine reconfiguration and emits the real event — at which point it *is* a genuine reconfiguration by definition, not a forged one.

Because forging the event's type tag is blocked by Move's type/module system (a VM-level invariant that this Rust-layer code correctly relies on), `has_new_epoch_event()` cannot be true for a non-reconfiguration transaction under normal (non-hard-fork, non-VM-bug) execution. This means the described corruption path into `get_all_checkpoint_indices` / `StateUpdateRefs::index_write_sets` is not reachable from unprivileged input as posed, so it does not meet the scope's "unprivileged input" root-cause requirement.
