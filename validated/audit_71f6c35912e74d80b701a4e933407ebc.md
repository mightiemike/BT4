### Title
Webhook `domain` (shop) header is not covered by HMAC signature, allowing cross-tenant impersonation in webhook processing - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`, `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
`shopify.webhooks.validate()` / `validateHmacFromRequestFactory` only computes and checks the HMAC over the raw request body [1](#0-0) . The `X-Shopify-Shop-Domain` header, which is later trusted as the identity ("account") the webhook belongs to, is read separately from the (unsigned) headers and is never included in the HMAC computation [2](#0-1) .

### Finding Description
This mirrors the Perennial `VerifierBase` pattern: a signature proves *something* was signed correctly (here, that `rawBody` matches a HMAC computed with the app's shared secret), but the value used afterward to select *whose account* the privileged action applies to (`common.account` in Perennial, `domain`/shop here) is not bound to that same signature.

Concretely:
- `validateHmacFromRequestFactory` validates `hmac` against `rawBody` only: `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` [3](#0-2) .
- `checkWebhooksHeaders`/`checkEventsHeaders` then independently pull `domain` (shop), `topic`, `webhookId`, etc. straight from HTTP headers with no cryptographic tie to the HMAC-validated body [2](#0-1) .
- Downstream, `authenticateWebhookFactory` uses `check.domain` directly to look up the shop's stored offline session and build an authenticated Admin API client for that shop: `ensureValidOfflineSession(params, check.domain)` followed by `adminClientFactory({params, session, ...})` [4](#0-3) .

Because the app's webhook secret (`apiSecretKey`) is shared across every shop installed on the app (it is not per-shop), any party who legitimately receives one genuine webhook delivery for their own shop (i.e., any single merchant using the app — an unprivileged, non-admin actor relative to other tenants) obtains a valid `(rawBody, hmac)` pair. Because `domain` is not part of the signed material, that same `(rawBody, hmac)` pair can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header changed to point at a different, victim shop that is also installed on the app. The HMAC check still passes (it only checks `rawBody`), and the webhook pipeline proceeds to load the victim shop's offline session and execute the app's webhook handler logic (and Admin API client) as if the event legitimately originated from the victim shop.

### Impact Explanation
This is a cross-tenant confused-deputy: a single merchant with no special privileges can cause the app's webhook processing pipeline to run under a different shop's identity/session — potentially triggering handler side effects (e.g. treating an `APP_UNINSTALLED` payload as coming from the victim shop, or any custom `webhooks.addHandlers` callback logic that reads `shop`/`domain` and acts on the victim's data/session), or obtaining a scoped Admin API client for the victim's shop inside `authenticateWebhookFactory`. The severity depends on what the consuming app does with `shop`/`session` in its webhook handlers, but the shopify-app-js framework itself provides no binding between the cryptographically-verified payload and the shop identity attached to it, which is exactly the missing-authorization-binding pattern described in the source report.

### Likelihood Explanation
Reachable by any anonymous HTTP POST to the app's public webhook endpoint — no secret leakage, no privileged access, and no dependency vulnerability is required. The only "credential" needed is a single previously-observed valid `(rawBody, hmac)` pair, which any merchant using the app naturally receives from Shopify for their own shop (or which could be replayed from a captured request). This satisfies the "anonymous HTTP/webhook request from a single merchant" reachability bar in the rules.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an independent header:
- Include the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`/timestamp) value inside the HMAC-signed material, or
- After validating the body HMAC, cross-check that the `domain` header matches an expected/allow-listed shop for that specific webhook subscription (e.g., verify against Shopify's registered webhook endpoint metadata or per-shop webhook secrets), and reject/replay-protect using `webhookId` to prevent reuse of a valid `(rawBody, hmac)` pair against a different `domain`.

### Proof of Concept
1. App is installed on Shop A and Shop B (both share the same app `apiSecretKey`).
2. Shopify sends a legitimate webhook to the app for Shop A: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. Shop A's owner (or anyone able to observe/capture this legitimate delivery, e.g. via their own endpoint logs) resends the identical `POST` with the same body `B` and same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `validateHmacFromRequestFactory` recomputes `HMAC(secret, B)`, which matches, so `valid: true` is returned along with `domain: 'shop-b.myshopify.com'` taken straight from the attacker-controlled header [5](#0-4) .
5. `authenticateWebhookFactory` loads Shop B's offline session via `ensureValidOfflineSession(params, check.domain)` and builds an Admin API client scoped to Shop B, then invokes the app's webhook handler with attacker-supplied body `B` attributed to Shop B [4](#0-3) .
