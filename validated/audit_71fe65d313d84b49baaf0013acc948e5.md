### Title
Hardcoded ETH-implicit wallet global-contract code hash constants create consensus-halt / bricking risk if incorrect - (File: runtime/near-wallet-contract/src/lib.rs)

### Summary
`near-wallet-contract` hardcodes the code hashes of the "global contract" that legacy ETH-implicit accounts must use for execution, keyed by `chain_id` (mainnet/testnet), analogous to `StableOracleWBTC.sol` hardcoding a price-feed address in its constructor. If any of these hardcoded hashes is wrong (does not correspond to an actually-deployed global contract with that hash on the corresponding chain), the runtime's contract resolution path will point ETH-implicit accounts at a global contract that cannot be found in state. [1](#0-0) 

### Finding Description
`eth_wallet_global_contract_hash` returns a hardcoded `CryptoHash` literal per chain, used by `RuntimeContractIdentifier::resolve` in the runtime apply path whenever an account is recognized as a legacy ETH-implicit account with a known "magic bytes" wallet contract hash: [2](#0-1) 

This resolved `Global { code_hash, .. }` value is later used to fetch the actual global contract's WASM bytes from the trie via `GlobalContractAccessExt::code`/`hash`, which explicitly raises `StorageError::StorageInconsistentState` if the referenced `GlobalContractCode` trie key is missing: [3](#0-2) 

This mirrors the audit finding's root cause exactly: a security- and execution-critical address/hash constant is hardcoded in source and trusted without further verification against on-chain state, rather than being derived, looked up, or asserted to match the actually-deployed contract identified by `wallet_contract_magic_bytes`/`LegacyEthWallet`. If the mainnet or testnet hash constant were wrong (e.g., swapped, mistyped, or pointing at a different contract version), every ETH-implicit account interaction that hits this legacy resolution branch would attempt to execute a non-existent (or, in an even worse scenario, an unintended but existing) global contract.

### Impact Explanation
Because `StorageError` propagates as `StorageInconsistentState`, which is treated as a fatal storage inconsistency throughout the runtime apply path, any function call, transfer-triggering execution, or view call against an affected ETH-implicit account would fail deterministically. This is a transaction-triggered halt/DoS for every legacy ETH-implicit wallet account on the affected chain, and because the value is baked into the binary rather than governed by protocol version data, a wrong constant would be silently wrong for all validators simultaneously (a shared systemic misconfiguration, not a state-root divergence between honest nodes, since all nodes run the same code) — but it would permanently freeze funds/functionality on all such accounts (no valid transaction can reach them until a protocol/binary fix ships), which matches the "permanently frozen funds" and "transaction-triggered halt" impact categories called out as in-scope.

### Likelihood Explanation
Likelihood of this exact bug existing today cannot be confirmed by static reading alone — verifying correctness would require comparing the hardcoded hashes against the actual deployed global contract WASM hash on mainnet/testnet, which requires live-chain state (out of reach for this review). The report itself only serves as a bug-class hint (hardcoded external address risk), not proof of an actual mismatch in this codebase. The pattern is structurally identical to the Solidity bug (hardcoded, unverified critical constant used directly in contract-resolution logic), and the blast radius (all legacy ETH-implicit wallet accounts) is broad, but I found no direct evidence of an actual mismatch between the hardcoded hashes and the deployed contracts.

### Recommendation
- Add a runtime or genesis-time consistency check that verifies `eth_wallet_global_contract_hash(chain_id)` actually corresponds to a `GlobalContractCode` entry present in state (or is otherwise guaranteed to be deployed before the ETH-implicit account migration takes effect), failing fast at node startup rather than at arbitrary user transaction time.
- Add unit/integration tests (beyond `wallet_contract.rs`) that assert `eth_wallet_global_contract_hash` for each chain matches the hash of the actual contract WASM bundled/deployed for that chain, to catch accidental constant drift at compile time (similar to how `MAINNET`/`TESTNET`/`LOCALNET` bytes are embedded via `include_bytes!`).
- Consider deriving these hashes from the embedded WASM (`CryptoHash::hash_bytes`) for `LOCALNET`-style chains, and only hardcode mainnet/testnet exactly because they are external deployments already on-chain — but add an explicit doc/test cross-reference so any change requires deliberate re-derivation.

### Proof of Concept
Not applicable as a live exploit — this is a static-constant-correctness class of bug requiring chain-state comparison to confirm. The reachable path for any wrongness is: any transaction/RPC `FunctionCall`/`Transfer` targeting a pre-existing legacy ETH-implicit account (`AccountType::EthImplicitAccount` with a recognized magic-bytes hash) → `RuntimeContractIdentifier::resolve` → `eth_wallet_global_contract_hash(chain_id)` → `GlobalContractAccessExt::code`/`hash` lookup failing with `StorageInconsistentState` if the hash doesn't match a deployed global contract. impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }
