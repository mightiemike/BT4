### Title
Fixed-cost rate limiting on `/getblockbylimitnext` allows disproportionate CPU cost per rate-limited call - ([File: framework/src/main/java/org/tron/core/services/http/GetBlockByLimitNextServlet.java])

### Summary
`GetBlockByLimitNextServlet.fillResponse` bounds the window to at most `BLOCK_LIMIT_NUM = 100` blocks per call, but the `RateLimiterServlet` wrapper that gates access only enforces a fixed QPS/permit budget, independent of how many blocks or transactions are actually serialized in the response. [1](#0-0)  An unprivileged caller can therefore always request the maximum 100-block window and slide it forward across the chain at the same rate-limited cost regardless of whether those blocks are empty or maximally full of transactions.

### Finding Description
`fillResponse` accepts `startNum`/`endNum` from an unauthenticated HTTP GET/POST and only checks `endNum > 0 && endNum > startNum && endNum - startNum <= BLOCK_LIMIT_NUM` before calling `wallet.getBlocksByLimitNext(startNum, endNum - startNum)` and serializing the result via `Util.printBlockList(reply, visible)`. [1](#0-0)  The only gating mechanism is `RateLimiterServlet.service`, which calls a per-endpoint `IRateLimiter.acquirePermit` and a `GlobalRateLimiter.acquirePermit`, both of which are QPS/permit-based token buckets keyed on request count, not on response size or number of transactions serialized. [2](#0-1)  The default adapter, `DefaultBaseQqsAdapter`, simply delegates to `QpsStrategy.tryAcquire()`/`acquire()`, a flat requests-per-second limiter with no notion of per-request "weight." [3](#0-2)  Consequently, a 100-block window packed with maximum-size blocks (full of transactions) costs exactly the same "one permit" as a 100-block window of near-empty blocks, even though the former requires materially more CPU/memory to fetch and serialize via `Util.printBlockList`.

### Impact Explanation
This is a resource-cost asymmetry: an attacker who always targets the busiest historical ranges (e.g., sliding across blocks with maximal transaction counts) pays the same rate-limit cost as an attacker requesting cheap/empty ranges, letting them extract the maximum achievable CPU/serialization cost per allowed QPS unit. This does not bypass rate limiting itself (it still applies), and it does not grant unauthorized reads (block history is intentionally public data, capped at 100 blocks per call by `BLOCK_LIMIT_NUM`), so the impact is limited to increased-but-bounded per-call CPU cost within an already-capped window, not unbounded amplification.

### Likelihood Explanation
Feasible without authentication and fully repeatable: any client can issue GET/POST requests to `/getblockbylimitnext` (and its PBFT/Solidity variants) at the servlet's configured QPS rate, always using the maximum window size and always targeting the historically busiest ranges. However, the effect is bounded — the window size is hard-capped at 100 blocks (`BLOCK_LIMIT_NUM`), so the maximum work per call is inherently bounded by chain-imposed limits on block size/transaction count, not unbounded amplification. This is a variance issue in cost accounting rather than an amplification/DoS vector that can grow unboundedly.

### Recommendation
If tighter cost fairness is desired, consider a cost-weighted rate limiter for this endpoint (e.g., weight permits by requested block-count and/or historical block size), or cap per-endpoint QPS conservatively assuming worst-case (max-size) blocks so that sustained worst-case usage stays within acceptable CPU budget. This is a defense-in-depth/cost-fairness hardening rather than a critical vulnerability, since the window is already bounded to 100 blocks by `BLOCK_LIMIT_NUM`.

  private void fillResponse(boolean visible, long startNum, long endNum,
      HttpServletResponse response)
      throws IOException {
    if (endNum > 0 && endNum > startNum && endNum - startNum <= BLOCK_LIMIT_NUM) {
      BlockList reply = wallet.getBlocksByLimitNext(startNum, endNum - startNum);
      if (reply != null) {
        response.getWriter().println(Util.printBlockList(reply, visible));
        return;
      }
    }

package org.tron.core.services.ratelimiter.adapter;

import org.tron.core.services.ratelimiter.RuntimeData;
import org.tron.core.services.ratelimiter.strategy.QpsStrategy;

public class DefaultBaseQqsAdapter implements IRateLimiter {

  private QpsStrategy strategy;

  public DefaultBaseQqsAdapter(String paramString) {
    this.strategy = new QpsStrategy(paramString);
  }

  @Override
  public boolean tryAcquire(RuntimeData data) {
    return strategy.tryAcquire();
  }

  @Override
  public boolean acquire(RuntimeData data) {
    return strategy.acquire();
  }
}
