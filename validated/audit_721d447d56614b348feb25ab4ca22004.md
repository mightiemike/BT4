## Title
Deleting an account leaks postponed-receipt and promise-yield state, letting a stale receipt execute against a re-created account - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` — the function invoked by `action_delete_account` when a `DeleteAccount` action is processed — only clears the account record, its contract code, its access/gas keys and its contract data. It never clears the receipt-plumbing rows keyed by the same `account_id`: `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`. This is analogous to the iwlwifi bug where `AP` removal failed to release the link-mapping resource, so a later attempt to reuse the same slot picked up stale state. Here, a later `DataReceipt`/`PromiseResume`/yield-timeout addressed to the same account id can still find the leftover pointer and will execute the old, pre-deletion receipt against whatever account currently occupies that id.

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs` is documented as removing "account, code and all access keys and gas keys associated to it," and that is exactly what it does: [1](#0-0) 
It iterates and deletes access keys/gas-key nonces and contract data: [2](#0-1) [3](#0-2) 
but it never touches `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`/`DataIdToYieldId` — all of which are keyed by `(receiver_id, data_id/receipt_id)`: [4](#0-3) 

`action_delete_account` calls `remove_account` and then simply sets the in-memory `account` to `None`, with no check for outstanding postponed receipts, yielded receipts, or pending data counts for that account: [5](#0-4) 

Meanwhile, an account can accumulate a postponed receipt (waiting for a cross-contract call's response) via `process_action_receipt`, which persists `PostponedReceiptId`, `PendingDataCount`, and the receipt itself keyed to the receiver account, before the corresponding `DataReceipt` has arrived: [6](#0-5) 

When the awaited `DataReceipt` eventually arrives — potentially after the account has been deleted and a *new* account created under the same id — `process_receipt` looks up `PostponedReceiptId` purely by `(receiver_id, data_id)`, with no check that the account is the same incarnation that created the dependency, decrements `PendingDataCount`, fetches the postponed receipt, and executes it via `apply_action_receipt` against whatever account now exists under that id: [7](#0-6) 

The same pattern exists for `PromiseYield`/`PromiseResume`: a yield receipt is stored keyed by `(receiver_id, data_id)` and is executed on a matching resume with no verification that the account hasn't been deleted/re-created since the yield was created: [8](#0-7) 
and yield timeouts are processed purely from the global `PromiseYieldTimeout` queue and the leftover `PromiseYieldReceipt` key, again with no account-incarnation check: [9](#0-8) 

The codebase already has a test acknowledging that delete+recreate within the same chunk is a real, exercised scenario (`test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`), but that test only guards code-resolution caching in the receipt-preparation pipeline, not the postponed-receipt/promise-yield trie state: [10](#0-9) 

### Impact Explanation
A stale `ActionReceipt` (with actions, deposit, and `predecessor_id` fixed at the time it was postponed/yielded, under the *old* account's authorization context) can be resurrected and executed against a *new* account occupying the same id. If the new account's contract trusts callbacks based on `predecessor_id` (e.g. an oracle/bridge/callback pattern), or if the resurrected actions include a `Transfer`/`FunctionCall` with a deposit, this results in unauthorized state changes or value movement against a contract that never issued the request that produced this receipt — an invalid state transition being accepted that no current account state authorized.

### Likelihood Explanation
Reaching this requires only ordinary, permission-less transactions: (1) trigger a cross-contract call whose callback is postponed (or a `yield`), (2) self-delete the account before the dependency resolves, (3) recreate the account (or have another party create it, since sub-account creation is permission-less by the parent). All three steps are standard `Action`s reachable by any signer/contract deployer; no validator or network-layer control is needed. Timing (deleting between dispatch and callback arrival) is achievable across shards/chunks given normal cross-shard receipt latency.

### Recommendation
`remove_account` should also scan and remove all `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` entries for the account being deleted (mirroring the existing access-key/contract-data iteration-and-delete pattern already used in the same function), or alternatively reject `DeleteAccount` while such pending entries exist for the account.

### Proof of Concept
1. Account `child.alice.near` makes a cross-contract call to `bob` and awaits the callback (creates `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` keyed to `child.alice.near`).
2. Before `bob`'s `DataReceipt` arrives, `child.alice.near` submits `DeleteAccount` (refunding balance to `alice.near`); `remove_account` clears the account/keys/contract but leaves the postponed-receipt rows.
3. `alice.near` immediately recreates `child.alice.near` and deploys a different/new contract.
4. `bob`'s delayed `DataReceipt` for the original `data_id` finally arrives; `process_receipt`'s `Data` branch finds the still-present `PostponedReceiptId`, decrements `PendingDataCount` to 0, fetches the original `PostponedReceipt`, and executes it via `apply_action_receipt` against the freshly created `child.alice.near`/new contract — running old, unrelated actions the new contract never requested.
