### Title
Wallet Contract Pays Relayer Fee Unconditionally Without Verifying the Underlying Transfer Succeeded - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract` (the eth-implicit-account emulation contract reachable via any relayed Ethereum-style transaction) creates the relayer's fee-refund promise *before* it knows whether the emulated action (`EOABaseTokenTransfer` or `ERC20Transfer`) actually succeeds. This is the on-chain analog of the reported ERC20 bug class: code assumes a value-moving operation succeeded and moves further funds on that assumption, without checking the actual execution result — exactly like not checking `transfer()`'s boolean return before treating it as successful.

### Finding Description
In `inner_rlp_execute`, for both `EOABaseTokenTransfer` and `ERC20Transfer` with a non-zero `fee`, the code immediately creates an independent promise batch that transfers the fee to the caller (relayer), unconditional on the outcome of the actual emulated action: [1](#0-0) 

This `refund_promise` is a separate receipt from the one that carries out the user's intended `ERC20Transfer`/base-token transfer and its `rlp_execute_callback`. The callback logic that does check `PromiseResult::Failed` vs `Successful` (and only refunds the *caller_deposit*, i.e. attached NEAR) is entirely independent of this fee transfer: [2](#0-1) 

Because the fee-paying promise is dispatched at the very start of `inner_rlp_execute` — before the NEP-141 `storage_balance_of`/`ft_transfer`/`storage_deposit` chain even begins — a relayer is paid its fee regardless of whether the underlying `ft_transfer` (or base-token transfer) later fails (e.g., insufficient token balance, receiver not registered and `storage_deposit` insufficient, non-standard token panics, or any other reachable failure in `nep_141_storage_balance_callback` / `rlp_execute_callback`). There is no check of the actual transfer's execution result before crediting the fee value to the relayer.

### Impact Explanation
Any submitted RLP-encoded transaction with a non-zero fee causes value (the fee, denominated in NEAR) to move to the relayer even when the user's actual token/base-token transfer action fails on-chain. This is unconditional/unauthorized value movement that is not gated on successful execution of the value-bearing action it is meant to compensate, matching the "loss of funds from unchecked transfer success" bug class from the source report. A relayer (or a user acting as their own relayer to a wallet contract they do not own) can systematically submit transactions destined to fail (e.g., transferring more tokens than balance, or to a receiver that will reject `storage_deposit`) while still collecting the fee every time, extracting value from the wallet-contract account without ever completing the promised action.

### Likelihood Explanation
This is reachable by any relayer/meta-transaction sender relaying a signed Ethereum-style transaction through `rlp_execute` — no privileged access is required, and it is a normal supported path (`ERC20Transfer`/`EOABaseTokenTransfer` with `fee` are documented, expected relayer-compensation mechanisms). No malicious validator, network, or node behavior is needed — only crafting/relaying a transaction whose target action is bound to fail while carrying a non-zero fee.

### Recommendation
Do not dispatch the fee-refund promise independently of the underlying action's outcome. Instead, chain the fee payment after (or make it conditional on) confirmation that the actual `ERC20Transfer`/`EOABaseTokenTransfer` action succeeded — e.g., move the fee transfer into `rlp_execute_callback` (or an equivalent step) gated on `PromiseResult::Successful`, symmetric to how `caller_deposit` refunds are already conditioned on `PromiseResult::Failed`.

### Proof of Concept
1. A relayer submits an RLP transaction via `rlp_execute` representing an `ERC20Transfer` with a non-zero `fee`, where the sender's token balance is insufficient (or the receiver's `storage_deposit` will fail).
2. `inner_rlp_execute` immediately schedules `env::promise_batch_action_transfer(refund_promise, *fee)` to the predecessor (relayer) at lines 381-384, independent of the transfer promise chain.
3. The subsequent `ft_transfer`/`storage_deposit` chain fails and `rlp_execute_callback` reports `success: false`, refunding only the `caller_deposit` (attached NEAR), not the already-paid fee.
4. The relayer has received the fee even though the intended value transfer never completed, demonstrating unconditional value movement decoupled from action success.
