### Title
Uncontrolled Recursion in `get_recursive_transaction_results` Enables RPC-Triggered Stack Overflow via Chained Receipts - ([File: chain/chain/src/chain.rs])

### Summary
`Chain::get_recursive_transaction_results` recurses once per receipt in a transaction's execution DAG, exactly mirroring the reported NestJS `handleData` bug class (CWE-674/CWE-770): unbounded, attacker-influenced recursion depth with no explicit maximum-depth guard, reachable by any unprivileged caller (RPC client asking for the status of a transaction that a signer/contract deployer constructed to produce a long receipt chain).

### Finding Description
`get_recursive_transaction_results` walks the outcome tree of a transaction depth-first, recursing for every `receipt_id` referenced by an outcome, with no depth counter or recursion limit: [1](#0-0) 

This is invoked directly by `get_final_transaction_result`, the function that answers `tx`/`EXPERIMENTAL_tx_status` JSON-RPC queries: [2](#0-1) 

A transaction signer fully controls the shape of this DAG: a contract can chain `promise_then`/`promise_create` cross-contract calls so that each receipt's execution produces exactly one more `receipt_id`, forming a long linear chain rather than a shallow tree. The repository already contains a test contract built for exactly this purpose — recursively re-invoking itself via cross-contract calls until gas runs low: [3](#0-2) 

Once such a transaction is included and its receipts begin executing, any RPC caller who queries its status causes the view client / chain code to recurse once per hop in that chain — the recursive-call analog of the Nest `handleData` issue, where each call only shrinks the remaining "buffer" (remaining receipt chain) by one instead of being bounded by an explicit depth/size check.

### Impact Explanation
If the receipt chain is deep enough to exhaust the call stack, the recursive walk aborts the OS thread with a stack overflow, which for Rust processes is not a catchable panic — it aborts the process. Because this code path is reachable through a plain JSON-RPC transaction-status query, an unprivileged RPC caller could crash the node process serving that RPC (view client), which is an availability impact and, if triggered against a chunk-producing node's RPC/view surface, a transaction-triggered halt vector. This matches CWE-674 (Uncontrolled Recursion) / CWE-770 (Allocation of resources without limits), the same defect class as the reported advisory.

### Likelihood Explanation
The likelihood is constrained: each additional hop in the receipt chain requires spending prepaid gas for a new action receipt (bounded by `max_total_prepaid_gas` = 300 Tgas per transaction and per-hop action/function-call fees), so a single transaction cannot make the chain arbitrarily deep. Whether the maximum achievable chain length (given per-hop gas costs) is sufficient to exhaust a node's stack depends on the per-frame stack cost of `get_recursive_transaction_results` (which calls into outcome/store lookups) and the configured thread stack size, which was not established in this review. This uncertainty means the finding is best treated as a plausible but not fully proven crash vector; it should be validated experimentally (constructing a maximal-length chain and measuring actual stack consumption) before treating it as confirmed-exploitable.

### Recommendation
- Convert `get_recursive_transaction_results` to an iterative worklist/stack-based traversal instead of native recursion, removing dependence on the call stack entirely.
- Add an explicit maximum traversal depth/outcome count independent of gas accounting, returning an error (e.g. truncated result or `TxStatusError`) once exceeded, analogous to the fix pattern used for `maxBufferSize` in the referenced advisory.

### Proof of Concept
1. Deploy a contract using a chained cross-contract-call pattern such as `max_self_recursion_delay` (already present in the test contracts) that recursively calls itself via `promise_then`, producing a long linear sequence of dependent receipts until gas is exhausted.
2. Submit the transaction and let its receipt chain execute across blocks.
3. As soon as the transaction hash exists in the chain store, issue repeated `tx`/`EXPERIMENTAL_tx_status` JSON-RPC calls against the node for that transaction hash, forcing `get_final_transaction_result` → `get_recursive_transaction_results` to recurse across the full chain length.
4. Measure whether the achievable chain depth (bounded by gas) combined with the per-frame stack cost of this function is sufficient to overflow the RPC/view-client thread's stack.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is

/// This is a stable alternative to yield/resume proposal at the time of writing.

pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];

    let recursion = u32::from_be_bytes(bytes);

        gas_fixed,
        gas_weight,
