### Title
Unbounded secondary-index growth lets any user inflate another account's `SplTokenOwner`/`SplTokenMint` index entry, making scans of that key disproportionately expensive - (File: accounts-db/src/accounts_index/secondary.rs)

### Summary
The `StrategyRegistry`-style bug (anyone can grow another user's on-chain array via a permissionless call, which is later copied wholesale into memory and made expensive to process) has a direct analog in Agave's `SecondaryIndex` used for `AccountIndex::SplTokenOwner` / `SplTokenMint` / `ProgramId`. Any user can create SPL Token accounts whose `owner` (or `mint`) field is set to an arbitrary pubkey — including another user's pubkey — with no cap on how many such accounts can be indexed under that key. Reads of that key (`get_index_key_pubkeys`, used to serve `getTokenAccountsByOwner`/`getProgramAccounts`-style scans) copy the *entire* list of inner keys out of the index in one call.

### Finding Description
`SecondaryIndex::insert` records `inner_key` (an account pubkey) under `key` (the token account's `owner` or `mint` field, both of which are attacker-controlled 32-byte values inside the account data) with no bound on how many inner keys can accumulate under a single outer key: [1](#0-0) 

Because the SPL Token "owner" field is arbitrary data chosen by whoever creates/initializes the token account, an attacker can create an unbounded number of token accounts stamped with a victim's pubkey as the owner, all of which get inserted into `spl_token_owner_index` for that victim: [2](#0-1) [3](#0-2) 

When anything later queries that key (e.g. a `getTokenAccountsByOwner` RPC call for the victim's pubkey), the full list of accumulated inner keys is copied out of the map: [4](#0-3) [5](#0-4) 

This is consumed directly by the RPC scan path used to serve owner-filtered token account queries: [6](#0-5) 

This is structurally identical to the reported bug class: a permissionless action (creating/initializing a token account with an arbitrary owner field) inflates a data structure keyed by *someone else's* identity, with no size limit, and a later legitimate operation (querying/scanning that identity's data) must copy/process the entire inflated structure.

### Impact Explanation
A validator/RPC node running with `--account-index spl-token-owner` (or `spl-token-mint`) enabled is vulnerable to a storage- and CPU-amplification DoS: an attacker can cheaply mint a very large number of token accounts with a chosen victim owner/mint key, growing that key's index entry without bound. Any subsequent `getTokenAccountsByOwner`/`getProgramAccounts`-with-secondary-index query for that key, or any internal metric/logging pass (`log_secondary_indexes`, `get_index_key_size`), incurs cost proportional to the attacker-inflated size rather than to genuine holdings, degrading RPC service and consuming excess memory. It does not cause consensus divergence or corrupt balances/hashes; the impact is disproportionate storage/CPU cost concentrated on the secondary-index feature.

### Likelihood Explanation
Creating SPL Token accounts with an arbitrary `owner` byte-field is a normal, permissionless, cheap operation (standard `InitializeAccount` with any owner pubkey); no special privilege is needed. The only precondition is that the node being targeted has the relevant secondary index (`SplTokenOwner`/`SplTokenMint`/`ProgramId`) enabled, which is common on RPC-serving nodes that support these queries. Given the lack of any cap in `SecondaryIndex::insert`, likelihood of triggering unbounded growth is high once secondary indexing is enabled.

### Recommendation
Bound the number of inner keys tracked per outer key in `SecondaryIndex` (e.g., a configurable maximum entries per outer key, analogous to the report's suggested cap of ~10 for spare subaccounts), and/or paginate `get_index_key_pubkeys`/`keys()` reads so a single query cannot be forced to copy an attacker-inflated list in one unbounded allocation. Consider rate-limiting or flagging owners/mints whose associated-account count grows anomalously fast.

### Proof of Concept
1. Enable `--account-index spl-token-owner` on a node.
2. Repeatedly submit `InitializeAccount`/`InitializeAccount3` instructions for new SPL Token accounts, each setting the `owner` field to a fixed victim pubkey (this field is fully attacker-controlled and requires no permission from the victim).
3. Each such account insertion calls `update_spl_token_secondary_indexes` → `SecondaryIndex::insert`, which pushes into `spl_token_owner_index.index[victim]` with no upper bound, as shown at `accounts_index.rs:557-580` and `secondary.rs:132-153`.
4. Once the index for `victim` contains a very large number of entries, any call to `getTokenAccountsByOwner(victim)` (`rpc.rs:2310-2358`) or internal calls to `get_index_key_pubkeys`/`get_index_key_size` (`accounts_index.rs:376-383`, `accounts_index.rs:582-596`) must materialize/iterate the entire inflated `Vec<Pubkey>`, imposing cost proportional to the attacker's spam rather than to the victim's actual holdings.
