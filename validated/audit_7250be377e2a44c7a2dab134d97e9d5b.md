### Title
DeleteAccount's single `beneficiary_id` field can cause an account's entire balance to be permanently burned instead of refunded - ([File: runtime/runtime/src/actions.rs])

### Summary
`DeleteAccountAction` uses a single, format-validated-only `beneficiary_id` field to receive the remaining balance of a deleted account. [1](#0-0)  Unlike other value-recipient fields in the runtime, there is no check that this account actually exists before the delete completes, and no existence check occurs until the resulting refund receipt is executed by a later (`system`-predecessor) receipt. If `beneficiary_id` does not exist and is not eligible for implicit-account creation, the refund receipt fails and the entire transferred balance is burned rather than returned to anyone — an unrecoverable, permanent loss of value, directly analogous to the reported "single recipient field is error-prone and can permanently destroy value" bug class.

### Finding Description
`action_delete_account` computes the account's balance and unconditionally pushes a new balance-refund receipt targeting `delete_account.beneficiary_id`, then deletes the account and clears its state: [2](#0-1) 

The only validation ever performed on `beneficiary_id` is that it is a syntactically valid `AccountId` — there is no existence check at the time the `DeleteAccount` action executes: [3](#0-2) 

The refund is materialized as a new `Receipt::new_balance_refund` with `predecessor_id = "system"` and a plain `Transfer` action to `beneficiary_id`: [4](#0-3) 

When that receipt is later applied, `check_account_existence` is invoked for the `Transfer` action. If the account does not exist, it falls into `check_transfer_to_nonexisting_account`, which only allows the transfer to proceed if the target id is eligible for **implicit** account creation; otherwise it fails with `AccountDoesNotExist`: [5](#0-4) [6](#0-5) 

Critically, when a receipt whose `predecessor_id` is `"system"` fails, the runtime does **not** retry or bounce the funds back anywhere — it burns them outright: [7](#0-6) 

So the sequence "syntactically-valid but non-existent, non-implicit `beneficiary_id`" → "refund receipt created" → "refund receipt fails on non-existent account" → "`other_burnt_amount` increases by the entire deposit" results in complete, permanent, unrecoverable loss of the deleted account's balance. This mirrors the external report's root cause exactly: a single recipient field that is not cross-checked for compatibility/existence before the value-transfer commits, leading to permanently lost value when the recipient cannot actually receive it.

### Impact Explanation
Any unprivileged account owner (or any full-access-key holder, or a relayer executing a meta-transaction/delegate action) who submits a `DeleteAccount` action with a mistyped, stale, or otherwise non-existent `beneficiary_id` permanently loses their entire remaining NEAR balance — it is burned from total supply rather than refunded to any party. This is a genuine, protocol-level unrecoverable value-loss condition reachable from a single submitted transaction, consistent with the "permanently frozen/lost funds" impact category. Because `DeleteAccount` must be the terminal action, there is no way to detect or roll back the mistake once the transaction is accepted.

### Likelihood Explanation
This is trivially triggerable by any account holder — no special privileges, malicious peers, or protocol-level conditions are required, only a typo or reuse of a previously-existing-but-now-deleted `beneficiary_id`, or supplying an account that was never created. Given that account deletion is a normal, commonly-used operation (e.g., cleanup, meta-transaction relayer flows such as `meta_tx_delete_account`), the likelihood of accidental value loss is non-trivial, and it is also exploitable/observable as a griefing vector against relayers who construct `DeleteAccountAction`s on behalf of users without validating the beneficiary first.

### Recommendation
Add an existence check for `beneficiary_id` (or apply the same "eligible for implicit account creation" rule) at `DeleteAccount` action-execution time, rejecting the action outright (before deleting the account and destroying its state) if the beneficiary cannot actually receive the refund. Alternatively, route the failed refund back to the account's `predecessor_id`/`signer_id` (similar to the `refund_to` mechanism already used for gas/deposit refunds) instead of unconditionally burning it, so that value is never destroyed purely because of an invalid single-field recipient.

### Proof of Concept
1. Attacker/user account `alice.near` holds balance `B > 0` and no locked stake.
2. `alice.near` signs a transaction with a single `DeleteAccountAction { beneficiary_id: "definitely-not-an-existing-account.near" }` (syntactically valid, but never created, and not implicit-account-eligible).
3. Runtime executes `action_delete_account`: it removes `alice.near` from state and emits a `Receipt::new_balance_refund("definitely-not-an-existing-account.near", B)` with `predecessor_id = "system"`. [2](#0-1) 
4. On the next apply pass, the runtime processes that refund receipt: `check_account_existence` sees no account for the `Transfer` action and, since the target is not implicit-eligible, returns `ActionErrorKind::AccountDoesNotExist`. [5](#0-4) 
5. Because `receipt.predecessor_id()` is `"system"` and `result.result.is_err()`, the runtime adds the entire deposit `B` to `stats.balance.other_burnt_amount` instead of refunding it to anyone. [7](#0-6) 
6. Result: `alice.near`'s entire balance `B` is permanently destroyed (removed from total supply) with no recipient ever receiving it, and no way to recover it after the fact.

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}
