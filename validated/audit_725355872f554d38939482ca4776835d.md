### Title
`liquidity_cap` on `TokenConfig` is validated at registration but never enforced during PRC20 minting, allowing unbounded unauthorized PRC20 mint via ordinary inbound deposits - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/handler.go`, `x/uregistry/types/token_config.go`)

### Summary
The external report's bug class is "a declared/expected economic guard (5%-of-treasury threshold) is enforced on one code path but silently absent for a functionally equivalent path, letting an attacker route through the ungated path to exceed the intended cap." The Push Chain analog: `TokenConfig.LiquidityCap` is a mandatory, validated field on every registered token (`x/uregistry/types/token_config.go:56-58`), clearly intended as a per-token mint ceiling for the PRC20 representation of a bridged asset. However, across the entire inbound-execution/minting path (`depositPRC20` in `x/uexecutor/keeper/handler.go`, `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` in `x/uexecutor/keeper/evm.go`, and all `ExecuteInbound*` keeper functions), the field is never read or checked. `grep` across `x/uexecutor/**` and `x/uregistry/keeper/**` returns zero matches for `LiquidityCap`, confirming the value is stored but functionally dead.

### Finding Description
Every FUNDS / FUNDS_AND_PAYLOAD / GAS_AND_PAYLOAD inbound that passes ballot finalization is executed via `depositPRC20` (`x/uexecutor/keeper/handler.go:12-46`), which looks up the `TokenConfig` purely to resolve `NativeRepresentation.ContractAddress`, then calls `k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)` with the inbound's raw `Amount` — a value entirely controlled by the external-chain event that an unprivileged user creates by depositing into the gateway contract on the source chain. `CallPRC20Deposit` (`x/uexecutor/keeper/evm.go:262-303`) mints the PRC20 unconditionally via `depositPRC20Token` on `UniversalCore`, with no reference to `tokenConfig.LiquidityCap` anywhere in the call chain.

`ValidateForExecution` (`x/uexecutor/types/inbound.go:126-175`), the sole per-inbound validation gate run after ballot finalization, checks only that the amount is a non-negative parseable `uint256` and non-zero for the relevant tx types — it has no notion of the registry's configured liquidity cap. The cap is validated for *presence* (non-empty string) at token-registration time (`ValidateBasic`, `x/uregistry/types/token_config.go:56-58`), which confirms the field is meant to carry semantic meaning, but nothing in the runtime enforces it as an upper bound on cumulative or per-tx minted supply for that token.

This mirrors the reported pattern exactly: a documented economic guard (5% treasury threshold / liquidity cap) exists in the type/schema and is validated at the configuration layer, but the actual value-moving execution path (`stewardSpend` / PRC20 deposit-mint) never consults it, so an unprivileged party can drive unbounded value creation through the normal, honest-validator-approved flow.

### Impact Explanation
Because bridging/minting on Push Chain is driven purely by external-chain deposit events voted in via `MsgVoteInbound` (ordinary users, no privileged action needed), and the mint amount is never bounded against `LiquidityCap`, an attacker can deposit (or cause deposits of) any external-chain amount and have the corresponding PRC20 minted 1:1 with no ceiling. This directly corrupts PRC20/native asset accounting (an "unauthorized mint" per the allowed-impact gate) relative to the registry's own configured liquidity ceiling for that token, and can be used to mint PRC20 supply far beyond what the corresponding locked/backing liquidity on the source chain or the protocol's own risk model assumes — undermining any downstream logic (swap pricing, gas-refund swaps via `CallPRC20DepositAutoSwap`, quoter-based accounting) that implicitly relies on the cap being respected.

### Likelihood Explanation
High reachability, low complexity: any unprivileged user can trigger this simply by depositing an arbitrarily large amount on a supported external chain and having honest Universal Validators observe and vote the inbound normally (2/3 quorum, no malicious validator assumption required). No admin or governance action is needed to trigger the mint — the missing check is purely on the Push Chain execution side.

### Recommendation
Add an explicit liquidity-cap enforcement step in the deposit/mint path before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` (e.g., in `depositPRC20` in `x/uexecutor/keeper/handler.go` or inside `ValidateForExecution`/a new pre-execution check): track cumulative minted supply per PRC20 (or query the PRC20 contract's `totalSupply`), compare `currentSupply + inboundAmount` against `tokenConfig.LiquidityCap`, and reject/queue-for-revert any inbound that would exceed it, mirroring how the reported fix aggregated spend amounts against the treasury balance before allowing execution.

### Proof of Concept
Not executed against a live devnet in this analysis (no filesystem/terminal access in ask-only mode). The reasoning is based on static code review:
1. `x/uregistry/types/token_config.go:56-58` — `LiquidityCap` is required non-empty at registration.
2. `x/uexecutor/keeper/handler.go:12-46` (`depositPRC20`) — resolves `NativeRepresentation.ContractAddress` from `TokenConfig` but never reads `LiquidityCap`.
3. `x/uexecutor/keeper/evm.go:262-303` (`CallPRC20Deposit`) — mints `amount` unconditionally via `depositPRC20Token`.
4. `x/uexecutor/types/inbound.go:126-175` (`ValidateForExecution`) — validates amount is a positive uint256, but has no cap check.
5. Confirmed via repo-wide `grep` that `LiquidityCap`/`liquidity_cap` never appears in `x/uexecutor/**` or `x/uregistry/keeper/**` outside protobuf/test files.

A concrete on-chain PoC would require submitting an `Inbound` (via `MsgVoteInbound` reaching quorum) with `Amount` set far above the token's configured `LiquidityCap` and observing that `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload` successfully mints the full amount with no rejection — this should be verified in a Devin session with access to the test harness (`test/integration/uexecutor/`) to confirm no other layer (e.g., an EVM-side cap in the `UniversalCore`/PRC20 contract itself, which is out of this repo's Go code and not indexed here) silently enforces the cap. That contract-side possibility is the main uncertainty in this finding, since the actual `UniversalCore`/PRC20 Solidity contracts are not part of this indexed repository and could not be inspected.
