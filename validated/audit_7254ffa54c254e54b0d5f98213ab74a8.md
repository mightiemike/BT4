### Title
Unbounded `PendingInbounds.Walk` scan on every ballot termination enables attacker-triggered O(n) / O(n²) DoS in inbound finalization - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
`afterInboundBallotTerminal` locates the `PendingInboundEntry` owning a terminating ballot by performing a **full linear scan (`Walk`) over the entire `PendingInbounds` collection** on every single inbound ballot termination (PASSED/REJECTED/EXPIRED), rather than looking it up directly. The size of `PendingInbounds` is driven by the number of distinct, concurrently in-flight source-chain inbound events, which any unprivileged user can inflate cheaply (e.g., dust bridge deposits on external chains), turning ordinary ballot finalization into an increasingly expensive, unbounded-scan operation — directly analogous to the reported `getAvailableReward` pattern of looping over an attacker-growable range with no upper bound check.

### Finding Description
`PendingInboundEntry` records are created by `RecordInboundVote` (`x/uexecutor/keeper/inbound.go:27-88`) the first time any Universal Validator (UV) observes a source-chain inbound event, keyed by `utx_key = sha256(source_chain:tx_hash:log_index)` [1](#0-0) . Because `utx_key` is derived from the source event itself, any unprivileged user can create arbitrarily many distinct `PendingInboundEntry` records by submitting many low-value/dust transfers on supported external chains — honest UVs will faithfully observe and vote on each one via the gasless `MsgVoteInbound` [2](#0-1) .

When any one of these ballots reaches a terminal state, `x/uvalidator`'s ballot machine invokes `BallotHooks.AfterBallotTerminal`, which for `INBOUND_TX` ballots calls `afterInboundBallotTerminal` [3](#0-2) . This function does **not** use a direct index lookup; instead it walks and deserializes every single entry currently in `PendingInbounds` looking for the one variant whose `BallotId` matches:

```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [4](#0-3) 

There is no index from `ballotID -> utxKey`; the code comment even acknowledges the design assumption that "the pending set is small and transient" [5](#0-4) . That assumption is not enforced anywhere — there is no cap on the number of concurrently pending inbound entries, and no code path bounds the walk. This mirrors exactly the reported bug class: a loop/scan whose cost is proportional to an attacker-influenced counter (`currentAvailableRewardPeriod` in the original report vs. the size of `PendingInbounds` here) with no guard to bound the work performed.

This hook fires synchronously inside the message-handling path for `MsgVoteInbound` (a gasless message type per `app/txpolicy/gasless.go`), meaning the cost of the scan is incurred deterministically by every validating node processing the block, and — because the message is gasless — is not necessarily bounded by fee-based gas metering in the way an ordinary paid transaction would be.

### Impact Explanation
As an attacker inflates the number of concurrently open `PendingInbounds` entries (cheap dust deposits across supported external chains, submitted in bursts so many inbounds are in-flight simultaneously), each individual ballot termination triggers an O(n) full-collection walk with deserialization. With `k` concurrently pending inbounds terminating around the same time, the aggregate cost across all terminations approaches O(n²). This can degrade block processing performance for every node validating `MsgVoteInbound`/ballot-terminal transitions, and in the worst case exhausts available gas/compute for that message, causing repeated failures of legitimate inbound finalization (denial of service against honest users' bridging operations) — a state-safety/DoS impact reachable purely by unprivileged, ordinary user deposit activity, consistent with the "denial of service...reachable without privileged control" impact category in scope.

### Likelihood Explanation
Medium. Triggering many concurrent inbound observations requires the attacker to fund real (if small/dust) transfers on external chains, which has non-trivial but low real-world cost, and requires honest UVs to actually observe and vote on them (no malicious validator assumption needed — this is the ordinary happy path). The attack does not require any privileged role, key compromise, or malicious validator collusion; it only requires volume of cheap external-chain transactions timed to overlap so many `PendingInbounds` entries coexist when ballots start terminating.

### Recommendation
Replace the O(n) `Walk`-based lookup with a direct index: maintain a secondary collection (`ballotID -> utxKey`) populated in `RecordInboundVote` when each variant/ballot is created, and consulted directly in `afterInboundBallotTerminal` instead of scanning all of `PendingInbounds`. This removes the unbounded-scan dependency on the size of the pending set, analogous to bounding the loop to the known valid range in the original `getAvailableReward` fix recommendation. As a secondary/defense-in-depth measure, consider capping the number of concurrently open `PendingInboundEntry` records or the maximum number of variants scanned per hook invocation.

### Proof of Concept
1. Attacker submits N distinct dust-value deposits on N different (source_chain, tx_hash, log_index) tuples across supported external chains within a short window, so all N produce independent `PendingInboundEntry` records via `RecordInboundVote`.
2. Honest UVs independently observe and vote on each of the N inbounds via gasless `MsgVoteInbound`.
3. As ballots reach quorum/expiry roughly concurrently, each of the N `AfterBallotTerminal` calls triggers a full `PendingInbounds.Walk` over all N (or up to N) still-pending entries, deserializing each `PendingInboundEntry` and its `Variants` — yielding roughly O(N²) total deserialization/comparison work concentrated in the blocks processing these terminations.
4. Increasing N (bounded only by the attacker's willingness to pay dust amounts on external chains) increases the per-terminal-transition cost linearly and the aggregate cost quadratically, with no code-level bound — demonstrating the same "unbounded loop over an attacker/user-growable range" root cause as the reported `getAvailableReward` issue.

Note: I was unable to fully verify from the indexed code whether `MsgVoteInbound`'s "gasless" designation in `app/txpolicy/gasless.go` also exempts it from standard Cosmos SDK block-gas-meter enforcement (vs. only fee deduction) — this affects whether the practical failure mode is "OOG revert of the finalizing transaction" or "elevated but gas-metered cost." I recommend a Devin session with full repository access (including `app/ante/` and `x/uexecutor/keeper/msg_server.go` in full) to confirm the exact gas-metering behavior of gasless messages and to size the real-world N required to cause material degradation before filing a severity-final report.

func (k Keeper) RecordInboundVote(
	ctx context.Context,
	inbound types.Inbound,
	voter string,
	ballotID string,
) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	height := uint64(sdkCtx.BlockHeight())
	utxKey := types.GetInboundUniversalTxKey(inbound)

	entry, err := k.PendingInbounds.Get(ctx, utxKey)
	if err != nil && !errors.Is(err, collections.ErrNotFound) {
		return err
	}
	if errors.Is(err, collections.ErrNotFound) {
		entry = types.PendingInboundEntry{
			UtxKey:          utxKey,
			CreatedAtHeight: height,
		}
	}

func (h BallotHooks) AfterBallotTerminal(
	ctx sdk.Context,
	ballotID string,
	ballotType uvalidatortypes.BallotObservationType,
	status uvalidatortypes.BallotStatus,
) error {
	switch ballotType {
	case uvalidatortypes.BallotObservationType_BALLOT_OBSERVATION_TYPE_INBOUND_TX:
		return h.afterInboundBallotTerminal(ctx, ballotID, status)
	default:
		// OUTBOUND_TX, TSS_KEY, FUND_MIGRATION — not handled here.
		// See doc comment on BallotHooks for rationale on outbound.

	}
}
