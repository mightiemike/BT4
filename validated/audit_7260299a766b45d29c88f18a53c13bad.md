## Title
Off-by-one boundary check in locked delegated resource expiration causes valid `UnDelegateResourceContract` transactions to be rejected exactly at the lock expiration timestamp - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The report's bug class ("time-ended" boundary check using strict `<` instead of `<=`, causing a resource to not be recognized as "expired" exactly at its end time) has a concrete analog in java-tron's locked-resource-delegation feature. Both `DelegatedResourceStore.unLockExpireResource` and `UnDelegateResourceActuator.validate()` treat a locked delegated resource as still-locked when `expireTime == now`, instead of treating equality as expired, unlike every other freeze/unfreeze expiration check in the codebase (which consistently use `<=`/`>` at the equality point to treat "now == expire" as expired).

### Finding Description
When a user locks delegated resources via `DelegateResourceActuator` with `lock = true`, the lock's `expireTime` is computed as an exact multiple of `BLOCK_PRODUCED_INTERVAL` from the block timestamp: [1](#0-0) 

Because TRON block timestamps increment in fixed `BLOCK_PRODUCED_INTERVAL` steps, `expireTime` will land exactly on a future block's `LatestBlockHeaderTimestamp` — this is a routine occurrence, not a rare edge case.

When the owner later calls `UnDelegateResourceContract` to reclaim the locked resource, `validate()` only counts the locked balance as available if the lock is *strictly* expired: [2](#0-1) 

The same strict `<` boundary is used in the execution-path helper that actually migrates locked balance to unlocked balance: [3](#0-2) [4](#0-3) 

This contradicts the convention used everywhere else in the resource-freeze subsystem, where "now == expireTime" is explicitly treated as expired (e.g. `frozen.getExpireTime() <= now`, `unfrozenV2.getUnfreezeExpireTime() <= now`): [5](#0-4) [6](#0-5) 

### Impact Explanation
At the block whose timestamp exactly equals the previously-computed lock `expireTime`, a legitimate `UnDelegateResourceContract` transaction that should succeed (the lock period has fully elapsed) is instead rejected with `insufficient delegatedFrozenBalance(BANDWIDTH/Energy)`, because the locked balance is not counted. This is a functional/availability defect: a user's otherwise valid, correctly-formed broadcast transaction fails deterministically at a predictable block, forcing a retry on the next block. It does not cause consensus divergence (all full nodes evaluate the same deterministic boundary identically) and does not lead to fund loss — the balance becomes unlockable one block later — but it is a genuine incorrect-timing defect reachable directly from a normal user-broadcast transaction, matching the reported bug class.

### Likelihood Explanation
Because `expireTime` is always calculated as an exact multiple of the fixed block-production interval from a past block's timestamp, hitting the exact boundary is a deterministic, easily-triggerable condition (any user submitting an unDelegate transaction in the exact block matching their lock's `expireTime` will hit it), not a rare probabilistic occurrence.

### Recommendation
Change the comparisons in `DelegatedResourceStore.unLockExpireResource` and `UnDelegateResourceActuator.validate()`/`execute()` from strict `<` to `<=` for `expireTimeForBandwidth`/`expireTimeForEnergy` versus `now`, consistent with the `<=` convention used by `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `WithdrawExpireUnfreezeActuator` elsewhere in the codebase.

### Proof of Concept
1. Call `DelegateResourceContract` with `lock = true` and `lockPeriod = N`; this sets `expireTime = now + N * BLOCK_PRODUCED_INTERVAL` on the locked `DelegatedResourceCapsule` (see `DelegateResourceActuator.delegateResource`, lines 291-298).
2. Wait until the chain's `LatestBlockHeaderTimestamp` equals exactly that `expireTime` (guaranteed to occur since block timestamps advance in fixed `BLOCK_PRODUCED_INTERVAL` increments).
3. Broadcast an `UnDelegateResourceContract` from the same owner/receiver pair for the full locked balance at that exact block.
4. Observe `ContractValidateException`: `"insufficient delegatedFrozenBalance(BANDWIDTH), request=X, unlock_balance=0"` (or ENERGY equivalent), because `lockResourceCapsule.getExpireTimeForBandwidth() < now` evaluates to `false` when they are equal, per `UnDelegateResourceActuator.java` lines 275-278/291-294.
5. Retrying the identical transaction one block later (when `now` strictly exceeds `expireTime`) succeeds, confirming the timing off-by-one.
