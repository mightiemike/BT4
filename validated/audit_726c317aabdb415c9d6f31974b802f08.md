## Analysis

The GMX report describes a comment that assumes a bound ("~7% max") holds without an enforced check, so the assumption silently breaks in edge cases. The closest reachable nearcore analog is the `DeterministicStateInit`/state-init entry-count bound used in congestion-gas accounting, described explicitly as unenforced-until-PV87 in `core/parameters/res/runtime_configs/87.yaml`.

`validate_number_of_state_init_entries` in `runtime/runtime/src/action_validation.rs` only rejects a receipt if the *total* number of state-init entries across all its actions exceeds `max_state_init_entries` [1](#0-0) . Before protocol version 87 this configuration value is effectively unbounded (`4294967295`, i.e. `u32::MAX`), so the check is a no-op for any transaction a signer can actually construct. The PV-87 config diff explains exactly why this matters: each entry costs `..._state_init_per_entry` (200 Ggas) to execute, "and that lands in the receipt's congestion gas whether or not it is burnt, so an uncapped count lets one receipt reserve several times `max_congestion_outgoing_gas` (10 PGas) and pin its own shard at full outgoing congestion" [2](#0-1) . It also explicitly notes that the contract-created path is already implicitly bounded (by `max_total_prepaid_gas` / 200 Ggas ≈ 1,500 entries) but that this new cap is only now being introduced to bring the transaction-created path into agreement, which means prior to PV87 the transaction-created path had no equivalent gas-budget bound.

The protocol-model documentation for this tree states the currently stable/active protocol version is 86, with mainnet only scheduled to vote PV86 (not 87) — i.e., the PV-87 fix described above is not yet live on the network modeled by this tree [3](#0-2) . `CongestionControlConfig.max_congestion_outgoing_gas` is the 10 PGas whole-shard cap referenced by the comment [4](#0-3) .

### Title
Unbounded `DeterministicStateInit`/`UniversalStateInit` entry count lets a single transaction blow past the whole-shard outgoing-congestion cap - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
Prior to the PV-87 fix, `max_state_init_entries` is effectively unbounded, so `validate_number_of_state_init_entries` never rejects a state-init action with a very large number of entries. Each entry is unconditionally counted into the receipt's congestion gas (independent of what's actually burnt), letting a normal, single, signed transaction reserve many times the shard's entire `max_congestion_outgoing_gas` budget.

### Finding Description
`validate_number_of_state_init_entries` sums `Action::num_state_init_entries` across the actions of a receipt and compares against `max_state_init_entries`, rejecting only if that count exceeds the limit [5](#0-4) . On this tree's stable/active protocol version, `max_state_init_entries` is the pre-PV87 default of `u32::MAX`, so the check imposes no real bound. The number-of-entries value is used to compute congestion gas contributed by the receipt via the per-entry state-init execution cost (200 Ggas/entry per the PV-87 changelog), and that congestion-gas contribution is added "whether or not it is burnt" [6](#0-5) . The fix that caps this at 1,500 entries — chosen specifically to keep a single receipt's congestion-gas reservation to roughly 3% of the 10 PGas outgoing cap — is not yet active given the stable protocol version reported for this tree [3](#0-2) . This is directly analogous to the GMX report: an implicit numeric assumption ("a receipt can't carry enough entries to matter") is relied upon by the congestion-control system but is not enforced by any explicit runtime check at the currently active protocol version.

### Impact Explanation
A shard driven to full outgoing congestion grants `Gas::ZERO` to all senders except its `allowed_shard` [7](#0-6) . An attacker who can pin a shard's outgoing congestion at 100% (or several multiples of the cap) can stall cross-shard receipt forwarding out of that shard for all other shards, a transaction-triggered denial of service against normal chain operation. This satisfies the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Medium-to-High: this requires only a single signed transaction from any unprivileged account containing a `DeterministicStateInit`/`UniversalStateInit` action with a very large number of small entries, packed to fit within `max_transaction_size`/`max_receipt_size`. No special privileges, validator status, or network position are needed — this is directly reachable by any transaction signer, matching the allowed reachable-path list (transaction/action validation, congestion control).

### Recommendation
Confirm the actual `max_state_init_entries` value in force on the target network's currently active protocol version. If it is still the unbounded default (pre-PV87), backport or accelerate activation of the PV-87 cap (1,500 entries) so the entry-count bound is enforced by `validate_number_of_state_init_entries` regardless of protocol version, rather than relying on a config value that is only tightened in a not-yet-active future protocol version.

### Proof of Concept
Not independently executed; based on static analysis only. Conceptually: construct a `SignedTransaction` with a single `DeterministicStateInit`/`UniversalStateInit` action whose `data: BTreeMap<Vec<u8>, Vec<u8>>` contains tens of thousands of minimal (1-2 byte key, empty value) entries, sized to approach `max_transaction_size`/`max_receipt_size`. At the pre-PV87 `max_state_init_entries` default, `validate_number_of_state_init_entries` accepts it; `compute_receipt_congestion_gas` then reserves `entries * 200 Ggas` of congestion gas for the receipt, which for tens of thousands of entries exceeds `max_congestion_outgoing_gas` (10 PGas) many times over, per the analysis captured in the PV-87 changelog comment.

**Note on uncertainty**: I could not directly confirm within available tool calls (a) the exact current numeric value of `max_state_init_entries` baked into `parameters.yaml` (the merged/cumulative current config) versus the per-version diff file `87.yaml`, since `parameters.yaml` also had matches for this parameter that I did not read in full, and (b) whether an independent protocol-feature gate (separate from the raw config value) already restricts this path before PV87. These would need direct verification in a full session before treating this as production-confirmed rather than a well-supported analog.

```rust
/// Bound the number of storage entries the state-init actions in one receipt
/// carry, in total. Each entry adds to the receipt's congestion gas, regardless if
/// it is ever burnt, so an unbounded count could congest the shard.
///
/// The bound is on the total and not per action, because a receipt can carry many
/// byte-identical copies of a state init, making per-action bound ineffective.
fn validate_number_of_state_init_entries(
    actions: &[Action],
    max_state_init_entries: u64,
) -> Result<(), ActionsValidationError> {
    let number_of_entries =
        actions.iter().map(Action::num_state_init_entries).fold(0u64, u64::saturating_add);

    if number_of_entries > max_state_init_entries {
        return Err(ActionsValidationError::TotalNumberOfStateInitEntriesExceeded {
            number_of_entries,
            limit: max_state_init_entries,
        });
    }

    Ok(())
}
```
