### Title
Uncontrolled decompression of user-supplied Cairo0 `compressed_program` causes memory-exhaustion DoS - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The JSON-RPC layer that accepts declare transactions with a deprecated (Cairo0) contract class decompresses the attacker-supplied gzip `compressed_program` field with no size cap before parsing it as JSON, unlike every other decompression path in the codebase which explicitly enforces a byte-limit before or during decompression.

### Finding Description
`decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs:671-682` base64-decodes an untrusted string and feeds it into `flate2::bufread::GzDecoder`, then calls `decoder.read_to_end(&mut decompressed)` with **no upper bound** on the output size: [1](#0-0) 

The `// TODO(dan): add time and size limits.` comment on the line immediately preceding the unbounded read confirms the missing guard is a known gap rather than an intentional design choice.

This function is invoked from `user_deprecated_contract_class_to_sn_api`, which converts a client-broadcast `BroadcastedDeclareV1Transaction`'s legacy `DeprecatedContractClass.compressed_program` field into the internal `starknet_api::deprecated_contract_class::ContractClass.program`: [2](#0-1) 

Because a Cairo0 declare transaction (`starknet_addDeclareTransaction` with a v1 `BROADCASTED_DECLARE_TXN`) is submitted by an unprivileged, unauthenticated caller, the attacker fully controls the compressed bytes. Every other gzip-decompression call site in this codebase explicitly bounds the inflated size before or during decompression:
- `decompress_with_size_limit` / `decode_and_decompress_with_size_limit` in `crates/starknet_api/src/compression_utils.rs:32-57` caps the decompressed length via `.take(max_size + 1)`.
- The deprecated HTTP-gateway Sierra path uses the same size-limited helper: `crates/apollo_http_server/src/deprecated_gateway_transaction.rs:289-301`.
- The p2p protobuf Cairo0 class converter enforces `MAX_CAIRO0_PROGRAM_SIZE` (4 MB) via `decode_and_decompress_with_size_limit`: `crates/apollo_protobuf/src/converters/class.rs:131-137`.

`decompress_program` is the sole exception: it has no cap on the decompressed size and no cap on the compression ratio, matching the CWE-400/CWE-409 decompression-bomb bug class described in the external advisory (unbounded ZIP/gzip inflation from an attacker-supplied file with no validation prior to full decompression).

### Impact Explanation
A small, highly-compressible gzip payload (a "decompression bomb") can inflate to gigabytes of memory during `read_to_end`, before any size or JSON-validity check occurs. Submitting such a v1 declare transaction to the RPC node's `starknet_addDeclareTransaction` (or any code path that exercises `user_deprecated_contract_class_to_sn_api`, e.g. simulate/estimate-fee flows for deprecated declare transactions) can exhaust the process's memory, causing the node to crash or become unresponsive — an availability-only denial-of-service impact, consistent with the referenced advisory's CVSS vector (`C:N/I:N/A:H`).

### Likelihood Explanation
High. No authentication, stake, or special privileges are required — any external caller of the RPC endpoint can submit a v1 declare transaction with a crafted `compressed_program`. Gzip decompression bombs are trivial and cheap to construct (a few KB of input can expand to GBs), and the vulnerable function performs no pre-inflation size check, unlike the size-limited variant used everywhere else in the same codebase.

### Recommendation
Replace the unbounded `decoder.read_to_end(&mut decompressed)` in `decompress_program` with the existing size-limited pattern already used elsewhere in the repo — e.g., wrap the `GzDecoder` with `.take(max_size + 1)` and reject the transaction if the decompressed length exceeds a configured cap (mirroring `decompress_with_size_limit` in `crates/starknet_api/src/compression_utils.rs`), before attempting `serde_json::from_reader`.

### Proof of Concept
1. Construct a gzip stream whose compressed size is small (e.g., a few KB, satisfying any outer request-body size limit) but whose decompressed content is many GB (a classic zip/gzip "quine"-style bomb, or simply gzip-compressing a huge repeated-byte buffer).
2. Base64-encode it and place it as the `program` field of a `DEPRECATED_CONTRACT_CLASS` inside a `BROADCASTED_DECLARE_TXN` (version 1) sent to the `starknet_addDeclareTransaction` RPC method (or any RPC call that routes through `user_deprecated_contract_class_to_sn_api`, e.g. simulate/estimate-fee with a legacy declare transaction).
3. `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) will call `GzDecoder::read_to_end` with no bound, driving the node's memory usage up to the fully-inflated size and causing an out-of-memory crash or severe resource exhaustion, before any JSON parsing or contract-class validation occurs.

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}
