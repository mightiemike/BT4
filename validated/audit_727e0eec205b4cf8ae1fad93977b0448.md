Based on my investigation, I found a genuine analog to the CVE's bug class in the gateway's transaction validation flow.

### Title
Signature Validation Skip for Invoke Transactions Trusts Mempool Presence Instead of Verifying Sender Authorization - (File: crates/apollo_gateway/src/stateful_transaction_validator.rs)

### Summary
CVE-2021-41100 is fundamentally a bug class where a weaker-trust credential/check (short-lived token) is used to authorize a sensitive action that should require a stronger-trust credential (long-lived token), enabling an attacker to bypass real authentication and take an unauthorized account action. The sequencer's `skip_stateful_validations` / `should_run_stateful_validations` logic contains the same class of bug: it substitutes a weak, unauthenticated precondition ("is there *any* transaction for this sender address already in the mempool or a recent block?") for the actual authorization check (`__validate__` signature verification), and uses that weak check to bypass signature validation for an `Invoke` transaction.

### Finding Description
In the gateway's stateful validation pipeline, `run_pre_validation_checks` calls `skip_stateful_validations`, which determines whether the mandatory `__validate__` entry point execution should be skipped for an `Invoke` transaction: [1](#0-0) 

The check only verifies `tx.nonce() == 1` and `account_nonce == 0`, then asks the mempool whether *any* transaction exists for `tx.sender_address()` — it does not verify that the specific invoke transaction being submitted is cryptographically tied to (or was authorized alongside) the deploy_account transaction that justifies the skip: [2](#0-1) 

The resulting `skip_validate` boolean flows into `extract_state_nonce_and_run_validations`, which conditionally skips `run_validate_entry_point` (the actual account-contract signature check) based on this weak proxy check: [3](#0-2) 

The equivalent logic also exists in the native blockifier validator path (`PyValidator::should_run_stateful_validations`), where `skip_validate` is derived purely from nonce/deploy-account-hash presence, not from any cryptographic binding between the invoke tx and the deploy_account tx: [4](#0-3) 

Because any address whose `deploy_account` transaction is currently pending in the (public) mempool — or was recently included in a block, i.e., is visible in a "recent block" — satisfies `account_tx_in_pool_or_recent_block`, any external submitter can craft a garbage/unsigned `Invoke` transaction with `nonce = 1` targeting that same `sender_address` and calldata of their choosing. Because `skip_validate` will be `true`, the gateway's `run_validate_entry_point` (the mechanism analogous to the "long-lived token" / real signature check) is bypassed entirely for that transaction, allowing it to be admitted to the mempool without the account owner ever authorizing its specific calldata.

### Impact Explanation
If the sender's account's `__validate__`/`__validate_deploy__` in the deploy_account transaction is legitimate but the follow-up invoke's contents were never actually signed/authorized by the account owner, an attacker observing a pending `deploy_account` transaction in the mempool can inject a spoofed follow-up `Invoke` transaction for the same account (e.g., transferring funds, calling `__execute__` with attacker-chosen calldata) that skips the account-contract's genuine `__validate__` check. This is an unauthorized account action analogous to the CVE's account-takeover primitive: a lower-assurance check is substituted for the real authorization gate, and the sequencer executes attacker-controlled calldata under a victim's account context without their signature.

### Likelihood Explanation
Reachable directly by any unprivileged transaction sender: the attacker only needs to observe a pending or recently-included `deploy_account` transaction for a target address in the public mempool (deploy_account+invoke bundling is a documented, common UX pattern) and then submit their own conflicting `Invoke` with `nonce=1` before the legitimate follow-up invoke is processed, exploiting the race/skip-validate window purely from the gateway/mempool layer.

### Recommendation
Do not use mere presence of an unrelated transaction in the mempool/recent block as sufficient authorization to skip `__validate__`. Bind the skip-validation decision to the specific accompanying transaction bundle (e.g., require the invoke tx hash to be explicitly paired with the deploy_account tx hash that the submitter provided, as is partially done via `deploy_account_tx_hash` in `PyValidator`, and enforce that pairing strictly rather than falling back to a generic address-presence check in `skip_stateful_validations`). At minimum, ensure only the first invoke transaction that is bundled/submitted together with its corresponding deploy_account transaction (via a verified hash reference) can bypass `__validate__`, and reject any other nonce-1 invoke for an undeployed account that isn't explicitly tied to that specific deploy.

### Proof of Concept
1. Victim submits a legitimate `DeployAccount` tx for address `A` (visible in mempool) intending to follow it with an authorized `Invoke` (nonce=1).
2. Attacker observes the pending `DeployAccount` for `A` and immediately submits their own crafted `Invoke` transaction with `sender_address = A`, `nonce = 1`, and attacker-chosen calldata (garbage/no valid signature).
3. Gateway's `skip_stateful_validations` sees `tx.nonce() == 1`, `account_nonce == 0`, and `mempool_client.account_tx_in_pool_or_recent_block(A) == true` (satisfied by the victim's pending deploy_account), returning `skip_validate = true`. [5](#0-4) 
4. `run_validate_entry_point` is skipped for the attacker's invoke, so it is admitted to the mempool and can be sequenced without ever passing the account contract's genuine `__validate__` signature check.

/// Check if validation of an invoke transaction should be skipped due to deploy_account not being
/// processed yet. This feature is used to improve UX for users sending deploy_account + invoke at
/// once.
async fn skip_stateful_validations(
    tx: &ExecutableTransaction,
    account_nonce: Nonce,
    mempool_client: SharedMempoolClient,
) -> StatefulTransactionValidatorResult<bool> {
    if let ExecutableTransaction::Invoke(ExecutableInvokeTransaction { tx, .. }) = tx {
        // check if the transaction nonce is 1, meaning it is post deploy_account, and the
        // account nonce is zero, meaning the account was not deployed yet.
        if tx.nonce() == Nonce(Felt::ONE) && account_nonce == Nonce(Felt::ZERO) {
            let account_address = tx.sender_address();
            debug!("Checking if deploy_account transaction exists for account {account_address}.");
            // We verify that a deploy_account transaction exists for this account. It is sufficient
            // to check if the account exists in the mempool since it means that either it has a
            // deploy_account transaction or transactions with future nonces that passed
            // validations.
            return mempool_client
                .account_tx_in_pool_or_recent_block(tx.sender_address())
                .await
                .map_err(|err| mempool_client_err_to_deprecated_gw_err(&tx.signature(), err))
                .inspect(|exists| {
                    if *exists {
                        debug!("Found deploy_account transaction for account {account_address}.");
                    } else {
                        debug!(
                            "No deploy_account transaction found for account {account_address}."
                        );
                    }
                });
        }

impl PyValidator {
    // Returns whether the transaction should be statefully validated.
    // If the DeployAccount transaction of the account was submitted but not processed yet, it
    // should be skipped for subsequent transactions for a better user experience. (they will
    // otherwise fail solely because the deploy account hasn't been processed yet).
    #[allow(clippy::result_large_err)]
    pub fn should_run_stateful_validations(
        &mut self,
        account_tx: &AccountTransaction,
        deploy_account_tx_hash: Option<TransactionHash>,
    ) -> StatefulValidatorResult<bool> {
        if account_tx.tx_type() != TransactionType::InvokeFunction {
            return Ok(true);
        }
        let tx_info = account_tx.create_tx_info();
        let nonce = self.stateful_validator.get_nonce(tx_info.sender_address())?;

        let deploy_account_not_processed =
            deploy_account_tx_hash.is_some() && nonce == Nonce(Felt::ZERO);
        let tx_nonce = tx_info.nonce();
        let is_post_deploy_nonce = Nonce(Felt::ONE) <= tx_nonce;
        let nonce_small_enough_to_qualify_for_validation_skip =
            tx_nonce <= self.max_nonce_for_validation_skip;

        let skip_validate = deploy_account_not_processed
            && is_post_deploy_nonce
            && nonce_small_enough_to_qualify_for_validation_skip;

        Ok(!skip_validate)
    }
