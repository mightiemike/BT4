### Title
Reward-set recipient matching in `LeaderBlockCommitOp::check_pox_pre_waterfall` uses a lossy address representation that conflates distinct hash-modes - (File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs)

### Summary
`to_burnchain_repr()` is used as the *sole* equality key when a leader block-commit's `commit_outs` are matched against the PoX contract's expected recipient set. This representation is built from `StacksAddress::version()` + `Hash160` only, but `AddressHashMode::to_version_mainnet/testnet` maps three distinct hash modes (`SerializeP2SH`, `SerializeP2WPKH`, `SerializeP2WSH`) to the identical multisig version byte. A stacker can register a PoX address under one hash mode (e.g. P2WSH) in the reward set, and a miner can satisfy the "must pay this recipient" check with a Bitcoin output whose `PoxAddress` decodes to a *different* hash mode but the same version+hash160 — an address the reward-set entry never actually specified, mirroring the `assetToken`/proxy-token bug where two distinct on-chain addresses are treated as interchangeable by an equality check that omits distinguishing metadata.

### Finding Description
The reward set stores `PoxAddress::Standard(StacksAddress, Some(AddressHashMode))`, where `AddressHashMode` is one of `SerializeP2PKH`, `SerializeP2SH`, `SerializeP2WPKH`, `SerializeP2WSH` (four semantically distinct Bitcoin output script types). When comparing block-commit outputs against the expected reward-set recipients, `check_pox_pre_waterfall` calls `self_commit.to_burnchain_repr()` and compares it string-wise against `check_commit.to_burnchain_repr()`: [3](#0-2) 

`to_burnchain_repr()` for `PoxAddress::Standard` only encodes `addr.version()` (the StacksAddress/C32 version byte) and `addr.bytes()` (the raw Hash160), explicitly dropping the `AddressHashMode`: [2](#0-1) 

But `AddressHashMode::to_version_mainnet`/`to_version_testnet` is not injective: `SerializeP2SH`, `SerializeP2WPKH`, and `SerializeP2WSH` all map to `C32_ADDRESS_VERSION_MAINNET_MULTISIG` (20) / `C32_ADDRESS_VERSION_TESTNET_MULTISIG` (21): [1](#0-0) 

Consequently, if a stacker registers a PoX address with hashbytes `H` and version byte `0x03` (`SerializeP2WSH`, a p2sh-wrapped p2wsh script) via `stack-stx`, the resulting `StacksAddress` inside the reward set has version 20/21 and hash160 `H`. `to_burnchain_repr()` for that entry is `"14-H"` (mainnet). A block-commit output whose `PoxAddress` was actually constructed as `SerializeP2SH` (a bare multisig redeem-script hash) or `SerializeP2WPKH` with the *same* hash160 `H` produces the identical `"14-H"` representation and is treated as an exact match by `check_pox_pre_waterfall`, even though it is a Bitcoin output paying a different script (P2SH vs. P2WSH-in-P2SH vs. P2WPKH-in-P2SH) than the one the stacker actually registered — exactly analogous to the `assetToken`/proxy-address collision in the reference finding, where an equality check on one identifier silently permits substitution by another address that is not truly equivalent.

This is an unprivileged, minority-triggerable divergence: any single miner constructing a `LeaderBlockCommitOp` chooses which hash mode/version encoding to use for `commit_outs`, and this is exactly the kind of "committed state a node reproduces differently" scenario the sortition/burn-operations validation is supposed to prevent from splitting nodes' interpretation of the burnchain.

### Impact Explanation
If different nodes' PoX/UTXO tooling decode the *same* Bitcoin scriptPubKey into different `AddressHashMode` variants (or if a miner deliberately crafts a payment using a hash-mode distinct from the one the stacker registered), the on-chain `check_pox_pre_waterfall` validation will accept it as satisfying the recipient, since the comparison is done purely on `to_burnchain_repr()`. This can cause: (1) reward payouts that Bitcoin-wallet software / stackers do not recognize as "their" address type, and (2) potential divergence between two nodes' independent reconstructions of `PoxAddress` from the same burnchain scriptPubKey if their address-classification heuristics differ, since `to_burnchain_repr()` erases the very information (`AddressHashMode`) that would disambiguate the two. This falls under "High – minority-triggerable... static-validation divergence... reward mis-payment bounded to fees" since the amount at stake is the block reward's PoX-portion, not chain-wide funds.

### Likelihood Explanation
Low-to-medium: it requires the reward-set entry's registered hash mode and the block-commit output's actual on-chain script type to differ while sharing the same hash160 and version-collapsed byte — a condition a miner (an unprivileged, unauthenticated participant that only needs to win/build a block-commit) fully controls when constructing `commit_outs`, without needing majority hash power or admin keys. The comment at `leader_block_commit.rs` acknowledges the design rationale ("hash mode…can't be used since it's not stored [on the burnchain]"), showing this collapsing is a known limitation rather than an accidental bug, which somewhat reduces the practical likelihood of an unnoticed divergence but does not eliminate the address-substitution risk.

### Recommendation
Where possible, avoid relying solely on the lossy `to_burnchain_repr()` (version + hash160) for recipient equality when hash-mode-sensitive script types are in play; incorporate the actual Bitcoin scriptPubKey bytes (which do differ between P2SH, P2WPKH-P2SH, and P2WSH-P2SH for the same hash160) as the canonical comparison key for block-commit output validation, similar to how `to_bitcoin_tx_out` already renders mode-specific scripts. This closes the "different underlying script, same collapsed representation" gap analogous to checking real transferred-balance deltas instead of a coarse address/version equality.

### Proof of Concept
1. A stacker calls `stack-stx` with a `pox-addr` tuple `{version: 0x03, hashbytes: H}` (`SerializeP2WSH`), producing a reward-set entry `PoxAddress::Standard(StacksAddress{version: 20, bytes: H}, Some(SerializeP2WSH))`.
2. A miner wins the sortition and constructs a block-commit whose actual Bitcoin output is a P2SH-multisig script (`SerializeP2SH`) hashing to the identical `H`; when decoded on the Stacks side this yields `PoxAddress::Standard(StacksAddress{version: 20, bytes: H}, Some(SerializeP2SH))`.
3. `check_pox_pre_waterfall` compares `self_commit.to_burnchain_repr()` == `"14-H"` against the expected recipient's `to_burnchain_repr()` == `"14-H"` — [4](#0-3)  — and the two are indistinguishable, so the miner's payment is accepted as satisfying the P2WSH stacker's recipient slot despite being a different script type on the underlying Bitcoin chain.
