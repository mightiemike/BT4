## Analysis

`object::owns` and `object::root_owner` implement conceptually the same "walk the ownership chain" logic, but with very different termination guarantees: [1](#0-0) 

`owns` bounds the walk with an explicit `count < MAXIMUM_OBJECT_NESTING` assertion and aborts (rather than mis-answering) if the chain doesn't resolve within 8 hops. [2](#0-1) 

`root_owner` has **no depth bound at all** — it loops `while (is_object(obj_owner))` until it hits a non-object address.

For this to actually diverge on mainnet, the ownership graph reachable from an `ObjectCore` chain must be able to become long enough (or cyclic) that the two functions behave differently. The critical question is whether an unprivileged actor can build such a graph.

### Where the depth cap is (and isn't) enforced

The only place `MAXIMUM_OBJECT_NESTING` is checked at the *write* path is `verify_ungated_and_descendant`, invoked from `transfer_to_object`/`transfer`: [3](#0-2) 

This function walks *up* from the transfer `destination` looking for the transferring `owner`, aborting past 8 hops. Critically, it validates the **pre-transfer** graph and never checks that the object being moved (`self`) does not itself appear as an ancestor of `destination`. After the check passes, the actual mutation (`object.owner = to`) is applied unconditionally elsewhere (see the analogous pattern in `transfer_with_ref`): [4](#0-3) 

Separately, `create_object`/`create_named_object` set `ObjectCore.owner` to an arbitrary caller-supplied address with **no existence or depth check whatsoever**: [5](#0-4) 

### Constructing a genuine cycle (not just a long chain)

Because `verify_ungated_and_descendant` only requires that walking up from `destination` reaches the *signer's* address (`owner`) within 8 hops — and does not exclude the object being transferred from that ancestor path — an unprivileged owner can:

1. Create `O1` and `O2`, both owned by `Alice` (`create_object`).
2. `transfer_to_object(Alice, O2, O1)` → `O2.owner = O1` (trivially passes the check, since `O1.owner == Alice`).
3. `transfer_to_object(Alice, O1, O2)` → check walks `O2.owner (O1) -> O1.owner (Alice)`, finds `Alice` at hop 2, **passes** — then sets `O1.owner = O2`.

Result: `O1.owner == O2` and `O2.owner == O1`, i.e., a genuine 2-cycle in the committed `ObjectCore` write-set chain, produced entirely through unprivileged, otherwise-valid framework entry functions.

### Divergence between `owns` and `root_owner` on this cyclic chain

- `owns(O1, Alice)` will loop around the cycle, incrementing `count` each hop, and safely **abort** with `EMAXIMUM_NESTING` once `count == 8` — a deterministic, bounded failure.
- `root_owner(O1)` has no such bound: since both `O1` and `O2` always satisfy `is_object(...) == true`, the `while (is_object(obj_owner))` loop **never terminates** (`obj_owner` oscillates between `O1` and `O2` forever).

For an on-chain transaction this would eventually be stopped by the VM's gas metering, but `root_owner` is a `#[view]` function, which is the exact class of "proof-bearing/authenticated API response" path called out in scope — full nodes and the API layer execute view functions to answer client queries about ownership at a specific ledger version. A view call that never returns is a functional failure of that authenticated response, and it is reachable purely from unprivileged transaction input (the two `transfer_to_object` calls) with no operator error involved.

## Title
Missing cycle exclusion in `verify_ungated_and_descendant` lets unprivileged users create cyclic `ObjectCore` ownership graphs, causing `root_owner`'s unbounded loop to never terminate - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`transfer_to_object`'s pre-transfer ancestor check (`verify_ungated_and_descendant`) does not exclude the object being moved from the destination's ancestor chain, allowing two ordinary `transfer_to_object` calls by a normal owner to create a 2-node ownership cycle in `ObjectCore`. `owns` handles this safely via an explicit depth cap and aborts; `root_owner` has no such cap and loops forever on the resulting cycle.

### Finding Description
`verify_ungated_and_descendant` (lines 608-639) only checks that the transferring `owner` is reachable within 8 hops from `destination`, prior to the transfer. It never checks that `destination`'s ancestor chain does not pass through the object being transferred itself. Combined with unconditional owner mutation (pattern shown in `transfer_with_ref`, lines 526-547) and the fact that object creation (`create_object_internal`, lines 329-350) never validates the owner address at all, an unprivileged user can sequence two transfers to make two objects mutually own each other, producing a cycle in the committed `ObjectCore` graph.

### Impact Explanation
Any subsequent `root_owner` view call on an object in the cycle will loop indefinitely, since `is_object` is always true for cycle members, unlike `owns`, which bails out deterministically via its `MAXIMUM_OBJECT_NESTING` cap. This corrupts the coherence guarantee between two supposedly-equivalent ownership queries served over the same committed state and can hang the view-function execution path used by authenticated API responses.

### Likelihood Explanation
Requires only two ordinary, self-authorized `transfer_to_object` calls by the object owner — no special privileges, no reliance on operator error.

### Recommendation
In `verify_ungated_and_descendant`, also reject the transfer if `destination`'s ancestor walk encounters the address of the object being transferred (`self`), preventing cycle formation; alternatively, add the same `MAXIMUM_OBJECT_NESTING` bound to `root_owner`'s loop so it fails closed like `owns` instead of looping unboundedly.

### Proof of Concept
1. `create_object(Alice)` → `O1` (owner `Alice`).
2. `create_object(Alice)` → `O2` (owner `Alice`).
3. `transfer_to_object(Alice, O2, O1)` → `O2.owner = O1`.
4. `transfer_to_object(Alice, O1, O2)` → passes ancestor check (`O2 -> O1 -> Alice`, 2 hops), sets `O1.owner = O2`.
5. Call `root_owner(O1)` → infinite loop; call `owns(O1, Alice)` → aborts with `EMAXIMUM_NESTING`.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
