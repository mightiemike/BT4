## Analysis

The reported bug class is a **missing-authorization check on a state-mutating, ID-driven action** (`stopDca` lets anyone act on another party's task because no ownership/correlation check gates the call). The equivalent, reachable pattern in this repository is the batch-prover's JSON-RPC surface: the RPC layer has a generic `Auth` middleware, but it only requires an API key for three specific method names, and every other RPC method — including several that mutate the prover's persistent job/commitment state — is completely unauthenticated.

### Root cause [1](#0-0) 

`PROTECTED_METHODS` only lists `backup_create`, `backup_validate`, `backup_info`; any other method name skips the API-key check entirely and is forwarded straight to the underlying service: [2](#0-1) 

The batch-prover exposes several methods that mutate persisted rollup-proving state and are not in that protected list:

- `batchProver_setCommitments` — overwrites/injects arbitrary `SequencerCommitment` records (merkle root, index, l2 end height) directly into the ledger DB and marks them pending for proving, with **no ownership or origin check** on the caller: [3](#0-2) 

- `batchProver_retryProvingJob` — takes only a `job_id` (obtainable via the equally unauthenticated `getProvingJobs`/`getProvingJobOfCommitment`), deletes the existing proving job from the ledger DB and re-queues its commitments, exactly mirroring the DCA pattern of "any caller supplies an ID and cancels/redirects someone else's active task, without proving they own it": [4](#0-3) 

- `pauseProving`, `submitFakeProof`, `createCircuitInput` are similarly declared with no authorization requirement: [5](#0-4) 

These methods are merged straight into the public RPC module tree that the node starts with `start_rpc_server`, whose only gate is the `Auth` layer shown above: [6](#0-5) 

### Title
Unauthenticated batch-prover JSON-RPC methods allow anyone to mutate proving state (`setCommitments`, `retryProvingJob`, etc.) - (File: crates/batch-prover/src/rpc.rs)

### Summary
The batch prover's JSON-RPC interface registers methods (`setCommitments`, `retryProvingJob`, `pauseProving`, `submitFakeProof`, `createCircuitInput`) that directly mutate the node's persisted proving/commitment state. The shared `Auth` RPC middleware only requires an API key for `backup_create`, `backup_validate`, and `backup_info`; every other method, including these, is reachable by any unauthenticated caller with network access to the RPC port.

### Finding Description
`Auth::call` in [2](#0-1)  forwards any request whose method name is not in the hard-coded `PROTECTED_METHODS` list without any credential check. The batch-prover RPC trait exposes multiple methods that were clearly intended for privileged/administrative use (overriding commitments, cancelling and re-queuing proving jobs, pausing the prover, forcing fake-proof submission) but none of them are added to that list, so they inherit no authentication whatsoever. This is directly analogous to `stopDca`: a caller supplies only an identifier (`job_id`, commitment `index`) and the callee performs a privileged state mutation without verifying the caller is authorized to act on that identifier.

### Impact Explanation
This falls squarely into the explicitly allowed High-impact category: "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`". Concretely:
- `retryProvingJob` lets any external party delete an in-flight proving job (`remove_proving_job_by_id`) and force re-queuing, disrupting the prover's ability to submit correct proofs on schedule.
- `setCommitments` lets any external party inject/overwrite `SequencerCommitment` entries in the ledger DB that the prover subsequently treats as the basis for `get_batch_proof_circuit_input_from_commitments`, corrupting the prover's local view of which commitments to prove.

### Likelihood Explanation
Likelihood is high: no authentication token, signature, or role check of any kind is required; the attacker only needs network reachability to the batch-prover's RPC endpoint, and the necessary `job_id`/commitment `index` values can be fetched from the equally-unauthenticated read-only endpoints (`getProvingJobs`, `getProvingJobOfCommitment`, `getCommitmentIndicesByL1`).

### Recommendation
- **Short term:** Add `batchProver_setCommitments`, `batchProver_retryProvingJob`, `batchProver_pauseProving`, `batchProver_submitFakeProof`, and `batchProver_createCircuitInput` (and any other state-mutating admin RPCs) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or move them to a separate, API-key-gated RPC module analogous to the backup RPC module.
- **Long term:** Invert the model — treat all RPC methods as protected by default and maintain an explicit allow-list of read-only/public methods, rather than an explicit deny-list of protected ones, to prevent this class of omission from recurring as new admin RPCs are added.

### Proof of Concept
1. Start a batch prover node with its RPC bound (no `api_key` needed for this class of method regardless of config, since the method names aren't in `PROTECTED_METHODS`).
2. As an unauthenticated third party, call `batchProver_getProvingJobs` to discover an active `job_id`.
3. Call `batchProver_retryProvingJob(job_id)` — the job is removed from the ledger DB and its commitments are re-queued under a new job id, without any credential being supplied, exactly as in the `stopDca` analog where any caller can halt another party's active task by ID alone.

    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>

    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,

    type Future = BoxFuture<'a, MethodResponse>;

        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {

            info!(

                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok

                .ledger_db

            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }

        Ok(())
    }

    async fn retry_proving_job(&self, job_id: Uuid) -> RpcResult<Uuid> {
        let ledger_db = &self.context.ledger_db;

        let mut commitment_indices = ledger_db
            .get_commitment_indices_by_job_id(job_id)
            .map_err(internal_rpc_error)?
            .ok_or_else(|| internal_rpc_error("Job ID not found"))?;
        commitment_indices.sort_unstable();

        ledger_db
            .remove_proving_job_by_id(job_id)
            .map_err(internal_rpc_error)?;

        for index in &commitment_indices {
            ledger_db
                .put_prover_pending_commitment(*index)
                .map_err(internal_rpc_error)?;
        }
        let _ = self.prove(PartitionMode::Normal).await?;

        let new_id = ledger_db
            .get_job_id_by_commitment_index(commitment_indices[0])
            .map_err(internal_rpc_error)?
            .ok_or_else(|| internal_rpc_error("New job ID not found"))?;

        info!("Retried proving job {}, new job id: {}", job_id, new_id);
        Ok(new_id)
    }
