## Title
Unbounded recursion in CASM bytecode hash computation over an untrusted, compiler-emitted segment tree can crash the gateway process (stack overflow) — ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
The reported `opcua` bug is a stack-overflow DoS caused by recursively deserializing/processing a self-referential message type (`ExtensionObject`/`Variant`) with no depth limit. The sequencer has an analogous unguarded recursion: `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recurses over a `NestedIntList`/`HashableNestedIntList` tree (`bytecode_segment_lengths`) with no depth bound, and this function runs in the (un-sandboxed) gateway process when hashing a freshly compiled class from a Declare transaction.

### Finding Description
`CasmContractClass` (produced by compiling a user-submitted Sierra program) carries a `bytecode_segment_lengths: Option<NestedIntList>` field, an enum that is inherently recursive: [1](#0-0) 

When the gateway computes the compiled class hash for a newly compiled class, it calls `HashableCompiledClass::hash`, which walks this tree recursively with **no depth limit or guard**: [2](#0-1) 

This differs from the only other place in the codebase that walks the same segment structure (`NestedFeltCounts::new_inner` in blockifier), which explicitly asserts `segmentation_depth <= 1` before recursing further, precisely to avoid unbounded nesting: [3](#0-2) 

The vulnerable call path is reached from a normal Declare transaction: `SierraCompiler::compile` invokes the (sandboxed, resource-limited) Sierra→CASM compiler subprocess to get a `CasmContractClass`, then immediately calls `.hash(&HashVersion::V2)` **in the parent gateway process**, outside of any subprocess resource sandbox: [4](#0-3) [5](#0-4) 

The subprocess compilation is resource-limited (CPU time, memory, bytecode size), so a stack overflow occurring *inside the subprocess* while building `bytecode_segment_lengths` would only kill that sandboxed subprocess. However, the hash computation over the resulting tree happens back in the unsandboxed parent process with no equivalent protection (no recursion-depth guard, no `rlimit`, no iterative rewrite), making the parent gateway process itself the impact target of any excessively deep tree that the compiler manages to emit.

### Impact Explanation
If an attacker can craft a Sierra program that the trusted `cairo-lang` compiler segments into a sufficiently deep nested tree (segments are derived from the program's control-flow/function structure, which the attacker fully controls via the declared class), the resulting `bytecode_hash_node` recursion in the gateway process can overflow the native stack, crashing the gateway component that handles Declare transaction validation for all users on that node — a network-wide-if-widely-run availability impact reachable by a single unprivileged Declare transaction. This matches the "network unable to confirm new transactions" acceptance criterion (crash-inducing DoS of the transaction-intake path), analogous in root cause (CWE-787/unbounded recursion) to the reported `opcua` advisory.

### Likelihood Explanation
Likelihood depends on whether the audited `cairo-lang` compiler can actually be coerced into emitting an arbitrarily deep segment tree from valid, size-limited Sierra input (bytecode size is capped by `max_bytecode_size`, ~80KB by default, but this bounds total leaves, not nesting *depth* of the `Node`/`Leaf` tree — deep, narrow nesting is not excluded by a byte-size cap alone). This needs to be corroborated against the actual segmentation algorithm in `cairo-lang-starknet-classes`/`cairo-lang-sierra-to-casm` (external dependency, not in this repo) to determine the practical maximum achievable nesting depth per unit of bytecode size, which determines feasibility.

### Recommendation
- Add an explicit recursion-depth (or convert to iterative/worklist) implementation for `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs`, matching the existing depth guard already used for the analogous walk in `blockifier/src/execution/contract_class.rs` (`assert!(segmentation_depth <= 1, ...)`), and reject/error instead of recursing past a safe bound.
- Alternatively/additionally, validate `bytecode_segment_lengths`' nesting depth immediately after compilation (before hashing) and reject the class if it exceeds an expected bound (e.g., 2, consistent with `NestedFeltCounts`'s assumption of depth ≤ 1).

### Proof of Concept
Not independently reproduced (would require exercising the external `cairo-lang` Sierra→CASM compiler to confirm it can be coerced into producing a `NestedIntList` tree deep enough to overflow a native thread stack from a Sierra program within `max_bytecode_size`). Root cause is demonstrated by code inspection: `bytecode_hash_node` recurses unconditionally over `node.iter_children()` with no depth tracking or limit, unlike the sibling function in blockifier that explicitly bounds depth to 1.

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }
