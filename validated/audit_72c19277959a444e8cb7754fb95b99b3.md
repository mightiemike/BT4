### Title
Relayer fee is unconditionally paid out via an independent, unchecked promise before the corresponding user action executes or is confirmed to succeed - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In the NEAR Wallet Contract's `inner_rlp_execute`, when an emulated `EOABaseTokenTransfer` or `ERC20Transfer` has a non-zero relayer `fee`, a separate `promise_batch_create`/`promise_batch_action_transfer` receipt paying the relayer is dispatched immediately and independently of the promise chain that actually performs the requested transfer. The fee-payment receipt is not chained (`.then()`) to the action promise and its result is never checked, so the relayer is paid even if the user's intended base-token or ERC-20 transfer subsequently fails.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330`) parses the RLP-encoded Ethereum transaction into a NEAR `action`/`transaction_kind`. For fee-bearing kinds it creates a standalone transfer promise to the relayer *before* building the promise that executes the actual requested action: [1](#0-0) 

This `refund_promise` is created via `env::promise_batch_create(&context.predecessor_account_id)` + `env::promise_batch_action_transfer`, completely separate from the `promise` variable built afterward at line 412 that actually dispatches the base-token/ERC-20 transfer (and its `.then(ext.rlp_execute_callback(...))` / `.then(ext.nep_141_storage_balance_callback(...))` chains): [2](#0-1) 

The only failure handling that exists is in `rlp_execute_callback`, which checks `env::promise_result(0)` for the *action* promise and, on failure, refunds the `caller_deposit` (the originally attached deposit) — but this has no relationship to, and does not claw back, the fee that was already sent to the relayer in a sibling receipt: [3](#0-2) 

Because the fee-transfer receipt is fired unconditionally at parse time and its outcome/ordering relative to the action promise is never checked or gated, this is structurally the same defect as the reported `CrosschainDistributor._settleClaim` issue: a cross-call (`xcall`/here, a NEAR cross-account `Promise`) whose completion/success is not verified before crediting value, allowing state (fee payment) to diverge from the actual outcome of the paired operation.

### Impact Explanation
A relayer (an unprivileged meta-transaction sender who merely calls `rlp_execute` on someone else's Wallet Contract account with an RLP-signed tx) can submit — or simply happen to submit — a transaction whose downstream transfer action fails (e.g., ERC-20 `ft_transfer` reverts due to insufficient balance, receiver registration issues, or gas exhaustion in the multi-hop `storage_balance_of` → `storage_deposit` → `ft_transfer` chain) while still being paid the attached `fee`. This is unauthorized value movement out of the wallet-contract owner's account: the owner pays a service fee for a transfer that never happens, with no code path to reclaim the fee. Since the wallet contract enforces only one in-flight transaction at a time (not a rollback across sibling promises), the fee payment is final and independent of whether the paired action succeeds.

### Likelihood Explanation
High feasibility: any relayer capable of calling `rlp_execute` (this is the intended, permissionless way anyone can relay a user's signed Ethereum-style transaction) can trigger the vulnerable path by relaying a transaction with a non-zero fee whose target action is engineered or naturally likely to fail (e.g., transferring an ERC-20 amount that exceeds available balance, or targeting a token/receiver combination that fails `storage_deposit`). No validator or node compromise is required; a single crafted transaction plus an already-signed user fee suffices.

### Recommendation
Chain the fee-payment transfer into the same promise pipeline as the action, gated behind the outcome of the action's execution (e.g., pay the fee only inside `rlp_execute_callback` after confirming `PromiseResult::Successful`), or use `promise_and`/sequential `.then()` composition so the relayer fee transfer only executes after the main action promise resolves successfully. Alternatively, have `rlp_execute_callback` explicitly refund the fee back to the user (or debit it from the relayer) when the paired action's `promise_result` is `Failed`.

### Proof of Concept
1. A relayer holds a valid, correctly-nonced RLP-encoded Ethereum transaction from the wallet owner specifying an `ERC20Transfer` (or `EOABaseTokenTransfer`) with `fee > 0`, where the transfer amount deliberately exceeds the wallet owner's token balance on the NEP-141 contract (or otherwise is guaranteed to fail, e.g., malformed `storage_deposit` interaction).
2. Relayer calls `WalletContract::rlp_execute(target, tx_bytes_b64)`.
3. In `inner_rlp_execute`, parsing succeeds, nonce is incremented, and because `fee` is non-zero and `predecessor_account_id != current_account_id`, the fee-refund promise is dispatched immediately (`lib.rs:381-384`).
4. Separately, the actual transfer promise chain (`storage_balance_of` → `ft_transfer`/`storage_deposit` → `rlp_execute_callback`) is built and returned; downstream it fails due to insufficient token balance.
5. `rlp_execute_callback` observes `PromiseResult::Failed` and returns an `ExecuteResponse{success: false, ...}` — but the fee receipt created in step 3 has already independently succeeded and transferred `fee` to the relayer.
6. Net result: the wallet owner is charged the relayer fee even though no actual transfer took place — unauthorized value movement with no recovery path.
