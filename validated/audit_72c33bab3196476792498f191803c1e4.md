### Title
Accounts-index disk bucket storage grows on churn but never shrinks, letting unprivileged users permanently inflate validator storage/CPU cost - (File: `bucket_map/src/bucket.rs`)

### Summary
The external report describes an attacker who cheaply and repeatedly inserts and immediately withdraws value to drain a shared, bounded resource (the LST adapter's redemption buffer), degrading service for everyone else. The closest reachable analog in this codebase is the on-disk accounts-index `BucketMap`: an unprivileged user can cause many pubkeys to be inserted into and then removed from a given index bin's on-disk bucket (e.g. by creating and then closing/zeroing many accounts whose keys hash into the same bin) purely through ordinary, permissionless transactions. Each burst of inserts causes `Bucket::grow_index`/`grow_data` to permanently enlarge that bin's backing mmap file [1](#0-0) , but there is no corresponding shrink path anywhere in `bucket.rs`/`bucket_storage.rs` — once grown, a bucket's file size and rehash cost never go back down, even after all the churned pubkeys are deleted via `delete_key`. This is a low-cost, repeatable user action that leaves a permanent, disproportionate storage and CPU tax on the validator, mirroring the report's "cheap deposit/redeem cycle drains a bounded shared resource" bug class.

### Finding Description
`Bucket::grow_index` and `Bucket::grow_data` are the only resize paths for the disk-backed index/data buckets, and both always grow: `grow_index` computes `new_capacity = (current_capacity * 110 / 100).max(anticipated_size)` and allocates a strictly larger `BucketStorage` [1](#0-0) ; `grow_data` similarly only increases `current_capacity_pow2 + 1` [2](#0-1) . `Bucket::delete_key` frees the slot inside the existing bucket storage (`self.index.free(elem_ix)`, `data_bucket.free(loc)`) but does not reallocate to a smaller backing file [3](#0-2) . A grep across the crate confirms there is no `shrink`/`shrink_to_fit` implementation for `Bucket`/`BucketStorage` — capacity is monotonically non-decreasing for the lifetime of the bin's file. `BucketMapHolder`/`InMemAccountsIndex` implement an analogous "reallocate to clear tombstones" for the *in-memory* hashmap layer only when Threshold index mode is enabled [4](#0-3) , but this rebuild only restores capacity down to `target_entries` (a fixed high-water-derived value), not below it, and has no equivalent for the on-disk `BucketMap` at all.

Because `bucket_ix` is a deterministic hash of the pubkey (`Bucket::bucket_index_ix` uses a per-validator random seed, but the number of bins is fixed and public), an attacker can target a specific bin by generating many keypairs and filtering for ones that hash into it, then issuing ordinary system-program `CreateAccount`/`Assign`+zero-lamport-close transactions to pump a burst of inserts into that bin over one epoch and then let them all become zero-lamport/dead and get purged by `clean_accounts`. The bin's disk bucket grows to accommodate the burst and never shrinks back, permanently increasing that bin's mmap file size and the cost of any future `grow_index` rehash/copy pass (`copy_contents` walks the entire old capacity) [5](#0-4) .

### Impact Explanation
This does not corrupt account state or hashes; the impact is a permanent, disproportionate increase in disk usage and CPU cost (grow/rehash time) for the affected accounts-index bin(s), inflicted by low-cost, unprivileged, repeatable transactions. Because bucket growth is one-directional, repeated bursts compound the effect over time, and the cost is paid by every validator that runs with the disk-backed index enabled (`--accounts-index-memory-limit-mb`/`IndexLimit::Minimal`/`Threshold`), which is common on validators with constrained RAM. This matches the "disproportionate storage and CPU cost" acceptance criterion.

### Likelihood Explanation
Triggering this requires only ordinary permissionless transactions (create/fund/close many accounts) and does not require any privileged role. It does require the target validator to be running with the disk index enabled, which is an operator choice but a common one for capacity reasons; it is not something an operator can trivially "fix by config" without giving up the memory savings the disk index provides. The attacker needs to precompute pubkeys hashing to a given bin, which is straightforward given a known, fixed bin count and per-process random seed is not needed to cause *some* bin to bloat — an attacker can simply churn a very large number of arbitrary keys to guarantee many bins are affected.

### Recommendation
Add a shrink/compaction path to `BucketStorage`/`Bucket` (mirroring `reallocate_to_clear_tombstones` in `InMemAccountsIndex`) that periodically rebuilds a bin's on-disk index/data buckets into a freshly sized allocation when the live entry count is far below the current capacity, reclaiming both disk space and future rehash cost. Consider tracking a per-bin low-water mark analogous to `ThresholdEntriesPerBin` and triggering compaction during idle/background maintenance windows (e.g., alongside `clean_accounts`/shrink) rather than only ever growing.

### Proof of Concept
1. Run a validator with the disk-backed accounts index enabled (`--accounts-index-memory-limit-mb` set, or any config selecting `IndexLimit::Minimal`/`Threshold`).
2. Generate a large batch of keypairs and pre-filter for ones whose `Bucket::bucket_index_ix` hash lands in a small set of bins (attacker can learn this offline against a locally-replicated bin count/hasher, or simply generate enough keys to guarantee saturation of many bins).
3. Submit `CreateAccount`+funding transactions for all of these keys within a short window, then zero their lamports/close them.
4. Observe via `bucket_map`/`accounts_index` metrics (`disk_index_resizes`, `disk_index_max_size`, `disk_data_file_size`) [6](#0-5)  that the targeted bin(s)' bucket capacity/file size increased and, after `clean_accounts` purges the now-dead keys, remains at the inflated size indefinitely — no corresponding shrink event occurs.

    /// Rebuild the bin's HashMap into a fresh allocation to clear tombstones left
    /// behind by evictions. hashbrown counts tombstones against `capacity`, so
    /// without this the bin's effective capacity drifts down over time and triggers
    /// the hashmap to double in capacity.
    ///
    /// Only called in Threshold mode, where `capacity >= target_entries` is guaranteed
    /// by the time eviction runs (`check_flush_trigger` gates on `high_water_mark`).
    fn reallocate_to_clear_tombstones(&self) {
        let stats = self.stats();
        let m = Measure::start("reallocate_hashmap");

        let target_entries = self
            .storage
            .threshold_entries_per_bin
            .as_ref()
            .expect("reallocate_to_clear_tombstones only runs in Threshold mode")
            .target_entries;

        let mut map = self.map_internal.write().unwrap();
        let capacity_pre = map.capacity();

        // Drain the old map into a fresh allocation sized to `target_entries` so the
        // backing storage stays stable across eviction cycles. Building a brand-new
        // map (rather than `shrink_to_fit`) guarantees a full rehash, which is what
        // actually clears the tombstones.
        let mut new_map = HashMap::with_capacity_and_hasher(target_entries, map.hasher().clone());
        new_map.extend(map.drain());
        *map = new_map;
        let capacity_post = map.capacity();
        drop(map);

        stats.update_in_mem_capacity(capacity_pre, capacity_post);
        Self::update_stat(&stats.num_hashmap_reallocates, 1);
        Self::update_time_stat(&stats.hashmap_reallocate_us, m);
    }

    /// copy contents from 'old_bucket' to 'self'
    /// This is used by data buckets
    fn copy_contents(&mut self, old_bucket: &Self) {
        let mut m = Measure::start("grow");
        let old_cap = old_bucket.capacity();
        let old_map = &old_bucket.mmap;

        let increment = self.contents.capacity_pow2() - old_bucket.contents.capacity_pow2();
        let index_grow = 1 << increment;
        (0..old_cap as usize).for_each(|i| {
            if !old_bucket.is_free(i as u64) {
                self.copying_entry((i * index_grow) as u64, old_bucket, i as u64);

                {
                    // copying from old to new. If 'occupied' bit is stored outside the data, then
                    // occupied has to be set on the new entry in the new bucket.
                    let start = self.get_start_offset_with_header((i * index_grow) as u64);
                    self.contents
                        .occupy(&mut self.mmap[start..], i * index_grow);
                }
                let old_ix = i * old_bucket.cell_size as usize;
                let new_ix = old_ix * index_grow;
                let dst_slice: &[u8] = &self.mmap[new_ix..new_ix + old_bucket.cell_size as usize];
                let src_slice: &[u8] = &old_map[old_ix..old_ix + old_bucket.cell_size as usize];

                unsafe {
                    let dst = dst_slice.as_ptr() as *mut _;
                    let src = src_slice.as_ptr();
                    std::ptr::copy_nonoverlapping(src, dst, old_bucket.cell_size as usize);
                };
            }
        });
        m.stop();
        // resized so update total file size
        self.stats.resizes.fetch_add(1, Ordering::Relaxed);
        self.stats.resize_us.fetch_add(m.as_us(), Ordering::Relaxed);
    }
