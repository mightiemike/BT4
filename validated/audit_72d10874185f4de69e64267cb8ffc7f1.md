### Title
Unbounded prefixQuery scan in `DelegatedResourceAccountIndexStore.getV2Index` reachable via `/wallet/getdelegatedresourceaccountindexv2` allows attacker-amplified DoS - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
The `GetDelegatedResourceAccountIndexV2Servlet.doGet` handler ultimately calls `DelegatedResourceAccountIndexStore.getV2Index` → `getWithPrefix`, which performs two unbounded RocksDB `prefixQuery` iterator scans (`FROM`/`TO` prefixed by the address) with no result-size cap or pagination. Since any funded account can call `DelegateResourceContract` for as little as 1 TRX to add a new `V2_TO_PREFIX+receiver+owner` key, an attacker can cheaply inflate the number of keys under a victim receiver's prefix and force the query endpoint to do proportionally more iterator work and allocate/sort proportionally larger in-memory lists per request.

### Finding Description
The HTTP endpoint `/wallet/getdelegatedresourceaccountindexv2` is served by `GetDelegatedResourceAccountIndexV2Servlet.doGet` [1](#0-0) , which calls `wallet.getDelegatedResourceAccountIndexV2(address)` [2](#0-1) . This in turn calls `DelegatedResourceAccountIndexStore.getV2Index`, which calls the private `getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address)` [3](#0-2) . That method issues two `this.prefixQuery(key)` calls — one for the `from` list and one for the `to` list — collects all matches into an `ArrayList`, and sorts them by timestamp, with no `limit` parameter anywhere in the call chain.

The underlying `prefixQuery` implementation in `RocksDbDataSourceImpl.prefixQuery` seeks to the prefix key and iterates forward through every matching key until the prefix no longer matches, materializing all matches into a `HashMap` before returning [4](#0-3) . `Chainbase.prefixQuery` further merges root-DB results with an in-memory snapshot scan, so cost also scales with any snapshot layer [5](#0-4) . Note that other paths (`getKeysNext`, `getValuesNext`, `getNext`) support a `limit` parameter, but `prefixQuery` and thus `getWithPrefix`/`getV2Index` do not.

To grow the number of index entries under a chosen receiver's `V2_TO_PREFIX+receiver` key, an unprivileged attacker can call `DelegateResourceContract` from many distinct funded owner accounts targeting the same receiver. `DelegateResourceActuator.validate()` requires only that `delegateBalance >= 1 TRX` and that receiver/owner accounts exist and aren't the same address or a contract account [6](#0-5) ; each successful delegation adds one `V2_TO_PREFIX+receiver+owner` entry via `delegatedResourceAccountIndexStore.delegateV2` [7](#0-6) . There is no cap on the number of distinct delegators per receiver enforced anywhere in the validate path.

`RateLimiterServlet` (the base class of `GetDelegatedResourceAccountIndexV2Servlet`) only throttles request rate (QPS per endpoint / per IP / globally) via `IRateLimiter.acquirePermit` [8](#0-7) ; it applies no cost-based throttling relative to the size of the underlying prefix scan or number of delegator entries, so a single request against a heavily-delegated address consumes CPU/IO proportional to attacker-controlled state size regardless of the rate limiter.

### Impact Explanation
This is a Denial-of-Service on the HTTP/RPC API layer of a node: each `getdelegatedresourceaccountindexv2` (and its solidity/PBFT variants, and the corresponding gRPC `GetDelegatedResourceAccountIndexV2`) request against an attacker-inflated address triggers an O(n) full prefix scan and in-memory sort over `n` attacker-created delegator entries, with no pagination or cap. Repeated/concurrent requests amplify CPU and I/O load on the serving node, degrading availability of the wallet API for legitimate users. This matches the "DoS via RPC-API" impact class scoped in the prompt. It does not affect consensus, funds, or private key material — only API responsiveness of the queried node.

### Likelihood Explanation
The attack requires only unprivileged, funded accounts (no special permissions) and cheap DelegateResourceContract transactions (minimum 1 TRX delegated balance plus standard bandwidth/energy cost per tx, each of which is refundable/re-usable since delegation can later be undone). It is fully repeatable and scriptable: an attacker can create/fund many accounts (or reuse a smaller number of accounts across resource types/lock variants to multiply distinct `(owner, receiver)` pairs) and broadcast many `DelegateResourceContract` transactions targeting one victim receiver address, then hit the read-only GET endpoint repeatedly. The per-request cost is real but bounded by how many distinct delegator entries the attacker is willing to pay to create; this is a resource-amplification/read-cost issue rather than a catastrophic single-request crash, so likelihood of enabling meaningful sustained degradation is moderate-to-high depending on how cheaply an attacker can create very large numbers of unique owner accounts.

### Recommendation
Add pagination/limits to `DelegatedResourceAccountIndexStore.getWithPrefix`/`getV2Index` (and the legacy V1 equivalent), e.g., accept an offset/limit and use the already-existing `getKeysNext`/`getNext`-style bounded iteration primitives instead of unbounded `prefixQuery`, and enforce a hard cap on the number of `(from/to)` accounts to return per query (with an API to page through the rest). Additionally consider limiting the maximum number of distinct delegator relationships a single receiver address can accumulate, or apply per-endpoint cost-based rate limiting (e.g., proportional to result set size) in `RateLimiterServlet`/its adapters for this and similarly unbounded scan endpoints.

### Proof of Concept
1. Fund N distinct owner accounts, each freeze bandwidth via `FreezeBalanceV2Contract`, then broadcast `DelegateResourceContract` from each to the same `RECEIVER_ADDRESS` with `balance = 1_000_000` (1 TRX) — reference actuator setup mirrors `DelegateResourceActuatorTest.testDelegateResourceForBandwidth` [9](#0-8) .
2. Repeat step 1 for N = 1,000 / 10,000 / 100,000 distinct owner addresses targeting the same receiver.
3. Issue concurrent HTTP GET requests: `GET /wallet/getdelegatedresourceaccountindexv2?value=<RECEIVER_ADDRESS_BASE58>&visible=true`, matching `GetDelegatedResourceAccountIndexV2ServletTest.testGet` request shape [10](#0-9) .
4. Measure response latency and node CPU utilization as N grows; expect near-linear latency/CPU growth with N and no server-side rejection due to result size, confirming the unbounded `prefixQuery` scan cost is proportional to attacker-controlled state and that `RateLimiterServlet` (rate-only) does not mitigate it.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  @Override
  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    resetDbLock.readLock().lock();
    try (final ReadOptions readOptions = getReadOptions();
         final RocksIterator iterator = getRocksIterator(readOptions)) {
      Map<WrappedByteArray, byte[]> result = new HashMap<>();
      for (iterator.seek(key); iterator.isValid(); iterator.next()) {
        if (Bytes.indexOf(iterator.key(), key) == 0) {
          result.put(WrappedByteArray.of(iterator.key()), iterator.value());
        } else {
          return result;
        }
      }
      return result;
    } finally {
      resetDbLock.readLock().unlock();
    }
  }

  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    Map<WrappedByteArray, byte[]> result = prefixQueryRoot(key);
    Map<WrappedByteArray, byte[]>  snapshot = prefixQuerySnapshot(key);
    result.putAll(snapshot);
    result.entrySet().removeIf(e -> e.getValue() == null);
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQueryRoot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      result = ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      result = ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    }
    return result;
  }
