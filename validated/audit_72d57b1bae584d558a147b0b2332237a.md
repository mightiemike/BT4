### Title
Blocked senders removed from Functions Gateway allowlist persistence but never removed from in-memory authorization state - (File: core/services/gateway/handlers/functions/allowlist/allowlist.go)

### Summary
The Chainlink Functions Gateway's `onchainAllowlist` component mirrors the reported bug class: it removes a revoked entity from one storage layer while leaving a stale, authoritative copy behind that is still consulted for access-control decisions. `syncBlockedSenders` deletes blocked senders from the persisted ORM table, but the in-memory `allowlist` map used by the actual authorization check `Allow()` is never updated to remove them.

### Finding Description
`onchainAllowlist.Allow()` is the sole authorization gate for the Functions Gateway, checking membership in the in-memory map held by `a.allowlist` (an `atomic.Pointer[map[common.Address]struct{}]`): [1](#0-0) 

In the batch-processing update path, `updateFromContractV1` calls `updateAllowedSendersInBatches` (which only adds newly allowed senders to the in-memory snapshot) followed by `syncBlockedSenders` (which only deletes blocked senders from the ORM/database layer): [2](#0-1) 

`updateAllowedSendersBatch` builds the in-memory snapshot exclusively by merging newly fetched allowed senders into `currentAllowedSenderList`, which itself is seeded from the *existing* in-memory allowlist — so once an address is in memory, it is never dropped by this path: [3](#0-2) [4](#0-3) 

Meanwhile, `syncBlockedSenders` only calls `a.orm.DeleteAllowedSenders`, touching the persisted table, not the in-memory map that `Allow()` actually checks: [5](#0-4) 

This is directly analogous to the `PermissionsRegistry.removeRole` bug: the "role" (allowlist membership) is removed from a secondary/administrative store (`_roles` list / ORM table) but the primary authorization-check structure (`hasRole` mapping / in-memory `allowlist`) still returns a stale positive.

### Impact Explanation
Once a sender address is loaded into the node's in-memory allowlist, it stays authorized indefinitely for that running process, even after the on-chain Terms-of-Service allowlist contract blocks/revokes it and even after subsequent periodic sync cycles run `syncBlockedSenders`. A previously-authorized-but-now-revoked entity can continue submitting requests to the Functions Gateway that pass the `Allow()` check, i.e., an unauthorized-privileged-action bypass in the gateway routing/authorization trust boundary. The in-memory state is only corrected by process restart, since `loadStoredAllowedSenderList` (which rebuilds from the now-corrected ORM table) only runs at `Start()`: [6](#0-5) 

### Likelihood Explanation
This triggers automatically any time the TOS allowlist contract blocks a previously allowed sender and the batch-processing update path (`tosContractMinBatchProcessingVersion` or newer) is in use with periodic updates enabled (`UpdateFrequencySec != 0`), which is the expected operating configuration for Functions Gateway nodes. No attacker action beyond having been allowlisted once (then subsequently revoked) is required — likelihood is high in any long-running node until restart.

### Recommendation
`syncBlockedSenders` should also remove blocked senders from the live in-memory `a.allowlist` snapshot (e.g., by deleting matching entries from the map under the same atomic-swap pattern used in `updateAllowedSendersBatch`), not just from the ORM table, so `Allow()` reflects revocations immediately rather than only after a node restart.

### Proof of Concept
1. Node A allowlists sender `S` on-chain via the TermsOfServiceAllowList contract; the periodic `UpdateFromContract` cycle runs `updateAllowedSendersInBatches`, adding `S` to `a.allowlist` in memory and to the ORM table.
2. `S` is later blocked/removed from the on-chain allowlist contract.
3. Next periodic update cycle calls `updateFromContractV1` → `updateAllowedSendersInBatches` (does not touch `S` since it's not newly allowed, and does not remove stale entries) → `syncBlockedSenders` (removes `S` only from the ORM table via `a.orm.DeleteAllowedSenders`).
4. `S` remains present in the in-memory `a.allowlist` map indefinitely.
5. `S` continues submitting requests to the Functions Gateway; `Allow(S)` at line 175-179 returns `true`, granting continued access despite on-chain revocation, until the node process is restarted.

// syncBlockedSenders fetches the list of blocked addresses from the contract in batches
// and removes the addresses from the functions_allowlist table if present
func (a *onchainAllowlist) syncBlockedSenders(ctx context.Context, tosContract *functions_allow_list.TermsOfServiceAllowList, blockNum *big.Int) error {
	count, err := tosContract.GetBlockedSendersCount(&bind.CallOpts{
		Pending:     false,
		BlockNumber: blockNum,
		Context:     ctx,
	})
	if err != nil {
		return errors.Wrap(err, "unexpected error during functions_allow_list.GetBlockedSendersCount")
	}

	throttleTicker := time.NewTicker(time.Duration(a.config.FetchingDelayInRangeSec) * time.Second)
	for idxStart := uint64(0); idxStart < count; idxStart += uint64(a.config.OnchainAllowlistBatchSize) {
		<-throttleTicker.C

		idxEnd := idxStart + uint64(a.config.OnchainAllowlistBatchSize)
		if idxEnd >= count {
			idxEnd = count - 1
		}

		blockedSendersBatch, err := tosContract.GetBlockedSendersInRange(&bind.CallOpts{
			Pending:     false,
			BlockNumber: blockNum,
			Context:     ctx,
		}, idxStart, idxEnd)
		if err != nil {
			return errors.Wrap(err, "error calling GetAllowedSendersInRange")
		}

		err = a.orm.DeleteAllowedSenders(ctx, blockedSendersBatch)
		if err != nil {
			a.lggr.Errorf("failed to delete blocked address from allowed list in storage: %v", err)
		}
	}
	throttleTicker.Stop()

	return nil
