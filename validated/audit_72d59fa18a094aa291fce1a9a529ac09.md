### Title
Missing voting-window enforcement lets any signer vote for an aggregate key outside the prepare phase - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
`vote-for-aggregate-public-key` never calls the contract's own `is-in-voting-window` helper, so a signer's vote for a reward cycle's aggregate public key is accepted at any burn height, not only during the prepare phase of the immediately-preceding reward cycle as the code's documentation and `is-in-voting-window`/`is-in-prepare-phase` helpers imply. This mirrors the reported bug class: a state-mutating action intended to be time/role-gated (the offering's `extendTime`, gated by `onlyOwner`) is left reachable by an unprivileged/unintended caller because the guard exists in code but is never wired into the entry point.

### Finding Description
`is-in-voting-window` (lines 95-98) and `is-in-prepare-phase` (lines 79-84) exist specifically to restrict voting to the prepare phase of the cycle preceding `reward-cycle`, matching the doc comment on `vote-for-aggregate-public-key` (lines 124-132): "This vote must happen after the list of signers has been set by the node, which occurs in the first block of the prepare phase." However, the public entry point `vote-for-aggregate-public-key` (lines 143-199) only checks:
- that the caller is a legitimate signer for that reward cycle (`get-signer-weight`, line 146, via `.signers get-signer-by-index` + `is-eq (get signer details) tx-sender)`),
- that no key has been finalized yet for the cycle (line 155, mislabeled with `ERR_OUT_OF_VOTING_WINDOW`),
- that the key is well-formed, novel, not double-voted, and the round increments by at most 1.

None of these asserts call `is-in-voting-window`. Any signer that is a member of the *current* signer set (as determined by `.signers get-signer-by-index`) can therefore submit a vote for a `reward-cycle` at any burn height — before the prepare phase begins, long after it ends, or even for a `reward-cycle` value the `.signers` set-cycle logic wasn't intended to expose yet — as long as `get-signer-by-index` for that arbitrary `reward-cycle` returns them as a signer and no aggregate key has been finalized for it yet.

### Impact Explanation
This breaks the equality the protocol depends on: "an aggregate-key vote is only valid if cast during the designated prepare-phase window for that reward cycle." Because the window check is dead code, votes cast far outside the intended window can accumulate weight and finalize an aggregate public key for a reward cycle prematurely or unexpectedly (e.g., before the final signer set / weights for that cycle are settled, or stale votes lingering from a previous round context). Since `get-and-cache-total-weight` (lines 103-109) caches `cycle-total-weight` the first time it's computed, an out-of-window vote can lock in a total-weight snapshot that doesn't correspond to the reward cycle's eventual/expected signer composition, producing a tally/threshold calculation that downstream nodes reproducing this logic from the intended timing model would not agree with — i.e., a "signer weight/threshold computed from the wrong set/time" style divergence, matching the report's rated class of a minority-triggerable divergence bounded to the signer-voting subsystem.

### Likelihood Explanation
Any single signer already possessing a valid position in `.signers` for some `reward-cycle` can trigger this merely by calling `vote-for-aggregate-public-key` outside the prepare-phase window — no majority collusion needed to trigger the missing check itself (though reaching the weight threshold to finalize a key still requires sufficient weight). The bug is a straightforward missing function call (dead validation helper), which is directly analogous to the reported missing `onlyOwner` check: the guard code exists but is never enforced at the call site.

### Recommendation
Add the missing check to `vote-for-aggregate-public-key`:
```clarity
(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))
```
placed alongside the other `asserts!` in the function body, ensuring votes are only accepted during the intended prepare-phase window for the target reward cycle, consistent with the function's documentation.

### Proof of Concept
1. Determine a signer's `signer-index` for some future `reward-cycle` `N` via `.signers get-signer-by-index`.
2. At any burn height outside the prepare phase of cycle `N-1` (e.g., immediately after cycle `N`'s prepare phase has already closed, or well before it opens), call `(contract-call? .signers-voting vote-for-aggregate-public-key signer-index key round N)` from that signer's principal.
3. Observe the call succeeds (no `ERR_OUT_OF_VOTING_WINDOW` or any window-related rejection), because `is-in-voting-window`/`is-in-prepare-phase` are never invoked in the function body — confirmed by inspection of `signers-voting.clar` lines 95-98 (helper defined) versus lines 143-199 (helper never referenced). ;; Signer vote for the aggregate public key of the next reward cycle
;;  Each signer votes for the aggregate public key for the next reward cycle.
;;  This vote must happen after the list of signers has been set by the node,
;;  which occurs in the first block of the prepare phase. The vote is concluded
;;  when the threshold of `threshold-consensus / 1000` is reached for a
;;  specific aggregate public key. The vote is weighted by the amount of
;;  reward slots that the signer controls in the next reward cycle. The vote
;;  may require multiple rounds to reach consensus, but once consensus is
;;  reached, later rounds will be ignored.
;;
;;  Arguments:
;;   * signer-index: the index of the calling signer in the signer set (from
;;     `get-signers` in the .signers contract)
;;   * key: the aggregate public key that this vote is in support of
;;   * round: the voting round for which this vote is intended
;;   * reward-cycle: the reward cycle for which this vote is intended
;;  Returns:
;;   * `(ok true)` if the vote was successful
;;   * `(err <code>)` if the vote was not successful (see errors above)
(define-public (vote-for-aggregate-public-key (signer-index uint) (key (buff 33)) (round uint) (reward-cycle uint))
    (let ((tally-key {reward-cycle: reward-cycle, round: round, aggregate-public-key: key})
            ;; vote by signer weight
            (signer-weight (try! (get-signer-weight signer-index reward-cycle)))
            (new-total (+ signer-weight (default-to u0 (map-get? tally tally-key))))
            (cached-weight (try! (get-and-cache-total-weight reward-cycle)))
            (threshold-weight (get-threshold-weight reward-cycle))
            (current-round (default-to {
                votes-count: u0, 
                votes-weight: u0} (map-get? round-data {reward-cycle: reward-cycle, round: round})))
                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
        ;; Check that the aggregate public key is the correct length
        (asserts! (is-eq (len key) u33) (err ERR_ILL_FORMED_AGGREGATE_PUBLIC_KEY))
        ;; Check that aggregate public key has not been used in a previous reward cycle
        (asserts! (is-novel-aggregate-public-key key reward-cycle) (err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY))
        ;; Check that signer hasn't voted in this reward-cycle & round
        (asserts! (map-insert votes {reward-cycle: reward-cycle, round: round, signer: tx-sender} {aggregate-public-key: key, signer-weight: signer-weight}) (err ERR_DUPLICATE_VOTE))
        ;; Check that the round is incremented by at most 1
        (try! (update-last-round reward-cycle round))
