## Finding

### Title
`ensure_match_transaction_info()` never checks the state-checkpoint hash, so replay-verify tooling accepts a state root that diverges from the authenticated ledger - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by the chunk-executor's "verify execution" path (backup restore with `VerifyExecutionMode`, `replay-on-archive`, and the debugger) to confirm that locally re-executed transactions reproduce the authenticated, on-chain-committed result. It checks status, gas used, the write-set hash, and the event root hash, but it explicitly skips comparing `state_checkpoint_hash` (the Sparse-Merkle state root) and the newer `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields. A locally computed state root that diverges from the authenticated one — the exact class of bug that would otherwise cause a hard fork — is silently accepted as a passing verification.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates a re-executed `TransactionOutput` against a `TransactionInfo` that has already been authenticated via a Merkle accumulator proof against a trusted `LedgerInfo`. It checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It never reads `txn_info.state_checkpoint_hash()` (nor the V1 `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`), which is the actual root of the authenticated world-state Sparse Merkle Tree at that version. The function's own comment admits this: [2](#0-1) 

This function is the sole per-transaction integrity check used in the chunk-executor's `verify_execution`, which is exercised by transaction-restore "verify" and "replay" flows and by `replay-on-archive`: [3](#0-2) 

Because `write_set_hash` only proves the write set's own hash matches, and no comparison of the resulting state root is performed, a bug (or maliciously constructed local executor/VM) that reproduces the same write set/events/gas/status but computes a *different* resulting state tree (e.g., due to a state-key normalization bug, ordering bug in Jellyfish Merkle updates, or a divergent state-checkpoint boundary) would pass this check even though the resulting `state_checkpoint_hash` — which is what feeds into `TransactionInfo` and ultimately into the transaction accumulator root that light clients and full nodes trust — is wrong.

This distinguishes it from `LedgerUpdateOutput::ensure_transaction_infos_match`, used by the state-sync `StateSyncChunkVerifier`, which does a full struct `==` comparison of the entire `TransactionInfo` (including all checkpoint hashes) and is therefore not affected: [4](#0-3) 

So the gap is confined to the "verify execution" / replay-verify code path (`chunk_executor::verify_execution`), which is precisely the tool whose job is to catch state-root divergence before it becomes a consensus-breaking, hard-fork-only bug.

### Impact Explanation
Replay-verify and `replay-on-archive` exist specifically to detect non-deterministic or buggy VM/state-computation changes against real historical, authenticated chain data before they are deployed to mainnet validators — i.e., to catch exactly the kind of state-divergence bug that would otherwise require a hard fork to fix. Because `ensure_match_transaction_info` omits the state-checkpoint hash comparison, this safety net is defeated for its most important property: it will report a passing/verified replay even when the recomputed world-state root is wrong. This can let a state-divergent VM/executor change slip through review and validation, directly matching the in-scope class "hard-fork-only divergence during commit, replay, restore, or proof verification" and "committed state that differs from the correct VM result."

### Likelihood Explanation
This is not a hypothetical edge case — every call into `verify_execution` (backup-cli restore-with-verify, `replay_on_archive`, `aptos-debugger`) is affected unconditionally, because the check is structurally missing rather than gated behind a rare condition. The bug requires no attacker action to trigger the missing validation; it only requires that whatever divergence exists in the executor/VM under test also happens to produce a matching write set/events (which is plausible for bugs in the state-commitment/Merkle layer that occur *after* the write set is finalized, e.g. state-checkpoint construction, hot-state root computation, or JMT update logic).

### Recommendation
Extend `ensure_match_transaction_info` to also assert `txn_info.state_checkpoint_hash()` (and, when applicable, `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`) against the locally computed state-checkpoint hash for that version, mirroring what `LedgerUpdateOutput::ensure_transaction_infos_match` already does via full-struct comparison. This requires threading the locally computed checkpoint hash into the comparison at the `chunk_executor::verify_execution` call site.

### Proof of Concept
1. In `execution/executor/src/chunk_executor/mod.rs::verify_execution`, re-execute a chunk of transactions from an archived backup using a local executor build that has a (hypothetical) bug that mutates the final state-checkpoint construction/JMT update logic without changing the emitted write set or events (e.g., a stale-key retention bug that only manifests during periodic checkpoint materialization).
2. The re-executed `TransactionOutput` will have identical `status`, `gas_used`, write-set hash, and event root hash to the authenticated `TransactionInfo`, so `ensure_match_transaction_info` at [1](#0-0)  returns `Ok(())`.
3. `verify_execution` returns `Ok(end_version)` at [5](#0-4) , and the overall `replay-on-archive`/restore-verify run reports success, even though the state root actually diverges from the one committed on the authenticated chain.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
    }
