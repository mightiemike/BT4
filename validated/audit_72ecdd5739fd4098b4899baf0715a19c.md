### Title
Precision (decimals) bound-check bypass in TRC10 asset issuance allows creation of tokens with unvalidated/out-of-range decimals - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
The external report describes a wallet trusting unvalidated server data and allowing tokens with "malicious Token Names and weird values for Token Decimals" to be added. The closest on-chain analog in java-tron is in `AssetIssueActuator.validate()`, where the `precision` (decimals) field of a broadcast `AssetIssueContract` transaction is only bounds-checked under a specific dynamic-property condition, allowing an attacker-controlled, out-of-range precision value to be persisted and later surfaced to clients (wallets, explorers, RPC consumers) exactly as in the reported scenario.

### Finding Description
In `validate()`: [1](#0-0) 
the precision range check (`precision < 0 || precision > ActuatorConstant.PRECISION_DECIMAL`) is only enforced when `dynamicStore.getAllowSameTokenName() != 0`. When `AllowSameTokenName` is `0`, an attacker submitting an `AssetIssueContract` transaction (any account can create a TRC10 token) can set an arbitrary `precision` value — including negative values or values far exceeding the intended maximum of 6 — without triggering `"precision cannot exceed 6"`.

In `execute()`: [2](#0-1) 
when `AllowSameTokenName == 0`, only the V2 capsule's precision is forcibly zeroed (`assetIssueCapsuleV2.setPrecision(0)`); the V1 `assetIssueCapsule` (built directly from the unvalidated contract) retains whatever unchecked precision value the attacker supplied, and this V1 capsule is persisted to `assetIssueStore`. This asset's precision/decimals metadata is subsequently exposed via read APIs (e.g., `GetAssetIssueList`/`GetAssetIssueByName` through `Wallet.java`, which reads directly from the stores) to any client, including wallets that display "Token Decimals" — mirroring the exact "weird values for Token Decimals" impact from the report, except the corrupted data originates from the chain itself rather than from a tampered HTTP response, and requires no server-side interception to reach downstream consumers.

### Impact Explanation
A malformed/out-of-range decimals value baked into consensus state can cause:
* Wallets/clients (as in the referenced report) to display and use nonsensical decimal places, leading to gross under/over-representation of balances shown to users.
* Downstream computations by any component that trusts the on-chain `precision` field for the V1 asset (e.g., UI-side balance formatting, external indexers) to misbehave or crash, matching the report's "Application Misbehavior" and "Unintended Data States" categories.
* This is a business-logic validation gap directly analogous to the reported bug: unvalidated token metadata (name/decimals) reaching end users because a validation branch that should always run is conditionally skipped.

### Likelihood Explanation
Exploitation only requires broadcasting a standard `AssetIssueContract` transaction (an unprivileged, anonymous-reachable operation available to any funded account) while the network's `AllowSameTokenName` dynamic parameter is `0`. On networks/private chains where this parameter has not yet been switched on (it is a witness-committee-controlled dynamic property, not necessarily enabled from genesis on every deployment), this is directly and repeatably triggerable, matching the moderate likelihood rating in the original report.

### Recommendation
* Remove the `dynamicStore.getAllowSameTokenName() != 0` gate from the precision bounds check in `AssetIssueActuator.validate()` so the `[0, PRECISION_DECIMAL]` range is enforced unconditionally, regardless of the `AllowSameTokenName` state.
* Ensure `execute()` normalizes/rejects invalid precision for both the V1 and V2 capsules consistently.
* Apply the same server-side validation principle recommended in the original report: never persist or expose token metadata (name, symbol, decimals) that has not passed strict bounds/format validation, since downstream consumers (wallets) will trust it implicitly.

### Proof of Concept
1. On a network/chain state where `DynamicPropertiesStore.getAllowSameTokenName() == 0` (e.g., a private/test java-tron network before this proposal parameter is activated).
2. Broadcast an `AssetIssueContract` transaction with `precision = -1` (or `precision = 100`) along with otherwise valid fields (name, url, totalSupply, trxNum, num, startTime/endTime, etc.).
3. `AssetIssueActuator.validate()` skips the precision bound check because `getAllowSameTokenName() != 0` is false: [1](#0-0) 
4. `execute()` persists the V1 `AssetIssueCapsule` with the attacker-supplied out-of-range precision to `assetIssueStore`: [3](#0-2) 
5. Any client querying the token's info via the node's read APIs receives the corrupted `precision`/decimals value as authoritative on-chain data, reproducing the report's "weird values for Token Decimals" outcome without any response tampering being necessary.
