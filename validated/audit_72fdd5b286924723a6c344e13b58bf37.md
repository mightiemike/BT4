### Title
Unvalidated `send_message_to_l1` `to_address` felt causes sequencer panic on L2→L1 message ordering - (File: `crates/blockifier/src/execution/call_info.rs`)

### Summary
The original ZetaChain bug is a root-cause class of "address-format confusion between two different chains' address encodings, applied without validation, leading to fund loss." The Starknet sequencer analog is in how an L2 contract's `send_message_to_l1` output (`to_address`, a raw felt supplied entirely by the calling contract) is converted into an Ethereum `EthAddress` when the execution result is finalized. The conversion assumes the felt always fits in the 160-bit range used by real Ethereum addresses, and panics via `.expect()` if it doesn't — a condition fully controllable by any unprivileged contract/transaction.

### Finding Description
`starknet_api::core::L1Address` is a thin wrapper around an arbitrary `Felt` value [1](#0-0) , and any felt in the full ~251-bit range can be stored there.

When a contract emits an L2→L1 message, blockifier collects it into `MessageToL1 { to_address: L1Address, payload }` [2](#0-1) . Nothing in this struct or its construction constrains `to_address` to the 160-bit range required for a genuine Ethereum address — it is simply whatever felt the executing Cairo contract passed to the `send_message_to_l1` syscall.

Later, when sorting/ordering these messages for the transaction's execution result, the code performs an unchecked conversion from the raw felt-based `L1Address` to the strict 20-byte `EthAddress` type and panics if it fails:
```rust
to_address: self
    .message
    .to_address
    .try_into()
    .expect("Failed to convert L1Address to EthAddress"),
``` [3](#0-2) 

The `TryFrom<Felt> for EthAddress` conversion explicitly rejects any felt whose upper 12 bytes are non-zero:
```rust
impl TryFrom<Felt> for EthAddress {
    type Error = StarknetApiError;
    fn try_from(felt: Felt) -> Result<Self, Self::Error> {
        const COMPLIMENT_OF_H160: usize = std::mem::size_of::<Felt>() - H160::len_bytes();
        let bytes = felt.to_bytes_be();
        let (rest, h160_bytes) = bytes.split_at(COMPLIMENT_OF_H160);
        if rest != [0u8; COMPLIMENT_OF_H160] {
            return Err(StarknetApiError::OutOfRange { string: felt.to_string() });
        }
        Ok(EthAddress(H160::from_slice(h160_bytes)))
    }
}
``` [4](#0-3) 

Because the felt supplied to `send_message_to_l1` originates directly from unvalidated Cairo contract execution (any deployed contract can call this syscall with an arbitrary `to_address` argument, e.g. `Felt::MAX`), and there is no bounds check performed at message-collection time, this `.expect()` will panic whenever `to_address >= 2^160`. This mirrors the root cause of the ZetaChain bug: an address value from one domain (arbitrary 251-bit Starknet felt) is passed through an interface that implicitly assumes the other domain's narrower address format (160-bit EVM address), and the mismatch is only discovered too late, after being accepted deeper into transaction processing.

### Impact Explanation
Unlike the original bug (funds silently routed to the wrong address), here the mismatch surfaces as an unrecoverable `panic!` inside the sequencer's/blockifier's execution-result finalization path (`to_ordered_tuple`, called from `sorted_items`, which is invoked whenever `CallInfo`/`TransactionExecutionInfo` is built for a transaction with an L2→L1 message). A crash here, triggered deterministically by a single unprivileged transaction/contract call, halts block building/processing for every honest node re-executing that transaction (including full nodes, RPC nodes, and the OS re-execution flow), producing a network unable to confirm new transactions — an explicitly accepted high-impact outcome for this analysis. This is reachable purely by any transaction sender deploying/calling a contract that invokes the `send_message_to_l1` syscall with an out-of-range `to_address` felt; no special privileges, node compromise, or p2p/consensus manipulation is required.

### Likelihood Explanation
Likelihood is high: `send_message_to_l1` is a standard, fully public Cairo syscall available to any contract, and Cairo code can pass any felt (including values ≥ 2^160) as the `to_address` argument without any Cairo-level or syscall-level restriction visible in the reviewed code. Triggering the panic only requires deploying a trivial contract that calls this syscall with such a value and invoking it in a transaction.

### Recommendation
Validate/normalize `to_address` at (or before) the point the L2→L1 message is recorded from the syscall (i.e., when constructing `MessageToL1`/`L1Address` in the syscall handler), returning a proper execution/syscall error (e.g., reverting the call) instead of deferring the check to a later `.expect()`-based conversion in `call_info.rs`. Replace the `.expect("Failed to convert L1Address to EthAddress")` with a graceful error path (charge the call as reverted / return a `SyscallExecutionError`) so a malicious or buggy contract cannot crash sequencer/node execution.

### Proof of Concept
1. Deploy a Cairo contract whose constructor or an entry point calls the `send_message_to_l1_syscall` with `to_address = Felt::MAX` (or any felt with a non-zero byte in the top 12 bytes) and an arbitrary payload.
2. Submit an ordinary `INVOKE` transaction calling that entry point.
3. During execution-result finalization, `OrderedL2ToL1Message::to_ordered_tuple` is invoked (via `sorted_items`) as part of building the `TransactionExecutionInfo`/`CallInfo` for that transaction [5](#0-4) .
4. The `try_into()` call on line 111 fails because the felt exceeds 160 bits, and the subsequent `.expect(...)` panics, crashing the executing process for every node that (re-)executes this transaction. [6](#0-5)
