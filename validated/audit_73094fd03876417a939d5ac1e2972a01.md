### Title
Vault gateway handler trusts user-supplied `Owner` field for secret create/update/delete instead of enforcing the authorized identity - (File: core/capabilities/vault/gw_handler.go)

### Summary
The Vault node-side gateway handler (`GatewayHandler.HandleGatewayMessage`) authorizes every `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` request through `h.requestProcessor.ProcessRequest`, which returns an `AuthResult` bound to the authenticated caller (`AuthResult.AuthorizedOwner()`). For `MethodSecretsList` the handler explicitly re-binds the request to the authenticated identity with `r.Owner = authResult.AuthorizedOwner()` [1](#0-0) . However, for `handleSecretsCreate`, `handleSecretsUpdate`, and `handleSecretsDelete`, the request structs are populated purely from the caller-supplied JSON `req.Params` and forwarded to `secretsService` with no equivalent override of the owner/identity field from `authResult` [2](#0-1) .

### Finding Description
This is the same bug class as the Reality Cards `Treasury.deposit()` M-09 finding: the system authenticates/whitelists one identity (the message signer / `msgSender()` equivalent, here the JWT- or allowlist-authorized caller resolved by `ProcessRequest`), but the privileged action is scoped to a different, user-controlled identity field embedded in the request body (the RC `_user` parameter; here the `Owner` field of the secrets request).

In `HandleGatewayMessage`, authorization is performed generically per-method via `h.requestProcessor.ProcessRequest(ctx, req, publicKey)` [3](#0-2) , yielding an `AuthResult` that represents the identity that was actually verified/allowlisted. The dispatch to method handlers only forwards this `authResult` to `handleSecretsList`, which uses it to overwrite the request's `Owner` field before calling the secrets service — an explicit acknowledgment by the code authors that the `Owner` value must come from the verified identity, not from client input [4](#0-3) .

By contrast, `handleSecretsCreate` and `handleSecretsUpdate` unmarshal `vaultcommon.CreateSecretsRequest`/`UpdateSecretsRequest` directly from `req.Params` and pass them straight to `h.secretsService.CreateSecrets`/`UpdateSecrets` without ever consulting `authResult` [5](#0-4) , and `handleSecretsDelete` does the same for `DeleteSecretsRequest` [6](#0-5) . Note also that `handleSecretsCreate`/`handleSecretsUpdate`/`handleSecretsDelete` are never even passed the `authResult` variable in their function signature, unlike `handleSecretsList` [7](#0-6) , which structurally makes it impossible for those three handlers to bind the operation to the authenticated identity even if they wanted to.

This mirrors the Treasury bug precisely: whitelist/JWT authorization is enforced on the "sender" (the caller resolved via signature/JWT and returned as `AuthResult`), while the actual state-mutating action (creating/updating/deleting a secret "owned" by a particular identity) is driven by a caller-supplied field that is not cross-checked against that authenticated identity in this handler layer.

### Impact Explanation
If the downstream request pipeline (`vaultcommon.CreateSecretsRequest.Owner`/`UpdateSecretsRequest.Owner`/`DeleteSecretsRequest`'s identifiers) is not independently re-validated against `authResult.AuthorizedOwner()` elsewhere in `ProcessRequest`/`secretsService`, a caller authorized only for their own owner scope could create, overwrite, or delete secrets belonging to another owner by simply setting a different `Owner`/identifier value in the request payload — analogous to how a de-whitelisted or restricted RC user could keep crediting deposits to an arbitrary `_user` via a still-whitelisted `msgSender`. In the Vault context this could mean cross-tenant secret tampering or destructive deletion of another workflow/DON participant's secrets, which is a direct "unsafe transaction/workflow execution" / secret-disclosure-adjacent integrity issue in the vault trust boundary explicitly called out as in-scope.

### Likelihood Explanation
Reachability requires only that a caller pass `ProcessRequest`'s authorization/allowlist/JWT check for their own identity, then submit an `Owner` (or equivalent) value in `CreateSecretsRequest`/`UpdateSecretsRequest`/`DeleteSecretsRequest` params that differs from their authorized identity — this is a normal, unprivileged remote request through the standard `MethodSecretsCreate`/`Update`/`Delete` gateway RPC path, requiring no node compromise or malicious-operator assumption.

### Recommendation
Mirror the pattern already used in `handleSecretsList`: after `ProcessRequest` succeeds, explicitly set/overwrite the owner (or equivalent identity field) on `CreateSecretsRequest`, `UpdateSecretsRequest`, and `DeleteSecretsRequest` from `authResult.AuthorizedOwner()` before invoking `secretsService`, and pass `authResult` into `handleSecretsCreate`/`handleSecretsUpdate`/`handleSecretsDelete` so this binding is structurally enforced rather than optional. Alternatively/additionally, enforce this invariant centrally inside `GatewayVaultRequestProcessor.ProcessRequest` so no handler can bypass it by omission.

### Proof of Concept
Conceptual reachable path (exact behavior of downstream validation in `gateway_vault_request_processor.go`/`validator.go` was not fully confirmed within this investigation and should be verified before treating this as fully proven):
1. Caller A is authorized (allowlisted/JWT) for owner identity `A` and passes `ProcessRequest` for `MethodSecretsCreate`.
2. Caller A crafts `CreateSecretsRequest` JSON params with an `Owner`/identifier field set to victim `B`.
3. `handleSecretsCreate` unmarshals this request and calls `h.secretsService.CreateSecrets(ctx, &vaultCapRequest)` unchanged [8](#0-7) , without rebinding the owner to the authenticated identity the way `handleSecretsList` does [9](#0-8) .
4. If no other layer re-validates `Owner == authResult.AuthorizedOwner()`, the secret is created/updated/deleted under victim `B`'s identity by an unrelated authorized caller `A`.

func (h *GatewayHandler) handleSecretsCreate(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	vaultCapRequest := vaultcommon.CreateSecretsRequest{}
	if err := json.Unmarshal(*req.Params, &vaultCapRequest); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized create secrets request", "request", vaultCapRequest.String())
	vaultCapResponse, err := h.secretsService.CreateSecrets(ctx, &vaultCapRequest)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.FatalError, err)
	}

	jsonResponse, err := toJSONResponse(vaultCapResponse, req.Method)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}
	return jsonResponse
}

func (h *GatewayHandler) handleSecretsDelete(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.DeleteSecretsRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized delete secrets request", "request", r.String())
	resp, err := h.secretsService.DeleteSecrets(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to delete secrets: %w", err))
	}

	resultBytes, err := resp.ToJSONRPCResult()
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&resultBytes),
	}
}
