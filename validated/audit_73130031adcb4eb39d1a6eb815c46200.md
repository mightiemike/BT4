### Title
Missing voting-window enforcement in `vote-for-aggregate-public-key` allows the DKG aggregate key to be set outside its intended prepare-phase window - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
The `signers-voting.clar` contract defines a helper `is-in-voting-window` that is supposed to restrict voting for a reward cycle's aggregate public key to the correct window (the prepare phase of the cycle whose signer set was just finalized by `.signers`), but this helper is never invoked from `vote-for-aggregate-public-key`. As a result, the equality the protocol relies on — "a vote for `reward-cycle` is only valid while `reward-cycle` is the currently active (`last-set-cycle`) cycle and while the chain tip is within that cycle's prepare phase" — is never enforced on-chain.

### Finding Description
`is-in-voting-window` is defined as: [1](#0-0) 

and its doc comment on `vote-for-aggregate-public-key` explicitly states the intended invariant ("This vote must happen after the list of signers has been set... which occurs in the first block of the prepare phase"): [2](#0-1) 

However, the actual public function body only checks: (1) no key is already approved for `reward-cycle`, (2) the key is 33 bytes, (3) the key hasn't been used for another cycle, (4) the caller hasn't already voted in this `reward-cycle`/`round`, and (5) the round is incremented by at most 1: [3](#0-2) 

None of these checks call `is-in-voting-window`, nor do they verify `(is-eq reward-cycle (contract-call? .signers get-last-set-cycle))` or `(is-in-prepare-phase burn-block-height)`. The `.signers` contract never purges `cycle-signer-set` for old cycles, so `get-signer-by-index`/`get-signers` for a stale `reward-cycle` continue to resolve successfully long after that cycle's window has closed: [4](#0-3) 

This breaks the "signer weight below threshold or from the wrong set" equality: a vote can be cast, tallied, and (with sufficient cooperating weight) can finalize `aggregate-public-keys` for `reward-cycle` at any point after that cycle's signer set is fixed — including after the intended prepare-phase window has already elapsed, or after subsequent tenures/cycles have advanced — rather than being scoped to the single canonical window the rest of the node's Nakamoto signing logic assumes.

### Impact Explanation
The value read via `get-approved-aggregate-key` is consumed by node-side chainstate logic (referenced in `stackslib/src/chainstate/stacks/boot/mod.rs`) to determine the aggregate public key used to validate Nakamoto block signer signatures for a reward cycle. If the on-chain vote for a cycle's key can be finalized late (outside the prepare-phase window that miners/signers/nodes assume is the sole valid window), different participants of the network can end up disagreeing about which aggregate key is authoritative for that reward cycle at a given point in time — nodes that already began operating under an assumption that no key is set for the cycle vs. nodes that observe the key set post-hoc. This is a signer/validation-verdict divergence bounded to the affected reward cycle's block-signature verification, matching the in-scope "signer weight below threshold or from the wrong set" / "validation verdict two nodes disagree on" class.

### Likelihood Explanation
Triggering requires only that cooperating signers (who are otherwise unprivileged/ordinary signer-set members, not node operators or contract admins) submit `vote-for-aggregate-public-key` transactions for a `reward-cycle` value outside the currently-active `last-set-cycle`/prepare-phase window — nothing in the contract prevents this, since the intended guard (`is-in-voting-window`) is simply not wired in. No majority of stake/hashpower or any admin key is required to submit an out-of-window vote; only the normal signer-weight threshold (`threshold-consensus`) is needed to actually finalize a key, which is the protocol's own intended (weight-based) mechanism, not an extraneous majority assumption.

### Recommendation
Call `is-in-voting-window` (or equivalent explicit checks: `(is-eq reward-cycle (unwrap-panic (contract-call? .signers get-last-set-cycle)))` and `(is-in-prepare-phase burn-block-height)`) as an `asserts!` at the top of `vote-for-aggregate-public-key`, returning `ERR_OUT_OF_VOTING_WINDOW` when it fails, mirroring the ordering guarantee that the External Report recommends for `stopPredictAt < endTime` (i.e., enforce that the vote's `reward-cycle` matches the window in which it is cast).

### Proof of Concept
1. Reward cycle `N`'s signer set is finalized by the node calling `.signers` `set-signers` at the start of cycle `N-1`'s prepare phase, setting `last-set-cycle = N`, populating `cycle-signer-set[N]`. [5](#0-4) 
2. The prepare phase for cycle `N` ends and `last-set-cycle` subsequently advances to `N+1` after the next `set-signers` call, but `cycle-signer-set[N]` is never removed.
3. If consensus was not reached for `reward-cycle = N` during its correct window (no entry in `aggregate-public-keys` map for `N`), any signer that was part of `cycle-signer-set[N]` can still call `vote-for-aggregate-public-key` with `reward-cycle = N` at an arbitrary later block height — `is-in-voting-window` is never checked, and `get-signer-weight`/`get-and-cache-total-weight` still resolve successfully against the stale `N` set. [6](#0-5) 
4. Given sufficient cooperating weight from that stale signer set, `aggregate-public-keys[N]` can be finalized long after cycle `N`'s intended window, producing a late/out-of-window key that nodes must reconcile against blocks already processed for cycle `N` under the assumption that no key (or a different key) applied.

;; Signer vote for the aggregate public key of the next reward cycle
;;  Each signer votes for the aggregate public key for the next reward cycle.
;;  This vote must happen after the list of signers has been set by the node,
;;  which occurs in the first block of the prepare phase. The vote is concluded
;;  when the threshold of `threshold-consensus / 1000` is reached for a
;;  specific aggregate public key. The vote is weighted by the amount of
;;  reward slots that the signer controls in the next reward cycle. The vote
;;  may require multiple rounds to reach consensus, but once consensus is
;;  reached, later rounds will be ignored.
;;
;;  Arguments:
;;   * signer-index: the index of the calling signer in the signer set (from
;;     `get-signers` in the .signers contract)
;;   * key: the aggregate public key that this vote is in support of
;;   * round: the voting round for which this vote is intended
;;   * reward-cycle: the reward cycle for which this vote is intended
;;  Returns:
;;   * `(ok true)` if the vote was successful
;;   * `(err <code>)` if the vote was not successful (see errors above)
(define-public (vote-for-aggregate-public-key (signer-index uint) (key (buff 33)) (round uint) (reward-cycle uint))
    (let ((tally-key {reward-cycle: reward-cycle, round: round, aggregate-public-key: key})
            ;; vote by signer weight
            (signer-weight (try! (get-signer-weight signer-index reward-cycle)))
            (new-total (+ signer-weight (default-to u0 (map-get? tally tally-key))))
            (cached-weight (try! (get-and-cache-total-weight reward-cycle)))
            (threshold-weight (get-threshold-weight reward-cycle))
            (current-round (default-to {
                votes-count: u0, 
                votes-weight: u0} (map-get? round-data {reward-cycle: reward-cycle, round: round})))
                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
        ;; Check that the aggregate public key is the correct length
        (asserts! (is-eq (len key) u33) (err ERR_ILL_FORMED_AGGREGATE_PUBLIC_KEY))
        ;; Check that aggregate public key has not been used in a previous reward cycle
        (asserts! (is-novel-aggregate-public-key key reward-cycle) (err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY))
        ;; Check that signer hasn't voted in this reward-cycle & round
        (asserts! (map-insert votes {reward-cycle: reward-cycle, round: round, signer: tx-sender} {aggregate-public-key: key, signer-weight: signer-weight}) (err ERR_DUPLICATE_VOTE))
        ;; Check that the round is incremented by at most 1
        (try! (update-last-round reward-cycle round))
        ;; Update the tally for this aggregate public key candidate
        (map-set tally tally-key new-total)
        ;; Update the current round data
        (map-set round-data {reward-cycle: reward-cycle, round: round} {
            votes-count: (+ (get votes-count current-round) u1),
            votes-weight: (+ (get votes-weight current-round) signer-weight)})
