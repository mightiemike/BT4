### Title
Lack of event/audit-log emission after sensitive vault secret write operations (CreateSecrets/UpdateSecrets/DeleteSecrets) - (File: core/services/ocr2/plugins/vault/plugin.go)

### Summary
The vault OCR3 reporting plugin's `stateTransitionCreateSecretsRequest`, `stateTransitionUpdateSecretsRequest`, and the corresponding delete-secrets state transition write/overwrite/remove encrypted workflow secrets in the on-node key-value store as a direct, consensus-approved consequence of unprivileged workflow-owner requests, but emit no audit/event record of the action — only a `Debugw` log line. This mirrors the reported bug class (sensitive state mutations with no emitted event), which prevents downstream observability/tracking of who changed which secret and when.

### Finding Description
`stateTransitionCreateSecretsRequest` and `stateTransitionUpdateSecretsRequest` perform the sensitive action of persisting an encrypted secret value into the KV store via `store.WriteSecret(...)`: [1](#0-0) [2](#0-1) 

After a successful write, the only trace left behind is a `Debugw` log statement emitted by the caller functions `stateTransitionCreateSecrets` / `stateTransitionUpdateSecrets`: [3](#0-2) [4](#0-3) 

No call to the node's `audit.AuditLogger` (the exact mechanism the codebase uses elsewhere for sensitive actions such as key create/import/export/delete) is made anywhere in `core/services/ocr2/plugins/vault/plugin.go`, confirmed by the audit-logger usage search returning zero hits in that file, versus consistent instrumentation for comparable sensitive actions in the HTTP/GraphQL layer: [5](#0-4) [6](#0-5) [7](#0-6) 

This is structurally identical to the reported bug class: sensitive state changes (`fundingRate`, `updateTime`, reward transfer in the original UMA report; here, `EncryptedSecret` value writes/overwrites) occur without any accompanying event/audit signal that off-chain or operator-facing tooling could subscribe to for tracking and alerting.

### Impact Explanation
Because vault secret creations/updates are only debug-logged and never audited, node operators and any downstream monitoring/alerting pipeline built on the `audit.AuditLogger` (e.g. `AUDIT_LOGGER_FORWARD_TO_URL`) have no visibility into workflow-secret create/update/delete events. This weakens the ability to detect anomalous or unauthorized secret mutation patterns (e.g., a compromised workflow owner rapidly overwriting many secrets, or unexpected deletion activity) and to reconstruct an audit trail after an incident. It does not directly cause fund loss or bypass consensus/authorization checks (the plugin's own request validation still gates writes), so the impact is best characterized as an observability/detection gap rather than a direct compromise.

### Likelihood Explanation
Every legitimate CreateSecrets/UpdateSecrets (and by symmetry DeleteSecrets) request that reaches OCR consensus triggers this code path, so the missing-event condition is deterministic and always occurs — it is not conditional on an edge case. The likelihood that this matters operationally is therefore high whenever an operator wants to audit or alert on vault secret changes.

### Recommendation
Add an audit-log (or equivalent structured event) emission alongside/after the `store.WriteSecret` / delete-secret calls in `stateTransitionCreateSecretsRequest`, `stateTransitionUpdateSecretsRequest`, and the delete-secrets state-transition path in `core/services/ocr2/plugins/vault/plugin.go`, following the existing `audit.AuditLogger.Audit(...)` pattern used by `core/web/keys_controller.go` and `core/web/csa_keys_controller.go`. Include identifying, non-sensitive metadata (e.g., secret `Owner`, `Namespace`, `Key`, request ID, sequence number) — never the encrypted/decrypted secret value itself — so operators can track "who/what/when" without leaking sensitive material. Define new `EventID` constants (e.g., `VaultSecretCreated`, `VaultSecretUpdated`, `VaultSecretDeleted`) in `core/logger/audit/audit_types.go` for consistency with existing sensitive-action event naming.

### Proof of Concept
Not applicable as an executable PoC — this is an observability/logging-gap finding, not an exploitable state-corruption or auth-bypass bug. The absence of instrumentation can be verified statically: `grep`-ing `core/services/ocr2/plugins/vault/plugin.go` for `auditLogger`/`AuditLogger` returns no matches, while the successful-write code paths (`stateTransitionCreateSecretsRequest` line 2228-2233, `stateTransitionUpdateSecretsRequest` line 2332-2337) execute unconditionally on every successful consensus-approved secret create/update, with only a `Debugw` log call as the sole trace of the action.

**Uncertainty note:** I was unable to fully confirm the exact implementation of the `stateTransitionDeleteSecrets`/`stateTransitionDeleteSecretsRequest` function bodies within the available iteration budget (grep confirmed their existence in `plugin.go`, but I did not retrieve their full source lines), so the finding for the delete path is inferred from the consistent absence-of-audit-logging pattern in the file rather than a direct line-level citation.

// Example:
// "POST <application>/keys/csa"
func (ctrl *CSAKeysController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	key, err := ctrl.App.GetKeyStore().CSA().Create(ctx)
	if err != nil {
		if errors.Is(err, keystore.ErrCSAKeyExists) {
			jsonAPIError(c, http.StatusBadRequest, err)
			return
		}

		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	ctrl.App.GetAuditLogger().Audit(audit.CSAKeyCreated, map[string]any{
		"CSAPublicKey": key.PublicKey,
		"CSVersion":    key.Version,
	})

	jsonAPIResponse(c, presenters.NewCSAKeyResource(key), "csaKeys")
}
