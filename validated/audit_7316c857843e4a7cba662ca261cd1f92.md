### Title
Dev-only `/v2/execute_capability` endpoint lets any run-role user directly invoke `capability.Execute` with forged workflow metadata, bypassing DON-binding checks - ([File: core/web/capability_controller.go])

### Summary
The `CapabilityController.ExecuteCapability` handler, mounted only when `build.IsDev()` is true, is guarded solely by `auth.RequiresRunRole` and calls `capability.Execute(ctx, capabilityRequest)` directly on whatever `ExecutableCapability` is returned by `capabilityRegistry.GetExecutable(name)`. The attacker fully controls `CapabilityRequest.Metadata` (including `WorkflowID`, `WorkflowOwner`, `WorkflowDonID`) via the unauthenticated-content `CapabilityRequest` protobuf bytes, and this path never passes through the `workflowDONBindingGate` check that exists specifically to prevent this kind of spoofing.

### Finding Description
`ExecuteCapability` binds `CapabilityRequestOuter{CapabilityName, CapabilityRequest []byte}` from the JSON body, looks up the named capability via `capabilityRegistry.GetExecutable(ctx, capabilityRequestOuter.CapabilityName)`, unmarshals the raw bytes into a `capabilities.CapabilityRequest` via `pb.UnmarshalCapabilityRequest`, and calls `capability.Execute(ctx, capabilityRequest)` — all attacker-supplied except for the outer HTTP auth check. [1](#0-0) 

Route registration confirms the only gate is `auth.RequiresRunRole` and the feature is limited to dev builds: [2](#0-1) 

`RequiresRunRole` only checks that the authenticated user's role is not `UserRoleView` — it applies to any logged-in operator/run-role token holder, not just admins, and performs no capability-, workflow-, or DON-specific authorization: [3](#0-2) 

The real workflow/DON binding protection (`workflowDONBindingGate`) exists only in the remote P2P executable-capability server path, which validates that `capabilityRequest.Metadata.WorkflowDonID` matches the authenticated calling DON before invoking `capability.Execute`: [4](#0-3) 

That check is entirely bypassed by the HTTP `ExecuteCapability` path because it calls `capability.Execute` directly rather than routing through `executeCapabilityRequest`/`ServerRequest`/`server.go`, which are the only components wired to `workflowDONBindingGate`. Nothing in `capability_controller.go` verifies that `Metadata.WorkflowID`/`WorkflowOwner`/`WorkflowDonID` correspond to any workflow actually owned by the authenticated session — those fields are taken verbatim from attacker-supplied protobuf bytes. This confirms the exact mechanism the question described: `GetExecutable` returns the underlying `capabilities.ExecutableCapability` (e.g., local target/vault/write capability implementations), and `Execute` is invoked with a caller-controlled `RequestMetadata` blob that downstream code (e.g. `secretsFetcher.vaultGetSecretsMetadata`, `ExecutionHelper.callCapability`) normally populates from an authenticated workflow-engine context rather than from raw user input. [5](#0-4) [6](#0-5) 

The unit test in the repo confirms this exact call pattern works with no additional binding check: an `ExecutableCapability` mock's `Execute` is invoked directly by the controller with an attacker-supplied `capabilities.CapabilityRequest`. [7](#0-6) 

### Impact Explanation
On a dev build, any authenticated run-role (non-view) user — which is a low privilege tier, well short of admin — can execute any capability registered in the node's local `CapabilitiesRegistry`, including privileged executable capabilities (e.g., vault/confidential-workflow capability, write-chain/write-report targets), while forging the `WorkflowID`/`WorkflowOwner`/`WorkflowDonID` in the request metadata. This can lead to unauthorized capability/workflow execution, and depending on the capability implementation, potential secret disclosure or unauthorized transaction/report execution impersonating an arbitrary workflow/owner. The impact is scoped to dev builds only (`build.IsDev()` gate), which limits real-world production exposure but is a genuine authz-bypass bug in the dev tooling code path that could be exploited if dev builds/config (`Insecure.DevWebServer`-style flags) are ever deployed or misconfigured in a shared environment.

### Likelihood Explanation
Preconditions: node built with `build.IsDev()==true` and the attacker possesses any valid run-role session or API token (a low bar — run-role is one of the lowest privileged authenticated roles, above view-only). Given these preconditions, exploitation is trivial and fully reproducible: a single HTTP POST to `/v2/execute_capability` with a crafted `CapabilityRequestOuter` triggers the bypass deterministically every time, with no rate-limiting, replay-protection, or metadata-validation obstacles in the handler itself.

### Recommendation
Route `ExecuteCapability` through the same binding/authorization checks used by the remote executable path (validate `Metadata.WorkflowID`/`WorkflowOwner`/`WorkflowDonID` against the authenticated caller's own workflow context, or require an explicit admin-only, non-forgeable debug credential), or restrict the endpoint to genuinely local/loopback-only debug tooling and never allow the raw `CapabilityRequestOuter.CapabilityRequest` metadata to be trusted from an ordinary web session role. At minimum, gate execution of remote/DON-bound capabilities behind the same `workflowDONBindingGate` semantics, and require `RequiresAdminRole` (not `RequiresRunRole`) for this dev-only endpoint.

### Proof of Concept
Integration test plan:
1. Build/run node with `build.IsDev()` true (or run existing `TestCapabilityController_ExecuteCapability` harness) and register a mock `ExecutableCapability` (or the real vault/confidential-workflow capability) in `CapabilitiesRegistry` under a known name.
2. Create a session/API token with `UserRoleRun` only (no edit/admin privileges).
3. POST `/v2/execute_capability` with `CapabilityRequestOuter{CapabilityName: "<privileged-capability-id>", CapabilityRequest: pb.MarshalCapabilityRequest(CapabilityRequest{Metadata: RequestMetadata{WorkflowID: "victim-workflow", WorkflowOwner: "victim-owner", WorkflowDonID: 999}, ...})}`.
4. Assert response is `200 OK` and the underlying capability's `Execute` was invoked with the forged `Metadata` (as already demonstrated by `TestCapabilityController_ExecuteCapability_MissingRequiredFields`/`TestCapabilityController_ExecuteCapability`), and that no `workflowDONBindingGate`-style check rejected the mismatched `WorkflowDonID`, unlike in `Test_ServerRequest_WorkflowDONBinding` where a mismatched `WorkflowDonID` is rejected when the gate is enabled.
5. Expected (fixed) behavior: the request should be rejected unless the caller's authenticated session/workflow context matches the supplied `Metadata`, or the endpoint should require `RequiresAdminRole`.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func executeCapabilityRequest(ctx context.Context, lggr logger.Logger, capability capabilities.ExecutableCapability, payload []byte, callingDonID uint32, workflowDONBindingGate limits.GateLimiter) ([]byte, error) {
	capabilityRequest, err := pb.UnmarshalCapabilityRequest(payload)
	if err != nil {
		lggr.Errorw("failed to unmarshal capability request", "err", err)

		// Do not include the unmarshal error in the response as it may contain sensitive information
		return nil, errors.New("failed to unmarshal capability request")
	}

	// When enabled, bind the caller-supplied WorkflowDonID to the authenticated
	// calling DON so it cannot be spoofed. All F+1 aggregated requests share this
	// payload (WorkflowDonID is part of the request hash), so a single check here
	// covers the quorum. The gate is guaranteed non-nil by NewServerRequest.
	enabled, gerr := workflowDONBindingGate.Limit(ctx)
	if gerr != nil {
		lggr.Errorw("failed to evaluate workflow DON binding gate", "err", gerr)
		return nil, errors.New("failed to evaluate workflow DON binding gate")
	}
	if enabled && capabilityRequest.Metadata.WorkflowDonID != callingDonID {
		lggr.Errorw("workflow DON ID in request metadata does not match calling DON",
			"metadataWorkflowDonID", capabilityRequest.Metadata.WorkflowDonID, "callingDonID", callingDonID)
		return nil, fmt.Errorf("workflow DON ID %d in request metadata does not match calling DON ID %d",
			capabilityRequest.Metadata.WorkflowDonID, callingDonID)
	}
