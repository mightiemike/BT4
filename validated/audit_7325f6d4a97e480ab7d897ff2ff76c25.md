This is a confirmed, publicly-tracked bug in nearcore (issue #12606) that is directly analogous to CVE-2021-41531: an unprivileged contract call can cause a value (receipt size / max-length equivalent) to exceed the protocol's declared bound, producing state that downstream validation logic must special-case rather than reject, exactly like an oversized ROA `max-length` producing invalid RTR payload that routers must reject/mishandle.

### Title
Receipts Can Be Created Above `max_receipt_size` via `output_data_receivers`/Return-Value Growth, Bypassing `ReceiptSizeExceeded` Validation - ([File: runtime/runtime/src/lib.rs])

### Summary
`validate_receipt` in `ValidateReceiptMode::NewReceipt` mode enforces that a freshly created receipt's borsh-serialized size does not exceed `max_receipt_size` [1](#0-0) . However, this check runs immediately after `apply_action` produces a receipt, before the runtime appends `output_data_receivers` or attaches a returned value from a subsequent promise callback [2](#0-1) . A contract can therefore create a receipt that measures exactly at `max_receipt_size` when validated, then have the runtime append additional `output_data_receivers` entries or a large returned value afterward, pushing the final serialized receipt above the configured limit without any further validation catching it.

### Finding Description
The `ValidateReceiptMode` enum explicitly documents this as a known, unfixed bug (tracked as nearcore issue #12606): "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed." [3](#0-2) 

Concretely, an oversized receipt can be produced by an unprivileged contract call in at least two ways, both exercised in the repo's own regression tests:
- A promise callback whose receipt is exactly `max_receipt_size` at creation time, but which is subsequently mutated to add `output_data_receivers`, pushing it over the limit [4](#0-3) 
- A contract returning a value close to `max_receipt_size`, which gets wrapped into a `Data` receipt that then exceeds the limit [5](#0-4) 

Once such an oversized receipt exists, it propagates through cross-shard forwarding and the bandwidth scheduler, both of which contain explicit "pretend it's `max_receipt_size`" workarounds rather than rejecting the oversized value:
- `try_forward` clamps the receipt's `size` to `max_receipt_size` purely for the purpose of comparing against the outgoing bandwidth limit, explicitly citing issue #12606 [6](#0-5) 
- `generate_bandwidth_request` clamps buffered receipt group sizes to `max_receipt_size` when building bandwidth requests, for the same reason [7](#0-6) 
- Incoming receipts on the receiving shard are validated with `ValidateReceiptMode::ExistingReceipt`, which deliberately skips the size check to "handle them gracefully" instead of rejecting [8](#0-7) 

This is the direct analog of CVE-2021-41531: just as an RPKI CA could set an oversized `max-length` value in a ROA that Routinator would faithfully encode into RTR payload, exceeding the RTR protocol's own size assumptions and causing routers to reject the feed — here an unprivileged contract can cause the runtime to construct a receipt whose true size exceeds the protocol's own `max_receipt_size` bound, and every downstream consumer (bandwidth scheduler, congestion control, cross-shard forwarding) has to special-case and "pretend" the value fits rather than being able to trust the declared limit.

### Impact Explanation
The `max_receipt_size` bound is a hard limit meant to cap `ChunkStateWitness` size (documented at 4 MiB, contributing to the ~17 MiB total witness budget) [9](#0-8) . An oversized receipt violates this budget and requires ad-hoc clamping logic scattered across `congestion_control.rs` to avoid the receipt getting permanently stuck in the outgoing buffer [10](#0-9) . Because the bug is a documented, accepted workaround rather than a rejection, it represents a persistent gap between the declared protocol invariant (`max_receipt_size`) and the actual data nodes must process, which is exactly the "invalid RTR payload accepted downstream instead of rejected" bug class from the CVE.

### Likelihood Explanation
This is triggerable by any account with a deployed contract issuing ordinary cross-contract call patterns (promise chaining with `promise_return`, or returning large values from a callback) — no special privileges, validator status, or network position are required, as demonstrated by the repository's own `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` tests [11](#0-10) .

### Recommendation
Re-validate receipt size (and other `NewReceipt`-mode checks) after all post-`apply_action` mutations to the receipt — specifically after `output_data_receivers` are attached and after return-value-derived `Data` receipts are constructed — so that `ReceiptSizeExceeded` is enforced against the true final serialized size before the receipt is committed to `new_receipts`, closing the gap tracked as issue #12606 instead of continuing to clamp downstream consumers.

### Proof of Concept
Reuse the repository's own reproduction, e.g. `test_max_receipt_size_promise_return` [12](#0-11) : deploy `near_test_contracts::rs_contract()`, then call `max_receipt_size_promise_return_method1` with `args_size` sized so the intermediate promise-return receipt sits exactly at `max_receipt_size`; the subsequent `output_data_receivers` attachment pushes it over the limit, and `assert_oversized_receipt_occurred` confirms an incoming receipt above `max_receipt_size` appears on-chain [13](#0-12) .

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
