Based on my investigation, I found a genuine analog: `AddressRegistrar::register` in the `near-wallet-contract` package accepts a `#[payable]` deposit but does not refund the excess over the required storage cost on the success path.

### Title
Excess attached deposit is not refunded on successful `register` in AddressRegistrar contract - (File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs)

### Summary
The `register` function of the `AddressRegistrar` contract (part of the eth-implicit-account wallet contract system) is marked `#[payable]` and only refunds the caller's attached deposit in the collision (`Entry::Occupied`) branch. On the success path (`Entry::Vacant`), any deposit amount above the computed `required_deposit` for storage is silently retained by the contract with no code path to withdraw or credit it back to the caller.

### Finding Description
`register` computes `required_deposit` from the storage bytes needed and compares it to `env::attached_deposit()` (`given_deposit`), rejecting the call if insufficient [1](#0-0) . If `given_deposit` exceeds `required_deposit`, however, the vacant-entry branch inserts the mapping and returns without refunding the difference: [2](#0-1) . Only the occupied-entry (collision) branch issues a refund of the *entire* given deposit via a promise batch transfer back to `predecessor_account_id` [3](#0-2) . There is no method on `AddressRegistrar` to later withdraw or reclaim this excess balance — `lookup` and `get_address` are read-only [4](#0-3) , and no owner/admin withdraw method exists in this contract.

This is invoked from the `WalletContract::rlp_execute` flow (`nep_141_storage_balance_callback`/`address_check_callback`), which is itself `#[payable]` and forwards deposits through cross-contract calls to the registrar as part of eth-transaction relaying [5](#0-4) .

### Impact Explanation
Any unprivileged transaction signer / RPC caller who attaches more than the exact required storage deposit when calling `register` (directly, or indirectly via a relayer through the wallet contract's rlp-execute path) will have the excess yoctoNEAR permanently locked in the `AddressRegistrar` contract's balance with no on-chain mechanism to retrieve it. This is a concrete, transaction-triggered case of permanently frozen user funds, matching the "payable keyword misuse causing stuck funds" bug class from the source report, mapped onto a real fund-loss path reachable by any caller submitting a transaction to this contract.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: callers (especially automated relayers building batched actions, as seen in `nep_141_storage_balance_callback`) often attach round/conservative deposit amounts rather than computing the exact storage byte cost, so overpayment on a successful (non-colliding) `register` call is a normal, easily triggered scenario requiring only a single transaction with no special privileges.

### Recommendation
In the `Entry::Vacant` success branch of `register`, compute the excess (`given_deposit - required_deposit`) and refund it to `predecessor_account_id` via a promise batch transfer, mirroring the refund logic already present in the `Entry::Occupied` branch, so only the exact storage cost is retained.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `new()`.
2. As any account, call `register(account_id)` attaching a deposit significantly larger than `storage_byte_cost() * (20 + account_id.len())` (e.g. 1 NEAR when only a few hundred yoctoNEAR-scaled bytes are required).
3. Observe the call succeeds (`Entry::Vacant` path), the mapping is inserted, and `Some(address)` is returned — but no refund promise is created (unlike the collision path) at [2](#0-1) .
4. Query the caller's account balance before/after: the caller's balance drops by the full attached deposit, not just `required_deposit`, and the `AddressRegistrar` contract's balance increases by the excess with no corresponding entry point to spend or return it.

    /// Attempt to look up the account ID associated with the given address.
    /// If an entry for that address is found then the associated account id
    /// is returned, otherwise `None` is returned. Use the `register` method
    /// to add entries to the map.
    /// This function will panic if the given address is not the hex-encoding
    /// of a 20-byte array. The `0x` prefix is optional.
    pub fn lookup(&self, address: String) -> Option<AccountId> {
        let address = {
            let mut buf = [0u8; 20];
            hex::decode_to_slice(address.strip_prefix("0x").unwrap_or(&address), &mut buf)
                .unwrap_or_else(|_| env::panic_str("Invalid hex encoding"));
            buf
        };
        self.addresses.get(&address).cloned()
    }

    /// Computes the address associated with the given `account_id` and
    /// returns it as a hex-encoded string with `0x` prefix. This function
    /// does not update the mapping stored in this contract. If you want
    /// to register an account ID use the `register` method.
    pub fn get_address(&self, account_id: AccountId) -> String {
        let address = account_id_to_address(&account_id);
        format!("0x{}", hex::encode(address))
    }
