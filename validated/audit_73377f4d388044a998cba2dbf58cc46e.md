### Title
Relayer fee refund is paid unconditionally before the underlying action executes, regardless of whether that action succeeds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In `inner_rlp_execute`, when an emulated `EOABaseTokenTransfer` or `ERC20Transfer` includes a non-zero relayer `fee`, the contract immediately schedules a NEAR transfer of `fee` to the relayer (`context.predecessor_account_id`) as an independent receipt, before the actual transfer/`ft_transfer` action has been attempted or has resolved. This mirrors the reported bug class: a caller/relayer is compensated based on a *requested* value rather than the *actual outcome* of the downstream operation, so the relayer is paid even when the withdrawal/transfer it is being compensated for silently fails.

### Finding Description
`inner_rlp_execute` parses the relayer-submitted Ethereum-emulated transaction and, for `EOABaseTokenTransfer`/`ERC20Transfer` with non-zero `fee`, does: [1](#0-0) 
This `env::promise_batch_create(&context.predecessor_account_id)` / `promise_batch_action_transfer` call is fired off as an unchained, independent receipt at parse time — it is not `.then()`-chained to, or made contingent on, the outcome of the actual value-moving action (the base-token `Transfer` or the `ft_transfer` `FunctionCall`) that is constructed later in the same function and sent through `rlp_execute_callback`: [2](#0-1) 
The eventual success/failure of that action is only checked afterward in `rlp_execute_callback`, which refunds the *caller's deposit* on failure but has no mechanism to claw back or cancel the relayer fee that was already dispatched as a separate, already-committed receipt: [3](#0-2) 
This is directly analogous to the reported Solidity bug: the "callback" for the actual value transfer (here, the NEP-141 `ft_transfer` or NEAR `Transfer`) can fail or be effectively a no-op (e.g., insufficient balance causing `ft_transfer` promise `Failed`, or the ERC20 receiver not being registered and consuming the deposit in `storage_deposit` first), yet a separate, unconditional payment (the relayer `fee`) has already been dispatched based on the *requested* fee amount, irrespective of whether the compensated action actually completed.

### Impact Explanation
A relayer can be paid its fee for relaying a transaction whose underlying ERC-20/base-token transfer fails on-chain (e.g., `ft_transfer` fails due to insufficient token balance, receiver registration issues, or gas exhaustion in the second leg of the promise chain). This causes unauthorized value movement: the user's wallet contract account pays out NEAR to the relayer without the corresponding action (that the fee was meant to compensate) ever completing successfully. Because the fee transfer happens unconditionally and outside of the success-checking `rlp_execute_callback` logic, there is no state consistency between "did the underlying transaction succeed" and "was the relayer paid," resulting in value leaving the account balance sheet without a corresponding successful state transition — a real, sole-signer-reachable value-movement bug.

### Likelihood Explanation
This path is reachable by any relayer that is authorized to submit `rlp_execute` calls (which is the intended, permissionless design of the wallet contract — any relayer can serve any wallet, per the code comments). No privileged or validator role is required; a normal transaction signer/relayer triggers this simply by submitting an `rlp_execute` call with a non-zero fee for a transfer that they know (or cause) will fail downstream (e.g. by racing token balance changes, or by using a target contract with unusual storage/registration requirements that make the second `function_call` in the promise chain fail). This makes exploitation straightforward and does not require any adversarial network or validator behavior.

### Recommendation
Chain the relayer-fee transfer to the outcome of the main action instead of dispatching it independently and unconditionally. Concretely:
- Move fee-refund logic so it is scheduled only after (i.e. `.then()`-chained on top of) the promise for the actual `Transfer`/`ft_transfer` action, checking `PromiseResult::Successful` before creating the fee-transfer batch action — similar to how `rlp_execute_callback` already conditionally refunds `caller_deposit` only in the `Failed` branch.
- Alternatively, extend `rlp_execute_callback` (and `nep_141_storage_balance_callback`) to accept the pending fee amount, and only issue the relayer-fee transfer there once the underlying action's `PromiseResult` is confirmed `Successful`.

### Proof of Concept
1. A relayer (any unprivileged account) submits `rlp_execute(target, tx_bytes_b64)` to a user's eth-implicit wallet contract account, encoding an `ERC20Transfer` (`ft_transfer`) with a non-zero `fee`.
2. `inner_rlp_execute` immediately creates and dispatches an independent NEAR transfer receipt of `fee` to the relayer's account: [1](#0-0) 
3. The subsequent multi-step promise chain (`storage_balance_of` → optional `storage_deposit` → `ft_transfer` → `rlp_execute_callback`) then executes; if the token contract's `ft_transfer` fails (e.g., insufficient FT balance, malicious/misbehaving token contract, or gas exhaustion in the chained function calls), `rlp_execute_callback` returns `success: false` and only refunds the caller's `NEAR` deposit — it has no way to reverse the relayer fee already paid in step 2: [3](#0-2) 
4. Net effect: the relayer receives `fee` in NEAR even though the compensated `ft_transfer` never completed, an unauthorized value transfer out of the wallet-contract account.
