### Title
Historical resource JSON decoding uses the latest module layout instead of the `ledger_version`-scoped layout, corrupting returned `MoveResource` field values - (File: `api/src/accounts.rs`)

### Summary
`Account::resources` (JSON path) fetches raw resource bytes at the caller-supplied `self.ledger_version`, but builds the BCS→JSON `MoveConverter` from `self.context.latest_state_view_poem(...)`, i.e. the *current* state, not a state view pinned to `ledger_version`. Struct layout resolution (module bytecode lookup for annotation) therefore always reflects the latest on-chain module version, even when the raw bytes being decoded were committed under an older module layout.

### Finding Description
In `api/src/accounts.rs`, `resources()`:
- Retrieves the raw, version-scoped resource bytes via `self.context.get_resources_by_pagination(..., self.ledger_version, ...)`, which correctly reads from `state_view_at_version(version)` internally (see `Context::get_resources_by_pagination`, `api/src/context.rs:511`, which does use `self.state_view_at_version(version)` for its own resource-group flattening).
- For JSON responses, it obtains a *different* state view: `self.context.latest_state_view_poem(&self.latest_ledger_info)` (`api/src/accounts.rs:476-478`), and builds `converter.try_into_resources(...)` from that state view. [1](#0-0) 

The `MoveConverter`/`AptosValueAnnotator` uses the provided `StateView` (`S`) to resolve module bytecode when annotating/decoding BCS bytes into typed JSON values (struct field names, types, layouts come from the module's current definition as seen through that view). Because the view here is `latest_state_view_poem`, not a view scoped to `ledger_version`, if the resource's defining module was upgraded (struct layout changed: field added/removed/reordered/retyped) between `ledger_version` and the current chain tip, the converter interprets the old raw bytes using the new struct layout. [2](#0-1) [3](#0-2) 

This directly contradicts the invariant that decoded fields must match the byte layout committed at `ledger_version`: `get_account_resource`/`get_resources_by_pagination` correctly reads raw bytes at the historical version, but the "decode to JSON" phase silently swaps in a state view bound to the latest version for its module/layout resolver.

### Impact Explanation
Any unauthenticated client calling `GET /accounts/:address/resources?ledger_version=<historical>` (or the equivalent single-resource endpoint that goes through the same converter pattern) against an account whose resource module was upgraded after that version will receive a `MoveResource` JSON body whose field names/types/values are computed under the wrong (newer) struct layout. This can silently corrupt or misrepresent historical state to any consumer trusting the authenticated API response for a specific `ledger_version` — e.g. auditors, indexers, or off-chain systems reconstructing historical account state, bridges/exchanges validating point-in-time balances, or governance/compliance tooling. Depending on how field types changed (e.g. u64 reinterpreted as a vector, or a moved/reordered field), decoding can produce entirely wrong values, decoding errors, or type-confused misleading data, all returned with a 200 OK bound to the requested (correct) ledger version/root, which is precisely the "authenticated response bound to the wrong version/object" class of defect.

### Likelihood Explanation
This is reachable by any unauthenticated caller with a single GET request and no special privileges — it only requires a historical `ledger_version` and a module that has since been upgraded (which happens routinely for both Aptos framework modules and third-party packages). No consensus, storage corruption, or trusted-operator error is needed; the request path (`get_resources_by_pagination` → JSON branch → `latest_state_view_poem`) is exercised on every default JSON request against `/accounts/:address/resources` with a historical `ledger_version` query parameter.

### Recommendation
Build the JSON converter's `StateView` from a version-scoped view (e.g. `self.context.state_view_at_version(self.ledger_version)` or an equivalent `db.state_view_at_version(Some(self.ledger_version))` poem-wrapped helper) instead of `latest_state_view_poem`, mirroring what `get_resources_by_pagination` already does internally for resource-group flattening. Apply the same fix to any other resource/module JSON conversion call sites in `api/src/accounts.rs`, `api/src/transactions.rs`, `api/src/view_function.rs`, etc. that similarly pair a `ledger_version`-scoped raw read with a `latest_state_view_poem`-based converter.

### Proof of Concept
1. Publish a package defining `struct Foo has key { a: u64 }` under account `0xA`, initialize a `Foo` resource, note the version `V1`.
2. Upgrade the module: change `Foo` layout to `struct Foo has key { b: vector<u8>, a: u64 }` (compatible upgrade for storage but changes decode layout/order), publish new module version at version `V2 > V1`.
3. Call `GET /v1/accounts/0xA/resources?ledger_version=V1`.
4. Compare the JSON `MoveResource` for `Foo` against the expected V1 layout (`{ "a": <value> }`). Because `resources()` uses `latest_state_view_poem` for conversion, the response will attempt to decode the V1 bytes using the V2 struct definition (`{ "b": ..., "a": ... }`), producing corrupted/incorrect field values or a decode error, instead of the byte-accurate V1-scoped representation.
