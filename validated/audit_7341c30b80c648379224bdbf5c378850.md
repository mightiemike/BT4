This confirms the analog exists: `VoteTssKeyProcess` immediately flips `CurrentTssKey` to the new pubkey the moment quorum passes [1](#0-0) , while outbound signing on `x/utss`'s external-chain vaults still holds funds at the *old* key's address until an admin separately runs `MsgInitiateFundMigration` per chain [2](#0-1) . In between, ordinary user-triggered outbound creation (from a normal inbound/payload) is signed with the **current** key only — `createSignSetup`/`GetCurrentKey` never consult `TssKeyHistory` for “does the vault under this address actually hold the funds” [3](#0-2) , and `verifyingPubkey` likewise always uses the current key for `SIGN_OUTBOUND` [4](#0-3) .

### Title
Outbound signing binds to the new TSS key immediately on KEYGEN finalization while vault funds remain under the old key until admin-driven migration completes - (File: x/utss/keeper/msg_vote_tss_key_process.go, universalClient/tss/coordinator/coordinator.go)

### Summary
This is the Push Chain analog of the Trail of Bits "partial refinancing" bug: an operation (KEYGEN) atomically flips the canonical "current provider" (`CurrentTssKey`) on Push Chain, but the actual balance move to the new provider (external-chain vault funds) is a separate, per-chain, admin-gated, asynchronous step (`FundMigration`). Any outbound created by ordinary user activity in the gap between key finalization and completed migration is signed against the new key/address, which may hold zero balance on that external chain.

### Finding Description
`VoteTssKeyProcess` finalizes a `KEYGEN` process and writes the new key to `CurrentTssKey` synchronously with the ballot reaching quorum [1](#0-0) . From that block onward, every outbound-signing code path — `createSignSetup` (uses `pushCore.GetCurrentKey`) and `verifyingPubkey`/`GetCurrentTSSKey` for `SIGN_OUTBOUND` — derives the signer/from-address from this single `CurrentTssKey`, with no per-chain awareness of whether that chain's vault has actually received funds under the new key [3](#0-2) [4](#0-3) .

Migrating each chain's vault balance from the old key to the new one is a distinct, admin-only, per-chain action (`MsgInitiateFundMigration`), gated on outbound being disabled and no pending outbounds for that chain [5](#0-4) . Nothing in the protocol forces outbound to be disabled automatically the instant a KEYGEN finalizes; disabling outbound is a manual `uregistry` admin step, and `x/utss`'s README documents this as a project-wide two-step, chain-by-chain process ("Each (old_key, chain) pair becomes a `FundMigration` record") [6](#0-5) . This is structurally identical to the ToB report: the protocol supports a "partial" move of the underlying value across providers (chains) while a shared piece of accounting/authorization state (`CurrentTssKey`, analogous to the Controller's active-provider pointer) is updated atomically for all of them at once.

Consequently, any ordinary unprivileged user whose crosschain inbound/payload triggers an outbound (a normal deposit + payload execution flow) during the window after a KEYGEN finalizes but before that specific destination chain's admin-run migration completes will have their outbound built and signed against the new-key vault address, which has not yet received the swept balance. The transaction will fail on-chain for insufficient funds (native transfer) or run against a vault contract whose access-control (`TSS_ADDRESS`) has not yet been rotated to the new key, causing a revert.

### Impact Explanation
The user's outbound gets stuck: `PendingOutbounds` entries are explicitly never auto-removed or auto-refunded on failure — the README states resolution is "governance-driven, not chain-driven" and auto-refund "risks double-pay" [7](#0-6) . This produces a permanent freeze of the user's funds (already deposited/committed on Push Chain, but the outbound leg cannot land) with no automatic recovery path — matching the "permanent freezing of user or protocol-controlled funds" allowed-impact category. It is unprivileged in the sense that the *triggering* user action (a normal inbound that spawns an outbound) requires no special privilege; only the KEYGEN itself is admin-initiated, but the exposure window and its exploitation by ordinary traffic is not gated by any privilege.

### Likelihood Explanation
Requires the admin to perform a `KEYGEN` (an expected, periodic operational event per the module's own design) and requires ordinary user traffic to hit a chain outbound during the gap before that chain's `FundMigration` is initiated/completed. Given `KEYGEN` fires migrations per-chain sequentially/asynchronously and there is no automatic global "disable outbound on all chains during KEYGEN" enforcement visible in the reviewed code, the window is operationally realistic, not merely theoretical, though it depends on operational timing/discipline by the admin.

### Recommendation
- **Short term:** Automatically disable outbound (`IsChainOutboundEnabled = false`) for every registered chain as part of `KEYGEN` finalization in `VoteTssKeyProcess`, atomically with the `CurrentTssKey` update, and only re-enable a given chain once its `FundMigration` reaches `FUND_MIGRATION_STATUS_COMPLETED`. Alternatively, have outbound-signing code paths check that the *current* key's vault balance/authorization on the destination chain has been migrated before honoring `SIGN_OUTBOUND` for that chain.
- **Long term:** Make the KEYGEN → per-chain fund migration transition an enforced, chain-aware state machine (e.g., track a per-chain "active signing key" that only flips to the new key once migration for that chain completes) rather than relying on a single global `CurrentTssKey` combined with manual, easy-to-forget admin follow-up.

### Proof of Concept
1. Admin runs `MsgInitiateTssKeyProcess(KEYGEN)`; UVs vote via `MsgVoteTssKeyProcess` until quorum, which sets `CurrentTssKey` to the new key/pubkey immediately (`msg_vote_tss_key_process.go:78`).
2. Before the admin disables outbound and runs `MsgInitiateFundMigration` for chain X (a separate, later admin action), an ordinary user submits a normal crosschain inbound+payload on Push Chain whose execution creates a pending outbound targeting chain X's vault (release/withdraw funds).
3. A Universal Validator picks up the pending outbound; `createSignSetup`/`GetCurrentKey` and `verifyingPubkey` bind the transaction to the **new** TSS key/address (`coordinator.go:696-712`, `msg_handler.go:257-267`), even though chain X's vault still recognizes/holds funds under the **old** key.
4. The broadcast either reverts (vault `TSS_ADDRESS` access-control still points to old key) or the new-key address has zero balance, so the transfer fails.
5. The outbound remains `PENDING` indefinitely; per `x/uexecutor/README.md`, `PendingOutbounds` entries are never auto-removed/auto-refunded on failure, freezing the user's funds pending manual governance intervention.

// InitiateFundMigration validates and creates a fund migration from an old TSS key vault
// to the current TSS key vault for a specific chain.
func (k Keeper) InitiateFundMigration(ctx context.Context, oldKeyId, chain string) (uint64, error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// 1. Validate old key exists in history
	oldKey, err := k.TssKeyHistory.Get(ctx, oldKeyId)
	if err != nil {
		return 0, fmt.Errorf("old key %s not found in TssKeyHistory: %w", oldKeyId, err)
	}

	// 2. Verify old key != current key
	currentKey, err := k.CurrentTssKey.Get(ctx)
	if err != nil {
		return 0, fmt.Errorf("no current TSS key set: %w", err)
	}
	if oldKeyId == currentKey.KeyId {
		return 0, fmt.Errorf("old_key_id %s is the current active key; cannot migrate from current key", oldKeyId)
	}

	// 4. Verify outbound is disabled for this chain
	outboundEnabled, err := k.uregistryKeeper.IsChainOutboundEnabled(ctx, chain)
	if err != nil {
		return 0, fmt.Errorf("failed to check outbound status for chain %s: %w", chain, err)
	}
	if outboundEnabled {
		return 0, fmt.Errorf("outbound is still enabled for chain %s; disable outbound before initiating migration", chain)
	}

	// 5. Verify no pending outbounds for this chain
	hasPending, err := k.uexecutorKeeper.HasPendingOutboundsForChain(ctx, chain)
	if err != nil {
		return 0, fmt.Errorf("failed to check pending outbounds for chain %s: %w", chain, err)
	}
	if hasPending {
		return 0, fmt.Errorf("chain %s still has pending outbounds; wait for them to drain before migration", chain)
	}
