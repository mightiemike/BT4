### Title
Weight double-counting for a single signer via distinct ECDSA signatures in `ValidateMultiSign` precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompiled contract computes a weighted multisig threshold by summing the weight of each recovered signer, but it only skips a signature when the *exact byte-identical* signature is repeated for a signer already counted. A signer can produce two *different* valid ECDSA signatures `(r,s,v)` over the same hash (since ECDSA signing is not required to be deterministic), and both will `ecrecover` to the same address yet be treated as distinct "new" signatures, letting that signer's weight be added to `totalWeight` more than once. This mirrors the reported `SubstrateSignatureValidator` bug class of counting duplicate signer signatures toward a threshold.

### Finding Description
`ValidateMultiSign.execute` iterates over the supplied signature array and accumulates weight: [1](#0-0) 

The dedup check only skips when the *raw signature bytes* (`sign`, after merging with the recovered address) exactly match a previous entry:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
``` [2](#0-1) 

If `recoveredAddr` was already seen but the current `sign` bytes differ (a different, but still valid, signature by the same key over the same `hash`), execution only calls `MUtil.checkCPUTime()` (a rate-limit/anti-DoS check) and then falls through to add `weight` again — it does **not** `continue`/skip. Because ECDSA allows arbitrarily many valid `(r,s)` pairs for the same message when different nonces `k` are used, one private-key holder can trivially produce N distinct valid signatures over the identical `hash` and submit them all in one call, inflating `totalWeight` by `N × weight` instead of `weight`. `getWeight` looks up weight purely by recovered address, with no per-signer usage cap other than the exact-signature dedup: [3](#0-2) 

This differs from the transaction-signing path (`TransactionCapsule.checkWeight`), which correctly deduplicates by recovered **address** (post fork `VERSION_4_7_1`) via a `HashMap`, rejecting any second signature from the same signer regardless of its raw bytes: [4](#0-3) . The `ValidateMultiSign` precompile, however, does not reuse this correct address-based dedup logic and instead implements its own flawed byte-level dedup.

### Impact Explanation
`ValidateMultiSign` is a public TVM precompiled contract callable from any Solidity smart contract to verify that a TRON account's on-chain permission (e.g., an M-of-N multisig `Active`/`Owner` permission) has been satisfied for arbitrary application data. Smart contracts (e.g., custodial wallets, DAOs, bridges) rely on this precompile as an authorization gate for privileged actions such as withdrawals or governance approvals. An attacker who controls only a single key configured in the permission (with weight `w < threshold`) can forge multiple distinct signatures over the same message and satisfy `totalWeight >= permission.getThreshold()` without any of the other required co-signers participating, completely bypassing the intended M-of-N authorization/access-control check — a concrete auth-bypass impact.

### Likelihood Explanation
Likelihood is high: producing multiple valid, distinct ECDSA signatures for the same message with a single private key requires only varying the ephemeral nonce `k` during signing, which is trivially achievable by any signer (no dependency on non-deterministic signing being disabled — an attacker fully controls their own signing process). No special privilege beyond holding one key in the target permission is needed, and the precompile is reachable by any contract/EOA that can call it.

### Recommendation
In `ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (not by the raw signature bytes): once an address has contributed weight, any further signature recovering to that same address should be skipped entirely (as `TransactionCapsule.checkWeight` already does for on-chain transaction signature verification), rather than only skipping exact byte-for-byte repeats.

### Proof of Concept
1. Configure an account with an `Active` permission containing two keys, `A` (weight 1) and `B` (weight 1), threshold 2.
2. Using only `A`'s private key, sign the same `hash` (computed from `address || permissionId || data`) twice using two different ephemeral nonces `k1 ≠ k2`, producing two distinct valid signatures `sig1 = (r1, s1, v1)` and `sig2 = (r2, s2, v2)`, both recovering to address `A`.
3. Call the `validateMultiSign` precompile with `signatures = [sig1, sig2]`.
4. Because `sig1 != sig2` as raw bytes, the dedup check `matrixContains(executedSignList, sign)` fails to match on the second iteration, so `totalWeight` becomes `1 + 1 = 2`, satisfying the threshold of 2 even though only signer `A` actually approved — confirmed by the code path at [5](#0-4) .
