### Title
Inconsistent null-vs-zero value comparison in `EnergyCost.getSstoreCost` lets an in-transaction zero-toggle downgrade a real `0→nonzero` write from SET_SSTORE (20000) to RESET_SSTORE (5000) - ([File: actuator/src/main/java/org/tron/core/vm/EnergyCost.java])

### Summary
`EnergyCost.getSstoreCost` classifies SSTORE cost by checking `oldValue == null` rather than `oldValue == null || oldValue.isZero()`. Because `Storage.getValue`/`Program.storageLoad` return a non-null `DataWord.ZERO` (not `null`) for a slot that was already written to `0` earlier in the *same* transaction (via the in-memory `rowCache`), a subsequent write of a nonzero value to that same slot is misclassified as `RESET_SSTORE` (5000) instead of the semantically-correct `SET_SSTORE` (20000).

### Finding Description
`getSstoreCost` decides the tier purely on `null`-ness of the previously loaded value: [1](#0-0) 

`program.storageLoad` resolves through `RepositoryImpl.getStorageValue` → `Storage.getValue`: [2](#0-1) 

If the key is present in `rowCache` (i.e., it was written earlier in the *same* transaction/call context), `getValue` always returns a real `DataWord` object — even when that value is numerically zero — instead of `null`. `null` is only returned when the key is absent from `rowCache` **and** the underlying store row does not exist. At commit time, rows whose final value is zero are deleted from the store: [3](#0-2) 

This produces the following observable exploit sequence, entirely reachable by an ordinary contract deployer/caller with no privileged role:

1. `SSTORE slot, nonzero` — `storageLoad(slot)` is `null` (never touched) → `oldValue == null && !newValue.isZero()` → correctly charged `SET_SSTORE` (20000). The slot is now cached in `rowCache` with a real (non-null) `DataWord`.
2. `SSTORE slot, 0` — `oldValue` is the cached nonzero `DataWord`, `newValue.isZero()` → `CLEAR_SSTORE` (5000). The cached row now holds a non-null `DataWord.ZERO`.
3. `SSTORE slot, nonzero` — `storageLoad(slot)` now returns the cached non-null `DataWord.ZERO` (since `rowCache.containsKey(key)` is true), so `oldValue != null`. The code falls into the `"oldValue != null && newValue != 0"` branch → `RESET_SSTORE` (5000), instead of `SET_SSTORE` (20000), even though logically the slot's real/persisted value is zero (identical to the never-set case in step 1).

Because `Storage.commit()` only deletes the zero-valued row from persistent storage at the *end* of the transaction, the discrepancy between "never set" (`null`) and "in-flight zero" (`non-null DataWord.ZERO`) exists only within the lifetime of a single transaction's `rowCache`, but that is exactly the window the attacker controls via ordinary SSTORE sequencing inside one contract call. No signature, permission, or fork-gate check inspects this cost classification — `getSstoreCost` is purely an energy-accounting function invoked by the interpreter, so none of `TransactionCapsule.validateSignature`, actuator `validate()`, or `ForkController` gates are relevant or protective here.

### Impact Explanation
This is a metering-faithfulness violation (systematic underpricing of storage writes), matching TRON's "DoS via the TRON protocol implementation" / energy-accounting-corruption class. Each repeated `0→nonzero` toggle cycle after the first real SET is undercharged by 15000 energy relative to the intended pre-EIP1283-style cost model (`RESET_SSTORE`=5000 charged instead of `SET_SSTORE`=20000). An attacker can loop this pattern many times within a single transaction's energy limit, performing far more storage-cache mutation work (and eventual disk writes at commit) than the energy they pay for, letting adversarial contracts get disproportionately cheap repeated state-changing execution within the fixed per-block/per-transaction energy budget. This does not, however, allow unbounded growth of distinct persisted slots (the discount only applies to a slot already resident in the same transaction's in-memory cache), so the practical impact is a bounded but real energy-underpricing/DoS-adjacent resource-accounting bug rather than unconstrained state-DB growth.

### Likelihood Explanation
Fully unprivileged and trivially reproducible: any account can deploy/call a contract that performs the three-SSTORE sequence on the same slot within one transaction. No special preconditions, fees beyond normal transaction/energy costs, or non-default configuration are required. It is deterministically repeatable on every call to the vulnerable pattern.

### Recommendation
Change the classification in `getSstoreCost` to treat "logically zero" uniformly regardless of `null`-ness, e.g.:
```java
boolean oldIsZero = (oldValue == null) || oldValue.isZero();
if (oldIsZero && !newValue.isZero()) {
  return SET_SSTORE;
}
if (!oldIsZero && newValue.isZero()) {
  return CLEAR_SSTORE;
}
return RESET_SSTORE;
```
This mirrors real EVM pre-EIP1283 semantics (compare against the numeric value zero, not object nullity), which is what `Storage.getValue`/`Storage.commit()`'s own zero-deletion policy assumes elsewhere.

### Proof of Concept
```java
// EnergyCostSstoreTest.java
@Test
public void testZeroValueVsNullMisclassification() {
  Program program = mock(Program.class);
  Stack stack = new Stack();
  DataWord slot = DataWord.ONE;

  // Step 3 state: slot was written to 0 earlier in same tx -> cached as non-null DataWord.ZERO
  when(program.storageLoad(slot)).thenReturn(DataWord.ZERO); // non-null, but numerically zero
  stack.push(slot);                 // stack.peek() -> slot
  stack.push(new DataWord(7));      // newValue = 7 (nonzero)
  when(program.getStack()).thenReturn(stack);

  long cost = EnergyCost.getSstoreCost(program);

  // Real semantics: slot's actual value is zero -> writing nonzero should be SET_SSTORE (20000)
  // Buggy behavior: oldValue != null -> classified as RESET_SSTORE (5000)
  assertEquals(20000L, cost); // FAILS: actual result is 5000L, proving the misclassification
}
```
Equivalently, at the transaction level: deploy a contract whose fallback performs `SSTORE(slot, X); SSTORE(slot, 0); SSTORE(slot, Y)` in one call, and observe via `ProgramResult`/trace that the third SSTORE consumes 5000 energy instead of the 20000 that a fresh `null→Y` write of the same logical (zero) state would cost.

    Stack stack = program.getStack();
    DataWord newValue = stack.get(stack.size() - 2);
