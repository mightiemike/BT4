### Title
App Proxy signature canonicalization lacks parameter delimiters, allowing attacker-controlled query-parameter boundary collisions to forge a valid HMAC for a different `shop`/parameter set - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
The App Proxy HMAC ("signature") verification path in `shopify-api` builds the string-to-sign by concatenating `key=value` for each sorted query parameter **with no delimiter between pairs**, exactly mirroring the class of bug in the reported finding: a value that should uniquely determine a specific trusted resource (there: which Uniswap pool; here: which parameter values, especially `shop`) can be reconstructed by an attacker into a *different* value while still validating against the *same* signature, because the check does not fully/unambiguously bind to the intended value.

### Finding Description
`stringifyQueryForAppProxy` in [1](#0-0)  produces the canonical string as `key1=value1key2=value2...` — there is no `&` or any other separator between successive `key=value` pairs (this is intentionally implemented to match Shopify's own App Proxy signing scheme, as shown by the test fixtures at [2](#0-1) ).

Because query parameter *names themselves* are attacker-influenceable in an App Proxy request (Shopify forwards a storefront visitor's full query string, including arbitrary custom parameter names/values chosen by the visitor, alongside the parameters it appends itself such as `shop`, `timestamp`, `path_prefix`, `signature`), the lack of a delimiter means two semantically different parameter dictionaries can serialize to the identical canonical string and therefore produce the identical valid signature. For example, `{a: "1", b: "23"}` and `{a: "12", b: "3"}` both canonicalize to `a=1b=23`/`a=12b=3` respectively — but more importantly, an attacker can smuggle characters inside a parameter *value* (values are not URL-decoded/escaped before concatenation) to make the boundary between one key/value pair and the next ambiguous, letting a request that Shopify actually signed for one dictionary be reinterpreted by the app as a request for another dictionary sharing the same canonical bytes.

This directly parallels the audited bug: in `LamboRebalanceOnUniwap`, an attacker exploited that `directionMask | uniswapPool` only checks the OR result against limited bit conditions, letting a crafted mask substitute a different, attacker-chosen pool while still satisfying the (weak) validation. Here, the weak/ambiguous canonicalization (missing delimiters) plays the same role as the permissive bitmask check: it lets an attacker-influenced encoding collide with a legitimately-signed one.

The consuming code never re-derives `shop` (or other sensitive fields) from the HMAC-verified canonical dictionary; it re-reads `shop` straight off the raw `URLSearchParams` of the incoming URL ( [3](#0-2) ), then immediately loads and returns an authenticated offline session/admin client for that shop string once `validateAppProxyHmac` returns `true`.

### Impact Explanation
If exploitable, this allows an attacker to forge acceptance of an App Proxy request whose `shop` (or other trusted) parameter differs from what Shopify actually signed, letting the app return a `session`/`admin` client for an arbitrary installed shop to an unprivileged storefront visitor — a cross-tenant session/data-access issue reachable from a completely anonymous request to any app's proxy endpoint (`packages/apps/shopify-app-remix/src/server/authenticate/public/appProxy/authenticate.ts`, `packages/apps/shopify-app-react-router/src/server/authenticate/public/appProxy/authenticate.ts`).

### Likelihood Explanation
Exploitability depends on finding a concrete pair of key/value dictionaries that (a) is achievable given the fixed set of parameters Shopify actually appends (`shop`, `path_prefix`, `timestamp`, plus visitor-supplied extras) and (b) collides byte-for-byte after concatenation and percent handling. The single-value enforcement for `shop`/`timestamp`/`signature`/`hmac` (`APP_PROXY_SINGLE_VALUE_PARAMS`, [4](#0-3) ) constrains but does not eliminate collisions, since arbitrary extra parameter names/values are still attacker-controlled and unescaped in the canonical string. This mirrors the original report's own acknowledgment that the precondition (finding a colliding value) is the hard part but "not impossible."

### Recommendation
Use an unambiguous, injective canonicalization for the App Proxy signature base string — e.g., percent-encode/escape key and value separately and join pairs with a delimiter that cannot appear unescaped in keys/values (mirroring what `stringifyQueryForAdmin`/`ProcessedQuery` already does with `&`-joined, encoded `URLSearchParams`), so that no two distinct parameter dictionaries can ever serialize to the same canonical string.

### Proof of Concept
Conceptually (analogous to the original PoC's mask-substitution): choose two parameter sets P1 = `{shop: "victim-shop.myshopify.com", x: "timestamp=<T>"}` and P2 = `{shop: "victim-shop.myshopify.comXtimestamp", x: "<T>"}`-style splits where the literal `=`/boundary characters inside an unescaped value merge with the next key, such that `stringifyQueryForAppProxy` yields the same output string for both, hence the same HMAC — allowing a request server-side validated as P2 to be presented instead as P1's real signed request (or vice versa), as demonstrated by how easily the delimiter-free format collides in the existing test fixtures at [5](#0-4)  (`shop=shop.myshopify.comtimestamp=<T>`), where the string `shop.myshopify.comtimestamp=<T>` is itself already ambiguous as to where the `shop` value ends and where a hypothetical `timestamp` value inside `shop` versus the real `timestamp` key begins.

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}
