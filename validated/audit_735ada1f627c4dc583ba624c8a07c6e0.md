## Analysis Summary

Reducing the external bug to its core invariant: **an authenticated/checked value must not be substituted for an unverified one before being committed to durable state.** In Illuminate, `Lender.mint()` trusted `principal` as distinct from the Illuminate PT without checking `p != Illuminate`. Looking for the Aptos analog of "proof covers X, but Y is smuggled in and trusted as if it were also covered by the proof," I traced the transaction-backup restore path, where the accumulator/event proof covers transactions and events, but **write sets are loaded from the same untrusted file and persisted without ever being checked against the proof-bound `state_change_hash`** — unlike the equivalent `TransactionOutputListWithProofV2::verify` path, which does perform that check.

### Title
Backup Restore Path Persists Unverified Write Sets Not Bound to the Proof-Checked `state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
When restoring a transaction backup, `LoadedChunk::load` reads `txns`, `txn_infos`, `event_vecs`, and `write_sets` from the same backup file, but only wraps `txns`/`event_vecs`/`txn_infos` in a `TransactionListWithProofV2` and calls `.verify()` on that structure. `write_sets` are carried alongside, completely outside the verified structure, and are later persisted straight into `WriteSetDb` via `restore_utils::save_transactions_impl` with no check that their hash matches `txn_info.state_change_hash()`.

### Finding Description
`LoadedChunk::load` builds a `TransactionListWithProofV2` from `txns`, `event_vecs`, and `txn_infos`, and calls `txn_list_with_proof.verify(ledger_info.ledger_info(), Some(manifest.first_version))?` [1](#0-0) . But `write_sets` is read from the very same file, independent of this struct, and never included in anything that gets verified [2](#0-1) .

`TransactionWithProof::verify` (the per-txn logic backing this list verification) only checks that the transaction hash matches `transaction_info.transaction_hash()` and, if events are present, that the event root hash matches `transaction_info.event_root_hash()` — it never touches `state_change_hash()` or any write set [3](#0-2) . This is correct by construction for that type, because `TransactionInfoWithProof`/`TransactionListWithProof` is not meant to carry write sets. However, the restore code effectively treats the write_sets loaded alongside it as trustworthy.

By contrast, when the codebase does need to authenticate a write set, it explicitly checks the write set hash against `txn_info.state_change_hash()`, as seen in `TransactionOutputListWithProofV2::verify`: [4](#0-3) 

The transaction backup/restore code path never performs this equivalent check. The unverified `write_sets` (for versions strictly before `first_to_replay`, i.e., not re-executed by the VM) are forwarded straight to `restore_handler.save_transactions(...)` [5](#0-4) , which calls `restore_utils::save_transactions` [6](#0-5) , which in turn calls `save_transactions_impl`. That function writes the given `write_sets` directly into `WriteSetDb` with no hash validation whatsoever: [7](#0-6) 

No code path between `LoadedChunk::load` and this `WriteSetDb::put_write_set` call ever compares `CryptoHash::hash(&write_set)` to `txn_info.state_change_hash()`, even though `txn_info` itself *is* proof-verified against the ledger accumulator.

### Impact Explanation
An attacker who controls or can tamper with the backup source (compromised backup storage backend, MITM on backup transport, or a corrupted/malicious archive supplied to an operator) can keep the proof-verified `(transaction, transaction_info, events)` triple untouched — so `verify()` still succeeds — while substituting an arbitrary `WriteSet` blob for any transaction whose version is below the `first_to_replay` cutoff (the common case: most historical transactions are saved directly, not re-executed). The forged write set is committed to `WriteSetDb` as durable ledger data without any integrity failure being raised. Any consumer trusting this restored node — new full nodes bootstrapped from backups, indexers/GRPC streams reading `get_transaction_outputs`/write-set data, or downstream audits — will observe committed write-set/state-change data for that version that was never bound to the accumulator/`state_change_hash` proof, i.e. committed state that differs from the correct VM result for that transaction. This falls squarely under "committed state that differs from the correct VM result or corrupts durable ledger data" and "authenticated API... output bound to the wrong... proof context."

### Likelihood Explanation
Requires control over (or ability to tamper with) the backup file(s) consumed by `TransactionRestoreController`/`TransactionRestoreBatchController` — a real-world threat model since backups are frequently stored on third-party object storage or transferred over less-trusted channels, and the restore tool is a standard operational bootstrap path (documented for state-sync v2 and node/backup recovery). No validator/consensus compromise is needed; only tampering with backup artifacts consumed by an unprivileged restore operation. This is a genuine local code gap (missing check), not merely a duplicate of the external report's exact mechanism.

### Recommendation
In `LoadedChunk::load` (or immediately before persisting), verify each `write_set`'s hash against the corresponding `txn_info.state_change_hash()` before returning/persisting, mirroring the check already performed in `TransactionOutputListWithProofV2::verify`. Reject the chunk (or the offending record) if the hashes disagree, for both the "save without replay" and "replay" code paths in `TransactionRestoreController`.

### Proof of Concept
1. Take a legitimate transaction backup manifest/chunk containing `(txn, txn_info, events, write_set)` records and a valid `(range_proof, ledger_info)`.
2. Replace the serialized `write_set` bytes for one record with an arbitrary crafted `WriteSet` (e.g., one that sets an attacker-chosen resource value), leaving `txn`, `txn_info`, and `events` untouched.
3. Run `aptos-db-restore` (or equivalent) against this tampered chunk with a `replay_from_version` set above this record's version (default/common operational usage), so this record falls into the "save without replay" branch.
4. `LoadedChunk::load` succeeds because `txn_list_with_proof.verify(...)` only checks `txn`/`events` hashes against the (unchanged, still valid) `txn_info`/accumulator proof.
5. `restore_handler.save_transactions(...)` → `save_transactions_impl` writes the forged `write_set` into `WriteSetDb` for that version with no hash check.
6. Querying the restored node's write set / transaction output for that version returns the attacker-forged data as if it were proof-verified ledger truth.

    pub fn verify(&self, ledger_info: &LedgerInfo) -> Result<()> {
        let txn_hash = self.transaction.committed_hash();
        ensure!(
            txn_hash == self.proof.transaction_info().transaction_hash(),
            "Transaction hash ({}) not expected ({}).",
            txn_hash,
            self.proof.transaction_info().transaction_hash(),
        );

        if let Some(events) = &self.events {
            let event_hashes: Vec<_> = events.iter().map(CryptoHash::hash).collect();
            let event_root_hash =
                InMemoryEventAccumulator::from_leaves(&event_hashes[..]).root_hash();
            ensure!(
                event_root_hash == self.proof.transaction_info().event_root_hash(),
                "Event root hash ({}) not expected ({}).",
                event_root_hash,
                self.proof.transaction_info().event_root_hash(),
            );
        }

        self.proof.verify(ledger_info, self.version)
    }
