### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash comparison during chunk replay verification - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (the function used by the chunk executor's `verify_execution` path and by `db-tool`'s `replay_on_archive` to confirm that a locally re-executed transaction matches the peer/backup-supplied `TransactionInfo`) checks status, gas used, write-set hash, and event-root hash, but never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is explicitly acknowledged in a `TODO(trading-native)` comment in the function itself.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates a re-executed `TransactionOutput` against an externally supplied `TransactionInfo` by comparing status, gas, `write_set_hash` vs `state_change_hash()`, and event root hash. It intentionally omits comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` carried on `TransactionInfo`, as stated in the trailing comment: [2](#0-1) 

This function is invoked by the chunk executor's replay-verification path, `verify_execution`, in [3](#0-2) , which is exercised when `VerifyExecutionMode::verify_all()` (or similar non-default modes) is configured, and by the standalone `replay_on_archive` tool in [4](#0-3) . In both cases, the `expected_txn_infos`/`transaction_infos` come from an external, potentially untrusted archive/backup source and are treated as ground truth for comparison against freshly re-executed VM output — but the checkpoint-hash fields (which anchor state/hot-state/position Merkle roots) are never cross-checked here.

This is distinct from the primary commit path (`DoStateCheckpoint`/`DoLedgerUpdate` in `execution/executor/src/chunk_executor/mod.rs` lines 363-448), which does compare `known_state_checkpoints`/`known_position_state_checkpoints` derived from the same untrusted `txn_infos` against the locally computed roots — that path is not affected. The gap is specifically in the secondary/auxiliary verifier `ensure_match_transaction_info`.

### Impact Explanation
For contexts that rely on `ensure_match_transaction_info` as the authoritative correctness check (chunk replay verification tooling and `replay_on_archive`), a divergence in the state/hot-state/position checkpoint roots between the locally re-executed result and the externally supplied `TransactionInfo` would not be detected — the function returns `Ok(())` even though the authenticated state root differs from the actual VM output. Per the code's own comment, this specifically undermines validation of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (native "position" state), allowing corrupted or diverged committed state to be reported as a successful replay/verification. This matches the state-integrity gate's criteria ("committed state that differs from correct VM result... accepted as valid") for the tools that rely on this specific comparator.

### Likelihood Explanation
Low-to-moderate. This gap only manifests where `ensure_match_transaction_info` is the actual gatekeeper — i.e., in the optional `VerifyExecutionMode::verify_all()` code path and the offline `replay_on_archive` verification tool — not in the default commit/consensus path (which uses `DoStateCheckpoint`'s separate, still-intact checkpoint comparison). The feature is also explicitly gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, which is not yet fully enabled (per the TODO), reducing current exposure. I was not able to fully verify whether `VerifyExecutionMode::verify_all()` is enabled by default anywhere in production node configuration paths (e.g., fast-sync/bootstrap) versus purely a CLI/debug flag — this remains uncertain given available context.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` against the locally computed roots (or accept them as optional parameters, mirroring the `known_state_checkpoints`/`known_position_state_checkpoints` mechanism already used in `DoStateCheckpoint`) before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, so that replay-verify tooling cannot silently accept a diverged state/position root.

### Proof of Concept
Not independently reproducible as a live mainnet exploit from local code alone — the gap requires (a) `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/native-position state to be enabled, and (b) using `VerifyExecutionMode::verify_all()` chunk replay or `db-tool replay-on-archive` against an archive/backup that has a manipulated or divergent `position_state_checkpoint_hash`/`state_checkpoint_hash` in its `TransactionInfo` while still yielding a matching write-set/event hash. Under that condition, calling `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` at [4](#0-3)  or the equivalent call in [5](#0-4)  returns `Ok(())` despite the state root mismatch, demonstrating the missed check described in the code's own TODO comment.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
