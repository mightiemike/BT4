**Reasoning:**

1. **The `upsert` swap sequence is a normal in-place replace, not an order-shuffling operation across the whole vector.** In `simple_map.move`, `upsert` finds the index `i` of the existing key, pushes the new `Element` to the end (`len`), swaps positions `i` and `len`, then pops the last element — this is a standard "replace-in-place via swap-with-last" idiom. The net effect is that the element at index `i` is replaced with the new key/value while every other element's index is unchanged. [1](#0-0) 

2. **Any "shift dependent on loop iteration count" for untouched keys does not occur.** Only the position of the key actually being upserted is touched; other elements' relative order and indices are preserved across repeated `upsert` calls on the same key. The final byte layout of the `data` vector is a deterministic function of the *sequence* of Move VM instructions executed — which is identical for every validator, since Move execution is fully deterministic and part of consensus. This is exercised directly in `test_upsert_test`. [2](#0-1) 

3. **There is no "fast-sync path that snapshots intermediate map states"** anywhere in the state-sync or storage stack. Fast sync (`state-sync/state-sync-driver/src/bootstrapper.rs`) and `storage_synchronizer.rs` stream *already-serialized, already-committed* `StateValueChunkWithProof` payloads — i.e., the final BCS-encoded bytes of the resource as produced once by execution — and verify them against a Jellyfish Merkle proof bound to the target ledger info's root hash. [3](#0-2) [4](#0-3) 
   Fast sync never re-executes Move code or "reconstructs" a `SimpleMap`'s internal vector layout from intermediate states; it copies the resource's already-final serialized bytes verbatim. There is no separate reconstruction logic that could diverge from full replay, because both paths ultimately transmit/verify the *same* bytes produced by the one canonical execution of the transaction.

4. **Consequently, there is no mechanism by which a "fast-sync snapshot-based reconstruction" would produce different vector-order bytes than full replay.** Both paths land on identical state value bytes for the resource, bound to the same version/root via Merkle proof verification. The premise of a divergent "snapshot-based reconstruction" that recomputes map layout independently of transaction execution does not correspond to any component in this codebase.

    fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_verify_chunk"]);
                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
                }
            },
        }

        Ok(())
    }
