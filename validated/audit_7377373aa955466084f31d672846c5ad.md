### Title
Excess attached deposit is permanently lost when calling `AddressRegistrar::register` with more than the exact storage cost - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar` contract, part of the NEAR wallet-contract system used by ETH-implicit accounts, exposes a `#[payable]` `register` method that only checks that the attached deposit is *at least* the exact storage cost, but on the success path it never refunds the excess over that exact cost. Any caller who overpays (attaches more `NEAR` than the precisely required storage deposit) permanently loses the difference, since the contract has no owner/withdraw function to recover it.

### Finding Description
`AddressRegistrar::register` computes the exact required deposit from the number of bytes to be stored: [1](#0-0) 

It then checks only `given_deposit < required_deposit` and panics if insufficient — but it never checks (or refunds) the case where `given_deposit > required_deposit`.

- If the address is **already occupied** (collision), the code explicitly refunds the *entire* `given_deposit` back to the caller: [2](#0-1) 

- If the address is **vacant** (the normal success path), the entry is inserted and the method returns without ever transferring back the excess (`given_deposit - required_deposit`): [3](#0-2) 

This is the exact bug-class pattern described in the reference report: a contract validates only a lower-bound on funds sent (`sent >= required`) but keeps whatever surplus was attached instead of refunding it, and that surplus becomes permanently unrecoverable because the contract exposes no owner/withdraw mechanism anywhere in the file.

### Impact Explanation
Any account (a plain RPC caller submitting a signed `FunctionCall` transaction, or the wallet contract acting as predecessor on behalf of an ETH-implicit account owner via `nep_141_storage_balance_callback`/relayer flows) that attaches more than the exact computed storage byte cost to `register` will have the excess permanently locked in the `AddressRegistrar` contract's balance with no way for the depositor, the contract, or anyone else to reclaim it. This is a direct, concrete loss of user funds triggered by a single transaction — matching "permanently frozen funds" impact criteria. Because `AddressRegistrar` is deployed as part of the NEAR wallet-contract stack that ETH-implicit accounts rely on to register themselves, any relayer or user computing a deposit slightly larger than the exact requirement (e.g., for safety margin, or due to storage price changes between quoting and execution) will silently lose funds.

### Likelihood Explanation
The `register` function is a public, `#[payable]` entry point reachable by any unprivileged account via a normal signed transaction/RPC call — no special privileges are required. Overpaying is a very plausible real-world scenario: callers who don't recompute the exact byte-for-byte storage price (which depends on `account_id.len()`) and instead attach a rounded/safety-margin deposit will trigger this loss on every successful registration. The existing test suite only asserts a `>=` inequality on the balance delta rather than exact equality, showing the surplus-retention behavior is present but unverified/unguarded: [4](#0-3) 

### Recommendation
In the `Entry::Vacant` success branch of `register`, compute `deposit_refund = given_deposit.checked_sub(required_deposit)` and, if nonzero, issue a `promise_batch_action_transfer` back to `env::predecessor_account_id()` for the excess, mirroring the refund already performed in the `Entry::Occupied` branch (which currently over-refunds by returning the whole deposit instead of just the excess in a partial-overpay case). At minimum, either refund exact excess on success or reject transactions whose deposit doesn't exactly match `required_deposit`.

### Proof of Concept
1. Caller computes `account_id` and calls `AddressRegistrar::register(account_id)` attaching `required_deposit + extra` yoctoNEAR (e.g., `required_deposit * 2`), where `required_deposit = storage_byte_cost * (20 + account_id.len())` as computed at [5](#0-4) .
2. Since `given_deposit >= required_deposit`, the check at lines 54–61 passes.
3. The address is vacant, so the `Entry::Vacant` branch executes at lines 65–72: the mapping is inserted and `Some(address)` returned — no refund transfer is created.
4. The `AddressRegistrar` contract's account balance increases by the *full* `given_deposit`, not just `required_deposit`; the caller has no way to reclaim the `extra` yoctoNEAR, and no admin/withdraw method exists in the contract to recover it either.
