### Title
Zero-length log messages bypass `LOG_MESSAGES_BYTES_LIMIT` byte-count check, permanently disabling truncation and enabling extra unbounded-within-CU-budget entries in `LogCollector::messages` - ([File: svm-log-collector/src/lib.rs])

### Summary
`LogCollector::log` computes `bytes_written = self.bytes_written.saturating_add(message.len())` and only pushes a truncation warning once `bytes_written >= limit`. If an attacker first fills the collector to `limit - 1` bytes and then sends zero-length messages, `bytes_written` never advances (adding 0 is a no-op), so every subsequent zero-length message satisfies `bytes_written < limit` and is pushed forever, while `limit_warning` is never set. This lets an attacker exceed the intended 10,000-entry/`LOG_MESSAGES_BYTES_LIMIT` cap on `messages.len()`.

### Finding Description
`LogCollector::log` at [1](#0-0)  checks the *cumulative byte count*, not the *message count*. Once `self.bytes_written` reaches `limit - 1`, any message of length `0` yields `bytes_written = (limit - 1).saturating_add(0) = limit - 1 < limit`, so the `else` branch executes: `self.bytes_written` is reassigned to the same unchanged value and the (empty) message string is pushed to `self.messages`. Because `bytes_written` never crosses the `limit` threshold again, this repeats indefinitely for every zero-length message, and the `if bytes_written >= limit` branch that sets `limit_warning = true` and appends `"Log truncated"` is never reached again.

This path is attacker-reachable because `LogCollector::log` is invoked from the `sol_log` syscall handler via `stable_log::program_log`, and the syscall accepts arbitrary `len`, including `0`, from BPF program code [2](#0-1) . Any user-deployed program can call the log syscall with an empty string in a loop.

However, each `SyscallLog` invocation still charges compute units via `invoke_context.get_execution_cost().syscall_base_cost.max(len)` before the log is recorded [3](#0-2) , so the number of zero-length log calls per transaction is bounded by `remaining_compute_units / syscall_base_cost`, not truly unbounded. The bug is real at the `LogCollector` unit level (unit tests can drive it without any compute budget), but its in-validator impact is capped by the per-transaction compute unit budget rather than being unbounded as the question's precondition implies.

### Impact Explanation
The intended invariant — that `messages.len()` and total logged bytes are bounded by `LOG_MESSAGES_BYTES_LIMIT` (10,000 bytes) — can be violated: an attacker can push additional zero-length `String` entries into `LogCollector::messages` beyond what the byte-limit truncation was meant to enforce, and `limit_warning`/`"Log truncated"` is never emitted once this stall state is reached. This falls into the "disproportionate storage and CPU cost" category — extra `Vec<String>` allocations and RPC log payload growth for a single transaction's simulation/log output — but the magnitude is capped by the transaction's compute-unit budget (each call still costs at least `syscall_base_cost`), so it is not an unbounded/OOM-class issue.

### Likelihood Explanation
Reaching the exact stall precondition (`bytes_written == limit - 1`) requires precise control over prior message byte lengths, achievable by any program that calls `sol_log`/`msg!` with attacker-chosen string lengths (e.g., 9,999 bytes of 1-byte messages) before switching to empty-string messages. This is fully within reach of an unprivileged user who deploys and invokes their own program, with no validator/leader/staked privileges required. The impact per transaction is bounded by the compute budget (e.g., a few thousand extra entries at typical `syscall_base_cost` values), making it a real but modest logic defect, reproducible deterministically.

### Recommendation
Fix the truncation check to also account for zero-length messages, e.g., compare using a saturating check that treats reaching/exceeding capacity independent of message length, or track message count separately, or add an explicit `if message.is_empty() { /* still counts as reaching limit only via count */ }`. Simplest correct fix: change the condition to strictly enforce the limit even when `message.len() == 0`, e.g. use `if bytes_written >= limit || (message.is_empty() && self.bytes_written >= limit.saturating_sub(1))`, or better, cap on `self.messages.len()` as a secondary limit in addition to byte count.

### Proof of Concept
```rust
#[test]
fn test_zero_length_message_bypasses_truncation() {
    let mut lc = LogCollector::default(); // bytes_limit = Some(LOG_MESSAGES_BYTES_LIMIT)

    // Fill to limit - 1 bytes using 1-byte messages.
    for _ in 0..(LOG_MESSAGES_BYTES_LIMIT - 1) {
        lc.log("x");
    }
    assert_eq!(lc.bytes_written, LOG_MESSAGES_BYTES_LIMIT - 1);
    assert!(!lc.limit_warning);

    // Now flood with zero-length messages; bytes_written never advances,
    // so the >= limit branch (and limit_warning) is never triggered again.
    for _ in 0..50_000 {
        lc.log("");
    }

    assert!(!lc.limit_warning, "limit_warning should have fired but did not");
    assert!(
        lc.messages.len() > LOG_MESSAGES_BYTES_LIMIT,
        "messages.len() grew past the intended cap: {}",
        lc.messages.len()
    );
}
```
This test operates directly on `LogCollector` (no compute-budget interaction) and demonstrates the stall: `messages.len()` grows to `LOG_MESSAGES_BYTES_LIMIT - 1 + 50_000` while `limit_warning` remains `false`.

    pub fn log(&mut self, message: &str) {
        let Some(limit) = self.bytes_limit else {
            self.messages.push(message.to_string());
            return;
        };

        let bytes_written = self.bytes_written.saturating_add(message.len());
        if bytes_written >= limit {
            if !self.limit_warning {
                self.limit_warning = true;
                self.messages.push(String::from("Log truncated"));
            }
        } else {
            self.bytes_written = bytes_written;
            self.messages.push(message.to_string());
        }
    }
