### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting replay-verify silently accept a diverged ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`aptos-debugger`, `db-tool replay_on_archive`, the CLI, and `execution/executor/src/chunk_executor`) to confirm that a locally-recomputed `TransactionOutput` matches the authenticated `TransactionInfo` taken from a signed `LedgerInfo`/proof. It checks status, gas, write-set hash, and event root hash, but it deliberately skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the exact fields that commit the state/hot-state/position Sparse-Merkle roots into the authenticated `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info` verifies transaction status, gas used, write-set hash, and event root hash against the `TransactionInfo` taken from an authenticated proof, but explicitly does **not** compare the state-checkpoint-related hashes: [1](#0-0) 

The comment in the code itself acknowledges the gap: [2](#0-1) 

`TransactionInfoV1`/`V0` carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, each derived from the corresponding Merkle root committed by the executor during `DoLedgerUpdate`/`DoStateCheckpoint`: [3](#0-2) 

The transaction accumulator (and therefore the ledger-info-authenticated root) is built purely from `TransactionInfo::hash()`, which does include these checkpoint hash fields: [4](#0-3) 

Because the accumulator/root is authenticated via `TransactionInfo::hash()`, a corrupted or divergent state/hot-state/position root can still validate at the accumulator-proof layer as long as write_set/events/status/gas match — `ensure_match_transaction_info` is the one function callers use to independently assert that the locally-computed side (state root) matches what was actually committed under signatures. Skipping the checkpoint hash comparison means any tool relying on this function (replay-verify, debugger, CLI-based replay) can report success even though the locally-recomputed state root, hot-state root, or position-state root differs from the one baked into the authenticated `TransactionInfo`.

### Impact Explanation
This breaks the "committed state matches VM result" and "proof context stays bound to the correct object/root" invariants required by the State-Integrity Gate: a replay/verification pass built on `ensure_match_transaction_info` (db-tool `replay_on_archive`, `aptos-debugger`, CLI commands) can certify that a local re-execution is consistent with an authenticated ledger segment even when the state (or hot-state, or position-state, used for `ENABLE_TRADING_NATIVE`) Merkle root diverged from what was actually committed on mainnet. This is exactly the kind of "hard-fork-only divergence during commit/replay" scenario the gate calls out — a bug that changes VM/storage semantics for the trading-native state root, hot-state root, or main state root would go undetected by any tool relying solely on this comparator, because they'd only compare gas/status/events/write-set, not the state roots that these checkpoint hashes commit.

### Likelihood Explanation
The bug is code-confirmed (not speculative): the omission is explicit and commented in `types/src/transaction/mod.rs` lines 2197-2203, referencing `db-tool`'s `replay_on_archive` by name, and the function's callers (`aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`) are all real production/operational tooling paths, not tests. Because `TransactionInfo::hash()` in `do_ledger_update.rs` does include these checkpoint hashes, any actual state-root divergence (e.g., a subtle non-determinism or logic bug in `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / hot-state computation) would fail full accumulator-proof verification against a signed `LedgerInfo`, but would not be caught by tools that only call `ensure_match_transaction_info` for a "soft" local sanity check before/without a full proof check — this makes the risk primarily about false-negative detection in operational/replay tooling rather than an on-chain consensus break by itself.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled), and `position_state_checkpoint_hash` (when `ENABLE_TRADING_NATIVE`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) against locally recomputed values, surfacing a clear mismatch error including the state root, hot-state root, and position-state root, so that all callers (replay-verify, debugger, chunk executor, CLI) get a true positive/negative on ledger-state divergence rather than silently passing on write-set/event/gas/status alone.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-logic gap rather than a directly exploitable state-corruption path. The gap can be demonstrated statically: construct a `TransactionOutput` whose `write_set`, `events`, `status`, and `gas_used` match a given `TransactionInfo`, but whose locally-computed state/hot-state/position checkpoint root differs from `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`; calling `ensure_match_transaction_info` will return `Ok(())` despite the mismatched checkpoint hash, as shown by the omitted checks at [5](#0-4) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
