### Title
Unguarded division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` can throw an unhandled `ArithmeticException` during TVM execution - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by the network-wide `totalEnergyWeight` value with only a Java `assert` as protection, which is a no-op in production JVMs (`-ea` is not enabled by default). This is directly analogous to the reported `Pool.sol` bug where a caller-influenceable value (`loanReceipt.duration`) reaching zero causes `Math.mulDiv`/division to fail, forcing an unintended failure path (liquidation instead of repayment). Here, if `totalEnergyWeight` reaches zero, the hardened calculation path performs `BigInteger.divide(BigInteger.ZERO)`, throwing an uncaught `ArithmeticException` inside TVM contract execution.

### Finding Description
`calculateGlobalEnergyLimit` reads `totalEnergyWeight` from `DynamicPropertiesStore` and, in the "hardened" code path, immediately divides by it with only a non-enforced `assert`: [1](#0-0) 

Contrast this with the sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`, which explicitly guards the same division with `if (totalEnergyWeight <= 0) return 0;` before ever performing the divide: [2](#0-1) 

The `RepositoryImpl` variant lacks this guard entirely, relying only on `assert totalEnergyWeight > 0;`, which does nothing at runtime unless the JVM is started with `-ea` (not the default for production nodes). This function is reachable from TVM opcode execution through the `Repository` interface, exposed via `ContractState.calculateGlobalEnergyLimit`, which simply forwards to the underlying `RepositoryImpl`: [3](#0-2) 

`totalEnergyWeight` is a network-global counter incremented/decremented by freeze/unfreeze operations (`addTotalEnergyWeight`), and is explicitly floored at 0 (not prevented from becoming exactly 0): [4](#0-3) 

If it reaches exactly `0` and `hardenResourceCalculation()` is enabled (the hardened/BigInteger-exact path), `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`, which is unhandled at this call site.

### Impact Explanation
This mirrors the reported bug class: an accounting/settlement value that should never be zero can become zero, and a division against it is performed without a defensive check, turning normal operation into a forced failure. In java-tron's case, the consequence is not "goes to liquidation" but an uncaught exception thrown mid-TVM-execution when any contract call path invokes this calculation (e.g., any code path that queries energy limits for an account with frozen energy balance). Depending on how exceptions from `Repository` methods are handled by the VM interpreter/`Program` runtime, this can manifest as an invalid transaction-processing state, inconsistent behavior between nodes running with/without `-ea`, or a processing halt for the affected transaction/block — a state-divergence/halt-class impact rather than a purely cosmetic one.

### Likelihood Explanation
Reaching `totalEnergyWeight == 0` network-wide requires essentially all frozen-for-energy TRX across the entire chain to be unfrozen simultaneously, which is extremely unlikely on TRON mainnet given its economic activity, but is plausible on private/side chains, in early genesis states, or in test/staging networks where freezing is sparse. The bug is also asymmetric: the identical calculation in `EnergyProcessor` was hardened with an explicit zero-check, while the `RepositoryImpl` copy was not, suggesting the guard was simply missed when the resource-limit logic was duplicated for TVM native-contract use — a maintenance/consistency defect that raises the likelihood of resurfacing in future refactors.

### Recommendation
Add the same explicit guard used in `EnergyProcessor` to `RepositoryImpl.calculateGlobalEnergyLimit`:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```
replacing (or supplementing) the ineffective `assert totalEnergyWeight > 0;` at: [5](#0-4) 

### Proof of Concept
Not independently verifiable through static review alone — reproducing the exact zero-`totalEnergyWeight` network state requires driving the chain's global frozen-energy weight to exactly zero (e.g., via a controlled private-chain/genesis configuration where no accounts have frozen TRX for energy) and then invoking a TVM contract path that calls `Repository.calculateGlobalEnergyLimit` for an account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`. This would require running an actual node with `hardenResourceCalculation()` enabled and assertions disabled to trigger the `ArithmeticException` at runtime, which is beyond what can be confirmed via code inspection alone.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
