## Title
Unvalidated empty L1-to-L2 calldata causes a panic in `l1_handler_message_hash` on the "from_address" access - (File: `crates/starknet_api/src/hash.rs`)

### Summary
The zkEVM report describes an off-by-one/missing bounds check that lets calldata be read at or beyond its declared length. The closest reachable analog in this sequencer is in the L1-handler message-hash computation, where the code unconditionally assumes the transaction's `calldata` is non-empty (`calldata[0]` = `from_address`) via `Vec::split_first().expect(...)`, without a prior length check analogous to `offset < len`.

### Finding Description
`l1_handler_message_hash` derives `from_address` and `payload` directly from the transaction calldata: [1](#0-0) 

```rust
pub fn l1_handler_message_hash(...) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
    ...
}
```

This mirrors the reported bug class: code assumes a minimum-length invariant on attacker/L1-influenced data (`calldata`) without enforcing `len >= 1` before indexing/splitting it, just as the zkEVM ROM assumed `offset < txCalldataLen` was equivalent to a safe read at `offset == txCalldataLen`.

The same unguarded pattern (`calldata.0[0]`) recurs in multiple places that convert an `L1HandlerTransaction` into a message representation: [2](#0-1) [3](#0-2) 

By contrast, `payload_size()` on the same struct was hardened against this exact issue with a `saturating_sub`, and its comment explicitly documents the underflow risk that `L1HandlerTransaction::calldata` "has no non-empty invariant": [4](#0-3) 

This shows the codebase is aware `calldata` can be empty (it derives `Deserialize`, with `Calldata` having no non-empty invariant enforced at the type level), yet `l1_handler_message_hash`, `consume_l1_to_l2_message` (Cairo OS, guarded by `assert_not_zero`), and the Rust-side message converters do not consistently apply the same guard.

### Impact Explanation
If an `L1HandlerTransaction` with empty `calldata` reaches `l1_handler_message_hash` (e.g., via RPC transaction-hash/message endpoints in `apollo_rpc`, or via the L1 scraper/events provider paths that construct `L1HandlerTransaction` from on-chain events), the `.expect()` triggers a Rust panic. Depending on which service/thread invokes it (RPC node, L1 event scraper, or batcher), this can crash or restart that component, potentially disrupting L1→L2 message intake or serving of transaction data — a liveness impact for a single, cheaply crafted input. This does not corrupt state or funds directly, so it sits below the "wrong root/frozen funds" bar for Critical, but qualifies as a Medium-severity availability issue if such empty-calldata L1 handler data is reachable from an untrusted L1 message or externally-crafted RPC transaction object before deeper structural validation runs.

### Likelihood Explanation
Likelihood depends on whether upstream validation (gateway/mempool/blockifier `run_execute` paths, `L1HandlerTransaction::create`, or L1 event decoding) enforces `calldata.len() >= 1` before any of the above functions are invoked. Given time constraints, this repository index did not let me confirm a validation gate that guarantees non-empty calldata specifically for L1-handler transactions prior to hash/message computation on all code paths (the `payload_size()` fix suggests at least one path previously lacked such a guard). This uncertainty should be resolved by a Devin session with full repo access.

### Recommendation
- Add an explicit length check (`calldata.0.len() >= 1`) at L1-handler transaction construction/validation (`L1HandlerTransaction::create` in `crates/starknet_api/src/executable_transaction.rs`) so malformed/empty-calldata L1 handler transactions are rejected early with a proper error instead of panicking downstream.
- Replace the `.expect()` in `l1_handler_message_hash` (`crates/starknet_api/src/hash.rs`) with a fallible check returning a typed error, consistent with the `saturating_sub` pattern already used in `payload_size()`.
- Apply the same length check to `crates/apollo_batcher/src/cende_client_types.rs` and other `calldata.0[0]` usages.

### Proof of Concept
1. Construct/deserialize an `L1HandlerTransaction` (via RPC transaction submission path or a simulated malformed L1 message) with `calldata = Calldata(vec![])`.
2. Call any code path that computes the L1→L2 message hash or converts the transaction to `L1ToL2Message`/anvil message format (e.g., `l1_handler.calc_msg_hash()` reached from `apollo_rpc` transaction-hash APIs, or `L1ToL2Message::from(...)` in `cende_client_types.rs`).
3. Observe the panic at `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")`, crashing the invoking task/thread.

Note: I could not fully verify within the available tool budget whether all reachable code paths (gateway, mempool, L1 scraper) enforce non-empty L1-handler calldata before reaching this function; this should be confirmed with full-repository access.
