Based on my research, I found a directly analogous pattern in nearcore's cross-shard congestion/bandwidth admission path.

### Title
Unchecked size-limit subtraction in `try_forward` risks underflow if the size-clamp invariant is ever violated - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`ReceiptSinkV2::try_forward` decrements the bandwidth `OutgoingLimit.size` for a shard using a plain, unchecked subtraction (`forward_limit.size -= size;`), while the adjacent gas accounting on the very same code path deliberately uses `saturating_sub` for defense-in-depth. This mirrors the firedancer QUIC report's pattern: a padding/size field decremented via unchecked arithmetic that is only safe today because of an upstream guard, with no protection if that guard is ever weakened by a future code change.

### Finding Description
`try_forward` is reached from the runtime's cross-shard receipt-forwarding logic whenever an outgoing receipt (created by any account's transaction/contract call) needs to be forwarded to another shard's `OutgoingLimit`: [1](#0-0) 

The function first clamps `size` to `max_receipt_size` only if `size > max_receipt_size`, explicitly citing a known bug (#12606) that allows oversized receipts to be created: [2](#0-1) 

It then checks `forward_limit.size >= size` before forwarding, and on success decrements gas with `saturating_sub` (safe even if invariants break) but decrements size with a bare `-=`: [3](#0-2) 

Today the `>=` check immediately preceding the subtraction makes the underflow unreachable — exactly the same situation the firedancer commit describes ("not actually reachable... but adds some defense in depth"). The asymmetry between `saturating_sub` for `gas` and unchecked `-=` for `size` in the same statement block is the code smell: any future refactor that reorders the clamp, changes `max_receipt_size` handling, or introduces a new receipt path that bypasses `validate_receipt`'s `ReceiptSizeExceeded` check (`runtime/runtime/src/verifier.rs:687-696`) could cause `size > forward_limit.size` to slip past the guard.

### Impact Explanation
If the invariant is ever violated (e.g., through a future protocol change, a resharding edge case producing an inconsistent size, or another size-limit bypass akin to #12606), `forward_limit.size -= size` would underflow. Since this code runs deterministically on every validator during chunk apply, the outcome would be a uniform panic/wraparound across all honest nodes at the same chunk — a network-wide halt or, if overflow-checks are disabled in that build profile, a wrapped-around huge size limit that defeats bandwidth admission for the rest of the chunk (potential DoS/resource-limit bypass, not fund theft).

### Likelihood Explanation
Low today: the guard directly precedes the subtraction and receipt sizes are validated by `validate_receipt` before receipts are created. However, the historical existence of issue #12606 (receipts that bypass the size limit) shows this exact invariant has been violated in production before, which is why the size-clamp workaround exists at all. The lack of `checked_sub`/`saturating_sub` symmetry with the neighboring `gas` field is a maintainability/defense-in-depth gap rather than an currently-exploitable bug.

### Recommendation
Change `forward_limit.size -= size;` to `forward_limit.size = forward_limit.size.saturating_sub(size);` (mirroring the `gas` field's treatment on the previous line) so that any future violation of the "size fits under limit" invariant degrades gracefully (size limit floors at zero) instead of underflowing/panicking or wrapping to `u64::MAX`.

### Proof of Concept
Not applicable as a live exploit under current code — like the referenced firedancer commit, this is a defense-in-depth hardening recommendation, not a currently reachable vulnerability. The precondition guard `forward_limit.size >= size` at [4](#0-3)  currently prevents underflow given today's invariants (size clamped to `max_receipt_size`, receipts validated via `validate_receipt`).

    fn try_forward(
        receipt: Receipt,
        gas: Gas,
        mut size: u64,
        shard: ShardId,
        outgoing_limit: &mut HashMap<ShardId, OutgoingLimit>,
        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,
        stats: &mut ReceiptSinkStats,
    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts
        // above the size limit might not fit under the maximum outgoing size limit. Let's pretend
        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

        // Default case set to `Gas::MAX`: If no outgoing limit was defined for the receiving
        // shard, this usually just means the feature is not enabled. Or, it
        // could be a special case during resharding events. Or even a bug. In
        // any case, if we cannot know a limit, treating it as literally "no
        // limit" is the safest approach to ensure availability.
        let default_gas_limit = Gas::MAX;

        // Since bandwidth scheduler, a shard is not allowed to send any receipts if it doesn't have a grant.
        let default_size_limit = 0;

        let default_outgoing_limit =
            OutgoingLimit { gas: default_gas_limit, size: default_size_limit };
        let forward_limit = outgoing_limit.entry(shard).or_insert(default_outgoing_limit);

        let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission
            .enabled(apply_state.current_protocol_version)
        {
            gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
        } else {
            gas
        };

        if forward_limit.gas >= admission_gas && forward_limit.size >= size {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "forwarding buffered receipt");
            outgoing_receipts.push(receipt);
            forward_limit.gas = forward_limit.gas.saturating_sub(gas);
            forward_limit.size -= size;
            stats.forwarded_receipts.entry(shard).or_default().add_receipt(size, gas);

            Ok(ReceiptForwarding::Forwarded)
        } else {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "not forwarding buffered receipt");
            Ok(ReceiptForwarding::NotForwarded(receipt))
        }
    }
