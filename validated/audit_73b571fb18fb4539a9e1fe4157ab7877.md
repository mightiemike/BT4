### Title
Unsynchronized reads in `TxCacheDB.get()` during concurrent `flush()`/`put()` can return a false "not present" for an already-cached transaction id, defeating duplicate-transaction detection - (File: chainbase/src/main/java/org/tron/core/db2/common/TxCacheDB.java)

### Summary
`TxCacheDB.get()` reads the `bloomFilters[0]`/`bloomFilters[1]` array elements with no synchronization, memory barrier, or `isValid` check, while `flush()`/`put()` mutate those same array slots (including replacing an entire `BloomFilter` object during epoch rotation) inside a `synchronized` block. Because there is no happens-before edge between the writer and the unsynchronized reader, a concurrently-running `get()` can observe stale or partially-updated bloom filter state and wrongly report a previously-inserted transaction id as absent.

### Finding Description
`bloomFilters` is a plain (non-volatile) array field: `chainbase/.../TxCacheDB.java:65`. Writes to its elements happen in `put()` (called from inside `synchronized void flush(...)`, `TxCacheDB.java:257-261`), including the rotation branch that discards and replaces `bloomFilters[currentFilterIndex]` with a brand-new empty `BloomFilter` (`TxCacheDB.java:210-219`) before re-inserting the key (`TxCacheDB.java:221`).

`get(byte[] key)` (`TxCacheDB.java:181-188`) is **not** `synchronized`, takes no lock, and does not read any `volatile` field (`isValid`, `currentFilterIndex`, `filterStartBlock`) before touching `bloomFilters[0]`/`bloomFilters[1]`:
```java
public byte[] get(byte[] key) {
  if (!bloomFilters[0].mightContain(key) && !bloomFilters[1].mightContain(key)) {
    return null;
  }
  return FAKE_TRANSACTION;
}
```
Since the reading thread establishes no happens-before relationship with the writer thread (the array field itself isn't volatile and `get()` reads none of the volatile guard fields that `flush()`/`put()` writes), the Java Memory Model does not guarantee the reader will observe writes made by `flush()`/`put()` in a timely or ordered fashion. Concretely:
- During a rotation (`blockNum - filterStartBlock > MAX_BLOCK_SIZE`), the writer thread replaces `bloomFilters[currentFilterIndex]` with a new, empty `BloomFilter` object reference and then inserts the key into it. A concurrent `get()` on another thread can, per JMM, still see the *old* object reference (or an incompletely published new one) for an arbitrarily long window, so `mightContain` on both slots can return `false` for a key that was already flushed and durably recorded from the writer's perspective.
- `flush()` explicitly toggles `isValid` around the mutation window (`TxCacheDB.java:258-260`), signaling that the state is "not settled" during that window — but `get()` never consults `isValid`, so the one existing guard mechanism intended for exactly this scenario is unused by readers.

Call-site context: `TxCacheDB` backs `TransactionCache` (`chainbase/.../TransactionCache.java`), which `Manager` uses via `containsTransaction`/dedup checks reachable from unprivileged transaction ingestion (broadcast/validation path), while `flush()` is invoked from the block-commit/snapshot-flush path, which `SnapshotManager` runs on a dedicated per-DB `flush-service` executor thread (`chainbase/.../SnapshotManager.java:155-157`). This confirms `get()` (validation thread) and `flush()` (flush-service thread) execute concurrently on different threads without a shared lock, so the visibility gap above is real and reachable by an ordinary node processing incoming transactions during block flush.

### Impact Explanation
If a transaction id that was already accepted/flushed into the bloom-filter cache is momentarily reported as "not present" due to this visibility race, `Manager`'s duplicate-transaction check can treat a replayed transaction as new and re-admit it, undermining the one-time-settlement guarantee the tx-cache is meant to enforce. Since the bloom filter is probabilistic and advisory (false positives are expected/tolerated), a false *negative* here is a correctness violation of the intended invariant "never say absent for something inserted," risking duplicate execution/duplicate settlement of a transaction across the false-negative window.

### Likelihood Explanation
The race requires precise timing: an unprivileged actor cannot directly control JIT/CPU memory visibility timing, so this is not a deterministically triggerable exploit on demand — it depends on scheduler/memory-model behavior around the exact moment `flush()` rotates or mutates the filters, which happens routinely at every `blockNum - filterStartBlock > MAX_BLOCK_SIZE` boundary and on every block's flush. Given `flush()` runs on every block commit and `get()` is invoked continuously for every incoming transaction, the race window recurs constantly, making it a realistic (if probabilistic/non-deterministic) concurrency defect rather than a purely theoretical one.

### Recommendation
- Make `bloomFilters` accesses safe for concurrent readers: e.g., publish filter state via a `volatile` holder (or `AtomicReferenceArray<BloomFilter<byte[]>>`), or wrap `get()` in the same lock/read-write lock used by `flush()`.
- Have `get()` honor `isValid`/use a `ReadWriteLock` so reads block or retry while a flush is in-flight, restoring the intended semantics of the existing `isValid` flag.
- Ensure the rotation logic in `put()` publishes the newly created `BloomFilter` with a safe-publication pattern (e.g., assign to a `volatile` field) so concurrent readers cannot observe a torn/half-initialized filter.

### Proof of Concept
```java
// Java multi-threaded test plan (JUnit + ExecutorService), placed alongside
// framework/src/test/java/org/tron/core/db/TxCacheDBTest.java

@Test
public void testConcurrentGetDuringFlushRotationNoFalseNegative() throws Exception {
  TxCacheDB db = new TxCacheDB("trans-cache-test", recentTransactionStore, dynamicPropertiesStore);
  db.init();

  byte[] key = randomKey();
  long baseBlock = 1000L;
  // Insert key before rotation boundary
  Map<WrappedByteArray, WrappedByteArray> firstBatch = ...; // key -> blockNum=baseBlock
  db.flush(firstBatch);
  assertNotNull(db.get(key)); // sanity: present

  AtomicBoolean falseNegativeSeen = new AtomicBoolean(false);
  ExecutorService pool = Executors.newFixedThreadPool(2);

  // Writer thread: repeatedly flush batches crossing
  // blockNum - filterStartBlock == MAX_BLOCK_SIZE to force rotation
  Future<?> writer = pool.submit(() -> {
    for (int i = 0; i < 10_000; i++) {
      long blockNum = baseBlock + MAX_BLOCK_SIZE + i;
      Map<WrappedByteArray, WrappedByteArray> batch = buildBatch(randomKey(), blockNum);
      db.flush(batch);
    }
  });

  // Reader thread: hammer get(key) for the originally-inserted key
  Future<?> reader = pool.submit(() -> {
    for (int i = 0; i < 1_000_000; i++) {
      if (db.get(key) == null) {
        falseNegativeSeen.set(true);
      }
    }
  });

  writer.get();
  reader.get();

  assertFalse("get() returned false negative for a previously-flushed key "
      + "during concurrent flush/rotation", falseNegativeSeen.get());
}
```
Expected (buggy) behavior: `falseNegativeSeen` becomes `true` in some runs (non-deterministic, JMM-dependent), demonstrating that `get()` can report an already-cached transaction id as absent while `flush()`/`put()` run concurrently, without needing `key` to actually fall outside the sliding two-filter window.
