## Finding: Replay-verification never checks the state-checkpoint hash, so corrupted/divergent state can be certified as a correct replay

### Title
Replay-verification (`ensure_match_transaction_info`) never checks `state_checkpoint_hash`, allowing a wrong state root to pass verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole function used by the chunk executor's replay/verify path to confirm that a locally re-executed transaction output matches the authoritative, accumulator-committed `TransactionInfo` fetched from a backup/archive. It checks status, gas, `state_change_hash` (write-set hash), and `event_root_hash`, but it deliberately never compares the computed state (or hot-state / position-state) checkpoint root against `txn_info.state_checkpoint_hash()`. This means a state root divergence at a checkpoint boundary is invisible to replay verification.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  It validates status, gas, write-set hash, and event root hash, but the block ending the function contains an explicit acknowledgment that checkpoint hashes are skipped: [2](#0-1) 

This function is the only per-transaction integrity gate used by `ChunkExecutorInner::verify_execution`, which drives the "replay-verify" tooling path (e.g. `db-tool`'s `replay_on_archive`), where a chunk of historical transactions is fetched, re-executed with the VM, and the freshly-computed `TransactionOutput` is checked against the `TransactionInfo` recorded in the backup/archive: [3](#0-2) 

Nowhere else in this replay path is the resulting state (or hot-state, or position-state, used for "trading-native" checkpoints) root hash cross-checked against the archived `TransactionInfo.state_checkpoint_hash()` (and, for `TransactionInfoV1`, `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`). The state-checkpoint computation itself lives in `DoStateCheckpoint`, which does compare computed hashes against "known" hashes when they are explicitly supplied, e.g. `get_state_checkpoint_hashes`: [4](#0-3)  — but the replay-verify caller (`verify_execution`) never wires the archived `state_checkpoint_hash` into that "known hashes" comparison; it relies solely on `ensure_match_transaction_info`, which skips it.

### Impact Explanation
Because replay-verify is the tool operators and auditors rely on to certify that an archived/backed-up transaction history reproduces the exact same ledger state as the original execution, this gap allows a divergent state root (whether from non-determinism, a corrupted backup, a storage/restore bug, or any future consensus/VM change) at a checkpoint boundary to pass `replay_on_archive` and similar verification as "successful," even though the authenticated state root differs from local execution. This is squarely within the requested proof-and-storage pivot: "Hard-fork-only divergence during commit, replay, restore, or proof verification" — a broken verification invariant that would let a materially wrong ledger state be certified as correct without producing any alarm.

### Likelihood Explanation
This isn't a live-mainnet consensus-commit bypass (the actual JMT/state-store root used for live consensus is computed independently of `TransactionInfo.state_checkpoint_hash`), but any use of replay-verify tooling against an archive (which is exactly the intended detection mechanism for state divergence, e.g. around hard forks or state-sync/restore correctness audits) will silently accept a wrong state checkpoint. The comment left in the code by the Aptos team itself (`// TODO(trading-native): ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution. Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS.`) confirms this is a known, reachable, and unaddressed gap, not a hypothetical.

### Recommendation
Extend `ensure_match_transaction_info` (or its caller `verify_execution`) to compute and compare the state checkpoint hash (and, where applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) produced by `DoStateCheckpoint` against the corresponding fields of the archived `TransactionInfo`, failing verification on any mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any dependent feature is enabled in production.

### Proof of Concept
1. Take any transaction chunk with a state-checkpoint boundary (e.g. end of an epoch/block) from a backup/archive.
2. Feed a `TransactionInfo` with a tampered/incorrect `state_checkpoint_hash` (all other fields — `transaction_hash`, `state_change_hash`, `event_root_hash`, `gas_used`, `status` — left correct) into `ChunkExecutorInner::verify_execution` alongside the correctly re-executed transactions/write-sets/events.
3. `ensure_match_transaction_info` at [5](#0-4)  returns `Ok(())` because it never reads `txn_info.state_checkpoint_hash()`.
4. `verify_execution` treats the chunk as fully verified and returns `end_version` as if replay matched, even though the recorded state root is wrong.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
