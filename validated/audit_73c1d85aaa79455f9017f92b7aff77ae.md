### Title
Unauthenticated request-ID collision in confidentialrelay handler's `activeRequests` map allows cross-caller request hijacking/DoS - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`confidentialrelay/handler.go`'s `activeRequests` map is keyed solely by the caller-supplied `req.ID` with no authentication or per-caller namespacing, unlike `requestcache.go`'s `globalId{sender, id}` compound key. Any unauthenticated caller can submit a JSON-RPC request whose `ID` collides with a concurrently in-flight request from another caller and either learn that a request with that ID exists (timing/existence oracle) or deny that request/have their own request denied via the "request ID already exists" error.

### Finding Description
The gateway dispatches incoming JSON-RPC requests directly to the handler with no sender binding: `g.ProcessRequest` calls `h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)` with no additional identity/session context attached to the request [1](#0-0) .

In `confidentialrelay/handler.go`, `HandleJSONRPCUserMessage` performs no authorization step at all (there is no `authorizer`/`AuthResult` in this handler, unlike vault) and immediately calls `h.newActiveRequest(req, callback)` using the raw, attacker-controlled `req.ID`: [2](#0-1) 

`newActiveRequest` keys the `activeRequests` map purely by `req.ID`, with no sender/owner component: [3](#0-2) 

This is weaker than `requestcache.go`, which builds a compound key from both `request.Body.Sender` and `request.Body.MessageId`, so two distinct callers can never collide even if they choose the same message ID: [4](#0-3) 

By contrast, `vault/handler.go` largely closes this gap for its authorized methods (`SecretsCreate/Update/Delete/List`): before `newActiveRequest` is called, `GatewayVaultRequestProcessor.authorizeAndStamp` rewrites `req.ID` to `authorizedOwner + RequestIDSeparator + originalRequestID`, so the map key used for `activeRequests` is effectively namespaced by the cryptographically/allow-list-verified owner, not the raw client-chosen ID [5](#0-4) , and vault's `newActiveRequest`/map lookup then operates on that owner-prefixed ID [6](#0-5) . The one vault exception is `MethodPublicKeyGet`, which explicitly skips authorization and calls `newActiveRequest` with the raw ID [7](#0-6) , but this path only guards a shared, non-secret, heavily-cached public key value common to all callers, so a collision there has negligible confidentiality/integrity impact.

`confidentialrelay/handler.go` has no equivalent owner-prefixing step anywhere in its pipeline, so the weaker, purely-ID-keyed namespacing described in the audit question applies to it in full.

### Impact Explanation
An attacker who submits a request with the same `ID` as a victim's concurrent, legitimate `confidentialrelay` request (`MethodSecretsGet`/`MethodCapabilityExec`) will either: (a) receive a `HandlerError` ("request ID already exists") which confirms the victim's request is currently active — an existence/timing side channel about another caller's activity — or (b) if the attacker's colliding request is registered first, cause the victim's legitimate request to be rejected outright, a request-availability denial. This matches a scoped "request availability denial / information leak" impact for the confidentialrelay flow specifically.

### Likelihood Explanation
Exploitability requires only that the attacker be able to send arbitrary JSON-RPC requests to the same gateway/DON concurrently with a victim and guess or otherwise learn/predict the victim's chosen `ID` value — both preconditions given by the audit prompt. No node-operator privilege, leaked keys, or social engineering is needed; the `confidentialrelay` handler performs no authentication/authorization check before registering the ID in `activeRequests`, so the attack surface is any unauthenticated caller of the gateway's confidentialrelay service. Likelihood of collision is entirely dependent on ID predictability/guessability, which is outside this handler's control but is not mitigated by any namespacing here (whereas it is largely mitigated in vault via owner-prefixing).

### Recommendation
In `confidentialrelay/handler.go`, namespace `activeRequests` keys by an authenticated/verified caller identity in addition to the raw request ID (e.g., adopt the same pattern vault uses: authorize/authenticate the caller and prefix `req.ID` with an owner identifier before inserting into `activeRequests`), mirroring `requestcache.go`'s `globalId{sender, id}` compound-key approach. At minimum, derive the namespace component from a value the caller cannot forge (verified auth/session identity), not from client-supplied request fields.

### Proof of Concept
Integration test in `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. Construct two independent "callers" (no distinguishing auth is required/verified by this handler) issuing `jsonrpc.Request{ID: "collide-1", Method: MethodSecretsGet}` concurrently to the same handler instance.
2. Caller A calls `HandleJSONRPCUserMessage` first and blocks (simulate slow node responses so the request stays in `activeRequests`).
3. While A's request is still active, Caller B calls `HandleJSONRPCUserMessage` with the same `ID`; assert it returns the `"request ID already exists"` error, proving cross-caller ID collision with no sender distinction.
4. Differential comparison: run the same two-caller sequence against `requestcache.go`'s `NewRequest` with distinct `Body.Sender` values but identical `MessageId`; assert both succeed without collision, demonstrating the stronger per-sender isolation there versus `confidentialrelay/handler.go`'s weaker global-ID-only isolation.

	defer h.mu.Unlock()

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil
