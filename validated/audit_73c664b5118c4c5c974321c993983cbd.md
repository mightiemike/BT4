### Title
Panic-inducing `unwrap()` on `receiver_shard_id()` for stale `GlobalContractDistribution` receipts causes a transaction-triggered chain halt - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unwraps the result of `Receipt::receiver_shard_id`, which can return `Err(EpochError::ShardingError)` for a `GlobalContractDistribution` receipt whose `target_shard` no longer exists in the current shard layout's split history. Because any account can trigger the creation of a `GlobalContractDistribution` receipt via a normal `DeployGlobalContract` transaction, and delayed/backlogged receipts can outlive the split-history horizon after successive reshardings, this `unwrap()` is reachable and will panic every honest validator processing the delayed-receipt queue for the affected shard, halting the chain — the direct DoS analog of the Net-SNMP `_set_key` NULL-pointer-dereference crash (CVE-2018-18065), just triggered via an unhandled `Result::Err` instead of a NULL pointer.

### Finding Description
`Receipt::receiver_shard_id` (core/primitives/src/receipt.rs) explicitly documents and handles the case where a `GlobalContractDistribution` receipt's `target_shard` is stale relative to the current shard layout: [1](#0-0) 

When `target_shard` cannot be resolved to a descendant in the current layout (`resolve_to_current_shard` returns `None`), the function deliberately returns `Err(EpochError::ShardingError(...))` rather than panicking — indicating the authors anticipated this as a recoverable, expected error condition.

However, the only caller inside the delayed-receipt draining path ignores this contract and unwraps the result directly: [2](#0-1) 

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

This function is invoked from `DelayedReceiptQueueWrapper::pop`, which is on the hot path of `process_delayed_receipts` used by every `Runtime::apply` call: [3](#0-2) 

A `GlobalContractDistribution` receipt is created whenever any account deploys a global contract (`DeployGlobalContract` action — available to any unprivileged signer) and is forwarded shard-by-shard via `forward_distribution_next_shard`: [4](#0-3) 

If this receipt becomes congested and is pushed to the delayed-receipt queue (e.g., because the target shard's compute/gas budget is saturated) and the shard undergoes further resharding while the receipt sits delayed, `target_shard` may point to a shard ID that predates the split history retained by the current `ShardLayout`. When `pop()` is eventually called to dequeue it, `receipt_filter_fn` panics via `.unwrap()` on the `Err(EpochError::ShardingError)`.

Because `process_delayed_receipts` is called unconditionally by every validator/chunk-producer applying that shard's chunk, this is not a localized failure — every node computing the state transition panics identically, producing a `RuntimeError`-turned-`panic!` that halts chunk/block production for the affected shard (a network-wide, deterministic denial of service), directly comparable to the remotely triggerable NULL-pointer crash in `_set_key`.

A test in the repository already documents this exact scenario and its consequence: [5](#0-4) 

### Impact Explanation
A panic inside `Runtime::apply` (via `process_delayed_receipts` → `receipt_filter_fn`) is unrecoverable at the node level — it is not converted into an `InvalidTx`/`InvalidTxError` outcome, it aborts the apply call for every honest validator processing that shard's chunk. Since state-transition logic must be deterministic across all validators, all nodes tracking the affected shard hit the identical panic when draining the delayed queue, producing a chain halt for that shard (denial of service) rather than a localized error. This satisfies the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Triggering requires: (1) any unprivileged account submitting a `DeployGlobalContract` transaction (fully permitted, low-cost action any signer can perform), (2) the resulting `GlobalContractDistribution` receipt getting delayed due to congestion on its current target shard (achievable by an attacker saturating that shard's compute budget with cheap gas-burning calls, as demonstrated in the referenced test), and (3) at least two resharding events occurring on the network while the receipt remains delayed, moving the target shard's ID outside the retained split history. Dynamic resharding is a protocol-scheduled event (not directly attacker-controlled), so this requires the attacker's window to overlap with naturally occurring reshardings — achievable but timing-dependent, hence Medium likelihood rather than trivially always-on.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (return `Result<bool, RuntimeError>` and map `EpochError::ShardingError` to a well-defined outcome, e.g., treat unresolved stale receipts as belonging to no live shard and drop/burn them safely, or route them into a recovery path), mirroring how `receiver_shard_id`'s caller in `ReceiptSinkV2::forward_from_buffer_to_shard` already propagates the error via `?` instead of unwrapping. Additionally, consider bounding how far shard split history must be retained so `resolve_to_current_shard` cannot silently drift out of range while a receipt is delayed.

### Proof of Concept
1. Attacker (or any user) submits `DeployGlobalContract` from an account on shard `S_A`, producing a `GlobalContractDistribution` receipt with `target_shard = S_A`.
2. Attacker saturates `S_A`'s per-chunk compute limit every block (e.g., repeated `burn_gas_raw` calls) so the distribution receipt is pushed into the delayed-receipt queue instead of being processed immediately.
3. While the receipt remains delayed, two consecutive dynamic-resharding splits occur on the network (network-scheduled based on configured thresholds), causing `S_A`'s shard ID to fall outside the split history retained by the now-current `ShardLayout`.
4. Once congestion eases and the delayed queue is drained, `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, which calls `receiver_shard_id` → `resolve_to_current_shard` → `None` → `Err(EpochError::ShardingError)` → `.unwrap()` panics.
5. Every honest validator applying that shard's chunk panics identically, halting chunk/block production for the shard — exactly reproduced by `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs`.

    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,

    state_update: &mut TrieUpdate,

    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(

            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );

        .shard_ids()

        return Ok(());

    let mut next_receipt = Receipt::new_global_contract_distribution(predecessor_id, next_receipt);
    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);

                receiver_account_id: next_receipt.receiver_id().clone(),
                shard_id: apply_state.shard_id,

        ));
    }
    receipt_sink.forward_or_buffer_receipt(next_receipt, apply_state, state_update)?;
