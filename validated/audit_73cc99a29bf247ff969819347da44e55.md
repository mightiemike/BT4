## Title
Signer weight double-counted across `total_weight_approved`/`total_weight_rejected` when a signer changes vote from Reject to Accept - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tracks per-block signer consensus with two independently-guarded weight counters, `total_weight_approved` and `total_weight_rejected`, that are supposed to satisfy the invariant `total_weight_approved + total_weight_rejected <= total_weight` (each signer's weight should be attributed to at most one bucket). The guard used for the reject path and the guard used for the accept path check two *different* sets, so a signer who first rejects and later accepts (or the reverse ordering is blocked, but this one is not) gets its weight counted in both totals.

### Finding Description
In the `BlockResponse::Rejected` handler, weight is only added once per signer, guarded by `block.responded_signers.insert(slot_id)`: [1](#0-0) 

In the `BlockResponse::Accepted` handler, weight is added guarded by a *different* map, `block.gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

and only afterwards does the code insert into both `gathered_signatures` and `responded_signers`: [3](#0-2) 

Because the reject path's guard (`responded_signers`) is a superset of what the accept path checks (`gathered_signatures`), the two directions are asymmetric:
- Accept → Reject: blocked correctly, since `responded_signers` already contains the slot from the earlier accept, so the reject branch's `insert` returns `false` and `total_weight_rejected` is not incremented.
- Reject → Accept: **not blocked**. The signer's earlier rejection sets `responded_signers` but not `gathered_signatures`. When the same signer later sends a valid `Accepted` message for the same block, `!block.gathered_signatures.contains_key(&slot_id)` is `true`, so `total_weight_approved` is incremented — while the stale weight contribution the same signer already made to `total_weight_rejected` is never removed.

The signer set membership and per-signer weight come from the Nakamoto reward-cycle signer set computed off-chain and evaluated in `signers.clar`/`signer_set.rs`, so this is triggerable by any single signer in the active reward cycle sending two StackerDB messages for the same block (reject, then accept) — no majority or admin privilege is required.

### Impact Explanation
This breaks the equality the miner-side coordinator relies on for consensus bookkeeping: `total_weight_approved + total_weight_rejected` can now exceed `self.total_weight`. The coordinator's rejection-timeout logic in `SignerCoordinator::get_block_status` uses `total_weight_rejected` to decide whether "a blocking minority (>30% weight)" has rejected the block and returns `NakamotoNodeError::SignersRejected`: [4](#0-3) 

Because a signer's rejection weight is never retracted after it later accepts, stale rejection weight can persist and combine with genuinely-current rejections from other signers to push `total_weight_rejected` over the blocking-minority threshold even though the real, currently-outstanding disapproval is lower — the miner may incorrectly treat a block as globally rejected (and separately bump `naka_rejected_blocks`/permanently exclude transactions) when the actual live signer weight supports acceptance. Conversely, because the approve/reject state is tracked per in-memory `BlockStatus` object per miner process rather than being canonically resolved from a single source of truth, two nodes computing `total_weight_approved`/`total_weight_rejected` from a differently-ordered set of the same StackerDB messages can reach different consensus verdicts for the same block, causing temporary tip disagreement among miners. This matches the "High" impact class: a minority-triggerable divergence in the block-acceptance verdict bounded to a temporary tip disagreement (not a deep, irreversible fork, since actual block inclusion still requires real gathered signatures reaching `weight_threshold`).

### Likelihood Explanation
A single non-privileged signer needs only to send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — a realistic scenario for a signer that initially rejects due to stale local state (e.g. it hasn't yet seen the parent tenure) and later re-evaluates and signs once its view catches up, or simply due to a signer client bug/retry that resends a changed vote. No coordination with other signers or elevated privilege is required, making this a minority (single-actor) triggerable condition.

### Recommendation
Guard both branches with the same "has this signer already responded" check, and/or maintain a single per-signer vote state (Accepted/Rejected) instead of two independently-guarded maps, so that a vote change retracts the previous weight contribution before adding the new one:
```rust
// On Accepted:
if let Some(prior) = block.vote_state.insert(slot_id, Vote::Accepted) {
    if prior == Vote::Rejected {
        block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
    }
}
if block.vote_state.get(&slot_id) == Some(&Vote::Accepted) { /* add to approved once */ }
```
More conservatively, once a signer has recorded any response (`responded_signers`), do not allow a second vote of the opposite kind to alter either weight total (make the first vote authoritative), which matches the existing behavior for Accept→Reject and should be made symmetric for Reject→Accept.

### Proof of Concept
1. Reward cycle N has signers `S1..Sk` with weights `w1..wk`; total weight `W = weight_threshold + blocking_minority`.
2. Miner proposes block `B`; `StackerDBListener` creates `BlockStatus{ total_weight_approved: 0, total_weight_rejected: 0, ... }`.
3. Signer `S1` sends `BlockResponse::Rejected` for `B`. Handler executes `block.responded_signers.insert(1)` → `true`, so `total_weight_rejected += w1`.
4. Enough other signers similarly reject such that `total_weight_rejected` is just below the blocking-minority threshold, i.e. `total_weight_rejected + weight_threshold <= total_weight` still (block not yet globally rejected).
5. `S1` (having re-evaluated) now sends a valid `BlockResponse::Accepted` for the same `B`. The accept handler checks `!block.gathered_signatures.contains_key(&1)` → `true` (since `S1` never appeared in `gathered_signatures`), so `total_weight_approved += w1`. `S1`'s weight `w1` is now counted in *both* `total_weight_approved` and `total_weight_rejected` simultaneously.
6. If additional signers reject afterward, `total_weight_rejected` (still including `S1`'s stale `w1`) can cross the blocking-minority threshold sooner than it should — causing `get_block_status` to return `NakamotoNodeError::SignersRejected` for a block that, based on currently-standing (non-stale) votes, should not yet be rejected, or vice versa causing divergent verdicts between miner processes that received the two messages in different relative timing/order.
