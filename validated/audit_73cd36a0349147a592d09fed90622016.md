### Title
Missing global outbound-amount tracking allows cumulative Push→Solana bridge transfers to exceed Solana's u64 balance capacity - (File: `x/uexecutor/keeper/outbound.go`, `x/uexecutor/keeper/create_outbound.go`, `universalClient/chains/svm/tx_builder.go`)

### Summary
Push Chain validates that each individual outbound `Amount` fits within Solana's `u64` range only at the point the transaction is built for signing/broadcast (`amount.IsUint64()`), but no component anywhere in the outbound lifecycle — `BuildOutboundsFromReceipt`, `handleFailedOutbound`/`handleSuccessfulOutbound`, or the `uregistry` token config — tracks the cumulative total amount of a given PRC20/token ever bridged out to a non-EVM (Solana) chain. Because Solana token accounts and the vault program represent balances as `u64` lamports/token units, repeated legitimate outbound transfers that individually pass the per-tx check can, in aggregate, drive the destination-chain vault or recipient balance past `u64::MAX`, causing an overflow/wraparound or a stuck transaction on the Solana side.

### Finding Description
`x/uexecutor/keeper/create_outbound.go`'s `BuildOutboundsFromReceipt` [1](#0-0)  constructs an `OutboundTx` from every `UniversalTxOutboundEvent` emitted by the `UNIVERSAL_GATEWAY_PC` contract with no aggregate accounting — each outbound is evaluated purely in isolation with only a per-destination-chain "is outbound enabled" boolean check, not a running total.

The only bound on amount size is enforced downstream, per-transaction, in the Solana `TxBuilder`: both `GetOutboundSigningRequest` and `BuildOutboundTransaction` independently call `amount.SetString(...)` and reject only if `!amount.IsUint64()` [2](#0-1) [3](#0-2) . This check bounds only a single transfer's magnitude, not the sum of all transfers ever sent to a given Solana vault/token account.

There is no counter or accumulator anywhere in `x/uexecutor` (e.g. in `handleFailedOutbound`/`handleSuccessfulOutbound` in `x/uexecutor/keeper/outbound.go` [4](#0-3) ) or in `x/uregistry` token configuration that records "total amount sent to chain X for token Y so far." A search of the codebase for total/cumulative/global-cap tracking constructs returns nothing relevant to outbound accounting.

Since ordinary, unprivileged users can repeatedly submit legitimate inbound transactions (each within normal limits) whose payloads trigger withdraw/outbound calls to the Universal Gateway, or repeatedly move funds cross-chain and back, the aggregate value routed to a single Solana-side account is fully attacker-influenced and unbounded by any on-chain invariant other than the u64 cap of each individual transfer.

### Impact Explanation
If the cumulative amount routed to a specific Solana vault/recipient token account (which stores balances as `u64`) exceeds `u64::MAX`, Solana-side arithmetic could overflow or the transaction could be rejected/stuck, potentially locking further legitimate outbound transfers to that chain, or (if any wraparound occurs in destination program logic that isn't checked) creating unexpected balance states. This maps to the "permanent freezing of user or protocol-controlled funds" and "unauthorized state transitions in universal execution flows" categories in scope, since ordinary outbound flow reachable by any user could push chain state past a hard capacity boundary with no gate to prevent it.

### Likelihood Explanation
Low likelihood in the near term: reaching `u64::MAX` (≈1.8×10^19 base units) cumulatively for a single token/chain pair requires an extremely large volume of transfers relative to realistic token supplies and decimals. It requires sustained usage/volume, not a single crafted transaction, and depends on token decimal configuration and total token supply. However, it is not privileged-actor-dependent — it is reachable purely through the ordinary, honest, unprivileged outbound flow.

### Recommendation
Track a per-(destination-chain, token) cumulative outbound total in `x/uregistry` or `x/uexecutor` state, incremented in `BuildOutboundsFromReceipt` (or in `handleSuccessfulOutbound`) each time an outbound is created/completed for a non-EVM destination. Before creating a new outbound, check that `runningTotal + newAmount` does not exceed the destination chain's native balance representation cap (e.g., `u64::MAX` for Solana/SVM chains), and revert/reject the transaction if it would.

### Proof of Concept
Not directly demonstrable without extremely large cumulative bridge volume; the vulnerability is structural (absence of an aggregate check) rather than a single-transaction exploit. Conceptually:
1. Repeatedly submit valid inbound `FUNDS`/`FUNDS_AND_PAYLOAD` messages whose payload invokes the Universal Gateway's withdraw function targeting the same Solana destination/token, each with `Amount` safely below `u64::MAX`.
2. Each individual `BuildOutboundsFromReceipt` call and each `TxBuilder.GetOutboundSigningRequest`/`BuildOutboundTransaction` call passes its `IsUint64()` check in isolation.
3. Over many iterations, the destination Solana vault/recipient's cumulative `u64` balance approaches and eventually would exceed `u64::MAX`, with no code path in `x/uexecutor` or `universalClient` ever aggregating or bounding the running total to prevent this.

// handleFailedOutbound mints back the bridged tokens to the revert recipient,
// then attempts to refund any excess gas (gasFee - gasFeeUsed) just like a
// successful outbound would. Both operations are recorded on the outbound.
func (k Keeper) handleFailedOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	// Only revert bridged funds for funds-related tx types
	if outbound.TxType == types.TxType_FUNDS || outbound.TxType == types.TxType_GAS_AND_PAYLOAD ||
		outbound.TxType == types.TxType_FUNDS_AND_PAYLOAD {

		// Decide revert recipient safely
		recipient := outbound.Sender
		if outbound.RevertInstructions != nil &&
			outbound.RevertInstructions.FundRecipient != "" {
			recipient = outbound.RevertInstructions.FundRecipient
		}

		amount := new(big.Int)
		amount, ok := amount.SetString(outbound.Amount, 10)
		if !ok {
			return fmt.Errorf("invalid amount: %s", outbound.Amount)
		}
		receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)

		pcTx := types.PCTx{
			Sender:      outbound.Sender,
			BlockHeight: uint64(ctx.BlockHeight()),
		}
		// Capture tx hash from receipt even on EVM revert for debugging.
		if receipt != nil {
			pcTx.TxHash = receipt.Hash
			pcTx.GasUsed = receipt.GasUsed
		}
		if err != nil {
			pcTx.Status = "FAILED"
			pcTx.ErrorMsg = err.Error()
			outbound.PcRevertExecution = &pcTx
			// Re-mint failed — mark as ABORTED for manual intervention
			return k.AbortOutbound(ctx, utxId, outbound,
				fmt.Sprintf("failed to re-mint tokens for revert: %s", err.Error()))
		}
		pcTx.TxHash = receipt.Hash
		pcTx.GasUsed = receipt.GasUsed
		pcTx.Status = "SUCCESS"
		outbound.PcRevertExecution = &pcTx
		k.Logger().Info("outbound failed: funds re-minted for revert",
			"utx_id", utxId,
			"outbound_id", outbound.Id,
			"tx_hash", receipt.Hash,
		)
	}

	outbound.OutboundStatus = types.Status_REVERTED
	k.Logger().Info("outbound reverted",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"dest_chain", outbound.DestinationChain,
	)

	// Refund excess gas regardless of tx type — gas was consumed on the external
	// chain whether the execution succeeded or failed.
	k.applyGasRefund(ctx, &outbound, obs)

	return k.UpdateOutbound(ctx, utxId, outbound)
}

// handleSuccessfulOutbound refunds unused gas fee when gasFee > gasFeeUsed.
func (k Keeper) handleSuccessfulOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	k.Logger().Info("outbound completed successfully",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"dest_chain", outbound.DestinationChain,
	)
	k.applyGasRefund(ctx, &outbound, obs)
	return k.UpdateOutbound(ctx, utxId, outbound)
}
