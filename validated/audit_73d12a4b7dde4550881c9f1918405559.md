## Analog Found

### Title
Contract deletion (`selfdestruct`) leaves stale contract-state and account-asset entries uncleared - (`actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.deleteContract()` is the java-tron equivalent of the reported `pruneQuorums()` bug: it deletes the "outer" record for a contract address but does not clear all of the "inner" per-address structures associated with that account, leaving stale nested data reachable if the address is later reused.

### Finding Description
`RepositoryImpl.deleteContract(byte[] address)` only clears three stores: [1](#0-0) 

```java
public void deleteContract(byte[] address) {
  getCodeStore().delete(address);
  getAccountStore().delete(address);
  getContractStore().delete(address);
}
```

It does **not** delete the corresponding entry in `ContractStateStore` (accessed via `getContractState`/`updateContractState`, keyed directly by the raw contract address), nor does it clear `AccountAssetStore` entries for that address: [2](#0-1) 

This is invoked through `Program.suicide()`/`suicide2()` when a contract self-destructs (via `getResult().addDeleteAccount(...)`, consumed later in `VMActuator.execute()`), i.e. it is reachable directly from a broadcast TVM transaction with no privileged access required. [3](#0-2) 

Just like the Solidity report — where `delete self.quorumSignatureSenders[h]` clears the outer mapping entry but leaves the inner mapping's storage slots intact — `deleteContract()` clears the "outer" account/contract/code records but leaves the "inner"/associated `ContractStateStore` record (and any un-migrated asset entries) behind, keyed by the same address.

Separately, per-slot contract storage (`Storage` class, `StorageRowStore`) is keyed by `addrHash = sha3(address)` or, for `CREATE2`-created contracts, `sha3(address || creationTxHash)` via `Storage.generateAddrHash()`: [4](#0-3) 

This transaction-hash salting appears intended to prevent "resurrection" storage collisions when a new contract is deployed to a previously self-destructed address, but I was not able to fully verify from the available code that this salting is applied on *every* contract-creation code path (vs. only `CREATE2`), nor whether `ContractStateStore`/`AccountAssetStore` are protected by any similar salting. This remains an open question that a background engineer with full repo access should confirm.

### Impact Explanation
If an address is reused after a contract self-destructs (e.g., through `CREATE2` redeployment to the same address, which java-tron supports per `Op.java`/`OperationRegistry.java`/`MUtil.java` references), the new contract could inherit stale `ContractStateCapsule` data (and possibly stale asset-related bookkeeping) left behind by the destroyed contract, because `deleteContract()` never purges it. Depending on what `ContractStateCapsule` tracks (e.g., "created"/frozen flags, nonce-like state used by TVM logic), this could lead to state confusion, incorrect resource/energy accounting, or unexpected TVM behavior for the newly deployed contract — a form of accounting/state corruption reachable purely from broadcast transactions.

### Likelihood Explanation
Likelihood is moderate and depends on details I could not fully confirm in this pass: (1) whether the raw `StorageRowStore` slot keys are always salted with the creation transaction hash (mitigating slot collision) for all contract-creation paths, and (2) what exactly `ContractStateCapsule` stores and how sensitive it is to staleness. If storage-row salting is comprehensive, the primary risk narrows to the un-cleared `ContractStateStore`/`AccountAssetStore` entries, which is a smaller but still real gap directly parallel to the reported bug class (delete-outer-without-clearing-inner).

### Recommendation
Extend `RepositoryImpl.deleteContract()` to also delete the corresponding `ContractStateStore` entry and any residual `AccountAssetStore` entries for the address, mirroring the recommendation in the original report to "properly clear the inner mappings." Additionally, confirm and document that all contract-creation code paths (not just `CREATE2`) salt storage-row keys sufficiently to prevent stale-slot reuse, or explicitly clear `StorageRowStore` rows for the address on `deleteContract()`.

### Proof of Concept
Conceptual PoC (requires live-node verification, not confirmed against runtime behavior in this pass):
1. Deploy Contract A via `CreateSmartContract`, causing `ContractStateStore`/`AccountAssetStore` entries to be written for address `X`.
2. Contract A calls `selfdestruct`/`suicide2`, triggering `RepositoryImpl.deleteContract(X)`, which removes `AccountStore`, `ContractStore`, and `CodeStore` entries for `X` but leaves `ContractStateStore[X]` intact.
3. Redeploy a new Contract B to the same address `X` (e.g., via `CREATE2` with identical salt/init-code, or after nonce/address collision conditions), and observe that stale `ContractStateStore` data for `X` is still readable/used by Contract B's execution context.

  private static byte[] addrHash(byte[] address) {
    return Hash.sha3(address);

  private static byte[] addrHash(byte[] address, byte[] trxHash) {
    if (ByteUtil.isNullOrZeroArray(trxHash)) {
      return Hash.sha3(address);
    }
    return Hash.sha3(ByteUtil.merge(address, trxHash));
  }

  public void generateAddrHash(byte[] trxId) {
    // update addreHash for create2
    addrHash = addrHash(address, trxId);
  }
