### Title
Unprivileged rescue-fund griefing permanently blocks a victim's legitimate stuck-fund rescue - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
`AttachRescueOutboundFromReceipt` accepts any `RescueFundsOnSourceChain` event emitted by the `UNIVERSAL_GATEWAY_PC` contract and attaches a `RESCUE_FUNDS` outbound to the referenced `originalUtxId` without verifying that the caller (`event.Sender`) is the account entitled to rescue those specific stuck funds. Combined with the one-active-rescue-per-UTX guard, an attacker can permissionlessly create a bogus rescue outbound against a victim's stuck `UniversalTx`, blocking the victim's real rescue until validator quorum resolves the attacker's outbound — and the attacker can repeat this indefinitely.

### Finding Description
`AttachRescueOutboundFromReceipt` at [1](#0-0)  decodes a `RescueFundsOnSourceChain` log and looks up the `originalUtx` purely from the attacker-controlled `event.UniversalTxId` field embedded in the log — there is no check binding `event.Sender` to `originalUtx.InboundTx.Sender` or to any owner of the stuck funds.

The eligibility checks only verify the *UTX's* state (deposit failed for CEA, or a reverted auto-revert for non-CEA) [2](#0-1) , not who is allowed to trigger the rescue.

Immediately after, the code enforces a single-active-rescue invariant per UTX:

```
// Guard against duplicate rescue outbounds: reject if an active rescue
// (PENDING or OBSERVED) already exists. A REVERTED rescue may be retried.
``` [3](#0-2) 

This is confirmed by the test `"second rescue is rejected when first is PENDING"` and `"second rescue is rejected when first is OBSERVED"` [4](#0-3) , which show the guard is keyed solely on `originalUtxId`, with no sender/ownership check anywhere in the eligibility path.

Because any address can trigger the `RescueFundsOnSourceChain` event on the source-chain gateway referencing an arbitrary `universalTxId` (the decode path only reads `event.Sender` for bookkeeping and never authorizes against it — see `DecodeRescueFundsOnSourceChainFromLog` [5](#0-4) ), an attacker who is not the depositor of the stuck UTX can submit their own rescue transaction that references the victim's `originalUtxId`. This creates a `PENDING` `RESCUE_FUNDS` outbound on the victim's UTX, which the guard treats as "active," making the victim's own genuine rescue call fail with `"already has an active rescue outbound"` until validators reach quorum and mark the attacker's bogus rescue `REVERTED` (a process that requires honest-validator observation of the destination-chain tx, i.e. it is not instantaneous and outside the victim's control) [3](#0-2) .

This is the same bug class as the Locke `arbitraryCall()`/`incentives[who]` issue: a permissionless, attacker-triggerable write to shared per-key state (`incentives[who]` there, "active rescue outbound per UTX" here) that must be reset before a legitimate/privileged flow can proceed, and the reset is gated behind a slow, externally-driven process (stream end in Locke; validator quorum finalization here) rather than being atomic with the legitimate actor's own action.

### Impact Explanation
Funds legitimately stuck on a source chain (failed CEA deposit or failed auto-revert) cannot be rescued by their rightful owner while an attacker keeps a bogus rescue outbound "active" for that UTX. This is a denial-of-service on the fund-recovery/refund path, matching the "permanent freezing... of user or protocol-controlled funds" and "corruption of ... refund accounting" impact categories in scope. The attacker can repeat the griefing after each of their bogus rescues resolves to `REVERTED`, indefinitely delaying recovery of the victim's stuck funds. Severity is bounded by the fact that this delays rather than permanently destroys funds, and by the attacker needing to spend gas on the source chain for each griefing attempt, but the asymmetry (cheap griefing vs. costly/slow resolution requiring validator quorum) makes this a practical, unprivileged, repeatable denial-of-service against a specific victim's fund recovery.

### Likelihood Explanation
No privileged access is required — an attacker only needs to be able to call the source-chain gateway's rescue-triggering function (or otherwise produce a matching `RescueFundsOnSourceChain` log) referencing a `universalTxId` for a UTX that is publicly known to be eligible for rescue (stuck-fund UTX IDs and their status are observable via `GetUniversalTx` queries). The trigger is a normal user transaction path, requiring only that the attacker knows an eligible target `universalTxId`, which is derivable/observable on-chain. This makes the attack straightforward to mount at low, repeatable cost.

### Recommendation
Bind the rescue-eligibility check to the account authorized to recover the stuck funds — e.g., require `event.Sender` (or the transaction's authenticated origin) to match `originalUtx.InboundTx.Sender`, or the resolved refund recipient (`RevertInstructions.FundRecipient`), before attaching the `RESCUE_FUNDS` outbound in `AttachRescueOutboundFromReceipt`. If the source-chain gateway contract also lacks this restriction, the same authorization check should be added there so an unrelated caller cannot even emit a rescue event for someone else's stuck UTX. Alternatively/additionally, allow multiple outstanding rescue outbounds per UTX from different senders so a legitimate attempt is never blocked purely by the existence of a bogus one from an unrelated address.

### Proof of Concept
1. An honest user's inbound is a CEA inbound whose PC-side deposit fails (`PcTx[0].Status == "FAILED"`), making its `originalUtxId` eligible for rescue, as set up in `setupRescueFundsTest` [6](#0-5) .
2. Before the victim submits their own rescue transaction on the source chain, an attacker (unrelated address, not `originalUtx.InboundTx.Sender`) submits a transaction to the source-chain `UniversalGatewayPC` contract that emits `RescueFundsOnSourceChain` with `universalTxId = originalUtxId` and `Sender = attacker`.
3. `AttachRescueOutboundFromReceipt` processes this log, passes all eligibility checks (which only look at the UTX's own state, not the caller), and attaches a `PENDING` `RESCUE_FUNDS` outbound to `originalUtxId`, exactly as in the flow validated by the "rescue outbound is attached" test [7](#0-6) .
4. The victim now submits their own legitimate rescue transaction referencing the same `originalUtxId`. `AttachRescueOutboundFromReceipt` rejects it with `"rescue: UTX %s already has an active rescue outbound"`, matching the guard demonstrated in the "second rescue is rejected when first is PENDING" test [8](#0-7) .
5. The victim must wait for validators to reach quorum and mark the attacker's bogus rescue `REVERTED` before retrying [9](#0-8)  — and the attacker can immediately repeat step 2 to re-block the victim.

func (k Keeper) AttachRescueOutboundFromReceipt(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalGatewayPC := strings.ToLower(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_GATEWAY_PC"].Address)

	evmChainID, err := utils.ExtractEvmChainID(ctx.ChainID())
	if err != nil {
		return fmt.Errorf("rescue: failed to extract EVM chain ID: %w", err)
	}
	pushChainCaip := fmt.Sprintf("eip155:%s", evmChainID)

	for _, lg := range receipt.Logs {
		if lg.Removed {
			continue
		}
		if strings.ToLower(lg.Address) != universalGatewayPC {
			continue
		}
		if len(lg.Topics) == 0 {
			continue
		}
		if strings.ToLower(lg.Topics[0]) != strings.ToLower(types.RescueFundsOnSourceChainEventSig) {
			continue
		}

		event, err := types.DecodeRescueFundsOnSourceChainFromLog(lg)
		if err != nil {
			return fmt.Errorf("failed to decode RescueFundsOnSourceChain: %w", err)
		}

		// The universalTxId in the event is a 0x-prefixed bytes32 matching our UTX key.
		originalUtxId := strings.TrimPrefix(event.UniversalTxId, "0x")

		originalUtx, found, err := k.GetUniversalTx(ctx, originalUtxId)
		if err != nil {
			return fmt.Errorf("rescue: failed to fetch UTX %s: %w", originalUtxId, err)
		}
		if !found {
			return fmt.Errorf("rescue: original UTX %s not found", originalUtxId)
		}
		if originalUtx.InboundTx == nil {
			return fmt.Errorf("rescue: UTX %s has no inbound tx", originalUtxId)
		}

func TestRescueFunds(t *testing.T) {
	prc20Addr := utils.GetDefaultAddresses().PRC20USDCAddr
	senderAddr := common.HexToAddress(utils.GetDefaultAddresses().DefaultTestAddr)

	t.Run("rescue outbound is attached to original UTX on valid CEA inbound with failed deposit", func(t *testing.T) {
		chainApp, ctx, _, utxId, _ := setupRescueFundsTest(t, 4)

		log := buildRescueFundsLog(t, utxId, prc20Addr, senderAddr,
			"eip155", big.NewInt(111), big.NewInt(1_000_000_000), big.NewInt(200_000))
		receipt := makeRescueReceipt(t, "0xrescuetx01", log)
		pcTx := uexecutortypes.PCTx{TxHash: "0xrescuetx01", Status: "SUCCESS"}

		err := chainApp.UexecutorKeeper.AttachRescueOutboundFromReceipt(ctx, receipt, pcTx)
		require.NoError(t, err)

		utx, found, err := chainApp.UexecutorKeeper.GetUniversalTx(ctx, utxId)
		require.NoError(t, err)
		require.True(t, found)

		rescueObs := findRescueOutbound(utx)
		require.NotNil(t, rescueObs, "RESCUE_FUNDS outbound must be attached")
		require.Equal(t, uexecutortypes.Status_PENDING, rescueObs.OutboundStatus)
		require.Equal(t, uexecutortypes.TxType_RESCUE_FUNDS, rescueObs.TxType)
		require.Equal(t, "eip155:11155111", rescueObs.DestinationChain)
		require.Equal(t, "1000000", rescueObs.Amount)
		require.Equal(t, "111", rescueObs.GasFee)

		// The rescue call must be recorded as a PCTx in the UTX history.
		// UTX already had the failed deposit PCTx; the rescue pcTx is appended after it.
		require.Greater(t, len(utx.PcTx), 1, "rescue PCTx must be appended to UTX history")
		lastPcTx := utx.PcTx[len(utx.PcTx)-1]
		require.Equal(t, "0xrescuetx01", lastPcTx.TxHash)
		require.Equal(t, "SUCCESS", lastPcTx.Status)
	})

func DecodeRescueFundsOnSourceChainFromLog(log *evmtypes.Log) (*RescueFundsOnSourceChainEvent, error) {
	if len(log.Topics) < 4 {
		return nil, fmt.Errorf("RescueFundsOnSourceChain: need 4 topics, got %d", len(log.Topics))
	}
	if strings.ToLower(log.Topics[0]) != strings.ToLower(RescueFundsOnSourceChainEventSig) {
		return nil, fmt.Errorf("not a RescueFundsOnSourceChain event")
	}

	event := &RescueFundsOnSourceChainEvent{
		UniversalTxId: log.Topics[1], // bytes32 as 0x-prefixed hex
		PRC20:         common.HexToAddress(log.Topics[2]).Hex(),
		Sender:        common.HexToAddress(log.Topics[3]).Hex(),
	}

	stringType, _ := abi.NewType("string", "", nil)
	uint8Type, _ := abi.NewType("uint8", "", nil)
	uint256Type, _ := abi.NewType("uint256", "", nil)

	arguments := abi.Arguments{
		{Type: stringType},  // chainNamespace
		{Type: uint8Type},   // txType
		{Type: uint256Type}, // gasFee
		{Type: uint256Type}, // gasPrice
		{Type: uint256Type}, // gasLimit
	}

	values, err := arguments.Unpack(log.Data)
	if err != nil {
		return nil, fmt.Errorf("failed to unpack RescueFundsOnSourceChain data: %w", err)
	}
	if len(values) != 5 {
		return nil, fmt.Errorf("RescueFundsOnSourceChain: unexpected value count %d", len(values))
	}

	event.ChainNamespace = values[0].(string)
	event.TxType = SolidityTxTypeToProto(values[1].(uint8))
	event.GasFee = values[2].(*big.Int)
	event.GasPrice = values[3].(*big.Int)
	event.GasLimit = values[4].(*big.Int)

	return event, nil
}
