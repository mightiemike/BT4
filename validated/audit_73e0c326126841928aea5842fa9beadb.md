### Title
CREATE2 contract-address front-running allows an attacker to permanently block a pending, not-yet-included smart contract deployment - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The Optimism finding centers on a general bug class: an identifier that must be globally unique is computed from state that is not yet final/canonical (an "unsafe" L2 block), letting an attacker pre-empt the identifier before the legitimate, canonical value can claim it — permanently blocking the honest actor because the store enforces "one registration per identifier." The closest reachable analog in java-tron is TVM's `CREATE2` contract-address derivation, which is deterministic and computable from public, pre-confirmation data (deployer address, user-chosen salt, and init-code), combined with a store that rejects re-use of an already-occupied contract address.

### Finding Description
`WalletUtil.generateContractAddress2` computes the CREATE2 target address purely from `(deployer address, salt, sha3(code))`: [1](#0-0) 

This is exactly the standard CREATE2 formula, and — critically — none of its inputs depend on transaction ordering, block inclusion, or transaction hash. Anyone who observes a pending (unconfirmed / "not yet safe") transaction in the mempool that will eventually execute a CREATE2 with a given salt and init-code can compute the resulting contract address in advance, before that transaction is included in a block.

`Program.createContractImpl` enforces global uniqueness on that address: if an account/contract already exists there, the legitimate deployment is rejected/blocked: [2](#0-1) [3](#0-2) 

The equivalent check exists for top-level `CREATE` deployments in `VMActuator.create()`: [4](#0-3) 

Because the CREATE2 address is a pure function of publicly-visible pending data (deployer, salt, init-code hash) rather than something tied to the eventual, finalized transaction hash, an attacker can:
1. Observe a pending transaction/internal call that will deploy via CREATE2 with a known salt and bytecode (e.g., a factory contract pattern, common in DEX/AMM pair deployments, deterministic wallet factories, etc.).
2. Independently compute the same target address using `generateContractAddress2`.
3. Submit their own transaction that reaches that address first (via fee/bandwidth prioritization) and deploys arbitrary junk bytecode there.
4. Because `contractAlreadyExists` becomes true, all subsequent legitimate attempts to deploy the intended contract at that address permanently fail with `BytecodeExecutionException("Trying to create a contract with existing contract address...")`.

This is structurally identical to the Optimism bug class: a deterministic, publicly-derivable identifier that must be unique is claimed by an attacker before the legitimate/canonical use of that identifier is settled, permanently denying the honest party the ability to register/use it.

### Impact Explanation
The impact is a denial-of-service / griefing on smart-contract deployment infrastructure that relies on CREATE2 for deterministic addressing (counterfactual wallets, cross-chain deterministic deployments, factory patterns). Once squatted with junk bytecode, the intended contract can never be deployed at that address on this chain, permanently breaking any protocol logic, off-chain tooling, or cross-chain address assumptions that depend on that deterministic address. This matches the "invalid-state/divergence/halt" class of impact: a legitimate, expected on-chain state (the correct contract at the precomputed address) is instead permanently squatted by an attacker.

### Likelihood Explanation
This is not TRON-specific misbehavior but an inherent property of the standard CREATE2 formula (shared with Ethereum and other EVM-compatible chains), so exploitation requires only: (1) visibility into a pending transaction/internal transaction destined to CREATE2-deploy at a known salt/bytecode, and (2) the ability to get a competing transaction processed first (higher bandwidth/energy fee, same-block ordering). Both are realistic for any contract or protocol on java-tron that publicly announces or predictably reuses CREATE2 salts before deployment. However, exploitation only harms specific factory/deterministic-deployment patterns rather than the entire chain's ability to finalize state, so likelihood/impact scope is narrower than the original L2 anchor-state freeze scenario.

### Recommendation
This is inherent to CREATE2 semantics and is a known, generally-accepted risk in the broader EVM ecosystem (mitigated at the application layer, e.g., by including deployer-controlled unpredictable salts, or by using `CREATE` with sequential nonces for sensitive deployments, or by having factories commit-then-reveal salts). No java-tron-specific code defect beyond the standard CREATE2 spec was identified; recommend documenting this risk for contract authors using CREATE2 on TVM and considering guidance/tooling that discourages predictable, low-entropy salts for security-sensitive deterministic deployments.

### Proof of Concept
1. Victim contract `Factory` intends to deploy `Target` via CREATE2 with `salt = S` and `init-code = C`; the deployment transaction is broadcast and sits pending in the mempool.
2. Attacker computes `addr = sha3omit12(deployerAddress || S || sha3(C))` exactly as done in `WalletUtil.generateContractAddress2`.
3. Attacker submits a transaction with higher bandwidth/energy fee that triggers a CREATE2 (or CREATE, depending on how the address is reached) resulting in junk bytecode being placed at `addr`, and it is confirmed first.
4. When the victim's original transaction later executes `createContractImpl`, `getContractState().getAccount(newAddress)` returns non-null and `contractAlreadyExists` evaluates true (per `Program.java` lines 827-833), causing the legitimate deployment to permanently fail with the "existing contract address" exception, and the intended `Target` contract can never be deployed at that address.
