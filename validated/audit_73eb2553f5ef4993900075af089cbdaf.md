### Title
Webhook HMAC Signature Does Not Bind Shop Domain, Enabling Cross-Tenant Webhook Forgery/Replay - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
Shopify webhook authenticity is verified by `validateHmacFromRequestFactory` / `validateHmacString`, which computes an HMAC over `rawBody` alone using the app's shared `apiSecretKey`. [1](#0-0)  The shop domain that a webhook claims to originate from (`X-Shopify-Shop-Domain` / events domain header) is read and trusted independently of this signature, in `checkWebhooksHeaders`/`checkEventsHeaders`, and is never mixed into the signed data. [2](#0-1)  Because the same `apiSecretKey` is shared by every shop that installs a given app, an HMAC computed over a given body is valid for *any* shop, not just the one that actually triggered it — directly analogous to the reported bug where a signature covers "nonce, bundle, chain ID" but not the wallet identity, so it can be replayed against a different wallet once the identity binding is broken.

### Finding Description
1. `validateFactory` reads `rawBody`, computes/validates the HMAC via `validateHmacFromRequestFactory`, and only afterward independently pulls the `domain` header value with `checkWebhookHeaders`, attaching it to the returned `WebhookValidationValid` object without any cryptographic linkage to the HMAC. [3](#0-2) [2](#0-1) 
2. `validateHmacFromRequest` verifies `hmac == HMAC_SHA256(apiSecretKey, rawBody)`, with `rawBody` as the sole signed material — the shop domain is not part of the hashed content. [4](#0-3) 
3. Downstream, `authenticateWebhookFactory` (shopify-app-remix and shopify-app-react-router) trusts `check.domain` from this validation result outright and uses it to load/create the offline session that is exposed to the webhook handler: `const session = await ensureValidOfflineSession(params, check.domain);`. [5](#0-4) 
4. Because `apiSecretKey` is a single, app-wide secret shared across every merchant installation (not per-shop), the HMAC for a given body is identical regardless of which shop it is claimed to be from. An attacker who controls one shop that has installed the target app can capture a real, Shopify-signed `(rawBody, hmac)` pair delivered to their own store's webhook endpoint (any topic, e.g. `app/uninstalled`, `customers/data_request`, or a custom app event they can trigger), then replay that exact HTTP body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a **victim** shop's domain that also uses the same app. The HMAC check still passes (since it only checks the body/secret pair), and the webhook is processed with the victim shop's offline session loaded and handed to the app's business logic.

This mirrors the reported bug class precisely: the signature authenticates *that data came from the app's Shopify integration*, but never binds it to the specific tenant (shop) it is deployed against, so a legitimately-signed payload can be "replayed" against a different, unauthorized tenant.

### Impact Explanation
An attacker who can install the target app on their own shop (or interact with a public app-proxy/checkout distribution) can forge webhook deliveries for any other shop that has installed the same app. Depending on the topics the app subscribes to, this enables:
- Cross-tenant griefing/DoS — e.g. forging `app/uninstalled` to trigger cleanup/session-revocation logic against a victim shop, or `shop/redact`/data-erasure style topics to trigger destructive handlers on a victim's data.
- Injection of attacker-controlled webhook payload content into a victim shop's session context, since `session` (the victim's real offline session/token) is loaded and made available to the handler while `payload` is fully attacker controlled body content.
- Any app-specific business logic keyed off `shop`/`topic`/`payload` (e.g. billing changes, order processing, product syncs) can be triggered for a shop the attacker does not own.

### Likelihood Explanation
Likelihood is limited to an unprivileged actor who is able to install the target app on a shop they control (a typical, low-barrier requirement for any public/embedded Shopify app) and capture one authentic webhook delivery from Shopify to a domain/URL they control. From there, forging the HTTP request to the shared webhook endpoint with a modified `X-Shopify-Shop-Domain` header requires no cryptographic secret and is trivially scriptable. No MITM, leaked secret, or privileged access to Shopify internals is required — only ordinary merchant-level access to the target app.

### Recommendation
Bind the destination shop identity into the signed material used for webhook (and app-proxy) authenticity checks, or otherwise verify server-side that the shop asserted in the `X-Shopify-Shop-Domain` header matches an app installation that is expected to receive that specific webhook (e.g., cross-check the domain against Shopify's webhook subscription record / topic registration for that specific shop, or require a per-shop signing key/registration secret rather than relying solely on the shared app secret). At minimum, before trusting `check.domain` to load a session, verify that a webhook with that `(hmac, topic, webhookId)` combination was actually registered for that shop (e.g., via GraphQL Admin API webhook subscription lookup) rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures/receives a webhook (e.g., `app/uninstalled`) at an endpoint they control, capturing the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed using the app's shared `apiSecretKey`.
2. Attacker sends a POST request directly to the target app's public `/webhooks` endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (victim's domain, which also has the app installed)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version` set to any registered values.
3. `validateHmacFromRequest` validates `H` against `HMAC_SHA256(apiSecretKey, B)` — this passes because the secret and body match exactly what Shopify originally signed. [6](#0-5) 
4. `checkWebhooksHeaders` extracts `domain: 'victim-shop.myshopify.com'` from the (unauthenticated) header and returns it as part of the `valid: true` result. [2](#0-1) 
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's real offline session and admin client, then invokes the app's webhook handler with attacker-controlled `payload` under the victim's identity. [5](#0-4)

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);

    missingHeaders,
  );

    headers,
    headerNames.webhookId,
    missingHeaders,
  );

      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };

    hmac: hmac!,
