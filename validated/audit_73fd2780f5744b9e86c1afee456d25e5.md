### Title
L1 handler transactions bypass fee-sufficiency checks, allowing dust-fee resource exhaustion attacks - (File: crates/blockifier/src/transaction/l1_handler_transaction.rs)

### Summary
`L1HandlerTransaction::execute_raw` only verifies that `paid_fee_on_l1` is nonzero (`paid_fee != Fee(0)`), not that it is sufficient to cover the actual execution cost. An L1 message sender can therefore trigger L2 execution consuming resources up to `l1_handler_max_amount_bounds` while paying only a dust fee (e.g. 1 wei on L1), analogous to the "dust loan" pattern where the cost of servicing a position/transaction is decoupled from the value backing it.

### Finding Description
In `crates/blockifier/src/transaction/l1_handler_transaction.rs`, after execution succeeds and the post-execution resource-bound check (`FeeCheckReport::check_all_gas_amounts_within_bounds`) passes, the only fee validation applied is: [1](#0-0) 

This code explicitly documents the weak guarantee: "For now, assert only that any amount of fee was paid." There is no comparison between `paid_fee_on_l1` and the `receipt.fee`/`receipt.gas` that was actually computed from the transaction's real resource consumption — the check that would enforce proportionality is commented as a TODO ("Consider removing this check. It is covered by the starknet core contract"), i.e., the sequencer relies on an L1 contract-level guarantee it does not itself enforce or verify at execution time.

The only real ceiling on resource usage per L1 handler transaction is the static `l1_handler_max_amount_bounds` (a fixed max L1/L2/L1-data gas amount), not a fee-proportional bound: [2](#0-1) 

Since `l1_handler_tx_execution_info` sets `receipt.fee = Fee(0)` regardless of the resources consumed, the sequencer/fee-accounting layer has no record that ties consumed compute/storage/calldata resources to compensation: [3](#0-2) 

An attacker (an ordinary L1 sender, which is an unprivileged, permissionless actor able to call `sendMessageToL2` on the core contract) can pay the L1 core contract's minimal nonzero fee, and cause the L2 entry point to consume up to the maximum allowed L1/L2/L1-data gas bounds. Existing tests confirm the sequencer accepts `Fee(1)` as sufficient regardless of computed cost: [4](#0-3) 

This mirrors the reported bug class: there is no lower bound tying the "collateral"/fee paid to the resource cost incurred by the network, so an attacker can force the sequencer/network to repeatedly pay processing costs (block space, storage writes, state diff computation, L2 execution) that dwarf the dust fee actually collected, while the resulting cost is nominally "covered" by the core-contract-side check that the sequencer does not itself enforce.

### Impact Explanation
Repeated submission of L1-to-L2 messages that each pay a minimal (dust) fee but consume resources near `l1_handler_max_amount_bounds` lets the attacker consistently extract sequencer/network compute, storage, and block-space capacity for negligible payment. Because `receipt.fee` is forced to `Fee(0)` for L1 handler transactions, there is no fee-based disincentive or proportional cost recovery mechanism at the blockifier layer; the bouncer/block-building capacity is consumed by many cheap L1 handler transactions crowding out fee-paying transactions, degrading the network's capacity to process legitimate transactions economically (a resource-imbalance/DoS-adjacent impact reachable purely from a single L1 message sender, not requiring any privileged or malicious-operator role).

### Likelihood Explanation
Likelihood is high: sending L1-to-L2 messages via the Starknet core contract with the minimal allowed fee is a standard, permissionless, low-cost operation available to any L1 account. The only gating factor is L1 gas cost of the `sendMessageToL2` call itself, which is far lower than the L2-side resources unlocked by `l1_handler_max_amount_bounds`, making the attack economically favorable at scale.

### Recommendation
Enforce that `paid_fee_on_l1` is proportional to (at least a documented minimum fraction of) the actual computed `receipt.fee`/`receipt.gas`, rather than merely checking `paid_fee != Fee(0)`. Remove reliance on the L1 core contract as the sole enforcement point for fee sufficiency, and reinstate/complete the fee-sufficiency check that was left as a TODO in `l1_handler_transaction.rs`, so that dust-fee L1 handler transactions with high resource consumption are rejected or capped proportionally to the fee paid.

### Proof of Concept
1. An L1 account calls the Starknet core contract's `sendMessageToL2` with `value = 1 wei` (minimal fee) and calldata/entry point selecting a contract function on L2 designed (or naturally) to consume gas up to `l1_handler_max_amount_bounds` (e.g., heavy storage writes/computation within the L1 handler bound).
2. The L1 events scraper picks up the message and it becomes an `ExecutableL1HandlerTransaction` with `paid_fee_on_l1 = Fee(1)`, as modeled in [5](#0-4) .
3. During execution, `execute_raw` computes `receipt.gas`/`receipt.fee` reflecting real (large) resource consumption, passes the `l1_handler_max_amount_bounds` check, and then only validates `paid_fee != Fee(0)` — the dust fee of 1 wei is accepted [6](#0-5) .
4. Repeating this from many L1 accounts (or the same account with incrementing nonces) lets an attacker force the sequencer to repeatedly execute near-maximum-cost L1 handler transactions while paying near-zero fees, exactly as demonstrated by the existing unit test that only fails when `paid_fee == Fee(0)`, not when it is insufficient relative to actual cost [7](#0-6) .
