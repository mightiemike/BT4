## Finding

### Title
`ensure_match_transaction_info` skips state-checkpoint hash verification, letting replay-verify accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that a freshly re-executed transaction matches the `TransactionInfo` that was actually committed to the chain (and thus covered by the transaction accumulator/ledger-info signatures). The function checks status, gas used, write-set hash and event-root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually authenticate the global state Merkle root. This is explicitly acknowledged in a TODO comment in the same function.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  compares a locally produced `TransactionOutput` against an authenticated `TransactionInfo` (pulled from backup/archive storage) by checking:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed event-accumulator root vs `txn_info.event_root_hash()`

It never compares against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, even though these fields exist precisely to authenticate the resulting global Sparse-Merkle-Tree / Jellyfish-Merkle-Tree root produced after applying this transaction (defined on `TransactionInfoV0`/`TransactionInfoV1` at [2](#0-1)  and [3](#0-2) ). The function itself documents the gap: [4](#0-3) 

`write_set_hash` (checked) only authenticates *this transaction's own* write set — it says nothing about whether the previously accumulated global state tree the write set is applied on top of is itself correct. A state root can diverge for reasons that don't change the current transaction's local write set at all (e.g., a bug in JMT/hot-state merge logic, node-key sharding, or the trading-native `position_state_checkpoint_hash` mentioned in the TODO), and this comparator would not detect it.

This function is consumed directly by the two tools whose entire purpose is to catch exactly this class of divergence:
- `storage/db-tool/src/replay_on_archive.rs`, which calls it after every re-executed chunk to decide pass/fail of replay-verify: [5](#0-4) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`'s `print_mismatches`, used for auditing historical execution: [6](#0-5) 

### Impact Explanation
Replay-verify (`replay_on_archive`) is the tool operators/CI use to certify that a full re-execution of archived history reproduces the exact ledger state that was actually committed and signed by validators. Because the comparator omits the state-checkpoint (state root) hashes, a corruption or divergence in accumulated global state — one that doesn't happen to alter the specific write set of the transaction under test — will not be flagged as a mismatch. This directly undermines the "authenticated API/proof verification must stay bound to the right root" guarantee: the tool can report "replay succeeded" while the actual state root diverges from the one signed into the `LedgerInfo`/committed `TransactionInfo`. Such silent divergence is exactly the class of hard-fork-relevant integrity break the scan targets, since it would hide a discrepancy between two nodes' (or one node vs. history's) state roots that should otherwise be caught before it becomes consensus-visible.

### Likelihood Explanation
This is not a hypothetical: it's a documented, always-present gap in the one code path responsible for detecting exactly this failure mode, and it triggers unconditionally on every replay-verify or debugger comparison call — no attacker input needed, just any bug elsewhere (in state-merge/trading-native code, sharded JMT construction, hot-state handling, etc.) that corrupts the accumulated state root without altering that step's own write set. The TODO in the code explicitly flags the trading-native `position_state_checkpoint_hash` case as one such live scenario ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution").

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionOutput`/executor state-checkpoint output) against the corresponding fields on `txn_info`, failing loudly on mismatch just as is done today for `state_change_hash` and `event_root_hash`. If a `TransactionOutput` doesn't carry the checkpoint hash for that transaction (checkpoints happen periodically, not every transaction), the checkpointed root should be reconstructed by the caller and compared at checkpoint boundaries before enabling any feature (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that relies on this check for correctness.

### Proof of Concept
1. Run `replay_on_archive` against an archive whose transactions have identical write sets to a locally re-executed chunk but whose downstream Merkle root (`state_checkpoint_hash`) has been corrupted (e.g., due to a JMT sharding bug or a bad `position_state_checkpoint_hash` from the trading-native pipeline, as called out in the TODO).
2. `execute_and_verify` in `replay_on_archive.rs` calls `ensure_match_transaction_info` ( [7](#0-6) ), which only checks `status`, `gas_used`, `write_set_hash`, and `event_root_hash`.
3. Because these four checks pass (the write set itself is unchanged), `ensure_match_transaction_info` returns `Ok(())` at [8](#0-7)  despite the state-checkpoint hash mismatch, and the tool reports a clean replay-verify pass even though the actual global state root has diverged from the committed/archived `TransactionInfo`.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
```
