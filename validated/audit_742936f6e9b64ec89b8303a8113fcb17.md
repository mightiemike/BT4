### Title
Signature malleability bypasses double-signing guard in `TransactionCapsule.checkWeight` pre-`VERSION_4_7_1` fork - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
`TransactionCapsule.checkWeight` deduplicates signer weights using a map keyed by the raw base64-encoded signature bytes instead of the recovered signer address, unless `ForkController.instance().pass(VERSION_4_7_1)` is true. Because ECDSA is malleable (`(r, s, v)` and `(r, n-s, v')` both recover to the same address for the same key), an attacker can submit two differently-encoded signatures from a single private key and have that key's weight counted twice toward a multisig threshold.

### Finding Description
`checkWeight` builds `addMap` keyed by `base64 = TransactionCapsule.getBase64FromByteString(sig)`, derived directly from the raw `(r, s, v)` bytes of the submitted signature via `Rsv.fromSignature` and `ECDSASignature.fromComponents(...).toBase64()` — no canonicalization (`toCanonicalised()`) is applied at this stage: [1](#0-0) 

`getBase64FromByteString` and `Rsv.fromSignature` simply copy the raw r/s/v bytes without normalizing `s` to the canonical low-S form: [2](#0-1) [3](#0-2) 

`SignUtils.signatureToAddress` correctly recovers the address using the recovery id `v` supplied in each signature, so both the original `(r, s, v)` and the malleable counterpart `(r, n-s, v')` recover to the identical address for the given key/hash — the address-recovery correctness is not the flaw; the flaw is the dedup key used before the fork check. Only once `ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)` is true does the code overwrite `base64` with `encode58Check(address)` before the `containsKey`/`put`, changing the dedup key to the actual signer address: [4](#0-3) 

`checkWeight` is reachable from multiple unprivileged, attacker-controlled entrypoints that accept arbitrary signature lists on a transaction: `TransactionCapsule.validateSignature`/`validatePubSignature` (used during broadcast/block validation), `Wallet.getTransactionSignWeight`/`TransactionUtil.getTransactionSignWeight`, `Wallet.getTransactionApprovedList`, and `TransactionCapsule.addSign`: [5](#0-4) [6](#0-5) 

Before the `VERSION_4_7_1` fork activates, an attacker holding one private key belonging to a multisig `Permission` can submit a transaction with two signatures generated from that single key — the canonical signature and its malleable counterpart `(r, n-s, flipped-v)` — and both will pass distinct `addMap` entries because their base64 encodings differ (different `s`/`v` bytes), even though both recover to the same address. `currentWeight` is incremented twice for one signer's weight, potentially satisfying a threshold that should require multiple distinct signers.

### Impact Explanation
An unprivileged attacker controlling only one key of a multisig `Permission` can craft a transaction that appears to meet the signing `threshold` using a duplicated (malleable) signature from that single key, allowing unauthorized execution of the permissioned contract (e.g., moving funds, changing account permissions) without collecting the required number of distinct co-signers — a direct authorization/threshold-bypass impact scoped to multisig accounts operating on a pre-`VERSION_4_7_1` chain state.

### Likelihood Explanation
Exploitability is fully gated by chain fork status: `ForkController.instance().pass(VERSION_4_7_1)` must be `false` for the vulnerable code path (raw-signature key) to be taken; once the fork has passed (default expectation on a fully hard-forked mainnet), the dedup key becomes the recovered address and the bypass is closed. On any network/private chain/testnet where this specific hard fork has not yet activated (e.g., freshly bootstrapped chains, forks of this codebase, or a chain paused before `VERSION_4_7_1` maintenance-interval activation), the exploit requires no privilege beyond owning one key in a multisig permission and standard `broadcastTransaction`/signing API access, and is fully reproducible.

### Recommendation
Always key `addMap` by the recovered signer address (`encode58Check(address)` or raw `address` bytes) rather than the raw signature encoding, regardless of fork status, removing the fork-gated behavior so the fix applies unconditionally: [4](#0-3) 

### Proof of Concept
```java
// chainbase/src/test/java/org/tron/core/capsule/TransactionCapsuleMalleabilityTest.java
@Test
public void testMalleableSignatureDoubleCountsPreFork() throws Exception {
  ECKey key = new ECKey(Utils.getRandom());
  byte[] address = key.getAddress();

  Permission permission = Permission.newBuilder()
      .setThreshold(2)
      .addKeys(Key.newBuilder().setAddress(ByteString.copyFrom(address)).setWeight(1))
      .addKeys(Key.newBuilder().setAddress(ByteString.copyFrom(otherAddress)).setWeight(1))
      .build();

  byte[] hash = Sha256Hash.hash(true, "test".getBytes());

  ECDSASignature sig = key.sign(hash); // raw, NOT canonicalised
  byte v = sig.v;
  // Malleable counterpart: (r, n-s, flipped recId)
  BigInteger nMinusS = ECKey.CURVE.getN().subtract(sig.s);
  byte flippedV = (byte) (v == 27 ? 28 : 27);
  ECDSASignature malleable = new ECDSASignature(sig.r, nMinusS);
  malleable.v = flippedV;

  ByteString sig1 = ByteString.copyFrom(toBytes(sig));
  ByteString sig2 = ByteString.copyFrom(toBytes(malleable));

  // Precondition: fork VERSION_4_7_1 not yet passed (simulate mock/stub returning false)

  long weight = TransactionCapsule.checkWeight(
      permission, Arrays.asList(sig1, sig2), hash, new ArrayList<>());

  // Vulnerable behavior: same key's weight (1) is counted twice => weight == 2 == threshold,
  // even though only ONE distinct signer participated.
  Assert.assertEquals(2, weight); // demonstrates bypass pre-fork

  // Expected/fixed behavior (post-fork or after fix): should throw PermissionException
  // "<address> has signed twice!" because dedup key is the recovered address.
}
```
Expected assertion for the fix: with the recommended change (dedup by address unconditionally), the second `checkWeight` call must throw `PermissionException` with message containing "has signed twice", and `currentWeight` must never exceed the sum of distinct signer weights.
