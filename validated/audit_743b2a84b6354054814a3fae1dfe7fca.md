## Title
Unbounded `PendingInbounds.Walk` in `AfterBallotTerminal` enables inbound-pipeline denial of service via spammed dust deposits - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
The Uniswap V3 report describes an unbounded loop (`swap`'s tick-crossing loop) whose cost scales with attacker-created state (many cheap positions), letting an unprivileged actor make the operation un-executable within the block gas limit. Push Chain's `x/uexecutor` module has a structurally identical pattern: `BallotHooks.afterInboundBallotTerminal` performs a full linear scan (`PendingInbounds.Walk`) over **every currently in-flight inbound in the whole chain** each time a single inbound ballot reaches a terminal state, and the size of that set is driven entirely by unprivileged, permissionless external-chain deposit activity.

### Finding Description
`RecordInboundVote` creates one `PendingInboundEntry` per unique `utx_key` (`sha256(source_chain:tx_hash:log_index)`), and `PendingInbounds` is never bounded — any external-chain deposit event that Universal Validators observe produces a new entry in this map: [1](#0-0) 

When any single ballot for an inbound reaches PASSED/REJECTED/EXPIRED, `x/uvalidator`'s `MarkBallotFinalized`/`MarkBallotExpired` invoke the registered `BallotHooks.AfterBallotTerminal`: [2](#0-1) 

For `INBOUND_TX` ballots this dispatches to `afterInboundBallotTerminal`, which — because ballot IDs are one-way digests — locates the owning `PendingInboundEntry` by **iterating the entire `PendingInbounds` collection** until a matching `BallotId` is found: [3](#0-2) 

The code's own comment claims "the pending set is small and transient," but there is no enforcement of that assumption anywhere in the reachable code: nothing limits how many distinct inbound events can be simultaneously pending, and nothing throttles how fast new inbound gateway events can be created on an external chain. This walk executes **inside the same `CacheContext`** used by `VoteInbound` before `commit()` is called: [4](#0-3) 

so a gas-metered `MsgVoteInbound` transaction pays for the full-collection scan as part of normal vote processing.

### Impact Explanation
An unprivileged user needs no elevated permissions to grow `PendingInbounds` — they only need to trigger many distinct gateway events on any connected external chain (e.g. thousands of dust-value deposits), which honest Universal Validators are obligated to observe and vote on via the ordinary `MsgVoteInbound` gasless flow. As the number of concurrently in-flight inbounds `N` grows, every subsequent ballot finalization/expiry pays an `O(N)` scan, and since every one of the `N` inbounds eventually finalizes or expires, the aggregate cost across the whole pipeline is `O(N²)`. Once `N` is large enough that a single scan approaches the tx/block gas limit, `MsgVoteInbound` transactions attempting to finalize (or expire) ballots begin failing with out-of-gas, which (per `CacheContext` semantics) rolls back `RecordInboundVote`/ballot state for that attempt — meaning the `PendingInbounds` set never shrinks and the same expensive scan recurs on every future vote. This can degrade or effectively stall the universal inbound execution pipeline (mints, PRC20 accounting, payload execution) for all users, matching the in-scope "denial of service ... reachable without privileged control" impact and "consensus or state-machine divergence/DoS reachable from ordinary user deposits ... alone."

### Likelihood Explanation
Likelihood is moderate-to-high in cost but requires sustained volume: the attacker must generate a large number of distinct external-chain gateway events (paying that chain's gas), similar to the Uniswap report's requirement to create "thousands of positions with 1 wei." No validator, admin, or TSS collusion is required — only ordinary deposit transactions on a connected external chain, which are permissionless by design (this is exactly the trust model `x/uexecutor` is built to support).

### Recommendation
- Replace the linear `PendingInbounds.Walk` lookup in `afterInboundBallotTerminal` with a direct index: store a `ballotID -> utxKey` (or `ballotID -> (utxKey, variantIdx)`) secondary map maintained alongside `RecordInboundVote`, so hook dispatch is O(1)/O(log n) instead of O(n).
- Alternatively/additionally, bound the number of concurrently outstanding `PendingInbounds` entries (e.g. per-source-chain rate limiting, minimum bridged-amount thresholds, or a hard cap with backpressure) so the audit-trail set cannot be inflated arbitrarily by low-value spam deposits, analogous to Uniswap's "minimum liquidity per position" mitigation.
- Ensure the gas cost of any such maintenance walk is either bounded or paid outside the per-tx gas budget so failed finalizations do not leave `PendingInbounds` permanently bloated.

### Proof of Concept
1. Attacker submits `N` (e.g. 50,000+) low-value/dust transfer transactions through a connected external chain's gateway contract, each producing a distinct `(source_chain, tx_hash, log_index)` triple.
2. Universal Validators observe and vote each one via `MsgVoteInbound` as normal, causing `RecordInboundVote` to create `N` separate `PendingInboundEntry` records (`x/uexecutor/keeper/inbound.go`).
3. As votes accumulate and ballots begin finalizing/expiring, each terminal transition invokes `afterInboundBallotTerminal`, which calls `k.PendingInbounds.Walk` over the full `N`-sized collection (`x/uexecutor/keeper/ballot_hooks.go:86-94`) inside the vote's gas-metered `CacheContext`.
4. As `N` grows, the per-vote scan cost grows linearly, and the cumulative cost across all `N` finalizations grows quadratically, until `MsgVoteInbound` transactions start failing on out-of-gas during hook execution — stalling processing of the inbound backlog and any votes needed to clear it, since failed attempts do not shrink `PendingInbounds`.

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
