### Title
Missing slippage/minimum-amount protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` enables sandwich attacks on TRC10 Bancor-style liquidity operations - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
Java-tron's built-in Bancor-style token exchange supports `ExchangeTransactionContract` (swap), `ExchangeInjectContract` (add liquidity), and `ExchangeWithdrawContract` (remove liquidity). While the swap operation includes an `expected` field that lets the caller specify an off-chain-computed minimum acceptable output [1](#0-0) , the inject and withdraw operations compute the counter-token amount purely from the live on-chain pool ratio at execution time, with no caller-supplied bound to protect against pool manipulation [2](#0-1) [3](#0-2) . This is the same bug class described in the report: liquidity add/remove operations that rely on same-transaction on-chain ratio calculations without an off-chain-computed slippage bound are vulnerable to sandwich attacks.

### Finding Description
`ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — no minimum/maximum bound field, unlike `ExchangeTransactionContract` which explicitly has an `expected` field for this purpose: [4](#0-3) 

In `ExchangeInjectActuator.doValidate` and `execute`, the counter-token amount (`anotherTokenQuant`) required to be contributed is computed strictly from the exchange's current `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction executes: [5](#0-4) 

Similarly, `ExchangeWithdrawActuator` computes the amount of the counter-token returned to the caller from the live pool ratio, with only a "not precise enough" rounding-error check, not a slippage-bound check against a caller-supplied minimum: [6](#0-5) 

Any account holding the exchanged tokens can freely submit `ExchangeTransactionContract` swaps (anonymous, unprivileged broadcast transactions) against the same `exchange_id` to shift `firstTokenBalance`/`secondTokenBalance` immediately before and after the exchange creator's inject/withdraw transaction lands in the same block, exactly as described in the external report (front-run to skew the ratio, then back-run to restore it). Because inject/withdraw derive their required/returned amounts solely from the manipulated ratio with no off-chain-verified bound, the attacker profits at the expense of whoever calls inject or withdraw.

### Impact Explanation
An attacker can force the exchange's liquidity provider to (a) contribute a disproportionately large amount of the counter-token during `ExchangeInjectContract`, or (b) receive a disproportionately small amount of the counter-token during `ExchangeWithdrawContract`, extracting value from the victim's assets. This directly causes on-chain asset/accounting loss consistent with the report's "Protocol assets can be stolen through sandwich attacks" impact.

### Likelihood Explanation
The attack requires only ordinary, unprivileged transactions (`ExchangeTransactionContract` swaps) that any account can broadcast; no special node/witness privilege or leaked keys are needed. Sandwiching is a well-known and easily automated technique against any DEX/AMM-like mechanism lacking slippage bounds, making this highly likely to be exploited whenever an inject/withdraw transaction becomes visible in the mempool.

### Recommendation
Add an explicit caller-supplied bound field to `ExchangeInjectContract` (e.g., `expected_another_token_quant` max) and `ExchangeWithdrawContract` (e.g., `expected_another_token_quant` min), computed off-chain by the caller, and enforce it in `ExchangeInjectActuator.doValidate`/`execute` and `ExchangeWithdrawActuator.doValidate`/`execute` the same way `ExchangeTransactionActuator` already enforces `expected` for swaps [1](#0-0) .

### Proof of Concept
1. Exchange creator C prepares to inject `tokenQuant` of token A into pool `exchangeId`, expecting to also contribute `X` of token B based on the current ratio.
2. Attacker observes C's pending `ExchangeInjectContract` transaction in the mempool and submits an `ExchangeTransactionContract` swap that heavily skews `firstTokenBalance`/`secondTokenBalance` in the same block, ordered before C's transaction.
3. C's inject transaction executes using the skewed ratio computed on-chain in `ExchangeInjectActuator` (lines 71-83/215-227), forcing C to contribute far more of token B than intended, since there is no caller-enforced upper bound on `anotherTokenQuant`.
4. Attacker submits a second swap restoring the original ratio, capturing the value taken from C.
5. The identical sequence applies to `ExchangeWithdrawContract`, where the attacker instead forces the withdrawer to receive less counter-token than expected.
