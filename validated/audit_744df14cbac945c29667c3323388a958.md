### Title
Sandwich attack on `ExchangeInjectActuator`/`ExchangeWithdrawActuator` allows draining an on-chain Exchange (Bancor-style AMM) pool by manipulating spot ratio before a privileged inject/withdraw call - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's built-in `Exchange` feature is a Bancor-style constant-formula AMM pool (`ExchangeCapsule`) that anyone can trade against via `ExchangeTransactionActuator`, but only the pool's `creatorAddress` may add/remove liquidity via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`. Both privileged actuators compute the counterpart token amount purely from the pool's *current* on-chain balances at execution time, with no expected/minimum-output parameter and no check that the ratio hasn't just been manipulated. This mirrors the Beefy bug class: a privileged action (`setPositionWidth`/`unpause`) that redeploys funds based on unprotected current price, sandwichable by an unprivileged trader.

### Finding Description
`ExchangeTransactionActuator.execute()` lets any unprivileged account trade against the pool, moving `firstTokenBalance`/`secondTokenBalance` arbitrarily within a single block via the Bancor relay math in `ExchangeCapsule.transaction()` / `ExchangeProcessor.exchange()`: [1](#0-0) 

`ExchangeInjectActuator.execute()` computes the counterpart amount to be pulled from the creator strictly from the pool's balances at execution time, with no slippage/expected-output guard: [2](#0-1) 

`ExchangeWithdrawActuator.execute()` has the identical pattern for withdrawals, computing `anotherTokenQuant` from live pool ratio: [3](#0-2) 

Neither actuator's `doValidate()` includes any check against expected minimum/maximum counterpart amount or against the pool ratio having been recently/artificially skewed - the only checks are address validity, fee balance, creator identity, and basic bounds: [4](#0-3) 

This is structurally the same root cause as the Beefy report: a value-moving state transition (inject/withdraw liquidity, analogous to Beefy's tick/range redeployment) that trusts the *current* spot state of a manipulable AMM pool, with no protection (there is no `onlyCalmPeriods`-equivalent check, no TWAP, no min/max expected output) against an attacker skewing that state immediately beforehand via a public, unprivileged action (`ExchangeTransactionActuator`).

### Impact Explanation
An attacker can:
1. Front-run the creator's pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction with a large `ExchangeTransactionContract` trade that heavily skews the pool's `firstTokenBalance`/`secondTokenBalance` ratio.
2. Let the creator's inject/withdraw execute at the now-distorted ratio, causing the creator to inject a disproportionately large amount of the more valuable token (or withdraw a disproportionately small amount of the valuable token) relative to fair market value.
3. Back-run by reversing the initial trade, extracting the value transferred into/out of the pool and pocketing the difference, while leaving the pool (and thus all other traders using this Exchange pair) with a distorted, drained balance sheet.

This directly causes an accounting/settlement loss: TRX/TRC10 tokens are moved out of the creator's account (and the shared public pool used by all traders of that pair) into the attacker's account at a manipulated price, with no minimum-output protection to abort the transaction if the price moved unfavorably.

### Likelihood Explanation
`ExchangeTransactionActuator` is callable by any account with sufficient balance/tokens with no calm-period, oracle, or TWAP protection, making the price-skewing precondition trivially and cheaply reachable by an unprivileged attacker in the same block as the targeted inject/withdraw transaction (classic sandwich via transaction ordering). The only barrier is visibility of the pending inject/withdraw transaction in the mempool/block, which is standard for MEV/sandwich attacks on public chains.

### Recommendation
Add an expected-minimum/maximum counterpart-amount parameter (slippage protection) to `ExchangeInjectContract`/`ExchangeWithdrawContract`, validated in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()` against the actually computed `anotherTokenQuant`, rejecting the transaction if it falls outside the caller-specified bounds. Alternatively, base the injected/withdrawn ratio on a time-weighted average of the pool balances rather than the instantaneous balances at execution time.

### Proof of Concept
1. Attacker observes exchange creator's pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction in the mempool targeting exchange pool `X` (firstToken/secondToken).
2. Attacker submits an `ExchangeTransactionContract` trade (via `ExchangeTransactionActuator`) that sells a large amount of `firstToken` into pool `X`, sharply depressing `secondTokenBalance` relative to `firstTokenBalance` (per `ExchangeCapsule.transaction()`/`ExchangeProcessor.exchange()`).
3. Creator's `ExchangeInjectContract` executes: `ExchangeInjectActuator.execute()` computes `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` using the now-skewed balances, forcing the creator to contribute an unfavorable amount of `secondToken` relative to fair value.
4. Attacker submits a reverse `ExchangeTransactionContract` trade selling `secondToken` back for `firstToken`, restoring the ratio and realizing profit equal to the value transferred from the creator's injection at the distorted price, minus trading fees (`calcFee()`).
5. Net result: the creator's injected liquidity is diluted at an unfavorable rate, and the attacker exits with a net profit extracted from the exchange pool - the same sandwich pattern as the Beefy `setPositionWidth`/`unpause` exploit, applied to `ExchangeInjectActuator`/`ExchangeWithdrawActuator`.
