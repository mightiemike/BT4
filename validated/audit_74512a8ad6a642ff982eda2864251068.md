## Title
Refund of prepaid execution/send gas is recomputed with the *current* `RuntimeConfig` fee schedule instead of the schedule that was active when the fee was actually purchased, causing charged vs. refunded gas amounts to diverge across a protocol upgrade — (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/config.rs`)

### Summary
The Sherlock finding is a generic "charge now at parameter P, refund later at parameter P′ ≠ P" bug class. In nearcore, a mutable-parameter analog exists in how prepaid execution/send gas is priced. It is computed once at transaction→receipt conversion time using the *signer shard's current* `RuntimeConfig`, but recomputed again — using whatever `RuntimeConfig` happens to be active for the chunk that finally executes the receipt — when the unspent-gas refund is generated. Because `RuntimeConfig` (the fee schedule) is versioned per protocol version and genuinely changes across upgrades, a receipt that is created under one protocol version and executed under a later one (e.g. because it was buffered/delayed by congestion control, cross-shard forwarding, or the delayed-receipt queue) will have its refund computed off a different fee table than the one used to charge the sender.

### Finding Description
- At transaction conversion time, `calculate_tx_cost` computes `prepaid_send_fee`/`prepaid_exec_fee` via `total_prepaid_send_fees`/`total_prepaid_exec_fees`, both taking a `config: &RuntimeConfig` argument, and uses the resulting `gas_remaining` to determine the token amount deducted from the signer's balance: [1](#0-0) 

- The `config` passed in here is whatever `RuntimeConfig` is active on the signer's shard/block at the moment the transaction is processed (versioned by protocol version via `RuntimeConfigStore`): [2](#0-1) 

- Later, when the resulting `ActionReceipt` is actually executed (possibly on a different shard/chunk, possibly after the receipt sat in the delayed-receipt queue or was buffered by congestion control across chunks/epochs), `refund_unspent_gas_and_deposits` **recomputes** `prepaid_gas`/`prepaid_exec_gas` from the raw actions using `config: &RuntimeConfig`, i.e. `apply_state.config` for the chunk that is executing *now*, not the config that was active when the tokens were originally charged: [3](#0-2) 

- `apply_state.config` is explicitly documented as "the Runtime config to use for the current transition" — i.e. it tracks the *current* chunk's protocol version, not the protocol version that was active when the receipt/transaction was created: [4](#0-3) 

- `RuntimeConfig`/fee values are versioned and do change between protocol versions (confirmed by the diff-chain mechanism and per-version yaml overrides, e.g. raising `create_account` fees at v85): [5](#0-4) 

The design comment for the refund function explicitly assumes gas is "purchased at one price" for "the entire execution," addressing *gas price* drift (NEP-536), but it does not address *fee-schedule* drift — `prepaid_gas`/`prepaid_exec_gas` are literally recomputed from the config in scope at refund time rather than being carried forward from the values computed (and paid for) at send time: [6](#0-5) 

### Impact Explanation
If exec/send fee parameters for any action type increase between the protocol version active when a receipt was created and the protocol version active when it is executed, `gross_gas_refund = prepaid_gas + prepaid_exec_gas − gas_used/burnt` is computed with an inflated `prepaid_exec_gas`, larger than what the signer actually paid for at conversion time. `unused_gas_balance_refund` is then paid out of that inflated figure, producing a refund transfer receipt whose deposit exceeds the amount of tokens that were actually deducted from the signer for that portion of the receipt — an unauthorized value movement (net token creation relative to what was ever collected). Conversely, if fees decrease, the signer is under-refunded relative to what they paid, and the difference is effectively lost (retained/burnt) rather than returned, harming the honest signer.

### Likelihood Explanation
This requires no privileged action from the attacker — any ordinary user transaction that produces a cross-shard `ActionReceipt` (or one that ends up in the delayed-receipt queue due to congestion control or gas-limit exhaustion) is subject to whatever `RuntimeConfig` is active for the chunk that eventually executes it. The trigger event (a protocol version upgrade activating a new `RuntimeConfig` with changed fee values) is a normal, expected network event (validators vote in a new protocol version every so often per `protocol-versioning`), not an attacker-controlled action, so likelihood is bounded by how close a receipt's in-flight window is to an upgrade boundary; it is not attacker-forced but is a structurally reachable window that widens under network congestion (larger delayed-receipt backlogs, longer buffering).

### Recommendation
Persist the `prepaid_gas`/`prepaid_send_fee`/`prepaid_exec_fee` amounts (or the specific `RuntimeConfig`/fee values) that were actually used and charged at transaction-conversion time as part of the `ActionReceipt`, and use those stored values — not a fresh recomputation against the currently active `RuntimeConfig` — inside `refund_unspent_gas_and_deposits` when computing `gross_gas_refund`. This mirrors the fix recommended in the original report: store the charged fee on the object rather than recomputing it from a mutable parameter at refund time.

### Proof of Concept
1. Protocol votes in a new protocol version at an epoch boundary that raises an action's exec fee (as has happened historically, e.g. `create_account` cost increase at v85; see `core/parameters/src/config_store.rs:26-63`).
2. A user submits a normal transaction under the old protocol version whose resulting `ActionReceipt` is a remote (cross-shard) receipt; `calculate_tx_cost` deducts tokens from the signer based on `prepaid_exec_fee` computed with the *old* `RuntimeConfig` (`runtime/runtime/src/config.rs:511-536`).
3. Due to congestion control/bandwidth scheduling or the delayed-receipt queue, the receipt is not executed until after the epoch boundary where the new `RuntimeConfig` (with the higher exec fee) is active.
4. `apply_action_receipt`/`refund_unspent_gas_and_deposits` recomputes `prepaid_exec_gas` using `apply_state.config` (the new, higher-fee config) at `runtime/runtime/src/lib.rs:1299-1316`, producing a `gross_gas_refund`/`unused_gas_balance_refund` larger than what the signer was actually charged in step 2, and a `Receipt::new_gas_refund` is emitted for that inflated amount (`runtime/runtime/src/lib.rs:1400-1416`).

    /// How we handle refunds since NEP-536.
    ///
    /// In this model, the user purchases gas at one price. This price stays the
    /// same for the entire execution of the transaction, even if the blockchain
    /// price changes.
    ///
    /// In this configuration, gas price changes do not affect refunds, either.
    /// Thus, we only create refunds for unspent gas and for deposits.
    fn refund_unspent_gas_and_deposits(
        &self,
        gas_burn_price: Balance,
        gas_purchase_price: Balance,
        receipt: &Receipt,
        action_receipt: &VersionedActionReceipt,
        result: &mut ActionReceiptResult,
        config: &RuntimeConfig,
        created_account: bool,
        protocol_version: ProtocolVersion,
    ) -> Result<GasRefundResult, RuntimeError> {
        let total_deposit = total_deposit(&action_receipt.actions())?;
        let prepaid_gas = total_prepaid_gas(&action_receipt.actions())?
            .checked_add(total_prepaid_send_fees(config, &action_receipt.actions())?.gas)
            .ok_or(IntegerOverflowError)?;
        let prepaid_exec_gas =
            total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
                .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee())
                .ok_or(IntegerOverflowError)?;
        let deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO };
        let gross_gas_refund = if result.result.is_err() {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_burnt)
                .unwrap()
        } else {
            prepaid_gas
                .checked_add(prepaid_exec_gas.gas)
                .ok_or(IntegerOverflowError)?
                .checked_sub(result.gas_used)
                .unwrap()
        };

        // NEP-536 also adds a penalty to gas refund.
        let refund_penalty: Gas = config.fees.gas_penalty_for_gas_refund(gross_gas_refund);
        let penalty_gas_price = if ProtocolFeature::AccountCostIncrease.enabled(protocol_version) {
            gas_burn_price
        } else {
            gas_purchase_price
        };
        let refund_penalty_amount = safe_gas_to_balance(penalty_gas_price, refund_penalty)?;

        // Refund for the leftover gas that was not used by this receipt.
        let unused_gas_balance_refund = safe_gas_to_balance(gas_purchase_price, gross_gas_refund)?
            .saturating_sub(refund_penalty_amount);
