**Rationale:**

The functions `update_state`, `update_state_summary`, `send_to_state_buffer`, and the `assert_ledger_state`/`assert_ledger_state_summary` helpers referenced in the question exist only inside `storage/aptosdb/src/state_store/tests/speculative_state_workflow.rs`, a `#[cfg(test)]` proptest harness used to validate the state pipeline against a naive reference implementation (`StateByVersion`), not production code that runs on validators/mainnet nodes.

Even within that test harness, the architecture does not match the premise of "reordering chunk delivery between two channels." The pipeline is a strictly linear, single-producer/single-consumer chain of `mpsc` channels:

`update_state` → (`to_summary_update`/`from_state_update` channel) → `update_state_summary` → (`to_db_commit`/`from_summary_update` channel) → `send_to_state_buffer` → (`to_buffered_state_commit`/`from_buffered_state_commit`) → `commit_state_buffer` [1](#0-0) 

Each stage consumes one `Chunk` at a time from its single inbound channel (which is FIFO by construction) and forwards the *same* chunk's derived state/summary downstream before processing the next chunk [2](#0-1) . There is no scenario with two independently-racing channels carrying the "state" half and "summary" half of the *same* chunk that could be delivered out of order relative to each other — `update_state` produces `(block, next_state, hot_state_updates)` as a single tuple sent atomically over one channel, so `update_state_summary` always receives the state and chunk together, in order [3](#0-2) .

`LedgerStateWithSummary::from_state_and_summary` itself simply pairs whatever `LedgerState` and `LedgerStateSummary` values are passed to it at the call site [4](#0-3) ; in both the test harness and the real production call sites (e.g. `replay_write_sets_after_snapshot` and the `commit_block_for_test` test helper), the `state` and `summary` values passed into it are derived from the *same* `state_update_refs`/chunk within the same synchronous code path, not threaded through independently reorderable channels [5](#0-4) [6](#0-5) .

Since the described mismatch requires a production execution pipeline with two separately-orderable channels for state vs. summary, and no such structure exists (this logic lives only in a test harness with a strictly sequential single-channel-per-stage design), the described exploit path does not exist in this codebase.

fn update_state(
    blocks: Vec<Chunk>,

        .num_threads(4)

                    state_by_version
                        .get_state_value_with_version_by_version(k, version)

                        .map(|(_ver, val)| val)
                });
                assert_eq!(value, expected_value)
            });
        });
        let memorized_reads = state_view.into_memorized_reads();

        let (next_state, hot_state_updates) = parent_state
            .update_with_memorized_reads(
                hot_state.clone(),
                &persisted_state,
                block.update_refs(),
                &memorized_reads,
            )
            .unwrap();

        state_by_version.assert_ledger_state(&next_state);

            for_ckpt_base

            for_latest_base,

        );

        parent_state = next_state.clone();

        to_summary_update
            .send((block, next_state, hot_state_updates))
