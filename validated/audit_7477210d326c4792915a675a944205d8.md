### Title
Unbounded prefix-scan and O(N log N) sort in `getWithPrefix` enables state-driven read-path DoS - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`getWithPrefix` (called from `getIndex`/`getV2Index`) loads *all* prefix-matching entries via `this.prefixQuery(key).values()` into an `ArrayList` and sorts the whole list with `Comparator.comparing(getTimestamp)`, with no cap on the number of entries. Because the number of delegation relationships an attacker can create for a single owner address is attacker-controlled (bounded mainly by economic cost, not by protocol-level limits), this is a real algorithmic-complexity read-path exposure, though the attacker's claimed "near-zero cost" (1 sun per call) is not accurate.

### Finding Description
`getWithPrefix` at [1](#0-0)  performs, for both the FROM and TO prefix directions, an unbounded `prefixQuery(key).values()` collected into an `ArrayList`, followed by `tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp))`. `getIndex` and `getV2Index` call this directly with no size limit [2](#0-1) . This is reachable from `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` [3](#0-2) , which are exposed via gRPC (`GetDelegatedResourceAccountIndex(V2)`) and the corresponding HTTP servlets on FullNode, SolidityNode and PBFT node, all reachable by any unprivileged client without authentication.

Each additional (owner, receiver) pair requires a separate `DelegateResourceContract` execution via `DelegateResourceActuator`, whose `validate()` enforces `delegateBalance >= 1 TRX` (not "1 sun" as claimed) per delegated relationship [4](#0-3) , plus the standard receiver-account and available-frozen-balance checks [5](#0-4) . There is no explicit cap in `DelegateResourceActuator`/`DelegatedResourceAccountIndexStore` on the number of distinct receivers an owner can accumulate. Because `UnDelegateResource` restores the owner's `FrozenV2Balance` immediately (verified in `UnDelegateResourceActuatorTest`), an attacker could in principle cycle delegate→undelegate→delegate-to-new-receiver reusing a small fixed frozen balance, at the cost of one signed transaction (and its bandwidth/energy fee) per unique receiver added to the index — each such transaction leaves a permanent entry keyed by `(prefix, address, counterparty)` in the store (delegate/undelegate calls `this.put`/`this.delete`, but old index entries for now-undelegated pairs are deleted, so the sustained-growth path actually requires keeping many relationships *live* simultaneously, which does require proportional frozen TRX, at 1 TRX minimum per relation).

### Impact Explanation
If exploited, this allows an attacker to inflate the number of index entries under a single owner address, causing `getWithPrefix`'s `O(N log N)` sort and unbounded list materialization to consume CPU and heap on every full/solidity/PBFT node that answers `GetDelegatedResourceAccountIndex(V2)` queries for that address — a DoS vector against the RPC/HTTP query layer, not a state-corruption or fund-theft issue. This matches the "DoS via RPC-API" bounty class, but is a *read-amplification* issue rather than unauthenticated/free — the attacker must pay to create and maintain N live delegation relationships (minimum 1 TRX frozen per relation plus per-transaction bandwidth/energy fees for N transactions), so it is a paid DoS/griefing vector, not a free one.

### Likelihood Explanation
Feasibility depends on economics: creating and *sustaining* N=100,000 live relationships requires at least N TRX of frozen balance (100,000 TRX) locked simultaneously (since undelegating a relation removes it from the index), plus ~100,000 broadcast transactions each incurring bandwidth/energy fees. This is a non-trivial but bounded and payable cost for a well-funded attacker, and is far from the "1 sun per call, negligible cost" premise asserted in the prompt. The lack of any protocol-level cap on distinct receivers per owner, combined with the absence of pagination/limits in `getWithPrefix`, is nonetheless a legitimate design weakness that scales node-side cost with attacker-supplied state at a favorable cost ratio (cheap to write once as chain state, expensive to read repeatedly by any node serving queries for that address).

### Recommendation
Add a hard cap on the number of concurrent delegation relationships per owner enforced in `DelegateResourceActuator.validate()` (analogous to counts enforced elsewhere, e.g. `FreezeCount`), and/or refactor `getWithPrefix` to support pagination/limit parameters and avoid loading and sorting the entire prefix range in memory on every query; consider maintaining the sort order incrementally (e.g., stored order) rather than sorting on every read.

### Proof of Concept
Not independently reproduced with a JUnit run in this analysis; a PoC would need to: (1) freeze/lock N TRX for bandwidth on an owner account, (2) issue N `DelegateResourceContract` transactions to N distinct receiver addresses (each ≥1 TRX, respecting `DelegateResourceActuator.validate()`), (3) call `wallet.getDelegatedResourceAccountIndexV2(owner)` and measure wall-clock/heap versus N, similar to the existing `testGetV2Index`/`testDelegateResourceForBandwidth` tests in `DelegatedResourceAccountIndexStoreTest.java` and `DelegateResourceActuatorTest.java`, scaled to large N. This was not executed here; the economic-cost claim in the audit prompt (near-zero cost per relation) is contradicted by the `>= 1 TRX` minimum enforced in `DelegateResourceActuator.validate()`.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
