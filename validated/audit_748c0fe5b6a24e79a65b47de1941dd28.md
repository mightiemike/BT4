### Title
Slippage protection for PRC20→PC auto-swaps derived from manipulable spot AMM price, not a manipulation-resistant reference - (File: x/uexecutor/keeper/evm.go, x/uexecutor/keeper/execute_inbound_gas.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go, x/uexecutor/keeper/outbound.go)

### Summary
The external report flags Velodrome's `AutoCompounder` for swapping with `amountOutMin = 0`, exposing trades to sandwich/MEV attacks, and recommends computing `amountOutMin` from a manipulation-resistant price source (TWAP/Chainlink) rather than letting it be derived from a spot price that an attacker can move. Push Chain's `uexecutor` module already implements the naive form of the recommended fix — it computes `minPCOut` as 95% of a swap quote before calling `depositPRC20WithAutoSwap` / `refundUnusedGas` — but that quote itself is sourced from `QuoterV2.quoteExactInputSingle`, i.e. the current spot price of the on-chain Uniswap V3 pool, exactly the type of manipulable source the original report warns against.

### Finding Description
Three module-originated swap flows all follow the same pattern:

1. `ExecuteInboundGas` (`x/uexecutor/keeper/execute_inbound_gas.go:104-153`) — GAS inbound path.
2. `gasAndPayloadDepositAutoSwap` (`x/uexecutor/keeper/execute_inbound_gas_and_payload.go:347-379`) — GAS_AND_PAYLOAD inbound path.
3. `applyGasRefund` (`x/uexecutor/keeper/outbound.go:213-234`) — outbound gas-refund swap path.

Each calls [1](#0-0)  to get `quote`, then computes `minPCOut := quote * 95 / 100` and immediately calls [2](#0-1)  (`CallPRC20DepositAutoSwap`) or `CallUniversalCoreRefundUnusedGas` to execute the real swap on the `UniversalCore` contract's own Uniswap V3 pool.

Because `quote` and the executed swap read from the pool's live reserves rather than any time-weighted or externally-verified rate, an unprivileged actor who can move the PRC20↔WPC pool price (e.g., via a large swap against the pool, which anyone can submit as an ordinary EVM transaction against `UniversalCore`'s pool, especially if pool liquidity is thin relative to bridged amounts) can bias the "fair" quote before the module's deposit-and-swap or refund-and-swap fires. The 5% band is calculated relative to *whatever the pool says right now*, not relative to a manipulation-resistant reference, so it bounds slippage from the quote but not the quote's own correctness. A sandwich/self-trade around the block containing the finalizing `MsgVoteInbound`/`MsgVoteOutbound` transaction lets the attacker capture the difference between the true PRC20/PC exchange rate and the manipulated one, at the expense of the bridging user (whose bridged funds convert to fewer native PC gas tokens than fair value) or the protocol (gas-refund recipient receiving less than entitled while the attacker extracts the delta from the pool).

This mirrors the exact residual risk called out in the original report even after Velodrome's fix: "This slippage parameter should be dynamically computed... otherwise... a source that cannot be manipulated (e.g. Chainlink, Custom TWAP)" — the current implementation dynamically computes it, but from a manipulable spot price.

### Impact Explanation
Impacted flows are user-reachable (ordinary bridging deposits trigger GAS/GAS_AND_PAYLOAD inbound processing, and every outbound with excess gas triggers a refund swap) and module-originated (`DerivedEVMCall` from the `uexecutor` module account), matching the in-scope "unauthorized module-originated EVM execution" / "corruption of ... gas fee accounting, refund accounting" categories. A successful attack causes bridging users or refund recipients to receive less native PC than fair value, with the difference captured by the attacker trading against the same pool — a real, if bounded (~5% per event, before accounting for pool depth), loss of user/protocol value with each affected inbound or outbound event.

### Likelihood Explanation
Likelihood depends on the depth/liquidity of the specific PRC20/WPC Uniswap V3 pool used by `UniversalCore` relative to bridged amounts, and on whether the chain's block-production/mempool model permits an attacker to get a manipulating trade included adjacent to the finalizing vote transaction. Push Chain uses CometBFT consensus (not Optimism's private-mempool argument the original report relies on to downgrade severity), so transaction ordering guarantees differ and should be assessed independently; regardless, thin liquidity alone (without needing perfect sandwich ordering) can already skew the spot quote used for `minPCOut` in the exploiter's favor across separate blocks.

### Recommendation
Replace or supplement the QuoterV2 spot quote with a manipulation-resistant reference price before computing `minPCOut`:
- Use a Uniswap V3 TWAP (time-weighted average price observation window) instead of `quoteExactInputSingle`'s instantaneous quote, or
- Cross-check the spot quote against an external oracle price and reject/clamp when they diverge beyond a safe bound, or
- Cap the swap size relative to available pool liquidity/depth to bound worst-case price impact, independent of the 5% band.

### Proof of Concept
Conceptual (no local execution environment available):
1. Attacker observes an in-flight bridge deposit (GAS or GAS_AND_PAYLOAD inbound) for a PRC20 token with a thinly-liquidity-backed Uniswap V3 pool on Push Chain.
2. Attacker submits an ordinary EVM transaction that swaps a large amount into/out of the same pool used by `GetSwapQuote`/`CallPRC20DepositAutoSwap`, shifting the pool's spot price unfavorably for the pending deposit-swap.
3. When quorum is reached and `ExecuteInboundGas` / `ExecuteInboundGasAndPayload` runs, `GetSwapQuote` (`x/uexecutor/keeper/evm.go:502-538`) returns the manipulated price; `minPCOut` (95% of that) still permits the module's swap to execute at the bad rate.
4. Attacker reverses their position, extracting the price-impact delta from the pool at the expense of the value the bridging user's UEA actually receives in PC. [3](#0-2)  and [4](#0-3)  show the identical pattern repeated across all three swap sites.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}

	}

	nonce, err := k.GetModuleAccountNonce(ctx)

		return nil, err

		return nil, err
	}

		abi,

		handlerAddr,        // destination: Handler contract
		big.NewInt(0),
