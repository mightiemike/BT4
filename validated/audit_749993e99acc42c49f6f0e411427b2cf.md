### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay/verify tooling accept a diverged state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single invariant-check function used by chunk-executor verification (`verify_execution`) and replay tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, CLI) to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` stored/committed on-chain. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of `TransactionInfoV1` and are meant to bind the authenticated transaction accumulator leaf to the actual JMT/state-checkpoint root produced by execution.

### Finding Description [1](#0-0) 

The function performs three checks — `status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash` — and then returns `Ok(())` without validating the state-checkpoint-related hashes carried in `TransactionInfoV1` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`). The code contains its own acknowledging TODO:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

This function is invoked from `chunk_executor::verify_execution`, which is the code path responsible for validating that a re-executed chunk's outputs match the persisted, signature-authenticated `TransactionInfo` entries pulled from a backup/archive during restore-verification and replay-verify workflows: [2](#0-1) 

Because `state_checkpoint_hash` (and the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) is never compared to the value computed by local re-execution, a corruption or divergence solely in the state-checkpoint/JMT root component of the committed `TransactionInfo` — while write-set hash, event hash, gas, and status remain unchanged — will not be detected by this verification path. The `assemble_transaction_infos` function that originally builds `TransactionInfo` during normal commit does compute and embed these checkpoint hashes: [3](#0-2) 

but the corresponding verifier does not re-derive and compare them, breaking the intended proof/commitment invariant that "authenticated `TransactionInfo` completely reflects the deterministic VM/state result."

### Impact Explanation
`state_checkpoint_hash` is the field that binds a `TransactionInfo` (and therefore the signed ledger info / transaction accumulator) to the actual Sparse-Merkle/Jellyfish-Merkle state root produced by execution. If this field is ever wrong in stored data (due to a storage bug, a bit-flip, a backup/restore bug, or a future code path that miscomputes it) — while write set, events, gas, and status happen to be unaffected — `verify_execution`/replay-verify tooling used to validate replay in db-tool and aptos-debugger will report success even though the state root committed to the accumulator diverges from the actual VM-computed state. This is exactly the class of impact the state-integrity gate flags as high severity: "wrong ... state proof accepted as valid" and "hard-fork-only divergence during commit, replay, restore, or proof verification" would go undetected by the one function whose job is to catch it.

### Likelihood Explanation
The gap is unconditional and always present in this comparator (not gated behind a flag) — it is exercised on every call to `ensure_match_transaction_info` from `verify_execution`, `aptos-debugger`, and `replay_on_archive`. The TODO comment indicates the authors themselves are aware the gap exists and intend to fix it "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," which suggests this state-checkpoint field is on a path to becoming operationally significant. The likelihood of exploitation depends on some other bug/divergence first producing a bad `state_checkpoint_hash` in stored `TransactionInfo`, but independent of how that divergence occurs, this verifier will fail to catch it, defeating the purpose of replay-verification safety net that operators and auditors rely on for detecting consensus/state divergence.

### Recommendation
Extend `ensure_match_transaction_info` to recompute the expected state-checkpoint hash(es) from the locally re-executed state and compare them against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` (where present/applicable), returning an error on mismatch just as is done for `write_set_hash` and `event_root_hash`.

### Proof of Concept
Not applicable as an exploitable transaction — this is a verification-gap issue, not a state-mutation exploit. Demonstration: construct a `TransactionOutput`/`TransactionInfo` pair where `write_set`, `events`, `gas_used`, and `status` match, but `state_checkpoint_hash` in the `TransactionInfo` is deliberately set to an incorrect value (simulating a corrupted checkpoint or a bug in a future code path that derives it). Call `ensure_match_transaction_info` — it returns `Ok(())`, confirming the checkpoint-hash divergence is silently accepted by the verifier used in `execution/executor/src/chunk_executor/mod.rs` `verify_execution` and downstream replay tooling.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
