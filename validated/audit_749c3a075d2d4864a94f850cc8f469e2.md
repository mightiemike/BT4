This confirms the analog: `ExchangeInjectContract` and `ExchangeWithdrawContract` carry no minimum/expected-output parameter (unlike `ExchangeTransactionContract`, which has an `expected` field for slippage protection), yet both `ExchangeInjectActuator.doValidate/execute` and `ExchangeWithdrawActuator.doValidate/execute` compute `anotherTokenQuant` strictly from the exchange pool's *current* on-chain `firstTokenBalance`/`secondTokenBalance` ratio at execution time. This is the direct analog of the report's front-running scenario: instead of an owner's second `_addInvestor` overwrite being sandwiched, here the exchange creator's inject/withdraw transaction (which is meant to rebalance or adjust the pool at an expected ratio) can be sandwiched with attacker `ExchangeTransactionContract` trades that shift the ratio just before the creator's tx lands and reverse it right after, extracting value from the pool/creator with no way for the creator to bound their exposure.

### Title
Front-runnable AMM ratio in ExchangeInject/ExchangeWithdraw allows value extraction from the exchange creator - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` (unlike `ExchangeTransactionContract`) provide no `expected`/minimum-output field to bound the counter-token amount the creator will receive or must pay. The actuators derive `anotherTokenQuant` purely from the exchange pool's balances at the moment the transaction executes <cite repo="Thankgoddavid56/java-tron--013" path="actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java" start="60,73"></cite><cite repo="Thankgoddavid56/java-tron--013" path="actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java" start="63,79"></cite>, so any party can move the pool ratio with `ExchangeTransactionContract` trades immediately before and after the creator's inject/withdraw transaction, forcing the creator to inject more or withdraw less of the counter-token than intended, and pocketing the difference — the same class of bug described in the report (a "correcting" state-changing operation gets sandwiched by an attacker's transaction ordering, letting the attacker capture value that should have gone to the legitimate party).

### Finding Description
- `ExchangeTransactionContract` explicitly includes an `expected` field used to bound slippage for a swap <cite repo="Thankgoddavid56/java-tron--013" path="Tron protobuf protocol document.md" start="1422-1440" /> and its actuator/store validate against it via `exchangeCapsule.transaction(...)`.
- `ExchangeInjectContract` and `ExchangeWithdrawContract`, however, only specify `owner_address`, `exchange_id`, `token_id`, and `quant` — no minimum/expected bound on the counter-token amount <cite repo="Thankgoddavid56/java-tron--013" path="Tron protobuf protocol document.md" start="1384-1420" />.
- `ExchangeInjectActuator.doValidate`/`execute` compute `anotherTokenQuant` as a straight ratio of the *current* `firstTokenBalance`/`secondTokenBalance` read from the store right before execution <cite repo="Thankgoddavid56/java-tron--013" path="actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java" start="60-83" />, then debits the creator's account for both `tokenQuant` and the computed `anotherTokenQuant` <cite repo="Thankgoddavid56/java-tron--013" path="actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java" start="88-99" />.
- `ExchangeWithdrawActuator.execute` similarly computes `anotherTokenQuant` from the live pool ratio and credits the creator that amount <cite repo="Thankgoddavid56/java-tron--013" path="actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java" start="74-104" />.
- Because block producers order transactions and any account can broadcast `ExchangeTransactionContract` trades against the same `exchange_id`, an attacker can submit a trade immediately before the creator's inject/withdraw transaction to skew the ratio, and a reversing trade immediately after to restore it and capture the price difference — a sandwich attack directly analogous to the reported "overwrite frontrunning": the creator's on-chain "correction" transaction is executed against a manipulated intermediate state instead of the state the creator observed when constructing the transaction.

### Impact Explanation
The exchange creator (an unprivileged, ordinary TRON account that created an `AssetIssue` exchange pool) loses value on every `ExchangeInjectContract`/`ExchangeWithdrawContract` they submit, proportional to how far an attacker can move the pool ratio within the sandwiching trades and the size of the exchange's liquidity limits (`getExchangeBalanceLimit`). This is an asset/accounting corruption vector reachable purely via ordinary broadcast transactions (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) with no special privilege required, fitting the exchange/market math category.

### Likelihood Explanation
Likelihood is high in principle: any account can watch the mempool/broadcast transactions for a target `exchange_id`, and TRON's transaction ordering (bandwidth/fee-based, not strict FIFO with private relay) allows adjacent-block or same-block ordering manipulation similar to other AMM sandwich attacks. The `Not precise enough` check in `ExchangeWithdrawActuator` bounds rounding error to a fixed 0.01% tolerance <cite repo="Thankgoddavid56/java-tron--013" path="actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java" start="228-243" /> but does nothing to prevent the ratio itself from having been manipulated beforehand by a legitimate `ExchangeTransactionContract` trade.

### Recommendation
Add an optional minimum/maximum bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (analogous to `expected` in `ExchangeTransactionContract`), and have `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate the computed `anotherTokenQuant` against that bound before executing, rejecting the transaction if the pool ratio has moved unfavorably beyond the creator's specified tolerance.

### Proof of Concept
1. Creator A holds an exchange pool with `firstTokenBalance = X`, `secondTokenBalance = Y`.
2. Creator A broadcasts `ExchangeWithdrawContract{exchange_id, token_id=first, quant=q}` expecting to receive `~Y*q/X` of the second token.
3. Attacker B, seeing A's pending transaction, broadcasts an `ExchangeTransactionContract` selling a large amount of the second token into the pool just before A's tx is packed into a block, driving `secondTokenBalance` down (and `firstTokenBalance` up).
4. A's `ExchangeWithdrawContract` executes against this skewed ratio via `ExchangeWithdrawActuator.execute`, giving A less of the second token than intended <cite repo="Thankgoddavid56/java-tron--013" path="actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java" start="77-89" />.
5. Attacker B immediately reverses the trade with a second `ExchangeTransactionContract`, restoring the ratio and capturing the value difference extracted from A's withdrawal.
