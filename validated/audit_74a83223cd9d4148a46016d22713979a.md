### Title
Malicious signer can permanently poison a future reward cycle's DKG aggregate-key vote by front-running with a known key value — (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
The `.signers-voting` contract enforces "an aggregate public key can be used only in a single reward cycle" via the `used-aggregate-public-keys` map, which is keyed **only by the 33-byte key value**, not by the `(key, reward-cycle)` pair. This is the exact bug class described in the external report: an oracle/value that is intended to be scoped to a specific pair is instead mapped from a coarser key, so writing an entry for one pair (here: one reward cycle) silently forecloses the value for a different, unrelated pair (a different reward cycle) — even when that write came from a losing/minority vote that never reached consensus.

### Finding Description
`used-aggregate-public-keys` records which cycle "claimed" a given 33-byte candidate key: [1](#0-0) 

`is-novel-aggregate-public-key` treats a key as "used" for a cycle *other than* the given one if `used-aggregate-public-keys` already has any entry for that key with a different `reward-cycle` value: [2](#0-1) 

Crucially, `vote-for-aggregate-public-key` writes to `used-aggregate-public-keys` **unconditionally on every vote**, regardless of whether that vote ever reaches the `threshold-consensus` needed to actually set `aggregate-public-keys` for the cycle: [3](#0-2) 

The equality the contract intends to preserve is: *"key K is approved for cycle C if and only if C is the one true cycle for which the honest signer majority converged on K via DKG."* Because `used-aggregate-public-keys` is keyed by `key` alone rather than by `(key, reward-cycle)`, the very first vote (even a single minority-weight, un-thresholded vote) for a given key value in cycle `M` permanently binds that key to `M` in the map. Any subsequent vote for the *same* key value in a *different* cycle `N` — including the legitimate, honestly-derived DKG result for cycle `N` — is rejected with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY`, because `is-novel-aggregate-public-key` compares the stored cycle (`M`) against `N` and finds them unequal.

A single registered signer (any nonzero weight, not requiring a majority) who is a member of both cycle `M`'s and cycle `N`'s signer sets can exploit this: DKG round communication for a cycle happens off-chain over StackerDB before the resulting key is posted on-chain via `vote-for-aggregate-public-key`. A malicious signer participating in that off-chain round for the *target* cycle `N` can observe (or otherwise predict) the aggregate public key value the honest majority is converging on, then submit a throwaway, non-winning vote for the *same* key value tagged to a different cycle `M` they also belong to. That single `map-set used-aggregate-public-keys key M` call permanently forecloses key `K` for cycle `N`: every honest signer's subsequent vote for `K` in cycle `N` fails `is-novel-aggregate-public-key` and the cycle can never converge on that key, even with unanimous honest supermajority support.

### Impact Explanation
This breaks a consensus-critical equality (poison attack): a minority, unprivileged signer can prevent the legitimate signer set from ever recording the honestly-produced DKG aggregate public key for a target reward cycle, forcing wasted DKG rounds / re-runs and potentially exhausting the prepare-phase voting window (`ERR_INVALID_ROUND` gates rounds to increment by at most 1, and the voting window is bounded to the prepare phase). Inability to establish the aggregate public key for a reward cycle degrades the network's ability to validate/aggregate signer signatures for that cycle's tenure, which maps to the "poison…bounded" / signer-set divergence category described as High impact in the analog rules. It requires only a single dishonest signer (not node operator/admin privileges, not majority) and does not require compromising Bitcoin or Clarity asset authority.

### Likelihood Explanation
The prerequisite is that the attacker is a registered signer for both the "poison source" cycle and the target cycle (a normal, permissionless outcome of being repeatedly selected into the signer set via stacking), and that they can learn or predict the exact 33-byte key value the honest signers are about to converge on in the target cycle before it is posted on-chain — plausible because signer-to-signer DKG coordination happens off-chain over StackerDB, visible to all participating signers (including a dishonest one) before the confirming vote transaction is broadcast. No majority or economic assumption is required; a single dishonest signer of any weight suffices to submit the poisoning vote.

### Recommendation
Scope `used-aggregate-public-keys` (and the novelty check) to the `(key, reward-cycle)` pair the way `votes` and `tally` already are, e.g. only record/deny reuse of a key once it has actually been *approved* (inserted into `aggregate-public-keys`) for some cycle, rather than recording every proposed-but-unconfirmed candidate. This restores the intended equality that a key's cycle-binding is determined by consensus outcome, not by the first vote cast for it.

### Proof of Concept
1. Attacker `A` is a registered signer in reward-cycle `M`'s and reward-cycle `N`'s signer sets (`N` in the future, prepare phase not yet started for `N`).
2. During cycle `N`'s off-chain DKG round, `A` observes (as a DKG participant) that honest signers are converging on aggregate key `K`.
3. Before honest signers post their `vote-for-aggregate-public-key` calls for cycle `N`, `A` calls `vote-for-aggregate-public-key(A_index, K, round=1, reward-cycle=M)` for the unrelated cycle `M` (where `A` is also a signer). This need not reach threshold; it only needs to execute the unconditional `(map-set used-aggregate-public-keys key reward-cycle)` at signers-voting.clar:171 with `reward-cycle = M`.
4. When honest signers later call `vote-for-aggregate-public-key(idx, K, round, reward-cycle=N)`, `is-novel-aggregate-public-key(K, N)` evaluates `used-aggregate-public-keys[K] == M`, compares `M == N` → false, and the call fails with `(err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY)` for every honest signer, permanently blocking `K` from ever being approved for cycle `N`.

            ;; vote by signer weight

            (cached-weight (try! (get-and-cache-total-weight reward-cycle)))

            (current-round (default-to {
                votes-count: u0, 
                votes-weight: u0} (map-get? round-data {reward-cycle: reward-cycle, round: round})))
                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
        ;; Check that the aggregate public key is the correct length
        (asserts! (is-eq (len key) u33) (err ERR_ILL_FORMED_AGGREGATE_PUBLIC_KEY))
