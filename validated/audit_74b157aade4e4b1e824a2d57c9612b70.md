## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` skips validating state/hot-state/position-state checkpoint hashes, allowing replay-verify to accept a state root that diverges from local execution - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function used by chunk execution, replay tooling, and the debugger to confirm that a freshly (re-)executed `TransactionOutput` actually matches the trusted, already-persisted/proof-carried `TransactionInfo` before it is treated as validated. It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but — per its own embedded TODO — it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 
computes and asserts equality only for status, gas, the write-set hash, and the event root hash. The function's own comment documents the gap explicitly: [2](#0-1) 

This means the state-checkpoint hash (the Jellyfish Merkle / state-summary root committed in `TransactionInfo`) is never cross-checked against the root actually produced by local re-execution in this code path, even though `TransactionInfo` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (in the V1/"trading-native" variant) `position_state_checkpoint_hash` as first-class committed fields (see `TransactionInfo::builder_v1`/`builder_v0` at [3](#0-2) ).

This function is invoked from multiple integrity-sensitive callers, including chunk execution (`execution/executor/src/chunk_executor/mod.rs`), backup replay verification (`storage/db-tool/src/replay_on_archive.rs`), the Aptos debugger, and the CLI — all places where a locally recomputed VM output is checked against a value inherited from a trusted proof before being accepted/committed. Since none of these call sites re-derive and compare the state-checkpoint hash through this helper, a divergence confined to state-tree/hot-state/position-state construction (as opposed to the write set itself) is not caught by this specific safety net.

### Impact Explanation
If the locally computed state-summary root (main state, hot state, or the trading-native position state) diverges from what a trusted `TransactionInfo` claims, but the write set, events, gas, and status still match, `ensure_match_transaction_info` reports success. Tooling that relies on this check (notably `replay_on_archive`, used to audit historical execution/replay correctness) would falsely certify a state root that does not match local computation, undermining the very audit invariant these tools exist to enforce. This is a proof/authenticated-value binding gap: a "checkpoint" field is trusted/propagated without ever being independently verified at this checkpoint, structurally analogous to the external report's core theme (a checkpointed value that is never re-validated against the value it should represent).

### Likelihood Explanation
The gap is real and self-documented in-repo, but its exploitability is constrained: the position-state checkpoint field is explicitly gated behind the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag, and the comment frames this as a known TODO to close "before enabling" that feature. I could not confirm within this pass whether the *main* `state_checkpoint_hash`/`hot_state_checkpoint_hash` omission is independently caught by another guard in the same call paths (e.g., accumulator-hash verification elsewhere in the chunk executor, or `DoStateCheckpoint::get_state_checkpoint_hashes`'s comparison against `known_state_checkpoints`), which could make this specific helper's gap non-exploitable in the currently-shipped configuration. Given the explicit self-acknowledgment and feature gating, likelihood on current mainnet configuration appears low-to-moderate rather than immediately critical, but the invariant is genuinely unenforced in this function today.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when present) `position_state_checkpoint_hash` between the recomputed output and the provided `txn_info`, closing the gap before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any other consumer relying on this function for state-root assurance) is enabled, and audit all call sites (`chunk_executor`, `replay_on_archive`, `aptos_debugger`, CLI) to ensure they don't rely on this function as their sole checkpoint-consistency guard.

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this requires a scenario where write-set/events/gas/status match but the state-checkpoint/hot-state/position-state root diverges (e.g., a bug isolated to JMT/hot-state/position-state tree construction). I was unable to fully verify, within the available tool budget, whether other guards in the same call paths (e.g., `DoStateCheckpoint`'s comparison against `known_state_checkpoints`) already prevent this from being independently exploitable end-to-end — this would need to be confirmed with a live Devin session tracing the full chunk-executor/replay call chain and testing a deliberately corrupted state-tree build against `ensure_match_transaction_info`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
