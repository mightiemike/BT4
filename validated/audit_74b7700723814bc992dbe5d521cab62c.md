### Title
Witness/voter reward "Vi" accumulator silently discards rewards earned during zero-vote cycles - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
Java-tron's witness voting reward mechanism uses a Synthetix-style "reward-per-share" accumulator (`witnessVi`) to let voters claim their proportional share of a witness's block/standby/transaction-fee rewards. Exactly as in the reported Solidity pattern, when the "total supply" analog (a witness's total vote count) is zero for a reward cycle, the reward amount that was already reserved for that witness is silently dropped instead of being carried forward or refunded — a real loss-of-funds accounting bug, not merely a UX nuisance.

### Finding Description
Each maintenance cycle, `MortgageService.payReward()` credits block/standby/tx-fee rewards to a witness by calling `delegationStore.addReward(cycle, witnessAddress, value)`, after deducting the witness's brokerage share which is immediately credited via `adjustAllowance`. [1](#0-0)

At maintenance time, `MaintenanceManager.doMaintenance()` calls `accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` for every witness, using the reward index accumulator pattern (analogous to `rewardPerTokenStored`): [3](#0-2)

If `voteCount == 0` for that cycle (the "total supply" analog), the function takes the `if` branch and simply *forwards* the previous `Vi` value without adding any delta — the `reward` value fetched from `getReward(cycle, address)` is read but never applied anywhere else. It is not carried over to a future cycle, not refunded to the fee pool, and not credited to any account. This exactly mirrors the reported bug's first defect: "when totalSupply = 0, no rewards are actually distributed... leftover is wasted."

Unlike the Solidity report's second defect (first-staker windfall), java-tron does not exhibit that half of the bug, because `Vi` is written every cycle (even when forwarding unchanged), so a later voter's `deltaVi = endVi - beginVi` computation (in `MortgageService.computeReward` / `VoteRewardUtil.computeReward`) cannot accidentally sweep in an entire dormant period's rewards — the affected cycle's reward is simply gone, not later mis-attributed to one lucky voter. [5](#0-4) 

### Impact Explanation
When a witness's on-chain vote count is zero during a reward cycle (e.g., a low-participation witness whose remaining voters fully unvote right at the cycle boundary, or a witness slot filled with zero votes on a sparsely-voted network/testnet), the TRX value already deducted from the transaction-fee pool / block-reward subsidy for that cycle (`chainBaseManager.getDynamicPropertiesStore().saveTransactionFeePool(...)` in `Manager.payReward`) is never credited to any account's allowance. This is a genuine, permanent loss of protocol funds (a form of value burn) rather than a cosmetic bug, matching the "waste" impact category from the source report. It is accounting-only impact reachable through ordinary voting/un-voting actions performed by unprivileged token holders, not through any privileged administrative operation. [6](#0-5) 

### Likelihood Explanation
Reaching this state requires a witness's tallied vote count to be exactly zero at the moment `accumulateWitnessVi` runs for a cycle in which that witness still earned nonzero `reward`. Because witness selection is vote-rank-based, this is uncommon on a healthy mainnet but is realistically reachable on low-participation networks, in early bootstrap phases, or via coordinated mass un-voting timed to a maintenance cycle boundary — all performed by regular unprivileged voters, requiring no special access.

### Recommendation
When `voteCount == 0` but `reward > 0` in `DelegationStore.accumulateWitnessVi` (and its duplicate in `RewardViCalService.accumulateWitnessVi`), do not silently drop the reward. Either (a) roll the un-distributable reward forward into the next cycle's reward pool for the same witness via `delegationStore.addReward(cycle + 1, address, reward)`, or (b) return it to the transaction-fee pool / block-reward budget so it is not permanently lost, and apply the same fix consistently everywhere the pattern is duplicated. [7](#0-6) 

### Proof of Concept
1. A witness `W` is active/standby-elected for cycle `N` (e.g., due to prior vote count > 0 or a low-participation network filling remaining SR slots).
2. During cycle `N`, `W` produces blocks / stands by, and `MortgageService.payBlockReward` / `payStandbyWitness` invoke `payReward`, which computes `value` (post-brokerage) and calls `delegationStore.addReward(N, W, value)` — real TRX is deducted from the transaction-fee pool for this. [8](#0-7) 
3. Before the maintenance for cycle `N` runs, all voters of `W` unvote, so `W.getVoteCount()` becomes `0` at maintenance time.
4. `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)`. [3](#0-2) 
5. Inside `accumulateWitnessVi`, `voteCount == 0`, so the `reward` fetched from `getReward(N, W)` is discarded — `Vi` is simply forwarded unchanged, and the `value` TRX credited via `addReward` is never applied to any voter's `allowance` in any subsequent `queryReward`/`withdrawReward` call. [4](#0-3) 
6. The TRX corresponding to `value` is permanently unaccounted for — deducted from the fee pool but never credited to any account.

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
