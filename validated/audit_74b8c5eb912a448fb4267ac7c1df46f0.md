### Title
Sierra-to-CASM compilation for Declare transactions is performed before signature and fee-bearing validation, enabling free CPU/memory-exhaustion DoS - (File: crates/apollo_gateway/src/gateway.rs)

### Summary
In `GenericGateway::add_tx_inner`, a submitted Declare transaction is sent to the Sierra compiler (a CPU- and memory-intensive subprocess) immediately after cheap stateless checks, but *before* the stateful validator runs the account's `__validate__` entry point (signature check) and before nonce/fee-bounds checks. This mirrors the reported Arbitrum WASM-activation bug class: an expensive operation (bytecode decompression there, Sierra→CASM compilation here) is performed prior to charging/validating the party responsible for its cost, so an attacker can trigger the expensive work for free by submitting transactions that will ultimately be rejected in the later, cheaper checks.

### Finding Description
`add_tx_inner` performs, in order:
1. `check_declare_permissions` and `stateless_tx_validator.validate(&tx)` — only format-level checks (Sierra version, class size/length, entry-point ordering); no signature verification and no balance/fee check. [1](#0-0) 
2. Acquisition of `declare_compilation_semaphore` and `convert_rpc_tx_to_internal_and_executable_txs`, which for Declare transactions triggers `ClassManager::add_class` → `SierraCompiler::compile`, invoking the actual Sierra-to-CASM compiler subprocess. [2](#0-1) [3](#0-2) [4](#0-3) 
3. Only *after* compilation completes does `stateful_transaction_validator.extract_state_nonce_and_run_validations` run, which performs nonce checks, fee-bound checks and (via Blockifier) executes the account's `__validate__` entry point that verifies the transaction signature. [5](#0-4) 

The project's own config comment acknowledges the ordering problem explicitly: "Compiling a declared Sierra class to CASM is CPU- and memory-intensive, and it happens during transaction ingestion before the transaction's signature and balance are verified," and mitigates it only with a process-global concurrency semaphore (`DEFAULT_MAX_CONCURRENT_DECLARE_COMPILATIONS = 40`), not with any fee/signature gate. [6](#0-5) 

Because signature checking and balance verification only happen after compilation, an attacker does not need a valid account signature or sufficient balance to force the compilation step to run — a syntactically well-formed (within stateless size/version bounds) but arbitrarily complex Sierra program that satisfies the cheap stateless checks will still reach the compiler. The documented transaction submission flow confirms the compile-before-validate ordering and that every node that receives the tx via P2P propagation independently repeats the same compile-before-validate flow ("Note over GW_B: Same validation flow"), meaning a single crafted Declare transaction forces compilation work across every node in the network, not just the originating one. [7](#0-6) 

### Impact Explanation
This is a network-wide compute-resource exhaustion (DoS) vector: an attacker can repeatedly submit Declare transactions with large/complex-but-stateless-valid Sierra programs that will always fail the later signature/nonce/fee checks, at effectively zero cost. Since the same compile-before-validate flow runs on every gateway node that receives the transaction via P2P, the attack amplifies across the network. If sustained, this saturates the `sierracompiler` fleet and the concurrency semaphore, causing legitimate Declare transactions to be rejected (`too_many_concurrent_declare_compilations`) and degrading overall transaction ingestion — directly matching the "network unable to confirm new transactions" impact criterion.

### Likelihood Explanation
Likelihood is elevated because reaching this path requires only sending a standard `RpcTransaction::Declare` through the public `add_tx` gateway entrypoint — no valid account, signature, or balance is required, only passing the stateless size/version/entry-point checks. The semaphore (40 concurrent compilations) mitigates but does not eliminate the issue, since an attacker can continuously refill the queue with rejected declares faster than legitimate ones can be processed, and the cost asymmetry (near-zero cost to attacker vs. compiler CPU/memory cost to the network) is exactly the pattern flagged in the reference report.

### Recommendation
- **Short term:** Reorder validation so that account existence, nonce, fee-bound/balance checks, and ideally signature verification occur before invoking `SierraCompiler::compile`, or require a bonded/staked minimum balance check prior to compilation. At minimum, charge/reserve fee or apply a per-sender rate limit before the compilation step in `add_tx_inner` (`crates/apollo_gateway/src/gateway.rs`).
- **Long term:** Review all other computationally expensive operations reachable during transaction ingestion (e.g., proof verification order, class hash computation) to ensure signature/fee gating happens first, consistent with the general principle recommended in the reference report.

### Proof of Concept
1. Craft a `RpcTransaction::Declare` (V3) with: a syntactically valid Sierra program that is within `max_sierra_version`/`max_class_length` limits but compiles slowly/expensively (e.g., large entry-point count or bytecode near the size cap), an arbitrary/garbage signature, and a sender address with zero balance or an invalid nonce.
2. Submit it repeatedly (varying `sender_address`/`nonce` to bypass duplicate-tx caching) via the gateway's `add_tx` RPC endpoint.
3. Observe in `add_tx_inner` that `stateless_tx_validator.validate` passes, the `declare_compilation_semaphore` permit is acquired, and `SierraCompiler::compile` runs to completion (consuming CPU/memory) before `stateful_transaction_validator.extract_state_nonce_and_run_validations` ultimately rejects the transaction for bad signature/insufficient balance/nonce.
4. Repeating this concurrently up to and beyond `max_concurrent_declare_compilations` (default 40) causes legitimate declare transactions to be rejected with `too_many_concurrent_declare_compilations`, and because propagated transactions are recompiled by every receiving node, the effect replicates across the network.

// Compiling a declared Sierra class to CASM is CPU- and memory-intensive, and it happens during
// transaction ingestion before the transaction's signature and balance are verified. Bound the
// number of compilations running concurrently to protect the node from resource exhaustion.
//
// Derivation: compilations are served by the sierracompiler instances, so the safe per-gateway
// bound is the sierracompiler fleet's headroom divided across the gateway fleet, i.e.
// `per_instance_capacity * num_sierracompiler_instances / num_gateway_instances`. Observed
// sierracompiler usage per compilation is small (memory spike ~0.75% of an instance), so a single
// instance can absorb many concurrent compilations. 40 stays well within that envelope while still
// capping the blast radius of a declare flood; retune via the formula above if the
// sierracompiler/gateway instance ratio or per-instance capacity changes.
const DEFAULT_MAX_CONCURRENT_DECLARE_COMPILATIONS: usize = 40;
