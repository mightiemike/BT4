## Analog Found: Missing Chain/Network Binding in Meta‑Transaction (`DelegateAction`) Signatures Enables Cross‑Network Replay

### Title
Meta-Transaction `DelegateAction` Signature Omits Chain-Binding Data, Enabling Cross-Network Replay - (`core/primitives/src/action/delegate.rs`)

### Summary
The NEP-366/NEP-461 meta-transaction signature scheme signs only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`. Unlike regular `SignedTransaction`s, which are anchored to a specific `block_hash` that only exists on one chain, the `DelegateAction` digest contains no chain/network identifier at all. This is the exact bug class from the external report (message digest missing `chainId`), reachable by any relayer who receives a `SignedDelegateAction` from a user.

### Finding Description
`DelegateAction::get_nep461_hash` builds the signed payload from a `SignableMessage` wrapping only the fields of `DelegateAction`: [1](#0-0) [2](#0-1) 

The signature verification in `SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify` only checks this hash against `public_key`, with no chain or network component: [3](#0-2) [4](#0-3) 

On the receiving side, `apply_delegate_action` only re-verifies the signature, checks `max_block_height` (a plain height number, not a chain-specific hash) and the sender-id/nonce via the access key state — nothing here is chain-specific either: [5](#0-4) 

By contrast, a normal `SignedTransaction` binds to a `block_hash` that is unique per chain/genesis, so it cannot be replayed across two independent NEAR networks. `DelegateAction` has no equivalent binding — only `nonce` (an access-key-scoped counter) and `max_block_height` (a bare integer, which is trivially satisfiable on a fresh/young chain).

This is materially the same gap flagged in the external report: an unprivileged/relayer-collected signed authorization message is valid on any chain that happens to share the same `sender_id`/`public_key`/nonce state, because the digest lacks a `chainId`-equivalent value. NEAR's own tooling implicitly acknowledges this: `tools/mirror` — built specifically to replay one chain's history onto another — must *re-sign* every `DelegateAction`/`DelegateActionV2` with a freshly mapped key rather than reuse the original signature, precisely because the original signature carries no chain binding and could otherwise be replayed verbatim: [6](#0-5) [7](#0-6) 

Note also the code comment in `actions.rs` explicitly stating "The inner delegate signature is verified below, here on the receiver shard" with no mention of any chain/network check being present: [8](#0-7) 

### Impact Explanation
NEAR implicit accounts (hex-encoded public keys) have the *identical account-id string format* on every NEAR-protocol-compatible network (mainnet, testnet, or any other chain sharing the account-id length/format rules), unlike named accounts (`.near` vs `.testnet` suffixes). A user who derives/uses the same key pair to create an implicit account on two networks will have the same `sender_id` and `public_key` on both. A relayer (or anyone who obtains a `SignedDelegateAction`, since relayers are explicitly untrusted intermediaries in this design — see `docs/architecture/how/meta-tx.md`) can take a `SignedDelegateAction` the user authorized for use on chain A and wrap it in a brand-new outer `SignedTransaction` (which the relayer signs fresh, satisfying chain-A-independent block-hash requirements) and submit it to chain B. If chain B's access-key nonce for that key is still below the delegate's `nonce` and the current block height is below `max_block_height` (both easily true on a young/idle account), the inner actions (transfers, `AddKey`, `FunctionCall` with attached deposit, etc.) execute on chain B exactly as if authorized there — moving value or granting access the user never approved for that chain.

### Likelihood Explanation
Exploitation requires only: (1) a relayer/observer capturing a `SignedDelegateAction` (an expected, routine occurrence per the meta-tx architecture, where relayers are semi-trusted but explicitly assumed capable of misbehaving — see `DelegateActionInvalidSignature`/`faulty relayer` handling patterns elsewhere in the codebase), and (2) the victim's account existing in the same nonce/height window on a second network with the same key — a realistic scenario for implicit accounts and for any deliberate/accidental key reuse across NEAR-compatible networks (e.g., mainnet vs. a fork, or two independently operated networks sharing the same genesis account-id conventions). No validator collusion, node compromise, or privileged access is required — a single relayer-submitted transaction suffices.

### Recommendation
Include a chain-binding value in the `DelegateAction` signature payload — e.g., the network's `genesis_hash`/chain id, or reuse the existing `MessageDiscriminant` scheme to embed a chain identifier — so that `SignableMessage`/`get_nep461_hash` binds the signature to one specific chain, mirroring how ordinary transactions are bound via `block_hash`. This should be treated as a protocol change (versioned similarly to `DelegateActionV2`) to avoid breaking already-deployed signing clients.

### Proof of Concept
1. User creates implicit account `abc123...` (64-hex account id) with key `K` on Network A (e.g. testnet) and signs a `DelegateAction` (`sender_id = abc123...`, `nonce = 1`, `max_block_height = A_head+100`, actions = `[Transfer{...}]`) for a testnet dApp/relayer, per the flow in `integration-tests/src/user/mod.rs::meta_tx` / `test-loop-tests/src/tests/meta_tx.rs`.
2. The relayer (or any party who intercepts the `SignedDelegateAction`) observes that the same `abc123...` implicit account, funded independently, also exists on Network B (e.g. mainnet or a fork) with an access key for `K` whose nonce is still `< 1` and whose current block height is `< max_block_height`.
3. Attacker builds a new outer `SignedTransaction` addressed to `abc123...` on Network B, signed by their own relayer key with a valid *Network‑B* `block_hash`, containing `Action::Delegate(signed_delegate_action)` — the exact, unmodified `SignedDelegateAction` from step 1.
4. `apply_delegate_action` on Network B verifies the (chain-agnostic) signature successfully via `VersionedSignedDelegateActionRef::verify` (`core/primitives/src/action/delegate.rs:83-96/210-220`), passes the `max_block_height`/nonce checks (`runtime/runtime/src/actions.rs:474-491`), and executes the transfer on Network B without any authorization from the user for that network.

    pub fn get_nep461_hash(&self) -> CryptoHash {

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }
