### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting `replay-on-archive` accept a diverged state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by replay/verification tooling such as `storage/db-tool/src/replay_on_archive.rs`) checks status, gas used, write-set hash (`state_change_hash`), and event root hash against the trusted `TransactionInfo`, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The code itself contains an acknowledged TODO describing exactly this gap.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  compares four fields between the locally re-executed `TransactionOutput` and the archived/authenticated `TransactionInfo`: execution status, gas used, the write-set hash against `state_change_hash`, and the event root hash. It deliberately stops there — the trailing comment explicitly states: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [2](#0-1) .

This function is the actual correctness gate used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions locally and calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` to decide pass/fail [3](#0-2) . It is also invoked from `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` for similar replay/simulation verification purposes.

The relevant `TransactionInfoV1` struct stores `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields [4](#0-3) , and these fields are populated from the state-checkpoint Merkle roots produced during execution (see `DoStateCheckpoint::run`, which computes `state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, and `position_state_checkpoint_hashes`) [5](#0-4) . None of these are cross-checked by `ensure_match_transaction_info`.

### Impact Explanation
If local re-execution produces a different world-state root (main state, hot state, or the native-position state) than what is recorded in the archived/on-chain `TransactionInfo` — due to a bug in state-checkpoint hashing, storage corruption, non-determinism in one of these newer state trees, or a malicious archive substituting write-set-consistent-but-state-root-divergent data — `replay_on_archive` will report success. This defeats the entire purpose of replay verification for the state-commitment invariant: proof/commitment integrity for the state root is not actually checked, only the write-set and event hashes are. Given `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a real, current feature flag wired through `BlockExecutorConfigFromOnchain::with_features` [6](#0-5) , a divergence in the position-state root (or hot-state root) introduced by any bug in that subsystem would go completely undetected by this verification tool on mainnet archives.

### Likelihood Explanation
This is not an attacker-triggered exploit in the traditional sense, but a verification-blind-spot: any bug or non-determinism in state-checkpoint / hot-state / native-position root computation across the fleet silently passes `replay_on_archive` validation. The comment in the code confirms this was a known, accepted gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), meaning the feature referenced is being staged for enablement while this integrity check remains incomplete — closely mirroring the external report's "forgot to include X in the verification/accumulation" bug class.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in both the recomputed checkpoint output and `txn_info`) before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, and add regression tests asserting `replay_on_archive`/`aptos-debugger` fail when any of these roots diverge.

### Proof of Concept
Not directly exploitable via a single transaction; the gap is demonstrated by code inspection: construct a `TransactionOutput` whose write set and events match `txn_info`, but pair it with a `TransactionInfoV1` whose `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are deliberately wrong (e.g., `HashValue::random()`); `ensure_match_transaction_info` returns `Ok(())`, and `replay_on_archive::Verifier::execute_and_verify` at [7](#0-6)  reports no mismatch despite the state roots being wrong.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
