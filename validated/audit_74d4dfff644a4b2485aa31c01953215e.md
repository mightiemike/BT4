### Title
Missing timeout/AbortSignal on outbound OAuth access-token requests can hang the auth handler indefinitely - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`, `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
The OAuth `callback` and `tokenExchange` flows both call `fetchRequestFactory(config)` to POST to `https://${cleanShop}/admin/oauth/access_token`, but never supply an `AbortSignal` or timeout, and `fetchRequestFactory` itself applies no default timeout — it just forwards `options` straight into `abstractFetch`.

### Finding Description
`fetchRequestFactory` is a thin wrapper that logs and calls `abstractFetch(url, options)` with whatever `RequestInit` it is given [1](#0-0) . Neither caller supplies a `signal`:
- `oauth.ts`'s `callback` builds the token-exchange POST body and awaits the response with no `signal` set [4](#0-3) .
- `token-exchange.ts`'s `tokenExchange` does the same for the token-exchange grant type [5](#0-4) .

Both functions are directly reachable from unauthenticated/anonymous or single-merchant HTTP requests:
- OAuth `callback` is invoked from the app's `/auth/callback` route, reachable by any party who can trigger (or replay) a callback request with a valid `code`/`hmac`/`state` — this is the exact route Shopify redirects to after merchant consent, so any request hitting this endpoint (including slow/broken upstream cases) blocks on this `await`.
- `tokenExchange` is invoked by `performTokenExchange` middleware (Express) and the analogous strategy in `shopify-app-remix`/`shopify-app-react-router`, triggered on every incoming request bearing a session token when the token-exchange future flag is enabled [6](#0-5) .

Documentation confirms that a timeout must be explicitly opted into via `signal: AbortSignal.timeout(...)`, meaning by default none of these OAuth code paths have any deadline: the "Setting a timeout" section of the GraphQL client docs shows this is only applied when explicitly passed by app code [7](#0-6) .

### Impact Explanation
If Shopify's `/admin/oauth/access_token` endpoint (or any network path to it) hangs or becomes slow/unresponsive, the request awaiting `fetchRequestFactory`'s promise in the OAuth callback or token-exchange handler will block indefinitely. In server runtimes with limited concurrency (e.g., Node's event loop combined with limited outbound connection pools, or serverless invocation timeouts), a burst of such requests (each of which can be triggered by any anonymous client hitting `/auth/callback` or `/auth` with a stale/invalid but well-formed session token that forces token exchange) can exhaust available request-handling resources, denying service to legitimate OAuth/token-exchange traffic and other app functionality that shares the same process. This matches the "Missing Timeout Check" bug class from the reference report, where an unbounded outbound call in a critical path could hang a whole processing pipeline.

### Likelihood Explanation
Reaching this code requires only a normal, low-privilege interaction: any client can call the app's `/auth/callback` endpoint, and any client possessing an (even invalid/expired) session token can trigger `performTokenExchange`. No special network position, secret disclosure, or privileged actor is required — an attacker simply needs to cause several such requests to be in flight while the outbound connection to Shopify (or a DNS/network intermediary) is slow, which is plausible under normal network degradation or targeted network-layer interference.

### Recommendation
Add a bounded `AbortSignal` (e.g., via `AbortSignal.timeout(N)`) to the `RequestInit` passed into `fetchRequestFactory` calls inside `oauth.ts`'s `callback` and `token-exchange.ts`'s `tokenExchange` (and similarly for `refresh-token.ts`, `client-credentials.ts`, `migrate-to-expiring-token.ts` which use the same factory), so a slow or unresponsive Shopify OAuth endpoint cannot indefinitely block these auth handlers.

### Proof of Concept
1. Configure a test/proxy that makes `https://${shop}/admin/oauth/access_token` hang indefinitely (never completes the TCP/TLS handshake or response body).
2. Trigger the app's OAuth callback route (`/auth/callback`) with a validly-signed `state`/`hmac`/`code` query string pointing at that shop.
3. Observe that the request handler in `oauth.ts`'s `callback` blocks forever awaiting `fetchRequestFactory(config)(...)` at [8](#0-7) , with no timeout ever firing, since no `signal` is provided anywhere in the call chain.
4. Repeat concurrently to exhaust the app server's available request-handling capacity.

export function fetchRequestFactory(config: ConfigInterface) {
  return async function fetchRequest(
    url: string,
    options?: RequestInit,
  ): Promise<Response> {
    const log = logger(config);
    const doLog =
      config.logger.httpRequests && config.logger.level === LogSeverity.Debug;

    if (doLog) {
      log.debug('Making HTTP request', {
        method: options?.method || 'GET',
        url,
        ...(options?.body && {body: options?.body}),
      });
    }

    const response = await abstractFetch(url, options);

    if (doLog) {
      log.debug('HTTP request completed', {
        method: options?.method || 'GET',
        url,
        status: response.status,
      });
    }

    return response;
  };
