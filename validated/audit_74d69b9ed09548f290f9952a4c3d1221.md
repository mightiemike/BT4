Confirmed: `KVSessionStorage.addShopIds` (unlike `RedisSessionStorage.addKeyToShopList`, which checks `if (!idKeysArray.includes(idKey))` before pushing) unconditionally appends `session.id` to the shop's tracking array on every `storeSession()` call, without checking whether that ID is already present.

### Title
Unbounded duplicate session-ID accumulation in `KVSessionStorage` leads to session-storage/auth-handler DoS - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage.storeSession()` calls the private `addShopIds()` helper on every store, which reads the existing `shop:${shop}` id-list key and blindly appends the new session id, with no de-duplication check [1](#0-0) [2](#0-1) . Because offline sessions use a deterministic, shop-scoped id (`offline_${shop}`), any repeated `storeSession()` call for the same session (e.g. repeated OAuth completions or repeated token-exchange refresh cycles) re-adds the same id to the array every time, growing it without bound.

### Finding Description
This is the direct code-pattern analog of the reported bug class: an array is appended to without first checking whether the element (a token address in the original report, a session id here) is already registered. The `RedisSessionStorage` implementation in the same monorepo demonstrates the correct pattern by guarding the push with `if (!idKeysArray.includes(idKey))` [3](#0-2) , confirming that `KVSessionStorage` is missing an equivalent duplicate check.

`storeSession()` is invoked repeatedly with the same offline session id (`offline_${shop}`) from multiple unprivileged-reachable auth code paths:
- Every completed OAuth authorization-code callback stores the offline session again: [4](#0-3) .
- Every token-exchange refresh cycle (triggered whenever the stored offline/online session is missing or near expiry) re-stores the session under the same id: [5](#0-4)  and the equivalent Express middleware [6](#0-5) .

A merchant (or anyone able to drive the shop through repeated install/re-authorization or repeated session-token refresh cycles, e.g. via `expiringOfflineAccessTokens`) can trigger `storeSession()` for the same shop arbitrarily many times. Each call appends one more duplicate entry to the `shop:${shop}` KV value with no cap, since `addShopIds` never checks for an existing id before pushing [2](#0-1) .

### Impact Explanation
`findSessionsByShop()` reads this id list and does one KV `get`/`loadSession` per entry [7](#0-6) , so an inflated, duplicate-laden list causes unbounded read amplification (increased KV read costs/latency) each time the app looks up sessions for that shop (e.g., during webhook processing or session cleanup). More critically, Cloudflare KV (the target platform for this adapter) enforces per-value size limits; once the JSON-serialized id array for a shop grows large enough, the `namespace.put()` call in `addShopIds` will fail, causing `storeSession()` to reject. Since `storeSession()` is awaited directly inside the OAuth callback and token-exchange auth handlers without being wrapped to tolerate this failure, this turns into an unhandled exception that breaks the auth/token-exchange handler for that shop, denying the merchant the ability to install or refresh authentication going forward (DoS of the auth handler for that tenant).

### Likelihood Explanation
Reaching this only requires driving normal, unauthenticated-to-the-app-backend OAuth/token-exchange flows for a single shop repeatedly (re-installing the app, or repeatedly presenting session tokens that force a token-exchange refresh) — actions available to the shop's own merchant/admin or anyone who can complete OAuth for that shop, with no elevated privileges required. No secrets, MITM, or third-party dependency compromise is needed; it purely depends on the missing duplicate check in `addShopIds`.

### Recommendation
Add a de-duplication check identical to the one already used in `RedisSessionStorage.addKeyToShopList`, e.g.:
```diff
 private async addShopIds(shop: string, ids: string[]) {
   const key = this.getShopSessionIdsKey(shop);
   const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
-  await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
+  const newIds = ids.filter((id) => !shopIds.includes(id));
+  if (newIds.length > 0) {
+    await this.namespace.put(key, JSON.stringify([...shopIds, ...newIds]));
+  }
 }
```
This mirrors the recommended fix pattern from the original report (checking for existing registration before pushing) and prevents unbounded growth of the per-shop session id list.

### Proof of Concept
1. Configure an app with `KVSessionStorage` and complete OAuth (or token exchange) for `shop.myshopify.com`, which calls `storeSession()` and results in `shop:shop.myshopify.com` = `["offline_shop.myshopify.com"]`.
2. Trigger the same OAuth callback or token-exchange refresh again for the same shop (e.g., re-authorize the app, or force session invalidation/expiry so `performTokenExchange`/`TokenExchangeStrategy.authenticate` re-runs) [8](#0-7) .
3. Observe that `shop:shop.myshopify.com` now contains `["offline_shop.myshopify.com", "offline_shop.myshopify.com"]` — repeat N times to observe unbounded growth of the array, since `addShopIds` never checks for pre-existing entries [2](#0-1) .
4. Continue until the KV value size limit is hit; subsequent `storeSession()` calls (and thus the OAuth callback / token-exchange handler that awaits them) begin failing for that shop.
