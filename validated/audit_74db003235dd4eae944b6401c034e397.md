### Title
Relayer fee payout in the NEAR Wallet Contract is unconditional and not tied to the success of the underlying transfer/call - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The reported PoolTogether bug class is: the vault credits/mints shares based on an *assumed* full transfer amount instead of the amount actually confirmed to have moved, and pays out downstream operations against that unverified assumption, breaking internal accounting when the real transferred amount differs. In the `WalletContract::inner_rlp_execute` function, the relayer "fee" transfer is scheduled as an independent promise **before** the underlying emulated action (`EOABaseTokenTransfer` / `ERC20Transfer`) is known to have succeeded, so the wallet pays the relayer regardless of whether the real transfer actually completes.

### Finding Description
In `inner_rlp_execute`, once a `TransactionKind::EthEmulation` is parsed with a non-zero `fee`, the contract immediately creates a separate promise batch to pay the relayer, unrelated to (not `.then()`-chained with) the promise that performs the actual transfer/call: [1](#0-0) 

```rust
if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { fee, .. })
| TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
    &transaction_kind
{
    if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
        let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
        env::promise_batch_action_transfer(refund_promise, *fee);
    }
}
```

This `refund_promise` is a *standalone* promise (created via `env::promise_batch_create`, not chained to the promise that will later execute the actual base-token transfer or `ft_transfer`/`storage_deposit` sequence built later in the same function and returned as `promise`). The actual transfer/call promise is only constructed afterward, based on `transaction_kind`, and can subsequently fail (e.g., `ERC20Transfer` fails if `storage_balance_of`/`storage_deposit`/`ft_transfer` reverts, or `EOABaseTokenTransfer` fails if the address-check/registrar lookup fails), which is handled later in `rlp_execute_callback` — but by that point the relayer fee promise has already been dispatched independently and will execute regardless: [2](#0-1) 

The `rlp_execute_callback` only refunds the *external caller's* `attached_deposit` (`CallerDeposit`) if the underlying promise fails — it does nothing about the fee already sent to the relayer:

```rust
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(refund_promise, NearToken::from_yoctonear(yocto_near.into()));
    }
    ...
}
```

Because the fee-payment promise is not conditioned on, nor causally linked to, the success of the transfer it is meant to compensate for, the wallet's internal accounting assumption ("pay the relayer `fee` because they will successfully deliver `transfer_amount`") can diverge from what actually happens on-chain — mirroring the PoolTogether pattern where a downstream payout/accounting step is computed from an assumed outcome rather than the confirmed result of the underlying operation.

### Impact Explanation
A user signs an Ethereum-style transaction (via `rlp_execute`) authorizing a `fee` to the relayer contingent on the relayer successfully delivering the user's intended transfer/call. Since the fee-payment promise executes unconditionally and independently of the transfer outcome, any relayer (which is by design meant to be trust-minimized/permissionless per the contract's own comments) can submit a transaction/target combination that is guaranteed or likely to fail the emulated transfer/ERC-20 path (e.g., referencing a target/receiver that will make `storage_deposit`/`ft_transfer` revert, or racing state so the transfer fails) while still collecting the `fee` from the wallet's own balance. This is a real, wallet-balance value movement to the relayer that is not conditioned on the wallet actually receiving what it paid for, directly resulting in unauthorized value extraction from the user's wallet account with no compensating transfer having occurred.

### Likelihood Explanation
This is triggerable purely by a permissionless relayer submitting a single `rlp_execute` call (as intended by design — the code comments explicitly state "This allows **any relayer** to safely serve base token transfers from any wallet without additional on-boarding"), i.e., an ordinary transaction/RPC caller with no special privileges. No validator, network, or sync-layer compromise is required; the reachable path is a standard NEAR function call plus a subsequent cross-contract callback failure, both of which are normal, unprivileged operations.

### Recommendation
Chain the relayer fee-payment promise to the outcome of the underlying transfer/call rather than dispatching it independently — e.g., build the fee-transfer promise as part of the same promise chain (via `.then()`/`.and()` composition) so it only executes after (and conditioned on) `PromiseResult::Successful` for the emulated transfer, or move the fee payout into `rlp_execute_callback` so it is only sent when `env::promise_result(0)` is `Successful`.

### Proof of Concept
1. Attacker controls (or is) a relayer with a `FunctionCall` access key on an eth-implicit wallet account (standard onboarding flow shown in `test_wallet_contract_interaction`/`test_base_token_transfer_with_relayer_refund`).
2. Attacker crafts a signed Ethereum-style ERC20/base-token transfer with a non-zero `gas_price` (mapped to `fee`) but targets a scenario engineered to fail the second leg (e.g., an ERC-20 target contract that will reject `storage_deposit`/`ft_transfer`, or a base-token target whose registrar lookup/address-check fails).
3. Calls `rlp_execute`. `inner_rlp_execute` immediately schedules `promise_batch_action_transfer(refund_promise, fee)` to the relayer's account, independent of the outcome of the main transfer promise built later in the function.
4. The main transfer/ERC-20 promise fails; `rlp_execute_callback` only refunds `CallerDeposit` (the external caller's `attached_deposit`, if any) — it does not revert or claw back the fee already sent to the relayer.
5. Result: relayer receives `fee` from the wallet's balance while the user's intended transfer never completed — value left the wallet with no corresponding successful transfer, and the wallet contract's `has_in_flight_tx`/balance state no longer reflects a coherent "fee for delivered service" accounting invariant, matching the reported bug class of paying out based on an assumed rather than confirmed transfer outcome.
