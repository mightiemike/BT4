### Title
Unbounded Transaction Pool Memory Consumption via Missing Serde Default on `transaction_pool_size_limit` - (File: `nearcore/src/config.rs`)

### Summary

`TransactionPool` enforces its size limit only when `total_transaction_size_limit` is `Some(…)`. The `Config` struct field `transaction_pool_size_limit: Option<u64>` carries no `#[serde(default = "…")]` attribute, so any `config.json` that omits the field deserializes it as `None`, silently disabling the cap. An unprivileged user who submits many valid transactions to such a node can grow the pool without bound until the process is killed by the OS OOM killer.

### Finding Description

`TransactionPool::insert_transaction` guards pool growth with:

```rust
if let Some(limit) = self.total_transaction_size_limit {
    if new_total_transaction_size > limit {
        return InsertTransactionResult::NoSpaceLeft;
    }
}
``` [1](#0-0) 

When `total_transaction_size_limit` is `None` the branch is never taken and every insertion succeeds regardless of pool size. [2](#0-1) 

`ShardedTransactionPool` passes `pool_size_limit` straight through to each per-shard `TransactionPool`: [3](#0-2) 

`pool_size_limit` originates from `ClientConfig::transaction_pool_size_limit`, which is populated directly from the `Config` struct field: [4](#0-3) 

The `Config` struct field is declared as a plain `Option<u64>` with no `#[serde(default = "…")]` attribute: [5](#0-4) 

`Config::default()` correctly calls `default_transaction_pool_size_limit()` (returns `Some(100_000_000)`): [6](#0-5) [7](#0-6) 

However, `Config::default()` is only used when generating a fresh config. When `serde_json` deserializes an existing `config.json` that lacks the `transaction_pool_size_limit` key, serde's standard `Option<T>` handling produces `None`, not `Some(100_000_000)`. Any node whose config predates the introduction of this field, or whose operator removed the key, runs with an unbounded pool.

Additionally, there is no per-account transaction count limit inside `TransactionPool`. Transactions are grouped by `(signer_id, public_key)` key but the `Vec<ValidatedTransaction>` per group is unbounded: [8](#0-7) 

### Impact Explanation

An unprivileged user with a small NEAR balance can submit a large number of valid transactions with sequential nonces. Each transaction passes `can_verify_and_charge_tx` because the balance check is evaluated against the current on-chain state (not the pending pool state), so the same balance satisfies every check. All transactions are inserted into the pool. With `total_transaction_size_limit = None`, pool memory grows without bound until the node process is terminated by the OS OOM killer, causing a complete local denial of service for that validator or RPC node.

Individual transaction size is bounded at `max_transaction_size = 1,572,864` bytes (1.5 MiB): [9](#0-8) 

but with no pool cap, an attacker can submit arbitrarily many such transactions.

### Likelihood Explanation

- Any node whose `config.json` was generated before `transaction_pool_size_limit` was introduced, or that was hand-edited to remove the key, is affected.
- The attack requires only a valid NEAR account with a small balance; no privileged access is needed.
- The `RpcHandlerActor` accepts transactions from the public JSON-RPC endpoint (`broadcast_tx_async`, `send_tx`) and inserts them into the shared pool: [10](#0-9) 

- The `NoSpaceLeft` branch only fires when a limit is set; with `None` it is never reached, so the attacker receives no rejection signal.

### Recommendation

1. Add `#[serde(default = "default_transaction_pool_size_limit")]` to the `transaction_pool_size_limit` field in `Config` so that absent keys in existing config files receive the intended 100 MB default rather than `None`.
2. Consider enforcing a hard minimum (non-`None`) in `TransactionPool::new` or in the config validation path so that `None` cannot reach production.
3. Add a per-account (or per-`PoolKey`) transaction count cap inside `TransactionPool::insert_transaction` to prevent a single account from monopolizing the entire pool budget.

### Proof of Concept

1. Start a nearcore node whose `config.json` omits `transaction_pool_size_limit` (or set it to `null`).
2. From an account with any positive balance, submit a loop of transactions with sequential nonces via `broadcast_tx_async`:
   ```
   for nonce in 1..=N:
       broadcast_tx_async(SignedTransaction(signer, nonce, max_size_payload))
   ```
3. Each call returns `ValidTx`; the pool grows by up to 1.5 MiB per transaction.
4. After enough iterations the node's RSS exceeds available RAM and the process is OOM-killed.

The missing serde attribute is the root cause: [5](#0-4) 

The guard that would stop growth is skipped when the limit is `None`: [11](#0-10)
