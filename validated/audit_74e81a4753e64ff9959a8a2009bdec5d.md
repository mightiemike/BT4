### Title
Unbounded recursion in `bytecode_hash_node` over attacker-supplied `bytecode_segment_lengths` causes stack-overflow DoS during compiled-class-hash computation - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`HashableCompiledClass::hash()` → `hash_inner()` → `bytecode_hash()` → `bytecode_hash_node()` recursively descends into a `NestedIntList` (`bytecode_segment_lengths`) sourced from the `CasmContractClass` field of an attacker-declared contract class, with no depth limit. [1](#0-0) 

### Finding Description
`bytecode_hash_node` recurses once per nesting level of the `NestedIntList::Node` structure via `node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child))`, with the base case only reached at `NestedIntList::Leaf`. [2](#0-1) 
This structure is taken directly from the `CasmContractClass.bytecode_segment_lengths` field, which is either explicitly present or defaulted to a single leaf: `get_bytecode_segment_lengths` in the same file returns the class-supplied structure as-is. [3](#0-2) 
This function is invoked from `CasmContractClass::hash()` (`hash_inner`) every time a compiled class hash needs computing — including inside blockifier when constructing a `CompiledClassV1` from JSON/CASM at Declare-transaction execution time. [4](#0-3) 
The related `create_bytecode_segment_structure_inner` used by the Starknet OS during re-execution/hash validation is similarly unbounded and recurses per `NestedIntList` nesting level. [5](#0-4) 
A companion function, `NestedFeltCounts::new_inner`, is explicitly restricted with `assert!(segmentation_depth <= 1, ...)`, indicating the authors are aware deep nesting is a hazard elsewhere in the codebase but did not apply the same guard to `bytecode_hash_node` or `create_bytecode_segment_structure_inner`. [6](#0-5) 
Because `bytecode_segment_lengths` originates from the declared CASM class (a field the class declarer controls when constructing/uploading the compiled class, and which is stored/reused verbatim for hashing and OS bytecode-segment reconstruction), a class declarer can submit a class whose `bytecode_segment_lengths` is a deeply nested `NestedIntList::Node` chain (e.g., depth in the tens of thousands), each holding trivial leaf content, well within any bytecode-size limit, causing the native call stack to overflow when `hash()`/`bytecode_hash_node` (or the OS's `create_bytecode_segment_structure_inner`) is invoked.

### Impact Explanation
A stack overflow in Rust aborts the process (no panic unwinding across a blown stack), crashing the sequencer/gateway/prover process handling the Declare transaction or OS re-execution. This is reachable from a single Declare transaction submitted by any account, matching the required "unauthenticated attacker with a single request" impact class from the analog report, and results in denial of the sequencer's ability to process transactions/blocks — a network unable to confirm new transactions.

### Likelihood Explanation
Likelihood is high for any component that computes or re-derives the compiled class hash from the class-supplied `bytecode_segment_lengths` (declare-transaction execution, class-hash validation, and OS bytecode-segment-structure reconstruction during re-execution), since none of these paths bound recursion depth. The only mitigating factor is if an earlier validation step rejects deeply nested `bytecode_segment_lengths` structures (e.g., structural validation during class ingestion) — I could not find such a depth-bounding check in the reachable code paths I inspected, though the sequencer's Sierra→CASM compilation step (in `apollo_compile_to_casm`/`apollo_sierra_compilation_config`) may constrain what segmentations a normally-compiled Sierra program can produce; I was not able to fully verify within available searches whether the compiler enforces a maximum segmentation nesting depth or whether a class-declarer can supply/influence a pre-compiled CASM class bypassing that compiler.

### Recommendation
Convert `bytecode_hash_node` (and the analogous `create_bytecode_segment_structure_inner` / `NestedFeltCounts::new_inner`) into iterative, explicit-stack-based implementations, or add and enforce a strict maximum nesting depth for `bytecode_segment_lengths` at class-ingestion/validation time (rejecting the class before it reaches hashing), consistent with the depth-limit already used for `NestedFeltCounts::new_inner`.

### Proof of Concept
Construct a `CasmContractClass` where `bytecode_segment_lengths` is `NestedIntList::Node(vec![NestedIntList::Node(vec![NestedIntList::Node(...)])])` nested to a very large depth (e.g., 100,000 levels), with `bytecode` containing a single trivial `Leaf` at the bottom, and submit it as the compiled/declared class in a Declare transaction. When the sequencer computes `compiled_class.hash(&HashVersion::V2)` (or `V1`) as part of Declare-transaction execution/validation via `hash_inner` → `bytecode_hash` → `bytecode_hash_node`, the recursive descent exhausts the native call stack and crashes the process — mirroring the `flatted.parse()` PoC's deeply nested `$`-index chain that crashed Node.js via unbounded `revive()` recursion. fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
