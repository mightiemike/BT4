### Title
Attached NEAR deposit permanently stuck in `WalletContract` for `AddKey`/`DeleteKey` eth-emulated transactions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entrypoint is `#[payable]` and accepts an attached NEAR deposit from any external caller for any decoded Ethereum-style action, tracking it generically as a `CallerDeposit` so it can be refunded if the resulting cross-contract promise fails. However, for `AddKey` and `DeleteKey` actions, `action_to_promise` never attaches any deposit to the outgoing promise, and the refund logic in `rlp_execute_callback` only returns the deposit to the caller when the promise result is `Failed`. When such a promise succeeds (the normal/expected case), the attached deposit is neither spent nor refunded and remains permanently held by the wallet contract, which exposes no withdrawal method for these funds.

### Finding Description
`inner_rlp_execute` builds an `ExecutionContext` from `env::attached_deposit()` regardless of the decoded action type, and `CallerDeposit::new` captures this deposit for any external (non-self) caller whenever it is non-zero: [1](#0-0) 

For `AddKey` and `DeleteKey` actions, `action_to_promise` builds the outgoing promise without ever passing along a deposit — `add_access_key_allowance_with_nonce` and `delete_key` take no `deposit` parameter: [2](#0-1) 

These actions are dispatched through the generic `_` branch in `inner_rlp_execute`, which attaches the `caller_deposit` only as a callback argument, not to the promise itself: [3](#0-2) 

The only place the `caller_deposit` is ever used to actually move funds is inside `rlp_execute_callback`, and only in the `PromiseResult::Failed` branch: [4](#0-3) 

If the `AddKey`/`DeleteKey` promise succeeds (which is the expected outcome for a valid transaction), the `Successful` branch simply returns the response without ever spending or refunding the deposit. Because the deposit was never attached to any outgoing action, it sits as part of the wallet contract account's own NEAR balance. The contract exposes no owner-only or public withdrawal/sweep function for this balance — `WalletContract`'s public surface is limited to `get_nonce` and `rlp_execute` (plus private callbacks), so any such deposit becomes permanently unreachable, structurally analogous to the reported `receive()`-with-no-withdrawal pattern.

### Impact Explanation
Any relayer or the account owner themself who attaches a NEAR deposit to an `rlp_execute` call whose decoded action is `AddKey` or `DeleteKey` will have that deposit permanently locked in the wallet contract once the action succeeds. This is a direct, unauthorized-permanent-freezing-of-funds bug reachable by a single ordinary transaction/relayed call, with no code path (public or private) to later reclaim the balance.

### Likelihood Explanation
Reaching this requires only a single `FunctionCall` to `rlp_execute` with a non-zero attached deposit and an RLP payload decoding to an `AddKey` (with `FunctionCall` permission — full access key add is already rejected) or `DeleteKey` action. This is trivially reachable by any unprivileged relayer or by the wallet owner via a standard signed transaction/meta-transaction; no privileged role or malicious-node behavior is required.

### Recommendation
Either reject `rlp_execute` calls carrying a non-zero deposit for `AddKey`/`DeleteKey` actions (returning an error before spawning the promise), or unconditionally refund the `caller_deposit` back to the caller in the `PromiseResult::Successful` branch of `rlp_execute_callback` whenever the executed action did not itself consume a deposit.

### Proof of Concept
1. Deploy `WalletContract` at an eth-implicit account and derive its associated signing key as usual.
2. As an external relayer account, call `rlp_execute(target, tx_bytes_b64)` attaching a non-zero deposit (e.g. 1 NEAR), where `tx_bytes_b64` is a valid RLP-encoded, correctly-signed Ethereum transaction whose decoded `near_action::Action` is `AddKey` with `FunctionCallPermission` (or `DeleteKey`) targeting the wallet's own account.
3. `inner_rlp_execute` computes `caller_deposit = Some(CallerDeposit { account_id: relayer, yocto_near: 1 NEAR })` per `CallerDeposit::new` [1](#0-0) , then dispatches through the `_` branch calling `action_to_promise` which produces `Promise::new(target).add_access_key_allowance_with_nonce(...)` with no deposit attached [5](#0-4) .
4. The `AddKey`/`DeleteKey` promise succeeds; `rlp_execute_callback` takes the `PromiseResult::Successful` branch and returns `ExecuteResponse{success:true,...}` without touching `caller_deposit` [6](#0-5) .
5. The relayer's 1 NEAR deposit remains part of the wallet contract account's balance; no method exists on `WalletContract` to move it out again.

Note: I was unable to fully trace `ExecutionContext::new` in `types.rs` beyond the `CallerDeposit::new` snippet shown, so I cannot rule out an early-rejection check elsewhere in `ExecutionContext::new` that might reject non-zero deposits for non-transfer actions; this should be verified directly against `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs` before treating this as confirmed exploitable.

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
