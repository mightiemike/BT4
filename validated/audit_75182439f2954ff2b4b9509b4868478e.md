## Title
Wallet Contract's relayer-ban promise can leave `has_in_flight_tx` permanently stuck, freezing an ETH-implicit account's funds and access forever - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

## Summary
The `WalletContract` (NEP-518) is the *only* way to move NEAR or call other contracts out of an ETH-implicit account, since such accounts cannot receive a full access key and cannot be deleted. Every mutating entry point (`rlp_execute`, `address_check_callback`, `nep_141_storage_balance_callback`) sets `has_in_flight_tx = true` before returning a `Promise`, with the documented invariant that it must be reset to `false` once the promise resolves via a callback (`rlp_execute_callback` or `ban_relayer`). The relayer-banning path builds a *single-receipt batch* (`delete_key` + `function_call_weight("ban_relayer", ...)`) rather than a `.then()` two-hop promise. If the `delete_key` action in that batch fails, the whole receipt fails atomically and `ban_relayer` (which resets `has_in_flight_tx`) never executes, leaving the flag permanently `true`. This blocks every future `rlp_execute` call on that account, permanently freezing all funds and the ability to use access keys held by the account.

## Finding Description
`rlp_execute` guards re-entrancy with `has_in_flight_tx`: [1](#0-0) 

The documented invariant states the flag must become `true` whenever a mutable method returns a promise, and by implication must be reset once that promise resolves: [2](#0-1) 

The reset only happens inside the two designated callbacks, `rlp_execute_callback` and `ban_relayer`: [3](#0-2) 

When a relayer error is detected and the transaction was signed by the account itself, `rlp_execute` (and `address_check_callback`) dispatch `create_ban_relayer_promise`, setting `has_in_flight_tx = true` and relying on `ban_relayer` to flip it back: [4](#0-3) 

Crucially, `create_ban_relayer_promise` is built as a *single-receipt batch* of two actions on the same account — `delete_key` followed by `function_call_weight("ban_relayer", ...)` — not as a `.then()`-chained callback promise: [5](#0-4) 

Within a single NEAR receipt, actions execute sequentially and the receipt is atomic: if an earlier action (`delete_key`) fails (e.g., the relayer's access key was already deleted/rotated concurrently, or the key no longer exists due to a race between two relayers/transactions, or it's already scheduled for deletion in a prior in-flight receipt), the receipt as a whole fails and later actions — including `function_call_weight("ban_relayer", ...)` — are never executed. Since `ban_relayer` is the only path that resets `has_in_flight_tx` for this branch, the flag remains permanently `true`.

Because `rlp_execute` unconditionally rejects any invocation while `has_in_flight_tx == true`, the account becomes permanently unable to process any subsequent Ethereum-compatible transaction. Given that an ETH-implicit account cannot receive a `FullAccessKey` and cannot be deleted, the Wallet Contract is the *only* execution path for that account's funds. A permanently stuck `has_in_flight_tx` therefore permanently freezes the account's entire NEAR balance and its capability to interact with any other contract, mirroring the GMX `Bank.sol` bug class where funds become permanently unreachable due to a missing/failing completion step in the value-transfer path.

## Impact Explanation
This is a direct, transaction-triggered permanent freeze of user funds: any unprivileged party able to submit an `rlp_execute` call with a "faulty relayer" condition (an attacker can act as a rogue/faulty relayer, or exploit a race with the legitimate relayer's own key rotation) can, under the right key-state condition, cause the `delete_key` action to fail, freezing the victim's ETH-implicit account indefinitely. This satisfies the "permanently frozen funds" acceptance criterion and is reachable from a single relayer-submitted `rlp_execute` transaction — no privileged, network-layer, or validator role is required.

## Likelihood Explanation
Triggering requires a specific race: the access key targeted by `delete_key` in `create_ban_relayer_promise` must no longer exist (or be otherwise unremovable) when the ban receipt executes, while `has_in_flight_tx` was already set `true` from the initiating call. This can plausibly happen when (a) a relayer's access key is deleted or replaced concurrently (e.g., a legitimate `DeleteKey` action processed by an earlier/parallel `rlp_execute` call), or (b) two relayers race to serve the same faulty transaction and both trigger a ban against the same key. Because the Wallet Contract explicitly is designed to support multiple relayer public keys with function-call-scoped permissions being added/removed dynamically, such key-removal races are a normal, reachable condition rather than a purely theoretical one. This places the likelihood at medium: it needs a specific but realistic ordering of relayer key management and faulty-transaction handling, not an adversarial validator or privileged action.

## Recommendation
- Make the relayer-ban path resilient to a failing `delete_key`: either split the batch so `function_call_weight("ban_relayer", ...)` is scheduled unconditionally (e.g., via a `.then()` callback on the `delete_key` promise, so `ban_relayer` runs and resets `has_in_flight_tx` regardless of whether the key deletion succeeded), or make `delete_key` best-effort (tolerate `AccessKeyDoesNotExist`) before proceeding to the `function_call_weight` action within the batch.
- Add a scheduled/expiring lock instead of an unconditional boolean toggle, so that `has_in_flight_tx` cannot remain stuck forever if any resolution path is skipped (e.g., store a timestamp/nonce and allow the lock to be cleared if it's older than some bound, provided replay protection via `nonce` is preserved).
- Add integration coverage where the relayer's key is removed/rotated exactly while a ban-relayer receipt is in flight, asserting `has_in_flight_tx` is always eventually reset to `false`.

## Proof of Concept
1. Deploy the Wallet Contract on an ETH-implicit account `E` and register relayer key `K1` with `FunctionCallPermission { receiver_id: E, method_names: ["rlp_execute"] }`, as done in `test_wallet_contract_interaction` (`integration-tests/src/tests/features/wallet_contract.rs:227-346`).
2. Register a second relayer key `K2` the same way.
3. Have `K1` submit an `rlp_execute` transaction whose `target`/`to` mismatch triggers the "faulty relayer" branch (as in `test_relayer_invalid_address_target`, `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs:175-240`). This sets `has_in_flight_tx = true` and schedules `create_ban_relayer_promise` targeting `K1`.
4. Before that receipt is applied, race in a `DeleteKey` action for `K1` from a separate, concurrently-processed transaction (e.g., issued by the account itself via a self-signed `rlp_execute` in the same block, or another relayer's ban action targeting `K1` simultaneously), so that by the time the `delete_key` action inside `create_ban_relayer_promise`'s receipt executes, `K1` no longer exists.
5. Observe: the `delete_key` action fails with `AccessKeyDoesNotExist`; the batch receipt fails atomically, so `function_call_weight("ban_relayer", ...)` never runs; `has_in_flight_tx` remains `true`.
6. Any subsequent `rlp_execute` call on `E` now immediately returns `"transaction already in progress, please try again later"` forever, matching the guard logic at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:97-105`, permanently freezing `E`'s balance and access.

*Note: Exact atomic-batch failure semantics (whether a failed non-final action in a batch receipt guarantees later actions are skipped) is based on general NEAR receipt/action processing model as documented and standard runtime behavior; I was not able to fully trace the multi-action-per-receipt short-circuit logic in `runtime/runtime/src/lib.rs` within the available search budget, so this should be confirmed against `apply_action_receipt`'s action-loop behavior before treating this as fully proven.*

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

    #[private]
    pub fn ban_relayer(&mut self) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        ExecuteResponse {
            success: false,
            success_value: None,
            error: Some("Error: faulty relayer".into()),
        }
    }

fn create_ban_relayer_promise(current_account_id: AccountId) -> Promise {
    let pk = env::signer_account_pk();
    Promise::new(current_account_id).delete_key(pk).function_call_weight(
        "ban_relayer".into(),
        Vec::new(),
        NearToken::from_yoctonear(0),
        Gas::from_tgas(1),
        GasWeight(1),
    )
}
