### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` RPC calls allow anyone to stop sequencer commitment production - (File: crates/sequencer/src/rpc.rs)

### Summary
The sequencer RPC server exposes `citrea_haltCommitments` and `citrea_resumeCommitments`, which unconditionally forward a control message to the sequencer's commitment-production loop. The global `Auth` middleware that gates the RPC server only protects three hardcoded methods, and these two are not among them, so any unauthenticated caller can halt or resume sequencer commitments.

### Finding Description
The broken binding: the caller authorized to invoke `citrea_haltCommitments`/`citrea_resumeCommitments` should equal "the sequencer operator holding the configured RPC `api_key`", i.e. `authenticated_caller == operator`. In practice, `authenticated_caller == anyone`.

The RPC server applies a global auth middleware at server construction: [1](#0-0) 
which wraps every request with `Auth::new(s, rpc_config.api_key.clone())`. That middleware only enforces the API key for a hardcoded allowlist: [2](#0-1) 
`PROTECTED_METHODS` contains only `"backup_create"`, `"backup_validate"`, `"backup_info"`. Any method name not in this list bypasses the API-key check entirely and is forwarded straight to the inner service.

`citrea_haltCommitments` and `citrea_resumeCommitments` are registered as ordinary methods on the sequencer's `SequencerRpcServer` trait with no additional guard inside their handlers: [3](#0-2) 
Unlike `publish_test_block`, which explicitly checks `self.context.test_mode` before acting: [4](#0-3) 
`halt_commitments`/`resume_commitments` have no such check — they unconditionally send `SequencerRpcMessage::HaltCommitments`/`ResumeCommitments` over `rpc_message_tx`: [5](#0-4) 

These messages are consumed by the sequencer's runner loop (`crates/sequencer/src/runner.rs`), which toggles internal commitment-production state accordingly. Since these methods are merged into the same public RPC module used for all other sequencer JSON-RPC calls (`register_rpc_methods` in `crates/sequencer/src/lib.rs:172`, and `create_rpc_module` in `crates/sequencer/src/rpc.rs:505-509`), any client that can reach the sequencer's public RPC port can invoke them with zero credentials, provided no external reverse-proxy layer filters them (out of scope per the auth logic living entirely in this repo's `Auth` middleware).

### Impact Explanation
Any unauthenticated caller can repeatedly call `citrea_haltCommitments` to permanently suppress sequencer commitment submission to Bitcoin DA. Since sequencer commitments are the trigger for downstream batch proof generation and eventual L1 finalization, this halts the entire pipeline that proves state and enables withdrawals, without requiring any privileged key, DA transaction, or state manipulation. This is repeatable indefinitely and affects the whole network (all nodes depending on sequencer commitments), matching the "High" category: an unauthenticated JSON-RPC call that mutates node state and bypasses `Auth`.

### Likelihood Explanation
Preconditions: the sequencer's JSON-RPC endpoint is reachable by the caller (no additional reverse-proxy authentication outside this crate). No BTC/cBTC cost, no special role, no key material is required — a single unauthenticated JSON-RPC POST suffices, and can be repeated arbitrarily to keep commitments halted. Attacker cost is effectively zero and the exploit is trivially repeatable across time/blocks.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and audit other sequencer control-plane RPCs) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or add an explicit operator-authentication/API-key check inside the `halt_commitments`/`resume_commitments` handlers in `crates/sequencer/src/rpc.rs`, consistent with how sensitive backup endpoints are protected today.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }
