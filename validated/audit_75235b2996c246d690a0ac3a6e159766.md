### Title
CancelAllUnfreezeV2 restores frozen TRON Power balance but does not reimburse the vote weight lost at unfreeze time - ([File: actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java])

### Summary
The reported Meta Finance bug is a fairness/accounting-consistency issue: when a user reverses an unstake (`reStake`), the amount previously "slashed" during the vesting period is not proportionally reimbursed, leaving the user's on-chain state permanently worse off than it should be for an action they cancelled. The same *class* of bug — "reversing an exit action does not restore state that was reduced when the exit began" — is reachable in java-tron's freeze/unfreeze v2 lifecycle for TRON_POWER (voting) resource.

### Finding Description
When an account calls `UnfreezeBalanceV2Actuator` for `TRON_POWER`, `updateVote()` immediately shrinks the account's recorded `Vote` list proportionally to the reduced TRON power, whenever total votes exceed the account's remaining TRON power: [1](#0-0)  specifically the vote-shrinking logic at lines 340-387: [2](#0-1) 

This is analogous to the "slash" in the report: unfreezing TRON_POWER causes an immediate, permanent reduction of the account's `votesList`/`VotesCapsule` — separate from and independent of the underlying frozen balance.

If the account subsequently calls `CancelAllUnfreezeV2Actuator` (the direct analog of `reStake`) before the unfreeze period expires, the frozen `TRON_POWER` balance and total resource weight are fully restored: [3](#0-2) 

However, `CancelAllUnfreezeV2Actuator.execute()` never calls anything analogous to `updateVote()` to restore the votes that were shed at unfreeze time — the actuator only manipulates `FrozenV2` balances and resource weights: [4](#0-3) 

The same gap exists in the TVM native-contract path used by smart contracts (`cancelAllUnfreezeV2Action` / `CancelAllUnfreezeV2Processor`), which also restores frozen balance/weight only, with no vote reconciliation: [5](#0-4) [6](#0-5) 

As a result, after a full unfreeze→cancel round-trip on TRON_POWER, the account's `getTronPowerFrozenV2Balance()` (and thus its true governance power) is fully restored, but its recorded `votesList` remains permanently reduced from the intermediate unfreeze step — a state divergence between actual TRON power and recorded voting weight that the user cannot fix except by manually re-voting (`VoteWitnessContract`).

### Impact Explanation
This is an accounting/state-divergence bug, not a fund-theft bug — same severity class ("Medium", fairness/completeness) as the original report. The affected account's SR voting weight is understated relative to its actual frozen TRON Power after cancelling an unfreeze, which is unfair to the user and can also skew SR election totals if not corrected (votes recorded in `VotesStore`/`VotesCapsule` no longer reflect real held TRON Power until the user manually re-votes).

### Likelihood Explanation
Reachable by any unprivileged user via two standard, publicly available transactions: `UnfreezeBalanceV2Contract` (resource = TRON_POWER) followed by `CancelAllUnfreezeV2Contract` before the unfreeze delay expires, or the equivalent TVM opcodes/precompiles in a smart contract. No special permissions or trusted role required, and `supportAllowCancelAllUnfreezeV2()`/`supportUnfreezeDelay()` merely need to be enabled (which they are in production once activated by committee).

### Recommendation
When cancelling unfreeze for `TRON_POWER` in `CancelAllUnfreezeV2Actuator` (and the TVM `CancelAllUnfreezeV2Processor`), recompute/restore the account's vote allocation proportionally to the restored TRON Power balance, mirroring the proportional reduction logic in `UnfreezeBalanceV2Actuator.updateVote()`, so that vote weight tracks frozen TRON Power symmetrically on both freeze and unfreeze-cancel paths.

### Proof of Concept
1. Account freezes X TRX for `TRON_POWER` and votes for an SR with the full X-derived vote weight.
2. Account calls `UnfreezeBalanceV2` for a large portion of that TRON_POWER; `updateVote()` proportionally shrinks `votesList` to match reduced TRON Power (lines 340-387 of `UnfreezeBalanceV2Actuator.java`).
3. Before the unfreeze delay expires, account calls `CancelAllUnfreezeV2`; frozen TRON_POWER balance and total resource weight are restored to the pre-unfreeze value (lines 195-201 of `CancelAllUnfreezeV2Actuator.java`).
4. Query the account's `votesList` / `VotesStore` entry: it remains at the reduced value from step 2, even though `getTronPowerFrozenV2Balance()` is back to the original amount — demonstrating the unreimbursed "slash" in voting weight.

  public Map<String, Long> execute(CancelAllUnfreezeV2Param param, Repository repo) throws ContractExeException {
    Map<String, Long> result = new HashMap<>();
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    long withdrawExpireBalance = 0L;
    for (Protocol.Account.UnFreezeV2 unFreezeV2: ownerCapsule.getUnfrozenV2List()) {
      if (unFreezeV2.getUnfreezeExpireTime() > now) {
        String resourceName = unFreezeV2.getType().name();
        result.put(resourceName, result.getOrDefault(resourceName, 0L) + unFreezeV2.getUnfreezeAmount());

        updateFrozenInfoAndTotalResourceWeight(ownerCapsule, unFreezeV2, repo);
      } else {
        // withdraw
        withdrawExpireBalance += unFreezeV2.getUnfreezeAmount();
      }
    }
    if (withdrawExpireBalance > 0) {
      ownerCapsule.setBalance(ownerCapsule.getBalance() + withdrawExpireBalance);
    }
    ownerCapsule.clearUnfrozenV2();

    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);

    result.put(VMConstant.WITHDRAW_EXPIRE_BALANCE, withdrawExpireBalance);
    return result;
  }
