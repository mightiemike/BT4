This closely matches the report's bug class: a mechanism (here, `DelegateAction`/meta transactions) that permits an action to bypass a receiver-scoped safety check by validating against the wrong account identity, similar to `arbitraryCall()` failing to check `incentives[who]`. ### Title
Pre-fix `validate_delegate_action` checked `DeterministicStateInit` receiver against the wrong account id, allowing meta-transactions to bypass the deterministic-account receiver binding - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
Prior to protocol feature `FixDelegatedDeterministicStateInit`, `validate_delegate_action` validated an inner `Action::DeterministicStateInit` action against the outer transaction's `receiver` (the relayer-chosen account acting as the delegate's `sender_id`) instead of the `DelegateAction`'s own `receiver_id`, which is the account that the inner actions actually execute against on-chain. This is directly analogous to the C4 finding: a privileged/derived-permission call path (`arbitraryCall`) performing an action against an address without checking the specific invariant (`incentives[who] == 0`) that should scope what that call is allowed to touch — here, the invariant is "the `DeterministicStateInit` action's receiver must equal the deterministic id derived from its `state_init`" (see `validate_deterministic_state_init`, `runtime/runtime/src/action_validation.rs:497-533`), and the wrong id was checked at validation time.

### Finding Description
`validate_delegate_action` in `runtime/runtime/src/action_validation.rs` computes an `inner_receiver` used to validate all actions nested inside a `DelegateAction`/`DelegateV2`: [1](#0-0) 
Before the fix, `inner_receiver` was set to the *outer* transaction's `receiver` (the account the meta-transaction envelope targets, i.e. the delegate's `sender_id`) rather than `delegate_action.receiver_id()` (the true target the inner actions run against once the relayer's transaction is unpacked into a receipt on the sender's shard). Because `validate_deterministic_state_init` only checks that `derive_near_deterministic_account_id(&action.state_init) == receiver_id` passed to it: [2](#0-1) 
a crafted `DelegateAction` could set `receiver_id` to a different deterministic account (`det_account_a`) than the one implied by `sender_id`/the id the pre-fix code actually validated against (`det_account_b`, which matches `state_init_b`). Initial transaction validation used the wrong id (`det_account_b`, matching), so the transaction was admitted — even though the real receipt, once forwarded to `det_account_a`, would fail the exact same check again at receipt-validation time and be rejected as `InvalidDeterministicStateInitReceiver`.

The test `try_meta_tx_deterministic_receiver_exploit` in `test-loop-tests/src/tests/deterministic_account_id.rs` reproduces exactly this scenario and documents that pre-fix, the exploit transaction is admitted at tx-validation but rejected at receipt-validation: [3](#0-2) 

### Impact Explanation
This is the closest reachable analog to the report's bug class (a call path that fails to validate the correct target/invariant, opening a window for unauthorized state manipulation). However, unlike the C4 finding — where the missing check directly enables fund theft via `transferFrom` — nearcore's second-layer defense (`validate_receipt`/`ReceiptValidationError::ActionsValidation` at receipt processing, re-running `validate_deterministic_state_init` against the actual delegate `receiver_id`) prevents the exploit transaction from ever executing successfully in any protocol version, as the test explicitly asserts (`"In no protocol version can this ever be allowed to be executed successfully."`, `test-loop-tests/src/tests/deterministic_account_id.rs:235`). So while the pre-fix code path admitted a malformed transaction into a chunk (wasting the relayer's/network's transaction-admission slot), it did not result in unauthorized value movement, supply inflation, receipt loss/duplication, or state-root divergence: it fails deterministically and identically on all honest nodes at the receipt-validation stage.

### Likelihood Explanation
Not applicable as a live vulnerability: the fix is already gated by `ProtocolFeature::FixDelegatedDeterministicStateInit`, and `MIN_SUPPORTED_PROTOCOL_VERSION` in this codebase is at or above the fix's activation version per the protocol-model spec (`protocol-model/spec/accounts-keys.md`), meaning any currently running nearcore binary already validates delegate-action-nested `DeterministicStateInit` actions against the correct `delegate_action.receiver_id()`.

### Recommendation
No action required on the current codebase — the fix is already merged and protocol-gated. This is documented for completeness because it is the closest structural analog to the reported bug class in the current nearcore codebase. Recommend continued vigilance for any new action types nested inside `Action::Delegate`/`Action::DelegateV2` to ensure they are always validated against `delegate_action.receiver_id()` (not the outer transaction's `receiver`) in `validate_delegate_action`, and that any such invariant is double-checked at both transaction-admission and receipt-processing stages, as is currently done.

### Proof of Concept
See `try_meta_tx_deterministic_receiver_exploit` and its two callers `test_deterministic_state_init_meta_tx_receiver_check_pre_fix` / `test_deterministic_state_init_meta_tx_receiver_check` in `test-loop-tests/src/tests/deterministic_account_id.rs:136-262` [4](#0-3) , which construct a `DelegateAction` with `sender_id = det_account_b`, `receiver_id = det_account_a`, wrapping a `DeterministicStateInit` action carrying `state_init_b` (which derives to `det_account_b`, not `det_account_a`). On protocol versions before the fix, this transaction passes tx-validation (because validation incorrectly checked against `det_account_b`) but is rejected once unpacked as a receipt addressed to `det_account_a`, with `ActionErrorKind::NewReceiptValidationError(ReceiptValidationError::ActionsValidation(ActionsValidationError::InvalidDeterministicStateInitReceiver))`.

fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }
