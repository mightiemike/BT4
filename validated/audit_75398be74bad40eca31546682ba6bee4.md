## #Title
Shielded Transaction "Pause" Config (`allowShieldedTransactionApi`) Is Not Enforced on the Broadcast/Execution Path - (`framework/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
The node-level control flag `allowShieldedTransactionApi`, which is meant to let an administrator disable/pause shielded (zk-SNARK) transaction functionality on a node, is only checked in `Wallet`'s convenience/helper API methods and is never checked in the actual actuator that validates and executes broadcast `ShieldedTransferContract` transactions. This mirrors the reported `WithdrawQueue` bug class: a pause/administrative gate exists but is not wired into the real state-transition entry point, so it has no effect on the reachable, unprivileged path.

### Finding Description
`Wallet.checkAllowShieldedTransactionApi()` throws a `ZksnarkException` when `Args.getInstance().isAllowShieldedTransactionApi()` is false, and is invoked from wallet-side helper methods used to *build* shielded transactions/parameters (e.g. `createShieldedTransaction`, `createShieldedContractParameters`). [1](#0-0) [2](#0-1) 

However, the actual transaction processing path that validates and applies a `ShieldedTransferContract` — `ShieldedTransferActuator.validate()` — only checks the on-chain governance parameters `getAllowSameTokenName()` and `dynamicStore.supportShieldedTransaction()`; it never calls or checks `Args.getInstance().isAllowShieldedTransactionApi()`. [3](#0-2) 

This is confirmed directly by an existing regression test that documents the flag's scope is intentionally limited to the wallet API and does not affect actuator-level validation: [4](#0-3) 

The broadcast/network path (`TransactionsMsgHandler.handleTransaction` → `TronNetDelegate.pushTransaction` → `Manager.pushTransaction` → `processTransaction` → actuator dispatch) similarly only checks `supportShieldedTransaction()` chain parameter, not the node-local `allowShieldedTransactionApi` config: [5](#0-4) 

### Impact Explanation
An administrator who sets `allowShieldedTransactionApi=false` (e.g., to disable/pause shielded functionality on a node for security, privacy-compliance, or incident-response reasons) has no actual enforcement against shielded transactions reaching consensus-relevant state. Any user can craft a `ShieldedTransferContract` transaction externally (bypassing the gated `Wallet` helper methods entirely — no special privilege required) and broadcast it via the P2P transaction relay or the node's own broadcast RPC; it will still be fully validated and executed by `ShieldedTransferActuator`, updating `NullifierStore`, the Merkle tree, and `TotalShieldedPoolValue`. This defeats the intended administrative control and allows continued shielded pool state mutation on a node that was configured to disallow it.

### Likelihood Explanation
High for any user with the ability to submit a signed transaction over the P2P network or broadcast RPC — no privileged role, leaked key, or malicious peer/node capability is required. All that's needed is constructing a well-formed `ShieldedTransferContract` outside of the gated wallet convenience methods, which is straightforward since the flag is a purely client/API-side check.

### Recommendation
Enforce `Args.getInstance().isAllowShieldedTransactionApi()` (or an equivalent chain/node-level check) inside `ShieldedTransferActuator.validate()`/`execute()` (and the analogous ShieldedTRC20 actuators/paths) so that disabling the flag actually blocks shielded transaction processing, not just the wallet helper API surface — analogous to adding `whenNotPaused` to the reachable state-changing functions in the original finding.

### Proof of Concept
1. Node operator sets `node.zksnark.allowShieldedTransactionApi = false` intending to pause shielded transaction support on this node.
2. Attacker independently builds and signs a valid `ShieldedTransferContract` transaction (using the protobuf/zk-proof primitives directly, without calling the gated `Wallet.createShieldedTransaction`/`createShieldedContractParameters`).
3. Attacker broadcasts the transaction to the node via P2P (`TransactionsMsgHandler`) or the broadcast RPC.
4. `Manager.pushTransaction` → `processTransaction` dispatches to `ShieldedTransferActuator`, whose `validate()` only checks `supportShieldedTransaction()` (a chain-wide committee parameter) — the node-local `allowShieldedTransactionApi` flag is never consulted, so the transaction is accepted and processed as if the "pause" were never set, exactly as the test `shieldedTransferValidationWorksWhenApiDisabled` demonstrates.

  /**
   * Test that shielded transfer transaction validation works even when
   * allowShieldedTransactionApi is disabled. This verifies that the API flag
   * only gates wallet/helper APIs, not the core transaction validation logic.
   */
  @Test
  public void shieldedTransferValidationWorksWhenApiDisabled() {
    boolean orig = Args.getInstance().isAllowShieldedTransactionApi();
    // Disable the shielded API (this should NOT affect transaction validation)
    Args.getInstance().setAllowShieldedTransactionApi(false);

    dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
    dbManager.getDynamicPropertiesStore().saveTotalShieldedPoolValue(AMOUNT);

    try {
      ZenTransactionBuilder builder = new ZenTransactionBuilder(wallet);
      SpendingKey sk = SpendingKey.random();
      ExpandedSpendingKey expsk = sk.expandedSpendingKey();
      PaymentAddress address = sk.defaultAddress();
      Note note = new Note(address, AMOUNT);
      IncrementalMerkleVoucherContainer voucher = createSimpleMerkleVoucherContainer(note.cm());
      byte[] anchor = voucher.root().getContent().toByteArray();
      dbManager.getMerkleContainer()
          .putMerkleTreeIntoStore(anchor, voucher.getVoucherCapsule().getTree());
      builder.addSpend(expsk, note, anchor, voucher);

      addZeroValueOutputNote(builder);

      long fee = dbManager.getDynamicPropertiesStore().getShieldedTransactionCreateAccountFee();
      String addressNotExist =
          Wallet.getAddressPreFixString() + "8ba2aaae540c642e44e3bed5522c63bbc21f0000";

      builder.setTransparentOutput(ByteArray.fromHexString(addressNotExist), AMOUNT - fee);

      TransactionCapsule transactionCap = builder.build();
      Contract contract =
          transactionCap.getInstance().toBuilder().getRawDataBuilder().getContract(0);
      ShieldedTransferActuator actuator = new ShieldedTransferActuator();
      actuator.setChainBaseManager(dbManager.getChainBaseManager()).setContract(contract)
          .setTx(transactionCap);

      // Validation should succeed even when API is disabled
      actuator.validate();
    } catch (ContractValidateException e) {
      Assert.fail("Shielded transfer validation should not throw ContractValidateException: "
          + e.getMessage());
    } catch (Exception e) {
      Assert.fail("Shielded transfer should not throw Exception: " + e.getMessage());
    } finally {
      Args.getInstance().setAllowShieldedTransactionApi(orig);
    }
  }
