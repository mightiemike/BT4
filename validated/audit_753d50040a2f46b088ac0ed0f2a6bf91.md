I have sufficient evidence now to write the analog finding.### Title
Div-before-mul precision loss in legacy vote-reward calculation underpays voters - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a super representative's cycle reward using `double voteRate = (double) userVote / totalVote;` followed by `reward += voteRate * totalReward;` — a division performed before the multiplication, exactly matching the M-1 bug class described in the external report (`balance = elapsedTime_ * (RATE_DECIMALS_MULTIPLIER * tokenAmount_ / duration) / RATE_DECIMALS_MULTIPLIER` div-before-mul pattern).

### Finding Description
In the legacy (pre new-reward-algorithm) reward path, `computeReward(long cycle, List<Pair<byte[], Long>> votes)` divides first and multiplies second: [1](#0-0) 

This is called once per legacy cycle from `getOldReward`, which is invoked from the main `computeReward(beginCycle, endCycle, accountCapsule)` whenever `beginCycle < newAlgorithmCycle` (i.e. any cycle that occurred before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` was set for a network/account, or in tests/older chains where the new algorithm hasn't kicked in yet): [2](#0-1) [3](#0-2) 

Contrast this with the corrected/"new" algorithm used for post-effective-cycle rewards and in `VoteRewardUtil`/`RewardViCalService`, both of which correctly multiply the `BigInteger` delta before dividing: [4](#0-3) [5](#0-4) 

The legacy path in `computeReward(cycle, votes)` never received this fix: `userVote / totalVote` is computed as a `double` first (already lossy for large vote counts, since `double` only has 53 bits of mantissa precision, well below `long`'s 63-bit magnitude), and the result is then multiplied by `totalReward`, compounding the rounding error across every historical cycle a voter is owed rewards for. `MortgageService.payReward` similarly applies `(double) brokerage / 100` before multiplying by `value` for brokerage cuts, and `IncentiveManager.reward` and `MortgageService.payStandbyWitness` use the identical `voteCount * ((double) totalPay / voteSum)` div-before-mul pattern for standby-witness payouts: [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a real, on-chain token accounting bug: every legacy-cycle voting reward computed via `MortgageService.withdrawReward`/`queryReward` for unprivileged token holders who voted for witnesses is subject to systematic rounding-down precision loss, and it is compounded per cycle (summed in `getOldReward`'s loop over `for (long cycle = begin; cycle < end; cycle++)`). Because rewards are ultimately credited to `AccountCapsule.allowance` and withdrawn as TRX balance via `adjustAllowance`, this results in voters receiving slightly less TRX than the mathematically exact `userVote * totalReward / totalVote` would yield — an underpayment (loss of value) to unprivileged accounts across the whole network for the entire pre-new-algorithm period. This matches the "underpriced-public-work / accounting" impact class: value that should accrue to voters is instead lost to floating-point truncation.

### Likelihood Explanation
Likelihood is high for any account/network still on (or historically reliant on) the legacy reward path — i.e., before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`/`allowChangeDelegation`/`allowTvmVote` were enabled, or when `allowOldRewardOpt()` is not set (which routes to the exact `RewardViCalService.getNewRewardAlgorithmReward` `BigInteger` path instead). No privileged role or special conditions are required to trigger it — it fires automatically for every vote-reward computation that falls in the legacy cycle range, i.e., normal usage by ordinary voters.

### Recommendation
Change `computeReward(long cycle, List<Pair<byte[], Long>> votes)` in `MortgageService.java` to multiply before dividing, using `long`/`BigInteger` arithmetic instead of `double`, e.g.:
```java
long userVote = vote.getValue();
reward += userVote * totalReward / totalVote; // or BigInteger for overflow safety
```
Apply the analogous mul-before-div fix to `payReward`'s brokerage calculation and to `IncentiveManager.reward` / `MortgageService.payStandbyWitness`'s standby-pay calculation to eliminate the compounding floating-point truncation across all these reward-distribution paths.

### Proof of Concept
For a cycle with `totalReward = 100`, `totalVote = 3`, and a voter with `userVote = 1`:
- Buggy: `voteRate = (double)1/3 = 0.3333333333333333`; `reward = 0.3333333333333333 * 100 = 33.33333333333333` → truncated/accumulated as `long` add, losing the `0.333...` fractional TRX unit every such cycle.
- Correct: `1 * 100 / 3 = 33` computed exactly with integer truncation happening only once, matching the deterministic on-chain semantics expected for reward accounting rather than double-precision floating point rounding that can drift differently depending on operand magnitude. [8](#0-7)

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
