### Title
Missing self-address (current-contract) check on `redeem()`/`deposit()` recipient lets a user permanently strand their own redeemed funds - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The vault's `transfer()` function explicitly guards against sending zft tokens back to the vault contract itself with `(asserts! (not (is-eq current-contract to)) ERR-TOKENIZED-VAULT-PRECONDITIONS)`, but the equivalent `redeem()` (and `deposit()`) functions, which move the *underlying* asset, contain no analogous check on the `recipient` principal. This is the same bug class as the referenced Ion-Protocol report ("no 0-address check … can cause loss of funds for the user due to a typo/omission"): a missing validation on a value that determines where funds end up, in a single-transaction flow where the funds-losing mutation (burn) happens before the transfer that should deliver value to the user.

### Finding Description
In `redeem()` [1](#0-0) , the sequence is:
1. `ft-burn? zft amount account` — the user's shares are burned unconditionally.
2. `send-underlying inkind recipient` — underlying is sent to whatever `recipient` was supplied.

There is no check that `recipient` is not `current-contract` (the vault itself), unlike `transfer()` in the very same contract which does check this exact condition: [2](#0-1) .

If `recipient` is (accidentally, or via a caller/integration bug) set to `current-contract`, `send-underlying` moves the underlying asset from the vault's own balance back to the vault's own balance (a no-op from the vault's perspective) while the corresponding `assets` accounting is decremented via `(var-set assets (- current-assets inkind))`. The net effect: the user's shares are destroyed, the vault's tracked `assets` variable is reduced by `inkind`, but the actual underlying tokens never leave the vault to reach the user — they are absorbed into the vault's reserve for other depositors. This is a single-transaction, single-block flow: the burn (mutation) happens before the guard that should have prevented the loss even exists, and no later step re-validates that the destination differs from the vault. The same missing check applies to `deposit()`'s `recipient` parameter and to the `funds-receiver`/`receiver` default-fallback pattern used throughout `market.clar`'s `borrow()`, `repay()`, `collateral-remove()`, and `collateral-remove-redeem()` [3](#0-2) , none of which validate `funds-receiver`/`collateral-receiver` against `current-contract`.

Notably, the protocol authors were aware of this exact class of risk and did add a defensive check — but only in `flashloan()`, via `(asserts! (is-standard funds-receiver-resolved) ERR-INVALID-ADDRESS)` [4](#0-3) , and in `transfer()` via the `current-contract` equality check. This selective coverage — protecting the flashloan/transfer paths but not the deposit/redeem/borrow/collateral paths that also move value based on a caller-supplied recipient — is the structural gap.

### Impact Explanation
This lands on temporary/permanent freezing of user funds: the shares are irrevocably burned in the same transaction that fails to deliver the underlying to the intended recipient, and the underlying instead becomes indistinguishable vault reserve, unrecoverable by the specific redeeming user through any normal accounting path.

### Likelihood Explanation
This requires a caller (user or an integrating contract building the `redeem`/`deposit`/`borrow`/`collateral-remove-redeem` call) to supply `current-contract` (the vault or market address) as the recipient/receiver argument — e.g., via a copy-paste, a default fallback bug in an integration, or a chained-call bug analogous to the `collateral-remove-redeem` pattern that already deliberately sets `receiver` to `current-contract` for the intermediate step. Because the vault's own `transfer()` treats this exact condition as dangerous enough to explicitly guard against, the likelihood of a caller passing this value elsewhere is non-negligible, and the consequence (irreversible share burn without value delivery) is a direct, single-transaction fund loss.

### Recommendation
Add `(asserts! (not (is-eq current-contract recipient)) ERR-TOKENIZED-VAULT-PRECONDITIONS)` (and equivalently for `funds-receiver`/`collateral-receiver`) to `deposit()`, `redeem()` in every vault contract, and to `borrow()`, `repay()`, `collateral-remove()`, and `collateral-remove-redeem()` in `market.clar`, mirroring the guard already present in `transfer()` and the `is-standard` check already present in `flashloan()`.

### Proof of Concept
1. User (or an integrating contract) calls `vault-usdc.redeem(amount, min-out, .v0-vault-usdc)` — passing the vault's own contract principal as `recipient`.
2. `ft-burn? zft amount account` burns the user's shares [5](#0-4) .
3. `send-underlying inkind recipient` transfers `inkind` underlying tokens to `current-contract` itself — no external transfer of value occurs, funds simply remain vault-held.
4. `(var-set assets (- current-assets inkind))` reduces tracked total assets, but the underlying was never sent to the user.
5. Transaction succeeds (`ok inkind`); user's shares are gone, user received nothing — funds are permanently lost to that user and absorbed into the general vault pool.
