### Title
Missing cross-validation between the `shop` parameter and the signed session token's `dest`/`iss` claim in `tokenExchange()` - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`shopify.auth.tokenExchange()` accepts `shop` and `sessionToken` as two independent, separately-supplied parameters. It decodes the JWT `sessionToken` only to validate its signature/expiry, but discards the decoded payload and never checks that the untrusted `shop` argument matches the token's own `dest`/`iss` claim before using `shop` to build the OAuth token-exchange request URL and the resulting `Session.shop`.

### Finding Description
In `tokenExchange()`, the session token is decoded purely for validation side effects — the return value is never used: [1](#0-0) 

```
export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({shop, sessionToken, requestedTokenType, expiring}) => {
    await decodeSessionToken(config)(sessionToken);   // payload discarded
    ...
    const cleanShop = sanitizeShop(config)(shop, true)!;  // caller-supplied, unrelated to token
    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`, ...);
    ...
    return {session: createSession({..., shop: cleanShop, ...})};
```

`decodeSessionToken` only verifies the HMAC signature, expiry, and (optionally) the `aud` claim (API key) — it never asserts anything about which shop the token belongs to: [2](#0-1) 

Meanwhile, the library's own published usage pattern for this API takes `shop` straight from an unauthenticated, attacker-controllable request query parameter, entirely independent of the session token being sent: [3](#0-2) 

```
app.get('/auth', async (req, res) => {
  const shop = shopify.utils.sanitizeShop(req.query.shop, true);
  ...
  await shopify.auth.tokenExchange({sessionToken, shop, requestedTokenType, ...});
});
```

This is structurally identical to the Hook Protocol bug: a caller-supplied argument (`shop`, analogous to `optionInstrumentAddress`) is used for all security-relevant checks and requests, while the signed/verified data that should be authoritative (the JWT's `dest`/`iss`, analogous to `order.optionMarketAddress`) is verified for validity but never cross-checked against the untrusted argument.

Note that the library's own built-in callers (`performTokenExchange` in shopify-app-express, `TokenExchangeStrategy`/`createTokenExchangeStrategy` in shopify-app-remix/react-router) happen to derive `shop` from `payload.dest` before calling `tokenExchange()`, so they are not directly exploitable: [4](#0-3) 

However, `shopify.auth.tokenExchange` is a documented, directly-callable public API intended for non-Remix/custom integrations, and the shipped example explicitly sources `shop` from `req.query.shop` rather than from the token payload.

### Impact Explanation
Any app built following the documented pattern (or any caller that separately supplies `shop`) inherits a request-forging primitive: an attacker who holds a validly-signed session token for shop A can submit it alongside `shop=B` (an arbitrary or victim shop domain). The library will POST the token-exchange request to `https://B/admin/oauth/access_token` using shop A's token as the `subject_token`, and on any response will construct a `Session` object stamped with the attacker-chosen `shop: cleanShop` value rather than the shop the token was actually issued for. If the app then stores/keys that session by the attacker-supplied shop, this becomes a cross-tenant session storage corruption / session confusion primitive, independent of whatever validation Shopify's remote OAuth endpoint may or may not perform.

### Likelihood Explanation
Reachable by a single unauthenticated/anonymous request: the `shop` parameter is explicitly documented as coming from `req.query.shop`, and any authenticated merchant/user already possesses a valid session token for their own shop, which is all that's needed to construct the request pair. No privileged access or secret leakage is required — only following the documented public API exactly as shown.

### Recommendation
After calling `decodeSessionToken`, use its returned payload and assert that `shop` (post-sanitization) equals the hostname derived from `payload.dest` (and/or `payload.iss`) before using `shop` anywhere in the request URL or resulting `Session`. Reject the call (throw `InvalidJwtError`/`InvalidShopError`) on mismatch, mirroring the fix pattern from the reference report of always trusting the value embedded in the verified/signed artifact rather than a separately-supplied argument.

### Proof of Concept
1. Attacker installs/uses the app normally on `attacker-shop.myshopify.com`, obtaining a legitimately signed session token `T` (valid `aud`, valid signature, `dest = attacker-shop.myshopify.com`).
2. Attacker calls the app's `/auth` endpoint (or any endpoint invoking `shopify.auth.tokenExchange`) with `shop=victim-shop.myshopify.com&id_token=T` (matching the documented usage pattern in `docs/reference/auth/tokenExchange.md`).
3. `tokenExchange()` decodes `T` (passes signature/expiry checks — no shop comparison performed) and then issues `POST https://victim-shop.myshopify.com/admin/oauth/access_token` with `subject_token: T`.
4. Regardless of the remote response, `createSession` is invoked with `shop: 'victim-shop.myshopify.com'` (attacker-controlled), producing a `Session` object mismatched from the token's true origin, which the calling app may persist keyed by the attacker-supplied shop.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
