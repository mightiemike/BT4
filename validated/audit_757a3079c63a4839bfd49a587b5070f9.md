Based on my investigation, this proposal-activation flow is exactly the analogous pattern to the report: a permissionless, front-runnable "initialize"-style step that a witness-committee proposal triggers once, and that silently no-ops (causing a feature-level DoS) if the target storage slot/address is already occupied by attacker-controlled state placed there beforehand.

### Title
Permissionless pre-occupation of the TIP-2935 canonical address can permanently DoS `HistoryBlockHashUtil.deploy()` activation - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` is invoked exactly once, from `ProposalService.process()` when the `ALLOW_TVM_PRAGUE` proposal is approved by the witness committee [1](#0-0) . Before writing the TIP-2935 (`EIP-2935`) `BlockHashHistory` bytecode/account/contract metadata to the fixed address `HISTORY_STORAGE_ADDRESS`, it checks whether code or contract metadata already exists there, and if so it silently skips the entire deployment while still letting the `ALLOW_TVM_PRAGUE` flag commit [2](#0-1) . This mirrors the reported bug class: a launch-critical initialization step that can be pre-empted by any unprivileged actor before the "official" finalization transaction runs, permanently disabling the feature once the flag is flipped (since the proposal cannot be re-activated per the code comments) [3](#0-2) .

### Finding Description
`deploy()` gates on `manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS) || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)` [2](#0-1) . If true, it logs a warning and returns without writing the code, contract metadata, or setting the install marker, but `saveAllowTvmPrague(1)` is still committed by the caller regardless of the outcome of `deploy()` [1](#0-0) . Because proposal activation for a given `ProposalType` happens at most once (the code comment explicitly states "Proposal validation rejects re-activation, so this runs at most once per chain history"), any successful pre-occupation of the address permanently and silently disables the TIP-2935 feature network-wide with no way to retry.

The write-path is protected by an `isBlockHashHistoryInstalled()` marker set only at the tail of a successful `deploy()`, so a skipped deploy also means `write()` never populates historical block hashes at that address for the life of the chain [4](#0-3) .

The code authors are aware of one collision vector (an EOA sending TRX to the canonical address) and handle it gracefully by upgrading the account type in place rather than skipping [5](#0-4) . However, the *code*/*contract* collision branch is only defended by the argument that reaching it "requires a SHA-3 pre-image of the address," i.e., the authors assert it is computationally infeasible for an attacker to deploy a contract (via `CREATE`/`CREATE2`, whose target address is `keccak256(...)`-derived) that lands exactly on `HISTORY_STORAGE_ADDRESS = 410000f90827f1c53a10cb7a02335b175320002935` [6](#0-5) .

### Impact Explanation
If this precondition were violated — e.g., an implementation bug in a different chain fork/component that placed foreign code/contract metadata at that specific address by a non-brute-force path, or in a private/test network where the address space is smaller/more guessable — the `ALLOW_TVM_PRAGUE` proposal would activate on-chain while the associated TIP-2935 historical-block-hash service silently and permanently never gets deployed. This is a protocol-level feature DoS: nodes would report `ALLOW_TVM_PRAGUE` as active, but any downstream tooling/contract relying on `BlockHashHistory` at the canonical address would get wrong results (calls would hit "foreign" bytecode instead) with no chain-level signal that the intended deployment failed, since the only trace is a WARN log line.

### Likelihood Explanation
On TRON mainnet, exploiting this via `CREATE`/`CREATE2` requires finding transaction/salt/codehash inputs whose `keccak256` hash collides with a fixed 160-bit target address — a ~2^160 brute-force problem, correctly identified by the code's own comments as practically infeasible. I could not find any other unprivileged path (e.g., an RPC call, actuator, or TVM opcode) that lets a caller choose an exact target contract address. Given this, likelihood is very low on a live network; this is flagged primarily because the coded defense is explicitly probabilistic/"belt-and-braces" rather than deterministic, and the analog to the reported bug class (front-running of a one-shot, address-keyed initialization step causing silent DoS of the "launch/finalization" transaction) is structurally identical even though the concrete precondition (address preimage) is not practically reachable today.

### Recommendation
- Make the address-collision defense deterministic rather than probabilistic: rather than silently skipping and letting `saveAllowTvmPrague(1)` commit unconditionally, fail loudly (e.g., halt consensus-critical processing, or emit a hard error/metric that operators must act on) so an unintended collision cannot silently and permanently disable a hard-fork-defining feature.
- Consider decoupling the flag-flip from the deploy() outcome: only persist `saveAllowTvmPrague(1)` if `deploy()` reports success, or retry deployment on subsequent blocks rather than treating the "run at most once" proposal-activation event as the sole opportunity.
- Add an explicit alerting/metrics hook (beyond a WARN log) when the collision branch fires, since currently the only operator-visible signal is a log line that can go unnoticed in production.

### Proof of Concept
Not practically constructible today: reaching the vulnerable branch requires computing a `CREATE`/`CREATE2` input whose resulting contract address equals the hardcoded 21-byte `HISTORY_STORAGE_ADDRESS`, which is a `keccak256` preimage search over effectively the full 160-bit address space. The existing test `HistoryBlockHashIntegrationTest.writeIsNoOpOnForeignCode()` demonstrates the *code path* by directly seeding `CodeStore` with foreign bytecode at the canonical address (bypassing the preimage requirement, since it's a unit test using direct store access) and confirms `deploy()` skips and `write()` becomes a permanent no-op [7](#0-6)  — this test validates the mechanism but does not demonstrate that an unprivileged, real-world actor can trigger it outside of a preimage attack.

  public static void write(Manager manager, BlockCapsule block) {
    // Genesis has no parent; applyBlock never invokes this for block 0, but be
    // explicit so (0-1) % 8191 = -1 in Java can never corrupt a slot.
    if (block.getNum() <= 0) {
      return;
    }
    // Defense-in-depth: deploy() skips on foreign state at the canonical
    // address, but the proposal flag still commits. Gate on the install
    // marker (set at the tail of a successful deploy()) so write() can never
    // overwrite an unrelated contract's storage. Single store hit, cached.
    if (!manager.getDynamicPropertiesStore().isBlockHashHistoryInstalled()) {
      return;
    }
    long slot = (block.getNum() - 1) % HISTORY_SERVE_WINDOW;
    Storage storage = new Storage(HISTORY_STORAGE_ADDRESS, manager.getStorageRowStore());
    storage.put(new DataWord(slot), new DataWord(block.getParentHash().getBytes()));
    storage.commit();
  }
