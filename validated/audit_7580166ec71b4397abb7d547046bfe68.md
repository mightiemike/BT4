### Title
Permanent Denial-of-Service on `WalletContract`: `has_in_flight_tx` can be left stuck `true` when a callback depending on an external contract fails, permanently freezing the eth-implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` (the NEAR Wallet Contract that emulates Ethereum accounts) uses a single boolean flag, `has_in_flight_tx`, to serialize execution: it is set to `true` before any promise is dispatched and is only reset to `false` inside a subsequent, `#[private]` callback [1](#0-0) . The design explicitly documents the invariant that this flag must be `true` while any promise chain is outstanding and `false` otherwise [2](#0-1) . Just as Augur's `Market.disavowCrowdsourcers`/`migrateThroughOneFork` depend on an external, potentially-malicious `repBondOwner` contract accepting an ERC777 hook call in order to complete a required state transition, the wallet contract's unlock of `has_in_flight_tx` depends on a callback resolving cleanly after calling into an externally-specified, attacker-influenceable contract (an NEP-141 "token" `target` for `ERC20Transfer` emulation, or the address registrar) [3](#0-2) .

### Finding Description
`rlp_execute` refuses to process any further transaction while `has_in_flight_tx` is `true`, and it sets that flag to `true` right before dispatching a promise, without any other unlock mechanism (no timeout, no owner override) besides the corresponding callback finishing successfully [4](#0-3) . For the emulated ERC-20 path, the contract calls `storage_balance_of` on the user-specified `token_id` contract and chains `nep_141_storage_balance_callback` to react to that (attacker-influenceable) result [3](#0-2) . `has_in_flight_tx` is only reset to `false` as the very first statement of that private callback [5](#0-4) ; if that callback function itself aborts (panics, or is dropped due to gas exhaustion while processing the externally-controlled response) rather than returning normally, NEAR's per-receipt state-commit model means *no* state mutations from that receipt — including the reset of `has_in_flight_tx` — are persisted. Because the flag was already durably set to `true` in the prior receipt, the account is left permanently unable to process any further `rlp_execute` calls, since every future call is short-circuited at the top of `rlp_execute` [6](#0-5) .

This mirrors the reported bug class exactly: a state machine's "unlock" step is gated behind a call into a contract the caller does not control (an ERC777 recipient hook in Augur; an NEP-141-like token contract in the wallet contract), and if that external call's effects on the caller are adversarial or malformed, the unlock never happens and the resource (dispute bonds in Augur; the entire eth-emulated account in nearcore) is permanently frozen.

### Impact Explanation
If exploitable, this is a **permanently frozen funds / permanent denial-of-service** condition on an individual eth-implicit account: once `has_in_flight_tx` is stuck at `true`, the account can never again submit any RLP-encoded Ethereum transaction through `rlp_execute`, effectively bricking the account and any assets/authority it controls on NEAR. This matches the "permanently frozen funds" and "transaction-triggered halt" categories called out as acceptable impact for this analysis.

### Likelihood Explanation
The wallet contract's own comments show its authors are already aware that externally-specified token contracts can behave adversarially (e.g., the hard-coded `NEP_141_STORAGE_DEPOSIT_AMOUNT` specifically to defend against "malicious token contracts... taking lots of $NEAR from eth-wallet-contract users") [7](#0-6) , but there is no equivalent defense for a malicious/malformed response causing the callback itself to fail to complete. I was **not able to fully confirm** a concrete, exploitable panic/gas-exhaustion path in `nep_141_storage_balance_callback` in the time available: the callback's JSON-deserialization failure path is handled gracefully (returns an `ExecuteResponse` rather than panicking) [8](#0-7) , and the gas budget for the callback (`callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`) scales with gas the *user* specifies in their signed Ethereum transaction rather than gas the attacker controls [9](#0-8) , which reduces (but does not conclusively rule out) attacker control over whether the callback runs out of gas. A full confirmation would require tracing exactly how much gas remains available to the callback's own execution (as opposed to gas forwarded to further sub-promises) and whether any other panic path (e.g., huge externally-controlled response sizes, protocol-level return-value limits, or reentrancy through the `storage_deposit`/`ft_transfer` chained promises) can be triggered by a token contract the user is induced to interact with.

### Recommendation
- Do not gate the reset of a liveness-critical flag like `has_in_flight_tx` behind the *success* of a callback whose execution depends on data returned by an untrusted, externally-specified contract.
- Ensure `has_in_flight_tx` is reset (or an equivalent "abandon in-flight tx" recovery path exists) even when the callback panics or runs out of gas — e.g., via a separate guaranteed-to-run cleanup receipt, or a scheduled/self-callback with a fixed, generously-provisioned gas budget independent of `action.gas()`, decoupled from the actual token-contract response processing.
- Add an explicit size/complexity bound on any promise-result data from externally specified contracts before deserializing it, and audit every private callback in `wallet-contract/src/lib.rs` for panics reachable from attacker-controlled response bytes.

### Proof of Concept
Not concretely demonstrated due to inability to fully verify the exact gas/panic trigger in the callback within the available investigation. The structural PoC sketch is:
1. Wallet owner (or a relayer on their behalf) submits an RLP-encoded Ethereum transaction emulating an ERC-20 transfer where `target`/`token_id` is a NEP-141-like contract controlled by an attacker.
2. `rlp_execute` sets `has_in_flight_tx = true` and dispatches `storage_balance_of` to the attacker's contract, chained to `nep_141_storage_balance_callback` [3](#0-2) .
3. The attacker's contract returns a response engineered so that `nep_141_storage_balance_callback` fails to complete (panics/runs out of gas) instead of returning normally.
4. Because the receipt fails, `self.has_in_flight_tx = false` is never committed, so all subsequent `rlp_execute` calls immediately fail with "transaction already in progress" [6](#0-5) , permanently freezing the account.
