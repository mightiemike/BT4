### Title
Disk-exhaustion I/O error during account flush causes validator panic instead of graceful degradation - (File: `fs/src/file_io.rs`, `accounts-db/src/accounts_db.rs`)

### Finding Description
`write_buffer_to_file` loops calling `arch_write_at` (a thin wrapper around `File::write_at`/`seek_write`) and, if the underlying write syscall returns `Ok(0)` while there is still unwritten data, converts this into a hard `Err(io::ErrorKind::WriteZero.into())`: [1](#0-0) 
This is the low-level write primitive used by `AppendVec` to persist account bytes to its backing file, imported directly from `agave_fs::file_io` in `append_vec.rs`: [2](#0-1) 
The AppendVec write path (`append_ptr` → `append_ptrs_locked` → `append_accounts`/`write_accounts`) surfaces any I/O failure from `write_buffer_to_file` as a `None` return rather than propagating a recoverable `Result` up through `AccountsDb`. That `None` is then consumed in `write_accounts_to_storage`, which treats "no result" as an unrecoverable programming error and panics: [3](#0-2) 

Disk exhaustion (ENOSPC-class conditions) is a state that can, in principle, be driven entirely by ordinary paid account creation/resizing/rewriting — no privileged access, leader/gossip control, or config change is required, only sustained data volume. Once local disk space runs out, subsequent account cache flushes to `AppendVec` storage can fail at the raw `write_at`/`seek_write` layer, and if that manifests as a truncated (`Ok(0)`) write rather than a hard `Err(ENOSPC)`, `write_buffer_to_file` returns `WriteZero`, which unwinds to the `panic!` in `write_accounts_to_storage`. Even where the OS instead returns `Err(ENOSPC)` directly (propagated via the `?` in `write_buffer_to_file` line 107), the same "no graceful recovery path" problem exists: `AccountsDb`'s write path has no capacity-check/backpressure mechanism ahead of the flush that would prevent attempting a write once the disk is full, and no code path converts an I/O failure at this layer into anything other than a fatal panic.

### Impact Explanation
This maps to a validator panic/halt triggered by unrecoverable I/O handling of routine (not maliciously crafted) storage writes, once local disk capacity is exhausted. Because there is no capacitycheck or per-account storage-cost throttle at this layer that stops flushes from being attempted against a full disk, and no recovery/backoff logic for I/O failures during flush, a sustained, purely fee-paid campaign of account creation/growth that fills the validator's disk can end in a hard process panic rather than a controlled failure mode (e.g., halting new writes, rejecting further account growth, or backpressuring). This is a node-availability (panic/halt) concern rather than a consensus-safety or balance-integrity issue.

### Likelihood Explanation
The precondition — filling a validator's disk via legitimate, paid account writes — is expensive (each byte of account data requires rent-exempt lamports) and would require sustained, high-volume usage over an extended period, and disk sizing/monitoring is normally an operator responsibility. However, this is exactly the class of "resource-cost invariant is proportional but I/O error handling isn't graceful" issue the question targets: nothing in `write_buffer_to_file`, `append_ptr`/`append_ptrs_locked`, or `write_accounts_to_storage` distinguishes a transient/temporary write shortfall from actual disk-full, and both are converted to an unconditional panic. The likelihood of naturally triggering `WriteZero` specifically (as opposed to a direct `Err(ENOSPC)`) is low and platform-dependent, but the broader gap — no graceful degradation anywhere along `AppendVec::write_accounts` → `write_accounts_to_storage` for I/O failures during flush — is real and independently reachable.

### Recommendation
- Do not `panic!` on `write_accounts` returning `None`/an I/O error in `write_accounts_to_storage`; propagate a proper `Result` from `AppendVec::append_accounts`/`write_accounts` up through `AccountsFile`/`AccountsDb` so I/O failures (disk full, EIO, etc.) can be handled — e.g., halt new account ingestion, surface a clear operator-facing error, or attempt allocation of a new storage location, rather than crashing the process.
- Add a pre-flush disk-space/capacity check (or monitor free space and reject/backpressure account growth) before attempting to extend/write `AppendVec` files, so that disk exhaustion is detected before hitting the raw write syscall.
- Ensure `write_buffer_to_file`'s `WriteZero` case is treated identically to other I/O errors and reaches the same graceful-error path.

### Proof of Concept

2. Drive `AccountsDb::write_accounts_to_storage` (or the public `AccountsDb::store`/`flush` API) with a stream of small `AccountSharedData` entries with distinct pubkeys until the injected write budget is exceeded.
3. Assert that the call returns an `Err`/does not panic, and that `AccountsDb` remains in a consistent, queryable state (e.g., accounts written before the failure point remain loadable, and no partial/corrupted `AppendVec` entries are indexed).

```rust
pub fn write_buffer_to_file(
    file: &File,
    mut buffer: &[u8],
    mut offset: FileSize,
) -> io::Result<()> {
    while !buffer.is_empty() {
        let wrote_len = arch_write_at(file, buffer, offset)?;
        if wrote_len == 0 {
            return Err(io::ErrorKind::WriteZero.into());
        }
        buffer = &buffer[wrote_len..];
        offset += wrote_len as FileSize;
    }
    Ok(())
}
```
