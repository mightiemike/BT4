### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay/verify tooling accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the equality-check invariant that binds a locally-produced execution result to the authenticated `TransactionInfo` (the leaf committed into the transaction accumulator and returned in proofs). It explicitly checks status, gas, write-set hash (`state_change_hash`) and event root, but by its own documented `TODO(trading-native)` comment it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash` against the target `TransactionInfo`. It never compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against anything computed locally, as the code itself acknowledges: [2](#0-1)  — "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

This function is used as the correctness gate in the chunk executor's replay/verify path (`execution/executor/src/chunk_executor/mod.rs`) and in debugger/CLI replay tooling (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`), all of which rely on it to detect state divergence between locally computed execution output and the trusted, proof-bound `TransactionInfo`. `TransactionInfoV1` was recently extended with `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` fields ( [3](#0-2) ) specifically to authenticate additional pieces of ledger state (hot-state root and the new "position" state checkpoint tied to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), yet the verification routine was not updated to check them.

### Impact Explanation
Because the checkpoint hashes are part of the value committed into the transaction accumulator and returned to light clients / verifiers as an authenticated proof of ledger state, skipping their comparison means the "state-integrity gate" (VM output vs. committed `TransactionInfo`) can pass even when the locally computed state/hot-state/position checkpoint root differs from the one bound in the accumulator. This directly matches the required impact category: "Committed state that differs from the correct VM result" being accepted as consistent, and "Authenticated API or state-view output bound to the wrong version, object, or proof context" for restore/replay flows relying on this check. On mainnet, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or hot-state) is enabled, this creates a real risk that state divergence introduced during chunk-executor replay, restore, or debugger-driven replay would go undetected, since the one function whose entire purpose is to catch such divergence silently ignores exactly the fields meant to detect it.

### Likelihood Explanation
Medium. The code is currently gated: the TODO says this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the feature flag is not yet active in production, which limits current exploitability. However, the gap is unconditional in the code path (it applies to every call of `ensure_match_transaction_info`, including hot-state checkpoints which may already be relevant), and the bug is self-acknowledged as a known, unresolved correctness hole in the committed code rather than a hypothetical — meaning any node/tooling relying on this comparator for replay-verify correctness is exposed today for hot-state, and will be exposed for position-state as soon as the feature flag is turned on.

### Recommendation
Extend `ensure_match_transaction_info` to compute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding locally-computed values before returning `Ok(())`, mirroring the pattern already used for `state_change_hash` and `event_root_hash`. This should be completed and enabled prior to (or gated alongside) turning on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Local repo evidence: 
1. `TransactionInfoV1` carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` fields intended to authenticate additional state roots: [3](#0-2) .
2. `ensure_match_transaction_info`, the sole correctness check tying computed `TransactionOutput` to the trusted `TransactionInfo`, checks only status/gas/write-set-hash/event-root and explicitly does not check the three checkpoint hashes, as documented in its own trailing comment: [2](#0-1) .
3. This function is invoked from the chunk executor's replay path (`execution/executor/src/chunk_executor/mod.rs`) and debugger/CLI replay tools, both of which use it as their state-integrity gate, so a divergent state/hot-state/position checkpoint hash would not surface as a mismatch through this API.

Note: I could not fully trace how/where `state_checkpoint_hash` divergence might already be caught elsewhere in the executor pipeline (e.g., possibly checked separately during `execution_output`/`state_checkpoint_output` construction) due to index/tool limits; if such a check exists independently, it would reduce (but not eliminate, given hot-state and position-state are unchecked) the severity of this specific comparator's gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
