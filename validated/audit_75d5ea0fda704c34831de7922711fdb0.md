### Title
`validate_shadow_parent_burnchain` short-circuits to `Ok(())` when the shadow parent header is not yet locally staged, allowing a malformed block-commit pointer to be accepted on lagging nodes - (File: `stackslib/src/chainstate/nakamoto/shadow.rs`)

### Summary
`NakamotoChainState::validate_shadow_parent_burnchain` only enforces the block-commit `parent_vtxindex == 0` / `parent_block_ptr == shadow_tenure_sortition_height` invariant when the local `staging_db` already has the shadow parent's `NakamotoBlockHeader` cached [1](#0-0) . On a node that has not yet received/staged the shadow parent, the lookup returns `None` and the function returns `Ok(())` immediately, bypassing the block-commit consistency check entirely [2](#0-1) .

### Finding Description
The broken equality is: **verdict(`validate_shadow_parent_burnchain`, node with shadow parent header staged) == verdict(same function, node without shadow parent header staged)**, for the identical `(block, block_commit)` pair.

The code path is:
```
staging_db.get_nakamoto_block_header(&block.header.parent_block_id) -> None
=> return Ok(())
```
versus, on a node that already has the header:
```
=> parent_header.is_shadow_block() == true
=> enforce block_commit.parent_vtxindex == 0
=> enforce block_commit.parent_block_ptr == parent_sn.block_height
``` [3](#0-2) 

The root cause is that this validation is order-dependent on local relay/staging state rather than being a pure function of consensus-visible inputs (the block, the block-commit, and burnchain/sortition data, all of which are globally available). Because shadow tenures are inserted directly into the staging DB via a schema/consensus upgrade rather than being relayed over the p2p network [4](#0-3) , there is a real window during which some nodes have already applied the shadow tenure while others have not yet done so.

An attacker with a single miner slot can construct a normal (non-shadow) `NakamotoBlock` whose `parent_block_id` references the shadow block, together with a `LeaderBlockCommitOp` whose `parent_vtxindex` is nonzero or whose `parent_block_ptr` does not match the shadow tenure's sortition height. On any node that has not yet locally staged the shadow parent's header, this malformed pointer passes silently. Once such a block is accepted into staging (as "valid" per this check) it is a candidate for later processing/append into that node's canonical chain, while a node that already has the shadow header would reject the same block at the same call site.

Existing guards elsewhere (`check_tenure_tx`, `common_validate_against_burnchain`, `validate_nakamoto_block_static`, `validate_nakamoto_tenure_snapshot`) do not check the block-commit's `parent_vtxindex`/`parent_block_ptr` against the shadow-tenure sortition height — that is exactly the job delegated to `validate_shadow_parent_burnchain`, so none of them close this gap.

### Impact Explanation
If a node with a missing shadow-parent header accepts and later processes this block into its chainstate while a node that already had the shadow header rejects it outright, the two nodes' canonical tips diverge — a chain split/fork, which falls in the Critical category ("an invalid block accepted... network-wide", here materializing as inconsistent acceptance across honest nodes depending on relay/sync timing of the shadow tenure). The affected nodes are any nodes that lag in receiving/applying the emergency shadow-tenure upgrade relative to others — a normal and expected condition during a chain-halt recovery rollout, not a contrived edge case.

### Likelihood Explanation
This requires: (1) a shadow tenure having been introduced via a SIP/consensus upgrade (an operational precondition, not attacker-controlled, but a real historical/expected occurrence per this module's stated purpose), and (2) some nodes not yet having ingested that shadow block when the attacker's malicious child block/commit propagates. The attacker only needs to win a single sortition slot (a minority position, consistent with the allowed attacker model) to submit a block-commit with a bad `parent_vtxindex`/`parent_block_ptr`, and produce a normal block pointing at the shadow block as parent. This is fully repeatable during any future shadow-tenure rollout window.

### Recommendation
Do not short-circuit to `Ok(())` when the parent header is missing from `staging_db`. Instead, either (a) defer acceptance of the child block until the parent header is available and re-run the full validation once it is, or (b) resolve the shadow-parent tenure via `SortitionDB`/burnchain-independent lookup (rather than relying on locally staged headers) so the check is deterministic regardless of local relay ordering, and re-validate this specific invariant at block-processing/append time, not only once at initial accept time.

### Proof of Concept
Rust integration test plan (two-node harness):
1. Set up two nodes, A and B, sharing the same sortition/burnchain view.
2. Apply the shadow tenure/shadow block schema update to node A only; delay relay to node B.
3. Craft a normal `NakamotoBlock` with `parent_block_id` = shadow block's id, and a `LeaderBlockCommitOp` with `parent_vtxindex != 0` (or `parent_block_ptr` mismatched to the shadow tenure's sortition height).
4. Call `NakamotoChainState::validate_shadow_parent_burnchain` (via `accept_block`) on node A: assert `Err(ChainstateError::InvalidStacksBlock(_))`.
5. Call the same function on node B (which lacks the shadow header): assert `Ok(())`.
6. Assert these two results differ for byte-identical inputs — proving the equality is broken.
7. Relay the shadow block to node B afterward, and process/append node B's staged (already "accepted") malicious block; assert node B's canonical tip now differs from node A's, demonstrating a fork.

    pub(crate) fn validate_shadow_parent_burnchain(
        staging_db: NakamotoStagingBlocksConnRef,
        db_handle: &SortitionHandleConn,
        block: &NakamotoBlock,
        block_commit: &LeaderBlockCommitOp,
    ) -> Result<(), ChainstateError> {
        // only applies if the parent is a nakamoto block (since all shadow blocks are nakamoto
        // blocks)
        let Some(parent_header) =
            staging_db.get_nakamoto_block_header(&block.header.parent_block_id)?
        else {
            return Ok(());
        };

        if !parent_header.is_shadow_block() {
            return Ok(());
        }

        if block_commit.parent_vtxindex != 0 {
            warn!("Invalid Nakamoto block: parent {} of {} is a shadow block but block-commit vtxindex is {}", &parent_header.block_id(), &block.block_id(), block_commit.parent_vtxindex);
            return Err(ChainstateError::InvalidStacksBlock("Invalid Nakamoto block: invalid block-commit parent vtxindex for parent shadow block".into()));
        }
        let Some(parent_sn) =
            SortitionDB::get_block_snapshot_consensus(db_handle, &parent_header.consensus_hash)?
        else {
            warn!(
                "Invalid Nakamoto block: No sortition for parent shadow block {}",
                &block.header.parent_block_id
            );
            return Err(ChainstateError::InvalidStacksBlock(
                "Invalid Nakamoto block: parent shadow block has no sortition".into(),
            ));
        };
        if u64::from(block_commit.parent_block_ptr) != parent_sn.block_height {
            warn!("Invalid Nakamoto block: parent {} of {} is a shadow block but block-commit parent ptr is {}", &parent_header.block_id(), &block.block_id(), block_commit.parent_block_ptr);
            return Err(ChainstateError::InvalidStacksBlock("Invalid Nakamoto block: invalid block-commit parent block ptr for parent shadow block".into()));
        }
