### Title
Unchecked subtraction in snapshot storage-length calculation can underflow `accounts_current_len` - ([File: runtime/src/serde_snapshot/storage.rs])

### Summary
This is the accounts-lattice/snapshot-generation analog of the reported "`params.path` length not checked → underflow" bug class. Instead of a router path array, the unvalidated quantity here is the storage's *obsolete-byte total*, which is subtracted directly from the storage's total byte length when building the serialized snapshot record for an `AccountStorageEntry`, without any bounds check or `checked_sub`.

### Finding Description
`SerializableAccountStorageEntry::new()` computes the persisted length of an account storage file as a raw, non-checked subtraction: [1](#0-0) 

```rust
pub fn new(
    accounts: &AccountStorageEntry,
    snapshot_slot: Slot,
) -> SerializableAccountStorageEntry {
    SerializableAccountStorageEntry {
        id: accounts.id() as SerializedAccountsFileId,
        accounts_current_len: accounts.accounts.len()
            - accounts.get_obsolete_bytes(Some(snapshot_slot)),
    }
}
```

`get_obsolete_bytes()` sums, over every entry currently recorded in `ObsoleteAccounts`, `min(stored_size(data_len), accounts.len() - offset)` for each obsolete offset: [2](#0-1) 

This sum is only guaranteed to stay `<= accounts.len()` if every offset in the `ObsoleteAccounts` list is unique and the byte ranges they cover never overlap or get double-recorded. `mark_accounts_obsolete()` itself performs no deduplication — it unconditionally appends whatever `(offset, data_len)` pairs it is given to the `Vec<ObsoleteAccountItem>`: [3](#0-2) 

The same unchecked-subtraction pattern also appears in the read-path used to build snapshot archives, `AccountStorageReader::new()`: [4](#0-3) 

```rust
let num_total_bytes = storage.accounts.len();
let mut num_alive_bytes = num_total_bytes - storage.get_obsolete_bytes(snapshot_slot);
...
num_alive_bytes -= tombstone_offsets.len() * tombstone_stored_size;
```

Both of these call sites trust that `get_obsolete_bytes()` (and, separately, tombstone-offset accounting) can never exceed `accounts.len()`, and neither uses `saturating_sub`/`checked_sub` to defend against the invariant being violated. If an account's offset is ever recorded as obsolete more than once (e.g., once via `clean_accounts_older_than_root`/`handle_reclaims` and again via a later reclaim, ancient-append-vec combination, or startup obsolete-account marking path such as `mark_obsolete_accounts_at_startup`), the summed obsolete bytes can exceed the storage's total length, and the subtraction underflows a `usize`.

### Impact Explanation
An underflowed `accounts_current_len`/`num_alive_bytes` wraps to a huge `usize` value in release builds (subtraction is not checked/wrapping-safe here) or panics in debug builds. A huge bogus length written into the bank snapshot (`SerializableAccountStorageEntry`) or used to size a read of the account storage file would cause: (1) a validator panic when it later tries to size or read that many bytes from a much smaller file, or (2) a corrupted/incorrect account storage length persisted into the snapshot, producing a stale/incorrect account-storage view on reload — i.e., a snapshot-vs-replay mismatch or node crash on startup from the snapshot. This maps to the in-scope categories of "node panic" and "honest-node snapshot-vs-replay mismatch."

### Likelihood Explanation
The bug requires the same storage offset to be marked obsolete more than once (or tombstone bytes to be double counted against alive bytes), which the code comments elsewhere in this file explicitly acknowledge as a *possible* scenario for the related `zero_lamport_single_ref_offsets` tracking ("If this happens, we will count this account as 'dead' twice... it just makes shrink more likely to visit this storage" — accounts-db/src/account_storage_entry.rs:39-45), showing that double-accounting races between concurrent clean/shrink/reclaim operations are a known possibility in this subsystem. `ObsoleteAccounts::mark_accounts_obsolete` performs no deduplication check, so nothing at that layer prevents the same offset being appended twice if callers ever race or re-mark. This makes the underflow reachable through honest-node operation (clean, shrink, ancient-append-vec combination, and startup obsolete marking all call into this same accounting), not merely from malicious/crafted input.

### Recommendation
Replace the raw subtractions with `checked_sub`/`saturating_sub`, and add an assertion/invariant check (in debug builds at least) that `get_obsolete_bytes(..) <= accounts.len()` and that tombstone/obsolete byte totals never double-count the same offset (e.g., dedupe in `mark_accounts_obsolete`, or track a `HashSet`/`IntSet` of already-marked offsets before appending).

### Proof of Concept
Not applicable — this analysis is a static-analysis-based finding derived from tracing the unchecked-subtraction pattern from `AccountStorageEntry::get_obsolete_bytes()` through `SerializableAccountStorageEntry::new()` and `AccountStorageReader::new()`; no live double-marking trigger sequence has been demonstrated on this codebase and would require targeted testing of the clean/shrink/ancient-append-vec concurrency paths to confirm reachability of the double-count precondition.

impl ObsoleteAccounts {
    /// Marks the accounts at the given offsets as obsolete
    pub fn mark_accounts_obsolete(
        &mut self,
        newly_obsolete_accounts: impl ExactSizeIterator<Item = (Offset, usize)>,
        slot: Slot,
    ) {
        self.accounts.reserve(newly_obsolete_accounts.len());

        for (offset, data_len) in newly_obsolete_accounts {
            self.accounts.push(ObsoleteAccountItem {
                offset,
                data_len,
