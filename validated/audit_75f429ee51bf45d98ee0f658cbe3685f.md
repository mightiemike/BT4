### Title
`allowHardenExchangeCalculation` governance flag introduces checked/exact arithmetic into Bancor exchange math, causing legitimate `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` operations to revert on overflow/underflow that the unchecked legacy path tolerated - ([File: actuator/src/main/java/org/tron/core/actuator/AbstractExchangeActuator.java])

### Summary
The external report describes Uniswap-v3-style code that switched from wraparound (unchecked) long-arithmetic — which the protocol design implicitly relies on for correctness — to checked arithmetic that reverts (`Error::FeeGrowthSubTick`) on overflow/underflow, breaking invariant assumptions and causing legitimate operations (fee accounting, withdrawals) to permanently fail. Java-tron's exchange subsystem contains a structurally analogous pattern: `ExchangeCapsule.transaction()` and the `ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` flows can operate in two arithmetic modes controlled by the `allowHardenExchangeCalculation` dynamic property/proposal — a legacy unchecked-`long` mode (`x + y`, `x - y`, silently wraps on over/underflow) and a "hardened" mode using `StrictMathWrapper.addExact/subtractExact` (checked math that throws `ArithmeticException`, converted into `ContractValidateException`/`ContractExeException`, aborting the transaction).

### Finding Description
`AbstractExchangeActuator` exposes `subtractExact`/`addExact` helpers that conditionally delegate to `StrictMathWrapper` (checked) or plain `long` arithmetic (unchecked, silently wraps) based on `allowHardenExchangeCalculation()`: [1](#0-0) 

`ExchangeCapsule.transaction()` similarly branches between legacy plain-`long` balance updates and `hardenedCalc` mode using `StrictMathWrapper.addExact/subtractExact`, throwing `ContractValidateException` when checked math detects overflow or a resulting negative balance: [2](#0-1) 

`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeCreateActuator` all use `subtractExact`/`addExact` (which are checked when hardening is enabled) for balance and pool-liquidity bookkeeping, catching `ArithmeticException` and converting it into a hard failure of the whole transaction: [3](#0-2) [4](#0-3) 

The `SafeExchangeProcessor` — the alternate hardened Bancor pricing engine — likewise uses `StrictMathWrapper.addExact` inside `exchangeToSupply`, so any pool where `balance + quant` exceeds `Long.MAX_VALUE`, or where the supply/balance ratio produces an intermediate division-by-zero (as directly demonstrated by the repository's own test `testSafeProcessorDivByZeroThrows`), throws instead of degrading gracefully: [5](#0-4) 

Exactly like the Uniswap v3 fee-growth accumulator bug class, this "hardening" swaps an unchecked/wrap-tolerant arithmetic model for a checked one without re-validating that all legitimate operational states remain overflow/underflow-free under checked semantics. Existing repo tests already demonstrate the failure mode is reachable and revert-inducing: [6](#0-5) [7](#0-6) 

### Impact Explanation
When `allowHardenExchangeCalculation` is enabled via governance proposal (`ProposalUtil.java`, `ProposalService.java`), any TRX-pair exchange pool whose balances approach `Long.MAX_VALUE`, or whose Bancor pricing intermediate values hit degenerate ratios, will cause `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract` transactions to unconditionally revert via `ArithmeticException` → `ContractExeException`/`ContractValidateException`, rather than gracefully handling the edge case. This can render funds/liquidity in an exchange pool permanently inaccessible for withdrawal/trading once such a state is reached — the same "operations revert unexpectedly, effectively locking funds" outcome the source report flags as high severity. This is reachable purely through broadcast transactions (`ExchangeInject`, `ExchangeWithdraw`, `ExchangeTransaction`) once the network-wide governance flag is on; no privileged actor is required to trigger it once the flag is active.

### Likelihood Explanation
Likelihood depends on the `allowHardenExchangeCalculation` dynamic property being enabled network-wide via the standard proposal/committee-approval mechanism (`ProposalUtil`), and on an exchange pool balance approaching overflow thresholds or hitting a degenerate Bancor ratio — both are governance/operational conditions rather than exploits requiring privileged access once enabled. This is lower likelihood than the Uniswap case (which triggers routinely in normal low-fee pools) because java-tron's `long` overflow threshold (`2^63`) is far from typical pool sizes, but the `-1` balance / division-by-zero edge case demonstrated by `testSafeProcessorDivByZeroThrows` shows a reachable, non-overflow-related revert path with much smaller preconditions.

### Recommendation
Before/if enabling `allowHardenExchangeCalculation` in production, formally verify that all reachable pool states (including adversarially injected/withdrawn balances) cannot produce an `ArithmeticException` in `StrictMathWrapper.addExact/subtractExact` or `SafeExchangeProcessor`'s BigDecimal division; add explicit bounds/pre-checks in `ExchangeCapsule.transaction`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` that reject or clamp inputs before invoking checked arithmetic, so that failure modes are validated (rejected at validate-time) rather than surfaced as execution-time reverts that can strand liquidity.

### Proof of Concept [8](#0-7) 
The repository's own `testSafeProcessorDivByZeroThrows` and `testSafeProcessorAddExactOverflowThrows` tests confirm that `SafeExchangeProcessor.exchange` throws `ArithmeticException` for a corrupted/edge balance (`-1L`) and for `Long.MAX_VALUE` balances respectively — demonstrating the checked-math path fails hard exactly where the unchecked legacy path would have silently wrapped/continued, matching the reported bug class.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);

  public void hardenedAddExactOverflowThrows() throws Exception {
    dbManager.getDynamicPropertiesStore().saveAllowSameTokenName(1);
    dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);

    // Corrupt pool balance to near-MAX so addExact overflows on inject.

    ExchangeCapsule pool = dbManager.getExchangeV2Store().get(ByteArray.fromLong(exchangeId));
    pool.setBalance(Long.MAX_VALUE - 10L, 200000000L);
    dbManager.getExchangeV2Store().put(pool.createDbKey(), pool);

    String firstTokenId = "123";
    AssetIssueCapsule a1 = new AssetIssueCapsule(
        AssetIssueContract.newBuilder()
            .setName(ByteString.copyFrom(firstTokenId.getBytes())).build());
    a1.setId(String.valueOf(1L));
    dbManager.getAssetIssueStore().put(a1.getName().toByteArray(), a1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(firstTokenId.getBytes(), 1000000000L,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    accountCapsule.setBalance(10000_000000L);
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);

    ExchangeInjectActuator actuator = new ExchangeInjectActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, exchangeId, firstTokenId, 1000000000L));
    try {
      Assert.assertThrows(ContractExeException.class,
          () -> actuator.execute(new TransactionResultCapsule()));
    } finally {
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(2L));
      dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    }
  }
