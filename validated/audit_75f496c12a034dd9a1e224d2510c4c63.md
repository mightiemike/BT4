### Title
Vote account authorized withdrawer can front-run reward distribution by instantly setting commission to 100% via `UpdateCommissionBps` - (File: programs/vote/src/vote_state/mod.rs)

### Summary
The vote program's `UpdateCommission` instruction enforces a "commission rug" protection rule: an increase is only allowed in the first half of an epoch, and even then, inflation-reward calculation additionally uses a state snapshot delayed by a full epoch to blunt any last-minute change. [1](#0-0) [2](#0-1)  The newer `UpdateCommissionBps` instruction (SIMD-0291/SIMD-0249), however, explicitly removes this rule for both the inflation-rewards commission and the block-revenue commission fields, allowing the authorized withdrawer to set the commission to its maximum value (100%) at any time, immediately before a reward/commission distribution event, mirroring the "owner sets fee to 100% and front-runs a payout" pattern from the report. [3](#0-2) 

### Finding Description
`update_commission` (the legacy, percentage-based instruction) computes `enforce_commission_update_rule` and rejects commission increases outside the allowed window via `is_commission_update_allowed`/`CommissionUpdateTooLate`: [1](#0-0) 

This rule exists specifically to stop "last minute commission rugs", as documented directly in the reward-calculation code, which additionally snapshots vote-account commission state from a full epoch earlier before using it to compute payouts: [2](#0-1) 

In contrast, `update_commission_bps`, dispatched from `VoteInstruction::UpdateCommissionBps` in `vote_processor.rs`, has no such rule — the comment explicitly states "No commission update rule, per SIMD-0249 and SIMD-0291" — and lets the authorized withdrawer set either `inflation_rewards_commission_bps` or `block_revenue_commission_bps` to any value (including the max, 10000 bps = 100%) at any slot with no epoch-window or cooldown restriction: [3](#0-2) 

This is a functional analog to the reported `DropEngineV2.setPrimarySaleFeeBps` bug: a privileged authority (contract owner ↔ vote account's authorized withdrawer) can change a fee/commission variable instantaneously and use that change to intercept value that should have gone to a third party (revenue recipient ↔ delegators/stakers) at the moment of payout (`configureSequence` mint payment ↔ block revenue / inflation reward distribution). For `BlockRevenue` commission specifically, distribution happens continuously (per SIMD-0123 delegator-reward deposits), so there is no analogous epoch-delay safety net protecting stakers the way `delay_commission_updates`/`CachedVoteAccounts` protects inflation rewards; the withdrawer can flip `block_revenue_commission_bps` to 10000 immediately before rewards accrue to the vote account and reclaim funds that would otherwise flow to delegators.

### Impact Explanation
If exploited, a malicious or compromised vote-account authorized withdrawer can capture up to 100% of the delegator-owed block revenue or inflation rewards for a given period by front-running the distribution with an `UpdateCommissionBps` instruction, at the direct expense of stakers/delegators — a concrete lamport-value theft/redirection at the validator layer.

### Likelihood Explanation
Low to moderate: it requires control of the vote account's authorized withdrawer key (a privileged, but not consensus-trusted, actor), analogous to the "malicious/compromised owner" precondition in the original report. No special network position or consensus-level access is required — only a signed `UpdateCommissionBps` transaction sent by the authorized withdrawer at an opportune slot.

### Recommendation
Reinstate an update-window/cooldown restriction (equivalent to `is_commission_update_allowed`) for `update_commission_bps`, especially for `block_revenue_commission_bps` given the lack of any epoch-delay protection at distribution time, and/or apply a delayed-snapshot read (as already done for inflation-reward commission via `CachedVoteAccounts`) when computing block revenue commission cuts, so a commission increase cannot be applied to rewards that have already accrued or are about to be distributed within the same slot/epoch.

### Proof of Concept
1. A delegator's stake is earning block revenue for a vote account whose `block_revenue_commission_bps` is currently low (e.g., 0–500 bps).
2. Immediately before the leader schedule processes `deposit_delegator_rewards` for that vote account's pending block revenue, the authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }`.
3. Because `update_commission_bps` performs no epoch-window check (per the "No commission update rule" comment) and there is no delayed-snapshot mechanism analogous to `CachedVoteAccounts` for block revenue, the very next distribution event uses the newly-set 100% commission, and the vote account (validator) retains the entire reward instead of splitting it with delegators.
4. This can be repeated indefinitely, effectively rugging any delegator relying on the previously advertised commission rate.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
