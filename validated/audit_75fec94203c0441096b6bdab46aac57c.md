## Title
Reward Value-Index (`Vi`) accumulation can silently overflow `long` via `BigInteger.longValue()`, corrupting witness-vote reward accounting and freezing/inflating `withdrawReward()` payouts - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
java-tron's vote-reward accounting uses a per-witness cumulative "value index" (`Vi`), computed the same way as the XDEFI `_pointsPerUnit` in the referenced report: `deltaVi = reward * DECIMAL_OF_VI_REWARD / totalVoteForWitness`. When `totalVoteForWitness` (the divisor) is small, `deltaVi` becomes disproportionately large. Later, when a user's share of that reward is computed as `deltaVi.multiply(userVote).divide(DECIMAL_OF_VI_REWARD)`, the code calls `.longValue()` instead of `.longValueExact()`, so any overflow of the `long` range is **silently truncated/wrapped** rather than throwing. This corrupts reward accounting (can inflate or invalidate a user's `allowance`) and can also cause the eventual balance-update math (`LongMath.checkedAdd`) to throw, permanently blocking `withdrawReward()`/`WithdrawBalanceContract` for the affected account - the same "malfunction/freeze funds" outcome described in the source report.

### Finding Description
The `Vi` accumulation mirrors the vulnerable formula exactly: [1](#0-0) 

```java
public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
  ...
  BigInteger deltaVi = BigInteger.valueOf(reward)
      .multiply(DECIMAL_OF_VI_REWARD)
      .divide(BigInteger.valueOf(voteCount));   // divide by total votes for this witness/cycle
  setWitnessVi(cycle, address, preVi.add(deltaVi));
}
```

`DECIMAL_OF_VI_REWARD` is `10^18`: [2](#0-1) 

If `voteCount` is small (e.g., a witness that only received a single small vote — analogous to Alice's "1 wei lock"), `deltaVi` becomes extremely large. This is the exact analog of `_pointsPerUnit += (newXDEFI * _pointsMultiplier) / totalUnitsCached` from the report.

Subsequently, when computing a specific voter's reward share, the code multiplies this inflated `deltaVi` by the voter's own vote count and then calls `.longValue()` (not `.longValueExact()`), which truncates silently instead of throwing on overflow: [3](#0-2) 

```java
if (beginCycle < endCycle) {
  for (Pair<byte[], Long>  vote : srAddresses) {
    ...
    BigInteger deltaVi = endVi.subtract(beginVi);
    if (deltaVi.signum() <= 0) { continue; }
    long userVote = vote.getValue();
    reward += deltaVi.multiply(BigInteger.valueOf(userVote))
        .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
  }
}
```

The identical unsafe pattern (`.longValue()` after `BigInteger` multiply/divide of `deltaVi`) is duplicated in: [4](#0-3) [5](#0-4) 

These are reachable via unprivileged, broadcastable paths:
- `WithdrawBalanceActuator.execute()` → `MortgageService.withdrawReward()` (via a `WithdrawBalanceContract` transaction): [6](#0-5) 
- `WithdrawRewardProcessor.execute()` → `VoteRewardUtil.withdrawReward()` (via TVM `withdrawReward()` precompile, callable by any contract): [7](#0-6) 

Downstream, if the truncated `reward`/`allowance` becomes an unexpectedly large (or negative) value, subsequent overflow-safe checks fail closed, e.g. `LongMath.checkedAdd(accountCapsule.getBalance(), accountCapsule.getAllowance())` in `WithdrawBalanceActuator.validate()`/`WithdrawRewardProcessor.execute()`, which throws and blocks withdrawal permanently for the affected account - reproducing the "freeze user funds" impact from the source finding. Conversely, if the wrapped value ends up positive and is added directly to `allowance` (as in `adjustAllowance`), it inflates the account's claimable balance beyond what was legitimately earned - an asset/accounting-corruption outcome.

### Impact Explanation
- Denial of service: an affected account's `allowance`/`balance` sum can permanently exceed `Long.MAX_VALUE` guard checks, making `WithdrawBalanceContract` / TVM `withdrawReward()` permanently fail for that account (funds functionally frozen, matching the H-severity impact in the referenced report).
- Accounting corruption: silent truncation via `.longValue()` (rather than `longValueExact()`) means the computed reward is not validated; it can wrap into an incorrect (potentially very large positive) `long`, corrupting the SR/voter reward ledger and enabling an account to be credited more TRX allowance than actually earned.

### Likelihood Explanation
Reaching a small `voteCount` divisor requires a witness/SR to have very few total votes for a reward cycle while still receiving `payReward()` (block/tx-fee reward) for that cycle - realistic on networks with few witness candidates (private/consortium/dev networks, or early-life low-participation periods), where any registered witness can become an active SR without needing a large vote count. An attacker controlling such a witness, or simply casting a minimal vote before a normal-sized reward is paid, is a plausible unprivileged actuator-only attack path (`VoteWitnessContract`/TVM `voteWitness` followed by `withdrawReward`), with no special privileges required.

### Recommendation
- Replace `.longValue()` with `.longValueExact()` (or explicit bounds checks) at all three sites (`MortgageService.computeReward`, `VoteRewardUtil.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`) so overflow throws a catchable `ArithmeticException` instead of silently wrapping, consistent with the exact-safe patterns already used elsewhere in the codebase (e.g., `ExchangeWithdrawActuator` uses `longValueExact()`).
- Enforce a minimum vote/stake threshold before a witness's votes are used as a `Vi` divisor, mirroring the "minimum units locked" mitigation adopted by the referenced project, to prevent a near-zero denominator from producing an extreme `deltaVi`.
- Ensure any caught overflow does not simply drop the reward silently but is logged/handled in a way that does not leave the account's `beginCycle`/`endCycle` state inconsistent, to avoid a permanent inability to progress reward accounting for the affected address.

### Proof of Concept
1. On a network configuration where the number of witness candidates is small (so all/most candidates become active SRs regardless of vote count), have the attacker create/control a witness `W`.
2. Attacker votes with a minimal amount (`voteCount = 1`) exclusively for `W` in cycle `c`, no other votes exist for `W` in that cycle.
3. `W` produces a block; `MortgageService.payBlockReward`/`payTransactionFeeReward` calls `payReward`, storing a normal-sized `reward` value via `delegationStore.addReward(cycle, W, value)`.
4. `DelegationStore.getWitnessVote(cycle, W)` returns `1`. When `accumulateWitnessVi`/`RewardViCalService.accumulateWitnessVi` runs, `deltaVi = reward * 10^18 / 1`, producing an extremely large `BigInteger`.
5. A later voter with a larger `userVote` for `W` (or the attacker increasing their own vote count in a subsequent cycle) triggers `computeReward`/`withdrawReward`; `deltaVi.multiply(userVote).divide(10^18).longValue()` overflows `long` and truncates silently.
6. Either (a) `WithdrawBalanceActuator.validate()`'s `LongMath.checkedAdd(balance, allowance)` throws `ArithmeticException`, permanently blocking that account's `WithdrawBalanceContract`/`withdrawReward()` execution, or (b) the wrapped value is credited as `allowance`, corrupting that account's claimable reward balance.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
