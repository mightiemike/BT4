### Title
Missing 32-byte length validation of PedersenHash content before native JNI call in `PedersenHashCapsule.combine` / `JLibrustzcash.librustzcashMerkleHash` - ([File: chainbase/src/main/java/org/tron/core/capsule/PedersenHashCapsule.java])

### Summary
`PedersenHashCapsule.combine(PedersenHash a, PedersenHash b, int depth)` passes `a.getContent().toByteArray()` and `b.getContent().toByteArray()` directly into `JLibrustzcash.librustzcashMerkleHash`, which forwards them unchecked to the native `librustzcash` JNI binding [1](#0-0) . Unlike sibling native-call wrappers in the same class (`librustzcashAskToAk`, `librustzcashNskToNk`, `librustzcashToScalar`, `librustzcashTreeUncommitted`), which all call `LibrustzcashParam.valid32Params`/`validParamLength` before invoking the native method, `librustzcashMerkleHash` performs no length check at all [2](#0-1) [3](#0-2) .

### Finding Description
`IncrementalMerkleTreeContainer.append(PedersenHash obj)` is called on every note commitment inserted into the incremental Merkle tree (both for the freshly-appended leaf and, when the tree is complete, for the parents being combined) [4](#0-3) . When two present nodes need to be merged, it calls `PedersenHashCapsule.combine(...)`, which never checks that `a`/`b` content is exactly 32 bytes before building `MerkleHashParams` and invoking the native `librustzcashMerkleHash` [1](#0-0) .

By contrast, other JNI entry points in `JLibrustzcash` that accept raw `byte[]` explicitly guard the array length (e.g. `librustzcashAskToAk` calls `LibrustzcashParam.valid32Params(ask)`, `librustzcashToScalar` calls `validParamLength(value, 64)` and `valid32Params(data)`), showing that the codebase's own convention is to validate array sizes in Java before crossing into native code [5](#0-4) [6](#0-5) . `librustzcashMerkleHash` and `LibrustzcashParam.MerkleHashParams` do not follow this convention.

I was not able to fully verify, within the available tool budget, whether `ShieldedTransferActuator.validate()` independently enforces that `ReceiveDescription.note_commitment` (`cm`) is exactly 32 bytes before `execute()` reaches `IncrementalMerkleTreeContainer.append`. I confirmed that `ShieldedTransferActuator.java` references `ReceiveDescription`/`getNoteCommitment` extensively, but could not inspect the exact validation logic before running out of iterations, so this is an open gap in my verification, not a confirmed absence of a check.

### Impact Explanation
If `ShieldedTransferActuator.validate()` does not independently bound-check the note commitment length to exactly 32 bytes prior to `execute()`, a crafted `ReceiveDescription.note_commitment` of a different length (e.g. 16 or 64 bytes) would reach `PedersenHashCapsule.combine` → `JLibrustzcash.librustzcashMerkleHash` → the native `librustzcash` library with a Java `byte[]` whose length does not match the native side's fixed 32-byte buffer assumption. Depending on the JNI parameter marshaling in the native wrapper, this could result in native out-of-bounds reads/writes, process crash (DoS), or in the worst case memory corruption/RCE on the node — matching the "node RCE" / "DoS via TRON protocol implementation" bounty classes.

### Likelihood Explanation
This is only exploitable if no size check for `note_commitment` exists earlier in `ShieldedTransferActuator.validate()` (or in the SNARK-proof verification path for outputs), which I was unable to confirm or refute with certainty in this session. If such an earlier check is absent, the attack requires only building a raw `ShieldedTransferContract` with a malformed `ReceiveDescription.note_commitment` length and broadcasting it via the standard `BroadcastTransaction` RPC — no special privilege, keys, or non-default configuration needed, and the cost is a single ordinary signed transaction.

### Recommendation
Add explicit length validation (`LibrustzcashParam.valid32Params`, consistent with sibling methods) for both `a`/`b` content and the `depth` bounds in `PedersenHashCapsule.combine` before constructing `MerkleHashParams`, and/or add the same guard inside `JLibrustzcash.librustzcashMerkleHash`/`LibrustzcashParam.MerkleHashParams`. Additionally, confirm and, if missing, add an explicit `note_commitment.size() == 32` check in `ShieldedTransferActuator.validate()` for every `ReceiveDescription`, so malformed transactions are rejected with a `ContractValidateException` before any zk-related native call is reached.

      .setContent(ByteString.copyFrom(new byte[32]))

  // Actual current behavior: no Java-side length check exists before

  assertThrows(ZksnarkException.class,
      () -> PedersenHashCapsule.combine(malformed, normal, 0));

  public void append(PedersenHash obj) throws ZksnarkException {
    if (isComplete(DEPTH)) {
      throw new ZksnarkException("tree is full");
    }
    if (!leftIsPresent()) {
      treeCapsule.setLeft(obj);
    } else if (!rightIsPresent()) {
      treeCapsule.setRight(obj);
    } else {
      PedersenHashCapsule combined =
          PedersenHashCapsule.combine(treeCapsule.getLeft(), treeCapsule.getRight(), 0);
      treeCapsule.setLeft(obj);
      treeCapsule.clearRight();
      for (int i = 0; i < DEPTH; i++) {
        if (i < treeCapsule.getParents().size()) {
          PedersenHashCapsule parentCompressCapsule =
              new PedersenHashCapsule(treeCapsule.getParents().get(i));
          if (parentCompressCapsule.isPresent()) {
            combined =
                PedersenHashCapsule.combine(
                    treeCapsule.getParents().get(i), combined.getInstance(), i + 1);
            treeCapsule.clearParents(i);
          } else {
            treeCapsule.setParents(i, combined.getInstance());
            break;
          }
        } else {
          treeCapsule.addParents(combined.getInstance());
          break;
        }
      }
    }
  }
