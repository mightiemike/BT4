### Title
Unbounded delegated-resource fan-out lets an unprivileged account force costly RPC/HTTP queries on any node - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegateResourceActuator` allows any account to call `delegateResource` an unbounded number of times to distinct receiver addresses, with no cap on the number of `to`/`from` entries recorded in `DelegatedResourceAccountIndexCapsule`. The public, unprivileged `getDelegatedResourceAccountIndex` RPC/HTTP endpoint then must read and sort this entire, attacker-controlled list on every request.

### Finding Description
`DelegateResourceActuator.execute`/`delegateResource` records a new delegation index entry for every `delegateResource` transaction via `DelegatedResourceAccountIndexStore.delegateV2`, with no validation on how many distinct receivers/senders an account may accumulate: [1](#0-0) 

The only bound-related checks in `validate()` concern balance sufficiency and lock-period limits, never the count of delegation relationships: [2](#0-1) 

`DelegatedResourceAccountIndexStore.getWithPrefix` (used by `getV2Index`) performs a `prefixQuery` over the DB for a given address prefix, materializes every matching entry into a list, and sorts it — cost proportional to the number of delegation relationships that address has accumulated: [3](#0-2) 

This query is reachable directly by any unauthenticated client through the HTTP servlet `GetDelegatedResourceAccountIndexServlet`, which simply forwards the caller-supplied address to `wallet.getDelegatedResourceAccountIndex` and writes out the full resulting list: [4](#0-3) 
and equivalently via the gRPC `getDelegatedResourceAccountIndex` RPC method exposed in `RpcApiService`.

An attacker can broadcast a very large number of cheap `DelegateResourceContract` transactions (1 TRX minimum delegate balance, self-funded, low fee) from one owner address to many distinct throwaway receiver addresses, building an arbitrarily large `toAccounts`/`fromAccounts` index for that owner address. Every subsequent (unauthenticated, rate-limited but not size-limited) call to the index-lookup RPC/HTTP endpoint for that address then forces the serving node to enumerate and sort the entire attacker-built list, and to serialize/return it over the wire.

This mirrors the report's bug class: an unprivileged actor (the borrower/delegator) unilaterally grows an unbounded, self-controlled list that a *different, unrelated party* (any RPC caller, or in the aggregate, every full node serving that RPC) is forced to pay processing cost for, with no cap analogous to `enterMarkets`'s missing market-count limit.

### Impact Explanation
Because the endpoint is public and unauthenticated, and the list size is entirely attacker-controlled with no upper bound enforced at the actuator level, a malicious user can inflate the per-query cost of `getDelegatedResourceAccountIndex`/`getDelegatedResourceV2` for their own address arbitrarily. Repeated or scripted invocation of this query (or simply causing legitimate wallets/explorers that display “who delegated to me / who did I delegate to” to hit this path) increases CPU (prefix scan + sort) and response-payload size on every full node that serves the API, which can degrade RPC/HTTP-API availability under load — a resource/DoS impact on the node's API surface, matching the "unbounded loop / gas-cost griefing" bug class from the source report, translated to TRON's iterate-and-serialize-on-read pattern rather than accrue-on-write.

### Likelihood Explanation
Likelihood is moderate: creating many delegation entries only costs the 1-TRX-minimum delegate balance and ordinary transaction fees per delegation (no special privilege required), so the attack is cheap to set up. The rate limiter on the servlet (`RateLimiterServlet`) mitigates raw request-flooding but does not bound the *size* of the underlying data structure being processed per request, so a modest number of legitimate-looking queries against a heavily-fan-out address can still be disproportionately expensive relative to normal use.

### Recommendation
- Enforce a maximum number of distinct delegate relationships (to/from) per owner address in `DelegateResourceActuator.validate()`, rejecting new delegations once the cap is reached (mirroring the report's recommendation to bound `enterMarkets`).
- Alternatively/additionally, bound or paginate the results returned by `DelegatedResourceAccountIndexStore.getWithPrefix`/`getV2Index` and the corresponding RPC/HTTP handlers, so a single query cannot force unbounded server-side work regardless of how large an index has already been allowed to grow.
- Add cost-based or size-based rate limiting (not just request-count limiting) to `getDelegatedResourceAccountIndex`/`getDelegatedResourceV2` endpoints.

### Proof of Concept
1. From account A, send `DelegateResourceContract` transactions delegating the minimum 1 TRX of bandwidth/energy to N distinct freshly-created receiver addresses (N large, e.g. tens of thousands), each accepted because `DelegateResourceActuator.validate()` never checks the count of existing delegations for A.
2. Each call appends to A's index via `delegatedResourceAccountIndexStore.delegateV2` with no cap.
3. Call `GET /wallet/getdelegatedresourceaccountindex?value=<A>` (or the gRPC equivalent) — the node must run `getWithPrefix`, scanning and sorting all N entries and serializing them in the response, incurring cost proportional to N on every invocation. [3](#0-2)

  private void delegateResource(byte[] ownerAddress, byte[] receiverAddress, boolean isBandwidth,
                                long balance, boolean lock, long lockPeriod) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicPropertiesStore = chainBaseManager.getDynamicPropertiesStore();
    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();
    DelegatedResourceAccountIndexStore delegatedResourceAccountIndexStore = chainBaseManager
        .getDelegatedResourceAccountIndexStore();

    // 1. unlock the expired delegate resource
    long now = chainBaseManager.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, now);

    //modify DelegatedResourceStore
    long expireTime = 0;
    if (lock) {
      expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL;
    }
    byte[] key = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, lock);
    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore.get(key);
    if (delegatedResourceCapsule == null) {
      delegatedResourceCapsule = new DelegatedResourceCapsule(ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));
    }

    if (isBandwidth) {
      delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
    } else {
      delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
    }
    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress,
        dynamicPropertiesStore.getLatestBlockHeaderTimestamp());

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
