### Title
Griefing smart-contract deployment by front-running the deterministic contract address with a pre-created account - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.create()` computes the new contract's address deterministically from the pending transaction and then rejects deployment if any account already exists at that address. Because the address is derived only from the transaction's own hash and the owner's address — both knowable as soon as the signed `CreateSmartContract` transaction is visible (e.g., in the P2P/mempool broadcast phase, before block inclusion) — an unprivileged third party can pre-create an account at the predicted address (via an ordinary TRX transfer) to make the legitimate deployment transaction fail. This is the same bug class as the reported `launchGroupCoinToUniswapV3`/`createPool` griefing: an unprivileged, permissionless action can "claim" a resource that a subsequent operation assumes is uninitialized, turning a normal deploy into a guaranteed-fail DoS.

### Finding Description
The contract address for a top-level `CreateSmartContract` transaction is computed as: [1](#0-0) 

`txRawDataHash` is simply the transaction ID of the (already fully signed) creation transaction, combined with the owner address and hashed. Both inputs are fully determined the moment the transaction is signed — no block inclusion or execution result is required to know them.

`VMActuator.create()` then treats the existence of an account at that computed address as fatal: [2](#0-1) 

Because ordinary TRX transfers to a non-existent address implicitly create an `AccountCapsule` at that address (standard TRON behavior), any observer who sees the signed-but-not-yet-included `CreateSmartContract` transaction (e.g. while it sits in the P2P transaction pool prior to block packing) can:
1. Extract the transaction bytes and recompute `contractAddress = sha3omit12(txId ++ ownerAddress)` exactly as `WalletUtil.generateContractAddress` does.
2. Broadcast (and get included) a trivial `TransferContract` sending any amount of TRX to that address before the original creation transaction is packed.
3. When the original creation transaction is later processed, `rootRepository.getAccount(contractAddress) != null` is true, so `create()` throws `ContractValidateException("Trying to create a contract with existing contract address: ...")`, and the deployment permanently fails for that transaction (the deployer still pays the transaction fee/bandwidth for the failed broadcast attempt, and must resubmit with a new nonce-changing transaction, whose new hash the attacker can race again).

This mirrors the external report's root cause exactly: a permissionless, cheap operation ("createPool"/"send TRX to an address") can pre-empt a subsequent privileged operation that unconditionally assumes the target slot ("pool"/"contract account") is empty, rather than checking-and-adapting to pre-existing state (as the report's recommended `_initUniV3PoolIfNecessary` pattern does).

### Impact Explanation
Impact is Medium: this is a targeted denial-of-service against specific contract deployments (not an unbounded network-wide DoS), and it does not cause direct fund loss to third parties. However, it can be used maliciously to block a specific victim's deployment repeatedly (a new race is possible each time the victim resubmits, since the transaction hash — and hence predicted address — changes with each new signature/nonce), wasting the victim's fees/bandwidth and delaying or indefinitely stalling a targeted contract launch. This matches the "Medium impact / Medium likelihood" classification of the analogous UniswapV3 report.

### Likelihood Explanation
Likelihood is Medium: the attacker needs only to observe a `CreateSmartContract` transaction after it is signed and broadcast (visible via P2P gossip before block packing) and race a plain TRX transfer to the computed address into an earlier block/position. No privileged role, leaked key, or protocol bug beyond normal P2P propagation timing is required — it is a standard front-running/griefing pattern applicable to any public node observing the transaction pool.

### Recommendation
Adopt the report's suggested pattern of "check-then-adapt" instead of "assume-empty-then-fail":
- In `VMActuator.create()`, when an account already exists at the predicted address but it is a plain (non-contract) account with no code/no `ContractCapsule`, allow the deployment to proceed by upgrading that account in place (mirroring the CREATE2 collision-handling branch already present in `Program.createContractImpl` at `actuator/src/main/java/org/tron/core/vm/program/Program.java:827-843`, which does exactly this: if `existingAccount != null` but `!contractAlreadyExists`, it updates the account type to `Contract` and proceeds).
- Only reject deployment if a `ContractCapsule`/code already exists at that address (i.e., a genuine collision), not merely because a plain account (e.g., funded by a transfer) exists there.

### Proof of Concept
1. Victim signs and broadcasts a `CreateSmartContract` transaction `T` (not yet included in a block).
2. Attacker observes `T` in the transaction pool, computes `txId = TransactionCapsule(T).getTransactionId()` and `contractAddress = sha3omit12(txId ++ ownerAddress)` exactly as `WalletUtil.generateContractAddress` does.
3. Attacker broadcasts a `TransferContract` sending 1 sun to `contractAddress`; this transaction gets included first (attacker can offer a higher energy/bandwidth priority or simply be faster).
4. When `T` is processed, `VMActuator.create()` at `actuator/src/main/java/org/tron/core/actuator/VMActuator.java:355-361` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException`, causing the victim's deployment to fail while the victim's fee/bandwidth is still consumed.

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
