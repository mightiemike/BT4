### Title
Backup restore commits unauthenticated write sets to the state store, allowing accepted state corruption independent of the accumulator proof — ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
In the `db-restore` pipeline, `LoadedChunk::load` reads `(txn, aux_info, txn_info, events, write_set)` tuples from a backup chunk, but only wraps `txns`, `events`, and `txn_infos` into a `TransactionListWithProofV2` for verification against the ledger accumulator. `write_sets` are carried alongside, entirely outside the verified structure, and are never checked against `txn_info.state_change_hash()` before being persisted to storage or fed into state reconstruction (`calculate_state_and_put_updates`).

### Finding Description
`LoadedChunk::load` in [1](#0-0)  deserializes each backup record into `(txn, aux_info, txn_info, events, write_set)`, then builds a `TransactionListWithProofV2` from only `txns`, `event_vecs`, and `txn_infos`, calling `.verify(ledger_info.ledger_info(), ...)`. `write_sets` is kept as a separate `Vec<WriteSet>` field on `LoadedChunk` and is never passed through this verification call.

The verification path used here is `TransactionListWithProof::verify` (via `TransactionListWithProofV2`), which checks the transaction hash and event root hash against each `TransactionInfo`, then verifies the `TransactionInfo` list against the accumulator root in the ledger info: [2](#0-1) . Unlike `TransactionOutputListWithProof::verify`, which explicitly checks `txn_info.state_change_hash() == CryptoHash::hash(&txn_output.write_set)` [3](#0-2) , `TransactionListWithProof` carries no write set field and therefore performs no such check.

After this partial verification, the unauthenticated `write_sets` are handed to `restore_handler.save_transactions` / `save_transactions_and_replay_kv` [4](#0-3) [5](#0-4) , which route into `restore_utils::save_transactions_impl`. There, the write sets are written directly to `WriteSetDb` and, in `kv_replay` mode, fed into `state_store.calculate_state_and_put_updates` to reconstruct the Jellyfish Merkle state and storage usage, with no hash comparison against the already-verified `txn_info.state_change_hash()`: [6](#0-5) .

Consequently, a backup archive whose `write_set` bytes have been corrupted or substituted (while `txn`, `events`, and `txn_info` remain intact and pass the accumulator proof) will restore successfully, and the resulting node will persist an incorrect write set into `WriteSetDb` and derive an incorrect state tree/state values via `calculate_state_and_put_updates`, all while the transaction, its events, and the accumulator proof still verify as authentic.

### Impact Explanation
This breaks the "proof and storage pivot" invariant that committed state values, and any values used to reconstruct the state tree, must be bound to the authenticated ledger content. Because the write set is decoupled from the accumulator-proof-verified transaction info, a restored node can end up with a state store/JMT that silently diverges from the correct VM-executed result for the affected version, while all standard proof checks (transaction, event, accumulator) still pass. Any node bootstrapped or state-synced from such a backup would serve wrong state values and would itself compute wrong state roots going forward — a durable, silent divergence of committed ledger data, matching the "committed state differs from correct VM result" and "corrupted durable ledger data" impact categories.

### Likelihood Explanation
This requires control over (or corruption of) the write-set portion of a backup transaction chunk file, which is plausible in scenarios involving compromised/untrusted backup storage, backup transport corruption, or a malicious/buggy backup producer — none of which are excluded by the out-of-scope list (this is not "malicious peer/node consensus behavior" or a third-party oracle issue; it's a local repo verification gap in the restore code path). The `db-restore` tool is a standard, unprivileged operational tool used to bootstrap nodes, including full/validator nodes, from externally-supplied backup files.

### Recommendation
In `LoadedChunk::load`, verify each `write_set`'s hash against the corresponding `txn_info.state_change_hash()` (mirroring the check already done in `TransactionOutputListWithProof::verify`) before accepting the chunk, or extend the verification structure used here to include and authenticate write sets, so that `save_transactions`/`save_transactions_and_replay_kv` and `calculate_state_and_put_updates` can never be reached with a write set that wasn't cryptographically bound to the already-verified `TransactionInfo`.

### Proof of Concept
1. Produce (or tamper with) a transaction backup chunk file such that the BCS-encoded `write_set` field for one record differs from the write set that originally produced `txn_info.state_change_hash()`, while `txn`, `events`, and `txn_info` are left untouched.
2. Run `db-restore` (or the internal `RestoreCoordinator`/`TransactionRestoreBatchController` flow) against this backup.
3. `LoadedChunk::load` verifies `txn_list_with_proof` successfully (transaction hash, event root hash, and accumulator proof all pass, since none of them cover `write_set`).
4. The tampered `write_sets` are passed to `restore_handler.save_transactions_and_replay_kv` → `restore_utils::save_transactions_impl`, which persists them to `WriteSetDb` and folds them into `calculate_state_and_put_updates`, producing a state tree/state values that do not match the correct VM output for that version — with no error or verification failure reported to the operator.

    pub fn verify(&self, ledger_info: &LedgerInfo) -> Result<()> {
        let txn_hash = self.transaction.committed_hash();
        ensure!(
            txn_hash == self.proof.transaction_info().transaction_hash(),
            "Transaction hash ({}) not expected ({}).",
            txn_hash,
            self.proof.transaction_info().transaction_hash(),
        );

        if let Some(events) = &self.events {
            let event_hashes: Vec<_> = events.iter().map(CryptoHash::hash).collect();
            let event_root_hash =
                InMemoryEventAccumulator::from_leaves(&event_hashes[..]).root_hash();
            ensure!(
                event_root_hash == self.proof.transaction_info().event_root_hash(),
                "Event root hash ({}) not expected ({}).",
                event_root_hash,
                self.proof.transaction_info().event_root_hash(),
            );
        }

        self.proof.verify(ledger_info, self.version)
    }
