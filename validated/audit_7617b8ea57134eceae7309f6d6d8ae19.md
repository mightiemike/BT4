### Title
Gateway HTTP server goroutine/connection leak via Slowloris-style slow request bodies bypassing `http.TimeoutHandler` - ([File: core/services/gateway/network/httpserver.go])

### Summary
`httpServer.handleRequest` reads the entire request body synchronously with `io.ReadAll(source)` before any authentication or `ProcessRequest` logic runs, and this read is not tied to the request `context.Context` at all. Because `http.TimeoutHandler` only cancels the context and returns a timeout response to the client — it does not forcibly terminate the wrapped handler goroutine — an attacker can keep the `handleRequest` goroutine (and its underlying TCP connection) blocked in `io.ReadAll` for up to `ReadTimeoutMillis`, independent of and potentially far longer than `RequestTimeoutMillis`.

### Finding Description
In `NewHTTPServer`, when `config.RequestTimeoutMillis > 0` the handler is wrapped with `http.TimeoutHandler(handler, ..., "Request timed out")` [1](#0-0) . `http.TimeoutHandler`'s documented behavior is to run the wrapped handler in its own goroutine, wait for either completion or the timeout, and on timeout write the "Request timed out" response to the client — but it never cancels or otherwise interrupts the still-running handler goroutine; that goroutine keeps executing until it naturally returns.

Inside `handleRequest`, the body is consumed with a plain, context-unaware `io.ReadAll(source)` call where `source` is an `http.MaxBytesReader` wrapping `r.Body` [2](#0-1) . `io.ReadAll` blocks on `Read()` until EOF, an error, or the max-byte limit is hit — it has no awareness of `r.Context()` being canceled by the `TimeoutHandler`. The only thing that can unblock this read is the connection-level `ReadTimeout` configured on `http.Server` from `config.ReadTimeoutMillis` [3](#0-2) , which is a value entirely independent of `RequestTimeoutMillis`.

This means:
- The body is fully read (attacker-controlled pacing) before any JWT/auth extraction or call into `s.handler.ProcessRequest`, so no authentication is required to occupy the goroutine/connection.
- If an operator sets `ReadTimeoutMillis` larger than `RequestTimeoutMillis` (a plausible config choice to tolerate large/slow legitimate uploads while keeping fast client-visible timeouts), or leaves `ReadTimeoutMillis` unset/0 (which disables the Go `http.Server` read timeout entirely, per `net/http` semantics), the handler goroutine and its connection can be held open far beyond, or entirely decoupled from, the client-visible timeout.
- No existing authz/signature/replay/rate-limit check in this path prevents an unauthenticated caller from opening many such connections against the gateway's public `Path` endpoint (e.g., `UserServerConfig`'s `/user`), since those checks only occur later inside `ProcessRequest`, after the body read completes.

### Impact Explanation
Each such slow-body connection ties up one server goroutine plus one open file descriptor/socket for up to `ReadTimeoutMillis` (or indefinitely if that value is 0/misconfigured), while the client already believes the request failed. An unprivileged attacker opening many concurrent slow connections can exhaust goroutines and file descriptors on the gateway process, producing denial of service for the Chainlink Gateway's HTTP-facing job/workflow submission endpoint — matching a resource-exhaustion / DoS impact class.

### Likelihood Explanation
Exploitability depends on configuration: it is most severe when `ReadTimeoutMillis` is 0 or set meaningfully larger than `RequestTimeoutMillis`. The sample configs in this repo set them equal (`ReadTimeoutMillis = 1000`, `RequestTimeoutMillis = 1000`) [4](#0-3) , which limits — but does not eliminate — the exposure window (a goroutine can still be held for up to the full `ReadTimeoutMillis` after the client already received a timeout response). No authentication, secrets, or special network position is required; the attack only needs standard TCP connectivity to the gateway's HTTP port and the ability to trickle bytes slowly, which is trivially repeatable and scriptable (classic Slowloris technique).

### Recommendation
Make the body-read in `handleRequest` context-aware so it aborts promptly when `r.Context()` is canceled (e.g., run `io.ReadAll` in a goroutine and `select` on `ctx.Done()` vs. completion, or use a context-aware reader/`io.Copy` with deadline propagation tied to the same duration as `RequestTimeoutMillis`). Additionally, ensure `ReadTimeoutMillis` is bounded and never allowed to be 0/unset in production configs, and consider setting the connection's read deadline explicitly to `min(ReadTimeoutMillis, RequestTimeoutMillis)` so the two timeouts stay coupled.

### Proof of Concept
Integration test plan:
1. Start `httpServer` via `NewHTTPServer` with `RequestTimeoutMillis` small (e.g., 200ms) and `ReadTimeoutMillis` large (e.g., 30s) or 0.
2. From N goroutines/clients, open raw TCP connections to the server's `Path` endpoint, send valid headers with a `Content-Length` larger than the bytes actually sent, then write a few bytes every ~150ms (below any single-read deadline) without completing the body.
3. Assert each connection receives the `"Request timed out"` response from `http.TimeoutHandler` after ~`RequestTimeoutMillis`.
4. Immediately after receiving the timeout response, sample `runtime.NumGoroutine()` and the process's open file descriptor count; assert they remain elevated (roughly proportional to N) well beyond `RequestTimeoutMillis`, only dropping back to baseline near `ReadTimeoutMillis` (or never, if `ReadTimeoutMillis` is 0) — demonstrating the goroutine/connection leak independent of the client-visible timeout.
5. While the leaked connections are held open, send a fresh legitimate request and assert it still succeeds but with degraded latency/availability as N grows, confirming resource pressure on the gateway service.
