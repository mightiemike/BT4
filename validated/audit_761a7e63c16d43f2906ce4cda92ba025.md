### Title
`verify_and_charge_tx_ephemeral` applies deposit to storage-stake check for sender-is-receiver transactions, blocking valid self-calls — (File: `runtime/runtime/src/verifier.rs`)

### Summary

In `verify_and_charge_tx_ephemeral`, the `LackBalanceForState` storage-stake guard uses `new_amount = balance − total_cost = balance − gas_cost − deposit_cost`. For sender-is-receiver (SIR) transactions the deposit is credited back to the same account when the receipt executes, so the true post-execution balance is `balance − gas_cost`. The check therefore uses an intermediate, artificially-deflated balance that does not reflect the final on-chain state, causing valid self-calls with deposits to be rejected with `LackBalanceForState` even though the final state satisfies the storage-stake invariant.

### Finding Description

`calculate_tx_cost` / `tx_cost` in `runtime/runtime/src/config.rs` computes:

```
deposit_cost = total_deposit(actions)
total_cost   = gas_cost + deposit_cost
``` [1](#0-0) 

The `sender_is_receiver` flag is used only to select `send_sir` vs `send_not_sir` gas fees; it is never used to exclude the deposit from `total_cost`. [2](#0-1) 

`verify_and_charge_tx_ephemeral` then computes:

```rust
let new_amount = account.amount().checked_sub(total_cost).unwrap();
// ...
match check_storage_stake(account, new_amount, config) {
``` [3](#0-2) 

`check_storage_stake` requires `new_amount + locked >= storage_amount_per_byte × storage_usage`. [4](#0-3) 

For a SIR transaction the deposit is deducted from the signer at validation time and then credited back to the same account (as receiver) when the receipt executes — either via a `Transfer` action or as the attached deposit of a `FunctionCall`. The net effect on the account balance is `balance − gas_cost`, not `balance − gas_cost − deposit_cost`. The storage-stake check is therefore performed against a balance that is `deposit_cost` lower than the actual post-execution balance, making it strictly more restrictive than necessary.

The `apply_action_receipt` path performs its own storage-stake check only after all actions have been applied and only on the actual resulting balance, so it would pass for the same transaction: [5](#0-4) 

The two checks are therefore inconsistent for SIR transactions with non-zero deposits.

### Impact Explanation

An account that has a contract deployed (non-trivial `storage_usage`) and whose liquid balance sits in the window `[storage_stake_required + gas_cost, storage_stake_required + gas_cost + deposit_cost)` cannot submit a self-directed function call with a deposit, even though the call would leave the account fully solvent. This is a **contract execution flow breakage**: the user is unable to invoke their own contract with attached value. If the blocked call is time-sensitive — for example, a self-managed DeFi position that requires a deposit to rebalance or avoid liquidation — the inability to execute it can result in direct loss of funds. The error is surfaced as `InvalidTxError::LackBalanceForState`, which is a hard rejection at the RPC / chunk-production layer, so the user has no recourse within the same transaction.

### Likelihood Explanation

The conditions are realistic and reachable by any unprivileged user:

1. **SIR transaction** — any account calling a method on itself (e.g., a contract owner invoking their own contract).
2. **Non-trivial storage usage** — any account with a deployed contract or significant on-chain data.
3. **Balance in the vulnerable window** — the window width equals `deposit_cost`; for a 10 NEAR deposit the window is 10 NEAR wide, which is easily reachable when an account's balance is close to its storage-stake requirement.

No special privileges, validator access, or network-level capabilities are required. A standard `SignedTransaction` with `signer_id == receiver_id` and a non-zero deposit is sufficient to trigger the rejection.

### Recommendation

In `verify_and_charge_tx_ephemeral`, when `tx.signer_id() == tx.receiver_id()`, exclude the deposit from the balance used for the storage-stake check, because the deposit will be returned to the same account at receipt execution time:

```rust
let sir = tx.signer_id() == tx.receiver_id();
let storage_check_amount = if sir {
    // deposit is credited back; only gas is permanently deducted
    account.amount().checked_sub(transaction_cost.gas_cost).unwrap_or(0)
} else {
    new_amount  // balance - gas_cost - deposit_cost
};
match check_storage_stake(account, storage_check_amount, config) { … }
```

Alternatively, expose a `deposit_cost` field from `TransactionCost` (it is already computed there) and subtract it from `new_amount` only when `!sir`. [6](#0-5) 

### Proof of Concept

**Setup:**
- `storage_amount_per_byte` = 10 000 000 000 000 000 000 yoctoNEAR (10^19)
- Alice's contract `storage_usage` = 10 000 bytes → `storage_stake_required` = 100 NEAR
- Alice's `amount` = 110 NEAR, `locked` = 0
- Transaction: `signer_id = receiver_id = alice`, action = `FunctionCall { deposit: 20 NEAR, gas: … }`
- `gas_cost` ≈ 1 NEAR (send + exec fees)

**At `verify_and_charge_tx_ephemeral`:**
```
total_cost  = gas_cost + deposit_cost = 1 + 20 = 21 NEAR
new_amount  = 110 − 21 = 89 NEAR
check_storage_stake(89 NEAR) → 89 < 100 → LackBalanceForState  ← REJECTED
```

**Actual post-execution balance (if the check were skipped):**
```
balance after tx validation deduction : 110 − 21 = 89 NEAR
deposit credited back at receipt exec  :  89 + 20 = 109 NEAR
check_storage_stake(109 NEAR) → 109 ≥ 100 → OK  ← WOULD PASS
```

The transaction is rejected at validation time with `InvalidTxError::LackBalanceForState` even though the final on-chain state would satisfy the storage-stake invariant. Alice cannot call her own contract with a 20 NEAR deposit despite having 110 NEAR — 10 NEAR above the storage-stake requirement. [7](#0-6) [8](#0-7)

pub fn calculate_tx_cost(
    receiver_id: &AccountId,
    signer_id: &AccountId,
    signer_public_key: &PublicKey,
    actions: &[Action],
    config: &RuntimeConfig,
    current_gas_price: Balance,
) -> Result<TransactionCost, IntegerOverflowError> {
    let sender_is_receiver = receiver_id == signer_id;
    let fees = &config.fees;
    let mut burnt: ParameterCost =
        fees.fee(ActionCosts::new_action_receipt).send_fee(sender_is_receiver);
    burnt = burnt.checked_add_result(total_send_fees(
        config,
        sender_is_receiver,
        actions,
        receiver_id,
    )?)?;
    // Burn the signature-verification cost as part of converting the
    // transaction. This raises the gas the signer must buy (burnt_amount /
    // total_cost below) but never `gas_remaining` (the gas attached to / left
    // for the resulting receipts), so on-chain function-call gas budgets are
    // unaffected.
    burnt =
        burnt.checked_add_result(signature_verification_cost(fees, signer_public_key, actions)?)?;

    // Calculate `gas_remaining`, which are all gas costs minus what is already
    // burnt in the sending step. Compute is not relevant here, as this gas will
    // be burnt later and has no effect on the current chunk capacity.
    // Gas attached to function calls
    let prepaid_gas = total_prepaid_gas(actions)?;
    // Send/Exec costs for actions inside the receipt
    let prepaid_send_fee = total_prepaid_send_fees(config, actions)?;
    let prepaid_exec_fee = total_prepaid_exec_fees(config, actions, receiver_id)?;
    // Exec cost for the receipt that wraps the actions
    let receipt_cost = fees.fee(ActionCosts::new_action_receipt).exec_fee();
    let gas_remaining = prepaid_gas
        .checked_add_result(prepaid_send_fee.gas)?
        .checked_add_result(receipt_cost.gas)?
        .checked_add_result(prepaid_exec_fee.gas)?;

    // Gas burned on converting the transaction to a receipt is burned at the current price.
    let burnt_amount = safe_gas_to_balance(current_gas_price, burnt.gas)?;

    // Gas attached to the receipt is purchased at a price which should be at least as large as
    // min_gas_purchase_price. Later it might be burned at a lower price, in which case the price
    // difference will be refunded.
    let receipt_gas_price = std::cmp::max(current_gas_price, config.min_gas_purchase_price);
    let remaining_gas_amount = safe_gas_to_balance(receipt_gas_price, gas_remaining)?;
    let gas_cost = safe_add_balance(burnt_amount, remaining_gas_amount)?;
    let deposit_cost = total_deposit(actions)?;
    let total_cost = safe_add_balance(gas_cost, deposit_cost)?;
    Ok(TransactionCost {
        gas_burnt: burnt.gas,
        compute_burnt: burnt.compute,
        gas_remaining,
        receipt_gas_price,
        burnt_amount,
        gas_cost,
        deposit_cost,
        total_cost,
    })
}

pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }
}

pub fn verify_and_charge_tx_ephemeral(
    config: &RuntimeConfig,
    account: &Account,
    access_key: &AccessKey,
    tx: &Transaction,
    transaction_cost: &TransactionCost,
    block_height: Option<BlockHeight>,
    pending: &PendingConstraints,
) -> TxVerdict {
    // It's the caller's responsibility to NOT call this function for transactions with
    // nonce_index (i.e. gas key transactions).
    assert!(
        tx.nonce().nonce_index().is_none(),
        "verify_and_charge_tx_ephemeral called for gas key transaction"
    );
    // Gas keys must be used via gas key transaction path (with nonce_index)
    if let Some(gas_key_info) = access_key.gas_key_info() {
        return TxVerdict::Failed(InvalidTxError::InvalidNonceIndex {
            tx_nonce_index: None,
            num_nonces: gas_key_info.num_nonces,
        });
    }
    let TransactionCost {
        gas_burnt,
        compute_burnt,
        gas_remaining,
        receipt_gas_price,
        total_cost,
        burnt_amount,
        ..
    } = *transaction_cost;
    let account_id = tx.signer_id();
    let tx_nonce = tx.nonce().nonce();
    let effective_nonce = std::cmp::max(access_key.nonce, pending.max_nonce);
    if let Err(e) = verify_nonce(tx_nonce, effective_nonce, block_height, tx.nonce_mode()) {
        return TxVerdict::Failed(e);
    }

    // saturating_sub is fine here: on the consensus path pending constraints
    // are always default (zero), so the subtraction is exact. On the RPC /
    // chunk-production path it is best-effort and does not affect consensus.
    let available_balance = account.amount().saturating_sub(pending.paid_from_balance);
    if available_balance < total_cost {
        return TxVerdict::Failed(InvalidTxError::NotEnoughBalance {
            signer_id: account_id.clone(),
            balance: available_balance,
            cost: total_cost,
        });
    }
    // Debit only this tx's cost, not the pending amount (which was already
    // charged in prior chunks and will be applied at execution time).
    let new_amount = account.amount().checked_sub(total_cost).unwrap();

    let new_allowance = match check_and_compute_new_allowance(
        access_key,
        account_id,
        tx.public_key(),
        total_cost,
    ) {
        Ok(a) => a,
        Err(e) => return TxVerdict::Failed(e),
    };

    match check_storage_stake(account, new_amount, config) {
        Ok(()) => {}
        Err(StorageStakingError::LackBalanceForStorageStaking(amount)) => {
            return TxVerdict::Failed(InvalidTxError::LackBalanceForState {
                signer_id: account_id.clone(),
                amount,
            });
        }
        Err(StorageStakingError::StorageError(err)) => {
            return TxVerdict::Failed(StorageError::StorageInconsistentState(err).into());
        }
    };

    // Validate FunctionCall permission constraints if applicable
    if let Some(function_call_permission) = access_key.permission.function_call_permission()
        && let Err(e) = verify_function_call_permission(function_call_permission, tx)
    {
        return TxVerdict::Failed(e);
    }

    TxVerdict::Success(VerificationResult {
        gas_burnt,
        compute_burnt,
        gas_remaining,
        receipt_gas_price,
        burnt_amount,
        new_account_amount: new_amount,
        access_key_update: AccessKeyUpdate::Regular { nonce: tx_nonce, new_allowance },
    })
}
