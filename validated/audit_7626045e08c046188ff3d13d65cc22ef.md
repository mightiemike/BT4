### Title
Stale per-block index cache in `market.clar` is not invalidated when a vault's index moves via bad-debt socialization or a direct `accrue()` call within the same block - (File: `local-testing/contracts/market/market.clar` / `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` maintains a per-`stacks-block-time` cache of vault borrow/liquidity indexes (`index-cache`) to avoid repeated cross-contract `vault-accrue` calls within the same block. The cache is looked up purely by `{timestamp: stacks-block-time, aid: aid}` and, on a hit, is returned without re-checking whether the vault's real index has moved since the cache entry was written. [1](#0-0) 

### Finding Description
`accrue-and-cache` is the single gate market.clar uses before trusting a vault's `index`/`lindex`:
```
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)          ;; cache HIT: no re-check
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [1](#0-0) 

Every hot-path entry point (`borrow`, `repay`, `collateral-add`, `collateral-remove`, `liquidate`) relies on this cache, via `accrue-user-debts`/`accrue-user-collateral`/`accrue-and-cache`, to obtain the index used for scaled-debt math, zToken price resolution (`resolve-ztoken`), and health checks. [2](#0-1) 

The cache key is `stacks-block-time`, which is identical for every transaction mined in the same block - so the cache persists (and is trusted) across multiple, independently-ordered transactions in that block, not just within one transaction.

The vault's underlying source of truth (`index`, `lindex`, `principal-scaled`) can move within that same block through paths that do not go through `accrue-and-cache`:
- `liquidate` calls `vault-socialize-debt` (bad-debt write-off) at the very end of the transaction, after the market has already cached that vault's index earlier in the same call for health/valuation math. [3](#0-2) 
- Every vault's `accrue()` is a permissionless `define-public` function with no caller-auth guard (unlike `system-borrow`, which explicitly calls `check-caller-auth`), so it can be invoked directly by anyone, independent of market.clar, updating `index`/`lindex`/`last-update` outside of market's caching path. [4](#0-3) 

Because `index-cache` is only invalidated by the block-time changing (a new block), any transaction later in the same block that hits the cache will use the index snapshot taken by an earlier transaction, even though the vault's real index has since moved due to `socialize-debt` or a direct `accrue()` call.

### Sequence
1. Tx1 (block time T): a user action (e.g. `market.borrow`) triggers `accrue-and-cache(aid)` → cache miss → `vault-accrue(aid)` returns `{index: I0, lindex: L0}` → market stores `{T, aid} -> {I0, L0}` in `index-cache`.
2. Later in Tx1 (or a subsequent Tx2 at the same block time T), `liquidate` runs and closes out a position with `no-collateral-left`, calling `vault-socialize-debt` for `aid`, which mutates the vault's real accounting for that asset (bad-debt write-off) without touching `index-cache`.
3. Tx3, still at block time T, calls `market.borrow`/`repay`/`collateral-add`/`liquidate` for `aid`. `accrue-and-cache(aid)` sees a cache HIT for `{T, aid}` and returns the pre-socialization `{I0, L0}` instead of the vault's now-updated state.
4. All downstream computations in Tx3 (scaled-debt conversion, zToken price via `resolve-ztoken`, health checks in `is-healthy`/`is-healthy-with-mask`) are computed against the stale index, diverging from the vault's true accounting.

### Impact Explanation
Debt/collateral valuations computed from a stale, pre-socialization index can misstate a borrower's real debt or the true price of zToken collateral for the rest of the block. This can let a borrow or collateral-add pass a health check that would fail against the vault's real (post-socialization) state, or let a liquidation compute an incorrect seize/repay amount - both of which push the protocol toward under-collateralization, i.e. protocol insolvency risk, which is an in-scope Critical impact.

### Likelihood Explanation
This requires two conditions in the same block: (a) a liquidation that triggers bad-debt socialization for an asset, and (b) a second, unrelated market action on the same asset later in the same block. Both are ordinary, permissionless operations (liquidation is open to anyone with an unhealthy target; borrow/repay are routine user actions), so the precondition is realistic during periods of liquidation activity, though it depends on transaction ordering within a block, which an attacker/searcher can influence via mempool positioning.

### Recommendation
Invalidate or bypass the `index-cache` entry for an asset whenever its vault state is mutated outside the normal `accrue-and-cache` path - specifically after `vault-socialize-debt`, and consider gating/removing the permissionless `accrue()` entry point (or having market.clar re-validate against `last-update` rather than trusting a timestamp-only cache key).

### Proof of Concept
A concrete PoC would need the local Clarinet/Vitest harness (`local-testing/tests/**`) to: (1) open a borrower position that will be liquidated to zero collateral, (2) in the same simulated block, first call `market.liquidate` fully socializing bad debt for asset `aid`, having a separate market operation on `aid` execute earlier in the block to prime `index-cache`, then (3) call a second `market` action on `aid` later in the same block and assert it used the pre-socialization cached index instead of the vault's updated state. I was not able to execute this against the harness in this session; the sequence above is derived directly from the code paths cited.

**Uncertainty note:** I could not fully trace what specific accounting change `vault-socialize-debt` performs internally on `index`/`principal-scaled` (the vault source files show `socialize-debt` referenced but its body wasn't inspected in this session), so the exact magnitude of index divergence per socialization event is unverified. Given index-size limits on the available context, a Devin session with full repository access would be needed to confirm the exact state mutation inside `socialize-debt` and build a runnable PoC.
