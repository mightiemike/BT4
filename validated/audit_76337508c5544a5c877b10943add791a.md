### Title
Frequent public `accrue()` calls can permanently stall liquidity-index growth while debt index keeps rising, freezing depositor yield - ([File: mainnet/contracts/vault/v0-vault-usdc.clar] and equivalent v0-vault-{sbtc,ststx,ststxbtc,stx,usdh}.clar)

### Summary
Each vault's `accrue` recomputes `index` (debt) and `lindex` (liquidity) from `stacks-block-time - last-update`, but only advances `last-update` when *either* index changed. Because the debt-index multiplier rounds up and the liquidity-index multiplier rounds down, an unauthenticated, frequently-called `accrue()` can repeatedly tick `index` up (resetting the shared clock) while `lindex` keeps rounding down to zero growth, permanently starving depositors of their share of accrued interest — the same "clock reset without accounting for the unaccrued remainder" root cause as the RocketPool inflation report.

### Finding Description
`next-index` and `next-liquidity-index` both derive `time-delta` from the single shared `last-update` variable: [1](#0-0) 

`calc-multiplier-delta` rounds the debt-index multiplier **up** and the liquidity-index multiplier **down**: [2](#0-1) 

`accrue()` is a public, unauthenticated function. It updates `index`/`lindex` independently, but only resets the shared `last-update` clock to `stacks-block-time` if *either* value changed: [3](#0-2) 

Because `mul-div-up` yields at least `1` whenever `rate > 0` and `time-delta > 0`, `index` will tick upward on almost every call, regardless of how small `time-delta` is. That non-zero change alone is enough to trigger the `(var-set last-update stacks-block-time)` branch. Meanwhile `next-liquidity-index` uses `mul-div-down`, which floors to `0` whenever `liquidity-rate * time-delta * INDEX-PRECISION < SECONDS-PER-YEAR-BPS` — i.e. whenever the call interval is short enough relative to the (lower) liquidity rate.

Sequence:
1. Attacker (or any bot) calls `accrue()` every block (or every few seconds).
2. Each call: `time-delta` is small. `next-index` (round-up) still increases `index` by ≥1 unit → the `is-eq idx next` check is false → `last-update` is reset to the current `stacks-block-time`.
3. `next-liquidity-index` (round-down) computes a multiplier that rounds to exactly `INDEX-PRECISION` (no change) for that same short `time-delta`, so `lindex` is left untouched.
4. Because `last-update` was already reset in step 2 (driven by the *debt* index tick), the next call's `time-delta` for the liquidity index starts from zero again — the fractional liquidity accrual that would eventually have rounded up to a positive delta if left to accumulate is discarded every time, forever.
5. Debt (`index`) — and hence `total-debt`/interest actually paid by borrowers — keeps growing normally each call, and part of that interest is skimmed into `treasury-lp` via `reserve-inc`/`fee-reserve`. The remainder that should flow to depositors through `lindex` growth never materializes because the clock backing that computation is perpetually reset by the unrelated debt-index tick.

This is the "clock advanced only on change" analog: a single shared timestamp (`last-update`) is invalidated by the mutation of *one* of two dependent accumulators (`index`), stranding the unaccrued remainder of the *other* accumulator (`lindex`) exactly as `inflationCalcBlock` was reset to `block.number` in the RocketPool report, discarding the fractional interval that had not yet completed.

### Impact Explanation
This causes permanent freezing/loss of unclaimed yield for liquidity providers: the portion of borrower-paid interest that should be reflected in `lindex` growth (and thus in the redemption value of vault shares / `zft`) is systematically discarded whenever `accrue()` is called at a high frequency relative to the current liquidity rate. Any user or bot can force this cadence by simply calling the permissionless `accrue()` repeatedly (a normal, cheap public call, not a flashloan or privileged action), degrading real depositor APY below the model rate indefinitely. This matches the in-scope High impact category: theft/permanent freezing of unclaimed yield.

### Likelihood Explanation
Likelihood is moderate-to-high in low/medium utilization markets where `liquidity-rate` is small relative to `interest-rate` (liquidity rate = interest-rate × utilization × (1 − fee-reserve)), making the rounding-to-zero window wide. An attacker only needs to submit a stream of low-cost `accrue()` calls (no capital, no permission checks) to keep `time-delta` below the liquidity-index rounding threshold indefinitely, while any organic transaction that touches `accrue()` (deposit/borrow/repay/redeem) reinforces the same reset.

### Recommendation
Track `last-update` independently for the two accumulators, or only reset `last-update` when computing `time-delta` for `next-liquidity-index` if that value actually produced a nonzero delta 못했다면 retain the elapsed time for the next liquidity-index computation instead of discarding it via the shared clock. Concretely: decouple the "clock reset" condition from `index`'s change and instead accumulate un-applied liquidity time separately (or simply never rely on rounding to gate the clock advance — always advance `last-update` based on real elapsed time and separately carry any liquidity-index rounding remainder forward rather than losing it).

### Proof of Concept
1. Deploy/observe a vault (e.g. `v0-vault-usdc.clar`) with non-zero `total-borrowed` so `interest-rate`/`liquidity-rate` are nonzero, and utilization/fee-reserve such that `liquidity-rate` is comparatively low.
2. Have a bot call `accrue()` every ~1 block for an extended period (no auth required, see the public `accrue` definition at lines 833-861).
3. Observe on-chain: `index` steadily increases each call (round-up ensures ≥1 unit growth whenever `rate>0`), and `last-update` is bumped to `stacks-block-time` each time due to the `(or (not (is-eq idx next)) ...)` check.
4. Observe `lindex` stays flat across many consecutive calls because each `time-delta` window is too short for `mul-div-down` to yield a nonzero liquidity multiplier delta — verify by comparing `lindex` before/after a long burst of rapid `accrue()` calls versus a single `accrue()` call after the same wall-clock duration without intermediate calls (the latter yields a visibly higher `lindex`).
5. This demonstrates depositors receive systematically less yield (reflected via `lindex`) under high-frequency `accrue()` calling than under natural, less frequent calling patterns, for the same elapsed real time and same total interest paid by borrowers.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
