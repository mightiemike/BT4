### Title
Missing Slippage Protection in `ExchangeInjectContract` / `ExchangeWithdrawContract` Allows Front-Running of Liquidity Operations - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
java-tron's Bancor-formula token-pair exchange module lets the pool creator inject or withdraw liquidity by specifying only the desired quantity of one token (`quant`); the required/returned amount of the *other* token is computed on-chain from the current pool ratio at execution time, with no user-supplied bound. This is the same missing-min/max-reserve-ratio class of bug described in the Hifi report for `HifiProxyTarget.addLiquidity()`/`removeLiquidity()`.

### Finding Description
`ExchangeInjectContract` and `ExchangeWithdrawContract` each carry only `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no minimum/maximum bound on the paired token amount. [1](#0-0) 

By contrast, `ExchangeTransactionContract` (a trade against the pool) does carry an `expected` field that protects the trader against slippage. [2](#0-1) 

In `ExchangeInjectActuator`, the amount of the counter-token (`anotherTokenQuant`) is derived purely from the pool's current `firstTokenBalance`/`secondTokenBalance` ratio at the moment of execution, and this value is neither bounded nor confirmed against any caller-supplied limit: [3](#0-2) 

The only checks performed are that the derived amount is `> 0` and that the resulting pool balances stay under `getExchangeBalanceLimit()` — nothing constrains it to what the caller expected when they signed the transaction: [4](#0-3) 

`ExchangeWithdrawActuator` has the exact same structure: `anotherTokenQuant` is computed from the live pool ratio, and the only extra checks are balance-sufficiency and a fixed-precision rounding check ("Not precise enough") — again, no caller-specified min/max: [5](#0-4) 

Both actuators restrict the caller to the exchange's `creatorAddress` (the account that ran `ExchangeCreateContract`), which is a self-selected liquidity-provider role — not a privileged network role like a witness or committee member — so this is an unprivileged-user-facing accounting flow: [6](#0-5) 

Because a transaction's execution can be delayed relative to submission (mempool/block ordering), any account can observe a pending `ExchangeInject`/`ExchangeWithdraw` transaction and submit a competing `ExchangeTransactionContract` trade beforehand to shift `firstTokenBalance`/`secondTokenBalance`. This changes the ratio used by `ExchangeProcessor`/`ExchangeCapsule.transaction()` and therefore the `anotherTokenQuant` computed when the inject/withdraw actuator finally executes: [7](#0-6) 

The creator's inject/withdraw transaction still succeeds unconditionally (as long as `anotherTokenQuant > 0` and balances are sufficient), depositing/receiving a worse ratio than intended — this is exactly the "sufficient slippage protection" gap the Hifi report describes for `addLiquidity()`/`removeLiquidity()`.

### Impact Explanation
An attacker can front-run a liquidity provider's inject/withdraw transaction with a trade transaction to manipulate the pool ratio, forcing the LP to deposit more of the counter-token than intended on inject, or to withdraw less counter-token than intended on removal. This constitutes a value-extraction/accounting-mismatch impact against the liquidity provider, analogous to the impermanent-loss-style slippage loss flagged in the original report.

### Likelihood Explanation
Any account can create an exchange (becoming its "creator"/LP) and any account can submit competing `ExchangeTransactionContract` trades; front-running via mempool observation and transaction ordering is a well-known, low-cost technique, making exploitation practical whenever an LP submits an inject/withdraw transaction that isn't executed atomically in the same block as construction.

### Recommendation
Add explicit slippage-bound fields to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `expected_another_token_quant` with min/max bound, or separate `min_another_token_quant`/`max_another_token_quant` fields), and validate the on-chain-computed `anotherTokenQuant` against that bound in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()`, mirroring the existing `expected` slippage guard already used in `ExchangeTransactionContract`.

### Proof of Concept
1. Account C creates an exchange pool for tokens A/B via `ExchangeCreateContract`, becoming the pool creator.
2. C submits `ExchangeInjectContract` intending to inject `quant` of token A, expecting to pay a proportional amount of token B based on the current ratio.
3. Before C's transaction is included, an attacker observes it in the mempool/network and submits an `ExchangeTransactionContract` trade that shifts the A/B ratio in the pool. [8](#0-7) 
4. When C's inject transaction executes, `ExchangeInjectActuator` recomputes `anotherTokenQuant` from the now-shifted ratio and deducts a larger amount of token B from C than C expected, with no validation against C's original intent. [9](#0-8) 
5. The same scenario applies symmetrically to `ExchangeWithdrawContract`, where C receives less of the counter-token than expected.

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {

          : firstTokenBalance + sellTokenQuant;
