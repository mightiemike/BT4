### Title
Panic-inducing `unwrap()` on `receiver_shard_id()` in `receipt_filter_fn` can halt a shard after chained resharding (stale `GlobalContractDistribution` receipt) - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally unwraps the `Result` returned by `Receipt::receiver_shard_id`. This mirrors the ncurses `_nc_parse_entry` bug class: a "dubious" condition (a receipt whose `target_shard` can no longer be resolved in the current `ShardLayout`) is detected deep in `receiver_shard_id`/`resolve_to_current_shard` and surfaced as an `Err`, but the caller proceeds straight to a dereference/unwrap path instead of propagating the error, causing a deterministic panic.

### Finding Description
`Receipt::receiver_shard_id` for a `GlobalContractDistribution` receipt tries to resolve `target_shard` in the current shard layout; if the shard no longer exists (e.g. because of a resharding split), it calls `shard_layout.resolve_to_current_shard(target_shard)` and returns `Err(EpochError::ShardingError(...))` when that fails: [1](#0-0) 

That `Result` is then blindly unwrapped in the delayed-receipt filter used while draining the delayed receipt queue during normal `Runtime::apply`: [2](#0-1) 

This filter is invoked from `pop()`, which is called every time the runtime drains delayed receipts as part of ordinary chunk application: [3](#0-2) 

A `GlobalContractDistribution` receipt is created whenever any unprivileged account deploys a global contract (`DeployGlobalContract` action, `runtime/runtime/src/global_contracts.rs`), and it carries a `target_shard` field that gets forwarded shard-by-shard: [4](#0-3) 

If such a receipt is pushed to the delayed-receipt queue (e.g. because the target shard's compute budget is saturated) and the chain performs **two** resharding/shard-split events while it is delayed, `target_shard` no longer belongs to any lineage `resolve_to_current_shard` can trace, and `receiver_shard_id` returns `Err`. The `.unwrap()` in `receipt_filter_fn` then panics.

This exact scenario is exercised (and expected to panic pre-fix) by an existing regression test in the repo, which documents the mechanism directly: [5](#0-4) [6](#0-5) 

I was unable to fully confirm from the index whether `ShardLayout::resolve_to_current_shard` (in `core/primitives/src/shard_layout/v3.rs` / `mod.rs`) has already been hardened to track split history across more than one resharding generation, which would determine whether the root cause (stale `target_shard` no longer resolvable) is still reachable in this codebase snapshot, or whether only the crash symptom (the `unwrap()`) remains as a latent defensive-depth issue. The index did not return the body of `resolve_to_current_shard`, so this could not be verified with certainty.

### Impact Explanation
Since every honest, correctly-configured validator processes the same delayed-receipt queue against the same deterministic shard layout, the panic in `receipt_filter_fn` fires identically on all nodes tracking the shard — this is not a Byzantine/malicious-node bug but a deterministic crash triggerable by an ordinary sequence of protocol events (two resharding splits) following a normal, unprivileged transaction (deploying a global contract). The result is a transaction/receipt-triggered chain halt for the affected shard(s): the shard cannot make progress past the point where the stale receipt is popped from the delayed queue, since `Runtime::apply` will panic every time is is invoked with that receipt in the queue.

### Likelihood Explanation
Reaching this requires: (1) any account deploying a global contract (trivial, unprivileged), (2) the resulting distribution receipt getting stuck in the delayed queue while its target shard is saturated for at least the time needed for two shard splits to occur. Dynamic resharding is intended to run based on configured thresholds, so this is a plausible, non-adversarial sequence of events rather than something requiring a malicious validator, though it does depend on resharding cadence and receipt timing which are not directly attacker-controlled on demand.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with proper error propagation (return a `RuntimeError`/`StorageError::StorageInconsistentState`, consistent with how other delayed-receipt validation failures are handled, e.g. `process_delayed_receipts`'s `validate_receipt(...).map_err(...)` pattern) rather than panicking. Additionally, verify/fix `ShardLayout::resolve_to_current_shard` so it can trace shard lineage across arbitrarily many resharding generations, eliminating the root cause of the stale `target_shard`.

### Proof of Concept
The repository's own test reproduces the trigger conditions end-to-end:
1. Deploy a test contract and a global contract from an account in shard `S_A` (`test_stale_global_contract_distribution_after_double_resharding`, lines 94–114).
2. Saturate compute on `S_A` every block so the `GlobalContractDistribution` receipt is pushed to the delayed queue (lines 116–124).
3. Force two sequential dynamic resharding splits while the receipt stays delayed (lines 52–92, 124–163).
4. Stop saturating and let the delayed queue drain; the receipt's `target_shard` (from shard layout two generations back) is fed into `receipt_filter_fn`, which calls `receiver_shard_id(&shard_layout).unwrap()` and panics if `resolve_to_current_shard` cannot resolve it (lines 163–186). [5](#0-4)

    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,
    receipt_sink: &mut ReceiptSink,
    receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
) -> Result<(), RuntimeError> {
    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()
    else {
        return Ok(());
    };
    let already_delivered_shards = Vec::from_iter(already_delivered_shards);
    let predecessor_id = receipt.predecessor_id().clone();
    let next_receipt = global_contract_data.forward(next_shard, already_delivered_shards);
    let mut next_receipt = Receipt::new_global_contract_distribution(predecessor_id, next_receipt);
    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);
    if apply_state.save_receipt_to_tx {
        receipt_to_tx.push((
            receipt_id,
            ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: *receipt.receipt_id(),
                    parent_predecessor_id: receipt.predecessor_id().clone(),
                }),
                receiver_account_id: next_receipt.receiver_id().clone(),
                shard_id: apply_state.shard_id,
            }),
        ));
    }
    receipt_sink.forward_or_buffer_receipt(next_receipt, apply_state, state_update)?;
    Ok(())
