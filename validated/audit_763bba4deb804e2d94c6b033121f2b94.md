## Title
Slippage protection in `depositPRC20WithAutoSwap` derives its own reference price from the manipulable spot AMM quote, allowing sandwich attacks to extract value from inbound GAS/GAS_AND_PAYLOAD deposits and outbound gas refunds - (File: `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
The external report flags Convex `Harvester.sol` swaps that pass `amountOutMinimum: 0` / `min_dy: 0`, leaving no slippage protection and exposing the swap to MEV sandwiching. Push Chain's `uexecutor` module has a structurally similar swap: GAS and GAS_AND_PAYLOAD inbound deposits, and outbound gas-fee refunds, are auto-swapped from PRC20 → WPC via `UniversalCore.depositPRC20WithAutoSwap` / `refundUnusedGas` on a Uniswap V3 pool [1](#0-0) . A prior upgrade replaced a hardcoded `minPCOut = 0` with a computed `minPCOut = quote * 95 / 100` [2](#0-1) , but the "quote" used as the slippage reference is itself fetched from the same on-chain pool, at spot price, immediately before the swap executes, via `GetSwapQuote` calling `QuoterV2.quoteExactInputSingle` with `SqrtPriceLimitX96: big.NewInt(0)` (no price-impact bound) [3](#0-2) .

### Finding Description
`ExecuteInboundGas` (and the GAS_AND_PAYLOAD equivalent `gasAndPayloadDepositAutoSwap`, and the outbound gas refund path `applyGasRefund`) compute `minPCOut` from a live quote fetched right before the swap, in the same keeper call: [4](#0-3) [5](#0-4) [6](#0-5) 

Because both the "reference" quote and the actual swap read the identical, unprotected spot price of the same Uniswap V3 pool (no TWAP, no price-impact cap via `SqrtPriceLimitX96`), the 5% tolerance only guards against price movement *between the quote call and swap call*, which occurs atomically within the same message execution. It provides no protection against price manipulation that already exists in the pool *before* the inbound vote reaches quorum (or before the outbound refund is processed) — i.e., an attacker who front-runs the finalizing transaction with a large trade on the same pool inflates/deflates the spot price, the module's own quote call then reflects that manipulated price, `minPCOut` is derived from the manipulated price, and the swap "succeeds" while the module receives materially worse execution than fair value. The attacker unwinds their position afterward, extracting the difference from protocol/user-controlled funds (`ueaAddr` recipient of the deposit, or `recipientAddr` of the gas refund) at the strategy's expense — the same MEV sandwich structure described in the source report, just relocated from the Convex Harvester onto Push Chain's native cross-chain deposit/refund auto-swap path.

This is reachable by an ordinary unprivileged actor: any user can submit an ordinary inbound (GAS or GAS_AND_PAYLOAD deposit) that will eventually reach vote quorum and trigger the auto-swap, and any external party can trade against the same Uniswap V3 pool on Push Chain's EVM to manipulate its spot price just before that swap executes, since pool state and mempool ordering around the block containing the finalizing `MsgVoteInbound`/outbound observation are attacker-observable and attacker-influenceable without needing validator or TSS privileges.

### Impact Explanation
A successful sandwich causes the module to execute the PRC20→WPC (or gasToken→PC-native) swap at a manipulated price, directly reducing the amount of native PC value credited to the user's UEA on inbound GAS deposits, or the amount refunded to the sender/fund_recipient on outbound gas refunds. This is a partial, per-transaction loss of user/protocol-controlled value extracted by an unprivileged attacker via price manipulation — falling under "corruption of ... gas fee accounting, refund accounting ... token mapping" and "unauthorized ... state transitions" impact categories for value siphoned from the swap counterparty (the module acting on behalf of users).

### Likelihood Explanation
Exploitability depends on pool liquidity/depth for the specific PRC20 being swapped and on attacker capital, same as in the original report. Push Chain's own upgrade notes explicitly call out this as still a 5%-tolerance design (not a TWAP-anchored one), and the fee tiers/quoter are read directly from mutable on-chain state controlled by `UniversalCore` (`defaultFeeTier`, `uniswapV3Quoter`, `WPC`) with no additional price-deviation circuit breaker. Any inbound GAS/GAS_AND_PAYLOAD deposit or outbound gas refund that goes through the auto-swap path is a candidate target, making this a systemic, repeatable pattern rather than an edge case.

### Recommendation
Do not derive `minPCOut` solely from a spot quote fetched immediately before the swap. Instead: (1) source the reference price from a time-weighted average (TWAP) oracle over a window resistant to single-block manipulation, or (2) bound the acceptable price deviation between the TWAP and the spot quote before allowing the swap to proceed (reverting/falling back to no-swap deposit if deviation exceeds a safety threshold), and/or (3) constrain `sqrtPriceLimitX96` to cap maximum price impact rather than leaving it at 0.

### Proof of Concept
1. Attacker monitors the mempool/chain for an inbound GAS deposit (`MsgVoteInbound`) approaching quorum, or an outbound observation about to trigger a gas refund.
2. Just before the finalizing transaction lands, attacker executes a large trade on the PRC20/WPC Uniswap V3 pool referenced by `UniversalCore`, moving the spot price unfavorably for the upcoming module swap.
3. The finalizing transaction executes `GetSwapQuote` → returns the manipulated price → `minPCOut = quote * 95/100` is computed from that manipulated price [7](#0-6)  → `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` executes at the bad rate and succeeds because it clears the (already-manipulated) `minPCOut` bar.
4. Attacker reverses their trade, realizing profit equal to the value extracted from the module's swap, at the expense of the deposit recipient's UEA balance or the gas-refund recipient.

```go
// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
```
