Based on my research, I found a structurally analogous issue in the TVM precompiled contracts of java-tron.

### Title
Missing length validation before indexed word extraction in `ValidateMultiSign.execute` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `_formatProof` bug in the external report stems from extracting a fixed number of bytes from a caller-supplied array without first checking that the array is long enough. The same root-cause pattern — indexing into a `DataWord[]` array derived directly from raw call data, without confirming the array actually contains enough words — exists in `ValidateMultiSign.execute()` [1](#0-0) .

### Finding Description
`ValidateMultiSign.execute(byte[] rawData)` calls `DataWord.parseArray(rawData)`, which slices `rawData` into 32-byte words based purely on `rawData.length / WORD_SIZE` [2](#0-1) . The function then immediately indexes `words[0]`, `words[1]`, `words[2]`, and (conditionally) `words[3]` without any guard confirming the array has at least 4-5 elements [3](#0-2) .

The only length-validation guard, `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)`, is gated behind `VMConfig.allowTvmOsaka()` [4](#0-3) , meaning it is only active once the corresponding TVM upgrade (TIP-854, per test comments) is activated on the network. When this flag is off (or on any fork/testnet where it has not been activated), short `rawData` (e.g., fewer than 4 words = 128 bytes) will cause `words[0]`/`words[1]`/`words[2]`/`words[3]` to throw `ArrayIndexOutOfBoundsException`. Unlike its sibling contract `BatchValidateSign`, whose entire `doExecute` body is wrapped by an outer `try { ... } catch (Throwable t) { return Pair.of(true, new byte[WORD_SIZE]); }` in `execute()` [5](#0-4) , `ValidateMultiSign.execute()` has no such outer wrapper — only the inner permission-check block is inside a `try/catch(Throwable)` [6](#0-5) . The word-parsing and indexing lines that precede it (1057–1074) are unprotected.

### Impact Explanation
Any unprivileged user can trigger this precompile via a `CALL`/`STATICCALL` to the `ValidateMultiSign` precompiled address from a smart contract, supplying arbitrarily short calldata. Prior to TIP-854 activation, this reaches unguarded array indexing and throws an uncaught `ArrayIndexOutOfBoundsException` inside precompile execution. Whether this results only in the calling transaction/frame reverting, or propagates further up through `Program`/`OperationActions` in a way that diverges node behavior, could not be conclusively determined from the code explored — the exact exception-handling boundary in the VM's precompile dispatch path (`Program.callToPrecompiledAddress`) was not fully inspected in this session. At minimum this is an availability/DoS-adjacent defect analogous to the reported Solidity issue (unchecked slicing causing a panic/revert on malformed input), and the asymmetry with `BatchValidateSign`'s full outer try/catch strongly suggests this is an unintentional gap rather than a deliberate design choice.

### Likelihood Explanation
High likelihood of triggering: the vulnerable path is reachable by any address executing an EVM `CALL` to the `ValidateMultiSign` precompiled contract with a short input, and no special permissions are required. The condition depends on `VMConfig.allowTvmOsaka()` not yet being active for the guard to be bypassed.

### Recommendation
Move the `isValidAbiEncoding` check (or an equivalent minimum-length check) outside of the `allowTvmOsaka()` conditional so it always runs before any indexing into `words[]`, and/or wrap `ValidateMultiSign.execute()` in the same defensive `try/catch(Throwable)` pattern already used in `BatchValidateSign.execute()` to guarantee malformed calldata degrades to a graceful `DATA_FALSE`/`Pair.of(false, EMPTY_BYTE_ARRAY)` result rather than an uncaught exception.

### Proof of Concept
A contract issuing `CALL` to the `ValidateMultiSign` precompiled address with calldata shorter than 4 words (128 bytes), while `VMConfig.allowTvmOsaka()` is disabled, causes `DataWord.parseArray` to return an array with fewer than 4 elements; the subsequent `words[3].intValueSafe()` (or earlier `words[1]`/`words[2]`) access throws `ArrayIndexOutOfBoundsException` outside of any local try/catch in `execute()` [3](#0-2) . Note: I was not able to fully confirm from indexed code alone whether an outer layer in the VM call stack (e.g., `Program.callToPrecompiledAddress`) catches this exception generically for all precompiles — the existing `testTip854OuterFrameContainment` test suggests some containment exists once TIP-854 is active, but analogous coverage for the pre-activation/legacy path for `ValidateMultiSign` (as opposed to `BatchValidateSign`) was not found in the explored test files.

  public static DataWord[] parseArray(byte[] data) {
    int len = data.length / WORD_SIZE;
    DataWord[] words = new DataWord[len];
    for (int i = 0; i < len; i++) {
      byte[] bytes = Arrays.copyOfRange(data, i * WORD_SIZE, (i + 1) * WORD_SIZE);
      words[i] = new DataWord(bytes);
    }
    return words;
  }
