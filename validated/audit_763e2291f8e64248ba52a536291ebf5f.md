## Title
Backup restore path persists unverified `WriteSet`s as canonical committed state — ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

## Summary
The transaction-backup restore path reads `(txn, aux_info, txn_info, events, write_set)` tuples from a backup archive, but only reconstructs a `TransactionListWithProofV2` from `txns`, `event_vecs`, and `txn_infos` to run `verify()` against the accumulator-checkpointed `LedgerInfo`. The `write_sets` vector is carried alongside completely outside of this verified structure and is later persisted directly to `WriteSetDb` via `restore_utils::save_transactions`, without ever being hash-checked against `txn_info.state_change_hash()`.

## Finding Description
In `LoadedChunk::load` (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs:99-186`), the loader deserializes each backup record into `txn`, `aux_info`, `txn_info`, `events`, `write_set`. It then builds: [1](#0-0) 
and calls `txn_list_with_proof.verify(ledger_info.ledger_info(), Some(manifest.first_version))?`.

`TransactionListWithProof::verify` (`types/src/transaction/mod.rs:2693-2752`) checks:
- transaction hashes match `txn_info.transaction_hash()`
- the `TransactionInfoListWithProof` is proven against the accumulator root in `ledger_info`
- event root hashes match `txn_info.event_root_hash()` (only if `events` are present in the verified struct)

Nowhere in this verification is `write_set` referenced — `TransactionListWithProof`/`TransactionListWithProofV2` structurally does not carry a write set field at all, by design (it proves transactions, not outputs). This is correct for the normal on-chain "transaction list" API, whose `verify` intentionally excludes state_change_hash because it has no write set to check.

However, in the backup/restore flow, the *separately loaded* `write_sets` (deserialized straight from the untrusted backup blob) are put back together with the *verified* `txn_infos` and persisted to durable storage as if they were validated: [2](#0-1) 
`WriteSetDb::put_write_set` stores the write set keyed by version with no accompanying integrity check that `CryptoHash::hash(write_set) == txn_info.state_change_hash()`. Compare this to the executor/execution paths, where `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) explicitly performs this exact check (`write_set_hash == txn_info.state_change_hash()`) before any output is treated as matching a `TransactionInfo`. That invariant exists precisely because `TransactionInfo` is "the object we store in the transaction accumulator" (see comment at `types/src/transaction/mod.rs:2229-2230`) — i.e., it is the accumulator-committed source of truth for what the write set *should* hash to. The restore path breaks this invariant: `txn_info` is accumulator-proven, but the `write_set` bytes riding alongside it in the backup archive are never checked against `txn_info.state_change_hash()` before being written to `WriteSetDb` and (in KV-replay/pre-replay phases) fed into `state_store.calculate_state_and_put_updates` (`storage/aptosdb/src/backup/restore_utils.rs:267-275`), directly mutating the JMT/state-kv store.

This mirrors the H-10 bug class: two related pieces of data (an accumulator-verified `TransactionInfo` and an independently-sourced `write_set`) are supposed to agree, one is checked, the other is trusted implicitly and used to mutate durable state, and the mismatch is never detected.

## Impact Explanation
If the backup source (an S3/GCS bucket, or any storage backend configured via `BackupStorage`) is compromised, corrupted, or served by a malicious/misconfigured replica, an operator restoring a node from that backup will commit a corrupted `WriteSet` into `state_kv_db`/`state_merkle_db` for transactions before the `replay_from_version` cutoff — i.e., for the majority of the chain's history when doing typical partial replay (`save_before_replay_version`). The resulting node's ledger state, once loaded, no longer reflects the actual VM-computed result of those transactions, yet its `TransactionInfo`/accumulator entries were successfully "verified" against a legitimate `LedgerInfo`. This produces state that diverges from the correct VM result while still appearing to have a consistent proof chain for transaction hashes and event roots — a durable ledger corruption with no detection mechanism in this path.

## Likelihood Explanation
Exploitability depends on control over, or corruption of, the backup artifact/storage — not on-chain unprivileged access, and it requires an operator to actually run `db-restore`/`db-backup restore` against the tampered backup. It's not a remote consensus-breaking exploit, but it is a genuine local-code root cause: the verification code path that exists (`TransactionListWithProofV2::verify`) provably does not, and structurally cannot (given the type), check `write_set` integrity, while the persistence code path unconditionally trusts and writes it. I could not fully trace whether the full "phase 2" replay-via-`ChunkExecutor` path (`replay_transactions`, using `VerifyExecutionMode::NoVerify` in `coordinators/restore.rs`) re-executes and independently recomputes write sets (which would mask this for post-tree-snapshot versions) — that portion of code re-executes transactions through `AptosVMBlockExecutor`, which likely would produce fresh outputs and mask a tampered `write_set` for that segment; the confirmed-vulnerable segment is specifically the pre-replay "save directly" path (`save_before_replay_version` → `restore_handler.save_transactions`) where no execution or hash check happens at all.

## Recommendation
In `LoadedChunk::load` and/or in `restore_utils::save_transactions_impl`, before writing to `WriteSetDb`, verify for every transaction that `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` (reusing the same check as `TransactionOutput::ensure_match_transaction_info`), and abort restoration with a clear error if any mismatch is found, for both the "save before replay" and general write path.

## Proof of Concept
Conceptual (I was not able to run this in the sandbox, no execution tools available):
1. Take a legitimate transaction backup chunk file and its accompanying `(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)` proof file.
2. Keep `txn`, `txn_info`, `events` untouched for one record, but replace only the serialized `write_set` bytes for that record with an attacker-chosen `WriteSet` (e.g., crediting attacker's account balance).
3. Run `TransactionRestoreController`/`aptos db-restore transaction-backup` (or the full bootstrap flow) pointing at this tampered backup, restoring to a version at or before `replay_from_version`.
4. Observe that `LoadedChunk::load` succeeds (`txn_list_with_proof.verify` passes, since it never touches `write_set`), and `restore_handler.save_transactions` persists the tampered write set into `WriteSetDb`/state store unconditionally.
5. Query the restored DB for that account's balance — it reflects the attacker's forged value, not the actual on-chain VM-executed result, despite the node's `TransactionInfo`/accumulator "proof" for that version being intact and verifiable. [3](#0-2) [2](#0-1) [4](#0-3)

impl LoadedChunk {
    async fn load(
        manifest: TransactionChunk,
        storage: &Arc<dyn BackupStorage>,
        epoch_history: Option<&Arc<EpochHistory>>,
    ) -> Result<Self> {
        let mut file = BufReader::new(storage.open_for_read(&manifest.transactions).await?);
        let mut txns = Vec::new();
        let mut persisted_aux_info = Vec::new();
        let mut txn_infos = Vec::new();
        let mut event_vecs = Vec::new();
        let mut write_sets = Vec::new();

        while let Some(record_bytes) = file.read_record_bytes().await? {
            let (txn, aux_info, txn_info, events, write_set): (
                _,
                PersistedAuxiliaryInfo,
                _,
                _,
                WriteSet,
            ) = match manifest.format {
                TransactionChunkFormat::V0 => {
                    let (txn, txn_info, events, write_set) = bcs::from_bytes(&record_bytes)?;
                    (
                        txn,
                        PersistedAuxiliaryInfo::None,
                        txn_info,
                        events,
                        write_set,
                    )
                },
                TransactionChunkFormat::V1 => bcs::from_bytes(&record_bytes)?,
            };
            txns.push(txn);
            persisted_aux_info.push(aux_info);
            txn_infos.push(txn_info);
            event_vecs.push(events);
            write_sets.push(write_set);
        }

        ensure!(
            manifest.first_version + (txns.len() as Version) == manifest.last_version + 1,
            "Number of items in chunks doesn't match that in manifest. first_version: {}, last_version: {}, items in chunk: {}",
            manifest.first_version,
            manifest.last_version,
            txns.len(),
        );

        let (range_proof, ledger_info) = storage
            .load_bcs_file::<(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)>(
                &manifest.proof,
            )
            .await?;
        if let Some(epoch_history) = epoch_history {
            epoch_history.verify_ledger_info(&ledger_info)?;
        }

        // make a `TransactionListWithProof` to reuse its verification code.
        let txn_list_with_proof =
            TransactionListWithProofV2::new(TransactionListWithAuxiliaryInfos::new(
                TransactionListWithProof::new(
                    txns,
                    Some(event_vecs),
                    Some(manifest.first_version),
                    TransactionInfoListWithProof::new(range_proof, txn_infos),
                ),
                persisted_aux_info,
            ));
        txn_list_with_proof.verify(ledger_info.ledger_info(), Some(manifest.first_version))?;

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
