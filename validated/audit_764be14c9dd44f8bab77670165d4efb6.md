### Title
`replace_class` syscall in the Starknet OS Cairo program omits the "class is declared" check enforced by the Blockifier, allowing state/root divergence - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The reported bug class is "a caller-supplied, unvalidated reference is trusted for a critical state-mutating decision without any allow-list/declaration check." In the sequencer, the closest reachable analog is the `replace_class` syscall handling inside the Starknet OS (SNOS) re-execution program. Unlike the Rust Blockifier, which explicitly requires the target `class_hash` to be a declared class before allowing `replace_class` to succeed, the Cairo OS implementation of the same syscall performs the class-hash swap unconditionally, with an explicit `TODO` marking the missing check.

### Finding Description
Any contract can invoke the `replace_class_syscall(class_hash)` — this is reachable directly from a normal, unprivileged transaction (a contract simply calls the syscall with an attacker/caller-chosen `class_hash` felt).

In the Blockifier (used for actual block building/validation), the syscall implementation explicitly requires the class hash to correspond to a previously declared class, and even that it be Cairo1: [1](#0-0) 
and the deprecated variant does the same check by attempting to read the compiled class first: [2](#0-1) 

Both are covered by tests that confirm undeclared class hashes are rejected with an "is not declared" error: [3](#0-2) 

However, in the Starknet OS Cairo program — used to re-execute blocks and compute the committed state root/block hash for proving — the equivalent `execute_replace_class` function performs the class-hash swap in the contract state dictionary **without** verifying that the class hash was ever declared: [4](#0-3) 

The `TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` comment on line 902 confirms this check is intentionally missing/not yet implemented, and the function proceeds directly to `dict_update` on `contract_state_changes` with the caller-supplied `class_hash`, regardless of whether it corresponds to any declared class.

### Impact Explanation
This is analogous to the reported "any address can be passed" bug class: an unprivileged, unvalidated value supplied by a normal contract call (the `class_hash` argument to `replace_class_syscall`) is trusted by a critical state-transition component (the OS state/commitment computation) without the same validation that the Blockifier performs. Because the contract-class tree/global state root computed by the OS (`state.cairo`, `commitment.cairo`) is exactly what becomes the network's committed state root and feeds into the block hash, a discrepancy between what the Blockifier allows (transaction reverts on undeclared class) and what the OS accepts (silently updates state to an undeclared class hash) produces a state/root divergence between the two re-execution paths. This maps to "wrong committed root or block hash" / "honest-node divergence" — the OS-computed state (used e.g. for proof verification of block validity) can diverge from the state the Blockifier actually committed for the same block, undermining the guarantee that the OS re-execution faithfully reproduces sequencer execution.

### Likelihood Explanation
Reachability is trivial and requires no special privileges: any contract deployed by any user can call `replace_class_syscall` with an arbitrary felt as `class_hash`. The only gating factor is whether the OS is actually exercised on a code path where the corresponding Blockifier execution would have reverted the same call (i.e., a scenario where Blockifier and OS execution results are expected to be consistent but are not, due to this missing check). Given it's marked with an explicit unresolved TODO in the source, this is a known/tracked gap rather than a hypothetical one, increasing confidence that the divergence is real and unaddressed as of this snapshot.

### Recommendation
Add the same declared-class validation used in the Blockifier's `replace_class` implementation (`syscall_base.rs::replace_class` / `hint_processor.rs::replace_class`) to the OS's `execute_replace_class` function in `syscall_impls.cairo`, i.e., assert that `class_hash` exists in the OS's tracked declared/compiled class facts (mirroring `syscall_base.rs` lines 369-378) before performing the `dict_update` on `contract_state_changes`, and reject/fail the transaction otherwise, exactly matching the Blockifier's enforcement.

### Proof of Concept
1. Deploy a Cairo1 contract exposing `test_replace_class(class_hash)` (or any external entry point that issues `replace_class_syscall(class_hash)`), as already exercised in the test contract `crates/blockifier_test_utils/resources/feature_contracts/cairo1/cairo_steps_test_contract.cairo` (`test_replace_class`).
2. Submit an ordinary invoke transaction calling `test_replace_class` with an arbitrary/undeclared `class_hash` felt (e.g., `1234`).
3. In the Blockifier, this transaction reverts with "is not declared" (as demonstrated by `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs::undeclared_class_hash`), so this class-hash update is never applied to the committed state.
4. If the same transaction/trace is fed into the Starknet OS re-execution path (`execute_replace_class` in `syscall_impls.cairo`), the class-hash swap proceeds unconditionally (no equivalent declared-class assertion exists), causing the OS-computed `contract_state_changes` — and consequently the contract state root / global state root produced by `state.cairo`/`commitment.cairo` — to diverge from what the Blockifier actually committed for that block.

Note: I was unable to fully trace whether a downstream cross-check (e.g., comparing OS-derived state diffs against Blockifier-derived state diffs before the OS's proof is accepted) exists elsewhere in the pipeline that might catch this discrepancy before it becomes consequential; the codebase index available to me did not show such a check for this specific field, but a full audit of `execute_transactions.cairo`/`os.cairo`'s consistency-checking logic between Blockifier-supplied inputs and OS-computed outputs would be needed to fully rule this out.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }

// Replaces the class.
func execute_replace_class{
    range_check_ptr,
    syscall_ptr: felt*,
    contract_state_changes: DictAccess*,
    revert_log: RevertLogEntry*,
}(contract_address: felt) {
    alloc_locals;
    let request = cast(syscall_ptr + RequestHeader.SIZE, ReplaceClassRequest*);

    // Reduce gas.
    let success = reduce_syscall_gas_and_write_response_header(
        total_gas_cost=REPLACE_CLASS_GAS_COST, request_struct_size=ReplaceClassRequest.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );

    assert [revert_log] = RevertLogEntry(selector=CHANGE_CLASS_ENTRY, value=state_entry.class_hash);
    let revert_log = &revert_log[1];

    return ();
}
