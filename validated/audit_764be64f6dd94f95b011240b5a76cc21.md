Found it: incoming cross-shard receipts are validated with `validate_receipt(..., ExistingReceipt)` in `process_incoming_receipts`, and any failure is mapped straight to `RuntimeError::ReceiptValidationError` via `.map_err(RuntimeError::ReceiptValidationError)?` [1](#0-0) . That `RuntimeError` variant is explicitly turned into a hard `panic!` at the client/chain layer that calls `Runtime::apply`: `RuntimeError::ReceiptValidationError(e) => panic!("{}", e)` [2](#0-1) , and the same panic exists in the sandbox/test runtime user apply path [3](#0-2) .

### Title
Cross-shard receipt with a receipt-size (or other `ExistingReceipt`) validation failure triggers a hard `panic!` in `Runtime::apply`, causing a transaction-triggered chunk-processing halt - ([File: runtime/runtime/src/lib.rs])

### Summary
An unprivileged contract-call/receipt sender can, through a `FunctionCall` action, cause the runtime to emit a new outgoing receipt whose size exceeds `max_receipt_size` after promise/`output_data_receivers` mutation. This is a documented, known bug (nearcore issue #12606) — a "New" receipt can be validated *before* it is enlarged and thus escape the strict `NewReceipt` size check, while `try_forward` explicitly works around the oversized-receipt bug by clamping size for admission purposes [4](#0-3) . When that oversized receipt later crosses shards and is re-validated as an incoming receipt with `ValidateReceiptMode::ExistingReceipt`, the failure is converted into `RuntimeError::ReceiptValidationError` and propagated out of `Runtime::apply` [1](#0-0) . The chain-layer caller of `apply` explicitly `panic!`s on this variant [2](#0-1) , which aborts chunk application on every node that must process the receiving shard's chunk.

### Finding Description
The runtime deliberately treats `ExistingReceipt` validation (of receipts already committed to state or arriving cross-shard) as more lenient than `NewReceipt` validation, specifically *because* the codebase acknowledges a known bug (#12606) that allows constructing receipts above `max_receipt_size` [5](#0-4) . The existing test suite (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`, `test_max_receipt_size_yield_resume`) shows exactly this: a `FunctionCall` action produces a receipt that passes the initial `NewReceipt` size check, is subsequently enlarged by `output_data_receivers` or return-value wrapping, and ends up over `max_receipt_size` [6](#0-5) . The `ReceiptSink`/congestion-control code explicitly clamps such receipts for admission accounting to avoid getting them "stuck," implying they can and do get forwarded to another shard as outgoing/incoming receipts [4](#0-3) .

Once such an oversized (or otherwise `ReceiptValidationError`-triggering) receipt is delivered as an *incoming* receipt to the receiving shard, `process_incoming_receipts` re-validates it with `ValidateReceiptMode::ExistingReceipt` and, on any validation error, immediately maps it to `RuntimeError::ReceiptValidationError` and returns it from `Runtime::apply` [1](#0-0) . Every caller of `Runtime::apply` in the client/chain layer treats this specific `RuntimeError` variant as an unrecoverable condition and panics rather than gracefully rejecting the individual receipt: `RuntimeError::ReceiptValidationError(e) => panic!("{}", e)` [2](#0-1) . This is explicitly marked `// TODO(#2152): process gracefully` in the source, confirming this is recognized as unhandled/aspirational cleanup rather than intentional hard-failure behavior for a case reachable by ordinary user transactions.

Contrast this with `process_delayed_receipts`, which validates delayed receipts the same way but converts any failure into a non-fatal `StorageError::StorageInconsistentState` instead of `RuntimeError::ReceiptValidationError` [7](#0-6)  — showing the incoming-receipt path is the outlier that turns an ordinary validation failure into a process-halting panic.

### Impact Explanation
Because every validating/tracking node that applies the chunk containing the malformed incoming receipt executes the same deterministic panic, this can be triggered simultaneously across the whole validator set that tracks the receiving shard — an availability impact analogous to the CVE's "hang or frequently repeatable crash (complete DOS)". A single unprivileged transaction/contract call (deploying a contract that returns an oversized promise value or attaches an oversized `output_data_receivers` list) is sufficient to construct the malicious receipt, satisfying the "transaction-triggered halt" acceptance criterion. This is a protocol/availability bug rather than a fund-theft bug, but it directly matches the required "transaction-triggered halt" impact category.

### Likelihood Explanation
The precondition (an oversized receipt escaping `NewReceipt` validation) is not hypothetical — it is a currently tracked, reproduced bug in this codebase (issue #12606), with existing regression tests demonstrating exactly how to produce such receipts via ordinary `FunctionCall` actions [8](#0-7) . The remaining step — whether the oversized receipt is actually forwarded cross-shard as an *incoming* receipt to another shard (versus staying local) rather than being caught earlier — determines full exploitability; I could not fully trace whether `try_forward`/buffering always keeps such oversized receipts routed to `outgoing_receipts` in all congestion states, so likelihood should be treated as `Medium` pending confirmation of that specific forwarding path.

### Recommendation
Change the `process_incoming_receipts` failure branch to handle `ReceiptValidationError` the same way `process_delayed_receipts` does (or reject/skip the offending receipt and record a failed outcome) rather than propagating a `RuntimeError` variant that every current caller treats as an unconditional `panic!`. Separately, fix the root cause (#12606) so that a receipt cannot become oversized after passing `NewReceipt` validation (e.g., re-validate size after all mutations, before it is queued for cross-shard delivery).

### Proof of Concept
1. Deploy a contract (as done in `test_max_receipt_size_promise_return` / `test_max_receipt_size_value_return`) that creates a promise chain where a returned value or `output_data_receivers` list inflates the receipt above `max_receipt_size` after the initial size check passes [9](#0-8) .
2. Ensure the receiver of the resulting oversized receipt is on a different shard so it is routed through `ReceiptSink`/`try_forward` as a cross-shard receipt [10](#0-9) .
3. When the receiving shard applies its next chunk, `process_incoming_receipts` re-validates the receipt with `ExistingReceipt` mode, fails, and returns `RuntimeError::ReceiptValidationError` [1](#0-0) .
4. The chain layer's `apply_transactions` handler panics: `RuntimeError::ReceiptValidationError(e) => panic!("{}", e)` [11](#0-10) , crashing every node applying that chunk for the tracked shard.

    /// Forward a receipt if possible and return whether it was forwarded or
    /// not.
    ///
    /// This does not take `&mut self` as first argument to make lifetime
    /// management easier. Instead it takes exactly the fields it requires,
    /// namely `outgoing_limit` and `outgoing_receipt`.
    fn try_forward(
        receipt: Receipt,
        gas: Gas,
        mut size: u64,
        shard: ShardId,
        outgoing_limit: &mut HashMap<ShardId, OutgoingLimit>,
        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,
        stats: &mut ReceiptSinkStats,
    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts
        // above the size limit might not fit under the maximum outgoing size limit. Let's pretend
        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

        // Default case set to `Gas::MAX`: If no outgoing limit was defined for the receiving
        // shard, this usually just means the feature is not enabled. Or, it
        // could be a special case during resharding events. Or even a bug. In
        // any case, if we cannot know a limit, treating it as literally "no
        // limit" is the safest approach to ensure availability.
        let default_gas_limit = Gas::MAX;

        // Since bandwidth scheduler, a shard is not allowed to send any receipts if it doesn't have a grant.
        let default_size_limit = 0;

        let default_outgoing_limit =
            OutgoingLimit { gas: default_gas_limit, size: default_size_limit };
        let forward_limit = outgoing_limit.entry(shard).or_insert(default_outgoing_limit);

        let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission
            .enabled(apply_state.current_protocol_version)
        {
            gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
        } else {
            gas
        };

        if forward_limit.gas >= admission_gas && forward_limit.size >= size {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "forwarding buffered receipt");
            outgoing_receipts.push(receipt);
            forward_limit.gas = forward_limit.gas.saturating_sub(gas);
            forward_limit.size -= size;
            stats.forwarded_receipts.entry(shard).or_default().add_receipt(size, gas);

            Ok(ReceiptForwarding::Forwarded)
        } else {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "not forwarding buffered receipt");
            Ok(ReceiptForwarding::NotForwarded(receipt))
        }

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(

        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));
