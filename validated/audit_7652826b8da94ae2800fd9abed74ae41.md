## No vulnerability found for this question.

The premise fails at the cryptographic and database level. `ConsensusHash::from_ops` computes the hash as `RIPEMD160(SHA256(fork_version || burn_header_hash || opshash || total_burn_be_bytes || pox_id || prev_consensus_hashes...))`, which is a preimage that includes the sortition's actual `burn_header_hash` (the literal Bitcoin block hash), the `OpsHash` derived from the txids of every accepted burn op in that block (including the winning `LeaderBlockCommitOp`'s txid), the cumulative burn total, and the full geometric chain of ancestor consensus hashes. [1](#0-0)  For two different sortition winners to produce the same `consensus_hash`, an attacker would need either a genuine SHA256+RIPEMD160 collision or an identical `burn_header_hash`/`OpsHash`/burn total/prev-hash chain — the latter being impossible for a "different winning sortition," since a different winning commit txid changes the `OpsHash` and a Bitcoin reorg producing a different underlying block necessarily changes `burn_header_hash`.

Separately, `SortitionDB`'s `snapshots` table enforces `consensus_hash TEXT UNIQUE NOT NULL` [2](#0-1) , and lookups such as `get_sortition_id_by_consensus` / `get_block_snapshot_consensus` explicitly panic with "FATAL: multiple block snapshots for the same block with consensus hash" if this invariant were ever violated [3](#0-2) , so the database itself cannot represent two distinct sortitions sharing one `consensus_hash`.

Even setting aside the hash-collision impossibility, the block-validation path does not rely on `consensus_hash` alone to bind a block to its sortition winner. `NakamotoBlock::check_miner_signature` independently recovers the miner's public key from the block signature and compares its hash160 against the sortition's registered leader key/`miner_pk_hash` [4](#0-3) , `validate_vrf_seed` binds the block-commit's VRF seed to the parent tenure's VRF proof [5](#0-4) , and `check_nakamoto_tenure` cross-validates the tenure-change payload's `tenure_consensus_hash`, `prev_tenure_consensus_hash`, and `burn_view_consensus_hash` against canonical-fork sortition snapshots via `check_valid_consensus_hash` [6](#0-5) . These are exactly the "independent binding checks beyond the header's consensus_hash field" the question's proof idea calls for, and they already exist. Since the two sides of the claimed equality (`block.header.consensus_hash` vs. the unique authorizing sortition's `consensus_hash`) cannot diverge without breaking a cryptographic hash function or a hard DB uniqueness constraint, there is no reachable attacker-triggerable divergence.

    fn from_ops(
        burn_header_hash: &BurnchainHeaderHash,
        opshash: &OpsHash,
        total_burn: u64,
        prev_consensus_hashes: &[ConsensusHash],
        pox_id: &PoxId,
    ) -> ConsensusHash {
        // NOTE: unlike stacks v1, we calculate the next consensus hash
        // simply as a hash-chain of the new ops hash, the sequence of
        // previous consensus hashes, and the total burn that went into this
        // consensus hash.  We don't turn them into Merkle trees first.
        // We also make it so the consensus hash commits to both the transactions and the block
        // that contains them (so two different blocks with the same Blockstack-relevant transactions
        // in the same order will have two different consensus hashes, as they should).

        let burn_bytes = total_burn.to_be_bytes();
        let result;
        {
            let mut hasher = Sha256::new();

            // fork-set version...
            hasher.update(SYSTEM_FORK_SET_VERSION);

            // burn block hash...
            hasher.update(burn_header_hash.as_bytes());

            // ops hash...
            hasher.update(opshash.as_bytes());

            // total burn amount on this fork...
            hasher.update(&burn_bytes);

            // pox-fork bit vector
            write!(hasher, "{}", pox_id).unwrap();

            // previous consensus hashes...
            for ch in prev_consensus_hashes {
                hasher.update(ch.as_bytes());
            }

            result = hasher.finalize();
        }

        use ripemd::Digest;
        let mut r160 = Ripemd160::new();
        r160.update(&result);

        let mut ch_bytes = [0u8; 20];
        ch_bytes.copy_from_slice(r160.finalize().as_slice());

        ConsensusHash(ch_bytes)
    }

                  "block_header.consensus_hash" => %block_header.consensus_hash

            return Ok(None);
        }

        if tenure_payload.previous_tenure_end != block_header.parent_block_id {
            warn!("Invalid tenure-change: does not confirm parent block";
                  "previous_tenure_end" => %tenure_payload.previous_tenure_end,
                  "parent_block_id" => %block_header.parent_block_id

        let Some(tenure_sn) =

            return Ok(None);
        };

            sort_handle,
            &tenure_payload.burn_view_consensus_hash,
        )?
