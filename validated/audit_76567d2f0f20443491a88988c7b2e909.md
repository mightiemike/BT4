### Title
Live delegation.stake divergence (Split/Merge) between reward calculation and distribution triggers `assert_eq!` panic in `Bank::build_updated_stake_reward`, independent of any Meta-only mutation - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`Bank::build_updated_stake_reward` re-derives `expected_delegation` from the *live* stakes-cache entry at distribution time and compares it via `assert_eq!` to the `delegation.stake` value computed and frozen during the earlier reward-calculation phase. Because the check only inspects `delegation.stake` (never any `Meta` field), an attacker's `SetLockupChecked`/`Authorize` transaction is entirely inert to this check, while a `Split` or `Merge` transaction submitted in the same window is the sole and sufficient trigger for the panic.

### Finding Description
In `build_updated_stake_reward`, when `adjust_delegations_for_rent` is `false` (the `relax_post_exec_min_balance_check` feature inactive): [1](#0-0) 

`expected_delegation` is computed from `stake.delegation.stake` — the value looked up live from `stakes_cache_accounts` at the moment of distribution — plus the reward amount that was computed during the earlier calculation phase (`calculate_stake_rewards_and_commissions`, in `calculation.rs`). `new_stake.delegation.stake` comes from `partitioned_stake_reward.inflation.stake.delegation.stake`, which is a value frozen at calculation time (`redeem_delegation_rewards` / `redeem_rewards`, see `calculation.rs` lines 726-748). Reward calculation and reward distribution are separated by up to `REWARD_CALCULATION_NUM_BLOCKS` blocks and by however many blocks the partitioned distribution itself spans, during which the stake account remains fully mutable by its owner via ordinary `StakeInstruction`s (`Split`, `Merge`, `SetLockupChecked`, `Authorize`, etc.) — none of this window is protected by any lock on individual stake accounts.

The assert only ever inspects `delegation.stake`; it does not read or validate any `Meta` field (lockup, authorized staker/withdrawer). Consequently:
- A `SetLockupChecked` or `Authorize` transaction changes only `Meta`, leaving `stake.delegation.stake` untouched, and is invisible to this check — it neither triggers the panic nor provides any additional protection against it.
- A `Split` or `Merge` transaction changes `delegation.stake` on the live account. If it lands anywhere between the calculation snapshot and the specific distribution block that processes this stake account's partition, `stake.delegation.stake` (live, post-Split/Merge) will differ from the value implied by the frozen `new_stake.delegation.stake` (pre-Split/Merge value + reward), causing `expected_delegation != new_stake.delegation.stake` and hitting the `assert_eq!`, panicking every validator that executes this bank — a deterministic, cluster-wide halt.

The Meta-only transaction functions only as harmless "noise"/timing cover in the attacker's sequence; it does not alter the reachability, root cause, or exploitability of the panic, which is driven solely by the delegation.stake divergence from Split/Merge.

### Impact Explanation
Concrete impact is a deterministic panic in `store_stake_accounts_in_partition`/`build_updated_stake_reward` executed identically by all validators processing the same partitioned-rewards block, causing a full cluster halt (liveness/safety violation) — this matches the same root-cause class as previously identified Split/Merge scenarios; the Meta-only instruction adds no new impact and no new mitigation.

### Likelihood Explanation
Precondition is simply an active stake account under attacker control, with `relax_post_exec_min_balance_check` inactive (the described mainnet-default state for a given bank), and normal, unprivileged `Split`/`Merge` instructions available to any staker; cost is a couple of ordinary transaction fees, fully repeatable by any staker across any epoch boundary.

### Recommendation
`build_updated_stake_reward` should not `assert_eq!` a live, attacker-mutable value against a value frozen from an earlier phase; instead it should either re-derive the reward using the current live delegation as the basis (as is already done in the `adjust_delegations_for_rent = true` path) or gracefully reject/burn the reward for accounts whose delegation changed since calculation, rather than panicking the whole validator.

### Proof of Concept
Unit test extending `test_build_updated_stake_reward`:
1. Store a stake account with `delegation.stake = S` at calculation time; compute `partitioned_stake_reward.inflation.stake.delegation.stake = S + reward` (as `calculate_stake_rewards_and_commissions` would).
2. Before calling `Bank::build_updated_stake_reward`, simulate a `SetLockupChecked`/`Authorize`-only mutation on the stored account (change `Meta` only, keep `delegation.stake = S`) and assert the function still succeeds (`expected_delegation == new_stake.delegation.stake`), proving Meta changes are inert.
3. Then simulate a `Split`/`Merge` mutation that changes the live stored account's `delegation.stake` to `S' != S` (keeping Meta constant), and call `Bank::build_updated_stake_reward` with the same `partitioned_stake_reward` (still `S + reward`). Assert this call panics with "stake reward delegation must be consistent...", proving the panic trigger is solely `delegation.stake` divergence, independent of any Meta mutation.
