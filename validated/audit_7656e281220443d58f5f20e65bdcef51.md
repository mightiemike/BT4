### Title
Replay-verify integrity check omits state-checkpoint (JMT) root validation, allowing corrupted state to pass verification — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by the chunk-executor's `verify_execution` path and by `db-tool`'s `replay-on-archive`/`replay-verify` to confirm that a locally re-executed transaction matches the trusted, ledger-info-signed `TransactionInfo` fetched from a backup archive. It checks status, gas used, write-set hash, and event root hash, but never compares `txn_info.state_checkpoint_hash()` (or the hot/position state checkpoint hashes) against any locally recomputed state root. [1](#0-0) 

### Finding Description
The `TransactionInfo` accumulator leaf embeds `state_checkpoint_hash`, the JMT root produced by applying a checkpoint transaction's writes — this is the field that authenticates the entire ledger state under the signed `LedgerInfo`. When verifying a replayed chunk, `verify_execution` calls `DoGetExecutionOutput::by_transaction_execution` to get raw VM `TransactionOutput`s and then calls `ensure_match_transaction_info` per transaction — it does **not** invoke `DoStateCheckpoint`/`DoLedgerUpdate` to recompute a state-tree root for comparison, and `ensure_match_transaction_info` itself performs no such comparison at all. [2](#0-1) 

The function's own comment acknowledges the gap for hot-state/position-state roots but the more fundamental fact is that even the baseline `state_checkpoint_hash` is unchecked in this comparator: [3](#0-2) 

This same function is the authoritative correctness gate for two production tools that operators rely on to validate that state restored/replayed from backups matches the canonical, signed chain history:
- `db-tool replay-on-archive` (`execute_and_verify`), used to validate an archive DB against re-execution. [4](#0-3) 
- `db-tool replay-verify` / `ReplayVerifyCoordinator`, run against downloaded backups before trusting a restored DB. [5](#0-4) 

Because the write set determines the resulting state given a correct base state, matching write-set hashes normally implies a matching state root — but this assumption silently breaks whenever the checkpoint hash itself is what's corrupted or misapplied (e.g., a bug in JMT/state-summary update logic in `DoStateCheckpoint`, in hot-state or position-state summary construction, or in how a restored/base state is reconstructed from a backup). None of those failure modes are covered by write-set/event equality checks, since `verify_execution` never re-derives or checks a state-tree root at all. [6](#0-5) 

### Impact Explanation
This breaks the intended proof/commitment invariant that replay-verify tooling exists to enforce: that a state root reconstructed from a backup matches the corresponding root authenticated in the accumulator/`LedgerInfo`. A defect elsewhere in the state-checkpoint pipeline (JMT construction, hot-state, position-state, or a restore-path bug that reinterprets committed writes into a different state) would produce a `TransactionOutput` whose write set/events still hash-match the trusted `TransactionInfo`, yet whose actual resulting state tree is wrong — and `ensure_match_transaction_info` would report success regardless. Operators trusting `replay-verify`/`replay-on-archive` as an integrity guarantee for bootstrapping or auditing archive/full nodes from backups could accept and continue serving a divergent, corrupted state root without detection. This directly matches the "restore paths must preserve deterministic proof binding" and "committed state that differs from the correct VM result" impact classes.

### Likelihood Explanation
This is not a hypothetical edge case requiring adversarial input — the check is structurally absent for every checkpoint transaction processed by these tools, and the gap is called out in the code's own TODO comment, confirming the maintainers are aware `state_checkpoint_hash`-class validation is missing. Any independent bug in the state-checkpoint/restore machinery (which is exactly the kind of subtle logic this task is scoped to scrutinize: JMT, restore helpers, versioned state views) would go undetected specifically because this is the last line of defense meant to catch it. The likelihood of the *comparator failing to catch a real divergence* is therefore high whenever such a divergence exists; it does not require the verifier to be malicious.

### Recommendation
Extend `ensure_match_transaction_info` (or the call sites in `chunk_executor::verify_execution` / `replay_on_archive::execute_and_verify`) to actually recompute the resulting state-checkpoint root (and hot/position roots when applicable) via `DoStateCheckpoint` for checkpoint transactions, and assert equality against `txn_info.state_checkpoint_hash()` (and the corresponding hot/position fields) before declaring the replayed chunk verified.

### Proof of Concept
Not independently reproducible from static analysis alone — the exploit requires an underlying state-computation defect (in JMT construction, hot-state summary, or restore path) whose only failure signature is a wrong state root while write set/events remain correct. What is directly verifiable from the code is the structural fact that:
1. `verify_execution` never calls `DoStateCheckpoint`, so no state root is computed during replay verification. [7](#0-6) 
2. `ensure_match_transaction_info` never reads `txn_info.state_checkpoint_hash()`. [1](#0-0) 

I could not further verify at what point (if any) in production node bootstrap (as opposed to the `db-tool` operator utilities) a state root recomputed during restore is cross-checked against the signed `TransactionInfo.state_checkpoint_hash`; this would require examining `storage/backup/backup-cli` state-snapshot restore and bootstrap flows in more depth than the available iterations permitted. If such a check exists in the mainline consensus/execution commit path (not just these auditing tools), the practical severity of this finding would be reduced to "tooling-only" rather than a consensus-affecting issue, and this should be confirmed before treating this as fully independent of the `replay-verify`/`replay-on-archive` operator tools.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
