## Title
Uncaught `ArithmeticException` from static `subtractExact`/`addExact` in `MarketSellAssetActuator.matchSingleOrder` bypasses the actuator's declared catch list, mirroring the "unhandled external-call revert locks all downstream access" bug class - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
The original finding is about `JBChainlinkV3PriceFeed.currentPrice()` calling `feed.latestRoundData()` with no `try/catch`, so any revert from an external/oracle dependency propagates uncontrolled and can permanently deny access to price data used by downstream logic. The closest reachable analog in java-tron is the TRC10/TRX exchange "market" order-matching path in `MarketSellAssetActuator`, which is the closest thing java-tron has to an on-chain "price" computation invoked from an anonymous, unprivileged broadcast transaction (`MarketSellAssetContract`).

### Finding Description
`MarketSellAssetActuator.execute()` wraps its logic in a narrow catch list: [1](#0-0) 
only `ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, and `ContractValidateException` are caught and converted into a controlled `ContractExeException`/failed-tx result.

Inside the price/quantity matching path (`matchOrder` → `matchSingleOrder`), quantity accounting uses `addExact`/`subtractExact`-style exact arithmetic helpers that throw the unchecked `ArithmeticException` on overflow: [2](#0-1) 
`ArithmeticException` is a `RuntimeException` and is **not** in the actuator's catch list, so it is not converted to a normal failed-transaction outcome the way `ContractValidateException` is — it propagates out of `execute()` uncaught by the actuator's own defensive boundary, analogous to how `latestRoundData()`'s revert propagates uncaught out of `currentPrice()` in the Chainlink report.

Some computation paths were later hardened defensively (e.g. `MarketUtils.multiplyAndDivide` explicitly catches `ArithmeticException` and falls back to `BigInteger`, and a `SafeExchangeProcessor`/hardened mode exists for the separate TRX/token `Exchange` feature), which confirms the project itself recognizes unhandled-arithmetic-exception-during-actuator-execution as a real, previously-addressed risk class: [3](#0-2) [4](#0-3) 
However, the `matchSingleOrder` balance-accounting arithmetic in `MarketSellAssetActuator` itself is not routed through such guarded helpers, and the actuator's outer `execute()` catch list does not include `ArithmeticException`.

### Impact Explanation
If an uncaught `ArithmeticException` (or any other unchecked exception) escapes `MarketSellAssetActuator.execute()` during block replay, the outcome depends on how the caller of `actuator.execute()` (transaction/block processing) treats unchecked exceptions versus the checked `ContractExeException`/`ContractValidateException` it expects. I was not able to fully confirm in this session (ran out of tool iterations) whether the block-processing call site wraps `actuator.execute()` in a broad `catch (Throwable)`/`catch (Exception)` that would safely convert this into a normal failed transaction, or whether it would propagate further and potentially abort block application on a node (a `latestRoundData`-style "permanent lock" analog — one node/all nodes failing to apply an otherwise-valid block containing such an order, which is a consensus-availability risk). This is the key open question that determines whether this is a low-severity local revert or a network-halting DoS.

### Likelihood Explanation
Reaching `matchSingleOrder` requires only broadcasting a `MarketSellAssetContract` transaction that matches against an existing maker order — this is fully reachable by any unprivileged account, no special permissions needed. Triggering the specific overflow requires crafting sell/buy token quantities (and existing order-book state) such that the intermediate multiplication in the exact-arithmetic accounting overflows a `long`; this requires large but still representable magnitudes (java-tron's own hardened-mode tests target similar overflow scenarios, e.g. `Long.MAX_VALUE - 5L` balances in `ExchangeTransactionActuatorTest`), so it is plausible but not trivially demonstrated without further testing.

### Recommendation
1. In `MarketSellAssetActuator.matchSingleOrder`/`matchOrder`, route all exact-arithmetic quantity accounting through the already-existing hardened helpers (e.g. `MarketUtils.multiplyAndDivide`'s BigInteger-fallback pattern, or a `SafeExchangeProcessor`-style wrapper) instead of raw exact-arithmetic calls that can throw uncaught.
2. Add `ArithmeticException` (or a broader `RuntimeException` catch) to `MarketSellAssetActuator.execute()`'s catch clause so any unexpected arithmetic failure is converted into a deterministic `ContractExeException`/failed transaction rather than an unhandled exception, consistent with how `ExchangeInjectActuator`/`ExchangeWithdrawActuator` already catch `ArithmeticException` explicitly: [5](#0-4) 
3. Confirm/verify at the block-processing call site that any actuator exception (checked or unchecked) is caught and converted to a failed-transaction result without aborting block application, to guarantee this cannot become a consensus-halting DoS.

### Proof of Concept
Not independently verified end-to-end in this session due to tool-call limits. The reasoning path is: (1) attacker/any account creates a large maker order via `MarketSellAssetActuator`, (2) attacker broadcasts a taker `MarketSellAssetContract` transaction whose matching quantities cause the exact-arithmetic calls in `matchSingleOrder` (lines 426-482) to overflow, (3) the resulting `ArithmeticException` is not caught by `execute()`'s catch list (lines 152-159), so it propagates uncaught. Confirming actual node-level impact would require tracing the exact call site that invokes `actuator.execute()` in transaction/block processing (not located within the available iterations) to determine whether it degrades gracefully to a failed transaction or causes broader block-application failure.

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
