### Title
Missing upper-bound validation of `max_price_per_unit` in `pack_resource_bounds` allows felt overflow / packing collisions during OS transaction-hash re-execution - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/transaction_hash/transaction_hash.cairo`)

### Summary
`pack_resource_bounds` in `transaction_hash.cairo` bounds-checks `max_amount` (`assert_nn_le(resource_bounds.max_amount, 2**64 - 1)`) but only checks `assert_nn(resource_bounds.max_price_per_unit)` for `max_price_per_unit`, with no corresponding upper-bound assertion (e.g., `< 2**128`) before it is combined via `* 2**128` with the other packed fields: [1](#0-0) 

This mirrors the reported bug class: a value that is shifted/multiplied into a packed field without validating that it stays within its allotted bit-width, enabling different logical inputs to collide in the packed representation once the field modulus is reached.

### Finding Description
`pack_resource_bounds` packs `resource`, `max_amount`, and `max_price_per_unit` into one felt as:
`(resource * 2**64 + max_amount) * 2**128 + max_price_per_unit` [2](#0-1) 

`max_amount` is explicitly restricted to `< 2**64` before packing, but `max_price_per_unit` is only checked to be non-negative — there is no `assert_nn_le(max_price_per_unit, 2**128 - 1)` (or similar) guaranteeing it stays under the `2**128` multiplier used for the higher fields. Because Cairo felts are field elements modulo a prime `P` (~2**251), if `max_price_per_unit` were allowed to reach or exceed `2**128`, the packed output would wrap into the bits reserved for `max_amount`/`resource`, producing the same packed felt for different `(resource, max_amount, max_price_per_unit)` triples. This packed value directly feeds `hash_fee_fields`, which is Poseidon-hashed into the account/L1-handler transaction hash: [3](#0-2) 

This function runs inside the Starknet OS during transaction-hash re-execution/verification, which is one of the explicitly in-scope reachable paths (transaction hashing and fields, Starknet OS re-execution).

Whether this is practically exploitable depends on whether any code path can present the OS with a `max_price_per_unit` felt `>= 2**128` prior to this packing call. On the Rust/blockifier side, `GasPrice`/`ResourceBounds.max_price_per_unit` is backed by a `u128` [4](#0-3) , which structurally cannot exceed `2**128 - 1`, so the gateway-validated, RPC-deserialized transaction object cannot carry an out-of-range value through the normal transaction-fields path. I was not able to fully confirm (given tool-call limits) whether every entry point that constructs the `ResourceBounds*` array consumed directly by the Cairo `hash_fee_fields`/`pack_resource_bounds` functions in the OS program enforces the same `u128` bound before invoking this Cairo code, or whether the OS treats these as raw felts read from program input without re-deriving the `u128` bound from the transaction's own signed fields.

### Impact Explanation
If `max_price_per_unit` could reach the OS packing function without an enforced `< 2**128` bound, two distinct resource-bound sets could produce an identical packed felt and therefore an identical `hash_fee_fields` output and final transaction hash. Since the transaction hash is what account contracts sign over, this would let logically different fee terms be substituted without changing the hash/signature validity — a hash-collision/underflow class bug that could enable honest-node divergence between how the hash was computed off-chain (e.g., by the sequencer/gateway using bounded `u128` values) and how it's re-derived in the Starknet OS if the OS ever operates on wider felt inputs, undermining the guarantee that a specific set of resource bounds is what was actually signed and charged.

### Likelihood Explanation
Likelihood is low-to-uncertain given confirmed evidence: the primary and best-understood ingress path (`starknet_api::transaction::fields::ResourceBounds`) constrains `max_price_per_unit` to `u128`, matching the `2**128` packing boundary exactly, so no overflow is reachable through that path. The residual risk is confined to any OS-internal re-derivation of `ResourceBounds` from raw program input felts that bypasses the `u128`-typed Rust struct — this could not be conclusively ruled in or out within the available investigation.

### Recommendation
Add an explicit upper-bound assertion on `max_price_per_unit` in `pack_resource_bounds`, symmetric to the existing `max_amount` check, e.g. `assert_nn_le(resource_bounds.max_price_per_unit, 2**128 - 1)`, so the packing function is self-contained and does not rely on upstream Rust types to guarantee felt-width invariants.

### Proof of Concept
Not independently constructible without confirming an OS entry point that supplies `max_price_per_unit >= 2**128` as a raw felt bypassing the `u128`-typed `ResourceBounds` struct; this gap could not be closed with the available read-only tools in the time allotted. Given this open question, treat this finding as an unconfirmed/likely-defense-in-depth issue rather than a proven exploitable vulnerability.

// Packs the given resource bounds in a single felt.
func pack_resource_bounds{range_check_ptr}(resource_bounds: ResourceBounds) -> felt {
    assert_nn_le(resource_bounds.max_amount, 2 ** 64 - 1);
    assert_nn(resource_bounds.max_price_per_unit);
    return (resource_bounds.resource * 2 ** 64 + resource_bounds.max_amount) * 2 ** 128 +
        resource_bounds.max_price_per_unit;
}

func hash_fee_fields{range_check_ptr, poseidon_ptr: PoseidonBuiltin*}(
    tip: felt, resource_bounds: ResourceBounds*, n_resource_bounds: felt
) -> felt {
    alloc_locals;

    let (local data_to_hash: felt*) = alloc();
    assert data_to_hash[0] = tip;
    assert_nn_le(tip, 2 ** 64 - 1);

    static_assert L1_GAS_INDEX == 0;
    static_assert L2_GAS_INDEX == 1;
    static_assert L1_DATA_GAS_INDEX == 2;

    with_attr error_message("Invalid number of resource bounds: {n_resource_bounds}.") {
        assert n_resource_bounds = 3;
    }

    // L1 gas.
    let l1_gas_bounds = resource_bounds[L1_GAS_INDEX];
    assert l1_gas_bounds.resource = L1_GAS;
    assert data_to_hash[1] = pack_resource_bounds(l1_gas_bounds);

    // L2 gas.
    let l2_gas_bounds = resource_bounds[L2_GAS_INDEX];
    assert l2_gas_bounds.resource = L2_GAS;
    assert data_to_hash[2] = pack_resource_bounds(l2_gas_bounds);

    // L1 data gas.
    let l1_data_gas_bounds = resource_bounds[L1_DATA_GAS_INDEX];
    assert l1_data_gas_bounds.resource = L1_DATA_GAS;
    assert data_to_hash[3] = pack_resource_bounds(l1_data_gas_bounds);

    let (hash) = poseidon_hash_many(n=n_resource_bounds + 1, elements=data_to_hash);
    return hash;
}
