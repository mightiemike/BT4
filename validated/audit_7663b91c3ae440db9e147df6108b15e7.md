## Title
Replay-verification comparator omits state/hot-state/position checkpoint-hash checks, allowing state-root divergence to go undetected — (File: `types/src/transaction/mod.rs`, function `TransactionOutput::ensure_match_transaction_info`)

### Summary
The invariant reduced from the external report is: *"a function that is trusted to gate an authorized/committed action must validate all fields relevant to that authorization, not just a subset."* On Aptos, the analogous invariant is that replay/verification code which asserts a locally re-executed transaction matches the canonical, consensus-committed `TransactionInfo` must check **every** commitment field carried in that `TransactionInfo` — not just the write-set and event hashes. `TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  checks `status`, `gas_used`, `write_set` hash, and `event_root_hash`, but explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` on `TransactionInfoV1`, as called out in its own TODO comment.

### Finding Description
`ensure_match_transaction_info` is the sole correctness gate used by the chunk-executor's replay-verification path, `verify_execution`, in [2](#0-1) . That function re-executes a range of transactions locally, and for each output calls `ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` — it does **not** call `DoStateCheckpoint`/`DoLedgerUpdate` to recompute and compare state, hot-state, or native-position Merkle roots against the trusted `TransactionInfo` obtained from a backup or from an already-verified epoch-ending ledger info.

The same comparator is reused by other authenticated-replay call sites:
- `aptos-debugger`'s `print_mismatches`, [3](#0-2) 
- the CLI replay/simulation path, [4](#0-3) 

The code itself documents the gap: [5](#0-4) 
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```
This is a state-commitment binding gap analogous to the reported "missing ownership check": the function is trusted (by callers doing replay/backup verification) to fully authenticate that local re-execution matches the canonical committed ledger state, but it only authenticates a subset of the commitment fields. `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are precisely the fields that bind the Jellyfish Merkle state root, hot-state root, and (once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` ships) the native-position state root into the transaction accumulator (see `TransactionInfo::builder_v1`, [6](#0-5) , and the feature description at [7](#0-6) ). Skipping them means a divergence purely in the state-root computation (e.g., a bug in JMT construction, hot-state promotion logic, or native-position extension logic that does not manifest as a different write-set hash) is invisible to `ensure_match_transaction_info`.

### Impact Explanation
This falls squarely in the required "Hard-fork-only divergence during commit, replay, restore, or proof verification" category. Replay-verification (`verify_execution_mode`, used by chunk-executor verify and `db-tool replay-verify`/`replay_on_archive`) is the safety mechanism that is supposed to catch exactly this class of bug before/while auditing historical or backup data, or before enabling new state-root features on mainnet. Because the comparator silently omits the checkpoint-hash fields, a corrupted or non-deterministic state root (main state, hot state, or the new native-position state once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on) can pass replay verification even though the locally computed ledger state differs from the authenticated one committed to the transaction accumulator. This can mask a genuine consensus/state divergence (a hard fork condition) from the tooling operators rely on to detect it.

### Likelihood Explanation
The gap is unconditionally present today in `ensure_match_transaction_info` (it always skips these fields, regardless of feature flags), and is exercised whenever `verify_execution_mode.should_verify()` is used by the chunk executor, or whenever `aptos-debugger`/CLI replay tooling compares against a trusted `TransactionInfo`. It requires no privileged access, malicious peer, or governance action to trigger — it is a passive verification blind spot. The comment shows the maintainers are aware and intend to close it "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS," confirming it is currently unclosed and reachable via mainline replay/backup-verification code paths that exist independent of that specific feature flag (main state and hot-state checkpoint hashes are already produced on `TransactionInfoV1` today).

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when applicable) `position_state_checkpoint_hash` between the locally computed `TransactionInfo` (or an equivalent freshly computed checkpoint output) and the `txn_info` parameter, failing verification on mismatch just as it does for `write_set`/`event_root_hash`. Since `TransactionOutput` alone doesn't carry state-checkpoint hashes, this likely requires passing the freshly computed `TransactionInfo`/`StateCheckpointOutput` into the comparator (or adding a companion check in `verify_execution`/`db_bootstrapper`/CLI replay call sites) rather than only comparing `TransactionOutput` fields.

### Proof of Concept
Code-level proof (no exploit harness needed — the omission is directly visible in source and reachable from the one authoritative comparator used by replay tooling):
1. `execution/executor/src/chunk_executor/mod.rs::verify_execution` re-executes a chunk and calls only `ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` for correctness — no state-root recomputation/comparison occurs in this function. See [8](#0-7) .
2. `ensure_match_transaction_info` in `types/src/transaction/mod.rs` compares only `status`, `gas_used`, `write_set` hash, `event_root_hash`; the trailing TODO explicitly states checkpoint hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are not compared. See [1](#0-0) .
3. Consequently, any hypothetical state-root computation bug (unrelated to the write set encoding itself) that produces a wrong `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` will not cause `verify_execution`, `aptos-debugger::print_mismatches`, or the CLI replay tool to report a mismatch, even though these tools are the designated safety net for detecting exactly such divergence during backup verification and replay.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
