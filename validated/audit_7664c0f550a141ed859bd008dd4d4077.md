### Title
Legacy `ExchangeCapsule.transaction` allows negative-balance / over-100% extraction from an Exchange pool via the Bancor curve tail - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
When `allowHardenExchangeCalculation` is disabled (the default/legacy path), `ExchangeCapsule.transaction()` computes `newFirstTokenBalance`/`newSecondTokenBalance` with the plain `-`/`+` operators and only checks for negativity when `hardenedCalc` is true. Because the underlying Bancor-style formula in `ExchangeProcessor.exchange` can, for an extreme sell quantity, return a `buyTokenQuant` slightly larger than the entire opposite-side reserve, the legacy path both pays out more of the counter-asset than the pool holds and persists a negative reserve into `ExchangeStore`/`ExchangeV2Store`.

### Finding Description
`ExchangeCapsule.transaction()` guards against negative resulting balances only when `hardenedCalc` is true: [1](#0-0) . In the legacy branch (`hardenedCalc == false`, which is the default unless `allowHardenExchangeCalculation` is enabled — see `allowHarden()` used in `ExchangeTransactionActuator.execute`/`doValidate`) the balances are updated with plain `long` arithmetic and no bound/negativity check, and the resulting capsule is unconditionally persisted via `Commons.putExchangeCapsule` [2](#0-1) .

The bonding-curve math itself (`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`) uses exponents `0.0005` and `2000` whose product is exactly `1`, making the two stages near-inverses only for small trades relative to pool size. Algebraically, letting `r = sellTokenQuant/(sellTokenBalance+sellTokenQuant)`, the resulting `buyTokenQuant` returned to the trader equals `buyTokenBalance * ((1/(2-(1+r)^0.0005))^2000 - 1)`. As `r → 1` (i.e., an attacker sells a quantity of the sold asset that is many orders of magnitude larger than the pool's opposing-side reserve for that asset), this expression asymptotically approaches `buyTokenBalance * 1.0011...`, i.e., **more than 100% of the buy-side reserve**. Reaching `r` close to 1 only requires the attacker to hold and sell a very large amount of some asset (e.g., a self-issued TRC10 with a large total supply, which is cheap/free to create in bulk) against a pool whose opposing-side reserve is comparatively thin — no special privilege is required [3](#0-2) .

`doValidate()` in the actuator does not perform any check that would catch this: it only enforces `tokenQuant > 0`, `tokenExpected > 0`, `firstTokenBalance/secondTokenBalance != 0`, an upper `balanceLimit` on the *sold*-side balance after the trade, and that the trader actually holds `tokenQuant` of the sold asset — there is no check on the resulting *opposite*-side balance staying non-negative for the legacy path [4](#0-3) . Because `execute()` re-fetches a fresh `ExchangeCapsule` and calls `transaction()` again (the `validate()`-time computation is discarded), the mutation that actually gets persisted is the one from `execute()`, with no additional safety net.

The immediate consequence occurs in the very same `execute()` call: the attacker's account is credited `anotherTokenQuant` (via `accountCapsule.setBalance`/`addAssetAmountV2`) even though that amount exceeds what the pool's opposite-side reserve actually holds, and the corrupted (negative) reserve is written into both `ExchangeStore` and `ExchangeV2Store` [5](#0-4) . This is a real, unprivileged over-extraction: the attacker walks away from a single `ExchangeTransactionContract` with more of the counter-asset than was ever deposited by anyone, and the exchange pool is left in an impossible negative-reserve state, which can then further corrupt subsequent `ExchangeTransactionContract`/`ExchangeWithdrawContract` calls against the same exchange (since `firstTokenBalance`/`secondTokenBalance` are treated as trusted non-negative quantities throughout the codebase, e.g. `ExchangeWithdrawActuator`'s subtraction of withdrawn amounts from these fields).

### Impact Explanation
An unprivileged attacker can drain more value than was ever deposited into an `Exchange`, up to roughly 0.1% of the pool's opposite-side reserve per abusive trade, by exploiting the tail behavior of the Bancor curve combined with the missing negativity guard on the legacy (non-hardened) calculation path. This is a direct value-theft / value-duplication bug affecting any TRC10/TRX exchange pool that has not benefited from `allowHardenExchangeCalculation` being enabled, and it leaves persistent corrupted (negative) state in `ExchangeStore`/`ExchangeV2Store` that can compound further inconsistencies in later `ExchangeTransactionContract`/`ExchangeWithdrawContract` operations on the same pool.

### Likelihood Explanation
Requires only: (1) `allowHardenExchangeCalculation` disabled — the legacy default, (2) an `ExchangeCreateContract` (or an existing thin-reserve exchange) — creatable by anyone, (3) a large quantity of some token to sell — trivially obtainable via a cheap self-issued TRC10 with a large total supply, and (4) a single `ExchangeTransactionContract` selling that asset against the exchange. No admin, governance, or off-chain access is needed, and the exploit is repeatable against any exchange with a thin enough opposing reserve relative to the attacker's sellable supply.

### Recommendation
Apply the same `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard (throwing `ContractValidateException`) unconditionally, regardless of `hardenedCalc`, in `ExchangeCapsule.transaction()`; i.e., remove the `hardenedCalc &&` qualifier on the check at chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:160, or better, make `allowHarden()` mandatory (deprecate/remove the legacy unguarded path) and additionally clamp/reject trades whose curve output would exceed the counter-side reserve at the `Processor` level.

### Proof of Concept
Java unit test (add to `framework/src/test/java/org/tron/core/actuator/ExchangeTransactionActuatorTest.java` or a new `ExchangeCapsuleTest`):

```java
@Test
public void legacyTransactionCanProduceNegativeBalance() throws Exception {
  // Do NOT enable allowHardenExchangeCalculation (hardenedCalc=false, legacy path)
  ExchangeCapsule exchange = new ExchangeCapsule(
      ByteString.copyFrom(ownerAddress), 1, 1_000_000,
      "sellToken".getBytes(), "buyToken".getBytes());
  // Thin opposite reserve vs. attacker's massive sell quantity
  exchange.setBalance(/*firstTokenBalance (sell side)*/ 1_000L,
                       /*secondTokenBalance (buy side)*/ 1_000_000L);

  long hugeSellQuant = 1_000_000_000_000_000L; // attacker-controlled huge quant of self-issued asset
  long buyTokenQuant = exchange.transaction(
      "sellToken".getBytes(), hugeSellQuant, /*useStrictMath*/ true, /*hardenedCalc*/ false);

  // Assert the pool's opposite-side balance has gone negative -
  // an impossible state that the hardened path would have rejected.
  Assert.assertTrue("buyTokenQuant exceeds pool reserve, causing negative balance",
      exchange.getSecondTokenBalance() < 0);

  // Contrast: same scenario with hardenedCalc=true must throw instead of corrupting state.
  ExchangeCapsule exchange2 = new ExchangeCapsule(
      ByteString.copyFrom(ownerAddress), 2, 1_000_000,
      "sellToken".getBytes(), "buyToken".getBytes());
  exchange2.setBalance(1_000L, 1_000_000L);
  try {
    exchange2.transaction("sellToken".getBytes(), hugeSellQuant, true, true);
    Assert.fail("Hardened path should reject the trade that drives balance negative");
  } catch (ContractValidateException e) {
    Assert.assertEquals("Exchange balance must be >=0 after transaction", e.getMessage());
  }
}
```

Follow-up integration test via `ExchangeTransactionActuator` (legacy mode, `allowHardenExchangeCalculation=0`): create an exchange with a thin reserve, fund the attacker account with a huge TRC10 balance of the sold asset, submit `ExchangeTransactionContract` with `tokenQuant = hugeSellQuant`, `validate()`+`execute()`, then assert: (a) `ret.getInstance().getRet() == SUCESS`, (b) the attacker's account balance/asset for the bought token increased by `anotherTokenQuant`, and (c) `exchangeCapsule.getSecondTokenBalance() < 0` after re-reading from `ExchangeStore`/`ExchangeV2Store`, demonstrating the payout was not backed by real deposits and the exchange state is corrupted.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
