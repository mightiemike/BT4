## Title
Divide-before-multiply in `BucketStorage::allocate_to_fill_page` can under-allocate a bucket-map data file and trip a hard `assert!`, panicking the validator - (File: `bucket_map/src/bucket_storage.rs`)

## Summary
`allocate_to_fill_page` computes the page-aligned byte size for a bucket-map storage file using a chained `divide-then-multiply-then-divide-then-multiply` expression. When `cell_size` is not a "nice" divisor of the page size, this ordering can produce a rounded byte count smaller than what was requested, and the function relies on a runtime `assert!` rather than a proven mathematical invariant to catch this.

## Finding Description
`allocate_to_fill_page` is used whenever the bucket map (Solana's on-disk secondary AccountsIndex storage, used under `IndexLimit::Threshold`) grows an index or data bucket with an *actual* requested capacity (`Capacity::Actual`), as opposed to the default power-of-two capacity path: [1](#0-0) 

```rust
fn allocate_to_fill_page(capacity: &mut Capacity, cell_size: u64) -> u64 {
    let mut bytes = capacity.capacity() * cell_size;
    if let Capacity::Actual(_) = capacity {
        const PAGE_SIZE: u64 = 4 * 1024;
        let full_page_bytes = bytes / PAGE_SIZE * PAGE_SIZE / cell_size * cell_size;
        if full_page_bytes < bytes {
            let bytes_new = ((bytes / PAGE_SIZE) + 1) * PAGE_SIZE / cell_size * cell_size;
            assert!(
                bytes_new >= bytes,
                "allocating less than requested, capacity: {}, bytes: {bytes}, bytes_new: {bytes_new}, full_page_bytes: {full_page_bytes}",
                capacity.capacity()
            );
            assert_eq!(bytes_new % cell_size, 0);
            bytes = bytes_new;
            *capacity = Capacity::Actual(bytes / cell_size);
        }
    }
    bytes
}
```

The classic divide-before-multiply bug class applies here: `bytes_new` is computed as `ceil(bytes / PAGE_SIZE) * PAGE_SIZE`, floor-divided by `cell_size`, and re-multiplied by `cell_size`. This is functionally "round `bytes` up to a page boundary, then round *down* to a multiple of `cell_size`." When `cell_size` is larger than `PAGE_SIZE` (which happens for `grow_index` / data-bucket resizing where `cell_size = elem_size * num_elems + offset` and `num_elems` doubles per data-bucket tier, i.e. `1 << i` in `apply_grow_data`/data-bucket allocation), the floor-division-then-multiply by `cell_size` can truncate `bytes_new` down to a value strictly less than the original `bytes`, in the worst case even to `0` (if the page-aligned byte count is still smaller than a single `cell_size`). This violates the intended invariant that `bytes_new >= bytes`, and the code's only defense against that is the `assert!` — i.e., the author already anticipated the divide-order issue could misbehave, but chose to panic rather than compute the correct ceiling (`bytes.div_ceil(cell_size) * cell_size` rounded again to a page boundary, or simply reordering to multiply/divide the other way).

This is the same bug class as the referenced report: a division performed ahead of a multiplication causes truncation that the "obviously correct" arithmetic does not protect against, and here the code's own author flagged the risk by adding a defensive assertion instead of fixing the arithmetic order.

## Impact Explanation
If the assertion is ever tripped (large `cell_size` relative to requested capacity/page size, e.g., during data-bucket growth for pubkeys whose slot lists (`ref_count`/slot list length) push `data_bucket_from_num_slots` into a high tier), the thread performing bucket-map growth panics via `assert!`. Because `grow_index`/data-bucket resize paths are invoked from the accounts-index background flush/eviction machinery (`InMemAccountsIndex` reallocation, `BucketMap::grow`), an unhandled panic here can crash the validator process, which the task's rules explicitly accept as a valid impact ("node panic").

## Likelihood Explanation
This code path is exercised only when `IndexLimit::Threshold`/disk-backed bucket map is enabled and a bucket must grow to an "actual" (not simple power-of-two) capacity — this happens naturally as account counts and pubkey ref-counts grow over time, particularly for popular accounts with many historical slot-list entries, driving `cell_size` up as data-bucket tiers double (`elem_size * (1 << i)`). No malicious snapshot or crafted RPC call is required; ordinary operation under sustained load can reach large tiers. However, triggering the exact edge case where `bytes_new < bytes` requires a specific numeric relationship between `capacity()`, `PAGE_SIZE` and `cell_size` that I was not able to fully enumerate with concrete numbers before running out of iterations — I could not conclusively prove a live-cluster combination of `DEFAULT_CAPACITY_POW2`, `cell_size` growth tiers, and `IndexEntry<T>`/data element sizes that trips the assert versus merely wasting extra allocation. This should be verified with concrete size calculations or a targeted test before treating it as confirmed-exploitable; I flag it as a plausible but unconfirmed reachable panic.

## Recommendation
Replace the divide-then-multiply rounding chain with an arithmetic-order-safe computation, e.g. compute the number of whole cells needed first (`let cells = bytes.div_ceil(cell_size);`), then compute `bytes = cells * cell_size`, and only after that round the byte total up to the nearest page boundary (`bytes = bytes.div_ceil(PAGE_SIZE) * PAGE_SIZE`) — i.e., always round up in terms of `cell_size` first, so the final byte count is guaranteed both a multiple of `cell_size` and `>=` the originally requested `bytes`, removing the need for a crash-inducing assertion to catch a case that should be structurally impossible.

## Proof of Concept
Because this requires driving live `BucketStorage::new_with_capacity`/`grow_index`/data-bucket-resize call paths with specific `capacity()` and `cell_size` values (dependent on `IndexEntry<T>` layout and `1 << i` data-bucket tier), I was unable to build and verify a concrete numeric PoC within the available tool budget. A verifying engineer should:
1. Compute `size_of::<IndexEntry<T>>() + offset` and the data-bucket `cell_size` formula (`elem_size * (1 << i) + offset`) for the concrete `AccountInfo`/index value types used in this repo.
2. Search for a `capacity()` (from `Capacity::Actual`) and tier `i` such that `bytes = capacity * cell_size` is not a multiple of `PAGE_SIZE`, and `((bytes / PAGE_SIZE) + 1) * PAGE_SIZE < cell_size` (or otherwise floors below `bytes` after the final `/ cell_size * cell_size`).
3. Call `BucketStorage::new_with_capacity` (or drive `grow_index`) with those values directly in a unit test to confirm whether the `assert!(bytes_new >= bytes, ...)` fires.
