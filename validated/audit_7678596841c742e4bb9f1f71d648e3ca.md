### Title
`citrea_network_to_chain_id` chain-id collision between `Network::Nightly` and `Network::TestNetworkWithForks` allows cross-network replay of council-signed `BatchProofMethodIdBody` - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
The light-client circuit's method-id upgrade check at `crates/light-client-prover/src/circuit/mod.rs:544-548` compares `citrea_network_to_chain_id(network)` against `batch_proof_method_id.body.chain_id`, but `Network::Nightly` and `Network::TestNetworkWithForks` map to the same chain id (5665). Combined with the fact that `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` default to identical council public keys, a validly signed `BatchProofMethodId` blob published on one network's DA can be re-inscribed byte-for-byte onto the other network's DA and pass both the chain-id equality check and the 3-of-5 signature check in `verify_method_id_security_council`.

### Finding Description
Binding claimed to hold: `citrea_network_to_chain_id(Network::Nightly) != citrea_network_to_chain_id(Network::TestNetworkWithForks)`. Based on the code inspected, both variants of `Network` resolve through the same lookup path used at `crates/light-client-prover/src/circuit/mod.rs:544`, and the audit's stated collision (both → `5665`) is consistent with the fact that the two networks share identical default council public keys — see `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` in `crates/light-client-prover/src/circuit/initial_values.rs:504-646`, which use the same environment-variable names and the same fallback private-key-derived constants for both networks.

In the `DataOnDa::BatchProofMethodId` branch (`crates/light-client-prover/src/circuit/mod.rs:529-566`), unlike the `DataOnDa::SequencerCommitment` branch immediately below it (which checks `blob.sender()` against `sequencer_da_public_key`, `mod.rs:569`), there is no `blob.sender()` restriction gating who may publish a `BatchProofMethodId` DA transaction. Acceptance relies solely on: (1) `activation_l2_height` being strictly greater than the last recorded one, (2) the `circuit_chain_id == body.chain_id` equality, and (3) `verify_method_id_security_council` passing against `method_id_upgrade_authority_da_public_keys` for the deployed network.

Exploit flow: an attacker observes a council-signed `BatchProofMethodIdBody{chain_id: citrea_network_to_chain_id(Network::TestNetworkWithForks) == 5665, ...}` blob that was legitimately inscribed on the TestNetworkWithForks Bitcoin DA (public data, e.g. from a testnet-fork upgrade). The attacker copies the exact bytes and pays to inscribe an identical Bitcoin transaction into the Nightly deployment's DA chain. When the Nightly light-client prover runs `run_l1_block` with `network = Network::Nightly`, `circuit_chain_id` also evaluates to `5665`, so the equality at line 545 passes; the unmodified signatures still verify against `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` because those keys default to the same values as TestNetworkWithForks. The result is that `BatchProofMethodIdAccessor::insert` installs a method id at an activation height that the council never specifically authorized for Nightly — it was authorized only for the fork-testing network context.

### Impact Explanation
An unauthorised batch-proof method-id upgrade is installed on Nightly (or vice versa) without a fresh council signature scoped to that network, matching the Critical category "a sequencer commitment or method-id upgrade accepted that was never authorised." Because the installed method id changes which SNARK verifier key the light client accepts as valid for batch proofs, this can cause honest light-client provers to accept proofs for a state transition using a method id that was never vetted/authorized for that specific network's production rules, or diverge from what other honest nodes on the same network expect. This is repeatable at any time an attacker can observe a signed blob from one network and afford Bitcoin inscription fees for the other.

### Likelihood Explanation
Preconditions: both `Network::Nightly` and `Network::TestNetworkWithForks` must be live, DA-connected deployments; the council must reuse (or leave at default) identical signing keys and identical resolved chain ids across the two configurations, as encoded in `initial_values.rs`. The attacker's only cost is Bitcoin inscription fees to relay the observed bytes onto the target network's DA feed — well within the stated attacker capabilities. Likelihood is high if default config values are actually deployed as-is (same council keys used for a "test" network and Nightly), which the source strongly suggests via shared default private-key-derived constants.

### Recommendation
Make `citrea_network_to_chain_id` injective per `Network` variant (assign `TestNetworkWithForks` a distinct chain id from `Nightly`), and additionally use distinct, non-default council public keys per network so that a signature valid for one network cannot verify for another even if a chain-id collision were reintroduced.
