## Analog Identified: Fund migration griefing via permissionless outbound spam

### Title
Unprivileged user can permanently block `MsgInitiateFundMigration` for a chain by keeping `HasPendingOutboundsForChain` perpetually true — (File: `x/utss/keeper/msg_initiate_fund_migration.go`)

### Summary
The GMX report shows an attacker blocking `PirexGmx.initiateMigration` by forcing a precondition ("no vester tokens held") to remain permanently unsatisfiable. Push Chain's `x/utss` module has a structurally identical precondition gate on `InitiateFundMigration`: it requires `HasPendingOutboundsForChain` to return `false` before an admin can migrate funds off an old TSS key for a given chain. Because outbound creation is a fully permissionless, unprivileged action (any user can trigger a `FUNDS`-type outbound simply by calling the Gateway's withdraw path with a PRC20 balance they hold), an attacker can keep injecting new `PENDING` outbounds for the targeted chain, keeping the "has pending outbound" condition perpetually true and blocking the admin's fund migration indefinitely — the same "attacker-controllable precondition blocks a privileged migration step" pattern as the GMX finding.

### Finding Description
`Keeper.InitiateFundMigration` explicitly gates on the absence of pending outbounds for the chain being migrated: [1](#0-0) 

`HasPendingOutboundsForChain` is backed by the `PendingOutbounds` index, which is populated every time a new outbound is attached to a `UniversalTx` — a path reachable by ordinary users through normal withdrawal flows (calling the Gateway's `withdraw`, which emits `UniversalTxOutboundEvent`, decoded and turned into a `PENDING` `OutboundTx`): [2](#0-1) [3](#0-2) 

No admin/whitelisting is required to create an outbound this way — any account holding PRC20 tokens on Push Chain can invoke a withdrawal to any enabled destination chain, which lands a new `PENDING` entry in `PendingOutbounds` for that chain, exactly as the `x/uexecutor` README describes (`TxType_FUNDS`: "Pure transfer of a PRC20 back out of Push Chain"): [4](#0-3) 

An outbound only leaves the `PendingOutbounds` index once Universal Validators reach quorum on `MsgVoteOutbound` and it transitions out of `PENDING`: [5](#0-4) 

Because there is latency between an outbound's creation and its finalization by UV quorum voting, an attacker who repeatedly submits small withdrawals to the specific chain the admin wants to migrate away from can keep at least one outbound perpetually `PENDING` for that chain, causing `InitiateFundMigration` to fail every time the admin attempts it — a direct structural analog of the GMX report's "keep a precondition unsatisfiable to block a privileged migration/rotation function" bug class.

### Impact Explanation
`InitiateFundMigration` is the only entry point for moving locked funds off an old TSS key vault to the new key on a per-chain basis, per the module's own documentation: [6](#0-5) 

If an unprivileged attacker can indefinitely stall this call for a chosen chain, funds secured under a retired/compromised TSS key on that chain cannot be swept to the current key — a denial-of-service on a security-critical migration path that is reachable without any privileged access, aligning with the in-scope impact category "denial of service ... reachable without privileged control" and TSS/migration-record corruption/blocking concerns called out in the allowed-impact gate.

### Likelihood Explanation
Likelihood is moderate-to-high: creating an outbound requires only a nonzero PRC20 balance and a normal withdrawal call — no special role, no governance action, and no validator collusion. The attacker only needs enough capital/turnover to keep a rolling PENDING outbound alive for the duration the admin wants the migration to succeed, and the cost is bounded (funds are eventually returned via the normal outbound success/revert flow, not permanently lost), making this an inexpensive, repeatable griefing vector rather than a one-shot exploit.

### Recommendation
Do not let an unprivileged, continuously-creatable value (arbitrary user-initiated pending outbounds) be a hard blocking precondition for a privileged migration operation. Options: scope the "no pending outbounds" check to outbounds that were created before the migration was requested (snapshot-based), allow the admin to force-drain/expire outbounds signed under the old key as part of migration instead of requiring zero pending outbounds up front, or decouple new outbound creation for a chain from in-flight migration by disabling new outbound admission (`IsChainOutboundEnabled`) sufficiently early and atomically with the pending-check so no new PENDING entries can be created between the check and migration initiation.

### Proof of Concept
1. Admin plans to call `MsgInitiateFundMigration` for `oldKeyId` on chain `C` after setting `IsOutboundEnabled = false` for `C` (satisfying the "outbound disabled" precondition per `msg_initiate_fund_migration.go:31-38`).
2. Attacker, holding any nonzero PRC20 balance minted from a prior legitimate deposit to chain `C`, repeatedly calls the withdraw path on the Universal Gateway targeting chain `C` (small amounts suffice) before outbound is fully disabled, and/or right as the admin's transaction is about to be included.
3. Each withdrawal is processed by `BuildOutboundsFromReceipt` / `attachOutboundsToUtx`, adding a new entry to `PendingOutbounds` for chain `C` (see `x/uexecutor/keeper/create_outbound.go:339-371`).
4. As long as at least one such outbound remains un-finalized (`PENDING`) at the moment the admin submits `MsgInitiateFundMigration`, `k.uexecutorKeeper.HasPendingOutboundsForChain(ctx, chain)` returns `true`, and `InitiateFundMigration` returns the error `"chain %s still has pending outbounds; wait for them to drain before migration"` (`x/utss/keeper/msg_initiate_fund_migration.go:40-47`), blocking the migration.
5. By timing new withdrawals to land before UV quorum finalizes the previous ones, the attacker can keep this condition true indefinitely, analogous to how the GMX attacker kept `gmxVester`/`glpVester` balances non-zero to block `signalTransfer`.

func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}
