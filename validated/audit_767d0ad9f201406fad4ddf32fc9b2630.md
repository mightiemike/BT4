### Title
Missing equivocation-check in `handle_poison_microblock` lets any two same-key-signed (non-conflicting) headers slash an honest miner - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`handle_poison_microblock` only verifies that both submitted `StacksMicroblockHeader`s recover to the same public-key hash and that this key hash was used within the maturity window; it never verifies that the two headers actually constitute a real equivocation (same `prev_block` with different content, or same `sequence` with different content) the way `StacksChainState::validate_parent_microblock_stream` / `load_descendant_staging_microblock_stream_with_poison` do. An attacker can therefore submit a `PoisonMicroblock` transaction built from two headers taken from a single, honest, non-forked microblock stream (or even the same header twice) and still have it accepted, forfeiting the honest miner's coinbase.

### Finding Description
The claimed equality is: `reward forfeited/paid == a genuine fork detected by node-side validate_parent_microblock_stream (Some((i-1, Some(PoisonMicroblock(...)))) == the (h1, h2) pair the attacker submits in a PoisonMicroblock tx`.

Node-side fork detection (the "producer" of legitimate poison payloads) only emits a `PoisonMicroblock` payload when it detects a real equivocation: duplicate `prev_block` [1](#0-0)  or two microblocks sharing a sequence number with differing block hash [2](#0-1) . The same rule is implemented independently in `load_descendant_staging_microblock_stream_with_poison` [3](#0-2) .

However, the acceptance path for a *submitted* `PoisonMicroblock` transaction, `handle_poison_microblock`, never re-derives or checks this condition. It only:
1. Confirms both headers recover to the same pubkey hash via `check_microblock_header_signer`, which solely compares `pkh1 != pkh2` and returns an error only on mismatch [4](#0-3) .
2. Looks up whether that pubkey hash was ever recorded and whether it is still within `MINER_REWARD_MATURITY` [5](#0-4) .
3. Records/updates the poison report keyed only by `mblock_header_1.sequence`, with no verification that `mblock_header_1` and `mblock_header_2` are distinct headers, share a `prev_block`, or share a `sequence` with differing content [6](#0-5) .

Because a valid anchored block can only ever use one microblock private key per fork/height (enforced separately by `has_microblock_pubkey_hash` at block-append time, rejecting reuse) [7](#0-6) , all headers signed by that key in the confirmed chain belong to one single miner's tenure. An attacker who observes the public, honest, non-forked microblock stream can pick any two headers from it — including the same header twice, or two legitimate contiguous headers at different sequences — pass them as `(mblock_header_1, mblock_header_2)` in a crafted `PoisonMicroblock` transaction, and `check_microblock_header_signer` will happily return the shared pubkey hash because it never checks that the headers conflict. `handle_poison_microblock` then proceeds to record a poison report and (via the surrounding coinbase-forfeiture/commission logic keyed on `mblock_pubk_height`) slashes the honest miner's reward at that height, paying a commission to the attacker's principal — with no real fork ever having existed.

Existing tests only cover the "unknown pubkey hash" rejection path [8](#0-7)  and the "genuine equivocation" acceptance path using headers that do share `prev_block`/`sequence` by construction [9](#0-8) ; there is no test asserting rejection of non-conflicting headers signed by the same key, confirming the gap is unguarded.

### Impact Explanation
An honest, non-equivocating miner has their coinbase reward at a matured height forfeited/slashed based on a forged report that does not correspond to any equivocation the node's own detection logic (`validate_parent_microblock_stream`) would ever produce. The attacker principal receives the associated reporter commission. This is a reward mis-payment/loss to an uninvolved party triggered by a minority (single) attacker, matching the "poison or reward mis-payment" category.

### Likelihood Explanation
The attacker needs only: (1) to observe any honest miner's already-broadcast, non-forked microblock stream (public data), (2) to submit a single, cheaply-crafted `PoisonMicroblock` transaction referencing two headers from that stream (even one header duplicated) before `MINER_REWARD_MATURITY` elapses. No majority stake, no signer key, and no privileged role is required — any unprivileged participant able to broadcast a Stacks transaction can do this repeatedly against any miner's tenure.

### Recommendation
In `handle_poison_microblock` (or in `check_microblock_header_signer`), explicitly re-verify that `mblock_header_1` and `mblock_header_2` constitute a genuine equivocation before accepting the report: require `mblock_header_1 != mblock_header_2`, and require either `mblock_header_1.prev_block == mblock_header_2.prev_block` or `mblock_header_1.sequence == mblock_header_2.sequence`, with differing content/hash in both cases. This mirrors the exact conditions used by `validate_parent_microblock_stream`/`load_descendant_staging_microblock_stream_with_poison` and ensures the on-chain acceptance criterion matches the node's own fork-detection criterion.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
