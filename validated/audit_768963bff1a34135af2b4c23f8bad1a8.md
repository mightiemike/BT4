### Title
`AuthenticateBySession` fails to normalize `sql.ErrNoRows`/`ErrUserSessionExpired` to `ErrorAuthFailed`, letting a stale/invalid session cookie short-circuit the `Authenticate` fallback chain and deny legitimate token/EI authentication - ([File: core/web/auth/auth.go])

### Summary
`Authenticate` iterates authentication methods and only continues to the next method while the error is exactly `auth.ErrorAuthFailed`; any other error breaks the loop and is returned as the final auth error. Unlike `AuthenticateByToken` and `AuthenticateExternalInitiator`, `AuthenticateBySession` does not map `sql.ErrNoRows` / `clsessions.ErrUserSessionExpired` returned by `AuthorizedUserWithSession` into `auth.ErrorAuthFailed`, so a stale or non-existent (but structurally present) session ID causes the loop to abort before `AuthenticateByToken` or `AuthenticateExternalInitiator` are ever tried.

### Finding Description
`Authenticate` implements a fallback chain: [1](#0-0) 

Compare the three method implementations. `AuthenticateByToken` explicitly converts "not found"/"expired" errors into `auth.ErrorAuthFailed` so the loop keeps trying subsequent methods: [2](#0-1) 

`AuthenticateExternalInitiator` does the same for `sql.ErrNoRows`: [3](#0-2) 

But `AuthenticateBySession` does not perform this normalization — it returns whatever `AuthorizedUserWithSession` yields verbatim: [4](#0-3) 

If a request presents a session cookie whose `SessionIDKey` decodes to a string (i.e., not simply "no session set", which is caught by the `!ok` branch and does return `ErrorAuthFailed`), but the corresponding row no longer exists or has expired (e.g., `sql.ErrNoRows`, `clsessions.ErrUserSessionExpired`), `AuthorizedUserWithSession` returns that error and `AuthenticateBySession` propagates it unchanged. Because that error is not `auth.ErrorAuthFailed`, the `Authenticate` loop breaks immediately on the first method, and any subsequently-registered method in the same middleware chain (commonly `AuthenticateByToken` and/or `AuthenticateExternalInitiator`, chained together on routes that accept multiple credential types) is never invoked — even though the request also carries valid `X-API-KEY`/`X-API-SECRET` headers.

### Impact Explanation
This is a functional denial-of-service against legitimate credential holders: a client whose browser/HTTP client sends both a stale session cookie (e.g., from a prior logged-out or expired UI session) and valid API token headers will be rejected with 401, even though the token alone would have authenticated successfully. It also creates non-deterministic/attacker-influenceable selection of which authentication method is actually evaluated, violating the stated invariant that method selection should not be steerable by request contents.

### Likelihood Explanation
This requires only an ordinary, unprivileged HTTP client to present a decodable-but-invalid/expired session identifier together with valid token headers in one request — a realistic and easily reproducible condition (e.g., an old session cookie left in a cookie jar/browser profile that is reused alongside a saved API token, or a session invalidated server-side while the cookie is still sent). No credentials or elevated access are needed to trigger the divergent code path; only knowledge of how the endpoint stacks the two auth methods.

### Recommendation
Make `AuthenticateBySession` symmetric with `AuthenticateByToken`/`AuthenticateExternalInitiator`: explicitly check `errors.Is(err, sql.ErrNoRows)` and `errors.Is(err, clsessions.ErrUserSessionExpired)` (and any other "not authenticated" sentinel returned by `AuthorizedUserWithSession`) and return `auth.ErrorAuthFailed` in those cases, reserving the raw error for genuine unexpected failures (e.g., real DB connectivity errors) so the fallback chain behaves consistently regardless of which method is listed first.

### Proof of Concept
Add a unit test in `core/web/auth/auth_test.go` analogous to the existing `userFindFailer`/`userFindSuccesser` helpers:

1. Define an `Authenticator` stub whose `AuthorizedUserWithSession` returns `sql.ErrNoRows`, and whose `FindUserByAPIToken` returns a valid user for a known token.
2. Wire a gin session middleware that sets `SessionIDKey` to an arbitrary non-empty string (simulating a stale/invalid session ID) so `AuthenticateBySession`'s `ok` check passes and `AuthorizedUserWithSession` is actually invoked.
3. Register `webauth.Authenticate(authr, webauth.AuthenticateBySession, webauth.AuthenticateByToken)` as middleware.
4. Send a request with both the stale session cookie set and valid `X-API-KEY`/`X-API-SECRET` headers for the stub user.
5. Assert the handler is reached and returns 200 (expected/fixed behavior), demonstrating that currently (pre-fix) the request is rejected with 401 because `AuthenticateBySession` returns `sql.ErrNoRows` unmapped, breaking the loop before `AuthenticateByToken` runs.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
