### Title
Unbounded array size in deprecated (Cairo0) syscall argument parsing allows attacker-controlled huge allocation / DoS - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The Cairo0 (deprecated) syscall argument reader converts an attacker-supplied felt directly into an allocation size with no upper bound before building a `Vec<Felt>`, mirroring the OneFlow `Tensor.new_empty/new_ones/new_zeros` bug class where an unvalidated shape/size parameter triggers a crafted-input DoS.

### Finding Description
`read_felt_array` in the deprecated syscall hint processor reads the array length felt directly from Cairo VM memory and converts it to a `usize` with no sanity check against the actual amount of data present, then immediately uses it to build a felt range: [1](#0-0) 

The size is fed straight into `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)`: [2](#0-1) 

In Cairo0, syscall argument segments (e.g. for `call_contract`, `library_call`, `deploy`, `send_message_to_l1`) are populated by raw felt writes performed by the contract's own compiled instructions, not by a type-safe span construct. A malicious Cairo0 contract can therefore write an arbitrary huge felt (e.g. `2^40`) as the "array size" word of a syscall request instead of the true length of the accompanying data segment. `usize::try_from(array_size.to_biguint())?` will succeed for any value up to `usize::MAX`, so this huge value is accepted and handed to `get_integer_range`, which builds/reserves a `Vec<Felt>` sized to the attacker-chosen length before validating that the underlying memory segment actually contains that many cells.

### Impact Explanation
Because `Felt` is a 32-byte type, a modest attacker-chosen size (tens of millions) is enough to force a multi-gigabyte-to-terabyte allocation attempt. Rust's global allocator aborts the process on allocation failure (this is not a catchable panic), so every sequencer/validator node that executes this transaction during block building or Starknet OS re-execution would crash deterministically. Since this is invoked from ordinary transaction execution (a contract call reachable by any unprivileged transaction sender who invokes a maliciously crafted, previously-declared/deployed Cairo0 contract), this can render the network unable to confirm new transactions if triggered inside block production, satisfying the "network unable to confirm new transactions" impact bucket.

### Likelihood Explanation
Likelihood is Medium: it requires deploying/declaring a Cairo0 contract that directly forges its own syscall-argument segment (something straightforward for a Cairo0 program author, since Cairo0 memory writes are unchecked at the language level) and then having any transaction call into that entry point. I was not able to inspect the internal allocation strategy of `cairo-vm`'s `Memory::get_integer_range` (it lives in an external dependency outside this repo's indexed code), so I cannot fully confirm whether that specific call pre-reserves capacity for `size` before validating memory presence versus incrementally reading and failing fast on the first missing cell. This uncertainty affects only the precise DoS mechanism (allocator abort vs. a bounded per-cell lookup failure), not the underlying finding that `array_size` is accepted with no explicit upper bound before being used to size a collection operation in this repo's own code path.

### Recommendation
Cap the parsed array size (`array_size` in `read_felt_array`, `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:939`) against a sane protocol-defined maximum (e.g. the max calldata/segment size already enforced elsewhere in the codebase) before converting to `usize` and before calling `felt_range_from_ptr`/`vm.get_integer_range`. Reject the syscall with a standard `VirtualMachineError`/`MemoryError` if the declared size exceeds that bound, rather than relying on the VM's memory-cell lookup to eventually fail.

### Proof of Concept
1. Declare and deploy a Cairo0 contract whose compiled bytecode, ahead of invoking `call_contract` (or `library_call`/`deploy`/`send_message_to_l1`), writes into the syscall request segment: `array_size = <huge felt, e.g. 2^40>` followed by a data pointer to a tiny (or non-existent) segment, instead of the correct calldata length.
2. Submit an ordinary `INVOKE` transaction that calls this contract's exposed entry point.
3. During execution, `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:939-949`) reads the forged `array_size`, converts it to `usize`, and calls `felt_range_from_ptr` (`crates/blockifier/src/execution/execution_utils.rs:228-237`), which attempts to materialize a `Vec<Felt>` of that size — triggering an allocation failure/abort (or, at minimum, an unbounded resource-consuming operation) on every node that executes this transaction.

```rust
pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
```

```rust
pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
```
