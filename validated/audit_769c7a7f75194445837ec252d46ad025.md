### Title
Exchange Pool Balance Overflow Due to Conditionally-Enabled Overflow Checks in `AbstractExchangeActuator` - (File: actuator/src/main/java/org/tron/core/actuator/AbstractExchangeActuator.java)

### Summary
The original report describes a Treasury contract whose unprotected, anyone-can-call `deposit()` allows an attacker to inflate a shared accounting variable (`_totalValue`) with attacker-controlled amounts, silently overflowing arithmetic and permanently breaking subsequent legitimate operations. The closest reachable analog in java-tron is the Exchange (bancor-style TRX/TRC10 market maker) subsystem, where `ExchangeCreateContract`, `ExchangeInjectContract`, and `ExchangeTransactionContract` are anonymous, broadcastable transactions that mutate a shared, persisted accounting structure (`ExchangeCapsule` token balances). The overflow protection for this shared state is not unconditional — it is gated behind a governance-activatable chain parameter.

### Finding Description
`ExchangeCreateActuator`, `ExchangeInjectActuator`, and `ExchangeTransactionActuator` all extend `AbstractExchangeActuator`, and use its `addExact`/`subtractExact` helpers to update exchange pool balances (`ExchangeCapsule.setBalance(...)`) and account balances during `execute()` and `validate()`: [1](#0-0) 

Critically, these helpers only perform overflow-checked arithmetic (`StrictMathWrapper.addExact/subtractExact`) when `dynamicStore.allowHardenExchangeCalculation()` returns true; otherwise they fall back to plain, unchecked `x + y` / `x - y`: [2](#0-1) 

`ExchangeCreateActuator.execute()` calls these unchecked-by-default helpers to compute exchange pool balances that are persisted for all future participants of the pair: [3](#0-2) 

`ExchangeInjectActuator.execute()` similarly derives new pool balances via `addExact`/`multiplyExact`/`floorDiv` using the same conditionally-checked arithmetic, and any account holding a small amount of any TRC10 token can call `ExchangeInjectContract` to inject into an existing pool it does not own... actually injection is restricted to the exchange creator, but `ExchangeCreateContract` itself is fully permissionless — any account with a nonzero token balance and the create fee can create arbitrarily many exchanges, and there is a per-token `balanceLimit` check in `validate()`, but this check itself uses the same `addExact` wrapper, meaning the guard itself is bypassable in unhardened mode when values approach `Long.MAX_VALUE`: [4](#0-3) 

`ExchangeTransactionActuator` performs swaps against the pool balances and also gates its arithmetic overflow protection behind the same flag via `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`: [5](#0-4) 

The test suite in this repository (`hardenedSuccessExchangeCreate`, `hardenedSubtractExactOverflowOnFee`) confirms these overflow protections are new and explicitly opt-in via `saveAllowHardenExchangeCalculation(1)`: [6](#0-5) 

The governance flag is only activated by the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal type in `ProposalUtil`/`ProposalService`, i.e. a network-wide SR vote is required before the checked arithmetic path is used at all. Before that proposal is passed (which is the default state on any deployment that has not yet upgraded/voted), every arithmetic operation on the shared `ExchangeCapsule` balances performed by permissionless, anonymous `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract` transactions uses raw Java `long` arithmetic with silent wraparound instead of throwing.

### Impact Explanation
This mirrors the Treasury bug's root cause: an unprivileged, anyone-callable operation (`ExchangeCreateContract`/`ExchangeInjectContract`, broadcastable by any account holding minimal TRX/TRC10 and paying the small creation fee) mutates a shared, persistently-stored accounting structure without unconditional overflow protection. If an attacker can drive a pool's `firstTokenBalance`/`secondTokenBalance` (or the fee/balance subtraction on their own account) to wrap around `Long.MAX_VALUE`/`Long.MIN_VALUE`, the resulting exchange pool state becomes corrupted (e.g., negative or wrapped balances), which then feeds into `ExchangeTransactionActuator.execute()`'s bancor-style swap math for every subsequent trader of that pair. This can produce incorrect swap outputs (asset/accounting corruption) or make the pool's `validate()`/`execute()` paths permanently throw (since `getExchangeCapsule.transaction()` derives ratios from the corrupted balances), effectively bricking that exchange (denial of service) for all legitimate users, exactly as the Treasury's `_totalValue` overflow blocked all further deposits.

### Likelihood Explanation
Reaching this requires only broadcasting standard, unprivileged `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract` transactions — no special privileges, keys, or node compromise. The primary constraint is that the attacker must supply token balances/quantities large enough to overflow `long` arithmetic (near `Long.MAX_VALUE`), which is bounded in practice by the `exchangeBalanceLimit` dynamic parameter and by the attacker's actual TRX/TRC10 holdings — an attacker would need to legitimately hold (or repeatedly inject with) balances approaching that limit, or exploit the fact that the `balanceLimit` check itself relies on the same non-strict `addExact` wrapper. This raises the bar compared to the trivial Treasury PoC (mint `type(uint256).max` of a self-controlled token), making exploitation harder but not impossible, and contingent on the `AllowHardenExchangeCalculation` proposal not yet being active on the target network.

### Recommendation
Make overflow-checked arithmetic unconditional in `AbstractExchangeActuator.addExact`/`subtractExact` (i.e., remove the `allowHarden()` gate and always use `Math.addExact`/`Math.subtractExact`/`StrictMathWrapper`), rather than requiring a governance proposal to opt in. Additionally, ensure `ExchangeCreateContract`'s `balanceLimit` validation and all downstream `ExchangeCapsule` balance mutations use BigInteger or strictly-checked arithmetic paths regardless of the hardening flag, so a permissionless create/inject/transaction call can never silently corrupt persisted exchange pool state.

### Proof of Concept
Not independently executable from static analysis alone (would require constructing/broadcasting `ExchangeCreateContract`/`ExchangeInjectContract` transactions with balances near `Long.MAX_VALUE` against a node where `allowHardenExchangeCalculation()` is false, then observing wraparound in the persisted `ExchangeCapsule`). The repository's own test suite demonstrates the mechanism: `hardenedSuccessExchangeCreate`/`hardenedSubtractExactOverflowOnFee` in `ExchangeCreateActuatorTest.java` show the identical code path behaves without overflow protection when `AllowHardenExchangeCalculation` is left at its default (unset) value, and only throws/protects once explicitly enabled via `saveAllowHardenExchangeCalculation(1)`.   protected boolean allowHarden() {
    return chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation();
  }

  public long subtractExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.subtractExact(x, y) : x - y;
  }

  public long addExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.addExact(x, y) : x + y;
  }
