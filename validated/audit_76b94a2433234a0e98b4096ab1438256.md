### Title
Replay-verify silently accepts a divergent authenticated `position_state_checkpoint_hash` (and other checkpoint hashes) because `ensure_match_transaction_info` never compares them - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by `replay_on_archive`/replay-verify tooling to confirm that locally re-executed transaction outputs match the transaction infos that were actually committed and authenticated on-chain (bound into the accumulator/ledger via `LedgerInfo` signatures). The function checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly skips the state checkpoint hash, hot-state checkpoint hash, and `position_state_checkpoint_hash` fields of `TransactionInfoV1`.

### Finding Description
In `types/src/transaction/mod.rs`, `ensure_match_transaction_info` compares only a subset of the fields carried inside `TransactionInfo`: [1](#0-0) 

It hashes and compares `write_set` (`state_change_hash`) and events (`event_root_hash`), but the function ends with an explicit TODO acknowledging that the state/hot-state checkpoint hashes and the native-trading `position_state_checkpoint_hash` are never validated: [2](#0-1) 

`position_state_checkpoint_hash` is a real, consensus-authenticated root: it is a field of `TransactionInfoV1`, gated by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature, computed during the state-checkpoint stage of block execution and folded into the transaction-info hash that gets included in the transaction accumulator, which is in turn signed by validators via `LedgerInfo`: [3](#0-2) [4](#0-3) 

`ensure_match_transaction_info` is called by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which is exactly the tool responsible for detecting divergence between locally re-executed state and the authenticated on-chain `TransactionInfo` list (`expected_txn_infos`) fetched from an archival/backup source: [5](#0-4) 

Because the position-state root (and the main/hot state checkpoint roots) are excluded from this comparison, a corrupted local native-position Jellyfish-Merkle root (e.g. from a bug in `merklize_position`, `position_summary_at_commit`, or `NativeStateCommitter::apply` in `storage/aptosdb/src/db/aptosdb_writer.rs`) would not be flagged by replay-verify even though the resulting `position_state_checkpoint_hash` differs from the value that was actually authenticated in the on-chain `TransactionInfoV1` and bound into the ledger's accumulator/`LedgerInfo`. The same silent gap applies to `state_checkpoint_hash` (main state root) and `hot_state_checkpoint_hash`.

### Impact Explanation
This breaks the "proof-and-storage pivot" invariant that VM outputs and derived state roots must survive the executor-to-storage handoff and be provably matched against consensus-authenticated `TransactionInfo` during replay/verification. Replay-verify is one of the primary mechanisms used to catch state divergence (including hard-fork-only divergence) between different validator/full-node software versions or execution engines. With this gap, a bug that corrupts the native-position state root (or the main state-checkpoint root under paths that don't independently assert it) is a false negative in replay-verify: it will report success while the durable/authenticated state has silently diverged from the correct VM result. Given the code comment itself flags this as a precondition that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," this is a genuine, currently-live integrity gap rather than a hypothetical one.

### Likelihood Explanation
Likelihood is tied to the native-trading state root feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) being enabled together with `TRANSACTION_INFO_V1` and `HOTNESS_IN_EPILOGUE`; while gated behind on-chain feature flags, it does not require any privileged actor to trigger — once enabled, replay-verify universally fails to catch state-root corruption in these fields for every processed chunk, since the check is structurally absent rather than conditionally bypassed by an attacker.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding locally recomputed roots (from `StateCheckpointOutput`/`DoStateCheckpoint`) whenever they are `Some` in the expected `TransactionInfo`, failing verification on mismatch, consistent with how `write_set_hash` and `event_root_hash` are already validated.

### Proof of Concept
Not applicable in the traditional sense (no external transaction input triggers this) — the issue is a missing assertion. Conceptually: 1) enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS`; 2) introduce or trigger any divergence in the locally computed native-position JMT root at commit time (e.g., a race/ordering bug in `position_summary_at_commit`); 3) run `replay_on_archive`/replay-verify over that version range — `execute_and_verify` will report success because `ensure_match_transaction_info` never inspects `position_state_checkpoint_hash`, even though the recomputed root differs from the authenticated one.

**Caveat:** I could not fully verify how many production hard-fork-detection paths beyond `replay_on_archive.rs` rely on `ensure_match_transaction_info` (I found `aptos-debugger` and `cli/src/commands.rs` also call it, but did not inspect their contexts due to iteration limits), so the full blast radius of this gap is not completely enumerated.
