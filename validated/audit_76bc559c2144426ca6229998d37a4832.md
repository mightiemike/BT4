### Title
`ensure_match_transaction_info` silently skips state/position checkpoint-hash validation, causing replay-verify to report success on divergent ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
The external report's bug class is: a state/ownership-binding check that omits a required party (approved operator) and therefore lets calls that should fail silently succeed for the wrong actor. The Aptos-native analog is a proof/commitment-binding check that omits required fields (state and position checkpoint hashes) and therefore lets a replay/audit verification succeed even though the locally re-executed state root diverges from the authenticated ledger data.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the function responsible for confirming that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` (and associated write set/events) that was actually committed to the ledger and covered by the transaction accumulator proof: [1](#0-0) 

It validates status, gas used, write-set hash (`state_change_hash`), and event root hash: [2](#0-1) 

But it explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the function's own comment documents this gap and its consequence: [3](#0-2) 

This function is the sole per-transaction correctness oracle used by Aptos's archive replay-verification tool (`db-tool replay-on-archive`), which re-executes historical transactions against a `state_view_at_version` and compares the freshly computed output to the expected (archived, proof-covered) `TransactionInfo`/write set/events: [4](#0-3) 

Because `ensure_match_transaction_info` never compares `state_checkpoint_hash` / `position_state_checkpoint_hash`, a divergence between the locally re-computed state (Sparse-Merkle/JMT root, and specifically the native-position state root introduced alongside `position_state_checkpoint_hashes`) and the ledger's authenticated checkpoint hash will not be detected by this tool. The checkpoint hash is produced during normal execution/commit via `assemble_transaction_infos`, which does fold `state_checkpoint_hash` and `position_state_checkpoint_hash` into the on-chain `TransactionInfo` used for the accumulator leaf: [5](#0-4) 

So the checkpoint hash is a first-class, accumulator-committed field — but the comparator that replay-verify relies on to catch divergence ignores it.

### Impact Explanation
`replay-on-archive` (and the other unprivileged call sites of `ensure_match_transaction_info` in `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) is the tool operators and auditors use to prove that historical execution reproduces the authenticated ledger state, i.e., a proof-of-correct-execution / hard-fork-detection tool. If a VM/state-computation bug (e.g. in the new native-position/state-checkpoint logic gated by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`position_state_summary` feature) causes the locally computed state root to diverge from the one actually committed on mainnet, this tool will report the replay as fully verified ("success") despite the state divergence, because the one invariant that would expose it (`state_checkpoint_hash`/`position_state_checkpoint_hash` equality) is never checked. This is exactly the "hard-fork-only divergence during commit/replay ... accepted as valid" class called out in the state-integrity gate: an authenticated, proof-bound value (the checkpoint hash baked into `TransactionInfo` and covered by the transaction-accumulator proof) is silently excluded from the tool meant to detect its divergence.

### Likelihood Explanation
The root cause is not speculative: it is called out by the maintainers' own TODO in the exact function used by `replay_on_archive.rs`, confirming (a) the check is genuinely missing today, and (b) the authors are aware it can mask a state divergence specifically for the newly introduced native-position state root. Any bug in the new position-state or state-checkpoint computation path (a nontrivial, actively-changing subsystem per the surrounding code) would go undetected by this tool until `COMPUTE_TRADING_NATIVE_STATE_ROOTS` validation is added, as the comment itself warns.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) between the freshly executed output/state and the expected `TransactionInfo`, gated appropriately by the relevant feature flags, before enabling/relying on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production replay/audit flows.

### Proof of Concept
1. Land a (hypothetical) bug in native-position state-root computation such that the locally computed `position_state_checkpoint_hash` for some transaction differs from the value actually committed on-chain (baked into the accumulator-covered `TransactionInfo` per `execution/executor/src/workflow/do_ledger_update.rs:82-121`).
2. Run `db-tool replay-on-archive` over the affected version range; `execute_and_verify` (`storage/db-tool/src/replay_on_archive.rs:388-406`) calls `ensure_match_transaction_info`, which checks status/gas/write-set-hash/event-root-hash only (`types/src/transaction/mod.rs:2159-2196`) and returns `Ok(())`.
3. The tool reports the range as fully verified/consistent even though the position state root diverges from the authenticated ledger, exactly as documented in the TODO at `types/src/transaction/mod.rs:2197-2203`.

Note: I was not able to fully trace whether any other, independent verification path (outside `ensure_match_transaction_info`) cross-checks `position_state_checkpoint_hash` during normal state-sync bootstrapping (`state-sync/state-sync-driver/src/bootstrapper.rs`) or chunk execution (`execution/executor/src/chunk_executor/mod.rs`); those files reference `position_state_checkpoint_hash` but I did not have remaining iterations to read their full logic. If such an independent check exists in the live consensus/state-sync commit path, the practical severity is limited to auditing/replay-verify tooling correctness rather than live ledger corruption; if it does not, the gap could also mask divergence during chunk-based state sync.
