### Title
Hardened Exchange price calculation can throw an unhandled `ArithmeticException` (division by zero) when a token pool balance is zero or negative, bricking TRC10 exchange trades - ([File: actuator/src/main/java/org/tron/core/capsule/SafeExchangeProcessor.java])

### Summary
`SafeExchangeProcessor.exchangeToSupply` computes `bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP)` where `bdNewBalance = balance + quant`. When `newBalance` is `0`, `BigDecimal.divide` throws `ArithmeticException` (division undefined for divisor 0), exactly the same "division-by-zero halts a computed rate/quantity used downstream" pattern described in the MerkleResistor `coinsPerSecond` report, where an attacker- or state-influenced value used as a divisor collapses to zero and reverts the operation. [1](#0-0) 

### Finding Description
`ExchangeCapsule.transaction()` selects between the legacy `ExchangeProcessor` (double-based) and the "hardened" `SafeExchangeProcessor` (BigDecimal-based) depending on the `allowHardenExchangeCalculation` flag, and is invoked by `ExchangeTransactionActuator.execute`/`doValidate` for user-submitted `ExchangeTransactionContract` trades on TRC10 exchange pools. [2](#0-1) [3](#0-2) 

Inside `SafeExchangeProcessor`, `exchangeToSupply(balance, quant)` computes `newBalance = balance + quant` and then divides `quant` by `newBalance`:
```java

  BigDecimal base = BigDecimal.ONE.add(
      bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));

``` [1](#0-0) 

If `balance + quant == 0` (e.g., `balance == 0` and one of the paired reserves has drifted to zero/negative through prior legacy-mode rounding, or the pool balance is otherwise `0`), the `BigDecimal.divide` call throws `ArithmeticException`. There is an existing unit test in the repo that directly demonstrates this: `testSafeProcessorDivByZeroThrows` shows `SafeExchangeProcessor.INSTANCE.exchange(-1L, 100L, 1L)` (where `balance + quant = 0`) throws `ArithmeticException`. [4](#0-3) 

`ExchangeTransactionActuator.doValidate()` calls `exchangeCapsule.transaction(...)` to compute `anotherTokenQuant` before performing the actual balance checks, and this call can throw the `ArithmeticException` before or independent of the guard `firstTokenBalance == 0 || secondTokenBalance == 0` check, because that guard only checks the *pre-trade* pool balances, not the internal `balance + quant` denominator used inside the exchange formula. [5](#0-4) 

This mirrors the MerkleResistor bug class precisely: a derived quantity (`coinsPerSecond` in the original report, `newBalance` here) is used as a divisor in a downstream formula, and when that derived quantity can legitimately become zero (or in this java-tron case, a negative/zero intermediate sum), the code throws an unhandled arithmetic exception instead of failing gracefully with a validation error, bricking the operation for legitimate users of that state.

### Impact Explanation
When `allowHardenExchangeCalculation` is enabled, any legitimate user attempting an `ExchangeTransactionContract` (TRC10 token swap) against a pool whose reserves reach the zero/negative-sum edge case will have their transaction fail with an `ArithmeticException` wrapped into `ContractExeException`, rather than a clean `ContractValidateException`. This can cause unexpected transaction failures (with fees still consumed) and denial-of-service on that specific exchange pool, since `execute()` only catches `ArithmeticException` after `validate()`/business-logic checks that do not fully prevent this input. It affects unprivileged users interacting with the public TRC10 Bancor-style exchange, an accounting/market flow explicitly in scope.

### Likelihood Explanation
The `doValidate()` path already guards `firstTokenBalance == 0 || secondTokenBalance == 0` before calling `transaction()`, which reduces likelihood for the straightforward zero-balance case. However, `newBalance = balance + quant` is an *internal* sum computed by `exchangeToSupply`, not the pool balance itself; because `StrictMathWrapper.addExact` is used (not a bounds check on the result being positive), any state or quant that drives this internal sum to `0` (rather than the raw pool balance) will not be caught by the existing `== 0` validation checks, and the repository's own hardened test suite (`testSafeProcessorDivByZeroThrows`) demonstrates the exact path throwing `ArithmeticException`. Reaching this in a live pool requires the reserve arithmetic to land on this exact edge (analogous to the report's "high upfront percentage"/"small reward amount" edge conditions producing an exact zero), making it a real but narrower-probability condition than a generic revert.

### Recommendation
- In `SafeExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, explicitly check `newBalance > 0` (and `supply > 0`) before performing the `BigDecimal.divide`, and throw a `ContractValidateException`-friendly signal (or have `ExchangeCapsule.transaction` surface a validation error) rather than letting a raw `ArithmeticException` propagate.
- In `ExchangeTransactionActuator.doValidate()`, add an explicit check on the *post-trade* computed balances via `transaction()`'s inputs to ensure the denominator sums used inside the Bancor formula (`balance + quant`) cannot reach zero, mirroring the existing `firstTokenBalance == 0 || secondTokenBalance == 0` pre-trade check.
- Ensure `ExchangeTransactionActuator.execute` and `validate` catch and convert this specific denominator-zero condition into a clear, documented `ContractValidateException` rather than relying solely on catching the generic `ArithmeticException`, so the failure mode is deterministic and does not silently consume fees on legitimate calls.

### Proof of Concept
1. Enable hardened exchange calculation: `dynamicPropertiesStore.saveAllowHardenExchangeCalculation(1)` (as done in `hardenedSuccessExchangeTransaction`/`hardenedPrecisionCheckFailsWhenImprecise` tests). [6](#0-5) 
2. Directly invoke `SafeExchangeProcessor.INSTANCE.exchange(balance, buyBalance, quant)` with `balance + quant == 0` (e.g., `balance = -1, quant = 1`), reproducing the repo's own test:
```java

    () -> SafeExchangeProcessor.INSTANCE.exchange(-1L, 100L, 1L));
``` [4](#0-3) 
3. Because `ExchangeCapsule.transaction()` and `ExchangeTransactionActuator.doValidate()`/`execute()` route to this same `SafeExchangeProcessor.exchange` call for hardened pools, an equivalent internal state (reachable through the pool's accumulated `firstTokenBalance`/`secondTokenBalance` and the submitted `tokenQuant`) will surface the same unhandled `ArithmeticException` during a user-submitted `ExchangeTransactionContract`, aborting the trade via `ContractExeException` instead of a clean validation failure.
