### Title
Local wall-clock timing in `check_parent_tenure_choice` lets signers disagree on whether a tenure reorg is permitted - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The external report's bug class is "bad assumptions about a time-derived quantity that consensus-critical logic depends on" (assuming constant block time, using it to gate function behavior). The analogous defect in stacks-core is in the signer's reorg-permission logic, `SortitionData::check_parent_tenure_choice`, which decides whether a new miner is allowed to reorg a prior tenure's blocks by comparing two **locally observed wall-clock timestamps** against a fixed threshold, `first_proposal_burn_block_timing`. Because the two timestamps being differenced are recorded independently by each signer node (not derived from any canonical, chain-committed value), signers can legitimately compute different `proposal_to_sortition` durations for the exact same reorg event, causing the boolean "is this reorg allowed" verdict to diverge across the signer set.

### Finding Description
`check_parent_tenure_choice` in [1](#0-0)  decides whether a miner's chosen parent tenure is a legitimate replacement for the previously canonical tenure. When the tenure being built on differs from the prior sortition, the function walks the reorged tenures and, for each one, computes: [2](#0-1) 

Specifically:
- `sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` — the **local** timestamp at which *this signer's node* observed the new burn block.
- `approved_at` comes from `local_block_info.approved_time` — the **local** timestamp at which *this signer* approved the earlier tenure's first block.
- The reorg is judged "poorly timed" (and thus **permitted**) if `sortition_state_received_time - approved_at < first_proposal_burn_block_timing`, otherwise it is **refused**.

Both timestamps are wall-clock values recorded independently per-signer as burn blocks and proposals arrive over the P2P/HTTP network, subject to normal network latency and clock skew between signer nodes. There is no consensus-committed value substituted here (unlike, e.g., a Bitcoin block timestamp or `burn_header_timestamp`, which is at least chain-committed even if occasionally spoofable). This means for a reorg attempt whose true elapsed time is close to the `first_proposal_burn_block_timing_secs` threshold (documented default 60s, per [3](#0-2) ), different signers can independently compute values on opposite sides of the threshold for the identical event, yielding opposite `Ok(true)`/`Ok(false)` verdicts from `check_parent_tenure_choice`.

This verdict feeds directly into block-proposal acceptance in `SortitionsView::check_proposal` ( [4](#0-3) ) and `validate_tenure_change_payload` ( [5](#0-4) ), both of which turn a `false` verdict into `RejectReason::ReorgNotAllowed`. It also gates `mark_tenure_superseded` bookkeeping in the DB ( [6](#0-5) ), so a split verdict means some signers will sign the reorging tenure-change block while others durably reject it and keep signing the old tenure as live.

The project's own integration tests acknowledge the sharp threshold boundary is meaningful for behavior (`check_proposal_reorg_timing_bad`/`check_proposal_reorg_timing_ok`, `check_parent_tenure_choice_reorg_timing_bad`/`_ok` in [7](#0-6)  and [8](#0-7) ), but these tests only exercise a single, deterministic signer's view of the timestamps — they do not model the cross-node clock/latency skew that exists in a real deployment with independently operated signer nodes.

### Impact Explanation
This is a minority-triggerable validation-verdict divergence between honest, unprivileged signer nodes: no attacker action, majority coordination, or admin/key access is required — it can occur purely from natural network jitter/clock skew around a legitimate miner handoff whose timing happens to sit near the 60-second default threshold. The consequence is that the signer set splits on which tenure (old vs. reorged) is the valid one to sign, producing a temporary tip disagreement: part of the signer weight approves the new miner's tenure-change block while the rest continues to defend the old tenure, potentially stalling block production until the discrepancy self-heals (or is manually/`capitulate`-resolved, per the flows documented in [9](#0-8) ). This matches the accepted "temporary tip disagreement" / "validation verdict two nodes disagree on" High-impact category; it is bounded by the signer protocol's convergence mechanisms and does not by itself force an invalid block through or double-pay a reward.

### Likelihood Explanation
Likelihood is non-trivial but timing-dependent: it only manifests when the true reorg timing is close to the configured `first_proposal_burn_block_timing_secs` boundary (default 60s) relative to the magnitude of inter-signer clock/network skew (typically sub-second to a few seconds in a healthy network, but can be larger under load or geographic dispersion). It does not require any malicious signer, only ordinary distributed-systems timing variance, so it is a natural, minority-triggerable occurrence rather than a contrived exploit — but it is not guaranteed to occur on most reorgs, only ones landing near the threshold.

### Recommendation
Avoid deciding reorg permission from two independently-observed, per-signer wall-clock timestamps compared against a fixed local threshold. Prefer a canonical, chain-derived signal (e.g., burn-block heights/ordinal distance, or a timestamp sourced from data all signers agree on, such as the Bitcoin block's own timestamp plus a wide safety margin) rather than `local received-time - local approved-time`. If wall-clock timing must be retained for UX reasons, widen the decision into a tolerance band (e.g., require agreement across two thresholds with hysteresis) so that timestamp skew near the boundary cannot flip the boolean outcome, and log/metric the raw skew observed between `sortition_state_received_time` and any node-reported equivalent to detect drift in production.

### Proof of Concept
1. Two miners run tenures; Miner A's tenure produces exactly one globally-accepted block (`first_block_mined = Some(..)`), so its reorg eligibility depends solely on the timing check.
2. Bitcoin produces a new block causing Miner B to win the next sortition close to the boundary — assume the "true" interval between the block's proposal and the new sortition is ~60s (the default `first_proposal_burn_block_timing_secs`).
3. Due to normal network latency, Signer X receives the `NewBurnBlock` event 2 seconds earlier than Signer Y (both record their own `insert_burn_block` receive time via `signer_db.get_burn_block_receive_time`), while both signers' locally recorded `approved_at` for Miner A's block differ by a similar margin due to independent P2P propagation of the block proposal.
4. Signer X computes `proposal_to_sortition = 59s` (< 60s) → `check_parent_tenure_choice` returns `Ok(true)`, signs Miner B's tenure-change block that reorgs Miner A's block.
5. Signer Y computes `proposal_to_sortition = 61s` (>= 60s) → returns `Ok(false)` → `RejectReason::ReorgNotAllowed`, refuses to sign Miner B's block and continues defending Miner A's tenure.
6. Neither signer is malicious or misconfigured; the divergence is a direct product of comparing two independently-recorded local timestamps, exactly the kind of "assume the timing input is uniform/consistent" flaw described in the external report, reproduced here in the reorg-permission code path at [2](#0-1) .

# Reorg protection window. Measures the time between when the first block
# of a tenure was signed and when the next burn block (sortition) arrived.
#
# If a new miner tries to reorg a tenure that already produced blocks:
#   - If (burn_block_received - first_block_signed) < this value:
#     Reorg is ALLOWED (the tenure was "poorly timed" and the incoming
#     miner did not have sufficient time to RBF an outdated commit)
#   - If (burn_block_received - first_block_signed) >= this value:
#     Reorg is DENIED (the tenure was established long enough for the
#     incoming miner to RBF any outdated commit)
#
# WARNING: Setting this too LOW allows dangerous reorgs of established
# tenures. Setting it too HIGH blocks legitimate miner handoffs when
# the previous tenure's first block arrived shortly before the sortition.
#
# Default: 60
# Units: seconds
# first_proposal_burn_block_timing_secs = 60

Signatures, not pre-commits, are what pin the view: a tenure whose only block
was pre-committed (never signed) can still time out, and a pre-committed block
