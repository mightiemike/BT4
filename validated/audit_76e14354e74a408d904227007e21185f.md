### Title
`liquidate-multi` swallows a failed sub-liquidation's error without rolling back its already-committed vault writes, permitting partial state commitment and uncollateralised debt - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate-multi` (line 1593) calls `call-liquidate` via `map` for each position, and `call-liquidate` (line 907) invokes `liquidate` as a plain in-contract function call (not `contract-call?`), returning its response unwrapped into the result list. Because `liquidate-multi` finally wraps the whole list in `(ok ...)` (line 1599) regardless of any individual element's error, a failure deep inside one `liquidate` invocation (e.g. the bad-debt-socialization `asserts!` at line 1548, whose value is computed by the `fold`+success-flag pattern in `socialize-debt-asset`, line 879) is captured as *data* rather than propagated as a transaction-aborting error.

### Finding Description
1. `liquidate-multi` (1593) takes `positions` and does `(ok (map call-liquidate positions))` (1599) — the top-level function's own return value is always `(ok ...)`.
2. `call-liquidate` (907-918) calls `liquidate` directly (same contract, no `contract-call?` boundary) with `price-feeds` hard-coded to `none` and returns its result unmodified — no `try!`/`unwrap!`/`asserts!` is used to propagate a failure.
3. Inside `liquidate` (1382+), several state-mutating `contract-call?`s to `.v0-market-vault` are executed and committed as soon as they return `ok`: `vault-system-repay` (1496), `debt-remove-scaled` (1499), `collateral-remove` (1506). Each of these is its own `contract-call?` rollback boundary; once it returns `ok`, its effects are committed to the pending transaction state independent of what `liquidate` eventually returns.
4. Later, if `no-collateral-left` is true, `socialize-debt-asset` is `fold`ed over the borrower's remaining debt list (1545) using the classic Clarity "success flag" pattern (879-903): each step does `(unwrap! (vault-socialize-debt ...) failed-status)`, and once one iteration fails, all following iterations pass the failure through unchanged.
5. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` (1548) causes `liquidate` — a plain function invocation within the same contract — to return `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
6. Because `liquidate`/`call-liquidate` are same-contract function calls (not `contract-call?`), this error is not an automatic rollback boundary; it is simply a value returned to `map`. `call-liquidate` does not use `try!`, so the error is stored as one element of the result list, not raised.
7. `liquidate-multi`'s own top-level return is still `(ok (list ...))`, so the entire transaction commits — including the earlier `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` writes that succeeded before the bad-debt-socialization step failed, plus any partial writes made by earlier-succeeding iterations of the `socialize-debt-asset` fold before the failing one.

The invariant "a failed sub-step aborts the transaction or is explicitly compensated" is violated: the sub-step (bad-debt socialization) fails and is recorded only as an `err` value in a list that nobody inspects for control flow, while its predecessor state-changing calls remain committed.

### Impact Explanation
For the affected borrower position: debt is removed from bookkeeping (`debt-remove-scaled`) and collateral is transferred to the liquidator (`collateral-remove`) and tokens are moved (`vault-system-repay`), but the corresponding write-off of the position's *other* remaining debt assets (which `socialize-debt-asset` was supposed to perform because collateral was fully exhausted) never completes. This leaves debt recorded in the vault with no backing collateral — uncollateralised debt — which is a protocol insolvency condition. Category: Critical - protocol insolvency through uncollateralised debt.

### Likelihood Explanation
The interleaving is fully attacker-chosen: any unprivileged liquidator picks the batch composition and ordering in `liquidate-multi`, targeting a borrower position whose last collateral asset removal will trigger `no-collateral-left` and whose `socialize-debt-asset` fold will fail on one of the remaining debt assets (e.g., via a vault-level condition on `vault-socialize-debt`/`vault-accrue`/`debt-remove-scaled` for that asset). No flashloan, oracle manipulation, or DAO/privileged access is required — only ordinary liquidation capital and control over the `positions` list argument. Repeatable per applicable borrower/asset combination.

### Recommendation
Change `call-liquidate` to explicitly propagate the underlying `liquidate` error to the top level (e.g., via `try!`) so a single failing position aborts and rolls back the entire `liquidate-multi` transaction, or, if partial-batch execution is intentionally desired, restructure so each position's `liquidate` invocation happens through its own `contract-call?`-equivalent isolation boundary (e.g., calling out through `as-contract?`/a helper trait dispatch that actually creates a rollback checkpoint) so that a failed position's already-executed vault mutations are guaranteed to be undone rather than silently retained.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy `v0-4-market.clar` and `v0-market-vault` with two collateral/debt assets configured (asset A collateral, asset B debt for the target borrower, asset C debt also owed by same borrower).
2. Set up borrower with collateral in asset A and debt in both B and C, structured so that liquidating B fully exhausts the collateral (`no-collateral-left` true) and triggers `socialize-debt-asset` over the remaining C debt.
3. Engineer/mocks so that `vault-socialize-debt`/`debt-remove-scaled` for asset C fails deterministically (e.g., stale index cache, insufficient vault total, or a crafted vault state) while `vault-system-repay`, `debt-remove-scaled` for B, and `collateral-remove` all succeed.
4. Call `liquidate-multi` with one position (this borrower, collateral A, debt B) as the unprivileged liquidator.
5. Assert: `liquidate-multi` returns `(ok (list (err ERR-BAD-DEBT-SOCIALIZATION-FAILED)))` — i.e., the outer call succeeds while the inner position result is an error.
6. Assert via read-only getters: borrower's scaled debt for B is now `u0` (removed), borrower's collateral A is reduced/zero (seized to liquidator), liquidator's debt-B FT balance decreased and collateral-A FT balance increased — despite the reported `err`.
7. Compare against baseline: call `liquidate` directly (not via `liquidate-multi`) under the identical failing-socialization condition and confirm the whole transaction reverts (no state changes) — demonstrating the divergence in atomicity between the single-call and batch entrypoints.
8. Confirm borrower still owes debt C with now-zero collateral, evidencing uncollateralised debt / protocol insolvency for that account.
