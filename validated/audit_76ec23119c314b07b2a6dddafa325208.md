### Title
Webhook validation accepts a genuine HMAC/body pair with an unauthenticated `X-Shopify-Shop-Domain` header, enabling cross-tenant webhook forgery - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`shopify.webhooks.validate` (and the resulting `authenticate.webhook` used by `shopify-app-remix`/`shopify-app-react-router`) verifies the webhook HMAC over the raw body only, then trusts the `domain`, `topic`, `webhookId`, etc. headers verbatim, with no cryptographic binding between the signed body and those headers. Because the webhook HMAC is computed with the app's single shared `apiSecretKey` (identical for every shop that installs the app), any actor who can obtain one genuine `(rawBody, hmac)` pair — e.g., by installing the app on their own development/test store and capturing a real webhook delivery — can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header of any other shop that has the app installed. `validate()` returns `valid: true` with the attacker-chosen `domain`, and the caller loads and acts on that victim shop's offline session.

### Finding Description
`validateFactory` in [1](#0-0)  first calls `validateHmacFromRequestFactory`, which computes the HMAC solely over `rawBody` and compares it to the `X-Shopify-Hmac-Sha256` (or events) header: [2](#0-1) . No header value (including `domain`) is included in the signed data.

Once the HMAC check passes, `checkWebhookHeaders`/`checkWebhooksHeaders` simply reads `domain`, `topic`, `apiVersion`, `webhookId` straight from HTTP headers and returns `{valid: true, domain, topic, ...}` without any additional authentication of those fields: [3](#0-2) .

The consuming `authenticateWebhookFactory` (identical in `shopify-app-remix` and `shopify-app-react-router`) then treats a `valid: true` result as an authenticated event for `check.domain`, and loads/creates an **offline session** and admin client scoped to that shop: [4](#0-3)  and [5](#0-4) . `ensureValidOfflineSession` performs no additional binding check against the HMAC-verified data — it just loads/creates a session keyed by the `shop` string handed to it: [6](#0-5) .

Because `apiSecretKey` is one shared secret per app (not per shop), a valid `(rawBody, hmac)` pair generated for shop A's webhook delivery remains cryptographically valid regardless of which `domain` header accompanies it. This is consistent with Shopify's documented webhook signing behavior (HMAC binds only the body to the app secret) but this SDK does nothing to mitigate the resulting cross-tenant risk — it passes the unauthenticated `domain` header straight through to session lookup and handler execution, effectively making `webhookContext.shop`/`session`/`admin` attacker-controlled for any shop that has installed the app.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (trivial for any public app, and possible even for private/custom-distribution apps if the attacker can get one install) can capture one genuine webhook `(body, X-Shopify-Hmac-Sha256)` pair. They can then POST that exact body/HMAC pair directly to the app's public webhook URL with `X-Shopify-Shop-Domain` set to any other shop that has the app installed. The app will:
- Treat the request as an authenticated webhook for the victim shop.
- Load or provision the victim's **offline session** (including its access token) via `ensureValidOfflineSession`.
- Execute the app's topic handler with an `admin` GraphQL/REST client authenticated as the victim shop.

Depending on which webhook topic the attacker chooses to replay (e.g., `app/uninstalled`, `customers/redact`, `shop/redact`, or any topic the app subscribes to with side effects), this can cause unauthorized data deletion, unauthorized admin API actions, or leakage of victim data back to the attacker if the handler's response/side effects are observable — all performed under the victim shop's real access token. This is a cross-tenant authentication/authorization bypass reachable by any anonymous or low-privileged actor who has installed the app once.

### Likelihood Explanation
The prerequisite (obtaining one genuine webhook delivery for a shop the attacker controls) is trivial for a self-service/public Shopify app — the attacker installs their own store, triggers any webhook-firing action, and captures the HTTP request their own server would normally receive. No secret leakage, MITM, or privileged access to Shopify's infrastructure is required; the app's webhook endpoint is a publicly reachable HTTP(S) URL. The only additional requirement is that the target victim shop also has the app installed, which is public knowledge/enumerable in many app-store scenarios. This makes the likelihood high for any app that performs privileged actions in webhook handlers and relies on `shopify.webhooks.validate`/`authenticate.webhook` as the sole authentication boundary.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` (or other identifying headers) purely because the body HMAC validates. Options:
1. Bind headers into the HMAC computation, or additionally verify that `domain` matches the shop associated with the specific `webhookId` recorded at subscription time (Shopify allows correlating `webhookId` to the shop that registered it via the Admin API), rejecting mismatches.
2. Maintain a per-shop registry of expected webhook IDs/topics and cross-check the incoming `domain`/`webhookId` pair against it before loading any session.
3. At minimum, document loudly that `domain` is unauthenticated, and encourage/require consuming apps to independently verify shop ownership before performing sensitive actions in webhook handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a benign webhook (e.g., `products/create`), capturing the exact `rawBody` and `X-Shopify-Hmac-Sha256` header Shopify sends to the app's webhook endpoint.
2. Attacker sends a new HTTP POST to the same app webhook endpoint:
   - Body: the captured `rawBody` (byte-for-byte).
   - Headers: the captured `X-Shopify-Hmac-Sha256` unchanged, but `X-Shopify-Shop-Domain` replaced with `victim-shop.myshopify.com`, and `X-Shopify-Topic`/`X-Shopify-Webhook-Id` optionally altered to a topic of interest.
3. `validateHmacFromRequestFactory` recomputes HMAC over the (unchanged) `rawBody` using the shared `apiSecretKey` and it matches — `validHmacResult.valid === true` — per [7](#0-6) .
4. `checkWebhooksHeaders` returns `{valid: true, domain: 'victim-shop.myshopify.com', topic, webhookId, ...}` per [3](#0-2) .
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, obtaining the victim's real offline session/access token, and invokes the app's registered handler for that topic with `shop`, `session`, and `admin` all pointing at the victim — per [8](#0-7) .

I was not able to execute this end-to-end in a live environment (no test/runtime access here), so this PoC is derived from static analysis of the cited validation and authentication code paths; a Devin session with the ability to run the existing Jest test suites (e.g. `packages/apps/shopify-api/lib/webhooks/__tests__/validate.test.ts`) could be used to add a concrete regression test that replays a valid `(rawBody, hmac)` pair with a mismatched `domain` header and confirm the currently-passing `valid: true` result.

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
