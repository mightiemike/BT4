### Title
Unbounded, non-deduplicated growth of the per-shop session ID array in `KVSessionStorage` leads to DoS of the OAuth/token-exchange handler - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds` appends every stored session id to a single Cloudflare KV value (`shop:${shop}`) without checking whether the id already exists, and `findSessionsByShop` reads and loads every id in that array on every call. Because `storeSession` is invoked on every OAuth callback and every token-exchange refresh — often with the *same, deterministic* session id (offline session id, or `getJwtSessionId(shop, sub)` for online sessions) — normal or attacker-forced re-authentication causes this array to grow without bound, mirroring the "unbounded array" gas-exhaustion bug class from the referenced report, but here manifesting as KV value bloat and request/subrequest exhaustion.

### Finding Description
`storeSession` always calls `addShopIds`, which does an unconditional concatenation with no dedup or cap: [1](#0-0) 

Compare this to the Redis implementation, which explicitly checks `idKeysArray.includes(idKey)` before pushing: [2](#0-1) 

The KV variant has no equivalent guard, so `storeSession` for the *same* session id (which happens routinely, since offline/online session ids are deterministic per shop/user via `getOfflineId`/`getJwtSessionId`) appends a duplicate entry every time.

`storeSession` is called from every auth path whenever a session is missing or inactive, e.g. the auth callback: [3](#0-2) 

and the token-exchange strategies used by `shopify-app-express` and `shopify-app-remix`, which are triggered on essentially every request once the stored session is no longer active: [4](#0-3) [5](#0-4) 

`findSessionsByShop` then loads and `Promise.all`s every id present in this array, including all accumulated duplicates: [6](#0-5) 

### Impact Explanation
There is no scheduled or automatic pruning of `shop:${shop}` beyond explicit `deleteSession`/`deleteSessions` calls (e.g., on uninstall). Any repeated authentication for a shop — whether by ordinary daily re-auth (online tokens expire and are re-fetched) or by an attacker/merchant simply hitting the `/auth` (or embedded token-exchange) flow repeatedly — inflates this single KV value indefinitely. Cloudflare KV enforces a per-value size limit and Workers enforce a per-request subrequest limit; once the accumulated ids push the JSON array past these limits, `namespace.put` in `addShopIds` will start failing, breaking `storeSession` for that shop, and `findSessionsByShop` will make an ever-growing number of `namespace.get` subrequests, eventually failing or timing out. This is a denial of service of the app's OAuth/token-exchange auth handler for the affected shop, requiring only ordinary or slightly repeated interaction from a single merchant/customer — no privileged access or secret leakage needed.

### Likelihood Explanation
Any Shopify app using `KVSessionStorage` and either the classic OAuth flow or (more commonly today) the token-exchange strategy in `shopify-app-express`/`shopify-app-remix` will call `storeSession` on every session refresh. Because online session expiry (~24h) and any transient invalidation of the offline token both trigger a fresh `storeSession`, the array grows continuously during the lifetime of every installed shop, and can be accelerated arbitrarily by simply reloading the embedded app or re-invoking the auth begin/callback endpoints, which are unauthenticated/public routes reachable by any actor who knows the shop domain.

### Recommendation
In `addShopIds`, deduplicate before writing (mirroring the Redis implementation's `includes` check), and consider capping/pruning stale/expired ids (or storing the reverse mapping without a monolithic per-shop list) so that `findSessionsByShop` and `storeSession` have bounded cost regardless of how many times a shop re-authenticates.

### Proof of Concept
1. Deploy an app using `KVSessionStorage` with the token-exchange or classic OAuth strategy.
2. As a normal merchant/user, repeatedly load the embedded app or call the `/auth` begin+callback endpoints for the same shop (this can be scripted without any special privileges).
3. Each call results in `storeSession` → `addShopIds` appending the same (deterministic) session id to `shop:${shop}` with no dedup check: [1](#0-0) 
4. Inspect the KV value for `shop:${shop}` — its length grows linearly with the number of authentication cycles, with no cap, eventually exceeding Cloudflare KV value size limits (causing `storeSession` to fail) or causing `findSessionsByShop` to exceed Workers subrequest limits when it `Promise.all`s a `loadSession` call per (duplicate) id.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
