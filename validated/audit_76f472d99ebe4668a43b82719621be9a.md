### Title
Rounding-down of the treasury reserve fee in `accrue` lets frequent small-interval calls permanently skirt protocol yield fees - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar` and equivalent per-asset vaults, e.g. `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
`accrue` computes the protocol's reserve cut of newly accrued interest as `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)`, using floor division. When `debt-delta * fee-reserve < BPS`, `reserve-inc` truncates to `u0` and no `treasury-lp` is minted to `.dao-treasury` for that call, even though the underlying debt/interest index (`lindex`/`index`) still advances and benefits depositors. `accrue` is `define-public` and carries no caller-authorization check, so anyone can invoke it directly and repeatedly with tiny time deltas, forcing `debt-delta` to stay below the rounding threshold on every call and permanently denying the DAO treasury its fee share — the same "fee rounds to zero on small amounts, repeat many times" pattern as the referenced report.

### Finding Description
In `accrue` (e.g. [1](#0-0) ), the fee logic is:

```
(old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
(new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
(debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```
with `BPS = u10000` [2](#0-1) .

`reserve-inc` uses `mul-div-down`, which floors. If `fee-reserve` is, say, `1000` (10%), any call whose `debt-delta < 10` (in the token's smallest unit) makes `reserve-inc = 0`, and the `(if (> reserve-inc u0) (try! (ft-mint? zft treasury-lp .dao-treasury)) false)` branch is skipped entirely for that accrual, so the treasury gets nothing for that slice of interest [3](#0-2) .

Critically, `next-index`/`next-liquidity-index` derive their multiplier from `time-delta = stacks-block-time - last-update` [4](#0-3) . A caller can invoke `accrue` on every block (or any short cadence) so each individual `time-delta`, and hence each `debt-delta`, stays small enough to floor `reserve-inc` to zero on every single call, while `index`/`lindex` are still advanced and `last-update` is still bumped [5](#0-4) . Because `last-update` moves forward after each such call, the "lost" interest slice is never recaptured later — there is no larger deferred `debt-delta` to tax; the fee opportunity for that slice is gone permanently.

`accrue` itself has no caller check (only the internal `(get accrue states)` pause flag is checked), so this is directly callable by any external principal, not just internal callers via borrow/repay/deposit flows [6](#0-5) .

This mirrors the referenced report's root cause exactly: a fee computed as `amount * rate / denominator` that rounds to zero for sufficiently small "amount" inputs, exploitable by repeatedly using small inputs instead of one large one, bypassing a fee that is only meant to be waived for a privileged party (here, none — the reserve fee is not meant to be skippable by anyone).

### Impact Explanation
The DAO treasury's reserve cut of interest is protocol yield (unclaimed at the time of accrual) and its loss here is permanent — once `last-update`/`index` advance past that debt-delta, the treasury's corresponding share of interest is unrecoverable for that slice. This falls squarely into "theft of unclaimed yield or royalties, permanent freezing of unclaimed yield or royalties" — a valid High-impact category. It does not touch user principal directly, so it is not a Critical fund-theft/insolvency case, but it degrades protocol revenue collection across every vault instance that shares this `accrue` pattern (sBTC, STX, USDC, USDH, stSTX, stSTXbtc vaults).

### Likelihood Explanation
Likelihood is fairly high in practice: `accrue` is public and callable with no gas-prohibitive precondition, and any actor motivated to reduce the protocol's take (e.g., a large borrower who wants to minimize the reserve fee accrued on their debt) can simply call `accrue` every block. The smaller the pool's fee-reserve BPS and the smaller the per-block interest accrual relative to `BPS`/`fee-reserve`, the easier this is — this is especially likely for low-utilization pools or pools with modest interest rates, where per-block `debt-delta` is naturally tiny.

### Recommendation
- Track undistributed/rounding-remainder interest across calls (e.g., accumulate a `pending-reserve` uint that is only reset once `reserve-inc` becomes non-zero) instead of discarding the floor remainder each call.
- Alternatively, use `mul-div-up` (round up) for `reserve-inc`, guaranteeing the treasury always receives at least the minimal unit whenever `debt-delta > 0` and `fee-reserve > 0`, consistent with how other protocol-favoring roundings in the codebase (e.g., `calc-cumulative-debt` via `mul-div-up`) already round in the protocol's favor.
- Consider restricting or rate-limiting unauthenticated `accrue` calls, or accruing reserve fees based on elapsed time since the last *fee* checkpoint rather than since the last arbitrary `accrue` call.

### Proof of Concept
1. Vault has `fee-reserve = u1000` (10%), `BPS = u10000`.
2. Under normal operation with a large `time-delta` (e.g., accrue called once per day), `debt-delta` for that period is, say, `10_000` sats; `reserve-inc = mul-div-down(10_000, 1000, 10000) = 1000` sats minted to treasury as `treasury-lp`.
3. Attacker/borrower instead calls `accrue()` on every block. Each call has a `time-delta` of ~1 block (~10 minutes), so `debt-delta` per call is roughly `10_000 / (144 blocks/day) ≈ 69` sats.
4. `reserve-inc = mul-div-down(69, 1000, 10000) = 6` (still nonzero here, but for vaults/rates where per-call `debt-delta` drops below `BPS/fee-reserve = 10`, e.g. low-utilization pools or a caller invoking `accrue` many times within the same block boundary/short intervals), `reserve-inc` floors to `0` every single call.
5. Each call still advances `index`/`lindex` and `last-update` [5](#0-4) , so the depositors' side of interest accrues normally, but the treasury's `treasury-lp` mint is skipped (`(if (> reserve-inc u0) ... false)`), and this loss is not later recovered since the next call again starts from the already-advanced `last-update`.
6. Repeated indefinitely, the treasury systematically collects less than the intended `fee-reserve` percentage of total interest, with the shortfall determined by call frequency — an attacker-controllable, permanent yield loss to the DAO. [7](#0-6)
