Based on my investigation, I found a genuine analog matching the "cached value not invalidated when its source moves" category from the rules.

### Title
Liquidation index cache goes stale after bad-debt socialization writes down the liquidity index, causing incorrect residual-debt/collateral math within the same transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches vault `{index, lindex}` per `{timestamp, aid}` for the duration of a block via `accrue-and-cache`/`get-cached-indexes` [1](#0-0) . Inside a single `liquidate` call, the cached `debt-aid` index is read multiple times (`rem-borrow-index`, `other-borrow-idx`) via `get-cached-indexes` after the vault's on-chain index/lindex have already been mutated by an earlier step in the *same* function (`vault-socialize-debt` + `vault-accrue`), because the cache is not refreshed for every read site.

### Finding Description
`socialize-debt-asset` (used for bad-debt write-down) explicitly re-caches the *new* post-write-down indexes: `(map-set index-cache { timestamp: stacks-block-time, aid: asset-id } (unwrap! (vault-accrue asset-id) failed-status))` [2](#0-1) . This acknowledges that the vault's index legitimately changes ("lindex decreased") mid-transaction and that stale cache entries must be corrected.

However, earlier in the very same `liquidate` execution, `remaining-debt-to-repay` and `other-debt-repayable` are computed using `(get index (unwrap-panic (get-cached-indexes debt-aid)))` [3](#0-2)  and [4](#0-3) . These reads happen in a `let` binding that is evaluated *before* `vault-system-repay`/`debt-remove-scaled`/`collateral-remove` execute and before `socialize-debt-asset`'s cache refresh runs (which only fires later, inside the `bad-debt-socialized` branch). Because Clarity `let` bindings evaluate sequentially and each binding's value is fixed once computed, `debt-final`, `scaled-to-remove`, `debt-to-repay`, `coll-final-raw`, and `remaining-debt-to-repay` are all derived from the *pre-repayment* cached index — an index tied to `{timestamp: stacks-block-time, aid: debt-aid}` that is the same cache key `socialize-debt-asset` will later overwrite. The write-down that changes the "source" (the vault's real index/lindex) happens after these values are already locked in, so any calculation that depends on the freshly-decreased index (post-bad-debt-write-down) instead uses the pre-write-down cached value.

This matches the "cached value not invalidated when its source moves" analog: the cache key is keyed only by `{timestamp, aid}` (not versioned per-mutation), so a mutation to the vault's index mid-transaction (via `vault-accrue`/`vault-socialize-debt` triggered by an earlier liquidation in the same batch, e.g. `liquidate-multi`, or a nested `socialize-debt-asset` call from a prior debt asset in a multi-debt position) is not reflected in the values already computed from the stale cache read earlier in the call.

### Impact Explanation
If a borrower has multiple debt positions and one asset's debt is fully socialized (bad debt written off, decreasing that vault's `lindex`), a subsequent liquidation calculation step reading `get-cached-indexes` for the same `aid` within the same transaction/batch (`liquidate-multi`) can use a stale, pre-write-down index for `other-debt-repayable`/`remaining-debt-to-repay`, causing incorrect residual-debt accounting and mis-sized collateral seizure. This can result in temporary freezing of funds (borrower's remaining collateral incorrectly locked/unlocked) or incorrect socialization amounts, impacting protocol solvency accounting for unclaimed yield tracked via the liquidity index.

### Likelihood Explanation
Requires a specific multi-asset liquidation/socialization sequence within `liquidate-multi` where an earlier position's bad-debt socialization on a shared debt asset (`aid`) mutates the cached index before a later position's liquidation reads it via `get-cached-indexes`. This is a plausible interleaving under Clarity's sequential `let`/`map` evaluation order but requires overlapping debt assets across batched liquidations.

### Recommendation
Re-read (`vault-accrue`/refresh cache) the debt asset's index immediately before every consumption site (`remaining-debt-to-repay`, `other-debt-repayable`) rather than relying on a cache value bound earlier in the same call, or invalidate/re-fetch the cache entry for `aid` whenever `vault-socialize-debt`/`vault-accrue` mutates it mid-transaction.

### Proof of Concept
1. Set up a borrower with two debt positions sharing the same debt asset `aid` (e.g., two collateral types both borrowing USDC).
2. Call `liquidate-multi` with two `liquidate` position specs for this borrower, ordered so the first liquidation fully drains the first collateral and triggers `socialize-debt-asset`, which calls `vault-accrue` and rewrites `index-cache` for `{timestamp, aid: USDC}` with the post-write-down index.
3. The second position entry's `liquidate` call, evaluated later in the same `map call-liquidate positions` [5](#0-4) , independently calls `get-cached-indexes` for the same `aid` at the point it computes `remaining-debt-to-repay`/`other-debt-repayable` — since each `liquidate` call in the `map` is its own execution, verify whether the intra-liquidate ordering of `get-cached-indexes` reads (bound early in the `let`) versus writes (in `socialize-debt-asset`, bound late) produces inconsistent index values for computations that occur after the write within the *same* `liquidate` call for positions with multiple debt entries on one asset. (define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
