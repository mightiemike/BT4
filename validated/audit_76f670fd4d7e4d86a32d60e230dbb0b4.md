### Title
Signer Can Permanently Poison a Future Reward Cycle's Aggregate Public Key via Unconditional `used-aggregate-public-keys` Write - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
`vote-for-aggregate-public-key` in the `.signers-voting` boot contract records every submitted candidate key in the global `used-aggregate-public-keys` map on every call — win or lose — before consensus is reached. Because the map is keyed only by the raw 33-byte key value (not by reward-cycle-scoped ownership), a single minority signer can cast a throwaway vote for a key value `K` in a cycle they control, which permanently blocks any future cycle's legitimate DKG round from using that same `K`, mirroring the "front-run and burn the identifier" bug class described in the external report.

### Finding Description
`is-novel-aggregate-public-key` enforces that a key can only ever be associated with one reward cycle: [1](#0-0) 

`vote-for-aggregate-public-key` unconditionally writes to `used-aggregate-public-keys` on **every** call that passes the basic checks, regardless of whether that vote reaches the consensus threshold: [2](#0-1) 

A `tx-sender` can only vote as `signer-index` for a given `reward-cycle` if `.signers get-signer-by-index` confirms they truly hold that index, so no forged identity is required — any legitimately-registered signer for some reward cycle, however small their weight, qualifies: [3](#0-2) 

Attack sequence:
1. Off-chain DKG among the signer set for reward-cycle `M+1` converges on aggregate public key `K` (or the attacker observes the first legitimate `vote-for-aggregate-public-key(idx, K, round, M+1)` transaction land in the mempool before it is mined).
2. The attacker, who is a legitimately indexed signer for a different (or the same, currently open) reward-cycle `M`, submits `vote-for-aggregate-public-key(attacker-idx, K, 0, M)`.
3. All checks pass (`aggregate-public-keys[M]` unset, key length 33, `K` never used before, no prior vote by attacker in `M`/round 0), and `used-aggregate-public-keys[K]` is set to `M` at line 171 — even though the attacker's vote weight is far below `threshold-weight` and never approves anything for cycle `M`.
4. Every honest signer's subsequent vote for cycle `M+1` using key `K` now fails `is-novel-aggregate-public-key`: `(default-to (M+1) (map-get? used-aggregate-public-keys K))` returns `M ≠ M+1`, so `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY` (u14) is returned to every legitimate signer, permanently, for that key.
5. This directly parallels the external report's pattern: a value (evidence hash / aggregate key) that legitimately belongs to a future/target dispute is pre-emptively and irreversibly claimed by a throwaway/minority action, permanently barring its legitimate use.

Since this same function is also invoked directly from consensus-critical `VoteForAggregateKeyOp` burnchain-operation processing, this is not a peripheral contract but part of the core signer-set bootstrapping logic: [4](#0-3) 

### Impact Explanation
This is a minority-triggerable griefing attack: no majority coordination is needed, only a single signer slot (however small) in some reward-cycle's signer set. Its effect is to force the entire signer set of the targeted future cycle to abort their agreed-upon DKG output and restart DKG/voting with a fresh key, since their intended key is now permanently unusable. If the attacker can repeat this against successive DKG outputs (e.g., by continuing to hold a minimal signer slot and observing/front-running each new round's key before it lands on-chain), the aggregate-public-key approval for a reward cycle can be repeatedly poisoned, delaying or, in the worst case, preventing timely consensus on the next cycle's signing key — a temporary but chain-wide disruption to Nakamoto signer-set bootstrapping. This falls under the "poison...bounded" / "temporary tip disagreement"-class High severity impact rather than a full chain split, since honest signers can eventually converge on an unpoisoned key, but each poisoning forces wasted rounds and potential missed reward-cycle deadlines.

### Likelihood Explanation
Likelihood is significant given: (a) the mempool is public, so the first vote transaction for a new candidate key reveals `K` before it's mined, giving any signer a front-running window; (b) no privileged role is needed — only membership (any weight) in some signer set, which is a normal, permissionless outcome of stacking; (c) the check that enables this — writing to a *global*, unscoped-by-cycle map on every vote rather than only on the winning vote — is unconditional and applies on the very first call.

### Recommendation
Scope `used-aggregate-public-keys` and the novelty check by reward cycle instead of using a single global map keyed only by the key value, e.g., only write the entry when a key actually reaches threshold and is inserted into `aggregate-public-keys` (move the `map-set used-aggregate-public-keys key reward-cycle` to occur only inside the `(if (>= new-total threshold-weight) ...)` branch, guarded by the successful `map-insert aggregate-public-keys reward-cycle key`), so that non-winning/minority votes cannot permanently consume a key value for cycles that never actually adopted it.

### Proof of Concept
```
;; Reward cycle M: attacker holds signer-index i (any weight) in cycle M's signer set
(contract-call? .signers-voting vote-for-aggregate-public-key i 0xK... u0 M)
;; -> succeeds; unconditionally sets used-aggregate-public-keys[0xK...] = M

;; Reward cycle M+1: honest signers who legitimately generated 0xK... via off-chain DKG
(contract-call? .signers-voting vote-for-aggregate-public-key honest-idx 0xK... u0 (+ M 1))
;; -> is-novel-aggregate-public-key returns false (used-value M != M+1)
;; -> fails with ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY (u14) for every honest signer
```
This matches the assertion path at [5](#0-4) , and can be verified in the existing test harness pattern used for aggregate-key voting in `pox_4_tests.rs`: [6](#0-5)

(define-public (vote-for-aggregate-public-key (signer-index uint) (key (buff 33)) (round uint) (reward-cycle uint))
    (let ((tally-key {reward-cycle: reward-cycle, round: round, aggregate-public-key: key})
            ;; vote by signer weight
            (signer-weight (try! (get-signer-weight signer-index reward-cycle)))
            (new-total (+ signer-weight (default-to u0 (map-get? tally tally-key))))
            (cached-weight (try! (get-and-cache-total-weight reward-cycle)))
            (threshold-weight (get-threshold-weight reward-cycle))
            (current-round (default-to {
                votes-count: u0, 
                votes-weight: u0} (map-get? round-data {reward-cycle: reward-cycle, round: round})))
                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
        ;; Check that the aggregate public key is the correct length
        (asserts! (is-eq (len key) u33) (err ERR_ILL_FORMED_AGGREGATE_PUBLIC_KEY))
        ;; Check that aggregate public key has not been used in a previous reward cycle
        (asserts! (is-novel-aggregate-public-key key reward-cycle) (err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY))
        ;; Check that signer hasn't voted in this reward-cycle & round
        (asserts! (map-insert votes {reward-cycle: reward-cycle, round: round, signer: tx-sender} {aggregate-public-key: key, signer-weight: signer-weight}) (err ERR_DUPLICATE_VOTE))
        ;; Check that the round is incremented by at most 1
        (try! (update-last-round reward-cycle round))
        ;; Update the tally for this aggregate public key candidate
        (map-set tally tally-key new-total)
        ;; Update the current round data
        (map-set round-data {reward-cycle: reward-cycle, round: round} {
            votes-count: (+ (get votes-count current-round) u1),
            votes-weight: (+ (get votes-weight current-round) signer-weight)})
        ;; Update used aggregate public keys
        (map-set used-aggregate-public-keys key reward-cycle)
