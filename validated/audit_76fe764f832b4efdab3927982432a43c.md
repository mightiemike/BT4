### Title
Stale/unregistered secondary-index (ProgramId/SplTokenMint/SplTokenOwner) entries persist after account owner reassignment - (File: accounts-db/src/accounts_index.rs)

### Summary
`AccountsIndex::update_secondary_indexes` (and its callee `update_spl_token_secondary_indexes`) only ever *adds* a mapping from an account's current owner/mint/token-owner to the account pubkey. It never removes the mapping from the account's *previous* owner when the account is reassigned to a new owner. This is structurally identical to the UMA `Registry` bug: a party-tracking registry that is updated on add but never synchronized on removal/change, leaving unregistered/former parties still listed.

### Finding Description
`update_secondary_indexes` at [3](#0-2)  inserts `pubkey` into `self.program_id_index` under `account_owner` (the account's *current* owner) every time an account is stored, and similarly into `spl_token_mint_index`/`spl_token_owner_index` via `update_spl_token_secondary_indexes` at [4](#0-3) . There is no code path that, upon detecting an owner change, removes `pubkey` from the *old* owner's `SecondaryIndex` bucket. The only cleanup path (`purge_secondary_indexes_by_inner_key_if` / `purge_secondary_indexes_for_dead_keys` in [5](#0-4) ) only fires when the pubkey is fully removed from the accounts index (i.e., the account dies / all rooted versions are cleaned), not when it is merely reassigned to a different owner while remaining alive. Consequently, once an account changes owner (e.g. from being an SPL token account to something else, or a program-owned account is reassigned), the old owner's secondary index continues to list the pubkey indefinitely, even though the account is fully alive and rooted.

This is confirmed as intended/known behavior by the in-repo test [6](#0-5) , which explicitly asserts that after re-storing an account under `another_program_id`, `get_filtered_indexed_accounts(&IndexKey::ProgramId(program_id), ...)` still returns the stale entry, requiring callers to apply a "post-processing filter" (`account.owner() == &program_id`) to discard false positives.

### Impact Explanation
This does not directly corrupt consensus state (lamports/hash), since the primary accounts index and account data remain correct — the flaw is confined to the secondary (non-consensus) indexes used by RPC methods such as `getProgramAccounts`, `getTokenAccountsByOwner`, and `getTokenLargestAccounts`. The stale entries accumulate unbounded over the life of a validator that stays online with secondary indexes enabled, causing:
- Unbounded/disproportionate memory growth in the `program_id_index`/`spl_token_mint_index`/`spl_token_owner_index` `DashMap`s (and their `reverse_index`) as active accounts churn across owners over time, with no compaction path apart from the account eventually dying.
- Increasing CPU/latency cost for every secondary-index scan, since each RPC call must load and filter an ever-growing list of stale candidate pubkeys per owner/mint/token-owner key that were never actually removed.

This is a disproportionate storage/CPU cost issue localized to opt-in secondary indexes, not a hash/capitalization divergence or balance issue.

### Likelihood Explanation
High likelihood in any validator/RPC node running with `--account-index program-id` or `--account-index spl-token-mint`/`spl-token-owner` enabled. Any workload where accounts are reassigned to a new owner (e.g., token account closures/recreations, program-owned account reassignment patterns) while remaining alive triggers the leak; no privileged access or malicious crafting is needed, since it is a natural consequence of ordinary account owner changes over many slots.

### Recommendation
When `update_secondary_indexes` detects that a live account's owner (or SPL mint/token-owner) has changed since the account's previous indexed state, explicitly call `remove_by_inner_key_if` (or an equivalent targeted removal) against the *previous* owner's bucket before/along with inserting the new mapping, rather than relying solely on full-account-death purges. This requires tracking the previously-indexed owner (e.g. via the previous slot-list entry or a lookup prior to overwrite) at update time.

### Proof of Concept
1. Enable the `ProgramId` secondary index.
2. Store account `A` owned by `program_id`.
3. Call `get_filtered_indexed_accounts(&IndexKey::ProgramId(program_id), ...)` — returns `A`.
4. Re-store `A` with `owner = another_program_id` (a live, non-zero-lamport update, no removal from the index).
5. Call `get_filtered_indexed_accounts(&IndexKey::ProgramId(program_id), ...)` again — `A` is still returned (stale), as directly demonstrated by [7](#0-6) . Repeating steps 2–4 across many owners for many accounts grows `program_id_index` without bound relative to the live working set.

    pub(crate) fn update_secondary_indexes(
        &self,
        pubkey: &Pubkey,
        account: &impl ReadableAccount,
        account_indexes: &AccountSecondaryIndexes,
    ) {
        if account_indexes.is_empty() {
            return;
        }

        let account_owner = account.owner();
        let account_data = account.data();

        if account_indexes.contains(&AccountIndex::ProgramId)
            && account_indexes.include_key(account_owner)
        {
            self.program_id_index.insert(account_owner, pubkey);
        }
        // Note because of the below check below on the account data length, when an
        // account hits zero lamports and is reset to AccountSharedData::Default, then we skip
        // the below updates to the secondary indexes.
        //
        // Skipping means not updating secondary index to mark the account as missing.
        // This doesn't introduce false positives during a scan because the caller to scan
        // provides the ancestors to check. So even if a zero-lamport account is not yet
        // removed from the secondary index, the scan function will:
        // 1) consult the primary index via `get(&pubkey, Some(ancestors), max_root)`
        // and find the zero-lamport version
        // 2) When the fetch from storage occurs, it will return AccountSharedData::Default
        // (as persisted tombstone for snapshots). This will then ultimately be
        // filtered out by post-scan filters, like in `get_filtered_spl_token_accounts_by_owner()`.

        self.update_spl_token_secondary_indexes::<spl_generic_token::token::Account>(
            &spl_generic_token::token::id(),
            pubkey,
            account_owner,
            account_data,
            account_indexes,
        );
        self.update_spl_token_secondary_indexes::<spl_generic_token::token_2022::Account>(
            &spl_generic_token::token_2022::id(),
            pubkey,
            account_owner,
            account_data,
            account_indexes,
        );
    }

    fn purge_secondary_indexes_for_dead_keys<'a>(
        &self,
        removed_keys: impl IntoIterator<Item = &'a Pubkey>,
    ) {
        if self.account_indexes.is_empty() {
            return;
        }
        for key in removed_keys {
            // Purging secondary entries for a key that is still alive in the primary index
            // would leave a live account invisible to secondary-index scans
            debug_assert!(
                !self.accounts_index.contains(key),
                "key removed from the primary index must not be present: {key}"
            );
            self.accounts_index.purge_secondary_indexes_by_inner_key_if(
                key,
                &self.account_indexes,
                || !self.accounts_cache.contains_pubkey(key),
            );
        }
    }
