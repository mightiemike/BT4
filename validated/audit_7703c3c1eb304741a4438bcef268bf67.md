### Title
`sanitizeHost` can throw an uncaught `TypeError` for crafted base64 host values, causing authenticate.admin() to fail with an unhandled exception instead of a controlled redirect - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-shop-and-host-params.ts])

### Summary
`validateShopAndHostParams` calls `api.utils.sanitizeHost(url.searchParams.get('host')!)` without a try/catch, relying on it returning `null` for invalid input. However `sanitizeHost` (in `shop-validator.ts`) constructs `new URL(`https://${decodeHost(sanitizedHost)}`)` on any string that merely matches the base64 character-class regex, and a decoded value starting with `[` (an unterminated IPv6-style host) makes the WHATWG `URL` constructor throw a `TypeError` instead of returning gracefully. This exception is not caught by `validateShopAndHostParams`, nor converted into a controlled response by the outer try/catch in `authenticateAdmin`, resulting in an unhandled exception/500 for an anonymous request.

### Finding Description
`sanitizeHost` first validates the raw string against `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/` (`packages/apps/shopify-api/lib/utils/shop-validator.ts` lines 52-56). This regex only restricts allowed characters, not the decoded content. It then unconditionally decodes and parses the decoded string as a URL host: [1](#0-0) 
If the base64-decoded plaintext begins with `[` without a matching `]` (e.g., plaintext `"[a"`, base64 `"W2E="`), `new URL('https://[a')` throws a `TypeError: Invalid URL` because the WHATWG URL parser treats a leading `[` as the start of an IPv6 literal and requires a closing `]`. Since `"W2E="` fully satisfies `base64regex`, this exception is thrown before the `sanitizedHost = null` fallback path is ever reached, and it is not wrapped in a try/catch anywhere in `sanitizeHost`.

`validateShopAndHostParams` calls this function directly with no exception handling: [2](#0-1) 
The thrown `TypeError` propagates out of `validateShopAndHostParams`, which is called from `authenticateAdmin`: [3](#0-2) 
`authenticateAdmin` wraps this in a try/catch, but that catch only special-cases `Response` instances (adding CORS headers) and otherwise simply re-throws the caught value verbatim: [4](#0-3) 
Since a `TypeError` is not a `Response`, it is re-thrown as a raw JS exception rather than converted to `redirectToLoginPath`'s expected `redirect()` Response. This means the Remix loader receives an unhandled exception instead of a redirect/4xx Response, which Remix will surface as a 500 error (or worse, an unhandled rejection depending on runtime), for a completely anonymous, unauthenticated caller who only needs a valid-looking `shop` param and a base64-charset `host` param.

### Impact Explanation
This is a Denial-of-Service / crash condition in the authentication entry point (`authenticate.admin()`), reachable by any anonymous HTTP client with `GET /app?shop=validshop.myshopify.com&host=W2E=` (or any other base64 string decoding to a leading unmatched `[`). It breaks the fail-closed invariant that invalid host/shop should redirect to the login path with a `Response`, and instead produces an uncaught fatal error, which can leak stack traces (depending on error boundary/dev vs prod config) and/or serve 500s to legitimate users hitting the app with malformed host query strings (e.g. via link sharing, proxies, or scanners). This matches Shopify's "DoS in an authentication handler" impact class.

### Likelihood Explanation
Fully attacker-controlled, unauthenticated, single-request trigger: no secrets, no privileged access, no race conditions, and 100% reproducible. The only precondition is that the app is an embedded app (`config.isEmbeddedApp`) which is the default configuration for most Shopify Remix apps using `authenticate.admin`.

### Recommendation
Wrap the `new URL(...)` construction inside `sanitizeHost` (and analogously `sanitizeShop`'s use of `shopAdminUrlToLegacyUrl`/URL parsing if applicable) in a try/catch that treats any parsing failure as an invalid host (returning `null` or throwing `InvalidHostError` when `throwOnInvalid` is true), consistent with the function's documented contract. Alternatively/defensively, wrap the `sanitizeHost`/`sanitizeShop` calls in `validateShopAndHostParams` in try/catch and redirect to the login path on any exception, and ensure the outer catch in `authenticateAdmin` converts unexpected non-`Response` errors into a safe controlled response rather than re-throwing raw exceptions.

test('sanitizeHost throws instead of returning null for malformed decoded host', () => {
  const shopify = shopifyApi(testConfig());

  // base64 for "[a" -> decodes to a leading unmatched '[' which breaks new URL()
  const malformedHost = Buffer.from('[a').toString('base64'); // "W2E="

  // Current (buggy) behavior: throws TypeError instead of returning null
  expect(() => shopify.utils.sanitizeHost(malformedHost)).toThrow(TypeError);
});
