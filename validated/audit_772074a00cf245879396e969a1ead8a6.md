## Analog Found

### Title
Hardcoded static callback gas in the Wallet Contract can become insufficient after future gas repricing, permanently freezing the caller's deposit and bricking the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The external report flags Solidity's `transfer()` as dangerous because it hard-codes a 2300-gas stipend that can become insufficient if gas costs change in the future, causing ETH transfers to permanently fail. The NEAR Wallet Contract (NEP-518) has a structurally identical pattern: it hard-codes fixed `Gas` constants for the promise callbacks that perform the caller-deposit refund logic, rather than forwarding all unused gas. If NEAR's gas-cost schedule is ever repriced (a routine, expected event in protocol evolution — see the gas-refund/versioning discussion in `docs/architecture/how/gas.md`), these fixed budgets can become insufficient, causing the refund callback itself to run out of gas and abort before it can execute the refund, and before it can reset the contract's re-entrancy guard.

### Finding Description
The Wallet Contract defines fixed gas constants for its callbacks: [1](#0-0) 

These are attached with `.with_static_gas(...)`, which caps the gas available to the callback at exactly that amount (no unused-gas forwarding), analogous to Solidity's `.transfer()` fixed 2300-gas stipend: [2](#0-1) 

The refund logic itself lives entirely inside `rlp_execute_callback`, which is only reached if the preceding action's callback successfully executes with its allotted static gas: [3](#0-2) 

Note that `self.has_in_flight_tx = false;` is the *first* statement of `rlp_execute_callback`. If the function call exceeds its statically-attached gas budget before completing (e.g., due to future gas repricing making the same WASM/host-function work cost more gas than `RLP_EXECUTE_CALLBACK_GAS` allows), the entire function call fails as an execution error. On NEAR, a failed `FunctionCall` receipt reverts all state changes performed by that call — so `has_in_flight_tx` is never reset to `false`, and the caller's deposit refund transfer is never issued.

The re-entrancy guard that becomes permanently stuck is enforced at the very entry point of the contract: [4](#0-3) 

Similarly, the fixed 2 Tgas allotted for non-`FunctionCall` actions (`Transfer`, `AddKey`, `DeleteKey`) is baked directly into the contract logic used to size these same static callback budgets: [5](#0-4) 

Because the Wallet Contract is deployed as an immutable global contract shared by all ETH-implicit accounts (see `docs/DataStructures/Account.md`, "Wallet Contract" section) and is invoked by any unprivileged relayer/caller via `rlp_execute`, this is directly reachable from a single submitted transaction with no special privileges.

### Impact Explanation
If the hardcoded gas constants (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, or the 2 Tgas non-function-call action budget) become insufficient after a future gas-cost repricing:
- The caller's attached deposit (`CallerDeposit`, tracked to be refunded on failure) can never be refunded, resulting in **permanently frozen funds**.
- `has_in_flight_tx` is never reset back to `false` because the state-mutating statement that resets it is undone by the failed-call revert, permanently locking the ETH-implicit account out of ever calling `rlp_execute` again (a **transaction-triggered halt** of that account, since implicit accounts using the Wallet Contract have no full access key and cannot be recovered any other way per the docs).

This mirrors exactly the reported bug class: a fixed, non-adaptive gas stipend that is safe today but is a latent landmine against future gas repricing, silently breaking fund transfers/refunds instead of scaling with actual cost.

### Likelihood Explanation
Gas cost recalibration is a normal, expected part of NEAR protocol evolution (as documented in `docs/architecture/how/gas.md`, referencing NEP-536 and prior repricing efforts). The Wallet Contract is deployed once as an immutable global contract (see `wallet_contract_magic_bytes`/`GlobalContractDeployMode::CodeHash` usage in `integration-tests/src/tests/features/wallet_contract.rs`), so it cannot be silently patched account-by-account if a repricing event pushes execution just over these hardcoded budgets. Any relayer forwarding a normal ETH-style transaction (base-token transfer, ERC-20 emulation, or `addKey`/`deleteKey`) that happens to trigger the fallback/failure branch is enough to exercise the vulnerable refund path — it requires no malicious relayer, validator, or node behavior, only an ordinary transaction plus a future protocol gas repricing.

### Recommendation
Avoid hardcoding a fixed, small gas amount for gas-sensitive callback logic (especially the refund path in `rlp_execute_callback`). Instead:
- Use `GasWeight`/unused-gas-forwarding (as already used elsewhere in the contract, e.g., `create_ban_relayer_promise`) so the refund/callback logic is not starved as gas costs change.
- Add a safety margin buffer to the static gas constants and make them configurable/upgradable independent of the immutable global contract code, or add an explicit recovery mechanism (e.g., an admin/DAO-triggerable unlock of `has_in_flight_tx`) so an out-of-gas failure in the callback cannot permanently brick the account and its funds.

### Proof of Concept
1. A relayer submits an ETH-style transaction via `rlp_execute` targeting another account, attaching a deposit as `caller_deposit` (`CallerDeposit::new`), and the routed action's cross-contract call fails (e.g., receiver panics), so the chain reaches `rlp_execute_callback` with `PromiseResult::Failed`.
2. Assume a future protocol gas repricing increases the cost of `env::promise_batch_create` / `env::promise_batch_action_transfer` or general WASM execution such that the fixed `RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)` budget attached via `.with_static_gas(...)` is no longer sufficient to reach the refund logic inside `rlp_execute_callback`.
3. The `rlp_execute_callback` function call exceeds its prepaid (static) gas and fails; NEAR reverts all of its state changes, so:
   - `has_in_flight_tx` remains `true` forever (permanent halt of the account for all further `rlp_execute` calls, since the guard at the top of `rlp_execute` — lines 97–105 — will always short-circuit).
   - No refund transfer is issued to `caller_deposit.account_id`, permanently freezing the caller's attached deposit inside the Wallet Contract account.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

impl Action {
    pub fn gas(&self) -> Gas {
        match self {
            Self::FunctionCall(fn_call) => fn_call.gas,
            // 2 Tgas is sufficient for any non-function call action
            Self::Transfer(_) | Self::AddKey(_) | Self::DeleteKey(_) => Gas::from_tgas(2),
        }
    }
