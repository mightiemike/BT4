### Title
Difficulty-retarget underflow in `calculate_new_difficulty` allows a forged low-difficulty Bitcoin header chain to be accepted by the light client - (File: `crates/bitcoin-da/src/verifier.rs`)

### Summary
`calculate_new_difficulty()`, used by `BitcoinVerifier::verify_header_chain_mainnet/testnet4/signet` to recompute the next difficulty-adjustment-period target during Bitcoin header-chain verification, subtracts two `u32` timestamps without checking their ordering, exactly analogous to the reported `time - lock_time` bug. This can wrap the timespan to a huge value, which is then clamped upward, producing an artificially *easier* (higher) target for the next 2016-block epoch than real Bitcoin consensus would allow. Any client (including the light-client prover) that trusts a header chain following this miscalculated, easier target can be made to accept a DA header chain that does not correspond to legitimate Bitcoin proof-of-work — a forged DA inclusion/completeness result.

### Finding Description
`calculate_new_difficulty` computes: [1](#0-0) 

```rust
let mut actual_timespan = last_timestamp - epoch_start_time;
if actual_timespan < expected_epoch_timespan / 4 {
    actual_timespan = expected_epoch_timespan / 4;
} else if actual_timespan > expected_epoch_timespan * 4 {
    actual_timespan = expected_epoch_timespan * 4;
}
```

`last_timestamp` is `block_header.time().secs()` of the *last* block of a 2016-block epoch and `epoch_start_time` is the timestamp of the *first* block of that epoch, set in `verify_header_chain_mainnet`/`_testnet4`/`_signet`: [2](#0-1) 

The only timestamp rule enforced on individual blocks is `verify_timestamp`, which only requires the new block's time to be strictly greater than the median of the previous 11 timestamps — it does not enforce global monotonicity between arbitrary blocks, nor a maximum future-drift bound: [3](#0-2) 

Because median-time-past allows a decreasing trend in raw timestamps as long as each new timestamp beats the rolling median, an entity that mines its *own* full alternate header chain (needed anyway to satisfy proof-of-work under a target it controls) can pick a high timestamp for the epoch's first block and a lower timestamp for the epoch's last block 2015 blocks later, while still passing `verify_timestamp` at every step. This makes `last_timestamp < epoch_start_time` reachable, causing `last_timestamp - epoch_start_time` to wrap around (Rust release builds wrap silently on overflow unless `overflow-checks` is enabled). The wrapped value is enormous, so it is clamped to `expected_epoch_timespan * 4`, i.e. the maximum allowed timespan — which yields the *easiest* possible retargeted difficulty (about 4x easier than the honestly computed value, and potentially much more if the true value should have clamped in the opposite, harder direction).

`total_work` is accumulated per-header from `target_to_work(target)` and is the basis for chain/fork comparisons in the light-client's header-chain acceptance logic. A miscalculated, artificially-easy target both (a) lets a much weaker adversary produce headers that satisfy PoW at a fraction of Bitcoin's real difficulty, and (b) inflates the apparent validity of that alternate chain's blocks under Citrea's own reimplementation of Bitcoin consensus rules, since `verify_target_hash` is checked against this bugged target rather than Bitcoin's real value.

### Impact Explanation
This breaks the DA-integrity binding relied upon by the light client (`BitcoinVerifier::verify_header_chain_*`, consumed when validating headers referenced by the light client proof / DA inclusion checks). If the target computed by Citrea's verifier diverges from the real Bitcoin retarget for the same epoch (because of the underflow), an attacker mining a forked/alternate chain of block headers only needs to satisfy the buggy, easier target rather than the real Bitcoin difficulty to have that chain accepted as a valid extension of the header chain by Citrea nodes/provers. This is exactly the "forged DA inclusion or completeness result" Critical-impact category: honest nodes' light client state could diverge from real Bitcoin, or a batch/light-client proof could be produced against headers that do not represent genuine Bitcoin PoW-secured history.

### Likelihood Explanation
Triggering requires the attacker to fully control (mine) a private/side header chain — feasible since PoW under the manipulated target is drastically cheaper than under real Bitcoin's target — and requires manipulating timestamps within the median-time-past rule across a full 2016-block epoch, which is a deliberate, achievable construction (not depending on majority hashrate over the real Bitcoin network, and not depending on any privileged role, key, or misconfiguration). This is a native/guest-shared bug: the same `calculate_new_difficulty` code runs both natively and inside the light-client circuit, so a bad actor can pre-compute headers that pass this exact (buggy) verification logic.

### Recommendation
Guard the subtraction, mirroring Bitcoin Core's actual retarget code:
```rust
let actual_timespan = last_timestamp.checked_sub(epoch_start_time)
    .unwrap_or(0); // or reject the header chain as invalid if last_timestamp < epoch_start_time
```
Additionally, consider validating that block timestamps are monotonic enough (or bounded) across an epoch to match Bitcoin Core's exact `GetBlockProof`/`CalculateNextWorkRequired` semantics, and audit `verify_timestamp` for the missing maximum future-time-drift check present in real Bitcoin consensus.

### Proof of Concept
1. Attacker mines a private header chain (needs only enough hashpower to satisfy PoW against whatever target `verify_header_chain_*` currently expects for the epoch, which starts at the honest/expected difficulty).
2. At the first block of a difficulty epoch (`epoch_block == 0`), the attacker sets a comparatively high timestamp `T0` for `epoch_start_time` (still passing `verify_timestamp` against the real chain's rolling median at that point).
3. For each of the following 2015 blocks, the attacker sets a timestamp that satisfies `block_time > median(prev_11_timestamps)` but trends downward, so that by block 2015 (`epoch_block == BLOCKS_PER_EPOCH - 1`), `last_timestamp < T0 = epoch_start_time`.
4. `calculate_new_difficulty(epoch_start_time=T0, last_timestamp<T0, ...)` computes `last_timestamp - epoch_start_time`, which underflows/wraps to a huge `u32`, then gets clamped to `expected_epoch_timespan * 4` — the maximum, easiest allowed timespan.
5. `target_to_bits` converts this into a target far easier than Bitcoin's genuine retargeted difficulty for that epoch.
6. All subsequent blocks in the new epoch only need to satisfy this attacker-favorable target in `verify_target_hash`, letting the attacker's low-hashpower chain pass Citrea's Bitcoin header-chain verification as if it were legitimate proof-of-work-secured Bitcoin history.
