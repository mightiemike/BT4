I reviewed the vault `redeem`/`deposit` functions (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-usdc.clar`, `v0-vault-ststxbtc.clar`) which are the closest analog to Illuminate's `Redeemer.sol` `redeem()` accounting bug. In all of them, `assets` is correctly decremented on redeem (`(var-set assets (- current-assets inkind))`) and correctly incremented on deposit (`(var-set assets (+ current-assets amount))`) — no inverted arithmetic exists. [1](#0-0) [2](#0-1) 

I also checked the `market.clar`/`v0-4-market.clar` accounting paths (`repay`, `borrow`, `system-repay`, `socialize-debt`, `liquidate`) for the specific analog classes permitted by the rules (stale cache not invalidated, pause pass-through, health-check-then-mutate ordering, fold absorbing failure, mutation before guard, multi-step entry point stranding value):

- The index cache (`index-cache`, `accrue-and-cache`) is keyed by `stacks-block-time`, so it cannot go stale within the same block/transaction, and no code path mutates the underlying vault index after caching without also refreshing the cache (`socialize-debt-asset` explicitly refreshes the cache after `vault-socialize-debt`). [3](#0-2) [4](#0-3) 
- `accrue` in the vault contracts implements pass-through-on-pause, but this is a deliberate admin-controlled pause switch (part of `pause-states`), which falls under the "deliberate safety design decisions" exclusion. [5](#0-4) 
- `socialize-debt-asset` is a fold that short-circuits on failure via `{success: false}` accumulator, but this is intentional batch-abort behavior visible to the caller, not a silently-absorbed failure that produces incorrect accounting. [6](#0-5) 
- `repay`, `borrow`, and `liquidate` all accrue debt/collateral (populating the cache) strictly before resolving prices, and all health checks are evaluated against consistent post-accrual state before the mutating vault calls; I did not find a place where a resolved health/debt value is used after the state it was computed from changes within the same call. [7](#0-6) 

None of these match a genuine underflow/inverted-sign accounting defect analogous to the Illuminate `redeem` bug, nor do they fit the other permitted single-transaction analog classes without relying on excluded categories (DAO-controlled pause, deliberate design). I could not identify a valid in-scope analog.

                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))
