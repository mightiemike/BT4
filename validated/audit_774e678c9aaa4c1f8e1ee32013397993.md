### Title
Exchange pool inject/withdraw lack slippage protection, allowing ratio manipulation between submission and execution - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` let an account add or remove liquidity proportionally from a bancor-style token pool (`ExchangeCapsule`) by specifying only `quant` of one token; the "other side" amount (`anotherTokenQuant`) is computed on-chain from the pool's `firstTokenBalance`/`secondTokenBalance` ratio at execution time [1](#0-0) . Unlike `ExchangeTransactionContract`, which carries an `expected` field used as a slippage bound [2](#0-1) , `ExchangeInjectContract`/`ExchangeWithdrawContract` carry no such bound [3](#0-2) .

### Finding Description
Between the time a user constructs and broadcasts an `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction and the time it is actually included and executed in a block, other transactions (e.g., `ExchangeTransactionContract` trades from arbitrage bots) can freely alter the pool's `firstTokenBalance`/`secondTokenBalance` ratio, since these are ordinary state-mutating actuators processed sequentially per block with no price staleness guard [4](#0-3) .

When the inject/withdraw transaction finally executes, `anotherTokenQuant` is recomputed from whatever the pool ratio happens to be at that later point:
```
anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance);
``` [5](#0-4) 

The same pattern exists in withdrawal, with an additional precision/"remainder" check but still no external minimum bound supplied by the user [6](#0-5) [7](#0-6) .

Because the user has no way to bound the acceptable `anotherTokenQuant` (no `expected`/min-out field exists in either contract, contrasted with `ExchangeTransactionContract.expected` at proto line 36), the pool can accept the injected/withdrawn liquidity at a ratio that has drifted arbitrarily from what the user intended by the time of broadcast — this mirrors the report's root cause: "computation for the re-balancing amount should be on-chain" is already true here, but the missing piece is that on-chain computation still uses **whatever the current (possibly manipulated) ratio is at execution time**, with no bound check tying it back to the state the user actually observed at submission.

### Impact Explanation
A liquidity provider who injects/withdraws can be economically disadvantaged: an attacker (unprivileged, ordinary account) can submit `ExchangeTransactionContract` trades immediately before the victim's inject/withdraw transaction is packed into the same block (front-running via fee/ordering, or simply timing), skewing the ratio so the victim contributes/receives a distorted proportion of assets, effectively extracting value from the victim through a sandwich-style attack. This is an accounting/economic-loss issue reachable by any account broadcasting a normal transaction — no privileged role or leaked key is required.

### Likelihood Explanation
Exploitation only requires the ability to submit ordinary broadcast transactions (`ExchangeTransactionContract`, `ExchangeInjectContract`) and control over transaction timing/fee to get favorable ordering within a block — capabilities available to any network participant. The `ExchangeCreateActuator`/`ExchangeTransactionActuator` control the balances, and `ExchangeInjectActuator`/`ExchangeWithdrawActuator` never re-check against a caller-supplied minimum, so the attack is straightforward to construct with existing wallet tooling (see `HttpMethed.exchangeInject`/`exchangeWithdraw` helpers used in tests) [8](#0-7) .

### Recommendation
Add an `expected`/slippage-bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and enforce a min/max bound on the computed `anotherTokenQuant` inside `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `execute()`/`doValidate()` paths, rejecting the transaction if the on-chain ratio at execution time diverges from the bound the caller specified when constructing the transaction.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim specifying `tokenQuant` of `firstTokenID`.
2. Attacker submits an `ExchangeTransactionContract` trade against the same exchange to shift `firstTokenBalance`/`secondTokenBalance` ratio favorably, using fee/ordering to land before the victim's transaction in the same block (see `ExchangeTransactionActuator.execute()` mutating pool balances) [9](#0-8) .
3. When the victim's `ExchangeInjectContract` executes, `anotherTokenQuant` is computed from the now-skewed ratio [1](#0-0) , causing the victim to inject at a worse-than-expected ratio, with no on-chain check preventing this since no `expected` bound exists in the contract.
4. Attacker reverses the initial trade afterward, extracting the difference.
