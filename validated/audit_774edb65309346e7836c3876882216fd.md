I'll investigate this by searching for analogous accounting/invariant patterns in Aptos's storage, accumulator, and proof-verification code.## Title
Authenticated `TransactionOutput`-to-`TransactionInfo` match check silently skips checkpoint hash fields, allowing a node to accept a corrupted/divergent position state root during apply-transaction-output sync and archive replay-verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated check used by state-sync's apply-output path and by the `db-tool replay-on-archive` verification path to confirm a locally-produced (or externally supplied) `TransactionOutput` matches the `TransactionInfo` that is bound into the transaction accumulator/ledger. The function explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — this gap is called out by the code's own TODO comment.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  checks the execution status, gas used, write-set hash (`state_change_hash`), and event root hash against the corresponding fields of a `TransactionInfo`, but explicitly skips the state-checkpoint related hashes:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
``` [2](#0-1) 

This is called from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs` [3](#0-2) . These are the exact code paths that authenticate a `TransactionOutput` against the `TransactionInfo` stored/proven in the ledger accumulator when a node is applying pre-computed outputs (state sync "apply-output" mode) or re-verifying archived history.

The `TransactionInfoV1.state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields are themselves committed into the transaction accumulator (they are part of what gets hashed into `TransactionInfo::hash()`, which is the accumulator leaf) [4](#0-3) . The state/hot-state/position Merkle roots are produced by a separate execution path (`DoStateCheckpoint` / `ProvablePositionStateSummary`) that runs independently of the `TransactionOutput` write-set materialization, similar to how the reported vault bug had two independently-maintained values (`totalSupplies`/`totalBorrows` accounting vs. raw `balanceOf`) that were expected—but not verified—to stay consistent. Here, the write-set/event/gas/status fields are cross-checked in `ensure_match_transaction_info`, but the state/hot-state/position checkpoint roots — a separate "accounting" value computed by a different subsystem — are not, even though `TransactionInfo` claims (via the accumulator) that they are authenticated.

### Impact Explanation
When a node applies pre-verified transaction outputs (rather than fully re-executing), or when `db-tool replay_on_archive` is used to verify an archived chain segment, `ensure_match_transaction_info` is the only cross-check tying the supplied `TransactionOutput` to the `TransactionInfo` object that the ledger accumulator/consensus actually committed to. Because it omits the checkpoint-hash fields, a `TransactionOutput` whose underlying state/hot-state/position Merkle root diverges from what was truly computed by the network will still pass this check and be treated as verified/matching. This directly falls under the "authenticated API or state-view output bound to the wrong version/proof context" and "restore/replay paths must not reinterpret committed data into a different ledger state" gates: replay-verification tooling can certify a chain segment as correct while the position (native-trading) state root — which is consensus-authenticated once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled — is not actually checked, undermining the very proof-binding replay-verify is meant to provide.

### Likelihood Explanation
The comment states this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [5](#0-4) , and that feature flag is gated off by default and requires `TRANSACTION_INFO_V1` and `HOTNESS_IN_EPILOGUE` [6](#0-5) [7](#0-6) . This means the gap is currently dormant on mainnet as long as `COMPUTE_TRADING_NATIVE_STATE_ROOTS` remains disabled; it is a self-acknowledged pre-existing defect that becomes exploitable/impactful the moment that feature is turned on, since nothing else in the reviewed code paths (chunk executor's apply-output flow, `replay_on_archive`) independently re-verifies the checkpoint hashes.

### Recommendation
Extend `ensure_match_transaction_info` to also assert that the locally recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/applicable) equal the corresponding fields on the supplied `TransactionInfo`, mirroring the existing checks for `write_set_hash` and `event_root_hash`. This should be done, and covered by tests, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network.

### Proof of Concept
Not independently exploitable today because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is off by default and the checked-in TODO documents the exact gap; a concrete PoC would require constructing a `TransactionOutput`/`TransactionInfo` pair with a divergent `position_state_checkpoint_hash` (or `state_checkpoint_hash`) and calling `ensure_match_transaction_info`, showing it returns `Ok(())` despite the mismatch — this can be directly demonstrated as a unit test against `types/src/transaction/mod.rs::ensure_match_transaction_info`, but real-world impact on mainnet is contingent on the feature flag being enabled, which I could not verify is currently the case.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",

            expected_events,
