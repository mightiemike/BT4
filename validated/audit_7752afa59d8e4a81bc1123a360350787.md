## Title
`meta_tx_v0` syscall computes a transaction hash indistinguishable from a real InvokeV0 transaction hash, enabling cross-domain signature replay - (File: crates/blockifier/src/execution/syscalls/syscall_base.rs)

## Summary
The `meta_tx_v0` syscall lets a contract have blockifier compute a transaction hash and set up a synthetic `TransactionInfo` for an inner `__execute__` call, using the exact same hash format as a legacy `InvokeTransactionV0`. There is no domain-separation between "a signature meant for the meta-tx syscall" and "a signature meant for an actual on-chain `InvokeTransactionV0`" — both hash the same fields (`contract_address`, `entry_point_selector`, `calldata`, `max_fee=0`, `chain_id`) with the same `INVOKE_HASH_PREFIX`/version-0 encoding. This mirrors the Nomic report's root cause: two logically distinct "destinations"/contexts share one commitment/hash format with no type prefix, so a value computed for one context is valid input for the other.

## Finding Description
`SyscallHandlerBase::meta_tx_v0` in `crates/blockifier/src/execution/syscalls/syscall_base.rs` (lines 286-367) builds the meta-transaction hash via: [1](#0-0) 
constructing an `InvokeTransactionV0` struct and calling `calculate_transaction_hash` with `TransactionVersion::ZERO` — the identical hash function/prefix used to compute the hash of a genuine, on-chain `InvokeTransactionV0` transaction (as also mirrored in the Cairo OS code at `compute_meta_tx_v0_hash`, which explicitly reuses `INVOKE_HASH_PREFIX` with `version=0`): [2](#0-1) 

Contrast this with every other transaction type in the same file (`compute_invoke_transaction_hash`, `compute_l1_handler_transaction_hash`, `compute_deploy_account_transaction_hash`, `compute_declare_transaction_hash`), each of which is bound to a distinct `tx_hash_prefix` constant that acts as domain separation between transaction kinds: [3](#0-2) 

The `meta_tx_v0` hash intentionally reuses the InvokeV0 format so that off-chain-signed "meta transactions" can be validated inside a contract's `__execute__`/account-abstraction logic using standard v0-invoke signature-verification code paths. However, this means a signature produced for a meta-transaction is byte-for-byte a valid signature for a genuine `InvokeTransactionV0` with the same `(contract_address, entry_point_selector, calldata, chain_id)`, and vice versa — there is no separate domain tag distinguishing "this hash was computed for use inside `meta_tx_v0`" from "this hash was computed for an actual transaction submitted to the network."

## Impact Explanation
If an account/wallet signs a payload intending it only to authorize an off-chain "meta transaction" (to be relayed through `meta_tx_v0` inside some contract's validation logic), that same signature is simultaneously valid as the signature for submitting a standalone `InvokeTransactionV0` transaction directly to the network (as long as V0 invoke transactions remain acceptable, e.g., via the min-version enforcement rules for legacy/L1-bound accounts or `v1_bound_accounts`-style deprecated flows). A malicious relayer/user who obtains such a signature (e.g., collected off-chain for meta-tx relaying purposes) could instead submit it directly as a real invoke transaction — bypassing whatever contract-level access-control or invariant the meta-tx flow was meant to enforce, and consuming the signer's account nonce/fee/state unexpectedly (unauthorized account action). This matches "unauthorized account action" impact class from the rubric.

## Likelihood Explanation
Reachability requires only: (1) a contract that exposes the `meta_tx_v0` syscall path (any contract can call it, subject to `EXECUTE_ENTRY_POINT_NAME` selector restriction) and (2) that legacy `InvokeTransactionV0` transactions are still constructible/acceptable in some flow (they remain a supported `starknet_api` transaction variant used throughout the codebase, e.g. `InvokeTransactionV0` still implements `TransactionHasher`/`calculate_transaction_hash`). The likelihood depends on whether V0 invoke transactions are actually still routable through the gateway/mempool in the current network configuration — this was not conclusively verified in the available index, since gateway-level version gating code was not found within the search budget.

## Recommendation
- Short term: Introduce an explicit domain-separation prefix for `meta_tx_v0` hashes (e.g., a distinct constant, not `INVOKE_HASH_PREFIX`), so a hash computed inside the syscall can never collide with a hash of a real submitted transaction.
- Long term: Audit all places reusing existing transaction-hash formats for auxiliary/off-chain purposes (syscalls, signature-verification helpers) and require every such reuse to inject a unique context tag. Add regression tests asserting that `meta_tx_v0` hashes and standalone `InvokeTransactionV0` hashes are computed with different domain separators even for identical `(contract_address, selector, calldata, chain_id)` inputs.

## Proof of Concept
1. A dApp asks a user to sign an "off-chain meta transaction" intended to be submitted only via `meta_tx_v0` inside contract X's `__execute__`, with fields `(contract_address=A, entry_point_selector=EXECUTE_ENTRY_POINT_NAME, calldata=D, max_fee=0, chain_id=C, version=0)`.
2. The resulting signature `S` is valid over `InvokeTransactionV0{contract_address: A, entry_point_selector, calldata: D}.calculate_transaction_hash(chain_id=C, version=0)`, per [1](#0-0) .
3. Because this is exactly the hash of a standalone `InvokeTransactionV0` transaction with the same fields, an attacker constructs and submits a real `InvokeTransactionV0{contract_address: A, entry_point_selector: EXECUTE, calldata: D, signature: S, max_fee: 0}` directly to the network (assuming V0 invoke submission is permitted for the target account/class).
4. If accepted, account `A`'s `__execute__` runs directly under the signer's authority outside the intended meta-tx contract/context, achieving unauthorized account action using a signature the user believed was scoped to a different (meta-tx) use case.

Note: Full confirmation that standalone V0 invoke submission is currently permitted end-to-end through the gateway (vs. only accepted historically/for specific legacy accounts) could not be completed within the available search iterations; this should be verified with a Devin session having full repo/gateway config access before treating this as conclusively exploitable in the current network configuration.
