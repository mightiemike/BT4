### Title
Unbounded O(n) migration loop in `DelegatedResourceAccountIndexStore.convert()` allows disproportionate synchronous work per zero-fee `FreezeBalanceContract` transaction - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore.convert(address)` iterates the entire legacy `toAccountsList`/`fromAccountsList` of a single-capsule delegated-resource index and calls `delegate()` once per entry, performing 2 store writes and prefix-key concatenations per entry with no size cap. This method is invoked synchronously inside `FreezeBalanceActuator.delegateResource()` (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:349-350`) whenever `supportAllowDelegateOptimization()` is enabled, for both the owner and receiver address, meaning any account whose legacy list was allowed to grow large before/without the optimization flag can trigger unbounded work the moment it participates again in a delegation, while `FreezeBalanceActuator.calcFee()` always returns 0.

### Finding Description
`convert()` has no bound on `toList`/`fromList` size: [1](#0-0) 

The legacy accumulation path in `FreezeBalanceActuator.delegateResource()` appends to `toAccountsList`/`fromAccountsList` (deduplicated by `.contains()`, but otherwise unbounded) whenever `supportAllowDelegateOptimization()` is false: [2](#0-1) 

Once the fork flag flips to true, any subsequent `delegateResource()` call touching the same owner/receiver address invokes `convert()` on that address, converting the entire accumulated legacy list into individual `delegate()`/store-write pairs synchronously, inside `execute()`, before the fee is charged: [3](#0-2) 

`calcFee()` for `FreezeBalanceActuator` is a fixed 0 regardless of the amount of migration work performed: [4](#0-3) 

None of `validate()`'s checks (address validity, balance, frozen count, frozen duration, `supportUnfreezeDelay`) bound the size of the legacy `toAccountsList`/`fromAccountsList`; there is no cap check anywhere in `FreezeBalanceActuator.validate()` on `accountCapsule`'s delegated-index list length.

### Impact Explanation
This is a resource-exhaustion / metering-invariant violation: a single transaction with fixed zero energy fee can force the node to perform O(n) store reads/writes proportional to a pre-accumulated legacy list size, rather than O(1) work. This falls into the "DoS via the TRON protocol implementation" bounty class — degraded block-processing time for validators/full nodes processing that transaction, disproportionate to the fee actually collected.

### Likelihood Explanation
Exploitability requires two preconditions that limit real-world impact:
1. The attacker must have accumulated a large legacy list **before** `supportAllowDelegateOptimization()` becomes true (or operate on a chain/testnet where that proposal is permanently disabled). On TRON mainnet this optimization has already been enabled for a long time, so accounts have already been converted; new legacy accumulation is no longer possible under current mainnet parameters.
2. Building up the legacy list itself is self-limiting: each `addToAccount`/`addFromAccount` call scans the existing list via `.contains()` (also O(n)), and each entry requires a distinct funded receiver address with `frozenBalance >= 1 TRX`, plus the attacker pays bandwidth for every transaction sent. Building a 50,000-entry list is costly and itself O(n²) for the attacker to construct, somewhat self-throttling the attack, though it does not prevent it.

Given these constraints, this is a real but narrow-window/low-repeatability issue — primarily relevant to older un-upgraded chains, forks that don't enable `AllowDelegateOptimization`, or the historical migration window on mainnet before the proposal took effect. It is not currently exploitable against a properly configured, fully-migrated mainnet node.

### Recommendation
- Cap the size of `toAccountsList`/`fromAccountsList` that can accumulate in the legacy format (e.g., reject further legacy additions past a fixed limit, forcing early migration in smaller batches).
- Alternatively, make `convert()` incremental/paginated (convert a bounded number of entries per call, using an internal cursor) rather than converting the entire list synchronously in one actuator execution.
- Charge fee/energy proportional to the number of legacy entries converted, so `calcFee()` reflects the actual store-write work performed by `convert()`.

### Proof of Concept
JUnit-style outline (mirrors the existing `DelegatedResourceAccountIndexStoreTest`):
```java
// 1. Manually construct a DelegatedResourceAccountIndexCapsule for `address`
//    with toAccountsList and fromAccountsList each containing 50,000 distinct
//    ByteString addresses (simulating pre-fork accumulation), and put() it
//    directly into DelegatedResourceAccountIndexStore (bypassing the
//    self-limiting per-tx build cost, to isolate convert()'s cost).
// 2. Call delegatedResourceAccountIndexStore.convert(address) directly
//    (or invoke it indirectly via FreezeBalanceActuator.execute() with
//    supportAllowDelegateOptimization() forced true).
// 3. Measure wall-clock time of convert() and compare it against
//    FreezeBalanceActuator.calcFee() == 0.
// Expected (violated) invariant: wall-clock time grows linearly with list
// size while charged fee remains constant at 0, demonstrating unmetered
// unbounded work per transaction.
```
Note: this PoC only demonstrates the cost of `convert()` in isolation; it does not by itself prove that an unprivileged attacker can cheaply reach the 50,000-entry precondition on a fully-migrated mainnet, since building the legacy list is only possible before `supportAllowDelegateOptimization()` is enabled (or on chains where it remains disabled), and is itself costly (funded receivers + bandwidth per entry).

```java
  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
```
