### Title
Unhandled `new URL()` exception in `sanitizeHost` on attacker-controlled `host` query parameter causes unhandled promise rejection / process crash - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` decodes an attacker-supplied, base64-encoded `host` query parameter and passes the raw decoded bytes directly into `new URL()` with no try/catch. If the decoded string contains a character forbidden in URL hostnames per the WHATWG URL spec (e.g. NUL, space, `@`, `#`, `\`, control characters), the WHATWG URL parser throws a `TypeError` synchronously. This exception is never caught inside `sanitizeHost`, nor by any of its many callers in auth/session-validation code paths, several of which are `async` request handlers.

`decodeHost` is a trivial `atob(host)` wrapper: [2](#0-1) . The only validation performed before decoding is a base64-charset regex — it does not constrain what bytes the decoded string contains. An anonymous request can supply any `host` value whose base64 decoding contains a character that the WHATWG URL hostname parser rejects (forbidden host code points such as NUL, TAB, space, `@`, `#`, `/`, `\`, `[`, `]`), which makes `new URL(...)` throw a `TypeError` that is not caught anywhere in `sanitizeHost`.

This function is invoked directly (without any surrounding try/catch) from multiple unauthenticated, request-facing code paths, for example:
- `validateShopAndHostParams` (React Router / Remix admin authentication entry point), called at the very start of `authenticate.admin()` before any session validation: [3](#0-2) 
- `redirectToShopifyOrAppRoot` in shopify-app-express, an `async` Express route handler with a non-null assertion right after the call, meaning a thrown error is not converted to a handled response: [4](#0-3) 

Because these call sites are `async` functions that do not wrap the `sanitizeHost` call in `try/catch`, a thrown `TypeError` becomes an unhandled promise rejection rather than a value returned via the existing `InvalidHostError` mechanism (the same function already supports returning `null` or a proper `InvalidHostError` for other invalid-input cases, but not for this one). In Express (Node), an unhandled promise rejection from a route handler is not automatically converted to a 500 response and, depending on Node's `--unhandled-rejections` policy, can crash the process. This is precisely the "panics as error-handling" class described in the report: the code path relies on validated `Result`-style error handling (`InvalidHostError` / `null`) everywhere else, but this specific code path (decoded bytes fed to `new URL()`) is missing that handling and instead panics.

### Impact Explanation
An anonymous, unauthenticated actor who can send a single crafted HTTP GET request (e.g. hitting the OAuth callback / exit-iframe / admin authentication endpoint with a malicious `host` query parameter) can trigger an uncaught exception in a live auth-handling request path. For shopify-app-express specifically, this can manifest as an unhandled promise rejection that is not turned into an HTTP error response, and in server configurations that treat unhandled rejections as fatal (Node's default since v15), this results in a full process crash — denial of service for the whole app, not just the requesting session. For the React Router/Remix packages, whether the process crashes or just returns a generic 500 depends on the surrounding framework error boundary, but at minimum, it represents an auth-handler path failing via panic-style exception instead of the sanitizer's intended `Result`-style (null/throw-controlled) contract.

### Likelihood Explanation
Likelihood is high for exploitation attempts: the `host` parameter is fully attacker-controlled, requires no authentication, no valid session, and no prior state (single anonymous request). The only barrier is finding a byte sequence, once base64-decoded, that trips the WHATWG URL forbidden-host-code-point check — a small and easily discoverable set of characters (e.g. embedding `%00`, space, or `@` in the pre-encoded string).

### Recommendation
Wrap the `new URL()` call inside `sanitizeHost` in a try/catch, and on parse failure fall back to the same `null` / `throwOnInvalid → InvalidHostError` control flow that all other invalid-host cases use, e.g.:
```ts
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  try {
    const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
    ...
  } catch {
    sanitizedHost = null;
  }
}
```
Additionally, audit and remove non-null assertions immediately following `sanitizeHost`/`sanitizeShop` calls in async request handlers (e.g. `redirect-to-shopify-or-app-root.ts`) so that a `null` result (or a thrown `InvalidHostError`) is always explicitly handled rather than assumed valid.

### Proof of Concept
1. Construct a string containing a forbidden URL host code point, e.g. `evil@host` or a string containing a NUL byte: `"a\x00b.myshopify.com"`.
2. Base64-encode it: `host = Buffer.from("a\x00b.myshopify.com").toString('base64')`.
3. Send a GET request to an app's embedded-auth entry point (e.g. `authenticate.admin` route in shopify-app-react-router/remix, or the express `redirectToShopifyOrAppRoot`/callback route) with `?host=<that base64>` and a valid-looking `shop` value.
4. `sanitizeHost` decodes the value with `atob`, then calls `new URL('https://a\x00b.myshopify.com')`, which throws `TypeError: Invalid URL`.
5. Because the calling `async` function does not catch this exception, it surfaces as an unhandled rejection instead of the expected 400/`InvalidHostError` response, at minimum breaking that request and, depending on the runtime's unhandled-rejection policy, crashing the Node process.

export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

      const originsRegex = [
        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

      if (config.domainTransformations) {
        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)
          .flatMap((t) =>
            getTransformationDomains({
              ...config,
              domainTransformations: [t],
            }),
          );
        originsRegex.push(...hostTransformationDomains);
      }

      const hostRegex = new RegExp(`\\.(${originsRegex.join('|')})$`);
      if (!hostRegex.test(hostname)) {
        sanitizedHost = null;
      }
    }
    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }

    return sanitizedHost;
  };
}
