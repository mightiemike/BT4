## Finding confirmed via code reading

`storage/db-tool/src/replay_on_archive.rs::execute_and_verify()` (the `aptos-db-tool replay-verify` command, used to validate archived/backed-up ledger history against local re-execution) validates each replayed transaction purely through `TransactionOutput::ensure_match_transaction_info()`: [1](#0-0) 

That function only checks transaction status, gas used, write-set hash (`state_change_hash`), and event root hash — it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`: [2](#0-1) 

The code itself documents the gap with a `TODO`:
> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

By contrast, the normal chunk-execution path (`ChunkExecutorInner::update_ledger`) does separately validate the checkpoint hashes, by feeding `known_state_checkpoints` / `known_position_state_checkpoints` into `DoStateCheckpoint::run()`: [3](#0-2) 

But the `replay_on_archive` tool bypasses that pipeline entirely: it calls `executor.execute_block(...)` directly and only runs `ensure_match_transaction_info`, so the state-root/checkpoint-hash comparison never happens there.

### Title
Replay-verify tooling accepts a divergent state root as a successful replay — (`File: storage/db-tool/src/replay_on_archive.rs`, `types/src/transaction/mod.rs`)

### Summary
`aptos-db-tool replay-verify`'s per-transaction verification (`execute_and_verify` → `TransactionOutput::ensure_match_transaction_info`) never compares the locally-recomputed state-checkpoint hash (nor hot-state / position-state checkpoint hashes) against the archived `TransactionInfo`'s committed hash. It only checks status, gas, write-set hash, and event root hash.

### Finding Description
`ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) is the sole correctness check used by the replay-verify path. It compares `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event-root hash — but the state root that is actually committed to the accumulator via `TransactionInfo::state_checkpoint_hash()` (and, on chains with the trading-native feature, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) is skipped entirely. This means a state value that is silently omitted, miscomputed, or otherwise diverges from a correct Jellyfish Merkle root — while write set/events/gas/status happen to match — will pass replay verification undetected.

### Impact Explanation
This falls squarely under "Hard-fork-only divergence during commit, replay, restore, or proof verification" — replay-verify is the tool operators/auditors rely on to detect exactly this class of divergence (e.g., after a VM/storage bug or an intentional bad archive). Because the state root is never checked, a corrupted or forked state tree in an archive can be "verified" as correct, defeating the integrity guarantee the tool is meant to provide.

### Likelihood Explanation
The bug is deterministic and always present — every invocation of `replay_on_archive::Verifier::verify` goes through this exact code path with no state-root check, unprivileged (no attacker control needed to trigger; a benign implementation bug or targeted archive corruption would go undetected).

### Recommendation
Extend `ensure_match_transaction_info` (or add a dedicated check in `execute_and_verify`) to also compare the locally-recomputed state checkpoint hash(es) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and (when applicable) `position_state_checkpoint_hash()`, mirroring the validation already performed in `ChunkExecutorInner::update_ledger` via `DoStateCheckpoint`.

### Proof of Concept
Not independently exploitable via a transaction — this is a verification-logic gap, demonstrated by direct code inspection: `execute_and_verify` (storage/db-tool/src/replay_on_archive.rs:392-406) calls only `ensure_match_transaction_info`, whose body (types/src/transaction/mod.rs:2139-2204) has no comparison against `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, confirmed by the in-code TODO acknowledging this exact gap.

**Note on confidence**: I could not fully trace whether any other layer (e.g. outer accumulator-root check across the whole replayed range) indirectly catches this in the `replay_on_archive` tool, since that would require the archived data itself to also be corrupted at the accumulator level, which is out of scope for this single-transaction-output check. This is a tooling/verification integrity gap rather than a live-mainnet consensus/state-commit divergence, so severity should be assessed accordingly.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    pub fn update_ledger(&self) -> Result<()> {
        let _timer = CHUNK_OTHER_TIMERS.timer_with(&["chunk_update_ledger_total"]);

        let (parent_state_summary, parent_position_state_summary, parent_accumulator, chunk) =
            self.commit_queue.lock().next_chunk_to_update_ledger()?;
        let ChunkToUpdateLedger {
            output,
            chunk_verifier,
        } = chunk;

        let txn_infos = chunk_verifier.transaction_infos();
        let known_state_checkpoints = Some(
            txn_infos
                .iter()
                .map(|t| t.state_checkpoint_hash())
                .collect_vec(),
        );
        let known_hot_state_checkpoints =
            output.execution_output.hot_state_root_in_txn_info.then(|| {
                txn_infos
                    .iter()
                    .map(|t| t.hot_state_checkpoint_hash())
                    .collect_vec()
            });
        let compute_trading_native_state_roots =
            output.execution_output.compute_trading_native_state_roots;
        let known_position_state_checkpoints = compute_trading_native_state_roots.then(|| {
            txn_infos
                .iter()
                .map(|t| t.position_state_checkpoint_hash())
                .collect_vec()
        });
        let position_persisted = compute_trading_native_state_roots
            .then(|| ProvablePositionStateSummary::new_persisted(self.db.reader.as_ref()))
            .transpose()?;

            // base supplies cold-key proofs. The known-hash check validates the

            .maybe_parent_position_state_summary(parent_position_state_summary.as_ref())
            .maybe_persisted_position_state_summary(position_persisted.as_ref())
            .maybe_known_position_state_checkpoints(known_position_state_checkpoints)
            .build()?;
