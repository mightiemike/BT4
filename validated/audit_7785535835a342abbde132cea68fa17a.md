## Finding

Based on my investigation, I found a concrete, self-documented state-proof integrity gap in the transaction-output verification helper used by Aptos's replay-verification tooling.

### Title
Replay/debugger transaction verification (`ensure_match_transaction_info`) does not validate the state checkpoint hash, allowing a divergent local ledger state to pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by `db-tool`'s `replay_on_archive` verifier, `aptos-debugger`, and the Move CLI to confirm that locally re-executed transaction outputs match the authenticated `TransactionInfo` fetched from an archive/network (which is itself bound into the ledger's transaction accumulator and signed `LedgerInfo`). It checks status, gas used, write-set hash, and event root hash, but explicitly skips checking `state_checkpoint_hash` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), per its own inline TODO comment.

### Finding Description [1](#0-0) 

The function `ensure_match_transaction_info` performs `ensure!` checks on:
- `status`
- `gas_used`
- write-set hash (`CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`)
- event root hash

but never compares the locally-computed state checkpoint hash (JMT state root produced by executing the transaction) against `txn_info.state_checkpoint_hash()` (or the hot-state/position-state checkpoint hash variants introduced for `TransactionInfoV1`). The comment explicitly states:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is consumed by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which drives mainnet replay-verification: it re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` against the authenticated `expected_txn_infos` pulled from the backup/archive to decide pass/fail. [2](#0-1) 

Because the state checkpoint hash is the actual Sparse-Merkle/Jellyfish-Merkle state root committed on-chain for that version, and this is the one value in `TransactionInfo` that authenticates the resulting global state (as opposed to just the write-set bytes of that one transaction), skipping it means the verifier can silently miss a state root divergence: e.g., differences accumulated from prior transactions' state application, or bugs in how the state tree is built (independent of the write-set hash of the single transaction being checked), would not be caught by this tool even though the write-set-hash and event-hash checks pass.

### Impact Explanation
This breaks the "authenticated ... proof-bearing responses must stay bound to the right ledger version, root" invariant for the replay/verification tooling: an operator or auditor running `db-tool replay-on-archive` (or `aptos-debugger`, or the Move CLI's replay path) to confirm that a node's local execution/state matches the authenticated chain history can get a false "success," while the actual computed ledger/state root has diverged from the one committed and signed in `LedgerInfo`. This is exactly the kind of hard-fork-only/replay divergence class called out as in-scope: a wrong state root can be accepted as "matching" during replay-verify, undermining confidence in archival/consistency guarantees that operators and auditors rely on for hard-fork detection and node validation.

### Likelihood Explanation
The gap is unconditional and always active for every version processed through this verifier — it is not "sometimes" wrong, it is a structural omission (there is no check at all for `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`). It would trigger on any real state-root divergence bug in the VM/state-computation pipeline that doesn't happen to also alter that single transaction's write set or events (which is a very plausible scenario, since state root divergence often stems from cumulative computation over prior transactions, feature-flag-gated hot-state/position-state computations, or from bugs in the state-tree construction path itself, none of which necessarily change the individual transaction's own write set).

### Recommendation
Extend `ensure_match_transaction_info` to also assert that the locally computed state checkpoint hash (when available, e.g., at checkpoint boundaries) equals `txn_info.state_checkpoint_hash()`, and similarly validate `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` when those fields are populated (particularly gating this on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` as the existing TODO suggests), before this tooling is relied upon to declare replay success on any state-root-bearing checkpoint.

### Proof of Concept
1. Run `db-tool replay-on-archive` (or `aptos-debugger`) to replay-verify a version range against an archive.
2. Introduce (or encounter) a bug/behavior change that alters the resulting state tree root for a version but leaves that specific transaction's write set and emitted events unchanged (e.g., an issue in how prior deltas materialize into the state tree, or a hot-state/position-state computation divergence).
3. `Verifier::execute_and_verify` calls `ensure_match_transaction_info`, which only checks status/gas/write-set-hash/event-root-hash and returns `Ok(())` despite the state checkpoint hash mismatch. [3](#0-2) 
4. The tool reports the replay as verified/successful for that version even though the locally committed state root differs from the authenticated one bound in the archived `TransactionInfo`/`LedgerInfo`.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
```
