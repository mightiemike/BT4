### Title
`check_microblock_header_signer` fails to enforce `mblock_header_1.sequence == mblock_header_2.sequence`, allowing poison-microblock slashing on non-conflicting microblocks - (File: `stackslib/src/chainstate/stacks/db/transactions.rs`)

### Summary
`check_microblock_header_signer` only verifies that both headers recover to the same public-key hash; it never checks that the two headers share the same `sequence` (or `prev_block`), even though a valid poison-microblock proof requires two *conflicting* microblocks signed by the same miner at the *same* position in the stream. `handle_poison_microblock` then unconditionally accepts `mblock_header_1.sequence` as the "fork point" and calls `insert_microblock_poison`, letting an attacker submit two entirely legitimate, sequential (non-conflicting) microblocks from an honest miner and still get a poison report recorded and rewarded.

### Finding Description
The claimed invariant is: a stored poison report must correspond to `mblock_header_1.sequence == mblock_header_2.sequence` AND both signatures verifying under the same miner pubkey. Only the pubkey-equality half is enforced: [1](#0-0) 

`check_microblock_header_signer` recovers `pkh1`/`pkh2` from each header via `check_recover_pubkey()` and only rejects when `pkh1 != pkh2`. There is no comparison of `mblock_header_1.sequence` vs `mblock_header_2.sequence`, and no comparison of `prev_block` or `tx_merkle_root` to prove the two headers actually conflict.

`handle_poison_microblock` then proceeds using only `mblock_header_1.sequence` as the reported fork sequence, never referencing or validating `mblock_header_2.sequence` at all: [2](#0-1) [3](#0-2) 

The stronger check that compares `sequence`, `prev_block`, and `version` for equality exists only in the **mempool-admission** path (`MemPoolRejection`), which gates transactions submitted through RPC/mempool but is not part of `process_transaction_payload` / `handle_poison_microblock`, the actual consensus-critical state-transition function invoked when a block is processed: [4](#0-3) 

Because a miner assembling their own block does not have to route the transaction through mempool admission, this equality check can be bypassed entirely: a `PoisonMicroblock` transaction with `mblock_header_1.sequence != mblock_header_2.sequence` (but the same signer) can be included directly in a block and will pass `process_transaction_payload` -> `handle_poison_microblock` unmodified, since the consensus-level check (`check_microblock_header_signer`) does not verify sequence equality.

**Exploit flow:** An honest miner publishes a normal microblock stream, e.g. sequence 5 and sequence 6, both properly signed by the miner's own key (this is completely normal, non-conflicting operation — no double-sign occurred). An attacker (or the miner producing their own next block) takes these two headers, submits `PoisonMicroblock(header_seq_5, header_seq_6)` directly in a block. `check_microblock_header_signer` succeeds because `pkh1 == pkh2` (same miner key signed both, as expected in normal operation). `handle_poison_microblock` records a poison report at `mblock_header_1.sequence` (5) for that miner's pubkey hash, crediting the reporting principal with the commission and effectively slashing an honest, non-equivocating miner. No actual fork/double-sign at the same sequence number was ever proven.

The two-different-miner-keys vector described in the question is correctly rejected by `pkh1 != pkh2`, but the mismatched-sequence vector is not blocked at the consensus layer.

### Impact Explanation
This causes reward mis-payment: an honest miner who never double-signed at a given sequence number can have their coinbase incorrectly flagged as poisoned, and the "reporter" (who could be the attacker, or a competing/malicious node) receives the commission that should have gone to the honest miner. This is a real theft of block reward triggerable by any unprivileged party who can observe two microblocks broadcast by any miner (which are inherently public) and craft/submit the `PoisonMicroblock` transaction — no majority stake or admin access required. This matches the Critical category "block-reward theft/double-payment" defined in scope, since it lets an attacker redirect an honest miner's earned coinbase commission without ever proving genuine miner misbehavior.

### Likelihood Explanation
Preconditions: the target miner must have signed at least two microblocks in a stream (extremely common/mandatory workflow, not a rare edge case), and the target microblock public key hash must still be within the `MINER_REWARD_MATURITY` maturation window (checked separately and does not block this bug). The attacker needs no BTC investment beyond an ordinary Stacks transaction fee to submit the `PoisonMicroblock` tx, and no elevated stake or role — a bare unprivileged Stacks account. This is repeatable against any miner who has produced a multi-microblock stream, making it a low-cost, broadly repeatable attack.

### Recommendation
Add an explicit equality check in `check_microblock_header_signer` (or immediately in `handle_poison_microblock`) requiring `mblock_header_1.sequence == mblock_header_2.sequence` (and ideally that the headers are not byte-identical, i.e., they actually differ in content/signature to prove equivocation at that same position), mirroring the check already present in the mempool-admission path (`blocks.rs` ~line 6845), and reject the transaction with `Error::InvalidStacksTransaction` otherwise.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
