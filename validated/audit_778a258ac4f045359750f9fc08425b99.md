### Title
Event-plugin block loading service permanently self-terminates on a single transient exception, silently halting `event-subscribe` block/transaction triggers - ([File: framework/src/main/java/org/tron/core/services/event/BlockEventLoad.java])

### Summary
`BlockEventLoad.init()` schedules a periodic task that calls `load()` and, on any exception, invokes `close()` which shuts down the underlying `ScheduledExecutorService`. This is the same bug class as the reported EVM channel task: a long-running background worker that is supposed to run indefinitely terminates itself permanently in response to a single (often transient) failure, while the rest of the node continues operating normally, unaware that the dependent subsystem has stopped.

### Finding Description
`BlockEventLoad.init()` schedules `load()` to run every 100ms via a single-thread `ScheduledExecutorService`. When `load()` throws, the handler does not just log the error and let the schedule continue firing — it calls `this.close()`, which calls `executor.shutdown()`, permanently terminating the scheduled task: [1](#0-0) 

`load()` itself can throw for reasons unrelated to any corruption — e.g. `blockEventGet.getBlockEvent(tmpNum)` reading blocks that momentarily are not yet available during a fork/reorg race, or any transient I/O exception while fetching a block: [2](#0-1) 

Once `executor.shutdown()` has been called, `scheduleWithFixedDelay` never fires again — there is no restart logic anywhere in the codebase for this specific executor (unlike `DposTask`, `AdvService`, `SyncService`, `ResilienceService`, etc., whose scheduled tasks only log the exception and let the fixed-delay schedule continue). The only components that call `blockEventLoad.init()` again are `EventService.init()` and `HistoryEventService.initEventService()`, both of which run once during node startup / after a full history resync, not on every failure: [3](#0-2) [4](#0-3) 

Because of this, once `load()` throws even once after startup, `BlockEventLoad` will never again pick up new blocks; `BlockEventCache` stays frozen at whatever block it last loaded, and `RealtimeEventService.add(...)`/`SolidEventService` never receive further `Event`s for `event-subscribe` block/transaction triggers derived from `BlockEventCache` (used when `EventPluginLoader.getInstance().getVersion() == 1`, per `Manager.blockTrigger`): [5](#0-4) 

Meanwhile the node itself continues producing/validating blocks and serving RPC normally — nothing in the health/liveness surface reflects the fact that the event subscription pipeline has silently died, exactly mirroring the reported pattern where the plugin keeps serving RPC while the underlying execution channel is dead.

### Impact Explanation
Downstream consumers relying on `event-subscribe` (version-1 plugin) block/transaction triggers (indexers, exchanges' deposit-detection services, monitoring/alerting) stop receiving new events indefinitely after a single transient failure, with no automatic recovery and no explicit alarm — only a single ERROR log line. This can cause silent divergence between on-chain state and off-chain systems that depend on this event feed (e.g., missed deposits/withdrawals notifications), which for exchange/bridge-style integrations is a meaningful availability/integrity issue, though it does not directly corrupt on-chain consensus state.

### Likelihood Explanation
`load()`'s call path (`blockEventGet.getBlockEvent`) touches block/DB lookups that can transiently fail (e.g. during forks, khaos DB inconsistency windows, or momentary I/O errors), so a single spurious exception is plausible during normal node operation over long uptimes — it does not require a malicious actor, just an unlucky transient condition, which is analogous to the "network issue" trigger described in the original report.

### Recommendation
Change the `catch` block in `BlockEventLoad.init()` to only log the exception (as all sibling services — `RealtimeEventService`, `SolidEventService`, `AdvService`, `SyncService`, etc. — already do) and let `scheduleWithFixedDelay` continue firing, instead of calling `close()`/`executor.shutdown()`. If a genuine unrecoverable error needs to stop the service, it should be explicitly distinguished from transient failures, and ideally paired with an automatic restart mechanism and/or an exposed health metric so operators can detect the stall.

### Proof of Concept
1. Configure a node with `event-subscribe` plugin version 1 enabled (`EventPluginLoader.getInstance().getVersion() == 1`), enabling `BlockEventLoad`/`RealtimeEventService` block/transaction triggers.
2. Cause `blockEventGet.getBlockEvent(tmpNum)` inside `load()` to throw once (e.g., by forcing a transient `ItemNotFoundException`/`BadItemException` on the requested block, which can occur naturally during a fork/reorg race, or by directly injecting an exception in a test via reflection/mocking).
3. Observe the log line `"Event load service fail."` followed by `"Event load service close."`.
4. Continue producing new blocks on the node; observe that `BlockEventCache` no longer advances and no new `block`/`transaction` triggers are emitted to the plugin, even though the node's block production/validation and RPC continue to function normally — confirming the permanent silent halt of the event-loading task.

  public synchronized void load() throws Exception {
    long cacheHeadNum = BlockEventCache.getHead().getBlockId().getNum();
    long tmpNum =  manager.getDynamicPropertiesStore().getLatestBlockHeaderNumber();
    if (cacheHeadNum >= tmpNum) {
      return;
    }
    synchronized (manager) {
      tmpNum =  manager.getDynamicPropertiesStore().getLatestBlockHeaderNumber();
      if (cacheHeadNum >= tmpNum) {
        return;
      }
      if (tmpNum > cacheHeadNum + MAX_LOAD_NUM) {
        tmpNum = cacheHeadNum + MAX_LOAD_NUM;
      }
      List<BlockEvent> blockEvents = new ArrayList<>();
      List<BlockEvent> rollbackBlockEvents = new ArrayList<>();
      BlockEvent tmp = BlockEventCache.getHead();

      BlockEvent blockEvent = blockEventGet.getBlockEvent(tmpNum);
      blockEvents.add(blockEvent);
      while (!blockEvent.getParentId().equals(tmp.getBlockId())) {
        tmpNum--;
        if (tmpNum == tmp.getBlockId().getNum()) {
          rollbackBlockEvents.add(tmp);
          tmp = BlockEventCache.getBlockEvent(tmp.getParentId());
        }
        blockEvent = blockEventGet.getBlockEvent(tmpNum);
        blockEvents.add(blockEvent);
      }

      rollbackBlockEvents.forEach(e -> realtimeEventService.add(new Event(e, true)));

      List<BlockEvent> l = Lists.reverse(blockEvents);
      for (BlockEvent e: l) {
        BlockEventCache.add(e);
        realtimeEventService.add(new Event(e, false));
      }
    }
  }
