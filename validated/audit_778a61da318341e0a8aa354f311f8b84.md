### Title
`TransactionOutput::ensure_match_transaction_info` never checks state/hot-state/position checkpoint hashes, letting replay-verify accept a diverged state root - (File: types/src/transaction/mod.rs)

### Summary
`ensure_match_transaction_info` is the sole check used by replay/debug tooling (`db-tool replay-on-archive`, `aptos-debugger`, `aptos move` CLI) to confirm that locally re-executed transaction output matches the version's committed, ledger-info-authenticated `TransactionInfo`. It validates status, gas, write-set hash (`state_change_hash`) and event root hash, but the code itself documents that it deliberately skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks four things — `status`, `gas_used`, write-set hash vs `state_change_hash`, and event root hash — then returns `Ok(())` without ever comparing the locally-computed state checkpoint root(s) to the ones baked into the fetched, ledger-info-proven `TransactionInfo`. The comment in the code confirms this is a known, acknowledged gap: [2](#0-1) 

`TransactionInfoV1` carries three separate roots that bind a version to a specific ledger state: `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (see the builder at [3](#0-2) ). These are exactly the values that the executor computes independently on each node via `DoStateCheckpoint::run` / `get_state_checkpoint_hashes` ( [4](#0-3) ) and later assembles into `TransactionInfo` in `DoLedgerUpdate::run` ( [5](#0-4) ) before it is accumulated into the ledger-info-signed transaction accumulator.

The consumer of the vulnerable function is `Verifier::execute_and_verify` in the mainnet replay-verify tool: it re-executes archived transactions through `AptosVMBlockExecutor`, then calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` where `expected_txn_infos[idx]` was read from (and is presumed authenticated against) the archive DB [6](#0-5) . Because the checkpoint hashes are excluded from the comparison, if the locally re-executed state root, hot-state root, or the (currently being rolled out) native "position" state root diverges from what is recorded in the archived `TransactionInfo` — e.g. due to a JMT/state-summary computation bug, a schema/serialization mismatch, or a corrupted archive that still carries a correct write-set hash and event root — `ensure_match_transaction_info` returns `Ok(())` and the replay-verify tool reports success. The tool's entire purpose is to catch exactly this class of divergence across large historical ranges; this gap defeats that purpose for the state-checkpoint dimension.

### Impact Explanation
This breaks the "authenticated data must stay bound to the right root" invariant required by the state-integrity gate: a wrong/corrupted state (or hot-state/position-state) root that differs from the correct VM result can pass replay-verify undetected, because the only place this comparison is meant to happen silently skips the checkpoint-hash fields. Since replay-verify against archives is a primary tool operators and Aptos Labs use to certify that historical execution/storage stayed correct (including hard-fork-adjacent state divergences), a bug in state-checkpoint computation, hot-state computation, or the new trading-native "position" state root could go unnoticed even though `ensure_match_transaction_info` returns success. The severity is amplified because this is explicitly called out as gating `COMPUTE_TRADING_NATIVE_STATE_ROOTS` — the code comment states this must be fixed "before enabling" that feature, indicating the developers recognize this is not yet safe.

### Likelihood Explanation
Today (with `COMPUTE_TRADING_NATIVE_STATE_ROOTS` presumably off) the practical exposure is limited to the state/hot-state hashes, which is still a live gap — nothing in `execute_and_verify` or in `ensure_match_transaction_info` will surface a state root mismatch. The `V1` fields are already fully wired (`TransactionInfoV1` construction includes `state_checkpoint_hash` and `hot_state_checkpoint_hash` unconditionally), so the missing check isn't merely a future-only concern; it applies now to the state and hot-state roots and will additionally apply to positions once that feature ships.

### Recommendation
Extend `ensure_match_transaction_info` to accept (or independently recompute) the state checkpoint hash, hot-state checkpoint hash, and position-state checkpoint hash for checkpoint-marked transactions, and `ensure!` they match `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` respectively before returning `Ok(())`. This should be done prior to relying on replay-verify for any release that turns on hot-state or native-position roots, and ideally before mainnet reliance on this tool for regular state-integrity certification.

### Proof of Concept
Not directly exploitable by an external attacker (this is a verification-tooling gap, not a consensus-path bug), so no transaction-level PoC applies. Conceptual repro:
1. Archive a version whose `TransactionInfo` (`V1`) has an incorrect `state_checkpoint_hash` (e.g. due to a hypothetical JMT computation bug) while write-set bytes/hash, events, gas and status remain correct.
2. Run `db-tool replay-on-archive` for that version range.
3. `Verifier::execute_and_verify` re-executes the transaction, gets a `TransactionOutput` whose write set hash and events match, and calls `ensure_match_transaction_info` — which returns `Ok(())` despite the state root divergence, because the function never reads or compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
4. The tool reports zero failed transactions, certifying a divergent state root as correct.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
