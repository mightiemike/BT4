This confirms the analysis. The critical binding is in `NakamotoChainState::validate_normal_nakamoto_block_burnchain`, which looks up the leader key strictly by `block_commit.key_block_ptr`/`block_commit.key_vtxindex` — i.e., the *specific* `LeaderKeyRegisterOp` that the winning block-commit's own author pointed to when it was broadcast on the burnchain.Based on tracing the exact code path, the claimed vulnerability does not hold.

**The equality claimed to be broken:** `recovered_miner_hash160` (from `NakamotoBlock::recover_miner_pubkh`) must equal `miner_pubkey_hash160` (from `LeaderKeyRegisterOp::interpret_nakamoto_signing_key()` of the leader key referenced by the winning block-commit).

**Trace:**
1. `check_tenure_tx` only checks internal self-consistency: `tc_payload.pubkey_hash == recovered_miner_hash160`, both derived from the block itself (the tenure-change payload the miner authored and the miner's own signature). This has nothing to do with the burnchain-registered leader key, so it is not the guard that binds the memo hash160 to the block signer — that binding happens elsewhere. [1](#0-0) 

2. The actual cross-check against the burnchain-registered signing key is `check_miner_signature(miner_pubkey_hash160)`, called from `validate_normal_against_burnchain`. [2](#0-1) 

3. `miner_pubkey_hash160` is derived from the specific `LeaderKeyRegisterOp` looked up via `block_commit.key_block_ptr` / `block_commit.key_vtxindex` — i.e., exactly the burn-chain leader-key op that the **winning block-commit's own author** pointed to when they broadcast their block-commit. [3](#0-2) 

**Why the attack scenario fails:** For an attacker's separately-registered `LeaderKeyRegisterOp` (with attacker's own memo/Hash160) to be used in place of the honest winning miner's registration, the attacker would need the winning block-commit itself to set `key_block_ptr`/`key_vtxindex` to point at the attacker's op instead of the honest miner's own op. But `key_block_ptr`/`key_vtxindex` are fields the block-commit's own signer chooses when broadcasting it — they are not attacker-controllable unless the attacker *is* the one broadcasting the winning block-commit. And winning the sortition with that commit requires producing a valid VRF proof under the VRF public key of whichever `LeaderKeyRegisterOp` is referenced (verified later via `check_normal_coinbase_tx`/`validate_vrf_seed`), which requires the corresponding VRF private key. [4](#0-3) 

So there are only two possibilities: (a) the attacker registers their own `LeaderKeyRegisterOp`+VRF key+block-commit — in which case `miner_pubkey_hash160` and `recovered_miner_hash160` are both the attacker's own values, self-consistent, no divergence; or (b) the attacker tries to reuse the honest miner's VRF proving key/winning commit — impossible without the honest miner's VRF private key, which the attacker (an unprivileged minority participant) does not possess. There is no code path by which a memo hash160 from one `LeaderKeyRegisterOp` gets substituted for the leader key actually pointed to by a different, honest party's winning block-commit.

The memo/Hash160 and VRF public key are set atomically within a single `LeaderKeyRegisterOp` (`set_nakamoto_signing_key`/`interpret_nakamoto_signing_key` both operate on the same op's `memo` field), and the lookup at validation time is keyed by the block-commit's own `key_block_ptr`/`key_vtxindex`, not by any attacker-supplied indirection. [5](#0-4)
