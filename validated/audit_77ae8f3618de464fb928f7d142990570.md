### Title
Per-transaction bouncer weight computation recomputes the full accumulated executed-class-hash set every call, causing quadratic block-building cost - (File: crates/blockifier/src/bouncer.rs)

### Summary
Analogous to the Renzo `calculateTVLs` finding, `Bouncer::try_update` in the sequencer's blockifier recomputes a value derived from *all state accumulated so far in the block* on every single incoming transaction, rather than incrementally tracking it. This turns per-transaction bookkeeping that should be O(marginal work) into O(block-so-far) work, making total block-building cost quadratic in the number of transactions/declared classes within a block.

### Finding Description
`Bouncer::try_update` is invoked once per transaction added to a block (during proposing and validating blocks), and computes the "marginal" (new) resources contributed by the transaction by diffing the transaction's data against the bouncer's already-accumulated state: [1](#0-0) 

The key call is `self.get_executed_class_hashes()`, which is *not* an O(1) accumulated-set reference but a fresh reconstruction that iterates over and clones every key that has been accumulated in the block so far: [2](#0-1) 

Because `try_update` calls this reconstruction function on every transaction, and the accumulated map (`casm_hash_computation_data_sierra_gas.class_hash_to_casm_hash_computation_gas`) grows with the number of distinct classes executed in the block, the cost of computing `marginal_executed_class_hashes` for the n-th transaction is proportional to the number of distinct classes accumulated by transactions 1..n-1. Summed across a full block, this is the same nested/quadratic pattern as Renzo's `calculateTVLs`: work that should be O(1) incremental "push" bookkeeping is instead "pulled" and fully recomputed on every call, scaling with the size of already-processed state rather than with the marginal transaction's own footprint.

This directly parallels the audited bug class: a function reachable on every ordinary transaction (block building path, used by both the proposer and the validator per the sequence diagrams) whose cost grows with the total number of prior operations in the same execution context (block), not with the caller's own transaction size.

### Impact Explanation
If an adversarial sequence of transactions (e.g., many `declare` transactions each introducing a new distinct class, or many invokes triggering library calls to many distinct classes) is included in a single block, the cumulative cost of `try_update`'s cloning of `get_executed_class_hashes()` grows quadratically with the number of distinct classes touched in that block. This can:
- Slow down block *proposal* (the proposer node building the block), risking missed block-time deadlines.
- Slow down block *validation* on all other validators executing `try_update` for the same block (since `validate_block` re-executes transactions through the same bouncer logic), causing consensus timeouts/failures — an "unable to confirm new transactions" scenario if the pathological block cannot be validated within the round timeout across the network.
- Because it is reachable by a single, ordinary account submitting Cairo transactions/declares (no privileged or malicious-node role required to *trigger* the underlying growth — an unprivileged sender can submit transactions/declares that populate `executed_class_hashes` for the block), this satisfies the reachability constraint of "unprivileged transaction sender."

The bouncer is specifically the resource-accounting mechanism meant to bound per-block work (`bouncer_config.has_room`), yet the accounting mechanism itself introduces unbounded (non-linear) overhead as a side effect of its own bookkeeping — the same "TVL-oracle recomputation" anti-pattern flagged in the source report.

### Likelihood Explanation
Medium. The `HashSet` clone/collect on each `try_update` call is real overhead that scales with the block's accumulated distinct-class count. However, the practical severity depends on:
- The actual number of distinct classes reachable per block under existing bouncer weight caps (e.g., `n_steps`/gas caps may already bound how many distinct classes fit in one block before this becomes dominant).
- Whether hashing/cloning `ClassHash` (a felt) at scale of hundreds/thousands of entries per block is enough to meaningfully delay block building/validation versus other per-tx costs.
Without empirical profiling (analogous to the PoC transaction gas measurements in the Renzo report), it is uncertain whether current bouncer resource limits already keep this from being a severe, block-halting issue, or whether it can be pushed close to consensus round timeouts. This uncertainty should be resolved via benchmarking rather than further static review.

### Recommendation
Replace the "pull and fully recompute" pattern with an incrementally maintained (pushed) structure:
- Maintain `self.accumulated_weights`'s executed-class-hash set as a persistent `HashSet<ClassHash>` field updated incrementally in `update()` (already extended via `.extend(...)` at line ~715), and have `try_update` diff directly against that persistent set instead of calling `get_executed_class_hashes()` (which reconstructs the set from a different map's keys each time).
- Audit other bouncer/`try_update`-adjacent computations for similar "recompute from full accumulated state" patterns, since the report is specifically about the general anti-pattern of pulling large aggregate state from scratch on every user-triggered operation rather than maintaining running aggregates.

### Proof of Concept
1. Construct a block proposal (or validation) with a sequence of `n` distinct `declare`/invoke transactions, each touching a new, previously-unseen class hash.
2. For each transaction `i`, `Bouncer::try_update` calls `self.get_executed_class_hashes()`, which clones all `i-1` previously accumulated class hashes into a new `HashSet`, then computes `.difference(...)`.
3. Summed across the block, this yields O(n²) hashing/cloning work purely from bookkeeping, independent of the actual execution cost of the transactions, mirroring the `n-OD x n-Tokens` quadratic blowup in the Renzo `calculateTVLs` finding.
4. Confirming the concrete wall-clock/resource impact at realistic block sizes (to determine if it threatens consensus round timeouts) requires running/benchmarking `try_update` under `crates/blockifier/src/bouncer_test.rs`-style test harnesses with an increasing count of distinct executed class hashes — this was not performed here and is noted as an open verification step.
