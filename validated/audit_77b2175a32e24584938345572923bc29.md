## Title
Signature-length validation gap allows padded/oversized signatures to pass consensus checks - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
The external report describes a replay/dup-check bypass caused by hashing signature bytes that can contain attacker-controlled extra trailing bytes, so a semantically identical signature can produce a different digest and defeat an "already processed" check. In java-tron there is no digest-of-signature used as a claim/dup key — transaction identity (`getTransactionId()`) is derived only from `Transaction.raw` bytes, not from the signature [1](#0-0) , so the exact bug class (digest-of-signature as replay key) does not reproduce. However, the same root cause family — insufficient/inconsistent validation of signature byte length before it is consumed by security-critical logic — is concretely present as a validation gap between admission-time and consensus-time signature checks.

### Finding Description
Two different signature-length checks exist in the codebase for the same signature bytes:

- The strict admission check `SignUtils.isValidLength(int size)` enforces a fixed range `[PER_SIGN_LENGTH, MAX_PER_SIGN_LENGTH]` and is used at RPC broadcast (`Wallet.broadcastTransaction`) and P2P transaction ingress (`TransactionsMsgHandler.check`) [2](#0-1) [3](#0-2) [4](#0-3) .
- The consensus-critical multi-sig weighting path `TransactionCapsule.checkWeight` only rejects signatures shorter than 65 bytes (`sig.size() < 65`), with **no upper bound**, and this is explicitly documented as intentional to tolerate "historical on-chain signatures that carry trailing padding bytes" [5](#0-4) [2](#0-1) .

Because ECDSA recovery (`SignUtils.signatureToAddress` / `ECKey.signatureToAddress`) only consumes the fixed 65-byte r/s/v prefix and silently ignores any trailing bytes, a signature padded with arbitrary extra bytes recovers to the same address as the canonical 65-byte signature. This is directly demonstrated by the test suite (`testApprovedListSigTruncate`, `testSignWeightSigTruncate`), where a 70-byte signature (65 bytes + 5 junk bytes) is accepted and silently truncated to 65 bytes for the response, while still resolving to the correct owner/weight [6](#0-5) [7](#0-6) .

The consequence: a transaction whose signature bytes are arbitrarily long (well beyond `MAX_PER_SIGN_LENGTH`, e.g. hundreds of bytes) will be **rejected** by `broadcastTransaction`/`TransactionsMsgHandler.check` (RPC/P2P admission), but the same transaction, if it reaches `Manager.processTransaction` → `validateSignature` → `checkWeight` through another path (e.g. included directly in a block produced by a witness, or via any code path that skips the admission-layer length check), would be **accepted** because `checkWeight` never bounds the upper length. This is a variable-length, attacker-controlled byte blob (the padding) that is fed into consensus-path signature validation with a checking discipline weaker than the one enforced at the network edge — the same class of bug as the audit finding (attacker-controlled extra bytes altering the outcome of a security check that should be canonical).

### Impact Explanation
If a padded signature can reach the consensus/block-processing path without going through the strict admission check (e.g. included in a produced block, replicated via block sync, or state-sync), full nodes validating that block via `Manager.processTransaction` → `trxCap.validateSignature` → `checkWeight` would still accept it, since only the lower bound is enforced. This creates two different notions of "valid transaction" between the P2P/RPC ingress layer and the consensus/replay layer, which is a source of potential DoS (non-witness nodes rejecting a transaction/block that other logic paths accept), inconsistent validation between full nodes, or unexpected acceptance of malformed data in permission-weighted multisig transactions. It does not, by itself, allow forging a signature or double-claiming a reward (unlike the original Move bug), because java-tron's replay protection (`getTransactionId`) is keyed off raw transaction data, not signature bytes.

### Likelihood Explanation
Moderate-to-low. Exploitation requires finding an RPC/P2P-external-facing route that can inject an over-length-signature transaction directly into a path that reaches `checkWeight`/`validateSignature` without passing through `SignUtils.isValidLength` (used at `Wallet.broadcastTransaction` and `TransactionsMsgHandler.check`). I was not able to fully verify all remaining call sites of `checkWeight`/`validatePubSignature`/`validateSignature(Transaction, ...)` in the time available (the last grep for the static overload of `validateSignature(Transaction ...)` did not return before the session ended), so it is uncertain whether any anonymous-RPC-reachable path exists that bypasses the strict check while still reaching `checkWeight`. This is a documented, intentional design tradeoff (per the code comment) rather than an obviously exploitable oversight, but the asymmetry itself is a real gap worth flagging.

### Recommendation
- Enforce a single canonical signature-length check (`PER_SIGN_LENGTH` to `MAX_PER_SIGN_LENGTH`) at every point signature bytes are consumed for consensus decisions, including `TransactionCapsule.checkWeight`, not only at RPC/P2P admission.
- If backward compatibility with historically padded signatures is required, explicitly canonicalize (truncate) all signatures to `PER_SIGN_LENGTH` immediately upon deserialization/ingestion, before any hashing, weighting, or storage — the same remediation style used in the original report ("validate length … using canonical index" rather than trusting caller-supplied padding).
- Audit all remaining callers of `checkWeight`, `validatePubSignature`, and `validateSignature` to confirm none are reachable from an anonymous RPC/P2P/broadcast path without first passing through `SignUtils.isValidLength`.

### Proof of Concept
1. Craft a `Transaction` with a valid 65-byte ECDSA signature for a multisig-permissioned account, then append 5+ arbitrary junk bytes (as done in `testSignWeightSigTruncate`) [8](#0-7) .
2. Submit via `Wallet.broadcastTransaction` — rejected only because `SignUtils.isValidLength` bounds the upper size to `MAX_PER_SIGN_LENGTH` [3](#0-2) .
3. Feed the same oversized-signature transaction directly to `TransactionCapsule.checkWeight` (as exercised by `getTransactionSignWeight`/`getTransactionApprovedList` in the test suite) — it is accepted and the permission weight/approval succeeds, proving the consensus-path check (`sig.size() < 65`) has no upper bound [9](#0-8) .
