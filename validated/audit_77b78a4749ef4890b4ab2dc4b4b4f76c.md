## Verdict: Real hang mechanism exists, but not through the proof idea's proposed cause (a naked partitioner bug); it stems from a static/dynamic write-set mismatch. Path to mainnet is unconfirmed.

### Summary
The proof-of-concept as literally stated ("dependency edge is created but the corresponding sender never calls `set_value`") does not describe a bug in `RemoteStateValue`/`CrossShardStateView` themselves — the partitioner always builds `required_edges` and `dependent_edges` as a matched pair from the same static analysis pass [1](#0-0) , so a required edge with no matching dependent edge cannot arise from partitioning logic alone. However, there is a genuine, unprivileged-input-triggerable divergence between the **statically predicted write set** used to build cross-shard edges and the **actual runtime write set** produced by VM execution, and that divergence can leave a `RemoteStateValue` permanently `Waiting`.

### Finding Description
`AnalyzedTransaction::write_hints` — the set of storage locations used by the partitioner to build both `required_edges` (consumer side) and `dependent_edges` (producer side) — is derived by pure static pattern-matching on the transaction's entry-function type, independent of actual runtime state or execution outcome [2](#0-1) . For example, `coin::transfer`/`aptos_account::transfer` unconditionally predicts writes to the sender and receiver's `CoinStore`/`AccountResource` [3](#0-2) .

At runtime, `CrossShardCommitSender::send_remote_update_for_success` only sends a `RemoteTxnWriteMsg` for a predicted key if that key is actually present in the transaction's real `TransactionOutput::write_set()` [4](#0-3) . If the transaction aborts or takes a branch where the predicted write never actually occurs (e.g., insufficient balance causing `coin::transfer` to abort before touching the receiver's `CoinStore`), the actual write set omits that key, and `send_remote_update_for_success` never emits a message for it. On the consumer shard, the corresponding `RemoteStateValue` was created in `RemoteValueStatus::Waiting` [5](#0-4)  and only transitions to `Ready` via `set_value` [6](#0-5) , which never happens. Any thread calling `get_value()` for that key blocks forever on the condvar loop [7](#0-6) , and the executing shard's `AptosVMBlockExecutorWrapper::execute_block` call inside `execute_transactions_with_dependencies` never returns, so no `TransactionOutput` is produced for that sub-block [8](#0-7) .

### Impact Explanation
If this sharded-executor path were used for mainnet block commitment, this would be a full liveness/state-corruption bug: the sub-block never returns, the block never assembles a complete write set, and consensus execution stalls or errors depending on how the caller times out. This is unprivileged-input-driven because any ordinary sender can submit a transaction that they know will abort at runtime (e.g., a `coin::transfer` with insufficient balance, sent alongside a colliding cross-shard transaction) without any special privilege.

### Likelihood Explanation — key caveat that blocks acceptance
I could not confirm this path is reachable from real, unprivileged, consensus-committed mainnet transactions:
- `Transaction::get_read_write_hints` only implements `coin::transfer`, `aptos_account::transfer`, and `aptos_account::create_account`; every other entry function, script, or multisig transaction hits `todo!("Only entry function transactions are supported for now")`, which panics [9](#0-8) . A production block containing arbitrary transaction types would panic immediately under this analysis, which is incompatible with how mainnet blocks are actually populated. This strongly suggests the block-partitioner/`AnalyzedTransaction` sharded path is not the live consensus execution path today, but rather an experimental/benchmark-only feature (referenced from `aptos-transaction-benchmarks`, `executor-service` test utilities, and integration tests) [10](#0-9) .
- I was not able to fully trace whether `VMBlockExecutor::execute_block_sharded` / `ExecutableTransactions::Sharded` is wired into the actual consensus `StateComputer::compute` path that validators use for mainnet block execution, versus only being reachable via test harnesses and the `executor-service` remote-execution demo binary [11](#0-10) .

Given the `todo!()` panic on non-whitelisted transaction types, it is unlikely this sharded path currently processes general mainnet blocks; if it did, any block with a module publish, generic Move script, or generic entry function would already panic before reaching the cross-shard-message logic at all. This makes the specific hang scenario secondary to a more fundamental "produces a panic on ordinary transactions" issue, and I cannot confirm mainnet reachability with the tools available.

### Recommendation
- Confirm (via full repo/CI configuration, not visible from the index) whether `ExecutableTransactions::Sharded` / the block-partitioner is enabled for actual mainnet consensus execution, or is gated behind an experimental/benchmark-only feature flag.
- If it is reachable in production, `send_remote_update_for_success` must send an explicit "no write" completion signal for every predicted `dependent_edge` key regardless of whether the real write set contains it, so that `RemoteStateValue::set_value(None)` is always eventually called, and `get_value`/`CrossShardCommitReceiver` should also honor a bounded timeout with error propagation instead of blocking indefinitely.
- Because I could not fully verify the wiring between `do_get_execution_output.rs`'s sharded branch and the real consensus pipeline within the indexed content, a Devin session with full repository access is recommended to confirm production reachability before treating this as a mainnet-exploitable finding.

### Proof of Concept
Not executable from the indexed code alone — reachability confirmation requires tracing feature flags/config wiring (e.g., `AptosVM::get_num_shards()`, on-chain config gating `ExecutableTransactions::Sharded`) that are outside what the index surfaced. The mechanism itself (predicted-vs-actual write set divergence via an aborting `coin::transfer`) is demonstrable purely from the cited code paths, but I cannot confirm it is triggerable against mainnet-committed state given the `todo!()` panic constraint above.
