**Analysis**

The `claim`/`claim_script` functions key lookups into `pending_claims` by a `TokenOfferId` struct that combines both the receiver address and the full `TokenId` (creator, collection, name, property_version) [1](#0-0) . Move structs use structural equality for `Table` keys, so `pending_claims.contains(token_offer_id)` at line 161 only succeeds if the exact tuple (creator, collection, name, property_version, receiver) matches a key that was previously inserted by an actual `offer`/`offer_script` call from that sender to that receiver [2](#0-1) .

There is no hashing, truncation, or partial-match logic involved — `create_token_offer_id` simply constructs the struct verbatim from the caller-supplied parameters [3](#0-2) . If the receiver supplies parameters that resolve to a different `TokenId` B than the one originally offered (token A), the resulting `TokenOfferId` key will not equal the key stored for token A, so `contains` returns false and the transaction aborts with `ETOKEN_OFFER_NOT_EXIST` at line 161. The only way `claim` can succeed for token B is if the sender genuinely offered token B to that same receiver via a separate `offer` call, in which case claiming it is the intended, honest VM-derived outcome, not a corruption of state.

Since the key comparison is exact structural equality over all fields (`creator`, `collection`, `name`, `property_version`, `to_addr`), there is no way for unprivileged input to make an unintended token resolve to the same table key as an intended one. This does not meet the state-integrity bar of causing committed state to diverge from the correct VM result.
