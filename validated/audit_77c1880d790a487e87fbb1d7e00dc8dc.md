### Title
Nakamoto block-ID malleability via unenforced low-S signer/miner signatures allows equally-valid blocks with different `StacksBlockId` values - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`NakamotoBlockHeader::verify_signer_signatures` intentionally recovers signer signatures with `Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s`, i.e. it does **not** enforce the canonical low-S form (EIP-2/BIP-62 style malleability check) for signer signatures over a Nakamoto block. [1](#0-0)  Because ECDSA signatures have a well-known malleability (`s' = n - s`, with the recovery bit flipped) that requires **no private key**, anyone who observes a valid signer or miner signature over a block can derive a second, equally-valid signature over the identical message. Since the signature bytes are part of the serialized `NakamotoBlockHeader` that the block hash/`StacksBlockId` is computed over, this yields two byte-distinct but semantically identical blocks with two different `StacksBlockId`s, both of which pass signature verification.

### Finding Description
`verify_signer_signatures` computes `message = self.signer_signature_hash()` (the pre-signature hash, which does **not** include the signature bytes themselves) and then, for every signature in `self.signer_signature`, recovers the public key with the low-S check disabled:
```
Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(message.bits(), signature)
``` [2](#0-1) 

This is explicitly confirmed as intentional/long-standing behavior for signer signatures by the accompanying unit test and its comment:
```
/// Test a secp256k1 signature with high S. Whether intentional or not,
/// this has always been allowed. We no longer allow it for transaction
/// signatures, but it's okay for signer signatures.
fn test_high_s_single_signature() { ... }
``` [3](#0-2) 

The test-support code base independently documents the resulting consequence for the *miner* signature: negating `s` (and flipping the recovery-id parity bit) produces a second signature that recovers to the same public key (so it's still "valid"), but changes the header's serialized bytes — and therefore the block's hash/ID — without altering the block's execution content:
```
/// ... It recovers to the same public key, so the signature remains valid,
/// but its bytes (and any hash committing to them) change. Used to construct
/// malleablized blocks: flipping the miner signature changes a block's id
/// without changing its execution.
fn malleablize_signature(sig: &MessageSignature) -> MessageSignature { ... }
``` [4](#0-3) 

The equality this breaks is the implicit consensus assumption that "the same tenure/block content maps to one canonical `StacksBlockId`". `StacksBlockId` is the primary key used throughout the chainstate/staging-block/tenure-linkage logic (e.g. `parent_block_id` references, `NakamotoStagingBlocksConnRef`, block download bookkeeping). If two relayers — or a single miner/signer acting alone, with no need for anyone else's private key — produce two byte-different, ID-different, but content-identical blocks that both pass `verify_signer_signatures`/`check_miner_signature`, different honest nodes can end up associating different `StacksBlockId`s with what is semantically the same tenure block, breaking any downstream code that keys off exact ID equality (e.g. children whose `parent_block_id` must match, or nodes that reject a differently-ID'd copy of a block they've already accepted/relayed under another ID).

### Impact Explanation
This is a minority-triggerable divergence: an attacker needs only to observe one valid quorum-satisfying signature set (already public once broadcast) and can locally compute the malleated variant — no signer/miner private key or majority collusion is required. The result is two "valid" representations of the same block with different `StacksBlockId`s, which can cause temporary tip/ID disagreement across nodes that receive different variants (e.g. via different relay paths), and can break identity-based lookups/deduplication that assume block content ⇒ unique ID. This matches the "High" bucket: a minority-triggerable static-validation divergence producing temporary tip disagreement, rather than a full irreversible chain split, since ultimately whichever `StacksBlockId` sortition/tenure-linkage settles on for descendant blocks becomes canonical.

### Likelihood Explanation
High likelihood of reachability: `verify_signer_signatures` is called on every Nakamoto block during validation, e.g. via `check_nakamoto_block_signer_signature` in the p2p unsolicited-block-handling path. [5](#0-4)  No special privileges are required: any party that can observe a broadcast block/signature can perform the ECDSA `s`-negation malleation, and the code's own tests demonstrate the malleated (high-S) signature is accepted by design. [3](#0-2) 

### Recommendation
Enforce canonical low-S signatures (or otherwise canonicalize the signature encoding before it is committed to the header/`StacksBlockId`) for both signer signatures (`verify_signer_signatures`) and the miner signature path (`check_miner_signature`/`recover_miner_pk`), analogous to the low-S enforcement already applied to transaction signatures via `TransactionAuthVerificationMode::EnforceLowS`. [6](#0-5)  Alternatively, compute `StacksBlockId`/block hash over a canonicalized signature encoding so that malleated variants map to the same ID.

### Proof of Concept
1. A miner/signer produces and broadcasts a valid Nakamoto block with signature set `S` satisfying `verify_signer_signatures`.
2. An attacker (any network participant, no private key needed) selects one signature `sig = (r, s, recid)` from `S`, and computes `sig' = (r, n - s, recid ^ 1)` exactly as done by `malleablize_signature`. [7](#0-6) 
3. The attacker substitutes `sig'` for `sig` in the header and rebroadcasts. `verify_signer_signatures` (or `check_miner_signature`/`recover_miner_pk` for the miner-signature case) accepts it because it uses the low-S-tolerant recovery path. [2](#0-1) 
4. Both the original and malleated blocks are semantically identical (same transactions, same execution) but hash to different `StacksBlockId`s, since the signature bytes are part of the serialized header used for the block hash.

/// Produce the other valid ECDSA encoding of a recoverable signature: the
/// high-S/low-S complement `s' = n - s`, with the recovery id's parity bit
/// flipped. It recovers to the same public key, so the signature remains valid,
/// but its bytes (and any hash committing to them) change. Used to construct
/// malleablized blocks: flipping the miner signature changes a block's id
/// without changing its execution.
fn malleablize_signature(sig: &MessageSignature) -> MessageSignature {
    // secp256k1 group order `n`, big-endian.
    const SECP256K1_ORDER_BE: [u8; 32] = [
        0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF,
        0xFE, 0xBA, 0xAE, 0xDC, 0xE6, 0xAF, 0x48, 0xA0, 0x3B, 0xBF, 0xD2, 0x5E, 0x8C, 0xD0, 0x36,
        0x41, 0x41,
    ];
    // MessageSignature layout: [recovery_id (1)][r (32)][s (32)].
    let mut bytes = sig.0;
    // s' = n - s, as a 32-byte big-endian subtraction.
    let mut borrow = 0i16;
    for i in (0..32).rev() {
        let diff = SECP256K1_ORDER_BE[i] as i16 - bytes[33 + i] as i16 - borrow;
        let (val, next_borrow) = if diff < 0 { (diff + 256, 1) } else { (diff, 0) };
        bytes[33 + i] = val as u8;
        borrow = next_borrow;
    }
    // Negating s flips the parity of R, so flip the recovery id's low bit.
    bytes[0] ^= 0x01;
    MessageSignature(bytes)
}

                self.get_local_peer(),

            return false;
        };

            .header
            .verify_signer_signatures(reward_set, epoch_id)

        }
