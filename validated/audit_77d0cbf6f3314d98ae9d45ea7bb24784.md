## Analysis

**Tracing the full call path:**

1. Unauthenticated RPC call → `EXPERIMENTAL_view_gas_key_nonces` or standard `query` with `view_gas_key_nonces` request type
2. `view_gas_key_nonces_local` → `ViewClientActor` via `view_client_send`
3. `NightshadeRuntime::view_gas_key_nonces` → `TrieViewer::view_gas_key_nonces`

**The unbounded loop:** [1](#0-0) 

The function iterates `(0..gas_key_info.num_nonces)` with one trie read per iteration — no cap, no timeout, no limit check. `num_nonces` is a `u16` (max 65535), and `MAX_NONCES_FOR_GAS_KEY` is enforced only at key-creation time in action validation. [2](#0-1) 

**Contrast with `view_access_keys`:** `TrieViewer` has an `access_keys_limit: u32` field and `view_access_keys` respects it. `view_gas_key_nonces` has no equivalent guard. [3](#0-2) 

**The RPC endpoint is publicly accessible with no authentication:** [4](#0-3) 

**Attacker steps are all unprivileged standard user actions:**
1. Create an account and fund it (standard)
2. Submit an `AddKey` transaction creating a gas key with `num_nonces = MAX_NONCES_FOR_GAS_KEY`
3. Flood `EXPERIMENTAL_view_gas_key_nonces` or `query/view_gas_key_nonces` with that account/key pair

Each request triggers up to 65535 trie reads on the `ViewClientActor` thread pool. Concurrent flooding saturates the pool, stalling all view queries.

**Fix does not require a hardfork** — adding a cap in `view_gas_key_nonces` (analogous to `access_keys_limit`) is a pure software change.

### Title
Unbounded O(num_nonces) Trie Reads in `TrieViewer::view_gas_key_nonces` Enables Non-Network-Level DoS via Unauthenticated RPC — (`runtime/runtime/src/state_viewer/mod.rs`)

### Summary
`TrieViewer::view_gas_key_nonces` performs one trie read per nonce slot with no upper bound, allowing any unprivileged caller to trigger up to 65535 trie reads per RPC call by querying a gas key created with the maximum `num_nonces`. Repeated concurrent calls saturate the `ViewClientActor` thread pool, stalling all view queries without affecting consensus or requiring a hardfork to fix.

### Finding Description
`TrieViewer::view_gas_key_nonces` iterates `(0..gas_key_info.num_nonces)` and calls `get_gas_key_nonce` once per index with no cap: [1](#0-0) 

`num_nonces` is a `u16` field of `GasKeyInfo`, bounded only at key-creation time by `MAX_NONCES_FOR_GAS_KEY` in action validation. The view function itself applies no limit. By contrast, `view_access_keys` is guarded by `access_keys_limit`: [3](#0-2) 

The endpoint is reachable via both the standard `query` RPC method and `EXPERIMENTAL_view_gas_key_nonces`, both unauthenticated: [5](#0-4) [4](#0-3) 

### Impact Explanation
Flooding the endpoint with max-nonce gas key queries saturates the `ViewClientActor` thread pool. All view queries (account state, access keys, contract calls, tx status) are stalled for the duration of the attack. This is a non-network-level DoS: block production and consensus are unaffected, but the node's RPC service becomes unresponsive.

### Likelihood Explanation
The attacker needs only a funded NEAR account (standard user), one `AddKey` transaction to create a max-nonce gas key, and a script to flood the unauthenticated RPC endpoint. No privileged access, validator role, or key compromise is required.

### Recommendation
Add a configurable cap on the number of nonces returned per `view_gas_key_nonces` call, mirroring the `access_keys_limit` pattern already present in `TrieViewer`. Alternatively, enforce a per-query trie-read budget or a wall-clock timeout at the view layer.

### Proof of Concept
1. Create account `attacker.near`, fund it.
2. Submit `AddKey` with `AccessKeyPermission::GasKeyFullAccess { num_nonces: MAX_NONCES_FOR_GAS_KEY, ... }`.
3. In a loop (e.g., 100 concurrent threads), call:
   ```
   POST /  {"jsonrpc":"2.0","method":"EXPERIMENTAL_view_gas_key_nonces",
             "params":{"account_id":"attacker.near","public_key":"<gas_key>","finality":"final"}}
   ```
4. Observe that each call performs O(MAX_NONCES_FOR_GAS_KEY) trie reads and that concurrent calls exhaust the `ViewClientActor` pool, causing all other view queries to time out.
