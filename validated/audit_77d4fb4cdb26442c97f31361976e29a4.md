## Title
`ensure_match_transaction_info` silently skips checkpoint-hash validation, letting a divergent state/position root pass replay-verification as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant that ties a locally-computed `TransactionOutput` (write set, events, gas, status) back to the `TransactionInfo` that is actually committed into the transaction accumulator. It is used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) to assert that a locally re-executed transaction produced the authenticated result. The function checks status, gas, write-set hash, and event root hash, but explicitly and knowingly omits comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — exactly the fields that bind a transaction to the Merkle root of the resulting world state / position state. This is the same class of bug as the bridge report: two representations of "the same fact" (locally computed state root vs. the authenticated `TransactionInfo` root) are supposed to be checked for consistency, but the check is only partially wired up, so a real divergence is accepted as if it matched.

### Finding Description
`TransactionInfo` (in `types/src/transaction/mod.rs`, lines 2229‑2284) is "the object we store in the transaction accumulator" and carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — each summarizing the Merkle root of a piece of world state after the transaction. `ensure_match_transaction_info` (lines 2139‑2204) is the sole "does this output actually match what was committed" gate: [1](#0-0) 

It checks `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash — but then returns `Ok(())` without ever comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against anything computed from the actual resulting state. The code even documents this as a known gap: [2](#0-1) 

This is structurally identical to the external report's root cause: a cross-check that is supposed to hold both sides of an equivalence (here: "committed accumulator root" vs. "locally recomputed state root") is only enforced for a subset of the fields, so a genuine mismatch does not surface as an error — it silently reports success. In the bridge case, the missing symmetric check caused an incorrect revert (false negative safety failure); here, the missing symmetric check causes an incorrect *pass* (false positive integrity confirmation), which is strictly worse under the state-commitment gate, since it lets diverging state be accepted as verified.

`replay_on_archive.rs` and `aptos_debugger.rs` rely on this function specifically to assert that replayed execution against archived data reproduces the authenticated ledger state: [3](#0-2) 

Because the `position_state_checkpoint_hash` / `hot_state_checkpoint_hash` fields exist to authenticate the native-position and hot-state Merkle roots produced by `DoStateCheckpoint`/`DoLedgerUpdate` (see `execution/executor/src/workflow/do_ledger_update.rs` and `execution/executor-types/src/state_checkpoint_output.rs`, which explicitly gate these hashes behind the `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flags): [4](#0-3) [5](#0-4) 

a replay tool or debugger that re-executes transactions with these features enabled has no automated way to detect that its locally computed position/hot-state root diverges from the one bound into the authenticated `TransactionInfo`/accumulator, as long as write set, events, gas, and status happen to match.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... accepted as verified" invariant from the State-Integrity Gate. Once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or `HOT_STATE_ROOT_IN_TXN_INFO`) is enabled on mainnet, any bug in native-position-state or hot-state root computation that produces a wrong root but a correct write set/events/gas/status will pass `ensure_match_transaction_info` undetected. This defeats the primary safety net (replay-verification) that is supposed to catch exactly this class of divergence before or after it ships, i.e. a hard-fork-only or storage-corruption bug in the position/hot-state root computation could go undetected by the tooling designed to catch it, and get silently accepted as a "verified" ledger state.

### Likelihood Explanation
The gap is code-documented (the TODO explicitly says the comparator "ignores the checkpoint hashes... so replay-verify tooling... can report a successful replay even when the authenticated position state root diverges from local execution"), meaning the maintainers are already aware the check is incomplete but it has not yet been closed. The severity is currently latent/pre-conditional: `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` are not yet the default execution path (per the comments in `do_ledger_update.rs` and `state_checkpoint_output.rs` stating these hashes are `None` on testnet/mainnet today), so it is not currently exploitable in production but becomes a real integrity blind spot the moment those features are turned on — which the code comments indicate is an active development direction ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS").

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the caller has (or can compute) the corresponding locally-derived roots, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` is enabled by default. At minimum, `replay_on_archive` and `aptos_debugger` should fail loudly (rather than silently pass) when these fields are `Some` in the authenticated `TransactionInfo` but are not independently re-verified.

### Proof of Concept
Conceptual (no external network/PoC harness needed — the gap is directly visible in the function body):
1. Enable `HOT_STATE_ROOT_IN_TXN_INFO` and/or `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in a test executor so `TransactionInfoV1::hot_state_checkpoint_hash` / `position_state_checkpoint_hash` are populated (`execution/executor/src/workflow/do_ledger_update.rs:30-45`).
2. Construct a `TransactionOutput` whose write set, events, gas, and status match the committed `TransactionInfo`, but whose resulting hot-state/position-state root (computed independently, e.g. via `DoStateCheckpoint`) differs from the `TransactionInfo`'s `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
3. Call `output.ensure_match_transaction_info(version, &txn_info, ..)`.
4. Observe it returns `Ok(())` despite the state-root divergence, because lines 2196‑2203 of `types/src/transaction/mod.rs` never compare those fields — confirming that `replay_on_archive`/`aptos_debugger` callers cannot detect this class of state-root corruption through this API.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
