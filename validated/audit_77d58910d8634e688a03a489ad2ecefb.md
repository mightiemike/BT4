### Title
Stale/reverted-block cache entries for Cairo 0 (deprecated) classes are served without re-validating declaration status - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` re-validates a *cached* class against the authoritative state reader (`is_declared`) only when the cached entry is a Cairo 1 class. For Cairo 0 (`RunnableCompiledClass::V0`) entries, the cache hit is returned immediately with **no** re-validation, even though the code's own comment on the Cairo 1 branch explicitly acknowledges that "existence in the cache does not guarantee that [it is declared] (it might contain a declared class from a reverted block, for example)." The same staleness risk applies to V0 classes, but the guard was omitted for them.

### Finding Description
`get_compiled_from_class_manager` in `crates/blockifier/src/state/state_reader_and_contract_manager.rs` reads from a process-wide, cross-block `ContractClassManager` cache (`RawClassCache`/`GlobalContractCache`) before falling back to the authoritative `StateReader`: [1](#0-0) 

- If the cached `RunnableCompiledClass` is `V0` (Cairo 0 / deprecated class), it is returned directly (`RunnableCompiledClass::V0(_) => {}`), with no check that the class hash is still actually declared in the current canonical state.
- If the cached class is Cairo 1 (any other variant), the code calls `self.state_reader.is_declared(class_hash)` and returns `StateError::UndeclaredClassHash` if the check fails, specifically to guard against the class having been cached "from a reverted block."

The asymmetry is structural, not incidental: `FetchCompiledClasses::is_declared` is documented to always return `false` for Cairo 0 classes: [2](#0-1) 

and the concrete implementation (`ApolloReader::is_declared`) only consults `get_class_definition_block_number`, which is populated for Cairo 1 declarations tracked by the class-definition-block index — it provides no oracle to re-validate V0 class declaration status at all: [3](#0-2) 

This means the reorg/reverted-block staleness protection that exists for Cairo 1 classes structurally cannot be extended to Cairo 0 classes with the current oracle, yet the vulnerable code path (serving a V0 class straight from the global cache) is identical. The test suite even documents this gap explicitly, contrasting the Cairo 1 case (`cached_but_verification_failed_after_reorg_scenario`, which asserts `UndeclaredClassHash` is returned) with the Cairo 0 case (`cairo_0_cached_scenario`, which sets `is_declared_result: None` — i.e., no verification call is made at all for a cached V0 class): [4](#0-3) [5](#0-4) 

`RawClassCache` (`GlobalContractCache`) is a long-lived, cross-block cache attached to the `ContractClassManager`, which is shared across executions in the same process (e.g., across speculative concurrent-execution attempts, block re-execution/re-validation, and subsequent blocks) rather than being scoped and invalidated per committed block: [6](#0-5) [7](#0-6) 

### Impact Explanation
If a Cairo 0 class ever gets populated into the shared global cache during execution that is subsequently not committed to the canonical chain state (e.g., speculative concurrent-execution of a block that is later discarded/re-executed, or a block whose declare transaction's effects get reverted), any later transaction referencing that same class hash (via `deploy`, `deploy_account`, or `replace_class`/invoke targeting a contract with that class hash) will receive the stale class from cache and execute it successfully — with no `UndeclaredClassHash` rejection — because the V0 branch skips the `is_declared` re-check entirely. This is the direct structural analog of the reported issue: consumers "mistakenly use an old/uncommitted cached version" because the cache-sync/validation logic wasn't applied uniformly to all cached entities.

Consequences include: execution succeeding against code that was never actually accepted as declared on the canonical chain, and — if cache state differs between nodes (warm vs. cold cache, differing execution/re-execution history) — honest nodes could diverge on whether a given transaction succeeds or fails (`UndeclaredClassHash` vs. successful execution), which is a state/consensus divergence risk.

### Likelihood Explanation
Reaching this requires a Cairo 0 class hash to enter the shared cache from an execution path whose result is not ultimately committed (reverted/re-executed speculative block, or discarded simulation sharing the same `ContractClassManager` instance as block building), and then a subsequent transaction from any ordinary sender referencing that class hash. The severity of "old contracts being used" was rated Medium in the original report for a comparable staleness gap; the missing symmetric guard here is a genuine code-level gap (confirmed by the test file's own documented asymmetry), though full confirmation of every trigger path (e.g., whether the batcher's speculative/aborted execution and the committed path definitely share one long-lived `ContractClassManager` instance across the block boundary) could not be fully traced within the available context.

### Recommendation
Extend the reorg/staleness re-validation performed for Cairo 1 classes to Cairo 0 classes as well: either (a) provide a `FetchCompiledClasses::is_declared`-equivalent oracle capable of confirming V0 declaration status against the authoritative state reader and invoke it on every V0 cache hit, mirroring the existing Cairo 1 branch, or (b) ensure the global class cache is strictly scoped/invalidated per committed block so that no entry from a non-committed (reverted/discarded) execution can ever be observed by a later, distinct block's execution.

### Proof of Concept
Not independently reproducible from static analysis alone; the gap is demonstrated directly by the test module itself, which documents that a cached Cairo 1 class is re-verified against `is_declared` after a simulated reorg (`cached_but_verification_failed_after_reorg_scenario`, returning `Err(StateError::UndeclaredClassHash(...))`), while the equivalent cached Cairo 0 scenario (`cairo_0_cached_scenario`) performs no such verification call and always returns `Ok(...)`: [8](#0-7)

impl FetchCompiledClasses for ApolloReader {
    fn get_compiled_classes(&self, class_hash: ClassHash) -> StateResult<CompiledClasses> {
        self.get_compiled_class_from_db(class_hash)
    }

    fn is_declared(&self, class_hash: ClassHash) -> StateResult<bool> {
        let state_number = StateNumber(self.latest_block);
        let class_declaration_block_number = self
            .reader()?
            .get_state_reader()
            .and_then(|sr| sr.get_class_definition_block_number(&class_hash))
            .map_err(|err| StateError::StateReadError(err.to_string()))?;
        Ok(
            matches!(class_declaration_block_number, Some(block_number) if block_number <= state_number.0),
        )
    }
}
