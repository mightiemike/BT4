Based on my research, I found a strong analog to the CVE-2024-53154 bug class (missing validation before dereference causing a panic reachable from external/attacker-influenced data), located in nearcore's cross-shard receipt processing path.

### Title
Panic-inducing `.unwrap()` on `receiver_shard_id()` in `receipt_filter_fn` can halt chunk production after resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()` while draining the delayed receipt queue during normal chunk `apply`. [1](#0-0)  `Receipt::receiver_shard_id` returns `Err(EpochError::ShardingError(...))` for a `GlobalContractDistribution` receipt whose `target_shard` cannot be resolved into the current shard layout via `resolve_to_current_shard`. [2](#0-1)  The `.unwrap()` in `receipt_filter_fn`, called from both `pop` and `peek_iter`, converts this `Err` into an unconditional panic during block/chunk apply. [3](#0-2) 

### Finding Description
`GlobalContractDistribution` receipts carry a `target_shard` field that is fixed at receipt-creation time. When a shard undergoes resharding (a split), the delayed-receipt queue is duplicated across child shards, and stale `GlobalContractDistribution` receipts referencing an old, now-nonexistent `target_shard` must be remapped through the shard layout's split history via `ShardLayout::resolve_to_current_shard`. The code comment in `receiver_shard_id` explicitly acknowledges this: "The target shard may be from an arbitrarily old layout (the receipt could have been delayed across multiple resharding events)." [4](#0-3) 

If `resolve_to_current_shard` cannot find a descendant shard for `target_shard` in the current layout (e.g., because the split history was not preserved deeply enough, or the receipt is stale across **two or more** resharding generations), `receiver_shard_id` returns `Err(EpochError::ShardingError(...))`. This propagates directly into `receipt_filter_fn`, which unconditionally `.unwrap()`s the result: [1](#0-0) 

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

This function is invoked from `pop()` (used every chunk to drain the delayed receipt queue during normal `apply`) and from `peek_iter()`. A panic here is not confined to a single failed transaction/receipt outcome — it aborts the entire chunk `apply` call, which is a chain-halting condition for the affected shard(s), analogous in severity to the kernel NULL-deref DoS in the reported CVE (both are unchecked dereference/unwrap of a value that can legitimately be absent/invalid, reachable without special privilege).

A repro test exists in the repo specifically targeting this code path — `test_stale_global_contract_distribution_after_double_resharding` — which forces two sequential shard splits and then drains the delayed queue, with the explicit comment: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations." [5](#0-4) 

I was unable to fully confirm from the available index whether `resolve_to_current_shard` (in `core/primitives/src/shard_layout/v3.rs`) has already been patched to correctly walk multi-generation split history, or whether this remains an open/reachable panic — my file-read attempts for `v3.rs` and the full test file did not return content in the final iteration due to tool errors. The presence of a dedicated regression test with this exact description strongly suggests this is (or recently was) a live concern in this codebase, but I cannot certify from what I retrieved whether the test currently passes (bug fixed) or is a reproducer for an unfixed issue.

### Impact Explanation
If reachable, this causes every honest validator applying the affected shard to panic during ordinary chunk apply, which is a transaction/receipt-triggered halt of chunk production for that shard — matching the "transaction-triggered halt" acceptance criterion. Because the trigger is a shard-splitting sequence combined with a global contract deployment (`UseGlobalContract`), which any account can initiate, this is reachable by an unprivileged contract deployer without needing malicious-validator or network-layer access.

### Likelihood Explanation
Triggering requires: (1) a `GlobalContractDistribution` receipt is created (via a normal `DeployGlobalContract`/`UseGlobalContract` action, reachable by any account), (2) the receipt sits in the delayed queue long enough to survive across two resharding events for the same shard lineage before being drained. This requires dynamic resharding to occur twice for the relevant shard while the receipt remains queued — a low-frequency but achievable condition on a chain with active dynamic resharding, and one an attacker could actively try to engineer by congesting the target shard to keep the receipt delayed across splits.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:876`) with a fallible path: on `Err` from `receiver_shard_id`, either treat the receipt as belonging to no live shard (drop deterministically across all shards with consistent handling) or propagate the error as a graceful `RuntimeError`/`StorageError::StorageInconsistentState` rather than panicking, consistent with the codebase's stated invariant that "a missing delayed/buffered/postponed/yield item referenced by an index yields `StorageError::StorageInconsistentState`" rather than panicking. Additionally, verify/fix `ShardLayout::resolve_to_current_shard` to correctly walk arbitrarily deep split histories so genuinely valid receipts are never misclassified as unresolvable.

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs` is a working PoC scaffold: it deploys a global contract to force a `GlobalContractDistribution` receipt, configures dynamic resharding to force two sequential splits of the shard containing the distributing account, saturates gas to keep receipts delayed through both splits, and then drains the delayed queue — asserting the chain height keeps advancing (i.e., asserting there is no panic).     pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }
