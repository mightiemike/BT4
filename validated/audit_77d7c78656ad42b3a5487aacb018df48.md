### Title
Meta-transaction attached-deposit refunds are misdirected to the sender (not the fee-paying relayer) on inner-action failure - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEAR's meta-transaction (`Delegate`/`DelegateV2`) mechanism lets a relayer pay all fees, gas, and attached deposits for actions submitted on behalf of another account ("the sender", e.g. Alice). When the relayer funds an attached-deposit action (e.g. `Transfer` or `FunctionCall` with `deposit`) that later fails on the receiver's shard, the protocol's balance-refund rule sends the refunded deposit to the **predecessor of the failed receipt**, which for an unwrapped delegate action is the sender (Alice), not the relayer who actually supplied the tokens. This is the same bug class as the Aave `repay()` issue: the party that paid the excess/failed value gets refunded to the wrong account.

### Finding Description
When a `Delegate`/`DelegateV2` action is processed, `apply_delegate_action` constructs a brand-new receipt whose `predecessor_id` is the delegate action's sender (Alice), while `signer_id`/`signer_public_key` are copied from the outer action receipt (i.e., the relayer):

<cite repo="patrichyt/nearcore--005" path="runtime/runtime/src/actions.rs" start="499="513" end="519" /> [1](#0-0) 

The comment in the same function explicitly states the consequence: *"If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer."* [2](#0-1) 

The generic refund logic in the runtime confirms this: for a failed receipt, the full attached deposit is refunded via `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`: [3](#0-2) 

and `balance_refund_receiver()` resolves to `refund_to` if present, otherwise falls back to `predecessor_id()`: [4](#0-3) 

Critically, the receipt built in `apply_delegate_action` is a plain `ReceiptEnum::Action(ActionReceipt{..})`, which is a receipt variant whose `refund_to()` accessor always returns `None` (only `ActionV2`/`PromiseYieldV2` variants carry a `refund_to` field): [5](#0-4) 

Because of this, the relayer has no mechanism to redirect the deposit refund to itself when it funds an inner action of a delegate action — the refund unconditionally goes to `predecessor_id`, which is the sender (Alice) rather than the fee/deposit-paying relayer.

This is not a hypothetical edge case; it is explicitly documented as a known, unresolved design tradeoff: [6](#0-5) 

### Impact Explanation
Whenever a relayer funds a meta-transaction whose inner action requires an attached deposit (e.g., a `Transfer` action or a payable `FunctionCall`), and that action fails execution on the receiver's shard (e.g., receiver has no matching contract method, hits a `LackBalanceForState`, or otherwise errors), the deposit that the relayer paid for is refunded to the sender (Alice) instead of back to the relayer. Because Alice — not the relayer — controls whether/how the inner action fails (e.g., by targeting a contract/method that will predictably reject the call), Alice can systematically cause meta-transactions with large attached deposits to fail on the receiver shard and collect the relayer-funded deposit for herself. This is a concrete unauthorized value transfer from the relayer to the sender, i.e. value that the relayer never intended to give away, extracted purely by choosing to submit meta-transactions engineered to fail.

### Likelihood Explanation
This requires only a single delegate-action transaction sent by an ordinary account (the "sender"/Alice) that convinces a relayer to co-sign/submit it (a normal use of meta-transactions, reachable by any unprivileged transaction signer using the standard NEP-366 delegate-action flow). No validator or node compromise is needed; it purely depends on relayer implementations funding deposits for inner actions without independently validating that the action cannot fail, which the documentation itself warns relayer implementers must guard against — indicating the runtime provides no protocol-level protection.

### Recommendation
For actions unwrapped from a `Delegate`/`DelegateV2` action, deposit refunds should be routed to the account that actually supplied the deposit (the outer relayer/signer) rather than unconditionally to the inner receipt's predecessor. Concretely, `apply_delegate_action` could construct the inner receipt as an `ActionReceiptV2` (or equivalent) with `refund_to` explicitly set to the outer `signer_id` (the relayer) whenever the relayer is the one funding the deposit, so `balance_refund_receiver()` correctly resolves to the paying party on failure — mirroring how gas refunds already go to the relayer.

### Proof of Concept
1. Relayer R submits a `SignedTransaction` containing a `Delegate` (or `DelegateV2`) action, `sender_id = Alice`, wrapping an inner `Transfer` (or payable `FunctionCall`) action with a large `deposit` targeting receiver `Bob`.
2. `apply_delegate_action` runs on Alice's shard, builds `new_receipt` with `predecessor_id = Alice`, `signer_id = R` (relayer), and forwards it to Bob's shard: [7](#0-6) 
3. On Bob's shard the inner action fails (e.g., Bob has no matching method, or the transfer causes `LackBalanceForState`).
4. `refund_unspent_gas_and_deposits` refunds the full attached deposit to `receipt.balance_refund_receiver()`, which resolves to `predecessor_id() == Alice` since the receipt has no `refund_to`: [3](#0-2) [8](#0-7) 
5. Alice receives the deposit that the relayer R funded, even though R paid for it and never intended to gift it to Alice.

```rust
    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }
```

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
