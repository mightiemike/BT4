### Title
Stale `last-update` timestamp during a zero-rate utilization band causes retroactive interest inflation - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The shared `accrue` logic in all `v0-vault-*.clar` contracts only advances `last-update` when the computed `index`/`lindex` actually changes. When the effective borrow rate is exactly `0` (a legitimate point on the DAO-configured interest curve), the index does not change no matter how much real time elapses, so `last-update` is silently frozen. Once utilization later moves into a nonzero-rate segment, the next `accrue()` call applies the *new* nonzero rate across the entire frozen (previously zero-rate) time window, retroactively charging/crediting interest for a period during which the protocol's own rate curve said interest should have been zero.

### Finding Description
`accrue` computes `next-index` / `next-liquidity-index` via `next-index`/`next-liquidity-index`, which multiply the current index by `calc-multiplier-delta(rate, time-delta, ...)`: [1](#0-0) 

When `rate` is `0`, `mul-div-up`/`mul-div-down` of `0` is `0`, so `calc-multiplier-delta` returns exactly `INDEX-PRECISION`, and `calc-index-next` returns the unchanged current index — **regardless of how large `time-delta` is**.

Back in `accrue`, the timestamp update is gated on the index actually having changed: [2](#0-1) 

So while utilization sits in a curve segment where `interest-rate` resolves to `0` (set via DAO-controlled `vault-set-points-rate`, e.g. a legitimate `0%` base rate at `0%` utilization), every call to `accrue` (triggered by ordinary `system-borrow`/`system-repay`/deposit/redeem calls) leaves `last-update` untouched, even across many blocks or days.

When utilization subsequently shifts (through ordinary user borrow/repay activity, not DAO compromise) into a segment of the curve with a nonzero rate, the very next `accrue()` computes:
```
time-delta = stacks-block-time - last-update   ;; = entire dormant zero-rate window
```
and applies the *current* (now nonzero) rate over that entire stale window via `calc-multiplier-delta`, inflating `index`/`lindex` as though the new rate had applied throughout the whole dormant period — even though the curve explicitly specified `0%` for that period. This inflated index increases `total-debt` for existing borrowers (`calc-cumulative-debt`) and the `reserve-inc`/`treasury-lp` minted to `.dao-treasury`: [3](#0-2) 

This is a direct analog to the referenced bug class: a value (`last-update`) is only advanced on state change, and the value it gates (elapsed time subject to the *old* rate) is later misapplied to a *new* rate once the guard condition is finally true again — an interleaving possible purely from normal Clarity execution order across two separate transactions (one that keeps rate at 0, one that later moves it nonzero).

### Impact Explanation
Existing borrowers are charged interest, and LPs/treasury are credited `treasury-lp`, for a period during which the protocol's own configured rate curve dictated `0%` interest. This misappropriates unclaimed yield between borrowers, depositors, and `.dao-treasury` — value that was never legitimately earned is transferred based on a stale clock, rather than the actual rate history. This lands on the in-scope High impact category: theft of unclaimed yield/interest (and, if the dormant zero-rate window is long and utilization swings are large, can materially inflate borrower debt).

### Likelihood Explanation
Reaching a genuine `0%` rate band requires the DAO-configured `points-ir` curve to contain a rate-0 point (a common, reasonable curve design, e.g. `0%` base rate at `0%` utilization) — this is a normal governance configuration, not a compromise. Once such a curve exists, ordinary user deposit/borrow/repay flow naturally moves utilization in and out of that band over time, making the stale-clock condition reachable without any privileged or malicious action.

### Recommendation
Always advance `last-update` to `stacks-block-time` on every `accrue()` call when not paused, regardless of whether `index`/`lindex` numerically changed, so that no "unaccounted" time window can silently accumulate and later be multiplied by a different (future) rate.

### Proof of Concept
1. DAO configures `points-ir` for a vault (e.g. `v0-vault-stx.clar`) with `rate = 0` at utilization `U0` via `vault-set-points-rate`. [4](#0-3) 
2. Utilization stays at/near `U0` for an extended real-time window `T` (many blocks) through normal borrow/repay activity that nets out utilization near `U0`; every `accrue()` call in this window computes `next == idx` and `nliq == lidx`, so `last-update` never advances.
3. A user action shifts utilization into a nonzero-rate band of the same curve.
4. The next `accrue()` call computes `time-delta = stacks-block-time - last-update`, equal to the full window `T`, and multiplies it by the new nonzero rate, inflating `index`/`lindex`, `total-debt`, and `treasury-lp` minted to `.dao-treasury` as if the new rate had applied for the whole dormant period `T`. [3](#0-2)

(define-private (calc-multiplier-delta (rate uint) (time-delta uint) (round-up bool))
  (+ INDEX-PRECISION
    (if round-up
      (mul-div-up rate
                  (* time-delta INDEX-PRECISION)
                  SECONDS-PER-YEAR-BPS)
      (mul-div-down rate
                  (* time-delta INDEX-PRECISION)
                  SECONDS-PER-YEAR-BPS))))
