### Title
Unbounded growth of `DelegatedResourceAccountIndex` to/from-account lists causes O(n) cost on every freeze/unfreeze/delegate call, enabling per-account DoS - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java, chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`FreezeBalanceActuator` (and the analogous non-optimized path in `UnfreezeBalanceActuator`) maintains a `DelegatedResourceAccountIndexCapsule` per account containing `toAccounts`/`fromAccounts` protobuf-repeated lists. There is no cap on how many distinct receiver/sender addresses can be added to these lists, and every freeze/unfreeze call that touches this structure does a full linear scan (`contains`, list copy + `remove`, or full re-serialization). This mirrors the reported bug class: an unbounded array that is fully iterated on every state-changing call, with no way to shrink or cap it, eventually making per-account operations arbitrarily expensive.

### Finding Description
When `supportAllowDelegateOptimization()` is false (legacy/non-optimized delegation index format), `FreezeBalanceActuator.delegateResource()` reads the owner's and receiver's `DelegatedResourceAccountIndexCapsule`, checks `toAccountsList.contains(...)` / `fromAccountsList.contains(...)`, and if absent appends via `addToAccount`/`addFromAccount`: [1](#0-0) 

There is no limit on the number of distinct receiver addresses an owner can delegate/freeze-to, nor on the number of distinct senders a receiver can accumulate — an unprivileged account can call `FreezeBalanceContract` repeatedly with a new random `receiverAddress` each time to grow its own `toAccountsList` (and the corresponding receivers' `fromAccountsList`) without bound. The append/lookup path (`contains`) is `O(n)` per call, and `UnfreezeBalanceActuator` performs an even more expensive operation, copying the entire list into a new `ArrayList` and calling `.remove()` on every unfreeze: [2](#0-1) 

Additionally, `DelegatedResourceAccountIndexStore.convert()` — invoked from the optimized delegate/undelegate/unfreeze paths the first time an account is touched after `supportAllowDelegateOptimization()` is enabled — loops over the *entire* legacy `toAccountsList` and `fromAccountsList` to re-write each entry into the new key-value format: [3](#0-2) 

Because an account could have built up an arbitrarily large `toAccountsList`/`fromAccountsList` (via many `FreezeBalanceContract` calls to distinct receivers before the optimization flag was flipped by governance), the very first subsequent delegate/undelegate/freeze/unfreeze transaction from that account triggers a single unbounded loop inside `convert()`, executed synchronously as part of block/transaction processing. This is directly analogous to the reported bug: a data structure that only grows (no removal cap, no upper bound enforced at write time) and is later iterated in full inside a state-transition method reachable from an ordinary broadcast transaction.

The full list content is also exposed and rebuilt on read via `Wallet.getDelegatedResourceAccountIndex` / `getDelegatedResourceAccountIndexV2`, which return the entire capsule including these lists: [4](#0-3) 

### Impact Explanation
If an account accumulates a very large `toAccountsList`/`fromAccountsList` (by repeatedly freezing/delegating small amounts to many distinct addresses — each such call is cheap, e.g. minimal `frozenBalance`), each subsequent freeze/unfreeze/delegate transaction from or to that account becomes progressively slower (`O(n)` `contains` calls, `O(n)` list rebuild on unfreeze, or a single `O(n)` `convert()` sweep). In the worst case, this can make transaction processing time for that account exceed acceptable limits, effectively preventing that account from unfreezing/withdrawing/delegating further resources — a denial of service scoped to the affected account(s) rather than the whole chain, since each `FreezeBalanceContract`/`UnfreezeBalanceContract` is typically its own transaction (not a single loop across arbitrarily many pools processed at once as in the original report).

### Likelihood Explanation
Low-to-moderate. It requires an attacker to send many low-cost `FreezeBalanceContract` transactions to distinct receiver addresses to grow their own index list, and/or to be targeted by many senders. `calcFee()` for these actuators is effectively free/near-free, network bandwidth/energy cost is the only friction, so building a large list is feasible for a motivated actor over time. The `convert()` full-DoS vector additionally depends on governance having enabled `supportAllowDelegateOptimization` after the attacker already built up a large legacy list, which is a narrower, more circumstantial condition. I could not fully verify within the available index whether `FreezeBalanceContract` remains callable once `supportAllowNewResourceModel`/`AllowDelegateOptimization` are enabled on current networks — this constrains confidence.

### Recommendation
- Enforce a maximum size on `toAccountsList`/`fromAccountsList` (and the V2 key-value equivalent count) per account, rejecting new delegate/freeze targets beyond that cap in `validate()`.
- Avoid `contains()`/list-rebuild-and-remove patterns over the full list on every call; use direct key-based lookups (as already done for the V2 delegate format) instead of embedding growable lists in a single protobuf message.
- For the `convert()` migration path, cap or chunk the number of entries converted per transaction, or perform the migration lazily/off the critical transaction-processing path, to avoid a single unbounded loop executing synchronously inside actuator `execute()`.

### Proof of Concept
1. Attacker account `A` (unprivileged, ordinary key) repeatedly broadcasts `FreezeBalanceContract` transactions with minimal `frozen_balance`, each specifying a distinct, freshly generated `receiver_address`, while `supportAllowDelegateOptimization()` is false and `supportDR()` is true.
2. Each call appends to `A`'s `DelegatedResourceAccountIndexCapsule.toAccountsList` via `FreezeBalanceActuator.delegateResource` (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:328-332`), with no upper bound enforced in `validate()`.
3. Repeat until the list contains a very large number of entries (e.g., tens of thousands), confirmed by `Wallet.getDelegatedResourceAccountIndex(A)` returning the full list (`framework/src/main/java/org/tron/core/Wallet.java:1040-1051`).
4. Subsequent `UnfreezeBalanceContract` calls by `A` now perform `new ArrayList<>(ownerIndexCapsule.getToAccountsList())` plus `.remove()` over the whole list on every unfreeze (`actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java:167-171`), and if/when `supportAllowDelegateOptimization` is later turned on, the first delegate/undelegate/freeze touching `A` triggers `DelegatedResourceAccountIndexStore.convert()`, which iterates the entire accumulated list in one synchronous call (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java:42-61`), degrading or blocking that account's ability to process further freeze/unfreeze/delegate transactions in reasonable time.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }
