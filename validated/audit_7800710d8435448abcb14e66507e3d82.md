### Title
Gas fee under-collection in `CalculateGasCost` due to premature truncation of `baseFee` before multiplication - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` truncates the fractional (sub-upc) component of `baseFee` before multiplying by `gasUsed`, instead of truncating the final gas-cost result. This mirrors the Wise Lending bug class: a rounding operation applied at the wrong point in a calculation used for a critical accounting invariant, which systematically produces an incorrect value in a user-reachable, fee-relevant code path.

### Finding Description
`DeductGasFeesFromReceipt` is the sole mechanism billing gas for `MsgExecutePayload`/`ExecutePayloadV2` EVM executions, since these messages are explicitly documented as gasless at the Cosmos ante-handler level:

> `MsgExecutePayload` — any user, gasless (the UEA itself authenticates the request) [1](#0-0) 

The actual fee is computed entirely inside `CalculateGasCost`:

```go
baseFeeBig := baseFee.BigInt()
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
...
gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig)
``` [2](#0-1) 

`baseFee` is an `sdkmath.LegacyDec` sourced from the feemarket module's `GetBaseFee`. The EIP-1559-style base-fee adjustment formula (`baseFee * (1 ± gasUsedDelta/gasTarget/elasticity)`) produces genuine fractional (sub-upc) values almost every block — the comment's assumption that "the base fee is always a whole number of upc" does not generally hold for a live fee market. `LegacyDec.BigInt()` returns the raw internal fixed-point integer (`actual_value * 1e18`); dividing that by `1e18` with integer division truncates (floors) any fractional upc **before** it is multiplied by `gasUsed`.

This is the same bug class as the Wise Lending finding: a rounding operation (floor vs. ceiling, and — critically — rounding applied before vs. after a multiplication) is performed at the point that maximizes accumulated error, rather than at the final result. Here, truncating the *unit price* before multiplying by the (potentially very large) `gasUsed` quantity compounds the rounding error by a factor of `gasUsed`, whereas truncating only the final `effectiveGasPrice * gasUsed` product would bound the error to less than 1 upc.

### Impact Explanation
Every `MsgExecutePayload` submission by an ordinary, unprivileged user goes through this exact path with no way to opt in/out. Because the truncation happens pre-multiplication, the protocol systematically under-collects and under-burns the intended gas fee for UEA-routed payload executions — this is "corruption of ... gas fee accounting" as called out in the allowed-impact list, reachable purely through the default `MsgExecutePayload` transaction path with no privileged actor or malicious validator involved. The magnitude of undercollection scales with `gasUsed`, so payloads with large gas consumption lose proportionally more fee revenue per block, persistently understating the correct fee burn versus what the fee-market design intends.

### Likelihood Explanation
High likelihood of triggering on essentially every block where the feemarket's dynamically adjusted base fee is not an exact integer multiple of `1e18` (i.e., almost always, given how EIP-1559-style adjustment arithmetic works). No attacker action beyond normal `MsgExecutePayload` usage is required — this happens automatically and silently on the default user-facing execution path.

### Recommendation
Compute `gasCost` using the full-precision `LegacyDec` value and only truncate once, at the very end:
```go
gasCost := baseFee.MulInt64(int64(gasUsed)).TruncateInt().BigInt()
```
or equivalently perform the `big.Int` multiplication using the untruncated 18-decimal representation of `baseFee` and `gasUsed`, and divide by `1e18` only after the multiplication, so any rounding error is bounded to less than 1 upc total rather than scaled by `gasUsed`.

### Proof of Concept
Given `baseFee = 1.9 upc` (represented internally as LegacyDec `1900000000000000000`, i.e., `1.9 * 1e18`) and `gasUsed = 10,000,000`:
- Current code: `baseFeeBig.Div(1.9e18, 1e18) = 1` (truncated) → `gasCost = 1 * 10,000,000 = 10,000,000 upc`.
- Correct value: `1.9 * 10,000,000 = 19,000,000 upc`.

The protocol under-collects/under-burns 9,000,000 upc (~47%) for this single execution, purely from calling `MsgExecutePayload` as an ordinary user with no elevated privileges. This can be verified by unit-testing `CalculateGasCost` with a fractional `LegacyDec` base fee (e.g., `sdkmath.LegacyMustNewDecFromStr("1.9")`) and comparing against the mathematically correct product. // - baseFee: current network base fee
// - maxFeePerGas: maximum total fee user is willing to pay
// - maxPriorityFeePerGas: maximum tip to validator
// - gasUsed: amount of gas consumed
func (k Keeper) CalculateGasCost(
	baseFee sdkmath.LegacyDec,
	maxFeePerGas *big.Int,
	maxPriorityFeePerGas *big.Int,
	gasUsed uint64,
) (*big.Int, error) {
	baseFeeBig := baseFee.BigInt()
	// @dev: LegacyDec stores values with 18-decimal precision internally, so 1 upc = 1e18
	// in the LegacyDec representation. Since 1 upc is the smallest denomination (like wei
	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.
	// This division unwraps the LegacyDec encoding back to the actual upc amount.

	baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))

	// Step 1: Validate maxFeePerGas >= baseFee

		return nil, fmt.Errorf("maxFeePerGas (%s) cannot be less than baseFee (%s)", maxFeePerGas, baseFeeBig)
	}

	// tipPlusBase := maxFeePerGas

	// Step 3: Find effective gas price by taking minimum
	// @dev: Currently, since we are not using maxPriorityFeePerGas, effectiveGasPrice is just baseFee
	effectiveGasPrice := new(big.Int).Set(baseFeeBig)

		"gas_cost", gasCost.String(),
	)

	return gasCost, nil
}
