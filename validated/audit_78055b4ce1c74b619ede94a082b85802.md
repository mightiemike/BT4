This confirms the analog. `LiquidityCap` is a per-token, per-chain configured limit on `TokenConfig` (validated as required in `ValidateBasic`), analogous to sUSX's `mintCap`, and the PRC20 `depositPRC20Token`/`depositPRC20WithAutoSwap` calls on the `UniversalCore`/PRC20 contract can revert for cap or other on-chain reasons (test evidence: `t.Run("solana FUNDS inbound with missing token config records FAILED PCTx"...)` shows deposit failures are handled as `"FAILED"` `PcTx`). The key issue is in the `IsCEA=true` branch of `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload`: when `depositPRC20` fails, the code explicitly skips creating an `INBOUND_REVERT` outbound ("isCEA failures never create an INBOUND_REVERT outbound"), unlike the non-CEA path which builds a `buildRevertOutbound` and refunds the user automatically.

### Title
Cross-chain inbound funds permanently locked when PRC20 mint/deposit fails on isCEA inbound path (mintCap/liquidityCap analog) - (File: x/uexecutor/keeper/execute_inbound_funds.go, execute_inbound_funds_and_payload.go, execute_inbound_gas_and_payload.go)

### Summary
When an inbound cross-chain transfer is routed through the `IsCEA` (Cross-chain Explicit Address) path and the PRC20 mint/deposit call (`depositPRC20` → `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` on `UniversalCore`) fails — e.g. because the destination-side `LiquidityCap` for that token is reached, or any other on-chain revert condition in the PRC20/`UniversalCore` mint path — the keeper records a `"FAILED"` `PcTx` but deliberately does **not** create an `INBOUND_REVERT` outbound to refund the user's funds back to the source chain. This exactly mirrors the sUSX report: destination-side mint cap causes the finalize/deposit step to revert, and there is no fallback path to return the user's already-bridged/locked funds.

### Finding Description
`ExecuteInboundFunds` [1](#0-0) , `ExecuteInboundFundsAndPayload` [2](#0-1) , and `ExecuteInboundGasAndPayload` [3](#0-2)  all share the same explicit design choice: "isCEA failures never create an INBOUND_REVERT outbound." This is enforced and asserted directly in tests [4](#0-3) .

The `depositPRC20` helper resolves the PRC20 token from `TokenConfig` and calls `CallPRC20Deposit`, which is a real `DerivedEVMCall` to the `UniversalCore`/PRC20 mint entrypoint [5](#0-4) [6](#0-5) . Each `TokenConfig` carries a mandatory `LiquidityCap` field (analogous to sUSX's `mintCap`), enforced only for non-emptiness in `ValidateBasic`, not for value sanity relative to actual usage [7](#0-6) . If the underlying PRC20/`UniversalCore` mint logic enforces that cap (or any other destination-side minting constraint) and reverts once it is reached, `depositPRC20` returns an error just like the "missing token config" case already covered by tests [8](#0-7) .

For the non-`IsCEA` path, this exact failure is caught and a `buildRevertOutbound` is attached automatically so UVs sign and broadcast a refund back to the source chain [9](#0-8) . But for `IsCEA=true` inbounds — which are user-reachable and driven purely by attacker/user-controlled `Recipient`/`AssetAddr` fields honestly observed and voted by UVs — the same deposit failure results only in a `FAILED` `PcTx` with no outbound created at all, confirmed by the "isCEA FUNDS_AND_PAYLOAD inbound deposit failure does NOT create revert outbound" test [10](#0-9) . There is no user-facing retry, no `RevertStuckInbound` applicability (that path requires an `EXPIRED` ballot, not a finalized-but-failed one, per `admin_revert.go`), and no automatic recovery mechanism for this specific failure mode.

### Impact Explanation
Funds bridged into Push Chain via an `IsCEA` inbound are consumed on the source chain (the gateway event already happened and was finalized by honest UV votes) but never minted as PRC20 on Push Chain if the deposit reverts, and the protocol records this as a terminal `FAILED` state with no automated path to refund the source-chain sender. This is a direct funds-locking condition reachable by an ordinary/honest user simply sending a large-enough transfer (or any transfer once cumulative volume nears the token's configured `LiquidityCap`), without any privileged or malicious actor involved — matching the "permanent loss" / "permanent freezing" allowed impact category.

### Likelihood Explanation
This requires no attacker sophistication: any user (or several users collectively) sending inbound `FUNDS`, `FUNDS_AND_PAYLOAD`, or `GAS_AND_PAYLOAD` transfers with `IsCEA=true` once the destination PRC20's mint constraint (`LiquidityCap` or equivalent on-chain limit) is reached will trigger this. The `IsCEA` flag and recipient are attacker/user-controlled in the inbound message flow, and honest UVs vote the inbound exactly as observed, so this is fully reachable through the default, non-privileged transaction submission path.

### Recommendation
Extend the deposit-failure handling in the `IsCEA` branches of `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload` to build and attach an `INBOUND_REVERT` outbound (same as the non-CEA path) whenever `depositPRC20`/`gasAndPayloadDepositAutoSwap` fails, rather than unconditionally suppressing the revert for all `IsCEA` failures. At minimum, provide a user- or permissionless-triggerable recovery path equivalent to `RevertStuckInbound` that does not require the ballot to be `EXPIRED` first.

### Proof of Concept
1. Register a `TokenConfig` with a `LiquidityCap`/mint cap that the destination PRC20 contract enforces on `depositPRC20Token`.
2. Submit enough inbound `FUNDS` transfers with `IsCEA=true` (or a single transfer large enough) so that the next deposit would exceed the cap.
3. UVs observe and vote the inbound to quorum via `MsgVoteInbound`; `ExecuteInboundFunds` calls `depositPRC20`, which reverts due to the cap.
4. Verify: `PcTx[0].Status == "FAILED"` and `utx.OutboundTx` contains **no** `INBOUND_REVERT` entry — as already demonstrated structurally by the existing test `"isCEA FUNDS_AND_PAYLOAD inbound deposit failure does NOT create revert outbound"` [10](#0-9) . The user's source-chain funds are now unrecoverable through any automated protocol path.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

// buildRevertOutbound creates an INBOUND_REVERT outbound with gas fields populated
// from the UniversalCore contract via getOutboundTxGasAndFees.
func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {
	recipient := inbound.Sender
	if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" {
		recipient = inbound.RevertInstructions.FundRecipient
	}

	outbound := &types.OutboundTx{
		DestinationChain:  inbound.SourceChain,
		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}
