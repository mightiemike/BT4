### Title
Open Redirect via Protocol-Relative URL Bypass in `sanitizeRedirectUrl` - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts] / [File: packages/apps/shopify-app-react-router/src/server/authenticate/admin/helpers/validate-redirect-url.ts])

### Summary
The gravity-bridge report's core failure pattern is that user/attacker-supplied input is trusted to determine the destination of a privileged operation without sufficiently restricting what that destination can be, letting an attacker redirect value/flow off the trusted system. The analogous pattern here is `sanitizeRedirectUrl`'s `isSafe()` check, which is meant to keep app-bridge/auth redirects scoped to the app's own domain but fails to reject protocol-relative URLs (`//evil.com`), allowing the redirect target's origin to be silently swapped to an attacker-controlled host.

### Finding Description
`isSafe()` in `validate-redirect-url.ts` performs these checks on a caller-supplied `redirectUrl` before allowing it to be used as a redirect target: [1](#0-0) [2](#0-1) 

It rejects triple-slash file URIs (`FILE_URI_MATCH = /\/\/\//`) and whitespace, then resolves the URL relative to `domain` via `new URL(redirectUrl, domain)`, and only validates the resulting `url.protocol` and `url.pathname` (for double-slash-containing paths). It never verifies that `url.hostname`/`url.origin` still matches the trusted `domain`.

A protocol-relative value such as `//evil.com` (only two slashes, so it passes `FILE_URI_MATCH`) resolves via the WHATWG `URL` constructor to `https://evil.com/` when combined with a base of `https://my-app.example.com`. Its `pathname` is simply `/`, so `INVALID_RELATIVE_URL` (`/[/\\][/\\]/`, checked only against `pathname`) never triggers. `protocol` is `https:`, which passes both `VALID_PROTOCOLS` and the `requireSSL` check. The function therefore returns a `URL` object pointing at an entirely different, attacker-chosen origin, and `sanitizeRedirectUrl` returns it as valid: [3](#0-2) 

This helper is used by `render-app-bridge.ts`/embedded-admin redirect flows (`renderAppBridge`) in both `shopify-app-remix` and `shopify-app-react-router` to decide where to send the browser during the embedded-app / session-token bounce and OAuth flows. Because these flows run before or during authentication (they are reached with only an anonymous/embedded request, no privileged session required), an attacker who can influence the redirect/bounce URL parameter can cause the app to issue a redirect to an attacker-controlled origin instead of keeping the user within the app/Shopify admin domain.

### Impact Explanation
This is a classic open-redirect condition in an authentication-adjacent code path. In the context of Shopify embedded apps, redirect targets during the auth/bounce flow can carry sensitive query parameters (`shop`, `host`, `id_token`, session-token bounce state). An attacker-controlled redirect destination could be leveraged for phishing (making a redirect that looks like it originates from the legitimate app to instead land on an attacker page), and in the worst case, referrer/query leakage of authorization-adjacent parameters to an external host. This matches the "open redirect" acceptance criterion for a valid analog of the reported bug class (trusting attacker-influenced routing/destination data without full validation, leading to value/credential exposure outside the trust boundary).

### Likelihood Explanation
The flaw is directly triggerable by any unauthenticated request that can supply a redirect URL to `sanitizeRedirectUrl`/`renderAppBridge` (e.g., via query parameters processed during the admin auth/bounce flow). No privileged actor, secret leak, or MITM is required — a single crafted HTTP request with a `//`-prefixed value is sufficient to make `isSafe()` return `true` for an off-app origin. This is a straightforward parsing bypass rather than a theoretical edge case, and the existing test suite specifically confirms the file-URI (`///`) and whitespace cases are rejected but does not test for a bare `//host` value, indicating the gap is untested/unguarded.

### Recommendation
In `isSafe()`, after resolving `url = new URL(redirectUrl, domain)`, explicitly verify that `url.origin` (or `url.hostname`) equals the origin/hostname of `domain`, rejecting any redirect that would leave the app's own origin — not just checking `protocol` and `pathname`. Additionally, treat any `redirectUrl` beginning with `//` (protocol-relative) as unsafe up front, consistent with the existing `FILE_URI_MATCH` intent.

### Proof of Concept
```ts
import {sanitizeRedirectUrl} from 'packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url';

// domain = the app's own trusted origin, e.g. "https://my-app.example.com"
const APP_URL = 'https://my-app.example.com';

// Attacker-supplied redirect value
const maliciousRedirect = '//evil.com/steal';

const result = sanitizeRedirectUrl(APP_URL, maliciousRedirect, {requireSSL: true});

console.log(result.href);
// Expected (if properly validated): should throw ShopifyError('Invalid URL. Refusing to redirect')
// Actual: returns a URL object for "https://evil.com/steal" — bypassing the same-origin intent of sanitizeRedirectUrl
```

```typescript
function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
```

```typescript
export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}
```
