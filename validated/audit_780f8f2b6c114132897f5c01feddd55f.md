### Title
`liquidate-multi` silently absorbs a failed `liquidate` sub-call, letting a partially-executed liquidation's fund movements persist while bad-debt socialization is skipped - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` invokes `liquidate` for each position through a bare `map`, without `try!`/`unwrap!` propagation of the inner `(response ...)` value [1](#0-0) . Inside `liquidate`, the fund-moving steps (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) execute and commit their state changes as independent `contract-call?`s **before** the final `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` guard that covers bad-debt write-off for any *other* debt asset the borrower still owes [2](#0-1) . When called directly, a failure of that later guard reverts the whole top-level transaction (all committed sub-calls included). When called via `liquidate-multi`, the error returned by the nested `liquidate` call is only captured as a list element and never propagated to the top level, so the top-level function still returns `ok` and none of the earlier successful `contract-call?`s are rolled back.

### Finding Description
`liquidate` performs, in order:
1. Repay the targeted debt via `vault-system-repay` (`try!`, an atomic `contract-call?` that commits on success) [3](#0-2) .
2. Remove the borrower's scaled debt for that asset via `contract-call? .market-vault debt-remove-scaled` and seize collateral via `contract-call? .market-vault collateral-remove` — both `try!`-wrapped, atomic, and committed independently of the rest of the function [4](#0-3) .
3. Only afterward, if the position ends up with no collateral left, it folds over the borrower's *other* debt entries with `socialize-debt-asset` and asserts the fold succeeded: `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [5](#0-4) .

`socialize-debt-asset` itself calls the vault's `socialize-debt`, which asserts `(> scaled-amount u0) ERR-AMOUNT-ZERO` [6](#0-5) , so any residual debt entry with a zero (or otherwise vault-rejected) scaled amount makes this fold fail, which is realistic for a borrower with dust-level residual debt on a second asset.

`liquidate` is a normal function call (not a `contract-call?`) when invoked from `call-liquidate`/`liquidate-multi`, so returning `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)` from step 3 does not, by itself, undo the already-committed `contract-call?`s from steps 1–2. Whether those changes ultimately persist depends solely on the *top-level* transaction's own return value. When a user calls `liquidate` directly, this is safe: `liquidate` is the top-level function, so an error there reverts the entire transaction, including steps 1–2. But `liquidate-multi` calls `liquidate` indirectly through `(map call-liquidate positions)` and wraps everything in `(ok (list ...))` [1](#0-0) , without ever checking or propagating each element's `err`. Because the top-level `liquidate-multi` call itself returns `ok`, the whole transaction succeeds, and the state committed by the earlier, successful `contract-call?`s inside the failed `liquidate` sub-call is never rolled back.

### Impact Explanation
For a borrower whose targeted debt/collateral pair is fully liquidated but who still holds bad debt on a different debt asset, a liquidator using `liquidate-multi` can end up with: the targeted debt marked repaid and its collateral seized/transferred (steps 1–2 persist), while the mandatory bad-debt socialization for the *other* debt asset never happens (step 3 fails and is swallowed). The position is left with zero collateral but outstanding, un-written-down debt on the other asset — debt that can never again be recovered through normal liquidation (there is no collateral left to seize) and was never socialized into the affected vault's liquidity index. This strands that debt as permanently unbacked, uncollectable bad debt against the corresponding vault's depositors, i.e. permanent freezing/insolvency of LP funds for that asset — a Critical/High impact per the accepted classes.

### Likelihood Explanation
No privileged access or DAO action is required; any liquidator can call the public `liquidate-multi` entry point with a single crafted position where the "no collateral left" branch is hit and the borrower carries a residual dust debt entry on a second asset that fails the vault's `(> scaled-amount u0)` check. This is a realistic and easily engineered state (multi-asset debt positions with small residuals are common), requiring only one transaction.

### Recommendation
In `liquidate-multi`, propagate each `call-liquidate` result instead of unconditionally wrapping in `ok`, e.g. by using `try!`/`unwrap!` semantics that abort the whole batch transaction on any per-position failure, or restructure `liquidate` so the bad-debt socialization checks happen before any debt/collateral transferring `contract-call?`s are committed (guard-then-mutate ordering), so a later failure cannot leave earlier fund movements persisted while the overall function reports failure.

### Proof of Concept
1. Borrower opens a position with collateral C and two debt assets: primary debt asset A (large, targeted for liquidation) and debt asset B (small residual, e.g. dust amount whose scaled representation can reach `u0` after rounding).
2. Price of C drops so the position is liquidatable; a liquidator calls `market.liquidate-multi` with a single position entry targeting debt asset A with an amount that consumes all of C.
3. Inside `liquidate`: `vault-system-repay` for A succeeds, `debt-remove-scaled` for A succeeds, `collateral-remove` seizes all of C (all committed, atomic `contract-call?`s).
4. `no-collateral-left` is `true`; the fold `socialize-debt-asset` is invoked on the remaining debt list containing asset B's dust `scaled: 0` entry; the vault's `socialize-debt` asserts `(> scaled-amount u0)`, fails, and `unwrap!` sets `success: false`.
5. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fires, `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.
6. Because this happened inside `map call-liquidate` in `liquidate-multi`, the error is just an element of the returned list; `liquidate-multi` still returns `(ok (list (err ERR-BAD-DEBT-SOCIALIZATION-FAILED)))` and the transaction succeeds.
7. Result: debt A is repaid and collateral C is transferred to the liquidator (steps from #3 persisted), but debt B remains outstanding against a position with zero collateral and was never socialized/written down in vault B's liquidity index.
