### Title
Panic-based Denial of Service via Client-Side Proof Fee Computation on Non-AllResourceBounds Transactions - (File: `crates/blockifier/src/fee/resources.rs`)

### Summary
`ArchivalDataResources::get_client_side_proof_gas_cost` in the blockifier fee module contains an `unreachable!()` branch that fires whenever a transaction is flagged as having a client-side proof (`has_client_side_proof = true`) while its gas-vector computation mode is `NoL2Gas`. The code assumes, purely by comment-level invariant rather than a compile-time or explicitly-enforced runtime check at this call site, that "Client side proving is only supported from V3 transactions, which use AllResourceBounds." If a transaction reaches this fee-computation path with `has_client_side_proof = true` but a resource-bounds configuration that maps to `GasVectorComputationMode::NoL2Gas` (e.g., a V3 `L1Gas`-only `ValidResourceBounds`), the sequencer process panics. ### Finding Description
`ArchivalDataResources::to_gas_vector` unconditionally calls `get_client_side_proof_gas_cost` as part of computing archival-data gas costs for every transaction's fee/resource accounting: [2](#0-1) 

Inside `get_client_side_proof_gas_cost`, the `All` branch returns a computed gas cost, while the `NoL2Gas` branch is treated as impossible and hard-panics via `unreachable!()`: [3](#0-2) 

The correctness of this `unreachable!()` depends entirely on an implicit invariant — "a transaction with client-side proof data always uses `ValidResourceBounds::AllResources`" — that is not enforced by the type system at this point in the code. `ValidResourceBounds` supports both an `L1Gas`-only variant and an `AllResources` variant for V3 transactions, and the resource-bounds variant chosen by the transaction sender directly determines whether `GasVectorComputationMode` resolves to `All` or `NoL2Gas`. The `RpcInvokeTransactionV3`/`proof_facts` fields that populate `has_client_side_proof` are attacker-controlled inputs from a single submitted transaction, structurally decoupled from the `resource_bounds` field on the same transaction. This is the same bug class as the reported OFFIS DCMTK issue: a component assumes a specific "shape"/type of a record (a query believed to always be well-formed and self-consistent) without validating that assumption before dereferencing/branching on it, allowing a single crafted input that violates the implicit shape/type assumption to crash the service.

### Impact Explanation
Fee/resource-vector computation via `TransactionResources::to_gas_vector` → `StarknetResources::to_gas_vector` → `ArchivalDataResources::to_gas_vector` runs during transaction execution for every account transaction processed by the blockifier (gateway pre-validation, mempool re-validation, and block building/execution). Because this is deterministic logic executed identically by every honest sequencer node on the same transaction, a single malicious transaction reaching this code path with `has_client_side_proof = true` and `L1Gas`-only resource bounds would panic every node that attempts to execute or fee-validate it — a process-crashing Denial of Service reachable from an unprivileged, single submitted transaction. If encountered during block building/proposal, this can result in the network becoming unable to process the transaction (and potentially the block containing it), which matches the "network unable to confirm new transactions" impact class for this analog scan.

### Likelihood Explanation
Likelihood depends on whether upstream transaction validation (RPC gateway ingestion, `apollo_gateway` stateless/stateful validators, or blockifier transaction construction) rejects the specific combination of non-trivial `proof_facts` together with non-`AllResources` `resource_bounds` before fee computation is reached. I was not able to conclusively confirm the presence or absence of such a cross-field check within the available tool budget — the only in-repo hit for `has_client_side_proof` outside of the fee module itself is a single reference in `crates/blockifier/src/transaction/account_transaction.rs`, which I was unable to inspect before running out of iterations. If no such explicit rejection exists prior to fee computation, likelihood is high, since an attacker fully controls both `proof_facts` and `resource_bounds` on a self-submitted V3 transaction.

### Recommendation
Replace the `unreachable!()` in `get_client_side_proof_gas_cost` with either (a) an explicit, enforced validation at transaction ingestion (gateway/stateless validation) that rejects any transaction where `proof_facts`/client-side-proof data is present but `resource_bounds` is not `ValidResourceBounds::AllResources`, returning a proper `TransactionFeeError`/validation error instead of panicking deep in fee computation, or (b) making the function itself return a `Result` and propagate a typed error for the `NoL2Gas` case rather than asserting an invariant that is not locally provable at that call site. Per the repository's own code-style rule ("Never panic on data reachable from requests"), this path must not panic on attacker-controlled input, and this exact invariant should be validated at the earliest point in the pipeline where both fields are jointly available.

### Proof of Concept
1. Craft a V3 invoke transaction (or declare/deploy-account, if `proof_facts`-bearing) with a non-empty `proof_facts` field (making `has_client_side_proof` true when constructing `ArchivalDataResources`).
2. Set `resource_bounds` to `ValidResourceBounds::L1Gas(...)` (L1-gas-only bounds), which resolves `GasVectorComputationMode` to `NoL2Gas` via `get_gas_vector_computation_mode()`.
3. Submit the transaction to the gateway/mempool as an ordinary unprivileged sender.
4. When the sequencer computes transaction resources/fee (`TransactionResources::to_gas_vector` → `ArchivalDataResources::to_gas_vector` → `get_client_side_proof_gas_cost`), the `NoL2Gas` branch executes `unreachable!()`, panicking the node process handling that transaction. [1](#0-0)

    /// Returns the fixed gas cost for client-side proofs.
    /// The per-felt cost for proof_facts is already included in calldata_length.
    fn get_client_side_proof_gas_cost(
        &self,
        versioned_constants: &VersionedConstants,
        mode: &GasVectorComputationMode,
    ) -> GasVector {
        if !self.has_client_side_proof {
            return GasVector::ZERO;
        }

        let archival_gas_costs = versioned_constants.get_archival_data_gas_costs(mode);

        // Client-side proofs have a fixed gas cost. This cost corresponds to the
        // current proof version (reflected in the first proof fact).
        let proof_gas: GasAmount = archival_gas_costs.gas_per_proof.to_integer().into();

        match mode {
            GasVectorComputationMode::All => GasVector::from_l2_gas(proof_gas),
            GasVectorComputationMode::NoL2Gas => {
                unreachable!(
                    "Client side proving is only supported from V3 transactions, which use \
                     AllResourceBounds."
                )
            }
        }
    }
