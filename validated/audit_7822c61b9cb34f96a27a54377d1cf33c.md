## Title
Feature-gated unfreeze withdrawal/cancellation checks are bypassed via TVM native contract calls - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/CancelAllUnfreezeV2Processor.java`)

### Summary
The `WithdrawExpireUnfreezeContract` and `CancelAllUnfreezeV2Contract` transactions are gated behind committee-controlled feature flags (`supportUnfreezeDelay()` and `supportAllowCancelAllUnfreezeV2()`), enforced in `WithdrawExpireUnfreezeActuator.validate()` and `CancelAllUnfreezeV2Actuator.validate()` respectively. However, the same operations are reachable from TVM smart contracts via the `withdrawExpireUnfreeze()` and `cancelAllUnfreezeV2Action()` opcodes in `Program.java`, which delegate to `WithdrawExpireUnfreezeProcessor` / `CancelAllUnfreezeV2Processor`. Neither native-contract processor checks the corresponding feature flag, so the "pause"/gate enforced at the actuator layer is bypassed entirely through the TVM path — directly analogous to the reported `registerOperatorWithChurn` bug class, where a guarded top-level entrypoint's protection is skipped by an alternate path that reaches the same internal state-mutating logic.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` enforces the feature gate: [1](#0-0) 

Similarly, `CancelAllUnfreezeV2Actuator.validate()` enforces its own feature gate: [2](#0-1) 

Both features are only meant to be usable once activated by a committee proposal (`ALLOW_CANCEL_ALL_UNFREEZE_V2` / `unfreezeDelayDays`), consistent with the governance flags documented in `common/src/main/resources/reference.conf` (e.g. `unfreezeDelayDays = 0`).

However, the equivalent business logic is duplicated in the TVM native-contract processors, which are invoked directly from opcode handlers in `Program.java`: [3](#0-2) [4](#0-3) 

Neither `WithdrawExpireUnfreezeProcessor.validate()` nor `CancelAllUnfreezeV2Processor.validate()` checks the `supportUnfreezeDelay()` / `supportAllowCancelAllUnfreezeV2()` flags that gate their actuator counterparts: [5](#0-4) [6](#0-5) 

This mirrors the reported vulnerability class exactly: a protective condition (`onlyWhenNotPaused` for deregister / feature-flag check for `validate()`) exists on one entrypoint, but a second entrypoint reaching the identical internal state mutation (`_deregisterOperator` internal function / `Processor.execute()`) omits the check, allowing the guarded action to occur regardless of the gate's state.

### Impact Explanation
If the committee has not yet enabled `unfreezeDelayDays` (i.e., `supportUnfreezeDelay()` is false) or has not enabled `allowCancelAllUnfreezeV2`, ordinary transaction submitters are blocked from calling `WithdrawExpireUnfreezeContract`/`CancelAllUnfreezeV2Contract`. However, any account can deploy or interact with a smart contract that invokes the corresponding TVM opcodes (`withdrawExpireUnfreeze`, `cancelAllUnfreezeBalanceV2`) to reach `Program.withdrawExpireUnfreeze()` / `Program.cancelAllUnfreezeV2Action()`, which bypasses the feature-flag validation entirely. This allows unauthorized early access to governance-gated resource/balance-unlock functionality, undermining the intended committee-controlled activation of these features and creating a state-transition path inconsistent with the actuator-level rules — a concrete invalid-state/governance-bypass impact.

### Likelihood Explanation
The TVM opcodes for `withdrawExpireUnfreeze` and `cancelAllUnfreezeV2Action` are unprivileged and reachable by any account deploying/calling a smart contract; no special role or permission is required. The bug is deterministic (always reachable whenever the flag is disabled), making it a fully practical, unprivileged-user-triggerable bypass — not merely theoretical.

### Recommendation
Add the same feature-flag checks (`repo.getDynamicPropertiesStore().supportUnfreezeDelay()` and `supportAllowCancelAllUnfreezeV2()`) inside `WithdrawExpireUnfreezeProcessor.validate()` and `CancelAllUnfreezeV2Processor.validate()`, mirroring the checks already present in `WithdrawExpireUnfreezeActuator.validate()` and `CancelAllUnfreezeV2Actuator.validate()`, so that both the actuator (regular transaction) path and the TVM native-contract path enforce identical governance gating.

### Proof of Concept
1. On a network/config where `unfreezeDelayDays` (or `allowCancelAllUnfreezeV2`) has not been enabled via committee proposal (default `0` per `common/src/main/resources/reference.conf`).
2. Confirm a regular `WithdrawExpireUnfreezeContract`/`CancelAllUnfreezeV2Contract` transaction fails validation with "Not support ... transaction, need to be opened by the committee" (as enforced in `WithdrawExpireUnfreezeActuator.validate()` / `CancelAllUnfreezeV2Actuator.validate()`).
3. Deploy a contract that triggers the TVM opcode paths exercised in `framework/src/test/java/org/tron/common/runtime/vm/FreezeV2Test.java` (`withdrawExpireUnfreeze(...)`, `cancelAllUnfreezeBalanceV2()`), which route to `Program.withdrawExpireUnfreeze()` / `Program.cancelAllUnfreezeV2Action()`.
4. Observe that the call succeeds and mutates account state (releases/cancels unfrozen balances) even though the equivalent top-level contract transaction is rejected — demonstrating the feature-gate bypass via the TVM entrypoint.

  public long withdrawExpireUnfreeze() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawExpireUnfreeze", nonce, null);

    try {
      WithdrawExpireUnfreezeParam param = new WithdrawExpireUnfreezeParam();
      param.setOwnerAddress(owner);

      WithdrawExpireUnfreezeProcessor processor = new WithdrawExpireUnfreezeProcessor();

      repository.commit();

    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
  }

      CancelAllUnfreezeV2Processor processor = new CancelAllUnfreezeV2Processor();

        addInternalTx(null, owner, owner, result.get(VMConstant.WITHDRAW_EXPIRE_BALANCE), null,

      if (internalTx != null && CommonParameter.getInstance().saveCancelAllUnfreezeV2Details) {

            BANDWIDTH.name(), result.getOrDefault(BANDWIDTH.name(), 0L),

            TRON_POWER.name(), result.getOrDefault(TRON_POWER.name(), 0L)));

      logger.warn("TVM CancelAllUnfreezeV2: validate failure. Reason: {}", e.getMessage());

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
  }
