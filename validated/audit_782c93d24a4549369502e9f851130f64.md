### Title
Unbounded per-address delegation index growth enables O(N) prefix scans and sort on every `getdelegatedresourceaccountindex` HTTP call - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore.delegateV2` writes one new key per `DelegateResourceContract` under the `V2_FROM_PREFIX`/`V2_TO_PREFIX` namespace with no cap on how many distinct receiver addresses a single owner can accumulate. `GetDelegatedResourceAccountIndexServlet.fillResponse` → `Wallet.getDelegatedResourceAccountIndex` → `getWithPrefix` then performs two full `prefixQuery()` scans plus an in-memory sort over all matching entries for the requested address, so both the write path is cheap and unbounded and the read path cost scales with the number of edges the attacker created.

### Finding Description
Each `DelegateResourceContract` from address A to a distinct address B calls `DelegateResourceActuator.delegateResource` → `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, timestamp)` [1](#0-0) , which unconditionally inserts a new key `V2_FROM_PREFIX+from+to` and `V2_TO_PREFIX+to+from` with no per-account limit on the number of distinct delegation edges [2](#0-1) . The `validate()` method checks balance/lock/account-existence but never bounds how many times an owner can delegate to distinct receivers, so an attacker can cheaply mint many receiver accounts (paying only account-creation + 1 TRX minimum delegate balance each, refundable via unfreeze cycles) to grow the from-owner's edge count arbitrarily [3](#0-2) .

On the read side, `getWithPrefix` performs `this.prefixQuery(key)` over `V2_FROM_PREFIX+address` and `V2_TO_PREFIX+address`, materializes all matches into an `ArrayList`, and sorts by timestamp with `Comparator.comparing` — an O(N log N) operation with no pagination or result-size cap [4](#0-3) . `GetDelegatedResourceAccountIndexServlet.fillResponse` calls this synchronously on the Jetty request thread with no size limit on the response, then serializes the full list to JSON [5](#0-4) . `RateLimiterServlet.service` only throttles per-endpoint/global QPS via `GlobalRateLimiter`/`IRateLimiter`; it does not bound the computational cost of a single already-admitted request, so a request that passes rate limiting still ties up a worker thread for a duration proportional to N [6](#0-5) . This matches the classic "cheap read, unbounded CPU" pattern: creating the edges is a one-time write cost, but every subsequent GET re-scans and re-sorts the full edge set.

### Impact Explanation
This is a DoS-via-RPC-API class issue: an attacker can grow the number of edges for one address unbounded, then repeatedly issue GET requests that consume disproportionate CPU/GC time per request relative to the fixed QPS cost accounted by the rate limiter, degrading HTTP thread-pool responsiveness for other API consumers on the same node. Impact is scoped to the queried full/solidity/PBFT node's HTTP API responsiveness — it does not affect consensus, funds, or private keys.

### Likelihood Explanation
Feasible for any funded account: creating N delegation edges requires N distinct receiver accounts (each needing to exist and receive ≥1 TRX in `FreezeBalanceV2`/delegate balance), account activation fees, and N signed `DelegateResourceContract` transactions — all payable with ordinary funds and no privileged role. This is a real cost but is linear and modest compared to the resulting superlinear-ish per-query CPU cost sustained across arbitrarily many repeated GETs; the "expensive setup once, cheap-looking abuse forever" pattern is the concerning part. Note: this analysis could not fully verify the exact big-O growth curve or measure real wall-clock numbers (e.g., benchmarking `prefixQuery` cost at N=50k) since this requires runtime profiling not available via static code reading; the severity in practice depends on underlying DB (LevelDB/RocksDB) prefix-scan performance characteristics.

### Recommendation
Add pagination (limit/offset or a hard cap, e.g., MAX_DELEGATE_INDEX_RESULTS) to `getWithPrefix` and to the HTTP API contract for `getdelegatedresourceaccountindex`, and/or persist delegation index entries in an already-sorted structure so no runtime sort over the full set is required. Consider also capping the number of distinct delegation edges a single owner/receiver pair set can create, or moving expensive prefix scans off the request-handling thread pool.

### Proof of Concept
Not able to provide a full runtime-measured JUnit/timing PoC without executing the code (no filesystem/terminal access in this session); the reachable code path evidence above (`DelegateResourceActuator.delegateResource` → `delegateV2` with no cap, and `GetDelegatedResourceAccountIndexServlet.fillResponse` → `getWithPrefix` with unbounded `prefixQuery` + full sort) supports the theoretical flow described in the question. A concrete reproduction would require: (1) scripting N `DelegateResourceContract` broadcasts from one funded owner to N distinct funded receiver addresses on a local full node, (2) timing repeated `GET /wallet/getdelegatedresourceaccountindex?value=<owner>` calls while measuring latency growth vs. N, and (3) confirming other concurrent `RateLimiterServlet`-backed endpoint calls are delayed while the large query executes on a shared Jetty thread pool.

  public void delegateV2(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(V2_FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));

    this.put(fromKey, toIndexCapsule);

  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
