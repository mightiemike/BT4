## Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, allowing replay/backup verification to accept a `TransactionOutput` whose committed state root diverges from local re-execution - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by chunk-executor replay, `db-tool`'s `replay_on_archive`, and the Aptos debugger to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` stored/retrieved from the ledger. The function explicitly does not compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that carry the committed state/hot-state/native-position Merkle roots. A local execution that produces a different state root than what was actually committed to the chain will still pass this check.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  verifies four things: transaction status, gas used, write-set hash (`state_change_hash`), and event root hash. It does not verify `state_checkpoint_hash` / `hot_state_checkpoint_hash` (in `TransactionInfoV1`) or `position_state_checkpoint_hash`, and the code contains an explicit acknowledgment of the gap: [2](#0-1) 

These checkpoint hashes are the actual Jellyfish Merkle roots (state root, hot-state root, and — under the new native-trading subsystem — the position-state root) that get embedded in `TransactionInfoV1` and folded into the transaction accumulator that ledger infos commit to, as seen in `TransactionInfo::builder_v1` at [3](#0-2)  and the feature-gating logic in `types/src/on_chain_config/aptos_features.rs` (`TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) at [4](#0-3) .

This check is used directly in the chunk-executor's replay-verify path, `verify_execution`, which re-executes historical transactions and calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` for every transaction in the chunk: [5](#0-4) 

It's also invoked by `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` — all tooling whose entire purpose is to assert "the state my node computed for this transaction is the same state that was actually committed to the ledger."

Because the comparator omits checkpoint-hash fields, if the state root actually committed on-chain diverges from what a node's local re-execution computes (e.g. due to a bug in the hot-state/native-position root computation path, or a schema/serialization mismatch introduced by the new `TRADING_NATIVE`/`HOTNESS_IN_EPILOGUE` write-set formats mentioned in `types/src/block_executor/config.rs`), replay-verify tooling will report success even though the two roots are different.

### Impact Explanation
This breaks the core state-commitment integrity invariant described in the task: "Committed state that differs from the correct VM result... survive[s] executor-to-storage handoff unchanged" and "replay paths... must not reinterpret committed data into a different ledger state." Replay-verify (`replay_on_archive`) and the debugger are the primary tools operators and auditors use to detect state divergence after a bug, upgrade, or malicious validator behavior. A silent gap in the very comparator that's supposed to catch such divergence means a hard-fork-class state-root corruption (e.g., from the newly introduced hot-state / native-position checkpoint roots) could go undetected by this tooling, masking exactly the kind of committed-state corruption these tools exist to catch.

### Likelihood Explanation
The gap is self-acknowledged in the code as a known, temporary omission ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating the feature (native trading position roots) is being staged and the safety check is not yet wired in. Since `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is not confirmed to be on-path for the default write-set format yet (I could not fully trace whether it's enabled on mainnet at present, nor did I confirm whether `hot_state_checkpoint_hash` is populated in the default `V0` transaction info path), I cannot assert with certainty this is exploitable today rather than a latent gap pending a not-yet-enabled feature. This uncertainty is a real limitation of my analysis.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against the equivalent values computed locally, before any code path that depends on this comparator for security-relevant replay/backup verification, and definitely before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Proof of Concept
Not executable from static review alone — this requires demonstrating that a divergent local re-execution state root is accepted by `chunk_executor::verify_execution` or `replay_on_archive`. I could not run tests in this environment to confirm this end-to-end; the finding is based on the explicit code comment and control-flow trace shown above indicating the checkpoint-hash fields are never compared in `ensure_match_transaction_info`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
