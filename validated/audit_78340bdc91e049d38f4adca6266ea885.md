### Title
Internal transaction value truncation before validation in TVM freeze/unfreeze native contracts causes indexers to record incorrect amounts - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
The `AtlETH.sol` report flags unsafe downcasting of `uint256` amounts to `uint112` that occurs *before* input validation, so events/logs can carry a truncated, misleading amount even when the underlying accounting operation reverts. The java-tron TVM native resource contracts (`freeze`, `freezeBalanceV2`, `unfreezeBalanceV2`) exhibit the same bug class: the amount recorded in the `InternalTransaction` (which feeds transaction traces / internal-transaction logs consumed by explorers and indexers) is derived from an **unchecked, truncating** conversion, while the actual accounting amount used moments later is derived from a **checked, exact** conversion that can throw and abort the operation.

### Finding Description
In `Program.freeze()`, `Program.freezeBalanceV2()`, and `Program.unfreezeBalanceV2()`, the resource amount is a 256-bit `DataWord` supplied directly from TVM stack input (attacker/caller controlled via a Solidity contract calling the native precompiled resource functions). The code first creates an `InternalTransaction` log entry using the unsafe `longValue()` accessor, which silently truncates/wraps a value outside the `long` range without throwing: [1](#0-0) 

Only afterward does the code attempt the actual accounting operation using `sValue().longValueExact()`, which throws `ArithmeticException` if the value does not fit in a `long`: [2](#0-1) 

The same pattern recurs for `freezeBalanceV2` and `unfreezeBalanceV2`: [3](#0-2) [4](#0-3) 

`DataWord.longValue()` performs no range check at all — it simply folds all 32 bytes into a `long` via shifting, which for values exceeding `Long.MAX_VALUE` produces an arbitrary, unrelated (and possibly negative) number: [5](#0-4) 

This is functionally identical to the AtlETH pattern: an oversized amount passed through an unchecked downcast is recorded/emitted (here, into the `InternalTransaction` value used for tracing/log output) *before* the code path that safely validates the amount and reverts (`ArithmeticException` → `internalTx.reject()`).

### Impact Explanation
When `internalTx.reject()` is called, the flag `rejected` is set on the `InternalTransaction` object, but the object itself (already constructed with the truncated/garbage `value`) was returned by `addInternalTx()` and may already have been added to the program's internal-transaction list before rejection is applied. Because the internal transaction's `value` field was already populated with the truncated `longValue()` result, external systems relying on program traces / internal transaction logs (`InternalTransactionPojo`, `TransactionLogTriggerCapsule`) can observe a nonsensical or misleadingly large/negative transferred amount for an operation that either never took effect or took effect with a completely different amount. This can confuse block explorers, accounting/indexing systems, and any downstream service that trusts the internal transaction value field, echoing the exact "confuse chain indexers" impact described in the original report. It does not directly cause fund loss or a consensus divergence (the real balance is protected by the subsequent `longValueExact()` check and `repository.commit()` only happens on success), so the impact is limited to observability/indexer-integrity rather than direct loss of funds.

### Likelihood Explanation
This is reachable by any unprivileged user through ordinary Solidity contracts calling the TVM native resource-management opcodes (`freezeBalanceV2(uint256,uint256)`, `unfreezeBalanceV2(uint256,uint256)`), which are documented, callable TVM extensions and require no special privilege — only the ability to pass a `uint256` value exceeding `Long.MAX_VALUE` (e.g., `2^63` or higher), which is trivial to construct. However, exploitation only produces a bad log/trace entry, not a state change, since the actual freeze/unfreeze is aborted on the `ArithmeticException`.

### Recommendation
Perform the safe/exact conversion (`sValue().longValueExact()`) first, and only construct/emit the `InternalTransaction` (and any other externally-visible artifact) using the validated `long` value. Alternatively, wrap the whole sequence (internal-tx creation + processor validate/execute) in a single try/catch so an out-of-range value never produces a partially-populated internal transaction with a garbage `value`.

### Proof of Concept
1. Deploy a Solidity contract that calls the native precompiled resource function equivalent to `freezeBalanceV2(uint256,uint256)` (or `unfreezeBalanceV2`) with an amount argument set to a `uint256` value greater than `Long.MAX_VALUE` (e.g., `2**64 - 1`).
2. In `Program.freezeBalanceV2(DataWord frozenBalance, DataWord resourceType)`, `addInternalTx(...,frozenBalance.longValue(), ...)` is invoked first, producing an internal transaction record with a truncated/wrapped `value` (not equal to the real requested amount).
3. `param.setFrozenBalance(frozenBalance.sValue().longValueExact())` subsequently throws `ArithmeticException`, causing `internalTx.reject()` to be called and the overall freeze operation to fail without state changes.
4. Inspect the transaction's internal-transaction trace/log (as exposed via `TransactionInfo`/`InternalTransactionPojo`/event triggers) — it will show an internal transaction with the garbage truncated `value` from step 2, which does not correspond to any real balance movement, misleading any indexer or explorer that parses this field.

Note: I was unable to fully confirm, within the available index, whether rejected internal transactions carrying this truncated value are actually surfaced through the public `TransactionInfo`/log-trigger APIs or filtered out downstream — this would need direct verification against `ProgramResult`, `TransactionLogTriggerCapsule`, and the internal-transaction JSON-RPC/HTTP endpoints in a full checkout of the repository (recommend a Devin session to trace this end-to-end if precise external exposure needs to be confirmed).

  public boolean freeze(DataWord receiverAddress, DataWord frozenBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,
        frozenBalance.longValue(), null,
        "freezeFor" + convertResourceToString(resourceType), nonce, null);

    FreezeBalanceParam param = new FreezeBalanceParam();
    param.setOwnerAddress(owner);
    param.setReceiverAddress(receiver);
    boolean needCheckFrozenTime = CommonParameter.getInstance()
        .getCheckFrozenTime() == 1; // for test
    param.setFrozenDuration(needCheckFrozenTime
        ? repository.getDynamicPropertiesStore().getMinFrozenTime() : 0);
    param.setResourceType(parseResourceCode(resourceType));
    try {
      FreezeBalanceProcessor processor = new FreezeBalanceProcessor();
      param.setFrozenBalance(frozenBalance.sValue().longValueExact());
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM Freeze: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM Freeze: frozenBalance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;

      processor.validate(param, repository);

    }
