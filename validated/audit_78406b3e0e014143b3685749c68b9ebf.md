### Title
Integer-division truncation in `BuiltinInstanceLimits::induced_gas_costs` can zero out per-instance proving-gas cost, letting a builtin be used for free in bouncer accounting - (File: crates/blockifier/src/bouncer.rs)

### Summary
`BouncerConfig::builtin_gas_costs` derives the proving-gas price of each Cairo builtin/opcode from the block-wide proving-gas budget and the builtin's configured per-block instance limit using floor division. When the proving-gas budget is smaller than (or not an exact multiple many times larger than) a builtin's instance limit, the induced cost per instance truncates to zero, exactly analogous to the StUSR bug where `underlyingAmount -> shares` truncation lets a transfer succeed while moving zero value.

### Finding Description
`BuiltinInstanceLimits::induced_gas_costs` computes, for every builtin, `cost = floor(proving_gas / limit)`: [1](#0-0) 
This is wired into `BouncerConfig::builtin_gas_costs`, which feeds `proving_builtin_gas_costs` used throughout `get_tx_weights` to compute `total_proving_gas` (`bouncer_weights.proving_gas`), the dimension that gates whether a transaction can be admitted into the block (`try_update` / `within_max_capacity_or_err`): [2](#0-1) [3](#0-2) 
Because integer division floors toward zero, any builtin whose instance limit is larger than the block's proving-gas capacity (or simply larger than `proving_gas` by more than the ratio needed to keep the quotient ≥ 1) yields a per-instance proving-gas cost of exactly `0`. A transaction that is dominated by usage of that builtin will then contribute `0` to `proving_gas` in `bouncer_weights` regardless of how many instances of the builtin it actually consumes, since `cairo_primitives_to_gas` simply multiplies the (zero) per-unit weight by the count: [4](#0-3) 
This mirrors the StUSR pattern precisely: a rounding-down division used to price a unit of "value" (there, underlying→shares; here, builtin-instance→proving-gas) can degenerate to zero for legitimate non-zero inputs, letting the "transfer" (here, the sender's builtin usage) go through without being charged/tracked, while the surrounding bookkeeping (allowance there; bouncer capacity here) still treats the operation as fully accounted for.

### Impact Explanation
The bouncer's `proving_gas` dimension exists specifically to bound the real proving cost of a block so that the (real) prover can always produce a proof within its resource envelope. If a builtin's induced cost floors to zero, a sender can craft transactions that maximize usage of that particular builtin (up to its VM/step limits) essentially for free from the bouncer's point of view, while the actual Cairo VM/prover work for that builtin is very much non-zero. Because `try_update`/`has_room` never see this cost, the sequencer can keep admitting such transactions into the block well past the proving_gas budget it believes it is respecting. This can cause a block whose *declared* proving-gas usage is within capacity while its *actual* prover workload exceeds it, risking the block becoming unprovable — i.e., a network unable to confirm (produce a proof for and finalize) that block. This is a resource/proving accounting soundness bug reachable purely by an unprivileged transaction sender choosing calldata that maximizes a specific builtin's usage; it is not proposer- or operator-only.

### Likelihood Explanation
Likelihood depends on the concrete `BouncerConfig` values (block proving-gas capacity vs. builtin instance limits) in a given deployment. The default `BuiltinInstanceLimits` values are large (e.g. `range_check: 66_666_666`, `bitwise: 10_500_000`, `keccak: 10_000`), so with a sufficiently constrained `block_max_capacity.proving_gas` (or any config change that lowers it, which is a normal versioned-constants tuning knob, not an attacker action) the ratio `proving_gas / limit` can floor to 0 for one or more builtins. I could not fully verify the exact default numeric value of `block_max_capacity.proving_gas` from the index within the available context, so I cannot state with certainty that the zero-cost condition is hit under the current shipped default config; the code path and truncation defect itself are confirmed, but real-world triggerability with the currently configured constants needs verification against the deployed `versioned_constants` JSON.

### Recommendation
Change `induced_gas_costs` to round up (`ceil`) rather than floor, or explicitly reject/clamp configurations where `proving_gas < limit` for any builtin (as is already done for zero limits via `NonZeroU64`), ensuring every builtin has an induced cost of at least 1 whenever it is enabled, so no builtin can be used to bypass the block's proving-gas accounting.

### Proof of Concept
1. Configure (or observe an existing/future) `BouncerConfig` where `block_max_capacity.proving_gas` is smaller than a given builtin's `builtin_instance_limits` entry (e.g., `range_check` limit `66_666_666` vs. a `proving_gas` capacity below that value, or any other builtin/limit pair with the same ratio property).
2. `BouncerConfig::builtin_gas_costs` → `BuiltinInstanceLimits::induced_gas_costs` computes `derive(limit) = proving_gas.0 / limit.get()`, yielding `0` for that builtin [5](#0-4) 
3. An unprivileged sender submits a transaction (e.g., an `invoke` call to a contract that repeatedly exercises that specific builtin, such as many `range_check`-heavy operations) up to the transaction's own step/gas limits.
4. `get_tx_weights` computes `total_proving_gas` for the transaction via `cairo_primitives_to_gas`, which multiplies the (zero) per-instance weight by the (large) builtin usage count, yielding `0` contribution to `bouncer_weights.proving_gas` [4](#0-3) 
5. `try_update` compares against `block_max_capacity` and finds room, admitting the transaction, even though the real Cairo VM/prover work for that builtin usage is substantial [6](#0-5) 
6. Repeating with more such transactions lets the block's actual proving workload for that builtin grow unbounded while the bouncer's `proving_gas` weight stays at (or near) zero for that component, potentially producing a block that cannot be proven within the prover's resource limits.

impl BuiltinInstanceLimits {
    /// Induces the per-instance proving-gas cost of each Cairo primitive from its per-block
    /// instance limit: `cost = floor(proving_gas / limit)`.
    pub fn induced_gas_costs(&self, proving_gas: GasAmount) -> BuiltinGasCosts {
        let derive = |limit: NonZeroU64| -> u64 { proving_gas.0 / limit.get() };
        BuiltinGasCosts {
            pedersen: derive(self.pedersen),
            range_check: derive(self.range_check),
            range_check96: derive(self.range_check96),
            poseidon: derive(self.poseidon),
            ecdsa: derive(self.ecdsa),
            ecop: derive(self.ecop),
            bitwise: derive(self.bitwise),
            keccak: derive(self.keccak),
            add_mod: derive(self.add_mod),
            mul_mod: derive(self.mul_mod),
            blake: derive(self.blake),
        }
    }

pub fn cairo_primitives_to_gas(
    cairo_primitives_counters: &CairoPrimitiveCounterMap,
    // NOTE: 'blake' is currently the only supported opcode, by being included in the
    // builtin_gas_costs.
    cairo_primitives_gas_costs: &BuiltinGasCosts,
) -> GasAmount {
    let cairo_primitives_gas =
        cairo_primitives_counters.iter().fold(0u64, |accumulated_gas, (name, &count)| {
            let cairo_primitive_weight =
                cairo_primitives_gas_costs.get_cairo_primitive_gas_cost(name).unwrap();
            cairo_primitive_weight
                .checked_mul(u64_from_usize(count))
                .and_then(|builtin_gas| accumulated_gas.checked_add(builtin_gas))
                .unwrap_or_else(|| {
                    panic!(
                        "Overflow while converting cairo primitives counters to gas.\nCairo \
                         primitive: {name:?}, Weight: {cairo_primitive_weight}, Count: {count}, \
                         Accumulated gas: {accumulated_gas}"
                    )
                })
        });

    GasAmount(cairo_primitives_gas)
}
