### Title
Floor-rounding of `anotherTokenQuant` makes `ExchangeInjectActuator` and `ExchangeWithdrawActuator` non-exact inverses, allowing dust-level value leakage on inject/withdraw round trips - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Both `ExchangeInjectActuator` (liquidity add) and `ExchangeWithdrawActuator` (liquidity remove) for TRON's built-in `Exchange`/`ExchangeV2` bancor-style token pools compute the "other side" token quantity by an integer division that always truncates toward zero (floor for positive operands). Because both the inject and the withdraw paths round in the same direction on independently-recomputed pool ratios, a user who injects liquidity and later withdraws the same nominal amount is not guaranteed to receive back exactly what was put in — mirroring the reported `allocate`/`remove` asymmetry in Primitive's `Reserve.sol`.

### Finding Description
When a user injects liquidity via `ExchangeInjectActuator.execute`, the required amount of the paired token is computed with `Math.floorDiv`:

```java
anotherTokenQuant = floorDiv(multiplyExact(
    secondTokenBalance, tokenQuant), firstTokenBalance);
``` [1](#0-0) 

This truncates any fractional remainder down, and the resulting (possibly under-proportional) pair `(tokenQuant, anotherTokenQuant)` is added to `exchangeCapsule`'s balances and deducted from the user's account.

When the pool creator later withdraws liquidity via `ExchangeWithdrawActuator.execute`, the paired amount is again computed via truncating integer division (BigInteger `.divide()` truncates toward zero, identical to floor for the non-negative operands used here):

```java
anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant)
    .divide(bigFirstTokenBalance).longValueExact();
exchangeCapsule.setBalance(subtractExact(firstTokenBalance, tokenQuant),
    subtractExact(secondTokenBalance, anotherTokenQuant));
``` [2](#0-1) 

Because the pool ratio (`secondTokenBalance / firstTokenBalance`) shifts slightly after every inject/trade/withdraw operation, and both operations independently floor-round their computed cross-amount against the *current* ratio at call time, `inject` followed by `withdraw` of the same nominal `tokenQuant` is not guaranteed to be an exact inverse: the user can receive a paired-token amount on withdraw that differs from (typically less than or equal to) what was actually contributed at inject time. This is the same root cause pattern as the reported bug — value is added to reserves with one rounding direction and removed with an independently-rounded computation, so the two operations are not exact inverses of one another, and the discrepancy is consistently biased in the pool's favor since both computations truncate down rather than up.

Unlike `ExchangeTransactionActuator`, which delegates to `ExchangeProcessor`/`SafeExchangeProcessor` (a bonding-curve/log calculation with its own explicit truncation via `RoundingMode.DOWN`) [3](#0-2) , `Inject`/`Withdraw` use simple linear-ratio truncating division, making the asymmetry deterministic and directly attributable to the two independent floor-roundings.

### Impact Explanation
The impact is bounded dust-level value loss (at most a few base units per operation, scaling with token quantities and pool ratio drift), not fund-draining or protocol-halting. It matches the Low severity of the original finding: any account that both creates an `Exchange` pool and calls `ExchangeInjectActuator`/`ExchangeWithdrawActuator` on it can lose small fractions of tokens due to the rounding mismatch between the two paths, without any protocol-level accounting invariant enforcing exact reversibility. This is an accounting/rounding correctness issue rather than a critical exploit, since `ExchangeWithdrawActuator` is restricted to the pool creator, but pool creation itself is available to any unprivileged account [4](#0-3) .

### Likelihood Explanation
Likelihood is high in the sense that the rounding mismatch is deterministic and triggers on essentially every inject/withdraw pair where the pool ratio does not divide evenly (the common case for real-valued liquidity ratios), but the resulting per-operation impact is tiny, so exploitation for meaningful profit would require repeated operations or specially crafted balances, similar to the Echidna-discovered scenario in the original report.

### Recommendation
- Short term: Document that `ExchangeInjectActuator` and `ExchangeWithdrawActuator` are not guaranteed to be exact inverses due to independent floor-rounding of the cross-token amount, and consider adding a tolerance/precision check (similar to the existing "Not precise enough" check already present in `ExchangeWithdrawActuator.doValidate`) [5](#0-4)  to `ExchangeInjectActuator` as well, so both directions share a consistent rounding/precision policy.
- Long term: Formally test (e.g., with property-based/fuzz testing) that sequences of `inject` followed by `withdraw` of the same nominal amount preserve balances within an explicitly documented and minimized delta, and consider using a rounding scheme (e.g., round-to-nearest or always-round-in-user's-favor with a fixed dust sink) that minimizes systematic bias toward the pool.

### Proof of Concept
1. Create an `Exchange` pool with `firstTokenBalance = A0`, `secondTokenBalance = B0` such that `B0/A0` is not an integer ratio (e.g., `A0=107`, `B0=108` after a prior inject).
2. As the pool creator, call `ExchangeInjectActuator` with `tokenQuant = Q` for `firstTokenID`; observe `anotherTokenQuant = floorDiv(B0*Q, A0)` computed at `ExchangeInjectActuator.java:73-74`.
3. Immediately call `ExchangeWithdrawActuator` with the same `tokenQuant = Q` for `firstTokenID`; observe the recomputed `anotherTokenQuant = (B0+injectedAnother)*Q / (A0+Q)` (truncating) at `ExchangeWithdrawActuator.java:79-80`.
4. Compare the second `anotherTokenQuant` to the first: for ratios where `B0*Q/A0` is not exactly integral, repeated tests across a range of `(A0, B0, Q)` will show cases where the withdrawn paired-token amount differs from the injected paired-token amount, demonstrating that `inject` and `withdraw` are not exact inverses.
