### Title
Wallet Contract accepts named NEAR accounts as if they were ETH-implicit targets due to a prefix-only address check - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs])

### Summary
`extract_address` in the NEAR Wallet Contract validates a target `AccountId` as an ETH-implicit account by checking only that it *starts with* `0x` followed by 40 hex characters, without requiring the account id to actually be 42 characters long. This is the same class of bug as the reported NextChat CVE: a structural/hostname-style check is replaced with a prefix/substring check. A relayer can exploit this to make the contract treat an ordinary, attacker-chosen named NEAR account as though it were the ETH-implicit account the user actually signed for in their RLP-encoded transaction, redirecting a `Transfer` action to a different receiver than the one cryptographically authorized by the wallet owner.

### Finding Description
`extract_address` only bounds-checks the first 42 bytes of the account id string: [1](#0-0) 

The comment explicitly acknowledges that in a non-production/testing context the account id "will be longer than 42 characters" and the function still returns `Ok(address)` in that case — i.e., it never verifies `hex_str.len() == 42`, only `>= 42`.

This loosely-validated address is then used by `parse_target` to classify an attacker-supplied `target: AccountId` argument (a caller-controlled parameter of `rlp_execute`, not part of the signed Ethereum payload) as `TargetKind::EthImplicit(address)`: [2](#0-1) 

`validate_tx_relayer_data` then confirms the classification using a full-string equality against `format!("0x{address}{suffix}")`, where the `suffix` is derived from the *current* wallet contract account only: [3](#0-2) [4](#0-3) 

Because the address portion of `target` is attacker-chosen (it just needs to match the first 42 characters), a relayer can name a real, ordinary NEAR account (e.g. `0x<40 arbitrary hex chars><current_account_suffix>`, a normal sub-account they control) so that it satisfies both the address-prefix match against the signed transaction's `to` field and the exact-string reconstruction check. This makes the contract believe the relayer's chosen named account *is* the ETH-implicit address the user's signed Ethereum transaction targeted, when in fact it is a completely different (and independently controlled) NEAR account.

When this classification is reached, `inner_rlp_execute`/`prepare_action` (the caller of `validate_tx_relayer_data`) downgrades the parsed action into a plain `Transfer` to `target`: [5](#0-4) 

Instead of aborting the transaction, the wallet forwards the deposit/transfer to whatever account the relayer designated as `target`, rather than the address the user's signature actually authorized.

### Impact Explanation
This allows a malicious relayer submitting `rlp_execute` calls on behalf of a wallet-contract user to redirect a `Transfer` (funded by the user's prepaid NEAR value in the eth transaction) to a NEAR account of the relayer's choosing, rather than the account genuinely encoded and cryptographically signed for by the wallet owner in the Ethereum-style transaction. This is unauthorized value movement: user funds attached to a signed eth transaction can be diverted to an account the user never intended nor signed for, purely because of the loose length validation in `extract_address`.

### Likelihood Explanation
The `rlp_execute` entry point is a normal, unprivileged public contract method — any account (acting as "relayer") can call it, supplying an arbitrary `target: AccountId`. Only crafting a suitable named account whose first 42 characters match a chosen 20-byte address, and whose suffix matches the current wallet's suffix, is required; NEAR account creation is permissionless subject to normal account-id rules (documented account id max length is 64, easily fitting `0x` + 40 hex + a short suffix such as `.testnet`/`.near`). This is directly reachable from a single submitted contract call.

### Recommendation
In `extract_address`, require the input to be *exactly* 42 bytes (`0x` + 40 hex chars) rather than merely `>= 42`, i.e., reject any account id whose length differs from 42, removing the "sub-account for testing" allowance from the production code path (or gate it behind an explicit test-only feature flag that cannot be reached from `rlp_execute` in a production deployment). Ensure `parse_target`/`validate_tx_relayer_data` cannot classify a differently-lengthed named account as `EthImplicit`/`CurrentAccount`.

### Proof of Concept
1. Wallet contract W is deployed at ETH-implicit account `0xCCCC...CCCC` (42 chars), with suffix `""` in production, but for illustration assume a deployment at `0xCCCC...CCCC.testnet` (suffix `.testnet`), matching the codebase's own documented testing scenario.
2. Wallet owner signs an Ethereum-style transaction with `to = 0xAAAA...AAAA` intending to send value to the real ETH-implicit account `0xAAAA...AAAA`.
3. Malicious relayer, instead of calling `rlp_execute(target="0xAAAA...AAAA", tx_bytes_b64=...)`, calls it with `target = "0xAAAA...AAAA.testnet"` — a normal named NEAR sub-account of `testnet` that the relayer independently owns/created.
4. `extract_address("0xAAAA...AAAA.testnet")` succeeds (only checks first 42 chars) → `parse_target` returns `TargetKind::EthImplicit(0xAAAA...AAAA)`.
5. `validate_tx_relayer_data` computes `format!("0x{}{}", hex(0xAAAA...AAAA), context.current_account_suffix())` = `"0xAAAA...AAAA.testnet"`, which equals `target.as_str()` exactly → validation passes.
6. The contract executes `Transfer { receiver_id: "0xAAAA...AAAA.testnet", yocto_near: <tx.value> }`, sending the user's funds to the relayer-controlled named account instead of the real `0xAAAA...AAAA` implicit account the user signed for.

Note: this analysis relies on `current_account_suffix()` and the surrounding validation logic exactly as shown above; I was not able to execute the wallet-contract test suite to empirically confirm end-to-end behavior, so this should be validated with a live/test-loop run of `rlp_execute` before treating it as fully confirmed.

/// Extracts a 20-byte address from a Near account ID.
/// This is done by assuming the account ID is of the form `^0x[0-9a-f]{40}`,
/// i.e. it starts with `0x` and then hex-encoded 20 bytes.
pub fn extract_address(current_account_id: &AccountId) -> Result<Address, Error> {
    let hex_str = current_account_id.as_bytes();

    // The length must be at least 42 characters because it begins with
    // `0x` and then a 20-byte hex-encoded string. In production it will
    // be exactly 42 characters because eth-implicit accounts will always
    // be top-level, but for testing we may have them be sub-accounts.
    // In this case then the length will be longer than 42 characters.
    if hex_str.len() < 42 {
        return Err(Error::AccountId(AccountIdError::AccountIdTooShort));
    }

    if &hex_str[0..2] != b"0x" {
        return Err(Error::AccountId(AccountIdError::Missing0xPrefix));
    }

    let mut bytes = [0u8; 20];
    hex::decode_to_slice(&hex_str[2..42], &mut bytes)
        .map_err(|_| Error::AccountId(AccountIdError::InvalidHex))?;

    Ok(bytes.into())
}

fn parse_target(target: &AccountId, current_address: Address) -> TargetKind<'_> {
    match extract_address(target) {
        Ok(address) => {
            if address == current_address {
                TargetKind::CurrentAccount
            } else {
                TargetKind::EthImplicit(address)
            }
        }
        Err(_) => TargetKind::OtherNearAccount(target),
    }
}

/// Validates the transaction is following the Wallet Contract protocol.
/// This includes checks for:
/// - from address matches current account address
/// - to address is present and matches the target address (or hash of target account ID)
/// - nonce matches expected nonce
/// If this validation fails then the relayer that sent it is faulty and should be banned.
fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }
