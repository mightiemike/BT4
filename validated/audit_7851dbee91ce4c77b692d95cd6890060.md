Found it. `BuildOutboundsFromReceipt` in `x/uexecutor/keeper/create_outbound.go` decodes an `UniversalTxOutboundEvent` emitted by the `UNIVERSAL_GATEWAY_PC` contract and builds an `OutboundTx` with `Amount: event.Amount.String()` and `GasFee`/`GasLimit`/`GasPrice` taken directly from the event, with **no check that `event.Amount` (or the gas fields) is non-zero** before it is queued into `PendingOutbounds` and requires UV/TSS signing and broadcast on the destination chain. [1](#0-0) 

This is reachable by an unprivileged attacker: any address can call the gasless `MsgExecutePayload` message (no Cosmos fee is charged, and the signer need not equal the UEA owner is fine since attackers use their own UEA) to invoke their own UEA's `executeUniversalTx`/gateway withdraw path with `amount = 0`, causing the EVM Gateway contract to emit a `UniversalTxOutbound` event with zero amount, which then flows unchecked into an `OutboundTx` and is written to `PendingOutbounds`: [2](#0-1) 

Each such record requires the Universal Validators to sign the outbound via TSS and broadcast it, and to vote back with `MsgVoteOutbound`, per the documented lifecycle in the module README [3](#0-2) . Since `MsgExecutePayload` is in the gasless allowlist, the attacker pays no Cosmos fee for repeatedly triggering this [4](#0-3) .

By contrast, the inbound path (`Inbound.ValidateForExecution`) explicitly guards against zero-amount for `FUNDS`/`GAS` tx types and only special-cases `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` to skip deposit while still executing payload — this is a deliberate, well-tested design choice, not a vulnerability [5](#0-4) . No equivalent amount-positivity check exists on the outbound-creation path from `BuildOutboundsFromReceipt`.

I could not fully confirm from the indexed code whether the on-chain `UNIVERSAL_GATEWAY_PC` Solidity contract itself already rejects zero-amount withdraw calls before emitting the event (that contract lives outside this repo's scope, referenced only via ABI/event signature). Given this uncertainty about whether the Solidity-side gateway enforces `amount > 0` before emitting `UniversalTxOutbound`, I cannot assert a confirmed exploitable gap in the scoped Go code alone — the Go keeper code trusts the event verbatim without its own defense-in-depth check.

### Title
Zero-amount UniversalTxOutbound events are accepted into `PendingOutbounds` without value validation, enabling free spam of UV/TSS signing work - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`BuildOutboundsFromReceipt` decodes `UniversalTxOutboundEvent` logs emitted by the Universal Gateway contract and constructs `OutboundTx` records without validating that `event.Amount` (or gas fields) is greater than zero, mirroring the "withdrawal with zero amount" bug class: an unprivileged, gasless caller can trigger UV TSS-signing and broadcast workload for outbounds carrying no economic value.

### Finding Description
`BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:16-105`) iterates gateway logs, decodes them via `DecodeUniversalTxOutboundFromLog`, and constructs an `OutboundTx` directly from decoded fields, with `Amount: event.Amount.String()`. There is no `event.Amount.Sign() > 0` (or similar) check anywhere in this function, unlike the inbound path where `Inbound.ValidateForExecution` explicitly enforces `amount must be positive for this tx type` for `FUNDS`/`GAS` tx types. The resulting `OutboundTx` is attached via `attachOutboundsToUtx`, which unconditionally writes an entry into `PendingOutbounds` and emits an `OutboundCreatedEvent`, triggering the UV/TSS signing + broadcast lifecycle documented in the module README, regardless of amount.

An attacker can reach this path for free: `MsgExecutePayload` is on the gasless allowlist (`app/txpolicy/gasless.go`), so submitting a payload that calls the attacker's own UEA to invoke a Gateway withdraw-style function with `amount = 0` costs no Cosmos fee. If the EVM Gateway contract does not itself reject zero-amount withdrawals (unconfirmed — contract source is outside this repo), each such call becomes a queued `PENDING` outbound requiring real UV/TSS signing and destination-chain broadcast work.

### Impact Explanation
Unbounded, cost-free creation of `PendingOutbounds` entries forces Universal Validators to perform real TSS signing ceremonies and destination-chain broadcasts for economically meaningless transfers. This is a denial-of-service vector against UV/TSS coordination resources reachable purely through an ordinary user's own gasless transaction submission, without any privileged access — matching the "denial of service...reachable without privileged control" allowed-impact category.

### Likelihood Explanation
Likelihood depends entirely on whether the external Solidity Gateway contract already enforces a positive-amount check before emitting `UniversalTxOutbound`. If it does, this Go-side gap is defense-in-depth-only and not independently exploitable. If it does not (which cannot be confirmed from this repository's scope), the path is trivially and repeatedly reachable by any unprivileged address at zero fee cost via the gasless `MsgExecutePayload` allowlist.

### Recommendation
Add an explicit `event.Amount.Sign() > 0` (or type-appropriate minimum) check inside `BuildOutboundsFromReceipt` before constructing an `OutboundTx` for `FUNDS`/`GAS`-style withdraw events, mirroring the guard already present in `Inbound.ValidateForExecution`, so that zero-amount outbound requests are rejected on the Push Chain side even if the Gateway contract's own validation is ever bypassed, weakened, or upgraded incorrectly.

### Proof of Concept
1. Attacker deploys/owns a UEA and funds it with a trivial or zero PRC20 balance.
2. Attacker submits `MsgExecutePayload` (gasless, no Cosmos fee) with a `UniversalPayload` whose `Data` calls the Gateway's withdraw-style function with `amount = 0`.
3. `ExecutePayload` → `CallUEAExecutePayload` executes the payload on-chain; if the Gateway contract does not itself reject zero amounts, it emits `UniversalTxOutbound` with `amount = 0`.
4. `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt` decodes the event and builds an `OutboundTx` with `Amount: "0"` with no rejection.
5. `attachOutboundsToUtx` writes the zero-amount outbound into `PendingOutbounds`, triggering UV TSS-signing/broadcast workload.
6. Attacker repeats step 2 indefinitely at zero Cosmos-side cost.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}
