## Analog Found: Global-Contract owner can permanently brick every deterministic account bound to it

### Title
Owner of an `AccountId`-mode Global Contract can permanently freeze all funds of every deterministic (`0s…`) account referencing it - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
NEAR's Global Contracts feature lets any unprivileged account deploy a contract under `GlobalContractDeployMode::AccountId`, which is explicitly mutable and can be redeployed at will by its owner [1](#0-0) . Deterministic accounts (NEP-616, `0s…` ids) are created by pinning their code to a `GlobalContractIdentifier` via `DeterministicStateInitAction`, and — unlike ordinary accounts — they can never obtain an access key or reclaim `actor_id` on themselves [2](#0-1) . This mirrors H-6 exactly: a permissionless "deployer" (the global-contract owner) can retroactively swap in code that makes every call revert, and the affected party (anyone who created a deterministic account pointing at that owner's `AccountId` identifier) has no recourse — including no way to move out even their raw NEAR balance.

### Finding Description
1. Anyone can deploy a global contract under `GlobalContractDeployMode::AccountId`, whose entire purpose is "This allows the owner to update the contract for all its users" [3](#0-2) . Redeployment overwrites the same trie slot (`TrieKey::GlobalContractCode { identifier }`) that all referencing accounts read from [4](#0-3) .
2. Anyone can create a deterministic account (`0s…`) via `DeterministicStateInitAction`, whose state-init payload only carries `code: GlobalContractIdentifier` and `data`, with no access-key field at all [5](#0-4) . The `code` is explicitly allowed to be the mutable `AccountId` variant, as used throughout the test suite [6](#0-5) .
3. `create_deterministic_account` deliberately does **not** set `actor_id` to the new account — it stays the predecessor "to prevent hijacking the account... preventing `AddKey`, `DeployContract`, or any other actions that only the account owner is permitted to do" [7](#0-6) .
4. `check_actor_permissions` enforces `actor_id == account_id` for exactly the actions that would let an account escape a bad global contract or move funds out unilaterally: `DeployContract`, `AddKey`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, `DeleteAccount` [8](#0-7) .
5. Because a deterministic account never has (and can never obtain) an access key, no transaction can ever be signed "as" it, so `actor_id` can never equal that account's id. Every one of those owner-only recovery actions is therefore permanently unreachable for a `0s…` account, no matter what the referenced global contract does to it.

### Impact Explanation
If a `0s…` deterministic account is created pointing at `GlobalContractIdentifier::AccountId(owner)` (as opposed to the immutable `CodeHash` form), the `owner` can, at any later time, redeploy new code to that same identifier via another `DeployGlobalContractAction` in `AccountId` mode. If the new code always traps/reverts on every method, then:
- Every `FunctionCall` receipt into the deterministic account fails forever, so any value tracked in the account's own `ContractData` storage (deposits, balances, LP shares, etc., seeded via the `data` field at creation) becomes permanently unreachable.
- The raw NEAR balance is equally frozen: `Transfer`-out, `DeleteAccount`, and `AddKey` all require `actor_id == account_id` per `check_actor_permissions`, which — as shown above — a `0s…` account can never satisfy. The only path by which NEAR can ever leave such an account is a `Promise::Transfer` issued from *inside* a successful execution of its own (global) contract code, which is exactly what the malicious redeploy breaks.
- This is a complete, irreversible freeze of 100% of the account's funds, matching the "permanently frozen funds" impact category and structurally identical to H-6 (pool deployer bricking `interestRateStrategy` to freeze vault-depositor withdrawals) — except here the victim has *even less* recourse than a Sherlock vault manager, since a named NEAR account can at least redeploy its own local contract to recover, whereas a deterministic account fundamentally cannot.

### Likelihood Explanation
Every step is reachable by an ordinary, unprivileged transaction signer using only documented, permissionless actions (`DeployGlobalContractAction`, `DeterministicStateInitAction`), with no validator/network/operator privilege required. The only "trust" step is that some other actor chooses to create a deterministic account referencing an `AccountId`-mode identifier owned by a third party — exactly the same voluntary-trust precondition Sherlock ruled sufficient for High severity in H-6 (a vault manager choosing to onboard a pool). Given that global contracts are a new, permissionless primitive intended to be reused by many unrelated protocols/wallets, and that `AccountId` mode is explicitly advertised as the "updatable" mode (as opposed to `CodeHash`), integrators are likely to use it for legitimate upgradeability — unaware that doing so for deterministic accounts removes all future recovery options.

### Recommendation
- Disallow (or require an explicit opt-in warning host-function/flag for) using `GlobalContractIdentifier::AccountId` as the `code` for `DeterministicStateInitAction`/`UniversalStateInit`-style zero-key accounts; restrict deterministic accounts to the immutable `CodeHash` identifier so their behavior cannot change out from under them.
- Alternatively, provide a protocol-level recovery path for deterministic accounts (e.g., a governance/timelocked mechanism, or a self-contained "escape hatch" receipt type) that does not depend on the contract code itself still functioning.
- At minimum, document prominently that any account (deterministic or otherwise) referencing an `AccountId`-mode global contract inherits full, continuous trust in that owner for the account's entire remaining lifetime, with no way to unwind for deterministic accounts specifically.

### Proof of Concept
1. Attacker `evil.near` deploys a benign-looking global contract in `AccountId` mode: `DeployGlobalContractAction { code: good_wasm, deploy_mode: AccountId }`, signed by `evil.near`.
2. A relayer/wallet creates deterministic account `0s…` via `DeterministicStateInitAction { state_init: V1 { code: GlobalContractIdentifier::AccountId("evil.near"), data: {...} }, deposit }`, funding it with NEAR and internal balances in `data`.
3. Users interact normally; funds/state accumulate on `0s…`.
4. `evil.near` submits a second `DeployGlobalContractAction { code: always_panics_wasm, deploy_mode: AccountId }`. Per `apply_distribution_current_shard`, this overwrites the same `TrieKey::GlobalContractCode` slot referenced by `0s…` [9](#0-8) .
5. Any subsequent `FunctionCall` to `0s…` now fails deterministically. Because `0s…` has no access key (`check_actor_permissions` blocks `AddKey`/`DeployContract`/`UseGlobalContract`/`DeleteAccount` for `actor_id != account_id` [10](#0-9) ), there is no transaction anyone can sign to add a key, redeploy locally, point at a different contract, or delete the account — the funds are permanently frozen.

```rust
        state_update.record_global_contract_deploy(ContractCode::new(
            global_contract_data.code().to_vec(),
            code_hash,
```

```rust
pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) | Action::UniversalStateInit(_) => (),
    };
    Ok(())
}
```
