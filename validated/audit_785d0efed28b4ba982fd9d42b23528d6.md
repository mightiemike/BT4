### Title
Stale `last-update` Timestamp Causes First Post-Idle Interest Accrual To Be Inflated By The Entire Idle Period - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vaults `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
`last-update` is only advanced when the interest index actually changes, not on every call to `accrue`. Whenever the vault has zero outstanding debt (so utilization and the borrow rate are both `u0`), the index cannot change, so `last-update` is silently left pointing at a stale timestamp — potentially the deployment time. As soon as debt is introduced again, the next `accrue` call measures `time-delta` from that stale timestamp to `stacks-block-time`, applying the *current* (now non-zero) interest rate over the whole idle interval as if debt had existed the entire time. This is the same "clock/anchor not reset when the state it depends on changes" bug class as the referenced report, just applied to the interest-index clock instead of a management-fee clock.

### Finding Description
The relevant timestamp variable is declared as: [1](#0-0) 

`next-index` / `next-liquidity-index` compute the multiplier from `time-delta = stacks-block-time - (var-get last-update)`: [2](#0-1) 

`accrue` only writes `last-update` when the index actually moved: [3](#0-2) 

`calc-utilization` returns `u0` whenever there is no outstanding debt, which drives the borrow rate to `u0` and therefore keeps the multiplier at `INDEX-PRECISION` (no change) in `calc-multiplier-delta`: [4](#0-3) 

Sequence:
1. Vault is deployed (or fully repaid down to zero debt). `last-update` is set to `stacks-block-time` at that point, and `principal-scaled` is `u0`, so `utilization = u0` and the interest `rate = u0`.
2. Time passes — deposits/redeems/borrow-attempts may call `accrue`, but since `rate = u0`, `next-index`/`next-liquidity-index` always return the unchanged current index, so the `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)` branch never fires. `last-update` stays frozen at the old timestamp indefinitely.
3. `system-borrow` is finally called, which invokes `accrue` first (still with zero prior debt, so still a no-op for `last-update`) and then sets `principal-scaled` to a positive value: [5](#0-4) 
4. On the very next call to `accrue` (from any deposit/redeem/borrow/repay), utilization is now non-zero, so `rate > u0`. `time-delta` is computed as `stacks-block-time - last-update`, which spans the entire idle period from step 1 through step 3/4 — not just the time since the debt was actually created.
5. `calc-multiplier-delta` applies this inflated `time-delta` to the current rate, producing an inflated `index`/`lindex` jump. `debt-delta` in `accrue` is computed from this jump and used to mint `treasury-lp` shares to `.dao-treasury`, diluting all other shareholders, and it inflates `total-assets`/`total-debt` figures that back share pricing.

### Impact Explanation
The fictitious debt/interest growth is not backed by any real economic activity (no debt existed for most of the measured interval), yet it is treated as real accrued interest: it increases `total-assets-preview`/`total-assets` (and thus the redeemable value per share) and mints real `treasury-lp` tokens to `.dao-treasury` via `ft-mint?`. This diverts unclaimed yield from depositors to the treasury based on a phantom time window, and can inflate the vault's reported NAV beyond what the real underlying token balance can support, creating a temporary funds-freezing/insolvency risk for later redeemers when the gap between inflated share price and real backing is realized. This lands in the in-scope **High** impact class — theft of unclaimed yield / temporary freezing of funds.

### Likelihood Explanation
This does not require any privileged access, oracle manipulation, or two colluding/competing users — it is a natural consequence of normal vault lifecycle (deploy → idle with zero utilization → first borrow after idle period, or fully repaid → idle → new borrow). Any vault that experiences a period of zero outstanding debt (common right after deployment, or after all borrowers repay) will hit this on the very next borrow.

### Recommendation
Update `last-update` unconditionally on every `accrue` call (or whenever `stacks-block-time` differs from the stored value), not only when the index numerically changes, so that idle periods with a zero rate don't leave the clock anchored to a stale timestamp. Alternatively, when utilization/rate is zero, still refresh `last-update` to the current `stacks-block-time` even though the multiplier is `INDEX-PRECISION`, mirroring the fix recommended in the referenced report (initialize/refresh the time anchor rather than letting it silently go stale).

### Proof of Concept
1. Deploy `v0-vault-usdc` (or any of the sibling vaults). `last-update = T0` (deploy time), `principal-scaled = u0`.
2. Let a long period elapse with no borrows (utilization stays `u0`); any deposits/redeems that call `accrue` leave `last-update` at `T0` because `rate = u0` keeps `idx`/`lindex` unchanged (`mainnet/contracts/vault/v0-vault-usdc.clar:379-390`, `837-864`).
3. At time `T1 = T0 + N` (large `N`), call `system-borrow` to create debt. `accrue` inside this call still sees `rate = u0` (pre-borrow state) so `last-update` remains `T0`.
4. Immediately after, call `accrue` again (e.g., via a deposit). Utilization is now non-zero, so `rate > 0`, and `time-delta = T1 - T0 ≈ N` is used in `calc-multiplier-delta`, producing an interest jump proportional to `N` even though the debt has existed for only an instant.
5. Observe `debt-delta`, `reserve-inc`, and `treasury-lp` minted in this single `accrue` call are disproportionately large relative to the real elapsed borrowing time, diluting existing shareholders and inflating `total-assets`.
