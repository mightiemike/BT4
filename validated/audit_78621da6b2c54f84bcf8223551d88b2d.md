## Finding: Attached deposits are permanently frozen in the NEAR wallet contract when `address_check_callback` / `nep_141_storage_balance_callback` fail before reaching `rlp_execute_callback`

### Title
Attached NEAR deposits are permanently lost in `WalletContract` when intermediate promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`) short-circuit with an error - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is `#[payable]`, so any NEAR tokens an external caller attaches are credited to the wallet contract's balance immediately upon receipt [1](#0-0) . The contract tracks this via `CallerDeposit`, created only for non-self (external) callers, with the explicit purpose of refunding it if the downstream cross-contract call fails [2](#0-1) . This refund is correctly performed in `rlp_execute_callback` when the *final* promise fails [3](#0-2) .

However, for two intermediate transaction kinds (`EOABaseTokenTransfer` with an address check, and `ERC20Transfer`), execution goes through extra callbacks — `address_check_callback` and `nep_141_storage_balance_callback` — before reaching `rlp_execute_callback`. Several early-return error branches inside these callbacks receive `caller_deposit: Option<CallerDeposit>` as a parameter but drop it on the floor without issuing any refund promise:

- Registrar lookup failed: [4](#0-3) 
- Unexpected response from registrar: [5](#0-4) 
- Target resolves to an existing named account and the top-level tx signer is not the wallet itself ("Invalid target" error): [6](#0-5) 

The `nep_141_storage_balance_callback` has the analogous problem for its own failure/parse-error branches.

### Finding Description
This is structurally the same bug class as the Derby `pushVaultAmounts`/`sendFundsToVault` issue: value is attached to a call, and a conditional branch that decides not to forward/consume that value fails to return it, leaving it stuck on the receiving contract's balance forever. Here, the "value attached to a call" is the NEAR deposit an external (non-self) caller attaches to `rlp_execute`, and the "conditional branch that doesn't use it" is any of the early-return error paths in `address_check_callback`/`nep_141_storage_balance_callback` that construct an `ExecuteResponse` directly instead of forwarding to `rlp_execute_callback` (the only place that actually issues the `promise_batch_action_transfer` refund) [7](#0-6) .

Root cause: `caller_deposit` is threaded through as a plain function parameter that is only *consumed* in the success path that continues on to `rlp_execute_callback` [8](#0-7) ; every other branch in these two callbacks simply returns `PromiseOrValue::Value(...)` without ever using `caller_deposit`, so the deposit remains on `WalletContract`'s balance with no code path left to move it out.

### Impact Explanation
Any external, unprivileged caller (a "relayer" using a function-call access key, or any account calling `rlp_execute` directly) who attaches NEAR tokens to cover an `EOABaseTokenTransfer` (to an address requiring an address-registrar lookup) or an `ERC20Transfer` (requiring an NEP-141 storage-balance check) can have those tokens permanently frozen inside the wallet contract if:
- the address registrar call fails or returns an unexpected response, or
- the target address resolves to an existing named account and the transaction was submitted by a relayer using a function-call access key (not the wallet's own full-access key), or
- the NEP-141 `storage_balance_of` call fails or returns an unparseable response.

None of these conditions require a malicious node, validator, or operator — they are reachable purely by network hiccups, a misbehaving/rug-pulled registrar or token contract, or normal relayer usage patterns, all triggerable by an ordinary transaction. This is a concrete, unauthorized permanent loss of funds for the external caller.

### Likelihood Explanation
Medium-to-high: these are not edge cases requiring adversarial coordination — a temporary failure of the address-registrar or token contract's cross-contract call (e.g. due to gas exhaustion, congestion, or the target contract simply not implementing the expected interface) is a realistic, commonly occurring condition, and the "invalid target" branch is hit whenever a relayer (using a function-call key) submits a transaction whose `target` turns out to already be a named account — a state the relayer cannot always know in advance without querying the registrar itself.

### Recommendation
In every early-return branch of `address_check_callback` and `nep_141_storage_balance_callback` that does not forward to `rlp_execute_callback`, issue the same refund-to-caller promise (`env::promise_batch_create` + `env::promise_batch_action_transfer`) that `rlp_execute_callback`'s `PromiseResult::Failed` arm performs whenever `caller_deposit` is `Some`, before returning the `ExecuteResponse`.

### Proof of Concept
1. External account `alice` (not the wallet contract itself) calls `rlp_execute` on `WalletContract` with an RLP-encoded ETH transaction representing an `EOABaseTokenTransfer` to an address requiring an address-registrar lookup, attaching a NEAR deposit `D` (`#[payable]` entry point) [1](#0-0) .
2. `D` is credited to `WalletContract`'s balance as part of normal NEAR receipt processing (the attached deposit is deposited before contract execution starts, per the protocol's Economics API) — see the general refund semantics documented in `docs/RuntimeSpec/Refunds.md`.
3. `inner_rlp_execute` computes `caller_deposit = CallerDeposit::new(&context)` = `Some(CallerDeposit { account_id: alice, yocto_near: D })` since predecessor != current account [9](#0-8) , and schedules a call to the address registrar followed by `address_check_callback` [10](#0-9) .
4. If the registrar cross-contract call fails (`PromiseResult::Failed`), `address_check_callback` returns an `ExecuteResponse{success:false,...}` directly, never touching `caller_deposit` [4](#0-3) .
5. `D` remains on `WalletContract`'s balance permanently; there is no subsequent code path that refunds `alice`. [11](#0-10)

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
