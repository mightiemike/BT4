### Title
Stale-price commission classification allows validator to bypass burn/incinerator redirection during reward distribution - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
The FPS mint/redeem bug is a class of vulnerability where an amount is computed from mutable shared state at time T1, then applied/settled against that same mutable state at a later time T2, with no bound/tolerance check to detect that the state moved between T1 and T2. `load_and_reward_commission_accounts` reproduces this exact pattern for validator commission distribution: the *type classification* of a commission collector account (`SystemAccount` vs `Incinerator`) is derived from the account's `pre_lamports` balance read fresh at distribution time (T2), while the `commission_lamports` amount being credited was fixed earlier during `calculate_stake_rewards_and_commissions` (T1), based on the account state and stake weights of that time. Between T1 and T2, the account balance can be legitimately mutated (as the code's own comment states: "intervening account mutations, e.g. VAT burns in `update_epoch_stakes`"), with no re-validation that the fixed `commission_lamports` amount is still consistent with the account's role/eligibility.

### Finding Description
`load_and_reward_commission_accounts` at [1](#0-0)  is explicitly documented as "the single point where commission account data is fetched, ensuring we always see the latest balances — including any intervening account mutations (e.g. VAT burns in `update_epoch_stakes`) that happen between calculation and distribution."

The flow is:
1. `commission_lamports` for each commission collector pubkey is computed once during `calculate_stake_rewards_and_commissions` / `redeem_delegation_rewards`, using the vote/stake state and `PointValue` current at calculation time [2](#0-1) .
2. At a later point (distribution), `load_and_reward_commission_accounts` loads the *current* on-chain balance of the commission account with `get_account_with_fixed_root_no_cache`, captures `pre_lamports` from that fresh read, and credits the previously-fixed `commission_lamports` onto it [3](#0-2) .
3. `pre_lamports` (the freshly-read, potentially manipulated balance) is then used to classify the collector via `collector_type_checked` — determining whether the recipient is treated as an ordinary `SystemAccount` or redirected to the `Incinerator` [4](#0-3) .

Because `pre_lamports` is read at T2 rather than at T1 (when `commission_lamports` was computed and the collector's eligibility/type was implicitly assumed), any lamport-balance-changing event that occurs on the commission account between T1 and T2 (the code itself names `update_epoch_stakes`'s VAT burn as one such event) changes the classification input without re-deriving or bounding the `commission_lamports` amount against the new state. This is structurally identical to the Equity FPS bug: an amount computed against reserve/supply at T1 is settled against reserve/supply at T2, and no min/max tolerance check exists to detect or reject the drift. Here the "reserve" is the commission account's lamport balance and the settlement decision (Incinerator redirection vs. normal credit) is coupled to a value that is guaranteed—by design and by this code's own comment—to be able to change between calculation and settlement.

### Impact Explanation
Depending on how a commission account's balance is set at T1 vs. T2 relative to the `Rent::minimum_balance` / reserved-key thresholds checked in `collector_type_checked`, this stale-vs-fresh mismatch can flip the fate of `commission_lamports`:
- Rewards intended for the validator/collector could be silently redirected to the Incinerator (burned) instead of credited, or
- Rewards that should have been burned due to a rent-exempt-violating account (as observed at commission-calculation time) could instead be delivered normally, because the account's balance was topped up before `load_and_reward_commission_accounts` runs.

Either direction constitutes a silent, protocol-level balance/capitalization divergence: lamports move (or fail to move) to unintended destinations without an explicit error, transaction, or on-chain event describing the discrepancy, which is exactly the "silent balance change" / "capitalization divergence" class called out as in-scope.

### Likelihood Explanation
The trigger condition — an account-balance-mutating event landing between the moment `commission_lamports`/collector eligibility is computed and the moment `load_and_reward_commission_accounts` reads the account — is not a rare race window requiring adversarial timing tricks; the code comment identifies a known, scheduled intra-protocol event (`update_epoch_stakes`'s VAT burn) that occurs in this exact window on every affected epoch boundary. This makes the condition a normal, expected occurrence within the reward-distribution pipeline rather than a hypothetical or purely theoretical race, meeting the bar of a concretely reachable path.

### Recommendation
Do not use a value read at distribution time (`pre_lamports`) to re-derive collector classification for an amount that was fixed at an earlier calculation time. Either:
1. Snapshot and carry forward the classification-relevant account state (balance, rent-exemption/eligibility) from the same point where `commission_lamports` was computed, and use *that* frozen state for `collector_type_checked`, or
2. If using the fresh balance is intentional (to always reflect final chain state), re-validate that the computed `commission_lamports` is still consistent with the *current* classification and bound/clamp the outcome (analogous to slippage-limit `minOut` parameters) rather than letting an intervening mutation silently flip whether funds are burned or delivered.

### Proof of Concept
1. At epoch-reward calculation time (T1), a validator's commission collector account balance and vote-account state yield a non-trivial `commission_lamports` for that epoch (via `redeem_delegation_rewards` → `calculate_stake_rewards_and_commissions`, [2](#0-1) ).
2. Before `load_and_reward_commission_accounts` executes for distribution (T2), the collector account's balance changes due to an intervening event in the same window explicitly named in the code — the VAT burn performed in `update_epoch_stakes` (as documented at [5](#0-4) ; this exact scenario is reproduced in the repo's own test `test_load_and_reward_commission_accounts_reflects_vat_burn` [6](#0-5) , which asserts the commission is credited on top of the post-burn balance rather than the pre-burn snapshot captured at calculation time).
3. `load_and_reward_commission_accounts` reads the now-changed balance as `pre_lamports` [7](#0-6)  and feeds it into `collector_type_checked` [4](#0-3) , potentially producing an `Incinerator`/`SystemAccount` classification different from what would have been obtained had the account state been frozen at T1, silently changing whether `commission_lamports` is delivered to the collector or burned.

    #[test]
    fn test_load_and_reward_commission_accounts_reflects_vat_burn() {
        let (genesis_config, _mint_keypair) = create_genesis_config(1_000 * LAMPORTS_PER_SOL);
        let bank = Bank::new_for_tests(&genesis_config);
        let thread_pool = ThreadPoolBuilder::new().num_threads(1).build().unwrap();
        let pubkey = solana_pubkey::new_rand();

        let pre_burn_balance = 10 * crate::bank::DEFAULT_VAT_TO_BURN_PER_EPOCH;
        let commission_lamports = 12_345;

        // Commission is planned against the pre-burn account state.
        let mut commission_account = AccountSharedData::default();
        commission_account.set_lamports(pre_burn_balance);
        bank.store_account_and_update_capitalization(&pubkey, &commission_account);
        let mut reward_commissions = RewardCommissions::default();
        reward_commissions.insert(
            pubkey,
            RewardCommission {
                commission_bps: Some(500),
                commission_lamports,
                burned_lamports: 0,
                is_vote_account: true,
            },
        );

        // Simulate the VAT burn that would run in `update_epoch_stakes`
        // between reward calculation and distribution.
        let post_burn_balance = pre_burn_balance - crate::bank::DEFAULT_VAT_TO_BURN_PER_EPOCH;
        let mut burned_account = commission_account.clone();
        burned_account.set_lamports(post_burn_balance);
        bank.store_account_and_update_capitalization(&pubkey, &burned_account);

        let result = bank.load_and_reward_commission_accounts(&reward_commissions, &thread_pool);

        assert_eq!(result.accounts_with_rewards.len(), 1);
        let (pubkey_result, reward_info, account) = &result.accounts_with_rewards[0];
        assert_eq!(*pubkey_result, pubkey);
        // Commission is credited on top of the post-burn balance, not the
        // pre-burn snapshot captured at calculation time.
        let expected_post_balance = post_burn_balance + commission_lamports;
        assert_eq!(account.lamports(), expected_post_balance);
        assert_eq!(
            *reward_info,
            RewardInfo {
                reward_type: RewardType::Voting,
                lamports: commission_lamports as i64,
                post_balance: expected_post_balance,
                commission_bps: Some(500),
            }
        );
        assert_eq!(result.amounts.distributed_lamports, commission_lamports);
    }
