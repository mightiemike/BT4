## Analog Vulnerability Found

### Title
Signer global-state-machine agreement threshold uses floor division while the consensus-critical Nakamoto block signing threshold uses ceiling division — ([File: libsigner/src/v0/signer_state.rs])

### Summary
The stacks-core repo computes a "supermajority weight threshold" in two different places using two different rounding rules for the same nominal fraction (`NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD`/10). The consensus-critical block-signature check rounds up (ceiling), while the signer-side `GlobalStateMachineEvaluator` used to decide global agreement on protocol version / transaction-replay-set state rounds down (floor). This mirrors the DnGmxJuniorVault bug class: two functions that are supposed to compute the "same" limit/threshold diverge, breaking an equality that downstream logic assumes holds.

### Finding Description
The on-chain, consensus-critical threshold for a Nakamoto block to be considered signed is computed with an explicit ceiling: [1](#0-0) 

```rust
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
``` [2](#0-1) 

This value is used to reject a block whose `signer_signature` weight is under threshold in `verify_signer_signatures`, i.e. it is the exact consensus rule for what counts as "enough signers agreed."

In contrast, the signer-side `GlobalStateMachineEvaluator::reached_agreement`/`reached_disagreement`, which determines whether the signer network's decentralized state machine (protocol version, transaction-replay set, etc.) has reached consensus, uses plain integer (floor) division with no ceiling adjustment: [3](#0-2) 

```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}

pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```

Both functions are meant to answer the identical question — "has the same nominal 70% (or whatever `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` is) supermajority weight been reached?" — but they diverge whenever `total_weight * threshold` is not an exact multiple of 10. For any `total_weight` where `(total_weight * threshold) % 10 != 0`, `compute_voting_weight_threshold` returns `floor(total_weight*threshold/10) + 1`, one unit higher than the value `reached_agreement` accepts.

### Impact Explanation
This is minority-triggerable: a coalition of signers holding exactly the floor-rounded weight (one weight unit less than the true, consensus-enforced ceiling threshold) can cause the `GlobalStateMachineEvaluator` on some/most signer nodes to declare `reached_agreement` — believing a global state (protocol version or transaction-replay set) has achieved supermajority — while this same weight would *not* satisfy `compute_voting_weight_threshold`, the rule blocks/signatures are actually checked against. This produces a genuine cross-node divergence in signer view of "what is the agreed protocol/tx-replay state," which can lead signers to disagree about whether to sign/reject blocks or which replay set to apply, i.e., a temporary tip/behavior disagreement among signers bounded to the fee/consensus layer described in the rules ("temporary tip disagreement," "minority-triggerable ... divergence"). It does not directly cause a chain split by itself since actual block acceptance is still gated by the ceiling-based `compute_voting_weight_threshold` in `verify_signer_signatures`, but it undermines the invariant that all signer-side agreement checks are consistent with the chain's canonical threshold, and it can cause honest signers relying on `reached_agreement`/`reached_disagreement` to make decisions (e.g. considering a tx-replay set adopted, or considering a reorg permanently rejected via `reached_disagreement`) one weight-unit earlier than the network-enforced rule allows.

### Likelihood Explanation
Requires only a minority group of signers whose combined weight equals `floor(total_weight*threshold/10)` (not the +1 ceiling amount) — no majority or admin privilege needed — and requires `total_weight * NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` to not be a multiple of 10, which is the common case for arbitrary weight distributions. This is easily and frequently triggerable in normal network operation given essentially any signer weight distribution.

### Recommendation
Make `GlobalStateMachineEvaluator::reached_agreement`/`reached_disagreement` in `libsigner/src/v0/signer_state.rs` use the same ceiling-rounding formula as `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs` (or better, call a single shared threshold function) so that all "have we reached X% signer weight" checks in the codebase are computed identically.

### Proof of Concept
Let `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7` and `total_weight = 13` (not evenly divisible by 10/7 relationship):
- `compute_voting_weight_threshold(13)`: `13*7=91`, `91 % 10 = 1 != 0` → ceil=1 → threshold = `91/10 + 1 = 10`.
- `reached_agreement(vote_weight=9)` on `total_weight=13`: `9 >= 13*7/10 = 91/10 = 9` (floor) → `9 >= 9` → **true**.

So with 9 weight units, `reached_agreement` reports true (global-state consensus reached) while the actual consensus-critical block-signing threshold requires 10 weight units — a divergence of one weight unit that a minority coalition can trigger to cause signer nodes to disagree about whether global agreement (e.g. transaction-replay set) has actually been reached, while the chain's own signature-verification threshold has not.
