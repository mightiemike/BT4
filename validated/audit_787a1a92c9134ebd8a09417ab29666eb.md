I found a genuine, code-documented integrity gap in `ensure_match_transaction_info`, but I have not been able to fully verify whether it is reachable on the mainnet consensus/execution path (as opposed to only the offline replay-verify/db-tool path), which limits my confidence in reporting it as a full HIGH/CRITICAL finding. I'm presenting what the local code proves and flagging what remains unverified.

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, allowing divergent state/position roots to pass replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function used to confirm that a locally-computed `TransactionOutput` matches a trusted, proof-carrying `TransactionInfo` (i.e. the authenticated ledger record) during chunk replay/verification (`execution/executor/src/chunk_executor/mod.rs::verify_execution`). It checks status, gas used, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed values, as stated directly in its own trailing comment.

### Finding Description [1](#0-0) 

The function is documented to compare `status`, `gas_used`, write-set hash, and event root hash against `TransactionInfo`, but its own comment admits the state-checkpoint-family hashes are intentionally left unchecked: [2](#0-1) 

This function is invoked from the chunk executor's `verify_execution` path, which is the mechanism that certifies that replaying a chunk of already-committed transactions against local state produces the same result as what is authenticated in the chain (used by `db-tool`'s `replay_on_archive` and related verify-execution tooling): [3](#0-2) 

Because `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are not compared, a state root divergence introduced anywhere in the executor's state-checkpoint computation (`DoStateCheckpoint`, hot-state root, or the "trading native" position-state root path) would not be caught by this verification step. The comment explicitly calls out that this gap must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", indicating the authors are aware this is a real, unresolved integrity hole in a feature currently being staged.

### Impact Explanation
If the actual state-checkpoint hash produced by local execution diverges from the one embedded in the authenticated `TransactionInfo` (e.g., due to a bug in the state-checkpoint/root computation, or a JMT/hot-state root mismatch), `ensure_match_transaction_info` would still report success as long as status/gas/write-set/events match. This would let verification and replay tooling silently accept a divergent state root as "verified," defeating the purpose of `verify_execution` for state-root correctness. This matters for state-commitment integrity if `verify_execution`/replay-verify is relied upon (e.g., in `db-tool replay-verify`, fast-sync validation, or similar auditing flows) as a check that local state matches the authenticated chain.

### Likelihood Explanation
I could **not** confirm from local code whether this same `ensure_match_transaction_info` path (or an equivalent checkpoint-hash check) is also invoked in the primary state-sync/consensus commit path where a divergent root would actually cause a "wrong committed state" on mainnet, versus only in the offline replay/verify-execution tooling path shown above. `DoLedgerUpdate::assemble_transaction_infos` (which builds the canonical `TransactionInfo` from local execution, including `maybe_state_checkpoint_hash`) is a separate code path from `ensure_match_transaction_info` (which is comparison-only, for verify/replay), and I did not find evidence that state-sync's real commit path (`StateSyncChunkVerifier::verify_chunk_result` in `execution/executor/src/chunk_executor/chunk_result_verifier.rs`) uses the accumulator-hash comparison to independently catch state-root mismatches, or whether it relies on `ensure_match_transaction_info` too. Given the "trading native" position-state root feature is explicitly gated as not-yet-enabled per the code comment, and the state-checkpoint-hash check gap is self-documented as a known, deliberate limitation rather than a silent oversight, likelihood on current mainnet is uncertain/low, but the gap itself is real and acknowledged in-repo.

### Recommendation
Extend `ensure_match_transaction_info` to compare the recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) `position_state_checkpoint_hash` against the corresponding values in `txn_info`, mirroring the treatment already given to `state_change_hash` and `event_root_hash`. This should be done before the trading-native position-state-root feature is enabled in production, and ideally before this verification path is relied upon for security-relevant replay/verify guarantees.

### Proof of Concept
No working PoC is provided — this finding is a documentation-supported code-review gap (self-admitted in the source comment), not a demonstrated exploit. Constructing a concrete PoC would require reproducing a scenario where local `DoStateCheckpoint` output diverges from an authenticated `TransactionInfo`'s checkpoint hash while all other fields (status/gas/write-set/events) match — which requires deeper access to the state-checkpoint computation and the exact commit/replay call graph than I was able to fully trace with the available tools.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
