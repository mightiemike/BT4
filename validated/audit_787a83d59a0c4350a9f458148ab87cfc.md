Based on the investigation, the strongest analog to the reported "missing reentrancy guard on withdraw" bug class in this nearcore snapshot is the **`WithdrawFromGasKey` action being reachable through a `Delegate`/`DelegateV2` meta-transaction receipt**, which bypasses the guard that restricts this fund-moving action to top-level transactions only.

### Title
Gas-key balance can be drained through a delegated (meta-transaction) `WithdrawFromGasKey` action, bypassing the transaction-only guard - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
`WithdrawFromGasKeyAction` moves balance from a `GasKeyInfo` sub-balance back into the owning account's main balance [1](#0-0) . The code documents an explicit invariant that this action is a privileged, direct-transaction-only primitive: "This action must only be available via transactions, not via contract execution (there is no corresponding promise batch action host function)" [2](#0-1) . That invariant is effectively the "reentrancy guard" for this fund-moving action — it should not be reachable from an indirect/derived execution path such as a contract-created or relayer-created receipt. The `RejectWithdrawFromGasKeyInDelegate` protocol feature was added specifically to close a hole where a `Delegate`/`DelegateV2` action (NEP-366 meta-transaction) carrying an inner `WithdrawFromGasKeyAction` was admitted and spawned a *new* receipt that executed the withdrawal, moving balance out of the gas key exactly as if it were a top-level transaction.

### Finding Description
`WithdrawFromGasKeyAction` is applied by `action_withdraw_from_gas_key`, which unconditionally subtracts `action.amount` from the gas key's `GasKeyInfo.balance` and credits the account's main `amount` [3](#0-2) . This function is invoked from the runtime's action-apply loop for the `Action::WithdrawFromGasKey` case [4](#0-3) . Before the `RejectWithdrawFromGasKeyInDelegate` fix, `validate_action` did not reject a `WithdrawFromGasKeyAction` nested inside a `Delegate`/`DelegateV2` action when creating a *new* receipt, which is exactly the pathway the doc-comment says must not exist. The dedicated regression test confirms the pre-fix behavior actually drains the key: it submits `TransferToGasKey` to fund a gas key, then a delegated `WithdrawFromGasKeyAction` executed via a relayer/meta-transaction receipt, and asserts "the nested withdrawal should have drained the gas key" while running on the pre-upgrade protocol version [5](#0-4) . The fix adds a new validation error, `WithdrawFromGasKeyNotAllowedInDelegate`, that rejects the action specifically in `NewReceipt` validation mode while still permitting it for already-in-flight (`ExistingReceipt`) receipts to preserve liveness across the protocol upgrade boundary [6](#0-5) .

### Impact Explanation
If `RejectWithdrawFromGasKeyInDelegate` is not yet the active default on a given protocol version, any relayer/meta-transaction sender who obtains a signed `WithdrawFromGasKeyAction` (or is otherwise able to wrap it in a `SignedDelegateAction`) can create a new receipt that moves the gas key's dedicated balance into the account's spendable `amount`, outside the transaction-only invariant the type was designed around. Because a gas key's balance is meant to be a bounded, restricted allowance (separate from the full account balance, and burned rather than refunded past a cap on deletion, per `MAX_BALANCE_TO_BURN` in `access_keys.rs`), routing withdrawal through delegate/meta-transaction receipts is an unauthorized value movement / invariant-bypass on the runtime's balance accounting for gas keys.

### Likelihood Explanation
The attack requires only a single submitted meta-transaction (a `SignedDelegateAction` carrying an inner `WithdrawFromGasKeyAction`) reaching the runtime's apply loop as a new receipt — no validator, network, or sync compromise is needed, and it is directly reachable from an unprivileged relayer/transaction signer using NEP-366 delegated actions. The only mitigating factor is that a dedicated protocol feature (`RejectWithdrawFromGasKeyInDelegate`) has been introduced to close this exact hole; whether it is active by default at the currently deployed `STABLE_PROTOCOL_VERSION` in this snapshot could not be conclusively confirmed from the available index (the version-gate line in `core/primitives-core/src/version.rs` was located but its exact activation version number was not retrievable before the tool budget ran out).

### Recommendation
Confirm `RejectWithdrawFromGasKeyInDelegate` is enabled at (or below) the currently deployed stable protocol version, and, if not, expedite activation. Independently, audit for any other code paths (e.g. `Action::WithdrawFromGasKey` reachability via other batch/delegate/global-contract mechanisms) that could similarly bypass the "must only be available via top-level transactions" invariant, and add unit/integration coverage ensuring `validate_action`/`validate_actions_with_mode` rejects `WithdrawFromGasKeyAction` in every `NewReceipt`-creating context, not just `Delegate`/`DelegateV2`.

### Proof of Concept [7](#0-6)  demonstrates the exploit path end-to-end: add a gas key, fund it via `TransferToGasKey`, then submit a delegated `WithdrawFromGasKeyAction` through a relayer prior to the protocol upgrade — the assertion confirms the withdrawal succeeds and drains the gas key balance, which is precisely the scenario the fix (`RejectWithdrawFromGasKeyInDelegate` / `WithdrawFromGasKeyNotAllowedInDelegate`) is designed to prevent going forward [8](#0-7) .

**Note on incomplete verification:** I was unable to confirm within the available tool budget the exact protocol version at which `RejectWithdrawFromGasKeyInDelegate` activates in `core/primitives-core/src/version.rs`, nor whether it equals or precedes the build's `STABLE_PROTOCOL_VERSION`. This determines whether the finding represents a currently-live vulnerability versus an already-patched historical one; a Devin session with full repo/terminal access would be needed to definitively resolve this by inspecting `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.protocol_version()` against `STABLE_PROTOCOL_VERSION`.

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
