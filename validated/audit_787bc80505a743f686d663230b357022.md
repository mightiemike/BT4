### Title
Duplicate excluded-range entries (tombstone offset re-marked obsolete) cause `AccountStorageReader::read` to falsely signal EOF and truncate live snapshot bytes - ([File: accounts-db/src/account_storage_reader.rs])

### Finding Description
`AccountStorageReader::new` builds `sorted_excluded_accounts` by combining two independently-populated lists: the obsolete-accounts list (`storage.obsolete_accounts_read_lock().filter_obsolete_accounts(...)`) and the tombstone list (`storage.tombstone_offsets_read_lock()`), then sorts them descending by offset without deduplication. [1](#0-0) 

A tombstone entry (a zero-lamport, data-less record written when an account is closed) is only ever *added* to `tombstone_offsets` via `batch_insert_tombstone_offsets`; no removal path exists in the codebase (`remove_tombstone*` does not appear anywhere in the repo). If the same pubkey is later revived (written again with a positive lamport balance), the write path marks the *previous* record's offset — which is the tombstone's own offset — as obsolete via `mark_accounts_obsolete`, because any prior version superseded by a new write is added to `ObsoleteAccounts`. [2](#0-1)  Since the tombstone offset is never purged from `tombstone_offsets`, that same offset now appears **twice** in `sorted_excluded_accounts`: once from the obsolete list and once from the still-present tombstone list, both with the identical `(offset, tombstone_stored_size)` pair.

In `Read::read`, the skip logic only pops an excluded entry when `file_offset == excluded_start` exactly: [3](#0-2) 
When the first duplicate is consumed via `consume_or_skip`, the file offset advances past the excluded offset (`file_offset = excluded_start + skip_len`). The second, still-queued duplicate entry has `excluded_start` equal to the *old* offset, which is now strictly less than the current `file_offset`. On every subsequent loop iteration:
- The equality check `file_offset == excluded_start` never matches again (offset has moved past it), so the duplicate is never popped.
- `bytes_to_read_from_file = excluded_start.saturating_sub(file_offset)` evaluates to `0` forever, since `excluded_start < file_offset`.
- `bytes_to_read = bytes_left_in_buffer.min(0) == 0`, so `self.reader.read(&mut buf[..0])` is invoked, which returns `Ok(0)`.
- The code interprets `read_size == 0` as EOF and `break`s, permanently truncating the stream even though the underlying file has more live bytes remaining after that offset.

Because `Read::read` returning `0` is the standard EOF signal used by callers such as `io::copy` (used when writing archive/snapshot contents), any consumer of `AccountStorageReader` will silently stop copying at the first duplicated excluded offset, dropping every subsequent still-alive account's bytes from the output archive.

The `num_alive_bytes` length computation (`storage.get_obsolete_bytes` plus tombstone subtraction) also double-counts the same offset, so `reader.len()` reported to callers is inconsistent with the actual truncated byte stream produced by `read`, meaning downstream integrity/length checks that trust `len()` will not necessarily catch the truncation immediately (the reported length is smaller than the true content length, but not matching the point where `read` silently short-circuits either, since it stops earlier still).

None of the guards in `AccountStorageReader::new` — slot filtering (`filter_obsolete_accounts`, `snapshot_slot`), zero-lamport dedup, or tombstone exclusion — prevent the same physical offset from appearing in both the obsolete and tombstone vectors, nor does the reader dedupe `sorted_excluded_accounts` before use.

### Impact Explanation
An unprivileged user who writes, closes (zero-lamports the account), and then revives the same pubkey within one storage file (achievable purely through ordinary transactions creating/writing/closing/rewriting their own accounts) can cause a superseded tombstone offset to be simultaneously tracked as both obsolete and tombstone. When that storage file is later serialized through `AccountStorageReader` (e.g., during `bank_to_full_snapshot_archive`), the resulting archive stream can be truncated mid-storage, silently dropping bytes for accounts written after the duplicated offset. This is a snapshot-vs-bank divergence / node data-loss bug (archived snapshot no longer byte-accurately represents the live bank state for that storage file), matching the "honest-node snapshot-vs-replay mismatch" bounty category referenced in the question.

### Likelihood Explanation
The trigger only requires ordinary account lifecycle operations available to any fee-paying user: write → close (zero-lamport) → rewrite/revive of the same pubkey within a single AppendVec storage before that storage is shrunk/rewritten from scratch. This does not require validator/leader control, staked nodes, or crafted snapshots — only normal transaction sequencing that an attacker fully controls the timing of. It is reproducible deterministically given a controlled write/close/revive sequence and a subsequent snapshot archive request.

### Recommendation
Deduplicate `sorted_excluded_accounts` by offset in `AccountStorageReader::new` (e.g., via `sort_unstable_by` + `dedup_by_key`) before use, and/or ensure `tombstone_offsets` removes an offset once it is also recorded in `ObsoleteAccounts` (i.e., a tombstone that gets superseded by a later write should be pruned from `tombstone_offsets` at the same time it is pushed into `ObsoleteAccounts`). Additionally, harden `Read::read` in `AccountStorageReader` to never treat a `0`-length requested sub-read (`bytes_to_read == 0` while more excluded/live bytes remain) as an implicit EOF signal — distinguish "buffer window shrunk to zero because of stale accounting" from genuine end-of-file.

### Proof of Concept
Rust integration test (extension of the existing `accounts-db/src/account_storage_reader.rs` test module):
```rust
#[test]
fn test_account_storage_reader_duplicate_offset_tombstone_then_obsolete() {
    let (storage, _temp_dirs) =
        create_storage_for_storage_reader(0, AccountsFileProvider::AppendVec);
    let slot = 0;
    let pubkey = Pubkey::new_unique();

    // 1. write A (live)
    let acct_live = AccountSharedData::new(1, 10, &Pubkey::default());
    let offsets1 = storage.accounts
        .write_accounts(&(slot, &[(&pubkey, &acct_live)][..]))
        .unwrap().offsets;

    // 2. close A -> zero-lamport tombstone record; supersedes offsets1[0]
    let acct_closed = AccountSharedData::new(0, 0, &Pubkey::default());
    let offsets2 = storage.accounts
        .write_accounts(&(slot, &[(&pubkey, &acct_closed)][..]))
        .unwrap().offsets;
    // mark offsets1[0] obsolete (simulating clean_accounts behavior)
    let len1 = storage.accounts.get_account_data_lens(&offsets1);
    storage.obsolete_accounts().write().unwrap()
        .mark_accounts_obsolete(offsets1.iter().copied().zip(len1), slot);
    // register the tombstone
    storage.batch_insert_tombstone_offsets(offsets2.clone());

    // 3. revive A -> supersedes the tombstone at offsets2[0]
    let acct_revived = AccountSharedData::new(1, 10, &Pubkey::default());
    let offsets3 = storage.accounts
        .write_accounts(&(slot, &[(&pubkey, &acct_revived)][..]))
        .unwrap().offsets;
    let len2 = storage.accounts.get_account_data_lens(&offsets2);
    storage.obsolete_accounts().write().unwrap()
        .mark_accounts_obsolete(offsets2.iter().copied().zip(len2), slot);
    // NOTE: tombstone_offsets still contains offsets2[0] (no removal path exists)

    // 4. write one more live account after the duplicated offset
    let acct_after = AccountSharedData::new(1, 10, &Pubkey::default());
    storage.accounts.write_accounts(&(slot, &[(&Pubkey::new_unique(), &acct_after)][..]));

    let storage = storage.reopen_as_readonly().unwrap_or(storage);
    let files = open_storage_files(iter::once(&storage), false)
        .collect::<io::Result<Vec<_>>>().unwrap();
    let mut file_reader = storage_file_buf_reader(
        ACCOUNT_STORAGE_MAX_BUFFER_SIZE, false, &IoSetupState::default(),
    ).unwrap();
    file_reader.set_file(files[0].as_ref(), storage.accounts.len() as u64).unwrap();

    let mut reader = AccountStorageReader::new(
        &storage, None, TombstonesFilter::Exclude, &mut file_reader,
    ).unwrap();

    let mut out = Vec::new();
    let bytes_written = io::copy(&mut reader, &mut out).unwrap();

    // EXPECTED (bug): bytes_written < reader.len(), and out is missing the
    // trailing "acct_after" bytes, because read() silently stops early at the
    // duplicated offset instead of reading through to EOF.
    assert_eq!(bytes_written as usize, reader.len(), "read() truncated early, losing live account bytes");
}
```
Expected result on the vulnerable code path: the assertion fails because `io::copy` stops once `read()` returns `0` at the duplicated offset, so `bytes_written` is smaller than `reader.len()` and the bytes for `acct_after` (a still-live account) never make it into the snapshot output — demonstrating silent truncation of live account data. A companion invariant/property test can generate randomized sequences of `(write, close, revive)` for many pubkeys within one storage and assert `bytes_written == reader.len() == manually-computed alive bytes` for both `use_direct_io = true/false`.
