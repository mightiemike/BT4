### Title
SVM event listener classifies logs from any program by scanning all `Program data:` lines in a transaction that merely references the gateway address, not just logs actually emitted by the gateway program — enabling fabricated inbound events - (File: `universalClient/chains/svm/event_listener.go`)

### Summary
`determineEventType` and its caller `processSignatureBatch` treat every `Program data: ...` log line in a transaction as a potential gateway event, as long as that transaction shows up under `GetSignaturesForAddress(gatewayAddr, ...)`. Solana's `getSignaturesForAddress` RPC returns any transaction that merely *references* an address in its account list — it does not require that the account's program was actually invoked. Combined with the fact that `determineEventType`/`ParseEvent` never check which program actually emitted a given log line (no parsing of the `Program <id> invoke`/`success` boundaries), an attacker can submit an ordinary, unprivileged transaction that:

1. Includes the gateway program's address as any (even read-only, non-signer) account key, and
2. Invokes an attacker-controlled program that calls `sol_log_data` directly to emit a fake `Program data: <base64>` line whose first 8 bytes match a real, publicly-known event discriminator (Anchor discriminators are derived from `sha256("event:<Name>")`, which is not secret) and whose remaining bytes are entirely attacker-chosen. [1](#0-0) [2](#0-1) 

### Finding Description
`processSlotRange` fetches transaction signatures only filtered by address reference, and `processSignatureBatch` then iterates over *every* log line of the transaction, feeding each into `determineEventType`, with no verification that the `Program data:` line came from an invocation of the gateway program itself: [3](#0-2) 

Because `determineEventType` decodes the base64 payload and looks up the first 8 bytes purely against a discriminator table, any program's log line matching a known discriminator will be classified as `send_funds`, `finalize_universal_tx`, `revert_universal_tx`, or `funds_rescued`: [2](#0-1) 

`ParseEvent`/`parseSendFundsEvent`/`parseOutboundObservationEvent` then trust the decoded byte layout entirely, extracting sender, recipient, bridge token, amount, tx IDs, etc. directly from attacker-controlled bytes with no cross-check against actual gateway state or SPL balances: [4](#0-3) 

Since this parsing is entirely deterministic on the raw transaction log content, this is not a case requiring a malicious/dishonest validator — every honest Universal Validator running the identical `universalClient` code against the same real Solana transaction data (the crafted transaction is fully public and immutable on-chain) will independently derive the exact same fabricated event, `EventID`, and payload. The confirmation stage (`event_confirmer.go`) only checks slot depth and `tx.Meta.Err`, not that the log actually originated from the gateway program: [5](#0-4) 

This satisfies the required "honest validator" model in the scope rules — the bug is in the shared, honestly-run listener code, not in any privileged actor's behavior. Once confirmed, this event is voted via `MsgVoteInbound`/`VoteOnInboundBallot`, and per the architecture, once 2/3+ Universal Validators agree, the core validator executes the inbound, minting PRC20 tokens / running the user's payload — with no independent revalidation against the gateway program's real on-chain state: [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged attacker can fabricate a fully valid-looking `send_funds` (or `finalize_universal_tx`/`revert_universal_tx`/`funds_rescued`) inbound observation without ever calling the real gateway program or locking/burning any real SVM assets. Since all honest UVs deterministically observe the same forged log content, quorum can be reached honestly, leading to unauthorized PRC20 minting or unauthorized outbound/refund/revert flows — direct theft of protocol/user funds.

### Likelihood Explanation
Requires only an ordinary unprivileged Solana transaction: deploy or reuse an arbitrary program that logs attacker-chosen bytes via `sol_log_data`, include the (public) gateway program address as an account reference, and set the first 8 bytes of the logged payload to a known/derivable event discriminator. This is fully within reach of an unprivileged external actor and does not need any race around slot finality — it is a data-validation gap, not a timing race, though repeating traffic around confirmation windows can be used to test which "confirmation_type" gate is easiest to clear.

### Recommendation
When iterating `tx.Meta.LogMessages`, only accept `Program data:` lines that appear within the `Program <gatewayProgramID> invoke [...]` / `Program <gatewayProgramID> success` boundary for the actual gateway program ID (parse Solana's structured log invocation stack, or better, decode the actual inner instructions/CPI stack from `tx.Meta.InnerInstructions` and confirm the emitting program ID equals the configured gateway address) before calling `determineEventType`/`ParseEvent`.

### Proof of Concept
1. Attacker deploys (or reuses) a Solana program `P` that accepts an instruction with arbitrary bytes and calls `sol_log_data(bytes)` on those bytes.
2. Attacker computes `disc = sha256("event:SendFunds")[:8]` (public constant used by the gateway's Anchor IDL) and builds `payload = disc || fake_sender || fake_recipient || fake_token || fake_amount || ...` matching the expected `send_funds` byte layout.
3. Attacker submits a transaction invoking `P` with this payload, adding the real gateway program address as an additional (read-only, non-signer) account so the transaction is returned by `GetSignaturesForAddress(gatewayAddr, ...)`.
4. Every Universal Validator's SVM `EventListener.processSignatureBatch` fetches this transaction, finds the `Program data: <payload>` log line, and `determineEventType` classifies it as `send_funds` — even though the gateway program was never actually invoked and no real funds moved.
5. After confirmation depth passes, `chainStore` marks the event `CONFIRMED`; validators vote `MsgVoteInbound`; once quorum is reached, `x/uexecutor` mints PRC20 tokens to the attacker-chosen recipient — funds theft with no corresponding real deposit.

// determineEventType determines the event type based on the log discriminator
func (el *EventListener) determineEventType(log string) string {
	if !strings.HasPrefix(log, "Program data: ") {
		return ""
	}

	eventData := strings.TrimPrefix(log, "Program data: ")
	decoded, err := base64.StdEncoding.DecodeString(eventData)
	if err != nil {
		return ""
	}

	if len(decoded) < 8 {
		return ""
	}

	discriminator := strings.ToLower(hex.EncodeToString(decoded[:8]))

	// Look up event type from discriminator map
	eventType, ok := el.discriminatorToEventType[discriminator]
	if !ok {
		return ""
	}

	return eventType
}

// parseSendFundsEvent parses a sendFunds event as UniversalTx
func parseSendFundsEvent(log string, signature string, slot uint64, logIndex uint, chainID string, logger zerolog.Logger) *store.Event {
	if !strings.HasPrefix(log, "Program data: ") {
		return nil
	}

	eventData := strings.TrimPrefix(log, "Program data: ")
	decoded, err := base64.StdEncoding.DecodeString(eventData)
	if err != nil {
		return nil
	}

	if len(decoded) < 8 {
		return nil
	}

	// Create EventID in format: signature:LogIndex
	eventID := fmt.Sprintf("%s:%d", signature, logIndex)

	logger.Debug().
		Str("event_id", eventID).
		Str("signature", signature).
		Uint("log_index", logIndex).
		Uint64("slot", slot).
		Msg("processing sendFunds event")

	// Create store.Event
	event := &store.Event{
		EventID:           eventID,
		BlockHeight:       slot,
		Type:              store.EventTypeInbound, // Gateway events from external chains are INBOUND
		Status:            store.StatusPending,
		ExpiryBlockHeight: 0, // Will be set based on confirmation type if needed
	}

	// Parse event data from this log
	parseUniversalTxEvent(event, decoded, logIndex, chainID, logger)

	return event

- **Inbound** — A gateway event observed on an external chain. Universal Validators wait for finality, then vote it via `MsgVoteInbound` on `x/uexecutor`. Once 2/3 vote the same observation, the core validator executes it on Push Chain (mints PRC20s, runs the user's payload through their UEA).

A single inbound's payload can spawn multiple outbounds; each outbound's destination event can become a new inbound. The core validator is the consistency point that keeps the whole graph deterministic.

func (k Keeper) VoteOnInboundBallot(
	ctx context.Context,
	universalValidator sdk.ValAddress,
	inbound types.Inbound,
) (isFinalized bool,
	isNew bool,
	err error) {
	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return false, false, err
	}

	universalValidatorSet, err := k.uvalidatorKeeper.GetEligibleVoters(ctx)
	if err != nil {
		return false, false, err
	}

	// number of validators
	totalValidators := len(universalValidatorSet)

	// votesNeeded = ceil(2/3 * totalValidators)
	// >2/3 quorum similar to tendermint
	votesNeeded := (types.VotesThresholdNumerator*totalValidators)/types.VotesThresholdDenominator + 1

	k.Logger().Debug("voting on inbound ballot",
		"ballot_key", ballotKey,
		"validator", universalValidator.String(),
		"total_validators", totalValidators,
		"votes_needed", votesNeeded,
	)

	// Convert []sdk.ValAddress → []string
	universalValidatorSetStrs := make([]string, len(universalValidatorSet))
	for i, v := range universalValidatorSet {
		universalValidatorSetStrs[i] = v.IdentifyInfo.CoreValidatorAddress
	}

	// Step 2: Call VoteOnBallot for this inbound synthetic
	_, isFinalized, isNew, err = k.uvalidatorKeeper.VoteOnBallot(
		ctx,
		ballotKey,
		uvalidatortypes.BallotObservationType_BALLOT_OBSERVATION_TYPE_INBOUND_TX,
		universalValidator.String(),
		uvalidatortypes.VoteResult_VOTE_RESULT_SUCCESS,
		universalValidatorSetStrs,
		int64(votesNeeded),
		int64(types.DefaultExpiryAfterBlocks),
	)
	if err != nil {
		return false, false, err
	}
