Based on the analysis, I've confirmed a genuine analog to the reported vulnerability class in java-tron's resource delegation accounting.

### Title
Unfair resource-usage reassignment via current-ratio share calculation in `UnDelegateResourceProcessor`/`UnDelegateResourceActuator` allows delegators to socialize their bandwidth/energy usage debt onto other delegators - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
The reported bug describes a DeFi staking pattern where `userShare` is computed from the *current* total pool balance divided by the *current* total staked accounting variable (`userShare = userStaked * totalTokenBalance / totalStaked`), allowing a later depositor to capture value accrued before their deposit, or allowing an early depositor to escape their share of a liability by having a later depositor dilute the pool. Java-tron's resource-delegation "un-delegate" logic (`UnDelegateResourceProcessor.execute` and its actuator twin `UnDelegateResourceActuator.execute`) uses the structurally identical current-ratio pattern to compute how much accumulated bandwidth/energy "usage debt" (`transferUsage`) an un-delegating owner takes back from a shared receiver account.

### Finding Description
When multiple accounts delegate frozen TRX (bandwidth/energy capacity) to the same receiver account, the receiver's `netUsage`/`energyUsage` (analogous to the "pool balance" that grows due to unrelated activity) is a *shared, fungible* liability across all current delegators, while `receiverCapsule.getAllFrozenBalanceForBandwidth()`/`...ForEnergy()` (analogous to `totalStaked`) is the *current* sum of everyone's delegated capacity.

When an owner un-delegates, the usage clawed back to them is:
```java
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
``` [1](#0-0) 

This is the exact same "current ratio of pool" formula the external report flags: `userShare = userStaked * totalBalance / totalStaked`. Because `receiverCapsule.getAllFrozenBalanceForBandwidth()` is a live sum across *all* delegators and can change between when the usage was actually consumed and when any individual delegator un-delegates, the amount of usage debt assigned to a withdrawing delegator depends on the pool's composition at withdrawal time rather than on when/by whom the usage was actually caused. The identical actuator-path duplicate exists in the legacy (non-VM) contract handler [2](#0-1) .

Concretely:
- Delegator A delegates a small amount to Receiver early; Receiver consumes heavy bandwidth/energy while the pool is small, so `netUsage` becomes large relative to A's share.
- Before A un-delegates, Delegator B delegates a much larger amount to the same Receiver, diluting `getAllFrozenBalanceForBandwidth()`.
- When A un-delegates, `transferUsage` is computed against the *diluted* denominator, so A reclaims only a small fraction of the usage debt that was actually caused by A's own capacity — the rest of that usage debt remains stuck on the receiver and is effectively passed on to B (and any other remaining/future delegators), who will bear a disproportionate `transferUsage` burden when they eventually un-delegate, despite not having caused that consumption.
- Any account can freely call `DelegateResourceContract`/`UnDelegateResourceContract` (or the TVM native contract equivalents) against any receiver, so this is fully unprivileged and reachable from ordinary broadcast transactions.

### Impact Explanation
This corrupts per-account resource accounting (bandwidth/energy usage), a core consensus-relevant state that determines free-tier throughput and fee computation for accounts. A malicious delegator can time delegate/un-delegate operations around a receiver's consumption spikes to shift usage liability onto co-delegators, effectively stealing "clean" resource capacity from others or forcing them to pay TRX fees earlier than they should (once their free bandwidth/energy is unfairly consumed by inherited usage). This is an accounting-corruption / unfair-value-transfer issue analogous to the staking reward-theft class, though bounded by TRX_PRECISION-scale amounts and by the min() cap with `unDelegateMaxUsage`.

### Likelihood Explanation
Medium: exploitation requires coordinating delegate/un-delegate timing around a receiver account's usage patterns, which is realistic since delegation is a widely used, permissionless product feature (commonly used by exchanges/dApps that receive delegated resources from many independent parties), and the attacker only needs ordinary transactions (`DelegateResourceContract`, `UnDelegateResourceContract`) with no special privilege.

### Recommendation
Track and attribute usage debt per delegator (e.g., accrue a "usage per unit delegated" index similar to `DelegationStore`'s Vi-based reward accumulator pattern used in `MortgageService`/`VoteRewardUtil`) rather than computing `transferUsage` from the instantaneous ratio of the withdrawing delegator's balance to the current total pool. Snapshotting usage at delegation time and settling deltas would prevent the socialization/manipulation of usage debt among delegators with different join times.

### Proof of Concept
1. Owner A delegates `X` TRX bandwidth capacity to Receiver R.
2. R (or any transaction using R's bandwidth) consumes bandwidth, causing `R.getNetUsage()` to accumulate while `R.getAllFrozenBalanceForBandwidth() == X`.
3. Before A un-delegates, Owner B delegates `Y >> X` TRX bandwidth capacity to the same Receiver R, so `R.getAllFrozenBalanceForBandwidth() == X + Y`.
4. A calls `UnDelegateResourceContract` (or the TVM `unDelegateResource` native contract) to reclaim `X`. `transferUsage = R.netUsage * X / (X + Y)` — much smaller than the usage A's capacity actually generated in step 2, per [3](#0-2) .
5. The residual usage debt remains on R and will later be disproportionately assigned to B when B un-delegates, even though B did not cause it.
