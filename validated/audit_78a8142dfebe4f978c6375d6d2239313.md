### Title
`EnergyProcessor.useEnergy()` skips the energy-limit cap check once `supportUnfreezeDelay` is active, letting energy usage exceed the account's frozen-energy cap - (File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java)

### Summary
`EnergyProcessor.useEnergy()` is the java-tron analog of Lyra's `canHedge()` gate: it is supposed to reject (`return false`) an energy consumption request when it would push usage beyond the account's `energyLimit` cap, forcing the caller to fall back to fee-based billing. However, the cap check is conditioned on flags that make it a no-op once `supportUnfreezeDelay()` (Stake 2.0 unfreeze-delay) is active, so the "above cap" case is silently approved instead of being disqualified, exactly the same root cause pattern described in the report.

### Finding Description
`useEnergy()` computes `energyLimit` via `calculateGlobalEnergyLimit()` and the account's current usage, then is supposed to reject requests that would exceed the cap: [1](#0-0) 

The rejection is gated by:
```java
if (energy > (energyLimit - newEnergyUsage)
    && dynamicPropertiesStore.getAllowTvmFreeze() == 0
    && !dynamicPropertiesStore.supportUnfreezeDelay()) {
  return false;
}
```
Once `supportUnfreezeDelay()` is `true` (a chain-wide hard-fork flag activated via the `UNFREEZE_DELAY_DAYS`/`ALLOW_CANCEL_ALL_UNFREEZE_V2` proposals, not something an individual user controls but a permanent state of any post-Stake-2.0 chain), the third conjunct is always `false`, so the entire condition is always `false` regardless of how far `energy` exceeds the available `energyLimit - newEnergyUsage`. `useEnergy()` unconditionally proceeds to increase usage and returns `true`: [2](#0-1) 

This mirrors the reported bug class precisely: a capacity-check function (`canHedge()` / here, the implicit "canUseEnergy" gate inside `useEnergy()`) is supposed to disqualify (return false) usage requests once the cap is reached or would be exceeded, but a logic condition neuters the check for a whole class of accounts/state (post-unfreeze-delay chains), so the check "will return true" (succeed) even above the defined cap.

The natural expectation (and how `getAccountLeftEnergyFromFreeze()` still computes it) is that `energyLimit` remains a hard cap on free/frozen energy usage that should be enforced before falling back to `feeLimit`-based TRX billing in `ReceiptCapsule.payEnergyBill()`/`getOriginUsage()`, which for the `supportUnfreezeDelay()` path also just clamps the *origin* portion with `min(...)` rather than re-validating against the cap: [3](#0-2) 

### Impact Explanation
If `useEnergy()` always returns `true` once `supportUnfreezeDelay()` is active, an account's `energyUsage` can be pushed above its computed `energyLimit` in the accounting store without the intended fallback (rejecting the free/frozen energy path and instead billing TRX at `feeLimit`, or failing the transaction). This is an accounting/state-divergence issue: the on-chain resource ledger (`AccountCapsule.energyUsage`) can diverge from the invariant that usage should not exceed the frozen-energy-derived cap, undermining resource-based fee accounting integrity, similar in class to the reported hedging cap bypass leading to invariant violation (delta neutrality vs. resource-cap neutrality here).

### Likelihood Explanation
`supportUnfreezeDelay()` reflects a chain-wide hard fork state that is permanently `true` on any updated java-tron network past the Stake 2.0 unfreeze-delay activation, so this code path is the *normal*, not an edge, path for such networks. Any transaction/contract call whose energy usage would exceed the caller's/origin's remaining frozen energy will hit this branch.

### Recommendation
Restore an explicit cap check in the `supportUnfreezeDelay()` branch of `useEnergy()`: compare `energy` against `energyLimit - newEnergyUsage` (using the `recovery()`-computed `newEnergyUsage`) independent of the `getAllowTvmFreeze()`/`supportUnfreezeDelay()` flags, and return `false` (triggering the normal fallback billing/rejection path) when the request would exceed the cap, consistent with `getAccountLeftEnergyFromFreeze()`'s cap computation.

### Proof of Concept
Not independently reproducible from static analysis alone: confirming actual end-to-end impact (i.e., that no other caller re-validates the cap before/after `useEnergy()` in the `supportUnfreezeDelay()` path, particularly for the "caller" portion in `ReceiptCapsule.payEnergyBill()`) would require running a testnet transaction with `supportUnfreezeDelay()` enabled and an account whose frozen energy is smaller than the energy consumed by a contract call, and observing whether the stored `energyUsage` exceeds `calculateGlobalEnergyLimit()` afterward. This was not verified against a live node/test in this analysis; only the source-level logic-gating flaw was confirmed via [4](#0-3) .

  public boolean useEnergy(AccountCapsule accountCapsule, long energy, long now) {

    long energyUsage = accountCapsule.getEnergyUsage();
    long latestConsumeTime = accountCapsule.getAccountResource().getLatestConsumeTimeForEnergy();
    long energyLimit = calculateGlobalEnergyLimit(accountCapsule);
    long newEnergyUsage;
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newEnergyUsage = increase(energyUsage, 0, latestConsumeTime, now);
    } else {
      // only participate in the calculation as a temporary variable, without disk flushing
      newEnergyUsage = recovery(accountCapsule, ENERGY, energyUsage,
          latestConsumeTime, now);
    }

    if (energy > (energyLimit - newEnergyUsage)
        && dynamicPropertiesStore.getAllowTvmFreeze() == 0
        && !dynamicPropertiesStore.supportUnfreezeDelay()) {
      return false;
    }
