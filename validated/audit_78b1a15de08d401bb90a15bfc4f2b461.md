## Analysis: Analog Found

The Backed Protocol bug is a reentrancy that lets an attacker (`currentLoanOwner`) re-invoke `lend()` with manipulated terms *before* the victim's original call completes, corrupting shared `loanInfo` state via an untrusted external call. The reachable analog in this repository is the **unauthenticated pipeline resume endpoint**, which allows the same class of "attacker-controlled external callback re-enters and overwrites in-flight state before the original transaction/consumer sees the final result."

### Title
Unauthenticated `/v2/resume/:runID` endpoint allows a malicious/compromised bridge adapter to repeatedly overwrite pipeline task-run results while the run is still in progress - (File: `core/web/pipeline_runs_controller.go`)

### Summary
The bridge async-task resume callback (`PATCH /v2/resume/:runID`) is registered without authentication and is invoked directly by the external bridge/adapter server referenced in a job spec. Nothing in `Runner.ResumeRun` / `orm.UpdateTaskRunResult` prevents the same `taskID` from being resumed multiple times with different, attacker-chosen values as long as the overall pipeline run's state is still `running` or `suspended` (e.g., while sibling legs of a multi-source median job are still pending). This mirrors the `NFTLoanFacilitator.lend()` bug class: an externally-controlled party can re-enter/re-invoke a state-mutating handler mid-flight and overwrite already-recorded values that a downstream consumer (the aggregation task / on-chain report) will use, without the node detecting the manipulation.

### Finding Description
`/v2/resume/:runID` is mounted in the *unauthenticated* route group: [1](#0-0) 

The handler decodes attacker-supplied JSON and forwards it straight to `ResumeJobV2`: [2](#0-1) 

`ResumeJobV2` calls `PipelineRunner.ResumeRun`, which updates the task result and restarts the run if it was suspended: [3](#0-2) 

The underlying `UpdateTaskRunResult` query only guards on the *overall run's* state (`running`/`suspended`), not on whether this specific `pipeline_task_runs` row already has a result/`finished_at` set: [4](#0-3) 

```
SELECT ... FROM pipeline_runs ... WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended') FOR UPDATE
...
UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1
```

Because a DAG can contain several concurrently-pending async legs (e.g., `ds1` bridge, `ds2`/`ds3` HTTP legs feeding a `median` task, as exercised in the test fixtures), the run remains in `running`/`suspended` state until *all* legs resolve. During that window, the party that received the `responseURL` for a given `taskID` (the bridge/external adapter — the "attacker" analog to `currentLoanOwner`, since it is external, untrusted infrastructure referenced by a bridge job) can call `/v2/resume/<taskID>` any number of times with different `value`/`error` payloads, and each call is accepted and overwrites the previously stored task output, exactly like the attacker in the report calling `lend()` again mid-transaction to overwrite `loanInfo` with different terms before the victim's transaction settles.

Existing tests confirm the resume URL and payload shape but do not test/guard against a second, contradictory resume call for the same task while the run is still open: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a **misreporting/data tampering** vector on the node's pipeline output: a malicious or compromised external adapter (the bridge server a job spec points at) can send an initial "correct-looking" result and then, before the sibling legs of the run finish, submit one or more additional resume calls to swap in a different value for the same task — for example changing a price value feeding a `median` task used by an OCR/flux job. Because the check is only on the run's aggregate state and not on per-task finality, the node has no way to detect that the "final" value used for aggregation differs from what was originally accepted, mirroring the "bad loan terms accepted without detection" impact in the source report. This can lead to incorrect on-chain reports being submitted by the node.

### Likelihood Explanation
Reachability requires only that: (1) the node runs a job with an async bridge/external-adapter task feeding a multi-leg aggregation (a supported, common configuration), and (2) the party operating the bridge endpoint (which is inherently external/untrusted network infrastructure) is malicious or compromised. No node/peer/operator privilege is required — the resume route is explicitly unauthenticated by design (`unauthedv2`), and the `taskID` is disclosed to the bridge itself as part of the outbound request. This fits the allowed "bridge or external-adapter abuse" trust-boundary category.

### Recommendation
- In `orm.UpdateTaskRunResult`, additionally guard on the target task row's own completion state (e.g., `WHERE pipeline_task_runs.id = $1 AND finished_at IS NULL`) so a resume call can only ever set a result once per task, rejecting subsequent resumes for the same `taskID`.
- Consider binding the resume callback to a single-use token/nonce independent of the predictable `taskID`, and audit-log/alert on repeated resume attempts for the same task.

### Proof of Concept
1. Configure a job whose DAG has an async bridge task (`ds1`, `async=true`) alongside other legs (`ds2`, `ds3`) feeding a `median` task, matching the pattern in `core/services/pipeline/runner_test.go` (`Test_PipelineRunner_AsyncJob_InstantRestart`).
2. Start the run; the node POSTs the bridge request including `responseURL=".../v2/resume/<taskID>"`.
3. From the (malicious) bridge server, before the other legs (`ds2`,`ds3`) finish, issue: `PATCH /v2/resume/<taskID>` with `{"data": <value A>}`.
4. Before the run reaches `RunStatusCompleted` (i.e., while sibling legs are still resolving), issue a second `PATCH /v2/resume/<taskID>` with `{"data": <value B>}`.
5. Observe that `UpdateTaskRunResult` accepts the second call (run state is still `running`/`suspended`), overwriting the task's `output`/`error`/`finished_at`, and the final aggregated result reflects the attacker's second, manipulated value rather than the value originally submitted and possibly already relied upon.

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
