The nearcore docs explicitly confirm the exact bug pattern from the Sherlock report: in meta-transactions (NEP-366 delegate actions), the relayer pays the deposit/balance for an inner action, but if that inner action's receipt fails on the receiver's shard, the refund is sent to `predecessor_id` (Alice, the signer of the delegate action) rather than to the relayer who actually funded the deposit — exactly mirroring "refund goes to recipient/intermediary instead of the actual payer."### Title
Meta-transaction deposit refunds are sent to the delegate-action `sender_id` (recipient/signer) instead of the relayer who actually funded the deposit - ([File: runtime/runtime/src/actions.rs])

### Summary
In NEP-366 meta transactions, the relayer's account (transaction `signer_id`) prepays and funds the attached deposit for every inner action wrapped in a `DelegateAction`. When `apply_delegate_action` converts the delegate action into a new receipt, the new receipt's `predecessor_id` is set to the delegate-action `sender_id` (e.g. "Alice"), not the relayer, even though the relayer is the one whose balance was actually debited to fund the deposit. Because deposit/balance refunds are routed to `receipt.balance_refund_receiver()`, which defaults to `predecessor_id()` [1](#0-0) , a failed inner action on the receiver's shard causes the deposit to be refunded to Alice (the delegate-action sender/signer) instead of back to the relayer who paid for it.

### Finding Description
When a relayer submits a meta transaction, gas and deposits for all inner actions are purchased from the relayer's account during transaction conversion. `apply_delegate_action` then builds a brand-new `Receipt` whose `predecessor_id` is the DelegateAction's `sender_id` (Alice), while the relayer only appears as `signer_id`/`signer_public_key` of the `ActionReceipt`: [2](#0-1) 

The code comment directly acknowledges the asymmetry: gas is refunded to the `signer_id` (the relayer), but deposit refunds go to the `predecessor_id`, which is `sender_id`/Sender from the DelegateAction (Alice), not the relayer: [3](#0-2) 

The generic refund logic confirms this: `refund_unspent_gas_and_deposits` pushes a `Receipt::new_balance_refund` addressed to `receipt.balance_refund_receiver()` [4](#0-3) , and `balance_refund_receiver()` returns `refund_to` if explicitly set, otherwise falls back to `predecessor_id()` [1](#0-0) . For the delegate-spawned receipt, `refund_to` is never set, so it resolves to Alice's account, not the relayer's.

This is explicitly documented as a known, exploitable financial-incentive issue in the architecture docs themselves: [5](#0-4) 

### Impact Explanation
- The relayer pays real NEAR tokens (deposit) to fund an inner action requested by Alice via a `DelegateAction`/`DelegateV2` (NEP-366/gas-key meta-transactions).
- If the inner action fails execution on the receiver's shard (Bob's shard), the deposit refund goes to Alice's account rather than back to the relayer.
- Alice has a direct financial incentive to craft delegate actions with high attached deposits targeting actions/receivers that are guaranteed or likely to fail, effectively siphoning funds from the relayer with no recourse, since this happens entirely inside protocol-level receipt/refund accounting - not an application bug the relayer can code around after signing.
- This constitutes unauthorized value movement: tokens debited from one account (relayer) end up credited to a different account (Alice) that the payer did not intend to fund, purely due to how `predecessor_id` is chosen for delegate-spawned receipts.

### Likelihood Explanation
High likelihood of misuse in practice: any user with access to a relayer service (a common pattern for gasless/meta-transactions, NEP-366) can trigger this by constructing a `SignedDelegateAction` whose inner actions have a deposit attached and are designed to fail on the receiver shard (e.g., targeting a non-existent method, an account that will reject the call, or a contract state that guarantees failure). No privileged access, validator collusion, or network-level attack is required - a single malicious signer interacting with an honest relayer is sufficient. The relayer cannot detect this at submission time beyond trusting that the inner actions will succeed, and the docs explicitly flag this as a "financial incentive" attack a malicious signer can exploit.

### Recommendation
For receipts spawned from `DelegateAction`/`DelegateV2`, set the receipt's `refund_to` field (via `ActionReceiptV2`) to the relayer (the transaction `signer_id`/original payer of the deposit) instead of relying on the default `predecessor_id` fallback in `balance_refund_receiver()`. This mirrors how gas refunds already correctly go to the relayer. Concretely, in `apply_delegate_action` (`runtime/runtime/src/actions.rs`), construct the new receipt using `ActionReceiptV2` with `refund_to: Some(action_receipt.signer_id().clone())` so that `Receipt::new_balance_refund` in `refund_unspent_gas_and_deposits` correctly reimburses the relayer rather than the delegate-action's `sender_id`.

### Proof of Concept
1. Relayer R signs and submits a `SignedDelegateAction` on behalf of Alice, wrapping an inner `FunctionCall` action with a nonzero `deposit` targeting `receiver_id = Bob`, where the call is engineered to fail (e.g., calls a nonexistent method or a method that always panics on Bob's contract).
2. R's account pays gas + deposit at transaction conversion time.
3. `apply_delegate_action` creates the inner receipt with `predecessor_id = Alice` (delegate `sender_id`), `receiver_id = Bob` (`runtime/runtime/src/actions.rs:499-513`).
4. The inner receipt executes on Bob's shard and fails (as designed by Alice).
5. `refund_unspent_gas_and_deposits` issues a `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, which resolves to `predecessor_id` = Alice (`core/primitives/src/receipt.rs:428-430`, `runtime/runtime/src/lib.rs:1402-1407`).
6. Alice's account balance increases by the deposit amount that was actually paid by relayer R; R's balance never gets it back.

## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
