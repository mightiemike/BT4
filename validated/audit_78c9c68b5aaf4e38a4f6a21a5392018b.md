This confirms the analog: `RemoteComponentServer::remote_component_server_handler` at [1](#0-0)  performs no sender authentication whatsoever — it deserializes any `Request` bytes received over the TCP/HTTP2 socket and forwards them directly to `local_client.send(request)`, which dispatches straight into the component's `handle_request`. For the mempool, this means any `MempoolRequest::AddTransaction(AddTransactionArgsWrapper)` reaching the mempool's remote port is processed by `MempoolCommunicationWrapper::add_tx` at [2](#0-1)  and then `Mempool::add_tx`/`add_tx_validations` at [3](#0-2) , none of which perform signature verification, declare-authorization checks, or resource-bound/stateless validation — those all live exclusively in the Gateway's `add_tx_inner` (`check_declare_permissions`, `stateless_tx_validator.validate`) at [4](#0-3) .

In the distributed/hybrid deployment configs, the mempool component is configured with `"components.mempool.execution_mode": "LocalExecutionWithRemoteEnabled"` and a `remote_server_config` bound to `0.0.0.0`, as seen in [5](#0-4) . This is architecturally identical to the Presto internal-API bypass: the mempool's remote server is an "internal" API meant only to be called by the co-located Gateway component, but it is exposed as a plain, unauthenticated HTTP/2 network service that accepts `MempoolRequest` values from any network-reachable client — completely bypassing the Gateway's authorization/validation chokepoint (declare-account allowlist, stateless signature/format checks, stateful nonce/fee/resource-bound blockifier validation).

However, I want to flag a caveat before finalizing: whether this is truly "reachable by an unprivileged transaction sender" depends on network exposure assumptions that the repo's deployment docs may or may not document as requiring network-level isolation (analogous to Presto's "does not affect installations that have not configured secure internal communication" carve-out). I did not find any additional authentication layer (mTLS, shared secret, allowlist) in `RemoteComponentServer` or `RemoteServerConfig`, and the `bind_ip` defaults to `0.0.0.0` (`DEFAULT_BIND_IP`) per [6](#0-5) , so I'm treating this as within scope for the analog since no compensating control exists in the code itself.

### Title
Unauthenticated Mempool Remote Component Server Allows Bypass of Gateway Authorization/Validation - (File: crates/apollo_infra/src/component_server/remote_component_server.rs)

### Summary
The `RemoteComponentServer` used by the Mempool (and other components) in distributed/hybrid deployments accepts and processes any well-formed `MempoolRequest` over its network-bound HTTP/2 socket without any sender authentication or authorization check. Because all transaction validation (declare-account allowlisting, signature/stateless checks, stateful nonce/fee/resource-bound validation via the Blockifier) is performed exclusively in the Gateway component before it calls the Mempool's `add_tx`, an attacker who can reach the Mempool's remote port can submit `AddTransaction` requests directly, completely bypassing the Gateway's validation and authorization pipeline — mirroring the class of bug in CVE-2020-15087, where authenticated actors could reach Presto's internal coordinator/worker APIs and bypass authorization enforced only at the outer layer.

### Finding Description
The transaction submission flow is designed so that all validation happens in the Gateway: `GenericGateway::add_tx_inner` calls `check_declare_permissions` (declare-account allowlist) and `self.stateless_tx_validator.validate(&tx)` before ever constructing an `AddTransactionArgsWrapper` and calling `self.mempool_client.add_tx(add_tx_args)` (`crates/apollo_gateway/src/gateway.rs:228-236, 275-286`). The Mempool component itself performs no equivalent checks: `MempoolCommunicationWrapper::add_tx` (`crates/apollo_mempool/src/communication.rs:120-132`) and `Mempool::add_tx`/`add_tx_validations` (`crates/apollo_mempool/src/mempool.rs:411-444, 479-513`) only check FIFO/capacity/nonce-ordering/fee-escalation invariants against already-trusted `AddTransactionArgs` fields (`tx`, `account_state`) — they never verify the transaction signature, never check `check_declare_permissions`-style allowlists, and never run stateful Blockifier `validate` entry-point execution.

In distributed/hybrid deployments, the Mempool component runs with `"execution_mode": "LocalExecutionWithRemoteEnabled"` and exposes a `RemoteComponentServer<MempoolRequest, MempoolResponse>` bound to `0.0.0.0` by default (`crates/apollo_deployments/resources/services/distributed/replacer_mempool.json:77-93`; `RemoteServerConfig::default()` in `crates/apollo_infra/src/component_server/remote_component_server.rs:144-156`). The server's request handler (`remote_component_server_handler`, lines 186-274) simply deserializes the incoming HTTP body into a `Request` (here, `MempoolRequest`) and forwards it via `local_client.send(request)` straight into `ComponentRequestHandler::handle_request` (`crates/apollo_mempool/src/communication.rs:230-263`) — there is no peer identity check, shared secret, mTLS, or IP allowlist enforced anywhere in this code path.

Because `MempoolRequest::AddTransaction(AddTransactionArgsWrapper)` is a `pub` request variant reachable by any TCP client that can open a connection to the bound port, and `AddTransactionArgsWrapper`/`AddTransactionArgs` are just `Serialize`/`Deserialize` structs constructed entirely from attacker-supplied bytes, an attacker can hand-craft an `InternalRpcTransaction` (bypassing signature verification, declare authorization, resource-bound checks, and Blockifier `validate` execution) and inject it directly into the Mempool, from where it will be included in `get_txs()` calls made by the Batcher for block building and also re-propagated to the P2P network via `send_tx_to_p2p`.

### Impact Explanation
This breaks the fundamental sequencer invariant that all transactions admitted to the mempool (and hence eligible for inclusion in a block) must have passed signature verification, declare-account authorization, and stateful account/fee/resource-bound validation. An attacker reaching the Mempool's remote port can:
- Inject unsigned/invalid transactions that skip signature verification, potentially leading to execution of transactions that were never validly authorized by the purported sender.
- Bypass the `authorized_declarer_accounts` allowlist (`check_declare_permissions`), a privileged Declare-transaction restriction, undermining an explicit authorization boundary.
- Cause the Batcher/blockifier to attempt executing invalid transactions during block building, potentially causing block-building failures, wasted resources, or divergence between honest sequencer nodes if the malformed transaction interacts unexpectedly with execution/fee logic.
This matches the report's threshold for "unauthorized account action" / "network unable to confirm new transactions" impact categories, and is High severity given it fully circumvents the platform's stated single validation chokepoint.

### Likelihood Explanation
Any deployment configuration enabling `LocalExecutionWithRemoteEnabled` for the Mempool component (as shown in the distributed/hybrid deployment resource JSON files) exposes the vulnerable remote server on the network. The `RemoteComponentServer` implementation contains no authentication code path at all — this is not a misconfiguration but the current default behavior of the shared `apollo_infra` component-server framework used across all components (Mempool, Committer, Gateway, etc.). Reaching it requires only network connectivity to the exposed port, i.e., an unprivileged network client, making exploitation straightforward wherever this port is not additionally firewalled at the infrastructure layer.

### Recommendation
Add authentication/authorization to `RemoteComponentServer` (e.g., mutual TLS between known sequencer components, a shared bearer token/HMAC validated per request, or a network-level allowlist enforced in code) so that inter-component "internal" RPC endpoints cannot be invoked by arbitrary network clients. At minimum, security-sensitive request variants like `MempoolRequest::AddTransaction` should independently re-run the same validation the Gateway performs (signature check, declare-account allowlist, stateful nonce/fee checks) rather than trusting the caller to have already done so, consistent with defense-in-depth and the Presto advisory's guidance to enforce authorization at the internal-API boundary itself rather than relying solely on outer-layer checks.

### Proof of Concept
1. Deploy the sequencer using a distributed/hybrid configuration (e.g., `crates/apollo_deployments/resources/services/distributed/replacer_mempool.json`) where the Mempool's `remote_server_config` is enabled and bound to `0.0.0.0`.
2. From any network location with access to the Mempool's exposed port, open an HTTP/2 connection and send a raw bincode/serde-serialized `MempoolRequest::AddTransaction(AddTransactionArgsWrapper { args: AddTransactionArgs { tx: <crafted InternalRpcTransaction with arbitrary/invalid signature>, account_state: AccountState { address, nonce } }, p2p_message_metadata: None })`, matching the wire format expected by `SerdeWrapper::<MempoolRequest>::wrapper_deserialize` in `remote_component_server_handler`.
3. Observe that `Mempool::add_tx_validations` (`crates/apollo_mempool/src/mempool.rs:411-444`) only checks nonce ordering/fee escalation/capacity, and the request is accepted into the pool without ever calling the Gateway's `check_declare_permissions` or `stateless_tx_validator.validate`, confirming the transaction bypassed all Gateway-enforced authorization and validation.
