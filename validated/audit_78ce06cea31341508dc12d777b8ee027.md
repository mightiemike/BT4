## Title
Inconsistent `AllowTvmCompatibleEvm` version-1 contract check between `TransferActuator` and `TransferAssetActuator` — ([File: actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java])

### Summary
`TransferActuator.validate()` enforces two independent, security-relevant checks before allowing a transfer to a smart-contract account: the `FORBID_TRANSFER_TO_CONTRACT` check and, separately, an `AllowTvmCompatibleEvm`-gated check that blocks transfers to contracts whose `ContractCapsule.getContractVersion() == 1` (EVM-compatible version-1 contracts), directing callers to use `TriggerSmartContract` instead. `TransferAssetActuator.validate()`, which handles the analogous operation for TRC10 asset transfers, only implements the first check (`getForbidTransferToContract`) and completely omits the second, version-1-specific guard.

### Finding Description
In `TransferActuator.validate()` (`actuator/src/main/java/org/tron/core/actuator/TransferActuator.java:141-156`), after the `ForbidTransferToContract` check, there is an additional check:
```java
if (dynamicStore.getAllowTvmCompatibleEvm() == 1
    && toAccount != null
    && toAccount.getType() == AccountType.Contract) {
  ContractCapsule contractCapsule = chainBaseManager.getContractStore().get(toAddress);
  ...
  } else if (contractCapsule.getContractVersion() == 1) {
    throw new ContractValidateException(
        "Cannot transfer TRX to a smartContract which version is one. "
            + "Instead please use TriggerSmartContract ");
  }
}
``` [1](#0-0) 

This check exists specifically because version-1 (EVM-compatible) contracts have different fallback/receive semantics under `VMConfig.allowTvmCompatibleEvm()` (see `VMActuator.create()` setting `.setVersion(1)` and `Program.createContractImpl` / `callToAddress` propagating `contractVersion` through calls) [2](#0-1) [3](#0-2) , meaning a bare value transfer (rather than a `TriggerSmartContract` call) to such a contract bypasses the contract's expected call semantics.

`TransferAssetActuator.validate()` (`actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java:169-175`) only performs the `ForbidTransferToContract` check:
```java
AccountCapsule toAccount = accountStore.get(toAddress);
if (toAccount != null) {
  if (dynamicStore.getForbidTransferToContract() == 1
      && toAccount.getType() == AccountType.Contract) {
    throw new ContractValidateException("Cannot transfer asset to smartContract.");
  }
  ...
}
``` [4](#0-3) 
There is no corresponding check for `getAllowTvmCompatibleEvm() == 1` combined with `contractVersion == 1`. This is confirmed by the existing test `TransferAssetActuatorTest.transferToContractAddress()`, which deploys a version-1-eligible contract, sets `VMConfig.initAllowTvmCompatibleEvm`-adjacent flags, and successfully executes a TRC10 asset transfer directly to the contract without hitting the version-1 rejection path that `TransferActuatorTest.transferToSmartContractAddress()` exercises for TRX transfers. [5](#0-4) [6](#0-5) 

This mirrors exactly the bug class in the external report: a security-relevant validation guard applied consistently to one route/operation (`TransferContract`/TRX transfers) but silently absent from a sibling route handling an analogous operation (`TransferAssetContract`/TRC10 transfers), reachable by any anonymous party broadcasting a transaction.

### Impact Explanation
Any account holding a TRC10 asset can send it directly (via `TransferAssetContract`, reachable from an unauthenticated broadcast RPC) to a version-1 EVM-compatible contract, bypassing the intended requirement to route value transfers to such contracts through `TriggerSmartContract`. Since version-1 contract call semantics (fallback/receive behavior, gas/energy stipend handling per `Program.getCallEnergy`) differ from the legacy TVM contract model, this can lead to funds/asset transfers landing in contracts that never execute their intended receive logic, silently deposited assets that the contract's accounting does not track, or other consensus-relevant asset/accounting inconsistencies between the TRX and TRC10 transfer paths for the same class of contracts. This is an accounting-consistency and unauthorized-operation-boundary issue affecting on-chain state, not merely a UX inconsistency.

### Likelihood Explanation
High reachability: `TransferAssetContract` is a standard, low-privilege user-broadcastable transaction type processed by `TransferAssetActuator`, requiring no special permission beyond owning the asset balance. No node operator action or misconfiguration is needed beyond the network having activated `AllowTvmCompatibleEvm` (an on-chain committee-controlled but already-existing feature flag) and at least one deployed version-1 contract, both of which are ordinary post-fork network states, not privileged or adversarial preconditions.

### Recommendation
Add the same `getAllowTvmCompatibleEvm() == 1 && contractCapsule.getContractVersion() == 1` guard to `TransferAssetActuator.validate()` that exists in `TransferActuator.validate()`, rejecting TRC10 transfers to version-1 contracts and directing callers to `TriggerSmartContract`, consistent with the TRX transfer path. More broadly, factor this shared validation logic into a common helper (e.g., in `ActuatorConstant` or a shared utility) invoked by both actuators (and any other actuators that create direct value/asset transfers to contract accounts) to prevent future drift.

### Proof of Concept
1. Enable `AllowTvmCompatibleEvm` via committee proposal (or in test/private-chain config).
2. Deploy a version-1 (EVM-compatible) contract.
3. Issue/hold a TRC10 asset on an account.
4. Broadcast a `TransferAssetContract` transaction sending that TRC10 asset to the version-1 contract's address.
5. Observe that `TransferAssetActuator.validate()` succeeds (as shown by the existing `TransferAssetActuatorTest.transferToContractAddress()` test, which performs an analogous scenario and asserts `code.SUCESS`), whereas the equivalent `TransferContract` (TRX) flow against the same contract is rejected by `TransferActuator.validate()` with `"Cannot transfer TRX to a smartContract which version is one."` as shown in `TransferActuatorTest.transferToSmartContractAddress()`.
