### Title
Non-Embedded OAuth Session Cookie Defaults to Domain-Wide `path: '/'`, Letting the Most-Recently-Authenticated Shop Overwrite Session Cookies for Other Shops in the Same Browser - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
The reported bug class is: a shared, security-critical resource (voting power in `StakingContract.sol`) is unconditionally reassigned in full to whoever performs the most recent unprivileged action (`stake`/`unstake`), rather than being tracked per-actor/proportionally. The `shopify-app-js` analog is the OAuth session cookie in the non-embedded flow: the `shopify_app_session` cookie is written with a **domain-wide default path (`/`)**, so the browser can only hold one such cookie at a time. Whichever shop most recently completed the OAuth callback "wins" the cookie, silently overwriting the session pointer for every other shop tab already open in that browser — an unprivileged, ordinary OAuth flow triggered by any merchant.

### Finding Description
In `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`, the `callback()` handler sets the session-id cookie like this: [1](#0-0) 

`cookiePath` defaults to `/` unless the app developer explicitly opts into a per-shop path via a factory function, as documented directly in the config type: [2](#0-1) 

The changelog confirms this was a known, previously-unmitigated defect that required an opt-in fix, and that the vulnerable default (`path: '/'`) remains the out-of-the-box behavior: [3](#0-2) 

Because `Set-Cookie` with `path: '/'` scopes the cookie to the entire domain, a browser can only store one `shopify_app_session` value per domain at a time. When a user (e.g., a merchant/agency managing multiple shops, or even the same user re-authenticating a second store) completes OAuth for Shop B in one tab, the resulting `Set-Cookie` **silently overwrites** the cookie that was pointing at Shop A's session in a different, still-open tab — exactly mirroring the staking bug's pattern of "the last unprivileged actor to complete a normal operation takes over the entire shared credential/resource."

### Impact Explanation
Once overwritten, any subsequent unauthenticated request from Shop A's tab resolves `getCurrentId`/session lookup using the cookie value that now actually belongs to Shop B's session id. Depending on how the app's session storage and route logic use that session id, this can result in:
- Requests intended for Shop A being served/authorized using Shop B's session context (cross-tenant session confusion), and
- Loss of the previously established session ("session index injection" via a shared browser cookie value), analogous to how the last staker in the original report unintentionally strips voting power from everyone before them.

This is a defect in default cookie-scoping in an authentication handler (`lib/auth/oauth/oauth.ts`), not a leaked secret or MITM issue, and is reachable from a normal, single (non-privileged) merchant/agency multi-shop OAuth flow using default configuration.

### Likelihood Explanation
Likelihood is limited to non-embedded apps using default configuration (no custom `cookiePath`) with a single browser managing multiple shop installs concurrently (a common pattern for agencies/dev shops testing multiple stores, or a user with several tabs open). Any embedded app, or any app that has already set `cookiePath`, is unaffected. The trigger (running the standard OAuth callback for a second shop) requires no special privileges.

### Recommendation
Ship a URL-based default for `cookiePath` that is unique per install (e.g., encode the shop domain into the path) instead of the domain-wide `/`, or force developers to explicitly configure a per-shop path before allowing multi-shop non-embedded deployment, and add a runtime warning/log whenever `cookiePath` is left at the domain-wide default and a session store request differs from the last-observed shop.

### Proof of Concept
1. Configure a non-embedded app with default settings (`cookiePath` unset).
2. In Browser Tab 1, complete OAuth for `shop-a.myshopify.com`; observe `Set-Cookie: shopify_app_session=offline_shop-a...; Path=/`.
3. In Browser Tab 2 (same browser), complete OAuth for `shop-b.myshopify.com`; observe `Set-Cookie: shopify_app_session=offline_shop-b...; Path=/`, which overwrites the Tab 1 cookie because both share `Path=/` on the same domain.
4. Return to Tab 1 and issue a request; the browser now sends the Shop B session id cookie, and the app looks up/acts on Shop B's session/session storage entry instead of Shop A's — confirmed by the test file demonstrating cookie collision at `packages/apps/shopify-api/lib/auth/oauth/__tests__/oauth.test.ts`: [4](#0-3)

  /**
   * The path to use for the OAuth session cookie in non-embedded apps.
   *
   * By default the cookie is written with `path: '/'`, making it domain-wide.
   * This means that when a user authenticates multiple shops in separate tabs,
   * each OAuth callback overwrites the previous cookie, causing all tabs to use
   * the most-recently-authenticated shop.
   *
   * Set this to a string or a function returning a string to scope the cookie to
   * a URL path prefix that is unique per shop. The browser will then maintain
   * one cookie per shop and deliver only the matching one per request.
   *
   * **Requirement:** the configured path must match the actual URL structure of
   * your app — e.g. if each shop lives under `/shops/:shop/`, use that prefix.
   * The library cannot derive this automatically.
   *
   * @example
   * // Static path (single-shop apps or apps with no shop-specific routing)
   * cookiePath: '/'
   *
   * @example
   * // Factory function (multi-shop non-embedded apps)
   * cookiePath: (session) => `/shops/${session.shop}/`
   *
   * @defaultValue `'/'`
   */
  cookiePath?: string | ((session: Session) => string);
```

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
