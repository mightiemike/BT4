## Analysis

The strongest reachable analog to CVE‑2025‑25374 (a state that permanently blocks *all future* application launches from a single trigger) is in the sequencer's Cairo‑Native compilation pipeline: `NativeClassManager` in `crates/blockifier/src/state/native_class_manager.rs`. A single contract declaration can permanently kill the async compilation worker thread, after which **every subsequent** class-compilation request from **any account** crashes the calling thread with an unhandled panic — a global compilation/execution denial of service, not limited to the triggering class.

### Title
Unrecoverable Cairo‑Native compilation worker crash permanently disables class compilation for all future transactions — ([File: crates/blockifier/src/state/native_class_manager.rs])

### Summary
`NativeClassManager::start` spawns exactly one long‑lived compilation worker thread that owns the receiving end of an `mpsc::sync_channel`, with no supervision or respawn logic [1](#0-0) . If that worker thread ever panics — which happens deterministically when `panic_on_compilation_failure` is enabled and a declared Sierra class fails native compilation [2](#0-1)  — the receiver is dropped during unwinding and the channel becomes permanently disconnected. Any later call to `send_compilation_request`, from any thread handling any transaction that needs lazy native compilation, then hits `TrySendError::Disconnected` and executes an unconditional `panic!("Compilation request channel is closed.")` [3](#0-2) . Because there is no mechanism to detect the dead worker and restart it, this is a one-shot, unrecoverable failure for the remainder of the process's lifetime.

### Finding Description
`NativeClassManager::set_and_compile` is invoked for every Cairo‑1 class encountered during execution — whenever `get_compiled_class`/`get_compiled_from_class_manager` misses the in-memory cache [4](#0-3) . When `CairoNativeMode::LazyCompilation` is configured, this dispatches a non-blocking send on the shared channel to the single worker thread [5](#0-4) .

The worker's `process_compilation_request` panics (killing the worker thread) whenever a compilation failure occurs and `panic_on_compilation_failure` is set — a first-party, publicly exposed config flag [6](#0-5) . A declarer only needs to submit one Sierra class engineered to fail native compilation (e.g., disallowed constructs, oversized program, resource-limit violation) to trigger this panic once native mode is active.

Once the worker thread dies, `receiver` (moved into the thread closure) is dropped, disconnecting the channel. From that point on, *every* subsequent transaction anywhere in the node that needs to compile/cache a class via `send_compilation_request` panics on `TrySendError::Disconnected` [7](#0-6) , confirmed by the dedicated unit test `test_send_compilation_request_channel_disconnected` [8](#0-7) . This panic occurs on whichever thread is executing/validating the transaction — potentially the batcher's block-building path — with no `catch_unwind`/supervision analogous to the `WorkerPool`'s panic-flag mechanism used elsewhere in the codebase [9](#0-8) , so it is not contained.

### Impact Explanation
This maps to "a network unable to confirm new transactions": once the single compilation worker dies, the node can no longer safely process any transaction whose execution path requires native-compiling a class, because doing so re-triggers the disconnected-channel panic. There is no self-healing (no worker respawn), so the condition persists until manual operator intervention/restart — and if the corrupting class/transaction is replayed (e.g., during OS re-execution or reprocessing), the same crash recurs. This is directly analogous to the cFS bug: a single interaction puts the platform into a state that prevents all further "application launches" (here, class compilations/executions).

### Likelihood Explanation
The trigger requires `cairo_native_run_config.cairo_native_mode` set to `LazyCompilation` and `panic_on_compilation_failure` set to `true`; in the sampled deployment configs shown, both default to `off`/`false` [10](#0-9) . However, this is a first-class, `"Public"` operator-tunable setting explicitly documented as "Whether to panic on compilation failure" [6](#0-5) , intended presumably as a fail-fast safety mechanism — but its actual effect is a permanent, attacker-triggerable, node-wide compilation outage from a single declare transaction, with no worker-restart safeguard. Likelihood is Medium: it depends on this specific (but supported and documented) configuration being enabled.

### Recommendation
- Make the compilation worker supervised: detect thread death/channel disconnection and respawn a fresh worker (with a fresh channel) instead of allowing the disconnected state to propagate into a hard `panic!` on unrelated call sites.
- Avoid `panic!` on `TrySendError::Disconnected` in `send_compilation_request`; degrade gracefully (e.g., fall back to non-native execution, log and skip native compilation) rather than crashing the calling thread.
- Re-evaluate whether `panic_on_compilation_failure=true` should ever be reachable in production topologies, or gate it so that a compilation failure for one class cannot cascade into loss of native compilation for all other classes.

### Proof of Concept
1. Deploy/run a sequencer node with `cairo_native_run_config.cairo_native_mode = "lazy_compilation"` and `panic_on_compilation_failure = true`.
2. Submit a `DECLARE` transaction for a Sierra class crafted to compile successfully to CASM (so it passes the mempool/gateway Sierra-to-CASM validation) but fails Sierra-to-Native compilation (e.g., violates the native compiler's resource/libfunc constraints) — this is the `create_faulty_request` scenario exercised in [11](#0-10) .
3. Once the class is executed/declared, `set_and_compile` dispatches the compilation request; the worker thread panics inside `process_compilation_request` (per the `panics_on_failure` test case) and dies, dropping `receiver`.
4. Submit any further transaction (unrelated declare/invoke) that requires `set_and_compile`/`send_compilation_request` for a new class — the calling thread now panics with "Compilation request channel is closed." as reproduced in [8](#0-7) , crashing that execution path for the remainder of the process's life.

    /// Sends a compilation request to the compilation worker. Does not block the sender. Logs an
    /// error if the channel is full.
    fn send_compilation_request(
        &self,
        request: CompilationRequest,
    ) -> Result<(), ContractClassManagerError> {
        let sender = self.sender.as_ref().expect("Compilation channel not available.");
        // TODO(Avi, 15/12/2024): Check for duplicated requests.
        sender.try_send(request).map_err(|err| match err {
            TrySendError::Full((class_hash, _, _)) => {
                log::debug!(
                    "Compilation request channel is full (size: {}). Compilation request for \
                     class hash {:#066x} was not sent.",
                    self.cairo_native_run_config.channel_size,
                    class_hash.0
                );
                ContractClassManagerError::TrySendError(TrySendError::Full(class_hash))
            }
            TrySendError::Disconnected(_) => {
                panic!("Compilation request channel is closed.")
            }
        })
    }

    fn _run_executor(&self, worker_executor: &WorkerExecutor<S>) {
        if self.a_thread_panicked.load(Ordering::Acquire) {
            panic!("Another thread panicked. Aborting.");
        }

        // Making sure that the program will abort if a panic occurred while halting
        // the scheduler.
        let abort_guard = AbortIfPanic;
        // If a panic is not handled or the handling logic itself panics, then we
        // abort the program.
        let res = panic::catch_unwind(panic::AssertUnwindSafe(|| {
            worker_executor.run();
        }));
        if let Err(err) = res {
            // First, set the panic flag. This must be done before halting the scheduler.
            self.a_thread_panicked.store(true, Ordering::Release);

            // If the program panics here, the abort guard will exit the program.
            // In this case, no panic message will be logged. Add the cargo flag
            // --nocapture to log the panic message.

            worker_executor.scheduler.halt();
            abort_guard.release();
            panic::resume_unwind(err);
        }
