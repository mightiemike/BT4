### Title
DeleteAccount refund to a non-existent `beneficiary_id` permanently burns the account's balance instead of returning it - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally sends the deleted account's remaining balance to `delete_account.beneficiary_id` via a system `Receipt::new_balance_refund`, with no validation that the beneficiary account actually exists [1](#0-0) . This is the same bug class as the ERC721 report: a value-transfer is performed to a target without verifying the target can actually accept the asset, and if it cannot, the asset is irrecoverably lost.

### Finding Description
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically valid account id; it does not require the account to exist [2](#0-1) . When the action executes, `action_delete_account` pushes a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` unconditionally whenever the balance is non-zero [1](#0-0) .

This refund receipt has `predecessor_id == "system"`. The runtime's own refund-handling logic states explicitly: "If the refund fails tokens are burned" [3](#0-2) , and this is documented generally: "If the execution of a refund fails, the refund amount is burnt" (`docs/RuntimeSpec/Refunds.md:12`). A test in the codebase confirms that a refund receipt targeting a non-existent account fails with `AccountDoesNotExist` and does not create the account [4](#0-3) . Combining these facts: if `beneficiary_id` does not exist at the time the `DeleteAccount` action executes, the balance-refund receipt fails, and — per the burn-on-failed-refund rule — the entire remaining account balance is permanently destroyed rather than returned to the deleting account or its predecessor.

This is directly analogous to the CouncilMember report's core defect: an unsafe transfer routine moves value to a target account without checking that the target can actually receive/handle it, and on failure the asset is not safely recovered but lost.

### Impact Explanation
Any transaction signer who submits a `DeleteAccount` action with a `beneficiary_id` that does not exist (a typo, a not-yet-created account, or an account that gets deleted/never created before the receipt executes cross-shard) causes their own account's entire remaining NEAR balance to be permanently burned. Because `DeleteAccount` can also be submitted via `promise_batch_action_delete_account` from a contract acting on a user's behalf, and because the beneficiary account's existence is checked at execution time on a potentially different shard/receipt than validation time, this is a real, protocol-level, transaction-reachable path to permanent loss of funds (burned, not stolen — but "permanently frozen/destroyed funds" is explicitly an accepted impact category).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the account owner (or code acting via a promise on their behalf) to pass a beneficiary account id that turns out not to exist at receipt-execution time. This can happen accidentally (typo in a hand-crafted `beneficiary_id`, referencing an account not yet deployed, or a race where the beneficiary is deleted between construction and execution of the receipt), and is not something the protocol currently guards against — validation only checks that the id is well-formed, not that it exists. Unlike a targeted attacker exploit against a third party, this class of loss is self-inflicted against the deleting account's own balance, similar to the low-severity classification given to the original ERC721 report.

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (an explicit read/check at action-validation or execution time), and reject the `DeleteAccount` action (returning an execution/validation error) if the beneficiary does not exist, rather than silently generating a system refund receipt that will burn the funds on failure. Alternatively, change the refund-on-failure semantics for balance-refund receipts specifically raised by `DeleteAccount` so that a failed refund is rerouted (e.g., to the predecessor/actor) instead of being burned.

### Proof of Concept
1. Create account `alice.near` funded with N NEAR.
2. `alice.near` submits a transaction with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near" })`, where `nonexistent.near` is a syntactically valid but never-created account id.
3. `action_delete_account` computes `account_balance = N` and unconditionally pushes `Receipt::new_balance_refund(&"nonexistent.near", N)` [1](#0-0) ; `alice.near`'s account is then removed.
4. The refund receipt executes with `predecessor_id == "system"` against `nonexistent.near`; because the account does not exist, execution fails with `AccountDoesNotExist` (mirroring the confirmed behavior in `refund_may_not_create_universal_account`) [5](#0-4) .
5. Per the "refund fails → burn" rule [3](#0-2) , the N NEAR is added to `other_burnt_amount` and permanently removed from total supply; it is not returned to `alice.near` or anyone else.
