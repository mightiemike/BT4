## Analog Found

### Title
Relayer fee is paid unconditionally before the wallet's underlying action is known to succeed - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`inner_rlp_execute` schedules the relayer-fee transfer as an independent promise batch, completely decoupled from the promise chain that actually performs the user's requested action (transfer / ERC-20 transfer / function call). The fee is dispatched purely based on successfully *parsing* the RLP transaction, not on whether the resulting action later succeeds. This mirrors the reported USSD bug: a value-moving side effect (there, burning USSD; here, paying the relayer) is executed unconditionally instead of being gated on the actual outcome of the operation it is supposed to be compensating.

### Finding Description
In `inner_rlp_execute`, once `parse_rlp_tx_to_action` successfully decodes the signed Ethereum transaction into a Near `Action` and its `TransactionKind`, the code immediately creates and dispatches a standalone promise batch that transfers the computed `fee` to the relayer (`predecessor_account_id`): [1](#0-0) 

This `refund_promise` is created via `env::promise_batch_create` / `env::promise_batch_action_transfer` as a brand-new, independent receipt — it is not `.then()`-chained to, or in any way conditioned on, the promise that will actually execute the user's action. That action promise is built afterwards, separately, in the `match transaction_kind { ... }` block: [2](#0-1) 

Only that second promise is wired to `rlp_execute_callback`, whose job is to detect success/failure of the real action and (for the *caller's attached deposit*, via `CallerDeposit`) refund on failure: [3](#0-2) 

Notice that this failure-handling logic only refunds the `caller_deposit` (the deposit attached by whoever called `rlp_execute`), never the relayer `fee` that was already sent out in the separate, unconditional promise batch. There is no code path that claws back or withholds the relayer fee if the actual transfer/function-call action later fails (e.g., insufficient wallet balance, receiver account doesn't exist, target contract call reverts, callback gas insufficient, etc.).

### Impact Explanation
Because the fee-payment promise executes independently of, and prior to knowledge of, the outcome of the user's intended action, the relayer is compensated even when it delivers no service — i.e., even when the signed transaction it relayed ultimately fails on-chain. This is unauthorized value movement out of the wallet-contract account (owned by the ETH-implicit-account user) to the relayer with no corresponding executed action, closely analogous to burning USSD tokens without confirming the swap that was supposed to justify the burn. Any legitimately signed transaction that fails for reasons the user did not intend (contract-side reverts, storage/account issues, insufficient gas on the follow-up call, etc.) results in silent, un-refundable fee loss to the account owner, since the nonce has already been incremented (preventing retry) and the fee already paid.

### Likelihood Explanation
Reachable by any relayer/transaction submitter who calls the wallet contract's public `rlp_execute` method with a validly signed RLP transaction that includes a non-zero `fee`; a relayer merely needs to submit (or resubmit under normal operational conditions) a transaction whose parsed action can fail for any of the many downstream reasons listed above (insufficient balance for the transfer, non-existent/incompatible receiver, reverting `ft_transfer`/function-call, address-registrar edge cases, etc.). No special privilege beyond being the entity that submits the transaction is required, matching the "meta-transaction sender" access path.

### Recommendation
Do not dispatch the relayer-fee `Transfer` as an independent promise batch. Instead, chain it after (or make it conditional on) the success of the promise that performs the user's actual action — e.g., only create/execute the fee transfer inside `rlp_execute_callback` (or an equivalent post-execution callback) after confirming `PromiseResult::Successful`, mirroring how `caller_deposit` refunds are already gated on the action's outcome.

### Proof of Concept
1. A relayer submits an `rlp_execute` call with a validly RLP-signed Ethereum transaction from the wallet owner specifying, e.g., an `EOABaseTokenTransfer` with a non-zero `fee` and a transfer `deposit`/target such that the follow-up `action_to_promise` transfer will fail (e.g., amount exceeds the wallet's current balance after fee/gas deduction, or targets an account that will cause `ActionError`).
2. `inner_rlp_execute` parses the transaction successfully, increments the nonce, and immediately fires the `refund_promise` sending `fee` yoctoNEAR to the relayer via [4](#0-3) .
3. The main action promise built afterward fails during execution (its result is `PromiseResult::Failed`), which `rlp_execute_callback` reports as `success: false` and only refunds `caller_deposit` if one exists ( [5](#0-4) ) — the relayer fee already sent is never returned.
4. Net result: the wallet account's balance has been debited by `fee` yoctoNEAR to the relayer even though the user's intended action never executed.

            let ext = WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let address_registrar = {
                let account_id = ADDRESS_REGISTRAR_ACCOUNT_ID
                    .trim()
                    .parse()
                    .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
                ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,
            ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
        }
