### Title
DoS of market makers via order-book queue packing at the best price level in `MarketSellAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchOrder()` walks a linked list of maker orders (`MarketOrderIdListCapsule`) at the best price for a trading pair and matches them one by one against a taker order. If the number of maker orders consumed while filling a single taker transaction exceeds `MAX_MATCH_NUM`, the whole transaction is aborted with `ContractValidateException`. Because any unprivileged user can place many minimal-size sell orders at the same price for a negligible, fixed `MarketSellFee`, an attacker can pack the best-price queue with more than `MAX_MATCH_NUM` tiny orders, causing any legitimate larger order that needs to walk through that queue to always exceed the match cap and revert — the same "unbounded array/list packing to grief a shared queue" pattern described in the RealWagmi report, adapted to java-tron's on-chain order book. [1](#0-0) 

### Finding Description
Orders at the same price for a token pair are stored in an on-chain doubly linked list (`MarketOrderIdListCapsule`), with `addOrder` appending to the tail and `removeOrder`/list traversal walking from the head: [2](#0-1) 

When a taker order is matched, `matchOrder()` fetches the best price key, then repeatedly pops the head order from that price's linked list via `matchSingleOrder`, incrementing `matchOrderCount` for every maker order consumed: [3](#0-2) 

If `matchOrderCount` exceeds `MAX_MATCH_NUM`, the actuator throws `ContractValidateException("Too many matches...")`, aborting the whole transaction — analogous to the "out-of-gas revert" impact in the reported bug, except here the failure mode is an explicit exception rather than gas exhaustion. [4](#0-3) 

Placing a maker order only costs the fixed `MarketSellFee` (a small flat fee, not scaled to the number of existing orders at that price or to order size), and validation does not bound the number of orders any single account can post at a given price: [5](#0-4) 

This mirrors the RealWagmi root cause precisely: a queue/array that (1) is grown cheaply by any unprivileged user, (2) must be fully or partially traversed by other users' unrelated operations, and (3) has no cap on how many entries a single attacker can inject at the position that matters (the best price), letting the attacker deterministically force the traversal-bound check to trip for victims.

### Impact Explanation
An attacker who posts `MAX_MATCH_NUM + 1` (or more) minimal-quantity sell orders at the best price for a token pair can make any subsequent taker order attempting to consume that price level always revert with "Too many matches," because it must walk through the attacker's orders before reaching any real liquidity or filling the required amount. This:
- Denies market makers' and takers' orders from executing at the affected price/pair, freezing legitimate trading activity for the pair (invalid-state/halt impact on the exchange feature).
- Wastes bandwidth/energy of victims whose transactions revert after having been validated and broadcast.
- Costs the attacker only `N × MarketSellFee` for `N` spam orders — asymmetric and comparatively cheap versus the disruption caused, similar to the $95k-vs-$1M asymmetry in the original report.
- The attacker's spam orders remain resident in the on-chain linked list until manually canceled (`MarketCancelOrderActuator`) or fully consumed, so the DoS persists until the attacker chooses to unwind it, and can be trivially re-applied to any newly created trading pair.

### Likelihood Explanation
Likelihood is moderate-to-high on any pair with meaningful trading interest, because:
- No privileged access is required — `MarketSellAssetActuator` (`AbstractActuator`) is reachable by any account with the trivial `MarketSellFee`.
- The `MAX_MATCH_NUM` cap is a fixed protocol constant, so the exact number of spam orders needed is knowable/precomputable off-chain by an attacker.
- Order quantities can be minimized (bounded only by normal minimum-amount checks in the actuator, not shown here but presumably small), making the attack cheap per unit.

### Recommendation
- Bound the number of live orders a single account can hold at the same price for a given trading pair, or require an order-count-proportional bonding/fee that scales with queue depth at a price level, to remove the free-griefing vector.
- Instead of reverting the entire taker transaction when `MAX_MATCH_NUM` is exceeded, partially fill up to the cap and let the remainder rest as a new maker order (this avoids penalizing the taker for an attacker-inflated queue) while emitting an event so callers can react.
- Consider rate-limiting or fee-scaling repeated small `MarketSellAssetContract` calls from the same account at the same price to make queue-packing economically unattractive.

### Proof of Concept
1. Attacker selects a low-liquidity token pair (or a brand-new pair) and computes `MAX_MATCH_NUM` (compile-time constant in `MarketSellAssetActuator`).
2. Attacker submits `MAX_MATCH_NUM + 1` `MarketSellAssetContract` transactions, each for the minimum tradable quantity, all priced at what will become the best price for that pair, paying the flat `MarketSellFee` each time (`calcFee()` in `MarketSellAssetActuator.java:288-291`).
3. These orders accumulate in the pair's price-level linked list via `MarketOrderIdListCapsule.addOrder` (`chainbase/.../MarketOrderIdListCapsule.java:159-181`).
4. A victim submits a legitimate opposite-side order that needs to match against this price level. `matchOrder()` walks the list head-to-tail via `matchSingleOrder`, incrementing `matchOrderCount` per maker order consumed (`MarketSellAssetActuator.java:342-360`).
5. Once `matchOrderCount` exceeds `MAX_MATCH_NUM`, the actuator throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = ...")` (`MarketSellAssetActuator.java:357-359`), reverting the victim's transaction and consuming their bandwidth/energy without executing the trade.
6. Because the attacker's orders remain in the list, every subsequent victim order at that price fails identically until the attacker cancels the spam orders — reproducing the "packed array/queue causes deterministic DoS for asymmetric attacker cost" pattern from the source report.

  // add order to linked list
  public void addOrder(MarketOrderCapsule currentCapsule, MarketOrderStore orderStore)
      throws ItemNotFoundException {
    byte[] orderId = currentCapsule.getID().toByteArray();

    if (this.isOrderEmpty()) {
      this.setHead(orderId);
      this.setTail(orderId);
    } else {
      // tail.next = order
      // order.pre = tail
      // this.tail = order
      byte[] tailId = this.getTail();
      MarketOrderCapsule tailCapsule = orderStore.get(tailId);
      tailCapsule.setNext(orderId);
      orderStore.put(tailId, tailCapsule);

      currentCapsule.setPrev(tailId);
      orderStore.put(orderId, currentCapsule);

      this.setTail(orderId);
    }
  }
