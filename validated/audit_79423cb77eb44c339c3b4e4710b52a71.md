## Analysis

The report describes an EIP712 replay problem: caching a chain-specific value (`DOMAIN_SEPARATOR`) so that a signed message stays valid on a forked/other chain that shares the same signer. In nearcore, the closest analog is the NEP‑366 meta‑transaction (`DelegateAction`) signing scheme.

Regular NEAR transactions bind the signature to a *specific chain history* by including `block_hash` in `Transaction`/`TransactionV1`, which is checked with `check_transaction_validity_period` against the actual block ancestry of the receiving chain [1](#0-0) [2](#0-1) . That check walks the chain's own block store, so a transaction that was valid on one chain's history cannot be replayed on a network with different block ancestry, even if the account/keys are identical.

`DelegateAction` / `SignedDelegateAction`, however, is hashed and signed over only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — there is no `block_hash`, `genesis_hash`, or any other chain-identifying field in the signed payload [3](#0-2) . The same is true of the newer `DelegateActionV2` / `VersionedDelegateActionPayload` [4](#0-3) . The `SignableMessage`/`MessageDiscriminant` wrapper that domain-separates delegate actions from plain transactions only encodes a NEP number, not a network/chain identity [5](#0-4) [6](#0-5) . Verification (`apply_delegate_action`) only checks the NEP‑461 signature, `max_block_height` (an absolute height, not a chain-ancestry hash), sender match, and access-key nonce/permission — nothing chain-specific [7](#0-6) .

Notably, nearcore's own `tools/mirror` (used to replay one network's traffic onto a cloned/forked network) explicitly re-signs `Delegate`/`DelegateV2` actions with re-derived keys before forwarding them, precisely because raw replay of a `SignedDelegateAction` across networks would otherwise "just work" [8](#0-7) .

This matches the report's bug class: a signature scheme meant to authorize an action lacks any binding to the network/chain instance, so a message signed once by an account (public key + matching nonce) remains valid on any other NEAR-protocol chain the same key/nonce state exists on (e.g., a state-snapshot-derived test/shadow network, a chain split, or any environment mirroring live account state) — enabling meta-transaction replay without the signer's renewed consent, as long as `max_block_height` hasn't been exceeded and the nonce hasn't advanced on that other chain.

### Title
Cross-network replay of `SignedDelegateAction` due to missing chain-binding in the NEP-366 signing payload - (File: `core/primitives/src/action/delegate.rs`)

### Summary
`DelegateAction`/`DelegateActionV2`, the payload signed by NEAR account owners to authorize meta-transactions (relayer-submitted transactions), is hashed for signing without any chain- or genesis-specific identifier. Unlike ordinary `SignedTransaction`s, which bind freshness/validity to `block_hash` and are checked against the actual receiving chain's block ancestry, a `SignedDelegateAction` is portable to any NEAR-protocol network where the same account/key/nonce state exists.

### Finding Description
`SignedDelegateAction::verify`/`sign` compute the signature over `get_nep461_hash()`, which hashes `SignableMessage { discriminant, msg: &delegate_action }` [9](#0-8)  and [10](#0-9) . The `discriminant` only encodes an on-chain NEP number (366 or 611) [11](#0-10) , and `DelegateAction`'s fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`) contain no chain/genesis identity [12](#0-11) .

`apply_delegate_action` verifies the signature, checks `max_block_height` against the local chain's current height, checks sender match, and validates the access key/nonce — none of which is chain-ancestry aware [13](#0-12) . Contrast this with ordinary transactions, whose `block_hash` field is validated against the actual block history of the receiving chain via `check_transaction_validity_period` [14](#0-13) , which inherently prevents replay across chains with divergent histories.

### Impact Explanation
Any relayer or observer who obtains a validly signed `SignedDelegateAction` can resubmit it, wrapped in an outer transaction, on any other NEAR network/instance where the signer's account has matching `public_key` state and an access-key nonce still below the signed nonce, and the current height is still under `max_block_height`. This can trigger unauthorized execution of the delegated actions (transfers, function calls with attached deposit, key/account management) on that other network without the account owner re-consenting for that specific network — a direct unauthorized-value-movement / invalid-authorization outcome, analogous to the reported EIP712 domain-separator replay issue.

### Likelihood Explanation
Exploitability depends on a second network existing where the victim account's key/nonce state coincides with the origin network — realistic in state-mirrored test networks, shard/chain-fork scenarios, or any deployment that clones account state from a live network (the existence of the `tools/mirror` re-signing logic in this very repo shows this is an anticipated, real operational scenario) [8](#0-7) . It requires no privileged access — only capturing a `SignedDelegateAction` that a relayer already possesses/forwards, which is inherent to the meta-transaction relay flow.

### Recommendation
Bind the NEP‑366/611 signed payload to the target network, e.g. by including the genesis hash or a persistent chain identifier (analogous to `EIP712`'s recommended live `chainid` binding) in `DelegateAction`/`DelegateActionV2`'s signed fields, or by requiring `apply_delegate_action` to check a network identifier against the local chain in addition to `max_block_height` and nonce.

### Proof of Concept
1. Alice signs a `SignedDelegateAction` (via `SignedDelegateAction::sign`) authorizing `ft_transfer` to Bob, intended for submission on Network A [15](#0-14) .
2. A relayer/observer captures this `SignedDelegateAction` (it is included in the outer transaction sent to Network A's mempool/JSON-RPC).
3. On Network B — any NEAR-protocol chain where Alice's account has the same `public_key` and an access-key nonce still less than the delegate action's `nonce`, and current height ≤ `max_block_height` — the same relayer wraps the identical `SignedDelegateAction` bytes in a new outer transaction and submits it via RPC.
4. `apply_delegate_action` on Network B verifies the signature successfully (no chain-specific check exists) and executes the action, moving Alice's funds/permissions on Network B without her having authorized that specific execution [13](#0-12) .

    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),

        .into());

    if result.result.is_err() {

        // "result.result" will be return to the User as the action execution result.
