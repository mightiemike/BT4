### Title
L1 handler transactions permanently stuck as "Committed" when their block is reverted, since `revert_block` never notifies the L1 Events Provider - (File: `crates/apollo_batcher/src/batcher.rs`)

### Summary
`Batcher::revert_block` reverts a committed block's storage, state diff, and commitment, but it never calls back into the `L1EventsProviderClient` to undo the effect that committing that same block had on the L1 handler `TransactionManager`. Because `TransactionRecord::mark_committed` can only transition a transaction to `Committed` and asserts/panics if it is ever marked committed twice, any L1-to-L2 message ("L1 handler transaction") that was consumed in the reverted block remains permanently frozen in the `Committed` state in the `TransactionManager`, even though the block that consumed it no longer exists on the canonical chain.

### Finding Description
When a block is committed, the batcher calls `commit_proposal_and_block`, which notifies the L1 Events Provider via `l1_events_provider_client.commit_block(...)`: [1](#0-0) 

This flows into `apply_commit_block`, which calls `TransactionManager::commit_txs`, moving the L1 handler tx record from `Pending` to `Committed`: [2](#0-1) [3](#0-2) 

`mark_committed` explicitly asserts that a transaction is never committed twice: [4](#0-3) 

And once `Committed`, `is_validatable`/`validate_tx` will permanently reject the transaction with `AlreadyIncludedOnL2` and it can never again be staged/proposed: [5](#0-4) [6](#0-5) 

Now examine `Batcher::revert_block`, which is the counterpart operation used to roll back a committed block (e.g. on a legitimate revert/rollback request, or when catching up/state-sync needs to unwind a height): [7](#0-6) 

This function reverts the local storage (`storage_writer.revert_block`) and the commitment/global-root state (`revert_commitment`), but it contains **no call whatsoever to `self.l1_events_provider_client`**. Indeed, the entire `L1EventsProviderClient` trait exposes no revert-style method at all — only `start_block`, `get_txs`, `validate`, `commit_block`, `add_events`, `initialize`, `get_l1_events_provider_snapshot`, and `get_provider_state`: [8](#0-7) 

Consequently, if a block that consumed an L1 handler transaction is reverted, the L1 Events Provider's `TransactionManager` is left completely unaware. The transaction record remains stuck at `TransactionState::Committed`, and because `mark_committed` can never be called on it again (it would panic on "committed twice"), and because `validate_tx`/`is_validatable` treat `Committed` as terminal, there is no code path that ever moves this L1 handler transaction back to `Pending`. This is structurally identical to the Optimism M-13 bug: the withdrawal/message's validity state is durably keyed to a specific block's inclusion, and once that inclusion is invalidated (reverted / re-proposed with different content), there is no mechanism to re-bind the message to a new valid inclusion — it is permanently excluded.

### Impact Explanation
Any legitimate L1→L2 message (e.g., a token bridge deposit, or any contract call triggered from L1) whose consuming block is reverted will never be executed on L2 again. Since the transaction manager also never re-adds/re-proposes it (the underlying L1 event was already scraped and merged into this now-"permanently committed" record, and re-scraping the same L1 log does not create a new record because `add_tx` treats an existing hash as already recorded), the L1 message and any associated funds/state effects are permanently stuck: they can't be re-included in a future block, and there is no user-facing recovery mechanism since consumption happened purely on the L2 sequencer/L1-events-provider side. This satisfies the "permanent freezing of funds" / inability of the network to correctly re-confirm a legitimate transaction criteria.

### Likelihood Explanation
`revert_block` is a normal, expected operational path in this codebase (reachable via legitimate consensus/administrative revert flows or state-sync catch-up unwinding, not just malicious actors), and its docstring even states it "will panic if there is a storage failure to revert the block," indicating it is a supported, exercised code path rather than an exotic corner case. Any block revert that happened to consume at least one L1 handler transaction will trigger this bug deterministically — there is no probabilistic or adversarial precondition required, unlike the original Optimism finding, which needed a malicious/compromised proposer. This makes the likelihood arguably higher than the original finding, since it requires only a normal revert operation rather than a leaked proposer key.

### Recommendation
Add a corresponding revert notification to the `L1EventsProviderClient` interface (e.g. `revert_block(height)`), and have `Batcher::revert_block` call it symmetrically with `commit_proposal_and_block`'s call to `commit_block`. On the provider side, add a `TransactionManager::revert_txs` (or similar) that transitions previously-`Committed` (and `Rejected`) transaction records for that height back to `Pending`, re-inserting them into the `proposable_index` so they become eligible for inclusion in a future block again.

### Proof of Concept
1. An L1 handler transaction `T` (L1→L2 message) is scraped and added to the `L1EventsProvider`'s `TransactionManager` as `Pending`.
2. A block at height `H` proposes and commits `T`; `commit_proposal_and_block` calls `l1_events_provider_client.commit_block([T], [], H)`, which calls `TransactionManager::commit_txs`, marking `T` as `Committed` (`transaction_record.rs:50-60`).
3. For any reason (bug fix, consensus fault-recovery, state-sync rollback), `Batcher::revert_block` is invoked for height `H` (`batcher.rs:1426-1457`). Storage and commitment are reverted, but no call is made to the L1 Events Provider.
4. `T`'s record in the `TransactionManager` remains `Committed`.
5. A new block is later built at height `H` (or later) with different content (not including `T`). `validate_tx`/`get_txs` for `T` will always report `AlreadyIncludedOnL2` (`transaction_manager.rs:116-145`), so `T` can never be proposed or validated again, even though it was never actually finalized on the canonical L2 chain.

    // This function will panic if there is a storage failure to revert the block.
    pub async fn revert_block(&mut self, input: RevertBlockInput) -> BatcherResult<()> {
        info!("Reverting block at height {}.", input.height);
        let height = self.get_height_from_storage()?.prev().ok_or(
            BatcherError::StorageHeightMarkerMismatch {
                marker_height: BlockNumber(0),
                requested_height: input.height,
            },
        )?;

        if height != input.height {
            return Err(BatcherError::StorageHeightMarkerMismatch {
                marker_height: height.unchecked_next(),
                requested_height: input.height,
            });
        }

        if let Some(height) = self.active_height {
            info!("Aborting all work on height {} due to a revert request.", height);
            self.abort_active_height().await;
        }

        // Wait for the revert commitment to be completed before reverting the storage.
        self.revert_commitment(height).await;

        self.storage_writer.revert_block(height);
        BUILDING_HEIGHT.decrement(1);
        GLOBAL_ROOT_HEIGHT.decrement(1);
        REVERTED_BLOCKS.increment(1);
        Ok(())
    }

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();
        }
        for &tx_hash in rejected_txs {
            self.with_record(tx_hash, |r| r.mark_rejected()).expect(
                "Rejected L1 handler tx has no record. Unreachable: all L1 handler txs in a \
                 committed block were validated as known (validation rejects unknown hashes), \
                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",
            );
        }
    }

        // Can't return error because committing only part of a block leaves the provider in an
