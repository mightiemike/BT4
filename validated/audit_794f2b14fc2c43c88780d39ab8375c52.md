### Title
ECDSA Signature Malleability Enables Multisig Weight Double-Counting in `ValidateMultiSign` Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract, reachable by any smart contract via a broadcast `TriggerSmartContract` transaction, deduplicates signatures by comparing raw signature bytes rather than solely by recovered signer address. Because ECDSA signatures are inherently malleable (for any valid `(r, s, v)` there exists a second valid `(r, N-s, v')` that recovers to the same address), an attacker holding a single legitimate signature from a key holder can derive a second, byte-distinct signature for the same signer and same message hash, causing that signer's weight to be counted twice toward the multisig threshold.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` iterates over the supplied signature array and tracks already-processed entries in `executedSignList`: [1](#0-0) 

The relevant logic is:
```
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
```
When `recoveredAddr` has already been seen, the code only skips (`continue`) if the exact same `sign` bytes were already seen. If the address matches but the raw signature bytes differ, execution falls through and the weight for that address is added again.

Signature recovery is performed by `recoverAddrBySign`, which builds an `ECDSASignature` from raw `r`, `s`, `v` components and only validates that `r` and `s` are within `[1, N-1]` — it does **not** enforce canonical (low-`s`) form: [2](#0-1) [3](#0-2) 

Because both `s` and `N - s` (with the complementary recovery id / `v`) pass `validateComponents()` and both recover to the same address, an attacker can trivially compute the malleable twin of any signature they observe (no private key needed) and submit it as a "second, independent" signature for the same signer. `Rsv.fromSignature` performs no canonicalization or malleability check either: [4](#0-3) 

This is the same bug class described in the external report (`ECDSA.recover` accepting malleable/alternate encodings for the same signer without a canonical-form check), manifesting here not via OpenZeppelin's Solidity library but via java-tron's own precompiled contract that mirrors the same signature-validation pattern.

By contrast, the analogous transaction-level multisig check `TransactionCapsule.checkWeight` explicitly guards against this by deduplicating on the **recovered address** (post-fork `VERSION_4_7_1`, it maps to `encode58Check(address)` specifically to avoid this class of issue): [5](#0-4) 
The TVM-level `ValidateMultiSign` precompile does not receive the same fix and still keys its de-dup on the combined `(address, raw-signature-bytes)` tuple, retaining the double-count weakness.

### Impact Explanation
`ValidateMultiSign` is the on-chain building block smart contracts use to implement multisig / permission checks (`validatemultisign` TVM builtin). Any contract that relies on this precompile to gate privileged actions (e.g., custodial wallets, DAO/multisig-style contracts, exchange withdrawal approval contracts) can have its signer-weight threshold satisfied with fewer independent legitimate approvers than intended, because a single signer's one authorization can be "duplicated" into two weight-contributing entries via a derived malleable signature. This is an unauthorized-account-operation / accounting-corruption class issue: it can let an attacker (who only needs to observe one valid signature, not steal a private key) push `totalWeight` over `permission.getThreshold()` when the true number of distinct authorizing keys is smaller, enabling unauthorized execution of the guarded contract logic (e.g., asset transfer, permission change) that the contract author believed required N independent signers.

### Likelihood Explanation
Exploitability requires: (1) a contract that uses `ValidateMultiSign` with a multi-key permission where the attacker already possesses (or can observe, e.g. from a previous broadcast or off-chain disclosure) one valid signature from a legitimate signer, and (2) that a single signer's weight plus its malleable duplicate is sufficient to reach the threshold together with other signatures the attacker controls or also possesses. This is not reachable purely by an anonymous party with zero signatures, but the underlying computation (deriving the malleable twin) requires no cryptographic secret — only arithmetic on public `(r, s)` and re-deriving `v`. Given that any DApp author who builds an N-of-M scheme atop this precompile with a signer weight distribution where 2×(one signer's weight) ≥ threshold would be silently vulnerable, likelihood is real but contract-usage-pattern dependent (medium).

### Recommendation
In `ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (as `TransactionCapsule.checkWeight` does post-fork), not by the combined `(address, signature-bytes)` pair — i.e., remove the inner `matrixContains(executedSignList, sign)` fallthrough and instead `continue` (or reject) whenever the address has already contributed weight, regardless of the raw signature bytes. Additionally, enforce canonical low-`s` signatures in `ECDSASignature.validateComponents` (reject `s > N/2`, matching Bitcoin/Ethereum's canonical-signature convention) so that malleable duplicates cannot be constructed from an already-accepted signature in the first place.

### Proof of Concept
1. Set up an account with an `Active` permission containing key `K1` with weight `W1` and threshold `T` such that `2*W1 >= T` but `W1 < T` (i.e., a single signer alone cannot satisfy the threshold, but the same signer counted twice can).
2. Key holder `K1` signs `hash = sha256(address || permissionId || data)` once, producing `sig1 = (r, s, v)`.
3. Compute the malleable twin without any private key: `s' = N - s`, `v' = v XOR 1` (adjust to the complementary recovery id) — both `sig1` and `sig2 = (r, s', v')` recover to `K1`'s address.
4. Call the `ValidateMultiSign` precompile (via `TriggerSmartContract`) with `signatures = [sig1, sig2]`.
5. In `execute`, the first iteration adds weight `W1` for `K1`. On the second iteration, `recoveredAddr` (`K1`) is already in `executedSignList`, but `sign` (the merged `recoveredAddr||sig2` bytes) differs from the first entry's `recoveredAddr||sig1`, so `matrixContains(executedSignList, sign)` is `false` and the `continue` is skipped — `W1` is added a second time, making `totalWeight = 2*W1 >= T`, and the call returns `true` (threshold satisfied) despite only one legitimate signer having actually authorized the action.

  private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }

  public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;
  }
