### Title
Validator reward overwrites protocol-treasury reward when treasury account is also a validator, causing minted-supply / credited-reward divergence - ([File: chain/epoch-manager/src/reward_calculator.rs])

### Summary
`RewardCalculator::calculate_reward` uses a single `HashMap<AccountId, Balance>` (`res`) to record both the fixed protocol-treasury cut and every individual validator's reward, keyed only by `AccountId`. If the `protocol_treasury_account` is (or later becomes) a staking validator included in `validator_block_chunk_stats`, its treasury entry is silently overwritten by its validator-reward entry, exactly analogous to the reported Olympus bug where a single owner-controlled mapping is shared between two conceptually distinct "reward streams" (internal vs. external), causing one stream's accounting to clobber the other.

### Finding Description
`calculate_reward` first inserts the treasury credit into the shared map: [1](#0-0) 

Then, for every validator that produced blocks/chunks/endorsements in the epoch, it inserts (not adds) that validator's reward into the *same* map keyed by `account_id`: [2](#0-1) 

`res.insert(account_id, reward)` at line 142 overwrites any prior entry for that `account_id`. Since `self.protocol_treasury_account` and a validator's `account_id` share exactly the same `AccountId` namespace, if the treasury account itself is present in `validator_block_chunk_stats` (i.e., it is staking and thus a validator that epoch), its treasury-reward entry inserted at line 84 is silently replaced by its own validator reward computed later in the loop.

Meanwhile, `epoch_actual_reward` (the value that becomes `minted_amount`, and ultimately drives `new_total_supply`) is accumulated independently and correctly includes both contributions:
- `epoch_actual_reward` starts at `epoch_protocol_treasury` (line 90)
- then `epoch_actual_reward = epoch_actual_reward.checked_add(reward)` for every validator, including the treasury account acting as a validator (line 143)

So `epoch_actual_reward` (minted amount) legitimately equals `treasury_reward + validator_reward_for_treasury_account + other validators' rewards`, but the returned `res` map — the structure actually used to credit account balances — has lost the `treasury_reward` portion for that account (only the validator-reward portion remains under that key).

This map is later consumed to credit `Account::locked` balances for each account in `chain/epoch-manager` / `runtime/runtime/src/lib.rs`'s validator-accounts-update path, which iterates the rewards map and adds `reward` to `account.locked()`: [3](#0-2) 

Because the treasury account's entry in the map only reflects the validator-reward figure (having lost the treasury figure to the overwrite), the `treasury_reward` amount that was counted in `minted_amount` is never credited to any account. This breaks the supply-conservation invariant documented in the protocol spec — minted amount is supposed to equal the sum of credited amounts (`treasury + Σ validator rewards`): [4](#0-3) [5](#0-4) 

### Impact Explanation
This is a direct analog of the reported bug class: two logically distinct accounting entries (treasury reward vs. validator reward) share one mapping keyed by the same identifier, and a later write silently clobbers an earlier one. The concrete protocol impact is:
- `new_total_supply = prev.total_supply + minted_amount - balance_burnt` uses `minted_amount = epoch_actual_reward`, which double-counts the treasury reward in the mint accounting but the corresponding tokens are never actually credited to any account balance — the tokens are effectively "minted" into total supply but never appear on any account, i.e., permanently unaccounted/lost issuance, a genuine invariant violation (supply says X was minted, but only X − treasury_reward is reachable/spendable by any account). This matches the class of "supply inflation / permanently frozen funds" harms called out as in-scope.
- Because `EpochManager::calculate_reward` executes deterministically the same way on every honest node (it operates purely on already-agreed-upon block/stake stats), all nodes compute the identical (buggy) result, so this does not itself cause a fork; the impact is a supply-accounting invariant violation rather than a cross-node divergence.

### Likelihood Explanation
Reachability requires the `protocol_treasury_account` (a genesis-configured, typically foundation-controlled account, e.g. `"near"`) to also submit a `Stake` action and become an active validator that epoch. This is not achievable by an arbitrary unprivileged third-party transaction signer unless they control the treasury account's keys — the treasury account is fixed at genesis and is not attacker-choosable. Because the bug is only triggered when the specific treasury account self-stakes, it is a plausible but narrow/config-dependent trigger rather than one reachable from any arbitrary submitted transaction. This significantly limits likelihood despite the code path being real and unguarded (there is no check preventing `protocol_treasury_account` from being included in the validator set, unlike the Solidity report's admin-added-duplicate-token scenario, which is fully owner-controlled).

### Recommendation
Track the treasury credit and per-validator rewards in separate maps (or add rather than insert/overwrite when a key collision with `protocol_treasury_account` occurs), then merge the two by summation before returning, e.g.:
```rust
*res.entry(account_id).or_insert(Balance::ZERO) = 
    res.get(&account_id).copied().unwrap_or(Balance::ZERO).checked_add(reward).unwrap();
```
instead of `res.insert(account_id, reward)`, ensuring the treasury account's combined reward (treasury cut + any validator reward) is preserved and that `epoch_actual_reward` always equals the sum of all entries in the returned map.

### Proof of Concept
1. Configure genesis so `protocol_treasury_account = "treasury.near"`.
2. Have `treasury.near` submit a `Stake` action with nonzero stake and become part of the active validator set for epoch `T`.
3. At the end of epoch `T`, `EpochManager` calls `RewardCalculator::calculate_reward` (`chain/epoch-manager/src/reward_calculator.rs:51`) with `validator_block_chunk_stats` containing `treasury.near`.
4. Trace execution:
   - Line 84: `res.insert("treasury.near", epoch_protocol_treasury)`.
   - Loop iteration where `account_id == "treasury.near"`: line 142 `res.insert("treasury.near", validator_reward)` overwrites the treasury entry.
   - Line 143: `epoch_actual_reward` still includes both `epoch_protocol_treasury` (added at line 90) and `validator_reward` (added at line 143) — i.e., `epoch_actual_reward` is correct, but `res.get("treasury.near")` now only returns `validator_reward`, permanently losing `epoch_protocol_treasury` from the credited-rewards map.
5. When `update_validator_accounts` (`runtime/runtime/src/lib.rs:1748`) applies `res` to account balances, `treasury.near`'s `locked` balance increases by only `validator_reward`, not `validator_reward + epoch_protocol_treasury`, while `minted_amount` (used for `new_total_supply`) reflects the full sum — an unrecoverable discrepancy between minted supply and credited balances.
