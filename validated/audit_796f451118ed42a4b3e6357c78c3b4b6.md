### Title
Open redirect via protocol-relative host swap bypassing `sanitizeRedirectUrl` allowlist - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts and identical shopify-app-react-router copy)

### Summary
`sanitizeRedirectUrl`/`isSafe` are meant to constrain a caller-supplied redirect target to the app's own domain, but the double-slash checks are applied to the wrong values: `FILE_URI_MATCH` runs on the raw input string and `INVALID_RELATIVE_URL` runs on the *parsed* `url.pathname`, never on `url.host`. A protocol-relative or backslash-relative input such as `//evil.example.com/steal` is resolved by `new URL(redirectUrl, domain)` into a URL whose host is `evil.example.com`, and none of the existing checks catch this, so `isSafe` returns `true` and `sanitizeRedirectUrl` returns a URL pointing off-domain.

### Finding Description
`isSafe` in `validate-redirect-url.ts` performs these checks, in order: [1](#0-0) 

1. `FILE_URI_MATCH.test(redirectUrl)` — checks the **raw string** for a literal triple slash `///`. `//evil.example.com/steal` contains only two consecutive slashes, so this does not match.
2. `url = new URL(redirectUrl, domain)` — WHATWG URL parsing treats a leading `//` as protocol-relative: the resulting `url.host` becomes `evil.example.com` while `url.protocol` is inherited from the base (`https:`). The same happens for `\\evil.example.com/steal`, since backslashes are normalized to slashes for special schemes.
3. `INVALID_RELATIVE_URL.test(url.pathname)` — this is checked against the **parsed pathname**, e.g. `/steal`, not against `url.host` or the raw input, so it never detects the host swap that already occurred in step 2.
4. Protocol checks pass because `url.protocol` is `https:` (inherited from the base domain).

There is no check anywhere in `isSafe` comparing `url.host`/`url.hostname` against the `domain` argument's host. As a result, any caller that passes attacker-controlled input into `sanitizeRedirectUrl(config.appUrl, userInput)` — for example `renderAppBridge`, which does `sanitizeRedirectUrl(config.appUrl, redirectTo.url)` — can be redirected to `evil.example.com` if the `redirectTo.url` value originates from a request-controlled parameter. [2](#0-1) 

### Impact Explanation
This is an open redirect: an app running in the authenticated admin/embedded context can be made to redirect (or `window.open`) to attacker-controlled infrastructure. Because the redirect occurs within an authenticated session context (embedded admin iframe / app bridge script), this matches Shopify's open-redirect impact class — it can be used for phishing, or, if URL fragments/Referer headers carry session tokens or codes, for token/credential leakage to the attacker's domain.

### Likelihood Explanation
No privileged access is required — only the ability to influence the string passed as `redirectUrl`/`redirectTo.url` into `sanitizeRedirectUrl`. The check is defeated with default configuration (default `requireSSL`), using ordinary crafted strings (`//evil.example.com/steal` or `\\evil.example.com/steal`); no secrets or non-default config are needed. The bug is deterministic and 100% reproducible via a unit test.

I was unable to fully confirm, within the available index, which specific end-user-facing entry point(s) pass raw, attacker-controlled query-string values directly into `sanitizeRedirectUrl` (e.g., whether `redirectTo.url` in `renderAppBridge` call sites is ever sourced straight from a request parameter without additional validation) — this would need to be verified in a live/full checkout of the repo before treating downstream exploitability as fully confirmed. The vulnerability in `isSafe`/`sanitizeRedirectUrl` itself, however, is confirmed by direct code inspection.

### Recommendation
After parsing with `new URL(redirectUrl, domain)`, explicitly compare `url.host` (or `url.origin`) against the `domain` argument's host/origin, and reject if they differ — rather than relying solely on regex checks against the raw string or the parsed pathname. Additionally, run `INVALID_RELATIVE_URL`/protocol-relative detection against the raw `redirectUrl` (before parsing) to catch `//` and `\\` prefixes explicitly.

### Proof of Concept
```ts
import {sanitizeRedirectUrl} from '../validate-redirect-url';

const APP_URL = 'https://my-app.com';

test('open redirect via protocol-relative URL', () => {
  const result = sanitizeRedirectUrl(APP_URL, '//evil.example.com/steal');
  expect(result.host).not.toBe(new URL(APP_URL).host); // FAILS: result.host === 'evil.example.com'
});

test('open redirect via backslash-relative URL', () => {
  const result = sanitizeRedirectUrl(APP_URL, '\\\\evil.example.com/steal');
  expect(result.host).not.toBe(new URL(APP_URL).host); // FAILS: result.host === 'evil.example.com'
});
```
Both assertions fail as written (i.e., `result.host` equals `evil.example.com`), demonstrating that `isSafe` incorrectly accepts these inputs and `sanitizeRedirectUrl` returns a URL pointing off the app's domain.

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
