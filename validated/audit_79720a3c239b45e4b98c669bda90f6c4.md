### Title
Unclosed native DB iterators in `TronStoreWithRevoking` allow unprivileged-user-triggerable native resource exhaustion - (File: chainbase/src/main/java/org/tron/core/db/TronStoreWithRevoking.java)

### Summary
`TronStoreWithRevoking.iterator()` wraps the underlying `revokingDB.iterator()` call with `Iterators.transform(...)` but never closes the returned native iterator, unlike the same class's `isNotEmpty()` method which explicitly closes it via `closeJniIterator()`. [1](#0-0) [2](#0-1) 

### Finding Description
`revokingDB.iterator()` resolves through `Chainbase.iterator()` → `SnapshotRoot.iterator()` → `db.iterator()`, which returns a `StoreIterator` (LevelDB) or `RockStoreIterator` (RocksDB) — both explicitly documented in the codebase as wrapping **native resources that must be closed**: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The `RocksIterator`/LevelDB `DBIterator` returned holds a native handle (and, in RocksDB's case, pins a snapshot) that is not released by garbage collection and must be explicitly `close()`d — this is the exact bug class described in the source report (`GetStakeRemovalsForBlock` etc. in the Allora emissions Keeper not closing collection iterators).

Multiple production store methods call `Streams.stream(iterator())` and never close the iterator returned by `TronStoreWithRevoking.iterator()`:
- `AssetIssueStore.getAllAssetIssues()` [7](#0-6) 
- `WitnessStore.getAllWitnesses()` [8](#0-7) 
- `ExchangeStore.getAllExchanges()` [9](#0-8) 
- `CodeStore.getTotalCodes()` and `TronStoreWithRevoking.size()` [10](#0-9) [11](#0-10) 

These are called directly from `Wallet` methods that are exposed via public, **unauthenticated** HTTP/gRPC endpoints:
- `getAssetIssueList()` / `getAssetIssueList(offset, limit)` / `getAssetIssueByAccount()` / `getAssetIssueByName()` / `getAssetIssueListByName()` [12](#0-11) [13](#0-12) 
- registered as `/wallet/getassetissuelist`, `/wallet/getpaginatedassetissuelist`, `/wallet/getassetissuebyaccount`, `/wallet/getassetissuebyname`, `/wallet/listwitnesses`, `/wallet/getpaginatednowwitnesslist`, `/wallet/getpaginatedexchangelist` [14](#0-13) 

Each invocation of these endpoints allocates a fresh native RocksDB/LevelDB iterator via `getRocksIterator`/`getDBIterator` that is never explicitly closed by the calling code path. The codebase's own inline documentation on `iterator()` in `RocksDbDataSourceImpl`, `LevelDbDataSourceImpl`, and `DBInterface` repeatedly warns: *"the returned iterator holds native resources and MUST be closed after use to prevent memory leaks"* [15](#0-14)  — confirming the developers are aware unclosed iterators are a real resource-leak vector, yet this particular path bypasses that discipline.

### Impact Explanation
An unprivileged, unauthenticated remote user can repeatedly call public read-only HTTP/gRPC APIs (e.g., `/wallet/getassetissuelist`, `/wallet/listwitnesses`, `/wallet/getpaginatedexchangelist`) to continuously allocate native RocksDB/LevelDB iterators that are never released. Over sustained repeated calls this leaks native memory/file handles and, for RocksDB, pins old SST files/snapshots, preventing compaction cleanup — degrading node performance and potentially leading to memory exhaustion or node crash (denial of service) on a full node. This falls under the "underpriced-public-work" / node-availability impact category, since these endpoints are free, unauthenticated, and can be invoked at high frequency without any resource cost proportional to the leak they cause.

### Likelihood Explanation
Likelihood is high: the affected endpoints are default public HTTP/gRPC APIs on every full node (no special privileges, keys, or fees required), and the leak occurs on every single call. Full iteration of the store (`Streams.stream(iterator())`) does exhaust the iterator via `hasNext()`, but nothing in the reviewed code path (`Iterators.transform`, `Streams.stream`) triggers `close()` on the underlying `AutoCloseable`/`Closeable` `DBIterator`, so the native handle leak occurs on every call regardless of dataset size.

### Recommendation
Modify `TronStoreWithRevoking.iterator()` (and `size()`) to ensure the underlying native `DBIterator` is closed after iteration completes or when an exception occurs, e.g., by wrapping the iteration in a try-with-resources block and returning a closing-aware iterator, or by exhaustively iterating and closing internally rather than exposing a transformed unclosed iterator to callers. Audit all other call sites of `revokingDB.iterator()` / `db.iterator()` for the same pattern and add `try (DBIterator iterator = ...) { ... }` semantics consistently.

### Proof of Concept
1. Start a full node exposing the default HTTP API.
2. Repeatedly send `GET /wallet/getassetissuelist` (or `/wallet/listwitnesses`, `/wallet/getpaginatedexchangelist`) in a loop, e.g. thousands of times in a short period.
3. Each call triggers `Wallet.getAssetIssueList()` → `AssetIssueStore.getAllAssetIssues()` → `TronStoreWithRevoking.iterator()` → `Chainbase.iterator()` → `SnapshotRoot.iterator()` → `RocksDbDataSourceImpl.iterator()`/`LevelDbDataSourceImpl.iterator()`, allocating a native `RocksIterator`/LevelDB `DBIterator` that is never explicitly `close()`d in this call chain.
4. Monitor native memory (RSS) / open native handles of the node process; observe continual growth correlated with the number of API calls, since the JVM garbage collector does not deterministically finalize native resources held by the LevelDB/RocksDB JNI iterator wrappers.

  @Override
  public boolean isNotEmpty() {
    Iterator iterator = revokingDB.iterator();
    boolean value = iterator.hasNext();
    // close jni
    if (value) {
      closeJniIterator(iterator);
    }

    return value;
  }

  private void closeJniIterator(Iterator iterator) {
    if (iterator instanceof DBIterator) {
      try {
        ((DBIterator) iterator).close();
      } catch (IOException e) {
        logger.error("Close jni iterator.", e);
      }
    }
  }
