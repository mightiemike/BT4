### Title
Forced TRX balance injection via `SELFDESTRUCT` bypasses "zero balance" guard invariants in TVM contracts - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
The external report describes a class of bug where a contract gates critical logic on a token-balance check (`balance != 0`), assuming that balance can only become non-zero through the contract's intended, permissioned flow. An unprivileged attacker defeats this assumption by force-depositing tokens directly to the contract's address, bypassing any application-level entry point and its associated checks. In java-tron's TVM, the `SELFDESTRUCT` opcode (`suicide`/`suicide2` in `Program.java`) provides an equivalent unprivileged mechanism: any user can deploy a trivial contract, fund it with TRX, then self-destruct it targeting an arbitrary victim contract address, forcibly crediting that address's TRX balance without invoking the victim's payable functions, fallback, or any `require`/guard logic.

### Finding Description
`Program.suicide()` and `Program.suicide2()` transfer the calling contract's entire remaining balance to an arbitrary `obtainerAddress` supplied by the caller in the bytecode, using `MUtil.transfer` to directly manipulate the account balance in the state repository rather than routing through the target's contract code. [1](#0-0) 

Because this is a direct state mutation (`getContractState().addBalance` / `MUtil.transfer`) rather than a call into the target contract, any TVM contract deployed on java-tron that gates functionality on a check such as `require(address(this).balance == 0)` (to prevent premature use before real funding arrives) or similar "has the contract truly received funds yet" logic can have its balance bumped by an attacker with no interaction with, or consent from, the target contract at all. `canSuicide()`/`canSuicide2()` only gate the operation on the *source* contract's frozen/delegated resource state — they impose no restriction whatsoever on the *target* address of the transfer. [2](#0-1) 

This is the same root cause as the TribeRedeemer finding: a balance check intended to gate a function until real, application-controlled deposits occur can be satisfied by an unprivileged party through an out-of-band balance-mutation primitive (there: plain ERC20 `transfer`; here: `SELFDESTRUCT`).

### Impact Explanation
Any TVM smart contract on the TRON network that relies on `address(this).balance == 0` (or similar zero/threshold checks on its own balance) to gate premature execution, close/lock states, or trigger "is funded" logic can be manipulated by an unprivileged attacker who deploys and self-destructs a helper contract targeting the victim address. Depending on the victim contract's logic, this can enable premature redemption/distribution logic to execute with insufficient funds (mirroring the TribeRedeemer scenario), corrupt accounting invariants that assume balance changes only occur through the contract's own payable entry points, or trigger unintended state transitions. This does not compromise the TRON protocol itself but is a systemic footgun affecting any deployed contract relying on such an assumption, consistent with "asset or accounting corruption" via the TVM's protocol-level execution semantics.

### Likelihood Explanation
Likelihood is low-to-medium, matching the original disputed/Medium severity determination. It requires: (1) a target contract that actually gates behavior on a zero/threshold self-balance check, (2) an attacker willing to deploy and fund a throwaway contract for the self-destruct, and (3) some other party trusting the vulnerable contract's guard to be enforceable. `SELFDESTRUCT` targeting arbitrary addresses is unrestricted for any user and requires no special privilege — it's a basic, always-available TVM primitive, so the attack itself is trivial to execute; the limiting factor is solely whether a given victim contract's logic is written to depend on this invariant.

### Recommendation
This is inherent EVM/TVM semantics (mirrors Ethereum's well-known "forced ether" issue) and is not something to "fix" in the TVM itself without breaking `SELFDESTRUCT` semantics broadly. Documentation/guidance for TVM contract developers should explicitly warn that `address(this).balance` (and TRC10 balances via `transferAllToken` in suicide) can be incremented outside of the contract's own payable functions via `SELFDESTRUCT`, and that contracts must not treat "balance != 0" or similar balance-based checks as a reliable gate for "funds arrived through my intended flow." Contracts should instead track internally-accounted deposits (e.g., an explicit "funded" flag set by a privileged/administrative call) rather than relying on the raw on-chain balance for such invariants.

### Proof of Concept
1. Deploy `VictimContract` with logic such as:
   ```solidity
   function redeem() external {
       require(address(this).balance != 0, "ZERO_BALANCE"); // guard against premature redemption
       // ... redeem TRX pro-rata based on address(this).balance ...
   }
   ```
   before the real reward/fund provider has sent any TRX to it.
2. Deploy `Attacker`:
   ```solidity
   contract Attacker {
       constructor() payable {}
       function attack(address victim) external {
           selfdestruct(payable(victim));
       }
   }
   ```
   funded with a trivial amount of TRX (e.g., 1 sun).
3. Call `Attacker.attack(victimAddress)`. This triggers `Program.suicide()`/`suicide2()`, which calls `MUtil.transfer` to directly add the attacker contract's balance to `VictimContract`'s balance in the state repository — no call into `VictimContract`'s code occurs. [3](#0-2) 
4. `VictimContract`'s `balance != 0` guard is now bypassed, and any user (potentially the attacker themselves, or a duped legitimate user) can call `redeem()` prematurely, causing incorrect pro-rata reward computation exactly as described for the TribeRedeemer contract.

    int ADDRESS_SIZE = VMUtils.getAddressSize();
    if (FastByteComparisons.compareTo(owner, 0, ADDRESS_SIZE, obtainer, 0, ADDRESS_SIZE) == 0) {
      // if owner == obtainer just zeroing account according to Yellow Paper
      getContractState().addBalance(owner, -balance);
      byte[] blackHoleAddress = getContractState().getBlackHoleAddress();
      if (VMConfig.allowTvmTransferTrc10()) {

        MUtil.transferAllToken(getContractState(), owner, blackHoleAddress);

      createAccountIfNotExist(getContractState(), obtainer);
      try {

        if (VMConfig.allowTvmConstantinople()) {
          throw new TransferException(
              "transfer all token or transfer all trx failed in suicide: %s", e.getMessage());
        }
        throw new BytecodeExecutionException("transfer failure");
      }
    }
