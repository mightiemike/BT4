## Finding: Replay-verify integrity check silently skips state-checkpoint hash validation

The strongest local candidate directly traces to a self-documented gap in the code itself, not a projection from the Solana report.

### Title
`TransactionOutput::ensure_match_transaction_info` omits state-checkpoint hash verification, letting replay/state divergence go undetected - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function that validates a freshly recomputed `TransactionOutput` (from local re-execution) against the authenticated, on-disk `TransactionInfo` during replay/backup verification. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check the state checkpoint hash (nor the hot-state / `position_state_checkpoint_hash`), as acknowledged directly in a `TODO(trading-native)` comment in the code.

### Finding Description [1](#0-0) 

The function verifies:
- `status` matches expected status derived from `txn_info` [2](#0-1) 
- `gas_used` matches [3](#0-2) 
- write-set hash matches `txn_info.state_change_hash()` [4](#0-3) 
- event root hash matches `txn_info.event_root_hash()` [5](#0-4) 

But the function returns `Ok(())` immediately after, with the comment stating explicitly:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [6](#0-5) 

This function is used by exactly the tooling the comment names — `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` — both of which invoke `ensure_match_transaction_info` as their pass/fail gate for confirming a locally re-executed transaction matches what is committed on-chain.

### Impact Explanation
Replay-verify is the primary safety mechanism for detecting non-determinism, VM bugs, or storage corruption that would otherwise cause a silent chain split (hard-fork-class divergence) between validators, or between validators and full nodes/state-sync targets. Because the state-checkpoint hash (the root that commits the actual persisted state trie/Merkle root, and reportedly a new "trading-native" state root component) is excluded from the comparison, a state root divergence introduced by a bug in write-set application, hot-state computation, or state-checkpoint construction would not be flagged by replay-verify even though the committed ledger state differs from the correct VM result. This directly matches the "Committed state that differs from the correct VM result" and "Hard-fork-only divergence during commit, replay, restore" impact categories, because the verification tool that is supposed to catch such divergence is blind to it.

### Likelihood Explanation
This is not a hypothetical: the gap is acknowledged in-code as a known limitation tied to an in-progress feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`). Any bug affecting state-checkpoint/hot-state root computation during this transitional period (execution ↔ storage handoff for checkpoint hashes) would go undetected by `replay_on_archive` and the Aptos debugger's replay checks, since those are the exact tools this comparator gates.

### Recommendation
Add validation of the state checkpoint hash (and hot-state/`position_state_checkpoint_hash` when applicable) inside `ensure_match_transaction_info` before enabling or shipping `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, so that replay-verify and the debugger's replay path fail loudly on any state-root divergence rather than only checking write-set/event hashes.

### Proof of Concept
Not independently exploitable as an attacker-triggered PoC — this is a coverage gap in a verification tool rather than a state-corrupting bug on its own. Concretely: any code path that computes an incorrect state-checkpoint/hot-state root during replay (e.g. a hypothetical bug in hot-state write-set materialization, as seen being introduced nearby in `execution/executor/src/workflow/do_get_execution_output.rs` around `convert_write_sets_to_v1`/hotness handling) would still pass `ensure_match_transaction_info` and be reported as a successful replay by `storage/db-tool/src/replay_on_archive.rs`, because that function never compares `txn_info.state_checkpoint_hash()` (or hot-state root) to the recomputed value.

**Caveat:** I could not fully trace how `position_state_checkpoint_hash` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are computed/gated (feature appears to be in-progress/unshipped per the TODO), so I cannot confirm whether this gap is currently reachable on mainnet or only in a not-yet-enabled code path. This uncertainty should be verified with a full Devin session before treating this as an active, exploitable mainnet issue.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
```
