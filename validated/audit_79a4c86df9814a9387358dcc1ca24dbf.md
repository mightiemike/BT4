### Title
Publish-vs-shutdown race in `NativeMessageQueue` causes NPE/undelivered events under concurrent block/transaction trigger publishing - (File: `framework/src/main/java/org/tron/common/logsfilter/nativequeue/NativeMessageQueue.java`)

### Summary
`NativeMessageQueue.publishTrigger()` and `NativeMessageQueue.stop()` both read/write the shared `publisher` and `context` fields, but the null/closed check in `publishTrigger()` is performed outside the `synchronized(this)` block that guards the actual send, while `stop()` closes and nulls those fields without holding that same lock consistently before nulling `instance`. [1](#0-0) 

### Finding Description
`publishTrigger(data, topic)` first checks `Objects.isNull(publisher) || Objects.isNull(context) || context.isClosed()` and only then enters a `synchronized(this)` block to call `publisher.sendMore(topic)` / `publisher.send(data)`. [2](#0-1)  Meanwhile `stop()` calls `publisher.close(); publisher = null;` and `context.close(); context = null;` without taking the `synchronized(this)` monitor for those writes, and only wraps the static singleton reset (`instance = null`) in a class-level lock. [3](#0-2) 

This creates a classic check-then-act TOCTOU race, directly analogous to the reported Broker bug where `Publish`/`Broadcast` races `<-ctx.Done()` shutdown without a shared mutex: a caller can pass the null/closed check in `publishTrigger()`, then have another thread invoke `stop()` (called from `EventPluginLoader.stopPlugin()`) which nulls `publisher`/closes `context` before the synchronized send executes, causing a `NullPointerException` inside the `synchronized` block (since `publisher` is now `null` when `sendMore`/`send` execute) or an operation on a closed ZMQ socket, instead of a clean, predictable error. [4](#0-3) 

`publishTrigger` is invoked from every trigger-posting path in `EventPluginLoader` (`postBlockTrigger`, `postContractLogTrigger`, `postContractEventTrigger`, `postTransactionTrigger`, `postSolidityLogTrigger`, `postSolidityEventTrigger`, `postSolidityTrigger`) whenever `useNativeQueue` is enabled, and these are called synchronously from block/transaction processing in `Manager.postContractTrigger` and `Manager.postBlockTrigger` during normal chain advancement and reorg handling. [5](#0-4) [6](#0-5)  This means the race is reachable simply by the node processing transactions/blocks while an operator-initiated (or automated) shutdown/plugin-stop sequence runs concurrently — not requiring any privileged actor or malicious peer, satisfying the "unprivileged, reachable from normal chain processing" requirement.

### Impact Explanation
An uncaught `NullPointerException` thrown from inside `publishTrigger`'s `synchronized` block is not caught by any `try/catch` in the calling chain (`EventPluginLoader.postXXXTrigger` methods have no try/catch around the native-queue branch), so it can propagate up into block-processing/trigger-emission code paths, risking process-level instability or an uncontrolled exception during trigger emission on shutdown, and inconsistent delivery of trigger/event data to external consumers (indexers, wallets, exchanges) subscribed via the ZeroMQ publisher — a denial-of-service/data-consistency issue for downstream event consumers of the RPC/event-plugin subsystem, matching the report's concern about undelivered messages and panics from concurrent publish+shutdown.

### Likelihood Explanation
Likelihood is Medium: this requires the node to be actively posting triggers (normal operation while native queue triggers are enabled) at the same moment `EventPluginLoader.stopPlugin()`/`NativeMessageQueue.stop()` is invoked (e.g., during a graceful node shutdown or plugin restart). This is a real, easily triggerable condition during ordinary node shutdown under load rather than requiring an attacker, but it is not attacker-controlled from the network in the same way as the RPC-facing issues; it is an internal lifecycle race exercised on every shutdown sequence when the native queue trigger feature is enabled.

### Recommendation
Guard both the check and the read/mutation of `publisher`/`context` under the same lock in `NativeMessageQueue`: perform the null/closed check and the `sendMore`/`send` calls, and the `close()`/nulling in `stop()`, under one consistent `synchronized(this)` (or a `ReentrantLock`/`volatile` + copy-on-write reference) so that `publishTrigger` and `stop` cannot interleave. Additionally, catch `NullPointerException`/`ZMQException` defensively inside `publishTrigger` so a shutdown race degrades to a logged error rather than propagating an unchecked exception, mirroring the report's recommendation that only a controlled error be surfaced.

### Proof of Concept
1. Enable native queue triggers (`useNativeQueue = true`) and start `NativeMessageQueue` via `EventPluginLoader` initialization.
2. Thread A: repeatedly call `Manager.postBlockTrigger(...)`/`Manager.postContractTrigger(...)` as blocks are processed, which invokes `EventPluginLoader.postBlockTrigger` → `NativeMessageQueue.getInstance().publishTrigger(...)`.
3. Thread B: concurrently call `EventPluginLoader.stopPlugin()` → `NativeMessageQueue.getInstance().stop()`.
4. Interleave so Thread A passes the `Objects.isNull(publisher) ... ` check in `publishTrigger` right before Thread B executes `publisher.close(); publisher = null;` in `stop()`; Thread A then enters the `synchronized(this)` block and calls `publisher.sendMore(topic)` on a now-`null` reference, throwing an `NullPointerException` uncaught by any surrounding trigger-posting code.   public void stop() {
    if (Objects.nonNull(publisher)) {
      publisher.close();
      publisher = null;
    }

    if (Objects.nonNull(context)) {
      context.close();
      context = null;
    }
    synchronized (NativeMessageQueue.class) {
      instance = null;
    }
  }

  public void publishTrigger(String data, String topic) {
    if (Objects.isNull(publisher) || Objects.isNull(context) || context.isClosed()) {
      return;
    }

    try {
      synchronized (this) {
        publisher.sendMore(topic);
        publisher.send(data);
      }
    } catch (RuntimeException e) {
      logger.error("write data to zeromq failed, data:{}, topic:{}, error:{}", data, topic,

    }
  }
