## Title
`ensure_match_transaction_info` skips validating state/hot-state/position checkpoint hashes, letting replay/verify tooling accept a divergent state root as matching a committed `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info`, the function used to verify that a locally-recomputed `TransactionOutput` matches an already-committed, accumulator-bound `TransactionInfo`, only checks transaction status, gas used, write-set hash (`state_change_hash`), and event root hash. It explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that commit the JMT/hot-state/native-position state roots into the transaction-info leaf that feeds the transaction accumulator. [1](#0-0) 

## Finding Description
`TransactionInfo` (V0/V1) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` alongside `state_change_hash` and `event_root_hash`, and these are all part of what gets hashed into the accumulator leaf. [2](#0-1) 

`ensure_match_transaction_info` is the function relied on to assert "this output I just computed corresponds to this authenticated `TransactionInfo`". It validates `status`, `gas_used`, `write_set_hash == state_change_hash`, and `event_root_hash`, but the function body contains its own admission that it stops there:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This helper is invoked from three consumers that all rely on it as the authoritative "does my recomputed output match the on-chain-authenticated `TransactionInfo`" check: `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, and `aptos-move/cli/src/commands.rs`. [4](#0-3) 

Meanwhile, the actual chunk-commit ledger-update path (`ChunkExecutorInner::update_ledger`) does perform full known-hash validation of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` by feeding them into `DoStateCheckpoint::run` as `known_state_checkpoints` / `known_hot_state_checkpoints` / `known_position_state_checkpoints`, which are checked against locally recomputed roots. [5](#0-4) 

So there are two independent code paths that are supposed to enforce the same invariant (locally recomputed state root == authenticated committed root), and one of them (`ensure_match_transaction_info`, used by replay/verify tooling and the CLI) silently omits the checkpoint-hash checks while the other (the live chunk-executor commit path) does perform them. The state feature flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS` gates whether `position_state_checkpoint_hash` is even computed/enforced at all in the commit path, and per the TODO, the gap in `ensure_match_transaction_info` was known to the developers as something that must be fixed before enabling that feature. [6](#0-5) 

## Impact Explanation
This maps directly onto the "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "Wrong accumulator root ... accepted as valid" gates. If node-local execution (during backup/restore replay, `db-tool replay-on-archive`, or CLI simulation-verification flows) produces a `WriteSet`/output whose resulting Merkle/Jellyfish state root, hot-state root, or native-position root diverges from what is authenticated in the committed `TransactionInfo` on the accumulator, `ensure_match_transaction_info` will report a **match** because it never compares those hash fields. Any auditing or verification tooling built on this function (replay-verify against archive, backup/restore integrity re-checks, CLI-side output verification) can therefore certify state that has silently diverged from the authenticated ledger state, defeating the purpose of the check without any consensus-level detection.

## Likelihood Explanation
This is not a purely theoretical scenario: the comment names the concrete trigger condition — a bug or non-determinism in native-position/hot-state computation that is masked as soon as `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or trading-native/hot-state features) is enabled, and the routine consumers of this exact function are backup/replay-verification tooling designed specifically to catch such divergences. The gap is unconditional (not behind a feature flag itself) and always present in `ensure_match_transaction_info`, so it applies today to `state_checkpoint_hash` and `hot_state_checkpoint_hash` as well, not only to the position-state field once that feature ships.

## Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally recomputed values (when the relevant summaries are available to the caller), mirroring the known-hash validation already performed in `ChunkExecutorInner::update_ledger` / `DoStateCheckpoint`, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or hot-state checkpointing is relied upon by any external-facing verification/replay tool.

## Proof of Concept
Not independently reproducible from static analysis alone — the code path itself documents the exact missing checks via the inline `TODO(trading-native)` comment at `types/src/transaction/mod.rs:2197-2203`, and the divergence between the strict checks in `ChunkExecutorInner::update_ledger` (`execution/executor/src/chunk_executor/mod.rs:373-413`) versus the checks omitted in `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) is directly visible by comparing the two functions' validated field sets.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
