### Title
Unbounded per-height sibling-block accumulation in `KhaosDatabase.push` due to broken `removeEldestEntry` eviction and unconditional insertion before signature/schedule validation - (`chainbase/src/main/java/org/tron/core/db/KhaosDatabase.java`)

### Summary
`KhaosDatabase.push(BlockCapsule)` inserts every structurally-linkable block into `miniStore.numKblkMap` before any witness-signature or DPoS-schedule validation occurs in `Manager.pushBlock`. Because `numKblkMap` is a `LinkedHashMap` whose `removeEldestEntry` size-based eviction only triggers when a brand-new `num` key is inserted (not when an `ArrayList` for an already-present `num` key grows), an attacker who repeatedly broadcasts distinct same-height sibling blocks referencing an already-known parent hash can grow a single `ArrayList<KhaosBlock>` without bound, and — for heights at or below the current chain head — the block is never cleaned up by `Manager.pushBlock` at all.

### Finding Description
`KhaosDatabase.push` only performs two checks before insertion: that a `KhaosBlock` for `block.getParentHash()` exists in `miniStore` and that `blk.getNum() == kblock.num + 1` [1](#0-0) . It performs **no signature or consensus-schedule validation**, and unconditionally calls `miniStore.insert(block)` [2](#0-1) .

`KhaosStore.insert` adds the block to `hashKblkMap` (keyed by unique block id) and to `numKblkMap` via `computeIfAbsent(block.num, ...).add(block)` [3](#0-2) . Because `computeIfAbsent` only creates a *new* map entry the first time a given `num` is seen, every subsequent block sharing that `num` merely appends to the existing `ArrayList` without touching the `LinkedHashMap`'s internal node-insertion path.

`removeEldestEntry` is Java's standard `LinkedHashMap` hook, which the JDK only invokes from `afterNodeInsertion`, itself only called when `putVal` creates a *new* map entry — not when an existing key's value is mutated in place. Consequently, `numKblkMap`'s eviction logic at [4](#0-3)  is never triggered for the second, third, ... Nth block sharing the same height — it only fires when a new distinct height key is inserted. This means the size of any single height's `ArrayList<KhaosBlock>` is completely unbounded by `maxCapacity`; only the number of distinct height keys is (eventually) capped.

Separately, `Manager.pushBlock` calls `this.khaosDb.push(block)` before it determines whether the pushed block actually becomes the new best/applied head [5](#0-4) . If the resulting `newBlock.getNum() <= headerNumber`, the method returns silently [6](#0-5)  without ever calling `khaosDb.removeBlk`, so any already-inserted low/equal-height sibling block remains permanently resident in `numKblkMap`/`hashKblkMap` (subject only to the broken age-based sweep described above). Full witness-signature/schedule validation (`consensus.validBlock`, `applyBlock`/`processBlock`) only happens later, deeper in the call chain [7](#0-6) , i.e., strictly after the memory has already been consumed by `khaosDb.push`.

Exploit flow: an attacker (a connected P2P peer, which requires no special privilege beyond running a node and being able to send block messages) crafts many distinct `BlockCapsule` objects that:
1. Share the same `parentHash`, pointing at any block hash currently present in `miniStore` (e.g. the well-known, publicly broadcast current chain head or a recent ancestor).
2. Share the same `num` = parent.num + 1.
3. Differ in some field (timestamp, empty transaction list variations, arbitrary witness address bytes, garbage/invalid signature) so each produces a unique block id/hash.

Each such block passes `KhaosDatabase.push`'s only two checks (parent presence + number continuity) and is inserted into the same `numKblkMap` entry, growing that entry's `ArrayList` without bound and without ever triggering `removeEldestEntry`.

### Impact Explanation
Sustained memory growth in the node process (`numKblkMap` entries and the backing `hashKblkMap`) can degrade or crash a full node (OOM), i.e., a denial-of-service against any node that relays/accepts blocks over the P2P layer, without requiring the attacker to be a witness or possess any signing key, and without the crafted blocks ever needing to be accepted as part of the canonical chain.

### Likelihood Explanation
Feasibility depends on whether an unauthenticated/untrusted P2P peer can get its block messages to reach `Manager.pushBlock`/`KhaosDatabase.push` without upstream filtering (e.g. a `BlockMsgHandler` performing early signature checks). Within the traced code, `push()` itself performs no signature/authorization check, and the caller (`Manager.pushBlock`) defers signature/schedule validation to well after `khaosDb.push` has already mutated state. Whether an earlier P2P-layer gate exists outside the files reviewed here could not be fully confirmed with the available tools; this is a caveat on likelihood, not on the described code-level defect, which is unconditionally present and repeatable via a straightforward Java unit test directly against `KhaosDatabase`.

### Recommendation
- Bound the number of sibling blocks tracked per height (e.g. cap `numKblkMap.get(num).size()` and reject/drop excess siblings) independent of the `LinkedHashMap`'s key-count-based eviction.
- Fix `removeEldestEntry`/eviction so it accounts for total block count (`hashKblkMap.size()`), not just distinct `num` keys, or explicitly trigger a capacity check inside `KhaosStore.insert` after every append (not relying on `LinkedHashMap`'s new-key-only callback).
- Move minimal structural/authentication checks (e.g., basic signature format, witness-schedule plausibility) before `khaosDb.push` is called in `Manager.pushBlock`, or clean up (`khaosDb.removeBlk`) any pushed block whenever `pushBlock` returns early instead of applying it.
