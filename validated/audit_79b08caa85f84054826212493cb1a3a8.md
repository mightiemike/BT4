## Analysis Result

### Title
`ensure_match_transaction_info()` never validates `state_checkpoint_hash`, allowing `db-tool replay-verify` to certify a divergent ledger state as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the sole authenticity check used by the `replay-verify` tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a freshly re-executed transaction matches the transaction info recorded by consensus/backup. It compares status, gas used, write-set hash, and event root hash, but never compares `TransactionInfo::state_checkpoint_hash()` (or the hot-state/position checkpoint hashes) against the locally computed state root. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` checks four fields: `status`, `gas_used`, the write-set hash against `txn_info.state_change_hash()`, and the event root hash against `txn_info.event_root_hash()`. [2](#0-1) 

It explicitly skips the state/hot-state checkpoint hash and `position_state_checkpoint_hash`, as documented directly in the code by an unresolved `TODO(trading-native)`: [3](#0-2) 

This is the only equality check invoked by the replay-verify pipeline in `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, where each re-executed transaction output is validated purely via `ensure_match_transaction_info`: [4](#0-3) 

The `state_change_hash` (write-set hash) only covers the writes produced by *that single transaction*; it says nothing about the resulting global Sparse-Merkle-Tree root. The separate `state_checkpoint_hash` field on `TransactionInfo` exists precisely to bind a transaction's checkpoint to the authoritative global state root at that version — but that field is never consulted here. Consequently, if the locally re-executed ledger state has already diverged from the archived/authoritative chain state (e.g., due to a state-tree corruption, a subtly wrong replay ordering, an executor bug affecting resulting state without changing an individual txn's own write-set bytes, or a hard-fork behavioral difference), a transaction whose own write-set/events/status/gas happen to match can still pass `ensure_match_transaction_info` even though the aggregated state root it commits to is wrong.

### Impact Explanation
`replay-verify` is the tool operators and infra rely on to detect ledger divergence between re-executed history and the authoritative backup/archive — this is explicitly one of the "restore/replay" integrity surfaces in scope. Because the checkpoint-hash comparison is missing, this tool can silently report success ("replay verified") on a version range where the true state root has diverged from the canonical chain. This defeats the primary purpose of the replay-verify safety net: it would fail to catch a real, otherwise undetected state-commitment divergence, which is a high-impact proof/commit-integrity gap even though the bug lives in a verification tool rather than in live consensus commit path.

### Likelihood Explanation
The comparison logic is unconditionally reached on every call — there is no feature gate around omitting the checkpoint hash check itself (the code comment references gating a *future* `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-related field, but the pre-existing `state_checkpoint_hash` on `TransactionInfo` is skipped unconditionally today). This makes the gap always active in the current replay-verify tool, not contingent on any feature flag or attacker action — it just requires an underlying state divergence to occur for the tool to fail to detect it, which is exactly the scenario replay-verify is meant to catch (e.g. after a state-sync/restore/backup ordering bug or a subtle executor determinism bug).

### Recommendation
Add an explicit comparison in `ensure_match_transaction_info` between the write-set-applied local state checkpoint root (computed as done in `do_ledger_update.rs::assemble_transaction_infos`) and `txn_info.state_checkpoint_hash()` (and, where applicable, hot-state / position-state checkpoint hashes), failing the check (and thus flagging a replay-verify error) on mismatch, before shipping any code path that relies on this function as a source of truth.

### Proof of Concept
1. Corrupt or diverge the locally maintained state tree in a way that does not alter the current transaction's own write-set contents (e.g., a stale/incorrect base state carried in from a prior undetected divergence, or a bug that produces the same write-set bytes but is applied to the wrong base state).
2. Run `db-tool replay-verify` (`storage/db-tool/src/replay_on_archive.rs::verify`) over the affected version range.
3. `execute_and_verify` calls `ensure_match_transaction_info`, which checks only status/gas/write-set-hash/event-root — all of which match because the transaction's own local write-set is unaffected by the upstream divergence. [5](#0-4) 
4. The tool returns no error for that transaction, and `replay-verify` reports the range as consistent, even though the resulting global state checkpoint root differs from the canonical chain's `state_checkpoint_hash` — the divergence goes undetected.

Note: I was unable to fully trace whether any other independent code path (outside this specific verification tool) cross-checks `state_checkpoint_hash` for the same re-executed outputs during `replay-verify`/`replay_on_archive` runs; my search of call sites for `ensure_match_transaction_info` found only `aptos-move/cli/src/commands.rs` and `storage/db-tool/src/replay_on_archive.rs` as callers, and neither appeared to perform a supplementary checkpoint-hash check.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
