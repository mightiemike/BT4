### Title
`TokenConfig.Enabled` flag is never enforced before minting/depositing PRC20 for inbound transfers, allowing funds to be processed for tokens the admin has disabled - (File: `x/uexecutor/keeper/execute_inbound_funds.go`)

### Summary
The external report's root cause is a registry-trust gap: a factory-style registry defines what counts as a "legitimate" deployed contract, but the consuming code never actually checks that flag/relationship before honoring user-controlled input, letting attacker-supplied data be treated as legitimate. In Push Chain's `x/uregistry` module, `TokenConfig` carries an `Enabled` boolean that is documented as gating "whether this token is enabled for minting/bridging" [1](#0-0) , and the module README states tokens can be un-whitelisted via `MsgUpdateTokenConfig`/`MsgRemoveTokenConfig` [2](#0-1) . However, the `x/uexecutor` inbound-processing paths only call `GetTokenConfig`, which merely checks that a `(chain, address)` entry exists in the map — it does not inspect `Enabled` at all [3](#0-2) .

### Finding Description
Every inbound execution path — `ExecuteInboundFunds`, `ExecuteInboundGasAndPayload`, and the analogous funds-and-payload/gas handlers — resolves the token purely via `k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)` and then immediately proceeds to deposit/mint the corresponding PRC20 into the recipient's UEA if the lookup succeeds [4](#0-3) . `ExecuteInboundFunds` similarly calls `depositPRC20` unconditionally on a successful config lookup [5](#0-4) . A grep across `x/uexecutor` for any reference to the `Enabled` field on `TokenConfig` returns no hits in the keeper logic that actually gates minting — the field is only referenced in mocks and unrelated struct fields (`ChainEnabled` for chain-level inbound/outbound gating, which is a different flag checked separately in `msg_vote_inbound.go`/`msg_execute_payload.go`).

This means the per-token `Enabled` flag — the mechanism the admin is expected to use to freeze a specific compromised, deprecated, or malicious token mapping without disabling the entire chain — has no enforcement point. Once a `(chain, address)` → PRC20 mapping has ever been registered, an unprivileged actor can continue to submit source-chain transfers of that asset through the honest gateway/validator voting pipeline, and honest universal validators will honestly observe and vote the inbound, and the executor will honestly mint/deposit PRC20 into the destination UEA — regardless of the admin having flipped `Enabled` to `false` in response to a discovered issue with that specific token (e.g., a rebasing/inflationary bug, a compromised bridge asset, or fraudulent listing).

### Impact Explanation
Because `Enabled` is a documented but unenforced control point, an admin's attempt to halt bridging/minting for a specific problematic token has no actual effect on the money path. An unprivileged user who has assets locked in the disabled token (or who exploits some other flaw specific to that token, prompting the disable in the first place) can keep triggering inbound mints/deposits of PRC20 into arbitrary UEAs after the token has been officially disabled, corrupting PRC20 supply accounting relative to what the registry's stated `Enabled` state promises operators and other integrators. This falls under "corruption of PRC20 or native asset accounting ... token mapping" in the allowed-impact scope, since the canonical registry state (`Enabled=false`) no longer matches what the executor's accounting actually permits.

### Likelihood Explanation
High reachability, low complexity: any external user who already has (or can generate) a valid signed source-chain transfer event for the affected token can trigger this path with no special privileges, and the honest validator voting/finalization pipeline processes it exactly as it would a legitimate, enabled token, since the only per-token gate (`GetTokenConfig` existence check) does not read `Enabled`. The precondition (admin having disabled a token) is an intentional protocol operation, not an attacker action, and is exactly the scenario the flag exists to protect against — so this is best understood as "the safety control silently doesn't work," not a privileged-actor assumption.

### Recommendation
In `x/uexecutor/keeper/execute_inbound_funds.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, and `execute_inbound_funds_and_payload.go`, after calling `GetTokenConfig`, explicitly check `tokenConfig.Enabled` and reject/revert the inbound (mirroring the existing `IsChainInboundEnabled` check pattern) if the token has been disabled, so admin de-listing actually stops future minting/deposits for that specific token.

### Proof of Concept
1. Admin registers `TokenConfig{Chain: "eip155:X", Address: tokenAddr, Enabled: true, ...}` via `MsgAddTokenConfig`.
2. A vulnerability/incident is discovered with `tokenAddr` (e.g. it can be minted arbitrarily on the source chain, or is fraudulent); admin calls `MsgUpdateTokenConfig` setting `Enabled: false`, expecting bridging to stop.
3. An unprivileged user (attacker) sends/observes a transfer of `tokenAddr` on the source chain to the Push gateway, as usual.
4. Honest universal validators vote the inbound normally (chain-level `IsInboundEnabled` is still `true`, since only the token was disabled).
5. `ExecuteInboundFunds`/`ExecuteInboundGasAndPayload` calls `GetTokenConfig(chain, tokenAddr)`, which succeeds and returns the config including `Enabled=false`, but that field is never inspected — `depositPRC20`/`gasAndPayloadDepositAutoSwap` proceed to mint/deposit PRC20 into the recipient's UEA exactly as before the disable, confirming the flag has no operational effect.

func (k Keeper) GetTokenConfig(ctx context.Context, chain, address string) (types.TokenConfig, error) {
	storageKey := types.GetTokenConfigsStorageKey(chain, address)
	config, err := k.TokenConfigs.Get(ctx, storageKey)
	if err != nil {
		return types.TokenConfig{}, err
	}
	return config, nil
}
