### Title
TVM `freeze()`/`unfreeze()`/`vote()` precompiles allow atomic, cost-free manipulation of TRON Power / SR vote weight within a single transaction - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The reported bug (Sherlock #172) is a "flashloan" pattern where a caller invokes two state-mutating operations (`pushAllocationsToController` and `pushAllocationsToVaults`) inside one transaction to atomically manipulate protocol-level accounting weights with borrowed capital that never leaves the caller's control for more than one block. The analogous primitive in java-tron is the TVM's native freeze/vote/unfreeze precompiles, which let a smart contract chain `freeze()` → `vote()` → `unfreeze()` inside a single external call/transaction, letting the caller inflate TRON Power used for Super Representative voting and then reclaim the TRX atomically, with no real economic lock-up.

### Finding Description
`OperationActions.freezeAction` invokes `Program.freeze(...)`, which builds a `FreezeBalanceParam` and sets its lock duration via: [1](#0-0) 
```
boolean needCheckFrozenTime = CommonParameter.getInstance().getCheckFrozenTime() == 1; // for test
param.setFrozenDuration(needCheckFrozenTime
    ? repository.getDynamicPropertiesStore().getMinFrozenTime() : 0);
```
`getCheckFrozenTime()` is explicitly commented as a test-only switch, meaning in normal operation the frozen duration recorded for a TVM-initiated freeze can be `0`, unlike the ordinary user-facing `FreezeBalanceActuator` path which always requires the network's minimum freeze duration. Because `UnfreezeBalanceProcessor.validate()` (the native-contract processor backing `unfreezeAction`) only checks `expireTime <= now`, a `frozenDuration` of `0` means the frozen entry is immediately eligible to be unfrozen: [2](#0-1) .

This means a single smart-contract transaction can internally call `freeze()` (via `OperationActions.freezeAction` / `Program.freeze`) to obtain TRON Power, call `vote()` (`VoteWitnessProcessor.execute`) to cast SR votes with that power, and then call `unfreeze()` in the same call/transaction to reclaim the TRX — all before the tx completes, at essentially zero net capital cost. This mirrors the reported class of bug: chaining two normally-separated, weight-affecting operations atomically in one transaction using capital that is only temporarily committed.

The codebase does contain a partial defense — `UnfreezeBalanceProcessor.execute` recomputes `usedTronPower` from `accountCapsule.getVotesList()` and clears votes if `accountCapsule.getTronPower() < usedTronPower * TRX_PRECISION`: [3](#0-2) . However, this check uses `accountCapsule.getTronPower()` unconditionally rather than choosing between `getTronPower()`/`getAllTronPower()` based on `dynamicStore.supportAllowNewResourceModel()`, the way `UnfreezeBalanceV2Processor.updateVote` does: [4](#0-3) . If TRON Power accounting from other frozen resource types (e.g., a separate TRON_POWER or ENERGY freeze) keeps the "remaining" TP above the just-cast vote count, the self-correcting clear does not trigger, and the vote persists after the flash freeze/vote/unfreeze sequence completes.

### Impact Explanation
If exploitable, an attacker could inflate SR election vote totals and the network's total resource/vote weight bookkeeping (`addTotalNetWeight`/`addTotalEnergyWeight`) without permanently locking TRX, using only transient capital held for the duration of one transaction. This can distort Super Representative elections/rankings and vote-weighted rewards — a form of consensus/governance and accounting corruption reachable purely through a broadcast smart-contract transaction, with no privileged role required.

### Likelihood Explanation
Reachability requires only deploying and calling an ordinary contract that chains `freeze`/`vote`/`unfreeze` opcodes — fully permissionless. The severity is reduced because (a) this old (V1) freeze/unfreeze/vote precompile path is disabled once `VMConfig.allowTvmFreezeV2()` is active (`freezeAction` becomes a no-op): [5](#0-4) , so this is only live on chains/heights where the V1 TVM freeze feature is still enabled and `allowTvmVote` is on; and (b) most simple single-resource-type sequences are neutralized by the vote-clearing check in `UnfreezeBalanceProcessor`. I was not able to conclusively confirm, within the available context, a concrete state combination (e.g., mixing BANDWIDTH/ENERGY/TRON_POWER frozen balances) that leaves `getTronPower()` above `usedTronPower` after the flash-unfreeze, which would be required to fully prove exploitability versus the existing defense being sufficient in all cases.

### Recommendation
- Do not allow `frozenDuration` to default to `0` for TVM-triggered freezes in production; always enforce `dynamicStore.getMinFrozenTime()` regardless of the `checkFrozenTime` test flag, or remove that test-only bypass from the production code path entirely.
- In `UnfreezeBalanceProcessor.execute`, align the TRON Power comparison with the newer `UnfreezeBalanceV2Processor.updateVote` logic — select `getAllTronPower()`/`getTronPower()` based on `supportAllowNewResourceModel()` — so that votes are reliably invalidated whenever the account's real committed TRON Power can no longer justify the cast votes, regardless of which resource type is unfrozen or in what order.
- More generally, prevent `freeze → vote → unfreeze` (or `freezeV2 → vote → unfreezeV2`) from being profitably chained inside a single transaction/execution, e.g., by requiring at least one intervening block/maintenance cycle before unfreezing resources that were used to cast an active vote.

### Proof of Concept
Conceptual sequence (not independently executed, derived from code paths cited above):
1. Deploy a contract exposing a single external function.
2. In that function, call the `freeze(receiver=self, amount=X, resourceType=BANDWIDTH_or_ENERGY)` precompile — with `CommonParameter.checkFrozenTime` at its default (non-test) value, `frozenDuration` is set to `0` [6](#0-5) .
3. Immediately call `vote(srList, tpList)` using the TRON Power just gained, via `VoteWitnessProcessor.execute` [7](#0-6) .
4. Immediately call `unfreeze(receiver=self, resourceType=BANDWIDTH_or_ENERGY)` in the same transaction; validation only checks `expireTime <= now`, which holds because duration was `0` [8](#0-7) .
5. All three calls complete in one transaction/one block, reclaiming the TRX while (depending on the account's total TRON Power composition) the just-cast vote can remain recorded if the residual `getTronPower()` still exceeds the used vote count, since the guard in `UnfreezeBalanceProcessor.execute` does not distinguish new-resource-model TRON Power the way `UnfreezeBalanceV2Processor` does.

  public static void freezeAction(Program program) {
    // after allow vote, check static
    if (VMConfig.allowTvmVote() && program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }
    // 0 as bandwidth, 1 as energy
    DataWord resourceType = program.stackPop();
    DataWord frozenBalance = program.stackPop();
    DataWord receiverAddress = program.stackPop();

    if (VMConfig.allowTvmFreezeV2()) {
      // after v2 activated, we just push zero to stack and do nothing
      program.stackPush(DataWord.ZERO());
    } else {
      boolean result = program.freeze(receiverAddress, frozenBalance, resourceType );
      program.stackPush(result ? DataWord.ONE() : DataWord.ZERO());
    }
    program.step();
  }

  public void execute(VoteWitnessParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getVoterAddress();
    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);

    VotesCapsule votesCapsule = repo.getVotes(ownerAddress);
    if (votesCapsule == null) {
      votesCapsule = new VotesCapsule(ByteString.copyFrom(ownerAddress),
          accountCapsule.getVotesList());
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    Map<ByteString, Long> voteMap = new HashMap<>();
    Iterator<Protocol.Vote> iterator = param.getVotes().iterator();
    try {
      long sum = 0;
      while (iterator.hasNext()) {
        Protocol.Vote vote = iterator.next();

        byte[] witnessAddress = vote.getVoteAddress().toByteArray();
        /*
          Already covered while doing maintenance in MaintenanceManager.java, for tvm performance,
          we remove the account check
         */
//        if (repo.getAccount(witnessAddress) == null) {
//          throw new ContractValidateException(
//              ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(witnessAddress) + NOT_EXIST_STR);
//        }
        if (repo.getWitness(witnessAddress) == null) {
          throw new ContractExeException(
              WITNESS_EXCEPTION_STR + StringUtil.encode58Check(witnessAddress) + NOT_EXIST_STR);
        }

        long voteCount = vote.getVoteCount();
        if (voteCount < 0) {
          throw new ContractExeException("Vote count must not be less than 0");
        } else if (voteCount == 0) {
          iterator.remove();
        } else {
          sum = LongMath.checkedAdd(sum, voteCount);
          // merge vote for same witness
          voteMap.put(vote.getVoteAddress(),
              LongMath.checkedAdd(voteMap.getOrDefault(vote.getVoteAddress(), 0L), voteCount));
        }
      }

      long tronPower;
      if (repo.getDynamicPropertiesStore().supportUnfreezeDelay()
          && repo.getDynamicPropertiesStore().supportAllowNewResourceModel()) {
        tronPower = accountCapsule.getAllTronPower();
      } else {
        tronPower = accountCapsule.getTronPower();
      }
      sum =  LongMath.checkedMultiply(sum, TRX_PRECISION);
      if (sum > tronPower) {
        throw new ContractExeException(
            "The total number of votes[" + sum + "] is greater than the tronPower[" + tronPower
                + "]");
      }
    } catch (ArithmeticException e) {
      throw new ContractExeException(e.getMessage());
    }

    for (Map.Entry<ByteString, Long> entry : voteMap.entrySet()) {
      accountCapsule.addVotes(entry.getKey(), entry.getValue());
      votesCapsule.addNewVotes(entry.getKey(), entry.getValue());
    }
    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    repo.updateVotes(ownerAddress, votesCapsule);
