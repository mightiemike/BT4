### Title
StackerDB chunk authentication digest omits the contract identifier, enabling cross-StackerDB signature replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` — the message a signer's key signs to authenticate a StackerDB chunk write — hashes only `slot_id`, `slot_version`, and `data_hash`. It contains no binding to the specific StackerDB smart contract (`QualifiedContractIdentifier`) the chunk is destined for, nor any chain/network identifier. This is structurally the same defect as the reported `instantWithdraw` bug: a signature intended for one destination (a specific StackerDB contract/slot) carries no destination-specific data, so it can be replayed verbatim against a different destination that happens to share the same `(slot_id, slot_version, data_hash)` triple.

### Finding Description
`auth_digest` is defined as: [1](#0-0) 

and is what `SlotMetadata::sign`/`verify` operate over: [2](#0-1) 

The HTTP handler that accepts a chunk write derives the contract to write into purely from the URL path (`/v2/stackerdb/{address}/{contract}/chunks`), and then calls `try_replace_chunk` against that specific contract's table — the signature itself never references which contract it was meant for: [3](#0-2) 

Each StackerDB contract (e.g. `.signers-1-1`, `.signers-2-1`, `.miners`) independently maps `slot_id -> signer public-key-hash` via its own on-chain config, and `SlotMetadata::verify` only checks that the recovered public key's hash matches the principal configured for that slot in the target contract — it does not check that the signature was produced *for that contract*: [4](#0-3) 

Because signer sets persist or overlap across reward cycles (the same signing key commonly owns the same `slot_id` in consecutive `.signers-N-1` contracts), and `slot_version` starts at 0 and increments predictably, an attacker who observes a chunk `(slot_id, slot_version, data, sig)` legitimately posted by a signer to StackerDB contract A can repost the exact same `(slot_id, slot_version, sig)` (with the identical `data`, hence identical `data_hash`) to a different StackerDB contract B that the same signer's key also owns that slot in. `SlotMetadata::verify` will recover the same public key and accept it, because nothing in the digest distinguishes contract A from contract B.

### Impact Explanation
This breaks the equality "a chunk accepted into StackerDB contract X was authored by its slot-owner *for X*." A chunk validly signed for one round/consumer (e.g. a signer's `.signers-N-1` message bus for reward cycle N) can be forcibly replayed into a different consumer contract's identical slot (e.g. `.signers-(N+1)-1`, or a differently-scoped `.miners` bus if slot layouts coincide), corrupting or confusing message consumption for that other channel — e.g. re-injecting a stale block-vote/nonce/DKG message from a prior reward cycle into the current cycle's signer coordination channel. Since StackerDB content directly drives signer-to-signer and miner-to-signer coordination (block proposals, block responses, DKG shares), this is a High-severity, minority-triggerable (single malicious relayer, no majority needed) divergence/griefing vector in signer coordination, though it does not directly falsify consensus-critical block signatures (`NakamotoBlockHeader::signer_signature_hash`, which is separately, and correctly, bound to full block-specific content including `consensus_hash`, `parent_block_id`, etc., per `stackslib/src/chainstate/nakamoto/mod.rs:1008-1045`).

### Likelihood Explanation
Requires no privileged access or majority — any network participant that can observe a StackerDB chunk broadcast (chunks are gossiped/relayed openly) and re-POST it to another contract endpoint can attempt the replay. Success requires only that `(slot_id, slot_version)` coincide across the two target contracts for the attacker's chosen victim signer, which is plausible given how slot assignments are typically stable/re-used across consecutive reward-cycle contracts.

### Recommendation
Bind the StackerDB signature to the destination, mirroring the SIP018 domain-separation pattern already used elsewhere in this codebase (e.g. `make_structured_data_domain` in `stackslib/src/util_lib/signed_structured_data.rs`). Concretely, include the `QualifiedContractIdentifier` (and ideally a chain-id) inside `SlotMetadata::auth_digest`'s hashed preimage, so a signature for one StackerDB contract cannot be replayed against another.

### Proof of Concept
1. Signer key `K` owns `slot_id = 3` in both `.signers-1-1` and `.signers-2-1` (a common configuration since signer sets/slots persist across adjacent cycles).
2. `K` legitimately signs and posts chunk `data` at `slot_version = 5` to `.signers-1-1`, producing `sig = Sign(K, H(slot_id=3 || slot_version=5 || H(data)))` per `auth_digest`.
3. An attacker observes this chunk over the p2p/HTTP relay and re-submits the identical `(slot_id=3, slot_version=5, sig, data)` via `POST /v2/stackerdb/<addr>/signers-2-1/chunks`.
4. `RPCPostStackerDBChunkRequestHandler::try_handle_request` looks up `.signers-2-1`'s slot 3 owner, finds it is also `K`, calls `SlotMetadata::verify`, which succeeds because `auth_digest` never encoded which contract the signature was for — the stale/foreign chunk is accepted into `.signers-2-1`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
