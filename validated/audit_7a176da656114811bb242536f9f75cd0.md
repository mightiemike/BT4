Based on the investigation, java-tron's `Exchange` (Bancor-relay AMM) subsystem contains an analogous root-cause pattern to the reported `Amm.sol` issue: a computed value from a formula is used to update pool state without validating that the result keeps the invariant/accounting in a safe range, and the safety check that *was* added is optional and gated behind a governance flag rather than being unconditional.

### Title
Non-hardened Exchange (Bancor Relay) calculation path allows exchange pool balances to go negative - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction()` computes `buyTokenQuant` via a `Processor` (bancor-relay formula) and then updates `firstTokenBalance`/`secondTokenBalance` accordingly. In the default (non-hardened) code path, the resulting new balances are written to storage with no check that they remain non-negative. Only the `hardenedCalc` path (enabled by the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal) performs this check.

### Finding Description
`transaction()` selects between `ExchangeProcessor` (double-precision `Math.pow`-based) and `SafeExchangeProcessor`/`hardenedCalc` (`BigDecimal`-based, exact) depending on the `hardenedCalc` flag: [1](#0-0) 

After computing `buyTokenQuant`, the new balances are derived, and only under `hardenedCalc` is a negative-balance check performed before persisting state: [2](#0-1) 

The default `ExchangeProcessor` uses floating-point `Maths.pow` in `exchangeFromSupply`, with no bound relating the computed payout to the actual `buyTokenBalance` held by the exchange pool: [3](#0-2) 

The dedicated regression tests confirm that only the hardened/`SafeExchangeProcessor` path is asserted to never overshoot the buy-side reserve: [4](#0-3) 

The gate for which path is used is `allowHarden()`, driven by the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain proposal, exercised through `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`: [5](#0-4) 

This directly mirrors the reported `Amm.sol` bug class: a corrective/exact calculation (the "budget"-respecting hardened path, analogous to the recommended `k`-adjustment budget check) exists, but the code does not unconditionally require passing through it — instead an unchecked, formula-only path (the un-hardened `ExchangeProcessor`) can be exercised and can push accounting state (pool reserve balances) into an invalid region (negative balances / more tokens paid out than held) without any post-computation validation, exactly as `repegCheck()` applied its 99% reduction without validating the recomputed `cost` against `_budget`.

### Impact Explanation
If the non-hardened path is used (i.e., before/absent the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal is active, or on any network where it hasn't been enabled), a sufficiently large trade relative to the pool's `supply`/reserve ratio can cause `exchangeFromSupply`'s floating point `pow` computation to return a `buyTokenQuant` exceeding the actual `buyTokenBalance`, driving `newSecondTokenBalance`/`newFirstTokenBalance` negative. This corrupts core Exchange (TRC10 AMM) accounting state stored on-chain — an invalid-state/accounting divergence impact, and it also lets a trader extract more of a token than the pool actually holds, an underpriced/incorrectly-priced settlement, potentially enabling other users' subsequent exchange transactions to fail or produce further miscalculations from the deranged reserve.

### Likelihood Explanation
Likelihood depends on whether `ALLOW_HARDEN_EXCHANGE_CALCULATION` has been activated on the target network; on networks where this proposal is not yet active (or for any historical unconfirmed period), any unprivileged account can call `ExchangeTransactionContract` and is only blocked from overshooting by validate()'s `tokenExpected` check, which does not itself bound overshoot relative to reserve [6](#0-5) . I was unable to confirm from the index whether this proposal is enabled by default on mainnet at the current hard-fork height, which is necessary to determine current-day exploitability.

### Recommendation
Make the negative-balance (and, more generally, invariant-preserving) checks unconditional in `ExchangeCapsule.transaction()` rather than gating them behind `hardenedCalc`/`ALLOW_HARDEN_EXCHANGE_CALCULATION`, or reject the trade in `validate()` if the computed `anotherTokenQuant` would exceed the corresponding pool balance, mirroring the report's recommendation to bound the corrective computation by the true available budget/reserve rather than assuming a single-pass computation is sufficient.

### Proof of Concept
Not independently verified against live parameters (I do not have access to run the code); this would need to be validated with a Devin session by constructing a `ExchangeCreateContract`/`ExchangeTransactionContract` sequence with `hardenedCalc` disabled and reserve ratios chosen to make `Maths.pow(1 + quant/newBalance, 2000)` overshoot the actual buy-side balance, then confirming `ExchangeCapsule.transaction()` persists a negative `secondTokenBalance`/`firstTokenBalance` without exception, as contrasted with the `testHardenedOverflowDetection`/`testSafeProcessorNoOvershootForTypicalInputs` tests that only assert this invariant for the hardened path.
