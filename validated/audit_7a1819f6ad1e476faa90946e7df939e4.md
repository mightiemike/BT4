### Title
Duplicate-account invariant for off-chain accounts lt hash updates is only enforced in debug builds, risking silent hash divergence - ([File: runtime/src/bank/accounts_lt_hash.rs])

### Summary
`Bank::enqueue_off_chain_accounts_lt_hash_updates` requires callers to guarantee that the `accounts` slice contains no duplicate pubkeys, but that invariant is only checked (and panics) when `cfg!(debug_assertions)` is true. In a release validator build, if any caller ever violates this contract, the function will silently mix in more than one version of the same account into the async lt-hash job stream without detecting the problem, analogous to `_pullTokenInputAndPayProtocolFee()` trusting that `safeTransferFrom()` succeeded without checking the resulting balance.

### Finding Description
`enqueue_off_chain_accounts_lt_hash_updates` is documented as: "Does not deduplicate accounts, requiring the caller to ensure there are no duplicates." [1](#0-0) 

The duplicate check that would catch a violation of this contract is gated behind `cfg!(debug_assertions)`:
```rust
if cfg!(debug_assertions) {
    // if debug assertions are on, we will check for duplicates
    ...
    if !duplicate_pubkeys.is_empty() {
        ...
        panic!("duplicate accounts were enqueued for hashing: {duplicate_accounts:?}");
    }
}
``` [2](#0-1) 

In a release build (the configuration validators actually run), this block is compiled out entirely. If a duplicate pubkey slips into `accounts` for any reason (a latent bug in a caller, a future refactor of a caller that batches accounts from multiple sources, etc.), each occurrence gets its previous version loaded and enqueued independently via `load_then_enqueue`/`async_progress.spawn(...)`, mixing in an update for the same address more than once: [3](#0-2) 

This directly contrasts with the "on-chain" counterpart, `enqueue_on_chain_accounts_lt_hash_updates`, which unconditionally deduplicates (keeps only the latest occurrence per pubkey) regardless of build configuration: [4](#0-3) 

The off-chain path has no equivalent unconditional protection — it only "checks" the precondition in debug builds, then proceeds to *assume* success in release builds, exactly like `_pullTokenInputAndPayProtocolFee()` assuming the transfer succeeded without checking post-state.

### Impact Explanation
If the no-duplicates invariant is ever violated in a release build, the computed `accounts_lt_hash` (which becomes the `SnapshotHash`/bank hash component via `finish_accounts_lt_hash_updates` and `get_snapshot_hash`) would silently diverge from the value that a correctly-deduplicated implementation (or a peer node) would compute. [5](#0-4) [6](#0-5)  This is a "hash divergence" class impact: it would not crash but would produce a validator computing a different bank hash than honest peers on a slot where a duplicate leaked through, or an honest-node snapshot-vs-replay mismatch if the divergence occurs at different times (e.g., snapshot verification via `calculate_accounts_lt_hash_at_startup_from_index` recomputing from the index rather than through this async path). [7](#0-6) 

### Likelihood Explanation
Likelihood is low today because current callers of `enqueue_off_chain_accounts_lt_hash_updates` (via `store_accounts_without_stakes_cache`/`store_accounts_par`) are expected to already respect uniqueness (e.g., partitioned epoch-rewards distribution stores one account per pubkey per call). However, the safety of the whole mechanism rests entirely on caller discipline enforced only by a debug-only assertion — there is no runtime (release-mode) guard, so any future caller mistake or refactor would go undetected until a hash mismatch is observed on-chain, which is a much more costly failure mode to diagnose than an immediate panic.

### Recommendation
Perform the duplicate-pubkey check unconditionally (not gated by `cfg!(debug_assertions)`), or make `enqueue_off_chain_accounts_lt_hash_updates` deduplicate defensively the same way `enqueue_on_chain_accounts_lt_hash_updates` does, so a caller-contract violation cannot silently corrupt the accounts lt hash in production builds.

### Proof of Concept
Not directly reproducible without modifying a caller (the current caller happens to respect the contract). Conceptually:
1. Build agave in release mode (`cfg!(debug_assertions)` is `false`).
2. Call `Bank::store_accounts_without_stakes_cache` (or any path reaching `enqueue_off_chain_accounts_lt_hash_updates`) with a `StorableAccounts` slice containing the same pubkey twice with different data.
3. Observe that the account is stored once (last-write-wins in `AccountsDb`), but the lt-hash job stream mixes in two versions of that pubkey's account, producing an `accounts_lt_hash`/bank hash that does not match a peer node or a from-index recomputation (`calculate_accounts_lt_hash_at_startup_from_index`), with no panic or error raised.

**Note:** I was unable to fully confirm within available iterations whether any current caller of `store_accounts_without_stakes_cache`/`store_accounts_par` can pass duplicate pubkeys under any existing code path (e.g., due to overlapping partitioned-rewards batches); this would need further investigation with full repository access (e.g., a Devin session) to trace all call sites of `store_accounts_without_stakes_cache` in `runtime/src/bank.rs` and confirm whether the "no duplicates" contract is enforced structurally elsewhere or only by convention.
