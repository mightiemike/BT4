### Title
`DelegateAction` Signed Payload Omits `chain_id`, Enabling Cross-Chain Replay of Meta Transactions — (`File: core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

### Summary

`DelegateAction` (NEP-366 meta transactions) and `DelegateActionV2` (NEP-611 gas-key meta transactions) produce their signing hash via `get_nep461_hash()`, which wraps the action body in a `SignableMessage` whose only domain-separation is a constant NEP discriminant integer. Neither the `DelegateAction` payload nor the `SignableMessage` wrapper includes the NEAR `chain_id`. A signature produced on mainnet is therefore cryptographically valid on testnet, on any hard-fork chain, or on any other NEAR network that shares the same account namespace, as long as the nonce has not yet been consumed on the target chain.

### Finding Description

`DelegateAction.get_nep461_hash()` is defined as:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
``` [1](#0-0) 

`SignableMessage` serializes as `(discriminant: u32, msg: &T)`:

```rust
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}
``` [2](#0-1) 

The discriminant is a compile-time constant derived from the NEP number:

```rust
SignableMessageType::DelegateAction =>
    MessageDiscriminant::new_on_chain(NEP_366_META_TRANSACTIONS).unwrap()
``` [3](#0-2) 

The `DelegateAction` struct itself contains `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — no `chain_id` field: [4](#0-3) 

`SignedDelegateAction.verify()` only checks the signature against this chain-agnostic hash:

```rust
pub fn verify(&self) -> bool {
    let hash = delegate_action.get_nep461_hash();
    self.signature.verify(hash.as_ref(), public_key)
}
``` [5](#0-4) 

The same omission applies to `VersionedDelegateActionPayload` (`DelegateActionV2`): [6](#0-5) 

Regular `SignedTransaction` has partial chain-binding through `block_hash` (which must be an ancestor of the current chain head within `transaction_validity_period`): [7](#0-6) 

`DelegateAction` has **no equivalent chain-binding** — `max_block_height` is a raw block number with no chain identity.

### Impact Explanation

An attacker who observes a `SignedDelegateAction` on one NEAR chain (e.g., mainnet) can submit the identical borsh-encoded object on any other NEAR chain (testnet, a hard-fork chain, a localnet with the same account) where:

1. The `sender_id` account exists.
2. The access key identified by `public_key` exists on that account.
3. The `nonce` has not yet been consumed on that chain.
4. The current block height is below `max_block_height`.

All four conditions are routinely satisfied when a user has the same account on mainnet and testnet, or when a chain fork preserves pre-fork state. The inner `actions` execute with `sender_id` as the predecessor, so any `Transfer`, `FunctionCall`, `AddKey`, or `DeleteKey` action inside the delegate runs under the victim's identity on the target chain — constituting an unauthorized transaction and potential fund loss.

### Likelihood Explanation

- `DelegateAction` objects are transmitted off-chain to relayers and are also embedded in on-chain transactions, making them publicly observable.
- NEAR accounts commonly exist on both mainnet and testnet with identical names and keys.
- `max_block_height` is often set to a large value (e.g., `BlockHeight::MAX` in test code and production SDKs) to avoid expiry, leaving the replay window open indefinitely.
- No runtime check in `apply_delegate_action` or `validate_delegate_action` compares the chain's `chain_id` against any field in the signed payload.

### Recommendation

Include the genesis `chain_id` string (or the genesis block hash, which is already part of `GenesisId`) in the data committed to by `get_nep461_hash()`. Concretely, add a `chain_id: String` field to `DelegateAction` (and `DelegateActionV2`) that is populated by the signer and verified by the runtime against `ApplyState::chain_id` (or equivalent), mirroring how EIP-712 `DOMAIN_SEPARATOR` binds a permit to a specific chain. Alternatively, include the genesis hash from `GenesisId` in the `SignableMessage` wrapper so the binding is automatic for all future message types.

### Proof of Concept

1. Alice signs a `DelegateAction` on mainnet transferring 10 NEAR to Bob, with `max_block_height = u64::MAX` and `nonce = 1`.
2. The relayer submits it on mainnet; it executes and Alice's mainnet nonce advances to 1.
3. An observer (or the relayer itself) takes the identical borsh-encoded `SignedDelegateAction` and submits it via `broadcast_tx_commit` on testnet, where Alice's testnet access-key nonce is still 0.
4. `SignedDelegateAction::verify()` passes because the hash is chain-agnostic.
5. The runtime's nonce check passes (`1 > 0`).
6. The transfer executes on testnet, draining Alice's testnet balance without her authorization.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
