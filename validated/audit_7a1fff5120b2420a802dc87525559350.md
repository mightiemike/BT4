Found it: `add-staker-to-bond-for-cycle` in `pox-5.clar` mutates `signer-shares-staked-for-cycle` and `staker-shares-staked-for-cycle` **without** first calling `settle-rewards`/`settle-staker-rewards`, unlike the sibling function `add-staker-to-signer-for-cycle`, which explicitly documents and enforces the invariant that these settle calls "MUST be called before any update to `signer-shares-staked-for-cycle` ... because changes to that state will effect rewards calculations."

### Title
Bond-registration path mutates signer/staker shares without settling prior rewards, corrupting reward-per-token accounting - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`add-staker-to-bond-for-cycle` (the per-cycle folder used by `add-staker-to-bond-cycles`, invoked from `register-for-bond`/bond registration flows) increases `signer-shares-staked-for-cycle` and `staker-shares-staked-for-cycle` and then unconditionally overwrites `staker-rewards-per-token-settled-for-cycle` with the *current* `rewards-per-token`, without ever calling `settle-rewards`/`settle-staker-rewards` first for the pre-existing shares at that cycle.

### Finding Description
The contract's own invariant, documented directly above `settle-rewards`, states: [1](#0-0) 

is required before any mutation of `signer-shares-staked-for-cycle`, because `compute-earned-rewards` (called inside `settle-rewards`) computes `earned = shares * (rewards_per_token - rewards_per_token_paid)` using the *pre-mutation* share amount. The sibling function that adds a staker to a signer's set correctly follows this rule: it calls `(settle-rewards signer cycle none)` and, if the staker already had shares, `(settle-staker-rewards signer cycle none staker)` before mutating any staked-share maps: [2](#0-1) 

However, `add-staker-to-bond-for-cycle`, used for bond-index based staking, mutates `total-shares-staked-for-cycle`, `signer-shares-staked-for-cycle`, and `staker-shares-staked-for-cycle` directly and then stamps `staker-rewards-per-token-settled-for-cycle` to the current `rewards-per-token`, with **no preceding `settle-rewards`/`settle-staker-rewards` call**: [3](#0-2) 

Because `settle-rewards` is skipped, any rewards that accrued on the signer's (or staker's) *existing* shares between the last settlement and this registration are never converted into `unclaimed-rewards`. The subsequent stamping of `staker-rewards-per-token-settled-for-cycle` to the current cumulative rate silently "erases" that unsettled delta for any future `compute-earned-rewards` call on the pre-existing balance — since the reference point moves forward without crediting the interim rewards.

This breaks the equality that the whole staker/signer accounting model depends on: `sum(all stakers' earned + unclaimed) == distributed rewards for that signer/cycle`. When two stakers register for the same bond/signer/cycle at different times, the first staker's already-accrued (but unsettled) rewards for that interval get permanently lost from the ledger the moment a second registration mutates the shared `signer-shares-staked-for-cycle` entry before settlement — mirroring exactly the reported Crate.sol class of bug (mutating pooled state before "rebalancing"/settling causes a later participant's accounting to diverge from the correct value).

### Impact Explanation
This is a minority-triggerable (single unprivileged caller registering/staking for a bond) divergence in reward accounting bounded to signer/staker reward distribution for a cycle — a reward mis-payment (loss/misallocation of already-accrued fee/reward amounts) rather than a chain split. This matches the "High" impact bucket: reward mis-payment bounded to fees/rewards.

### Likelihood Explanation
Any sequence where a bond staker with existing shares in `signer-shares-staked-for-cycle`/`staker-shares-staked-for-cycle` for a given `(signer, cycle, bond-index)` has additional shares added via `add-staker-to-bond-for-cycle` after some rewards have already accrued (i.e., `rewards-per-token-for-cycle` has increased since the last settlement) will trigger this loss. This is a normal, unprivileged, permissionless flow (bond registration extension) requiring no majority or special privilege — only two calls into the bond-registration path separated by a reward accrual.

### Recommendation
Add `(settle-rewards signer reward-cycle (some bond-index))` and, when `current-signer-staked > u0` (for the signer) or existing staker shares are non-zero, `(settle-staker-rewards signer reward-cycle (some bond-index) staker)` at the start of `add-staker-to-bond-for-cycle`, mirroring the pattern already used in `add-staker-to-signer-for-cycle`, before mutating `signer-shares-staked-for-cycle`/`staker-shares-staked-for-cycle`/`total-shares-staked-for-cycle`.

### Proof of Concept
1. Signer `S` has staker `A` registered for bond `B` at cycle `C` with `staker-shares-staked-for-cycle{S,C,B,A} = X`, `rewards-per-token-for-cycle{S,C,B} = R0`.
2. `calculateRewards`/reward distribution runs, bumping `rewards-per-token-for-cycle{S,C,B}` to `R1 > R0`. `A`'s earned-but-unsettled reward is `X*(R1-R0)`, but `A`'s `staker-rewards-per-token-settled-for-cycle` is still `R0` (never updated because no settlement occurred).
3. Staker `B2` calls `register-for-bond` for the same `(S, C, bond-index)`, invoking `add-staker-to-bond-for-cycle`. This does not call `settle-rewards`/`settle-staker-rewards` for `S`/`A`; it only updates shares and stamps `B2`'s own settled snapshot to `R1`.
4. When `A` later claims rewards, `get-earned-staker-rewards` recomputes using `A`'s stored `rewards-per-token-settled = R0` vs the current signer rate — but because the signer-level snapshot (`signer-rewards-per-token-settled-for-cycle`) was never re-synced through `settle-rewards`, the signer-level `unclaimed-rewards` bucket used to gate/validate distributions is now inconsistent with the sum of individual stakers' true accrued amounts, so total payouts for `(S,C,B)` no longer equal the rewards actually distributed for that signer/cycle.
