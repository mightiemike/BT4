## Analog Found

### Title
Front-running `AccountCreateContract` via unprivileged `TransferContract`/`TransferAssetContract` permanently blocks account creation - (File: actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java)

### Summary
`CreateAccountActuator.validate()` rejects account creation if the target `accountAddress` already exists in the `AccountStore`. Any unprivileged user can pre-create that address as a plain account by sending it a trivial amount of TRX (`TransferActuator`) or TRC10 tokens (`TransferAssetActuator`) before the legitimate `AccountCreateContract` transaction lands, permanently blocking the intended account creation for that address — the same bug class as the SEDA vesting-account front-run.

### Finding Description
`CreateAccountActuator.validate()` enforces:
```java
if (accountStore.has(accountAddress)) {
  throw new ContractValidateException("Account has existed");
}
``` [1](#0-0) 

Separately, both `TransferActuator.execute()` and `TransferAssetActuator.execute()` silently auto-create the recipient account (as `AccountType.Normal`) if it does not yet exist, whenever anyone sends it TRX or a TRC10 token:
```java
AccountCapsule toAccount = accountStore.get(toAddress);
if (toAccount == null) {
  ...
  toAccount = new AccountCapsule(ByteString.copyFrom(toAddress), AccountType.Normal, ...);
  accountStore.put(toAddress, toAccount);
  fee = fee + dynamicStore.getCreateNewAccountFeeInSystemContract();
}
``` [2](#0-1) [3](#0-2) 

Because `AccountCreateContract` requires the target `accountAddress` field to be an address for which the owner controls the corresponding private key/permissions (typical use case: pre-creating an account of a specific `AccountType`, e.g. via wallet SDKs like `WalletClient.createAccountCreateContract`, which lets the caller specify `AccountType`) [4](#0-3) , an attacker who knows the target address (e.g. observed in the mempool, or a deterministically derivable/expected address) can broadcast a minimal `TransferContract`/`TransferAssetContract` to that address first. Once the account exists (even with zero meaningful balance), any subsequent `AccountCreateContract` for that address fails permanently with `"Account has existed"`, and there is no path in the codebase to delete an account or otherwise "upgrade" an existing plain account through `AccountCreateContract` — the actuator has no update/overwrite branch, only creation. This mirrors the SEDA report's root cause: “a [target account] can only be created if the recipient does not already exist,” which can be trivially defeated by anyone sending funds to that address first.

### Impact Explanation
The victim (owner of the intended `accountAddress`) is permanently denied the ability to have that address registered via `AccountCreateContract` with their chosen parameters (e.g., `AccountType`), since java-tron has no mechanism to convert/delete an existing account. This is a DoS/griefing vector reachable purely from an anonymous broadcast transaction (`TransferContract`/`TransferAssetContract`), consistent with the "unprivileged actuator state transition" class in scope. The severity is lower than the original SEDA report because in java-tron a "Normal" auto-created account is functionally similar to one created via `AccountCreateContract` (both can receive/send funds, vote, etc.) — the difference is primarily the `AccountType` field set at creation time and payment of the creation fee by the intended creator rather than the front-runner. So the concrete loss is: the intended owner/payer of the `AccountCreateContract` transaction cannot set the desired `AccountType` for that address, and cannot recoup any fee already reserved for that operation, but core `Normal` account functionality is not blocked.

### Likelihood Explanation
Likelihood is low-to-moderate: the attacker must know (or predict) the target address before the `AccountCreateContract` transaction is confirmed (e.g., by observing it in the transaction pool before block inclusion, similar to standard front-running), and must be willing to pay the transfer fee/energy plus the new-account creation fee themselves. There is no economic incentive for the attacker other than griefing, and the resulting harm is bounded to account-type customization rather than fund loss or consensus impact.

### Recommendation
Consider one of:
1. Allow `AccountCreateContract` to update an existing `Normal` account's `type`/permissions if the caller can prove ownership (e.g., is the account's owner, verified via signature on the `AccountCreateContract` transaction itself, similar to `AccountUpdateContract`), rather than unconditionally rejecting when the address already exists.
2. Document/accept this as intended behavior (as SEDA's team did — "acknowledged"), since the practical damage is limited to `AccountType`/fee semantics rather than fund safety, and mitigate off-chain by broadcasting `AccountCreateContract` with minimal mempool exposure or via private relay.

### Proof of Concept
1. Alice wants to call `AccountCreateContract` to create address `X` with `AccountType.Contract` (or any specific type) and broadcasts the transaction.
2. Attacker observes the pending transaction (or predicts address `X`) and immediately broadcasts a `TransferContract` sending a minimal amount (e.g., 1 sun) to `X`.
3. If the attacker's `TransferContract` is included first, `TransferActuator.execute()` auto-creates `X` as `AccountType.Normal` per [2](#0-1) .
4. Alice's `AccountCreateContract` transaction then fails validation with `"Account has existed"` per [1](#0-0) , and this failure is permanent since there is no deletion/overwrite path for accounts in `CreateAccountActuator`.
