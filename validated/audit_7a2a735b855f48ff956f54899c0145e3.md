I have sufficient evidence to identify the strongest analog. The legacy (non-hardened) `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` paths in `BandwidthProcessor` and `EnergyProcessor` perform an integer division (`frozeBalance / TRX_PRECISION`) before a multiplication with a double-cast ratio — exactly the same "divide-then-multiply causes truncation" bug class flagged in the report. This path is default-active (the "hardened" corrected version requires the `allowHardenResourceCalculation` committee-controlled flag to be enabled) and is invoked on every ordinary bandwidth/energy consuming transaction.

### Title
Truncated-weight-before-multiply in legacy bandwidth/energy limit calculation understates user resource limits - ([File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java], [File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`BandwidthProcessor.calculateGlobalNetLimit` and `EnergyProcessor.calculateGlobalEnergyLimit` compute a user's personal bandwidth/energy limit from frozen TRX. When the network-wide "hardened" resource calculation flag is not enabled (the default unless the committee has activated `allowHardenResourceCalculation`), the legacy formula truncates the user's weight via **integer division before multiplication**:

```java
long netWeight = frozeBalance / TRX_PRECISION;                          // truncated first
return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));  // then multiplied
``` [1](#0-0) 

The equivalent legacy path exists for energy:
```java
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [2](#0-1) 

This is structurally identical to the reported SmartEscrow bug class: `initialTokens + ((_timestamp - start) / vestingPeriod) * vestingEventTokens` — dividing first discards the fractional remainder before it can contribute to the multiplication, systematically rounding the result against the party that should benefit from precision (here, the TRX holder freezing balance for resources).

### Finding Description
`frozeBalance / TRX_PRECISION` is a `long`/`long` integer division that truncates any TRX amount that is not an exact multiple of `TRX_PRECISION` (1,000,000 sun = 1 TRX) down to the nearest whole TRX. That truncated integer weight is then multiplied by the `totalNetLimit/totalNetWeight` ratio. This project's own test suite documents the resulting discrepancy versus the "fractional-weight-preserved" hardened formula:

```java
// V1 path
// Legacy V1 expectation: floor(1.5) * 25.0 = 1 * 25 = 25
Assert.assertEquals(25L, v1New);
// V2 path with the same balance keeps the fractional weight
// Legacy V2 expectation: 1.5 * 25.0 = 37.5 -> 37
Assert.assertEquals(37L, v2New);
``` [3](#0-2) 

The same computation feeds `useAccountNet` and `consumeBandwidthForCreateNewAccount`, which decide whether an ordinary transaction is charged bandwidth resource or a TRX fee, i.e. it is on the hot path of every broadcast transaction: [4](#0-3) 

The corrected/hardened version explicitly preserves the fractional weight through the multiplication and only truncates once, at the very end:
```java
protected long calculateGlobalLimitV2(long frozeBalance,
    long totalLimit, long totalWeight) {
  return BigInteger.valueOf(frozeBalance)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(TRX_PRECISION)
          .multiply(BigInteger.valueOf(totalWeight)))
      .longValueExact();
}
``` [5](#0-4) 

This confirms the developers themselves recognize divide-before-multiply as a precision-loss bug distinct from the hardened fix, and gate the fix behind a committee-controlled flag `allowHardenResourceCalculation`, meaning the legacy vulnerable arithmetic remains the default/active path unless a chain governance proposal enables hardening.

### Impact Explanation
Every account whose frozen balance for bandwidth/energy is not an exact integer multiple of `TRX_PRECISION` (1 TRX) — which, for any account using the V1 (pre-`supportUnfreezeDelay`) freeze path, is common — receives a systematically understated `netLimit`/`energyLimit` relative to the amount that should be proportionally allocated. This causes:
- Users to be charged TRX fees or run out of free/allocated bandwidth/energy sooner than they are entitled to, silently misallocating the resource-for-stake exchange that underlies TRON's fee model.
- A protocol-wide accounting divergence between the "should be" allocation (multiply-then-divide) and the actual allocation (divide-then-multiply), consistently biased in one direction (rounding down the user's own limit) rather than being an unbiased/negligible rounding artifact.

This does not require any privileged actor — it triggers automatically for every account resource calculation with a non-exact-multiple frozen balance, on the default/legacy calculation path, similar in effect (accounting corruption, not consensus divergence since it's deterministic across nodes) to the reported SmartEscrow rounding-in-favor-of-benefactor bug.

### Likelihood Explanation
The vulnerable arithmetic executes on `hardenCalculation() == false` (default), which is the case unless a chain-wide committee parameter proposal for `allowHardenResourceCalculation` is passed — this is not an attacker-controlled setting but the current default network behavior for most existing deployments/chains that have not yet activated hardening. The trigger condition (`frozeBalance` not an exact multiple of `TRX_PRECISION`) is trivially achieved by freezing any TRX amount with a non-zero remainder mod 1,000,000 sun, which any ordinary user can do via a normal `FreezeBalanceContract` broadcast transaction.

### Recommendation
Replace the legacy divide-before-multiply path with the same order-of-operations fix already implemented for the hardened path (`calculateGlobalLimitV1`/`calculateGlobalLimitV2`), i.e. multiply first and divide once at the end using widened (`BigInteger`) arithmetic, and consider making this the unconditional default rather than gating it behind `allowHardenResourceCalculation`, since the "legacy" behavior is provably a precision bug rather than an intentional design choice.
