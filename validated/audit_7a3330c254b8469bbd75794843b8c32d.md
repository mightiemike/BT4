## Title
Permanent freezing of bridged funds when a CEA recipient contract's `executeUniversalTx` hook reverts after deposit succeeds - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
For `isCEA` inbounds whose recipient is a deployed smart contract (not a UEA), `x/uexecutor` first mints PRC20 to the recipient contract and then calls the recipient's `executeUniversalTx` hook to notify/credit it. If that hook call reverts, the module never reverts the already-committed deposit, never creates an `INBOUND_REVERT` outbound (by explicit design for all `isCEA` paths), and the on-chain `RESCUE_FUNDS` escape hatch is only eligible when the *deposit itself* failed — not when the deposit succeeded but the hook failed. The bridged tokens become permanently stranded in the recipient contract's PRC20 balance with no protocol-level path to recover them, mirroring the reported "broken hook blocks user funds" class of bug.

### Finding Description
In `ExecuteInboundFundsAndPayload` (and the parallel `GAS_AND_PAYLOAD` variant in `execute_inbound_gas_and_payload.go`), the `isCEA` smart-contract branch does the deposit first, then calls the hook in a `CacheContext` that is only used to make the hook call and the *gas fee deduction* atomic with each other — the deposit is explicitly documented as staying committed regardless of what happens next: [1](#0-0) 

If `contractErr != nil` (the hook reverted, e.g. because the destination contract is paused, buggy, or the payload data doesn't match its expected format), the code only records a `FAILED` `PCTx` and returns — no revert outbound is scheduled: [2](#0-1) 

This is by explicit design: `isCEA` failures never create an `INBOUND_REVERT` outbound, as stated repeatedly in comments and enforced by tests: [3](#0-2) [4](#0-3) 

The only recovery path in the codebase, `AttachRescueOutboundFromReceipt`, explicitly requires the *deposit itself* (`PcTx[0]`) to have `FAILED` status for CEA inbounds to be rescue-eligible: [5](#0-4) 

Since in the failing-hook scenario the deposit `PcTx[0]` is `SUCCESS` (the mint already landed), this rescue condition can never be satisfied, and no other code path (admin `RevertStuckInbound` requires an `EXPIRED` ballot pre-finalization and errors if the UTX already exists — see `x/uexecutor/keeper/admin_revert.go` lines 53-59) can recover the funds.

### Impact Explanation
Once the deposit succeeds and the hook subsequently reverts, the bridged PRC20 tokens are permanently held in the recipient contract's balance with no mapping inside that contract crediting them to anyone (since the crediting call never completed), and no protocol-level revert/rescue mechanism can trigger. This is a permanent, unrecoverable freezing of user-bridged funds, directly matching the in-scope impact "permanent freezing... of user... funds" reachable via ordinary universal-execution flows.

### Likelihood Explanation
Any unprivileged user (or an attacker crafting a payload against a third-party CEA integration) who bridges `FUNDS_AND_PAYLOAD` / `GAS_AND_PAYLOAD` to a smart-contract recipient whose `executeUniversalTx` implementation reverts for that particular call (e.g., malformed payload, paused contract, insufficient internal validation, reentrancy guard, or any legitimate bug in the destination dApp) triggers this condition. No validator, admin, or TSS misbehavior is required — a single honestly-processed inbound with a reverting destination hook is sufficient.

### Recommendation
Add a fallback/emergency-exit path for the case where the CEA deposit succeeds but the hook call fails: either (a) treat hook failure as rescue-eligible by also checking for a `FAILED` post-deposit `PCTx` entry (not just `PcTx[0]`), or (b) wrap the deposit and hook call together so that a hook failure also reverts the deposit and creates a normal `INBOUND_REVERT` outbound, consistent with the non-`isCEA` behavior.

### Proof of Concept
1. An attacker (or a legitimate but buggy dApp) deploys a CEA contract whose `executeUniversalTx(...)` always reverts for a specific payload shape.
2. A user (or the attacker, to grief a third party's UX) submits an inbound with `IsCEA=true`, `TxType=FUNDS_AND_PAYLOAD`, `Recipient=<that contract>`.
3. Validators vote to quorum; `ExecuteInboundFundsAndPayload` runs: `depositPRC20` succeeds (PRC20 minted to the contract), then `CallExecuteUniversalTx` reverts.
4. `utx.PcTx` ends with `[SUCCESS(deposit), FAILED(executeUniversalTx)]`; no outbound is created (`utx.OutboundTx` is empty, confirmed by existing tests such as `inbound_cea_payload_test.go:295-305`).
5. `AttachRescueOutboundFromReceipt`'s eligibility check `originalUtx.PcTx[0].Status != "FAILED"` fails (since `PcTx[0]` is `SUCCESS`), so `MsgRescueFunds`-triggered rescue can never be attached for this UTX.
6. The PRC20 balance sits permanently in the recipient contract with no path back to the depositor.
