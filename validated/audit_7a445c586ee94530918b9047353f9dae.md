### Title
Bootstrap declare backdoor lets any unauthenticated sender permanently declare classes fee-free and signature-free - ([File: crates/blockifier/src/transaction/account_transaction.rs])

### Summary
The bootstrap-declare fast path, intended only for initializing a brand-new Starknet system, is guarded solely by three transaction-field conditions: `sender_address == bootstrap_address()`, `nonce == 0`, and `charge_fee == false`. There is no state check verifying that the system has not already been bootstrapped, no signature/`__validate_declare__` call, and no nonce increment. Because `bootstrap_address()` is a public, hard-coded constant (the felt encoding of the string `'BOOTSTRAP'`) and `charge_fee` can be made `false` by any attacker who crafts zero/degenerate resource bounds, any external, unauthenticated transaction sender can submit a `Declare` transaction that satisfies this guard at any block height, not only at genesis.

### Finding Description
The bypass condition is defined in `is_bootstrap_declare`: [1](#0-0) 

and consumed unconditionally in transaction execution: [2](#0-1) 

When this branch is taken, the transaction:
- Skips `perform_pre_validation_stage` (nonce/fee pre-checks),
- Skips `__validate_declare__` (no signature verification of any kind),
- Skips fee charging entirely,
- Only enforces "class hash must not already be declared" via `prev_value=0` in the state dict, as mirrored in the Starknet OS Cairo re-execution path: [3](#0-2) 

Critically, the guard is purely a function of transaction *fields* the attacker controls (sender address constant, nonce, and a derived `charge_fee` boolean), not of chain state (e.g., "is this genesis," "has bootstrap already happened," "is a given system-bootstrap flag still unset"). This mirrors the reported bug class exactly: a bootstrap-only administrative/privileged code path that should stop being reachable after the one-time initialization event, but whose guard check does not actually verify that state, so it remains permanently exploitable.

On the gateway side, no additional restriction blocks this address from reaching execution: `validate_nonce` for non-DeployAccount, non-Declare-with-`reject_future_declare_txs` transactions only checks nonce ranges against `account_nonce`, and an undeployed account (such as the `bootstrap_address()`, which is never deployed) simply has nonce `0`, matching the required `nonce == 0` for free: [4](#0-3) 

Additionally, `validate_resource_bounds` is itself skippable via config ("Skip this validation during the systems bootstrap phase"), and `enforce_fee`/`charge_fee` is derived from the transaction's own resource bounds: [5](#0-4) [6](#0-5) 

Nothing in the gateway, mempool, or blockifier verifies that a "bootstrap declare" transaction is only accepted once for the lifetime of the chain, or only during an actual genesis/bootstrap phase.

### Impact Explanation
Any unprivileged party who can submit a transaction can construct a `DeclareTransactionV3` with `sender_address = bootstrap_address()`, `nonce = 0`, and resource bounds engineered to yield `charge_fee == false`, and thereby:
- Declare an arbitrary new Sierra/Cairo class at zero fee, at any point in the chain's life (not just genesis), bypassing the fee market entirely — a direct violation of the network's fee-enforcement invariant and a resource-consumption/DoS vector (state/DA bloat with no compensating fee).
- Perform this "unauthorized account action" (a state-mutating declare) with no signature check whatsoever, since `__validate_declare__` is never invoked for this branch.
- Cause the class-declared state diff to be committed into the canonical state/Patricia tree without having paid for it, since the OS re-execution path faithfully reproduces the same unconditional skip (`SkipTx` hint), meaning the sequencer and the OS agree on this incorrect, fee-free state transition rather than diverging from it — i.e., the bad transition is provably correct/committed, not merely rejected by honest nodes.

This satisfies "unauthorized account action" and "concrete loss" (griefing/fee-bypass economic loss) criteria under the validation rules.

### Likelihood Explanation
High likelihood: the bootstrap sender address is a hard-coded, publicly known constant computed directly from the ASCII string `'BOOTSTRAP'`, requires no private key, no deployed account, and no special privileges to reference as `sender_address` in a submitted transaction. The only engineering effort required by the attacker is crafting resource bounds that make `charge_fee` evaluate to `false` (as already exercised by the project's own test helpers such as `generate_bootstrap_declare` / `create_for_testing_no_fee_enforcement`), which is a client-side transaction-construction detail, not a privileged operation.

### Recommendation
Gate the bootstrap-declare fast path on actual chain state rather than transaction fields alone: e.g., only allow it when the current block number is the genesis block (block 0) and/or introduce an explicit, state-tracked "bootstrap completed" flag that is set the first time a bootstrap declare succeeds and is checked (and enforced) on every subsequent attempt, analogous to fixing the countable-check bug by querying actual admin existence rather than a type-confused truthy value. Additionally, consider requiring this path to be usable only through a privileged/internal invocation path (not a regular submitted `Declare` transaction reachable via the gateway/mempool) so that external senders can never construct a qualifying transaction.

### Proof of Concept
1. Compute `bootstrap_address()` (felt of `'BOOTSTRAP'`, `0x424f4f545354524150`) as documented in `crates/starknet_api/src/executable_transaction.rs`.
2. Construct a `DeclareTransactionV3` with:
   - `sender_address = bootstrap_address()`
   - `nonce = Nonce(Felt::ZERO)`
   - `resource_bounds` set to values that make `enforce_fee` return `false` (e.g., `ValidResourceBounds::create_for_testing_no_fee_enforcement()`, as used in `generate_bootstrap_declare` in `crates/mempool_test_utils/src/starknet_api_test_utils.rs`)
   - An arbitrary, not-yet-declared `class_hash`/`compiled_class_hash` and empty/default `signature`
3. Submit this transaction through the gateway at any block height after genesis (no account deployment or funding required, since the sender address is never validated as a real account).
4. Observe that `is_bootstrap_declare` returns `true` in `AccountTransaction::execute_raw`, causing `__validate_declare__`, nonce increment, and fee charge to all be skipped, while the new class is declared into state — reproducing the class-declaration side effect of `test_bootstrap_declare` in `crates/blockifier/src/transaction/account_transactions_test.rs` but from an external, unprivileged, unsigned submission instead of an internal `AccountTransaction::new_for_sequencing` call.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }

        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
