### Title
Unvalidated zero-address `RevertInstructions.FundRecipient` causes permanent loss of bridged/refunded funds on outbound revert - ([File: x/uexecutor/keeper/outbound.go])

### Summary
`x/uexecutor/keeper/outbound.go`'s `handleFailedOutbound` and `applyGasRefund` select the fund-return address with a bare non-empty-string check on `outbound.RevertInstructions.FundRecipient`, never checking against the zero address. This is the same defect class as the PANTHEON `FEE_ADDRESS` report: a default/unset value that formats as a non-empty string (`"0x0000000000000000000000000000000000000000"`) passes the `!= ""` guard and is used as a real mint/transfer target, permanently burning funds instead of falling back to the safe default (`outbound.Sender`).

### Finding Description
`OutboundTx.RevertInstructions` is populated in `x/uexecutor/keeper/create_outbound.go` directly from the PC-side `UniversalTxWithdraw` event log emitted by `UNIVERSAL_GATEWAY_PC`: [1](#0-0) 

`event.RevertRecipient` is attacker/caller-controlled (any account can invoke the gateway's withdraw path with an unset or zero `revertRecipient`). Later, when an outbound fails or needs a gas refund, the recipient is chosen like this: [2](#0-1) 

and identically in the refund path: [3](#0-2) 

Both checks are `FundRecipient != ""` only. If `RevertRecipient` is the zero address (either because the caller never set it — a common "optional field" pattern — or explicitly supplied `address(0)`), the string is non-empty (`"0x0000...0000"`), so it overrides the safe fallback (`outbound.Sender`) and is fed straight into `common.HexToAddress(refundRecipient)`, which is then used as the mint/deposit target in `CallPRC20Deposit` / `CallUniversalCoreRefundUnusedGas`.

Notably, the codebase already has a defined sentinel for exactly this situation: [4](#0-3) 

but that constant is used only on the `Inbound.Recipient` normalization path (`NormalizeForTxType`), not on `OutboundTx.RevertInstructions.FundRecipient` in `outbound.go`. There is no `ValidateBasic`/`ValidateForExecution` check anywhere that rejects or filters a zero-address `RevertInstructions.FundRecipient` before it reaches the fund-movement calls in `x/uexecutor/keeper/outbound.go`.

### Impact Explanation
Any outbound that fails (revert of bridged `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD`) or accrues an excess-gas refund, and whose triggering `RevertInstructions.FundRecipient` is the zero address, will have its re-minted PRC20 tokens or refunded gas token permanently sent to `0x0`. Since PRC20 supply is minted via `depositPRC20Token`/`refundUnusedGas` directly to that address with no recovery path, this is an irreversible loss of user/protocol funds — matching "permanent loss ... of user or protocol-controlled funds" in the allowed impact list. This is reachable purely from an ordinary user's/relayer's own withdraw call plus a naturally-occurring outbound failure (e.g., destination-chain execution revert, or a swap-refund failure elsewhere in `applyGasRefund`), requiring no privileged actor, malicious validator, or consensus-level manipulation — only honest nodes processing a default/attacker-supplied zero value that was never filtered.

### Likelihood Explanation
Medium. It requires (a) an outbound-triggering call where `revertRecipient` is left as its zero/default value (plausible if the calling contract or SDK wrapper treats it as optional) or is deliberately set to `address(0)`, and (b) that outbound subsequently fails or has excess gas to refund — both of which are ordinary, non-adversarial occurrences in normal cross-chain operation (destination-chain reverts happen routinely). No validator collusion or privileged access is needed, and the vulnerable code path (`handleFailedOutbound`, `applyGasRefund`) is exercised by every outbound's failure/refund flow, which raises the practical likelihood above a purely theoretical edge case.

### Recommendation
In `x/uexecutor/keeper/outbound.go`, harden both recipient-selection sites to treat the zero address the same as an empty string, mirroring the existing `EvmZeroAddress` sentinel already defined in `x/uexecutor/types/inbound.go`:

```go
recipient := outbound.Sender
if outbound.RevertInstructions != nil &&
    outbound.RevertInstructions.FundRecipient != "" &&
    !strings.EqualFold(outbound.RevertInstructions.FundRecipient, types.EvmZeroAddress) {
    recipient = outbound.RevertInstructions.FundRecipient
}
```

Apply the same guard to the `refundRecipient` selection in `applyGasRefund`. Additionally, consider validating `RevertInstructions.FundRecipient` (reject or normalize zero-address) at the point `OutboundTx` is constructed in `create_outbound.go`, so a bad value can never reach the fund-movement keeper functions in the first place.

### Proof of Concept
1. A user (or any caller) invokes the withdraw/outbound path on `UNIVERSAL_GATEWAY_PC` for a `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` tx type without setting `revertRecipient` (or explicitly setting it to `address(0)`).
2. `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:86-88`) records `OutboundTx.RevertInstructions.FundRecipient = "0x0000000000000000000000000000000000000000"`.
3. Universal Validators later vote the outbound as failed via `MsgVoteOutbound` (e.g., destination-chain execution reverted for unrelated reasons — gas, contract error, etc.).
4. `handleFailedOutbound` (`x/uexecutor/keeper/outbound.go:99-161`) evaluates `outbound.RevertInstructions.FundRecipient != ""` → true, sets `recipient` to the zero address, and calls `CallPRC20Deposit(ctx, prc20, 0x0, amount)`, minting the bridged tokens to the burn address instead of back to `outbound.Sender`.
5. The tokens are permanently unrecoverable — no admin, governance, or user action can retrieve funds sent to `0x0` on an EVM-compatible chain.

*Note: I was unable to fully verify, within available tool calls, whether the upstream Solidity/EVM contract layer (`UNIVERSAL_GATEWAY_PC`, outside this repo's Go/Cosmos scope) defaults `revertRecipient` to the zero address when the caller omits it, versus requiring an explicit non-zero value at the contract level. If the contract enforces a non-zero `revertRecipient` (or defaults it to `msg.sender`), likelihood is lower and limited to the case of a caller explicitly passing `address(0)`. This would need confirmation via a Devin session with access to the full contract source, which is outside the scope of what could be indexed here.*
