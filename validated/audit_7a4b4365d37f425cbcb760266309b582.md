### Title
Deterministic account "fixed code" invariant can be silently broken when initialized with an `AccountId`-mode global contract reference - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
Deterministic accounts (NEP-616) are documented and specified as having "a fixed code and fixed initial state associated with it," with the account ID being a commitment (`keccak256` of the borsh-encoded `DeterministicAccountStateInit`) to that code and state. However, `DeterministicAccountStateInitV1.code` is typed as a `GlobalContractIdentifier`, which can be either `CodeHash` (immutable) or `AccountId` (mutable — explicitly documented as allowing "the owner to update the contract for all its users"). Any caller can create a deterministic account whose `code` field commits only to an *account id* reference rather than to the actual bytecode, so the "fixed code" guarantee is not actually enforced for `AccountId`-mode identifiers.

### Finding Description
`action_deterministic_state_init` in `runtime/runtime/src/deterministic_account_id.rs:15` handles the `DeterministicStateInitAction`. On first execution against an uninitialized account it calls `deploy_deterministic_account`, which in turn calls `use_global_contract` (`runtime/runtime/src/global_contracts.rs:76`) with `state_init.code()`. `use_global_contract` accepts a `GlobalContractIdentifier` and, when it is the `AccountId` variant, sets the account's `AccountContract` to `AccountContract::GlobalByAccount(id)` — i.e., "run whatever code is currently stored under this global-contract account id," rather than pinning to a specific hash.

The `AccountId` deploy mode is deliberately mutable: `action_deploy_global_contract` → `initiate_distribution` (`runtime/runtime/src/global_contracts.rs:143-171`) lets the owning account redeploy new code under the same `GlobalContractIdentifier::AccountId(account_id)` identifier at any time (subject only to nonce-based freshness ordering, see `check_and_update_nonce`, `global_contracts.rs:251`). The documentation for `GlobalContractDeployMode::AccountId` even states this is "allows the owner to update the contract for all its users" (`docs/RuntimeSpec/Actions.md:445-448`).

Because the deterministic account ID is derived by hashing the `DeterministicAccountStateInit` (which contains only the `GlobalContractIdentifier`, not the code bytes, when `AccountId` mode is used — `docs/DataStructures/Account.md:156-172`), the account ID does not actually commit to fixed code in this mode: the referenced global-contract owner can later swap the code out from under every account (deterministic or not) that resolved its contract via that `AccountId` identifier, and the deterministic account's ID stays exactly the same even though its executable behavior has changed. This contradicts the documented invariant "Deterministic accounts have a fixed code and fixed initial state associated with it" (`docs/DataStructures/Account.md:140-142`), and is structurally analogous to the reported Allo issue: a component (`IStrategy`/global-contract code) is trusted to conform to an assumed-fixed-behavior contract via an opaque reference/cast, but nothing in the runtime prevents the underlying implementation from being swapped/mutated after the fact, breaking downstream invariants that depend on that reference being immutable.

### Impact Explanation
Any protocol logic, off-chain tooling, or on-chain contract that relies on the deterministic account ID as a cryptographic commitment to fixed code+data (as the spec explicitly promises) can be deceived: the owner of an `AccountId`-mode global contract can change the code that many "deterministic" accounts run, post-creation, with the account IDs unchanged. This can enable a bait-and-switch: create/advertise a deterministic account referencing benign code, get users/relayers/other contracts to trust or fund it based on that code, then swap in different code via `DeployGlobalContract` (`AccountId` mode) to alter behavior (e.g. change what a receiving contract does with funds sent to it), all without the deterministic account ID changing. This is a state-transition/trust-assumption violation reachable purely by ordinary transactions (`DeployGlobalContractAction`, `UseGlobalContractAction`/`DeterministicStateInitAction`) from unprivileged signers.

### Likelihood Explanation
Likelihood is limited by the fact that exploitation requires the attacker to also control (or induce someone to reference) an `AccountId`-mode global contract, and for some other party to place trust in the deterministic account ID as an immutability guarantee — which is exactly what the specification promises ("fixed code and fixed initial state"). Given that the feature explicitly supports and documents `AccountId` mode as an option for `DeterministicAccountStateInitV1.code`, this is directly reachable with a small number of standard transactions and no privileged access.

### Recommendation
Either (a) disallow `GlobalContractIdentifier::AccountId` as the `code` field for `DeterministicAccountStateInitV1`, restricting deterministic accounts to the immutable `CodeHash` variant so the account ID commitment is a true fixed-code guarantee, or (b) explicitly document and enforce (e.g., via a distinct account state/type) that deterministic accounts built from `AccountId`-mode code are *not* immutable, so integrators do not rely on the ID as a code-fixation commitment. Enforcing this at `deploy_deterministic_account` (`runtime/runtime/src/deterministic_account_id.rs:142`)/`use_global_contract` (`runtime/runtime/src/global_contracts.rs:76`) — e.g., rejecting `AccountId` identifiers there — would close the gap while preserving `CodeHash` mode's intended immutability semantics.

### Proof of Concept
1. Owner account `A` calls `DeployGlobalContract { code: <benign_code>, deploy_mode: AccountId }` (`action_deploy_global_contract`, `global_contracts.rs:25`), publishing global contract code referenced by `GlobalContractIdentifier::AccountId(A)`.
2. A user submits `DeterministicStateInitAction` with `state_init = DeterministicAccountStateInitV1 { code: GlobalContractIdentifier::AccountId(A), data: {...} }`. The account id `0s...` is derived deterministically from this struct (`docs/DataStructures/Account.md:167-172`) and `action_deterministic_state_init` → `deploy_deterministic_account` → `use_global_contract` sets the new account's `AccountContract::GlobalByAccount(A)` (`global_contracts.rs:95-98`).
3. Third parties observe/interact with the deterministic account, trusting that its code (and therefore its behavior) is fixed forever by its ID, per spec.
4. Owner `A` later calls `DeployGlobalContract { code: <different_code>, deploy_mode: AccountId }` again. `initiate_distribution` bumps the nonce and distributes the new code under the same `GlobalContractIdentifier::AccountId(A)` (`global_contracts.rs:143-171`), and `apply_distribution_current_shard` overwrites the stored code for that identifier (`global_contracts.rs:191-246`).
5. Every account — including the deterministic account created in step 2, whose ID never changed — now executes `<different_code>` on its next `FunctionCall`, violating the "fixed code" guarantee promised by the deterministic-account ID. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

## Deterministic accounts

Deterministic accounts are an advanced kind of implicit account.
A normal implicit account has a fixed access key that is implicitly associated with it.
Deterministic accounts have a fixed code and fixed initial state associated with it.

### State-initializing data of deterministic accounts

The initial state of a deterministic account is fully defined by an instance of `DeterministicAccountStateInit`.

Key-value pairs in `data` must be at most `max_length_storage_key` and `max_length_storage_value` bytes long,
respectively. These parameters are currently both set to 4Mib (4194304 bytes).

### Deterministic account ID

The account ID is derived from a `DeterministicAccountStateInit` instance.

To derive the deterministic account id, borsh-encode the `DeterministicAccountStateInit` enum instance into raw
bytes. Then use the following formula: `'0s' + keccak256(bytes)[12:32].hex()`.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}
