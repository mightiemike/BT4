### Title
Replay-verify comparator skips state-checkpoint-root validation, allowing a corrupted state root to pass as verified - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) is the function used by proof/replay verification tooling to confirm that a freshly-recomputed `TransactionOutput` matches the trusted, accumulator-authenticated `TransactionInfo` for a given version. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash` (the JMT/state root), `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is a locally-provable gap, already flagged by an in-code TODO.

### Finding Description
`TransactionInfo` commits to several fields that are ultimately what gets Merkle-authenticated through the transaction accumulator: `transaction_hash`, `state_change_hash` (write-set hash), `event_root_hash`, and `state_checkpoint_hash` (the state tree root at checkpoints), plus optional `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. [1](#0-0) 

`ensure_match_transaction_info` is the comparator meant to prove that a recomputed `TransactionOutput` is consistent with a trusted `TransactionInfo` (i.e., that local execution reproduces the authenticated commitment). It verifies status, gas, write-set hash, and event-root hash: [2](#0-1) 

But it stops there — the function's own comment admits the state-root fields are never compared: [3](#0-2) 

This comparator is used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions with the VM and calls `ensure_match_transaction_info` against the archive-provided (trusted) `TransactionInfo` to decide pass/fail of the replay: [4](#0-3) 

Because `state_checkpoint_hash` is never compared, a divergence between the locally recomputed JMT state root (produced by `DoStateCheckpoint::run`, see `execution/executor/src/workflow/do_state_checkpoint.rs:36-49`) and the archived/authenticated root is silently ignored. The write-set hash check alone is insufficient because `state_checkpoint_hash` is derived from applying writes into the *versioned state tree* (an independent tree-construction/merge step), not merely from hashing the raw write-set; a bug in state-tree construction, checkpoint indexing, or hot-state merging can corrupt the root without changing the write-set hash. The same comparator is also referenced from `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`. [5](#0-4) 

### Impact Explanation
This breaks the "proof-integrity" invariant required by the audit scope: authenticated/committed state (here, the JMT state root embedded in `TransactionInfo` and bound into the transaction accumulator) must be independently re-derivable and checked during replay/verification. Because the check is skipped, `replay-verify`/`replay-on-archive` tooling — the primary mechanism operators and the Aptos Labs infra use to detect state divergence bugs across releases/hard forks — can report a clean, successful verification even when the locally computed state root has silently diverged from the correct, network-committed root. This masks state-corrupting VM/executor bugs (e.g., in state-checkpoint merging, hot-state root computation, or the newer trading-native/position state root) instead of catching them, directly matching the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... proof accepted as valid" impact categories in scope.

### Likelihood Explanation
Likelihood of the *comparator gap being exercised* is high in the sense that any real state-computation bug (which is the exact class of bug this tool exists to catch) will not be flagged, i.e., the safety net has a real, unprivileged hole. It requires an underlying divergence bug to actually manifest (this finding does not itself corrupt state), so it functions as a detection-bypass/verification-integrity issue rather than a live state-corruption exploit by itself — but it is a genuine, code-provable break of the intended proof/commitment invariant, and the code's own TODO confirms this is a known, unresolved gap that becomes more consequential as `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state roots are enabled.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against independently recomputed values before returning `Ok(())`, so replay/verify tooling cannot report success while the authenticated state root diverges from local execution.

### Proof of Concept
1. In `storage/db-tool/src/replay_on_archive.rs`, re-execute a chunk whose VM output produces the correct write set/events/gas/status but a different state root than the archived `TransactionInfo` (e.g., simulate a bug in `DoStateCheckpoint::run`'s state-tree merge logic that alters the resulting root without altering the write-set contents/hash — achievable since `state_change_hash` is over the write set only, while `state_checkpoint_hash` is over the merged state tree).
2. Call `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_info, ...)`.
3. Observe the call returns `Ok(())` despite `state_checkpoint_hash` mismatching, because lines 2197-2203 never perform that comparison — i.e., `replay-verify`/`replay-on-archive` reports success for a corrupted-state-root replay. [6](#0-5)

        &self,
        executor: &AptosVMBlockExecutor,
        current_version: &mut Version,
        cur_txns: &mut Vec<Transaction>,
        cur_persisted_aux_info: &mut Vec<PersistedAuxiliaryInfo>,
        expected_txn_infos: &mut Vec<TransactionInfo>,
        expected_events: &mut Vec<Vec<ContractEvent>>,
        expected_writesets: &mut Vec<WriteSet>,
    ) -> Result<Option<Error>> {
        if cur_txns.is_empty() {
            return Ok(None);
        }
        let txns = cur_txns
            .iter()
            .map(|txn| SignatureVerifiedTransaction::from(txn.clone()))
            .collect::<Vec<_>>();
        let txns_provider = DefaultTxnProvider::new(
            txns,
            cur_persisted_aux_info
                .iter()
                .map(|info| AuxiliaryInfo::new(*info, None))
                .collect(),
        );
        let executed_outputs = executor
            .execute_block(
                &txns_provider,
                &self
                    .arc_db
                    .state_view_at_version(current_version.checked_sub(1))?,
                BlockExecutorConfigFromOnchain::new_no_block_limit(), // TODO(HotState): will need to incorporate some features.
                TransactionSliceMetadata::Chunk {
                    begin: *current_version,
                    end: *current_version + cur_txns.len() as u64,
                },
            )
            .map(BlockOutput::into_transaction_outputs_forced)?;
        assert_eq!(executed_outputs.len(), cur_txns.len());

        for idx in 0..cur_txns.len() {
            let version = *current_version;
            *current_version += 1;

            if let Err(err) = executed_outputs[idx].ensure_match_transaction_info(
                version,
                &expected_txn_infos[idx],
                Some(&expected_writesets[idx]),
                Some(&expected_events[idx]),
            ) {
                cur_txns.drain(0..idx + 1);
                cur_persisted_aux_info.drain(0..idx + 1);
                expected_txn_infos.drain(0..idx + 1);
                expected_events.drain(0..idx + 1);
                expected_writesets.drain(0..idx + 1);

                return Ok(Some(err));
            }
        }
