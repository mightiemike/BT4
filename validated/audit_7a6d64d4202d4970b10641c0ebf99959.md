### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting `verify_execution`/`replay_on_archive` accept a divergent state root during transaction replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by the chunk-executor's `verify_execution` path (invoked from backup/restore transaction replay and `db-tool`'s replay-verify/`replay_on_archive` tooling) to confirm that a freshly re-executed transaction output matches the persisted, ledger-info-authenticated `TransactionInfo` for that version. It checks status, gas, write-set hash, and event-root hash, but the code itself documents (via a `TODO(trading-native)` comment) that it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [1](#0-0) .

### Finding Description
`ensure_match_transaction_info` is called from `ChunkExecutor::verify_execution` in the replay path used when restoring/verifying a chunk of transactions from backup: it re-executes each transaction with the VM and compares the resulting `TransactionOutput` to the archived `TransactionInfo` [2](#0-1) . The comparator validates:
- execution status [3](#0-2) 
- gas used [4](#0-3) 
- write-set hash against `state_change_hash` [5](#0-4) 
- event root hash [6](#0-5) 

It never compares the recomputed state (or hot-state / native-position) checkpoint root against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, even though `TransactionInfoV1` carries those fields specifically to authenticate the post-execution state root [7](#0-6) . The comment explicitly acknowledges this: "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [8](#0-7) .

By contrast, `TransactionOutputListWithProof::verify` — used for authenticated client-facing responses — likewise only checks write-set hash, gas, status, and event root against the proof's `TransactionInfo`, and never checks the state-checkpoint hash field either [9](#0-8) . That said, that gap can be partially benign for API-serving because the ledger commit path itself computes the true SMT root from the write sets via `do_state_checkpoint.rs`/`aptosdb_writer.rs`, so a normal client verifying against a canonical, correctly-produced accumulator is not directly defrauded through this API. The concrete, provable break is specifically in the **replay/restore verification path**: `verify_execution`'s only role is to assert that VM re-execution of archived transactions reproduces the same state as was originally committed and authenticated in the accumulator. Because it doesn't check state-checkpoint hashes, a chunk executor performing state-sync/backup-replay/restore can silently accept a re-executed result whose state root differs from the originally-committed, ledger-info-signed state root, as long as write-set bytes, gas, status, and events happen to match. This defeats the entire purpose of replay-verification (which exists to catch execution/consensus divergence and JMT/state divergence introduced by node bugs, backup corruption, or non-determinism) for the state-tree component specifically.

### Impact Explanation
This weakens the trustworthiness of `db-tool replay-verify`/`replay_on_archive` and of chunk-executor-based restore/replay for state-root integrity: a node restoring history from backups, or an auditor running replay-verify against an archive, can get a "successful replay" result even though the reconstructed Jellyfish Merkle / hot-state / native-position root does not match the value that was originally accepted and signed off by validators in the `TransactionInfo`/accumulator. This is exactly the "hard-fork-only divergence during commit, replay, restore, or proof verification" category called out as in-scope, because it means a corrupted or forked state tree resulting from a storage/backup bug, non-deterministic execution, or an intentionally tampered backup archive could pass replay verification undetected, and downstream tooling/restored nodes would proceed to serve or continue building on a state that has silently diverged from the canonical one.

### Likelihood Explanation
The gap is unconditional in the current code (not gated behind the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature as the comment implies it should be) — every call to `verify_execution`/`ensure_match_transaction_info` in the replay path skips checkpoint-hash comparison today. It requires a triggering condition (an existing divergence in JMT/state-root computation, a corrupted backup, or a bug elsewhere), so it is a detection/defense-in-depth gap rather than a spontaneously exploitable one; but given that this is the code path explicitly relied upon by `replay_on_archive` and `replay-verify` to catch such divergence, the missing check is a direct, self-acknowledged (via the TODO) invariant violation in the intended integrity control.

### Recommendation
In `ensure_match_transaction_info`, additionally recompute and compare the state checkpoint hash (and hot-state / `position_state_checkpoint_hash` when applicable) produced by the replay against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, as the TODO already specifies, rather than leaving this unchecked pending a feature flag. If these state roots are not available at the point `TransactionOutput` is constructed (only write sets are), thread them through from the checkpoint-computation stage of `verify_execution`/`ExecutedChunk` so the comparison can occur before accepting the chunk as verified.

### Proof of Concept
Not independently reproducible from static analysis alone (requires constructing a divergent local JMT/state root, e.g., via a backup with corrupted or replayed-out-of-order state, and running `db-tool`'s `replay_on_archive`/`replay-verify` over it, to confirm no error is raised where one should be). This should be validated by a background engineer with test-execution access: build a chunk whose write set/hash matches but whose accumulated state tree differs (e.g., from a pre-existing state discrepancy at the parent version) and confirm `verify_execution` in `execution/executor/src/chunk_executor/mod.rs` returns `Ok` despite the diverging root, as implied by the code's own TODO comment.
