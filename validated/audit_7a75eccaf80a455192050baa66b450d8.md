The premise requires two nodes to have "divergent (but each locally-valid) views of the prior sortition" for the *same* burnchain height, which can only happen if they are following different Bitcoin forks. `get_last_vrf_seed` at [1](#0-0)  is a deterministic pure function of `sort_tx.get_last_snapshot_with_sortition(burn_block_height - 1)`, which is itself a deterministic function of the linear sequence of Bitcoin blocks and burn ops recorded in that sortition-handle's fork, built recursively via `BlockSnapshot::make_snapshot_in_epoch` [2](#0-1) . Given identical burnchain history and identical `burn_dist`/ops for a given block, every honest node computes the same `winning_block_txid`, the same `new_seed`, and the same `final_sortition_hash` [3](#0-2) ; there is no attacker-controlled nondeterminism inside this code path.

For node A and node B to disagree on the "prior sortition's winner" while both are "each locally-valid," they would need to be anchored on two different Bitcoin block sequences (a Bitcoin-level fork/reorg), not something an unprivileged Stacks-layer attacker can force merely by broadcasting block-commits, leader-keys, or burn ops with their own BTC. That scenario is explicitly out of scope: "Bitcoin-consensus defects with no path through this repo." A `MissedBlockCommit` misclassification affecting `winning_block_txid` would itself have to be a bug in the deterministic op-processing/classification logic (`burnchain.rs`, `distribution.rs`) applied identically by all nodes to the same Bitcoin data — the question does not identify such a concrete divergence bug in this scope, only speculates about its downstream effect on `get_last_vrf_seed`. Without a demonstrated attacker-triggerable divergence in the deterministic classification of ops from identical Bitcoin data, the equality (sortition winner == deterministic function of `(burn_dist, VRF_seed, sortition_hash)`) holds on every honest node, and no chain split originates from `get_last_vrf_seed` itself.

    fn get_last_vrf_seed(
        sort_tx: &mut SortitionHandleTx,
        block_header: &BurnchainBlockHeader,
    ) -> Result<VRFSeed, db_error> {
        let burn_block_height = block_header.block_height;

        // get the last winner's VRF seed in this block's fork
        let last_sortition_snapshot =
            sort_tx.get_last_snapshot_with_sortition(burn_block_height - 1)?;

        let vrf_seed = if last_sortition_snapshot.is_initial() {
            // this is the sentinal "first-sortition" block
            VRFSeed::initial()
        } else {
            // there may have been a prior winning block commit.  Use its VRF seed if possible
            sort_tx
                .get_block_commit(
                    &last_sortition_snapshot.winning_block_txid,
                    &last_sortition_snapshot.sortition_id,
                )?
                .expect("FATAL ERROR: no winning block commits in database (indicates corruption)")
                .new_seed
        };
        Ok(vrf_seed)
    }
