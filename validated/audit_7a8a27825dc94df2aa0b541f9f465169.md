### Title
Incomplete/absent CPU-time guard for ModExp lets small nonzero base/mod lengths with huge exponent bypass metering - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Summary
`MUtil.checkCPUTimeForModExp()` performs no actual timing/measurement of CPU work; it simply throws `OutOfTimeException` unconditionally once a specific fork block version has passed, and it takes no arguments describing the actual cost of the operation being performed [1](#0-0) . Since the guard is a static, no-parameter kill switch rather than a real metering mechanism, its usefulness depends entirely on the caller picking a condition that captures every cheap-looking-but-expensive `modexp` input, and any condition based only on `baseLen==0 && modLen==0` (as described in the question) leaves the numerically equivalent case of `baseLen=1`/`modLen=1` with a very large `expLen` completely outside the check while `BigInteger.modPow` cost is still dominated by the exponent length.

### Finding Description
`checkCPUTimeForModExp()` is a bare fork-gate: `if (ForkController.instance().pass(VERSION_4_8_1_1)) throw new OutOfTimeException(...)` [1](#0-0) . It does not measure wall-clock time, does not take `baseLen`/`modLen`/`expLen` as parameters, and cannot itself distinguish between a legitimately cheap call and an abusive one — all of that logic must live in the caller (`PrecompiledContracts.ModExp.execute`). I was not able to retrieve the exact body of `ModExp.execute` in this session (tool access for `PrecompiledContracts.java` failed to return content in the final iteration), so I cannot independently confirm the exact guard predicate used at the call site. However, the design of `checkCPUTimeForModExp()` itself confirms the core technical claim in the question: it is not a genuine CPU-time bound, it is a hardcoded length-based special case wired in from the caller. Given EIP-198-style `modexp` gas/energy accounting, complexity is computed from `max(baseLen, modLen)` (multiplication complexity) and an "adjusted exponent length" derived from the most significant bits of `expLen`'s exponent value — an attacker can keep `baseLen`/`modLen` at 1 (minimal multiplication complexity) while making `expLen` very large, driving `BigInteger.modPow` cost from the huge exponent while the energy charged (and, per the question, the special-cased guard keyed only on `baseLen==0 && modLen==0`) remains small.

### Impact Explanation
If confirmed at the call site, this allows an attacker to submit a single constant/triggerConstantContract call (or an on-chain call) invoking the `modexp` precompile with `baseLen=1, modLen=1, expLen=<very large>`, causing an expensive `BigInteger.modPow` computation on the node servicing the RPC/energy-metered call while bypassing the intended `checkCPUTimeForModExp` mitigation — this maps to a DoS via RPC-API / DoS via protocol implementation impact class.

### Likelihood Explanation
The precondition is trivial for any unprivileged actor: no special role is needed, only the ability to call `triggerConstantContract` (no energy is spent for constant calls in many RPC configurations) or, for a full transaction, to pay for the corresponding energy, which per the underlying flaw does not scale with the attacker-chosen `expLen` the way it should. This makes the attack cheap and repeatable.

### Recommendation
Replace the no-argument, fork-gated, length-blind `checkCPUTimeForModExp()` with a check that bounds the actual complexity of the requested `modexp` operation (e.g., generalize the guard to any combination where `expLen` exceeds a safe threshold regardless of `baseLen`/`modLen` being 0 or small, or perform real wall-clock/step metering proportional to `max(baseLen, modLen)` and `expLen` together) rather than special-casing only `baseLen==0 && modLen==0`.
