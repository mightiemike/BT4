### Title
`ensure_match_transaction_info` omits state/hot-state/position checkpoint hash checks, letting replay-verify tooling accept a diverged authenticated ledger root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used by db-tool's `replay_on_archive` (and by `aptos-debugger`/`aptos-move/cli`) to decide whether a locally re-executed transaction matches the transaction info that was actually committed and authenticated by validator signatures on-chain. The function explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, so a divergence in the committed state/hot-state/position Merkle root is never detected by this integrity check.

### Finding Description
`ensure_match_transaction_info` validates transaction status, gas used, write-set hash, and event root hash against the trusted `TransactionInfo`, but its own comment acknowledges the gap: [1](#0-0) 

It never compares `self`-derived checkpoint roots (there is in fact no `self` value it could compare a hot/position checkpoint hash to, since `TransactionOutput` does not carry these roots) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`. These three fields are part of `TransactionInfoV1` and are hashed into the accumulator leaf that ultimately produces the `LedgerInfo.transaction_accumulator_hash`, i.e. they are proof-bearing/authenticated fields: [2](#0-1) 

The only consumer of `ensure_match_transaction_info` that is meant to catch a mismatch between locally re-executed state and the authenticated, previously-committed ledger state is `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which calls it per-transaction after block execution and treats an `Err` as the sole failure signal for that transaction: [3](#0-2) 

Because the comparator does not check the checkpoint hashes, if the locally computed Sparse Merkle Tree root (state checkpoint), hot-state root, or the new "position state" root diverges from what was authenticated in the archived `TransactionInfo`/`LedgerInfo`, `ensure_match_transaction_info` still returns `Ok(())` as long as status/gas/write-set-hash/event-root happen to match. The tool then reports the chunk as successfully replayed. The same comparator is reused verbatim by `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`, so the blind spot propagates to every tool that relies on it as the ground-truth divergence detector.

### Impact Explanation
This breaks the "authenticated response / proof-bearing data must stay bound to the correct ledger version and root" invariant for a class of self-serve integrity tooling used to detect state divergence (including hard-fork-only divergence) against mainnet archives. A bug in the position-state or hot-state accumulation logic (both are relatively new mechanisms per the `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` features referenced in `do_ledger_update.rs` and `aptos_features.rs`) could silently corrupt the durable committed state root while `replay_on_archive` continues to report a clean, verified replay, because the very comparator responsible for flagging exactly this kind of state corruption does not look at the checkpoint hash fields. This directly matches the "Wrong accumulator root ... accepted as valid" and "Hard-fork-only divergence during commit, replay ... verification" impact categories: an operator relying on `replay_on_archive`/`aptos-debugger` for correctness assurance of the state/hot-state/position roots would get a false positive, masking data corruption in committed ledger state.

### Likelihood Explanation
The gap is not hypothetical: it is an acknowledged TODO in the source itself, guarding a feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that is being staged. Since `position_state_checkpoint_hash` and `hot_state_checkpoint_hash` are newly introduced fields (`TransactionInfoV1`, "trading-native" state roots, hot state), the probability of a real divergence bug in their construction logic (`DoStateCheckpoint`, `do_ledger_update.rs`) during initial rollout is elevated, and this comparator is precisely the safety net meant to catch that class of bug — but it does not.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding value is derivable/known at that call site (e.g., threading the locally-computed state checkpoint root, hot-state root, and position-state root into the comparator, matching them against `txn_info.state_checkpoint_hash()`, `.hot_state_checkpoint_hash()`, and `.position_state_checkpoint_hash()`), before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet, as the code's own TODO already recommends.

### Proof of Concept
1. `replay_on_archive` (or `aptos-debugger`) reads a `TransactionInfo` (V1 variant) from an archived, validator-signed backup for some version `v`, containing a specific `position_state_checkpoint_hash`/`hot_state_checkpoint_hash`. [4](#0-3) 
2. The tool re-executes the transaction locally via `AptosVMBlockExecutor::execute_block` and obtains a `TransactionOutput` whose write-set hash, event-root hash, gas, and status happen to match the archived `TransactionInfo`, but whose locally-recomputed position-state/hot-state Merkle root (not carried on `TransactionOutput` at all) actually diverges due to a bug in position/hot-state checkpoint construction.
3. `ensure_match_transaction_info` is invoked and returns `Ok(())` because it never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. [5](#0-4) 
4. `execute_and_verify` records no error for this transaction, and `Verifier::run`/`replay_on_archive` reports the chunk as replay-verified despite an actual divergence in committed ledger state at that version.

Uncertainty: I was unable to fully explore how `state_checkpoint_hash` (the pre-existing V0 field) is validated elsewhere in the execution/replay pipeline outside this comparator (index limits prevented reading `do_state_checkpoint.rs` and the full `aptosdb_reader.rs` feature-gate logic), so it is possible the classic `state_checkpoint_hash` divergence is caught by another path (e.g., accumulator root mismatch surfaced separately). However, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` are not accumulator-root-bearing on their own (they are auxiliary fields inside `TransactionInfoV1`), so unlike `state_change_hash`/`event_root_hash`, an accumulator-root check alone would not catch a mismatch confined only to these fields if the rest of `TransactionInfoV1` is byte-identical. Confirming the exact production trigger for `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and whether hot-state currently affects the accumulator hash would require deeper file access (`do_state_checkpoint.rs`, feature flag wiring) than the index could provide — starting a full Devin session against the complete repository would allow verifying this end-to-end.
