Based on my investigation, I found a strong structural analog to the Alchemix `RevenueHandler` double-counting bug in agave's SIMD-0123 block-revenue-sharing / `pending_delegator_rewards` mechanism.

### Title
Unbounded re-distribution of `pending_delegator_rewards` in block-reward calculation causes lamport over-issuance / stake-account insolvency - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The vote account's `pending_delegator_rewards` field accumulates block-revenue fees deposited each slot, but is used by `calculate_block_reward()` at every epoch boundary to compute each delegator's proportional share of the *entire accumulated balance*, not just the newly-accrued delta since the last distribution. I was unable to find any code path that decrements or resets `pending_delegator_rewards` after it is paid out as `block_reward`, which mirrors the Alchemix bug where unclaimed/previously-allotted revenue is re-counted as new revenue on every checkpoint.

### Finding Description
Block revenue (transaction fees) is deposited into the leader's vote account via `deposit_delegator_fees()`, which both credits the account's lamports and increments `pending_delegator_rewards`: [1](#0-0) 

The only mutator of this field that I could find is the additive one — `add_pending_delegator_rewards` (used by the `DepositDelegatorRewards` instruction) and `increment_pending_delegator_rewards_checked` (used by fee deposits): [2](#0-1) [3](#0-2) 

At each epoch boundary, `calculate_block_reward()` reads this same `pending_delegator_rewards` value directly off the vote account and computes each stake delegation's proportional share of it: [4](#0-3) 

This computed `block_reward` is then credited to the stake account's lamport balance during distribution: [5](#0-4) 

A repo-wide search for any subtraction, `saturating_sub`/`checked_sub`, or a "set to zero" operation on `pending_delegator_rewards` returned no results — only additive call sites exist. This is architecturally identical to the Alchemix bug: `RevenueHandler.checkpoint()` re-read `IERC20(token).balanceOf(address(this))` (a value that included previously-unclaimed/unallocated revenue) every epoch and re-counted it as new distributable revenue, rather than tracking a delta since the previous checkpoint.

### Impact Explanation
If `pending_delegator_rewards` is never decremented after being distributed, then on every subsequent epoch, `calculate_block_reward()` will again compute a proportional share of the *same, still-nonzero* `pending_delegator_rewards` balance and mint it again to stake accounts via `build_updated_stake_reward`'s `checked_add_lamports(block_reward)`. Since stake-account lamports are directly incremented for each qualifying epoch without any observed corresponding reduction of the vote account's `pending_delegator_rewards` or lamports balance, this would cause repeated re-payment of the same revenue pool, i.e., lamport over-issuance/inflation and eventual insolvency of the vote account relative to the aggregate amount validators believe delegators are owed — a direct analog to "protocol insolvency" and unbounded claim inflation described in the source report.

### Likelihood Explanation
This is reachable purely through ordinary block production and stake-reward distribution (an unprivileged, always-running path — no malicious transaction is even required, since fees are deposited automatically every slot the SIMD-0123/0232 features are active). Given the severity of the potential outcome (lamport supply divergence from validator/capitalization accounting), and that I could not find the corresponding decrement code within the available index, this warrants an explicit code-level confirmation.

### Caveat (important)
I was **not able to conclusively verify** the absence of a decrement/reset of `pending_delegator_rewards`, only the absence of any such call site matching common naming patterns in the indexed portion of the codebase. The codebase index has size limits and may exclude some file contents (e.g., there could be a decrement performed via direct field mutation on `VoteStateV4` that doesn't match the grep patterns used, or done via a different accounting mechanism entirely, such as the `total_active_stake` clamp behaving as an implicit cap rather than reward being re-paid). Given this uncertainty, I recommend starting a full Devin session with complete repository access to trace every mutation site of `pending_delegator_rewards` (including raw struct-field writes in `VoteStateV4`) end-to-end through a full epoch-boundary distribution cycle, and to write a reproduction test that deposits block revenue, distributes rewards once, then advances an epoch without further deposits to check whether `calculate_block_reward` pays out a nonzero amount a second time for the same underlying revenue — directly mirroring the Alchemix POC's method of calling `checkpoint()` twice with no new revenue and asserting claimable amounts are equal.

### Proof of Concept
Conceptual PoC (mirroring the source report's structure), to be implemented and run against the full repo since I cannot execute Rust tests via ask-only tools:
1. Create a vote account and deposit block revenue via `deposit_delegator_fees`, setting `pending_delegator_rewards = X`.
2. Advance one epoch with `block_revenue_sharing` active; call the reward-calculation pipeline once (`calculate_stake_rewards_and_commissions` → `calculate_block_reward`) and distribute (`distribute_epoch_rewards_in_partition`), recording the stake account's post-balance delta (`block_reward_1`).
3. With **no new fee deposits**, advance a second epoch and repeat the reward calculation/distribution.
4. Assert `block_reward_2 == 0` (no new revenue accrued). If `calculate_block_reward` still returns a nonzero value proportional to the still-nonzero `pending_delegator_rewards`, this confirms the double-counting/insolvency bug, exactly as `testClaimNonAlchemicRevenueInsolvency` demonstrated for `RevenueHandler.sol`.

    // pending delegator rewards. If successful, returns the new balance of that
    // account
    fn deposit_delegator_fees(
        &self,
        vote_address: &Pubkey,
        fees: u64,
    ) -> Result<u64, DepositFeeError> {
        let mut account = self
            .get_account_with_fixed_root_no_cache(vote_address)
            .ok_or(DepositFeeError::InvalidVoteAccount)?;

        if *account.owner() != solana_sdk_ids::vote::id() {
            return Err(DepositFeeError::InvalidVoteAccount);
        }

        let account_data = account.data_as_mut_slice();
        let mut vote_state = VoteStateViewMut::new_v4(account_data)
            .map_err(|_| DepositFeeError::InvalidVoteAccount)?;

        vote_state
            .increment_pending_delegator_rewards_checked(fees)
            .ok_or(DepositFeeError::LamportOverflow)?;

        account
            .checked_add_lamports(fees)
            .map_err(|_| DepositFeeError::LamportOverflow)?;

        self.store_account(vote_address, &account);
        Ok(account.lamports())
    }

    pub fn increment_pending_delegator_rewards_checked(&mut self, lamports: u64) -> Option<()> {
        // Size is checked at creation, so this is safe
        let current_pending_delegator_rewards = u64::from_le_bytes(
            self.data[PENDING_DELEGATOR_REWARDS_START_OFFSET..PENDING_DELEGATOR_REWARDS_END_OFFSET]
                .try_into()
                .unwrap(),
        );
        let new_pending_delegator_rewards =
            current_pending_delegator_rewards.checked_add(lamports)?;
        self.data[PENDING_DELEGATOR_REWARDS_START_OFFSET..PENDING_DELEGATOR_REWARDS_END_OFFSET]
            .copy_from_slice(&new_pending_delegator_rewards.to_le_bytes());
