### Title
Unbounded recursive-descent JSON parsing of RPC request bodies allows stack-overflow denial of service - (File: chain/jsonrpc/src/lib.rs)

### Summary
The NEAR JSON-RPC server deserializes every incoming HTTP POST body directly into `near_jsonrpc_primitives::message::Message` via Axum's `Json<Message>` extractor, which is backed by `serde_json`. `serde_json`'s deserializer uses recursive descent with no built-in recursion-depth limit, and nearcore does not add one. Because the `Message`/`WireMessage` types contain an untagged `serde_json::Value` (`params: Value`) and an untagged enum (`WireMessage`), arbitrarily deeply nested JSON arrays/objects (e.g. `[[[[[...]]]]]`) are decoded with one native stack frame per nesting level. The request body size is capped (`limits_config.json_payload_max_size`, applied via `RequestBodyLimitLayer`), but that cap bounds only total bytes, not nesting depth — a payload of a few bytes per nesting level can reach hundreds of thousands of recursion levels while staying well under the size cap, exhausting the worker thread's stack and crashing the process. This mirrors the CVE-2017-11624 bug class: a "stack-consumption" DoS caused by unbounded recursive parsing of attacker-controlled input.

which takes `Json(request): Json<Message>` directly from Axum, meaning `serde_json` performs the full deserialization of the attacker-supplied body before any of nearcore's own validation logic runs.

`Message` deserialization goes through the untagged `WireMessage`/`Broken` wrapper: [2](#0-1) 

and the `Request`/`Notification` types carry a raw, unconstrained `serde_json::Value` for `params`: [3](#0-2) 

`serde_json::Value`'s `Deserialize` implementation recurses once per JSON array/object nesting level with no depth counter — this is a documented characteristic of `serde_json`, not something nearcore code guards against anywhere in the RPC crates (no `recursion_limit`, no pre-validation of nesting depth was found in `chain/jsonrpc*`).

The only protection in front of this parse is a byte-size limit on the whole request body: [4](#0-3) 

`limits_config.json_payload_max_size` bounds total bytes (default documented as 10MB in `chain/jsonrpc/RPC_ARCHITECTURE.md`), but a deeply nested array needs only ~2 bytes (`[`/`]`) per nesting level, so a payload well under that limit can encode many hundreds of thousands of nesting levels — far more than needed to exhaust a typical thread stack (usually a few MiB) during recursive descent.

### Impact Explanation
Any unauthenticated network client that can reach the JSON-RPC HTTP endpoint (`POST /`) can send a single crafted request with deeply nested JSON and crash the handling thread via native stack overflow. In Rust, stack overflow is not a catchable panic — it triggers an abort/SIGSEGV of the process. Because the JSON-RPC server shares the same process as the `ClientActor`/`ViewClientActor`/chunk-production and validation logic in nearcore (the RPC server is one of several components in the same node binary, per the JSON-RPC architecture notes), a crash of the RPC-handling thread/process halts the entire node — including validator duties if the node is a validator — constituting a remotely triggerable full-node halt from a single unauthenticated RPC request. This satisfies the "transaction/RPC-triggered halt" impact category.

### Likelihood Explanation
High likelihood: the endpoint is unauthenticated by default (default port 3030, no signature or account requirement), requires no funds, no valid transaction, and no special privileges — just an HTTP POST with a crafted JSON body under the existing size cap. Constructing deeply nested JSON is trivial (e.g. programmatically generate `"[".repeat(N) + "]".repeat(N)`).

### Recommendation
- Impose an explicit maximum JSON nesting depth check before/while parsing untrusted RPC request bodies (e.g., pre-scan bracket/brace nesting depth, or use a `serde_json` deserializer configured with a depth limit / iterative parser) independent of the byte-size cap.
- Alternatively, parse the top-level `Message` using a non-recursive/streaming approach that rejects excessive nesting early, and only allow bounded recursion for `params`/`id` values.
- Consider running the JSON-RPC HTTP request-parsing path on a thread with strict resource isolation (e.g., a dedicated thread with a guard page and use `catch_unwind`-safe boundaries, or a separate process) so a stack exhaustion cannot bring down the whole node process.
- Add a regression test asserting that a deeply nested JSON payload (within the byte-size limit) is rejected gracefully rather than crashing the server.

### Proof of Concept
```bash
python3 -c "
depth = 200000
body = '{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"status\",\"params\":' + '['*depth + ']'*depth + '}'
print(len(body))
open('payload.json','w').write(body)
"
curl -s -X POST http://127.0.0.1:3030/ \
  -H 'Content-Type: application/json' \
  --data-binary @payload.json
```
The generated payload is only slightly larger than `2 * depth` bytes (well under the default `json_payload_max_size`), yet parsing it via `Json<Message>` in `rpc_handler` (`chain/jsonrpc/src/lib.rs`) drives `serde_json`'s recursive-descent array parser `depth` levels deep, exhausting the worker thread's stack and crashing the node process before any nearcore-level request validation executes.

**Note on uncertainty**: I was unable to directly inspect the exact default numeric value configured for `json_payload_max_size` in the running config (only its presence/usage as a byte-size limiter was confirmed in `chain/jsonrpc/src/lib.rs`, `chain/rosetta-rpc/src/lib.rs`, and example config JSON files), nor could I confirm whether any global `serde_json` recursion-limit feature flag is enabled at the Cargo level across the workspace. If a recursion limit or depth-limited parser is enforced elsewhere (e.g., a custom `Deserializer` wrapper not indexed here), this would reduce or eliminate the finding; a full audit of `Cargo.toml` feature flags for `serde_json`/`axum` and any custom JSON deserializer wrapper is recommended to fully confirm exploitability in this exact fork.

/// A trick to easily deserialize and detect valid JSON, but invalid Message.
#[derive(serde::Deserialize)]
#[serde(untagged)]
pub enum WireMessage {
    Message(Message),
    Broken(Broken),
}

pub fn decoded_to_parsed(res: JsonResult<WireMessage>) -> Parsed {
    match res {
        Ok(WireMessage::Message(Message::UnmatchedSub(value))) => Err(Broken::Unmatched(value)),
        Ok(WireMessage::Message(m)) => Ok(m),
        Ok(WireMessage::Broken(b)) => Err(b),
        Err(e) => Err(Broken::SyntaxError(e.to_string())),
    }
}

pub type Parsed = Result<Message, Broken>;

/// Read a [Message](enum.Message.html) from a slice.
///
/// Invalid JSON or JSONRPC messages are reported as [Broken](enum.Broken.html).
pub fn from_slice(s: &[u8]) -> Parsed {
    decoded_to_parsed(::serde_json::de::from_slice(s))
}
