## Title
Event-V2→V1 translators (incl. `OptInTransferTranslator`) resolve resources against the *latest* state instead of the event's historical version, making replay of `TranslatedV1EventSchema` non-deterministic across state upgrades - (File: `storage/indexer/src/event_v2_translator.rs`)

### Summary
`EventV2TranslationEngine::get_state_value_bytes_for_resource` / `get_state_value_bytes_for_object_group_resource`, used by every `EventV2Translator` implementation (including the one registered for `OPT_IN_TRANSFER_TYPE`, i.e. `OptInTransferTranslator`), fetch the referenced resource (e.g. `TokenEventStoreV1Resource`) from `main_db_reader.latest_state_checkpoint_view()` rather than from a state view pinned at the historical version of the `ContractEventV2` being translated: [1](#0-0) 

This state view is used to read the resource's embedded `EventHandle` (key + count) that determines the derived `ContractEventV1`'s `EventKey` and `sequence_number`, which are then persisted verbatim into `TranslatedV1EventSchema`: [2](#0-1) 

### Finding Description
The internal indexer's `process_a_batch` iterates historical transactions/events from `start_version` to `end_version` and, for every `ContractEvent::V2`, calls `translate_event_v2_to_v1`, which dispatches to the type-specific translator via `event_v2_translation_engine.translators`. Every translator that needs to recover the legacy `EventHandle` (creation number / running count) for the equivalent V1 event calls `engine.get_state_value_bytes_for_resource(...)`, which unconditionally reads `self.main_db_reader.latest_state_checkpoint_view()` — the *current* (at indexing time) state — not a state view snapshotted at the event's own version.

This is architecturally sound only if resource layout/values relevant to the translation are immutable once created (e.g., a fixed `EventHandle` creation number is assigned once and never changes). However, the correctness of the derived `ContractEventV1` (`key`, `sequence_number`) depends on reading the resource *as it existed at that historical version* — e.g. the running event count inside `TokenEventStoreV1Resource`/`CoinStoreResource`/`AccountResource`, etc. — because `get_next_sequence_number` uses a cache keyed by `EventKey` seeded from that count: [3](#0-2) 

If the indexer is:
1. run live/incrementally as blocks land (each `process_a_batch` call sees state at approximately the point in time closest to that version), versus
2. run later during a fast-sync/restore replay pass or a reprocessing pass that starts from a *different* internal indexer progress marker and reads state via `latest_state_checkpoint_view()` at a much later point in chain history,

then the two runs can observe different underlying resource bytes for the same historical `(address, struct_tag)` pair whenever the account/resource has since been mutated, migrated (e.g. legacy `TokenEventStoreV1Resource`/`token_event_store` fields deprecated or replaced under a newer token standard), or deleted and recreated. Because the translator derives the `EventKey` and `sequence_number` from whatever it reads at call time rather than at the event's true version, the same input `ContractEventV2` at the same version can be translated into two different `ContractEventV1` values depending solely on *when* translation is executed, not on the immutable historical ledger state at that version.

This breaks the required invariant that replay/reprocessing of `TranslatedV1EventSchema` for a given `(version, index)` produces a byte-identical `ContractEventV1` to what was recorded during the original live indexing pass — a general property of the whole `EventV2Translator` trait, not specific to any protocol-level VM execution, but real for this indexer's derived-state artifact.

### Impact Explanation
`TranslatedV1EventSchema` is served back out through `DBIndexer::get_events_by_event_key` as an authenticated-looking substitute for `ContractEvent::V2` when API/RPC callers request legacy V1-style events: [4](#0-3) 

A node whose internal indexer replays from a checkpoint/restore (fast-sync, indexer DB rebuild, or backup restore) can end up with `TranslatedV1EventSchema` entries diverging from what another node computed during live indexing for identical historical versions, producing different `EventKey`/`sequence_number` for the same logical event depending on indexer implementation timing — a determinism/consistency defect in a derived, non-consensus-critical data structure. It does not corrupt the authenticated ledger state, JMT/accumulator proofs, transaction outputs, or write sets themselves, since `TranslatedV1EventSchema` is an internal-indexer convenience index, not part of consensus-verified storage or state-proof material.

### Likelihood Explanation
Triggering divergence requires only unprivileged, ordinary use of the chain (any transaction that mutates or migrates the underlying legacy resource, e.g. `TokenEventStoreV1Resource`) combined with the indexer being restarted/replayed at different points — a routine operational scenario for node operators doing fast-sync or indexer-db rebuilds, not attacker-controlled maliciousness. This is a data-consistency bug in the auxiliary indexer, not a corruption of the state-commitment or proof layer.

### Recommendation
Have `EventV2TranslationEngine::get_state_value_bytes_for_resource`/`get_state_value_bytes_for_object_group_resource` accept and use a state view/version pinned to the version of the `ContractEventV2` being translated (e.g. via `main_db_reader.state_view_at_version(version)` or equivalent) instead of `latest_state_checkpoint_view()`, so translation is a pure, deterministic function of the historical ledger state at that version, guaranteeing `TranslatedV1EventSchema` is byte-identical regardless of when/how many times it is recomputed.

### Proof of Concept
Not able to fully construct an executable PoC from static review alone; the mechanism is: (1) index a version live so `TranslatedV1EventSchema[(v, idx)]` is written while the relevant legacy resource (e.g. `TokenEventStoreV1Resource`) is in state S1; (2) mutate/replace that resource in a later transaction (state S2); (3) wipe the internal indexer db and call `process_a_batch`/`process` again over the same version range — since `get_state_value_bytes_for_resource` reads `latest_state_checkpoint_view()` (now reflecting S2, not the historical S1), the recomputed `ContractEventV1` (`EventKey`/`sequence_number`) for that historical version can differ from the originally-recorded one. This would need to be validated end-to-end in a running test harness (e.g. extending `execution/executor/tests/internal_indexer_test.rs`) to confirm actual divergent bytes, which was not run here.     pub fn get_state_value_bytes_for_resource(
        &self,
        address: &AccountAddress,
        struct_tag: &StructTag,
    ) -> Result<Option<Bytes>> {
        let state_view = self
            .main_db_reader
            .latest_state_checkpoint_view()
            .expect("Failed to get state view");
        let state_key = StateKey::resource(address, struct_tag)?;
        let maybe_state_value = state_view.get_state_value(&state_key)?;
        Ok(maybe_state_value.map(|state_value| state_value.bytes().clone()))
    }
