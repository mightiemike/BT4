Based on my investigation, I found a directly analogous issue, though it appears to already be patched behind a protocol-version gate rather than being an active, currently-exploitable vulnerability in the default configuration.

### Title
Meta-transactions could bypass the "full access key required" restriction on `WithdrawFromGasKey`, allowing unauthorized draining of gas-key funds through a lower-privilege delegated path - ([File: runtime/runtime/src/action_validation.rs])

### Summary
NEAR's `WithdrawFromGasKey` action moves NEAR from a gas key's prepaid balance to the owning account. Similar to the Airflow bug where an authenticated-but-under-privileged user could still perform a privileged update because the specific action lacked its own permission check, `WithdrawFromGasKey` could historically be smuggled inside a `Delegate` (meta-transaction) action and executed, even though the intent of the design is that this sensitive, fund-moving action should not be reachable via delegated/meta-transaction execution paths.

### Finding Description
The fix (`ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate`, gated by `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`) is visible in `runtime/runtime/src/action_validation.rs`, and the accompanying regression test [1](#0-0)  explicitly demonstrates the pre-fix behavior: a `DelegateAction` whose inner action is `WithdrawFromGasKey` was **admitted and executed successfully**, draining the gas key balance [2](#0-1) . Only after a protocol upgrade to `RejectWithdrawFromGasKeyInDelegate` is the action rejected at admission with `WithdrawFromGasKeyNotAllowedInDelegate` [3](#0-2) . The root cause is the same class as the Airflow report: a state/permission-mutating action (withdraw funds) was validated for its generic action-shape constraints (access-key `RequiresFullAccess`, single-action, receiver/method match, per `verify_function_call_permission` in `runtime/runtime/src/verifier.rs`) but was missing a dedicated check preventing it from being wrapped in the lower-trust `Delegate`/meta-transaction envelope, which has different signer/relayer semantics than a direct transaction.

### Impact Explanation
If exploited pre-fix, an account holder could route a `WithdrawFromGasKey` action through a `Delegate` action — potentially via a relayer — to move gas-key prepaid balance to the account despite the action being intended as "must only be available via transactions, not via contract execution" and (per the fix) not via delegation either, per the doc comment on `WithdrawFromGasKeyAction`. This is a concrete unauthorized value movement class matching CWE-284 (improper access control), analogous to Airflow's missing per-action permission check.

### Likelihood Explanation
This is confirmed already fixed and gated behind `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`, requiring a protocol version upgrade to take effect network-wide. I could not conclusively determine from the index whether the current default `PROTOCOL_VERSION` in this repo snapshot has this feature enabled (stable) or still pending — the test itself early-returns when the feature isn't enabled at `PROTOCOL_VERSION`, and asserts the pre-fix protocol version must still be `>= MIN_SUPPORTED_PROTOCOL_VERSION`, implying nodes running older-but-still-supported protocol versions could still be vulnerable to this exact bypass during the network's upgrade window. I was unable to verify from available index content whether `RejectWithdrawFromGasKeyInDelegate.protocol_version()` is below or at/above the current stable `PROTOCOL_VERSION` value in `core/primitives-core/src/version.rs`.

### Recommendation
Confirm `RejectWithdrawFromGasKeyInDelegate` is enabled at (or below) the current stable protocol version for all supported protocol versions in production, and audit for any other privileged/fund-moving actions (e.g. `TransferToGasKey`, future single-purpose actions) that similarly lack an explicit "not allowed in delegate" check, applying the same defense-in-depth pattern used for `WithdrawFromGasKey`.

### Proof of Concept
Use the existing regression test as the reproduction recipe: `test_reject_delegated_gas_key_withdraw_protocol_upgrade` in `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs` sets protocol version to `RejectWithdrawFromGasKeyInDelegate.protocol_version() - 1`, then submits a `Delegate` action whose inner action is `WithdrawFromGasKey` on the sender's own gas key signed only by the sender's regular (non-full-access at the gas-key level) signer relayed through a separate `relayer` account, and shows the withdrawal succeeds and drains the gas key pre-upgrade [4](#0-3) .

    env: &TestLoopEnv,

    let delegate_action = DelegateAction {

        receiver_id: sender.clone(),
        actions: vec![

                public_key: gas_key.public_key(),
                amount: WITHDRAW_AMOUNT,

            .try_into()
            .unwrap(),
        ],
        nonce: env.rpc_node().get_next_nonce(sender),
        max_block_height: 1_000_000,
        public_key: sender_signer.public_key(),
    };
    let signed_delegate = SignedDelegateAction::sign(&sender_signer, delegate_action);
    env.rpc_node().tx_from_actions(
        relayer,
        sender,
        vec![Action::Delegate(Box::new(signed_delegate))],
    )
}

fn test_reject_delegated_gas_key_withdraw_protocol_upgrade() {
