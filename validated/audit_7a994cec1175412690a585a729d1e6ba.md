## Analysis Result

Searching write-set/transaction-info construction, accumulator/Merkle proof verification, restore flows, and authenticated API responses for a state-integrity analog to the Chainlink staleness bug (missing sanity check against a trusted reference before accepting data), the strongest local candidate is the incomplete field-comparison in `TransactionOutput::ensure_match_transaction_info`.

### Title
`ensure_match_transaction_info` silently skips comparing state-checkpoint hashes, defeating replay/execution-verification against the authenticated `TransactionInfo` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used across the codebase (chunk executor's `verify_execution`, `replay_on_archive`, `aptos-debugger`) to confirm that a freshly (re-)executed `TransactionOutput` matches the trusted, accumulator-authenticated `TransactionInfo` for a version. It checks status, gas used, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), as acknowledged by its own TODO comment. [1](#0-0) 

### Finding Description
The comparator is meant to be the safety net that catches divergence between local computation and the value already committed/authenticated by consensus (analogous to the oracle staleness check that should reject stale/wrong data before it's trusted). It verifies transaction status, gas, write-set hash and event-root hash: [2](#0-1) 

But it stops short of validating the state/hot-state/position checkpoint hashes, with the code itself documenting the gap: [3](#0-2) 

This function is invoked by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which re-executes a chunk locally and calls `ensure_match_transaction_info` per transaction against the chunk's supplied `TransactionInfo` list to decide whether local execution matches expected results before verified chunks are treated as validated: [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`, both of which exist specifically to independently re-derive state and flag any divergence from the archived/committed ledger data — i.e., exactly the "hard-fork-only divergence" detection tooling this task asks about.

Because `state_checkpoint_hash` is the field that binds a transaction's execution to the resulting Merkle/Jellyfish state root, omitting it means these tools can report a **successful, matching replay/verification even when the locally-computed state root diverges** from the authenticated one in the accumulator leaf. Any bug in state-checkpoint construction (e.g., `DoStateCheckpoint`, hot-state hashing, or a future on-chain feature interacting with `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO`) would corrupt the state root while still passing this check, since write-set hash, event hash, gas, and status can all match while the state root differs (state root is a function of applying the write set to prior state, not solely a hash of the write set itself).

### Impact Explanation
This breaks the "authenticated proof/state binding must stay correct" invariant for the specific class of tools designed to catch commit/replay/restore divergence:
- `verify_execution` in the chunk executor is one of the mechanisms guarding state-sync/chunk-apply correctness before accepting a chunk as validated.
- `replay_on_archive` and `aptos-debugger` are the primary tools operators/auditors use to detect state-root divergence bugs across historical/archived data (hard-fork risk detection).

If either tool is relied upon to certify "no divergence" this gap means a silent state-root corruption (from a VM/state-checkpoint bug) would not be flagged, i.e., a wrong state root could be accepted as consistent with the ledger — directly matching the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category.

### Likelihood Explanation
Medium-to-high for *detection failure* (not exploitation): the gap is not attacker-triggered but is a passive false-negative in verification tooling — it activates whenever any state-checkpoint-hash-affecting bug exists elsewhere (e.g., in `DoStateCheckpoint`/hot-state/position-state-checkpoint logic), silently hiding it from the tools whose entire purpose is to catch such bugs. The TODO comment confirms this is a known, currently-unaddressed gap, and it is explicitly tied to the upcoming `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature, implying it is presently an active blind spot for the "trading-native" position-state-checkpoint hash and hot-state root.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute and compare `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against `txn_info`'s corresponding fields before returning `Ok(())`, mirroring the existing write-set/event-hash checks. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the code comment itself flags.

### Proof of Concept
Not applicable as an exploit PoC — this is a verification-logic omission, not an attacker-triggerable transaction. Demonstration path: construct a `TransactionOutput` whose write-set/events/gas/status match a target `TransactionInfo`, but whose actual resulting state (post state-checkpoint) differs (e.g., inject a divergent state-checkpoint hash through a modified `DoStateCheckpoint` in a test harness); `ensure_match_transaction_info` will return `Ok(())` despite the state root mismatch, which can be confirmed by comparing `txn_info.state_checkpoint_hash()` against the independently computed hash — the current implementation never performs that comparison, at [5](#0-4) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
