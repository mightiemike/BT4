## Finding: `replay_on_archive` / chunk-executor `verify_execution` accepts a replay whose state root diverges from the committed ledger

### Title
Replay-verification tooling (`db-tool replay-on-archive` and `ChunkExecutorInner::verify_execution`) accepts a divergent state/hot-state/position-state root as a successful replay - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole per-transaction integrity check used by both `storage/db-tool/src/replay_on_archive.rs` (`Verifier::execute_and_verify`) and `execution/executor/src/chunk_executor/mod.rs` (`ChunkExecutorInner::verify_execution`) to decide whether a locally re-executed transaction matches the authenticated on-chain `TransactionInfo`. The function checks status, gas, write-set hash (`state_change_hash`) and event root hash, but — by its own documented admission — never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The comparator ends with an explicit TODO acknowledging the gap: [2](#0-1) 

This function is the only correctness check performed in two independent verification call sites:
1. `db-tool`'s `replay_on_archive` verifier, which re-executes historical transactions and calls `ensure_match_transaction_info` per transaction to decide pass/fail: [3](#0-2) 
2. `ChunkExecutorInner::verify_execution`, used during backup/replay verification of a transaction chunk, which likewise loops and calls the same function per transaction: [4](#0-3) 

By contrast, the *normal* commit path (`update_ledger` → `DoStateCheckpoint::run`) does independently validate the computed state/hot-state/position-state checkpoint hash against the known hash from `TransactionInfo`: [5](#0-4)  and [6](#0-5) . But `verify_execution` is a distinct, standalone replay-check path that does **not** go through `DoStateCheckpoint`; it only calls `ensure_match_transaction_info`, so it never independently recomputes/compares the checkpoint roots.

### Impact Explanation
This falls squarely in the "Hard-fork-only divergence during commit, replay, restore, or proof verification" category from the state-integrity gate: if the local VM's resulting state tree (state root, hot-state root, or the newer position/trading-native state root) diverges from what is authenticated in the committed `TransactionInfo` — e.g., due to a non-determinism bug, a storage corruption, or a state-view bug — both `replay_on_archive` (used to audit historical mainnet replay correctness) and the chunk-executor's `verify_execution_mode` (used by backup/restore verification tooling) will report the replay as **successful** even though the actual state content differs. This defeats the purpose of these tools, which exist specifically to catch state divergence before it propagates or is trusted, and could mask a genuinely corrupted/incorrect ledger state as "verified."

### Likelihood Explanation
This is not attacker-triggerable on its own (it requires an underlying execution/state divergence to exist), but it is a real, standing gap in the verification code itself — not speculative. The comment in the source is explicit that this check is missing and names the exact consequence ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"), which is a direct local admission of a broken proof-verification invariant.

### Recommendation
Extend `ensure_match_transaction_info` to accept and check `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the recomputed checkpoint hashes for the same transaction, so `replay_on_archive` and `verify_execution` fail loudly on any state-root mismatch instead of silently ignoring it, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any state root path relying on this comparator) is enabled in production verification flows.

### Proof of Concept
Not independently exploitable without a separate root-cause bug that produces divergent state; the "proof" here is that the code path itself, by inspection, cannot detect such a divergence:
1. Suppose local re-execution (via `AptosVMBlockExecutor`) computes a correct write-set/events/gas/status matching the recorded `TransactionInfo` (so all four checks in `ensure_match_transaction_info` pass) but produces a different resulting state tree/root (e.g., due to a JMT/hot-state/position-state computation bug elsewhere).
2. `replay_on_archive::execute_and_verify` (types/src/transaction/mod.rs:2139-2204 via storage/db-tool/src/replay_on_archive.rs:392-397) and `ChunkExecutorInner::verify_execution` (execution/executor/src/chunk_executor/mod.rs:692-697) both call only `ensure_match_transaction_info`, which does not compare `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
3. Both tools report the transaction/chunk as successfully verified even though the state root diverges — confirmable purely by reading the comparator's field list and the TODO comment acknowledging this exact scenario.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
