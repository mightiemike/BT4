### Title
`accounts_data_len` underflow during startup index generation on duplicate-pubkey accounting - ([File: accounts-db/src/accounts_db.rs])

### Summary
During accounts-index generation at startup, `AccountsDb::generate_index` subtracts the total data length attributable to duplicate account entries (`accounts_data_len_from_duplicates`) from the running total (`total_accum.accounts_data_len`) using a plain `-=` operator instead of a checked subtraction, unlike the adjacent capitalization computation which explicitly uses `checked_sub(...).expect(...)`.

### Finding Description
In `generate_index`, capitalization is decremented with an explicit underflow guard: [1](#0-0) 
but the accounts data length in the very next line uses unchecked arithmetic: [2](#0-1) 
`total_accum.accounts_data_len` and `accounts_data_len_from_duplicates` are both `u64` accumulated from `visit_duplicate_pubkeys_during_startup` over all storages/duplicate pubkeys during index generation at startup (from a snapshot or fastboot load): [3](#0-2) 
If the duplicate-derived data length ever exceeds the total accumulated data length (e.g., due to a bug in how `accounts_data_len` is accumulated across duplicate/obsolete/zero-lamport accounts, or a discrepancy in how `stored_size_alive`/`accounts_data_len` is tracked when duplicates span differing account data sizes), this subtraction underflows a `u64` and panics in debug builds, or silently wraps to a huge value in release builds (Rust arithmetic without overflow checks does not panic in release mode).

This is analogous to the reported Solidity issue where an unchecked subtraction (`paths[i].length` not checked before use) can underflow; here the root cause is the same bug class — an unchecked subtraction on an accumulator that is not proven safe by prior validation, right next to a sibling line that *is* protected with `checked_sub`.

### Impact Explanation
`accounts_data_len` feeds into runtime accounting (e.g., cap on total accounts data size, and is reported/logged as `total_accum.accounts_data_len`), and startup index generation happens on every validator boot/fastboot from a snapshot. A wraparound here (in release builds, since overflow checks are typically off) would silently corrupt the tracked total accounts data length, which downstream code uses for resource limiting and capacity checks — potentially causing incorrect enforcement (allow unbounded growth) or divergent behavior across nodes if the corruption differs by local state. This falls under a disproportionate/incorrect-accounting class of impact (not a crash, but a silent state corruption of a size counter used by consensus-adjacent accounting).

### Likelihood Explanation
The likelihood of an actual underflow depends on whether `accounts_data_len_from_duplicates` can, by construction, exceed `total_accum.accounts_data_len`. Under normal operation, this invariant probably holds (duplicates are a subset of the accounts accounted for in the total), but this has not been proven from the code inspected; the presence of an explicit `checked_sub` for the twin `capitalization` field just above it suggests that the developers know the analogous computation *can* be at risk, and chose to guard capitalization but not accounts_data_len. Since I could not fully trace all contributors to `total_accum.accounts_data_len` and `accounts_data_len_from_duplicates` (visit_duplicate_pubkeys_during_startup internals, obsolete-account interactions), I cannot confirm a concrete practical trigger. This should be treated as a hardening gap rather than a proven exploit.

### Recommendation
Use `checked_sub` (or `saturating_sub` with a `debug_assert!`/warning on underflow) for the `accounts_data_len` update, mirroring the capitalization guard:
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```
This converts a silent wraparound (release) or unlabeled panic (debug) into an explicit, diagnosable failure, consistent with the neighboring capitalization check.

### Proof of Concept
Not independently reproducible from static inspection alone. Confirming an actual underflow requires demonstrating a startup/snapshot scenario where the accumulated `accounts_data_len_from_duplicates` (summed by `visit_duplicate_pubkeys_during_startup` across duplicate pubkeys) exceeds `total_accum.accounts_data_len` accumulated during storage scanning at [4](#0-3) . I was not able to trace `visit_duplicate_pubkeys_during_startup`'s internals within the available context to construct a concrete failing sequence, so this finding should be validated with a live Devin session that can inspect `visit_duplicate_pubkeys_during_startup` and construct a snapshot/storage layout (e.g., duplicate pubkeys with obsolete/zero-lamport accounts) that could exceed the total.
