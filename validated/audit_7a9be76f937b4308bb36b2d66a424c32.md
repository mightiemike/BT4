### Title
Webhook domain header is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts, packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
`shopify.webhooks.validate`/`process` authenticate an incoming webhook solely by recomputing an HMAC over the raw request body with the app's shared `apiSecretKey`. The `X-Shopify-Shop-Domain` header (and other identity headers such as topic/webhook-id) are read after HMAC verification but are never included in the HMAC computation, so they are not cryptographically bound to the signed payload. Any party who can obtain one genuine webhook delivery (body + valid HMAC) for a shop that uses the app can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a different (victim) shop installed on the same app, and the request will still pass validation.

### Finding Description
`validateHmacFromRequestFactory` computes `localHmac` from `apiSecretKey` and `rawBody` only, and compares it against the `X-Shopify-Hmac-Sha256` header value using `safeCompare` <cite repo="patrichyt/shopify-app-js--014" path="packages/apps/shopify-api/lib/utils/hmac-validator.ts" start="168,200" end="168,200" />. Once this passes, `validateFactory` calls `checkWebhookHeaders`, which simply reads `domain`, `topic`, `webhookId`, `apiVersion` from the (unauthenticated) headers and returns them as trusted fields with `valid: true` <cite repo="patrichyt/shopify-app-js--014" path="packages/apps/shopify-api/lib/webhooks/validate.ts" start="89,145" end="97,145" />. Because the `apiSecretKey` is shared across all shops that install the same app, and the HMAC only covers the body, the same (body, hmac) pair remains valid regardless of which shop domain is claimed in the header.

Downstream, `authenticateWebhookFactory` in both `shopify-app-remix` and `shopify-app-react-router` trusts `check.domain` as the authenticated shop identity and immediately uses it to look up and attach the corresponding offline session and Admin API client to the webhook handler context, with no secondary check that the domain matches an expected/authorized value <cite repo="patrichyt/shopify-app-js--014" path="packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts" start="35,96" end="52,102" />. This mirrors the VodkaVaultV2 flaw: the callback (`afterDepositExecution`/webhook handler) is invoked with attacker-controllable metadata (the `deposit.account`/`X-Shopify-Shop-Domain`) without validating that this metadata was actually the object of the authenticated/initiating event.

### Impact Explanation
An attacker who controls or has installed the app on their own shop (an unprivileged, single-merchant actor) can capture one legitimate webhook delivery from Shopify to their own store, then forge a POST to the app's webhook endpoint with the same body/HMAC but with the `X-Shopify-Shop-Domain` header set to any other shop that has the app installed. The webhook processing pipeline will treat the request as an authenticated webhook "from" the victim shop, load the victim's offline session, construct an Admin API client authenticated as the victim, and invoke the app's webhook handler business logic using victim identity/session. This is a cross-tenant access vulnerability that could lead to unauthorized data access/mutation on behalf of another merchant, depending on what the app's webhook handlers do with the provided session/admin client and payload.

### Likelihood Explanation
Any merchant that installs the app can trivially capture a real webhook delivery to their own shop endpoint (e.g., via the app's own delivery logs, a proxy, or simply having an endpoint log raw headers/body). No secret material beyond what is already exposed to the merchant/attacker is required, and forging the header on a replayed request is straightforward HTTP tampering. The bar to exploit is low, and the resulting session/domain context is directly consumable by the app's webhook business logic.

### Recommendation
Bind the shop domain (and other identity headers used to route/authorize the request, e.g. topic, webhook-id) to the HMAC by including them in the signed material, or cross-validate the domain claimed in the header against an independent trust anchor (e.g., require it to match the domain associated with the webhook subscription/registration recorded when the webhook was registered, or validate using Shopify's newer signed webhook mechanisms that scope the signature to the specific shop/topic). At minimum, the webhook consumer should not unconditionally trust `check.domain` to select a session without additional verification that ties the specific HMAC to that specific shop.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com` and capture a real inbound webhook request Shopify sends, including body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `apiSecretKey`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and the same `H`, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com` (a real shop that also installed the app), keeping other required headers.
3. `shopify.webhooks.validate`/`process` recomputes HMAC over `B`, which matches `H` (since the header is not part of the signed data), so `valid: true` is returned with `domain: 'victim.myshopify.com'` per `checkWebhooksHeaders` <cite repo="patrichyt/shopify-app-js--014" path="packages/apps/shopify-api/lib/webhooks/validate.ts" start="105,131" end="107,133" />.
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` with `check.domain = 'victim.myshopify.com'`, loading the victim's session and attaching an Admin API client scoped to the victim shop for the attacker-controlled request <cite repo="patrichyt/shopify-app-js--014" path="packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts" start="52,92" end="52,96" />.
