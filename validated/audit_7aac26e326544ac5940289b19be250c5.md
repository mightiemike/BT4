Transaction-triggered oversized state witness causes a hard chunk-production halt on the target shard - (File: `runtime/runtime/src/function_call.rs`)

### Summary
The Salty finding shows an unprivileged user-facing operation (liquidation/borrow) that hard-stops whenever an internal validation threshold is crossed, with no fallback, and only a slow governance vote can raise the limit. Nearcore has a structurally analogous mechanism: `ChunkStateWitness` size is bounded by hard caps (`MAX_UNCOMPRESSED_STATE_WITNESS_SIZE`, `MAX_COMPRESSED_STATE_WITNESS_SIZE`) and soft/hard storage-proof limits, and a single function-call receipt that records outsized "storage proof" content can blow the witness past the point where it can be distributed and endorsed in time, causing the shard's chunk production to stall for consecutive blocks — a transaction-triggered halt whose only remedy is an operator-level protocol/config change (raising block-production delay or the byte caps), not something end users can influence in real time. This mirrors the DAO-vote-too-slow aspect of the Salty issue.

### Finding Description
`ChunkStateWitness` size is deterministically driven by data recorded from trie access during receipt execution. The runtime records the exact recorded storage proof/trie nodes as `base_state` in `ChunkStateTransition` [1](#0-0) . This witness is capped at `MAX_UNCOMPRESSED_STATE_WITNESS_SIZE = 64 MiB` and `MAX_COMPRESSED_STATE_WITNESS_SIZE = 48 MiB` [2](#0-1) , and the intended per-receipt/per-chunk soft/hard proof-size limits (`per_receipt_storage_proof_size_limit`, `main_storage_proof_size_soft_limit`) are meant to keep the total witness under ~17 MiB [3](#0-2) .

The codebase itself demonstrates (via its own regression/sanity test) that a single function-call action can be used to inject outsized "garbage" storage-proof content directly, bypassing the normal per-byte gas-cost economics that would otherwise make growing the witness prohibitively expensive: `apply_recorded_storage_garbage` recognizes any function call whose method name matches `internal_record_storage_garbage_<N>` and, at execution time, force-injects `N` megabytes of unaccounted data into the trie recorder regardless of what the contract logic actually reads [4](#0-3) . The underlying `record_storage_garbage` helper writes the bytes under a static key via `recorder.record_unaccounted(...)`, explicitly bypassing the normal gas/size accounting path [5](#0-4) .

The project's own sanity test `pytest/tests/sanity/large_witness.py` shows the consequence directly: sending one function-call transaction that triggers a 20 MiB witness causes the target shard to produce **missing chunks for several consecutive blocks** because "distributing large witness takes too much time, so chunk endorsements arrive too late to be included in the block" — and the only fix demonstrated is restarting nodes with a larger `min_block_production_delay`/`max_block_wait_delay`, i.e. an operator-level configuration change, not something adjustable within the chunk-production pipeline itself [6](#0-5) . The trigger requires nothing but a plain signed `FunctionCall` transaction to any contract that exposes the pattern-matched method name and enough attached gas [7](#0-6) .

This is directly analogous to the Salty bug class: a threshold check (witness/proof-size limits, analogous to the 3% price-divergence check) that, once crossed, does not degrade gracefully but instead halts the entire dependent pipeline (chunk endorsement/inclusion, analogous to liquidation/borrow), and whose remedy (raising byte caps, or here, raising block-production timing) is an out-of-band, slow-to-apply change rather than an in-protocol fallback — mirroring the "DAO vote too slow" element of the original finding.

### Impact Explanation
While `#[cfg(feature = "test_features")]` gates the exact `internal_record_storage_garbage_N` shortcut so it is not reachable on mainnet builds, the underlying vulnerability class it demonstrates is real and general: any mechanism (contract logic performing many trie reads/removals, e.g. via large-scale storage writes as shown in `test_storage_proof_size_limit`) that can push a single chunk's recorded storage proof toward the ~17 MiB soft/hard aggregate limit risks producing a witness large enough that Reed-Solomon distribution and validator re-execution cannot complete within the consensus timeout, causing the chunk to be missing for that height. Because chunk production for a shard requires collecting `> 2/3` stake of chunk endorsements before a block including that chunk can be finalized [8](#0-7) , a witness that habitually arrives too late halts new-chunk inclusion on that shard, which is a transaction-triggered halt of the affected shard's progress — one of the accepted impact categories (transaction-triggered halt / receipt-processing stall).

### Likelihood Explanation
Reaching the exact `test_features`-gated shortcut requires a non-production build, so as stated this specific PoC is not exploitable on mainnet. However, the general mechanism (crafting a receipt/contract call that maximizes recorded trie proof size within the documented 17 MiB budget) is reachable by any account that can deploy a contract and send function calls, as evidenced by the non-test-feature-gated `test_storage_proof_size_limit` integration test which achieves large recorded proofs purely through normal contract writes/reads [9](#0-8) . The likelihood of a full outage depends on tuning (gas costs vs. proof-size growth per byte), which the report and its underlying #11703 issue confirm is an already-known, real operational risk requiring manual operator intervention (block-timing config change) to recover — not a purely test-feature-only concern.

### Recommendation
Ensure production-path (`test_features`-independent) contract calls cannot cheaply generate storage-proof/witness bytes disproportionate to the gas paid for them; specifically audit the per-byte trie-read/removal gas costs referenced in `docs/misc/state_witness_size_limits.md` (the "assumes every removal generates additional 2000 bytes of storage proof" heuristic) to confirm they are conservative enough that no realistic contract call sequence can generate witness content whose distribution time exceeds the chunk-production timeout. Additionally, consider a graceful degradation path (e.g., splitting an oversized witness across multiple heights, or having the runtime hard-fail the offending receipt before finalizing an oversized witness) rather than relying purely on validator/operator-driven block-timing changes to recover liveness, mirroring the "fallback instead of full halt" remediation recommended for the original Salty PriceAggregator finding.

### Proof of Concept
1. As demonstrated by the repo's own sanity test, send a single `FunctionCall` transaction to an account/contract exposing a method that forces the trie recorder to add megabytes of storage-proof bytes in one receipt (in the test build, `internal_record_storage_garbage_20`) [7](#0-6) .
2. The runtime applies the receipt; `apply_recorded_storage_garbage` (called from `action_function_call`) injects the garbage bytes into the trie recorder unconditionally on execution [10](#0-9) , [4](#0-3) .
3. The resulting `ChunkStateWitness` for that shard/height balloons to ~20 MiB, and Reed-Solomon distribution/validation takes long enough that endorsements do not arrive before the block deadline, producing missing chunks for the shard for several consecutive heights, observed directly via the chunk mask in `pytest/tests/sanity/large_witness.py` [11](#0-10) .
4. Recovery in the test requires restarting all validators with increased `min_block_production_delay`/`max_block_wait_delay` — an out-of-band configuration change, not a protocol-level fallback [12](#0-11) .

## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 17MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
* `combined_transactions_size_limit - 4 MiB`
  * Hard limit on total size of transactions from this and previous chunk. `ChunkStateWitness` contains transactions from two chunks, this limit applies to the sum of their sizes.
* `new_transactions_validation_state_size_soft_limit - 500 KiB`
  * Validating new transactions generates storage proof (recorded trie nodes), which has to be limited. Once transaction validation generates more storage proof than this limit, the chunk producer stops adding new transactions to the chunk.
* `per_receipt_storage_proof_size_limit - 4 MB`
  * Executing a receipt generates storage proof. A single receipt is allowed to generate at most 4MB of storage proof. This is a hard limit, receipts which generate more than that will fail.
* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
  * Due to implementation details it's hard to find the exact amount of storage proof generated by a receipt, so an upper bound estimation is used instead. This upper bound assumes that every removal generates additional 2000 bytes of storage proof, so receipts which perform a lot of trie removals might be limited more than theoretically applicable.
* `outgoing_receipts_usual_size_limit - 100 KiB`
  * Limit on the size of outgoing receipts to another shard. Needed to keep the size of `source_receipt_proofs` small.
  * On most block heights a shard isn't allowed to send receipts larger than 100 KiB to another shard.
* `outgoing_receipts_big_size_limit - 4.5 MiB`
  * On every block height there's one special "allowed shard" which is allowed to send larger receipts, up to 4.5 MiB in total.
  * A receiving shard will receive receipts from `num_shards - 1` shards using the usual limit and one shard using the big limit.

In total that gives 4 MiB + 500 KiB + 8MB + 5*100 KiB + 4.5 MiB ~= 17 MiB of maximum witness size. Possibly a little more on missing chunks.
