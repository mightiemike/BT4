## Title
Rounding-down in `checkUndelegateResource` lets a delegator escape proportional "dirty" (used) resource accounting via small undelegate amounts - (File: actuator/src/main/java/org/tron/core/vm/utils/FreezeV2Util.java)

### Summary
`FreezeV2Util.checkUndelegateResource` splits an `unDelegateResource` amount into a "clean" (unused, immediately withdrawable) portion and a "dirty" (already-consumed-by-usage) portion using a floating-point ratio truncated to `long`. This mirrors the `StakingRewards._decreaseUserShare` rounding bug: a proportional deduction (`virtualRewardsToRemove` there, `clean`/used-portion here) is computed with a rounding mode that favors the caller, and it can be driven to zero by choosing a sufficiently small `amount`, letting a caller repeatedly bypass the intended proportional accounting.

### Finding Description
`checkUndelegateResource` computes: [1](#0-0) 

```java
amount = min(amount, resourceLimit, VMConfig.disableJavaLangMath());
if (resourceLimit <= usagePair.getLeft()) {
  return Triple.of(0L, amount, usagePair.getRight());
}
long clean = (long) (amount * ((double) (resourceLimit - usagePair.getLeft()) / resourceLimit));
return Triple.of(clean, amount - clean, usagePair.getRight());
```

`clean` is the proportion of `amount` corresponding to *unused* frozen balance; `amount - clean` is the proportion corresponding to already-*used* (dirty) balance that must be reconciled against the account's live bandwidth/energy usage window. Because `clean` is computed via `double` multiplication then truncated with `(long)` cast (always rounds toward zero, i.e. down), for a small enough `amount` relative to `resourceLimit`, `clean` rounds to `0`, so the entire `amount` is classified as "dirty" (or vice versa depending on ratio, the truncation always benefits whichever side is being minimized by the caller's choice of `amount`). This is structurally identical to the reported bug: `virtualRewardsToRemove = (user.virtualRewards * decreaseShareAmount) / user.userShare` in `StakingRewards.sol` is floored, letting a user with a carefully chosen small decrease amount always round the "should-be-deducted" fraction down to zero.

This value feeds into the real accounting update performed in `UnDelegateResourceProcessor.execute`, where the "dirty"/usage proportion of an undelegated balance determines `transferUsage` — the resource usage that must move from receiver back to owner (or be discounted) when a delegator reclaims delegated bandwidth/energy: [2](#0-1) 

The related actuator-level computation has the same double-based rounding pattern: [3](#0-2) 

By repeatedly calling `unDelegateResource` (native contract, reachable from any TVM contract via `checkUndelegateResource`/`unDelegateResource` opcodes — see `PrecompiledContracts.java` references) with small amounts instead of one large amount, a caller can make the proportional "dirty usage" (or "clean") split round to zero on each call, systematically avoiding the intended proportional transfer of consumed bandwidth/energy usage between owner and receiver.

### Impact Explanation
This affects on-chain resource accounting (bandwidth/energy), which is directly monetizable (bandwidth/energy otherwise costs TRX to acquire). If a delegator can split undelegation into many small calls to avoid ever paying the "dirty" usage penalty, the receiver keeps consumed usage credit it should have lost, or the owner fails to recover usage credit it is entitled to — corrupting the global resource-weight/usage bookkeeping (`TotalNetWeight`/`TotalEnergyWeight`, per-account `NetUsage`/`EnergyUsage`) over many transactions. This falls in the "resource and reward accounting" category called out by the task.

### Likelihood Explanation
The rounding is deterministic and callable from any TVM contract (unprivileged) via the freeze-v2 delegate/undelegate native contract opcode, requiring only that `VMConfig.allowTvmFreezeV2()` is enabled. An attacker fully controls the `amount` parameter and can trivially choose amounts that round `clean`/`amount-clean` to zero, and can repeat the call arbitrarily (bounded only by gas cost of many small transactions/internal calls), making exploitation practically feasible once the exact usage/limit conditions are met.

### Recommendation
Round the proportional split up (ceiling), or perform the computation in integer/`BigInteger` arithmetic consistently rounding in favor of the protocol (as was done elsewhere in the codebase, e.g. `divideCeilExact` in `ResourceProcessor.unDelegateIncreaseV2`), instead of using `double` multiplication with `(long)` truncation in `checkUndelegateResource`. Ensure that for any non-zero `amount`, the "dirty"/used portion cannot be forced to `0` by amount selection when `usagePair.getLeft() > 0`.

### Proof of Concept
Conceptual (based on code inspection only — not independently executed):
1. Deploy/have a contract with delegated bandwidth/energy where `resourceLimit > usagePair.getLeft() > 0` (i.e., some but not all frozen balance is consumed as usage).
2. Repeatedly call the freeze-v2 `unDelegateResource` native contract with a small `amount` such that `amount * (resourceLimit - usagePair.getLeft()) / resourceLimit` truncates to `0` (e.g., `amount` on the order of `resourceLimit / (resourceLimit - usage)`).
3. Each call returns `clean = 0`, meaning `amount - clean = amount` is treated entirely as "dirty" usage (or the reverse, depending on which side of the ratio is targeted), never proportionally splitting as intended for a single larger call.
4. Repeat across many small calls to accumulate an undelegated amount whose aggregate usage-transfer differs from what a single equivalent call would have produced, corrupting the receiver's/owner's tracked `NetUsage`/`EnergyUsage` and the global weight totals over time.

Note: I could not execute this against a live node to confirm the exact numeric divergence magnitude; this assessment is based on static code analysis of the rounding logic and its downstream consumers only.
