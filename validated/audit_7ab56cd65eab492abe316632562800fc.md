## Finding

**Rounding-to-zero maker payout consumes the maker's full remaining order without paying any tokens in `MarketSellAssetActuator.matchSingleOrder` (taker == maker branch)** - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The Aave report describes `AToken.redeem` allowing a caller to burn aTokens while receiving zero underlying assets in exchange, because the exchange-rate division rounds down to zero and the transaction is never reverted. The same bug class — a floor-division rate calculation whose zero result is applied to state changes without any zero-guard — exists in java-tron's on-chain order book actuator `MarketSellAssetActuator`, specifically in the "taker == maker" matching branch.

### Finding Description
`matchSingleOrder` computes how many tokens the maker receives from a match using `MarketUtils.multiplyAndDivide`, which performs an integer (floor) division: [1](#0-0) 

In the `taker == maker` branch, `makerBuyTokenQuantityReceive` is computed at lines 426-428 and used unconditionally: the maker's order `sellTokenQuantityRemain` is set to `0` and the order is marked `INACTIVE` (fully closed) at line 439, **without any check that `makerBuyTokenQuantityReceive > 0`**.

Compare this with the sibling "taker > maker" branch just below, which explicitly guards against the exact same rounding-to-zero scenario: [2](#0-1) 

There, if `makerBuyTokenQuantityReceive == 0`, the code refunds the maker's remaining sell tokens instead of closing the order with zero payout — the exact safeguard that is missing in the `taker == maker` branch.

After the branch logic, the (possibly zero) `makerBuyTokenQuantityReceive` is credited to the maker's account and the order is persisted as fully closed: [3](#0-2) 

This mirrors the Aave root cause precisely: a `floorDiv`-based exchange-rate calculation is allowed to yield `0`, and that `0` is applied to close out (burn/consume) the victim's position instead of reverting or refunding.

Note: by contrast, the analogous TRC10/TRC10-exchange flows (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`, `ParticipateAssetIssueActuator`) all explicitly check `anotherTokenQuant <= 0` / `exchangeAmount <= 0` in `validate()` and throw `ContractValidateException`, so those are not vulnerable to this bug class: [4](#0-3) [5](#0-4) 

The market actuator's `taker == maker` branch is the one unguarded path.

### Impact Explanation
A maker with an active resting order can have their entire remaining sell-token balance consumed (order fully closed, `sellTokenQuantityRemain` set to 0) while being credited zero buy tokens, resulting in an outright loss of the maker's assets with no compensation. This is a direct, unprivileged-user-reachable accounting/loss-of-funds bug triggered purely by normal trading activity (no special permissions required), since any account can place sell/buy orders via `MarketSellAssetContract`.

### Likelihood Explanation
The condition is reachable whenever a maker's remaining sell quantity, multiplied by the maker's buy quantity, is smaller than the maker's original sell quantity (i.e., `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`), and a taker's order size happens to exactly match the maker's remaining sell quantity (`takerBuyTokenQuantityRemain == makerSellRemainQuantity`). This scenario naturally arises after partial fills reduce a maker's remaining quantity to a small value relative to a low-numerator price ratio — an easily achievable state in normal market use, and can also be intentionally engineered by an attacker controlling both taker and maker order sizes/prices.

### Recommendation
Add the same zero-check safeguard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, refund the maker's remaining sell tokens via `returnSellTokenRemain` instead of zeroing out `sellTokenQuantityRemain` and closing the order with no payout.

### Proof of Concept
1. Maker places an order selling token A for token B with a low `buyQuantity/sellQuantity` ratio (e.g., sell 200 A for 100 B), which gets partially filled down to a small `sellTokenQuantityRemain` (e.g., remain = 1, ratio 100/200 → `multiplyAndDivide(1, 100, 200)` = 0).
2. A taker places a `MarketSellAssetContract` order whose computed `takerBuyTokenQuantityRemain` exactly equals the maker's `sellTokenQuantityRemain` (1), triggering the `taker == maker` branch in `matchSingleOrder`.
3. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 100, 200) = 0` (floor division).
4. The code proceeds to set `makerOrderCapsule.setSellTokenQuantityRemain(0)`, marks the maker order `INACTIVE`, and calls `addTrxOrToken(makerOrderCapsule, 0)` — the maker's order is fully closed while receiving zero tokens B, silently losing their last unit of token A.

**Uncertainty**: I was not able to directly execute or step through a live test to numerically confirm an exact triggering set of order sizes within this session, but the code path and missing zero-guard are confirmed by direct source inspection and by contrast with the parallel, guarded branch a few lines below.
