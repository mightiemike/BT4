### Title
Unbounded duplicate accumulation in `shop:<shop>` session-index causes DoS of `KVSessionStorage` - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` calls `addShopIds` on every store, but `addShopIds` unconditionally appends the session id to the shop's index array without checking whether that id is already present [1](#0-0) . Because `storeSession` is invoked repeatedly for the *same* session id whenever it is created/refreshed (OAuth callback, token-exchange offline/online token refresh), this index grows without bound and is never deduplicated, causing eventual denial-of-service once the KV value size limit is reached.

### Finding Description
`storeSession` writes the session payload keyed by `session.id`, then unconditionally records that id into a shop-scoped list stored at `shop:<shop>` via `addShopIds`: [2](#0-1) 

`addShopIds` reads the existing list and appends the new id(s) with no de-duplication check: [1](#0-0) 

Deallocation only happens through the mirrored `removeShopIds` path, which is exclusively invoked from `deleteSession`/`deleteSessions` [3](#0-2) . However, `storeSession` is called every time an offline or online session is (re-)persisted — for example on every OAuth callback and on every token-exchange refresh when the current session is missing or inactive: [4](#0-3) 

Each of these calls upserts the same `session.id` key in KV (overwrite is fine) but *appends a new duplicate entry* to the `shop:<shop>` array every single time, since `addShopIds` never checks for an existing entry. This mirrors the reported bug class: a resource ("space" — here the KV shop-index array) is reserved on every allocation-triggering action, but deallocation is only wired to a narrow cleanup path (`deleteSession`) that ordinary session refresh/re-auth flows never exercise. A single merchant/app installation whose session repeatedly expires and is refreshed (a normal, unprivileged, unauthenticated-triggerable flow through the OAuth/token-exchange handlers) will cause the `shop:<shop>` list to grow monotonically and indefinitely, with no cap, dedup, or TTL.

### Impact Explanation
KV-backed stores (e.g., Cloudflare Workers KV) impose a maximum value size (25 MB). As the `shop:<shop>` JSON array accumulates duplicate ids indefinitely, its serialized size grows until `namespace.put` for that key begins failing, which breaks `storeSession` and `findSessionsByShop` for the affected shop — i.e., a DoS of the authentication/session-storage layer for that tenant. Because the growth is driven purely by normal or attacker-amplified re-authentication traffic (no elevated privileges needed), a merchant or an attacker who can trigger repeated OAuth/token-exchange cycles for a shop can degrade or fully break that shop's session persistence over time.

### Likelihood Explanation
Every token-exchange/offline-session refresh cycle triggers `storeSession`, so the growth occurs during completely ordinary usage and is easily amplified by an attacker forcing repeated re-authentication (e.g., by invalidating/expiring the session or replaying OAuth flows), requiring no secret knowledge or privileged access — only the ability to complete or trigger the OAuth/token exchange handshake for a shop repeatedly.

### Recommendation
In `addShopIds`, deduplicate before writing (e.g., use a `Set` or filter out ids already present) so re-storing the same session id does not grow the shop index; additionally, prefer syncing the shop-id index from the actual set of live sessions or persisting it with defensive size caps/TTL, rather than always appending.

### Proof of Concept
1. Configure `KVSessionStorage` for a shop.
2. Repeatedly call `storeSession` with a `Session` object that has the same `id` (simulating repeated OAuth/token-exchange refresh cycles for the same offline/online session), e.g.:
```ts
const storage = new KVSessionStorage(kvNamespace);
for (let i = 0; i < N; i++) {
  await storage.storeSession(session); // same session.id each time
}
```
3. Inspect the `shop:<shop>` key in the KV namespace — observe that it contains `N` duplicate copies of `session.id` rather than a single entry, confirming unbounded growth as shown by `addShopIds` at [1](#0-0) .
