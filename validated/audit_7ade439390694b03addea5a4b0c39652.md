### Title
Permanent `has_in_flight_tx` lock via out-of-gas callback panic causes irreversible denial-of-service of the NEAR Wallet Contract — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit-account global contract that lets Ethereum-signed transactions be relayed onto NEAR) uses a boolean flag `has_in_flight_tx` as a manual reentrancy guard across asynchronous promise/callback chains, exactly analogous in intent to the CEI-style guard the external report says was missing in `V3Vault.onERC721Received`. The flag is set to `true` before any promise-returning path and is only ever reset to `false` as the *first* statement of the eventual callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). If that callback receipt fails for any reason *after* the flag-reset line executes but before the callback function returns (e.g. it runs out of prepaid gas while deserializing/processing an oversized cross-contract response), NEAR's atomic-execution model rolls back **all** state writes made during that failed function call — including the `has_in_flight_tx = false` reset — while the promise chain itself is still considered "delivered" and will never be re-invoked. This leaves `has_in_flight_tx` stuck at `true` forever, and every subsequent `rlp_execute` call is rejected with "transaction already in progress," permanently disabling the wallet contract for its owner.

### Finding Description
`has_in_flight_tx` is documented as an invariant: it "must be `true` when a mutable method of this contract returns a promise and `false` otherwise" (`lib.rs:48-54`). The only way to clear it is inside one of the terminal callbacks: [1](#0-0) [2](#0-1) [3](#0-2) 

Each of these callbacks sets `self.has_in_flight_tx = false;` as its very first statement, then proceeds to inspect `env::promise_result(0)` and deserialize a cross-contract response (via `serde_json::from_slice`) that originates from an untrusted, attacker-influenceable contract (the address registrar, an emulated NEP-141 token, or an arbitrary `target`/`token_id` account chosen when the transaction was submitted). The static gas budgeted for these callbacks is a small fixed constant (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `lib.rs:34-41`), only partially inflated by `action.gas()` for the outer method call — not sized to the potential size of the promise's returned payload.

Because NEAR function-call execution is atomic (a panic — including gas exhaustion — anywhere in a receipt's execution discards *all* state mutations performed during that receipt, not merely the ones after the panic point), a callback that resets the flag to `false` and then panics later in the same call (e.g., while reading/deserializing a large or malformed `PromiseResult::Successful` payload, or while executing the subsequent branch that builds another promise) causes the entire receipt — including the flag reset — to be rolled back. The net effect: `has_in_flight_tx` remains `true` as it was before the callback ran, with no other code path ever able to reset it (there is no timeout, admin key, or exception handler for this case).

`inner_rlp_execute` sets `has_in_flight_tx = true` unconditionally for every promise-returning path (`lib.rs:117-124`), and `rlp_execute` itself refuses any further calls whenever the flag is `true`: [4](#0-3) 

This is structurally the same class of bug as the reported issue: a shared piece of accounting/guard state (`has_in_flight_tx` here, `tokenConfigs[...].totalDebtShares` in the report) is updated in an order that assumes the following external interaction (a cross-contract call/promise resolution there, `onERC721Received`'s `_cleanupLoan` external transfer here) completes cleanly, but a hostile counterparty can force that later step to fail/abort in a way that undoes or skips the accounting update, leaving the guard permanently in the wrong state.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the wallet contract permanently rejects all future `rlp_execute` calls with "transaction already in progress, please try again later" (`lib.rs:97-105`). Since this contract *is* the on-chain identity/authorization surface for the corresponding ETH-implicit account (its assets, access keys it may hold, and any further Ethereum-emulated actions), this results in permanently frozen functionality for that account — no further Ethereum-emulated transaction can ever be relayed through it again. This matches the "permanently frozen funds" / "transaction-triggered halt" acceptance category: a single crafted transaction (one where the relayer-chosen `target`, or the intermediary `address_registrar`/NEP-141 `token_id` contract, returns an oversized or expensive-to-deserialize payload) can brick the account irreversibly.

### Likelihood Explanation
The `target` account for an emulated ERC-20 transfer, and the token/registrar contracts invoked in the two-callback paths, are external, attacker-reachable accounts (any account ID can be named as `target`/`token_id`); a malicious or compromised contract at that address can return payloads engineered to be maximal in size or costly to deserialize relative to the fixed callback gas budget. A malicious relayer (who supplies `target` and submits the underlying transaction) is an unprivileged party under this scan's threat model, so this is reachable from a single submitted transaction. The exact gas margin required to trigger the failure was not fully re-derived against NEAR's per-byte promise-result host costs in this pass, so the precise conditions under which the callback's fixed gas allotment is insufficient are not proven numerically here — this should be validated with a concrete gas-cost calculation or a reproduction on a live/sandbox node.

### Recommendation
- Make the `has_in_flight_tx` reset resilient to a subsequently failing callback: perform any state-changing/parsing logic that could panic *before* relying on the flag remaining consistent, or use a mechanism that is set outside the atomic unit that can fail (e.g., commit the flag reset in its own minimal, unlikely-to-fail step, or use a scheduled recovery/timeout receipt to clear the flag if the primary callback fails).
- Bound the gas required to process `env::promise_result` payloads (validate/cap size before full deserialization) so an oversized or malformed response cannot cause an unrecoverable out-of-gas panic in the callback.
- Add a recovery path (e.g., a privileged/self-only "unstick" method, or a delayed retry receipt) so a stuck `has_in_flight_tx` cannot permanently disable the account.

### Proof of Concept
1. User (via relayer) submits an RLP-encoded Ethereum transaction to `rlp_execute` with `target` set to `token_id`, triggering the `EthEmulationKind::ERC20Transfer` path (`inner_rlp_execute`, `lib.rs:433-458`), which sets `has_in_flight_tx = true` and schedules `storage_balance_of` → `nep_141_storage_balance_callback`.
2. `token_id` is an account controlled by the attacker (or the intended NEP-141 token has been compromised/redeployed) that responds to `storage_balance_of` with an unusually large or deeply nested JSON payload.
3. `nep_141_storage_balance_callback` executes: line `self.has_in_flight_tx = false;` runs and (would) commit, but the subsequent `serde_json::from_slice::<Option<StorageBalance>>` deserialization, or the following promise construction, exhausts the remaining prepaid callback gas (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, fixed at 5+5+5 Tgas) and panics.
4. Because the whole `nep_141_storage_balance_callback` function call panics, its entire state diff — including the `has_in_flight_tx = false` write — is discarded per NEAR's atomic execution semantics; the persisted value of `has_in_flight_tx` remains `true` from step 1.
5. Any further call to `rlp_execute` immediately hits the guard at `lib.rs:97-105` and returns `"transaction already in progress, please try again later"` — permanently, since no other path can ever clear the flag.

Note: this analysis establishes the code-level mechanism (atomic rollback undoing an early flag reset when a callback panics later) and the reachability path (attacker-controlled `target`/`token_id` contract response). Full confirmation of the exact gas parameters needed to reliably trigger the out-of-gas panic under the current `RuntimeConfig`/host fee schedule was not completed in this pass and should be verified with a live gas-cost trace or reproduction.
