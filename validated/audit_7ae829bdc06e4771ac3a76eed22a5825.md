This confirms the root cause. The `URL_STRING` property is a `WritableObjectPropertyKey` set exactly once, in the `DocumentPictureInPictureHeaderMediator` constructor, from `mOpenerWebContents.getLastCommittedUrl()` at PiP-window-creation time [1](#0-0) . The only navigation-driven listener attached to the opener's `WebContentsObserver` overrides `didChangeVisibleSecurityState()`, which refreshes the security lock icon but never re-derives or re-sets `URL_STRING` [2](#0-1) . There is no `didFinishNavigation` override anywhere in this class or its view binder that refreshes the URL host label [3](#0-2) .

### Title
Stale opener-origin label in Document Picture-in-Picture header enables navigation spoofing - (File: chrome/android/java/src/org/chromium/chrome/browser/media/document_picture_in_picture_header/DocumentPictureInPictureHeaderMediator.java)

### Summary
The Android Document Picture-in-Picture (PiP) header shows a security icon plus a host/URL label meant to identify which origin owns the floating PiP window. That label is computed once, at construction time, from the opener tab's last-committed URL, and is never refreshed when the opener tab subsequently navigates to a different origin.

### Finding Description
`DocumentPictureInPictureHeaderMediator`'s constructor reads `mOpenerWebContents.getLastCommittedUrl()` a single time and writes the formatted host into the `URL_STRING` property, along with an elision policy chosen based on that URL [1](#0-0) . Two `WebContentsObserver` instances are then registered — one on the PiP child `WebContents`, and one on `mOpenerWebContents` — but both only override `didChangeVisibleSecurityState()`, which drives `updateSecurityIcon()` (icon/lock state), not the origin text [4](#0-3) [5](#0-4) . Neither observer overrides `didFinishNavigation`/`didFinishNavigationInPrimaryMainFrame`, so `URL_STRING` and `URL_ELLIPSIZE_BEHAVIOR` are frozen for the entire lifetime of the PiP window. `getUrlString()` — the helper that derives the display text from a `GURL` and special-cases `file://`/`content://` schemes — is only invoked from the constructor path, confirming it's never re-invoked on navigation [6](#0-5) . The view binder simply renders whatever `URL_STRING` currently holds with no independent freshness check [3](#0-2) .

This is analogous to CVE-2023-1816 ("Incorrect security UI in Picture In Picture ... allowed a remote attacker to potentially perform navigation spoofing"): a page can open a Document PiP window while on a benign/trusted origin (so the header commits and caches that origin's host string), then, from script on the opener page, immediately perform a same-tab cross-origin navigation (e.g. `location.href = 'https://attacker.example/'`). Because only the security-level (lock icon) is refreshed on navigation and not the textual origin/host, the PiP header continues to display the pre-navigation (trusted) origin string and elision behavior even though the opener tab (and the "Back to tab" affordance) now points at attacker-controlled content. A user who trusts the displayed origin (and uses "Back to tab" or otherwise reasons about which site owns the floating window) is misled about the true origin currently associated with the PiP session.

### Impact Explanation
This is a security-UI spoofing vulnerability: an attacker-controlled page can cause the browser chrome (PiP header host label) to continue displaying an origin the user is no longer actually on, which can be leveraged for phishing/social-engineering (e.g., displaying a bank/trusted site's host while the underlying tab has already navigated to an attacker's phishing page). It matches CVSS vector characteristics of the referenced CVE (network-reachable, requires user to interact by opening PiP, no privileges, integrity impact via UI spoof, no confidentiality/availability impact).

### Likelihood Explanation
Reachable purely from web content: requesting Document Picture-in-Picture (`documentPictureInPicture.requestWindow()`) requires only a user gesture that many sites already have (e.g., clicking to open a floating video/chat widget), after which the opener page's own script can navigate itself to any origin at will. No special flags, extensions, or privileges are required, making this straightforward to trigger from a single malicious page.

### Recommendation
Register a `didFinishNavigation` (or equivalent primary-main-frame-commit) callback on `mOpenerWebContentsObserver` that re-derives `URL_STRING` and `URL_ELLIPSIZE_BEHAVIOR` from the opener's current `getLastCommittedUrl()`/origin whenever the opener navigates, mirroring the existing `updateSecurityIcon()` refresh pattern, so the header text stays synchronized with the opener's live origin for the lifetime of the PiP window.

### Proof of Concept
1. Host a page at `https://trusted.example/pip.html` that calls `await documentPictureInPicture.requestWindow({...})` on a user gesture, opening a Document PiP window; the header renders `trusted.example` as the origin/host label via `DocumentPictureInPictureHeaderMediator`'s constructor-time `getUrlString(openerUrl)` call.
2. Immediately after the PiP window is created (before or without navigating the PiP document itself), have the same script on `trusted.example` execute `window.location.href = "https://attacker.example/phish.html"` on the opener tab.
3. Observe that the PiP header still displays `trusted.example` (and the corresponding lock/security icon transition is the only thing that updates via `didChangeVisibleSecurityState`), even though the opener tab has fully navigated to `attacker.example`, misrepresenting the current origin associated with the floating window and its "Back to tab" control.

    private String getUrlString(@Nullable GURL url) {
        if (url == null || url.isEmpty() || !url.isValid()) {
            return "";
        }

        final String scheme = url.getScheme();
        if (UrlConstants.FILE_SCHEME.equals(scheme)) {
            // File scheme URLs do not have a host, so we use the path instead.
            return url.getPath();
        }

        if (UrlConstants.CONTENT_SCHEME.equals(scheme)) {
            return url.getSpec();
        }

        if (url.getHost().isEmpty()) {
            return "";
        }

        return UrlFormatter.formatUrlForSecurityDisplay(url, SchemeDisplay.OMIT_HTTP_AND_HTTPS);
    }
