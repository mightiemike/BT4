## Analog Found: Global Resource-Weight Manipulation via Freeze/Unfreeze to Deny Bandwidth/Energy to Other Accounts

### Title
Instant, cost-free manipulation of `TotalNetWeight`/`TotalEnergyWeight` via `FreezeBalanceV2`/`UnfreezeBalanceV2` to skew other accounts' proportional resource limits - (File: `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`, `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`)

### Summary
The Flayer bug lets an attacker cheaply mint/burn ERC20 supply via `deposit`/`redeem`, distorting a global `utilizationRate` that other users' liquidation health depends on. The analogous java-tron mechanism is `TotalNetWeight`/`TotalEnergyWeight`, a global denominator updated by `FreezeBalanceV2Actuator`/`UnfreezeBalanceV2Actuator`, which every account's proportional bandwidth/energy allowance is derived from via `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`.

### Finding Description
`FreezeBalanceV2Actuator.execute` increases `TotalNetWeight`/`TotalEnergyWeight` the instant a freeze transaction executes: [1](#0-0) 

`UnfreezeBalanceV2Actuator.execute` decreases that same global weight immediately when the unfreeze transaction executes, well before the underlying TRX principal is actually returned (that part is subject to the unlock delay, tracked separately via `addUnfrozenV2List`/`unfreezeExpire`): [2](#0-1) 

Critically, `UnfreezeBalanceV2Actuator.validate` enforces no minimum holding period between a `FreezeBalanceV2` and its corresponding `UnfreezeBalanceV2` — only a cap of `UNFREEZE_MAX_TIMES` (32) and an amount check: [3](#0-2) 

This global weight is the sole denominator used to compute every account's free bandwidth/energy allowance, proportional to each account's own weight: [4](#0-3) [5](#0-4) 

Because freezing/unfreezing large amounts of self-owned TRX is essentially free (no fee, `calcFee()` returns 0) and reversible with no lock-in period on the weight adjustment itself, an attacker can broadcast a large `FreezeBalanceV2Contract` transaction to spike `TotalNetWeight`/`TotalEnergyWeight`, wait for it to land in a block, then immediately broadcast `UnfreezeBalanceV2Contract` to revert the spike. During the window the inflated weight is live on-chain, every other account's `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` result (a function of `weight_i / TotalWeight`) drops, since the attacker's own weight dominates the denominator while other accounts' weights stay fixed.

### Impact Explanation
This lets an attacker deterministically and cheaply shrink the free-resource allowance of every other account for the duration the attacker chooses. Legitimate transactions/contract calls landing in that window can fail from insufficient bandwidth (`useAccountNet` returning `false`) or run out of energy mid-execution (a form of resource/energy accounting corruption analogous to the referenced bug's "force liquidation" mechanism — here, "force resource exhaustion/DoS" for specific targeted transactions), forcing victims to pay TRX fees for what should have been free-tier transactions, or causing contract calls to revert due to out-of-energy. The attacker fully recovers their frozen TRX (subject to the standard unlock delay for the *principal*, though the *weight* effect is instantaneous and reversible), so the manipulation itself carries close to zero net cost beyond transaction fees and temporary balance lock exposure.

### Likelihood Explanation
Any unprivileged account holding sufficient TRX (even leveraged via multiple large transfers/freezes) can execute this with two ordinary, unprivileged transactions (`FreezeBalanceV2Contract` then `UnfreezeBalanceV2Contract`) — no special permissions, keys, or node access are required, only broadcasting standard transactions to the network. The precision of the attack (targeting a specific victim transaction) depends on the attacker's ability to time/order their transactions relative to the victim's, which is influenced by mempool/block-packing behavior, making it opportunistic rather than perfectly deterministic, but the underlying mechanism itself is reliably reachable at any time.

### Recommendation
Introduce an economic or time-based disincentive analogous to the report's "use fees in deposit and redeem" recommendation — e.g., require a minimum holding duration before `TotalNetWeight`/`TotalEnergyWeight` reductions take effect for a freshly created `FreezeBalanceV2` position, or smooth/rate-limit how quickly an individual account's contribution to `TotalNetWeight`/`TotalEnergyWeight` can change within a short window, so a single account cannot cause large instantaneous swings in the global denominator used by `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`.

### Proof of Concept
1. Attacker account A holds `N` TRX.
2. A broadcasts `FreezeBalanceV2Contract` with `frozenBalance = N`, `resource = BANDWIDTH` (or `ENERGY`). On execution, `dynamicStore.addTotalNetWeight(...)` is called, instantly inflating `TotalNetWeight` [6](#0-5) .
3. While this transaction's effect is live on-chain, other accounts B's `calculateGlobalNetLimit(B)` computed via `chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight()` returns a smaller value than before [7](#0-6) , so B's free-bandwidth transactions that would have succeeded now fail via `useAccountNet` returning `false`, or B's contract calls run out of energy sooner.
4. A immediately broadcasts `UnfreezeBalanceV2Contract` for the same amount; `updateTotalResourceWeight` reduces `TotalNetWeight` back down instantly (no delay on the weight itself) [8](#0-7) , while A's principal returns to A's balance after the standard unfreeze delay.
5. Net cost to A: transaction fees only; A's targeted DoS window against B is achieved for free.

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }
