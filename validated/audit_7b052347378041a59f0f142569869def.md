### Title
Missing concurrency control on `exchangeToken()` calls in `performTokenExchange` allows request amplification against Shopify's token-exchange API - (File: `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

### Summary
`performTokenExchange` performs a check-then-act sequence (load session → check `isActive` → call `exchangeToken` → store session) with no locking or de-duplication around the `exchangeToken` calls themselves. Any client holding a currently-valid session token for a shop can send several concurrent requests before the first exchange completes and is persisted, causing each concurrent request to independently invoke `api.auth.tokenExchange` (once for offline, again for online if `useOnlineTokens` is set), multiplying outbound calls to Shopify's token-exchange endpoint from a single legitimate JWT.

### Finding Description
In `performTokenExchange` (`packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts:65-132`), the flow is:
1. `decodeSessionToken` validates the JWT signature/exp (this check is legitimate and not bypassed).
2. `config.sessionStorage.loadSession(sessionId)` is called to check for an existing active session [1](#0-0) .
3. If no active session is found, `exchangeToken()` is called for the offline token, and optionally for the online token, and the result is stored via `sessionStorage.storeSession` [2](#0-1) .

This load-check-exchange-store sequence is **not atomic and not deduplicated**. Notably, the codebase already contains a purpose-built mechanism for this exact problem — `IdempotentPromiseHandler`, keyed by `sessionToken` — but it is applied only to `callAfterAuthHook` [3](#0-2) , not to the `exchangeToken` calls that actually hit Shopify's network API. Consequently, if N concurrent requests arrive bearing the same valid (unexpired) session token before the first request's `storeSession` call completes, all N requests will independently pass the `session.isActive` check as false and each will call `exchangeToken` for offline (and online) tokens, producing up to 2N outbound calls to Shopify per burst. This same missing-idempotency pattern is present in the `shopify-app-remix` and `shopify-app-react-router` token-exchange strategies as well [4](#0-3) [5](#0-4) .

Note this does **not** allow unbounded sequential replay: once a session is successfully stored and remains active, subsequent sequential requests short-circuit at the `session.isActive` check and return `next()` without calling `exchangeToken` again [6](#0-5) . The amplification is bounded by the number of *concurrent* requests sent within the race window before the first exchange's `storeSession` completes, not unbounded across time as characterized in the question.

### Impact Explanation
This is a request-amplification issue rather than an authentication-handler crash/hang. A caller in possession of one valid session token can multiply outbound calls to Shopify's token-exchange endpoint by firing concurrent requests, which consumes the app's Shopify API/token-exchange quota and adds server-side CPU/network load for that shop's tenant. It does not enable cross-tenant access, forged sessions, or secret disclosure — impact is scoped to increased resource consumption tied to the requester's own shop context.

### Likelihood Explanation
Requires the caller to already hold a currently-valid, non-expired session token for the target shop (obtainable normally by loading the embedded app as that merchant, no forgery needed) and requires firing several requests concurrently within the narrow race window before the first `storeSession` completes (typically the latency of one network round-trip to Shopify). This is feasible but only produces a small, bounded multiplication per burst, not a sustained unbounded loop as long as sessions are correctly persisted and reused afterward.

### Recommendation
Apply the same `idempotentPromiseHandler` (or a dedicated mutex/in-flight-request cache keyed by `sessionToken` or `sessionId`) around the `exchangeToken` calls in `performTokenExchange`, so concurrent requests bearing the same session token await/share a single in-flight exchange result rather than each independently calling `api.auth.tokenExchange`. Apply the equivalent fix to the `shopify-app-remix` and `shopify-app-react-router` token-exchange strategies.

```ts
it('exchangeToken is called once per burst of concurrent requests with same token', async () => {
  const sessionToken = validSignedSessionTokenForShopA; // legitimately obtained
  const sessionStorage = new MemorySessionStorage(); // loadSession returns undefined until storeSession completes
  const api = mockApiWithSlowTokenExchange(); // api.auth.tokenExchange takes e.g. 50ms

  const requests = Array.from({length: 10}, () =>
    performTokenExchange({req, res, next, api, config: {...config, sessionStorage}, sessionToken}),
  );
  await Promise.all(requests);

  // Currently fails: exchangeToken (api.auth.tokenExchange) is called more than once
  expect(api.auth.tokenExchange).toHaveBeenCalledTimes(1);
});
```
Expected current (vulnerable) behavior: `api.auth.tokenExchange` is invoked once per concurrent request that races ahead of `storeSession`, demonstrating the amplification described above.
