### Title
Failed `SystemEvent::BridgeDeposit` in `process_sys_txs` is silently dropped and then unconditionally purged from `DepositDataMempool`, permanently freezing the corresponding BTC deposit - (File: crates/sequencer/src/runner.rs)

### Summary
`produce_l2_block_inner` fetches a batch of deposits with `fetch_deposits` and, regardless of whether every individual deposit in that batch was actually included in the produced block, unconditionally calls `remove_deposits(&deposit_data)` on the whole fetched batch at the end of block production. Combined with `process_sys_txs`'s behavior of reverting the working set and `continue`-ing (dropping the failing deposit from `all_txs`) on `EvmSystemTransactionNotSuccessful`, a deposit that fails during real (non-simulated) execution is removed from the mempool forever without ever being minted and without any error surfaced to the depositor.

### Finding Description
The intended binding is: for every `Deposit` blob for which `citrea_sendRawDepositTransaction` returns `Ok(())`, that blob is eventually removed from `DepositDataMempool::accepted_deposit_txs` **if and only if** its `BridgeContract::deposit` call was actually applied and committed in an `L2Block` (cBTC minted). The code breaks this: `remove_deposits` is called with the entire `deposit_data` slice that was *fetched* for the block attempt [1](#0-0) , not with only the deposits that ended up in `all_txs`/the committed block. `remove_deposits` matches purely by `calc_tx_id` and deletes any match unconditionally [2](#0-1) .

`send_raw_deposit_transaction` only validates the deposit with a *read-only* `evm.get_call` simulation against `BlockId::pending()` at submission time, then unconditionally inserts the blob into `DepositDataMempool` and returns `Ok(())` to the caller [3](#0-2) . This simulation happens once, potentially many blocks before the deposit is actually picked up by `fetch_deposits` and executed as a real `SYSTEM_SIGNER` state-mutating transaction in `produce_and_run_system_transactions`/`process_sys_txs`. State can drift between these two points (other transactions landing in intervening blocks, target address becoming a contract, balance/state changes, etc.), so a deposit that passed the simulation can legitimately fail when actually applied.

The failure-handling pattern shown for ordinary EVM pool transactions revert-and-`continue`s while decrementing the nonce [4](#0-3) ; per the question, the analogous branch for `SystemEvent::BridgeDeposit` under `EvmSystemTransactionNotSuccessful` in `process_sys_txs` follows the same discard-and-continue pattern without re-queueing the failed deposit blob anywhere. Because that deposit was fetched (but not included) in this block's `deposit_data`, it is still swept up by the unconditional `remove_deposits(&deposit_data)` call at the end of `produce_l2_block_inner` once the block is otherwise successfully produced — deleting it from the mempool even though it was never applied.

Existing guards do not catch this: `evm.get_call` is a stateless simulation with no guarantee of matching later execution context; `fetch_deposits` does not remove entries (only `remove_deposits` does, and it removes by the original fetch batch, not the applied set); there is no mechanism that reconciles "fetched" vs. "actually included" deposits before purging the mempool.

### Impact Explanation
A deposit blob whose underlying Bitcoin-side BTC transfer to the vault is real and irreversible can be permanently dropped from `DepositDataMempool` without the corresponding cBTC ever being minted on L2, and with no error ever returned to the depositor (the RPC already returned `Ok(())` at submission time, long before the failure occurs during block production). This matches the Critical category: funds permanently frozen (BTC locked with no corresponding cBTC minted and no path to resubmit, since duplicate submission is prevented by `pending_deposits`/`calc_tx_id` unless the mempool state is otherwise reset). The blast radius is one deposit per occurrence but is repeatable across blocks/deposits whenever a griefing state-difference condition can be engineered between the RPC-time simulation and later block-production-time execution.

### Likelihood Explanation
This requires only unprivileged capabilities already in scope: crafting/submitting an EVM transaction sequence and a deposit blob via `citrea_sendRawDepositTransaction` such that the deposit's execution path succeeds under `evm.get_call` at submission time but fails once actually applied later (e.g., by getting another transaction landed first that changes relevant state for the deposit's recipient/logic). The cost is limited to normal transaction/gas fees and Bitcoin fees for the actual deposit inscription. No majority hashrate, key compromise, or privileged role is needed. Exact reproducibility depends on details of `process_sys_txs`/`produce_and_run_system_transactions` (not fully inspected here due to file size truncation), but the unconditional `remove_deposits(&deposit_data)` call at [1](#0-0)  is independently confirmed and is sufficient by itself to break the stated binding whenever any deposit in the fetched batch fails to be included in the resulting block for any reason.

### Recommendation
Track which deposits from `deposit_data` were actually included in `all_txs`/the committed block (e.g., have `produce_and_run_system_transactions`/`process_sys_txs` return the set of successfully-applied deposits), and call `remove_deposits` only with that subset. For deposits that fail with `EvmSystemTransactionNotSuccessful`, either leave them in the mempool for retry in a future block, or explicitly surface a persistent, queryable rejection state so the depositor has an observable error and, ideally, a path to resubmit/reclaim.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

    fn send_raw_deposit_transaction(&self, deposit: Bytes) -> RpcResult<()> {
        debug!("Sequencer: citrea_sendRawDepositTransaction");

        let deposit_tx_size = deposit.len();
        SM.deposit_tx_size.record(deposit_tx_size as f64);

        let evm = Evm::<DefaultContext>::default();
        let mut working_set = WorkingSet::new(self.context.storage.clone());

        let dep_tx = self
            .context
            .deposit_mempool
            .lock()
            .make_deposit_tx_from_data(deposit.clone().into());

        let start = std::time::Instant::now();
        let tx_res = evm.get_call(
            dep_tx,
            Some(BlockId::pending()),
            None,
            None,
            &mut working_set,
            &self.context.ledger,
        );
        let deposit_tx_call_duration = Instant::now()
            .saturating_duration_since(start)
            .as_secs_f64();
        SM.deposit_tx_call_duration.record(deposit_tx_call_duration);

        match tx_res {
            Ok(hex_res) => {
                tracing::debug!("Deposit tx processed successfully {}", hex_res);
                let add_result = self
                    .context
                    .deposit_mempool
                    .lock()
                    .add_deposit_tx(Deposit::from(deposit.to_vec()));

                match add_result {
                    Ok(true) => Ok(()),
                    Ok(false) => Err(jsonrpsee::types::error::ErrorObject::owned(
                        jsonrpsee::types::error::INVALID_PARAMS_CODE,
                        "Deposit already pending in mempool",
                        None::<()>,
                    )),
                    Err(_) => Err(jsonrpsee::types::error::ErrorObject::owned(
                        jsonrpsee::types::error::INVALID_PARAMS_CODE,
                        "Invalid deposit",
                        None::<()>,
                    )),
                }
            }
            Err(e) => {
                error!("Error processing deposit tx: {:?}", e);
                SM.unaccepted_deposit_txs.increment(1);
                Err(e)
            }
        }
