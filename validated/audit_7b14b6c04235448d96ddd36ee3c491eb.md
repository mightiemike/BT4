### Title
Signature-Malleability Duplicate-Detection Bypass in `ValidateMultiSign` Allows Multisig Weight Double-Counting - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract loops over a caller-supplied array of signatures and accumulates `totalWeight` for each signer address recovered from the account's `Permission`. The duplicate-prevention logic inside the loop only skips an entry when the *exact byte sequence* `(recoveredAddr, sign)` has already been seen; if the same address is recovered from a **different** raw signature (achievable via ECDSA signature malleability), the loop falls through and adds the same key's weight a second time, letting an attacker satisfy a multisig `threshold` with fewer genuinely-authorized keys than required.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()`: [1](#0-0) 

```java
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
```

The intent is clearly to avoid counting the same key's weight twice (mirrored by the `checkWeight`/`addMap.containsKey` duplicate-address check used elsewhere for real transaction signature verification): [2](#0-1) 

However, the branch structure here is broken in exactly the same way as the reported `PoolDistributor.claimLpAmount()` bug: the "already-seen" state (`executedSignList`) is only used to detect an **identical** re-submission, not to reject *any* second occurrence of the same recovered address. When `recoveredAddr` is already present but the concatenated `sign` bytes differ, the code calls `MUtil.checkCPUTime()` (a DoS/CPU-limit guard, not a duplicate-rejection) and then **falls through** to add the weight again and push a second `(sign, addr)` pair.

ECDSA signatures are malleable: for any valid `(r, s, v)` over a message hash, `(r, n-s, 1-v)` (where `n` is the secp256k1 curve order) is also a valid signature that recovers to the identical address. An attacker who controls one private key in the permission's key list can therefore submit the genuine signature plus its malleable counterpart as two "different" entries in the `signatures` array; both recover to the same address but have different raw bytes, so the exact-match check is bypassed and the key's weight is counted twice.

### Impact Explanation
`ValidateMultiSign` is a public precompiled contract (address `0x0a`) callable by any smart contract to check whether a set of off-chain signatures satisfies an account's `Permission` threshold — this is a widely used building block for on-chain multisig/authorization logic (e.g., custodial contracts, gateways, bridges relying on TRON account permissions). Double-counting a single key's weight lets an attacker satisfy a `threshold` using strictly fewer distinct authorized keys than the permission was configured to require, defeating the security guarantee of the multisig scheme and enabling unauthorized execution of privileged logic gated by this precompile — a concrete authorization/access-control bypass.

### Likelihood Explanation
Exploitation only requires: (1) possession of any single valid private key already present in the target `Permission`'s key list (which is the normal case for one of several cosigners who might be malicious or compromised), and (2) trivial ECDSA signature-malleability arithmetic (`s' = n - s`, adjusted recovery id) that is computable off-chain without needing the private key itself once the original signature is known. No special privileges are needed to call `ValidateMultiSign`. This makes exploitation straightforward for any party holding, or intercepting, one valid signature share.

### Recommendation
Change the duplicate check so that a second occurrence of a *recovered address*, regardless of raw signature bytes, is unconditionally skipped (rather than only skipping exact `(addr, sign)` duplicates and otherwise proceeding to add weight):
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    continue; // any repeat of the same address must not contribute weight again
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
executedSignList.add(recoveredAddr);
```
This mirrors the fix pattern for the original report: ensure the state tracking "already processed" identifiers is properly consulted on every iteration so a semantically duplicate entry (same key, different encoding) cannot be counted more than once.

### Proof of Concept
1. Attacker controls key `K1`, one of `N` keys in an `Active` `Permission` with `threshold = 3`, each key weight `1` (so 3 distinct keys are required).
2. Attacker obtains one legitimate signature `sig1 = (r, s, v)` from `K1` over `hash` (e.g., leaked/observed, or attacker is a legitimate co-signer).
3. Attacker computes the malleable counterpart `sig1' = (r, n - s, 1 - v)`, which recovers to the same address as `sig1` but has different raw bytes.
4. Attacker calls `ValidateMultiSign(address, permissionId, data, [sig1, sig1'])`.
5. In the loop: iteration 1 adds weight `1` for `K1`'s address and records `(sig1, addr)`; iteration 2 finds `recoveredAddr` already in `executedSignList` but `sign` (built from `sig1'`) is not found in the list, so it calls `MUtil.checkCPUTime()` and falls through, adding weight `1` again — `totalWeight = 2`.
6. Adding one more genuinely different key's signature (weight 1) reaches `totalWeight = 3 = threshold`, even though only 2 distinct authorized keys actually participated, versus the 3 required by the permission.

Note: I could not inspect the implementation of `ByteArray.matrixContains` and `merge` in this session (index/tool budget exhausted) to fully confirm the exact byte-comparison semantics; the analysis above is based on the call-site logic and naming/usage pattern visible in `PrecompiledContracts.java`. A Devin session with full repository access should verify `ByteArray.matrixContains`'s comparison semantics and add a unit test reproducing the malleable-signature double-count before merging a fix.
