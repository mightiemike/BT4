### Title
Webhook authentication trusts the unauthenticated `X-Shopify-Shop-Domain` header, letting one merchant impersonate another tenant's webhook — (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`, `packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts`)

### Summary
Webhook validation only checks the HMAC of the raw request body; it never binds the `X-Shopify-Shop-Domain` header to that signature. Because a webhook's HMAC is computed with the app's single shared client secret across *all* installed shops (not a per-shop secret), any merchant who has the app installed can capture one of their own genuine webhook deliveries (valid `rawBody` + valid `hmac`) and simply resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different (victim) shop. The library's own validation happily reports `valid: true` and returns the attacker-controlled `domain` value, which downstream code (`authenticateWebhookFactory`) uses—unverified—to load the victim's offline session and construct an authenticated `admin` API client that is then handed to the app's webhook business logic.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC using only `rawBody` and the shared `apiSecretKey`, and compares it to the header's HMAC: [1](#0-0) 

`validateFactory` — used by `shopify.webhooks.validate` — runs that HMAC check and then extracts request headers (including the shop domain) via `checkWebhookHeaders`, with no cross-check that the domain is consistent with anything cryptographically bound to the signed payload: [2](#0-1) 

The domain returned by this check (`check.domain`) is then trusted directly by the higher-level `authenticateWebhookFactory` implementations in both `shopify-app-remix` and `shopify-app-react-router`. It is used, without any additional verification, to look up and vend an authenticated Admin API client: [3](#0-2) [4](#0-3) 

This is directly analogous to the reported `_debitFrom` bug: the function that grants a privileged resource (here, an authenticated `admin` client bound to a specific shop's offline session, there, an NFT transfer) trusts an attacker-suppliable identifier (`X-Shopify-Shop-Domain` / `_from`) instead of verifying it corresponds to the actual authenticated actor of the request. The only "ownership" check performed is an HMAC over the body — which is signed with a secret shared across every shop that has the app installed, so it does not bind the payload to a specific shop's domain claim.

### Impact Explanation
A single merchant who has installed the app (an unprivileged actor with respect to other tenants) can:
1. Receive/capture a genuine webhook delivered to their own shop (body + valid HMAC).
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. Cause the framework to treat the request as an authentic webhook "from" the victim shop, load the victim's offline session, and construct an authenticated `admin` GraphQL/REST client scoped to the victim's shop, which is then passed into the app's own webhook handler code.

Depending on what the app's webhook handler does with `context.admin` and `context.payload` (e.g., processing `orders/create`, updating data, calling mutations), this can result in unauthorized actions being taken against a different merchant's store using their access token, i.e. cross-tenant compromise — a legitimate merchant's data or store state can be manipulated by another merchant abusing this trust gap.

### Likelihood Explanation
High relative to effort required: it requires no secret leakage, no MITM, and no elevated privileges — the attacker only needs their own valid, working install of the target app (which is the normal state for any merchant using it) to obtain a legitimately signed body/HMAC pair, and can then trivially forge the `X-Shopify-Shop-Domain` header on a raw HTTP request to the app's public webhook endpoint.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or the app-proxy/webhook `domain`/`shop` field in general) purely because the request's HMAC validates. At minimum:
- Cross-check that the offline session loaded for `check.domain` actually exists and is legitimately associated with real traffic for that shop (e.g., via additional binding, rate limiting, or requiring the payload itself to independently identify the shop where verifiable, such as validating against Shopify's known IP ranges or using mTLS where available).
- Consider including the shop domain as part of the data whose integrity is verified, or require an additional signed assertion (e.g., only trust a domain once it has completed OAuth/token exchange and matches session storage keyed identifiers established independently of header content) before handing out an authenticated `admin` client.
- At a minimum, document/flag this as a known limitation and encourage consumers of `authenticateWebhookFactory`/`shopify.webhooks.validate` to treat `admin`/`session` from webhook context as a shared-secret trust boundary spanning the app's entire merchant base, not per-tenant isolation.

### Proof of Concept
1. Merchant M installs the target app on `m-shop.myshopify.com` and captures a real webhook delivery, e.g. `orders/create`, noting the raw JSON body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because it's `base64(hmac_sha256(apiSecretKey, B))`, and `apiSecretKey` is shared by the app across all shops).
2. M sends a POST to the app's public webhook route with:
   - Body: `B` (unchanged)
   - Headers: `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Topic: orders/create`, `X-Shopify-Webhook-Id: <any>`, `X-Shopify-Api-Version: <any>`, and **`X-Shopify-Shop-Domain: victim-shop.myshopify.com`**.
3. `shopify.webhooks.validate` (`packages/apps/shopify-api/lib/webhooks/validate.ts`) validates `H` against `B` successfully (domain is irrelevant to the HMAC), and returns `{valid: true, domain: 'victim-shop.myshopify.com', ...}`.
4. `authenticateWebhookFactory` then calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loads victim's offline session/access token, and returns `{admin, session, payload: JSON.parse(B), shop: 'victim-shop.myshopify.com', ...}` to the app's webhook handler — despite the request never having originated from Shopify on behalf of `victim-shop`.

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}
