### Title
`depositPRC20` never checks `TokenConfig.Enabled` before minting PRC20s on inbound execution - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`x/uregistry`'s `TokenConfig` has an explicit `Enabled` boolean documented as "whether this token is enabled for minting/bridging" [1](#0-0) . This is the direct analog of the Vault's paused flag in the external report. However, the actual mint path — `depositPRC20` in `x/uexecutor/keeper/handler.go` — fetches the `TokenConfig` only to read `NativeRepresentation.ContractAddress`, and never checks `tokenConfig.Enabled` before calling `CallPRC20Deposit`.

### Finding Description
`depositPRC20` is the single chokepoint used by all inbound execution paths (`FUNDS`, `FUNDS_AND_PAYLOAD`, `GAS`) to mint PRC20 tokens to a recipient/UEA based on an inbound observed by Universal Validators: [2](#0-1) 

It calls `k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)` and only validates that `NativeRepresentation` is non-nil before proceeding directly to `CallPRC20Deposit`. It never inspects `tokenConfig.Enabled`.

This function is invoked from:
- `ExecuteInboundFunds` (`x/uexecutor/keeper/execute_inbound_funds.go:24`)
- `ExecuteInboundFundsAndPayload` (`x/uexecutor/keeper/execute_inbound_funds_and_payload.go:70,90`)

By contrast, the codebase demonstrably knows how to gate on registry-level enable flags elsewhere — `IsChainInboundEnabled`/`IsChainOutboundEnabled` are checked in `VoteInbound` [3](#0-2)  and in outbound creation (`BuildOutboundsFromReceipt`) [4](#0-3) . The equivalent `TokenConfig.Enabled` check is simply absent from the deposit/mint path — the field is set and stored by admins via `MsgAddTokenConfig`/`MsgUpdateTokenConfig` [5](#0-4) [6](#0-5)  but is never read anywhere in the mint/deposit flow.

### Impact Explanation
The `Enabled` flag on `TokenConfig` is the intended admin kill-switch for a specific token — e.g., to pause bridging of a token after a source-chain exploit, a depeg event, an oracle failure, or a bug discovered in that specific token's gateway integration, without disabling the entire chain (`ChainConfig.Enabled` is chain-wide, not token-specific). Because `depositPRC20` ignores `Enabled`, an unprivileged user submitting an ordinary gateway deposit on the source chain (a normal, honestly-observed inbound event) will still cause honest Universal Validators to vote it through `MsgVoteInbound`, and the core validator will still mint the corresponding PRC20 via `CallPRC20Deposit` even though the admin explicitly disabled that token. This is an "unauthorized mint" continuing to occur against explicit admin intent — the accounting invariant that a disabled token cannot mint further PRC20 supply is broken, directly mirroring the Vault bug where `_depositable`/`_withdrawable` allow deposit/withdrawal flows to proceed despite the pool being paused.

### Likelihood Explanation
Medium. The trigger requires an admin to have disabled a token config (a defensive, presumably rare action taken in response to some anomaly) while inbound events for that same token continue to arrive from the source chain. Any ordinary user depositing on the gateway contract for that (disabled) token/chain pair triggers the bug through the completely standard inbound flow — no privileged action or validator collusion is needed, and honest UVs will vote the observation through as normal because nothing in `VoteInbound`/`ExecuteInboundFunds` checks token-level enablement.

### Recommendation
Add a check for `tokenConfig.Enabled` in `depositPRC20` (and any other token-consuming execution path, e.g. `gasAndPayloadDepositAutoSwap`) immediately after `GetTokenConfig`, returning an error (equivalent to the existing "token config not found" failure path, which already correctly creates a FAILED PCTx / revert flow) when the token is disabled — mirroring how `IsChainInboundEnabled`/`IsChainOutboundEnabled` are already enforced at the chain level.

### Proof of Concept
1. Admin registers `TokenConfig{Chain: "eip155:11155111", Address: usdcAddr, Enabled: true, ...}` and later calls `MsgUpdateTokenConfig` to set `Enabled: false` in response to a security concern about that specific token.
2. An ordinary user deposits `usdcAddr` on the source-chain gateway as usual (no privileged access needed).
3. Honest Universal Validators observe this real gateway event and submit `MsgVoteInbound` — nothing in `VoteInbound` checks `TokenConfig.Enabled` (only `IsChainInboundEnabled` is checked) [3](#0-2) .
4. Once quorum is reached, `ExecuteInboundFunds` calls `depositPRC20`, which fetches the (disabled) `TokenConfig` and proceeds to `CallPRC20Deposit` without checking `Enabled` [7](#0-6) .
5. PRC20 is minted to the recipient despite the admin having disabled that token — the kill switch has no effect on already-in-flight deposit minting.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```
