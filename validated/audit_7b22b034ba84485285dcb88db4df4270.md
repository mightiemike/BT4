### Title
Deposit admission simulated against stale pending state can succeed while actual on-chain execution reverts, silently and permanently dropping the deposit - (File: crates/sequencer/src/rpc.rs, crates/sequencer/src/runner.rs)

### Summary
`send_raw_deposit_transaction` accepts a deposit into `DepositDataMempool` based solely on an `evm.get_call` simulation against `BlockId::pending()` [1](#0-0) . The actual system-transaction execution happens later in `process_sys_txs` against a different, cumulative working-set state built up during real block production, and if it fails with `EvmSystemTransactionNotSuccessful` the code reverts and silently `continue`s without re-queueing [2](#0-1) . Worse, the deposit is then unconditionally removed from the mempool using the original fetched `deposit_data` list, not filtered by whether it was actually included, permanently dropping the failed deposit with no compensating notification or refund [3](#0-2) .

### Finding Description
The broken binding: `send_raw_deposit_transaction` returning `Ok(())` (RPC admission success) should imply the deposit blob is eventually and durably minted on-chain. In code:

- Simulation: `evm.get_call(dep_tx, Some(BlockId::pending()), ...)` runs against a fresh `WorkingSet` built from `self.context.storage.clone()` at `BlockId::pending()`, i.e., the state as of "now" [4](#0-3) . If it returns `Ok`, the deposit blob is added to `DepositDataMempool` and the RPC returns `Ok(())` to the caller, implying the deposit is accepted and will mint [5](#0-4) .
- Later, at real block production time, `produce_l2_block_inner` fetches queued deposits via `fetch_deposits` (not removing them) [6](#0-5)  and passes them into `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs`, which applies `BridgeWrapper::deposit` system transactions sequentially against a working set that has already accumulated all prior system events and, in the real (non-dry-run) apply path, real user transactions applied earlier in the same block [7](#0-6) .
- If the recipient/bridge call reverts at this later point (e.g., recipient contract state changed between simulation time and inclusion time — deployed code, `selfdestruct`, storage changes, or any other state mutation reachable by an unprivileged attacker via ordinary EVM transactions), `apply_l2_block_txs` returns `StateTransitionError::ModuleCallError(EvmSystemTransactionNotSuccessful)`. The code specifically special-cases this for deposits: it reverts the working set and `continue`s to the next system event, without erroring the whole block [8](#0-7) .
- Critically, back in `produce_l2_block_inner`, after the block is finalized, the code removes deposits from the mempool using the **entire fetched `deposit_data`** list (line 638), not a filtered list of deposits that were actually successfully included in `all_txs`: `self.deposit_mempool.lock().remove_deposits(&deposit_data)` [3](#0-2) . This means a deposit that failed inside `process_sys_txs` (and was `continue`d past, never actually appearing in the committed block's system transactions) is nonetheless permanently purged from `DepositDataMempool` by `remove_deposits`, since `remove_deposits` matches by `calc_tx_id` against the full `deposit_data` slice passed in, with no distinction between succeeded and failed deposits [9](#0-8) .

No existing guard prevents this: there is no re-queue path, no dead-letter mempool, no RPC callback, and no `Auth`/authentication-layer check involved—this is a purely internal state-consistency bug between admission-time simulation and inclusion-time execution, compounded by an unconditional mempool purge that does not distinguish success from failure.

Attack path: an unprivileged attacker calls `citrea_sendRawDepositTransaction` with a deposit blob whose Bitcoin move-tx targets an L2 recipient/contract interaction that currently succeeds under simulation (e.g., recipient is an EOA or currently-non-reverting contract). Before the sequencer next produces a block including that deposit, the attacker (or anyone) sends an ordinary EVM transaction that mutates the recipient's on-chain state to cause the bridge's mint/transfer call to revert (e.g., deploys code at that address if it was an EOA-like precondition path, or flips a `require`-guarded flag in a contract the recipient uses, or exhausts a fixed-size structure the bridge writes to). When the sequencer includes both transactions in the same or later block, the deposit's mint reverts with `EvmSystemTransactionNotSuccessful`, is silently skipped, and is then permanently removed from `DepositDataMempool`.

### Impact Explanation
The depositor's Bitcoin-backed cBTC deposit is accepted by the RPC (implying success) but never actually minted, and the deposit blob is permanently dropped from the sequencer's deposit mempool with no re-queue, refund, or notification mechanism, per `remove_deposits` unconditionally purging by `deposit_data` regardless of the sys-tx outcome [3](#0-2) . This matches the Critical impact category "funds permanently frozen" — the depositor's Bitcoin is locked/moved on the DA side but the L2 credit never materializes, and there is no code path to retry, since the deposit blob is gone from mempool state and there's no on-chain-only trigger (deposits are driven purely by the sequencer's mempool contents). This is repeatable per deposit and can be triggered against any depositor's queued deposit if the attacker can find/create a state-dependent revert condition in the recipient path before block inclusion.

### Likelihood Explanation
No privileged role is required. The attacker only needs the ability to submit ordinary L2 transactions (already assumed capability) between the time a target deposit is admitted via `citrea_sendRawDepositTransaction` and the time it is actually included in a produced L2 block — a window that exists on every deposit due to the mempool/fetch/produce cycle (`fetch_deposits` at production time, not at admission time) [6](#0-5) . Whether an attacker can reliably manufacture a revert-inducing state transition depends on the specific `BridgeWrapper::deposit` recipient-handling logic (not fully visible in the index), but the underlying sequencer-level bug — mismatched simulation state vs. execution state, and unconditional mempool purge on failure — is unconditionally present and independently exploitable by anyone who can cause any state change that flips the deposit call from succeeding to reverting between simulation and inclusion (this needn't be adversarial in intent; ordinary contention could also trigger it, but an attacker can deliberately engineer it). Cost is limited to normal L2 gas fees plus the cost of inscribing a deposit-format Bitcoin transaction.

### Recommendation
Re-validate deposit calls immediately before real inclusion (i.e., simulate against the actual working-set state used in `process_sys_txs` right before applying, not a separate `BlockId::pending()` snapshot taken at admission time), and/or change `process_sys_txs`/`produce_l2_block_inner` to only remove from `DepositDataMempool` the deposits that were actually included in `all_txs` (successful), leaving failed ones in the mempool for retry, or explicitly move failed deposits to a distinct "failed/needs-manual-intervention" store with an RPC/API to inspect and refund them rather than silently dropping the blob.

    /// Removes specific deposits from the mempool after they have been successfully included in a block
    ///
    /// # Arguments
    /// * `deposits_to_remove` - The deposits that were successfully included
    ///
    /// # Returns
    /// The number of deposits actually removed
    #[instrument(level = "trace", skip_all, ret)]
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
