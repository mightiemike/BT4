### Title
Unprotected ratio-based liquidity Inject/Withdraw in the TRC10 Bancor Exchange allows atomic price-manipulation extraction of value - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The reported bug class is a mismatch between how a pooled-asset protocol values/handles deposits vs. withdrawals, allowing an attacker to exploit a stale or manipulable valuation for one side of the pool to extract more value than deposited. Java-tron's built-in TRC10 "Exchange" (a Bancor-style two-token relay pool) has an analogous flaw: `ExchangeInjectContract`/`ExchangeWithdrawContract` compute the paired token amount from the **current spot ratio** of the pool reserves, with **no slippage/"expected" bound** (unlike `ExchangeTransactionContract`, which does have an `expected` field). Because the pool's ratio can be shifted arbitrarily within the same transaction/block via `ExchangeTransactionContract` (which moves reserves through a non-linear bonding-curve formula, not a simple constant ratio), the linear ratio used by Inject/Withdraw diverges from the "fair" curve-implied price and can be manipulated immediately before an Inject/Withdraw call.

### Finding Description
`ExchangeInjectActuator.execute()` computes the paired token amount purely from the current linear reserve ratio: [1](#0-0) 

`ExchangeWithdrawActuator.execute()` does the same for withdrawals: [2](#0-1) 

Neither contract message carries a caller-supplied bound/deadline to protect against ratio movement: [3](#0-2) 

By contrast, `ExchangeTransactionContract` (the actual swap operation) explicitly exposes an `expected` minimum-output guard, showing the protocol designers recognized the need for slippage protection for one operation but omitted it for Inject/Withdraw: [4](#0-3) 

Critically, a swap (`ExchangeTransactionContract`) moves the pool through a Bancor "relay" bonding-curve formula (`ExchangeProcessor.exchange`), which is **not** a simple constant ratio — it intentionally produces a different marginal price than the raw `firstTokenBalance : secondTokenBalance` ratio used by Inject/Withdraw: [5](#0-4) [6](#0-5) 

This is the exact class of bug from the report: two different mechanisms operate on the same shared pool of value using two different valuation methodologies (bonding-curve swap price vs. linear reserve-ratio deposit/withdraw price), and one of them (Inject/Withdraw) has no protection against the other (swap) shifting the reference price within the same transaction bundle/block. Only the exchange creator can call Inject/Withdraw, but this is a self-selected role available to any account that calls `ExchangeCreateActuator` (not a system-privileged actor like a witness or node operator), and the victims of the manipulation are the pool's counterparties who trade via `ExchangeTransactionContract` against the corrupted reserves: [7](#0-6) [8](#0-7) 

### Impact Explanation
An exchange creator (any ordinary account, not a privileged node role) can atomically bundle: (1) an `ExchangeTransactionContract` swap to skew reserves away from the bonding-curve-implied fair value, (2) an `ExchangeWithdrawContract`/`ExchangeInjectContract` call that computes the paired-token amount from the now-skewed linear ratio (extracting a disproportionate amount of the more valuable reserve token or contributing a cheaper amount of the less valuable one), and (3) a reversing swap to restore the visible ratio. This directly corrupts the exchange's reserve accounting relative to its bonding-curve pricing invariant, degrading the effective liquidity/price available to subsequent unprivileged traders using `ExchangeTransactionContract`, and lets the creator siphon value out of (or cheaply inject undervalued liquidity into) the pool. This falls under "asset or accounting corruption" reachable purely via broadcast transactions.

### Likelihood Explanation
All required contracts (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) are ordinary broadcastable transactions with no special permission beyond being the exchange's creator address, which any account can become by calling `ExchangeCreateContract`. Bundling multiple transactions from the same account within one block (or as sequential transactions) is trivial for any user, requiring no validator/witness collusion, no leaked keys, and no P2P-level manipulation.

### Recommendation
Add slippage/deadline protection to `ExchangeInjectContract` and `ExchangeWithdrawContract` (an `expected`/minimum or maximum paired-token bound, analogous to the field already present on `ExchangeTransactionContract`), and/or compute Inject/Withdraw paired amounts using a time-weighted or otherwise manipulation-resistant reference of the pool ratio rather than the instantaneous post-swap reserve ratio, consistent with the general recommendation from the referenced report (even out exposure across valuation sources / avoid single-block atomic valuation dependence, or add a timelock between swap and liquidity operations).

### Proof of Concept
1. Attacker creates an exchange via `ExchangeCreateContract` supplying `firstTokenBalance`/`secondTokenBalance` (becomes the pool "creator"), executed by `ExchangeCreateActuator.execute()`.
2. From any account, attacker (or an accomplice) submits an `ExchangeTransactionContract` selling a large quantity of `firstToken`, which is processed by `ExchangeCapsule.transaction()` using the Bancor `ExchangeProcessor`, materially shifting `firstTokenBalance`/`secondTokenBalance` away from their bonding-curve-consistent fair ratio: [9](#0-8) 
3. Immediately after (same block), the creator submits `ExchangeWithdrawContract` for a chosen `tokenQuant` of `secondToken`; `ExchangeWithdrawActuator` computes `anotherTokenQuant` (amount of `firstToken` returned) using the now-skewed linear ratio rather than the pre-swap fair ratio: [10](#0-9)  — extracting more `firstToken` per unit of `secondToken` withdrawn than would be fair pre-manipulation, with no `expected`/minimum check available on this contract type to block it.
4. Attacker reverses the initial swap with a second `ExchangeTransactionContract`, restoring the visible ratio while having permanently extracted the manipulated withdrawal delta from the pool's reserves, at the expense of the pool's economic backing for future traders.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
