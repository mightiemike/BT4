### Title
Replay-verify integrity check omits state-checkpoint-hash comparison, masking state-root divergence during archive replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by `db-tool replay_on_archive`'s `Verifier::execute_and_verify` to confirm that locally re-executed transactions match the transaction infos recorded on the authenticated backup/archive. It compares status, gas used, write-set hash, and event-root hash, but explicitly does **not** compare the `state_checkpoint_hash` (or hot-state/position checkpoint hashes) carried in the authenticated `TransactionInfo` against anything derived from local re-execution.

### Finding Description
`ensure_match_transaction_info` at [3](#0-2)  validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set` hash vs `txn_info.state_change_hash()`
- event-root hash vs `txn_info.event_root_hash()`

It never touches `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The function's own trailing comment concedes this gap: "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [4](#0-3) .

`replay_on_archive.rs`'s `Verifier::execute_and_verify` calls exactly this function as the terminal correctness check for each replayed transaction, with no additional comparison of any state-tree root anywhere else in that path [5](#0-4) . The write-set hash check only confirms the *raw list of write ops* matches — it says nothing about whether applying that write-set to the *local Merkle/Jellyfish state tree* produces the same root that was actually committed and signed at that version. Divergence in the state-tree layer (e.g., in how a write-set is folded into the persistent Sparse/Jellyfish Merkle tree, or in hot-state/position-state constructs) is exactly the class of bug this checkpoint-hash field exists to catch, and it is silently skipped.

### Impact Explanation
This weakens the state-integrity guarantee of the `db-tool replay_on_archive` verification tool. If the local execution/storage pipeline produces a state root that differs from the one actually committed/signed by validators — while still generating an equal write-set list, events, gas, and status — `replay_on_archive` will report success even though the "committed state differs from the correct VM result or corrupts durable ledger data" for that version. This is a state-commitment/proof-integrity gap explicitly in scope (replay-verify masking divergence). However, the impact is bounded: this tool only affects an offline auditing/verification utility, not the live consensus/commit path itself — it does not corrupt a live node's ledger, and does not by itself let anyone forge a proof accepted by mainnet nodes during normal operation. It reduces confidence that replay-verify would catch a hard-fork-class divergence, but does not itself cause one.

### Likelihood Explanation
The gap is deterministic and unconditional (no feature flag gate for the ordinary path since `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is referenced only as a not-yet-enabled placeholder in the comment), meaning any local execution/storage bug that changes only the state-tree structure while leaving write-set contents unchanged would go undetected by this tool every time it runs — a real, reachable condition, not a hypothetical.

### Recommendation
Extend `ensure_match_transaction_info` (and its callers, including `replay_on_archive`) to compare `txn_info.state_checkpoint_hash()` (and, where enabled, hot-state/position-state checkpoint hashes) against the checkpoint hash computed from local re-execution's resulting state, so replay-verify cannot report success while the authenticated state root diverges from local computation.

### Proof of Concept
Not applicable as an exploitable transaction sequence — this is a verification-logic gap in an offline tool, not a state-transition bug reachable by a normal transaction. Demonstrating it requires constructing a local storage/execution bug that preserves write-set/event/gas/status equality but changes the resulting state-tree root, which is outside what can be confirmed from static code reading alone.

**Uncertainty**: I was not able to fully confirm whether any other check elsewhere in `replay_on_archive` (e.g., a full JMT root comparison performed outside `execute_and_verify`) independently closes this gap for the CLI tool. Within the code I could inspect, no such independent check exists in `storage/db-tool/src/replay_on_archive.rs`, but I could not rule out that check being intentionally deferred pending the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature work referenced in the comment, which would mean this is already a tracked/acknowledged gap rather than an undiscovered one.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
