## Title
Missing slippage protection in TRON native Exchange inject/withdraw actuators enables price-manipulation extraction - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's built-in Bancor-style `Exchange`/`ExchangeV2` market (TRC10 AMM pools) exposes `ExchangeInjectContract` (liquidity mint) and `ExchangeWithdrawContract` (liquidity burn) actuators that compute the counter-asset amount purely from the pool's live balances at execution time, with no user-supplied minimum/maximum bound and no deadline field, exactly mirroring the reported Mint/Burn order design flaw.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no minimum-received (`anotherTokenQuant`) bound. In `ExchangeInjectActuator.execute()` the paired amount is derived from whatever the pool balances are at execution time: [1](#0-0)  Likewise, `ExchangeWithdrawContract` only carries a `quant` to burn, and `ExchangeWithdrawActuator.execute()` recomputes the paired payout from the live pool ratio: [2](#0-1)  Neither `doValidate()` in the inject actuator nor the withdraw actuator accepts or checks a user-specified slippage bound — the withdraw actuator's only bound-like check is an unrelated rounding-precision guard (`"Not precise enough"`), not a user intent/minimum-output check: [3](#0-2) 

Because these are ordinary broadcast transactions processed asynchronously (mempool → block inclusion), an attacker can submit an `ExchangeTransactionContract` swap (also unprivileged, callable by any account) to shift `firstTokenBalance`/`secondTokenBalance` immediately before a pending inject/withdraw is packed into the same or a following block, then reverse the swap afterward — precisely the "Bob" scenario from the external report, but here realized against java-tron's native Bancor exchange rather than a Tolk-based CLMM pool.

### Impact Explanation
A liquidity provider injecting or withdrawing from an `Exchange`/`ExchangeV2` pool can be forced into an unfavorable balance split with no on-chain guard to make the transaction revert, allowing an attacker to extract value from the victim's mint/burn action via sandwich-style manipulation of the pool ratio. This is exchange/market-math accounting corruption reachable purely via broadcast transactions, matching the report's "value extraction from user's withdrawal" impact.

### Likelihood Explanation
Likelihood is limited by the fact that only the exchange's `creatorAddress` may call `ExchangeInjectContract`/`ExchangeWithdrawContract` for a given pool (enforced in `doValidate()`), [4](#0-3)  so the victim set is restricted to that pool's creator rather than arbitrary LPs. However, the attacker side of the exploit (the manipulative swap via `ExchangeTransactionContract`) requires no special privilege, and TRON's native exchange feature is still active/reachable in this repo's actuator set, so a motivated attacker monitoring a known exchange creator's pending inject/withdraw transactions could execute this at low cost.

### Recommendation
Short term: add optional minimum/maximum counter-token-quant fields (and optionally an expiration/deadline) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce them in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` execute paths so the transaction fails (`ContractExeException`) when the computed `anotherTokenQuant` falls outside the caller's bound. Long term: add regression tests that manipulate pool balances between contract construction and execution (simulating an interleaved swap) and assert inject/withdraw revert when bounds are violated and succeed when within bounds, following the pattern already used for `ExchangeTransactionActuator`'s `expected` parameter.

### Proof of Concept
1. Exchange creator C broadcasts `ExchangeWithdrawContract{exchangeId, tokenId=T1, quant=Q}` intending to receive `~R` of `T2` based on the current pool ratio.
2. Attacker A observes C's pending transaction and broadcasts a large `ExchangeTransactionContract` swap that shifts the pool's `firstTokenBalance`/`secondTokenBalance` ratio, timed to land before C's withdraw executes (both are ordinary unprivileged broadcast transactions competing for block inclusion).
3. `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` from the now-manipulated balances [2](#0-1)  — C receives significantly less `T2` than expected, with no revert path since no minimum bound exists.
4. A reverses the swap afterward, capturing the price differential, analogous to the reported sandwich attack on Mint/Burn orders.
