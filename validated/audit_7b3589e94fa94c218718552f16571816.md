### Title
Unbounded parallel Future submission to shared `sectionExecutor` in `LogBlockQuery.partialMatch`/`subMatch` allows `eth_getLogs` RPC calls to exhaust the JSON-RPC executor pool - (File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java)

### Summary
`LogBlockQuery.getPossibleBlock()` iterates every section between `minSection` and `maxSection` (derived directly from the caller-supplied `fromBlock`/`toBlock`) and, for each section, `partialMatch()` submits one `Future` per unique bloom bit index to the shared `sectionExecutor` [1](#0-0) . Nothing in this code path bounds the number of concurrently in-flight `Future`s per request or across concurrent requests, so a wide-range `eth_getLogs` query (e.g. `fromBlock=0,toBlock=latest`) generates a number of tasks proportional to `(maxSection - minSection) * uniqueBitIndexes`, and many concurrent such requests multiply that load on one shared thread pool.

### Finding Description
`getPossibleBlock()` computes `minSection`/`maxSection` straight from the RPC-supplied `fromBlock`/`toBlock` filter values [2](#0-1) , then calls `subMatch()` once per condition, which loops `section = minSection..maxSection` and calls `partialMatch()` for every section [3](#0-2) . Inside `partialMatch()`, for every unique bloom bit index derived from the filter’s addresses/topics, a task is submitted to `sectionExecutor.submit(...)` and the resulting `Future` is stored in a `Map`, then all Futures are joined with blocking `.get()` calls [4](#0-3) . There is no semaphore, queue-depth check, or per-request task cap in this method or in the callers (`subMatch`, `getPossibleBlock`).

Because `sectionExecutor` is passed in from the JSON-RPC service layer and reused for all `eth_getLogs`-style queries, concurrent wide-range requests each spawn a burst of tasks against the same pool. If the pool is bounded (fixed size) with an unbounded work queue, tasks pile up in the queue, delaying/starving other legitimate RPC filter queries relying on the same executor; if the queue is bounded, `RejectedExecutionException` may propagate, but more importantly the blocking `.get()` calls on outstanding Futures tie up whatever thread issued the RPC call for the full duration of processing the backlog, and per-request memory (`Map<Integer, Future<BitSet>>`, `resultCache`) scales with `(maxSection-minSection) * uniqueBitIndexes`, so many concurrent full-range requests can also drive up heap usage.

I could not confirm from the retrieved code whether a maximum block-range guard (e.g., a `maxBlockRange`/filter size limit config) is enforced upstream in `TronJsonRpcImpl` before constructing `LogBlockQuery`; searches located many references in that file and in `reference.conf` but I was unable to view the exact validation logic before running out of iterations. This is a gap in my verification — if such a limit exists and defaults to a small range, the practical severity of this finding would be substantially reduced. Based on the code that was directly inspected, `LogBlockQuery` itself performs no such bounding, so the exposure exists at least at this layer.

### Impact Explanation
This falls under DoS via RPC-API: an unprivileged remote client issuing ordinary `eth_getLogs` JSON-RPC calls (no auth, no fee, no on-chain transaction required) can force disproportionate CPU/thread/memory consumption on the shared `sectionExecutor`, degrading or stalling other RPC-API log-filter operations for other callers on the same node.

### Likelihood Explanation
Preconditions are default configuration and no special privileges — just network access to the node's JSON-RPC endpoint, which is normal for any public full node exposing `eth_getLogs`. The attack is cheap (no gas/fee, just HTTP requests) and trivially repeatable/parallelizable from multiple sockets. Actual severity depends on (a) the `sectionExecutor`'s configured pool/queue size and (b) whether an upstream block-range limit exists in `TronJsonRpcImpl`, both of which I was unable to fully confirm in the available context.

### Recommendation
Add an explicit cap on the number of sections/bit-index tasks a single `LogBlockQuery` can submit (e.g., reject or chunk queries whose `(maxBlock-minBlock)` exceeds a configurable maximum, independent of/complementing any existing upstream range check), and/or use a bounded semaphore or dedicated bounded thread pool per request to cap concurrently in-flight `Future`s so that one or many concurrent wide-range queries cannot monopolize the shared executor used by other RPC callers.

  private BitSet subMatch(int[][] bitIndexes) throws ExecutionException, InterruptedException {

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet subBitSet = new BitSet(capacity);

    for (int section = minSection; section <= maxSection; section++) {
      BitSet partialBitSet = partialMatch(bitIndexes, section);

      for (int i = partialBitSet.nextSetBit(0); i >= 0; i = partialBitSet.nextSetBit(i + 1)) {
        // operate on index i here
        if (i == Integer.MAX_VALUE) {
          break; // or (i+1) would overflow
        }
        int offset = (section - minSection) * SectionBloomStore.BLOCK_PER_SECTION + i;
        subBitSet.set(offset);
      }
    }

    return subBitSet;
  }

  private BitSet partialMatch(final int[][] bitIndexes, int section)
      throws ExecutionException, InterruptedException {
    // 1. Collect all unique bitIndexes
    Set<Integer> uniqueBitIndexes = new HashSet<>();
    for (int[] index : bitIndexes) {
      for (int bitIndex : index) { //normally 3, but could be less due to hash collisions
        uniqueBitIndexes.add(bitIndex);
      }
    }

    // 2. Submit concurrent requests for all unique bitIndexes
    Map<Integer, Future<BitSet>> bitIndexResults = new HashMap<>();
    for (int bitIndex : uniqueBitIndexes) {
      Future<BitSet> future
          = sectionExecutor.submit(() -> sectionBloomStore.get(section, bitIndex));
      bitIndexResults.put(bitIndex, future);
    }

    // 3. Wait for all results and cache them
    Map<Integer, BitSet> resultCache = new HashMap<>();
    for (Map.Entry<Integer, Future<BitSet>> entry : bitIndexResults.entrySet()) {
      BitSet result = entry.getValue().get();
      if (result != null) {
        resultCache.put(entry.getKey(), result);
      }
    }
