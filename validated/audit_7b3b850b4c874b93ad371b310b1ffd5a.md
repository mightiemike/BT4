## Analog Found: Insufficient Chain-Head-Based Confirmation Depth Permits Unbacked PRC20 Minting on Source-Chain Reorg

### Title
Inbound confirmation relies on live chain-head confirmation counts (not safe/finalized tags), allowing honest Universal Validators to vote in — and Push Chain to permanently mint PRC20 for — an inbound event whose source-chain transaction is later reorganized out - (File: `universalClient/chains/evm/event_confirmer.go`)

### Summary
This is the direct Push Chain analog of the reported Chainlink VRF `REQUEST_CONFIRMATIONS` issue: a fixed number of block confirmations, counted against a chain's *live* head rather than a reorg-safe checkpoint, is used to decide when an externally observed event is "final" enough to act upon. In Push Chain, the `EventConfirmer` marks an inbound `CONFIRMED` once `latestBlock - receipt.BlockNumber + 1 >= requiredConfirmations`, using confirmation counts (`FastInbound`/`StandardInbound`, defaulting to 2/5 and 12) sourced from `uregistry.BlockConfirmation` [1](#0-0) . Once confirmed, Universal Validators submit `MsgVoteInbound`, and once 2/3+ honest votes converge, `x/uexecutor` permanently mints PRC20 tokens to the recipient's UEA via `depositPRC20`/`CallPRC20Deposit` [2](#0-1) . If the source chain later reorganizes past the configured confirmation depth (exactly the Polygon reorg scenario in the external report), the underlying deposit transaction can vanish from the canonical chain while the corresponding PRC20 mint on Push Chain is irreversible.

### Finding Description
The event-confirmation logic in `universalClient/chains/evm/event_confirmer.go` computes confirmations purely from the RPC's `latest` block head: `confirmations := latestBlock - receipt.BlockNumber.Uint64() + 1` [3](#0-2) . There is no use of a chain's `safe`/`finalized` block tag, and the required confirmation counts default to only 2 (fast) / 12 (standard) blocks [4](#0-3) , values chosen per-chain by the admin-curated `uregistry.ChainConfig.BlockConfirmation` [5](#0-4) . The Solana client has the analogous `applyDefaults`/`EventConfirmer` logic using `latestSlot` [6](#0-5) .

Once `CONFIRMED`, honest Universal Validators independently submit `MsgVoteInbound` for the observed event; the ballot machine finalizes at 2/3+ agreement [7](#0-6) . On finalization, `x/uexecutor` unconditionally executes the inbound and calls `depositPRC20` → `CallPRC20Deposit`, which performs a real, module-signed EVM mint of PRC20 tokens into the recipient UEA [8](#0-7) . There is no subsequent on-chain or off-chain mechanism that re-checks the source-chain transaction's continued canonical inclusion after the mint has occurred (i.e., no post-mint reorg watch, no burn/claw-back on later-discovered reorg). Confirmed/pending event bookkeeping only distinguishes `PENDING` vs `CONFIRMED` vs terminal states (`COMPLETED`, `REVERTED`, `REORGED`) at the pre-vote stage [9](#0-8) ; the `REORGED` status exists for pre-confirmation cleanup, but nothing detects a reorg of an already-`CONFIRMED`/already-voted/already-minted event.

Because confirmation counts are measured against a live, unbounded chain head rather than a chain-native finality checkpoint, and because the values are static per-chain defaults not derived from empirically observed reorg depth (mirroring the flaw the external report identifies for `REQUEST_CONFIRMATIONS = 3` on Polygon), a source chain with reorg depth exceeding the configured `StandardInbound`/`FastInbound` value can cause every honest, correctly-functioning Universal Validator to observe, confirm, and vote for a transaction that is subsequently dropped from that chain's canonical history — with Push Chain having already permanently minted the corresponding PRC20 supply.

### Impact Explanation
This is a direct unauthorized/unbacked mint of PRC20 tokens: value materializes on Push Chain that is not backed by a corresponding locked/burned asset on the source chain, since the underlying deposit is later invalidated by a legitimate (not malicious) chain reorg. This falls squarely within the allowed impact gate's "unauthorized mint... of user or protocol-controlled funds" and "corruption of PRC20 or native asset accounting," triggered purely by ordinary user deposit flow plus an honest-but-reorg-prone source chain — no privileged or malicious actor is required.

### Likelihood Explanation
Likelihood depends heavily on which source chains are configured and their actual confirmation defaults versus that chain's real-world reorg statistics — for EVM chains with fast block times and probabilistic finality (the exact class the original report warns about), the default `StandardInbound = 12` may be insufficient in the same way `REQUEST_CONFIRMATIONS = 3` was insufficient for Polygon. Because these thresholds are admin-set per chain (not attacker-controlled), likelihood is chain-dependent and contingent on operational configuration choices rather than a code-level authorization bypass; nonetheless it is a code-level design gap that no configuration value can fully close on a probabilistic-finality chain, since the check never consults a chain's own finality signal (`safe`/`finalized` tag) as a floor.

### Recommendation
- Where the source chain's RPC exposes `safe` or `finalized` block tags (post-merge Ethereum, and equivalents on other EVM chains), require confirmation against that tag rather than (or in addition to) a fixed offset from `latest`.
- For chains without native finality tags, derive `StandardInbound`/`FastInbound` defaults from measured historical reorg depth for that specific chain (as the original report recommends for Polygon), and validate that operators cannot configure a value below a chain-specific safe floor.
- Add a lightweight post-confirmation/post-vote reorg watchdog: after `CONFIRMED` (and ideally after mint), periodically re-verify the transaction/receipt still exists at the same block hash for some additional trailing window, and if not, drive a compensating on-chain action (e.g., flag the `UniversalTx` for admin/governance review or trigger a burn/adjustment path) rather than treating the mint as unconditionally final.

### Proof of Concept
1. Admin configures `ChainConfig.BlockConfirmation.StandardInbound = 12` for an EVM chain with occasional reorgs deeper than 12 blocks (as documented for Polygon).
2. A user deposits funds into the gateway contract on that chain; the deposit lands in block `N`.
3. `EventConfirmer.processPendingEvents` observes `latestBlock - N + 1 >= 12` and marks the event `CONFIRMED` [10](#0-9) .
4. All honest Universal Validators independently reach the same conclusion and submit `MsgVoteInbound`; 2/3+ threshold is reached and the ballot finalizes [11](#0-10) .
5. `x/uexecutor` executes `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit`, minting PRC20 to the recipient UEA [12](#0-11) .
6. A 13+ block reorg occurs on the source chain (documented as occurring on chains like Polygon) that removes block `N` and the deposit transaction from the canonical chain.
7. The minted PRC20 on Push Chain remains — no compensating burn or reversal mechanism exists — resulting in unbacked PRC20 supply.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) VoteOnInboundBallot(
	ctx context.Context,
	universalValidator sdk.ValAddress,
	inbound types.Inbound,
) (isFinalized bool,
	isNew bool,
	err error) {
	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return false, false, err
	}

	universalValidatorSet, err := k.uvalidatorKeeper.GetEligibleVoters(ctx)
	if err != nil {
		return false, false, err
	}

	// number of validators
	totalValidators := len(universalValidatorSet)

	// votesNeeded = ceil(2/3 * totalValidators)
	// >2/3 quorum similar to tendermint
	votesNeeded := (types.VotesThresholdNumerator*totalValidators)/types.VotesThresholdDenominator + 1

	k.Logger().Debug("voting on inbound ballot",
		"ballot_key", ballotKey,
		"validator", universalValidator.String(),
		"total_validators", totalValidators,
		"votes_needed", votesNeeded,
	)

	// Convert []sdk.ValAddress → []string
	universalValidatorSetStrs := make([]string, len(universalValidatorSet))
	for i, v := range universalValidatorSet {
		universalValidatorSetStrs[i] = v.IdentifyInfo.CoreValidatorAddress
	}

	// Step 2: Call VoteOnBallot for this inbound synthetic
	_, isFinalized, isNew, err = k.uvalidatorKeeper.VoteOnBallot(
		ctx,
		ballotKey,
		uvalidatortypes.BallotObservationType_BALLOT_OBSERVATION_TYPE_INBOUND_TX,
		universalValidator.String(),
		uvalidatortypes.VoteResult_VOTE_RESULT_SUCCESS,
		universalValidatorSetStrs,
		int64(votesNeeded),
		int64(types.DefaultExpiryAfterBlocks),
	)
	if err != nil {
		return false, false, err
	}

	if isNew {
		k.Logger().Debug("inbound ballot created", "ballot_key", ballotKey)
	}
	if isFinalized {
		k.Logger().Info("inbound ballot finalized", "ballot_key", ballotKey, "source_chain", inbound.SourceChain)
	}

	return isFinalized, isNew, nil
}
