### Title
Insufficient duplicate-detection in `ValidateMultiSign.execute` allows ECDSA signature-malleability double-counting of a single signer's weight - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompile deduplicates signatures by comparing the exact byte content of `recoveredAddr + sign` (`matrixContains(executedSignList, sign)`), not by comparing `recoveredAddr` alone. Because ECDSA signatures are malleable (a signature `(r, s, v)` and its counterpart `(r, n-s, 1-v)` both recover to the same address but are byte-distinct), an attacker can submit two differently-encoded signatures from the *same* private key and have `totalWeight` incremented twice for that single key.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute`: [1](#0-0) 

For each supplied signature, `recoveredAddr` is computed, then `sign` is redefined as `merge(recoveredAddr, sign)`. The loop only skips weight accumulation (`continue`) when the **exact merged byte array** already exists in `executedSignList`. If `recoveredAddr` is already present but the merged `sign` bytes differ, the code calls `MUtil.checkCPUTime()` and then falls straight through into the weight-accumulation logic instead of skipping it — there is no `continue` after the `checkCPUTime()` call on that path. This means `TransactionCapsule.getWeight(permission, recoveredAddr)` is invoked again for the same address and `totalWeight` is incremented a second time.

Because ECDSA signatures are malleable, an attacker holding a single valid signing key can produce two byte-distinct 65-byte signatures `(r, s, v)` and `(r, n-s, 1-v)` (where `n` is the secp256k1 curve order) that both recover to the identical `recoveredAddr` for the same message hash. Since the dedup check compares the full merged byte array rather than `recoveredAddr`, these two malleable variants are treated as "different" signatures, and the weight for that one key is added twice into `totalWeight`.

This bypasses the intended multisig invariant that `totalWeight` should reflect only unique signer weights. An attacker with a single key whose permission weight is less than `permission.getThreshold()` but at least half of it can reach the threshold by submitting the same key's signature in both malleable forms.

### Impact Explanation
This is an authorization/permission-threshold bypass in the `validateMultiSign` precompile used by smart contracts to gate privileged operations (e.g., asset transfers, multisig-protected withdrawals) on TVM. An attacker can satisfy a multisig `Active` permission threshold using effectively one private key's weight counted twice, enabling unauthorized execution of the gated contract logic — falling into the "unauthorized account operations / asset accounting corruption" bounty impact class.

### Likelihood Explanation
Preconditions: the target account's `Active` permission has `threshold` set such that a single key's weight, if doubled, meets or exceeds it (e.g., weight ≥ threshold/2), and the attacker already possesses a valid signature from one authorized key (this could be the attacker's own key if they are one of several signers with insufficient combined weight, or a leaked/authorized-but-insufficient key). No privileged role, RPC/node config changes, or special access is required — this is purely a crafted contract call with attacker-supplied `rawData`. Generating the malleable counterpart signature `(r, n-s, 1-v)` from a known `(r, s, v)` is trivial arithmetic (`s' = n - s`, `v' = 1 - v`), so the exploit is cheap and fully repeatable.

### Recommendation
Change the duplicate-detection to be based solely on `recoveredAddr` (not the full merged signature bytes): once an address has contributed weight, any subsequent signature recovering to that same address — malleable or not — must be skipped via `continue`, regardless of byte-level differences in the signature. E.g., restructure the loop to check/add only `recoveredAddr` in `executedSignList` before computing weight, removing reliance on exact-byte signature comparison for dedup.
