### Title
DoS via unsatisfiable "Not precise enough" precision check permanently blocking ExchangeWithdraw of small remaining pool balances - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator.doValidate()` computes a proportional "another token" amount from the exchange pool's current balances and rejects the withdrawal if the rounding error exceeds a relative tolerance (`0.0001`). Like the reported Amun `BasketFacet` bug — where a hard-coded `MIN_AMOUNT` check applied to the whole pool (not the caller's own balance) makes the final withdrawal impossible once the pool shrinks — this TRON check is evaluated against the pool's *current* `firstTokenBalance`/`secondTokenBalance` rather than being scaled to guarantee satisfiability for any remaining state, so as the pool balances shrink toward small values the relative-precision requirement can become permanently unsatisfiable for any nonzero partial withdrawal quantity, without offering the caller a way to correct it.

### Finding Description
In `doValidate()`, when a token id matches `firstTokenID`, the code computes: [1](#0-0) 
the `anotherTokenQuant` via integer (`divideToIntegralValue`) division, then separately re-computes the same ratio with 4-decimal rounding and compares the delta against `0.0001 * anotherTokenQuant`, throwing `"Not precise enough"` if it fails. This same pattern is mirrored in the `secondTokenID` branch: [2](#0-1) 
Because the tolerance is relative to `anotherTokenQuant` (which itself shrinks as pool balances shrink and rounds to small integers), for small pool balances the achievable set of `tokenQuant` values that pass this check can become empty except for withdrawing the *entire* remaining balance in one shot (and even that isn't always guaranteed depending on the balance ratio). The existing unit tests demonstrate this directly — attempting to withdraw quantities that don't align with the current exchange ratio throws `"Not precise enough"` even for otherwise legitimate small withdrawals: [3](#0-2) 
This is structurally the same root cause as the Amun finding: a check computed from pool-wide state (rather than being satisfiable for the specific withdrawal being attempted) that can make it impossible to extract a valid amount once the pool's remaining balances fall into certain ranges.

### Impact Explanation
If the exchange's `firstTokenBalance`/`secondTokenBalance` shrink to a state where no positive `tokenQuant` less than the full balance satisfies the 0.0001 relative-precision bound, the exchange creator (the only party authorized to call `ExchangeWithdrawContract`, per the creator check at line 181) may be unable to perform partial withdrawals of the remaining pool assets, potentially locking those TRX/TRC10 tokens inside the exchange object indefinitely if the creator does not (or cannot, due to other validation like `withdraw token quant must greater than zero`) withdraw the exact full remaining balance in a single transaction.

### Likelihood Explanation
Because `ExchangeWithdrawContract` is restricted to the exchange creator address, this is lower-severity than the original Amun multi-holder scenario (any address could deposit/exit the basket), but it is still reachable by any account that created a `Bancor`-style exchange via `ExchangeCreateContract` and injected/traded down its balances via `ExchangeTransactionContract`, both broadcastable by ordinary transactions without special privilege.

### Recommendation
Avoid rejecting withdrawals purely on a relative-precision heuristic computed from current pool state; either allow withdrawal of the full remaining balance unconditionally, or perform the precision check using the requested `tokenQuant`/`anotherTokenQuant` pair validated against an absolute tolerance that is guaranteed satisfiable at any balance level, ensuring the creator can always drain the exchange down to zero.

### Proof of Concept
1. Create an exchange with small `firstTokenBalance`/`secondTokenBalance` (e.g., via repeated `ExchangeTransactionContract` trades that shrink the pool, as in `SameTokenNameCloseNotPreciseEnough2`/`SameTokenNameOpenNotPreciseEnough2` tests).
2. Call `ExchangeWithdrawActuator` with a `tokenQuant` of `1`, observing rejection with `"withdraw another token quant must greater than zero"` (integer division rounds to 0) as shown at [4](#0-3) .
3. Try incrementally larger `tokenQuant` values; observe that many still fail with `"Not precise enough"` due to the relative-tolerance check at [5](#0-4) , until the exact remaining balance is withdrawn, demonstrating that partial exits from a shrunk pool can be systematically blocked.
