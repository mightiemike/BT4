### Title
Unbounded growth of `DelegatedResourceAccountIndex` to/from-account lists enables RPC/actuator DoS - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
The legacy (v1) resource-delegation bookkeeping stores every delegator/delegatee relationship for an account inside a single `DelegatedResourceAccountIndex` protobuf record, in two repeated fields (`to_accounts` / `from_accounts`) that are appended to with no upper bound, analogous to the unbounded `MAX_DELEGATES` array in the reported VotingEscrow bug. Any account can be added as a new delegatee/delegator on every `FreezeBalance` call, so an attacker can grow one account's index list arbitrarily large at negligible cost, which is then fully loaded, iterated, and rewritten by later actuator/store/RPC code paths.

### Finding Description
`DelegatedResourceAccountIndexCapsule` exposes `addToAccount`/`addFromAccount`, which unconditionally append a new `ByteString` to the `to_accounts`/`from_accounts` repeated fields with no size limit: [1](#0-0) 

This capsule is read, mutated, and rewritten as a whole (`get`/`put`) by `FreezeBalanceActuator` whenever a delegation is created in the pre-optimization (v1) model, so every unique delegatee address appended by the owner grows the single stored value linearly, as confirmed by the existing regression test that appends 100+ distinct delegatee addresses to one owner's index without any validation rejecting the size: [2](#0-1) 

The same unbounded list is later fully materialized and iterated in `DelegatedResourceAccountIndexStore.convert()`, which loops over every entry in `toList`/`fromList` to migrate v1 records into the v2 prefix-keyed model: [3](#0-2) 

It is also served in full over unauthenticated node RPC via `Wallet.getDelegatedResourceAccountIndex`/`getV2Index`-style APIs and the `getWithPrefix` query path, which loads, sorts, and streams every recorded from/to relationship for a queried address: [4](#0-3) 

Because there is no cap analogous to `MAX_DELEGATES`, an attacker who controls (or Sybil-creates) an owner account can repeatedly call `FreezeBalance` with distinct new receiver addresses to inflate this single record indefinitely. Subsequent operations that must load/rewrite or fully iterate this record (further freezes/unfreezes from the same owner, the v1→v2 `convert()` migration triggered during unfreeze/withdrawal flows, and the `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` RPC/HTTP endpoints) incur cost that scales with the attacker-controlled list size, each of which the protobuf serialization/deserialization and full-list rewrite make increasingly expensive as the list grows.

### Impact Explanation
This mirrors the reported bug class: an unbounded, attacker-growable array embedded in a single on-chain record that must be fully processed by core state-transition logic and public read APIs. Left unbounded, it can degrade or fail block validation/RPC serving for the affected account (denial of service on the actuator execution path and on the `getDelegatedResourceAccountIndex(V2)` RPC/HTTP endpoints), and in the worst case blocks the victim's own further freeze/unfreeze operations that must load and rewrite the bloated record, causing a form of self-inflicted or attacker-inflicted resource lock analogous to the reported NFT-lock DoS.

### Likelihood Explanation
Growing the list only requires repeatedly calling `FreezeBalance`/legacy delegate contract with new receiver addresses (cost is limited to normal freeze fees/bandwidth, no protocol-level cap enforced on the number of distinct delegatees an owner may accumulate). This is reachable by any account via a standard broadcast transaction, requiring no privileged access, making the likelihood non-trivial for any account willing to spend ordinary transaction fees over time.

### Recommendation
Introduce and enforce a maximum size (e.g., a `MAX_DELEGATE_ACCOUNTS` constant) for `to_accounts`/`from_accounts` in `DelegatedResourceAccountIndexCapsule`, validated in `FreezeBalanceActuator`/`DelegateResourceActuator` before appending new entries, and consider migrating fully off the v1 aggregate-list model (the v2 prefix-keyed `delegate()`/`unDelegate()` scheme in `DelegatedResourceAccountIndexStore` already avoids this pattern) to prevent unbounded single-record growth.

### Proof of Concept
1. Create account `A` with sufficient balance to pay minimal freeze amounts.
2. From `A`, repeatedly submit `FreezeBalanceContract` transactions delegating tiny amounts of bandwidth/energy to N distinct, freshly generated receiver addresses (as done programmatically in the existing test loop) — no protocol check rejects this growth: [2](#0-1) 
3. Observe that `A`'s `DelegatedResourceAccountIndex` record (queried via `getDelegatedResourceAccountIndex`) grows linearly and unboundedly with N.
4. Query the RPC/HTTP endpoint for `A`'s delegated resource index and observe increasing response size/latency, and/or trigger `convert()`/further freeze-unfreeze operations from `A` and observe increasing per-call cost as N grows, demonstrating the DoS vector.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

    }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
