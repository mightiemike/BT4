Based on my research, I found a direct architectural analog of the Gearbox `PoolService.transferFrom`/USDT fee-on-transfer bug in Push Chain's inbound-minting pipeline.

### Title
Inbound PRC20 minting trusts the gross gateway/vault event `amount` instead of the actual vault balance delta, allowing over-minting against fee-on-transfer or deflationary source-chain tokens - (File: `x/uexecutor/keeper/handler.go`)

### Summary
The Gearbox bug minted Diesel tokens using the caller-specified `amount` parameter of `transferFrom` instead of the actual balance increase, so fee-on-transfer tokens (like USDT with fees enabled) let the pool under-collateralize its minted shares. Push Chain has the same shape of bug in its cross-chain deposit pipeline: the amount minted as PRC20 on Push Chain is taken verbatim from the source-chain `sendFunds` event log, never cross-checked against the vault contract's actual received balance.

### Finding Description
When a user deposits an ERC20 into the source-chain vault, the Universal Client's EVM event parser extracts the bridged amount directly from event log data (Word 1) with no reference to actual token balance change: [1](#0-0) 

This value flows unmodified into the `Inbound.Amount` field constructed for on-chain voting: [2](#0-1) 

Once quorum is reached, `x/uexecutor` deposits PRC20 tokens using exactly that reported `Amount`, with no secondary validation against a vault-balance delta observed on the source chain: [3](#0-2) 

The value is then passed straight through to `CallPRC20Deposit`, which calls `depositPRC20Token` on `UniversalCore` to mint the PRC20 representation: [4](#0-3) 

Nowhere in this path — event parsing, `constructInbound`, `depositPRC20`, or `CallPRC20Deposit` — is the emitted `amount` reconciled against an actual balance-before/balance-after check on the vault holding the real asset. If the source-chain vault's `sendFunds` implementation calls `transferFrom(user, vault, amount)` on a fee-on-transfer, rebasing, or deflationary ERC20 (any token registered via `uregistry` `TokenConfig`), the vault ends up holding strictly less than `amount`, but Push Chain still mints the full `amount` of PRC20 against it — an unbacked/over-minted synthetic asset, exactly mirroring the Gearbox `PoolService` defect.

### Impact Explanation
Over-minting PRC20 against insufficient real collateral held by the TSS-controlled vault directly corrupts PRC20/native asset accounting invariants. Every subsequent user who redeems/burns PRC20 for the underlying asset via outbound withdrawal draws from a vault that is short by the accumulated fee leakage, ultimately causing legitimate users to be unable to withdraw (funds are permanently short) — a protocol-fund-drain/permanent-loss class impact squarely within the allowed impact gate ("corruption of PRC20 or native asset accounting ... unauthorized mint").

### Likelihood Explanation
Exploitability is gated entirely by whether any token registered in `uregistry.TokenConfig` for a given `sourceChain`/`assetAddr` has fee-on-transfer, deflationary, or rebasing semantics. If any such token is ever onboarded (a routine registry/governance action, not a privileged attack), any unprivileged user who calls `sendFunds` with that asset immediately triggers over-minting on every single deposit — no colluding validators, no chain compromise, and no privileged actor needed on the Push Chain side.

### Recommendation
Do not trust the gross `amount` emitted in the gateway/vault event as the mint quantity. Either (a) have the source-chain vault contract measure and emit the actual balance delta (`balanceAfter - balanceBefore`) at the time of `transferFrom`, mirroring the Gearbox fix, and have Universal Validators/`x/uexecutor` mint that value instead of the caller-declared `amount`, or (b) explicitly disallow onboarding any token whose contract can apply a transfer fee/rebase (enforce this at `TokenConfig` registration time with a hard compatibility check), and add a reconciliation step in `depositPRC20`/`ExecuteInboundFunds` that fails/reverts the inbound if the reported amount cannot be corroborated against an observed vault balance-delta.

### Proof of Concept
1. Registry onboards a `TokenConfig` for `sourceChain=eip155:X`, `assetAddr=<FeeOnTransferToken>` with a `NativeRepresentation` PRC20.
2. Attacker (unprivileged user) calls the source-chain gateway's `sendFunds` with `amount = 1,000,000` of `FeeOnTransferToken`, which internally does `transferFrom(attacker, vault, 1,000,000)` but only `950,000` lands in the vault due to a 5% transfer fee.
3. The vault contract still emits `bridgeAmount = 1,000,000` in its `sendFunds` event (per `event_parser.go` Word-1 parsing shown above).
4. Universal Validators vote in the `Inbound` carrying `Amount = "1000000"`; `x/uexecutor.ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints `1,000,000` PRC20 to the recipient, while the vault only actually holds `950,000` of the underlying token.
5. Repeating this drains the collateral ratio further with every deposit; eventually legitimate PRC20 holders cannot redeem the full backing amount via outbound withdrawal, since the vault is short by the accumulated fee leakage.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
