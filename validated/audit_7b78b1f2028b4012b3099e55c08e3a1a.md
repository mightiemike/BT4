### Title
Method-ID upgrade authority binding broken across networks by identical `chain_id` and identical council pubkeys - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the same value (5665), and the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` constants for these two networks are also byte-for-byte identical [1](#0-0) . Consequently a security-council-signed `BatchProofMethodIdBody` inscribed on Nightly's DA stream can be re-inscribed verbatim on TestNetworkWithForks and will pass every check in `run_l1_block` (activation-height check, chain-id check, and `verify_method_id_security_council`), because the signature message and the verifying keys are the same on both networks.

### Finding Description
The intended binding is: `body.chain_id` uniquely identifies the network the council authorized the method-id upgrade for, i.e. `body.chain_id == citrea_network_to_chain_id(network)` should hold only for the one network the signers actually intended. In `run_l1_block`'s `DataOnDa::BatchProofMethodId` branch [2](#0-1) , the guard sequence is:
1. `activation_l2_height > last_activation_height` (per-network JMT state, independent check),
2. `citrea_network_to_chain_id(network) == body.chain_id`,
3. `verify_method_id_security_council(pubkeys, body.serialize(), signatures)`.

Because `citrea_network_to_chain_id(Nightly) == citrea_network_to_chain_id(TestNetworkWithForks) == 5665` [1](#0-0) , check (2) does not distinguish the two networks. Additionally, `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` uses the exact same default hex-encoded public keys as `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` [3](#0-2) , so check (3) — `verify_method_id_security_council`, which EIP-191-hashes `body.serialize()` and verifies against the constant pubkeys [4](#0-3)  — will also succeed identically for the replayed bytes on either network.

Attack flow: attacker observes the publicly-inscribed, council-signed `BatchProofMethodIdBody{method_id, activation_l2_height, chain_id: 5665}` + 3 signatures on Nightly's Bitcoin DA. Attacker copies these exact bytes into a new inscription on the TestNetworkWithForks chain (any unprivileged party can inscribe/broadcast a Bitcoin transaction). When a TestNetworkWithForks light-client-prover node processes this DA blob via `run_l1_block`, provided its `last_activation_height` is lower than `activation_l2_height` in the copied body, all three checks pass and `BatchProofMethodIdAccessor::insert` commits the method ID into TestNetworkWithForks's JMT state [5](#0-4) .

### Impact Explanation
If exploited on a network deployment that matters, this allows a method-id upgrade to be applied on a chain the council never separately authorized for that chain, changing which RISC0/SP1 guest program is trusted to verify batch proofs on that network without a fresh council decision — a "method-id upgrade accepted that was never authorised" scenario, which the audit brief classifies Critical. However, `TestNetworkWithForks` is explicitly documented as "All forks from genesis to Nightly. This is used for testing purposes only" [6](#0-5) , and its fork configuration (`ALL_FORKS`, with forks landing at heights 100/200/210/220) marks it as an internal test harness network rather than a real public value-bearing deployment [7](#0-6) . I was unable to find evidence in the indexed code that TestNetworkWithForks is ever run as a live, publicly-reachable, bridge-connected deployment; it appears used only in local fork-transition tests (`bin/citrea/tests/bitcoin/fork.rs`, `batch_prover_test.rs`). No cBTC minting, withdrawal, or state-root divergence between honest nodes is caused directly by this cross-mapping — both Nightly and TestNetworkWithForks are separate, non-interacting deployments (separate JMT states, separate genesis roots, separate DA public keys for prover/sequencer), so no funds move and no honest nodes on a single logical network diverge.

### Likelihood Explanation
The precondition that both constants collide is real and present in code today, but requires that TestNetworkWithForks actually be run as a standing node whose light-client-prover ingests DA blobs from wherever Nightly's inscriptions are also visible (in practice, distinct regtest/DA environments per network, so cross-network blob visibility is itself operationally unlikely). Given TestNetworkWithForks is a testing-only network per its own doc-comment and fork table, this is a naming/config hygiene defect rather than a demonstrable path to unauthorized state change on a value-bearing deployment.

### Recommendation
Assign a distinct `chain_id` to `TestNetworkWithForks` (and ideally distinct method-id-upgrade-authority keys, as already done via distinct env var defaults would fix if actually differentiated) so `citrea_network_to_chain_id` is injective across all `Network` variants.

```rust
// crates/light-client-prover/src/circuit/method_id_verifier.rs (illustrative)
#[test]
fn chain_id_collision_and_cross_network_replay() {
    use sov_rollup_interface::Network;
    assert_eq!(
        citrea_network_to_chain_id(Network::Nightly),
        citrea_network_to_chain_id(Network::TestNetworkWithForks)
    ); // 5665 == 5665, binding broken

    let body = BatchProofMethodIdBody {
        method_id: [0u32; 8],
        activation_l2_height: 100,
        chain_id: citrea_network_to_chain_id(Network::Nightly),
    };
    let msg = body.serialize();
    let prehash = eip191_hash_message(msg.as_slice());
    let (_, signers) = generate_initial_pub_keys_with_signers();
    let sigs = create_valid_signatures(&signers, &prehash);

    // Same pubkeys constant used for both networks in initial_values.rs
    let nightly_pubkeys = bitcoinda::NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS;
    let test_pubkeys = bitcoinda::TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS;

    assert!(verify_method_id_security_council(nightly_pubkeys, msg.as_slice(), &sigs));
    assert!(verify_method_id_security_council(test_pubkeys, msg.as_slice(), &sigs)); // passes identically
}
```
This proves the equality collision and identical-signature-acceptance across both `Network` values, but does not by itself demonstrate cross-network DA blob delivery or a live TestNetworkWithForks deployment reachable by an unprivileged attacker with bridge-connected value, which the audit scope requires for Critical impact — that operational precondition could not be confirmed from the indexed repository contents.

```rust
pub fn verify_method_id_security_council(
    initial_da_pubkeys: [[u8; SECURITY_COUNCIL_COMPRESSED_PUBKEY_SIZE];
        SECURITY_COUNCIL_MEMBER_COUNT],
    msg: &[u8],
    signatures_with_idx: &[([u8; SECURITY_COUNCIL_SIGNATURE_SIZE], u8);
         SECURITY_COUNCIL_SIGNATURE_THRESHOLD],
) -> bool {
    // EIP-191 prefix + keccak256 → 32-byte prehash
    let prehash = eip191_hash_message(msg);

    // Check that signature indices are within bounds
    for &(_, index) in signatures_with_idx {
        if index >= 5 {
            log!("Invalid signature index: {}", index);
            return false;
        }
    }

    // Make sure the indexes are in ascending order to prevent duplicates
    for i in 0..signatures_with_idx.len() - 1 {
        if signatures_with_idx[i].1 >= signatures_with_idx[i + 1].1 {
            log!(
                "Signature indices are not in ascending order, failing indices: {}, {}",
                signatures_with_idx[i].1,
                signatures_with_idx[i + 1].1
            );
            return false;
        }
    }

    for signature_with_idx in signatures_with_idx.iter() {
        let signature = signature_with_idx.0;
        let pubkey_idx = signature_with_idx.1;
        let const_pubkey = initial_da_pubkeys[pubkey_idx as usize];

        // ensure the inscription pubkey matches the expected constant (compressed 33B)
        let verifying_key = VerifyingKey::from_sec1_bytes(const_pubkey.as_slice())
            .expect("Initial DA pubkeys must be parsable to k256 VerifyingKey form sec1 bytes");

        let Ok(parsed_sig) = Signature::from_bytes(&signature.into()) else {
            log!("Invalid signature format");
            return false; // invalid signature format, fail
        };

        // verify prehash with the matching verifying key
        if verifying_key
            .verify_prehash(prehash.as_slice(), &parsed_sig)
            .is_err()
        {
            log!("Signature verification failed for index: {}", pubkey_idx);
            return false;
        }
    }

    true
}
```
