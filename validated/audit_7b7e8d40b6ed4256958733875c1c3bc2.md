### Title
Unbounded native recursion in Sierra→CASM `bytecode_segment_lengths` hashing/tree-building allows stack-exhaustion DoS via Declare transaction - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
The Panda3D report describes an unvalidated, attacker-controlled quantity (`argc`) driving an unbounded native stack allocation (`alloca`), causing stack exhaustion and undefined behavior. The closest reachable analog in this sequencer is unbounded *native Rust recursion* (not heap-simulated Cairo VM recursion) over the `bytecode_segment_lengths` tree of a declared class's compiled CASM, whose nesting depth is derived from the structure of a user-submitted Sierra program and is not depth-checked before recursive processing.

### Finding Description
`bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recursively walks a `NestedIntList`/`HashableNestedIntList` tree to compute the compiled-class bytecode hash: [1](#0-0) 

The recursion depth is bounded only by the depth of `node.iter_children()`, i.e., the nesting depth of `bytecode_segment_lengths`, which is a field carried on `CasmContractClass` (`self.bytecode_segment_lengths`): [2](#0-1) 

A structurally identical, equally unbounded native recursion exists in `create_bytecode_segment_structure_inner`, used by the Starknet OS hint processing when building the bytecode segment tree for re-execution/proving: [3](#0-2) 

Unlike Cairo contract-call recursion, which is explicitly rate-limited by `RecursionDepthGuard`/`max_recursion_depth` in the blockifier's entry-point execution: [4](#0-3) 

...there is no equivalent depth guard for this native-code recursion that walks the compiled class's own segment-length structure. This is the same bug class as the Panda3D issue: an attacker-influenced quantity (here, Sierra program structure depth, submitted via a Declare transaction from an unprivileged declarer) directly drives unbounded native stack consumption with no validation of depth before recursing.

### Impact Explanation
If an attacker can submit (or otherwise get compiled) a Sierra program whose compiled CASM produces a `bytecode_segment_lengths` tree with sufficiently deep nesting, computing the compiled class hash (`bytecode_hash`/`hash_inner`) or building the bytecode segment structure (`create_bytecode_segment_structure`) would recurse natively far enough to exhaust the OS thread stack, crashing the sequencer process (or the Starknet OS re-execution/proving process) with a segmentation fault / abort — a denial-of-service. Because this hashing happens deterministically from declared-class data, and the OS-side function is invoked during block re-execution/proving, a crash here could also cause honest-node divergence if only some nodes hit the stack limit (e.g., different thread stack sizes across sequencer/prover machines) — though this is a real availability/soundness risk rather than a direct funds-loss bug, capping impact at denial-of-service/crash severity.

### Likelihood Explanation
Reachability requires only a Declare transaction (class declarer) whose Sierra program compiles into deeply nested branch/function structures, which is generally within an untrusted user's control given they choose the Sierra program contents. Whether current gateway/compiler-side limits (max contract bytecode size, Sierra program size limits, compilation resource limits) sufficiently bound the resulting *nesting depth* of `bytecode_segment_lengths` (as opposed to total size) could not be fully confirmed from the code reachable in this session — the actual generation of `bytecode_segment_lengths` happens inside the `cairo-lang-starknet-classes` compiler dependency, which was not available to inspect here. This is the main source of uncertainty for likelihood.

### Recommendation
Add an explicit recursion-depth bound (mirroring the existing `RecursionDepthGuard` pattern used for Cairo contract-call recursion) to `bytecode_hash_node` and `create_bytecode_segment_structure_inner`, returning a hard error instead of recursing when a configured maximum nesting depth is exceeded. Alternatively, convert both functions to explicit iterative/worklist-based traversal (using a heap-allocated stack) to remove the dependency on native call-stack depth entirely.

### Proof of Concept
Not independently verified: could not confirm in this session whether the Sierra-to-CASM compiler (external dependency `cairo-lang-starknet-classes`) permits generating `bytecode_segment_lengths` trees with attacker-controllable, effectively unbounded nesting depth from a single declared Sierra class within existing gateway/versioned-constants size limits. A concrete PoC would require crafting (or compiling) a Sierra program with maximal function/branch nesting and confirming the resulting CASM's `bytecode_segment_lengths` nesting depth is large enough to overflow the executing thread's stack when `bytecode_hash`/`create_bytecode_segment_structure` is invoked — this step requires running the actual Sierra compiler and was not verifiable via static code search alone.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
