### Title
Reachable `Option::expect()` panic in Secp256k1/Secp256r1 add/mul syscalls before segment initialization - ([File: crates/blockifier/src/execution/syscalls/syscall_executor.rs])

### Summary
The `secp256k1_add`, `secp256k1_mul`, `secp256r1_add`, and `secp256r1_mul` default trait methods in `SyscallExecutor` unwrap an `Option<Relocatable>` with `.expect("Secp segment must be set.")` before ever validating the syscall's point pointers. This `Option` is only populated by a prior `secp256k1_new`/`secp256r1_new`/`secp256k1_get_point_from_x`/`secp256r1_get_point_from_x` call in the same execution context. A contract can invoke `secp256k1_add_syscall`/`secp256k1_mul_syscall`/`secp256r1_add_syscall`/`secp256r1_mul_syscall` directly, as the very first secp-related syscall in its execution, causing the `Option` to still be `None` and triggering the `.expect()` panic — analogous to a null/unset-value dereference triggered by a crafted (attacker-controlled) input sequence, similar in bug-class to CVE-2021-3514.

### Finding Description
`SyscallHintProcessor::new` (and the analogous `SnosHintProcessor`/OS hint processor state) initializes `secp_points_segment_base: None` [1](#0-0) . The segment is only set to `Some(..)` as a side effect inside `SecpHintProcessor::allocate_point`, which is only reached from `secp_new`/`secp_get_point_from_x` [2](#0-1) .

However, the default implementations of `secp256k1_add`, `secp256k1_mul`, `secp256r1_add`, and `secp256r1_mul` in the `SyscallExecutor` trait fetch the `Option<Relocatable>` and immediately call `.expect("Secp segment must be set.")` on it, *before* delegating to `SecpHintProcessor::secp_add`/`secp_mul` (which would otherwise fail gracefully via `get_point_by_ptr`'s `Result`-based error handling for invalid pointers): [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Because there is no dispatcher-level ordering enforced (a contract can invoke `secp256k1_add_syscall` or `secp256k1_mul_syscall` as the first Secp-related syscall in a Cairo entry point without first calling `secp256k1_new_syscall`/`secp256k1_get_point_from_x_syscall`), `optional_secp_segment_base` remains `None`, and the `.expect()` call panics inside the syscall executor. This is a Rust panic reachable purely from Cairo contract bytecode driven by calldata supplied in a transaction (invoke, or a constructor/entry point reached via deploy), i.e. controllable by any unprivileged transaction sender or contract deployer.

### Impact Explanation
An unwind/panic inside `execute_next_syscall` (invoked from `HintProcessorLogic::execute_hint`, [7](#0-6) ) propagates up through the Cairo VM run. I could not confirm within the available tool budget that every execution path (gateway `add_tx`/`StatefulTransactionValidator`, sequential block-building, Starknet OS re-execution) wraps VM execution in `catch_unwind`; the only `catch_unwind` usage found in the blockifier crate is in the concurrent block-building worker pool (`crates/blockifier/src/concurrency/worker_pool.rs`), which suggests panics from transaction execution are an anticipated risk that is only mitigated in that specific concurrency path. If the gateway's stateful validation, sequential block building, or the Starknet OS's re-execution path lacks equivalent panic isolation, this bug could crash the executing thread/process, denying transaction validation or block production (a network-availability / DoS-class impact), which the report's rules allow under "a network unable to confirm new transactions." I was not able to conclusively verify whether this uncaught panic escalates to full sequencer-process termination versus a caught, isolated failure — this is the primary source of uncertainty in this finding.

### Likelihood Explanation
The trigger requires no privileged access: any account that can submit an INVOKE transaction, or any contract that gets called (directly or via `call_contract`), can execute a single instruction sequence — `secp256k1_add_syscall` (or the mul/r1 variants) as the first Secp-related call — to hit this code path deterministically. No prior state setup, special permissions, or race condition is needed.

### Recommendation
Replace the `.expect("Secp segment must be set.")` calls in `secp256k1_add`, `secp256k1_mul`, `secp256r1_add`, and `secp256r1_mul` with either: (1) lazily allocating the segment inline (mirroring the `if points_segment_base.is_none() { *points_segment_base = Some(vm.add_memory_segment()); }` pattern already used in `SecpHintProcessor::allocate_point`), or (2) returning a proper `SyscallExecutorBaseError`/`Result` when the segment is unset, instead of panicking. Additionally, audit all `.expect()`/`.unwrap()` calls in the syscall executor trait (`crates/blockifier/src/execution/syscalls/syscall_executor.rs`) reachable from contract-controlled syscall invocation order, per the repository's own code-style guideline "Never panic on data reachable from requests" [8](#0-7) .

### Proof of Concept
Deploy a Cairo 1 contract entry point that calls `secp256k1_add_syscall(p0, p1)` (or `secp256k1_mul_syscall`, `secp256r1_add_syscall`, `secp256r1_mul_syscall`) as its very first Secp-related syscall, with `p0`/`p1` being arbitrary `Secp256Point` values (they need not correspond to previously-created points, since the panic occurs before point validation). Existing test helpers in the feature-contract test fixtures always call `secp256k1_new_syscall` first [9](#0-8) , so a minimal new test contract/entry point that omits the `new`/`get_point_from_x` call and calls `add`/`mul` directly, invoked via a standard INVOKE transaction, would reach `optional_secp_segment_base.expect("Secp segment must be set.")` with `None`, causing a Rust panic during execution.

```rust
    fn execute_hint(
        &mut self,
        vm: &mut VirtualMachine,
        exec_scopes: &mut ExecutionScopes,
        hint_data: &Box<dyn Any>,
    ) -> HintExecutionResult {
        let hint = hint_data.downcast_ref::<Hint>().ok_or(HintError::WrongHintData)?;
        // Segment arena finalization is relevant only for proof so there is no need to allocate
        // memory segments for it in the sequencer.
        let no_temporary_segments = true;
        match hint {
            Hint::Core(hint) => {
                execute_core_hint_base(vm, exec_scopes, hint, no_temporary_segments)
            }
            Hint::Starknet(hint) => Ok(execute_next_syscall(self, vm, hint)?),
            Hint::External(_) => {
                panic!("starknet should never accept classes with external hints!")
            }
        }
    }
```

```rust
    pub fn secp_new(
        &mut self,
        vm: &mut VirtualMachine,
        request: SecpNewRequest,
        points_segment_base: &mut Option<Relocatable>,
        id: usize,
    ) -> SyscallBaseResult<SecpNewResponse> {
        let affine = new_affine::<Curve>(request.x, request.y)?;
        let optional_ec_point_ptr = match affine
            .map(|ec_point| self.allocate_point(ec_point, vm, points_segment_base, id))
        {
            Some(Ok(ptr)) => Some(ptr),
            Some(Err(err)) => return Err(err),
            None => None,
        };
        Ok(SecpNewResponse { optional_ec_point_ptr })
    }

    fn allocate_point(
        &mut self,
        ec_point: short_weierstrass::Affine<Curve>,
        vm: &mut VirtualMachine,
        points_segment_base: &mut Option<Relocatable>,
        id: usize,
    ) -> SyscallBaseResult<Relocatable> {
        if points_segment_base.is_none() {
            *points_segment_base = Some(vm.add_memory_segment());
        }
        let point_address = (points_segment_base.expect("Points segment base must be set.")
            + EC_POINT_SEGMENT_SIZE * id)?;
        self.points.insert(point_address, ec_point);
        Ok(point_address)
    }
```

```markdown
### Never panic on data reachable from requests
- Code reachable from HTTP handlers or external input must never use `.unwrap()`, `.expect()`, or unchecked indexing on values derived from that input
- Reserve panics for compile-time invariants where failure is a programmer bug, not a runtime possibility
- Return `Result` with a descriptive error variant, or use saturating/capping alternatives
```
