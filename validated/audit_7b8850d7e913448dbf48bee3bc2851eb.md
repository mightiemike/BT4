### Title
Unbounded request body size in WebAuthn FinishRegistration allows authenticated-user resource-exhaustion DoS - (File: core/web/webauthn_controller.go, core/sessions/webauthn.go)

### Summary
`WebAuthnController.FinishRegistration` passes the raw `*http.Request` (via `c.Request`) directly into `WebAuthnSessionStore.FinishWebAuthnRegistration`, which forwards it unmodified to `webAuthn.FinishRegistration(waUser, sessionData, response)` in the third-party `go-webauthn` library. [1](#0-0) [2](#0-1)  No `http.MaxBytesReader` or equivalent size cap is applied to `c.Request.Body` anywhere in this handler chain before the body is parsed.

### Finding Description
`FinishRegistration` first authenticates the caller via `auth.GetAuthenticatedUser(c)`, so this path requires a valid session (any role), consistent with the stated precondition. [3](#0-2)  After that check, the handler calls `w.inProgressRegistrationsStore.FinishWebAuthnRegistration(*user, uwas, c.Request, webAuthnConfig)`, handing the entire unbounded `http.Request` (including its `Body io.ReadCloser`) into the library call. [4](#0-3)  Inside `webauthn.go`, `FinishWebAuthnRegistration` does not wrap or limit `response.Body` before calling `webAuthn.FinishRegistration(waUser, sessionData, response)` — the go-webauthn library itself reads and JSON-decodes the request body internally. [5](#0-4) 

I searched the repository for `http.MaxBytesReader`/`LimitReader` usage and found none applied to the general web/API router or the WebAuthn routes — the matches that exist are all in unrelated services (gateway network servers, vault JWT auth, external adapter client), not in `core/web` request handling. This confirms no explicit per-request body size limit is enforced ahead of `FinishRegistration`. I could not fully verify whether `core/cmd/shell.go`'s `http.Server` configuration sets a global `ReadTimeout`/`ReadHeaderTimeout` (grep found matches there but I was unable to inspect the exact values before running out of iterations); if such timeouts exist, they would mitigate a slow-drip/"slowloris"-style hang but would **not** limit the total bytes a client can upload within the timeout window, so a large (not necessarily slow) POST body to `FinishRegistration` could still drive up per-request memory/CPU usage during JSON parsing of the WebAuthn attestation response.

### Impact Explanation
Because the caller must already hold an authenticated session, this is not an unauthenticated, internet-wide DoS vector — it is a self-inflicted or malicious-authenticated-user resource-exhaustion issue scoped to the calling goroutine/connection. Repeated large-body requests from one or more authenticated users could still increase memory pressure and CPU time in the JSON/CBOR parsing path used by go-webauthn, potentially degrading availability of the API server for other users, but it does not achieve auth bypass, privilege escalation, secret disclosure, or transaction/workflow tampering.

### Likelihood Explanation
Exploitability requires only a valid session of any role and a completed `BeginRegistration` call to seed session state, both of which are readily achievable by any legitimate authenticated user. The main uncertainty is whether existing HTTP-server-level timeouts (in `core/cmd/shell.go`, unverified in this pass) already bound total request duration, which would reduce — but not eliminate — the size-based (as opposed to slow-drip) portion of this issue.

### Recommendation
Wrap `c.Request.Body` with `http.MaxBytesReader(c.Writer, c.Request.Body, <reasonable limit, e.g. 64KB>)` in `WebAuthnController.FinishRegistration` before invoking `FinishWebAuthnRegistration`, since legitimate WebAuthn attestation responses are small. Additionally confirm/add `ReadTimeout`/`ReadHeaderTimeout` on the underlying `http.Server` to bound slow-drip uploads globally.

### Proof of Concept
Integration test: authenticate a session, call `BeginRegistration` to seed `inProgressRegistrationsStore`, then POST to `FinishRegistration` with a body streamed slowly (e.g. 1 byte per second) or an extremely large (multi-GB) body. Assert that the server either rejects the request quickly with `413 Request Entity Too Large` / times out promptly, rather than allowing the handler goroutine to block indefinitely or allocate unbounded memory while `webAuthn.FinishRegistration` parses the body.

func (store *WebAuthnSessionStore) FinishWebAuthnRegistration(user User, uwas []WebAuthn, response *http.Request, config WebAuthnConfiguration) (*webauthn.Credential, error) {
	webAuthn, err := webauthn.New(&webauthn.Config{
		RPDisplayName: "Chainlink Operator", // Display Name
		RPID:          config.RPID,          // Generally the domain name
		RPOrigin:      config.RPOrigin,      // The origin URL for WebAuthn requests
	})
	if err != nil {
		return nil, err
	}

	userRegistrationIndexKey := user.Email + "-registration"
	sessionData, err := store.GetWebauthnSession(userRegistrationIndexKey)
	if err != nil {
		return nil, err
	}

	waUser, err := duoWebAuthUserFromUser(user, uwas)
	if err != nil {
		return nil, err
	}

	credential, err := webAuthn.FinishRegistration(waUser, sessionData, response)
	if err != nil {
		return nil, pkgerrors.Wrap(err, "failed to FinishRegistration")
	}
