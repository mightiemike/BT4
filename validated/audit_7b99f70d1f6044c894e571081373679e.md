### Title
Stale `last-update` timestamp only advanced on index change causes back-dated interest accrual across pool utilization gaps - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, analogous in `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
`last-update` is the analog of the report's `lastHarvestManagementFeeTime`/`lastHarvestPerformanceFeeTime`: it is the "clock" that bounds the period over which interest/fees accrue. In `accrue()`, this clock is only advanced when the computed index actually changes:
`(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)` [1](#0-0) . When utilization (and thus `interest-rate`) is zero, `next-index`/`next-liquidity-index` return the same value as the current index, so this condition is false and `last-update` is never advanced, exactly like the report's bug where the timestamp anchor is not reset when it should track "actual usage start."

### Finding Description
`next-index` computes the elapsed period as `(- stacks-block-time (var-get last-update))` and applies `interest-rate` (a function of current `utilization`) over that entire period: [2](#0-1) . `interest-rate` itself is derived purely from the current utilization at call time [3](#0-2) .

`accrue()` writes `index`/`lindex` and advances `last-update` only conditionally on those values changing [4](#0-3) . This is a "clock advanced only on change" pattern: while utilization is zero (rate = 0), `next == idx` and `nliq == lidx`, so `last-update` is left untouched at whatever the last true accrual point was — potentially the deployment/initialize timestamp, since `last-update` is a data-var initialized once to `stacks-block-time` at deploy time [5](#0-4) .

Sequence:
1. Vault is deployed and `initialize` is called, which only deposits `MINIMUM-LIQUIDITY` (no borrow) — `last-update` remains at deployment time [6](#0-5) .
2. Time passes with zero utilization (no borrows) — every call to `accrue()` (invoked internally by `system-borrow`, `system-repay`, deposit/redeem paths) computes `next-index`/`next-liquidity-index` equal to the current values because `interest-rate` is 0 at 0% utilization, so the `is-eq` checks are true and `last-update` is never bumped forward [7](#0-6) .
3. A borrow finally occurs via `system-borrow`, which calls `accrue()` before applying the new principal, so this first accrual still sees utilization 0 and again does not move `last-update` [8](#0-7) .
4. On the *next* state-changing call (e.g., another `system-borrow`/`system-repay`), `interest-rate` is now non-zero because utilization is non-zero, and `next-index` is computed using `time-delta = stacks-block-time - last-update`, where `last-update` is still the stale deployment/initialize timestamp from step 1 rather than the time the debt was actually created in step 3.
5. The resulting interest is charged over the entire elapsed wall-clock period since deployment (including the idle, zero-utilization period), not just the actual period during which debt existed — mirroring the H-02 root cause of charging fees for a period funds were not actually deposited/at risk.

### Impact Explanation
This inflates `index`/`lindex` beyond what the actual borrowing period justifies, causing `total-debt` (via `calc-cumulative-debt`) to overstate borrower obligations and `total-assets`/`total-assets-preview` to overstate lender-side value derived from interest that was never actually earned during a period with zero utilization [9](#0-8) . Borrowers are overcharged interest they did not owe for a period when they held no debt, which is theft/overcharging of unclaimed yield-equivalent value from borrowers to the pool/treasury (a portion is minted to `.dao-treasury` via `treasury-lp`) [10](#0-9) . This lands in the High-impact "theft of unclaimed yield" category, since it misappropriates value that should not have accrued to the protocol.

### Likelihood Explanation
This is not a contrived edge case — any pool with an idle period after deployment/initialize (before first borrow) or any pool that returns to zero utilization for a stretch (all debt repaid) before a new borrow will trigger the stale-clock condition, since `interest-rate` is deterministically zero at zero utilization [11](#0-10) . No privileged action or attacker collusion is required — it happens through normal single-actor usage (a single borrower's deposit/borrow/repay/re-borrow lifecycle), consistent with the "single-transaction/single-block analog" scope.

### Recommendation
Unconditionally set `last-update` to `stacks-block-time` on every non-paused `accrue()` call, regardless of whether `index`/`lindex` changed, so the elapsed-period clock always reflects the last time accrual was evaluated rather than the last time it produced a nonzero delta. Alternatively, track the utilization-start timestamp separately, or compute `time-delta` bounded by the period during which any principal actually existed, instead of relying on the value-equality check as a proxy for "no accrual needed."

### Proof of Concept
Conceptual repro (contract-level, single actor, sequential transactions):
1. Deploy `v0-vault-stx` and call `initialize` at `T0` — `last-update = T0`, `principal-scaled = 0`, utilization = 0, so `interest-rate = 0`.
2. Wait a long idle period (e.g., `T0 + 180 days`, no borrows) — any incidental call to `accrue()` in this window leaves `last-update = T0` because `next-index == index` (rate is 0 while `principal-scaled = 0`).
3. At `T1 = T0 + 180 days`, call `system-borrow(amount, receiver)`. Internally this calls `accrue()` first (utilization still 0 pre-borrow) — `last-update` still not advanced — then sets `principal-scaled` to a non-zero value, making utilization/`interest-rate` non-zero going forward.
4. Shortly after, at `T2 = T1 + 1 day`, call `system-repay` or any function invoking `accrue()`. `next-index` now computes `time-delta = T2 - last-update = T2 - T0 ≈ 181 days` using the now non-zero `interest-rate`, instead of the correct `T2 - T1 ≈ 1 day`.
5. The resulting `index`/`lindex` update — and therefore `total-debt`, `interest-paid` in `system-repay`, and the `treasury-lp` minted to `.dao-treasury` — reflect ~181 days of interest accrual for a loan that only existed for ~1 day, overcharging the borrower by roughly 180x the correct interest amount.

Note: I was not able to further verify the exact call graph for `set-points-ir` (interest-rate curve configuration) or confirm whether any other function in the vault unconditionally resets `last-update` outside of `accrue()`, due to the final-iteration constraint on tool calls. This does not affect the core finding, which is fully supported by the `accrue()`/`next-index`/`next-liquidity-index` code shown above, but a full review should double-check all state-changing entry points for any alternate `last-update` reset path.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
