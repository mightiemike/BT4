## Finding

### Title
Backup-derived `write_set` bytes are never checked against the accumulator-proven `TransactionInfo.state_change_hash` during transaction restore - ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
The external report's bug class is "a numeric configuration input is accepted without validating it against the value that is supposed to bound/protect the system, silently disabling the protection." The Aptos-native analog is structural rather than numeric: during transaction-backup restore, the `write_set` for every transaction is read straight from an untrusted backup file and is *never* checked against the corresponding `state_change_hash` field of the `TransactionInfo` that was cryptographically bound to the trusted `LedgerInfo` via the accumulator range proof. Only the transaction and event data are covered by that proof check; the write set — the actual durable ledger state being restored — is not.

### Finding Description
In `LoadedChunk::load` (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs:99-186`), each backup record is deserialized into `(txn, aux_info, txn_info, events, write_set)`, and `write_set` is pushed into a `write_sets: Vec<WriteSet>` collected separately from the fields that are proof-checked: [1](#0-0) 

The code then builds a `TransactionListWithProofV2` out of only `txns`, `event_vecs`, and `txn_infos` (via `TransactionListWithProof`/`TransactionInfoListWithProof`) and calls `.verify(...)`: [2](#0-1) 

`TransactionListWithProof` structurally has no `write_set` field at all — it is a proof over transactions and events only. Its verification path (`TransactionListWithAuxiliaryInfos::verify` → inner `transaction_list_with_proof.verify` → auxiliary-info check) validates transaction hashes, event root hashes, and that the `TransactionInfo`s are proven under the accumulator/ledger info, exactly as shown by the analogous, but distinct, `TransactionOutputListWithProof::verify`, which *does* check the write-set hash against `txn_info.state_change_hash()`: [3](#0-2) 

That check exists for `TransactionOutputListWithProof` but has no counterpart for the `write_sets` vector loaded alongside `TransactionListWithProof` in the backup/restore path. After `LoadedChunk::load` returns, `write_sets` is unpacked and carried forward through `TransactionRestoreBatchController` to be written into the target database for versions that are not being VM-replayed (the common case for historical backup data, contrasted with `replay_from_version`). Because the `TransactionInfo.state_change_hash()` for these versions is the value cryptographically bound to the trusted ledger info (the accumulator leaf hash of the `TransactionInfo`), it is the only reliable anchor that the associated write set is authentic. Skipping the comparison of `CryptoHash::hash(&write_set)` against `txn_info.state_change_hash()` means the write-set bytes taken from the backup storage are trusted purely on the say-so of the file itself.

### Impact Explanation
If the backup storage (an untrusted or compromised `BackupStorage` implementation, corrupted file, or MITM'd transfer) supplies a `write_set` that does not match the `TransactionInfo` proven under the accumulator, a node performing (non-replay) transaction restore will commit that forged write set to its durable ledger state while its transaction/event data still pass the proof check. This is a genuine "committed state differs from the correct VM result / corrupts durable ledger data" outcome as scoped by the state-integrity gate: the restored node's state tree, and any subsequent state proofs it serves, would silently diverge from the authentic historical ledger, even though the restore reports success. This directly matches the pattern in `types/src/transaction/mod.rs` where the analogous output-list function (`TransactionOutputListWithProof::verify`) treats this exact write-set-hash check as mandatory — its absence here is the missing "bounds check" analog.

### Likelihood Explanation
This path is only exercised via `TransactionRestoreController`/`TransactionRestoreBatchController` (used by node bootstrap-from-backup and DB restore tooling), not the online consensus/execution path, so it requires an operator to restore from an untrusted or compromised backup source. I was not able to fully trace, within this session's tool budget, the exact downstream commit call (e.g., inside `ChunkExecutorTrait`/`aptos-db` restore handler) to confirm there is no independent write-set-hash check performed later before the write set is persisted; if such a check exists further downstream, this issue would be mitigated. This uncertainty should be resolved by inspecting `execution/executor/src/chunk_executor` and `storage/aptosdb/src/backup/restore_handler.rs` for any write-set-vs-`state_change_hash` validation.

### Recommendation
Add an explicit check in `LoadedChunk::load` (or immediately before write sets are handed to the restore/commit path) that `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every transaction in the chunk, mirroring the check already present in `TransactionOutputListWithProof::verify` (`types/src/transaction/mod.rs:2976-2984`). This ties the untrusted write-set bytes back to the value that is actually bound by the accumulator/ledger-info proof.

### Proof of Concept
Not independently confirmed end-to-end due to inability to trace the final commit call in this session; the concrete, verifiable gap is that `TransactionListWithProof`/`TransactionListWithProofV2::verify` (used in `LoadedChunk::load`) contains no comparison of `write_sets[i]`'s hash to `txn_infos[i].state_change_hash()`, unlike the parallel `TransactionOutputListWithProof::verify` implementation that performs exactly this check.
