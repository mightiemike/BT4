### Title
Delegated `WithdrawFromGasKey` bypasses the pending-transaction-queue gas-key balance accounting, letting a relayer/attacker sequence gas-key withdrawals that are "guaranteed to apply" without being reflected in admission-time balance checks - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
This is the same bug class as the Perennial-v2 finding: an action whose acceptance is guaranteed once admitted (a `WithdrawFromGasKey` nested inside a `Delegate`/`DelegateV2` meta-transaction) can move balance (from a gas key to an account) while the balance-accounting layer used to gate further admissions (`PendingTxSession`/`PendingTransactionQueue`) only tracks `WithdrawFromGasKey` amounts that appear as **top-level** actions of a transaction, not amounts nested inside a delegate action's inner actions.

### Finding Description
`PendingTxSession::check_pending` and `PendingTransactionQueue::add_chunk_transactions` are the mechanisms that make "pending but not yet certified" balance effects visible to admission-time checks (`verify_and_charge_tx_ephemeral` / `verify_and_charge_gas_key_tx_ephemeral`), exactly analogous to Perennial's collateral/fee accounting used in `InvariantLib` margin checks. Both places scan a transaction's actions for `Action::WithdrawFromGasKey` and add the withdrawn amount to `paid_from_gas_key`/`gas_key_costs`: [1](#0-0) [2](#0-1) 

This scan only iterates `tx.transaction.actions()` — the outer transaction's action list. A `WithdrawFromGasKey` action carried **inside** a `Delegate`/`DelegateV2` action's `actions: Vec<NonDelegateAction>` is never visited by this loop, so its effect on the gas key's balance is invisible to `paid_from_gas_key`/pending accounting, even though (before the mitigating protocol feature) the action is "guaranteed to execute" once the outer delegate meta-transaction is admitted and forwarded to the target shard — the same "guaranteed execution, unaccounted pending effect" pattern as Perennial's `Intent` orders.

The project's own regression test documents this exact hole and that it is protocol-version-gated, not universally fixed: [3](#0-2) [4](#0-3) 

The test explicitly asserts `old_protocol >= MIN_SUPPORTED_PROTOCOL_VERSION` with the comment "no supported protocol version still admits a delegated `WithdrawFromGasKey`, so there is nothing left to test here — remove this test." As long as that assertion holds (which it does, since the test still exists and did not fail), there exists a **currently supported** protocol version where a delegated `WithdrawFromGasKey` is admitted and drains the gas key, while the pending-transaction-queue accounting used for RPC/chunk-production admission does not track it (since the scan only looks at outer actions).

### Impact Explanation
On any node still running/replaying blocks at a supported pre-`RejectWithdrawFromGasKeyInDelegate` protocol version, an attacker can:
1. Fund a gas key.
2. Submit multiple `Delegate`/`DelegateV2` meta-transactions, each nesting a `WithdrawFromGasKey` action that drains the gas key to the account balance.
3. Because `PendingTxSession`/`PendingTransactionQueue` never scans nested delegate actions for `WithdrawFromGasKey`, `paid_from_gas_key` under-counts the true committed withdrawals across multiple in-flight (included-but-uncertified) transactions within the same block-production window.
4. This allows admission of additional gas-key transactions that should have been rejected with `NotEnoughGasKeyBalance`, or allows the account-balance side (`WithdrawFromGasKey` credits `account.amount()`) to be spent again before the gas-key balance is correctly reflected — mirroring the Perennial case where fees committed later create a state where more value was extracted than the ledger accounted for at admission time. This is a state-transition/fee-accounting bypass in the balance-checking invariant, potentially producing balance/gas-key mismatches or double-spend windows across pending chunks.

### Likelihood Explanation
This requires no special privileges beyond a normal transaction signer with a funded gas key and access to a relayer to submit `Delegate`/`DelegateV2` actions — well within the "unprivileged transaction signer / meta-transaction sender" threat model. It is a real, previously-shipped protocol behavior (not merely a hypothetical), evidenced by the existence of a dedicated protocol feature and regression test whose own comments confirm the vulnerable behavior is still admitted on at least one currently supported protocol version. The remaining uncertainty is whether `MIN_SUPPORTED_PROTOCOL_VERSION` in this exact build has already been bumped past the fix version — I could not fully confirm the numeric values of `RejectWithdrawFromGasKeyInDelegate`'s activation version versus `MIN_SUPPORTED_PROTOCOL_VERSION` from the truncated search results, so likelihood should be validated against the concrete version constants in `core/primitives-core/src/version.rs` before treating this as exploitable on the current network's minimum supported version.

### Recommendation
- Make the pending-transaction-queue's `WithdrawFromGasKey` scan recursive: also inspect the inner `actions` of any `Delegate`/`DelegateV2` action (both in `PendingTxSession::check_pending`/session tracking and `PendingTransactionQueue::add_chunk_transactions`), consistent with how `total_deposit`/`total_prepaid_send_fees` already recurse into delegate actions (`runtime/runtime/src/config.rs` `total_deposit`, `total_prepaid_send_fees`).
- Ensure the `RejectWithdrawFromGasKeyInDelegate` action-validation rejection is applied unconditionally (not protocol-version-gated) going forward, or confirm and document that `MIN_SUPPORTED_PROTOCOL_VERSION` has moved past the vulnerable version so no supported chain state can hit this path — until confirmed, the pending-queue fix above should be applied defensively regardless of the validation-layer fix, since accounting bugs and validation bugs are independent layers.

### Proof of Concept
Using the existing test as the reproduction harness for the underlying primitive (pre-fix protocol version): [5](#0-4) 
This shows a delegated `WithdrawFromGasKey` succeeding and draining the gas key balance pre-upgrade. To weaponize the accounting gap: submit two (or more) such delegated-withdraw transactions signed against the same gas key within the same block-production window (before certification), relying on `PendingTransactionQueue`'s inner-action-blind scan (`chain/client/src/pending_transaction_queue.rs:311-320`) to under-report `paid_from_gas_key`, then submit a further gas-key transaction that the (correct) accounting should have rejected via `NotEnoughGasKeyBalance` but that the pending-queue's stale/incomplete count admits instead.
