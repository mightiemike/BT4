### Title
Stale/reverted Cairo0 class bytecode trusted from global cross-block cache without re-validating declaration - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
The DNS CVE describes a resolver caching "promiscuous" auxiliary records that accompany a validated response without checking that those records are actually authorized/relevant, letting stale/attacker-influenced data poison the cache. The sequencer has a structurally analogous flaw: `StateReaderAndContractManager::get_compiled_from_class_manager` re-validates that a **Cairo1** class pulled from the process-global `ContractClassManager` cache is still actually declared in the canonical state before trusting it, but explicitly skips this re-validation for **Cairo0 (V0)** classes.

### Finding Description
`get_compiled_from_class_manager` looks up `class_hash` in the global, block-independent `contract_class_manager` cache. If found: [1](#0-0) 

For non-V0 (Cairo1) classes it re-checks `self.state_reader.is_declared(class_hash)` because "existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)". For `RunnableCompiledClass::V0(_)` this check is explicitly skipped (`=> {}`), so a Cairo0 class hash that was cached during execution of a candidate/speculative block that was later reverted or aborted (e.g. via `Batcher::abort_proposal`/`revert_block`, or a consensus-rejected proposal) remains trusted forever afterward, without any check that it is actually declared in the canonically committed state at the time of use.

This mirrors the CVE's root cause exactly: a piece of data (here, compiled Cairo0 bytecode) that was learned in one, potentially-untrusted or non-final context (a discarded/aborted block build) is cached and later served as if it had the trust level of data belonging to the current, canonical, final context — because the validation of "is this actually currently relevant/authorized" is applied inconsistently (done for V1, skipped for V0).

The cache (`ContractClassManager`/`TrivialClassManager`/`NativeClassManager`) is a long-lived, per-process, cross-block, cross-proposal structure keyed only by `ClassHash`: [2](#0-1) 
It is not scoped to a specific block or state root, and is not cleared on `abort_proposal`/`revert_block`. Batcher proposal aborts and block reverts only affect batcher-level state (`executed_proposals`, storage), not this class cache: [3](#0-2) [4](#0-3) 

The test suite even documents the asymmetry as an intentional design choice, confirming the code path and its behavior: [5](#0-4) 

### Impact Explanation
If a Cairo0 class hash is executed/compiled once (e.g. as part of a validated or speculatively-built candidate block that never gets committed — for example a `validate_block`/`propose_block` flow that's aborted, or a proposal for a competing/losing block in consensus), its compiled bytecode is inserted into the process-global cache. If that class was never actually declared canonically (or its declaration is later reverted), a subsequent transaction referencing the same class hash on the same node will be served the cached bytecode as "declared" with no re-check, since only V1 performs `is_declared`. This can let a transaction sender or contract deployer cause the sequencer to execute code for an address/class that is not actually declared in the committed state, producing:
- A state transition (and resulting state root / block hash) that diverges from what other honest sequencers (whose caches were not similarly polluted, e.g., after a restart or on a node that never built the discarded proposal) would produce for the same transaction — an honest-node divergence / wrong committed root, exactly the class of impact required.
- Potential execution of code that was never actually agreed upon/declared by consensus, i.e., unauthorized contract-class use, since "declared" state is supposed to be the sole gate for using a class's bytecode.

### Likelihood Explanation
Reachability requires only ordinary sequencer operation from an unprivileged transaction sender: submit a Declare + Invoke/DeployAccount referencing a Cairo0 class inside a proposal that ultimately gets aborted/reverted (a routine, frequent occurrence in consensus — e.g., losing a round, timeout, or validation failure), then resubmit a transaction touching the same class hash. No malicious operator, peer, or p2p compromise is needed — this is purely a function of the local sequencer's normal proposal lifecycle plus an attacker-chosen sequence of transactions.

### Recommendation
Apply the same `is_declared` re-validation to `RunnableCompiledClass::V0` cache hits as is already done for other variants in `get_compiled_from_class_manager`, removing the special-cased `V0(_) => {}` branch, or otherwise ensure the global `ContractClassManager` cache is invalidated/scoped per committed state so stale entries from aborted/reverted proposals can never be trusted without a canonical-state check.

### Proof of Concept
1. Submit a Declare transaction for a Cairo0 class `C` plus a transaction that exercises it (e.g. Invoke/DeployAccount) such that it gets included in a candidate block proposal built by the batcher (`propose_block`/`validate_block`), causing `get_compiled_from_class_manager` to compile and cache `C` in the global `ContractClassManager`.
2. Cause that proposal to be aborted or the block to be reverted (e.g., via `abort_proposal`/`revert_block`, or normal consensus round failure) so that `C` is never actually committed/declared in canonical state.
3. Submit a new transaction on the same node referencing class hash `C` (e.g., another DeployAccount or a call assuming `C` is declared).
4. Observe: for a V1 class this second call would correctly fail with `StateError::UndeclaredClassHash` via the `is_declared` check (as demonstrated by `cached_but_verification_failed_after_reorg_scenario` in `state_reader_and_contract_manager_test.rs`); for the equivalent V0 (Cairo0) scenario, no such check exists, and the class is served from cache and treated as declared, allowing execution to proceed and diverge from a node without the polluted cache.

        self.ensure_validate_proposal_exists(proposal_id)?;

        self.validate_tx_streams.remove(&proposal_id);

        info!("Reverting block at height {}.", input.height);
        let height = self.get_height_from_storage()?.prev().ok_or(
            BatcherError::StorageHeightMarkerMismatch {
                marker_height: BlockNumber(0),
                requested_height: input.height,
            },
        )?;

        if height != input.height {
            return Err(BatcherError::StorageHeightMarkerMismatch {
                marker_height: height.unchecked_next(),
                requested_height: input.height,
            });
        }

        if let Some(height) = self.active_height {
            info!("Aborting all work on height {} due to a revert request.", height);
            self.abort_active_height().await;
        }

        // Wait for the revert commitment to be completed before reverting the storage.
        self.revert_commitment(height).await;

        self.storage_writer.revert_block(height);
        BUILDING_HEIGHT.decrement(1);
        GLOBAL_ROOT_HEIGHT.decrement(1);
        REVERTED_BLOCKS.increment(1);
        Ok(())
    }
