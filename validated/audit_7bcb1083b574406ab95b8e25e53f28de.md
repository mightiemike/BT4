### Title
Missing verification that session-token `dest` matches caller-supplied `shop` in `tokenExchange` allows cross-tenant token exchange - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`shopify.auth.tokenExchange` accepts two independent identity inputs — a signed session token (whose `dest`/`iss` claims identify the shop it was issued for) and a caller-supplied `shop` string — and never checks that they refer to the same shop before using the session token as the `subject_token` in an OAuth token-exchange request sent to `https://{shop}/admin/oauth/access_token`. This mirrors the Babylon bug class: two values that are supposed to represent distinct, matching identities (there, staker key vs. finality-provider key; here, the token's `dest` vs. the request's `shop`) are never compared for equality/consistency, silently collapsing a security invariant.

### Finding Description
`tokenExchange` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` does: [1](#0-0) 

It calls `decodeSessionToken(config)(sessionToken)` purely to validate signature/expiry/audience, but discards the returned payload entirely — it never compares `payload.dest` (or `payload.iss`) to the `shop` parameter that was passed in: [2](#0-1) 

The `shop` parameter is then independently sanitized with `sanitizeShop` and used to build the target URL for the token-exchange POST request: [3](#0-2) 

Critically, the library's own documented usage pattern derives `shop` from the request query string (`req.query.shop`), a value fully independent of the session token's embedded `dest` claim: [4](#0-3) 

While the built-in `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` middlewares happen to derive `shop` safely from the token's own `dest` claim (see `perform-token-exchange.ts` line 67: `const shop = new URL(payload.dest).hostname;`), the underlying `shopify-api` library function itself provides no such guarantee and its documented API/example explicitly takes `shop` from request input separate from the token. Any app built directly against `shopify.auth.tokenExchange` per the documented pattern (or any future/alternate integration that doesn't happen to derive `shop` from the token) is exposed to a shop/session mismatch that the library does nothing to prevent — the equality check between the two identity sources is simply absent.

### Impact Explanation
If an app (following the documented API) passes a `shop` value from request input that is not cross-checked against the session token's `dest`, an authenticated user of shop A could exchange a session token they legitimately hold for an access-token request scoped to an arbitrary shop B. Depending on how the resulting `Session` (with `shop: cleanShop`) is subsequently used/persisted by the app, this can lead to cross-tenant session confusion — sessions being stored, looked up, or attributed to the wrong shop, or an app's afterAuth/session bootstrapping logic operating on behalf of a shop different from the one that actually authenticated. This is the equivalent of the Babylon issue: a security invariant ("the token's subject and the shop being acted upon must be the same principal") is not enforced by the library, silently letting an unprivileged caller reduce two independent security checks to one.

### Likelihood Explanation
Likelihood is elevated because the library's own reference documentation for `tokenExchange` explicitly instructs callers to source `shop` from request/query parameters independently of the session token, without ever mentioning the need to verify token/shop consistency. Any developer using `shopify-api` directly (i.e., not exclusively through the fully-wired `shopify-app-express`/`shopify-app-remix` middlewares, or any custom middleware/backend that reimplements token exchange per the docs) is likely to reproduce this gap.

### Recommendation
In `tokenExchange` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), capture the decoded payload from `decodeSessionToken` and verify that `new URL(payload.dest).hostname` (or the sanitized equivalent) equals the sanitized `shop` parameter before proceeding; throw an `InvalidJwtError`/`InvalidOAuthError` on mismatch. Update the documentation example to derive `shop` from the decoded token rather than from request query parameters, consistent with how `perform-token-exchange.ts` already does it internally.

### Proof of Concept
1. Merchant/attacker with a valid, unexpired session token for `attacker-shop.myshopify.com` (obtained legitimately as an installed-app user of that shop) calls an app's `/auth` (or equivalent) endpoint per the documented pattern:
   `GET /auth?shop=victim-shop.myshopify.com` with `Authorization: Bearer <session-token-for-attacker-shop>`.
2. The app code (following the documented example in `tokenExchange.md`) does:
   ```ts
   const shop = shopify.utils.sanitizeShop(req.query.shop, true); // "victim-shop.myshopify.com"
   await shopify.auth.tokenExchange({ sessionToken, shop, requestedTokenType: ... });
   ```
3. `tokenExchange` decodes/validates the token (audience check passes — `aud` only needs to match the app's `apiKey`, which is shop-independent), discards the payload, and issues a POST to `https://victim-shop.myshopify.com/admin/oauth/access_token` with `subject_token` set to the token issued for `attacker-shop.myshopify.com` — with no check that the token's `dest` matches `victim-shop.myshopify.com`.
4. The resulting `Session` object is created with `shop: "victim-shop.myshopify.com"` regardless of the token's true origin, which the calling app may then persist/serve as if it belongs to the victim shop.

```typescript
export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,

        },
      },
    );
```

```typescript
export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
```
