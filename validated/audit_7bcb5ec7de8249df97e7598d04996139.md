### Title
JIT vote manipulation dilutes witness voter rewards via cycle-boundary vote-count inflation - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
java-tron's DPoS voter-reward mechanism computes each Super Representative's (SR) per-vote reward ("VI", value-per-vote) for a cycle using the witness's vote count that is captured *after* all votes cast during that cycle have been folded in. A holder of already-frozen TRX (Tron Power) can cast a large, free, zero-lockup vote for a specific witness in the last block before a maintenance/cycle boundary, causing that inflated vote count to become the permanent denominator used to calculate the *next* cycle's reward-per-vote for that witness, then immediately reallocate the vote away in the next block — diluting the rewards earned by all legitimate long-term voters of that witness for that cycle, at zero cost to the attacker.

### Finding Description
Reward accrual for witness voters is done via a cumulative "VI" (value-per-vote) accumulator. At every maintenance/cycle boundary, `MaintenanceManager.doMaintenance()`:

1. First accrues VI for the cycle that just ended using the witness's vote count *as of before this epoch's votes are applied* — [1](#0-0) 
2. Then applies all votes cast during the epoch to the witness's running vote count via `countVote` and `witnessCapsule.setVoteCount(...)` — [2](#0-1) 
3. Finally snapshots that *just-inflated* vote count as the vote-count denominator to use for the **next** cycle's reward calculation — [3](#0-2) 

The per-cycle reward-per-vote (VI) delta is `reward / voteCount` computed in `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`: [4](#0-3) 

Any voter's reward for holding votes across cycles is then `deltaVi * userVote`, computed in `MortgageService.computeReward` / `VoteRewardUtil.computeReward`: [5](#0-4) 

Casting or changing a vote is free and instantaneous: `VoteWitnessActuator.calcFee()` returns `0`, there is no lockup, cooldown, or minimum holding period for votes — only frozen TRX (Tron Power) is required as a ceiling on total vote weight: [6](#0-5) [7](#0-6) 

This mirrors the Sturdy `distributeYield` JIT/MEV bug class: a participant can insert a large, uncommitted stake immediately before a reward-accounting snapshot, get folded into the denominator/weighting used for the next distribution period, and withdraw immediately after — diluting the yield/reward of participants who genuinely contributed for the whole period, without ever being economically exposed themselves.

### Impact Explanation
Any large holder of already-frozen TRX (a whale, or TRX borrowed/rented just for this purpose) can, at the very last block before a maintenance boundary, cast (or redirect) a large vote to a target witness. This vote is folded into `witnessCapsule.getVoteCount()` before that count is persisted as the vote-count denominator for the next cycle's reward computation. The attacker can then immediately clear/redirect the vote in the very next block (cost-free, per `calcFee()==0`) with no lockup requirement. Because the deltaVi (reward-per-vote) for the next cycle is `reward / voteCount`, this artificially inflated denominator permanently reduces the reward-per-vote credited to every honest voter who kept their vote on that witness for that cycle — an accounting divergence that unfairly and irreversibly redistributes/diminishes value from legitimate long-term voters, matching the "invalid-state/accounting" impact class of the underlying report even without the attacker necessarily capturing reward themselves.

### Likelihood Explanation
The attack requires no special privilege — only ownership of frozen TRX (Tron Power) sufficient to cast a large vote, and the ability to time a transaction to land in the last block before a known/predictable maintenance boundary (`nextMaintenanceTime`, a public, deterministic on-chain value) — which is directly analogous to watching the mempool for `distributeYield` in the original report. No mempool-privacy tooling is even strictly required since maintenance time is deterministic and publicly known in advance, making this easier to execute reliably than the original MEV-based attack.

### Recommendation
Snapshot the vote-count denominator used for a cycle's reward computation using the vote count that was in effect *throughout* that cycle (i.e., the pre-cycle vote count, before that cycle's new votes are folded in), rather than the vote count that includes votes cast in the final block(s) before the boundary. Alternatively, require votes to be held for a minimum duration (e.g., at least one full cycle) before they count toward a witness's reward-weighting denominator, so that vote weight used in reward math reflects sustained support rather than instantaneous, freely-reversible vote placement.

### Proof of Concept
1. Attacker holds/acquires frozen TRX (Tron Power) sufficient to cast a large vote for target witness `W` (no need to freeze new TRX if reusing existing Tron Power; votes can be freely redirected via `VoteWitnessActuator`, fee `0`).
2. Shortly before the on-chain, publicly known `nextMaintenanceTime` is reached, attacker submits `VoteWitnessContract` voting a large amount for `W`.
3. The block containing this vote is the last block of cycle `N`; `MaintenanceManager.doMaintenance()` runs: it computes cycle `N`'s VI using `W`'s pre-epoch vote count (excludes attacker, so attacker doesn't distort the cycle that just ended), then folds the attacker's vote into `W`'s running vote count and stores that inflated count as the denominator for cycle `N+1`'s reward math.
4. In the first block(s) of cycle `N+1`, attacker redirects/clears their vote away from `W` at zero cost.
5. At the next maintenance (end of cycle `N+1`), `W`'s deltaVi is computed as `reward / inflatedVoteCount`, permanently lowering the reward-per-vote credited to all voters who genuinely held votes on `W` throughout cycle `N+1`, while the attacker incurred no lockup and no loss.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
