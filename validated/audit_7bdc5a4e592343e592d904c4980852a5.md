## Title
Chunk-halting panic via unwrap on `receiver_shard_id()` for stale `GlobalContractDistribution` receipts across multiple reshardings - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`Receipt::receiver_shard_id()` can return `Err(EpochError::ShardingError(...))` for a `GlobalContractDistribution` receipt whose `target_shard` no longer exists in the current shard layout and cannot be resolved via `resolve_to_current_shard`. This error path exists because `resolve_to_current_shard` relies on the accumulated `shards_split_map` history, and it is only guaranteed to resolve a shard that is actually present in that history. Multiple call sites unconditionally `.unwrap()` this `Result`, most notably `receipt_filter_fn` in the delayed-receipt draining path used during resharding [1](#0-0) .

### Finding Description
`GlobalContractDistribution` receipts, created whenever any account deploys a global contract, carry a fixed `target_shard` that is computed once at creation time (`runtime/runtime/src/global_contracts.rs`, `apply_global_contract_distribution_receipt`) [2](#0-1) . If chunk compute is saturated, the receipt can sit in the delayed-receipt queue across one or more resharding events before being processed.

`Receipt::receiver_shard_id()` special-cases `GlobalContractDistribution`: if the recorded `target_shard` is no longer part of the current shard layout, it calls `shard_layout.resolve_to_current_shard(target_shard)`, and only if that also fails does it return `Err(EpochError::ShardingError(...))` [3](#0-2) .

`resolve_to_current_shard` walks `shards_split_map`, which is built from a bounded `layout_history` slice passed to `derive_with_layout_history`/`build_shard_split_map` [4](#0-3)  and returns `None` "only if the shard ID is absent from both the current layout and the split history" [5](#0-4) . If the split history available to a given epoch's `ShardLayoutV3` does not go back far enough (e.g. layout constructed from a base layout via `derive()`, which carries over only its own `shards_split_map` without re-deriving full ancestry, or a V1/V2→V3 transition that truncates `layout_history`), a target shard from an older generation is not recoverable, and `receiver_shard_id()` legitimately returns `Err`.

The delayed-receipt drain path, `DelayedReceiptQueueWrapper::receipt_filter_fn`, calls this function and immediately `.unwrap()`s the result: `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()` [1](#0-0) . This is invoked from `pop()`, which is on the hot path every chunk applies when draining the delayed receipt queue during/after resharding [6](#0-5) . The same unwrap-on-error pattern recurs in the outgoing-buffer forwarding path, `forward_from_buffer_to_shard`, via `receipt.receiver_shard_id(&shard_layout)?` (there it is propagated as `RuntimeError`, but callers of `RuntimeError::ReceiptValidationError`/unexpected variants in `chain/chain/src/runtime/mod.rs` `panic!` on several error kinds during chunk apply) [7](#0-6) [8](#0-7) .

This is directly analogous to CVE-2021-27345 (lrzip's `ucompthread` NULL-pointer dereference from unchecked internal state during decompression, causing DoS): here an internal invariant ("delayed cross-shard receipt target is always resolvable") is assumed but not actually guaranteed once resharding history exceeds what a given shard layout retains, and the unchecked `.unwrap()` converts a recoverable `Err` into a process abort.

Note: the repository already contains a regression test, `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs`, whose own comments state: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations."* [9](#0-8) . This strongly indicates the underlying `.unwrap()` panic is a known/still-tracked risk class in this exact code path, and that `resolve_to_current_shard`'s history-based mitigation is a best-effort fix rather than a structural guarantee for arbitrarily deep or history-truncated resharding sequences (e.g. layout derivation paths that don't propagate full `layout_history`, or long-lived delayed receipts across many epochs combined with GC/history pruning).

### Impact Explanation
A successful trigger causes every validator applying the chunk to panic in `Runtime::apply` while draining the delayed receipt queue. Because this happens deterministically for all honest nodes processing the same chunk, it manifests as a **transaction/receipt-triggered chain halt** (repeated panics on all validators attempting to apply the same block), matching the accepted impact category "a transaction-triggered halt." Any account can trigger the underlying receipt type by deploying a global contract, and the panic depends on chunk-compute saturation plus resharding schedule/timing (validator-controlled but not attacker-required to cooperate maliciously), keeping the causal chain within the closure of "contract deployer" actions plus routine protocol resharding.

### Likelihood Explanation
Likelihood is constrained by needing: (1) a global contract deployment whose distribution receipt is still delayed, and (2) at least one (potentially two, per the existing test) resharding events whose combined split history is not fully retained/derivable for that receipt's original `target_shard` at the point it is dequeued. This requires specific timing/config (dynamic resharding with force-splits, compute saturation to delay the receipt) that is more readily reproducible in test/validator-influenced conditions than a fully attacker-controlled single-transaction exploit, so likelihood is lower than a pure single-tx trigger, but the pattern is real, deterministic once conditions align, and already codified as a named regression scenario in-repo.

### Recommendation
- Replace all `.unwrap()` calls on `receiver_shard_id()` (e.g., in `receipt_filter_fn`, `runtime/runtime/src/congestion_control.rs:876`) with proper error propagation into `RuntimeError`/`StorageInconsistentState`-style handling instead of panicking, consistent with how other delayed-receipt validation failures are already treated (`runtime/runtime/src/lib.rs:2500` treats a validate_receipt failure on dequeue as `StorageInconsistentState` rather than panicking).
- Ensure `shards_split_map`/`layout_history` is never truncated for any V3 layout so `resolve_to_current_shard` is guaranteed complete for every shard ID that could still be referenced by an in-flight delayed/buffered receipt; audit `ShardLayoutV3::derive()` and any V1/V2→V3 transition path for correct propagation of full split ancestry.
- Add an explicit protocol-level invariant/test ensuring a `GlobalContractDistribution` receipt's `target_shard` is always resolvable for the maximum number of reshardings a receipt could realistically survive while delayed (bounded by GC/epoch retention), and add fuzzing/property tests around `resolve_to_current_shard` with adversarial split-history truncation.

### Proof of Concept
Conceptual reproduction (a working version already exists in-repo as `test_stale_global_contract_distribution_after_double_resharding`):
1. Deploy a global contract from an account in shard `S_A` — this creates a `GlobalContractDistribution` receipt with `target_shard = S_A`.
2. Saturate `S_A`'s chunk compute every block so the receipt is pushed into (and stays in) the delayed receipt queue.
3. Force two sequential dynamic reshardings that split `S_A` (and later one of its children) via `DynamicReshardingConfig{force_split_shards: [...]}`, so that after two split generations `S_A` is no longer directly resolvable/complete in the current layout's `shards_split_map`.
4. Stop saturating compute and let the delayed queue drain; when the stale receipt is popped, `DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receiver_shard_id(&shard_layout).unwrap()`, which panics if `resolve_to_current_shard` cannot walk back far enough in the retained split history, halting chunk application on all nodes that process that chunk.

            // Check proof size limit before each receipt is popped.

                break;

                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;

                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

/// Build `ShardsSplitMapV3` from a sequence of previous shard layouts.
///
/// Assumes that layouts are ordered from newest to oldest, and that there are no duplicates.
/// Ignores layouts with `version()` lower than `VERSION` (this is **not** the struct version).
pub fn build_shard_split_map(layout_history: &[ShardLayout]) -> ShardsSplitMapV3 {
    let mut split_history = ShardsSplitMapV3::new();

    for window in layout_history.windows(2) {
        let current_layout = &window[0];
        let prev_layout = &window[1];

        if current_layout.version() < VERSION || prev_layout.version() < VERSION {
            break;
        }

        debug_assert_ne!(current_layout, prev_layout);

        for shard_id in current_layout.shard_ids() {
            match current_layout.try_get_parent_shard_id(shard_id).expect("invalid shard_id") {
                Some(parent_id) if parent_id != shard_id => {
                    split_history.entry(parent_id).or_default().push(shard_id);
                }
                _ => continue,
            }
        }
    }

    split_history
}

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }
