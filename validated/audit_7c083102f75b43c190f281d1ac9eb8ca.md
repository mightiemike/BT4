### Title
CREATE2 Front-Running Denial-of-Service for Deterministic Contract Deployment - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
TVM's `CREATE2` opcode computes contract addresses deterministically from `sender`, `salt`, and `init code`, all of which are attacker-visible once a deployment transaction enters the mempool [1](#0-0) . Any unprivileged actor can copy the observed `salt`/bytecode arguments, compute the same target address, and race the legitimate deployer's transaction with their own `CREATE`/`CREATE2` call. The legitimate deployment then reverts because `createContractImpl` refuses to deploy over an already-existing contract, causing a denial-of-service that mirrors the `permit()` front-running bug class described in the external report (a publicly observable, single-use, address/argument-bound operation that a third party can "consume" ahead of the intended caller).

### Finding Description
`Program.createContractImpl` computes whether the target address already holds a contract and, if so, rejects the deployment: [2](#0-1) [3](#0-2) 

For `CREATE2`, the resulting address is fully deterministic from `(sender, salt, keccak256(initcode))`, and this exact formula is reproducible off-chain by anyone observing the pending transaction data, as demonstrated by the `getCreate2Addr` helper in the test fixture: [1](#0-0) 

Because the salt and init code (and thus the target address) are visible in the mempool before the deploying transaction is confirmed, a malicious actor can broadcast their own transaction with the same `(sender-context, salt, initcode)` pattern (via any contract they control that can call `CREATE2` with attacker-chosen inputs, or even by deploying identical bytecode from a different factory address if the victim's factory address is also predictable) to occupy the target address first. The original, legitimate deployer's transaction then fails validation in `createContractImpl`, which explicitly throws when `contractAlreadyExists`: [3](#0-2) 

This is structurally identical to the reported `permit()` front-running issue: a publicly visible, argument-dependent, one-time-consumable on-chain action (deploy to computed address / consume permit signature) that any unprivileged party can pre-empt, causing the victim's dependent transaction to revert.

### Impact Explanation
Applications relying on deterministic `CREATE2` deployment (e.g., counterfactual wallets, deterministic proxy factories, precomputed vault addresses referenced by other contracts before deployment) can have their deployment transactions denial-of-serviced by any unprivileged user who monitors the mempool. The victim's transaction consumes energy/bandwidth and fails, and the flow relying on the specific deterministic address is blocked/delayed. This matches the "invalid-state/divergence/halt" and DOS impact classes called out in the validation criteria.

### Likelihood Explanation
Exploitation requires no special privileges — the attacker only needs mempool visibility (public on TRON) and the ability to submit a competing `CREATE`/`CREATE2` transaction ahead of the victim's. This is a well-known, inherent property of deterministic contract creation and is not unique to a coding defect; it depends entirely on the victim application choosing to reveal salt/initcode before final confirmation, which is a common pattern for factory-based deployments (as shown by the project's own `Create2Test.java`, which asserts that a second, competing deployer's transaction to the same computed address fails): [4](#0-3) 

### Recommendation
There is no core-protocol fix analogous to "use try/catch for permit," since this is an inherent characteristic of deterministic address derivation (identical to Ethereum's CREATE2 semantics) rather than a defect in `java-tron`'s implementation. Recommend documenting the front-running risk for dApp/factory authors and advising them to bind additional caller-specific or nonce-based entropy into the `salt` (e.g., include `msg.sender` and an application-level nonce) so that the deterministic address cannot be trivially reproduced and squatted by a third party observing the mempool, and to design deployment flows to tolerate/retry on a `contractAlreadyExists`-style revert rather than treating it as fatal.

### Proof of Concept
1. A factory contract computes a `CREATE2` address from `(salt, initcode)` and exposes a `deploy(bytes initcode, uint256 salt)` entry point, as in the project's own test fixture: [5](#0-4) 
2. A legitimate user broadcasts a transaction calling `deploy(testCode, salt)`. Because it sits in the public mempool, the `(testCode, salt)` pair — and hence the target address — is visible to everyone.
3. An attacker copies these exact arguments and submits their own `deploy(testCode, salt)` transaction with higher priority/fee, landing first.
4. When the victim's original transaction executes, `createContractImpl` sees `contractAlreadyExists == true` and rejects it: [3](#0-2) 
5. This is exactly the behavior asserted (for a differently-owned second caller) in the repository's own `Create2Test`: [4](#0-3)

```text
    // selector: 0xbb63e785
    // Predict CREATE2 address without deploying
    //
    // TRON CREATE2 formula (differs from standard EVM):
    //   address = keccak256(prefix ++ sender[20] ++ salt[32] ++ keccak256(code)[32])[12:]
    //
    // - Standard EVM uses 0xff as prefix (magic byte)
    // - TRON replaces it with the address prefix byte (0x41 for mainnet, 0xa0 for testnet)
    // - This value is hardcoded at compile time by tron-solc
    //
    function getCreate2Addr(uint256 salt) public view returns (address) {
        bytes memory bytecode = type(FreezeContract).creationCode;
        bytes32 hash = keccak256(
            abi.encodePacked(
                bytes1(0x41),       // TRON mainnet address prefix
                address(this),      // 20-byte factory address
                salt,               // 32-byte salt
                keccak256(bytecode) // 32-byte code hash
            )
        );
        return address(uint160(uint256(hash)));
    }
```
