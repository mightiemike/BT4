### Title
Unbounded growth of `IdempotentPromiseHandler.identifiers` map enables memory-exhaustion DoS of the token-exchange auth handler - ([File: packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts])

### Summary
The token-exchange authentication strategy (used by `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express`) deduplicates `afterAuth` hook invocations using a shared `IdempotentPromiseHandler` instance keyed by the raw session-token JWT string. Entries are only purged lazily, once per invocation, and only if older than a fixed 60-second TTL — mirroring the CKB `misbehavior` HashMap bug class: a map keyed by an ever-changing, attacker-influenced value that grows without a cap and is cleaned up only after the fact rather than bounded up front.

### Finding Description
`IdempotentPromiseHandler` stores a `Map<string, number>` of identifiers with no maximum size and no proactive eviction — cleanup only removes entries strictly older than `IDENTIFIER_TTL_MS` (60000ms), and only as a side effect of another call to `handlePromise`: [1](#0-0) 

This handler is invoked from the token-exchange auth flow, keyed directly by the raw session-token JWT string received on every authenticated request to the embedded app: [2](#0-1) 

The identical pattern exists in the Express middleware, keyed by `sessionToken` as well: [3](#0-2) 

Session tokens minted by Shopify's App Bridge for a given embedded session are short-lived (~1 minute) and are refreshed frequently by the client-side app. Because the map key is the full JWT string (not a hash or a stable per-shop identifier), and each token differs (different `iat`/`exp`/`jti` claims each time it is (re)issued), a single authenticated merchant/customer session that repeatedly triggers `handleAfterAuthHook` / `callAfterAuthHook` with distinct-but-valid session tokens (e.g. by causing the offline/online session to be treated as inactive on each request, or simply by requesting fresh tokens in rapid succession and hitting the token-exchange path concurrently) inserts a new, never-deduplicated entry into the shared, process-wide `identifiers` map on every call. Because `clearStaleIdentifiers` only evicts entries older than 60 seconds, the map can grow to size proportional to `(request rate) × 60s` with no upper bound, and because the handler instance is shared across all shops/sessions in the process (constructed once at `shopifyApp()` setup time), the memory cost accumulates across the whole app server, not just for one tenant.

This directly parallels the CKB advisory's root cause: an unbounded map keyed by an ever-incrementing/unique value, with entries removed only reactively (never proactively bounded), reachable trivially by a remote/low-privilege actor issuing repeated protocol-valid requests.

### Impact Explanation
An attacker with only a normal merchant/customer-level embedded app session (no special privilege) can drive sustained memory growth in the app server process by flooding the token-exchange endpoint with concurrent requests carrying distinct, validly-signed session tokens. Because the `IdempotentPromiseHandler` is a single shared instance for the whole app (not scoped per shop, per IP, or capped in size), this is a process-wide resource-exhaustion vector: sufficient request volume can degrade performance for all tenants of the app and, in the worst case, exhaust available memory and crash the server (matching the "Resource exhaustion paths" / "DoS of an auth handler" scenario called out in the assessment rules).

### Likelihood Explanation
Likelihood is moderate-to-high for any app using the token-exchange strategy under load: no secret material or privileged access is required, only the ability to repeatedly authenticate as a normal embedded-app session (something any installed merchant, or an attacker who has convinced a merchant to load a malicious script inside the app iframe, can do) and issue enough concurrent requests within the 60-second cleanup window to keep the map growing faster than it drains.

### Recommendation
- Cap the size of `IdempotentPromiseHandler.identifiers` (e.g., bounded LRU) so it cannot grow past a fixed limit regardless of request rate.
- Avoid keying by the full raw session-token string; use a stable, size-bounded key (e.g., a hash, or the `sub`+`shop`+`jti` tuple) so repeated tokens for the same logical session collide instead of each refresh producing a new entry.
- Proactively evict/reject new insertions once a size threshold is hit rather than relying solely on time-based lazy cleanup.
- Consider scoping the idempotency map per shop/session rather than a single process-wide instance, to prevent one tenant from affecting others.

### Proof of Concept
1. Install the app for a shop and load it in an embedded session to obtain a valid App Bridge session token.
2. From the client (or via a script that repeatedly requests fresh App Bridge session tokens), fire a burst of concurrent requests to the app's token-exchange-authenticated route, each carrying a freshly minted (but distinct) valid session token, at a rate high enough that new entries are added to `identifiers` faster than the 60-second TTL clears old ones (e.g., hundreds of requests/second sustained).
3. Observe that `config.idempotentPromiseHandler.handlePromise({..., identifier: sessionToken})` is invoked with a unique `identifier` each time, per [4](#0-3) , causing `this.identifiers` in [5](#0-4)  to grow continuously; monitor process RSS to confirm unbounded growth proportional to sustained request volume rather than plateauing at a fixed cap.

const IDENTIFIER_TTL_MS = 60000;

export class IdempotentPromiseHandler {
  protected identifiers: Map<string, number>;

  constructor() {
    this.identifiers = new Map<string, number>();
  }

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {
      if (Date.now() - date > IDENTIFIER_TTL_MS) {
        map.delete(identifier);
      }
    });
  }
}
