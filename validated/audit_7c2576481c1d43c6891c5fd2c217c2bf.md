### Title
Front-runnable asset-name identifier allows censorship of `AssetIssueActuator` token creation - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
When `ALLOW_SAME_TOKEN_NAME` is disabled (`getAllowSameTokenName() == 0`, the legacy/default mode), `AssetIssueActuator.validate()` treats the raw asset `name` field as the unique identifier for token creation and rejects any transaction whose name is already present in the `AssetIssueStore`, independent of who the transaction's owner is [1](#0-0) . This is structurally the same defect as the reported MesonSwap bug: a value visible in the mempool (the desired token name) is used as the sole existence/collision key, and it carries no binding to the original submitter's address, so anyone who observes a pending `AssetIssueContract` transaction can front-run it with an identical name and permanently block the original submitter's swap/asset creation for that name.

### Finding Description
`AssetIssueActuator.validate()` performs:
```java
if (dynamicStore.getAllowSameTokenName() == 0
    && assetIssueStore.get(assetIssueContract.getName().toByteArray()) != null) {
  throw new ContractValidateException("Token exists");
}
``` [1](#0-0) 

The `assetIssueContract.getName()` value is fully attacker-observable in the mempool before confirmation (it's a plaintext field in the pending transaction), and the existence check keys purely off that name — there is no binding of the reservation to the original signer's address before the name is claimed. This mirrors the MesonSwap flaw where `encodedSwap` (observable in the mempool) is used as the primary key in `_postedSwaps[encodedSwap]`, without embedding the initiator's address, allowing a `require(_postedSwaps[encodedSwap] == 0)` front-run failure for the legitimate submitter.

An attacker who sees a pending `AssetIssueContract` transaction for name `"FOO"` from victim `V` can construct their own `AssetIssueContract` for the same name `"FOO"` (any total supply/fees they can pay), and if their transaction is included first, `assetIssueStore.get("FOO")` becomes non-null. When `V`'s original transaction executes afterward, `validate()` throws `"Token exists"`, and the transaction fails — `V`'s TRX fee for building/broadcasting was still consumed by other network activity, and, more importantly, `V` is permanently denied the name unless they abandon it (asset names must be globally unique while this mode is active). The test `IssueSameTokenNameAssert` explicitly demonstrates that once "Token exists" is set, the same name from the same/any owner can never succeed while `AllowSameTokenName == 0` [2](#0-1) .

Additionally, `AssetIssueActuator` further restricts issuance to "one asset per owner" — this check (elsewhere in `doValidate`, seen in `assetIssueNameTest`, which asserts `"An account can only issue one asset"`) compounds the impact: a griefer only needs to squat a victim's chosen name once to render that specific name permanently unusable to the victim while legacy mode is active, since the collision is on `name`, and the account-scoped "one asset" restriction limits how the victim can respond.

### Impact Explanation
This is a denial-of-service / censorship vector on the `AssetIssueContract` actuator: a bad actor with mempool visibility can permanently block a specific user's ability to issue a specific token name by front-running with the same name and a trivial supply. Since asset names function similarly to on-chain identity/branding for TRC-10 tokens, this can be used to grief specific projects or accounts, and the condition (`AllowSameTokenName == 0`) is the legacy/default path still present and reachable in the actuator code, gated only by a dynamic parameter rather than removed. As in the original report, this is a low-severity, not directly profitable, griefing/DoS issue rather than a fund-theft issue, consistent with the "Low/Denial of Service" classification of the source report.

### Likelihood Explanation
Likelihood is moderate-to-low: the front-runner needs mempool visibility and to get their transaction included before the victim's, which is achievable via standard MEV/front-running techniques on any public mempool, and costs the attacker only the asset-issue fee. It only applies when the dynamic parameter `ALLOW_SAME_TOKEN_NAME` is set to `0`; if the network has this parameter permanently set to `1` (allowing duplicate names, keyed by numeric ID instead), the vulnerable branch is unreachable in practice on that specific network. I was not able to fully confirm from the index whether `ALLOW_SAME_TOKEN_NAME` is still toggleable to `0` or is now hard-locked to `1` on mainnet-equivalent configurations; the actuator code itself unconditionally supports and executes the `== 0` branch, so the vulnerability is present in the code regardless of the currently configured value.

### Recommendation
- Short term: Monitor `AssetIssueContract` transactions for name-collision failures ("Token exists") caused by conflicting near-simultaneous submissions, to detect active griefing.
- Long term: If the `ALLOW_SAME_TOKEN_NAME == 0` code path is still relevant, avoid rejecting purely on an attacker-visible, un-bound name; e.g., require a commit-reveal scheme for name reservation, or bind name reservation eligibility to a prior on-chain commitment (hash of name+owner) submitted ahead of time, similar to how `swapId` (which incorporates more context than a bare identifier) is recommended over `encodedSwap` in the original report.

### Proof of Concept
1. Victim `V` broadcasts an `AssetIssueContract` transaction with `name = "FOO"`, visible in the mempool.
2. Attacker `A` observes `"FOO"` in the mempool and broadcasts their own `AssetIssueContract` with `name = "FOO"` and minimal valid parameters, with a higher gas/priority so it is included first.
3. `AssetIssueActuator.execute()` for `A`'s transaction stores the asset under key `"FOO"` in `AssetIssueStore` [3](#0-2) .
4. When `V`'s transaction is later processed, `AssetIssueActuator.validate()` finds `assetIssueStore.get("FOO".toByteArray()) != null` and throws `ContractValidateException("Token exists")` [1](#0-0) , exactly as reproduced in the existing unit test `IssueSameTokenNameAssert`, which shows the "Token exists" failure occurring purely from a name collision, independent of ownership [4](#0-3) .
5. `V` is now permanently unable to issue an asset named `"FOO"` while `AllowSameTokenName == 0`.
