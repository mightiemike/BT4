### Title
Unbounded future oracle timestamp permanently poisons the monotonic `last-update` ratchet, freezing price resolution for the affected asset - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`price-resolve` gates every oracle price read behind `oracle-timestamp-fresh`, which treats any timestamp *in the future relative to the current block* as automatically "fresh" (delta forced to `u0`), and unconditionally ratchets the persistent `last-update` map upward whenever a larger timestamp is seen. There is no upper bound on how far into the future an accepted timestamp may be, and no mechanism to roll the ratchet back. A single anomalous/inflated `publish-time` accepted once permanently blocks all subsequent (correct) price reads for that asset, because the monotonicity check `(>= ts prev)` can never again be satisfied by real block timestamps until real time actually reaches the poisoned value.

The value bound: `last-update` (a per-`{type, ident}` map, persisted across blocks/transactions) is a monotonic ratchet advanced to `timestamp` whenever `timestamp > last-update-time`.

The event that invalidates it: `oracle-timestamp-fresh` never rejects a timestamp for being *too far in the future* - if `ts > stacks-block-time`, `delta` is forced to `u0`, which trivially satisfies `(<= delta max-staleness)`. So any anomalously large `publish-time` (arising from a decoder/relayer bug, a clock-skew edge case between Pythnet/DIA publish time and `stacks-block-time`, or any malformed-but-otherwise-valid update accepted upstream) is accepted as "fresh" and written into `last-update` as the new floor.

The later use: every subsequent call to `price-resolve` for that same `{type, ident}` key re-checks `(>= ts prev)` against this poisoned floor. Because real block timestamps can never exceed the erroneously large stored value (until actual chain time eventually reaches it, potentially far in the future), every future legitimate price update fails the monotonicity check and `price-resolve` reverts with `ERR-ORACLE-INVARIANT`.

This is directly reachable from the production entry points that call `price-resolve`/`price-multi-resolve` via `get-notional-evaluation`/`get-asset-value`, all of which are invoked before value-changing operations: [4](#0-3) 

`borrow` resolves prices via `get-notional-evaluation`; `repay`, `collateral-add`/`collateral-remove`, `liquidate`, and `supply-collateral-add` follow the identical accrue→price-resolve pattern shown for `add-collateral` and `liquidate`: [5](#0-4) [6](#0-5) 

### Impact Explanation
Once the `last-update` entry for a widely-used asset (e.g. `STX`, `USDC`) is poisoned, `price-resolve` for that asset reverts on every subsequent call, so `borrow`, `repay`, `collateral-add`, `collateral-remove`, `liquidate`, and `supply-collateral-add` for any position touching that asset become permanently unusable until real chain time catches up to the corrupted timestamp. Users cannot withdraw collateral, repay debt, or be liquidated safely - this is a temporary/permanent freezing of funds, in scope per the impact classification. Given no on-chain recovery path (no reset function for `last-update` was found), and depending on the magnitude of the erroneous timestamp, the freeze can be effectively permanent.

### Likelihood Explanation
The trigger does not require any privileged compromise: it only requires one accepted price update whose `publish-time`/timestamp is ahead of `stacks-block-time` by more than the natural clock drift the protocol otherwise tolerates. This can occur through legitimate-looking data (feed provider clock skew, decoder edge cases in `pyth-pnau-decoder-v3`, or a DIA feed timestamp-unit mismatch feeding into `resolve-dia`'s ms→s division) without any check ever rejecting "too far in future" timestamps. Because the flaw is in Zest's own `oracle-timestamp-fresh`/`price-resolve` logic (missing an upper bound and lacking any ratchet-reset mechanism), rather than being a data-correctness issue solely attributable to the third-party oracle, it stays in scope of "Oracle manipulation caused by a bug in THIS code."

### Recommendation
Add an explicit upper bound on `ts` relative to `stacks-block-time` (reject if `ts` is more than a small tolerance ahead of the current block time, rather than forcing `delta` to `u0`), and/or provide a DAO-gated recovery function to reset/correct a poisoned `last-update` entry so that a single anomalous timestamp cannot permanently brick price resolution for an asset.

### Proof of Concept
1. A price update for asset `X` (`{type, ident}`) is submitted via `write-feeds` → `resolve-pyth`/`resolve-dia`, returning a `timestamp` value that is inflated ahead of `stacks-block-time` (e.g. due to a decoder/timestamp-unit bug).
2. `price-resolve` calls `oracle-timestamp-fresh(timestamp, last-update-time, max-staleness)`; since `timestamp > stacks-block-time`, `delta` is forced to `u0`, so the freshness check passes trivially, and `(>= ts prev)` also passes.
3. `price-resolve` executes `(map-set last-update key timestamp)`, storing the inflated future value as the new floor for asset `X`.
4. In a later block, a legitimate relayer submits a correct price update for `X` with a real `publish-time` close to actual `stacks-block-time`.
5. `price-resolve` calls `oracle-timestamp-fresh` again; now `ts < last-update-time` (the poisoned floor), so `(>= ts prev)` fails, and `oracle-timestamp-fresh` returns `false`.
6. `price-resolve` asserts fail with `ERR-ORACLE-INVARIANT`, and this propagates through `get-notional-evaluation`/`get-asset-value` into every `borrow`, `repay`, `collateral-add`, `collateral-remove`, `liquidate`, and `supply-collateral-add` call that involves asset `X`.
7. All users with positions involving asset `X` are unable to interact with the market for that asset until `stacks-block-time` naturally reaches the poisoned value, freezing their funds.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
