### Title
Improper Handling of Malformed `host` Parameter Causes Unhandled Exception in Shop/Host Sanitization - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
The nimiq advisory panics because an election-block header passes an outer signature/format check but an inner field (`voting_key`) is not validated before being force-unwrapped, so a malformed-but-envelope-valid value crashes the node. The same class of bug exists in `sanitizeHost`: its base64 charset regex accepts strings that are *not* well-formed base64 (wrong length/padding), and the subsequent `atob()` call in `decodeHost` throws an uncaught, uncontrolled exception instead of the intended `InvalidHostError`.

### Finding Description
`sanitizeHost` validates the `host` query parameter using only a character-set regex: [1](#0-0) 

`base64regex = /^[0-9a-zA-Z+/]+={0,2}$/` matches strings such as a single character (e.g. `"A"`), which is not valid base64 (WHATWG base64 decoding requires the un-padded length mod 4 to not equal 1). It then immediately calls `decodeHost(sanitizedHost)`: [2](#0-1) 

`decodeHost` is a bare wrapper around the global `atob`, with no try/catch. `atob` throws (`DOMException`/`InvalidCharacterError`-style) on malformed input such as `"A"`. This throw happens *before* the function reaches the `throwOnInvalid` branch that would normally raise the controlled `InvalidHostError`: [3](#0-2) 

This is the same root-cause pattern as the nimiq bug: an outer "looks-valid" check (regex / block signature) is not sufficient to guarantee the inner decode/parse step (`atob` / `voting_key.uncompress()`) succeeds, and the failure path is an unhandled exception rather than a graceful validation error.

`sanitizeHost` is invoked from `validateShopAndHostParams`, which runs on unauthenticated document requests to the app's admin authentication entry point before any session token is present — i.e., reachable by any anonymous request carrying a `host` query parameter: [4](#0-3) 

The top-level `authenticateAdmin` handler only special-cases errors that are `Response` instances; any other thrown error (such as the raw `atob` exception) is simply re-thrown: [5](#0-4) 

So instead of the intended, controlled `InvalidHostError` (400-style handling), an anonymous request with a crafted `host` value that satisfies the regex but is not valid base64 causes an unhandled runtime exception to escape the auth handler.

### Impact Explanation
An anonymous, unauthenticated request to any embedded-app document/auth route with a malformed `host` query parameter (e.g. `?host=A`) forces an unhandled exception out of the request-authentication path (`validateShopAndHostParams` → `sanitizeHost` → `decodeHost` → `atob`) instead of the expected, safely-handled `InvalidHostError`. This is an availability/robustness issue in an auth-adjacent handler: requests can be crafted to bypass the intended validation-error flow and instead trigger uncontrolled exceptions, which is exactly the "Unchecked Return Value / Improper Handling of Exceptional Conditions" class cited in the report, applied to the host-sanitization step of the OAuth/session flow.

### Likelihood Explanation
High likelihood of triggering: the `host` parameter is fully attacker-controlled on any embedded app's document request, no authentication or secret knowledge is required, and simple values like a single letter or improperly padded strings satisfy the character-set regex while failing `atob`'s stricter length rules.

### Recommendation
Wrap the `atob` call in `decodeHost` (or in `sanitizeHost` around the `decodeHost`/`new URL` calls) in a try/catch and convert any decode/parse failure into the same controlled `InvalidHostError` path used for other invalid-host cases, mirroring the upstream nimiq fix of validating the inner field (`voting_key`) before use rather than blindly unwrapping it.

### Proof of Concept
1. Send an anonymous GET request to an embedded app's document route (any route hitting `authenticateAdmin`/`authenticate`) without a session-token header, and with `?shop=<valid-shop>.myshopify.com&host=A`.
2. `host=A` passes `base64regex` (`/^[0-9a-zA-Z+/]+={0,2}$/`) since it's a single alphanumeric character.
3. `sanitizeHost` calls `decodeHost('A')` → `atob('A')`, which throws because the input length (1) is invalid for base64 decoding.
4. The exception is not an `InvalidHostError` and is not caught by `sanitizeHost` or by the top-level `authenticateAdmin` try/catch (which only special-cases `Response` instances), so it propagates as an unhandled error instead of the expected 400-style invalid-host response.
