Based on the investigation, I found a genuine analog of the ELFi fee-misrouting bug in `java-tron`'s fee accounting logic.

### Title
Multi-sign fee and memo fee bypass the TransactionFeePool, causing witness reward funds to be permanently burned instead of collected in the corresponding pool - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`java-tron` supports an on-chain feature, `ALLOW_TRANSACTION_FEE_POOL` (`supportTransactionFeePool()`), whose design intent is that transaction-related fees paid by users are accumulated into a `TRANSACTION_FEE_POOL` and later distributed to witnesses (Super Representatives) as `transactionFeeReward` in `payReward()`. However, two fee types — the multi-signature fee and the memo fee — never check this flag and are unconditionally burned or sent to the blackhole address, exactly mirroring the ELFi bug where "borrowing fees" were left in the wrong pool (`UsdPool`) instead of being routed to the pool that the protocol design says should receive them (`LpPool`).

### Finding Description
`Manager.consumeMultiSignFee` and `Manager.consumeMemoFee` deduct fees from the paying account and then route them like this: [1](#0-0) [2](#0-1) 

Both methods check only `supportBlackHoleOptimization()`, and if true they call `dynamicPropertiesStore.burnTrx(fee)` (a permanent supply reduction), otherwise they send the fee to the blackhole account — never checking `supportTransactionFeePool()`.

Compare this with every other fee-routing path in the codebase, which all check `supportTransactionFeePool()` first before falling back to burn/blackhole:
- Bandwidth fee in `ResourceProcessor.consumeFeeForBandwidth`: [3](#0-2) 
- Energy fee in `ReceiptCapsule.payEnergyBill`: [4](#0-3) 

The pool is later drained proportionally each block to pay witnesses: [5](#0-4) 

So the protocol's design intent (as implemented consistently for bandwidth and energy fees) is that *all* transaction fees should flow into `TRANSACTION_FEE_POOL` when the feature is enabled, to be redistributed to witnesses. `consumeMultiSignFee` and `consumeMemoFee` break this invariant and permanently remove/burn the fee instead — an exact structural analog of the ELFi report, where fees that should be routed to a specific accounting destination (`LpPool`/witness reward pool) are instead left/burned in the wrong destination (`UsdPool`/blackhole), and cannot be retrieved afterward.

### Impact Explanation
This is a fund-misdirection / accounting-corruption issue: witness (SR) rewards funded by `TRANSACTION_FEE_POOL` are systematically under-distributed whenever transactions use multi-signature accounts or include memo data, because those specific fees are diverted to burn/blackhole rather than the reward pool, even though `ALLOW_TRANSACTION_FEE_POOL` is enabled on-chain today. This silently changes the economic distribution promised to consensus participants (witnesses) — a consensus-relevant reward-accounting inconsistency, not merely a cosmetic one, since `MULTI_SIGN_FEE` and `MEMO_FEE` are user-configurable, non-trivial values (`getMultiSignFee()`, `getMemoFee()`).

### Likelihood Explanation
This path is reachable by any user submitting an ordinary broadcast transaction with more than one signature or with a non-empty `data` field — both anonymous, unprivileged, everyday transaction patterns — and triggers on every affected transaction as long as `allowTransactionFeePool` is set (proposal #48), which is standard on live networks. No special conditions or attacker capability beyond normal transaction submission are required, so likelihood is high.

### Recommendation
Route both fees through the same conditional chain used elsewhere: check `dynamicPropertiesStore.supportTransactionFeePool()` first and, if true, call `dynamicPropertiesStore.addTransactionFeePool(fee)` instead of burning/blackholing, falling back to the existing `supportBlackHoleOptimization()`/blackhole logic only when the transaction fee pool feature is disabled.

### Proof of Concept
1. Enable `ALLOW_TRANSACTION_FEE_POOL` (already default on production chains via proposal #48).
2. Submit a transaction signed by 2+ keys under a multi-sign account (or any transaction with a non-empty `data`/memo field).
3. Observe in `Manager.consumeMultiSignFee`/`consumeMemoFee` that the account balance is reduced by `getMultiSignFee()`/`getMemoFee()`, but `TRANSACTION_FEE_POOL` (queryable via `getTransactionFeePool()`) is not incremented — the fee instead goes to `burnTrx` or the blackhole address, unlike bandwidth/energy fees which do increment `TRANSACTION_FEE_POOL` under identical settings.
4. Confirm at the next witness reward payout (`Manager.payReward` → `mortgageService.payTransactionFeeReward`) that the multi-sign/memo fee amount is absent from the reward calculation, permanently diverted away from the intended recipients.
