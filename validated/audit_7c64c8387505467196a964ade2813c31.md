### Title
OAuth callback shop-parameter confusion via HTTP Parameter Pollution allows HMAC validation to be performed on a different `shop` value than the one used for token exchange - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
`OAuth.callback()` extracts the `shop` query parameter using two different mechanisms that resolve differently when the query string contains a duplicated `shop` key. `URLSearchParams.get('shop')` returns the **first** occurrence, while `Object.fromEntries(query.entries())` (used to build the object that is HMAC/state-validated) collapses duplicate keys to the **last** occurrence. This mirrors the reported bug class where a fixed decoding assumption ("the first element in the structure is the ‘one’ relevant value") is applied to data whose actual structure allows multiple values, causing the wrong entity to be selected for a security-critical operation.

### Finding Description
In `callback()`: [1](#0-0) 

`shop` here is taken via `query.get('shop')`, which returns the **first** `shop=` value in the query string.

Later, the same `URLSearchParams` object is converted to a plain object for HMAC/state validation: [2](#0-1) 

`Object.fromEntries()` iterates all entries and lets later duplicate keys overwrite earlier ones, so `authQuery.shop` ends up being the **last** `shop=` value — the opposite of what `query.get('shop')` returned above.

The plain object then flows into `validateHmac(config)(authQuery)`, whose `normalizeQuery` only special-cases duplicate keys for `URLSearchParams` input or for the `appProxy` signator; for a plain object with the default `admin` signator it is passed through unchanged: [3](#0-2) 

So HMAC validation is computed and checked entirely against the **last** `shop` value, while the shop used to actually perform the privileged `/admin/oauth/access_token` exchange (and later stored as the session's `shop`) is the **first** value: [4](#0-3) 

This is the direct structural analog of the `SponsorPaymaster` bug: a security check is performed on one interpretation of attacker-supplied structured input (the "last" `shop`), while the sensitive action (the token exchange / session creation) is executed using a different interpretation of the same input (the "first" `shop`) — the two code paths silently diverge on which value is "the" shop.

### Impact Explanation
An attacker who legitimately completes OAuth for their own store can obtain a genuinely Shopify-signed callback URL (`code`, `hmac`, `state`, `shop=attacker.myshopify.com`, `timestamp`). By injecting an additional `shop=<victim>.myshopify.com` parameter before their own `shop` parameter, the resulting URL still passes `validateHmac`/state checks (because those are computed over the last-value collapsed object, which still equals the originally-signed query), yet the code-exchange POST request is sent to `https://<victim>.myshopify.com/admin/oauth/access_token`, and — if that request were ever accepted — the resulting `Session` would be persisted with `shop: <victim>.myshopify.com`. This is a shop/session-identity confusion bug reachable by a single, unauthenticated attacker crafting a URL; it breaks the invariant that "a request that passes HMAC/state validation is validated for the exact shop it acts upon," which is the core trust boundary of the OAuth callback handler.

### Likelihood Explanation
Triggering the divergence requires nothing more than an attacker adding a duplicate `shop` query parameter to a callback URL they already legitimately possess for their own store — no cryptographic material needs to be forged, only ordinary HTTP parameter pollution of a URL the attacker fully controls. The real-world payoff is bounded by whether Shopify's own `/admin/oauth/access_token` endpoint ties a given `code` strictly to the shop domain it was issued for (in which case the POST to the victim's domain would fail server-side); however, the application-level defect itself — validating one interpretation of `shop` while acting on another — is unconditionally present and violates the intended one-to-one binding between the value that is checked and the value that is used, independent of Shopify's downstream enforcement.

### Recommendation
Reject requests whose query string contains duplicate `shop` (or other single-value OAuth) parameters before any processing, the same way `normalizeQuery` already does for `appProxy` via `APP_PROXY_SINGLE_VALUE_PARAMS`. Extend that same duplicate-rejection logic to the `admin` signator path, and make `callback()` derive `shop` from a single canonical source (e.g., always from the already-validated `authQuery.shop`) instead of independently re-reading `query.get('shop')`, so the value used for HMAC/state validation and the value used for the token exchange/session creation can never diverge.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`, letting Shopify redirect them to the app's OAuth callback with a validly signed query: `?code=CODE&hmac=VALID_HMAC&shop=attacker.myshopify.com&state=STATE&timestamp=TS`.
2. Attacker intercepts this browser request before it reaches the app server and rewrites it to: `?code=CODE&hmac=VALID_HMAC&shop=victim.myshopify.com&shop=attacker.myshopify.com&state=STATE&timestamp=TS`.
3. In `callback()`, `query.get('shop')` returns `victim.myshopify.com` (first match) and is used to build `cleanShop` and the token-exchange URL `https://victim.myshopify.com/admin/oauth/access_token`. [5](#0-4) 
4. `authQuery = Object.fromEntries(query.entries())` collapses to `shop=attacker.myshopify.com` (last match), which is exactly what Shopify originally signed, so `validateHmac(config)(authQuery)` returns `true` and state validation passes. [2](#0-1) 
5. The app proceeds to exchange the attacker's OAuth `code` against `victim.myshopify.com`'s token endpoint and, on any success path, would create/store a `Session` object keyed to `victim.myshopify.com`.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }
