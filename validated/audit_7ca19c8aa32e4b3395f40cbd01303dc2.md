### Title
Unauthenticated Fee/Nonce/Signature Bypass via Forgeable Bootstrap-Declare Sender Address - (File: crates/starknet_api/src/executable_transaction.rs)

### Summary
The blockifier's declare-transaction execution path grants a fully unauthenticated fast-path — skipping signature validation (`__validate_declare__`), nonce enforcement, and fee charging — to any `Declare` transaction whose `sender_address` equals a hardcoded, public constant (`bootstrap_address()`, the felt encoding of the string `'BOOTSTRAP'`), whose `nonce` field is `0`, and whose fee is not enforced. Because this "authorization" is nothing more than a comparison against a publicly known constant baked into the source code — not an actual signature, private key, or any state-backed ownership check — any unprivileged transaction sender can forge a `Declare` transaction that satisfies these conditions and obtain the bootstrap fast-path on a live, already-running chain, not only during genesis bootstrapping as intended.

### Finding Description
`DeclareTransaction::bootstrap_address()` returns a fixed, publicly computable address: [1](#0-0) 

`is_bootstrap_declare` decides whether a given declare transaction should take the bootstrap fast-path purely based on transaction-supplied fields — the claimed `sender_address`, the claimed `nonce`, and whether fee is being charged — with no cryptographic or state-based verification that the caller actually controls/owns that identity: [2](#0-1) 

This flag is consumed directly in `AccountTransaction::execute_raw`, where, if `is_bootstrap_declare` returns true, the transaction executes with **no** call to `perform_pre_validation_stage` (which is what enforces nonce checks and fee bounds) and **no** `run_or_revert`/`__validate_declare__` invocation — it goes straight to `run_execute` and returns: [3](#0-2) 

Crucially, the on-chain/actual state nonce of the bootstrap address is never consulted for this decision — `is_bootstrap_declare` only checks the nonce value declared inside the submitted transaction, and the fast path itself never calls `state.get_nonce_at` or `increment_nonce`. As a result, the "account" at the bootstrap address never advances state, so the bypass is repeatable indefinitely for arbitrarily many different classes, at any block height, not only at genesis.

The same "magic sender + nonce" check is duplicated in the Starknet OS Cairo program that re-executes transactions for proving, using an identical hardcoded string comparison: [4](#0-3) 

On the gateway side, the only declare-time restriction is an optional allow-list (`authorized_declarer_accounts`), which is unset by default: [5](#0-4) [6](#0-5) 

Nothing in `check_declare_permissions` or elsewhere restricts the bootstrap fast-path to genesis time, to the node operator, or to a state where no blocks exist yet — a regular chain running with default gateway configuration will accept and execute such transactions from any submitter, exactly mirroring how `FootiumAcademy.mintPlayer` in the referenced report incorrectly derives authorization from an externally-controllable/spoofable check (`ownerOf`) instead of a securely bound, verified credential: here the "credential" is merely `sender_address == 'BOOTSTRAP'`, a public constant with no corresponding private key, and any attacker can set this field on a self-crafted, unsigned `Declare` transaction.

### Impact Explanation
Any unprivileged sender can craft a valid `DeclareTransactionV3` with `sender_address = bootstrap_address()`, `nonce = 0`, an empty/default signature, and resource bounds that yield zero enforced fee (e.g. `AllResourceBounds::new_unlimited_gas_no_fee_enforcement()`), and have it:
- Skip signature/`__validate_declare__` verification entirely (no authentication whatsoever),
- Skip nonce enforcement/increment (state nonce is never checked or updated for this path, enabling unlimited repeated forged bootstrap declares for new class hashes),
- Skip fee charging (declare a class completely for free).

This constitutes unauthorized account action (a "pseudo-account" acting without any credential) that lets attackers permanently and repeatedly bypass the declare fee market and consume gateway/sequencer CPU resources (Sierra→CASM compilation, class-hash computation) for free, and, because the class-declaration write is a genuine committed state change (`contract_class_changes` dict update / `compiled_class_hashes` state diff), it also corrupts the intended fee-for-declare economic model of the network — a concrete loss-of-funds-equivalent condition (unpaid resource consumption charged to no one) as well as unauthorized account action from an address nobody controls.

### Likelihood Explanation
High. No cryptographic material, special privilege, or genesis-only condition gates this path in the reachable production code — an attacker only needs to know the well-documented constant `bootstrap_address()` (visible directly in the open-source code) and construct the required transaction fields, all of which are attacker-controlled inputs to `add_tx`/`Declare` submission. The default gateway configuration (`authorized_declarer_accounts: None`) does not block it.

### Recommendation
Do not derive the bootstrap-declare authorization solely from transaction-supplied fields. Instead:
1. Gate the bootstrap fast-path on actual chain state (e.g., only permit it when the target class-hash's declaration slot is empty **and** the current block number/state indicates genesis/bootstrap phase), rather than trusting the transaction's self-reported `sender_address`/`nonce`/fee fields.
2. Alternatively, require the bootstrap declare to be injected only through a trusted, non-p2p, operator-controlled channel (e.g., a dedicated genesis-block-building API) rather than being reachable via the normal `add_tx` gateway path from arbitrary untrusted senders.
3. Add an explicit configuration/one-shot flag that disables acceptance of `sender_address == bootstrap_address()` transactions once the chain has left the genesis/bootstrap phase, and audit the duplicate logic in the Starknet OS Cairo program (`transaction_impls.cairo`) for the same fix, since re-execution/proving must stay consistent with the sequencer's decision.

### Proof of Concept
1. Attacker crafts an `RpcDeclareTransaction::V3` (or `DeclareTransactionV3`) with:
   - `sender_address = DeclareTransaction::bootstrap_address()`
   - `nonce = Nonce(Felt::ZERO)`
   - `signature = TransactionSignature::default()` (empty/unsigned)
   - `resource_bounds` set so `enforce_fee` evaluates to `false` (e.g. `AllResourceBounds::new_unlimited_gas_no_fee_enforcement()`), matching the pattern used in `generate_bootstrap_declare()`: [7](#0-6) 
   - `class_hash`/`compiled_class_hash` for any Sierra contract class the attacker wants declared for free.
2. Attacker submits this transaction to the gateway's `add_tx` endpoint (no `authorized_declarer_accounts` restriction by default).
3. `AccountTransaction::execute_raw` detects `tx.is_bootstrap_declare(charge_fee=false) == true` and executes `run_execute` directly — bypassing `perform_pre_validation_stage` (nonce/fee checks) and `run_or_revert` (signature validation) — successfully declaring the class with zero fee and no valid signature.
4. Because the state nonce for the bootstrap address is never touched, the attacker can repeat step 1–3 for any number of distinct classes indefinitely, at any block height, not just at genesis.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

        // Do not run validate or perform any account-related actions for declare transactions that
        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
            }
