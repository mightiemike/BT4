### Title
PoisonMicroblock accepted for non-conflicting, sequential microblocks — no fork check between `mblock_header_1` and `mblock_header_2` - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`check_microblock_header_signer` only verifies that the two supplied microblock headers recover to the *same* public key hash; it never verifies that the headers actually conflict (i.e., that they are two different, competing headers at the *same* sequence position). `handle_poison_microblock` then uses `mblock_header_1.sequence` directly as the "fork point" without ever comparing it to `mblock_header_2.sequence` or checking that the header contents diverge. As a result, any two legitimately-produced, non-forked microblocks from an honest miner's normal, sequential microblock stream (e.g. sequence 5 and sequence 9) satisfy the acceptance check, letting an unprivileged reporter claim a poison-microblock slash/reward without any actual equivocation.

### Finding Description
The broken equality: "reward paid" should equal "exactly one valid double-signature (two headers with the *same* sequence number but different content) by the slashed miner," but the code allows reward payment for "any two headers signed by the same key," including headers at different sequence numbers with no conflict at all.

Code path:
- `check_microblock_header_signer` (stackslib/src/chainstate/stacks/db/transactions.rs:686-713) recovers `pkh1` and `pkh2` via `check_recover_pubkey()` and only asserts `pkh1 == pkh2`. There is no assertion that `mblock_hdr_1.sequence == mblock_hdr_2.sequence`, and no assertion that the two headers are actually distinct/conflicting (e.g., different block hashes at the same sequence). [1](#0-0) 
- `handle_poison_microblock` (lines 722-883) calls this check, then unconditionally treats `mblock_header_1.sequence` as the reported fork sequence and records it via `insert_microblock_poison`, again without ever reading or comparing `mblock_header_2.sequence`. [2](#0-1) 

Because a single miner signs every microblock in a tenure with the same microblock signing key, *every* pair of microblocks in that miner's entire honest, non-forked stream will pass `pkh1 == pkh2`. An attacker (any address able to submit a Stacks transaction) can pick any two ordinary, sequential microblock headers the miner legitimately produced (e.g., at sequence 5 and sequence 9), package them as a `PoisonMicroblock` payload, and have `handle_poison_microblock` accept them as proof of equivocation — even though the miner never signed two conflicting microblocks at the same position.

No other guard in the reachable path (`process_transaction` → `run_poison_microblock` → `handle_poison_microblock`) checks sequence equality or header divergence before this point; the only gates are the same-height/maturity check (`get_microblock_pubkey_hash_height` + `MINER_REWARD_MATURITY` comparison) and the "already reported" check, neither of which validates that the two headers actually represent a fork.

### Impact Explanation
This is a reward-mispayment/miner-slashing bug bounded to the punished miner's coinbase/commission: an honest miner who never equivocated has their coinbase diverted to an unrelated, unprivileged "reporter" who merely resubmitted two of the miner's own valid, sequential microblock headers. This matches the "poison or reward mis-payment" High-severity category (it does not cause a chain split or unrecoverable state-root divergence, since all honest nodes apply the same faulty logic deterministically and agree on the outcome, but it does result in wrongful reward transfer/miner slashing without cause). The attack is repeatable against every honest miner tenure that produces at least two microblocks, at zero cost beyond a normal transaction fee.

### Likelihood Explanation
Preconditions are trivial and match ordinary, expected chain operation: any tenure where the miner produces two or more microblocks signed with the same microblock private key (the normal case). The attacker needs no special stake, no BTC operations, no majority position — only the ability to observe two of the miner's already-broadcast microblock headers (public information) and submit a standard `PoisonMicroblock` transaction. This is fully within the unprivileged-reporter threat model defined in the rules and is trivially and repeatably exploitable against any active miner.

### Recommendation
In `check_microblock_header_signer` (or in `handle_poison_microblock` immediately after it), additionally require:
1. `mblock_hdr_1.sequence == mblock_hdr_2.sequence` (the whole premise of Poison-microblock is that the miner signed two competing headers at the same position in the microblock stream), and
2. The two headers are not identical (e.g., compare block hashes/signatures) so that a header can't be "poisoned" against a copy of itself.
Reject the transaction with `InvalidStacksTransaction` if either check fails.

### Proof of Concept
Rust integration test plan (chainstate/stacks/db/transactions.rs or an integration test module):
1. Boot a test chainstate; have a miner produce a tenure containing at least microblocks at sequence 0..9, all signed with the same microblock private key, with no equivocation (ordinary linear stream).
2. Extract `mblock_header_at_seq_5` and `mblock_header_at_seq_9` from the confirmed stream (assert `header_5.sequence == 5`, `header_9.sequence == 9`, and that both `check_recover_pubkey()` return the same `Hash160`, confirming the "same signer" precondition but explicitly asserting `header_5.sequence != header_9.sequence`, i.e., the broken equality: NOT `(header_5.sequence == header_9.sequence)`).
3. Construct and submit a `PoisonMicroblock(header_5, header_9)` transaction from an unprivileged reporter account.
4. Run `process_transaction` → confirm `handle_poison_microblock` returns `Ok(...)` (no error), and `get_poison_microblock_report` returns `Some((reporter, 5))`.
5. Assert that the miner's mature coinbase reward is diverted/slashed in favor of the reporter's account despite no fork/equivocation having occurred, proving reward theft under the stated precondition of an honest, non-forked miner tenure.

    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
