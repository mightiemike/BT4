## Title
Griefing DoS in TRC10 asset‑issuance participation via front‑run drain of issuer's remaining token balance - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
`ParticipateAssetIssueActuator` computes the amount of TRC10 tokens a participant will receive from a fixed exchange ratio and then unconditionally requires the issuer's ("to") account to hold at least that many tokens, both at `validate()` time and again at `execute()` time. Any anonymous account can submit its own minuscule `ParticipateAssetIssueContract` transactions against the same issuer to shrink the issuer's remaining token balance immediately before a victim's already-broadcast, larger participation transaction is processed, causing the victim's transaction to fail with `ContractExeException`/`ContractValidateException`. This mirrors the reported bug class: a strict "amount must not exceed remaining shared balance" check that lets a low-cost attacker force an otherwise-valid transaction to revert.

### Finding Description
In `validate()`, the exchange amount is computed from a fixed ratio (`num`/`trxNum`) and TRX `amount`, and the issuer account (`toAccount`) must have enough of the asset: [1](#0-0) 

The same check is repeated (non‑atomically with the mempool state) in `execute()`, where the actual token transfer occurs: [2](#0-1) 

`reduceAssetAmountV2` on the issuer account simply returns `false` if the current balance is less than the requested amount, with no partial-fulfillment path: [3](#0-2) 

Because `AssetIssueCapsule` supply held by the issuer (`toAccount`) is a single shared mutable value, any anonymous account can submit its own `ParticipateAssetIssueContract` transaction referencing the same asset. If an attacker observes a victim's pending, not-yet-mined participation transaction in the mempool (which reveals the intended `amount`/`exchangeAmount` since the exchange ratio is public asset metadata), the attacker can submit one or more transactions ahead of it that reduce the issuer's remaining balance by just enough so that the victim's computed `exchangeAmount` (line 77-78/184-185) no longer fits, causing `Asset balance is not enough !` (validate) or `reduceAssetAmount failed !` (execute, wrapped in `ContractExeException`) — see the exact revert paths exercised by the existing test suite: [4](#0-3) 

The attacker's cost is minimal: `calcFee()` for this actuator returns `0`, so the only cost to the griefer is bandwidth/energy for a trivial-value transaction: [5](#0-4) 

### Impact Explanation
An attacker can repeatedly and cheaply cause a victim's `ParticipateAssetIssueContract` transaction to be rejected/reverted during an active TRC10 crowdsale, denying the victim the ability to participate in the sale (a form of griefing/DoS analogous to the reported `repay`/`liquidate` reversion attack). Unlike ordinary exhaustion of a finite supply (which is expected market behavior), here the attacker only needs to shave a small, targeted amount off the issuer's remaining balance to invalidate one specific victim transaction, and can repeat this cheaply as long as the sale (time window) remains open and supply remains above zero. No funds are irrecoverably lost by the victim (the balance debit only becomes persistent after the token credit succeeds, since `accountStore.put` calls occur only after `reduceAssetAmountV2` succeeds), but the victim's transaction is denied service and their broadcast fee/energy for the failed attempt is wasted.

### Likelihood Explanation
Exploitation requires only visibility into the (public, unencrypted) mempool for the victim's pending transaction, and the ability to submit ordinary, unprivileged transactions ahead of it — the same MEV precondition the original report's judge explicitly accepted as valid ("the attack vector includes MEV as a necessary condition"). No special privileges, leaked keys, or malicious node behavior are required, only normal broadcast-transaction capability during an open asset-issuance window.

### Recommendation
Avoid all-or-nothing reverts driven by a shared, externally-drainable balance. Options include: (1) cap the participant's `exchangeAmount`/`cost` to the issuer's currently available balance and refund/return the excess TRX rather than reverting the whole transaction, or (2) reserve/lock supply per pending transaction is not feasible on-chain, so at minimum surface a clear, non-punishing failure mode (e.g., partial fill) instead of a hard revert, mirroring how `MarketSellAssetActuator.matchSingleOrder` already handles partial fills gracefully instead of reverting.

### Proof of Concept
1. Issuer creates a TRC10 asset issuance with a limited remaining token balance `R` and exchange ratio `num`/`trxNum`.
2. Victim broadcasts `ParticipateAssetIssueContract(amount = A)` expecting `exchangeAmount = A * num / trxNum <= R`.
3. Attacker observes the pending victim transaction in the mempool, computes the same `exchangeAmount`, and broadcasts (at higher fee/priority, or via any block-inclusion-ordering advantage) a `ParticipateAssetIssueContract(amount = a)` for the same asset such that after processing, remaining balance `R' = R - a' < exchangeAmount` (where `a'` is the attacker's own consumed share).
4. When the victim's transaction is processed, `validate()`/`execute()` re-check `toAccount.assetBalanceEnoughV2(...)` against the now-reduced balance and throw `ContractValidateException("Asset balance is not enough !")` or `ContractExeException("reduceAssetAmount failed !")`, as demonstrated by the existing unit tests at `framework/src/test/java/org/tron/core/actuator/ParticipateAssetIssueActuatorTest.java` (`sameTokenNameCloseNotEnoughAssetTest`, `sameTokenNameOpenNotEnoughAssetTest`).
5. Attacker repeats this with negligible-cost transactions (`calcFee()` = 0) each time the victim retries, denying the victim's participation indefinitely while the sale window remains open.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
