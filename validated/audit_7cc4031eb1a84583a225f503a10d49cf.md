## Title
Unchecked subtraction in `AccountsDb::generate_index` can underflow `accounts_data_len` and panic the validator during snapshot-based startup index generation - (`accounts-db/src/accounts_db.rs`)

### Summary
`AccountsDb::generate_index()`, executed when a validator rebuilds its accounts index from a snapshot at startup, computes `total_accum.accounts_data_len -= accounts_data_len_from_duplicates;` using plain unchecked subtraction on `u64` values, unlike the structurally identical capitalization computation two lines above it, which uses `checked_sub(...).expect(...)`.

### Finding Description
During index generation, `total_accum.accounts_data_len` is accumulated (in `hash_storage_info`/`IndexGenerationAccumulator::accumulate`) by summing the data length of every non-zero-lamport account across every processed slot, including all duplicate (older) versions of a pubkey that appear in multiple rooted slots. [1](#0-0) 

Separately, `visit_duplicate_pubkeys_during_startup` walks the *duplicate* (non-max-slot) entries for each pubkey and sums their data length into `accounts_data_len_from_duplicates`, so that the true accounts_data_len can be recovered by subtracting the duplicate contributions from the total. [2](#0-1) 

The subtraction step for capitalization is protected with `checked_sub(...).expect("capitalization cannot underflow")`, but the immediately following `accounts_data_len` subtraction is a bare `-=` with no checked arithmetic and no invariant assertion: [3](#0-2) 

This is structurally the same bug class described in the external report: two independently accumulated quantities are subtracted with an implicit assumption that the left-hand side is always ≥ the right-hand side, with no defensive check. If that invariant is ever violated — e.g., due to a discrepancy between how "duplicate" data length is filtered (`lamports > 0` check in `visit_duplicate_pubkeys_during_startup`) versus how the original data length was accumulated (`is_account_zero_lamport` check in `hash_storage_info`), or due to any future refactor that changes one path but not the other — the subtraction underflows a `u64`. In a build with overflow checks enabled (debug builds, and CI/test builds; also any build compiled with `overflow-checks = true`), this triggers an immediate panic and crash. Even in an optimized build without overflow checks, the wrap-around would silently corrupt `accounts_data_len`, which is later used to seed `IndexGenerationInfo::accounts_data_len` and drives the bank's on-chain accounts-data-size accounting. [4](#0-3) 

Note: I could not locate an explicit Cargo profile setting `overflow-checks = true`/`false` for the production release profile within the indexed portion of the repo, so I cannot confirm with certainty whether release validator binaries panic on this underflow or silently wrap. Either outcome is a legitimate defect (crash vs. silent state corruption), but the exact runtime behavior in the shipped release binary is unverified due to indexing limits.

### Impact Explanation
`generate_index()` runs on every validator startup that loads state from an accounts snapshot (normal restart/bootstrap path), not just malicious snapshots. A validator that unexpectedly panics here would be unable to complete startup, causing a denial of service on that node. If, instead, the release build wraps silently, `accounts_data_len` (which is later fed into `IndexGenerationInfo` and compared/used against the bank's `accounts_data_len` invariant) would become a huge incorrect `u64` value, potentially causing the subsequent "verify accounts data size" or downstream size-limit checks to behave incorrectly — a state divergence between the honest snapshot and the replayed index. This matches the category of "honest-node snapshot-vs-replay mismatch" or "node panic" called out as in-scope impacts.

### Likelihood Explanation
The likelihood of the *exact* invariant violation firing under current, correct duplicate-detection logic is low under normal operation, because the two computations (`hash_storage_info`'s zero-lamport filter and `visit_duplicate_pubkeys_during_startup`'s `lamports > 0` filter) are intended to be consistent. However, unlike the capitalization computation, this specific subtraction has zero defensive tooling (no `checked_sub`, no assertion, no test coverage found for the underflow case), so any future code change to either accumulation path (which happens in active development, as evidenced by the surrounding `obsolete_accounts`/tombstone/ZLSR logic being recently added) can silently reintroduce a real underflow with no compiler or test signal, unlike the parallel capitalization path which is explicitly guarded and has dedicated overflow tests (`test_calculate_capitalization_overflow_intra_slot`, `test_calculate_capitalization_overflow_inter_slot`). [5](#0-4) 

### Recommendation
Make the `accounts_data_len` subtraction consistent with the capitalization subtraction immediately preceding it:
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```
This makes the invariant explicit, produces a clear diagnostic panic message instead of a generic arithmetic-overflow panic (or silent wraparound in release builds), and matches the existing defensive pattern already used for `capitalization` in the same function.

### Proof of Concept
A concrete runtime PoC could not be constructed from static analysis alone, since triggering the underflow requires making `accounts_data_len_from_duplicates` (sum of duplicate accounts' data lengths with `lamports > 0`) exceed `total_accum.accounts_data_len` (sum of all non-zero-lamport accounts' data lengths across all slots) — under the current, consistent filtering logic in both accumulation paths, this should not currently occur. The vulnerability is therefore a code-level defect (missing checked arithmetic on an unverified cross-thread invariant) reachable through the normal `generate_index()` startup path, rather than a demonstrated externally-triggerable underflow in the current logic. A Devin agent with terminal/test access would be needed to add a unit test that intentionally injects an inconsistency between the two data-length accumulation paths (e.g., via a mocked/duplicated slot with a mismatched zero-lamport boundary condition) to confirm whether the panic is reachable, and to verify the fix.
