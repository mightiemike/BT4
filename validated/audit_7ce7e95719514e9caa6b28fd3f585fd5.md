Confirmed: there is no test case (and no code path) validating that the `shop` parameter passed to `tokenExchange()` matches the `dest`/`iss` claim inside the decoded `sessionToken`. The function decodes the token purely to verify its signature/expiry/audience, discards the payload, and then independently sanitizes and uses the caller-supplied `shop` string to build the outbound request URL and to derive `cleanShop` used in the returned `Session`.

### Title
Missing binding between session-token identity and `shop` parameter in `tokenExchange` allows cross-tenant token/session creation - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`tokenExchange()` accepts two independent, caller-supplied inputs — `sessionToken` and `shop` — and never verifies that they refer to the same store. This mirrors the root cause of the referenced H-01 finding: a privileged action (minting a session/access token) is triggered based on an unrelated piece of state/input that is trusted without being cryptographically bound to the actor performing the request, letting the caller attach one party's proof-of-identity to another party's resource.

### Finding Description
`tokenExchange` calls `decodeSessionToken(config)(sessionToken)` only to validate the JWT's signature, expiry and audience, but the returned payload (which contains `dest`, the shop the token was actually issued for) is discarded: [1](#0-0) 

The function then independently sanitizes the caller-supplied `shop` argument and uses it to build the outbound Shopify OAuth token-exchange request URL, and later constructs the returned `Session` for that same `cleanShop`: [2](#0-1) [3](#0-2) 

Nothing in `tokenExchange` cross-checks `payload.dest`/`payload.iss` against the `shop` parameter. The existing test suite exercises only the case where `shop` matches the token's `dest`, and separately the case of a malformed shop string (`InvalidShopError`) — there is no test, and no code, asserting that a session token issued for shop A is rejected when combined with `shop = B`: [4](#0-3) [5](#0-4) 

By contrast, `shopify-app-express`'s middleware wrapper does derive `shop` safely from the decoded payload's `dest` rather than from request input before calling the exchange helper: [6](#0-5)  — but this safety is only enforced by that one caller's convention, not by the `tokenExchange` API itself. The library's own documentation explicitly shows `shop` being taken from `req.query.shop` (attacker-controllable) independently of the session token: [7](#0-6)  This is a foot-gun API shape: any integrator (or a future/alternate framework adapter) that follows the documented pattern of sourcing `shop` from the query string, and passes it alongside a validly-decoded session token, will not have the mismatch caught by the library.

### Impact Explanation
If an app (or a Shopify framework adapter) trusts a request-supplied `shop` value together with a token that only proves the caller's identity/session on a *different* shop, `tokenExchange` will still issue a POST to `https://{attacker-chosen-shop}/admin/oauth/access_token` using the victim/attacker's own valid session token as `subject_token`. Whether this results in actual cross-tenant token issuance depends on Shopify's server-side enforcement of `dest`/audience matching, but the client-side library provides zero defense-in-depth here — the exact analog of the reported bug: a resource-affecting call proceeds based on attacker-supplied state without binding it to the verified identity.

### Likelihood Explanation
Requires only an unprivileged single merchant/user obtaining their own valid session token and invoking `tokenExchange` with an arbitrary `shop` string — reachable from any HTTP request to an app route that forwards `req.query.shop` as documented. Exploitability of the ultimate impact hinges on Shopify's backend cross-checking token audience/dest against the requested shop, which is outside this repo's control, so this is reported as a missing defense-in-depth / API misuse-prevention gap rather than a confirmed full compromise.

### Recommendation
Inside `tokenExchange`, after decoding the session token, assert that the token's `dest` (normalized) equals the sanitized `shop` parameter, and throw (e.g. `InvalidJwtError`/`InvalidOAuthError`) on mismatch — analogous to binding an action strictly to the authenticated party rather than to unrelated caller-supplied state:
```ts
const payload = await decodeSessionToken(config)(sessionToken);
const cleanShop = sanitizeShop(config)(shop, true)!;
if (new URL(payload.dest).hostname !== cleanShop) {
  throw new ShopifyErrors.InvalidJwtError('Session token does not match shop');
}
```

### Proof of Concept
1. Attacker has a valid, unexpired session token for `attacker-shop.myshopify.io` (obtained legitimately as an installed-app user on their own store).
2. Attacker (or a vulnerable app route following the documented pattern) calls `shopify.auth.tokenExchange({ shop: 'victim-shop.myshopify.io', sessionToken: attackerToken, requestedTokenType: OfflineAccessToken })`.
3. `decodeSessionToken` succeeds (signature/expiry/audience are all valid — it's the attacker's own legitimately-issued token), see [8](#0-7) .
4. `tokenExchange` proceeds to POST to `https://victim-shop.myshopify.io/admin/oauth/access_token` with `subject_token = attackerToken`, and — if Shopify's backend accepted it — would create and return a `Session` object scoped to `victim-shop.myshopify.io` per [9](#0-8) , which the app would then store/use as if it were the victim shop's authenticated session.

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );
