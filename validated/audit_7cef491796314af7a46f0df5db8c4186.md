This confirms the finding: `DeductGasFeesFromReceipt` is the deliberate, protocol-wide invariant that every user-derived `DerivedEVMCall` (payload execution) must be paired with, and it's even wrapped in a `CacheContext` in the `ExecutePayload`/`ExecutePayloadV2`/inbound-execution paths specifically to close a documented "free-execution gap" (see the `F-2026-16738` test comment) when the recipient has no native `upc` to pay. `MsgMigrateUEA`'s keeper handler (`x/uexecutor/keeper/msg_migrate_uea.go`) is architecturally identical (real EVM tx from a user-derived `evmFrom`, `gasless=false` at the `DerivedEVMCall` layer) but never calls `DeductGasFeesFromReceipt` at all — the exact same "one path bills, the sibling path silently skips it" defect pattern as the LES bug.

### Title
Free, unbilled EVM execution via `MsgMigrateUEA` — gas-accounting bypass on a gasless, user-reachable message - (File: x/uexecutor/keeper/msg_migrate_uea.go)

### Summary
`MsgMigrateUEA` triggers a real, state-changing `DerivedEVMCall` (`CallUEAMigrateUEA`) from a user-derived EVM address, exactly like `MsgExecutePayload`. Every other path that performs this pattern (`ExecutePayload`, `ExecutePayloadV2`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`) always calls `k.DeductGasFeesFromReceipt(...)` after the call — in fact recent hardening (`F-2026-16738`) wrapped that pairing in a `CacheContext` specifically to close a "free execution" gap. `keeper.MigrateUEA` never calls `DeductGasFeesFromReceipt`, so this one message type performs real EVM computation that is never billed to anyone.

### Finding Description
`MsgMigrateUEA` is registered in `x/uexecutor`'s `MsgServer` (`x/uexecutor/keeper/msg_server.go:57-70`) and is on the gasless-Cosmos-fee whitelist (`app/txpolicy/gasless.go:18`), so the Cosmos-level tx fee is already zero for any signer. The handler `keeper.MigrateUEA` (`x/uexecutor/keeper/msg_migrate_uea.go:15-84`) resolves the UEA and calls: [1](#0-0) 
No subsequent call to `k.DeductGasFeesFromReceipt` exists anywhere in this function or its caller (`msgServer.MigrateUEA`, `x/uexecutor/keeper/msg_server.go:57-70`).

Compare with the canonical pattern in `ExecutePayload` (same file structure, same `CallUEA*` call shape): [2](#0-1) 
and the even stricter `ExecutePayloadV2` variant that additionally wraps both calls in a `CacheContext` so a failed fee deduction rolls back the EVM state: [3](#0-2) 

`CallUEAMigrateUEA` (`x/uexecutor/keeper/evm.go:196-227`) passes `gasless=false` to `DerivedEVMCall` with the same inline rationale used everywhere else ("we need gas to be emitted in the tx receipt"), confirming the receipt's `GasUsed` is meant to be read back and billed — the billing step was simply never wired up for this message.

The README (`x/uexecutor/README.md:207`) states "There used to be a separate `MsgMigrateUEA` message; that path has been removed," but the proto (`proto/uexecutor/v1/tx.proto:86-105`), the gRPC service (`api/uexecutor/v1/tx_grpc.pb.go:225-241`), the `MsgServer` interface/impl, and the gasless whitelist all still wire it live — this is a stale doc pointing at dead documentation, not a removed code path, so the message remains fully reachable by any unprivileged account.

### Impact Explanation
Any account holding a deployed UEA (or any account with `VerificationData` that recovers to a UEA it controls) can submit `MsgMigrateUEA` for free (gasless Cosmos fee) and force real EVM computation (the UEA's `migrateUEA` entrypoint) with zero `upc` billed for the EVM gas consumed, unlike every other equivalent execution path in the module. This breaks the "gas fee accounting" invariant the module otherwise enforces uniformly, and is an unprivileged, network-independent resource-exhaustion vector: an attacker can repeatedly submit valid self-signed `MsgMigrateUEA` transactions (bounded only by contract-level nonce/deadline checks inside the UEA, which the attacker fully controls since they sign their own payload) to drive real, uncompensated EVM state-changing computation, consuming node CPU/storage resources without paying gas — a non-network-level DoS/resource-drain reachable without any privileged control, matching the in-scope "denial of service...not network-level and...reachable without privileged control" and "corruption of...gas fee accounting" impact categories.

### Likelihood Explanation
High. No special conditions are needed: the message is on the public gasless whitelist, requires only a self-controlled UEA and a validly signed migration payload (which the caller can produce for their own UEA at will), and every code path is exercised by a single `MsgMigrateUEA` submission. No validator collusion, no privileged role, and no race condition is required.

### Recommendation
Add the identical `DeductGasFeesFromReceipt` call (ideally within a `CacheContext`, mirroring `ExecutePayloadV2`'s F-2026-16738 hardening) to `keeper.MigrateUEA` immediately after `CallUEAMigrateUEA`, so migration gas is billed to the UEA exactly like payload execution. Alternatively, if `MsgMigrateUEA` is truly meant to be a dead/removed path (per the README), remove it from the `MsgServer`, the gasless whitelist, and the proto surface so it cannot be invoked at all — leaving it registered but unbilled is the actual defect.

### Proof of Concept
1. Deploy a UEA for an attacker-controlled origin account via the normal `MsgExecutePayload`/auto-deploy flow.
2. Construct a valid `MigrationPayload` + `Signature` that the UEA's `migrateUEA` entrypoint will accept (attacker signs with their own owner key — no privileged data required).
3. Submit `MsgMigrateUEA{Signer: any_funded_or_unfunded_account, UniversalAccountId: <attacker's UA>, MigrationPayload, Signature}`. The Cosmos tx costs nothing (gasless whitelist), and `keeper.MigrateUEA` executes `CallUEAMigrateUEA` as a real, receipted EVM transaction.
4. Observe: unlike `MsgExecutePayload` against the same UEA (which triggers `DeductGasFeesFromReceipt` and visibly debits the UEA's `upc` balance — see `x/uexecutor/keeper/msg_execute_payload.go:91`), the UEA's `upc` balance is unchanged after `MsgMigrateUEA` despite `receipt.GasUsed > 0`, confirming the EVM computation was performed with no corresponding fee accounting.
