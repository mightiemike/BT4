### Title
`ensure_match_transaction_info` skips validating `position_state_checkpoint_hash`/hot-state checkpoint hashes, allowing replay-verify to accept a divergent trading-native state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single invariant that binds a locally re-executed `TransactionOutput` to the authenticated `TransactionInfo` (which is itself proven against the accumulator/`LedgerInfo`). It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check the state-checkpoint hashes carried in `TransactionInfo` — specifically the (hot-)state checkpoint hash and the new `position_state_checkpoint_hash` used by the "trading-native" position Merkle tree. This is called out by an unresolved `TODO(trading-native)` comment in the function itself.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  verifies status, gas used, write-set hash and event-root hash against the authenticated `txn_info`, but the function ends with an explicit acknowledgement that it does not verify the checkpoint hashes: [2](#0-1) 

This function is the authoritative "did local execution reproduce the committed/authenticated ledger state" check used by replay/verify tooling. It is invoked directly by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which re-executes historical transactions and calls `ensure_match_transaction_info` per transaction to decide whether replay succeeded or diverged: [3](#0-2) 

Because the comparator never touches the position/hot-state checkpoint hash fields, `replay_on_archive` (and any other caller relying on this same function to assert VM-output correctness) will report success even when the locally computed Jellyfish-Merkle root for the native "position" state subsystem (or the hot-state root) differs from the value that is actually bound into the authenticated `TransactionInfo`/accumulator. The `TransactionInfo`/checkpoint-hash plumbing for this subsystem already exists elsewhere in the codebase (`execution/executor-types/src/state_checkpoint_output.rs`, `execution/executor/src/workflow/do_ledger_update.rs`, `execution/executor/src/chunk_executor/mod.rs`, `state-sync/state-sync-driver/src/bootstrapper.rs` all reference `position_state_checkpoint_hash`), confirming this is a real, wired-in field on the committed `TransactionInfo`, not a dead/unused one — it is simply excluded from this particular verification routine.

### Impact Explanation
This breaks the proof/replay-binding invariant: "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged," specifically for the position/hot-state root component of `TransactionInfo`. A wrong committed position-state root (e.g., produced by a buggy or malicious hot-state/position-Merkle implementation, or by state corruption during restore) would not be caught by replay-verify, which is a primary integrity backstop used to detect exactly this class of divergence. This matters for hard-fork-only divergence detection and for authenticated proof binding of the position state root — replay tooling would falsely certify a corrupted ledger state as correct.

However, the actual severity is gated by whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (an on-chain feature flag, referenced in `types/src/on_chain_config/aptos_features.rs`, `aptos-move/framework/move-stdlib/sources/configs/features.move`, `storage/aptosdb/src/db/aptosdb_reader.rs`, `storage/aptosdb/src/db/aptosdb_writer.rs`) is currently enabled on mainnet. The comment itself says the checkpoint hashes must be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying this is a known, tracked gap that the team intends to close prior to activating the feature. I was not able to conclusively determine from the available index whether this flag is already active on mainnet or still pending — that would need to be checked directly (e.g., via `aptos-move/aptos-release-builder/src/components/feature_flags.rs` or on-chain feature state) in a live session.

### Likelihood Explanation
This is not a privileged/attacker-triggered bug in the classic sense — it is a missing-check gap in verification tooling. Likelihood of it mattering depends entirely on (a) `COMPUTE_TRADING_NATIVE_STATE_ROOTS` being enabled and (b) some other bug or storage corruption actually causing the position/hot-state root to diverge from correct VM execution. The finding is best characterized as a proof/verification-integrity gap that silently widens the blast radius of any future divergence in that specific state root, rather than an exploitable primitive on its own. The code explicitly flags this as unresolved via the `TODO(trading-native)`, so the root cause is confirmed and un-mitigated in this snapshot of the repo.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to also compare the state/hot-state checkpoint hash and `position_state_checkpoint_hash` (when present, e.g. as a checkpoint transaction or under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) against locally recomputed values, mirroring the write-set/event-root checks already present. Do this before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network, and add regression tests in `storage/db-tool/src/replay_on_archive.rs` that intentionally corrupt the position state root to confirm replay-verify now fails.

### Proof of Concept
Conceptual (verification-gap) PoC, since this is a missing-check rather than a directly triggerable state corruption:
1. Enable/simulate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and produce a `TransactionInfo` whose `position_state_checkpoint_hash` (or hot-state checkpoint hash) does not match the actual position Merkle root computed from the transaction's true state effects (e.g., by feeding replay tooling a corrupted/incorrect checkpoint hash while keeping write_set/events/gas/status identical).
2. Run `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which calls `ensure_match_transaction_info` per transaction [4](#0-3) .
3. Observe that replay succeeds (no error returned) because `ensure_match_transaction_info` never checks the checkpoint hash fields, despite the position-state root being wrong — demonstrating that the tool cannot detect this specific class of state-commitment divergence.

            version,
            self.gas_used(),
            txn_info.gas_used(),
        );
