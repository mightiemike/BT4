### Title
Disabling shielded transactions via committee proposal permanently locks users' funds in the shielded pool - ([File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java])

### Summary
`ShieldedTransferActuator.validate()` gates **every** shielded operation type (deposit/MINT, TRANSFER, and withdrawal/BURN) behind a single global switch, `dynamicStore.supportShieldedTransaction()`. When the committee sets `ALLOW_SHIELDED_TRANSACTION` to `0` (e.g., in response to a discovered protocol issue), no user can perform any shielded transaction, including the operation that converts shielded notes back to a transparent public balance. Funds already committed to the shielded pool have no other exit path once this switch is off.

### Finding Description
The single validate() check does not distinguish between deposit-style operations (transparent → shielded) and withdrawal-style operations (shielded → transparent): [1](#0-0) 

```java
if (dynamicStore.getAllowSameTokenName() != 1) {
  throw new ContractValidateException("shielded transaction is not allowed before "
      + "ALLOW_SAME_TOKEN_NAME is opened by the committee");
}

if (!dynamicStore.supportShieldedTransaction()) {
  throw new ContractValidateException("Not support Shielded Transaction, need to be opened by"
      + " the committee");
}
```

This is analogous to the reported Superposition bug: `update_position_internal`'s documentation says the pool-disabled check should not gate liquidity removal, yet `update_position` applies the check unconditionally regardless of whether `delta` (add vs. remove) is positive or negative. Here, `ShieldedTransferActuator` applies the same "not supported" gate unconditionally regardless of whether the transaction is a deposit (transparent input → shielded note, at-risk funds increasing) or a withdrawal (shielded note being spent, value exiting the pool to a transparent address). There is no carve-out that would let a user redeem an existing shielded note (i.e., "remove liquidity" from the shielded pool) while the feature is toggled off.

Tests confirm the gate is unconditional for all transaction shapes (funding in, transfer within, and spend-out): [2](#0-1) 

Note this differs from the `allowShieldedTransactionApi` flag, which only gates convenience wallet/gRPC helper APIs and explicitly does **not** affect the on-chain actuator's `validate()` logic: [3](#0-2) 

That confirms `supportShieldedTransaction` (the `DynamicPropertiesStore`/committee-controlled parameter) is the actual on-chain enforcement point that blocks all shielded transactions, deposits and withdrawals alike, at the consensus level — this is the parameter analogous to the pool's "enabled" flag in the original report.

### Impact Explanation
If the committee disables `ALLOW_SHIELDED_TRANSACTION` (governance action, e.g. in response to an emergency such as a discovered cryptographic weakness or the historical Zcash-class counterfeiting risk that shielded pools are exposed to), any TRX or shielded TRC-20 value already held as unspent notes in the shielded pool becomes unspendable through this actuator: users cannot submit a BURN/withdraw-style `ShieldedTransferContract` to move their value back to a transparent, publicly-controlled address. This is the same class of impact called out in the original finding — an emergency-disable mechanism that should still allow users to exit with their funds instead traps them, directly contradicting the intent of an emergency pause (which is normally meant to prevent new risk exposure while still letting users withdraw what they already have).

### Likelihood Explanation
Disabling shielded transactions is a real, exercised governance lever in java-tron (`ALLOW_SHIELDED_TRANSACTION` proposal parameter, referenced in `ProposalUtil.java` and `DynamicPropertiesStore.java`), and the flag has historically been toggled on mainnet. The scenario (committee needs to react to a shielded-pool-related emergency by disabling shielded transactions) is realistic and directly mirrors the report's "problem occurs in the pool" premise. The unprivileged users impacted are anyone holding value in an unspent shielded note at the time the flag is turned off.

### Recommendation
Differentiate the validate() gate by transaction direction: continue blocking transactions that increase the amount of value held in the shielded pool (transparent→shielded deposits and MINT operations), but allow transactions whose net effect only spends existing shielded notes to a transparent output (BURN/withdraw), analogous to only checking pool-enabled state on liquidity increases and not decreases, as recommended in the original finding.

### Proof of Concept
1. Committee passes proposal setting `ALLOW_SHIELDED_TRANSACTION = 0`, calling `dynamicStore.saveAllowShieldedTransaction(0)`.
2. A user holding an existing unspent shielded note attempts to submit a `ShieldedTransferContract` with a spend description and a transparent output address (a withdrawal/burn), analogous to `shieldAddressToPublic()` in `ShieldedTransferActuatorTest`.
3. `ShieldedTransferActuator.validate()` reaches `if (!dynamicStore.supportShieldedTransaction())` at [4](#0-3)  and throws `ContractValidateException("Not support Shielded Transaction, need to be opened by the committee")`, exactly as demonstrated by `testCreateBeforeAllowZksnark`/`testBroadcastBeforeAllowZksnark` in [5](#0-4) .
4. The user's funds remain locked in the shielded pool with no alternative on-chain redemption path while the flag remains disabled.

  /**
   * Test that shielded transfer transaction validation works even when
   * allowShieldedTransactionApi is disabled. This verifies that the API flag
   * only gates wallet/helper APIs, not the core transaction validation logic.
   */
  @Test
  public void shieldedTransferValidationWorksWhenApiDisabled() {
    boolean orig = Args.getInstance().isAllowShieldedTransactionApi();
    // Disable the shielded API (this should NOT affect transaction validation)
    Args.getInstance().setAllowShieldedTransactionApi(false);

    dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
    dbManager.getDynamicPropertiesStore().saveTotalShieldedPoolValue(AMOUNT);

    try {
      ZenTransactionBuilder builder = new ZenTransactionBuilder(wallet);
      SpendingKey sk = SpendingKey.random();
      ExpandedSpendingKey expsk = sk.expandedSpendingKey();
      PaymentAddress address = sk.defaultAddress();
      Note note = new Note(address, AMOUNT);
      IncrementalMerkleVoucherContainer voucher = createSimpleMerkleVoucherContainer(note.cm());
      byte[] anchor = voucher.root().getContent().toByteArray();
      dbManager.getMerkleContainer()
          .putMerkleTreeIntoStore(anchor, voucher.getVoucherCapsule().getTree());
      builder.addSpend(expsk, note, anchor, voucher);

      addZeroValueOutputNote(builder);

      long fee = dbManager.getDynamicPropertiesStore().getShieldedTransactionCreateAccountFee();
      String addressNotExist =
          Wallet.getAddressPreFixString() + "8ba2aaae540c642e44e3bed5522c63bbc21f0000";

      builder.setTransparentOutput(ByteArray.fromHexString(addressNotExist), AMOUNT - fee);

      TransactionCapsule transactionCap = builder.build();
      Contract contract =
          transactionCap.getInstance().toBuilder().getRawDataBuilder().getContract(0);
      ShieldedTransferActuator actuator = new ShieldedTransferActuator();
      actuator.setChainBaseManager(dbManager.getChainBaseManager()).setContract(contract)
          .setTx(transactionCap);

      // Validation should succeed even when API is disabled
      actuator.validate();
    } catch (ContractValidateException e) {
      Assert.fail("Shielded transfer validation should not throw ContractValidateException: "
          + e.getMessage());
    } catch (Exception e) {
      Assert.fail("Shielded transfer should not throw Exception: " + e.getMessage());
    } finally {
      Args.getInstance().setAllowShieldedTransactionApi(orig);
    }
  }
