### Title
Missing voting-window enforcement lets stale/out-of-window votes set the aggregate public key in `signers-voting.clar` - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
`vote-for-aggregate-public-key` in `signers-voting.clar` defines an `is-in-voting-window` helper explicitly meant to gate when a signer vote is valid, but the public voting entry point never calls it. [1](#0-0)  As in the analog report (a "cooldown window" defined but not actually bound to the action that should be constrained by it), the check exists in the contract's source but is decoupled from the state-mutating function, so the window it was meant to enforce is effectively a no-op.

### Finding Description
`is-in-voting-window` is defined to restrict voting to signers of the *latest set* reward cycle and only while the burn height is within the prepare phase: [1](#0-0) 

However, `vote-for-aggregate-public-key`, the only public entry point that mutates `votes`, `tally`, `rounds`, `round-data`, and ultimately `aggregate-public-keys`, never invokes `is-in-voting-window`. Its actual guard set is: [2](#0-1) 

The only checks performed are: (1) the aggregate key hasn't already been approved for that `reward-cycle`, (2) the key is 33 bytes, (3) the key hasn't been used in a previous cycle, (4) the caller hasn't voted in that exact `(reward-cycle, round)` before, and (5) the round only increments by at most 1 relative to the last round recorded for that `reward-cycle`. None of these bind the vote to "am I in the prepare phase of `current-reward-cycle`, and is `reward-cycle` the one that was just set by `.signers`". A caller can pass an arbitrary `reward-cycle` argument (any past cycle that hasn't yet had a key approved, or a distant future cycle already assigned signer weights) at any burn height, so long as `get-signer-weight` (which looks up `.signers get-signer-by-index reward-cycle signer-index` and requires `tx-sender` to match) succeeds for that cycle.

This mirrors the structural flaw in the sNOTE report: a window-check function is written and clearly intended to gate an action, but the state-mutating call path bypasses it, letting the "vote" (analogous to "redeem") happen outside its intended window — including hopping between reward cycles the way the sNOTE report describes hopping between accounts to exploit disjoint redeem windows.

### Impact Explanation
If `vote-for-aggregate-public-key` can be called for a reward cycle before its intended voting window opens or after it "should" have closed, then:
- A minority of signers (well under the 70% consensus-threshold weight, since threshold enforcement itself is intact) could not unilaterally set the key — the `threshold-consensus` (70%) check on `new-total >= threshold-weight` still gates the actual `map-insert aggregate-public-keys` write.
- But because there's no enforcement that votes for reward-cycle N only happen during N's prepare phase, votes cast far outside the intended window (e.g., very early, before all signers have even seen the `.signers` set finalized for that cycle, or replayed against a still-open cycle after the "round" bookkeeping should have closed) could let an atypical/incomplete set of signer weights reach threshold and lock in an aggregate key that the full signer set never had a coordinated opportunity to vote on within the proper window.
- This affects the aggregate public key used for the reward cycle's threshold signature scheme (Nakamoto block signing), a State value nodes rely on. If a divergent aggregate key is set due to out-of-window voting, this is a state-root/consensus-relevant value.

Given that the value-threshold gate (70% weight) is untouched, this is bounded to High rather than Critical: it does not allow a single minority actor to unilaterally forge state, but it does break the intended temporal binding between "the signer set that was established for reward cycle N" and "when votes for N's aggregate key are accepted," which is exactly the class of bug flagged in the source report (a cooldown/window defined but not actually enforced at the point of the sensitive action).

### Likelihood Explanation
Likelihood is moderate to low in practice: exploiting this still requires assembling ≥70% signer weight for a divergent key, which requires either an already-misbehaving/colluding majority (out of scope per the analog rules) or exploiting timing edge cases in cycle transition where the `.signers` map for a given `reward-cycle` is populated before or after the corresponding voting round the community expects. I was not able to fully verify from source alone in this pass whether `get-signer-weight`/`.signers get-signer-by-index` for a given `reward-cycle` returns a valid (i.e., committed) entry outside of that cycle's intended prepare-phase window — this would need checking `signers.clar`'s `get-signer-by-index`/`set-signer` logic, which I was unable to fetch in this session due to tool errors when reading `signers.clar` directly.

### Recommendation
Add an explicit `(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))` call inside `vote-for-aggregate-public-key`, binding every state-mutating vote to the same window semantics the read-only helper already encodes, rather than leaving the helper unused. Confirm via unit tests that votes submitted before or after the prepare-phase window for a given `reward-cycle` are rejected with `ERR_OUT_OF_VOTING_WINDOW`.

### Proof of Concept
1. Note that `ERR_OUT_OF_VOTING_WINDOW` (`u12`) is defined and referenced in the map-based check `(asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))`, but this only checks "has this cycle already been decided," not "are we in the correct window for this cycle." [3](#0-2) 
2. `is-in-voting-window` is defined but grep confirms it is referenced only in its own definition site and never called from `vote-for-aggregate-public-key` or any other public function in this file. [1](#0-0) 
3. Any signer with a valid index/weight entry for a `reward-cycle` (past or future, as long as no key has been approved yet for it) can call `vote-for-aggregate-public-key` at any burn height, accumulating tally weight toward `threshold-weight` for that cycle outside of the prepare-phase window the contract's own helper was designed to enforce. [4](#0-3) 

Note: I was unable to fully trace `signers.clar`'s `get-signer-by-index`/`get-last-set-cycle` implementation in this session due to a tool-call error, so I cannot definitively confirm whether the signer-weight lookup itself independently restricts `reward-cycle` to only the currently-active or next cycle. If it does not, the window bypass described above is directly exploitable as stated; if it does, the missing `is-in-voting-window` call is still dead/vestigial code representing an incomplete-refactor risk consistent with the analog bug class, but with a narrower practical impact. A Devin session with full repo access should confirm this by reading `stackslib/src/chainstate/stacks/boot/signers.clar` in full.

(define-public (vote-for-aggregate-public-key (signer-index uint) (key (buff 33)) (round uint) (reward-cycle uint))
    (let ((tally-key {reward-cycle: reward-cycle, round: round, aggregate-public-key: key})
            ;; vote by signer weight
            (signer-weight (try! (get-signer-weight signer-index reward-cycle)))
            (new-total (+ signer-weight (default-to u0 (map-get? tally tally-key))))
            (cached-weight (try! (get-and-cache-total-weight reward-cycle)))
            (threshold-weight (get-threshold-weight reward-cycle))
            (current-round (default-to {
                votes-count: u0, 
                votes-weight: u0} (map-get? round-data {reward-cycle: reward-cycle, round: round})))
                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
        ;; Check that the aggregate public key is the correct length
        (asserts! (is-eq (len key) u33) (err ERR_ILL_FORMED_AGGREGATE_PUBLIC_KEY))
        ;; Check that aggregate public key has not been used in a previous reward cycle
        (asserts! (is-novel-aggregate-public-key key reward-cycle) (err ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY))
        ;; Check that signer hasn't voted in this reward-cycle & round
        (asserts! (map-insert votes {reward-cycle: reward-cycle, round: round, signer: tx-sender} {aggregate-public-key: key, signer-weight: signer-weight}) (err ERR_DUPLICATE_VOTE))
        ;; Check that the round is incremented by at most 1
        (try! (update-last-round reward-cycle round))
        ;; Update the tally for this aggregate public key candidate
        (map-set tally tally-key new-total)
        ;; Update the current round data
        (map-set round-data {reward-cycle: reward-cycle, round: round} {
            votes-count: (+ (get votes-count current-round) u1),
            votes-weight: (+ (get votes-weight current-round) signer-weight)})
        ;; Update used aggregate public keys
        (map-set used-aggregate-public-keys key reward-cycle)
        (print {
            event: "voted",
            signer: tx-sender,
            reward-cycle: reward-cycle,
            round: round,
            key: key,
            new-total: new-total,
        })
        ;; If the new total weight is greater than or equal to the threshold consensus
        (if (>= new-total threshold-weight)
            ;; Save this approved aggregate public key for this reward cycle.
            ;; If there is not already a key for this cycle, the insert will
            ;; return true and an event will be created.
            (if (map-insert aggregate-public-keys reward-cycle key)
                (begin
                    ;; Create an event for the approved aggregate public key
                    (print {
                        event: "approved-aggregate-public-key",
                        reward-cycle: reward-cycle,
                        round: round,
                        key: key,
                    })
                    true)
                false
            )
            false
        )
        (ok true)))
