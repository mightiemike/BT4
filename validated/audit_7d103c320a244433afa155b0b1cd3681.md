### Title
Idempotent promise handler permanently marks a failed `afterAuth` hook as "already run," silently skipping post-auth setup (e.g. webhook registration) on retry - ([File: packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts])

### Summary
`IdempotentPromiseHandler.handlePromise` records an identifier as "handled" **before** it knows whether the wrapped promise succeeds, and never clears that state on failure — only after a fixed 60-second TTL. This is structurally the same bug class as the reported `ContractWcFeeDistributor` issue: bookkeeping state (`s_validatorData.collateralReturnedCount` there, the `identifiers` map here) is updated unconditionally, regardless of whether the guarded operation actually completed successfully, so a failed attempt is treated as a completed one for a whole window of time.

### Finding Description
`isPromiseRunnable` inserts the identifier into the map *before* `promiseFunction()` runs, and `handlePromise` swallows nothing — but crucially, if `promiseFunction()` throws, the identifier is **not removed** from the map. It is only evicted once `Date.now() - date > IDENTIFIER_TTL_MS` (60 seconds) elapses: [1](#0-0) 

This handler guards the `afterAuth` hook, keyed by the raw session token (JWT), in both the token-exchange and auth-code-flow strategies: [2](#0-1) [3](#0-2) 

If the developer-supplied `afterAuth` hook throws on the first invocation for a given session token (e.g. transient error while calling `shopify.registerWebhooks`, or a downstream DB write during shop provisioning), the outer caller correctly surfaces a 500: [4](#0-3) 

However, because the identifier was already recorded as "runnable and consumed" in the `identifiers` map on the *first* call, any subsequent retry using the same still-valid session token (App Bridge frequently retries the identical token-exchange request when a request fails) will find `isPromiseRunnable(identifier) === false`, skip re-invoking `promiseFunction`, and return a resolved promise with no error — even though the hook never actually completed successfully. The caller then proceeds as if authentication and post-auth setup finished normally, returning/continuing with the session.

### Impact Explanation
Any post-auth setup performed in `afterAuth` (most commonly webhook registration, including mandatory GDPR/`app/uninstalled` webhooks, or per-shop provisioning) can be silently and permanently skipped for the affected install, without the app or merchant ever being informed, for up to 60 seconds after the first failure — long enough for typical client-side retry behavior. Because `app/uninstalled` webhook registration is one of the most common uses of this hook, a shop can end up installed with a stored, valid access token but no working uninstall webhook, meaning the app never learns the shop uninstalled and the offline token/session data is never cleaned up — a stale-credential retention issue directly analogous to the original report's "collateral gets treated as returned when it wasn't."

### Likelihood Explanation
This is reachable by a single, legitimate merchant during normal app installation — no attacker forgery is required. It only requires the `afterAuth` hook to throw once (any transient failure: network blip, DB timeout, rate limit) and the client to retry with the same session token inside the 60-second window, which is a common and expected pattern for embedded apps using App Bridge token exchange.

### Recommendation
Only mark an identifier as "handled" after `promiseFunction()` resolves successfully; on failure, remove the identifier from the map (or don't insert it until success) so that a subsequent retry with the same identifier re-attempts the hook instead of being silently treated as already completed. Consider making `handlePromise` propagate a rejection state to concurrent/duplicate callers rather than silently no-op behavior on prior failure.

### Proof of Concept
1. Configure an app with a `hooks.afterAuth` that fails on its first call for a shop (simulate a transient error).
2. Start install/token-exchange for that shop with session token `T`; `afterAuth` throws, the middleware returns HTTP 500, but `identifiers` map now contains `T`.
3. Within 60 seconds, the client (e.g. App Bridge auto-retry) re-sends the token-exchange request with the same still-valid `T`.
4. `isPromiseRunnable(T)` returns `false`; `handlePromise` resolves without invoking `afterAuth` again; the middleware proceeds and returns a valid session to the caller as if setup succeeded, even though `afterAuth` never completed — as shown by the existing tests only covering the "success" and "single failure" cases, not the "retry after failure within TTL" case: [5](#0-4)

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }
