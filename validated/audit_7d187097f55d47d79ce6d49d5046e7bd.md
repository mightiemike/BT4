## Title
Extreme-price-ratio orders can round the maker's received quantity to zero, letting a taker drain a maker's market order for free - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes both sides of a trade via `MarketUtils.multiplyAndDivide`, an integer multiply-then-divide helper used to convert quantities across the maker/taker price ratio. The taker-side result is explicitly checked for a zero outcome and handled safely, but the maker-side result in the "exact match" branch (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`) is not checked before being used to pay the maker and close out the maker's order. This mirrors the disclosed `splits-oracle` bug class: an extreme price ratio between the two sides of a division can round the computed amount down to zero, and that zero silently flows into settlement, allowing one party to receive a valuable asset for free.

### Finding Description
In `matchSingleOrder`, the taker's expected quantity is computed and validated: [1](#0-0) 

But in the equal-match branch, the amount the maker is supposed to *receive* is computed the same way, with no analogous zero check, before the maker's order is fully closed and the taker walks away with the maker's entire remaining sell quantity: [2](#0-1) 

That `makerBuyTokenQuantityReceive` value is later credited to the maker's account and recorded in the trade detail, and the maker's order is fully consumed regardless of whether this value is zero: [3](#0-2) 

By contrast, the "taker > maker" branch does explicitly guard against `makerBuyTokenQuantityReceive == 0` and returns the sell-token remainder to the maker instead of consuming the order: [4](#0-3) 

This asymmetry means the exact-match branch (`taker == maker` quantities) is the only path in `matchSingleOrder` where a maker's order can be fully closed (`makerOrderCapsule.setSellTokenQuantityRemain(0)`) while `makerBuyTokenQuantityReceive` is 0, i.e., the maker sells its entire remaining balance for nothing. I was not able to inspect the body of `MarketUtils.multiplyAndDivide` itself in this pass (it lives in `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java` per `grep_search`, but its implementation was not retrieved), so I cannot fully confirm the exact rounding/truncation semantics (e.g., whether it always rounds toward zero, and whether it has internal overflow-safety switches via `disableJavaLangMath()`). Given java-tron order quantities are `long` integers (not fixed-point WAD values like the Solidity oracle), triggering an exact zero requires `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` under integer division — achievable with a maker order whose `buyTokenQuantity` is very small relative to `sellTokenQuantity` (i.e., an extreme price ratio) combined with a small residual `sellTokenQuantityRemain` after partial fills, or directly by placing a maker order with a very small `buyTokenQuantity` and a `sellTokenQuantityRemain` chosen so the equal-match condition is hit.

### Impact Explanation
If `makerBuyTokenQuantityReceive` rounds to zero in the exact-match branch, the maker's order is marked `INACTIVE`/fully consumed and the maker's entire remaining sell-token balance is transferred to the taker via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)`, while the maker receives `0` of the buy token via `addTrxOrToken(makerOrderCapsule, 0)`. This is a direct loss of value for the maker and a free asset for the taker/bot executing the match — the same "steal tokens for free" impact called out in the referenced report, but manifesting in java-tron's on-chain decentralized exchange (Market) settlement rather than an external price oracle.

### Likelihood Explanation
Reaching the equal-match branch requires the taker's computed `takerBuyTokenQuantityRemain` to exactly equal the maker's `sellTokenQuantityRemain` — this is attacker-controllable because the taker crafts their own `sellTokenQuantity`/`buyTokenQuantity` contract fields (`MarketSellAssetActuator.execute`/`validate`, lines 117-120, 197-200) to hit any desired `takerBuyTokenQuantityRemain`, and a colluding or opportunistic actor can also place the maker order with an extreme sell:buy ratio ahead of time. This makes the trigger conditions attacker-controlled rather than incidental, though it does require careful selection of quantities and awareness of `multiplyAndDivide`'s exact rounding behavior, which I could not fully verify from the available code.

### Recommendation
Add an explicit zero-result check in the exact-match branch of `matchSingleOrder`, mirroring the guard already present for the taker-side and for the "taker > maker" maker-side computation: if `makerBuyTokenQuantityReceive == 0`, do not close out the maker's order or transfer the taker's full quantity — instead treat it like the "quantity too small" case (return remaining sell tokens, or reject the match) as done at lines 406-413 and 466-477.

### Proof of Concept
Conceptual PoC (exact byte-level reproduction requires the `multiplyAndDivide`/`disableJavaLangMath` implementation, which was not retrieved in this session):
1. Maker places a `MarketSellAssetContract` selling token A for token B with an extreme ratio, e.g. `sellTokenQuantity = 1_000_000_000_000L`, `buyTokenQuantity = 1L` (maker wants at least 1 unit of B for all of its A).
2. A prior partial fill (or a second crafted maker order) leaves `makerOrderCapsule.getSellTokenQuantityRemain()` at some small residual value `R` such that `R * buyTokenQuantity(=1) / sellTokenQuantity(=1_000_000_000_000L)` truncates to `0` under integer math.
3. Taker submits a `MarketSellAssetContract` whose computed `takerBuyTokenQuantityRemain` (via `multiplyAndDivide`) exactly equals `R`, hitting the `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch at line 418.
4. `matchSingleOrder` computes `makerBuyTokenQuantityReceive = 0`, sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` (fully closing the maker's order) and transfers `takerBuyTokenQuantityReceive = R` units of token A to the taker via `addTrxOrToken`, while crediting the maker `0` units of token B.
5. Result: the maker's remaining A tokens are transferred to the taker with no compensation credited to the maker. [2](#0-1)
