## Title
`ensure_match_transaction_info` never validates `state_checkpoint_hash`, allowing a divergent state root to pass replay/output verification - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity comparator used by replay/verification tooling (e.g. `storage/db-tool/src/replay_on_archive.rs`) to check that a locally-computed `TransactionOutput` matches the authenticated `TransactionInfo` fetched from a backup/archive. It checks `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`, but it never compares `state_checkpoint_hash` (the Sparse-Merkle-Tree / JMT state root committed in `TransactionInfoV0`/`V1`), nor `hot_state_checkpoint_hash` or `position_state_checkpoint_hash`. This is acknowledged in-code by a `TODO(trading-native)` comment, which frames the gap narrowly as a trading-native/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` concern, but the omission of `state_checkpoint_hash` itself is unconditional and pre-dates that feature — it affects every checkpoint transaction on every network today. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` is documented as the function that ensures a `TransactionOutput` matches its `TransactionInfo` (the object committed in the transaction accumulator and covered by consensus signatures via `LedgerInfo`). Walking through its checks:

- status match [2](#0-1) 
- gas used match [3](#0-2) 
- write-set hash match against `state_change_hash` [4](#0-3) 
- event root hash match [5](#0-4) 

There is **no** comparison against `txn_info.state_checkpoint_hash()`, which is the field that authenticates the entire world-state (SMT/JMT root) at a checkpoint boundary — the most important state-commitment invariant in the whole system. The function's own trailing comment confirms the checkpoint hashes are ignored and explicitly calls out the consequence: `replay_on_archive` can "report a successful replay even when the authenticated position state root diverges from local execution." [6](#0-5) 

The one caller of this method found in the codebase is `storage/db-tool/src/replay_on_archive.rs`, the replay-verification tool used to validate that re-execution of archived/backed-up transactions reproduces the exact committed results before those transactions are trusted (e.g. for db-tool `replay-on-archive` jobs referenced by `testsuite/replay-verify/main.py`). [7](#0-6) 

Because `state_checkpoint_hash` is not compared here, a locally-recomputed `TransactionOutput` whose write set hash and event root happen to match, but whose materialized state (post-application to the SMT/JMT) diverges from the state root recorded in the authenticated `TransactionInfo`, will still pass `ensure_match_transaction_info` without error. This defeats the core purpose of replay-verification: proving that re-executing archived transactions reproduces the exact, consensus-committed ledger state.

Compare this with the equivalent verification path for `TransactionOutputListWithProof::verify`, which is used for state-sync/data-client verification and similarly checks `state_change_hash`, `gas_used`, `status`, and `transaction_hash`, but likewise does not check `state_checkpoint_hash` at that layer [8](#0-7)  — the SMT root's authenticity in that pipeline instead flows implicitly through the accumulator/`LedgerInfo` proof and the executor's own re-derivation of state during real block execution, not through this comparator. `replay_on_archive`, however, uses `ensure_match_transaction_info` as its primary output-equivalence check, so the state-root gap there is not otherwise compensated.

### Impact Explanation
This is a proof/replay-integrity gap: a `TransactionOutput` whose resulting state diverges from the mainnet-committed state (whether due to a VM bug, non-determinism, or storage-schema/replay-path defect) would not be caught by `replay_on_archive`'s consistency check, since only the write-set hash (pre-application digest) and event root are validated, not the state root that authenticates the actual applied state. This directly undermines the "Proof And Storage Pivots" invariant that "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" and that "replay paths ... must not reinterpret committed data into a different ledger state" — replay-verify is exactly the mechanism meant to catch such reinterpretation, and it silently passes divergent state roots. This is a hard-fork-class detection gap: it doesn't itself corrupt live consensus state, but it removes a load-bearing safety check that is relied upon to detect ledger-state divergence during replay/backup verification, which is precisely the kind of "hard-fork-only divergence during commit, replay, restore, or proof verification" scope called out in the task.

### Likelihood Explanation
The missing check is unconditional (not behind any feature flag) and applies to the `state_checkpoint_hash` field that has existed since `TransactionInfoV0`, so any code path that constructs a `TransactionOutput` with a subtly wrong resultant state but a coincidentally-correct write-set hash would go undetected by this specific check today. However, I could not fully confirm within the available tooling budget whether other layers of `replay_on_archive`'s pipeline (e.g. the underlying `AptosDB`/state-merkle commit path itself, which does compute and could independently assert state roots) provide an independent, redundant catch of state-root mismatches; the `read_file` call on `replay_on_archive.rs` lines 136–242 returned empty content due to the final-iteration tool cutoff, so I was not able to inspect `execute_and_verify` directly to confirm whether it re-derives or re-checks the state root through a separate call. This is a real, but reduced-confidence limitation on the finding.

### Recommendation
Add `state_checkpoint_hash` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` when present in `TransactionInfoV1`) comparisons to `ensure_match_transaction_info`, comparing against the locally-computed SMT/JMT root produced when the output is applied to the state view, consistent with the TODO already present in the code. This should be done regardless of whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, since the base `state_checkpoint_hash` field is unconditionally part of `TransactionInfo` and its integrity is the load-bearing state-commitment guarantee that `replay_on_archive` is supposed to certify.

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this gap requires constructing a divergent VM/state-application path that (a) is invoked through `replay_on_archive::verify` / `execute_and_verify`, and (b) produces a `TransactionOutput` with a coincidentally-matching write-set hash (`state_change_hash`) and event root but a different resultant merklized state root than the one recorded on-chain. I was unable to confirm the exact reachability of `execute_and_verify` due to the tool truncation noted above; a background engineer with full file access should inspect `storage/db-tool/src/replay_on_archive.rs` (function `execute_and_verify`, around lines 136–242) to confirm whether it calls `ensure_match_transaction_info` directly on the executor's produced output without any separate state-root re-derivation/comparison, which would make this fully exploitable as described.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
