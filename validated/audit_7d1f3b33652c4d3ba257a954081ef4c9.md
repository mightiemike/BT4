### Title
Missing check that an `Extended`-cause `TenureChange`'s `tenure_consensus_hash` matches the parent block's real ongoing tenure - (File: `stackslib/src/chainstate/nakamoto/tenure.rs`)

### Summary
In `check_nakamoto_tenure`, the branch that handles `TenureChangeCause::Extended` (and its `ExtendedRuntime`/`ExtendedReadCount`/`ExtendedReadLength`/`ExtendedWriteCount`/`ExtendedWriteLength` variants) only checks that `tenure_payload.tenure_consensus_hash == tenure_payload.prev_tenure_consensus_hash` — a self-referential, fully attacker-controlled equality — and never compares either value against `parent_tenure.tenure_id_consensus_hash`, the tenure actually reached by walking `block_header.parent_block_id` via `get_ongoing_tenure`. The `BlockFound` branch does perform this real cross-check (`parent_tenure.tenure_id_consensus_hash != tenure_payload.prev_tenure_consensus_hash`, lines 779-787), but the `Extended` branch (lines 789-806) omits the analogous comparison.

### Finding Description
The claimed equality that should hold is:
`tenure_payload.tenure_consensus_hash == parent_tenure.tenure_id_consensus_hash`
where `parent_tenure` is obtained from `Self::get_ongoing_tenure(headers_conn, &block_header.parent_block_id)` [1](#0-0)  — i.e., the tenure that the block's real ancestor chain belongs to.

Tracing `check_nakamoto_tenure`:
- Line 660 forces `block_header.consensus_hash == tenure_payload.tenure_consensus_hash` [2](#0-1) , so these two attacker-supplied/header fields are not independent — the attacker cannot use them to bypass anything beyond what the payload itself claims.
- The `prev_sn.consensus_hash == tenure_sn.consensus_hash` check at line 722 is derived purely from `tenure_payload.prev_tenure_consensus_hash` and `tenure_payload.tenure_consensus_hash` via `check_valid_consensus_hash`, which simply looks up the snapshot by that exact hash [3](#0-2) . This is trivially satisfiable by an attacker who sets both fields equal — but it is *not* the actual security-relevant check; it's re-derived/redundant with the explicit equality check performed later at lines 797-804.
- The real security-relevant step is the `match tenure_payload.cause` block at lines 774-806. For `BlockFound`, it validates `parent_tenure.tenure_id_consensus_hash != tenure_payload.prev_tenure_consensus_hash` — binding the payload to the real parent tenure [4](#0-3) . For `Extended` and its variants, only `tenure_payload.tenure_consensus_hash != tenure_payload.prev_tenure_consensus_hash` is checked [5](#0-4)  — there is no comparison against `parent_tenure.tenure_id_consensus_hash` at all.

`check_tenure_continuity`, which the question cites as a possible catch, is irrelevant here: it is only invoked for blocks that do **not** carry a `TenureChange` transaction (i.e., ordinary continuation blocks within an already-open tenure) — a tenure-extend block always carries a `TenureChange` tx and is validated exclusively through `check_nakamoto_tenure`/`advance_nakamoto_tenure` [6](#0-5) . So it can never serve as a backstop for the missing check in the `Extended` branch.

An attacker acting as block author for an extend-cause block can therefore set `tenure_consensus_hash = prev_tenure_consensus_hash = CH_x`, where `CH_x` is any validly-sortitioned, canonical consensus hash (satisfying `check_valid_consensus_hash`, the block-height ordering checks, and the `prev_sn.sortition`/shadow-block checks), while `block_header.parent_block_id` actually points into a chain whose real ongoing tenure is `CH_real != CH_x`. `check_nakamoto_tenure` returns `Ok(Some(parent_tenure))` (the *real* tenure record, fetched independently of the payload) without ever asserting `CH_x == parent_tenure.tenure_id_consensus_hash`. `advance_nakamoto_tenure` then calls `insert_nakamoto_tenure`, which writes the attacker-chosen `tenure.tenure_consensus_hash = CH_x` into `nakamoto_tenure_events` [7](#0-6) , mismatched from the block's real ancestry.

### Impact Explanation
If exploitable end-to-end, this would let an attacker record a tenure-extend event under a tenure ID (`CH_x`) that the extending block's real ancestor chain does not belong to, corrupting `nakamoto_tenure_events`/coinbase-height accounting used by `get_matured_miner_reward_schedules` and `calculate_scheduled_tenure_reward`, which could misattribute or mis-schedule block rewards — matching the "block-reward mis-payment" Critical category if it actually diverges accepted chain state between honest nodes. However, I could not verify within the available exploration budget whether other validation performed elsewhere in `stackslib/src/chainstate/nakamoto/mod.rs` (e.g., in `append_block`, sortition/burn-view tie-breaking, or signer-signature verification against the expected tenure) independently re-derives and checks `block_header.consensus_hash`/`tenure_consensus_hash` against the parent's real tenure before a block is actually appended to the chain tip. Given the assertion at `insert_nakamoto_tenure` line 438 only checks internal self-consistency (already guaranteed), and given `check_tenure_continuity` does not apply to tenure-change blocks, the burden of this cross-check appears to fall solely on the missing comparison identified above — but full confirmation requires reading the calling code in `mod.rs` that was not reachable within this session's tool budget.

### Likelihood Explanation
Preconditions: the attacker must be an unprivileged block author (any miner/authorized signer set for the block) able to produce a `TenureChange` with `cause = Extended` (or a related extend variant) and choose `tenure_consensus_hash`/`prev_tenure_consensus_hash` freely, subject only to those hashes corresponding to a real, canonical, previously-sortitioned burnchain block (`CH_x`) that is an ancestor-height-compatible snapshot (`tenure_sn.block_height <= sortition_sn.block_height`). This is fully within attacker control as block author and requires no majority stake — only the ability to have a block signed/accepted by whatever mechanism gates block acceptance (signer signature threshold), which is outside this function's scope per the audit rules.

### Recommendation
Add an explicit equality check in the `Extended`-cause branch of `check_nakamoto_tenure` (mirroring the `BlockFound` branch) asserting `tenure_payload.tenure_consensus_hash == parent_tenure.tenure_id_consensus_hash`, i.e., that the tenure being extended is in fact the ongoing tenure of `block_header.parent_block_id` as tracked by `get_ongoing_tenure`, not merely self-consistent within the payload.

    /// Check that this block is in the same tenure as its parent, and that this tenure is the
    /// highest-seen tenure.  Use this to check blocks that do _not_ have BlockFound tenure-changes.
    ///
    /// `parent_ch` is the tenure ID consensus hash of the given block's parent.
    ///
    /// Returns Ok(bool) to indicate whether or not this block is in the same tenure as its parent.
    /// Returns Err(..) on DB error
    pub(crate) fn check_tenure_continuity<SDBI: StacksDBIndexed>(
        headers_conn: &mut SDBI,
        parent_ch: &ConsensusHash,
        block_header: &NakamotoBlockHeader,
    ) -> Result<bool, ChainstateError> {
        // block must have the same consensus hash as its parent
        if block_header.is_first_mined() || parent_ch != &block_header.consensus_hash {
            test_debug!("Block is discontinuous with tenure: either first-mined or has a different tenure ID";
                        "parent_ch" => %parent_ch,
                        "block_header.consensus_hash" => %block_header.consensus_hash,
                        "is_first_mined()" => block_header.is_first_mined(),
            );
            return Ok(false);
        }

        // block must be in the same tenure as the highest-processed tenure.
        let Some(highest_tenure) =
            Self::get_ongoing_tenure(headers_conn, &block_header.parent_block_id)?
        else {
            // no tenures yet, so definitely not continuous
            test_debug!("Block is discontinuous with tenure: no ongoing tenure";
                        "block_header.parent_block_id" => %block_header.parent_block_id,
            );
            return Ok(false);
        };

        if &highest_tenure.tenure_id_consensus_hash != parent_ch {
            // this block is not in the highest-known tenure, so it can't be continuous
            test_debug!("Block is discontinuous with tenure: parent is not in current tenure";
                        "parent_ch" => %parent_ch,
                        "highest_tenure.tenure_id_consensus_hash" => %highest_tenure.tenure_id_consensus_hash,
            );
            return Ok(false);
        }

        Ok(true)
    }
