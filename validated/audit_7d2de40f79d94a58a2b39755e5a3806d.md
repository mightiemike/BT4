## Title
Integer-division truncation lets a taker drain a maker's exact-match order for zero payment in `MarketSellAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The reported bug class is: an integer-division/rounding truncation that silently rounds a small computed amount down to zero, so one side of a transfer keeps the input while the counterparty ends up crediting nothing. In java-tron's on-chain order-matching logic (`MarketSellAssetContract`, reachable directly from a broadcast transaction), the "exact match" branch of `matchSingleOrder` computes the maker's payment with the same floor-division helper used elsewhere, but — unlike the other two branches in the same method — never checks whether that result is zero before consuming the maker's entire remaining order.

### Finding Description
`matchSingleOrder` in `MarketSellAssetActuator` handles three cases depending on how the taker's computed buy amount compares to the maker's remaining sell amount [1](#0-0) .

- In the "taker < maker" case, before doing anything else, the code checks `takerBuyTokenQuantityRemain == 0` and returns the sell tokens back to the taker if the computed quantity rounded to zero [1](#0-0) .
- In the "taker > maker" case, the code explicitly re-checks `makerBuyTokenQuantityReceive == 0` after computing it via `MarketUtils.multiplyAndDivide`, and if so, returns the maker's remaining sell tokens instead of giving them away, with a comment acknowledging this rounding-to-zero scenario is a known risk [2](#0-1) .
- However, in the "taker == maker" (exact match) branch, `makerBuyTokenQuantityReceive` is computed with the exact same `MarketUtils.multiplyAndDivide` helper, but there is **no zero-check** at all. The maker's order is immediately marked fully consumed (`setSellTokenQuantityRemain(0)`, state set to `INACTIVE`) regardless of whether `makerBuyTokenQuantityReceive` is zero, while the taker unconditionally receives `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` — i.e. the maker's *entire* remaining sell-token balance [3](#0-2) .

`MarketUtils.multiplyAndDivide` performs `floorDiv(a*b, c)`, which truncates any fractional remainder to zero for small `a` (e.g. small `makerSellRemainQuantity`) relative to `makerSellQuantity` [4](#0-3) . So a maker order whose original sell quantity is large but whose *remaining* quantity has been whittled down to a small value (through prior partial fills) can, on the next exact-match fill, yield `makerBuyTokenQuantityReceive == 0` while still being fully drained and marked inactive — the taker receives the asset for free and the maker gets nothing back, and neither the maker nor a third party has any way to prevent or detect this at validation time (`validate()` only bounds absolute quantities via `getMarketQuantityLimit()`, not the ratio-driven rounding behavior of in-flight partial fills) [5](#0-4) .

This is directly analogous to the reported class of bug: a valid, unprivileged, attacker-controlled transaction (crafting a `MarketSellAssetContract` sized to exactly match a target maker order's remaining quantity) triggers integer-division truncation that silently assigns zero of the expected asset to one party while the other party's balance is fully consumed — the same "small amount rounds to zero, and the code doesn't guard for it" defect that the report describes for `DSTContract.sol`, except here it corrupts actual on-chain TRC10/TRX asset accounting rather than a test ERC20 fallback.

### Impact Explanation
An attacker able to observe the order book (which is fully public) can craft a `MarketSellAssetContract` sized so that it exactly matches (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`) a maker order whose remaining quantity is a small fraction of its original quantity, engineering `multiplyAndDivide` to floor to zero. The result is asset/accounting corruption: the maker's order is force-closed and its remaining sell-side balance handed to the attacker without the corresponding buy-side payment ever being credited to the maker. This is a direct loss of funds for the maker and an unearned gain for the attacker, executed purely through normal exchange transactions.

### Likelihood Explanation
Exploitation requires no special privileges — any account can submit `MarketSellAssetContract` transactions, and the order book (prices, remaining quantities) is public information queryable via existing wallet/HTTP APIs, so an attacker can precisely target a maker order whose remaining quantity is small enough relative to its price ratio to trigger the truncation. The surrounding two branches of the very same function already anticipate and guard against this exact rounding condition, indicating the missing check in the "exact match" branch is a real, reachable gap rather than a theoretical one.

### Recommendation
Add the same zero-quantity guard used in the other two branches of `matchSingleOrder` to the "taker == maker" branch: after computing `makerBuyTokenQuantityReceive` via `MarketUtils.multiplyAndDivide` at [6](#0-5) , check if it is `0` and, if so, return the maker's remaining sell tokens (mirroring the handling at lines 466-477) instead of proceeding to zero out the maker's order and transfer the full amount to the taker.

### Proof of Concept
1. Maker places a sell order with `sellTokenQuantity = S`, `buyTokenQuantity = B` where `S` is much larger than `B` (a price ratio such that `B/S` is very small), e.g. `S = 10_000_000`, `B = 1`.
2. Through prior partial fills (or a sequence of taker transactions), reduce the maker order's `sellTokenQuantityRemain` down to a small value `r` such that `r * B / S == 0` under `floorDiv` (e.g. `r < S/B`, which given `B=1` means any `r < S`).
3. Attacker (taker) submits a `MarketSellAssetContract` whose computed `takerBuyTokenQuantityRemain` exactly equals `r` (the maker's remaining quantity), landing in the `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch.
4. `makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(r, B, S, ...) = floor(r*B/S) = 0`.
5. The actuator sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` and marks it `INACTIVE`, while crediting the taker with `takerBuyTokenQuantityReceive = r` (the maker's full remaining sell-token balance) via `addTrxOrToken` [7](#0-6) . The maker receives nothing in return for its consumed `r` tokens.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
