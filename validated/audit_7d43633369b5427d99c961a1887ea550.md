## Analysis

The reported bug class — a per-caller/per-key aggregate silently rounding down to **zero** when a "total" denominator based on a *different* grouping is used to gate eligibility — maps directly onto the legacy Nakamoto signer-set construction in `StacksChainState::make_signer_set` (pre‑PoX‑5).

### Title
Legacy PoX signer-set construction can floor every signer's weight to zero, degenerating the Nakamoto block-approval threshold to 0 and letting an unsigned block pass validation - (File: `stackslib/src/chainstate/stacks/boot/mod.rs`)

### Summary
`StacksChainState::make_reward_set` computes two *independently grouped* aggregates from the same list of `RawRewardSetEntry` using the *same* `threshold`: reward-slot eligibility is grouped **by PoX reward address**, while signer voting weight is grouped **by signing key** in `make_signer_set`. [1](#0-0)  Because these groupings are different, it is possible for a reward address to accumulate enough stacked STX to earn reward slots (address-grouping ≥ threshold) while every individual signing key associated with that address stays below `threshold`, causing each signing key's weight (`stacked_amt / threshold`) to floor to 0 and be filtered out. [2](#0-1)  If this happens for *every* signing key in the cycle, `make_signer_set` returns `Some(vec![])` — a non-`None`, but empty, signer list. [3](#0-2) 

### Finding Description
`RewardSet::signers()` returns `Some(&vec![])` in this case (not `None`), so downstream code that only checks for `None` treats the reward set as valid. `RewardSet::total_signing_weight()` then folds over an empty vector, yielding `total_weight = 0`. [4](#0-3) 

In `NakamotoBlockHeader::verify_signer_signatures`, the code only rejects `None`, not an empty `Some(vec![])`: `total_weight` is then `0`. [5](#0-4)  `compute_voting_weight_threshold(0)` computes `ceil(0 * 70 / 100) = 0`. [6](#0-5)  Since `total_weight_signed` starts at `0` (no signatures need to be iterated), the check `total_weight_signed < threshold` (`0 < 0`) is `false`, so the function returns `Ok(0)` — a block with **zero** signer signatures is treated as validly signed. [7](#0-6) 

This is the same bug class as the GMIndex report: a denominator/aggregate ("total supply"/"total weight") that is legitimately zero on a degenerate but reachable input is not special-cased, so a formula that should require a nonzero minimum instead silently authorizes the zero case. Stacks-core has already recognized and fixed exactly this failure mode for the newer PoX-5 scheme (`pox_5_make_signer_set` uses a largest-remainder/Hare apportionment specifically so that "every signer's weight floors to 0" no longer drops the whole set — see the regression test `equal_stakes_exceeding_reward_slots_are_not_all_zeroed`), but the legacy `make_signer_set` used for PoX-1..PoX-4 reward-set construction still uses the naive floor-and-drop scheme and has no such protection. [8](#0-7) 

### Impact Explanation
If the signer set for a reward cycle degenerates to empty in this way, `verify_signer_signatures` accepts any block for that cycle regardless of actual signer approval — effectively disabling the Nakamoto 70%-weight signer-approval invariant for that cycle. A miner could then produce and have accepted blocks with no real signer consensus, which is a critical break of the "committed state requires signer approval" equality and can cause node disagreement/chain split, since the network's safety assumption (blocks require ≥70% signer weight) no longer holds for that cycle.

### Likelihood Explanation
Triggering requires only that stackers arrange stacked STX for one reward address across multiple distinct signing keys such that each signing key's aggregate stays under the flat PoX stacking-minimum `threshold` while the address's combined total clears it (e.g., 3 stackers each contributing `threshold/3` to the same reward address with 3 different signer keys, and no other signer in the cycle individually clears `threshold`). This does not require a stake majority — only that no single signing key in the cycle individually exceeds `threshold`, which is achievable by a small/minority set of cooperating stackers.

### Recommendation
- In `RewardSet::signers()`/`total_signing_weight()` and `NakamotoBlockHeader::verify_signer_signatures`, explicitly treat an empty (but `Some`) signer list the same as `None` and reject the block/reward set (return `ChainstateError::NoRegisteredSigners`).
- Port the largest-remainder (Hare) apportionment fix already used in `pox_5_make_signer_set` back into the legacy `make_signer_set` so per-signing-key weight can never universally floor to zero while reward slots remain allocated.
- Add an explicit invariant check that `total_signing_weight() > 0` whenever `rewarded_addresses` is non-empty, and fail closed if this invariant is violated.

### Proof of Concept
1. In a PoX-4-era reward cycle, have 3 distinct principals each stack `threshold/3` uSTX to the same PoX reward address, each registering a distinct `signer-key`.
2. `make_reward_set` groups by reward address: total = `threshold` ⇒ 1 reward slot is allocated. [9](#0-8) 
3. `make_signer_set` groups the same entries by signing key: each key's `stacked_amt < threshold` ⇒ `weight == 0` ⇒ filtered out ⇒ `signer_set = vec![]`, returned as `Some(vec![])`. [2](#0-1) 
4. `RewardSet::total_signing_weight()` returns `0`; `NakamotoBlockHeader::compute_voting_weight_threshold(0) == 0`.
5. A Nakamoto block for this reward cycle with an empty `signer_signature` vector passes `verify_signer_signatures`, returning `Ok(0)`, i.e., accepted as validly signed with zero real signer approval.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

#[test]
fn equal_stakes_exceeding_reward_slots_are_not_all_zeroed() {
    // Regression: more distinct signers than reward_slots, all with equal stake.
    //
    // The old floor-and-drop scheme set threshold = ceil(N*S / R) > S, so every
    // signer's weight floored to 0 and the entire set was dropped -- stalling the
    // chain. The Hare round must instead award one slot each to the top `R` signers
    // (by remainder, then signing_key), dropping only the surplus signers.
    let pox_constants = test_pox_constants(1); // reward_slots() == 4
    let reward_slots = pox_constants.reward_slots();
    assert_eq!(reward_slots, 4);
    let stake = 1_000_000u128;
    // 5 signers, only 4 slots.
    let entries: Vec<_> = (0..5u8)
        .map(|i| RawPox5Entry {
            signer_key: signer_key(i),
            amount_ustx: stake,
        })
        .collect();
    let mut iter = entries.into_iter().map(Ok);
    let Pox5SignerSetOutput { signer_set, .. } =
        NakamotoSigners::pox_5_make_signer_set(&mut iter, &pox_constants).expect("ok");

    assert_eq!(
        signer_set.len(),
        reward_slots as usize,
        "expected exactly reward_slots signers, not an empty/zeroed set"
    );
    for entry in &signer_set {
        assert_eq!(
            entry.weight, 1,
            "each surviving signer should hold one slot"
        );
    }
    let total_weight: u128 = signer_set.iter().map(|e| u128::from(e.weight)).sum();
    assert_eq!(total_weight, u128::from(reward_slots));
    // Ties broken by signing_key ascending: keys 0x00..0x03 win, 0x04 is dropped.
    assert!(
        !signer_set.iter().any(|e| e.signing_key == signer_key(0x04)),
        "highest-key signer should be the one dropped on tie-break"
    );
}
