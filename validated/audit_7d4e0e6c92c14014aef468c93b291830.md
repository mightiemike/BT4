### Title
Non-deterministic floating-point arithmetic in Exchange bonding-curve calculation risks consensus divergence and precision-loss exploitation - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The external report describes an "unnecessarily complex" token-amount formula that caused precision loss through chained integer operations, fixed by simplifying the math. The same bug *class* — an overly complex, non-exact arithmetic formula in a token-accounting path — exists in java-tron's bancor/bonding-curve exchange calculation, but in a more severe form: it uses `double`-precision floating point and `Math.pow` instead of exact/deterministic arithmetic, which is explicitly flagged by the codebase itself as unsafe for consensus-critical code.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on a governance-controlled flag (`hardenedCalc`, derived from a dynamic-property/proposal): [1](#0-0) 

When the hardened path is not active, it uses `ExchangeProcessor`, whose bancor-curve math is computed with `double` and `Math.pow`: [2](#0-1) 

The `Maths` helper that backs this legacy path is explicitly documented as deprecated because non-strict `Math` operations are not guaranteed to produce identical results across platforms/JVMs, and callers are told to use `StrictMathWrapper` instead: [3](#0-2) 

The fix path (`SafeExchangeProcessor`) that the team added replaces the floating-point pow-chain with `BigDecimal`/`StrictMathWrapper` based computation — functionally the same remediation direction recommended in the external report (replace an imprecise chained formula with an exact/deterministic one): [4](#0-3) 

This calculation is reachable directly from anonymous, unprivileged broadcast transactions: `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract`, all of which call `exchangeCapsule.transaction(...)` and persist the resulting balances/amounts to the account and exchange stores. [5](#0-4) [6](#0-5) [7](#0-6) 

The test suite itself proves the two code paths produce different results for identical inputs, confirming the precision/behavior gap between the legacy floating-point path and the hardened exact-math path: [8](#0-7) 

### Impact Explanation
If any node in the network computes `Math.pow` with different JIT optimizations, native math libraries, or hardware (a well-documented risk for `double`-based transcendental functions across platforms/architectures), the legacy `ExchangeProcessor` path can return a different `anotherTokenQuant`/`buyTokenQuant` for the exact same transaction and exchange state. Since this value is written directly into account asset balances and exchange reserve balances, this can produce **consensus divergence** (different nodes committing different resulting state for the same block) or, at minimum, exploitable precision loss letting a party extract more/less value than the exact bonding-curve formula would allow. This is accounting/consensus-critical code, not a cosmetic or test-only issue.

### Likelihood Explanation
The vulnerable path is only removed when the `allowStrictMath`/hardened-exchange-calculation proposals are activated network-wide; until/unless that governance switch is flipped, the default `ExchangeProcessor` (non-strict, `double`-based) is what actually executes for every `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` sent by any ordinary account — no special privilege is required to trigger it, and it is exercised on every exchange trade. The presence of both a deprecation warning on `Maths` and a fully built parallel "Safe"/hardened implementation strongly indicates the java-tron team is aware of and has partially mitigated this issue, but the legacy code path is still present and reachable when the corresponding chain parameter/proposal is not enabled.

### Recommendation
- Confirm the default/mainnet value of the `allowStrictMath` and `allowHardenExchangeCalculation` dynamic properties; if not universally enabled, prioritize activating the hardened path (or removing the legacy `ExchangeProcessor`/`Maths` path entirely) network-wide.
- Replace remaining `double`/`Math.pow`-based accounting arithmetic in `ExchangeProcessor` with the exact `BigDecimal`/`StrictMathWrapper` implementation already provided by `SafeExchangeProcessor`, consistent with the external report's guidance of using exact rate-based multiplication instead of chained, lossy formulas.
- Audit other exchange/market accounting code (e.g., `ExchangeInjectActuator`, `ExchangeWithdrawActuator` BigDecimal/BigInteger paths) for any remaining use of platform-dependent floating point.

### Proof of Concept
Not independently reproducible from static analysis alone — a concrete PoC would require running `ExchangeProcessor.exchange()` with identical inputs on different JVM builds/CPU architectures (or comparing `MathWrapper.pow` vs `StrictMathWrapper.pow` results for the same operands) to demonstrate a differing `long` result, then showing that value is what gets committed via `ExchangeTransactionActuator.execute()` to account/exchange balances. The existing test `ExchangeProcessorTest.testStrictMath()` already demonstrates that the non-strict and strict paths diverge for the same inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), which is the core evidence for this analog. /**
 * This class is deprecated and should not be used in new code,
 * for cross-platform consistency, please use {@link StrictMathWrapper} instead,

  /**
   * Returns the value of the first argument raised to the power of the second argument.
   * @param a the base.
   * @param b the exponent.
   * @return the value {@code a}<sup>{@code b}</sup>.
   */
  public static double pow(double a, double b, boolean useStrictMath) {
    return useStrictMath ? StrictMathWrapper.pow(a, b) : MathWrapper.pow(a, b);

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
