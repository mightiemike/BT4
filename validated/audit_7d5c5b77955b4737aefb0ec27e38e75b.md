## Title
`TransactionOutput::ensure_match_transaction_info` silently skips state-checkpoint / hot-state / position-state root comparison, letting replay-verify and chunk-replay tooling accept execution output whose durable state root diverges from the authenticated `TransactionInfo` — ([File: types/src/transaction/mod.rs])

### Summary
`ensure_match_transaction_info` is the single gate used by replay/verification tooling (`ChunkExecutorInner::verify_execution`, `aptos-debugger`, `aptos-move/cli` transaction replay, and `storage/db-tool/src/replay_on_archive.rs`) to decide whether a locally re-executed transaction matches the trusted, already-committed `TransactionInfo` before treating replay as successful. The function checks status, gas, write-set hash, and event-root hash, but the code itself documents (via a `TODO`) that it deliberately does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed values. This means replay/verify code paths can report "match" even when the recomputed state (Merkle) root diverges from the one authenticated in the accumulator-backed `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info` explicitly documents the gap: [1](#0-0) 

Compare this to `TransactionOutputListWithProof::verify`, which similarly only checks event root, write-set hash, gas, status, and transaction hash — again omitting any check of `state_checkpoint_hash` fields carried inside `TransactionInfo`: [2](#0-1) 

The state/hot-state/position-state checkpoint hashes are computed authoritatively in `DoStateCheckpoint::run` and threaded into `TransactionInfo` via `DoLedgerUpdate::assemble_transaction_infos`, which builds the V1 `TransactionInfo` including `maybe_hot_state_checkpoint_hash` and `maybe_position_state_checkpoint_hash`: [3](#0-2) 

and [4](#0-3) 

These fields are part of the `TransactionInfo` hash that is committed into the transaction accumulator (i.e., they are authenticated data bound to a ledger version/root), yet the one place designed to independently re-validate a replayed transaction's output against that authenticated `TransactionInfo` (`ensure_match_transaction_info`) does not check them. All production call sites rely on this comparator to catch divergence:
- Chunk executor replay verification: [5](#0-4) 
- `aptos-debugger`'s mismatch printer: [6](#0-5) 
- `storage/db-tool`'s `replay_on_archive`: [7](#0-6) 
- `aptos-move/cli` transaction replay comparison: [8](#0-7) 

This is directly analogous to the external report's core pattern: a dedicated, stricter validation path exists (regular liquidation vs. bad-debt liquidation checks in the Numa case; full state-root verification vs. partial `TransactionInfo` comparison here), but a commonly-used code path (`ensure_match_transaction_info` / `TransactionOutputListWithProof::verify`) omits a subset of the checks that the "safe" path is supposed to guarantee, silently accepting a result that should have been rejected.

### Impact Explanation
If a bug in state-checkpoint computation, hot-state root computation, or the trading-native `position_state_checkpoint_hash` computation causes a divergence between what the executor recomputes and what is authenticated in the committed `TransactionInfo`, none of the verification tooling that relies on `ensure_match_transaction_info` (chunk-executor replay verification used during fast sync/restore, `db-tool replay_on_archive` used for release validation, and CLI/debugger tooling used to sanity-check historical execution) would detect it. This falls squarely under "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Committed state that differs from the correct VM result" in the impact criteria — a wrong state root could be silently accepted as matching during a verification/replay flow that exists specifically to catch such divergence, undermining a primary safety net against consensus/execution non-determinism (particularly relevant to the newly introduced hot-state and trading-native/position-state features, which are exactly the checkpoint hash types explicitly excluded by the TODO).

### Likelihood Explanation
Low to medium, matching the "requires a specific event" characterization of the seed report. The gap is only actionable if there is a genuine non-determinism or bug in state/hot-state/position-state checkpoint computation across two independent executions (e.g., due to the hot-state or trading-native features, which are new/experimental and explicitly called out by the code's own TODO as unvalidated). This is not a routinely triggerable bug on its own — it is a missing safety check that would fail to catch a real divergence if and when one occurs, similar to how the Numa bug required deprecation to first occur.

### Recommendation
Extend `ensure_match_transaction_info` (and `TransactionOutputListWithProof::verify`) to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values carried in `TransactionInfo` whenever those fields are populated (i.e., whenever `HOT_STATE_ROOT_IN_TXN_INFO` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled), rather than only checking write-set/event/gas/status hashes. This closes the gap the code's own TODO flags before these features are relied upon in production replay/verify flows.

### Proof of Concept
No dynamic PoC was constructed; the finding is based on static analysis of the code's own explicit acknowledgment of the gap: [9](#0-8) 
A concrete PoC would require: (1) enabling `HOT_STATE_ROOT_IN_TXN_INFO` and/or `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, (2) engineering (or waiting for) a bug that causes a genuine hot-state/position-state root divergence between two executions of the same transaction, and (3) demonstrating that `ChunkExecutorInner::verify_execution` / `replay_on_archive::execute_and_verify` report success despite the divergence. Given tool-access limits in this session, this last step could not be executed; the impact assessment above is based on direct code reading of the omission and its call sites, not on an actually exploited divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
