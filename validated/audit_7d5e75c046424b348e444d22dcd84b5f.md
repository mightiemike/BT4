### Title
Attached deposit to `rlp_execute` is permanently lost when `action_to_promise` fails after parsing succeeds - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point is `#[payable]` and accepts a caller-attached NEAR deposit alongside an RLP-encoded Ethereum-style transaction. The contract tracks that deposit in a `CallerDeposit` struct specifically so it can be refunded to the external caller if the resulting cross-contract call fails. However, if the Near action construction step (`action_to_promise`) fails *after* the deposit has already been captured but *before* any promise is actually created, the error is propagated directly out of `inner_rlp_execute` via `?`, completely bypassing the promise chain and the only code path (`rlp_execute_callback`) that performs the refund. The caller's attached deposit is then permanently absorbed into the wallet contract's own balance with no way to recover it, mirroring the underlying bug class in the report: a data/format-triggered failure that happens after funds have already changed custody, with no validation/refund safety net.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` immediately after building the `ExecutionContext` from `env::attached_deposit()`: [1](#0-0) 

`CallerDeposit` exists solely to allow refunding this deposit if the eventual cross-contract call fails: [2](#0-1) 

But the refund only ever happens inside `rlp_execute_callback`, which is invoked as a promise callback *after* a real cross-contract promise has resolved: [3](#0-2) 

In the default (catch-all) branch of `inner_rlp_execute`, the promise is built via `action_to_promise(target, action)?.then(...)`. If `action_to_promise` returns an `Err`, the `?` operator immediately returns that error from `inner_rlp_execute` — no promise is ever created, so `rlp_execute_callback` (and therefore the refund logic tied to `caller_deposit`) is never reached: [4](#0-3) 

Back in the top-level `rlp_execute` handler, any `Err` returned from `inner_rlp_execute` (other than the specific relayer-ban case) is converted straight into an `ExecuteResponse` value with no refund promise scheduled: [5](#0-4) 

Since the whole method is `#[payable]`, the deposit that was attached to this NEAR function call transaction is already credited to the wallet contract's account by the runtime by the time the method body executes; the only way it is returned to the caller is by the contract explicitly issuing a transfer promise. Because the `action_to_promise` failure path never issues that promise, the deposit is stranded on the wallet contract permanently.

This is structurally identical to the reported bug class: data that passes an initial format/parsing check (here, ABI decoding and `parse_rlp_tx_to_action`) but is only found to be malformed/unsupported at a later processing stage (`action_to_promise`), after funds have already moved custody, with no compensating refund logic on that specific failure path.

### Impact Explanation
This allows unrecoverable loss of user funds (NEAR tokens) attached by any external, unprivileged caller (an ordinary relayer or dApp acting on a user's behalf) invoking `rlp_execute` on a NEAR Wallet Contract instance. The `test_caller_refunds` test in the suite confirms the intended behavior is "external caller gets a refund when the cross-contract call fails" — but this only covers failures surfaced through the promise/callback mechanism, not failures raised earlier by `action_to_promise` itself: [6](#0-5) 

Since the Wallet Contract is meant to be widely deployed for eth-implicit accounts and interacted with by third-party relayers, this represents concrete unauthorized value loss for any caller whose deposit-attached call happens to trigger this un-refunded error path.

### Likelihood Explanation
Reachable by any account (no special privileges) simply calling `rlp_execute` with a deposit and a transaction whose action fails only inside `action_to_promise` (i.e., passes `parse_rlp_tx_to_action`/ABI validation but is rejected when actually being turned into a promise). I was not able to fully enumerate every condition under which `action_to_promise` itself returns `Err` (its definition was not fully retrieved in this session), so I cannot confirm with certainty which exact malformed inputs trigger it or how easy they are to construct — this is the main uncertainty in this analog. Given the existing pattern in the codebase (multiple explicit "faulty relayer"/"user error" branches for malformed ABI data), it is plausible that some validation is deferred to `action_to_promise`, making this reachable, but confirming the precise trigger requires reading that function's full body, which I did not have the remaining budget to fetch.

### Recommendation
- Short term: Ensure that any failure path following the point where `caller_deposit` is computed schedules a refund transfer to `caller_deposit.account_id` before returning the error, not only failures observed through the promise-callback mechanism. Specifically, wrap the `action_to_promise(target, action)?` call so that on `Err`, a refund promise is issued (mirroring the logic already present in `rlp_execute_callback`'s `PromiseResult::Failed` branch) before propagating the error.
- Long term: Audit all `?`-based early-return paths in `inner_rlp_execute` that occur after `caller_deposit` is computed to guarantee no error path can discard an already-captured deposit; add regression tests exercising failures specifically within `action_to_promise` (not just within `parse_rlp_tx_to_action`) to catch this class of bug.

### Proof of Concept
Not independently constructed/verified in this session due to inability to inspect the full body of `action_to_promise`; the vulnerable code path is directly cited above (`lib.rs:466-470` combined with `lib.rs:106-127`). A concrete PoC would require identifying an action for which `parse_rlp_tx_to_action` succeeds (producing a valid `near_action::Action`) but `action_to_promise` returns `Err`, then calling `rlp_execute` as an external predecessor with a nonzero attached deposit and observing that the deposit is not refunded.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
