### Title
Missing shop-match validation in non-embedded cookie session resolution allows cross-tenant session/access-token confusion - ([File: packages/apps/shopify-api/lib/session/session-utils.ts])

### Summary
`getCurrentSessionId`'s non-embedded branch resolves a session id purely from a validly-signed cookie value, without tying that id to the shop implied by the current request (`shop` query param) [1](#0-0) . Consumers are expected to cross-check the resolved session's `shop` against the request's `shop` before trusting it; `shopify-app-express` does this [2](#0-1) , but `shopify-app-remix`'s `AuthCodeFlowStrategy.authenticate` does not, allowing a user who legitimately holds a valid session cookie for shop A to have that session (and its access token) used to service a request whose URL/query claims shop B.

### Finding Description
For non-embedded apps, `getCurrentSessionId` simply returns whatever session id is inside the caller's signed cookie, with no binding to the shop in the request URL: [1](#0-0) 

In `shopify-app-remix`, `getSessionTokenContext` computes `shop` from `url.searchParams.get('shop')` for the non-embedded branch, and independently computes `sessionId` from the cookie via `api.session.getCurrentId`, with no connection between the two: [3](#0-2) 

The loaded session (looked up by the cookie-derived `sessionId`, regardless of shop) is then handed to `AuthCodeFlowStrategy.authenticate`, which only checks whether a session exists and is active/unexpired — it never compares `session.shop` to the `shop` derived from the request: [4](#0-3) 

This is in contrast to `shopify-app-express`'s equivalent flow, which explicitly detects and rejects this exact condition: [5](#0-4) 

The preceding `ensureInstalledOnShop` check in `auth-code-flow.ts` only verifies that shop B (from the URL) has *some* offline session installed on the app (via `getOfflineId(shop)`), it does not verify that the *cookie-derived* session belongs to shop B: [6](#0-5) 

Exploit flow: an attacker with a legitimate account/browser session on shop A obtains a validly signed `shopify_app_session` cookie (issued by the app itself during their own real OAuth flow with shop A — no secret key needed, no forgery of the HMAC). They then send a request to a route on the same app instance with `?shop=shop-b.myshopify.io` while presenting their shop-A cookie. `getCurrentSessionId` returns the shop-A session id (cookie signature validates correctly since it really was signed by the app for the attacker). `AuthCodeFlowStrategy.authenticate` accepts this session because it is active, without checking it matches shop B, and returns shop A's session (including its access token) as the context for what the app/route believes is a shop-B request.

### Impact Explanation
This results in cross-tenant session/access-token confusion: an app instance serving multiple shops with the non-embedded (cookie-based) `AuthCodeFlowStrategy` in `shopify-app-remix` can be tricked into using shop A's `Session`/access token in a request logically scoped to shop B. Depending on how the route handler uses `shop` vs. `session` (e.g., `admin.graphql` calls bound to `session`), this can lead to cross-tenant data leakage or writes against the wrong tenant, and violates the TENANT_ISOLATION invariant.

### Likelihood Explanation
Requires: (1) a non-embedded app built on `shopify-app-remix` using the auth-code-flow strategy with cookie-based sessions, (2) multiple shops installed on the same app instance, (3) attacker has a legitimate account/session on shop A (unprivileged, self-service — no special access), and (4) the app's route logic derives shop context from the URL `shop` param separately from `session.shop` without an app-level cross-check. This is a realistic, low-privilege attacker capability (just replay their own cookie against a different `shop=` query value), but is contingent on the specific `shopify-app-remix` non-embedded/auth-code-flow configuration, so likelihood is moderate rather than universal.

### Recommendation
Add an explicit shop-match check in `AuthCodeFlowStrategy.authenticate` (and any other strategy resolving cookie-derived sessions) mirroring the check already present in `shopify-app-express`'s `validateWithAuthCodeFlow`: after loading `existingSession`, verify `session.shop === shop` (the shop derived from the request) before treating the session as valid; if it doesn't match, treat it as no session and redirect to OAuth for the requested shop.

// packages/apps/shopify-app-remix/.../__tests__/cross-tenant-session.test.ts
it('BUG: accepts shop-A cookie session for a request scoped to shop-B', async () => {
  const shopify = shopifyApp(testConfig({isEmbeddedApp: false}));

  const sessionA = await setUpValidSession(shopify.sessionStorage, {
    shop: 'shop-a.myshopify.io',
  });
  await setUpValidSession(shopify.sessionStorage, {
    shop: 'shop-b.myshopify.io', // shop B is also installed on this app instance
  });

  const request = new Request(`${APP_URL}?shop=shop-b.myshopify.io`);
  await signRequestCookie({
    request,
    cookieName: SESSION_COOKIE_NAME,
    cookieValue: sessionA.id, // attacker's legitimately-signed cookie for shop A
  });

  const {session} = await shopify.authenticate.admin(request);

  // EXPECTED (secure): should redirect to OAuth for shop-b, not return shop-A's session
  expect(session.shop).toBe('shop-b.myshopify.io');
  // ACTUAL (vulnerable): session.shop === 'shop-a.myshopify.io'
});
