### Title
Self-matching orders in `MarketSellAssetActuator` cause silent loss of matched tokens due to stale account state overwrite - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator`, java-tron's native TRC10/TRX order-book exchange actuator, never checks that the maker order being matched belongs to a different account than the taker (the transaction sender). This is the direct analog of the reported `seller != buyer` check missing in `matchOneToOneOrders()`/`matchOrders()` etc. In java-tron's implementation the consequence is not just griefing but an actual accounting bug: when a user's new order self-matches one of their own pre-existing resting orders, the "maker-side" token credit is computed against a stale, unpersisted `AccountCapsule` and is subsequently overwritten and lost when the taker-side account state is persisted at the end of `execute()`.

### Finding Description
`validate()` and `execute()` in `MarketSellAssetActuator` never compare the taker (contract owner, `contract.getOwnerAddress()`) against the owner of any maker order fetched from the order book during matching. [1](#0-0) 

During `execute()`, the taker's `AccountCapsule` is loaded once, mutated in memory across several steps, and only persisted at the very end: [2](#0-1) 

Inside `matchSingleOrder()`, the taker side is credited via the overload that mutates the already-loaded, in-memory `takerAccountCapsule` object (no store read/write): [3](#0-2) 

The maker side is credited via a different overload that re-fetches the account fresh from `accountStore`, mutates it, and immediately persists it back to the store: [4](#0-3) 

When the maker order's owner is the *same* address as the taker (self-match), this maker-side `addTrxOrToken` call fetches a copy of the account from `accountStore` that does **not** yet reflect the in-memory changes already applied to the taker's `accountCapsule` (the sell-token debit and the taker-side buy-token credit), because those changes are still only in memory and haven't been flushed. The maker write then persists that stale copy plus the maker credit. Immediately afterward, `execute()` finishes and unconditionally overwrites the store with the taker's in-memory `accountCapsule`: [5](#0-4) 

This last write clobbers the maker-side credit that was just persisted in `addTrxOrToken(makerOrderCapsule, num)`, so the `makerBuyTokenQuantityReceive` amount is silently dropped from the account's final balance/asset map.

### Impact Explanation
This is an accounting/settlement correctness bug reachable by any unprivileged user, not merely griefing: a user whose new `MarketSellAssetContract` order matches against one of their own existing resting orders in the order book will have the maker-side proceeds of that match permanently disappear from their balance/asset ledger, while the corresponding token/TRX was already debited from the counter-order and consumed as part of matching (the maker order is marked `INACTIVE`/consumed and removed from the book). This constitutes real fund loss for the affected account and a divergence between expected settlement (sum of taker-receive + maker-receive) and actual on-chain state.

### Likelihood Explanation
Likelihood is moderate: it requires a user (or an automated market-making bot operated by a single account) to place resting orders on both sides of the same token pair (e.g., sell A for B and sell B for A) — a common trading pattern for liquidity providers or bots rebalancing inventory — and then have a new order self-match against their own resting order. No malicious counterparty or off-chain coordination is required, unlike the original Solidity report which needed a cooperating/malicious off-chain matching engine; here it can occur purely from ordinary self-trading/order-book usage by a single account.

### Recommendation
In `matchOrder()`/`matchSingleOrder()`, explicitly skip or reject matches where `makerOrderCapsule.getOwnerAddress()` equals the taker's `contract.getOwnerAddress()`. Independently (defense-in-depth), fix the underlying state-management bug by ensuring maker-side account updates in `addTrxOrToken(MarketOrderCapsule, long)` and taker-side updates operate on a single consistently-fetched/persisted `AccountCapsule` per address within one transaction (e.g., cache and reuse account capsules by address, and perform a single `accountStore.put` per address at the end of `execute()`), rather than mixing an in-memory mutate for one side with an immediate fetch-mutate-persist for the other.

### Proof of Concept
1. Account `U` creates order `O1`: sell 100 of Token A, buy 100 of Token B (a resting maker order), added to `pairPriceToOrderStore` via `MarketSellAssetActuator`.
2. Later, the same account `U` creates order `O2`: sell 100 of Token B, buy 100 of Token A (matching `O1`'s price/pair) via a new `MarketSellAssetContract`.
3. In `execute()` for `O2`: `accountCapsule` (U's account) is loaded, debited by 100 Token B (`transferBalanceOrToken`), `O2` is created; `matchOrder()`→`matchSingleOrder()` matches `O2` against `O1`.
4. `addTrxOrToken(takerOrderCapsule=O2, takerBuyTokenQuantityReceive=100 A, takerAccountCapsule)` credits the in-memory `accountCapsule` with 100 Token A (not yet persisted).
5. `addTrxOrToken(makerOrderCapsule=O1, makerBuyTokenQuantityReceive=100 B)` fetches `U`'s account fresh from `accountStore` (still reflecting pre-step-3 state, since nothing has been persisted yet), adds 100 Token B, and persists this to `accountStore` immediately.
6. `execute()` finishes: `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` overwrites the store with the in-memory copy from step 3/4 — which has the 100 Token B debit from step 3 and the 100 Token A credit from step 4, but does **not** include the 100 Token B credit written in step 5.
7. Net result: `U` permanently loses the 100 Token B that should have been credited back as the maker-side proceeds of the self-match, even though `O1` was fully consumed/marked `INACTIVE`.
