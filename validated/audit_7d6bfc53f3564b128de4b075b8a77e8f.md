Webhook HMAC validation signs only the raw body, allowing forged `X-Shopify-Shop-Domain` header to bind an attacker-supplied webhook payload to a victim shop's offline session - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
Shopify webhook authenticity is verified by computing an HMAC over the raw request body only. The `X-Shopify-Shop-Domain` (and topic/webhookId/apiVersion) headers, which determine *which merchant's* session/admin client is loaded to process the webhook, are never included in the signed data. Because the webhook signing secret (`apiSecretKey`) is the app's single client secret shared across every shop that installs the app, any merchant can capture a validly-signed webhook for their own shop and replay the same body+HMAC pair while spoofing the shop-domain header to point at a victim shop, causing the app to process attacker-controlled data using the victim's offline session/admin token.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC purely from `rawBody` and compares it against the `X-Shopify-Hmac-Sha256` header value: [1](#0-0) 

The shop/topic/webhookId/apiVersion values used elsewhere are pulled straight from HTTP headers and are only checked for *presence*, not cryptographically bound to the signed payload: [2](#0-1) [3](#0-2) 

The reference test helper confirms the HMAC is computed as `HMAC-SHA256(secret, body)` with no header material mixed in: [4](#0-3) 

The resulting `check.domain` (sourced from the unauthenticated header) is then used directly to look up and return the shop's **offline session** (containing its admin access token), which is attached to the webhook context together with the attacker-controlled body/topic: [5](#0-4) [6](#0-5) [7](#0-6) 

The lower-level `process()` path (used by `shopify-app-express`) similarly forwards the unauthenticated `webhookCheck.domain` to the registered handler callback alongside the raw body: [8](#0-7) 

Because `apiSecretKey` is the app's single client secret (identical for every shop installation of the app, not per-tenant), a merchant who legitimately installs the app can capture a real webhook (valid body + valid HMAC) delivered to their own shop, then re-POST that exact `(rawBody, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and, if desired, topic/webhookId) headers with a victim shop's domain. The HMAC check still succeeds because it only validates the body, and the app will bind the forged payload to the victim's offline session.

This is the same root-cause pattern as the referenced Solidity bug: a subset of attacker-controlled input (`ref_`/`artId_`/`imageURI` there, shop-domain/topic headers here) is excluded from the cryptographic proof (Merkle hash / HMAC) yet is trusted downstream to select privileged resources (referral payout / art record there, victim's session and admin token here).

### Impact Explanation
An attacker with a legitimate installation of the app on their own shop can trigger the target app's webhook handlers to run with a victim shop's `session`/`admin` client while supplying arbitrary `topic` and `rawBody`. Depending on the app's registered handlers, this enables:
- Cross-tenant confused-deputy actions against the victim's shop (e.g., triggering handlers that call the Admin API using the victim's access token based on attacker-chosen payload data).
- Denial of service / data corruption against the victim tenant if a handler (e.g., `APP_UNINSTALLED`) deletes or mutates session storage keyed by the spoofed shop domain.
- Confusion of per-shop business logic (e.g., order/product sync) between attacker and victim shops.

This is a genuine cross-tenant/unauthenticated-request-acceptance impact, not merely theoretical, since the HMAC's guarantee ("this body was produced by Shopify for this app") is silently extended by the code to also imply "this body belongs to shop X," which is not something the HMAC proves.

### Likelihood Explanation
Medium-High. Exploitation only requires:
1. A single merchant (unprivileged, not the app developer) installs the target public app on their own store to receive at least one legitimately HMAC-signed webhook.
2. That attacker replays the captured body+HMAC to the app's public `/webhooks` endpoint with a forged `X-Shopify-Shop-Domain` header.

No secret leakage, MITM, or privileged access is required — only normal app installation, which is the standard, unprivileged interaction any Shopify merchant can perform.

### Recommendation
- Bind the shop domain (and ideally topic/webhookId) into the HMAC verification, or independently authenticate the domain header against the session store before trusting it (e.g., reject if the offline session for that domain doesn't have a recent webhook subscription record for the observed webhook id, or cross-check webhook id uniqueness/replay).
- Track and reject replayed `webhookId` values per shop, since Shopify webhook IDs are unique per delivery — this closes the specific replay-with-forged-domain vector even though `domain` isn't in the signed body.
- Consider deriving the shop context from a value that is verifiably tied to the specific installation making the original request rather than solely from an unauthenticated header.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook event on that shop, capturing the delivered request: `rawBody`, and headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`.
3. Re-POST to the app's public webhook endpoint with the **same** `rawBody` and `X-Shopify-Hmac-Sha256`, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `validateHmacFromRequestFactory` (packages/apps/shopify-api/lib/utils/hmac-validator.ts) returns `valid: true` because only `rawBody` is checked.
5. `authenticateWebhookFactory`/`process()` calls `ensureValidOfflineSession(params, 'victim.myshopify.com')`, loading the victim's offline session/access token and invoking the app's webhook handler with attacker-supplied `rawBody`/`topic` bound to the victim's `session`/`admin` client.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

import {AppDistribution, BasicParams} from '../types';

export async function createOrLoadOfflineSession(
  {api, config, logger}: BasicParams,
  shop: string,
) {
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    logger.debug('Creating custom app session from configured access token', {
      shop,
    });
    return api.session.customAppSession(shop);
  } else {
    logger.debug('Loading offline session from session storage', {shop});
    const offlineSessionId = api.session.getOfflineId(shop);
    const session = await config.sessionStorage!.loadSession(offlineSessionId);

    return session;
  }
}
