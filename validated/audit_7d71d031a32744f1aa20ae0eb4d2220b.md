## Title
Rounding-to-zero in `MarketUtils.multiplyAndDivide` lets an attacker drain a maker's order for free in the "taker == maker" branch of `MarketSellAssetActuator.matchSingleOrder` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The reported bug is a classic "rounding-to-zero" flaw in a price-derivation formula: `curvePriceWad = (amountInQuote * WAD) / deltaBase` can floor to `0` under imbalanced reserves, which then propagates into a mis-priced (or reverting) trade. Java-tron's TRC10 order-book matching engine, `MarketSellAssetActuator`, contains the same class of bug in integer division for cross-rate conversion via `MarketUtils.multiplyAndDivide` (`floor(a*b/c)`) [1](#0-0) . Unlike the two other call sites in the same function, which explicitly guard against a `0` result, the "taker == maker" branch does **not**, allowing a maker's order to be fully closed while the maker receives zero tokens in return.

### Finding Description
`matchSingleOrder` computes `takerBuyTokenQuantityRemain` and, when it is *exactly* equal to the maker's remaining sell quantity, enters the "taker == maker" branch: [2](#0-1) 

Here `makerBuyTokenQuantityReceive` is computed with `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which performs integer floor division and **is not checked for zero** — unlike the structurally identical computation in the "taker > maker" branch a few lines below, which does check for zero and safely refunds the maker (`makerBuyTokenQuantityReceive == 0` handling, `returnSellTokenRemain`) [3](#0-2) , and unlike the taker-side computation earlier in the same function, which is checked [4](#0-3) .

When `makerBuyTokenQuantityReceive` rounds to `0`:
- `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` — the taker still receives the maker's *entire* remaining sell-token balance.
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0` — the taker's own remaining sell balance is **not reduced at all**.
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` and `updateOrderState(makerOrderCapsule, State.INACTIVE, ...)` are executed unconditionally, permanently closing the maker's order with **zero proceeds credited** (`addTrxOrToken(makerOrderCapsule, 0, ...)`).
- Since `takerSellTokenLeft != 0`, the taker's order stays `ACTIVE` and re-enters the matching loop, so the exploit can be repeated against additional maker orders at the same or adjacent price levels within the same or subsequent transactions.

This is mathematically identical to the Securitize bug: an integer-division price/quantity computation floors to zero under achievable reserve/quantity ratios, and the code path that consumes that zero value lacks the zero-guard present elsewhere in the same function, producing an inconsistent, exploitable state transition.

### Impact Explanation
This is a direct loss-of-funds and broken-accounting bug in an unprivileged, user-facing DEX feature (the TRC10 exchange/market module): any account can construct a sell order (`MarketSellAssetContract`) that matches an existing maker order under the specific ratio/remaining-quantity conditions described, causing the maker's order to be fully consumed and marked `INACTIVE` while receiving `0` tokens, while the taker obtains the maker's full remaining balance without spending any of their own sell tokens (their remaining balance is left untouched and can be reused in further matches). This is a genuine "underpriced/free execution" and accounting-divergence impact matching the External Report's "buyer receives tokens ... seller receives nothing" failure mode.

### Likelihood Explanation
Reaching the exact-equality branch (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`) combined with the rounding-to-zero condition requires a specific combination of `sellTokenQuantity`/`buyTokenQuantity` ratios and small remaining order quantities, but these are all attacker-controlled inputs (the attacker can create both the maker order via one account/order and the taker order via another) or can be found opportunistically by scanning the live order book for maker orders with a small remaining quantity and a sell:buy ratio > 1. No privileged role is required; only ordinary `MarketSellAssetContract` transactions are needed.

### Recommendation
Add the same zero-result guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0` after `MarketUtils.multiplyAndDivide`, refund the maker's remaining sell tokens via `MarketUtils.returnSellTokenRemain` instead of unconditionally zeroing/deactivating the maker order, mirroring the existing safe-guard in `MarketSellAssetActuator.matchSingleOrder` (lines 461-477).

### Proof of Concept
Choose a maker order with `makerSellTokenQuantity = 3`, `makerBuyTokenQuantity = 2` (ratio 1.5), and `makerSellTokenQuantityRemain = 1` (i.e., the maker has previously been partially filled down to 1 unit remaining). An attacker submits a taker sell order for the paired asset with `takerSellTokenQuantityRemain = 1`.

- `takerBuyTokenQuantityRemain = floor(1 * 3 / 2) = 1`, which equals `makerSellTokenQuantityRemain (1)` → enters the "taker == maker" branch.
- `makerBuyTokenQuantityReceive = floor(1 * 2 / 3) = 0`.
- `takerBuyTokenQuantityReceive = 1` (attacker receives the maker's last token).
- `takerSellTokenLeft = 1 - 0 = 1` (attacker's sell balance unchanged; order remains `ACTIVE`).
- Maker order is marked `INACTIVE` with `0` tokens credited — total loss of the maker's remaining 1 unit for nothing in return, and the attacker's order is free to match again against further maker orders. [2](#0-1)
