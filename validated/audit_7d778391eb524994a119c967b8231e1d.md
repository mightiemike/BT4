### Title
Starknet OS `replace_class` syscall does not validate that the target class hash is declared, diverging from Blockifier's execution and enabling wrong committed state roots - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The external report's core issue is that a contract accepts and acts on an externally supplied address/identifier (the voting adaptor) without validating that it refers to a legitimate, properly instantiated entity — it only checks for non-zero, not integrity/validity. The same class of bug exists in the Starknet OS Cairo program's `replace_class` syscall handler: it takes an attacker/user-supplied `class_hash` from a transaction and directly overwrites the contract's class hash in state without checking that this class hash was ever declared, unlike the Rust Blockifier execution path used by the sequencer for real block building, which explicitly performs this check.

### Finding Description
In the Blockifier (the component that actually executes transactions and builds blocks), `replace_class` calls `self.state.get_compiled_class(class_hash)?` before updating state — this both ensures the class is declared and additionally checks it is a Cairo1 (V1) class: [1](#0-0) 

The deprecated syscalls hint processor performs the analogous check for the legacy syscall path: [2](#0-1) 

This is directly tested — an undeclared class hash is rejected with "is not declared", and a V0 class hash is rejected with "Cannot replace V1 class hash with V0 class hash": [3](#0-2) 

However, the Cairo implementation of the same syscall inside the Starknet OS program (used for re-execution/proving of the block, i.e. the component that must reproduce exactly the state transition the sequencer/Blockifier committed) explicitly skips this validation, with an open TODO acknowledging the gap: [4](#0-3) 

The comment at line 902, `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.`, confirms the class hash is written into `contract_state_changes` unconditionally — no read/check against `contract_class_changes` or any declared-class-hash validation is performed, in contrast to Blockifier's `get_compiled_class` check. The legacy (deprecated) syscall variant of `execute_replace_class` has the identical gap: [5](#0-4) 

### Impact Explanation
The Starknet OS is the component that re-executes a committed block (as part of proving/verifying that the sequencer produced a valid state transition). If a transaction invoking `replace_class` with an undeclared (or Cairo0/V0) class hash is executed by Blockifier, it correctly fails/reverts that call (per the tests cited above), meaning the class hash for the contract is left unchanged and the transaction is marked REVERTED (fees still charged, no class replacement). If the OS's `execute_replace_class`/`execute_deploy_syscall`-driven path does not enforce the same declared-class check, then when the OS independently re-executes/re-derives the block's state transition (e.g., during proving or via `starknet_os_flow_tests`), it could compute a different `contract_state_changes` outcome (accepting the class replacement) than what Blockifier actually committed to the block's state diff. This is a state-transition divergence between the block-building component (Blockifier) and the proving/verification component (Starknet OS), which can result in the OS committing to a wrong state root / block hash relative to what the sequencer actually produced, undermining the soundness guarantee that the OS proof attests to the correct execution of the block.

### Likelihood Explanation
Any unprivileged account contract can invoke the `replace_class` syscall as part of its own `__execute__` logic with an arbitrary `class_hash` argument (e.g. via a call chain that includes an undeclared class hash, or one belonging to a Cairo0 class). Reaching this code path requires nothing more than sending a standard `INVOKE` transaction from a deployed account contract that calls `replace_class_syscall(arbitrary_class_hash)`. This makes the divergence reachable by any single submitted transaction without any special privilege, matching the reachable-path requirement.

### Recommendation
Add the same validation to the OS's Cairo implementation of `execute_replace_class` (both in `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo`) that Blockifier performs: verify, via `contract_class_changes` dict reads (or an equivalent hint-backed declared-class check), that the target `class_hash` corresponds to a declared class before updating `contract_state_changes`, and reject (or revert, consistent with Blockifier's error semantics) when it does not, including the Cairo0 vs Cairo1 distinction currently enforced only on the Blockifier side.

### Proof of Concept
1. Declare and deploy an account contract A whose `__execute__` calls `replace_class_syscall(class_hash=X)` where `X` is a class hash that has never been declared on-chain (or is a Cairo0 class hash while A is Cairo1).
2. Submit an `INVOKE` transaction from A calling this entry point.
3. Blockifier executes the transaction: `replace_class` in `crates/blockifier/src/execution/syscalls/syscall_base.rs` (lines 369-378) calls `get_compiled_class(X)`, which fails since `X` is undeclared (or fails the `is_cairo1` check) — the inner call/transaction reverts, and no `CHANGE_CLASS_ENTRY` is recorded in the committed state diff.
4. When the Starknet OS re-executes this same transaction as part of block proving, `execute_replace_class` in `crates/apollo_starknet_os_program/.../syscall_impls.cairo` (lines 881-920) performs no equivalent declared-class check (per the explicit TODO at line 902) and unconditionally updates `contract_state_changes` with the new (undeclared) `class_hash`, unless it is otherwise reverted by unrelated logic — producing a `contract_state_changes` entry inconsistent with what Blockifier actually committed for this contract address.
5. This divergence in the derived `contract_state_changes` between the two independent implementations of the same syscall constitutes a state-transition/state-root mismatch risk for the OS-produced proof relative to the sequencer-committed block.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }

        // Not enough gas to execute the syscall.
