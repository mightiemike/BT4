### Title
Resource Delegation `windowSize` Computed With Floor Division Instead of Ceiling, Causing Resource Usage to Decay Faster Than Intended - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The Sherlock report M-12 describes a rounding-direction bug in Bond Protocol's `BondBaseSDA.sol`: the "delay increment" that advances the debt-decay reference timestamp was rounded down (`mulDiv`) instead of up (`mulDivUp`) as specified in the whitepaper, causing the debt component to decay faster than intended and market price to fall faster than expected. `java-tron`'s bandwidth/energy delegation accounting contains the analogous defect: the weighted-average `windowSize` used to model resource-usage decay after a delegate/undelegate operation is computed with floor (truncating) division in the legacy path, while the newer/"corrected" `*V2` path for the exact same computation explicitly rounds up.

### Finding Description
In `ResourceProcessor.increase()` and `ResourceProcessor.unDelegateIncrease()`, when `dynamicPropertiesStore.supportAllowCancelAllUnfreezeV2()` is `false` (the default/legacy path, still active unless that chain proposal has been activated), the new `windowSize` for an account's resource usage is computed by `getNewWindowSize()`: [1](#0-0) 

```java
private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
    long windowSize, long newUsage) {
  if (hardenCalculation()) {
    BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
        .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
    return bi.divide(BigInteger.valueOf(newUsage)).longValueExact();
  }
  return (lastUsage * lastWindowSize + usage * windowSize) / newUsage;
}
```

Both branches use plain truncating (`BigInteger.divide` / integer `/`) division — i.e., round **down**. This function is called from the non-`allowCancelAllUnfreezeV2` code paths: [2](#0-1) [3](#0-2) 

Compare this to `increaseV2()` / `unDelegateIncreaseV2()`, which compute the exact same "weighted-average window size" quantity but explicitly round **up** using `divideCeilExact`/`divideCeil`: [4](#0-3) 

This shows the codebase's own intended/corrected semantics for this computation is round-up (consistent with `averageLastUsage`/`averageUsage` elsewhere in the same class, which always use `divideCeil`/`divideCeilExact`, e.g. lines 96-104), but the still-live legacy path silently uses floor division for the window-size aggregation, exactly mirroring the Bond Protocol defect where the decay-time increment was rounded down instead of up against spec.

### Impact Explanation
`windowSize` governs how fast an account's resource usage (`NetUsage`/`EnergyUsage`) decays back toward zero — see the `decay = (windowSize - delta) / windowSize` factor used in `increase()`/`increaseV2()`. A `windowSize` that is systematically rounded down (smaller than the mathematically correct weighted value) shortens the effective decay window, so recorded bandwidth/energy usage decays to zero faster than the protocol's accounting model intends. Since `unDelegateIncrease()`/`increase()` are invoked from unprivileged, user-triggered actuators such as `DelegateResourceActuator` and `UnDelegateResourceActuator`, any account delegating/undelegating frozen-balance resources is affected. The practical effect is that a delegator's/receiver's resource usage window (and therefore effective available bandwidth/energy) recovers prematurely relative to the intended decay model — an accounting divergence that under-prices the "decay" cost of resource usage, analogous to the bond market underpricing debt decay in the referenced report.

### Likelihood Explanation
This code path is the default behavior whenever `ALLOW_CANCEL_ALL_UNFREEZE_V2` has not been activated via chain proposal (it is a `ProposalType` gated feature, not always-on), so on any network state where that proposal is inactive, every `DelegateResourceContract`/`UnDelegateResourceContract` transaction from any ordinary account exercises the buggy floor-division `getNewWindowSize()` path. No privileged role is required — it is triggered by normal resource-delegation transactions.

### Recommendation
Round the `windowSize` aggregation in `getNewWindowSize()` up (ceiling), matching the `divideCeil`/`divideCeilExact` semantics already used for the equivalent computation in `increaseV2()`/`unDelegateIncreaseV2()` and for `averageLastUsage`/`averageUsage` elsewhere in `ResourceProcessor`:

```java
private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
    long windowSize, long newUsage) {
  if (hardenCalculation()) {
    BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
        .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
    return divideCeilExact(bi, BigInteger.valueOf(newUsage));
  }
  return divideCeil(lastUsage * lastWindowSize + usage * windowSize, newUsage);
}
```

### Proof of Concept
1. On a network where `ALLOW_CANCEL_ALL_UNFREEZE_V2` is inactive (so `supportAllowCancelAllUnfreezeV2()` returns `false`) but `UNFREEZE_DELAY` support is active (`supportUnfreezeDelay()` returns `true`).
2. Account A delegates bandwidth/energy resource to account B via `DelegateResourceContract`.
3. Account B (or A after receiving resources back) later calls `UnDelegateResourceContract`, triggering `ResourceProcessor.unDelegateIncrease()` → `getNewWindowSize()` at [3](#0-2) .
4. Because `getNewWindowSize()` truncates the weighted-average division instead of rounding up, the resulting `newOwnerWindowSize` stored on the account is smaller than the value the protocol's own `V2` implementation would compute for the identical inputs.
5. Subsequent resource-usage `recovery`/`increase` calls for that account use this too-small `windowSize`, causing the usage average to decay to zero (and thus resource capacity to "free up") in fewer blocks than the correct accounting model specifies — reproducible deterministically by comparing the legacy (`increase`/`unDelegateIncrease`) output against the `V2` (`increaseV2`/`unDelegateIncreaseV2`) output for the same `lastUsage`, `lastWindowSize`, `usage`, `windowSize`, `newUsage` inputs.
