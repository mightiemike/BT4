### Title
Default `constantCallTimeoutMs=0` lets a single `estimateenergy` HTTP request consume dozens of full block-production CPU budgets, enabling unauthenticated DoS - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.calculateCpuLimitInUs` falls back to `maxCpuTimeOfOneTxMs * cpuLimitInUsRatio` for constant calls whenever `constantCallTimeoutMs` is left at its default `0`, meaning a read-only `estimateenergy`/`triggerconstantcontract` call is granted the same CPU deadline as a full block-producing transaction. Because `Wallet.estimateEnergy` performs a binary search that invokes `callConstantContract` roughly 30-40 times per HTTP request (plus retries on `OutOfTimeException`), an attacker can submit one unauthenticated, feeless POST that forces the node to burn dozens of full `maxCpuTimeOfOneTx` slices of wall-clock CPU time.

### Finding Description
`VMActuator.calculateCpuLimitInUs` is: [1](#0-0) 
When `isConstantCall` is true but `constantCallTimeoutMs <= 0` (the documented default), the method returns `maxCpuTimeOfOneTxMs * ONE_THOUSAND * cpuLimitInUsRatio` — i.e., the *same* deadline used for real block-producing/verifying transactions — instead of a bounded, cheap timeout for read-only calls. This value feeds `vmShouldEndInUs` in both `call()` and `create()`: [2](#0-1) [3](#0-2) 

For constant calls, `executorType` is forced to `ET_PRE_TYPE` in `validate()`: [4](#0-3) 
which makes `getCpuLimitInUsRatio()` return `1.0` (full ratio, no reduction) since it only special-cases `ET_NORMAL_TYPE`: [5](#0-4) 
So the effective per-call CPU ceiling for a constant call under default config equals the full `maxCpuTimeOfOneTx` used for block production — confirmed by the existing unit test asserting exactly this fallback behavior: [6](#0-5) 

The attacker-reachable entry point is `EstimateEnergyServlet` → `Wallet.estimateEnergy`, which does a bounded binary search (initial doubling check + `log2` narrowing over the fee-limit range up to `dps.getMaxFeeLimit()`), each iteration calling `cleanContextAndTriggerConstantContract` → `triggerConstantContract` → `callConstantContract` → `VMActuator.validate/execute`: [7](#0-6) 
Additionally, on `Program.OutOfTimeException` the loop retries up to `estimateEnergyMaxRetry` times per binary-search step rather than aborting, amplifying total CPU consumption further: [8](#0-7) [9](#0-8) 

Energy is not a real limiter here: for constant calls `energyLimit` is set to `maxEnergyLimitForConstant` (capped by the caller-supplied `feeLimit`/energy price, but no TRX is actually spent since it's a read-only call) — see the `isConstantCall` branch in `call()`/`create()`: [10](#0-9) [11](#0-10) 
An attacker can craft bytecode (e.g., a tight loop of cheap opcodes) that consumes energy slowly relative to wall-clock time, so the CPU deadline — not the energy limit — becomes the binding constraint, letting each of the ~30-40 internal executions run right up to `maxCpuTimeOfOneTx`.

No existing check mitigates this: there is no per-request or per-node aggregate CPU budget for `estimateEnergy`, no rate limiter tied to constant-call CPU usage, and `constantCallTimeoutMs` (the only mitigation) defaults to `0` (disabled) per `reference.conf`.

### Impact Explanation
This is a DoS via RPC-API: a single unauthenticated, feeless HTTP POST to `/wallet/estimateenergy` can force one node thread to consume CPU time on the order of `(binary-search iterations) × maxCpuTimeOfOneTx` (tens of full block-CPU-budget slices), and can be repeated indefinitely/concurrently by the same attacker to exhaust node CPU resources and stall block processing/RPC serving on that node. This matches the "DoS via RPC-API" bounty impact class, scoped to the single node processing the request (not a network-wide consensus fault).

### Likelihood Explanation
- Precondition: `vm.constantCallTimeoutMs` left at default `0`, which is the shipped default in `reference.conf`.
- Attacker: fully unprivileged — any anonymous HTTP client can call `/wallet/estimateenergy` with a contract engineered to run near-`maxCpuTimeOfOneTx` per execution without triggering `OutOfTimeException` cheaply (or exploiting retries if it does).
- Cost: zero — `estimateEnergy` is a read-only call; no transaction is broadcast, no fee is paid, no signature/permission check applies.
- Repeatability: trivially repeatable and parallelizable across many concurrent requests, amplifying impact linearly with attacker request rate.

### Recommendation
Give constant calls (especially `estimateEnergy`/`triggerConstantContract`) a bounded, independent CPU deadline that does not default to the full block-processing budget:
- Set a sane non-zero default for `vm.constantCallTimeoutMs` (e.g., a small fraction of `maxCpuTimeOfOneTx`) instead of `0`/disabled.
- In `calculateCpuLimitInUs`, when `isConstantCall` is true, never fall back to the full `maxCpuTimeOfOneTxMs * cpuLimitInUsRatio`; always apply an explicit, conservative constant-call ceiling regardless of configuration.
- Add an aggregate CPU/time budget across the whole `estimateEnergy` binary search (cap total wall-clock time or total iterations more strictly), and stop retrying on repeated `OutOfTimeException` rather than consuming `estimateEnergyMaxRetry` additional full-budget executions.

  assertEquals(blockCpuLimitUs, constantCpuLimitUs);
}

  private double getCpuLimitInUsRatio() {

    double cpuLimitRatio;

    if (ExecutorType.ET_NORMAL_TYPE == executorType) {
      // self witness generates block
      if (blockCap != null && blockCap.generatedByMyself
          && !blockCap.hasWitnessSignature()) {
        cpuLimitRatio = 1.0;
      } else {
        // self witness or other witness or fullnode verifies block
        if (trx.getRet(0).getContractRet() == contractResult.OUT_OF_TIME) {
          cpuLimitRatio = CommonParameter.getInstance().getMinTimeRatio();
        } else {
          cpuLimitRatio = CommonParameter.getInstance().getMaxTimeRatio();
        }
      }
    } else {
      // self witness or other witness or fullnode receives tx
      cpuLimitRatio = 1.0;
    }

    return cpuLimitRatio;
  }
