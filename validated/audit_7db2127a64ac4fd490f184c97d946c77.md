### Title
Session-token shop identity not cross-checked against caller-supplied `shop` in `tokenExchange` allows session/shop confusion - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`shopify.auth.tokenExchange()` is the entry point apps use to convert a Shopify App Bridge session token into an offline/online access token (token-exchange OAuth flow). The session token's cryptographic authenticity (HMAC signature, expiry, audience) is verified, but the shop identity carried inside that verified token (`payload.dest`) is never compared against the separate `shop` string argument that the calling code supplies and that actually drives which Shopify domain is contacted and which `Session.shop` value is persisted.

### Finding Description
`tokenExchange()` calls `decodeSessionToken(config)(sessionToken)` purely to validate the JWT and immediately discards the returned payload: [1](#0-0) 

It then builds the request and the resulting `Session` entirely from the caller-supplied `shop` argument, not from the token's verified `dest`/`iss` claim: [2](#0-1) 

`createSession()` likewise stamps the new `Session.shop`, its offline id (`getOfflineId(config)(shop)`), and its online JWT session id (`getJwtSessionId(config)(shop, ...)`) using this same untrusted `shop` value: [3](#0-2) 

This mirrors the reported bug class: the code validates that a credential is authentic (HMAC / signer) but uses a *different, unverified* identity field for the security-relevant action (constructing the endpoint URL and the session/shop mapping) rather than the identity embedded in the verified credential.

In the framework packages that ship with this repo (`shopify-app-remix`, `shopify-app-react-router`, `shopify-app-express`), the `shop` passed into `tokenExchange` is always derived from the verified `payload.dest` of the same session token, so in-the-box usage is safe: [4](#0-3) [5](#0-4) 

However, `shopify.auth.tokenExchange` is a public, documented API and its own reference documentation explicitly shows deriving `shop` from an untrusted request query parameter rather than from the session token: [6](#0-5) 

Any custom integration (non-remix/react-router/express, or a hand-rolled route) that follows this documented pattern is exposed to shop/session confusion: a caller can supply a valid, currently-authenticated session token for Shop A together with an arbitrary `shop` value for Shop B in the same request, and the library will not reject the mismatch before making the token-exchange call and persisting a `Session` keyed to Shop B.

### Impact Explanation
If Shopify's own token-exchange endpoint strictly validates that `subject_token`'s `dest` matches the shop domain in the request URL (as it should), the outbound network call itself will simply fail for a mismatched pair, limiting the blast radius largely to denial-of-service/error noise. However, the local library performs no such check itself, so behavior for a mismatched pair is entirely dependent on server-side Shopify enforcement rather than app-side defense-in-depth; the resulting `Session` object, its storage id (`getOfflineId`/`getJwtSessionId`), and the endpoint contacted are all keyed off the unverified `shop` parameter. Any custom app-server code that follows the library's own documented pattern (`shop` taken from `req.query.shop`) inherits this weakness and stores/looks-up sessions under a shop identity that was never cryptographically tied to the session token used to obtain it.

### Likelihood Explanation
Low-to-moderate: exploitation requires (1) a custom integration that does not derive `shop` from the verified JWT `dest` — which is exactly what the package's own documentation illustrates — and (2) that the actual security boundary sits entirely on Shopify's OAuth server correctly rejecting subject_token/shop mismatches, which is outside this repository's control and cannot be verified here.

### Recommendation
Have `tokenExchange()` capture the decoded payload and assert that `new URL(payload.dest).hostname` (after applying the same `sanitizeShop` normalization) matches the `shop` argument before making the outbound request, throwing `InvalidJwtError`/`InvalidShopError` on mismatch — mirroring the defense-in-depth already used for `dest`-derived shop elsewhere (`getSessionTokenContext`, `performTokenExchange`). Update the public `tokenExchange` docs to stop showing `shop` sourced from a request query parameter and instead show it derived from the decoded session token.

### Proof of Concept
1. Obtain a valid, signed session token for `shop-a.myshopify.com` (e.g., via App Bridge in a session for Shop A).
2. Following the documented usage pattern, call `shopify.auth.tokenExchange({ shop: 'shop-b.myshopify.com', sessionToken: <token for shop-a>, requestedTokenType: RequestedTokenType.OfflineAccessToken })`, as illustrated in [6](#0-5) .
3. Observe that `token-exchange.ts` performs no comparison between the token's `dest` and the supplied `shop` before issuing `POST https://shop-b.myshopify.com/admin/oauth/access_token` with `subject_token` bound to shop-a, and — if Shopify's endpoint were to accept it — would create/store a `Session` with `shop: 'shop-b.myshopify.com'` id'd via `getOfflineId(config)('shop-b.myshopify.com')`, per [7](#0-6) .

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };
