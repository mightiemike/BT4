### Title
Unbounded recursive receipt-chain traversal in `tx_status`/`tx` RPC handling causes stack overflow and node crash - ([File: chain/chain/src/chain.rs])

### Summary
`Chain::get_recursive_transaction_results` in `chain/chain/src/chain.rs` recursively walks the tree of receipts descending from a transaction's outcome with no depth limit and no iterative/stack-based rewrite, unlike other similar traversal functions in the codebase that were explicitly hardened against stack overflow.

### Finding Description
`get_recursive_transaction_results` recurses once per receipt id found in `outcome.receipt_ids`, and is invoked by `get_final_transaction_result`, which backs the public `tx`/`tx_status`/`EXPERIMENTAL_tx_status` JSON-RPC methods (via `ViewClientActor::get_tx_status` → `Chain::get_partial_transaction_result_option`/`get_final_transaction_result`, exposed through `chain/jsonrpc/src/lib.rs`'s `tx_status_common`/`tx_status_fetch`): [1](#0-0) 

Because a NEAR account/contract can produce arbitrarily long *chains* of receipts (a "linear" chain of cross-contract calls: A calls B, B calls C, C calls D, ...), the recursion depth of `get_recursive_transaction_results` is bounded only by however many hops a transaction submitter manages to string together across the transaction's lifetime, not by any protocol-level constant. This is directly analogous to the Mosquitto bug (CVE-2019-11779), where a client-controlled input with an unbounded number of repeated separators/levels drives unbounded native-stack recursion in a parser and overflows the stack.

Other similar traversal code in the codebase has since been explicitly rewritten to avoid this class of bug:
- `trie_recording.rs::get_subtree_size` was converted to an iterative `VecDeque`-based walk specifically "to avoid any potential stack overflows" [2](#0-1) .
- The newer `GetReceiptToTx` RPC handler explicitly caps chain traversal at `MAX_DEPTH=1000` and returns a `DepthExceeded` error rather than recursing unbounded [3](#0-2) .

`get_recursive_transaction_results` has no such protection, and it is reachable purely by an unprivileged RPC caller/transaction submitter querying the status of their own (or any) transaction after having caused a sufficiently deep receipt chain to accumulate in the chain's outcome store.

### Impact Explanation
A stack overflow in Rust is undefined behavior / an abort that crashes the process. Since `ViewClientActor` (which handles `tx`/`tx_status`/`EXPERIMENTAL_tx_status`) typically runs in the same node process as validator/RPC infrastructure, a crafted deep receipt chain, once queried via a standard read-only RPC call, can crash the serving node. If this RPC path is exposed by validator or seed nodes (which is common), this becomes a transaction/RPC-triggered node crash — a form of a transaction-triggered halt, one of the explicitly in-scope impacts.

### Likelihood Explanation
Building a long, purely linear receipt chain is achievable by an unprivileged contract deployer using ordinary cross-contract call chaining (`promise_then`/`promise_batch_then`), as demonstrated by the codebase's own `max_self_recursion_delay` test contract, which self-chains dozens to hundreds of hops within gas limits of a single receipt-processing window [4](#0-3) . An attacker willing to spend gas across many blocks/epochs (there is no protocol cap on total chain length over time, only per-block gas) can extend such a chain far beyond what a native thread stack (default ~8MB, smaller in some deployment configs) can support for a per-frame recursive call that pushes to a `Vec` and calls `get_execution_outcome`. Exact frame size and thus exact required depth are unverified without a live build/binary, so the precise number of hops needed is an estimate rather than a proven constant.

### Recommendation
Rewrite `Chain::get_recursive_transaction_results` to use an explicit stack/queue (as already done in `trie_recording.rs::get_subtree_size`) instead of native recursion, and/or impose an explicit maximum receipt-chain depth (mirroring the `MAX_DEPTH=1000` pattern used in the newer `GetReceiptToTx` handler) with a graceful error returned to the RPC caller when exceeded, rather than allowing unbounded stack growth.

### Proof of Concept
Conceptual (not executed, since this environment has no code-execution access):
1. Deploy a contract exposing a recursive/self-chaining method similar to `max_self_recursion_delay`, but designed to continue the receipt chain indefinitely across many blocks (e.g., re-triggering itself via cron-like scheduled calls or repeated resubmission), building a linear chain of tens/hundreds of thousands of receipts hanging off a single originating transaction hash.
2. Once the chain has grown sufficiently deep, call the public `tx`/`tx_status`/`EXPERIMENTAL_tx_status` JSON-RPC method for the original transaction hash against a node that tracks the relevant shard.
3. `ViewClientActor::get_tx_status` → `Chain::get_final_transaction_result` → `get_recursive_transaction_results` recurses once per receipt in the chain with no depth bound, exhausting the native stack and crashing the serving process.

Note: the exact chain length required to trigger a real stack overflow depends on compiled frame size, thread stack size, and inlining, none of which could be measured in this read-only, non-executing environment; this PoC establishes the reachable code path and its lack of bound rather than a confirmed crash threshold.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,

        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );

}
