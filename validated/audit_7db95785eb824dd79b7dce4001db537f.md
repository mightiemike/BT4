### Title
Nested `WithdrawFromGasKey` inside a `DelegateAction` bypasses the pending-transaction-queue's gas-key balance accounting, allowing gas-key overspend/double-spend within a chunk-production window - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
The SPICE `PendingTransactionQueue` tracks a gas key's uncertified spend so that concurrently-admitted transactions cannot collectively overdraw a gas key's balance before the chunks that spend it are certified. It does this by scanning `tx.actions()` — the **top-level** actions of the submitted transaction — for `Action::WithdrawFromGasKey` and adding the withdrawn amount to `pending_gas_key_costs`. A `WithdrawFromGasKey` action nested inside a `DelegateAction` (a meta-transaction) is never a top-level action of the *outer* transaction the queue scans, so its effect on the gas key's balance is invisible to admission control while remaining fully executed by the runtime. This is the same bug class as the GitLab advisory: a restricted/derived credential path (a meta-transaction relayed on someone's behalf, analogous to a "deploy key") bypasses an authorization/accounting gate ("push to archived repo" / gas-key spend limit) that the primary path enforces.

### Finding Description
`ShardedPendingTransactionQueue::add_chunk_transactions` builds a per-chunk `PendingChunkData` and specifically scans `tx.actions()` for `WithdrawFromGasKey` to update `gas_key_costs`: [1](#0-0) 

This scan only ever sees the outer transaction's action list. If the withdrawal is embedded as an inner action of a `DelegateAction` (submitted via `Action::Delegate`), it is not a top-level action and is skipped by this loop and by the identical scan in `PendingTxSession::check_pending`: [2](#0-1) 

The protocol authors were aware of this and added a fix, `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`, whose doc comment states the root cause directly: [3](#0-2) 

The fix is enforced in `validate_delegate_action`, gated behind the protocol feature and only for `ValidateReceiptMode::NewReceipt`: [4](#0-3) 

Critically, this feature is bucketed with a set of features pinned to protocol version 87 (`RejectDelegateV2`, `FixContractLoadingError`, `UniversalAccounts`, etc.): [5](#0-4) 

The repo's own architecture spec states the currently-verified stable protocol version for this tree is 86 ("`STABLE_PROTOCOL_VERSION = 86`"): [6](#0-5) 

This means that at the protocol version actually active/stable on this codebase, `RejectWithdrawFromGasKeyInDelegate` is **not yet enabled**, so the guard in `validate_delegate_action` does not fire and a delegated `WithdrawFromGasKey` is admitted and executed normally by the runtime (`action_withdraw_from_gas_key` in `access_keys.rs`), while the pending-transaction-queue's accounting continues to miss it. The runtime-level execution of `WithdrawFromGasKey` is unconditional and correctly moves balance from the gas key to the account — the bug is purely in the *admission-control* accounting used for concurrent-chunk gas-key balance enforcement.

An explicit regression test in the repo confirms the pre-upgrade behavior: the nested withdrawal executes successfully and drains the gas key even though it is a meta-transaction: [7](#0-6) 

### Impact Explanation
The pending-transaction-queue's gas-key balance tracking exists specifically to prevent a gas key from having more of its balance committed across concurrently-pending (uncertified) chunks than it actually holds — this is the SPICE equivalent of double-spend prevention for gas keys, analogous to how `paid_from_balance` prevents overspending a regular account's balance across pending chunks. By routing a `WithdrawFromGasKey` through a `DelegateAction`, an attacker (the gas key owner, or anyone who can get a relayer to relay such a delegate on their behalf) can withdraw funds from a gas key multiple times within the same pending-chunk window without the queue accounting for the drain, because `check_pending`/`add_chunk_transactions` only ever inspect top-level actions. This can result in the gas key's actual on-chain balance requirement being violated relative to what concurrent chunk producers believed was available — i.e., unauthorized value movement / balance-accounting bypass reachable directly from a signed meta-transaction submitted over RPC, with no reliance on malicious validators, peers, or operators.

### Likelihood Explanation
This is trivially reachable by any account holding (or delegating for) a gas key: it only requires constructing a `SignedDelegateAction` whose inner `actions` contains `Action::WithdrawFromGasKey`, wrapped in an outer `Action::Delegate`, and submitting it via ordinary RPC (`send_tx`/`send_tx_and_wait`), exactly as demonstrated in the repository's own test. No elevated privileges, validator collusion, or race conditions beyond ordinary chunk-production timing are needed. The only mitigating factor is that the fix (`RejectWithdrawFromGasKeyInDelegate`) already exists in code, gated by protocol version — but per the codebase's own documentation the currently active stable protocol version (86) predates its activation (grouped at v87), so on that version the vulnerable path is live.

### Recommendation
- Confirm the actual protocol version scheduled for mainnet activation and ensure `RejectWithdrawFromGasKeyInDelegate` is enabled at or before that version; do not allow a window where the fix exists in code but is inactive.
- Independently of the validation-time rejection, make `PendingTransactionQueue`'s scanning logic recurse into `DelegateAction`/`DelegateV2` inner actions (not just top-level actions) so that any nested `WithdrawFromGasKey` is correctly accounted for even for older, still-supported protocol versions.
- Add defense-in-depth by having the ephemeral verifier/apply path independently re-validate the gas key's balance against uncertified pending state rather than relying solely on the mempool-level admission check.

### Proof of Concept
The repository already contains a working reproduction demonstrating the bypass pre-upgrade: [8](#0-7) 
This builds a `DelegateAction` whose `sender_id == receiver_id == sender`, with a single inner action `Action::WithdrawFromGasKey`, signed by the sender's plain access key and wrapped in `Action::Delegate`, then submitted through a relayer. The test explicitly asserts that, before the protocol upgrade activating `RejectWithdrawFromGasKeyInDelegate`, this delegated withdrawal is admitted and successfully drains the gas key: [9](#0-8) 
Because the pending-transaction-queue's action scan (`add_chunk_transactions`/`check_pending`) only inspects top-level actions, submitting several such delegated withdrawals concurrently across pending (uncertified) chunks will not be reflected in `pending_gas_key_costs`, allowing the aggregate withdrawn amount within the pending window to exceed what the admission control believes is available.
