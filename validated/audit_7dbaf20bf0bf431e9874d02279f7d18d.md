### Title
Disk-index `BucketMap` bucket selection uses a fixed, non-randomized pubkey prefix, unlike the in-memory index, enabling grindable bucket concentration - ([File: bucket_map/src/bucket_map.rs])

### Summary
The PoolTogether finding is a case of trusting attacker-supplied/attacker-influenced input (a malicious ticket's arbitrary balance/supply) without validation, letting the attacker skew accounting to their advantage. The closest analog in AccountsDb-adjacent code is `BucketMap::bucket_ix()` [1](#0-0) , which selects a disk-index bucket by reading fixed, non-randomized bytes straight out of the pubkey the (unprivileged) account owner fully controls, in contrast to the in-memory `PubkeyBinCalculator` used for the primary accounts index, which explicitly randomizes its byte/bit offset per process specifically to prevent this exact kind of grinding.

### Finding Description
`AccountsIndex`'s in-memory bin calculator, `PubkeyBinCalculator`, is built with a randomized offset chosen at each validator's startup: [2](#0-1) 
The comment states directly that this is a grinding defense: "Skip the beginning and end of the pubkey range, which is the most common to grind." Each validator gets a *different* offset (`with_bins()` uses `rng()`), so an attacker cannot know which bytes of the pubkey determine a given validator's bin, and cannot craft a set of pubkeys that all collide into the same bin on every validator.

`bucket.rs`'s per-bucket internal index/hash (`bucket_index_ix`) has the identical defensive rationale and mechanism, using a locally-generated random seed: [3](#0-2) 

However, the top-level `BucketMap::bucket_ix()` — which decides which of the (much smaller, `max_buckets_pow2`-sized) top-level disk-index buckets a pubkey maps into — reads a fixed, un-randomized slice of the pubkey's raw bytes: [1](#0-0) 
`read_be_u64` always reads bytes `[0..8]` of the pubkey, and the bucket is derived from the top `max_buckets_pow2` bits of that fixed 64-bit prefix: [4](#0-3) 
There is no per-process randomization anywhere in this path (unlike `PubkeyBinCalculator::with_bins()`), and the mapping is deterministic and identical on every validator that enables the disk-backed accounts index (`--accounts-index-bins` / disk index config feeding into `BucketMapConfig`, wired via `accounts-db/src/accounts_index/bucket_map_holder.rs` and `accounts_index_storage.rs`).

Because Solana pubkeys are freely generatable by any unprivileged user (via ordinary keypair generation, `Pubkey::create_with_seed`, or PDA `find_program_address` bump-seed grinding), an attacker can cheaply grind for many keys whose top `max_buckets_pow2` bits of `bytes[0..8]` collide on a single target bucket — this needs on average only `2^max_buckets_pow2` attempts, and (unlike attacking `PubkeyBinCalculator`) the same offset works identically against every honest validator, because the selection is not randomized per node.

### Impact Explanation
An unprivileged user who funds/creates a large number of accounts whose addresses collide into a single top-level `BucketMap` disk-index bucket can force that one bucket's index file (and its associated data buckets) to grow far larger than the statistically expected size for the configured `max_buckets`, while other buckets remain sparse. This is a disproportionate storage and CPU cost: lookups, inserts, and resizes (`Bucket::grow`, `batch_insert_non_duplicates_internal`) against the disk index degrade for accesses that land in the oversized bucket, on every disk-index-enabled validator identically (since the mapping is deterministic and not process-randomized). This matches the in-scope impact category "disproportionate storage and CPU cost," analogous to how the malicious-ticket bug let an attacker inflate accounting values by supplying data the protocol trusted without bound — here the attacker "supplies" the pubkey itself, and the protocol trusts a fixed byte-window of it as a uniformly-distributed hash without validating/rerandomizing that assumption at the top bucket-selection layer.

### Likelihood Explanation
Likelihood is speculative/moderate: the disk index (`BucketMap`) is an optional accounts-index backing store (not the default in-memory `PubkeyBinCalculator` path), so exploitability depends on the operator's index configuration. Grinding pubkeys against a fixed 8-byte prefix is computationally cheap (`2^max_buckets_pow2` on average, typically a small number of bits given realistic `max_buckets` sizes), and account creation itself costs only rent-exempt lamports plus a transaction fee — no special privilege is required. This is weaker than a wallet-drain but stronger than a purely theoretical issue, since the randomization gap is real and intentional in the sibling code path.

### Recommendation
Apply the same per-process randomized byte/bit-offset technique used by `PubkeyBinCalculator` (`accounts-db/src/pubkey_bins.rs`) to `BucketMap::bucket_ix()`, e.g., derive the top-level bucket index from a randomized (per-validator-instance, not necessarily persisted-restart-incompatible) hash of the pubkey rather than a fixed byte offset, or route bucket selection through the same `PubkeyBinCalculator`/`ahash::RandomState`-seeded mechanism already used inside `bucket.rs` for intra-bucket hashing.

### Proof of Concept
Conceptual PoC (cannot be executed without full repository/build access, and index-config wiring was not fully confirmed in this pass):
1. Configure a validator/tool with the disk-backed accounts index enabled (`BucketMapConfig` with some `max_buckets_pow2 = N`).
2. Off-chain, grind keypairs (or PDA seeds) such that the top `N` bits of `bytes[0..8]` of the pubkey are identical for a large batch of addresses (expected ~`2^N` attempts per matching key, trivially parallelizable).
3. Fund/create accounts for all of these pubkeys via ordinary `SystemProgram::CreateAccount` transactions (no elevated privilege needed).
4. Observe that `BucketMap::bucket_ix()` [5](#0-4)  routes all of them into the same on-disk index bucket, growing that bucket's `BucketStorage`/`Bucket::grow` far beyond the average, while `PubkeyBinCalculator`-based in-memory bins receiving the same pubkeys would spread across bins unpredictably per-validator due to its randomized offset — confirming the asymmetric, grindable behavior specific to `BucketMap`.

    /// Get the bucket index for Pubkey `key`
    pub fn bucket_ix(&self, key: &Pubkey) -> usize {
        if self.max_buckets_pow2 > 0 {
            let location = read_be_u64(key.as_ref());
            (location >> (u64::BITS - self.max_buckets_pow2 as u32)) as usize
        } else {
            0
        }
    }

impl PubkeyBinCalculatorBuilder {
    /// Builds a `PubkeyBinCalculator` with `num_bins`.
    ///
    /// The returned bin calculator will produce *unique* mappings
    /// compared to other bin calculators!
    ///
    /// # Panics
    ///
    /// This function will panic if the following conditions are not met:
    /// * `num_bins` must be a power of two
    /// * `num_bins` must be <= 2^25
    pub fn with_bins(num_bins: NonZeroUsize) -> PubkeyBinCalculator {
        // Skip the beginning and end of the pubkey range, which is the most common to grind.
        const SKIP: usize = 16;
        let offset = rng().random_range(SKIP..=(MAX_OFFSET - SKIP));
        Self::with_bins_and_offset(num_bins, offset)
    }
