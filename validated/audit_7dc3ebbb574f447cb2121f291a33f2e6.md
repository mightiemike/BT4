### Title
`set-pause-liquidation` never clears `pause-liquidation` on unpause, permanently freezing liquidations - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
The market contract's liquidation pause toggle mutates the wrong state variable on the "unpause" branch: when transitioning from paused to unpaused, the function only writes a grace-period timestamp and never resets the `pause-liquidation` boolean itself, so `liquidation-paused` continues to read `true` forever after the first pause, unconditionally blocking all liquidations even after governance calls the unpause path.

### Finding Description
The market's liquidation circuit breaker is implemented as:
```clarity
(define-data-var pause-liquidation bool false)
(define-data-var liquidation-grace-end uint u0)

(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (if (and was-paused (not paused))
        ;; When unpausing, set grace period
        (var-set liquidation-grace-end
                 (+ stacks-block-time grace-period))
        (var-set pause-liquidation paused))))

(define-read-only (liquidation-paused)
  (let ((manual-pause (var-get pause-liquidation))
        (grace-active (< stacks-block-time
                         (var-get liquidation-grace-end))))
    (or manual-pause grace-active)))
``` [1](#0-0) 

This is the documented behavior for `mainnet/contracts/market/v0-4-market.clar`, whose source confirms matching identifiers `pause-liquidation`, `liquidation-grace-end`, `set-pause-liquidation`, `liquidation-paused` all present in that file [2](#0-1) .

The bug is a mutation-evaluated-under-the-wrong-guard analog: the `if` branch intended to perform "unpause" (`was-paused` is `true` and the caller passes `paused = false`) writes only `liquidation-grace-end`, leaving `pause-liquidation` untouched at `true`. The `var-set pause-liquidation paused` call — the only line that can ever set the flag back to `false` — sits in the `else` branch, which is unreachable for the unpause case because the `if` condition `(and was-paused (not paused))` is exactly the unpause case. Consequently:
- Governance calls `set-pause-liquidation false grace-period` intending to resume liquidations.
- `was-paused` is `true`, `paused` is `false` → the `if` branch executes → only `liquidation-grace-end` is updated.
- `pause-liquidation` remains `true` (its value from the earlier pause call) permanently.
- `liquidation-paused` reads `(or manual-pause grace-active)`; since `manual-pause` is always `true` once the market has ever been paused, `liquidation-paused` returns `true` forever, regardless of the grace period elapsing.

The only way to actually reset `pause-liquidation` to `false` is to call `set-pause-liquidation false ...` while `was-paused` is `false` — which is a no-op state already, or call `set-pause-liquidation true ...` (which just re-pauses). There is no code path that flips the flag from `true` back to `false`.

### Impact Explanation
Once the DAO pauses liquidations for any reason (security incident, oracle outage, planned maintenance) and then attempts to unpause, the market permanently retains `pause-liquidation = true`. All under-collateralized positions become permanently unliquidatable through the normal governance-intended unpause flow, exposing the protocol to insolvency risk as bad debt accumulates without any liquidation mechanism to clear it. This is a temporary/permanent freezing-of-funds-class issue at the protocol level (liquidators' expected yield/fees are also permanently frozen), landing squarely on the in-scope "permanent freezing of funds" / protocol solvency impact category.

### Likelihood Explanation
This triggers on the very first legitimate governance action pausing and then unpausing liquidations — a normal, expected operational sequence, not an edge case requiring adversarial interleaving. Any DAO-authorized caller of `set-pause-liquidation` following the documented pause→unpause flow reproduces the bug deterministically in a single transaction.

### Recommendation
In the unpause branch, also reset `pause-liquidation` to `false` (or restructure so `var-set pause-liquidation paused` always executes, with the grace-period write added as an additional side effect only in the unpause transition):
```clarity
(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (var-set pause-liquidation paused)
    (if (and was-paused (not paused))
        (var-set liquidation-grace-end (+ stacks-block-time grace-period))
        true)))
```

### Proof of Concept
1. DAO calls `set-pause-liquidation true u0` → `pause-liquidation` becomes `true`.
2. DAO calls `set-pause-liquidation false u3600` intending to resume liquidations after a 1-hour grace period.
3. Inside the function, `was-paused` is `true`, `paused` is `false`, so the `if` branch runs: only `liquidation-grace-end` is set to `stacks-block-time + 3600`; `pause-liquidation` is never reset.
4. Any subsequent call to `liquidation-paused` evaluates `(or manual-pause grace-active)`; `manual-pause` is `(var-get pause-liquidation)` = `true`, so the result is `true` forever, even after the grace period timestamp passes.
5. All liquidation entry points gated by `liquidation-paused` remain blocked indefinitely, with no governance call able to clear the state short of a contract upgrade.
