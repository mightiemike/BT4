## Title
Global resource weight (`TotalNetWeight`/`TotalEnergyWeight`) can be freely manipulated within a block via cost-free freeze/unfreeze round-trips, corrupting bandwidth/energy limit calculations for all accounts - ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java])

### Summary
The Aloe report describes a spot-state, single-block manipulable "liquidity" parameter that feeds directly into a risk ratio (IV → LTV) with no TWAP smoothing, at zero cost beyond gas. java-tron has a structurally identical pattern: `TotalNetWeight`/`TotalEnergyWeight` are global spot counters that are incremented the instant TRX is frozen and decremented the instant unfreeze is *requested* (not when funds are actually returned), and every account's bandwidth/energy limit is computed on-the-fly from the current value of these counters with no time-averaging.

### Finding Description
`FreezeBalanceV2Processor.execute` (called by `FreezeBalanceV2Actuator`) increments the global weight immediately when TRX is frozen: [1](#0-0) 

`UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor.updateTotalResourceWeight` decrements the same global counter as soon as `UnfreezeBalanceV2Contract` is executed: [2](#0-1) 

Critically, `UnfreezeBalanceV2Actuator.validate()` enforces no minimum freeze duration and no cooldown between freeze and unfreeze — it only checks that the account currently has a matching frozen balance and that the number of concurrent unfreeze requests is under 32: [3](#0-2) 

The actual TRX is only returned after `unfreezeDelayDays`, but the *effect on the global weight* is instantaneous and reversible with a second, unrestricted transaction. This mirrors Aloe's "deposit, call update, withdraw" pattern exactly: freeze (inflate weight) or unfreeze (deflate weight), use the manipulated global value, then reverse the action later — all at the cost of two transaction fees.

This manipulated global weight is the direct input (no TWAP) to every account's derived resource limit: [4](#0-3) [5](#0-4) 

The same spot value is also used for computing how much resource an account can delegate to others (`calcCanDelegatedEnergyMaxSize`/`calcCanDelegatedBandWidthMaxSize`) and for computing usage transferred during undelegation: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker (or colluding accounts) can call `UnfreezeBalanceV2Contract` to instantly deflate `TotalEnergyWeight`/`TotalNetWeight`, which inflates the `totalEnergyLimit/totalEnergyWeight` (or net equivalent) ratio used by `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` for every account with existing frozen balance in that same block window — giving attackers (or anyone) an inflated energy/bandwidth quota to run TVM calls essentially for free, and simultaneously degrading the resource available to all other legitimate frozen accounts sharing the same denominator. Conversely, freezing a large amount inflates the weight, temporarily shrinking everyone's derived limit. Because the frozen principal is never actually lost (only delayed for legitimate withdrawal; the weight-adjustment itself has no delay), this is a free (gas-only) DoS/resource-theft primitive against the shared bandwidth/energy pool, directly analogous to the "IV decreased for free" bug pattern in the report.

### Likelihood Explanation
`FreezeBalanceV2Contract` and `UnfreezeBalanceV2Contract` are ordinary, unprivileged, anonymously-broadcastable transactions requiring only TRX balance/frozen balance ownership — no special permissions. There is no minimum lock duration in the V2 model and no rate-limiting on how often the weight can be toggled by a single account (up to 32 concurrent unfreezes are allowed). The manipulation is reachable from any node via standard broadcast transactions.

### Recommendation
Do not let a single freeze/unfreeze transaction instantaneously move the global `TotalNetWeight`/`TotalEnergyWeight` used for the *current* block's resource-limit computation. Options: (1) apply the weight delta only after the same cool-down/lock period enforced for principal withdrawal (so weight changes track fund availability, not intent), or (2) use a time-weighted/smoothed average of `TotalNetWeight`/`TotalEnergyWeight` over recent blocks (analogous to the report's TWAP recommendation) when computing `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`, so a single-block freeze/unfreeze round trip cannot materially move any account's derived resource limit.

### Proof of Concept
1. Attacker account A freezes a very large amount of TRX for ENERGY via `FreezeBalanceV2Actuator`, immediately incrementing `TotalEnergyWeight` (`repo.addTotalEnergyWeight(...)`).
2. In a following transaction (no minimum hold time required), A calls `UnfreezeBalanceV2Actuator`, which immediately decrements `TotalEnergyWeight` back down via `updateTotalResourceWeight`, while the actual TRX remains locked pending `unfreezeDelayDays` — the weight change is already committed to the shared global state.
3. Between steps 1 and 2 (or by orchestrating unfreeze-then-refreeze in the opposite order to deflate the weight instead), any account calling `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` (e.g., during a TVM call or via `getAccountResource`) computes its limit using the manipulated `TotalEnergyWeight`/`TotalNetWeight`, yielding an incorrect (inflated or deflated) resource limit for the duration of the manipulation, at the cost of only transaction fees.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
