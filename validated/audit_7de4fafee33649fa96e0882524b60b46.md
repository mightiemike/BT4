### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, allowing replay/verification tooling to accept a divergent committed state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by chunk replay/verification paths (`execution/executor/src/chunk_executor/mod.rs::verify_execution`, `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`) to confirm that a locally re-executed transaction output matches the persisted, ledger-committed `TransactionInfo`. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly and admittedly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that authenticate the state/hot-state/position Merkle roots against the transaction accumulator.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  compares only 4 fields between the locally computed `TransactionOutput` and the trusted `TransactionInfo` supplied by the caller (obtained from an already-verified accumulator proof or persisted ledger): execution status, gas used, write-set hash, and event root hash. It never compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against any locally-derived root. The function contains a code comment self-acknowledging the gap: [2](#0-1) 

This function is the authoritative correctness gate in two real commit/verification paths:
- `ChunkExecutorInner::verify_execution`, called during `TransactionReplayer` chunk replay (state-sync / restore replay path), at [3](#0-2) .
- `replay_on_archive`'s `execute_and_verify`, the archival-replay verification tool that re-executes historical transactions and cross-checks them against persisted `TransactionInfo`, at [4](#0-3) .

Because neither caller independently re-verifies the checkpoint hashes elsewhere in this comparison step, a locally computed state root (state Merkle root, hot-state root, or the newer position/"trading-native" state root) that diverges from what is embedded in the committed `TransactionInfo` will not be caught by this function. As long as status, gas, write-set hash, and event root all match, `Ok(())` is returned, i.e., verification/replay reports success despite the authenticated checkpoint root being wrong.

### Impact Explanation
This breaks the "committed state must match verifier's locally computed VM/state result" invariant described in the task's proof/storage pivots. Concretely:
- During chunk replay (state sync from a chunk executor, restore path in `storage/backup/backup-cli`), a bug in state-checkpoint-root computation (e.g., in `DoStateCheckpoint`, hot-state, or the position/trading-native state summary code) would silently pass local verification, because `ensure_match_transaction_info` never compares the checkpoint hash it recomputes against the one baked into the trusted `TransactionInfo`.
- `db-tool`'s `replay_on_archive`, which exists specifically to detect state divergence/hard-fork bugs by replaying historical transactions against an archive node and comparing to committed info, would falsely report a clean replay even when the state/hot-state/position root differs from the authenticated ledger data. This directly undermines the tool's purpose of detecting exactly the class of hard-fork/consensus-divergence bugs called out in the task's scope ("Hard-fork-only divergence during commit, replay, restore, or proof verification").

This is a genuine correctness gap in a security-relevant integrity check, but the concrete state-corrupting effect (an actual divergent checkpoint hash reaching a `TransactionInfo`) still requires that another component (e.g., `DoStateCheckpoint`, hot-state materialization, or the trading-native/position-state root computation) independently miscomputes the root and gets committed to the accumulator — this comparator's gap is a "silent verifier" bug rather than a state-corruption bug on its own. Given the position/trading-native feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is explicitly noted in the TODO as "before enabling," it is plausible this is pre-production/gated functionality, which affects how far this can be considered a currently-exploitable mainnet issue versus a documented pre-launch gap.

### Likelihood Explanation
The code path is always reachable when replay/verify tooling or chunk-executor-based state sync runs (`VerifyExecutionMode::Verify` in normal chunk replay, and any invocation of `replay_on_archive`); no attacker action or feature flag is needed to reach the comparator itself. However, *triggering* an actual divergence requires an independent root-computation bug elsewhere (e.g., in state-checkpoint or position-state root logic), so likelihood of an actual undetected divergence depends on the correctness of those other components, which I did not exhaustively audit given the scope and time available.

### Recommendation
Extend `ensure_match_transaction_info` to also compare locally recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when applicable/known) against `txn_info`'s corresponding fields, returning an error on mismatch, exactly as the existing TODO comment specifies before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and any other checkpoint-hash-dependent feature) is enabled in production.

### Proof of Concept
1. In a state-sync/chunk-replay scenario, assume `DoStateCheckpoint` (or hot-state/position-state root computation) has a latent bug that computes an incorrect state/hot-state/position Merkle root for a given chunk of transactions, while producing correct write sets, events, gas, and status for those transactions.
2. `ChunkExecutorInner::verify_execution` (or `replay_on_archive::execute_and_verify`) re-executes the chunk locally and calls `txn_out.ensure_match_transaction_info(version, txn_info, ...)` at [5](#0-4) .
3. Because the comparator only checks status/gas/write-set-hash/event-root-hash ( [6](#0-5) ) and never checks the checkpoint hashes, the call returns `Ok(())` even though the locally derived state/hot-state/position root differs from the one embedded in the persisted `TransactionInfo`.
4. Replay/verification reports success ("replay OK") for a chunk whose authenticated state root has silently diverged, defeating the exact hard-fork/divergence detection this tooling exists to provide. [1](#0-0)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
