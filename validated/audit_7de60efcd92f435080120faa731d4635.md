### Title
Concurrent `BucketApi::grow` calls under shared read-lock can trigger `assert_eq!` panic in `Reallocated::add_reallocation` - ([File: bucket_map/src/bucket.rs])

### Finding Description
`Bucket::grow_index` and `Bucket::grow_data` are documented as taking only an immutable `&self` reference and are reachable via `BucketApi::grow`, which explicitly acquires a **read** lock (not a write lock) on `self.bucket: RwLock<Option<Bucket<T>>>` before calling `bucket.grow(err)`: [1](#0-0) 

Because `RwLock::read()` permits multiple simultaneous readers, two threads that each fail a `try_write` on the *same* bucket and independently call `BucketApi::grow(err)` can both hold a read guard concurrently and both execute `grow_index`/`grow_data`, which call `self.reallocated.add_reallocation()`: [2](#0-1) [3](#0-2) 

`add_reallocation` hard-asserts that `active_reallocations` was `0` before the increment: [4](#0-3) 

The intended invariant relies on `BucketApi::try_write` acquiring the **write** lock, calling `handle_delayed_grows()` first, and only *afterwards* dropping the write lock when it returns an error — with the actual `grow()` call happening later under a read lock: [5](#0-4) [6](#0-5) 

The retry loop in `InMemAccountsIndex::write_to_disk` shows the exact call sequence: `try_write` (write lock, then dropped) → `disk.grow(err)` (read lock) → loop back to `try_write` (write lock, applies delayed grow via `handle_delayed_grows`): [7](#0-6) 

Because the write lock is released between the failed `try_write` and the subsequent `grow()` call, and again released between `grow()` and the next `try_write`, there is a window during which **another thread operating on a different pubkey that hashes into the same bucket/bin** can also fail its `try_write` and call `grow()` concurrently. If that second thread's `grow()` call executes before the first thread's next `try_write`/`handle_delayed_grows()` clears the pending reallocation, `add_reallocation()` will observe `active_reallocations == 1` and panic via `assert_eq!`.

The write-through path (`try_write_through` → `write_through` → `write_to_disk`) is invoked per-pubkey during normal account writes/upserts, not centrally serialized per bucket: [8](#0-7) [9](#0-8) 

I confirmed the existence of this `grow()` read-lock/write-lock split and the assert, and traced the call sites in `in_mem_accounts_index.rs` that could invoke `grow` on the same bin from multiple threads (background flush threads, `write_through` on upsert). However, I was not able to fully verify within this session whether the actual runtime scheduling (bank replay parallelism, background flush thread assignment per bucket, or an additional un-surfaced lock/mutex serializing `grow()` calls per bin) makes two genuinely concurrent `grow()` calls on the *same* `Bucket` instance reachable purely from unprivileged account-write traffic. The background flusher (`BucketMapHolder::background`) appears to assign distinct buckets to threads via `next_bucket_to_flush()`, which may reduce (but does not obviously eliminate, given the separate synchronous `write_through` path) the chance of two threads targeting the same bucket concurrently.

### Impact Explanation
If reachable, this is a `panic!`-based denial-of-service: the assertion failure aborts the thread performing the account write/flush, which in a validator context (unwind-not-caught in a critical index/flush thread) can crash or poison the accounts index, taking down the validator process. This would match Agave's "node panic" / DoS bounty category if fully proven reachable from unprivileged write traffic.

### Likelihood Explanation
The precondition — two pubkeys hashing to the same disk-index bin, both needing a resize (index-full or data-full) in the same narrow window, with intervening `handle_delayed_grows()` not yet run — requires precise thread interleaving across the flush/write-through paths and a bucket-fill state that is not entirely attacker-controlled (bucket assignment depends on internal randomized hashing, `self.random`, not just the pubkey). This makes exploitation plausible in principle from the code structure, but the exact scheduling and per-bucket thread affinity of `BucketMapHolder`'s background flusher (and whether `write_through` can run concurrently with the background flusher on the same bin) needs further live/dynamic verification, which I could not complete in this session due to running out of iterations.

### Recommendation
Serialize grow operations per bucket, e.g., have `BucketApi::grow` take the write lock (matching `try_write`/`handle_delayed_grows`) instead of a read lock, or replace the `assert_eq!`-based invariant in `add_reallocation` with a `compare_exchange` that gracefully queues/merges concurrent reallocation requests instead of panicking.

### Proof of Concept
Because full reachability from the public write path could not be confirmed with certainty in this session, a concrete PoC would need to be validated by a background agent with build/run access:
1. Unit test directly on `Bucket`/`Reallocated`: spawn two threads holding simultaneous read guards analogous to `BucketApi::grow`'s locking, one calling `grow_index` and the other `grow_data` (or two `grow_index` calls) on the same `Bucket` instance without an intervening `handle_delayed_grows`, and assert no panic (currently expected to panic, demonstrating the bug).
2. Integration-level fuzz test via `InMemAccountsIndex`/`BucketApi`: from multiple threads, drive concurrent `upsert`+`try_write_through` calls for pubkeys engineered (via `Bucket::bucket_index_ix`/random seed instrumentation, or via `dev-context-only-utils` bucket item introspection) to land in the same bin while the bucket is near its index/data capacity limit, and assert the process does not panic under `RUST_BACKTRACE`/`catch_unwind`.

Given the incomplete confirmation of end-to-end reachability from unprivileged transaction/write traffic alone (thread-affinity of the background flusher not fully verified), this finding should be treated as a **plausible but not fully confirmed** race condition rather than a proven DoS; further dynamic testing is recommended before final triage.

    pub fn grow_index(&self, mut current_capacity: u64) {
        if self.index.contents.capacity() == current_capacity {
            // make sure to grow to at least % more than the anticipated size
            // The indexing algorithm expects to require some over-allocation.
            let anticipated_size = self.anticipated_size * 140 / 100;
            let mut m = Measure::start("grow_index");
            //debug!("GROW_INDEX: {}", current_capacity_pow2);
            let mut count = 0;
            loop {
                count += 1;
                // grow relative to the current capacity
                let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
                let (mut index, file_name) = BucketStorage::new_with_capacity(
                    Arc::clone(&self.drives),
                    1,
                    std::mem::size_of::<IndexEntry<T>>() as u64,
                    Capacity::Actual(new_capacity),
                    self.index.max_search,
                    Arc::clone(&self.stats.index),
                    Arc::clone(&self.index.count),
                );
                // index may have allocated something larger than we asked for,
                // so, in case we fail to reindex into this larger size, grow from this size next iteration.
                current_capacity = index.capacity();
                let mut valid = true;
                for ix in 0..self.index.capacity() {
                    if !self.index.is_free(ix) {
                        let elem: &IndexEntry<T> = self.index.get(ix);
                        let new_ix =
                            Self::bucket_create_key(&mut index, &elem.key, self.random, true);
                        if new_ix.is_err() {
                            valid = false;
                            break;
                        }
                        let new_ix = new_ix.unwrap();
                        let new_elem: &mut IndexEntry<T> = index.get_mut(new_ix);
                        *new_elem = *elem;
                        index.copying_entry(new_ix, &self.index, ix);
                    }
                }
                if valid {
                    self.stats.index.update_max_size(index.capacity());
                    let mut items = self.reallocated.items.lock().unwrap();
                    items.index = Some(index);
                    self.reallocated.add_reallocation();
                    self.restartable_bucket.set_file(file_name, self.random);
                    break;
                }
            }
            m.stop();
            if count > 1 {
                self.stats
                    .index
                    .failed_resizes
                    .fetch_add(count - 1, Ordering::Relaxed);
            }
            self.stats.index.resizes.fetch_add(1, Ordering::Relaxed);
            self.stats
                .index
                .resize_us
                .fetch_add(m.as_us(), Ordering::Relaxed);
        }
    }
