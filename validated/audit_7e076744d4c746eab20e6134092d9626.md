### Title
Meta-transaction sender can steal a relayer's prepaid deposit by crafting an inner action that fails on the receiver shard - (File: `runtime/runtime/src/actions.rs`)

### Summary
In NEP-366 meta transactions, a relayer prepays all gas and all attached deposits for the inner actions of a `DelegateAction`, but if the inner action fails on the receiver shard, the deposit refund is routed to the **sender** of the `DelegateAction` (the predecessor of the generated receipt), not to the relayer who actually funded the deposit. A malicious sender can therefore attach a large deposit to an inner action that is engineered to fail once it reaches the receiver, causing the relayer's prepaid tokens to be refunded to the malicious sender instead of back to the relayer. This is directly analogous to the Notional finding: a caller supplies a small/no real "cost" (here: gas/signature only) while extracting value that was actually funded by another party (the wrapper's cash balance / the relayer's balance), because the protocol's refund/solvency logic tracks the pooled/receipt-level owner rather than the party that actually contributed the funds.

### Finding Description
When a relayer submits a transaction containing a `Delegate`/`DelegateV2` action, `apply_delegate_action` builds a new `ActionReceipt` whose actions are exactly the inner actions signed by the sender, and whose `predecessor_id` is set to `sender_id` (the meta-tx sender, e.g. Alice), while the relayer is only the signer of the *outer* transaction: [1](#0-0) 

The comment in the same function explicitly documents the fund-flow: the relayer prepays all deposits, but on failure the deposit is refunded to the sender: [2](#0-1) 

`total_deposit` sums the deposits of a `DelegateAction`'s inner actions and this total is charged to the relayer (the signer of the outer transaction) at transaction-conversion time: [3](#0-2) 

If the inner action later fails when executed on the receiver's shard, `refund_unspent_gas_and_deposits` computes `deposit_refund = total_deposit` and generates a deposit-refund receipt directed at the receipt's `predecessor_id` — which is the sender_id set by `apply_delegate_action`, not the relayer: [4](#0-3) 

This exact behavior and its risk are documented in the project's own architecture notes: the relayer pays for the deposit, but on failure the predecessor (sender) receives the refund, creating "a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard": [5](#0-4) 

The structural parallel to the Notional bug: in Notional, `mintViaUnderlying` let a caller specify a `fCashAmount` (value extracted) independent of `depositAmountExternal` (value actually contributed), and the code's solvency check passed because it looked at the wrapper's pooled cash balance rather than verifying the caller's own contribution covered the extraction. Here, a meta-tx sender specifies an inner action (value/deposit "requested") independent of what they themselves contribute (nothing — the relayer pays), and the refund-routing logic checks/credits based on the receipt's `predecessor_id` (a value the sender fully controls via `apply_delegate_action`) rather than the account that actually funded the deposit (the relayer). Both bugs stem from conflating "who is credited/refunded" with "who is solvent/who paid," letting an unprivileged actor divert funds contributed by someone else back to themselves.

### Impact Explanation
A malicious sender can drain relayer funds one meta-transaction at a time: attach a large deposit to an inner action targeted at a receiver/method they control (or a nonexistent method) so it deterministically fails, and receive the deposit refund themselves while the relayer's balance is permanently reduced by that amount. This is a concrete unauthorized transfer of value from the relayer to the sender, satisfying the "unauthorized value movement" bar. Any general-purpose relayer service that doesn't pre-simulate/validate every inner action (or that races with a sender who intentionally alters conditions between check and submission) is exposed to token loss, which is High severity for relayer operators/protocols building on meta-transactions.

### Likelihood Explanation
This is reachable by a single, unprivileged meta-transaction sender colluding with (or acting as) their own relayer, or by any sender submitting to a public/general-purpose relayer — no elevated privileges, no validator/node compromise, no network-layer assumptions. The precondition is simply: the relayer must accept and forward a `SignedDelegateAction` without perfectly predicting whether the inner action will fail at execution time (e.g., a race condition where the sender changes state between the relayer's check and execution, or a receiver contract designed to conditionally reject). Given relayers are explicitly documented as needing to "trust" the sender for this exact reason, this is a realistically reachable and already-acknowledged risk, though it requires an imperfect/naive relayer implementation to actually lose funds.

### Recommendation
Route deposit refunds for a `DelegateAction`'s inner actions to the relayer (the outer transaction's signer / predecessor of the wrapping receipt) rather than to `sender_id`, or require relayers to enforce escrow/pre-validation before spending. Concretely, consider carrying the relayer's account id through `ActionReceipt`/`apply_delegate_action` so `refund_unspent_gas_and_deposits` can direct `deposit_refund` there instead of to `sender_id`, mirroring how gas refunds already correctly go to the signer (the relayer) rather than the predecessor.

### Proof of Concept
1. Relayer R receives a `SignedDelegateAction` from sender S targeting receiver B with an inner `FunctionCall` action carrying a large `deposit` and calling a method that S knows/arranges will fail on B's shard (e.g., a nonexistent method, or a method with a condition S can flip after R checks but before execution).
2. R wraps it in a transaction it signs and submits; `total_deposit` charges R for the full deposit at tx conversion: [3](#0-2) 
3. `apply_delegate_action` creates the inner receipt with `predecessor_id = S`: [6](#0-5) 
4. Execution on B's shard fails as engineered by S.
5. `refund_unspent_gas_and_deposits` issues the deposit refund to the receipt's predecessor, i.e., S, not R: [4](#0-3) 
6. Net effect: R's balance decreased by the deposit amount; S's balance increased by the same amount, despite S never having funded it — matching the documented risk in [5](#0-4) .

pub fn total_deposit(actions: &[Action]) -> Result<Balance, IntegerOverflowError> {
    let mut total_balance = Balance::ZERO;
    for action in actions {
        let action_balance;
        if let Some(delegate_action) = delegate_inner_action(action) {
            // Note, here Relayer pays the deposit but if actions fail, the deposit is
            // refunded to Sender of DelegateAction
            let actions = delegate_action.get_actions();
            action_balance = total_deposit(&actions)?;
        } else {
            action_balance = action.get_deposit_balance();
        }

        total_balance = safe_add_balance(total_balance, action_balance)?;
    }
    Ok(total_balance)
}

## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
