## Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, letting replay/chunk-sync verification accept a locally recomputed state that diverges from the trusted, committed ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by state-sync chunk execution verification and by db-tool replay-verification to confirm that a *locally recomputed* transaction output matches the already-authenticated `TransactionInfo` obtained from a backup or from a peer. The function checks status, gas used, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that commit to the accumulated state root. This is analogous to the reported bug pattern: a verification/accounting routine silently omits checking one of several components (the "reward token" analog here is the state-checkpoint root) while still reporting success, because the omission is gated on an unrelated/absent condition rather than being enforced unconditionally.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates only four properties of the recomputed `TransactionOutput` against the trusted `TransactionInfo`: execution status, gas used, `write_set_hash` (against `state_change_hash`), and `event_root_hash`. The code contains an explicit acknowledgment of the gap: [2](#0-1) 

This comment states the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

This function is invoked in two integrity-relevant call sites:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which recomputes transaction outputs during chunk-based state sync/replay and compares them against `transaction_infos` supplied externally as ground truth: [3](#0-2) 
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, used to audit historical replay correctness against archived, previously-committed `TransactionInfo`s: [4](#0-3) 

Because `state_checkpoint_hash` (the Sparse-Merkle/JMT state root commitment) is never compared, a node performing chunk-verified state sync, or an operator running `replay-on-archive`/`replay-verify`, can locally recompute a state whose accumulated Merkle root differs from the one actually committed and signed by validators, yet the verification step will report success as long as the per-transaction write set and event hashes happen to match. This decouples the "verified" outcome from the true accumulator/state-root binding that the transaction info and its accumulator proof are supposed to guarantee.

### Impact Explanation
This breaks the "accumulator root / Merkle proof accepted as valid" and "authenticated response bound to right root" invariants called out in the state-integrity gate: a divergent JMT/state-checkpoint root can pass local replay-verification undetected. In a hard-fork-only or storage-bug scenario (e.g. a bug in state merklization, hot-state summary computation, or the newer `position_state_checkpoint_hash` for trading-native features), this verification path is the primary safety net meant to catch state root divergence during backup verification and chunk-based syncing — and it is silently blind to exactly that class of error. This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category explicitly listed as in-scope.

### Likelihood Explanation
The gap is unconditional (not behind a feature flag for the state/hot-state checkpoint hashes — the comment says "ignores the checkpoint hashes (state/hot-state and position_state_checkpoint_hash)"), and the function is on the hot path of both production chunk-executor state-sync verification and the `db-tool replay_on_archive`/`replay_verify` operational tooling used to certify historical correctness. No attacker action is required to trigger it — a discrepancy can arise from any deterministic-execution/state-merklization bug that produces a correct write set but a wrong accumulated root, and the current code cannot detect it. The severity is capped by the fact that it is a detection-only bypass (it does not itself corrupt the ledger), and the surrounding TODO indicates it is a recognized, intentional, work-in-progress gap tied to unreleased `COMPUTE_TRADING_NATIVE_STATE_ROOTS` functionality, which somewhat lowers confidence that this is an unaddressed oversight versus a deliberately staged rollout limitation.

### Recommendation
Add comparisons of `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when present in the recomputed output, i.e., at checkpoint-transaction boundaries) inside `ensure_match_transaction_info`, matching the way `write_set_hash` and `event_root_hash` are already enforced, before removing/relaxing any feature gates that depend on this comparator's completeness.

### Proof of Concept
Not directly exploitable by an external attacker without a state-merklization defect to trigger a mismatch; the concrete "proof" is the code path itself:
1. Feed `verify_execution` (chunk_executor) or `execute_and_verify` (replay_on_archive) a chunk whose write set and events match the recorded `TransactionInfo` but whose recomputed `state_checkpoint_hash` (accumulated JMT root) differs, e.g., due to any bug in `merklize_snapshot`/`calculate_top_levels`.
2. `ensure_match_transaction_info` at [5](#0-4)  passes since it never inspects `state_checkpoint_hash`.
3. `verify_execution`/`execute_and_verify` reports success despite the state root divergence, as acknowledged directly in the surrounding code comment.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
