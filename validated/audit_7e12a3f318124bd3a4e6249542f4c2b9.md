Based on my investigation, I found a confirmed, reachable analog to the RLP dual-implementation inconsistency bug in nearcore's receipt size validation path.

---

### Title
Receipt Size Validation Bypass via Post-Validation `output_data_receivers` Mutation Causes Congestion Accounting Inconsistency — (`runtime/runtime/src/verifier.rs`, `runtime/runtime/src/lib.rs`, `runtime/runtime/src/congestion_control.rs`)

---

### Summary

The receipt size check in `validate_receipt` runs against the receipt's Borsh-serialized length **before** the runtime appends `output_data_receivers` to the receipt in `apply_action_receipt`. This is the exact structural analog to the RLP bug: one code path (validation) measures the size of an incomplete object, while a second code path (post-execution mutation) silently grows the object past the limit. The result is that receipts exceeding `max_receipt_size` (4,194,304 bytes) enter the congestion-control forwarding and buffering pipeline, where a third inconsistent implementation clamps the size to `max_receipt_size` for bandwidth accounting, causing the shard's outgoing byte counter to undercount actual bytes sent.

---

### Finding Description

**Step 1 — Validation checks size of the incomplete receipt.**

In `validate_receipt`, when `mode == ValidateReceiptMode::NewReceipt`, the size is measured and compared to `max_receipt_size`:

```rust
// runtime/runtime/src/verifier.rs:533-541
if mode == ValidateReceiptMode::NewReceipt {
    let receipt_size: u64 =
        borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
    if receipt_size > limit_config.max_receipt_size {
        return Err(ReceiptValidationError::ReceiptSizeExceeded { ... });
    }
}
```

At this point the receipt's `output_data_receivers` field is still empty (`vec![]`). [1](#0-0) 

**Step 2 — After validation, the runtime mutates the receipt by appending `output_data_receivers`.**

In `apply_action_receipt`, when the VM returns `ReturnData::ReceiptIndex(receipt_index)` (a `promise_return`), the parent receipt's `output_data_receivers` are appended to the child receipt **after** it has already passed the size check:

```rust
// runtime/runtime/src/lib.rs:1019-1036
if !action_receipt.output_data_receivers().is_empty() {
    if let Ok(ReturnData::ReceiptIndex(receipt_index)) = result.result {
        match result.new_receipts.get_mut(receipt_index as usize)... {
            ReceiptEnum::Action(new_action_receipt) | ... =>
                new_action_receipt.output_data_receivers
                    .extend_from_slice(&action_receipt.output_data_receivers()),
            ...
        }
    }
}
``` [2](#0-1) 

Each `DataReceiver` entry added here is a `(CryptoHash, AccountId)` pair (~100 bytes). With `max_number_input_data_dependencies = 128`, up to ~12,800 bytes can be appended, pushing a receipt that was exactly at `max_receipt_size` to ~4,207,104 bytes.

**Step 3 — The `ExistingReceipt` mode explicitly skips the size check.**

The `ValidateReceiptMode` enum documents this gap:

```rust
// runtime/runtime/src/verifier.rs:579-585
/// 2) There is a bug which allows to create receipts that are above the size limit. Runtime has
///    to handle them gracefully until the receipt size limit bug is fixed.
///    See https://github.com/near/nearcore/issues/12606 for details.
ExistingReceipt,
``` [3](#0-2) 

**Step 4 — The congestion-control forwarding path silently clamps the size, creating an accounting inconsistency.**

In `ReceiptSinkV2::try_forward`, the oversized receipt's size is clamped to `max_receipt_size` before being subtracted from the shard's outgoing bandwidth grant:

```rust
// runtime/runtime/src/congestion_control.rs:413-427
// There is a bug which allows to create receipts that are above the size limit.
// Let's pretend that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
if size > max_receipt_size {
    size = max_receipt_size;
}
// ...
forward_limit.size -= size;  // decremented by max_receipt_size, not actual size
``` [4](#0-3) 

But when the same receipt is **buffered** instead of forwarded, `buffer_receipt` stores the actual (oversized) size in `StateStoredReceiptMetadata.congestion_size` and adds it to `own_congestion_info.receipt_bytes`:

```rust
// runtime/runtime/src/congestion_control.rs:477-487
let metadata = StateStoredReceiptMetadata { congestion_gas: gas, congestion_size: size };
// ...
self.own_congestion_info.add_receipt_bytes(size)?;  // actual oversized size
``` [5](#0-4) 

This is the two-implementation inconsistency: forwarded oversized receipts are counted at `max_receipt_size`; buffered oversized receipts are counted at their actual size. The shard's outgoing bandwidth grant is decremented by less than the actual bytes transmitted.

**The codebase itself confirms this is a live, unresolved bug:** [6](#0-5) 

---

### Impact Explanation

1. **Protocol invariant violation / contract execution flow breakage**: Receipts exceeding `max_receipt_size` are created and processed without rejection. The `max_receipt_size` limit exists to bound state witness size; oversized receipts can push state witnesses past their soft limits, potentially causing chunk validation to fail on honest nodes.

2. **Congestion accounting inconsistency (bandwidth scheduler bypass)**: When an oversized receipt is forwarded directly, the shard's outgoing size counter is decremented by `max_receipt_size` instead of the actual size. The shard therefore believes it has more remaining bandwidth than it actually used, allowing it to forward additional receipts beyond its true grant. This is a non-network-level, execution-path DoS vector fixable without a hardfork.

3. **`compute_receipt_size` vs. stored `congestion_size` divergence**: `compute_receipt_size` uses `borsh::object_length(&receipt).unwrap()` (the live size), while `receipt_size` for a `StateStoredReceipt` reads from `metadata().congestion_size` (the size at store time). For oversized receipts that are buffered, the stored size is the actual oversized value; for forwarded ones, the accounting uses the clamped value. These two paths produce different numbers for the same receipt depending on whether it was forwarded or buffered. [7](#0-6) 

---

### Likelihood Explanation

**Medium.** Any unprivileged user can deploy a contract and craft a promise DAG of the form `[A -then-> B]` where promise A does a `promise_return(C)` and receipt C is sized exactly at `max_receipt_size - sizeof(output_data_receivers_to_be_appended)`. The test `test_max_receipt_size_promise_return` demonstrates this is reproducible with a standard test contract. No privileged access, validator control, or key compromise is required. [8](#0-7) 

---

### Recommendation

1. **Short term**: Move the receipt size check in `validate_receipt` to occur **after** `output_data_receivers` have been appended, or add a second size check in `apply_action_receipt` after the mutation at lines 1029–1035 of `lib.rs`. This mirrors the RLP recommendation: ensure both the pre-check and the post-mutation state agree.

2. **Short term**: Remove the silent size clamping in `try_forward` once the root cause is fixed. The clamping was added as a workaround for issue #12606 and masks the accounting inconsistency.

3. **Long term**: Unify the two size-measurement paths (`compute_receipt_size` via `borsh::object_length` and the inline `borsh::object_length` in `validate_receipt`) into a single canonical function called at a single point after the receipt is fully constructed, analogous to the RLP recommendation to settle on one implementation.

### Proof of Concept

The nearcore test suite itself contains a passing end-to-end proof of concept:

```
test-loop-tests/src/tests/max_receipt_size.rs
  fn test_max_receipt_size_promise_return()   // promise_return path
  fn test_max_receipt_size_value_return()     // value-return data receipt path
```

Both tests call `assert_oversized_receipt_occurred`, confirming that receipts exceeding `max_receipt_size` are observed in the validator's incoming receipt stream after execution — i.e., the oversized receipt was created, forwarded, and delivered without being rejected. [9](#0-8) 

The exact corrupted value is `CongestionInfo::receipt_bytes` in the chunk header: for a forwarded oversized receipt of actual size `S > max_receipt_size`, the field is decremented by `max_receipt_size` instead of `S`, leaving the shard believing it has `S - max_receipt_size` more outgoing bytes available than it actually does. [10](#0-9)

/// Get the receipt size from the receipt that was retrieved from the state.
/// If it is a [Receipt], the size will be computed.
/// If it s the [StateStoredReceipt], the size will be read from the metadata.
pub(crate) fn receipt_size(
    receipt: &ReceiptOrStateStoredReceipt,
) -> Result<u64, IntegerOverflowError> {
    match receipt {
        ReceiptOrStateStoredReceipt::Receipt(receipt) => compute_receipt_size(receipt),
        ReceiptOrStateStoredReceipt::StateStoredReceipt(receipt) => {
            Ok(receipt.metadata().congestion_size)
        }
    }
}

/// Calculate the size of a receipt before it is pushed into a state queue or
/// buffer. Please note that this method should only be used when storing
/// receipts into state. It should not be used for retrieving receipts from the
/// state.
///
/// The calculation is part of protocol and should only be modified with a
/// protocol upgrade.
pub(crate) fn compute_receipt_size(receipt: &Receipt) -> Result<u64, IntegerOverflowError> {
    let size = borsh::object_length(&receipt).unwrap();
    size.try_into().map_err(|_| IntegerOverflowError)
}
