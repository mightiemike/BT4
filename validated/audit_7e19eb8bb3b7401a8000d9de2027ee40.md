### Title
Open redirect via protocol-relative URL bypass in `isSafe` (missing host verification) - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts)

### Summary
`isSafe` in `validate-redirect-url.ts` is supposed to ensure a redirect target stays within the app's own domain, but it never checks that the resolved `URL.host` matches the app's configured domain. A protocol-relative string such as `//evil.com` (or backslash-equivalent variants like `/\evil.com`, `\\evil.com`) resolves via the WHATWG `URL` constructor to a completely different host while still passing every existing check in `isSafe`.

### Finding Description
`isSafe` performs these checks, in order: [1](#0-0) 

1. `FILE_URI_MATCH` (`/\/\/\//`) rejects only **three** consecutive slashes (`file://`-style triple slash), not two.
2. `WHITESPACE_CHARACTER` rejects whitespace.
3. `new URL(redirectUrl, domain)` is constructed.
4. `INVALID_RELATIVE_URL` (`/[/\\][/\\]/`) is tested only against `url.pathname`, never against `url.host`/`url.hostname`.
5. Only `url.protocol` (http/https) and SSL requirement are checked.

Crucially, there is **no comparison of `url.host` (or `url.hostname`) against the `domain` argument's host**. Per the WHATWG URL spec, when a base URL is supplied and the input string begins with `//`, the parser treats it as a "network-path reference": it keeps the base's scheme but takes the host from the input itself. So:

```js
new URL('//evil.com', 'https://my-app.example.com')
// => { protocol: 'https:', host: 'evil.com', pathname: '/', ... }
```

This passes `isSafe` because:
- Only two slashes are present, so `FILE_URI_MATCH` (three slashes) does not match.
- No whitespace present.
- `url.pathname` is `/`, so `INVALID_RELATIVE_URL` (which only inspects `pathname`) does not match.
- `url.protocol` is `https:`, which is in `VALID_PROTOCOLS`, and satisfies `requireSSL`.

`sanitizeRedirectUrl` then returns `new URL(redirectUrl, domain)` — a `URL` object whose host is `evil.com`, not the app's domain — as the "sanitized" result: [2](#0-1) 

This value is consumed by `renderAppBridge`, which embeds it verbatim into a `<script>window.open(...)</script>` payload rendered inside the embedded app iframe response: [3](#0-2) 

Because there is no host check, this function fails its stated invariant of keeping redirects scoped to the app's own domain — it only ever checked for double-slash sequences inside the pathname, not for a hostname substitution attack via a protocol-relative or backslash-normalized string.

### Impact Explanation
If any code path passes an externally influenced string into `sanitizeRedirectUrl`/`renderAppBridge`'s `redirectTo.url`, an attacker can force the embedded app iframe to `window.open` an attacker-controlled origin (`evil.com`) instead of validating against the configured `config.appUrl`. This matches the "open redirect leading to token theft" impact class referenced in the question — the embedded session context could be abused to phish/steal tokens if the redirect target is reachable from attacker-influenced input.

### Likelihood Explanation
The `isSafe`/`sanitizeRedirectUrl` bug itself is unconditionally reachable and reproducible with a plain unit test — no privileged access or secrets are needed to demonstrate that the validator accepts a cross-host URL it is documented to reject. However, I could not fully confirm within the available context whether any call site actually forwards raw, attacker-controlled request query-string values into `sanitizeRedirectUrl`'s `redirectUrl` argument end-to-end from an unauthenticated HTTP request (the visible call site, `renderAppBridge`, takes `redirectTo.url` from internal library/developer-supplied logic, e.g. `redirect.ts`, `redirect-to-auth-page.ts`, `redirect-to-bounce-page.ts`, `redirect-to-install-page.ts`, `authenticate.ts`, and the billing handlers). I was not able to trace those remaining files before running out of tool budget, so whether a fully attacker-controlled string reaches `isSafe` in the default configuration is unverified.

### Recommendation
In `isSafe`, after constructing `url`, explicitly verify that `url.host` (or `url.hostname`) equals the `host`/`hostname` of `new URL(domain)`, rejecting any redirect target whose resolved host differs from the app's own domain. Do not rely solely on pattern-matching the raw string or the pathname for double slashes/backslashes, since the `URL` parser's own protocol-relative resolution already sidesteps those checks.

```typescript
function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
```

```typescript
export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}
```
