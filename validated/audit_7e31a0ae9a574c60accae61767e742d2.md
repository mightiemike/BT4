### Title
Session created/bound to an unvalidated `shop` query parameter instead of the authenticated session-token identity - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts])

### Summary
This is analogous to the reported `split()` bug, where a privileged operation (minting a new NFT) used `msg.sender` instead of the entity that was actually authorized/verified. In `shopify-app-js`, the `getSessionTokenContext` helper used by the admin authentication strategy factory has two code paths: one derives `shop` from the cryptographically-verified session token payload (`payload.dest`), and the other — used for `AppDistribution.ShopifyAdmin` (remix) / when `config.isEmbeddedApp` is false in one branch — takes `shop` directly from the request's URL query string without tying it back to the verified session token identity.

### Finding Description
In `getSessionTokenContext`, for the "verified" branch the shop is derived only after validating the session token: [1](#0-0) 

But for the other branch (`AppDistribution.ShopifyAdmin` in react-router, or the non-embedded branch in remix), `shop` is read straight from the request URL: [2](#0-1) 

The returned `shop` value (not the value implied by the verified session/cookie) is then propagated to the authorization strategy (`strategy.authenticate(request, {session: existingSession, sessionToken, shop})`) and used downstream (e.g., to build `sessionId`, to decide whether the current session matches the request, and to drive redirects such as `redirectToAuth`), exactly the way `split()` used `msg.sender` rather than the true, validated NFT owner when minting/creating a new entity.

### Impact Explanation
If an attacker (a single unprivileged actor) can influence the `shop` query parameter independently of the authenticated session (JWT/cookie), functions that key session storage or redirect logic off of `shop` rather than off the verified identity risk operating against the wrong tenant — e.g. issuing an OAuth redirect to, or comparing sessions against, a shop the requester does not actually control. This maps to the "session/OAuth CSRF or cross-tenant confusion" class explicitly called out as acceptable analogs in scope.

### Likelihood Explanation
Medium: exploitation requires the attacker to control or manipulate the `shop` query parameter on a request that still carries a legitimately signed cookie/session-id for a different shop, and for downstream comparison/redirect logic to trust the unauthenticated `shop` value rather than re-deriving it from the verified token. I was not able to fully trace every downstream consumer (e.g., `auth-code-flow.ts` strategy) within the remaining iterations to conclusively confirm whether a same-request mismatch check (`session.shop !== shop`) fully neutralizes this in all code paths (the express middleware `validate-authenticated-session.ts` does appear to perform such a check at [3](#0-2) , but I could not verify the equivalent check exists uniformly in the remix/react-router `getSessionTokenContext` → `strategy.authenticate` chain for the `ShopifyAdmin` distribution branch before it terminates in my available iterations).

### Recommendation
In `getSessionTokenContext`, always derive `shop` from a cryptographically verified source (decoded session token `payload.dest`, or the value already bound to the loaded, verified session/cookie) rather than trusting the raw URL `shop` query parameter, mirroring how the header-token branch already does it. Any comparison between a loaded session and a request should always compare against the verified identity, not a value taken from unauthenticated request input, exactly as `merge()`, `increase_amount()`, etc. preserve original ownership in the referenced report's recommendation.

### Proof of Concept
Not fully reproducible from static analysis alone: constructing a concrete PoC requires confirming (in a running app) that no downstream `session.shop !== shop` guard rejects the mismatched, URL-supplied `shop` before the value is used to build a session id or trigger a redirect in the `ShopifyAdmin` distribution branch. I could not complete this verification within the available tool-call budget, so this finding should be treated as a **hint requiring confirmation** by tracing `strategy.authenticate` (`auth-code-flow.ts` and `token-exchange.ts` under `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/`) to see whether `sessionContext.shop` is ever used to build a session ID, redirect target, or OAuth begin call without being re-validated against the token/cookie-verified shop.
