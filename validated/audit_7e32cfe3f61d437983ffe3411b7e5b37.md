## Analysis

The reported Merit Circle bug is a "first depositor inflates a `pointsPerShare`/reward-per-share accumulator, causing a later, unbounded arithmetic operation to corrupt or revert" pattern. In java-tron, the closest structural analog is the **witness vote-reward accumulator (`Vi`)** used by the SR (Super Representative) voting/reward-withdrawal system.

`DelegationStore.accumulateWitnessVi()` computes a per-witness accumulator exactly like `pointsPerShare`:

```java
BigInteger deltaVi = BigInteger.valueOf(reward)
    .multiply(DECIMAL_OF_VI_REWARD)
    .divide(BigInteger.valueOf(voteCount));
setWitnessVi(cycle, address, preVi.add(deltaVi));
``` [1](#0-0) 

`DECIMAL_OF_VI_REWARD` is a large, fixed multiplier (`1e18`) analogous to Merit Circle's `POINTS_MULTIPLIER`: [2](#0-1) 

If `voteCount` (the total votes for a given witness in that cycle) is very small (the minimum non-zero vote is `1`, enforced only by `voteCount <= 0` checks), `deltaVi` can be driven to an extremely large `BigInteger` value in a single cycle: [3](#0-2) [4](#0-3) 

Later, when reward is computed for any voter of that witness (including a legitimate voter with a much larger vote count), the code does:

```java
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
```
This exact pattern appears identically in three places: `MortgageService.computeReward()`, `VoteRewardUtil.computeReward()`, and `RewardViCalService.getNewRewardAlgorithmReward()`. [5](#0-4) [6](#0-5) [7](#0-6) 

Unlike Solidity, Java's `BigInteger.longValue()` **does not throw on overflow** — it silently truncates the value to the low 64 bits. So the failure mode differs from the original report (which reverts): here, the accumulated `Vi` inflation, once `deltaVi * userVote` exceeds `Long.MAX_VALUE`, causes `computeReward`/`withdrawReward`/`queryReward` to silently return a wrong (truncated/wrapped, potentially negative-looking-then-cast) reward value rather than reverting, corrupting `adjustAllowance()`'s `accountCapsule.setAllowance()` update.

The precondition — a witness (SR candidate) with an extremely low total vote count that still nets a reward for a cycle — is reachable by any unprivileged account: registering as a witness and voting for oneself is a permissionless, public action (`WitnessCreateContract` + `VoteWitnessContract`, minimum `1` vote = `1` TRX of tron power). Standby-witness rewards in TRON are distributed to the top-127 candidates proportional to votes, so a witness parked at the bottom of that list with a trivially small vote count can still receive nonzero reward each cycle, letting an attacker/operator of a low-competition or private/consortium chain (or simply a low-ranked witness on any network) inflate `Vi` for their own address's witness before larger legitimate voters interact with it.

### Title
Witness vote-reward accumulator (`Vi`) inflation via low-vote-count witnesses can silently corrupt reward accounting through unchecked `BigInteger.longValue()` truncation - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
The SR vote-reward system computes a per-witness accumulator `Vi` as `reward * DECIMAL_OF_VI_REWARD / voteCount` in `DelegationStore.accumulateWitnessVi()`. Because the minimum enforced `voteCount` is `1`, and `DECIMAL_OF_VI_REWARD` is a large fixed multiplier (`1e18`), a witness that receives even small standby/block rewards while having a very low total vote count accumulates an extremely large `Vi` value over successive cycles. When any voter's reward is later computed as `deltaVi.multiply(userVote).divide(DECIMAL_OF_VI_REWARD).longValue()` in `MortgageService.computeReward()`, `VoteRewardUtil.computeReward()`, and `RewardViCalService.getNewRewardAlgorithmReward()`, the result can exceed `Long.MAX_VALUE`. `BigInteger.longValue()` does not throw in this case — it silently truncates, producing an incorrect reward figure that then feeds into `AccountCapsule.setAllowance()`.

### Finding Description
`Vi` acts as java-tron's "points-per-share" accumulator, tracking cumulative reward-per-unit-vote for each witness across cycles: [1](#0-0) . The scaling constant `DECIMAL_OF_VI_REWARD = 10^18` [8](#0-7)  plays the same role as Merit Circle's `POINTS_MULTIPLIER`. When the divisor (`voteCount`) is small, `deltaVi` for that cycle grows proportionally larger. Vote validation only requires `voteCount > 0` [3](#0-2) , so a witness supported by a single minimal voter is a valid, unprivileged state. Reward computation later multiplies the accumulated `deltaVi` by a (potentially much larger) legitimate voter's `userVote` and converts to `long` via `.longValue()` with no bounds check: [5](#0-4) . `BigInteger.longValue()` per the JDK spec discards all but the low-order 64 bits when the value doesn't fit, producing a wrong result rather than an exception — a silent corruption instead of the revert seen in the Solidity original.

### Impact Explanation
If reached, the consequence is silent, incorrect reward accounting for real voters/witnesses — either drastically under- or over-crediting `AccountCapsule` allowances via `adjustAllowance()` [9](#0-8) , which is worse than a mere revert because it is not detectable at the point of failure and directly affects on-chain TRX reward balances (a fund-accounting divergence).

### Likelihood Explanation
Registering a witness and self-voting with the minimum `1` vote is fully permissionless and requires no special role. However, to accumulate a materially large `Vi`, the witness must also receive nonzero standby/block rewards over enough cycles while keeping its total vote count tiny — plausible on low-competition, private, or consortium java-tron deployments, but hard to sustain on a highly contested top-127 candidate list such as TRON mainnet. This makes the likelihood conditional on network competitiveness rather than being a fully attacker-controlled, single-transaction setup as in the original Merit Circle report.

### Recommendation
- Enforce a meaningful minimum vote-count threshold for reward-eligible witnesses (or floor/normalize `voteCount` before dividing) to prevent extreme accumulator scaling from low-vote witnesses.
- Replace unchecked `BigInteger.longValue()` conversions in `MortgageService.computeReward()`, `VoteRewardUtil.computeReward()`, and `RewardViCalService.getNewRewardAlgorithmReward()` with `longValueExact()` (or an explicit range check) so an overflow condition throws/reverts rather than silently truncating the reward value.
- Consider reducing `DECIMAL_OF_VI_REWARD`'s magnitude or bounding cumulative `Vi` growth per cycle.

### Proof of Concept
1. Attacker creates a new witness (permissionless, subject to registration fee) and casts the minimum `1` vote (`1` TRX of tron power) for it via `VoteWitnessActuator`/`VoteWitnessProcessor` [10](#0-9) .
2. Over successive maintenance cycles, the witness receives nonzero standby/block reward while `voteCount` stays at `1`; `DelegationStore.accumulateWitnessVi()` compounds `deltaVi = reward * 1e18 / 1` into `Vi` each cycle [1](#0-0) .
3. A legitimate voter with a large `userVote` later votes for the same witness and calls reward withdrawal/query; `computeReward()` calculates `deltaVi.multiply(userVote).divide(1e18).longValue()` [5](#0-4) .
4. Once the intermediate `BigInteger` result exceeds `Long.MAX_VALUE`, `.longValue()` silently truncates instead of throwing, yielding an incorrect reward amount that is then applied to the voter's `allowance` via `adjustAllowance()` [9](#0-8) .

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
