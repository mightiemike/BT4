### Title
Unsafe double-to-long numeric casting in legacy `ExchangeProcessor` leads to unvalidated/unbounded exchange trade output - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The legacy (default) TRC10 bancor-exchange math implementation performs floating-point computations and casts the result directly to `long` with no bounds, NaN/Infinity, or division-by-zero checks, mirroring the reported bug class of unvalidated numeric casting on user-controlled trade parameters (`oid`/`sz`/`px` analog: `sellTokenQuant`/token balances).

### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute a bonding-curve trade using raw `double` arithmetic and then narrow the result with an unchecked cast: [3](#0-2) 

- `quant / newBalance` is a `double` division; if `newBalance` (i.e., `balance + quant`) is `0`, this silently yields `Infinity`/`NaN` instead of throwing.
- `Maths.pow(...)` on an `Infinity` base propagates `Infinity`/`NaN`.
- `(long) issuedSupply` / `(long) exchangeBalance` on `Infinity` silently yields `Long.MAX_VALUE` (or `Long.MIN_VALUE` for `-Infinity`) per Java's narrowing-conversion semantics — no exception, no validation, no bounds check.
- The result then flows unchecked into `supply += out`, and back in `ExchangeCapsule.transaction`, into `newFirstTokenBalance`/`newSecondTokenBalance` via plain `+`/`-` (non-hardened branch), and ultimately into `AccountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` in `ExchangeTransactionActuator.execute` [4](#0-3) .

This is the exact analog of the reported bug: user-supplied numeric parameters (`tokenQuant`/pool balances reachable via `ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) drive a numeric computation whose result is cast to a narrower/bounded type without validating the intermediate value, allowing malformed/extreme inputs to produce out-of-range or nonsensical results that are trusted as valid trade amounts. The project's own `SafeExchangeProcessor` (BigDecimal + `longValueExact()` + `addExact`) demonstrates the team is aware this exact computation is unsafe without hardening — but hardening is opt-in and off by default [5](#0-4) .

### Impact Explanation
Any account holding an existing exchange pair position can broadcast an `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transaction with a boundary `tokenQuant` that drives `newBalance` toward `0` or drives the pow computation toward `Infinity`. Because the unsafe cast never throws, the actuator will accept a fabricated `anotherTokenQuant` (potentially `Long.MAX_VALUE`) and credit the attacker's account via `addAssetAmountV2`/`setBalance` while only debiting the small `tokenQuant` actually supplied — this is direct token/TRX accounting corruption (invalid trade execution), reachable purely from an anonymous broadcast transaction, matching the report's "invalid trades or corrupted state propagation" impact.

### Likelihood Explanation
Medium. It requires the attacker to control or create an exchange pair (`ExchangeCreateContract` is available to any account) and craft quantities that push the balance ratio to the double-precision boundary (e.g., `tokenQuant` that makes `balance + quant == 0` is impossible for positive longs, but extreme ratios near the pool's edges can still push `Maths.pow` results to values that lose precision or overflow when cast, and repeated small drains at the boundary can still bias reserves over time). The `ArithmeticException`-based hardened path is not the default, so this exposure exists on any node/network that hasn't enabled `ALLOW_HARDEN_EXCHANGE_CALCULATION` via governance proposal.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal + `addExact`/`longValueExact`) the default and unconditional processor rather than gating it behind `allowHardenExchangeCalculation`, or fail closed (throw) whenever the legacy `ExchangeProcessor` path detects `Infinity`/`NaN` or a cast that loses precision.
- In `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, validate `newBalance != 0`, check `Double.isFinite(issuedSupply/exchangeBalance)` before casting, and use `Math.round`/exact conversions that throw on overflow instead of a raw `(long)` cast.
- Add explicit upper/lower bounds on `tokenQuant` relative to current pool reserves in `doValidate()` for all three Exchange actuators.

### Proof of Concept
1. Attacker creates an exchange pair with a very small reserve on one side (e.g., `firstTokenBalance = 1`, `secondTokenBalance = 1`) via `ExchangeCreateContract`.
2. Attacker broadcasts `ExchangeTransactionContract` selling a `tokenQuant` chosen so that `quant / newBalance` in `exchangeToSupply` is extremely large, driving `Maths.pow(1 + ratio, 0.0005)` and then `-supply * (1 - powResult)` toward `Double.POSITIVE_INFINITY`.
3. `(long) issuedSupply` silently becomes `Long.MAX_VALUE` (no exception) instead of the actuator rejecting the transaction.
4. This inflated `relay` is fed into `exchangeFromSupply(buyTokenBalance, relay)`, and the (also uncapped) `(long) exchangeBalance` returns an attacker-favorable `anotherTokenQuant` that is credited to the attacker's account via `accountCapsule.addAssetAmountV2`, while the pool's `setBalance` records inconsistent reserves — corrupting the exchange's accounting state.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
