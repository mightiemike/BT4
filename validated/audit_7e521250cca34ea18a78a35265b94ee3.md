Given the front-running mechanism described in the report (two independent users racing each other) is explicitly out of scope per the rules, I mapped the underlying bug class ("group lock/unlock logic bypassed via a check that gets invalidated") to the closest single-transaction analog permitted: **a fold/batch construct that absorbs a sub-call's failure**, found in `liquidate-multi`.

### Title
`liquidate-multi` swallows per-position `liquidate` failures via `map`, permanently stranding un-socialized bad debt - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` batches calls to the internal helper `call-liquidate`, which invokes the public `liquidate` function directly (a same-contract call, not `contract-call?`), and wraps the whole batch in `(ok (map call-liquidate positions))` [1](#0-0) . Because `map` never propagates an individual element's `(err ...)` upward, the top-level transaction always returns `(ok ...)`, so its overall success is decoupled from whether any given `liquidate(...)` call in the batch actually completed its liquidation and bad-debt bookkeeping successfully.

### Finding Description
Inside `liquidate`, execution order is: pre-checks (pause/auth/amount/slippage) → `vault-system-repay` (debt repayment) → `market-vault debt-remove-scaled` → `market-vault collateral-remove` → conditional bad-debt socialization via `(fold socialize-debt-asset fresh-debt-list ...)`, guarded by `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [2](#0-1) . All of the debt-repay and collateral-seize `contract-call?`s occur, and succeed (and are individually committed), before this final `asserts!`. If `socialize-debt-asset` fails for one of the borrower's other debt assets (e.g. `vault-socialize-debt`, the index-cache refresh, or `debt-remove-scaled` returns an error) [3](#0-2) , the `fold`'s accumulator absorbs the failure (`{success:false}`) and the outer `asserts!` then makes `liquidate` itself return `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.

When `liquidate` is called directly (single-call path), this `err` is the top-level transaction's return value, so the whole transaction (including the earlier successful debt-repay/collateral-seize `contract-call?`s) is rolled back — safe.

When the same `liquidate` is invoked through `call-liquidate` inside `liquidate-multi`'s `map`, this `err` is captured as one element of the response list, not propagated. `liquidate-multi` still returns `(ok (list ... (err ERR-BAD-DEBT-SOCIALIZATION-FAILED) ...))`. Since this is the outer, user-invoked transaction and it returns `ok`, every previously-successful nested `contract-call?` inside that particular failed `liquidate` invocation — the debt repayment, the collateral seizure/transfer to the liquidator, and the removal of the seized collateral from the borrower's obligation — remains committed, while the bad-debt socialization for the borrower's *other* debt assets never happens.

### Impact Explanation
The result is a borrower left with a "phantom" obligation: their collateral for the liquidated asset has been fully seized (correctly reducing `no-collateral-left` conditions), but their remaining debt on other assets is never written down/socialized in `market-vault`, even though there is no longer collateral to ever repay it. This debt remains counted in the vault's live obligation/utilization accounting indefinitely, distorting interest-rate and utilization calculations for all depositors of that asset and permanently freezing/misrepresenting that portion of vault liquidity as "outstanding" when it is actually uncollectible bad debt that will never be socialized through the normal path again (since the collateral triggering `no-collateral-left` was already removed). This is a temporary/permanent freezing-of-funds and insolvency-accounting issue at the vault level, which is an in-scope High/Critical impact.

### Likelihood Explanation
`liquidate-multi` is explicitly designed for permissionless batch liquidation and is reachable by any caller with `(list 64 {...})` positions. Triggering `socialize-debt-asset`'s failure path requires a borrower with multiple debt assets where the "no collateral left" condition is met for the liquidated collateral asset, and one of the secondary debt-socialization steps (`vault-socialize-debt`, `vault-accrue`, or `debt-remove-scaled`) errors — plausible under specific vault states (e.g., paused vault, debt cap mismatch) rather than trivially always exploitable, but requires no privileged access, only crafting a batch call.

### Recommendation
`liquidate-multi` should not use `map` to silently absorb per-position errors when those positions may have already mutated cross-contract state that depends on later assertions succeeding. Either: (1) make `liquidate`'s bad-debt socialization failure non-swallow-able by having `liquidate-multi` propagate/short-circuit on such an error (e.g. use `fold` with `try!`/abort semantics for the whole batch, or filter/validate that bad-debt-triggering positions cannot appear in `liquidate-multi`), or (2) restructure `liquidate` so that debt-repay/collateral-seize side effects are only committed after the socialization step has been confirmed to succeed, rather than before it.

### Proof of Concept
1. Set up a borrower with two debt assets (A and B) and collateral only sufficient to cover asset A's liquidation, such that after seizing all collateral for asset A, `no-collateral-left` is `true` and debt asset B must be socialized.
2. Construct conditions so that `socialize-debt-asset` fails for asset B during the fold inside `liquidate` (e.g., vault B is paused for `system-borrow`/write-down operations, or another state causes `vault-socialize-debt`/`debt-remove-scaled` to return an error) [3](#0-2) .
3. Call `liquidate` directly with these parameters: transaction reverts entirely (expected/safe), no state changes persist.
4. Instead, call `liquidate-multi` with a single position matching the above parameters [4](#0-3) .
5. Observe: `liquidate-multi` returns `(ok (list (err ERR-BAD-DEBT-SOCIALIZATION-FAILED)))` — the overall call succeeds, yet inspect vault/market-vault state afterward: debt asset A has been repaid and its collateral seized/transferred to the liquidator, but debt asset B's obligation for the borrower remains outstanding in `market-vault` despite the borrower now having zero collateral, and it was never socialized to the vault's bad-debt accounting.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))
