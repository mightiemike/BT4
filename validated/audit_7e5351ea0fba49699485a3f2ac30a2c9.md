## Title
Voting power redistribution rounds down every witness vote, permanently losing part of an account's TRON Power from the vote tally on unfreeze - (`actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`)

### Summary
The `votingPower` rounding-down bug reported for PartyDAO (individual shares floor-rounded so they never sum to the total, making a 100%/unanimous threshold unreachable) has a direct analog in java-tron's proportional vote-redistribution logic that runs whenever an account's `TronPower` drops below the total number of votes it has already cast (e.g., after `UnfreezeBalanceV2`). Each witness's re-scaled vote count is computed independently with floor-rounding double arithmetic, so the sum of the redistributed votes is systematically less than the account's actual remaining `TronPower`, permanently discarding a fraction of the account's real voting power from the on-chain vote tally.

### Finding Description
`updateVote()` in `UnfreezeBalanceV2Actuator` recomputes each witness vote count proportionally when an account's owned TronPower can no longer cover its previously cast total votes: [1](#0-0) 

For every vote entry it computes:
```
newVoteCount = (long) ((double) vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION)
```
This is applied independently per witness with a final integer truncation, exactly the pattern flagged in the report ("rounds down the voting power of all users except..."). Because each of the N witness allocations is truncated separately, `Σ newVoteCount_i` is generically strictly less than `ownedTronPower / TRX_PRECISION`; the shortfall grows with the number of witnesses voted for and is never redistributed to anyone (no "last one gets the remainder" logic exists, unlike the report's suggested fix).

The identical logic is duplicated in the TVM-native path used for `unfreezeBalanceV2` invoked from smart contracts: [2](#0-1) 

Both call sites share the same root cause as the reported bug: per-recipient floor rounding of a proportional split with no compensating remainder mechanism, so the aggregate of the parts is less than the whole.

### Impact Explanation
Every time an account unfreezes enough stake that its `TronPower` falls below its currently cast total vote count, some of the account's real voting power is silently dropped from the recorded votes held by `VotesStore`/`AccountCapsule` and thus from what ultimately gets aggregated into each `WitnessCapsule`'s vote count during maintenance (`MaintenanceManager`). This is a genuine on-chain accounting divergence: the account's `getAllTronPower()`/`getTronPower()` value and the sum of its own `getVotesList()` after redistribution no longer correspond to a lossless proportional split, and the discrepancy is unrecoverable by the user (they cannot "regain" the rounded-off fraction without re-voting for the full remaining power manually). At scale (many holders repeatedly freezing/unfreezing small amounts across many witnesses), this causes a fleet of small, un-refundable losses of effective voting power in the DPoS witness-election and reward (`MortgageService.computeReward`) accounting, which is the "state divergence / underpriced accounting" class of impact called out for this bug family. It mirrors PartyDAO's acknowledged Medium-risk classification: not fund-draining, but a real, reachable accounting rounding defect in unprivileged core consensus/staking flows.

### Likelihood Explanation
This code path triggers automatically, without any privileged role, whenever an unprivileged account calls `UnfreezeBalanceV2Actuator`/`unfreezeBalanceV2` (or the TVM native equivalent) while it has active votes exceeding its post-unfreeze `TronPower` — a very common sequence (freeze → vote for several witnesses → partially unfreeze). No special conditions or attacker collusion are required; it happens organically for ordinary voters with several witness votes.

### Recommendation
Redistribute the rounding remainder instead of discarding it — e.g., accumulate a running sum of already-allocated vote count and assign the final witness (or the largest allocation) `ownedTronPower/TRX_PRECISION - runningSum`, guaranteeing `Σ newVoteCount_i == ownedTronPower/TRX_PRECISION` exactly, in both `UnfreezeBalanceV2Actuator.updateVote()` and `UnfreezeBalanceV2Processor.updateVote()`.

### Proof of Concept
1. Account freezes TRX giving `TronPower = 100` (in TRX units) and casts votes: 10 votes each to 10 different witnesses (`totalVote = 100`).
2. Account calls `UnfreezeBalanceV2` reducing `ownedTronPower` to `95`.
3. `updateVote()` computes, for each witness: `newVoteCount = floor(10/100*95) = floor(9.5) = 9`.
4. Sum across all 10 witnesses = `90`, even though the account's real remaining `TronPower` is `95`. 5 TRX-worth of voting power (`≈5.3%` of the account's remaining power) is silently lost from the vote tally with no way for the user to reclaim it short of re-issuing a full new `VoteWitnessContract` for the exact remaining power.
