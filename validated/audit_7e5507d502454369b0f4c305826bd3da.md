## Title
Multiple `.then()` callbacks on the same base promise to the same receiver overwrite the `PostponedReceiptId` link, permanently orphaning one callback receipt - ([File: runtime/runtime/src/lib.rs])

## Summary
`process_action_receipt` records, for every missing input data dependency of a postponed `ActionReceipt`, a single mapping from `(receiver_id, data_id)` to one `receipt_id` via `TrieKey::PostponedReceiptId`. This mirrors the Perennial `KeeperOracle` bug pattern: a key that can legitimately be shared by multiple concurrent "waiters" is backed by a single-value slot instead of a set/list, so a later write silently overwrites (and thereby loses) an earlier registration.

## Finding Description
When a receipt has unmet `input_data_ids`, the runtime stores, for each missing `data_id`, a link from `(receiver_id, data_id)` to the postponed receipt's id: [1](#0-0) 

This trie key is a plain single-value slot, not a set: [2](#0-1) 

A contract can create two different callback receipts (via the promise `.then()` host function) that both depend on the *same* `data_id` (the result of one base promise) and target the *same* receiver account — e.g. calling `.then()` twice on the identical promise index with the same receiver. This is a completely normal, unprivileged usage of the promise API, reachable from any `FunctionCall` action in a signed transaction. When both resulting callback receipts arrive at the shared receiver and are postponed (because the shared data hasn't arrived yet), the second call to `process_action_receipt` for the second callback overwrites the `TrieKey::PostponedReceiptId{receiver_id, data_id}` entry that the first callback just wrote, exactly as `KeeperOracle.request` overwrote/skipped adding market+account entries for all but the first caller in a given oracle version.

When the awaited `DataReceipt` for that `data_id` finally arrives, the runtime looks up `PostponedReceiptId` to find which postponed receipt to wake and decrement, per the documented flow: [3](#0-2) [4](#0-3) 

Only the receipt_id recorded last (the second callback) is resolvable through this key; the first callback's `PendingDataCount` entry (keyed separately by `receipt_id`, so it is not overwritten) is decremented for the wrong/only-surviving link, or never decremented at all for the first callback, and its `PostponedReceipt` entry is never retrieved or removed, per `apply_action_receipt` cleanup logic: [5](#0-4) 

The orphaned postponed receipt (and its `PendingDataCount`/`PostponedReceipt` trie entries) remains stuck in state permanently, since the data it needs will never be delivered again for that `data_id` (the sending shard only emits one `Data` receipt per `output_data_receivers` entry, and once delivered/consumed the link is gone).

## Impact Explanation
This causes permanent loss (non-execution) of a receipt that a contract legitimately created and is entitled to have executed — a "receipt loss / permanently frozen" outcome matching the accepted impact categories. If the orphaned callback was meant to release escrowed funds, finalize a transfer, or otherwise mutate balances, those funds/state effectively become permanently stuck, since the triggering data will never re-arrive. It is also state-affecting: the trie retains dangling `PendingDataCount`/`PostponedReceipt` entries indefinitely (storage bloat / inconsistent internal accounting), and different nodes could observe divergent behavior if timing of the two `.then()` callback deliveries were to differ across queue orders (though same-shard delivery is deterministic per chunk, so state-root divergence is unlikely; the core damage is deterministic receipt loss on canonical execution, not merely a liveness bug — every honest node would replay it identically and permanently drop the same receipt).

## Likelihood Explanation
Any signed transaction that calls a contract using the standard promise API (`.then()`/`promise_then`) can trigger this by attaching two callbacks to the same base promise both directed at the same account (a pattern that is not disallowed anywhere in the runtime or SDK, and is a plausible outcome of generic composability helpers, e.g. calling the same "then" builder twice, or two different logical callbacks both needing the base promise's result delivered to the same contract). No validator, node, or protocol privilege is required — a normal contract deployer/caller can hit this path.

## Recommendation
Change the `PostponedReceiptId` (and correspondingly the notification path in the `Data`-receipt arrival handler) from a single-value mapping of `(receiver_id, data_id) -> receipt_id` to a set/list of receipt ids, analogous to fixing `KeeperOracle.request` by always registering the requester before any early-return/overwrite. Concretely:
- Store all pending `receipt_id`s per `(receiver_id, data_id)` (e.g. as an `EnumerableSet`-like structure or an appended list) instead of a single scalar in `set(state_update, TrieKey::PostponedReceiptId {...}, receipt.receipt_id())`.
- When the corresponding `Data` receipt arrives, iterate over *all* registered receipt ids for that `(receiver_id, data_id)` key, decrementing each one's own `PendingDataCount` and executing/removing each independently, rather than assuming a single receipt_id.
- Add a regression test creating two `.then()` callbacks on the same base promise targeting the same receiver account and asserting both eventually execute exactly once.

## Proof of Concept
1. Deploy a contract with a method that:
   - Creates a base promise `P` (e.g., a cross-contract call) via `promise_create`.
   - Calls `promise_then(P, receiver=self, method="callback_a", ...)`.
   - Calls `promise_then(P, receiver=self, method="callback_b", ...)` on the **same** promise index `P`, targeting the same receiver.
2. Submit a signed transaction invoking this method.
3. Observe: both `callback_a` and `callback_b` action receipts are created with `input_data_ids = [data_id_of_P]` and are postponed at the same `receiver_id` (self) while `P` executes.
4. When `process_action_receipt` runs for `callback_a`, it writes `TrieKey::PostponedReceiptId{receiver_id, data_id}` = `receipt_id(callback_a)`; when it later runs for `callback_b`, it overwrites the same key with `receipt_id(callback_b)`.
5. When `P`'s result `Data` receipt (with `data_id`) arrives at `receiver_id`, only the entry pointing to `callback_b` is found and woken; `callback_a` never executes, and its `PendingDataCount`/`PostponedReceipt` entries remain permanently in state.
(This scenario needs to be validated end-to-end in a running node/integration test, since I could not directly execute code; the trie-key definition and the single-value `set()` call in `process_action_receipt` are confirmed from the source, and this analysis follows the documented data-receipt resolution flow.)

## Processing DataReceipt

#### Received DataReceipt

First of all, runtime saves the incoming `DataReceipt` to the storage as:

- **`key`** = `account_id`,`data_id`
- **`value`** = `[u8]`

_Where `account_id` is [`Receipt.receiver_id`](#receiver_id), `data_id` is [`DataReceipt.data_id`](#data_id) and value is a [`DataReceipt.data`](#data) (which is typically a serialized result of the call to a particular contract)._

Next, runtime checks if there are any [`Postponed ActionReceipt`](#postponed-actionreceipt) waiting for this `DataReceipt` by querying [`Pending DataReceipt` to the Postponed Receipt](#pending-datareceipt-for-postponed-actionreceipt). If there is no postponed `receipt_id` yet, we do nothing else. If there is a postponed `receipt_id`, we do the following:

- decrement [`Pending Data Count`](#pending-datareceipt-count) for the postponed `receipt_id`
- remove found [`Pending DataReceipt` to the `Postponed ActionReceipt`](#pending-datareceipt-for-postponed-actionreceipt)

If [`Pending DataReceipt Count`](#pending-datareceipt-count) is now 0 that means all the [`Receipt.input_data_ids`](#input_data_ids) are in storage and runtime can safely apply the [Postponed Receipt](#postponed-actionreceipt) and remove it from the store.

### 3. Data dependencies: postponed receipts and promise results

An action receipt carries `input_data_ids` (`receipt.rs:605`) that must all be
satisfied before it runs. In `process_action_receipt` (`lib.rs:1529`) the runtime
counts how many of those ids are *not* yet in state (`has_received_data`,
`lib.rs:1546`); for each missing one it records a `PostponedReceiptId` link
(`lib.rs:1550`). If `pending_data_count == 0` it executes immediately
(`lib.rs:1561`); otherwise it stores a `PendingDataCount` and the receipt itself as a
**postponed receipt** (`lib.rs:1581`, `set_postponed_receipt`).

When a `Data` receipt arrives (`process_receipt`, `lib.rs:1322`) the runtime writes
`ReceivedData` (`lib.rs:1325`), then, if a `PostponedReceiptId` link exists, decrements
`PendingDataCount`; when it reaches 1→0 it removes the postponed receipt and executes
it (`lib.rs:1357-1391`). On execution, an action receipt's outputs become `Data`
receipts routed to each `output_data_receivers` entry (`lib.rs:1059`), so a
cross-contract call is: caller creates a callback action receipt with an
`input_data_id`, records itself as an `output_data_receiver` on the callee's receipt
(`receipt_manager.rs:111`, `create_action_receipt`), and the callee's return value is
turned into the `Data` receipt that resolves the dependency.
