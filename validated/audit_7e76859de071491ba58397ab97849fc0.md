### Title
Stale `PromiseYieldReceipt` Persists After `DeleteAccount`, Enabling Callback Replay on Recreated Account — (`File: core/store/src/utils/mod.rs`)

---

### Summary

`remove_account` does not erase `PromiseYieldReceipt`, `PromiseYieldStatus`, or yield-ID mapping trie keys when an account is deleted. Because NEAR account IDs are reusable (a sub-account can be deleted and recreated by its parent), a stale PromiseYield receipt left in the trie is indistinguishable from a live one. After the account is recreated at the same ID, the new account can call `promise_yield_resume` with the old `data_id`, causing the runtime to execute the pre-deletion callback against the new account's balance and state.

---

### Finding Description

**Root cause — `remove_account` leaves receipt-related trie keys behind**

`remove_account` in `core/store/src/utils/mod.rs` removes only four categories of per-account trie keys:

| Removed | Not removed |
|---|---|
| `TrieKey::Account` | `TrieKey::PromiseYieldReceipt` |
| `TrieKey::ContractCode` | `TrieKey::PromiseYieldStatus` |
| `TrieKey::AccessKey` / gas-key nonces | `TrieKey::YieldIdToDataId` / `DataIdToYieldId` |
| `TrieKey::ContractData` | `TrieKey::PostponedReceipt` / `PendingDataCount` / `PostponedReceiptId` / `ReceivedData` | [1](#0-0) 

All of the "not removed" columns are listed in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, confirming they are per-account trie entries that survive deletion. [2](#0-1) 

**How `promise_yield_resume` is scoped to the calling account**

`submit_promise_resume_data` in `runtime/runtime/src/ext.rs` looks up the PromiseYield receipt using `self.account_id` (the account currently executing) as the trie key prefix. This means `promise_yield_resume` can only resume a yield that was created by the same account — but it does not verify that the account was never deleted and recreated. [3](#0-2) 

**How the PromiseResume receipt is processed**

When a `PromiseResume` receipt arrives, `process_receipt` looks up the PromiseYield receipt by `(account_id, data_id)` and immediately executes it via `apply_action_receipt`. There is no check that the account currently exists or that it is the same account instance that created the yield. [4](#0-3) 

**`action_delete_account` delegates to `remove_account` without additional cleanup** [5](#0-4) 

---

### Impact Explanation

An attacker who controls a parent account (e.g., `attacker.near`) can:

1. Create `sub.attacker.near` and deploy a contract with a `drain_funds` callback that transfers the account's full balance to `attacker.near`.
2. Call `promise_yield_create("drain_funds", …)` from within that contract. The runtime stores a `PromiseYieldReceipt` under `(sub.attacker.near, data_id)` in the trie.
3. Call `DeleteAccount` on `sub.attacker.near`. The account record, code, and contract data are erased, but the `PromiseYieldReceipt` and `PromiseYieldStatus` remain.
4. Recreate `sub.attacker.near` from `attacker.near` and deploy the same contract.
5. Lure a victim into sending funds to `sub.attacker.near` (it appears to be a fresh account).
6. Call `promise_yield_resume(data_id, …)` from `sub.attacker.near`. `submit_promise_resume_data` finds `has_yield_receipt_in_state = true` (the stale entry), creates a `PromiseResume` receipt, and sets `PromiseYieldStatus::ResumeInitiated`.
7. The `PromiseResume` receipt is processed; the stale `PromiseYieldReceipt` is retrieved and executed via `apply_action_receipt`. The `drain_funds` callback runs against the new account's state, transferring the victim's deposited funds to `attacker.near`.

**Corrupted value:** the victim's balance on `sub.attacker.near` is drained to `attacker.near` without the victim's consent, via a callback that was authorized by a prior, now-deleted account instance.

Additionally, the yield timeout queue entry (stored in global shard state, not per-account) is also not cleaned up on deletion. When the timeout fires it emits a `PromiseResume` with `data: None`, executing the callback with a failure result on the recreated account — a secondary, uncontrolled execution path. [6](#0-5) 

---

### Likelihood Explanation

- Any NEAR account holder who controls a parent account can perform this attack against their own sub-accounts.
- Deterministic accounts (`DeterministicStateInitAction`) are equally affected: the account ID is derived from the initial state, so the same `state_init` recreates the same ID after deletion.
- The attack requires no privileged role, no validator access, and no network-level capability — only ordinary transaction submission.
- The victim has no on-chain signal that the account they are sending funds to has a stale PromiseYield receipt pending against it. [7](#0-6) 

---

### Recommendation

1. **In `remove_account`**, iterate and delete all per-account receipt-related trie keys before returning:
   - `TrieKey::PromiseYieldReceipt { receiver_id, data_id }` (all entries for the account)
   - `TrieKey::PromiseYieldStatus { receiver_id, data_id }`
   - `TrieKey::YieldIdToDataId` / `DataIdToYieldId`
   - `TrieKey::PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`
   - The corresponding `PromiseYieldTimeout` entries in the global timeout queue

2. **Alternatively**, reject `CreateAccount` / `DeterministicStateInitAction` if any `PromiseYieldReceipt` or `PostponedReceipt` trie keys exist under the target account ID, preventing reuse of an ID that has pending receipt state.

3. **Also**, remove the corresponding `PromiseYieldTimeout` queue entries when an account is deleted, to prevent the timeout path from executing a callback on a recreated account.

---

### Proof of Concept

```
Block N:
  sub.attacker.near executes:
    1. promise_yield_create("drain_funds", args, gas)
       → TrieKey::PromiseYieldReceipt{sub.attacker.near, DATA_ID} written to trie
       → TrieKey::PromiseYieldTimeout enqueued in global queue
    2. promise_batch_action_delete_account(self, attacker.near)
       → remove_account() called: Account/Code/Keys/Data removed
       → PromiseYieldReceipt{sub.attacker.near, DATA_ID} NOT removed  ← bug

Block N+1:
  attacker.near sends [CreateAccount, DeployContract(drain_funds+resume_yield)] to sub.attacker.near
  → sub.attacker.near recreated with same malicious code

Block N+2:
  victim sends 100 NEAR to sub.attacker.near

Block N+3:
  sub.attacker.near calls resume_yield(DATA_ID):
    submit_promise_resume_data(DATA_ID, payload):
      has_yield_receipt_in_state = true  ← stale entry found
      → PromiseResume receipt created for sub.attacker.near

Block N+4:
  PromiseResume processed:
    get_promise_yield_receipt(sub.attacker.near, DATA_ID) → stale receipt found
    apply_action_receipt(yield_receipt):
      drain_funds() executes on sub.attacker.near
      → 100 NEAR transferred to attacker.near  ← victim funds stolen
```

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })

                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }
