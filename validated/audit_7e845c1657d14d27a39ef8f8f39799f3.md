### Title
Deleting an account leaves stale postponed-receipt / promise-yield state reachable and executable after account recreation - ([File: core/store/src/utils/mod.rs])

### Summary
`DeleteAccountAction` is analogous to `pruneQuorums()` deleting `self.quorumSignatureSenders[h]` in the reported Solidity bug: it deletes the "outer" object (the `Account` record) but leaves several "inner mapping" trie entries keyed by that same `account_id` untouched. Because NEAR account ids are reusable (an account can be deleted and a new, unrelated account created under the same name), the orphaned entries can later be picked up and executed against the new account, which never authorized them.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`) to clean up the account before setting `*account = None`. [1](#0-0) 

`remove_account` only removes `TrieKey::Account`, `TrieKey::ContractCode`, all `AccessKey`/gas-key-nonce rows, and `ContractData` rows: [2](#0-1) 

It never touches the following per-`account_id` trie columns defined in `core/primitives/src/trie_key.rs`, all of which are keyed by `receiver_id`/`account_id` exactly like `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`: [3](#0-2) 

These rows exist precisely when the account has receipts awaiting incoming data (multi-cross-contract-call joins) or outstanding `yield`/`resume` promises — see the account-receipt-storage design doc: [4](#0-3) 

Crucially, `action_delete_account` performs only three guard checks before wiping the account: account storage-usage cap (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`), staking lock, and gas-key balance-to-burn cap: [5](#0-4) 

There is no check for outstanding postponed receipts, pending received data, or unresolved promise-yields, and the storage-usage counted at line 342-363 is derived from `account.storage_usage()`/contract code size, not from these detached trie columns — I found no code path (`storage_usage_change`) that adds `ReceivedData`/`PostponedReceipt`/`PromiseYield*` bytes to `account.storage_usage()`, so an account can be deleted freely even while such pending cross-contract state exists.

When the delayed matching `DataReceipt` (or `PromiseResume`) eventually arrives on this shard, `Runtime::process_receipt`/`resolve_promise_yield_timeouts` look up these entries purely by `account_id`/`receiver_id`, with no existence check on the `Account` record itself, e.g. the pending-data-count completion path that fetches and executes the postponed receipt: [6](#0-5) 
and the promise-resume path that looks up `PromiseYieldReceipt`/`PromiseYieldStatus` by `account_id`: [7](#0-6) 

If, between the `DeleteAccount` action and the arrival of the outstanding data/resume receipt, the same `account_id` is recreated (implicit-account creation via transfer, or explicit `CreateAccount` by an unrelated party — account ids are not permanently reserved after deletion), the stale `PostponedReceipt`/`PromiseYieldReceipt` — containing actions (e.g. `FunctionCall`, `Transfer`) authored by the *old* account/contract — will be executed as if issued by/for the *new* account, exactly mirroring the reported bug's "reuse of signatures" concern (here: reuse/replay of stale receipt/action state against a different account owner).

### Impact Explanation
This allows execution of receipts/actions that the current (recreated) account owner never authorized, executing arbitrary leftover `FunctionCall`/`Transfer` actions against the new account's state — i.e., unauthorized state transitions and potential unauthorized value movement, sourced entirely from a single submitted `DeleteAccount` transaction plus normal cross-shard receipt delivery. It can also produce state-root divergence if the timing/ordering of the stale receipt's arrival differs across nodes reprocessing state, or permanently orphaned trie state (never GC'd) increasing state bloat with no owner able to clean it up. Severity is High given it is triggerable purely through standard transaction/receipt flows without any privileged or network-level access.

### Likelihood Explanation
Reachable by any account holder issuing a normal `DeleteAccount` action while it has in-flight cross-contract calls awaiting `DataReceipt` inputs (a common pattern — e.g. `Promise::and` / multi-callback patterns) or unresolved `yield`/`resume` promises, then having (or arranging for, e.g. via an implicit-account transfer) the same account id recreated before the outstanding receipt is delivered. No validator, network, or privileged access is required — likelihood is Medium-High since it requires specific timing (deleting while data is still pending, and account-id reuse), which a deliberate attacker can engineer deterministically by controlling both the deletion and the recreation transactions.

### Recommendation
Before allowing `DeleteAccountAction` to fully remove the account, `action_delete_account`/`remove_account` should either:
1. Reject deletion if any `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` entries exist for the account (analogous to the existing staking-lock guard), or
2. Explicitly iterate and delete all such per-account_id trie prefixes as part of `remove_account`, mirroring how `ContractData` and access keys are already prefix-iterated and removed.

### Proof of Concept
Conceptual sequence (cannot be executed in this read-only environment, but the code paths are fully cited above):
1. Account `victim.near` issues an `ActionReceipt` with two `input_data_ids` (a two-way join, e.g. via `Promise::and`), which the runtime stores as `PostponedReceipt`/`PendingDataCount` keyed by `victim.near` while waiting on the second `DataReceipt`.
2. Before the second `DataReceipt` arrives, `victim.near` submits a `DeleteAccount` action with a small enough `storage_usage()` (unaffected by the pending receipt data) to pass `MAX_ACCOUNT_DELETION_STORAGE_USAGE`; `remove_account` deletes `Account`/`AccessKey`/`ContractCode`/`ContractData` but leaves `PostponedReceipt`/`PendingDataCount` for `victim.near` in the trie.
3. Someone recreates `victim.near` (e.g., via an ETH-implicit or named account creation flow).
4. The delayed second `DataReceipt` arrives; `Runtime::process_receipt` (`runtime/runtime/src/lib.rs:1475-1509`) finds the leftover `PendingDataCount`/`PostponedReceipt` under `victim.near` and executes the old postponed `ActionReceipt`'s actions against the newly created account — actions the new owner never authorized.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
