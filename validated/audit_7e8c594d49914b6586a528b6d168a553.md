### Title
Interest-accrual pause silently freezes the share-index while deposit/redeem/borrow/repay remain active, mispricing zToken exchange rate - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent v0-vault-{sbtc,usdc,usdh,ststx,ststxbtc}.clar)

### Summary
Each Zest vault's `accrue()` function contains a dedicated `accrue` pause flag that, when set, makes `accrue()` return the stale, previously-stored `index`/`lindex` instead of computing and persisting the real accrued interest, and it silently skips minting the DAO treasury's protocol-fee shares for that period. Because `deposit`, `redeem`, `system-borrow`, and `system-repay` gate on their *own* independent pause flags (`deposit`, `redeem`, `borrow`, `repay`) rather than on the `accrue` flag, all four operations remain fully callable while `accrue` is paused. Every one of them calls `(try! (accrue))` first, then reads `(var-get index)`/`(var-get assets)` to price zToken shares — so they execute against a frozen exchange rate that omits real economic interest which is still notionally accruing on outstanding debt.

### Finding Description
`accrue()` is structured as a pass-through-on-pause function rather than a revert-on-pause function:

```clarity
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          ...
``` [1](#0-0) 

The pause-states record defines `accrue` as an independent toggle from `deposit`, `redeem`, `borrow`, and `repay`: [2](#0-1) 

`deposit` and `redeem` each begin with `(u (try! (accrue)))`, then immediately read `(var-get assets)` (and, transitively through `convert-to-shares-preview`/`convert-to-assets-preview`, the stored `index`) to price the exchange between underlying and zToken shares, while only checking their own local pause bit (`(get deposit states)` / `(get redeem states)`): [3](#0-2) [4](#0-3) 

The same pattern repeats for `system-borrow`, which is gated by `(get borrow states)` only, not `accrue`: [5](#0-4) 

**Root cause / mechanism**: `accrue`'s pause is a *pass-through instead of a revert*. Because it does not propagate its paused state to `index`/`lindex`/`last-update`, and because sibling operations do not check the `accrue` bit before consuming those same variables, a single independently-togglable pause flag decouples the "index freshness" invariant from the operations that depend on it being fresh. Any deposit/redeem/borrow/repay executed while `accrue` is paused (but the sibling flag is not) prices shares against a stale index that omits interest genuinely owed for the elapsed time (`stacks-block-time - last-update`), even though that same interest is later captured in a single retroactive jump the next time `accrue` runs unpaused (since `next-index`/`next-liquidity-index` compute off elapsed time from `last-update`, not off the pause window).

### Impact Explanation
While `accrue` is paused and `deposit`/`redeem` remain enabled:
- Users who **redeem** shares are paid out based on the stale (lower) exchange rate, permanently losing the yield portion that had already accrued between `last-update` and the time of their redemption — this yield is instead retained by remaining shareholders once the index eventually catches up.
- Users who **deposit** during the window mint shares priced without that same accrued interest, diluting existing shareholders' claim on the yield that will be booked in the future catch-up accrual.
- The DAO treasury's protocol fee share (`treasury-lp`, minted only inside the non-paused branch of `accrue`) is not lost outright (it is captured on the next successful accrual), but any interest realized against a stale index during the paused window is transferred between users rather than correctly reflected per-transaction.

This is theft/mispricing of unclaimed yield transacted during a legitimate operational window, matching the in-scope impact class "theft of unclaimed yield ... or temporary freezing of unclaimed yield."

### Likelihood Explanation
Triggering this requires only that the DAO (or whoever holds `set-pause-states` authority) pause `accrue` independently of `deposit`/`redeem`/`borrow`/`repay` — a state that is easy to reach unintentionally (e.g., pausing accrual for a rate-model migration while leaving deposits open) since the four flags are stored together in one tuple but enforced independently by each entrypoint. No attacker privilege is required beyond normal deposit/redeem/borrow calls during that window; only the operator's pause configuration choice determines the window's existence.

### Recommendation
Make every entrypoint that reads `index`/`lindex`/`assets` for pricing also assert on the `accrue` pause bit (or fold the accrual pause into a single unified check), so that pausing accrual reverts dependent deposit/redeem/borrow/repay calls instead of silently letting them execute against a stale index. Alternatively, have `accrue()` revert when paused (matching the non-pass-through convention used elsewhere) so callers cannot proceed with unaccrued state.

### Proof of Concept
1. DAO calls `set-pause-states` on `v0-vault-stx` with `{accrue: true, deposit: false, redeem: false, borrow: false, repay: false, flashloan: false}` (see pause-states shape) [2](#0-1) .
2. Time passes; real utilization-based interest would raise `next-index`/`next-liquidity-index` above the stored `index`/`lindex`.
3. User A calls `redeem`, which runs `(try! (accrue))` — this hits the paused branch and returns the stale `idx`/`lidx` without updating state [6](#0-5) ; `redeem` then computes `inkind` via `convert-to-assets-preview`, using the stale `assets`/index, and burns shares/pays out underlying at the depressed rate [4](#0-3) .
4. DAO unpauses `accrue`; the next call to `accrue()` jumps `index`/`lindex` directly to the value reflecting the entire elapsed period, retroactively capturing the yield User A's redemption never received.
5. Repeat across `vault-sbtc`, `vault-usdc`, `vault-usdh`, `vault-ststx`, `vault-ststxbtc` (mainnet and local-testing), which share the identical `accrue`/pause-state structure.

**Uncertainty**: I could not directly inspect the full bodies of `next-index`, `next-liquidity-index`, `convert-to-shares-preview`, and `convert-to-assets-preview` (only their call sites were indexed), so I cannot cite the exact arithmetic proving the magnitude of mispricing beyond the pattern shown above. The index size limits of this tool may exclude some file contents; a full Devin session with direct file access would be needed to confirm the precise numeric divergence and whether any other safeguard (e.g., a global staleness check elsewhere in `market.clar`) mitigates this at the caller level.
