### Title
Legacy WebAPI Trigger handler skips authorization/allowlist checks that its v2 counterpart enforces - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway exposes two implementations for handling WebAPI trigger requests destined for a DON: a legacy path in `core/services/gateway/handlers/capabilities/handler.go` (`HandleLegacyUserMessage`) and a newer v2 path in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` (`HandleUserTriggerRequest`). The v2 path enforces per-workflow authorization via `authorizeRequest`/`WorkflowMetadataHandler.Authorize` (JWT signer must be in the workflow's `authorizedKeys` set) before forwarding a request to DON nodes. The legacy path performs no equivalent authorization or allowlist check — it explicitly contains a `// TODO: apply allowlist and rate-limiting here` comment — and forwards any well-formed, non-expired message straight to all DON members.

### Finding Description
In `capabilities/handler.go`, `HandleLegacyUserMessage` validates only payload shape and message staleness before dispatching the request to every DON member: [1](#0-0) 
There is no call to any allowlist, authorized-key set, or signer verification analogous to what the v2 handler performs. Compare this to the v2 `authorizeRequest`, which requires that the request's JWT signer be present in `workflowMetadataHandler.authorizedKeys[workflowID]`: [2](#0-1) 
and `WorkflowMetadataHandler.Authorize`, which enforces the authorized-key/signer check and JWT replay protection: [3](#0-2) 

This mirrors the reported bug class exactly: the protocol intends only authorized/whitelisted callers to trigger the privileged action (workflow execution via a DON), but a second, less-guarded entrypoint (the legacy handler, still reachable via `gateway.ProcessRequest` when a legacy `DonId`-bearing message is submitted) allows any caller to invoke the same privileged action without the whitelist/authorization check that the "correct" endpoint enforces. [4](#0-3) 

### Impact Explanation
Any external, non-whitelisted user able to reach the gateway can submit a legacy-format WebAPI trigger message and have it forwarded to all DON nodes for processing/execution, bypassing the JWT/authorized-key gating that governs the v2 entrypoint for the same functional capability. This is an unauthorized-trigger/workflow-execution trust-boundary bypass — it lets unapproved parties invoke DON-side workflow logic that was designed to be gated by authorization.

### Likelihood Explanation
Likelihood is moderate-to-high in deployments where the legacy DON-ID-keyed routing path in `gateway.ProcessRequest` remains active alongside the v2 service-name routing (both code paths coexist in `gateway.go`), since selecting the legacy path requires only crafting a message with `msg.Body.DonId` set, which is straightforward for any external caller reaching the gateway's public interface.

### Recommendation
Implement the same authorization gate in `HandleLegacyUserMessage` that exists in the v2 path (verify caller/signer against `authorizedKeys` for the target workflow, or equivalently enforce the intended allowlist/rate-limit) before forwarding to DON members, removing the outstanding `// TODO: apply allowlist and rate-limiting here` in `core/services/gateway/handlers/capabilities/handler.go`. Alternatively, deprecate/disable the legacy handler entirely once all callers migrate to the v2 authorized path, and add integration tests asserting that unauthorized legacy-format requests are rejected the same way unauthorized v2 requests are.

### Proof of Concept
Not executable from static review alone; conceptually: craft an `api.Message` with `Body.DonId` set to a DON with the capabilities handler enabled, `Body.Method` = `MethodWebAPITrigger`, and a valid (non-expired) `TriggerRequestPayload.Timestamp`, then submit via the gateway's legacy JSON-RPC path. Because `HandleLegacyUserMessage` only checks payload decodability and timestamp freshness, this message is forwarded to all `donConfig.Members` without any signer/authorized-key verification, unlike the equivalent v2 flow which requires `authorizeRequest` to succeed first.

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
