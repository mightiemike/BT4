### Title
Snapshot-restore reward recalculation uses live (post-mutation) stake amount instead of the epoch-boundary-frozen delegation, causing capitalization/bank-hash divergence between continuously-replayed and snapshot-restarted nodes - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`Bank::recalculate_stake_rewards` is invoked only when a node restarts from a snapshot while `EpochRewards` is still active, and it recomputes stake rewards from `self.stakes_cache.stakes()` — the *current* state — rather than reusing the frozen `all_stake_rewards` that was computed once at the epoch boundary and cached in `EpochRewardStatus`. While the total per-validator delegated-stake denominator is protected against tampering via the persisted `RewardEpochDelegatedStakesAccount`, the individual stake account's own effective-stake *numerator* is derived directly from the live, mutable `Delegation::stake` field, letting an attacker who merges/tops-up an already-activated stake account in the gap window inflate the reward computed for a past (`rewarded_epoch`) once a restart-triggered recalculation occurs.

### Finding Description
`recalculate_partitioned_rewards_if_active` (called only from `Bank::initialize_after_snapshot_restore`, itself only invoked on snapshot load, `runtime/src/bank.rs:6081` / `runtime/src/bank.rs:2219`) fires whenever `epoch_rewards_sysvar.active` is true: [1](#0-0) 

`Bank::epoch_reward_status`, which holds the epoch-boundary-frozen `all_stake_rewards`, is **not** serialized to the snapshot (`get_fields_to_serialize` has no such field) and is reset to `EpochRewardStatus::default()` on load: [2](#0-1) [3](#0-2) 

`recalculate_stake_rewards` therefore has to reconstruct it from `self.stakes_cache.stakes()`, the live stakes as of the snapshot slot: [4](#0-3) 

The engineering team is aware that intermediate mutation of the total delegated stake per vote account (from distributed rewards or new activations) could corrupt the AG points denominator, so they froze it on-chain in `REWARD_EPOCH_DELEGATED_STAKES_ACCOUNT`, written once at the epoch boundary in `calculate_activated_stake`/`RewardEpochDelegatedStakes::set` and re-read (unmodifiable by users, since only the runtime writes it) during recalculation: [5](#0-4) [6](#0-5) 
Test `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` confirms this defense exists specifically for the denominator.

However, the **numerator** — each stake account's own effective/activated stake for the rewarded epoch — is computed with `delegation_effective_stake(&stake.delegation, epoch, stake_history, …)`, which reads directly from the *live* `Stake.delegation.stake` field in `self.stakes_cache.stakes()` at recalculation time, not a value frozen at the epoch boundary: [7](#0-6) [8](#0-7) 

For a stake delegation that is already fully activated (activation_epoch well before `rewarded_epoch`), the underlying `Delegation::stake`/`stake_v2` warmup/cooldown math simply returns the current `delegation.stake` value for any queried past epoch once fully warmed — it has no notion of "what the stake amount was specifically during `rewarded_epoch`" versus "what it is now." If an attacker merges additional already-active stake lamports into their own delegated stake account (an unprivileged, ordinary stake-program instruction) in a slot after `begin_partitioned_rewards` cached the epoch-boundary calculation but before all partitions are distributed, and the validator then restarts from a snapshot taken in that window, `recalculate_stake_rewards` will compute a *larger* effective stake for `rewarded_epoch` than the value that existed when the epoch actually ended, inflating that attacker's stake_reward/points relative to the frozen `all_stake_rewards` that a continuously-replaying node would have retained. Both the AG (`calculate_alpenglow_points`) and legacy Tower (`tower_epoch_credits_iter`) point-calculation paths call into the same `delegation_effective_stake`/`stake.stake()` mechanism, so this is not confined to Alpenglow.

### Impact Explanation
This produces a genuine honest-node snapshot-vs-replay mismatch: a validator that continuously replays the ledger pays the frozen, epoch-boundary-computed stake reward, while a validator that restarts from a snapshot taken in the distribution gap window recomputes and pays a different (potentially larger) reward for the same historical epoch/attacker delegation. Since stake reward lamports are minted into `capitalization` during `distribute_epoch_rewards_in_partition`, this leads to capitalization and bank-hash divergence between otherwise-honest nodes that processed identical transaction logs but differ only in whether/when they restarted from a snapshot — a consensus-safety issue, not merely a metrics or cosmetic bug.

### Likelihood Explanation
Preconditions are attacker-controllable and require no privileged access: the attacker only needs (a) an existing stake delegation that is one of the `rewarded_epoch`'s delegations, and (b) the ability to submit an ordinary stake-merge/top-up transaction in a slot between the epoch boundary and full distribution completion, both of which are normal unprivileged stake-account operations. The only condition outside attacker control is that some node restarts from a snapshot taken within that gap — a routine, non-malicious validator operational event (process restart, RPC/backup node bootstrap from a fresh snapshot, ledger-tool replay) rather than an attacker-crafted snapshot. Given the reward distribution window can span many blocks (`REWARD_CALCULATION_NUM_BLOCKS` plus multiple partitions), the exploitable window is not vanishingly small, making this realistically repeatable in a long-running network with frequent validator restarts.

### Recommendation
Freeze each stake delegation's effective stake for `rewarded_epoch` at the time of `begin_partitioned_rewards` (analogous to how `RewardEpochDelegatedStakes` freezes the aggregate denominator), and persist enough state (or reconstruct it deterministically from the already-persisted `stake_history` and pre-boundary activation/deactivation epochs rather than the live current `delegation.stake` amount) so that `recalculate_stake_rewards` cannot be influenced by any stake-account mutation performed after `begin_partitioned_rewards` executed. Alternatively, serialize `EpochRewardStatus`'s `all_stake_rewards`/`StakeRewardCalculation` into the snapshot so recalculation is never necessary and the exact epoch-boundary values are always restored unchanged.

### Proof of Concept
Rust integration-test plan (mirroring the existing `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` and `test_initialize_after_snapshot_restore` tests in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`):
1. Build a reward bank with one stake delegation fully activated well before the epoch boundary (`create_reward_bank_with_specific_stakes`), and cross the epoch boundary so `begin_partitioned_rewards` caches `all_stake_rewards` in `EpochRewardStatus::Calculation`, recording `original_stake_rewards` for the attacker's `stake_pubkey`.
2. On a cloned "attacker" path, before all partitions are distributed, submit a stake-merge/top-up instruction that increases `delegation.stake` for the attacker's already fully-activated stake account (simulate via `bank.store_account` writing an updated `StakeStateV2` with increased `delegation.stake`, or via the real stake-program `merge` instruction in an integration test using `program-test`).
3. Simulate snapshot restore by resetting transient state and calling `bank.initialize_after_snapshot_restore(...)`, which triggers `recalculate_stake_rewards`.
4. Assert that the recalculated `PartitionedStakeReward` for the attacker's `stake_pubkey` differs from `original_stake_rewards` (specifically `inflation.stake_reward` is larger), whereas on the non-restarted path (continuing without a snapshot restore) the reward stays equal to `original_stake_rewards`.
5. Extend to full bank-level assertion: build two banks from the identical transaction/block log except that one bank undergoes a simulated snapshot restore in the gap slot; after completing distribution on both, assert `bank.capitalization()` and `bank.hash()`/`get_bank_hash()` differ between the two, demonstrating consensus-relevant divergence.

impl RewardEpochDelegatedStakes {
    pub(crate) fn set(&self, bank: &Bank, distribution_vote_accounts: &VoteAccounts) {
        assert!(
            distribution_vote_accounts.len() <= MAX_ALPENGLOW_VOTE_ACCOUNTS,
            "reward epoch delegated stakes account must be bounded by MAX_ALPENGLOW_VOTE_ACCOUNTS"
        );

        let mut delegated_stakes = distribution_vote_accounts
            .delegated_stakes()
            .map(
                |(vote_pubkey, _delegated_stake)| RewardEpochDelegatedStake {
                    vote_pubkey: *vote_pubkey,
                    delegated_stake: self
                        .delegated_stakes
                        .get(vote_pubkey)
                        .copied()
                        .unwrap_or_default(),
                },
            )
            .collect::<Vec<_>>();
        delegated_stakes.sort_unstable_by_key(|stake| stake.vote_pubkey);

        let account = RewardEpochDelegatedStakesAccount {
            epoch: self.epoch,
            delegated_stakes,
        };
        let data = wincode::serialize(&account).unwrap();
        let lamports = bank
            .get_minimum_balance_for_rent_exemption(RewardEpochDelegatedStakesAccount::max_size());
        let mut account = AccountSharedData::new(lamports, data.len(), &system_program::ID);
        account.set_data_from_slice(&data);

        bank.store_account_and_update_capitalization(
            &REWARD_EPOCH_DELEGATED_STAKES_ACCOUNT,
            &account,
        );
    }

    pub(crate) fn get(bank: &Bank) -> Option<Self> {
        let account = bank.get_account(&REWARD_EPOCH_DELEGATED_STAKES_ACCOUNT)?;
        (!account.data().is_empty()).then(|| {
            let account: RewardEpochDelegatedStakesAccount = wincode::deserialize(account.data())
                .expect("Couldn't deserialize reward epoch delegated stakes");
            assert!(
                account.delegated_stakes.len() <= MAX_ALPENGLOW_VOTE_ACCOUNTS,
                "reward epoch delegated stakes account exceeds MAX_ALPENGLOW_VOTE_ACCOUNTS"
            );
            account.into()
        })
    }
