### Title
Unbounded, attacker-controlled `UniversalPayload.GasLimit` lets an inbound payload starve ballot-finalization/vote transactions, DoSing UTX finalization - (File: `x/uexecutor/types/universal_payload.go`, `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/msg_vote_inbound.go`)

### Summary
The LooksRare finding is a class of bug where a VRF-callback-style function that "must not revert" (`fulfillRandomWords`) can exceed the network's hard gas ceiling because a configurable multiplier scales an internal loop without an upper bound, causing consensus-critical finalization to fail. Push Chain has a structurally identical pattern: `UniversalPayload.GasLimit` — a fully attacker-controlled, user-supplied field carried inside an `Inbound` — is validated only for being a syntactically valid non-negative integer and is then passed **unbounded** as the explicit EVM `gasLimit` argument to `DerivedEVMCall` when the payload is executed synchronously inside the finalizing Universal Validator's `MsgVoteInbound` transaction.

### Finding Description
`UniversalPayload.ValidateBasic()` only checks that `gas_limit` parses as a non-negative `uint256` string; there is no upper bound check anywhere in the validation path: [1](#0-0) 

`ValidateForExecution()` (invoked after ballot finalization) likewise only calls `p.UniversalPayload.ValidateBasic()` for `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbounds — it never caps `GasLimit` against a sane maximum: [2](#0-1) 

That raw value is parsed straight into a `*big.Int` and handed to `DerivedEVMCall` as an explicit gas limit with no clamping: [3](#0-2) 

This call path is reached synchronously the moment an inbound ballot reaches quorum, i.e. inside the *last* voting Universal Validator's own `MsgVoteInbound` transaction (`VoteInbound` → `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` → `ExecutePayloadV2` → `CallUEAExecutePayload` → `DerivedEVMCall`): [4](#0-3) [5](#0-4) 

`MsgVoteInbound` is a gasless, whitelisted message type that bypasses ordinary fee/gas-limit checks in the ante pipeline (`MinGasPriceDecorator`, `DeductFeeDecorator` are skipped): [6](#0-5) 

An unprivileged attacker sending funds/payload through the external gateway fully controls the `UniversalPayload.GasLimit` field encoded in their inbound raw payload. Because this field is never capped relative to the Push Chain block gas limit before being fed to `DerivedEVMCall`, an attacker can construct an inbound whose `GasLimit` is astronomically large (e.g. `2^256-1`). When the ballot for that inbound reaches quorum, the finalizing validator's `MsgVoteInbound` transaction attempts to run `executeUniversalTx` with that gas limit via `DerivedEVMCall` (`isModuleSender=true`, explicit `gasLimit`), which — analogous to the LooksRare VRF-callback overflow — risks exceeding the practical execution bounds of the EVM call/transaction (out-of-gas panics, block-gas-limit interactions in the underlying fork, or simply pathological gas accounting), jeopardizing the atomic vote+finalize transaction that is supposed to "always create a UniversalTx" per the module's own documented invariant.

### Impact Explanation
Per the module's design, `VoteInbound` is documented to *always* create a `UniversalTx` after ballot finalization "regardless of whether the inbound passes execution validation," so users can query what happened instead of having funds silently stuck: [7](#0-6) 

If the finalizing vote transaction itself fails/panics due to the unbounded `GasLimit` being fed into `DerivedEVMCall`, that invariant breaks: the ballot has technically reached quorum but the transaction that was supposed to atomically create the `UniversalTx` (and remove the pending-inbound entry) does not complete, leaving the inbound stuck in `PendingInbounds` with no `UniversalTx` record, and forcing every subsequent UV that tries to finalize it to hit the same failure — a repeatable, low-cost, unprivileged denial-of-service against inbound finalization for that UTX, and by extension against user funds that are already locked in the source-chain gateway.

### Likelihood Explanation
Likelihood is high: constructing an inbound with an oversized `GasLimit` requires no privilege beyond being a normal bridge user submitting funds through the gateway. `ValidateBasic`/`ValidateForExecution` both pass such a value unchanged, and no site between message ingestion and `DerivedEVMCall` clamps the value to a sane bound (e.g. Push Chain's block gas limit).

### Recommendation
Enforce a maximum bound on `UniversalPayload.GasLimit` in `ValidateBasic()` and/or `ValidateForExecution()` (e.g., capped at a fraction of the chain's configured block gas limit), and defensively clamp the value again immediately before it is passed into `DerivedEVMCall` in `CallUEAExecutePayload`, rejecting/failing the payload gracefully (recorded as a `FAILED` PCTx, per the existing failure-handling pattern) rather than letting an unbounded value reach the EVM execution layer inside the validator's own finalizing transaction.

### Proof of Concept
1. Craft a `FUNDS_AND_PAYLOAD` (or `GAS_AND_PAYLOAD`) inbound gateway event on a supported external chain where the encoded `UniversalPayload.GasLimit` is set to an extreme value (e.g., `"115792089237316195423570985008687907853269984665640564039457584007913129639935"`, the max `uint256`).
2. Universal Validators observe and vote via `MsgVoteInbound` as usual; `ValidateBasic`/`ValidateForExecution` accept the payload because they only check "valid unsigned integer," not magnitude (`x/uexecutor/types/universal_payload.go` lines 41-58, `x/uexecutor/types/inbound.go` lines 150-164).
3. On the finalizing vote, `VoteInbound` → `ExecuteInboundFundsAndPayload` → `ExecutePayloadV2` → `CallUEAExecutePayload` parses `GasLimit` into a `*big.Int` and passes it directly as the `gasLimit` argument to `DerivedEVMCall` (`x/uexecutor/keeper/evm.go` lines 172-192), with no upper-bound check anywhere in the call chain.
4. Observe whether the finalizing validator's `MsgVoteInbound` transaction fails/panics due to the pathological gas limit, leaving the UTX unfinalized and the inbound stuck in `PendingInbounds`.

// CallUEAExecutePayload executes a universal payload through UEA
func (k Keeper) CallUEAExecutePayload(
	ctx sdk.Context,
	from, ueaAddr common.Address,
	universal_payload *types.UniversalPayload,
	verificationData []byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	abi, err := types.ParseUeaABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UEA ABI")
	}

	abiUniversalPayload, err := types.NewAbiUniversalPayload(universal_payload)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal payload")
	}

	gasLimit := new(big.Int)
	gasLimit, ok := gasLimit.SetString(universal_payload.GasLimit, 10)
	if !ok {
		return nil, fmt.Errorf("invalid gas limit: %s", universal_payload.GasLimit)
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,
		ueaAddr,
		big.NewInt(0),
		gasLimit,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"executeUniversalTx",
		abiUniversalPayload,
		verificationData,
	)
}

func (k Keeper) ExecutePayloadV2(ctx context.Context, evmFrom common.Address, ueaAddr common.Address, universalPayload *types.UniversalPayload, verificationData string) (*vmtypes.MsgEthereumTxResponse, error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Debug("execute payload v2",
		"uea", ueaAddr.Hex(),
		"from", evmFrom.Hex(),
	)

	// Step 1: Validate payload and verificationData early (fast-fail before EVM work)
	if _, err := types.NewAbiUniversalPayload(universalPayload); err != nil {
		return nil, errors.Wrapf(err, "invalid universal payload")
	}

	verificationDataVal, err := utils.HexToBytes(verificationData)
	if err != nil {
		return nil, errors.Wrapf(err, "invalid verificationData format")
	}

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}
