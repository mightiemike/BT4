### Title
`DeleteAccount` with `beneficiary_id == account_id` Permanently Burns Account Balance — (`runtime/runtime/src/actions.rs`)

---

### Summary

`action_delete_account` in `runtime/runtime/src/actions.rs` creates a balance-refund receipt addressed to `beneficiary_id`, then immediately removes the account from state. No guard checks whether `beneficiary_id == account_id`. When they are equal the refund receipt arrives at a now-deleted account, fails with `AccountDoesNotExist`, and the protocol's own refund-failure path burns the entire balance into `other_burnt_amount`. The documented invariant — "tokens are transferred to `beneficiary_id`" — is silently violated and the funds are permanently destroyed.

---

### Finding Description

**Broken invariant:** `DeleteAccountAction` documentation states the account balance is transferred to `beneficiary_id`. When `beneficiary_id == account_id` the balance is instead burnt.

**Step-by-step execution path:**

1. **Validation — no self-referential check.**
   `validate_delete_action` only calls `validate_action_account_id(&action.beneficiary_id)`, confirming the string is a syntactically valid account ID. It never compares `beneficiary_id` to the receipt's `receiver_id` (the account being deleted). [1](#0-0) 

2. **Execution — refund receipt created, then account removed.**
   `action_delete_account` reads `account_balance`, pushes `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` into `result.new_receipts`, and then calls `remove_account(state_update, account_id)` / sets `*account = None`. When `beneficiary_id == account_id` the refund receipt targets the account that is about to cease to exist. [2](#0-1) 

3. **Refund receipt processing — failure burns the deposit.**
   The balance-refund receipt has `predecessor_id == "system"`. In `apply_action_receipt`, the system-predecessor branch is:
   ```rust
   // If the refund fails tokens are burned.
   if result.result.is_err() {
       stats.balance.other_burnt_amount = safe_add_balance(
           stats.balance.other_burnt_amount,
           total_deposit(&action_receipt.actions())?,
       )?
   }
   ```
   The receipt fails because the target account no longer exists, so the full `account_balance` is added to `other_burnt_amount`. [3](#0-2) 

4. **Transfer to non-existent account — no implicit recreation.**
   `check_transfer_to_nonexisting_account` explicitly notes: *"Account deletion with beneficiary creates a refund, so it'll not create a new account."* Even for implicit-account IDs the `implicit_account_creation_eligible` flag is `false` for system-predecessor receipts, so the account is never recreated. [4](#0-3) 

5. **Refund receipt construction — Transfer action carries the full balance.**
   `Receipt::new_balance_refund` wraps the amount in a `Transfer` action with `predecessor_id = "system"`. When the transfer fails the deposit is burnt per the rule above. [5](#0-4) 

---

### Impact Explanation

**Loss of funds.** The entire unlocked balance of the deleted account is permanently destroyed. The broken invariant is: the protocol guarantees tokens reach `beneficiary_id`, but when `beneficiary_id == account_id` they are instead added to the protocol's burn accounting and never credited to any live account. This matches the "balance manipulation / loss of funds" impact category.

---

### Likelihood Explanation

**Low-to-medium.** A user must explicitly set `beneficiary_id` to their own account ID. This is unlikely in a hand-crafted transaction but is reachable in two realistic scenarios:

- A smart contract calls `promise_batch_action_delete_account` and passes `env::current_account_id()` as the beneficiary (a natural pattern for a self-destructing contract that intends to recover its own balance before deletion — the developer may not realise the account is gone before the refund arrives).
- A wallet or tooling bug that defaults `beneficiary_id` to the signer/receiver account.

No privileged role is required; any account holder can trigger this with a standard signed transaction.

---

### Recommendation

Add a guard in `validate_delete_action` (or in `action_delete_account`) that rejects or specially handles the case where `beneficiary_id == account_id`:

```rust
fn validate_delete_action(
    action: &DeleteAccountAction,
    receiver_id: &AccountId,          // the account being deleted
) -> Result<(), ActionsValidationError> {
    validate_action_account_id(&action.beneficiary_id)?;
    if action.beneficiary_id == *receiver_id {
        return Err(ActionsValidationError::DeleteAccountBeneficiaryIsSelf {
            account_id: receiver_id.clone(),
        });
    }
    Ok(())
}
```

Alternatively, mirror the SENDALL fix from the external report: skip emitting the balance-refund receipt when `beneficiary_id == account_id` (and optionally burn the balance explicitly, or reject the action). The validation path is preferable because it surfaces the error early and avoids silent fund loss.

---

### Proof of Concept

```
1. Alice holds 10 NEAR on account "alice.near".
2. Alice submits a signed transaction:
     signer_id:   "alice.near"
     receiver_id: "alice.near"
     actions:     [DeleteAccount { beneficiary_id: "alice.near" }]
3. Runtime executes action_delete_account:
     - account_balance = 10 NEAR
     - Pushes Receipt::new_balance_refund("alice.near", 10 NEAR)
     - Calls remove_account(state_update, "alice.near")  ← account gone
4. Balance-refund receipt is processed:
     - predecessor_id == "system"
     - Transfer(10 NEAR) → "alice.near"
     - check_account_existence → AccountDoesNotExist
     - result.result = Err(...)
     - stats.balance.other_burnt_amount += 10 NEAR   ← funds destroyed
5. Final state: "alice.near" does not exist, 10 NEAR is burnt.
   Expected state per documentation: "alice.near" receives 10 NEAR.
```
