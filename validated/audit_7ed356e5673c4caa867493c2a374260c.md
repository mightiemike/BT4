This confirms `MsgVoteInbound.GetSigners()` returns the address parsed straight from `msg.Signer` (a plain bech32 string field), independent of any cryptographic pubkey — exactly the value used by `AccountInitDecorator` as `newAccAddr`, and exactly the value passed downstream to `IsBondedUniversalValidator` checks in `x/uexecutor/keeper/msg_server.go`. This is the missing link that turns the ante-layer flaw into an unauthorized-vote-injection primitive.

### Title
Missing pubkey-to-address binding in gasless first-use account bootstrap allows forged Universal Validator votes and messages - (File: app/ante/account_init_decorator.go)

### Summary
`AccountInitDecorator.verifySignatureForNewAccount` treats "account does not yet exist on-chain" as an implicit trust window — analogous to RocketStorage's `storageInit == false` phase — and short-circuits the entire remaining ante chain (skipping `SetPubKeyDecorator`, `ValidateSigCountDecorator`, `SigVerificationDecorator`) after only checking that *some* valid ECDSA/Ed25519 signature exists over the signed bytes with `account_number=0, sequence=0`. It never checks that the signing pubkey's derived address equals the claimed signer address, which `SetPubKeyDecorator` normally enforces. Because Cosmos SDK message signer addresses (e.g. `MsgVoteInbound.Signer`) are plain string fields returned by `GetSigners()` rather than values cryptographically derived from the signature, an attacker can sign a transaction with **their own arbitrary keypair** while setting the message's `Signer` field to any address that has no on-chain account yet (e.g. a freshly-registered Universal Validator hotkey that has never transacted).

### Finding Description
`app/ante/account_init_decorator.go:31-81` is wired in `app/ante/ante_cosmos.go:48` to run before `SetPubKeyDecorator`, `SigVerificationDecorator`, etc., specifically for gasless message types (`app/txpolicy/gasless.go`, which whitelists `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`, `MsgExecutePayload`).

When `!aid.ak.HasAccount(ctx, newAccAddr)` (line 53), the decorator calls `verifySignatureForNewAccount` (lines 83-170) and, on success, **returns `(ctx, nil)` directly, bypassing every other signature/pubkey decorator** (lines 68-74). `verifySignatureForNewAccount` builds `SignerData{Address: newAccAddr.String(), AccountNumber: 0, Sequence: 0, PubKey: <sig's pubkey>}` and calls `authsigning.VerifySignature` — this only proves the signature is cryptographically valid for *some* keypair over the given sign bytes; it never checks `pubKey.Address() == newAccAddr`, the check that `SetPubKeyDecorator` normally performs.

Since `newAccAddr` comes from `sigTx.GetSigners()`, which for these custom messages simply parses the message's own `Signer` string field (`x/uexecutor/types/msg_vote_inbound.go:47-50` — `sdk.AccAddressFromBech32(msg.Signer)`), an attacker fully controls which address is "authenticated" independent of which key actually produced the signature.

### Impact Explanation
An unprivileged attacker can:
1. Identify a bonded/pending Universal Validator hotkey address (public, from `x/uvalidator` state) or any UEA-controlling address that has not yet sent its first Cosmos transaction (`HasAccount == false`) — an expected bootstrap state explicitly designed for ("lets a freshly-keygen'd Universal Validator hot key vote on its very first tx, without anyone first having to fund it," per `app/README.md:182`).
2. Craft `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration` with `Signer` = victim address, sign the transaction with an unrelated attacker-owned key, and submit it.
3. The ante chain accepts it via the bootstrap bypass; message execution proceeds to `x/uexecutor/keeper/msg_server.go`'s `IsBondedUniversalValidator(signer)` check, which passes because the signer *address* (not key) matches a real bonded UV.
4. The forged vote is recorded as if the legitimate UV had voted — corrupting honest-validator ballot finalization (wrong inbound/outbound/chain-meta/TSS-event ballot outcome), potentially pushing a malicious `InboundVariant` toward `PASSED` before the real validator ever transacts, or forging a TSS key-process/fund-migration vote.

This directly matches the "Honest-validator finalization path" and "Admission and cryptographic path ... first-use account initialization ... must not turn attacker input into accepted authorization" impact categories, and can lead to unauthorized state transitions in universal execution (wrong ballot/UTX outcome), which are explicitly in scope.

### Likelihood Explanation
Medium-High. It requires only public information (UV registry, or any address that is a message signer in a gasless-eligible message and has not yet transacted) and no privileged keys. The bootstrap window (address registered/known, but `HasAccount == false`) is a normal, expected, and even documented operational state for freshly-onboarded Universal Validators, making the precondition realistic rather than contrived. The attacker only needs to win a race to submit before the legitimate key's first transaction lands.

### Recommendation
- In `verifySignatureForNewAccount`, after successful cryptographic verification, explicitly assert `sdk.AccAddress(pubKey.Address()).Equals(newAccAddr)` before creating the account or allowing the tx to proceed — mirroring the check performed by the standard `SetPubKeyDecorator`.
- Alternatively, do not fully bypass `SetPubKeyDecorator`/`SigVerificationDecorator`; instead only special-case the "account doesn't exist yet" branch to skip the *sequence-number lookup* (using implicit 0/0), while still routing through the standard pubkey-binding check.
- Add a regression test asserting that a transaction signed by key A but declaring `Signer` = address B (where B has no account) is rejected.

### Proof of Concept
1. Attacker generates a fresh keypair `K_attacker` (any random key, unrelated to the target).
2. Attacker identifies a bonded Universal Validator hotkey address `V` registered in `x/uvalidator` state that has not yet submitted any transaction (`accountKeeper.HasAccount(ctx, V) == false`).
3. Attacker builds `MsgVoteInbound{Signer: V, Inbound: <attacker-chosen forged inbound data>}`, wraps it in a transaction, and signs it using `K_attacker` with `account_number=0, sequence=0`.
4. Attacker broadcasts the transaction. `AccountInitDecorator.AnteHandle` sees `HasAccount(V) == false`, calls `verifySignatureForNewAccount`, which validates the signature (valid, since `K_attacker` genuinely signed the exact bytes) and returns success without ever checking that `K_attacker`'s derived address equals `V`.
5. The decorator creates a `BaseAccount` at `V` with sequence 1 and returns `(ctx, nil)`, bypassing `SetPubKeyDecorator`/`SigVerificationDecorator`.
6. Baseapp proceeds to execute `MsgVoteInbound`; `msg_server.go`'s `IsBondedUniversalValidator(V)` check passes because `V` is a real bonded UV, recording a forged vote from `V` that the attacker never actually controlled the key for.
