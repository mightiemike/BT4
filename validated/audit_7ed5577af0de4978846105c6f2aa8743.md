This confirms the analog: `check_block_hash_consistency` only verifies that the calculated `new_block_hash` matches the sequencer-supplied `os_input.new_block_hash` (an internal sanity check within the same execution) [1](#0-0) , but the **previous** block hash and previous state root fed into `get_block_hashes`/`get_block_os_output_header` are both prover-guessed hints, and the OS explicitly does not verify that they are consistent with each other — that check is deferred to "the consumer of the OS output" [2](#0-1) .

### Title
Missing verification that previous block hash matches previous state root in single-block OS output header - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/os_utils.cairo`)

### Summary
`get_block_os_output_header` builds the `OsOutputHeader` for a block by calling `get_block_hashes`, which guesses (via hint) both `previous_block_hash` and the previous state root implicitly used to derive them, without asserting that this guessed `previous_block_hash` actually corresponds to the `initial_root`/previous state root that the OS is committing against [3](#0-2) . The Cairo code itself documents this gap with a `TODO(Yoni)` comment stating the OS "does not verify their consistency ... The consumer of the OS output should verify both" [4](#0-3) .

### Finding Description
`get_block_hashes` in `block_hash.cairo` takes `state_root` (the *new* final root, which is verified via the Patricia commitment) as an argument, but guesses `previous_block_hash` purely via the `GetBlockHashes` hint with no in-circuit tie to the *previous* state root [5](#0-4) . The only in-circuit check performed (`CheckBlockHashConsistency`) is a sanity check that the *newly calculated* hash matches the hint-provided `new_block_hash`, which is exactly what's being computed — it proves nothing about the *previous* block hash's relationship to the previous root [1](#0-0) . This mirrors the LineaRollup bug class: shnarfs/state roots (here: previous block hash / previous state root) are threaded through the finalization/output-construction logic without being cross-validated against each other, so an inconsistent chain could be accepted structurally while still passing the OS's own "does it match itself" check.

Note the code comment explicitly flags this as a known, unresolved TODO rather than something already fixed, unlike the original report's mitigated LineaRollup issue.

### Impact Explanation
If the "consumer of the OS output" (the component that finalizes/commits the block header on L1 or persists it in state-sync/storage) does not perform this cross-check, a chain of block headers with a `prev_block_hash`/`prev_state_root` pair that doesn't correspond to the actual previously committed state could be accepted as valid, since the OS proof itself doesn't constrain this relationship. This could allow wrong committed block hashes/state chains to be finalized (honest-node divergence or acceptance of an incorrect header lineage), similar in class to the original LineaRollup finding.

### Likelihood Explanation
This is gated by whether the actual OS-output consumer (e.g., the batcher/state-sync/L1 commitment path) independently re-derives and checks previous_block_hash/previous_state_root against stored records before trusting the OS-output header. I was not able to conclusively locate and confirm such a downstream check in the reachable sequencer code within the scope of this investigation (only test harnesses like `starknet_os_flow_tests/test_manager.rs` construct these fields directly rather than validating them against stored records). Given the explicit TODO in production Cairo code acknowledging the gap, likelihood depends entirely on unverified downstream code that I could not confirm within the current investigation.

### Recommendation
Add an in-circuit (or immediately-following, cryptographically-tied) assertion within `get_block_os_output_header`/`get_block_hashes` that the guessed `previous_block_hash` is consistent with the previous state root used by the block (e.g., by threading the actual previous root through and checking it against a committed/expected value), removing reliance on an unverified external consumer, consistent with the TODO comment's own suggested remediation.

### Proof of Concept
Not applicable — this is a structural/missing-check finding identified via code and comment inspection (`TODO(Yoni)` in `os_utils.cairo`), not a demonstrated exploit, because verifying exploitability requires confirming the absence of a downstream consumer-side check, which could not be fully confirmed within the available tool-based investigation.

// Checks that the calculated block hash is consistent with the expected block hash (sanity check).
pub(crate) fn check_block_hash_consistency<S: StateReader>(
    hint_processor: &mut SnosHintProcessor<'_, S>,
    ctx: HintContext<'_>,
) -> OsHintResult {
    let os_input = &hint_processor.get_current_execution_helper()?.os_block_input;
    let calculated_block_hash = ctx.get_integer(Ids::BlockHash)?;

    if calculated_block_hash != os_input.new_block_hash.0 {
        return Err(OsHintError::AssertionFailed {
            message: format!(
                "Calculated block hash {calculated_block_hash} does not match expected block hash \
                 {}",
                os_input.new_block_hash.0
            ),
        });
    }

    Ok(())
}
