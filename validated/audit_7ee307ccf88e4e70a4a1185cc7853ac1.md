### Title
Single nil bridge response poisons `MedianTask`, causing DoS of otherwise-healthy price aggregation - (File: core/services/pipeline/task.median.go)

### Summary
`MedianTask.Run` in the Chainlink node's pipeline task runner is designed to tolerate a configurable number of faulty inputs (`AllowedFaults`) before rejecting an OCR/price-feed aggregation. However, when `Lax` and `CountNilsAsFaults` are both left at their default (disabled) settings, a single bridge response that resolves to `nil` (e.g., an external adapter returning HTTP 200 with a `null` value) is *not* filtered out by `FilterErrors()` and is *not* counted as a fault. It survives into the `values` slice passed to `decimalValues.UnmarshalPipelineParam(values)`, which fails hard on the nil element and aborts the entire task — even though enough valid observations were present to compute a correct median.

### Finding Description
The task logic is: [1](#0-0) 

Specifically:
1. If `Lax` is enabled, nils are filtered out before fault counting (excluded entirely, not penalized).
2. `values, faults := valuesAndErrs.FilterErrors()` only removes/counts genuine `error`-typed results — a `nil` `Value` with no `Error` is not an "error" and is not filtered here.
3. If `CountNilsAsFaults` is enabled, nils are filtered out and counted as faults *after* error counting.
4. If neither `Lax` nor `CountNilsAsFaults` is set (the default), nil-valued (non-error) results remain in `values` and flow into `decimalValues.UnmarshalPipelineParam(values)` at line 89, which returns `ErrBadInput` when it cannot unmarshal a nil into a decimal, aborting the whole task regardless of `AllowedFaults`.

This is confirmed by the test case explicitly documenting the behavior: [2](#0-1) 

The analog to the external report is structural: just as `depositEther()` in the Frax code reverted the *entire* batch operation because of one already-used validator entry (rather than skipping/tolerating the bad element), `MedianTask.Run` aborts the *entire* aggregation because of one poisoned/null observation, rather than treating it consistently with other faults under the configured fault-tolerance policy (`AllowedFaults`). In both cases, a fault-tolerant batch operation is rendered fully inoperable by a single anomalous element that the tolerance mechanism was supposed to absorb.

### Impact Explanation
`MedianTask` is a core pipeline task used to aggregate observations from multiple external data sources/bridges for on-chain price reporting (e.g., OCR median jobs). If a single external adapter transiently returns a null/empty value (a routine, non-malicious occurrence — HTTP 200 with `null` body, JSON parse producing a nil field, etc.), the entire median computation for that observation round fails with `ErrBadInput`, discarding otherwise sufficient valid data (e.g., 3 good values in the example). This defeats the purpose of `AllowedFaults`, which node operators configure specifically to tolerate a bounded number of bad/missing inputs without failing the job. Repeated or systematic nils (e.g., from a flaky bridge) can cause missed/delayed observations for that OCR round, potentially affecting round participation/liveness of price reporting, until an operator identifies the misbehaving bridge and manually enables `Lax` or `CountNilsAsFaults`, or fixes the adapter — analogous to needing governance intervention in the referenced bug.

### Likelihood Explanation
This does not require a malicious/privileged actor; it can be triggered by any external adapter/bridge (which is inherently unprivileged relative to the node's trust boundary and commonly a third-party HTTP service) that occasionally returns a null numeric value under normal, non-adversarial conditions (e.g., a data source temporarily lacking a value, a JSON schema returning `null` for a field). Because `Lax`/`CountNilsAsFaults` are both opt-in and default to disabled, most existing median job specs are exposed to this behavior by default unless operators have proactively set these flags.

### Recommendation
Treat nil (non-error) values consistently with the fault-tolerance policy by default: either always filter nils before feeding `decimalValues.UnmarshalPipelineParam`, or always count nils as faults against `AllowedFaults` (as `CountNilsAsFaults` already implements), rather than requiring operators to opt into `Lax` or `CountNilsAsFaults` to avoid a hard failure. At minimum, document this default-disabled gap clearly and consider defaulting `CountNilsAsFaults` (or equivalent nil handling) to true so a single null bridge response cannot unconditionally fail the whole median task when enough valid values exist to satisfy `AllowedFaults`.

### Proof of Concept
Using the existing test harness in `core/services/pipeline/task.median_test.go`, with default settings (`Lax=""`, `CountNilsAsFaults` unset), and `AllowedFaults="3"`:

```go
inputs: []pipeline.Result{
    {},                           // bridge returned HTTP 200 with null value
    {Value: mustDecimal(t, "1")}, // 3 valid bridges — enough for a median
    {Value: mustDecimal(t, "2")},
    {Value: mustDecimal(t, "3")},
},
allowedFaults: "3",
lax: "",
want: pipeline.Result{Error: pipeline.ErrBadInput}, // nil poisons the entire batch
``` [2](#0-1) 

Even though only 1 of 4 inputs is faulty and up to 3 faults are allowed, the task returns `ErrBadInput` instead of computing the median of the 3 valid values, because the nil value bypasses `FilterErrors()` at [3](#0-2)  and reaches the hard-failing unmarshal at [4](#0-3) .
