### Title
`ensure_match_transaction_info` silently skips checkpoint-hash validation, letting replay-verify tooling accept a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
The bug-class analog to the oracle report is: a function whose entire purpose is to validate that produced data matches an authenticated reference value, but which omits validating some of the security-critical fields. In Aptos, `TransactionOutput::ensure_match_transaction_info` is the function relied upon by replay/verify tooling to confirm that a freshly-executed `TransactionOutput` matches the authenticated `TransactionInfo` (which is itself accumulator-proven against a signed `LedgerInfo`). It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that represent the authenticated Merkle root of the post-commit state.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . It validates transaction status, gas used, write-set hash, and event root hash against the supplied `TransactionInfo`, but the trailing comment makes the gap explicit: [2](#0-1) 

This means the function never compares the locally-computed state checkpoint hash (which is derived from the Jellyfish Merkle / hot-state root after applying the write set, see `assemble_transaction_infos` at [3](#0-2) , which folds `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` into the `TransactionInfo` that is hashed and accumulated) against the checkpoint hash actually recorded in the authenticated `TransactionInfo` being verified against.

This comparator is the sole state-divergence gate in two integrity-relevant call sites:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, used for chunk replay verification against authenticated `transaction_infos` fetched from the ledger: [4](#0-3) 
- `aptos-debugger`'s `print_mismatches`, used to diff locally re-executed outputs against expected `TransactionInfo`s pulled from a real network/DB via `AptosValidatorInterface`: [5](#0-4) 

Because neither call site independently re-derives and compares the state/hot-state/position checkpoint hashes elsewhere, a locally computed state root that diverges from the authenticated on-chain state root (e.g., due to a state-computation bug, JMT/hot-state corruption, or a malicious/faulty state provider) will not be flagged as a mismatch by these tools as long as status, gas, write-set hash, and events still match.

### Impact Explanation
This breaks the "committed data must survive replay/verification unchanged" invariant called out in the state-integrity gate: replay-verify is Aptos's designated mechanism for catching hard-fork-only state divergence bugs before they reach mainnet consensus. If the state root diverges (the exact class of bug replay-verify exists to catch) but write-set/event/gas/status remain equal, `db-tool replay-verify` and `aptos-debugger` compare-execution paths will both report success, masking a real ledger-state divergence. This is a proof-integrity failure: an authenticated checkpoint-hash field is not bound/checked during verification, defeating the intended detection of exactly the kind of consensus-breaking bug this tooling protects against.

### Likelihood Explanation
The comment in the code is a first-party acknowledgment ("TODO(trading-native): ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution") that this gap exists today and is a known, reachable condition, not a hypothetical. It requires no privileged access — any state-computation bug (including from the referenced "trading-native"/position feature) that changes checkpoint hashes without changing the write set/events would be silently missed by standard replay-verify runs.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`-derived (or caller-supplied) `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields on `txn_info`, and fail loudly on mismatch, mirroring how `write_set_hash` and `event_root_hash` are already checked. Callers (`chunk_executor::verify_execution`, `aptos-debugger::print_mismatches`) should supply the locally computed checkpoint hashes so the comparison is meaningful.

### Proof of Concept
Not applicable as a runnable exploit (this is a verification-omission bug, not an exploitable transaction). Conceptual trigger:
1. Run `db-tool replay-verify` (or `aptos-debugger` transaction-output comparison) against a chunk where local re-execution produces a correct write set/events/status/gas but a divergent state checkpoint root (e.g., due to a bug in state summary/hot-state computation).
2. `verify_execution` calls `ensure_match_transaction_info`, which never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
3. The tool reports the chunk as verified/matching even though the authenticated ledger state root and the locally computed root disagree.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        txn_outputs: &[TransactionOutput],
        expected_txn_infos: &[TransactionInfo],
        first_version: Version,
    ) {
        for idx in 0..txn_outputs.len() {
            let txn_output = &txn_outputs[idx];
            let txn_info = &expected_txn_infos[idx];
            let version = first_version + idx as Version;
            txn_output
                .ensure_match_transaction_info(version, txn_info, None, None)
                .unwrap_or_else(|err| println!("{}", err))
        }
