### Title
Missing slippage protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` allows sandwich-style value extraction from bancor-style TRX/TRC10 exchange pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's legacy on-chain exchange (bancor-style AMM for TRX/TRC10 pairs) exposes three actuators: `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator`. Only `ExchangeTransactionActuator` (the trade/swap path) enforces a caller-supplied minimum-output check via the `expected` field. `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-asset amount (`anotherTokenQuant`) purely from the pool's current on-chain ratio at execution time, with no minimum/maximum bound supplied by the caller, mirroring the "no slippage parameter" bug class from the external report.

### Finding Description
`ExchangeTransactionContract` carries an `expected` field that is enforced in `ExchangeTransactionActuator`'s `doValidate()`: [1](#0-0) 

In contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` have no such field at the protobuf level: [2](#0-1) 

`ExchangeInjectActuator::execute` computes `anotherTokenQuant` directly from the live pool ratio (`secondTokenBalance * tokenQuant / firstTokenBalance` or the symmetric case) and immediately debits/credits both sides — there is no lower/upper bound check on `anotherTokenQuant`: [3](#0-2) 

Its `doValidate()` similarly never checks a caller-supplied expected value for `anotherTokenQuant`: [4](#0-3) 

`ExchangeWithdrawActuator` has the identical pattern — `anotherTokenQuant` is derived from `bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` (or its symmetric case) with no floor enforced by the caller: [5](#0-4) [6](#0-5) 

Because the pool ratio can be moved arbitrarily within the same block window by any account calling `ExchangeTransactionContract` against the same `exchange_id` (this is a normal, unprivileged, public operation, and pricing follows the same bonded-curve `ExchangeCapsule::transaction`/`ExchangeProcessor` logic used for swaps: [7](#0-6) ), an attacker (or a block-producing witness ordering transactions in the block they produce) can move the ratio immediately before an inject/withdraw transaction executes and move it back immediately after, extracting value from the party performing the inject/withdraw — exactly the "no slippage parameter" pattern described in the external report, just applied to the liquidity-management operations instead of a swap.

### Impact Explanation
The exchange creator issuing `ExchangeInject`/`ExchangeWithdraw` receives a counter-asset amount computed at execution time with no minimum-received guarantee. A manipulated pool ratio at the moment of execution directly changes the TRX/TRC10 accounting recorded on both the `AccountCapsule` balances and the `ExchangeCapsule` reserves — this is concrete state/accounting impact, not theoretical, since balances are mutated unconditionally once `doValidate()` passes (which does not check the ratio-derived output against any expectation). Depending on execution order (attacker front/back-running within the block, or an SR reordering transactions inside a block it produces), the creator can lose value proportional to how far the pool is moved, with no on-chain mechanism to cap the loss for these two contract types.

### Likelihood Explanation
Exploitation requires: (1) an existing exchange pool with tradable liquidity (`ExchangeCreateContract` is open to any account), and (2) transaction ordering control or timing within the same block/short window, achievable either by a searcher submitting sandwich transactions or by the block-producing witness ordering transactions within its own produced block. Both `ExchangeTransactionContract` (to move the ratio) and `ExchangeInjectContract`/`ExchangeWithdrawContract` are unprivileged, publicly callable contract types with no cooldown or oracle-based price check, making this practically reachable whenever the pool has non-trivial liquidity and low fees relative to the manipulation profit.

### Recommendation
Add an `expected`/minimum (and/or maximum) `anotherTokenQuant` bound to `ExchangeInjectContract` and `ExchangeWithdrawContract` protobuf messages, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `doValidate()` exactly as `ExchangeTransactionActuator` already does for `expected`, rejecting the transaction if the computed counter-asset amount falls outside the caller's tolerance.

### Proof of Concept
1. Attacker (or the SR producing the current block) observes a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` from the exchange creator for `exchange_id = X`.
2. Attacker submits an `ExchangeTransactionContract` against the same `exchange_id` immediately before it, shifting `firstTokenBalance`/`secondTokenBalance` sharply in one direction (or the SR simply places its own transaction earlier in the block it produces).
3. The creator's inject/withdraw executes against the manipulated ratio in `ExchangeInjectActuator::execute` / `ExchangeWithdrawActuator::execute`, computing `anotherTokenQuant` from the skewed reserves with no floor check, mutating `AccountCapsule` balances and `ExchangeCapsule` reserves accordingly.
4. Attacker submits a second `ExchangeTransactionContract` reversing the ratio, realizing the value taken from the creator's inject/withdraw, all within the same block or a narrow window, with no on-chain slippage guard blocking any step.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
