### Title
Hardened resource-limit calculation can throw uncaught `ArithmeticException` on overflow, blocking energy/bandwidth accounting for the transaction - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
The reported bug class is: a signed accounting value that can legitimately become out-of-range for its target unsigned/limited representation is converted via a strict, exception-throwing conversion instead of being clamped or handled gracefully, so a single "credit/limit" computation reverts and takes down every downstream operation that depends on it (withdraw/redeem in the report). In java-tron, the `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`/`calculateGlobalNetLimitV2`/`calculateGlobalEnergyLimitV2` family (in `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java` and `BandwidthProcessor.java`, mirrored in `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`) exhibits the analogous pattern when `allowHardenResourceCalculation` (hardened math mode) is enabled: the limit is computed with `BigInteger` arithmetic and finalized with `.longValueExact()`, which throws `ArithmeticException` if the mathematically correct result does not fit into a `long`.

### Finding Description
`calculateGlobalEnergyLimit` computes an account's energy limit from `frozeBalance`, `totalEnergyLimit`, and `totalEnergyWeight`: [1](#0-0) 

```java
protected long calculateGlobalLimitV1(long frozeBalance,
    long totalLimit, long totalWeight) {
  long weight = frozeBalance / TRX_PRECISION;
  return BigInteger.valueOf(weight)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(totalWeight))
      .longValueExact();
}
```

and the V2 variant: [2](#0-1) 

Both `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` and `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` route into these helpers when `hardenCalculation()` (`VMConfig.allowHardenResourceCalculation()`) is on: [3](#0-2) 

This "hardened" replacement is explicitly demonstrated in test code to throw `ArithmeticException` on overflow, rather than silently wrapping like the legacy `double`-based path: [4](#0-3) [5](#0-4) 

The same pattern is duplicated in the VM-side `RepositoryImpl.calculateGlobalEnergyLimit`, used by TVM execution to gate energy consumption for contract calls: [6](#0-5) 

These limit-calculation functions are on the critical path for consuming energy/bandwidth for *every* transaction and TVM call (`EnergyProcessor.useEnergy`, `BandwidthProcessor.useAccountNet`), exactly analogous to `getVaultCreditCapacity` being on the critical path for `redeem()`/withdrawals in the reported bug: [7](#0-6) [8](#0-7) 

Unlike the reported vault bug (negative value causing revert), here the trigger is a very large positive intermediate/result (frozen balance × totalLimit) that legitimately overflows `long`, and the "fix" (hardened BigInteger math with `longValueExact()`) throws instead of clamping or falling back — turning a value that should be computable into an uncaught runtime exception. This is the same root-cause shape as the report: a value outside the target type's safely-representable range is converted with a throwing, all-or-nothing conversion function instead of a saturating/graceful one, and that conversion sits directly on the hot path of a core accounting operation (resource-limit/credit check) that every user-facing resource-consuming action depends on.

### Impact Explanation
If `allowHardenResourceCalculation` is enabled network-wide (it is a chain parameter, gated by `VMConfig`/`DynamicPropertiesStore`, and is exercised extensively by dedicated overflow tests suggesting it is an active/enabled feature path) and any account accumulates a combination of `frozenBalance`/`totalNetLimit`/`totalNetWeight` (or the energy equivalents) such that `weight * totalLimit` exceeds `Long.MAX_VALUE` before the division reduces it back into range, `longValueExact()` throws `ArithmeticException`. Because this call happens inside `useEnergy`/`useAccountNet`, which are invoked for ordinary account bandwidth/energy consumption and for TVM contract execution's energy accounting, an uncaught `ArithmeticException` here would abort transaction processing for that account/resource path — a deterministic, network-wide DoS on that account's ability to transact (analogous to the reported "complete vault lockout"), and potentially a chain processing halt if unhandled at a higher level (this repo excerpt does not show a catch clause wrapping these specific calls at the block-processing layer, so whether this becomes a per-transaction failure vs. a node halt could not be fully confirmed from the available context).

### Likelihood Explanation
The overflow requires extremely large `totalLimit`/`weight` products (test cases use values near `Long.MAX_VALUE / 2` to `Long.MAX_VALUE / 4`), which are far outside realistic TRX-denominated resource parameters under normal network conditions. Reaching this in production would require either an extreme, likely-unrealistic combination of `totalNetLimit`/`totalEnergyCurrentLimit` and low `totalNetWeight`/`totalEnergyWeight` (e.g., total weight collapsing toward very small values while limits remain large), or a governance-set parameter change producing such a ratio. This is a plausible-but-low-likelihood edge case rather than a trivially triggerable one, unlike the reported vault bug where becoming "underwater" is a normal, expected state reachable through ordinary market movement.

### Recommendation
1. In `calculateGlobalLimitV1`/`calculateGlobalLimitV2` (and the VM-side duplicate in `RepositoryImpl`), replace the throwing `.longValueExact()` with a saturating conversion (clamp to `Long.MAX_VALUE`/`0` as appropriate) or explicitly catch `ArithmeticException` at the call sites (`useEnergy`, `useAccountNet`, `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` callers) and fail closed to a safe default (e.g., `0` limit, forcing the legacy non-hardened computation, or rejecting only the offending transaction) rather than allowing an unchecked exception to propagate.
2. Add bounds validation on `totalNetLimit`/`totalEnergyCurrentLimit`/`totalNetWeight`/`totalEnergyWeight` writes (in `DynamicPropertiesStore`) to prevent parameter combinations that make overflow reachable.
3. Add regression tests asserting that hardened-mode overflow is handled gracefully (no unchecked exception reaches transaction/block processing) rather than only asserting that `ArithmeticException` is thrown, since the current tests document the throw as expected behavior rather than treating it as a bug to fix.

### Proof of Concept
Existing repository tests already demonstrate the throwing behavior, confirming the mechanism (not a hypothetical): [4](#0-3) 

```java
@Test
public void testGlobalEnergyLimitOverflowDetectedWithHardening() {
  dbManager.getDynamicPropertiesStore().saveTotalEnergyCurrentLimit(Long.MAX_VALUE / 2);
  dbManager.getDynamicPropertiesStore().saveTotalEnergyWeight(1L);
  ownerCapsule.setFrozenForEnergy(Long.MAX_VALUE / 4, 0L);
  dbManager.getAccountStore().put(ownerCapsule.getAddress().toByteArray(), ownerCapsule);

  dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(1);

  Assert.assertThrows(ArithmeticException.class,
      () -> energyProcessor.calculateGlobalEnergyLimit(ownerCapsule));
}
```

and the bandwidth equivalent: [5](#0-4) 

This confirms that when hardened resource calculation is active, an account whose frozen-balance/weight/limit ratio produces an out-of-`long`-range intermediate causes `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` to throw `ArithmeticException` instead of returning a usable (even if imprecise) value — the same "negative-to-unsigned/overflow conversion reverts and blocks the operation" root cause described in the external report, applied here to energy/bandwidth accounting instead of vault credit capacity.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimitV2(long frozeBalance) {

    }
    double energyWeight = (double) frozeBalance / TRX_PRECISION;

  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
