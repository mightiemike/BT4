### Title
`ensure_match_transaction_info()` skips checkpoint-hash validation, letting corrupted state/hot-state/position-state roots pass replay and chunk-apply verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the shared invariant check used to confirm that a locally-computed `TransactionOutput` (from re-execution) matches an authenticated `TransactionInfo` (status, gas, write-set hash, event root). It is invoked both by `execution/executor/src/chunk_executor/mod.rs` (transaction/output-chunk apply and replay paths, used in normal state sync / fast sync) and by `storage/db-tool/src/replay_on_archive.rs` (replay-verify tooling). The function, however, deliberately does not compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` between the locally computed value and the authenticated `TransactionInfo`, a gap the code itself documents but does not fix.

### Finding Description
`ensure_match_transaction_info()` validates transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against the trusted `TransactionInfo`, but the function returns `Ok(())` without ever checking the state-checkpoint-related hash fields carried in `TransactionInfo` V1 (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`): [1](#0-0) 

The code itself documents this as an unresolved gap: [2](#0-1) 

This matters because `TransactionInfo` V1's `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are exactly the fields that bind a transaction's authenticated info to the JMT/SMT state root computed by `DoStateCheckpoint` and folded into `TransactionInfo` in `DoLedgerUpdate::assemble_transaction_infos`, which then feeds the transaction accumulator root used for consensus signing and later Merkle-proof verification: [3](#0-2) 

`ensure_match_transaction_info` is the only cross-check that ties a *locally re-executed* `TransactionOutput` back to that authenticated `TransactionInfo` in two live code paths:
- `execution/executor/src/chunk_executor/mod.rs`, used during state-sync/fast-sync chunk application and transaction replay.
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, used for archive replay verification. [4](#0-3) 

Because the checkpoint hashes are excluded from this comparison, a node that (due to a bug, storage corruption, or divergent execution logic in the state-checkpoint computation) computes a wrong `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` will still pass `ensure_match_transaction_info()` as long as status/gas/write-set-hash/event-root match. The transaction is then treated as verified and committed via the chunk executor path, with the wrong checkpoint hash embedded in the locally stored `TransactionInfo`/ledger data, even though the accumulator root (built from `TransactionInfo::hash()`, which does include these fields) would differ from the network-agreed root under `TransactionInfo::builder_v1()`: [5](#0-4) 

### Impact Explanation
If a divergence in state-checkpoint-hash computation exists elsewhere (e.g., the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / hot-state / position-state root logic referenced in the TODO), this verification gap removes the safety net that would otherwise catch it during chunk-based execution/replay and archive replay-verify tooling, allowing a node to silently persist an incorrect state/hot-state/position-state root while reporting successful verification. This is a state-commitment integrity gap: authenticated per-transaction proof material (`TransactionInfo`) could diverge from the actually-committed state root without detection by this check, undermining the guarantee that `ensure_match_transaction_info` exists to provide, and it can mask a genuine ledger-divergence bug from operators relying on replay-verify or chunk executor checks. The realistic exploitation of this gap depends on a co-occurring bug that produces incorrect checkpoint hashes; on its own, this is a missing-defense-in-depth issue rather than a directly exploitable state-corruption primitive today, since the underlying checkpoint hash computation feeds into the accumulator root elsewhere and would still need to independently diverge from the network to cause any consensus-level ledger split.

### Likelihood Explanation
Low-to-Medium: the gap is only actionable when combined with a separate bug in checkpoint-hash computation (e.g., under the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature, or hot-state/position-state root logic), and the code's own TODO comment confirms this is a known, currently gated concern rather than actively triggerable in the default configuration. It is not a directly attacker-triggerable primitive by itself.

### Recommendation
Extend `ensure_match_transaction_info()` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on both sides) before returning `Ok(())`, so that chunk executor and replay-verify tooling actually catch divergence in the authenticated position/hot-state root, as the existing TODO comment recommends doing before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Proof of Concept
Not independently exploitable without a second bug producing an incorrect checkpoint hash; the code path demonstrating the gap is:
1. `DoLedgerUpdate::assemble_transaction_infos` builds `TransactionInfo` V1 including `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` [5](#0-4) .
2. A locally re-executed `TransactionOutput` with a wrong checkpoint hash is checked via `ensure_match_transaction_info`, which never inspects these fields and returns `Ok(())` [6](#0-5) .
3. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` (or the chunk executor's equivalent call) treats the divergent replay as verified [7](#0-6) .

Note: I could not fully trace the chunk_executor's exact call site/context for `ensure_match_transaction_info` within the available iterations (only the imports were retrieved), so I cannot confirm with certainty whether that path runs in the default consensus-critical commit flow versus only in verify/replay chunk modes. This should be verified with a full read of `execution/executor/src/chunk_executor/mod.rs` before treating this as conclusively mainnet-committing.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
