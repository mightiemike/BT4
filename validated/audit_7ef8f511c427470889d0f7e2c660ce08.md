Confirmed vulnerability. In `extractDestGasAmountFromMap` (core/capabilities/ccip/ccipsolana/executecodec.go, lines 220-242), the `int64` branch checks only `v > math.MaxUint32` but never checks `v < 0`, so `uint32(v)` on a negative `int64` wraps around to an unintended large uint32 value via two's-complement truncation.

### Title
Missing negative-value check in `extractDestGasAmountFromMap` allows int64→uint32 sign-wrap corruption of `DestGasAmount` - ([File: core/capabilities/ccip/ccipsolana/executecodec.go])

### Summary
`extractDestGasAmountFromMap` validates the upper bound (`v > math.MaxUint32`) for the LOOP-converted `int64` `destgasamount` field but omits a lower-bound (`v < 0`) check before casting to `uint32`, unlike its sibling function `parseExtraDataMap`'s `computeunits`/`accountiswritablebitmap` handling in `core/capabilities/ccip/ccipsolana/msghasher.go` which explicitly checks `v < 0`. A negative `int64` will silently wrap into a large, attacker-influenced `uint32` value that is folded into `ccip_offramp.Any2SVMTokenTransfer.DestGasAmount`, corrupting both the OCR message hash (`msghasher.go`) and the execute report encoding (`executecodec.go`).

### Finding Description
`extractDestGasAmountFromMap` (core/capabilities/ccip/ccipsolana/executecodec.go:220-242) is called from both `MessageHasherV1.Hash` (core/capabilities/ccip/ccipsolana/msghasher.go:64) and `ExecutePluginCodecV1.Encode` (core/capabilities/ccip/ccipsolana/executecodec.go:75), using the map produced by `ExtraDataCodec.DecodeTokenAmountDestExecData` from an untrusted, attacker-supplied `RampTokenAmount.DestExecData` field originating from the source-chain message. The comment at msghasher.go:114-117 explicitly documents that when the source chain's `ExtraDataCodec` runs inside a LOOP plugin, gRPC protobuf serialization converts `uint32` values to `int64`. In that code path:

```go
case int64: // LOOP converts expected uint32 to int64
    if v > math.MaxUint32 {
        return 0, fmt.Errorf("destGasAmount exceeds uint32 max, got %d", v)
    }
    return uint32(v), nil //nolint:gosec // G115: validated to be within uint32 max above
```

only the upper bound is checked. A negative `int64` (e.g., `-1`) passes this check and `uint32(v)` performs a two's-complement truncation, yielding `0xFFFFFFFF` instead of being rejected. This corrupted value is then used verbatim as `DestGasAmount` in `ccip_offramp.Any2SVMTokenTransfer` (msghasher.go:76, executecodec.go:85), which is hashed via `ccip.HashAnyToSVMMessage` and also serialized into the execute plugin report. This contradicts the sibling validation pattern in the same package (`msghasher.go:126,138`) which correctly checks `v < 0` for other LOOP-converted fields, confirming the omission here is an inconsistency/bug rather than intentional design.

### Impact Explanation
Since `DestGasAmount` directly feeds the consensus-critical message hash computed by every oracle node independently from the same source-chain data, a negative value being silently wrapped is deterministic and reproducible by all honest nodes — it does not by itself cause a hash *mismatch* between honest nodes (they'd all compute the same wrapped value). However, it does mean the on-chain `DestGasAmount` used for execution gas budgeting on Solana can be corrupted to an attacker-chosen large value (`0xFFFFFFFF`) purely by crafting a negative encoded gas amount on the source chain, which is a data-integrity/parsing correctness bug that could affect gas estimation (`gas_helpers.go`) and execution behavior, but does not on its own grant unauthorized fund transfer or bypass an authorization check.

### Likelihood Explanation
This is only reachable when the source chain's `ExtraDataCodec` operates via a LOOP plugin that performs gRPC protobuf `int64` conversion of a `uint32` field (documented as occurring for chains like TON), and requires the attacker to control the source-chain-encoded `DestExecData` gas value to be negative — feasible for an unprivileged message sender constructing a CCIP message with a maliciously encoded `DestExecData`.

### Recommendation
Add a lower-bound check `if v < 0 { return 0, fmt.Errorf(...) }` alongside the existing `v > math.MaxUint32` check in `extractDestGasAmountFromMap`, mirroring the pattern already used in `parseExtraDataMap` for `computeunits` and `accountiswritablebitmap`.

### Proof of Concept
Add a fuzz/unit test in `core/capabilities/ccip/ccipsolana/executecodec_test.go` calling `extractDestGasAmountFromMap(map[string]any{"destgasamount": int64(-1)})` and asserting it returns an error rather than `uint32(0xFFFFFFFF), nil`; extend with table cases for `math.MaxUint32`, `math.MaxUint32+1`, and `0` to confirm correct boundary behavior. func extractDestGasAmountFromMap(input map[string]any) (uint32, error) {
	// Search for the gas fields
	for fieldName, fieldValue := range input {
		lowercase := strings.ToLower(fieldName)
		switch lowercase {
		case "destgasamount":
			switch v := fieldValue.(type) {
			case uint32:
				return v, nil
			case int64: // LOOP converts expected uint32 to int64
				if v > math.MaxUint32 {
					return 0, fmt.Errorf("destGasAmount exceeds uint32 max, got %d", v)
				}
				return uint32(v), nil //nolint:gosec // G115: validated to be within uint32 max above
			default:
				return 0, errors.New("invalid type for destgasamount, expected uint32 or int64")
			}
		default:
		}
	}

	return 0, errors.New("invalid token message, dest gas amount not found in the DestExecDataDecoded map")
}
