Based on my analysis, I found a real, exploitable gap between the JWT replay cache's TTL and JWT validity duration.

### Title
JWT replay protection window can be shorter than JWT validity window, allowing replay of a still-unexpired signed JWT after cache eviction - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The `jwtReplayCache` in `WorkflowMetadataHandler.Authorize` [1](#0-0)  evicts recorded `jti` entries after a fixed `cleanupPeriod` derived from `cfg.JWTReplayPeriodMs`, independent of the JWT's own `exp` claim, which can be configured for up to `maxJWTExpiryDuration` (5 minutes) [2](#0-1) . If the configured replay-cache cleanup period is shorter than the JWT's actual `exp - iat` lifetime, a previously-used but still cryptographically-valid (unexpired) JWT can be evicted from the replay cache and successfully replayed for a second unauthorized workflow execution.

### Finding Description
`Authorize` checks `h.jwtCache.isReplay(claims.ID)` before authorizing, and calls `h.jwtCache.recordUsage(claims.ID)` only after successful authorization [3](#0-2) . The cache is periodically swept by a ticker running every `cleanupPeriod` (`= JWTReplayPeriodMs`), which deletes any `jti` whose `recordUsage` timestamp is older than `now - cleanupPeriod` [4](#0-3) [5](#0-4) .

Crucially, `isReplay`/`recordUsage`/`cleanupOldEntries` are only in-memory, TTL-bounded structures decoupled entirely from JWT's own expiration handling. `VerifyRequestJWT` (via `jwt.ParseWithClaims`, golang-jwt/v5) independently enforces `exp` as part of standard claims validation [6](#0-5) , and also enforces a maximum lifetime bound of `maxJWTExpiryDuration` (5 minutes) unless a caller supplies `WithMaxExpiryDuration` [7](#0-6) . Nothing in `Authorize` or the cache correlates cache TTL to the token's `exp` claim.

If `cfg.JWTReplayPeriodMs` (the gateway's replay-cache cleanup interval) is configured to a value smaller than the JWT's actual lifetime (up to 5 minutes), the following sequence is possible entirely from an unprivileged, previously-authorized caller (someone who already legitimately obtained one valid signed JWT for a workflow, e.g., a normal user of the workflow trigger):
1. Attacker sends request #1 with JWT `jti=X`, `exp` = now+5min. `isReplay` returns false, `Authorize` succeeds, `recordUsage(X)` records it.
2. `jwtCache` cleanup ticker fires after `JWTReplayPeriodMs` (e.g., configured to 30s, well under the 5-minute JWT max lifetime) and evicts `X` because `createdAt` is now `> cleanupPeriod` old.
3. Attacker replays the exact same JWT (still cryptographically valid because `exp` has not passed) at, say, t=45s. `VerifyRequestJWT` succeeds (still within exp), `isReplay(X)` returns false (evicted from cache), and `Authorize` grants execution again — a second unauthorized workflow execution with the same signed token.

This directly matches the scoped invariant: replay protection must last for the JWT's full validity lifetime, not just the internal cache TTL. No existing check (rate limiting, request-ID dedup in `httpTriggerHandler.setupCallback`, etc.) prevents this because those checks operate on `requestID`, not `jti`, and are unrelated to JWT replay semantics [8](#0-7) .

### Impact Explanation
An attacker who has legitimately used one JWT can replay it to re-trigger the same workflow execution a second (or more) times within the JWT's `exp` window, once the cache TTL has cycled — this is unauthorized re-execution of a workflow using a stale-but-still-valid signed token, bypassing the intended one-time-use guarantee of the `jti` replay defense. This matches "unauthorized transaction or workflow execution" impact class scoped in the prompt. The severity is bounded by whatever a single duplicate workflow invocation can cause (e.g., duplicate on-chain writes, double payment triggers, resource exhaustion via repeated invocation), scaled by how many jti-eviction cycles occur within the JWT's `exp` window.

### Likelihood Explanation
Exploitability depends entirely on the deployed value of `JWTReplayPeriodMs` relative to JWTs' actual `exp-iat` duration (up to 5 minutes, enforced in `VerifyRequestJWT`/`maxJWTExpiryDuration`). I could not confirm the operator-configured default of `JWTReplayPeriodMs` from the indexed files (only its usage in `http_handler.go` was found in five other locations that were not fully retrievable within tool limits) — if the default/documented value is deliberately set to be `>= maxJWTExpiryDuration`, the described gap does not exist in practice, and this becomes a config hygiene issue rather than a code-level bypass. But nothing in the code enforces or asserts `JWTReplayPeriodMs >= JWT max lifetime`, so any deployment (or future config change) with a shorter cleanup period is exploitable by any client that has obtained one valid JWT, with 100% repeatability once the timing condition is met.

### Recommendation
Enforce an invariant in code (not just deployment convention) that `jwtReplayCache.cleanupPeriod` (derived from `JWTReplayPeriodMs`) is always `>= maxJWTExpiryDuration` (or dynamically `>=` each request's actual `exp - iat`), e.g. by validating this relationship at `NewWorkflowMetadataHandler` construction time and refusing to start with an invalid config, or by keying cache eviction directly off each JWT's own `exp` claim (store `exp` alongside `jti` and only evict once `now > exp`) rather than off a fixed sliding cleanup window unrelated to token validity.

### Proof of Concept
Unit test in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go` (or equivalent):
1. Construct a `WorkflowMetadataHandler` with `cfg.JWTReplayPeriodMs` set to a small value (e.g., 50ms).
2. Create a signed JWT via `utils.CreateRequestJWT` with `exp` set well beyond the cache cleanup period (e.g., `WithExpiry(500*time.Millisecond)`), for an authorized signer/workflow.
3. Call `Authorize(workflowID, token, req)` — assert success and that `jwtCache.isReplay(jti)` is true immediately after.
4. Manually invoke `jwtCache.cleanupOldEntries(time.Now())` (or sleep past `cleanupPeriod` and let the ticker fire) to simulate eviction.
5. Call `Authorize(workflowID, token, req)` again with the *same* token (still within its `exp`) — expected (buggy) result: success (replay allowed); expected (fixed) result: rejection with "JWT token has already been used" regardless of cache-eviction timing, as long as `time.Now() < claims.ExpiresAt`.

// cleanupOldEntries removes expired entries from the cache
func (cache *jwtReplayCache) cleanupOldEntries(cutoff time.Time) int {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	var expiredCount int
	for jti, createdAt := range cache.cache {
		if createdAt.Before(cutoff) {
			delete(cache.cache, jti)
			expiredCount++
		}
	}
	return expiredCount
}
