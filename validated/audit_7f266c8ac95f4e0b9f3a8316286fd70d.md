I found a confirmed, developer-acknowledged issue that maps closely to the CVE's bug class: a **size-limit-check-then-later-uncontrolled-growth** flaw, analogous to the GPAC "unchecked addition after a bounds decision leads to memory corruption" pattern.

### Title
Receipt size validated before `output_data_receivers` is appended, allowing state-witness oversized receipts to bypass the protocol size limit - (File: `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` enforces `max_receipt_size` on a newly created receipt [1](#0-0) . This check runs immediately after `apply_action` returns, before the runtime later mutates that same receipt by appending `output_data_receivers` in `apply_action_receipt` [2](#0-1) . Because the size check happens first and the mutation happens afterward with no re-check, a contract can craft a promise/`promise_return` DAG whose receipt is exactly at `max_receipt_size` at validation time, then have `output_data_receivers` appended, producing a receipt that exceeds `max_receipt_size` and is nonetheless persisted/forwarded.

### Finding Description
The `ValidateReceiptMode::ExistingReceipt` variant even carries a code comment acknowledging this is a known, unresolved bug: "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed. See https://github.com/near/nearcore/issues/12606" [3](#0-2) . The corresponding integration tests explicitly reproduce this as a live, currently-unfixed bug rather than a hypothetical: `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` construct a receipt sized to exactly `max_receipt_size`, trigger the `output_data_receivers` append path, and confirm an oversized receipt is produced instead of being rejected [4](#0-3) .

This is directly analogous to the CVE's bug class: a size/bounds decision is made once (checked addition/validation), then subsequent unchecked growth of the same buffer/structure invalidates that earlier bound, and downstream code (serialization into `ChunkStateWitness`, cross-shard receipt forwarding, congestion/bandwidth accounting sized against `max_receipt_size`) all assume the invariant still holds.

### Impact Explanation
`max_receipt_size` is a foundational invariant used to bound `ChunkStateWitness` size (state-witness limits, `docs/misc/state_witness_size_limits.md`), congestion-control receipt-size accounting, and bandwidth-scheduler grants (`BandwidthSchedulerParams::calculate` asserts `max_single_grant >= max_receipt_size`) [5](#0-4) . An oversized receipt slipping past `NewReceipt` validation can inflate the actual `ChunkStateWitness` beyond its designed ~21 MiB budget, and can be sized larger than `max_single_grant`, which the bandwidth scheduler explicitly assumes is impossible ("it'll be impossible to send a max size receipt" otherwise). This is a resource/liveness-class issue reachable from a single unprivileged contract call, not a direct fund-theft primitive — the runtime is documented to already "handle them gracefully" once such receipts exist (i.e., there is defensive code downstream), which weakens (but does not eliminate) severity.

### Likelihood Explanation
High likelihood of reachability: this is triggered purely by an unprivileged contract call chain (`promise_create` → `promise_then` → `promise_return`), no special privileges needed, and is already demonstrated end-to-end by the repository's own tests as reproducible today.

### Recommendation
Re-validate (or re-check just the size delta) of a receipt after any post-creation mutation such as the `output_data_receivers` append in `apply_action_receipt`, rather than relying solely on the pre-mutation `validate_receipt(..., NewReceipt)` call. Alternatively, account for the maximum possible `output_data_receivers` payload size at the point of the original size check so the bound is conservative and cannot be invalidated by later appends.

### Proof of Concept
Use the repository's own reproduction, `test_max_receipt_size_promise_return` (`test-loop-tests/src/tests/max_receipt_size.rs:130-208`): deploy the test contract, call `max_receipt_size_promise_return_method1`, which creates promise `A` that (on execution) creates promise `C` sized to exactly `max_receipt_size` and issues `promise_return(C)`; the runtime later appends the caller's `output_data_receivers` onto `C`'s receipt, pushing it above `max_receipt_size` without a re-check, as confirmed by `assert_oversized_receipt_occurred` at the end of the test. /// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

// A function call will generate a new receipt. Size of this receipt will be equal to
// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
// Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`.
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
