### Title
Unbounded recursive hashing of attacker-controlled bytecode segment tree causes sequencer stack overflow - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
CVE-2021-3500 is a stack overflow in `djvulibre` caused by unbounded recursion while parsing an attacker-crafted, deeply-nested document structure. The Starknet sequencer has an analogous unbounded-recursion pattern: the CASM `bytecode_segment_lengths` field (a `NestedIntList`) that accompanies every Sierra→CASM compiled class is walked with plain, non-tail recursive functions that have no depth limit, and this structure's nesting is derived from the shape of a declarer-supplied Sierra program.

### Finding Description
When a class is declared, the Sierra program is compiled to CASM and the resulting `CasmContractClass` carries a `bytecode_segment_lengths: NestedIntList` field describing how the bytecode is split into (possibly nested) segments. Two independent, unbounded recursive functions consume this structure directly from the compiled artifact:

- `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` (lines 111-132) recurses once per `NestedIntList::Node` level with no depth check: [1](#0-0) 
- `create_bytecode_segment_structure_inner` in `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs` (lines 277-307) performs the identical unbounded recursion while the Starknet OS builds its bytecode segment tree during (re-)execution and hashing of every declared class: [2](#0-1) 

Both functions are reached from a single, unprivileged declare transaction:
- `SierraCompiler::compile` in `crates/apollo_compile_to_casm/src/lib.rs` (lines 60-74) compiles the class in a resource-limited subprocess, but then calls `executable_class.hash(&HashVersion::V2)` **after** the subprocess returns, in the unsandboxed compiler-service process: [3](#0-2) 
- `DeclareTransaction::check_compile_class_hash_v2_declaration` (`crates/starknet_api/src/executable_transaction.rs`, lines 228-244) invokes `casm.hash(&HashVersion::V2)` directly in the blockifier/gateway process during declare-transaction processing: [4](#0-3) 
- Every full node re-executing the block via the Starknet OS calls `create_bytecode_segment_structure` for every compiled class it processes, in `load_classes_and_create_bytecode_segment_structures` (`crates/starknet_os/src/hints/hint_implementation/compiled_class/implementation.rs`, lines 211-217): [5](#0-4) 

Unlike the entry-point/syscall call-recursion path, which is explicitly protected by `RecursionDepthGuard` (`crates/blockifier/src/execution/entry_point.rs`, lines 706-733) and a configured `max_recursion_depth`, and unlike `NestedFeltCounts::new_inner` in `crates/blockifier/src/execution/contract_class.rs` which explicitly asserts `segmentation_depth <= 1`, neither `bytecode_hash_node` nor `create_bytecode_segment_structure_inner` enforce any bound on the nesting depth of the `NestedIntList`/`HashableNestedIntList` tree they walk: [6](#0-5) [7](#0-6) 

Because the segmentation tree's shape is a direct function of the declared Sierra program's structure (function/segment nesting), a declarer who crafts a Sierra program that compiles into a pathologically deeply-nested segment tree can drive these recursive walkers past the process stack limit, crashing the sequencer/full-node process performing the hash computation or OS re-execution — mirroring the DjVu stack-overflow bug class where crafted nested container structures caused unbounded native-stack recursion.

### Impact Explanation
A crash of the Sierra compiler service, the gateway/blockifier process validating a declare transaction, or a full node's Starknet OS re-execution constitutes a denial-of-service against block production/validation: an attacker submitting a single declare transaction (or a class referenced by it) can repeatedly crash sequencer/validator processes that must recompute the same hash to accept or reprove the block, potentially causing honest nodes to diverge (some crash, others may not, depending on stack size) or halting the network's ability to process new declare transactions. This satisfies the "network unable to confirm new transactions" / crash-based DoS bar for High severity, matching the CVSS-7.8/DoS-oriented rating of the original CVE.

### Likelihood Explanation
Likelihood depends on unverified compiler internals: whether the `cairo-lang-starknet-classes` bytecode segmentation algorithm actually permits deep nesting proportional to attacker-controlled program structure (e.g., deeply nested function-call scopes) rather than a shallow, one-function-per-leaf flat tree, and whether `max_bytecode_size` bounds effectively cap achievable nesting depth in practice. This repo does not vendor that compiler crate, so the exact nesting depth achievable per unit of Sierra program size could not be confirmed with the available tools — this is a real limitation of the analysis. Given that the mechanism (unbounded native recursion over a structure whose depth is influenced by user-supplied input, with no depth guard analogous to the one already used elsewhere in the codebase for entry-point recursion) is clearly present and reachable from an unprivileged declare transaction, the likelihood should be treated as at least Medium pending confirmation of the compiler's segmentation depth bound.

### Recommendation
- Add an explicit depth bound (mirroring `RecursionDepthGuard` / the `segmentation_depth <= 1` assertion already used in `NestedFeltCounts::new_inner`) to `bytecode_hash_node` and `create_bytecode_segment_structure_inner`, rejecting/erroring out on `NestedIntList` trees deeper than a small, well-reasoned constant.
- Convert these functions to explicit iterative (stack-based) traversal instead of native recursion, removing dependence on process stack size entirely.
- Validate `bytecode_segment_lengths` nesting depth as part of class/CASM validation immediately after compilation, before it is used in any subsequent hash or OS-hint computation.

### Proof of Concept
Not independently reproducible with available tooling: constructing a concrete Sierra program that the `cairo-lang-starknet-classes` compiler segments into an arbitrarily deep `NestedIntList` tree requires access to that external compiler crate's segmentation algorithm, which is not vendored in this repository and could not be inspected. Conceptually, a PoC would (1) craft a Sierra program with deep, non-inlinable function nesting designed to maximize compiler-generated segment-tree depth, (2) submit it via a Declare V3 transaction, and (3) observe a stack overflow/crash when `SierraCompiler::compile`, `check_compile_class_hash_v2_declaration`, or OS re-execution invoke `hash()`/`create_bytecode_segment_structure` on the resulting `CasmContractClass`.

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
