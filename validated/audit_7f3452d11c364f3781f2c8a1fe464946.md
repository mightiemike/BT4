### Title
Front-runnable canonical address lets an unprivileged user pre-load consensus-relevant account state before TIP-2935 `BlockHashHistory` deployment, which is preserved when the address is converted into a contract - (File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java)

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP-2935 (EIP-2935) `BlockHashHistory` system contract at a fixed, publicly-known address, `HISTORY_STORAGE_ADDRESS` [1](#0-0) . Exactly like the Swell Network report — where an attacker could interact directly with the deposit contract before the "official" `stake()` call and have their (malicious) data silently accepted because the system only validates on first-registration — any unprivileged user can send an ordinary transaction to this hardcoded address *before* the TIP-2935 proposal activates, and the code that finally installs the contract only partially normalizes the pre-existing state rather than rejecting or fully resetting it.

### Finding Description
`HISTORY_STORAGE_ADDRESS` is a hardcoded constant, not a derived/CREATE2 address that requires a hash preimage to target [2](#0-1) . Because the value is known ahead of time (it mirrors Ethereum's canonical EIP-2935 address), anyone can target it with ordinary, unprivileged transactions long before the chain committee activates the corresponding proposal.

Ordinary account-mutating transactions do not require control of the private key of the target address:
- `TransferContract`/`TransferAssetContract` will auto-create a normal account at any destination address and set its balance / TRC10 asset holdings, as shown for the general "create account if not exist" pattern [3](#0-2) .
- `FreezeBalanceActuator`/`DelegateResourceActuator`/`DelegateResourceProcessor` let any signer freeze/delegate resources **to** an arbitrary `receiverAddress` without that receiver ever signing anything; the receiver's `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` (or V2 equivalents) is mutated purely because it is named as the receiver [4](#0-3) [5](#0-4) .
- `AccountCreateContract` can pre-create the account with an attacker-chosen name at that address, as shown in `CreateAccountActuator` [6](#0-5) .

When `HistoryBlockHashUtil.deploy()` finally runs (from `ProposalService` during maintenance), it checks only whether *code* or *contract metadata* already exist at the address, not whether an account with attacker-supplied state exists [7](#0-6) . If a normal account is already present (the "common case" the author's own comment acknowledges), the code takes the branch that **mutates the existing capsule in place**, only flipping its `AccountType` to `Contract` and calling `clearDelegatedResource()` — explicitly preserving balance and other pre-existing state [8](#0-7) . This is modeled after the CREATE2-collision branch in `Program.createContractImpl()` [9](#0-8) , but that CREATE2 case is defensible only because reaching a *specific* address requires a SHA-3 preimage (the deploy javadoc itself notes this: "A SHA-3 pre-image of the address is the only realistic way that branch fires"). For `HISTORY_STORAGE_ADDRESS` there is no such barrier — the address is fixed and known in advance, so the "pre-existing account" branch is not a rare edge case but a directly, trivially reachable path for any unprivileged user.

This is structurally the same bug class as the Swell report: a security-relevant on-chain object is identified by something an attacker can predict/target ahead of the "official" registration event (there: the validator pubkey/withdrawal-credentials pairing; here: the canonical system address), the system trusts whatever got there first, and the legitimate installation step only partially reconciles state instead of rejecting or fully resetting it.

### Impact Explanation
Once the account is converted to `AccountType.Contract` at the canonical `BlockHashHistory` address while retaining attacker-influenced fields not covered by `clearDelegatedResource()` (e.g. balance, TRC10 asset holdings, account name, and any `AcquiredDelegatedFrozenBalance*` set by third parties targeting it as a receiver), the resulting system contract account carries state it was never supposed to have. Depending on what exactly `clearDelegatedResource()` zeroes (not fully verified within available context), this can range from cosmetic corruption of a system contract's account record to consensus-relevant resource-accounting corruption (extra bandwidth/energy backing a contract address that should have none) — a deterministic, network-wide outcome since every node applies the same pre-state, so it does not itself cause a fork, but it does permanently corrupt the state of a network system contract account in a way core developers did not intend, and is reachable purely from broadcastable, unprivileged transactions.

### Likelihood Explanation
High reachability: `HISTORY_STORAGE_ADDRESS` is a compile-time constant known to anyone reading the code (or Ethereum's EIP-2935 spec, since it mirrors it) well before the TIP-2935 proposal is voted in and activated. Sending TRX, TRC10 assets, or issuing `FreezeBalanceContract`/`DelegateResourceContract` transactions naming it as `receiverAddress`/`toAddress` requires no special privilege and no knowledge of a private key for that address — it is a completely ordinary broadcast transaction.

### Recommendation
In `HistoryBlockHashUtil.deploy()`, treat *any* pre-existing account at `HISTORY_STORAGE_ADDRESS` (not just pre-existing code/contract metadata) as a "foreign state" collision, or fully reset every field of that account (asset balances, name, all delegated/acquired resource counters) to the canonical template rather than only clearing delegated resources and flipping the type. At minimum, do not silently normalize attacker-supplied pre-state into a permanent system contract account; log/skip deterministically as is already done for the code/contract-store collision case.

### Proof of Concept
1. Before the TIP-2935 proposal is activated on the network, an unprivileged user broadcasts a `TransferContract` sending 1 TRX to `HISTORY_STORAGE_ADDRESS` (`41 0000f90827f1c53a10cb7a02335b175320002935`), auto-creating a normal account there with attacker-chosen balance/state (see `TransferActuator`'s "create account if not exists" behavior) [3](#0-2) .
2. The same or another unprivileged user then broadcasts a `FreezeBalanceContract`/`DelegateResourceContract` naming `HISTORY_STORAGE_ADDRESS` as `receiverAddress`, adding acquired-delegated resource balances to that account without needing its private key [4](#0-3) .
3. When the committee activates the TIP-2935 proposal and `ProposalService` calls `HistoryBlockHashUtil.deploy()`, the code/contract-store check passes (no code/contract yet), so it falls into the pre-existing-account branch, converts the account to `Contract` type, clears only delegated resources, and leaves the rest of the attacker-supplied state (balance, asset holdings, name) intact at the now-official system contract address [8](#0-7) .

Note: full verification of exactly which `AccountCapsule` fields `clearDelegatedResource()` zeroes (and thus the precise blast radius of residual state) was not completed within the available tool budget; a Devin session with full repository access should inspect `AccountCapsule.clearDelegatedResource()` in `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` to confirm the exact set of fields left uncleared.

    }

  @Override
  public boolean execute(Object result)
      throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) result;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    try {
      AccountCreateContract accountCreateContract = any.unpack(AccountCreateContract.class);
      boolean withDefaultPermission =
          dynamicStore.getAllowMultiSign() == 1;
      AccountCapsule accountCapsule = new AccountCapsule(accountCreateContract,
          dynamicStore.getLatestBlockHeaderTimestamp(), withDefaultPermission, dynamicStore);

      accountStore
          .put(accountCreateContract.getAccountAddress().toByteArray(), accountCapsule);

      adjustBalance(accountStore, accountCreateContract.getOwnerAddress().toByteArray(), -fee);
      // Add to blackhole address
      if (dynamicStore.supportBlackHoleOptimization()) {
        dynamicStore.burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }
      ret.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }
