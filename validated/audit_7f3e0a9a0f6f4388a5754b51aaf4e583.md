`get_burnchain_header_hash_by_consensus` is a simple deterministic lookup keyed on `consensus_hash` with `pox_valid = 1 LIMIT 1`, using `query_row_panic` which panics if more than one row matches [1](#0-0) . It performs no fork-choice logic and has no arrival-order dependence itself — it is only used to resolve a burn header hash for a given consensus hash (e.g., in `check_sortition_exists`) after canonical-tip selection has already occurred [2](#0-1) .

The uniqueness of the `pox_valid = 1` row per `consensus_hash`/`burn_header_hash` is enforced at insertion time: `insert_block_snapshot` explicitly checks for and panics on any existing pox-valid snapshot for the same `burn_header_hash` before inserting a new one [3](#0-2) . Actual canonical burn-chain tip selection is done deterministically via `get_canonical_burn_chain_tip`, which orders by `block_height DESC, burn_header_hash ASC` — a fixed deterministic tiebreak independent of message arrival order [4](#0-3) . Since `consensus_hash` is derived deterministically from the burnchain history and sortition inputs, and the PoX-valid uniqueness invariant is enforced on write, two honest nodes that have processed the same burnchain history will always resolve the same `burn_header_hash` for a given `consensus_hash`, regardless of arrival order of block-commits, leader keys, Nakamoto blocks/microblocks, poison reports, or forks extended by a minority attacker. No code path was found where this specific function's behavior diverges based on message arrival order in a way that breaks the canonical-tip equality across nodes.
