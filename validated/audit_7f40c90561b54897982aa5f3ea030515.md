### Title
Unbounded recursion in compiled-class bytecode hash computation can stack-overflow the sequencer on a crafted Declare transaction - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` recurses once per level of the CASM bytecode segment tree (`get_bytecode_segment_lengths()`), with no depth bound, mirroring the CVE-2018-6544 pattern where `pdf_load_obj_stm` recursed on nested/self-referential object streams until the process ran out of stack. Any account can trigger this path by submitting a `Declare` transaction whose Sierra program compiles to CASM with a deeply nested segment structure, causing a native stack overflow (process abort/crash) rather than a graceful error.

### Finding Description
`bytecode_hash_node` in [1](#0-0)  walks the `HashableNestedIntList` tree produced by the Sierra→CASM compiler and calls itself recursively once per nesting level with no maximum-depth check:
```
fn bytecode_hash_node<H, NL>(...) -> (usize, Felt) {
    if node.is_leaf() { ... }
    else {
        let inner_nodes = node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child)).collect_vec();
        ...
    }
}
```
This is invoked by `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash` [2](#0-1) , which is called synchronously right after Sierra→CASM compilation in `SierraCompiler::compile`:
```
let executable_class_hash = executable_class.hash(&HashVersion::V2);
``` [3](#0-2) 

Notably, the sibling implementation used elsewhere in blockifier (`NestedFeltCounts::new_inner`) explicitly documents and enforces that this kind of nesting is "only supported for segmentation depth at most 1" via an `assert!`, [4](#0-3)  — showing the codebase is aware that deeper nesting is a design edge case, yet the production hashing path in `starknet_api::contract_class::compiled_class_hash` has no such guard. Unlike Cairo/Sierra program execution, which is protected by an explicit `RecursionDepthGuard` [5](#0-4)  and simulates its stack in the VM's heap-backed memory segments (immune to native stack exhaustion, as noted in the test comment at [6](#0-5) ), this Rust-native recursive routine runs directly on the OS thread stack of the compiling process and has neither a depth guard nor an iterative/worklist implementation.

### Impact Explanation
`SierraCompiler::compile` runs inside the gateway/class-manager's compilation service, which processes Declare transactions from any unprivileged sender before mempool admission, per the flow documented in `docs/diagrams/02-tx-submission-flow.md` [7](#0-6) . A crafted Sierra program that compiles to CASM with a sufficiently deep bytecode-segment tree (achievable using nested branching/function structures within the existing `max_bytecode_size` budget) will overflow the native stack when `.hash(&HashVersion::V2)` is invoked, aborting the compiling process (Rust cannot catch stack overflow — it is a process abort, not a recoverable `Result::Err`). Because this hashing is not isolated in the resource-limited compilation subprocess (that subprocess only performs Sierra→CASM translation; hashing happens back in the calling Rust process, see `compiler.rs`), the crash affects the sequencer's own class-manager/gateway process. Repeated declare submissions of this kind can repeatedly crash the compilation service, denying declare-transaction processing network-wide until manual intervention — matching the "network unable to confirm new transactions" impact bar for this bug class.

### Likelihood Explanation
Likelihood is Medium: the attacker needs no special privileges (any account can send a Declare transaction), and the resource limits enforced (`max_bytecode_size`, `max_memory_usage`, `max_cpu_time` in `SierraCompilationConfig` [8](#0-7) ) bound the compiler subprocess but do not bound recursion depth of the post-compilation hashing step that runs in the calling process. Constructing a Sierra program whose CASM segment tree reaches the depth needed to exhaust a typical thread stack (tens of thousands of frames) is a compiler/code-structuring exercise, not a cryptographic one, making it feasible for a moderately determined attacker, though I could not directly verify from the indexed code exactly how deep the cairo-lang-sierra-to-casm compiler's real-world segment trees can go for a given bytecode budget — this would need runtime verification.

### Recommendation
Convert `bytecode_hash_node` to an iterative traversal using an explicit heap-allocated worklist/stack (as is already done for other tree-walks in this codebase, e.g., `fetch_patricia_paths_inner` and `fetch_nodes` in `crates/starknet_committer/src/db/trie_traversal.rs`, which use `Vec`-based work queues instead of native recursion), or add an explicit maximum-depth check that rejects contract classes whose segment structure exceeds a safe depth (mirroring the `assert!(segmentation_depth <= 1)` invariant already present in `NestedFeltCounts::new_inner`) before invoking `.hash()`.

### Proof of Concept
1. Author a Cairo1 contract whose control flow (deeply nested `if`/`match` chains or many small functions) causes the `cairo-lang-sierra-to-casm` compiler to emit a `CasmContractClass` with a `bytecode_segment_lengths` tree of very high nesting depth while staying within `max_bytecode_size`/`max_memory_usage`/`max_cpu_time` limits enforced on the compiler subprocess.
2. Submit this class via a standard Declare transaction (`add_tx` → gateway → `SierraCompiler::compile`) as in [3](#0-2) .
3. After successful subprocess compilation, the call to `executable_class.hash(&HashVersion::V2)` recurses through `bytecode_hash_node` in the calling process's native stack, ultimately overflowing it and aborting the compiling process — denying declare-transaction throughput for the sequencer instance.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
