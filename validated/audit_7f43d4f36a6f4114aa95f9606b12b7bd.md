### Title
`ensure_match_transaction_info` omits checkpoint-hash comparison, letting replay-verify accept a computed output whose state/hot-state/position-state root diverges from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm a freshly re-executed transaction output matches the trusted, on-chain-committed `TransactionInfo` for that version. It checks status, gas used, write-set hash, and event root hash, but the code itself documents (in a `TODO`) that it deliberately skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`. [1](#0-0) [2](#0-1) 

### Finding Description
`TransactionInfo` (both V0 and V1) carries `state_checkpoint_hash` and, in V1, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, which authenticate the Merkle root of the on-chain state (and, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` features are enabled, the hot-state and native-position state trees) at that transaction/checkpoint. [3](#0-2) 

These checkpoint hashes are produced from the executor's `LedgerUpdateOutput`/`DoStateCheckpoint` pipeline and are exactly the values whose correctness is at stake if there is any divergence between local state-tree computation and the authenticated ledger — e.g., a bug in `DoStateCheckpoint`'s position-state or hot-state root computation (`execution/executor/src/workflow/do_state_checkpoint.rs`), a JMT/position-SMT computation defect, or a corrupted/omitted native-position write set. [4](#0-3) 

`ensure_match_transaction_info` is exactly the safety check meant to catch such divergences during replay, forensic debugging, and archive-node validation. But it validates only `status`, `gas_used`, `write_set_hash` (state_change_hash), and `event_root_hash` — never `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [5](#0-4) 

This function is invoked directly by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the tool used to replay-verify mainnet history against archived transaction infos, feeding it the pre-recorded `expected_txn_infos` (which carry the authenticated checkpoint hashes) but never checking those fields against the locally re-executed state. [6](#0-5) 

The consequence: if the *write set* and *events* of a re-executed transaction happen to match (e.g., a bug only manifests in how the state-checkpoint/position-state root is aggregated, rather than in the individual write ops themselves — such as an off-by-one in checkpoint index selection, or a native-position leaf-collection bug in `do_state_checkpoint.rs`'s `collect`/`extend` logic), replay-verify will report success even though the authenticated state/position root committed to the ledger diverges from what local execution computes. The comment in the code makes this explicit: "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." [7](#0-6) 

### Impact Explanation
This breaks the proof/commitment-binding invariant that authenticated API and archive-verification output must stay bound to the correct state root. A wrong `state_checkpoint_hash`/`position_state_checkpoint_hash`/`hot_state_checkpoint_hash` produced by an executor bug (independent from write-set/event computation) would go completely undetected by the primary tool designed to catch exactly this class of error (replay verification against archived ledger data). Because state/position roots gate proofs served to light clients and state-sync peers, an undetected divergence here means corrupted or wrong state commitments can silently persist and be served as "verified" via `TransactionInfoWithProof`/state proofs, without any replay-verify alarm — a hard-to-detect, high-severity gap in the ledger's self-consistency checking, directly analogous to the external report's core lesson: a code path uses/derives a value from one source (local recomputation) while silently ignoring a second, independently authenticated source of truth (checkpoint hash in `TransactionInfo`) that should be reconciled.

### Likelihood Explanation
This is a real, currently-shipped gap (not hypothetical): the code contains its own explicit TODO acknowledging that checkpoint hashes are unchecked, tied directly to the new `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature rollout (native-position state trees) and `HOT_STATE_ROOT_IN_TXN_INFO`. Since these are newly introduced, more complex state-tree pipelines (position-state SMT bookkeeping in `do_state_checkpoint.rs`, hot-state root aggregation in `do_ledger_update.rs`), the probability of a subtle computation bug specifically in checkpoint-root aggregation (as opposed to individual write ops) is non-trivial, and once such a bug ships, this gap guarantees it is invisible to the tool whose entire purpose is catching it. [8](#0-7) [9](#0-8) 

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/known) between the recomputed output and the expected `TransactionInfo`, mirroring the pattern already used in `do_state_checkpoint.rs::get_state_checkpoint_hashes`'s "known hash" validation. This should be enabled before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on for mainnet, per the code's own TODO.

### Proof of Concept
Not independently exploitable as a standalone PoC by an external attacker; the gap is a missing-check defect proven directly by the code:
1. `ensure_match_transaction_info` body — only checks `status`, `gas_used`, `write_set_hash`, `event_root_hash`: [10](#0-9) 
2. The function's own acknowledging TODO of the exact bypass scenario: [7](#0-6) 
3. Its call site in the mainnet replay-verify tool, which relies solely on this function for pass/fail: [11](#0-10) 

Given the reasoning-effort constraints of this session, I was not able to fully trace whether any other caller of `TransactionOutput`/replay pipeline (e.g., `aptos-debugger`/`cli/commands.rs`) independently re-validates the checkpoint hashes elsewhere, which would mitigate the impact; that would require further review of those two call sites.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
