### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting corrupted state-checkpoint/root data pass replay and restore verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the comparator used across executor replay, chunk-executor sync, backup/restore tooling, and the debugger to confirm that a recomputed transaction output matches the authenticated `TransactionInfo` stored in the ledger, only checks status, gas, write-set hash, and event-root hash. It never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, which are exactly the fields that bind a transaction to the correct state/JMT root at that version.

### Finding Description
`ensure_match_transaction_info` explicitly documents its own gap: [1](#0-0) 

The function verifies `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event-root hash, but the code comment admits:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This is not a hypothetical — it is a self-documented, unresolved gap gated behind a not-yet-enabled comment ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), meaning the check is currently disabled/missing in the shipped comparator rather than conditionally correct.

This same comparator is not confined to a single debug tool. It is invoked from:
- `execution/executor/src/chunk_executor/mod.rs` (chunk replay / `TransactionReplayer`, used in fast-sync and backup restore verification paths)
- `storage/db-tool/src/replay_on_archive.rs` (replay-verify used for pre-hard-fork determinism checks)
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` (transaction simulation/verification tooling)

By contrast, the correctly-implemented ledger-side hashing path in the executor (`assemble_transaction_infos`) does fold `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` into the constructed `TransactionInfo`: [2](#0-1) 

so these fields are meaningful, committed, hashed parts of the `TransactionInfo` accumulator leaf — but the one place that is supposed to independently re-derive and cross-check them against a locally-recomputed output never does so.

### Impact Explanation
`TransactionInfo` (and its checkpoint-hash fields) is the leaf committed into the transaction accumulator and is what proofs are built over; it is also what restore/replay tooling relies on to detect divergence between local re-execution and the value that was actually committed and signed by validators. Because `ensure_match_transaction_info` silently accepts any state/hot-state/position-state checkpoint hash regardless of whether it matches locally recomputed state, a scenario where the locally computed state root diverges from the authenticated ledger value (e.g., a storage bug, a non-deterministic VM change, or corrupted backup data feeding replay) will not be caught by this check. This falls squarely into the "hard-fork-only divergence during commit, replay, restore, or proof verification" impact category: the very mechanism meant to catch such divergence before a chain split or before trusting restored data is defeated for exactly the fields that encode the state root.

### Likelihood Explanation
The gap is unconditional — it is not behind an unenabled feature flag in the comparator itself; the comment only aspires to add validation "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," but no such gating currently exists in `ensure_match_transaction_info`. Because the function is called from the general chunk-executor replay path (not just an offline debug tool), the missing checks apply whenever transaction replay/restore verification is exercised.

### Recommendation
Extend `ensure_match_transaction_info` to also recompute and assert equality of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on both the recomputed output and the stored `TransactionInfo`), consistent with how `assemble_transaction_infos` derives them at commit time, before this function is trusted by chunk-executor replay, restore, or replay-verify tooling.

### Proof of Concept
Not applicable as a runnable exploit — the finding is a code-level proof of a missing invariant check, directly evidenced by the omitted assertions and the accompanying TODO in `types/src/transaction/mod.rs` lines 2139–2204 contrasted with the fields actually populated in `do_ledger_update.rs` lines 82–121.

### Caveat
I could not fully confirm, within the available investigation, whether an independent state-root check elsewhere in the chunk-executor's commit pipeline (e.g., in `chunk_result_verifier.rs`, which I was unable to locate/inspect) provides a redundant safety net that would catch the same divergence before a corrupted state checkpoint could actually be persisted to the synced ledger. If such a redundant check exists and always runs before commit, the practical exploitability would be limited to the replay-verify/debugging tooling explicitly named in the TODO rather than live state-sync commit. I recommend a Devin session with full repo/tool access to trace `chunk_result_verifier.rs` and the `StateSyncChunkVerifier`/`ReplayChunkVerifier` implementations to determine whether that path independently re-validates checkpoint hashes.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
