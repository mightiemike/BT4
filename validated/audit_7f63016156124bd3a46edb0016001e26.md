### Title
Unbounded eth_getLogs block range causes shared sectionExecutor thread-pool exhaustion (DoS) - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java])

### Summary
`LogBlockQuery.partialMatch` submits one `Future` to the shared `sectionExecutor` for every unique bloom bit index, once per section in `[minSection, maxSection]`, and blocks the calling RPC thread on `Future.get()` for all of them. Because `minSection`/`maxSection` are derived directly from the caller-supplied `fromBlock`/`toBlock` with no maximum-range check before this loop runs, an unprivileged caller can request a full-chain range and force thousands of task submissions per call, and many concurrent such calls can starve the bounded `sectionExecutor` pool used to service all `eth_getLogs`/`eth_getFilterLogs`/`eth_newFilter` requests.

### Finding Description
`LogBlockQuery`'s constructor computes `minSection`/`maxSection` purely from the requested `fromBlock`/`toBlock` (clamped only against `currentMaxBlockNum`, with no minimum-side clamp and no maximum span limit): [1](#0-0) 

`getPossibleBlock()` iterates every condition (address + up to 4 topic lists) and calls `subMatch`, which serially loops `section` from `minSection` to `maxSection` and calls `partialMatch` for each section: [2](#0-1) 

`partialMatch` then submits a `Future` to `sectionExecutor` for every unique bloom bit index (up to 3 per address/topic value, potentially more with multiple OR'd values) for that single section, and blocks synchronously on all of them via `.get()`: [3](#0-2) 

The only bound on results is `MAX_RESULT`, which is checked only *after* the entire scan across all sections has already been executed: [4](#0-3) 

There is no pre-check limiting `maxSection - minSection` (i.e., the requested block range width) before submitting work to the shared executor. Any anonymous JSON-RPC caller can set `fromBlock=0` (or `earliest`) and `toBlock=latest`, spanning the entire chain height, which on a long-lived chain produces a very large number of sections. Each section triggers up to several `Future` submissions to the shared, presumably bounded `sectionExecutor`, and the calling RPC handler thread blocks until all of them complete. Multiple concurrent such requests can queue enough tasks/block enough worker threads that the shared pool becomes saturated, delaying or starving other legitimate `eth_getLogs`/`eth_getFilterLogs` callers — an availability degradation of the JSON-RPC log-query subsystem. No fee, signature, or authentication is required to reach this code path, since `eth_getLogs`/`eth_newFilter` are unauthenticated JSON-RPC methods.

### Impact Explanation
This is a resource-exhaustion / thread-pool-starvation DoS confined to the JSON-RPC log-query feature (`eth_getLogs`, `eth_getFilterLogs`, filter polling backed by `LogBlockQuery`). It does not affect consensus, accounting, or private-key material — impact is scoped to degraded/unavailable RPC service for the log-query surface, consistent with a "DoS via RPC-API" bounty class rather than a critical chain-integrity issue.

### Likelihood Explanation
Feasibility depends heavily on unverified deployment/runtime details: the actual size of the `sectionExecutor` pool, its queue policy (bounded vs. unbounded — an unbounded queue would turn this into memory pressure rather than starvation), whether reverse proxies/rate limiters are typically deployed in front of the JSON-RPC endpoint, and how large `SectionBloomStore` sections are relative to real chain height (large section size could reduce the number of sections needed to span the full chain, lowering the number of Futures per call and reducing severity). These configuration details were not found in the indexed portion of the codebase, so likelihood cannot be fully confirmed without further investigation (e.g., locating where `sectionExecutor`/`ExecutorServiceManager` pool size is configured for this specific service, and any `node.jsonrpc` range-limit config).

### Recommendation
Enforce a maximum allowed block range (`maxSection - minSection`, or equivalently `toBlock - fromBlock`) for `eth_getLogs`/`eth_newFilter` before any section processing begins, rejecting oversized ranges early with `JsonRpcInvalidParamsException`/`JsonRpcExceedLimitException`. Additionally, consider bounding the number of concurrent `Future` submissions from a single logical query (e.g., a semaphore or per-request task cap) and using a dedicated/isolated executor per client or with backpressure so a single caller cannot starve the pool for others.

### Proof of Concept
Not fully verifiable without confirming `sectionExecutor` pool size/config and `SectionBloomStore.BLOCK_PER_SECTION`/section count for a realistic chain height, which were not located in the indexed code. Conceptual PoC:
1. Configure/observe a node with substantial block height.
2. Issue N concurrent JSON-RPC calls: `eth_getLogs({"fromBlock":"0x0","toBlock":"latest","address":["0x<collision-prone address>"],"topics":[["0x<collision-prone topic>"]]})`.
3. Assert via metrics/thread dump that `sectionExecutor` worker threads/queue are saturated and that a benign concurrent `eth_getLogs` request experiences significant added latency or rejection while the attack requests are in flight.

A JUnit-level equivalent would directly construct `LogBlockQuery` with `fromBlock=0`, `toBlock=currentMaxBlockNum` (large), call `getPossibleBlock()` from many threads against a shared small `ExecutorService`, and assert queue/thread saturation, mirroring the shape of existing tests in `framework/src/test/java/org/tron/core/jsonrpc/LogBlockQueryTest.java`.   private BitSet subMatch(int[][] bitIndexes) throws ExecutionException, InterruptedException {

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet subBitSet = new BitSet(capacity);

    for (int section = minSection; section <= maxSection; section++) {
      BitSet partialBitSet = partialMatch(bitIndexes, section);

      for (int i = partialBitSet.nextSetBit(0); i >= 0; i = partialBitSet.nextSetBit(i + 1)) {
        // operate on index i here
        if (i == Integer.MAX_VALUE) {
          break; // or (i+1) would overflow
        }
        int offset = (section - minSection) * SectionBloomStore.BLOCK_PER_SECTION + i;
        subBitSet.set(offset);
      }
    }

    return subBitSet;
  }
