Cross-Tenant Session Access via Unauthenticated Webhook `domain` Header (Missing Destination Binding in HMAC) - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`shopify.webhooks.validate()` verifies webhook authenticity by computing an HMAC over `rawBody` only, using the app's single, shop-wide `apiSecretKey`. None of the identifying headers — in particular `X-Shopify-Shop-Domain` (the "destination" that determines which tenant's session gets loaded) — are included in the signed data. This mirrors the reported CCTP bug class: the authorization check validates the signature/discriminator-equivalent (HMAC) but never validates the destination parameter (`domain`) that determines where the resulting privileged action (loading an offline session/access token and invoking the app's webhook handler with an authenticated Admin client) is directed.

### Finding Description
`validateHmacFromRequestFactory` in <cite repo="Thankgoddavid56/shopify-app-js--004" path="packages/apps/shopify-api/lib/utils/hmac-validator.ts" start="168-197" /> computes and compares the HMAC exclusively against `rawBody`: [1](#0-0) 

`validateFactory` in [2](#0-1)  calls this HMAC check and, once it passes, simply reads the `domain`, `topic`, `webhookId`, etc. straight from the (unsigned) HTTP headers via `checkWebhooksHeaders`: [3](#0-2) 

Downstream, `authenticateWebhookFactory` trusts `check.domain` (attacker-controlled header, unauthenticated by the signature) to look up and load the shop's stored offline session, and constructs an authenticated Admin API client from it: [4](#0-3) [5](#0-4) 

`ensureValidOfflineSession` → `createOrLoadOfflineSession` uses that unauthenticated `shop` string directly as the session-storage key: [6](#0-5) [7](#0-6) 

Because the API secret key is shared across *all* shops that install the app (it is the app's client secret, not per-shop), any merchant that installs the app can obtain a genuinely-signed `(rawBody, hmac)` pair from a real webhook Shopify sends them. Since the signature covers only `rawBody`, that attacker can resend the identical body+HMAC to the app's own webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to point at an arbitrary victim shop. `validateHmacFromRequest` will report `valid: true` because the body/HMAC pair is genuinely valid — the "destination" (`domain`) was simply never bound to the signature, exactly analogous to `destination_domain` being unchecked in the CCTP `authorize` function while only `mint_recipient`/discriminator are checked.

There is existing test coverage acknowledging a related replay risk (reusing an OAuth-cookie signature as the webhook HMAC), showing the maintainers are aware HMAC-replay is a concern, but no test or code path binds the `domain` header to the signed payload: [8](#0-7) 

### Impact Explanation
A single unprivileged merchant who has installed the app (and therefore received at least one legitimate webhook) can forge a request to the app's webhook endpoint that appears to originate from a different, victim shop. This causes the framework to load the victim shop's stored offline access token/session and hand an authenticated Admin API client to the app's webhook handler for the attacker-chosen topic/body — a cross-tenant access vulnerability that can leak or expose actions against another merchant's data with no interaction from the victim.

### Likelihood Explanation
Likelihood is moderate-to-high: the only prerequisite is that the attacker install the app on their own store (a normal, unprivileged action) and observe one legitimate webhook delivery to learn a valid `(rawBody, hmac)` pair for a topic whose body content they don't need to control precisely (many webhook topics accept minimal/near-empty JSON bodies). No secret leakage, MITM, or privileged access is required — only crafting an HTTP POST to the app's own public webhook endpoint with substituted headers.

### Recommendation
Bind the destination identity to the signed payload before trusting it: verify that the `X-Shopify-Shop-Domain` header corresponds to a shop for which the app expects this specific webhook delivery (e.g., cross-check against `topicForStorage`/registered subscriptions per shop, or require that shop domain format via `sanitizeShop`), and/or include the domain/topic/webhook-id headers as part of the HMAC-verified data rather than trusting them unauthenticated post-hoc. At minimum, do not use headers that are excluded from the signature to select which tenant's stored credentials get loaded and exposed to a handler.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`; the app registers a webhook (e.g. `app/uninstalled`) and eventually receives a real webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(apiSecretKey, B)`.
2. Attacker replays the exact same body `B` and header `H` to the app's `/webhooks` endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
3. `validateHmacFromRequest` recomputes `HMAC-SHA256(apiSecretKey, B)`, which still equals `H`, so `validHmacResult.valid === true` (see [9](#0-8) ).
4. `checkWebhooksHeaders` returns `{valid: true, domain: 'victim-shop.myshopify.com', ...}` from the unsigned headers ( [10](#0-9) ).
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's offline session/access token from storage and constructing an authenticated `admin` client, then invokes the app's webhook handler with it ( [11](#0-10) ).

Note: I was unable to independently verify whether any additional runtime-level protections (e.g., IP allow-listing of Shopify's webhook servers, or per-shop signing secrets configured outside this repo) exist in deployed apps that would mitigate this at the network layer; the review here is scoped strictly to the `shopify-app-js` library's own validation logic, where no such binding exists in code.

export async function createOrLoadOfflineSession(
  {api, config, logger}: BasicParams,
  shop: string,
) {
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    logger.debug('Creating custom app session from configured access token', {
      shop,
    });
    return api.session.customAppSession(shop);
  } else {
    logger.debug('Loading offline session from session storage', {shop});
    const offlineSessionId = api.session.getOfflineId(shop);
    const session = await config.sessionStorage!.loadSession(offlineSessionId);

    return session;
  }
