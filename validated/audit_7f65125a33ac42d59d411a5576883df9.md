### Title
Starknet OS `charge_fee` discards the fee-token `transfer` success return value, committing a fee charge without verifying the ERC20 call actually returned success - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/execute_transaction_utils.cairo])

### Summary
The Sherlock report describes `LMPVault.redeem` burning a user's full share amount while only *assuming* (via a comment, not an assertion) that the amount pulled from destinations equals the amount owed, instead of verifying the transferred amount against the promised amount before finalizing the irreversible state change (burn). The same bug class — committing an irreversible accounting effect based on an *assumed* success of a value transfer rather than a *verified* one — is reachable in the Starknet OS's fee-charging flow.

### Finding Description
`charge_fee` in `crates/apollo_starknet_os_program/.../transaction_impls.cairo` builds an ERC20 `transfer` call to the sequencer and executes it via `non_reverting_select_execute_entry_point_func`: [1](#0-0) 

`non_reverting_select_execute_entry_point_func` (in `execute_transaction_utils.cairo`) only asserts that the call did not *revert* (`is_reverted = 0`); it never inspects `retdata` at all: [2](#0-1) 

Compare this to `run_validate` in the same file, which explicitly checks the retdata for the `__validate__` call (`assert retdata_size = 1; assert retdata[0] = VALIDATED;`): [3](#0-2) 

For the fee-transfer call, no equivalent check exists on the ERC20 `transfer`'s `(success: felt)` return value — the OS never asserts `retdata[0] == 1`. If a fee token contract's `transfer` entrypoint returns without reverting but with `success = 0` (a legitimate ERC20 pattern — return false instead of reverting on insufficient balance/failure, as reflected in the fee-token ABI's `(success: felt)` output type used elsewhere in the codebase, e.g. `crates/apollo_rpc_execution/resources/erc20_fee_contract_class.json:218-226`), the OS still treats the fee as charged and proceeds to commit the transaction and the block, exactly mirroring the reported bug class: assuming a value-transfer's success instead of verifying the returned/committed value.

### Impact Explanation
If this path is reachable with the network's default fee token, it would mean the sequencer/OS could commit a block state in which a transaction's declared fee is treated as paid to the sequencer while the ERC20 contract's own bookkeeping never actually moved funds (success=0 silently ignored) — a state/root divergence between what actually happened at the token-contract level and what the OS commits, and a potential fee-collection bypass (unauthorized "free" transaction execution) or a wrong committed state root relative to honest re-execution expectations, depending on how retdata is/isn't checked in other paths (e.g., the Rust blockifier CallInfo for the fee transfer).

### Likelihood Explanation
Likelihood is constrained by the fact that the fee-token class hash used in `charge_fee` is the network's own well-known fee-token contract (`fee_token_address` from `starknet_os_config`), not an arbitrary user-supplied contract — see `crates/apollo_starknet_os_program/.../transaction_impls.cairo:138`. The known/canonical ERC20 fee-token implementations in this codebase (e.g., `ERC20_base.cairo`) generally revert via `assert` on insufficient balance rather than returning `success = 0`, which would make the retdata check moot for the current fixed fee-token deployment. I was not able to fully verify (due to iteration limits) whether every fee-token implementation reachable in this system's config always reverts rather than returning a false success flag, nor whether the Rust `blockifier` side (`execute_fee_transfer` in `account_transaction.rs`) independently validates the `CallInfo`'s returned data for the transfer. This leaves genuine uncertainty about real-world reachability versus a purely structural code-review-level analog.

### Recommendation
Add an explicit assertion in `charge_fee` (mirroring `run_validate`'s pattern) checking that the fee-token `transfer` call's `retdata` equals `(success = 1)` before treating the fee as charged, rather than relying solely on "did not revert." This closes the same class of gap identified in the original report: never treat a value-transfer as fully successful without positively verifying its return value/committed effect.

### Proof of Concept
Not independently reproduced against a live sequencer within the scope of this analysis; the finding is a static code-path analysis showing `non_reverting_select_execute_entry_point_func` (used by `charge_fee`) discards `retdata` entirely, in contrast to `run_validate`'s explicit retdata check in the same file, matching the report's "assumed success without verification" bug class. Confirming exploitability would require verifying whether any admissible fee-token class (per current OS/Bouncer config) can return `success = 0` without reverting.
