### Title
Duplicate witness addresses in `VoteWitnessContract` are not merged in `VoteWitnessActuator`, causing vote/reward accounting divergence - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
`VoteWitnessActuator.countVoteAccount` iterates a user-supplied list of `Vote` entries from a broadcast `VoteWitnessContract` and appends each entry directly to the account's votes without checking for or merging duplicate witness addresses. This mirrors the reported bug class (RelayerV2's unchecked duplicate items in a user-supplied list causing incorrect fund/accounting outcomes), because the sibling code path for the same feature — the TVM native contract `VoteWitnessProcessor` — explicitly defends against this exact problem.

### Finding Description
In the classic actuator path, `countVoteAccount` does: [1](#0-0) 
It calls `votesCapsule.addNewVotes(...)` and `accountCapsule.addVotes(...)` once per entry in `voteContract.getVotesList()`, with no deduplication or merging by witness address. `validate()` only sums `voteCount` across all entries (including duplicates) to check against `tronPower`; it never rejects or normalizes duplicate witness addresses: [2](#0-1) 

By contrast, the TVM-facing `VoteWitnessProcessor.execute` explicitly builds a `voteMap` keyed by witness address and merges vote counts for the same witness, with a comment stating this intent ("merge vote for same witness"): [3](#0-2) 

This inconsistency between the two implementations of the same underlying feature (regular transaction vs. TVM `voteWitness` opcode, reachable via `Program.voteWitness`) is direct evidence that duplicate witness entries are a recognized hazard that was fixed in one code path but not the other.

### Impact Explanation
If duplicate witness addresses are stored as separate `Vote` entries in `AccountCapsule`'s votes list (rather than being merged), downstream logic that iterates per-`Vote` entry — witness vote tallying during maintenance (`MaintenanceManager`/consensus vote counting) and reward distribution in `MortgageService.withdrawReward` — may double count or otherwise mis-attribute vote weight/rewards for the same witness depending on how that logic keys or iterates the votes list. This can lead to incorrect reward payouts (fund accounting corruption) or divergence in witness vote totals used for consensus, both of which are high-impact classes (asset/accounting corruption, consensus divergence) per the validation criteria.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a user (or their wallet/tooling) to submit a `VoteWitnessContract` with duplicate `voteAddress` entries, which is unusual but not prevented by any validation check, and is trivially reachable by anyone broadcasting a transaction — no privileged role is required.

### Recommendation
Add the same deduplication/merge-by-witness-address logic used in `VoteWitnessProcessor` (a `Map<ByteString, Long>` accumulation) to `VoteWitnessActuator.countVoteAccount`, or explicitly reject contracts containing duplicate `voteAddress` entries in `validate()`.

### Proof of Concept
1. Attacker/user crafts a `VoteWitnessContract` with `votes = [{W1, 5}, {W1, 3}]` (duplicate witness `W1`).
2. `validate()` sums `5+3=8` against the account's `tronPower`; if `tronPower >= 8*TRX_PRECISION`, validation passes — no duplicate check exists. [2](#0-1) 
3. `execute()` → `countVoteAccount()` calls `accountCapsule.addVotes(W1, 5)` then `accountCapsule.addVotes(W1, 3)`, and similarly for `votesCapsule.addNewVotes`, producing two separate `Vote` entries for the same witness instead of one merged `{W1, 8}` entry as the TVM path would produce. [1](#0-0) 
4. Depending on how reward/vote-count consumers iterate this list (e.g., `MortgageService.withdrawReward`), the duplicate entries can cause reward or vote-count miscalculation for witness `W1` relative to the merged-entry behavior guaranteed by `VoteWitnessProcessor`.

Note: I was unable to fully trace `AccountCapsule.addVotes` and `MortgageService.withdrawReward`'s exact per-entry iteration semantics within the available tool budget, so the precise magnitude of reward/vote miscalculation (over- vs under-counting) could not be confirmed with full certainty; this should be verified against `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` and `chainbase/src/main/java/org/tron/core/service/MortgageService.java`.
