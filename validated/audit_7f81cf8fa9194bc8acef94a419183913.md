### Title
Receipts can be created above `max_receipt_size` after the size check, letting oversized receipts bypass the protocol's size-validation invariant - ([File: runtime/runtime/src/receipt_manager.rs])

### Summary
The report's bug class is a mismatch between the payload/size a system uses for admission/limit checks and the actual larger payload the system later sends/creates - the check is done against an underestimated quantity, letting an over-limit object through. The nearcore analog is issue #12606: a receipt's size is validated against `max_receipt_size` in `validate_receipt` (`runtime/runtime/src/verifier.rs:681-696`) at creation time, but `ReceiptManager::create_action_receipt` (`runtime/runtime/src/receipt_manager.rs:112-138`) later mutates an *already-created* receipt by pushing extra `output_data_receivers` (`receipt_manager.rs:120-125`), and a promise's returned value can likewise be attached after the fact. This means the size actually persisted/forwarded can exceed the size that was checked, so the runtime accepts and processes receipts that violate the declared protocol invariant `max_receipt_size`.

### Finding Description
`validate_receipt` (`runtime/runtime/src/verifier.rs:681-696`) computes `borsh::object_length(receipt)` and rejects it if larger than `limit_config.max_receipt_size`, but only in `ValidateReceiptMode::NewReceipt`. The check happens once, at receipt-creation time. However, `ReceiptManager::create_action_receipt` (`receipt_manager.rs:112-138`) can later append `DataReceiver` entries to an *existing* action receipt's `output_data_receivers` (`receipt_manager.rs:119-125`, called whenever a subsequent promise declares a dependency on this receipt via `promise_return`/`promise_then`). Because the size check already passed before these appends happen, a receipt that was exactly at `max_receipt_size` at check time can grow past the limit afterward without being re-validated.

This is a known, currently open bug (tracked as https://github.com/near/nearcore/issues/12606) with explicit workarounds elsewhere in the runtime:
- `try_forward` (`runtime/runtime/src/congestion_control.rs:403-427`) clamps an oversized receipt's size down to `max_receipt_size` purely "to avoid receipts getting stuck," explicitly noting "There is a bug which allows to create receipts that are above the size limit" (`congestion_control.rs:413-417`).
- `generate_bandwidth_requests`/`generate_bandwidth_request` clamps buffered receipt-group sizes the same way for the same reason (`congestion_control.rs:556-562`).
- `validate_receipt`'s `ValidateReceiptMode::ExistingReceipt` mode exists specifically to "tolerate" already-created oversized receipts that must still be executed (`verifier.rs:727-739`).
- Dedicated regression tests (`test-loop-tests/src/tests/max_receipt_size.rs:124-267`) demonstrate the bug directly: a receipt is built to be exactly `max_receipt_size`, and adding `output_data_receivers` (via `promise_return`) or a large returned value pushes it over the limit; the tests state "The receipt should be rejected, but currently isn't because of a bug."

### Impact Explanation
The receipt-size limit (`max_receipt_size`) is a protocol invariant meant to bound trie storage entries, congestion "memory" accounting (`receipt_bytes` in `CongestionInfo`), state-witness sizes, and network transfer of receipts between shards. Because oversized receipts are silently accepted into the delayed/outgoing-buffer queues and forwarded between shards, this is an accepted invalid-state-transition: the chain durably stores and processes objects that violate a size bound the validation logic is supposed to enforce. This can inflate per-shard memory/storage beyond intended bounds, feed into congestion-control size clamps that under-report true memory usage, and (per the code comments) risks the receipt getting permanently "stuck" if all the various downstream clamps were not consistently applied - the runtime currently mitigates the symptom (stuck receipts) rather than the root cause (the size check being bypassable), so any future change that removes or misses one of those clamps reopens a chunk-execution halt risk for any shard receiving such a receipt.

### Likelihood Explanation
Reachable directly by an unprivileged contract caller: any account can deploy a contract that builds a promise DAG close to `max_receipt_size` and then calls `promise_return`/adds a dependent promise (exactly what the existing regression tests in `test-loop-tests/src/tests/max_receipt_size.rs` do), causing `output_data_receivers` to be appended after the size check. No validator or privileged access is required - a single transaction from any signer suffices, and the runtime code paths and test harness already confirm the condition is trivially triggerable today.

### Recommendation
Re-validate the *final* receipt size (after all `output_data_receivers`/return-value mutations are applied, immediately before it is queued/forwarded) against `max_receipt_size`, rather than only checking at the initial `ReceiptManager::create_action_receipt` call. If a receipt would exceed the limit only after later mutation, the offending action (e.g., the `promise_return`/`promise_then` call that pushes the receipt over the limit) should fail with a clear host error instead of silently producing an oversized receipt that must be tolerated downstream. This removes the need for the compensating clamps in `try_forward` and `generate_bandwidth_request`, closing the root cause tracked in GitHub issue #12606 rather than only mitigating its symptoms.

### Proof of Concept
The existing `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` tests in `test-loop-tests/src/tests/max_receipt_size.rs:124-267` are a concrete PoC already present in the codebase:
1. Deploy a test contract.
2. Call a method that builds a promise DAG `A -then-> B`, where `A` creates a further promise `C` and calls `promise_return`, changing the DAG to `C -then-> B`.
3. `C`'s receipt is constructed to be exactly `max_receipt_size` before `output_data_receivers` is attached; attaching it (via `promise_return`) pushes the receipt over `max_receipt_size`.
4. `assert_oversized_receipt_occurred` (`test-loop-tests/src/tests/max_receipt_size.rs:350-429`) then scans the chain and finds a receipt whose actual borsh-encoded size exceeds `max_receipt_size`, confirming the invariant violation is accepted on-chain. pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    pub(super) fn create_action_receipt(
        &mut self,
        input_data_ids: Vec<CryptoHash>,
        receipt_indices: Vec<ReceiptIndex>,
        receiver_id: AccountId,
    ) -> Result<ReceiptIndex, VMLogicError> {
        assert_eq!(input_data_ids.len(), receipt_indices.len());
        for (data_id, receipt_index) in input_data_ids.iter().zip(receipt_indices.into_iter()) {
            self.action_receipts
                .get_mut(receipt_index as usize)
                .ok_or(HostError::InvalidReceiptIndex { receipt_index })?
                .output_data_receivers
                .push(DataReceiver { data_id: *data_id, receiver_id: receiver_id.clone() });
        }

        let new_receipt = ActionReceiptMetadata {
            receiver_id,
            refund_to: None,
            output_data_receivers: vec![],
            input_data_ids,
            actions: vec![],
            is_promise_yield: false,
        };
        let new_receipt_index = self.action_receipts.len() as ReceiptIndex;
        self.action_receipts.push(new_receipt);
        Ok(new_receipt_index)
    }

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
