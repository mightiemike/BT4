### Title
Unbounded `receiver_id` string in `FunctionCallPermission` accepted before AccountId validation - ([File: runtime/runtime/src/action_validation.rs])

### Summary
`FunctionCallPermission.receiver_id` is stored as a plain `String` (not the parsed `AccountId` type), so it carries no length limit at the Borsh/type level. It is only checked against `AccountId` validity rules deep inside action validation, by which point the entire string has already been deserialized as part of the transaction/`AddKey` action.

### Finding Description
`Transaction`'s own `signer_id`/`receiver_id` fields are typed as `AccountId`, which enforces a length cap (`MAX_LEN = 64`) at Borsh-deserialization time [1](#0-0) . However, `FunctionCallPermission::receiver_id`, embedded in an `AddKey` action's `AccessKeyPermission`, is a raw `String`, so it is not subject to that same early length gate. The only place this field's validity is checked is `validate_access_key_permission` in the action-validation pass, which calls `fc.receiver_id.parse::<AccountId>()` on the full string [2](#0-1) . An existing integration test explicitly documents that an oversized `receiver_id` (e.g. `"A".repeat(1024)`) is accepted through deserialization and signing, and only rejected later by this parse/validate step, which walks and truncates the string only for the error message, not before validation [3](#0-2) . Because `receiver_id` has no dedicated size limit (unlike `method_names`, which are separately capped via `max_length_method_name`/`max_number_bytes_method_names` in the same function [4](#0-3) ), the size of the attacker-controlled string reaching `AccountId::parse`/`validate` is bounded only by the overall transaction/receipt size limits (e.g. `max_receipt_size`, general transaction size limits), not by any FunctionCallPermission-specific cap.

This mirrors the reported bug class: a field is validated as a structured identifier (email / account ID) without an early precondition on its size, so the validation routine is invoked on attacker-supplied data whose size is limited only by generic message/transaction size ceilings rather than by a small, purpose-specific bound.

### Impact Explanation
Because `AccountId::validate`/`parse` performs character-by-character scanning proportional to string length, and no length pre-check exists specific to `receiver_id`, a signer can submit an `AddKey` action whose `FunctionCallPermission.receiver_id` is a large string (up to whatever the transaction/receipt size limit permits). This validation runs during transaction admission, block/chunk apply, and re-validation of receipts (`validate_receipt`/`validate_action_receipt` re-invoke the same or similar `AccountId::validate` machinery for every receipt in every chunk) [5](#0-4) . While `AccountId::validate` itself is linear (not exponential/backtracking) based on the code paths inspected, the lack of a tight, dedicated size bound for this specific field is the structural analog of the reported flaw: an identifier-like input is validated without an early, cheap length precondition, unlike sibling fields (`method_names`) that do have such bounds.

### Likelihood Explanation
Reachable directly by any unprivileged transaction signer via a single `AddKey` action containing a `FunctionCallPermission` with an oversized `receiver_id`; no special privileges or node cooperation are required, and the same code path is exercised by the meta-transaction (`DelegateAction`) validation route as well, since it reuses `validate_actions`.

### Recommendation
Add an explicit length pre-check on `FunctionCallPermission.receiver_id` (e.g. cap at `AccountId::MAX_LEN` or a small constant) before invoking `.parse::<AccountId>()`/`AccountId::validate` in `validate_access_key_permission`, mirroring the existing `max_length_method_name` treatment for `method_names`, so the string is rejected on size grounds prior to any character-level validation work.

### Proof of Concept
1. Construct a `TransactionV0`/`TransactionV1` with a single `Action::AddKey` action.
2. Set the access key permission to `AccessKeyPermission::FunctionCall(FunctionCallPermission { allowance: None, receiver_id: "a".repeat(N), method_names: vec![] })` where `N` is large (bounded only by the overall transaction/receipt size limit rather than any `receiver_id`-specific cap) — as already exercised at smaller scale (`N = 1024`) in `test_very_long_account_id` [6](#0-5) .
3. Sign and submit the transaction via RPC; observe that the string is fully deserialized and reaches `validate_access_key_permission`'s `fc.receiver_id.parse::<AccountId>()` call before being rejected, confirming no field-specific size precondition exists ahead of identifier validation [7](#0-6) .

fn validate_access_key_permission(
    limit_config: &LimitConfig,
    permission: &AccessKeyPermission,
) -> Result<(), ActionsValidationError> {
    if let Some(fc) = permission.function_call_permission() {
        // Check whether `receiver_id` is a valid account_id. Historically, we
        // allowed arbitrary strings there!
        match limit_config.account_id_validity_rules_version {
            near_primitives_core::config::AccountIdValidityRulesVersion::V0 => (),
            near_primitives_core::config::AccountIdValidityRulesVersion::V1
            | near_primitives_core::config::AccountIdValidityRulesVersion::V2 => {
                if let Err(_) = fc.receiver_id.parse::<AccountId>() {
                    return Err(ActionsValidationError::InvalidAccountId {
                        account_id: truncate_string(&fc.receiver_id, AccountId::MAX_LEN * 2),
                    });
                }
            }
        }
