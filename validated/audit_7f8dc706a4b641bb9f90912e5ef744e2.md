### Title
Webhook shop identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header not bound to the HMAC signature - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
The reported bug's root cause is that `FaultDisputeGame`/`DisputeGameFactory` binds a bond to `tx.origin` — an unauthenticated identity claim that is decoupled from the actual cryptographically-verified action (`msg.value`/call authorization) — letting an unprivileged party intercept a legitimately-authorized transaction and substitute themselves as the beneficiary. The same class of bug (identity claim decoupled from the signed/verified payload) exists in the webhook verification path of `shopify-api`: the HMAC signature only covers the raw request body, while the shop identity (`X-Shopify-Shop-Domain` header) used for session lookup and app logic is read separately and is never included in the signed data.

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  computes the local HMAC exclusively from `rawBody` and compares it to the `hmac` header value, entirely ignoring every other header, including the domain header: [2](#0-1) 

`validateFactory` in [3](#0-2)  only checks HMAC validity, then separately pulls the shop identity from headers via `checkWebhooksHeaders`/`checkEventsHeaders`, which merely check for the *presence* of the `domain` header — not that it is cryptographically tied to the signed body: [4](#0-3) 

Downstream, `authenticateWebhookFactory` in both `shopify-app-remix` and `shopify-app-react-router` trusts `check.domain` as the shop identity, using it to load/associate the session and admin API client: [5](#0-4) 

Because the domain header is not part of the signed payload, anyone who can produce a body+HMAC pair that is valid for the shared app secret (e.g., because they legitimately received one real webhook delivery for a shop they control) can resend that exact body+HMAC combination directly to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value. The HMAC check will still pass (it only validates the body against the secret), and the app will process the request as if it originated from the spoofed shop.

This mirrors the `tx.origin` issue precisely: the verifiable artifact (HMAC-signed body / bond-funding transaction) is not cryptographically bound to the identity used for accounting (shop domain / `claimant`), so an unprivileged actor can graft a valid proof from one context onto a forged identity claim in another.

### Impact Explanation
Depending on which topic is replayed, an attacker can:
- Forge an `APP_UNINSTALLED` event attributed to a victim shop, which apps typically use to purge stored data/sessions (see `AppInstallations.delete` in [6](#0-5) ), causing denial-of-service against the victim merchant (their offline session/access token deleted without an actual uninstall).
- Inject arbitrary payload data attributed to a victim's shop into the app's business logic (cross-tenant data confusion), since `shop`/`domain` is trusted downstream by webhook handlers for record association.

This is constrained relative to the original finding since exploitation requires the attacker to have obtained at least one legitimate signed webhook body/HMAC pair (e.g., from their own shop's app install) and to know or guess a target shop domain, and is limited to topics whose body content doesn't otherwise leak/require shop-specific secrets. It does not grant arbitrary body forgery — only identity relabeling of an already-signed body.

### Likelihood Explanation
Any merchant/developer capable of installing the app on a shop they control can capture real webhook deliveries with valid signatures (this is not privileged access — any unprivileged store owner can trigger events subscribed by the app). Replaying that request directly at the app's public webhook endpoint with a modified domain header is a simple unauthenticated HTTP request; no MITM, leaked secret, or bypass of TLS is required — matching the "accepted forged Shopify request" / "cross-tenant access" categories.

### Recommendation
Bind the shop identity to the authenticated payload rather than trusting an independent header:
- Extend the HMAC-covered data to include the domain (or otherwise verify that the domain header matches a value obtainable only from Shopify, e.g., cross-check against `topic`+`webhookId`+the app's own webhook subscription registry per shop).
- Alternatively, require replay protection (e.g., single-use `webhookId` tracking) so that any given signed body+HMAC pair can only be processed once, closing off the ability to resubmit a captured payload with an altered domain claim.
- At minimum, document/emit a warning that `domain`/`shop` in `webhooks.validate()`/`authenticate.webhook()` is not itself authenticated by the HMAC and should not be treated as fully trusted without additional binding.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets it deliver a legitimate `APP_UNINSTALLED` (or any subscribed topic) webhook; the attacker's server captures the raw body `B` and the valid `X-Shopify-Hmac-Sha256: H` computed as `HMAC-SHA256(apiSecretKey, B)`.
2. Attacker sends a direct POST to the app's public webhook endpoint (e.g., `/webhooks`) with the same body `B`, the same `hmac: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and (if required) the other topic/webhook-id headers copied verbatim.
3. `validateHmacFromRequestFactory` ( [7](#0-6) ) validates `H` against `B` successfully, since domain is not part of the signed data.
4. `checkWebhooksHeaders` returns `valid: true` with `domain: 'victim.myshopify.com'` ( [8](#0-7) ).
5. `authenticateWebhookFactory` looks up/acts on the victim's session using `check.domain` ( [9](#0-8) ), and — for `APP_UNINSTALLED` handling as implemented in `AppInstallations.delete` — the victim's stored session/access token is deleted, effectively locking the victim out of the app despite never uninstalling it.
