## #Vulnerability found for this question.

### Title
TotalNetWeight/TotalEnergyWeight can permanently drift from the true sum of frozen balances due to non-atomic, per-call raw-division accounting in `FreezeBalanceProcessor.execute` - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java])

### Summary
`FreezeBalanceProcessor.execute` increments `TotalNetWeight`/`TotalEnergyWeight` by `frozenBalance / TRX_PRECISION` on every individual freeze call, instead of computing `floor(newTotalFrozen/TRX_PRECISION) - floor(oldTotalFrozen/TRX_PRECISION)` like `FreezeBalanceV2Processor` and the "new reward" branch of `FreezeBalanceActuator` do. Since `sum(floor(x_i))` can be strictly less than `floor(sum(x_i))` when sub-TRX remainders accumulate across multiple freezes on the same account, an unprivileged attacker can repeatedly call the TVM `freeze` opcode with non-multiple-of-`TRX_PRECISION` amounts to make `TotalNetWeight` permanently under-count relative to the account's actual frozen balance.

### Finding Description
`FreezeBalanceProcessor.validate` only requires `frozenBalance >= TRX_PRECISION`, it does **not** require `frozenBalance` to be an exact multiple of `TRX_PRECISION`: [1](#0-0) 

In `execute`, the total weight is bumped using the *raw* frozen amount of the current call, not a before/after delta of the account's total frozen balance: [2](#0-1) 

Compare this to `FreezeBalanceV2Processor.execute`, which correctly computes the weight contribution as a delta of `floor` values before and after mutating the account's frozen balance: [3](#0-2) 

And compare to the "new reward" branch of the top-level `FreezeBalanceActuator`, which also uses a delta-of-floor computation once `dynamicStore.allowNewReward()` is active: [4](#0-3) 

Because `floor(a) + floor(b)` can be strictly less than `floor(a+b)` (e.g. `floor(1.5) + floor(1.5) = 2 < floor(3.0) = 3`), repeated calls to `FreezeBalanceProcessor.execute` on the same account with amounts that are not exact multiples of `TRX_PRECISION` will under-credit `TotalNetWeight`/`TotalEnergyWeight` relative to the account's true accumulated frozen balance / `TRX_PRECISION`. This entrypoint is reachable by any unprivileged account through the TVM `FREEZE` opcode via `Program.freeze`: [5](#0-4) 

reached from `OperationActions.freezeAction`, gated only by the `allowTvmFreeze` chain parameter being enabled and `allowTvmFreezeV2` not yet enabled (the opcode is a no-op once FreezeV2 activates): [6](#0-5) 

No validate/execute check enforces that `frozenBalance` be a multiple of `TRX_PRECISION`, and no check reconciles the incremental raw addition against the account's actual total frozen balance, so the drift is never corrected. The drift is additionally aggravated when mixed with the top-level `FreezeBalanceActuator`, since that actuator switches to the accurate delta computation once `allowNewReward` is on, while `FreezeBalanceProcessor` (TVM path) never does — creating an asymmetry between the two live code paths that manipulate the same underlying account fields (`setFrozenForBandwidth`/`setFrozenForEnergy`) and the same global counters.

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight` are global, chain-wide state values used to compute bandwidth/energy unit pricing for every account on the network. A drift here silently miscalculates fee/resource pricing for all users, since the divisor used in bandwidth/energy allocation no longer matches the true amount of TRX locked as collateral. This is a public, deterministic-state-divergence bug that affects protocol-level accounting rather than the attacker's own funds.

### Likelihood Explanation
Fully feasible for any unprivileged user: it only requires deploying/calling a contract that repeatedly triggers the `freeze` TVM opcode with non-multiple-of-1,000,000-sun amounts on the same address/resource, which is a normal, permission-less operation once the `allowTvmFreeze` proposal is active (and before `allowTvmFreezeV2` activates, or generally on any chain configuration where the legacy opcode path remains reachable). No special privileges, timing races, or governance access are needed — just multiple ordinary freeze calls.

### Recommendation
Change `FreezeBalanceProcessor.execute` to compute the weight increment the same way `FreezeBalanceV2Processor`/`FreezeBalanceActuator` (new-reward path) do: snapshot `floor(oldFrozenBalance / TRX_PRECISION)` before mutating the account, mutate the frozen balance, then add `floor(newFrozenBalance / TRX_PRECISION) - floor(oldFrozenBalance / TRX_PRECISION)` to `TotalNetWeight`/`TotalEnergyWeight`, mirroring the delegate-resource branch handling as well.

// Pseudocode integration test using FreezeBalanceProcessor directly (or via TVM freeze opcode)

AccountCapsule account = repo.getAccount(ownerAddress);

param1.setOwnerAddress(ownerAddress);

param2.setOwnerAddress(ownerAddress);
param2.setReceiverAddress(ownerAddress);
param2.setResourceType(BANDWIDTH);
param2.setFrozenBalance(1_500_000L); // 1.5 TRX again
new FreezeBalanceProcessor().validate(param2, repo);
new FreezeBalanceProcessor().execute(param2, repo);

long totalNetWeight = repo.getDynamicPropertiesStore().getTotalNetWeight();
long actualFrozen = repo.getAccount(ownerAddress).getFrozenBalance(); // 3,000,000
long trueWeight = actualFrozen / TRX_PRECISION; // = 3

// FAILS: totalNetWeight == 2 (1+1 from two raw-truncated increments)
// but trueWeight == 3 (floor(3,000,000/1,000,000))

    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,

        "freezeFor" + convertResourceToString(resourceType), nonce, null);

    FreezeBalanceParam param = new FreezeBalanceParam();
    param.setOwnerAddress(owner);
    param.setReceiverAddress(receiver);
    boolean needCheckFrozenTime = CommonParameter.getInstance()
        .getCheckFrozenTime() == 1; // for test
    param.setFrozenDuration(needCheckFrozenTime
        ? repository.getDynamicPropertiesStore().getMinFrozenTime() : 0);
    param.setResourceType(parseResourceCode(resourceType));
    try {
      FreezeBalanceProcessor processor = new FreezeBalanceProcessor();
      param.setFrozenBalance(frozenBalance.sValue().longValueExact());
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM Freeze: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM Freeze: frozenBalance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }

  public static void freezeAction(Program program) {
    // after allow vote, check static
    if (VMConfig.allowTvmVote() && program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }
    // 0 as bandwidth, 1 as energy
    DataWord resourceType = program.stackPop();
    DataWord frozenBalance = program.stackPop();
    DataWord receiverAddress = program.stackPop();

    if (VMConfig.allowTvmFreezeV2()) {
      // after v2 activated, we just push zero to stack and do nothing
      program.stackPush(DataWord.ZERO());
    } else {
      boolean result = program.freeze(receiverAddress, frozenBalance, resourceType );
      program.stackPush(result ? DataWord.ONE() : DataWord.ZERO());
    }
    program.step();
  }
