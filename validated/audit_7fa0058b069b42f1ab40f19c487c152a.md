### Title
Missing round-up in calldata/signature/code L2 gas cost calculation causes systematic fee under-collection - (File: crates/blockifier/src/fee/resources.rs)

### Summary
The `ArchivalDataResources::get_calldata_and_signature_gas_cost` and `ArchivalDataResources::get_code_gas_cost` functions compute L1/L2 gas cost by multiplying a `Ratio`-typed per-unit cost by the (attacker-controlled) calldata/signature/code size and calling `.to_integer()` directly, which truncates towards zero (floor), instead of using `.ceil().to_integer()` as is done consistently elsewhere in the same fee-calculation module.

### Finding Description
Throughout `crates/blockifier/src/fee/fee_utils.rs` and `crates/blockifier/src/blockifier_versioned_constants.rs`, every gas/fee unit conversion that scales a `Ratio<u128>` (`ResourceCost`) cost by a usage count is explicitly rounded up, e.g.: [1](#0-0) [2](#0-1) 

However, `ArchivalDataResources::get_calldata_and_signature_gas_cost` and `get_code_gas_cost` — both directly reachable from any submitted transaction (calldata length, signature length, and declared class code size are all sender-controlled) — compute the gas amount via: [3](#0-2) [4](#0-3) 

`Ratio::to_integer()` truncates any fractional remainder rather than rounding up, in contrast to the `.ceil().to_integer()` pattern used for VM resource costs and gas unit conversions elsewhere in the same fee module. This is the sequencer's structural analog of the reported bug class: a fee-relevant multiplication/division that is not consistently rounded in the fee-favorable (round-up) direction, allowing fractional remainders to be silently dropped.

### Impact Explanation
Because `gas_per_data_felt` and `gas_per_code_byte` are configured as `Ratio<u128>` values (allowing fractional gas-per-unit pricing) and are multiplied by attacker-controlled sizes (`extended_calldata_length + signature_length`, `code_size`), any transaction whose resulting product has a nonzero fractional part will have its computed gas amount silently truncated down. This under-counted gas amount flows directly into `receipt.gas` and thus `receipt.fee`, meaning the sender is charged less L1/L2 gas than the true configured cost for every such transaction. As in the original report, each individual truncation is small, but because this applies to essentially all invoke/declare/deploy transactions with any calldata, signature, or code payload, it compounds into a systematic under-collection of fees network-wide (loss of funds relative to the intended fee schedule), and can also be leveraged by an attacker to bias fee estimates or to intentionally choose calldata/signature/code sizes maximizing the truncated fraction per transaction.

### Likelihood Explanation
High likelihood of being exercised: `get_calldata_and_signature_gas_cost` and `get_code_gas_cost` are on the fee-computation path for every Invoke/Declare/DeployAccount transaction that includes calldata, a signature, or declared code — i.e., essentially all transactions. No special privilege is needed; any unprivileged transaction sender determines calldata length, signature length, and code size, and can trivially select sizes that maximize the truncated remainder for `gas_per_data_felt`/`gas_per_code_byte` (when configured as non-integer ratios).

### Recommendation
Change both computations to round up consistently with the rest of the fee module, e.g.:
```rust
let gas_amount = (archival_gas_costs.gas_per_data_felt * total_data_size).ceil().to_integer().into();
```
and similarly for `get_code_gas_cost`, matching the `.ceil().to_integer()` pattern used in `fee_utils::calculate_resource_gas_cost` and `blockifier_versioned_constants.rs`'s gas conversion functions.

### Proof of Concept
1. Configure (or use a network configuration where) `gas_per_data_felt` (or `gas_per_code_byte`) in `VersionedConstants`/`ArchivalDataGasCosts` is a non-integer `Ratio<u128>` (e.g. `Ratio::new(5, 2)` = 2.5 gas/felt).
2. Submit an Invoke transaction with `extended_calldata_length + signature_length` chosen such that `gas_per_data_felt * total_data_size` has a fractional part (e.g. total_data_size = 1 → 2.5, which should round up to 3 but `to_integer()` yields 2).
3. Compare the computed `gas_amount` from `get_calldata_and_signature_gas_cost` against the value obtained by applying `.ceil()` before `.to_integer()`; the current code returns a value 1 unit lower per transaction where the fractional remainder is nonzero, per transaction, causing an under-charge propagated into `receipt.fee`.

Note: I could not verify via `git blame` whether this inconsistency (floor vs. ceil) is intentional by design in the current constants configuration (e.g., if `gas_per_data_felt`/`gas_per_code_byte` are always configured as integers in production versioned-constants JSON files, the bug would be latent/unreachable). This should be confirmed by inspecting the actual versioned-constants JSON files and/or git history for this function before treating it as exploitable in production.
