### Title
`ensure_match_transaction_info` never validates state-checkpoint hashes, letting state-root divergence pass replay/restore verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to verify that a re-executed transaction's output matches the corresponding `TransactionInfo` that is already bound by an accumulator/ledger-info proof. It checks status, gas used, write-set hash, and event-root hash, but — as the code itself documents — it deliberately skips comparing the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields. This is the write-set/proof-conversion analog of the ERC-20 "ignored return value" bug class: a critical correctness signal (state root divergence) is computed but never checked, so a mismatch is silently accepted as a match.

### Finding Description
`ensure_match_transaction_info` performs `ensure!` checks for status, gas, write-set hash vs `state_change_hash`, and event root hash vs `event_root_hash`, but ends with only a comment instead of a check: [1](#0-0) 

The trailing comment explicitly states the gap: [2](#0-1) 

`TransactionInfo` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class, accumulator-hashed fields (part of `TransactionInfoV0`/`V1`, which is what gets hashed into the transaction accumulator leaves and is bound by ledger-info signatures): [3](#0-2) 

These state-checkpoint hashes are the committed representation of the JMT/state-tree root at that version — exactly the kind of "authenticated proof-bearing" value the task scope calls out. `ensure_match_transaction_info` is used by:
- `execution/executor/src/chunk_executor/mod.rs` — chunk/state-sync replay verification (re-executes transactions and compares outputs to the accumulator-verified `TransactionInfo` from a peer/archive chunk).
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` — replay-verify tooling used against archive/mainnet data.

Because the state-checkpoint-hash fields are never compared, a node can locally materialize a state tree whose root differs from the one recorded in the authenticated `TransactionInfo` (e.g. due to a JMT/restore/state-computation bug, or a state root produced under a divergent path such as the in-progress "trading-native" hot-state feature gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), and `ensure_match_transaction_info` will still return `Ok(())`. [4](#0-3) 

### Impact Explanation
This breaks the "committed state must survive executor-to-storage / replay handoff unchanged" and "restore/replay paths must not reinterpret committed data into a different ledger state" invariants called out in the scope. Concretely:
- During chunk-executor-driven state sync/replay, a locally computed state root that diverges from the authenticated on-chain `state_checkpoint_hash` will not be flagged, so a node can silently persist state whose JMT root does not match the canonical committed root while still believing it matches (since the check that should catch this passes vacuously).
- Replay-verify tooling built on the same function (used to detect exactly this class of divergence against archived/mainnet data) can report "successful replay" even when the position/hot-state root has diverged, defeating its purpose as a correctness safety net for hard-fork-causing state bugs.

This is a state-commitment integrity gap: it removes the check that is supposed to detect and stop a wrong state root from being treated as valid, which is squarely in the mainnet-relevant state-integrity gate (wrong state root/proof accepted as valid; hard-fork-only divergence not caught during replay/restore).

### Likelihood Explanation
The gap only manifests when there is already an underlying state-computation/materialization bug (e.g., in JMT restore, hot-state/position-state computation, or sharded total-supply patching) that produces a divergent root — this function does not itself corrupt state, it fails to *detect* corruption. So likelihood of triggering visible impact depends on a second, independent bug elsewhere; however, because this is the single centralized safety-net check reused across three tools (chunk executor, debugger, CLI replay), any latent state-root bug in those adjacent areas becomes silently undetectable rather than caught. The code's own TODO acknowledges the gap is known and currently unaddressed pending the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature.

### Recommendation
Add explicit `ensure!` comparisons in `ensure_match_transaction_info` for `txn_info.state_checkpoint_hash()` (and, where applicable, `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`) against the locally computed values before returning `Ok(())`, mirroring the existing write-set-hash and event-root-hash checks, gated appropriately behind the relevant feature flags so it activates exactly when those checkpoint hashes are populated.

### Proof of Concept
Not applicable as an exploit PoC — this is a detection-gap issue, not an attacker-triggerable state corruption by itself. The "proof" is the code path itself:
1. `ensure_match_transaction_info` computes and checks `write_set_hash` and `event_root_hash` but performs no analogous check for `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, as shown at [5](#0-4) .
2. Any caller (chunk executor replay verification, `aptos-debugger`, CLI replay) that relies solely on this function to validate re-executed output against authenticated `TransactionInfo` will accept a transaction output whose materialized state root differs from the canonical one, as long as write set and events happen to match.

**Verification limitation:** I was unable to retrieve the full body of `execution/executor/src/chunk_executor/mod.rs` around its call to `ensure_match_transaction_info` in this session (tool returned no content on the final read attempt), so I could not confirm whether an additional, separate state-root check exists at that call site that might compensate for this gap. This should be verified directly in the repository before treating the finding as fully confirmed for that specific call site; the gap in `types/src/transaction/mod.rs` itself, however, is directly visible and self-documented in the code.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
