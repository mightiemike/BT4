### Title
`ValidateMultiSign` precompile builds its authorization digest without chain/contract domain separation, enabling cross-chain signature replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile lets any smart contract verify an off-chain signature against an account's on-chain `Permission`. The digest it recomputes to check the signature is `SHA256(address || permissionId || data)` — it contains no chain identifier, network magic, or precompile/contract identity. This mirrors the reported `UniswapV4KEMHook`/`PancakeSwapInfinityKEMHook` flaw where the signed quote digest omitted `chainid`, allowing a signature valid on one deployment to be replayed on another.

### Finding Description
`ValidateMultiSign.execute` decodes `address`, `permissionId`, and `data` from calldata, then builds the digest to check against supplied signatures: [1](#0-0) 

This `hash` is passed to `recoverAddrBySign`, which ECDSA-recovers the signer and checks it against the account's `Permission` keys with weighted threshold logic: [2](#0-1) 

The digest formula `address || permissionId || data` contains nothing that ties the signature to a specific chain (mainnet vs. Nile/Shasta testnet, or any independently operated java-tron-based network/fork), nor to the calling contract's address. TRON account addresses are derived purely from the private key and are identical across every java-tron-based chain; `Permission` objects (keys/threshold) are frequently configured identically across environments by the same operator (e.g., exchange custody wallets, multisig treasuries). Consequently, a signature produced by an off-chain signer to authorize a specific `data` payload (e.g., a withdrawal, quote, or order hash consumed by a smart contract that calls this precompile) carries no domain separator and is valid wherever the same address/permissionId/data triple recurs — exactly the missing-domain-separator issue described in the report for the KEM hooks' quote digest.

### Impact Explanation
Any DApp built on top of `ValidateMultiSign` for permission-gated actions (multisig-authorized withdrawals, trade settlement, custodial approvals) is exposed to cross-chain/cross-deployment replay: a signature obtained for a given `(address, permissionId, data)` on one network can be resubmitted verbatim on another java-tron-compatible network (or reused against another contract that happens to pass the same `data`) to satisfy the same threshold check, since `recoverAddrBySign`/the weight check has no way to detect the digest is contextually reused. This directly enables unauthorized settlement/authorization actions on the reused chain — a concrete auth/replay impact for exchange, custody, and market contracts that use this precompile as their signature-checking primitive, matching the report's "unintended trades/actions execute without the signer's intention."

### Likelihood Explanation
Exploitability requires: (1) the same account/private key and identical `Permission` configuration existing on two java-tron-based networks/environments (common for exchange custody wallets and DAO/multisig treasuries deployed consistently across mainnet/testnet or forked chains), and (2) an off-chain signer producing a signature intended for a single deployment. Both conditions are realistic operational patterns for TRON-ecosystem custodial/multisig products, making this a medium-likelihood, unprivileged-user-triggerable issue (the precompile is callable by any contract/account, no privileged role required).

### Recommendation
Fold a domain separator into the `ValidateMultiSign` (and `BatchValidateSign`) digest — at minimum the chain ID (`CommonParameter`/genesis block hash already tracked by java-tron) and ideally the calling contract address — before hashing, e.g. `hash = SHA256(chainId || callingContract || address || permissionId || data)`. Document this domain-binding requirement clearly for DApp developers relying on this precompile so they don't independently need to add their own separator, and consider making it consensus-gated as an activation feature (similar to other TIP-gated precompile behavior changes already present in this file, e.g. `VMConfig.allowTvmOsaka()`).

### Proof of Concept
1. Deploy identical account address `A` (same private key) with the same `Permission` (`permissionId`, threshold, keys) on two java-tron-based networks, Chain-1 and Chain-2 (e.g., mainnet and a permissioned/forked deployment, or two independently run testnets sharing the same seed accounts).
2. An operator/signer produces a signature intended for use only on Chain-1, authorizing `data = D` (e.g., a withdrawal payload) for `address = A`, `permissionId = P`. The digest signed is `SHA256(A || P || D)` per `PrecompiledContracts.java:1062-1064`.
3. On Chain-1, a contract calls `ValidateMultiSign(A, P, D, [sig])`; the precompile recovers the signer, matches weight ≥ threshold, and the contract proceeds with the authorized action.
4. An attacker observes this signature (e.g., from a public mempool/broadcast tx on Chain-1) and resubmits the same `(A, P, D, [sig])` calldata to an equivalent contract deployed on Chain-2. Because the digest formula is identical and contains no chain/contract-specific salt, `recoverAddrBySign` again recovers the same signer address and the weight check passes, causing the action to execute on Chain-2 without the signer's intent for that chain — the cross-chain replay scenario analogous to the reported KEM hook digest issue.
