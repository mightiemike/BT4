The strongest nearcore analog to this bug class is in the reward-distribution loop of `update_validator_accounts`, which behaves like an "all-or-nothing" batch operation over a `HashMap` of accounts (validators + protocol treasury) — exactly the same batching pattern that let a single "malicious" (in this case, missing) entry in a reward list block the entire operation and corrupt state, except in nearcore the failure mode is worse: it halts every node applying the chunk rather than merely reverting a transfer.

### Root cause

`Runtime::update_validator_accounts` iterates over `validator_accounts_update.stake_info` to add rewards/return stake, then separately credits the protocol treasury account: [1](#0-0) 

If the protocol treasury account does not exist in state at the time its per-epoch reward is due, `get_account(...).ok_or_else(...)` returns `StorageError::StorageInconsistentState`, which is wrapped into `RuntimeError::StorageError`.

Any account holder can permissionlessly delete their own account via a normal `DeleteAccount` action as long as they have zero locked stake — the protocol treasury account is an ordinary account and is not staked, so this is a fully unprivileged, single-signer transaction path (`action_delete_account`): [2](#0-1) 

The protocol treasury is guaranteed a non-zero reward each epoch under standard `protocol_reward_rate` (documented in the economics spec): "the protocol treasury account gets its reward if it did not already receive one as a validator" every epoch boundary. [3](#0-2) 

Once `RuntimeError::StorageError(StorageError::StorageInconsistentState(..))` propagates up to `apply_chunk`, it is not one of the two tolerated storage errors (`FlatStorageBlockNotSupported`, `MissingTrieValue`) and hits the fallback panic: [4](#0-3) 

Because every honest validator applies the same chunk deterministically, this panic is reproduced on every node that tries to apply the epoch-boundary block, which is a **transaction-triggered halt** of the entire chain — a strict superset in severity of the original "reward token blocks legitimate claims" bug (there, only the solver's individual claim was blocked; here, the whole network can be frozen).

### Title
Deleting the protocol treasury account before an epoch boundary causes a deterministic node panic / chain halt on reward distribution — ([File: runtime/runtime/src/lib.rs])

### Summary
`update_validator_accounts` treats the presence of the protocol treasury account in state as an unconditional invariant when crediting its per-epoch reward. An unprivileged transaction signer who controls the account configured as `protocol_treasury_account` can delete that account with an ordinary `DeleteAccount` action (allowed because the account is unstaked). At the next epoch boundary, when the guaranteed treasury reward is due, `get_account` returns `None`, and the code turns this into `StorageError::StorageInconsistentState` instead of a recoverable `ActionError`. This error is not one of the storage errors nearcore tolerates in `apply_chunk`, so it triggers a `panic!` on every node applying that chunk, halting the chain.

### Finding Description
Reward crediting for validators and the protocol treasury is implemented as a single pass that is expected to succeed for every entry (`runtime/runtime/src/lib.rs:1717-1835`). The per-validator loop has an explicit "defense in depth" comment acknowledging that an uninitialized/missing validator account is a possible edge case and handles it, but the treasury branch (`lib.rs:1807-1834`) has no such handling — it unconditionally assumes the treasury account exists and unconditionally assumes a reward entry exists for it, using `.ok_or_else(|| StorageError::StorageInconsistentState(...))?` in both cases. [5](#0-4) 

`StorageInconsistentState` is nearcore's designated "should never happen" error class; call sites outside the tolerant `Db`/`FlatStorage` recovery paths panic on it rather than gracefully rejecting the block: [4](#0-3) 

The precondition — the treasury account no longer existing — is trivially reachable: any signer controlling the treasury account can submit a `DeleteAccount` action against their own account, which is permitted as long as the account has zero locked stake, which is normally true for a treasury account: [6](#0-5) 

### Impact Explanation
This is a chain halt reachable from a single ordinary transaction, deterministically reproduced by every node validating the chunk (not a per-node liveness bug), making it Critical/High: it is a stronger, network-wide version of the reported bug's "legitimate claim gets permanently blocked" pattern — instead of one solver losing a reward, the entire network stops producing/validating blocks at the next epoch boundary.

### Likelihood Explanation
Medium-to-high: it requires only that the account named as `protocol_treasury_account` in genesis be deletable by its owner (no special stake, no validator role, no multi-party coordination) and for a normal `DeleteAccount` transaction to land before the next epoch boundary. The economics of mainnet make the treasury account attractive/likely to be a normal, non-staking account, satisfying the precondition without any additional setup.

### Recommendation
Treat a missing protocol treasury account (and a missing reward-map entry for it) as a recoverable condition rather than a fatal invariant violation — e.g., skip crediting silently (mirroring the "uninitialized account" defense-in-depth branch already present for validators) or explicitly disallow deletion of the configured protocol treasury account, instead of returning `StorageError::StorageInconsistentState` that upstream code paths turn into a panic.

### Proof of Concept
1. Identify the account configured as `protocol_treasury_account` in genesis (e.g. `near` account, `protocol_reward_rate > 0`).
2. From that account, submit an ordinary `DeleteAccount` action to itself; this succeeds because the account is unstaked (`runtime/runtime/src/actions.rs:330-405`, no `DeleteAccountStaking` error).
3. Wait for the next epoch boundary block. `EpochManager::calculate_reward` computes a non-zero `protocol_treasury_reward` per the standard reward split, and `update_validator_accounts` is invoked with `protocol_treasury_account_id` set and a non-empty `validator_rewards` entry for it.
4. Because the account no longer exists, `get_account(state_update, account_id)?.ok_or_else(...)` returns `Err(StorageError::StorageInconsistentState(...))` (`runtime/runtime/src/lib.rs:1810-1815`).
5. This propagates to `apply_chunk`, which panics rather than gracefully failing (`chain/chain/src/runtime/mod.rs:1296-1301`), causing every node applying this chunk to crash — halting the chain.
