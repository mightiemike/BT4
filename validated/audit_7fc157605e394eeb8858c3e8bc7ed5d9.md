### Title
Outbound-disabled check runs after PRC20/UEA-side execution already burned/moved the withdrawn asset, permanently orphaning funds with no outbound and no revert path - (File: `x/uexecutor/keeper/create_outbound.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/evm_hooks.go`)

### Summary
This mirrors the reported bug class: a state machine (`SessionManager`) is allowed to progress irreversibly (`Concluded`) even though a prerequisite configuration (`rankedRewards`/`numberOfWinners`) was never set, so funds become permanently unclaimable. On Push Chain, the analogous invariant lives in the `UniversalTx` (UTX) lifecycle: an EVM-side state change (a `UniversalTxOutbound` event, i.e. a user's UEA/CEA payload calling `UniversalGatewayPC` to withdraw a PRC20/native asset) is allowed to execute and commit to state **before** `IsChainOutboundEnabled` is checked. If the destination chain has outbound disabled, `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:49-57`) rejects with `"outbound is disabled for chain %s"`, but by that point the EVM call that emitted the event (and, on the Solidity side of `UniversalGatewayPC`, presumably burned/locked the PRC20 as part of emitting `UniversalTxOutbound`) has already run inside the same already-committed PC transaction. The caller only records `utx.RevertError`, it does not roll back the EVM state or reconstruct the withdrawn funds.

### Finding Description
The check for `IsChainOutboundEnabled` is a *late* validation gate, analogous to `FixedRanksReward`'s `Created`-state gate being checked at configuration time but never enforced at the point of irreversible state transition (`startAndRevealGameQuestion`).

Concretely:
- `k.Keeper.ExecuteInboundFundsAndPayload` (and the `ExecuteInboundGasAndPayload` sibling) executes the user's payload via `ExecutePayloadV2` / `CallUEAExecutePayload`, which runs the full EVM call including any withdraw/burn logic inside `UniversalGatewayPC`, and marks the PCTx `SUCCESS` (`x/uexecutor/keeper/execute_inbound_funds_and_payload.go:290-317`).
- Only *after* that commit does the code call `k.AttachOutboundsToExistingUniversalTx(sdkCtx, receipt, utx)` (line 318), which internally calls `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:16-57`).
- `BuildOutboundsFromReceipt` checks `k.uregistryKeeper.IsChainOutboundEnabled(ctx, event.ChainId)` and, if disabled, returns an error instead of an `OutboundTx`.
- Back in the caller, that error is swallowed into `utx.RevertError` only (`execute_inbound_funds_and_payload.go:318-325`) — **no outbound is attached, no revert/refund is issued, and the already-executed EVM state (the withdraw/burn side effects inside the payload's UEA call) is not rolled back** because it occurred inside the already-committed `receipt`/PCTx scope, not inside the `CacheContext` that only wraps fee deduction.
- The same pattern exists in the raw EVM-hook path `EVMHooks.PostTxProcessing` → `CreateUniversalTxFromReceiptIfOutbound` → `BuildOutboundsFromReceipt`, confirmed by the test `"outbound disabled returns error"` (`test/integration/uexecutor/evm_hooks_and_outbound_test.go:576-627`), which shows the hook returns an error but does not demonstrate any compensating rollback of the emitted-log's EVM side effects.

The result is structurally identical to the external report: a prerequisite condition (`outboundEnabled`) is validated only at a downstream step, after an earlier, irreversible action (the EVM withdraw/burn call) has already taken effect, and the failure path has no way to reconstruct the lost value — the `UniversalTx` never gets an `OutboundTx` entry (so `PendingOutbounds` never sees it and UVs never observe/broadcast anything), and there is no automatic re-mint of the burned asset the way `handleFailedOutbound` re-mints funds when an already-created outbound *later* fails on the destination chain.

### Impact Explanation
If the destination-chain outbound is (or becomes) disabled between vote finalization and PC-side payload execution — e.g. an admin disables a chain for maintenance/incident response while an inbound is already mid-flight and executing its payload — a user's synthetic asset gets withdrawn/burned on Push Chain as part of the payload call, but the corresponding cross-chain outbound is never created and no PRC20/native re-mint occurs. This is a permanent, unrecoverable loss of user funds recorded only as an opaque `RevertError` string on the UTX, with no `OutboundTx`, no `PendingOutbounds` entry, and none of the existing recovery paths (`AttachRescueOutboundFromReceipt`'s rescue eligibility logic explicitly requires either a failed CEA deposit or a `REVERTED` `INBOUND_REVERT` outbound — neither condition is met here, since the deposit succeeded and no outbound was ever created) can reach it.

### Likelihood Explanation
This requires an unprivileged user's ordinary in-flight cross-chain payload (a `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbound whose payload calls `UniversalGatewayPC` to trigger an outbound) to race against an admin toggling `IsOutboundEnabled` for the destination chain, which is plausible during routine chain-config maintenance rather than attacker-controlled alone. I was not able to fully verify from the indexed code whether `UniversalGatewayPC`'s Solidity implementation actually burns/locks the withdrawn PRC20 *before* emitting `UniversalTxOutbound` (that contract source was not available in this index), which is the crux of whether funds are truly unrecoverable versus merely "outbound event dropped with tokens still sitting at their pre-withdraw location." This should be confirmed against the `UniversalGatewayPC` Solidity source before treating this as a certain fund-loss bug rather than an availability/bookkeeping gap.

### Recommendation
- Move the `IsChainOutboundEnabled` (and token-config) check to happen *before* invoking the EVM call that can emit `UniversalTxOutbound`, ideally inside `UniversalGatewayPC` itself (reject the withdraw call at the Solidity level, or gate it via a precompile check) so the burn/withdraw and the outbound-enabled check are atomic.
- Alternatively, wrap the entire payload execution + outbound-attach sequence in a single `CacheContext` (mirroring the existing fee-deduction pattern), and only `writeCache()` after `BuildOutboundsFromReceipt` succeeds — so a disabled-outbound rejection rolls back the withdraw/burn side effects together with the payload call.
- If rollback isn't feasible (e.g. the disabled check must remain post-hoc), add an automatic re-mint/refund path when `BuildOutboundsFromReceipt` fails with "outbound is disabled", equivalent to `handleFailedOutbound`'s re-mint logic, instead of only recording `RevertError`.

### Proof of Concept
Conceptual reproduction (mirrors `test/integration/uexecutor/evm_hooks_and_outbound_test.go:576-627` and `execute_inbound_funds_and_payload.go:187-206,318-325`):
1. Register chain `eip155:X` with `IsOutboundEnabled: true` and a token config whose `NativeRepresentation` is a PRC20.
2. Submit and finalize (via UV quorum) a `FUNDS_AND_PAYLOAD` inbound whose `UniversalPayload` calls the UEA, which in turn calls `UniversalGatewayPC`'s withdraw method for `eip155:X`, minting a `UniversalTxOutbound` log.
3. Before/at execution time, have `IsOutboundEnabled` for `eip155:X` be `false` (as in `evm_hooks_and_outbound_test.go:576-627`, or via a chain config update).
4. Observe: `ExecutePayloadV2` succeeds and its PCTx is recorded `SUCCESS`; `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt` returns `"outbound is disabled for chain eip155:X"`; `utx.RevertError` is set; `utx.OutboundTx` remains empty.
5. Query the UTX: no `OutboundTx` entry exists, `PendingOutbounds` has no entry, and `AttachRescueOutboundFromReceipt`'s eligibility check rejects any rescue attempt because the CEA deposit succeeded / there's no `REVERTED INBOUND_REVERT` outbound — leaving the withdrawn value with no recorded recovery path. // AttachRescueOutboundFromReceipt scans the receipt for RescueFundsOnSourceChain events
// emitted by UniversalGatewayPC and, for each one found, attaches a RESCUE_FUNDS outbound
// to the original UTX referenced by the event's universalTxId.
//
// Unlike normal outbounds (which create a new UTX), rescue outbounds are appended to the
// already-existing UTX whose funds are stuck on the source chain.
func (k Keeper) AttachRescueOutboundFromReceipt(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalGatewayPC := strings.ToLower(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_GATEWAY_PC"].Address)

	evmChainID, err := utils.ExtractEvmChainID(ctx.ChainID())
	if err != nil {
		return fmt.Errorf("rescue: failed to extract EVM chain ID: %w", err)
	}
	pushChainCaip := fmt.Sprintf("eip155:%s", evmChainID)

	for _, lg := range receipt.Logs {
		if lg.Removed {
			continue
		}
		if strings.ToLower(lg.Address) != universalGatewayPC {
			continue
		}
		if len(lg.Topics) == 0 {
			continue
		}
		if strings.ToLower(lg.Topics[0]) != strings.ToLower(types.RescueFundsOnSourceChainEventSig) {
			continue
		}

		event, err := types.DecodeRescueFundsOnSourceChainFromLog(lg)
		if err != nil {
			return fmt.Errorf("failed to decode RescueFundsOnSourceChain: %w", err)
		}

		// The universalTxId in the event is a 0x-prefixed bytes32 matching our UTX key.
		originalUtxId := strings.TrimPrefix(event.UniversalTxId, "0x")

		originalUtx, found, err := k.GetUniversalTx(ctx, originalUtxId)
		if err != nil {
			return fmt.Errorf("rescue: failed to fetch UTX %s: %w", originalUtxId, err)
		}
		if !found {
			return fmt.Errorf("rescue: original UTX %s not found", originalUtxId)
		}
		if originalUtx.InboundTx == nil {
			return fmt.Errorf("rescue: UTX %s has no inbound tx", originalUtxId)
		}

		// Rescue eligibility differs by inbound type:
		//
		//  CEA inbounds: the deposit (first PCTx) must have failed, meaning the funds
		//  never arrived on Push Chain and are still locked on the source chain.
		//
		//  Non-CEA inbounds: the auto-generated INBOUND_REVERT outbound must exist and
		//  have reached REVERTED status, meaning TSS could not return the funds to the
		//  source chain and they are stuck (held by the gateway contract or in escrow).
		if originalUtx.InboundTx.IsCEA {
			if len(originalUtx.PcTx) == 0 || originalUtx.PcTx[0] == nil || originalUtx.PcTx[0].Status != "FAILED" {
				return fmt.Errorf("rescue: UTX %s CEA deposit did not fail", originalUtxId)
			}
		} else {
			hasRevertedAutoRevert := false
			for _, ob := range originalUtx.OutboundTx {
				if ob != nil && ob.TxType == types.TxType_INBOUND_REVERT && ob.OutboundStatus == types.Status_REVERTED {
					hasRevertedAutoRevert = true
					break
				}
			}
			if !hasRevertedAutoRevert {
				return fmt.Errorf("rescue: UTX %s has no reverted inbound-revert outbound", originalUtxId)
			}
		}
