### Title
Response cache key omits `WorkflowID`, allowing cross-workflow HTTP response cache poisoning - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The `responseCache` used by `gatewayHandler.makeOutgoingRequest` keys cache entries solely on `req.Hash()`, and the `Hash()` implementation is explicitly documented and unit-tested to **exclude `WorkflowID`**, contradicting the README's claim ("Cache Key: Generated from workflow ID and request hash" / "Workflow Isolation: Cache entries are scoped by workflow ID"). Any attacker-owned workflow that issues an `OutboundHTTPRequest` with the same Method/URL/Headers/Body as a target/victim workflow's request will read from and write to the exact same cache slot, enabling cross-workflow (not just within-workflow) cache poisoning.

### Finding Description
`gatewayHandler.makeOutgoingRequest` (`core/services/gateway/handlers/capabilities/v2/http_handler.go:395-446`) parses an `OutboundHTTPRequest` sent by a DON node and, when `CacheSettings.MaxAgeMs > 0`, calls: [1](#0-0) 

`responseCache.Fetch` and `Set` both use `req.Hash()` alone as the map key: [2](#0-1) [3](#0-2) 

The unit test `TestRequestHash` explicitly proves that `WorkflowID` is **not** part of the hash input, i.e., two requests differing only in `WorkflowID` produce the identical cache key: [4](#0-3) 

This directly contradicts the documented invariant in the module's own README: [5](#0-4) 

Because caching is not workflow-scoped, any user who can deploy/own a workflow on the same DON (an ordinary, unprivileged action — no node-operator or admin privilege required) can craft a workflow that issues an `OutboundHTTPRequest` with `CacheSettings.Store=true` and `Method`/`URL`/`Headers`/`Body` matching a value they expect (or can observe/guess, e.g., a commonly used public API endpoint or a URL disclosed in shared/public workflow metadata) that a victim workflow will also request. If the attacker's request reaches the endpoint first (or the endpoint is attacker-controlled/attacker-influenced, e.g., via race conditions, DNS/redirect timing, or a shared third-party API the attacker also controls a response path for), the attacker's response gets cached under a key that the victim's subsequent identical request will also hash to and retrieve via `responseCache.Fetch` (`http_handler.go:427`), because `isExpiredOrNotCached` and `Fetch` never check `WorkflowID`.

No authz, replay, or namespace check exists to prevent this: `makeOutgoingRequest` performs no per-workflow cache-key derivation, `HandleNodeMessage` only enforces per-node/global rate limits (`http_handler.go:239-246`), which do not prevent a different, unrelated workflow from colliding on cache keys.

Regarding the specific sub-hypothesis in the question (Headers vs MultiHeaders collision while URL+Body match, within the *same* workflow) — the actual `Hash()` implementation lives in the external `chainlink-common` module and is not present in this repo's index, so I cannot confirm or deny whether `MultiHeaders` is separately captured from `Headers` in the hash computation. This narrower claim is **unverified**. However, the broader and confirmed defect — complete omission of `WorkflowID` from the cache key — independently satisfies and exceeds the scoped impact described (cross-request/cross-workflow cache poisoning), and is directly provable from existing test code.

### Impact Explanation
An attacker with an ordinary (unprivileged) workflow deployed to the same DON can poison the shared HTTP response cache for any other workflow that happens to issue a request with identical Method/URL/Headers/Body, causing that victim workflow to execute business logic on attacker-influenced HTTP response data. This is a workflow-execution-on-tampered-data issue (misreporting/data tampering impact class), scoped to the HTTP action capability's outbound cache.

### Likelihood Explanation
Feasibility depends on: (1) attacker being able to deploy/run a workflow on the same DON (ordinary user capability, not requiring compromise), (2) attacker being able to predict or influence a URL+Method+Headers+Body combination that a victim workflow also uses, and (3) getting an attacker-favorable response cached before the victim's fetch. Precondition (2)/(3) require some target knowledge/timing, making this a moderate-likelihood, workflow-configuration-dependent issue rather than trivially exploitable against arbitrary victims, but the root cause (missing `WorkflowID` in the cache key) is unconditionally present and testable.

### Recommendation
Include `WorkflowID` (and ideally `WorkflowOwner`, consistent with the existing hash design) as part of the cache map key — either by prefixing `req.Hash()` with `req.WorkflowID` when indexing `rc.cache` (e.g., `key := req.WorkflowID + ":" + req.Hash()`), or by updating `OutboundHTTPRequest.Hash()` in `chainlink-common` to include `WorkflowID` in its digest. Add/restore a unit test asserting that identical requests with different `WorkflowID` produce different cache keys/lookups (the current test at `response_cache_test.go:139-149` asserts the opposite and should be corrected to reflect the intended workflow-isolation invariant from the README).

### Proof of Concept
Extend `response_cache_test.go`:
1. Build two `OutboundHTTPRequest`s identical in Method/URL/Headers/Body but with `WorkflowID = "victim-workflow"` vs `WorkflowID = "attacker-workflow"`, both with `CacheSettings.Store = true` and `MaxAgeMs > 0`.
2. Call `responseCache.Set` for the attacker request with a fabricated malicious `OutboundHTTPResponse` (e.g., status 200, attacker-chosen body).
3. Call `responseCache.Fetch` for the victim request with a `fetchFn` that would return a distinct legitimate response.
4. Assert (current buggy behavior) that `Fetch` returns the attacker's cached response instead of invoking `fetchFn` — proving cross-workflow poisoning.
5. After applying the fix (key including `WorkflowID`), assert `Fetch` invokes `fetchFn` and returns the legitimate response, unaffected by the attacker's cache entry.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
