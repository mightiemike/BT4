### Title
Dynamic energy factor decay/increase is dependent on the call frequency that triggers cycle catch-up, causing inconsistent energy pricing - (File: chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java)

### Summary
`ContractStateCapsule::catchUpToCycle()` implements the "dynamic energy" pricing mechanism used by the TVM to penalize/relax energy cost for heavily-used contracts [1](#0-0) . The factor is incremented once per cycle when usage exceeds a threshold, and decreased using `pow(1 - increaseFactor/DECREASE_DIVISION/precision, cycleCount)` for the number of elapsed cycles since the last update [2](#0-1) . Because `getUpdateCycle()`/`lastCycle` is only advanced when a transaction actually invokes the contract (via `Program.updateContextContractFactor()` → `VM.play()`), the effective compounding path taken by the factor depends on exactly when and how often calls land relative to cycle boundaries [3](#0-2) .

### Finding Description
The increase step is a single per-cycle multiplicative bump applied only if usage in the immediately preceding tracked cycle exceeded `threshold`, then the code jumps straight to computing a decrease for `cycleCount = newCycle - lastCycle` using a `pow()` decay applied as if decay were continuous over the full gap [4](#0-3) . This mixes two different compounding models in one function: a single discrete "increase" event based on only the most-recently observed usage snapshot, followed by exponential decay based on the raw cycle gap. If a contract is called frequently (once per cycle), each cycle's usage is checked and the increase/decrease path is re-evaluated every cycle, matching intended behavior. But if calls are sparse (skipping several cycles), the code only ever sees the last cycle's `getEnergyUsage()` value at the moment `catchUpToCycle` finally executes, so multiple cycles of heavy usage that occurred in between are invisible to the increase branch — only whatever usage happens to be recorded when catch-up finally executes is used to decide whether to bump the factor, while the decay is nonetheless applied for the entire elapsed span. This is directly analogous to the reported issue: the resulting `EnergyFactor` (effectively an APY-like multiplier on energy price) differs depending on how frequently the contract's catch-up path is invoked, rather than being a deterministic function of true historical usage.

### Impact Explanation
Since `EnergyFactor` directly scales TVM energy cost per opcode when `allowDynamicEnergy` is enabled (`VM.play()` multiplies `energy` by `factor`) [5](#0-4) , an attacker/contract owner can manipulate the observed compounding path (by choosing exactly when transactions land relative to maintenance cycles) to keep the dynamic-energy penalty artificially low despite sustained high usage, or conversely to cause inconsistent/unfair energy pricing across otherwise-identical usage patterns. This is an economic/resource-accounting correctness issue reachable purely via ordinary broadcast transactions calling the contract (no privileged actor needed), fitting the "resource and reward accounting" / "TVM execution and energy metering" category.

### Likelihood Explanation
Likelihood is moderate: exploiting this requires precise timing of transactions relative to `currentCycleNumber` maintenance boundaries, which is observable on-chain, so a sophisticated caller/contract deployer could deliberately schedule their own calls (or a bot swarm) to minimize the recorded snapshot usage right at catch-up time while still consuming high energy in between cycles that are never checked at their true usage level.

### Recommendation
Track cumulative/per-cycle usage independent of when catch-up executes (e.g., persist per-cycle usage snapshots rather than only the "current" `energyUsage`, or checkpoint usage at cycle boundaries via the maintenance manager rather than lazily on the next contract call), so that the increase/decrease factor computed in `catchUpToCycle()` is invariant to the specific frequency/timing of calls that happen to trigger the catch-up logic.

### Proof of Concept
Not independently verifiable without running a full node/test harness against `catchUpToCycle` under different call-timing schedules; this assessment is based on static analysis of `ContractStateCapsule::catchUpToCycle()` and its usage from `VM.play()`/`Program.updateContextContractFactor()`. Confidence is moderate — the exact conditions needed to produce an economically meaningful factor discrepancy (specific `threshold`, `increaseFactor`, `maxFactor` values) were not verified through execution.

  public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }

    // No need to decrease
    long cycleCount = newCycle - lastCycle;
    if (cycleCount <= 0) {
      return true;
    }

    // Calc the decrease percent (decrease factor [75% ~ 100%])
    double decreasePercent = pow(
        1 - (double) increaseFactor / DYNAMIC_ENERGY_DECREASE_DIVISION / precisionFactor,
        cycleCount, useStrictMath
    );

    // Decrease to this cycle
    // (If long time no tx and factor is 100%,
    //  we just calc it again and result factor is still 100%.
    //  That means we merge this special case to normal cases)
    this.contractState = ContractState.newBuilder()
        .setUpdateCycle(newCycle)
        .setEnergyFactor(max(
            0,
            (long) ((getEnergyFactor() + precisionFactor) * decreasePercent) - precisionFactor,
            disableMath))
        .build();
