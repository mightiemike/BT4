### Title
External initiator credentials can trigger job runs for arbitrary jobs via integer job ID, bypassing intended EI/webhook restriction - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` in addition to `SessionExternalInitiatorKey`, so any check based on `auth.GetAuthenticatedUser(c)` cannot distinguish a real session/token user from an external-initiator-authenticated request. `PipelineRunsController.Create` uses exactly this ambiguous check (`isUser, ok := auth.GetAuthenticatedUser(c)`) to gate the "run job by int32 ID" code path, with a comment claiming "EIs not allowed" — but the check does not actually enforce that. As a result, a caller authenticated only via EI access-key/secret headers can call `RunJobV2` for any integer job ID, not just a job bound to their own external initiator.

### Finding Description
The `userOrEI` router group in `core/web/router.go` wires `POST /v2/jobs/:ID/runs` behind `auth.Authenticate` with `AuthenticateExternalInitiator`, `AuthenticateByToken`, and `AuthenticateBySession` as alternative auth methods, guarded by `auth.RequiresRunRole(prc.Create)`: [1](#0-0) 

In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` authenticates the EI token, then sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` (to a synthetic run-role user) in the gin context: [2](#0-1) 

In `PipelineRunsController.Create`, the handler branches on `isUser, ok := auth.GetAuthenticatedUser(c)` to decide whether integer job IDs may be run, with a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed": [3](#0-2) 

However, `auth.GetAuthenticatedUser` simply reads `SessionUserKey` from context: [4](#0-3) 

Since `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for EI-authenticated requests exactly the same as for real session/token users. The intended gate ("EIs not allowed" for int-ID runs) is not actually enforced by this code — the comment describes behavior that the implementation does not provide. Consequently, an EI-authenticated caller reaches `prc.App.RunJobV2(ctx, jobID, nil)` for any parseable `int32` job ID with no check that the job is bound to (or was created for) that specific external initiator.

Separately, the UUID-based path (which historically mapped to the webhook job's `externalJobID`, the mechanism that ties a job to a specific EI) is now unconditionally rejected because webhook job creation/execution by external UUID has been removed (`job.ErrJobTypeRemoved`), as shown by `TestPipelineRunsController_RunExistingWebhookJobRejected` and `TestRunner_WebhookJobRemoved`: [5](#0-4) [6](#0-5) 

This means the only functioning "run by ID" path left for EI-authenticated requests is the integer-ID path — which is exactly the path whose ownership check is broken.

### Impact Explanation
An attacker who can create an external initiator (requires edit role) or otherwise obtains any valid EI access key/secret can call `POST /v2/jobs/<any_int_job_ID>/runs` and trigger `RunJobV2` for jobs that have nothing to do with their EI. This breaks the job-ownership binding invariant for external-initiator-authenticated requests and allows unauthorized triggering of arbitrary pipeline jobs (including privileged tasks configured by other integrations/webhooks), which matches "unauthorized workflow execution" bounty impact.

### Likelihood Explanation
Requires the attacker to possess valid EI access-key/secret headers (via edit-role EI creation or another leak vector, per the question's stated precondition). Given that, the exploit is a single unauthenticated-looking HTTP POST with EI headers and an arbitrary integer job ID — fully repeatable and requires no other privilege, since the `RequiresRunRole` check also passes trivially (EI is assigned `UserRoleRun`).

### Recommendation
Distinguish EI-authenticated requests from real user-authenticated requests explicitly (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` presence rather than relying on `GetAuthenticatedUser`), and reinstate an explicit binding check that ties an EI's allowed run targets to jobs actually associated with that initiator (e.g., via the job's configured external initiator name/URL) before calling `RunJobV2`. At minimum, `PipelineRunsController.Create`'s int-ID branch should reject requests where `GetAuthenticatedExternalInitiator(c)` returns ok, matching the stated intent in the code comment.

### Proof of Concept
Integration test outline:
1. Create two jobs, JobA and JobB (or one job JobA and any arbitrary int-ID job JobB not associated with any EI).
2. Create external initiator EI-A via `POST /v2/external_initiators` (`cltest.CreateExternalInitiatorViaWeb`), obtaining `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<JobB.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-A's credentials, and assert the response is `200 OK` and a `pipeline_runs` row is created for JobB — despite EI-A having no relationship to JobB.
4. Contrast with the intended behavior: assert the request should have been rejected (e.g., `401`/`403`) since EI-A is not authorized to trigger runs for JobB.

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
