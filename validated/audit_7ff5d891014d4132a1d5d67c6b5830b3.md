### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify to accept a divergent authenticated state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (chunk executor replay, `db-tool`'s `replay_on_archive`, `aptos-debugger`, and the Move CLI's local simulation/verification commands) to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed to the ledger/accumulator. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [1](#0-0) .

### Finding Description
`TransactionInfo` (both `V0` and `V1`) carries `state_checkpoint_hash` and, in `V1`, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` — these are the authenticated Merkle/state-summary roots that get folded into the transaction accumulator and hence into the block's `LedgerInfo` root hash [2](#0-1) . These roots are exactly the "proof-bearing" ledger state that mainnet consensus/verifiers rely on.

`ensure_match_transaction_info` is the single audited comparison point that is supposed to guarantee "the transaction output computed locally reproduces the same committed state as recorded on-chain." It validates `status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash`, but the developers' own comment acknowledges the checkpoint hashes are left unchecked:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

The `compute_trading_native_state_roots` flag it references is not a speculative/future flag — it is a live per-block/on-chain-config-driven boolean already wired through the execution pipeline: it's read in `execution/executor/src/block_executor/mod.rs` to decide whether to construct `ProvablePositionStateSummary` during state checkpointing [4](#0-3) , and it's a field threaded through `ExecutionOutput`/`BlockExecutorConfigFromOnchain` and `DoGetExecutionOutput`. This means the position-state / "trading native" checkpoint hash is already an active, authenticated part of `TransactionInfoV1` (`position_state_checkpoint_hash`) once this on-chain config is turned on, but the verification helper that all replay/verify tooling calls does not check it.

`ensure_match_transaction_info` is consumed by at least four call sites performing genuine integrity verification: `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. Any of these paths — most notably `replay_on_archive`, whose entire purpose is auditing historical execution correctness against an archive node — will report success even if the locally recomputed `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` differs from what was actually committed and authenticated in the on-chain `TransactionInfo`/accumulator.

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant that "committed state must match the correct VM result" for the checkpoint/position-state root class of authenticated data. A divergence in `state_checkpoint_hash` (Sparse Merkle Tree root) or `position_state_checkpoint_hash` (native/position state summary root) — caused by a state-computation bug, an unintended migration, or an inconsistent storage schema interpretation — would go completely undetected by the tooling whose specific job is to catch exactly this class of divergence. Consequently:
- A hard-fork-only or replay-only divergence in checkpoint state would not be flagged by `replay_on_archive`/chunk-executor replay verification, defeating the intended safety net for auditing historical/committed ledger correctness.
- Authenticated proof fields (`position_state_checkpoint_hash`, `state_checkpoint_hash`) can silently diverge from the actual recomputed state while verification reports a clean match, i.e. an incorrect state root is treated as valid.

This matches the required "Wrong accumulator root, Merkle proof… accepted as valid" and "Authenticated API/state-view output bound to the wrong version/object/proof context" impact classes.

### Likelihood Explanation
The gap is 100% code-path deterministic — every call to `ensure_match_transaction_info` skips the checkpoint-hash comparison, so the likelihood of hitting the omission is not probabilistic; it triggers whenever there is any legitimate mismatch in checkpoint hashes (state, hot-state, or position-state) during replay/verify. The severity depends on there actually being an underlying divergence, which requires a separate root-cause bug in state computation/storage/restore — this finding by itself does not prove such a divergence exists, only that the safety-net check that should catch it is absent. The in-code TODO indicates the Aptos team is aware and is deliberately gating full enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` until this validation is added, which somewhat reduces immediate live exposure but does not eliminate risk for any partial/staged rollout where the position-state root is already being computed and persisted (as seen in `block_executor/mod.rs` and `aptosdb_writer.rs`'s `commit_native_position`).

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between the locally recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when present), and `position_state_checkpoint_hash` (when present) against the corresponding fields of the input `txn_info`, mirroring the existing pattern used for `state_change_hash` and `event_root_hash`. This check must be enforced before `compute_trading_native_state_roots`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network, per the code's own TODO.

### Proof of Concept
Conceptual PoC (cannot be executed without a full node/replay harness, but the code path is deterministic):
1. Enable/simulate a block execution where `compute_trading_native_state_roots` is `true`, producing a `TransactionInfoV1` with a real `position_state_checkpoint_hash` [4](#0-3) .
2. Introduce (or naturally encounter) any divergence in the locally recomputed position-state root relative to what was persisted/authenticated on-chain (e.g., via `storage/aptosdb/src/db/aptosdb_writer.rs`'s `commit_native_position` producing a different summary than execution intended).
3. Run `storage/db-tool/src/replay_on_archive.rs`'s replay-verify flow, which calls `ensure_match_transaction_info` to validate the replayed `TransactionOutput` against the archived `TransactionInfo`.
4. Because `ensure_match_transaction_info` never compares `position_state_checkpoint_hash` (or `state_checkpoint_hash`/`hot_state_checkpoint_hash`), the call returns `Ok(())` despite the divergence [5](#0-4) , so the verification tool reports a successful replay even though the authenticated state root differs from local execution.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
