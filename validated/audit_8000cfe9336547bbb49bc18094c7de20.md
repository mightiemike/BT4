### Title
Wallet Contract's `has_in_flight_tx` guard can become permanently stuck after a failed downstream callback, freezing the account - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The NEAR Wallet Contract (used to give Ethereum-style ECDSA accounts, "eth-implicit accounts", the ability to sign and submit NEAR transactions) uses a boolean invariant flag `has_in_flight_tx` to guarantee that only one Ethereum transaction is processed at a time. This flag is set to `true` in one receipt and is only ever reset to `false` as the first statement of a *separate, later* receipt (a `#[private]` promise callback). Because NEAR only persists state changes for a receipt that completes without failure, if that later callback receipt fails (e.g. runs out of its statically-assigned gas budget while processing attacker-influenced data returned from an external contract), the reset of `has_in_flight_tx` is never committed, while the earlier `true` assignment was already committed in a prior, successful receipt. With no other code path able to clear the flag, `rlp_execute` will reject every subsequent call forever, permanently disabling the wallet.

### Finding Description
`has_in_flight_tx` is set to `true` in three places, always right before returning a `PromiseOrValue::Promise`: [1](#0-0) [2](#0-1) [3](#0-2) 

It is only ever reset to `false` as the *first statement* inside the downstream `#[private]` callbacks: [4](#0-3) [5](#0-4) [6](#0-5) 

These callbacks are scheduled with a *fixed, statically computed* gas budget (`ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `RLP_EXECUTE_CALLBACK_GAS`): [7](#0-6) 

but they must parse a response value coming from an *externally controlled* contract before doing anything else — e.g. the address registrar's `lookup` result in `address_check_callback`, or a NEP-141 token's `storage_balance_of` result in `nep_141_storage_balance_callback`: [8](#0-7) [9](#0-8) 

The `target`/`token_id` for these calls is derived directly from the user's own signed Ethereum transaction (`to` field), so it can point to any account, including one the attacker fully controls: [10](#0-9) 

If the target contract (an attacker-controlled "token" or a compromised/adversarial contract at the address the transaction targets) returns an oversized or otherwise gas-expensive-to-deserialize payload, `serde_json::from_slice` inside the callback can exhaust the fixed gas budget before `self.has_in_flight_tx = false` (already executed in program order, but not yet *committed* — NEAR only commits state for a receipt that finishes without failure) becomes durable. The whole callback receipt then fails, its state changes (including the reset of the flag) are discarded, and the previously-committed `has_in_flight_tx = true` remains permanently.

From that point on, every future call to `rlp_execute` is rejected at the very first check: [11](#0-10) 

There is no method exposed on `WalletContract` to manually clear `has_in_flight_tx`, so the account becomes permanently unable to process any further Ethereum-style transactions.

This mirrors the reported bug class: an internal invariant/guard (`dynamicPoolCounter` visibility in the original report vs. `has_in_flight_tx` reset here) depends on a downstream call that can unconditionally fail, and once it fails the contract enters a state from which it can never recover — a permanent deadlock reachable by ordinary users of the contract.

### Impact Explanation
Any eth-implicit account (an ordinary user-controlled NEAR account driven by the Wallet Contract) can be permanently frozen — unable to sign or relay any further NEAR actions — by a single crafted transaction targeting a malicious/adversarial contract that returns an oversized response to `storage_balance_of` or the registrar `lookup`. This is a permanent denial of service on the account's ability to move its own funds via the wallet-contract mechanism, matching "permanently frozen funds" impact criteria.

### Likelihood Explanation
The attack requires only a normal signed Ethereum-style transaction (as accepted by `rlp_execute`) whose `to` address resolves to an attacker-deployed NEAR contract returning a large/expensive-to-parse payload for `storage_balance_of` (ERC-20 emulation path) or by controlling the address-registrar's response path. No validator, relayer, or protocol privilege is required — an ordinary transaction signer or relayer submitting a transaction on the user's behalf can trigger it, whether accidentally (interacting with a buggy/malicious token) or deliberately (a malicious relayer steering the target).

### Recommendation
Reset `has_in_flight_tx` in a way that is resilient to callback failure — for example, use a `#[callback_unwrap]`-free structure and record the "in flight" state with a timeout/expiry (e.g., height or nonce-based), or ensure the flag can be cleared independently of the specific gas budget/success of the deserialization logic (e.g., decode results with a fixed, cheap bound check before doing any parsing, and/or attach gas dynamically based on the actual size of the returned value rather than a fixed constant).

### Proof of Concept
1. Deploy a malicious contract `evil.near` exposing a `storage_balance_of` method that returns a very large (e.g., multi-megabyte) JSON blob.
2. A relayer submits an RLP-encoded ERC-20 `transfer` Ethereum transaction on behalf of a user's eth-implicit wallet contract, with `to` set (via signature) so that `target == evil.near`.
3. `inner_rlp_execute` recognizes this as `EthEmulationKind::ERC20Transfer`, sets `has_in_flight_tx = true` and schedules `Promise::new(evil.near).function_call("storage_balance_of", ...)` followed by `.then(ext.nep_141_storage_balance_callback(...))` with the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget ( [10](#0-9) ).
4. `evil.near` returns the oversized payload; `nep_141_storage_balance_callback` runs out of gas while calling `serde_json::from_slice` on it, so its receipt fails and the `self.has_in_flight_tx = false` assignment is never committed ( [9](#0-8) ).
5. Any subsequent call to `rlp_execute` on this wallet contract now permanently returns `"Error: transaction already in progress, please try again later."` ( [12](#0-11) ), freezing the account indefinitely.
