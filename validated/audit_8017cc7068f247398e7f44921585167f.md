## Title
`ensure_match_transaction_info` never validates `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, letting replay-verify accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the integrity check used by replay/verification tooling to confirm that a freshly re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on the ledger. It checks execution status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never compares `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, or the native-position (`position_state_checkpoint_hash`) — the function's own comment acknowledges this gap [2](#0-1) .

### Finding Description
`ensure_match_transaction_info` is called from the archive replay-verify tool `storage/db-tool/src/replay_on_archive.rs`, where it is the sole correctness gate comparing locally re-executed outputs against `expected_txn_infos` pulled from a backup/archive source [3](#0-2) . It is also used by `execution/executor/src/chunk_executor/mod.rs` and `aptos-move/cli/src/commands.rs`.

The `TransactionInfo` carries a `state_checkpoint_hash` (the Merkle root of the state at a checkpoint version) and, when `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled, additional hot-state and native-position checkpoint roots [4](#0-3) . These roots are computed independently of the transaction's own write set — they represent the cumulative state tree, not per-transaction writes — via `DoStateCheckpoint` and are threaded through `LedgerUpdateOutput`/accumulator construction as consensus-verified fields of `TransactionInfoV1` [5](#0-4) .

Because `ensure_match_transaction_info` checks only `status`, `gas_used`, `write_set_hash` (`state_change_hash`), and `event_root_hash`, it silently accepts any `TransactionInfo` whose `state_checkpoint_hash` (or hot-state / position-state checkpoint hash) diverges from what local re-execution actually produces. A write-set hash match does not imply a matching global state root, since `state_change_hash` only hashes this transaction's own write ops, not the resulting whole-tree Merkle root.

### Impact Explanation
This breaks the "authenticated proof/state-commitment output must survive verification unchanged" invariant specifically for the archive-replay verification pipeline. `replay_on_archive` is the tool operators/auditors run to detect divergence between an archived (potentially malicious, corrupted, or hard-fork-diverged) ledger and independent re-execution. Since the check never inspects the checkpoint-hash fields, a corrupted or tampered `state_checkpoint_hash` (or the newer hot-state/native-position roots) in an archive would pass `replay_on_archive`'s verification even though the actual account/hot/position state tree computed by local execution is different from what the archive's ledger accumulator commits to. This is exactly the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong … state proof accepted as valid" class called out in the task's required impacts, applied to the state-checkpoint root rather than a JMT proof directly.

The severity is bounded by the fact that this is a replay/verification tool rather than the live consensus commit path — the on-line chunk-executor / state-sync path uses `DoStateCheckpoint`'s own `known_state_checkpoints` comparisons elsewhere in `chunk_executor/mod.rs` to validate checkpoint hashes during real bootstrapping, so it does not by itself corrupt consensus state. However, for the specific tool whose entire purpose is verifying that an archived/replicated dataset's authenticated ledger state matches independent execution, this is a real gap: it can mask ledger-state corruption or a hard-fork execution divergence that manifests only in the state (not the write-set) root.

### Likelihood Explanation
Likelihood is moderate: exploitation requires either (a) an archive/data source with a state-checkpoint-hash mismatch (e.g., due to storage corruption, a non-deterministic state-tree bug, or a malicious archive maintainer) or (b) a hard-fork-only client divergence in state-checkpoint-root computation (position tree, hot-state tree) that doesn't affect the transaction's own write set. The comment in the code itself flags this as a known, unaddressed TODO ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating the authors are aware the gap is not yet closed as new checkpoint-root features (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) are rolled out.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally-computed state checkpoint hash(es) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when present/enabled), mirroring the `known_state_checkpoints`/`known_position_state_checkpoints` validation already performed in `DoStateCheckpoint` during normal chunk execution. This requires threading the checkpoint-hash outputs of `DoStateCheckpoint`/`DoLedgerUpdate` into the replay-verify call sites so a real mismatch surfaces as a hard failure instead of being silently accepted.

### Proof of Concept
No executable PoC was constructed; this is a code-inspection finding based on the explicit gap between the fields validated in `ensure_match_transaction_info` (status/gas/write_set_hash/event_root_hash only) and the full set of authenticated fields on `TransactionInfo` (which also include `state_checkpoint_hash`, and on V1, hot-state/position-state checkpoint hashes), combined with the fact that `replay_on_archive.rs` uses exactly this function as its only per-transaction correctness gate. I was not able to fully trace whether any other guard in the chunk-executor path (outside the direct call to `ensure_match_transaction_info`) also independently re-validates checkpoint hashes for the archive-replay tool specifically (as opposed to the state-sync/chunk-apply path), so confidence that this manifests as an exploitable, unguarded end-to-end gap in `replay_on_archive` specifically is moderate rather than fully proven.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
```
