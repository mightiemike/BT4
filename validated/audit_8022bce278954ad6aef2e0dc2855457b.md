### Title
Missing synchronization between `RocksDbDataSourceImpl.closeDB()`/`resetDb()` and open `RockStoreIterator` allows native-crash race - ([File: chainbase/src/main/java/org/tron/common/storage/rocksdb/RocksDbDataSourceImpl.java])

### Summary
`RockStoreIterator` only tracks its own `close` flag; it never checks whether the underlying `RocksDbDataSourceImpl`'s native `RocksDB` handle has been closed by an independent `closeDB()`/`resetDb()` call. Because `iterator()` does not hold `resetDbLock` for the lifetime of the returned iterator, `closeDB()`/`resetDb()` can free the native `database`/`RocksIterator` resources concurrently with in-flight `hasNext()`/`next()`/`getKey()`/`getValue()` calls on an already-open iterator, risking a JNI-level use-after-free.

### Finding Description
`RocksDbDataSourceImpl.iterator()` creates a `ReadOptions` and a `RocksIterator` and wraps them in a `RockStoreIterator`, but it does **not** acquire `resetDbLock.readLock()` for the duration the caller uses the iterator [1](#0-0) . Compare this with every other read/scan method in the same class (`allKeys`, `getNext`, `prefixQuery`, etc.), which explicitly hold `resetDbLock.readLock()` around the entire scan loop [2](#0-1) .

`closeDB()`/`resetDb()` take `resetDbLock.writeLock()` and close the native `Options` and `database` objects [3](#0-2) . Because the public `iterator()` method releases any lock immediately after construction, nothing prevents `closeDB()`/`resetDb()` from running to completion — closing the native `RocksDB` object — while a caller still holds and uses a previously obtained `RockStoreIterator`.

`RockStoreIterator`'s own guard (`checkState()`/`checkValid()` via the `AtomicBoolean close`) only reflects whether *that iterator's own* `close()` was invoked; it has no visibility into the datasource's `alive` flag or `resetDbLock` [4](#0-3) . Consequently `getKey()`/`getValue()`/`hasNext()`/`next()` can pass their internal checks and then call into `dbIterator.key()`/`dbIterator.value()`/`dbIterator.isValid()` on a `RocksIterator` object whose backing native `RocksDB` handle has just been destroyed by a concurrent `closeDB()`, which is documented as unsafe/undefined behavior in RocksDB's JNI bindings and can lead to a native crash (JVM segfault) rather than a clean Java exception.

### Impact Explanation
This is a Denial-of-Service class: a native crash terminates the whole JVM process, taking the node offline. The scoped impact requested is opportunistic DoS amplification — an unprivileged client issuing heavy read-RPCs (which internally use `iterator()`/`getNext()`/`prefixQuery()`-style calls through the DB layer) increases the probability that a read is in-flight at the exact moment a legitimate, operator/node-triggered `resetDb()`/`closeDB()` executes, turning an otherwise benign maintenance event into a full node crash.

### Likelihood Explanation
Reaching this bug requires two conditions to coincide: (1) an open `RockStoreIterator` actively being read, and (2) `closeDB()`/`resetDb()` on the same `RocksDbDataSourceImpl` executing concurrently. The attacker cannot trigger condition (2) directly — it can only be caused by legitimate node lifecycle operations (e.g., store re-initialization) — so this is not independently attacker-reachable, but an unprivileged client can trivially maximize the read-side race window by flooding read-heavy RPCs. Precise identification of which production code path invokes `resetDb()`/`closeDB()` outside of tests was not fully verifiable with the tools available (grep in this session found call-sites primarily in `TronDatabase.java`, `db2/common/LevelDB.java`, and `db2/common/RocksDB.java`, whose invocation triggers I did not have iterations left to trace fully) — this should be confirmed with a full repository checkout/Devin session.

### Recommendation
Make iterator lifetime lock-aware: either (a) have `iterator()` acquire `resetDbLock.readLock()` and only release it when the returned `RockStoreIterator.close()` is called (i.e., pass the lock into `RockStoreIterator` so it unlocks on close), or (b) have `RockStoreIterator` check the owning datasource's `alive`/closed state (e.g., via a shared `AtomicBoolean` updated by `closeDB()`) before every native call and throw a clean `IllegalStateException`/`TronDBException` instead of touching the native handle. Additionally, `closeDB()`/`resetDb()` should not proceed while any iterator obtained from that instance is still open, or should invalidate outstanding iterators safely before releasing native resources.

### Proof of Concept
```java
// framework/src/test/java/org/tron/common/storage/rocksdb/RocksDbDataSourceImplRaceTest.java
@Test
public void testIteratorSurvivesConcurrentCloseDB() throws Exception {
  RocksDbDataSourceImpl db = new RocksDbDataSourceImpl(tmpDir, "test-race");
  db.putData("k".getBytes(), "v".getBytes());

  DBIterator it = db.iterator();
  it.hasNext(); // primes dbIterator.seekToFirst(), passes checkState()

  Thread closer = new Thread(db::closeDB);
  closer.start();
  closer.join();

  // Expect a clean, catchable exception (e.g., IllegalStateException/TronDBException),
  // NOT a JVM crash/segfault from touching a freed native RocksIterator/RocksDB handle.
  assertThrows(RuntimeException.class, it::getKey);
}
```
Currently this call sequence can invoke `dbIterator.key()` on a `RocksIterator` bound to an already-closed native `RocksDB`, which is undefined behavior in RocksDB's JNI layer rather than a guaranteed Java-level exception.

  public void closeDB() {
    resetDbLock.writeLock().lock();
    try {
      if (!isAlive()) {
        return;
      }
      if (this.options != null) {
        this.options.close();
      }
      database.close();
      alive = false;
    } catch (Exception e) {
      logger.error("Failed to find the dbStore file on the closeDB: {}.", dataBaseName, e);
    } finally {
      resetDbLock.writeLock().unlock();
    }
  }

      initDB();
    } finally {

    }
  }
