### Title
`handle_poison_microblock` slashes miners for cross-tenure microblock-key reuse without verifying same-tenure/same-slot equivocation - (File: `stackslib/src/chainstate/stacks/db/transactions.rs`)

### Summary
`handle_poison_microblock` (transactions.rs:722-883) only requires that two microblock headers recover to the same signer pubkey hash via `check_microblock_header_signer` (transactions.rs:686-713). It never checks that the two headers actually belong to the same tenure/parent-anchored-block context (e.g. `prev_block` equality) or that they represent a genuine same-slot equivocation, so a legitimately reused signing key across two unrelated, non-conflicting tenures can be reported as a poison and the associated miner's coinbase seized.

### Finding Description
The equality that should be enforced for a valid poison report is:

`h1.sequence == h2.sequence AND h1` and `h2` descend from the **same** parent/tenure context (e.g. `h1.prev_block == h2.prev_block`), in addition to the recovered signer pubkey hash being equal.

Tracing the code: `check_microblock_header_signer` (transactions.rs:686-713) recovers the pubkey from each header via `check_recover_pubkey()` and only compares `pkh1 != pkh2`. It never inspects `prev_block`, `sequence`, or any tenure/parent-block identifier of either header. `handle_poison_microblock` (transactions.rs:722-883) then:
- looks up `get_microblock_pubkey_hash_height(&pubkh)` (transactions.rs:754-757) to find which anchored block height declared this pubkey hash for its microblock stream,
- checks maturity window (transactions.rs:770-803),
- and stores/updates a poison report keyed only by `mblock_pubk_height` and `mblock_header_1.sequence` (transactions.rs:805-856) — again with no cross-check that `mblock_header_2` (or the pair as a whole) shares the same tenure/parent context as `mblock_header_1`.

Since Stacks does not enforce microblock-signing-key uniqueness across tenures, a miner can legitimately reuse the same key `K` in two separate, non-overlapping microblock streams at heights `H1` and `H2`. An attacker can then take one legitimately-signed header from stream at `H1` (sequence `S`) and one legitimately-signed header from the unrelated stream at `H2` (sequence `S`, same value by coincidence or attacker's crafted transaction ordering) and submit them as a `PoisonMicroblock` pair. `check_microblock_header_signer` passes because both recover to `K`; no downstream check rejects the pair for lacking a shared parent/tenure. The report is accepted, and the honest miner's coinbase associated with `mblock_pubk_height` is slashed and the bounty paid to the false reporter.

### Impact Explanation
This results in block-reward theft: an honest miner who did nothing wrong (reused a microblock key across two disjoint tenures, which is permitted by the protocol) has their coinbase seized and paid to an attacker via `insert_microblock_poison`/reporter commission (transactions.rs:828-855). This is a reward mis-payment/theft impact directly tied to a single miner's funds, satisfying the "block-reward theft/double-payment/loss" Critical category, since the true owner of the reward is never made whole and the report/slash is deterministic and enforced by all nodes identically (not merely a tip disagreement).

### Likelihood Explanation
The attacker needs only: (1) observe two microblock headers, from two different tenures, signed with the same key `K` (which the protocol allows and which some miner implementations might do by not re-generating a fresh key per tenure), and (2) submit them as a `PoisonMicroblock` transaction referencing the two headers. No majority stake, no signer key compromise, and no privileged role are required — any unprivileged participant who observes such headers (which are broadcast publicly as part of the normal microblock relay) can craft and submit the transaction. The only limiting factor is finding/waiting for a case of key reuse across tenures, and constructing (if not already present) a matching `sequence` value, which is a small field easily satisfied by the honest streams' natural sequence numbering (sequences 0..N are common in every stream).

### Recommendation
In `check_microblock_header_signer` (or immediately in `handle_poison_microblock` before processing), additionally require that `mblock_header_1.sequence == mblock_header_2.sequence` represents a genuine same-slot conflict scoped to the tenure that declared the pubkey hash — i.e., validate that both headers chain from the same parent anchored block (`prev_block`) associated with `mblock_pubk_height`, or otherwise validate both headers against the specific microblock stream committed to at that height rather than trusting a bare pubkey-hash match across arbitrary headers.

### Proof of Concept
Rust integration test plan (chainstate test harness, e.g. in `stackslib/src/chainstate/stacks/db/transactions.rs` tests or a chainstate integration test):
1. Build tenure T1 anchored at height H1 whose block header commits `microblock_pubkey_hash = hash160(K)`; produce a legitimate microblock stream signed by `K` including header `h1` at `sequence = 3`, `prev_block = <T1 parent hash>`.
2. Build a separate, non-overlapping tenure T2 anchored at height H2 (H2 != H1) whose block header also commits `microblock_pubkey_hash = hash160(K)` (key reuse, no fork, no conflict with T1); produce a legitimate microblock stream signed by `K` including header `h2` at `sequence = 3`, `prev_block = <T2 parent hash, != T1 parent hash>`.
3. Submit a `PoisonMicroblock(h1, h2)` transaction via `handle_poison_microblock`.
4. **Assertion (equality check)**: assert `h1.prev_block != h2.prev_block` (proving they are from unrelated tenures) yet `handle_poison_microblock` still returns `Ok(...)` and `insert_microblock_poison` is called for `mblock_pubk_height` — demonstrating the missing context check. A correct implementation must return `Err(Error::InvalidStacksTransaction(...))` for this pair; if the current code returns `Ok`, the test should flag this as the reward-theft bug (i.e., assert that the miner of the block at `mblock_pubk_height` is wrongfully slashed even though no `h1.sequence == h2.sequence`-same-tenure equivocation occurred).
