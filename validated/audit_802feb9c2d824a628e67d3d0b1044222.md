### Title
Front-running griefing of `CreateSmartContract` deployment via deterministic contract-address pre-creation - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
The external report describes a griefing attack where an unprivileged party front-runs a privileged/legitimate state transition by causing a "target already exists" check to trip, permanently blocking the legitimate actor's transaction. In java-tron's TVM contract-creation flow, `VMActuator.create()` derives the new contract's address deterministically from the transaction's raw-data hash and owner address, then rejects deployment if any account already exists at that address. Because this address is fully computable by anyone who observes the pending (broadcast, unconfirmed) transaction, an unprivileged attacker can pre-create an account at that exact address (e.g., via a trivial TRX transfer) before the deploy transaction is confirmed, causing the legitimate deployer's transaction to fail deterministically and irrecoverably for that specific signed transaction.

### Finding Description
`WalletUtil.generateContractAddress(trx)` computes the new contract address as:
```
byte[] txRawDataHash = trxCap.getTransactionId().getBytes(); // SHA256 of trx.getRawData()
combined = txRawDataHash + ownerAddress
contractAddress = Hash.sha3omit12(combined)
``` [1](#0-0) 

This is purely a function of the transaction's raw data (which is fixed once the transaction is constructed/signed, before it is mined) and the owner's address — no private key or block-inclusion randomness is used. `VMActuator.create()` then performs an existence check on that computed address and hard-fails deployment if it already exists:
```
byte[] contractAddress = WalletUtil.generateContractAddress(trx);
// insure the new contract address haven't exist
if (rootRepository.getAccount(contractAddress) != null) {
  throw new ContractValidateException(
      "Trying to create a contract with existing contract address: " + ...);
}
``` [2](#0-1) 

This mirrors the Bribe.sol pattern exactly: the vulnerable check is a naive "does the target state/slot already exist" guard with no consideration that an unprivileged party can create that exact state ahead of time. In the Bribe case, calling the public `notifyRewardAmount(newToken, 1)` implicitly "enables" `newToken`, tripping the `require(rewards[i] != newToken)` guard in `swapOutRewardToken`. In java-tron, sending any transaction (e.g., a 1-sun TRX transfer, itself an anonymous/unprivileged broadcast transaction) that creates an `AccountCapsule` at the deterministically-computable `contractAddress` trips the `rootRepository.getAccount(contractAddress) != null` guard in `create()`.

Once a deploy transaction is broadcast to the network (and thus visible in the mempool to any node/peer), any third party can:
1. Compute `contractAddress = sha3omit12(SHA256(rawData) || ownerAddress)` from the pending transaction.
2. Send a minimal-value transfer to `contractAddress` before the deploy transaction is included in a block.
3. Once the deploy transaction executes, `rootRepository.getAccount(contractAddress) != null` is true, and the deployment is rejected with `ContractValidateException`.

Because the raw data (and hence the address) is already fixed once the transaction is signed and broadcast, the victim cannot "fix" that specific signed transaction — they must discard it and construct/sign/re-broadcast an entirely new transaction (which changes `raw_data` and hence the resulting address), repeating the exposure window each time.

### Impact Explanation
This is a griefing/DoS impact with no profit motive required for the attacker, consistent with the reported bug class: an unprivileged network participant can repeatedly and cheaply (single low-value TRX transfer) force targeted `CreateSmartContract` transactions to fail. Because `create()` executes during the actuator's execution phase (post fee/energy deduction) rather than pure pre-broadcast validation, the victim's transaction is included in a block and consumes bandwidth/energy resources despite failing, resulting in a real resource loss for the victim and denial of the specific intended contract deployment, matching a "griefing (no profit motive, but damage to users)" classification.

### Likelihood Explanation
Likelihood is limited by the attacker's need for mempool visibility of the pending, unconfirmed deploy transaction (to read its raw data) before it is mined. Given java-tron's public P2P propagation of unconfirmed transactions, and that `contractAddress` computation requires only publicly-visible `raw_data` (available before signature verification/confirmation), an attacker monitoring the mempool for `CreateSmartContract` transactions can react quickly with a trivial transfer transaction. This makes the attack low-cost and repeatable, though it requires timing precision within the mempool propagation/block-confirmation window.

### Recommendation
Do not fail contract creation solely because an account (not yet a contract) already exists at the computed address; only reject when actual contract code/metadata already exists there (this is precisely the improved semantics already implemented for the `allowTvmConstantinople` path in `Program.createContractImpl`, via `isContractExist`, but the top-level `VMActuator.create()` check does not apply this same relaxation). Align `VMActuator.create()`'s existence check with `Program.createContractImpl`'s `contractAlreadyExists` semantics (treat a plain, codeless account at the target address as eligible for promotion to a contract, as already done for CREATE2), rather than unconditionally rejecting on any pre-existing account.

### Proof of Concept
1. Attacker runs a full node or lightweight watcher subscribed to the node's mempool/pending-transaction stream.
2. Victim signs and broadcasts a `CreateSmartContract` transaction (`rawData` fixed at signing time).
3. Attacker computes `contractAddress = sha3omit12(SHA256(rawData) || ownerAddress)` exactly as `WalletUtil.generateContractAddress` does [1](#0-0) .
4. Attacker immediately broadcasts a minimal `TransferContract` sending 1 sun to `contractAddress`, aiming to have it confirmed before the victim's deploy transaction.
5. If the attacker's transfer confirms first, `rootRepository.getAccount(contractAddress)` is non-null when the victim's deploy transaction executes, and `VMActuator.create()` throws `ContractValidateException("Trying to create a contract with existing contract address: ...")` [2](#0-1) , permanently invalidating that specific signed deploy transaction (fees/energy already spent) and forcing the victim to reconstruct and resubmit.

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
