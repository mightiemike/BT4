## Analysis

I found a real correctness gap here, though I want to flag one wiring detail I could not fully confirm due to a tool/index limitation (noted below).

### What's confirmed

`CrossShardStateView::get_usage()` unconditionally discards the real global usage and returns `Untracked`, regardless of what the underlying base view reports: [1](#0-0) 

This type is constructed per sub-block from the transaction's declared cross-shard read/write dependencies: [2](#0-1) 

and it is imported/used inside `sharded_executor_service.rs`, which builds the state view that each shard's sub-block execution runs against: [3](#0-2) 

Contrast this with the "unsharded" `AggregatorOverriddenStateView`, whose `get_usage()` correctly forwards to the base view instead of stubbing it out: [4](#0-3) 

The Move-level consumer of `get_usage()`/the native is `state_storage::on_new_block`, which snapshots `Usage.items`/`Usage.bytes` **only when the epoch changes**, and the module's own doc-comment warns this is only deterministic "if called from the first transaction of the block ... because the execution layer guarantees a fresh state view then": [5](#0-4) 

The whole (non-partitioned) base `state_view` is dispatched identically to every shard via `ExecutorShardCommand::ExecuteSubBlocks(state_view.clone(), ...)`: [6](#0-5) 

So the base view itself has correct, global usage — the corruption path is specifically through the `CrossShardStateView` wrapper stubbing `get_usage()` to `Untracked` for any transaction whose resolver is backed by it.

### Uncertainty I could not resolve

I attempted to read `ShardedExecutorService::execute_transactions_with_dependencies` — the function that actually constructs the resolver/state view passed into `AptosVMBlockExecutorWrapper` for each sub-block — but the tool returned an empty/blank body for that range, which appears to be an indexing artifact for this file rather than the file genuinely being empty there. I was therefore unable to conclusively confirm from the index whether the VM resolver used for the epoch-boundary transaction's execution is backed by `CrossShardStateView` (making the bug live) or is bypassed for that specific native call. Given the import list and the surrounding architecture (`CrossShardStateView::create_cross_shard_state_view` is clearly built for wrapping sub-block execution), it is highly likely this is the resolver in use, but this specific wiring should be verified by reading the full file contents directly (not through the index) before treating this as fully proven.

### Title
`CrossShardStateView::get_usage()` always returns `Untracked`, corrupting epoch-boundary `StateStorageUsage` under sharded execution — ([File: aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_state_view.rs])

### Summary
`state_storage::on_new_block` snapshots global item/byte counts into the on-chain `StateStorageUsage` resource once per epoch, via a native that reads `StateView::get_usage()` of the resolver active for that transaction. In sharded execution, sub-block transactions are resolved against a `CrossShardStateView` wrapping the real base view, but `CrossShardStateView::get_usage()` unconditionally returns `StateStorageUsage::Untracked` instead of delegating to the base view. If the epoch-boundary transaction is executed through this wrapper, the resulting on-chain `Usage{items,bytes}` value differs from what a non-sharded validator (or the `AggregatorOverriddenStateView`, which correctly delegates) would compute for the identical block.

### Finding Description
- The comparable state view used elsewhere in the sharded pipeline (`AggregatorOverriddenStateView`) forwards `get_usage()` to the base view, preserving correctness [4](#0-3) .
- `CrossShardStateView`, used to resolve reads for transactions inside a shard's sub-block, does not do this — it always returns `Untracked` [1](#0-0) .
- `state_storage::on_new_block` only refreshes `Usage` at an epoch boundary, and explicitly documents the fragility of `get_state_storage_usage_only_at_epoch_beginning()` to which state view backs the call [7](#0-6) .
- Because ordinary unprivileged user transactions in the block (transfers, resource creation/deletion, package publication, etc.) are exactly what changes the true global item/byte counts, the divergence is directly a function of unprivileged transaction content: the correct (non-sharded) count reflects those writes; the sharded path silently reports `Untracked`/zero instead.

### Impact Explanation
`StateStorageUsage.usage` is a committed Move resource, consumed by `aptos_framework::storage_gas` for gas-schedule computation and is part of the deterministic ledger state. If sharded execution produces `Untracked`/zero usage where non-sharded execution produces the true item/byte counts, the write set for the `on_new_block` transaction differs between the two execution modes, producing a different post-state root — a hard-fork-only divergence between validators running sharded vs. non-sharded execution for the same block.

### Likelihood Explanation
This is not attacker-triggerable at will (epoch boundaries are governance/time-scheduled, not per-transaction), but it is deterministic and inevitable at every epoch change whenever sharded execution is enabled and the wrapping described above applies. It requires no privileged operator mistake — it is a latent bug in shared production code triggered purely by normal chain operation (any block that happens to be the first of a new epoch).

### Recommendation
Fix `CrossShardStateView::get_usage()` to delegate to `self.base_view.get_usage()` (matching `AggregatorOverriddenStateView`), so epoch-boundary usage queries always observe the full/global state, not a partial or stubbed view, regardless of execution mode. Additionally, verify (via direct file read outside the index) exactly which state view backs VM execution in `ShardedExecutorService::execute_transactions_with_dependencies`, since that determines whether this stub is actually hit for the epoch-boundary transaction.

### Proof of Concept
Differential test: construct a block whose last transaction triggers an epoch change (or directly invoke `on_new_block` at epoch boundary) preceded by transactions from unprivileged accounts that alter global item/byte counts (e.g., account creation, resource writes). Execute the block once via `AptosVMBlockExecutor::execute_block_no_limit` (non-sharded) and once via `ShardedBlockExecutor::execute_block` with the transaction partitioned into a shard's sub-block. Assert `StateStorageUsage.usage.items`/`bytes` (read via `state_storage::current_items_and_bytes`) and the resulting state roots are identical between the two runs — the sharded run would report zero/`Untracked`-derived values while non-sharded reports the true counts, and state roots diverge. This mirrors the existing sharded/non-sharded comparison test scaffolding at [8](#0-7) , extended to force an epoch-boundary transaction and assert on the `StateStorageUsage` resource rather than just transaction outputs.

    pub fn create_cross_shard_state_view(
        base_view: &'a S,
        transactions: &[TransactionWithDependencies<AnalyzedTransaction>],
    ) -> CrossShardStateView<'a, S> {
        let mut cross_shard_state_key = HashSet::new();
        for txn in transactions {
            for (_, storage_locations) in txn.cross_shard_dependencies.required_edges_iter() {
                for storage_location in storage_locations {
                    cross_shard_state_key.insert(storage_location.clone().into_state_key());
                }
            }
        }
        CrossShardStateView::new(cross_shard_state_key, base_view)
    }

    public(friend) fun on_new_block(epoch: u64) acquires StateStorageUsage {
        assert!(
            exists<StateStorageUsage>(@aptos_framework),
            error::not_found(ESTATE_STORAGE_USAGE)
        );
        let usage = borrow_global_mut<StateStorageUsage>(@aptos_framework);
        if (epoch != usage.epoch) {
            usage.epoch = epoch;
            usage.usage = get_state_storage_usage_only_at_epoch_beginning();
        }
    }

    public(friend) fun current_items_and_bytes(): (u64, u64) acquires StateStorageUsage {
        assert!(
            exists<StateStorageUsage>(@aptos_framework),
            error::not_found(ESTATE_STORAGE_USAGE)
        );
        let usage = borrow_global<StateStorageUsage>(@aptos_framework);
        (usage.usage.items, usage.usage.bytes)
    }
