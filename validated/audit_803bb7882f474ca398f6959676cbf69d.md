### Title
Unchecked integer subtraction in startup index generation can panic or (in release builds) silently corrupt `accounts_data_len` - ([File: accounts-db/src/accounts_db.rs])

### Summary
During accounts-index generation at node startup, `AccountsDb::generate_index` computes a running total of account data length (`accounts_data_len`) and then subtracts out the contribution from duplicate (stale) account versions found across storages. Every other arithmetic accumulation in this same code path (capitalization, lt-hash) is done with explicit `checked_add`/`checked_sub` and an `.expect(...)` guarding against overflow/underflow, but the `accounts_data_len` subtraction uses a bare, unchecked `-=` operator.

### Finding Description
In `visit_duplicate_pubkeys_during_startup`, the accumulator sums `data_len` for every non-max-slot (i.e., stale/duplicate) version of a pubkey with `lamports > 0`: [1](#0-0) 

That per-shard result is combined into the running total with a bare subtraction, unlike the parallel capitalization field which is protected by `checked_sub().expect(...)`: [2](#0-1) 

Compare this to the capitalization accumulation logic right above it and to the accumulator merge logic used elsewhere (`IndexGenerationAccumulator::accumulate`), which consistently uses `checked_add`/`checked_sub` with explicit panics on overflow: [3](#0-2) 

`accounts_data_len` itself is only ever incremented per-storage inside `generate_index_for_slot` for non-zero-lamport accounts: [4](#0-3) 

Because the `-=` on line 6112 is a plain, unchecked integer operation on a `u64`, if `accounts_data_len_from_duplicates` were ever computed larger than `total_accum.accounts_data_len` — whether from a latent accounting bug in this duplicate-detection path, a malformed/edge-case account storage (e.g., unusual `slot_list` orderings, zero-lamport/nonzero-lamport transitions on duplicate slots), or future code changes that don't preserve the invariant — the result differs sharply by build profile:
- In debug builds (overflow-checks enabled), this panics the node during startup/snapshot loading (`node panic`).
- In release builds (overflow-checks typically disabled for validators), this silently wraps around to a huge `u64` value, producing a corrupted `accounts_data_len` with **no panic, no log warning, and no assertion**, unlike every neighboring arithmetic operation in the same function.

This is exactly the bug class flagged in the external report: arithmetic performed without the "safe math" idiom used consistently elsewhere in the same module, creating an unguarded overflow/underflow surface.

### Impact Explanation
`accounts_data_len` computed during index generation becomes `IndexGenerationInfo.accounts_data_len`, which seeds the bank's accounts-data-size tracking used to enforce the network's total accounts-data-size limit. A silently wrapped (corrupted) value here would desynchronize an honest node's view of accounts-data usage from the correct value that other nodes compute, which is a form of state divergence between honest nodes that loaded from the same snapshot via different code paths/builds, and could affect enforcement of the accounts-data-size cap after restart. In the debug/overflow-checked case, it is a straightforward node panic during snapshot load/startup indexing.

### Likelihood Explanation
The likelihood of the underflow being reached in practice is low, since under the documented invariant "the duplicates' contribution is a subset of the total accumulated," the subtraction should never underflow in a correct index. However, unlike the capitalization field a few lines above it (which is explicitly hardened with `checked_sub().expect(...)` precisely because such invariants can be violated by edge cases like clean/duplicate corner cases), the `accounts_data_len` path has no such guard, so if the invariant is ever violated (bug, unusual snapshot content, or future refactor breaking the assumption), the failure mode is either a hard panic (debug) or a silent, undetected corruption of validator-visible accounting state (release) — the worst possible outcome for a lattice/size-tracking value, since no error is surfaced at all.

### Recommendation
Replace the unchecked `total_accum.accounts_data_len -= accounts_data_len_from_duplicates;` with a checked operation consistent with the surrounding code, e.g.:
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```
This makes any invariant violation fail loudly and deterministically in all build profiles (matching the treatment already given to `capitalization` and other accumulators in this function), instead of silently producing a wrapped, corrupted value in release builds.

### Proof of Concept
Static-analysis PoC (no runtime harness available in this repository as indexed):
1. Locate `visit_duplicate_pubkeys_during_startup` at `accounts-db/src/accounts_db.rs:6230-6285`, which sums `data_len` of "older" duplicate account versions into `accounts_data_len_from_duplicates`.
2. Locate the consumer at `accounts-db/src/accounts_db.rs:6103-6113` in `generate_index`, where `total_accum.accounts_data_len -= accounts_data_len_from_duplicates;` is executed unchecked, immediately adjacent to a `checked_sub().expect(...)` guard used for `capitalization` on the very same duplicate set.
3. Contrast with `IndexGenerationAccumulator::accumulate` (`accounts_db.rs:445-462`), which uses `checked_add`/`.expect(...)` for every other numeric field being merged, establishing that unchecked arithmetic here is an inconsistency/oversight rather than an intentional design choice.

I could not fully trace, within the available indexed context, a concrete honest-node code path that causes `accounts_data_len_from_duplicates` to exceed `total_accum.accounts_data_len` (this would require deeper tracing through `generate_index`'s multi-pass storage scan and slot-list construction, which was not fully retrievable before the tool budget was exhausted). The finding is reported as a defense-in-depth / inconsistent-hardening issue rather than a proven reachable underflow.
