### Title
Open Redirect via Protocol-Relative URL Bypass in `sanitizeRedirectUrl` - (packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts)

### Summary
`sanitizeRedirectUrl`'s `isSafe()` check only inspects `url.pathname` (via `INVALID_RELATIVE_URL`) and the raw input string (via `FILE_URI_MATCH`), but never verifies that the resolved URL's `hostname`/`origin` matches the app's configured domain. A protocol-relative or backslash-based input such as `//attacker.com` or `\\attacker.com` is resolved by the WHATWG `URL` constructor against the app's base origin, and the attacker-controlled host ends up entirely outside `url.pathname`, so both regex checks are bypassed while `url.protocol` stays `https:`/`http:`.

### Finding Description
In `validate-redirect-url.ts`, `isSafe()` performs these checks in order: [1](#0-0) 

- `FILE_URI_MATCH = /\/\/\//` is tested against the raw `redirectUrl` string and only catches three consecutive slashes (`file:///...`-style payloads).
- `url = new URL(redirectUrl, domain)` resolves the URL against the app's own domain.
- `INVALID_RELATIVE_URL = /[/\\][/\\]/` is tested only against `url.pathname`, never against `url.host`/`url.hostname`/`url.origin`.
- `VALID_PROTOCOLS` only restricts the scheme to `http:`/`https:`.

For a protocol-relative input like `//attacker.com/x` (or a backslash variant like `\\attacker.com/x`, since WHATWG URL parsing normalizes backslashes to slashes for special schemes), `new URL("//attacker.com/x", "https://myapp.com")` resolves to `https://attacker.com/x` — the attacker's host is consumed as the authority component, leaving `url.pathname` as simply `/x`. Neither `FILE_URI_MATCH` (only 2 leading slashes, needs 3) nor `INVALID_RELATIVE_URL` (checks pathname only, which contains no doubled separators) reject this, and the protocol is still `https:`, so `isSafe` returns `true` and `sanitizeRedirectUrl` returns a `URL` pointing at `attacker.com`.

This function is reachable with fully unauthenticated, attacker-controlled input via the exit-iframe endpoint, which forwards the raw `exitIframe` query parameter straight into `renderAppBridge`: [2](#0-1) . `renderAppBridge` then calls `sanitizeRedirectUrl(config.appUrl, redirectTo.url)` and embeds the result unescaped inside a `window.open(destination, '_top')` script: [3](#0-2) . Existing tests confirm this route is reachable without any prior session/auth setup by simply hitting `/auth/exit-iframe?exitIframe=<payload>&shop=<shop>`: [4](#0-3) .

### Impact Explanation
This is an open redirect: an attacker can craft a link on the app's own domain (`/auth/exit-iframe?exitIframe=//attacker.com&shop=...`) that, when visited, causes the top-level browser window to navigate to attacker-controlled infrastructure. Because the navigation appears to originate from the legitimate app/Shopify admin flow and breaks out of the iframe (`_top`), it can be used for phishing (e.g., a fake Shopify login page) against merchants who click the link. Note: query-parameter forwarding of session-related values (e.g., `id_token`) in the general `redirect()` helper is gated by an explicit same-origin check (`parsedUrl.origin === new URL(config.appUrl).origin`) at [5](#0-4) , so the specific "session token leaking via query forwarding" claim in the question is not substantiated by the code — but the underlying open-redirect primitive itself is real and matches Shopify's open-redirect impact class.

### Likelihood Explanation
The vulnerable endpoint (`/auth/exit-iframe`) requires no authentication, no HMAC, and no session — it's directly reachable by any anonymous party who can get a merchant to click a crafted link, as shown by the existing unauthenticated test cases for this path. The bypass only requires a two-character prefix (`//` or backslash equivalents), making it trivially reproducible.

### Recommendation
In `isSafe()`, after constructing `url`, explicitly verify that `url.host` (or `url.origin`) equals the `domain`'s host/origin (unless an explicit allow-list of external targets, e.g., `admin.shopify.com`, is intended), rather than relying solely on regex checks against `url.pathname`.
