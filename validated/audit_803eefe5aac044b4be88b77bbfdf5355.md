Confirmed: in `nep_141_storage_balance_callback` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:194-221`), when the intermediate `storage_balance_of` cross-contract call fails (`PromiseResult::Failed`) or returns malformed data, the function returns an error `ExecuteResponse` immediately at lines 204-210 / 211-220 **without ever consuming or refunding `caller_deposit`**. Compare this to `rlp_execute_callback`'s `Failed` branch (lines 296-312), which explicitly creates a refund promise back to `caller_deposit.account_id` for `caller_deposit.yocto_near`. `address_check_callback`'s `Failed` branch (lines 141-148) has the exact same gap — it drops `caller_deposit` on early return without refunding.

This matches the DODO bug class precisely: an external, unprivileged caller (any account calling `rlp_execute` on someone else's ETH-implicit wallet with an `ERC20Transfer` or address-checked base-token-transfer action) attaches a deposit (`#[payable] rlp_execute`, tracked via `CallerDeposit::new` at `types.rs:180-191`) that is supposed to be refundable on failure (as proven by the working `test_caller_refunds` test at `sanity.rs:170-229`, which only exercises the `register`/direct-failure path through `rlp_execute_callback`). But the intermediate NEP-141 registration-check path (`nep_141_storage_balance_callback`) and the address-registrar-lookup path (`address_check_callback`) both silently swallow `caller_deposit` when their own promise fails, transferring the caller's attached $NEAR into the wallet-contract account's balance permanently, with no method exposed by the wallet contract to reclaim it — an unrecoverable loss functionally identical to ETH being trapped by an empty `receive()` with no matching withdrawal path.

I did not have iterations left to trace this end-to-end through a running test-loop (e.g. crafting an `ERC20Transfer` action where the token's `storage_balance_of` call fails/panics, or the address-registrar lookup call fails, while a non-self caller attaches a deposit) to empirically confirm the loss, so this is based on static code-path analysis of the two callback functions, not a live-tested exploit.

### Title
Caller deposit is dropped (never refunded) when intermediate NEP-141/address-registrar lookups fail in the Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (`WalletContract::rlp_execute`) accepts an attached deposit from an external caller and tracks it via `CallerDeposit` so it can be refunded if the underlying cross-contract action fails. This refund logic is correctly implemented in `rlp_execute_callback`'s `Failed` arm, but two upstream callback functions — `address_check_callback` and `nep_141_storage_balance_callback` — return early on their own promise failure without forwarding or refunding the caller's deposit, permanently trapping those funds in the wallet contract's account balance.

### Finding Description
`inner_rlp_execute` (`lib.rs:330-472`) computes `caller_deposit = CallerDeposit::new(&context)` whenever the predecessor calling `rlp_execute` differs from the wallet's own account, i.e. an arbitrary external caller attached a deposit (`types.rs:180-191`). For an `ERC20Transfer` action, execution is routed through `nep_141_storage_balance_callback` (`lib.rs:194-273`) after a `storage_balance_of` lookup on the token contract. If that lookup call fails (`PromiseResult::Failed`, `lib.rs:203-210`) or returns an undecodable value (`lib.rs:211-220`), the function returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})` directly — `caller_deposit` is a function parameter that is simply dropped, never consumed to create a refund promise the way `rlp_execute_callback` does. Similarly, `address_check_callback` (`lib.rs:134-192`) drops `caller_deposit` on its own `PromiseResult::Failed` arm (`lib.rs:141-148`). In both cases the attached deposit was already credited to the wallet-contract account's balance when the transaction was sent (per NEAR's economics model, `attached_deposit` is deposited to the receiver before contract execution — see `docs/RuntimeSpec/Components/BindingsSpec/EconomicsAPI.md:6-11`); since the deposit is never returned, it stays on the wallet contract permanently, and no method on `WalletContract` allows the contract owner or the depositing caller to withdraw an "orphaned" deposit balance.

### Impact Explanation
Any unprivileged account can call `rlp_execute` on an ETH-implicit account's Wallet Contract with an attached deposit for an `ERC20Transfer` action (or an address-checked base-token transfer). If the token contract's `storage_balance_of` view call fails — which an attacker can force by choosing a `token_id` that reverts/panics, is not deployed, or simply by racing/griefing gas limits — or if the address registrar lookup fails, the caller's attached deposit is permanently and unrecoverably absorbed into the wallet contract's balance. This is a direct, unauthorized-by-design loss of the caller's $NEAR with no compensating value returned, matching the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Reachable by any transaction signer with no special privilege: simply call `rlp_execute` targeting a token contract known (or crafted) to fail `storage_balance_of`, or targeting an eth-implicit `target` so the address-registrar lookup path is used, while attaching a deposit. Because `nep_141_storage_balance_callback` and `address_check_callback` are `#[private]` callbacks invoked automatically as part of the normal ERC-20/address-check flow, the failure path is trivially triggerable, not merely theoretical.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, mirror `rlp_execute_callback`'s `Failed` handling: when the intermediate promise result is `Failed` (or fails to deserialize), issue a refund transfer of `caller_deposit.yocto_near` to `caller_deposit.account_id` before returning the failure `ExecuteResponse`, exactly as done at `lib.rs:296-312`.

### Proof of Concept
1. Deploy the Wallet Contract on an ETH-implicit account `W` (as in `integration-tests/src/tests/features/wallet_contract.rs` / `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`).
2. As an external account `Caller` (i.e. `predecessor_account_id != current_account_id`), call `W.rlp_execute(target, tx_bytes_b64)` with an RLP-encoded ERC-20 transfer transaction (`EthEmulationKind::ERC20Transfer`) and attach a non-zero deposit, e.g. `deposit_amount = NearToken::from_near(3)` similar to `test_caller_refunds` (`sanity.rs:170-229`), but set `token_id` to a contract that either does not implement `storage_balance_of` or is configured to panic on that call.
3. This routes through `nep_141_storage_balance_callback`; the `storage_balance_of` sub-call fails, hitting the `PromiseResult::Failed` branch (`lib.rs:204-210`).
4. Assert (as the negative counterpart of `test_caller_refunds`) that `Caller`'s account balance decreases by the full `deposit_amount` and never recovers it (unlike the assertion at `sanity.rs:208-213`, which only holds for the direct-failure path through `rlp_execute_callback`), while `W`'s balance increases by the deposit amount permanently.
