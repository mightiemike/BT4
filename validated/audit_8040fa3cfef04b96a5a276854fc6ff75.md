## Finding [1](#0-0) 

### Title
Excess Attached Deposit Permanently Stranded in `AddressRegistrar::register` on Successful Registration - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `#[payable]` method `register` on the `AddressRegistrar` contract only refunds the caller's attached deposit when a collision occurs (the `Entry::Occupied` branch). On the success path (`Entry::Vacant`), any deposit attached above the computed `required_deposit` is silently kept by the contract with no mechanism to reclaim it, permanently freezing the excess funds.

### Finding Description
`register` computes the exact storage cost `required_deposit` from `bytes_to_store` and `env::storage_byte_cost()`, then only checks `given_deposit < required_deposit` to reject under-payment via `env::panic_str` [2](#0-1) . There is no corresponding `given_deposit > required_deposit` handling.

In the success (`Entry::Vacant`) branch, the entry is inserted and the address returned, but `given_deposit` (which may exceed `required_deposit`) is never refunded — only the log/insert/return happens [3](#0-2) . Contrast this with the `Entry::Occupied` (collision) branch, which explicitly creates a transfer promise back to `env::predecessor_account_id()` for the *entire* `given_deposit` because "no storage was updated" [4](#0-3) . This asymmetry shows the excess-refund logic exists conceptually for one branch but was never applied to the more common success branch.

The contract has no owner, admin, or withdraw method — confirmed by searching the crate — so any yoctoNEAR retained above `required_deposit` becomes permanently unrecoverable by any party, including the contract's deployer.

This mirrors the reported `buy()` bug class exactly: a payable entry point validates `msg.value/deposit >= required` but never handles/returns the surplus when the underlying operation succeeds, causing user overpayment to become a stuck balance.

### Impact Explanation
Any account calling `register` (e.g., via the wallet-contract's `rlp_execute` flow described in `near_action.rs`/`wallet-contract/src/lib.rs`, or directly) with a deposit larger than the exact storage cost permanently loses the difference. Since the contract exposes no `withdraw`/admin-drain method, these funds are frozen forever inside the `AddressRegistrar` account — a "permanently frozen funds" outcome, triggered purely by a single unprivileged transaction/FunctionCall with an over-estimated deposit (a very plausible outcome given the caller is expected to estimate `storage_byte_cost * bytes_to_store` off-chain, e.g. rounding up for safety, as done in `NEP_141_STORAGE_DEPOSIT_AMOUNT` elsewhere in the wallet-contract code).

### Likelihood Explanation
High likelihood: `storage_byte_cost` is a runtime parameter the caller must fetch and multiply themselves; any client that rounds up or double-attaches for safety margin (a very common defensive pattern, as seen in the sibling `NEP_141_STORAGE_DEPOSIT_AMOUNT` constant in the same wallet-contract package) will trigger the bug on every successful, non-colliding call. No adversarial conditions or race are required — a single, ordinary transaction from any signer is sufficient.

### Recommendation
In the `Entry::Vacant` success branch of `register`, compute `excess = given_deposit.checked_sub(required_deposit)` and, if non-zero, issue a `promise_batch_action_transfer` refunding `excess` back to `env::predecessor_account_id()`, matching the pattern already used in the `Entry::Occupied` branch. Alternatively, require `given_deposit == required_deposit` and reject any positive excess up front.

### Proof of Concept
1. Deploy/use the `AddressRegistrar` contract (as done in wallet-contract integration tests, e.g. `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`).
2. Call `register` with `account_id = "alice.near"` and attach a deposit clearly larger than `storage_byte_cost * (20 + len("alice.near"))`, e.g. `NearToken::from_near(1)` as done in `test_register_without_deposit` [5](#0-4) .
3. Observe the call succeeds (`Some(address)` returned) and the contract's account balance increases by the *entire* attached deposit rather than just `required_deposit`.
4. Confirm there is no method on `AddressRegistrar` to withdraw the excess — the caller's overpayment is permanently stuck in the contract account.

    #[payable]
    pub fn register(&mut self, account_id: AccountId) -> Option<String> {
        // It is not allowed to register eth-implicit accounts because the purpose
        // of the registry is to allow looking up the named account associated with
        // an address obtained via hashing, but eth-implicit accounts are already
        // parsable as addresses.
        if is_eth_implicit(&account_id) {
            let log_message = format!("Refuse to register eth-implicit account {account_id}");
            env::log_str(&log_message);
            return None;
        }

        // Must store the address and the account id
        let bytes_to_store = 20 + (account_id.len() as u128);
        let required_deposit =
            NearToken::from_yoctonear(env::storage_byte_cost().as_yoctonear() * bytes_to_store);
        let given_deposit = env::attached_deposit();
        // The caller must pay for the storage cost of registering.
        if given_deposit < required_deposit {
            let message = format!(
                "Insufficient deposit to cover storage cost. Given={} Expected={}",
                given_deposit.as_yoctonear(),
                required_deposit.as_yoctonear(),
            );
            env::panic_str(&message);
        }

        let address = account_id_to_address(&account_id);

        match self.addresses.entry(address) {
            Entry::Vacant(entry) => {
                let address = format!("0x{}", hex::encode(address));
                let log_message = format!("Added entry {} -> {}", address, account_id);
                entry.insert(account_id);
                env::log_str(&log_message);
                Some(address)
            }
            Entry::Occupied(entry) => {
                let log_message = format!(
                    "Address collision between {} and {}. Keeping the former.",
                    entry.get(),
                    account_id
                );
                env::log_str(&log_message);
                // Transfer the deposit back to the caller since no storage was updated.
                let refund_promise = env::promise_batch_create(&env::predecessor_account_id());
                env::promise_batch_action_transfer(refund_promise, given_deposit);
                None
            }
        }
    }

/// Test asserting the address registrar requires a deposit.
#[tokio::test]
async fn test_register_without_deposit() -> anyhow::Result<()> {
    let TestContext { worker, address_registrar, .. } = TestContext::new().await?;

    let method = "register";
    let args = br#"{"account_id": "birchmd.near"}"#;
    let result = address_registrar.call(method).args(args.to_vec()).transact().await?;
    assert!(result.is_failure(), "Call without deposit must fail");

    let pre_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    let deposit_amount = NearToken::from_yoctonear(320000000000000000000);
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output.as_deref(), Some("0x4bfcff9a964925adf801c866f6ada98bd7ec40ca"));
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );
