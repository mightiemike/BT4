### Title
`replay-verify` accepts an execution replay whose state-checkpoint / hot-state / position-state root diverges from the authenticated ledger, because `TransactionOutput::ensure_match_transaction_info` never checks those hash fields - ([File: types/src/transaction/mod.rs])

### Summary
`ensure_match_transaction_info` is the function the archive/backup "replay-verify" tooling (`storage/db-tool/src/replay_on_archive.rs`) and the Aptos debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`) use to decide whether a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` pulled from a backup/archive. The function checks status, gas, write-set hash, and event-root hash, but explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — fields that are part of `TransactionInfoV1` and are meant to authenticate the resulting state (Merkle) roots at that version.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  validates only:
- `status` vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs. `txn_info.state_change_hash()`
- Recomputed event-root hash vs. `txn_info.event_root_hash()`

It then contains an explicit acknowledgement of the gap: [2](#0-1) 

This means `state_checkpoint_hash` (the Sparse Merkle root of world state at checkpoint boundaries), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (TransactionInfoV1-only fields) are never compared between the locally computed replay result and the trusted, backup-sourced `TransactionInfo`. Both consumers of this function rely on it as their sole correctness gate for a replayed chunk:
- `replay_on_archive.rs::execute_and_verify` calls it per-transaction and only flags a mismatch (`Err`) as a "failed" transaction if this function returns an error: [3](#0-2) 
- `aptos_debugger.rs` imports `TransactionOutput`/`TransactionInfo` for the equivalent local debugging/verification flow.

Because `TransactionInfo` variants derive `BCSCryptoHash` over *all* their fields (including checkpoint hashes), the accumulator-proof path (`AccumulatorProof::verify`, `TransactionInfoListWithProof::verify`) does correctly bind the whole `TransactionInfo` (including checkpoint hashes) to the trusted ledger accumulator root when a proof is checked — see [4](#0-3) . However, `ensure_match_transaction_info` does not re-derive the state/hot-state/position checkpoint hash from the locally executed `TransactionOutput` at all and compares it to nothing, so this specific comparison path provides **no protection** against a local VM/executor computing a different state root than the one recorded in the authenticated (and proof-verified) `TransactionInfo` fetched from backup. The backup-restore/replay-verify tool trusts the backup's `TransactionInfo` (already proof-verified against a trusted waypoint/ledger-info) as ground truth and is specifically supposed to catch cases where local re-execution diverges from it; the state-root fields are the primary signal for state divergence, and they are the ones left unchecked.

### Impact Explanation
This is a proof/verification integrity gap directly in scope: "Wrong accumulator root, Merkle proof, transaction proof ... accepted as valid" and "restore ... must not reinterpret committed data into a different ledger state." If the VM/executor's state-checkpoint hash computation diverges from the value embedded in the authenticated `TransactionInfo` (e.g., due to a bug in a Move VM path, a hot-state promotion bug, an aggregator materialization bug, or the incoming `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state-checkpoint logic referenced directly in the TODO), `replay-on-archive`/`replay-verify` will report success even though the resulting state tree root is wrong. This defeats the entire purpose of replay-verify as a mainnet-data-integrity check: operators and the security team use it to detect exactly this class of divergence before trusting a restored/replayed DB snapshot. Silent acceptance of a wrong state root is a "committed state differs from the correct VM result" condition that goes undetected by the tool designed to catch it.

### Likelihood Explanation
The gap is unconditionally present today (not gated behind the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature) — `state_checkpoint_hash` and `hot_state_checkpoint_hash` are always omitted from the check, and this is the only integrity check performed by both call sites (`replay_on_archive.rs`, `aptos_debugger.rs`). The only mitigant is that a state-root bug in the base executor would likely also manifest via other consensus-time checks (e.g., `do_state_checkpoint.rs`'s `get_state_checkpoint_hashes` which does compare against `known_state_checkpoints` during live block-execution/state-sync-with-verification, see [5](#0-4) ). But `replay_on_archive`/`aptos_debugger` are separate, independent tools that go through `TransactionOutput::ensure_match_transaction_info` and not through `do_state_checkpoint`'s comparison, so a bug that is specific to these standalone replay tools' code paths (or a state-root divergence introduced by a change only exercised in ad-hoc replay, e.g. running against archived history with different feature flags/timed-feature overrides as `replay_verify.rs` does) would not be caught there.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionInfo` variant) against the locally computed checkpoint roots, mirroring what `do_state_checkpoint.rs::get_state_checkpoint_hashes` already does for the live block-execution path. At minimum, gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on this fix being present, per the existing TODO, and until fixed, treat `replay-on-archive`/`aptos-debugger` "verification passed" results as **not** authoritative for state-root correctness.

### Proof of Concept
Not directly exploitable by an external attacker; this is a verification-tooling correctness gap. Conceptual PoC:
1. Take an existing backup/archive of a chunk of transactions with valid, proof-verified `TransactionInfo` records (including `state_checkpoint_hash`).
2. Run `replay_on_archive` (or `aptos-debugger`) locally with a build of the executor that has a (hypothetical or injected-for-testing) bug that produces a different but syntactically valid write set / events (same `state_change_hash`/`event_root_hash`, both of which are independent of the state-tree root) yet a different resulting Sparse Merkle root at the checkpoint boundary (e.g., due to a hot-state promotion or aggregator materialization bug affecting only global state ordering, not the individual write-set contents).
3. Observe that `execute_and_verify` in [3](#0-2)  reports no failure, because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`, even though the resulting DB state diverges from the one certified by the ledger info that originally proof-verified this `TransactionInfo`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
