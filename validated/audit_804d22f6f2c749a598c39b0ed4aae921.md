## Analog Found

### Title
Exchange balance injection transaction can be validated successfully but revert at execution due to `long`-width overflow in the token-ratio multiplication - (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the same "another token" quantity twice: once in `doValidate()` using wide `BigInteger` arithmetic, and again in `execute()` using narrow 64-bit `long` arithmetic via `multiplyExact`/`floorDiv`. Because the intermediate product in the `execute()` path is bounded to `long` range while the `validate()` path is not, a transaction that is legitimately accepted by `validate()` can still throw `ArithmeticException` and fail during `execute()`, exactly mirroring the `OpenEdition.buy()` bug class where a narrow-width multiplication overflows and reverts a transaction that should otherwise succeed.

### Finding Description
In `doValidate()`, the ratio is computed with `BigInteger`, which never overflows for realistic TRX/token balances: [1](#0-0) 

In `execute()`, the identical mathematical computation is instead performed with checked `long` arithmetic: [2](#0-1) 

`multiplyExact(secondTokenBalance, tokenQuant)` (or `firstTokenBalance, tokenQuant` in the other branch) computes the full numerator **before** dividing by the other balance. Even though the final quotient `anotherTokenQuant` is bounded by `dynamicStore.getExchangeBalanceLimit()` (checked in `doValidate()` at lines 233-236), the intermediate product `secondTokenBalance * tokenQuant` is not bounded and can exceed `Long.MAX_VALUE` (~9.22×10^18) for balances and quantities that are individually valid and within the exchange balance limit (e.g. `secondTokenBalance ≈ 10^12`, `tokenQuant ≈ 10^12` already produces `10^24`, far beyond `long` range), while `firstTokenBalance` can be large enough that the final quotient is small and well within the allowed limit.

This is the exact bug class from the report: a narrow integer type (`long` here, `uint24`/`uint72` in the Solidity report) is multiplied without widening first, causing overflow that reverts a transaction that the wider-arithmetic validation path proved should succeed.

### Impact Explanation
Any unprivileged exchange creator/owner calling `ExchangeInjectContract` (`ExchangeInjectActuator`) can construct — or unintentionally trigger — a combination of `firstTokenBalance`, `secondTokenBalance`, and `tokenQuant` that passes `validate()` (bounded by `BigInteger` math and the exchange balance limit) but throws `ArithmeticException` in `execute()`, converted to `ContractExeException`: [3](#0-2) 
This causes legitimate on-chain exchange balance/liquidity operations to fail at broadcast time with wasted fees/bandwidth for the caller, and creates a divergence between the two arithmetic paths used for the same accounting decision — a state/accounting-consistency defect in unprivileged, reachable actuator code.

### Likelihood Explanation
`ExchangeInjectContract` is a standard user-facing TRC10 exchange contract type, callable by any account that created a Bancor-style exchange pair (`ExchangeCreateContract`), which itself is unprivileged. Balances scale with TRX_PRECISION (6 decimals) and popular token supplies, so multiplications on the order of `10^12 * 10^12` are realistic for actively used liquidity pools, making the overflow condition practically reachable, not purely theoretical.

### Recommendation
Make `execute()` use the same wide-arithmetic computation as `doValidate()` (i.e. compute `anotherTokenQuant` via `BigInteger` multiply-then-divide, or otherwise avoid computing the unbounded intermediate product in 64-bit `long`) so the two paths never diverge and a `validate()`-approved transaction cannot fail in `execute()` due to an avoidable overflow.

### Proof of Concept
1. Create an exchange with `firstTokenBalance = 5_000_000_000_000L` (5×10^12) and `secondTokenBalance = 4_000_000_000_000L` (4×10^12), both within `getExchangeBalanceLimit()`.
2. Inject `tokenQuant` on the `firstTokenID` side such that `secondTokenBalance * tokenQuant` (the numerator in the `execute()` path) exceeds `Long.MAX_VALUE` (~9.22×10^18), e.g. `tokenQuant = 3_000_000_000_000L` (3×10^12): `4×10^12 * 3×10^12 = 1.2×10^25`, which overflows `long`, while the true ratio `anotherTokenQuant ≈ secondTokenBalance*tokenQuant/firstTokenBalance ≈ 2.4×10^12` easily stays under the balance limit checked by `doValidate()`.
3. `doValidate()` (using `BigInteger`) computes this correctly and accepts the transaction; `execute()`'s `multiplyExact(secondTokenBalance, tokenQuant)` throws `ArithmeticException`, causing `ContractExeException` and transaction failure despite passing validation.
