This confirms the key finding: `DeployAccountTransaction::calculate_contract_address` always uses `DEPLOYER_ADDRESS = ContractAddress(PatriciaKey::ZERO)` [1](#0-0)  — meaning the counterfactual address is derived solely from `(salt, class_hash, constructor_calldata)`, all of which are publicly known/predictable before the `DeployAccount` transaction lands. Any unprivileged caller can pre-occupy that exact address via a plain `deploy` syscall with `deploy_from_zero=true` from any contract, matching the same `class_hash`/`salt`/`calldata` [2](#0-1) . Once occupied, `execute_deployment` permanently rejects any future deployment attempt to that address with `UnavailableContractAddress`, since it strictly requires `current_class_hash == ClassHash::default()` [3](#0-2) , and the `DeployAccount` flow relies on exactly this same check, having pre-funded the target address (a very common wallet pattern) before deployment [4](#0-3) .

### Title
Unprivileged address-squatting via the `deploy` syscall permanently bricks counterfactually-funded `DeployAccount` addresses - (File: `crates/blockifier/src/execution/execution_utils.rs`)

### Summary
The Starknet contract-address derivation for `DeployAccount` transactions is fully deterministic and public: `contract_address = h(salt, class_hash, constructor_calldata, deployer_address=0)`. Because the deployer address is hard-coded to zero for this flow, and the other three inputs (salt, class hash, calldata) are chosen and often published by the future account owner (e.g., wallets that pre-compute and advertise a counterfactual address to receive funds before the account is ever deployed), any unprivileged party can compute the same address and occupy it first via a standard `deploy` syscall from an arbitrary already-deployed contract, permanently preventing the intended `DeployAccount` transaction from ever succeeding — directly analogous to the Sandclock griefing pattern where an attacker forces a "must be empty" precondition to become permanently non-empty.

### Finding Description
`DeployAccountTransaction::calculate_contract_address` computes the target address using a fixed `DEPLOYER_ADDRESS = ContractAddress(PatriciaKey::ZERO)` [1](#0-0) . This is the same address space reachable by the `deploy` syscall when `deploy_from_zero=true`, which also forces `deployer_address_for_calculation = ContractAddress::default()` [2](#0-1) .

`execute_deployment`, the shared routine used both by the `deploy` syscall and by `DeployAccount` transaction execution (via the OS's `deploy_contract`), enforces a strict precondition analogous to the vault's `investedAssets() == 0` check: it requires `current_class_hash == ClassHash::default()` at the target address before allowing deployment, else it returns `StateError::UnavailableContractAddress` [3](#0-2) . This is confirmed by tests showing that attempting to deploy to an already-used address fails with `UnavailableContractAddress` [5](#0-4)  and by the syscall-level "deploy to unavailable address" test [6](#0-5) .

Because `salt`, `class_hash`, and `constructor_calldata` are all attacker-visible (the address is typically published/advertised by wallets so users can pre-fund it, and is trivially recomputed by anyone from these three public parameters), an unprivileged attacker can submit an ordinary `INVOKE` transaction from any already-deployed contract that calls the `deploy` syscall with `deploy_from_zero=true` and matching `(salt, class_hash, constructor_calldata)`. Once `state.set_class_hash_at(deployed_contract_address, ...)` is committed for that address [7](#0-6) , the address permanently and irreversibly fails the `UnavailableContractAddress` check for any future `DeployAccount` transaction — there is no mechanism in the codebase to reset or transfer a `class_hash` at a contract address once set.

### Impact Explanation
Contract addresses are commonly pre-computed off-chain by wallets and published/funded before deployment (a widely used "counterfactual wallet" pattern). If a griefer front-runs the legitimate `DeployAccount` transaction with a cheap `deploy` syscall call targeting the same address, the victim's account can never be deployed at that address — any funds sent to it (fee tokens, ERC-20 balances, etc.) become permanently frozen, since there is no `__validate_deploy__`/constructor path that can ever execute there again. This matches the required impact bar: permanent freezing of funds and inability to complete a legitimate account-deployment state transition, triggered entirely by an unprivileged transaction sender.

### Likelihood Explanation
Likelihood is high in adversarial/MEV-aware environments: the attack only requires observing a mempool `DeployAccount` transaction (or independently guessing a commonly-used salt, e.g., `ContractAddressSalt::default()` as used throughout the codebase's own test helpers [8](#0-7) ) or observing a publicly advertised counterfactual address and its underlying `(class_hash, calldata, salt)` triple, then submitting one cheap `INVOKE` transaction with a `deploy` syscall before the real `DeployAccount` transaction lands. No special privileges, staking, or protocol access are needed — only a funded account able to submit an ordinary transaction.

### Recommendation
Consider either (a) deriving the account contract address using the transaction's own public key/signature commitment (or another user-bound secret) as part of the salt/deployer-namespace so that no third party can pre-compute and squat the address, or (b) allowing a permissioned recovery path in `execute_deployment`/OS `deploy_contract` such that an address squatted with a *foreign, arbitrary* class hash (not matching the account's declared class) can still be reclaimed by the rightful `DeployAccount` transaction, rather than treating any prior occupation as permanently unavailable regardless of intent.

### Proof of Concept
1. A wallet publishes (or a griefer independently derives) a counterfactual account address `A = calculate_contract_address(salt, class_hash, constructor_calldata, deployer=0)` for a not-yet-deployed account, per `crates/starknet_api/src/transaction.rs:457-472`.
2. The victim funds `A` in anticipation of later sending a `DeployAccount` transaction (as modeled in the test helper pattern `fund_account(..., deploy_address, ...)` in `crates/blockifier/src/transaction/account_transactions_test.rs:839`).
3. Before the victim's `DeployAccount` transaction is included, an attacker submits an ordinary `INVOKE` transaction from any deployed contract calling the `deploy` syscall with `deploy_from_zero=true` and the same `(salt, class_hash, constructor_calldata)`, per `crates/blockifier/src/execution/syscalls/syscall_base.rs:380-426`, which succeeds and sets `class_hash_at(A)` to a non-default value via `execute_deployment` (`crates/blockifier/src/execution/execution_utils.rs:364-373`).
4. The victim's `DeployAccount` transaction now permanently fails with `UnavailableContractAddress` (`crates/blockifier/src/execution/execution_utils.rs:347-356`), exactly as reproduced by the existing regression test at `crates/blockifier/src/transaction/transactions_test.rs:2312-2338`, and any funds already sent to `A` remain permanently stranded since no future transaction can ever deploy code there.
