### Title
OAuth Authorization Bearer token leaked to redirect target on cross-origin 3xx redirect - (File: chrome/browser/contextual_tasks/contextual_tasks_url_loader_factory_interceptor.cc)

### Summary
`ContextualTasksProxyingURLLoaderFactory` injects a Google OAuth `Authorization: Bearer <token>` header into requests whose original URL host matches an allow-list (`google.com`, `googlers.com`), then hands the request off to a custom `ContextualTasksURLLoader` that proxies the request to the real network stack. On any subsequent 3xx redirect, `ContextualTasksURLLoader::FollowRedirect` forwards the redirect unmodified, never stripping the previously-injected `Authorization` header even though the redirect target may be a completely different origin. This mirrors the reported LWP::UserAgent bug class: the redirect handler forwards Authorization headers to the new destination without an origin check.

### Finding Description
The allow-list check that gates adding the OAuth token is applied only to the **original** request URL and, optionally, the request initiator, at `ShouldAddAuthHeader`: [1](#0-0) 

Once the token is decided to be attached, it is written directly into the `network::ResourceRequest` in `OnAccessTokenReceived`: [2](#0-1) 

That request (now carrying the `Authorization` header) is handed to `ContextualTasksURLLoader`, which owns the loader for the rest of the request's lifetime, including all redirects: [3](#0-2) 

Crucially, `FollowRedirect` on this loader simply forwards the caller-supplied `headers_update_params` and `new_url` straight to the underlying `target_loader_` with **no** check on whether the redirect target is same-origin/same-site as the original allow-listed host, and no removal of the `Authorization` header: [4](#0-3) 

The only place the injected header is ever stripped is `OnComplete`, and only as a retry mechanism for CORS-preflight failures — not as a general cross-origin redirect safeguard: [5](#0-4) 

For comparison, other Chromium proxying loaders that attach headers to a request explicitly recompute and strip those headers on redirect based on the new origin — e.g. `AwURLLoaderThrottle::WillRedirectRequest` removes previously injected headers when the redirect crosses domains: [6](#0-5) 

and `InterceptedRequest::ApplyOriginMatchedHeaders` recomputes attached headers per-origin on every redirect: [7](#0-6) 

`ContextualTasksURLLoader` has no equivalent logic for the OAuth `Authorization` header it injects, meaning that if a request to an allow-listed host (`google.com`/`googlers.com`) is met with a 3xx response whose `Location` points to an attacker-influenced origin (e.g., an open-redirect endpoint on the allow-listed host, or any subsequent hop in a redirect chain), the token continues to be sent unchanged to that new origin.

### Impact Explanation
An OAuth Bearer access token intended only for Google-owned properties can be disclosed to an arbitrary cross-origin host reachable via a redirect chain rooted at an allow-listed origin. This is a credential/cross-origin information disclosure (confidentiality impact), matching the CVSS profile of the reported analog (`C:H`), without requiring flags, extensions, or MITM — a normal HTTP 3xx response from the allow-listed host is sufficient to trigger the forwarding path.

### Likelihood Explanation
Exploitability depends on the presence of a redirect (e.g., an open redirect or attacker-influenced `Location` response) reachable on `google.com`/`googlers.com` from a context where `ShouldAddAuthHeader`/initiator checks pass, and on `ContextualTasksSendFullVersionListEnabled`/the feature being active with the token attached. Given the breadth of Google's own surface and the fact that no additional per-redirect origin re-validation exists in this specific loader, likelihood is non-trivial but conditioned on discovery of a redirect vector on the allow-listed host.

### Recommendation
In `ContextualTasksURLLoader::FollowRedirect`, compare the redirect target's origin/site against the origin that was originally used to gate `ShouldAddAuthHeader`, and add the `Authorization` header to `headers_update_params.removed_headers` whenever the redirect crosses that boundary, mirroring the pattern already used in `AwURLLoaderThrottle::WillRedirectRequest` and `InterceptedRequest::ApplyOriginMatchedHeaders`.

### Proof of Concept
1. Trigger a request to an allow-listed host (e.g. `https://google.com/...`) from a context that satisfies `ShouldAddAuthHeader` and the initiator check, causing `ContextualTasksProxyingURLLoaderFactory` to attach `Authorization: Bearer <token>` via `OnAccessTokenReceived`.
2. Have that endpoint respond with a 3xx redirect (e.g. an open-redirect parameter) whose `Location` points to an attacker-controlled origin.
3. Observe that `ContextualTasksURLLoader::FollowRedirect` forwards the request to the new origin with the `Authorization` header still present, since neither `FollowRedirect` nor `OnReceiveRedirect` in this class perform any origin check or header stripping. The attacker's server receives the Bearer token in the `Authorization` header of the cross-origin request.

```text
bool ShouldAddAuthHeader(const GURL& url) {
  // Don't add the Authorization header to OGB URLs, since they don't support
  // OAuth. Attaching an OAuth token can result in 403 errors.
  if (url.spec().contains(kOneGoogleIdentifier)) {
    return false;
  }

  // Don't add the Authorization header to any domain in the deny list.
  for (const char* domain : kAuthTokenDenyList) {
    if (url.DomainIs(domain)) {
      return false;
    }
  }

  // Only add the Authorization header to domains in the allow list.
  for (const char* domain : kAuthTokenAllowList) {
    if (url.DomainIs(domain)) {
      return true;
    }
  }
  return false;
}
```

```text
  if (!added_headers_.empty()) {
```

```text
void InterceptedRequest::ApplyOriginMatchedHeaders(
    std::vector<std::string>* redirect_headers_to_remove,
    net::HttpRequestHeaders* redirect_headers_to_modify) {
  // TODO(crbug.com/422368112): Figure out how to handle CORS requests.
  url::Origin request_origin = url::Origin::Create(request_.url);
  if (options_ & network::mojom::kURLLoadOptionAsCorsPreflight) {
    for (const auto& matched_header : origin_matched_headers_) {
      if (matched_header->MatchesOrigin(request_origin)) {
        base::UmaHistogramBoolean(
            "Android.WebView.AndroidX.Profile.ExtraHeaderTargetsCorsPreflight",
            true);
        break;
      }
    }
    // For now we simply omit the header on a CORS preflight, but otherwise
    // attach the header on the GET request.
    return;
  }

  if (redirect_headers_to_remove) {
    redirect_headers_to_remove->insert(redirect_headers_to_remove->end(),
                                       attached_origin_matched_headers_.begin(),
                                       attached_origin_matched_headers_.end());
  }

  // This request might be in the process of being redirected to a different
  // domain, where we need to apply different headers, so remove previously
  // attached headers from the canonical set of headers.
  for (const auto& header_name : attached_origin_matched_headers_) {
    request_.headers.RemoveHeader(header_name);
  }

  attached_origin_matched_headers_.clear();

  for (const auto& [header_name, header_value] :
       AwOriginMatchedHeader::GetCombinedMatchingHeaders(
           origin_matched_headers_, request_origin)) {
    // TODO(crbug.com/423581920): Follow up to determine what the best merging
    // strategy is. The current strategy is to only attach if there is no
    // collision, which is least likely to break existing web pages.
    bool should_attach = !request_.headers.HasHeader(header_name);
    base::UmaHistogramBoolean(
        "Android.WebView.AndroidX.Profile.ExtraHeaderAttached", should_attach);
    if (should_attach) {
      request_.headers.SetHeader(header_name, header_value);
      attached_origin_matched_headers_.emplace_back(header_name);
      if (redirect_headers_to_modify) {
        redirect_headers_to_modify->SetHeader(header_name, header_value);
      }
    }
  }
}
```
