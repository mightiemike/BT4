### Title
DeleteAccountAction lets a signer permanently burn their own remaining balance by naming a non-existent beneficiary - ([File: runtime/runtime/src/actions.rs])

### Summary
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically well-formed `AccountId`; it never checks that the beneficiary account actually exists in state, at either the stateless validation layer or inside `action_delete_account`. If the named beneficiary does not exist, the delete succeeds, the account is removed, and the ensuing balance-refund receipt to the beneficiary fails and the entire remaining balance is burned instead of being delivered — a direct analog of the Canto "recipient existence mismatch between validation and consensus layers" bug: an action that a single unprivileged signer submits passes all up-front checks, but silently fails to have the intended economic effect once processed, and by the time the failure is observed the triggering state (the deleted account) can no longer be reverted or retried.

### Finding Description
`validate_delete_action` (the stateless action-validation function) only calls `validate_action_account_id(&action.beneficiary_id)` — a purely syntactic account-id format check — with no existence check: [1](#0-0) 

At execution time, `action_delete_account` unconditionally emits a system refund receipt carrying the account's entire remaining balance to `beneficiary_id`, with no check that the beneficiary account exists, before removing the account: [2](#0-1) 

When that refund receipt (predecessor `system`) is later processed as a `Transfer` action against the (possibly non-existent) beneficiary, `check_account_existence` rejects it: for a `Transfer`, if the account doesn't exist, `implicit_creation_allowed` is consulted, and it unconditionally returns `false` whenever the receipt is a refund, regardless of account type: [3](#0-2) [4](#0-3) 

This is directly confirmed by an existing unit test that pins exactly this behavior — a refund to a missing account fails with `AccountDoesNotExist` and creates nothing: [5](#0-4) 

Finally, when a refund receipt (`predecessor_id().is_system()`) fails, the deposit amount is not returned to anyone — it is explicitly burned into `other_burnt_amount`: [6](#0-5) 

The `docs/RuntimeSpec/Refunds.md` documentation confirms this is the designed behavior for refunds in general ("If the execution of a refund fails, the refund amount is burnt"), but this generic refund-failure rule was never designed with `DeleteAccountAction`'s user-chosen, unchecked `beneficiary_id` in mind: [7](#0-6) 

This mirrors the Canto/Turnstile report precisely: the application-layer action (`register` in Canto / `DeleteAccountAction` in NEAR) validates only a syntactic/loose constraint on the target address (non-zero address / valid `AccountId` format), while the deeper execution/consensus layer enforces a stricter "must exist" rule on that same target — and the mismatch is invisible to the submitter because the outer transaction still reports success (or, in this case, an unrelated success followed only by the beneficiary's own receipt silently failing).

### Impact Explanation
Any account holder who submits a `DeleteAccountAction` with a `beneficiary_id` that does not exist on chain — a typo'd account, a never-funded implicit/derived account, or any other syntactically valid but never-created `AccountId` — permanently loses their entire remaining account balance. The account is deleted (irreversible), so there is no way to retry or recover: the funds are burned from total supply rather than transferred, which is a permanent, protocol-level loss of user funds triggered entirely by a single unprivileged transaction, with no attacker interaction required (self-inflicted, but caused by a genuine mismatch between the action's validation surface and its actual execution guarantees).

### Likelihood Explanation
Likelihood is non-trivial: `DeleteAccountAction`'s beneficiary is user-supplied free text (an `AccountId`), so any client, wallet, or CLI misconfiguration, typo, or use of a freshly-generated but never-funded account as the beneficiary reproduces this outcome deterministically and immediately, with no special privileges, and it is invisible until the fatal receipt (a routine consequence of routine account cleanup/migration flows). It requires no cross-shard timing or racing — the outcome is fully deterministic given the transaction's action list.

### Recommendation
Add an execution-time (or ideally earlier, validation-time) check in `action_delete_account`/`check_account_existence` that verifies `beneficiary_id` corresponds to an existing, initialized account before permitting `DeleteAccountAction` to proceed (analogous to how `Action::DeleteAccount` itself already requires `account` to exist). If a stricter existence requirement is impractical at validation time (since it requires state access), the delete action should be rejected with an explicit error (e.g., a new `ActionErrorKind::BeneficiaryDoesNotExist`) rather than silently letting the follow-on refund fail and burn the funds.

### Proof of Concept
1. Create and fund `alice.near`.
2. `alice.near` submits `DeleteAccountAction { beneficiary_id: "nonexistent-fresh-account.near" }` (an account never created on chain) as the sole action in the transaction.
3. `validate_delete_action` passes (id is syntactically valid) — no state check occurs.
4. `action_delete_account` runs: it computes `alice.near`'s balance, pushes `Receipt::new_balance_refund(&"nonexistent-fresh-account.near", account_balance)`, and deletes `alice.near`. The delete-account receipt itself reports success.
5. The refund receipt is later processed as a `Transfer` action to `nonexistent-fresh-account.near`; since it is a refund (`is_refund = true`), `implicit_creation_allowed` returns `false` and `check_account_existence` returns `ActionErrorKind::AccountDoesNotExist`.
6. Because the failing receipt's predecessor is `system`, the runtime burns the whole `account_balance` into `other_burnt_amount` instead of refunding it to anyone — confirmed by the exact same mechanism exercised in `refund_may_not_create_universal_account` at `runtime/runtime/src/tests/apply.rs:6880-6926`.
7. `alice.near`'s account and balance are both gone permanently; no recovery path exists since the deleting transaction already succeeded and the account no longer exists to retry the action.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
