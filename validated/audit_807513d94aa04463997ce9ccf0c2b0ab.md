### Title
`ensure_match_transaction_info` never validates the state-checkpoint / hot-state / position-state root hashes, letting replay-verify tooling accept a diverged committed state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant-checking function used to confirm that a locally re-executed `TransactionOutput` matches an externally supplied, ledger-authenticated `TransactionInfo`. It is the closest Aptos analog to the Tempus bug: instead of validating against the field that actually binds ledger state (the state-checkpoint hash), it only validates status, gas, write-set hash, and event-root hash, silently skipping the state-checkpoint-hash family of fields entirely.

### Finding Description
`ensure_match_transaction_info` checks status, gas_used, `state_change_hash` (write set), and `event_root_hash`, but never reads or compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against any locally computed value: [1](#0-0) 

The code even documents this gap explicitly: [2](#0-1) 

This function is the sole correctness gate in two state-integrity-critical call sites:
1. `ChunkExecutor::verify_execution`, which re-executes a batch of transactions and is supposed to catch divergence between local VM execution and the trusted/authenticated `TransactionInfo` list before committing: [3](#0-2) 
2. `storage/db-tool`'s `replay_on_archive`, the tool operators use to replay-verify archived history against authenticated ledger data: [4](#0-3) 

Since `state_checkpoint_hash` is the root hash of the Sparse Merkle Tree describing the entire world state at a checkpoint boundary (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are analogous roots for other state partitions): [5](#0-4) 

any divergence in the *state* produced by local execution (as opposed to the write set/events, which are checked) is invisible to this comparator.

### Impact Explanation
This does not corrupt the primary write path — actual committed state values come from `TransactionOutput.write_set()`, which is checked (via `state_change_hash`), so ordinary consensus-driven block commit is not directly affected. The impact is specifically in the two above use sites, which exist precisely to catch state-root divergence bugs (fast-sync `ChunkExecutor` replay verification, and offline `replay_on_archive` tooling). Because neither path compares the state-checkpoint hash family, a bug or non-determinism that causes locally-recomputed world state to diverge from the authenticated chain state (while write set/events happen to match) will be reported as a successful, verified replay/commit — exactly the "hard-fork-only divergence during commit/replay/restore/proof-verification" class called out in scope. This means the very tooling meant to detect a consensus-breaking state-root divergence would silently pass, masking a real ledger-state corruption instead of catching it.

### Likelihood Explanation
Likelihood is Medium: this requires an underlying non-determinism or VM/state-tree bug that changes computed state roots without changing the write set or events (e.g., a bug in state-tree assembly for hot-state/position-state components, or divergent handling not reflected in the write set itself). Such bugs are rare, but when they occur, this gap prevents both the online chunk-executor verify path and the offline replay-verify tool from detecting them — the two independent watchdogs both share the same blind spot, since they call the same comparator.

### Recommendation
Extend `ensure_match_transaction_info` (or its callers) to independently compute and compare the state-checkpoint hash (and, if enabled, hot-state/position-state checkpoint hashes) against `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` whenever these are present, rather than only validating write-set and event hashes. If per-transaction verification is structurally impossible (since checkpoint hashes are computed once per checkpoint boundary across a batch, not per `TransactionOutput`), the checkpoint-hash comparison must be added at the checkpoint-boundary aggregation point in both `ChunkExecutor::verify_execution` and `replay_on_archive::execute_and_verify`, mirroring the check already resolved by the TODO comment before any dependent feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled.

### Proof of Concept
Not independently reproducible from static analysis alone — the code path itself (not a runtime exploit) is the vulnerability: any test that constructs a `TransactionOutput` with a correct write set/events but simulates a divergent state-checkpoint hash (e.g., by feeding a `TransactionInfo` with a mismatched `state_checkpoint_hash`) into `ensure_match_transaction_info` will observe `Ok(())` returned instead of an error, confirming the missing check: [6](#0-5) 

**Uncertainty / limitations**: I was not able to fully trace whether `state_checkpoint_hash` divergence is caught by some other independent mechanism further up the `ChunkExecutor` stack (e.g., an aggregate root-hash comparison performed after committing a checkpoint-aligned batch, outside `verify_execution`). If such an aggregate check exists elsewhere in the commit path, it would reduce the severity of this finding to a documentation/tooling gap in `replay_on_archive` only rather than a chunk-executor state-integrity gap. I could not locate such a check within the explored files, and the explicit TODO comment in the code itself corroborates that the gap is real and acknowledged by the Aptos developers, but did not state whether it's fully mitigated elsewhere.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
