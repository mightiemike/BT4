### Title
Rounding-truncated global weight accounting in TVM freeze/unfreeze native contracts causes `TotalNetWeight`/`TotalEnergyWeight` to diverge from zero even after all frozen balances are fully unfrozen - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java] / [File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java])

### Summary
The reported LiquidityPool bug is a class of issue where a global aggregate ("debt shares sum") is updated using a rounding-down calculation on withdrawal/repayment that is not symmetric with how it was accumulated, so the aggregate can never return exactly to zero even though every individual user's tracked balance has reached zero. The same structural pattern (asymmetric floor-division updates to a global weight/sum, keyed by per-transaction amounts rather than by delta-of-current-state) exists in java-tron's legacy TVM freeze/unfreeze native contracts that adjust `TotalNetWeight` / `TotalEnergyWeight`.

### Finding Description
`FreezeBalanceProcessor.execute` increments the chain-wide weight counters using `frozenBalance / TRX_PRECISION` (integer floor division) at freeze time: [1](#0-0) 

`UnfreezeBalanceProcessor.execute` decrements the same counters, again using `-unfreezeBalance / TRX_PRECISION` on the raw unfrozen amount: [2](#0-1) 

Both operations independently floor-divide the *transaction amount* by `TRX_PRECISION` rather than computing the delta between two already-floored "current state" snapshots (which is what the corresponding legacy actuator, `UnfreezeBalanceActuator`, does correctly via `oldNetWeight`/`newNetWeight` deltas computed from the account's total frozen balance before/after the operation): [3](#0-2) 

Because `FreezeBalanceProcessor`/`UnfreezeBalanceProcessor` allow multiple partial freeze/unfreeze operations per account (each rounding its own amount down independently, since `frozenCount` can accumulate across freeze calls before being fully unfrozen), the sum of independently-floored increments and decrements is not guaranteed to cancel out exactly, unlike a single delta computed on the aggregate balance. This mirrors the LiquidityPool bug's root cause: `shareChange` is computed per-repayment from `amount` rather than as an exact inverse of how the share was originally minted, so cumulative floor-division across multiple partial operations leaves dust in the global aggregate (`debtSharesSum` / `TotalNetWeight`) even when every individual account balance (`shareOfDebt` / `frozenBalance`) is exactly zero.

### Impact Explanation
If `TotalNetWeight`/`TotalEnergyWeight` retain small positive residual dust after all frozen balances chain-wide return to zero (or drift below the true sum of live weights due to accumulated rounding across many freeze/unfreeze cycles), this corrupts `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` computations used throughout bandwidth/energy allocation (e.g., `RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight`), producing durably incorrect global resource limits for all accounts on the network. This is a state/accounting divergence bug of Low impact (small dust amounts, self-correcting as more accounts freeze) but High likelihood, since floor-division on transaction amounts happens on every partial freeze/unfreeze call through this native-contract (TVM `freezeBalance`/`unfreezeBalance` precompile) code path.

### Likelihood Explanation
`FreezeBalanceProcessor`/`UnfreezeBalanceProcessor` are reachable by any unprivileged account via a smart contract invoking the legacy TVM freeze/unfreeze precompiles (`allowTvmFreeze`-gated). Any account can trigger this path with an arbitrary `frozenBalance` not a multiple of `TRX_PRECISION` (1,000,000 sun), and partial freeze/unfreeze sequences are explicitly supported (`frozenCount` 0 or 1, multiple unfreeze calls accumulate more frozen entries before expiry). This makes the rounding-drift pattern highly likely to occur in normal usage, though each individual occurrence's magnitude is bounded by `TRX_PRECISION - 1` sun-equivalent weight units.

### Recommendation
Compute `TotalNetWeight`/`TotalEnergyWeight` adjustments as the delta between the account's total frozen balance before and after the operation (as `UnfreezeBalanceActuator` already does for the legacy actuator path), rather than floor-dividing the transaction's raw `frozenBalance`/`unfreezeBalance` amount independently in `FreezeBalanceProcessor` and `UnfreezeBalanceProcessor`. This guarantees that after a full unfreeze, the account's contribution to the global weight is decremented by exactly the amount it was incremented by, eliminating the possibility of residual dust in the global aggregate.

### Proof of Concept
Conceptual scenario (not verified by test execution, since I could not run the code):
1. Account A freezes 1,999,999 sun for bandwidth via `FreezeBalanceProcessor` (`frozenBalance / TRX_PRECISION` = 1, since `TRX_PRECISION` = 1,000,000). `TotalNetWeight += 1`.
2. Account A later freezes an additional 1,999,999 sun (assuming multiple entries or after first entry expires and re-freezes), again `TotalNetWeight += 1` — total weight added = 2, but the account's actual total frozen balance is 3,999,998, whose "true" weight (using the delta approach) would be `3,999,998 / 1,000,000 = 3` were it computed atomically, or conversely could be less if unfrozen partially.
3. Account A fully unfreezes both entries at different times, each via `UnfreezeBalanceProcessor`, decrementing `TotalNetWeight -= (1,999,999 / 1,000,000) = 1` each time — total decrement = 2.
4. Net effect: `TotalNetWeight` returns to its pre-freeze value in this specific example, but because increments and decrements are computed independently per-call rather than as a single delta over the account's aggregate state, sequences with different partial-freeze/partial-unfreeze amounts (e.g., freezing 1,000,001 and 999,999 in two calls, then unfreezing the combined 2,000,000 in a way that hits the "expired-frozen-list" branch which sums multiple `Frozen` entries into one `unfreezeBalance`) can produce a decrement (`2,000,000/1,000,000=2`) that does not exactly match the sum of independent per-call increments (`1+0=1`), leaving `TotalNetWeight` with a `-1` drift versus the true value, i.e., a residual imbalance analogous to the reported "debt shares remain after full repayment."

**Note on confidence:** I was unable to fully trace every call path (e.g., all callers of `FreezeBalanceProcessor`/`UnfreezeBalanceProcessor`, and whether `allowTvmFreeze` is enabled in current mainnet configuration, since freeze v1 may be deprecated in favor of Freeze V2) or execute a concrete test to confirm the exact drift amount and whether other invariant checks elsewhere in the codebase (e.g., `RepositoryImpl` harden-mode BigInteger paths) already mitigate this for the V1 freeze path specifically. This should be verified with a targeted unit test exercising repeated partial freeze/unfreeze sequences via the TVM precompile before treating this as confirmed exploitable drift.
