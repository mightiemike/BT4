### Title
`ensure_match_transaction_info` omits the position-state (and hot-state) checkpoint hashes, letting `replay_on_archive`/debugger report a successful replay despite a diverging authenticated state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-replay integrity check used by `db-tool`'s `replay_on_archive` and `aptos-debugger`/CLI tooling to confirm that a locally re-executed transaction matches the `TransactionInfo` that was actually committed to the ledger accumulator. The function verifies `status`, `gas_used`, the write-set hash (`state_change_hash`), and `event_root_hash`, but never checks `TransactionInfoV1`'s `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The gap is explicitly flagged by an in-code `TODO(trading-native)` comment, confirming it is a known, unaddressed hole rather than a benign omission.

### Finding Description
`TransactionInfoV1` carries multiple proof-bearing roots beyond the write-set/event hashes: `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) `position_state_checkpoint_hash` [1](#0-0) . These fields are populated from `StateCheckpointOutput`, which is derived by extending the position/state Merkle summaries during `DoStateCheckpoint::run` and `compute_position_checkpoint`, and they become part of the on-chain-committed `TransactionInfo` that clients verify via accumulator proofs [2](#0-1) .

`ensure_match_transaction_info` is the sole comparator used to confirm a re-executed `TransactionOutput` (from a local VM re-execution) is equivalent to the previously-committed `TransactionInfo`: [3](#0-2) 

It checks `status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash`, then returns `Ok(())` — it never reads or compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`. The trailing comment in the function itself states this exact gap: [4](#0-3) 

This function is invoked directly in the replay-verification hot loop of `db-tool replay-on-archive`, whose entire purpose is to detect divergence between locally re-executed VM outputs and the historically committed ledger: [5](#0-4) 

Because the comparator ignores the checkpoint-hash fields, if the persisted-state/hot-state/native-position Merkle tree logic (or a future serialization/versioning change to `PositionSlot`, `native_position_iter`, or `compute_position_checkpoint`) diverges from the originally committed root while write-set, events, gas, and status remain byte-identical, `replay_on_archive` will report a clean, successful replay. It also means any hard-fork-only divergence confined to the checkpoint hash computation (e.g. an unintended difference in how `parent_latest.extend(...)` merges position writes across versions, or key hashing changes in `PositionSlot`) would go completely undetected by the tool whose specific job is to catch exactly this class of bug.

### Impact Explanation
This breaks the "authenticated state-view output must stay bound to the correct proof context" invariant for the one tool designed to detect it: an operator or auditor running `replay-on-archive` to confirm ledger integrity after an upgrade, migration, or suspected divergence can get a false "all good" result while the position/hot-state root that consensus and light clients actually trust has silently diverged from what local execution produces. Since `COMPUTE_TRADING_NATIVE_STATE_ROOTS` gates whether `position_state_checkpoint_hash` is consensus-verified at all [6](#0-5) , a bug in that subsystem (native-position JMT extension logic) that corrupts the persisted checkpoint root would not be caught by replay-verify tooling, delaying detection of a genuine committed-state corruption or hard fork until much later (or never, if this is the only verification mechanism used in an incident response).

### Likelihood Explanation
The comparator gap is unconditional and always active whenever `ensure_match_transaction_info` is called with a `TransactionInfoV1` carrying checkpoint hashes — no attacker action is required, and no privileged access is needed to trigger it; it simply silently under-verifies. The self-documented `TODO(trading-native)` comment confirms the authors are aware the check is incomplete, and explicitly warns it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" — indicating the feature may currently be enabled or planned for enablement while the verification gap remains open.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` (when present) against locally-recomputed equivalents, mirroring the existing `ensure!` pattern for `write_set_hash`/`event_root_hash`. At minimum this must be resolved before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network relying on `replay_on_archive`/debugger for integrity verification.

### Proof of Concept
No exploit transaction is required since this is a verification-omission bug, not a state-corruption-inducing one on its own. Local proof:
1. `TransactionOutput::ensure_match_transaction_info` source shows only 4 fields checked (`status`, `gas_used`, `write_set_hash`, `event_root_hash`) with no reference to `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` anywhere in the function body [3](#0-2) .
2. `TransactionInfo` (V1) exposes `position_state_checkpoint_hash()` as a distinct, consensus-relevant accessor populated during ledger update [7](#0-6) , confirming the field exists and is meant to be authenticated but is excluded from the comparator.
3. `replay_on_archive.rs::execute_and_verify` calls this exact function as the pass/fail gate for its replay loop, with no additional checkpoint-hash comparison anywhere else in the file [8](#0-7) .

Constructing a live divergence in the native-position Merkle extension logic to actually trigger a false-positive replay is not something that can be verified without executing the code (out of scope for static/index-based review); the above establishes the root cause and confirms the comparator's blind spot is real and reachable in the primary replay-verification tool.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
