## Analysis

The GOAT bug class is: **a check computed from a live, externally-donatable balance is used to build a value that must match across independent evaluations, and an attacker can grief it for the cost of a token transfer.** Push Chain's TSS fund-migration flow has a structurally identical pattern.

### Root cause

`GetFundMigrationSigningRequest` computes the amount to sweep from the old TSS address as `balance − gasCost − L1Fee`, where `balance` is fetched live from the source chain's RPC when no `Balance` is pre-supplied: [1](#0-0) 

The coordinator calls this once to build the signing setup (`createFundMigrationSignSetup` → `buildFundMigrationTransaction` with `claimedAmount=nil`, i.e. "query chain for balance"): [2](#0-1) 

Each participant then **independently re-queries the balance** to rebuild the same hash for verification, in `verifyFundMigrationSigningRequest`: [3](#0-2) 

Since the old TSS address is a fixed, publicly-derivable address (`DeriveEVMAddressFromPubkey(migrationData.OldTssPubkey)`), and the balance is queried independently by the coordinator and by every participant at different wall-clock times over the p2p round-trip, **any unprivileged external actor can send a dust native-token transfer to that address between those queries**. This changes the computed `maxTransfer`, causing the participant's independently rebuilt `signingReq.SigningHash` / `TSSFundMigrationAmount` to differ from the coordinator's, and the participant explicitly rejects the round:

> `"fund migration signing hash mismatch: our computed hash does not match coordinator's hash"`

This is the direct analog of GOAT's `aEthValue = _geth.balanceOf(address(this))` check breaking because an attacker can donate tokens between the moment the check-relevant balance is captured and the moment it's consumed/compared — except here the "compare" happens across independently-polling honest TSS participants rather than a single transaction, making the race window (network round trip + multiple RPC calls) considerably larger and easier to hit than a single-block front-run.

### Impact

Every time a `KEYGEN` rotates the TSS key, all externally-locked funds under the old key must be migrated via this exact signing flow. An attacker who repeatedly sends negligible-value dust transfers to the known old-TSS address whenever a migration round is attempted can reliably desynchronize the coordinator's and participants' independently-queried balances, causing signature rounds to fail validation and preventing threshold-signature quorum from completing. Because the attack costs only gas/dust and can be repeated indefinitely and cheaply (exactly the "cost reduced to gas fees" property in the source report), a persistent attacker can keep the migration from ever finalizing, freezing protocol funds under a retired TSS key — an unprivileged, non-network-level denial of service that maps to the in-scope "permanent freezing ... of protocol-controlled funds" and "TSS coordination" impact categories.

### Likelihood

Requires only: (1) knowledge of the old TSS address, derivable by anyone from public `OldTssPubkey` data as soon as a keygen event is emitted, and (2) the ability to send a normal token transfer on the external chain — both trivially available to any unprivileged external actor, with no reliance on malicious validators, peers, or privileged roles.

### Recommendation

Do not have participants independently re-query a live, attacker-influenceable balance for verification. Instead, have the coordinator's claimed balance/amount (or the resulting `TSSFundMigrationAmount`) be the single source of truth that participants validate for *plausibility* (e.g., bounded by a snapshot balance recorded at event-confirmation time, before the signing round begins) rather than for exact equality against a fresh RPC read taken at an unsynchronized later moment. Alternatively, snapshot and persist the balance in the `FundMigrationInitiatedEventData` at the point the on-chain `FundMigration` record is created (a value all UVs already vote on/observe), and have both the coordinator and participants derive `maxTransfer` from that persisted, agreed-upon value instead of a fresh live RPC call each participant performs on their own schedule.

func (c *Coordinator) createFundMigrationSignSetup(ctx context.Context, eventData []byte, partyIDs []string, assignedNonce *uint64) ([]byte, *common.UnsignedSigningReq, error) {
	var migrationData utsstypes.FundMigrationInitiatedEventData
	if err := json.Unmarshal(eventData, &migrationData); err != nil {
		return nil, nil, fmt.Errorf("failed to unmarshal fund migration event data: %w", err)
	}

	// Load old keyshare as a sanity check; keyID bytes are derived from the string.
	if _, err := c.keyshareManager.Get(migrationData.OldKeyID); err != nil {
		return nil, nil, fmt.Errorf("failed to load keyshare for old keyId %s: %w", migrationData.OldKeyID, err)
	}
	keyIDBytes := deriveKeyIDBytes(migrationData.OldKeyID)

	signingReq, err := c.buildFundMigrationTransaction(ctx, eventData, assignedNonce, nil /* query chain for balance */)
	if err != nil {
		return nil, nil, fmt.Errorf("failed to build fund migration transaction: %w", err)
	}

	participantIDs := make([]byte, 0, len(partyIDs)*10)
	for i, partyID := range partyIDs {
		if i > 0 {
			participantIDs = append(participantIDs, 0)
		}
		participantIDs = append(participantIDs, []byte(partyID)...)
	}

	setupData, err := session.DklsSignSetupMsgNew(keyIDBytes, nil, signingReq.SigningHash, participantIDs)
	if err != nil {
		return nil, nil, fmt.Errorf("failed to create fund migration sign setup: %w", err)
	}

	return setupData, signingReq, nil
}
