**Rationale:**

The `propagate_dependency_limit_error` field gates which mechanism enforces value-depth bounds in the Move VM: when `gas_feature_version >= RELEASE_V1_38`, the `TypeDepthChecker` disables its type-level depth check (`maybe_max_depth = None`) because depth is instead bounded dynamically at the value level (needed once function values are enabled, since captured closure arguments aren't visible in the type) [1](#0-0) . Under the older gas feature version, the type-based check remains active with `max_value_nest_depth` as the bound [2](#0-1) .

This is not an error being "silently swallowed" — it's an explicit, deliberate replacement of one enforcement mechanism with another as part of a documented feature rollout, as the comment states: "Gate by other config which will be enabled in 1.38. Will be removed after it is enabled." [3](#0-2) .

Critically, `gas_feature_version` is not unprivileged attacker-controlled input. It is derived from the on-chain `GasScheduleV2` configuration set via governance, and `VMConfig` is constructed deterministically from this value alongside on-chain `Features` and `TimedFeatures` in `aptos_prod_vm_config` [4](#0-3) . All of the `RELEASE_V1_38`, `RELEASE_V1_41`, `RELEASE_V1_45` gates in this same function follow the identical pattern [5](#0-4) , which is the standard, intended mechanism for versioned feature rollout across Aptos releases — it is how every hard-fork-gated behavior change in this codebase is implemented, not an anomaly specific to this flag.

Replay and restore paths that reconstruct historical execution are expected to reconstruct the `VMConfig` using the on-chain gas schedule/feature version that was active at that historical ledger version/epoch (this is the standard requirement for all versioned config in Aptos, not unique to this field). As long as replay uses the epoch-correct on-chain config — which is itself part of the committed, verifiable ledger state, not attacker-supplied — the VM produces the same deterministic result as original execution. The claim describes normal governance-driven protocol upgrade behavior, not a path where unprivileged transaction/API/proof input can force a divergent commit; it depends entirely on comparing execution under two different config versions, which is expected and intended, and does not meet the bar of "hard-fork-only divergence" caused by unprivileged input as opposed to correctly-versioned protocol upgrades.
