## Finding

Based on my investigation, I found a concrete state-persistence divergence bug in the order-matching logic that mirrors the reported pattern (tokens/value returned to a user, but the tracking record used to determine future availability/validity is not updated), which in java-tron's `MarketSellAssetActuator` can lead to a **double refund of the same order's remaining sell-token quantity**.

### Title
Maker order remainder returned to user balance without persisting updated order state, enabling double-refund via cancel - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
In `matchSingleOrder`, when a match would yield a rounding-caused zero buy amount for the maker, the code refunds the maker's remaining sell-token quantity to their account and marks the order inactive in memory, then returns early — **skipping** the `orderStore.put(makerOrderCapsule...)` call that persists this state on every other code path. The DB-persisted order record keeps its stale `ACTIVE` state and non-zero `sellTokenQuantityRemain`, even though the tokens have already been credited back to the user's balance.

### Finding Description
`matchSingleOrder` handles the "taker > maker" branch as follows: [1](#0-0) 

Specifically, when `makerBuyTokenQuantityReceive == 0`: [2](#0-1) 

The maker's remaining sell-token quantity is credited back to the maker's balance via `returnSellTokenRemain`, which also zeroes `orderCapsule.setSellTokenQuantityRemain(0L)` in memory: [3](#0-2) 

However, the function then `return`s immediately, bypassing the `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule)` call that exists later in the method for the normal (non-early-return) code path: [4](#0-3) 

Because the mutated `makerOrderCapsule` (with `State.INACTIVE` and `sellTokenQuantityRemain == 0`) is never written back to `orderStore`, the persisted order record retrieved by `orderId` still reflects its pre-match state: `State.ACTIVE` (or whatever it was before) with the original non-zero `sellTokenQuantityRemain`. This is the same accounting-divergence root cause as the external report: value is moved out of the "pool" (the maker's escrowed sell tokens are returned to their spendable balance) while the tracking record that gatekeeps future access is not updated to reflect that movement.

### Impact Explanation
`MarketCancelOrderActuator.validate()` and `.execute()` both operate on the record fetched directly from `orderStore`: [5](#0-4) 

If the owner subsequently cancels this same order, `isActive()` still returns true (stale persisted state), so validation passes, and `execute()` calls `MarketUtils.returnSellTokenRemain` a second time on the stale, non-zero `sellTokenQuantityRemain`: [6](#0-5) 

This credits the same sell-token quantity to the user's balance a second time — a direct token/TRX duplication (accounting/fund-creation impact), analogous to the reported "idleETH" desync that made returned funds unreachable/mismatched from tracked state, except here the divergence is exploitable to create value out of thin air rather than merely lock it.

### Likelihood Explanation
The trigger condition (`makerBuyTokenQuantityReceive == 0` due to integer-division rounding when `takerBuyTokenQuantityRemain > makerOrderCapsule.getSellTokenQuantityRemain()`) is reachable by any unprivileged user simply by placing sell/buy orders with quantities/prices chosen to produce this rounding edge case, then calling `MarketCancelOrderActuator` on the maker order afterward. No special privileges are required — only ordinary `MarketSellAssetContract` and `MarketCancelOrderContract` transactions.

### Recommendation
Persist `makerOrderCapsule` to `orderStore` (and update its `State`) *before* returning in the `makerBuyTokenQuantityReceive == 0` branch of `matchSingleOrder`, exactly as done on the normal exit path at line 486, so the stored order state and the account balance changes remain consistent at every return point.

### Proof of Concept
1. Attacker creates maker sell order O for token A (sell A, buy TRX) with quantities chosen (e.g., `sellQuantity=200`, `buyQuantity=100`) so that a later matching taker order produces `makerBuyTokenQuantityReceive == 0` under `MarketUtils.multiplyAndDivide` integer division (per the in-code comment example at lines 466-477 of `MarketSellAssetActuator.java`).
2. A taker submits an opposing `MarketSellAssetContract` order that matches against O and triggers the `takerBuyTokenQuantityRemain > makerOrderCapsule.getSellTokenQuantityRemain()` ("taker > maker") branch, hitting the `makerBuyTokenQuantityReceive == 0` sub-case.
3. `returnSellTokenRemain(makerOrderCapsule)` credits O's remaining sell-token quantity back to the attacker's balance; the function then returns without calling `orderStore.put(...)`, leaving the persisted `orderStore` record for O with `State.ACTIVE` and the original non-zero `sellTokenQuantityRemain`.
4. Attacker submits `MarketCancelOrderContract` for order O. `MarketCancelOrderActuator.validate()` reads the stale persisted record, sees `isActive() == true`, and passes.
5. `MarketCancelOrderActuator.execute()` calls `MarketUtils.returnSellTokenRemain` again on the stale non-zero quantity, crediting the attacker's balance a second time with the same tokens — duplicating funds.

**Uncertainty**: I was not able to fully inspect `MarketOrderIdListCapsule.removeOrder` (used in the outer `matchOrder` loop) within the available context to confirm whether it independently deletes the `orderStore` entry in a way that could pre-empt this scenario. The core defect — the missing `orderStore.put` call on the early-return path, in contrast to every other path in the same function — is directly confirmed from the cited source. If `removeOrder` does not delete/overwrite the `orderStore` record (which its signature suggests it does not, since it primarily manipulates the price-index linked list), the double-refund path described above is valid as analyzed.
