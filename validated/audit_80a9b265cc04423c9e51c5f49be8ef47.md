### Title
`isSafe` in `validate-redirect-url.ts` accepts protocol-relative redirect targets, allowing host-injection into embedded redirect URLs - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts`)

### Summary
`isSafe`/`sanitizeRedirectUrl` is meant to constrain a redirect target to the app's own domain, but it never compares the resolved `URL.host` against the `domain` argument. A protocol-relative input such as `//evil.com` resolves via `new URL(redirectUrl, domain)` to `https://evil.com/`, passing every check in `isSafe` (no `///` file-URI match, no whitespace, valid `https:` protocol, no `//` in `pathname`), so the function returns `true` and `sanitizeRedirectUrl` returns a URL pointing at an attacker-controlled host instead of the configured app domain.

### Finding Description
`isSafe` in `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts` performs these checks, in order:
1. `FILE_URI_MATCH` (`/\/\/\//`) rejects triple-slash (file-URI) inputs like `///path` [1](#0-0) .
2. `WHITESPACE_CHARACTER` rejects inputs with spaces [2](#0-1) .
3. `url = new URL(redirectUrl, domain)` resolves the URL [3](#0-2) .
4. `INVALID_RELATIVE_URL` (`/[/\\][/\\]/`) is checked only against `url.pathname`, not the raw input or the resolved host [4](#0-3) .
5. Protocol and SSL checks are performed [5](#0-4) .

Crucially, **there is no comparison of `url.host` (or `url.origin`) against the `domain` parameter anywhere in this function.** A protocol-relative input like `//evil.com` has only two slashes (doesn't trip `FILE_URI_MATCH`, which requires three), no whitespace, resolves via the WHATWG URL spec to `https://evil.com/` (host taken from the input, protocol inherited from the base `domain`), has `pathname` `"/"` (no double-slash), a valid `https:` protocol, and satisfies `requireSSL`. Every guard passes, and `isSafe` returns `true`, so `sanitizeRedirectUrl(domain, '//evil.com')` returns `new URL('https://evil.com/')` — a URL entirely outside `domain`.

`sanitizeRedirectUrl` is consumed by `renderAppBridge` (`packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/render-app-bridge.ts:21`), which embeds the sanitized destination directly into an inline `<script>window.open(destination, target)</script>` tag served inside the embedded-app HTML shell [6](#0-5) . If any caller path allows a user/attacker-influenced value to reach `redirectTo.url` (e.g., a `return_to`/reload-style query parameter processed during the OAuth/auth-code flow that calls `redirect`/`renderAppBridge`), this check fails to constrain the destination to the app's own origin, defeating the intended invariant that "embedded app URL host is verified."

I was unable to fully trace, within the remaining budget, which specific top-level entrypoint (e.g. `authenticate.ts`'s auth-code-flow, `billing/request.ts`) feeds a raw, attacker-supplied string into `redirect.toApp`/`renderAppBridge`'s `redirectTo.url` versus a value the app developer controls; several found call sites pass developer/billing-config strings, not obviously raw query parameters. Confirming an end-to-end unprivileged HTTP-request-to-open-redirect chain would require checking `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/redirect.ts`, `strategies/auth-code-flow.ts`, and `authenticate.ts` in more depth than tool budget allowed.

### Impact Explanation
Regardless of the exact caller, this is a real logic defect in the library's own redirect-domain allowlisting function: it advertises host-restriction semantics (function is invoked with an app `domain` to constrain the destination) but silently permits protocol-relative escapes to arbitrary hosts. Where this helper is reachable with attacker-influenced input, it enables open redirect out of the embedded iframe context (`window.open(...)`), which can be leveraged for phishing or, combined with any flow that appends session/OAuth state to the redirect, token/state leakage to an attacker-controlled origin.

### Likelihood Explanation
Exploitability depends entirely on whether a given call site passes attacker-controlled input as `redirectUrl`. The `isSafe`/`sanitizeRedirectUrl` API itself provides no protection against this class of input in any caller, so any current or future call site that forwards a query parameter, header, or other externally influenced string to `sanitizeRedirectUrl` is immediately vulnerable to a two-character bypass (`//`) — this is a low-effort, highly repeatable bypass once such a call site exists.

### Recommendation
In `isSafe`, after resolving `url = new URL(redirectUrl, domain)`, explicitly re-validate that `url.host === new URL(domain).host` (or that `url.origin === new URL(domain).origin`) before returning `true`. Do not rely solely on `pathname`/protocol checks, since protocol-relative (`//host`) and absolute (`https://host`) inputs both parse successfully via `new URL(input, base)` and can change the host silently.

### Proof of Concept
```ts
import {sanitizeRedirectUrl} from '../validate-redirect-url';

describe('protocol-relative URL bypass', () => {
  it('incorrectly treats //evil.com as safe relative to the app domain', () => {
    const APP_URL = 'https://my-app.example.com';

    const result = sanitizeRedirectUrl(APP_URL, '//evil.com/phish');

    // BUG: host is evil.com, not my-app.example.com
    expect(result.host).toBe('evil.com');
    expect(result.host).not.toBe(new URL(APP_URL).host);
  });
});
```
Expected (buggy) result: the test passes, showing `sanitizeRedirectUrl` returns `https://evil.com/phish` for a call whose `domain` argument is `https://my-app.example.com`, confirming `isSafe` fails to enforce host containment for protocol-relative inputs.

const FILE_URI_MATCH = /\/\/\//;
const INVALID_RELATIVE_URL = /[/\\][/\\]/;
const WHITESPACE_CHARACTER = /\s/;
const VALID_PROTOCOLS = ['https:', 'http:'];

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }
