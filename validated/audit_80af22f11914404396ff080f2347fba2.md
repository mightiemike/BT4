## Analog Found

### Title
Wallet Contract permanently freezes caller deposits when the hard-coded Address Registrar reference becomes stale — ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `near-wallet-contract` (NEAR's EVM-emulation Wallet Contract, deployed as a global contract used by many eth-implicit accounts) hard-codes the account ID of the "Address Registrar" it depends on at compile time via `ADDRESS_REGISTRAR_ACCOUNT_ID: &str = std::include_str!("ADDRESS_REGISTRAR_ACCOUNT_ID")` [1](#0-0) . This is analogous to the reported bug pattern: a critical external dependency address is captured once and never re-validated, so if that dependency's real location changes, the operation that relies on it becomes permanently unavailable — except here the concrete on-chain consequence is worse than a simple revert: the caller's attached deposit is never refunded when the stale-dependency call fails, permanently trapping funds.

### Finding Description
When a relayer submits an RLP-encoded Ethereum-style base-token transfer whose target is another eth-implicit account, `inner_rlp_execute` builds a cross-contract call to the registrar using the compiled-in `ADDRESS_REGISTRAR_ACCOUNT_ID`: [2](#0-1) 

The result of that lookup is consumed in `address_check_callback`. If the registrar call fails (`PromiseResult::Failed`) — which will happen deterministically and permanently once the registrar account referenced by the baked-in constant no longer matches the real, current registrar (e.g. it was redeployed/migrated to a new account, the exact "AAVE changes lending pool address" scenario from the report) — the callback simply returns an error and **does not refund the caller's deposit**: [3](#0-2) 

Contrast this with the sibling failure path `rlp_execute_callback`, which *does* correctly refund `caller_deposit` on `PromiseResult::Failed`: [4](#0-3) 

The deposit attached by the external caller in the `#[payable]` `rlp_execute` entrypoint is added to the Wallet Contract's balance immediately as part of the call, and the only mechanism for the caller to get it back if the transaction is refused/fails is an explicit refund promise built from `caller_deposit`: [5](#0-4)  Since `address_check_callback`'s failure branch omits that refund, once the hard-coded registrar reference is stale, every affected transfer deterministically fails at this step and the attached NEAR is stranded in the Wallet Contract with no code path to return it.

### Impact Explanation
This matches the accepted impact category of **permanently frozen funds**. Once the compiled-in `ADDRESS_REGISTRAR_ACCOUNT_ID` no longer resolves to a functioning registrar contract (analogous to the lending-pool address rotation in the report), any external caller/relayer who submits a base-token transfer to a not-yet-verified eth-implicit target via `rlp_execute` with an attached deposit will have that deposit permanently locked in the Wallet Contract, since the failure path that is actually taken skips the refund logic present elsewhere in the same file. This affects every deployed instance of the Wallet Contract (it is a global contract used broadly), not a single account.

### Likelihood Explanation
Reaching this state requires the precondition described in the source report itself (an external, administrative change — here, the registrar being redeployed/migrated so the baked-in account ID becomes wrong), which is out of the caller's control, same as in the original finding. Once that precondition holds, the vulnerable path is trivially and deterministically reachable by any unprivileged account via a single `rlp_execute` call with a nonzero deposit — no special privileges, validator status, or malicious peer behavior needed.

### Recommendation
In `address_check_callback`'s `PromiseResult::Failed` branch, mirror the refund logic already present in `rlp_execute_callback`: if `caller_deposit` is `Some`, issue a `promise_batch_action_transfer` back to the caller before returning the failure `ExecuteResponse`. More generally, avoid baking a single external dependency's account ID into the contract binary without a refresh/rollback mechanism; consider validating/parsing it once at a safer boundary and ensuring every failure branch that can be reached after a deposit has been accepted includes a refund path.

### Proof of Concept
1. Assume the Address Registrar account referenced by the compiled `ADDRESS_REGISTRAR_ACCOUNT_ID` value is redeployed/migrated to a different account (or otherwise becomes non-functional) after the Wallet Contract binary was built — the same "provider changes the underlying address" precondition as in the original report.
2. Any external account calls `rlp_execute(target, tx_bytes_b64)` on a Wallet Contract instance with an attached deposit, where `tx_bytes_b64` encodes a base-token transfer whose `to` resolves to `TargetKind::EthImplicit` (i.e., `address_check: Some(address)` in `EOABaseTokenTransfer`).
3. `inner_rlp_execute` schedules the registrar `lookup` call against the stale `ADDRESS_REGISTRAR_ACCOUNT_ID` (lib.rs:419-431).
4. That cross-contract call fails since the registrar no longer exists/responds at that account.
5. `address_check_callback` observes `PromiseResult::Failed` and returns an `ExecuteResponse{ success: false, ... }` without issuing any refund promise (lib.rs:140-148).
6. The caller's attached deposit remains in the Wallet Contract's balance permanently, with no remaining code path to reclaim it.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }
