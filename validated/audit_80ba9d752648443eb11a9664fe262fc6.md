## Title
`claim-staker-rewards-for-signer` in pox-5.clar can be called directly (without going through a signer-manager's payment logic) to zero out a staker's unclaimed sBTC rewards without any transfer occurring - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`claim-staker-rewards-for-signer` is a `define-public` function meant, per its own doc comment, to be "only callable by the signer manager contract" as an internal bookkeeping step that a signer-manager trait implementation calls *after* it has actually paid a staker out. In practice the function enforces no invariant that a payment happened, and no invariant that `contract-caller` is a signer legitimately associated with the given `staker`/`reward-cycle`/`bond-index` triple beyond what falls out of state being namespaced by `contract-caller` itself. [1](#0-0) 

### Finding Description
The function settles the staker's earned rewards and then unconditionally zeroes `staker-unclaimed-rewards-for-cycle` for that key, regardless of whether the settled `earned` amount is zero, positive, or whether any sBTC transfer ever occurred in the same transaction: [2](#0-1) 

This mirrors the structure of the reported `withdrawToken()` bug: a state-mutating "detach"/"mark-claimed" operation that is exposed as a standalone public entry point instead of being gated so it can only run as an atomic sub-step of a real settlement flow that guarantees value actually moves. Compare with the sibling function `update-claimable-rewards`, which is `define-private` and can only run inside `claim-rewards`' controlled flow (which requires `(asserts! (> total-rewards u0) ERR_NO_CLAIMABLE_REWARDS)` and performs the sBTC transfer atomically before touching state): [3](#0-2) [4](#0-3) 

`claim-staker-rewards-for-signer`, by contrast, is `define-public`, uses `contract-caller` directly as the "signer" identity with no `(asserts! ...)` verifying that `contract-caller` is the staker's actual registered signer for that cycle/bond, and it neither requires `earned > 0` nor performs any token transfer itself - it is documented as trusting the calling contract to have already paid out the staker in the same call.

### Impact Explanation
Because a signer-manager contract is any arbitrary user-deployed contract implementing `signer-manager-trait` (e.g., `contrib/core-contract-tests/contracts/signer-manager.clar`), a malicious or buggy signer-manager can call `claim-staker-rewards-for-signer` for a staker registered under it without pairing the call with an actual sBTC transfer to that staker. This zeroes `staker-unclaimed-rewards-for-cycle` (and advances `staker-rewards-per-token-settled-for-cycle`) for that staker/cycle/bond, permanently erasing their claim to already-earned rewards recorded in pox-5's own accounting - a reward loss bounded to the fees/rewards owed to that staker for that cycle, without requiring a majority of signers, an admin, or any other party's key. This satisfies the High-severity bar ("a poison or reward mis-payment bounded to fees").

### Likelihood Explanation
Reachable by any single, unprivileged actor: deploy a contract implementing `signer-manager-trait`, register/attract a staker to stake through it (or become the signer of record for cycles the staker already has shares in), then call `claim-staker-rewards-for-signer` directly on `.pox-5` without performing the corresponding sBTC transfer. No cooperation from other signers, miners, or node operators is required, and the call is a normal contract-call transaction.

### Recommendation
Make `claim-staker-rewards-for-signer` `define-private` (or otherwise unreachable except as an atomic step of a function that itself performs the sBTC transfer to the staker and requires `earned > 0`), mirroring how `update-claimable-rewards` is scoped as `define-private` and only invoked from within `claim-rewards`'s guarded, atomic flow. If it must remain public for signer-manager composability, require the transfer and the "earned > 0" check to happen in the same call, and consider recording/asserting that the corresponding sBTC actually left the contract before zeroing the staker's unclaimed balance.

### Proof of Concept
1. Deploy a minimal contract `C` implementing `signer-manager-trait` that does nothing except forward calls (or is entirely benign initially).
2. Have staker `S` stake via pox-5 using `C` as `signer-manager`, accruing `staker-unclaimed-rewards-for-cycle` for `(reward-cycle, bond-index, signer: C, staker: S)` as pool rewards are distributed and `S`'s shares accrue rewards per token (see `settle-staker-rewards` / `get-earned-staker-rewards`): [5](#0-4) 
3. From `C` (or any contract where `contract-caller` resolves to `C`), directly call `.pox-5.claim-staker-rewards-for-signer(S, reward-cycle, bond-index)` without transferring any sBTC to `S`.
4. Observe: `staker-unclaimed-rewards-for-cycle` for `S` under `C` is now `u0`, and `get-earned-staker-rewards` returns `0` for that key going forward, even though `S` never received the corresponding sBTC - the reward is permanently lost with no token movement, unlike the guarded `claim-rewards` path which enforces `total-rewards > 0` and performs the transfer atomically before zeroing state.

**Note:** I was unable to fully trace, within the tool budget available, whether any pox-5-level guard (e.g., a reentrancy or trait-authorization check) elsewhere in the contract restricts which principals can legitimately be treated as a "signer" for a given staker at the time `claim-staker-rewards-for-signer` is invoked (i.e., whether `contract-caller` must already match a `staker-signer-cycle-membership` entry before this function has any real effect). The `validate-no-reentrancy` check present in the function only guards against reentrancy, not against an unauthorized/self-serving `contract-caller`. Verifying this precisely would require reading the definitions of `staker-signer-cycle-membership`, `get-staker-shares-staked-for-cycle`, and the full `signer-manager-trait` contract, which exceeded the remaining investigation budget.

;; As a signer manager contract, mark a specific staker as having claimed
;; rewards. This is used to mutate internal rewards settlement state.
;;
;; This is only callable by the signer manager contract.
(define-public (claim-staker-rewards-for-signer
        (staker principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let ((rewards-info (settle-staker-rewards contract-caller reward-cycle bond-index staker)))
        ;; ensure no reentrancy through signer-manager trait calls
        (try! (validate-no-reentrancy))
        (map-set staker-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: contract-caller,
            staker: staker,
        }
            u0
        )
        (print {
            topic: "claim-staker-rewards-for-signer",
            signer-manager: contract-caller,
            staker: staker,
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            rewards-claimed: (get earned rewards-info),
        })
        (ok rewards-info)
    )
)
