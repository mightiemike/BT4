### Title
Silent, unlogged early-return in ancient storage packing lets an unprivileged user permanently block ancient append-vec combining, causing disproportionate storage growth - (File: accounts-db/src/ancient_append_vecs.rs)

### Summary
`combine_ancient_slots_packed_internal` computes a packed layout for ancient (old-epoch) storages and then checks whether the computed number of packed storages (`pack.len()`) fits into the number of available `target_slots_sorted`. If it does not fit, the function silently returns, discarding all packing work for that invocation with **no logging, no stats counter, and no external signal** — unlike the sibling guard just above it (`many_ref_accounts_can_be_moved`), which does emit `datapoint_info!` and `log::info!` when it aborts. This mirrors the reported bug class: a threshold check silently blocks a core maintenance operation (there, token exchange; here, ancient storage compaction), and the fix suggested in the report — add an event/log so operators can detect and correct the situation externally — is exactly what is missing on this path.

`target_slots_sorted` is populated by `calc_accounts_to_combine`, and its size is driven by how many ancient slots contain *only* ref-count-1 accounts vs. how many contain ref-count>1 ("many ref") accounts that must stay pinned to specific slots: [3](#0-2) 

An unprivileged user can influence this ratio directly and cheaply: by creating many distinct accounts that are duplicated across several old ("ancient") slots (i.e., accounts with `ref_count > 1` whose live copy sits in a high slot), the number of usable `target_slots_sorted` shrinks relative to `pack.len()`, since `pack()` must still lay out all "one_ref" and "many_refs_newest" accounts into storages sized to `ideal_storage_size`. When `pack.len() > target_slots_sorted.len()`, the whole combine invocation returns with zero external evidence of the skipped work.

Because `combine_ancient_slots_packed` is invoked repeatedly by the background service on the same growing set of ancient slots, an adversary who keeps re-touching a moderate set of pubkeys so they remain duplicated across many old slots can keep tripping this specific silent-return branch on every pass, indefinitely preventing packing of ancient append vecs into fewer, larger storages — all without any log line, metric, or `datapoint_info!` entry that operators/monitoring can act on, unlike every other early-exit in this function.

### Impact Explanation
Ancient append vec combining exists specifically to bound the number of on-disk storage files/roots and keep per-slot storage overhead low. Silently and repeatedly failing to pack means storages accumulate unbounded relative to what the system was designed to maintain, producing disproportionate storage growth and repeated wasted CPU/I/O work (the function still does the expensive `get_unique_accounts_from_storage_for_combining_ancient_slots`, `shrink_collect`, and `PackedAncientStorage::pack` computation on every call before discarding the result). Because there is no telemetry for this specific failure mode, an operator has no way to detect that ancient combining is stuck versus merely idle, unlike the `many_ref_accounts_can_be_moved` failure which is visible via logs/metrics.

### Likelihood Explanation
Reaching this condition requires only ordinary account writes from any user: duplicating a moderate number of pubkeys' liveness across many old (ancient-eligible) slots is achievable through normal transaction activity over time, with no special privileges. The condition is a function of `many_refs_newest`/`accounts_keep_slots` sizing vs. `target_slots_sorted` sizing, both of which are influenced by ordinary write patterns, so the likelihood of an attacker triggering and sustaining it is moderate to high given persistence.

### Recommendation
Add explicit logging/metrics (mirroring the existing `many_ref_accounts_can_be_moved` branch) on the `pack.len() > accounts_to_combine.target_slots_sorted.len()` early return, e.g. a `datapoint_info!("shrink_ancient_stats", ("pack_overflow", 1, i64))` and `log::info!` with `pack.len()` and `target_slots_sorted.len()`, so operators can detect and diagnose sustained ancient-pack failures externally, consistent with the report's recommendation to "add an event so that you can record and correct such situations from the outside."
