## Title
Permissionless `ExchangeCreateContract` allows attacker to set an arbitrary, extremely skewed initial price for a TRC10/TRX trading pool with no minimum liquidity or cooldown - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
Just as the Vader `VaderPoolFactory.createPool()` finding allowed an attacker to unilaterally fix a pool's price at creation time by depositing 1 wei of a new coin and 10^18 wei of Vader, java-tron's built-in Bancor-style AMM exchange (`ExchangeCreateContract`) lets any account with a balance permissionlessly create a TRX↔TRC10 (or TRC10↔TRC10) trading pool and set its `first_token_balance`/`second_token_balance` to any positive values it chooses, fixing the initial exchange ratio with no sanity checks, no minimum liquidity requirement, and no cooldown before trading is enabled.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks that `firstTokenBalance` and `secondTokenBalance` are each greater than zero and below the global `exchangeBalanceLimit`; it performs no check relating the deposited amounts to any real market price, and imposes no minimum absolute liquidity: [1](#0-0) 

`execute()` then immediately creates the `ExchangeCapsule` with these attacker-chosen balances and persists it to both the V1 and V2 exchange stores, making the pool tradeable in the very next transaction — there is no cooldown period and no mechanism to revoke or adjust a maliciously-priced pool once created: [2](#0-1) 

Once created, `ExchangeTransactionActuator` lets anyone (including the creator) trade against the pool using the Bancor-formula pricing derived purely from `exchangeCapsule.transaction(...)`, which is driven entirely by the ratio set at creation time — there is no external price oracle or deviation check: [3](#0-2) 

This mirrors the reported root cause precisely: `createPool`/`ExchangeCreateContract` is permissionless, the first depositor unilaterally fixes the price, there is no minimum-liquidity floor or cooldown, and there is no way to revoke a mispriced pool.

### Impact Explanation
An attacker can create an `Exchange` pool between TRX and any TRC10 token they control (or any two TRC10 tokens) with a grossly skewed ratio (e.g., depositing 1 unit of token X against a huge amount of TRX, or vice versa), then immediately use `ExchangeTransactionContract` to trade against that pool at the manipulated price. Because there is no whitelist restricting which token pairs can be paired and no floor on liquidity, this can be used to create decoy/spoofed pools with the same token pair but artificial pricing that could mislead other users or wallets/exchanges that enumerate exchanges by ID, or be used in self-dealing schemes to extract value if other unsuspecting counterparties (bots, aggregators) interact with the pool. This is an accounting/pricing-integrity impact within TRON's on-chain DEX feature — funds moved through the actuator are real TRX/TRC10 balances (see the balance mutations in `execute()`), not simulated state.

### Likelihood Explanation
`ExchangeCreateContract` is a standard, permissionless transaction type available to any account holding sufficient balance to pay `calcFee()` and the deposit amounts; no privileged role or governance approval is required, matching the "front-run createPool" scenario in the source report almost exactly. The only "cost" is holding the deposited token amounts and the exchange-create fee, which can be made arbitrarily small (e.g., depositing 1 unit of the smaller token), so the attack is cheap and immediately actionable.

### Recommendation
Introduce a minimum absolute liquidity requirement for both sides of a newly created exchange pool (analogous to the report's "1M Vader" suggestion, scaled appropriately for TRX/TRC10 economics), and/or require a cooldown period after `ExchangeCreateContract` before `ExchangeTransactionContract` trades against that exchange ID are accepted, giving the network/governance time to flag or react to obviously mispriced pools. Consider also emitting stronger warnings/metadata (e.g., flag pools whose implied price deviates enormously from any known reference) for downstream tooling.

### Proof of Concept
1. Attacker account holds `1` unit of TRC10 token `X` and `100_000_000_000000` (an arbitrarily large amount) of TRX (or vice versa; amounts are entirely attacker-chosen).
2. Attacker submits `ExchangeCreateContract{first_token_id=TRX, first_token_balance=100_000_000_000000, second_token_id=X, second_token_balance=1}` — validated only by the `>0` and `< exchangeBalanceLimit` checks shown in `ExchangeCreateActuator.doValidate()` (lines 201-208), with no price-sanity check.
3. `ExchangeCreateActuator.execute()` immediately persists this pool to `ExchangeStore`/`ExchangeV2Store` (lines 78-119), making it live.
4. Any account (including the attacker via a second address) can immediately call `ExchangeTransactionContract` against this `exchange_id`, receiving `anotherTokenQuant` computed off the skewed ratio via `exchangeCapsule.transaction(...)` (`ExchangeTransactionActuator.java` lines 61-98), extracting value at the attacker-chosen mispriced rate with no cooldown or revocation possible.
