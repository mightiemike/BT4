### Title
Unchecked sentinel value from `parseEnergyFee` corrupts `effective_energy_price` in Ethereum-compatible transaction event triggers - (File: `framework/src/main/java/org/tron/core/services/event/BlockEventGet.java`)

### Summary
This is a direct structural analog to the sUSDe oracle bug: an external "price" value is fetched from a historical record and consumed by downstream code **without checking for the function's documented sentinel/error value**, causing a bogus number (`-1`) to be propagated into consumer-facing data instead of being rejected or defaulted.

### Finding Description
`JsonRpcApiUtil.parseEnergyFee(long timestamp, String energyPriceHistory)` walks the `ENERGY_PRICE_HISTORY` string and returns the matching historical energy price for a given timestamp. If no entry satisfies `timestamp > time` (e.g., the history string is malformed, empty, or the timestamp predates every recorded entry), the function explicitly returns `-1` as a sentinel "not found" value: [1](#0-0) 

One call site, `Wallet.getEnergyFee(long timestamp)`, correctly checks for this sentinel and falls back to the current default fee: [2](#0-1) 

However, the second call site, `BlockEventGet.getEnergyPrice(long blockTime)`, calls the same parser and returns its result **directly, with no `-1` check**: [3](#0-2) 

This unchecked value is then used as `energyUnitPrice` and fed into every `TransactionLogTriggerCapsule` built for a block when Ethereum-compatible transaction log triggers are enabled: [4](#0-3) 

This mirrors the sUSDe bug precisely: an oracle-style getter returns an unchecked value (`usdePriceInUsd` in the report, `-1` sentinel here) that is consumed by downstream accounting logic (`effectiveGasPrice`/`energyUnitPrice`) without validating it is a legitimate, non-error value.

### Impact Explanation
Since `-1` is silently accepted as a valid "energy unit price", any Ethereum JSON-RPC compatible consumer relying on the emitted transaction log trigger event's per-transaction gas/energy price field (`effective_energy_price`, computed from `energyUnitPrice`) will receive a corrupted, negative value instead of the real price or a safe fallback. Downstream indexers, exchanges, and gas-fee estimators consuming this event stream would compute incorrect fee totals or reject/misprocess the data. This is a data-integrity/DoS-adjacent issue in the event/log-trigger subsystem rather than a direct fund-loss bug, since it does not affect on-chain consensus or the actuator-level fee logic (which is unaffected — `ReceiptCapsule` uses `dynamicPropertiesStore.getEnergyFee()` directly for real billing).

### Likelihood Explanation
This path only triggers when the operator has explicitly enabled `isTransactionLogTriggerEthCompatible()` event plugin support, and only during the narrow window before `EnergyPriceHistoryLoader` populates history or if the persisted `ENERGY_PRICE_HISTORY` string ever fails to contain an entry satisfying `timestamp > time` (e.g., a block timestamp at or before the very first history entry, or right after a fresh chain reset/migration). It's a real but conditional/edge-case data integrity defect rather than a broadly reachable RPC exploit — it is not attacker-triggerable on demand, but it can occur naturally from genesis/history construction edge cases and is unconditionally unguarded in code, unlike the twin call site in `Wallet.java` which was patched with the correct check.

### Recommendation
Mirror the guard already present in `Wallet.getEnergyFee(long timestamp)` inside `BlockEventGet.getEnergyPrice`: check if `parseEnergyFee(...)` returns `-1`, and if so fall back to `manager.getDynamicPropertiesStore().getEnergyFee()` (the current default), instead of propagating the sentinel value into `TransactionLogTriggerCapsule`.

### Proof of Concept
1. Configure the node with the Eth-compatible transaction log trigger enabled (`isTransactionLogTriggerEthCompatible() == true`).
2. Arrange (or observe naturally at genesis/history-migration) a block whose `block.getTimeStamp()` is not strictly greater than any timestamp recorded in `ENERGY_PRICE_HISTORY` (e.g., default/empty history state before `EnergyPriceHistoryLoader.doWork()` completes, per `DEFAULT_ENERGY_PRICE_HISTORY` initialization logic referenced in `DynamicPropertiesStore.java` lines 883-892).
3. Call `BlockEventGet.getTransactionLogTrigger(block, solidNum)` for that block.
4. Observe `getEnergyPrice(block.getTimeStamp())` returns `-1` from `JsonRpcApiUtil.parseEnergyFee`, and this `-1` is passed unchecked into the constructed `TransactionLogTriggerCapsule`, corrupting the emitted event's energy price field for all transactions in the block.

```java
  public static long parseEnergyFee(long timestamp, String energyPriceHistory) {
    String[] priceList = energyPriceHistory.split(",");

    for (int i = priceList.length - 1; i >= 0; i--) {
      String[] priceArray = priceList[i].split(":");
      long time = Long.parseLong(priceArray[0]);
      long price = Long.parseLong(priceArray[1]);
      if (timestamp > time) {
        return price;
      }
    }

    return -1;
  }
```
