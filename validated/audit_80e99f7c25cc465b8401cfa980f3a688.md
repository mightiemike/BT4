### Title
Unbounded `UniversalPayload.Data` / `Inbound.RawPayload` accepted through `MsgVoteInbound` causes permanent UTX state bloat and repeated-vote storage amplification - (File: `x/uexecutor/types/inbound.go`, `x/uexecutor/types/universal_payload.go`)

### Summary
Neither `Inbound.ValidateBasic()` nor `UniversalPayload.ValidateBasic()` impose any length limit on the hex-encoded `RawPayload`/`Data` fields that originate from an attacker-controlled source-chain gateway event. This is the direct analog of the Hats `details`/`imageURI` bug: an unprivileged external-chain user can emit a gateway event with an arbitrarily large calldata payload, and honest Universal Validators — behaving correctly by faithfully relaying what they observed — will submit that oversized payload via `MsgVoteInbound`. The payload is then durably persisted in the `UniversalTx` state and re-processed by every voting validator.

### Finding Description
- `Inbound.ValidateBasic()` (`x/uexecutor/types/inbound.go:90-121`) only checks that `SourceChain`, `TxHash`, `Sender`, `LogIndex`, and `TxType` are non-empty/well-formed. It performs **no size check** on `RawPayload` or `VerificationData`. [1](#0-0) 
- `UniversalPayload.ValidateBasic()` (`x/uexecutor/types/universal_payload.go:24-65`) validates that `Data` is valid hex, but places **no upper bound on its length**. [2](#0-1) 
- `Canonicalize()` only trims/normalizes the hex blob; it does not truncate or reject on size. [3](#0-2) 
- On ballot finalization, `NormalizeForTxType()` decodes `RawPayload` into `UniversalPayload.Data` and only clears `RawPayload` "to save storage" — the same byte volume is retained inside `UniversalPayload.Data`. [4](#0-3) 
- The finalized `Inbound` (including the oversized payload) is stored permanently and append-only inside `UniversalTx.InboundTx` via `CreateUniversalTx`, which per the module's own documentation is never pruned. [5](#0-4) 
- Before ballot finalization, each individual UV's vote is separately recorded via `RecordInboundVote` (called once per validator, per `VoteInbound` call), meaning the full-size payload is written to the KV store **once per voting validator** prior to finalization — amplifying the storage/write cost relative to a single copy. [6](#0-5) 

Because `MsgVoteInbound` is on the gasless allowlist, `DeductFeeDecorator` and `MinGasPriceDecorator` both skip fee/min-gas-price enforcement for these transactions, so the honest UV submitting the vote pays no fee for the extra bytes it is forced to relay. [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
An unprivileged attacker on a source chain (e.g., Ethereum) can call the real Push Chain gateway contract with a very large `data` field. This is a completely legitimate, unprivileged, single-transaction action on the source chain — there is no need to slowly grow the field over many transactions as in the original Hats bug, because there's no on-chain "growth" step here; the attacker can attach a large payload directly on the source-chain gateway call (bounded only by the source chain's own tx-size/gas limits, e.g. Ethereum calldata limits, which are far larger than what Push Chain's own validation permits). Honest UVs, which must faithfully relay what they observed to reach ballot consensus, are then forced to:
1. Submit multiple gasless votes (`MsgVoteInbound`) each carrying the full oversized `RawPayload`, at zero fee cost to anyone.
2. Have the payload permanently persisted, append-only, in `UniversalTx` state that is never pruned (per the module's own documented lifecycle).
3. Have the payload subsequently read back for execution attempts (`ExecuteInbound` → `CallUEAExecutePayload`/`CallExecuteUniversalTx`), and be queryable indefinitely via the module's UTX query endpoints.

This causes unbounded, gasless, permanent state growth and repeated processing/storage cost triggered entirely by an unprivileged external actor — a direct DoS-via-unbounded-string analog to the Hats `details`/`imageURI` issue, but here the impact is state-bloat/permanent-storage-cost amplification rather than a single expensive read.

### Likelihood Explanation
High likelihood of the trigger condition (an attacker can freely call any real gateway contract with large calldata at will, no coordination or privileged access required), but the magnitude is constrained by two factors I could not fully verify in this pass:
- Whatever maximum tx-size / mempool `max-tx-bytes` limits CometBFT/the node's `app.toml`/`config.toml` enforce (I found no explicit override of `MaxTxBytes` in the scoped repo, implying default CometBFT/Cosmos limits, typically ~1MB per tx) — this bounds a single vote's payload size but does not eliminate the amplification-by-repeated-votes or permanent-storage-growth issue, since an attacker can repeat this across many inbound events over time.
- Whether `EncodeUniversalPayloadToRaw`/gateway-side encoding imposes any additional cap not visible in the indexed portion of the repository.

### Recommendation
Introduce an explicit maximum length (in bytes) for `Inbound.RawPayload`, `Inbound.VerificationData`, and `UniversalPayload.Data` in both `Inbound.ValidateBasic()` and `UniversalPayload.ValidateBasic()`, rejecting the vote before any state (including per-validator `RecordInboundVote` entries) is written. The cap should be small enough to bound worst-case UTX storage growth and query/read cost per UTX entry (e.g., an EVM calldata cap consistent with reasonable payload-execution gas limits), and should be enforced identically regardless of source-chain namespace (EVM ABI-encoded vs. Solana Borsh-encoded paths).

### Proof of Concept
Conceptual PoC (not executed against a live node):
1. Deploy/interact with the real Push Chain gateway contract on a supported source chain (e.g., Sepolia) as an ordinary, unprivileged user.
2. Submit a bridging transaction of type `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` whose ABI-encoded `UniversalPayload.data` field is filled with the maximum calldata the source chain allows (bounded only by that chain's own limits, which can be much larger than anything Push Chain enforces since Push Chain enforces nothing).
3. Observe that honest UVs pick up the event and submit `MsgVoteInbound` (gasless, no fee) carrying the full oversized `RawPayload` — verified by inspecting `Inbound.ValidateBasic()` (`x/uexecutor/types/inbound.go:90-121`) and confirming no size guard exists, and by inspecting the gasless allowlist that exempts this message from fee checks (`app/README.md:161-170`).
4. After ballot finalization, confirm via `GetUniversalTx` that the full-size payload is persisted permanently in `UniversalTx.InboundTx.UniversalPayload.Data` (`x/uexecutor/types/inbound.go:53-64`, `x/uexecutor/keeper/msg_vote_inbound.go:109-119`), with no pruning mechanism, and repeat across multiple inbounds to demonstrate unbounded, gasless, attacker-driven state growth.

func (p Inbound) ValidateBasic() error {
	// Validate source_chain (must follow CAIP-2 format) — needed for UTX key
	chain := strings.TrimSpace(p.SourceChain)
	if chain == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain cannot be empty")
	}
	if !strings.Contains(chain, ":") {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain must be in CAIP-2 format <namespace>:<reference>")
	}

	// Validate tx_hash — needed for UTX key
	if strings.TrimSpace(p.TxHash) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "tx_hash cannot be empty")
	}

	// Validate sender — needed for revert recipient fallback
	if strings.TrimSpace(p.Sender) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "sender cannot be empty")
	}

	// Validate log_index — needed for UTX key
	if strings.TrimSpace(p.LogIndex) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "log_index cannot be empty")
	}

	// Validate tx_type enum — needed to route execution
	if _, ok := TxType_name[int32(p.TxType)]; !ok || p.TxType == TxType_UNSPECIFIED_TX {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid tx_type: %v", p.TxType)
	}

	return nil
}
