### Title
Outbound funds burned/locked when `IsChainOutboundEnabled` is false while `IsChainInboundEnabled` remains true — asymmetric pause causes permanent loss of PRC20 (Scroll USDC-pause analog) - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
The Scroll finding describes an L1/L2 gateway pair with independently-settable pause flags: L1 deposits keep succeeding while L2 finalization is paused, permanently trapping the user's tokens with no refund path. Push Chain has the structurally identical asymmetry between `ChainEnabled.IsInboundEnabled` and `ChainEnabled.IsOutboundEnabled` on the same `ChainConfig`, checked at two different, non-atomic points in the inbound→outbound pipeline.

### Finding Description
`VoteInbound` gates only on `IsChainInboundEnabled` before executing an inbound: [1](#0-0) . For a `FUNDS_AND_PAYLOAD` inbound whose `UniversalPayload` calls the `UniversalGatewayPC` contract's `withdraw`/`withdrawAndExecute`, execution: (1) deposits/mints PRC20 to the user's UEA, then (2) runs the payload, which burns PRC20 and emits a `UniversalTxOutbound` event as part of the same committed EVM call (`DerivedEVMCall` with `commit=true`) — see the deposit call pattern in [2](#0-1) .

Only afterward, when the receipt logs are parsed to build the outbound record, is `IsChainOutboundEnabled` checked: [3](#0-2) 

If the destination chain's outbound is disabled, `BuildOutboundsFromReceipt` returns an error and **no outbound is attached to the UTX** — confirmed by the integration test asserting `utx.OutboundTx` is empty while the UTX itself is still created: [4](#0-3) .

Because the EVM call that burned the PRC20 (inside `UniversalGatewayPC.withdraw`) was already committed before this check runs, and there is no compensating re-mint, revert-outbound, or rescue path wired for this specific failure mode (the rescue path in `AttachRescueOutboundFromReceipt` only fires for inbound-side failures — CEA deposit failure or a `REVERTED` `INBOUND_REVERT` outbound — not for "burned but outbound-disabled"), the burned tokens have no reachable outbound and no reachable refund. This is the same invariant break as the Scroll report: two independently toggled pause/enable flags on the two ends of a bridge flow, checked at different times, where the state-mutating (burn) side commits before the gating check on the other side is enforced.

### Impact Explanation
Any ordinary user submitting an inbound whose payload triggers a gateway withdraw to a chain currently configured with `IsOutboundEnabled=false` (while `IsInboundEnabled=true`) has their PRC20 permanently burned with the corresponding value never released on the destination chain and no `OutboundTx` record to retry against. This is a permanent, unrecoverable loss of user-controlled funds, matching the "permanent freezing / permanent loss ... unauthorized burn ... without unauthorized refund" allowed-impact category. It requires no privileged action by the attacker — an ordinary, honestly-submitted cross-chain transaction is sufficient; the only precondition is the (independently, legitimately) configured chain-enabled state, exactly as in the Scroll case where the precondition was the operator's independent pause toggles, not attacker privilege.

### Likelihood Explanation
`IsInboundEnabled` and `IsOutboundEnabled` are two independent booleans on `ChainConfig`/`ChainEnabled` that admins can set differently per chain (e.g., to halt outbound liquidity on a congested/compromised destination chain while still accepting inbound deposits), and nothing in the vote/execute pipeline cross-checks them before the EVM call that performs the burn executes. Any user whose payload happens to route through `withdraw`/`withdrawAndExecute` while this configuration exists will trigger the loss deterministically — the existing integration test in the repo demonstrates the exact zero-outbound outcome.

### Recommendation
Check `IsChainOutboundEnabled` for the destination chain *before* invoking the payload that can call `withdraw`, or make the outbound-enabled check part of the same atomic/cached execution used for `ExecutePayload`/inbound execution so the whole EVM call (including the burn) rolls back if outbound is disabled. Alternatively, if outbound is disabled post-hoc, ensure `BuildOutboundsFromReceipt`'s failure path automatically creates a compensating re-mint/refund/rescue-eligible record instead of silently dropping the outbound.

### Proof of Concept
1. Admin/registry state: `ChainConfig` for `eip155:X` has `IsInboundEnabled=true`, `IsOutboundEnabled=false` (independently settable, as shown in `test/integration/uexecutor/chain_enabled_test.go`).
2. A user submits (or a validator set votes to quorum on) a `FUNDS_AND_PAYLOAD` inbound whose `UniversalPayload.To` is `UniversalGatewayPC` and whose `Data` calls `withdraw`/`withdrawAndExecute` targeting `eip155:X`.
3. `VoteInbound` passes the `IsChainInboundEnabled` gate and executes the inbound: PRC20 is deposited then burned by the gateway call, emitting `UniversalTxOutbound`.
4. `BuildOutboundsFromReceipt` evaluates `IsChainOutboundEnabled(eip155:X)` → `false`, returns an error; `attachOutboundsToUtx` is never called for this event.
5. Resulting `UniversalTx` has no `OutboundTx` entries (per the existing test assertion), while the user's PRC20 balance was already burned — funds are unrecoverable through any exposed rescue/refund path.

**Uncertainty flagged:** I was unable to locate the Solidity source of the production `UniversalGatewayPC.withdraw` in this repository (the deployed bytecode is referenced only as a constant/system contract; test setup notes explicitly that the *test* fixture contract skips the burn step). I relied on the test-file comments and the surrounding keeper logic to establish that burn/withdraw execution is expected to precede outbound-record creation in production; if the production contract instead defers the burn until after an outbound-enabled check performed on-chain (which I could not verify given index limits), the severity of this specific path would be reduced. I'd recommend starting a full Devin session with repository/tooling access to pull and review the actual deployed `UniversalGatewayPC` bytecode/ABI or source to confirm the exact ordering of burn vs. event emission before treating this as fully confirmed.

		require.True(t, found, "UTX should still be created even when outbound is disabled")
		require.Empty(t, utx.OutboundTx, "no outbound should be attached when destination chain outbound is disabled")
	})
