## Finding: Unenforced `TokenConfig.Enabled` Flag Permits Continued PRC20 Minting After Token Is Disabled

### Title
Minting/bridging of an external asset continues after `TokenConfig.Enabled` is set to `false` - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
The external report describes a class of bug where a config field intended to gate/limit an asset's treatment (E-Mode collateral factor) is not actually re-checked at the point of use, so the previously-granted elevated treatment silently persists after the permission is revoked. The direct analog in Push Chain's `x/uregistry`/`x/uexecutor` is the `TokenConfig.Enabled` field: `TokenConfig` explicitly documents this field as "Whether this token is enabled for minting/bridging" [1](#0-0) , but none of the inbound execution paths that call `GetTokenConfig` and then mint/deposit PRC20 (`depositPRC20`, `ExecuteInboundGas`, and the gas-and-payload equivalent) check this flag before proceeding.

### Finding Description
`GetTokenConfig` simply returns whatever `TokenConfig` row is stored, with no filtering on `Enabled` [2](#0-1) . Every downstream consumer in `x/uexecutor` that fetches a token config for the purpose of minting/depositing PRC20 uses the returned `NativeRepresentation.ContractAddress` unconditionally:

- `depositPRC20` fetches the token config and calls `CallPRC20Deposit` without checking `tokenConfig.Enabled` [3](#0-2) .
- `ExecuteInboundGas` fetches the token config for the gas-swap path and proceeds to resolve/deploy the UEA and swap without an `Enabled` check [4](#0-3) .
- `buildRevertOutbound` also reads `tokenCfg.NativeRepresentation` without checking `Enabled` [5](#0-4) .

By contrast, the analogous `ChainConfig.Enabled` (`IsInboundEnabled`/`IsOutboundEnabled`) *is* actively enforced: `VoteInbound` explicitly calls `IsChainInboundEnabled` and rejects the vote if disabled [6](#0-5) , and `MsgExecutePayload`/outbound creation similarly check chain-level enablement (confirmed by dedicated tests) [7](#0-6) . No equivalent test or code path exists asserting that `TokenConfig.Enabled == false` blocks minting — this is the precise "E-Mode" analog: a per-asset permission field exists to gate elevated/special treatment (minting eligibility), but the enforcement point never re-checks it, so once a token has been whitelisted (`Enabled: true`) and an admin later disables it (`MsgUpdateTokenConfig` with `Enabled: false`), an unprivileged user's inbound funds transfer still triggers a mint of the PRC20, exactly as if the token were still enabled.

### Impact Explanation
If this holds under the "wrong balance" lens (matching the required impact "corruption of PRC20 or native asset accounting"), this allows unauthorized/continued minting of a PRC20 representation for an asset the protocol has explicitly disabled — e.g. because the asset was found to be compromised, has an inflation/decimals bug, or is being sunset. This is a mint-authorization/accounting bypass: attacker-controlled inbound deposits keep minting PRC20 tokens whose backing legitimacy the protocol intended to revoke, exposing the protocol to reserve/backing mismatches and potential bad debt if the PRC20 is later used for swaps, collateral, or redemption elsewhere in the system.

### Likelihood Explanation
Reaching this requires only an ordinary, unprivileged user submitting a normal cross-chain funds transfer (an "inbound") for an asset that an admin has disabled via `MsgRemoveTokenConfig`/`MsgUpdateTokenConfig` — no validator collusion, no privileged action by the attacker, and no chain-level disablement is needed since only the token-level `Enabled` flag is stale/unchecked. Since `RemoveTokenConfig` deletes the config entirely (causing `GetTokenConfig` to error and route to revert, as validated by `TestInboundGas`) [8](#0-7) , the more concrete trigger is `MsgUpdateTokenConfig` setting `Enabled: false` while leaving the row (and its `NativeRepresentation`) present — a supported, distinct admin workflow from removal. I was unable to find (with the available search budget) any code path that reads `tokenConfig.Enabled` at all in `x/uexecutor`, which increases confidence that this flag is dead/unenforced.

### Recommendation
Add an explicit `Enabled` check on the `TokenConfig` returned by `GetTokenConfig` at every point it gates PRC20 minting/depositing/bridging (`depositPRC20` in `x/uexecutor/keeper/handler.go`, `ExecuteInboundGas` in `x/uexecutor/keeper/execute_inbound_gas.go`, and the funds-and-payload/gas-and-payload equivalents), mirroring the existing `IsChainInboundEnabled`/`IsChainOutboundEnabled` enforcement pattern. If a token is disabled mid-flight, the inbound should fail cleanly and produce an `INBOUND_REVERT`, consistent with how a missing token config is already handled.

### Proof of Concept
Conceptual reproduction (not independently executed, based on code paths read):
1. Admin adds a `TokenConfig` for `usdcAddress` on `eip155:11155111` with `Enabled: true` and a valid `NativeRepresentation.ContractAddress` (PRC20).
2. Admin later calls `MsgUpdateTokenConfig` to set `Enabled: false` for the same token/chain (config row remains, only the flag flips).
3. An unprivileged user submits a normal gateway deposit event on the source chain; Universal Validators vote `MsgVoteInbound`, which only checks `IsChainInboundEnabled` (chain-level), not the token's `Enabled` flag.
4. On ballot finalization, `ExecuteInboundGas`/`depositPRC20` calls `k.uregistryKeeper.GetTokenConfig(...)`, which returns the row unchanged; the mint/deposit proceeds because `tokenConfig.Enabled` is never inspected.
5. Result: PRC20 is minted for an asset the admin explicitly disabled, corrupting the protocol's intended accounting for that "de-listed" asset.

**Note on confidence**: I confirmed via `grep_search` that no occurrence of `tokenConfig.Enabled` (or similar) exists in `x/uexecutor/keeper/*.go`, and no dedicated integration test (analogous to `chain_enabled_test.go`) exists for token-level enablement. However, due to index size limits, I could not exhaustively rule out an enforcement check located in a file/branch not surfaced by the search (e.g., inside `execute_inbound_gas_and_payload.go` or `execute_inbound_funds_and_payload.go`, which were only partially read). If a Devin session with full repository access confirms `Enabled` is checked somewhere in those files, this finding should be downgraded or rejected.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
