## Finding

### Title
Replay‑verify integrity check silently ignores the state‑checkpoint (SMT/JMT) root, letting a diverged committed state pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the sole invariant checker used by the replay‑verify tool (`storage/db-tool/src/replay_on_archive.rs`), the chunk‑executor's `verify_execution` path (`execution/executor/src/chunk_executor/mod.rs`), and the Move debugger/CLI replay commands, only compares transaction status, gas used, the per‑transaction write‑set hash (`state_change_hash`), and the event root hash against the trusted `TransactionInfo`. It never compares the `state_checkpoint_hash` (nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) — the field that actually authenticates the accumulated Sparse/Jellyfish Merkle state root — leaving state‑commitment divergence undetected by the very tool meant to catch it.

### Finding Description
`ensure_match_transaction_info` explicitly checks only: [1](#0-0) 

and then a developer‑authored comment concedes the gap: [2](#0-1) 

The per‑transaction `write_set_hash` only authenticates the delta produced by a single transaction. The `state_checkpoint_hash` is a separate, independently computed value — the root of the Sparse/Jellyfish Merkle Tree after `batch_update`ing all state deltas accumulated since the last checkpoint, produced in a completely different code path (`DoStateCheckpoint`/`state_store` batch update, `storage/aptosdb/src/state_store/mod.rs`, `execution/executor/src/workflow/do_state_checkpoint.rs`). A bug confined to that accumulation/hashing path (e.g., an ordering issue in JMT batch updates, an incorrect hot‑state/position‑state root computation, or corrupted archive data for that specific field) would produce write sets whose *individual* hashes still match `state_change_hash`, yet whose *cumulative* root diverges from the authenticated `state_checkpoint_hash`. `ensure_match_transaction_info` cannot detect this because it never reads `txn_info.state_checkpoint_hash()`.

This function is the actual integrity gate for:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which is the mainnet/testnet replay‑verify safety net that re‑executes archived transactions and is expected to fail loudly on any divergence from the recorded ledger state: [3](#0-2) 
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, used when verifying a chunk of backup/state‑sync transactions against pre‑recorded `TransactionInfo`s: [4](#0-3) 

By contrast, the normal commit-time path (`DoStateCheckpoint::get_state_checkpoint_hashes` inside chunk execution) *does* validate the computed checkpoint hash against `known_state_checkpoints` when committing new chunks: [5](#0-4) 
so live state‑sync commit is protected. However, `verify_execution` (the explicit, standalone "verify" mode used for validated replay of historical data, and independently the replay‑on‑archive tool) relies exclusively on `ensure_match_transaction_info`, which the developers themselves flag as blind to checkpoint-root divergence.

### Impact Explanation
Replay‑verify (`replay_on_archive`) and `verify_execution` are the designated mechanisms for detecting non‑determinism or state‑computation bugs by replaying historical mainnet transactions and confirming the locally recomputed ledger state matches the authenticated on‑chain record. Because the state (and, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot‑state features are enabled, hot‑state and position‑state) checkpoint root is never compared, a hard‑fork‑class bug that corrupts only the accumulated Merkle root (while leaving individual write‑set hashes unaffected) — or corrupted/tampered archive data for that field — would be reported as a **successful, verified replay**. This directly matches the "hard‑fork‑only divergence during commit, replay, restore, or proof verification" and "wrong accumulator root ... accepted as valid" impact categories: it is the exact safety‑net whose entire purpose is to catch state‑root divergence, silently disabled for that one critical field.

### Likelihood Explanation
This is not a hypothetical exploit requiring an attacker with special privileges — any bug or data corruption confined to the state-checkpoint/JMT accumulation path (a plausible, previously‑seen class of bug distinct from per‑transaction write‑set computation) would trigger this gap automatically, with no adversarial action needed beyond the underlying divergence occurring. The gap is confirmed in-code by the developers' own TODO, indicating it is a known, currently-live limitation rather than a false positive.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`-derived (or freshly computed) state checkpoint hash(es) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` whenever those fields are `Some` in the trusted `TransactionInfo`, propagating the necessary post‑checkpoint SMT/JMT root(s) into the callers (`replay_on_archive.rs`, chunk executor `verify_execution`) so replay‑verify and state‑sync verification cannot report success while the authenticated state root has diverged.

### Proof of Concept
Conceptual (no working exploit possible purely from static review, but the code path is deterministic):
1. Introduce (or trigger) any divergence solely in the periodic Merkle accumulation step (e.g. a bug in `StateStore`/JMT `batch_update` ordering, or a corrupted `state_checkpoint_hash`/`position_state_checkpoint_hash` byte in an archive backup) that does not change any individual transaction's write set.
2. Run `replay_on_archive`/`ReplayVerifyCoordinator` (or the chunk executor's `verify_execution` path) over the affected version range.
3. `execute_and_verify` → `ensure_match_transaction_info` only checks status/gas/write_set_hash/event_root_hash — all of which remain unchanged — so `Ok(())` is returned, and the tool reports "no failed transactions," even though the actual ledger state (Merkle root) at that version has diverged from what is authenticated in the persisted `TransactionInfo`.
