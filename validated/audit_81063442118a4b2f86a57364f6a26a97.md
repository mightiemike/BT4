### Title
Race condition in `performTokenExchange` allows a stale in-flight request to wipe out a freshly obtained access token, causing denial of service of the auth handler - ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
`performTokenExchange` captures a session snapshot (`sessionToInvalidate`) via `loadSession` *before* performing the slow, asynchronous `api.auth.tokenExchange` network call, and later uses that stale snapshot to invalidate the stored access token on a 401 error. Because there is no optimistic-concurrency check or locking around `storeSession`, two concurrent requests for the same session token/shop can interleave such that a stale, pre-exchange session object overwrites a session that was already refreshed by another concurrent request — exactly the "resume past the target version" pattern described in the Aptos race condition (a delayed/stale operation completing after and clobbering more recent correct state).

### Finding Description
In `performTokenExchange`: [1](#0-0) 

`sessionToInvalidate` is set from `loadSession(sessionId)` at the very start of request handling, well before the network round trips to Shopify's token endpoint. Later, if the token exchange call for *this* request fails with a 401, the code invalidates whatever `sessionToInvalidate` was captured at the beginning of *this* request: [2](#0-1) 

`invalidateAccessToken` simply blanks the `accessToken` field on that (possibly stale) in-memory `Session` object and unconditionally upserts it back into storage: [3](#0-2) 

`storeSession` implementations across all storage backends perform a blind upsert (`INSERT ... ON CONFLICT DO UPDATE` / `REPLACE INTO` / `upsert`) keyed only by session id, with no version check against what is currently persisted, e.g.: [4](#0-3) 

Race sequence (same shop, `useOnlineTokens`/offline flow, concurrent client requests carrying the same or overlapping session tokens — reachable from any client holding a session token, no privileged access required):
1. Request A loads session `S1` (stale/expiring token) → `sessionToInvalidateA = S1`.
2. Request B arrives concurrently and also loads `S1` before A finishes → `sessionToInvalidateB = S1`.
3. Request A successfully exchanges for a fresh token and calls `storeSession(newSession)` — the shop's session now has a valid, current `accessToken`.
4. Request B's own token exchange fails with a 401 (e.g., transient Shopify-side error, revoked/duplicate `code`, or an attacker deliberately racing requests to trigger this branch).
5. Because `sessionToInvalidateB` is still the *pre-exchange* snapshot `S1` captured in step 2, `invalidateAccessToken` blanks `S1.accessToken` and blindly persists it, **overwriting the valid, freshly-stored session from step 3** with one that has `accessToken: undefined`.

This mirrors the Aptos bug class precisely: the "later"/authoritative write (A's fresh token) is subsequently clobbered by a "stale" operation (B's invalidation based on outdated state) that had no way to detect it was operating on outdated data.

### Impact Explanation
The result is a self-inflicted denial of service on the shop's authentication state: the shop's offline/online session in storage is nulled out even though a valid token had just been obtained, forcing all subsequent requests for that shop to re-enter the token-exchange/OAuth path, and in tight request bursts this can repeatedly race and thrash the stored session, degrading availability of the app for that merchant. Because `performTokenExchange` sits in the authenticated request handling path invoked on every request bearing a session token, this is a DoS of an auth handler, reachable by any client (including a malicious one deliberately firing concurrent/duplicate requests) that can present a session token for the shop.

### Likelihood Explanation
Triggering the race requires concurrent requests hitting the same shop's session-token auth path with timing such that one request's 401 failure occurs after another concurrent request's successful token refresh — a scenario more likely under normal embedded-app usage patterns (multiple parallel fetches from the frontend on load, App Bridge retries) or can be intentionally amplified by an attacker sending duplicate parallel requests with a session token they possess, deliberately provoking one branch to fail. No secret knowledge or privileged access is required beyond having a valid session token, which any authenticated merchant/customer browser session naturally has.

### Recommendation
- Re-fetch (or re-verify) the current stored session immediately before invalidating it in the 401 handler, rather than relying on a snapshot captured at the start of request processing.
- Use optimistic concurrency (e.g., compare-and-swap on a version/updated-at column, or only null out `accessToken` if it still matches the token that produced the 401) when calling `storeSession` from `invalidateAccessToken`.
- Consider serializing token-exchange/invalidate operations per session id (similar to the existing `IdempotentPromiseHandler` used for `afterAuth`) to prevent interleaved read-modify-write sequences across concurrent requests for the same shop/session.

### Proof of Concept
Not independently executable from static analysis alone; the race requires precise timing of two concurrent HTTP requests bearing session tokens for the same shop such that Request A's `storeSession(newSession)` (line 101/114 of `perform-token-exchange.ts`) completes strictly before Request B's `invalidateAccessToken(sessionToInvalidate, config)` (line 152) executes with a `sessionToInvalidate` captured (line 76-77) prior to A's write. This can be reproduced in an integration test by mocking `config.sessionStorage.loadSession` to return the same stale `Session` object to two concurrent invocations of `performTokenExchange`, then forcing the second invocation's `api.auth.tokenExchange` to reject with an `HttpResponseError` (code 401) after the first invocation's `storeSession` call has resolved, and asserting the persisted session no longer has the access token written by the first request.

import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}

  public async storeSession(session: Session): Promise<boolean> {
    await this.ready;

    // Note milliseconds to seconds conversion for `expires` property
    const entries = session
      .toPropertyArray(true)
      .map(([key, value]) =>
        key === 'expires'
          ? [key, Math.floor((value as number) / 1000)]
          : [key, value],
      );
    const query = `
      INSERT INTO "${this.options.sessionTableName}"
      (${entries.map(([key]) => `"${key}"`).join(', ')})
      VALUES (${entries
        .map((_, i) => `${this.client.getArgumentPlaceholder(i + 1)}`)
        .join(', ')})
      ON CONFLICT ("id") DO UPDATE SET ${entries
        .map(([key]) => `"${key}" = Excluded."${key}"`)
        .join(', ')};
    `;
    await this.client.query(
      query,
      entries.map(([_key, value]) => value),
    );
    return true;
  }
