### Title
Unbounded prefix scan in `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` allows DoS via anonymous RPC/HTTP request - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix()` performs an unbounded `prefixQuery` scan across the entire keyspace for a given address prefix, converts all matching entries into a list, sorts them, and returns the full result with no cap on the number of entries. This is reachable from anonymous, unauthenticated HTTP and gRPC requests via `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`, mirroring the reported bug class (an accessor that retrieves an unbounded range/set of records with no sanity limit, exposing the node to DoS).

### Finding Description
`DelegatedResourceAccountIndexStore.getWithPrefix` is invoked by `getIndex`/`getV2Index`: [1](#0-0) 

It calls `this.prefixQuery(key)` twice (once for the "to" prefix, once for the "from" prefix) and materializes the entire result set into `ArrayList`s, then sorts by timestamp and rebuilds two lists (`toAccounts`, `fromAccounts`) with no limit on size:
```
List<DelegatedResourceAccountIndexCapsule> tmpToList =
    new ArrayList<>(this.prefixQuery(key).values());
...
List<DelegatedResourceAccountIndexCapsule> tmpFromList =
    new ArrayList<>(this.prefixQuery(key).values());
```
Unlike sibling range/list accessors in the same codebase, this path has no sanity limit:
- `BlockStore.getLimitNumber`/`RpcApiService.getBlockByLimitNext` caps range span at `BLOCK_LIMIT_NUM = 100`: [2](#0-1) 
- `AssetIssueStore.getAssetIssuesPaginated` caps `limit` at `ASSET_ISSUE_COUNT_LIMIT_MAX`: [3](#0-2) 
- `Wallet.getPaginatedProposalList`/`getPaginatedExchangeList` cap `limit` at `PROPOSAL_COUNT_LIMIT_MAX`/`EXCHANGE_COUNT_LIMIT_MAX`: [4](#0-3) 

By contrast, `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` take only an address, apply no size limit, and pass the entire scanned result straight into the outbound protobuf response: [5](#0-4) 

The call is reachable via anonymous HTTP: [6](#0-5) 

and gRPC: [7](#0-6) 

Since delegated-resource relationships (`DelegateResourceActuator`/`FreezeBalanceActuator`) can be created by any account transacting on-chain (an unprivileged, broadcastable transaction type), an attacker can programmatically grow the `from`/`to` list for a single target address to an arbitrarily large size over many transactions, then repeatedly query `getDelegatedResourceAccountIndex` for that address to force the node to scan, materialize, sort, and serialize the entire unbounded set on every request.

### Impact Explanation
Each request against a "poisoned" address triggers a full keyspace prefix scan and in-memory sort/serialization of an unbounded number of entries, which can consume disproportionate CPU/memory/I-O on the node per request. Because this endpoint requires no privileged access (no API key, no witness/SR role) and can be invoked repeatedly and concurrently, an attacker who has first inflated the delegation index for an address can use this endpoint to degrade or exhaust node resources — a DoS via the RPC/HTTP API, consistent with the reported bug class.

### Likelihood Explanation
Likelihood is moderate-to-high: the endpoint is unauthenticated and always reachable; the only prerequisite is inflating the from/to accounts list, which requires the attacker to execute many `DelegateResourceContract`/`FreezeBalanceContract` (delegation) transactions to/from a target address — cheap in resources but requires many transactions/time to build a large index, and each of those transactions consumes bandwidth/energy from the attacker. Still, this is far less resource-intensive for the attacker than for the victim node servicing repeated unbounded-scan queries against that inflated index, echoing the asymmetry described in the original report.

### Recommendation
Add a sanity limit to `DelegatedResourceAccountIndexStore.getWithPrefix` (and its callers) analogous to `AssetIssueStore.getAssetIssuesPaginated`/`ASSET_ISSUE_COUNT_LIMIT_MAX`: cap the number of entries fetched/returned per prefix scan (e.g., via a `MAX_ACCOUNT_INDEX_ENTRIES` constant), and/or expose an offset/limit-paginated variant of `getDelegatedResourceAccountIndex` similar to `GetPaginatedAssetIssueList`, rejecting or truncating overly large lists at the store layer before serialization.

### Proof of Concept
1. From an attacker-controlled account, freeze balance and repeatedly call `DelegateResourceContract`/`FreezeBalanceContract` (with `receiverAddress` set) targeting a single victim address as either delegator or receiver, across many transactions, to grow that address's `to`/`from` accounts list in `DelegatedResourceAccountIndexStore` to a very large size (bounded only by chain throughput/attacker's own bandwidth/energy).
2. Send repeated anonymous HTTP requests to `/wallet/getdelegatedresourceaccountindex?value=<victim_address>` (see `GetDelegatedResourceAccountIndexServlet.doGet`) or the equivalent gRPC `GetDelegatedResourceAccountIndex` call.
3. Each request forces the full unbounded `prefixQuery` + sort + serialize path in `DelegatedResourceAccountIndexStore.getWithPrefix`, with no limit enforced anywhere in `Wallet.getDelegatedResourceAccountIndex` or the RPC/HTTP layer, unlike the capped `getBlockByLimitNext`/`getPaginatedAssetIssueList` endpoints — causing disproportionate resource consumption on the node per request.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,

    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
