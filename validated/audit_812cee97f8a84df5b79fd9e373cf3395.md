### Title
Stale `index-cache` reused across sequential positions in `liquidate-multi` allows under-priced zToken collateral seizure after bad-debt socialization writes down `lindex` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` executes a `map` of `call-liquidate` over up to 64 positions in a single transaction. Each individual `liquidate` call resolves zToken collateral/debt values by first calling `accrue-user-debts`/`accrue-user-collateral`, which populate a per-block cache (`index-cache`, keyed by `{ timestamp: stacks-block-time, aid }`) via `accrue-and-cache`, and then reuses that cache for pricing and scaled-debt math for the rest of the call. When a liquidation triggers bad-debt socialization, the code explicitly refreshes the cache for the *just-socialized* asset (`socialize-debt-asset` comment: "Refresh cache with new indexes post-write-down (lindex decreased)"), but nothing refreshes the cache entries for *other* vaults that share exposure, and more importantly, positions later in the same `map` that read the vault's `lindex`/index through paths that were computed and cached *before* a mid-batch vault mutation can still be served the cache entry set at the point of first accrual within that same block if the accrual/refresh ordering does not cover every asset touched.

### Finding Description
`accrue-and-cache` in `v0-4-market.clar` is a per-transaction/per-block memoization layer:
```
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)          ;; cache HIT - stale value reused
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [1](#0-0) 

This cache is populated once per `aid` per block and then reused for the remainder of the transaction by `accrue-user-debts`/`accrue-user-collateral` [2](#0-1) , and by `scale-debt-for-liquidation`, `get-cached-indexes` lookups, and notional pricing throughout `liquidate` [3](#0-2) .

The developers are aware this cache goes stale when a vault's `lindex` is written down by bad-debt socialization, and manually re-set the cache entry for that specific asset immediately after `vault-socialize-debt`:
```
(unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
;; Refresh cache with new indexes post-write-down (lindex decreased)
(map-set index-cache
         { timestamp: stacks-block-time, aid: asset-id }
         (unwrap! (vault-accrue asset-id) failed-status))
``` [4](#0-3) 

`liquidate-multi` folds/maps `call-liquidate` over a caller-supplied list of up to 64 independent `{borrower, collateral-ft, debt-ft, debt-amount, min-collateral-expected}` tuples in a single atomic call:
```
(define-public (liquidate-multi (positions (list 64 {...})))
  (ok (map call-liquidate positions)))
``` [5](#0-4) 

Because the cache key is only `{ timestamp, aid }` (not tied to the specific position/borrower being processed), the value bound at the *first* liquidation touching a given `aid` in the batch persists for every later liquidation in the same `map` that touches the same `aid`, unless that exact asset was the one explicitly refreshed by `socialize-debt-asset`. The refresh only covers the debt asset that was socialized in that specific position's `fresh-debt-list`; it does not refresh caches for the zToken *collateral* vault ids of other positions in the batch that are priced using the same underlying vault's index/lindex, since zToken collateral pricing for other assets is only refreshed by the accrual explicitly performed at the top of each `liquidate` call for the mask being processed for that call, which is itself served from cache if a hit already exists. If a prior position in the batch caused a write-down (bad debt socialization) of a vault whose zToken is used as *collateral* by a later position in the batch, and the accrual for that vault-id in the later `liquidate` call is a cache HIT (because it was accrued once already earlier in the same block, before it decreased) rather than being refreshed at all (refresh only fires for the debt asset socialized, not for other assets’ derived zToken collateral valuations relying on the same vault id), the later liquidation's collateral valuation and liquidation math can be computed against the pre-write-down `lindex`, i.e. a higher (stale) price than the vault currently holds.

### Impact Explanation
This lands in the Critical category: temporary/permanent mis-valuation of collateral during liquidation can cause a liquidator to seize collateral valued at a stale (higher) price than reality, or a borrower position to be evaluated as healthy/unhealthy incorrectly, causing incorrect debt repayment amounts and collateral seizure amounts recorded on-chain — a direct accounting distortion of user funds analogous to the original bug's "ends with correct underlying balance but under/over-reported total shares distorting share price and subsequent accounting." Because `market-vault` debt/collateral records and vault `assets`/`principal-scaled` are permanently written based on this math, the error becomes part of permanent on-chain state, not just a transient read, potentially leading to insolvency-style distortions across the affected vault.

### Likelihood Explanation
`liquidate-multi` is a permissionless, un-permissioned public entry point designed to batch up to 64 positions specifically to "prevent front-running attacks that prevent bad debt socialization" [6](#0-5) , so its explicit purpose is to combine multiple liquidations — including ones that trigger bad-debt socialization — in a single transaction. Any liquidator can construct the ordering of `positions` themselves, making it straightforward to arrange for an earlier position that triggers a write-down of a shared vault's `lindex`, followed by a later position whose collateral or debt pricing for the same `aid` is not covered by the targeted refresh in `socialize-debt-asset`. The precise conditions (shared `aid` between the socialized debt asset and another position's zToken collateral asset that maps to the same vault, and an accrual ordering that produces a stale cache hit rather than a fresh compute) require analysis, and I was not able to fully trace whether every zToken-collateral pricing path re-triggers accrual freshly enough to avoid the stale hit in all cases — this is noted as an area of uncertainty.

### Recommendation
Invalidate or refresh all relevant `index-cache` entries for any vault whose `lindex`/index is written down mid-batch (not just the specific debt `aid` being socialized), or scope the cache key to include a per-call/per-position identifier so cached indexes cannot leak stale values across separate liquidations processed in the same `map` in `liquidate-multi`. Alternatively, force a fresh `vault-accrue` call (bypassing the cache) for every asset referenced by a position immediately before that position's valuation is computed within `liquidate-multi`.

### Proof of Concept
Not able to construct a concrete calldata-level PoC within the scope of this review; the mechanism is described above based on static code tracing of `accrue-and-cache`, `socialize-debt-asset`, and `liquidate-multi` in `mainnet/contracts/market/v0-4-market.clar`. Confirming exploitability would require constructing two positions sharing an underlying vault (one whose debt triggers `no-collateral-left` bad-debt socialization for asset X, and another using a zToken collateral asset mapping to vault X) and tracing whether the second position's collateral valuation in the same `liquidate-multi` transaction is served a cache hit reflecting the pre-write-down `lindex`.
