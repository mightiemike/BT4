### Title
`ExchangeWithdrawActuator` lacks a minimum-received (slippage) guard, letting a swap or basket-skewing transaction ordered before a withdraw silently drain the withdrawer's expected proceeds - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
The Reserve report describes a victim submitting a redemption expecting a certain amount back, while an attacker reorders/injects a state-changing transaction (basket refresh + minimal collateral injection) immediately before it, so the victim's redemption executes against a drastically different, attacker-controlled ratio and returns almost nothing. The structural root cause is: an output amount computed from a pool/basket ratio at execution time, with no user-supplied floor on the acceptable output.

### Finding Description
`ExchangeWithdrawContract` (the LP-style pool "redeem" analog to RToken redemption) has only `owner_address`, `exchange_id`, `token_id`, `quant` — no `expected`/minimum-output field, unlike `ExchangeTransactionContract`, which explicitly carries `expected` and enforces it: [1](#0-0) 

In `ExchangeWithdrawActuator.doValidate()`, `anotherTokenQuant` (the amount the withdrawer will receive of the other token) is derived purely from the exchange pool's *current* `firstTokenBalance`/`secondTokenBalance` ratio at validation/execution time, with only a "not precise enough" rounding check — no floor value supplied or enforced by the caller: [2](#0-1) 

Execution recomputes the same ratio-derived amount and pays it out unconditionally: [3](#0-2) 

Because Tron transactions can be freely reordered within a block by block producers (and mempool ordering can be influenced), an attacker can, in the same block and before the victim's `ExchangeWithdrawContract` lands, execute an `ExchangeTransactionContract` swap that sharply moves `firstTokenBalance`/`secondTokenBalance` in the pool the victim is withdrawing from. Since `ExchangeWithdrawActuator` has no attacker-independent floor (`expected`) the victim's `quant` of `tokenID` is silently redeemed at whatever skewed ratio exists at execution time, mirroring the "no issuance, just transfer" redemption-drain pattern in the Reserve report exactly: the withdrawer submits expecting one ratio, an intervening transaction changes the pool state, and the withdrawer's redemption executes against the new, unfavorable state without any check.

By contrast, `ExchangeTransactionActuator` (a simple swap) *does* carry and enforce this floor: [4](#0-3) 

This shows the protocol authors were aware of this exact class of MEV/ordering risk and mitigated it for swaps, but the LP-withdraw path (the closer structural analog to RToken redemption from a shared pool of backing assets) was left unprotected.

### Impact Explanation
An LP/exchange participant calling `ExchangeWithdrawContract` to redeem their share of an `Exchange` pool can receive a value far below what they intended if a large swap (`ExchangeTransactionContract`) against the same pool is included immediately before their withdrawal in the same block. This is a direct value-extraction/accounting-integrity issue: the withdrawer's proceeds are determined by transaction-ordering rather than by their intent, and there is no on-chain mechanism (unlike the sibling actuator) to reject an unfavorable execution. This matches the "concrete accounting/settlement impact" bar — real funds are misallocated between a legitimate user and an attacker purely by ordering a cheap follow-on/front-run transaction.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an existing `Exchange` pool with meaningful liquidity that a target withdrawer is redeeming from, and (b) the ability to place a transaction ahead of the victim's in the same block, which any account can attempt by paying bandwidth/energy and relying on mempool/packing order — the same assumption the original Reserve report itself relies on ("requires ordering transactions, or just getting very unlucky"). No privileged role is needed; both the swap and the withdraw are ordinary user-callable actuators.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()`, rejecting the withdrawal if the computed `anotherTokenQuant` (and/or `tokenQuant` returned) falls below the caller-specified minimum. This closes the same reordering/state-change window that the report exploits against Reserve's redemption path.

### Proof of Concept
1. Attacker/creator sets up `Exchange` pool with `firstToken` (e.g. TRX) and `secondToken` A, with balances such that ratio ≈ 1:1, using `ExchangeCreateActuator`.
2. Victim broadcasts `ExchangeWithdrawContract` intending to redeem `quant` of `firstToken` for a proportional amount of `secondToken`, expecting roughly 1:1 return, per the ratio check logic: [5](#0-4) 
3. Before the victim's transaction is packed, attacker submits `ExchangeTransactionContract` performing a large swap of `secondToken` into the pool, drastically shrinking `secondTokenBalance` relative to `firstTokenBalance` (attacker's swap is protected because it supplies its own `expected` floor, per `ExchangeTransactionActuator` validate at lines 217–221 above).
4. Attacker's transaction is ordered first in the block (or lands first in mempool relay); victim's `ExchangeWithdrawContract` executes next, against the now-skewed pool ratio, computing a far smaller `anotherTokenQuant` than the victim anticipated, per `ExchangeWithdrawActuator.execute()` (lines 77–89 above) — with no minimum-output check to abort the transaction.
5. Victim's withdrawal succeeds ("SUCESS") but the victim receives far less `secondToken` than expected, and the attacker can subsequently reverse their swap (or the pool naturally rebalances) to recapture most of the extracted value.
