Based on my investigation, I found the analogous bug class: an uncaught panic when parsing untrusted external input reaches `L1HandlerTransaction::calc_msg_hash`, in the same "malformed-container-crashes-on-parse" family as the zip4j report.

### Title
Uncaught panic in `l1_handler_message_hash` on empty calldata — (`File: crates/starknet_api/src/hash.rs`)

### Summary
`l1_handler_message_hash` (called via `L1HandlerTransaction::calc_msg_hash`) unwraps `calldata.0.split_first()` with `.expect(...)`, assuming the calldata always contains at least one element (the `from_address`). `Calldata` and `L1HandlerTransaction` derive `Deserialize` with no non-empty invariant, so a value with empty calldata is constructible without validation before this call, as already documented and defended against in the sibling function `payload_size()`.

### Finding Description
`crates/starknet_api/src/hash.rs:167-174`: [1](#0-0) 
uses `.expect("Invalid calldata, expected at least from_address")` where `calldata` originates from an `L1HandlerTransaction`, which is deserializable and has no enforced non-empty-calldata invariant, as explicitly called out in the neighboring, already-hardened function: [2](#0-1) [3](#0-2) 
The `payload_size()` sibling method was hardened with `saturating_sub` specifically because "`Calldata` has no non-empty invariant" and `L1HandlerTransaction derives Deserialize`, but `calc_msg_hash`/`l1_handler_message_hash` was not given the same treatment and still panics via `.expect()` on the same class of malformed/empty-calldata input.

`calc_msg_hash` is exposed and reachable through RPC-facing code paths (`apollo_rpc/src/v0_8/api/api_impl.rs`) that compute the L1-to-L2 message hash for querying/serving transaction data, and it operates on `L1HandlerTransaction` values that can be deserialized (e.g., via JSON APIs or internal message plumbing) without calldata non-emptiness being checked beforehand. Because `L1HandlerTransaction`/`Calldata` derive `Deserialize` uniformly across the JSON-RPC transaction types, an externally-supplied or malformed L1-handler transaction object with empty `calldata` reaching this hashing routine (e.g., through the RPC layer or any consensus/OS re-derivation path that recomputes the message hash from transaction data) triggers an uncaught panic rather than a graceful error, consistent with the zip4j-class "uncaught exception on malformed input causes crash" bug pattern.

### Impact Explanation
A panic in a widely-reachable message-hash computation routine, triggered by a value that can be constructed purely via `Deserialize` with no upstream invariant check, crashes the calling component/process. If this is reachable in a sequencer/RPC node component processing untrusted data (e.g., serving `starknet_getMessagesStatus`-style queries, or any consensus code recomputing L1↔L2 message hashes from possibly node-local/replayed data), this results in denial of service for that component — the node becomes unable to process transactions or answer requests until restarted, matching a Medium-severity "network unable to confirm/serve" pattern.

### Likelihood Explanation
Likelihood depends on whether an external, unprivileged actor can supply an `L1HandlerTransaction`/`Calldata` value with empty calldata into a live code path that calls `calc_msg_hash`/`l1_handler_message_hash` before any calldata-non-emptiness validation occurs. I confirmed the panic-guard is missing here and that the exact same class of defect was already found and fixed in the sibling `payload_size()` function (with an explicit regression test), which strongly suggests this specific call site was simply missed during that hardening pass. However, I was **not able to fully confirm** an end-to-end reachable path where the JSON-RPC/message layer accepts and forwards an attacker-supplied, unvalidated empty-calldata `L1HandlerTransaction` all the way to `calc_msg_hash` without an intervening validation step (e.g., L1 events scraper always prepends `from_address`, so it is not naturally empty; the risk is specifically in RPC/query-serving code paths in `apollo_rpc/src/v0_8/api/api_impl.rs` that may recompute this hash from stored/replayed transaction data). This uncertainty should be verified with a deeper trace of `apollo_rpc/src/v0_8/api/api_impl.rs`'s calls to `calc_msg_hash`.

### Recommendation
Replace the `.expect(...)` panic in `l1_handler_message_hash` with a proper `Result`-returning check (mirroring the `saturating_sub` guard already applied in `L1HandlerTransaction::payload_size`), returning a typed error for empty calldata instead of panicking, and audit all callers of `calc_msg_hash` to confirm none can be reached with attacker-supplied or malformed L1-handler transaction data prior to validation.

### Proof of Concept
Construct an `L1HandlerTransaction` (either the `executable_transaction::L1HandlerTransaction` or `transaction::L1HandlerTransaction`) with `calldata: Calldata(Arc::new(vec![]))` (valid per the type's `Deserialize` impl, as demonstrated by the existing test `l1_handler_payload_size_empty_calldata_does_not_underflow`), then call `.calc_msg_hash()` on it: [4](#0-3) 
This invokes `l1_handler_message_hash`, which panics at the `.expect("Invalid calldata, expected at least from_address")` on `calldata.0.split_first()` since an empty slice returns `None`.
