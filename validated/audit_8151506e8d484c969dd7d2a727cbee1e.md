### Title
Unbounded `listExchanges`/`listProposals` RPC handlers return the full exchange/proposal registry, enabling gas/DoS on node RPC as registries grow - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getExchangeList()` and `Wallet.getProposalList()` call `ExchangeStore.getAllExchanges()` / `ProposalStore.getAllProposals()`, which iterate the *entire* underlying store and materialize every entry into a response message with no size cap. These are exposed as anonymous, unauthenticated RPC/HTTP endpoints (`listExchanges`, `listProposals`). This is the same bug class as the GovNFTFactory/GovNFTTimelockFactory `govNFTs()` finding: an ever-growing, permissionlessly-populated registry is returned via a single unbounded getter, which will eventually fail/degrade as the registry grows, and there is no way for callers to iterate partially through the unbounded RPC path.

### Finding Description
`ExchangeStore.getAllExchanges()` streams the full store iterator, sorts it, and collects it into a `List<ExchangeCapsule>` with no limit: [1](#0-0) 

`ProposalStore.getAllProposals()` does the same for proposals: [2](#0-1) 

These are surfaced without any pagination in `Wallet.getExchangeList()` and `Wallet.getProposalList()`, which build a full `ExchangeList`/`ProposalList` protobuf message from the entire result set: [3](#0-2) [4](#0-3) 

`listProposals` is wired directly into the gRPC service as an anonymous, unauthenticated call: [5](#0-4) 

`listExchanges` is likewise exposed via the RPC/HTTP surfaces (`RpcApiService`, `FullNodeHttpApiService`, and the solidity/PBFT variants), calling the same unbounded `getExchangeList()`.

Exchange pairs are created via a permissionless `ExchangeCreateContract` actuator (any account can create a trading pair by paying `EXCHANGE_CREATE_FEE`), so the exchange registry, like the GovNFT registry in the analog, is expected to grow unboundedly over time from ordinary user activity, not just privileged operations.

Note that partially mitigating, paginated variants already exist — `Wallet.getPaginatedProposalList(offset, limit)` and `Wallet.getPaginatedExchangeList(offset, limit)`, bounded by `PROPOSAL_COUNT_LIMIT_MAX`/`EXCHANGE_COUNT_LIMIT_MAX` — exposed via `GetPaginatedProposalListServlet` and an analogous exchange servlet: [6](#0-5) [7](#0-6) 

However, the original unbounded `listProposals`/`listExchanges` endpoints remain live alongside the paginated ones and are not deprecated or capped, so the vulnerable, unbounded code path is still reachable by any anonymous RPC/HTTP caller.

### Impact Explanation
As the number of proposals or exchange pairs grows large (analogous to the 100-200+ threshold in the GovNFT report), calls to `listExchanges`/`listProposals` will consume increasing memory/CPU on the node to build the full response, and eventually will produce very large gRPC/HTTP payloads or fail/timeout, denying legitimate access to this data through the intended unbounded API and increasing load on full nodes that must serve these calls repeatedly. This is a node-level availability/DoS-class issue reachable via anonymous RPC, not an accounting or consensus corruption.

### Likelihood Explanation
Likelihood is moderate: exchange creation is fee-gated but fully permissionless, so the registry size is attacker-influenceable given enough time/funds; proposal creation is gated by witness/committee status, so that registry grows more slowly. The exchange path is the more realistic growth vector over time given java-tron's long operational history and permissionless `ExchangeCreateContract`.

### Recommendation
- Deprecate or hard-cap the unbounded `listExchanges`/`listProposals` handlers (and their HTTP equivalents) in `Wallet.java`/`RpcApiService.java`, directing integrators to the existing paginated `getPaginatedProposalList`/`getPaginatedExchangeList` methods.
- Alternatively, apply the same fix pattern as the referenced Velodrome fix: enforce a bound (e.g., default/max page size) directly inside `getExchangeList()`/`getProposalList()` rather than relying on callers to know about the separate paginated methods.

### Proof of Concept
1. Node accumulates a large number of exchange pairs over time via repeated `ExchangeCreateContract` broadcasts (permissionless, fee-gated).
2. An anonymous client calls the `listExchanges` gRPC/HTTP endpoint (or `listProposals`), which invokes `Wallet.getExchangeList()` → `ExchangeStore.getAllExchanges()`.
3. The store iterator is fully materialized and sorted in memory, then serialized into a single `ExchangeList` protobuf response with no size limit, degrading or failing the RPC response as the exchange count grows, while the safer bounded alternative (`getPaginatedExchangeList`) is not enforced as the mandatory path.

  public ProposalList getPaginatedProposalList(long offset, long limit) {

    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestProposalNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestProposalNum();
    if (latestProposalNum <= offset) {
      return null;
    }
    limit =
        limit > PROPOSAL_COUNT_LIMIT_MAX ? PROPOSAL_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestProposalNum ? latestProposalNum : end;
    ProposalList.Builder builder = ProposalList.newBuilder();

    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ProposalCapsule::calculateDbKey).map(key -> {
      try {
        return chainBaseManager.getProposalStore().get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(proposalCapsule -> builder
            .addProposals(proposalCapsule.getInstance()));
    return builder.build();
  }

  protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    try {
      String input = request.getReader().lines()
          .collect(Collectors.joining(System.lineSeparator()));
      Util.checkBodySize(input);
      boolean visible = Util.getVisiblePost(input);
      PaginatedMessage.Builder build = PaginatedMessage.newBuilder();
      JsonFormat.merge(input, build, visible);
      fillResponse(build.getOffset(), build.getLimit(), visible, response);
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  private void fillResponse(long offset, long limit, boolean visible, HttpServletResponse response)
      throws IOException {
    ProposalList reply = wallet.getPaginatedProposalList(offset, limit);
    if (reply != null) {
      response.getWriter().println(JsonFormat.printToString(reply, visible));

      response.getWriter().println("{}");

  }
