### Title
Unsigned invoke transactions can be smuggled into the mempool by exploiting the deploy_account "skip validate" grace window - ([File: crates/apollo_gateway/src/stateful_transaction_validator.rs])

### Summary
The gateway's `skip_stateful_validations` UX feature bypasses `__validate__` execution (signature/account-existence checks) for an invoke transaction at nonce `1` whenever *any* transaction for the same sender address is already present in the mempool or a recent block. Because this check only tests presence of *a* transaction for the address — not that it is specifically the corresponding `deploy_account` tx submitted by the legitimate account owner — any third party who observes a pending `deploy_account` transaction for a not-yet-deployed account can immediately submit a forged, unsigned invoke transaction at `nonce = 1` for that same sender address. That transaction skips `__validate__` and is admitted into the mempool, occupying the `(address, nonce=1)` slot. This blocks the legitimate account's own subsequent nonce-1 transaction the same way the Sherlock `checkOrder` bug blocks `depositAuction`/`withdrawAuction` by squatting on a nonce value.

### Finding Description
`skip_stateful_validations` decides whether `__validate__` should be skipped for an invoke transaction: [1](#0-0) 

The only guard is `tx.nonce() == 1 && account_nonce == 0` plus `mempool_client.account_tx_in_pool_or_recent_block(tx.sender_address())`, which merely checks that *some* transaction from that address exists: [2](#0-1) 

This flag flows into `run_validate_entry_point`, which sets `execution_flags.validate = !skip_validate` and therefore never runs `__validate__` (the entry point that performs signature verification) for the smuggled invoke: [3](#0-2) [4](#0-3) 

Once `__validate__` is skipped, the *only* remaining stateful checks are nonce-range/`InvalidTransactionNonce` checks and mempool nonce bookkeeping — no signature or ownership proof is required. An attacker who front-runs a legitimate `deploy_account` transaction (visible once it is accepted into the mempool/gateway, e.g. via public RPC feeds, P2P propagation, or simple polling of the account state) can:
1. Observe the victim's `deploy_account` tx for address `A` enter the mempool (`account_tx_in_pool_or_recent_block(A) == true`, `account_nonce == 0`).
2. Immediately submit a garbage/unsigned invoke transaction for sender `A` with `nonce = 1` and arbitrary calldata/signature.
3. This transaction bypasses `__validate__` and is accepted by the mempool as the tx occupying `(A, nonce=1)`.
4. When the legitimate owner submits their real invoke at nonce 1, the mempool rejects it via `MempoolError::DuplicateNonce`/`NonceTooOld` unless fee escalation is configured and the attacker's tx can be replaced, exactly mirroring the front-run/nonce-squat mechanism described in the reported `CrabNetting.checkOrder` bug: [5](#0-4) [6](#0-5) 

The forged transaction later fails execution in the batcher/blockifier (the account contract doesn't exist yet from the forged tx's perspective, or its `__validate__` would have failed had it run), but by then it has already consumed the mempool slot for `nonce=1`, delaying or permanently displacing the legitimate transaction until it is dropped/expired and the user must resubmit — precisely the "stuck system" pattern from the report, without the attacker ever needing the victim's private key.

### Impact Explanation
This allows any unprivileged network participant to grief a specific victim account during its first post-deployment interaction, causing denial-of-service against that account's transaction inclusion (temporary freezing of the account's ability to transact until the forged tx expires/is evicted, and re-submission with a bumped nonce or fee is required). Because `__validate__` is entirely skipped for this class of transaction, no signature is needed to occupy the slot — a strictly weaker bar than the original Sherlock finding, which at least required a valid off-chain signature. This is a targeted, repeatable DoS against onboarding accounts (impacts transaction confirmation for that account), qualifying as at least a Medium/High severity issue depending on fee-escalation configuration and TTL.

### Likelihood Explanation
Likelihood is high: the attack requires only observing a pending `deploy_account` transaction (public mempool state) and submitting one crafted invoke transaction with `nonce=1` and the victim's sender address — no special privileges, keys, or race-condition timing beyond ordinary front-running are required. The `nonce == 1 && account_nonce == 0` and `account_tx_in_pool_or_recent_block` checks are the sole gate, and both are satisfiable by an outside observer.

### Recommendation
Do not gate the validation-skip decision solely on "any tx for this address exists." Instead, tie the skip specifically to the deploy_account transaction hash/id that the invoke transaction references (as is partially done via the `deploy_account_tx_hash` parameter pattern seen in `PyValidator::should_run_stateful_validations`), or require that the transaction whose validation is skipped be bundled/tied atomically to the deploy_account transaction rather than merely coexisting in the mempool for the same address. Alternatively, still perform a lightweight signature/consistency check (e.g., verify the transaction hash matches a hash pre-declared alongside the deploy_account) before admitting the nonce-1 invoke without a full `__validate__` run.

### Proof of Concept
1. Victim submits `deploy_account_tx` for undeployed account `A` (nonce implicitly 0). It is accepted into the mempool.
2. Attacker observes `A`'s pending `deploy_account_tx` (e.g., via public feeder-gateway/mempool visibility) and immediately submits `invoke_tx_forged` with `sender_address = A`, `nonce = 1`, arbitrary/garbage signature and calldata.
3. Gateway's `extract_state_nonce_and_run_validations` → `run_pre_validation_checks` → `skip_stateful_validations` returns `true` because `tx.nonce()==1`, `account_nonce==0`, and `account_tx_in_pool_or_recent_block(A) == true` (satisfied by the victim's own pending deploy_account tx).
4. `run_validate_entry_point` sets `execution_flags.validate = false`, so `__validate__` is never invoked; `invoke_tx_forged` is admitted to the mempool at `(A, nonce=1)`.
5. Victim's legitimate `invoke_tx_real` at `(A, nonce=1)` is now rejected by the mempool as `DuplicateNonce`/insufficient fee escalation (`validate_fee_escalation` in `crates/apollo_mempool/src/mempool.rs:760-792`), blocking the account's intended transaction until the forged tx is evicted/expires or is out-bid by fee escalation.

async fn skip_stateful_validations(
    tx: &ExecutableTransaction,
    account_nonce: Nonce,
    mempool_client: SharedMempoolClient,
) -> StatefulTransactionValidatorResult<bool> {
    if let ExecutableTransaction::Invoke(ExecutableInvokeTransaction { tx, .. }) = tx {
        // check if the transaction nonce is 1, meaning it is post deploy_account, and the
        // account nonce is zero, meaning the account was not deployed yet.
        if tx.nonce() == Nonce(Felt::ONE) && account_nonce == Nonce(Felt::ZERO) {
            let account_address = tx.sender_address();
            debug!("Checking if deploy_account transaction exists for account {account_address}.");
            // We verify that a deploy_account transaction exists for this account. It is sufficient
            // to check if the account exists in the mempool since it means that either it has a
            // deploy_account transaction or transactions with future nonces that passed
            // validations.
            return mempool_client
                .account_tx_in_pool_or_recent_block(tx.sender_address())
                .await
                .map_err(|err| mempool_client_err_to_deprecated_gw_err(&tx.signature(), err))
                .inspect(|exists| {
                    if *exists {
                        debug!("Found deploy_account transaction for account {account_address}.");
                    } else {
                        debug!(
                            "No deploy_account transaction found for account {account_address}."
                        );
                    }
                });
        }

    /// `(address, nonce)` via fee escalation, without mutating any state. Returns the existing
    /// transaction to be replaced when a valid replacement exists, `None` when there is nothing to
    /// replace, or an error when a replacement is present but not permitted.
    fn validate_fee_escalation(
        &self,
        incoming_tx_reference: TransactionReference,
    ) -> MempoolResult<Option<TransactionReference>> {
        let TransactionReference { address, nonce, .. } = incoming_tx_reference;

        self.validate_no_delayed_declare_front_run(incoming_tx_reference)?;

        if !self.config.static_config.enable_fee_escalation {
            if self.tx_pool.get_by_address_and_nonce(address, nonce).is_some() {
                return Err(MempoolError::DuplicateNonce { address, nonce });
            };

            return Ok(None);
        }

        let Some(existing_tx_reference) = self.tx_pool.get_by_address_and_nonce(address, nonce)
        else {
            // Replacement irrelevant: no existing transaction with the same nonce for address.
            return Ok(None);
        };

        if !self.should_replace_tx(&existing_tx_reference, &incoming_tx_reference) {
            info!(
                "{existing_tx_reference} was not replaced by {incoming_tx_reference} due to \
                 insufficient fee escalation."
            );
            // TODO(Elin): consider adding a more specific error type / message.
            return Err(MempoolError::DuplicateNonce { address, nonce });
        }

        Ok(Some(existing_tx_reference))
    }

    pub fn perform_validations(&mut self, tx: AccountTransaction) -> StatefulValidatorResult<()> {
        // Deploy account transaction should be fully executed, since the constructor must run
        // before `__validate_deploy__`. The execution already includes all necessary validations,
        // so they are skipped here.
        // Declare transaction should also be fully executed - otherwise, if we only go through
        // the validate phase, we would miss the check that the class was not declared before.
        match tx.tx {
            ApiTransaction::DeployAccount(_) | ApiTransaction::Declare(_) => self.execute(tx),
            ApiTransaction::Invoke(_) => {
                let tx_context = Arc::new(self.tx_executor.block_context.to_tx_context(&tx));
                tx.perform_pre_validation_stage(self.state(), &tx_context)?;
                if !tx.execution_flags.validate {
                    return Ok(());
                }

                // `__validate__` call.
                let (_optional_call_info, actual_cost) = self.validate(&tx, tx_context.clone())?;

                // Post validations.
                PostValidationReport::verify(
                    &tx_context,
                    &actual_cost,
                    tx.execution_flags.charge_fee,
                )?;

                Ok(())
            }
        }
    }
