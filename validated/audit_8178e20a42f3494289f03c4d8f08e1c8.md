### Title
Unconditional `.unwrap()` on `receiver_shard_id()` in delayed-receipt filtering can panic and halt chunk application - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally unwraps the `Result` returned by `Receipt::receiver_shard_id`, which can legitimately return an `Err` for `GlobalContractDistribution` receipts whose `target_shard` cannot be resolved to any shard in the current layout's split history. This mirrors the GVE XDP bug class: an internal codepath assumes a piece of state ("this receipt always maps to a known shard") always exists, and panics instead of gracefully erroring when that assumption is violated after state transitions (here, resharding) that a normal user's transaction (a global contract deploy) can trigger and put on the delayed-receipt path.

### Finding Description
`receiver_shard_id` (`core/primitives/src/receipt.rs:437-465`) explicitly documents and implements a fallible path for `GlobalContractDistribution` receipts: if the receipt's `target_shard` is not in the current `shard_layout` and `resolve_to_current_shard` fails to find a descendant shard, it returns `Err(EpochError::ShardingError(...))` rather than a `ShardId`.

`receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:874-878` calls this function and immediately `.unwrap()`s the result:
```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```
This is called from `DelayedReceiptQueueWrapper::pop` (`:905`) — invoked on every delayed receipt during normal chunk apply (`Runtime::process_delayed_receipts`) — and from `peek_iter` (`:919`). Any delayed `GlobalContractDistribution` receipt whose `target_shard` cannot be remapped after resharding (e.g. across two or more resharding generations, or if `resolve_to_current_shard`'s split-history bookkeeping is incomplete for some edge case) causes a hard `panic!` inside chunk application, which — because it is entirely deterministic given the receipt and shard layout — is a transaction/deploy-triggered halt reproducible on every honest validator processing that chunk.

### Impact Explanation
A panic inside `process_delayed_receipts`/chunk apply crashes the validator/RPC process applying that chunk. Because the condition is deterministic (same receipt, same shard layout, same code on every node), all honest nodes that apply the chunk crash identically, producing a chain-wide halt triggered entirely by a user's `DeployGlobalContractAction` transaction combined with resharding timing — no privileged access, malicious validator, or network-layer manipulation required. This matches the "transaction-triggered halt" impact category.

### Likelihood Explanation
Reaching this bug requires: (1) submitting a `DeployGlobalContractAction` transaction as any account, and (2) the resulting `GlobalContractDistribution` receipt remaining in a shard's delayed-receipt queue while the shard undergoes resharding across generations such that `resolve_to_current_shard` cannot map the stale `target_shard`. The project's own regression test (`test_stale_global_contract_distribution_after_double_resharding`) demonstrates this exact scenario is constructible with ordinary dynamic-resharding configuration and congestion-induced delay, and explicitly exists because this was previously a real, reachable panic. Confidence that the current `resolve_to_current_shard` implementation covers *all* multi-generation staleness cases (vs. only the specific two-split scenario tested) could not be fully verified from the available index.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (`Result<bool, RuntimeError>` or similar), converting an unresolvable `target_shard` into a `StorageError::StorageInconsistentState`-style recoverable error (consistent with how other queue-consistency violations are handled elsewhere in this file, e.g. `TrieQueue::pop_front`/`pop_back`), or explicitly handle the "shard no longer exists and cannot be resolved" case by treating the receipt as belonging to no current shard and safely dropping/redirecting it, rather than allowing an uncaught panic in the middle of the delayed-receipt pop loop. Add regression coverage for resharding depths beyond what `test_stale_global_contract_distribution_after_double_resharding` currently exercises.

### Proof of Concept
1. Deploy a genesis/epoch config with `DynamicReshardingConfig` enabling force-splits of the target shard across at least two resharding generations (as in `test-loop-tests/src/tests/global_contracts_distribution.rs:32-186`).
2. From an account on the shard scheduled to split, submit a `DeployGlobalContractAction` transaction, producing a `GlobalContractDistribution` receipt targeting that shard.
3. Saturate the shard's compute budget every block (e.g. repeated `burn_gas_raw` calls) so the distribution receipt is pushed into the delayed-receipt queue instead of executing immediately.
4. Allow two resharding events to occur while the receipt remains delayed.
5. Stop saturating and let the delayed queue drain; if `resolve_to_current_shard` cannot map the receipt's stale `target_shard` for the given split-history depth, `receipt_filter_fn`'s `.unwrap()` panics during `DelayedReceiptQueueWrapper::pop`, halting chunk application on every node.     pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard

                            "Shard {target_shard} does not exist in the shard layout or its split history",

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;

    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");

    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {

        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();

    ]));

        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
