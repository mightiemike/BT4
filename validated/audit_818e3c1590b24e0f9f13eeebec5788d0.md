## Analysis

The external report's core invariant is: **signed/attested state must be validated against something that cannot be silently bypassed** (missing expiry/binding checks let stale attestations be reused). Mapping this to Aptos-native proof/commit integrity, I looked at the checkpoint-hash comparison path used by replay-verification tooling.

### Title
Replay-verification comparator silently skips state/hot-state/position checkpoint root validation - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, used by `db-tool replay-on-archive`, `aptos-debugger`, and the CLI to independently re-verify historical execution against archived `TransactionInfo`s, checks status, gas, write-set hash, and event-root hash, but **does not compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`** against recomputed values.

### Finding Description [1](#0-0) 

The function validates `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash — but ends with an explicit TODO acknowledging that the state-checkpoint-related root hashes carried in `TransactionInfoV1` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are never checked: [2](#0-1) 

This comparator is the sole correctness check performed by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` to decide pass/fail: [3](#0-2) 

Since none of the checkpoint hashes are part of the comparison, a divergence between locally-recomputed state roots (main state Merkle root, hot-state root, or the newer native-position Merkle root) and the authenticated `TransactionInfo` on the archived ledger would go completely undetected by this tool.

By contrast, the actual commit-time path (`execution/executor/src/workflow/do_state_checkpoint.rs::get_state_checkpoint_hashes`) does assert computed checkpoint hashes against `known_state_checkpoints`/`known_position_state_checkpoints` pulled from the committed `TransactionInfo`s: [4](#0-3) [5](#0-4) 

So consensus/state-sync commit and chunk-replay (the `ChunkExecutor` path) already enforce this. The gap is isolated to the diagnostic/audit tool `ensure_match_transaction_info`, which is a distinct, weaker verification routine.

### Impact Explanation
The `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flags exist to make these state roots consensus-verified and auditable (per the framework feature comments): [6](#0-5) 

If any of these features are enabled and a bug causes the recomputed state/hot-state/position root to diverge from the archived, authenticated value at some historical version, `db-tool replay-on-archive` (and `aptos-debugger`, `aptos cli` uses of the same function) would report a clean pass despite an actual state-commitment divergence — defeating the purpose of the audit tool as an independent integrity check on archived/backed-up ledger data. This does not itself corrupt committed state (the primary commit path enforces the checks), so the impact is confined to false assurance from the audit/replay-verification tooling rather than a live consensus fork.

### Likelihood Explanation
Low-to-moderate. `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a new, not-yet-broadly-enabled feature (explicitly noted as gated and only recently introduced with a TODO in the exact same function acknowledging the gap before enabling it). The bug is real and self-evident in the code (the TODO literally states this), but its practical trigger requires (a) the feature flags being enabled on the target network, and (b) an actual computation bug elsewhere causing a root divergence — this finding only concerns the *detection* of such a divergence via replay-verify tooling, not a new way to corrupt commit-time state.

### Recommendation
Extend `ensure_match_transaction_info` (or add a parallel checkpoint-aware comparator used by `replay_on_archive.rs`, `aptos-debugger`, and CLI) to compare `expected_write_set`'s/recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against `txn_info`'s corresponding fields whenever those checkpoints are present, mirroring the checks already done in `do_state_checkpoint.rs::get_state_checkpoint_hashes`. Do this before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any live network, as the code comment itself recommends.

### Proof of Concept
Not independently exploitable as a live-network state-corruption bug (a PoC would require triggering an actual computation bug in the position/hot-state root elsewhere, which is out of scope here). The proof of the flaw is structural: trace `replay_on_archive.rs:392` → `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) → the checkpoint-hash comparisons are absent (confirmed by the function's own trailing TODO comment) → any silent state/hot-state/position root divergence at a given version is unreported by this replay-verify path, unlike the equivalent checks present in `do_state_checkpoint.rs`.

**Caveat:** I could not fully trace whether `ReplayChunkVerifier`/`StateSyncChunkVerifier` (in `execution/executor/src/chunk_executor/chunk_result_verifier.rs`) independently re-validate these checkpoint hashes during full chunk-based state-sync replay before my tool budget ran out — if they do, the exposure is strictly limited to the standalone `db-tool`/`aptos-debugger`/CLI utilities, further narrowing impact to an auditing/tooling gap rather than any node-level consensus risk.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
