### Title
Attached deposit from a relayer/caller is silently kept by the Wallet Contract on early-error paths, with no refund — Wallet Contract (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract::rlp_execute` entry point is `#[payable]`, meaning any external account can attach a NEAR deposit when calling it to fund the ETH-emulated transaction's value. The contract tracks this contribution as `CallerDeposit` so it can be refunded if the downstream cross-contract call fails. However, several early-return code paths in `rlp_execute`/`inner_rlp_execute` complete synchronously (return `PromiseOrValue::Value`, i.e., no promise is scheduled) *before* any refund promise is created, even though the caller's `attached_deposit` has already been unconditionally credited to the wallet's own account balance (per Near semantics, deposits are credited to the receiver before the method body runs). In these paths, the caller's deposit is permanently absorbed into the wallet owner's balance with no way for the caller to recover it — the same class of bug as ETH becoming inaccessible when sent directly to Compound's Timelock, except here there is no workaround at all.

### Finding Description
`rlp_execute` is annotated `#[payable]` [1](#0-0) , so any external caller (relayer) can attach a NEAR deposit to the call. Once attached, that value is already part of the wallet (current) account's balance before any contract logic executes, matching the documented Economics API semantics [2](#0-1) .

Inside `rlp_execute`, before `inner_rlp_execute` is even invoked, if another transaction is already in flight the function returns synchronously without creating any promise, meaning any attached deposit is neither used nor refunded: [3](#0-2) 

`CallerDeposit::new` is only constructed inside `inner_rlp_execute`, i.e. after the in-flight check has already passed, and it is only referenced by promises that are actually scheduled: [4](#0-3) [5](#0-4) 

Crucially, when `inner_rlp_execute` returns any `Err` variant (e.g. `Error::User`, `Error::AccountId`, `Error::AccountNonceExhausted`, or `Error::Relayer` when the caller is not the wallet's own signer), `rlp_execute` returns `PromiseOrValue::Value(e.into())` directly — no promise, no refund: [6](#0-5) 

The refund logic that *does* exist only fires from `rlp_execute_callback`, which is reached solely via a scheduled promise chain, and only refunds `caller_deposit` when the ultimate downstream promise fails: [7](#0-6) 

Likewise, `address_check_callback`'s relayer-mismatch branch returns a `Value` directly, dropping `caller_deposit` without refund: [8](#0-7) 

Because `Error::Relayer` and `Error::User` conditions (invalid target, invalid nonce, insufficient gas, malformed RLP, excess yoctoNear, etc., see `validate_tx_relayer_data`/`parse_tx_data`) are reachable purely from data supplied in the call and can occur for reasons outside the caller's control (e.g., a benign nonce race between two relayers, or malformed calldata), an external caller who attaches a deposit intending to subsidize the wallet owner's transaction value can lose that deposit outright whenever the very first validation step fails, since none of these paths create a promise back to them.

### Impact Explanation
Funds attached by an external, unprivileged account calling `rlp_execute` on an ETH-implicit account's Wallet Contract can be irrecoverably transferred into that wallet's balance without the wallet owner performing any corresponding action and without the depositor being refunded — a permanent, one-directional, unauthorized value movement triggered purely by a transaction/contract-call from an ordinary caller. This matches "permanently frozen/lost funds" and "unauthorized value movement" in the accepted impact classes.

### Likelihood Explanation
This is trivially triggerable: any account that calls `rlp_execute` on any ETH-implicit account with a non-zero deposit and a transaction that fails first-pass relayer/user validation (e.g., stale nonce due to a concurrent relayer, insufficient gas, or a malformed/borderline transaction) hits the vulnerable path deterministically. No special privileges, validator status, or race with the protocol layer are required — only a standard `FunctionCall` to a deployed contract with a positive deposit.

### Recommendation
Ensure the caller's `attached_deposit` is tracked and refunded (or simply never accepted) whenever `rlp_execute` returns synchronously without scheduling a promise. Concretely:
- Compute `CallerDeposit` in `rlp_execute` itself (using `env::attached_deposit()`/`env::predecessor_account_id()`), before the `has_in_flight_tx` check and before calling `inner_rlp_execute`.
- On every `PromiseOrValue::Value(...)` return path (in-flight guard, all `Err(e)` branches in `rlp_execute`, and the relayer-mismatch branch of `address_check_callback`), issue a transfer promise refunding the tracked deposit to the predecessor before returning the error value, mirroring the logic already present in `rlp_execute_callback`.
- Alternatively, reject the call outright (assert deposit is zero) unless the flow that will actually consume it is guaranteed to be reached, following the OpenZeppelin-style pattern referenced in the source report of only accepting funds that the executing logic can account for.

### Proof of Concept
1. Deploy/observe an ETH-implicit account `0xabc...` with the Wallet Contract, currently mid-execution of a transaction (`has_in_flight_tx == true`), e.g. because a prior `rlp_execute` call is awaiting a cross-contract callback.
2. An external account `attacker.near` (not the wallet owner, no private key over `0xabc...`) calls `rlp_execute` on `0xabc...` attaching, say, 5 NEAR, with any (even garbage) `tx_bytes_b64`.
3. `rlp_execute` observes `self.has_in_flight_tx == true` and returns `PromiseOrValue::Value(ExecuteResponse { success: false, ... })` immediately — see [9](#0-8) .
4. No promise is scheduled, so the 5 NEAR attached by `attacker.near` is never returned; it is now permanently part of `0xabc...`'s account balance, with `attacker.near`'s call reporting failure and no compensating transfer.
5. The same result is reproducible deterministically by instead causing `inner_rlp_execute` to return any `Err` (e.g., submit a transaction with `nonce != expected_nonce`, forcing `Error::Relayer(RelayerError::InvalidNonce)` from `validate_tx_relayer_data`, see [10](#0-9) ) while the transaction is signed by an account other than the wallet itself, hitting the bare `Err(e) => PromiseOrValue::Value(e.into())` branch at [11](#0-10) .
