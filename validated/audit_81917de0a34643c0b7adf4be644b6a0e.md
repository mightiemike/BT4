Fulfillment-service HMAC does not bind to shop domain, allowing cross-tenant session/token disclosure via header spoofing - (File: packages/apps/shopify-app-react-router/src/server/authenticate/fulfillment-service/authenticate.ts)

### Summary
`authenticateFulfillmentServiceFactory` validates the request's HMAC via `api.fulfillmentService.validate`, but that validation only checks `HMAC(apiSecretKey, rawBody)` and never covers the `X-Shopify-Shop-Domain` header. The `shop` used to fetch the offline session is read directly and unverified from that header, so a valid `(rawBody, hmac)` pair obtained from one shop's fulfillment-service callback can be replayed with a forged shop header to load a different shop's offline session/access token.

### Finding Description
In `authenticate.ts` the flow is:
1. `rawBody = await request.text()`.
2. `result = await api.fulfillmentService.validate({rawBody, rawRequest: request})` [1](#0-0) .
3. `validateFactory` delegates straight to `validateHmacFromRequestFactory` with `HmacValidationType.FulfillmentService` [2](#0-1) .
4. `validateHmacFromRequestFactory` computes `validHmac = validateHmacString(config, rawBody, hmac, HashFormat.Base64)`, i.e. it only signs/verifies `rawBody` — it never reads or incorporates `ShopifyHeader.Domain` (or any other header) into the HMAC input [3](#0-2) , and `validateHmacString` only hashes `data` (the raw body) with the app's single global `apiSecretKey` [4](#0-3) .
5. Back in `authenticate.ts`, after `result.valid` is true, `shop` is taken directly from the unverified header: `const shop = request.headers.get(ShopifyHeader.Domain) || '';` [5](#0-4) .
6. That unverified `shop` is passed straight into `ensureValidOfflineSession(params, shop)` to fetch/refresh an offline session, and the resulting session (with its access token) is bound into the returned `admin` client via `adminClientFactory({params, session})` [6](#0-5) .

Since the HMAC is computed with the app's single `apiSecretKey` and only over `rawBody` (no shop/domain binding, no signator-specific salt), a legitimate `(rawBody, hmac)` pair the attacker received for their own store's fulfillment-service registration is cryptographically valid for *any* shop header value — the HMAC check has no way to bind the request to a particular tenant. The `X-Shopify-Shop-Domain` header, which is the only tenant-selection input, is completely outside the signed data. This breaks TENANT_ISOLATION: the shop used for session lookup is not cryptographically bound to the HMAC-verified content.

### Impact Explanation
An attacker who runs a fulfillment service on their own store (a normal, unprivileged merchant capability) can capture one valid `(rawBody, hmac)` request, then replay it against the app's fulfillment endpoint while overriding `X-Shopify-Shop-Domain` to a victim shop that also has the app installed. If the victim has a stored offline session, `ensureValidOfflineSession` returns the victim's session/access token, and the handler builds an authenticated `admin` GraphQL/REST client scoped to the victim shop, handing the attacker cross-tenant access. This matches Shopify's "cross-tenant data/session access via forged request" bounty impact class.

### Likelihood Explanation
Feasible and repeatable: the only precondition is that the attacker registers/operates a fulfillment service on their own store to legitimately receive one Shopify-signed fulfillment-service callback (rawBody+HMAC), which is standard, unprivileged app functionality. The header can then be freely modified in any subsequent replayed POST since it is not part of the signed payload, and this can be repeated for any target shop domain the attacker wants to probe, as long as that shop has a stored offline session for the same app installation.

### Recommendation
Bind the shop identity into the HMAC-verified data path rather than trusting a separate header:
- Either include a shop-specific value in the HMAC computation (impossible to change without breaking Shopify's actual signing scheme), or
- Cross-check that the `shop` extracted from the header matches shop information embedded in the verified payload/rawBody itself (e.g. Shopify's fulfillment order payload typically identifies the shop via an authenticated JWT/session token, not solely a header), or
- At minimum, ensure `ensureValidOfflineSession` fails closed unless the request also carries a session token / other tenant-bound signed credential that ties back to the same shop, instead of relying solely on the unauthenticated `X-Shopify-Shop-Domain` header.

```ts
it('accepts a valid HMAC/body pair with a forged shop-domain header', async () => {
  const sessionStorage = new MemorySessionStorage();
  const shopify = shopifyApp(testConfig({sessionStorage}));

  // Attacker's own valid rawBody + HMAC (obtained from their own registered
  // fulfillment service callback).
  const body = {kind: 'FULFILLMENT_REQUEST'};
  const rawBody = JSON.stringify(body);
  const validHmac = getHmac(rawBody); // HMAC(apiSecretKey, rawBody) — same for all shops

  // Victim shop already has an offline session stored.
  const victimSession = await storeValidSession(sessionStorage, 'victim-shop.myshopify.com');

  const forgedRequest = new Request(FULFILLMENT_URL, {
    method: 'POST',
    body: rawBody,
    headers: {
      'X-Shopify-Hmac-Sha256': validHmac,
      'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // forged, attacker does not own this shop
    },
  });

  const {session, admin} = await shopify.authenticate.fulfillmentService(forgedRequest);

  // THEN: attacker receives victim's offline session/access token bound admin client
  expect(session.shop).toBe('victim-shop.myshopify.com');
  expect(session.accessToken).toBe(victimSession.accessToken);
});
```
