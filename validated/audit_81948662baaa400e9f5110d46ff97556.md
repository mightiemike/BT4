### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay/verification tooling to accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the shared integrity check used by chunk execution/replay verification (`execution/executor/src/chunk_executor/mod.rs`), the CLI (`aptos-move/cli/src/commands.rs`), and the debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated, accumulator-proven `TransactionInfo` for a given version. The function checks status, gas used, write-set hash, and event root hash, but by its own admitted `TODO(trading-native)` comment it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [1](#0-0) .

### Finding Description
`ensure_match_transaction_info` is meant to be the authoritative comparator between a freshly computed `TransactionOutput` and the on-chain, consensus-signed `TransactionInfo` (which is itself accumulator-proven back to a `LedgerInfo`, per `verify_transaction_info` in `types/src/proof/mod.rs`) [2](#0-1) . It verifies:
- transaction status
- gas used
- `write_set` hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

but explicitly skips the state checkpoint hash, hot-state checkpoint hash, and the newly introduced `position_state_checkpoint_hash` (used for the native-position/trading state tree gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), as the code comment states directly:

```rust
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This function is called from `execution/executor/src/chunk_executor/mod.rs` (chunk replay/state-sync verification path) as well as `storage/db-tool/src/replay_on_archive.rs`'s `Verifier` (via the shared replay path used by CLI/debugger tooling — confirmed the symbol is referenced in `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`) [4](#0-3) .

Meanwhile, `do_state_checkpoint.rs`'s `get_state_checkpoint_hashes` *does* validate checkpoint hashes, but only against a `known_state_checkpoints` value that is itself sourced from a `TransactionInfo` that has already been accepted by the checks in `ensure_match_transaction_info`/replay verification — i.e., the state-checkpoint-hash gap in `ensure_match_transaction_info` is the weak link that lets a divergent computed state root be silently accepted as correct in the replay-verification/tooling flow [5](#0-4) .

### Impact Explanation
Under the intended design, `TransactionInfo.state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` are the fields that bind a version's ledger state root into the accumulator and hence into consensus-signed `LedgerInfo`. Any tool (replay-verify CI, `db-tool replay-on-archive`, `aptos-debugger`) that relies on `ensure_match_transaction_info` to detect divergence between locally computed execution results and the authenticated on-chain record will fail to flag a state-root divergence at the checkpoint level. This means:
- A bug in state computation (e.g., in the native-position/trading-native state tree, hot-state tree, or main state tree) that produces the *correct* write-set hash but a *wrong* materialized state root would not be caught by this comparator.
- Replay-verification, which is one of the primary safety nets used to catch state-divergence bugs in Aptos before a hard fork or before trusting archival replay for auditing, would silently report success even though the authenticated state root diverged from local computation.

This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated API or state-view output bound to the wrong version, object, or proof context" categories in the state-integrity gate: it is precisely the kind of tooling-level integrity blind spot that could mask a real consensus-committed state corruption from being detected via replay.

### Likelihood Explanation
This is not directly exploitable by an unprivileged attacker to corrupt mainnet state by itself — it is a gap in a verification tool, not in the execution or commit path itself. Its severity is contingent on: (1) a separate bug existing in trading-native/hot-state root computation, and (2) `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` being enabled. The code's own comment acknowledges this is a known gap that must be fixed "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS," which suggests the feature may not yet be enabled on mainnet, reducing immediate exploitability but leaving latent risk if the feature is turned on before the TODO is addressed.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values (mirroring the checks already done in `do_state_checkpoint.rs::get_state_checkpoint_hashes`), and block/gate enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` until this validation is in place, per the code's own TODO.

### Proof of Concept
Not directly demonstrable as a standalone exploit since this is a verification-tooling gap rather than a state-corrupting bug in the commit path itself. The concrete condition to reproduce the blind spot:
1. Enable `TRANSACTION_INFO_V1`, `HOTNESS_IN_EPILOGUE`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.
2. Introduce (or have) a bug that causes the locally recomputed native-position/hot-state root to diverge from the authenticated `TransactionInfo.position_state_checkpoint_hash`/`hot_state_checkpoint_hash` while leaving `write_set` hash and events unchanged.
3. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) or the debugger/CLI paths that call `ensure_match_transaction_info` — the tool would report success despite the state-root divergence, because only status/gas/write-set-hash/event-root are checked [6](#0-5) .

Note: I was unable to fully trace every call site (`aptos-debugger` and `cli/commands.rs` usages) to confirm the exact downstream consumer behavior beyond the symbol match, due to index/tool-call limits; a full Devin session with file access would be needed to verify those call sites line-by-line and confirm current mainnet feature-flag status for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
