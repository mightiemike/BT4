## Title
`promise_batch_action_add_key_with_function_call` / gas-key variant collapse an explicit zero allowance into `None` ("unlimited"), making it impossible to grant a truly zero-spend FunctionCall access key - (File: `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`)

### Summary
The host functions that let a contract add a `FunctionCall`-permission access key via a promise batch action treat an `allowance` value of `0` as a sentinel meaning "unlimited," instead of the literal, explicit value "zero." This is the same bug class as the referenced Aloe `Borrower.modify` issue: a legitimate, distinct value (here, an explicit zero allowance) is silently coerced into a different, more permissive semantic value ("no cap" instead of "no cap for spending"), because the encoding cannot represent it.

### Finding Description
`promise_batch_action_add_key_with_function_call` decodes the raw `u128` allowance from guest memory and converts it with: [1](#0-0) 

```
let allowance = Balance::from_yoctonear(get_u128(...)?);
let allowance = if allowance > Balance::ZERO { Some(allowance) } else { None };
```

The identical pattern is used for gas keys in `promise_batch_action_add_gas_key_with_function_call`: [2](#0-1) 

This is documented as intended behavior in the Promises API spec: [3](#0-2) 

> "If the `allowance` value (not the pointer) is `0`, the allowance is set to `None` (which means unlimited allowance)."

`FunctionCallPermission.allowance` is `Option<Balance>` specifically so that `None` (unlimited) and `Some(0)` (zero-spend) can both be represented: [4](#0-3) 

and the runtime does distinguish these two states correctly when they originate from a *signed transaction's* `AddKeyAction` (e.g. `verify_nonce`/`check_and_compute_new_allowance` in `verifier.rs` treat `Some(0)` as "no further allowance," causing `NotEnoughAllowance` on the very next spend): [5](#0-4) 

However, when a *contract* constructs the `AddKeyAction` indirectly through the promise-batch host function (rather than a user directly submitting an `AddKeyAction`), there is no way to reach the `Some(0)` state at all: any attempt to pass an explicit `0` allowance is silently rewritten to `None` before it ever reaches `append_action_add_key_with_function_call` / `append_action_add_gas_key_with_function_call`: [6](#0-5) [7](#0-6) 

### Impact Explanation
A contract that programmatically manages access keys on behalf of users (e.g. a wallet/session-key contract, a delegated-authorization contract, or any contract issuing restricted keys as part of its business logic) cannot create a FunctionCall key that is spend-capped at exactly zero. Such a "zero-allowance" key is a legitimate and useful configuration: it is authorized to call the specified method/receiver, but cannot independently pay for gas/fees out of the account balance as a directly-signed transaction (it would only be usable, if at all, as an authorizer inside a meta-transaction where a relayer pays). Because the host function coerces the caller's intended `0` into `None`, the key that gets created instead has **unlimited allowance**, i.e. it can spend the account's entire NEAR balance on gas/fees for any transaction it signs directly. This silently and unexpectedly grants a spending capability the contract's logic explicitly tried to deny, resulting in unauthorized value movement out of the account if that key is later used (or compromised).

### Likelihood Explanation
This is triggered purely by contract logic executed on behalf of any unprivileged caller — any contract can invoke `promise_batch_action_add_key_with_function_call` (or the gas-key variant) with an allowance argument of `0` as part of normal execution; no special privileges are required. The behavior is deterministic and always occurs when `0` is passed, so any contract designed around the (reasonable) assumption that `Option<Balance>` faithfully encodes "explicit zero vs. unlimited" will be affected every time it attempts to issue a zero-allowance key.

### Recommendation
Do not overload `0` as a sentinel for "unlimited" in the host function ABI. Instead, use a dedicated sentinel (e.g. `u128::MAX`, or a separate flag/pointer indicating "no allowance value provided") to signal "unlimited," and treat a literal `0` passed by the caller as `Some(0)`, matching the semantics already supported by `FunctionCallPermission.allowance: Option<Balance>` and already honored correctly on the verifier path for user-submitted `AddKeyAction`s.

### Proof of Concept
1. A contract executes a promise batch action calling `promise_batch_action_add_key_with_function_call(promise_idx, pk_len, pk_ptr, nonce, allowance_ptr, ...)` with the 16 bytes at `allowance_ptr` encoding `0u128`, intending to add a `FunctionCall` key that cannot independently spend any of the account's balance.
2. In `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`, `get_u128` decodes `0`; the line `let allowance = if allowance > Balance::ZERO { Some(allowance) } else { None };` converts this to `None`.
3. `append_action_add_key_with_function_call` (`runtime/runtime/src/receipt_manager.rs:601-631`) builds an `AddKeyAction` with `FunctionCallPermission { allowance: None, .. }`.
4. The resulting on-chain access key has `allowance: None` = unlimited, contrary to the contract's intent, and can be used to sign ordinary transactions that drain the account's NEAR balance to pay for gas/fees — a capability the contract's logic never intended to grant.

```rust
fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
```

```rust
    pub(super) fn append_action_add_gas_key_with_function_call(
        &mut self,
        receipt_index: ReceiptIndex,
        public_key: PublicKey,
        num_nonces: NonceIndex,
        allowance: Option<Balance>,
        receiver_id: AccountId,
        method_names: Vec<Vec<u8>>,
    ) -> Result<(), VMLogicError> {
        self.append_action(
            receipt_index,
            Action::AddKey(Box::new(AddKeyAction {
                public_key,
                access_key: AccessKey::gas_key_function_call(
                    num_nonces,
                    FunctionCallPermission {
                        allowance,
                        receiver_id: receiver_id.into(),
                        method_names: method_names
                            .into_iter()
                            .map(|method_name| {
                                String::from_utf8(method_name)
                                    .map_err(|_| HostError::InvalidMethodName)
                            })
                            .collect::<std::result::Result<Vec<_>, _>>()?,
                    },
                ),
            })),
        );
        Ok(())
    }
```
