### Title
OAuth callback resolves `shop` inconsistently between HMAC/state validation and token-exchange/session creation, enabling parameter-pollution shop confusion - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
`callback()` in `oauth.ts` reads the `shop` query parameter twice using two different semantics: once via `URLSearchParams.get('shop')` (which returns the **first** occurrence of a duplicated key) for the token-exchange URL and session creation, and once via `Object.fromEntries(query.entries())` (which keeps the **last** occurrence) for HMAC and `state` validation. A caller who appends a duplicate `shop` (or `hmac`/`state`/`timestamp`) parameter to the callback URL can make the HMAC-validated value differ from the value the library actually uses to build the access-token request and the resulting `Session`.

### Finding Description
In `callback()`:
- Line 147: `const shop = query.get('shop')!;` — first occurrence, used only for logging.
- Line 178: `const authQuery: AuthQuery = Object.fromEntries(query.entries());` — later duplicate keys overwrite earlier ones, so this collapses to the **last** occurrence.
- Line 179: `validQuery({config, query: authQuery, stateFromCookie})` validates HMAC and `state` against `authQuery` (last-value semantics).
- Line 194: `const cleanShop = sanitizeShop(config)(query.get('shop')!, true)!;` — re-reads `shop` from the raw `URLSearchParams`, i.e. **first**-value semantics, and this `cleanShop` is what is used to build the `/admin/oauth/access_token` POST URL and the `shop` field of the created `Session`. [1](#0-0) [2](#0-1) 

`validateHmac`/`normalizeQuery` in `hmac-validator.ts` only rejects duplicated `hmac`/`shop`/`signature`/`timestamp` keys when `signator === 'appProxy'`: [3](#0-2) 

Since `oauth.ts` calls `validateHmac(config)(query)` with the default `signator: 'admin'`, and additionally pre-collapses the `URLSearchParams` into a plain object before calling it, the app-proxy duplicate-key hardening (`Query parameter "..." must not appear more than once.`) never applies to the OAuth `/auth/callback` path at all — it exists only for the app-proxy code path, exactly as shown by the tests at `hmac-validator.test.ts:227-244`, which explicitly scope this protection to `signator: 'appProxy'`.

An attacker who can produce (or replay) a legitimately Shopify-signed callback for shop `Y` can prepend a duplicate `shop=X` parameter before the real `shop=Y`. `Object.fromEntries` still resolves `authQuery.shop` to `Y` (last), so HMAC/state validation passes exactly as Shopify signed it, but `query.get('shop')` resolves to `X` (first), so the library performs the access-token exchange against `X`'s domain and stamps the resulting `Session.shop` as `X` — a value that was never part of the HMAC-signed parameter set. This violates the stated invariant that "authenticity via HMAC must be unambiguous over the exact signed parameter set."

### Impact Explanation
This is a violation of the HMAC-signed-parameter invariant: the shop that is cryptographically validated (`Y`) is not the shop the library actually acts on (`X`) for the token exchange/session shop binding — a within-library parameter-pollution/canonicalization mismatch matching the "cross-tenant OAuth token binding" impact class in the prompt. Full end-to-end account takeover additionally depends on Shopify's `/admin/oauth/access_token` endpoint accepting a code across a different shop domain than it was issued for; if Shopify enforces per-shop code binding server-side (standard OAuth practice), the token exchange to shop `X` will fail server-side and no session for `X` is created, capping the practical blast radius to a failed/erroring request rather than a completed cross-tenant session. Regardless, the library-level canonicalization ambiguity is real and inconsistent with the hardening Shopify already applied to the app-proxy path in the same file.

### Likelihood Explanation
Reachable via a normal unauthenticated HTTP client crafting the callback URL/query string — no special role or secret needed, and the "confusable" duplicate shop is trivially added before an intercepted or replayed legitimate signed callback. However, achieving observable cross-tenant impact hinges on an external factor (Shopify's OAuth token endpoint shop-code binding) outside this repository's control, which likely blocks the token exchange, reducing practical exploitability to a discovered inconsistency rather than a demonstrated account takeover in this codebase alone.

### Recommendation
Canonicalize the query exactly once in `callback()` and use that single canonical value everywhere: pass the raw `URLSearchParams` into `validateHmac` (or a helper that both validates and returns a single normalized `shop`), reject duplicated `shop`/`hmac`/`state`/`timestamp` keys unconditionally (not just for `signator === 'appProxy'`), and use that same validated `shop` value at line 194 for `sanitizeShop`, the token-exchange URL, and the created `Session`, rather than re-reading `query.get('shop')`.

### Proof of Concept
```ts
// Demonstrates first-vs-last duplicate 'shop' resolution divergence
// between HMAC validation (Object.fromEntries -> last) and
// oauth.ts's token-exchange/session shop (URLSearchParams.get -> first).

const qs =
  'shop=attacker.myshopify.com' +         // first occurrence -> used by query.get('shop')
  '&code=REAL_CODE_FOR_VICTIM' +
  '&state=REAL_STATE' +
  `&timestamp=${Math.trunc(Date.now() / 1000)}` +
  '&shop=victim.myshopify.com' +          // last occurrence -> wins in Object.fromEntries
  '&hmac=REAL_HMAC_SIGNED_FOR_SHOP_VICTIM';

const params = new URL(`https://app.example.com/auth/callback?${qs}`).searchParams;

console.log(params.get('shop'));                      // "attacker.myshopify.com" (first)
console.log(Object.fromEntries(params.entries()).shop); // "victim.myshopify.com" (last)

// -> validateHmac(authQuery) validates against "victim.myshopify.com" and PASSES
//    (matches Shopify's real signature), but oauth.ts's cleanShop
//    (query.get('shop')) resolves to "attacker.myshopify.com", so the
//    access-token POST is sent to https://attacker.myshopify.com/admin/oauth/access_token
//    and Session.shop is set to "attacker.myshopify.com" -- a value never
//    covered by the validated HMAC.
```
Expected (desired) behavior: `callback()` should reject this request outright with an `InvalidHmacError`/`Query parameter "shop" must not appear more than once.` instead of silently using divergent `shop` values for validation vs. action, matching the protection already present for `signator: 'appProxy'` at [4](#0-3) .

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
