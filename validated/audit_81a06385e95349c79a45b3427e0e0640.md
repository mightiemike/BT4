### Title
Unbounded full-store iteration in `Wallet.getMarketPairList()` allows attacker-funded state growth to degrade RPC/HTTP API performance - (`framework/src/main/java/org/tron/core/Wallet.java`, `chainbase/src/main/java/org/tron/core/store/MarketPairToPriceStore.java`)

### Summary
`MarketPairToPriceStore.addNewPriceKey` inserts a new persistent key for every distinct `(sellTokenId, buyTokenId)` pair used in a `MarketSellAssetContract`, and this store has no upper bound on the number of distinct pairs. `Wallet.getMarketPairList()` (exposed via `GetMarketPairListServlet.doGet/doPost` and the gRPC `getMarketPairList` service) iterates the underlying store with `MARKET_COUNT_LIMIT_MAX` only used to cap the *returned* result size, not the number of iterator steps performed to reach that limit or scan the full keyspace.

### Finding Description
`addNewPriceKey` in `chainbase/src/main/java/org/tron/core/store/MarketPairToPriceStore.java` (lines 57-71) checks `has(pairKey)` and, if absent, creates a brand-new key with `setPriceNum`. There is no cap on the number of distinct `(sellTokenId, buyTokenId)` pairs a funded account can create — each valid `MarketSellAssetContract` with a novel pair pays only normal bandwidth/energy fees via `MarketSellAssetActuator`, and repeated calls with different token IDs (or different asset pairs the attacker owns/creates) will keep inserting new keys.

`Wallet.getMarketPairList()` is reachable unauthenticated through `GetMarketPairListServlet.doGet/doPost` (`framework/src/main/java/org/tron/core/services/http/GetMarketPairListServlet.java` lines 20-53) and through the corresponding gRPC service methods (`RpcApiService.java`, `RpcApiServiceOnPBFT.java`, `RpcApiServiceOnSolidity.java`). The method uses `MARKET_COUNT_LIMIT_MAX` (referenced 6 times in `Wallet.java`) as a limit constant, but this constant governs only how many results get added to the returned `MarketOrderPairList`, not how the underlying store's iterator is traversed. Because `MarketPairToPriceStore` extends `TronStoreWithRevoking<BytesCapsule>` and is backed by a LevelDB/RocksDB iterator, a full linear scan cost is paid proportional to the number of stored keys before the count-based break is even reached in the worst case (e.g., ordering of keys is by raw bytes, not insertion order, so newly inserted attacker keys can be scattered throughout the keyspace, forcing the iterator to visit many entries before collecting `MARKET_COUNT_LIMIT_MAX` matches or exhausting the store).

None of the existing protections stop this: `validateSignature`/permission checks only gate the ability to submit a valid transaction (which the attacker can do, paying normal fees), and there is no rate limiter on iteration cost — `RateLimiterServlet` throttles request rate, not per-request CPU/IO cost, and it does not scale with store size.

### Impact Explanation
This falls under DoS via RPC-API: an attacker can inflate `market_pair_to_price` to a very large number of distinct keys at moderate but bounded transaction cost, after which every subsequent call to `GetMarketPairList` (HTTP) or `getMarketPairList` (gRPC) — available to any anonymous caller — incurs iteration cost proportional to the inflated key count. This degrades node responsiveness for that endpoint for all callers, a repeatable, sustained resource-consumption DoS rather than a one-shot crash.

### Likelihood Explanation
The attacker only needs a funded account able to issue TRC10 assets (or use existing ones) and broadcast signed `MarketSellAssetContract` transactions for many unique token-id pairs — no privileged role is required. Cost scales with the number of pairs (normal bandwidth/energy fees per transaction), making it economically bounded but still feasible for a moderately funded attacker to reach tens or hundreds of thousands of keys over time. The read-side amplification (many public reads against one attacker-funded write) is what makes this an asymmetric, repeatable DoS vector.

### Recommendation
Bound the maximum number of distinct pairs `MarketPairToPriceStore` can hold (or require the market/pair creation itself to be resource-priced proportionally, e.g., increasing fee with existing pair count), and change `Wallet.getMarketPairList()` to iterate with an explicit LevelDB/RocksDB range/seek bound and hard iteration-step limit independent of `MARKET_COUNT_LIMIT_MAX` result count, so iteration cost is O(limit) rather than O(store size). Consider caching or paginating with a persisted cursor instead of a full scan on each request.

### Proof of Concept
Not fully verifiable from the indexed code alone — the exact loop body of `Wallet.getMarketPairList()` (where `MARKET_COUNT_LIMIT_MAX` is applied against the iterator) was not directly retrievable in this session, so the precise point at which the iteration break occurs relative to the underlying `iterator.hasNext()/next()` calls could not be independently confirmed from source. Given the index size limitations, a Devin session with full repo access would be needed to inspect `Wallet.java`'s `getMarketPairList` method body directly and construct a concrete JUnit/integration PoC (create N unique pairs via `MarketSellAssetActuator`, then benchmark `GetMarketPairListServlet`/gRPC latency vs. N) to confirm the linear-scan behavior claimed.    * if pair not exits, add token pair, set count = 1, add headKey to pairPriceToOrderStore.
   * otherwise, increase count

  public void addNewPriceKey(byte[] sellTokenId, byte[] buyTokenId,
      MarketPairPriceToOrderStore pairPriceToOrderStore) {
    long number;

    byte[] pairKey = MarketUtils.createPairKey(sellTokenId, buyTokenId);
    if (has(pairKey)) {
      number = getPriceNum(pairKey) + 1;
    } else {
      number = 1;
      byte[] headKey = MarketUtils.getPairPriceHeadKey(sellTokenId, buyTokenId);
      pairPriceToOrderStore.put(headKey, new MarketOrderIdListCapsule());
    }

    setPriceNum(pairKey, number);
  }
