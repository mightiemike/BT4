### Title
Wallet Contract Silently Upgrades a Zero/None `FunctionCall` Allowance to Unlimited Allowance - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract` (the eth-implicit wallet used to let an Ethereum-style signature control a NEAR account) translates an Ethereum-encoded `AddKey` action into a NEAR `AddKey` promise. When building the access-key allowance for a new `FunctionCall` access key, it collapses two semantically different attacker/user-supplied inputs — "no allowance specified" (`None`) and "an explicit zero allowance" (`Some(0)`) — into the same `Allowance::Unlimited` value, exactly mirroring the reported "excessive/blanket approval instead of an exact, bounded amount" bug class from the external report.

### Finding Description
`action_to_promise` builds the `AddKey` promise for a `FunctionCall` permission like this: [1](#0-0) 

```rust
near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
    .add_access_key_allowance_with_nonce(
        action.public_key,
        access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
        access.receiver_id,
        access.method_names.join(","),
        action.access_key.nonce,
    )),
```

`access.allowance` is `Option<NearToken>`, decoded directly from the caller-supplied Ethereum RLP transaction payload via `near_action::FunctionCallPermission`: [2](#0-1) 

In the near-sdk `Allowance` API, `Allowance::limited(amount)` returns `None` when `amount` is zero (a "limited-to-zero" request has no meaningful representation as `Limited`) and `Some(Limited(amount))` otherwise. Because the surrounding code does `.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited)`, **both** of the following inputs collapse to the *same* result, `Allowance::Unlimited`:
- `access.allowance == None` (the documented NEAR convention for "unlimited allowance", matching `FunctionCallPermission::allowance` semantics elsewhere in the protocol: `core/primitives-core/src/account.rs:960-966`)
- `access.allowance == Some(NearToken::from_yoctonear(0))` (an explicit "zero/no spending power" request)

The rest of the protocol treats these two cases very differently: everywhere else in nearcore, `None` means unlimited and `Some(0)` (or any finite value) is a hard, protocol-enforced spending cap that is checked and decremented on every use (`check_and_compute_new_allowance`, `runtime/runtime/src/verifier.rs:282-303`). The wallet contract's fallback erases this distinction and always grants an unlimited allowance whenever the caller's zero/absent allowance value fails to produce a `Limited` variant.

### Impact Explanation
An unprivileged holder of the eth-implicit account's private key (or, more importantly, any front-end/relayer that constructs the RLP transaction on the user's behalf and gets it signed) can cause a `FunctionCall` access key to be added to the account with **unlimited** spending allowance on account balance for gas/fees, even though the transaction explicitly encoded a zero allowance. A malicious or compromised dApp/relayer that crafts the "AddKey" request with `allowance = 0` (visually/semantically presented to the user as "this key cannot spend any of your balance") will silently obtain a key that can drain the account's NEAR balance via repeated `FunctionCall` gas/fee charges, without the user ever intending to grant that capability. This is a direct, unauthorized-value-movement class issue reachable purely through a single signed RLP payload processed by `rlp_execute`, matching the "excessive approval to an external/untrusted party" bug class from the report (there, unlimited router approvals; here, unlimited access-key spending allowance).

### Likelihood Explanation
Reaching this path only requires calling the wallet contract's public `rlp_execute` entry point with an `AddKey`/`FunctionCall` action whose `allowance` field is `0` or absent — both are ordinary, easily constructed inputs, no privileged role or compromised validator is needed. The only precondition is a valid Ethereum-style signature over the RLP transaction, which is exactly the transaction-signer capability explicitly in scope.

### Recommendation
Distinguish the "explicit unlimited" (`None`) case from "explicit zero" (`Some(0)`) case before falling back to `Allowance::Unlimited`. For example, only default to `Unlimited` when `access.allowance.is_none()`, and reject (or treat as a no-op / error) an explicit `Some(0)` allowance instead of silently promoting it to unlimited:
```rust
let allowance = match access.allowance {
    None => Allowance::Unlimited,
    Some(amount) => Allowance::limited(amount)
        .ok_or_else(|| /* explicit zero allowance error */)?,
};
```

### Proof of Concept
1. Attacker-controlled or compromised front-end constructs an Ethereum RLP transaction targeting the victim's eth-implicit account, containing a NEAR `Action::AddKey` with `FunctionCallPermission { allowance: Some(NearToken::from_yoctonear(0)), receiver_id: <victim-chosen contract>, method_names: [...] }` and an attacker-supplied `public_key`.
2. Victim signs the transaction believing they are authorizing a key with zero spending power (as literally encoded).
3. Victim (or relayer) submits it via `rlp_execute(target, tx_bytes_b64)`.
4. `action_to_promise` computes `access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited)` → `Allowance::Unlimited`, because `Allowance::limited(0)` returns `None`.
5. The resulting `AddKey` promise creates a `FunctionCall` access key on the victim's account with **unlimited** allowance instead of the requested zero, letting the attacker's key drain the account balance via subsequent function calls' gas/fee charges.
