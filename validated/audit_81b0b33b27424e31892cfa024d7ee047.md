The comment `runtime/near-vm-runner/src/imports.rs:312-316` and the design note in `core/primitives/src/action/mod.rs:337-340` establish the intended security invariant: a `WithdrawFromGasKey` action must only ever be reachable as a **top-level transaction action** signed directly by the account owner, specifically so that the SPICE pending-transaction queue (which polices gas-key solvency for in-flight transactions) can see it and account for the balance being drained. This is functionally identical to the Open Dollar bug: a lower-level state-mutating primitive (`action_withdraw_from_gas_key` / `SafeEngine.modifySAFECollateralization`) is supposed to be reachable only through one gate (top-level tx / `ODSafeManager`) that keeps a companion bookkeeping system accurate, but before the fix a second path (`Delegate`/`DelegateV2` nesting → `SafeEngine` direct call) let a signer reach the primitive while bypassing that bookkeeping, corrupting the higher-level invariant it exists to protect (surplus/tax accounting vs. SPICE's funded-gas-key accounting).

### Title
Nested `WithdrawFromGasKey` inside a `DelegateAction` bypassed the pending-transaction queue's gas-key solvency accounting - ([File: runtime/runtime/src/action_validation.rs])

### Summary
Before `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`, a signer could wrap a `WithdrawFromGasKeyAction` inside a `DelegateAction`/`DelegateV2` meta-transaction and have it accepted and executed by `apply_delegate_action`, even though `WithdrawFromGasKey` was designed to be reachable only as a direct, top-level transaction action.

### Finding Description
`WithdrawFromGasKeyAction` moves prepaid balance out of a `GasKeyInfo` back into the owning account (`runtime/runtime/src/access_keys.rs` `action_withdraw_from_gas_key`, executed from `Action::WithdrawFromGasKey` in `runtime/runtime/src/lib.rs:812-820`). Its doc comment explicitly states: "This action must only be available via transactions, not via contract execution (there is no corresponding promise batch action host function)" [1](#0-0) , and the VM import table reiterates: "Actions that reduce gas key balance must only be initiated via transactions, not by contracts. Otherwise, they will not be visible to the pending transaction queue... See NEP-611" [2](#0-1) .

The root cause documented for the fix: "The SPICE pending transaction queue scans only the top level actions of a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key that the queue still counts as funded" [3](#0-2) . That is, a companion subsystem (analogous to the `ODSafeManager`/tax collector) maintains an out-of-band ledger of gas-key balances assumed to still be funded for pending transactions, but nesting the withdrawal inside a `Delegate` action let it execute through `apply_delegate_action` (`runtime/runtime/src/actions.rs`) without that ledger observing it, exactly as calling `SafeEngine.modifySAFECollateralization()` directly bypassed `ODSafeManager`'s tax-collector call.

The fix added `validate_withdraw_from_gas_key_action` at the top level and rejected the action when nested, via `ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate` [4](#0-3) , gated by `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`.

### Impact Explanation
A gas key's funded balance is relied upon by the pending-transaction queue to admit further gas-key transactions optimistically before they finalize. If a nested withdrawal can drain the key without the queue's knowledge, subsequent gas-key transactions admitted against the (stale) assumed balance can be charged against funds that no longer exist, leading to accounting/consensus-relevant mismatches between what the pending queue believes is available and true on-chain state — a state-transition/bookkeeping bypass in the same class as generating unbacked debt in the reported bug.

### Likelihood Explanation
Reachable by any account holder with a gas key and a relayer (or self as relayer) — no privileged role, validator, or network position required; only a standard `SignedDelegateAction` wrapping a `WithdrawFromGasKeyAction`, as demonstrated in the regression test `test_reject_delegated_gas_key_withdraw_protocol_upgrade` [5](#0-4) , which shows the nested withdrawal being admitted and executed pre-fix.

### Recommendation
This is already fixed on protocol version `RejectWithdrawFromGasKeyInDelegate` via `validate_withdraw_from_gas_key_action` rejecting `WithdrawFromGasKey` whenever it appears inside a `Delegate`/`DelegateV2` payload for new transactions/receipts [6](#0-5) . Confirm the fix is active at/above the deployed protocol version and that any other "transaction-only" gas-key actions (e.g. future host-function-less actions) are similarly validated against nesting inside `Delegate` payloads, and that any other queue/ledger that only scans top-level actions is audited for the same nested-action blind spot.

### Proof of Concept
Use the existing regression test as the PoC, run against the protocol version prior to the fix: it builds a `DelegateAction` whose single inner action is `WithdrawFromGasKeyAction`, submits it via a relayer, and shows the withdrawal succeeds and drains the gas key balance without the pending queue rejecting it [7](#0-6) .

/// Validates a single given action.
/// The `mode` only affects nested validation of `Action::Delegate` payloads
fn validate_action_with_mode(
    limit_config: &LimitConfig,
    action: &Action,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    match action {
        Action::CreateAccount(_) => Ok(()),
        Action::DeployContract(a) => validate_deploy_contract_action(limit_config, a),
        Action::DeployGlobalContract(a) => validate_deploy_global_contract_action(limit_config, a),
        Action::UseGlobalContract(a) => validate_use_global_contract_action(a),
        Action::FunctionCall(a) => {
            validate_function_call_action(limit_config, a, current_protocol_version, mode)
        }
        Action::Transfer(_) => Ok(()),
        Action::Stake(a) => validate_stake_action(a),
        Action::AddKey(a) => validate_add_key_action(limit_config, a, current_protocol_version),
        Action::DeleteKey(_) => Ok(()),
        Action::DeleteAccount(a) => validate_delete_action(a),
        Action::Delegate(a) => validate_delegate_action(
            limit_config,
            (&a.delegate_action).into(),
            receiver,
            current_protocol_version,
            mode,
        ),
        Action::DelegateV2(a) => {
            require_protocol_feature(
                ProtocolFeature::DelegateV2,
                "DelegateV2",
                current_protocol_version,
            )?;
            // Receipts created before the removal are still in flight and must
            // keep executing, so only new transactions and receipts are refused.
            if mode == ValidateReceiptMode::NewReceipt {
                reject_removed_protocol_feature(
                    ProtocolFeature::RejectDelegateV2,
                    "DelegateV2",
                    current_protocol_version,
                )?;
            }
            validate_delegate_action(
                limit_config,
                (&a.delegate_action).into(),
                receiver,
                current_protocol_version,
                mode,
            )
        }
        Action::DeterministicStateInit(a) => {
            validate_deterministic_state_init(limit_config, a, receiver)
        }
        Action::UniversalStateInit(a) => {
            validate_universal_state_init(limit_config, a, receiver, current_protocol_version)
        }
        Action::TransferToGasKey(_) => {
            validate_transfer_to_gas_key_action(current_protocol_version)
        }
        Action::WithdrawFromGasKey(_) => {
            validate_withdraw_from_gas_key_action(current_protocol_version)
        }
    }
