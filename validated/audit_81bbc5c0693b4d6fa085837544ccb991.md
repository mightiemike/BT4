### Title
Unbounded gzip decompression of user-supplied Cairo0 program in RPC declare-transaction path (zip bomb DoS) - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
The RPC node's `decompress_program` function decompresses a base64+gzip-encoded Cairo0 `program` field supplied directly by an unprivileged RPC caller, without any size or time limit, unlike every other decompression path in this codebase.

### Finding Description
`decompress_program` reads a caller-supplied base64 string, gzip-decodes it, and streams the output into an unbounded `Vec<u8>` via `decoder.read_to_end(&mut decompressed, ...)`, with only a `// TODO(dan): add time and size limits.` comment acknowledging the gap: [1](#0-0) 

This is reached from `user_deprecated_contract_class_to_sn_api`, which is invoked when converting a `BroadcastedDeclareTransaction::V1` (a Cairo0 declare, containing a user-controlled `contract_class.compressed_program`) into an executable transaction for local RPC execution (e.g., `starknet_estimateFee` / `starknet_simulateTransactions` / trace endpoints): [2](#0-1) 

By contrast, every other decompression path in the repository enforces an explicit output-size cap:
- `starknet_api::compression_utils::decompress_with_size_limit` bounds the GzDecoder read via `.take(max_size + 1)` and errors on overflow: [3](#0-2) 
- `apollo_storage::compression_utils::decompress` bounds zstd output to `MAX_DECOMPRESSED_SIZE` (256 MB): [4](#0-3) 
- The gateway's own Cairo0-program decompression path (used for transactions submitted to the sequencer for inclusion) is size-limited via `decode_and_decompress_with_size_limit` with a 4 MB cap: [5](#0-4) 

`decompress_program` is the one outlier that omits this protection, mirroring the akka-http `decodeRequest`/`decodeRequestWith` bug class (CVE-2018-16131): an attacker sends a small, highly-compressed payload that expands to a huge amount of memory during decompression, causing memory exhaustion / node crash — the same "decompression bomb" primitive described in the external report.

### Impact Explanation
An unprivileged JSON-RPC caller invoking an execution-simulation endpoint (`starknet_estimateFee`, `starknet_simulateTransactions`, or similar) with a `BroadcastedDeclareTransaction` V1 whose `contract_class.compressed_program` is a crafted gzip bomb (e.g., a few KB compressing to gigabytes) can force the RPC node process to allocate unbounded memory, leading to OOM and process crash — denial of service against that RPC node. If the RPC node is co-located with, or shares resources with, sequencer/execution infrastructure, this could degrade or halt block production/serving on that instance, matching "network unable to confirm new transactions" for the affected node. Severity is bounded to the RPC service reachable via this specific conversion path; it does not by itself corrupt state or funds.

### Likelihood Explanation
High likelihood: this is directly reachable with a single unauthenticated/unprivileged JSON-RPC request containing a `DECLARE` v1 broadcasted transaction, no special permissions or prior state are required, and the vulnerable function has an explicit unresolved TODO marking the missing protection, confirming the gap is intentional/known but unaddressed rather than defended by an outer layer (the HTTP body-size limit only bounds the *compressed* wire size, not the decompressed output size).

### Recommendation
Apply the same bounded-decompression pattern already used elsewhere in the codebase to `decompress_program`: use `starknet_api::compression_utils::decode_and_decompress_with_size_limit` (or wrap the `GzDecoder` with `.take(MAX_SIZE)` as done in `decompress_with_size_limit`) with an explicit, configured maximum decompressed program size, returning an RPC error instead of unbounded allocation when the limit is exceeded.

### Proof of Concept
1. Construct a Cairo0 program JSON object and gzip-compress it with a highly repetitive/compressible payload (a classic zip bomb: e.g., a few KB of zeros compresses to gigabytes) and base64-encode it.
2. Submit a JSON-RPC request to an execution-simulation method (e.g., `starknet_estimateFee`) with a `BroadcastedDeclareTransaction` of version `0x1` where `contract_class.compressed_program` is the crafted payload.
3. Server-side, `TryFrom<BroadcastedDeclareTransaction>` calls `user_deprecated_contract_class_to_sn_api` → `decompress_program`, which calls `GzDecoder::read_to_end` with no size cap [1](#0-0) , causing the process to attempt to allocate the fully decompressed size in memory, exhausting available memory and crashing/hanging the RPC node.

fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
