### Title
Off-chain accounts lattice hash updates silently corrupt the accounts hash on duplicate pubkeys in release builds - ([File: runtime/src/bank/accounts_lt_hash.rs])

### Summary
`Bank::enqueue_off_chain_accounts_lt_hash_updates` only *detects* duplicate pubkeys under `cfg!(debug_assertions)`, and even then only panics rather than correcting the accounting. In release builds (i.e. real validators), the debug-only duplicate check is compiled out entirely, and if the same pubkey appears more than once in a single off-chain `store_accounts` batch, both updates are independently enqueued to the async lt-hash worker pool with no ordering guarantee between them.

### Finding Description
`enqueue_off_chain_accounts_lt_hash_updates` is explicitly documented as *not* deduplicating and *requiring the caller to ensure there are no duplicates* [1](#0-0) , in contrast to its sibling `enqueue_on_chain_accounts_lt_hash_updates`, which explicitly walks the batch in reverse and skips all but the latest version of each pubkey [2](#0-1) .

The only safety net for the off-chain path is a `cfg!(debug_assertions)` block that scans for duplicate pubkeys and `panic!`s if any are found [3](#0-2) . This check is compiled out in release builds, which is exactly how validators run in production. If a duplicate pubkey does slip into `accounts` in a release build, each occurrence independently calls `load_with_fixed_root_do_not_populate_read_cache` to snapshot a "previous" account state and then enqueues an `AccountsLtHashUpdate { prev_account, curr_account }` job to the async hasher thread pool [4](#0-3) .

Each queued job is processed independently and unconditionally: `process()` mixes out whatever `prev_account` it captured and mixes in `curr_account`, with no coordination between jobs touching the same pubkey [5](#0-4) . Because the jobs are scheduled onto a rayon thread pool (`thread_pool.spawn`) and the loads happen at spawn-time in `load_then_enqueue`, whichever duplicate entry is scheduled/executed "first" determines what "previous" state gets subtracted, and the accumulation order across workers is non-deterministic (`accumulators[worker_index]` mixed per-thread, then merged in `finish()`) [6](#0-5) . This is the direct analog of the reported bug class: multiple "contributions" to a single shared, order-independent aggregate (the lattice hash) are computed from a naive "before/after" snapshot without proper accounting for concurrent/duplicate updates to the same key, so whichever update is processed "first" effectively determines (and can corrupt) the final shared result — mirroring the "first mover" flaw in the original report where a shared pooled balance was computed via simple subtraction without tracking which contribution had already been consumed.

`store_accounts` / `store_accounts_without_stakes_cache`, which call this function, are documented with the same caller obligation ("Callers must ensure there are no duplicates in `accounts`") [7](#0-6) , and are used for off-chain paths such as partitioned epoch-reward stake-account stores [8](#0-7) . If any future off-chain caller (or a regression in reward computation / duplicate stake-reward entries) ever produces two entries for the same pubkey in one batch, the accounts lattice hash update becomes silently non-deterministic/incorrect in production, since the debug-only detection would not fire.

### Impact Explanation
An incorrect accounts lt-hash mixing (missing a mix-out, double mixing-in, or mixing based on a stale/aliased `prev_account`) causes the bank's cumulative accounts lattice hash to diverge from the true post-state of accounts. This directly threatens accounts-hash/capitalization integrity guarantees (`Bank::verify_accounts` compares this value against an independently recomputed hash from the index) [9](#0-8) , and could produce an honest-node hash mismatch (bank hash divergence) that is undetectable in release builds because the guarding assertion only exists under `debug_assertions`.

### Likelihood Explanation
Low-to-moderate. Under `cfg!(debug_assertions)`, any duplicate immediately panics, so this would surface quickly in debug/test builds if a caller ever violated the "no duplicates" contract, and current known callers (partitioned epoch reward stake-account stores) appear to avoid duplicates by construction. However, the release-build silent-failure mode is a real gap: nothing in the type system or in `store_accounts`'s production code path enforces the "no duplicates" invariant, so any future or overlooked code path that batches off-chain stores with a repeated pubkey (e.g. a reward-calculation bug producing two entries for the same stake account, or a future off-chain feature reusing `store_accounts`) would corrupt the hash without any runtime signal in a production/release validator.

### Recommendation
Make the duplicate-pubkey guard unconditional (not gated by `cfg!(debug_assertions)`) in `enqueue_off_chain_accounts_lt_hash_updates`, or better, make the function itself deduplicate (mirroring `enqueue_on_chain_accounts_lt_hash_updates`'s reverse-scan/skip-earlier-duplicates logic) rather than relying on caller discipline enforced only by doc comments and debug-only assertions.

### Proof of Concept
The codebase's own regression test demonstrates the exact failure surface, but only proves detection under debug assertions — it does not, and structurally cannot, prove correctness in release builds: [10](#0-9) 
This test shuffles duplicate `(pubkey, account)` pairs and calls `bank.store_accounts(...)`, expecting a panic ("duplicate accounts were enqueued for hashing"). In a `--release` build this panic path is compiled out (`cfg!(debug_assertions)` is `false`), so the same input would silently proceed to enqueue independent, unordered `AccountsLtHashUpdate` jobs for the duplicated pubkey via `load_then_enqueue`/`spawn`, and `finish_accounts_lt_hash_updates` would fold the result into `Bank::accounts_lt_hash` with no correctness guarantee, exactly the reachable release-mode path described above.

    /// Enqueues `update` into `thread_pool` for asynchronous processing.
    fn spawn(&self, thread_pool: &'static ThreadPool, update: AccountsLtHashUpdate) {
        self.num_jobs_pending.fetch_add(1, Ordering::Relaxed);
        self.num_jobs_total.fetch_add(1, Ordering::Relaxed);
        thread_pool.spawn({
            let accumulators = Arc::clone(&self.accumulators);
            let num_jobs_pending = Arc::clone(&self.num_jobs_pending);
            move || {
                // SAFETY: We always call from the same/correct Rayon thread pool.
                let worker_index = thread_pool.current_thread_index().unwrap();

                // SAFETY: There are num_threads accumulators, and each
                // thread's index shall always be in range 0..num_threads.
                debug_assert!(worker_index < accumulators.len());
                let accumulator = unsafe { accumulators.get_unchecked(worker_index) };

                Self::process(&mut accumulator.lock().unwrap(), update);

                // Decrementing the number of pending jobs MUST happen *after*
                // accumulating the result.  This ensures `finish()` cannot
                // observe zero pending jobs until all workers are done.
                num_jobs_pending.fetch_sub(1, Ordering::Relaxed);
            }
        });
    }

    /// Waits for all pending jobs to complete, then mixes the results into `lt_hash`.
    ///
    /// Returns the number of asynchronous jobs completed.
    ///
    /// Note: Since an LtHash is large, `lt_hash` is passed as an in-out parameter.
    /// This it to avoid Rust compiler bug that fails to perform return value optimization.
    fn finish(&self, lt_hash: &mut LtHash) -> u64 {
        while self.num_jobs_pending.load(Ordering::Relaxed) > 0 {
            // Spin, do not yield! This is called by Bank::freeze() and we want to be fast.
            hint::spin_loop();
        }

        for thread_accumulator in self.accumulators.iter() {
            lt_hash.mix_in(&thread_accumulator.lock().unwrap());
        }
        self.num_jobs_total.load(Ordering::Relaxed)
    }

    /// Processes `update` and mixes the result into `accum_lt_hash`.
    ///
    /// Note: Since an LtHash is large, `accum_lt_hash` is passed as an in-out parameter.
    /// This it to avoid Rust compiler bug that fails to perform return value optimization.
    fn process(accum_lt_hash: &mut LtHash, update: AccountsLtHashUpdate) {
        let AccountsLtHashUpdate {
            address,
            prev_account,
            curr_account,
        } = update;
        if let Some(prev_account) = prev_account {
            let prev_lt_hash = AccountsDb::lt_hash_account(&prev_account, &address);
            accum_lt_hash.mix_out(&prev_lt_hash.0);
        }
        if let Some(curr_account) = curr_account {
            let curr_lt_hash = AccountsDb::lt_hash_account(&curr_account, &address);
            accum_lt_hash.mix_in(&curr_lt_hash.0);
        }
    }

        &self,
        accounts: impl StorableAccounts<'a>,

        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();

        (0..accounts.len()).for_each(|i| {
            accounts.account(i, |account| {
                self.stakes_cache.check_and_store(
                    account.pubkey(),
                    &account,
                    new_warmup_cooldown_rate_epoch,
                    use_fixed_point_stake_math,
                )

        self.store_accounts_without_stakes_cache(accounts, thread_pool_for_loading_accounts);
        m.stop();
        self.rc
            .accounts
            .accounts_db
            .stats
            .stakes_cache_check_and_store_us
            .fetch_add(m.as_us(), Relaxed);
    }
