### Title
Disabled/deprecated TokenConfig entries are still honored for minting during inbound execution - (File: x/uexecutor/keeper/execute_inbound_gas.go, x/uexecutor/keeper/execute_inbound_funds_and_payload.go, x/uregistry/keeper/keeper.go)

### Summary
The external report's core lesson is: an account/config that is supposed to gate an operation (`master_edition` gating non-fungibility) was fetched and trusted without checking the flag/field that actually encodes its validity. In Push Chain, `TokenConfig.enabled` (`bool enabled = 6; // Whether this token is enabled for minting/bridging`, [1](#0-0) ) is documented as the authorization gate for minting/bridging a given external asset, but `Keeper.GetTokenConfig` ( [2](#0-1) ) never inspects it, and none of the `x/uexecutor` execution paths that call `GetTokenConfig` (`ExecuteInboundGas`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`) check `tokenConfig.Enabled` before deriving the PRC20 address and calling `depositPRC20`/`gasAndPayloadDepositAutoSwap`.

### Finding Description
An unprivileged attacker who deposits on a source chain controls the `AssetAddr` field observed by Universal Validators (it is simply the token address used in their own on-chain deposit transaction, e.g. via the `addFunds` gateway method). Honest UVs faithfully report this value in `Inbound.AssetAddr`, and `MsgVoteInbound` finalizes a `UniversalTx` once quorum is reached — no validator dishonesty is required. [3](#0-2) 
The keeper resolves `tokenConfig.NativeRepresentation.ContractAddress` purely from the existence of a `TokenConfigs` entry keyed by `(chain, asset_addr)`, with no check of `tokenConfig.Enabled`: [2](#0-1) 
The same pattern repeats in the isCEA branches of `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`, which call `k.uregistryKeeper.GetTokenConfig` and immediately use the returned `NativeRepresentation.ContractAddress` to mint PRC20 tokens, again without an `Enabled` gate: [4](#0-3) 
If governance disables a `TokenConfig` (e.g., because the external asset is compromised, delisted, or has a stale/incorrect `NativeRepresentation`/`decimals`/`liquidity_cap`) rather than removing it outright, the row still exists in `TokenConfigs`, so `GetTokenConfig` still succeeds and the PRC20 mint path is still exercised.

### Impact Explanation
This corrupts PRC20/native asset accounting semantics: tokens documented as "disabled for minting/bridging" can still be minted by an ordinary depositor, which is the same category as the external report's core issue (an on-chain gate is fetched but not enforced). This does not steal validator/protocol funds directly, but it violates the intended registry invariant that `Enabled=false` blocks minting, potentially reintroducing a token with a stale/incorrect liquidity cap or contract mapping into circulation after it was deliberately disabled.

### Likelihood Explanation
I could not fully verify how frequently or for what purpose token configs are disabled in production versus removed outright, nor whether any earlier stage (e.g. `ValidateForExecution`, ante handlers, or a chain/registry-level check I didn't locate) enforces `Enabled` before this code is reached — my search of `x/uexecutor` for `.Enabled` references only found two unrelated hits (`msg_execute_payload.go`, `msg_migrate_uea.go`), and `x/uregistry`'s own `AddTokenConfig`/`RemoveTokenConfig` tests focus on canonical-key collisions, not on enforcement of the `Enabled` flag downstream. Given the index size limits mentioned for this tool, it's possible a check exists elsewhere (e.g., in `ValidateForExecution` in `x/uexecutor/types/inbound.go`, which I reviewed and does not reference `Enabled` either) that I was unable to surface. I'd recommend confirming with a full-repo grep for `.Enabled` across `x/uregistry` and `x/uexecutor` in a Devin session before treating this as fully confirmed — the `ChainConfig.Enabled` gate is clearly enforced (`chainConfig.Enabled.IsInboundEnabled` in `msg_execute_payload.go`), but the parallel `TokenConfig.Enabled` gate appears absent from the paths I traced.

### Recommendation
Add an explicit `tokenConfig.Enabled` check immediately after every `GetTokenConfig` call in the inbound execution paths (`execute_inbound_gas.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`), analogous to the existing `chainConfig.Enabled.IsInboundEnabled` check, and treat a disabled token the same as a missing token config (FAILED PCTx + revert outbound where applicable).

### Proof of Concept
Not independently confirmed end-to-end due to tool limitations; the described trigger is: (1) governance sets `TokenConfig.Enabled=false` for a given `(chain, asset_addr)` pair without removing the row, (2) an attacker deposits the corresponding external asset on the source chain using an ordinary user transaction, (3) honest UVs observe and vote the inbound, (4) `ExecuteInboundGas`/`ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` still successfully call `GetTokenConfig` and proceed to mint PRC20 via `depositPRC20`/`gasAndPayloadDepositAutoSwap` because `Enabled` is never checked.
