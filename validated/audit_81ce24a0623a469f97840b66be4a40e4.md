## Root cause

NEAR added a `promise_set_refund_to` host function (NEP-esque feature) that lets the **predecessor** of a receipt override the account that receives the balance refund if that receipt fails, instead of the receipt defaulting to the predecessor itself. [1](#0-0) 

The value passed to `set_refund_to` is stored on the pending `ActionReceipt` and later used as the target of `Receipt::new_balance_refund` when the receipt fails. [2](#0-1) [3](#0-2) 

When the receipt is validated, `refund_to` is checked only for **syntactic** `AccountId` validity — there is no check that the account exists or is of an implicit/creatable type: [4](#0-3) 

When the resulting balance-refund receipt is later executed, its single `Transfer` action goes through `check_account_existence`. For a `Transfer`, if the target account does not exist, implicit creation is only permitted for accounts whose id has an implicit/deterministic format (`is_implicit()`); an ordinary named account id (e.g. `"doesnotexist.near"`) that is syntactically valid but does not exist is rejected with `AccountDoesNotExist`: [5](#0-4) 

Per the refund model, when a refund receipt itself fails to execute, the amount is **not** re-refunded anywhere — it is simply burnt: [6](#0-5) 

This is the direct nearcore analog of the zkSync `_requestL2Transaction` bug: an attacker-controllable "refund recipient" field is accepted without verifying the recipient can actually receive the funds, so the refund/bridged value becomes permanently unrecoverable when the underlying receipt fails.

### Title
Unchecked `refund_to` account allows permanent loss of failed-receipt deposit refunds - (File: `runtime/runtime/src/verifier.rs`)

### Summary
`promise_set_refund_to` lets a contract redirect the balance refund of a receipt it creates to an arbitrary `AccountId` of its choosing. `validate_action_receipt` only validates that this id is syntactically well-formed, never that the account exists or can be auto-created. If the target account does not exist and is not one of the auto-creatable implicit account-id formats, the deposit-refund `Transfer` action fails with `AccountDoesNotExist`, and because refund receipts do not themselves get a further refund on failure, the deposited NEAR is burnt.

### Finding Description
A contract on behalf of a user calls another contract with an attached deposit through `promise_batch_create` / `promise_batch_action_function_call`, then calls `promise_set_refund_to` to redirect the deposit-refund target for that receipt to any account id string it likes: [1](#0-0) 

`set_refund_to` stores this value with no existence check: [7](#0-6) 

At receipt-validation time, only `AccountId::validate` (format/charset/length) is applied to `refund_to`; there is no check that the account exists, nor that it belongs to an auto-creatable class (`NearImplicit`/`EthImplicit`/`NearDeterministic`): [8](#0-7) 

If the downstream call fails (e.g. calling a non-existent method, insufficient gas, or any deliberate/attacker-engineered failure), a `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)` is generated targeting the attacker-chosen `refund_to` account: [9](#0-8) 

Executing that refund receipt runs the `Transfer` action against the (possibly nonexistent) target. `check_account_existence` only allows implicit account auto-creation for implicit-format ids; for an ordinary named, nonexistent id, it returns `AccountDoesNotExist`: [10](#0-9) 

Per protocol design, when a refund receipt (predecessor `"system"`) itself fails, the deposit is not refunded again — it is burnt outright: [6](#0-5) 

Existing tests only cover the intended, successful redirection case (`test_refund_to`), where `refund_to` points at a valid, existing account: [11](#0-10) 

There is no test or protocol rule preventing `refund_to` from being set to a syntactically-valid, non-existent, non-implicit account id, which is exactly the scenario that leads to burning.

### Impact Explanation
Any intermediary/relayer contract handling third-party deposits (e.g. a marketplace, bridge-style, or proxy contract that forwards a user's attached deposit to another contract call) can use `promise_set_refund_to` to redirect the refund path. If the downstream call is engineered or naturally fails, the user's deposited NEAR that should have been refunded to the predecessor is instead sent to a non-existent account and burnt — a real, unauthorized, permanent loss of user funds with no path to recovery. This matches the accepted impact category "permanently frozen funds" (here, destroyed rather than merely frozen, which is strictly worse).

### Likelihood Explanation
Reachable by any unprivileged contract deployer/caller: it requires only a `FunctionCall` action that invokes `promise_batch_create`, `promise_batch_action_function_call`, and `promise_set_refund_to` with an arbitrary account-id string, plus a downstream call that fails (trivially engineered by the calling contract itself, e.g. calling a non-existent method name). No validator, node, or protocol privilege is required — a single transaction/contract call chain is sufficient.

### Recommendation
Add a check in `validate_action_receipt` (or in `promise_set_refund_to` at host-function time) requiring `refund_to` to reference an account that either already exists or belongs to an implicit/auto-creatable account-id class, rejecting the action/receipt otherwise. Alternatively, when a balance-refund `Transfer` fails specifically due to `AccountDoesNotExist` for a `refund_to`-redirected refund, fall back to refunding the original predecessor instead of burning the deposit.

### Proof of Concept
1. Deploy a contract `relay` that: receives a deposit from user `Alice` via a `FunctionCall`, then does:
   - `promise_batch_create("victim_contract")`
   - `promise_batch_action_function_call(..., method_name="nonexistent_method", deposit=Alice_deposit, ...)` (guaranteed to fail, no contract/method there)
   - `promise_set_refund_to(promise_idx, "totally-nonexistent-account.near")`
2. `Alice` calls `relay` with an attached deposit.
2. The downstream call to `victim_contract::nonexistent_method` fails.
3. Runtime generates `Receipt::new_balance_refund("totally-nonexistent-account.near", deposit)` per `refund_unspent_gas_and_deposits`.
4. Executing that receipt's `Transfer` action hits `check_account_existence`, finds `"totally-nonexistent-account.near"` is a named (non-implicit) nonexistent account, and fails with `AccountDoesNotExist`.
5. Per the refund-receipt failure rule, the deposit is burnt rather than returned to `Alice` or `relay` — the funds are permanently lost, confirmed by the code paths at `runtime/runtime/src/verifier.rs:756-760`, `runtime/runtime/src/actions.rs:842-850`, and `docs/RuntimeSpec/Refunds.md:10-13`.

pub fn promise_set_refund_to(
    ctx: &mut Ctx,
    memory: &mut [u8],
    promise_idx: u64,
    account_id_len: u64,
    account_id_ptr: u64,

    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_set_refund_to".to_string(),
        }
        .into());
    }

        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        &ctx.config,
        account_id_ptr,
        account_id_len,

    let promise = ctx
        .promises
        .get(promise_idx as usize)
        .ok_or(HostError::InvalidPromiseIndex { promise_idx })?;

        Promise::Receipt(receipt_idx) => Ok(*receipt_idx),
        Promise::NotReceipt(_) => Err(HostError::CannotSetRefundToOnJointPromise),
    }?;

    ctx.ext.set_refund_to(receipt_idx, refund_to);
    Ok(())

    receipt: VersionedActionReceipt,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,

) -> Result<(), ReceiptValidationError> {
    if receipt.input_data_ids().len() as u64 > limit_config.max_number_input_data_dependencies {

        limit_config,
        receipt.actions(),
        receiver,
        current_protocol_version,
        mode,
    )
    .map_err(ReceiptValidationError::ActionsValidation)
}

pub(crate) fn check_account_existence(
    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    receipt_shape: ReceiptShape,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            }
            if get_account_type(account_id, config).is_implicit() {
                // Implicit accounts can only be created implicitly.
                // `CreateAccount` claims `actor_id` for the new account, which
                // would let the rest of the receipt add an access key to an id
                // whose private key the sender does not hold. Rejecting the action
                // is the simplest way to close that.
                // See https://github.com/nearprotocol/NEPs/pull/71
                return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::Transfer(_) => {
            let account_type = get_account_type(account_id, config);
            if account.is_none() && !implicit_creation_allowed(account_type, receipt_shape) {
                return Err(ActionErrorKind::AccountDoesNotExist {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

fn test_refund_to() {
    let group = RuntimeGroup::new(4, 4, near_test_contracts::rs_contract());

    let signer_sender = group.signers[0].clone();
    let signer_receiver = group.signers[1].clone();
    let deposit = Balance::from_yoctonear(1000);

    let data = serde_json::json!([
        {
            "batch_create": {
                "account_id": "near_2",
            },
            "id": 0
        },
        {
            "action_function_call": {
                "promise_index": 0,
                "method_name": "non_existing_function",
                "arguments": [],
                "amount": deposit,
                "gas": GAS_2,
            },
            "id": 0
        },
        {
            "set_refund_to": {
                "promise_index": 0,
                "beneficiary_id": "near_3"
            }, "id": 0
        }
    ]);

    let signed_transaction = SignedTransaction::from_actions(
        1,
        signer_sender.get_account_id(),
        signer_receiver.get_account_id(),
        &signer_sender,
        vec![Action::FunctionCall(Box::new(FunctionCallAction {
            method_name: "call_promise".to_string(),
            args: serde_json::to_vec(&data).unwrap(),
            gas: GAS_1,
            deposit,
        }))],
        CryptoHash::default(),
    );

    let handles = RuntimeGroup::start_runtimes(group.clone(), vec![signed_transaction.clone()]);
    for h in handles {
        h.join().unwrap();
    }

    println!("{:?}", group.executed_receipts);

    use near_primitives::transaction::*;
    let [r0] = &*assert_receipts!(group, signed_transaction) else {
        panic!("Incorrect number of produced receipts")
    };

    let receipts = &*assert_receipts!(group, "near_0" => r0 @ "near_1",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),
        {},
        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_1);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "call_promise");
        }
    );
    let [r1, refunds @ ..] = &receipts else { panic!("Incorrect number of produced receipts") };
    group.assert_gas_refunds(&refunds[..]);

    let receipts = &*assert_receipts!(group, "near_1" => r1 @ "near_2",

    );
