### Title
Replay-verification skips checkpoint hash comparison, allowing corrupted world-state root to pass as verified during backup restore/replay-verify - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs`) is the integrity check used by replay-verification tooling — `ChunkExecutorInner::verify_execution` (`execution/executor/src/chunk_executor/mod.rs`), backup restore's `TransactionRestoreController` (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`), `db-tool`'s `replay_on_archive`, and `aptos-debugger` — to confirm that locally re-executing a transaction produces the same result as the `TransactionInfo` fetched from an (accumulator/consensus-authenticated) source. The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as acknowledged by the in-code TODO.

### Finding Description
`ensure_match_transaction_info` builds a set of equality assertions between a freshly-computed `TransactionOutput` and an externally supplied, cryptographically authenticated `TransactionInfo`: [1](#0-0) 

It validates `status`, `gas_used`, the write-set hash (`state_change_hash`) and the event root hash, but the comment at lines 2197-2202 states verbatim that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", explicitly warning that "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

The write-set hash (`state_change_hash`) only commits to the individual transaction's write set — it says nothing about the resulting Sparse-Merkle/Jellyfish state root (`state_checkpoint_hash`) that is periodically computed and stored in `TransactionInfoV0`/`V1` (`types/src/transaction/mod.rs` lines 2405-2461). Two different sequences of prior states/writes can independently hash to the same write-set hash while producing different world-state roots. Consequently, comparing only the write-set hash instead of the state checkpoint hash misses genuine state divergence at exactly the point (state checkpoint construction) where a wrong VM/storage merge would first manifest.

This function is the sole "did local execution match the archived/authenticated record" gate for:
- `ChunkExecutorInner::verify_execution`, invoked from the chunk executor's epoch-replay path used by `TransactionReplayer` (backed up transaction restore) at `execution/executor/src/chunk_executor/mod.rs` lines 648-708. [2](#0-1) 
- Backup transaction restore (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`), which drives `TransactionReplayer` when restoring/verifying a backup against the chain's proven ledger info.
- `db-tool`'s `replay_on_archive` and `aptos-move/cli` / `aptos-debugger` transaction replay comparisons.

Because none of these call sites independently re-verify the state checkpoint hash against the JMT/accumulator-authenticated `TransactionInfo`, a divergence in the actually-committed state root (e.g., from a storage bug, a corrupted archive/backup chunk, a non-deterministic VM/storage bug, or an intentionally crafted malicious backup source feeding `TransactionListWithProof`/`TransactionOutputListWithProof`) would not be caught by `ensure_match_transaction_info`, even though the outer accumulator/write-set/event checks otherwise pass.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... must not silently persist" invariant for the replay/restore path: a node restoring from backup or running replay-verify can accept and commit a `TransactionInfo`/resultant state whose Merkle state root diverges from what local re-execution actually produced, while the tool reports success. This can corrupt durable ledger data on the restoring node (its Jellyfish Merkle Tree / state store would no longer match the honest network state), and any subsequent state-proof, account read, or API response served from that corrupted state would be silently wrong even though the restore/replay tool claimed a verified match. Because it's restricted to backup restore / replay-verify / debugging tools rather than the live consensus commit path, and the actual state-sync `apply_chunk`/commit path (`DoStateCheckpoint` with `maybe_known_state_checkpoints`, seen in `execution/executor/src/chunk_executor/mod.rs` lines 374-413) does perform a separate, correct check of computed vs. known checkpoint hashes, the practical blast radius is scoped to nodes relying on `verify_execution`/backup-restore-driven replay as their sole confidence check (e.g., archival nodes restoring from a backup, or operators running `replay-verify`/`replay_on_archive` to audit historical correctness).

### Likelihood Explanation
Triggering requires either (a) a genuine, otherwise-undetected non-determinism/storage bug that changes the state root without changing the write-set hash (unlikely but exactly what this check exists to catch), or (b) a malicious/corrupted backup source supplying self-consistent `(write_set, events, status, gas)` but a bad `state_checkpoint_hash`/state — which is plausible since these tools consume off-chain backup archives and can be pointed at attacker-controlled storage backends. Likelihood is moderate: it depends on an external/backup input being wrong or malicious, not on any privileged mainnet consensus behavior, but it is a real, already-acknowledged gap (the TODO in the source is explicit about it) rather than a hypothetical.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`-derived (or freshly recomputed) state-checkpoint hash, hot-state-checkpoint hash, and position-state-checkpoint hash against the corresponding fields on `txn_info` whenever those fields are `Some` on the authenticated `TransactionInfo`, mirroring the check the code comment says should exist before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled. At minimum, gate all call sites that rely on `ensure_match_transaction_info` as their integrity boundary (`ChunkExecutorInner::verify_execution`, backup transaction restore, `replay_on_archive`, `aptos-debugger`) so they fail loudly rather than silently succeeding when checkpoint hashes are absent from comparison.

### Proof of Concept
Conceptual (no local repro executed, since this is a logic-gap in a verification comparator rather than an exploitable transaction):
1. Prepare a `TransactionInfo` (as would come from an untrusted/compromised backup file or archive) whose `write_set`-derived fields (`state_change_hash`, `event_root_hash`, `gas_used`, `status`) match a given transaction/output pair exactly, but whose `state_checkpoint_hash` corresponds to a different (attacker-chosen) resulting state — feasible for a state-checkpoint transaction (e.g., a `StateCheckpoint`/`BlockEpilogue` boundary) where the "real" state differs from local storage due to a prior corrupted restore step.
2. Feed this into `TransactionReplayer`/`ChunkExecutorInner::verify_execution` (via backup restore or `replay_on_archive`) with `verify_execution_mode` enabled.
3. Observe that `ensure_match_transaction_info` returns `Ok(())` because it never inspects `txn_info.state_checkpoint_hash()`, even though the locally committed Jellyfish Merkle state now diverges from the network's authenticated state root.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
