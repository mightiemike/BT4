Based on my research, I found a strong analog to the CvgRewards division-by-zero bug in the Zest vault contracts' `accrue` function.

### Title
Division by Zero in vault `accrue` treasury-lp calculation permanently DoSes all vault operations - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

### Summary
The `accrue` function present identically in all six vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) computes a `treasury-lp` mint amount using `mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)`. If `total-assets-preview()` equals `reserve-inc`, the denominator is zero, causing a Clarity division-by-zero runtime abort. Since `accrue` is invoked at the top of every state-mutating vault entry point (`system-borrow`, `system-repay`, `deposit`, `redeem`), this failure blocks all further interaction with the vault, mirroring the `CvgRewards::_distributeCvgRewards` pattern where a shared denominator hitting zero permanently freezes protocol state and user funds.

### Finding Description
`accrue` reads cached state (`index`, `principal-scaled`, `total-borrowed`, `assets`, `fee-reserve`) and computes: [1](#0-0) 

- `debt-delta` = growth in debt this accrual (`new-debt - old-debt`)
- `reserve-inc` = `mul-div-down debt-delta fee-reserve BPS` (protocol's cut of the interest)
- `treasury-lp` = `mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)`, only computed when `reserve-inc > u0`

`total-assets-preview` is: [2](#0-1) 

If `total-assets-preview()` (i.e. `current-assets + interest`) is equal to `reserve-inc`, the subtraction yields `u0`, and `mul-div-down` divides by zero: [3](#0-2) 

This is directly analogous to the reported bug: in `CvgRewards`, `totalWeightLocked` could become zero and get used as a divisor in `_distributeCvgRewards`, permanently blocking cycle advancement and locking all users' CVG. Here, the denominator `(total-assets-preview - reserve-inc)` plays the same role as `totalWeightLocked`: it is a value derived from live state (not validated to be non-zero) that is used as a divisor inside a function (`accrue`) that gates every subsequent state-changing operation.

Critically, because Clarity's division-by-zero causes an unrecoverable runtime abort of the *entire transaction* (not a catchable `(err ...)` response), the call fails and **no state is persisted** — `index`, `lindex`, `assets`, and `total-borrowed` remain exactly as they were. This means the next call to any of `system-borrow`, `system-repay`, `deposit`, or `redeem` (all of which call `accrue` first) recomputes the identical `debt-delta`/`reserve-inc`/`total-assets-preview` values and hits the same zero denominator again — an irrecoverable, permanent DoS, since there is no external lever to reset `assets`, `total-borrowed`, or `fee-reserve` relationship to break the deadlock other than a governance parameter change (setting `fee-reserve` to zero), if even possible/known to operators.

### Impact Explanation
This lands squarely in the "permanent freezing of funds" impact class: once triggered, `deposit` and `redeem` on the affected vault revert unconditionally (since `accrue` is invoked unconditionally at the top of both, based on the surrounding code seen at lines 839-869 across vault files), stranding all depositor principal and any accrued yield inside the vault with no path to withdraw, exactly like the CvgRewards `burnPosition` being permanently blocked by the cycle never advancing.

### Likelihood Explanation
Low likelihood but not impossible — it requires the specific numeric coincidence `total-assets-preview() == reserve-inc()` at the moment `accrue` runs (e.g., very early after vault deployment, when `current-assets` and prior accumulated interest are small/zero and `fee-reserve` is configured at or near 100% of a debt-delta that exactly equals the vault's total assets preview). This mirrors the Sherlock judgment on the original issue: "unlikely but possible," and per Sherlock's rules a bug that "causes a loss of funds but requires certain external conditions or specific states" is valid at Medium/High depending on program rules — here it is a genuine unguarded division with no floor/zero-check, structurally identical to the reported root cause.

### Recommendation
Guard the division the same way the original fix recommends: check the denominator for zero before dividing, e.g.
```clarity
(treasury-lp (if (and (> reserve-inc u0) (> (total-assets-preview) reserve-inc))
                 (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))
                 u0))
```
This avoids the division-by-zero abort and lets `accrue` (and therefore all dependent lending operations) proceed, forfeiting only the treasury mint for that edge case rather than freezing the whole vault.

### Proof of Concept
1. A vault (e.g. `v0-vault-stx`) is initialized with `assets = u0`, `total-borrowed = u0`, `principal-scaled = u0`, and governance sets `fee-reserve` to a high value (up to `BPS`, i.e. 100%) as seen in the data var default of `u0` that governance/proposals can update. [4](#0-3) 
2. A borrower calls `system-borrow`, which calls `accrue` first (harmless while `reserve-inc == u0` since no debt exists yet) then sets `principal-scaled`/`total-borrowed`. [5](#0-4) 
3. On the next call that triggers `accrue` (e.g. a subsequent `deposit`, `redeem`, `system-borrow`, or `system-repay`), interest has accrued such that `debt-delta > 0`; with `fee-reserve` near `BPS`, `reserve-inc` approaches the full accrued interest amount, and if `current-assets` is `u0` and the accrued `interest` exactly equals `reserve-inc`, `total-assets-preview() - reserve-inc == u0`.
4. `mul-div-down reserve-inc (total-supply) u0` triggers a Clarity division-by-zero abort, reverting the whole transaction and leaving `index`/`lindex`/`assets`/`total-borrowed` unchanged.
5. Every future call to `deposit`, `redeem`, `system-borrow`, `system-repay` recomputes the identical inputs via `accrue` and reverts identically, permanently freezing all funds already deposited in that vault.

I was not able to fully verify, within the remaining tool budget, the exact governance/proposal mechanism and bounds for setting `fee-reserve` (e.g., whether it is capped below `BPS`), nor did I locate the precise numeric conditions in production deployment that would make `total-assets-preview() == reserve-inc` reachable in practice. This uncertainty affects the *likelihood* assessment but not the structural validity of the unguarded division itself, which is present verbatim in all six vault contracts.
