### Title
Sandwichable spot-price AMM quote with fixed 5% slippage in module-originated gas-swap execution - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
The Unitas bug is a price-feed timing gap: an attacker sandwiches a public oracle update transaction with two swaps at the stale/new price to extract value. Push Chain has a structurally similar pattern in the module-originated gas-swap flows: instead of a separate price feed, the "price" the protocol trusts for a swap is a live spot quote pulled from an on-chain Uniswap V3 `QuoterV2` pool (`GetSwapQuote`), and the only protection against price deviation is a fixed 5% slippage floor computed from that very same (attacker-influenceable) quote, in the same block.

### Finding Description
In `ExecuteInboundGas` [1](#0-0) , the keeper fetches a swap quote via `GetSwapQuote` against the on-chain WPC/PRC20 pool and then computes `minPCOut = quote * 95 / 100` before immediately calling `CallPRC20DepositAutoSwap` with that `minPCOut`. The identical pattern is used for the gas-fee refund path in `applyGasRefund` / `getSwapQuoteForRefund` [2](#0-1) .

Because `minPCOut` is derived from the *same* spot quote that the actual swap will execute against, this "slippage protection" only bounds movement between the quote call and the swap call — both of which happen back-to-back inside one keeper function during one EVM state. It does **not** protect against the pool's spot price itself being pushed away from its fair value by a large swap executed shortly beforehand (in the same or an adjacent block), the way a TWAP-based oracle would. An attacker who swaps a large amount into/out of the WPC pool immediately before a gas-inbound execution or gas-refund execution lands can shift the spot price by more than 5%, causing the module's swap to execute at the manipulated rate and mint/refund an amount that reflects the distorted price rather than the fair market price, then reverse their manipulation afterward to capture the difference — the same "manipulate-then-trade-then-restore" shape as the Unitas sandwich, just against an AMM spot quote instead of a mempool-visible admin price update.

The e2e test configuration explicitly acknowledges this fragility, warning that repeated tests could "drain the tiny WPC/pSOL AMM pool" [3](#0-2) , indicating the pool is thin and spot-price-sensitive in practice.

### Impact Explanation
If exploitable, an attacker could extract value from the gas-abstraction swap (`ExecuteInboundGas`) or the excess-gas-refund swap (`applyGasRefund`) by manipulating the WPC pool's spot price around the moment the module executes its `DerivedEVMCall` swap, causing the protocol to over- or under-value the PRC20 gas token relative to WPC. This corrupts the PRC20↔native accounting for the deposit/refund path (mis-minted PC amounts), a fund-safety invariant explicitly in scope.

### Likelihood Explanation
Likelihood is materially lower than the Unitas original because: (1) the quote and swap are fetched and executed atomically inside a single keeper call rather than being separated by a publicly-broadcast, delayed oracle-update transaction; (2) the timing of `ExecuteInboundGas`/`applyGasRefund` execution is driven by UV vote finalization and CometBFT block scheduling, not directly by attacker-chosen mempool placement, so precisely sandwiching a specific block is harder than on an EVM chain with public mempool ordering; (3) a 5% band does provide some cushion. However, likelihood is non-trivial for low-liquidity WPC pools (as acknowledged in the e2e setup) where a modestly sized swap can move spot price by more than 5%.

### Recommendation
Do not derive slippage protection from the same instantaneous spot quote that will be consumed by the swap. Use a TWAP-based quote (or a governance/admin-configured reference price with bounded deviation checks) for `minPCOut`, and/or clamp deposit/refund swap sizes relative to available pool liquidity so a single attacker-sized trade cannot move the effective execution price beyond a safe bound.

### Proof of Concept
Conceptual, not confirmed against live pool depth/config:
1. Attacker observes (or predicts) that their own inbound gas deposit will soon be processed by `ExecuteInboundGas`, or that an outbound they control will soon trigger `applyGasRefund`.
2. Immediately before the module's `DerivedEVMCall` swap executes, attacker submits a large swap against the same WPC/PRC20 Uniswap V3 pool, moving the spot price.
3. `GetSwapQuote` returns the distorted price; `minPCOut = quote * 0.95` is computed from this distorted quote, so it does not protect against the pre-existing manipulation.
4. `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas` executes at the distorted price, minting/refunding PC to the attacker's UEA/recipient at a rate favorable to the attacker.
5. Attacker reverses their manipulating swap, restoring the pool and pocketing the difference.

Note: I could not verify actual WPC pool liquidity depth, block-timing predictability of `ExecuteInboundGas`/`applyGasRefund` execution relative to attacker-submitted transactions, or whether any additional pool-level protections (e.g., minimum liquidity guards) exist elsewhere in the EVM contracts, since those Solidity contracts are outside the indexed Go codebase. This uncertainty should be resolved with a live/staging test against the actual pool parameters before treating this as a confirmed exploit.

// getSwapQuoteForRefund fetches a Uniswap quote for the gas token refund swap.
func (k Keeper) getSwapQuoteForRefund(ctx sdk.Context, gasToken common.Address, fee *big.Int, amount *big.Int) (*big.Int, error) {
	quoterAddr, err := k.GetUniversalCoreQuoterAddress(ctx)
	if err != nil {
		return nil, err
	}
	wpcAddr, err := k.GetUniversalCoreWPCAddress(ctx)
	if err != nil {
		return nil, err
	}
	return k.GetSwapQuote(ctx, quoterAddr, gasToken, wpcAddr, fee, amount)
