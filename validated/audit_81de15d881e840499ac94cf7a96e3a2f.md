**Reasoning:** The premise assumes `ENABLE_FUNCTION_VALUES` (and thus `enable_depth_checks`) can be "on" for one node and "off" for another node processing the *same* transaction/block, causing divergent abort/`StateValue` outcomes. That premise is false in this codebase.

`enable_depth_checks` in `aptos_prod_vm_config` is derived from `features.is_enabled(FeatureFlag::ENABLE_FUNCTION_VALUES)`, where `features: &Features` is an **on-chain config** read from committed ledger state (the `Features` resource), not a node-local or per-process setting. [1](#0-0) 

Because `Features` is part of consensus-committed state, every validator executing a given block reads the identical `Features` resource at the identical version, so `enable_depth_checks` (and every other feature-gated field in `VMConfig`) is deterministically the same for all validators processing that block. [2](#0-1) 

The only way `enable_depth_checks` differs is across a governance-driven feature-flag *upgrade* (activating `ENABLE_FUNCTION_VALUES` via on-chain governance), which changes behavior from one version onward for *all* validators simultaneously — this is the intended, versioned hard-fork mechanism, not an unprivileged-input path. The `assert_eq!` at the end of `aptos_prod_vm_config` is a developer sanity check tying the constant `DEFAULT_MAX_VM_VALUE_NESTED_DEPTH` to the config field, not a security boundary. [3](#0-2) 

There is no code path where an unprivileged transaction can cause two honest validators, both executing against the same committed on-chain `Features` state at the same version, to compute different `enable_depth_checks` values or different `VMConfig`s for the same transaction. This scenario therefore does not meet the "unprivileged input corrupts committed state / creates hard-fork-only divergence" bar — any divergence here is fully explained by an intentional, governance-gated protocol upgrade, which is out of scope per the review rules (trusted/privileged governance action).
