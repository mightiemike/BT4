## Finding: Local Analog Identified

Tracing the "callable-but-unimplemented integrity check" bug class to Aptos led to a documented, self-acknowledged gap in the executor's proof/output-integrity comparator — not a `todo!()` panic, but a *missing check* with the same effect: an authenticated field is silently excluded from the verification a downstream trust boundary relies on.

### Title
`ensure_match_transaction_info` omits `state_checkpoint_hash`/`hot_state_checkpoint_hash` verification, allowing divergent state roots to pass replay/backup verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to confirm that a locally re-executed transaction's output (status, gas, write-set hash, event root) matches an externally supplied, untrusted `TransactionInfo` (e.g., from a backup, state-sync chunk, or replay-verify tool). The function's own comment admits it does not check `state_checkpoint_hash` / `hot_state_checkpoint_hash` (or `position_state_checkpoint_hash`), meaning the state root itself is never authenticated at this call site. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` checks execution status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly skips the checkpoint hashes: [2](#0-1) 

This function is the integrity gate used by `ChunkExecutor::verify_execution` when replaying/verifying a chunk (e.g., during backup restore verification or `db-tool replay-on-archive`): the VM re-executes the transactions locally and the resulting `TransactionOutput`s are checked against the `transaction_infos` supplied alongside the chunk (which come from a potentially untrusted source such as a backup file or state-sync peer) before the chunk is accepted. [3](#0-2) 

Because the comparator never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`, a supplied `TransactionInfo` whose state-checkpoint hash does not correspond to the actually computed state (while status/gas/write-set/event hashes are kept consistent, which is feasible since these are independently derivable from the write set/events) will still pass `ensure_match_transaction_info`. The comment in the code names this exact scenario:

> "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [4](#0-3) 

### Impact Explanation
This breaks the state-root binding invariant required for restore/replay verification: an accumulator built from mismatched `TransactionInfo.state_checkpoint_hash` values can be accepted as a "verified" match against local VM execution even though the two state roots diverge. Any tooling or node relying on `verify_execution`/`ensure_match_transaction_info` to certify that a restored/replayed ledger's state root is correct can silently accept a corrupted or forked state checkpoint hash, undermining confidence in backup verification and replay-based auditing of committed state.

### Likelihood Explanation
The gap is deterministic and code-confirmed (not speculative): the check is provably absent from the function body, and the authors' own TODO comment documents the exact failure mode. Exploitability depends on being able to supply a `TransactionInfo`/write-set/output combination with correct write-set and event hashes but a divergent checkpoint hash, which is plausible for anyone controlling the input to a replay/restore/backup-verification pipeline (untrusted backup source or state-sync chunk data feeding `ChunkExecutor::verify_execution`).

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (once enabled) `position_state_checkpoint_hash` between the locally computed output/state and `txn_info`, as the existing comment itself recommends before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Not independently executed; based on static code review, a PoC would: (1) execute a chunk of transactions to obtain correct write-set/event hashes, (2) build `TransactionInfo`s with correct `state_change_hash`/`event_root_hash`/`gas_used`/`status` but an arbitrary/incorrect `state_checkpoint_hash`, (3) feed this into `ChunkExecutor::verify_execution`, and observe that `ensure_match_transaction_info` returns `Ok(())` despite the state checkpoint mismatch.

**Note on completeness**: I was unable to retrieve the full body of `execution/executor/src/chunk_executor/mod.rs` in this session (tool output was truncated/empty on the final read) to confirm whether an independent, redundant state-checkpoint-hash check exists elsewhere in the chunk-replay commit path that would fully mitigate this gap. The finding rests on the explicit TODO/comment in `ensure_match_transaction_info` itself, which is strong first-party evidence of the gap, but a full audit of `chunk_executor/mod.rs`'s complete commit path is recommended to confirm there is no compensating control.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
