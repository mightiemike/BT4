The critical evidence: `PendingOutbounds.Remove` only happens when validators reach `PASSED` consensus on an observation, and the README explicitly states **"Ballot expiry does NOT remove the entry"** and there is **"no safe automatic resolution"** for stuck outbounds — resolution is "governance-driven, not chain-driven." ### Title
Zero/missing Chain Meta gas price permanently freezes user funds in outbound flow - (File: `x/uexecutor/keeper/chain_meta.go`, `universalClient/chains/evm/tx_builder.go`)

### Summary
`ChainMeta.gas_price` (the Push Chain analog of a Chainlink price feed) can legitimately be zero or stale-gapped for a destination chain — e.g., immediately after an admin adds a new `ChainConfig` (before 3 fresh UV votes bootstrap the oracle per `chainMetaMinVotesForFirstWrite`), or after `PruneValidatorVotes` empties `ChainMetas` for a chain whose only voters left the validator set. `x/uexecutor/keeper/gas_fee.go`'s `GetOutboundTxGasAndFees` reads `gasPriceByChainNamespace` from the `UniversalCore` EVM contract, and this feeds `OutboundTx.GasPrice` in the `UniversalTxOutboundEvent` emitted at outbound creation. Any ordinary user whose payload triggers an outbound to such a chain gets an outbound record with `GasPrice = "0"`. Downstream, `universalClient/chains/evm/tx_builder.go`'s `GetOutboundSigningRequest` (lines 98-106) explicitly refuses to build/sign a transaction when `gasPrice.Sign() == 0`, returning `"gas price is zero or missing in outbound event"`. This mirrors the Chainlink report exactly: a legitimate gap in the on-chain price/meta oracle causes the settlement-equivalent function (outbound signing) to be unable to proceed.

### Finding Description
Unlike the Chainlink `settle()` case (a hard revert), here the failure is silent and permanent: the TSS coordinator/session manager can never produce a signing request for the outbound because every validator's local `verifyOutboundSigningRequest` call (`universalClient/tss/sessionmanager/sessionmanager.go` ~line 956) independently calls the same `GetOutboundSigningRequest`, which fails identically for everyone (deterministic zero gas price), so the DKLS signing session never completes. Per `x/uexecutor/README.md` (lines 262-282), `PendingOutbounds` entries are "removed ONLY when validators reach consensus" via `OutboundObservation`, and explicitly "ballot expiry does NOT remove the entry" — there is "no safe automatic resolution... resolution is governance-driven, not chain-driven." Because the outbound is never broadcast, no `OutboundObservation` (success or failure) can ever be voted, so the entry can never terminate through the normal path, and the bridged PRC20/native funds already debited/locked as part of that outbound remain stuck indefinitely with no automated revert or refund route.

### Impact Explanation
This matches the "Allowed Impact Gate" category of permanent freezing of user-controlled funds via an unprivileged, ordinary crosschain flow (deposit/payload targeting a chain with a gas-price gap), with honest validators and honest nodes. No malicious validator or admin action is required — only a timing/registry gap in the reserve-less gas-price oracle.

### Likelihood Explanation
Moderate: requires targeting a chain whose `ChainMeta` has zero fresh votes at the moment `getOutboundTxGasAndFees` is called on-chain — realistic immediately after a new chain is registered (before the 3-vote bootstrap quorum in `chainMetaMinVotesForFirstWrite` is reached) or after validator churn empties `PruneValidatorVotes` for a low-activity chain. An attacker/user does not need special privilege; simply directing a payload to such a chain during the gap window suffices.

### Recommendation
Add a reserve/fallback behavior analogous to the report's recommendation: (1) block/queue outbound creation in `x/uexecutor` (reject at `getOutboundTxGasAndFees`/outbound-creation time) rather than emitting an `OutboundTx` with `GasPrice = "0"` that can never be signed; and/or (2) allow `PendingOutbounds` to be resolved via an explicit escape-hatch/refund path (as already planned for `ExpiredInbounds`) when the destination chain's gas price has never been populated, so funds are not permanently stuck without any on-chain terminal state.

### Proof of Concept
1. Admin registers a new `ChainConfig` for chain X via `MsgAddChainConfig` (or an existing chain's UV signer set is pruned via `PruneValidatorVotes` down to zero entries).
2. Before 3 UVs submit fresh `MsgVoteChainMeta` votes for chain X (bootstrap gate in `VoteChainMeta`, `chain_meta.go` lines 132-143), `ChainMetas[X]` has no entry, so `UniversalCore.gasPriceByChainNamespace(X)` returns 0.
3. A normal user submits an inbound with a `PAYLOAD`/`FUNDS_AND_PAYLOAD` intent that triggers a Push-Chain-side outbound to chain X. `GetOutboundTxGasAndFees` returns `gasPrice = 0`, producing `OutboundTx{GasPrice: "0", ...}` and a `PendingOutbounds` entry.
4. Every Universal Validator's coordinator/session-manager calls `GetOutboundSigningRequest`, which returns `"gas price is zero or missing in outbound event"` for all of them — the DKLS session can never reach `SIGNED`.
5. Per the documented lifecycle, the `PendingOutbounds` entry is never removed (no ballot vote ever occurs since no tx is ever broadcast for validators to observe), and the user's bridged funds tied to that outbound remain frozen indefinitely. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

### `PendingOutbounds`

- **Created** by chain code at outbound creation in `create_outbound.go` —
  BEFORE any validator vote. The chain knows the outbound exists because it
  generated the destination-chain transaction itself; validators are tasked
  with observing whether/how it landed.
- **Keyed** by deterministic chain-derived `outbound_id`.
- **Variant-aware:** validator votes append `OutboundObservationVariant`s as
  they arrive (`RecordOutboundVote` inside `VoteOutbound`). Multiple variants
  per outbound indicate validator divergence on the destination-chain
  observation (different `success`/`tx_hash`/`error_msg`/`gas_fee_used`).
- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.
