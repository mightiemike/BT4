### Title
Stale `last-update` timestamp in `accrue` when index is unchanged skews future interest accrual - ([File: mainnet/contracts/vault/v0-vault-stx.clar] and identical logic in v0-vault-sbtc.clar, v0-vault-ststx.clar, v0-vault-ststxbtc.clar, v0-vault-usdc.clar, v0-vault-usdh.clar)

### Summary
The `accrue` function in all six mainnet vault contracts only updates the `last-update` timestamp when the computed borrow index or liquidity index actually changes. If a call to `accrue` produces `next == idx` and `nliq == lindex` (e.g. because the interest rate resolved by `interpolate-rate` is `u0` at the prevailing utilization, or `calc-multiplier-delta` rounds down to no growth), `last-update` is left untouched even though real time has elapsed. A subsequent `accrue` call then computes `time-delta` as `stacks-block-time` minus this stale, older `last-update`, causing the elapsed time window to silently include the earlier idle period. This is the same bug class as the reported `RAACMinter.tick()` issue: a clock/checkpoint value is only advanced conditionally on the presence of a nonzero effect, letting elapsed time compound across calls and produce disproportionate output on the next invocation.

### Finding Description
`accrue` computes the next borrow/liquidity index from the interest rate and the time elapsed since `last-update`: [1](#0-0) 

The multiplier and resulting `next` index depend directly on `time-delta = stacks-block-time - last-update`.

In `accrue`, `last-update` is only advanced if the index or liquidity index actually changed: [2](#0-1) 

If `next` equals `idx` and `nliq` equals `lindex` (which happens whenever `interest-rate`, driven by `interpolate-rate` over the current `utilization`, evaluates to `u0`, or when the multiplier rounds to `INDEX-PRECISION` with no net change), the `(var-set last-update stacks-block-time)` branch is skipped. `last-update` remains at its old value while blocks/time continue to pass.

When utilization later shifts (via `system-borrow`, `system-repay`, deposits, or withdrawals) so that `interest-rate` becomes positive, the next `accrue` call computes `time-delta` against the stale `last-update`, effectively backdating the interest-accrual window to include the entire idle period during which the rate was zero. This inflates `debt-delta`, `reserve-inc`, and the treasury-lp mint amount computed in the same call: [3](#0-2) 

and, symmetrically, inflates the liquidity index that determines depositors' redeemable value — since both `next-index` and `next-liquidity-index` share the identical `time-delta` computed from the same stale `last-update`: [4](#0-3) 

This mirrors the reported analog exactly: a value (`lastUpdateBlock` / `last-update`) is bound at a checkpoint, an event occurs (`emissionRate` returns to positive / `interest-rate` returns to positive) without invalidating the stale checkpoint, and the later use (`tick()` / `accrue()`) computes an elapsed-time-based amount using the wrong (too-old) baseline, producing disproportionately large minted/accrued amounts.

### Impact Explanation
Because every `system-borrow`/`system-repay`/deposit/withdraw call in the vault first invokes `accrue` (see `system-borrow` calling `(try! (accrue))`), the inflated `debt-delta` and treasury-lp mint directly and immediately mis-mint LP shares to `.dao-treasury`, and inflate the borrow index used to compute every borrower's outstanding debt and every depositor's redeemable share value going forward. This causes incorrect distribution of protocol yield (treasury fee share) and mis-priced index values affecting unclaimed yield for lenders/borrowers — falling under "theft of unclaimed yield" / "temporary freezing of funds" for depositors whose redemption value is miscalculated by the corrupted index.

### Likelihood Explanation
This requires the vault's `interest-rate` (derived from `utilization` via `interpolate-rate` over the configured rate curve `points-ir`) to actually be `u0` for at least one accrual cycle, which occurs naturally at zero or near-zero utilization (e.g. right after vault deployment, or after a period where all debt is repaid) and is a routine operating condition rather than an attacker-crafted edge case, so likelihood is Medium.

### Recommendation
Update `last-update` to `stacks-block-time` unconditionally on every non-paused `accrue` call, regardless of whether `idx`/`lindex` actually changed, mirroring the report's fix of always advancing `lastUpdateBlock` in `tick()`:
```clarity
(var-set last-update stacks-block-time)
```
should run outside the `is-eq` guard so that `time-delta` in the next call always reflects only the time since the last accrual attempt, not since the last *effective* index change.

### Proof of Concept
1. Vault utilization drops to a level where `interpolate-rate` (over `points-ir`) yields `rate = u0` (e.g., all debt repaid).
2. A user calls `accrue` (directly, or indirectly via a deposit/redeem). `next-index`/`next-liquidity-index` compute `multiplier = INDEX-PRECISION` (no growth) since `rate = 0`, so `next == idx` and `nliq == lindex`; the `is-eq` guard in `accrue` prevents `last-update` from being set, even though `stacks-block-time` has advanced.
3. Time passes (many blocks/seconds) while utilization remains at 0% and rate stays 0; each additional `accrue` call likewise skips updating `last-update`.
4. A new borrow occurs (`system-borrow`), which calls `accrue` internally; utilization jumps above 0, so `interest-rate` becomes positive.
5. `next-index`/`next-liquidity-index` compute `time-delta = stacks-block-time - last-update` using the *stale* `last-update` from step 2, spanning the entire idle low-utilization period, not just the time since the last `accrue` invocation.
6. The resulting `debt-delta`, `reserve-inc`, and treasury-lp mint amount, along with the jump in `next`/`nliq`, are computed as if the positive rate had applied over the whole stale interval, producing an inflated one-time index jump and improper treasury LP mint.

(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta rate time-delta true))))
          (calc-index-next idx multiplier)))))

(define-private (next-liquidity-index)
  (let ((states (var-get pause-states))
        (lidx (var-get lindex)))
    (if (get accrue states)
        lidx
        (let (
            (rate (interest-rate))
            (liquidity-rate (calc-liquidity-rate rate (utilization) (var-get fee-reserve)))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta liquidity-rate time-delta false))))
          (calc-index-next lidx multiplier)))))
