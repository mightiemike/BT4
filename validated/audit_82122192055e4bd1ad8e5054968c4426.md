The premise doesn't hold up under review. The `MoveStructType` impl for `TokenDeposit` hardcodes `MODULE_NAME = "token"` and `STRUCT_NAME = "TokenDeposit"`, but `TokenDeposit::struct_tag()` also binds to `TOKEN_ADDRESS` (`0x3`) via `TOKEN_DEPOSIT_TYPE` [1](#0-0) , giving a fully-qualified `StructTag{address, module, name}` triple. This matches the semantics of `MoveStructType::struct_tag()` in `move-core-types`, which combines `ADDRESS`, `MODULE_NAME`, and `STRUCT_NAME` [2](#0-1) .

This type tag is used purely as a dispatch key inside `EventV2TranslationEngine`, a `HashMap<TypeTag, Box<dyn EventV2Translator>>` used by the storage indexer to translate V2 events into legacy V1 event format for API/indexing purposes [3](#0-2) . Since `TOKEN_ADDRESS` (0x3) is the fixed, hardcoded address of the real on-chain `aptos_token::token` module, only genuine `TokenDeposit` events emitted by that specific bytecode at that address will match this dispatch key — an unprivileged user cannot forge an event with this exact `StructTag` to hijack a different translator or corrupt dispatch, since event `type_tag()` is set by the VM based on the actual emitting module, not attacker-supplied data.

Moreover, this translation engine operates on the internal indexer DB (`aptos_db_indexer_schemas`), a secondary read-side service, not the executor-to-storage commit path, accumulator/JMT proof construction, or consensus-critical write-set handling. It doesn't touch `WriteSet`, `TransactionInfo`, state proofs, or authenticated API root/version binding — it only reformats already-committed event data for legacy API compatibility [4](#0-3) . There is no path from unprivileged transaction/API/bytecode input through this code that corrupts committed state, proof material, or authenticated response binding.

            let key = *object_resource.opt_in_events().key();

            sequence_number,
            OPT_IN_TRANSFER_EVENT_TYPE.clone(),
            bcs::to_bytes(&opt_in_transfer_event)?,
        )?)
    }
