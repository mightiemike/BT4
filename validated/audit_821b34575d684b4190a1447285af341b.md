### Title
Unvalidated bucket-index and pointer fields in stateless state-diff decompression cause out-of-bounds panic (DoS) - (File: crates/starknet_os/src/hints/hint_implementation/stateless_compression/utils.rs)

### Summary
`decompress()` in `crates/starknet_os/src/hints/hint_implementation/stateless_compression/utils.rs` parses a compressed DA (data-availability) segment by reading header fields (`bucket_lengths`, `n_repeating_values`, `repeating_value_pointers`, `bucket_index_per_elm`) directly out of the untrusted `compressed` felt stream and uses them, unvalidated, as vector indices. This mirrors CVE-2017-5841's root cause: a length/offset field taken from parsed input data is trusted and used to index into a buffer without checking it is within bounds.

### Finding Description
In `decompress()`: [1](#0-0) 

- `repeating_value_pointers` (line 587-591) are read straight from the compressed stream as `usize` values bounded only by `unique_values.len()` supplied as the `elm_bound` to `unpack_felts_to`, but `unpack_felts_to` (lines 513-541) computes remainders mod `elm_bound` — it does not itself guarantee the decoded values are `< unique_values.len()` if `elm_bound` accounting or a malformed/adversarial felt stream produces inconsistent bit-packing.
- `unique_values[*ptr]` at line 594 indexes directly with the unchecked pointer.
- `bucket_index_per_elm` (line 599-600) is bounded to `TOTAL_N_BUCKETS`, but `bucket_offset_trackers[bucket_index]` (line 611) and `all_values[*offset]` (line 612) are indexed without validating `offset < all_values.len()`, so a header claiming bucket lengths that don't sum consistently with the actual number of unique/repeating values produced causes an out-of-bounds `Vec` index, which panics in Rust (a hard process abort) rather than a silent heap read as in the C-based GStreamer bug, but the underlying root cause — untrusted length/offset fields consumed without range validation before being used to index a buffer — is identical in class.

This function is exercised when parsing an OS-output DA segment via `PartialOsStateDiff::try_from_output_iter` / `FullOsStateDiff::try_from_output_iter`, which invoke `decompress(iter)`: [2](#0-1) 

### Impact Explanation
A panic in this code path aborts the process performing the parse (e.g., a node re-executing/verifying the Starknet OS output or reconstructing the state diff from a DA segment, such as `starknet_os_flow_tests`/re-execution/proof-verification tooling using `PartialCommitmentOsStateDiff`/`FullCommitmentOsStateDiff`). This is a liveness/DoS impact (a network unable to confirm new transactions if this path is on the block-verification critical path) rather than memory corruption, since Rust performs bounds-checked panics instead of true OOB reads.

### Likelihood Explanation
Reachability is uncertain: `decompress()` is marked `#[allow(dead_code)]` in the source, indicating it is presently exercised primarily by tests (`crates/starknet_os/src/hints/hint_implementation/stateless_compression/tests.rs`, `state_diff_encryption/utils_test.rs`) and by `starknet_os_flow_tests`, and the DA segment it consumes is normally produced by the sequencer's own trusted `compress()` routine (in the paired Cairo implementation), not directly by an arbitrary transaction sender. I could not confirm a production code path where this Rust `decompress()` is invoked on a DA segment sourced from an untrusted L1 message, transaction, or declared class rather than the sequencer's/OS's own generated output. Given this uncertainty about a concretely reachable untrusted-input path satisfying the "single submitted transaction / contract call / declared class / L1 message" requirement, and because the only demonstrated triggers are test-only or self-generated data, I cannot confirm this rises to a valid, reachable analog under the strict scope rules (which exclude malicious-proposer/malicious-node paths, and require the vulnerability be reachable by an unprivileged sender).

### Recommendation
Regardless of exact reachability, harden `decompress()` to reject malformed headers before indexing: validate that every `repeating_value_pointers` entry is `< unique_values.len()`, validate that `bucket_index_per_elm` entries index only into non-empty buckets, and validate that the sum of `all_bucket_lengths` matches `all_values.len()` and `data_len`, returning a `Result` error instead of panicking on out-of-range indices.
