### Title
Rescue-funds outbound creation bypasses the destination-chain `IsChainOutboundEnabled` safeguard - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
Push Chain enforces a "chain must be outbound-enabled" invariant before any `OutboundTx` is created for a destination chain, implemented in `BuildOutboundsFromReceipt`. `AttachRescueOutboundFromReceipt`, the dedicated recovery path used when funds are stuck on a source chain, creates and attaches a `RESCUE_FUNDS` outbound to that same source chain without ever calling this check, mirroring the reported bug class where a "special-case" recovery path is not gated by the same safeguard enforced on the normal path.

### Finding Description
`BuildOutboundsFromReceipt` explicitly gates outbound creation on the registry's per-chain flag before building any `OutboundTx`: [1](#0-0) 

This is the module's canonical safeguard for "don't send funds to/through a chain the admin has disabled" (used, e.g., when a chain is deprecated, paused for a security incident, or being decommissioned) — see `IsChainOutboundEnabled` in `x/uregistry/keeper/keeper.go`. [2](#0-1) 

However, `AttachRescueOutboundFromReceipt` — the alternate, dedicated path invoked when a CEA deposit failed or an auto-revert outbound itself reverted — builds and attaches an `OutboundTx` whose `DestinationChain` is `originalUtx.InboundTx.SourceChain` with **no equivalent `IsChainOutboundEnabled` (or `IsChainInboundEnabled`) check anywhere in the function**: [3](#0-2) 

The function validates several other invariants (UTX existence, inbound presence, CEA-deposit-failed / auto-revert-reverted eligibility, no duplicate active rescue), but never re-checks whether the source/destination chain is still an outbound-enabled chain in `uregistry`. This is exactly analogous to the referenced report: a dedicated "recovery/edge-case" code path (bad-debt liquidation there, rescue-funds here) omits a safeguard that the "normal" path (regular liquidation there, `BuildOutboundsFromReceipt` here) enforces, letting the disabled/deprecated state be routed around.

### Impact Explanation
If a chain is disabled for outbound (e.g., because it was deprecated, its gateway/vault contract compromised, or TSS keys for it are being rotated/retired), the `x/uregistry` admin flips `IsOutboundEnabled = false` expecting no further outbound transactions — including PRC20 releases — to be created or signed for that chain. The rescue path silently ignores this and still creates a `PENDING` `RESCUE_FUNDS` outbound, which is then picked up by `PendingOutbounds`, signed via TSS, and broadcast by Universal Validators just like any other outbound. This can cause funds to be released on a chain the protocol has explicitly decided to stop servicing (mirrors the wrong-asset/misrouted-value class in the Registry/Accounting invariant), and undermines the operational safety mechanism that `IsChainOutboundEnabled` is meant to provide across every outbound-creation code path.

### Likelihood Explanation
Requires the chain to first be disabled for outbound by the admin (a legitimate, expected operational event, e.g. deprecation or incident response) *and* an eligible stuck-funds condition to exist (CEA deposit failure, or auto-revert reverted) — both realistic, low-privilege-triggerable conditions once the precondition (chain disabled) occurs. No validator or admin collusion is needed to exploit it; only the standard rescue trigger flow (a `rescueFunds` call on the gateway emitting `RescueFundsOnSourceChain`) is required, matching the "requires a specific event" medium-likelihood characterization of the original report.

### Recommendation
Add the same `IsChainOutboundEnabled` (and/or `IsChainInboundEnabled`, since `SourceChain` here is the destination for the rescue outbound) check used in `BuildOutboundsFromReceipt` to `AttachRescueOutboundFromReceipt` before constructing/attaching the `RESCUE_FUNDS` outbound, returning an error (and leaving the UTX untouched) if the chain is disabled — consistent with how every other outbound-creation path enforces this invariant.

### Proof of Concept
1. Register chain `eip155:X` with `Enabled.IsOutboundEnabled = true`, create a CEA inbound whose PRC20 deposit fails (unregistered token, as in `setupRescueFundsTest`). [4](#0-3) 
2. Admin disables outbound for `eip155:X` via `MsgUpdateChainConfig` (`Enabled.IsOutboundEnabled = false`) — simulating chain deprecation/incident.
3. Trigger a `RescueFundsOnSourceChain` event (via the normal rescue flow) and call `AttachRescueOutboundFromReceipt`.
4. Observe that unlike a normal `FUNDS`/`FUNDS_AND_PAYLOAD` outbound (which would be rejected with `"outbound is disabled for chain %s"` by `BuildOutboundsFromReceipt`), the call succeeds and a `PENDING` `RESCUE_FUNDS` `OutboundTx` is attached to the UTX, entering `PendingOutbounds` and becoming eligible for TSS signing/broadcast despite the chain being disabled.

I was not able to fully trace whether `rescueFunds` on the EVM gateway contract itself has any additional destination-chain-disabled gating (that Solidity contract source is outside indexed scope), so if such a check exists purely on the EVM side it could partially mitigate this; a Devin session with full repository access would be needed to confirm the gateway contract logic.

// IsChainOutboundEnabled checks if outbound is enabled for a given chain
func (k Keeper) IsChainOutboundEnabled(ctx context.Context, chain string) (bool, error) {
	config, err := k.GetChainConfig(ctx, chain)
	if err != nil {
		if errors.Is(err, collections.ErrNotFound) {
			// chain not found
			return false, nil
		}
		return false, err
	}
	if config.Enabled == nil {
		return false, nil
	}
	return config.Enabled.IsOutboundEnabled, nil
}
