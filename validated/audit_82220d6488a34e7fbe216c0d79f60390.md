### Title
Integer-division precision loss in `MarketUtils.multiplyAndDivide` allows a maker's entire remaining order to be drained for zero payment in `MarketSellAssetActuator.matchSingleOrder` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The TRC10 order-book market (`MarketSellAssetActuator`) computes order fills using integer division via `MarketUtils.multiplyAndDivide`, which truncates (floors) fractional results to `0` just like the reported `_getExchangeRate` bug. In the "taker == maker" match branch, this zero result is never checked before tokens are transferred, letting an attacker consume a maker's full remaining order while paying it nothing.

### Finding Description
`MarketUtils.multiplyAndDivide` performs `floor(a*b/c)` [1](#0-0) , exactly the same rounding-to-zero integer-division pattern as the Sherlock report's `_getExchangeRate` (`(priceIn * 1e8) / priceOut`).

In `MarketSellAssetActuator.matchSingleOrder`, this function is used to compute how many buy tokens a matched party receives. Two of the three match branches ("taker < maker" and "taker > maker") explicitly guard against a `0` result and safely return unmatched tokens [2](#0-1) [3](#0-2) .

The "taker == maker" branch, however, has **no such guard**: [4](#0-3) 

Here `makerBuyTokenQuantityReceive` is recomputed via `multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`. If `makerBuyQuantity` is small relative to `makerSellQuantity` (a legitimately valid, unbounded price ratio — only checked for `> 0` and below `dynamicStore.getMarketQuantityLimit()` [5](#0-4) ), this division rounds down to `0` even though `makerSellRemainQuantity > 0`.

Since a taker fully controls their own `sellTokenQuantity`/`buyTokenQuantity` when creating a `MarketSellAssetContract`, an attacker can craft a taker order whose computed `takerBuyTokenQuantityRemain` (also via `multiplyAndDivide`) exactly equals a target maker's `sellTokenQuantityRemain`, forcing execution into the unguarded "==" branch. When `makerBuyTokenQuantityReceive` resolves to `0`:
- `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` — attacker receives the maker's entire remaining sell tokens.
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0` — attacker's own tokens are not reduced.
- `addTrxOrToken(makerOrderCapsule, 0, ...)` — maker receives nothing in return.

The maker's order is then marked `INACTIVE` and removed [6](#0-5) , permanently losing the tokens with no compensation.

### Impact Explanation
This is a direct, unprivileged fund-drain: any account can place TRC10 sell orders on the on-chain market, so any user acting as taker can exploit extreme but valid maker price ratios to steal a maker's entire remaining order balance, receiving tokens for free. This mirrors the reported bug's impact class (settlement/accounting bypass leading to complete loss of counterparty funds), just realized in java-tron's native `Market*` actuators instead of a Solidity `AutomationMaster`.

### Likelihood Explanation
Reachable by any account without special privileges — it only requires: (1) `AllowMarketTransaction` enabled (already a live feature), (2) a maker order with a sufficiently skewed `sellTokenQuantity`/`buyTokenQuantity` ratio and a small remaining balance, and (3) an attacker crafting a taker order whose `sellTokenQuantity` makes `multiplyAndDivide` land exactly on `makerSellRemainQuantity`. No admin/committee action is needed beyond the market being enabled.

### Recommendation
Add the same zero-result guard used in the other two branches to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0` (or more generally, if the recomputed value doesn't correspond to a fair/non-zero settlement), reject the match or return the maker's remaining tokens instead of transferring them for free. Consider also bounding allowable price ratios (`sellTokenQuantity`/`buyTokenQuantity`) in `MarketSellAssetActuator.validate()` to prevent ratios that make `multiplyAndDivide` structurally prone to zero-rounding.

### Proof of Concept
1. Maker creates a sell order with `sellTokenQuantity = S`, `buyTokenQuantity = B` where `B << S` (e.g., `S = 10^15`, `B = 1`), and lets it partially fill down to a small `sellTokenQuantityRemain = r` (e.g., `r = 999,999,999,999`, still `< S`, so `floor(r*B/S) == 0`).
2. Attacker (taker) submits a `MarketSellAssetContract` with `sellTokenQuantity` chosen such that `takerBuyTokenQuantityRemain = multiplyAndDivide(takerSellRemainQuantity, S, B)` equals exactly `r`, forcing the "taker == maker" branch in `matchSingleOrder`.
3. `makerBuyTokenQuantityReceive = multiplyAndDivide(r, B, S) = floor(r*1/S) = 0`.
4. Execution proceeds: attacker receives `r` sell tokens from maker (`addTrxOrToken(takerOrderCapsule, r, ...)`), while `addTrxOrToken(makerOrderCapsule, 0, ...)` credits the maker nothing; attacker's own `sellTokenQuantityRemain` is unchanged since `takerSellTokenLeft = takerRemain - 0`.
5. Maker's order is closed (`INACTIVE`) having received zero compensation for `r` tokens — fund drain confirmed.
