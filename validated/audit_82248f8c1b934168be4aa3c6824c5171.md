### Title
Cost model / compute-unit metering does not charge for real ELF load, verification, and JIT-compilation time, allowing cheap-CU transactions to trigger disproportionate leader wall-clock cost - (File: program-runtime/src/loaded_programs.rs)

### Summary
`ProgramCacheEntry::new_internal` in `program-runtime/src/program_cache_entry.rs` performs `Executable::load`, `RequisiteVerifier::verify`, and `jit_compile` on the cold-load path exercised by `replenish_program_cache`/`load_program_with_pubkey`, and none of this wall-clock cost is reflected in the transaction's charged compute units. The cost model (`cost-model/src/cost_model.rs::get_estimated_execution_cost`) derives `programs_execution_cost` solely from the declared `compute_unit_limit`, independent of the size or freshness of the invoked program, so a transaction that sets a minimal `SetComputeUnitLimit` while invoking a large, never-before-cached program can force full ELF load/verify/JIT work far exceeding its charged CUs.

### Finding Description
The relevant call chain is:
`TransactionBatchProcessor::load_and_execute_sanitized_transactions` → `replenish_program_cache` (`svm/src/transaction_processor.rs:894-972`) → `load_program_with_pubkey` (`svm/src/program_loader.rs:99-193`) → `ProgramCacheEntry::new` → `ProgramCacheEntry::new_internal` (`program-runtime/src/program_cache_entry.rs:241-288`), which unconditionally performs: [1](#0-0) 

These operations are timed into `LoadProgramMetrics` (`load_elf_us`, `verify_code_us`, `jit_compile_us`) purely for observability, not for charging: [2](#0-1) 

Meanwhile, the cost model that gates block capacity (`CostTracker`/`CostModel`) computes `programs_execution_cost` exclusively from the declared `compute_unit_limit` (or per-instruction defaults), with no term for program size or cache-miss status: [3](#0-2) 

An attacker with a funded keypair can: (1) deploy N distinct BPF Loader Upgradeable programs sized near `MAX_PERMITTED_DATA_LENGTH`, none yet invoked in the current program-cache generation (e.g., deployed by a prior leader/slot and later evicted, or freshly deployed in a way that a subsequent leader must reload due to fork/rooting rules), and (2) submit N transactions, each invoking a distinct program with `ComputeBudgetInstruction::set_compute_unit_limit(200)`. Each such transaction forces `replenish_program_cache` to take the cold path through `new_internal`, incurring `load_elf`, `verify::<RequisiteVerifier>`, and `jit_compile` proportional to program size, while only charging ~200 CU (plus fixed builtin/loader CU overhead) against the leader's CU-based cost tracker.

Existing checks that partially bound (but do not eliminate) this:
- The program cache is a shared, cluster-wide LRU-like structure (`ProgramCache`) with `evict_using_random_selection`/`sort_and_unload` (`program-runtime/src/loaded_programs.rs:862-930`), so once a program is loaded by any thread/leader it stays cached until evicted, limiting *repeat* cold-loads of the *same* program.
- Cooperative loading (`replenish_program_cache`'s `loading_task_waiter`) ensures only one thread loads a given program concurrently, but does not reduce the aggregate cost of loading many *distinct* programs.
- Deploying large, distinct programs is not free: the program (data) account must be rent-exempt for its size, so an attacker deploying N programs near `MAX_PERMITTED_DATA_LENGTH` (~10 MiB) must lock up substantial lamports per program, which is an economic — not a metering — deterrent.
- No mechanism in `replenish_program_cache`, `deploy_program`, or the cost model charges a CU surcharge proportional to ELF size for the load/verify/JIT-compile steps specifically.

### Impact Explanation
This matches "Cost-model/CU-meter/lock accounting does not charge for real ELF load/verify/JIT-compile cost, exhausting block capacity" — a resource-exhaustion / liveness-degradation issue on the leader's block-production path, since CU-based block-cost accounting can be satisfied while real wall-clock processing time (bounded by the ~400ms slot budget) is consumed disproportionately by uncharged load/verify/JIT work. It does not cause loss of funds, consensus divergence, or a cluster-halting panic; the impact is scoped to leader liveness/performance degradation.

### Likelihood Explanation
Preconditions: a funded keypair capable of paying rent-exemption for N distinct near-max-size BPF Loader Upgradeable programs, and ordinary devnet/mainnet transaction submission — no privileged access needed. The attack is repeatable but bounded by the economic cost of renting large program-data accounts for each distinct "cold" program and by the shared, cluster-wide nature of the program cache (a program loaded once by any validator/leader for a given environment generation remains cached until evicted), which reduces the marginal benefit of repeating the attack against the same program set across many slots. Feasibility on a live cluster requires further empirical validation of net wall-clock-vs-CU divergence at scale, which is why this class of finding is inherently sensitive to deployment cost and cache-eviction dynamics.

### Recommendation
Introduce a compute or fee surcharge in the cost model (and/or actual metering in `new_internal`/`replenish_program_cache`) proportional to ELF size for cold-load operations — e.g., charge CUs based on `elf_bytes.len()` for `load_elf`, `verify`, and `jit_compile`, similar to how `loaded_accounts_data_size_cost` already scales with account bytes. Alternatively, bound the number of distinct cold program loads permitted per batch/block independent of declared CU limits, or require an explicit "load surcharge" instruction analogous to loaded-accounts-data-size limits.

### Proof of Concept
Bank/SVM integration test plan:
1. Deploy N (e.g., 20) distinct upgradeable BPF programs near `MAX_PERMITTED_DATA_LENGTH`, ensuring they are absent from the active `ProgramCache` generation (e.g., via `evict_using_random_selection` or a fresh environment).
2. Construct N transactions, each invoking one distinct program with `ComputeBudgetInstruction::set_compute_unit_limit(200)`.
3. Call `TransactionBatchProcessor::load_and_execute_sanitized_transactions` and capture `execute_timings.details.create_executor_load_elf_us`, `create_executor_verify_code_us`, `create_executor_jit_compile_us` (per `svm-timings/src/lib.rs` accumulators) alongside `CostModel::calculate_cost` sums for the batch.
4. Assert that summed `load_elf_us + verify_code_us + jit_compile_us` grows materially with total program bytes while summed `compute_unit_limit`/`programs_execution_cost` charged remains flat at `N * 200` (plus fixed loader overhead), demonstrating the absence of any per-tx surcharge scaling with program size.

    fn get_estimated_execution_cost(
        transaction: &impl TransactionMeta,
        feature_set: &FeatureSet,
    ) -> (u64, u64) {
        // if failed to process compute_budget instructions, the transaction will not be executed
        // by `bank`, therefore it should be considered as no execution cost by cost model.
        let (programs_execution_costs, loaded_accounts_data_size_cost) =
            match transaction.transaction_configuration(feature_set) {
                Ok(config) => (
                    u64::from(config.compute_unit_limit),
                    Self::calculate_loaded_accounts_data_size_cost(
                        config.loaded_accounts_data_size_limit,
                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }
