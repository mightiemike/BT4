Based on my investigation, I found a plausible analog in the `near-wallet-contract` runtime (the Ethereum-transaction-emulation contract that lets an eth-implicit account submit EVM-encoded transactions that get translated into native NEAR actions). However, I was not able to fully verify all downstream assumptions (e.g., the exact `assert_one_yocto` behavior of the specific NEP-141 implementation used in tests, and the full body of `validate_tx_value`) before running out of tool budget, so I flag this uncertainty explicitly.

### Title
Combining a nonzero Ethereum `value` field with ERC-20 transfer calldata causes an unconditionally-paid relayer fee to be spent on a transaction that is guaranteed to fail - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The wallet contract's `inner_rlp_execute`/`parse_rlp_tx_to_action` pipeline treats the Ethereum transaction's `value` field as extra NEAR deposit to attach to whatever native action is derived from the calldata, with no validation that `value == 0` when the calldata is recognized as an ERC-20 (`ft_transfer`) emulation. This mirrors the original report's root cause: an amount field (`ether`/`value`) is accepted independently of a mode selector (`_tokenAddress`/"is this an ERC-20 call"), and the two are never cross-validated, so the value is combined into a context where it cannot be honored.

### Finding Description
`eth_emulation::try_emulation` builds the `ft_transfer` `Action::FunctionCall` for an ERC-20 transfer with a hardcoded `yocto_near: 1` (the conventional 1-yoctoNear marker many NEP-141 contracts require via `assert_one_yocto`): [1](#0-0) 

Separately, in `internal::parse_rlp_tx_to_action`, regardless of which `TransactionKind`/`Action` was produced (native action, self-action, or ERC-20 emulation), the code unconditionally adds the Ethereum `value` field (converted to yoctoNear) on top of whatever `yocto_near` the action already carries: [2](#0-1) 

There is no check anywhere in `try_emulation` or `parse_rlp_tx_to_action` that `tx.value` is zero when the calldata is recognized as `ERC20_TRANSFER_SELECTOR` (or any other ERC-20 selector). Consequently, a transaction that has both a nonzero `value` and ERC-20 transfer calldata produces a `ft_transfer` call with deposit `1 + value*1_000_000` yoctoNear instead of exactly `1`, which will be rejected by any standard NEP-141 implementation enforcing `assert_one_yocto()`.

Before this action is even dispatched, `inner_rlp_execute` unconditionally pays the relayer's fee out of the wallet's own balance the moment the transaction is classified as `ERC20Transfer` with nonzero fee — this payment does not depend on whether the subsequent `ft_transfer` promise succeeds: [3](#0-2) 

The nonce is also incremented immediately for the `ERC20Transfer` branch (it is only deferred for the `EOABaseTokenTransfer{address_check: Some(_)}` case): [4](#0-3) 

So the sequence for a transaction with ERC-20 calldata + nonzero `value` is: (1) relayer fee is paid out of the wallet's NEAR balance, (2) the nonce is consumed, (3) the outgoing `ft_transfer` promise is created with a corrupted deposit and is guaranteed to fail against any standards-compliant NEP-141 token, (4) the intended token transfer never happens. The wallet's own deposit attached to the failed promise is refunded per the protocol's standard deposit-refund rules (`Receipt::new_balance_refund`, `refund_unspent_gas_and_deposits`) — [5](#0-4)  — but the relayer fee that was already transferred out is not refunded, and the user's nonce and intended action are consumed with no token transfer taking place.

### Impact Explanation
This is a value-loss bug reachable purely from a signer's own RLP-encoded transaction (no privileged relayer/validator role required): a caller who sets a nonzero `value` on an eth-emulated ERC-20 transfer (either by user tooling mistake or by a malicious/careless relayer constructing the RLP bytes to be signed) causes the wallet contract to pay out a relayer fee for a transaction that structurally cannot succeed, burning real $NEAR value from the wallet account for zero effect, while also consuming a nonce slot that could have been used for a legitimate transaction. This is a concrete, transaction-triggered unauthorized value movement (the fee payment) that provides no counter-value, matching the "value lost due to unvalidated combination of amount + mode fields" class from the source report.

### Likelihood Explanation
Reachability is straightforward: any account owning an eth-implicit wallet, or any relayer submitting `rlp_execute` on its behalf, can construct an RLP transaction with `to = <NEP-141 token address>`, ERC-20 `transfer` selector data, and a nonzero `value` field. No special privileges, no race condition, and no cooperation from other network participants are required. The main uncertainty is whether real deployments would ever legitimately produce such a transaction (well-behaved Ethereum tooling would never populate `value` for a non-payable ERC-20 `transfer()` call), which somewhat limits accidental occurrence, but a malicious relayer or a buggy dApp/SDK integration could trigger it deliberately or by mistake, and the contract does not defend against it.

### Recommendation
In `eth_emulation::try_emulation` (and any other Ethereum-standard emulation path that produces a native action with a fixed/expected `yocto_near`), validate that `tx.value` is zero before accepting the transaction as a valid ERC-20 (or other emulated-standard) call; if `tx.value != 0`, return a `UserError` (e.g., a new `UnexpectedValueForTokenCall` variant) instead of silently folding it into the outgoing deposit. Additionally, consider deferring/conditioning the relayer fee refund on successful validation of the derived action (or at least on the deposit being compatible with the target's expected calling convention) so that a malformed transaction cannot both consume nonce and drain a relayer fee while guaranteed to fail.

### Proof of Concept
1. Attacker/relayer builds an EIP-2930 transaction with `to = <address of NEP-141 token contract>`, `data = ERC20_TRANSFER_SELECTOR || abi.encode(recipient, amount)`, and `value = 1` (nonzero), plus a nonzero `gas_price`/`gas_limit` so `tx_fee` is nonzero (see fee computation) — [6](#0-5) .
2. Wallet owner signs this transaction (or is tricked into signing it by malicious tooling).
3. A relayer submits it via `rlp_execute`; `parse_rlp_tx_to_action` classifies it as `EthEmulationKind::ERC20Transfer` with the given `fee`.
4. `inner_rlp_execute` immediately transfers `fee` from the wallet's balance to the relayer/predecessor — [7](#0-6)  — and increments the nonce.
5. The resulting `ft_transfer` FunctionCall action carries deposit `1 + value*1_000_000` yoctoNear (via `try_into_near_action`) instead of exactly `1`.
6. The NEP-141 target's `ft_transfer` (standard `assert_one_yocto()` implementations) rejects the call, the cross-contract promise fails, and `rlp_execute_callback` reports failure; the deposit itself is protocol-refunded to the wallet, but the relayer fee already sent in step 4 is not recovered, and the nonce has been consumed for a transaction that accomplished nothing.
