### Title
Fork-dependent poison-microblock report causes `assert_eq!` panic in `inner_insert_matured_miner_reward` when two forks mature a shared ancestor tenure - (File: stackslib/src/chainstate/stacks/db/accounts.rs)

### Finding Description
The equality the code assumes is: `matured_reward(parent_block_id, child_block_id)` computed while processing fork A == `matured_reward(parent_block_id, child_block_id)` computed while processing fork B, for any shared ancestor tenure `(parent_block_id, child_block_id)`. `inner_insert_matured_miner_reward` explicitly documents and relies on this invariant ("the only time it's okay to re-insert the same reward is if there are two Stacks forks trying to store the same matured rewards for a common ancestor block") and enforces it with `assert_eq!(rw, reward, ...)` [1](#0-0) .

The reward value is produced by `calculate_miner_reward`, which branches on `poison_reporter_opt` [2](#0-1) . That option is populated by `get_poison_microblock_report`, which queries the *currently executing* Clarity/MARF state for a poison report at the maturing tenure's height [3](#0-2) . Because a `PoisonMicroblock` report can be mined into any descendant block after the fork point (not necessarily into the shared ancestor block itself), the Clarity DB state seen by `get_poison_microblock_report` is fork-specific: a node that has processed fork B's blocks (which include the report) will see `poison_reporter_opt = Some(..)`, while the same node processing fork A's blocks (which never included that transaction) will see `None`. This yields two different `MinerReward` values (`child_address`, `coinbase_reward`, `punished` all differ) for the identical `(parent_block_id, child_block_id)` pair, breaking the invariant the assert relies on.

`insert_matured_child_miner_reward`/`insert_matured_parent_miner_reward` call `inner_insert_matured_miner_reward` unconditionally from `advance_tip` for each processed tip [4](#0-3) . Nothing in `check_tenure_tx`, VRF/sortition validation, or MARF hashing constrains poison-microblock report visibility to be fork-independent — the report's effect is purely a function of which blocks (transactions) a given fork happened to include before the maturity window elapsed, which is by design chain-specific.

### Impact Explanation
When a node has ingested and processed blocks from both forks (normal behavior for a full node reconciling competing tips before fork-choice settles), calling `advance_tip` for the second fork triggers the `assert_eq!` panic in `inner_insert_matured_miner_reward`, aborting that node's block processor. This is a local liveness failure (node halt/DoS) for any honest node that observes both forks, rather than a network-wide invalid-state acceptance; it does not corrupt the MARF root or cause other honest nodes to compute different final balances once one fork is finally selected, but it does halt block processing on the affected node until manual restart/intervention, which functionally freezes that node's chain view.

### Likelihood Explanation
Preconditions: an unprivileged attacker needs only to (a) create/extend a minority fork off a common ancestor tenure, and (b) submit a `PoisonMicroblock` report transaction so it is mined into a block that lands on only one of the two forks before the shared tenure's reward matures (`MINER_REWARD_MATURITY` blocks later). No majority stake, signer control, or admin access is required — filing a poison report and extending a fork are both permitted unprivileged actions. The main uncertainty (not fully resolved from available context) is whether `PoisonMicroblock` transactions remain a reachable/valid transaction type for tenures processed under Nakamoto consensus, since microblocks are otherwise deprecated in Nakamoto; this affects the practical reachability of the exact call path described in Nakamoto's `advance_tip`, and should be verified against the current tx-validation rules for `PoisonMicroblock` before treating this as fully confirmed in the Nakamoto epoch.

### Recommendation
Make matured-reward reconciliation fork-tolerant instead of asserting equality: when a conflicting reward is detected for the same `(parent_block_id, child_block_id)` pair, resolve deterministically (e.g., always prefer "no poison" over "poison", or key the poison-report lookup by the ancestor tenure's own state rather than by the currently-processing fork's state) and log/skip instead of panicking. Alternatively, restrict poison-microblock report attribution to be computed once, from the state as of the maturing block itself (not from whichever fork is currently being advanced), so the result is provably fork-independent.

### Proof of Concept
1. Build a two-fork integration harness (`stackslib` test utilities) with a common ancestor tenure `T` (parent block `P`, child block `C`).
2. Extend fork A for `MINER_REWARD_MATURITY` blocks without any poison report.
3. Extend fork B similarly, but include a `PoisonMicroblock` transaction (referencing a genuine microblock fork under tenure `T`) in one of fork B's blocks before maturity.
4. On a single node/chainstate instance, call `NakamotoChainState::advance_tip` (or the equivalent append path) for fork A's matured tip, then for fork B's matured tip.
5. Assert: `get_matured_miner_payment(P, C)` should be identical for both calls (asserting `reward_on_fork_A == reward_on_fork_B`); observe instead that the second call triggers `assert_eq!(rw, reward, ...)` panic in `inner_insert_matured_miner_reward`, documenting the divergence and node halt.
