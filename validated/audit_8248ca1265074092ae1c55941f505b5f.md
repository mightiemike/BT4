Based on my analysis, I found a solid, reachable analog to the "unchecked SafeCall + fallback sweep" bug class in the `near-wallet-contract`'s deposit-refund flow.

### Title
Fire-and-forget deposit refund in `rlp_execute_callback` is not verified, permanently trapping an external caller's attached NEAR if the refund transfer itself fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Wallet Contract's `rlp_execute_callback` refunds an external caller's attached deposit by firing a brand-new, independent `Transfer` promise to `caller_deposit.account_id` whenever the inner cross-contract call fails [1](#0-0) . This is structurally the same pattern flagged in the external report: a critical payment is dispatched via a "send-and-forget" mechanism whose success is never checked, so if that payment itself fails, the funds are silently diverted away from the intended recipient with no on-chain accounting kept to recover them.

### Finding Description
`inner_rlp_execute` records the external caller's attached deposit in a `CallerDeposit { account_id, yocto_near }` struct, keyed on the caller's account ID at the time the transaction was submitted [2](#0-1) . This `caller_deposit` is threaded through the chain of promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) and only used at the very end, if the underlying action promise fails:

```rust
match env::promise_result(0) {
    PromiseResult::Failed => {
        // The cross-contract call failed, refund the caller if needed
        if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
            let refund_promise = env::promise_batch_create(&account_id);
            env::promise_batch_action_transfer(
                refund_promise,
                NearToken::from_yoctonear(yocto_near.into()),
            );
        }
        ...
``` [3](#0-2) 

This refund `Promise` is created with `env::promise_batch_create` and dispatched with `promise_batch_action_transfer`, but its own execution result is never checked (no `.then()` callback is attached to verify success), and `rlp_execute_callback` immediately returns `ExecuteResponse { success: false, ... }` regardless of whether the refund transfer will actually succeed. This mirrors the reported `SafeCall.send(...)` pattern that ignores the return value of a critical payment.

`Transfer` actions in the runtime require the target account to exist (unless implicit-account creation applies), enforced by `check_account_existence`: `Action::Transfer(_) => { if account.is_none() && !implicit_creation_allowed(...) { return Err(ActionErrorKind::AccountDoesNotExist ...) } }` [4](#0-3) . Because the refund receipt is generated asynchronously (it is a genuine cross-contract/cross-shard receipt, not a protocol-level `system` refund), there is a window between when the caller's original deposit-bearing transaction is submitted and when this refund receipt is finally executed. If the caller account is deleted in that window (e.g., the caller submits a `DeleteAccount` action via a separate, independently-routed transaction/receipt, which any account holder can always do unilaterally), the refund `Transfer` action fails with `AccountDoesNotExist`.

Since this failing receipt's predecessor is the Wallet Contract's own promise (not `"system"`), the protocol's deposit-refund mechanism described in `docs/RuntimeSpec/Refunds.md` sends the attached balance back to the receipt's *predecessor* — i.e., back into the Wallet Contract account's own balance [5](#0-4) . The Wallet Contract has no bookkeeping or mechanism to detect this returned balance or reattribute/re-release it to anyone; the funds are permanently commingled into the contract's balance, unreachable by the original caller.

### Impact Explanation
The external caller's attached NEAR deposit becomes permanently unrecoverable: it is not returned to the caller (who no longer exists) and not tracked as belonging to any other party in the Wallet Contract's state. This satisfies "permanently frozen funds" — the exact impact category matched by the reported issue, where a fire-and-forget payment failure causes value to be irrecoverably misdirected.

### Likelihood Explanation
This requires only an unprivileged actor (the caller who attached the deposit) to submit a `DeleteAccount` action for their own account while their `rlp_execute` call to a Wallet Contract is still in flight (i.e., before the asynchronous cross-contract callback resolves) — no validator or node compromise, no multi-party collusion, and no privileged access is needed. The caller (or anyone controlling that account's keys) can trigger this deterministically by design, similar to how the original report characterizes its trigger as "unlikely but deployer/receiver controlled" — here it is even more directly reachable since the affected account is the caller's own.

### Recommendation
Do not dispatch the refund as an unchecked fire-and-forget promise. Instead:
1. Chain a callback (`.then(...)`) onto the refund `Transfer` promise to detect failure.
2. On refund failure, record the stranded amount in contract state (e.g., a map from `account_id` to unclaimed balance) rather than silently absorbing it into the Wallet Contract's balance.
3. Provide a separate, permissionless method allowing the amount to be reclaimed/withdrawn later (e.g., by the original caller if the account is recreated, or redirected per an explicit recovery policy), analogous to the report's recommendation to track `optimismHoldings` separately and expose a dedicated withdrawal path.

### Proof of Concept
1. An external account `caller.near` calls `wallet.rlp_execute(target, tx_bytes_b64)` with an attached deposit, where the encoded action is engineered/guaranteed to fail at the target contract (e.g., call a nonexistent method or unregistered NEP-141 receiver) [6](#0-5) .
2. `inner_rlp_execute` records `CallerDeposit { account_id: caller.near, yocto_near: deposit }` and dispatches the cross-contract promise chain ending in `rlp_execute_callback` [7](#0-6) .
3. Before this asynchronous chain resolves (same or nearby block/chunk), `caller.near` submits a separate transaction executing `DeleteAccount`, removing itself from state.
4. The target call fails as expected; `rlp_execute_callback` creates the refund `Transfer` promise toward `caller.near`, which no longer exists.
5. The runtime rejects the `Transfer` with `ActionErrorKind::AccountDoesNotExist` per `check_account_existence` [4](#0-3) ; the deposit-refund receipt (per `docs/RuntimeSpec/Refunds.md`) returns the balance to the Wallet Contract account itself, with no record tying it back to the deleted caller — permanently stranding those funds.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
