### Title
Unbounded decimal-string parsing of `UniversalPayload` numeric fields in `MsgExecutePayload` enables gasless CPU-exhaustion DoS - (File: `x/uexecutor/types/universal_payload.go`)

### Summary
`MsgExecutePayload` is a gasless message that any unprivileged user can submit directly (per `app/README.md`: "any user, gasless — the UEA itself authenticates the request"). Its `UniversalPayload.ValidateBasic()` parses six attacker-controlled string fields (`Value`, `GasLimit`, `MaxFeePerGas`, `MaxPriorityFeePerGas`, `Nonce`, `Deadline`) directly into `big.Int` with no length or canonical-format check before parsing, mirroring the external report's gnark issue where arbitrary-length decimal strings are handed to expensive big-integer parsing before any cheap rejection.

### Finding Description
`UniversalPayload.ValidateBasic()` iterates over the numeric string fields and calls `new(big.Int).SetString(value, 10)` unconditionally: [1](#0-0) 

This is invoked from `MsgExecutePayload.ValidateBasic()`: [2](#0-1) 

`MsgExecutePayload` is on the gasless whitelist (`app/txpolicy/gasless.go`) and is described as callable by "any user": [3](#0-2) 

The ante-handler chain runs `ante.NewValidateBasicDecorator()` — which calls `msg.ValidateBasic()` for every message in a tx — before the fee/gas-consumption decorators (`NewConsumeGasForTxSizeDecorator`, `NewDeductFeeDecorator`) and before `NewMinGasPriceDecorator` skips fee checks for gasless txs: [4](#0-3) 

There is no field-level length cap on `UniversalPayload.Value`/`GasLimit`/`MaxFeePerGas`/`MaxPriorityFeePerGas`/`Nonce`/`Deadline` at the proto or Go-type level, so a caller can populate any of these with a decimal string sized up to the node's tx-size limit (there is no repo-level `MaxTxBytes`/tx-size-limit constant found — the only cap is CometBFT's configurable mempool `max_tx_bytes`, typically ~1MB by default). `big.Int.SetString` base-10 parsing cost grows superlinearly with input length, so a multi-hundred-KB decimal string forces meaningful CPU work on every node that runs `CheckTx` (during mempool gossip/re-checks) and `DeliverTx`, for a message the attacker pays **no fee** to submit.

### Impact Explanation
Because `MsgExecutePayload` is explicitly gasless, an attacker can broadcast a stream of such transactions at effectively zero cost while forcing CPU/memory overhead on every full node that validates the tx (CheckTx is re-run repeatedly as the tx propagates and sits in the mempool). This matches the "denial of service...reachable without privileged control" allowed-impact category. It is not a fund-theft or state-corruption bug — the numeric fields are otherwise correctly bounds-checked for sign/format (just not for length) — so the material impact is availability degradation of the gasless admission path, consistent with the external report's classification as a Medium-severity verifier-side DoS analog rather than a soundness break.

### Likelihood Explanation
Reachable by a fully unprivileged external user with no bonded UV/validator status and no gas token balance (gasless path), using only the standard `MsgExecutePayload` RPC. No other guard (ante decorator or field validator) rejects oversized numeric strings before the `big.Int.SetString` parse, and this happens prior to any fee-based cost that could otherwise disincentivize spam.

### Recommendation
In `UniversalPayload.ValidateBasic()` (`x/uexecutor/types/universal_payload.go`), enforce a hard maximum length on each numeric string field (e.g., ≤78 decimal digits, sufficient for a uint256) and reject with a cheap string-length check before calling `big.Int.SetString`. Apply the same bound to `Inbound.Amount` in `ValidateForExecution` (`x/uexecutor/types/inbound.go`) and any other user-reachable decimal-string parse. Consider also adding a general max-size validation for `MsgExecutePayload`/`UniversalPayload` fields at the proto/CLI boundary.

### Proof of Concept
1. Construct a `MsgExecutePayload` with a valid `Signer`, `UniversalAccountId`, and `VerificationData`, but set `UniversalPayload.GasLimit` (or `Value`/`Nonce`/`Deadline`) to a syntactically valid but extremely long decimal string (e.g., hundreds of thousands of `9` digits, sized close to the mempool's `max_tx_bytes` limit).
2. Broadcast the tx with zero fee (it qualifies for the gasless whitelist).
3. Observe that `ValidateBasic()` → `UniversalPayload.ValidateBasic()` calls `new(big.Int).SetString(value, 10)` on the full-length string before any format/length rejection, consuming disproportionate CPU on every node performing `CheckTx`, and that this cost is incurred with no attacker-side fee cost.
4. Repeat with many such transactions to observe cumulative CPU load on the mempool across nodes.
