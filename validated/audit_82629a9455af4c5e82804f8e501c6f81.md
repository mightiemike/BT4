## Analysis

The report describes a class of bug where a shared, mutable counter (`perp_clients_count`) determines a per-user price via a formula, and any unprivileged actor can transiently move that counter (buy then sell) to extract value from a victim whose price/allocation is computed off the *current* counter value rather than a value fixed at their own action.

The closest reachable analog in java-tron is the **resource-weight accounting used for free bandwidth/energy** (`TotalNetWeight` / `TotalEnergyWeight`), which is a global, shared denominator that any account can instantly inflate or deflate via `FreezeBalanceV2Actuator` / `UnfreezeBalanceV2Actuator`, and which is read live (per-transaction) by `BandwidthProcessor`/`EnergyProcessor` to compute *every other account's* free-resource allocation.

### Root cause

`FreezeBalanceV2Actuator.execute` increments `TotalNetWeight`/`TotalEnergyWeight` immediately, in the same transaction that freezes TRX: [1](#0-0) 

`UnfreezeBalanceV2Actuator.execute` decrements the same weight **immediately** as well — only the TRX principal return is delayed (`addUnfrozenV2List`/`expireTime`), not the weight change: [2](#0-1) [3](#0-2) 

Every account's free-bandwidth limit is computed *at the moment of use* from the current, global `TotalNetLimit`/`TotalNetWeight` ratio: [4](#0-3) 

The identical shared-denominator pattern exists for energy (`TotalEnergyWeight` / `TotalEnergyCurrentLimit`), used by `EnergyProcessor` and by `DelegateResourceActuator`/`UnDelegateResourceActuator` validation: [5](#0-4) 

This is structurally identical to the report's `perp_clients_count`-driven `seat_price`: a globally shared parameter, changeable in real time by any unprivileged account, that determines the outcome (price/allocation) for other unrelated users' concurrent operations.

### Finding

Title: Instant TotalNetWeight/TotalEnergyWeight manipulation via same-block Freeze/UnfreezeBalanceV2 lets any account grief or extract value from other users' resource allocation - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceV2Actuator.java`, `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`, `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`)

**Finding Description:** `TotalNetWeight`/`TotalEnergyWeight` are global denominators used to compute every account's free bandwidth/energy limit (`calculateGlobalNetLimit`, energy equivalent). `FreezeBalanceV2Actuator` increases this weight instantly upon freezing, and `UnfreezeBalanceV2Actuator` decreases it instantly upon unfreezing — only the return of the frozen TRX principal is subject to the unfreeze delay period, not the weight adjustment itself. Consequently, an attacker can broadcast a large `FreezeBalanceV2Contract` immediately before a victim's bandwidth/energy-consuming transaction is packed into the same or an adjacent block, temporarily inflating the global weight and shrinking every other account's computed free-resource limit (`netWeight * (totalNetLimit/totalNetWeight)`), then immediately follow with `UnfreezeBalanceV2Contract` to restore the previous state — reclaiming their capital with only momentary opportunity cost. Because `calculateGlobalNetLimit`/energy equivalents are recomputed live from the current global weight rather than from a value pinned at the time an account froze its own balance, other users' free-resource allocation is at the mercy of any third party's transient stake changes within the same block window.

**Impact Explanation:** Victims whose free-bandwidth/energy allocation is shrunk by the attacker's transient freeze may have their transactions rejected for insufficient free bandwidth (`useAccountNet` returns false) or forced to burn TRX for extra bandwidth/energy that they would not otherwise have needed to pay — an unpermissioned, temporary resource-accounting manipulation causing financial harm/DoS to unrelated accounts, mirroring the reported "attacker extracts value by manipulating a shared price/allocation denominator around a victim's transaction."

**Likelihood Explanation:** Requires only ordinary account balance and standard `FreezeBalanceV2`/`UnfreezeBalanceV2` transactions, no privileged role, and relies on transaction ordering within a block or short window (block producers or any user paying priority fees can achieve this), consistent with the "no front-running required, only ordering/timing" nature of the referenced report.

**Recommendation:** Snapshot or smooth the resource-weight denominator (e.g., use weight as of the start of block/maintenance cycle rather than live value), or require a minimum holding period between `FreezeBalanceV2` and the corresponding `UnfreezeBalanceV2`/weight decrement so that weight changes cannot be reverted within the same block, removing the ability to transiently move the shared denominator at zero cost.

**Proof of Concept:** 1) Attacker submits `FreezeBalanceV2Contract` for a very large `frozenBalance`, which raises `TotalNetWeight` immediately per `FreezeBalanceV2Actuator.execute` [6](#0-5) . 2) In the same or next block, the victim's transaction consumes `BandwidthProcessor.calculateGlobalNetLimit`, which now computes a smaller free-bandwidth ceiling due to inflated `TotalNetWeight` [7](#0-6) , causing the victim's transaction to fail the free-bandwidth check or to pay TRX for bandwidth. 3) The attacker immediately submits `UnfreezeBalanceV2Contract`, instantly restoring `TotalNetWeight` to its prior value while only the principal return is delayed [8](#0-7) , leaving the attacker's capital effectively unaffected but the victim harmed.

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                        long unfreezeBalance) {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    switch (unfreezeBalanceV2Contract.getResource()) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        dynamicStore.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        dynamicStore.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(-unfreezeBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        dynamicStore.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        //this should never happen
        break;

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }
