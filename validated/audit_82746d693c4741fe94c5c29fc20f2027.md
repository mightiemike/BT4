## Analysis

The External Report's bug class is: a component stores a monotonically-tracked per-account value, and legitimate future state transitions are rejected/broken because the code assumes strict monotonic progression without validating the actual invariant holds. The strongest analog in this sequencer codebase is in the mempool's `MempoolState::stage` function, which hard-codes the invariant that every account's staged nonces form a strict increment chain, and enforces it with a runtime `assert_eq!` rather than a graceful error — reachable directly from a single account's transaction submissions in FIFO ("Echonet") mode.

### Title
Out-of-order-nonce transactions from a single account panic the mempool's `stage()` and halt block building - (File: `crates/apollo_mempool/src/mempool.rs`)

### Summary
In `BehaviorMode::Echonet` (FIFO queue mode), the mempool inserts every accepted transaction of an account into the ready queue **regardless of nonce**, with no gap/order enforcement beyond rejecting nonces below the account's current nonce. When `get_txs` later stages the popped chunk, `MempoolState::stage` assumes staged nonces for an address are strictly consecutive and enforces this via `assert_eq!`, which panics instead of returning an error if a single account has two ready transactions in non-sequential nonce order within the same chunk.

### Finding Description
`add_tx_inner` unconditionally inserts a transaction into the FIFO queue in Echonet mode, independent of nonce ordering relative to other queued transactions of the same address: [1](#0-0) 

`validate_incoming_tx` (both the `Mempool` wrapper and `MempoolState` version) only rejects a transaction whose nonce is *strictly lower* than the resolved account nonce; it performs no check that pool/queue transactions for an address remain nonce-contiguous or arrive in ascending nonce order: [2](#0-1) 

The FIFO queue's `insert` simply appends every accepted tx to the back of the queue in arrival order, with no nonce-order enforcement, and `pop_ready_chunk` pops the chunk strictly in that arrival order: [3](#0-2) [4](#0-3) 

When `get_txs` builds a chunk, it stages every transaction reference in the popped (arrival) order via `MempoolState::stage`: [5](#0-4) 

`stage` assumes that if an address already has a staged nonce from an earlier tx in the same batch, the new tx's next nonce must be exactly `existing_nonce + 1`, and panics via `assert_eq!` if this is violated: [6](#0-5) 

If a single account submits two (or more) transactions to the mempool with non-sequential nonces where the higher-nonce transaction arrives before the lower-nonce one (e.g., nonce 5 submitted before nonce 3, both currently valid because account_nonce ≤ 3), both are accepted into the pool and pushed to the FIFO queue in that arrival order. If both end up in the same `pop_ready_chunk` result, `stage` is called first for nonce 5 (`staged[addr] = 6`), then for nonce 3 (`next_nonce = 4`), causing `assert_eq!(try_increment_nonce(6), 4)` to fail and panic. This is exactly analogous to the reported bug class: a stored, assumed-monotonic per-account value (`migratedAmount` / staged nonce) makes an otherwise-valid state transition (a legitimately-priced lower-nonce transaction) fail — except here the failure is a hard panic rather than a graceful revert.

### Impact Explanation
A panic inside `MempoolState::stage`, invoked from `Mempool::get_txs` during block building, aborts the mempool's transaction-fetching flow. Depending on how the batcher/sequencer wraps this call, this can crash the mempool component or the sequencer process, preventing the sequencer from producing further blocks — i.e., "a network unable to confirm new transactions," which is an explicitly accepted impact category. This is triggerable by a single unprivileged account submitting an ordinary sequence of transactions with nonces out of arrival order, without needing to be a malicious operator, proposer, or peer.

### Likelihood Explanation
Reaching this requires: (1) the mempool running in FIFO/Echonet mode, and (2) a single account submitting two transactions whose FIFO arrival order does not match ascending nonce order (readily achievable by any client sending nonce 5 before nonce 3, both of which validate individually since neither is "too old"), and (3) both transactions landing in the same `pop_ready_chunk` result. None of these require privileged access, and the FIFO insertion path explicitly documents that "FIFO mode: add all transactions to the queue immediately, regardless of nonce," so the precondition is a designed behavior of the mode rather than an edge case.

### Recommendation
In `MempoolState::stage`, replace the `assert_eq!` invariant with a proper `MempoolResult` error path (analogous to other nonce-validation errors like `NonceTooOld`), or enforce nonce-order-safety earlier — e.g., have the FIFO queue's `pop_ready_chunk` never return two transactions from the same address unless they are nonce-consecutive, or reject/defer transactions whose nonce is out of arrival-order relative to already-pooled transactions for the same address before they can reach `get_txs`.

### Proof of Concept
1. Configure the mempool with `BehaviorMode::Echonet` (FIFO queue).
2. From account `A` with current on-chain/account nonce `0`, submit `add_tx` for nonce `5` (accepted; not "too old").
3. Submit `add_tx` for nonce `3` from the same account `A` (also accepted, since `3 >= 0`, and FIFO mode doesn't check consecutiveness with other pooled/queued nonces).
4. Both `TransactionReference`s are pushed to the FIFO queue in submission order: `[nonce=5, nonce=3, ...]`, per `add_tx_inner`'s unconditional `insert_to_tx_queue` call in FIFO mode.
5. Call `Mempool::get_txs(n)` with `n` large enough to pop both in one chunk. `pop_ready_chunk` returns `[nonce=5, nonce=3]` in that arrival order.
6. `get_txs`'s staging loop calls `self.state.stage(tx_reference)` for nonce `5` first (`staged[A] = 6`), then for nonce `3` (`next_nonce = 4`); the `assert_eq!(try_increment_nonce(6), 4)` inside `stage` fails and panics, unwinding out of `get_txs`.

    fn pop_ready_chunk(&mut self, n_txs: usize) -> Vec<TransactionReference> {
        if self.queue.is_empty() {
            return Vec::new();
        }

        let Some(current_state) = self.current_proposal_state.as_mut() else {
            panic!(
                "FIFO pop_ready_chunk: missing proposal state; resolve_timestamp must run before \
                 get_txs for this queue"
            );
        };

        let front_tx =
            self.queue.front().expect("FIFO pop_ready_chunk: queue non-empty after is_empty check");
        if !current_state.matches_tx(front_tx) {
            debug!(
                "FIFO pop_ready_chunk: empty chunk (head_block={:?}, expected_block={:?})",
                front_tx.block_number, current_state.expected_block_number,
            );
            return Vec::new();
        }

        let mut result = Vec::with_capacity(n_txs);
        while result.len() < n_txs {
            let Some(front_tx) = self.queue.front() else {
                break;
            };
            if !current_state.matches_tx(front_tx) {
                break;
            }

            let tx = self.queue.pop_front().expect("Queue front must exist if peek succeeded");
            result.push(tx.tx_reference);
            self.staged_txs.push(tx);
        }

        debug!(
            "FIFO pop_ready_chunk: popped {} txs (requested cap n_txs={}, queue_len_after={})",
            result.len(),
            n_txs,
            self.queue.len()
        );

        if !result.is_empty() {
            current_state.advance_block_if_drained(&self.queue);
        }
        result
    }
