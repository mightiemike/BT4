## Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay/execution divergence for state/hot-state/position roots pass as "verified" - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the single invariant-check function used across the executor's replay/verification paths (chunk executor's `verify_execution`, `aptos-debugger`, and the CLI's replay comparator) to confirm that a locally computed `TransactionOutput` matches an authenticated `TransactionInfo`. The function checks status, gas, write-set hash, and event-root hash, but explicitly and admittedly does **not** check the state checkpoint hash, hot-state root, or `position_state_checkpoint_hash`, per its own inline `TODO(trading-native)` comment.

## Finding Description [1](#0-0) 

`ensure_match_transaction_info` verifies:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (`CryptoHash::hash(self.write_set())`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but ends with:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

This function is the sole cross-check invoked by `ChunkExecutorInner::verify_execution` in the chunk executor's replay path [2](#0-1)  and by `aptos-debugger`'s mismatch printer and the CLI replay tool [3](#0-2) [4](#0-3) . None of these call sites separately check the state-checkpoint/hot-state/position-state root hashes; they all rely on `ensure_match_transaction_info` as the complete correctness oracle.

Because the state/hot-state checkpoint root and `position_state_checkpoint_hash` are precisely the fields designed to authenticate the Merkle-committed state (and, per the config plumbing `compute_trading_native_state_roots` / `hot_state_root_in_txn_info` in `BlockExecutorConfigFromOnchain` used throughout `do_get_execution_output.rs`, `do_state_checkpoint.rs`, `do_ledger_update.rs`), a divergence in locally-computed state root vs. the authenticated `TransactionInfo`'s checkpoint hash is not detected by this comparator. This is a proof/commitment invariant gap: the accumulator leaf (`TransactionInfo`) contains a `state_checkpoint_hash` (and, when the trading-native feature is active, additional roots), but the verification utility used by replay/verify tooling silently omits comparing it.

## Impact Explanation
This breaks the "proof and storage pivot" invariant that "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and "committed state that differs from the correct VM result... must not be accepted as valid." Concretely:
- `db-tool replay-verify` / `replay_on_archive` and the CLI's local-replay comparator can report a **successful** replay even though the locally recomputed state/hot-state Merkle root (or the position-state checkpoint root once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) diverges from what was authenticated on-chain.
- This is a hard-fork-class detection gap: if execution semantics change (intentionally or via a bug) in a way that alters the resulting state tree but leaves write-set/event/gas/status unchanged in a way that still round-trips through this incomplete check, replay-verification tooling used to validate backups, historical archives, and node bootstrap integrity will not flag the divergence.
- Because the same `Result` gate feeds `verify_execution_mode.mark_seen_error()` / process exit codes for `db-tool ReplayVerify` (see `storage/db-tool/src/replay_verify.rs`), operators and auditors trusting a "success" replay-verify result would have false confidence in the correctness of a stored/restored ledger.

The comment itself is an explicit acknowledgment by the developers that this gap exists and that it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," confirming this is a real, currently-live incomplete invariant in the mainline verification code path rather than a hypothetical.

## Likelihood Explanation
This does not require any privileged actor; it is a property of the verification code itself, triggered any time replay-verify/debugger/CLI replay tooling is used with a `TransactionInfo` whose checkpoint-hash fields would have differed from a correct re-execution but whose write-set/event/gas/status output does not differ. The likelihood of exploitation (i.e., a state-root divergence not accompanied by write-set/event changes) depends on the nature of the divergence-causing bug, but the detection gap itself is unconditionally present today in `ensure_match_transaction_info`.

## Recommendation
Extend `ensure_match_transaction_info` to also compare `txn_info.state_checkpoint_hash()` (and, when `compute_trading_native_state_roots`/hot-state root fields are present, the hot-state and `position_state_checkpoint_hash`) against the locally recomputed values, before any code path enables `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. All callers (`chunk_executor::verify_execution`, `aptos-debugger`, CLI replay) should be updated/tested to pass the expected checkpoint hash so a true state-root mismatch causes verification failure rather than a silent pass.

## Proof of Concept
Conceptual PoC (not exploit code, since this is a verification-logic gap rather than a directly triggerable state corruption):
1. Take any historical (or specially crafted, in a test harness) `TransactionInfo` and a re-executed `TransactionOutput` whose write set, events, gas, and status are identical to the original, but whose actual resulting state tree (state checkpoint / hot-state / position-state root) differs from `txn_info.state_checkpoint_hash()` (e.g., simulate this by executing against a state view that already contains a subtly different value not touched by the write set, or under a future onchain-config toggle affecting root construction).
2. Call `TransactionOutput::ensure_match_transaction_info(version, &txn_info, None, None)` — as done in `execution/executor/src/chunk_executor/mod.rs:692-697`.
3. Observe that the call returns `Ok(())` despite the state-root divergence, because the function body (`types/src/transaction/mod.rs:2139-2204`) never reads or compares `txn_info.state_checkpoint_hash()`.
4. This confirms that `db-tool replay-verify`/CLI replay would report success on a ledger with a divergent (uncommitted-consistent) state root.

**Note on verification limitations:** I was unable to fully trace, within the available indexed code, the exact schema/type of `position_state_checkpoint_hash` on `TransactionInfo` or confirm whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`compute_trading_native_state_roots` is currently enabled on mainnet (the feature flag exists in `types/src/on_chain_config/aptos_features.rs` and `move-stdlib/sources/configs/features.move`, but I could not retrieve those files' full contents due to indexing limits). If the feature is not yet enabled on mainnet, the practical severity is currently bounded to the standard `state_checkpoint_hash` field (still unchecked) rather than the additional trading-native fields; I'd recommend a Devin session with full repo access to confirm the current activation status of this feature flag on mainnet before finalizing severity.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
