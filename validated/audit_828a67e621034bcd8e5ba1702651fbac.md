### Title
Unchecked `ArithmeticException` from `BigInteger.longValueExact()` overflow in `getTotalEnergyLimitWithFixRatio` bypasses declared `ContractValidateException` contract - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`getTotalEnergyLimitWithFixRatio` computes `creatorEnergyLimit` via `BigInteger.valueOf(callerEnergyLimit).multiply(BigInteger.valueOf(ONE_HUNDRED - consumeUserResourcePercent)).divide(BigInteger.valueOf(consumeUserResourcePercent)).longValueExact()` [1](#0-0) . When `callerEnergyLimit` is large and `consumeUserResourcePercent` is small (e.g. 1), the multiplication result can exceed `Long.MAX_VALUE`, and `longValueExact()` throws an unchecked `ArithmeticException` rather than the `ContractValidateException` the method signature declares [2](#0-1) .

### Finding Description
`getTotalEnergyLimitWithFixRatio` is called with `caller`- and `feeLimit`-derived energy (`callerEnergyLimit`), and a contract-owner-controlled `consumeUserResourcePercent` read from `ContractCapsule.getConsumeUserResourcePercent` [3](#0-2) . For percent values strictly between 0 and 100, the code executes `min(BigInteger.valueOf(callerEnergyLimit).multiply(BigInteger.valueOf(100 - percent)).divide(BigInteger.valueOf(percent)).longValueExact(), ...)` [4](#0-3) . `BigInteger` arithmetic itself never overflows, but `longValueExact()` throws `ArithmeticException` if the resulting `BigInteger` does not fit into a `long`. With `percent = 1`, the multiplier is 99, so if `callerEnergyLimit` is roughly `Long.MAX_VALUE / 99` or larger, the division result still exceeds `Long.MAX_VALUE` and `longValueExact()` throws.

This is a legitimate defect: the method's signature declares `throws ContractValidateException`, but an unchecked `ArithmeticException` (a `RuntimeException`) can escape from inside it, bypassing the caller's expectation that only `ContractValidateException` needs to be handled at this call site.

I was not able to fully confirm within the available context (1) the exact upstream caller chain for `getTotalEnergyLimitWithFixRatio` (i.e., where in `VMActuator.execute`/`validate` it is invoked) and whether a broader `catch (Exception e)` / `catch (Throwable t)` wraps that call, and (2) whether `feeLimit`/energy-price validation elsewhere in the transaction pipeline (e.g. a max fee-limit check before this code runs) already prevents `callerEnergyLimit` from ever reaching magnitudes near `Long.MAX_VALUE / 99`. In typical java-tron RPC handling, `triggerconstantcontract`/`triggersmartcontract` requests are processed per-request in HTTP/gRPC handler threads, and unhandled exceptions there are generally caught by the servlet/gRPC framework and returned as an error response to the single caller rather than crashing the whole node process — so the "full-node crash" characterization in the prompt is not confirmed by the code reviewed; what is confirmed is a violation of the checked-exception contract (`ContractValidateException` expected, `ArithmeticException` thrown), which can produce an ungraceful 500/internal error for that one request instead of a well-formed validation error.

### Impact Explanation
Concrete impact is limited to a per-request denial of service / ungraceful failure on `triggerconstantcontract`/`triggersmartcontract` calls that hit this exact overflow condition, rather than a demonstrated crash of the node process, based on the code reviewed. This maps to a minor "DoS via RPC-API" class (malformed/edge-case error handling) rather than a node-crashing DoS, pending confirmation of the surrounding exception-handling layers, which I could not fully verify with the available tool budget.

### Likelihood Explanation
Triggering the overflow requires an attacker (or the attacker acting as their own contract deployer) to deploy a contract with `consumeUserResourcePercent` set to a small value like 1, and then call it as a *different* account (not the contract owner, since the owner-call path returns early at line 721) with a `feeLimit`/energy configuration large enough to make `callerEnergyLimit` approach `Long.MAX_VALUE/99`. Whether an ordinary attacker can actually drive `callerEnergyLimit` (derived from `feeLimit` via `getAccountEnergyLimitWithFixRatio`, not fully traced here) to that magnitude depends on fee-limit/energy-price validation elsewhere in the codebase that I was unable to confirm within this session.

### Recommendation
Wrap the `BigInteger` division/`longValueExact()` call in a try/catch for `ArithmeticException` and rethrow it as `ContractValidateException` (consistent with the method's declared contract), or clamp the computed value to `Long.MAX_VALUE` before calling `longValueExact()`, so that overflow conditions are converted into a well-defined validation error instead of an unchecked runtime exception.

### Proof of Concept
```java
// JUnit-style PoC (conceptual, requires full VMActuator/repository setup):
long callerEnergyLimit = Long.MAX_VALUE / 2; // large caller energy limit
long consumeUserResourcePercent = 1; // contract owner-configured value 1-99

BigInteger result = BigInteger.valueOf(callerEnergyLimit)
    .multiply(BigInteger.valueOf(100 - consumeUserResourcePercent))
    .divide(BigInteger.valueOf(consumeUserResourcePercent));
// result ~ 49.5 * Long.MAX_VALUE, far exceeding Long.MAX_VALUE

// Expected (per method signature): ContractValidateException
// Actual: result.longValueExact() throws ArithmeticException("BigInteger out of long range")
result.longValueExact();
```
Assertion to add to `getTotalEnergyLimitWithFixRatio` tests: invoking it with the above inputs should throw `ContractValidateException`/`ContractExeException`, not an unchecked `ArithmeticException`.
