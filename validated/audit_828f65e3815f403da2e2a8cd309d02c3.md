### Title
Precompiled-contract calls in the TVM permanently transfer `callValue` even when the call fails due to insufficient energy - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
`Program.callToPrecompiledAddress()` transfers the TRX/TRC10 `endowment` (the value attached to a `CALL`/low-level `call{value:X}(...)` targeting a precompiled contract address) *before* verifying that the caller supplied enough energy to actually execute the precompiled contract. The code's own comment states the transfer "is not reversible by rollback." If the forwarded energy is insufficient, the call returns failure (`stackPushZero`) but the value that was already moved is not reverted, mirroring the Velodrome `RedemptionSender` class of bug: an irreversible value-moving side effect is performed before the fee/energy sufficiency check that determines whether the intended action (the precompiled call) actually succeeds.

### Finding Description
In `callToPrecompiledAddress`: [1](#0-0) 

the endowment is transferred into the child `deposit` repository unconditionally once a non-zero `endowment` and distinct sender/context addresses are detected. Only afterwards does the code check: [2](#0-1) 

If `requiredEnergy > msg.getEnergy().longValue()`, the branch simply refunds 0 energy and pushes zero onto the stack — it does *not* attempt to reverse the value transfer performed moments earlier. The explicit in-code comment "`// Charge for endowment - is not reversible by rollback`" documents that this transfer is treated as final/committed regardless of whether the subsequent precompiled-contract execution check passes.

This is structurally identical to the Velodrome bug: a user-controlled/attacker-controlled amount of "fee"/energy is supplied for an operation (there, `msg.value` for a LayerZero message; here, `msg.getEnergy()` forwarded to a `CALL`), an irreversible value transfer happens first, and only then is it discovered that the supplied fee/energy was insufficient for the intended operation to actually take effect.

### Impact Explanation
Because the value transfer is applied to the child `deposit` Repository before the energy sufficiency check, and the code comment claims it "is not reversible by rollback," a contract author (or an attacker crafting bytecode/calling a vulnerable contract) can cause a `CALL` with `value > 0` to a precompiled address to always deduct the sender's balance/TRC10 token even though the call returns failure (0) to the caller. This can lead to token or TRX loss disguised as a "failed call," corrupting expected atomicity assumptions of contract logic that checks the boolean return of `call.value(...)` before trusting that funds moved. If any accounting logic in a wrapping smart contract assumes "call returned false ⇒ no state change occurred," that assumption is violated, which can be leveraged to drain balances or desynchronize internal contract bookkeeping — an accounting corruption bug reachable purely through a normal `TriggerSmartContract` broadcast transaction that invokes a `CALL` opcode toward a precompiled address with value and insufficient energy.

### Likelihood Explanation
This code path is reachable by any account through an ordinary contract-call transaction: deploy or invoke a contract that performs a low-level `.call{value: x}(precompiledAddress, data)` (or `CALLCODE`/generic `CALL`) while deliberately supplying less energy/gas than `EnergyForData` requires for that precompiled contract. No special privileges, validator collusion, or off-chain component is needed — it is purely a TVM opcode-execution edge case, making it fully attacker-triggerable from an anonymous broadcast transaction. The main uncertainty is whether the child `deposit` repository's changes are guaranteed to propagate to the parent state even without an explicit `deposit.commit()` call (e.g., due to shared in-memory account-object references) — this could not be fully confirmed from the available `RepositoryImpl` excerpts before the investigation budget was exhausted, so verification of the exact persistence mechanism is recommended.

### Recommendation
- Defer the endowment transfer until *after* the energy sufficiency check (`requiredEnergy > msg.getEnergy()`) succeeds, so failed precompiled calls never move value.
- Alternatively, explicitly roll back (discard) the `deposit` repository's balance mutation before pushing zero to the stack when the energy check fails.
- Add regression tests exercising `CALL` with value to each precompiled address using energy exactly one unit below `requiredEnergy`, asserting the sender's balance/TRC10 balance is unchanged after the failed call.

### Proof of Concept
Conceptual PoC (cannot be fully validated without running the node, since child-repository persistence semantics were not fully confirmed):
1. Deploy a contract with a function:
   ```solidity
   function attack(address precompiled) public payable {
       precompiled.call.value(msg.value)(new bytes(0)); // low-level call, insufficient gas
   }
   ```
2. Invoke `attack` via `TriggerSmartContract`, forwarding energy less than the precompiled contract's `EnergyForData(data)` cost (configurable via `feeLimit`/gas stipend on the inner call).
3. Observe: the inner `call` returns `false` (per `callToPrecompiledAddress`'s failure branch at [3](#0-2) ), yet the sender's balance is decremented by `msg.value` because the transfer executed earlier at [4](#0-3)  is not reversed in this failure path.
