## Title
Unrestricted, un-timelocked global-contract owner upgrade lets one account unilaterally rug every account referencing it via `UseGlobalContractByAccountId` - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
NEAR's global-contract feature includes an `AccountId`-based deployment mode that is functionally identical to an upgradeable proxy: an account deploys a global contract once, and any other account can opt to "use" that contract by referencing the deployer's `AccountId` rather than an immutable code hash. The deploying account can redeploy new code under the same `AccountId` at any time, and it instantly becomes the live implementation for every account that referenced it — with no timelock, no multisig, and no on-chain notice to the accounts relying on that code.

### Finding Description
`GlobalContractDeployMode` explicitly documents this trust model: [1](#0-0) 

- `CodeHash` mode is immutable — reference is to a specific hash.
- `AccountId` mode is explicitly mutable: "This allows the owner to update the contract for all its users."

Deployment is a plain `DeployGlobalContractAction` executed by `action_deploy_global_contract`, which simply burns storage cost and pushes the new code into distribution — there is no access control, delay, or approval step beyond the deployer signing their own transaction: [2](#0-1) 

Any other account opts in via `UseGlobalContractAction`, which stores `AccountContract::GlobalByAccount(id)` — a live pointer to whatever code currently sits under that `AccountId`, not a pinned hash: [3](#0-2) 

Because the account's `AccountContract::GlobalByAccount(id)` pointer resolves dynamically at call time to whatever the deployer most recently pushed, the deployer can redeploy arbitrary WASM (including code that issues `Promise::transfer` actions to move the referencing account's own balance, or otherwise abuses the account's storage/state) at any moment after other accounts have already wired themselves to it. The documentation for `DeployGlobalContractAction` confirms the propagation is automatic and global, with no consent mechanism for existing users: [4](#0-3) 

This is the direct on-chain analog of the reported Vault.sol issue: an "owner" (the global-contract deployer) can swap the logic that other accounts/users depend on to a malicious implementation and drain funds, exactly the "Owner can upgrade Vault to a malicious implementation and rug users" class of centralization risk, reachable purely through ordinary transactions (`DeployGlobalContract...` then `UseGlobalContract...`, both are ordinary unprivileged actions, not operator/validator-only).

### Impact Explanation
Any account that adopts a shared implementation via `UseGlobalContractByAccountId` implicitly grants the deploying account permanent, unilateral control over its executable logic. If that deployer is compromised or acts maliciously, it can push new code that drains balances or corrupts state of every dependent account with no warning, no delay, and no override — a direct path to unauthorized value movement across potentially many accounts simultaneously.

### Likelihood Explanation
Likelihood depends entirely on user adoption of `AccountId`-mode global contracts (e.g., wallet/shared-library patterns, as seen in the ETH-implicit-account and ZBA test flows in the codebase) and on the trustworthiness/security of the deploying account's key. Since the mechanism is a documented, intended feature rather than a bug in validation logic, exploitation requires either a compromised deployer key or a deployer acting maliciously post-adoption — this is a design-level centralization risk rather than a memory-safety or consensus bug.

### Recommendation
- Consider adding an explicit "pinning"/consent mechanism so referencing accounts can opt to freeze at the currently-deployed code version, or require an explicit re-approval (fresh `UseGlobalContract` signature) after every redeploy rather than silent live-swap.
- Consider surfacing a mandatory timelock or multi-key requirement (e.g., requiring a full access key threshold or a delay window) before an `AccountId`-mode global contract redeploy takes effect for already-bound accounts, mirroring the standard "use a timelock/multisig for upgradeable proxies" recommendation from the referenced report.
- Improve documentation/wallet UX to make the live-upgrade risk of `AccountId` mode unmistakably clear at the point where a user account calls `UseGlobalContractByAccountId`.

### Proof of Concept
1. Deployer account `D` calls `DeployGlobalContractAction{ code: benign_code, deploy_mode: AccountId }` (see `runtime/runtime/src/global_contracts.rs` `action_deploy_global_contract`).
2. Victim account `V` calls `UseGlobalContractAction{ contract_identifier: AccountId(D) }`, binding `V`'s `AccountContract` to `GlobalByAccount(D)` (see `use_global_contract` in the same file).
3. At any later time, `D` redeploys `DeployGlobalContractAction{ code: malicious_code, deploy_mode: AccountId }` under the same `AccountId`. Nonce-based idempotency only guards against stale/out-of-order overwrites (`test_global_contract_nonce_prevents_stale_overwrite` in `test-loop-tests/src/tests/global_contracts_distribution.rs`), it does not prevent an intentional, authorized malicious redeploy by `D`.
4. Any caller now invoking a function on `V` executes `malicious_code`, which can issue transfer promises against `V`'s own balance/state, exfiltrating funds without `V`'s renewed consent.

```rust
pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}
```

```rust
pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
```

}

**Outcome**:

- First, the provided code is made available as global contract on the current shard.
- The same code propagates globally, shard by shard.
- Eventually, all accounts on all shards can reference the submitted code by the corresponding global contract identifier.
