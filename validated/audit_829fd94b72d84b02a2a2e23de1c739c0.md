### Title
Unbounded Gzip Decompression in `decompress_program` Allows Memory Exhaustion via Crafted `simulate_transaction`/`estimate_fee` RPC Declare-V1 Payload - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
`BroadcastedDeclareTransaction::V1` submitted to the RPC node's `simulate_transactions` / `estimate_fee` / `trace_transaction`-adjacent execution endpoints carries a base64+gzip-compressed Cairo-0 `program`. It is decompressed by `decompress_program`, which reads the gzip stream to completion with `GzDecoder::read_to_end` and **no output size bound**, unlike every other decompression path in the codebase.

### Finding Description
`decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs` decodes and inflates a user-supplied compressed program with an explicit TODO acknowledging the missing bound: [1](#0-0) 

This is invoked from `user_deprecated_contract_class_to_sn_api`, which is called when converting a `BroadcastedDeclareTransaction::V1` into an `ExecutableTransactionInput` for execution/simulation: [2](#0-1) [3](#0-2) 

By contrast, every other user-controlled decompression entry point in the codebase bounds the output: the gateway's `DeprecatedGatewaySierraContractClass::convert_to_sierra_contract_class` uses `decode_and_decompress_with_size_limit` [4](#0-3) , the p2p `Cairo0Class` protobuf converter enforces `MAX_CAIRO0_PROGRAM_SIZE` [5](#0-4) , and the generic helper `decode_and_decompress_with_size_limit` caps decompressed bytes via `.take(max_size + 1)` [6](#0-5) . `decompress_program` is the sole outlier that omits this protection, exactly mirroring the `cow_spdy:inflate/2` bug class: attacker-supplied compressed bytes are fed straight to the decompressor with no cap, so a small (few-KB) payload of highly repetitive data can expand to gigabytes, exhausting node memory.

### Impact Explanation
Any unauthenticated JSON-RPC client can call `simulate_transactions`/`estimate_fee` with a `DECLARE` V1 broadcasted transaction whose `program` field is a small, highly-compressible gzip blob. This forces the full-text RPC node to allocate an unbounded `Vec<u8>` during decompression before any size or gas validation occurs, causing memory exhaustion / OOM on the node process serving RPC. This is a network-reachable, unauthenticated denial-of-service against a full node's RPC-serving process.

### Likelihood Explanation
High: no authentication, staking, fees, or prior state is required — a single crafted JSON-RPC request is sufficient, and gzip compression ratios of >1000:1 are trivially achievable for repeated-byte payloads, so a few KB of request body can expand to gigabytes before the process notices.

### Recommendation
Apply the same size-bounding pattern used elsewhere in the codebase (`decode_and_decompress_with_size_limit` / `.take(max_size)`) inside `decompress_program`, rejecting the payload once a configured maximum decompressed size (e.g., matching `MAX_CAIRO0_PROGRAM_SIZE` or a dedicated RPC constant) is exceeded, before or during `read_to_end`.

### Proof of Concept
1. Craft a Cairo-0 `program.json` consisting of a long run of a single repeated byte (or JSON-compatible repeated structure) to maximize gzip compression ratio; gzip-compress and base64-encode it into a payload of only a few KB (the size of `base64_compressed_program.txt` fixture shows how these payloads are structured) [7](#0-6) .
2. Submit an RPC `starknet_estimateFee` or `starknet_simulateTransactions` request with a `DECLARE` transaction of `version: "0x1"` (`BroadcastedDeclareV1Transaction`), setting `contract_class.program` to the crafted payload.
3. The node calls `TryFrom<BroadcastedDeclareTransaction>::try_from` → `user_deprecated_contract_class_to_sn_api` → `decompress_program`, which decompresses without a size cap, allocating gigabytes of memory and potentially OOM-killing the RPC node process.

Note: I was unable to fully trace whether an upstream request-body size limit (e.g., an HTTP layer body limit before JSON-RPC deserialization) might partially mitigate this by capping the compressed input size — if such a limit exists, the achievable amplification factor should be recomputed based on that bound, but the missing decompression-size cap remains a genuine defect matching the reported bug class.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
