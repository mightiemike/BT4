## Title
Unchecked `long` addition in reward `allowance` accounting can overflow and corrupt withdrawable balances - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
`VoteRewardUtil.adjustAllowance` updates an account's reward `allowance` field with a raw, unchecked `long` addition (`allowance + amount`), unlike every sibling balance-mutation path in the codebase which performs overflow-checked arithmetic. This mirrors the `PublicVault.yIntercept` bug class: an unchecked addition on an accounting variable that gates how much a user can later withdraw.

### Finding Description
`adjustAllowance` in `VoteRewardUtil.java` computes the new allowance as a plain `long` sum with no overflow guard: [1](#0-0) 

This is invoked from `withdrawReward`, which is reached from `WithdrawRewardProcessor.execute()` — the handler for the TVM native `withdrawreward` contract call, triggered from any broadcast transaction/contract call as long as `VMConfig.allowTvmVote()` is enabled: [2](#0-1) 

Notice that `WithdrawRewardProcessor.execute()` itself is careful to use `LongMath.checkedAdd` when moving `allowance` into `balance` — but by that point `allowance` may already have silently overflowed inside `adjustAllowance`, because that step used unguarded addition. This is inconsistent with the rest of the accounting code in the same codebase, which consistently guards additions: [3](#0-2) [4](#0-3) 

The analogous legacy path `MortgageService.adjustAllowance` (used during block reward distribution) has the same unguarded pattern: [5](#0-4) 

### Impact Explanation
If `allowance` accumulates enough reward across cycles to overflow past `Long.MAX_VALUE`, the stored value silently wraps to a negative number (Java `long` overflow is not checked here, unlike `addBalance`/`adjustBalance`/`checkedAdd` elsewhere). A negative or corrupted `allowance` corrupts the user's reward-withdrawal accounting: subsequent `WithdrawRewardProcessor.execute()` calls (`LongMath.checkedAdd(oldBalance, allowance)`) would compute an incorrect balance delta, either destroying legitimately earned reward or producing inconsistent account state — an accounting-corruption/DoS-on-withdrawal condition directly analogous to the `yIntercept` overflow preventing vault LPs from withdrawing their true share.

### Likelihood Explanation
Reachability is high in principle: `withdrawReward`/`adjustAllowance` is exercised by any account voting and triggering reward-cycle rollovers via ordinary broadcast transactions/contract calls, with no privileged role required. However, actually driving `allowance` (denominated in SUN) past `Long.MAX_VALUE` (~9.2×10^18) requires reward accrual far beyond TRX's realistic total-supply-bounded emission, so — as with the original report's caveat about "high precision tokens" — practical feasibility under current TRX economics is low; it remains a latent defect that could bite if reward parameters, decimals, or emission bounds change, or is intrinsically unsafe compared to the checked-arithmetic pattern used everywhere else in this codebase.

### Recommendation
Replace the unchecked `allowance + amount` in `VoteRewardUtil.adjustAllowance` (and the equivalent code in `MortgageService.adjustAllowance`) with `Math.addExact`/`LongMath.checkedAdd`, consistent with `RepositoryImpl.addBalance` and `Commons.adjustBalance`, so an overflow throws rather than silently wrapping the account's reward accounting.

### Proof of Concept
1. Enable TVM vote rewards (`VMConfig.allowTvmVote()` true) and have an account vote for a validator across many reward cycles without ever calling the balance-withdrawal step that resets `allowance` to `0`.
2. Each cycle rollover invokes `VoteRewardUtil.withdrawReward` → `adjustAllowance(address, reward, repository)`, which does `accountCapsule.setAllowance(allowance + amount)` with no overflow check.
3. If cumulative `allowance` is driven near/above `Long.MAX_VALUE` (e.g., via crafted `DelegationStore` VI values feeding `computeReward`'s `BigInteger` result truncated into a `long`), the stored `allowance` wraps to a negative value.
4. A later `withdrawreward` call computes `LongMath.checkedAdd(oldBalance, allowance)` using the corrupted (possibly negative) `allowance`, permanently misreporting/losing the account's true reward balance.

```java
  private static void adjustAllowance(byte[] address, long amount, Repository repository) {
    if (amount <= 0) {
      return;
    }
```

```java
  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
```

```java
  public static void adjustBalance(AccountStore accountStore, AccountCapsule account, long amount,
                                   boolean useStrict)
      throws BalanceInsufficientException {

    long balance = account.getBalance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && balance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, balance: %d, amount: %d",
              StringUtil.createReadableString(account.createDbKey()), balance, -amount));
    }
    account.setBalance(addExact(balance, amount, useStrict));
    accountStore.put(account.getAddress().toByteArray(), account);
  }
```

```java
  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }
```
