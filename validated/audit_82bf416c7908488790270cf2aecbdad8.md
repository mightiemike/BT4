### Title
Permissionless Declare flood can exhaust the process-global `declare_compilation_semaphore`, blocking all legitimate Declare submissions - (File: crates/apollo_gateway/src/gateway.rs)

### Summary
The `Voter.sol` bug let an unprivileged actor permissionlessly fill a small, fixed-capacity, permission-less slot list (`MAX_BRIBES_PER_POOL = 5`) with worthless registrations, permanently denying legitimate registrations for the affected pool/period. The apollo Gateway has a structurally analogous fixed-capacity, permissionless resource: the `declare_compilation_semaphore`, sized to `max_concurrent_declare_compilations` (default `40`), which any transaction sender can occupy before any real cost (fee/signature/nonce) is verified.

### Finding Description
In `GenericGateway::add_tx_inner` [1](#0-0) , the only checks performed before a Declare transaction acquires a slot on the shared `declare_compilation_semaphore` are `check_declare_permissions` (an allow-list that is empty/disabled by default — permissionless) and `stateless_tx_validator.validate(&tx)`. `StatelessTransactionValidator::validate` [2](#0-1)  performs only syntactic checks: field-size limits, DA-mode, Sierra version, calldata/signature length, contract bytecode/class-object size limits, and entry-point sort order. It does **not** verify the transaction signature, verify that `sender_address` is a real deployed account, check account balance/fee sufficiency, or validate the nonce — all of that happens only in stateful validation, which runs strictly after the compilation permit is acquired and dropped:

The comment in the code itself acknowledges the intent — bound concurrent Sierra-to-CASM compilations — but the semaphore is process-global and shared across *all* callers/senders [3](#0-2) , with a small default capacity of 40 [4](#0-3) . Since the permit only requires passing cost-free, signature-free stateless checks, an attacker can submit `max_concurrent_declare_compilations` (or more, from many distinct forged `sender_address` values, since address realness is never checked pre-permit) concurrent Declare transactions with maximal-size Sierra programs (up to `max_contract_bytecode_size` / `max_contract_class_object_size`), each of which occupies a slot for the full duration of the Sierra-to-CASM compilation. While these slots are held, any legitimate Declare transaction (real developer deploying a genuine contract) is immediately rejected with `too_many_concurrent_declare_compilations` [5](#0-4) . The attacker can repeat this continuously and for free (rejected/garbage Declares never reach the mempool, so no fee is ever charged), sustaining a persistent denial of Declare-transaction admission for the whole gateway/node.

This directly mirrors the `Voter.sol` bug class: a bounded, shared resource meant to gate a legitimate registration action (bribe rewarder registration ↔ Declare-compilation slot) that is filled permissionlessly by cheap/worthless submissions from unprivileged senders, before any deposit/fee/ownership check is enforced, denying service to genuine users of that same resource.

### Impact Explanation
This is a real availability impact reachable purely by unprivileged transaction submission: it can make a sequencer/gateway instance unable to admit any new Declare transactions for as long as the attacker sustains the flood, which is a network-unable-to-confirm-new-transactions scenario for an entire transaction type. It does not cause loss of funds or wrong state commitments, but it satisfies the "network unable to confirm new transactions" acceptance criterion for the Declare transaction class.

### Likelihood Explanation
High likelihood: the attack requires no special privileges, no valid account state, no real fee payment (the flood transactions are rejected before mempool admission and thus never consume fee), and no coordination with sequencer/validator operators — only crafting maximal-size Sierra programs and sending them concurrently to the gateway RPC endpoint. `max_concurrent_declare_compilations` defaults to a small number (40) [4](#0-3) , making the required concurrency modest.

### Recommendation
Perform a minimal stateful/economic check (e.g. that `sender_address` is a real deployed account with sufficient balance/fee for the declared resource bounds, or require a valid signature) before acquiring the compilation permit, so that occupying a compilation slot costs the attacker real, chargeable resources instead of being free. Alternatively, apply per-sender-address or per-IP rate limiting on concurrent Declare compilation attempts so a single unauthenticated actor cannot consume the entire process-global semaphore.

### Proof of Concept
1. Craft `N = max_concurrent_declare_compilations` (default 40) distinct `RpcDeclareTransaction::V3` payloads, each with a unique but never-deployed `sender_address`, a Sierra program near `max_contract_bytecode_size`, valid DA modes (L1/L1), empty `account_deployment_data`/`paymaster_data`, and resource bounds satisfying `validate_resource_bounds` (no real funds needed — bounds are just numeric fields).
2. Fire all `N` `add_tx` calls concurrently at the gateway. Each passes `check_declare_permissions` (no allow-list configured) and `stateless_tx_validator.validate` (purely syntactic), then acquires a permit on `declare_compilation_semaphore` and enters `convert_rpc_tx_to_internal_and_executable_txs` (Sierra-to-CASM compilation) [6](#0-5) .
3. While these N compilations are in flight, submit a legitimate Declare transaction from a real, funded account — it receives `StarknetError::too_many_concurrent_declare_compilations()` immediately [7](#0-6) , confirming the DoS. The existing test `test_declare_compilation_concurrency_limit` [8](#0-7)  demonstrates the mechanism (with a limit of 1) and can be trivially adapted to show unprivileged, cost-free exhaustion of the default-40 limit by garbage/duplicate Declare submissions.
