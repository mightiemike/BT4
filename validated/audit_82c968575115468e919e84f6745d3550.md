### Title
Shielded transaction bandwidth exemption allows cheap CPU-cost amplification via zk-SNARK verification - ([File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java])

### Summary
`BandwidthProcessor.consume` explicitly `continue`s for `ShieldedTransferContract` before any bandwidth accounting is applied, meaning shielded transactions never consume net/bandwidth resources like ordinary transactions do. Meanwhile, `ShieldedTransferActuator.validate()` unconditionally performs expensive native zk-SNARK verification (`librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck`) for every submitted shielded transaction, creating an asymmetry between the (near-zero, fixed) bandwidth cost and the actual CPU cost imposed on every validating node.

### Finding Description
In `BandwidthProcessor.consume` [1](#0-0) , the loop over contracts in a transaction skips all subsequent bandwidth-accounting logic (`useAssetAccountNet`, `useAccountNet`, `useFreeNet`, `useTransactionFee`, `trace.setNetBill`) entirely for `ShieldedTransferContract` type contracts, which normally would meter and charge bandwidth/energy proportional to transaction size and processing cost [2](#0-1) .

Meanwhile, `ShieldedTransferActuator.validate()` is reached during transaction pre-validation (before/at broadcast acceptance) and unconditionally calls `checkProof()`, which — for a transaction not already cached in `ZKProofStore` — invokes up to 1 `librustzcashSaplingCheckSpend`, up to 2 `librustzcashSaplingCheckOutput`, and 1 `librustzcashSaplingFinalCheck` native call, each involving elliptic-curve pairing operations that are CPU-intensive [3](#0-2) . This work happens regardless of whether bandwidth/net was charged.

The only economic cost paid by the attacker is the fixed fee returned by `calcFee()`, which is `getShieldedTransactionFee()` (or `getShieldedTransactionCreateAccountFee()` when creating a new destination account) [4](#0-3)  — a fixed, non-CPU-proportional cost, unlike bandwidth/energy metering which is supposed to reflect real resource consumption for ordinary contracts like `TransferContract`.

Existing mitigations are limited: `checkProof` caches the verification result in `ZKProofStore` keyed by transaction ID [5](#0-4) , but this only prevents re-verifying the *same* transaction twice; it does nothing to stop an attacker from generating and broadcasting many *distinct* valid shielded transactions, each of which forces a fresh full zk-proof verification pass on every node in the network at broadcast time and again at block-inclusion time, while paying only the fixed fee and no proportional bandwidth cost.

### Impact Explanation
This matches TRON's "DoS via the TRON protocol implementation" bounty impact class. An attacker who can generate valid shielded proofs (a normal capability of any accountholder participating in the shielded pool — no privileged role is required) can submit a stream of distinct `ShieldedTransferContract` transactions that consume disproportionate CPU relative to the flat fee charged and the near-zero bandwidth billed, unlike equivalent-size `TransferContract` transactions which are metered by bandwidth/energy in proportion to real work. This can be used to degrade transaction processing throughput of full nodes/witnesses that must validate the mempool and blocks.

### Likelihood Explanation
Preconditions are met by default in current mainnet configuration (`dynamicStore.supportShieldedTransaction()==true`), and the attacker needs only a funded account (to pay the fixed shielded fee and provide balance for `transparent_from` amount) or an existing shielded note to construct spend/receive descriptions. Constructing valid zk-proofs does require the attacker to do proof-generation work off-chain, which is nontrivial but well within reach of an unprivileged actor using the standard Sapling proving libraries already used by wallets; this is a one-time cost per transaction that is then amplified across every validating node in the network, which is the classic verification-asymmetry pattern exploited by these kinds of DoS vectors.

### Recommendation
Charge bandwidth/energy or a proportional fee for `ShieldedTransferContract` commensurate with the CPU cost of Sapling proof verification, instead of unconditionally exempting it in `BandwidthProcessor.consume`. Consider either: (1) removing the blanket `continue` for `ShieldedTransferContract` and applying appropriate net/energy billing reflecting the fixed cost of one spend + up to two receive verifications, or (2) significantly raising and dynamically adjusting `getShieldedTransactionFee()`/`getShieldedTransactionCreateAccountFee()` to reflect real verification cost, combined with rate-limiting the number of shielded transactions accepted into the mempool per time window per source.

  private void checkProof(List<SpendDescription> spendDescriptions,
      List<ReceiveDescription> receiveDescriptions, long fee) throws ZkProofValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    ZKProofStore proofStore = chainBaseManager.getProofStore();
    if (proofStore.has(tx.getTransactionId().getBytes())) {
      if (proofStore.get(tx.getTransactionId().getBytes())) {
        return;
      } else {
        throw new ZkProofValidateException("record is fail, skip proof", false);
      }
    }

    byte[] signHash = getShieldTransactionHashIgnoreTypeException(tx.getInstance());

    if (CollectionUtils.isNotEmpty(spendDescriptions)
        || CollectionUtils.isNotEmpty(receiveDescriptions)) {
      long ctx = JLibrustzcash.librustzcashSaplingVerificationCtxInit();
      try {
        for (SpendDescription spendDescription : spendDescriptions) {
          if (!JLibrustzcash.librustzcashSaplingCheckSpend(
              new CheckSpendParams(ctx,
                  spendDescription.getValueCommitment().toByteArray(),
                  spendDescription.getAnchor().toByteArray(),
                  spendDescription.getNullifier().toByteArray(),
                  spendDescription.getRk().toByteArray(),
                  spendDescription.getZkproof().toByteArray(),
                  spendDescription.getSpendAuthoritySignature().toByteArray(),
                  signHash)
          )) {
            throw new ZkProofValidateException("librustzcashSaplingCheckSpend error", true);
          }
        }

        for (ReceiveDescription receiveDescription : receiveDescriptions) {
          if (receiveDescription.getCEnc().size() != ZC_ENCCIPHERTEXT_SIZE
              || receiveDescription.getCOut().size() != ZC_OUTCIPHERTEXT_SIZE) {
            throw new ZkProofValidateException("Cout or CEnc size error", true);
          }
          if (!JLibrustzcash.librustzcashSaplingCheckOutput(
              new CheckOutputParams(ctx,
                  receiveDescription.getValueCommitment().toByteArray(),
                  receiveDescription.getNoteCommitment().toByteArray(),
                  receiveDescription.getEpk().toByteArray(),
                  receiveDescription.getZkproof().toByteArray())
          )) {
            throw new ZkProofValidateException("librustzcashSaplingCheckOutput error", true);
          }
        }

        long valueBalance;
        long totalShieldedPoolValue = dynamicStore
            .getTotalShieldedPoolValue();
        try {
          valueBalance = addExact(subtractExact(
              shieldedTransferContract.getToAmount(),
              shieldedTransferContract.getFromAmount()), fee);
          totalShieldedPoolValue = subtractExact(
              totalShieldedPoolValue, valueBalance);
        } catch (ArithmeticException e) {
          logger.debug(e.getMessage(), e);
          throw new ZkProofValidateException(e.getMessage(), true);
        }

        if (totalShieldedPoolValue < 0) {
          throw new ZkProofValidateException("shieldedPoolValue error", true);
        }

        if (!JLibrustzcash.librustzcashSaplingFinalCheck(
            new FinalCheckParams(ctx,
                valueBalance,
                shieldedTransferContract.getBindingSignature().toByteArray(),
                signHash)
        )) {
          throw new ZkProofValidateException("librustzcashSaplingFinalCheck error", true);
        }
      } catch (ZksnarkException e) {
        throw new ZkProofValidateException(e.getMessage(), true);
      } finally {
        JLibrustzcash.librustzcashSaplingVerificationCtxFree(ctx);
      }
    }

    recordProof(tx.getTransactionId(), true);
  }
