### Title
Unsanitized control characters/arbitrary bytes accepted in on-chain account name, asset description, and witness/asset URL fields enable output/log injection - (`actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`)

### Summary
`TransactionUtil` performs only length checks — not character/format validation — on several user-supplied byte strings that get written into permanent blockchain state via broadcastable transactions: account name (`AccountUpdateContract`), asset description (`AssetIssueContract`/`UpdateAssetContract`), and witness/asset URLs (`WitnessCreateContract`, `WitnessUpdateContract`, `AssetIssueContract.url`). These fields are later returned verbatim by the node's RPC/HTTP APIs and consumed by wallets, explorers, and CLI tooling, which is exactly the bug class described in the external report (Rocketpool timezone/email fields only length-checked, enabling control-character/format injection into downstream consumers).

### Finding Description
`TransactionUtil.validAccountName`, `validAssetDescription`, and `validUrl` all delegate to `validBytes`, which only checks a maximum length and (for descriptions/urls) allow-empty — it performs no character-class restriction: [1](#0-0) 

This is in contrast to `validAccountId`, `validAssetName`, and `validTokenAbbrName`, which route through `validReadableBytes` and explicitly reject any byte outside the printable ASCII range `0x21`–`0x7E`: [2](#0-1) 

Because `validAccountName`/`validAssetDescription`/`validUrl` use the permissive `validBytes` path, an attacker can broadcast:
- `AccountUpdateContract` with an `account_name` containing newlines, carriage returns, ANSI escape sequences, or other control characters — validated and stored by `UpdateAccountActuator.validate()`/`execute()`: [3](#0-2) [4](#0-3) 

- `AssetIssueContract` with a `description`/`url` containing the same kind of unsanitized bytes, validated via `TransactionUtil.validAssetDescription`/`validUrl`: [5](#0-4) 

- `WitnessCreateContract`/`WitnessUpdateContract` URLs, which are similarly length-only validated (tests explicitly confirm arbitrary hex/byte content up to 256 bytes is accepted with no character restriction): [6](#0-5) 

These fields are exposed unmodified through the node's RPC/HTTP API surface — e.g. `RpcApiService.updateAccount2`, `updateAsset`, and equivalents — and are flagged in `HttpSelfFormatFieldName` as fields requiring special hex/byte handling on the HTTP layer, confirming they are treated as raw/opaque byte blobs end-to-end rather than validated text: [7](#0-6) [8](#0-7) 

Any client (block explorer, wallet, exchange back office, monitoring dashboard, terminal-based tooling) that reads `account_name`, asset `description`, or witness/asset `url` from `GetAccount`, `ListWitnesses`, `GetAssetIssueList`, etc., and displays them via string concatenation/`printf`-style output without its own sanitization will render attacker-controlled control characters, potentially spoofing displayed balances/status lines, corrupting terminal output, or enabling injection into HTML/log/SQL sinks if the consuming application does not additionally validate.

### Impact Explanation
This does not compromise TVM execution, consensus, or resource accounting directly, but it allows any unprivileged account (with sufficient TRX/bandwidth for the relevant fee) to permanently write attacker-controlled, unsanitized byte content into on-chain state fields that are documented and expected to be human-readable text (account name, description, URL). Because java-tron's own APIs are the primary distribution channel for this data to third-party wallets/explorers, the node is the root cause of downstream terminal/log/UI injection risks across the ecosystem — mirroring exactly the impact class in the referenced Rocketpool report (falsified balance/status text, control-character/log injection, XSS-style injection in web consumers).

### Likelihood Explanation
High reachability: any account holder can trivially construct and broadcast an `AccountUpdateContract`, `AssetIssueContract`, `UpdateAssetContract`, `WitnessCreateContract`, or `WitnessUpdateContract` with raw bytes (e.g. via `TriggerConstantContract`-style raw protobuf construction or direct gRPC/HTTP calls) since only byte-length constraints are enforced. No special privilege or malicious peer/node behavior is required — this is reachable from a normal broadcast transaction.

### Recommendation
Apply the same `validReadableBytes`-style (or UTF-8 printable/whitelist) character validation currently used for `validAccountId`/`validAssetName`/`validTokenAbbrName` to `validAccountName`, `validAssetDescription`, and `validUrl` in `TransactionUtil`, rejecting control characters (`< 0x20`, `0x7F`, and other non-printable/format characters) while still allowing UTF-8 text as appropriate for display fields. Additionally, ensure any node-side logging or debug output that echoes these fields is defensively sanitized (encode/strip CR/LF and non-printables) regardless of the storage-level fix, and document in developer-facing security guidance that these fields are attacker-controlled and must be sanitized again by any consuming application before display.

### Proof of Concept
1. Build an `AccountUpdateContract` with `account_name` set to bytes including `\r\n` and other control characters, e.g. `"Balance: 1000000 TRX\r\nStatus: Trusted\x1b[31m"`.
2. Sign and broadcast the transaction; `UpdateAccountActuator.validate()` only calls `TransactionUtil.validAccountName`, which enforces only a ≤200-byte length check and accepts the payload as-is.
3. Query the node's `GetAccount` RPC/HTTP endpoint for the account; the raw unsanitized bytes are returned verbatim in `account_name`.
4. Any wallet/explorer that prints this field directly to a terminal or renders it in HTML without its own sanitization will display the injected/falsified content or execute the control sequences, replicating the Rocketpool-class terminal/output injection issue at the java-tron node level. The same technique applies to `description`/`url` fields via `AssetIssueContract`/`UpdateAssetContract`/`WitnessCreateContract`/`WitnessUpdateContract`.

  private static boolean validReadableBytes(byte[] bytes, int maxLength) {
    if (ArrayUtils.isEmpty(bytes) || bytes.length > maxLength) {
      return false;
    }
    // b must be readable
    for (byte b : bytes) {
      if (b < 0x21) {
        return false; // 0x21 = '!'
      }
      if (b > 0x7E) {
        return false; // 0x7E = '~'
      }
    }
    return true;
  }
