### Title
Deploy syscall in the Starknet OS always asserts `failure_flag=0` regardless of constructor execution outcome, and explicitly requires constructor reverts to be impossible — ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo], [File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/deploy_contract.cairo])

### Summary
The external report describes a Solidity Timelock contract that calls `_executeTransaction()`, ignores its boolean success/failure result, and unconditionally treats the call as successful — resetting queue state and emitting `TransactionExecuted` even when the inner call actually failed. The analogous bug class ("failure of a sub-call is not propagated/checked, and the caller commits state or reports success unconditionally") is reachable in the Starknet OS's `deploy` syscall handling, which is directly triggerable by any contract deployer via the `deploy` syscall (also used implicitly by `DeployAccount` transactions and any contract calling `deploy_from_zero`/deploy).

### Finding Description
In `execute_deploy` (`crates/apollo_starknet_os_program/.../execution/syscall_impls.cairo:456-560`), the OS invokes the constructor via `deploy_contract`, then unconditionally writes:
```
// TODO(Yoni, 1/1/2026): support failures.
assert [response_header] = ResponseHeader(gas=remaining_gas, failure_flag=0);
``` [1](#0-0) 

The `deploy_contract` function itself (`crates/apollo_starknet_os_program/.../execution/deploy_contract.cairo:81-92`) invokes the constructor and then hard-asserts that no revert occurred:
```
let (is_reverted, retdata_size, retdata, _is_deprecated) = select_execute_entry_point_func(...)
...
// The deprecated deploy syscalls do not support reverts.
assert is_reverted = 0;
``` [2](#0-1) 

This mirrors the reported pattern exactly: the caller (`execute_deploy`) never inspects the actual outcome of the sub-execution and instead hardcodes a "success" response (`failure_flag=0`), while the deeper function (`deploy_contract`) additionally *forces* the assumption that failure is impossible via a bare `assert is_reverted = 0`. Compare this to the correctly-implemented `contract_call_helper` used for `CALL_CONTRACT`/`LIBRARY_CALL`, which does propagate `is_reverted` into the response header:
```
assert [response_header] = ResponseHeader(gas=remaining_gas, failure_flag=is_reverted);
``` [3](#0-2) 

The blockifier (Rust) side, by contrast, correctly threads through failure: in `deploy` (`crates/blockifier/src/execution/native/syscall_handler.rs:364-394` and `crates/blockifier/src/execution/syscalls/hint_processor.rs:566-584`), a failed constructor is surfaced as an error/failed `CallInfo`, and `snos_syscall_executor.rs` even checks `execution.failed` and returns a `Revert` explicitly:
```
if execution.failed {
    let revert_data = RevertData::new_temp(execution.retdata.0.clone());
    return Err(SnosSyscallError::Revert(revert_data));
};
``` [4](#0-3) 

This shows that the "OS program" side (the actual Cairo OS logic executed and proven, `apollo_starknet_os_program`) is the one that hardcodes non-failure, in explicit contradiction with the blockifier's ability to produce a failed/reverted constructor call. If blockifier allows an account's `deploy` syscall constructor to fail/revert while charging/consuming gas normally (i.e., not causing the entire calling transaction to revert), but the corresponding Starknet OS re-execution (Cairo program used by the prover) asserts `is_reverted = 0` unconditionally, then a real chain event (failed constructor) cannot be faithfully re-executed/proven by the OS — the OS assertion would fail, halting proof generation, or, if the blockifier's actual execution semantics differ from what the assertion assumes, this creates a divergence between the components responsible for committing state (blockifier) and the component responsible for proving/verifying that state transition (Starknet OS).

### Impact Explanation
This falls under "honest-node divergence" / "network unable to confirm new transactions": if a contract deployer causes the deployed contract's constructor to fail (e.g., a revert inside the constructor) via a legitimate `deploy` syscall call, the actual sequencer/blockifier execution can process this as a failed inner call, but the accompanying OS re-execution used for proof generation asserts `is_reverted = 0`, which would abort/fail the OS execution for a transaction that the blockifier successfully executed on-chain. This can stall block proving or force disagreement between the state that was actually committed by the sequencer and what the OS/prover computes, which can halt the network's ability to finalize/confirm blocks containing such transactions.

### Likelihood Explanation
Reachable directly and trivially by any unprivileged transaction sender: any account contract (or any contract with a `deploy` syscall) can attempt to deploy a contract whose constructor deliberately reverts. This does not require special privileges, a malicious sequencer, or p2p manipulation — a single crafted transaction calling `deploy` with a reverting constructor is sufficient to trigger the divergent code paths. The explicit `TODO(Yoni, 1/1/2027): handle failures` and `TODO(Yoni, 1/1/2026): support failures` comments in the source confirm this is a known, currently-unhandled limitation rather than a hypothetical.

### Recommendation
Ensure the OS-side `deploy_contract`/`execute_deploy` implementation matches the blockifier's actual constructor-failure semantics:
- If blockifier's deploy syscall genuinely cannot produce a reverted constructor without reverting the entire calling transaction, add explicit protocol-level enforcement (in the Cairo/native syscall handler) that prevents such a state from ever reaching the OS, and document/verify this invariant with tests.
- If constructor failures are a legitimate outcome, the OS must propagate `is_reverted`/`failure_flag` faithfully (as `contract_call_helper` already does for `CALL_CONTRACT`), rather than hard-asserting `is_reverted = 0` or writing a hardcoded `failure_flag=0`.
- Add end-to-end/flow tests (in `starknet_os_flow_tests`) that specifically deploy a contract with a reverting constructor and confirm the OS handles this without assertion failure and produces results consistent with blockifier's `TransactionExecutionInfo`.

### Proof of Concept
Not independently verifiable purely via static code reading — reproducing the divergence requires running a full blockifier execution against a constructor that reverts, then re-running the same block through the Starknet OS (`starknet_os_flow_tests`) to observe whether the `assert is_reverted = 0` in `deploy_contract.cairo` triggers a Cairo VM assertion failure, versus whether blockifier's `deploy` syscall path prevents such reverted constructors from occurring at all (e.g., by making the whole transaction revert instead of encoding a `failed=true` CallInfo). This should be confirmed with a background Devin session that can execute the relevant test suites (`starknet_os_flow_tests`, `blockifier/src/execution/syscalls/syscall_tests/deploy.rs`) with a deliberately-reverting constructor contract.
