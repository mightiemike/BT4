Based on the investigation, I found a concrete, self-documented integrity gap that is a direct structural analog to the Derby bug (a completeness check that omits a critical field, allowing a divergent/incorrect state to pass as valid).

### Title
`TransactionOutput::ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, letting replay-verify accept a diverged authenticated state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by the chunk executor and backup/restore tooling to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` fetched from an archive/backup. It checks status, gas, write-set hash, and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually authenticate the Sparse-Merkle-Tree state root at checkpoint boundaries.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks four things: transaction status, gas used, write-set hash (`state_change_hash`), and event root hash. It explicitly does not check the state-root-bearing fields, and the code openly documents this: [2](#0-1) 

This comparator is exactly the same one used by `ChunkExecutor::verify_execution`, the routine invoked by replay-verify tooling (`db-tool`'s `replay_on_archive`, and `TransactionRestoreBatchController`'s verify-execution path) to confirm that locally re-executing archived transactions reproduces the authenticated result: [3](#0-2) 

`TransactionInfoV0`/`TransactionInfoV1` carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` specifically to authenticate the Merkle state root at checkpoint boundaries: [4](#0-3) . These fields are consumed elsewhere as the authoritative state root for verified state views and state-sync bootstrapping — e.g. `VerifiedStateViewAtVersion` binds state reads to `state_checkpoint_hash()` [5](#0-4) , and state-sync's bootstrapper takes `ensure_state_checkpoint_hash()`/`position_state_checkpoint_hash()` as the expected snapshot root to sync to [6](#0-5) . So these hashes are load-bearing for real state-root binding elsewhere in the system, yet the one function responsible for cross-checking re-executed output against the archived/backed-up `TransactionInfo` silently skips them.

By contrast, normal live-node commit path does check the root hash against `LedgerInfo` (`check_and_put_ledger_info`, [7](#0-6) ), so a live validator/full node computing state independently would still catch a divergence through consensus / accumulator root agreement. The gap is specifically in the standalone chunk-executor replay/verify path that re-executes historical transactions against a `TransactionInfo` pulled from backup or archive without independently re-deriving/comparing the checkpoint state root.

### Impact Explanation
If a stored/backed-up `TransactionInfo`'s `state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) does not match what local VM re-execution actually produces — whether due to a backup/archive data corruption, a bug in state materialization, or a hard-fork-only VM divergence — `verify_execution`/`ensure_match_transaction_info` will not detect it. The replay-verify tool (used to validate archive/backup integrity, and used as `VerifyExecutionMode` in restore flows) will report success even though the authenticated state root diverges from what local execution computed. This is exactly the class of impact called out in scope: "Wrong ... state proof accepted as valid" / "Hard-fork-only divergence during ... replay ... accepted as valid," because the tool whose entire purpose is to catch such divergence has an explicit blind spot for the state-root fields.

### Likelihood Explanation
This isn't a theoretical composition — it's an already-known, in-repo-documented gap (the TODO literally states db-tool's `replay_on_archive` "can report a successful replay even when the authenticated position state root diverges from local execution"). It reliably triggers whenever `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or generally state-checkpoint-hash divergence) is exercised through the standard verify-execution/replay-verify code path, with no additional privileged access required — it's inherent in the tool's normal operation.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` from the locally computed checkpoint result against the corresponding fields on `txn_info`, whenever the checkpoint boundary applies (i.e., when the given transaction is a checkpoint boundary in `to_commit`). This closes the gap before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/similar reliance on replay-verify as an integrity guarantee.

### Proof of Concept
1. Take an authenticated `TransactionInfo` from backup/archive where `state_checkpoint_hash` (or `position_state_checkpoint_hash`) has been corrupted/tampered independently of `write_set`/`events`/`status`/`gas_used` (these remain self-consistent and correctly hashed against the transaction's own write set/events).
2. Run `TransactionRestoreBatchController`/chunk-executor `verify_execution` (as used by `replay_on_archive`) against this manifest.
3. `ensure_match_transaction_info` passes because it only checks `status`, `gas_used`, `write_set_hash`, and `event_root_hash` — never touching `state_checkpoint_hash`.
4. The replay-verify tool reports success despite the state root diverging from the true post-execution SMT root, defeating the purpose of the verification pass.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn verified_state_view_at_version(
        &self,
        version: Option<Version>,
        ledger_info: &LedgerInfo,
    ) -> StateViewResult<DbStateView> {
        let db = self.clone();

        if let Some(version) = version {
            let txn_with_proof =

            Ok(DbStateView {
                db,
                version: Some(version),
                maybe_verify_against_state_root_hash: Some(state_root_hash),
            })
        } else {
            Ok(DbStateView {
                db,
                version: None,
                maybe_verify_against_state_root_hash: None,
            })
        }

    /// The expected snapshot root for the given kind at the target version, read
    /// from the target transaction info: main state's state checkpoint hash, or
    /// the committed position state root (guaranteed present once the position
    /// stage runs, per `snapshot_kind_applies_to_target`). All kinds share the
    /// target version, so this is taken from the target output, not a storage read.
    fn expected_snapshot_root(&mut self, kind: StateKind) -> Result<HashValue, Error> {
        let transaction_output_to_sync = self.get_transaction_output_to_sync()?;
        let target_transaction_info = transaction_output_to_sync
            .get_output_list_with_proof()
            .proof
            .transaction_infos
            .first()
            .ok_or_else(|| {
                Error::UnexpectedError("Target transaction info does not exist!".into())
            })?;
        match kind {
            StateKind::MainState => target_transaction_info
                .ensure_state_checkpoint_hash()
                .map_err(|error| {
                    Error::UnexpectedError(format!(
                        "State checkpoint must exist! Error: {:?}",
                        error
                    ))
                }),
            StateKind::Position => target_transaction_info
                .position_state_checkpoint_hash()
                .ok_or_else(|| Error::UnexpectedError("Missing position state root!".into())),
        }
