### Title
Inconsistent duplicate-`shop`-parameter parsing in `callback()` allows the HMAC-validated shop to diverge from the shop actually used for token exchange/session creation - (File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts)

### Summary
In `callback()`, the `shop` value used for the actual access-token request and session creation (`query.get('shop')`, which returns the **first** occurrence per the `URLSearchParams` spec) is derived differently than the `shop` value that is HMAC/state-validated (`authQuery.shop`, built via `Object.fromEntries(query.entries())`, which keeps the **last** occurrence for duplicate keys). By appending a duplicate `shop` query parameter to an otherwise legitimately-signed callback URL, an attacker can make the code validate the HMAC/state against one shop while performing the token exchange and creating the session against a different, attacker-chosen shop string.

### Finding Description
`callback()` extracts the shop value twice, using two different, inconsistent methods: [1](#0-0) 

- `shop = query.get('shop')!` uses `URLSearchParams.get()`, which per spec returns the **first** value for a repeated key.
- `authQuery = Object.fromEntries(query.entries())` iterates all entries in order and assigns them onto a plain object, so for a duplicated key the **last** value wins and overwrites the first.

`authQuery` (the "last-wins" object) is what gets passed into `validQuery`, which in turn calls `validateHmac(config)(authQuery)`: [2](#0-1) [3](#0-2) 

`validateHmac` → `normalizeQuery` performs no de-duplication for plain (non-`URLSearchParams`) objects when `signator === 'admin'` (dedup/rejection of repeated keys is only enforced for `signator === 'appProxy'`), so `authQuery` is used as-is: [4](#0-3) 

`generateLocalHmac` then strips `hmac`/`signature` and stringifies the remaining keys of `authQuery` (which already contains only the *last* `shop` value, since it's a plain object) via `stringifyQueryForAdmin`: [5](#0-4) 

Because a plain-object key can only hold one value, if the attacker duplicates `shop` as `shop=attacker.example&...&shop=legitimate.example` (attacker value first, legitimate value last, with all other params identical to an authentic previously-issued callback URL), then:
- `authQuery.shop` = `legitimate.example` (last-wins) — this exactly reproduces the original signed query, so `generateLocalHmac` recomputes the same `hmac` that Shopify originally issued, and `validateHmac` (and thus `validQuery`) **passes**.
- Later, at line 194, `cleanShop = sanitizeShop(config)(query.get('shop')!, true)!` re-reads the raw `URLSearchParams`, which returns the **first** value, `attacker.example`. [6](#0-5) 

As a result, the access-token POST request is sent to `https://attacker.example/admin/oauth/access_token`, and the `Session` object is created with `shop: cleanShop` = `attacker.example`, even though the HMAC/state authenticity check was performed and passed against `legitimate.example`. The library's own authenticity invariant — "the shop we validate is the shop we act on" — is broken purely by duplicate-parameter parsing inconsistency, requiring no secret and no privileged access; the attacker only needs to be able to submit a modified query string to their app's own callback endpoint (a plain GET request, which is directly attacker-reachable).

### Impact Explanation
This breaks the binding between the cryptographically-validated query and the shop the code subsequently acts on, matching the "OAuth callback processed for/against wrong shop" scoped impact. In the strict sense, the resulting `Session` object is created with `shop = attacker.example` while everything else (state cookie CSRF token, HMAC) was validated against `legitimate.example`'s data — this is a genuine authenticity/binding failure inside the library, independent of whether Shopify's backend would separately reject the mismatched code-vs-shop token exchange. At minimum this is a session/shop-confusion bug that can corrupt session storage with attacker-controlled shop identifiers derived from a request that only proves authenticity for a *different* shop, and in embedded/multi-tenant app scenarios could lead to state/log/session-storage confusion across tenants.

### Likelihood Explanation
No privileged access, no secret, and no non-default configuration are required. The attacker simply needs to be able to send a GET request with a crafted query string to the app's own `/callback` (or configured callback path) endpoint — trivial to do since OAuth callbacks are plain GET requests and the URL is fully attacker-controlled once they intercept or replay a legitimate authorization redirect. The precondition is only "possess one valid, unused callback query (hmac+code+state) for some shop," which is a normal artifact of the standard OAuth flow that any merchant/attacker running the app on their own store already possesses.

### Recommendation
Use a single, consistent method to resolve `shop` throughout `callback()`. Reject the request outright if the `shop` (or any single-value OAuth parameter such as `hmac`, `state`, `code`, `timestamp`) appears more than once in the query string — mirroring the existing `APP_PROXY_SINGLE_VALUE_PARAMS` duplicate-rejection logic in `normalizeQuery`, but applied to the `admin` signator path as well. Then derive both the HMAC-validated shop and the shop used for token exchange/session creation from that same normalized, de-duplicated query object (e.g., always from `authQuery.shop`, never re-reading `query.get('shop')` separately).

```ts
import {shopify} from '../../../__tests__/test-helper';
import {createSHA256HMAC} from '../../../../runtime/crypto';
import {HashFormat} from '../../../../runtime/crypto/types';

test('duplicate shop param lets HMAC-validated shop diverge from acted-upon shop', async () => {
  const legitimateShop = 'legitimate-shop.myshopify.com';
  const attackerShop = 'attacker-shop.myshopify.com';
  const state = 'nonce123';
  const timestamp = Math.floor(Date.now() / 1000).toString();

  // Build the canonical query Shopify would have originally signed for legitimateShop
  const signedParams: Record<string, string> = {
    code: 'real-code-for-legit-shop',
    host: Buffer.from(`${legitimateShop}/admin`).toString('base64'),
    shop: legitimateShop,
    state,
    timestamp,
  };
  const sortedQs = Object.keys(signedParams)
    .sort()
    .map((k) => `${k}=${signedParams[k]}`)
    .join('&');
  const realHmac = await createSHA256HMAC(
    shopify.config.apiSecretKey,
    sortedQs,
    HashFormat.Hex,
  );

  // Attacker prepends a duplicate `shop` before the legitimate one
  const maliciousUrl =
    `/callback?shop=${attackerShop}` +
    `&code=${signedParams.code}` +
    `&hmac=${realHmac}` +
    `&host=${signedParams.host}` +
    `&shop=${legitimateShop}` +
    `&state=${state}` +
    `&timestamp=${timestamp}`;

  // ... issue request with a valid stateFromCookie === state, mock fetchRequestFactory
  // to return a fake access token response, then call shopify.auth.callback(...)

  // Expected (secure) behavior: callback() should THROW (reject duplicate shop param)
  // Actual (vulnerable) behavior: callback() succeeds, and:
  //   - HMAC validation passed using shop = legitimateShop (authQuery, last-wins)
  //   - session.shop === attackerShop (query.get('shop'), first-wins)
  // demonstrating the shop used for authenticity check != shop acted upon.
});
```
Expected assertion in a fixed implementation: `callback()` throws `InvalidOAuthError` (or equivalent) whenever `shop` (or any admin OAuth param) appears more than once in the query string, rather than silently resolving to two different values.

```typescript
function stringifyQueryForAdmin(query: AuthQuery): string {
  const processedQuery = new ProcessedQuery();
  Object.keys(query)
    .sort((val1, val2) => val1.localeCompare(val2))
    .forEach((key: string) => processedQuery.put(key, query[key]));

  return processedQuery.stringify(true);
}

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}

export function generateLocalHmac(config: ConfigInterface) {
  return async (
    params: AuthQuery,
    signator: HMACSignator = 'admin',
  ): Promise<string> => {
    const {hmac: _hmac, signature: _signature, ...query} = params;

    const queryString =
      signator === 'admin'
        ? stringifyQueryForAdmin(query)
        : stringifyQueryForAppProxy(query);

    return createSHA256HMAC(config.apiSecretKey, queryString, HashFormat.Hex);
  };
}
```

```typescript
function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {

          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,

        }

    }

    return query;
```
