### Title
Block/standby rewards credited to a Super Representative are permanently lost when its recorded vote count is zero at cycle-end settlement - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
java-tron's DPoS reward accounting works like a reward-per-share ("Vi") pool, structurally identical to the StakingRewardsV3 `rewardPerLiquidity` pattern flagged in the external report: a reward amount is accrued for a cycle and then divided by the "stake" (vote count) present for that cycle to produce a per-vote reward index (`Vi`). If a witness earns reward in a cycle in which its recorded vote total is `0`, the code silently skips updating `Vi` for that cycle instead of carrying the reward forward or refunding it — the minted reward amount is written to the `reward` key in `DelegationStore` but is never reflected in any voter's payout and can never be claimed by anyone. This is the direct analog of "funds frozen because reward accrued when there is no depositor/stake to receive it."

### Finding Description
The core accrual logic lives in `DelegationStore.accumulateWitnessVi` (also duplicated in `RewardViCalService.accumulateWitnessVi` for backfill): [1](#0-0)

When `reward > 0` but `voteCount == 0` for that cycle, the branch "just forwards" the previous `Vi` unchanged. Because voters' payouts are computed strictly from the delta between two `Vi` snapshots (`endVi.subtract(beginVi)` in `MortgageService.computeReward` / `VoteRewardUtil.computeReward`), an unchanged `Vi` means the reward recorded for that cycle contributes `0` to every voter's payout, forever: [2](#0-1) 

The same class of loss exists in the pre-Vi ("old") algorithm, `MortgageService.computeReward(cycle, votes)`, which explicitly `continue`s (drops) the reward when `totalVote == REMARK || totalVote == 0`: [3](#0-2) 

The reward itself is minted and recorded via `payReward` → `delegationStore.addReward(cycle, witnessAddress, value)` at every block/standby payout (from `payBlockReward`, `payTransactionFeeReward`, `payStandbyWitness`): [4](#0-3) 

and this raw per-cycle reward value is never read again by any other code path except the `Vi` accrual above — once skipped due to `voteCount == 0`, the value is orphaned in the DB, unrecoverable and unclaimed by anyone.

The trigger point is `MaintenanceManager.doMaintenance()`, which is executed automatically every maintenance cycle from ordinary block processing (i.e., reachable purely through normal chain activity — voting/unvoting via broadcast `VoteWitnessContract`/`WithdrawBalanceContract` transactions and block production), and calls `accumulateWitnessVi` with the witness's **current** `voteCount` for every witness returned by `getAllWitnesses()`: [5](#0-4) 

If a witness's recorded vote count reaches `0` in a cycle where it still accrued reward (e.g., all voters withdraw/redirect their votes such that the witness's tallied vote count drops to zero for that settlement window while reward from block production for that same cycle was already recorded), the accrued reward for that cycle becomes permanently stuck: it is not paid to the witness, not paid to any voter, and not returned to the reward pool.

### Impact Explanation
This is an on-chain accounting corruption bug: newly minted TRX reward is computed and recorded but becomes permanently unclaimable, silently shrinking the amount of reward actually distributed versus the amount nominally minted/allocated for a cycle. This is a genuine "funds frozen"/lost-value condition analogous to the reported `rewardPerLiquidity` issue, reachable purely by ordinary voting/unvoting transaction activity — no privileged actor is required.

### Likelihood Explanation
Reaching the exact zero-vote-with-nonzero-reward window requires a specific sequencing of vote withdrawal relative to block production and maintenance-cycle boundaries (the vote count used is the one recorded at the previous maintenance, so a witness must go from actively earning to fully unvoted precisely straddling the settlement of the cycle in which its reward was recorded). This makes it a real but comparatively narrow condition to trigger deterministically, and it does not appear to have been the primary design case tested (existing tests such as `VoteTest.testRewardAlgorithmNo3` verify the "already fully unvoted, zero reward, zero query" case, but do not test the mid-cycle transition case where reward is recorded before vote-count reaches zero).

### Recommendation
When `reward > 0` and `voteCount == 0` for a cycle in `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`, the un-distributable reward should not simply be dropped. Options: (a) roll the un-distributable reward forward into the next cycle's reward pool for the same witness so it is redistributed once votes reappear, or (b) route it back to the witness's own allowance/brokerage as a fallback recipient, mirroring the fix recommended for `StakingRewardsV3-1.sol` (properly handling the reward-per-share calculation when there is no stake to divide by, instead of leaving the numerator un-accounted for).

### Proof of Concept
1. Witness `W` is actively voted for and is producing blocks; `MortgageService.payBlockReward`/`payTransactionFeeReward` call `delegationStore.addReward(cycle, W, value)` during cycle `N`, accumulating a positive `reward` for `W` at cycle `N`.
2. During cycle `N`, all voters broadcast `VoteWitnessContract`/`WithdrawBalanceContract`/re-vote transactions withdrawing their votes for `W`, such that by the time `MaintenanceManager.doMaintenance()` settles cycle `N` (`consensusDelegate.getAllWitnesses().forEach(witness -> delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount()))`), `W.getVoteCount()` reads as `0` for that settlement.
3. `accumulateWitnessVi` takes the `voteCount == 0` branch and does not add the delta `Vi` for cycle `N`, even though `getReward(N, W) > 0`.
4. Any voter who was voting for `W` up through cycle `N` computes their payout via `MortgageService.computeReward`/`VoteRewardUtil.computeReward` using `endVi.subtract(beginVi)`, which is unaffected by the dropped cycle-`N` reward — they receive `0` extra reward for cycle `N`.
5. The value stored under `buildRewardKey(N, W)` in `DelegationStore` is never read again by any withdrawal/query path, so the minted reward for cycle `N` is permanently unclaimable by any account.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
