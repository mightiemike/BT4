## State-Integrity Analog Analysis

I reduced the external bug (a hardcoded constant bound to the wrong real-world entity, silently breaking correctness) to its Aptos-native invariant: **a "match" check that is supposed to bind computed execution output to authenticated ledger data must check every field that participates in the commitment; if it silently skips a field, corrupted/divergent state for that field is accepted as valid.**

I traced 3 candidate paths (write-set `try_combine_into_storage_change_set`, `AccumulatorProof::verify`, `TransactionOutput::ensure_match_transaction_info`) and the third is self-documented as incomplete in the code itself, giving a verifiable local root cause.

### Title
`TransactionOutput::ensure_match_transaction_info` omits state/hot-state/position checkpoint hash comparison, allowing replay-verify and debugger tooling to accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `execution/executor/src/chunk_executor/mod.rs`) to assert that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` pulled from a backup/archive. It explicitly checks `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash`, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) [2](#0-1) 

### Finding Description
`TransactionInfo` commits to the post-transaction world state via `state_checkpoint_hash` (root of the Sparse/Jellyfish Merkle state tree at checkpoint boundaries), and, in the V1 variant, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`: [3](#0-2) 

These fields are the actual state-commitment roots stored per-transaction in the ledger (they feed into `TransactionInfo::hash()`, which is what gets embedded in the transaction accumulator, as constructed in `DoLedgerUpdate::assemble_transaction_infos`): [4](#0-3) 

`ensure_match_transaction_info` is the sole comparator used by tools that re-execute transactions from a `Transaction` list and validate the *locally-computed* `TransactionOutput` against the *previously committed/authenticated* `TransactionInfo` (loaded from backup or archive). It validates 4 of the ~7 commitment fields, and the code contains an explicit acknowledgment of the gap: [5](#0-4) 

Concretely: `replay_on_archive.rs`'s `Verifier::execute_and_verify` re-executes transactions with `AptosVMBlockExecutor` and calls `executed_outputs[idx].ensure_match_transaction_info(...)` against `expected_txn_infos[idx]` sourced straight from the backup: [6](#0-5) 

Because the comparator does not derive/compare the state root that the local re-execution would have produced (via `DoStateCheckpoint`/`LedgerStateSummary` machinery) against `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, any divergence confined to those fields — e.g., a bug in `DoStateCheckpoint::compute_position_checkpoint` (see the position-state SMT extension logic) or in the Jellyfish Merkle apply path that produces a different state root while leaving `write_set`/`events`/`status`/`gas_used` unchanged — is invisible to this check. [7](#0-6) 

By contrast, the normal execution/commit path (`DoStateCheckpoint::get_state_checkpoint_hashes`) does perform this comparison for online block replay, using `ensure!(known[idx] == Some(computed_last_checkpoint_hash), ...)`: [8](#0-7) 

So the true state-root recomputation-and-check logic exists and is exercised in the live commit pipeline, but the offline replay-verification tool bypasses it, using the incomplete `ensure_match_transaction_info` instead. This is exactly analogous to the reported bug pattern: a critical invariant-checking constant/function is silently wrong/incomplete, so the intended safety check does not fire, and downstream consumers (replay-verify, `db-tool`, `aptos-debugger`) get false assurance.

### Impact Explanation
Replay-verify (`storage/db-tool/src/replay_on_archive.rs`, and the `RestoreCoordinator`/`replay_verify.rs` pipeline it backs) is the primary mechanism operators and Aptos Labs use to independently confirm that an archived transaction history, when replayed, produces the exact same ledger state that was originally committed and signed by validators. If a state-root-only divergence (state tree corruption, hot-state tree bug, or the newly-added position-state tree bug) exists in the execution/storage stack, `ensure_match_transaction_info` will report success even though the locally computed state root differs from the authenticated one. This defeats the primary purpose of replay-verify: it is a state-commitment / proof-integrity blind spot that can mask a durable ledger-state corruption or a hard-fork-class divergence during replay, exactly the class of impact called out as in-scope ("committed state that differs from the correct VM result... Hard-fork-only divergence during commit, replay, restore, or proof verification"). The comment in the code itself flags this specifically for the upcoming `COMPUTE_TRADING_NATIVE_STATE_ROOTS` position-state feature, meaning any bug in `DoStateCheckpoint::compute_position_checkpoint`'s incremental SMT extension would go undetected by replay-verify.

### Likelihood Explanation
This is a real, code-confirmed gap rather than a hypothetical: it's called out inline by the developers as a known TODO ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), and I could not find any other call site or wrapper that adds the missing checkpoint-hash comparison before/around `ensure_match_transaction_info` in the traced call sites (`replay_on_archive.rs`, `aptos-debugger`, `cli/src/commands.rs`, `chunk_executor/mod.rs`). The feature flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS` was found in `aptos_features.rs`/`aptosdb_reader.rs`, but I was unable to fully confirm within the remaining budget whether it is currently enabled on mainnet or still dormant — this affects only the position-state-specific portion of the impact; the `state_checkpoint_hash`/`hot_state_checkpoint_hash` gaps are unconditional and apply regardless of that flag.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` (or its callers) to independently recompute the post-transaction state-checkpoint root(s) — reusing the same `DoStateCheckpoint` logic used in live block execution — and assert equality against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()` (for V1), and `position_state_checkpoint_hash()` whenever populated, mirroring the `ensure!(known[idx] == Some(computed_last_checkpoint_hash), ...)` check already present in `DoStateCheckpoint::get_state_checkpoint_hashes`.

### Proof of Concept
Conceptual PoC (I could not execute this given tool constraints, but the code path is directly traceable):
1. Construct a two-transaction chunk where transaction 2 is a checkpoint boundary.
2. Introduce (or simulate) a state-tree apply bug that changes the resulting Jellyfish Merkle root without changing any resource `write_set` entry's value (e.g., a bug purely in the position-state SMT bucket key derivation in `DoStateCheckpoint::compute_position_checkpoint`, lines 90–189, that hashes a `StateKey` incorrectly, producing a different `new_last_checkpoint.root_hash()`network-wide vs. what the original archive recorded).
3. Feed the same transaction list, the corrupted `TransactionOutput`s, and the original archived `TransactionInfo`s into `Verifier::execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` (lines 388–406).
4. Observe: `ensure_match_transaction_info` returns `Ok(())` because it only compares `status`, `gas_used`, `write_set` hash, and `event_root_hash` — none of which reflect the corrupted state-checkpoint root — so replay-verify reports success despite the mismatched ledger-state commitment.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn compute_position_checkpoint(
        execution_output: &ExecutionOutput,
        parent: Option<&LedgerWithSummary<PositionStateWithSummary>>,
        persisted: &ProvablePositionStateSummary,
        known_position_state_checkpoints: Option<Vec<Option<HashValue>>>,
    ) -> Result<(
        LedgerWithSummary<PositionStateWithSummary>,
        Vec<Option<HashValue>>,
    )> {
        let _timer = OTHER_TIMERS.timer_with(&["get_position_checkpoint_hashes"]);

        let num_txns = execution_output.to_commit.len();
        let first_version = execution_output.first_version;
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();
        let base_summary = persisted.summary();
        // No in-memory parent at genesis / first block after enabling: seed
        // from the pre-committed position tip (covers committed writes the
        // merklized snapshot may lag).
        let parent_latest =
            parent.map_or_else(|| persisted.base().latest().clone(), |p| p.latest().clone());
        let parent_last_checkpoint = parent.map_or_else(
            || persisted.base().last_checkpoint().clone(),
            |p| p.last_checkpoint().clone(),
        );

        // Empty chunk: nothing to extend (avoids the `num_txns - 1` underflow).
        if num_txns == 0 {
            let summary = LedgerWithSummary::from_latest_and_last_checkpoint(
                parent_latest,
                parent_last_checkpoint,
            );
            return Ok((summary, vec![]));
        }

        // Collapse position writes (latest-per-key) over a version range into
        // SMT leaf updates.
        let collect = |range: std::ops::Range<usize>| -> Vec<(HashValue, PositionSlot)> {
            let mut latest: HashMap<HashValue, PositionSlot> = HashMap::new();
            for i in range {
                for (key, op) in execution_output.to_commit.transaction_outputs[i]
                    .write_set()
                    .native_position_iter()
                {
                    let value_hash = op.as_write_op().as_state_value_opt().map(StateValue::hash);
                    latest.insert(key.hash(), PositionSlot {
                        state_key: key.clone(),
                        value_hash,
                        value: None,
                    });
                }
            }
            latest.into_iter().collect()
        };

        let (new_latest, new_last_checkpoint) = if let Some(ci) = last_checkpoint_index {
            let checkpoint_version = first_version + ci as u64;
            let new_ckpt = parent_latest.extend(
                checkpoint_version,
                collect(0..ci + 1),
                base_summary,
                persisted,
            )?;
            if ci + 1 == num_txns {
                (new_ckpt.clone(), new_ckpt)
            } else {
                let last_version = first_version + num_txns as u64 - 1;
                let new_latest = new_ckpt.extend(
                    last_version,
                    collect(ci + 1..num_txns),
                    base_summary,
                    persisted,
                )?;
                (new_latest, new_ckpt)
            }
        } else {
            // No checkpoint in this chunk: only the latest advances.
            let last_version = first_version + num_txns as u64 - 1;
            let new_latest = parent_latest.extend(
                last_version,
                collect(0..num_txns),
                base_summary,
                persisted,
            )?;
            (new_latest, parent_last_checkpoint)
        };

        // Per-tx hash vector + known-hash validation (shared with main/hot state).
        let hashes = Self::get_state_checkpoint_hashes(
            execution_output,
            known_position_state_checkpoints,
            new_last_checkpoint.root_hash(),
            "position_state",
        )?;

        let summary =
            LedgerWithSummary::from_latest_and_last_checkpoint(new_latest, new_last_checkpoint);
        Ok((summary, hashes))
