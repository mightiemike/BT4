## Title
Missing slippage/minimum-amount protection in `ExchangeWithdrawContract` (`ExchangeWithdrawActuator`) enables MEV-style value extraction from exchange-pool liquidity withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The TRON on-chain Bancor-style token-pair exchange (`Exchange`/`ExchangeV2`) supports `ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeTransactionContract` (swap) and `ExchangeWithdrawContract` (liquidity/proceeds withdrawal by the pool creator). Unlike the swap contract, which carries an `expected` field enforced at validation time, `ExchangeWithdrawContract` has no equivalent minimum-output parameter, so a withdrawal can be sandwiched/frontrun by a swap transaction that shifts the pool ratio, causing the withdrawer to receive less of the paired asset than intended — directly analogous to the omnipool `remove_liquidity` missing `minimum_amount_out` issue.

### Finding Description
`ExchangeWithdrawContract` only carries `token_id` and `quant` (amount of one side to withdraw); there is no `expected`/minimum-amount-out field: [1](#0-0) 

By contrast, `ExchangeTransactionContract` (a swap) has an `expected` field that is checked in validation (`anotherTokenQuant < tokenExpected` fails): [2](#0-1) [3](#0-2) 

`ExchangeWithdrawActuator.execute` computes `anotherTokenQuant` purely from the *current* pool balances at execution time using the constant-value Bancor-style ratio (`bigSecondTokenBalance * bigTokenQuant / bigFirstTokenBalance`, or the inverse), with no way for the caller to bound the acceptable output: [4](#0-3) 

`doValidate()` similarly recomputes `anotherTokenQuant` from the *validation-time* balances and only checks that the value is `> 0` and reasonably precise — never that it meets any user-specified floor: [5](#0-4) 

Because Java-Tron orders and executes transactions from the mempool/block based on packing logic (not strict submission order), and `ExchangeTransactionContract` (swap) is available to any unprivileged account holding the traded asset, an attacker can broadcast a swap against the same `exchange_id` that shifts `firstTokenBalance`/`secondTokenBalance` immediately before the victim's `ExchangeWithdrawContract` is packed into the same or a following block, changing the ratio used to compute `anotherTokenQuant` at withdrawal time. This mirrors exactly the `remove_liquidity`-without-`minimum_amount_out` bug class described in the external report: the withdrawer has no way to enforce a floor on the amount of paired-asset received.

### Impact Explanation
Any account that is the creator of a TRON exchange pool (this is not a privileged system role — pool creation is open to any account via `ExchangeCreateContract`) is exposed to MEV/sandwich losses when withdrawing accumulated proceeds or liquidity via `ExchangeWithdrawContract`. An attacker can front-run/sandwich the withdrawal with `ExchangeTransactionContract` swaps to shift the pool's internal price just before the withdrawal executes, extracting value from the withdrawer with no bound on the resulting slippage loss (unlike swaps, which are capped by `expected`). This is an accounting/asset-value corruption for the withdrawing user, reachable purely through normal broadcast transactions with no special privileges.

### Likelihood Explanation
Likelihood is moderate-to-high wherever exchange pools have significant balances and mempool visibility of pending `ExchangeWithdrawContract` transactions, since:
- `ExchangeTransactionContract` swaps are unrestricted and callable by anyone with balance in either token.
- Block producers/SRs (or MEV searchers submitting via broadcast) can reorder/insert transactions within a block to front/back-run the withdrawal.
- No on-chain control (unlike the swap's `expected` field) exists to prevent this for withdrawals.

### Recommendation
Add a `minimum_amount_out` (or `expected`) field to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` analogous to the `tokenExpected` check already present in `ExchangeTransactionActuator`: [6](#0-5) 
Reject the withdrawal (`ContractValidateException`) if the computed `anotherTokenQuant` is less than the caller-specified minimum.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from the pool creator (victim) for `exchange_id = X`, withdrawing `tokenQuant` of `firstTokenID`.
2. Attacker broadcasts `ExchangeTransactionContract` selling a large amount of `secondTokenID` for `firstTokenID` in the same exchange, shifting `firstTokenBalance` up and `secondTokenBalance` down (or vice versa), which is unrestricted and requires only holding the relevant asset — see validation path in `ExchangeTransactionActuator.doValidate()`: [7](#0-6) 
3. When the victim's `ExchangeWithdrawContract` executes afterward, `anotherTokenQuant` is recomputed from the now-shifted balances in `ExchangeWithdrawActuator.execute()`: [8](#0-7) 
4. The victim receives a materially different (lower) amount of the paired asset than they would have without the attacker's intervening swap, with no on-chain mechanism to reject the withdrawal for insufficient output — confirming the missing-slippage-check analog to the reported omnipool `remove_liquidity` finding.
