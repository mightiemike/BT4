### Title
Standby-witness reward is split using an unsorted, arbitrarily-truncated witness list instead of the top-N by vote - ([File: consensus/src/main/java/org/tron/consensus/dpos/IncentiveManager.java])

### Summary
`IncentiveManager.reward(List<ByteString> witnesses)` truncates the witness list to `WITNESS_STANDBY_LENGTH` entries and divides the fixed standby-witness allowance pool among the *remaining* entries, proportional to their vote counts. The list it receives, however, is not sorted by vote count — it is built directly from `WitnessStore.getAllWitnesses()`, whose order follows the underlying DB key/iteration order (witness address), not vote rank. This is structurally the same defect as the reported Foundation Market bug: an array meant to represent "the top N recipients" is truncated positionally rather than by rank, so whichever witnesses happen to sort later in the (unsorted) list can receive nothing regardless of how many votes they actually have, while lower-voted witnesses that happen to sort earlier get paid instead.

### Finding Description
`IncentiveManager.reward` is invoked from `MaintenanceManager.doMaintenance()` on every maintenance cycle, in the legacy (`allowChangeDelegation() == false`) reward code path: [1](#0-0) 

The list passed in, `newWitnessAddressList`, is populated purely by iterating `consensusDelegate.getAllWitnesses()` in whatever order the store returns them — no sort by vote count is ever applied before this list reaches `IncentiveManager.reward`: [2](#0-1) [3](#0-2) 

Inside `IncentiveManager.reward`, the truncation and payout logic is: [4](#0-3) 

This is exactly the pattern flagged in the external report: an array is capped at a fixed maximum size (`MAX_ROYALTY_RECIPIENTS_INDEX` in the report, `WITNESS_STANDBY_LENGTH` here) and only the first N entries participate in the payout, with no guarantee that those first N entries are the ones that were actually supposed to receive the largest shares.

Compare this with the *correct* implementation of the same concept elsewhere in the same codebase — `MortgageService.payStandbyWitness()` — which explicitly sorts witnesses by vote count (descending) before truncating to the standby length: [5](#0-4) [6](#0-5) 

The existence of `WitnessStore.getWitnessStandby()` (which does the sort correctly) alongside `IncentiveManager.reward` (which does not) confirms that the sort step was simply omitted in the legacy path, mirroring the root cause described in the report: the truncation logic exists, but it operates on the wrong (unsorted) ordering, so the actual "top vote getters" are not guaranteed to be inside the truncated set.

### Impact Explanation
When the total witness count exceeds `WITNESS_STANDBY_LENGTH`, witnesses with high vote counts that happen to fall outside the first N entries in address/iteration order receive **zero** standby allowance for that maintenance cycle, while lower-voted witnesses that happen to be earlier in the (unsorted) list are paid instead — and the `voteSum` used to compute `eachVotePay`/`pay` is also computed only over the truncated (wrong) subset, so the payout ratios are further skewed. This is direct on-chain fund misallocation of the `WITNESS_STANDBY_ALLOWANCE` pool: some accounts are shorted of reward they are entitled to by vote weight, and other accounts receive reward they should not have received. This is an accounting-corruption class issue reachable purely through ordinary block/maintenance-cycle processing, not requiring a malicious or privileged actor.

Note: this specific reward path is only executed while `allowChangeDelegation()` is `false` (the pre-"new delegation model" legacy branch) — `MortgageService.payStandbyWitness()` is the corresponding correctly-sorted implementation used once `allowChangeDelegation()` is enabled. On networks/chains that have not yet enabled the new delegation model (or during any transitional/private-chain deployment still running the legacy algorithm), this bug is live and affects every maintenance cycle whenever the witness count exceeds 127.

### Likelihood Explanation
Any network can exceed `WITNESS_STANDBY_LENGTH` witnesses simply by many accounts submitting `WitnessCreateContract` transactions (an ordinary, unprivileged transaction type), so the truncation condition is easy to trigger. The bug fires automatically and deterministically every maintenance cycle under that condition — no attacker interaction with a specific transaction is needed once the witness count threshold is crossed. Likelihood is limited only by whether a given deployment is still running with `allowChangeDelegation() == false` (pre-migration/legacy behavior); on chains where that flag has already been switched on (e.g., long-established mainnet), this exact code path is dormant, but the flawed logic remains present and reachable on any chain/testnet/fork that has not enabled or has reset this flag.

### Recommendation
In `IncentiveManager.reward`, sort the incoming `witnesses` list by vote count (descending) — using the same approach as `WitnessStore.sortWitnesses`/`getWitnessStandby` — before truncating to `WITNESS_STANDBY_LENGTH`, so the truncated subset always corresponds to the highest-voted witnesses, consistent with the correct behavior already implemented in `MortgageService.payStandbyWitness()`.

### Proof of Concept
1. Configure/start a chain with `allowChangeDelegation()` returning `false` (legacy reward algorithm active).
2. Create more than `WITNESS_STANDBY_LENGTH` (127) witness accounts via ordinary `WitnessCreateContract` transactions, and have votes cast (via `VoteWitnessContract`) so that some witnesses whose addresses sort *after* the 127th position (in `WitnessStore` iteration order) accumulate very high vote counts, while witnesses sorting within the first 127 positions have low or zero votes.
3. Let a maintenance cycle run (`MaintenanceManager.doMaintenance()` → `incentiveManager.reward(newWitnessAddressList)`).
4. Observe that the high-vote witnesses outside the first 127 positions of `newWitnessAddressList` receive no standby allowance (`accountCapsule.getAllowance()` unchanged), while low-vote witnesses inside the first 127 positions are paid — even though `voteSum`/`pay` computations assume the truncated set represents the top vote-getters.

    List<WitnessCapsule> ret;
    List<WitnessCapsule> all = getAllWitnesses();
    sortWitnesses(all, isSortOpt);
    if (all.size() > Parameter.ChainConstant.WITNESS_STANDBY_LENGTH) {
      ret = new ArrayList<>(all.subList(0, Parameter.ChainConstant.WITNESS_STANDBY_LENGTH));
    } else {
      ret = new ArrayList<>(all);
    }
    // trim voteCount = 0
    ret.removeIf(w -> w.getVoteCount() < 1);
    return ret;

  public void reward(List<ByteString> witnesses) {
    if (consensusDelegate.allowChangeDelegation()) {
      return;
    }
    if (witnesses.size() > WITNESS_STANDBY_LENGTH) {
      witnesses = witnesses.subList(0, WITNESS_STANDBY_LENGTH);
    }
    long voteSum = 0;
    for (ByteString witness : witnesses) {
      voteSum += consensusDelegate.getWitness(witness.toByteArray()).getVoteCount();
    }
    if (voteSum <= 0) {
      return;
    }
    long totalPay = consensusDelegate.getWitnessStandbyAllowance();
    for (ByteString witness : witnesses) {
      byte[] address = witness.toByteArray();
      long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
          / voteSum));
      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);
      consensusDelegate.saveAccount(accountCapsule);
    }
  }

  public void payStandbyWitness() {
    List<WitnessCapsule> witnessStandbys = witnessStore.getWitnessStandby(
        dynamicPropertiesStore.allowWitnessSortOptimization());
    long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
    if (voteSum < 1) {
      return;
    }
    long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
    double eachVotePay = (double) totalPay / voteSum;
    for (WitnessCapsule w : witnessStandbys) {
      long pay = (long) (w.getVoteCount() * eachVotePay);
      payReward(w.getAddress().toByteArray(), pay);
      logger.debug("Pay {} stand reward {}.", Hex.toHexString(w.getAddress().toByteArray()), pay);
    }
  }
