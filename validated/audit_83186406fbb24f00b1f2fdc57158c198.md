### Title
Rounding-down in TRC10 exchange order matching lets a taker fully consume a maker's order while under-paying — accumulated free tokens - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the amount a taker must pay to fully consume a maker's remaining sell order using integer division that always rounds *down* (via `MarketUtils.multiplyAndDivide` → `floorDiv`), while crediting the taker with the maker's *entire* remaining sell quantity. This is the same bug class as the reported `RedemptionPool.receiptToBurn` issue: an amount that should be rounded up (the amount consumed/paid) is instead rounded down, so the payer parts with less value than the goods received are worth, and the difference is retained by the payer's own remaining balance.

### Finding Description
In the "taker == maker" branch: [1](#0-0) 
`makerBuyTokenQuantityReceive` (what the taker pays the maker) is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which internally does `floorDiv`: [2](#0-1) 
Meanwhile `takerBuyTokenQuantityReceive` is set to the maker's *full* `getSellTokenQuantityRemain()` — the entire remaining sell-side asset — with no corresponding rounding-up of the price paid.

The same pattern repeats in the "taker > maker" branch: [3](#0-2) 
Here again `takerBuyTokenQuantityReceive` is the maker's full remaining sell quantity (line 455), but `makerBuyTokenQuantityReceive` — the amount deducted from the taker's own sell-side balance (line 480-481) — is computed with the same floor-dividing `multiplyAndDivide`.

Because the maker's order is fully closed (`setSellTokenQuantityRemain(0)`) and fully paid out to the taker in both cases, but the taker is only debited a floor-rounded amount, the taker systematically retains a few extra units of its own sell-side asset on every partial/complete match where a division remainder exists. This exactly mirrors the reported flaw: an amount that represents "what should be burned/consumed to obtain the delivered assets" is rounded down instead of up, silently inflating the payer's residual balance at the counterparty's expense.

The test suite even acknowledges rounding/accuracy issues in this exact code path (see test names `partMatchMakerLeftNotEnoughBuyOrders1` and comments "(Accuracy problem)"), but only handles the degenerate case where the computed amount rounds down to exactly zero (lines 466-477); it does not address the systemic single/double-unit under-payment on every match.

### Impact Explanation
This is TRC10 asset-exchange (Market) accounting code reachable by any unprivileged user via `MarketSellAssetContract`/`MarketSellAssetActuator`, which is a production, user-facing transaction type. The rounding bias favors the taker (the party initiating `execute`) at the direct expense of maker accounts whose orders get fully closed for a price that is rounded down from the exact fixed-point ratio. Repeated or crafted trades (choosing price ratios that maximize the division remainder, e.g., `makerSellRemainQuantity * makerBuyQuantity` not evenly divisible by `makerSellQuantity`) let an attacker accumulate free tokens/TRX across many trades, draining value from maker liquidity providers — a concrete underpriced-settlement / accounting-drift impact in exchange logic.

### Likelihood Explanation
Medium. Any account can place TRC10 sell orders (maker) and any account can submit a matching sell order (taker) via the public `MarketSellAssetContract`. An attacker can act as both maker and taker (or coordinate with a maker) using self-chosen quantities to force a non-exact division and repeat the match many times to accumulate the discrepancy, similar to how the original report describes repeated partial-fill exploitation. No privileged role is required.

### Recommendation
When computing `makerBuyTokenQuantityReceive` (the amount the taker must pay to obtain the maker's full remaining sell quantity) in both the "taker == maker" and "taker > maker" branches, round the division **up** rather than down (e.g., `ceilDiv` instead of `floorDiv` in `MarketUtils.multiplyAndDivide` for this specific direction), so the taker pays at least the fair-value amount for goods fully received. Alternatively, keep the floor-rounded quantity for `takerBuyTokenQuantityReceive` as well (proportionally reduce what the taker receives) instead of granting it the maker's entire remaining balance while under-charging.

### Proof of Concept
Conceptual PoC (cannot be executed without a live node, but derivable from the code):
1. Maker places a sell order with `sellTokenQuantity` / `buyTokenQuantity` ratio chosen such that `makerSellRemainQuantity * makerBuyQuantity` is not evenly divisible by `makerSellQuantity` (e.g., maker sells 200 unit A for 101 unit TRX after a partial fill leaves `makerSellRemainQuantity = 199`).
2. Attacker (taker) submits a sell order for TRX/A sized so that `takerBuyTokenQuantityRemain >= makerOrderCapsule.getSellTokenQuantityRemain()` (triggers "taker == maker" or "taker > maker" branch) in `matchSingleOrder` (actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:418-482).
3. `takerBuyTokenQuantityReceive` is set to the maker's full 199 units (all of asset A), while `makerBuyTokenQuantityReceive = floor(199 * makerBuyQuantity / makerSellQuantity)` — losing the fractional remainder of TRX that should have been paid.
4. Attacker's own sell-side (TRX) balance is only decremented by the floor-rounded `makerBuyTokenQuantityReceive`, retaining the rounding remainder each time this scenario is triggered; repeating across many orders accumulates a measurable, free surplus of TRX/tokens for the attacker.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
