### Title
Silent truncation via `DataWord.longValue()` diverges from its documented overflow-checked contract, enabling TRC10 token-id/amount confusion in TVM calls - (File: `common/src/main/java/org/tron/common/runtime/vm/DataWord.java`)

### Summary
`DataWord.longValue()` (and `intValue()`) is documented to throw `ArithmeticException` "if this will not fit in a long", mirroring the semantics of `longValueExact()`/`intValueExact()` used elsewhere in the codebase (e.g. Solidity's `SafeCast`). The implementation, however, performs raw byte-shifting truncation of a 256-bit `DataWord` down to 64/32 bits with no range check and never throws, silently wrapping large values — the exact "unsafe downcast, larger type truncated to smaller type" bug class described in the Harpie `uint256`→`uint128` report. [2](#0-1) 

### Finding Description
The javadoc for `longValue()`/`intValue()` explicitly promises an exception on overflow, and the codebase clearly distinguishes this "checked" API from the "safe" variants (`longValueSafe()`/`intValueSafe()`, which clamp to `MAX_VALUE`) and from `sValue().longValueExact()` (used correctly for endowments — see `Program.callToAddress()` line 1034, `Program.callToPrecompiledAddress()` line 1679, `Program.freezeBalanceV2()`/`voteWitness()`). Callers throughout the VM opcode-handling code rely on this contract to safely reduce a 256-bit stack word to a Java primitive for use as an amount, token id, or index.

In `Program.callToAddress()` (the internal implementation backing the `CALL`/`CALLTOKEN` opcodes reachable by any smart contract), the TRC10 token identifier passed from bytecode is converted with the unchecked `longValue()`, not `longValueExact()`:
```java
tokenId = String.valueOf(msg.getTokenId().longValue()).getBytes();
``` [3](#0-2) 
and again in `callToPrecompiledAddress()`: [4](#0-3) 

If a contract pushes a 256-bit value for the token-id argument that exceeds `Long.MAX_VALUE` (e.g. crafted via `PUSH32`), `longValue()` silently truncates/wraps it to an arbitrary (possibly small, possibly negative-looking after cast to `String`) `long`, instead of throwing as its contract promises. This is analogous to the Harpie bug where `uint128(_amount)` silently truncated instead of reverting: the code *believes* it is operating on an exact, validated value (per the misleading javadoc) but is actually operating on wrapped, attacker-influenced data.

### Impact Explanation
Because the truncated value is used to construct the TRC10 `tokenId` byte string used for balance lookups (`deposit.getTokenBalance`, `deposit.addTokenBalance`), an attacker-controlled overflow could cause the balance check and the balance mutation to operate against a *different* token id than intended, or against a wrapped/negative-looking numeric string that does not correspond to any real, existing asset ID. Since real TRC10 asset ids are small positive integers, in practice this specific call site is more likely to produce a lookup on a nonexistent asset (leading to reverts) than a fund-diverting outcome — but the mismatch between documented and actual behavior of `DataWord.longValue()`/`intValue()` is a general foot-gun: any future or existing call site that (unlike the endowment paths) uses `longValue()`/`intValue()` instead of `longValueExact()`/`sValue().longValueExact()` for an amount, balance, or accounting-relevant field would silently accept unchecked, wrapped values from untrusted bytecode, exactly mirroring the "loss of funds via unsafe downcast" bug class.

### Likelihood Explanation
Reachable by any unprivileged account deploying/calling a smart contract that issues `CALL`/`CALLTOKEN` with a maliciously large token-id word on the stack — no special privilege required. However, current TRC10 amount/endowment paths already use the exact-checked accessor, limiting today's concrete monetary impact to the token-id argument specifically.

### Recommendation
Fix `DataWord.longValue()` and `intValue()` to match their documented contract by delegating to `sValue().longValueExact()` / `sValue().intValueExact()` (as already done correctly for endowments), or rename/redocument them to clearly indicate they perform unchecked truncation, and audit all remaining call sites to ensure amount/id/index fields consistently use the exact-checked or explicitly-safe (`*Safe()`) variants rather than the mismatched `longValue()`/`intValue()`.

### Proof of Concept
1. Deploy a contract that executes `CALLTOKEN` with the token-id stack argument set to a 32-byte word representing a value `> Long.MAX_VALUE` (e.g. `0xFF...FF`).
2. `Program.callToAddress()` (or `callToPrecompiledAddress()`) invokes `msg.getTokenId().longValue()`, which silently wraps the value into an unrelated `long` instead of throwing, per `DataWord.longValue()`'s unchecked byte-shifting loop. [5](#0-4) 
3. The resulting `tokenId` byte string is used directly in `deposit.getTokenBalance`/`addTokenBalance`, deviating from the caller's intended (and validated) 256-bit value with no exception raised, contrary to the documented "checking for lost information" behavior.

  /**
   * Converts this DataWord to a long, checking for lost information. If this DataWord is out of the
   * possible range for a long result then an ArithmeticException is thrown.
   *
   * @return this DataWord converted to a long.
   * @throws ArithmeticException - if this will not fit in a long.
   */
  public long longValue() {

    long longVal = 0;
    for (byte aData : data) {
      longVal = (longVal << 8) + (aData & 0xff);
    }

    return longVal;
  }
