### Title
`ExecuteInboundGasAndPayload` reports the pre-swap PRC20 amount/asset to the CEA recipient contract instead of the actual post-swap value it received - (File: `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
For `TxType_GAS_AND_PAYLOAD` inbounds with `IsCEA=true` whose recipient is a deployed smart contract (not a UEA), the keeper deposits funds into the recipient via `depositPRC20WithAutoSwap` (which swaps the inbound PRC20 into WPC/native PC before crediting the recipient), but then calls the recipient's `executeUniversalTx` with the *original* pre-swap PRC20 address and amount, not the actual token/amount the recipient received. This mirrors the LoopFi `tokenOut` bug: the value actually moved on-chain diverges from the value recorded/reported downstream, corrupting accounting for any consumer that trusts the reported parameters instead of its own balance.

### Finding Description
In `ExecuteInboundGasAndPayload` (`x/uexecutor/keeper/execute_inbound_gas_and_payload.go`), the smart-contract (isCEA, non-UEA) branch:

1. Calls `gasAndPayloadDepositAutoSwap` → `CallPRC20DepositAutoSwap` → EVM method `depositPRC20WithAutoSwap(prc20, amount, target, fee, minPCOut, deadline)` [1](#0-0) . This method swaps the inbound PRC20 token into WPC/native PC and credits `target` (the recipient contract) with the **swap output**, whose exact size depends on the live Uniswap V3 quote and is only bounded by a 5% slippage tolerance [2](#0-1) , i.e. the actual credited amount can legitimately range anywhere between `minPCOut` and the full quoted output, and the asset credited is not the original PRC20 at all.
2. Immediately after, for the smart-contract path, the keeper calls `CallExecuteUniversalTx(cacheCtx, ueaAddr, sourceChain, sender, payload, scAmount, prc20Addr, txId)`, where `scAmount` is parsed straight from `utx.InboundTx.Amount` (the raw pre-swap inbound amount) and `prc20Addr` is the original PRC20 token config address — **not** WPC and **not** the actual swapped-out amount [3](#0-2) .
3. `CallExecuteUniversalTx` forwards these exact parameters (`amount`, `prc20AssetAddr`) as part of the ABI-encoded call to the recipient contract's `executeUniversalTx(sourceChain, ceaAddress, payload, amount, prc20AssetAddr, txId)` [4](#0-3) .

The recipient contract is therefore told it received `scAmount` of `prc20Addr`, while the EVM state change it actually experienced is a credit of a swap-derived amount of WPC/native PC. This is directly analogous to the LoopFi `_onDecreaseLever` bug: a real value-moving operation occurred (the autoswap deposit), but the bookkeeping value handed to the next consumer does not reflect what actually happened — here the mismatch is not a "returns 0" omission but a wrong-asset/wrong-amount report, which is the accounting-corruption variant of the same root cause (state mutated one way, tracked value reported another way).

### Impact Explanation
Any recipient contract implementing the `executeUniversalTx` interface that trusts the `amount`/`prc20AssetAddr` parameters (rather than independently verifying its own token balance before/after the call) will operate on a false view of what it received: it may credit an internal ledger with the pre-swap PRC20 amount/asset while its real balance change is a different, slippage-dependent amount of WPC. This falls squarely under the allowed "corruption of PRC20 or native asset accounting ... token mapping ... canonical UniversalTx state" impact category, and is reachable purely from an ordinary user's inbound submission with `IsCEA=true` — no privileged actor is required; honest Universal Validators faithfully relay the real source-chain event, and the divergence is entirely a Push Chain-side bookkeeping bug.

### Likelihood Explanation
Any external-chain user can trigger a `GAS_AND_PAYLOAD` + `IsCEA=true` inbound targeting a contract they control (deploying their own "recipient contract" to receive `executeUniversalTx` calls) with an amount they choose, so the divergent-amount/asset condition is trivially reachable on every such inbound (the swap output essentially never equals the raw input 1:1, and the token itself changes from PRC20 to WPC). The severity for Push Chain itself is bounded by the fact that no protocol-level fund transfer is stolen or lost (the *actual* WPC amount is correctly deposited on-chain); the damage is to any consumer contract that naively trusts the reported values, similar to how the original finding was downgraded to Medium because it's an edge-case/downstream-accounting issue rather than a direct drain.

### Recommendation
In `ExecuteInboundGasAndPayload`'s isCEA smart-contract branch, capture the actual swap output amount and destination asset address returned/emitted by `depositPRC20WithAutoSwap` (e.g., decode it from the EVM receipt/logs, similar to how LoopFi's fix recommends decoding `tokenOut` unconditionally) and pass that real amount/asset — not the pre-swap PRC20 amount/address — into `CallExecuteUniversalTx`. If the receipt does not expose the swap output, the WPC address and actual received balance should be looked up explicitly before invoking `executeUniversalTx`.

### Proof of Concept
1. Attacker deploys a minimal recipient contract on Push Chain implementing `executeUniversalTx(sourceChain, ceaAddress, payload, amount, prc20AssetAddr, txId)` that simply logs/credits `amount` of `prc20AssetAddr` to an internal per-user ledger (a plausible real-world CEA integration pattern) without checking its own token balance.
2. Attacker performs a real gateway deposit on an external chain of `amount = 1_000_000` of a registered PRC20-backed asset, with `TxType = GAS_AND_PAYLOAD`, `IsCEA = true`, `Recipient = <attacker's contract>`.
3. Universal Validators honestly observe and vote the inbound; `ExecuteInboundGasAndPayload` executes: `gasAndPayloadDepositAutoSwap` swaps the PRC20 into WPC and deposits, e.g., `950,000` WPC-equivalent units into the recipient (5% slippage-bound, or whatever the live quote yields) — see the deposit/swap flow [5](#0-4) .
4. `CallExecuteUniversalTx` is then invoked with `amount = 1,000,000` and `prc20AssetAddr = <original PRC20 address>` [6](#0-5) , so the recipient contract's ledger is credited for `1,000,000` of the original PRC20 even though it actually holds `950,000` of a different token (WPC).
5. This state can be repeated/tuned by the attacker (choosing tokens/fee tiers with worse liquidity to widen the gap up to the 5% slippage bound, or exploiting quote staleness) to maximize the accounting drift between reported and real value received by their own contract, which could then be leveraged against any protocol logic built on top of that (mis)reported value.

// gasAndPayloadDepositAutoSwap handles the swap quote + deposit autoswap for GAS_AND_PAYLOAD.
func (k Keeper) gasAndPayloadDepositAutoSwap(
	sdkCtx sdk.Context,
	prc20AddressHex common.Address,
	ueaAddr common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	quoterAddr, err := k.GetUniversalCoreQuoterAddress(sdkCtx)
	if err != nil {
		return nil, err
	}

	wpcAddr, err := k.GetUniversalCoreWPCAddress(sdkCtx)
	if err != nil {
		return nil, err
	}

	fee, err := k.GetDefaultFeeTierForToken(sdkCtx, prc20AddressHex)
	if err != nil {
		return nil, err
	}

	quote, err := k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)
	if err != nil {
		return nil, err
	}

	// 5% slippage: minPCOut = quote * 95 / 100
	minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
	minPCOut.Div(minPCOut, big.NewInt(100))

	return k.CallPRC20DepositAutoSwap(sdkCtx, prc20AddressHex, ueaAddr, amount, fee, minPCOut)
}

// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
}
