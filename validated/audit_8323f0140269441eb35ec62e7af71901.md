### Title
Truncated 160-bit NEP-616 deterministic-account-id derivation is vulnerable to hash-collision account hijacking - (File: `core/primitives/src/utils.rs`, `runtime/runtime/src/deterministic_account_id.rs`, `runtime/runtime/src/action_validation.rs`)

### Summary
NEAR's deterministic-account feature (NEP-616) derives an account id by truncating a `keccak256` hash to 160 bits, exactly the same truncated-hash construction (and thus the same ~2^160 collision space) discussed in the Kyber Router.sol report. The protocol's only defense is a self-consistency check that the *submitted* `DeterministicAccountStateInit` hashes to the claimed receiver id — it never verifies that the submitted payload is the one the address's original funder intended. Combined with the fact that a deterministic account can be pre-funded (via ordinary `Transfer`) while still "uninit" (`AccountContract::None`), and that the first `DeterministicStateInitAction` to reach an uninit account permanently and irrevocably sets its code/data, an attacker who brute-forces a second, differently-coded/keyed `DeterministicAccountStateInit` that collides on the truncated 160-bit hash can front-run the legitimate owner and seize control of the pre-funded balance.

### Finding Description
`derive_near_deterministic_account_id` computes the account id as `'0s' + keccak256(borsh(state_init))[12..32].hex()` — a 160-bit truncated hash of an attacker-controllable structure (`code: GlobalContractIdentifier`, `data: BTreeMap<Vec<u8>, Vec<u8>>`): [1](#0-0) 

The only validation performed when a `DeterministicStateInitAction` is submitted is that the derived id of the *given* `state_init` equals the receiver — a purely self-referential check, with no linkage to a canonical registry proving this is the "real" owner's payload: [2](#0-1) 

This is architecturally identical to the Router.sol flaw: `Router.sol` verified `msg.sender == computeAddress(...)` without checking the factory that a genuine pool exists there; here the runtime verifies `derive_near_deterministic_account_id(payload) == receiver_id` without checking that `payload` is the one the account's original funder committed to.

Execution of `DeterministicStateInitAction` is idempotent and first-write-wins: it only performs the `uninit -> active` deployment (setting contract code/data) `if account.contract().is_none()`: [3](#0-2) 

Meanwhile, a deterministic account can already exist in `uninit` state holding a nonzero balance, purely from an ordinary `Transfer` (per docs: "A Transfer can also deposit a balance before the DeterministicStateInitAction"): [4](#0-3) [5](#0-4) 

Because the account id space is only 160 bits (same magnitude as the Router.sol pool-address collision), an attacker who brute-forces a distinct `DeterministicAccountStateInit` (different `code`/`data`, e.g. pointing at an attacker-deployed `GlobalContractIdentifier` that grants the attacker withdrawal/control ability) whose truncated hash collides with an already pre-funded but not-yet-initialized target account can submit `DeterministicStateInitAction` first and permanently install their own malicious contract on that address, seizing the deposited balance and all future control of the account.

### Impact Explanation
This yields concrete unauthorized value movement and permanent loss of funds/control: any deterministic account funded ahead of its `DeterministicStateInitAction` (the exact usage pattern the protocol itself documents and supports) is vulnerable to being permanently hijacked by whoever wins the race with a colliding payload. Because contract-init is a one-time, irreversible `None -> Some` transition, the legitimate owner permanently loses the ability to initialize their intended code/data at that address once an attacker's colliding payload lands first — this is the runtime-execution/global-accounts analog called out in scope (deterministic/universal accounts, runtime apply loop, balance accounting).

### Likelihood Explanation
Identical cost/likelihood profile to the original report: the collision space is 2^160 (truncated keccak256), giving an approximate birthday-collision attack cost of ~2^80–2^81 hash operations to find a colliding `DeterministicAccountStateInit` against a target address — currently expensive but decreasing over time as hashing/storage costs fall, and profitable against any high-value pre-funded deterministic account (mirroring the "immutable Router, forever-standing approvals" argument that the escalation judge accepted as Medium in the source report). Unlike the Router.sol case, the attacker does not even need to search two independent 2^80 sets (EOA + pool) — only one 2^80 search over candidate `state_init` payloads is needed per target account, making the attack strictly cheaper than the original finding.

### Recommendation
Do not rely solely on a 160-bit truncated hash as the sole authorization mechanism for claiming ownership/initialization rights over a value-bearing account. Options include: widening the derived-id truncation to the full 256-bit hash (removing the truncation that reintroduces this Ethereum-style collision risk), or requiring the `DeterministicStateInitAction` to be co-signed/bound to the same predecessor/actor that performed the initial pre-funding transfer, so an unrelated third party's colliding payload cannot claim a pre-funded uninit account.

### Proof of Concept
1. Victim sends a `Transfer` action to `receiver_id = "0s<160-bit hash of victim's intended DeterministicAccountStateInit>"`, creating the account in `uninit` state with a nonzero balance (`action_implicit_account_creation_transfer`, `NearDeterministicAccount` branch).
2. Before the victim submits their `DeterministicStateInitAction`, an attacker who has precomputed (offline, ~2^80 keccak256 evaluations) a distinct `DeterministicAccountStateInit'` — pointing `code` at an attacker-controlled `GlobalContractIdentifier` (e.g., a global contract that adds a full-access key or transfers out balance to the attacker) — such that `derive_near_deterministic_account_id(state_init') == receiver_id`, submits `DeterministicStateInitAction { state_init: state_init', deposit }` to that same `receiver_id`.
3. `validate_deterministic_state_init` passes because `derived_id == receiver_id` holds for the attacker's payload (`action_validation.rs:431-438`).
4. `action_deterministic_state_init` sees `account.contract().is_none()` (still uninit) and calls `deploy_deterministic_account`, installing the attacker's global contract and data (`deterministic_account_id.rs:38-48`, `:117-151`).
5. The account, along with its pre-funded balance, is now running attacker-chosen code; the attacker can drain the balance or otherwise take control, and the legitimate owner's intended `DeterministicStateInitAction` becomes a no-op ("if the account was already created before: do nothing").

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let data = borsh::to_vec(&state_init).expect("borsh must not fail");
    let hash = sha3::Keccak256::digest(&data);
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

### Deterministic account creation

Deterministic accounts cannot be created with a `CreateAccount` nor with a `Transfer` action.
A special action, `DeterministicStateInitAction`, is required.
This action validates that the account id matches its initial state.

As with all account types, you have to attach a large enough deposit to cover for the account storage. If the code and
initial state is small enough to fit below the zero-balance limit, no balance is required. The
`DeterministicStateInitAction` has a field to include a balance specifically to cover storage. Anything above the
required amount to cover storage requirements is refunded.

A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable,
however, until the `DeterministicStateInitAction` is also executed.
