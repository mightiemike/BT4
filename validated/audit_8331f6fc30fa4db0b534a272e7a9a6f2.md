### Title
Attacker can front-run `AccountInitDecorator`'s new-account fast path to grief gasless first-tx admission for Universal Validator hot keys - (File: app/ante/account_init_decorator.go)

### Summary
`AccountInitDecorator` provides a special "first-use" bootstrap branch for gasless transactions, analogous to the Crab Strategy's first-deposit bookkeeping branch: it only runs when `!aid.ak.HasAccount(ctx, newAccAddr)`. Just as any unprivileged user could add collateral to the CrabStrategy vault to make `strategyDebt == 0 && strategyCollateral == 0` false and break the one-time initialization, an unprivileged actor can cause `HasAccount` to become `true` for a victim's not-yet-used address before the victim's first gasless transaction lands, permanently routing that address away from the intended bootstrap path.

### Finding Description
`AccountInitDecorator.AnteHandle` (`app/ante/account_init_decorator.go:31-81`) special-cases "new account" gasless senders (Universal Validators submitting `MsgVoteInbound`/`MsgVoteOutbound`/etc., or UEA owners submitting `MsgExecutePayload`/`MsgMigrateUEA`): [1](#0-0) 

If the account does **not yet exist** (`!aid.ak.HasAccount`), the decorator bypasses normal signature verification and instead verifies the signature under the fixed assumption `AccountNumber=0, Sequence=0` ( [2](#0-1) ), then creates the account with `SetSequence(1)`. This lets a freshly-generated UV hot key (which has never interacted with the chain and holds zero balance) submit its very first gasless vote without needing to be pre-funded or registered — this is stated explicitly in the docs: *"lets a freshly-keygen'd Universal Validator hot key vote on its very first tx, without anyone first having to fund it."* (`app/README.md:180-182`).

Whether the account already exists is decided purely by `AccountKeeper.HasAccount`, which is a global, permissionless-to-influence piece of state. Any unprivileged party who knows the target address (UV hot keys and UEA-derived Cosmos addresses are deterministic/observable — e.g., derived from an EVM address via `sdk.AccAddress(evmFrom.Bytes())`, as used throughout the executor code, see `test/integration/uexecutor/execute_payload_test.go:68-84`) can pre-create the on-chain account record for that address before the legitimate owner ever transacts. This mirrors the report's core bug class: the "first-time" branch is only reachable through a state predicate (`strategyDebt==0 && strategyCollateral==0` in the original; `!HasAccount` here) that any unprivileged actor can flip.

Once the account exists (via `SetAccount`/`NewAccountWithAddress` triggered by some other benign or attacker action, e.g. any module or flow that materializes a `BaseAccount` for that address, or plain interaction from the AccountInitDecorator's own creation path if executed by an attacker-controlled forged tx that manages to piggyback signature checks disabled at `sequence 0`), `HasAccount` returns `true` on the victim's legitimate first submission, and the decorator falls through to `next(ctx, tx, simulate)` (`app/ante/account_init_decorator.go:77-80`). The normal ante pipeline then requires standard fee payment/signature verification with the real (attacker-influenced or simply non-zero) `account_number`/`sequence`, which the victim's UV or UEA owner never expected to need and is not equipped to pay for (gasless UV hot keys hold no gas token by design). This permanently blocks that address's gasless admission until manually funded/fixed — a denial-of-service on the very "first deposit"/"first-use" invariant the decorator exists to protect.

### Impact Explanation
This is a denial-of-service on the gasless admission path (in-scope: "denial of service only when it is not network-level and is reachable without privileged control"). It targets an unprivileged, user-reachable flow (`app/ante/account_init_decorator.go`, part of the custom ante/gasless controls explicitly called out in scope) and blocks legitimate UV hot keys or UEA owners from bootstrapping their very first gasless transaction — defeating the entire purpose of the gasless design described in `app/README.md`. It does not directly steal funds, but it can stall a Universal Validator's very first vote (impacting ballot finalization liveness for that validator) or block a fresh UEA owner's first `MsgExecutePayload`/`MsgMigrateUEA` until it is manually remediated (funding + normal signed tx), which is an availability/liveness violation of the gasless-admission invariant reachable by any unprivileged actor observing a not-yet-used, deterministically-derivable address.

### Likelihood Explanation
Medium-to-High. Addresses for UV hot keys and UEA owners are either publicly known ahead of time (network registration/setup, deterministic derivation from EVM address) or can be predicted, and no privileged access is required to attempt the pre-creation. The exact mechanism by which `HasAccount` becomes `true` (e.g., whether ordinary `bank.SendCoins` to an address auto-creates an `AccountKeeper` entry versus only touching the balance store) is dependent on the vendored Cosmos SDK version and was not fully verifiable from the indexed code — this repository does not include the vendored `x/auth`/`x/bank` keeper source, so I could not conclusively confirm from this codebase whether a plain token transfer materializes the `BaseAccount` record. This uncertainty affects the exact griefing vector (a bare `MsgSend` vs. some other account-materializing action) but not the underlying design flaw: the decorator's fast-path is gated solely by mutable, attacker-influenceable global state (`HasAccount`), exactly like the original report's `strategyDebt == 0 && strategyCollateral == 0` gate.

### Recommendation
Do not gate the one-time bootstrap behavior solely on `HasAccount`. Consider:
- Binding the special "new account" signature-verification bypass to an explicit, one-time allowlist/registration (e.g., only for addresses registered as Universal Validator hot keys via `x/uvalidator`, or UEA addresses verified against the factory) rather than any never-before-seen address.
- If an account already exists but has `sequence == 0` and no meaningful history (i.e., it was created purely by a balance-only touch, not a genuine prior tx), still allow the bootstrap signature-verification path instead of unconditionally deferring to `next`.
- Add integration tests (mirroring `test/integration/uexecutor/execute_payload_test.go`'s "griefing-recovery" pattern already used for UEA pre-funding) that pre-create/pre-fund a UV hot key or UEA-owner address before its legitimate first gasless tx, and assert that legitimate first-use admission still succeeds.

### Proof of Concept
1. Generate a fresh keypair for a Universal Validator hot key address `A` (or derive a UEA owner's Cosmos address from a known EVM address) that has never transacted on-chain — `AccountKeeper.HasAccount(ctx, A) == false`.
2. As an unprivileged attacker, execute any action that results in `AccountKeeper.SetAccount(ctx, A)` being called for `A` before the victim's first gasless tx (e.g., sending a small amount of `upc` to `A`, or any other module flow that materializes a `BaseAccount` record for a previously-untouched address — see `createAndFundAccount`/`SendCoinsFromModuleToAccount` patterns in `test/utils/account_setup.go:36-55`, which is the same primitive class the codebase itself acknowledges as a griefing vector for UEA addresses in `TestExecutePayload_AutoDeployOnPreFundedAddress`).
3. The victim later submits their legitimately pre-signed gasless tx (e.g. `MsgVoteInbound`) assuming `AccountNumber=0, Sequence=0` per the bootstrap convention.
4. `AccountInitDecorator.AnteHandle` now finds `HasAccount(ctx, A) == true` and calls `next(ctx, tx, simulate)` instead of the bootstrap verification path (`app/ante/account_init_decorator.go:53,77-80`).
5. The tx proceeds through the standard ante chain, which enforces the account's actual `account_number`/`sequence` and normal fee/gas requirements; since the victim's pre-signed payload used `account_number=0, sequence=0` and the hot key holds no gas token, signature verification and/or fee deduction fails, and the legitimate first-use transaction is rejected.
