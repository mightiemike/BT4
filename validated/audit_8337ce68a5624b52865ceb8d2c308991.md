### Title
Missing slippage protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` allows same-block price manipulation of the AMM pool ratio - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` compute the paired-token amount (`anotherTokenQuant`) purely from the exchange pool's live `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with no caller-supplied bound. Unlike `ExchangeTransactionContract`, which carries an `expected` field checked against the computed output [1](#0-0) , neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` has an equivalent minimum/maximum guard [2](#0-1) . This mirrors the reported `CToken.mintFresh()`/`exchangeRateStoredInternal()` issue: a mint/redeem-like operation prices itself off mutable pool state that any unprivileged account can shift in the same block.

### Finding Description
The pool ratio (`firstTokenBalance` / `secondTokenBalance`) held in `ExchangeCapsule` is the "exchange rate" for this bancor-like AMM [3](#0-2) . Any account can shift this ratio arbitrarily via `ExchangeTransactionActuator`, which is open to any caller (no creator check in `doValidate`/`execute`) [4](#0-3) .

`ExchangeInjectActuator.doValidate()` and `execute()` compute `anotherTokenQuant` as a direct ratio of the *current* `firstTokenBalance`/`secondTokenBalance` against the injected `tokenQuant`, with no expected/minimum parameter to bound it: [5](#0-4) . The same pattern exists in `ExchangeWithdrawActuator`: [6](#0-5) .

By contrast, `ExchangeTransactionActuator` explicitly protects the caller with the `expected` field: `tokenExpected = contract.getExpected()` and `if (anotherTokenQuant < tokenExpected) throw ...` [7](#0-6) . This is precisely the slippage-bound mitigation the external report recommends for `V2Migrator.migrate()`, and it exists for swaps but is absent for inject/withdraw.

Because TRON blocks batch multiple independently-submitted transactions ordered by the producing witness (not by the sender), an attacker can submit a large `ExchangeTransactionContract` swap that lands in the same block immediately before a victim's `ExchangeInjectContract`/`ExchangeWithdrawContract`, skewing `firstTokenBalance`/`secondTokenBalance` at the moment the victim's transaction is executed. Since the victim's `anotherTokenQuant` is derived from that skewed ratio and is unbounded, the victim is forced to inject an inflated amount of the counterpart token (locking excess funds into the pool) or withdraw a disproportionately reduced counterpart amount, then the attacker can reverse their swap afterward to restore the ratio and repeatedly extract value — the same "manipulate exchange rate around a mint/redeem call with no slippage check" pattern as the report's `CToken.mintFresh()`/`exchangeRateStoredInternal()` bug.

### Impact Explanation
A victim performing `ExchangeInjectContract` or `ExchangeWithdrawContract` can lose funds to a sandwiching unprivileged attacker with no way to bound the resulting `anotherTokenQuant`, causing an accounting/settlement loss identical in nature to the underpriced-mint issue in the source report. This is a concrete accounting impact reachable by any account holding the traded tokens.

### Likelihood Explanation
The `ExchangeTransactionActuator` swap path required to manipulate the ratio is open to any account with no special privileges [4](#0-3) , and low-liquidity exchange pools (which do exist on TRON, similar to the report's assumption of low-liquidity V2 pools) make the ratio easy and cheap to move within a single block.

### Recommendation
Add an `expected`/slippage-bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (protobuf) analogous to `ExchangeTransactionContract.expected`, and enforce it in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()` by rejecting the operation if the computed `anotherTokenQuant` deviates from the caller-specified bound, mirroring the existing check in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker (unprivileged account) observes a pending `ExchangeInjectContract` from a pool creator specifying `tokenQuant` for `firstTokenID`.
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of `secondTokenID` into the same exchange, which via `ExchangeCapsule.transaction()` sharply changes `firstTokenBalance`/`secondTokenBalance` [8](#0-7) .
3. If the attacker's transaction lands first in the block, the victim's `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` off the now-skewed ratio [9](#0-8) , forcing the victim to deposit far more (or less) of the counterpart token than intended, with no `expected` check to reject the trade.
4. Attacker reverses their swap afterward to restore the ratio, banking the difference extracted from the victim's forced injection/withdrawal.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
