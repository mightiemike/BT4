## Title
Delayed/postponed receipt that was admissible under the runtime config in effect at creation time can later fail `validate_receipt` on dequeue and crash every validator applying that chunk - ([File: runtime/runtime/src/verifier.rs])

## Summary
The Sherlock finding describes a class of bug where a payload is validated only when it is finally *consumed* (built into an outbound tx), rather than when it is admitted, so a malformed-but-admitted item gets permanently stuck and blocks all follow-on processing with no recovery. The nearcore analog is the gap between receipt *admission-time* validation (`ValidateReceiptMode::NewReceipt`) and *dequeue-time* re-validation (`ValidateReceiptMode::ExistingReceipt`) for receipts parked in the delayed queue: a receipt that is valid when it is created can become invalid by the time it is popped and re-validated, and unlike the SUI case (stuck cctx), the NEAR failure mode is a hard `panic!` that halts every honest validator applying that chunk.

## Finding Description
`validate_receipt` is the single validation function used both for brand-new receipts and for receipts that are re-validated after being pulled back out of the trie-backed delayed queue [1](#0-0) . Some checks inside it are deliberately gated to run only in `NewReceipt` mode - e.g. `max_receipt_size` is only enforced `if mode == ValidateReceiptMode::NewReceipt` [2](#0-1)  - specifically so that receipts admitted under older/looser rules keep executing instead of failing when dequeued.

However, `validate_action_receipt`'s check on `input_data_ids().len()` against `limit_config.max_number_input_data_dependencies` is unconditional, independent of `mode` [3](#0-2) . The developers are aware that enforcing a validation rule identically in `ExistingReceipt` mode is dangerous: a dedicated test/comment explicitly states that "an incoming or delayed receipt that fails validation is a `RuntimeError`, not an action error, so enforcing this in `ExistingReceipt` mode would fail the whole chunk," and shows the code specifically exempting `ExistingReceipt` mode for the `DeterministicStateInit` limit for this reason [4](#0-3) .

When a delayed receipt is popped in `process_delayed_receipts`, it is re-validated with `ValidateReceiptMode::ExistingReceipt` and the *current* protocol version (not the version in effect when the receipt was created); any failure is converted into `StorageError::StorageInconsistentState` [5](#0-4) . That error is not treated as a soft/recoverable error: in `Runtime::apply_chunk`, any `StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue` triggers `panic!("{err}")` [6](#0-5) . This is the same treatment applied to `RuntimeError::ReceiptValidationError` and `RuntimeError::UnexpectedIntegerOverflow`, both marked `// TODO(#2152): process gracefully` at the higher-level runtime adapter [7](#0-6) .

So: if `max_number_input_data_dependencies` (or any future config limit that isn't given the same `NewReceipt`-only exemption) is ever tightened by a protocol/config change, a receipt already sitting in a shard's delayed queue - created earlier and admitted under the old, looser limit - will fail `validate_receipt` the moment it is dequeued after the new limit activates, and every honest validator applying that chunk will panic. This is directly analogous to the SUI bug: an item that looked fine at admission time is only checked at consumption time, gets stuck, and blocks everything queued behind it - except nearcore's failure mode escalates a "stuck queue" into a deterministic node crash / chain halt, since delayed receipts are processed strictly FIFO before later ones can be reached.

A related, already-fixed instance of exactly this bug class exists in the codebase's regression test suite: a `GlobalContractDistribution` receipt that becomes stale (target shard no longer resolvable) after two resharding events used to panic in `receipt_filter_fn`/`receiver_shard_id` when dequeued from the delayed queue [8](#0-7) , confirming this exact "admission valid, dequeue invalid ⇒ panic" pattern has occurred for real in this codebase.

## Impact Explanation
If any validation rule inside `validate_action_receipt`/`validate_data_receipt` is added or tightened without being scoped to `ValidateReceiptMode::NewReceipt` only, a single previously-submitted transaction/receipt sitting in the delayed queue can deterministically crash every validator that applies the shard's chunk once the new limit takes effect - a transaction-triggered chain halt, not merely a resource-exhaustion DoS. This matches the currently-unconditional `NumberInputDataDependenciesExceeded` check, which has no such carve-out today.

## Likelihood Explanation
Exploitation requires a receipt to be admitted under one set of limits and to still be sitting in the delayed queue when a stricter limit becomes active (via a runtime-config/protocol-version change), which needs either network congestion (to keep the receipt queued) timed around a config change, or the config being lowered administratively. This is a lower-frequency, config-change-dependent trigger rather than an always-available attack, and the devs have already special-cased the one limit change they anticipated (`DeterministicStateInit`), so likelihood is moderate rather than trivial - but the `max_number_input_data_dependencies` check is not currently protected the same way, so it is not merely theoretical.

## Recommendation
- Scope every `validate_action_receipt`/`validate_data_receipt` check that depends on a config limit (in particular `NumberInputDataDependenciesExceeded`) to `ValidateReceiptMode::NewReceipt` only, matching the pattern already used for `max_receipt_size` and `DeterministicStateInit`, so pre-existing queued receipts are never re-validated against limits that postdate their creation.
- Add a process/lint rule (and regression test, similar to `test_stale_global_contract_distribution_after_double_resharding`) requiring any new receipt/action validation limit to explicitly justify its `ExistingReceipt`-mode behavior before merge.
- Consider making the `StorageInconsistentState` path from a failed delayed-receipt re-validation recoverable (e.g., skip/park the offending receipt with an error outcome) instead of hard-panicking the whole chunk apply.

## Proof of Concept
1. Submit a transaction that creates an action receipt with `input_data_ids` just below the current `max_number_input_data_dependencies`, targeting a receiver shard that is heavily congested so the receipt is pushed into the delayed queue instead of executed immediately (`process_incoming_receipts`/`process_local_receipts` overflow path).
2. Get `max_number_input_data_dependencies` lowered below that receipt's `input_data_ids` count via a runtime-config update tied to a protocol-version upgrade (this is a config change, not a code bug, but the check has no `NewReceipt`-only guard to protect against it).
3. Once the new protocol version activates and the shard's delayed queue drains to that receipt, `process_delayed_receipts` calls `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)` [5](#0-4) , which now fails and returns `StorageInconsistentState`.
4. `Runtime::apply_chunk` converts this into `panic!("{err}")` [6](#0-5) , crashing every honest validator that applies this chunk - a single, previously-accepted receipt halts the chain.

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-runner/src/wasmtime_runner/logic.rs#fn(read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt)
        | VersionedReceiptEnum::PromiseYield(action_receipt) => validate_action_receipt(
            limit_config,
            action_receipt,
            receipt.receiver_id(),
            current_protocol_version,
            mode,
        ),
        VersionedReceiptEnum::Data(data_receipt)
        | VersionedReceiptEnum::PromiseResume(data_receipt) => {
            validate_data_receipt(limit_config, &data_receipt)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
    }
}
