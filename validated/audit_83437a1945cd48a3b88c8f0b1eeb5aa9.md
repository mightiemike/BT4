### Title
Unbounded BigDecimal exponent parsing in `Util.getJsonLongValue` allows CPU/memory amplification DoS via `TriggerSmartContractServlet` - ([File: framework/src/main/java/org/tron/core/services/http/TriggerSmartContractServlet.java])

### Summary
`TriggerSmartContractServlet.doPost` only enforces a coarse whole-body size cap (`Util.checkBodySize`) before parsing `call_value`, `call_token_value`, `token_id`, and `fee_limit` via `Util.getJsonLongValue`, which (per the question's stated implementation) converts the field to `BigDecimal` and calls `longValueExact()`. There is no per-field length/format validation (e.g., rejecting scientific notation or capping digit count) before this conversion, so a numerically small but syntactically crafted value (e.g., `"1e100000"`) can force the JVM to materialize an enormous internal `BigInteger` while checking exactness, producing CPU/memory cost wildly disproportionate to the few bytes sent.

### Finding Description
`TriggerSmartContractServlet.doPost` reads the raw body, calls `Util.checkBodySize(contract)` which only bounds total body bytes against `httpMaxMessageSize`, and then parses individual numeric fields with `Util.getJsonLongValue(jsonObject, "call_token_value"/"call_value"/"fee_limit")` [1](#0-0) . `PostParams.getPostParams` shows the same `checkBodySize` pattern is the only gate applied at the body-ingestion layer, with no per-value inspection [2](#0-1) . Since `BigDecimal`'s scientific-notation form (`digitsEexponent`) lets a tiny literal represent a value with an astronomically large scale, and `longValueExact()` must materialize/compare the true magnitude (via internal `BigInteger` scaling for negative-scale values) to determine whether it fits in a `long`, the cost of processing such a string is not bounded by the input string's byte length but by the *decimal magnitude* implied by the exponent — this is a superlinear/asymmetric-cost primitive independent of `checkBodySize`, which only measures literal bytes, not the semantic magnitude of the number being parsed.

This bypasses the intended "faithful metering" invariant: `checkBodySize` correctly limits an attacker from submitting megabytes of literal digits, but does nothing to stop a handful of bytes (`"1e2000000000"`-style strings, bounded only by `int` range for the exponent) from causing a multi-gigabyte-scale internal `BigInteger` allocation/computation attempt inside `longValueExact()`, all before any signature check, fee/energy accounting, or `ContractValidateException` handling occurs — this parsing happens purely in the unauthenticated HTTP request-processing thread, before `wallet.createTransactionCapsule`/`triggerContract` is ever reached.

### Impact Explanation
This is a DoS via RPC-API: a single crafted HTTP POST to `/wallet/triggersmartcontract` can consume disproportionate CPU/memory in the servlet thread relative to the tiny number of bytes sent, and repeated/concurrent requests can exhaust node memory or stall HTTP worker threads, degrading availability of the JSON-RPC/HTTP API for legitimate users. No funds, keys, or consensus state are affected — this is availability-only impact scoped to the node's HTTP interface.

### Likelihood Explanation
The attacker needs only unauthenticated HTTP access to a full node's JSON-RPC endpoint (no signed transaction, no funded account, no special permissions), and the payload is trivially small and repeatable, making this low-cost and highly feasible to attempt at scale (e.g., concurrent connections each carrying a `"1e999999999"`-style field). However, exact severity depends on internal JVM behavior of `BigDecimal.longValueExact()` for large negative scales and on the concrete implementation of `Util.getJsonLongValue`/`checkBodySize`, which I was unable to fully view in this session (repository index did not return the full contents of `Util.java`, including `getJsonLongValue`'s exact body and the `httpMaxMessageSize` default). This limits my ability to definitively confirm the code path constructs a `BigInteger` proportional to the exponent rather than throwing early (e.g., `NumberFormatException`) — later JDK versions include hardening (JDK-8199732-family fixes) that reject BigDecimal strings whose exponent would cause disproportionate allocation, which could mitigate or eliminate this depending on the JDK version java-tron targets.

### Recommendation
Add explicit validation in `Util.getJsonLongValue` before constructing `BigDecimal`: reject strings containing exponent markers (`e`/`E`) or restrict to plain digit sequences with a small maximum length (e.g., ≤20 digits, sufficient for any `long`), rather than relying solely on the coarse `checkBodySize` byte-count cap.
