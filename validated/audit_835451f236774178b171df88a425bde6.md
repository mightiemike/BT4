## Analysis

The Panoptic report's core invariant is: **a state-transition event (bad-debt socialization) mutates the accounting ratio, and code paths exist where an actor can act on stale/partial state before the mutation is fully reflected, letting corrupted or divergent state slip past the check that should catch it.** The closest verified Aptos analog is not a timing/front-running issue (Aptos consensus doesn't expose "front-runnable" pre-commit windows to arbitrary state mutation the way an AMM does), but a **verification-gap** analog: a replay/consistency check that is supposed to bind computed output to the authenticated `TransactionInfo` silently skips newly added state-root fields, so a corrupted native-trading state root can be committed/replayed without being caught by the one function designed to catch exactly that class of divergence.

### Finding Description

`TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` is the authoritative function used to verify that a locally computed `TransactionOutput` matches the on-chain, signed `TransactionInfo` for a given version. It checks status, gas, write-set hash, and event root hash [1](#0-0) . However, the code explicitly acknowledges it does **not** validate the newer `TransactionInfoV1` checkpoint fields — the state/hot-state checkpoint hash and, most notably, `position_state_checkpoint_hash` (the native-position Merkle root gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) [2](#0-1) .

This matters because `position_state_checkpoint_hash` is a real, consensus-verified state root: `BlockExecutorConfigFromOnchain::with_features` wires `compute_trading_native_state_roots` from the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag [3](#0-2) , and `DoLedgerUpdate::assemble_transaction_infos` embeds `position_state_checkpoint_hashes` into `TransactionInfoV1` so it becomes part of the hashed, accumulator-committed transaction info [4](#0-3) . That hash is exactly the kind of value the transaction accumulator commits and later proofs are built over (see `DoLedgerUpdate::run` appending `transaction_info_hashes` to the accumulator) [5](#0-4) .

`ensure_match_transaction_info` is used by `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/cli/src/commands.rs`, and `aptos-move/aptos-debugger/src/aptos_debugger.rs` — i.e., it is the shared gate used by chunk execution (state-sync replay) and by the archival replay-verification tool that operators/auditors rely on to detect if a node's VM execution diverges from the canonical chain. Because the comparator omits the position-state (and hot-state/state) checkpoint hashes, any of these consumers can report a **successful match** even when the locally recomputed native-position state root diverges from the authenticated one in the signed `TransactionInfoV1`.

### Impact Explanation

If `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled (a real, permanent feature flag already defined in `aptos_features.rs`/`features.move`) [6](#0-5) [7](#0-6) , a bug in the native-position tree computation, in chunk-executor state-sync replay, or in a malicious/buggy fullnode's local execution could silently commit or apply a divergent native-position state root without `ensure_match_transaction_info` (used by chunk execution and by `replay_on_archive`) ever flagging the mismatch. This is precisely the class of bug the state-integrity gate targets: "committed state that differs from the correct VM result" and "hard-fork-only divergence during commit, replay ... verification" that an authenticated check is supposed to catch but doesn't. It would let a fork of trading-native (position/orderbook/collateral) state pass replay-verification undetected — a high-severity gap because the entire purpose of this function is defense-in-depth verification against exactly this failure mode.

### Likelihood Explanation

Currently low-but-real: `COMPUTE_TRADING_NATIVE_STATE_ROOTS` requires `TRANSACTION_INFO_V1` and `HOTNESS_IN_EPILOGUE` to also be enabled (per the `with_features` gating logic) [3](#0-2) , so the gap is latent until that feature combination goes live on mainnet. The code comment itself is a self-acknowledged TODO ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS") [8](#0-7) , confirming this is a known, unresolved gap rather than a defense that was deliberately scoped out. Given the trading-native subsystem is actively being built out (native position/orderbook/collateral feature flags 119–122), this gap is likely to become exploitable as those features roll out.

### Recommendation

Extend `ensure_match_transaction_info` to compare `self`'s recomputed state checkpoint hash, hot-state checkpoint hash, and `position_state_checkpoint_hash` (when present in `txn_info`) against locally computed equivalents, returning an error on mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network.

### Proof of Concept

Not independently executable without a running node and the trading-native feature enabled; the vulnerability is demonstrated structurally by the code itself:
1. Enable `TRANSACTION_INFO_V1`, `HOTNESS_IN_EPILOGUE`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.
2. Introduce (or trigger via a bug) a divergence in the locally computed native-position Merkle root vs. the one embedded in the canonical `TransactionInfoV1.position_state_checkpoint_hash`.
3. Run chunk-executor replay or `db-tool replay-on-archive`, both of which call `ensure_match_transaction_info`.
4. Observe that replay reports success despite the state-root divergence, because the comparator never reads `position_state_checkpoint_hash` (or the other checkpoint hash fields) from `txn_info`.

Note: I could not fully trace how `chunk_executor/mod.rs` and `replay_on_archive.rs` invoke `ensure_match_transaction_info` line-by-line (the file reads returned empty in the final tool pass due to iteration limits); the call-site existence was confirmed via `grep_search`, but exact argument wiring around each call site is unverified and should be checked in a follow-up session for full confidence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
