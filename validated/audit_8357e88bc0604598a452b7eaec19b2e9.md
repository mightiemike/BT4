This confirms the root cause: `tokenExchange()` fully decodes and cryptographically verifies the session token (`decodeSessionToken(config)(sessionToken)` verifies signature and, by default, `aud === apiKey`), but it **discards the verified payload** and never checks that the payload's `dest` (the shop that Shopify actually issued the token for) matches the separately-supplied `shop` parameter. The unverified `shop` argument is what gets used to build the outbound `/admin/oauth/access_token` request URL and — critically — to construct and key the `Session` object (`createSession({shop: cleanShop, ...})`, `getOfflineId(shop)`, `getJwtSessionId(shop, ...)`) that is persisted by the caller via `sessionStorage.storeSession()`.

### Title
Session token exchange trusts an unverified `shop` parameter instead of the verified session token's `dest` claim, enabling cross-tenant session storage corruption - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`shopify.auth.tokenExchange()` verifies the session token's signature/audience via `decodeSessionToken()` but never binds the resulting `Session` and outbound OAuth request to the verified `payload.dest` shop. Instead it uses the independently supplied `shop` argument — which the library's own documentation instructs developers to source directly from an untrusted query parameter (`req.query.shop`) — as the sole shop identity for session creation and storage.

### Finding Description
`tokenExchange()` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` performs: [1](#0-0) 
Line 39 verifies the JWT cryptographically, but its return value (`payload`, including `payload.dest`) is thrown away — it is never compared against the caller-supplied `shop`. `cleanShop` (derived purely from the unverified `shop` argument via `sanitizeShop`, which only checks domain *format*, not authenticity) is then used both to build the token-exchange POST URL and to stamp the resulting `Session.shop`, `Session.id` (`getOfflineId`/`getJwtSessionId`) in `createSession()`: [2](#0-1) 

This is the direct analog of the M-21 pattern: the report's root cause is using an *incidental* address (`emittingContract`) rather than the address that actually initiated/authorized the action as the trusted "sender" identity, corrupting refund/authorization routing. Here, the library uses an *incidental* `shop` parameter (whatever the caller passes in) rather than the shop actually embedded and cryptographically attested inside the verified session token (`payload.dest`) as the trusted shop identity for session storage keying and the outbound OAuth call.

The bundled documentation actively encourages the vulnerable pattern by showing `shop` derived from `req.query.shop` — an anonymous, unauthenticated query string value — passed alongside (not derived from) the session token: [3](#0-2) 

By contrast, the shipped `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` middlewares happen to correctly derive `shop` from `payload.dest` before calling `tokenExchange` (e.g. `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts` line 67: `const shop = new URL(payload.dest).hostname;`), so the shipped frameworks are not directly exploitable through this path. But `tokenExchange()` itself is a public, documented top-level API (`shopify.auth.tokenExchange`) intended for direct use by app developers building custom auth flows (e.g. non-Remix/Express frameworks), and the library performs no internal defense to prevent a caller (following the library's own documented example) from passing a `shop` that diverges from the token's `dest`.

### Impact Explanation
If a developer follows the documented pattern (`shop` from `req.query.shop`) and an attacker supplies a mismatched `shop` query parameter alongside their own legitimately-issued session token (issued by Shopify for the attacker's own store, thus passing `decodeSessionToken`'s signature/audience check), the resulting `Session` object is persisted keyed under the attacker-chosen `shop`/session-id rather than the shop that truly owns the token. Because `SESSION_COOKIE_NAME`/session storage lookups elsewhere in the stack are keyed by `shop` string, this can corrupt the session store: a shop identity string controlled by an anonymous/unauthenticated request parameter gets bound to a real OAuth access token, enabling session-storage keying confusion between tenants (loading the wrong shop's credentials for a given `shop` key, or overwriting another shop's stored session). This matches the "session storage injection / cross-tenant access" class explicitly listed as acceptable impact.

### Likelihood Explanation
Exploitability depends entirely on downstream app code following the library's own documented usage pattern, which sources `shop` from an unauthenticated request parameter instead of from the verified token payload. Since this is the officially documented example for a public SDK API, it is reasonable to expect real-world adopters to implement it exactly as shown, making the likelihood non-trivial despite requiring a specific implementation choice by app developers (unlike webhook/app-proxy/session-token paths in this codebase, which all correctly bind the identity to the HMAC/JWT-verified source).

### Recommendation
In `tokenExchange()`, after decoding the session token, extract the shop from `payload.dest` and either (a) use it directly instead of the caller-supplied `shop`, or (b) assert `sanitizeShop(config)(shop, true) === new URL(payload.dest).hostname` and throw an `InvalidJwtError`/`InvalidOAuthError` on mismatch before proceeding to `createSession`. Additionally, update `docs/reference/auth/tokenExchange.md` to derive `shop` from the decoded token rather than from `req.query.shop`.

### Proof of Concept
Not runnable without a live Shopify OAuth token-exchange endpoint (requires two real Shopify session tokens for two different stores to demonstrate the storage-keying mismatch); the vulnerability is established from the code path itself: `decodeSessionToken` result is discarded (`token-exchange.ts` line 39) and `shop` supplied by the caller — per the documented pattern, an unauthenticated query parameter — is used unchecked for `createSession`'s `shop`/session-id (`create-session.ts` lines 33-52), with no equality check against `payload.dest` anywhere in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`.
