## Analysis

The external report's bug class is: an attacker can call a public, unprivileged entry point using a victim's identifier/address, and the callee code path unconditionally triggers a state-changing side effect (fund movement / distribution) *belonging to the victim*, at a time the victim did not choose, using the victim's own balance — with no requirement that the caller be authorized by the victim for that specific side effect.

The Push Chain analog is in `MsgExecutePayload` → `Keeper.ExecutePayload`, which is reachable by **any** unprivileged account and takes an arbitrary `UniversalAccountId` (a public identifier, not a secret) as caller-supplied input: [1](#0-0) 

### Title
Unprivileged `MsgExecutePayload` caller can force UEA auto-deployment and burn gas fees from any target account's UEA balance - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
`ExecutePayload` computes the target UEA address purely from the caller-supplied `UniversalAccountId` (not from the transaction signer), and if that UEA is undeployed but funded, it auto-deploys it and then unconditionally deducts/burns gas fees from that UEA's balance based on `receipt.GasUsed` — **regardless of whether the payload execution (`execErr`) succeeded** and regardless of whether `verificationData` was ever valid for that owner.

### Finding Description
Step 2 resolves `ueaAddr` from `universalAccountId` alone: [2](#0-1) 

If the UEA isn't deployed but carries a positive native balance, it is auto-deployed using the caller's own `evmFrom` as sender — no check that the caller is the account's actual owner: [3](#0-2) 

The payload is then executed through the UEA, and **fee deduction happens unconditionally before the execution error is even checked**: [4](#0-3) 

`DeductGasFeesFromReceipt` only short-circuits on `receipt == nil || receipt.GasUsed == 0`; it does not check whether the underlying UEA call reverted due to bad `verificationData`, and it debits/burns from `recipient` (the UEA account), not from the tx signer: [5](#0-4) 

Since a reverting `executeUniversalTx` call still consumes gas up to the point of failure (`receipt.GasUsed > 0`), an attacker can submit `MsgExecutePayload` with any `UniversalAccountId` they don't control and syntactically-valid-but-unauthorized `verificationData`/payload. This forces:
1. Irreversible deployment of the victim's UEA at a time chosen by the attacker rather than the owner (consuming the victim's balance for gas to deploy) — the design's own test acknowledges auto-deploy consumes the target's pre-funded balance: [6](#0-5) 
2. A real gas burn from the victim's UEA balance via `DeductAndBurnFees`, even though `execErr` is non-nil (the payload itself failed), because fee deduction (Step 4) runs before the `execErr` check (Step 5's `return execErr` only happens after burning): [7](#0-6) 

This mirrors the report's root cause exactly: a function meant to support a legitimate authorized flow (`collect()`/payload execution for the rightful owner) is reachable through an adjacent unprivileged call (`transferFrom` amount=0 / `MsgExecutePayload` with unauthorized `verificationData`) that triggers the victim-affecting side effect (claim collection / fee burn + forced deploy) without the victim's consent or valid authorization for that action.

### Impact Explanation
An unprivileged, unauthorized third party can:
- Force any address's UEA to be deployed on-chain at a time not chosen by its owner (a permanent state transition), and
- Repeatedly burn real `upc` gas fees out of that UEA's balance by submitting spam `MsgExecutePayload` calls with invalid `verificationData`/payload targeting that `UniversalAccountId`, draining funds intended for the legitimate owner's future payload execution with zero cost to the attacker beyond their own tx submission fee.

This falls within the allowed impact scope: "unauthorized UEA ... execution" and "draining ... of user or protocol-controlled funds" via a default, unprivileged transaction submission path.

### Likelihood Explanation
High reachability: `UniversalAccountId` values are public (derived from external-chain address + chain namespace/id), `MsgExecutePayload` requires no special permission, and gasless-tx status doesn't even apply here (this message isn't in the gasless allowlist per `app/txpolicy/gasless.go`), so any funded account can submit it repeatedly against any target `UniversalAccountId` whose UEA happens to hold a positive balance (e.g., after a bridged inbound deposit but before the owner's first payload execution).

### Recommendation
Do not deduct/burn gas fees, nor auto-deploy the UEA, purely as a side effect of an `execErr`-producing (unauthorized) `CallUEAExecutePayload` attempt. Specifically:
- Validate `verificationData` authorization for the given `universalAccountId`/payload nonce *before* performing the auto-deploy and *before* any fee deduction, so a failed/invalid authorization cannot itself trigger deployment or fund debit.
- Consider gating `DeductGasFeesFromReceipt` on `execErr == nil`, or otherwise ensure only calls that pass verification data checks inside the UEA can consume gas from the account's balance.

### Proof of Concept
1. Observe (or predict) that a `UniversalAccountId` (`chain_namespace`, `chain_id`, `owner`) has a UEA address that is funded (e.g., from a completed inbound deposit) but not yet deployed.
2. As an unrelated attacker account, submit `MsgExecutePayload` with `signer = <attacker>`, `universal_account_id = <victim's UAID>`, and any syntactically valid `universal_payload` + `verification_data` (need not be a valid signature for the victim — it only needs to pass `ValidateBasic`/ABI parsing, per `x/uexecutor/types/msg_execute_payload.go` `ValidateBasic`, which checks hex-decodability, not cryptographic validity).
3. `ExecutePayload` auto-deploys the victim's UEA (Step 2) because it is funded and undeployed, then attempts execution; even if the underlying `executeUniversalTx` call reverts inside the UEA due to bad `verification_data`, `receipt.GasUsed > 0`, so `DeductGasFeesFromReceipt` burns gas cost from the victim's UEA balance, and `ExecutePayload` returns `execErr` only afterward.
4. Repeat to progressively drain the victim's UEA balance and force the deploy at attacker-chosen timing.

**Note on confidence:** I was unable to fully trace `CallFactoryToGetUEAAddressForOrigin` and `DeployUEAV2` implementations in this pass (only located their file locations, not full bodies) due to running out of tool iterations, so I could not confirm with certainty whether `evmFrom` (the caller, not the victim owner) has any bearing on the deterministic UEA address computation or deploy authorization inside the factory contract. If the factory or `executeUniversalTx` enforces stricter caller-binding than what's visible here, this could reduce or eliminate the impact — a Devin session with full repo/EVM-contract access should verify `x/uexecutor/keeper/evm.go` (`CallFactoryToGetUEAAddressForOrigin`) and `x/uexecutor/keeper/deploy_uea.go` (`DeployUEAV2`) plus the Solidity UEA/Factory contracts before treating this as fully confirmed.

```go
func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}
```
