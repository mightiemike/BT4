### Title
Inbound CEA funds are permanently deposited into the recipient contract before `executeUniversalTx` compatibility is verified, with no revert path on failure - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
The external report flags the general pattern of pushing value to an on-chain recipient (`transferFrom` instead of `safeTransferFrom`) without confirming the recipient can actually receive/handle it, causing potential permanent loss when the recipient cannot process the incoming asset. Push Chain's CEA (Contract Execution Address) inbound flow has the same structural weakness: PRC20 funds are minted into an arbitrary recipient contract *before* the code confirms that contract correctly implements the `executeUniversalTx` handler, and by explicit design the CEA path never creates a compensating `INBOUND_REVERT` outbound if that follow-up call fails.

### Finding Description
In `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`, when `utx.InboundTx.IsCEA` is true and the recipient is not a recognized UEA, the code only checks whether the recipient address has *any* bytecode (`k.evmKeeper.GetCodeHash`) to decide `isSmartContract`, then unconditionally deposits the bridged PRC20 amount to that address via `depositPRC20`/`gasAndPayloadDepositAutoSwap`: [1](#0-0) 

Only after that deposit is committed does the module attempt `k.CallExecuteUniversalTx(...)` against the recipient — with no prior validation that the contract actually exposes/implements a compatible `executeUniversalTx` selector: [2](#0-1) 

The `executeUniversalTx` call and gas-fee deduction are wrapped in a `CacheContext` so *that* call can roll back on failure, but the comment makes explicit that the preceding deposit is not part of this safety net:
> "The deposit (above this scope) stays committed regardless."

Crucially, the code comments in both files explicitly document that CEA failures are terminal with no compensating action: [3](#0-2) [4](#0-3) 

So if the recipient contract does not implement `executeUniversalTx` with the exact expected signature (or reverts on it for any reason — access control, missing fallback, wrong ABI, out-of-gas, reentrancy guard, etc.), the `executeUniversalTx` call fails and is recorded as `FAILED`, but the PRC20 deposit that already landed in that contract is not reverted, refunded, or recoverable through any protocol-level path (`buildRevertOutbound`/`INBOUND_REVERT` is only invoked for the non-CEA and pre-deposit-failure branches).

### Impact Explanation
This mirrors the ERC-721 report's core invariant — "the vault should not release value to a party it hasn't confirmed can properly receive/act on it" — except here it's the opposite direction (protocol pushing funds *into* a contract instead of *out*), and the consequence is worse: the funds are minted into a contract with no owner-recognized way to move them out (since it never received a properly authenticated `executeUniversalTx` call), and Push Chain's own accounting explicitly forecloses any automated recovery for this path. The result is a permanent, protocol-acknowledged loss of the bridged PRC20 amount whenever the specified CEA target is incompatible.

### Likelihood Explanation
`Recipient` and `IsCEA` on the inbound come from data an ordinary user supplies when constructing/relaying their cross-chain deposit — no privileged role is required to pick an incompatible contract address as the CEA target (whether by mistake, a buggy dApp integration, or a contract that legitimately reverts under specific conditions such as access control on `executeUniversalTx`). Because the check performed (`GetCodeHash != empty`) only verifies "has bytecode," not "implements the expected interface correctly," this is trivially triggerable through the normal, unprivileged inbound-execution path with honest validators/finalization.

### Recommendation
Before depositing funds to a non-UEA CEA recipient, verify the contract exposes a compatible `executeUniversalTx` selector (e.g., a lightweight static/dry-run call, or an ERC-165-style capability check) and only mint the PRC20 amount after that verification succeeds, wrapping deposit + call in the same all-or-nothing `CacheContext`/atomic unit. Alternatively, if the interface check or `executeUniversalTx` call fails, allow an `INBOUND_REVERT`/refund outbound for the CEA path just as is done for the non-CEA path, instead of leaving funds stuck with only a `FAILED` `PCTx` record.

### Proof of Concept
1. On the source chain, submit a bridging deposit specifying `isCEA = true` and `recipient` = the address of a deployed Push Chain contract that has bytecode but does **not** implement `executeUniversalTx(string,bytes,bytes,uint256,address,bytes32)` (or implements it with access control that reverts for the module sender).
2. Universal Validators observe and vote the inbound to quorum; `ExecuteInboundFundsAndPayload` (or `ExecuteInboundGasAndPayload`) runs.
3. `GetCodeHash` returns non-empty → `isSmartContract = true` → `depositPRC20`/`gasAndPayloadDepositAutoSwap` mints the bridged PRC20 amount into the recipient contract and commits.
4. `CallExecuteUniversalTx` reverts/fails (function does not exist or reverts) → `contractErr != nil` → `callPcTx.Status = "FAILED"` is recorded.
5. Because `IsCEA` is true, no `buildRevertOutbound`/`INBOUND_REVERT` is generated (per the explicit `// isCEA failures never create an INBOUND_REVERT outbound` comment) — the minted PRC20 balance remains permanently locked in the incompatible contract with no protocol-level recovery path.
