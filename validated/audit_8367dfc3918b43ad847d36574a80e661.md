### Title
Module blindly calls `executeUniversalTx` on any deployed contract with non-empty bytecode, with no CEA opt-in verification - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go, x/uexecutor/keeper/evm.go)

### Summary
For `isCEA=true` inbounds, once the recipient is confirmed not to be a UEA, the keeper's only test for whether to invoke the smart-contract path is `codeHash != EmptyCodeHash`, with no additional check that the target contract implements or has registered for the CEA protocol.

### Finding Description
In `ExecuteInboundFundsAndPayload`, when `utx.InboundTx.IsCEA` is true and `CallFactoryGetOriginForUEA` reports the recipient is not a UEA, the code does: [1](#0-0) 
setting `isSmartContract = true` purely from a non-empty `codeHash`. Later this drives an unconditional module-originated EVM call: [2](#0-1) 
which resolves to `CallExecuteUniversalTx`, a `DerivedEVMCall` with `isModuleSender=true` that ABI-encodes and dispatches `executeUniversalTx(sourceChain, ceaAddress, payload, amount, prc20AssetAddr, txId)` against the attacker-chosen `recipientAddr`: [3](#0-2) 

There is no registry, allowlist, or ERC-165/`supportsInterface`-style check anywhere in the codebase confirming the target contract intentionally implements the CEA `executeUniversalTx` interface. Any deployed contract — including ones with no awareness of Push Chain's CEA protocol — satisfies "non-empty codeHash" and will receive this module-originated call.

### Impact Explanation
Practically, the call the module makes is ABI-encoded with a fixed 4-byte selector for `executeUniversalTx(string,bytes,bytes,uint256,address,bytes32)`. For the call to actually mutate a "victim" (non-opted-in) contract's state, that contract would need to happen to expose a function whose selector collides with this exact signature (fallback-style dispatch of an arbitrary raw payload embedded mid-calldata is not reachable, since the attacker only controls the `payload` and `sourceChain`/`ceaAddress` fields inside the ABI encoding, not the leading selector or overall calldata layout). This limits practical exploitation largely to contracts that deliberately or accidentally implement this specific function signature. The design intent, per the documentation and dedicated integration tests, does appear to be that any contract implementing `executeUniversalTx` is treated as CEA-capable purely by exposing that function — no explicit registry-based opt-in exists. [4](#0-3) [5](#0-4) 

Because gas fee deduction (`DeductGasFeesFromReceipt`) is wrapped in a `CacheContext` with rollback on fee failure, unfunded/unaware contracts that don't hold `upc` for gas will have their `executeUniversalTx` call and any resulting state mutation discarded — this significantly narrows unsolicited mutation to only contracts that (a) implement the exact selector and (b) hold enough native gas token to pay the deducted fee. [6](#0-5) 

### Likelihood Explanation
Low-to-moderate. Exploitation requires an unaware, funded contract that happens to expose a function with the exact `executeUniversalTx(string,bytes,bytes,uint256,address,bytes32)` selector — this is not a generic "any contract with bytecode" compromise as the question implies, because arbitrary raw calldata forwarding (e.g., via proxy fallback delegatecall) is not achievable through this fixed ABI-encoded dispatch.

### Recommendation
Add an explicit CEA opt-in check before invoking `executeUniversalTx` on a non-UEA recipient — e.g., an ERC-165 `supportsInterface` probe for a dedicated CEA interface ID, or a registry/allowlist maintained in `x/uregistry` that contracts must register into, rather than inferring "smart contract" status solely from `codeHash != EmptyCodeHash`.

### Proof of Concept
1. Deploy a contract on Push Chain that happens to implement (deliberately, to simulate an "unaware" victim reusing this common-looking function name) `function executeUniversalTx(string,bytes,bytes,uint256,address,bytes32)` with state-mutating logic, and fund it with `upc`.
2. Submit an inbound with `IsCEA=true`, `Recipient` set to that contract, and an arbitrary `payload`.
3. Have honest validators vote to finalize the inbound.
4. Observe `ExecuteInboundFundsAndPayload` invoke `CallExecuteUniversalTx` against the contract and mutate its storage using attacker-supplied `payload` bytes, as shown by the existing `deployStatefulRecipientContract` test pattern. [7](#0-6)

// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
}
