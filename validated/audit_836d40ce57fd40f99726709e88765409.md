### Title
Two-phase check-then-lock in `try_lock_transaction_batch` allows simultaneous write and read locks on the same account within one batch - (File: `accounts-db/src/account_locks.rs`)

### Summary
`AccountLocks::try_lock_transaction_batch` validates every transaction in a batch against the *current* (pre-batch) state of `self` in a first pass, and only mutates the lock tables in a second pass. Because the validation pass never reflects locks that earlier transactions *in the same batch* are about to take, two transactions in one batch that touch the same account with conflicting access (one writable, one read-only) can both pass validation and then both be granted their locks, producing a state where `is_locked_write(A)` and `is_locked_readonly(A)` are simultaneously true for the same account.

### Finding Description
`try_lock_transaction_batch` is implemented as: [1](#0-0) 

The first `for_each` loop calls `self.can_lock_accounts(keys.clone())` for every transaction, but `can_lock_accounts` is a pure read (it never mutates `write_locks`/`readonly_locks`): [2](#0-1) 

`can_write_lock`/`can_read_lock` rely solely on `is_locked_write`/`is_locked_readonly`, which only look at whatever is already committed in `self.write_locks`/`self.readonly_locks` at the time of the call: [3](#0-2) 

Because the check pass does not update `self` after each transaction is validated, if a caller supplies a batch containing transaction T1 (writes account `A`) and transaction T2 (reads account `A`) together, both are checked against the *same* unlocked pre-batch state: `can_write_lock(A)` returns `true` for T1 (nothing is locked yet) and `can_read_lock(A)` also returns `true` for T2 (write lock for T1 has not actually been applied yet, since the first pass never calls `lock_write`/`lock_readonly`). Both transactions are therefore marked `Ok`, and the second pass unconditionally applies `lock_accounts` for every `Ok` entry, calling `lock_write(A)` for T1 and `lock_readonly(A)` for T2. After this, `is_locked_write(&A) == true` and `is_locked_readonly(&A) == true` hold at the same time — the exact invariant the audit question asks about is broken by the batch-locking driver around `is_locked_write`, not by `is_locked_write` itself (which is a correct simple counter check).

This is reachable purely by an attacker submitting two of their own transactions (T1 writing account `A`, T2 read-locking account `A`) that end up validated together as one "batch" passed to `try_lock_transaction_batch`. I was not able to fully trace, within the available tool budget, the exact call site in `accounts-db/src/accounts.rs` that constructs the `validated_batch_keys` vector and determines whether/when multiple transactions from a single attacker can be coalesced into one call to `try_lock_transaction_batch` (this needs further confirmation with a Devin session that can read the full call site and the batching/scheduler code that decides what goes into one batch). If any code path forwards a set of transactions to this function without having already pairwise-conflict-filtered them, the mutual-exclusion invariant is violated by design of this function, independent of any other safeguard.

### Impact Explanation
If two transactions with conflicting write/read access to the same account can be locked simultaneously and then executed concurrently (which is the entire purpose of taking these locks — to serialize access before parallel execution), this can produce divergent execution ordering/results between validators (a validator that happens to interleave the two transactions' account reads/writes differently than another), leading to bank hash divergence — a Critical Consensus/Safety Violation as scoped in the question.

### Likelihood Explanation
Exploitability depends entirely on whether any real call site can present `try_lock_transaction_batch` with a set of transactions that were not already filtered to be pairwise non-conflicting (e.g., a scheduler bug, or a design where a "batch" is not guaranteed conflict-free before this call). This function's own two-phase implementation provides no defense against that scenario — it does not detect or reject intra-batch conflicts by itself. Without being able to confirm the exact caller guarantees in `accounts-db/src/accounts.rs` (not fully traced due to tool-call limits), I cannot confirm this is reachable end-to-end from an unprivileged attacker's transaction submission alone.

### Recommendation
Make `try_lock_transaction_batch` self-defending regardless of caller assumptions: perform validation and locking incrementally per-transaction within a single pass (check `can_lock_accounts`, and if `Ok`, immediately call `lock_accounts` before validating the next transaction in the batch), so that later transactions in the same batch are checked against the locks already taken by earlier transactions in that same batch, rather than against a stale pre-batch snapshot.

### Proof of Concept
Add a unit test in `accounts-db/src/account_locks.rs`'s `#[cfg(test)] mod tests`:
```rust
#[test]
fn test_try_lock_transaction_batch_intra_batch_conflict() {
    let mut account_locks = AccountLocks::default();
    let account_a = Pubkey::new_unique();

    // tx1: writes account_a
    let tx1_keys = vec![(&account_a, true)];
    // tx2: reads account_a
    let tx2_keys = vec![(&account_a, false)];

    let batch: Vec<TransactionResult<_>> =
        vec![Ok(tx1_keys.into_iter()), Ok(tx2_keys.into_iter())];

    let results = account_locks.try_lock_transaction_batch(batch);

    // Assert the invariant: never both write-locked and read-locked at once.
    let write_and_read_both_locked =
        account_locks.is_locked_write(&account_a) && account_locks.is_locked_readonly(&account_a);
    assert!(
        !write_and_read_both_locked,
        "account {:?} is simultaneously write-locked and read-locked: results={:?}",
        account_a, results
    );
}
```
Expected (buggy) behavior: both `results` entries are `Ok(())`, and the final assertion fails because `is_locked_write(&account_a)` and `is_locked_readonly(&account_a)` are both `true` after the call — demonstrating the invariant break directly against `is_locked_write`/`is_locked_readonly`.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_write(&self, key: &Pubkey) -> bool {
        self.write_locks.get(key).is_some_and(|count| *count > 0)
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }
