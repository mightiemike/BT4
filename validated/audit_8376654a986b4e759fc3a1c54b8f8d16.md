### Title
Deterministic Accounts Can Reference a Mutable `GlobalContractIdentifier::AccountId`, Breaking the "Fixed Code" Invariant and Allowing Funds Held by Deterministic Accounts to Be Rug-Pulled - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
The TokenVault bug allowed an owner-controlled `identifier -> address` mapping to be changed after the fact, breaking the assumption that a currency identifier always resolves to the same, immutable token address, which could halt withdrawals or redirect calls. NEAR's deterministic-account feature (`0s...` accounts, NEP-616) has an analogous mutable-binding problem: a deterministic account's identity is documented as "fixed code and fixed initial state" [1](#0-0) , but the `code` field of `DeterministicAccountStateInitV1` can be a `GlobalContractIdentifier::AccountId`, which is explicitly designed to be redeployable/mutable by its owning account at any time [2](#0-1) .

### Finding Description
`DeterministicAccountStateInitV1` stores its code as a `GlobalContractIdentifier`, which is one of two variants: `CodeHash` (immutable, content-addressed) or `AccountId` (mutable, addressed by an account that can redeploy new code under the same identifier) [3](#0-2) . The deterministic account ID is derived purely from the borsh-serialized `DeterministicAccountStateInit` (which for `AccountId` mode only commits to the *account id string*, not to any code hash) [4](#0-3) .

When a `DeterministicStateInitAction` is applied, the account's contract is set via `use_global_contract`, which for the `AccountId` variant sets `AccountContract::GlobalByAccount(id)` — i.e., the account's code is *not* copied into the account, but is a live reference to whatever code currently sits at that global-contract account id [5](#0-4) . `deploy_deterministic_account` does exactly this at account-creation time and never freezes/pins the code [6](#0-5) .

Separately, the `GlobalContractDeployMode::AccountId` mode is explicitly documented to let the owning account "update the contract for all its users" by redeploying new code under the same account id at any later time [7](#0-6) , and `action_deploy_global_contract` performs this redeploy without any restriction tied to already-created deterministic accounts referencing it [8](#0-7) , [9](#0-8) .

This produces the exact TokenVault-class flaw: the association between a fixed identifier (the deterministic account's `code` field / derived id) and the actual executable content behind it is not immutable when `AccountId` mode is used, even though the entire security model of deterministic accounts assumes fixed code tied to a fixed id (the NEP-616 design and docs explicitly call this out: "Deterministic accounts have a fixed code and fixed initial state associated with it") [10](#0-9) . A user (or protocol/dApp) that creates or funds a deterministic account referencing a `GlobalContractIdentifier::AccountId` is trusting that the code will never change; but the owner of that global-contract account can redeploy arbitrary new WASM under the same identifier at any point after the deterministic account has accumulated a balance, and that new code becomes the deterministic account's contract logic on the very next call.

### Impact Explanation
Any deterministic account created with `code: GlobalContractIdentifier::AccountId(owner)` silently inherits whatever code `owner` deploys in the future. If `owner` (or an attacker who compromises/social-engineers `owner`, or a malicious dApp author who published such a global-contract account id for wide reuse) redeploys malicious code, every deterministic account that was created pointing at that identifier and holds a NEAR balance can have that balance drained via a crafted `FunctionCall`/`Promise` inside the new code, executed with the deterministic account's own authority (its balance, its access to any `Transfer`/`FunctionCall` promises it can issue). This is unauthorized value movement / permanently frozen or stolen funds for any holder of such a deterministic account, triggered purely by a transaction from the global-contract owner (`DeployGlobalContractAction`) followed by any transaction invoking the victim account — no validator or network-layer compromise required.

### Likelihood Explanation
Reachable entirely through ordinary, unprivileged transactions: (1) deploy a global contract in `AccountId` mode, (2) have users create deterministic accounts referencing that identifier and fund them (a natural pattern encouraged by helper contracts, e.g. the `spread()` "sharded contract" pattern in `runtime/near-test-contracts/sharded-contract/src/lib.rs` deliberately creates deterministic accounts backed by `GlobalContractIdentifier::AccountId` [11](#0-10) ), (3) redeploy new code under the same account id later. No special privilege is required beyond owning the account used as the global-contract identifier, which is by definition attacker-controllable if the attacker is the one who published/offered the shared contract. Because this is a documented, intentional capability of `AccountId`-mode global contracts rather than an implementation bug, the likelihood of it being exploited depends on ecosystem adoption of `AccountId`-mode global contracts as the `code` for deterministic accounts holding value — but nothing in validation prevents this combination, and the currently indexed code offers no warning, opt-out, or pinning mechanism for it.

### Recommendation
1. Require or strongly discourage deterministic accounts from referencing `GlobalContractIdentifier::AccountId` when the deterministic account will hold value; ideally, only allow `GlobalContractIdentifier::CodeHash` (immutable) for `DeterministicAccountStateInitV1::code`, consistent with the "fixed code" invariant documented for deterministic accounts.
2. If `AccountId` mode must remain supported for deterministic accounts, pin the resolved code hash at state-init time (store it in the account state) so that subsequent redeployments to the same `AccountId` identifier do not retroactively change already-created deterministic accounts' behavior.
3. Add explicit documentation/warnings (and ideally a validation error) surfaced at `validate_deterministic_state_init` time when `GlobalContractIdentifier::AccountId` is used, since this directly contradicts the "fixed code and fixed initial state" guarantee advertised for deterministic accounts.

### Proof of Concept
1. Attacker account `attacker.near` deploys a benign-looking global contract via `DeployGlobalContractAction { deploy_mode: AccountId }` (`GlobalContractIdentifier::AccountId(attacker.near)`).
2. Victim (or a dApp) creates a deterministic account via `DeterministicStateInitAction` with `state_init.code = GlobalContractIdentifier::AccountId(attacker.near)`, funds it with NEAR (covered by `deposit`), per `action_deterministic_state_init`/`deploy_deterministic_account` [12](#0-11) .
3. The deterministic account accumulates balance over time through normal use (transfers, protocol logic).
4. `attacker.near` submits a new `DeployGlobalContractAction { deploy_mode: AccountId }` with malicious code (e.g., a `FunctionCall` handler that creates a `Promise` transferring the calling account's balance to `attacker.near`), which is distributed and replaces the code referenced by `AccountContract::GlobalByAccount(attacker.near)` for every account using it, per `initiate_distribution`/`apply_distribution_current_shard` [9](#0-8) , [13](#0-12) .
5. Any subsequent `FunctionCall` transaction against the victim deterministic account now executes the attacker's new code with the deterministic account's own authority, allowing the attacker to move or lock the victim's accumulated balance without the victim's consent.

Note: I could not find any protocol-level restriction, warning, or pinning mechanism in the indexed code that prevents step 4 from affecting already-created deterministic accounts from step 2; this analysis is based on the currently indexed files and documentation, and a full end-to-end runtime reproduction (compiling and running a test-loop scenario) would require the fuller repository access a Devin session could provide.

/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

fn apply_distribution_current_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
) -> Result<Compute, RuntimeError> {
    let identifier = match &global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => GlobalContractCodeIdentifier::CodeHash(*hash),
        GlobalContractIdentifier::AccountId(account_id) => {
            GlobalContractCodeIdentifier::AccountId(account_id.clone())
        }
    };

    let is_nonce_fresh = check_and_update_nonce(global_contract_data, &identifier, state_update)?;
    if !is_nonce_fresh {
        return Ok(0);
    }

    let config = apply_state.config.wasm_config.clone();
    let trie_key = TrieKey::GlobalContractCode { identifier };
    let code_len = global_contract_data.code().len() as u64;
    state_update.set(trie_key, global_contract_data.code().to_vec());

    // Record the deploy so a same-chunk call can find the code without a warm cache.
    let code_hash = match global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => Some(*hash),
        GlobalContractIdentifier::AccountId(_) => None,
    };
    if ProtocolFeature::GlobalContractSameChunkCallFix.enabled(apply_state.current_protocol_version)
    {
        state_update.record_global_contract_deploy(ContractCode::new(
            global_contract_data.code().to_vec(),
            code_hash,
        ));
    }

    state_update.commit(StateChangeCause::ReceiptProcessing { receipt_hash: receipt.get_hash() });

    precompile_contract_with_warming(
        &ContractCode::new(global_contract_data.code().to_vec(), code_hash),
        config,
        apply_state.next_wasm_config.clone(),
        apply_state.cache.as_deref(),
    );
    near_vm_runner::report_metrics(apply_state.shard_id, "global_contract");
    let fees = &apply_state.config.fees;
    let per_byte_total = fees
        .deploy_global_contract_execution_per_byte
        .checked_mul(code_len)
        .ok_or(IntegerOverflowError)?;
    let compute = fees
        .deploy_global_contract_execution_base
        .checked_add(per_byte_total)
        .ok_or(IntegerOverflowError)?;
    Ok(compute)
}

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition. "uninit" here is the
        // NEP-616 sense, a deterministic account with no contract yet, not
        // `Account::Uninitialized`: a `0u` id can never reach this, because
        // `validate_deterministic_state_init` pins the receiver to the derived
        // `0s` id.
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }
    if result.result.is_err() {
        return Ok(());
    }

    settle_state_init_deposit(
        account,
        action.deposit,
        account_id,
        receipt,
        &apply_state.config,
        result,
    )
}
