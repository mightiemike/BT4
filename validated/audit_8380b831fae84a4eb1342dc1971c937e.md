## Analysis

The reported Polynomial bug is a **griefing pattern**: a queued backlog (`queuedPerpSize`) is only drained when a gating condition (`order.sizeDelta == 0`) is true, but the code that runs when the gate opens processes only the *newest* increment (`sizeDelta`) rather than the backlog, and an unprivileged actor can repeatedly re-trigger the "new increment" path immediately after the gate opens, so the backlog is never actually drained.

nearcore has a directly analogous structural pattern in the chunk-apply receipt scheduler, reachable by an ordinary transaction signer.

### Root cause

`Runtime::process_receipts` (`runtime/runtime/src/lib.rs:2787-2843`) processes receipts strictly in the order **local → delayed → incoming**, each gated by the *same* shared `compute_limit`/`total.compute` budget: [1](#0-0) 

`process_local_receipts` (`runtime/runtime/src/lib.rs:2486-2560`) iterates every new local receipt (receipts where `signer_id == receiver_id`, generated by transactions the attacker submits themselves) and only defers a receipt to the delayed queue once `processing_state.total.compute >= compute_limit`: [2](#0-1) 

`process_delayed_receipts` (`runtime/runtime/src/lib.rs:2570-2663`) — which is supposed to drain the persistent backlog of previously-delayed receipts (analogous to `queuedPerpSize`) — runs strictly *after* local receipts and its very first loop check breaks immediately if the compute budget is already exhausted: [3](#0-2) 

The compute budget itself equals the chunk gas limit (`apply_state.gas_limit`), a single fixed pool shared by all three phases: [4](#0-3) 

### Finding

An attacker who controls one signing account can submit, in every chunk on the shard, a set of self-directed transactions (`signer_id == receiver_id`, e.g. repeated `FunctionCall`/`Transfer` to itself) sized to consume the *entire* per-chunk compute budget as local receipts. Because `process_local_receipts` runs first and is capped only by the shared budget, and `process_delayed_receipts` runs second and bails out immediately once that budget is spent, the delayed-receipt backlog — which can contain other users' pending cross-shard action receipts, refunds, and callback executions — never shrinks for as long as the attacker keeps flooding local receipts. This mirrors the report's dynamic exactly: a queue/backlog that only drains when a gate is open, and an unprivileged actor who can perpetually keep that gate closed for backlog draining by prioritizing self-submitted "current work" every single round (`runtime/runtime/src/lib.rs:2799-2813`, docs corroborate: `protocol-model/spec/runtime-execution.md:39` — "local → delayed → incoming order matters").

This is a genuine, reachable griefing vector that "has a counter" (the attacker must keep paying gas every chunk, same rationale the original judge used to set Medium severity), so it fits a Medium-severity analog rather than a resource-only/no-impact issue: it produces an indefinite, attacker-controlled halt of progress on the delayed-receipt queue, during which other users' funds/receipts tied to those delayed receipts remain functionally frozen.

### Title
Attacker can indefinitely starve the delayed-receipt backlog by flooding local receipts every chunk - (File: `runtime/runtime/src/lib.rs`)

### Summary
`Runtime::process_receipts` processes new **local** receipts before draining the **delayed** backlog, both gated by the same shared per-chunk `compute_limit`. Any account can submit self-directed transactions each block that consume the entire compute budget as local receipts, causing `process_delayed_receipts` to break out on its very first iteration every single chunk, so the delayed queue never drains as long as the attacker repeats the flood.

### Finding Description
`process_receipts` (`runtime/runtime/src/lib.rs:2799-2813`) calls, in order, `process_local_receipts`, then `process_delayed_receipts`, then `process_incoming_receipts`, all against one shared `compute_limit = apply_state.gas_limit` (`:2795-2797`). `process_local_receipts` (`:2513-2522`) only stops feeding local receipts into execution once `processing_state.total.compute >= compute_limit`; until then it happily executes every local receipt supplied in the chunk. `process_delayed_receipts` (`:2591-2596`) is the mechanism that is supposed to drain the persistent, trie-stored backlog of previously delayed receipts (belonging to potentially unrelated accounts/shards), but its loop condition breaks immediately if `total.compute` is already at or above the limit — which will always be true if local receipts alone consumed the whole budget.

Because a transaction where `signer_id == receiver_id` is classified as a **local** receipt and processed with priority over the delayed backlog, a single account can, every chunk, submit enough self-directed transactions (e.g., cheap `Transfer` or gas-heavy `FunctionCall`s to itself) to saturate `compute_limit` before any delayed receipt is even attempted. This is structurally identical to the reported bug: a backlog accumulator is only drained through a gate that closes as soon as "new work" is submitted, and the "new work" path takes precedence every time the gate opens, so an unprivileged actor can perpetually re-close the gate.

### Impact Explanation
Receipts sitting in the delayed queue can represent other users' pending cross-shard actions, refunds, or callback executions with attached deposits. If the delayed queue is prevented from draining for an extended period, those funds/state transitions are functionally frozen for as long as the attack continues, and the backlog (and the associated `receipt_bytes`/`delayed_receipts_gas` congestion metrics) grows unbounded, worsening `CongestionInfo.congestion_level` and potentially triggering `shard_accepts_transactions` rejections for the whole shard (`core/primitives/src/congestion_info.rs:44,123`), collaterally impacting unrelated users beyond the attacker's own delayed receipts.

### Likelihood Explanation
The attack requires no privileges beyond being able to sign and submit ordinary transactions with `signer_id == receiver_id`, and no special contract deployment. It is a sustained-cost griefing attack (the attacker pays real gas every chunk to keep flooding), giving it a natural economic "counter" similar to the original finding, but it is trivially repeatable and does not require any race condition or precise timing — only that local-receipt gas consumption reach `compute_limit` each chunk.

### Recommendation
Interleave or budget-share local, delayed, and incoming receipt processing (e.g., reserve a guaranteed minimum fraction of `compute_limit` for delayed-queue draining each chunk, or process delayed receipts before/concurrently with local receipts) so that a shard's own newly-submitted local work cannot unconditionally starve the delayed backlog. This mirrors the original recommendation of ensuring the accumulated backlog is always given a path to be submitted rather than being perpetually deferred by newly arriving work.

### Proof of Concept
1. Attacker account `A` waits until the shard's delayed-receipt queue is non-empty (naturally occurs whenever a chunk was previously compute-limited, per `runtime/runtime/src/lib.rs:2513-2521`).
2. Every subsequent chunk, `A` submits a batch of self-directed transactions (`signer_id == receiver_id`) sized so that `process_local_receipts` alone consumes `>= compute_limit` (`runtime/runtime/src/lib.rs:2486-2560`).
3. `process_delayed_receipts` (`runtime/runtime/src/lib.rs:2591-2596`) checks `total.compute >= compute_limit` on its very first loop iteration and breaks immediately without popping any delayed receipt.
4. Repeat step 2 every chunk; the delayed queue length never decreases, and any receipts belonging to other users placed in that queue remain unexecuted indefinitely.
