## Title
Wallet Contract's `has_in_flight_tx` guard can become permanently stuck, freezing an ETH-implicit account's funds — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The bug report is about a per-user proxy contract (`YieldAccount`) whose mandatory "unlock" step (`onERC721Received`) is never satisfied, so the withdrawal permanently reverts and funds are stuck behind an incompatible callback requirement. The closest reachable analog in nearcore is the **NEP-518 Wallet Contract** (`AccountContract::Global` code deployed for every ETH-implicit account), which gates *all* future `rlp_execute` calls behind an in-memory boolean, `has_in_flight_tx`, that can only be cleared by one of its own `#[private]` promise callbacks completing successfully. If any of those callbacks traps instead of returning normally, the flag is never cleared and the account — which by protocol design can never get a `FullAccess` key or be deleted — is locked forever.

### Finding Description
Every mutating entry point of the Wallet Contract enforces a single-flight invariant: [1](#0-0) 

`rlp_execute` refuses to run if `has_in_flight_tx` is `true`: [2](#0-1) 

The flag is cleared only inside `#[private]` callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), which are invoked asynchronously via `.then(...)` after the wallet's own promise chain resolves: [3](#0-2) [4](#0-3) [5](#0-4) 

Two of these callbacks deserialize attacker/contract-influenced cross-contract response bytes with `serde_json::from_slice` *before* the line that clears the flag has any chance to persist: [6](#0-5) [7](#0-6) 

Under NEAR's WASM contract execution model, a contract's mutable state (`near_bindgen`-derived `WalletContract`) is only persisted back to storage if the exported function returns normally. If it traps (out-of-gas, stack overflow from adversarial input, or any other unrecoverable guest error) at *any* point — even after the `self.has_in_flight_tx = false;` assignment earlier in the same function body — the entire receipt's state changes are discarded, exactly as if the function had never executed. Since `has_in_flight_tx = true` was already durably committed in the prior receipt (the one that spawned this callback), a trap inside the callback leaves the flag permanently `true`. There is no other action or callback that can clear it: every reset path is `#[private]`, reachable only through the wallet's own promise resolution, not by any direct transaction.

Once `has_in_flight_tx` is stuck at `true`, `rlp_execute` unconditionally rejects every future call, for anyone (owner or relayer). Per protocol, an ETH-implicit account "can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added": [8](#0-7) 

Hence there is no recovery path — this is structurally the same as the reported bug class: a mandatory account-specific callback (analogous to `onERC721Received`) that, if not correctly reached/executed, permanently traps the account's assets behind an implicit interface it cannot satisfy again.

### Impact Explanation
Any NEAR balance and NEP-141/ERC-20 token balances held by the affected ETH-implicit account become permanently unreachable — no transfer, function call, key-add, or key-delete is possible through the only interface these accounts expose. This is a full, irreversible loss-of-funds condition for that account, matching the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Triggering requires driving one of the two JSON-deserializing callbacks (`address_check_callback` reading the address registrar's `lookup` response, or `nep_141_storage_balance_callback` reading a NEP-141 contract's `storage_balance_of` response) into a WASM trap after the flag has been durably set. Both callback targets (the token contract for an ERC-20-style transfer, or any contract claiming to be the address registrar's dependency) can return attacker-crafted response payloads sized/shaped to exceed the callback's statically reserved gas (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`) during `serde_json::from_slice`, or to induce a stack overflow via deep nesting. This only requires an unprivileged actor to get the wallet owner (or a relayer acting for them) to route a `rlp_execute` call whose `target` is a malicious/compromised token/registrar-dependent contract — a realistic condition given tokens are frequently third-party, upgradeable contracts.

### Recommendation
- Reserve callback gas generously and independent of attacker-controlled response size, or cap/validate the size of cross-contract response bytes before attempting `serde_json::from_slice`.
- Clear `has_in_flight_tx` as the very first durable action rather than relying on function-return-based persistence, e.g. by using a two-phase approach (write the "cleared" state immediately via a dedicated low-gas helper before doing any additional parsing), or by adding a time/height-based fallback (e.g., a permissionless "unstick" method guarded by a timeout) so the invariant cannot be wedged indefinitely by a single failed callback.
- Bound/validate untrusted JSON before deserialization (e.g., enforce a maximum byte length and nesting depth) to eliminate the trap vector entirely.

### Proof of Concept
1. Deploy (or compromise) a NEP-141-like contract `T` whose `storage_balance_of` method returns an adversarially large/deeply-nested JSON payload (still within max return-value limits).
2. From an ETH-implicit account `W` (Wallet Contract), submit a `rlp_execute` transaction encoding an ERC20Transfer against `T` (`target = T`), which routes through `Promise::new(T).function_call("storage_balance_of", ...)` `.then(nep_141_storage_balance_callback)`, setting `has_in_flight_tx = true` durably.
3. When the callback receipt executes, `serde_json::from_slice::<Option<StorageBalance>>(&value)` on `T`'s crafted payload causes the wasm execution to run out of the statically reserved callback gas (or trap on a deep-recursion parse), before any state write-back.
4. The receipt fails; `WalletContract`'s state is unchanged from the prior "in-flight" snapshot — `has_in_flight_tx` remains `true`.
5. Any subsequent `rlp_execute` call to `W`, from any signer, is rejected with `"transaction already in progress"` forever, verified against the check at [9](#0-8) , with no other on-chain action able to clear the flag or otherwise access `W`'s funds.

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
