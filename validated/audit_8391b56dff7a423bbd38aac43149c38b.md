## Title
Metering credit conversion can round down to zero for small resource spends, allowing workflow owners to evade CRE billing - (File: `core/services/workflows/metering/balance_store.go`)

### Summary
The Chainlink CRE (Chainlink Runtime Environment) workflow metering system converts a capability's raw resource usage (gas, compute, etc.) into "universal credits" before deducting them from a workflow's billing balance. For gas-denominated spend, this conversion divides the resource amount by a conversion rate and rounds the result to a fixed decimal precision. This is structurally the same bug class as the reported PooledCreditLine issue: a division whose result can legitimately round to zero when the numerator is small relative to the divisor/precision, letting an unprivileged actor (a workflow owner submitting CRE workflow executions) evade paying for consumed resources by keeping each individually-billed increment below the rounding threshold.

### Finding Description
`convertToBalance` in `core/services/workflows/metering/balance_store.go` performs the resource→credit conversion: [1](#0-0) 

For gas spend types it computes `amount.Div(rate).Round(defaultDecimalPrecision)`, where `defaultDecimalPrecision` is fixed at 10 decimal places: [2](#0-1) 

This conversion is invoked from `Report.Settle`, which aggregates per-node spend reports for a capability step, converts the unit-shifted gas amount (`value.Shift(18)`) via `ConvertToBalance`, and adds the resulting credits to `spentCredits`, which is what ultimately gets reported to the billing service and deducted from the workflow's local balance: [3](#0-2) 

Because `Div(...).Round(10)` truncates any fractional credit amount smaller than `1e-10` credits to exactly zero, any individual gas-spend report whose true credit value falls below that threshold contributes `0` to `spentCredits` — identical in mechanism to the original Solidity bug where `principal * rate * time / YEAR / SCALE` truncates to zero for small enough inputs.

### Impact Explanation
A workflow owner (an unprivileged CRE platform user, not a node operator) controls how many discrete capability-invocation steps their workflow performs and can structure a workflow to repeatedly perform many cheap, gas-spending capability calls instead of fewer, larger ones. If the per-step reported gas amount (after unit shifting and dividing by the configured gas-per-credit rate) is small enough to round to zero at 10-decimal precision, that step's `AggregatedSpends`/`spentCredits` contribution is `0`, even though real node/network resources (gas, RPC calls, compute) were consumed on the workflow owner's behalf. Repeated across many steps or many workflow executions, this allows systematic under-billing of the workflow owner, i.e. a metering/billing bypass reachable purely through user-controlled workflow structure — a misreporting/tampering-adjacent impact on the CRE billing trust boundary. The existing test suite already documents a related "settles zero value rate" case that converts a nonzero gas spend to `0` credits, confirming the mechanism exists and is treated as expected behavior rather than defended against: [4](#0-3) 

### Likelihood Explanation
Likelihood is Medium: the workflow owner is fully unprivileged and only needs to control workflow shape (number and size of capability calls), which is normal, permitted usage of the platform — no node compromise or protocol violation is required. However, exploitability is bounded by real-world costs: to trigger the zero-rounding, the *actual* gas usage per settled step must be genuinely tiny relative to the configured gas-per-credit rate, and truly consequential capability actions (e.g., real EVM writes) tend to have meaningful minimum gas costs. The bug is most exploitable when the configured `GasTokensPerCredit` rate is large (gas is "cheap" relative to credits) or when compute/other resource rates interact with `defaultDecimalPrecision` in a way that a burst of many tiny steps each dodges billing while still consuming node compute/RPC resources.

### Recommendation
- Track and carry forward rounding remainders instead of discarding them per step (e.g., accumulate sub-precision fractional credits across `Settle` calls within a `Report` and only round once at receipt-submission time).
- Alternatively, increase `defaultDecimalPrecision` or perform gas/credit conversion in fixed-point integer arithmetic with a global remainder ledger, mirroring the "scale principal to 1e18 precision" mitigation recommended in the original report, so that no individual conversion silently truncates a nonzero true value to zero.
- Add a monitoring/alerting check that flags workflows with unusually high step counts and per-step spend values consistently near the rounding threshold, similar to how `switchToMeteringMode` already guards against multiple gas executions in a single step (`core/services/workflows/metering/metering.go` lines 463-465).

### Proof of Concept
1. Configure `GasTokensPerCredit` with a large value (gas is cheap relative to credit, as in the "successfully settles zero value rate" test scenario) via `GetWorkflowExecutionRates`.
2. Design a CRE workflow that performs many capability invocations, each reporting a very small `SpendValue` for `testUnitGas` (e.g., `"0.000700000000000000"` as used in the existing test), such that after `value.Shift(18)` and `Div(rate).Round(defaultDecimalPrecision)` in `convertToBalance`, the resulting per-step credit contribution is `0`.
3. Repeat across many workflow executions/steps; each `Settle` call adds `0` to `spentCredits`, and `SubmitWorkflowReceipt` reports `CreditsConsumed: "0"` despite nonzero real resource usage, exactly as demonstrated in `core/services/workflows/metering/metering_test.go` lines 1005-1017 (`{Peer2PeerID: "xyz", SpendUnit: testUnitGas, SpendValue: "0.000700000000000000"}, // should convert to 0 credits`).

```go
func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(fromResourceType) {
		if rate.IsZero() {
			return decimal.Zero, nil
		}

		return amount.Div(rate).Round(defaultDecimalPrecision), nil
	}

	return amount.Mul(rate), nil
}
```
