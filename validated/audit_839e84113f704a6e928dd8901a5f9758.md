### Title
Signer State-Machine Agreement Threshold Rounds Down While Nakamoto Block Approval Threshold Rounds Up, Causing Off-by-One Weight-Threshold Divergence - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
`GlobalStateEvaluator::reached_agreement` computes the 70% signer-weight consensus threshold using **floor** division, while the analogous on-chain threshold used to actually approve a Nakamoto block, `NakamotoBlockHeader::compute_voting_weight_threshold`, computes the same 70% threshold using **ceiling** division. This is the same class of defect as the Bond `marketPrice`/`_currentMarketPrice` rounding mismatch: two implementations of one specification value round in opposite directions, breaking the equality that both are supposed to enforce.

### Finding Description
The canonical 70%-of-weight approval threshold used to accept a Nakamoto block signature set is computed with a ceiling (round-up) division: [1](#0-0) 

```rust
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
```
i.e. `threshold = ceil(total_weight * 7 / 10)`. This is used directly to gate whether a block is accepted: [2](#0-1) 

However, the signer-side `GlobalStateEvaluator`, which is used across `libsigner`/`stacks-signer` to decide whether the signer network has reached agreement on protocol version, burn view, current-miner state, and transaction-replay set, computes the *same* 70% threshold using floor division combined with `>=`: [3](#0-2) 

```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```
i.e. `agreement iff vote_weight >= floor(total_weight * 7 / 10)`.

For any `total_weight` where `total_weight * 7` is not a multiple of 10 (the overwhelmingly common case), `floor(total_weight*7/10) < ceil(total_weight*7/10)`. Concretely, for `total_weight = 511` (used as the round-up regression test for the node-side function): [4](#0-3) 

- Node-side (`compute_voting_weight_threshold`): `ceil(511*7/10) = 358`.
- Signer-side (`reached_agreement`): `floor(511*7/10) = 357`.

So `reached_agreement(357)` returns `true` while `verify_signer_signatures`/`compute_voting_weight_threshold` would require `358` weight to actually approve a block with that same `total_weight`. This is a direct analog of the Bond issue: the specification (70% weight quorum) is rounded up in the code path that decides real on-chain state (block acceptance) but rounded down in the sibling code path (`GlobalStateEvaluator`) that signers use to decide their own local beliefs about global consensus state (current miner, burn view, protocol version, replay set).

### Impact Explanation
`GlobalStateEvaluator::reached_agreement` gates `determine_global_state`, `determine_global_burn_view`, and `determine_latest_supported_signer_protocol_version`, all of which drive what a signer believes is the agreed-upon miner/tenure/burn-view/protocol version and therefore what it is willing to sign: [5](#0-4) 

Because this threshold is systematically one weight-unit lower than the actual block-approval threshold, a marginal (minority-weight) signer's presence or absence in a given vote tally can make `reached_agreement` flip to `true` at a weight sum that a node applying `compute_voting_weight_threshold` would still consider *insufficient* for block approval. This produces a divergence bounded to a single low-weight signer's worth of weight between what signers believe is "global consensus" and what the chain layer actually requires for block approval — i.e., a minority-weight-triggerable, non-majority-required divergence in state-machine agreement views across signers, consistent with the "temporary tip disagreement" / "signer weight below threshold" category.

### Likelihood Explanation
This is not a rare edge case — it occurs whenever `total_weight * 7 mod 10 != 0`, which is the generic case for any reward-cycle signer-weight total. No malicious majority is required; the discrepancy is baked into the code and is exposed by the natural variance of per-cycle total stacked weight. The regression tests already demonstrate the exact off-by-one behavior for both the ceiling function (`total_weight=511` case) and the floor-based evaluator (`total_weight=2_000_000_000` overflow regression), showing the authors are aware of rounding subtleties but did not reconcile the two implementations.

### Recommendation
Change `GlobalStateEvaluator::reached_agreement` (and correspondingly `reached_disagreement`, for the complementary blocking-minority 30% threshold) to use the same ceiling-division formula as `NakamotoBlockHeader::compute_voting_weight_threshold`, so that both code paths encode identical rounding semantics for the 70%/30% weight thresholds:
```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    let total = u64::from(self.total_weight);
    let num = total.strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD);
    let threshold = num.div_ceil(10);
    u64::from(vote_weight) >= threshold
}
```

### Proof of Concept
1. Configure a reward cycle where signer weights sum to `total_weight = 511` (matches the existing node-side round-up unit test).
2. Node-side block approval requires `compute_voting_weight_threshold(511) == 358` weight of valid signatures for the block to be accepted: [4](#0-3) 
3. Construct a `GlobalStateEvaluator` with `total_weight = 511` and accumulate `vote_weight = 357` (one weight-unit short of the real requirement) across `address_updates`.
4. Call `evaluator.reached_agreement(357)`; per `libsigner/src/v0/signer_state.rs:171-175`, `357 >= floor(511*7/10) = 357` is `true`, so the evaluator declares agreement reached.
5. This causes `determine_global_state`/`determine_global_burn_view`/`determine_latest_supported_signer_protocol_version` to settle on a value at 357/511 weight, even though the chain-level `verify_signer_signatures` path would reject a block signed by only that same 357/511 weight, since it needs 358 — demonstrating the two "70% threshold" implementations disagree by exactly one weight-unit.

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }
