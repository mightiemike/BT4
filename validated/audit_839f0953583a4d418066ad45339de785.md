### Title
Unchecked subtraction on `accounts_data_len` during startup index generation can panic/underflow if duplicate-account accounting exceeds the running total - (File: accounts-db/src/accounts_db.rs)

### Summary
`generate_index()`'s duplicate-pubkey reconciliation step mirrors the `Basket.sol#handleFees()` bug class: a value accumulated from scanning storages (`total_accum.accounts_data_len`) is reduced by a separately-computed value (`accounts_data_len_from_duplicates`) using a bare `-=` instead of a checked/saturating subtraction, unlike the adjacent `capitalization` field in the very same struct which *is* protected with `checked_sub(...).expect(...)`.

### Finding Description
In `AccountsDb::generate_index()`, after scanning all storages and finding pubkeys that occur in more than one slot, the code computes per-duplicate contributions (`accounts_data_len_from_duplicates`, `capitalization_from_duplicates`) and then reconciles the totals: [1](#0-0) 

Note the asymmetry: `capitalization` is subtracted with `checked_sub(...).expect("capitalization cannot underflow")`, which will cleanly panic with a diagnostic message if the invariant is violated, but `accounts_data_len` uses a raw `-=` on a `u64`. If `accounts_data_len_from_duplicates` were ever computed to be larger than `total_accum.accounts_data_len` (e.g., due to a reconciliation/accounting discrepancy between how the initial per-storage scan tallies data length versus how `visit_duplicate_pubkeys_during_startup` computes the "duplicate" contribution for accounts that changed data length across slots, were resized, or were closed/reopened), this line will:
- panic with an unwrap-style overflow panic in debug/overflow-checks-enabled builds (a node crash), or
- silently wrap around to a huge `u64` value in release builds without overflow checks, corrupting `accounts_data_len` for the entire bank going forward.

This is directly analogous to the `Basket.sol` finding: an accrual computed independently of the base value is subtracted from that base without a bound/guard, and the only question is whether inputs can make the subtrahend exceed the minuend. The `capitalization` field is explicitly guarded against this exact class of bug in the same reduction step, but `accounts_data_len` was not given the same treatment.

This path is reached during `generate_index()`, which runs during startup / snapshot rebuild (index generation from on-disk account storages) — squarely in the "AccountsDB storage and index" and "snapshot generation and rebuild" categories.

### Impact Explanation
If triggered, this causes either:
- A validator node panic during snapshot loading / index generation (a startup crash / liveness issue for the node), or
- A silently corrupted `accounts_data_len` total (via unsigned wraparound) that is subsequently used for total accounts-data-length enforcement and can propagate into hash/capitalization divergence relative to other honest nodes that computed the value differently (e.g., processed transactions live vs. rebuilt from snapshot).

Because I could not fully trace `visit_duplicate_pubkeys_during_startup`'s exact accounting logic or the per-storage `accounts_data_len` accumulation logic within my available searches (the function body and the initial `total_accum.accounts_data_len` accumulation site were not returned by my final queries), I cannot confirm with certainty that ordinary (non-malicious) account activity can actually drive `accounts_data_len_from_duplicates` above `total_accum.accounts_data_len`. The asymmetric hardening (checked on `capitalization`, unchecked on `accounts_data_len`) strongly suggests the developers considered this an invariant that could plausibly be violated for at least one of the two fields.

### Likelihood Explanation
Likelihood is uncertain given the incomplete trace. It requires a specific data condition on-disk (duplicate pubkeys across multiple rooted slots with data-length bookkeeping that disagrees with the duplicate-contribution calculation) that arises during normal snapshot-restart index generation — not through a single malicious RPC call or a crafted snapshot (which is explicitly out of scope). If reachable via ordinary account lifecycle (writes/reallocs/closures across slots prior to a clean/shrink pass, followed by node restart from snapshot), it would be a "no special privilege needed" node-panic/corruption bug, matching the required "unprivileged-user analog" criterion.

### Recommendation
Replace the unchecked subtraction with the same pattern used for `capitalization`:
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```
This converts a potential silent wraparound (release) or unwrap panic without context (or worse, undefined arithmetic behavior) into an explicit, diagnosable invariant violation, and — more importantly — should be paired with an audit of `visit_duplicate_pubkeys_during_startup` and the initial `accounts_data_len` accumulation in `generate_index()` to confirm the invariant `accounts_data_len_from_duplicates <= total_accum.accounts_data_len` actually always holds; if it can legitimately be violated under non-malicious conditions, the underlying accounting logic needs to be fixed, not just the panic message.

### Proof of Concept
I was not able to fully construct a concrete end-to-end PoC within the available tool budget: the body of `visit_duplicate_pubkeys_during_startup` (which computes `accounts_data_len_from_duplicates`) and the site where `total_accum.accounts_data_len` is first accumulated during the storage scan were not retrieved before the tool budget was exhausted, so I cannot confirm the exact sequence of account operations (e.g., resizing an account's data across multiple rooted slots via CPI-driven realloc, then restarting from snapshot) that would make `accounts_data_len_from_duplicates > total_accum.accounts_data_len`.
