### Title
Truncating (non-ceiling) rounding in calldata/signature/code archival gas-cost conversion undercharges L1/L2 gas for attacker-controlled data — (File: crates/blockifier/src/fee/resources.rs)

### Summary
`ArchivalDataResources::get_calldata_and_signature_gas_cost` and `get_code_gas_cost` in `crates/blockifier/src/fee/resources.rs` convert a fractional per-felt/per-byte gas rate (`ResourceCost`, a `Ratio<u128>` loaded from versioned-constants JSON, e.g. `128/1000` or `5120/1`) into an integer `GasAmount` using `.to_integer()` — which truncates toward zero — instead of `.ceil().to_integer()`, which is the rounding rule used everywhere else the codebase converts a fractional resource-cost ratio into a charged gas integer (e.g. `calculate_resource_gas_cost` in `crates/blockifier/src/fee/fee_utils.rs:88-91`, and every `*_round_up` conversion in `blockifier_versioned_constants.rs`). This is the same class of bug as the reported Solidity issue: a fractional conversion factor between two "denominations" (felt/byte count vs. gas units) is divided/multiplied and then floored rather than ceiled, so an attacker-controlled input size can be chosen to make the true (fractional) cost round down to a value strictly lower than the protocol intends, instead of erroring or safely rounding in the protocol's favor.

### Finding Description
`get_calldata_and_signature_gas_cost`: [1](#0-0) 

`get_code_gas_cost`: [2](#0-1) 

Both compute `(archival_gas_costs.gas_per_data_felt_or_byte * count).to_integer()`, where `gas_per_data_felt`/`gas_per_code_byte` are `Ratio<u128>` constants loaded from versioned-constants config files (e.g. `deprecated_l2_resource_gas_costs.gas_per_data_felt = [128, 1000]` in `blockifier_versioned_constants_0_13_2.json`, or `archival_data_gas_costs.gas_per_data_felt = [5120, 1]`), and `count` is `extended_calldata_length + signature_length` or `code_size` — quantities directly controlled by the transaction sender (an unprivileged tx sender chooses calldata size, signature length, and — via a `declare` transaction — the size of the declared class's code).

By contrast, the sibling function `calculate_resource_gas_cost` used for VM-step/builtin gas costs explicitly applies `.ceil()` before `.to_integer()`: [3](#0-2) 

and every `VersionedConstants` gas-unit conversion method is explicitly documented and implemented to round up (never down), e.g.: [4](#0-3) 

The archival-data functions are the outlier: they truncate. With a ratio such as `128/1000` (used for `gas_per_data_felt` under `deprecated_l2_resource_gas_costs` in several versioned-constants files, e.g. `blockifier_versioned_constants_0_13_2.json:15-19`, `_0_13_2_1.json`, `_0_13_3.json`, `_0_13_4.json`, `_0_14_0.json`, `_0_14_1.json`), any `count` in the range `[1, 7]` produces `count*128/1000 < 1`, which `.to_integer()` truncates to `0` — i.e. the sender is charged **zero** L1/L2 gas for that calldata/signature/code data instead of the correctly-rounded value of `1`. This mirrors exactly the reported bug class: a "decimals"/scale mismatch between an amount and a resource unit is resolved via integer division/multiplication that floors to zero for small enough attacker-chosen amounts, silently losing value that the protocol's accounting model assumes is always collected.

### Impact Explanation
These gas costs feed directly into (a) the fee actually charged to the user (`get_fee_by_gas_vector` via `TransactionResources::to_gas_vector` → `GasVector::cost`), and (b) the bouncer's block-capacity accounting (`get_tx_weights` uses `tx_resources.starknet_resources.to_gas_vector`, which includes this archival-data component, when computing `sierra_gas`/L1 gas weights consumed against `BouncerWeights::block_max_capacity`). A systematic undercount (rather than a rounding error that self-corrects) means:
- The sender is charged strictly less STRK/ETH fee than the protocol-specified per-felt/per-byte cost dictates for calldata, signature, and declared-class code, i.e. free/underpriced resource consumption reachable from a single ordinary `invoke`/`declare` transaction.
- The bouncer under-accounts the true L1/L2 gas weight consumed by such transactions, letting more resource-heavy transactions be packed into a block than the configured `block_max_capacity` intends — a resource-accounting/blockifier execution-path bug reachable by any transaction sender, not requiring a malicious operator/proposer.
- Because this happens deterministically from public inputs (calldata/signature/code length and versioned constants), the effect is systemic rather than incidental: an attacker can deliberately craft calldata/signature/declare-class-code lengths in the truncation-favorable range to repeatedly extract free "storage" gas units.

This is a fee-computation/resource-accounting correctness bug in the transaction-fee and bouncer-weight computation path (in-scope per the analog categories: fee and resource accounting, bouncer weights), reachable from an unprivileged transaction sender.

### Likelihood Explanation
High likelihood of being triggered unintentionally, and trivially reproducible/exploitable deliberately: `gas_per_data_felt`/`gas_per_code_byte` ratios with non-unit denominators (e.g. `128/1000`) are the values shipped in the historical versioned-constants files still supported by the node (`deprecated_l2_resource_gas_costs`), and the affected code path (`get_calldata_and_signature_gas_cost`, `get_code_gas_cost`) executes unconditionally for every `invoke`/`declare`/`deploy_account` transaction that carries calldata, a signature, or declared code — i.e. essentially all transactions. No special privileges, timing, or node compromise are required; only the choice of a small calldata/signature/code length under the specific versioned constants in effect.

### Recommendation
Make the archival-data gas-cost conversions consistent with the rest of the fee-accounting code by rounding up rather than truncating, e.g.:
```rust
let gas_amount = (archival_gas_costs.gas_per_data_felt * total_data_size).ceil().to_integer().into();
```
Apply the same `.ceil()` fix to `get_code_gas_cost` and any other archival-data-derived `.to_integer()` conversion that currently floors (`get_client_side_proof_gas_cost` already uses a pure-integer ratio, so is unaffected, but should be audited too). Add regression tests asserting that gas cost for any nonzero calldata/signature/code length is never rounded down below the mathematically correct fractional value, mirroring existing `calculate_resource_gas_cost` ceiling-rounding tests.

### Proof of Concept
Given versioned constants where `gas_per_data_felt = Ratio::new(128, 1000)` (as shipped in `blockifier_versioned_constants_0_13_2.json` and related files) and a transaction with `extended_calldata_length + signature_length = 7`:

```
cost = (128/1000) * 7 = 896/1000 = 0.896
get_calldata_and_signature_gas_cost -> (0.896).to_integer() = 0   // charged: 0 gas
calculate_resource_gas_cost-style rounding -> (0.896).ceil().to_integer() = 1  // correct: 1 gas
```

The sender is charged `0` L1/L2 gas units for 7 felts of calldata+signature instead of the correctly-rounded `1` unit — an off-by-truncation undercharge directly reachable from a standard `invoke`/`declare` transaction, confirmed by reading the exact arithmetic in: [5](#0-4)

    /// Returns the cost for transaction calldata and transaction signature. Each felt costs a
    /// fixed and configurable amount of gas. This cost represents the cost of storing the
    /// calldata and the signature on L2.
    fn get_calldata_and_signature_gas_cost(
        &self,
        versioned_constants: &VersionedConstants,
        mode: &GasVectorComputationMode,
    ) -> GasVector {
        let archival_gas_costs = versioned_constants.get_archival_data_gas_costs(mode);

        // TODO(Avi, 20/2/2024): Calculate the number of bytes instead of the number of felts.
        let total_data_size = u64_from_usize(self.extended_calldata_length + self.signature_length);
        let gas_amount =
            (archival_gas_costs.gas_per_data_felt * total_data_size).to_integer().into();

        match mode {
            GasVectorComputationMode::All => GasVector::from_l2_gas(gas_amount),
            GasVectorComputationMode::NoL2Gas => GasVector::from_l1_gas(gas_amount),
        }
    }
