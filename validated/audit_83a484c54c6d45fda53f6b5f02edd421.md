## Finding: Hardcoded Ed25519/Stark private key used to instantiate the production `SignatureManager` component

### Title
Sequencer node wires its production `SignatureManager` to a hardcoded, publicly-known private key - (File: `crates/apollo_signature_manager/src/lib.rs`)

### Summary
The Katello advisory (CVE-2012-3503) is a textbook "hardcoded secret used for real signing/authentication" bug class: a fixed, source-visible cryptographic secret is baked into every deployment, letting anyone who reads the source forge trusted artifacts. The sequencer repository has a direct analog: `create_signature_manager()`, the function the node uses to build its `SignatureManager` component, unconditionally constructs a `LocalKeyStore` from a **hardcoded private key literal** embedded in the source tree, with no override or "real keystore" implementation anywhere in the codebase.

### Finding Description
`LocalKeyStore::new_for_testing()` hardcodes a Stark curve private key constant directly in source: [1](#0-0) 

Despite being named `new_for_testing`, this is the **only** constructor ever used to build the production `SignatureManager`: [2](#0-1) 

`create_signature_manager()` is referenced by the node's component-wiring module `apollo_node/src/components.rs`, which is the code that assembles the running sequencer's components — i.e., this is not confined to a test target but is reachable from the production node binary. There is no alternate `KeyStore` implementation in the repository backed by a securely provisioned/secret-managed key (e.g., loaded from a vault or generated per node); `LocalKeyStore` is the sole concrete `KeyStore` and its only constructor embeds the fixed constant.

This key store backs `SignatureManager::sign_identification` and `SignatureManager::sign_precommit_vote`, i.e., peer-identity challenge-response signing and consensus precommit-vote signing: [3](#0-2) 

Because the private key is a constant literal committed to the public repository, its corresponding public key (`0x125d56b1fbba593f1dd215b7c55e384acd838cad549c4a2b9c6d32d264f4e2a`) and private key (`0x608bf2cdb1ad4138e72d2f82b8c5db9fa182d1883868ae582ed373429b7a133`) are known to anyone, exactly mirroring the Katello flaw where the same `secret_token` was baked into every installation.

### Impact Explanation
If any deployed sequencer/consensus node actually runs with this default key store (i.e., no production override path exists in the codebase to replace it with a securely generated/provisioned key), any external party who has read the source can:
- Sign valid `sign_identification` responses to peer-identity challenges, allowing impersonation of that node's P2P identity to other peers relying on `verify_identity`.
- Sign valid `sign_precommit_vote` messages for any block hash, forging consensus precommit votes attributable to that node's public key, verified via `verify_precommit_vote_signature`.

This can lead to unauthorized actions being falsely attributed to a validator/proposer identity and potentially to honest-node divergence in consensus vote accounting if the forged precommit is accepted as genuine, since the signature verifies correctly against the (public) hardcoded key.

### Likelihood Explanation
The likelihood hinges entirely on whether any production deployment actually instantiates `SignatureManager` via `create_signature_manager()`/`LocalKeyStoreSignatureManager::new()` without substituting a real key. The code shows this is the only implementation wired into `apollo_node/src/components.rs`, and there is an explicit TODO acknowledging the gap: "understand how key store would look in production and better define the way the signature manager is created" [4](#0-3) . This strongly suggests the hardcoded key path is currently what ships, making exploitation likely if this component is active for any node whose signing key is expected to carry real trust.

### Recommendation
- Rename/restrict `LocalKeyStore::new_for_testing()` (and mark it `#[cfg(test)]`) so it cannot be reached from `create_signature_manager()`.
- Implement a production `KeyStore` that loads a per-node private key from a secret manager or generates/persists a unique key per node, and wire `apollo_node/src/components.rs` to use it instead of the hardcoded literal.
- Add a compile-time or startup assertion that fails if the production binary ever instantiates the well-known constant key.

### Proof of Concept
1. Read `crates/apollo_signature_manager/src/signature_manager.rs` to obtain the hardcoded `PRIVATE_KEY = 0x608bf2cdb1ad4138e72d2f82b8c5db9fa182d1883868ae582ed373429b7a133`.
2. Compute `ecdsa_sign(PRIVATE_KEY, message_digest)` for a target `peer_id`/`challenge` (or block hash for precommit votes) exactly as `sign_identification`/`sign_precommit_vote` does.
3. Present the forged signature to any verifier calling `verify_identity`/`verify_precommit_vote_signature` with the corresponding known public key `0x125d56b1fbba593f1dd215b7c55e384acd838cad549c4a2b9c6d32d264f4e2a`; verification succeeds because the node's actual production key store is this same hardcoded pair, per `create_signature_manager()`'s wiring in `apollo_node/src/components.rs`.

    async fn sign(&self, message_digest: MessageDigest) -> SignatureManagerResult<RawSignature> {
        let private_key = self.keystore.get_key().await?;
        let signature = ecdsa_sign(&private_key, &message_digest)
            .map_err(|e| SignatureManagerError::Sign(e.to_string()))?;

        Ok(signature.into())
    }
