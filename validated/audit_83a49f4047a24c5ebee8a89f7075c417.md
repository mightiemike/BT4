### Title
Unbounded recursive JSON parsing of declared contract classes allows stack-overflow DoS - ([File: crates/apollo_http_server/src/http_server.rs])

### Summary
The `/gateway/add_transaction` HTTP endpoint deserializes an attacker-controlled request body directly into transaction structs (including deprecated DECLARE V0/V1/V2 contract classes) via `serde_json::from_str`/`serde_json::from_value`, before any structural depth or size validation is performed. Several of the deserialized types (`Program`/`ContractClass` fields such as `abi`, `identifiers`, `reference_manager`, `hints`) are typed as raw `serde_json::Value`, which is parsed and later processed (e.g. `sort_json_value` in `hinted_class_hash.rs`) with unbounded, naturally recursive algorithms. This mirrors the CVE-2022-23460 Jsonxx bug class: an unprivileged transaction sender can submit deeply nested JSON to exhaust the call stack of the process handling the request.

### Finding Description
The HTTP `add_tx` handler parses the raw request body string directly with `serde_json::from_str(&tx)` into `DeprecatedGatewayTransactionV3`, which is a `#[serde(tag = "type")]` enum including a `Declare` variant carrying a `DeprecatedContractClass`/`ContractClass` (Cairo v0) or `SierraContractClass`. [1](#0-0) 

Only a body-size limit (`max_request_body_size`) is enforced before parsing; there is no JSON-nesting-depth check anywhere in the request path. [2](#0-1) 

For the deprecated (Cairo v0) contract class, several `Program` fields are typed as unconstrained `serde_json::Value` (e.g. `identifiers`, `reference_manager`, `hints`), and `abi` is also `serde_json::Value`: [3](#0-2) 

`serde_json`'s own `Value` deserializer and `Drop` implementation are naturally recursive with no depth limit; a JSON payload containing a very deeply nested array/object (e.g., `[[[[...]]]]` many thousands deep) inside `abi`, `identifiers`, `hints`, or `reference_manager` can exhaust the thread's call stack purely during parsing, before any of the gateway's post-parse validators (`validate_class_length`, `max_contract_class_object_size`, etc.) ever run. [4](#0-3) 

The size/byte-length checks in `stateless_transaction_validator.rs` only apply to the Sierra (v3 RPC) declare path, and even there they run only *after* the JSON has already been fully parsed into a `SierraContractClass`. The deprecated V0/V1/V2 declare path has no equivalent length/size gate at all before or after deserialization; it goes straight from `serde_json::from_str` to `convert_to_rpc_tx`. [5](#0-4) 

Additionally, once a Cairo v0 class is declared/loaded, `compute_cairo_hinted_class_hash` re-serializes/deserializes it into `CairoContractDefinition` and calls `sort_json_value`, a hand-written recursive function over `serde_json::Value` with no depth guard, walking the same attacker-supplied nested structure again during class-hash computation (used by execution/OS re-execution paths, not just the gateway). [6](#0-5) [7](#0-6) 

### Impact Explanation
A stack overflow in a Rust process is an unrecoverable abort (there is no panic-catch for stack overflow), crashing the thread/process handling the request. If this occurs in the HTTP server / gateway thread that accepts `add_transaction`, it can repeatedly crash the sequencer's ingestion path, preventing the network from confirming new transactions submitted through that path — matching the "network unable to confirm new transactions" impact category. If it occurs during block building / OS re-execution when computing the hinted class hash for an already-included declared class, it could crash the batcher/prover pipeline as well, since `compute_cairo_hinted_class_hash` is used along the execution/verification path for Cairo v0 contract classes.

### Likelihood Explanation
Reachable by any unprivileged HTTP client with no authentication: a single POST to `/gateway/add_transaction` with a `DECLARE` (v0/v1/v2) transaction containing a deeply nested `abi`/`program.identifiers`/`program.hints` value. The only defense is the byte-size cap (`max_request_body_size`), but deeply nested JSON (e.g. thousands of `[` characters) is extremely compact relative to nesting depth, so a payload well under the size limit can still reach a depth sufficient to overflow a typical thread stack. This makes the likelihood high once such a message reaches the deserialization code, though it is somewhat mitigated by not yet confirming the exact default stack size of the HTTP-server/gateway threads (native execution threads are explicitly sized via `stack_size`/`RUST_MIN_STACK`, but the HTTP/gateway tokio task/thread's stack size configuration was not directly confirmed in this investigation).

### Recommendation
- Enforce a JSON nesting-depth limit before or during deserialization of any untrusted transaction payload (e.g., using a depth-limited deserializer, or pre-scanning bracket/brace depth) at the `add_tx`/`add_rpc_tx` handlers in `apollo_http_server/src/http_server.rs`, prior to calling `serde_json::from_str`/`Json<RpcTransaction>` extraction.
- Replace unconstrained `serde_json::Value` fields in `Program`/`ContractClass`/`CairoContractDefinition` (`abi`, `identifiers`, `reference_manager`, `hints`) with strongly-typed structures wherever feasible, or wrap `Value` parsing with an explicit recursion-depth counter.
- Rewrite `sort_json_value` in `crates/starknet_os/src/hints/class_hash/hinted_class_hash.rs` to use an explicit iterative stack instead of native recursion, with a hard depth cap that yields an error instead of crashing.
- Apply the same length/size gates that exist for Sierra (v3) declare transactions to the deprecated V0/V1/V2 declare path before parsing (e.g., reject the request based on a depth/structure pre-check on the raw string) rather than only after building the full struct.

### Proof of Concept
1. Construct a JSON DECLARE V1 transaction body for `POST /gateway/add_transaction` where `contract_class.abi` (or `program.identifiers` / `program.reference_manager` / `program.hints`) is a deeply nested array, e.g. `"abi": ` followed by ~100,000 repetitions of `[` and matching `]` — kept under `max_request_body_size`.
2. Send the request to the gateway's `add_tx` handler, which calls `serde_json::from_str::<DeprecatedGatewayTransactionV3>(&tx)` directly on the raw body. [8](#0-7) 
3. The recursive `serde_json` `Value` parser (and later `Drop`) walks the nested structure with one stack frame per nesting level; sufficiently deep nesting overflows the thread's stack, aborting the process without a catchable panic — denying the node's ability to keep processing further transactions on that path.

/// Recursively sorts all JSON objects by their keys.
/// This ensures deterministic serialization regardless of the `preserve_order` feature in
/// serde_json.
fn sort_json_value(value: serde_json::Value) -> serde_json::Value {
    match value {
        serde_json::Value::Object(map) => {
            let sorted: BTreeMap<String, serde_json::Value> =
                map.into_iter().map(|(k, v)| (k, sort_json_value(v))).collect();
            serde_json::Value::Object(sorted.into_iter().collect())
        }
        serde_json::Value::Array(arr) => {
            serde_json::Value::Array(arr.into_iter().map(sort_json_value).collect())
        }
        other => other,
    }
}

pub fn compute_cairo_hinted_class_hash(
    contract_class: &ContractClass,
) -> Result<Felt, HintedClassHashError> {
    // Serialize to Value, sort all objects by keys for deterministic output, then to bytes.
    // The sorting is necessary because serde_json with `preserve_order` feature enabled

    // TODO(Meshi): Compute hinted hashes when loading serialized contracts from storage, before
    // deserializing, to avoid back-and-forth serde.
    let contract_value = serde_json::to_value(contract_class)?;
    let sorted_contract_value = sort_json_value(contract_value);
    let contract_definition_vec = serde_json::to_vec(&sorted_contract_value)?;
    let contract_definition: CairoContractDefinition<'_> =
