## Analog Identified

The Wireshark CVE describes **uncontrolled recursion** in a dissector triggered by attacker-supplied nested/recursive data, causing a stack-overflow DoS. The sequencer repo has a structurally analogous pattern in the **compiled-class-hash computation**, where the recursion depth is driven by a nested segment-tree structure (`NestedIntList` / `bytecode_segment_lengths`) that originates from an untrusted, attacker-declared Sierra→CASM compilation output.

### Title
Uncontrolled recursion in `bytecode_hash_node` over attacker-influenced CASM bytecode-segment tree enables stack-overflow DoS on Declare processing - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
`bytecode_hash_node` recursively walks the `bytecode_segment_lengths` tree (`NestedIntList`) of a compiled class to compute its compiled-class-hash, with no depth limit or iterative fallback. [1](#0-0) 

### Finding Description
`HashableCompiledClass::hash` calls `bytecode_hash`, which calls `bytecode_hash_node` recursively once per tree level of `get_bytecode_segment_lengths()`. [2](#0-1) 
For `CasmContractClass`, this segment tree comes directly and unmodified from the Sierra-to-CASM compilation output (`self.bytecode_segment_lengths`), with no depth restriction imposed in this repo. [3](#0-2) 

This `hash()` call is invoked in-process (not inside the resource-limited compiler subprocess) immediately after Sierra→CASM compilation completes, on every Declare transaction: [4](#0-3) 

It is invoked again by any node re-validating that the submitter's claimed `compiled_class_hash` matches the recomputed hash, which is required logic that every sequencer/full node performs when accepting or re-executing the Declare: [5](#0-4) 

By contrast, the *execution-time* accounting structure `NestedFeltCounts` explicitly caps recursion depth (`assert!(segmentation_depth <= 1, ...)`), showing the project is aware deep nesting is a hazard for one code path but does not appear to bound it in the direct compiled-class-hash path. [6](#0-5) 

The recursion is not tail-recursive (it collects children into a `Vec` and combines results after recursing), so each nesting level consumes native stack space that the Rust compiler cannot optimize away. [7](#0-6) 

### Impact Explanation
If an attacker can get the Sierra-to-CASM compiler (an external, audited compiler binary not reviewed as part of this repo) to emit a deeply nested `bytecode_segment_lengths` tree for a maliciously crafted but otherwise valid Cairo1 contract, every node that computes `CasmContractClass::hash()` for that class — the declaring gateway/class-manager immediately, and every sequencer/full node re-validating or re-executing the resulting Declare transaction thereafter — would recurse to the same depth and could crash with a stack overflow. Because this affects **every honest node processing the same Declare**, it is a network-wide denial-of-service vector rather than a single-node crash, matching the required "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Exploitability depends entirely on whether the external `cairo-lang-sierra-to-casm` compiler can be coerced into emitting a segment tree deep enough to overflow a typical thread stack (Rust's default is a few MB; the sequencer explicitly raises `RUST_MIN_STACK` for `native_blockifier` to accommodate deep recursion elsewhere, suggesting stack exhaustion is a known concern in this codebase). This repo does not itself bound or validate the depth of `bytecode_segment_lengths` before hashing it, so if the compiler's segmentation algorithm scales with nested control flow (e.g. deeply nested branches/functions) rather than being capped, a crafted declare could reach a triggering depth within the existing `max_bytecode_size` budget. [8](#0-7) 

### Recommendation
- Impose an explicit maximum depth (or convert to an iterative/worklist algorithm) in `bytecode_hash_node` (and its OS-side counterpart `bytecode_hash_internal_node`/`create_bytecode_segment_structure_inner`) independent of what the external compiler happens to produce.
- Validate `bytecode_segment_lengths` depth as part of `validate_class_length`/stateless validation in the gateway, before it is hashed outside the sandboxed compiler subprocess.
- Confirm whether `cairo-lang-sierra-to-casm`'s segmentation algorithm bounds tree depth; if not, treat this as a shared upstream/sequencer issue.

### Proof of Concept
Not constructed — reproducing this requires driving the external Sierra-to-CASM compiler to emit a deep `bytecode_segment_lengths` tree, which depends on compiler internals outside this repo's index. This should be validated experimentally (e.g., a Cairo1 contract with many deeply nested `if`/`match` branches or function-call chains) rather than asserted as certain.

---
**Caveat:** The actual maximum nesting depth producible via a legitimately-compiling Sierra program is governed by the external `cairo-lang-sierra-to-casm` compiler crate, whose segmentation algorithm is not part of this codebase and could not be fully verified with the tools available. I recommend a Devin session with full repository/dependency access to trace `cairo-lang-starknet-classes`' segment-tree construction logic and confirm whether attacker-reachable depths are actually large enough to overflow the stack before treating this as a confirmed, fully proven vulnerability.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,

        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());

        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
