### Title
Unbounded gzip decompression in RPC `decompress_program` allows attacker-controlled memory exhaustion (DoS) - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
`decompress_program` in the Starknet RPC read/execution API decompresses a base64-encoded, gzip-compressed Cairo0 `program` field taken directly from an unprivileged RPC caller's `BroadcastedTransaction` (used by `simulate_transactions` / `estimate_fee` for deprecated `DECLARE` transactions), and writes the entire decompressed output into an unbounded `Vec<u8>` with no size cap, unlike the bug-class hint (unbounded buffer growth on untrusted input with no cap, leading to OOM/DoS).

### Finding Description
`decompress_program` reads the caller-supplied base64 string, decodes it, and feeds it to `GzDecoder::read_to_end`, growing an in-memory `Vec<u8>` without any limit: [1](#0-0) 

The `// TODO(dan): add time and size limits.` comment on the line immediately preceding the unbounded `read_to_end` call confirms the missing guard is a known gap, not an intentional design choice. This is structurally identical to the reported bug class: a component reads attacker-controlled compressed/streamed bytes into an ever-growing in-memory buffer with no cap, relying only on an implicit terminator (end of gzip stream) rather than a size bound, so a maliciously crafted small input (a gzip/zip "bomb") can expand to an arbitrarily large allocation.

By contrast, the sequencer's actual transaction-ingestion path (used by the gateway for real `DECLARE` transactions) enforces a size limit on decompression: [2](#0-1) 

That function uses `.take(max_size + 1)` before `read_to_end` and returns `CompressionError::SizeLimitExceeded` if the decompressed data exceeds the bound. `decompress_program` lacks this protection entirely, meaning the RPC execution/simulation surface (reachable by any unprivileged RPC caller submitting a `BroadcastedTransaction` containing a deprecated contract class) is not subject to the same size-limiting discipline applied elsewhere in the codebase for the same kind of data (compressed Cairo program bytes).

### Impact Explanation
An attacker can submit a `simulate_transactions` / `estimate_fee` (or similar execution-simulation RPC) request containing a `BroadcastedDeclareTransaction` (V1/V2 deprecated Cairo0 class) whose `program` field is a small, highly-compressible gzip payload (a "zip bomb"). When the node calls `decompress_program`, it will allocate memory proportional to the *decompressed* size (potentially gigabytes) from a tiny request payload, with no cap on time or memory. Because RPC nodes are typically reachable by any client without special privileges, repeated requests can exhaust process memory, causing the node process to be OOM-killed — a remote, pre-auth denial-of-service against a sequencer's RPC/execution service, consistent with the reported CVE's "Availability: High" impact via unbounded buffer growth.

### Likelihood Explanation
Likelihood is high: the vulnerable function is reachable through a standard, unauthenticated JSON-RPC call available to any client of the node's read/execution API, requires no on-chain funds, gas payment, or special network position, and the missing bound is explicitly flagged as a known TODO in the source, indicating the gap is real and unaddressed.

### Recommendation
Apply the same bounded-decompression pattern used elsewhere in the codebase (`starknet_api::compression_utils::decompress_with_size_limit` / `decode_and_decompress_with_size_limit`, which use `.take(max_size + 1)` and return an explicit `SizeLimitExceeded` error) to `decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs`, capping the maximum decompressed program size (and ideally decompression time) before accepting the class into execution/simulation.

### Proof of Concept
1. Craft a gzip stream that decompresses to several hundred MB to several GB of repetitive zero/byte data (a classic zip bomb), keeping the compressed size small (KBs).
2. Base64-encode the compressed bytes and place them in the `program` field of a `DEPRECATED_DECLARE`-style contract class inside a `BroadcastedTransaction`.
3. Submit this transaction to the node's `starknet_simulateTransactions` or `starknet_estimateFee` RPC endpoint (or any endpoint that ultimately calls `decompress_program`).
4. Observe the node's memory usage spike as `decoder.read_to_end(&mut decompressed)` in `decompress_program` (crates/apollo_rpc/src/v0_8/api/mod.rs:678-680) allocates unboundedly; repeating the request against a node (or sending several concurrently) drives it to OOM.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
