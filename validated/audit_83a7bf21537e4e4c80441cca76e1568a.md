## Title
Payable `rlp_execute()` traps attached NEAR deposit on early parse/validation failure - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

## Summary
The NEAR Wallet Contract's `rlp_execute()` entry point is `#[payable]`, meaning callers can attach a NEAR deposit when invoking it. When the inner parsing/validation of the RLP-encoded Ethereum transaction fails (e.g., malformed `tx_bytes_b64`, invalid nonce, or other `Error::User`/`Error::AccountId` conditions detected in `inner_rlp_execute`), the function returns early via `Err(e) => PromiseOrValue::Value(e.into())` without ever creating a promise or transfer to refund the `attached_deposit` back to the predecessor. This is structurally identical to the reported `bridgeRingToAbstract()` bug: a payable entry point validates input, and on the "reject" path it returns a value/short-circuits without handling the money that was attached to the call.

## Finding Description
`rlp_execute` is defined as: [1](#0-0) 

It calls `inner_rlp_execute`, which begins by capturing the deposit for later refund purposes only in the *cross-contract-call-failure* case via `CallerDeposit::new(&context)`: [2](#0-1) 

`CallerDeposit` is only ever consulted inside `rlp_execute_callback` / `address_check_callback`, i.e., after a `Promise` has actually been dispatched: [3](#0-2) 

However, when `parse_rlp_tx_to_action` fails — for example on `Error::User(_)` (malformed/garbage RLP bytes, bad nonce, etc.) — `inner_rlp_execute` returns `Err(err)` directly, before any `Promise` is created: [4](#0-3) 

Back in `rlp_execute`, this `Err` path is converted straight into a value response with no refund logic at all: [5](#0-4) 

Because `attached_deposit` is implicitly merged into the contract's account balance on receipt execution and there is no explicit transfer-back in this failure branch, any NEAR tokens a caller/relayer attaches while invoking `rlp_execute` with a malformed transaction, bad nonce, or other validation-early-reject condition are absorbed into the Wallet Contract's account balance and are not returned. This mirrors the pattern in the external report exactly: a payable function performs an input check, takes an early return/no-op path, and never refunds the attached value.

## Impact Explanation
This affects any unprivileged caller (an ordinary NEAR account, relayer, or the wallet owner via their own access key) that sends a transaction calling `rlp_execute` with a nonzero attached deposit and malformed/garbage `tx_bytes_b64`, or any other case producing `Error::User`/similar before promise creation. The caller's attached NEAR is permanently absorbed into the Wallet Contract account instead of being refunded, which is unauthorized/unintended value movement (funds leaving the caller's control with no compensating action) and a form of frozen/lost user funds. Because the Wallet Contract is a widely-deployed global contract underpinning every ETH-implicit account on NEAR, this is a realistically reachable Medium-severity issue: it requires a signer to make a mistake (attach a deposit while sending a bad transaction), similar to the original ETHBridge scenario requiring a caller to attach ETH with an empty array.

## Likelihood Explanation
Likelihood is Medium: it requires a caller to both (a) invoke `rlp_execute` with a non-zero deposit, and (b) supply a transaction that fails parsing/validation before a promise is created (bad RLP bytes, replayed/invalid nonce, or other `Error::User` conditions). Relayers programmatically constructing transactions could hit this more easily than end users manually crafting calls, and any bug in relayer tooling attaching gas-refund-covering deposits alongside a malformed payload would silently strand funds, with no on-chain signal beyond an error response.

## Recommendation
In `inner_rlp_execute`/`rlp_execute`, whenever the function returns an `Err` (or otherwise short-circuits) before dispatching any cross-contract promise, explicitly refund `env::attached_deposit()` back to `env::predecessor_account_id()` via a `Promise` transfer (the same mechanism already used for `CallerDeposit` refunds in `rlp_execute_callback`), rather than relying on refund logic that only fires after a promise chain is created. Alternatively, require `attached_deposit == 0` for calls that are expected to fail validation, and revert (fail the whole receipt, which triggers the runtime's normal deposit-refund receipt as described in `docs/RuntimeSpec/Refunds.md`) instead of returning a success/soft-error value with the deposit silently retained.

## Proof of Concept
1. Deploy/target the Wallet Contract for an ETH-implicit account (as in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs`, `test_relayer_invalid_tx_data`, which already demonstrates the "garbage data" failure path but does not assert on deposit refunds).
2. As any account (`caller`), call `rlp_execute(target, tx_bytes_b64)` on the deployed Wallet Contract with:
   - `tx_bytes_b64` = garbage bytes (e.g., `b"random_garbage_data"` as used in the existing relayer test), and
   - a non-zero attached deposit (e.g. 1 NEAR).
3. Observe the call returns `ExecuteResponse { success: false, error: Some(...) }` (a `PromiseOrValue::Value` — see `lib.rs:116-127`), with no `Promise::transfer` back to `caller`.
4. Query `caller`'s account balance before/after: it decreases by the attached deposit amount, and the Wallet Contract's account balance increases by the same amount, confirming the deposit was absorbed rather than refunded.

Note: I could not fully inspect `error.rs` and `types.rs`/`internal.rs` contents (tool calls for those files failed to execute in this session), so the exact enumeration of every `Error` variant that triggers this early-return path (beyond the `Error::User` case shown in `lib.rs:389-409`) is not fully confirmed. A Devin session with full file access should verify all `Err` branches of `inner_rlp_execute` and `parse_rlp_tx_to_action` to enumerate every code path where attached deposit is dropped.
