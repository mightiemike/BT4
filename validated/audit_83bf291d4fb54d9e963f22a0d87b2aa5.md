## Finding

Both the Solr CVE and this codebase share the same bug class: **a cached/copied resource is implicitly trusted because the validation path that would re-check its authoritative status is skipped for one resource variant.**

### Analog Location [1](#0-0) 

### Finding Description
`StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from a process-global `ContractClassManager` cache that outlives any single block's execution. For non-V0 (Cairo1) classes, the code explicitly re-validates the cache hit against the authoritative state before trusting it: [2](#0-1) 

The comment makes the threat model explicit: cache presence "does not guarantee" the class is currently declared, "it might contain a declared class from a reverted block, for example." This directly matches the Solr root cause — a resource carried over from an operation that didn't go through the current authoritative path can retain stale trust unless explicitly re-checked.

However, this re-validation is **skipped entirely for `RunnableCompiledClass::V0` (Cairo 0)** classes — the `match` arm is a no-op. The `FetchCompiledClasses::is_declared` trait contract even documents that it cannot answer for V0: [3](#0-2) 

The concrete implementation in `ApolloReader::is_declared` computes declaration status generically via `get_class_definition_block_number` and compares it to the current state's block number: [4](#0-3) 

This suggests the underlying storage primitive is not actually restricted to Cairo1 classes, yet the caller intentionally bypasses this check for V0 based on the (possibly outdated) assumption baked into the trait's documentation comment. As a result, a stale V0 entry left in the global cache from a reverted/rolled-back block would be served indefinitely as "declared" without any re-validation against current committed state, while the equivalent Cairo1 path is protected.

### Impact Explanation
If a Cairo0 class becomes cached in the shared, long-lived `ContractClassManager` (e.g., due to a chain reorg/block revert that un-declares the class, or any scenario where the backing committed state and the process cache diverge), a subsequent call into a contract using that class hash would execute using the stale cached bytecode instead of failing with `UndeclaredClassHash`. Because different sequencer/full nodes may have different cache population histories (e.g., one node observed the class before the revert, another did not), this can produce **honest-node divergence** in transaction execution results and the committed state root for identical blocks — nodes that still hold the stale cache entry execute successfully where nodes without it would reject the transaction as referencing an undeclared class.

### Likelihood Explanation
This requires a corrective block revert/reorg to occur after a Cairo0 declare — an operationally rare event in this environment, but explicitly anticipated and guarded against for Cairo1 in the very code adjacent to this gap, indicating the sequencer authors consider revert-induced cache staleness a real risk. The asymmetric protection (Cairo1 guarded, Cairo0 not) means the residual risk is concrete whenever that revert path is exercised, moving this out of "low" into a genuine correctness/divergence risk category rather than a theoretical one.

### Recommendation
Extend the authoritative re-validation to V0 classes as well: confirm that `ApolloReader::is_declared` (or an equivalent Cairo0-aware existence check backed by `get_class_definition_block_number`) is queried for `RunnableCompiledClass::V0` cache hits in `get_compiled_from_class_manager`, removing the special-cased skip and the stale assumption that Cairo0 classes cannot be checked. Update the `FetchCompiledClasses::is_declared` documentation to match the corrected, version-agnostic behavior.

### Proof of Concept
1. Declare a Cairo0 class in block `N`; the class becomes committed to storage, and a subsequent read via `get_compiled_from_class_manager` populates the global `ContractClassManager` cache with the V0 compiled class.
2. Trigger (or simulate, in a reorg-capable deployment) a revert of block `N`, so that the authoritative storage no longer reports the class hash as declared (`get_class_definition_block_number` returns `None`/a later value).
3. Submit an `Invoke` transaction to a contract address whose `class_hash` is the reverted Cairo0 class hash. On a node whose process cache still holds the stale entry, `get_compiled_from_class_manager` hits the `RunnableCompiledClass::V0(_) => {}` no-op branch and returns the compiled class without consulting `is_declared`, executing the transaction successfully.
4. On a node without the stale cache entry (fresh cache, or one that evicted it), the same call falls through to `state_reader.get_compiled_classes`, which fails with `UndeclaredClassHash` since storage no longer has the class declared.
5. The two nodes now disagree on whether the transaction is valid, producing different state roots for the same block — an honest-node divergence directly caused by the missing re-validation, exactly analogous to Solr's implicitly-trusted restored ConfigSet.

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
