### Title
`sanitizeRedirectUrl` fails to enforce same-origin, accepting any `https:`/`http:` absolute URL as a "safe" redirect - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts`)

### Summary
`sanitizeRedirectUrl`/`isSafe` never verifies that the parsed redirect URL's origin matches the trusted `domain` argument passed in. It only rejects `file://`-style triple slashes, embedded whitespace, `//`-doubled relative paths, and disallowed protocols/SSL. Any absolute URL such as `https://evil.example.com/x` is treated as "safe" and returned unmodified.

### Finding Description
`isSafe()` builds `new URL(redirectUrl, domain)` [1](#0-0)  and then only checks:
- `INVALID_RELATIVE_URL` against `url.pathname` (path traversal via doubled slashes),
- `url.protocol` is in `['https:', 'http:']`,
- optional SSL requirement. [2](#0-1) 

Because the WHATWG `URL` constructor uses the `base` (`domain`) argument only when `redirectUrl` is relative, passing an absolute URL like `https://evil.example.com` completely bypasses the intended base/origin, and none of the existing checks compare `url.origin`/`url.hostname` against `domain`'s origin. The existing unit test suite confirms this: it only asserts rejection based on protocol/SSL (e.g. `http://example.com` fails solely because `requireSSL: true`, not because the hostname differs from `APP_URL`) [3](#0-2) ; there is no test verifying rejection of a different **https** host, because the function has no such check.

`sanitizeRedirectUrl` is consumed by `renderAppBridge`, which takes `redirectTo.url` and injects the resulting `destination.toString()` into a `<script>window.open(...)</script>` tag served in the OAuth/embedding bounce response [4](#0-3) . Any call site that forwards request-derived data (e.g. a `redirectUri`/`return_to`-style parameter) into `redirectTo.url` without itself re-validating the origin would produce an open redirect / window.open to an attacker-controlled origin, since the library-level "sanitizer" does not actually confine the target to the app's own domain.

### Impact Explanation
This is an open-redirect-class weakness in the shared helper that is documented/relied upon as the app's redirect sanitizer. If any admin/auth flow forwards an attacker-influenced absolute URL to `sanitizeRedirectUrl`/`renderAppBridge`, an attacker can cause the embedded app to `window.open`/redirect the merchant's browser to an attacker-controlled HTTPS origin from within the authenticated Shopify Admin context, which can be leveraged for phishing/token-theft flows consistent with the "open redirect leading to token theft" impact class in scope.

### Likelihood Explanation
No privileged access is required — an unprivileged actor need only supply an absolute URL that reaches `sanitizeRedirectUrl` as `redirectUrl`. The bug is deterministic and 100% reproducible against the exported function itself via a direct unit test; whether it is remotely triggerable end-to-end additionally depends on whether a given call site (e.g. `renderAppBridge` callers in `auth-code-flow.ts`) passes attacker-influenced data into `redirectTo.url` — I was not able to fully trace every call site of `renderAppBridge`/`redirect()` within the remaining budget to confirm a concrete unauthenticated HTTP entry point that supplies a fully-attacker-controlled absolute URL into this specific parameter (as opposed to `sanitizeHost`, which decodes/validates the `host` query param separately). This should be verified further.

### Recommendation
In `isSafe()`, after constructing `url`, explicitly verify same-origin against `domain`, e.g. compare `url.origin === new URL(domain).origin` (or restrict acceptance to relative URLs only, disallowing absolute URLs with a different host entirely) before returning `true`.

### Proof of Concept
```ts
import {sanitizeRedirectUrl} from '../validate-redirect-url';

it('BUG: accepts an absolute URL pointing to a different https origin', () => {
  const APP_URL = 'https://my-app.example.com';
  const result = sanitizeRedirectUrl(APP_URL, 'https://evil.example.com/steal', {
    requireSSL: true,
  });
  // Vulnerable: this currently returns a URL for evil.example.com instead of throwing
  expect(result.origin).toBe('https://evil.example.com');
});
```
This test passes against the current implementation, demonstrating that `sanitizeRedirectUrl` does not enforce same-origin as its name/usage implies.

  {config}: BasicParams,
  request: Request,
  redirectTo?: RedirectToOptions,

  let redirectToScript = '';
  if (redirectTo) {
    const destination = sanitizeRedirectUrl(config.appUrl, redirectTo.url);
