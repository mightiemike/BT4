### Title
Fork-dependent PoisonMicroblock reporting causes `assert_eq!(rw, reward, ...)` panic in `inner_insert_matured_miner_reward` - ([File: stackslib/src/chainstate/stacks/db/accounts.rs])

### Summary
`inner_insert_matured_miner_reward` assumes that for a fixed `(parent_block_id, child_block_id)` key, any two Stacks forks that mature the same ancestor tenure must compute an identical `MinerReward`, and it hard-asserts this with `assert_eq!`. However, the poison-microblock adjustment fed into `calculate_miner_reward` is read from the *current fork's* Clarity state at the time of maturation, not from the matured block's own committed contents, so two forks sharing a common ancestor tenure can legitimately compute different `MinerReward` values and hit this assertion, crashing the node.

### Finding Description
The broken equality is: **MinerReward(parent_block_id, child_block_id)** must be the same value regardless of which fork computed it, since it is keyed only by the ancestor tenure's block ids [1](#0-0) . The code explicitly documents this invariant: "the only time it's okay to re-insert the same reward is if there are two Stacks forks trying to store the same matured rewards for a common ancestor block" [2](#0-1) , and enforces it via `assert_eq!(rw, reward, "FATAL: tried to insert multiple distinct matured parent block reward records")`.

The reward is computed in `find_mature_miner_rewards`, which reads whether a poison-microblock was reported at `reward_height` from the **current fork's tip** Clarity DB state: `StacksChainState::get_poison_microblock_report(clarity_tx, reward_height)` [3](#0-2) . This result (`poison_recipient_opt`) is passed into `calculate_miner_reward`, which changes the coinbase recipient, zeroes out the miner's anchored/streamed tx fees, and pays a commission to the reporter instead of the miner if a report is present [4](#0-3) .

Because `get_poison_microblock_report` queries the Clarity/MARF state as of the querying fork's own tip, its result is fork-dependent even when the tenure being rewarded (and hence `parent_block_id`/`child_block_id`) is identical across both forks. An attacker (any unprivileged party who can submit a `PoisonMicroblock` transaction) can broadcast a valid poison report referencing an equivocating microblock pair signed against the shared ancestor tenure, and get it mined into a later block on fork A only, while fork B's chain tip never processes such a transaction. When both forks independently mature the reward for the shared ancestor tenure, `inner_insert_matured_miner_reward` is invoked twice against the same shared sqlite `matured_rewards` table with two different `MinerReward` values for the same `(parent_block_id, child_block_id)` key, triggering the `assert_eq!` panic.

Existing guards do not prevent this: `check_tenure_tx`, `verify_signer_signatures`, `validate_vrf_seed`, and the maturation-window logic all operate on tenure/block validity and timing, not on whether poison-report presence is deterministic across forks sharing an ancestor — there is no mechanism forcing all forks to agree on poison-report status for a matured tenure before the shared reward is computed.

### Impact Explanation
The panic is an unconditional Rust `assert_eq!`, which aborts the process. Because the vulnerable code path is reached deterministically whenever a node processes two forks off a common ancestor with differing poison-report status, any node that receives and processes both fork branches (which chainstate does for non-canonical candidate forks, per the code's own "two Stacks forks" comment) will crash. This is a reachable node crash/DoS, and because it depends on which blocks/txs a given node has seen, different honest nodes can crash at different times or diverge on which fork they're able to continue validating, producing tip disagreement and node unavailability at the affected chain tip — matching the Critical/High "temporary tip disagreement" / crash-to-chain-split boundary described.

### Likelihood Explanation
The precondition is a temporary situation where two forks share a common ancestor tenure (a normal, frequent occurrence during any reorg or fork race), and the attacker only needs to get a legitimate `PoisonMicroblock` evidence transaction mined into one branch's chain and withheld from the other — something any unprivileged participant able to submit transactions and observe/target miners can attempt without stake, majority power, or privileged roles. Equivocating microblock evidence, once created, remains valid indefinitely and can be submitted to either branch at will, making this fully attacker-controlled and repeatable.

### Recommendation
Compute the poison-microblock adjustment from data intrinsic to the matured tenure itself (e.g., record whether/who reported the poison as part of the ancestor block's own committed state at the time it was mined, or scope the report lookup so it only reflects transactions confirmed by the tenure being rewarded) rather than from the querying fork's current tip state. Alternatively, remove the `assert_eq!` and instead deterministically resolve conflicts (e.g., always favor "no punishment" or the first-seen reward, updating documentation of consensus rules accordingly) so that reward computation is provably identical for a given `(parent_block_id, child_block_id)` across all forks.

### Proof of Concept
1. Set up a two-node/two-fork chainstate harness (using `stackslib/src/chainstate/stacks/db/accounts.rs` test infra, e.g. `advance_tip`) that shares a common ancestor tenure with microblocks signed such that an equivocation exists (two conflicting microblocks at same sequence number, same signing key).
2. On fork A, mine a subsequent block containing a valid `PoisonMicroblock` transaction reporting that equivocation.
3. On fork B, mine a subsequent block from the same ancestor without that report.
4. Advance both forks to `MINER_REWARD_MATURITY` and call `find_mature_miner_rewards` / `insert_matured_child_miner_reward` on both forks against the same shared chainstate db.
5. Assert: `reward_A.total() != reward_B.total()` (showing the equality break: poison-adjusted vs. normal reward for the same `(parent_block_id, child_block_id)`), and observe that the second call to `inner_insert_matured_miner_reward` panics on `assert_eq!(rw, reward, ...)` instead of returning `Ok(())`.

    fn inner_insert_matured_miner_reward(
        tx: &mut DBTx<'_>,
        parent_block_id: &StacksBlockId,
        child_block_id: &StacksBlockId,
        reward: &MinerReward,
    ) -> Result<(), Error> {
        // the only time it's okay to re-insert the same reward is if there are two Stacks forks
        // trying to store the same matured rewards for a common ancestor block.
        let cur_rewards = StacksChainState::inner_get_matured_miner_payments(
            tx,
            &parent_block_id.clone().into(),
            &child_block_id.clone().into(),
        )?;
        if !cur_rewards.is_empty() {
            let mut present = false;
            for rw in cur_rewards.iter() {
                if (rw.is_parent() && reward.is_parent()) || (rw.is_child() && reward.is_child()) {
                    // must insert a parent or a child at most once
                    assert_eq!(rw, reward, "FATAL: tried to insert multiple distinct matured parent block reward records");
                    present = true;
                }
            }

            if present {
                return Ok(());
            }
        }
