### Title
Reward-distribution block clamp bounds block count but not per-block stake-account write amplification - ([File: accounts-db/src/partitioned_rewards.rs])

### Summary
`Bank::get_reward_distribution_num_blocks` computes `num_chunks = total_stake_accounts.div_ceil(stake_account_stores_per_block)` and then clamps the result to at most `slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH`. The clamp only limits the *number of blocks* used to spread reward distribution, not the *number of accounts processed per block*, so once `total_stake_accounts` grows large enough to trigger the clamp, `hash_rewards_into_partitions` still spreads all accounts (via hashing) across the clamped, smaller partition count, giving each partition far more than `stake_account_stores_per_block` accounts.

### Finding Description
`get_reward_distribution_num_blocks` (`runtime/src/bank/partitioned_epoch_rewards/mod.rs:409-428`) is:
```rust
let num_chunks = total_stake_accounts.div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize) as u64;
num_chunks.clamp(1, (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1))
``` [1](#0-0) 

The intent of `stake_account_stores_per_block` is to bound per-block AccountsDB write work (documented in `accounts-db/src/partitioned_rewards.rs` as "Baseline number of stake accounts to store in one block") [2](#0-1) . However, the upper clamp on `num_chunks` caps only the block *count*, so once `total_stake_accounts` is large enough that the unclamped `num_chunks` exceeds `slots_per_epoch / 10`, the resulting `num_partitions` value passed downstream is the fixed clamp cap rather than a value derived from `stake_account_stores_per_block`.

This `num_partitions` (from `get_reward_distribution_num_blocks`) is used by `begin_partitioned_rewards` to size the epoch-rewards sysvar and later by `distribute_partitioned_epoch_rewards`, which calls `hash_rewards_into_partitions(&status.all_stake_rewards, &epoch_rewards_sysvar.parent_blockhash, epoch_rewards_sysvar.num_partitions as usize)` [3](#0-2) . `hash_rewards_into_partitions` (`runtime/src/bank/partitioned_epoch_rewards/epoch_rewards_hasher.rs:6-24`) hashes every stake account's pubkey into one of the `num_partitions` buckets and pushes its index into that bucket, with no bound on bucket size:
```rust
for (i, reward) in stake_rewards.enumerated_rewards_iter() {
    let partition_index = hasher.clone().hash_address_to_partition(&reward.stake_pubkey);
    indices[partition_index].push(i);
}
``` [4](#0-3) 

Each block's partition is then processed by `store_stake_accounts_in_partition`, called from `distribute_epoch_rewards_in_partition` via `distribute_partitioned_epoch_rewards` [5](#0-4) , which stores every stake account in that partition into AccountsDB in one block, as demonstrated by `test_store_stake_accounts_in_partition` [6](#0-5) .

Consequently, if `total_stake_accounts = N` is large enough that `N.div_ceil(stake_account_stores_per_block) > slots_per_epoch/10`, the number of blocks stays fixed at `slots_per_epoch/10`, but the average number of accounts stored per block becomes `N / (slots_per_epoch/10)`, growing linearly with `N` and unbounded by `stake_account_stores_per_block`. The existing test `test_get_reward_distribution_num_blocks_cap` only checks that the number of blocks is capped; it does not check (and the code does not enforce) that per-block account count stays near `stake_account_stores_per_block` once the cap is hit [7](#0-6) .

An attacker who funds and delegates a very large number of distinct stake accounts (each costing only the fixed stake-account rent-exemption plus a transaction fee) before an epoch boundary can drive `N` far past the `stake_account_stores_per_block * slots_per_epoch/10` threshold, forcing the distribution blocks after the epoch boundary to each store a disproportionately large number of accounts in AccountsDB, well beyond the intended per-block budget, at a fixed per-account cost to the attacker unrelated to the amplified per-block validator work.

### Impact Explanation
This is a disproportionate per-block AccountsDB storage/index write-amplification issue: validators processing distribution blocks after the epoch boundary must perform `store_stake_accounts_in_partition` work proportional to `N / clamp_cap` rather than the intended `stake_account_stores_per_block`, for a cost to the attacker that is only proportional to fixed per-account creation costs (rent-exemption + tx fee), not to the amplified validator work. This falls under "disproportionate storage and CPU cost" relative to fees paid, matching the described bounty category for reward-distribution DoS/resource-exhaustion issues.

### Likelihood Explanation
Feasibility requires only an unprivileged user creating and delegating a large number of stake accounts before an epoch boundary — no special privileges, leaked keys, or validator/leader control needed. This is directly reproducible: an attacker chooses `N` proportional to the desired amplification factor and simply waits for the epoch boundary; the effect scales deterministically and repeatably with `N`, as it is driven entirely by the pure function `get_reward_distribution_num_blocks` and the deterministic hashing in `hash_rewards_into_partitions`.

### Recommendation
Change the clamp logic so that when `num_chunks` (computed from `stake_account_stores_per_block`) exceeds the `MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH` block-count cap, the system should not silently balloon per-block account counts. Options: (a) keep the block-count cap but additionally clamp/limit the number of stake accounts credited per epoch (e.g., cap total processed accounts, deferring/rejecting excess into a later epoch), or (b) recompute an effective `stake_account_stores_per_block` for the epoch as `total_stake_accounts / num_chunks_clamped` is disallowed from significantly exceeding the configured baseline by instead scaling `MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH`/block cap dynamically with `total_stake_accounts`, or introduce a maximum enforced ceiling on delegated stake accounts eligible for reward per epoch that is consistent with `stake_account_stores_per_block * slots_per_epoch`.

### Proof of Concept
```rust
// runtime/src/bank/partitioned_epoch_rewards/mod.rs (tests module)
#[test]
fn test_get_reward_distribution_num_blocks_amplification() {
    let (mut genesis_config, _mint_keypair) = create_genesis_config(1_000_000 * LAMPORTS_PER_SOL);
    genesis_config.epoch_schedule = EpochSchedule::custom(432_000, 432_000, false);

    let mut accounts_db_config: AccountsDbConfig = ACCOUNTS_DB_CONFIG_FOR_TESTING;
    let stake_account_stores_per_block = 4096u64;
    accounts_db_config.partitioned_epoch_rewards_config =
        PartitionedEpochRewardsConfig::new_for_test(stake_account_stores_per_block);

    let bank = Bank::new_from_genesis(
        &genesis_config, Arc::new(RuntimeConfig::default()), Vec::new(), None,
        accounts_db_config, None, Some(SlotLeader::new_unique()), Arc::default(), None, None,
    );

    let max_blocks = genesis_config.epoch_schedule.slots_per_epoch / 10; // clamp cap

    for n in [
        max_blocks * stake_account_stores_per_block,          // right at the cap
        max_blocks * stake_account_stores_per_block * 10,     // 10x over
        max_blocks * stake_account_stores_per_block * 100,    // 100x over
    ] {
        let stake_rewards = (0..n)
            .map(|_| Some(PartitionedStakeReward::new_random()))
            .collect::<PartitionedStakeRewards>();

        let num_blocks = bank.get_reward_distribution_num_blocks(&stake_rewards);
        assert_eq!(num_blocks, max_blocks, "block count stays clamped");

        // Average accounts stored per block grows unbounded with n, well beyond
        // stake_account_stores_per_block, despite the clamp:
        let avg_per_block = n / num_blocks;
        assert!(
            avg_per_block > stake_account_stores_per_block,
            "expected amplification: avg_per_block={} > baseline={}",
            avg_per_block, stake_account_stores_per_block
        );
    }
}
```
Expected result: for all three values of `n`, `num_blocks` stays fixed at `max_blocks`, while `avg_per_block` scales linearly with `n`, demonstrating that per-block work (subsequently executed by `store_stake_accounts_in_partition` via `hash_rewards_into_partitions`) is not bounded by `stake_account_stores_per_block` once the block-count clamp is hit.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
