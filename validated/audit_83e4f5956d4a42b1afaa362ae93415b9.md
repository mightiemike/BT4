### Title
Weight double-counting via ECDSA signature malleability in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract (address `0x66`) sums per-signer weights to check whether a multisig permission's threshold is met, but it deduplicates signers by matching the **exact raw signature bytes** paired with the recovered address, rather than deduplicating solely by the recovered signer address. Because ECDSA signatures are malleable (a valid `(r, s, v)` triple can be trivially turned into a second, distinct, but equally valid `(r, N-s, v')` triple that recovers to the same address — the same SWC-117 class of bug described in the external report), an attacker can submit two syntactically different signatures derived from the *same* single signature to make the same signer's weight count twice toward the permission threshold.

### Finding Description
In `ValidateMultiSign.execute`, weight is accumulated using `executedSignList` for de-duplication: [1](#0-0) 

For each signature in the array, the code recovers the signer address with `recoverAddrBySign`, then merges the address with the raw signature bytes (`sign = merge(recoveredAddr, sign)`) and only `continue`s (skips adding weight) if **both** the address *and* the merged (address+raw-signature) value already exist in `executedSignList`. If the address is already present but the raw signature bytes differ from a previous entry, the code does not skip — it only calls `MUtil.checkCPUTime()` (a CPU-budget guard) and then proceeds to add the signer's weight to `totalWeight` again.

`recoverAddrBySign` uses `SignUtils.fromComponents(...).validateComponents()` and `ECDSASignature.validateComponents()`, which only checks that `r` and `s` lie in `[1, N)` — it does not enforce a canonical/low-`s` form: [2](#0-1) [3](#0-2) 

Consequently, given one valid signature `(r, s, v)` from a real key-holder over the multisig hash, an attacker can compute the mathematically-equivalent malleable signature `(r, N-s, v^1)` — no private key knowledge required — which is byte-wise different from the original but still recovers to the exact same address. Submitting both signatures in the `signatures` array passed to `ValidateMultiSign` causes the loop to add that single signer's `weight` twice, inflating `totalWeight` and potentially satisfying `permission.getThreshold()` with fewer independent, real signers than the permission actually requires.

This mirrors the report's root cause precisely: replay/duplicate protection is keyed off the full signature value instead of the signer identity (the "nonce"/address here), so signature malleability defeats the intended de-duplication.

### Impact Explanation
`ValidateMultiSign` is a public TVM precompile invocable by any smart contract from any unprivileged transaction, taking attacker-controlled `address`, `permissionId`, `data`, and an array of signatures. Any contract logic (in-chain or third-party) that relies on this precompile to gate on-chain actions behind a multisig threshold (e.g., custodial/vault contracts, DAOs, bridges) can have its threshold check bypassed using only signatures obtainable from legitimately-signing parties (or even just one legitimate signer plus malleated duplicates), reducing the effective number of independent approvals required. This is an authorization/threshold-bypass impact in a core signature-verification primitive exposed to all TVM contracts.

### Likelihood Explanation
Exploitation only requires: (1) one valid signature from a signer already in the permission's key list (which may itself be attacker-obtained through normal, legitimate channels such as a single cooperating/compromised co-signer), and (2) trivial arithmetic to derive the malleable counterpart signature — no cryptographic secret is needed. The vulnerable code path is unconditionally reachable by any contract invocation of the precompile, making this a low-effort, high-confidence bypass whenever a contract's security model depends on the number of *distinct* signers meeting a threshold via this precompile.

### Recommendation
Change the de-duplication logic in `ValidateMultiSign.execute` to key strictly on the recovered signer address (or on canonicalized signatures) rather than on the raw signature bytes: once `recoveredAddr` has already contributed weight in this call, always `continue` (skip adding weight again) regardless of whether the exact raw signature bytes match. Optionally, also reject non-canonical (high-`s`) signatures in `ECDSASignature.validateComponents()`/`recoverAddrBySign` to eliminate malleable duplicates outright, consistent with the recommendation in the referenced report to track identity/nonce rather than the full signature value.

### Proof of Concept
1. Deploy a contract `V` whose account has an active `Permission` with `threshold = 2 * weight(signerA)` and only `signerA` in its key list with that weight (or more generally, a threshold reachable by double-counting one signer).
2. Obtain one valid signature `sigA = (r, s, v)` from `signerA` over the hash `sha256(address || permissionId || data)` computed exactly as in `ValidateMultiSign.execute` (lines 1058-1064).
3. Compute the malleable counterpart `sigA' = (r, N - s, v XOR 1)` — this recovers to the same `signerA` address via `recoverAddrBySign`.
4. Call the `ValidateMultiSign` precompile (address `0x66`) from a contract with `signatures = [sigA, sigA']`.
5. Observe that `executedSignList` dedup check at line 1092-1096 fails to skip the second entry (since the merged `sign` bytes differ), so `totalWeight` is incremented twice for the same `weight(signerA)`, and the precompile returns `dataOne()` (success) even though only one real signer approved.
