Based on my investigation, I found a genuine analog of the reported bug-class, but I could not fully confirm the network-reachability of the vulnerable code path before running out of iterations. I'll report what is locally provable and flag the uncertainty explicitly.

### Title
Missing Merkle range-proof verification in `StateSnapshotRestoreMode::KvOnly` allows unverified state values to be committed during restore - (File: storage/aptosdb/src/state_restore/mod.rs)

### Summary
`StateSnapshotRestore::add_chunk` branches on `restore_mode`. In `StateSnapshotRestoreMode::Default`, each chunk's `SparseMerkleRangeProof` is verified against the tree (`tree_restore.verify_chunk(...)`) *before* the raw key/value data is written to the state-KV store. In `StateSnapshotRestoreMode::KvOnly`, that verification step is entirely absent — the function accepts a `proof` parameter but never uses it, and blindly writes the supplied `(K, V)` chunk to the KV store via `kv_restore.add_chunk(chunk)`, exactly mirroring the reported pattern where a check ("round must be active") is enforced on one code path but silently skipped on a sibling path (matching-pool donations).

### Finding Description [1](#0-0) 

```rust
fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
    match self.restore_mode {
        StateSnapshotRestoreMode::KvOnly => {
            let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
            self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
        },
        StateSnapshotRestoreMode::TreeOnly => {
            ...
            self.tree_restore.lock().as_mut().unwrap()
                .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
        },
        StateSnapshotRestoreMode::Default => {
            // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
            self.tree_restore.lock().as_mut().unwrap()
                .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
        },
    }
    Ok(())
}
```

The `KvOnly` arm takes `proof` as an argument but discards it — it never calls `verify_chunk` or any equivalent cryptographic check against `expected_root_hash` before persisting the values. This is structurally identical to the reported `donate()` flaw: the round-activity/`project_id` check is applied for the "public" branch but omitted for the sibling ("matching pool") branch, letting the sibling branch bypass an invariant the code clearly intends to enforce for all callers of `add_chunk`.

This code is exercised both from the backup-restore CLI (`storage/backup/backup-cli/src/coordinators/restore.rs`, phase 1.a: `StateSnapshotRestoreMode::KvOnly` used to restore KV history below `ledger_history_start_version`) and is a reachable public mode of `StateSnapshotRestore`, which implements `StateSnapshotReceiver` — the same trait used by state-sync/fast-sync consumers (`state-sync/state-sync-driver/src/storage_synchronizer.rs`, `bootstrapper.rs::process_state_values_payload`).

### Impact Explanation
If `KvOnly` mode is reachable with attacker-influenced chunk data (e.g., a compromised/malicious backup source, or if any state-sync code path selects `KvOnly` for KV-history replication), the state-KV database would be populated with values that were never checked against the expected Merkle root. Because reads of the JMT (tree) side are hash-only while the KV side stores the actual serialized state, this can desynchronize the authenticated value returned by APIs from the value implied by proofs/accumulator roots — i.e., "authenticated API or state-view output bound to the wrong ... proof context," directly matching one of the required state-integrity impacts.

### Likelihood Explanation
I was **not able to fully verify** the likelihood before running out of tool budget. Specifically:
- I confirmed `KvOnly` is used in the backup-restore CLI (`coordinators/restore.rs`) for restoring `kv_snapshot` (a version below the KV history retention start), which is a locally/operator-invoked flow — this alone is a weaker, operator-trust-bounded impact.
- I could **not confirm or rule out** whether `StateSnapshotRestoreMode::KvOnly` (as opposed to `Default`) is ever selected by the state-sync/fast-sync path (`bootstrapper.rs`, `storage_synchronizer.rs`) that consumes chunks from **untrusted network peers**. If it is only ever used in the backup CLI with operator-supplied/trusted backups, the practical impact is bounded by backup-provider trust (closer to out-of-scope "third-party" trust assumptions). If it is reachable via peer-supplied network sync data, the impact would be critical and clearly in-scope.

Because I could not close this gap with the remaining iterations, I'm flagging the finding with this caveat rather than asserting full exploitability with certainty.

### Recommendation
Regardless of current reachability, `StateSnapshotRestoreMode::KvOnly`'s `add_chunk` should verify the `SparseMerkleRangeProof` against the mode's own `expected_root_hash` (matching the `Default`/`TreeOnly` behavior) before writing values to `kv_restore`, so no code path can persist state-KV data without proof binding. At minimum, `KvOnly` should be documented and gated so it is only reachable from flows where the KV bytes are independently guaranteed correct by another verified step in the same restore session (and that guarantee should be enforced in code, not just by convention).

### Proof of Concept
Not constructed — a full PoC requires confirming an untrusted-input call path into `StateSnapshotRestoreMode::KvOnly`, which I was unable to trace to completion (`state-sync/state-sync-driver/src/storage_synchronizer.rs` and `bootstrapper.rs` reference `get_state_snapshot_receiver`/`initialize_snapshot_synchronizer`, but I did not get to inspect their `StateSnapshotRestoreMode` selection logic before the iteration budget was exhausted).
