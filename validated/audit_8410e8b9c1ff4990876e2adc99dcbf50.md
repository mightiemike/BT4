No stateful "blocked" status machine analogous to `GMXVault`'s `Deposit` status exists in this repo's in-scope bridge/deposit code. The `deposit` function in `Bridge.sol` already implements exactly the fix recommended in the external report: if the native transfer to the recipient fails (e.g., recipient is an unpayable contract or blocklisted), the funds are pushed to a `failedDepositVault` instead of reverting or leaving the system stuck.No vulnerability found for this question.

The GMX report's bug class is a "push‑payment during an in‑progress state machine" issue: `GMXVault.status` gets set to `Deposit` and only released back to `Open` by a callback that pushes ETH back to `msg.sender`; if that push reverts (unpayable contract), the vault is permanently stuck in `Deposit`, blocking all future deposits/withdrawals for every other user.

Citrea's analogous flow — `Bridge.sol::deposit()` — has no such shared, blockable state machine. Each deposit is processed as an independent, atomic system transaction with no persistent "in-progress" status gating subsequent deposits [1](#0-0) . Crucially, the contract already implements exactly the "pull instead of push" mitigation the external report recommends: if the native transfer to the extracted `recipient` fails, the funds are redirected to a `failedDepositVault` rather than reverting the whole operation [2](#0-1) .

Even in the edge case where the `failedDepositVault` transfer itself fails (causing the whole `deposit()` system transaction to revert), the sequencer's system-transaction processing loop explicitly handles a failed deposit system transaction by reverting only that transaction's working-set checkpoint and continuing to process the remaining system and non-system transactions, rather than leaving any shared state stuck [3](#0-2) . Because deposits aren't removed from the `DepositDataMempool` until they're successfully included in a block, and a failing one simply gets retried later without blocking others in the same batch, there is no equivalent of `GMXVault`'s stuck `Deposit` status that would freeze the bridge or a proof/commitment binding [4](#0-3) .

No custody, proof, determinism, DA-integrity, or authority boundary is crossed by this bug class in the in-scope repository code.

    /// Removes specific deposits from the mempool after they have been successfully included in a block
    ///
    /// # Arguments
    /// * `deposits_to_remove` - The deposits that were successfully included
    ///
    /// # Returns
    /// The number of deposits actually removed
    #[instrument(level = "trace", skip_all, ret)]
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
