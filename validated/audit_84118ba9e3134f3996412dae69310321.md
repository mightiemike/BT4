### Title
Deposits removed from mempool unconditionally regardless of `process_sys_txs` success/failure - ([File: crates/sequencer/src/runner.rs])

### Summary
`produce_l2_block_inner` fetches deposit blobs from `DepositDataMempool::fetch_deposits` and later calls `remove_deposits(&deposit_data)` unconditionally on the *entire fetched batch*, without checking which deposits actually succeeded inside `process_sys_txs`. A deposit whose `Bridge.deposit` call reverts inside `process_sys_txs` (e.g. because `BitcoinLightClient::SetBlockInfo` for the referenced L1 block was not yet applied at this `l2_height`) is silently reverted via checkpoint/revert but is still permanently evicted from the mempool with no re-queue mechanism.

### Finding Description
The invariant that should hold is: `{deposits removed from DepositDataMempool} == {deposits whose BridgeDeposit system event was successfully applied in process_sys_txs}`. Tracing the code shows this equality is broken.

`fetch_deposits` (crates/sequencer/src/deposit_data_mempool.rs:57-69) returns up to `deposit_mempool_fetch_limit` deposits without removing them, and this is the `deposit_data` fetched in `produce_l2_block_inner` at [1](#0-0) .

These deposits are converted into `SystemEvent::BridgeDeposit` events via `populate_deposit_system_events(deposit_data)` and appended after the `SetBlockInfo` events in `produce_and_run_system_transactions` [2](#0-1) .

Inside `process_sys_txs`, each event is applied inside a fresh checkpoint; if the deposit's underlying EVM call fails with `EvmSystemTransactionNotSuccessful` the working set is reverted and the loop simply `continue`s to the next event, without any signal that this specific deposit failed being propagated back to the caller [3](#0-2) . The function's return value (`all_txs`, the applied system tx RLPs) contains only the *encoded system transactions*, not any per-deposit success/failure map that could be used to selectively retain failed deposits in the mempool.

Back in `produce_l2_block_inner`, after the block is saved, the code unconditionally removes every deposit that was fetched at the start of the function, regardless of whether it succeeded in `process_sys_txs`: [4](#0-3) . There is no filtering against `all_txs` or any success list — `deposit_data` is the full batch fetched at line 517-520, so `remove_deposits(&deposit_data)` removes both successful and failed deposits identically.

Given the attacker's scenario — a deposit blob `B` whose Merkle proof references an L1 block that has not yet had its `SetBlockInfo` event applied at this `l2_height` (a legitimate DA-lag race, not an attack on validation logic) — `B`'s `Bridge.deposit` call correctly fails the inclusion check against `BitcoinLightClient` state, is reverted inside `process_sys_txs`, but is still stripped from the `DepositDataMempool` at line 638 because removal is keyed on the original fetch, not on execution outcome.

### Impact Explanation
A genuinely locked BTC deposit is permanently frozen: cBTC is never minted for it, and the deposit blob is evicted from `DepositDataMempool` with no automatic re-submission path (the attacker/user would need to manually resubmit via `citrea_sendRawDepositTransaction`, and nothing in the protocol guarantees they know to do so or that a resubmission will be treated as non-duplicate once `calc_tx_id`-based `pending_deposits` tracking is stale). This matches the Critical category: funds permanently frozen. The bug is repeatable for any deposit whose L1 reference block lags relative to the sequencer's currently-processed `da_blocks` window at the exact `l2_height` it happens to be picked up — it's a structural sequencer bug, not merely user error, since nothing prevents `fetch_deposits`+`process_sys_txs`+`remove_deposits` racing ahead of `SetBlockInfo` availability.

### Likelihood Explanation
This does not require any adversarial capability beyond normal use of `citrea_sendRawDepositTransaction` with a valid deposit that happens to be observed by the mempool slightly before the sequencer's DA ingestion catches up to the referenced L1 block for that specific `l2_height`. No majority hashrate, key compromise, or privileged role is needed — it can occur from ordinary timing/DA-lag alone, making it plausible in normal operation, not just a contrived attack. Cost to the "attacker" (or unlucky user) is the real BTC they lock in their own deposit; the harm is losing access to their own funds.

### Recommendation
Track per-deposit success/failure in `process_sys_txs` (e.g., return a set of deposit blobs whose corresponding `BridgeDeposit` event was actually applied without reverting) and only call `remove_deposits` with that successful subset in `produce_l2_block_inner`, leaving failed deposits in the mempool so they are retried in a subsequent `l2_height` once the required `SetBlockInfo` event is present.
