### Title
Stale session snapshot used to invalidate access token clobbers a freshly-stored valid token during token exchange - (File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts)

### Summary
`performTokenExchange()` captures the session it loaded from storage *before* running the OAuth token-exchange flow (`sessionToInvalidate = session`), then later — if the **online** token-exchange call fails with a `401` — invalidates that pre-exchange, stale session object. Because the offline token exchange has already succeeded and stored a *new* valid access token under the same session ID by that point, the invalidation call overwrites the newer good token with `accessToken: undefined`, discarding correct state that was already persisted.

### Finding Description
In `performTokenExchange`, `sessionToInvalidate` is assigned once, right after the initial `loadSession()` call, before any exchange has happened: [1](#0-0) 

When `useOnlineTokens` is enabled, the flow subsequently performs the offline exchange and immediately persists it: [2](#0-1) 

If the **online** exchange (`exchangeToken(..., RequestedTokenType.OnlineAccessToken, ...)`) subsequently throws an `HttpResponseError` with code `401`, the outer `catch` block runs: [3](#0-2) 

`invalidateAccessToken(sessionToInvalidate, config)` calls `config.sessionStorage.storeSession(session)` with the **stale** `sessionToInvalidate` object (the pre-exchange offline session, sharing the same session ID as the just-stored `offlineSession`) and its `accessToken` set to `undefined`: [4](#0-3) 

Because `sessionId` for the offline token is derived deterministically from the shop (`api.session.getOfflineId(shop)`), this write targets the exact same storage key that `offlineSession` was just stored under a few lines earlier. The result: the brand-new, valid offline access token obtained moments before is wiped out and replaced with `undefined`, even though the offline exchange itself succeeded — the failure being invalidated actually belongs to the *online* token request, not the offline one. This is directly analogous to the report's root cause: a value/decision (which session/token to invalidate) is derived from a state snapshot taken earlier, then applied after the state has already moved forward (offline token stored), producing an incorrect final outcome.

### Impact Explanation
Every request from a merchant whose app has `useOnlineTokens: true` and whose *online* token-exchange call fails with a `401` (e.g., due to app configuration, scope changes, or the Partner/Admin API rejecting the online token grant while offline grants remain valid) will have its legitimate, freshly obtained offline access token erased from session storage on each such request. This forces the app into a persistent re-authentication loop for that shop even though a perfectly valid offline token was just issued and discarded by the app's own logic — a self-inflicted denial of service of the auth/token-exchange handler for the affected shop, and unnecessary repeated OAuth token-exchange calls to Shopify.

### Likelihood Explanation
This is reachable in the normal, unprivileged code path for any single merchant using `useOnlineTokens: true` with the token-exchange future flag — no privileged actor or secret compromise is required. It triggers whenever the online-token exchange leg fails with 401 after the offline leg has already succeeded, which is a realistic and repeatable condition (e.g., online token requests can fail independently of offline ones due to per-request user context, session/cookie validity on Shopify's side, or timing/scope issues), so the corrupted state can recur on every subsequent request until fixed.

### Recommendation
Do not invalidate a session snapshot captured before the exchange ran. Instead:
- Re-derive/reload the session that actually needs invalidation at the point of failure (i.e., load the current state by session ID right before invalidating), or
- Track separately which specific exchange (offline vs. online) failed and only invalidate the session tied to *that* specific request/type, never a stale pre-exchange reference, and
- Avoid persisting an invalidation write that could race with (and overwrite) a more recent, valid `storeSession` call for the same session ID.

### Proof of Concept
1. Configure the app with `future: { tokenExchange: true }` and `useOnlineTokens: true`.
2. A merchant's request arrives with a valid session token; the stored session for the shop is missing/inactive, so `performTokenExchange` runs.
3. `sessionToInvalidate` is set to the (empty/undefined or stale) session loaded from storage before any exchange.
4. The offline token exchange (`RequestedTokenType.OfflineAccessToken`) succeeds, and `offlineSession` (with a fresh, valid `accessToken`) is stored via `config.sessionStorage.storeSession(offlineSession)`.
5. The online token exchange (`RequestedTokenType.OnlineAccessToken`) then fails, throwing `HttpResponseError` with `code: 401` (mirroring the existing test at `packages/apps/shopify-app-express/src/middlewares/__tests__/perform-token-exchange.test.ts:154-193`, but with the failure occurring on the online leg after the offline leg has already succeeded and stored a token).
6. The outer `catch` executes `invalidateAccessToken(sessionToInvalidate, config)`, which calls `storeSession` on the stale pre-exchange session object, using the same offline session ID — overwriting the just-stored valid `offlineSession.accessToken` with `undefined`.
7. Loading the offline session afterward (`shopify.config.sessionStorage.loadSession(shopify.api.session.getOfflineId(TEST_SHOP))`) shows `accessToken` is now `undefined`, even though a valid offline token was successfully obtained and persisted in step 4.

import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}
