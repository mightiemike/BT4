Based on my investigation, I found a strong analog in the NEAR Wallet Contract's ERC-20 emulation logic.

### Title
Native NEAR value attached to an emulated ERC-20 transfer transaction is silently dropped/lost - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/eth_emulation.rs])

### Summary
The NEAR Wallet Contract emulates Ethereum RLP-encoded transactions, mapping ERC-20 `transfer` calldata to NEP-141 `ft_transfer` actions. Similar to the OpenQ bug where MATIC sent alongside an ERC20 deposit call is lost because the receiving function only accounts for the token path and ignores `msg.value`, the Wallet Contract's `try_emulation` function for `ERC20_TRANSFER_SELECTOR` only decodes the transaction's `data` field into an NEP-141 `ft_transfer` action and never inspects or validates the transaction's native `value` field (the Ethereum-style attached "MATIC/ETH equivalent").

### Finding Description
In `eth_emulation.rs`, `try_emulation` matches on `tx.data[0..4]` to detect the ERC-20 `transfer` selector, then builds an `Action::FunctionCall` for `ft_transfer` with `yocto_near: 1` (the mandatory NEP-141 1-yoctoNEAR requirement) [1](#0-0) . Nowhere in this function, nor in the caller `parse_rlp_tx_to_action`/`parse_tx_data` path, is `tx.value` checked to be zero when the parsed action turns out to be an `ERC20Transfer`.

Compare this to the `EOABaseTokenTransfer`/native transfer path, which explicitly converts an Ethereum transaction's `value` field (using `MAX_YOCTO_NEAR` scaling) into a NEAR `Transfer` action's deposit, e.g. in the test helper `create_rlp_execute_tx`, where `value` is derived from the intended NEAR deposit [2](#0-1) . This confirms that `value` is treated by the protocol as native NEAR to be moved with `Transfer`/`FunctionCall` deposit fields — but the ERC-20 transfer path in `eth_emulation.rs` completely ignores it when building the `ft_transfer` `Action::FunctionCall`.

Because `parse_rlp_tx_to_action` only forwards the parsed `Action`/`TransactionKind` and never surfaces or rejects a non-zero `tx.value` for the `ERC20Transfer` kind, a caller who submits a transaction with `to = <NEP-141 token contract>`, `data = ERC20_TRANSFER_SELECTOR + args`, and a non-zero `value` field will have that attached NEAR value neither transferred to the receiver nor refunded to the sender/relayer — it is simply never referenced by any action or promise created in `inner_rlp_execute`.

### Impact Explanation
Any NEAR value encoded in the `value` field of an RLP transaction that also encodes an ERC-20 (`ft_transfer`) call is permanently unaccounted for: it is not moved to the token receiver, not sent back to the wallet owner, and not refunded to the relayer/predecessor via the `CallerDeposit` mechanism (which only tracks `env::attached_deposit()` of the *outer* NEAR `rlp_execute` call, not the *inner* emulated ETH tx's `value` field). This is a permanent, protocol-level loss-of-funds bug reachable purely by any account (a normal transaction signer/relayer) calling `rlp_execute` on a deployed Wallet Contract instance with a crafted RLP payload — no privileged access required.

### Likelihood Explanation
High likelihood of accidental triggering: any wallet/tooling (or user) that naively reuses the same transaction-construction logic used for token+value transfers on Ethereum (where `value` and ERC-20 `data` can coexist, though ERC-20 transfers conventionally use `value = 0`) could set a non-zero `value` alongside ERC-20 `transfer` calldata, causing silent fund loss. It can also be deliberately triggered by any external caller since no special permission is needed to call `rlp_execute`.

### Recommendation
In `eth_emulation.rs::try_emulation` (or in `internal.rs::parse_rlp_tx_to_action`/`parse_tx_data`), when the transaction is classified as `ParsableEthEmulationKind::ERC20Transfer`, explicitly validate that `tx.value.is_zero()`, and return a `UserError` (e.g., `UnsupportedValueWithErc20Transfer`) otherwise, mirroring the recommended fix in the referenced report (`require(msg.value == 0, ...)`). Alternatively, add an explicit NEAR `Transfer` action to the returned promise chain that moves the corresponding `value` to the receiver before or alongside the `ft_transfer` promise.

### Proof of Concept
1. Deploy a Wallet Contract instance (`eth_implicit_account`) and fund it with NEAR, and have a NEP-141 token contract mint tokens to it (as in `test_erc20_emulation`, see `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs:204-296`).
2. Construct an Ethereum-style `Transaction2930` with:
   - `to` = the NEP-141 token contract address,
   - `data` = `ERC20_TRANSFER_SELECTOR` + ABI-encoded `(recipient_address, amount)`,
   - `value` = a non-zero `Wei` amount (e.g. equivalent to 1 NEAR).
3. Sign it with the wallet's secret key and submit via `rlp_execute(token_contract_id, signed_tx)`.
4. Observe: `ft_transfer` executes and moves NEP-141 tokens correctly, but the wallet's NEAR balance is not decreased by the `value` amount, no NEAR is transferred to the recipient wallet, and no refund promise is generated for it — the attached NEAR value is unaccounted for (only gas costs reduce the wallet's balance). Confirm by comparing account balances before/after as done in `test_erc20_emulation`, and note that no `Transfer` action or extra `promise_batch_action_transfer` referencing `tx.value` exists anywhere in `inner_rlp_execute` for the `ERC20Transfer` branch [3](#0-2) .
