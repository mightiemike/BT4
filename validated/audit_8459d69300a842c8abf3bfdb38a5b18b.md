### Title
PoX-4 `make_signer_set()` floor-and-drop weighting can zero out the entire Nakamoto signer set for a reward cycle, halting the chain - (File: `stackslib/src/chainstate/stacks/boot/mod.rs`)

### Summary
`StacksChainState::make_signer_set` (used by the still-active PoX-4 reward-set computation path) assigns each stacker a weight of `stacked_amt / threshold` and unconditionally drops any entry whose weight floors to `0`, with no remainder-redistribution. If the stackers registered in a cycle produce a distribution where every entry floors to zero (e.g. more distinct signer keys than reward slots, each holding roughly equal stake), the computed signer set becomes empty for that entire reward cycle. Because this reward set feeds directly into Nakamoto block/signature validation, an empty signer set makes the reward cycle unusable and the coordinator explicitly errors out (`Error::PoXAnchorBlockRequired`), stalling chain progress for every node that reaches that cycle - deterministically and without requiring majority stake.

### Finding Description
`make_signer_set` computes weight via plain floor division and filters zero-weight entries with no fallback: [1](#0-0) 

This is exactly the "floor-and-drop" scheme that the codebase's own regression test documents as buggy and chain-stalling for the newer PoX-5 signer-set builder, which was fixed with a largest-remainder (Hare) method: [2](#0-1) 

However, PoX-4 reward-cycle computation still calls the old, unfixed `make_signer_set` via `make_reward_set`: [3](#0-2) [4](#0-3) 

The threshold itself is a smooth, liquid-supply/participation-scaled function (`get_reward_threshold_and_participation`), which any minority stacker set can steer by choosing how much and how many distinct signer keys to stack with, given knowledge of the total participation in the cycle: [5](#0-4) 

Once `pox_4_compute_and_update_signers` computes an empty `signers()` list, it is written to the `.signers` contract regardless (`reward_set.signers().unwrap_or(&empty_signers)`), and downstream `OnChainRewardSetProvider::get_reward_set` treats an empty Nakamoto signer set as fatal: [6](#0-5) 

Every node computes the reward set deterministically from the same on-chain stacking transactions, so all honest nodes hit this same `Error::PoXAnchorBlockRequired` for the affected reward cycle - this is a liveness/equality-breaking bug: the invariant "a Nakamoto reward cycle always has a non-empty signer set when there is nonzero participation" is violated by the flooring scheme, not by any node disagreement, but the practical effect is a network-wide inability to select/validate blocks for that cycle.

### Impact Explanation
This falls under the Critical bucket ("permanent freezing via irreversible reorg" / network-wide inability to process a reward cycle): a reward cycle with an all-zeroed signer set cannot produce a valid Nakamoto tenure, and `PoXAnchorBlockRequired` blocks reward-set loading for every node reaching that cycle boundary, deterministically. Unlike the PoX-5 path (already patched with the Hare remainder method), PoX-4's `make_signer_set` retains the exact defect the project's own tests describe as chain-stalling.

### Likelihood Explanation
Reaching the degenerate "more distinct signers than reward slots, near-equal stake" condition does not require majority stake - it only requires influencing the composition of stacked entries in a cycle (e.g., splitting one's own stack across many `stack-stx`/`stack-aggregation-commit` calls with distinct signer keys, or timing participation so that combined with existing honest stackers the threshold computation makes every entry floor to zero). Since `reward_slots` is typically small (e.g. hundreds), and thresholds are derived from aggregate liquid/participation amounts that are often publicly observable near a prepare phase, an attacker can tune their own stacked amounts and signer-key count to trigger the zeroing condition documented by the project's own regression test.

### Recommendation
Backport the same largest-remainder (Hare) allocation used in `pox_5_make_signer_set` (`stackslib/src/chainstate/nakamoto/signer_set.rs`) to the PoX-4 `make_signer_set` path in `stackslib/src/chainstate/stacks/boot/mod.rs`, so that `reward_slots` are always fully allocated to at least the top stackers by remainder even when many entries floor to zero, guaranteeing a non-empty signer set whenever there is nonzero PoX-4 participation.

### Proof of Concept
1. In a PoX-4 reward cycle, have `N > reward_slots` distinct stackers (which can include Sybil signer-keys controlled by a single minority participant plus incidental honest stackers) each lock approximately equal `amount_stacked` such that `threshold = ceil(scale_by / reward_slots)` computed by `get_reward_threshold_and_participation` (`stackslib/src/chainstate/stacks/boot/mod.rs:1211-1243`) exceeds each individual `amount_stacked`.
2. `pox_4_compute_and_update_signers` (`stackslib/src/chainstate/nakamoto/signer_set.rs:703-738`) calls `make_reward_set` → `make_signer_set` (`stackslib/src/chainstate/stacks/boot/mod.rs:1020-1072`), where every entry's `stacked_amt / threshold == 0`, producing an empty `signer_set`.
3. This empty signer set is written to `.signers` and later read by `OnChainRewardSetProvider::get_reward_set` (`stackslib/src/chainstate/coordinator/mod.rs:349-352`), which returns `Err(Error::PoXAnchorBlockRequired)` for every node once the Nakamoto reward cycle activates, blocking further block production/validation for that cycle across the whole network.

    pub fn get_reward_threshold_and_participation(
        pox_settings: &PoxConstants,
        addresses: &[RawRewardSetEntry],
        liquid_ustx: u128,
    ) -> (u128, u128) {
        let participation = addresses
            .iter()
            .fold(0, |agg, entry| agg + entry.amount_stacked);

        assert!(
            participation <= liquid_ustx,
            "CORRUPTION: More stacking participation than liquid STX"
        );

        // set the lower limit on reward scaling at 25% of liquid_ustx
        //   (i.e., liquid_ustx / POX_MAXIMAL_SCALING)
        let scale_by = cmp::max(participation, liquid_ustx / POX_MAXIMAL_SCALING);

        let reward_slots = u128::try_from(pox_settings.reward_slots())
            .expect("FATAL: unreachable: more than 2^128 reward slots");
        let threshold_precise = scale_by / reward_slots;
        // compute the threshold as nearest 10k > threshold_precise
        let ceil_amount = match threshold_precise % POX_THRESHOLD_STEPS_USTX {
            0 => 0,
            remainder => POX_THRESHOLD_STEPS_USTX - remainder,
        };
        let threshold = threshold_precise + ceil_amount;
        info!(
            "PoX participation threshold is {}, from {} + {} ({}), participation is {}",
            threshold, threshold_precise, ceil_amount, scale_by, participation
        );
        (threshold, participation)
    }

#[test]
fn equal_stakes_exceeding_reward_slots_are_not_all_zeroed() {
    // Regression: more distinct signers than reward_slots, all with equal stake.
    //
    // The old floor-and-drop scheme set threshold = ceil(N*S / R) > S, so every
    // signer's weight floored to 0 and the entire set was dropped -- stalling the
    // chain. The Hare round must instead award one slot each to the top `R` signers
    // (by remainder, then signing_key), dropping only the surplus signers.
    let pox_constants = test_pox_constants(1); // reward_slots() == 4
    let reward_slots = pox_constants.reward_slots();
    assert_eq!(reward_slots, 4);
    let stake = 1_000_000u128;
    // 5 signers, only 4 slots.
    let entries: Vec<_> = (0..5u8)
        .map(|i| RawPox5Entry {
            signer_key: signer_key(i),
            amount_ustx: stake,
        })
        .collect();
    let mut iter = entries.into_iter().map(Ok);
    let Pox5SignerSetOutput { signer_set, .. } =
        NakamotoSigners::pox_5_make_signer_set(&mut iter, &pox_constants).expect("ok");

    assert_eq!(
        signer_set.len(),
        reward_slots as usize,
        "expected exactly reward_slots signers, not an empty/zeroed set"
    );
