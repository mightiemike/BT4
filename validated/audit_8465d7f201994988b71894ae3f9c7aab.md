The bug class here — trusting a value from one context (BTC/USD) to authoritatively represent a different, related-but-distinct value (WBTC/USD) that isn't cryptographically/contractually bound to it — maps to the webhook validation flow in `shopify-app-js`, where the `X-Shopify-Hmac-Sha256` signature only binds to the raw request body but the shop-identifying `domain` header used for session lookup and tenant routing is never covered by that signature.

### Title
Webhook HMAC does not bind the `X-Shopify-Shop-Domain` header, enabling cross-tenant webhook forgery - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
`validateFactory` in [1](#0-0)  computes and checks the webhook HMAC only over `rawBody` via `validateHmacFromRequestFactory`, then separately reads the `domain` header out of `checkWebhooksHeaders`/`checkEventsHeaders` without any cryptographic linkage between the two values.

### Finding Description
`validateHmacFromRequestFactory` (in `hmac-validator.ts`) computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` and compares it against the `X-Shopify-Hmac-Sha256` header using `safeCompare` — see [2](#0-1) . This signature is derived from the app's single shared `apiSecretKey`, which is identical for *every* shop that installs the app — it is not shop-specific. Separately, `checkWebhooksHeaders`/`checkEventsHeaders` extract the `domain` header purely as a required-presence header with no relation to the HMAC computation: [3](#0-2) .

Downstream, `authenticateWebhookFactory` trusts `check.domain` directly to resolve which shop's offline session to load and attach to the webhook context: [4](#0-3)  (identical logic exists in the react-router package: [5](#0-4) ).

Because the HMAC only proves "this body was signed with the app's shared secret" and not "this body was destined for shop X," any actor who has legitimately received one valid `(rawBody, hmac)` pair from Shopify (e.g., by installing the app on their own store and triggering a webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value. The signature check passes (it never inspected `domain`), and the webhook is processed as if it originated from the shop named in the forged `domain` header — including loading that shop's real offline session/access token and invoking the app's topic handlers with attacker-controlled payload content.

### Impact Explanation
This allows cross-tenant webhook forgery: an attacker who is merely an app-installing merchant on their own store can forge webhook events attributed to any other shop that has previously installed the app (their session need only still exist in storage), because `check.domain` is used unauthenticated to select the tenant. Depending on what webhook topics the app subscribes to, this can lead to unauthorized state changes performed under a victim's admin session (e.g., corrupting synced data, triggering `app/uninstalled` cleanup logic against a shop that never actually uninstalled, or feeding attacker-controlled payload into business logic gated only by "this is a validly-signed webhook, so `domain` is trustworthy"). This is a cross-tenant authorization bypass at the webhook-authentication boundary, reachable from an unprivileged single merchant's own webhook traffic.

### Likelihood Explanation
Likelihood is moderate: the attacker does not need the app's secret key (excluded per rules), only the ability to install the app on their own store (a single, unprivileged merchant) and capture one legitimately Shopify-signed `(rawBody, hmac)` pair for a topic whose body content is generic/predictable enough to be replayed meaningfully (e.g., GDPR/mandatory topics or topics with minimal/static payload shape), then resend it with a forged `domain` header pointing at any shop with an existing stored session. No cryptographic secret disclosure, MITM, or privileged access is required — only observed traffic from the attacker's own installation.

### Recommendation
Cryptographically bind the shop identity to the signed payload before trusting it for session/tenant resolution:
- After HMAC validation succeeds, independently verify that a session actually exists for `check.domain` before treating the payload as authentic for that shop, and additionally cross-check the `domain` header value against fields embedded in the JSON payload itself where Shopify includes shop identifiers (and reject on mismatch).
- Where feasible, incorporate the `domain` (and `topic`/`webhook_id`) into the value being HMAC'd/verified, or require an out-of-band verification (e.g., re-fetching the resource via the resolved session's access token and comparing shop identity) before executing any state-changing webhook handler logic.
- At minimum, document and enforce that webhook handlers must not assume `domain` alone proves the request originated from that shop, and require idempotency/ownership checks against the loaded session before executing sensitive operations.

### Proof of Concept
1. Attacker installs the target app on their own development store (`attacker.myshopify.com`), obtaining offline session storage entry, `apiSecretKey` shared across all installs.
2. Attacker triggers (or waits for) a webhook with a generic/static body — e.g., a mandatory compliance topic or an event whose JSON body is minimal/predictable — and captures the real `rawBody` and the valid `X-Shopify-Hmac-Sha256` header Shopify computed with the shared `apiSecretKey`.
3. Attacker sends a POST to the app's webhook endpoint with the identical `rawBody` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a real shop that has previously installed the app and still has a stored offline session), and appropriate `X-Shopify-Topic`/`X-Shopify-Webhook-Id`/`X-Shopify-Api-Version` headers.
4. `validateFactory` → `validateHmacFromRequestFactory` validates the HMAC (it only checked `rawBody`), returns `valid: true` with `domain: 'victim.myshopify.com'` per [6](#0-5) .
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim.myshopify.com')`, loading the victim's real offline session/access token, and invokes the app's webhook handler with the attacker-controlled payload as if it were a genuine event from the victim shop: [7](#0-6) .

      }
      return validHmacResult;
    }

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }
