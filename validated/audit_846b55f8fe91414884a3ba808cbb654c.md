### Title
Race condition in offline access-token refresh allows concurrent requests to corrupt the stored session, permanently invalidating the app's refresh token (DoS of the auth/session-refresh handler) - (File: `packages/apps/shopify-app-remix/src/server/helpers/ensure-offline-token-is-not-expired.ts`)

### Summary
The Axelar report's core bug class is a **check-then-act desync**: a value (token balance / amount) is read and used to make a security/consistency decision, but the underlying external state (the rebasing token's real balance) can change between the read and the write, causing either an unfair transfer or a hard failure that locks funds. The same "stale local state vs. authoritative external state, last-write-wins" pattern exists in shopify-app-js's offline access-token refresh flow, using Shopify's OAuth refresh-token endpoint, which rotates (single-use) refresh tokens.

### Finding Description
When the `expiringOfflineAccessTokens` future flag is enabled, every code path that touches an offline session (`validateAuthenticatedSession`, `ensureValidOfflineSession`, used from webhook handlers, cron jobs, and queues per the docs) independently loads the session, checks if it is within 5 minutes of expiry, and if so calls `refreshToken` with the currently-stored `session.refreshToken`, then unconditionally overwrites the stored session: [1](#0-0) 

This same pattern is duplicated verbatim in `shopify-app-react-router` and (functionally) in `shopify-app-express`: [2](#0-1) [3](#0-2) 

The underlying `refreshToken` call sends `refresh_token` grant requests to Shopify's `/admin/oauth/access_token` endpoint: [4](#0-3) 

Refresh tokens are rotated on use (each successful exchange returns a *new* `refresh_token`), analogous to the rebasing token's balance mutating outside the code path that "locked" it. There is no locking, versioning, or optimistic-concurrency check anywhere in this flow: `session.isExpired(...)` is evaluated against the value read at the start of the request, and `storeSession` performs a blind upsert keyed only by session id, e.g.: [5](#0-4) [6](#0-5) 

If two requests (e.g., a normal authenticated request and a concurrently-firing background job/webhook using `ensureValidOfflineSession`, both explicitly documented as valid concurrent callers) observe the same near-expiry `refreshToken` at the same time, both issue a `refresh_token` grant to Shopify with the identical (single-use) token value. Depending on Shopify's rotation/grace-window semantics, whichever request's `storeSession` call resolves last "wins" and persists its resulting `{accessToken, refreshToken}` pair, discarding the other's newer credential. If the loser's response is written last, the session that ends up in storage can reference a refresh token that Shopify has already invalidated (rotated away), making all subsequent refresh attempts fail with `invalid_grant`/`HttpResponseError`, since there is no retry or reconciliation path once this happens.

### Impact Explanation
Once the stored `refreshToken` becomes stale relative to Shopify's server-side state, the offline session becomes permanently unusable: `ensureOfflineTokenIsNotExpired` will keep calling `refreshToken`, which will keep failing, and any background work relying on `ensureValidOfflineSession` (webhooks, cron jobs, queues — the very use case the helper was built for) will be denied service until the merchant manually re-authenticates the app. This is a self-inflicted Denial of Service of an authentication/session-refresh handler triggered purely by ordinary concurrent traffic, with no attacker privilege required — mirroring the ITS Hub finding where legitimate value became permanently stuck due to stale tracked state colliding with externally-mutated authoritative state.

### Likelihood Explanation
The condition is reachable by unprivileged, ordinary usage: any app that enables `expiringOfflineAccessTokens` and has more than one consumer of the offline session near its 5-minute expiry window (a page load plus a webhook delivery, two concurrent webhook deliveries, a cron job overlapping with a user request, etc.) can trigger overlapping refresh attempts. The documentation explicitly encourages calling `ensureValidOfflineSession` from multiple independent execution contexts (webhook handlers, fulfillment services, cron jobs, queues), which increases the likelihood of two callers racing on the same near-expiry token.

### Recommendation
Serialize refresh attempts per shop/session (e.g., via a distributed lock, a `SELECT ... FOR UPDATE`/conditional update keyed on the previous `refreshToken` value, or an in-flight-refresh promise cache) so only one refresh request is issued per session per expiry window, and make `storeSession` for the refresh path a compare-and-swap on the prior `refreshToken`/`accessToken` rather than a blind upsert, so a losing concurrent writer does not overwrite a newer, valid credential.

### Proof of Concept
1. Enable `future: { expiringOfflineAccessTokens: true }` in an app using `shopify-app-remix`/`shopify-app-react-router`/`shopify-app-express`.
2. Let the stored offline session's `refreshToken` sit within `WITHIN_MILLISECONDS_OF_EXPIRY` (5 minutes) of `expires`.
3. Fire two near-simultaneous requests that both traverse `ensureOfflineTokenIsNotExpired`/`ensureValidOfflineSession` for the same shop (e.g., an authenticated admin request and a webhook delivery, or two concurrent webhook deliveries).
4. Both read the same stale `session.refreshToken` and each call `shopify.auth.refreshToken` in `refresh-token.ts`, each receiving a distinct new `access_token`/`refresh_token` pair from Shopify.
5. Whichever `config.sessionStorage.storeSession(offlineSession)` call completes last persists its pair; if Shopify has already invalidated the other (now-discarded-but-possibly-final) refresh token due to rotation, the next refresh attempt returns `invalid_grant`, permanently breaking automated refresh for that shop until re-installation.

export async function ensureOfflineTokenIsNotExpired(
  session: Session,
  params: BasicParams,
  shop: string,
) {
  const {config} = params;
  if (
    config.future?.expiringOfflineAccessTokens &&
    session.isExpired(WITHIN_MILLISECONDS_OF_EXPIRY) &&
    config.distribution !== AppDistribution.ShopifyAdmin &&
    session.refreshToken
  ) {
    const offlineSession = await refreshToken(
      params,
      shop,
      session.refreshToken,
    );

    await config.sessionStorage!.storeSession(offlineSession);
    return offlineSession;
  }
  return session;
}

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      refresh_token: refreshToken,

    const postResponse = await fetchRequestFactory(config)(

      {

          Accept: DataType.JSON,
        },
      },
    );

  public async storeSession(session: Session): Promise<boolean> {
    await this.ensureReady();
    const data = this.sessionToRow(session);

    try {
      await this.getSessionTable().upsert({
        where: {id: session.id},
        update: data,
        create: data,
      });
    } catch (error) {
      if (
        error instanceof Prisma.PrismaClientKnownRequestError &&
        error.code === UNIQUE_KEY_CONSTRAINT_ERROR_CODE
      ) {
        console.log(
          'Caught PrismaClientKnownRequestError P2002 - Unique Key Key Constraint, retrying upsert.',
        );
        await this.getSessionTable().upsert({
          where: {id: session.id},
          update: data,
          create: data,
        });
        return true;
      }
      throw error;
    }

    return true;
  }
