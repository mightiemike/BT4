### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by HMAC verification, allowing shop-domain spoofing via signed-body replay - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`validateHmacFromRequestFactory` computes and verifies the webhook HMAC solely over `rawBody`, never over the `X-Shopify-Shop-Domain` (or Events equivalent) header. `checkWebhooksHeaders`/`checkEventsHeaders` then extract the `domain` field directly from that unauthenticated header and pass it, unchanged, into `callWebhookHandlers` → the app's `handler.callback(topic, domain, ...)`. A merchant who legitimately installs the app can replay one of their own genuinely-signed webhook deliveries while swapping only the domain header to a victim shop's domain, and the request still passes HMAC verification. The claim about injecting SQL metacharacters or oversized strings into that value is not viable, however, because the library's documented/standard consumption path (`getOfflineId` → `sanitizeShop`) enforces a strict `myshopify.com`/`shopify.com`/`myshopify.io`/`shop.dev` regex and throws on anything that doesn't match this format.

### Finding Description
- `validateFactory` (packages/apps/shopify-api/lib/webhooks/validate.ts, lines 56-73) first calls `validateHmacFromRequestFactory(config)` and only calls `checkWebhookHeaders` (which dispatches to `checkWebhooksHeaders`/`checkEventsHeaders`) if `validHmacResult.valid` is `true`. So the domain field is indeed only read into `fields` after HMAC succeeds — but "HMAC succeeds" does not mean the domain header itself was validated. [1](#0-0) 
- `validateHmacFromRequestFactory` verifies the HMAC by calling `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — it only reads the HMAC header and the raw body; it never touches the domain/shop header at all. [2](#0-1) 
- `checkWebhooksHeaders`/`checkEventsHeaders` then simply pull `domain` from `headerNames.domain` (the `X-Shopify-Shop-Domain` header) with no cross-check against the HMAC-covered body. [3](#0-2) 
- `process.ts`'s `callWebhookHandlers` forwards `webhookCheck.domain` straight into the app-registered `handler.callback(topic, domain, rawBody, webhookId, apiVersion, context)`. [4](#0-3) 
- The library's own documented pattern for webhook handlers is to take that `shop` parameter directly into `shopify.session.getOfflineId(shop)`, which only calls `sanitizeShop(config)(shop, true)` for format validation — it does **not** verify the shop is the one that actually sent the request. [5](#0-4) [6](#0-5) 
- `sanitizeShop` enforces a strict regex (`^[a-zA-Z0-9][a-zA-Z0-9-_]*\.(myshopify\.com|shopify\.com|myshopify\.io|shop\.dev)[/]*$`) and throws `InvalidShopError` on non-conforming input, so SQL metacharacters/oversized payloads are rejected before reaching `getOfflineId`/session storage. [7](#0-6) 

**Exploit flow:** An attacker who is a legitimate (unprivileged) merchant with the app installed on their own shop receives a real webhook delivery (valid `rawBody` + valid HMAC computed by Shopify for that body). They replay that exact `rawBody`/HMAC pair to the app's webhook endpoint but substitute the `X-Shopify-Shop-Domain` header with another (real, format-valid) shop's domain. HMAC validation still passes because it never covers headers. The forged domain is then handed to the app's webhook callback as the "shop" for this event, and if the app follows the library's documented pattern (`getOfflineId(domain)` → `sessionStorage.loadSession(id)`), it resolves to the victim shop's real offline session id and the attacker's payload/data gets processed under the victim's tenant context.

### Impact Explanation
This is a cross-tenant confusion/attribution bug, not SQL injection: the strict regex in `sanitizeShop` blocks metacharacter/oversized-payload injection into session storage. The real, scoped impact is that a webhook event (with attacker-controlled body content, since only the body's HMAC is checked, not its correctness relative to the claimed shop) can be attributed to and processed against another tenant's offline session/data, which can lead to state corruption in the victim's tenant or unintended actions being taken on the victim's behalf, depending on what the host app's webhook handler does with the resolved session. This falls under Shopify's "cross-tenant data/state access" impact class, though the depth of impact is bounded by what a given app's own callback logic does with the session.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to be an ordinary merchant/customer who can install the app (or otherwise capture one legitimately HMAC-signed webhook body for a topic the app subscribes to) and can freely re-POST arbitrary headers to the app's public webhook endpoint — no `apiSecretKey` or privileged role is required. It requires the target app to have registered an HTTP webhook handler and to follow the library's own documented `shop`-parameter usage pattern (`getOfflineId(shop)`), which is the primary/recommended usage shown in the library's docs, not a misconfiguration.

### Recommendation
The library should not allow the `domain`/shop identity used by webhook consumers to be trusted purely from the unauthenticated header. Either:
1. Include the shop domain (and/or webhook id/topic) as part of the HMAC-covered material verified in `validateHmacFromRequestFactory`, or
2. Cross-validate the `X-Shopify-Shop-Domain` header value against a value derived from an authenticated source (e.g., the shop referenced in the app's own webhook registration/session storage) before handing it to `callWebhookHandlers`, or
3. At minimum, update the `getOfflineId` documentation/warning to explicitly state that the `domain` header on webhook requests is not covered by the webhook HMAC and must not be trusted as request-authenticating on its own.

### Proof of Concept
```ts
// Jest-style PoC demonstrating header/body decoupling in HMAC validation
import {validateHmacFromRequestFactory} from '../../utils/hmac-validator';
import {HmacValidationType} from '../../utils/types';
import {createSHA256HMAC} from '../../../runtime/crypto';
import {HashFormat} from '../../../runtime/crypto/types';

test('HMAC validation ignores X-Shopify-Shop-Domain header', async () => {
  const config = testConfig(); // existing test helper
  const rawBody = JSON.stringify({id: 1, note: 'attacker-controlled-body'});
  const hmac = await createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64);

  const request = {
    method: 'POST',
    headers: {
      'X-Shopify-Hmac-Sha256': hmac,
      'X-Shopify-Topic': 'orders/create',
      'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // swapped, format-valid domain
      'X-Shopify-Webhook-Id': 'some-id',
      'X-Shopify-API-Version': '2024-01',
    },
    url: 'https://my-app.example/webhooks',
  };

  const result = await validateHmacFromRequestFactory(config)({
    type: HmacValidationType.Webhook,
    rawBody,
    webhookType: 'webhooks',
    rawRequest: request,
  });

  // HMAC validation succeeds even though the domain header was swapped,
  // because the HMAC only covers rawBody, not headers.
  expect(result.valid).toBe(true);
});
```
Expected assertion: `result.valid === true` despite the `X-Shopify-Shop-Domain` header not matching the shop that actually produced `rawBody`/`hmac`, confirming that downstream `checkWebhooksHeaders` will surface the attacker-chosen `domain` to `callWebhookHandlers` and any app callback using `getOfflineId(domain)`.

export function sanitizeShop(config: ConfigInterface) {
  return (shop: string, throwOnInvalid = false): string | null => {
    let shopUrl = shop;
    const domainsRegex = [
      'myshopify\\.com',
      'shopify\\.com',
      'myshopify\\.io',
      'shop\\.dev',
    ];

    // Add domains from transformations (both source and target)
    if (config.domainTransformations) {
      domainsRegex.push(...getTransformationDomains(config));
    }

    const shopUrlRegex = new RegExp(
      `^[a-zA-Z0-9][a-zA-Z0-9-_]*\\.(${domainsRegex.join('|')})[/]*$`,
    );

    const shopAdminRegex = new RegExp(
      `^admin\\.(${domainsRegex.join('|')})/store/([a-zA-Z0-9][a-zA-Z0-9-_]*)$`,
    );

    const isShopAdminUrl = shopAdminRegex.test(shopUrl);
    if (isShopAdminUrl) {
      shopUrl = shopAdminUrlToLegacyUrl(shopUrl) || '';
    }

    const sanitizedShop = shopUrlRegex.test(shopUrl) ? shopUrl : null;
    if (!sanitizedShop && throwOnInvalid) {
      throw new InvalidShopError('Received invalid shop argument');
    }

    if (sanitizedShop && config.domainTransformations) {
      return applyDomainTransformations(sanitizedShop, config);
    }

    return sanitizedShop;
  };
