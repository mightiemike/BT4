### Title
Unprivileged attacker can burn an arbitrary victim UEA's PC balance by submitting a gasless `MsgExecutePayload` targeting the victim's account with an intentionally invalid signature - (File: x/uexecutor/keeper/msg_execute_payload.go)

### Summary
`MsgExecutePayload` lets any Cosmos signer (`msg.Signer`) execute a payload against a `UniversalAccountId.Owner` that they do not control. The gas fee for the resulting EVM call is deducted and burned from the *target UEA's* balance — not the caller's — regardless of whether the payload execution ultimately succeeds or reverts. This is the same bug class as the eUSD `executeFlashloan` finding: a caller-chosen "receiver"/target address is charged a fee that only the caller decided to trigger, without needing the target's consent, and the caller pays nothing because the message type is on the gasless allowlist.

### Finding Description
`ExecutePayload` in `x/uexecutor/keeper/msg_execute_payload.go` resolves `ueaAddr` deterministically from the attacker-supplied `UniversalAccountId` (which can name *any* existing UEA owner, not necessarily the caller's own account) [1](#0-0) , then calls the UEA with attacker-controlled `verificationData` [2](#0-1) , and — critically — deducts and burns gas fees from that resolved `ueaAddr` "regardless of success/failure" of the payload execution [3](#0-2) .

`DeductGasFeesFromReceipt` only short-circuits when `receipt == nil || receipt.GasUsed == 0` [4](#0-3) ; any real EVM computation performed before a `revert` (e.g. signature-recovery/hash/nonce checks inside the UEA's `executeUniversalTx`) still shows up as non-zero `GasUsed` in the receipt, and that cost is billed straight out of the target UEA's spendable UPC balance via `DeductAndBurnFees`, which transfers from the recipient account to the module and burns it [5](#0-4) [6](#0-5) .

`msgServer.ExecutePayload` performs no check that `msg.Signer` corresponds to `UniversalAccountId.Owner`, and `MsgExecutePayload.ValidateBasic` only checks that fields are non-nil/well-formed, not that the caller is authorized over the target account [7](#0-6) [8](#0-7) . The module's own documentation confirms this is an intentional design choice ("contract-only binding"): any account may submit the message, and the *EVM execution gas is deducted from the UEA, not the signer* [9](#0-8) . The documented safety argument is that a bad `verificationData` causes the UEA contract to revert and "the entire Cosmos transaction... rolls back atomically... No state changes survive a failed signature check" [10](#0-9) . This reasoning conflates *EVM state changes* with *bank-module state changes*: the gas-fee burn happens in `DeductGasFeesFromReceipt`, called from the Cosmos keeper *after* `CallUEAExecutePayload` returns (whether it errored or not), using `sdkCtx`/`ctx` directly rather than being nested inside the same reverted EVM state — it is not itself rolled back by a UEA-level revert, because the burn is a `bankKeeper` operation, not part of the EVM state transition that reverted.

Since `MsgExecutePayload` is on the gasless allowlist (`app/txpolicy/gasless.go`) [11](#0-10) , an attacker pays no Cosmos transaction fee to repeatedly submit this message, making the griefing/drain economically free to the attacker while it steadily burns real PC from the victim's UEA.

### Impact Explanation
This is an unauthorized burn of protocol/user-controlled funds by an unprivileged attacker: any account can force a burn of PC from any deployed UEA that holds a balance, without the UEA owner's consent or valid signature, purely by naming that UEA as the target of a `MsgExecutePayload` with a bogus `verificationData`. Because the underlying message is gasless, the attack is free and repeatable, allowing incremental griefing/drain of a target UEA's balance. This falls squarely within the in-scope impact "unauthorized burn... of user or protocol-controlled funds" and "corruption of... gas fee accounting."

### Likelihood Explanation
High reachability: `MsgExecutePayload` is a standard user-facing, gasless message type reachable by any account with no bonding, staking, or privileged role required. The only requirement is knowledge of a target `UniversalAccountId` (deterministically derivable/public), and crafting any `verificationData` that fails signature verification inside the UEA (trivial — any garbage bytes). The per-call financial damage is bounded by whatever gas the UEA's revert path consumes before reverting (likely modest per call), but the attack costs the attacker nothing and can be automated/repeated at will against any funded UEA.

### Recommendation
- Do not burn gas fees from the target UEA (`ueaAddr`) when `CallUEAExecutePayload` returns an error (i.e., only charge on successful/committed execution), or bound the chargeable amount to a fixed minimal "verification-only" cost rather than full receipt `GasUsed`.
- Alternatively, wrap `CallUEAExecutePayload` + `DeductGasFeesFromReceipt` in a single `CacheContext` (as is already done in `ExecutePayloadV2`, see `execute_payload.go`) so that a signature-verification failure causes the entire fee deduction to also roll back, matching the documented invariant that "no state changes survive a failed signature check." Note `ExecutePayload` (used by `msg_server.go`) currently lacks this cache-context wrapping that `ExecutePayloadV2` has, creating an inconsistency between the two code paths.
- Consider requiring `msg.Signer` to bear at least a minimal anti-spam cost, or rate-limit failed-signature `MsgExecutePayload` submissions per target UEA.

### Proof of Concept
1. Attacker identifies a deployed, funded UEA belonging to victim `Owner` on some source chain (UEA addresses are deterministic/public via the factory).
2. Attacker (any unfunded/unprivileged account) submits `MsgExecutePayload` with:
   - `Signer` = attacker's own address (not the victim),
   - `UniversalAccountId` = victim's `Owner`/chain (resolves to victim's real UEA via `CallFactoryToGetUEAAddressForOrigin`),
   - `UniversalPayload` = arbitrary well-formed payload with `MaxFeePerGas`/`GasLimit` set,
   - `VerificationData` = random/garbage bytes (fails the UEA's owner-signature check).
3. Since `MsgExecutePayload` is in the gasless allowlist, the attacker pays no Cosmos fee to submit this transaction repeatedly.
4. `k.ExecutePayload` resolves the victim's `ueaAddr` and calls `CallUEAExecutePayload`, which reverts inside the UEA's `executeUniversalTx` due to the invalid signature, but the EVM receipt still reports `GasUsed > 0` for the computation performed before the revert.
5. `DeductGasFeesFromReceipt` computes `gasCost = baseFee * GasUsed` and calls `DeductAndBurnFees(ctx, victimUeaAccAddr, gasCost)`, which transfers PC from the victim's UEA account and burns it — with no state rollback, since this happens outside the reverted EVM execution.
6. Attacker repeats step 2–5 as many times as desired, at zero cost, incrementally burning the victim UEA's PC balance.

func (msg *MsgExecutePayload) ValidateBasic() error {
	// Validate signer
	if _, err := sdk.AccAddressFromBech32(msg.Signer); err != nil {
		return errors.Wrap(err, "invalid signer address")
	}

	// Validate universalAccountId
	if msg.UniversalAccountId == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal account cannot be nil")
	}

	// Validate universal payload
	if msg.UniversalPayload == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal payload cannot be nil")
	}

	// Validate verificationData
	if len(msg.VerificationData) == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "verificationData cannot be empty")
	}
	if _, err := hex.DecodeString(strings.TrimPrefix(msg.VerificationData, "0x")); err != nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "invalid verificationData hex")
	}

	// Validate universalAccountId structure
	if err := msg.UniversalAccountId.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universalAccountId")
	}

	// Validate universal payload structure
	if err := msg.UniversalPayload.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universal payload")
	}

	return nil
}

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```

4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
```
