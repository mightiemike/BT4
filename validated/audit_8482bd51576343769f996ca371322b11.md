### Title
Unbounded per-block work in `eth_getBlockReceipts` can consume excessive CPU/memory on a single anonymous JSON-RPC request - (File: framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java)

### Summary
The external report describes a bug class where a single call whose cost scales with the number of transactions/logs in a block (block finalization) can exceed the resource budget the operator assumed, causing degraded service or DoS. The closest reachable analog in java-tron is `eth_getBlockReceipts`, a JSON-RPC method that iterates over **every transaction and every event log of an entire block** in one synchronous call, with no cap on the number of transactions/logs processed per invocation — unlike other range-based endpoints (`getBlockByLimitNext`, `eth_getLogs`) which explicitly cap the number of *blocks* that can be scanned.

### Finding Description
`getBlockReceipts` fetches a full block and its `TransactionInfoList`, then calls `getTransactionReceiptsFromBlock`, which loops over all transactions in the block and, for each one, builds a `TransactionReceipt` that itself iterates over all of that transaction's logs: [1](#0-0) [2](#0-1) [3](#0-2) 

Unlike `eth_getLogs`/`eth_getFilterLogs`, which explicitly bound the number of *blocks* scanned via `jsonRpcMaxBlockRange` (`LogFilterWrapper.validateBlockRange`) and cap total results via `LogBlockQuery.MAX_RESULT` in `LogMatch.matchBlockOneByOne`: [4](#0-3) [5](#0-4) 

`eth_getBlockReceipts` has **no equivalent cap** — it is only bounded by the size of the block itself. A block's transaction/log payload is bounded only by the protocol-level `BLOCK_SIZE` constant (2,000,000 bytes): [6](#0-5) 

A 2 MB block packed densely with small transactions that each emit multiple event logs (via `LOGx` opcodes) can contain a large number of transactions/logs. Every `eth_getBlockReceipts("latest")` (or by hash/number) call against such a block reconstructs receipts and logs for the entire block synchronously on the calling thread, with output serialized and returned in a single JSON-RPC response. There is no per-servlet/per-method rate limiter specifically covering JSON-RPC calls (`rate.limiter` config only applies to HTTP servlets and gRPC methods, not the JSON-RPC dispatcher), and no `maxResponseSize`-style truncation is applied before the work is done — `maxResponseSize` in `jsonrpc` config is documented as applying to request bodies, not this kind of expensive read-then-serialize response.

### Impact Explanation
Repeated calls to `eth_getBlockReceipts` against heavy blocks force the FullNode/JSON-RPC service to repeatedly do O(transactions × logs) work and allocate large `List<TransactionReceipt>` objects, without any block-content-based cap analogous to `jsonRpcMaxBlockRange` or `LogBlockQuery.MAX_RESULT`. An attacker who can identify or produce a log-heavy block can repeatedly hit this endpoint to consume CPU and memory on the node's JSON-RPC service, degrading availability for legitimate RPC users — the same class of issue as the reported "block finalization gas exceeds gas limit" bug, translated to "unbounded per-request work scaling with block content" in java-tron's RPC layer.

### Likelihood Explanation
`eth_getBlockReceipts` is reachable by any unauthenticated caller of the JSON-RPC HTTP endpoint (`httpFullNodeEnable`/`httpSolidityEnable`) with only a block number/hash/tag parameter — no special privileges, keys, or malicious peer/node behavior required. Producing (or waiting for) a transaction/log-heavy block that fits within the 2 MB block-size protocol limit is realistically achievable by any network participant submitting many event-emitting transactions, since transaction/log volume is not otherwise gated for this specific read path.

### Recommendation
Apply the same defensive pattern already used for `eth_getLogs`/`eth_getFilterLogs`: bound the amount of work `eth_getBlockReceipts` (and similar full-block-scan RPC methods) can do per call, e.g., cap the number of transactions/logs processed and returned, reject or paginate blocks whose transaction/log count exceeds a configurable threshold, and consider adding it to the `rate.limiter` configuration (`GlobalPreemptibleAdapter`/`IPQPSRateLimiterAdapter`) the way HTTP servlets are protected. Benchmark real-world worst-case block payloads (max transactions × max logs per transaction within `BLOCK_SIZE`) to size this limit appropriately.

### Proof of Concept
1. Submit enough transactions that each emit several event logs (e.g., via `LOG3`/`LOG4` opcodes) to fill a block close to the 2,000,000-byte `BLOCK_SIZE` limit.
2. Once the block is produced, repeatedly call the JSON-RPC method `eth_getBlockReceipts` with that block's number/hash from an unauthenticated client.
3. Each call triggers `getTransactionReceiptsFromBlock` to iterate over every transaction and every log in the block and construct/serialize a full `TransactionReceipt[]` response — with no analog to `jsonRpcMaxBlockRange`/`MAX_RESULT` limiting the amount of work done, unlike `eth_getLogs`.
4. Repeating this against a busy node measurably increases CPU/memory use on the JSON-RPC service, illustrating the DoS potential from unbounded per-block-content work.

  @Override
  public List<TransactionReceipt> getBlockReceipts(String blockNumOrHashOrTag)
      throws JsonRpcInvalidParamsException, JsonRpcInternalException {

    Block block = null;

    if (blockNumOrHashOrTag != null && Pattern.matches(HASH_REGEX, blockNumOrHashOrTag)) {
      block = getBlockByJsonHash(blockNumOrHashOrTag);
    } else {
      // null falls through to getBlockByNumOrTag -> parseBlockNumber -> -32602 (not an NPE)
      block = getBlockByNumOrTag(blockNumOrHashOrTag);
    }

    // block receipts not available: block is genesis, not produced yet, or pruned in light node
    if (block == null || block.getBlockHeader().getRawData().getNumber() == 0) {
      return null;
    }

    BlockCapsule blockCapsule = new BlockCapsule(block);
    long blockNum = blockCapsule.getNum();
    TransactionInfoList transactionInfoList = wallet.getTransactionInfoByBlockNum(blockNum);

    // energy price at the block timestamp
    long energyFee = wallet.getEnergyFee(blockCapsule.getTimeStamp());

    // Validate transaction list size consistency
    int transactionSizeInBlock = blockCapsule.getTransactions().size();
    if (transactionSizeInBlock != transactionInfoList.getTransactionInfoCount()) {
      throw new JsonRpcInternalException(
          String.format("TransactionList size mismatch: "
                  + "block has %d transactions, but transactionInfoList has %d",
              transactionSizeInBlock, transactionInfoList.getTransactionInfoCount()));
    }

    return getTransactionReceiptsFromBlock(blockCapsule, transactionInfoList, energyFee);
  }

  private List<TransactionReceipt> getTransactionReceiptsFromBlock(BlockCapsule blockCapsule,
      TransactionInfoList transactionInfoList, long energyFee) {

    List<TransactionReceipt> receipts = new ArrayList<>();
    long cumulativeGas = 0;
    long cumulativeLogCount = 0;

    for (int index = 0; index < transactionInfoList.getTransactionInfoCount(); index++) {
      TransactionInfo info = transactionInfoList.getTransactionInfo(index);
      ResourceReceipt resourceReceipt = info.getReceipt();

      TransactionReceipt.TransactionContext context = new TransactionContext(
          index, cumulativeGas, cumulativeLogCount);

      // Use the constructor with pre-calculated context
      TransactionReceipt receipt = new TransactionReceipt(blockCapsule, info, context, energyFee);
      receipts.add(receipt);

      cumulativeGas += resourceReceipt.getEnergyUsageTotal();
      cumulativeLogCount += info.getLogCount();
    }
    return receipts;
