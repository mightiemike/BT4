### Title
Missing purpose-binding in `validateHmacFromRequestFactory` allows a Webhook-signed payload to be replayed as a valid FulfillmentService (or Flow) request - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`validateHmacFromRequestFactory` (used by `shopify.fulfillmentService.validate`, `shopify.webhooks.validate`, and `shopify.flow.validate`) computes and checks the signature the same way regardless of the `HmacValidationType` passed in: `HMAC-SHA256(apiSecretKey, rawBody)` read from the `X-Shopify-Hmac-Sha256` header (`ShopifyHeader.Hmac`). The `type` argument is never mixed into the signed data - it is only used for debug-log strings in `fail`/`succeed`. Because standard Webhooks also sign with `ShopifyHeader.Hmac` over the raw body (`WEBHOOK_HEADER_NAMES.webhooks.hmac === ShopifyHeader.Hmac`), a genuine Shopify webhook body+signature is byte-for-byte indistinguishable from what `fulfillmentService.validate` expects, so it will be accepted as a valid fulfillment-service request.

### Finding Description
- `fulfillmentService.validate` calls `validateHmacFromRequestFactory(config)({type: HmacValidationType.FulfillmentService, rawBody, ...adapterArgs})` with no `webhookType`, so the header used is the default `ShopifyHeader.Hmac`: [1](#0-0) 
- Inside `validateHmacFromRequestFactory`, the header is selected as `webhookType ? WEBHOOK_HEADER_NAMES[webhookType].hmac : ShopifyHeader.Hmac`, and the actual check is `validateHmacString(config, rawBody, hmac, HashFormat.Base64)`, i.e. `safeCompare(hmac, HMAC-SHA256(apiSecretKey, rawBody))`. The `type` value is passed through only to `fail()`/`succeed()`, which merely log it: [2](#0-1) [3](#0-2) 
- `webhooks.validate` for the standard "Webhooks" delivery type signs/validates using the identical header (`ShopifyHeader.Hmac`) and identical scheme: [4](#0-3) [5](#0-4) 
- `fulfillmentService.validate` never checks `X-Shopify-Topic`, `X-Shopify-Shop-Domain`, or any other purpose/audience marker the way `webhooks.validate` additionally does via `checkWebhookHeaders`/`checkWebhooksHeaders` (topic, domain, apiVersion, webhookId). It only checks presence of a body and a matching HMAC of that body: [6](#0-5) 

Root cause: the signed string (`rawBody`) and the header carrying the signature are identical between the "Webhook" and "FulfillmentService" `HmacValidationType`s, and no type/audience tag is folded into the signed material. This is a textbook signature-confusion / missing-domain-separation bug: the same MAC over the same message under the same key is valid input for two different validators with two different downstream trust decisions.

Exploit flow: an app that both registers standard webhooks and exposes a fulfillment-service endpoint (a supported, non-exotic configuration per the docs) will accept a real Shopify-delivered webhook body+HMAC when it is instead POSTed to the fulfillment-order-notification route. Any party who legitimately receives a real webhook for their own shop (e.g. a merchant who installed the app, who by definition can see the webhooks Shopify sends to that app for their shop) can capture that valid `(rawBody, X-Shopify-Hmac-Sha256)` pair and replay it against `/fulfillment_order_notification` (or wherever the host wires up `authenticate.fulfillmentService`), and `api.fulfillmentService.validate` will return `{valid: true}` even though the payload was never a fulfillment-service message.

### Impact Explanation
Downstream, `authenticateFulfillmentServiceFactory` trusts `result.valid` to gate `JSON.parse(rawBody)` and looks up the offline session/admin client for the shop in the `X-Shopify-Shop-Domain` header: [7](#0-6) . Because the check is only "is this HMAC valid for this body," an attacker can smuggle a differently-shaped, Shopify-signed JSON body (from a webhook they legitimately received for their own shop) into the fulfillment-service code path, bypassing the intended semantic guarantee that the payload is actually a `FULFILLMENT_REQUEST`/`CANCELLATION_REQUEST` fulfillment-order body. This corresponds to Shopify's "improper authentication / broken access control due to missing signature-purpose binding" class. The concrete blast radius is bounded by the fact that the attacker can only replay signatures the sharing of the same `apiSecretKey`-derived scheme allows, and (in this repo, with the standard "Webhooks" type) always for their own shop, since they cannot produce or intercept another merchant's webhook without owning that other merchant's data. So exploitation does not by itself grant cross-tenant access in the base case, but it does let a single malicious/customer-controlled merchant subvert an authenticity invariant the library documents as a security boundary ("validates that it's a legitimate fulfillment service request") and feed attacker-selected-but-Shopify-signed payloads into a code path that expects fulfillment-order semantics, which can cause the app's fulfillment handling logic to run on unintended input.

### Likelihood Explanation
High feasibility, low privilege required: the only precondition is that (a) the app has webhooks registered for the same shop (default for essentially all embedded apps) and (b) the app also implements the fulfillment-service endpoint using this library's `fulfillmentService.validate`. A merchant/customer who is a normal, unprivileged user of the app can simply forward one webhook delivery they received to the fulfillment-service URL with the same headers/body - no secret is needed, no timing attack, no MITM. This is fully repeatable and requires no non-default configuration.

### Recommendation
Bind the `HmacValidationType` (and, ideally, request-specific context such as topic/shop/timestamp) into the signed material check rather than only using it for log strings:
- Either require and check purpose-specific headers per type (as `webhooks.validate` does with `checkWebhookHeaders`) inside `fulfillmentService.validate`/`flow.validate` as well, rejecting the request if webhook-only headers (e.g. `X-Shopify-Topic`) are present, or
- Include a type-specific constant/prefix in the HMAC-verified data (this would require Shopify's signer to also include it, so in practice this needs to be paired with distinguishing metadata already present in legitimate fulfillment-service/Flow requests, e.g. specific required headers not present in generic webhook deliveries), or at minimum
- Explicitly document and enforce that `fulfillmentService.validate`/`flow.validate` must also verify a type-distinguishing header (e.g. presence/absence of `X-Shopify-Topic`) so a webhook payload cannot be replayed there, closing the domain-separation gap in `validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts`.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/fulfillment-service/__tests__/cross-type-replay.test.ts
import {shopifyApi} from '../..';
import {ShopifyHeader} from '../../types';
import {createSHA256HMAC, HashFormat, type NormalizedRequest} from '../../../runtime';
import {testConfig} from '../../__tests__/test-config';

it('accepts a webhook-signed body as a valid fulfillment-service request (should NOT)', async () => {
  const shopify = shopifyApi(testConfig());

  // A body that looks like a normal webhook payload, not a fulfillment order notification
  const webhookBody = JSON.stringify({id: 12345, note: 'orders/create payload'});

  const hmac = await createSHA256HMAC(
    shopify.config.apiSecretKey,
    webhookBody,
    HashFormat.Base64,
  );

  // This is exactly what Shopify sends for a real "orders/create" webhook delivery
  const req: NormalizedRequest = {
    method: 'POST',
    url: 'https://my-app.my-domain.io/fulfillment_order_notification',
    headers: {[ShopifyHeader.Hmac]: hmac},
  };

  const result = await shopify.fulfillmentService.validate({
    rawBody: webhookBody,
    rawRequest: req,
  });

  // Expected (secure) behavior: result.valid === false, reason indicating type mismatch
  // Actual behavior: result.valid === true  -> vulnerability confirmed
  expect(result).toMatchObject({valid: true});
});
```

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
