### Title
Receipt size validation runs before `output_data_receivers`/data-receiver mutation, allowing receipts above `max_receipt_size` to be accepted and persisted - ([File: runtime/runtime/src/lib.rs])

### Summary
The Unbound CVE stems from a class of bug where a buffer/space size is calculated and validated *before* additional data is written into it, so the final encoded object exceeds the size that was checked, causing an overflow past the validated bound. nearcore has a directly analogous, already–acknowledged size-accounting bug in the runtime's receipt pipeline: `validate_receipt` checks the borsh size of a freshly created action receipt in `ValidateReceiptMode::NewReceipt` mode immediately after action execution, but the runtime subsequently mutates that receipt (attaching `output_data_receivers` for a `promise_return`, or generating a `Data`/`PromiseResume` receipt) *after* this size check has already passed. The receipt that is actually persisted/forwarded can therefore be larger than `max_receipt_size`, silently bypassing a protocol-level bound.

### Finding Description
`validate_receipt` performs the size-limit check only for `NewReceipt` mode: [1](#0-0) 

This validation is invoked right after each action executes and produces new receipts, inside the per-action loop of `apply_action_receipt`: [2](#0-1) 

However, the "Output data" step — where `output_data_receivers` are attached to the returned receipt, or where the return value is wrapped into a new `Data` receipt — happens *after* this per-action validation loop has already completed, as documented in the runtime execution spec: [3](#0-2) 

Because `promise_return` lets a callee redirect the DAG's output receivers onto a *different*, previously-created receipt (one that was already size-validated without those receivers), the final serialized receipt written to state / forwarded cross-shard can exceed `limit_config.max_receipt_size` even though it passed validation. The code itself documents this as a live, unresolved issue (`near/nearcore#12606`): [4](#0-3) 

Downstream, the congestion-control forwarding path has an explicit workaround that admits this bug is unresolved and papers over its consequences by clamping the observed size to `max_receipt_size` purely to avoid receipts getting permanently stuck in the outgoing buffer: [5](#0-4) 

Tests explicitly reproduce the acceptance of over-limit receipts through both `promise_return` (`output_data_receivers` added post-check) and large value returns (oversized `Data` receipt), confirming this is reachable purely by an unprivileged contract call: [6](#0-5) 

### Impact Explanation
`max_receipt_size` is a protocol-enforced invariant used to bound trie/state-witness storage, congestion accounting (`compute_receipt_size`, `receipt_bytes` in `CongestionInfo`), and bandwidth-scheduler admission. Silently accepting receipts above this bound means:
- Congestion/bandwidth accounting can be built on truncated/clamped sizes (`try_forward` clamps to `max_receipt_size` for admission purposes while the true, larger receipt is what's actually pushed to `outgoing_receipts` and later serialized into the chunk), which can push actual chunk/state-witness payloads above sizes other validators/clients assumed, risking cross-shard receipt handling divergence.
- It provides an avenue to bypass a hard resource/DoS limit that is otherwise enforced strictly for `NewReceipt` mode, undermining the guarantee that no receipt in the system exceeds `max_receipt_size` — the very invariant the `ExistingReceipt` mode had to be weakened for (`verifier.rs:736-738`) in order to remain compatible with receipts already violating it.
- The maintainers' own workaround at `congestion_control.rs:413-427` shows this bug already has externally visible effects on the forwarding/buffering logic that could affect receipt admission behavior between shards.

### Likelihood Explanation
This is triggerable by any unprivileged account via a plain contract call using standard `promise_create`/`promise_then`/`promise_return` host functions (or a large return value), with no special privileges, as demonstrated in `test-loop-tests/src/tests/max_receipt_size.rs`. It requires no validator or network-level position — purely a transaction submitted through RPC.

### Recommendation
Move (or re-run) the `ReceiptSizeExceeded` size check to occur *after* all mutations to a receipt are finalized (i.e., after `output_data_receivers`/return-value wrapping is applied), so that the borsh size actually persisted/forwarded is what gets validated, closing the gap described in `near/nearcore#12606`. Until fixed, ensure all downstream consumers (congestion control, state witness, bandwidth scheduler) treat the *true* size rather than a clamped approximation, to avoid divergent behavior across implementations.

### Proof of Concept
The existing repository test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs:130-208` is a working PoC: a contract call creates promise DAG `A -> B`, where `A` creates promise `C` and calls `promise_return(C)`. `C`'s receipt is validated at exactly `max_receipt_size` bytes (bypassing the check), and then output data receivers are attached, pushing the *actual* stored/forwarded receipt above `max_receipt_size` — confirmed via `assert_oversized_receipt_occurred`. `test_max_receipt_size_value_return` (lines 216-267) similarly reproduces the bug through a large return value turned into an oversized `Data` receipt.

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);

        101,

        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),

        "".into(),
