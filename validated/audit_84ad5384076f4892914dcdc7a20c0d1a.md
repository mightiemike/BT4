Based on my review of protobuf-go's boolean decoding paths, no analog of the reported bug exists in this codebase.

The Sherlock report describes an out-of-bounds/over-read bug where hand-written EVM assembly reads 32 bytes (`mload(ptr)`) instead of 1 byte when parsing a boolean flag, causing the boolean to always evaluate true regardless of the actual encoded value. In protobuf-go, all boolean decoding paths use `protowire.ConsumeVarint` (or its inlined fast-path equivalent) which correctly bounds the read to the actual varint length and validates `len(b)` at each byte before consuming it [1](#0-0) . The decoded value is then converted via `protowire.DecodeBool`, which is a simple `x != 0` on the correctly-sized `uint64` value — there is no fixed-size/mismatched-size read anywhere in this pipeline [2](#0-1) .

This pattern is consistent across every unmarshal path for bools: the generic reflection-based decoder [3](#0-2) , the fast-path generated-message codec for scalar, pointer, and slice bool fields [4](#0-3) [5](#0-4) [6](#0-5) , and the reflect-value-based coder used for maps/extensions [7](#0-6) . In every case the byte count consumed (`n`) is determined by the actual varint length, never a hardcoded oversized read, and `n < 0` is checked to reject truncated/malformed input before any value is derived.

There is no fixed-width, oversized, or mismatched-length read of a 1-byte boolean field anywhere in protobuf-go's wire decoding, so the reported bug class does not have a live analog on a reachable path in this codebase.
