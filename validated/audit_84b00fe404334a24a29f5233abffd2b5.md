### Title
Proposal approval threshold uses the current (mutable) active witness set instead of a snapshot from proposal creation, allowing witness-set churn to flip governance consensus - (File: framework/src/main/java/org/tron/core/consensus/ProposalController.java)

### Summary
The proposal approval mechanism in java-tron's on-chain governance suffers from the same class of bug described in the referenced report: a "total voting power"-like denominator (`activeWitnesses.size()`) is read at the time the proposal is *processed*, not snapshotted at the time the proposal was *created* or at the time approvals were cast. Because the active Super Representative (witness) set is re-elected every maintenance cycle and can change in size or membership while a proposal is still pending, the effective approval threshold silently shifts after voters have already cast their approvals, which can flip whether a proposal passes or fails independent of voters' intent.

### Finding Description
When a proposal is created, witnesses call `ProposalApproveActuator` to add their address to `proposal.approvals` [1](#0-0) . The proposal is only judged much later, at `hasExpired` maintenance time, via `ProposalController.processProposal` [2](#0-1) .

At judging time, `ProposalController.processProposal` fetches the *current* active witness list from `WitnessScheduleStore` and evaluates `hasMostApprovals` against it: [3](#0-2) 

`hasMostApprovals` computes the pass threshold as 70% of the *current* `activeWitnesses.size()`, not the witness set size at proposal creation time or at the time each approval was cast: [4](#0-3) 

The active witness list (`WitnessScheduleStore.getActiveWitnesses()`) is refreshed every maintenance cycle in `MaintenanceManager.doMaintenance` via `dposService.updateWitness(...)`, which can change both membership and size of the active set [5](#0-4) . This is the direct analog of `totalVotingPower` changing in the Party Protocol report: the denominator used to determine pass/fail is taken from a mutable, continuously-updated quantity instead of a value fixed at proposal creation.

Additionally, `hasMostApprovals` filters approvals by membership in the *current* active set (`activeWitnesses.contains(witness)`) rather than the active set at the time the vote was cast, so a witness who validly approved while an active SR can have their vote silently discarded if they are voted out of the active set before the proposal reaches maintenance-time processing [6](#0-5) .

### Impact Explanation
This is a consensus/governance-integrity issue affecting on-chain parameter changes (`ProposalService.process`, invoked from `setDynamicParameters`) [7](#0-6) . Analogous to the referenced bug:
- If the active witness set count increases between when approvals were gathered and when the proposal is processed, previously-sufficient approvals may fall below the newly enlarged 70% threshold, causing legitimate proposals to be wrongly disapproved.
- If the active witness set count decreases, a smaller absolute number of approvals may satisfy the 70% threshold, or an approver who is no longer an active witness may have their vote invalidated, or membership churn may allow proposals to pass with fewer effective votes than originally intended.
- Because witness re-election happens automatically every maintenance cycle (roughly every 6 hours) purely from on-chain voting activity (an unprivileged, permissionless process reachable via broadcast `VoteWitnessContract` transactions), an adversary or even ordinary voting activity can alter the active witness set composition/size during a proposal's pending window, causing consensus divergence on whether a governance proposal (which can modify critical chain dynamic parameters) should be approved.

### Likelihood Explanation
Witness set changes are a normal, frequent, and unprivileged occurrence in java-tron — they happen at every maintenance cycle as a direct result of ordinary `VoteWitnessContract` transactions from any account, not a privileged actor. Proposals routinely remain pending across multiple maintenance cycles (`expirationTime` is typically set well beyond a single cycle), making it likely that the active witness set will have already changed by the time `processProposal` runs its threshold check. This makes the scenario realistically reachable without any special privilege, purely through the normal course of broadcasting `VoteWitnessContract` transactions.

### Recommendation
Snapshot the active witness list (or at least its size and membership) at proposal creation time, and use that snapshot — rather than the live `WitnessScheduleStore.getActiveWitnesses()` result — in `ProposalCapsule.hasMostApprovals` when the proposal is later judged in `ProposalController.processProposal`. Concretely:
1. Store the active witness set (or its size) in `ProposalCapsule` when the proposal is created.
2. Modify `hasMostApprovals` to accept and use this snapshot instead of the currently-active witness list.
3. Ensure any witness approvals are validated against the snapshot too, so churn in the active set after proposal creation cannot invalidate or unintentionally validate votes.

### Proof of Concept
1. Witness set `S1 = {A, B, C, D, ..., 27 witnesses}` is active. A proposal `P` is created.
2. 19 of 27 witnesses approve `P` (>70% of 27), satisfying the pass threshold under `S1`.
3. Before `P` expires and is processed (i.e., before the next maintenance cycle finalizes), ordinary `VoteWitnessContract` transactions cause the active witness set to change to `S2`, adding several new witnesses so that the active set membership shifts and `activeWitnesses.contains(witness)` no longer matches some of the original 19 approvers, or the required 70% threshold recalculated against `S2`'s membership disqualifies enough of the original approvals.
4. When `ProposalController.processProposal` runs, `hasMostApprovals(S2)` [4](#0-3)  computes the count of valid approvals still in `S2` and compares it to `S2.size() * 7 / 10`, producing a different accept/reject outcome than what the original 19-of-27 approvers intended when they voted under `S1`, demonstrating consensus divergence caused by using a live, unsnapshotted witness set as the governance denominator.

  public boolean hasMostApprovals(List<ByteString> activeWitnesses) {
    long count = this.proposal.getApprovalsList().stream()
        .filter(witness -> activeWitnesses.contains(witness)).count();
    if (count != this.proposal.getApprovalsCount()) {
      List<ByteString> InvalidApprovalList = this.proposal.getApprovalsList().stream()
          .filter(witness -> !activeWitnesses.contains(witness)).collect(Collectors.toList());
      logger.info("InvalidApprovalList:" + getAddressStringList(InvalidApprovalList));
    }
    if (activeWitnesses.size() != MAX_ACTIVE_WITNESS_NUM) {
      logger.info("activeWitnesses size = {}", activeWitnesses.size());
    }
    return count >= activeWitnesses.size() * 7 / 10;
  }

  public void processProposal(ProposalCapsule proposalCapsule) {

    List<ByteString> activeWitnesses = this.manager.getWitnessScheduleStore().getActiveWitnesses();
    if (proposalCapsule.hasMostApprovals(activeWitnesses)) {
      logger.info(
          "Processing proposal,id:{},it has received most approvals, "
              + "begin to set dynamic parameter:{}, "
              + "and set proposal state as APPROVED",
          proposalCapsule.getID(), proposalCapsule.getParameters());
      setDynamicParameters(proposalCapsule);
      proposalCapsule.setState(State.APPROVED);
      manager.getProposalStore().put(proposalCapsule.createDbKey(), proposalCapsule);
    } else {
      logger.info(
          "Processing proposal,id:{}, "
              + "it has not received enough approvals, set proposal state as DISAPPROVED",
          proposalCapsule.getID());
      proposalCapsule.setState(State.DISAPPROVED);
      manager.getProposalStore().put(proposalCapsule.createDbKey(), proposalCapsule);
    }

  }
