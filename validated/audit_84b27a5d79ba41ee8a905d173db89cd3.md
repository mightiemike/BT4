### Title
Poison-microblock commission integer-division underflow makes a punished coinbase reward misclassified as "parent" (`coinbase == 0`), breaking the `is_child()`/`is_parent()` invariant and triggering a deterministic `FATAL` panic on every node that matures the reward - (File: `stackslib/src/chainstate/stacks/db/accounts.rs`)

### Summary
`MinerReward::is_child()`/`is_parent()` classify a reward record solely by whether `coinbase > 0`, but `calculate_miner_reward`'s poison-punishment branch computes the punished participant's award as `poison_microblock_commission(coinbase_reward) = (coinbase_reward * POISON_MICROBLOCK_COMMISSION_FRACTION) / 100`, which truncates to `0` whenever the pre-commission coinbase share is small enough. When that happens, the "child" reward for the tenure ends up with `coinbase == 0`, satisfying `is_parent()` and failing `is_child()`, which violates the assumed invariant that exactly one of the two matured-reward records for a tenure is a child and one is a parent. `stackslib/src/chainstate/stacks/db/accounts.rs:162-186`, `stackslib/src/chainstate/stacks/db/accounts.rs:872-980`.

### Finding Description
The equality that must hold: the two `MinerReward` rows stored for `(parent_block_id, child_block_id)` must always partition into exactly one `is_child()==true` record and one `is_parent()==true` record, so `get_matured_miner_payment` can safely call `try_add_parent` and preserve `matured_reward.total() == coinbase_reward_ustx(tenure) + confirmed_fees(tenure)`.

`calculate_miner_reward` always builds the "miner" (child) record with `tx_fees_streamed_produced: 0` hardcoded (`accounts.rs:974`), so `is_child()` (`coinbase > 0 && tx_fees_streamed_produced == 0`, `accounts.rs:162-164`) collapses to simply `coinbase > 0`. In the punished branch (`accounts.rs:872-895`), when a `poison_reporter_opt` is present and `participant.miner` is true, the reward given to the *reporter* is `poison_microblock_commission(coinbase_reward)` — an integer division by 100 (`accounts.rs:795-797`). If the participant's coinbase share (`coinbase_reward`, itself already proportional to `this_burn_total/burn_total`, `accounts.rs:841-867`) is small enough that `coinbase_reward * POISON_MICROBLOCK_COMMISSION_FRACTION / 100 == 0`, the resulting child-reward record has `coinbase == 0`, `tx_fees_anchored == 0`, `tx_fees_streamed_confirmed == 0` (both zeroed by `punished`), and `tx_fees_streamed_produced == 0` — i.e. it is indistinguishable from a legitimate "parent" reward (`is_parent()` returns true, `is_child()` returns false).

An attacker (any miner who wins a single sortition slot) can engineer this by keeping their own `burnchain_commit_burn` small relative to total participant burns (their own choice/cost) so their proportional coinbase share is small, and by having a confederate/self file a `PoisonMicroblockOp` against their own tenure. This is fully reachable with only a minority stake: any single miner controls their own commit-burn amount, and any participant can file a poison report.

This record is passed to `insert_matured_child_miner_reward`, which asserts `child_reward.is_child()` before writing (`accounts.rs:600-603`): `assert!(child_reward.is_child(), "FATAL: tried to insert a non-child reward as the child reward");`. Since `is_child()` is now false, **this assertion panics deterministically on every node** that processes the tenure at reward-maturation height (`find_mature_miner_rewards` is invoked from block-validation/append code common to all nodes). Even if this early assert were bypassed, the record would reach `get_matured_miner_payment` (`accounts.rs:654-691`) with two `is_parent()==true` records, both `ret_0.is_child()` and `ret_1.is_child()` false, hitting the `else` arm `panic!("FATAL: got two parent rewards")` (`accounts.rs:677-679`) rather than the `try_add_parent` `.expect("FATAL: got two child rewards")` cited in the question — but the practical effect (deterministic panic on all nodes maturing this reward) is the same class of bug.

No existing guard prevents this: `calculate_miner_reward` performs no minimum-threshold check before applying the commission fraction, and the classification predicates `is_child()`/`is_parent()` do not use any positive tag (e.g., a discriminant field) — they infer role purely from `coinbase > 0`, which the poison-commission integer division can zero out.

### Impact Explanation
Because `find_mature_miner_rewards` / `inner_insert_matured_miner_reward` run identically on every full node processing the same chain state, this is a deterministic, network-wide panic that halts every node attempting to mature/apply the reward for the affected tenure — effectively "a valid block rejected network-wide" once the maturation height is reached, i.e. a liveness-affecting chain halt. It requires no majority stake: any single miner who can control their own commit-burn size (trivial, since they choose it) combined with a poison report against their own tenure can trigger it.

### Likelihood Explanation
Preconditions: normal tenure sequence; `MINER_REWARD_MATURITY` window elapsed; a `PoisonMicroblockOp` filed against the target tenure; the attacker's `burnchain_commit_burn` chosen small enough, relative to total burns among participants in that block, that `coinbase_reward * POISON_MICROBLOCK_COMMISSION_FRACTION / 100` truncates to 0. This is attacker-controlled (their own burn amount) and requires only minority/minimal BTC spend — the smaller the commit, the more certain the trigger, at the cost of a lower chance of winning the sortition. It is repeatable each time the attacker wins a sortition with a sufficiently small commit and arranges a poison report.

### Recommendation
Do not infer reward role (child vs. parent) from `coinbase > 0`. Add an explicit discriminant (e.g., a `role: ChildOrParent` enum field) to `MinerReward` set at construction time in `calculate_miner_reward`, and use that field in `is_child()`/`is_parent()`/`try_add_parent` instead of inferring it from `coinbase`/`tx_fees_streamed_produced`. Separately, guard `poison_microblock_commission` and the punished-coinbase path so a legitimately punished child record is never structurally identical to a parent record (e.g., always keep a marker/tag independent of the truncated numeric fields).

Rust integration test plan (extends existing tests in `stackslib/src/chainstate/stacks/db/accounts.rs`'s `#[cfg(test)] mod test`):
1. Construct a `MinerPaymentSchedule` for a miner `participant` whose `burnchain_commit_burn` is small relative to `other_burn_total` from injected user-burn-support entries, such that the computed `coinbase_reward = participant.coinbase * this_burn_total / burn_total` is less than `100 / POISON_MICROBLOCK_COMMISSION_FRACTION` (so the subsequent commission floors to 0).
2. Call `StacksChainState::calculate_miner_reward(..., poison_reporter_opt = Some(&reporter_addr))` directly, and assert `miner_reward.coinbase == 0`.
3. Assert on both sides of the invariant: `assert!(!miner_reward.is_child())` and `assert!(miner_reward.is_parent())` — proving the classification collapse.
4. Drive it through `insert_matured_child_miner_reward` in a `DBTx` and assert the call panics with `"FATAL: tried to insert a non-child reward as the child reward"` (use `std::panic::catch_unwind` to capture it without aborting the test process), demonstrating the deterministic crash path that every node hits when maturing this record.
5. As a secondary assertion path (bypassing the insert-time guard by writing directly via `inner_insert_matured_miner_reward`), populate two rows for the same `(parent_block_id, child_block_id)` pair where neither satisfies `is_child()`, then call `get_matured_miner_payment` and assert it panics with `"FATAL: got two parent rewards"`, confirming the divergence described in the question manifests one function earlier than originally hypothesized but with equivalent liveness impact.
