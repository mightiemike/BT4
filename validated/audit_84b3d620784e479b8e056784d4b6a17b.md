### Title
Timing side-channel in `localLoginFallback` allows user-enumeration of local admin accounts via `/sessions` login endpoint - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.localLoginFallback` (and the analogous `orm.CreateSession` path in `core/sessions/localauth/orm.go`) performs a database lookup for the submitted email and returns an error immediately if no row is found in the `users` table, only reaching `constantTimeEmailCompare` and the expensive `utils.CheckPasswordHash` (bcrypt) call when a matching row exists. This produces a measurable timing difference between "email exists" and "email does not exist" responses, independent of the constant-time email comparison itself.

### Finding Description
In `core/sessions/ldapauth/ldap.go`:
```go
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(...) { ... }
	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) { ... }
	...
}
``` [1](#0-0) 

If the SQL lookup returns `sql.ErrNoRows` (email not in the local `users` table), the function returns immediately — bcrypt (`utils.CheckPasswordHash`) is never invoked. If the email exists, execution proceeds to `constantTimeEmailCompare` (genuinely constant-time) and then to bcrypt password verification, which costs on the order of tens of milliseconds depending on the configured cost factor. This is reachable from `ldapAuthenticator.CreateSession`, which calls `localLoginFallback` whenever the LDAP bind and `FindUser` LDAP path fail [2](#0-1) , i.e., on every login attempt reaching the `/sessions` endpoint for any email not present upstream in LDAP.

The identical pattern also exists in the default local-auth provider:
```go
user, err := o.FindUser(ctx, sr.Email)
if err != nil {
    return "", err
}
...
if !constantTimeEmailCompare(...) { ... }
if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) { ... }
``` [3](#0-2) 

The `constantTimeEmailCompare` helper itself is correctly implemented using `subtle.ConstantTimeCompare` over a padded fixed-length buffer [4](#0-3) , so it does not leak information by itself. The actual leak is structural: the bcrypt hash check is skipped entirely for nonexistent emails, making the "user exists" branch measurably slower than the "user does not exist" branch, regardless of password correctness.

### Impact Explanation
An unprivileged remote attacker submitting repeated `CreateSession` requests to the `/sessions` login endpoint with different candidate emails and a fixed invalid password can statistically distinguish valid local admin/API-user emails from invalid ones by aggregate response latency (bcrypt cost vs. immediate DB-miss return). This enables enumeration of valid Chainlink node operator email/usernames, which can be used to focus subsequent credential-stuffing or brute-force attempts against `/sessions`, and to identify which named users have local (non-LDAP) accounts as opposed to LDAP-federated identities. This is an information-disclosure/enumeration issue, not by itself an authentication bypass, secret disclosure, or code-execution primitive — it does not directly cause fund loss, transaction tampering, or node compromise on its own.

### Likelihood Explanation
Exploitability requires only unauthenticated network access to the `/sessions` endpoint and the ability to send many repeated requests with different candidate emails and a constant invalid password, then apply statistical analysis (e.g., averaging over many samples to reduce network jitter noise). No credentials, LDAP configuration knowledge, or special privileges are needed. This is a relatively straightforward class of timing side-channel and does not depend on any test-only or mock code — it is present in the production authentication code path used by both local and LDAP-fallback logins.

### Recommendation
Perform a constant-cost password verification even when the queried email does not exist, e.g., always compute `utils.CheckPasswordHash` against a precomputed dummy/fake bcrypt hash when the DB lookup returns `sql.ErrNoRows`, before returning the "invalid email" error, so that the total latency of "email exists / wrong password" and "email does not exist" paths converge. Apply the same fix to `orm.CreateSession` in `core/sessions/localauth/orm.go`. Additionally consider adding a global rate limiter/backoff on the `/sessions` endpoint to further reduce the statistical feasibility of timing analysis.

### Proof of Concept
Integration/timing-fuzz test plan:
1. Seed the `users` table with one known local user (`known@example.com`) with a bcrypt-hashed password.
2. Repeatedly (N ≥ 500) call `ldapAuthenticator.CreateSession` (or `orm.CreateSession`) with:
   - Group A: `sr.Email = "known@example.com"`, `sr.Password = "definitely-wrong-password"`.
   - Group B: `sr.Email = "unknown-<random>@example.com"`, `sr.Password = "definitely-wrong-password"`.
3. Record wall-clock latency for each call (mock/stub the LDAP bind to always fail so the local fallback path is always exercised, isolating DB+bcrypt effects).
4. Compute mean/median latency and perform a statistical test (e.g., Mann-Whitney U or Welch's t-test) comparing Group A vs Group B distributions.
5. Assert: latencies for Group A (existing email) are statistically significantly higher than Group B (nonexistent email), demonstrating the timing oracle; after applying the dummy-hash-check fix, assert the two distributions become statistically indistinguishable (p-value above significance threshold).

	var user sessions.User

	err := l.ds.GetContext(ctx, &user, sql, sr.Email)

		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}

const constantTimeEmailLength = 256

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
