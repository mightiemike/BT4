**Analysis:**

The premise doesn't hold up. `MoveResource::resource_path()` is defined as:
```rust
fn resource_path() -> Vec<u8> {
    Self::struct_tag().access_vector()
}
``` [1](#0-0) 

For `UnlimitedSupplyResource`, `struct_tag()` is built entirely from compile-time constants inherited from `MoveStructType`: `ADDRESS` defaults to `CORE_CODE_ADDRESS` (`0x1`), and `MODULE_NAME`/`STRUCT_NAME` are hardcoded to `"collection"`/`"UnlimitedSupply"` with no `type_args()` override (defaults to empty). [2](#0-1) [3](#0-2) 

None of these fields — address, module, struct name, type args — are influenced by unprivileged transaction inputs such as object addresses or collection names. The specific object address that owns a given `UnlimitedSupply` resource instance is not part of the `StructTag`/`resource_path()` output at all; it is supplied as a separate parameter when constructing the actual `AccessPath`/`StateKey`, e.g. `StateKey::resource(address, struct_tag)` or `AccessPath { address, path }`. [4](#0-3) [5](#0-4) 

The path bytes themselves are produced by BCS-serializing `Path::Resource(struct_tag)`, the same enum/serialization the VM and storage layer use to construct `AccessPath`s for the same on-chain resource. [6](#0-5) [7](#0-6)  Since the struct tag encoding is fixed at compile time and identical to the Move-level type `0x1::collection::UnlimitedSupply`, there is no mechanism by which an unprivileged party — controlling only object addresses or Move-level collection names (which are stored as *data* inside the resource, not as part of its type) — can cause `resource_path()`'s bytes to diverge from the VM's actual `AccessPath` for the same logical resource. The "collection name" is data, not a type parameter, so it never touches `struct_tag()`/`access_vector()`.

Because address binding happens outside `resource_path()` and the type-tag encoding is deterministic and shared between Rust and Move-side computation, there is no path here for state-view reads to return a stale or unrelated value at a given version due to input-driven struct-tag divergence. This does not meet the state-integrity gate.
