### Title
Sierra-to-CASM compiler component blocks Tokio worker threads on synchronous subprocess calls, allowing declare-transaction flood to stall the whole component's async runtime - ([File: crates/apollo_compile_to_casm/src/communication.rs])

### Summary
The `SierraCompiler` component's request handler calls a fully synchronous, OS-process-spawning compile routine directly inside an `async fn`, without offloading it to a blocking-thread pool (`tokio::task::spawn_blocking`). Because `ConcurrentLocalComponentServer` dispatches each request via a plain `tokio::spawn` on the shared multi-threaded runtime, every in-flight `Compile` request occupies one Tokio worker thread for the *entire* duration of the external compiler subprocess (up to `max_cpu_time`, default 600s). This is the same underlying bug class as CVE-2022-36127 (SkyWalking NodeJS agent): a legitimate, attacker-reachable request path can synchronously block the async event loop while waiting on a slow external resource, exhausting the runtime and making the component (and anything relying on responsive processing from it) unavailable.

### Finding Description
`ComponentRequestHandler<SierraCompilerRequest, SierraCompilerResponse>::handle_request` is an `async fn` but its body is a direct, synchronous call: [4](#0-3) 

`SierraCompiler::compile` itself performs no async yielding — it shells out to the Cairo compiler binary and blocks on the whole subprocess lifetime: [5](#0-4) [2](#0-1) 

`ConcurrentLocalComponentServer::process_requests` runs each request's `process_request(...)` call inside a bare `tokio::spawn`, gated only by a semaphore permit count (`max_concurrency`), with no dedicated blocking-thread offload: [6](#0-5) 

A synchronous, CPU-bound-but-blocking call (`Command::output()`) executed inside a task spawned on Tokio's default multi-threaded scheduler occupies one of the scheduler's core worker threads for the full duration of the external process. If the number of concurrently in-flight compile requests approaches or exceeds the number of Tokio worker threads configured for the process (commonly equal to CPU core count), all worker threads become synchronously blocked, and the async runtime cannot schedule *any* other task on that thread pool — including unrelated requests handled by the same process (if co-located) and the completion/response-dispatch path for other in-flight `Compile` requests. The `max_cpu_time` resource limit (default 600 seconds per compile) bounds *when* a stuck compiler process is killed but does nothing to prevent the thread-pinning itself while it runs; a burst of declare transactions with large/complex-but-valid Sierra classes that each take tens of seconds to compile is sufficient to occupy every worker thread simultaneously, independent of any bug or hang in the compiler binary.

The gateway path that reaches this is directly attacker-controlled: any declare transaction submitted via `add_tx` triggers `ClassManager::add_class` → `self.compiler.compile(class.clone()).await`, which in turn dispatches to this component with no request-level timeout on the caller's side either: [7](#0-6) [8](#0-7) 

The gateway does throttle concurrent declare compilations to `max_concurrent_declare_compilations` (default 40) per gateway instance, and that permit is held for the duration of compilation, but this only bounds concurrency from a single gateway's perspective — it does not prevent the SierraCompiler component's own Tokio runtime from being saturated if the compiler's worker-thread count is smaller than the number of concurrently permitted compilations (or if multiple gateway instances / P2P-relayed declares from other sequencers funnel into the same compiler fleet instance).

Notably, this codebase elsewhere explicitly recognizes and defends against exactly this hazard for a *different* blocking path — `ClassReader::block_on_request`, used when a state reader blocks on the class manager, has an explicit `deadline` mechanism with extensive comments about "a stalled class manager... pinning that thread forever" [9](#0-8)  and is covered by dedicated regression tests [10](#0-9) . No equivalent protection (spawn_blocking isolation, dedicated blocking-thread pool, or bounded worker allocation) exists for the Sierra-to-CASM compile path itself.

### Impact Explanation
If enough concurrent declare transactions with slow-to-compile (but valid, non-malicious) Sierra classes are submitted — well within the `max_concurrent_declare_compilations` allowance and far under the 600-second CPU limit — every Tokio worker thread serving the SierraCompiler component can become synchronously blocked on `Command::output()` simultaneously. This freezes the compiler component's ability to service *any* request, including compile requests from other sequencers relayed over P2P declare propagation, causing declare-transaction processing to stall network-wide until the subprocesses complete. Depending on deployment topology (monolithic vs. distributed components), this can also starve other async work sharing the same runtime. This matches the report's "service unavailable due to unhealthy connection with no isolation" bug class, resulting in the network being temporarily unable to confirm new (declare) transactions — a covered impact category (network unable to confirm new transactions).

### Likelihood Explanation
Reachable by any unprivileged account submitting ordinary declare transactions — no special privileges are required, and the classes used to trigger long compile times need not be malicious, only sufficiently large/complex (which is itself bounded loosely by `max_bytecode_size`, not by compile-time). Reproducing requires only submitting several declare transactions concurrently, which is straightforward for any external sender and does not depend on any operator misconfiguration, network partition, or malicious peer.

### Recommendation
Move the synchronous subprocess invocation (`compile_with_args` / `Command::output()`) inside `tokio::task::spawn_blocking` so it runs on Tokio's dedicated blocking-thread pool instead of the async worker-thread pool, mirroring the isolation pattern already used and documented for `ClassReader::block_on_request`. Additionally, consider bounding the SierraCompiler component's own concurrency (e.g., a semaphore sized to the blocking-pool budget) independent of any per-gateway-instance limit, since multiple gateways/relayed declares can all target the same compiler fleet concurrently.

### Proof of Concept
1. Deploy a `SierraCompiler` component with the default Tokio worker-thread count `N` (e.g., number of CPU cores).
2. From one or more accounts, submit `N` (or more) declare transactions concurrently, each containing a valid but compilation-heavy Sierra class (e.g., large but within `max_bytecode_size`, causing tens of seconds of CPU-bound compilation in the `cairo-lang` compiler binary).
3. Observe that all `N` Tokio worker threads become synchronously blocked inside `Command::output()` for the duration of each compile, and that no further `Compile` requests (from this or other declares, including P2P-relayed ones) can be scheduled or responded to until at least one compile finishes — demonstrating a full stall of the SierraCompiler component's async runtime purely from legitimate transaction load.
