### Title
Poison-microblock reward can be stolen via front-running/copy-report of identical `(h1,h2)` evidence - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`handle_poison_microblock` determines which reporter earns the `poison_microblock_commission` purely by comparing `sequence` numbers of the submitted microblock header pair, and only replaces a stored report if the new sequence is *strictly lower* than the one already on record. It performs no check that the sender is the transaction that *originally discovered* the equivocating headers, so any unprivileged party who observes another user's pending `PoisonMicroblock(h1,h2)` transaction in the mempool can copy the exact same header pair into their own transaction, pay a higher fee to be ordered first in the block, and claim the commission for themselves.

### Finding Description
The broken equality is: *reward paid == reward paid to the first (honest) discoverer of a given equivocation at a given sequence*. This holds only if either (a) reports for equal sequences are attributed to whichever reporter discovered the evidence first, or (b) the evidence itself is bound to the discoverer via a signature/commitment that cannot be copied by a third party.

Neither holds in the current logic. `StacksChainState::get_poison_microblock_report`/`insert_microblock_poison` records only `(StacksAddress, sequence)` per block height, and the acceptance rule in `handle_poison_microblock` is:
- If no report exists yet for that height, whoever's transaction is processed first (regardless of sender) is recorded as the reporter for that `seq`.
- If a report already exists, a new submission only overwrites it when the new `seq` is *strictly less than* the stored `seq` — an equal-sequence resubmission from a different sender is silently ignored, leaving whichever sender was processed first as the credited reporter.

Because the evidence (`mblock_header_1`, `mblock_header_2`) is just two signed microblock headers produced by the *miner*, not by the reporter, there is nothing cryptographically tying the report to the discoverer. A `PoisonMicroblock` transaction's `sender_principal` is simply whoever pays the fee and broadcasts it — the discoverer's identity is not embedded in the evidence itself. This is visible in `StacksChainState::calculate_miner_reward` in `stackslib/src/chainstate/stacks/db/accounts.rs`, where the `poison_reporter_opt` address recorded by `get_poison_microblock_report`/`insert_microblock_poison` is the sole determinant of who receives `poison_microblock_commission(coinbase_reward)` [1](#0-0) , and `poison_microblock_commission` computes a fixed fraction of the coinbase [2](#0-1) .

Exploit flow:
1. Honest reporter A observes microblock fork evidence `(h1, h2)` at sequence `seq`, builds and broadcasts `PoisonMicroblock(h1, h2)` signed by A, and it enters the mempool.
2. Attacker B, an unprivileged network participant, observes A's pending transaction, extracts the plaintext `(h1, h2)` header pair (no secret is needed — these are public microblock headers), and constructs an identical-content `PoisonMicroblock(h1, h2)` transaction signed by B's own key, with a higher fee.
3. The miner assembling the block orders transactions by fee, so B's transaction is processed before A's within the same block (or in an earlier block/tenure).
4. When B's transaction executes first, `get_poison_microblock_report` returns `None` for that height, so B's `(seq)` is inserted via `insert_microblock_poison`.
5. When A's transaction executes afterward, the report already exists with the same `seq`; since A's `seq` is not *strictly lower* than the stored `seq`, the existing (B's) record is retained.
6. At reward maturation, `calculate_miner_reward` pays the `poison_microblock_commission` to B instead of A, even though A was the actual, original discoverer of the equivocation.

Existing guards do not intervene: `check_tenure_tx`, `verify_signer_signatures`, `validate_vrf_seed`, and MARF-hashing operate on block/tenure validity and sortition, none of which have any bearing on `PoisonMicroblock` transaction sender attribution or evidence-origin tracking.

### Impact Explanation
This causes a reward mis-payment bounded to the poison-microblock commission fraction (`POISON_MICROBLOCK_COMMISSION_FRACTION = 5`, i.e., 5% of a coinbase reward) being paid to a copy-reporter B instead of the original discoverer A. This matches the "High" severity category defined by the rules ("a poison or reward mis-payment bounded to fees"). Funds affected are limited to the coinbase commission share; the miner and broader chain state are unaffected, and there is no chain split or double-spend. The attack is repeatable for every poison-microblock report opportunity where evidence becomes visible in the mempool before being mined.

### Likelihood Explanation
The attacker needs only: (1) the ability to observe pending transactions in the mempool (any node/full network participant can do this), (2) the ability to construct and sign an ordinary transaction (no special privilege, key, or stake), and (3) enough STX to pay a marginally higher fee than the original reporter to win block-ordering priority. No majority stake, no signer key, and no miner slot are required — it is achievable by a purely unprivileged actor. This makes the attack highly feasible and repeatable whenever a poison-microblock opportunity exists and the honest reporter's transaction is visible before confirmation.

### Recommendation
Bind the poison-microblock report to the actual discoverer rather than to fee-based transaction ordering. Options include: requiring the reporting transaction to include a discoverer-specific commitment (e.g., a signature over the reporter's principal combined with the header hashes, submitted ahead of time or via a reveal scheme), or changing the tie-breaking rule so that for equal `seq`, the *earliest known* report (e.g., by original broadcast time recorded off-chain, or by strict precedence rules that can't be gamed by fee-based reordering) wins, and rejecting a resubmission of byte-identical `(h1,h2)` evidence from a different sender than the one who first got it recorded on-chain.

### Proof of Concept
Rust integration test plan (two-transaction-in-one-block harness):
1. Create equivocating microblocks `h1`, `h2` at a fixed `sequence` for a test tenure.
2. Construct `tx_a = PoisonMicroblock(h1, h2)` signed by principal A with fee `F`.
3. Construct `tx_b = PoisonMicroblock(h1, h2)` (identical headers) signed by principal B with fee `F + 1`.
4. Mine a block including both `tx_b` and `tx_a`, with `tx_b` ordered before `tx_a` due to higher fee.
5. Assert: `StacksChainState::get_poison_microblock_report(clarity_tx, height) == Some((B_address, seq))`, not `Some((A_address, seq))`.
6. Progress chain to reward maturity and assert the matured `MinerReward` recipient for the poison commission is `B`, not `A`, confirming the reward-theft equality is broken (`reward_recipient == B != A == original_discoverer`).
