## Finding

### Title
Replay-verify tooling accepts divergent state/hot-state/position-state checkpoint roots as a valid replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness gate used by the archive replay-verify tool (`storage/db-tool/src/replay_on_archive.rs`) and other debugging/replay tools to confirm that locally re-executed transactions match the authenticated `TransactionInfo` recovered from backup. This function checks status, gas, write-set hash and event-root hash, but explicitly skips verification of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that authenticate the Sparse-Merkle/"trading-native" state root. As a result, a locally computed state root that diverges from the archived, ledger-info-anchored root is never detected by `verify()`, and the tool reports success.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and it deliberately omits comparison of the checkpoint-hash fields, with an explicit TODO acknowledging the gap: [2](#0-1) 

These checkpoint hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are precisely the fields that bind a `TransactionInfo` to the resulting global state root — they are computed in `assemble_transaction_infos` and folded into `TransactionInfo::builder_v0`/`builder_v1`, which is subsequently hashed and inserted into the transaction accumulator: [3](#0-2) . That accumulator leaf hash is what a `LedgerInfo` ultimately commits to and what all downstream proofs (`TransactionAccumulatorProof`, `TransactionInfoListWithProof`) are verified against, e.g. [4](#0-3) .

The replay-verify tool `storage/db-tool/src/replay_on_archive.rs` re-executes transactions from backup and calls exactly this incomplete comparator to decide pass/fail: [5](#0-4) . Because `ensure_match_transaction_info` never compares `state_checkpoint_hash` (or the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) against the archived `TransactionInfo`, any divergence purely in the resulting state root — caused by a Move VM bug, a JMT/hot-state construction bug, or a hard-fork-only state-computation change — is invisible to this tool. Write-set bytes and events can match exactly while the actual state tree that the write-set is applied against (and its resulting root) silently diverges, and the tool still reports the chunk as verified.

### Impact Explanation
This breaks the state-commitment integrity invariant "committed state that differs from the correct VM result...must be caught during replay/restore verification." The replay-verify tool is the primary safety mechanism operators and Aptos Labs use to confirm that a candidate execution/storage change does not silently alter historical state roots before it reaches mainnet. A state-root divergence bug (in JMT construction, hot-state promotion, or VM state application) that preserves write-set/event equality but corrupts the derived state root would pass replay-verify undetected, and could be deployed to mainnet, producing an undetected chain split or unauthenticated resource content served from state-sync/API for the affected version range. This is a high-severity gap in the proof/replay verification pivot explicitly called out in the review scope ("Hard-fork-only divergence during commit, replay, restore, or proof verification").

### Likelihood Explanation
The gap is unconditionally present in shipped code (not gated behind an experimental flag) and is triggered any time `replay_on_archive` (or other callers such as `aptos-debugger`/`aptos-move/cli`) is used to validate replayed transactions — this is standard practice for validating storage/executor changes before release. The bug requires an underlying state-root-producing defect elsewhere to have practical effect, but the check that should catch such a defect is provably absent by this comparator's own code and its own TODO comment acknowledging the exact failure mode.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present, based on feature flags) between the locally computed `TransactionInfo` and the expected one, failing the check on any mismatch, so replay-verify and other consumers of this comparator actually authenticate the resulting global/hot/trading-native state roots rather than accepting a partial match.

### Proof of Concept
1. In `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, re-execute a chunk of backed-up transactions whose write-set bytes and events happen to match the archived `TransactionInfo`, but where the executor's derived state-checkpoint hash (e.g., due to a JMT/hot-state bug) diverges from the archived `state_checkpoint_hash`.
2. `ensure_match_transaction_info` is invoked at [6](#0-5)  and returns `Ok(())` because it never reads `txn_info.state_checkpoint_hash()` / hot/position variants — see the omission at [7](#0-6) .
3. `verify()` in `replay_on_archive.rs` therefore reports zero failed transactions even though the resulting state root for that version diverges from the one anchored in the mainnet `LedgerInfo`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
