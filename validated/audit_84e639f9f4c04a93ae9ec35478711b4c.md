### Title
Unbounded Duplicate Session-ID Accumulation in KV Session Storage's Shop Index - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
The `@shopify/shopify-app-session-storage-kv` adapter maintains a per-shop array of session IDs (`shop:<shop>` key) used by `findSessionsByShop()`. Unlike the Redis adapter's equivalent function, the KV adapter's `addShopIds()` helper appends a session ID to this array on every `storeSession()` call without checking whether the ID is already present, allowing the same ID to be added repeatedly and the tracking array to grow without bound.

### Finding Description
`storeSession()` writes the session record and then unconditionally calls `addShopIds(session.shop, [session.id])`: [1](#0-0) 

`addShopIds()` simply concatenates the new id onto the existing array and writes it back, with no de-duplication check: [2](#0-1) 

This is the same bug class as the reported `whitelistAmm()` issue: an entry can be inserted multiple times into a list that is later iterated/aggregated, because the insertion path lacks an "already exists" guard. The library's own Redis adapter demonstrates the correct pattern is known and expected — `addKeyToShopList()` explicitly checks `if (!idKeysArray.includes(idKey))` before pushing: [3](#0-2) 

whereas the KV adapter omits this check, making it the outlier among the session-storage backends.

Because offline session IDs are deterministically derived from the shop domain (not random per install), any repeated `storeSession()` call for the same shop's offline session — which happens on every OAuth token exchange, re-authorization, or scope-update flow — re-adds the identical ID to the shop's KV list. `removeShopIds()` only strips duplicates when `deleteSession()`/uninstall runs, so between installs/re-auths the list can accumulate arbitrarily many duplicate entries: [4](#0-3) [5](#0-4) 

`findSessionsByShop()` then performs one KV `get` per entry in that list, including all duplicates, and returns duplicate `Session` objects to the caller: [6](#0-5) 

### Impact Explanation
`findSessionsByShop()` is a primary building block apps use in auth-adjacent flows (e.g., locating all sessions for a shop during uninstall/GDPR shop-redact webhook handling, or bulk offline+online session cleanup). If the shop-id list contains many duplicate entries:
- The read amplifies into N KV `get` calls for what should be 1 distinct session, degrading/DoS-ing the session-storage layer and any auth handler that depends on it (webhook processing, uninstall cleanup) as the list grows unbounded over the app's lifetime.
- Consumers that assume `findSessionsByShop()` returns one entry per distinct session (a very common integration assumption) will process/act on the same session multiple times, which is exactly the double-counting failure mode described in the report (there, `unrealizedPnl`; here, duplicate session processing/deletion calls).

This is not a full account-takeover, but it is a genuine defect in an auth-infrastructure component (session storage) that a legitimate merchant's normal usage pattern (repeated authorization) can trigger, with a resource-growth/DoS impact on the storage layer used by auth handlers.

### Likelihood Explanation
High for occurrence, since `storeSession()` is called on every offline-token OAuth completion, and offline session IDs are deterministic per shop — no attacker trickery is needed, just normal repeated re-installs/re-auth or scope updates by the merchant, over time growing the array unboundedly. Exploiting it maliciously would require a merchant (or someone able to trigger many token exchanges for the shop) to intentionally cause repeated OAuth completions, which is plausible for an unprivileged single-tenant actor causing self-inflicted or app-wide storage degradation.

### Recommendation
Mirror the Redis adapter's fix in the KV adapter: check `idKeysArray`/`shopIds` for existing membership before pushing in `addShopIds()`:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Configure an app to use `KVSessionStorage`.
2. Complete OAuth for a shop, producing offline session `id = offline_<shop>`; `storeSession()` runs, `addShopIds` sets `shop:<shop> = ["offline_<shop>"]`.
3. Trigger a second OAuth/token-exchange cycle for the same shop (e.g., merchant re-installs the app, or app requests additional scopes causing re-auth) without first deleting the prior session. `storeSession()` runs again with the same deterministic id; `addShopIds` appends it again: `shop:<shop> = ["offline_<shop>", "offline_<shop>"]`.
4. Repeat N times — the array grows to N duplicate entries.
5. Call `findSessionsByShop(shop)`; observe N KV `get` calls and N duplicate `Session` objects returned instead of 1, confirming both the amplification and the double-counting effect.

      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
