### Title
Unbounded `data`/`input` size in JSON-RPC `eth_call`/`eth_estimateGas` enables memory/CPU exhaustion - (File: framework/src/main/java/org/tron/core/services/jsonrpc/types/BuildArguments.java)

### Summary
`BuildArguments.resolveData()` validates the `input`/`data` hex strings only for format (prefix, parity) via `requireValidHex`, with no maximum length check, before the value is converted with `ByteArray.fromHexString` and fed into `Wallet.triggerConstantContract` / `Wallet.estimateEnergy`. An unauthenticated client can submit an `eth_call`/`eth_estimateGas` request with a multi-megabyte `data`/`input` field, forcing the node to allocate large byte arrays and run VM interpretation work per request, unlike other JSON-RPC inputs in the same codebase that do enforce explicit length caps.

### Finding Description
`resolveData()` calls `requireValidHex("input", input, HexMode.STRICT)` and `requireValidHex("data", data, HexMode.LENIENT)` [1](#0-0) . `requireValidHex` only checks the `0x` prefix / even length (STRICT mode) and then attempts `ByteArray.fromHexString(value)` to confirm it parses — it never bounds `value.length()` [2](#0-1) . This is in contrast to other inputs in the same file that explicitly cap length before expensive parsing, e.g. `MAX_BLOCK_NUM_HEX_LEN`/`parseBlockNumber` and `MAX_STORAGE_KEY_HEX_LEN` guards documented as "API-level DoS guard" [3](#0-2) [4](#0-3) .

In `TronJsonRpcImpl.estimateGas`, the resolved data string is passed straight to `ByteArray.fromHexString(args.resolveData())` and then to `estimateEnergy(...)` or `callTriggerConstantContract(...)`, which build a `TriggerSmartContract` and invoke `wallet.estimateEnergy` / `wallet.triggerConstantContract` [5](#0-4) . These are constant/local calls (not broadcast transactions), so they bypass any broadcast-time transaction-size validation that normally protects the chain from oversized transactions. The only bound eventually hit is whatever internal max-transaction/contract-data-size check exists deep inside `Wallet`/VM (not confirmed in the reachable code reviewed), but the hex string is fully decoded into a byte array in memory before any such check can occur, and the JSON-RPC layer itself performs no early rejection.

### Impact Explanation
Each request forces allocation of the full decoded byte array (roughly half the hex string length) plus JSON parsing/string overhead for the original hex payload, and then queues that payload for constant-contract execution/energy estimation. Sending many concurrent requests with several-MB `data` fields can drive heap pressure and CPU consumption (JSON deserialization, hex decoding, `TransactionCapsule` construction, VM invocation) disproportionately to the cost imposed on the attacker, degrading service for other JSON-RPC clients on the same node.

### Likelihood Explanation
`eth_call`/`eth_estimateGas` are public, unauthenticated JSON-RPC methods enabled by default on full nodes with JSON-RPC turned on. No signature, fee, or size-limiting check is applied before the payload reaches `ByteArray.fromHexString` and the wallet execution path, so the attack is straightforward to script and repeat concurrently.

### Recommendation
Add an explicit maximum length check for `data`/`input` in `requireValidHex` or in `BuildArguments.resolveData()` before calling `ByteArray.fromHexString`, mirroring the pattern already used for `MAX_STORAGE_KEY_HEX_LEN` / `MAX_BLOCK_NUM_HEX_LEN` (e.g., cap at the node's configured max contract/transaction data size), and reject oversized payloads early with a `JsonRpcInvalidParamsException`.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/services/jsonrpc/types/BuildArgumentsDoSTest.java
@Test
public void resolveData_rejectsOversizedPayload() {
  BuildArguments args = new BuildArguments();
  // 10 MB of hex chars => 5 MB decoded payload
  StringBuilder sb = new StringBuilder("0x");
  for (int i = 0; i < 10_000_000; i++) {
    sb.append('a');
  }
  args.setData(sb.toString());

  long before = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();
  long start = System.nanoTime();

  // Expected (fix): should throw JsonRpcInvalidParamsException for oversized data
  // Actual (bug): resolveData() succeeds and returns the huge hex string
  Assertions.assertThrows(JsonRpcInvalidParamsException.class, args::resolveData);

  long after = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();
  long elapsed = System.nanoTime() - start;
  // Assert bounded latency/memory growth as a regression guard once fixed
  Assertions.assertTrue(after - before < 1_000_000, "unexpected large heap growth");
}
```
Run with increasing payload sizes (1 MB, 10 MB, 50 MB) and assert request latency/memory grows without bound today (proving the missing cap), then re-run after adding a length guard to confirm early rejection.

```java
  public static void requireValidHex(String fieldName, String value, HexMode mode)
      throws JsonRpcInvalidParamsException {
    if (value == null) {
      return;
    }
    if (mode == HexMode.STRICT) {
      if (value.isEmpty()) {
        return;
      }
      if (!value.startsWith("0x") || value.length() % 2 != 0) {
        throw new JsonRpcInvalidParamsException(
            "invalid hex string for \"" + fieldName + "\"");
      }
    }
    try {
      ByteArray.fromHexString(value);
    } catch (Exception e) {
      throw new JsonRpcInvalidParamsException(
          "invalid hex string for \"" + fieldName + "\"");
    }
  }
```
