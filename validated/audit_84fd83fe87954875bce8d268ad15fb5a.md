### Title
PoX-4 signer-set computation can floor every signer's weight to zero, dropping the entire signer set and stalling block production - (File: stackslib/src/chainstate/stacks/boot/mod.rs)

### Summary
`StacksChainState::make_signer_set` (still used by the PoX-4 path via `pox_4_compute_and_update_signers`) computes each signer's weight as `stacked_amt / threshold` with plain floor division, and drops any signer whose weight floors to `0`. [1](#0-0)  This is the identical "rather harsh requirement" bug class as the audit report: an amount can legitimately be non-trivial yet still be `< threshold`, and get truncated to zero and excluded entirely, rather than being handled proportionally (as the newer PoX-5 largest-remainder method now does). [2](#0-1) 

### Finding Description
The equality that this breaks is: "the reward-cycle signer set computed independently by every node from on-chain PoX-4 stacking state must be non-empty and represent the actual staked STX distribution used to validate block signatures." `make_signer_set` allocates weight via `u32::try_from(stacked_amt / threshold)`, filtering out any entry whose integer-divided weight is `0`. [3](#0-2)  This function is called from `pox_4_compute_and_update_signers`, which stores the resulting reward set into the `.signers` contract and is subsequently used by the Nakamoto coordinator to validate block-commits and block signatures. [4](#0-3) 

The codebase's own regression test on the successor (`pox_5_make_signer_set`) explicitly documents this exact failure mode for the old scheme: "The old floor-and-drop scheme set threshold = ceil(N*S / R) > S, so every signer's weight floored to 0 and the entire set was dropped -- stalling the chain." [5](#0-4)  This proves the bug class is real and reachable in this codebase — it was fixed for PoX-5's `pox_5_make_signer_set` with a largest-remainder ("Hare") apportionment method that guarantees every stacker whose base weight is nonzero keeps their slot and leftover slots are handed out so the set is never emptied by degenerate equal-stake distributions. [6](#0-5)  However, `StacksChainState::make_signer_set` (the PoX-4 code path) was not given the equivalent fix and retains the original floor-and-drop logic. [7](#0-6) 

Any node computing the PoX-4 reward set independently from on-chain stacking data will deterministically reproduce the same (potentially empty) filtered set — so this is not a split between honest nodes, but it is a minority-triggerable state (a set of many roughly-equal-stake, sub-threshold stackers) that can zero out the entire signer set for a reward cycle, exactly mirroring the WBTC/EURS "too harsh a requirement" scenario from the external report, generalized from token amounts to STX stacking weight.

### Impact Explanation
If enough distinct stackers hold stake below `threshold` such that all floor to weight `0` (e.g., many participants each stacking just under the per-slot minimum, which is influenced by `reward_slots` and total liquid STX and is not something any single participant fully controls but can be engineered by a coordinated minority of stackers choosing amounts near the threshold), `check_and_handle_prepare_phase_start` -> `pox_4_compute_and_update_signers` can update `.signers` with an empty or severely truncated signer set for that reward cycle. Because the Nakamoto coordinator validates block signatures against exactly this signer set and required-weight threshold, an empty/degenerate signer set halts valid block production for that cycle across the whole network — a chain-liveness stall reachable without requiring a majority attacker, consistent with the report's rated impact ("system becomes inapplicable"/unusable for the affected configuration). This matches the Critical/High class described in the rules (temporary tip disagreement / stall via a reproducible, minority-triggerable computation divergence from expected behavior), though it manifests as a liveness failure rather than a state-root mismatch since all honest nodes compute the same (broken) result deterministically.

### Likelihood Explanation
Reaching this condition requires only that a set of PoX-4 stackers (not a majority of network hash power or stake) collectively stack amounts that are individually below the computed `threshold` for that cycle — the PoX-4 reward-cycle threshold is derived from `get_reward_threshold_and_participation`, and adversarial/organic clustering of stacked amounts near or under it is plausible, especially with many small stackers, mirroring how WBTC/EURS holders naturally fell short of the harsh per-token requirement in the original report. This is a pre-existing, unfixed code path (PoX-4) sitting alongside a codebase-documented fix for the identical bug in PoX-5, which strongly indicates the maintainers recognize the vulnerability class as real and exploitable when triggerable.

### Recommendation
Apply the same largest-remainder ("Hare") apportionment method used in `pox_5_make_signer_set` to `StacksChainState::make_signer_set`/`make_reward_set` for the PoX-4 path: compute `threshold = max(1, total_stacked.div_ceil(reward_slots))`, assign `weight = stacked_amt / threshold` as a base allocation, then distribute any leftover slots (`reward_slots - sum(base_weights)`) to stackers in descending order of remainder (`stacked_amt % threshold`), with a deterministic tie-break (e.g., by signing key), ensuring the signer set is never spuriously emptied by floor-division truncation.

### Proof of Concept
1. Configure a PoX-4 reward cycle with `reward_slots = R` and a total liquid-STX-derived `threshold = T`.
2. Have `N > R` distinct stackers each stack an amount `< T` but collectively summing to more than `R * T` is not required — simply have every individual stacked amount `< T` (e.g., all stackers stack `T - 1`).
3. Call `StacksChainState::make_reward_set` / `make_signer_set` with these entries; observe `slots_taken = stacked_amt / threshold == 0` for every entry, exactly as demonstrated by the existing unit test pattern in `signers_tests.rs`'s `make_signer_units`, which relies on `stacked_amt / threshold` flooring per-entry weight to zero for sub-threshold stacked amounts. [8](#0-7) 
4. The resulting `signer_set` is `None`/empty, `pox_4_compute_and_update_signers` writes an effectively unusable `.signers` state for the cycle, and the Nakamoto coordinator can no longer validate/accept new blocks signed by a valid quorum for that cycle, exactly as the maintainers' own comment states was possible before the PoX-5 fix. [9](#0-8)

    pub fn make_signer_set(
        threshold: u128,
        entries: &[RawRewardSetEntry],
    ) -> Option<Vec<NakamotoSignerEntry>> {
        let Some(first_entry) = entries.first() else {
            // entries is empty: there's no signer set
            return None;
        };
        // signing keys must be all-or-nothing in the reward set
        let expects_signing_keys = first_entry.signer.is_some();
        for entry in entries.iter() {
            if entry.signer.is_some() != expects_signing_keys {
                panic!("FATAL: stacking-set contains mismatched entries with and without signing keys.");
            }
        }
        if !expects_signing_keys {
            return None;
        }

        let mut signer_set = BTreeMap::new();
        for entry in entries.iter() {
            let signing_key = entry
                .signer
                .expect("BUG: signing keys should all be set in reward-sets with any signing keys");
            if let Some(existing_entry) = signer_set.get_mut(&signing_key) {
                *existing_entry += entry.amount_stacked;
            } else {
                signer_set.insert(signing_key, entry.amount_stacked);
            };
        }

        let mut signer_set: Vec<_> = signer_set
            .into_iter()
            .filter_map(|(signing_key, stacked_amt)| {
                let weight = u32::try_from(stacked_amt / threshold)
                    .expect("CORRUPTION: Stacker claimed > u32::max() reward slots");
                if weight == 0 {
                    return None;
                }
                Some(NakamotoSignerEntry {
                    signing_key,
                    stacked_amt,
                    weight,
                })
            })
            .collect();

        // finally, we must sort the signer set: the signer participation bit vector depends
        //  on a consensus-critical ordering of the signer set.
        signer_set.sort_by_key(|entry| entry.signing_key);

        Some(signer_set)
    }

        // Allocate `reward_slots` weight across signers in proportion to stake using the
        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
