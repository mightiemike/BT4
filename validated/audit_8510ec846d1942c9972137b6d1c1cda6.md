### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify tooling to accept a corrupted state/hot-state/position-state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by chunk-executor and replay/db-tool paths to confirm that a re-executed `TransactionOutput` matches the authenticated `TransactionInfo` stored in the ledger/accumulator. It validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are the authenticated Merkle roots of the actual account/global state.

### Finding Description [1](#0-0) 

The function checks:
- transaction status vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- `write_set` hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

But the code contains an explicit acknowledgment that checkpoint hashes are skipped:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```
`state_checkpoint_hash` is the Sparse-Merkle-Tree root summarizing the full world state at a checkpoint boundary [2](#0-1) , and `TransactionInfoV1` additionally carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` [3](#0-2) . These are the same hashes that back state proofs consumed by clients and restore tooling (e.g. `ensure_state_checkpoint_hash` in the state-snapshot restore path [4](#0-3) ).

`ensure_match_transaction_info` is called by `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs` — i.e., it is the shared "does re-execution match the ledger" gate for chunk-sync/replay verification tooling. Because it omits the checkpoint-hash comparison, replay/verify flows that rely on it can report success even when locally-recomputed state roots diverge from the authenticated `TransactionInfo` root that is bound (via the accumulator) to a signed `LedgerInfo`.

I was not able to fully trace, within the remaining tool budget, whether the primary block-commit path (executor → storage write, not the replay/chunk-verify path) independently recomputes and compares `state_checkpoint_hash` before persisting — the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag references in `storage/aptosdb/src/db/aptosdb_writer.rs` and `storage/aptosdb/src/db/aptosdb_reader.rs` suggest this state-root computation is currently gated/experimental ("trading-native"), and the comment implies the gap is a known pre-condition that must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." This suggests the gap is intentionally called out as unresolved rather than already mitigated elsewhere, but I could not verify with certainty whether an independent checkpoint-hash check exists in the live consensus-driven commit path (as opposed to only chunk-sync/replay-verify/debugger tooling).

### Impact Explanation
If this comparator is the only integrity check performed by chunk-sync replay and replay-verify tooling before accepting re-executed data as consistent with an already-certified `TransactionInfo`, a divergence between local state computation and the authenticated ledger state (e.g., due to a bug in state-checkpoint-hash computation for the new "trading-native"/position-state components) would not be caught by these tools, and corrupted/incorrect state roots could be silently accepted as valid during replay, chunk-sync catch-up, or archival verification — a direct proof-integrity and state-commitment gap as defined by the Required Impacts (hard-fork-only divergence during commit/replay, or wrong proof/root accepted as valid).

### Likelihood Explanation
Low-to-moderate under normal conditions, because `state_change_hash` (write-set hash) is still checked, which catches most divergences in ordinary execution. The gap specifically matters for the newer `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` fields tied to the not-yet-fully-enabled trading-native/hot-state features; the comment itself flags this as a pre-requisite to close before that feature is turned on, implying the authors are aware the check is currently insufficient for those code paths.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) against the locally recomputed state roots before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, so replay-verify and chunk-executor tooling cannot report success on a checkpoint-hash mismatch.

### Proof of Concept
Not independently reproducible from static analysis alone — the finding is a documented, explicit code-level gap (`types/src/transaction/mod.rs:2197-2203`) rather than a demonstrated exploit; exploitation would require the "trading-native" hot-state/position-state checkpoint computation to actually diverge from ledger-committed values, which I could not trigger or confirm via the available read-only tools.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
