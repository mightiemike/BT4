## Title
`TransactionOutput::ensure_match_transaction_info` silently skips state-checkpoint root verification, letting replay/restore tooling accept a diverged ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by replay/verify tooling to confirm that a freshly re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain (i.e., proven against a `LedgerInfo`/accumulator root). Similar to the `GuardCM.checkTransaction()` bug pattern — a guard function that is supposed to fully validate an operation but has one silently-excluded branch — this function validates status, gas, write-set hash, and event-root hash, but explicitly omits comparing `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, the very fields that commit to the world-state root. The gap is acknowledged in-code but left unfixed.

### Finding Description
`ensure_match_transaction_info` checks four things against the authenticated `txn_info`: execution status, gas used, write-set hash (`state_change_hash`), and event root hash. It never checks `txn_info.state_checkpoint_hash()` (or the V1 `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against anything derived from the locally computed state. The comment directly above the `Ok(())` return documents this: [1](#0-0) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. ...
```

This function is the sole correctness gate used by two production verification tools:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` to decide pass/fail for each transaction. [2](#0-1) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`'s `print_mismatches`, used by the `aptos-debugger`/CLI replay path to flag execution divergence. [3](#0-2) 

Because `txn_info` here comes from the authenticated backup/archive (proven, at some point, against a `LedgerInfoWithSignatures`), `txn_info.state_checkpoint_hash()` is the ground-truth committed state root. If the locally re-executed state diverges from that (e.g., due to non-determinism, a state-checkpoint/Merkle-hash computation bug, or corrupted/stale state passed into the executor), the write-set hash and event hash can still match while the actual world-state root differs — `ensure_match_transaction_info` will not detect it, and the tool reports the replay/restore as successful.

This contrasts with the normal block-commit path, `DoStateCheckpoint::get_state_checkpoint_hashes`, which *does* assert the computed checkpoint hash matches known values: [4](#0-3) 

So the gap is specific to the replay-verify/debugger comparator, not the live consensus/execution commit path.

### Impact Explanation
Replay-verify tooling (`db-tool replay-on-archive`) exists specifically to detect state-commitment divergence between historical execution and the authenticated ledger — this is precisely the "hard-fork-only divergence during commit, replay, restore" class the task calls out. With this gap, a state-root divergence (which could stem from a JMT/state-checkpoint hashing bug, an archive/backup data corruption, or a subtle non-determinism in execution) would pass replay verification as a false positive. This undermines the primary safety net operators rely on to catch consensus-breaking state bugs before they propagate (e.g., via fast-sync from an archive, or governance sign-off on historical correctness), and could allow a corrupted or hard-fork-diverged state root to be treated as validated/trusted.

### Likelihood Explanation
The unprivileged root cause is a coding oversight (not attacker-triggerable by itself), but it is on the critical path of the only tool designed to catch a specific class of hard-fork-level state bugs. Any latent state-root computation bug (independent of this issue) combined with this comparator gap means the safety net silently fails exactly when it's needed most — likelihood of *triggering the underlying divergence* is low, but likelihood of the check *failing to catch it once triggered* is 100%, since the field is never inspected in this codepath.

### Recommendation
Add explicit checks in `ensure_match_transaction_info` comparing the locally derivable state-checkpoint hash information against `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` for `TransactionInfoV1`) whenever that data is available/computable in the given caller context (as the TODO already suggests, gating this on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or passing in the computed checkpoint hash explicitly), so replay/restore tooling cannot report success while the state root has actually diverged.

### Proof of Concept
Not directly exploitable by an external attacker; the issue is a verification-logic gap. It can be demonstrated by:
1. Constructing (or injecting via a modified fork of the local VM) a `TransactionOutput` whose write set and events hash correctly (matching `state_change_hash`/`event_root_hash`) but which, when applied to state, produces a different Sparse-Merkle root than the one committed in the corresponding archived `TransactionInfo.state_checkpoint_hash`.
2. Running it through `replay_on_archive`'s `execute_and_verify` / `ensure_match_transaction_info` (`storage/db-tool/src/replay_on_archive.rs:392`) and observing that no error is returned, because `state_checkpoint_hash` is never compared. [5](#0-4)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
