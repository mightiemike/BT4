### Title
Unbounded VotesStore iteration in `MaintenanceManager.doMaintenance()` enables block-processing denial of service - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
`MaintenanceManager.doMaintenance()` is invoked synchronously from `applyBlock()` on every block that crosses a maintenance boundary, and it calls `countVote(votesStore)`, which iterates over **every single entry** in `VotesStore` with no cap. `VotesStore` gains one entry per distinct address that casts a vote via `VoteWitnessContract`/TVM `voteWitness`, and casting a vote only requires a trivially small amount of TronPower (as little as 1 TRX). An attacker can cheaply create a very large number of voting accounts/entries, inflating `VotesStore` to a size that makes `countVote()` take an unbounded amount of time on every node, directly slowing or stalling block processing/consensus — the same "unbounded loop whose size is attacker-controlled via many cheap entries" bug class described in the Uniswap V3 report (many 1-wei positions inflating the swap loop).

### Finding Description
`doMaintenance()` is called from `applyBlock()` whenever the maintenance time boundary is crossed: [2](#0-1) 

Inside it, `countVote(votesStore)` performs a `while (dbIterator.hasNext())` loop over the *entire* `VotesStore` key space, with no limit on the number of iterations, and for each entry, does map lookups/inserts plus a `votesStore.delete(next.getKey())` write: [3](#0-2) 

Every entry in `VotesStore` corresponds to one voter address, and is created/updated by the `VoteWitnessActuator`/`VoteWitnessProcessor` (also reachable from TVM via the `voteWitness` opcode). The only requirement to place a vote (and thus grow `VotesStore` by one entry) is that the account holds enough TronPower to cover the requested vote count — as little as 1 TRX of frozen balance is sufficient for a 1-vote entry: [4](#0-3) [5](#0-4) 

`MAX_VOTE_NUMBER` only bounds the number of witnesses a *single* vote transaction can target, not the total number of distinct voter accounts/entries in `VotesStore`. There is no global cap on how many accounts can vote in a given maintenance cycle, so the size of the loop in `countVote()` is fully attacker-controllable: an attacker (or, as in the analogous Uniswap report, a miner/validator with free transaction inclusion) can create a large number of low-balance accounts, each freezing the minimal amount of TRX and casting one vote, to make `VotesStore` arbitrarily large before the next maintenance boundary.

### Impact Explanation
Because `doMaintenance()` runs synchronously as part of block application (`applyBlock`) for *every full/witness node in the network*, an inflated `VotesStore` forces all nodes to perform the same expensive unbounded iteration at the same time, at the maintenance-cycle boundary. This can:
- Significantly delay block production/validation for the witness node producing that block, increasing the risk of missed block slots.
- Cause node-to-node processing time divergence or timeouts across the network at maintenance boundaries, risking consensus-level liveness degradation (the same "invalid-state/divergence/halt" impact class called out in the validation rules).

This differs from the Uniswap analog only in the "operation" being rate-limited: instead of a single transaction running out of gas, it is the periodic (every maintenance interval, default every 6 hours but configurable, and re-triggered on every applicable block) global maintenance step that every node must execute, so the effect is chain-wide rather than confined to a single caller's transaction.

### Likelihood Explanation
Likelihood is high given:
- Anyone can call `VoteWitnessContract` cheaply (minimal frozen TRX) and TVM exposes an equivalent `voteWitness` precompiled path.
- There is no upper bound on distinct voter entries in `VotesStore`.
- `doMaintenance()`/`countVote()` execution is mandatory and synchronous in the block-application path, not optional or skippable.
- No fee scales with the number of stored vote entries actually processed at maintenance time (the cost of voting is a one-time actuator fee at cast time, not proportional to the long-term maintenance cost it imposes).

### Recommendation
- Cap the total number of distinct outstanding vote entries (`VotesStore` size) processed per maintenance cycle, or process them in bounded batches across multiple blocks rather than in one synchronous pass.
- Consider requiring a minimum TronPower/stake threshold for a vote to be persisted as a distinct `VotesStore` entry, so that voting with trivial amounts (e.g., 1 TRX) cannot cheaply inflate the store.
- Add monitoring/metrics on `VotesStore` size and `countVote()` execution time, and document/enforce bounds so growth cannot silently degrade block-processing time.

### Proof of Concept
1. Create N accounts, each funded with the minimum TRX required to freeze balance and obtain ≥1 TronPower.
2. From each account, submit `VoteWitnessContract` (or invoke TVM `voteWitness`) casting 1 vote for any valid witness — this creates one new entry in `VotesStore` per account per cycle, at minimal cost per entry.
3. Repeat for a large N (e.g., tens of thousands) before the next maintenance boundary.
4. At the maintenance boundary, `applyBlock()` → `doMaintenance()` → `countVote(votesStore)` iterates over all N entries synchronously while producing/applying that block, measurably increasing block-processing latency proportional to N, demonstrating the unbounded-loop DoS vector.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
