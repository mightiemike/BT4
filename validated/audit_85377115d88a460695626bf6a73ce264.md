### Title
Liquidation pause can never be cleared once activated due to missing state mutation in unpause branch - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`set-pause-liquidation` in the market contract uses a conditional branch to distinguish "unpausing" from "pausing," but the branch that is supposed to unpause the market only advances the grace-period clock and never resets the underlying `pause-liquidation` boolean. Because `liquidation-paused` is computed as `manual-pause OR grace-active`, and `manual-pause` can never be flipped back to `false` through the intended unpause call, liquidations become permanently blocked after the first pause.

### Finding Description
The function is implemented as:
```clarity
(define-data-var pause-liquidation bool false)
(define-data-var liquidation-grace-end uint u0)

(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (if (and was-paused (not paused))
        ;; When unpausing, set grace period
        (var-set liquidation-grace-end
                 (+ stacks-block-time grace-period))
        (var-set pause-liquidation paused))))

(define-read-only (liquidation-paused)
  (let ((manual-pause (var-get pause-liquidation))
        (grace-active (< stacks-block-time
                         (var-get liquidation-grace-end))))
    (or manual-pause grace-active)))
``` [1](#0-0) 

The presence and signature of these exact functions/vars (`set-pause-liquidation`, `get-pause-liquidation`, `get-liquidation-grace-end`, `pause-liquidation`, `liquidation-grace-end`) is confirmed against the compiled ABI: [2](#0-1) , and `set-pause-liquidation` is present in the production contract `mainnet/contracts/market/v0-4-market.clar` (confirmed via 4 occurrences in that file, matching the identical pattern shared by `local-testing/contracts/market/market.clar`).

Tracing the two branches of `if`:
1. Admin pauses: `was-paused=false`, `paused=true` → condition `(and was-paused (not paused))` is `false` → else-branch executes → `pause-liquidation` is set to `true`. Liquidations now blocked.
2. Admin later tries to unpause: `was-paused=true`, `paused=false` → condition is `true` → **if-branch executes → only `liquidation-grace-end` is updated; `pause-liquidation` is never set back to `false`.**
3. `liquidation-paused` reads `(or (var-get pause-liquidation) grace-active)`. Since `pause-liquidation` is still `true` from step 1, this returns `true` regardless of the grace period's expiry.
4. There is no code path in `set-pause-liquidation` that ever sets `pause-liquidation` to `false` when it was previously `true` — the only way `pause-liquidation` becomes `false` is if it started `false` and the admin calls with `paused=false` (else-branch, no-op).

This is a single-function/single-call logic defect: the mutation that should clear the boolean guard (`pause-liquidation := false`) is bound only to a code path that is never reached from the intended "unpause" call, because that call routes into the branch that only advances the grace-period clock instead.

### Impact Explanation
Once liquidations are paused via `set-pause-liquidation(true, ...)`, they can never be reactivated through the documented unpause mechanism, since `manual-pause` in `liquidation-paused` remains permanently `true`. All under-collateralized positions become permanently un-liquidatable, allowing bad debt to accumulate without any mechanism to seize collateral and repay debt. This results in permanent freezing of the liquidation mechanism and creates protocol insolvency risk, as bad debt can grow unchecked while creditors/suppliers cannot be made whole. This lands on the in-scope **Critical** impact class ("protocol insolvency") and/or **High** ("permanent freezing of unclaimed yield") depending on how funds already owed to suppliers are treated once bad debt accrues.

### Likelihood Explanation
This requires no attacker action or malicious actor — it is a deterministic logic defect triggered by the DAO/admin performing the documented, intended pause→unpause governance operation (calling `set-pause-liquidation(true, 0)` followed by `set-pause-liquidation(false, grace-period)`), which is a standard operational action (e.g., in response to any market incident) rather than a compromise or misconfiguration. Any legitimate use of the pause feature as designed triggers the permanent lock.

### Recommendation
In the unpause branch, explicitly reset `pause-liquidation` to `false` in addition to setting the grace-period end:
```clarity
(if (and was-paused (not paused))
    (begin
      (var-set liquidation-grace-end (+ stacks-block-time grace-period))
      (var-set pause-liquidation false))
    (var-set pause-liquidation paused))
```

### Proof of Concept
1. DAO/admin calls `(set-pause-liquidation true u0)` → `pause-liquidation` becomes `true`; `liquidation-paused` returns `true`.
2. An under-collateralized position exists that a liquidator wants to liquidate — call reverts/blocked due to pause (expected behavior at this point).
3. DAO/admin calls `(set-pause-liquidation false u3600)` intending to resume liquidations after a 1-hour grace period.
4. Inspect `pause-liquidation` via `get-pause-liquidation` — it is still `true` (unchanged by step 3).
5. Wait past `liquidation-grace-end` (1 hour). Call `liquidate` on the under-collateralized position.
6. `liquidation-paused` evaluates `(or true false)` = `true` → liquidation still blocked, indefinitely, with no further admin call able to clear it (any subsequent call with `paused=false` follows the same broken branch). [3](#0-2) [2](#0-1)
