### Title
Protocol-relative redirect target (`//evil.com`) bypasses `isSafe` host validation - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts])

### Summary
`isSafe` in `validate-redirect-url.ts` validates a redirect target by resolving it against the trusted app domain using `new URL(redirectUrl, domain)`, then checks `url.pathname`, `url.protocol`, and SSL requirement, but never validates that `url.host`/`url.origin` still matches the trusted `domain`. A protocol-relative input like `//evil.com` is resolved by the WHATWG URL parser to `https://evil.com/`, which passes every existing check and is returned as a "safe" URL.

### Finding Description
`isSafe` receives `domain` (the app's own trusted `appUrl`, e.g. `config.appUrl` in `render-app-bridge.ts`) and `redirectUrl` (attacker-controlled, e.g. a `redirectTo.url` value that ultimately reaches `renderAppBridge`). [1](#0-0) 

Flow:
1. `FILE_URI_MATCH = /\/\/\//` only rejects three-or-more slashes (`///path`), so `//evil.com` (two slashes) is not caught.
2. `WHITESPACE_CHARACTER` doesn't match.
3. `url = new URL(redirectUrl, domain)`: per the URL spec, a string beginning with `//` is a "network-path reference" — the parser keeps the base's scheme but takes the **host from the input**, i.e. `new URL('//evil.com', 'https://myapp.com')` yields `https://evil.com/`.
4. `INVALID_RELATIVE_URL.test(url.pathname)` — `url.pathname` for `https://evil.com/` is `/`, which does not match `[/\\][/\\]`, so it passes (the check operates on the *parsed* pathname, not the raw input, so the injected `//` in the host portion is invisible to this check).
5. `VALID_PROTOCOLS.includes(url.protocol)` — `https:` is valid.
6. `requireSSL` check passes since protocol is `https:`.

At no point is `url.host`, `url.origin`, or `url.hostname` compared against `domain`'s host. The function only guards against `javascript:`/`file:` schemes and malformed relative paths, not against the redirect target pointing to a completely different origin. This directly used by `renderAppBridge` in `render-app-bridge.ts`, where `sanitizeRedirectUrl(config.appUrl, redirectTo.url)` output is embedded into a `window.open(...)` script served to the merchant's browser inside the embedded admin iframe context. [2](#0-1) 

The question's framing around `decodeHost` (`packages/apps/shopify-api/lib/auth/decode-host.ts`) is a separate code path (`buildEmbeddedAppUrl`/`getEmbeddedAppUrl`) that decodes the `host` query param via `atob` after `sanitizeHost` validation — that path is unrelated to `isSafe`, and I found no code connecting `decodeHost` output into `isSafe`'s `redirectUrl` argument. The actual vulnerability is the origin-bypass in `isSafe` itself via protocol-relative URLs, independent of `decodeHost`. [3](#0-2) 

### Impact Explanation
Any caller that passes an attacker-influenced `redirectUrl` into `sanitizeRedirectUrl`/`isSafe` (e.g. `renderAppBridge`'s `redirectTo.url`) can be redirected to an attacker-controlled origin (`https://evil.com`) despite the function's intent to constrain redirects to the app's own domain. This is an open redirect within the embedded-app redirect flow, matching the "open redirect" impact class described in the question.

### Likelihood Explanation
Exploitability depends entirely on whether an unprivileged attacker can control the `redirectTo.url` value passed to `renderAppBridge`/`sanitizeRedirectUrl` in a given host app — this is a helper function, and I could not find, within the indexed code, a built-in library entrypoint that lets an anonymous HTTP client directly control this value without the app developer choosing to forward untrusted input into it. If a host app does forward a query parameter or user input into `redirectTo.url`, exploitation is trivial and fully repeatable (single crafted string `//evil.com`, no secrets or privileged access needed). The bug is real and confirmed at the unit level via the reproduction below, but real-world reachability depends on integrating application behavior, which is outside pure library-code guarantee.

### Recommendation
After parsing `url`, explicitly verify that `url.host` (or `url.origin`) equals the host/origin of the trusted `domain` (or is on an explicit allow-list), rejecting any URL whose resolved host differs from the base domain. Also update `INVALID_RELATIVE_URL`/`FILE_URI_MATCH` checks to be applied against the raw `redirectUrl` string before resolution, since post-resolution `pathname` checks can't detect origin-changing patterns like `//host`.

### Proof of Concept
```ts
import {sanitizeRedirectUrl} from '../validate-redirect-url';

it('BUG: protocol-relative redirectUrl escapes the app domain', () => {
  const APP_URL = 'https://myapp.example.com';
  const result = sanitizeRedirectUrl(APP_URL, '//evil.com');

  // Expected (secure) behavior: should throw ShopifyError('Invalid URL. Refusing to redirect')
  // Actual behavior: returns a URL pointing to the attacker's origin
  expect(result.origin).toBe('https://evil.com');
});
```
Running this against the current `isSafe`/`sanitizeRedirectUrl` implementation shows `result.origin === 'https://evil.com'` instead of throwing, confirming the bypass. [4](#0-3)

```typescript
function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
```
