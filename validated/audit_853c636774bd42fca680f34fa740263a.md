### Title
Rounding-down in `CalculateGasCost` truncates fractional base-fee amounts, causing systematic under-collection of UEA execution gas fees - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`Keeper.CalculateGasCost` (`x/uexecutor/keeper/fees.go`) converts the `feemarket` module's `LegacyDec` base fee into a whole-`upc` `*big.Int` using integer division (`baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))`) and then multiplies by `gasUsed` to derive the amount charged to a UEA for `MsgExecutePayload`/`ExecutePayloadV2` execution. [1](#0-0) 

### Finding Description
The comment justifying the division claims "the base fee is always a whole number of upc -- no fractional upc exists," but this is an invariant of the caller's assumption, not something enforced anywhere in this code path. `feemarket.Keeper.GetBaseFee` returns an `sdkmath.LegacyDec`, and the EIP-1559-style base-fee adjustment formula performed by the `feemarket` module each block (`baseFee ± baseFee*gasUsedDelta/(gasTarget*denominator)`) is exact only in `LegacyDec`'s 18-decimal fixed point arithmetic; it commonly produces a base fee value whose internal `Int` representation is *not* an exact multiple of `1e18`. When that happens, `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` truncates (Go's integer division rounds toward zero/floor for positive values) instead of rounding up, silently discarding up to `(1e18 - 1)` worth of fractional upc precision from the effective gas price used in `effectiveGasPrice := new(big.Int).Set(baseFeeBig)` before it is multiplied by `gasUsed` in `gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig)`. [2](#0-1) 

This is structurally the same rounding-class bug as the referenced `TradingLimits::update()` report: a division is performed without rounding up on the remainder, and the resulting per-unit value is then multiplied by a large quantity (`gasUsed`), which amplifies the truncated fraction into a material aggregate loss. `DeductGasFeesFromReceipt` (`x/uexecutor/keeper/fees.go:97-148`) uses this truncated `gasCost` to burn funds from the UEA's balance via `DeductAndBurnFees`, so every `MsgExecutePayload` and `ExecutePayloadV2` execution (`x/uexecutor/keeper/msg_execute_payload.go`, `x/uexecutor/keeper/execute_payload.go`) systematically under-charges the UEA relative to the network's actual base fee, whenever the underlying `LegacyDec` base fee is not an exact multiple of `1e18`. [3](#0-2) 

### Impact Explanation
This corrupts gas-fee accounting: the protocol's fee-burn mechanism systematically collects less than the true EIP-1559 base fee owed, on every payload execution where the fractional truncation applies. Because `effectiveGasPrice` is rounded down once and then multiplied by `gasUsed` (which can be in the millions per `GasLimit: "21000000"` seen in test fixtures), the aggregate under-collection per transaction can be significant, and it recurs on every `ExecutePayload` call network-wide — a permanent, uncapturable loss of protocol fee revenue rather than a one-off rounding error. This matches the "corruption of ... gas fee accounting" allowed-impact category for this scope.

### Likelihood Explanation
Likelihood depends on how often the `feemarket` base fee's `LegacyDec` value is *not* an exact multiple of `1e18` — I was unable to confirm within the available code whether `feemarket`'s `CalculateBaseFee`/`SetBaseFee` logic (vendored dependency, not part of this repo's indexed source) guarantees whole-upc granularity by construction, or whether it can produce genuine fractional `upc` values through its adjustment formula. The in-repo comment's claim that "no fractional upc exists" is asserted, not enforced by any visible code in this repository, and `sdkmath.LegacyDec` is a general fixed-point type that supports fractional values as first-class citizens. Since triggering this only requires ordinary unprivileged `MsgExecutePayload` submission whenever the base fee happens to carry a fractional remainder, no privileged access or malicious peer/validator behavior is required — it is a byproduct of standard EIP-1559 base-fee dynamics, if those dynamics can produce non-multiple-of-`1e18` values (unconfirmed from this repo alone).

### Recommendation
Do not assume the base fee is always a whole multiple of `1e18`. Round the unwrapped base fee up (ceiling) rather than truncating, e.g.:
```go
baseFeeBig := baseFee.BigInt()
divisor := big.NewInt(1e18)
remainder := new(big.Int)
baseFeeBig.QuoRem(baseFeeBig, divisor, remainder)
if remainder.Sign() != 0 {
    baseFeeBig.Add(baseFeeBig, big.NewInt(1))
}
```
Alternatively, avoid the intermediate integer unwrap entirely and perform the final `gasCost = effectiveGasPrice(Dec) * gasUsed(Dec)` multiplication in `LegacyDec` space, then take `.Ceil().RoundInt()` once at the very end (mirroring the pattern already used correctly in `app/cosmos/min_gas_price.go`'s `fee := gp.Amount.Mul(gasLimit).Ceil().RoundInt()`), so any fractional-upc precision is preserved through the multiplication and rounded up only once, in the caller's favor rather than the protocol's disfavor. [4](#0-3) 

### Proof of Concept
1. Assume the `feemarket` module's dynamic base-fee adjustment produces a base fee of, e.g., `1_000_000_000.999999999999999999` (represented internally in `LegacyDec` as `1000000000999999999999999999`), a value not evenly divisible by `1e18`.
2. `k.feemarketKeeper.GetBaseFee(sdkCtx)` returns this `LegacyDec` inside `DeductGasFeesFromReceipt`.
3. `CalculateGasCost` computes `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` → floors to `1_000_000_000` upc, discarding the `.999999999999999999` fractional upc.
4. For `gasUsed = 21,000,000` (a `GasLimit` value seen in existing test fixtures such as `test/integration/uexecutor/execute_payload_test.go`), the under-collection versus the true fractional base fee approaches `20,999,999` upc worth of value per execution, silently lost from the protocol's fee-burn accounting on every such call. [5](#0-4) 

**Caveat**: I could not verify from the indexed portion of this repository (the `feemarket` module implementation is a vendored/external dependency not fully present in the codebase index) whether the base fee value can, in practice, ever be a non-multiple of `1e18` under the current `feemarket` parameters. If `feemarket` always snaps `base_fee` to whole-upc values by construction, this finding would be inert. I recommend starting a Devin session with full repository/dependency access to confirm the exact `feemarket.CalculateBaseFee` arithmetic before treating this as a confirmed, exploitable vulnerability rather than a defensive-coding gap.
