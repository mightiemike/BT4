## Summary

The Panoptic report describes a safety check (`isSafeMode`'s `highDivergence` comparison) whose threshold can never be reached, making the check dead code that provides a false sense of protection. The Aptos-native analog I found is structurally identical: a **transaction-replay integrity comparator that never checks the fields it claims to guard**, giving replay/backup-verify tooling a false sense that a replayed ledger state matches the authenticated one.

### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint roots, letting replay-verify tooling certify a wrong ledger state as correct - (File: `types/src/transaction/mod.rs`)

### Finding Description
`TransactionInfo` carries several fields that are the *authenticated* binding between a committed transaction and the resulting world state: `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` [1](#0-0) . These hashes (together with the transaction hash, event root, and write-set hash) are what get hashed into `TransactionInfo::hash()`, which in turn is the leaf committed into the transaction accumulator whose root is bound in a `LedgerInfo` and authenticated by validator signatures.

`TransactionOutput::ensure_match_transaction_info` is the function used to verify that a locally re-executed `TransactionOutput` matches the trusted, previously-committed `TransactionInfo`. It checks `status`, `gas_used`, the write-set hash (`state_change_hash`) and the event root hash [2](#0-1) , but explicitly stops before checking any of the checkpoint hashes, with the function's own comment documenting the gap: [3](#0-2) 

The write-set hash check only proves that the *raw write-set bytes* produced by re-execution match those originally committed—it says nothing about whether applying that write set to the (locally reconstructed) prior state tree yields the same Sparse-Merkle/Jellyfish-Merkle root, hot-state root, or position-state root as the authenticated ledger. A divergence at the state-application layer (e.g., a bug in JMT update logic, hot-state maintenance, or the new position-state tree, or an incorrect prior-state input at a chunk boundary) would still pass this check as long as write-set bytes and events line up.

This comparator is not test-only code — it is invoked as the pass/fail gate in real verification tools:
- `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, the dedicated tool for verifying that replaying an entire archived chain against freshly executed transactions produces the correct result [4](#0-3) .
- `execution/executor/src/chunk_executor/mod.rs` (state-sync/backup chunk replay path), `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`.

In all of these call sites, "replay succeeded" is reported based on this comparator, even though the state-checkpoint roots are never cross-checked.

### Impact Explanation
This is a proof/commitment-integrity blind spot rather than a consensus-safety bug: it does not let bad state get committed by validators (the state-checkpoint hash is still computed and embedded by the executor during normal block commit via `do_state_checkpoint.rs`/`do_ledger_update.rs`). The impact is that the tooling relied on to *detect* state divergence — chain replay-verify (`db-tool replay-on-archive`), archival node bootstrapping/verification, and backup/restore transaction replay — can silently certify that a locally recomputed ledger state matches the authenticated one, when in fact the state root (hot-state root, position-state root, or even the plain state-checkpoint root) diverges. This is exactly the kind of "authenticated ledger data reinterpreted as matching when it does not" failure the state-integrity gate targets: a corrupted/incorrect state root at a checkpoint transaction would not be flagged by the one tool designed to catch it, undermining confidence in replay-verify results used to validate full-node/archive-node correctness and backup integrity.

### Likelihood Explanation
The gap is not hypothetical: the author of the code explicitly flagged it via the `TODO(trading-native)` comment, tying it to the upcoming `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature and `position_state_checkpoint_hash` field. Since `position_state_checkpoint_hash`, `hot_state_checkpoint_hash`, and even the base `state_checkpoint_hash` are already populated fields on `TransactionInfo` today, any executor bug or replay path bug affecting state-tree computation (hot state, position state, or the base SMT) is *currently* unreachable by this specific verification path independent of whether the new feature is enabled — the comment says the checkpoint hashes are ignored unconditionally, not gated behind the flag. This makes it a live, currently-reachable verification gap in shipped tooling, not dead code guarded by an unactivated flag.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding locally-recomputed roots for any transaction that is a checkpoint boundary, before shipping/enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. Until this validation is added, treat all replay-verify (`db-tool replay-on-archive`), chunk-executor replay, and debugger replay results as unable to catch state-root divergence, and flag any past "successful" replay-verify runs as unverified with respect to state-checkpoint correctness.

### Proof of Concept
1. Introduce (or trigger) a bug in state-checkpoint materialization that changes the resulting hot-state or position-state root while keeping the write set’s raw byte hash and event root identical (e.g., a stale intermediate hot-state input, or an off-by-one in position-state tree update logic).
2. Run `storage/db-tool/src/replay_on_archive.rs` (`db-tool replay-on-archive`) across the affected version range.
3. Observe that `execute_and_verify` reports zero failed transactions [5](#0-4) , because `ensure_match_transaction_info` only compares `status`, `gas_used`, `state_change_hash`, and `event_root_hash`, never `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` [6](#0-5) .
4. Confirm independently (e.g., by directly recomputing and diffing the state root) that the locally-reconstructed state root at the checkpoint transaction differs from `TransactionInfo::state_checkpoint_hash()`, demonstrating that the tool's "success" result is a false pass.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
