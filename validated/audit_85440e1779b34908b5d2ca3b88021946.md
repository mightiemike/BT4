### Title
Nakamoto block acceptance decouples `header.parent_block_id`'s VRF lineage from the block-commit's own `parent_block_ptr`/`parent_vtxindex` ancestor - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoBlock::validate_vrf_seed` resolves the "parent tenure" whose VRF proof must match `block_commit.new_seed` purely from `self.header.parent_block_id` (an attacker-chosen field in the block header itself), never from the block-commit's own `parent_block_ptr`/`parent_vtxindex`. This means the equality "the tenure identified by `block_commit.parent_block_ptr`/`parent_vtxindex` on the burnchain == the tenure identified by `block.header.parent_block_id`" is never asserted in this function.

### Finding Description
`validate_vrf_seed` is defined as: [1](#0-0) 

It calls `NakamotoChainState::get_parent_vrf_proof(chainstate_conn, &self.header.parent_block_id, sortdb_conn, &self.header.consensus_hash, &block_commit.txid)` and then checks `block_commit.new_seed.is_from_proof(&parent_vrf_proof)`. The only inputs used to locate the "parent" whose VRF proof must be matched are `self.header.parent_block_id` (a Stacks-block-header field fully controlled by the block's author at submission time) and `self.header.consensus_hash`. Neither `block_commit.parent_block_ptr` nor `block_commit.parent_vtxindex` — the fields that are supposed to encode, at burnchain-commit-broadcast time, which ancestor sortition/tenure this specific winning commit is extending — are read or cross-checked here.

Separately, `check_tenure_tx`/`try_get_tenure_change_payload` only enforces internal self-consistency: `tc_payload.previous_tenure_end == self.header.parent_block_id`, i.e., the tenure-change payload and the header must agree with each other, not with the block-commit's `parent_block_ptr`/`parent_vtxindex`: [2](#0-1) 

So a miner could broadcast a `LeaderBlockCommitOp` with `parent_block_ptr`/`parent_vtxindex` pointing at tenure T2's winning sortition (satisfying whatever burnchain-side lineage/`check_intended`-style validation exists in `leader_block_commit.rs` for that commit to be considered a valid continuation of *some* prior winning commit), and, if that commit wins its sortition, subsequently produce a Nakamoto block whose `header.parent_block_id` points at a different tenure T1, with a VRF proof that is legitimately derived from T1's tenure. Because `validate_vrf_seed` only checks self-consistency against `header.parent_block_id` (T1), and `check_tenure_tx` only checks self-consistency between the header and the tenure-change payload (also T1), this block would pass both checks despite its own block-commit's on-chain `parent_block_ptr`/`parent_vtxindex` claiming lineage from T2.

### Impact Explanation
If accepted, this produces a block that is internally VRF/tenure-consistent with T1 while its burnchain block-commit record claims descent from T2 — a mismatch between the sortition-recorded lineage and the actual Stacks fork the block extends. Two honest nodes that key their bookkeeping (fork-choice, reward-cycle/tenure accounting tied to `parent_block_ptr`) off the burnchain commit-chain versus the Stacks-level `parent_block_id` chain could diverge on which tenure/fork is canonical, which is the class of divergence the rules classify as High ("a minority-triggerable sortition/VRF/static-validation divergence, ... temporary tip disagreement").

### Likelihood Explanation
This requires only a single miner slot (own BTC, own block-commit) — no majority stake or majority signer collusion is needed to construct the mismatched commit/block pair. However, I could not confirm within the available inspection budget whether other guards outside `nakamoto/mod.rs` — specifically the burnchain-side commit-chain validation in `leader_block_commit.rs`/`sortdb.rs` (e.g. `check_intended`, parent-commit resolution during sortition processing) or the signer-side block proposal validation (`verify_signer_signatures`) — independently re-derive and enforce the T1==T2 equality before a block is signed/accepted. Those checks are explicitly called out in the audit "Validate" step as potential existing guards, and I was unable to fully trace them before running out of tool budget.

### Recommendation
In `validate_vrf_seed` (or a preceding check in `append_block`), resolve the tenure-start block/consensus_hash implied by `block_commit.parent_block_ptr`/`block_commit.parent_vtxindex` via the sortition DB, and assert it equals the tenure/consensus_hash of `self.header.parent_block_id` before accepting the block, rather than trusting `self.header.parent_block_id` alone to select which VRF proof to check against.

### Proof of Concept
Given I could not fully confirm the absence of a countervailing check in `leader_block_commit.rs`/`sortdb.rs`/signer validation within budget, I cannot certify this as a fully proven, unmitigated Critical/High finding. A concrete test to settle it would need to: construct two tenures T1 and T2 on a two-node harness, broadcast a `LeaderBlockCommitOp` with `parent_block_ptr`/`parent_vtxindex` set to T2's sortition, mine a `NakamotoBlock` with `header.parent_block_id` = T1's tip and a VRF proof derived from T1, call `NakamotoChainState::append_block` on both nodes, and assert whether it is accepted and whether the two nodes' MARF roots diverge — exactly as the question proposes. This test was not run and the surrounding burnchain-side/signer-side guards were not fully traced, so this should be treated as an open lead rather than a fully confirmed vulnerability.

    pub fn validate_vrf_seed<SDBI: StacksDBIndexed>(
        &self,
        sortdb_conn: &Connection,
        chainstate_conn: &mut SDBI,
        block_commit: &LeaderBlockCommitOp,
    ) -> Result<(), ChainstateError> {
        // the block-commit from the miner who created this coinbase must have a VRF seed that
        // is the hash of the parent tenure's VRF proof.
        // Do the query relative to the parent block ID, since this block may not be processed yet.
        let parent_vrf_proof = NakamotoChainState::get_parent_vrf_proof(
            chainstate_conn,
            &self.header.parent_block_id,
            sortdb_conn,
            &self.header.consensus_hash,
            &block_commit.txid,
        )?;
        if !block_commit.new_seed.is_from_proof(&parent_vrf_proof) {
            warn!("Invalid Nakamoto block-commit: seed does not match parent VRF proof";
                  "consensus_hash" => %self.header.consensus_hash,
                  "stacks_block_hash" => %self.header.block_hash(),
                  "stacks_block_id" => %self.block_id(),
                  "parent_block_id" => %self.header.parent_block_id,
                  "commit_seed" => %block_commit.new_seed,
                  "proof_seed" => %VRFSeed::from_proof(&parent_vrf_proof),
                  "parent_vrf_proof" => %parent_vrf_proof.to_hex(),
                  "block_commit" => format!("{:?}", &block_commit)
            );
            return Err(ChainstateError::InvalidStacksBlock(
                "Invalid Nakamoto block: bad VRF proof".into(),
            ));
        }
        Ok(())
    }
