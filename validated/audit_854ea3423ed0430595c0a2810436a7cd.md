### Title
`calculate_matured_miner_rewards` reads `get_poison_microblock_report` before that same block's `PoisonMicroblock` transaction is processed, letting a miner collect the full coinbase for the exact tenure being slashed - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoChainState::setup_block` computes `matured_rewards_opt` via `Self::calculate_matured_miner_rewards` immediately after opening the block's `clarity_tx`, and only afterward does block/tenure transaction processing (which runs `PoisonMicroblock` transactions via `handle_poison_microblock`) execute against that same `clarity_tx`/MARF handle. If a `PoisonMicroblock` transaction targets the exact `microblock_pubkey_hash` height that matures in the current block (`reward_height == tip_stacks_height - MINER_REWARD_MATURITY`), its `insert_microblock_poison` write happens strictly after `get_poison_microblock_report(reward_height)` was already read (and returned `None`) for reward computation, so the miner is paid in full despite the poison report being valid and timely.

### Finding Description
The broken equality is: `get_poison_microblock_report(reward_height)` returned by `StacksChainState::find_mature_miner_rewards` should equal the poison state that will ultimately be visible for `reward_height` in the finalized block, i.e., "if a valid `PoisonMicroblock` tx for `reward_height` is included in this same block, `calculate_miner_reward`'s `poison_reporter_opt` must be `Some`." In practice, this equality is broken by an ordering bug.

`NakamotoChainState::setup_block` [1](#0-0)  opens `clarity_tx` and, before any block transaction is processed, calls `Self::calculate_matured_miner_rewards` (which calls `find_mature_miner_rewards` → `get_poison_microblock_report(clarity_tx, reward_height)`) [2](#0-1) . This read happens against the `clarity_tx` at the moment the block begins — before the block's own transactions (including any `PoisonMicroblock` tx) are processed.

`handle_poison_microblock` validates that a poison report is admissible as long as `height + MINER_REWARD_MATURITY >= current_height` [3](#0-2) , i.e., it allows `height` exactly equal to `current_height - MINER_REWARD_MATURITY`. That is precisely `reward_height` as computed in `find_mature_miner_rewards` (`reward_height = tip_stacks_height - MINER_REWARD_MATURITY`) [4](#0-3) . So a `PoisonMicroblock` transaction naming the maturing block's `microblock_pubkey_hash` is legal to include in the very same block that matures that reward, and `insert_microblock_poison` for that key/height is only written when that transaction executes later in the block [5](#0-4) .

Because reward computation already ran and captured `poison_recipient_opt = None`, `calculate_miner_reward` computes the coinbase reward as unpunished (`punished = false`, full coinbase to the miner) [6](#0-5) . The resulting `MinerReward`/`MaturedMinerRewards` are already finalized in `SetupBlockResult` and later committed to the miner-payments table via `insert_matured_child_miner_reward` [7](#0-6) , independent of the fact that `get_poison_microblock_report(reward_height)` would return `Some` for any query made after the block finishes processing. No later code re-checks or recomputes the reward after the poison transaction commits within the same block; the reward is one-shot and permanent once written to the payments table.

This is not the same as the existing, working same-block poison test in `transactions.rs` (`process_poison_microblock`), which only asserts that `get_poison_microblock_report` returns the correct value *after* `process_transaction` runs a standalone transaction against a bare `conn` — it does not exercise the full `setup_block`/tenure ordering where the report is read for reward-calculation purposes *before* the transaction stream is processed.

### Impact Explanation
This is a block-reward mispayment/theft: the miner who forked their own microblock stream at `reward_height` retains 100% of the coinbase for that block instead of being slashed, and the honest reporter who filed a technically valid and timely `PoisonMicroblock` report permanently loses the commission they were entitled to (there is no re-evaluation once the reward is committed to the payments table). This is a real, deterministic outcome reproducible by every honest node processing the same block (all nodes apply the identical `setup_block` ordering), so it does not cause a fork/consensus divergence between nodes — it is consistently wrong on every node. That places it as a "poison or reward mis-payment bounded to fees/coinbase" class finding rather than a chain split, matching the **High** category (poison/reward mis-payment) rather than "Critical" (since there's no double-payment, no chain split, and no invalid/valid block dispute — all nodes agree on the same, incorrectly-unpunished outcome).

### Likelihood Explanation
The attacker only needs: (1) to be a miner who signs two conflicting microblocks with the same `microblock_pubkey_hash` (already something any miner does naturally when running a normal Stacks tenure), and (2) to ensure a `PoisonMicroblock` transaction targeting that exact height is placed into the block that matures the reward, at `height == current_height - MINER_REWARD_MATURITY` exactly. Both a miner protecting itself (self-poisoning to guarantee unpunished payout is nonsensical for a miner but a colluding reporter or the same miner controlling both mempool inclusion and its own tenure could time this deterministically) or any reporter racing the exact maturation block can trigger this by simply broadcasting the report transaction to land in the block at the maturity boundary height. This requires no majority stake, no signer collusion, and no privileged role — it is achievable by a single unprivileged miner/reporter with correctly timed transaction submission. It is fully repeatable each time a poison condition arises at exactly the maturity boundary.

### Recommendation
Reorder `setup_block` so that `PoisonMicroblock` transactions (or at least their `insert_microblock_poison` writes) affecting `reward_height` are applied to the `clarity_tx` before `calculate_matured_miner_rewards`/`find_mature_miner_rewards` is invoked, or defer/re-run the matured-reward computation after all of the block's transactions (including poison reports) have been processed. Alternatively, explicitly disallow the boundary case in `handle_poison_microblock`: change the maturity check to `height + MINER_REWARD_MATURITY < current_height` **or `== current_height`** rejection, so that a poison report can only affect *future* maturation events and never the reward being matured within the very block containing the report.

### Proof of Concept
Rust integration test plan (two-node/single-node full block harness, not the low-level `process_transaction` unit test):
1. Build a chain to height `H_target` such that `H_target + MINER_REWARD_MATURITY == H_current` will hold once a new block at `H_current` is mined (i.e., set up the exact boundary).
2. At tenure/block `H_target`, have the miner produce microblocks signed with `mblock_privk`, and record `microblock_pubkey_hash` → recorded at height `H_target`.
3. Fork the microblock stream at `H_target` (two conflicting `StacksMicroblockHeader`s with the same pubkey, different content) to create valid poison evidence.
4. Construct block at `H_current = H_target + MINER_REWARD_MATURITY` that includes a `PoisonMicroblock` transaction reporting this fork, submitted through the normal mempool/miner block-assembly path (not raw `process_transaction`), so it goes through `setup_block` → `calculate_matured_miner_rewards` → tenure transaction processing in the real order.
5. After the block is appended, assert both sides of the equality:
   - `get_poison_microblock_report(clarity_tx_at_H_current, H_target)` returns `Some((reporter_addr, seq))` (the poison report is present in the committed state).
   - `StacksChainState::get_matured_miner_payment(...)` for the miner's reward maturing at `H_target` shows `coinbase == full_coinbase` (unpunished) instead of `0`, and the reporter's account balance does not receive the `poison_microblock_commission`.
6. Assert this contradicts the invariant `reward_paid_to_miner == 0` whenever `get_poison_microblock_report` is `Some` for that height, demonstrating the mispayment.
