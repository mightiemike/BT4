### Title
Missing "ForbidTransferToContract" enforcement in `ShieldedTransferActuator` allows bypass of committee-controlled TRX-to-contract restriction - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`TransferActuator` and `TransferAssetActuator` both enforce a protocol-level restriction — when the `ForbidTransferToContract` dynamic parameter is enabled, plain TRX/TRC10 transfers to a smart-contract account are rejected, forcing value to reach contracts only through `TriggerSmartContract`. `ShieldedTransferActuator`, which implements a third, functionally equivalent "transparent-to" leg (`transparentToAddress`/`toAmount`) that credits an ordinary account balance exactly like `TransferActuator`, does not perform this same check. This mirrors the reported `FighterFarm` bug class: a restriction is enforced on some, but not all, code paths that achieve the same underlying state transition (crediting an address's balance), letting an unprivileged user reach the same effect through the unguarded path.

### Finding Description
`TransferActuator.validate()` explicitly checks:
```
if (dynamicStore.getForbidTransferToContract() == 1
    && toAccount != null
    && toAccount.getType() == AccountType.Contract) {
  throw new ContractValidateException("Cannot transfer TRX to a smartContract.");
}
``` [1](#0-0) 

`TransferAssetActuator.validate()` enforces the analogous restriction for TRC10 asset transfers:
```
if (dynamicStore.getForbidTransferToContract() == 1
    && toAccount.getType() == AccountType.Contract) {
  throw new ContractValidateException("Cannot transfer asset to smartContract.");
}
``` [2](#0-1) 

`ShieldedTransferActuator` supports a "transparent" public leg that credits an arbitrary `transparentToAddress` with TRX (represented internally as the ZEN TRC10 token) via `executeTransparentTo()`, which simply looks up/creates the destination account and calls `Commons.adjustAssetBalanceV2` to increase its balance — with no check of the account's `AccountType`: [3](#0-2) 

The corresponding validation function `validateTransparent()` validates addresses, amounts, sender balance sufficiency, and overflow, but never queries `dynamicStore.getForbidTransferToContract()` or the destination account's `AccountType`, unlike the two sibling actuators: [4](#0-3) 

Thus a `ShieldedTransferContract` with a non-empty `transparent_to_address` pointing at a smart-contract account, and an empty spend/receive shielded portion balanced only by the transparent legs, can deliver TRX value directly into a contract's balance while `ForbidTransferToContract` is active — exactly the scenario the two other actuators are designed to prevent.

### Impact Explanation
This is a state/accounting-divergence bug of the same class as the referenced report: a protocol invariant ("no direct external TRX credit to contract accounts once `ForbidTransferToContract` is enabled") is enforced inconsistently across otherwise-equivalent value-transfer code paths. The restriction exists specifically to prevent contracts from receiving value outside of `TriggerSmartContract` (avoiding un-metered/unexpected value injection that a contract's accounting logic, written assuming all incoming value arrives via `CALL`, does not anticipate). An unprivileged user can bypass this governance-controlled restriction using `ShieldedTransferContract`, which is a normal, permissionless transaction type (no special/trusted role required, since sender only needs to control the `transparentFromAddress` and can specify any `transparentToAddress`).

### Likelihood Explanation
High for any deployment where `ForbidTransferToContract` has been activated by the committee (this proposal exists in mainnet governance). Any ordinary account holder can issue a `ShieldedTransferContract` with a transparent-to leg targeting a contract address; no shielded proof of a spend is even required against the destination side, only the standard fee/from-amount validation. The exploit path requires no privileged role, no mocked environment, and directly reaches production actuator logic executed by every full node.

### Recommendation
Add the same `ForbidTransferToContract` + `AccountType.Contract` check to `ShieldedTransferActuator.validateTransparent()` (and mirror it before `executeTransparentTo()`), consistent with `TransferActuator` and `TransferAssetActuator`, e.g.:
```java
if (hasTransparentTo) {
  ...
  AccountCapsule toAccount = accountStore.get(toAddress);
  if (toAccount != null) {
    if (dynamicStore.getForbidTransferToContract() == 1
        && toAccount.getType() == AccountType.Contract) {
      throw new ContractValidateException("Cannot transfer to a smartContract.");
    }
    ...
  }
}
```
More generally, centralize this restriction check in a shared helper invoked by all actuators that can credit an arbitrary destination account with TRX/TRC10 value, so future new transfer-like contract types cannot silently omit it (the same remediation principle recommended in the original report: enforce transferability restrictions through a single common path rather than duplicating checks per entry point).

### Proof of Concept
Conceptual reproduction (would need to be validated by a background agent with test harness access, since I could not execute code in this environment):
1. Committee enables `ForbidTransferToContract` (`dynamicStore.getForbidTransferToContract() == 1`).
2. Deploy/observe an existing smart contract account `C` (`AccountType.Contract`).
3. Attacker submits a `ShieldedTransferContract` with:
   - `transparent_from_address` = attacker address, `from_amount` = X (X > fee)
   - `transparent_to_address` = `C`, `to_amount` = X − fee
   - empty `spend_description`/`receive_description` lists is disallowed (`checkSender`/`checkReceiver` require exactly one of spend/transparent-from and require at least one receive description) — so the shielded receive portion must balance the pool; a minimal valid shielded receive note can be constructed to net the pool to zero while the transparent legs still move value into `C`.
4. `ShieldedTransferActuator.validate()` passes (no contract-type check exists in `validateTransparent`), `execute()` calls `executeTransparentTo()` and credits `C`'s balance directly, bypassing the restriction that `TransferActuator`/`TransferAssetActuator` enforce.

I was unable to fully verify the exact minimal-valid shielded note construction (this involves zk-SNARK proof generation code, `JLibrustzcash`, outside what the indexed code search surfaced) needed to satisfy `checkProof`/`checkSender`/`checkReceiver` while keeping the transparent-to leg non-zero; a background agent with the full test suite (`ShieldedTransferActuatorTest` or similar, if present) should confirm end-to-end exploitability and produce a working unit test.

  private void executeTransparentTo(byte[] toAddress, long amount, TransactionResultCapsule ret,
      long fee)
      throws ContractExeException {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    AssetIssueStore assetIssueStore = chainBaseManager.getAssetIssueStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    try {
      AccountCapsule toAccount = accountStore.get(toAddress);
      if (toAccount == null) {
        boolean withDefaultPermission =
            dynamicStore.getAllowMultiSign() == 1;
        toAccount = new AccountCapsule(ByteString.copyFrom(toAddress), AccountType.Normal,
            dynamicStore.getLatestBlockHeaderTimestamp(), withDefaultPermission, dynamicStore);
        accountStore.put(toAddress, toAccount);
      }
      Commons.adjustAssetBalanceV2(toAddress, CommonParameter.getInstance().getZenTokenId(),
          amount, accountStore, assetIssueStore,
          dynamicStore);
    } catch (BalanceInsufficientException e) {
      ret.setStatus(0, code.FAILED);
      ret.setShieldedTransactionFee(fee);
      throw new ContractExeException(e.getMessage());
    }
  }

```java
  private void validateTransparent(ShieldedTransferContract shieldedTransferContract, long fee)
      throws ContractValidateException {
    boolean hasTransparentFrom;
    boolean hasTransparentTo;
    byte[] toAddress = shieldedTransferContract.getTransparentToAddress().toByteArray();
    byte[] ownerAddress = shieldedTransferContract.getTransparentFromAddress().toByteArray();

    hasTransparentFrom = (ownerAddress.length > 0);
    hasTransparentTo = (toAddress.length > 0);
    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fromAmount = shieldedTransferContract.getFromAmount();
    long toAmount = shieldedTransferContract.getToAmount();
    if (fromAmount < 0) {
      throw new ContractValidateException("from_amount should not be less than 0");
    }
    if (toAmount < 0) {
      throw new ContractValidateException("to_amount should not be less than 0");
    }

    if (hasTransparentFrom && !DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid transparent_from_address");
    }
    if (!hasTransparentFrom && fromAmount != 0) {
      throw new ContractValidateException("no transparent_from_address, from_amount should be 0");
    }
    if (hasTransparentTo && !DecodeUtil.addressValid(toAddress)) {
      throw new ContractValidateException("Invalid transparent_to_address");
    }
    if (!hasTransparentTo && toAmount != 0) {
      throw new ContractValidateException("no transparent_to_address, to_amount should be 0");
    }
    if (hasTransparentFrom && hasTransparentTo && Arrays.equals(toAddress, ownerAddress)) {
      throw new ContractValidateException("Can't transfer zen to yourself");
    }

    if (hasTransparentFrom) {
      AccountCapsule ownerAccount = accountStore.get(ownerAddress);
      if (ownerAccount == null) {
        throw new ContractValidateException("Validate ShieldedTransferContract error, "
            + "no OwnerAccount");
      }
      long balance = getZenBalance(ownerAccount);
      if (fromAmount <= 0) {
        throw new ContractValidateException("from_amount must be greater than 0");
      }
      if (balance < fromAmount) {
        throw new ContractValidateException(
            "Validate ShieldedTransferContract error, balance is not sufficient");
      }
      if (fromAmount <= fee) {
        throw new ContractValidateException(
            "Validate ShieldedTransferContract error, fromAmount should be great than fee");
      }
    }

    if (hasTransparentTo) {
      if (toAmount <= 0) {
        throw new ContractValidateException("to_amount must be greater than 0");
      }
      AccountCapsule toAccount = accountStore.get(toAddress);
      if (toAccount != null) {
        try {
          addExact(getZenBalance(toAccount), toAmount);
        } catch (ArithmeticException e) {
          logger.debug(e.getMessage(), e);
          throw new ContractValidateException(e.getMessage());
        }
      }
    }
  }
