### Title
Front-running a bogus `vote-for-aggregate-public-key` call permanently poisons the legitimate DKG aggregate key for a reward cycle - ([File: stackslib/src/chainstate/stacks/boot/signers-voting.clar])

### Summary
The `.signers-voting` contract's `vote-for-aggregate-public-key` function unconditionally records every voted-on aggregate key in a global `used-aggregate-public-keys` map, keyed only by the raw key bytes, *before* any consensus threshold is reached. A single minority-weight signer can pre-emptively "use up" the exact aggregate key that the honest signer majority is about to vote for in the correct reward cycle, tagging it as belonging to a different (attacker-chosen) cycle. Every subsequent honest vote for that key in the intended cycle then fails the `is-novel-aggregate-public-key` equality check and reverts with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY`, permanently blocking that key from ever being approved for the target cycle.

### Finding Description
`vote-for-aggregate-public-key` in `stackslib/src/chainstate/stacks/boot/signers-voting.clar` (lines 143-199) lets any registered signer for a reward cycle cast a vote, gated only by: [1](#0-0) 
which verifies caller identity via `get-signer-weight`, but places **no minimum-weight requirement** on who may cast a vote — any signer, however small their slot allocation, can call it.

The uniqueness guard is: [2](#0-1) 
```
(define-read-only (is-novel-aggregate-public-key (key (buff 33)) (reward-cycle uint))
    (is-eq (default-to reward-cycle (map-get? used-aggregate-public-keys key)) reward-cycle))
```
and it is enforced in the voting function: [3](#0-2) 

Crucially, `(map-set used-aggregate-public-keys key reward-cycle)` is executed on **every** call that passes the asserts, not only on the vote that crosses the 70% weight threshold: [4](#0-3) 

Because signers coordinate the DKG-generated aggregate public key off-chain before submitting votes, the exact 33-byte key value that the honest majority intends to vote for in reward cycle `N` is knowable in advance — either because the attacker is themselves a signer participating in the DKG round, or because the first honest vote transaction for cycle `N` is visible in the mempool before it is mined. An attacker (a signer with minimal weight, unprivileged beyond ordinary signer registration) can front-run this by submitting a single cheap transaction:

`vote-for-aggregate-public-key(attacker_index, K, round=0, reward_cycle = N+1)`

targeting the *same key bytes* `K` but declaring it for a different (e.g. future) reward cycle `N+1`. This call succeeds (no relationship is asserted between `K` and `N+1`, since the key value is arbitrary attacker input) and sets `used-aggregate-public-keys[K] = N+1`.

From that point forward, **every** honest signer's vote for `(K, N)` — the correct pairing — fails `is-novel-aggregate-public-key`:
`(default-to N (map-get? used-aggregate-public-keys K))` now returns `N+1`, and `is-eq N+1 N` is `false`, so `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY` is returned and the vote reverts. This mirrors the reported bug class exactly: a strict equality check computed at call time (`is-eq` on a value an attacker can move) is broken by an attacker's minuscule, cheap transaction, causing subsequent legitimate transactions relying on the unmoved value to revert deterministically — the on-chain analogue of `RepayExceedsDebt`/`DebtChanged`.

### Impact Explanation
This is a minority-triggerable divergence in a signer-boot-contract consensus mechanism: any single low-weight signer can permanently deny the correct aggregate key from ever being approved for its intended reward cycle, since `used-aggregate-public-keys` entries are never cleared or corrected once poisoned. The signer set is forced into an additional DKG round to generate a brand-new key (round-limited but repeatable — the attacker can repeat the poisoning on every subsequent DKG candidate key it can observe/predict before it lands on-chain), which stalls convergence on the reward cycle's aggregate public key. Given that the `.signers-voting` contract is explicitly in-scope ("the signer boot contracts") and the described mechanism is used to establish the reward cycle's aggregate key (consumed via `get_aggregate_public_key_pox_4` and integrated into Nakamoto's signer-set/reward-cycle bookkeeping in `stackslib/src/chainstate/nakamoto/signer_set.rs`), this fits the "High" bucket: a minority-triggerable divergence bounded to griefing/stalling consensus-relevant signer coordination for a cycle, not a chain split by itself, but a genuine denial of the intended protocol outcome that requires no majority collusion, no admin key, and no other party's key — only a single registered signer's ordinary transaction.

### Likelihood Explanation
Likelihood is non-trivial but requires the attacker to be a registered signer for the affected reward cycle (any weight suffices) and either participate in the off-chain DKG ceremony to learn the target key ahead of time, or observe an honest signer's `vote-for-aggregate-public-key` transaction in the mempool and front-run it with a higher-fee transaction for the wrong cycle number. As the original C4 report itself notes, this class of exploit requires MEV-style front-running, which is a realistic capability on Bitcoin/Stacks-adjacent tx-pool observation but not something a completely passive minority can pull off without active monitoring and rebroadcast timing.

### Recommendation
- Scope `used-aggregate-public-keys` uniqueness checks by `(key, reward-cycle)` pair intent, or require that the `reward-cycle` argument supplied in a vote matches the caller's currently active/voting reward cycle (already partially enforced via `is-in-voting-window`, but that check is not applied before the `used-aggregate-public-keys` write).
- Only write to `used-aggregate-public-keys` once a key has actually reached consensus (i.e., inside the `map-insert aggregate-public-keys reward-cycle key` success branch), rather than unconditionally on every vote, so that a losing/no-consensus round cannot permanently squat on a key value for an unrelated cycle.
- Consider gating vote submission by minimum signer weight or adding a stake/bond to raise the cost of griefing votes.

### Proof of Concept
1. Off-chain, the legitimate signer set for reward cycle `N` completes DKG and agrees on aggregate key `K`.
2. Before honest signers' `vote-for-aggregate-public-key(idx, K, 0, N)` transactions confirm, attacker (any registered signer for cycle `N+1`, arbitrarily small weight) submits and gets mined first:
   `vote-for-aggregate-public-key(attacker_idx, K, 0, N+1)`
   This succeeds and sets `used-aggregate-public-keys[K] = N+1`.
3. Every subsequent honest vote `vote-for-aggregate-public-key(idx, K, 0, N)` now evaluates `is-novel-aggregate-public-key(K, N)` → `is-eq N+1 N` → `false`, and reverts with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY`.
4. The reward cycle `N` can never approve `K` as its aggregate key; the signer set must run a fresh DKG round, which the attacker can repeat against.
