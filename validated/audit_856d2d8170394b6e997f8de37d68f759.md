This confirms a concrete, already-known analog: a malicious/unprivileged contract can deliberately size its `value_return` or `promise_return` data so that the resulting receipt's `output_data_receivers` are appended *after* the size check in `validate_receipt` (`ValidateReceiptMode::NewReceipt`), producing a `Receipt` whose borsh-encoded size exceeds `max_receipt_size` while bypassing rejection. This is tracked as a known bug (nearcore issue #12606) and is explicitly the same bug class as the report: return-data size is checked, but late mutation of the receipt (appending `output_data_receivers`) is not re-validated, so an attacker-controlled contract can create an oversized receipt that is accepted into the chain.

### Title
Unbounded receipt growth after size validation lets an unprivileged contract create/forward oversized receipts, forcing an unsafe silent size-clamp workaround in cross-shard forwarding - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/congestion_control.rs`)

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` checks a newly created receipt's borsh-encoded size against `max_receipt_size` [1](#0-0) . However, after this check runs (during `value_return`/`promise_return` processing), the runtime appends `output_data_receivers` onto the already-validated receipt in `process_action_receipt` (`runtime/runtime/src/lib.rs`), growing it past the checked size without any subsequent re-validation [2](#0-1) . Any account can trigger this by calling a contract it controls that returns data sized right at `max_length_returned_data`/`max_receipt_size` and chaining a `.then()` callback, causing the resulting receipt to exceed `max_receipt_size` post-validation.

### Finding Description
The size check the report calls out in VUSD (unbounded/uncapped size of returned data being stored, causing later processing to break) maps directly to nearcore's own documented and currently-open workaround for issue #12606: `ValidateReceiptMode::ExistingReceipt` exists specifically because oversized receipts *are* known to slip through [3](#0-2) . The size check only fires for `ValidateReceiptMode::NewReceipt`, at the point the receipt is first constructed [1](#0-0) , but `output_data_receivers` — populated when the account has a `.then()` callback awaiting this receipt's promise return — are spliced onto the receipt's action list afterward [2](#0-1) . The runtime's own cross-shard forwarding logic (`try_forward` in `congestion_control.rs`) has to special-case and silently clamp any receipt whose size exceeds `max_receipt_size` down to `max_receipt_size` purely "to avoid receipts getting stuck," explicitly citing issue #12606 [4](#0-3) . This is a state-witness/size-limit invariant violation reachable purely by an unprivileged transaction signer deploying and calling their own contract — the same "unbounded returned-data size breaks downstream processing" root cause as the VUSD report, just realized in nearcore's receipt/size-limit machinery instead of Solidity's `returndata` copy.

### Impact Explanation
An oversized receipt that bypasses `max_receipt_size` can exceed the sizing assumptions that the entire `ChunkStateWitness` budget (~21 MiB total, documented in `docs/misc/state_witness_size_limits.md`) is built on [5](#0-4) . `max_receipt_size` is a *hard limit* that the witness-size model assumes is always enforced; an accepted receipt above that limit inflates witness size beyond the design bound and forces defensive, silent size-clamping logic in bandwidth-limited cross-shard forwarding (`try_forward`) that misreports the true size used for admission decisions [4](#0-3) . This is a real, already-acknowledged invalid-state-transition-adjacent bug (nearcore's own test suite marks it as "should be rejected, but currently isn't because of a bug") rather than a hypothetical: [6](#0-5) [7](#0-6) .

### Likelihood Explanation
High — no privileged access is required. Any transaction signer can deploy a contract, call `value_return`/`promise_return` with data sized to hit exactly `max_length_returned_data`/`max_receipt_size`, and chain a callback so `output_data_receivers` gets appended post-validation, as demonstrated by nearcore's own regression tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` [8](#0-7) [9](#0-8) .

### Recommendation
Re-validate receipt size (or reserve headroom for `output_data_receivers` before the initial check) after `output_data_receivers` are spliced onto a receipt in `process_action_receipt`, so `validate_receipt`'s `NewReceipt` size check reflects the receipt's final, post-mutation size before it is accepted, closing the gap that currently forces `try_forward`'s silent clamp workaround.

### Proof of Concept
Nearcore's own test-loop tests already reproduce this: `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` deploy a contract, call methods that return data sized to exactly `max_receipt_size`, chain a `.then()` callback so `output_data_receivers` get appended after size validation, and assert (`assert_oversized_receipt_occurred`) that a receipt exceeding `max_receipt_size` is found in the chain despite the intended hard limit [10](#0-9) [11](#0-10) .

            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,

        &account_signer,
