### Title
Failed re-mint on a reverted FUNDS/GAS_AND_PAYLOAD/FUNDS_AND_PAYLOAD outbound permanently aborts the outbound with no reachable rescue path, losing user funds — (File: `x/uexecutor/keeper/outbound.go`)

### Summary
When an outbound cross-chain transfer fails on the destination chain, `handleFailedOutbound` tries to re-mint the bridged PRC20 back to the sender/revert-recipient on Push Chain via `CallPRC20Deposit`. If that re-mint call itself fails, the outbound is marked `ABORTED` and the funds are never restored. Unlike the `INBOUND_REVERT` case (an inbound revert that fails on the source chain), which the `RESCUE_FUNDS` mechanism explicitly recognizes as an eligible recovery scenario, a normal outbound of `TxType_FUNDS` / `TxType_GAS_AND_PAYLOAD` / `TxType_FUNDS_AND_PAYLOAD` whose remint fails is never eligible for rescue, because the rescue-eligibility check for non-CEA inbounds requires an `INBOUND_REVERT` outbound in `REVERTED` status, not a `FUNDS`-type outbound in `ABORTED` status. This is the direct Push Chain analog of the ZetaChain M-08 bug: "funds burned on the source side, revert/re-mint fails, and the CCTX is aborted without any way to redeem the tokens."

### Finding Description
The lifecycle is:
1. A user's inbound is executed successfully on Push Chain (PRC20 minted, payload executed) and a normal outbound (`FUNDS`, `GAS_AND_PAYLOAD`, or `FUNDS_AND_PAYLOAD`) is created via `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:69-91`). Creating this outbound corresponds to burning/withdrawing the PRC20 on Push Chain (per `UniversalGatewayPC` withdraw semantics, documented in `x/uexecutor/README.md:130-136`).
2. UVs broadcast the outbound to the destination chain. It fails there (e.g. reverts, insufficient gas on destination), and UVs vote it as failed via `MsgVoteOutbound`, which is a legitimate, unprivileged, honestly-observed outcome — no malicious validator assumption is required.
3. `handleFailedOutbound` (`x/uexecutor/keeper/outbound.go:99-161`) is invoked. For `FUNDS`/`GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` types it attempts to re-mint the bridged amount back to the sender/revert recipient via `CallPRC20Deposit`: [1](#0-0) 
4. If that `CallPRC20Deposit` call fails (EVM-level revert on the derived call, contract-side condition, or any other failure of the module-originated `DerivedEVMCall`), the code marks the outbound `ABORTED` and returns immediately, **never** setting `Status_REVERTED`: [2](#0-1) 
5. `AbortOutbound` removes the outbound from `PendingOutbounds` and just emits a monitoring event — there is no automatic retry and no state left indicating funds are recoverable: [3](#0-2) 
6. The only funds-recovery backstop in the module is `AttachRescueOutboundFromReceipt` (`x/uexecutor/keeper/create_outbound.go:193-337`). For non-CEA inbounds it requires: [4](#0-3) 
This condition checks specifically for a `TxType_INBOUND_REVERT` outbound in `REVERTED` status. A normal outbound of `TxType_FUNDS`/`GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` that ends in `ABORTED` (as in step 4) never satisfies this predicate — there is no `INBOUND_REVERT` outbound on this UTX at all, because this is an outbound execution failure, not an inbound-revert failure. The CEA branch is also inapplicable (it checks `PcTx[0].Status == "FAILED"`, i.e., a failed deposit, not this scenario).

Consequently, once `handleFailedOutbound`'s re-mint attempt fails for a normal funds-carrying outbound, the resulting `ABORTED` state is a dead end: it is not indexed anywhere for retry, and the `RESCUE_FUNDS` mechanism's eligibility gate structurally excludes it.

### Impact Explanation
The PRC20 tokens were already withdrawn/burned on Push Chain when the (now-failed) outbound was created; the destination-chain execution failed; and the compensating re-mint on Push Chain also failed. The user's tokens are unauthorized-permanently-lost/locked with no on-chain path to reclaim them (matching the "in scope" impact: permanent loss/freezing of user funds due to broken revert accounting). This directly mirrors the ZetaChain M-08 report's core defect: a revert path that can itself fail, aborting the transaction and stranding funds without recourse.

### Likelihood Explanation
Triggering this requires only two ordinary, unprivileged conditions to co-occur: (1) an outbound genuinely fails on the destination chain (common — gas issues, contract reverts, chain congestion), and (2) the subsequent re-mint `DerivedEVMCall` to `CallPRC20Deposit` also fails (e.g., PRC20 contract paused/frozen for that asset, minting cap hit, or any transient EVM-level failure of the module-originated call). Neither condition requires a malicious validator, TSS operator, or admin — both are reachable through the standard, honestly-reported vote-outbound flow. Because the rescue path's eligibility check is hard-coded to look for an `INBOUND_REVERT`-typed outbound specifically, this is a structural gap rather than an edge-case timing issue, making it fully reproducible whenever the remint step fails.

### Recommendation
- In `handleFailedOutbound`, when the re-mint (`CallPRC20Deposit`) fails, do not simply abort silently — either (a) retry via a queued re-mint mechanism, or (b) create/attach a rescue-eligible marker (e.g., synthesize a rescue-eligible outbound entry, or extend `AttachRescueOutboundFromReceipt`'s eligibility check to also treat a `FUNDS`/`GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` outbound in `ABORTED` status — where the re-mint specifically failed — as rescue-eligible).
- Persist enough state on the UTX/outbound (already partially done via `PcRevertExecution.ErrorMsg`) to allow a permissionless or admin-gated retry of the re-mint step specifically, rather than relying solely on the `RescueFundsOnSourceChain` event path which is scoped only to `INBOUND_REVERT`/CEA-deposit-failure scenarios.
- Add an explicit index (analogous to `PendingOutbounds`) for `ABORTED` outbounds pending manual/automated remediation, so operators/users can discover and resolve stuck funds instead of them being invisible after `AbortOutbound` removes the pending-outbound entry.

### Proof of Concept
1. Set up a non-CEA `FUNDS_AND_PAYLOAD` inbound; drive it through quorum so it mints PRC20 and creates a normal `OutboundTx` (`TxType_FUNDS_AND_PAYLOAD`) with `Status_PENDING`, following the same setup pattern as `test/integration/uexecutor/vote_outbound_test.go` (`setupOutboundVotingTest`).
2. Vote the outbound as failed via `MsgVoteOutbound` (as in `TestOutboundVoting`'s "outbound failure triggers revert execution" subtest) to invoke `handleFailedOutbound`.
3. Force `CallPRC20Deposit` to fail during the re-mint attempt (e.g., mock/point the PRC20 contract address at a paused or non-existent contract so the derived EVM call reverts) — this is the same failure class already asserted in `outbound.go:130-137`, which is exercised by unit coverage that only checks it moves to `ABORTED` (`k.AbortOutbound`), not that funds are recoverable.
4. Observe: `outbound.OutboundStatus == Status_ABORTED`, no `INBOUND_REVERT` outbound exists on the UTX.
5. Attempt to call `AttachRescueOutboundFromReceipt` for this UTX (simulate a `RescueFundsOnSourceChain` event as in `test/integration/uexecutor/rescue_funds_test.go`) — it returns the error `"rescue: UTX %s has no reverted inbound-revert outbound"` (per `create_outbound.go:259-261`), confirming there is no path to recover the funds.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}
