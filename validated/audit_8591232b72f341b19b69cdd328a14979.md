This confirms the full chain: `webhookCheck.domain` from the unauthenticated header flows directly into `handler.callback(webhookCheck.topic, webhookCheck.domain, rawBody, webhookId, ...)` [1](#0-0)  and into `ensureValidOfflineSession(params, check.domain)` in the Remix/React Router authenticate flows [2](#0-1) , with no cryptographic binding between the domain header and the HMAC.

### Title
Webhook domain-header spoofing due to HMAC covering only `rawBody`, not `X-Shopify-Shop-Domain`, enabling cross-tenant webhook replay - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`checkWebhooksHeaders` extracts the `X-Shopify-Shop-Domain` header and returns it as trusted `domain` field as long as the HMAC over `rawBody` validates, but the HMAC (computed with the app's single shared `apiSecretKey`) never covers the domain, topic, or webhook-id headers. Because the same `apiSecretKey` is valid for every shop that has installed a given app, any attacker who possesses one legitimately valid `(rawBody, hmac)` pair (e.g., a real webhook delivered to their own shop, or a Notifications test payload) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value naming a victim shop that also uses the app.

### Finding Description
`validateFactory` first runs `validateHmacFromRequestFactory`, which only checks `safeCompare(hmac, createSHA256HMAC(config.apiSecretKey, rawBody))` [3](#0-2) . Once this passes, `checkWebhookHeaders` → `checkWebhooksHeaders` simply reads the `domain`, `topic`, `webhookId`, and `apiVersion` headers verbatim off the request with `getRequiredHeader`, with no cross-check against the HMAC-covered body or any list of shops the app knows about [4](#0-3) .

Because `apiSecretKey` is one static value per app (shared by every installed shop), a valid `(rawBody, hmac)` pair generated for shop A is *also* a mathematically valid pair for any other domain claimed in the header, since the domain is never part of the signed data. This is a legitimate design gap in this library layer: it does not bind the authenticated payload to the shop identity claimed in unsigned headers, and relies entirely on the caller trusting that only Shopify's infrastructure can reach the endpoint — an assumption that does not hold for a public HTTP webhook URL.

Downstream, both consumers of `validate()`/`process()` propagate the unauthenticated `domain` value directly into tenant-scoping logic:
- `packages/apps/shopify-api/lib/webhooks/process.ts` passes `webhookCheck.domain` straight into the registered handler callback as the shop identity [1](#0-0) .
- `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts` uses `check.domain` to call `ensureValidOfflineSession(params, check.domain)`, loading the victim's stored offline access token/session and building an authenticated `admin` client scoped to that victim shop [5](#0-4) .

An attacker who is a legitimate (if unprivileged) merchant of the same multi-tenant app can:
1. Install/observe the app on their own shop and capture a real, valid `rawBody` + `X-Shopify-Hmac-Sha256` pair delivered to their own webhook endpoint (no secret ever needs to leak — this is a legitimately signed pair for *their* tenant).
2. Replay that exact body and HMAC to the app's webhook URL, but with `X-Shopify-Shop-Domain` set to a victim shop's domain (shop domains are typically guessable/public, e.g. `victim.myshopify.com`).
3. `checkWebhooksHeaders` accepts the forged domain since HMAC validation already passed on the body alone.
4. The handler/`ensureValidOfflineSession` loads the victim's session/access token and executes the handler logic (attributed to the victim tenant) using the attacker-controlled (replayed) payload content.

### Impact Explanation
This breaks the session/tenant isolation invariant: a webhook handler executes with an attacker-chosen shop domain and the corresponding victim's stored offline access token/admin client, while the payload content is attacker-supplied (replayed). Depending on the host app's webhook handler logic, this can cause cross-tenant data writes, spurious API calls billed/attributed to the victim shop, or state corruption in the victim's data using the victim's real access token — matching the "cross-tenant session/data access" and "webhook forgery" bounty impact classes.

### Likelihood Explanation
Preconditions: (1) attacker only needs to be an unprivileged, ordinary installer/merchant of the same multi-tenant app (no admin/dev role, no leaked `apiSecretKey`); (2) the app must use shop-specific/registered webhook handlers that key authorization off the `domain` header (a very common integration pattern, as shown by the shipped Remix/Express/React Router helpers); (3) attacker must know or guess a target shop's `.myshopify.com` domain, which is commonly public. Given these, the attack is fully repeatable and requires no MITM, no secret theft, and no non-default configuration — it exploits the default `checkWebhooksHeaders`/HMAC design as shipped.

### Recommendation
Do not treat the `X-Shopify-Shop-Domain` (or topic/webhook-id) header as trusted purely because the body HMAC validates. Options: (a) require host apps to verify the claimed `domain` actually corresponds to a shop for which this exact `webhookId` was expected/registered (e.g., dedupe/bind `webhookId` to the shop it was created for, tracked at subscription time); (b) document explicitly and prominently that `domain`/`topic`/`webhookId` headers are NOT authenticated by the webhook HMAC and that host apps must not use them for authorization without additional binding; (c) consider validating against Shopify's known outbound IP ranges as defense-in-depth, since header/body HMAC alone cannot prove header authenticity.

```ts
// packages/apps/shopify-api/lib/webhooks/__tests__/validate.test.ts (added case)
it('accepts a replayed rawBody+hmac pair for an arbitrary forged domain', async () => {
  const shopify = shopifyApi(testConfig());
  const app = getTestApp(shopify);
  const rawBody = '{"foo": "bar"}';
  const validHmac = hmac(shopify.config.apiSecretKey, rawBody); // legitimately obtained from attacker's own shop delivery

  // Attacker replays same body+hmac but claims a different (victim) shop domain
  const response = await request(app)
    .post('/webhooks')
    .set(headers({hmac: validHmac, domain: 'victim-shop.myshopify.com'}))
    .send(rawBody)
    .expect(200);

  // Currently PASSES as valid=true with attacker-chosen domain — demonstrates the gap.
  expect(response.body.data).toMatchObject({
    valid: true,
    domain: 'victim-shop.myshopify.com',
  });
});
```
Expected (fixed) behavior: `checkWebhooksHeaders`/downstream `ensureValidOfflineSession` should reject this request, or the library should document that `domain` must be independently authorized before being used to select tenant credentials — currently it is accepted with no such binding.
