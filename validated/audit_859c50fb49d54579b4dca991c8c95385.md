## Title
Missing Slippage Protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` allows ratio-manipulation to force users into unfavorable token amounts - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's on-chain bancor-style TRC10 exchange feature exposes `ExchangeInjectContract` and `ExchangeWithdrawContract`, which behave like Pancake Router's `addLiquidity`/`removeLiquidity`: a user specifies the amount of one token, and the protocol computes the paired ("another") token amount from the *current* pool ratio at execution time. Unlike `ExchangeTransactionContract` (the swap path), which carries an `expected` field enforced in `ExchangeTransactionActuator.doValidate()`, neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carries any bound (min/max) on the computed `anotherTokenQuant`. This is the exact bug class described in the external report: no non-zero safe minimum/maximum is enforced, so slippage/ratio-shift protection is entirely absent (strictly worse than Pancake's `amountAMin=0`, since here there isn't even a field to set).

### Finding Description
`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` purely from the exchange pool's live balances at the moment the transaction executes: [1](#0-0) 

The same pattern exists in `ExchangeWithdrawActuator.execute()`: [2](#0-1) 

Both actuators' `doValidate()` methods enforce sanity checks (balance limits, non-zero quant, precision for withdraw) but never compare `anotherTokenQuant` against any caller-supplied bound, because `ExchangeInjectContract` and `ExchangeWithdrawContract` simply don't define such a field: [3](#0-2) 

Contrast this with `ExchangeTransactionContract`, which does carry an `expected` (minimum receive) field, validated in `ExchangeTransactionActuator.doValidate()`: [4](#0-3) 

The ratio used for both inject/withdraw calculations is derived from `firstTokenBalance`/`secondTokenBalance`, which are mutated by every `ExchangeTransactionContract` trade against that same exchange (`ExchangeCapsule.transaction()`): [5](#0-4) 

Because Tron transactions sit in the mempool/pending pool before being packed by a block producer, and ordering within a block is controlled by the packing SR, an attacker (or a colluding/malicious SR) can insert an `ExchangeTransactionContract` trade immediately before a victim's pending `ExchangeInjectContract`/`ExchangeWithdrawContract` to skew `firstTokenBalance`/`secondTokenBalance`, then reverse the trade afterward — a classic sandwich attack. The victim's inject/withdraw is forced to execute against the manipulated ratio with zero ability to bound `anotherTokenQuant`, exactly analogous to a router that always passes `amountAMin`/`amountBMin` as 0.

### Impact Explanation
This is a concrete accounting/economic-loss vulnerability reachable by any unprivileged user:
- On `ExchangeInject`, a victim depositing token A can be forced to have far more of paired token B debited from their account than they anticipated when they signed the transaction (`accountCapsule.reduceAssetAmountV2`/`setBalance` for `anotherTokenQuant` in `ExchangeInjectActuator.execute`), because the amount is computed only at execution time against a manipulated ratio.
- On `ExchangeWithdraw`, a victim withdrawing token A can receive far less of paired token B than expected, since `anotherTokenQuant` credited back is likewise computed post-manipulation.
- The attacker profits by trading against the skewed pool before reversing, capturing the value the victim overpaid or under-received — a direct funds-loss/accounting impact on an unprivileged, publicly reachable actuator path.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation only requires the ability to submit an `ExchangeTransactionContract` transaction and have it ordered adjacent to the victim's pending `ExchangeInjectContract`/`ExchangeWithdrawContract` — achievable via mempool front-running or trivially by any block-producing SR who can freely order transactions within their own produced block. No privileged role or internal/mocked-only condition is required; both contract types are standard user-facing wallet API calls (`/wallet/exchangeinject`, `/wallet/exchangewithdraw`) with no trusted-role gate beyond needing to be the exchange's creator for withdraw (still an ordinary account, not a privileged system role).

### Recommendation
Add an `expected`/bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), e.g. `expected_another_token_quant_min` for inject and `expected_another_token_quant_max`/`min` for withdraw, and enforce it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` by comparing the computed `anotherTokenQuant` against the caller-supplied bound and throwing `ContractValidateException` if violated — the same pattern already used for `ExchangeTransactionContract`.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim specifying `tokenQuant` of token A for exchange `exchangeId`, expecting `anotherTokenQuant` of token B to be debited based on the pool ratio at signing time.
2. Attacker submits (or, as a colluding SR, orders first) an `ExchangeTransactionContract` trade against the same `exchangeId` that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for the victim (per `ExchangeCapsule.transaction()`), [6](#0-5) .
3. Victim's `ExchangeInjectContract` executes next, and `ExchangeInjectActuator.execute()` recomputes `anotherTokenQuant` from the now-skewed balances, debiting significantly more token B from the victim than they intended, [7](#0-6) .
4. Attacker submits a reverse `ExchangeTransactionContract` trade to restore the ratio and realize the profit extracted from the victim's forced over-deposit. No validation in `doValidate()` prevents this because no min/max bound field exists on `ExchangeInjectContract`, [8](#0-7) .

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
