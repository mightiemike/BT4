### Title
No slippage/minimum-output protection on `ExchangeInjectContract` and `ExchangeWithdrawContract` (unlike `ExchangeTransactionContract`) - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-asset amount (`anotherTokenQuant`) purely from the live TRC10 exchange pool ratio at validate/execute time, with no user-supplied minimum/expected bound analogous to the `expected` field that `ExchangeTransactionContract` already implements. This is the same class of bug as the reported SafEth `stake()` missing `minMintAmountOut`: the ratio used to compute the amount deposited/received can move between the time the transaction creator builds/signs the transaction and the time it is actually validated and packed into a block, exposing the exchange creator to unbounded, unprotected slippage.

### Finding Description
`ExchangeTransactionContract` (a normal DEX-style swap on TRON's built-in Bancor-style TRC10 exchange) includes an `expected` field that is validated against the actual computed output before the trade executes: [1](#0-0) 

However, the two other exchange-mutating actuators that also compute an amount from the pool ratio — `ExchangeInjectActuator` (add liquidity) and `ExchangeWithdrawActuator` (remove liquidity) — do not have any equivalent field in their protobuf contracts: [2](#0-1) 

In `ExchangeInjectActuator`, `anotherTokenQuant` (the amount of the paired token that will be pulled from the caller's account and injected into the pool) is derived solely from `firstTokenBalance`/`secondTokenBalance` read at validate time and again independently recomputed at execute time: [3](#0-2) [4](#0-3) 

There is no check bounding `anotherTokenQuant` against any value the account owner actually intended — only a `> 0` sanity check and balance-sufficiency checks: [5](#0-4) 

Similarly, `ExchangeWithdrawActuator` computes `anotherTokenQuant` (the amount of the paired token returned to the withdrawer) from the live pool ratio, and only checks for rounding "precision" between two computation methods — not a price/ratio bound versus attacker-observable trades: [6](#0-5) [7](#0-6) 

Both `ExchangeInjectContract` and `ExchangeWithdrawContract` are ordinary transactions broadcastable by any TRC10-exchange-creator account (the only "privilege" check is `getCreatorAddress()`, which is just whichever account created that particular exchange — not a system-privileged role): [8](#0-7) [9](#0-8) 

Because `ExchangeTransactionContract` trades (which any unprivileged account can broadcast) directly move `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()`: [10](#0-9) 

the pool ratio used by Inject/Withdraw is trivially moved by anyone observing the mempool or simply trading against the pool between the time the exchange creator signs their Inject/Withdraw transaction and the time it is packed into a block.

### Impact Explanation
The exchange creator has no way to bound the counter-asset amount pulled from (Inject) or paid to (Withdraw) their account. An attacker who sees a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction in the network (or who simply trades opportunistically) can shift the pool ratio with `ExchangeTransactionContract` calls executed in the same or a preceding block, causing:
- Inject: the creator's account is drained of a larger amount of the counter token than intended for the same amount of the primary token injected, effectively donating value to whoever moved the ratio.
- Withdraw: the creator receives less of the counter token than they expected based on the ratio observed when they built the transaction.

This is direct, unrecoverable asset/accounting loss for the affected account, reachable purely through normal broadcast transactions with no privileged access required — matching the SafEth `stake()` slippage bug class, but on TRON's native TRC10 exchange rather than an ERC20 staking vault.

### Likelihood Explanation
Likelihood is moderate: the attack requires exchange trading activity (or an actively watching adversary) between transaction construction and block inclusion, similar to standard AMM front-running/sandwich conditions, which are well understood and commonly exploited on TRON's TRC10 exchange given transactions sit briefly in the mempool before block packing.

### Recommendation
Add a user-supplied minimum/maximum bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and validate the freshly computed `anotherTokenQuant` against it in `doValidate()`/`execute()` of `ExchangeInjectActuator` and `ExchangeWithdrawActuator`, rejecting the transaction if the computed amount falls outside the caller-specified tolerance.

### Proof of Concept
1. Exchange creator holds a TRC10 exchange pool with ratio R = firstTokenBalance/secondTokenBalance, and constructs an `ExchangeInjectContract` transaction intending to inject `tokenQuant` of the first token, expecting to also spend approximately `tokenQuant * R` of the second token (per `ExchangeInjectActuator.execute` lines 71-83).
2. Before this transaction is packed into a block, any unprivileged account broadcasts one or more `ExchangeTransactionContract` trades against the same `exchange_id`, shifting `firstTokenBalance`/`secondTokenBalance` (via `ExchangeCapsule.transaction()`), which changes R substantially.
3. When the creator's `ExchangeInjectContract` is finally validated/executed, `anotherTokenQuant` is recomputed from the now-shifted balances (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java` lines 215-227 and 71-83), causing the creator to spend a materially different (larger) amount of the second token than intended, with no `expected`/minimum check to reject the trade — unlike `ExchangeTransactionActuator`, which would reject via the `tokenExpected` check at lines 217-221.
4. The same scenario applies symmetrically to `ExchangeWithdrawActuator`, where the withdrawer can receive a materially smaller `anotherTokenQuant` than anticipated, bounded only by a rounding-precision check (lines 228-243), not a price/slippage check.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
