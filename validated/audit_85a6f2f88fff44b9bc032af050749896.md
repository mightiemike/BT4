### Title
Sybil sender rotation bypasses per-sender rate limiting and exhausts the shared global token bucket, causing gateway DoS - ([File: core/services/functions/connector_handler.go])

### Summary
`functionsConnectorHandler.HandleGatewayMessage` gates every `secrets_set`/`secrets_list`/`heartbeat` request behind `h.allowlist.Allow(fromAddr)` and `h.rateLimiter.Allow(body.Sender)`, but the rate limiter keys its per-sender token bucket by the attacker-controlled `body.Sender` string while sharing a single global token bucket across all senders. An attacker who cheaply mints fresh ECDSA keys per request never gets throttled by the per-sender bucket (each new key starts with a full bucket), yet every request still debits the shared global bucket, letting a Sybil flood exhaust `GlobalRPS`/`GlobalBurst` and deny service to legitimate senders sharing that same bucket.

### Finding Description
`HandleGatewayMessage` derives `fromAddr` directly from the unauthenticated (but signature-verified) `body.Sender` field and calls `h.allowlist.Allow(fromAddr)` then `h.rateLimiter.Allow(body.Sender)` before any business logic runs: [1](#0-0) . The underlying rate limiter (chainlink-common `pkg/ratelimit.RateLimiter`, mirrored in this repo's `core/services/workflows/ratelimiter/ratelimiter.go`) maintains one global `rate.Limiter` shared by all callers and a per-sender map keyed by the `sender` string, creating a brand-new full-burst limiter the first time a given sender string is seen: [2](#0-1) . Because `body.Sender` is just a hex address string chosen by the caller (any address for which the caller can produce a valid signature, i.e., any freshly generated ECDSA keypair — free to create), an attacker can present a new `Sender` value on every request. Each new sender gets its own fresh `PerSenderBurst` allowance, so the per-sender check almost never denies the attacker, while every accepted request still consumes one token from the single shared `global` limiter. Once `GlobalBurst`/`GlobalRPS` is exhausted by the attacker's flood, `rl.global.Allow()` (or the combined `Allow` in the connector handler) returns false for everyone, including legitimate DON participants and legitimate Functions users sending `secrets_set`/`secrets_list`/heartbeat requests through the same handler instance. The `OnchainAllowlist` check (`h.allowlist.Allow(fromAddr)`) does not stop this when disabled or configured permissively, as the precondition states; and even with an allowlist active, any address that is on it (attacker-controlled but permitted) can still perform this Sybil rotation exploiting only the rate limiter's shared global bucket versus per-identity bucket split.

### Impact Explanation
This yields denial of service against the Functions gateway/DON connector handler: legitimate node/user requests for `secrets_list`, `secrets_set`, and `heartbeat` get silently dropped (`h.lggr.Errorw("request rate-limited", ...); return nil`) once the shared global bucket is drained by attacker-controlled traffic, without any corresponding cost or persistent penalty to the attacker who simply rotates identities. This matches the "Gateway/DON denial of service" impact category — availability degradation of Chainlink Functions off-chain secrets/heartbeat delivery for all tenants sharing the same gateway connector handler instance, not just the attacker.

### Likelihood Explanation
Feasibility is high under the stated preconditions (allowlist disabled/permissive): generating an ECDSA keypair is computationally cheap, requires no on-chain transaction or balance, and each new address automatically gets a full `PerSenderBurst` allowance from the rate limiter's lazy-init map. The attack is trivially repeatable and scales linearly with the number of distinct sender addresses used, bounded only by attacker request throughput, not by any resource cost. Note that if `PerSenderRPS`/`PerSenderBurst` is configured equal to or greater than `GlobalRPS`/`GlobalBurst` (as seen in some test/default configs, e.g. 100/100/100/100), a single sender can already exhaust the global bucket without needing Sybil rotation at all — in that case identity rotation adds no incremental advantage. The distinct incremental risk described here materializes specifically when `PerSenderRPS/Burst` is configured meaningfully lower than `GlobalRPS/Burst` (the intended, security-conscious configuration), where Sybil rotation is the only way for a single attacker to reach the full global ceiling that would otherwise require many independent legitimate senders.

### Recommendation
Do not rely solely on a caller-supplied `Sender` string as the rate-limit partition key for unauthenticated/low-cost identities. Consider: (1) binding per-sender limiting to a more expensive-to-rotate dimension (e.g., source connection/gateway session, TLS/mTLS identity, or requiring on-chain allowlist/subscription membership before consuming rate-limit budget), (2) reserving a portion of the global budget exclusively for allowlisted/subscribed senders so Sybil traffic from non-vetted addresses cannot starve legitimate quota, and (3) applying a decay/eviction policy plus a cap on the number of distinct per-sender limiter entries tracked, combined with a cost (e.g., minimum-balance check as already used for `secrets_set`) applied before the rate limiter/allowlist check rather than after, for all methods including `secrets_list`.

### Proof of Concept
Integration test plan (extending `core/services/functions/connector_handler_test.go` patterns):
1. Configure `ratelimit.NewRateLimiter(ratelimit.RateLimiterConfig{GlobalRPS: 5, GlobalBurst: 5, PerSenderRPS: 5, PerSenderBurst: 5})` but with allowlist mocked permissive (`allowlist.On("Allow", mock.Anything).Return(true)`).
2. Generate N=50 fresh ECDSA keypairs; for each, sign and send one `secrets_list` `api.Message` with a unique `Sender` via `handler.HandleGatewayMessage`.
3. Assert that after the first `GlobalBurst` (5) accepted requests, `connector.SendToGateway` is invoked with a rate-limited/no-op outcome (or no response at all, matching current silent-drop behavior) for all subsequent distinct-sender requests — i.e., total accepted requests across all 50 unique senders is capped at `GlobalBurst`, not `50 * PerSenderBurst`.
4. In the same test, interleave one legitimate, pre-registered sender's request after the flood and assert it is also denied (`rateLimiter.Allow` returns false), demonstrating cross-tenant DoS impact from Sybil identity rotation.

```go
func (h *functionsConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("failed to decode request", "id", gatewayID, "err", err)
		return nil
	}
	body := &msg.Body
	fromAddr := ethCommon.HexToAddress(body.Sender)
	if !h.allowlist.Allow(fromAddr) {
		h.lggr.Errorw("allowlist prevented the request from this address", "id", gatewayID, "address", fromAddr)
		return nil
	}
	if !h.rateLimiter.Allow(body.Sender) {
		h.lggr.Errorw("request rate-limited", "id", gatewayID, "address", fromAddr)
		return nil
	}
```

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
```
