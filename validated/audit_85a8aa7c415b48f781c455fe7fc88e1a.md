## Finding: Native-position writes silently dropped from persisted `WriteSet` when `HOTNESS_IN_EPILOGUE` is not enabled, independent of `NATIVE_POSITION` gating

### Title
Native-position extension data silently dropped on serialization for `WriteSetV0`, causing replay/restore state divergence - (File: `types/src/write_set.rs`)

### Summary
`WriteSetV0` marks its `hotness` and `extensions` fields `#[serde(skip)]`, so anything stored in those fields is invisible to BCS serialization, storage persistence, and hashing. The only code path that promotes a `WriteSet` to the serializing `WriteSetV1` format is gated exclusively by the `HOTNESS_IN_EPILOGUE` feature flag [1](#0-0) , not by the separate `NATIVE_POSITION` feature that gates whether native-position writes (`Extension::NativePosition`) are produced at all [2](#0-1) . If `NATIVE_POSITION` is enabled while `HOTNESS_IN_EPILOGUE` is not, position data written via `add_native_positions` on an otherwise-`V0` write set is committed to the accumulator hash correctly (since the hash is computed on the in-memory object before this loss), but is dropped the moment the `WriteSet` is serialized — e.g. to `WriteSetDb`, to `TransactionOutput` sent over state sync, or during backup/restore — because `extensions` is `#[serde(skip)]` on the `V0` variant.

### Finding Description
`WriteSetV0` is defined as:
```
pub struct WriteSetV0 {
    value_writes: WriteSetMut,
    #[serde(skip)]
    hotness: BTreeSet<StateKey>,
    #[serde(skip)]
    extensions: Vec<Extension>,
}
``` [3](#0-2) 

`extensions` carries `Extension::NativePosition`, which is populated via `add_native_positions` [4](#0-3)  and later consumed by the storage commit applier through `native_position_iter()`, explicitly documented as "Used by the storage commit applier; main-state consumers never see these entries" [5](#0-4) .

The only place that promotes a write set from `V0` to the serializing `V1` format (`into_v1()`, which preserves `hotness`/`extensions` through serialization [6](#0-5) ) is `DoGetExecutionOutput::convert_write_sets_to_v1`, invoked only when `onchain_config.hotness_in_epilogue()` is true, both in the unsharded and sharded execution paths [1](#0-0) [7](#0-6) .

The developers already recognized that `V0` drops extensions, and defensively require `hotness_in_epilogue` to be on before enabling the root-commitment feature `compute_trading_native_state_roots`:
```
// Requires transaction_info_v1 (the root rides in TransactionInfoV1) and
// hotness_in_epilogue (only the V1 write-set format it enables serializes
// the native-position extensions; V0 drops them, so output-replay would
// diverge). Degrades to off if either is missing.
self.compute_trading_native_state_roots = features.is_compute_trading_native_state_roots_enabled()
    && features.is_transaction_info_v1_enabled()
    && features.is_hotness_in_epilogue_enabled();
``` [8](#0-7) 

However, this gate only protects the *root-hash computation* feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`). It does not gate whether native-position **writes** are produced in the first place — that is controlled by the independent `NATIVE_POSITION` feature flag, described as "Gates native-position writes" [2](#0-1) , with no code found tying its activation to `HOTNESS_IN_EPILOGUE`. If governance enables `NATIVE_POSITION` without also enabling `HOTNESS_IN_EPILOGUE`, the VM can produce a write set carrying `Extension::NativePosition` data that never gets promoted to `V1`, and that data is then silently discarded on serialization to storage or over state-sync wire formats.

### Impact Explanation
This breaks the "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" invariant. The original executing node commits the position write in-memory (state applied to the position DB immediately, before serialization), but once the `WriteSet` round-trips through serialization (persisted to `WriteSetDb`, replayed via `TransactionOutputListWithProof`, or restored from backup), the `extensions` field vanishes. A full node that state-syncs via transaction outputs, replays via the chunk executor, or restores from a backup and replays transactions will fail to reapply the native-position write, producing a native-position ledger state that silently diverges from the originating validator's committed state — a hard-fork-class divergence during replay/restore, matching the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category. Because the accumulator's `state_change_hash` (`TransactionInfo`) is computed from the write set as it exists in memory before this loss and does not itself cover `extensions` in `V0` form, no proof-verification failure is raised — the missing write is undetectable through normal consensus/replay verification.

### Likelihood Explanation
Exploitability depends on governance being able to enable `NATIVE_POSITION` independently of `HOTNESS_IN_EPILOGUE`. I could not find code in this indexed snapshot that couples these two flags together (only `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is coupled to `HOTNESS_IN_EPILOGUE`), nor could I locate the actual VM/native call site that invokes `add_native_positions` — it is likely implemented in the `aptos-vm`/native-function crates that were not surfaced by my searches, so I cannot fully confirm today's exact governance rollout sequence or whether an additional flag coupling exists elsewhere outside the indexed portion of the repository. This uncertainty should be resolved before treating this as confirmed-exploitable in production; the currently observed code strongly suggests the underlying serialization/promotion gap exists, but the feature-flag rollout order needed to trigger it in practice is not fully verifiable from the available code.

### Recommendation
- Couple the `V0`→`V1` promotion (and thus `NATIVE_POSITION`/other extension-writing features) directly to `HOTNESS_IN_EPILOGUE`/`TRANSACTION_INFO_V1` rather than relying on separate, independently-governed feature flags, or refuse to activate `NATIVE_POSITION` unless `HOTNESS_IN_EPILOGUE` is already active.
- Remove the `#[serde(skip)]` on `extensions` (and reconsider it for `hotness`) in `WriteSetV0`, or make `add_native_positions`/native-position write production itself force promotion to `WriteSetV1` at the point of write, so that no execution path can produce a native-position write inside a non-serializing `WriteSet` variant.
- Add a debug-time invariant check (e.g., in `TransactionOutput::ensure_match_transaction_info` or at commit time) that asserts a `WriteSetV0` never carries non-empty `extensions`/`hotness` before being persisted.

### Proof of Concept
Not independently executable from the indexed code alone (the VM call site producing `Extension::NativePosition` was not located in this snapshot). The mechanical proof is:
1. Enable `NATIVE_POSITION` without `HOTNESS_IN_EPILOGUE`.
2. A transaction produces a `WriteSet::V0` with `add_native_positions(...)` populating `extensions`.
3. `DoGetExecutionOutput` skips `convert_write_sets_to_v1` because `onchain_config.hotness_in_epilogue()` is `false` [1](#0-0) .
4. The `WriteSet::V0` is serialized (e.g., `WriteSetDb::put_write_set`, or `TransactionOutput` sent for state sync) — `extensions` is `#[serde(skip)]` and is lost [9](#0-8) .
5. Any node that reconstructs state from the serialized write set (replay, restore, output-based state sync) never reapplies the native-position write, diverging from the originating node.
