### Title
Missing binding check between session-token `dest` and caller-supplied `shop` in `tokenExchange` — (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`tokenExchange()` decodes and cryptographically verifies the session token (signature, `exp`/`nbf`, `aud`) but never checks that the token's `dest` claim (the shop the token was actually issued for) matches the separately supplied `shop` parameter used to build the outbound `/admin/oauth/access_token` request. This is structurally identical to the Monero `SpendProofV1` bug: one value is authenticated (`sessionToken` via `decodeSessionToken`), but a second, independently supplied identifier (`shop`) — never checked for consistency with the authenticated value — is what actually drives the privileged action (target host of the OAuth exchange, and the `shop` recorded on the resulting `Session`).

### Finding Description
In `tokenExchange`, the code is:

```ts
await decodeSessionToken(config)(sessionToken);
...
const cleanShop = sanitizeShop(config)(shop, true)!;
const postResponse = await fetchRequestFactory(config)(
  `https://${cleanShop}/admin/oauth/access_token`,
  { method: 'POST', body: JSON.stringify(body), ... },
);
...
return { session: createSession({ ..., shop: cleanShop, ... }) };
``` [1](#0-0) 

`decodeSessionToken` verifies the JWT's HMAC signature and standard claims (`exp`, `nbf`, `aud`), but its return value is discarded here — the caller-supplied `shop` argument is used verbatim (after only `sanitizeShop` formatting) to build the target URL and to tag the resulting `Session`. [2](#0-1) 

Compare this to `check_tx_proof` in the Monero report, which explicitly asserts `tx_hash == txid` before trusting the fetched data — here there is no assertion that `payload.dest == shop`.

The official documented usage pattern for framework integrations builds `shop` straight from the query string, independent of the session token:

```ts
app.get('/auth', async (req, res) => {
  const shop = shopify.utils.sanitizeShop(req.query.shop, true);
  ...
  await shopify.auth.tokenExchange({ sessionToken, shop, requestedTokenType, expiring });
});
``` [3](#0-2) 

The first-party framework adapters (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) happen to derive `shop` from the decoded token's `dest` before calling `tokenExchange`, so those specific call sites are self-consistent: [4](#0-3) [5](#0-4) 

But `tokenExchange()` itself — the public, documented API surface (`shopify.auth.tokenExchange`) — enforces no such invariant, and the library's own documentation instructs integrators to source `shop` from an unauthenticated, attacker-influenced input (`req.query.shop`) rather than from the verified token payload.

### Impact Explanation
Any integrator following the documented pattern (or any custom framework glue code) can be tricked into calling `tokenExchange` with a `sessionToken` valid for shop A but a `shop` value for shop B (e.g., via a crafted `?shop=` query parameter on the auth route). Because the function does not assert `payload.dest === shop`, the app will:
- POST shop A's session-token-derived `subject_token` to `https://B.myshopify.io/admin/oauth/access_token`, leaking a token bound to tenant A's user to tenant B's endpoint/domain (potential cross-tenant token disclosure to a malicious/typosquatted shop domain the attacker controls via `sanitizeShop`'s myshopify.io suffixing), and
- Tag/store the resulting `Session` under `shop: cleanShop` (B) even though the authentication actually originated from A's token, i.e., session storage keyed on an unverified identifier — the "cross-tenant access / session-storage injection" class of impact.

### Likelihood Explanation
Exploitability depends entirely on how an app wires up the `shop` argument. Any Shopify app author who follows the library's own documented example (`req.query.shop`) or otherwise builds a custom OAuth/token-exchange route is directly exposed, reachable via a single unauthenticated/attacker-crafted query parameter. The maintained framework packages (`shopify-app-express`/`remix`/`react-router`) are not currently affected because they independently derive `shop` from the verified token, but the shared library function that all of them (and any custom integration) call provides no defense-in-depth.

### Recommendation
In `tokenExchange()` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), capture the decoded payload and assert consistency before proceeding:
```ts
const payload = await decodeSessionToken(config)(sessionToken);
const tokenShop = sanitizeShop(config)(new URL(payload.dest).hostname, true);
const cleanShop = sanitizeShop(config)(shop, true)!;
if (tokenShop !== cleanShop) {
  throw new ShopifyErrors.InvalidJwtError('Session token shop does not match requested shop');
}
```
Additionally, update `tokenExchange.md`'s example to derive `shop` from the decoded session token's `dest` claim rather than `req.query.shop`.

### Proof of Concept
1. Obtain a valid, signed session token issued by Shopify for shop A (`dest: https://A.myshopify.io`).
2. Build (or use a custom app that follows the documented pattern) an auth route that reads `shop` from `req.query.shop` and calls `shopify.auth.tokenExchange({ sessionToken, shop: req.query.shop, requestedTokenType })`.
3. Send a request `GET /auth?shop=B.myshopify.io` while presenting the session token for shop A.
4. Observe that `tokenExchange()` does not throw despite `payload.dest` (`A.myshopify.io`) not matching `shop` (`B.myshopify.io`); it proceeds to POST shop A's `sessionToken` as `subject_token` to `https://B.myshopify.io/admin/oauth/access_token` and constructs/stores a `Session` object with `shop: 'B.myshopify.io'`. export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
