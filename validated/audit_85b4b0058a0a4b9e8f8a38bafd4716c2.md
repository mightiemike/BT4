### Title
Multi-sign and memo fees bypass the TransactionFeePool and are always burned, diverting witness-reward funds - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
`consumeMultiSignFee` and `consumeMemoFee` in `Manager.java` charge the fee from the account and then route it either to `burnTrx` (blackhole optimization) or directly to the blackhole account, but they never check `supportTransactionFeePool()`. This is inconsistent with the other two fee-consuming paths in the codebase, `consumeFeeForBandwidth` (`ResourceProcessor.java`) and `payEnergyBill` (`ReceiptCapsule.java`), both of which check `supportTransactionFeePool()` first and route the fee into `TRANSACTION_FEE_POOL` (later distributed to witnesses via `payReward`/`mortgageService.payTransactionFeeReward`) before falling back to burn/blackhole. ### Finding Description
This is structurally analogous to the ELFi report: the protocol has a design invariant that all transaction fees should end up in the same accounting bucket (the `TransactionFeePool`, from which witness rewards are later paid via `payReward` in `Manager.java`), just as ELFi expects all position fees to be settled into the `LpPool`. However, one fee-charging code path — multi-sign fees and memo fees — never checks the `ALLOW_TRANSACTION_FEE_POOL` chain parameter and always burns the fee (or sends it to the blackhole address) instead of contributing it to `TRANSACTION_FEE_POOL`: [5](#0-4) [6](#0-5) 

Compare this to the two other fee-consuming paths, which correctly check `supportTransactionFeePool()` first: [3](#0-2) [7](#0-6) 

`consumeMultiSignFee` is invoked whenever a broadcast transaction has more than one signature, and `consumeMemoFee` whenever a transaction carries non-empty `data` (memo). Both are reachable from any ordinary, unprivileged, anonymously-broadcast transaction — no special permission is required to attach multiple signatures or a memo. The fee is always deducted from the sender's balance, but is misrouted to burn/blackhole instead of `TRANSACTION_FEE_POOL`, even when the network has explicitly enabled `supportTransactionFeePool()` — the parameter meant to redirect fee revenue from burn to witness rewards. [8](#0-7) 

### Impact Explanation
When `ALLOW_TRANSACTION_FEE_POOL` is enabled network-wide (a governance decision meant to redirect all transaction fee revenue toward witness rewards instead of burning), multi-sign fees and memo fees still get permanently burned/sent to blackhole rather than distributed to witnesses through `TRANSACTION_FEE_POOL`. This is an accounting/economic-incentive corruption: funds that should flow to the reward pool for SR (super representative/witness) compensation are silently diverted to burn, understating rewards and misrepresenting the network's actual fee-distribution economics. This does not compromise consensus safety or allow theft, but it is a genuine, systemic misallocation of collected fees — the same class of defect flagged in the ELFi report (fees stranded in the wrong pool instead of the pool intended by protocol design).

### Likelihood Explanation
High likelihood of occurrence in practice: any transaction with multiple signatures or a non-empty memo field triggers this code path unconditionally, and these are extremely common transaction types (multi-sig wallets, memos for exchanges/attribution). No attacker action or special conditions are needed — it happens automatically on every qualifying transaction once `ALLOW_TRANSACTION_FEE_POOL` is active.

### Recommendation
Make `consumeMultiSignFee` and `consumeMemoFee` consistent with `consumeFeeForBandwidth`/`payEnergyBill`: check `dynamicPropertiesStore.supportTransactionFeePool()` first and call `addTransactionFeePool(fee)` in that case, falling back to `burnTrx`/blackhole only when the transaction fee pool feature is not enabled.

### Proof of Concept
1. Enable `ALLOW_TRANSACTION_FEE_POOL` via governance proposal (`ProposalService.process`, case `ALLOW_TRANSACTION_FEE_POOL`). [9](#0-8) 
2. Broadcast an ordinary transaction with two signatures (multi-sig) or a non-empty `data`/memo field from any account.
3. Observe `consumeMultiSignFee`/`consumeMemoFee` execute: the fee is deducted from the sender, and — because neither method checks `supportTransactionFeePool()` — the fee is sent to `burnTrx`/blackhole instead of `addTransactionFeePool`. [10](#0-9) 
4. At block-close, `payReward` distributes only the (now understated) `TRANSACTION_FEE_POOL` balance to the witness, confirming those fees never reach the reward pool as intended by the enabled parameter. [11](#0-10)

  public void consumeMultiSignFee(TransactionCapsule trx, TransactionTrace trace)
      throws AccountResourceInsufficientException {
    if (trx.getInstance().getSignatureCount() > 1) {
      long fee = getDynamicPropertiesStore().getMultiSignFee();
      boolean disableJavaLangMath = getDynamicPropertiesStore().disableJavaLangMath();
      List<Contract> contracts = trx.getInstance().getRawData().getContractList();
      for (Contract contract : contracts) {
        byte[] address = TransactionCapsule.getOwner(contract);
        AccountCapsule accountCapsule = getAccountStore().get(address);
        try {
          if (accountCapsule != null) {
            adjustBalance(getAccountStore(), accountCapsule, -fee, disableJavaLangMath);

            if (getDynamicPropertiesStore().supportBlackHoleOptimization()) {
              getDynamicPropertiesStore().burnTrx(fee);
            } else {
              adjustBalance(getAccountStore(), this.getAccountStore().getBlackhole(), +fee,
                  disableJavaLangMath);
            }
          }
        } catch (BalanceInsufficientException e) {
          throw new AccountResourceInsufficientException(
              String.format("account %s insufficient balance[%d] to multiSign",
                  StringUtil.encode58Check(address), fee));
        }
      }

      trace.getReceipt().setMultiSignFee(fee);
    }
  }

  private void payReward(BlockCapsule block) {
    WitnessCapsule witnessCapsule =
        chainBaseManager.getWitnessStore().getUnchecked(block.getInstance().getBlockHeader()
            .getRawData().getWitnessAddress().toByteArray());
    if (getDynamicPropertiesStore().allowChangeDelegation()) {
      mortgageService.payBlockReward(witnessCapsule.getAddress().toByteArray(),
          getDynamicPropertiesStore().getWitnessPayPerBlock());
      mortgageService.payStandbyWitness();

      if (chainBaseManager.getDynamicPropertiesStore().supportTransactionFeePool()) {
        long transactionFeeReward = floorDiv(
            chainBaseManager.getDynamicPropertiesStore().getTransactionFeePool(),
                Constant.TRANSACTION_FEE_POOL_PERIOD,
            chainBaseManager.getDynamicPropertiesStore().disableJavaLangMath());
        mortgageService.payTransactionFeeReward(witnessCapsule.getAddress().toByteArray(),
            transactionFeeReward);
        chainBaseManager.getDynamicPropertiesStore().saveTransactionFeePool(
            chainBaseManager.getDynamicPropertiesStore().getTransactionFeePool()
                - transactionFeeReward);
      }
    } else {
      byte[] witness = block.getWitnessAddress().toByteArray();
      AccountCapsule account = getAccountStore().get(witness);
      account.setAllowance(account.getAllowance()
          + chainBaseManager.getDynamicPropertiesStore().getWitnessPayPerBlock());

      if (chainBaseManager.getDynamicPropertiesStore().supportTransactionFeePool()) {
        long transactionFeeReward = floorDiv(
            chainBaseManager.getDynamicPropertiesStore().getTransactionFeePool(),
                Constant.TRANSACTION_FEE_POOL_PERIOD,
            chainBaseManager.getDynamicPropertiesStore().disableJavaLangMath());
        account.setAllowance(account.getAllowance() + transactionFeeReward);
        chainBaseManager.getDynamicPropertiesStore().saveTransactionFeePool(
            chainBaseManager.getDynamicPropertiesStore().getTransactionFeePool()
                - transactionFeeReward);
      }

      getAccountStore().put(account.createDbKey(), account);
    }
  }
