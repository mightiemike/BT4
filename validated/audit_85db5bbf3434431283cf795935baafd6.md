### Title
Missing zero-shares check in `deposit` allows depositor funds to be pulled while minting 0 shares - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, and equivalently `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
The `deposit` function in the Zest v0 vault contracts computes `inkind` (shares to mint) via `convert-to-shares-preview`, checks it only against a caller-supplied `min-out` slippage bound, and never asserts `inkind > 0` before pulling the underlying asset and minting shares. By contrast, the sibling `redeem` function in the same contracts explicitly enforces `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. This asymmetry means a deposit whose share calculation rounds down to zero (due to integer division in `mul-div-down`, or because the caller passes `min-out` as `u0`) will proceed: `receive-underlying` pulls the depositor's funds into the vault, `ft-mint? zft u0 recipient` mints zero shares, and `assets` is increased — permanently absorbing the depositor's contribution into the pool without giving them any claim on it.

### Finding Description
In `v0-vault-usdc.clar`'s `deposit`: [1](#0-0) 
the `inkind` value is computed once via `convert-to-shares-preview amount`, then only checked with:
```
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
```
There is no `(asserts! (> inkind u0) ...)` guard. `convert-to-shares-preview` does integer division (`mul-div-down amount ts ta`), which rounds down toward zero, so for a sufficiently small `amount` relative to the pool's `total-assets`/`total-supply` ratio, `inkind` legitimately evaluates to `u0`: [2](#0-1) 

Once `inkind` is `u0`, the deposit still proceeds: the guard `(>= inkind min-out)` trivially passes when `min-out` is `u0` (which is a normal/degenerate input, not attacker-controlled front-running), the underlying is pulled from the depositor via `receive-underlying`, `ft-mint?` mints zero shares, and `assets` is bumped by the deposited amount — silently socializing the depositor's funds to existing shareholders with the depositor receiving nothing in return: [3](#0-2) 

This is the exact bug class from the external report (`sharesToMint` should be checked `> 0`), but here the root cause is purely an internal, single-transaction contract defect — a mutation (`receive-underlying` + `ft-mint?` + `var-set assets`) executed without a guard that should have validated the previously-computed `inkind` value, mirroring the "mutation evaluated before its guard" analog class. Note that the vault tracks `assets` as an internally-updated variable (not via a raw balance read that a donation/self-destruct attacker could inflate), so the front-running/donation vector described in the external report does not apply here; the in-scope defect is the missing zero-shares assertion itself, which the contract's own `redeem` path already recognizes as necessary (`ERR-OUTPUT-ZERO`) but `deposit` omits.

### Impact Explanation
A depositor whose `amount` rounds down to zero shares has their underlying asset permanently transferred into the vault with no corresponding share minted and no revert. This is a permanent loss of the depositor's principal (their funds are absorbed into `assets` and effectively redistributed pro-rata to existing shareholders) — falling under "permanent freezing/loss of funds" for the affected depositor. The likelihood scales with vault total-assets/total-supply ratio (large, mature vaults with high share price make small deposits round to zero) and does not require any adversarial front-running, only a normal deposit call with a `min-out` of `u0` or an amount below the rounding threshold.

### Likelihood Explanation
This can be triggered by any single depositor in a single transaction, without needing another user's interference, provided the vault has accumulated enough assets/shares that `mul-div-down amount ts ta` rounds to `u0` for their chosen `amount`, and they supply `min-out` as `u0` (a common default when a UI doesn't force a nonzero slippage bound, or when a caller integrates directly with the contract). No privileged access, oracle manipulation, or DAO action is required.

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` (mirroring the existing `redeem` guard) to `deposit` in all affected vault contracts (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`) before pulling the underlying asset, so that deposits which would mint zero shares revert instead of silently consuming depositor funds.

### Proof of Concept
1. Vault has accrued significant `assets`/`total-supply` such that the share price (`ta/ts`) is high.
2. A user calls `deposit` with a small `amount` and `min-out` set to `u0`.
3. `convert-to-shares-preview` computes `inkind = mul-div-down amount ts ta`, which rounds down to `u0`.
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes since `u0 >= u0`.
5. `receive-underlying amount account` pulls `amount` of the underlying token from the depositor.
6. `ft-mint? zft u0 recipient` mints zero shares to the depositor.
7. `var-set assets (+ current-assets amount)` — the depositor's funds are now part of the pool, boosting the value of all existing shares, while the depositor holds zero shares and has irreversibly lost `amount`. [4](#0-3)
