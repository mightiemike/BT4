### Title
Reward preview/query logic (`MortgageService.queryReward`) diverges from the mutating `withdrawReward` logic, allowing incorrect validation and reward accounting for delegation rewards - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService` exposes two parallel implementations for computing a voter's delegation reward: `withdrawReward(address)` (state-mutating, used when actually paying out) and `queryReward(address)` (read-only, used to preview the amount). [1](#0-0)  These two methods are supposed to compute the identical reward amount for the same account/cycle state, exactly like NotionalV2's `_mintInternal` vs `previewDeposit` in the referenced report. They do not.

### Finding Description
In `withdrawReward`, there is a guard that does not exist in `queryReward`: [2](#0-1) 

```
if (beginCycle == currentCycle) {
  AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
  if (account != null) {
    return;
  }
}
```

`queryReward` has no equivalent branch for `beginCycle == currentCycle`; it only special-cases `beginCycle > currentCycle` [3](#0-2)  and otherwise falls straight through to the `beginCycle + 1 == endCycle` branch and the final `computeReward(beginCycle, endCycle, accountCapsule)` call using the *current* `accountCapsule.getVotesList()` rather than the vote snapshot recorded for that already-processed cycle. This mirrors exactly the reported bug class: the preview path lacks an edge-case branch present in the mutating path, so it computes the reward using the wrong basis (current votes rather than the cycle's already-recorded snapshot) whenever `beginCycle == currentCycle` and an account-vote snapshot has already been recorded for that cycle.

This preview/query result is not cosmetic — it directly gates a real state-changing actuator: `WithdrawBalanceActuator.doValidate()` uses `mortgageService.queryReward(ownerAddress) <= 0` as the sole check (together with `allowance`) to decide whether the `WithdrawBalanceContract` transaction is allowed to proceed. [4](#0-3)  If `queryReward` reports a nonzero value in a state where the "real" `withdrawReward` would have returned early with 0 additional reward (because a vote snapshot for the current cycle already exists), validation passes based on a value that `execute()`'s call to `mortgageService.withdrawReward(...)` [5](#0-4)  will not actually realize into `allowance`, in the exact same "preview says X shares, mint gives Y" pattern as the Notional issue. `VoteRewardUtil.queryReward`/`withdrawReward` in the TVM native-contract path have the identical asymmetric guard [6](#0-5) , so the same inconsistency is independently reachable from a contract's `withdrawReward()`/reward-query opcode path via `Program.withdrawReward()` [7](#0-6) .

### Impact Explanation
This causes user-facing accounting inconsistency between the amount reported as "claimable reward" and what is actually credited by the state-changing withdraw, on delegation/voting reward accounting reachable by any account issuing a `WithdrawBalanceContract` broadcast transaction or a smart contract invoking the TVM reward-withdraw opcode. It does not itself corrupt validator vote-reward pools' total balances (the underlying `computeReward`/`adjustAllowance` accounting still nets out over subsequent cycles), but it can let `validate()` pass in states where no real reward exists to withdraw, and can present a misleading reward figure to callers who rely on `queryReward` to decide when/whether to withdraw.

### Likelihood Explanation
The `beginCycle == currentCycle` condition combined with a pre-existing `getAccountVote(beginCycle, address)` snapshot is a normal state that can arise in ordinary voting/withdraw cycles (e.g., an account that already had a reward processed earlier in the same cycle then votes again), making this readily reachable through routine `VoteWitnessContract`/`WithdrawBalanceContract` sequences rather than requiring adversarial setup.

### Recommendation
Align `MortgageService.queryReward` (and `VoteRewardUtil.queryReward`) with the exact branch structure of `withdrawReward`, including the `beginCycle == currentCycle` short-circuit when a vote snapshot already exists for the current cycle, so the preview and mutating paths always agree on the computed/reportable reward amount.

### Proof of Concept
Not independently executed; derived purely from static comparison of `MortgageService.withdrawReward` (lines 89-134) against `MortgageService.queryReward` (lines 136-169) and the caller `WithdrawBalanceActuator.doValidate()` (lines 130-133), which I could not run against a live node to confirm the exact numeric divergence — a Devin session with the built codebase would be needed to construct a concrete two-cycle vote/withdraw sequence and diff the returned amounts.

  public long withdrawReward() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawReward", nonce, null);

    WithdrawRewardParam param = new WithdrawRewardParam();
    param.setOwnerAddress(owner);
    param.setNowInMs(getTimestamp().longValue() * 1000);
    try {
      WithdrawRewardProcessor processor = new WithdrawRewardProcessor();
      processor.validate(param, repository);
      long allowance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(allowance);
      }
      return allowance;
    } catch (ContractValidateException e) {
      logger.warn("TVM WithdrawReward: validate failure. Reason: {}", e.getMessage());
    } catch (ContractExeException e) {
      logger.warn("TVM WithdrawReward: execute failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
  }
