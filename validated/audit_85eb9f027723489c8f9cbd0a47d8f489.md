### Title
Silent skip of state-index computation during KV-replay restore when `first_version == 0` or prior usage is unavailable — commit progress advances without state being derived - (File: `storage/aptosdb/src/backup/restore_utils.rs`)

### Summary
`save_transactions_impl` in `storage/aptosdb/src/backup/restore_utils.rs` gates the entire state-index/state-value derivation step (`calculate_state_and_put_updates`) behind an `if` that silently no-ops when `first_version == 0` or when `state_store.get_usage(Some(first_version - 1))` fails, yet unconditionally advances `LedgerCommitProgress`/`OverallCommitProgress` to the last version of the batch regardless of whether state was derived.

### Finding Description
In the `kv_replay` restore path used by `TransactionRestoreBatchController::replay_kv` (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs:553-648`), transactions/write-sets are saved directly to the ledger DB without going through the chunk executor, and state indices (state-by-version key/value entries used to serve authenticated state reads and compute state roots) are derived via `state_store.calculate_state_and_put_updates`: [1](#0-0) 

This call is conditioned on `kv_replay && first_version > 0 && state_store.get_usage(Some(first_version - 1)).is_ok()`. If any of these conditions is false — in particular if `first_version == 0`, or the prior version's storage usage lookup fails for any reason (e.g., not yet populated because a preceding step failed or was skipped) — the whole branch is skipped with no error, warning, or fallback.

Despite skipping state derivation, the function unconditionally writes the transactions, transaction infos, accumulator entries, and raw write sets, and then unconditionally advances the commit-progress markers to `last_version`: [2](#0-1) 

Because `LedgerCommitProgress`/`OverallCommitProgress` are the authoritative markers other code (e.g., DB open/recovery logic, `get_synced_version`, state view construction) uses to decide which versions are "safely committed," advancing them past a range whose per-version state (`StateValueByKeyHashSchema` entries maintained by `put_state_values`) was never populated means later state reads and state-root computations for that range can silently diverge from the write sets that were actually recorded — they would read stale/missing values rather than the true post-write-set state.

### Impact Explanation
If this path is hit in a genuine restore (any restore beginning at genesis, i.e., `first_version == 0`, or any restore where a transient/incomplete previous stage leaves storage-usage lookup failing), the resulting DB will report itself as fully committed up to `last_version` via the commit-progress keys, but will not have live/derived state entries for the affected versions in the state KV database. Any authenticated API response, state-view read, or state-root computation built on that malformed data would be silently wrong — bound to a version whose backing state was never written — rather than failing loudly. This matches the state-commitment/API-binding gate (durable ledger data diverging from the true derived state, authenticated responses bound to an incorrect state at a given version).

### Likelihood Explanation
This code path is only exercised by specific offline restore/replay tooling (`backup-cli` restore, particularly the `kv_replay`/KV-only replay branch), not by normal consensus or execution. Triggering it requires operating this restore tool with `first_version == 0` (a full restore from genesis via this code path) or with a broken/partial precondition that makes the prior-version usage lookup fail; I could not fully confirm from the available index whether current callers (`replay_kv`/`save_transactions_and_replay_kv`, and `force_state_version_for_kv_restore`) ever legitimately invoke this with `first_version == 0`, since I was unable to locate and read the body of `save_transactions_and_replay_kv`/`force_state_version_for_kv_restore` (the grep only found their call sites, not full definitions, due to indexing limits). This uncertainty limits confidence that the bug is reachable in practice with default tooling flows versus being dead/defensive code for an unreachable case.

### Recommendation
- Do not silently skip state derivation: if `kv_replay` is requested but state cannot be derived (e.g., `first_version == 0` needing special genesis handling, or `get_usage` failing), return an explicit error instead of proceeding to advance commit progress.
- Decouple "raw transaction/write-set persisted" progress from "state derived" progress so the two cannot silently diverge, or assert invariants before advancing `LedgerCommitProgress`/`OverallCommitProgress`.
- Add test coverage for `kv_replay` starting at version 0 and for the `get_usage` failure branch to ensure the DB is left in a self-consistent (or clearly failed) state rather than falsely marked as fully committed.

### Proof of Concept
Not independently reproduced end-to-end; conceptual trace based on local code, contingent on the unresolved reachability question above:
1. Invoke the backup-cli transaction restore in `kv_replay`/KV-only mode (`replay_kv`) such that `save_transactions_and_replay_kv` is called with `first_version == 0` (e.g., a from-genesis KV-only replay) — see call site: [3](#0-2) 
2. This flows into `save_transactions` → `save_transactions_impl` with `kv_replay = true`, `first_version = 0`.
3. The `first_version > 0` check in the guard is `false`, so `calculate_state_and_put_updates` (and thus `put_state_values`/state index writes) is never invoked: [1](#0-0) 
4. `LedgerCommitProgress`/`OverallCommitProgress` are nonetheless advanced to `last_version`: [2](#0-1) 
5. Subsequent state reads/proofs at those versions would be served from an incomplete state KV store even though the DB reports itself committed through that version.
