### Title
Inconsistent delegated-resource accounting causes division-by-zero / extreme usage transfer in `UnDelegateResourceActuator` and `UnDelegateResourceProcessor` - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
The reported bug class is a mismatch between a "principal" accounting mapping and the real underlying balance of a receiver, which causes a downstream arithmetic operation (`getEarnings()`) to underflow into a huge, misleading value. The closest reachable analog in java-tron is in the un-delegate-resource logic, where the receiver's `acquiredDelegatedFrozenV2BalanceForBandwidth/Energy` mapping is checked against `unDelegateBalance`, but the "safe" branch's usage-transfer calculation divides by `receiverCapsule.getAllFrozenBalanceForBandwidth()` / `getAllFrozenBalanceForEnergy()` without verifying that value is non-zero, and the two quantities (`acquired...` vs `allFrozenBalance...`) are updated by *different* actuators, so they can legitimately desynchronize.

### Finding Description
In `UnDelegateResourceActuator.execute()` and its TVM equivalent `UnDelegateResourceProcessor.execute()`, when a resource owner un-delegates bandwidth/energy back from a receiver, the code takes one of two branches: [1](#0-0) 

- If `receiverCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth() < unDelegateBalance`, the code takes the defensive branch and resets `acquired...` to `0` — this comment explicitly acknowledges the mapping can be stale relative to the real state ("A TVM contract suicide, re-create will produce this situation").
- Otherwise, it computes `transferUsage` by dividing `receiverCapsule.getNetUsage() * unDelegateBalance` by `receiverCapsule.getAllFrozenBalanceForBandwidth()` (same pattern for Energy with `getAllFrozenBalanceForEnergy()`), with **no check that the divisor is non-zero**.

The same logic is duplicated in the native/TVM path used by contract calls: [2](#0-1) 

The `acquiredDelegatedFrozenV2BalanceForBandwidth/Energy` field and the `allFrozenBalanceForBandwidth/Energy` field are independent pieces of account state that are updated by different code paths (freeze/unfreeze/delegate/undelegate actuators, TVM `suicide2`/contract re-creation, etc.). This is structurally the same bug class as the reported vault issue: a secondary accounting value (here, `acquired...`) is not guaranteed to stay consistent with the real underlying balance (`allFrozenBalance...`), and the code that consumes it (`transferUsage` calculation) assumes consistency without verifying it, performing an unchecked division. If `allFrozenBalanceForBandwidth`/`allFrozenBalanceForEnergy` is `0` while the `acquired...` value still satisfies the `>= unDelegateBalance` guard, the division yields `Infinity`/`NaN`, and casting that to `long` in Java produces `Long.MAX_VALUE`, `Long.MIN_VALUE`, or `0` depending on sign — an extreme, corrupted value that then flows into `receiverCapsule.setNetUsage(...)` / `setEnergyUsage(...)`.

### Impact Explanation
If reachable, this corrupts the receiver account's bandwidth/energy usage tracking with an extreme value, which can:
- Desynchronize resource accounting between owner and receiver, potentially granting or denying resource incorrectly (accounting corruption), and
- Be leveraged for a denial-of-service against the affected account's subsequent resource calculations (bandwidth/energy limit checks), since usage values feed into throttling logic in `BandwidthProcessor`/`EnergyProcessor`.

This is reachable both via a broadcast `UnDelegateResourceContract` transaction (`UnDelegateResourceActuator`) and via a TVM contract call to the native `unDelegateResource` builtin (`Program.unDelegateResource` → `UnDelegateResourceProcessor`), both of which are triggerable by any account, satisfying the "anonymous RPC/broadcast transaction/contract call" reachability requirement.

### Likelihood Explanation
Medium/uncertain — reaching the exact zero-divisor state requires the receiver's `acquiredDelegatedFrozenV2Balance...` to remain `>= unDelegateBalance` while `allFrozenBalance...` is simultaneously `0`. The code's own comment ("A TVM contract suicide, re-create will produce this situation") confirms such desynchronization is a known, occurring scenario in production, but I could not fully trace every code path that mutates `allFrozenBalanceForBandwidth`/`Energy` independently of `acquired...` within the available index, so I cannot state with certainty the precise sequence of transactions that forces the zero-divisor branch. This should be verified with a live repository session (e.g., tracing `AccountCapsule.getAllFrozenBalanceForBandwidth()`/`getAllFrozenBalanceForEnergy()` definitions and every setter of `acquiredDelegatedFrozenV2Balance...`) to construct a concrete PoC transaction sequence.

### Recommendation
Add explicit zero-checks before dividing by `getAllFrozenBalanceForBandwidth()` / `getAllFrozenBalanceForEnergy()` in both `UnDelegateResourceActuator.execute()` and `UnDelegateResourceProcessor.execute()`; if the divisor is `0`, take the same defensive fallback used in the `acquired... < unDelegateBalance` branch (reset the acquired value to `0` and skip usage transfer) rather than performing the unchecked division. More broadly, ensure `acquiredDelegatedFrozenV2Balance...` and `allFrozenBalance...` are updated atomically/consistently wherever a receiver account's resource state can be reset (contract suicide/re-creation, unfreeze, etc.) to prevent this class of stale-mapping inconsistency.

### Proof of Concept
Not fully constructible from the indexed code alone; a concrete PoC requires: (1) delegating bandwidth/energy to a receiver so `acquiredDelegatedFrozenV2BalanceForBandwidth/Energy >= X`, (2) driving the receiver's `allFrozenBalanceForBandwidth/Energy` to `0` through an independent path (e.g., contract suicide followed by account re-creation, as hinted by the existing code comment) without clearing `acquired...`, then (3) issuing `UnDelegateResourceContract`/`unDelegateResource` with `unDelegateBalance = X`, which would enter the else-branch and divide by zero. This sequence should be validated against the full repository (via a Devin session) to confirm reachability and observe the resulting `NetUsage`/`EnergyUsage` corruption, since the exact setters affecting `allFrozenBalanceForBandwidth/Energy` were not fully traceable within the indexed snippets.
