### Title
Fund migration can get permanently stuck in PENDING with no admin recovery, unlike every other ballot-backed workflow — `x/utss` (`InitiateFundMigration`, `VoteFundMigration`, `VoteOnFundMigrationBallot`)

### Summary
`x/utss` implements the same "single in-flight record blocks all new records of that kind" pattern as LimboDAO's current-proposal slot, but for `FundMigration`. Every other ballot-backed state machine in this codebase (`x/uvalidator` ballots, `x/uexecutor` inbound reverts, `x/utss` TSS key processes) has an explicit recovery path for a ballot that never reaches quorum: `RecomputeBallotQuorum`/`MarkBallotExpired` + `RevertStuckInbound` for inbounds, and automatic force-expiry on re-initiation for TSS key processes (`InitiateTssKeyProcess`, lines 22-57). `FundMigration` has none of these. If the underlying fund-migration ballot never reaches the 2/3+1 quorum for either SUCCESS or FAILURE, the `FundMigration` record stays `PENDING` forever and `PendingMigrations` never clears the entry, permanently blocking any new migration for that `(oldKey, chain)` pair.

### Finding Description
`InitiateFundMigration` (`x/utss/keeper/msg_initiate_fund_migration.go:49-63`) hard-rejects a new migration if any `PendingMigrations` entry exists for the same chain: [1](#0-0) 

The only way `PendingMigrations` is cleared is inside `VoteFundMigration`, and only when the underlying ballot actually finalizes to PASSED or REJECTED via `VoteOnFundMigrationBallot`/`CheckIfFinalizingVote`: [2](#0-1) 

The ballot itself is created with `fundMigrationExpiryBlocks = 100_000_000` (effectively "never"): [3](#0-2) 

Compare this with the sibling module `x/uexecutor`, which has a dedicated recovery flow for a ballot that stalls: `RecomputeBallotQuorum` can drive a stuck `PENDING` ballot to `EXPIRED` when the eligible-voter set shrinks to zero, and `RevertStuckInbound` explicitly requires and consumes that `EXPIRED` status to unblock the system: [4](#0-3) [5](#0-4) 

Similarly, `x/utss` TSS key processes have their own self-healing mechanism: any new `InitiateTssKeyProcess` call force-expires a still-active current process before starting a new one, so a stuck keygen/refresh can never permanently block the next one: [6](#0-5) 

`FundMigration` has no analog to either mechanism:
- No code calls `RecomputeBallotQuorum` (or any equivalent) on a fund-migration ballot key.
- Even if an operator manually forced the underlying generic `Ballot` to `EXPIRED` via the generic `MsgRecomputeBallotQuorum`/`MarkBallotExpired` path, nothing reads that back into the `FundMigration.Status` field or removes the entry from `PendingMigrations` — `VoteFundMigration` only transitions status on a PASSED/REJECTED ballot outcome, never on EXPIRED.
- There is no `AbortFundMigration`, `CancelFundMigration`, or equivalent admin message in `x/utss` (confirmed by absence of any `Abort|Cancel|ForceExpire` keeper code in `x/utss`).

Because eligible voters for the fund-migration ballot are recomputed fresh on every vote call via `k.uvalidatorKeeper.GetEligibleVoters(ctx)` (`x/utss/keeper/voting.go:113-119`), ordinary Universal Validator set churn between votes (validators unbonding, being removed from the UV set, or new validators joining and diluting the vote split) can make it impossible for either the SUCCESS or FAILURE branch of the same ballot to ever reach the recomputed 2/3+1 threshold — no malicious action is required, just normal honest-validator lifecycle events landing between votes.

### Impact Explanation
Once a fund migration for a given `(old_key_id, chain)` becomes permanently unfinalizable:
- `PendingMigrations` retains the stale entry forever, so `InitiateFundMigration` will reject every subsequent attempt to migrate funds off the old TSS key for that chain (`"pending migration already exists for chain"`).
- Since fund migration is the only mechanism that moves bridge-custodied funds from a retired TSS key to the current one after a `KEYGEN`, the funds parked under the old key on that chain become permanently unrecoverable through the normal on-chain flow — a form of protocol-level fund freezing with no on-chain remediation path, matching the "stuck state" impact class from the source report.
- This is a genuine denial-of-service/freezing condition, not a network-level DoS, and requires no privileged or malicious actor to trigger — normal UV set churn during an in-flight migration vote is sufficient.

### Likelihood Explanation
Medium. Triggering requires: (1) an admin-initiated fund migration (a normal, expected operational action following a `KEYGEN`), and (2) UV set membership changing between votes such that neither SUCCESS nor FAILURE can reach the recomputed 2/3+1 threshold on the same ballot key. Validator churn (unbonding, tombstoning, lifecycle transitions) is a routine, unprivileged/uncontrolled network condition already handled elsewhere in this codebase specifically because it is expected to happen (see `RecomputeBallotQuorum`'s existence for inbound/outbound ballots). The absence of any equivalent safeguard for fund migrations means the same class of routine event that is explicitly handled for inbound/outbound ballots is left completely unhandled here.

### Recommendation
- Add a fund-migration analog of `RecomputeBallotQuorum` that periodically or on-demand recomputes the eligible-voter set/threshold against the current UV set for any `PENDING` fund-migration ballot, and drives it to a terminal state (e.g., `FUND_MIGRATION_STATUS_FAILED`) when the ballot cannot reach quorum (e.g., when recomputed eligible voters is 0, or when neither branch can mathematically reach threshold).
- Add an admin-gated `MsgAbortFundMigration` (or equivalent) that removes an unfinalizable migration from `PendingMigrations` and marks it `FAILED`, mirroring `RevertStuckInbound`'s role for inbounds, so operators can retry the migration afterward.
- Ensure the recomputation/abort path actually writes back to `FundMigration.Status` and clears `PendingMigrations`, not just the underlying generic ballot record, since `VoteFundMigration` never re-reads ballot status.

### Proof of Concept
Conceptual reproduction (cannot be executed here, but derivable directly from the code paths cited above):
1. Admin calls `InitiateFundMigration(oldKeyId, chain)` after a `KEYGEN`; a `FundMigration` record (`PENDING`) and matching `PendingMigrations` entry are created (`x/utss/keeper/msg_initiate_fund_migration.go:85-110`).
2. Universal Validators start voting via `VoteFundMigration`, which delegates to `VoteOnFundMigrationBallot` (`x/utss/keeper/voting.go:103-160`), recomputing `votesNeeded` from `GetEligibleVoters` on every call.
3. Before quorum is reached for either SUCCESS or FAILURE, the UV set changes (e.g., a UV that already voted becomes unbonded/inactive, or new UVs join), such that the votes already cast can never combine with any future votes to reach `votesNeeded` for either branch (analogous to `ShouldReject`/`ShouldPass` in `x/uvalidator/types/ballot.go:80-91` never being satisfiable given the actual voter dynamics).
4. The ballot never transitions out of `PENDING` (expiry is 100,000,000 blocks away), so `CheckIfFinalizingVote` never fires and `FundMigration.Status` stays `PENDING` forever; `PendingMigrations` entry is never removed.
5. Any subsequent `InitiateFundMigration(oldKeyId2, chain)` (or the same `oldKeyId`) for that chain now fails permanently with `"pending migration already exists for chain"` (`x/utss/keeper/msg_initiate_fund_migration.go:55-58`), and no `x/utss` message exists to clear the stuck entry.
