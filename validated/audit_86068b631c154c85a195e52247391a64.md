This confirms a concrete analog. The HMAC validation for fulfillment-service requests only signs `rawBody` — it never binds the `X-Shopify-Shop-Domain` header into the HMAC computation, as shown in `validateHmacFromRequestFactory` [1](#0-0) . Since the app secret is shared across all shops installed on a given app, any shop can produce a request with a valid HMAC over an attacker-chosen `rawBody`. The `authenticateFulfillmentServiceFactory` handler then trusts the unauthenticated `X-Shopify-Shop-Domain` header value — independent of the HMAC-signed body — to select which shop's offline session/access token gets loaded and handed back as an authenticated `admin` client.

### Title
Fulfillment-service authentication trusts an unsigned shop-domain header to select which tenant's session/access-token is returned - ([File: packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts])

### Summary
`authenticateFulfillmentServiceFactory` validates only the request body's HMAC signature, then reads the shop identity from the `X-Shopify-Shop-Domain` header — a value that is not covered by the HMAC — to load that shop's offline session and mint an authenticated Admin API client.

### Finding Description
The handler performs:
1. `api.fulfillmentService.validate({rawBody, rawRequest})`, which only checks that `hmac(rawBody, apiSecretKey)` matches the `X-Shopify-Hmac-Sha256` header [1](#0-0) .
2. It then independently reads `const shop = request.headers.get(ShopifyHeader.Domain) || '';` from the request headers [2](#0-1) .
3. That attacker-controllable `shop` value is passed straight into `ensureValidOfflineSession(params, shop)` to fetch the shop's offline session, and an `admin` client is built from it [3](#0-2) .

This is structurally the same bug class as the `VaderPoolV2.mintFungible` finding: a caller-supplied identity parameter (`from` in the Solidity report, `shop` header here) is used to select whose privileged resource (LP-token-backed assets there, offline access token / admin session here) gets accessed, without that identity being cryptographically bound to the authenticated proof (the HMAC signature only covers `rawBody`, not the domain header). Contrast this with `authenticateWebhookFactory`, which derives `check.domain` from the value validated internally by `api.webhooks.validate()` rather than reading an independent, unauthenticated header [4](#0-3) .

Because the app's HMAC secret (`apiSecretKey`) is a single per-app secret shared across every shop that installs the app, a legitimate merchant/fulfillment-service holder for Shop A (or anyone who can produce a validly-HMAC'd payload for the app, e.g., by replaying/crafting any accepted body) can send a POST to the fulfillment-service endpoint with `X-Shopify-Shop-Domain` set to Shop B, and the handler will load Shop B's offline session/access token and return an authenticated admin client scoped to Shop B — a cross-tenant session/authorization confusion.

### Impact Explanation
An attacker capable of generating any valid body+HMAC pair for the app (this only requires the shared `apiSecretKey`, not the target shop's own token) can select an arbitrary `shop` domain via a header that is not covered by the signature, and receive back an authenticated Admin API context (with the target shop's offline access token) for that shop. This is a cross-tenant session hijack analogous to the reported "any user-supplied identity used to pull privileged resources" bug in `VaderPoolV2.mintFungible`.

### Likelihood Explanation
Exploitability depends on whether an attacker can obtain any valid `(rawBody, hmac)` pair signed by the app's secret without already possessing legitimate access to the target shop — e.g., by reusing a signature from their own installation's fulfillment-service traffic (since the same `apiSecretKey` is used for HMAC across all shops of the app) while swapping the `X-Shopify-Shop-Domain` header. This is plausible for any actor who is a legitimate merchant/fulfillment partner on one shop of a multi-tenant app and wants to target another shop of the same app — an unprivileged-relative-to-victim attacker.

### Recommendation
Do not source the shop identity from an independently-readable header after only validating the body HMAC. Either:
- Include the shop domain in the HMAC-signed material (bind `shop` cryptographically to the signature), or
- Derive `shop` from data returned/validated by `api.fulfillmentService.validate()` itself (similar to how `webhooks.validate()` returns `check.domain`), rather than reading `ShopifyHeader.Domain` separately in `authenticate.ts`.

### Proof of Concept
1. App is installed on Shop A and Shop B (both share the same `apiSecretKey`).
2. Attacker (a party with fulfillment-service access on Shop A) crafts `rawBody` and computes `hmac(rawBody, apiSecretKey)` — reusable since it only depends on the shared app secret and the body, not the shop.
3. Attacker sends `POST /authenticate/fulfillment_order_notification` with header `X-Shopify-Hmac-Sha256: <valid hmac>` and `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `authenticateFulfillmentServiceFactory` accepts the HMAC as valid (it only checks the body) [5](#0-4) , reads `shop = 'shop-b.myshopify.com'` from the header, loads Shop B's offline session, and returns an authenticated `admin` client for Shop B to the attacker's handler code [3](#0-2) .
