### Title
Validator accepts proposer-supplied L1Handler transaction content without verifying it against the locally recorded message - (File: crates/apollo_batcher/src/transaction_provider.rs)

### Summary
`ValidateTransactionProvider::get_txs` (crates/apollo_batcher/src/transaction_provider.rs:187-224) validates L1Handler transactions received from the consensus proposer by calling `l1_events_provider_client.validate(tx.tx_hash, self.height)`, passing only the `tx_hash` field. If the transaction manager finds this hash validatable, the validator proceeds to include the *proposer-provided* `InternalConsensusTransaction::L1Handler(tx)` object — with all of its fields (`contract_address`, `entry_point_selector`, `calldata`, `nonce`) — directly in the block being built, without ever confirming that these fields match the message actually recorded by the local `TransactionManager`/L1 events scraper.

### Finding Description
`TransactionManager::validate_tx` (crates/apollo_l1_events/src/transaction_manager.rs:116-145) looks up a record purely by `tx_hash` and returns `ValidationStatus::Validated` based on the record's state (pending/staged), never comparing or returning the transaction body. The caller, `L1EventsProvider::validate` (crates/apollo_l1_events/src/l1_events_provider.rs:254-277), also only takes a `tx_hash`.

Crucially, `ValidateTransactionProvider::get_txs` (crates/apollo_batcher/src/transaction_provider.rs:198-222) receives the full `L1HandlerTransaction` object from the network/consensus channel (`tx_receiver`), extracts only `tx.tx_hash` to validate, and — as soon as `l1_validation_status` is not `Invalid` — pushes the **original proposer-supplied `tx` object** into `buffer`, which is returned as-is for block building (`Ok(buffer)`, line 223). There is no code path in this function (or in `TransactionManager`) that fetches the canonical `L1HandlerTransaction` payload stored under that hash and asserts its fields are identical to what the proposer sent.

This mirrors the analog bug class precisely: verification is keyed off a single identifying value (transaction hash / "identifier") while the substantive payload (calldata, contract address, selector, nonce / "token") that will actually be executed and committed to state is taken on faith from an untrusted party (the block proposer).

### Impact Explanation
An L1 handler transaction hash by itself does not commit to the full calldata/address/selector/nonce tuple in the validator's local execution path the way this code is structured — the validator's acceptance decision is entirely hash-keyed. If any component in the pipeline (malicious/buggy proposer, corrupted serialization, a hash-collision-adjacent scenario, or any bug that lets a `tx_hash` be attached to different `L1HandlerTransaction` content across nodes) results in the proposer sending an `L1HandlerTransaction` whose hash coincidentally/maliciously validates but whose body diverges from what other honest validators computed/scraped independently from L1, the batcher will execute the proposer's version of the transaction (different calldata/entry point/contract address) rather than the message that was actually locked/verified via L1 scraping. This can cause:
- Execution of unauthorized/unintended calldata against a contract under the guise of a legitimate L1 message (unauthorized account/contract action).
- Divergence between the committed state root/block hash and what an honest node deriving the transaction content independently would compute (honest-node divergence / wrong committed root).

### Likelihood Explanation
Reachable directly from the standard L1-handler consensus validation path used every time a proposer includes an L1Handler transaction in a block — no special privileges beyond acting as (or spoofing input observed by) a validator are required, and the vulnerable code executes for every L1Handler transaction during block validation. The severity depends on whether `tx_hash` in practice always uniquely commits to content earlier in the pipeline (e.g., during gRPC/consensus deserialization) elsewhere in the stack, which was not verifiable within the available index; if any single upstream check that ties `tx_hash` to `tx` content is missing or bypassable, this is directly exploitable.

### Recommendation
In `TransactionManager::validate_tx`, return (or have the caller cross-check against) the canonical stored `L1HandlerTransaction` payload for the given hash, and in `ValidateTransactionProvider::get_txs`, compare the proposer-supplied transaction fields (or recompute `tx.tx_hash` from the supplied `contract_address`, `entry_point_selector`, `calldata`, and `nonce` via `calculate_transaction_hash`) against the locally scraped record before accepting it into the block. Reject the transaction if the recomputed hash or stored payload does not match what the proposer provided.

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    pub fn validate(
        &mut self,
        tx_hash: TransactionHash,
        height: BlockNumber,

        self.check_height_with_error(height)?;
