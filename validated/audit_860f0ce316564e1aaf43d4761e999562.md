## Title
Name-only deduplication in `AssetIssueActuator` permits permanent token-name squatting with mismatched terms - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
The Salty finding shows that identifying a stateful, disputable object (a DAO ballot) solely by a partial key (its `ballotName`) while ignoring the object's other substantive parameters lets an attacker pre-empt/squat that key with different, malicious terms and block the legitimate object from ever being created. `AssetIssueActuator.validate()` in java-tron contains the same root-cause pattern for TRC10 token issuance: when `AllowSameTokenName == 0`, uniqueness is enforced purely on the asset `name` field, while none of the other economically important fields (`totalSupply`, `url`, `description`, `frozenSupply`, `startTime`/`endTime`, `precision`) are part of the identity check. [1](#0-0) 

### Finding Description
`AssetIssueActuator.validate()` rejects an `AssetIssueContract` only if an asset with the identical `name` bytes already exists in `assetIssueStore`: [1](#0-0) 

No other field of the contract — `totalSupply`, `url`, `description`, `precision`, `frozenSupply`, `startTime`/`endTime` — is included in this uniqueness check, exactly mirroring the Salty root cause where `ballotName` alone gated creation while `address1`, `number1`, `string1`, `string2` were excluded. Any account with enough balance to pay the asset-issue fee can call `AssetIssueContract` — this is an ordinary unprivileged action (it only requires an existing `AccountCapsule`, unlike `ProposalCreateContract` which additionally requires the caller to already be a registered witness): [2](#0-1) 

Once an asset name is taken in this store, there is no delete/expire path analogous to a ballot's finalization — `assetIssueStore` entries persist permanently — so the squat is not just a multi-day DOS window like the Salty ballot case but a permanent block on the legitimate name.

The unit test `assetIssueNameTest` documents the intended behavior "An account can only issue one asset [with that name]," confirming the check is by-name only: [3](#0-2) 

### Impact Explanation
An attacker who observes (front-runs) or simply anticipates a well-known project's intended TRC10 token name can issue their own `AssetIssueContract` with that exact `name` but forged `totalSupply`, `url`, `description`, and vesting/frozen-supply schedule before the legitimate issuer's transaction lands. Because `assetIssueStore.get(name) != null` triggers `"Token exists"` for any subsequent submitter with the same name, the legitimate project's transaction permanently fails, and there is no recovery mechanism — the name is squatted indefinitely with attacker-controlled economic parameters, misleading users who trust the asset name and blocking the real issuer's launch. This is a concrete, unprivileged-actor, no-mocking griefing/DOS impact reachable through a standard public actuator.

### Likelihood Explanation
This legacy path is gated by `dynamicStore.getAllowSameTokenName() == 0`. This flag is a one-way DAO-controlled proposal switch (`ALLOW_SAME_TOKEN_NAME` in `ProposalUtil`/`ProposalService`) that public TRON networks have already flipped to `1` for a long time, at which point uniqueness-by-name is bypassed entirely and tokens are keyed by an internal numeric ID instead. I was unable to fully confirm from the index whether any currently-operating java-tron-based network (including private/consortium/fork deployments that reuse this codebase) still runs with `AllowSameTokenName == 0`; the flag's default and any private deployments' configuration were not resolvable from the available file excerpts. On mainnet/testnet where the flag is already `1`, this specific code path is dead and not exploitable — this significantly limits confirmed real-world likelihood.

### Recommendation
- Remove or fully retire the legacy `AllowSameTokenName == 0` code path from `AssetIssueActuator`, since it is superseded by the ID-based scheme and retains a squattable, no-recourse "Token exists" name check.
- If backward compatibility must be preserved for any private/forked deployment still running with the flag off, extend the uniqueness check (or add a companion check) to compare more of the substantive contract fields, or bind the check to `(name, ownerAddress)` plus a resolution/dispute mechanism, so a mismatched or malicious duplicate cannot permanently block a legitimate issuer.

### Proof of Concept
1. Deploy/operate a java-tron network with `AllowSameTokenName == 0` (legacy mode).
2. Attacker observes (mempool/frontrun) or simply guesses a project's intended TRC10 `name`, e.g. `"PROJECTX"`.
3. Attacker submits `AssetIssueContract{name="PROJECTX", totalSupply=1, url="http://phish.example", ...}` which passes validation because `assetIssueStore.get("PROJECTX") == null` at that point: [1](#0-0) 
4. The legitimate project's later `AssetIssueContract{name="PROJECTX", totalSupply=1_000_000_000, url="https://real.example", ...}` now fails validation with `"Token exists"`, permanently, as reproduced by the existing test pattern: [4](#0-3)
