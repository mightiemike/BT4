### Title
Precision Loss in Legacy Vote-Reward Computation Causes Silent Loss of Small Holders' Rewards - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a super representative's cycle reward using a floating-point ratio (`userVote / totalVote`) multiplied by the total reward and truncated to a `long`. This is structurally the same class of bug as the PirexRewards `(rewardState * userRewards) / globalRewards` issue: when a voter's stake is small relative to the total vote for a witness, the computed per-cycle reward truncates to zero, and because the withdrawal logic advances `beginCycle`/`endCycle` past the settled range regardless of the truncated result, the lost fractional reward can never be recovered.

### Finding Description
The legacy ("old") reward algorithm lives in: [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
```

`voteRate * totalReward` is a `double`; the compound assignment `reward += ...` implicitly narrows the result to `long`, truncating any fractional token amount toward zero. If a voter's `userVote` is small enough relative to `totalVote` (or `totalReward` is small enough), `voteRate * totalReward` can be `< 1.0`, so the truncated contribution for that cycle becomes exactly `0`, and the corresponding fraction of the reward is silently discarded.

This per-cycle computation is invoked from the multi-cycle old-algorithm accumulator: [2](#0-1) 

```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
  if (dynamicPropertiesStore.allowOldRewardOpt()) {
    return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
  }
  long reward = 0;
  for (long cycle = begin; cycle < end; cycle++) {
    reward += computeReward(cycle, votes);
  }
  return reward;
}
```

When `allowOldRewardOpt` is not enabled, the loop calls `computeReward(cycle, votes)` independently *for every single cycle in the range* and truncates each cycle's contribution before summing — so the fractional loss compounds across many cycles instead of only occurring once at final settlement (unlike the newer Vi-based algorithm, which accumulates a `BigInteger` delta over the whole range and only truncates once at the very end via `.divide(...).longValue()`): [3](#0-2) 

Crucially, once `computeReward`/`getOldReward` is invoked for a range `[beginCycle, endCycle)`, the caller unconditionally advances the stored `beginCycle`/`endCycle` pointers regardless of whether the returned `reward` was accurate or truncated to zero: [4](#0-3) 

There is no fallback, no accumulation of the fractional remainder, and no revert if `reward == 0` after a legitimate positive vote existed — the already-earned proportional reward for that cycle is permanently lost the same way Alice's accrued `esGMX` was lost in the PirexRewards report: the ratio-based division rounds to zero and the tracked state (here, the cycle pointer) is advanced past the point of recovery.

The same ratio-truncation pattern also appears in the standby-witness payout path, which is a related but separate reward computation: [5](#0-4) 

### Impact Explanation
Voters (any TRON account holder who freezes TRX and votes for a super representative) with a small vote weight relative to a witness's total votes will have their computed reward for one or more cycles truncate to zero via `computeReward(cycle, votes)`. Because `withdrawReward` (reachable from `WithdrawBalanceActuator`, `VoteWitnessActuator.countVoteAccount`, `UnfreezeBalanceProcessor`, and the TVM `withdrawReward`/`voteWitness` opcodes via `VoteRewardUtil`) always advances the account's `beginCycle`/`endCycle` bookkeeping after computing rewards for a settled range, the truncated (lost) fraction can never be reclaimed in a later call. This is a direct loss-of-funds / reward-accounting-corruption issue for affected accounts, satisfying the "asset or accounting corruption" impact category.

### Likelihood Explanation
This path is reachable by any anonymous broadcast transaction that triggers a reward withdrawal or a vote-clearing on an account whose unclaimed reward range predates `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()` (i.e., accounts that have not withdrawn since before the Vi-based algorithm switch, or during any period where `allowOldRewardOpt` is not enabled). Any voter with a low proportional vote share relative to the witness's total votes will trigger truncation naturally through ordinary use (freeze, vote, wait for cycles, withdraw) — no privileged access or malicious peer is required.

### Recommendation
- Replace the double-based ratio computation in `computeReward(long cycle, List<Pair<byte[], Long>> votes)` with an integer/`BigInteger` based reward-per-vote accumulation consistent with the Vi-based approach already used in `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)`, avoiding per-cycle truncation.
- If exact per-cycle computation must be retained for backward compatibility, track and carry forward the truncated remainder (in a scaled fixed-point representation) so that fractional rewards are not discarded but accumulate until they can be paid out as a whole unit.
- Ensure `beginCycle`/`endCycle` state is only advanced once the corresponding reward has been fully and correctly accounted for, or make truncation errors bounded/negligible by design (as intended by the Vi migration) for all legacy accounts still on the old algorithm.

### Proof of Concept
1. On a chain/testnet where `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()` is greater than the current cycle (or `allowOldRewardOpt` disabled), have witness `SR1` receive a very large total vote (`totalVote`) from many large holders, while `victim` votes a comparatively tiny amount (`userVote`) for `SR1`.
2. Let a cycle pass so `delegationStore.addReward(cycle, SR1, value)` records a reward for `SR1` in `payReward`.
3. Call `mortgageService.withdrawReward(victim)` (e.g., via `WithdrawBalanceContract` or by voting again to trigger `countVoteAccount`).
4. Inside `computeReward(cycle, votes)`, `voteRate = userVote / totalVote` is small enough that `voteRate * totalReward < 1.0`, so the contribution truncates to `0` and is added to `reward`.
5. Regardless of the truncated (zero) result, `delegationStore.setBeginCycle(address, endCycle)` and `setEndCycle(address, endCycle + 1)` advance past the settled cycle — the victim's rightful fractional reward for that cycle is permanently unrecoverable, matching the PirexRewards "rewards computed as zero and subsequently cleared/unrecoverable" bug class.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
