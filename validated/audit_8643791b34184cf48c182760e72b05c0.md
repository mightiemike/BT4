## Finding

### Title
State-checkpoint root hashes are excluded from `TransactionOutput`↔`TransactionInfo` consistency check used in chunk replay/verification - (File: types/src/transaction/mod.rs)

### Summary
The shared consistency check `TransactionOutput::ensure_match_transaction_info` — used by the chunk executor, the replay-verify db-tool, the aptos-debugger, and CLI replay commands to confirm that a locally re-executed transaction produced the output that a peer/backup claims (and that is itself only authenticated via an accumulator proof against a signed `LedgerInfo`) — validates `status`, `gas_used`, `write_set` (via `state_change_hash`) and `event_root_hash`, but explicitly skips the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields carried inside `TransactionInfo`.

### Finding Description
`TransactionInfo` is the accumulator leaf that gets authenticated end-to-end by the transaction accumulator root inside a signed `LedgerInfo` [1](#0-0) . When a chunk of transactions/outputs is replayed (state-sync chunk executor, `db-tool replay-on-archive`, `aptos-debugger`, CLI replay), the code re-executes the transactions locally and calls `ensure_match_transaction_info` to confirm the freshly computed `TransactionOutput` matches the `TransactionInfo` that came with the (proof-verified) chunk [2](#0-1) .

That function checks `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash against `event_root_hash` [3](#0-2) . It never compares the locally-computed state checkpoint / hot-state checkpoint / position-state checkpoint roots against the corresponding fields in the received `TransactionInfo`. The code itself documents this exact gap: [4](#0-3) 

These checkpoint hashes are produced by `DoStateCheckpoint::run`, which folds state updates into a `LedgerStateSummary`/JMT-style root (and, when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is on, a separate "position state" root) and only cross-checks them against caller-supplied `known_state_checkpoints` when such a value is explicitly threaded in [5](#0-4) . In the replay/verify tools that call `ensure_match_transaction_info`, no such cross-check of the checkpoint hash against the *authenticated* `TransactionInfo.state_checkpoint_hash` happens at all — the comparison function used for that purpose simply omits the field.

### Impact Explanation
If the executor's state-checkpoint/hot-state/position-state root computation diverges from the canonical value embedded in the accumulator-authenticated `TransactionInfo` (e.g., due to a state-store bug, a JMT/position-state update bug, or a hard-fork-induced divergence in how state roots are folded), `ensure_match_transaction_info` would still report success as long as the write set, events, gas, and status match. Replay-verify tooling (`db-tool replay-on-archive`) and any restore/verification flow relying on this check could therefore certify a chunk as correctly replayed even though the locally maintained state-checkpoint root has silently diverged from the authenticated ledger state. This is precisely the "authenticated ledger-state divergence goes undetected by the verification path meant to catch it" class of integrity bug this scan is meant to surface — it undermines the guarantee that "committed/derived state must match the correct, proof-bound result."

### Likelihood Explanation
This is not itself an externally triggerable exploit against a running validator — it requires an independent bug in state-root computation to actually produce a divergence. Its significance is that the safety-net designed to catch exactly such divergences (replay-verify / debugger / CLI consistency checks) is known, by the code's own comment, to not check these three hash fields, so any future or existing state-checkpoint computation bug (including one only observable on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-enabled networks) would go undetected by this tooling.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (when V1 / hot-state feature applies), and `txn_info.position_state_checkpoint_hash()` (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` applies) against locally computed checkpoint roots, threading the actual computed state-checkpoint hash into this comparison the same way `write_set`/`event_root_hash` are compared today.

### Proof of Concept
Not applicable as a live exploit — this is a code-audit finding based on the documented gap in `ensure_match_transaction_info` [4](#0-3)  and its call site in the replay-verify tool [2](#0-1) .

**Uncertainty note:** I could not fully inspect `execution/executor/src/chunk_executor/mod.rs` (the file content returned empty in the tool output despite a confirmed grep match for `ensure_match_transaction_info`), so I cannot confirm the exact calling context/gating in the state-sync chunk-executor path (e.g., whether it's used only in a debug/test mode or in the production untrusted-chunk-apply path). This should be verified directly in a full checkout before treating this as conclusively exploitable in the mainnet sync path; the `db-tool` and `aptos-debugger`/CLI call sites are confirmed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
