### Title
Excess attached deposit is not refunded on successful `AddressRegistrar::register`, permanently locking user funds - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `register` method of the `AddressRegistrar` contract (part of the `near-wallet-contract` system used by eth-implicit / wallet-contract accounts on NEAR) only requires `given_deposit >= required_deposit`, but on the success path it consumes the *entire* attached deposit rather than only the `required_deposit` needed to cover storage. Any excess ("dust" or larger) attached by the caller is not refunded, unlike the collision path which does refund the full deposit.

### Finding Description
`register` computes the exact storage cost needed to persist the `address -> account_id` mapping: [1](#0-0) 

It only checks that `given_deposit >= required_deposit` and panics otherwise, but never bounds or refunds the difference. In the success branch (`Entry::Vacant`), the full `given_deposit` is implicitly kept by the contract — there is no promise created to return `given_deposit - required_deposit` to `env::predecessor_account_id()`: [2](#0-1) 

By contrast, the collision branch (`Entry::Occupied`) explicitly creates a transfer promise to refund the *entire* deposit back to the caller because no storage was consumed: [3](#0-2) 

This asymmetry shows the refund logic is inconsistent: the contract is capable of issuing a refund transfer but simply never computes/sends the excess-over-`required_deposit` in the success path. `register` is `#[payable]` and callable directly by any unprivileged account (transaction signer / RPC caller / relayer), and is also invoked internally by the wallet contract's `rlp_execute` flow when an address needs to be checked/registered against a named account, as referenced via `ADDRESS_REGISTRAR_ACCOUNT_ID` in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`.

### Impact Explanation
Any caller (a user directly, or a relayer/wallet-contract acting on a user's behalf) who attaches more NEAR than the exact byte-storage cost to `register` permanently loses the excess — it is retained by the `AddressRegistrar` contract account with no path to reclaim it. Because a wallet-contract-driven registration path composes deposits/fees on behalf of end users (as seen in the wallet contract's cross-contract call flow), a caller supplying a deposit that is not fined to the exact required byte cost (e.g., rounding, safety margin, or a value chosen without knowing the exact per-byte storage price at call time) suffers permanently frozen funds. This matches the "permanently frozen funds" acceptance criterion — it is a concrete, unauthorized-value-retention bug reachable from a single contract call by an unprivileged party.

### Likelihood Explanation
Likelihood is high for any caller who does not compute the exact required deposit off-chain before calling (e.g. attaches a round number like 1 NEAR, or a safety-margin amount), since `storage_byte_cost()` and `account_id.len()` determine an exact, non-round yoctoNEAR value. Since `register` is a public payable method with no owner/admin restriction, this is trivially reachable by any transaction signer.

### Recommendation
In the `Entry::Vacant` success branch, refund the excess deposit the same way the collision branch does: compute `excess = given_deposit.saturating_sub(required_deposit)` and, if non-zero, create a transfer promise back to `env::predecessor_account_id()` for `excess`, keeping only `required_deposit` in the contract.

### Proof of Concept
1. Compute `required_deposit` for a given `account_id` as `storage_byte_cost() * (20 + account_id.len())`.
2. Call `AddressRegistrar::register(account_id)` attaching `given_deposit = required_deposit + 1_000_000` yoctoNEAR (or any amount strictly greater than `required_deposit`) for an address that is not yet registered (hits `Entry::Vacant`).
3. Observe the call succeeds (`Some(address)` is returned, entry inserted), and no transfer/refund receipt is generated back to the caller — the `given_deposit - required_deposit` excess remains permanently in the `AddressRegistrar` contract's balance, contrasted with the `Entry::Occupied` branch at [4](#0-3)  which does issue a full refund transfer.
