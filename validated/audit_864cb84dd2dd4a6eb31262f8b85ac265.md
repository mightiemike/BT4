### Title
Uncaught `TypeError` in `sanitizeHost` when base64 `host` param decodes to an invalid URL authority - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost` only validates that the raw `host` query parameter is syntactically valid base64 via `base64regex`, then unconditionally calls `new URL(`https://${decodeHost(sanitizedHost)}`)` with no surrounding `try/catch`. If the decoded bytes contain characters forbidden in a URL host (e.g. a space, control character, or other forbidden host code point), the WHATWG `URL` constructor throws a `TypeError`, which propagates out of `sanitizeHost` uncaught.

### Finding Description
In [1](#0-0) . `decodeHost` simply calls `atob(host)` with no further validation [2](#0-1) . The decoded string is then interpolated directly into `new URL(`https://${decodeHost(sanitizedHost)}`)` [3](#0-2) , with no `try/catch`. Any base64 payload that decodes to a string containing a character the WHATWG URL host parser rejects (space, control characters, etc.) causes the `URL` constructor to throw a `TypeError: Invalid URL`, and that exception is not caught anywhere in `sanitizeHost`.

This function is reachable directly from an unauthenticated HTTP request: `validateShopAndHostParams` reads `url.searchParams.get('host')` straight from the request and passes it to `api.utils.sanitizeHost(...)` with no prior sanitization [4](#0-3) , and the same pattern exists in the react-router package [5](#0-4) . `validateShopAndHostParams` is called unconditionally for any non-session-token document request inside `authenticateAdmin` [6](#0-5) .

The outer `authenticateAdmin` does wrap the whole flow in a `try/catch`, but that catch block only adds CORS headers when the caught value is a `Response`; for a plain thrown `TypeError` it just rethrows it unchanged [7](#0-6) . So instead of the intended graceful handling for an invalid host (redirect to app-bridge or login, as done via the `if (!host) { ... }` branch), the request bubbles up an unhandled `TypeError` that gets converted into a generic framework error response for that request, bypassing the library's own designed "invalid host" flow.

### Impact Explanation
This is a low-severity, per-request denial-of-service / reliability bug: any single crafted `host` query parameter causes that individual request's `authenticate.admin()` call to throw an unhandled `TypeError` instead of the intended graceful invalid-host handling (redirect to login/app-bridge). It does not crash the whole server process and requires no privileges, matching a "DoS in an authentication handler" class, but scoped to per-request failures rather than a full outage, since each request is independently caught by the surrounding web framework's own error boundary/500 handling.

### Likelihood Explanation
Trivial to trigger: no authentication, no secrets, and no non-default configuration are required. An attacker simply needs to send a GET request to any `authenticate.admin()`-protected route with a `host` query parameter whose value is base64 of a string containing a forbidden host character. This is fully repeatable and deterministic.

### Recommendation
Wrap the `new URL(...)` call in `sanitizeHost` in a `try/catch`, treating a thrown parse error the same as an invalid host (`sanitizedHost = null`, then follow the existing `throwOnInvalid` branch) instead of letting `URL`'s exception propagate uncaught.
