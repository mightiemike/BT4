## Title
Post-validation growth of a receipt above `max_receipt_size` bypasses `validate_receipt`'s size check and can cause an oversized receipt to be admitted into cross-shard forwarding/buffering — (File: `runtime/runtime/src/congestion_control.rs`, `runtime/runtime/src/verifier.rs`)

## Summary
The reported Biconomy bug is a class of "two checks computed over different amounts": a value is validated once at one point (deposit-time check without reward), then a *larger* actual value is checked/used later (transfer-time check with reward included), causing a mismatch that reverts and burns/loses funds. The analogous pattern in nearcore is `Receipt` size validation: `validate_receipt(..., ValidateReceiptMode::NewReceipt)` (`runtime/runtime/src/verifier.rs:681-696`) checks a receipt's borsh-encoded size against `max_receipt_size` **at creation time**, but the receipt's `output_data_receivers` (and thus its final serialized size) can be mutated *after* this validation, in `receipt_manager.rs`, when a later action in the same receipt registers itself as a data receiver. The size check therefore validates a smaller version of the receipt than what is actually forwarded/buffered by the congestion-control/bandwidth-scheduler logic in `runtime/runtime/src/congestion_control.rs`.

## Finding Description
`validate_receipt` is called with `ValidateReceiptMode::NewReceipt` immediately after a new receipt is created inside `apply_action_receipt`, per the spec's own description: "for each action ... on success validate every newly created receipt with `validate_receipt(..., NewReceipt)`" (`runtime/runtime/src/lib.rs:871`, referenced in `protocol-model/spec/runtime-execution.md:67`). This check enforces:

```
runtime/runtime/src/verifier.rs:687-696
if mode == ValidateReceiptMode::NewReceipt {
    let receipt_size: u64 = borsh::object_length(receipt)...;
    if receipt_size > limit_config.max_receipt_size {
        return Err(ReceiptValidationError::ReceiptSizeExceeded { size: receipt_size, limit: ... });
    }
}
```

However, subsequent actions inside the same batch of promises can still append entries to that already-validated receipt's `output_data_receivers` (a cross-contract callback registering a data dependency, via `receipt_manager.rs`). This addition happens *after* the size check has already passed, so the final, on-the-wire receipt can exceed `max_receipt_size` without ever failing `ReceiptSizeExceeded`. This exact mismatch is acknowledged in-repo:

```
test-loop-tests/src/tests/max_receipt_size.rs:124-128
// A function call will generate a new receipt. Size of this receipt will be equal to
// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
```

The consuming code that relies on `max_receipt_size` as an invariant is the congestion-control/bandwidth-scheduler forwarding path, `ReceiptSinkV2::try_forward`:

```
runtime/runtime/src/congestion_control.rs:412-427
// There is a bug which allows to create receipts that are above the size limit. Receipts
// above the size limit might not fit under the maximum outgoing size limit. Let's pretend
// that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
// See https://github.com/near/nearcore/issues/12606
let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
if size > max_receipt_size {
    ...
    size = max_receipt_size;
}
```

This is precisely the same failure mode as the Biconomy bug: one code path (`validate_receipt`, `NewReceipt` mode) checks a value (receipt size) that is smaller than the value actually used later (the real serialized receipt size used in `compute_receipt_size` / `try_forward`), because the receipt is mutated between the two checks. The runtime tries to patch the resulting inconsistency defensively by clamping `size` to `max_receipt_size` for admission-limit bookkeeping, but this clamp is an admitted workaround, not a fix of the root cause — the actual receipt bytes stored/transmitted remain oversized.

## Impact Explanation
An oversized receipt that slips past `validate_receipt`'s `NewReceipt` check can:
- Be pushed into `outgoing_receipts`, `ShardsOutgoingReceiptBuffer`, or the delayed-receipt queue while being byte-accounted as if it were only `max_receipt_size` (the clamp in `try_forward`), understating its true congestion/bandwidth cost and causing `own_congestion_info`/`CongestionInfo` byte accounting to diverge from the receipt's actual trie/wire size.
- Feed size/gas figures into `CongestionInfo` (`receipt_bytes`) that do not match the real bytes stored, which is exactly the kind of cross-node accounting divergence that the "no impact" exclusion rules explicitly want to avoid; here it is directly reachable by an unprivileged contract caller issuing ordinary cross-contract calls (no privileged/validator/network role required), matching the rule that only reachable, transaction-triggered analogs count.
- The repo's own regression tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs:129-267`) confirm oversized receipts are still produced and observed on-chain (`assert_oversized_receipt_occurred`), i.e. this is a live, exploitable path today, not a theoretical one.

This maps to the "invalid state transition acceptance" / accounting-divergence category: a receipt that should have been rejected for exceeding a protocol-defined size limit is instead accepted, stored, and its size subsequently misreported to the congestion-control system that both honest nodes rely on for identical scheduling decisions.

## Likelihood Explanation
High reachability: any account can deploy a contract that issues a `FunctionCall` promise near the size limit and then, in a callback, registers an `output_data_receivers` entry on that already-created receipt (e.g., via `promise_return`/`promise_then` patterns used by `runtime/runtime/tests/test_async_calls.rs` and the exact test scenarios in `max_receipt_size.rs`). No special permissions, validator role, or network position are required — a single unprivileged transaction/contract call is sufficient, matching the reachable-role requirement of the rules (transaction/contract-call/meta-transaction sender).

## Recommendation
Re-validate (or defer validation of) receipt size in `validate_receipt`/`ValidateReceiptMode::NewReceipt` *after* all mutations to a receipt (including `output_data_receivers` appended by later actions in the same batch) are finalized, rather than immediately upon creation, so the exact same value (final on-wire size) is checked and later relied upon by `compute_receipt_size`/`try_forward`/`CongestionInfo` accounting. Until fixed at the root, the `try_forward` clamp workaround should not be treated as sufficient — it only prevents receipts from getting permanently stuck but does not correct the size accounting divergence propagated into `CongestionInfo` and persisted trie queues.

```markdown
### Action receipt execution (`apply_action_receipt`, `runtime/runtime/src/lib.rs:776`)

1. Gather each `input_data_id` from state as a `PromiseResult` and remove it (`runtime/runtime/src/lib.rs:796`); commit prior updates with `ActionReceiptProcessingStarted` (`:825`).
2. Load the receiver account; seed the receipt-level result with the `new_action_receipt` exec fee (`runtime/runtime/src/lib.rs:833`).
3. If `EnforcePerReceiptStorageProofLimit` (v86) is enabled, snapshot `recorded_storage_size_upper_bound` before the receipt so per-receipt storage-proof growth can be bounded (`runtime/runtime/src/lib.rs:838`).
4. **Execute actions in order** (`runtime/runtime/src/lib.rs:848`): for each action compute an `action_hash`, call `apply_action`, and on success validate every newly created receipt with `validate_receipt(..., NewReceipt)` (`:871`). `merge` folds the result; on the first `Err` the loop records the action index and breaks (`runtime/runtime/src/lib.rs:884`).
```
