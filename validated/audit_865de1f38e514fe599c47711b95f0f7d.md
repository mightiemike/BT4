### Title
Bond reward index truncates to zero while `earned` is still deducted from the pool - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`calculate-bond-rewards` in `pox-5.clar` computes a per-bond reward-per-sat accumulator (`accrued-rewards-per-sat`) by integer-dividing `earned * PRECISION` by `total-sats`. When `total-sats` is large relative to `earned`, this division truncates to `u0`, so `rewards-per-token-for-cycle` for that bond is never advanced. However, `earned` is unconditionally subtracted from `available-rewards` in the same call (and folded into `total-bond-rewards`/`last-accounted-rewards-only`), so the sBTC is treated as "distributed" even though no staker's claimable balance (`get-earned`) increases. This is the same root-cause pattern as the referenced LoopFi `_updateRewardIndex()` finding: the "balance" side of the accumulator advances while the "index" side does not, permanently orphaning the truncated reward inside the contract.

### Finding Description
In `calculate-bond-rewards` [1](#0-0) :
```
(total-sats (get-total-shares-staked-for-cycle reward-cycle (some bond-index)))
(available-rewards (get available-rewards accumulator))
(target-yield (/ (/ (* total-sats (get target-rate bond)) u10000) u50))
(earned (if (>= available-rewards target-yield) target-yield available-rewards))
...
(accrued-rewards-per-sat (if (is-eq total-sats u0)
    u0
    (/ (* earned PRECISION) total-sats)
))
```
The accumulator is then bumped by `accrued-rewards-per-sat`: [2](#0-1) 

and the fold returns `available-rewards - earned` to the caller unconditionally [3](#0-2) .

Back in `calculate-rewards`, the aggregate deltas are committed as consumed/accounted regardless of whether any bond's index moved: `total-bond-rewards = gross-accrued-rewards - remaining-rewards`, and `last-accounted-rewards-only` is advanced by `gross-accrued-rewards - reserve-deposit` [4](#0-3) .

So whenever `earned * PRECISION / total-sats == 0` (i.e., `earned < total-sats / PRECISION`), the bond's per-sat reward index (`rewards-per-token-for-cycle`) is not incremented, but `earned` sBTC has already been carved out of `available-rewards` and is accounted for as spent via `last-accounted-rewards-only`. No signer's `get-earned`/`compute-earned-rewards` value changes for that bond (it depends only on `rpt-current - rpt-paid`), so those sBTC tokens become permanently unclaimable — they sit in the contract balance but are excluded from `get-new-rewards` in all future calculations (since `last-accounted-rewards-only` already "consumed" them).

This breaks the equality that should hold between the amount debited from the reward pool and the amount credited to the per-sat accumulator (`sum(earned) == sum(accrued-rewards-per-sat_i * total-sats_i) / PRECISION`), causing a silent, permanent reward loss for bond stakers, analogous to the `_updateRewardIndex()` bug in the LoopFi report where `lastBalance` advances without `index` advancing.

### Impact Explanation
This is a reward-mispayment/loss bug bounded to the sBTC reward pool that accumulates for a given bond over each `calculate-rewards` call in which `total-sats` (bond stake) is large relative to `target-yield`/`earned` per period (e.g. early in a bond's life, low reward rate, or a bond with a very large staked-sats value but modest `target-rate`). Any unprivileged caller can trigger `calculate-rewards` — it is a `define-public` function gated only by `(> calculation-height last-calc)` [5](#0-4)  — so no privileged party or majority is required to realize the loss; it happens on the normal, expected call path once per distribution cycle. The loss is capped to the rounding remainder per calculation and per bond (bounded, not catastrophic), matching the "High: minority-triggerable ... reward mis-payment bounded to fees" impact tier, not a chain split.

### Likelihood Explanation
Likelihood depends on `PRECISION`'s magnitude versus `total-sats` and `earned`/`target-rate`; without confirming the exact `PRECISION` constant value in this snapshot (grep found it defined in `pox-5.clar` but its value was not retrieved before tool budget ran out), I cannot precisely quantify how often `earned*PRECISION/total-sats` rounds to zero in practice. Given `earned = total-sats * target-rate / 10000 / 50` is itself already a nested-truncated computation and `target-rate` is a basis-point APY-like value divided by 500000 total, it is plausible for `earned` to be small relative to `total-sats` at low target rates or early in a reward cycle, making this a realistic occurrence rather than a purely theoretical one — but I could not fully verify the numeric ranges (`PRECISION` value, typical `target-rate`/`total-sats` magnitudes) within the available exploration.

### Recommendation
Compute `delta-index = (/ (* earned PRECISION) total-sats)` first, then redefine the amount actually deducted from `available-rewards` as `(/ (* delta-index total-sats) PRECISION)` rather than the original `earned`. This way, if `delta-index` truncates to zero, no funds are removed from `available-rewards` either, keeping the balance and index accounting always in lock-step and eliminating the compounding rounding loss, mirroring the recommended fix from the referenced report.

### Proof of Concept
1. Set up bond `B` with a very large `total-sats` (bond's staked-sats value) and a small `target-rate`, such that `target-yield = total-sats * target-rate / 500000` is nonzero but `earned * PRECISION / total-sats < 1` (i.e., `earned < total-sats / PRECISION`).
2. Call `calculate-rewards` (any unprivileged principal) once the calculation window elapses.
3. Observe `accrued-rewards-per-sat = 0` for bond `B` (no change to `rewards-per-token-for-cycle`), while `available-rewards`/`last-accounted-rewards-only` are reduced/advanced by `earned > 0`.
4. Repeat over several distribution cycles: `get-earned` for all stakers of bond `B` remains unaffected by these cycles' `earned` amounts, while the sBTC balance corresponding to those `earned` amounts is never claimable — it is not in `get-new-rewards` (already accounted) nor reflected in any staker's accumulator, permanently orphaning the funds inside the contract.
