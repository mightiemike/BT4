### Title
Denial of Service via unhandled exception in `sanitizeHost` when parsing attacker-controlled `host` query parameter - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` only checks that the `host` query parameter matches a base64-charset regex before decoding it and feeding the decoded bytes directly into the WHATWG `URL` constructor [1](#0-0) . It does not catch exceptions thrown by `new URL()`, so a syntactically-valid base64 string that decodes to a value the URL parser rejects (e.g. containing a raw space or other forbidden host code point) throws an uncaught `TypeError`. This mirrors the `fd_store` bug class: data received from an untrusted, anonymous caller (there: `fd_shred`'s `fd_shred34_t`; here: the HTTP `host` query param) is only partially validated (regex/struct-shape check) before being handed to a downstream parser (`fd_ext_blockstore_insert_shreds` / `URL()`), which then crashes on malformed-but-format-passing input.

### Finding Description
`sanitizeHost` validates the raw `host` string with `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/`, which accepts many byte sequences after decoding — it does not restrict what characters the *decoded* string may contain [2](#0-1) . It then calls `decodeHost` (a thin wrapper over `atob`) and immediately constructs `new URL(`https://${decodeHost(sanitizedHost)}`)` [3](#0-2) [4](#0-3) .

Per the WHATWG URL Standard, certain "forbidden host code points" (space, `#`, `%`, `/`, `:`, `<`, `>`, `?`, `@`, `[`, `\`, `]`, `^`, `|`, NUL, and other control characters) occurring in the authority/host portion of a URL string that isn't otherwise delimited (no following `/`) cause `new URL()` to throw a `TypeError`. Because base64 decoding of an attacker-chosen input can trivially produce such characters (e.g. base64 of the string `"a b"` is `YSBi`, which passes the regex and decodes to a string containing a space), an anonymous caller can supply a `host` value that passes the base64 shape check but crashes the `URL` constructor with no surrounding `try/catch` in `sanitizeHost`.

This function is reachable from multiple unauthenticated, pre-auth entry points across the packages:
- `packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts` (`buildEmbeddedAppUrl`) [5](#0-4) 
- `packages/apps/shopify-app-express/src/redirect-to-auth.ts` (`clientSideRedirect`, called from an `async` handler with no `try/catch`) [6](#0-5) 
- `packages/apps/shopify-app-express/src/middlewares/ensure-installed-on-shop.ts` → `embedAppIntoShopify` (this call path *is* wrapped in try/catch, so it degrades gracefully) [7](#0-6) 
- `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-shop-and-host-params.ts` and the equivalent react-router helper, called directly with no try/catch during the admin authentication flow [8](#0-7) 

The most severe reachable path is `redirect-to-auth.ts`'s `clientSideRedirect`: it is invoked synchronously inside the `async function redirectToAuth`, with no `try/catch` anywhere in the file. A synchronous throw inside an `async` function body becomes a rejected `Promise`; if the calling middleware (e.g. `ensureInstalledOnShop`) does not itself wrap the call in `try/catch` and forward the error to `next(err)`, this becomes an **unhandled promise rejection**. In Node.js (v15+), the default behavior for unhandled promise rejections is to terminate the process, which would crash the entire app server for all merchants/customers, not just the requester — a full application-level DoS from a single anonymous, unauthenticated request.

### Impact Explanation
An anonymous, unauthenticated attacker can send a single crafted GET request (e.g. to the app's install/auth redirect endpoint with `?embedded=1&host=<crafted-base64>`) that causes an uncaught exception inside an auth-flow handler. Depending on the calling framework's error handling:
- In `shopify-app-express`'s `redirectToAuth`/`clientSideRedirect` path, this is not wrapped in a `try/catch`, risking an unhandled promise rejection and potential process crash (DoS of the entire app for all shops).
- In Remix/React Router admin authentication helpers, it likely surfaces as an uncaught error in a single request (500/error boundary), i.e. localized DoS of that auth handler.

This falls under the accepted "DoS of an auth handler" impact category, matching the crash-on-malformed-input bug class described in the source report (where partially-validated, attacker-influenced structured data crashes a downstream parser).

### Likelihood Explanation
High likelihood of triggerability: the `host` parameter is fully attacker-controlled, requires no authentication, and only needs to satisfy a permissive base64-alphabet regex. Constructing an input that decodes to a string containing a forbidden host code point (e.g., a space) is trivial and requires no special access or privilege — consistent with the "unprivileged actor" and "single anonymous HTTP request" criteria in scope.

### Recommendation
Wrap the `new URL()` call inside `sanitizeHost` in a `try/catch` and return `null` (or throw the existing `InvalidHostError`) on failure, rather than allowing the underlying `TypeError` to propagate:
```ts
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  try {
    const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
    // ... existing regex checks
  } catch {
    sanitizedHost = null;
  }
}
```
Additionally, audit all callers of `sanitizeHost`/`sanitizeShop`/`decodeHost` (especially `shopify-app-express/src/redirect-to-auth.ts`) to ensure every call site wraps synchronous throws in `try/catch` or otherwise guarantees the resulting rejection is handled, preventing unhandled promise rejections from propagating out of Express middleware.

### Proof of Concept
```ts
import {shopifyApi} from '@shopify/shopify-api';
import {testConfig} from '../__tests__/test-config';

const shopify = shopifyApi(testConfig());

// base64 for the string "a b" (contains a raw space) — passes the base64
// character-class regex but decodes to a value the URL parser rejects.
const maliciousHost = Buffer.from('a b').toString('base64'); // "YSBi"

// This throws an uncaught TypeError ("Invalid URL") instead of returning null,
// because `new URL()` inside sanitizeHost is not wrapped in try/catch.
shopify.utils.sanitizeHost(maliciousHost);
```
Sending this value as the `host` query parameter to an unauthenticated `shopify-app-express` route that calls `redirectToAuth` with `embedded=1` (`GET /auth?shop=<valid-shop>&embedded=1&host=YSBi`) reaches `clientSideRedirect`, which calls `sanitizeHost` unguarded, producing the same crash inside request handling.

**Note on confidence**: I was unable to execute the actual Node.js runtime here to confirm the exact exception message/behavior for every malformed-but-base64-valid string, or to trace whether the top-level Express app in this repo installs a global unhandled-rejection handler that would prevent a full process crash. A Devin session with a live environment should verify runtime behavior (confirm `new URL('https://a b')` throws, confirm whether an unhandled promise rejection actually crashes the process in the app's specific Express/Node setup) before treating the "process crash" impact as certain versus "single-request 500."

  config: AppConfigInterface,
  req: Request,
  res: Response,
  shop: string,

  const host = api.utils.sanitizeHost(req.query.host as string);
  if (!host) {
    res.status(500);
    res.send('No host provided');
    return;
