The strongest local analog to the ERC20Method finding is a self-documented (via TODO) validation gap in `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs`, used by replay-verification tooling.### Title
Replay-verification skips validating state-checkpoint hashes, letting a divergent post-txn state root pass as a match - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function that decides whether a locally re-executed transaction's output "matches" an authoritative, previously-committed `TransactionInfo` (the object bound into the transaction accumulator/Merkle proof). It only compares status, gas used, write-set hash, and event-root hash. It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` between the two, even though these fields exist specifically to authenticate the resulting global state root at that version. This mirrors the ERC20Method pattern: a discriminating/authenticating field exists but is silently skipped before the code treats two different objects as equivalent.

### Finding Description
`ensure_match_transaction_info` performs field-by-field validation of a freshly produced `TransactionOutput` against an `expected` `TransactionInfo` (the one committed to the ledger and provably bound to a `LedgerInfo` via the transaction accumulator): [1](#0-0) 

It checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed `event_root_hash` vs `txn_info.event_root_hash()`

It never touches `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` — the fields that authenticate the Sparse-Merkle-Tree root of the *entire world state* (and hot-state/position-state trees) after the transaction, as opposed to just the write set of that one transaction. The gap is called out explicitly in a `TODO` right inside the function: [2](#0-1) 

`TransactionInfoV0`/`V1` carry these fields specifically for this purpose: [3](#0-2) [4](#0-3) 

This function is the sole verification gate used by the archive replay-verification tool (`aptos db-tool replay-on-archive`), which re-executes historical transactions against a target `AptosDB` and checks the result against previously stored `TransactionInfo`s pulled from the same DB: [5](#0-4) 

It is also invoked from the Aptos debugger and CLI commands (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`), i.e., every tool that claims to "verify" historical execution correctness against stored data uses this exact check.

Because the write-set hash and event-root hash are checked but the state-checkpoint hash is not, a scenario where the transaction's own write set and events are correct, but the *resulting Sparse-Merkle-Tree root* differs (e.g., due to a state-merge/aggregation bug, an off-by-one during checkpointing, or corruption introduced in an unrelated code path that touches the state tree without touching this transaction's write set) will be reported as a full match with no error.

### Impact Explanation
This is a proof-integrity gap in the "authenticated output must stay bound to the correct root" sense: the `state_checkpoint_hash` (and the newer hot-state/position-state checkpoint hashes) are precisely the accumulator-bound values that are supposed to authenticate the world-state root at a version. A tool whose entire purpose is to detect whether locally-computed state diverges from the authoritative, already-committed (and consensus-signed) ledger data will silently pass even when the state root has diverged. This defeats the primary safety net used to catch historical state corruption or non-determinism bugs on mainnet archives, and it is exactly the kind of "authenticated output bound to the wrong … root" class called out in the task's proof/storage pivots. Given this tooling is relied on to certify that a full DB replay reproduces the canonical chain state, an undetected root mismatch could let ledger corruption go unnoticed indefinitely.

It is not, by itself, a way to get a wrong value committed to consensus (the executor's normal commit path independently computes and signs its own checkpoint hash; this function doesn't gate the commit itself). Its severity is scoped to defeating the verification/replay tooling's core guarantee rather than directly forging a wrong committed root.

### Likelihood Explanation
This is deterministic, code-level behavior (not a race or timing issue), reachable any time `replay_on_archive`, the debugger, or the CLI verification commands run over an archive that has a divergent state-checkpoint hash for some historical transaction while its write set/events happen to match. Given the comment already flags this as a known, intentional gap pending future work (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`), the maintainers are aware but it remains unpatched in the codebase examined.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally-computed output/checkpoint result and `txn_info`, at least whenever these values are computed for the version in question (they may be `None` for non-checkpoint versions, which should be handled explicitly rather than skipped for all cases). This closes the gap before the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature (referenced by the existing TODO) is enabled, ensuring replay-verify/debugger tooling cannot silently accept a divergent post-transaction state root.

### Proof of Concept
Conceptual, based on static code reading (no live repro executed):
1. Take an archived DB where transaction at version `v` has `TransactionInfo.state_checkpoint_hash = H1`.
2. Re-execute that transaction locally producing a `TransactionOutput` whose `write_set` and `events` hash identically to what's stored (so `state_change_hash` and `event_root_hash` checks pass), but whose actual resulting global state tree root would hash to `H2 != H1` (e.g., due to a bug in state-checkpoint construction that doesn't affect the per-txn write set, such as issues in `do_state_checkpoint.rs`'s state-root computation logic).
3. Call `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` as done in `replay_on_archive.rs`.
4. Because `state_checkpoint_hash` is never compared, `ensure_match_transaction_info` returns `Ok(())`, and `replay_on_archive` reports the chunk as verified successfully despite the true state root having diverged.

Note: I was not able to fully trace whether `state_checkpoint_hash` divergence can arise independently of `write_set`/`event` divergence within the current codebase (e.g., via a hot-state or position-state computation bug) — this would require deeper analysis of `do_state_checkpoint.rs`'s hashing logic, which I could not fully verify with the available tool budget. The core vulnerability — that the equality check omits these fields entirely — is directly confirmed in the code and its own TODO comment.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
