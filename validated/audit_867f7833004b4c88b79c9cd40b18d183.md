### Title
Fixed-size `long` overflow in `ExchangeInjectActuator.execute()` ratio calculation causes denial of service for validated token-injection transactions - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` computes the counter-asset amount for a bancor-style TRC10 exchange pool using two different arithmetic strategies in `validate()` and `execute()`. `validate()` uses `BigInteger` multiplication/division (arbitrary precision, cannot overflow on the multiply step) [1](#0-0) , while `execute()` recomputes the same ratio using fixed-width `long` arithmetic via `multiplyExact`/`floorDiv` [2](#0-1) . This is directly analogous to the Dango DEX finding: an internal ratio/price value that is legitimate and passes higher-level bounds checks can still exceed the maximum value representable by the fixed-size type used in the actual state-mutating computation, causing the operation to fail.

### Finding Description
`validate()` only bounds the **final** balances (`newTokenBalance`, `newAnotherTokenBalance`) against `dynamicStore.getExchangeBalanceLimit()` [3](#0-2) ; it does not bound the **intermediate product** `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`). Because `validate()` performs this multiplication in `BigInteger`, an intermediate product that exceeds `Long.MAX_VALUE` (~9.22e18) is handled without error, and only the final quotient — which does fit in a `long` — is checked via `.longValueExact()` [4](#0-3) .

`execute()`, however, recomputes the exact same ratio using `multiplyExact(secondTokenBalance, tokenQuant)` (a `long`-only fixed-point multiply, effectively `Math.multiplyExact` wrapped by `Maths.multiplyExact`) before dividing [5](#0-4) , with the underlying helper defined in `AbstractActuator.multiplyExact` [6](#0-5) . If the raw product `secondTokenBalance * tokenQuant` overflows 64 bits — even though `secondTokenBalance`, `tokenQuant`, and the eventual quotient `anotherTokenQuant` are all well within the `ExchangeBalanceLimit` — `multiplyExact` throws an `ArithmeticException`, which is caught and converted into a failed transaction with status `FAILED` (a `ContractExeException`) [7](#0-6) .

This is the same bug class as the Dango DEX report: a legitimate operation (in-scope per the exchange's own limits) is rejected because an *intermediate* fixed-point representation cannot hold the value, even though the final result is representable. In the Dango case it was `Udec128_24` overflow during price scaling; here it is `long` overflow during ratio scaling in a two-step computation that is inconsistent between the validation path (BigInteger, safe) and the execution path (long, unsafe).

### Impact Explanation
Because `validate()` and `execute()` use different arithmetic domains for the same formula, a transaction can pass `validate()` (accepted into a block) and then throw during `execute()`, being marked `FAILED` on-chain. This is a state-machine/availability defect: for asset pairs where one token has a large supply/precision (e.g., a token with 0 decimals and huge integer balances paired against a token requiring large injected quantities), otherwise valid `ExchangeInjectContract` operations become permanently unusable — a denial-of-service for that specific exchange pair's inject path, mirroring the "certain trading pairs become non-functional" impact described in the source report. It does not directly cause fund loss because balances are not mutated before the exception is thrown, but it breaks the documented guarantee that anything passing validation should execute correctly, and can strand liquidity providers unable to inject additional balance into affected exchanges.

### Likelihood Explanation
Likelihood is limited by how large `getExchangeBalanceLimit()` is configured and by the specific mix of token balances at the moment of injection; `validate()` deliberately avoids this overflow via `BigInteger`, so most exchanges will not naturally hit it unless the pool balances and injected quantity are large enough that their raw product exceeds ~9.22e18 while the quotient still fits comfortably under the balance limit (e.g., a pool skewed heavily toward one high-balance side). This requires a specific configuration/exchange state rather than being triggerable in every case, but it is directly reachable by any unprivileged user who controls the exchange (the creator performing `ExchangeInjectContract`) once such a pool exists.

### Recommendation
Make `execute()` use the same `BigInteger` multiply/divide logic as `validate()` (or vice versa), so the two computations are guaranteed consistent, and any overflow is caught deterministically and rejected during validation rather than causing an execution-time `ArithmeticException`. Alternatively, add an explicit intermediate-product bound check in `validate()` that mirrors the constraint actually enforced by `execute()`'s `long`-based arithmetic.

### Proof of Concept
Conceptual PoC (bounded by index limitations — recommend a Devin session to run against a live node for exact byte-level reproduction):
1. Create an `Exchange` pool via `ExchangeCreateActuator` with `firstTokenBalance` and `secondTokenBalance` chosen such that `secondTokenBalance` is large (close to `ExchangeBalanceLimit`, e.g. on the order of 1e15–1e18 depending on configured limit).
2. Submit an `ExchangeInjectContract` with `tokenQuant` (for `firstTokenID`) chosen such that `secondTokenBalance * tokenQuant` exceeds `Long.MAX_VALUE` (~9.22e18) but `secondTokenBalance * tokenQuant / firstTokenBalance` (the actual `anotherTokenQuant`) remains below `ExchangeBalanceLimit`.
3. `validate()` succeeds because the `BigInteger` computation at lines 217-218 of `ExchangeInjectActuator.java` never overflows and only the final quotient is checked against the limit.
4. `execute()` throws `ArithmeticException` at `multiplyExact(secondTokenBalance, tokenQuant)` (line 73-74), producing a `ContractExeException` and a `FAILED` transaction status — despite the operation being valid per the exchange's own business rules.
