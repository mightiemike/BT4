### Title
Method ID upgrade chain-id gate does not distinguish `Network::Nightly` from `Network::TestNetworkWithForks` (both map to chain_id 5665) - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the identical constant `5665`, so the chain-id equality check in `run_l1_block`'s `DataOnDa::BatchProofMethodId` handler cannot disambiguate which of the two networks a council-signed `BatchProofMethodIdBody` was intended for. Since `chain_id` is embedded in `body.serialize()` (the signed prehash), a body signed for one network verifies identically on the other whenever the two networks share the same council public keys.

### Finding Description
The intended binding is `body.chain_id == citrea_network_to_chain_id(network)` should uniquely identify exactly one network. In code: [1](#0-0) 

`Network::Nightly => 5665` and `Network::TestNetworkWithForks => 5665` are the same value, so this binding is not injective — two distinct `network` values satisfy the same `chain_id`.

In `run_l1_block`, the gate is: [2](#0-1) 

If `circuit_chain_id != batch_proof_method_id.body.chain_id`, the blob is skipped; otherwise `verify_method_id_security_council` is invoked with `method_id_upgrade_authority_da_public_keys` for whichever network is currently running. Because the `chain_id` field is serialized into `body.serialize()` (the signed message), a signature valid for `Nightly` (chain_id 5665) is also structurally valid for `TestNetworkWithForks` (chain_id 5665) — the gate passes on both sides.

The default council key material for `TestNetworkWithForks` and `Nightly`, as configured in `initial_values.rs`, use the exact same fallback private keys (e.g. `79122E48DF1A002FB6584B2E94D0D50F95037416C82DAF280F21CD67D17D9077` etc.) when the corresponding `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` environment variables are not set: [3](#0-2) 
compare to Nightly's defaults: [4](#0-3) 

So by default (absent operator-supplied env-var overrides), both networks share identical council keys, satisfying the question's stated precondition exactly.

### Impact Explanation
If a deployment of `TestNetworkWithForks` is run with default (unoverridden) council keys — matching `Nightly`'s defaults — then a `BatchProofMethodId` blob inscribed and signed for `Nightly` can be replayed verbatim against the `TestNetworkWithForks` light-client prover (or vice versa). `verify_method_id_security_council` succeeds and `BatchProofMethodIdAccessor::insert` commits an unauthorized method-id/activation-height pair into that network's JMT state, which subsequently governs `Z::verify` for batch proofs in `process_complete_proof`. This is an unauthorized method-id upgrade — the council never signed anything scoped to the receiving network, breaking the AUTHORITY guarantee for accepting method-id upgrades. This matches the Critical impact category "a sequencer commitment or method-id upgrade accepted that was never authorised."

### Likelihood Explanation
This requires the two networks to actually be run with identical council keys — which is the codebase's own compiled-in default when no `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` env vars are supplied at build time. Given `TestNetworkWithForks` is explicitly documented as "used for testing purposes only" and is not one of the standard production networks (`Mainnet`/`Testnet`/`Devnet`), the practical likelihood of this scenario occurring against a genuine value-bearing mainnet/testnet deployment is low; it primarily affects nightly/test deployments where the shared default keys are most likely to be used unmodified. The attacker cost is limited to observing a publicly-inscribed council-signed reveal transaction and re-inscribing/rebroadcasting the identical bytes on the target network's DA — no signing capability is needed.

### Recommendation
Assign each `Network` variant a distinct, non-colliding chain-id constant (e.g. give `TestNetworkWithForks` its own unique value distinct from `Nightly`'s 5665), and/or additionally bind the signed body to a network-specific domain separator so that signatures cannot be replayed across any two networks even if a chain-id collision is later reintroduced.

// cargo test -p light-client-prover-circuit cross_network_chain_id_collision
#[test]
fn cross_network_chain_id_collision() {
    use sov_rollup_interface::Network;
    use crate::circuit::citrea_network_to_chain_id;

    let nightly_id = citrea_network_to_chain_id(Network::Nightly);
    let test_forks_id = citrea_network_to_chain_id(Network::TestNetworkWithForks);

    // Binding claim: body.chain_id == citrea_network_to_chain_id(network) should uniquely
    // identify ONE network. Assert it does NOT.
    assert_eq!(nightly_id, test_forks_id, "chain ids collide: {} == {}", nightly_id, test_forks_id);

    // Construct a BatchProofMethodIdBody signed with chain_id = nightly_id (5665),
    // using council keys shared by both networks' default constants.
    // Run run_l1_block once configured for Network::Nightly and once for
    // Network::TestNetworkWithForks with the identical signed blob bytes.
    // Assert BatchProofMethodIdAccessor::get(..) on BOTH runs contains the
    // same injected method_id/activation_l2_height, proving the gate does not
    // scope the authorization to a single network.
}

pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        sov_rollup_interface::Network::Mainnet => 4114,
        sov_rollup_interface::Network::Testnet => 5115,
        sov_rollup_interface::Network::Devnet => 62298,
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
