**Rationale:** `VestingAdminStore` in `types/src/vesting.rs` is a plain Rust deserialization struct used only by client-side/CLI tooling to read and display an already-committed Move resource — it is referenced solely in `crates/aptos/src/node/mod.rs` and `crates/aptos/src/stake/mod.rs` for resource lookups, not in any execution, storage-commit, Jellyfish Merkle, accumulator, or proof-verification code path. [1](#0-0) [2](#0-1) 

The state commitment and value hashing performed by validators during execution/commit operate on the raw BCS bytes produced by the Move VM for the on-chain `vesting.move` resource, not on this Rust struct's own (re-)serialization. Layout evolution of the Move resource is governed by the Move module's struct definition and any schema change requires a coordinated upgrade of the Move framework itself (which is subject to governance, not unprivileged input); a mismatch between this Rust decoder and an upgraded Move layout would cause a BCS deserialization error in the CLI (an operational/display failure for whoever ran the tool), not a divergence in the validator-computed state hash, write set, or proof, since consensus/state commitment never invokes this struct at all. Therefore there is no path from unprivileged input through this struct to hard-fork divergence, corrupted proofs, or misbound authenticated responses.
