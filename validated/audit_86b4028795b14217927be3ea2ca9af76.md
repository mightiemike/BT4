### Title
Missing declared-class-hash validation in Starknet OS `execute_replace_class` allows honest-node divergence between blockifier execution and SNOS re-execution - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The Starknet OS Cairo implementation of the `replace_class` syscall accepts any `class_hash` supplied by a contract without validating that a contract class of that hash was actually declared, and without checking that the class version (Cairo0/V0 vs Cairo1/V1) is compatible with the contract being replaced. This mirrors the reported bug class ("no validation of contract types") — here, the OS trusts caller-supplied `class_hash` data as being of a valid/declared class type without verifying it, while the Rust blockifier execution path enforces exactly these checks.

### Finding Description
In the Rust blockifier, the `replace_class` syscall handler explicitly (1) ensures the class is declared by reading it via `get_compiled_class`, and (2) forbids replacing a V1 class hash with a V0 class hash (`ForbiddenClassReplacement`): [1](#0-0) [2](#0-1) 

Corresponding tests confirm both checks are enforced at the blockifier layer: an undeclared class hash is rejected ("is not declared") and downgrading a Cairo1 (V1) contract to a Cairo0 (V0) class hash is rejected ("Cannot replace V1 class hash with V0 class hash"): [3](#0-2) 

However, the Starknet OS's own Cairo implementation of the same syscall — used for state-transition re-execution/proving (`execute_replace_class` in `syscall_impls.cairo`) — has no such validation. The class hash from the syscall request is written straight into the new `StateEntry` with only a TODO comment acknowledging the missing check: [4](#0-3) 

Because the OS never confirms `class_hash` corresponds to a declared class (of any type) before committing the new `StateEntry` for the contract, the OS's constraint system permits a state transition (a "type" of `class_hash` on a `StateEntry`) that the actual blockifier execution client would never produce or accept.

### Impact Explanation
The Starknet OS is the constraint program the honest sequencer's re-execution/proving pipeline must satisfy to attest a block's state transition as valid. If the OS's semantics for `replace_class` are strictly weaker than the blockifier's runtime semantics (missing "declared class" check and missing V1→V0 downgrade prohibition), the OS could nonetheless accept and commit a state root reflecting a `class_hash` value that never went through declaration validation, or that violates the version-compatibility invariant the blockifier enforces. This creates a discrepancy between what the sequencer's execution layer would produce as canonical output and what the OS-generated proof/commitment attests to be valid — a form of honest-node/re-execution divergence and a wrong committed state root risk, since the two components (blockifier vs. OS) are supposed to be semantically equivalent for consensus/proving purposes.

### Likelihood Explanation
This is reachable from a single unprivileged transaction: any account contract can invoke the `replace_class` syscall (Cairo1 `library_call`-adjacent execution path) with an arbitrary `class_hash` argument as part of ordinary transaction execution — no special privileges are required. The TODO comment in the source itself confirms this gap is a known, currently-unaddressed item in the codebase, increasing confidence that it is a genuine current state rather than a hypothetical.

### Recommendation
Add the missing validation in the OS's `execute_replace_class` (in `syscall_impls.cairo`, and its deprecated counterpart in `deprecated_execute_syscalls.cairo`) to mirror the blockifier: verify that `class_hash` corresponds to a declared compiled class fact within the OS's tracked state (e.g., asserting a nonzero/known entry in `contract_class_changes`/declared-classes dict, analogous to `get_compiled_class`), and enforce the same "cannot replace V1 class hash with V0 class hash" rule that the Rust `ForbiddenClassReplacement` error implements, before committing the new `StateEntry`.

### Proof of Concept
Not applicable as an executable exploit — the vulnerability is a structural code-review finding: comparing the enforced checks in the Rust `replace_class` syscall implementation (declared-class check plus V1/V0 forbid) against the Cairo OS implementation which performs neither, evidenced directly by the `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` comment at line 902 of `syscall_impls.cairo` with no equivalent check present anywhere in `execute_replace_class`.

// Replaces the class.
func execute_replace_class{
    range_check_ptr,
    syscall_ptr: felt*,
    contract_state_changes: DictAccess*,
    revert_log: RevertLogEntry*,
}(contract_address: felt) {
    alloc_locals;
    let request = cast(syscall_ptr + RequestHeader.SIZE, ReplaceClassRequest*);

    // Reduce gas.
    let success = reduce_syscall_gas_and_write_response_header(
        total_gas_cost=REPLACE_CLASS_GAS_COST, request_struct_size=ReplaceClassRequest.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );

    assert [revert_log] = RevertLogEntry(selector=CHANGE_CLASS_ENTRY, value=state_entry.class_hash);
    let revert_log = &revert_log[1];

    return ();
}
