### Title
`Bank::enqueue_off_chain_accounts_lt_hash_updates()` only checks for duplicate pubkeys under `debug_assertions`, silently corrupting the accounts lattice hash in release builds - ([File: runtime/src/bank/accounts_lt_hash.rs])

### Summary
`Bank::enqueue_on_chain_accounts_lt_hash_updates()` (the transaction-processing path) unconditionally deduplicates its input via a `seen_accounts` hash set before enqueueing lt-hash mix-in/mix-out jobs [1](#0-0) . Its off-chain sibling, `enqueue_off_chain_accounts_lt_hash_updates()`, documents the same "no duplicates" requirement but only *verifies* it when `cfg!(debug_assertions)` is true, panicking on violation in debug builds only [2](#0-1) ; in release builds (which is what production validators run) this check compiles away entirely, and any duplicate pubkeys are silently mixed in/out multiple times.

### Finding Description
The comment on `enqueue_off_chain_accounts_lt_hash_updates()` states the contract explicitly: "Does not deduplicate accounts, requiring the caller to ensure there are no duplicates." [3](#0-2)  The enforcement of this contract is guarded by `if cfg!(debug_assertions) { ... }` [4](#0-3) . This mirrors the ERC1155Voucher bug class: one code path (`onERC1155Received`/`enqueue_on_chain_...`) enforces an invariant unconditionally, while the sibling batch path (`onERC1155BatchReceived`/`enqueue_off_chain_...`) is missing the enforcement — here, the enforcement exists in source but is optimized out for the build configuration that ships to validators.

If a caller violates the "no duplicates" contract with the release binary running, `load_then_enqueue` is invoked once per duplicate entry, and for each duplicate the *same* previous-state is mixed out and the *same* current-state mixed in via `AccountsLtHashAsyncProgress::process()` [5](#0-4) . Because `LtHash::mix_in`/`mix_out` are not idempotent no-ops for repeated application (each mix-out/mix-in pair for the *same* final state does cancel algebraically only when prev/curr are correctly paired once — but if the same pubkey appears more than once in `accounts`, each occurrence independently loads the identical "previous" account state on-chain and mixes the identical current state, so mix-out/mix-in pairs are applied `N` times instead of once), the resulting incremental lt-hash delta diverges from the value that would be computed by a canonical, deduplicated apply. This risks producing an incorrect final `accounts_lt_hash` for the bank relative to any other honest node whose call site does not introduce duplicates, or relative to a full recomputation from the merkle/lattice hash of accounts state (used for cross-checking at snapshot load and for `AccountsDb::calculate_accounts_lt_hash_at_startup`-style verification).

The reachable caller path is `Bank::store_accounts_without_stakes_cache()`, which calls `enqueue_off_chain_accounts_lt_hash_updates()` and documents the identical "callers must ensure no duplicates" contract [6](#0-5) . Its public wrapper `Bank::store_accounts()` carries the same undocumented-enforcement contract [7](#0-6) , and is used by production code such as `store_stake_accounts_in_partition()` during partitioned epoch reward distribution, which builds `updated_stake_rewards` from a `PartitionedStakeReward` list and passes it straight to `store_accounts()` [8](#0-7) , and `store_commission_accounts_partitioned()` similarly [9](#0-8) . If either of these input collections is ever built with a duplicate stake/commission pubkey (e.g., a bug in reward partitioning, hashing collisions across partitions, or a future change to the reward pipeline that doesn't re-verify uniqueness), the release-mode enforcement gap means the divergence is not caught until (and unless) it manifests as a downstream hash mismatch.

### Impact Explanation
An incorrect `accounts_lt_hash` accumulation is a capitalization/hash correctness issue: the lattice hash is used to detect corruption/tampering of account state and is checked against snapshots and during startup verification. A silent divergence introduced by duplicate entries in an off-chain store batch (which is exactly the kind of "runs only in production, not caught by debug assertion" bug that testing in debug mode would miss) could cause a validator to compute a wrong accounts lt hash without panicking, which is the disproportionate/silent-divergence class explicitly called out as in-scope ("hash/capitalization divergence"). It does not require any change to consensus code and is a purely internal accounts-db/bank hashing correctness gap, matching the request's unprivileged-user AccountsDB hashing category.

### Likelihood Explanation
The precondition (a duplicate pubkey being passed into the off-chain store path) is currently prevented in-repo by the callers being carefully constructed to avoid duplicates (e.g., `updated_stake_rewards` is built one entry per unique stake pubkey per partition). However, the *safety net* that would catch a violation of this invariant is entirely absent in release builds, which is the actual defect being reported (an analog to the missing check in the batch function): the invariant is enforced only in configurations that are not what validators run, so any future regression, edge case in reward calculation, or additional off-chain store caller silently corrupts hashing instead of panicking, and there is currently no `debug_assert!`-independent runtime enforcement or metric to detect the corruption after the fact.

### Recommendation
Make the duplicate-pubkey check in `enqueue_off_chain_accounts_lt_hash_updates()` run unconditionally (not gated by `cfg!(debug_assertions)`), or at minimum add a lightweight, always-on hashset-based dedup check with a `datapoint_error!`/`panic!` outside of debug builds, so the invariant that is documented as a caller contract is actually enforced in the binaries that validators run — mirroring the unconditional dedup that `enqueue_on_chain_accounts_lt_hash_updates()` performs.

### Proof of Concept
1. Build the validator in release mode (`cargo build --release`, i.e., `debug_assertions` disabled).
2. Construct any `StorableAccounts` batch containing the same pubkey twice with different lamport/data values (e.g., by crafting a `PartitionedStakeRewards`-like storable containing a duplicate `stake_pubkey`, or directly calling `bank.store_accounts_without_stakes_cache()` with a duplicate list, as exercised by the existing debug-only test `test_enqueue_off_chain_accounts_lt_hash_updates_catches_duplicates` [10](#0-9) ).
3. In debug builds this panics with "duplicate accounts were enqueued for hashing"; in release builds it does not, and `enqueue_off_chain_accounts_lt_hash_updates()` proceeds to enqueue one lt-hash mix job per duplicate occurrence [11](#0-10) , producing an `accounts_lt_hash` that differs from the value computed by any path that properly deduplicates the same input (e.g., `enqueue_on_chain_accounts_lt_hash_updates()`), demonstrating the silent divergence.

                    // we've already seen this account, so add it to the duplicates list

                }

    ///
    /// Note: Since an LtHash is large, `accum_lt_hash` is passed as an in-out parameter.
    /// This it to avoid Rust compiler bug that fails to perform return value optimization.
    fn process(accum_lt_hash: &mut LtHash, update: AccountsLtHashUpdate) {
        let AccountsLtHashUpdate {
            address,
            prev_account,
            curr_account,
        } = update;
        if let Some(prev_account) = prev_account {
            let prev_lt_hash = AccountsDb::lt_hash_account(&prev_account, &address);
            accum_lt_hash.mix_out(&prev_lt_hash.0);

            let curr_lt_hash = AccountsDb::lt_hash_account(&curr_account, &address);
            accum_lt_hash.mix_in(&curr_lt_hash.0);
        }
    }
