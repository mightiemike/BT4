### Title
Witness block/tx-fee rewards are permanently lost when a witness has zero recorded votes for a cycle - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.payReward()` unconditionally credits block-production and transaction-fee rewards to a witness's per-cycle reward pool via `delegationStore.addReward(cycle, witnessAddress, value)`, without checking whether that witness actually has any recorded votes for the cycle. When a voter (or the witness itself) later calls `withdrawReward()`/`queryReward()`, `computeReward()` silently skips reward attribution for any cycle where `delegationStore.getWitnessVote(cycle, srAddress) == REMARK || == 0`. The result: rewards deposited for a "voter-less" cycle become permanently unclaimable and are effectively burned/stuck, mirroring the external report's pattern of fees being emitted for a period before verifying that the period actually has eligible voters.

### Finding Description
Each block, `Manager.payReward()` calls `mortgageService.payBlockReward()` / `payTransactionFeeReward()` for the forging witness: [1](#0-0) 

Both delegate to `payReward()`, which computes a brokerage split and unconditionally adds the remainder to the delegation reward pool for the *current cycle*, with no check on the witness's vote total for that cycle: [2](#0-1) 

`addReward` simply accumulates the value keyed by `(cycle, witnessAddress)`: [3](#0-2) 

Distribution to actual voters only happens later in `computeReward()`, which explicitly skips (loses) the accumulated reward whenever the witness's recorded vote total for that cycle is `REMARK` (unset) or `0`: [4](#0-3) 

The per-cycle vote snapshot used for this check is written once per maintenance cycle in `MaintenanceManager.doMaintenance()`, for *every* witness returned by `getAllWitnesses()` (not only active/top-27 witnesses), using whatever `voteCount` the witness currently has — including `0`: [5](#0-4) 

A concrete zero-vote path exists via `tryRemoveThePowerOfTheGr()`, which can zero out a genesis witness's `voteCount` mid-cycle while that witness may still be scheduled to forge blocks for the remainder of the cycle under the previously computed schedule: [6](#0-5) 

Another path is normal vote withdrawal: if all voters unvote a witness (bringing its `voteCount` to 0) right before/at a maintenance boundary while the witness continues to be scheduled/forges through the remainder of the current cycle, `setWitnessVote(nextCycle, ..., 0)` records a zero total for that cycle, and any block/tx-fee rewards subsequently added via `payReward()` for that cycle become unclaimable once `computeReward()` runs and hits the `totalVote == 0` branch.

This is structurally identical to the external report's root cause: **reward emission for a period is decoupled from a check of whether that period has any eligible claimants**, so the funds are added to a distribution pool that can never be paid out and are lost from circulation (they remain "stuck" as an untouchable ledger entry rather than rolling forward to a period with actual voters).

### Impact Explanation
Funds intended as witness/voter incentive rewards (block rewards, transaction-fee-pool rewards) are permanently lost/unclaimable whenever they accrue against a cycle where the forging witness's recorded vote total is zero. This is an accounting-correctness/asset-loss defect in the core DPoS incentive mechanism, not merely a cosmetic issue — it silently reduces total distributable rewards without transferring value anywhere reclaimable, and does so as part of normal chain operation (block production and vote fluctuations), not requiring any privileged actor.

### Likelihood Explanation
The zero-vote condition requires a witness to be actively forging (or eligible for the transaction-fee-pool payment path) during a cycle for which its snapshotted vote count is `0`. This can occur through ordinary vote withdrawal timing around maintenance-cycle boundaries or through the genesis-witness power-removal path (`tryRemoveThePowerOfTheGr`), both of which are reachable through normal, unprivileged voting/actuator activity rather than any privileged operation. It is a narrower/edge-timing condition (vs. the original report where "no votes for a gauge" is common), which is why likelihood should be assessed as low-to-medium rather than certain, but the mechanism itself is real and unconditional in the code as written.

### Recommendation
Before (or as part of) crediting rewards via `delegationStore.addReward()` in `MortgageService.payReward()`, or when running `computeReward()`, ensure symmetry between reward emission and reward eligibility: e.g., check the witness's current-cycle vote total before adding the reward, and if it is zero, either roll the reward forward into a period with voters, redirect it to the witness's own brokerage/allowance, or otherwise avoid depositing it into a pool keyed to a vote total of zero that can never be claimed.

### Proof of Concept
1. A witness `W` is actively forging blocks and is scheduled for the remainder of cycle `N` under `MaintenanceManager`'s current schedule.
2. During cycle `N`, all voters withdraw their votes from `W` (or `W` is a genesis witness affected by `tryRemoveThePowerOfTheGr`), causing `W.voteCount` to become `0`.
3. At the next maintenance boundary, `MaintenanceManager.doMaintenance()` calls `delegationStore.setWitnessVote(N+1, W, 0)` (or the vote for cycle `N` was already recorded as effectively `0`/`REMARK`).
4. While still scheduled, `W` forges blocks in cycle `N`; `Manager.payReward()` → `mortgageService.payBlockReward()`/`payTransactionFeeReward()` → `payReward()` unconditionally calls `delegationStore.addReward(N, W, value)`.
5. Any account subsequently calling `withdrawReward()`/`queryReward()` for cycle `N` against witness `W` hits `computeReward()`'s `totalVote == 0` branch and receives `0` for that cycle — the reward amount added in step 4 is never distributed to anyone and remains permanently stored under the `(N, W)` reward key with no code path that ever reclaims or forwards it.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
```java
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
