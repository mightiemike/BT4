### Title
Silent zero-clamping of `sierra_gas_to_steps_gas` underflow lets a transaction sender understate proving-gas/bouncer weight accounting - (File: crates/blockifier/src/bouncer.rs)

### Summary
The Opyn report flags `getExcessCollateral`/`getProceed` for coercing a signed "deficit" into an unsigned magnitude, silently turning an undercollateralized (negative) state into a value that looks safe/positive. The same coercion pattern — a subtraction that can conceptually go negative being clamped to zero and treated as "no problem" — exists in the sequencer's bouncer/gas-accounting code, in `sierra_gas_to_steps_gas`, which is on the transaction-inclusion path reachable by any unprivileged sender.

### Finding Description
`sierra_gas_to_steps_gas` computes the "steps" portion of Sierra gas by subtracting the gas attributable to Cairo builtins from the total Sierra gas reported for a transaction: [1](#0-0) 

```rust
pub fn sierra_gas_to_steps_gas(
    sierra_gas: GasAmount,
    cairo_primitives_counters: &CairoPrimitiveCounterMap,
    sierra_builtin_gas_costs: &BuiltinGasCosts,
) -> GasAmount {
    let cairo_primitives_gas =
        cairo_primitives_to_gas(cairo_primitives_counters, sierra_builtin_gas_costs);

    sierra_gas.checked_sub(cairo_primitives_gas).unwrap_or_else(|| {
        log::debug!(...);
        GasAmount::ZERO
    })
}
```

If `cairo_primitives_gas` (computed from the transaction's actual builtin usage, using `sierra_builtin_gas_costs`) exceeds `sierra_gas` (the total gas reported for the call), the subtraction underflows and the function silently returns `GasAmount::ZERO` instead of propagating an error or a signed/negative value. This result feeds `proving_gas_from_cairo_primitives_and_sierra_gas` and `get_tx_weights`, which combine it with a *separate* builtin-gas cost table (`proving_builtin_gas_costs`, derived from `BuiltinInstanceLimits`) to compute `total_proving_gas` and `total_sierra_gas`, which become the transaction's `BouncerWeights.sierra_gas` / `BouncerWeights.proving_gas`: [2](#0-1) 

Because two independent builtin-gas-cost tables are used (`sierra_builtin_gas_costs` for the "steps" derivation and `proving_builtin_gas_costs` for proving-gas accounting), and their per-builtin rates are not required to be proportional to each other, a transaction whose builtin mix makes `cairo_primitives_gas` (under the *sierra* cost table) exceed the total `sierra_gas` reported by the VM can drive `sierra_gas_to_steps_gas` into the zero-clamp branch. This mirrors the Opyn bug class exactly: a value that should reflect a real accounting deficit (an inconsistency between reported total gas and its constituent parts) is coerced to zero, discarding the sign/magnitude information, and the caller (`get_tx_weights`/`Bouncer::try_update`) treats the clamp as if the steps-derived component were legitimately zero rather than as a red flag of miscounted resource usage.

### Impact Explanation
`BouncerWeights.sierra_gas` and `BouncerWeights.proving_gas` are the exact quantities checked against `BouncerConfig::block_max_capacity` in `Bouncer::try_update` / `BouncerWeights::has_room` to decide whether a transaction fits in the current block [3](#0-2) . If the steps-gas component of a transaction's true resource usage is silently zeroed instead of correctly computed, the bouncer under-accounts that transaction's contribution to the block's proving/gas budget. An attacker (a single unprivileged transaction sender) crafting calldata/entry points whose builtin-vs-step gas ratio triggers this underflow can get transactions admitted into blocks while contributing less "counted" proving/sierra gas than they actually consume. Repeated across many transactions in a block, this allows the sequencer to pack blocks whose *real* proving/computation cost exceeds the intended `block_max_capacity`, risking blocks that cannot be proven/processed within the expected time budget — a liveness/DoS risk on block production (network unable to confirm new transactions in a timely manner), which is the class of impact this report's rules require (not merely "resource-only" bookkeeping, but an availability failure stemming from a bypassed capacity check).

### Likelihood Explanation
Reachable from a single submitted, unprivileged transaction — no operator, prover, or peer collusion required. The only requirement is constructing calldata whose builtin counter mix and Sierra gas usage relationship trips the underflow branch, which depends on the concrete (currently unverified against the exact rate tables) relationship between `sierra_builtin_gas_costs` and how “total Sierra gas” is measured for a call. This is plausible given that the two gas-cost tables (`sierra_builtin_gas_costs` from `versioned_constants.os_constants.gas_costs.builtins` and `proving_builtin_gas_costs` derived from `BouncerConfig::builtin_gas_costs()`/`BuiltinInstanceLimits`) are independently configured, but I was not able to fully verify a concrete transaction/builtin combination that triggers the underflow in this session due to running out of remaining tool iterations — this should be validated by directly testing `sierra_gas_to_steps_gas` with builtin counters/gas values pulled from live `VersionedConstants` and `BouncerConfig::builtin_gas_costs()` outputs.

### Recommendation
Do not silently clamp the underflow to zero. If `cairo_primitives_gas > sierra_gas`, this indicates an accounting inconsistency between the Sierra gas total and its constituent builtin costs; the code should either (a) treat this as a hard error / reject the transaction rather than admitting it with an undercounted weight, or (b) ensure by construction (e.g., an invariant check enforced at the VM/execution layer) that `cairo_primitives_gas` can never exceed `sierra_gas`, so the `unwrap_or_else` branch becomes unreachable rather than a silent zero-substitution that a resource-accounting check downstream relies on.

### Proof of Concept
Not independently reproduced in this session due to tool-iteration limits. To construct a PoC: pull `sierra_builtin_gas_costs` from `VersionedConstants::latest_constants().os_constants.gas_costs.builtins` and `proving_builtin_gas_costs` from `BouncerConfig::default().builtin_gas_costs()`, then find/execute a transaction whose Cairo-primitive builtin counters (e.g., heavy use of an expensive builtin under the sierra cost table) make `cairo_primitives_to_gas(counters, sierra_builtin_gas_costs) > total_sierra_gas` for that call, and confirm via `sierra_gas_to_steps_gas`/`get_tx_weights` that the resulting `BouncerWeights.sierra_gas`/`proving_gas` is lower than the transaction's real proving cost, allowing extra oversized transactions to be admitted past `BouncerConfig::has_room`.
