### Title
Unbounded full `AssetIssueStore` scan on public `GetAssetIssueListServlet`/`GetAssetIssueListByNameServlet` endpoints allows attacker-funded store growth to create disproportionate, repeatable CPU cost per free query - (`framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.getAssetIssueList()` and `Wallet.getAssetIssueListByName()` both call `AssetIssueStore.getAllAssetIssues()` / `AssetIssueV2Store.getAllAssetIssues()`, which iterates and materializes the *entire* asset-issue store on every single call, with no offset/limit enforcement. These methods are directly exposed via the unauthenticated `/wallet/getassetissuelist` and `/wallet/getassetissuelistbyname` HTTP endpoints, protected only by a fixed QPS-based `RateLimiterServlet`, not by any cost accounting tied to store size. An attacker can pay the one-time `AssetIssueFee` to grow the store to size N, then issue unlimited free repeated queries, each costing the node O(N) work, unlike the already-existing paginated variant that caps results via `ASSET_ISSUE_COUNT_LIMIT_MAX`.

### Finding Description
- `GetAssetIssueListServlet.doGet` calls `wallet.getAssetIssueList()` with no request parameters at all (framework/src/main/java/org/tron/core/services/http/GetAssetIssueListServlet.java:19-22). [1](#0-0) 
- `Wallet.getAssetIssueList()` fetches `getAllAssetIssues()` (unbounded) and runs a `forEach` over the full list, invoking `BandwidthProcessor.updateUsage` per element: [2](#0-1) 
- `GetAssetIssueListByNameServlet.fillResponse` calls `wallet.getAssetIssueListByName(...)`, which again fetches `getAllAssetIssues()` unconditionally and does an in-memory `stream().filter()` over the entire store just to find matches by name: [3](#0-2) 
- `AssetIssueStore.getAllAssetIssues()` performs a full iterator scan of the underlying DB with no size cap: [4](#0-3) 
- By contrast, the codebase already demonstrates awareness of this cost by providing a paginated variant, `getAssetIssuesPaginated`, which explicitly clamps `limit` to `ASSET_ISSUE_COUNT_LIMIT_MAX`: [5](#0-4) 
- The only gatekeeping on these endpoints is `RateLimiterServlet`, which enforces a fixed QPS/permit-based limiter (`DefaultBaseQqsAdapter`/`IPQPSRateLimiterAdapter`) independent of the actual cost of the underlying work: [6](#0-5) 
- Issuance-side, `AssetIssueActuator.validate()` restricts each *account* to issuing only one asset (`"An account can only issue one asset"`), but this is not a barrier against attacker-controlled growth of N, since an attacker can create arbitrarily many funded accounts (unprivileged, ordinary account creation) each issuing one low-value asset for the minimum `AssetIssueFee`: [7](#0-6) [8](#0-7) 

Root cause: the fee model prices the one-time act of *writing* an asset record, but the *read* API has no cost model proportional to N and no pagination is enforced by default on the primary listing endpoints, only QPS throttling that is unrelated to per-call CPU/IO cost.

### Impact Explanation
As the attacker grows N (number of stored assets) by paying the fixed, cheap `AssetIssueFee` per asset across multiple funded accounts, every subsequent call to `/wallet/getassetissuelist` or `/wallet/getassetissuelistbyname` (unauthenticated, public) forces a full O(N) DB iteration, list materialization, sort/filter, and bandwidth-usage update for each entry. Because the QPS rate limiter bounds the *rate* of requests but not their *cost*, the cumulative CPU/IO the attacker can impose per unit time grows linearly with N while their marginal cost per query is zero. This is a resource-exhaustion / underpriced-public-work vector against full/solidity/PBFT nodes (this servlet is mounted on `FullNodeHttpApiService`, `SolidityNodeHttpApiService`, `GetAssetIssueListByNameOnPBFTServlet`, and `GetAssetIssueListByNameOnSolidityServlet`).

### Likelihood Explanation
Fully feasible for an unprivileged attacker: asset issuance is a standard, permissionless contract type requiring only the `AssetIssueFee` and a funded account (one asset per account, so multiple cheap accounts suffice to grow N). The query endpoints require no authentication, no API key, and no session, and are reachable directly over HTTP by design. The attack is fully repeatable indefinitely once N is large, bounded only by the configured QPS ceiling, which is a request-count limit, not a cost/size-aware limit.

### Recommendation
- Require and enforce `offset`/`limit` (with a hard cap, e.g. reuse `ASSET_ISSUE_COUNT_LIMIT_MAX`) on `getAssetIssueList()`/`getAssetIssueListByName()` similarly to `AssetIssueStore.getAssetIssuesPaginated`, or deprecate/rate-cost-scale the unbounded endpoints.
- Consider maintaining a name index (e.g., secondary lookup keyed by asset name) instead of a full-store linear scan for `getAssetIssueListByName`.
- Add a cost-aware or store-size-aware rate limiter (e.g., token bucket weighted by current `AssetIssueStore` size) for these specific endpoints, rather than a flat QPS limiter.

### Proof of Concept
Java integration test plan (using existing test harness patterns from `GetAssetIssueListByNameServletTest`/`GetAssetIssueListServletTest`):
1. Populate `AssetIssueStore`/`AssetIssueV2Store` with N (e.g. 100k) `AssetIssueCapsule` entries directly via the store API (simulating N accounts each having paid `AssetIssueFee` via `AssetIssueActuator`).
2. Benchmark `AssetIssueActuator.execute()` cost per single asset issuance (fixed, O(1) write) vs. `Wallet.getAssetIssueList()` / `Wallet.getAssetIssueListByName()` invocation latency as N grows (e.g., N = 1k, 10k, 100k), asserting call latency scales linearly with N (`assertTrue(latency(N2)/latency(N1) ≈ N2/N1)`).
3. Fire repeated calls to `GetAssetIssueListServlet.doGet`/`GetAssetIssueListByNameServlet.doGet` in a loop bounded only by the configured QPS limiter and assert total CPU time consumed by the node scales with `N * numberOfQueries`, while assert the one-time cumulative issuance fee paid by the attacker (`N * AssetIssueFee`) remains constant regardless of the number of subsequent queries — demonstrating the cost asymmetry.

  public AssetIssueList getAssetIssueListByName(ByteString assetName) {
    if (assetName == null || assetName.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getName().equals(assetName))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
