### Title
ZKProofStore cache is not rolled back on block/session revert, allowing shielded proof re-verification bypass and double-application of a shielded transaction - (File: `chainbase/src/main/java/org/tron/core/store/ZKProofStore.java`)

### Summary
`ZKProofStore` extends the plain `TronDatabase` class instead of `TronStoreWithRevoking`, so its writes go directly to the underlying LevelDB/RocksDB source and are never registered with `SnapshotManager`/`RevokingDatabase`. Consequently, when a block (and its transactions) is popped/reverted — e.g. during a chain reorg — the `nullifierStore` and other `TronStoreWithRevoking`-backed state get rolled back, but the `zkProof` cache entry recorded by `ShieldedTransferActuator#checkProof` for that transaction's `txId` remains `true` forever. Re-applying the same `ShieldedTransferContract` transaction (same `txId`) after such a revert causes `checkProof` to short-circuit on the stale cache and skip `librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck`, while `executeShielded` treats the nullifier as fresh (since `nullifierStore` was rolled back) and applies the spend/merkle update a second time.

### Finding Description
`ShieldedTransferActuator#checkProof` in [1](#0-0)  checks `proofStore.has(tx.getTransactionId().getBytes())` and returns immediately without any zk-proof verification if the cached result is `true`. This cache is written by `recordProof` at [2](#0-1)  keyed solely on `tx.getTransactionId()`.

`ZKProofStore` is declared as `extends TronDatabase<Boolean>` and writes straight to `dbSource` with no interaction with the revoking/checkpoint machinery: [3](#0-2) . In contrast, `NullifierStore extends TronStoreWithRevoking<BytesCapsule>` [4](#0-3) , and `TronStoreWithRevoking` registers itself with `RevokingDatabase`/`SnapshotManager` in its `@PostConstruct init()` (`revokingDatabase.add(revokingDB)`) [5](#0-4) , meaning its state is rolled back on `SnapshotManager.revoke()`/session revert [6](#0-5) .

Because `ZKProofStore` is never added to `revokingDatabase`, it is excluded from this rollback set entirely. If a block containing a `ShieldedTransferContract` transaction is reverted (block pop / reorg) and the same transaction is subsequently re-included/re-applied (same transaction bytes ⇒ same `txId`), the flow is:
1. `nullifierStore` reverts — the nullifier previously marked spent is gone.
2. `proofStore` does NOT revert — `proofStore.has(txId)` is still `true`.
3. On re-validation, `checkProof` returns early at line 281 without calling `librustzcashSaplingCheckSpend`/`CheckOutput`/`librustzcashSaplingFinalCheck`.
4. `execute()` calls `executeShielded`, which sees `nullifierStore.has(nullifier) == false` (rolled back) and proceeds to `nullifierStore.put(...)` and applies the merkle tree/receive updates again [7](#0-6) , and the shielded pool value is adjusted again in `execute()` [8](#0-7) .

The nullifier double-spend guard alone is insufficient here because its state was legitimately rolled back by the chain-reorg/revert mechanism, while the proof-verification skip guard (`ZKProofStore`) was not — breaking the intended invariant that both stores move consistently with block application/reversion.

### Impact Explanation
A shielded spend/output can be re-applied (double-settled) after a legitimate block revert/reorg without the zk-proof being cryptographically re-verified, since `librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` are skipped on replay. This can duplicate shielded value into the pool and desynchronize `dynamicStore`'s `TotalShieldedPoolValue` accounting and the merkle tree state relative to actual proof validity, undermining the "one-time settlement" invariant for shielded transactions.

### Likelihood Explanation
This requires a block reorg/pop event that includes a `ShieldedTransferContract` transaction — a scenario the consensus layer's chain-switching logic is explicitly designed to support (chainbase module doc explicitly states rollback support exists for reorgs). Any full node processing a chain reorg containing a prior shielded transaction, followed by re-inclusion of the identical transaction in the new fork/chain, will trigger this. No privileged access is required; an attacker only needs to get their shielded transaction included, then benefit from (or induce, via typical liveness/fork conditions) a reorg.

### Recommendation
Make `ZKProofStore` participate in the same revoking/snapshot mechanism as other transactional stores (i.e., extend `TronStoreWithRevoking` or otherwise register it with `RevokingDatabase`/`SnapshotManager`) so that its cached proof-verification results are rolled back consistently with `nullifierStore` and other chain state on block revert/reorg. Alternatively, remove the proof-result caching entirely and always re-run the zk-proof checks in `checkProof`, since caching a security-critical "already verified" flag outside the atomic/revoking storage boundary is unsafe.

### Proof of Concept
```java
// Illustrative unit test (framework/src/test/java/org/tron/core/actuator/ShieldedTransferActuatorTest.java)
@Test
public void proofCacheSurvivesNullifierRevert() throws Exception {
  dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
  dbManager.getDynamicPropertiesStore().saveTotalShieldedPoolValue(AMOUNT);

  TransactionCapsule transactionCap = getShieldedTransferTransaction(); // build a valid shielded tx
  Contract contract = transactionCap.getInstance().toBuilder().getRawDataBuilder().getContract(0);
  ShieldedTransferActuator actuator = new ShieldedTransferActuator();
  actuator.setChainBaseManager(dbManager.getChainBaseManager()).setContract(contract)
      .setTx(transactionCap);
  TransactionResultCapsule ret = new TransactionResultCapsule();

  // First application: proof verified and recorded true, nullifier stored
  actuator.validate();
  actuator.execute(ret);

  ShieldedTransferContract shieldContract = transactionCap.getInstance().getRawData()
      .getContract(0).getParameter().unpack(ShieldedTransferContract.class);
  byte[] nullifier = shieldContract.getSpendDescription(0).getNullifier().toByteArray();

  // Simulate block revert: nullifierStore rolled back, ZKProofStore is NOT
  dbManager.getNullifierStore().delete(nullifier);
  Assert.assertFalse(dbManager.getNullifierStore().has(nullifier));
  Assert.assertTrue(dbManager.getChainBaseManager().getProofStore()
      .has(transactionCap.getTransactionId().getBytes())); // stale cache still true

  // Re-apply the SAME transaction object: checkProof should skip real verification
  // but nullifier no longer blocks the "double spend" -> executeShielded succeeds again
  actuator.validate();          // passes without calling librustzcashSaplingCheckSpend/CheckOutput
  actuator.execute(ret);        // succeeds, applying the spend/output a second time

  // Assert: the vulnerable behavior manifests as a second successful application
  // (expected secure behavior would be re-verification failing or an explicit guard
  // preventing settlement of a transaction whose supporting state was reverted)
  Assert.assertEquals(code.SUCESS, ret.getInstance().getRet(0).getContractRet());
}
```
Expected secure behavior: the second `execute()` (after nullifier-store revert) should either re-verify the zk-proof from scratch or be rejected, not silently succeed via the stale `ZKProofStore` cache.

@Component
public class ZKProofStore extends TronDatabase<Boolean> {

  @Autowired
  public ZKProofStore(ApplicationContext ctx) {
    super("zkProof");
  }

  @Override
  public void put(byte[] key, Boolean item) {
    byte[] b = {(byte) (item.booleanValue() ? 0x01 : 0x00)};
    dbSource.putData(key, b);
  }

  @Override
  public void delete(byte[] key) {
    dbSource.deleteData(key);
  }

  @Override
  public Boolean get(byte[] key) {
    return dbSource.getData(key)[0] == 0x01;
  }
