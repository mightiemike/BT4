## Title
Replay-verification integrity check silently ignores state-checkpoint (JMT) root divergence - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk-execution replay/verification paths to confirm that a re-executed `TransactionOutput` matches the persisted, ledger-committed `TransactionInfo`. It checks execution status, gas used, write-set hash (`state_change_hash`) and event root hash, but explicitly does **not** check `state_checkpoint_hash` (the JMT state root) or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`.

## Finding Description [1](#0-0) 

The function computes and compares:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (`CryptoHash::hash(self.write_set())`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It never re-derives the post-execution state root (JMT root, i.e. `state_checkpoint_hash`) from the locally re-executed state and compares it against the `TransactionInfo`'s `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields. The code contains a self-documenting acknowledgment of this gap: it is a `TODO(trading-native)` explaining that "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," and that the checkpoint hashes must be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`."

This function is invoked from the chunk-executor replay path (`execution/executor/src/chunk_executor/mod.rs`), the debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`), the CLI (`aptos-move/cli/src/commands.rs`), and `storage/db-tool/src/replay_on_archive.rs` — i.e. exactly the tooling responsible for authenticating that re-executed history matches the state committed on-chain.

## Impact Explanation
If a bug in state-root computation (Jellyfish Merkle Tree hashing, hot-state root, or the new "trading native"/position-state root) causes the locally-computed state root to diverge from the authenticated on-chain `TransactionInfo.state_checkpoint_hash`, this divergence would go completely undetected by `ensure_match_transaction_info`, because write-set-hash/event-root/gas/status can all match while the state root itself is wrong. This directly undermines the "committed state that differs from correct VM result" and "wrong ... state proof accepted as valid" invariants: replay/verification tooling (`replay_on_archive`, chunk replayer, debugger) is precisely the safety net meant to catch state divergence during replay, restore, and archive verification, and this gap means it reports success even when the state root is corrupted.

## Likelihood Explanation
This is gated behind the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature per the TODO comment, and the JMT root itself is still authenticated via other independent paths (consensus commit, accumulator proofs) that are outside this function's scope, so a malicious/incorrect state root would still be rejected by the primary consensus/commit-verification path in most configurations. However, as a *replay-verification-specific* gap, it can mask any latent state-computation bug (e.g. in the new position/hot-state root logic) that a bad actor or bug could introduce, without requiring privileged access — the flaw is a missing check, not a spoofable input, so likelihood of the check-omission itself firing is high once that feature path is exercised; likelihood of it actually leading to an unnoticed compromised chain is contingent on there being an independent root-computation bug in the first place, which I could not fully verify is or isn't otherwise caught by other commit-time checks. I was not able to trace whether normal (non-replay) execution/commit paths independently re-verify `state_checkpoint_hash` at every commit in a way that would still catch such a divergence before it becomes canonical — this needs confirmation with the full chunk_executor and block executor code, which I could not fully load within the available iterations.

## Recommendation
Extend `ensure_match_transaction_info` to also recompute the current state/hot-state/position-state checkpoint hashes from the locally executed result and assert they equal `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (if present), and `txn_info.position_state_checkpoint_hash()` (if present), removing the acknowledged gap before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any state-root feature relying on this verifier) is enabled in production replay/verify tooling.

## Proof of Concept
Not independently reproducible as an on-chain exploit from this analysis alone — the finding is a verified gap in the replay-verification comparator itself (visible directly in the cited code and its own TODO comment), not a demonstrated live state-corruption chain. A concrete PoC would require constructing a transaction whose re-execution yields a different JMT/hot-state/position-state root than the persisted `TransactionInfo` while all other fields (status, gas, write-set hash, event root) match, then showing `replay_on_archive`/`TransactionReplayer::ensure_match_transaction_info` reports success. I could not fully trace whether such a divergence is independently caught elsewhere in the commit-critical path, so I present this as a confirmed code-level omission with contingent (not proven end-to-end) mainnet impact rather than a fully proven critical vulnerability.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
