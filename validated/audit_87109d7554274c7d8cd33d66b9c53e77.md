### Title
`ensure_match_transaction_info` silently skips checkpoint-hash verification, allowing replay/verify tooling to accept a transaction output whose committed state root diverges from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
This is the local, unprivileged analog of the "ignored success flag" bug class: instead of a fallback function discarding a call's success flag, `TransactionOutput::ensure_match_transaction_info` discards part of the "success" signal of a state-commitment check — it verifies `status`, `gas_used`, `write_set` hash, and `event_root_hash` against the authenticated `TransactionInfo`, but never checks `state_checkpoint_hash` (nor the newer `position_state_checkpoint_hash`). The code says the check "passes" (`Ok(())`) even though a real commitment field was never verified.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  is the function used to validate that a locally re-executed `TransactionOutput` matches the trusted, proof-bound `TransactionInfo` for a given version — this is exactly the kind of authenticated-response/commitment binding the task calls out. It checks status, gas used, and the write-set hash (`state_change_hash`) and event root hash, all with `ensure!`.

However, the function's own trailing comment documents that it does **not** validate the checkpoint hashes: [2](#0-1) 

This means the function returns `Ok(())` — i.e., "match confirmed" — even when the `state_checkpoint_hash` / `position_state_checkpoint_hash` recorded in the authenticated `TransactionInfo` do not correspond to the state root actually produced by local execution. This is structurally identical to the sequencer-entrypoint bug: a boolean/result that is supposed to gate "was this operation actually correct" is computed but then ignored for part of its scope, so callers treat the outcome as fully verified when it is only partially verified.

Since `state_checkpoint_hash` is precisely the field meant to bind a `TransactionInfo` to the actual Merkle/JMT state root at that version (used elsewhere for `StateCheckpointTransaction`/state-checkpoint proof binding, see fields listed at [1](#0-0) ), omitting it from this consistency check breaks the state-commitment invariant: "committed state that differs from the correct VM result...verified as valid."

### Impact Explanation
`ensure_match_transaction_info` is the type used by replay/verification flows (e.g., `db-tool`'s `replay_on_archive`, and callers in `aptos-move/cli/src/commands.rs`) to assert that locally computed transaction outputs are consistent with what is claimed on ledger. Because the state/hot-state checkpoint hash is excluded from the comparison, a divergence in the actual state root (e.g., introduced by a state-computation bug, a non-deterministic native, or a malicious/corrupted backup/replay source) would not be detected by this check. Replay-verify tooling could then report a "successful" verification while the position/state root has actually diverged from correct execution — a hard-fork-class, silent divergence exactly within the scope defined by the gate ("Hard-fork-only divergence during commit, replay, restore, or proof verification").

### Likelihood Explanation
This is not attacker-triggered by itself; it's a latent gap in an integrity check that is only exercised when *some other* divergence in state-checkpoint computation already exists (e.g., the trading-native/hot-state work referenced by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` mentioned in the same comment). The comment in the code itself flags this as a known TODO ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), which indicates the aptos-core maintainers are aware the gap exists and consider it a prerequisite for enabling that feature — i.e., this is a genuine, currently-live gap in a proof/commitment consistency check, not a hypothetical.

### Recommendation
Extend `ensure_match_transaction_info` to also assert `self` state-checkpoint-derived hash(es) equal `txn_info.state_checkpoint_hash()` (and `position_state_checkpoint_hash` once that field is populated), returning an error on mismatch just as is done for `write_set_hash`, `gas_used`, and `event_root_hash`. This should be resolved (not merely left as a TODO) before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any hot-state feature relying on this consistency check is enabled on mainnet.

### Proof of Concept
I could not fully verify all call sites (`aptos-move/cli/src/commands.rs`) or confirm the exact production replay-verify code path that consumes this function due to tool-call limits reached before completing that trace. I am flagging this with medium confidence: the local root cause (the check's own comment admitting it skips the checkpoint hash) is concretely proven in-repo at [3](#0-2) , but I was not able to construct an end-to-end runnable PoC showing a concrete divergent value being accepted, nor confirm whether any caller currently relies on this function in a security-critical (mainnet, unprivileged) path versus only in developer/CLI tooling. Given this uncertainty about caller privilege and exploitability, this finding should be treated as **medium confidence** rather than definitively "critical," and would benefit from further investigation (with more tool budget) into all callers of `ensure_match_transaction_info` and whether `position_state_checkpoint_hash` is already populated/relied upon on mainnet today.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),

            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
