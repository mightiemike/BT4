### Title
Unauthenticated Request-ID collision causes Denial of Service in Gateway Vault/Confidential-Relay handlers - ([File: core/services/gateway/handlers/vault/handler.go], [File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
The Folks Finance report describes a `createUserLoan` function that first-come-first-serve keys a critical resource (`loanId`) supplied by the caller, and reverts if that key already exists — allowing an attacker to front-run and permanently occupy a victim's chosen ID, causing DoS. The Chainlink gateway `vault` and `confidentialrelay` JSON-RPC handlers exhibit the same "attacker-controlled/collidable key, first-write-wins, reject-if-exists" pattern for `req.ID`, which is used as the map key for in-flight request tracking.

### Finding Description
Both `core/services/gateway/handlers/vault/handler.go` and `core/services/gateway/handlers/confidentialrelay/handler.go` implement `newActiveRequest`, which locks a mutex, checks if `h.activeRequests[req.ID]` already exists, and if so returns an error ("request ID already exists") instead of processing the request: [1](#0-0) [2](#0-1) 

The `req.ID` is a user-supplied JSON-RPC request identifier that comes in via `HandleJSONRPCUserMessage`, is only checked for emptiness and length (`req.ID == ""`, `len(req.ID) > 200`), with no binding to a specific caller's identity/session prior to the `activeRequests` uniqueness check for the vault handler's public-key path: [3](#0-2) 

If an unauthenticated/unprivileged party can predict or observe (front-run) a victim's chosen `req.ID` before the victim's request is registered, they can pre-populate `h.activeRequests[req.ID]`, causing the legitimate request with the same ID to fail with "request ID already exists" — directly mirroring the `LoanManager.createUserLoan` DoS pattern (front-run same key → block legitimate creation).

### Impact Explanation
For the `vault` handler, this could block legitimate `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` calls or `MethodPublicKeyGet` cache-miss fetches for a targeted `req.ID`, denying users the ability to interact with the Vault capability via the gateway. For `confidentialrelay`, it would block `MethodSecretsGet`/`MethodCapabilityExec` calls. This is a griefing/availability impact (matching the reported "Griefing" impact category), not fund loss or node compromise.

### Likelihood Explanation
Exploitability depends on two factors I could **not fully verify** given remaining tool budget:
1. Whether `req.ID` values are attacker-guessable/observable before being registered (e.g., predictable client-generated UUIDs, or visible in a public mempool/queue analogous to a blockchain mempool). Unlike an on-chain `loanId` in a public mempool, gateway JSON-RPC requests are typically sent directly node-to-node over HTTP/WS and are **not broadcast to a public mempool**, which significantly reduces front-running feasibility compared to the on-chain analog.
2. Whether authorization (`h.requestProcessor.ProcessRequest`) occurs before or after the `newActiveRequest` uniqueness check — for the vault handler, authorization happens *before* `newActiveRequest` is called for the general (non-public-key) path [4](#0-3) , meaning only requests that already passed authorization can be inserted, but the `req.ID` itself doesn't appear to be scoped per-authorized-owner in the map key, so a second authorized (but different) caller reusing the same `req.ID` could still collide.

Because the transport is not a public broadcast channel like a blockchain mempool, likelihood is **lower** than the on-chain analog, and I was unable to confirm gateway-level guarantees (e.g., per-connection or per-owner namespacing of `req.ID`) that might already mitigate this.

### Recommendation
- Namespace `activeRequests` keys by a combination of authenticated owner/session identity and `req.ID`, rather than raw `req.ID` alone, so unrelated callers cannot collide on the same key.
- Alternatively, generate the request-tracking key server-side (e.g., hash of caller pubkey + client-provided ID + nonce) instead of trusting the raw client-supplied `req.ID` as the sole uniqueness key.
- Add rate limiting / short TTL cleanup (already appears present via `removeExpiredRequests` in confidentialrelay) to bound the blast radius, and confirm it is present for the vault handler too.

### Proof of Concept
Not independently verified end-to-end (no test harness run). Conceptually: a client sends `HandleJSONRPCUserMessage` with `req.ID = "victim-request-1"` before the intended victim's request reaches `newActiveRequest`; the victim's subsequent request with the same `req.ID` is rejected with error `"request ID already exists: victim-request-1"` as shown in the existing test `TestConfidentialRelayHandler_DuplicateRequestID`: [5](#0-4) 

**Caveat**: I could not confirm whether the transport layer or client SDK already generates cryptographically unpredictable, per-session `req.ID` values that would make guessing/front-running infeasible in practice — this would need verification of the gateway client/connector code and `core/capabilities/vault/gateway_vault_request_processor.go`, which I was unable to read before running out of iterations. Given the reduced likelihood due to non-public-mempool transport and unverified ID-generation guarantees, I present this as a **plausible but not conclusively proven** analog rather than a fully confirmed critical vulnerability.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	t.Parallel()
	h, cb, don, _ := setupHandler(t, 4)
	don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-dup",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
