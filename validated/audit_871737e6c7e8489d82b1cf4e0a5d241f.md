### Title
Missing address validation and unauthorized account auto-creation in `FreezeBalanceProcessor.validate` (TVM `freeze` precompile) - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java])

### Summary
`FreezeBalanceProcessor.validate` is reachable from any smart contract via the TVM `freeze` opcode (`Program.freeze`), and unlike the transaction-level `FreezeBalanceActuator` and `DelegateResourceProcessor`, it neither validates the `receiverAddress` format with `DecodeUtil.addressValid` nor requires that the receiver account already exist — it silently calls `repo.createNormalAccount(receiverAddress)` for any attacker-chosen 21-byte value and then mutates that new account's `AcquiredDelegatedFrozenBalance` fields without any signature from the receiver.

### Finding Description
`FreezeBalanceProcessor.validate` (lines 54–70) branches into a delegation path whenever `receiverAddress != ownerAddress`: [1](#0-0) 
It fetches `receiverCapsule = repo.getAccount(receiverAddress)` and, if `null`, calls `repo.createNormalAccount(receiverAddress)` — with no prior call to `DecodeUtil.addressValid(receiverAddress)` and no exception thrown when the account does not exist.

This is inconsistent with the sibling implementations in the same codebase:
- `FreezeBalanceActuator.validate` explicitly calls `DecodeUtil.addressValid(receiverAddress)` and **throws** `ContractValidateException(... + NOT_EXIST_STR)` if the receiver account does not exist, rather than creating it: [2](#0-1) 
- `DelegateResourceProcessor.validate` (the newer delegate-resource native contract) also validates the address and requires the account to pre-exist: [3](#0-2) 

`FreezeBalanceProcessor` is the only one of the three that auto-creates the receiver account. The entry point is `Program.freeze`, which is invoked by the TVM `freeze` opcode from any deployed contract, with `owner = getContextAddress()` (the calling contract) and `receiver` fully attacker-controlled from opcode stack data: [4](#0-3) 
This means an unprivileged contract deployer/caller can trigger `execute()` (lines 137–167 of `FreezeBalanceProcessor.java`), which mutates the newly created receiver's `AcquiredDelegatedFrozenBalanceForBandwidth`/`ForEnergy` fields without the receiver ever signing anything: [5](#0-4) 

Because there is no `DecodeUtil.addressValid` check, the attacker can also supply addresses that are not well-formed TRON addresses to be persisted as new `AccountCapsule` records, which the sibling actuators would reject outright.

### Impact Explanation
The concrete, reproducible impact is **unauthorized account-state mutation**: an attacker's contract can force creation of an `AccountCapsule` record for any 21-byte address of its choosing and add delegated-resource balances to it, without any signature or consent from that address's key holder. This does not directly steal funds or grant the attacker control over the victim's future account — a pre-created account with extra acquired bandwidth/energy is not harmful to the eventual owner — but it is an unauthorized write to third-party account state and enables cheap, repeatable `AccountStore` growth (one new account record per 1 TRX frozen plus opcode gas), which is disproportionate compared to how account creation is normally fee-gated/validated in the equivalent transaction-level actuators. This maps to an "unauthorized state change" / storage-bloat class of impact rather than fund theft.

### Likelihood Explanation
The attacker only needs to be able to deploy and call a smart contract (no special privilege), have at least 1 TRX of frozen balance in the calling contract's account per call, and pay the TVM opcode's energy cost. This is fully repeatable at scale, since each call can target a different receiver address and each freeze/create cycle costs a small, fixed, attacker-controlled amount. The precondition (target address not yet present in `AccountStore`) is trivially satisfiable for large numbers of unregistered addresses.

### Recommendation
Bring `FreezeBalanceProcessor.validate` in line with `FreezeBalanceActuator`/`DelegateResourceProcessor`: validate `receiverAddress` with `DecodeUtil.addressValid` before use, and either (a) reject delegation to non-existent receiver accounts (throw `ContractValidateException`), matching the legacy actuator behavior, or (b) if auto-creation is an intended feature of the TVM path, explicitly charge the standard new-account creation fee and document/gate this divergence from the transaction-level actuator so it isn't a silent, cheaper bypass.

### Proof of Concept
```java
// FreezeBalanceProcessorTest.java
@Test
public void testFreezeToNonexistentReceiverAutoCreatesAccount() throws Exception {
  byte[] owner = ...; // funded contract account
  byte[] receiver = randomUnusedAddress(); // never seen in AccountStore, no signature available
  assertNull(repo.getAccount(receiver));

  FreezeBalanceParam param = new FreezeBalanceParam();
  param.setOwnerAddress(owner);
  param.setReceiverAddress(receiver);
  param.setFrozenBalance(1_000_000L); // 1 TRX
  param.setResourceType(BANDWIDTH);

  FreezeBalanceProcessor processor = new FreezeBalanceProcessor();
  processor.validate(param, repo);     // does NOT throw, silently creates account (line 62)
  processor.execute(param, repo);

  AccountCapsule created = repo.getAccount(receiver);
  assertNotNull(created);              // account created without receiver's consent/signature
  assertTrue(created.getAcquiredDelegatedFrozenBalanceForBandwidth() > 0); // line 163 mutation
}
```
Expected result: `validate()` should reject (or require pre-existing) the unknown receiver, as `FreezeBalanceActuator` and `DelegateResourceProcessor` do; instead it succeeds and silently plants a new account record, confirming the divergence described above.
