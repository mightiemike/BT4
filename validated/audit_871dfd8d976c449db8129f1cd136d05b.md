### Title
Webhook HMAC does not bind the `X-Shopify-Shop-Domain` header, allowing cross-tenant webhook forgery - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
Shopify webhook authentication in `shopify-api`/`shopify-app-remix`/`shopify-app-react-router` validates the webhook HMAC over the raw request body only, using a single API secret shared by every shop that has the app installed. The shop identity (`X-Shopify-Shop-Domain` header) used later to select which shop's offline session/access token is loaded for the webhook handler is never included in, or cryptographically bound to, the HMAC preimage. This is the same class of bug as the reported Sequence "missing wallet binding" issue: the signature (HMAC) authenticates *that a body was signed by the shared secret*, but not *for which tenant*. A merchant who has installed the app on their own shop can capture one of their own genuinely-signed webhook deliveries and replay the exact same body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a different (victim) shop that also has the app installed, causing the app to process the payload as if it came from the victim shop and to hand the webhook handler the victim's offline access token/session.

### Finding Description
The HMAC generation/verification path only signs `rawBody`: [1](#0-0) 

`validateHmacFromRequestFactory` reads the `hmac` header, computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)`, and compares — it never mixes in `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id`.

`validateFactory` in the webhook validation module runs this body-only HMAC check first, and only afterward extracts the shop `domain` (and other) values directly from unauthenticated headers: [2](#0-1) [3](#0-2) 

The `domain` field returned as part of `WebhookValidationValid`/`WebhooksWebhookFields` is defined as a plain string sourced from a header, with no cryptographic tie to the HMAC: [4](#0-3) 

Both the Remix and React Router webhook authentication flows then use this attacker-controllable `check.domain` value directly to look up (and lazily create/refresh) that shop's offline session and access token, and pass an authenticated `admin` API client built from that session to the developer's webhook handler: [5](#0-4) 

`ensureValidOfflineSession` performs no additional binding check against the HMAC-verified data; it simply loads/creates a session for whatever `shop` string it is given: [6](#0-5) 

Because the same `apiSecretKey` is used to compute/verify HMACs for *every* shop that installs the app, any attacker who is themselves a legitimate merchant of the app can obtain a validly-HMAC'd webhook body (e.g., by triggering an event on their own store, or capturing any interceptable webhook), then resend that exact `(rawBody, hmac header)` pair directly to the app's public webhook endpoint while spoofing the `X-Shopify-Shop-Domain` (and `X-Shopify-Webhook-Id`/`X-Shopify-Topic`, also unauthenticated) header to reference a different installed shop. The HMAC check still passes because it never depended on those headers, and the app will treat the forged request as a genuine webhook for the victim shop.

### Impact Explanation
This lets any single app-installing merchant (an "unprivileged" actor relative to other tenants of the same multi-tenant app) forge webhook deliveries attributed to a different, victim shop of the same app, while the webhook handler executes with the victim shop's offline session/access token (`admin` API client). Depending on which webhook topics the app registers, this can be used to:
- Trigger app business logic keyed to the victim shop's data with attacker-chosen payload content (e.g., forged `orders/create`, `app/uninstalled`, `customers/data_request`, `shop/redact` handlers), potentially causing unauthorized administrative actions, data deletion (GDPR/redact flows), incorrect billing, or corrupted state for a shop the attacker does not own.
- Because the handler is given the real victim access token via the `admin` client, any code path where the handler echoes attacker-supplied webhook body fields back through Admin API calls (e.g., writing metafields, creating draft orders, etc., based on payload content) effectively lets the attacker perform authenticated write operations on the victim's store using the victim's own token, entirely without compromising that victim's credentials.

### Likelihood Explanation
Exploitability requires only that the attacker be a merchant who has installed the same app as the victim (a very low, "single merchant" privilege bar) and be able to send an arbitrary POST directly to the app's public webhook URL with custom headers — both are trivially available to any external actor since the webhook endpoint is a public HTTP endpoint by design and is not restricted to Shopify's IP ranges or additionally authenticated in this codebase. No secrets need to be leaked; the exploit only reuses a body/HMAC pair that was legitimately generated for the attacker's own shop.

### Recommendation
Bind the tenant identity into what is authenticated for a webhook request before it is trusted:
- Cryptographically verify that the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`, to prevent replay) is bound to the request, e.g., by additionally checking it against a per-shop expectation (an installed/known shop with a stored offline session for that domain, and/or maintaining a webhook-id de-duplication/replay cache), rather than trusting the header at face value once the shared-secret HMAC passes.
- Where feasible, incorporate the domain/topic/webhook-id into the HMAC preimage validation logic (or perform an independent server-side lookup verifying the domain is one that legitimately triggered this specific webhook, e.g., via a nonce or webhook-id uniqueness check per shop) so that a signature valid for one tenant cannot be replayed with a different tenant's identity.
- At minimum, enforce webhook-id uniqueness/idempotency tracking per shop to prevent exact-body replay across shop boundaries, since the current design otherwise allows any two installations of the app to swap identities on any webhook delivery.

### Proof of Concept
Conceptual PoC (based on code paths above, not independently executed against a live deployment):
1. Attacker installs the target app on `attacker-shop.myshopify.com`. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(apiSecretKey, B)`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)` (they can, since it is their own inbound webhook, or by running a local proxy in front of their store's webhook subscription).
3. Attacker sends a new POST directly to the app's webhook endpoint with the same body `B` and the same header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a different shop that has also installed the app).
4. `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-200`) recomputes `HMAC-SHA256(apiSecretKey, B)` and finds it equals `H`, so validation succeeds — the domain header was never part of the check.
5. `checkWebhooksHeaders` (`packages/apps/shopify-api/lib/webhooks/validate.ts:99-146`) extracts `domain = victim-shop.myshopify.com` from the (forged) header and returns it as `valid: true`.
6. `authenticateWebhookFactory` (`packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts:33-103`) calls `ensureValidOfflineSession(params, "victim-shop.myshopify.com")`, loading/refreshing the victim's real offline session and access token, and invokes the developer's webhook handler with `shop: "victim-shop.myshopify.com"`, attacker-controlled `payload`, and an authenticated `admin` client scoped to the victim's store.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
