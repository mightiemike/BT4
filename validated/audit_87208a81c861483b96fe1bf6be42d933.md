Confirmed: `apollo_compile_to_native_types::SierraCompilationConfig` has no `audited_libfuncs_only` field at all, unlike `apollo_sierra_compilation_config::SierraCompilationConfig` used for CASM compilation. [1](#0-0) [2](#0-1) 

### Title
Missing audited-libfunc restriction in Sierra→Native compilation allows in-process execution of unaudited native code from declared classes - (File: crates/apollo_compile_to_native/src/compiler.rs)

### Summary
The Sierra-to-CASM compiler path enforces `audited_libfuncs_only` (defaulting to `true`, and explicitly `true` in mainnet/sepolia-alpha production deployments) via `--allowed-libfuncs-list-name` when invoking the CASM compiler binary. [3](#0-2) [4](#0-3) 

The parallel Sierra-to-Native compiler (`SierraToNativeCompiler::compile`), which is invoked on the same declared Sierra program to produce an `AotContractExecutor` (native machine code loaded and JIT-executed directly inside the sequencer process), passes no analogous libfunc allow-list argument at all — its config type doesn't even have such a field. [5](#0-4) [1](#0-0) 

### Finding Description
When a `Declare` transaction reaches the gateway, the class's Sierra program is compiled to CASM through `SierraCompiler::compile`, which invokes the `cairo-lang-starknet` CASM compiler binary with `--allowed-libfuncs-list-name audited` (in production configs). [6](#0-5) 
This is the sequencer's sanctioned mechanism for ensuring only vetted, safety-reviewed libfuncs reach execution — analogous to a script-engine allow-list that prevents unvetted "scripts" (contract bytecode) from running unsafely.

Independently, whenever Cairo Native execution is enabled (`CairoNativeMode::WaitOnCompilation` or `LazyCompilation`), the exact same declared `SierraContractClass` is handed to `SierraToNativeCompiler::compile` via `NativeClassManager` / `process_compilation_request`, which builds the compiler command with only `--opt-level` and an output path — no libfunc allow-list flag exists, and none can be passed because `apollo_compile_to_native_types::SierraCompilationConfig` has no such field to begin with. [7](#0-6) [8](#0-7) 

The output of native compilation, `AotContractExecutor`, is not run inside the sandboxed Cairo VM interpreter — it is ahead-of-time-compiled native machine code that gets executed directly in the sequencer's own process address space when the contract is invoked (via `blockifier`'s cairo_native execution path). Unlike CASM execution (bounds-checked, interpreted, memory-safe VM semantics enforced by `cairo-vm`), native execution trusts the code generated for whatever libfunc semantics the Sierra-to-Native backend implements for that libfunc — including any libfunc not on the audited list (which exists precisely because certain libfuncs have known safety/soundness issues under adversarial input, that is why an audited allow-list exists for CASM at all). Since the native compiler doesn't reject or filter libfuncs the way the CASM compiler does, a class containing a non-audited libfunc can be silently native-compiled and its native code executed in-process, defeating the entire purpose of the audited-libfunc gate for that execution path.

### Impact Explanation
If any current or future libfunc is intentionally excluded from the audited list because its safety properties (e.g., soundness of gas/resource accounting, or memory-safety of its native lowering) haven't been fully vetted, an attacker can declare a class using that libfunc. It will be rejected by the CASM path only if `audited_libfuncs_only=true`, but the native compilation path has no equivalent check and will compile and later execute the libfunc's native lowering directly in the sequencer process. Depending on the specific libfunc's native implementation, this can range from resource-accounting/gas-metering divergence (leading to wrong fee charges or bouncer weight miscalculation) to memory-safety issues in the compiled code that runs unsandboxed inside the sequencer process — i.e., an RCE-class primitive analogous to the reported GraalScriptEngineCreator issue, since untrusted "script" (contract) code ends up executed in the trusted host process without the safety gate that the rest of the system relies on. This can also cause honest-node divergence between sequencers running with Cairo Native enabled versus those running pure CASM execution, if the native lowering of an unaudited libfunc computes different results/resources than the audited CASM semantics.

### Likelihood Explanation
Likelihood depends on whether cairo_native is enabled in the deployment (`CairoNativeMode` other than `Off`) and whether any current libfunc implementation genuinely has unsafe native lowering that the audited list was designed to exclude — I was not able to fully verify from the available index whether any of the presently-existing (non-audited) libfuncs actually have unsafe native codegen, or whether the Sierra-to-Native backend independently enforces its own libfunc support list that happens to coincide with the audited set. The compiled contract test resources indicate a `PENDING_LIBFUNCS` list (e.g., `sha512_process_block_syscall`) of libfuncs present in `allowed_libfuncs.json` but not yet in the "audited" list, showing the CASM/audited distinction is actively maintained and not purely historical, which supports there being real libfuncs currently outside the audited set. [9](#0-8) 

### Recommendation
Add an `audited_libfuncs_only`-equivalent restriction to `apollo_compile_to_native_types::SierraCompilationConfig` and pass a matching allow-list argument/validation step in `SierraToNativeCompiler::compile`, mirroring the CASM path, so that a class rejected from the audited CASM path cannot silently be native-compiled and executed in-process. Alternatively, gate native compilation eligibility behind the same libfunc validation performed for CASM before ever dispatching a class to `NativeClassManager`.

### Proof of Concept
Not independently verified with a concrete unsafe libfunc due to index limitations — the index does not contain the native codegen implementation for each libfunc, so I cannot demonstrate a specific memory-corruption trigger. The structural gap (native compiler taking no libfunc allow-list argument or config field at all, while the CASM compiler explicitly does) is directly confirmed in code: [10](#0-9) [3](#0-2) 

A concrete PoC would require identifying at least one libfunc present in `cairo_lang_starknet_classes::allowed_libfuncs`'s full list but absent from `BUILTIN_AUDITED_LIBFUNCS_LIST`, and confirming its Cairo-Native lowering has an exploitable safety issue — this requires reviewing the `cairo-native` crate's per-libfunc codegen, which is outside this repo's index. I recommend a Devin session with full repository/dependency access to pursue this further and confirm/deny exploitability.

    pub fn compile(
        &self,
        contract_class: ContractClass,
    ) -> Result<AotContractExecutor, CompilationUtilError> {
        let compiler_binary_path = &self.path_to_binary;

        let output_file = NamedTempFile::new()?;
        let output_file_path = output_file.path().to_str().ok_or(
            CompilationUtilError::UnexpectedError("Failed to get output file path".to_owned()),
        )?;
        let optimization_level = self.config.optimization_level.to_string();
        let additional_args = [output_file_path, "--opt-level", &optimization_level];
        let resource_limits = ResourceLimits::new(
            Some(self.config.max_cpu_time),
            self.config.max_file_size,
            Some(self.config.max_memory_usage),
        );
        let _stdout = compile_with_args(
            compiler_binary_path,
            contract_class,
            &additional_args,
            resource_limits,
        )?;

        Ok(AotContractExecutor::from_path(output_file.path())
            .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
            .unwrap())
    }
