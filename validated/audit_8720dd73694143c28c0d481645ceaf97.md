# Title
Missing zero-address validation in `AccountPermissionUpdateActuator.checkPermission()` allows permanent account lockout - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets any account owner replace their `owner`/`witness`/`active` permissions in a single unprivileged transaction. The key-address validation performed in `checkPermission()` only calls `DecodeUtil.addressValid()`, which checks address length/prefix format but does not reject the all-zero address. An account can therefore set its `Owner` permission's sole key to the zero address, permanently losing the ability to ever update permissions again — structurally the same bug class as the reported `MainToken.set_mint_multisig()` issue: a critical control field can be set to the zero address with no safeguard, causing irrecoverable loss of control.

### Finding Description
`AccountPermissionUpdateActuator.validate()` requires an `Owner` permission and calls `checkPermission(owner)` [1](#0-0) . Inside `checkPermission()`, each key's address is checked only via `DecodeUtil.addressValid()` [2](#0-1) , and weight/threshold consistency is verified, but there is no check that the address is non-zero or corresponds to a controllable key. `execute()` then unconditionally overwrites the account's permissions with `account.updatePermissions(...)` [3](#0-2) , with no way to revert since future `AccountPermissionUpdateContract` transactions themselves require a valid signature satisfying the (now zero-address-only) `Owner` permission.

I located `DecodeUtil.addressValid` at `common/src/main/java/org/tron/common/utils/DecodeUtil.java`, but was not able to fully re-verify its exact implementation in this session (index limits truncated the read). Based on its usage pattern across the codebase (only ever used to reject malformed/wrong-length/wrong-prefix addresses, never to reject the zero address specifically), it is highly likely it does not special-case the zero address; a Devin session with full file access should confirm this directly.

### Impact Explanation
If a user (accidentally, or by a crafted wallet/UI bug) submits an `AccountPermissionUpdateContract` whose `Owner` permission contains only the zero address as a key, the account's owner-permission-controlled actions (which include issuing any further `AccountPermissionUpdateContract`) become permanently unsignable, since nobody holds the private key for the zero address. This is an irrecoverable "bricking" of account governance — a concrete invalid/halt-state impact, directly analogous to the reported loss of `minting_multisig`.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires either user/wallet error or a deliberate self-inflicted action, and the transaction is otherwise fully valid (multi-sign must be enabled via `getAllowMultiSign()` check [4](#0-3) ). It doesn't require any privileged role — any normal account holder can trigger it on their own account, matching the "unprivileged-user analog in actuators" criterion.

### Recommendation
In `checkPermission()`, explicitly reject an all-zero key address (and/or require that at least the transaction signer's own key, or some recoverable key, remain among the `Owner` permission's keys) before accepting the new permission set, mirroring the recommended fix for `set_mint_multisig()`.

### Proof of Concept
1. Attacker/user constructs `AccountPermissionUpdateContract` for `owner_address = A`, with `owner` permission containing a single `Key{address = 0x410000000000000000000000000000000000000000, weight = 1}` and `threshold = 1`.
2. `validate()` passes: address length/prefix is valid per `DecodeUtil.addressValid`, weight sum (1) ≥ threshold (1), keys distinct, count > 0.
3. `execute()` calls `account.updatePermissions(...)`, overwriting account A's owner permission.
4. Account A can no longer produce a valid signature satisfying the new `Owner` permission (no private key for the zero address exists), permanently losing the ability to submit any further `AccountPermissionUpdateContract` or other owner-permission-gated transactions.
