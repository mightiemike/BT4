### Title
Unauthorized universal-payload execution against any victim's UEA via `isCEA` inbound routing bypassing owner-signature binding - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
The Lens `tryMigrate()` bug allowed an attacker to force a "consented" relationship (a follow) onto a victim by satisfying a shallow, spoofable precondition ("holds the token") instead of real authorization. Push Chain's `isCEA` inbound-execution path has the same failure shape: the check that gates a trusted, signature-exempt EVM call ("recipient is a real deployed UEA") can be satisfied by pointing at *any* existing user's UEA — not necessarily one belonging to the party that triggered the inbound — after which the module executes an attacker-supplied `UniversalPayload`/`VerificationData` against that victim's UEA using the module's own signature-check-exempt calling context.

### Finding Description
`MsgVoteInbound` → ballot finalization → `ExecuteInboundFundsAndPayload` / `ExecuteInboundGasAndPayload` process an `Inbound` record whose `Sender`, `Recipient`, `Amount`, `UniversalPayload`, and `VerificationData` are all derived from a source-chain gateway event that an unprivileged attacker fully controls (they are the "sender" of that source-chain transaction).

For `TxType_FUNDS_AND_PAYLOAD` / `TxType_GAS_AND_PAYLOAD` with `IsCEA = true`, `ValidateForExecution` only requires that `Recipient` be a syntactically valid hex address [1](#0-0) . The keeper then checks whether that recipient is a genuine deployed UEA via `CallFactoryGetOriginForUEA` [2](#0-1)  — this check only confirms the address *is somebody's* UEA, not that it belongs to the inbound's sender. If it is a UEA, funds are deposited into it, and execution falls through to an unconditional call:

```go
receipt, payloadErr = k.ExecutePayloadV2(ctx, ueModuleAddr, ueaAddr, utx.InboundTx.UniversalPayload, utx.InboundTx.VerificationData)
``` [3](#0-2) 

The same fallthrough exists in the gas-and-payload path [4](#0-3) . Both `UniversalPayload` (decoded from attacker-controlled `raw_payload`) and `VerificationData` are preserved for `IsCEA` payload types by `NormalizeForTxType` [5](#0-4) , so the attacker fully controls both arguments.

`ExecutePayloadV2` invokes `CallUEAExecutePayload` with `evmFrom = ueModuleAddr` (the `uexecutor` module account) [6](#0-5) [7](#0-6) . Per the module's own documentation, the UEA's owner-signature check is enforced only when the EVM caller is *not* the `UNIVERSAL_EXECUTOR_MODULE` address; the module is explicitly a trusted, signature-check-exempt caller in the normal (non-CEA) flow because there `ueaAddr` is *deterministically derived from the inbound's own `Sender`* via `CallFactoryToGetUEAAddressForOrigin` [8](#0-7) .

The `isCEA` path breaks that invariant: `ueaAddr` there is `utx.InboundTx.Recipient` — an address the attacker chooses freely, unrelated to their own derived UEA — yet the module still calls `ExecutePayloadV2` as the trusted, signature-exempt caller. The net effect: an attacker can name *any* existing victim UEA as the `Recipient` of a self-crafted, cheap source-chain inbound event, and have the module execute an attacker-authored `UniversalPayload` (with arbitrary `VerificationData` since the check on it is bypassed for the module-as-caller path) against that victim's UEA — an unauthorized state transition/execution on someone else's account, exactly analogous to forcing an unwanted state change onto a victim by satisfying a shallow ownership/"holder" check instead of genuine consent.

### Impact Explanation
This falls squarely within "unauthorized UEA or CEA execution, unauthorized module-originated EVM execution, or unauthorized state transitions in universal execution flows" and potentially "stealing, draining ... of user or protocol-controlled funds," since `executeUniversalTx` on a UEA can, depending on the UEA implementation, move the UEA's PRC20/native balances or call arbitrary downstream contracts on the victim's behalf. Any funded UEA on Push Chain could be targeted by simply relaying a cheap event on any supported source chain that names that UEA as `Recipient`.

### Likelihood Explanation
High reachability: the trigger is a single unprivileged inbound transaction on any enabled source chain (only requires the gateway contract to emit a `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` event with `IsCEA=true` and `Recipient` set to a target UEA address — data fully controlled by the transaction's sender). Ballot voting by honest Universal Validators only attests that this event genuinely occurred on the source chain, not that its content is benign; consensus does not prevent this since the malicious `Recipient`/payload content is part of the honestly-observed event itself. No privileged actor or malicious node/validator assumption is required.

### Recommendation
Enforce a genuine ownership/authorization binding for the `isCEA` + UEA branch before allowing the signature-exempt module-originated `ExecutePayloadV2` call:
- Require that when the resolved `Recipient` is a UEA, the payload execution still be authenticated against that UEA's real owner (i.e., do not treat the module as signature-exempt for `isCEA` targets that were not derived from `InboundTx.Sender`), or
- Restrict `isCEA` UEA-targeted flows to deposit-only (no `ExecutePayloadV2` call), routing payload execution only through the deterministic sender-derived UEA path, or
- Require `VerificationData` to be independently verified against the target UEA's owner key even when `evmFrom == UNIVERSAL_EXECUTOR_MODULE`, whenever the UEA being called differs from the one derived from `InboundTx.Sender`.

### Proof of Concept
1. Identify a victim's deployed UEA address `V` (fetchable via `getUEAForOrigin` on the factory, public state).
2. As an attacker, submit/trigger a source-chain gateway transaction that emits a `FUNDS_AND_PAYLOAD` (or `GAS_AND_PAYLOAD`) inbound event with:
   - `IsCEA = true`
   - `Recipient = V`
   - `raw_payload` decoding to an attacker-chosen `UniversalPayload` (e.g., a call transferring the UEA's PRC20 balance to the attacker)
   - `VerificationData` set to arbitrary attacker-controlled bytes.
3. Universal Validators honestly observe and vote `MsgVoteInbound` for this real (attacker-initiated) source-chain event; ballot passes because the event genuinely happened.
4. `ExecuteInboundFundsAndPayload` resolves `V` via `CallFactoryGetOriginForUEA`, confirms it is a UEA, deposits funds if `Amount>0`, then calls `ExecutePayloadV2(ueModuleAddr, V, attackerPayload, attackerVerificationData)`.
5. Because `evmFrom == ueModuleAddr` is treated as the signature-check-exempt caller, the UEA `V` executes the attacker's payload without any proof that the attacker holds `V`'s owner key, resulting in unauthorized execution/fund movement from the victim's UEA.

Note: full confirmation that the on-chain UEA Solidity contract (out of this repo, in `push-chain-core-contracts`) truly skips signature verification when `msg.sender == UNIVERSAL_EXECUTOR_MODULE` could not be independently verified from this repository alone — this is stated as the documented design in `x/uexecutor/README.md` and is the basis for the "safe under Signer≠Owner" reasoning for the non-CEA flow, but that reasoning implicitly assumes `ueaAddr` is always the sender's own UEA, an assumption the `isCEA` code path violates.

func (p *Inbound) NormalizeForTxType() error {
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		// Payload types: recipient is only meaningful when isCEA
		if !p.IsCEA {
			p.Recipient = EvmZeroAddress
		}
		// Always clear universal_payload — whatever the UV sends is ignored.
		// Core validator decodes from raw_payload.
		p.UniversalPayload = nil

		// Decode raw_payload → universal_payload
		if p.RawPayload != "" {

			}
			if decoded == nil {
				return fmt.Errorf("raw_payload decoded to nil for payload tx type")
			}
			p.UniversalPayload = decoded
			p.RawPayload = "" // clear after successful decode to save storage
		}

func (k Keeper) ExecutePayloadV2(ctx context.Context, evmFrom common.Address, ueaAddr common.Address, universalPayload *types.UniversalPayload, verificationData string) (*vmtypes.MsgEthereumTxResponse, error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Debug("execute payload v2",
		"uea", ueaAddr.Hex(),
		"from", evmFrom.Hex(),
	)

	// Step 1: Validate payload and verificationData early (fast-fail before EVM work)
	if _, err := types.NewAbiUniversalPayload(universalPayload); err != nil {
		return nil, errors.Wrapf(err, "invalid universal payload")
	}

	verificationDataVal, err := utils.HexToBytes(verificationData)
	if err != nil {
		return nil, errors.Wrapf(err, "invalid verificationData format")
	}

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}

func (k Keeper) CallUEAExecutePayload(
	ctx sdk.Context,
	from, ueaAddr common.Address,
	universal_payload *types.UniversalPayload,
	verificationData []byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	abi, err := types.ParseUeaABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UEA ABI")
	}

	abiUniversalPayload, err := types.NewAbiUniversalPayload(universal_payload)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal payload")
	}

	gasLimit := new(big.Int)
	gasLimit, ok := gasLimit.SetString(universal_payload.GasLimit, 10)
	if !ok {
		return nil, fmt.Errorf("invalid gas limit: %s", universal_payload.GasLimit)
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,
		ueaAddr,
		big.NewInt(0),
		gasLimit,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"executeUniversalTx",
		abiUniversalPayload,
		verificationData,
	)
}

#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
