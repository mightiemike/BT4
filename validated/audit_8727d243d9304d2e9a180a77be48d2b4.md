## Title
Stale `assets` state read during external transfer in `redeem` inflates share price for reentrant deposit/redeem calls - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`)

### Summary
`deposit` guards against reentrancy during a flashloan via `(asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)`, but `redeem` has no equivalent guard. In `redeem`, the `assets` data-var (which backs `convert-to-assets-preview`/`convert-to-shares-preview` share pricing) is only decremented *after* the external underlying transfer (`send-underlying`) completes, mirroring exactly the check-effects-interactions violation described in the external report for `TransactionManager.removeLiquidity`. [1](#0-0) 

### Finding Description
1. `redeem` reads `current-assets` from `(var-get assets)` at the start of the call.
2. It burns the caller's shares via `(try! (ft-burn? zft amount account))`.
3. It then performs the external transfer via `(try! (send-underlying inkind recipient))` — this can invoke a `<ft-trait>`/`stx-transfer?` code path.
4. Only *after* the transfer returns does it apply `(var-set assets (- current-assets inkind))`.

If the underlying transfer path can trigger a callback into this same vault (e.g. a reentrant `deposit`/`redeem` call, matching how the report describes reentering `TransactionManager` via `removeLiquidity` or `fulfill`), the callback would read `(var-get assets)` still holding the pre-decrement value — i.e., a value that has not yet been invalidated even though the shares corresponding to it have already been burned. Any `convert-to-assets-preview`/`convert-to-shares-preview` computation performed by that reentrant call would price shares against an artificially inflated `assets` total, exactly the "artificially increased share value" mechanism from the report. [2](#0-1) 

The `deposit` function explicitly anticipates this class of risk by checking `in-flashloan` before proceeding, but that flag only covers the flashloan code path, not a token-triggered reentrant call during `redeem`'s own transfer step, and `redeem` itself carries no reentrancy check at all. [3](#0-2) 

### Impact Explanation
If exploitable, this would let a user extract more underlying assets than their shares entitle them to, or mint shares at a stale (favorable) price during the reentrant window — a direct theft of user/protocol funds at rest, landing in the Critical impact class.

### Likelihood Explanation
Low/uncertain. This requires the underlying asset's transfer mechanism (or an intermediate call in `send-underlying`) to yield control back into the vault contract before completing — the same caveat the original report itself makes about "tokens that behave as described... might be rare or not exist at all." I was not able to fully verify from the index whether `send-underlying`'s implementation performs a call capable of reentering the vault (its definition body was not retrieved before the tool budget was exhausted), so root-cause confirmation on the exact external-call semantics is incomplete.

### Recommendation
Update `assets` state before performing the external transfer in `redeem` (and any other function following the same burn-then-transfer-then-account order), or add an explicit reentrancy guard consistent with the one already used in `deposit`.

### Proof of Concept
Not fully constructed — depends on confirming `send-underlying`'s exact external-call behavior, which I could not retrieve within the available tool budget. The sequence above is the theoretical PoC outline consistent with the pattern found in code.
