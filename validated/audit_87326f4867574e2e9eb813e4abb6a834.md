### Title
Disk-index bucket restart-reuse trusts on-disk `IndexEntry<T>` layout without an ABI/type version check - ([File: bucket_map/src/bucket.rs])

### Summary
The `_TYPE_RETRY_RECEIVE_POOL` bug class is: bytes persisted by one on-chain/runtime "version" get blindly re-decoded under a *different* current version's struct layout because no version tag is checked before interpreting the bytes as the current type. The closest in-scope analog is Agave's disk-backed accounts index (`bucket_map`), which persists raw `IndexEntry<T>` records across validator restarts and reuses that file on the next run purely by matching `(buckets, max_search)` in a small `restart.rs` header — it never records or checks a layout/type identity for `IndexEntry<T>` itself.

### Finding Description
`RestartableBucket`/`Restart` in `bucket_map/src/restart.rs` persist only three things to allow disk-index-file reuse across restarts: `version` (a static const bumped only when the *restart file's own* format changes), `buckets`, and `max_search` [1](#0-0) . `Restart::get_restart_file` only rejects reuse if the file length or these three header fields mismatch [2](#0-1) ; nothing here validates the record layout of the actual index bucket files that get reused.

The actual reuse of an on-disk bucket file happens in `Bucket::new`: it computes `elem_size` from `std::mem::size_of::<IndexEntry<T>>()` in the *currently running binary* and calls `BucketStorage::load_on_restart` with that size, remapping the old file's raw bytes directly as `IndexEntry<T>` [3](#0-2) . `BucketStorage::load_on_restart` derives `num_elems` purely by dividing `(file_len - header_offset)` by the *current* `elem_size` and, if that's non-zero, mmaps the file and reinterprets every slot as `IndexEntry<T>` with no check that this file was ever written with that same layout [4](#0-3) .

This is structurally identical to the reported bug class: bytes written under one struct/version definition are decoded under a different current struct/type definition, keyed only on the destination's belief that "this is my own file" (via the `restart_config_file`'s random `file_name`), never on an explicit content/layout version match. If `IndexEntry<T>`'s layout changes between Agave releases (field reordering, added/removed fields, or a different `T` from a config change such as bins/disk-index settings) but `size_of::<IndexEntry<T>>()` happens to remain unchanged (or coincidentally divides the old file size), the validator will silently reinterpret stale bytes as valid index entries — corrupting `key`, `ref_count`, or slot-list/data-bucket offsets used to locate accounts. Unlike the toki-bridge report where a decode failure at least reverts, here corrupted `IndexEntry` fields feed straight into pointer arithmetic against `data` buckets (see `read_value`'s `data_buckets[data_bucket_ix]` indexing and `MultipleSlots::data_loc`) [5](#0-4) , which can silently point at the wrong data-bucket slot (returning a different account's stored slot-list) or panic.

### Impact Explanation
Because the accounts index is authoritative for slot->storage-location mapping, silently reinterpreting stale/foreign bytes as `IndexEntry<T>` could make lookups resolve to the wrong `ref_count`/slot-list, causing an honest node to read wrong account/version data (stale or wrong-version account load) or to panic (`assert!(!data_bucket.is_free(loc))` in `read_value`), producing a validator crash — both are in the accepted impact set (stale/wrong-version account load, honest-node divergence/panic). This only manifests on-disk-index configurations and requires the coincidence that the current binary's `size_of::<IndexEntry<T>>()` still evenly divides the stale file's length, so the practical trigger window (e.g., across an upgrade that changes `IndexEntry`'s layout while keeping its size the same, or reuses generic type parameters differently) is narrow and not concretely demonstrated in this codebase snapshot.

### Likelihood Explanation
Low-to-Medium. The restart/reuse path is exercised only when `restart_config_file` is configured (disk-index enabled) and the process restarts with a leftover index file whose `file_name`/`random` still match the restart config — this is the normal fast-restart path, not attacker-triggered. The missing piece is a genuine version/layout guard on `IndexEntry<T>` bytes analogous to `HEADER_VERSION` already used for the restart config file itself; today, only the restart config's own header is versioned, not the index bucket file's element layout, which is inconsistent and is the gap that mirrors the reported bug class.

### Recommendation
Persist an explicit layout/type identity (e.g., a hash of `IndexEntry<T>`'s size and a compile-time layout constant, similar to `HEADER_VERSION`) alongside each bucket file (or in the `OneIndexBucket`/`Header` restart record), and check it in `BucketStorage::load_on_restart`/`Bucket::new` before reusing a file, deleting and recreating the bucket storage if the check fails — exactly the "compare version before decoding, reject unsupported versions" recommendation from the source report.

### Proof of Concept
1. Configure a validator with disk index (`restart_config_file` set) and let it run, persisting `IndexEntry<T>` bucket files under the accounts-index drives.
2. Upgrade the Agave build to a version where `IndexEntry<T>`'s field layout changes (e.g., reordering `key`/slot-count fields) but `std::mem::size_of::<IndexEntry<T>>()` stays numerically the same (plausible with padding changes).
3. Restart the validator with the new binary; `Restart::get_restart_file` still matches (`buckets`/`max_search` unchanged), so `Bucket::new` reuses the old file via `BucketStorage::load_on_restart`, remapping the stale bytes as the new `IndexEntry<T>` layout with no check.
4. Subsequent index lookups (`read_value`) return corrupted `ref_count`/slot-list data or panic on `assert!(!data_bucket.is_free(loc))`, either silently serving a wrong account version or crashing the node.

    pub(crate) fn get_restart_file(config: &BucketMapConfig) -> Option<Restart> {
        let path = config.restart_config_file.as_ref()?;
        let metadata = std::fs::metadata(path).ok()?;
        let file_len = metadata.len();

        let expected_len = Self::expected_len(config.max_buckets);
        if expected_len as u64 != file_len {
            // mismatched len, so ignore this file
            return None;
        }

        let file = OpenOptions::new()
            .read(true)
            .write(true)
            .create(false)
            .open(path)
            .ok()?;
        let mmap = unsafe { MmapMut::map_mut(&file).unwrap() };

        let restart = Restart { mmap };
        let header = restart.get_header();
        if header.version != HEADER_VERSION
            || header.buckets != config.max_buckets as u64
            || header.max_search != config.max_search.unwrap_or(MAX_SEARCH_DEFAULT)
        {
            // file doesn't match our current configuration, so we have to restart with fresh buckets
            return None;
        }

        Some(restart)
    }

    /// load and mmap the file that is this disk bucket if possible
    pub(crate) fn load_on_restart(
        path: PathBuf,
        elem_size: NonZeroU64,
        max_search: MaxSearch,
        stats: Arc<BucketStats>,
        count: Arc<AtomicU64>,
    ) -> Option<Self> {
        let offset = Self::get_offset_to_first_data();
        let num_elems = std::fs::metadata(&path)
            .ok()
            .map(|metadata| metadata.len().saturating_sub(offset) / elem_size)?;
        if num_elems == 0 {
            return None;
        }
        let mmap = Self::map_open_file(&path, false, 0, &stats)?;
        Some(Self {
            path,
            mmap,
            cell_size: elem_size.into(),
            count,
            stats,
            max_search,
            contents: O::new(Capacity::Actual(num_elems)),
            // since we loaded it, it persisted from last time, so we obviously want to keep it present disk.
            delete_file_on_drop: false,
        })
    }
