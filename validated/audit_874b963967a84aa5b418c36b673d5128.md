### Title
Payload builder computes base fee as `0` instead of `INITIAL_BASE_FEE` at the London activation boundary, producing a reth-built block that fails its own consensus validation - (File: `crates/ethereum/evm/src/lib.rs`)

### Summary
`EthEvmConfig::next_evm_env` derives the next block's base fee via `EthChainSpec::next_block_base_fee`, whose default implementation returns `None` whenever the parent header has no `base_fee_per_gas` (i.e. the parent is pre-London). The caller then does `.unwrap_or_default()`, silently coercing that `None` into `0`. Meanwhile, reth's own consensus validation (`validate_against_parent_eip1559_base_fee`) special-cases exactly this situation and requires the base fee of the first post-London block to equal `INITIAL_BASE_FEE` (1 gwei), not `0`. As a result, when reth builds the very first block after the London fork activates, it assembles a header with `base_fee_per_gas = Some(0)`, which its own validator (and every spec-compliant client) would reject.

### Finding Description
`EthChainSpec::next_block_base_fee` (default trait method) is defined in [1](#0-0) :

```rust
fn next_block_base_fee(&self, parent: &Self::Header, target_timestamp: u64) -> Option<u64> {
    Some(calc_next_block_base_fee(
        parent.gas_used(),
        parent.gas_limit(),
        parent.base_fee_per_gas()?,
        self.base_fee_params_at_timestamp(target_timestamp),
    ))
}
```

`parent.base_fee_per_gas()?` returns `None` for the whole function when the parent header predates London (no base fee field set). This is used by the block-building path in `EthEvmConfig::next_evm_env`: [2](#0-1) 

```rust
fn next_evm_env(
    &self,
    parent: &Header,
    attributes: &NextBlockEnvAttributes,
) -> Result<EvmEnv, Self::Error> {
    Ok(EvmEnv::for_eth_next_block(
        parent,
        NextEvmEnvAttributes { ... },
        self.chain_spec().next_block_base_fee(parent, attributes.timestamp).unwrap_or_default(),
        ...
    ))
}
```

When `next_block_base_fee` returns `None` (parent pre-London, current block London-active), `.unwrap_or_default()` yields `0`, which is fed straight into `block_env.basefee`. `EthBlockAssembler::assemble_block` then unconditionally copies this value into the header whenever London is active for the block being built: [3](#0-2) 

```rust
let base_fee_per_gas = self
    .chain_spec
    .is_london_active_at_block(block_number)
    .then(|| evm_env.block_env.basefee());
```

So the block reth builds at the London transition gets `base_fee_per_gas = Some(0)`.

Contrast this with reth's own validation logic, `validate_against_parent_eip1559_base_fee`, which explicitly handles the transition block and expects `INITIAL_BASE_FEE`, not `0`: [4](#0-3) 

```rust
let expected_base_fee = if chain_spec
    .ethereum_fork_activation(EthereumHardfork::London)
    .transitions_at_block(header.number())
{
    alloy_eips::eip1559::INITIAL_BASE_FEE
} else {
    chain_spec.next_block_base_fee(parent, header.timestamp()).ok_or(ConsensusError::BaseFeeMissing)?
};
if expected_base_fee != base_fee {
    return Err(ConsensusError::BaseFeeDiff(...))
}
```

The two code paths compute two different equalities for the exact same boundary condition: the builder path silently defaults to `0`, while the validator path (matching EIP-1559 and every other client's implementation) expects `INITIAL_BASE_FEE`. This is the same root-cause pattern as the referenced report: a code path that skips/omits the intended guard (here, the special-case handling for the fork boundary) that exists elsewhere in the codebase, producing a divergent, spec-violating value.

### Impact Explanation
This breaks the equality "a reth-built block passes reth's (and every other client's) own validation of that same block." Any chain (custom devnet, test network, or any deployment where London activates at a non-genesis block while the node is producing blocks via the Engine API/payload builder) that hits this exact activation boundary will have reth build an invalid block: `base_fee_per_gas = 0` instead of `INITIAL_BASE_FEE`. That block would be rejected by every spec-compliant peer client and even by reth's own `validate_against_parent_eip1559_base_fee` on execution/sync, causing the produced payload to be invalid and the chain to stall at that boundary until manual intervention. This matches the High-impact category: "reth-built blocks rejected by other clients … stalling nodes until manual intervention."

### Likelihood Explanation
No malicious actor or privileged access is required — this triggers deterministically whenever a chain configuration activates London at a block after genesis while the EL is producing blocks through the standard payload-building flow (`default_ethereum_payload` → `builder_for_next_block` → `next_evm_env`). This is a realistic configuration for private/test networks and non-mainnet chains that reuse `EthEvmConfig`/`NextBlockEnvAttributes`, since mainnet activated London at genesis for post-merge builder flows but custom chains frequently configure hardfork block numbers independently.

### Recommendation
Mirror the special-case handling used in `validate_against_parent_eip1559_base_fee` inside `EthChainSpec::next_block_base_fee` (or at its call site in `next_evm_env`): when the parent lacks a base fee because the target block is the first block where London is active, return `INITIAL_BASE_FEE` instead of `None`/`0`. Concretely, add a check using `ethereum_fork_activation(EthereumHardfork::London).transitions_at_block(...)` (or the timestamp equivalent) before falling back to `unwrap_or_default()`, so the two code paths compute the same value.

### Proof of Concept
1. Configure a `ChainSpec` where London activates at some block `N > 0` (not at genesis) and the chain is otherwise post-merge so that block building goes through `builder_for_next_block`/`default_ethereum_payload`.
2. Build block `N` via the payload builder: `parent` (block `N-1`) has `base_fee_per_gas = None`.
3. `EthChainSpec::next_block_base_fee(parent, ts)` returns `None` because `parent.base_fee_per_gas()?` short-circuits.
4. `next_evm_env` computes `basefee = None.unwrap_or_default() = 0`.
5. `EthBlockAssembler::assemble_block` sets `header.base_fee_per_gas = Some(0)` because London is active at block `N`.
6. Feeding this same header/parent pair into `validate_against_parent_eip1559_base_fee` yields `expected_base_fee = INITIAL_BASE_FEE (1_000_000_000)`, which does not match the built header's `base_fee_per_gas = 0`, returning `ConsensusError::BaseFeeDiff`. The block reth just built is rejected by its own validator.

/// Validates the base fee against the parent and EIP-1559 rules.
#[inline]
pub fn validate_against_parent_eip1559_base_fee<ChainSpec: EthChainSpec + EthereumHardforks>(
    header: &ChainSpec::Header,
    parent: &ChainSpec::Header,
    chain_spec: &ChainSpec,
) -> Result<(), ConsensusError> {
    if chain_spec.is_london_active_at_block(header.number()) {
        let base_fee = header.base_fee_per_gas().ok_or(ConsensusError::BaseFeeMissing)?;

        let expected_base_fee = if chain_spec
            .ethereum_fork_activation(EthereumHardfork::London)
            .transitions_at_block(header.number())
        {
            alloy_eips::eip1559::INITIAL_BASE_FEE
        } else {
            chain_spec
                .next_block_base_fee(parent, header.timestamp())
                .ok_or(ConsensusError::BaseFeeMissing)?
        };
        if expected_base_fee != base_fee {
            return Err(ConsensusError::BaseFeeDiff(GotExpected {
                expected: expected_base_fee,
                got: base_fee,
            }))
        }
    }

    Ok(())
}
