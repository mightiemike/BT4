Based on my investigation, I found a genuine analog to the "small order spam" DoS pattern in the Push Chain node's inbound-voting/ballot-finalization pipeline.

### Title
Unbounded `PendingInbounds` linear scan on every ballot termination enables cheap inbound-tx flooding DoS - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
`TalentirMarketplaceV1`'s bug let an attacker submit many cheap orders that must always be traversed first, causing legitimate orders to run out of gas. The Push Chain analog is `BallotHooks.afterInboundBallotTerminal`, which — every time *any* inbound ballot reaches a terminal state (PASSED/REJECTED/EXPIRED) — performs a full linear `Walk` over the entire `PendingInbounds` collection to find the entry whose variant carries the terminating `ballotID`, because "Ballot IDs are one-way canonical digests (not reversible)".

### Finding Description
`RecordInboundVote` creates one `PendingInboundEntry` per unique `utx_key` (`source_chain:tx_hash:log_index`) and appends a `variant` for every distinct byte-encoding validators observe for that inbound. [1](#0-0) 

Each such entry's ballot is created and voted on via `VoteOnInboundBallot`/`VoteOnBallot`, and when quorum is reached, `MarkBallotFinalized` fires `fireBallotTerminalHook`, which invokes `BallotHooks.AfterBallotTerminal` → `afterInboundBallotTerminal`. [2](#0-1) 

That handler does a full `Walk` across **all** `PendingInbounds` entries to locate the one owning the terminating ballot ID: [3](#0-2) 

This lookup cost is `O(total pending inbound entries)` and is paid **once per terminal ballot event, for every ballot**, not amortized. Any unprivileged external party can trigger new `PendingInboundEntry` creation cheaply and at will simply by submitting many distinct, tiny/dust cross-chain transfers on a supported external source chain — honest validators will honestly observe and vote on each one via `MsgVoteInbound`/`VoteInbound`, each creating its own `utx_key` entry. [4](#0-3) 

Compounding this, ballot expiry is effectively disabled by design: `DefaultExpiryAfterBlocks = 100_000_000` (~19 years), explicitly because "Ballots should not expire without an escape hatch for stuck pending items." [5](#0-4) 

While honest validators eventually finalize each dust inbound once quorum is reached (removing it from `PendingInbounds`), an attacker can keep the size of `PendingInbounds` large by continuously injecting new dust inbound events faster than they finalize (block-time/mempool/vote-latency bound), forcing every terminal-ballot event — including those from legitimate users' inbound transfers — to pay an `O(n)` scan cost where `n` is the concurrently-pending count. This mirrors the report's core mechanism: cheap attacker-controlled entries that legitimate traffic is forced to iterate through, causing gas/computation blow-up on the honest path.

### Impact Explanation
This is a state-machine-execution DoS reachable purely by unprivileged submission of ordinary (if dust-valued) cross-chain transfers — no privileged validator, relayer, or admin action is required. As `PendingInbounds` grows, `VoteInbound` processing (which every validator must execute to finalize legitimate deposits) becomes progressively more expensive per finalization, degrading throughput of the universal-execution inbound pipeline and delaying/failing legitimate users' cross-chain deposits — an in-scope, non-network-level DoS under "Push Chain Allowed Impact Gate".

### Likelihood Explanation
Moderate-to-high. The attacker needs only to originate many small/dust value transfers from any supported external chain into the gateway/registry-tracked contract — a purely economic cost (source-chain gas), not requiring any Push Chain privilege, key compromise, or validator collusion. The near-infinite ballot expiry (100M blocks) means there is no natural pressure evicting stale/slow-to-quorum entries, so the attacker can sustain an elevated `PendingInbounds` size indefinitely by continuously injecting new dust inbounds.

### Recommendation
Replace the `ballotID`-to-`utxKey` reverse lookup with a direct index (e.g., store `ballotID → utxKey` mapping at vote-recording time in `RecordInboundVote`) so `afterInboundBallotTerminal` performs an `O(1)` lookup instead of an `O(n)` `Walk`. Additionally, consider introducing a minimum-inbound-amount threshold or per-source-chain rate limiting for inbound observation, and reintroduce a bounded, sane `ExpiryAfterBlocks` (with a proper escape-hatch/refund flow) so stale pending entries cannot accumulate unbounded.

### Proof of Concept
1. Attacker sends `N` (e.g., thousands of) tiny-value transfers from an enabled external source chain to the Push Chain gateway in quick succession, each with a unique `tx_hash`/`log_index`.
2. Honest universal validators observe and submit `MsgVoteInbound` for each, causing `RecordInboundVote` to create `N` concurrent `PendingInboundEntry` records via `k.PendingInbounds.Set` ( [6](#0-5) ).
3. As each ballot reaches quorum and finalizes, `afterInboundBallotTerminal`'s `k.PendingInbounds.Walk` scans the full, growing set to locate the matching variant ( [7](#0-6) ), so total work across all `N` finalizations approaches `O(N^2)`.
4. If the attacker sustains injection faster than the honest quorum-finalization rate, `PendingInbounds` size — and thus per-finalization scan cost — keeps growing, slowing down or stalling processing of concurrent legitimate users' inbound finalizations on the same path.

```go
func (k Keeper) MarkBallotFinalized(ctx context.Context, id string, status types.BallotStatus) error {
	if status != types.BallotStatus_BALLOT_STATUS_PASSED && status != types.BallotStatus_BALLOT_STATUS_REJECTED {
		return fmt.Errorf("invalid finalization status: %v", status)
	}

	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as finalized",
		"ballot_id", id,
		"final_status", status.String(),
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.FinalizedBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = status
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, status)
	return nil
```

```go
func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
```

```go
func (k Keeper) VoteInbound(ctx context.Context, universalValidator sdk.ValAddress, inbound types.Inbound) error {
	// Canonicalize first so every derived key + the stored inbound use one
	// representation per logical event.
	inbound.Canonicalize()

	k.Logger().Info("vote inbound received",
		"validator", universalValidator.String(),
		"source_chain", inbound.SourceChain,
		"tx_hash", inbound.TxHash,
		"tx_type", inbound.TxType.String(),
		"sender", inbound.Sender,
	)

	// Check inbound enabled before any state changes
	enabled, err := k.uregistryKeeper.IsChainInboundEnabled(ctx, inbound.SourceChain)
	if err != nil {
		return errors.Wrap(err, "failed to check inbound enabled")
	}
	if !enabled {
		k.Logger().Warn("vote inbound rejected: chain inbound disabled", "source_chain", inbound.SourceChain)
		return fmt.Errorf("inbound is disabled for chain %s", inbound.SourceChain)
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Step 1: Derive UTX key from the original inbound data (source_chain:tx_hash:log_index)
	universalTxKey := types.GetInboundUniversalTxKey(inbound)
	found, err := k.HasUniversalTx(ctx, universalTxKey)
	if err != nil {
		return errors.Wrap(err, "failed to check UniversalTx")
	}
	if found {
		k.Logger().Warn("vote inbound rejected: utx already exists", "utx_key", universalTxKey)
		return fmt.Errorf("universal tx with key %s already exists", universalTxKey)
	}

	// use a temporary context to not commit any ballot state change in case of error
	tmpCtx, commit := sdkCtx.CacheContext()

	// Step 2: Record this validator's vote in the per-utx PendingInbounds entry
	// (variant-aware audit trail). Each unique Inbound payload becomes its own
	// variant; multiple variants per utx_key indicate validator divergence.
	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return errors.Wrap(err, "failed to derive inbound ballot key")
	}
	if err := k.RecordInboundVote(tmpCtx, inbound, universalValidator.String(), ballotKey); err != nil {
		return err
	}
```
