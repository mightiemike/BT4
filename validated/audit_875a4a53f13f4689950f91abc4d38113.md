### Title
Panic-inducing `.unwrap()` on Sierra→Native compilation result reachable from an unprivileged Declare transaction - (File: `crates/apollo_compile_to_native/src/compiler.rs`)

### Summary
The CVE analog (MySQL DDL crash/hang triggered by a crafted request) maps to Starknet's DDL-equivalent operation: a `Declare` transaction that causes Sierra→CASM/Native compilation. In the Cairo-Native compilation path, `SierraToNativeCompiler::compile` calls `.unwrap()` on an `Option` returned by `AotContractExecutor::from_path`, after the compiler subprocess has already exited successfully. Any account that submits a class declaration that reaches this compilation path can potentially trigger a panic in the sequencer's contract-class-manager, causing a crash or a permanently broken native-compilation worker (repeatable "hang"), matching the CVE's "unauthorized ability to cause a hang or frequently repeatable crash" class of bug.

### Finding Description
Unlike the Sierra→CASM path (`crates/apollo_compile_to_casm/src/compiler.rs`) and the resource-limited subprocess wrapper (`crates/apollo_compilation_utils/src/compiler_utils.rs`), which carefully convert every subprocess failure/signal into a `Result::Err` (`format_compiler_error`, handling SIGKILL/SIGXFSZ/other signals), the native-compilation path does not fully preserve this safety: [1](#0-0) 

```rust
pub fn compile(
    &self,
    contract_class: ContractClass,
) -> Result<AotContractExecutor, CompilationUtilError> {
    ...
    let _stdout = compile_with_args(
        compiler_binary_path,
        contract_class,
        &additional_args,
        resource_limits,
    )?;

    Ok(AotContractExecutor::from_path(output_file.path())
        .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
        .unwrap())
}
```

`compile_with_args` only returns `Err` when the subprocess itself fails (non-zero exit / killed by signal). If the subprocess exits successfully but produces an output artifact that `AotContractExecutor::from_path` parses without an `Err` yet still yields `None` (e.g., because of a version/format mismatch, a truncated/incomplete shared object produced under resource pressure, or any other edge case the external `cairo_native` crate treats as "no executor" rather than "error"), the trailing `.unwrap()` panics.

This code is reachable from an unprivileged `Declare` transaction: `NativeClassManager::set_and_compile` invokes `process_compilation_request`, which calls `compiler.compile(...)`: [2](#0-1) 

- In `CairoNativeMode::WaitOnCompilation`, this call happens synchronously inside `set_and_compile`, which is invoked directly from transaction/class execution flow (`get_compiled_from_class_manager`), i.e., inside the same execution path used to service a submitted Declare transaction.
- In `CairoNativeMode::LazyCompilation`, the same `compile` call is invoked from the dedicated `run_compilation_worker` thread, which processes requests from a channel fed by declared classes; a panic there kills the worker thread and, because the channel senders remain live, permanently disables native compilation for all subsequent declares reaching that mode. [3](#0-2) 

By contrast, the codebase's own style rules explicitly forbid this pattern ("Never panic on data reachable from requests" / "Trace user-controlled values through the full call graph"), and the sibling CASM compiler path was hardened against exactly this (subprocess signal handling, resource limits, no bare `.unwrap()` on compiler output). The native-compiler path was not brought up to the same standard.

### Impact Explanation
- If the panic propagates out of the worker thread (`run_compilation_worker`) with the default `panic = "unwind"` profile, the thread terminates but the process may survive; however, the native-compilation pipeline becomes permanently stuck (no more requests are drained), which is functionally the "hang" described in the CVE — legitimate declared classes will never be promoted to native execution, and (depending on the deployment's panic hooks/supervisor configuration) a panicking worker thread can also be configured to abort the process.
- In `WaitOnCompilation` mode, the panic occurs synchronously in the same call stack used to execute/validate the transaction batch, which is a more direct crash vector for the sequencer/batcher process handling that specific Declare transaction (and, if it also affects re-execution during Starknet OS / block-building, an honest node could crash while others behave differently, causing an availability incident or divergence).
- Either outcome is a Medium-severity availability-only impact consistent with the CVE's CVSS profile (`AV:N/AC:H/PR:H/UI:N/C:N/I:N/A:H`): no confidentiality/integrity impact, only availability (hang/crash), and it requires crafting a Sierra program specifically able to steer the native compiler's on-disk artifact into the `None` branch, which is non-trivial (`AC:H`).

### Likelihood Explanation
Exploitability is currently uncertain because the exact conditions under which `cairo_native::executor::AotContractExecutor::from_path` returns `Ok(None)` versus `Err` are defined in an external crate not present in this repository, so I could not fully verify from the indexed code whether an attacker-controlled Sierra program can realistically drive that branch (e.g., via truncated output under CPU/memory/file-size resource limits, or a version-mismatched artifact). The reachability of the vulnerable code from an ordinary Declare transaction is confirmed and does not require any special privilege, matching the "PR:H" (the CVE requires elevated privilege; here the class-manager/native-compilation feature must simply be enabled in the deployment, e.g., `CairoNativeMode::LazyCompilation`/`WaitOnCompilation`) — but whether the feature is enabled and whether the exact panic condition is reachable, needs confirmation via a live Devin session (running the actual compiler binary and probing `from_path`'s `None` conditions), which I was unable to do in this ask-only investigation.

### Recommendation
Replace the trailing `.unwrap()` in `SierraToNativeCompiler::compile` with proper error propagation, e.g.:
```rust
AotContractExecutor::from_path(output_file.path())
    .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
    .ok_or_else(|| CompilationUtilError::CompilationError(
        "Native compiler produced no executable artifact".to_owned(),
    ))
```
Additionally, audit `process_compilation_request` and `run_compilation_worker` to ensure a single failed/panicking compilation request cannot permanently stall the worker thread (e.g., wrap the compile call in `std::panic::catch_unwind`, or ensure the worker thread is automatically respawned on panic), consistent with the "never panic on data reachable from requests" rule already established elsewhere in the codebase for the CASM compilation path.

### Proof of Concept
1. Enable native compilation in a sequencer/batcher instance (`CairoNativeMode::LazyCompilation` or `WaitOnCompilation`).
2. Craft/submit a `Declare` transaction whose Sierra program compiles successfully at the subprocess level (exit status 0) but produces a native artifact that `cairo_native::executor::AotContractExecutor::from_path` accepts without an `Err` yet resolves to `None` (candidate triggers include partial/truncated output caused by hitting `max_file_size`/`max_memory_usage` resource limits right at the boundary, or artifacts from a mismatched `cairo_native` build/version).
3. Observe the panic in `SierraToNativeCompiler::compile` (`crates/apollo_compile_to_native/src/compiler.rs:58-60`), propagating through `process_compilation_request` (`crates/blockifier/src/state/native_class_manager.rs:274-320`), and confirm the native-compilation worker thread terminates (LazyCompilation) or the transaction-execution call stack panics (WaitOnCompilation).

Note: I could not fully validate step 2 (the precise byte-level trigger for `from_path` returning `None`) because `cairo_native`'s implementation is an external dependency not present in the indexed codebase; a Devin session with full filesystem/build access would be required to construct and verify a concrete PoC artifact.

/// Processes a compilation request and caches the result.
fn process_compilation_request(
    class_cache: RawClassCache,
    compiler: Arc<SierraToNativeCompiler>,
    compilation_request: CompilationRequest,
    panic_on_compilation_failure: bool,
) -> Result<(), CompilationUtilError> {
    let (class_hash, sierra, casm) = compilation_request;
    if let Some(CompiledClasses::V1Native(_)) = class_cache.get(&class_hash) {
        // The contract class is already compiled to native - skip the compilation.
        return Ok(());
    }
    let sierra_for_compilation = into_contract_class_for_compilation(sierra.as_ref());
    let start = Instant::now();
    let compilation_result = compiler.compile(sierra_for_compilation);
    let duration = start.elapsed();
    log::info!(
        "Compiling to native contract with class hash: {:#066x}. Duration: {:.3} seconds",
        class_hash.0,
        duration.as_secs_f32()
    );
    match compilation_result {
        Ok(executor) => {
            let native_compiled_class = NativeCompiledClassV1::new(executor, casm);
            class_cache.set(
                class_hash,
                CompiledClasses::V1Native(CachedCairoNative::Compiled(native_compiled_class)),
            );
            log::info!("Compilation succeeded");
            Ok(())
        }
