### Title
Mempool size limit (`maxTransactionPendingSize`) is not enforced inside `Manager.pushTransaction`, allowing bypass via the P2P transaction-relay path - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
This is the same bug class as the sei-tendermint mempool report: a transaction-count limit check exists (`canAddTx` there, `isTooManyPending()`/`isBusy()` here), but the function that actually inserts a transaction into the pending pool (`CheckTx`/`addNewTransaction` there, `Manager.pushTransaction` here) does not itself enforce that limit. Any code path that reaches the insertion function without going through the specific caller that performs the check can add unlimited transactions to the pending pool.

### Finding Description
`Manager.pushTransaction()` unconditionally adds the transaction to `pendingTransactions` after `processTransaction` succeeds; it enforces only the shielded-transaction sub-limit, not the overall pending-size limit: [1](#0-0) 

The overall limit is instead enforced by `isTooManyPending()`, which sums `pushTransactionQueue`, `pendingTransactions` and `rePushTransactions`: [2](#0-1) 

This check is called by the gRPC/HTTP broadcast entrypoint, `Wallet.broadcastTransaction()`, *before* `dbManager.pushTransaction(trx)` is invoked: [3](#0-2) 

However, the P2P transaction-relay path does not perform this check at the point of insertion. `TransactionsMsgHandler.handleTransaction()` calls `tronNetDelegate.pushTransaction(trx.getTransactionCapsule())` directly, with no call to `isTooManyPending()`/`isBusy()` immediately before insertion: [4](#0-3) 

The only gate on the P2P path is `InventoryMsgHandler.check()`, which calls `transactionsMsgHandler.isBusy()` when an INV message announcing transaction hashes is *received*, not when the actual transactions are later delivered and pushed: [5](#0-4) 

`isBusy()` itself is defined as a threshold comparison against `maxTrxCacheSize`, independent from and coarser than `isTooManyPending()`/`maxTransactionPendingSize`: [6](#0-5) 

Because the "busy" check happens at INV-receipt time (a different point in time and against a different, coarser accounting than `pendingTransactions` size), and because many peer connections can each pass this time-of-check gate before any of the subsequent `TransactionsMessage` deliveries land, an attacker controlling or influencing multiple peer connections can drive many transactions through `handleTransaction()` → `pushTransaction()` in parallel, each of which is inserted into `pendingTransactions` without any recheck of `maxTransactionPendingSize` inside `pushTransaction()` itself. This mirrors the reported root cause: the size-limit check is bolted onto specific callers rather than being enforced inside the shared insertion function, so any caller that skips or races the check can flood the pending pool.

### Impact Explanation
If exploited, this allows an unprivileged network peer to grow `pendingTransactions`/`rePushTransactions` beyond the operator-configured `maxTransactionPendingSize`, consuming memory and CPU (each pushed transaction runs full `processTransaction`, i.e. signature/state validation, inside `pushTransaction`), and potentially degrading transaction propagation/block production for the node, consistent with the report's "network shutdown due to transaction limit overflow" impact class. This is a liveness/DoS-class issue rather than a fund-theft issue.

### Likelihood Explanation
Exploitability depends on the ability to open/maintain multiple concurrent P2P connections to a victim node and race valid transaction delivery against the coarse, time-of-INV `isBusy()` check — a capability available to any unprivileged network participant, not a trusted role. However, I could not fully verify from the indexed code whether `pendingTransactions`/`rePushTransactions` are bounded `BlockingQueue`s with a fixed capacity (which would cap real memory growth even without the explicit check) — this could not be confirmed with the tools available, so the practical severity of unbounded growth is uncertain.

### Recommendation
Enforce `isTooManyPending()` (or an equivalent count/size check) inside `Manager.pushTransaction()` itself, immediately before adding to `pendingTransactions`, so that every caller (RPC broadcast, P2P relay, re-push) is subject to the same hard limit rather than relying on a caller-side, time-of-check gate that can be bypassed or raced.

### Proof of Concept
Not independently reproduced; this is a static code-path analysis. A concrete PoC would require running a multi-peer test harness that opens several concurrent `PeerConnection`s to a node, has each send an `InventoryMessage` for distinct transactions while `isBusy()` is still false, then delivers all corresponding `TransactionsMessage`s concurrently so that `pushTransaction()` is invoked many more times than `maxTransactionPendingSize` allows, and observes `pendingTransactions`/`rePushTransactions` sizes exceed the configured limit — I could not execute this verification within the available tooling.
