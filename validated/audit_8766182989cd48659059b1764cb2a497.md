## Analysis

The reported bug class is: an unprivileged actor sends a "dust" amount to a target address, causing an **exact equality check** (`balance == X`) used to detect "operation complete / fully drained" to flip, thereby corrupting the intended state-transition logic and blocking legitimate completion of an operation.

The closest reachable analog in `agave` is in the System Program's nonce-withdrawal handler `withdraw_nonce_account`, which uses an *exact* lamport-equality test to decide whether a withdrawal is a "close the nonce account" operation versus a "partial withdrawal that must retain rent-exemption" operation: [1](#0-0) 

Because any unprivileged client can send lamports to an arbitrary account via a plain System Program transfer (no signature from the recipient is required), an attacker can front-run a legitimate "close/fully-withdraw nonce account" transaction by transferring 1 lamport of dust to the target nonce account. This changes `from.get_lamports()` so that `lamports == from.get_lamports()` (the intended full-withdrawal branch) becomes false, forcing execution into the `else` branch, which then requires `lamports + rent-exempt minimum <= from.get_lamports()`. Since the victim's requested `lamports` value was computed to equal the *pre-dust* balance, this new check fails and the instruction returns `InsufficientFunds`, permanently denying the withdrawal/close attempt as long as the attacker keeps re-dusting the account.

## Title
Unprivileged dust-lamport griefing of the exact-balance equality check in `withdraw_nonce_account` blocks legitimate nonce-account closure - (File: `programs/system/src/system_instruction.rs`)

### Summary
`withdraw_nonce_account` in the System Program decides whether a withdrawal fully closes an initialized nonce account using the exact comparison `lamports == from.get_lamports()`. An unprivileged attacker can send an arbitrary System-Program transfer of as little as 1 lamport to the target nonce account before the victim's withdrawal transaction lands, permanently invalidating this equality check and forcing the withdrawal into the "partial withdrawal" branch, which then fails with `InsufficientFunds` because the requested `lamports` value no longer satisfies `lamports + min_balance <= from.get_lamports()`.

### Finding Description
`withdraw_nonce_account` at [1](#0-0)  branches on whether the requested withdrawal amount exactly matches the current account balance:
- If `lamports == from.get_lamports()`, the nonce is fully drained and the account state is reset to `Uninitialized` (this is the "close" path used by clients that want to reclaim 100% of their lamports and deallocate the nonce account).
- Otherwise, it enforces that the account must retain at least `rent.minimum_balance(...)` lamports.

Because System Program transfers can target *any* account without the recipient's signature, any unprivileged sender can top up the nonce account's lamport balance by a trivial amount at any time, including via front-running a pending "full withdrawal" transaction observed in the mempool/leader schedule. Once the balance changes, a previously valid full-withdrawal instruction (built against the pre-dust balance) no longer satisfies the equality branch and instead falls into the partial-withdrawal branch, where it fails the `amount > from.get_lamports()` check and returns `InstructionError::InsufficientFunds`/`TransactionError::InsufficientFundsForFee`. This is structurally identical to the reported Maple Finance bug: an unprivileged party manipulates a balance via a permissionless transfer specifically to defeat an *exact* balance-based completion check used by a legitimate, otherwise-authorized operation.

### Impact Explanation
This is a denial-of-service / fund-lockup primitive reachable by any unprivileged client transaction against a standard, frequently-used System Program instruction (nonce withdrawal/account closure). An attacker who wants to prevent a user from closing/fully draining their own nonce account (e.g., to grief rent reclamation, deny account closure that a dApp/backend depends on for accounting, or repeatedly force retries with different, unpredictable amounts) can do so indefinitely and essentially for free (1 lamport per griefing transaction), as long as they can observe or predict the target nonce account address and the timing of the intended withdrawal.

### Likelihood Explanation
Likelihood is high: nonce accounts are public, their pubkeys are known on-chain, "full withdrawal" instructions are commonly constructed client-side against a previously fetched balance, and sending lamports to an arbitrary pubkey is a completely permissionless, cheap System Program transfer available to any transaction sender.

### Recommendation
Avoid relying on an exact-equality comparison against a manipulable account balance to select control flow. Instead, base the "full withdrawal / close" decision on whether the resulting balance after withdrawal would be zero (`from.get_lamports().checked_sub(lamports) == Some(0)`) combined with an explicit intent flag, or simply always allow full-balance withdrawal down to zero without requiring exact equality to the pre-computed balance snapshot, or have clients withdraw the full *current* on-chain balance (queried by the transaction, not by a pre-signed amount) rather than a value fixed ahead of time. More generally, exact balance comparisons that can be perturbed by third-party permissionless transfers should not gate authorization-sensitive control flow.

### Proof of Concept
1. Victim creates an initialized nonce account with balance `N` and later constructs `withdraw_nonce_account(nonce_pubkey, authority, N)` intending to fully withdraw and uninitialize the account (`lamports == from.get_lamports()` branch).
2. Attacker observes the pending transaction (e.g., in the mempool or via account-address prediction) and submits `system_instruction::transfer(attacker, nonce_pubkey, 1)` beforehand.
3. When the victim's withdrawal executes, `from.get_lamports()` is now `N + 1`, so `lamports (N) == from.get_lamports() (N + 1)` is false; execution falls into the `else` branch at [2](#0-1) , which requires `N + min_balance <= N + 1`, failing for any positive `min_balance`, returning `InstructionError::InsufficientFunds`.
4. The victim's withdrawal/close transaction fails; the attacker can repeat this before every retry, indefinitely preventing account closure.
