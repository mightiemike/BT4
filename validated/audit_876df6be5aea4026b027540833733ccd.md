### Title
Txpool-prewarm `CachedReads` snapshot caches speculative, uncommitted account/storage state and can be served as the parent's committed post-state during block validation - (File: crates/engine/tree/src/tree/txpool_prewarm/worker.rs)

### Summary
`Worker::warm_one_batch` executes pool transactions speculatively on top of one shared `CachedReads`/`State` instance across an unbounded number of iterations (up to `REFRESH_INTERVAL`), with nonce and balance checks disabled. Because `CachedReadsDbMut::basic`/`storage` populate `self.cached.accounts` lazily and `State` commits each transaction's post-execution changes back into that same underlying cache/database on the next reads, the recorded `CachedReads` entries reflect the speculative post-state of earlier, unconfirmed pool transactions rather than the actual balance/nonce/storage committed at `parent_hash`. This `CachedReads` is published as `TxPoolPrewarmCacheSnapshot` and consulted as the **first** lookup tier by `CachedStateProvider` during real block validation (`crates/engine/tree/src/tree/payload_validator.rs`), gated only by a `parent_hash` match, not by data correctness.

### Finding Description
`Worker::warm_one_batch` (`crates/engine/tree/src/tree/txpool_prewarm/worker.rs:180-229`) builds:
```rust
let mut state = State::builder()
    .with_database(self.cache.as_db_mut(StateProviderDatabase::new(state_provider)))
    .build();
...
while ... {
    let Some(transaction) = transactions.next() else { return BatchEnd::Rest };
    evm.transact(transaction.transaction)
}
```
`self.cache` (a `CachedReads`) persists across the whole batch and across many pool transactions from potentially the same or different senders. `revm::db::State` commits/applies each executed transaction's resulting account state to its underlying DB cache as subsequent reads occur, meaning a second transaction from the same sender (or one touching an account changed by an earlier transaction) will read the *speculative post-tx1* balance/nonce/storage, not the value actually committed on-chain at `parent_hash`. Since nonce/balance checks are explicitly disabled (`disable_nonce_check`, `disable_balance_check`, `disable_base_fee` at lines 210-212), transactions that would be invalid against real chain state (e.g., insufficient balance, nonce gaps) are still executed and their side effects land in `self.cache`, further increasing the chance of contaminated entries.

This `self.cache` is periodically cloned and published as an immutable `TxPoolPrewarmCacheSnapshot` (`publish_snapshot_if_dirty`, lines 231-250) keyed only by `parent_hash`. `Control::snapshot` (`crates/engine/tree/src/tree/txpool_prewarm/control.rs:50-56`) returns this snapshot to block validation whenever the requested parent hash matches — with no verification that the cached values equal the actual committed state at that hash.

During real block/payload validation, `CachedStateProvider` (`crates/engine/execution-cache/src/cached_state.rs`) is built `.with_txpool_snapshot(txpool_snapshot)` and consults the snapshot as the *first* tier for `basic_account`/`storage` lookups, ahead of the execution cache and the real database-backed state provider (see `crates/engine/tree/src/tree/payload_validator.rs:671-718` and `crates/engine/tree/src/tree/txpool_prewarm/worker.rs` snapshot construction). If a snapshot entry was polluted by speculative multi-transaction chaining (as described above), the real block's own transactions from the same address will read the wrong `AccountInfo`/storage during EVM execution of the *actual* new block, i.e., a state read diverges from the parent's actually committed post-state. ### Impact Explanation
If the corrupted snapshot causes `basic_account`/`storage` reads during block validation to diverge from the true parent post-state, EVM execution of the real block's transactions can produce different balances/nonces/storage than a serial, snapshot-free execution would — a non-deterministic-vs-serial-execution divergence that can silently produce a wrong execution result (wrong state/receipts root) for the block being validated, or an incorrect validity verdict (rejecting a valid block or accepting outputs that don't match spec-mandated serial semantics). This maps to the "Critical: a state root ... differing from the spec" / "non-deterministic execution between cached/prewarmed and serial paths" impact categories.

### Likelihood Explanation
Requires: (1) txpool prewarming enabled, (2) two or more pool transactions in the same warm batch that touch the same account/storage in a way that changes state (e.g. same sender back-to-back, or one tx funds/changes another address), and (3) the resulting `parent_hash` matching a subsequently validated real block whose transactions touch that same account before it's independently re-read via normal execution cache paths. This is plausible under normal high-throughput pool activity and does not require a malicious peer — an attacker only needs to submit ordinary pool transactions designed to produce cache pollution (e.g., self-transfers or transactions between two addresses they control) to increase likelihood of hitting the snapshot's polluted entries in a subsequent real block.

### Recommendation
Do not let the prewarming worker share one mutable `CachedReads`/`State` instance across multiple pool transactions when publishing to `TxPoolPrewarmCacheSnapshot`. Either: (a) snapshot/discard `self.cache`'s per-transaction writes so only the pristine pre-transaction DB reads are retained (i.e., only record `DatabaseRef` misses against the real parent state, never intermediate execution results), or (b) reset `state`'s cache between each speculative transaction so each transaction reads strictly from `parent_hash`'s real committed state instead of chained speculative output. Additionally, validate on the consuming side (`CachedStateProvider`) that entries served from `TxPoolPrewarmCacheSnapshot` are read-only DB reads and never post-execution-committed values.

### Proof of Concept
1. Enable txpool prewarming; submit two pool transactions from sender `A`: `tx1` transfers value out of `A` to `B`, `tx2` (also from `A`, nonce+1) spends the resulting reduced balance.
2. In `warm_one_batch`, both execute against the same shared `state`/`self.cache`; after `tx1`, `A`'s `AccountInfo` in `self.cache.accounts` reflects post-tx1 balance/nonce (a speculative, unconfirmed state) — this becomes a cache entry that is *not* actually committed to `parent_hash`'s state on-chain (tx1 might never be included, or is included later at a different price/order).
3. `publish_snapshot_if_dirty` publishes this contaminated `CachedReads` as `TxPoolPrewarmCacheSnapshot` for `parent_hash`.
4. A real payload with `parent_hash` as its parent arrives for validation; `payload_validator.rs` builds a `CachedStateProvider::with_txpool_snapshot(...)` using this snapshot. If the real block also contains a transaction from `A`, `CachedStateProvider::basic_account`/`storage` (via the snapshot tier) returns the polluted post-tx1 speculative balance/nonce instead of `A`'s true balance/nonce committed at `parent_hash`, causing the real block's execution to diverge from a correct serial execution against `parent_hash`'s actual state.

    fn warm_one_batch(&mut self) -> BatchEnd {
        let (_, job) = self.job.as_ref().expect("wait_until_runnable installed a job");
        let (parent_hash, transactions) =
            self.transactions.as_mut().expect("open_transactions installed an iterator");

        // Building a state provider opens a database transaction; don't bother under a pending
        // command.
        if !self.commands.is_empty() {
            return BatchEnd::GoAgain
        }

        let state_provider = match job.state_provider_factory.database_provider_ro() {
            Ok(provider) => provider,
            Err(err) => {
                trace!(
                    target: "engine::tree::txpool_prewarm",
                    %err,
                    ?parent_hash,
                    "failed to build txpool prewarming state provider"
                );
                return BatchEnd::Rest
            }
        };
        let mut state = State::builder()
            .with_database(self.cache.as_db_mut(StateProviderDatabase::new(state_provider)))
            .build();
        // The environment is the head block's own, not a predicted next-block one, and execution
        // is out of context by design: transaction viability is the pool's business, so nonce,
        // balance and (one-block-stale) basefee checks must not gate which state gets warmed.
        let mut evm_env = job.evm_env.clone();
        evm_env.cfg_env.disable_nonce_check = true;
        evm_env.cfg_env.disable_balance_check = true;
        evm_env.cfg_env.disable_base_fee = true;
        let mut evm = self.evm_config.evm_with_env(&mut state, evm_env);

        let deadline = Instant::now() + REFRESH_INTERVAL;
        while self.commands.is_empty() && Instant::now() < deadline {
            let Some(transaction) = transactions.next() else { return BatchEnd::Rest };
            if let Err(err) = evm.transact(transaction.transaction) {
                trace!(
                    target: "engine::tree::txpool_prewarm",
                    %err,
                    tx_hash = ?transaction.hash,
                    sender = %transaction.sender,
                    "speculative txpool transaction execution failed"
                );
            }
        }
        BatchEnd::GoAgain
    }

    /// Publishes a fresh snapshot if the cache gained reads since the last publication.
    fn publish_snapshot_if_dirty(&mut self) {
        let entries = entry_counts(&self.cache);
        if entries == self.published_entries {
            return
        }

        let parent_hash = self.cache_parent.expect("reads only accumulate after a cache reset");
        *self.publication.write() = Some(Snapshot::new(parent_hash, Arc::new(self.cache.clone())));
        self.published_entries = entries;
        let (accounts, storage, bytecodes) = entries;
        debug!(
            target: "engine::tree::txpool_prewarm",
            ?parent_hash,
            accounts,
            storage,
            bytecodes,
            "published txpool prewarming snapshot"
        );
    }
