### Title
`ensure_match_transaction_info` skips verifying `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` when applying transaction outputs, letting a diverging state root pass authentication - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function that binds an (untrusted, locally-produced-or-received) `TransactionOutput` to an already-authenticated `TransactionInfo` (the leaf that is covered by the transaction accumulator proof). It checks status, gas, write-set hash, and event-root hash, but explicitly and knowingly skips the `TransactionInfoV1` fields `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`TransactionInfoV1` carries additional checkpoint-hash fields beyond the classic `state_checkpoint_hash`, including `position_state_checkpoint_hash`, which is meant to authenticate the root of the separate "native position" Merkle tree (the trading-native feature's own state tree, restored via `StateSnapshotRestore`/`get_position_snapshot_receiver` in `storage/aptosdb/src/position_state_sync.rs`). [2](#0-1) [3](#0-2) 

When a `TransactionInfo` is assembled during execution, `position_state_checkpoint_hash` is populated from the actual computed position-state checkpoint for that transaction. [4](#0-3) 

However, `ensure_match_transaction_info` — used to verify that a `TransactionOutput` (which may come from applying transaction outputs during state sync, replay-verify, or the aptos-debugger) matches an already-committed/authenticated `TransactionInfo` — only checks `status`, `gas_used`, `write_set_hash` against `state_change_hash`, and `event_root_hash`. It never compares the recomputed `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` against the authenticated values in `txn_info`. This gap is called out directly in the code's own TODO: "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." [5](#0-4) 

This function is not test-only: it is invoked from the executor's chunk-apply path (`execution/executor/src/chunk_executor/mod.rs`), from `storage/db-tool/src/replay_on_archive.rs`, from `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and from `aptos-move/cli/src/commands.rs`. [6](#0-5) 

Because the write-set hash check (`state_change_hash`) only covers the regular `WriteSet`, and the native-position tree lives in a separate storage/tree (`PositionDb`/`PositionMerkleDb`, distinct from the JMT used for regular account state), a divergence between the locally computed position-state root and the authenticated `position_state_checkpoint_hash` in the accumulator-proven `TransactionInfo` is not detected by this integrity check.

### Impact Explanation
This breaks the invariant that "committed state must not differ from the correct/authenticated result, and authenticated proof-bearing responses must stay bound to the right root." A node applying transaction outputs (fast-sync `ApplyTransactionOutputs` mode, replay-verify tooling, or debugger-based replay) can silently accept and persist a position-state Merkle root that diverges from the canonical, accumulator-authenticated root, because the one field designed to catch that divergence is never compared. This is a genuine state-commitment/proof-binding gap in a production verification routine, not merely a cosmetic or test-only omission — it matches the "authenticated API or state-view output bound to the wrong version/object/proof context" and "restore paths must not reinterpret committed data into a different ledger state" criteria.

### Likelihood Explanation
Likelihood is currently constrained: the code's own comment notes this gap must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," and that flag/constant does not appear elsewhere in the codebase as an active, wired feature flag — indicating the trading-native checkpoint-hash population/enforcement pipeline is still being rolled out rather than fully active on mainnet today. Once the feature is turned on (which the repository is actively building toward, given the surrounding `native_position.move`/`trading_native_capability.move` framework code and populated `position_state_checkpoint_hash` field), any bug or malicious deviation in position-state computation during output-based replay would go undetected by this specific comparator.

### Recommendation
Extend `ensure_match_transaction_info` to also recompute and compare `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` (when present in the `TransactionInfoV1` being matched) against the values recomputed from the locally derived state, mirroring the existing `write_set_hash`/`event_root_hash` checks, before the trading-native checkpoint-hash feature is enabled for state-sync/replay verification paths.

### Proof of Concept
Not applicable as an exploit script; this is a code-inspection finding. Trace: `execution/executor/src/workflow/do_ledger_update.rs::assemble_transaction_infos` populates `position_state_checkpoint_hash` in the authenticated `TransactionInfoV1` → this `TransactionInfo` is bound into the accumulator and covered by consensus/ledger-info signatures → during chunk/output application or replay, `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) is the sole function asserting the locally produced `TransactionOutput` matches that authenticated `TransactionInfo`, and it never touches `position_state_checkpoint_hash`/`hot_state_checkpoint_hash`, so any divergence in the separately stored native-position Merkle tree slips through unnoticed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
