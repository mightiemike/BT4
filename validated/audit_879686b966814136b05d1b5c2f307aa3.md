### Title
Replay verification (`verify_execution`/`ensure_match_transaction_info`) does not validate state-checkpoint/hot-state/position-state roots, allowing divergent local execution to pass as "verified" - (File: `types/src/transaction/mod.rs`, `execution/executor/src/chunk_executor/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — used by `ChunkExecutorInner::verify_execution` during chunk-replay/backup-verify — checks status, gas, write-set hash, event root, and transaction hash against a trusted `TransactionInfo`, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values the local VM execution actually produced.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates several fields but has a documented gap: [2](#0-1) 
This comparator is invoked from `ChunkExecutorInner::verify_execution`, which is the code path used both by `db-tool`'s `replay_on_archive` and by `TransactionReplayer::enqueue_chunks` (state-sync/backup replay), to decide whether locally-executed output matches a supplied/trusted `TransactionInfo`: [3](#0-2) 

Because the comparator never re-derives or compares `state_checkpoint_hash` (the Sparse Merkle Tree world-state root at that transaction) nor the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields, a locally-executed replay whose resulting state root differs from the committed/trusted `TransactionInfo`'s checkpoint hash will still report success. All other fields (write-set hash, event root, gas, status, txn hash) can match while the actual world-state root diverges, since the state root is computed from the running Sparse Merkle Tree across the whole chunk, not solely from the individual write set.

### Impact Explanation
This breaks the "replay path must not reinterpret committed data into a different ledger state" invariant. `replay_on_archive`/replay verification exists specifically to catch state-root divergence between historical, trusted `TransactionInfo`s and local re-execution (e.g., after a VM or Merkle-tree bug). With this gap, a divergent state root — the actual failure mode replay-verify is meant to detect — is silently accepted as "OK", masking a state-integrity bug instead of surfacing it. This directly undermines detection of hard-fork-only divergence during replay, which is explicitly in the impact scope of this exercise.

### Likelihood Explanation
This is not attacker-triggered on mainnet consensus directly (chunk-executor's `verify_chunk_result`/accumulator checks still separately validate `TransactionInfo` hashes against the accumulator for normal state-sync chunk application), so it does not by itself corrupt a live node's committed ledger. The concrete, reproducible failure is scoped to the replay/verification tooling path (`verify_execution`, used by `db-tool replay_on_archive` and by `TransactionReplayer`), where the gap is unconditionally present any time state-checkpoint hashes diverge — i.e., deterministic and easy to trigger with any code change that alters SMT root computation without altering the write set/events.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally-computed state-checkpoint hash (and, where enabled, hot-state and position-state checkpoint hashes) against `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` whenever those fields are present in the transaction info being checked (i.e., at the checkpoint-producing transaction), as the existing TODO in the code already flags. This requires threading the same state-checkpoint hash computation used in `DoStateCheckpoint`/`DoLedgerUpdate` into the replay verification call site so it can be checked, not skipped.

### Proof of Concept
Not independently demonstrable purely from static inspection — the concrete PoC would require constructing two `TransactionOutput`s with identical write sets/events/gas/status but where the enclosing chunk's SMT-derived `state_checkpoint_hash` differs (e.g., due to a stale/incorrect parent state root fed to `DoStateCheckpoint` during replay) and showing `ensure_match_transaction_info` returns `Ok(())` despite the mismatch — the code path and the exact missing checks are shown above; the TODO comment at lines 2197-2202 explicitly documents this as unvalidated by the developers.

**Confidence caveat:** I could not fully trace whether `verify_chunk_result`/the transaction accumulator check (which does hash the full `TransactionInfo`, including checkpoint hashes, against the accumulator root) provides an independent, always-executed safety net for the *replay* path in all invocation modes (e.g., `db-tool replay_on_archive`'s exact call sequence), so I cannot confirm with certainty that this gap is exploitable to accept a genuinely wrong state root as "verified" in every replay tool invocation, versus only in narrower diagnostic scenarios. Given this residual uncertainty about whether an independent accumulator-based check always closes the gap, I present this as the strongest local candidate but flag it as not fully proven to reach "Critical" mainnet impact — it is a real, developer-acknowledged verification blind spot in state-checkpoint-hash comparison during replay tooling, but I was unable to fully confirm an end-to-end exploitable path without further tracing of `db-tool`'s `replay_on_archive.rs` call sequence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
