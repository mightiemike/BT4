### Title
Replay-verification skips checking the authenticated state-checkpoint (JMT root) hash, allowing corrupted state roots to pass verification undetected - (File: `execution/executor/src/chunk_executor/mod.rs`, `types/src/transaction/mod.rs`)

### Summary
The external report's bug class reduces to one invariant: a value that is supposed to authenticate committed state (a slot/word in the pump bug; here, a state root) must actually be checked/derived correctly, or downstream consumers will accept a corrupted value as valid. In Aptos, the analogous invariant is that replay-verification tooling must recompute and compare *every* authenticated field of `TransactionInfo` — including the state-checkpoint (Jellyfish Merkle) root hash — against the locally re-executed result. I found that `TransactionOutput::ensure_match_transaction_info`, the sole comparator used by the chunk-executor's `verify_execution` path (the code backing `db-tool`/`aptos-debugger` replay-verify), checks status, gas, write-set hash, and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` explicitly omits checkpoint-hash comparison, with a comment in the code itself acknowledging the gap: [1](#0-0) 

The checks performed are: execution status, gas used, write-set hash (`state_change_hash`), and event root hash. The state/hot-state/position-state checkpoint hashes carried in `TransactionInfo` — which authenticate the JMT state root at each checkpoint version — are never recomputed or compared here.

This comparator is the *only* correctness check performed by `verify_execution` in the chunk executor, which independently re-executes historical transactions (using the archived `write_sets`/`transaction_infos`) to confirm they match what is claimed to have been committed: [2](#0-1) 

Note that `verify_execution` calls `DoGetExecutionOutput::by_transaction_execution` directly and loops over `ensure_match_transaction_info` per transaction — it never calls `DoStateCheckpoint::run`/`get_state_checkpoint_hashes`, which is the function that *does* correctly validate a computed state root against the known one, but which is only reached via the normal chunk-executor commit path (`update_ledger`), not via `verify_execution`: [3](#0-2) 

In other words, there are two independent ledger-verification code paths in the same crate:
1. `update_ledger()` → `DoStateCheckpoint::run()` → `get_state_checkpoint_hashes()`, which *does* assert `known[idx] == Some(computed_last_checkpoint_hash)`.
2. `verify_execution()` → `ensure_match_transaction_info()`, used specifically for offline replay-verify/debugging of historical chain segments, which *does not* check any checkpoint hash at all.

Path 2 is precisely the path whose purpose is to be an independent state-integrity check against archived/mainnet data (e.g., to detect a hard-fork-only divergence or a state-corruption bug introduced anywhere in the VM/storage stack). Its comparator silently accepts any state root, meaning a corrupted or manipulated state root in archived `TransactionInfo` records (or a genuine divergence caused by a bug elsewhere in JMT/restore code) will not be flagged as a mismatch.

### Impact Explanation
This breaks the "authenticated API or state-view output bound to the wrong version/root" invariant specifically for the tool whose entire job is to catch such divergences. If a bug (in JMT restore, state merklization, hot-state, or the trading-native "position state" root introduced by this codebase) silently produces a wrong state root at some historical version, `replay_on_archive`/replay-verify would report success even though committed state differs from the correct VM result. This directly undermines the primary state-integrity safety net used to validate mainnet history (e.g., after upgrades, hard forks, or when auditing archived data), which is exactly the class of impact the gate calls out: "Hard-fork-only divergence during commit, replay, restore, or proof verification" going undetected.

### Likelihood Explanation
The gap is not theoretical — it is explicitly acknowledged in the code's own comment as a known incompleteness ("this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"). Any caller relying on `verify_execution`/`ensure_match_transaction_info` for full ledger-integrity assurance (rather than the narrower `update_ledger` path) is currently blind to state-root corruption. This requires no attacker action beyond feeding archived data (or a state-root bug elsewhere) into the replay-verify tool — it is a passive detection gap, not an active exploit, but it defeats an integrity control relied upon for mainnet correctness auditing.

### Recommendation
Extend `ensure_match_transaction_info` (or the call site in `verify_execution`) to also recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally computed state summary root(s) for that transaction, mirroring the check already performed in `DoStateCheckpoint::get_state_checkpoint_hashes`. At minimum, `verify_execution` should route through `DoStateCheckpoint::run` so checkpoint hashes are asserted, not skipped, before being reported as "verified."

### Proof of Concept
1. Take an archived transaction chunk (`transactions`, `transaction_infos`, `write_sets`, `event_vecs`) where the `TransactionInfo.state_checkpoint_hash` field has been altered/corrupted (or diverges due to an actual state-computation bug) while `write_set`, `events`, `gas_used`, and `status` remain byte-for-byte identical to what local re-execution produces.
2. Invoke `ChunkExecutorInner::verify_execution` (as used by `db-tool replay-verify` / `aptos-debugger`) on this chunk.
3. `ensure_match_transaction_info` is called per transaction; because it never reads or compares `state_checkpoint_hash`, the mismatched/corrupted state root is never surfaced.
4. `verify_execution` returns `Ok(end_version)`, reporting the replayed chunk as fully verified, even though the archived state root does not match what execution actually computed — masking a state-commitment divergence that should have been flagged as Critical/High.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
