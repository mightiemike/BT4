### Title
`GlobalContractDistribution` receipts can panic `receipt_filter_fn` after resharding, causing a transaction-triggered chain halt - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::pop`/`peek_iter` filter delayed receipts by shard using `receipt_filter_fn`, which calls `receiver_shard_id(&shard_layout).unwrap()` on every delayed receipt popped from the queue [1](#0-0) . This is analogous to Suricata's defrag "policy bypass" bug class: a stale/lingering fragment (here, a stale delayed receipt whose target shard mapping becomes invalid across multiple reassembly/resharding events) is misinterpreted by the reassembly/lookup logic, producing incorrect handling — in this codebase, an unrecoverable `unwrap()` panic instead of merely a bypass.

### Finding Description
`DeployGlobalContract` actions create `GlobalContractDistribution` receipts that are routed by `target_shard` and can sit in the delayed-receipt queue across chunk boundaries [2](#0-1) . When popping from the delayed queue, `DelayedReceiptQueueWrapper::pop` calls `self.receipt_filter_fn(&receipt)` for every entry to decide whether it belongs to the *current* shard after a resharding split (ReshardingV3) [3](#0-2) :

```
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

Both `.unwrap()` calls assume `receiver_shard_id` can always be resolved against the *current* epoch's shard layout. This works for one resharding generation, but the repository's own regression test `test-loop-tests/src/tests/global_contracts_distribution.rs` demonstrates that after **two** resharding (shard-split) generations, a stale `GlobalContractDistribution` receipt that has been sitting in the delayed queue can no longer be remapped to a valid shard under the new (twice-split) `ShardLayout`, and `receiver_shard_id()` fails/panics when the filter tries to resolve it [4](#0-3) . The same filter is invoked in `peek_iter` as well [5](#0-4) , and `pop` is called on the standard per-chunk `process_delayed_receipts` path used by every chunk producer/validator [6](#0-5) .

### Impact Explanation
Unlike the Suricata analog (silent detection/policy bypass), the nearcore variant is more severe: the `unwrap()` panic in `receipt_filter_fn` is executed deterministically by *every* honest validator/chunk-producer node applying the same chunk, so the entire network halts in lock-step once the delayed queue is drained to the point where the stale receipt is popped. This matches the allowed impact category "a transaction-triggered halt": a single `DeployGlobalContract` transaction, submitted by an ordinary account before a shard-split epoch boundary, can plant the poisoned `GlobalContractDistribution` receipt in the delayed queue; congestion (or simply timing) then keeps it there across two subsequent resharding events, at which point every node panics identically when draining the backlog.

### Likelihood Explanation
Reaching this bug requires two consecutive resharding (shard-split) epochs to occur while the receipt remains un-drained in the delayed queue, which requires either sustained congestion or specific timing around governance-triggered resharding — this is not trivially triggerable within a single block by an attacker on demand. It is nonetheless directly reachable from an ordinary `DeployGlobalContract` transaction with no special privileges, and the presence of a dedicated repository test (`global_contracts_distribution.rs`) that explicitly builds and asserts against this exact panic scenario indicates the nearcore team has already identified this as a real, reachable regression risk tied to the resharding/GlobalContractDistribution interaction.

### Recommendation
Replace both `.unwrap()` calls in `receipt_filter_fn` with graceful handling: if `receiver_shard_id` cannot be resolved against the current shard layout (e.g., because the receipt's original target shard no longer exists after multiple resharding generations), either (a) remap the receipt to its nearest valid descendant shard using the historical shard-layout chain, or (b) drop/re-route the stale receipt with an explicit, auditable state transition instead of panicking. Add versioned protocol handling so that `GlobalContractDistribution` (and any other receipt kind routed by `target_shard`) carries enough information to be remapped correctly across an arbitrary number of resharding events, and extend test coverage to assert the queue drains without panicking after N ≥ 2 shard splits.

### Proof of Concept
Exact reproduction steps require live network stepping through two resharding epochs, which is already codified in the repository's own test: [4](#0-3) 
1. Deploy a global contract via a normal `DeployGlobalContract` transaction, generating a `GlobalContractDistribution` receipt targeted at a shard.
2. Saturate/delay so the receipt lands and stays in the delayed-receipt queue (`DelayedReceiptQueueWrapper::push`, [7](#0-6) ).
3. Drive the chain through two shard-split (resharding) epoch boundaries.
4. Stop saturating and let the delayed queue drain; `DelayedReceiptQueueWrapper::pop` invokes `receipt_filter_fn`, which panics inside `receiver_shard_id().unwrap()` [8](#0-7) , halting the chain across all honest validators applying that chunk.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

### 2. Admission into the delayed queue (incoming backpressure)

Incoming receipts are validated first, then either executed or deferred:
`process_incoming_receipts` (`lib.rs:2541`) executes a receipt only while
`total.compute < compute_limit` and the storage-proof size limit is not exceeded;
otherwise it calls `delayed_receipts.push(...)` (`lib.rs:2578`) to persist it for a
later chunk. `compute_limit` is the chunk gas limit (`lib.rs:2668`). Delayed
receipts are drained FIFO in `process_delayed_receipts` (`lib.rs:2441`), stopping on
the same compute / proof-size checks (`lib.rs:2462`). Each `pop`/`push` updates the
wrapper's accumulated gas/bytes (`congestion_control.rs:838` push, `:880` pop), which
feed `delayed_receipts_gas` and `receipt_bytes` in `CongestionInfo`.

`DelayedReceiptQueueWrapper::pop` (`congestion_control.rs:880`) also breaks *before*
popping if `trie.check_proof_size_limit_exceed()` (`:889`), and — for
ReshardingV3 — accounts gas/bytes for every popped receipt but returns only those
whose `receiver_shard_id` matches the current shard (`receipt_filter_fn`, `:874`),
skipping receipts that belong to a sibling shard after a split.
