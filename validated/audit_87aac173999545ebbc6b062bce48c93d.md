### Title
Unbounded Linear Scan in Secondary-Index Reverse Mapping Enables CPU-Cost Griefing - ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
`SecondaryIndex::insert()` maintains a per-inner-key reverse-index entry as a `Vec<Pubkey>` (`SecondaryReverseIndexEntry`), explicitly justified by a comment claiming this case is "rare." Insertion performs a linear `contains()` scan of this vector for every insert, and `remove_by_inner_key_if()` drains the entire vector on removal. Since account owners/mints (the "inner key") are attacker-controlled inputs derived directly from ordinary token account data, an attacker can grow this vector to be much larger than the "rare" assumption intends, causing O(n) cost per insert/remove that scales with attacker-supplied data, mirroring the reported gas-griefing pattern of linear search over an unbounded, adversarially-grown vector.

### Finding Description
The comment at [1](#0-0)  explicitly assumes it is "rare" for an inner key (e.g., an SPL token account's owner or mint pubkey) to map to more than one outer key, and uses a `Vec<Pubkey>` instead of a `HashSet` for that reason, despite performing "existence checks" on it.

In `insert()`, every insertion into the secondary index does a linear `outer_keys.contains(key)` scan over this vector before conditionally pushing: [2](#0-1) . The reverse-index entry for a given inner key grows every time the same inner key (owner/mint) is associated, across different slots, with a *new* distinct outer key — i.e., whenever the indexed account data for that key changes across account rewrites in different slots: [3](#0-2) .

In `remove_by_inner_key_if()`, cleanup drains and iterates the entire vector, invoking `remove_index_entries()` once per outer key entry: [4](#0-3) .

Because "inner_key" values here (SPL token owner/mint pubkeys, program IDs) are derived directly from account data that any unprivileged user can create and rewrite across slots (e.g., by repeatedly writing different SPL Token account states that get indexed with `AccountSecondaryIndexes` for `SplTokenOwner`/`SplTokenMint`/`ProgramId` enabled), an attacker can drive up the number of distinct outer keys mapped to a single inner key far beyond what the "rare" assumption anticipates. Every subsequent `insert()` for that same inner key pays a linear scan cost proportional to the number of accumulated outer keys, and every `remove_by_inner_key_if()` call pays a linear drain/removal cost — the same asymptotic griefing shape described in the report (attacker inserts cheaply, victim/validator pays cumulative O(n) cost on every subsequent index maintenance operation touching that inner key).

### Impact Explanation
This is a disproportionate CPU-cost vulnerability in AccountsDB's secondary index maintenance path, which runs on every validator that enables secondary indexes (`--account-index spl-token-owner`/`spl-token-mint`/`program-id`). An attacker who can cheaply cause many distinct "outer key" associations for the same inner key (by rewriting indexed account data across slots) inflates the cost of every future `insert()` and `remove_by_inner_key_if()` call touching that inner key, since both operations are linear in the size of the accumulated `Vec<Pubkey>`. This does not corrupt account state or hashes, but it degrades index-maintenance throughput disproportionately to the attacker's own cost, consistent with the "disproportionate storage and CPU cost" acceptance criterion.

### Likelihood Explanation
Requires the validator operator to have enabled a secondary index (`SplTokenOwner`, `SplTokenMint`, or `ProgramId`) — a common configuration for RPC nodes serving `getProgramAccounts`/`getTokenAccountsByOwner`. Given that, any unprivileged user can submit transactions that repeatedly change the indexed field (owner/mint) of accounts across different slots, incrementally growing the reverse-index vector for a chosen inner key at negligible cost to themselves.

### Recommendation
Replace the `Vec<Pubkey>` reverse-index entry (`SecondaryReverseIndexEntry`) with a `HashSet<Pubkey>` (or an equivalent O(1)-lookup structure), removing the "rare" assumption and its linear `contains()`/drain-based removal cost, consistent with how the forward index (`RwLockSecondaryIndexEntry`) already uses a `HashSet`.

### Proof of Concept
Not independently executable from static analysis alone — this is a code-level cost-asymmetry finding rather than a demonstrated live exploit. Conceptually: enable a secondary index (e.g., `SplTokenOwner`), then repeatedly write token accounts across many slots such that the same owner pubkey (inner key) becomes associated with N distinct token-account pubkeys (outer keys) as SPL Token account data changes across slots — driving `SecondaryIndex::insert()`'s `outer_keys.contains(key)` scan, and any later `remove_by_inner_key_if()` drain, to cost O(N) per call for that owner, as shown in [5](#0-4)  and [6](#0-5) .

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }

        // explicitly drop the locks so we don't hold them while reporting metrics
        drop(outer_keys);
        drop(reverse_index_entry);

        if self.stats.last_report.should_update(1000) {
            datapoint_info!(
                self.metrics_name,
                ("num_secondary_keys", self.index.len(), i64),
                (
                    "num_inner_keys",
                    self.stats.num_inner_keys.load(Ordering::Relaxed),
                    i64
                ),
                ("num_reverse_index_keys", self.reverse_index.len(), i64),
            );
        }
    }
