### Title
Cross-Chain/Cross-Network Replay of Meta-Transaction `DelegateAction` Signatures Due to Missing Chain-Binding Data - (File: `core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

### Summary
NEAR's meta-transaction (NEP-366) signature scheme signs a `DelegateAction`/`DelegateActionV2` payload that contains no chain-specific binding data (no genesis hash, chain id, or even the ordinary `block_hash` used by regular transactions). The signed hash is derived only from `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`. This is the same bug class as the reported EIP-4337 `VerifyingSingletonPaymaster.getHash()` finding: an authorization hash that omits chain identity, permitting the exact same signed payload to be relayed and accepted on more than one chain instance that shares the signer's account/access-key state.

### Finding Description
`DelegateAction::get_nep461_hash()` and `VersionedDelegateActionPayload::get_nep461_hash()` compute the signed hash purely from the `SignableMessage` wrapper (a NEP-number discriminant) plus the `DelegateAction`/`DelegateActionV2` fields: [1](#0-0) [2](#0-1) 

The `SignableMessage` wrapper only prefixes a NEP-scheme discriminant; it carries no genesis hash, chain id, or network identifier: [3](#0-2) [4](#0-3) 

By contrast, an ordinary `SignedTransaction` binds its signature to a specific `block_hash` from the chain it will be submitted to, which — because block hashes are chain-unique — naturally prevents cross-chain replay for regular transactions: [5](#0-4) [6](#0-5) 

The `DelegateAction`, however, only uses an absolute `max_block_height` (a plain number, not a hash) together with an access-key `nonce` for expiry/replay protection at the runtime level: [7](#0-6) [8](#0-7) 

Neither `max_block_height` nor `nonce` is chain-specific: `max_block_height` is just an integer height that trivially exists on any chain, and the access-key `nonce` is account-local state, not chain-local state. If the same account (same `sender_id` + `public_key` + access key with the same or lower nonce) exists on more than one live chain that can trace back to a shared genesis/state — for example a testnet reset from a mainnet snapshot, a migrated/forked network, or any other nearcore-based chain that imports account/genesis state (nearcore explicitly supports constructing genesis records and `SignedDelegateAction`s programmatically, see `tools/mirror/src/genesis.rs`) — a single `SignedDelegateAction` signed once by the user can be wrapped by a relayer and submitted as a valid `Action::Delegate`/`Action::DelegateV2` on every such chain, executing the same fund-moving or state-changing actions repeatedly under one signature. [9](#0-8) 

This mirrors exactly the reported bug class: an off-chain/relayer-submitted authorization hash omits any chain-binding element, so a "paymaster"/relayer-style construct on one chain can validly replay a signature intended for (or already used on) another.

### Impact Explanation
An attacker (or even an honest but careless relayer) that operates on two chains sharing account state can replay a user's `SignedDelegateAction` to trigger the same value transfers, contract calls, or key operations twice — once per chain — using only a single user signature. Since the relayer pays gas/deposit costs on each chain independently and the inner actions execute on behalf of `sender_id` on each chain independently, this can result in unauthorized duplicate value movement (e.g., duplicated transfers or `FunctionCall` actions with deposits) on any chain where the sender's account and nonce state happen to coincide with the signed payload. This satisfies "concrete unauthorized value movement" across what should be isolated ledger instances.

### Likelihood Explanation
Exploitation requires a chain-state precondition (the signer's account/access-key nonce existing identically on ≥2 chains), which is a real, recurring situation in the NEAR ecosystem: testnets and sandboxes are frequently bootstrapped from mainnet-derived genesis/state snapshots, and nearcore explicitly ships tooling (`tools/mirror`) for constructing/replaying genesis records and delegate-action-bearing receipts across chain instances. Any unprivileged user who signs a meta-transaction and any relayer that is willing to submit it on more than one such chain instance can trigger this — no validator or network-layer privilege is required, matching the "unprivileged transaction signer / meta-transaction sender" reachability requirement.

### Recommendation
Bind the `DelegateAction`/`DelegateActionV2` signature to the specific chain it is authorized for, mirroring how regular transactions bind to `block_hash`. Concretely, add a chain-identifying field (e.g., genesis hash or a recent `block_hash` from the target chain) into the `DelegateAction`/`DelegateActionV2` struct and include it in the `SignableMessage` payload hashed in `get_nep461_hash()`, and validate it in `apply_delegate_action`/`validate_delegate_action_key` against the executing chain's actual genesis/recent block hash, rejecting the delegate action if it doesn't match.

### Proof of Concept
1. Bootstrap two nearcore-based chains, `Chain A` and `Chain B`, both containing account `alice.near` with the same public key and identical access-key nonce (e.g., `Chain B` genesis is exported/imported from `Chain A`'s state as supported by `tools/mirror/src/genesis.rs`).
2. `alice.near` signs one `DelegateAction { sender_id: "alice.near", receiver_id: "bob.near", actions: [Transfer], nonce: N, max_block_height: H, public_key }` via `SignedDelegateAction::sign` — the hash covers no chain identifier: [10](#0-9) 
3. A relayer wraps this `SignedDelegateAction` in `Action::Delegate` inside a normal `SignedTransaction` (whose own `block_hash` only needs to be valid *for the chain it's submitted to*) and submits it to `Chain A`; `apply_delegate_action` validates and executes it, advancing `alice.near`'s nonce to `N` on `Chain A`.
4. The same relayer (or a colluding one) wraps the identical `SignedDelegateAction` bytes in a new outer `SignedTransaction` with `Chain B`'s current `block_hash` and submits it to `Chain B`. Because `Chain B`'s copy of `alice.near`'s access key still has nonce `< N` (independent chain state), `validate_delegate_action_key` accepts it and the actions execute again on `Chain B`, without any second signature from `alice.near`.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
