Found a direct analog in the NEAR Wallet Contract's Ethereum-transaction emulation relayer fee logic.

### Title
Wallet-contract relayer fee is paid unconditionally, before the emulated action executes, letting a relayer collect payment without delivering the transfer - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract::rlp_execute` entry point lets any unprivileged predecessor account ("relayer") submit a user-signed RLP-encoded Ethereum transaction, which is translated into a Near `Action` and executed on the user's behalf. For emulated base-token transfers and ERC-20 transfers, the wallet contract computes a `fee` from the signed transaction's `max_fee_per_gas * gas_limit` and immediately fires an independent transfer promise paying that fee to the relayer, *before* the promise chain that performs the actual transfer/ERC-20 call is created and *without any dependency on that chain's success*.

### Finding Description
In `inner_rlp_execute`, after parsing the RLP transaction into an `Action`/`TransactionKind`: [1](#0-0) 

the relayer refund is created as a *standalone* `promise_batch_create` / `promise_batch_action_transfer` pair, keyed only on the parsed `TransactionKind` carrying a non-zero `fee` and `predecessor != current_account`. This transfer batch is entirely independent of the `promise` that is built afterwards to actually perform the transfer or ERC-20 call: [2](#0-1) 

For the ERC-20 case in particular, the actual value movement requires a multi-step promise chain (`storage_balance_of` → optional `storage_deposit` → `ft_transfer` → `rlp_execute_callback`), any step of which can fail (insufficient token balance inside `ft_transfer`, insufficient gas, or the target contract behaving unexpectedly). None of these failure paths claw back the fee that was already sent to the relayer in the earlier, unconditional promise batch. The same is true for the plain `EOABaseTokenTransfer` path where the underlying `Transfer` action could still fail (e.g., insufficient wallet balance) after the fee has already been dispatched.

This mirrors the reported Splits bug class exactly: a percentage/fixed "incentive" fee meant to compensate a third party for performing real work (the swap in Splits; delivering the transfer/ERC-20 call here) is paid out regardless of whether that work is ever completed, letting an opportunistic caller collect the fee "for free" at the expense of the account that is supposed to benefit from the underlying action.

### Impact Explanation
Any account that submits (or intercepts and re-submits) the RLP transaction as the `predecessor_account_id` of `rlp_execute` — i.e., any unprivileged transaction/RPC caller acting as a "relayer" — can collect the user-authorized fee from the wallet contract's own NEAR balance even when the intended base-token transfer or ERC-20 transfer subsequently fails and the intended recipient receives nothing. This is a concrete unauthorized value movement out of the wallet account, matching the required impact category (fee bypass / unauthorized value transfer) for a valid finding.

### Likelihood Explanation
The relayer only needs to submit a validly-signed, correctly-targeted transaction (so it clears `validate_tx_relayer_data` and reaches the fee-refund block) and does not need to control gas or ensure the downstream call succeeds; failure can arise naturally (stale wallet/token balance at submission time, insufficient attached gas for the deep promise chain, or a malicious/self-controlled `target` contract that reverts). Because the fee promise fires unconditionally before the transfer chain is even created, no special timing or race is required beyond normal message relaying, making this straightforward to trigger for any relayer willing to submit a transaction whose downstream leg they can predict or cause to fail.

### Recommendation
Chain the relayer-fee transfer to the outcome of the actual transfer/ERC-20 promise (e.g., only send the fee from within `rlp_execute_callback` after observing `PromiseResult::Successful`), or make the fee payment conditional on success by including it as part of the same promise batch/callback instead of firing it independently and unconditionally in `inner_rlp_execute`.

### Proof of Concept
1. Wallet owner signs an RLP ERC-20 `transfer` (or base-token transfer) transaction with `max_fee_per_gas * gas_limit` set to a non-trivial `fee`, intending to pay a relayer for submitting it.
2. Before submission, the wallet's balance of the ERC-20 token (or NEAR balance, for base-token transfers) drops below what's needed to satisfy the transfer (e.g. spent via another action, or `target`/registrar conditions are arranged to force `ft_transfer` to fail).
3. A relayer calls `rlp_execute(target, tx_bytes_b64)` as predecessor. `inner_rlp_execute` parses the transaction, matches `TransactionKind::EthEmulation(ERC20Transfer { fee, .. })`, and immediately schedules the independent fee-transfer promise to the relayer (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:374-385`), then separately kicks off the `storage_balance_of` → `ft_transfer` promise chain.
4. The `ft_transfer` step fails (insufficient token balance/gas), so the intended recipient never receives the transfer, but the relayer has already been paid the fee from the wallet's NEAR balance, since that transfer promise was independent and already executed.

            // create a promise to send the refund to the relayer. This allows any relayer
            // to safely serve base token transfers from any wallet without additional
            // on-boarding because the relayer will receive some compensation for sending
            // the transaction. Users should always verify the fee before signing a base token
            // transfer. Relayers should also verify the fee before sending to make sure the
            // user's signed transaction will refund enough to cover the relayer's gas costs.

                fee,
                ..
            })

                &transaction_kind
