### Title
Stale vote/stake account entries persist in `StakesCache` after account owner changes away from the vote/stake program, allowing consensus-relevant stake weight to survive account reassignment - ([File: runtime/src/stakes.rs])

### Summary
`StakesCache::check_and_store` — the single choke point that keeps the bank's in-memory `Stakes<StakeAccount>` (used to derive validator stake weights, vote credits, and leader schedule) synchronized with on-chain account state — only reacts to two cases: the account's owner is currently the vote program, or currently the stake program (in which case it upserts), or the account's lamports are zero (in which case it evicts). If a previously-cached vote or stake account has its **owner reassigned to any other program** while keeping nonzero lamports, none of the branches fire, and the stale cached `VoteAccount`/`StakeAccount` entry is left untouched in the cache.

### Finding Description
`check_and_store` is documented with an explicit unresolved TODO acknowledging the gap: [1](#0-0) 

The logic branches only on `solana_vote_program::check_id(owner)` and `stake_program::check_id(owner)`; there is no `else` branch that evicts an entry when the owner no longer matches either program. This is structurally the same root cause as the Blast `setStaking()` bug: a privileged/consumed reference (here, the cached stake/vote entry keyed by pubkey) is mutated at the source (account owner reassigned via a normal system/program instruction from an unprivileged client, e.g. `Assign`/`CreateAccountWithSeed` reusing the pubkey, or any CPI that reassigns ownership) but the dependent bookkeeping structure (`StakesCache`) is never updated/reset to reflect that the account is no longer a valid stake or vote account. The comment in `check_and_store` itself references the historical Solana Labs PR discussion (`solana-labs/solana#24200`) flagging this exact scenario as unresolved: "If the account is already cached as a vote or stake account but the owner changes, then this needs to evict the account from the cache."

This is reachable from an ordinary client transaction: any instruction that changes an account's owner (e.g. via the System Program's `Assign`, or a CPI-driven reassignment) while the account still carries lamports triggers `check_and_store` with the new owner, but the function silently no-ops instead of evicting the stale cached vote/stake entry.

### Impact Explanation
The bank's consensus-critical structures — active stake weights (`Stakes<StakeAccount>` used for `EpochStakes`, leader schedule, and vote-credit accounting via `bank.vote_accounts()` / `bank.stakes()`) — are derived from this cache. Per the corroborating test `check_stake_vote_account_validity` in `runtime/src/bank/tests.rs`, changing a staked vote/stake account's owner to a bogus program is explicitly tested as a scenario that must be excluded from `bank.vote_accounts()`/loaded stake/vote accounts (`assert_eq!(bank.vote_accounts().len(), 1)` after the owner is changed for one of two accounts), which implies the wider stake/vote loading path is defended elsewhere (e.g., `load_vote_and_stake_accounts` re-validates ownership independently). However, `StakesCache` itself, which is the fast-path structure many other consumers query directly (bank.stakes(), rewards distribution, EpochStakes snapshotting), is left with a stale entry per the acknowledged TODO. If any downstream consumer trusts `StakesCache` without re-verifying current account ownership (unlike the hardened `load_vote_and_stake_accounts` path shown in the test), it could compute stake weights, vote credits, or rewards for a pubkey that is no longer actually a stake/vote account — a potential state/consensus divergence between validators whose caches update at different times/paths, or a lamport/rewards accounting bug (paying stake rewards to an account that is no longer owned by the stake program).

### Likelihood Explanation
Reaching this requires only a standard `Assign`-style ownership change instruction on an account previously delegated as a stake or vote account with nonzero lamports remaining — no elevated privilege needed, any account owner/authority can reassign ownership of their own account. The gap is explicitly documented as a known, unfixed TODO in the current codebase, indicating it is a real, acknowledged latent defect rather than a hypothetical one, though its blast radius depends on which other consumers rely on `StakesCache` without independent re-validation (a fact I could not fully confirm within the remaining exploration budget).

### Recommendation
Add an `else` branch (or restructure the owner check) in `StakesCache::check_and_store` so that when neither `solana_vote_program::check_id(owner)` nor `stake_program::check_id(owner)` matches, but the pubkey is currently present in the vote/stake cache, the entry is explicitly evicted via `remove_vote_account` / `remove_stake_delegation`, mirroring the zero-lamport eviction paths already implemented for the matching-owner branches.

### Proof of Concept
1. Delegate a stake account (or use an existing validator vote account) so it is present in `bank.stakes()`/`StakesCache`.
2. Submit an ordinary client transaction invoking `system_instruction::assign` (or any instruction that calls `set_owner`) on that account to a new, arbitrary program ID while leaving lamports nonzero.
3. Observe that `StakesCache::check_and_store` is invoked with the new (non-stake/non-vote) owner and takes no action — the entry is not evicted, per the code path shown at `runtime/src/stakes.rs:87-116` and the corresponding acknowledged TODO comment.
4. Confirm divergence by directly querying `bank.stakes()` internals (`StakesCache`) for the pubkey versus a hardened consumer such as `load_vote_and_stake_accounts` (exercised in `runtime/src/bank/tests.rs::check_stake_vote_account_validity`), which independently re-checks ownership and excludes the account — demonstrating the cache and the "correct" state have diverged.

Note: I was unable to fully trace every downstream consumer of `StakesCache` within the available exploration budget to conclusively determine whether all consensus-relevant consumers independently re-validate ownership (which would limit this to a latent/defense-in-depth gap rather than an exploitable divergence). This should be verified by a deeper audit of all callers of `Stakes::vote_accounts()`/`Stakes::stake_delegations()` before treating this as a confirmed high-severity consensus bug.

    pub(crate) fn check_and_store(
        &self,
        pubkey: &Pubkey,
        account: &impl ReadableAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,
    ) {
        // TODO: If the account is already cached as a vote or stake account
        // but the owner changes, then this needs to evict the account from
        // the cache. see:
        // https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
        let owner = account.owner();
        // Zero lamport accounts are not stored in accounts-db
        // and so should be removed from cache as well.
        if account.lamports() == 0 {
            if solana_vote_program::check_id(owner) {
                let _old_vote_account = {
                    let mut stakes = self.0.write().unwrap();
                    stakes.remove_vote_account(pubkey)
                };
            } else if stake_program::check_id(owner) {
                let mut stakes = self.0.write().unwrap();
                stakes.remove_stake_delegation(
                    pubkey,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
            }
            return;
        }
