### Title
Missing Early Return in `validate_delegate_action_key` Allows Nonce Consumption on `DepositWithFunctionCall` Error Path — (`runtime/runtime/src/actions.rs`)

---

### Summary

In `validate_delegate_action_key`, when a `DelegateAction` is validated against a function-call access key and the inner `FunctionCall` carries `deposit > 0`, the `DepositWithFunctionCall` error is written to `result.result` but — on protocol versions below 85 — execution is **not** halted. It falls through to the receiver-id and method-name checks, and, if those pass, continues to the unconditional nonce-update block at lines 685–699. The nonce is committed to the trie even though the action is ultimately rejected, consuming the sender's nonce slot without executing the intended action. The caller `apply_delegate_action` detects `result.result.is_err()` and suppresses receipt creation, but the trie write has already occurred.

---

### Finding Description

`validate_delegate_action_key` (`runtime/runtime/src/actions.rs:535`) is responsible for three things: key lookup, nonce validation, and permission enforcement. After all checks pass it unconditionally writes the new nonce to the trie (lines 685–699). The permission block (lines 628–683) is supposed to `return Ok(())` on every failure, but the `DepositWithFunctionCall` branch (lines 637–650) is missing the early return on pre-fix protocol versions:

```rust
if function_call.deposit > Balance::ZERO {
    result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
        InvalidAccessKeyError::DepositWithFunctionCall,
    ).into());
    // ← no return here on protocol < 85
    if ProtocolFeature::FixDelegateActionDepositWithFunctionCallError
        .enabled(apply_state.current_protocol_version)
    {
        return Ok(());   // only added at protocol 85
    }
}
// execution continues to receiver_id check …
```

If the delegate action's `receiver_id` matches the key's `receiver_id` **and** `method_names` is empty (or the method name is in the allowed list), neither of the subsequent guards fires a `return`. Execution reaches:

```rust
match nonce_update {
    DelegateNonceUpdate::AccessKey => {
        access_key.nonce = delegate_nonce.nonce();
        set_access_key(state_update, sender_id.clone(), public_key.clone(), &access_key);
    }
    // …
}
```

The nonce is written to the `TrieUpdate`. `apply_delegate_action` then checks `result.result.is_err()` and returns without emitting a receipt, but the trie write is already staged. Because action-receipt state changes are committed even on action failure (gas has been paid; the outcome records the error), the sender's access-key nonce is permanently advanced.

A secondary consequence: when `receiver_id` does **not** match, the `ReceiverMismatch` error overwrites `DepositWithFunctionCall` in `result.result`, giving the caller a misleading error code. This is confirmed by the in-tree regression test `test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix`.

---

### Impact Explanation

**Nonce manipulation / unauthorized state change.** A relayer (unprivileged user) who receives a `SignedDelegateAction` where the sender used a function-call access key and attached a non-zero deposit can submit it on a node running protocol version < 85. The action fails (no receipt is created, no funds move), but the sender's access-key nonce is incremented. Any subsequent valid transaction from the sender that reuses that nonce will be rejected as `InvalidNonce`. The relayer pays gas; the sender loses a nonce slot and must issue a new transaction with a higher nonce.

**Wrong error code.** When `receiver_id` also mismatches, the reported error is `ReceiverMismatch` rather than `DepositWithFunctionCall`, breaking any client-side logic that branches on the error kind.

---

### Likelihood Explanation

The `FixDelegateActionDepositWithFunctionCallError` feature is assigned protocol version 85 (stable). On any node running protocol version ≥ 85 the early return is active and the bug is unreachable. The legacy code path is preserved in the binary for backward compatibility with older protocol versions. Any node that has not yet upgraded past version 85, or any test/staging environment pinned to an older version, is vulnerable. The trigger requires only a valid `SignedDelegateAction` submitted via the standard JSON-RPC endpoint — no privileged access is needed.

---

### Recommendation

The fix is already present in the codebase, gated behind `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError`. Once all nodes have upgraded past protocol version 85, the legacy fallthrough branch can be removed entirely:

```rust
if function_call.deposit > Balance::ZERO {
    result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
        InvalidAccessKeyError::DepositWithFunctionCall,
    ).into());
    return Ok(()); // unconditional after protocol 85 is universal
}
```

---

### Proof of Concept

**Setup (protocol version < 85):**

1. Account `alice.near` holds a `FunctionCall` access key with `receiver_id = "token.near"` and `method_names = []`.
2. Alice signs a `DelegateAction`:
   - `receiver_id = "token.near"` (matches the key's receiver)
   - inner action: `FunctionCall { method_name: "transfer", deposit: 1 yoctoNEAR, … }`
   - `nonce = N + 1`
3. A relayer submits the meta-transaction via `broadcast_tx_async`.

**Observed behaviour (pre-fix):**

- `validate_delegate_action_key` sets `result.result = Err(DepositWithFunctionCall)`.
- `receiver_id` check passes (they match); `method_names` check passes (empty list).
- Nonce update executes: `access_key.nonce = N + 1` is written to the `TrieUpdate`.
- `apply_delegate_action` detects `result.result.is_err()`, returns without a receipt.
- State is committed: Alice's access-key nonce is now `N + 1`.
- Alice's next transaction with nonce `N + 1` is rejected as `InvalidNonce`.

**Expected behaviour (post-fix, protocol ≥ 85):**

- `validate_delegate_action_key` sets `result.result = Err(DepositWithFunctionCall)` and immediately returns.
- Nonce update is never reached; Alice's nonce remains `N`.

The regression tests `test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix` and `test_delegate_deposit_with_function_call_reports_deposit_error` in `runtime/runtime/src/actions.rs` (lines 1763–1796) confirm both the pre-fix and post-fix behaviour.
