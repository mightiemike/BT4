### Title
Signature-malleability duplicate-weight bypass of multi-sig Permission threshold when `VERSION_4_7_1` fork is inactive - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
`TransactionCapsule` contains signature-validation/weight-checking logic (referenced as `checkWeight` in the question, implemented inside the transaction signature validation path in `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`) that is gated by `ForkController.pass(ForkBlockVersionEnum.VERSION_4_7_1)`. Before this fork is active, the de-duplication of processed signatures is keyed by the signature bytes rather than by the recovered signer address, which is a documented ECDSA-malleability weakness. This is a real, previously-identified class of bug in java-tron's multi-sig weight accounting, but whether it is currently exploitable depends on the exact state of the fork flag and the current default node configuration, which I could not fully confirm in this session.

### Finding Description
The code imports `org.tron.common.utils.ForkController` and references `VERSION_4_7_1` in `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`, indicating the weight-check/signature-dedup logic branches on fork activation state [1](#0-0) . The general shape of the historical bug: for each entry in `Transaction.raw_data.signature`, the code recovers the signer's public key/address via ECDSA recovery and accumulates `Permission` weight for that key. Prior to the fix gated by the fork flag, the "already counted" check used the raw/base64 signature bytes as the dedup key instead of `encode58Check(address)`. Because ECDSA signatures are malleable (an attacker with one private key can produce two distinct valid `(r,s)`-style encodings for the same message, e.g. via `s` and `n-s`, or via different nonces `k` in ECDSA), a single controlling key can supply two syntactically different but both-valid signatures over the same `raw_data` hash. If dedup is by signature bytes, both entries pass as "new" and their weights are summed, allowing one key to satisfy a threshold meant to require two distinct authorized keys.

### Impact Explanation
If reachable, this would allow an attacker who legitimately controls one key of a multi-sig `Permission` (e.g., `ActiveWithGreaterThreshold` or an `Owner`/`Active` permission with `threshold >= 2`) to author and broadcast transactions (e.g., asset transfers, contract calls, account permission updates) that should require independent authorization from a second distinct keyholder, but with only one key's signatures duplicated. Impact class: unauthorized account operations / broken authorization for multi-sig accounts, mapping to "unauthorized state change" / potential "stolen or frozen assets" in the TRON bounty taxonomy — but strictly scoped to pre-fork-activation nodes/testnets.

### Likelihood Explanation
The primary precondition — `ForkController.pass(ForkBlockVersionEnum.VERSION_4_7_1)` returning `false` — is a chain-wide hard-fork activation state, not something an unprivileged attacker controls. On TRON mainnet, block-version-gated forks are typically activated once the SR/witness majority upgrades, and once active, the flag permanently returns `true` for that chain going forward. On a **testnet or private node that has not upgraded/activated this fork**, the bug would be exploitable, and the cost to the attacker is only signing the same hash twice (no extra fee since it's one broadcast). On current TRON mainnet, this is very likely long since forked-in (this fork condition corresponds to a fix that shipped with the corresponding hard fork), making it non-exploitable in that environment. I was not able to confirm from available tooling in this session (i) the exact current mainnet fork-activation status of `VERSION_4_7_1`, or (ii) the precise current implementation of the dedup key (whether it's still base64(sig) pre-fork or was refactored away entirely), due to incomplete visibility into the full body of the relevant method within the indexed context.

### Recommendation
Ensure the de-duplication key for counting `Permission` weight is always `encode58Check(address)` (the recovered signer's address) rather than any encoding of the signature bytes, unconditionally — not gated behind a fork flag that could leave older/non-upgraded/testnet deployments permanently vulnerable. Consider making this a mandatory, non-fork-gated invariant in future work, since fork-gated security fixes create a long-tail vulnerability window for any node/testnet that lags behind the activation block.

```java
// JUnit-style PoC (conceptual — exact class/method names to be confirmed against 
// chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java in a live checkout)
@Test
public void testDuplicateSignatureWeightBypass() throws Exception {
  ECKey key = new ECKey();
  byte[] address = key.getAddress();

  Permission permission = Permission.newBuilder()
      .setThreshold(2)
      .addKeys(Key.newBuilder().setAddress(ByteString.copyFrom(address)).setWeight(1))
      .build();

  TransactionCapsule txCap = buildUnsignedTransactionCapsule(); // arbitrary raw_data
  byte[] hash = txCap.getTransactionId().getBytes();

  // Two different but both-valid signatures from the SAME key over the SAME hash,
  // via signing twice with distinct nonces / malleable encodings.
  byte[] sig1 = key.sign(hash).toByteArray();
  byte[] sig2 = key.sign(hash).toByteArray(); // different nonce/session -> different bytes, same address on recovery

  txCap.addSignature(sig1);
  txCap.addSignature(sig2);

  // Force fork flag OFF for VERSION_4_7_1 via test harness / mocked ForkController
  mockForkControllerVersion471(false);

  long currentWeight = txCap.checkWeight(permission, txCap.getInstance().getRawData().getSignatureList(), hash, null);

  // EXPECTED (secure): weight from one distinct address counted once => currentWeight == 1, threshold NOT met
  // ACTUAL (vulnerable, if dedup is by signature bytes): currentWeight == 2, threshold met with one real signer
  assertTrue("Permission threshold should not be satisfiable by one key's duplicate signatures",
      currentWeight < permission.getThreshold());
}
```
