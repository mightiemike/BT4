### Title
Unsynchronized raw-pointer reads race with mutex-protected mmap writes in `FileHandler` - ([File: crates/apollo_storage/src/mmap_file/mod.rs])

### Summary
`FileHandler<V, Mode>` stores a raw `*const u8` pointer (`memory_ptr`) into a memory-mapped file and manually forces `Send`/`Sync` on it via `unsafe impl`, even though reads through this pointer are never synchronized with the `Mutex`-guarded writes to the same memory region. This mirrors the `lever` `AtomicBox<T>` advisory pattern: a type is unconditionally marked thread-safe via `unsafe impl Send/Sync` while its actual access pattern is not race-free, enabling cross-thread data races/UB on the shared memory region.

### Finding Description
`open_file` creates a single `MmapMut` wrapped in `Arc<Mutex<MMapFile<V>>>`, but also hands out the raw pointer `mmap_ptr = mmap.as_ptr()` to both the `RW` and `RO` `FileHandler` instances as `memory_ptr`: [1](#0-0) 

`FileHandler` is explicitly forced to be `Send + Sync` via unsafe impls, analogous to the `lever` `AtomicBox<T>` bug where `Send`/`Sync` were blanket-implemented without verifying the safety invariant actually holds: [2](#0-1) 

The writer path (`append`) takes the `Mutex` lock, writes into `mmap_file.mmap`, and updates `offset`: [3](#0-2) 

But the reader path (`Reader::get`) dereferences `self.memory_ptr` directly via `std::slice::from_raw_parts`, entirely bypassing the `Mutex`: [4](#0-3) 

This is a genuine data race under the Rust memory model: one thread performs synchronized writes (through the `Mutex`) to the mmap while another thread performs unsynchronized reads of the same bytes through a raw pointer that was never subject to any lock or atomic fence. There is no happens-before relationship enforced between the writer's mutation of the underlying bytes (`append`) and the reader's raw dereference (`get`) beyond whatever ordering the caller externally imposes (e.g., committing a DB transaction that publishes the `LocationInFile`). If a reader thread observes the updated `LocationInFile` from the DB (LMDB) transaction/commit but the corresponding mmap byte writes are not yet globally visible on that thread (due to compiler/CPU reordering, since the read path uses no atomic/lock synchronization at all), `get` can read torn/stale/partially-written bytes, which are then fed into `V::deserialize`.

This directly affects consensus-critical storage tables reachable from unprivileged actions: `casm`, `contract_class`, `deprecated_contract_class`, `transaction`, `transaction_output`, and `thin_state_diff`, all backed by `FileHandler`: [5](#0-4) 

CASM/class bytes written via `append_casm` (triggered by a declare transaction) are read back through `get_casm_from_location` / `get_casm_unchecked`, which is on the path used to fetch compiled classes for execution: [6](#0-5) [7](#0-6) 

### Impact Explanation
If a reader thread (serving a state read, class fetch, or re-execution request) observes torn or stale bytes from the mmap due to the unsynchronized raw-pointer read racing with a concurrent writer's mutex-protected mutation, deserialization of a `CasmContractClass`, `SierraContractClass`, `DeprecatedContractClass`, `Transaction`, `TransactionOutput`, or `ThinStateDiff` can silently succeed with corrupted content (or panic, depending on `StorageSerde::deserialize` behavior on malformed bytes) instead of failing safely. Because CASM/class bytes feed directly into contract execution and compiled-class-hash verification, this can lead to divergence between nodes (a node reading corrupted CASM behaves differently from one reading the correct CASM), i.e., honest-node divergence — one of the explicitly accepted impact categories.

### Likelihood Explanation
The `FileHandler<..., RO>` reader handles are shared (`Arc<Mutex<MMapFile<V>>>` for the writer state, but the raw pointer is held outside any lock) across the storage reader and writer components, which run concurrently in the sequencer (e.g., gateway/mempool serving class reads while the batcher/committer appends new classes/txs during block building). Any declared class (a call reachable by any unprivileged declare transaction) triggers `append_casm`/`append_contract_class`, and any subsequent read of that class (reachable by any transaction referencing it, e.g., during execution or a state read RPC) exercises the racing `get` path. No special privilege is needed to trigger both the write (declare transaction) and the read (any transaction invoking the class, or a storage read query) sides of the race.

### Recommendation
Do not derive `Send`/`Sync` unsafely for `FileHandler` while giving out an unsynchronized raw pointer. Instead: (1) route all reads through the same `Mutex`-guarded `MMapFile` state used for writes so that reads and writes are properly ordered, or (2) use an atomic/fenced mechanism (e.g., store the raw pointer address in a way that reads are only permitted after acquiring at least a shared lock, or use `Arc<RwLock<...>>` semantics), ensuring a happens-before edge exists between `append`'s mutation and any subsequent `get`'s raw read of the same byte range. Add loom/miri-based or stress concurrency tests exercising simultaneous `append` and `get` on the same `FileHandler` pair to catch such races going forward.

### Proof of Concept
1. Two threads share the `(FileHandler<V, RW>, FileHandler<V, RO>)` pair returned by `open_file`.
2. Thread A repeatedly calls `append(val)` (writer), which takes `mmap_file.lock()`, writes bytes into `mmap_file.mmap[offset..]`, and returns the `LocationInFile` — publishing it via an external, unsynchronized channel/`Arc<AtomicUsize>` visible to Thread B (mirroring how `casm_table.insert` publishes the location via the LMDB txn without any fence tied to the mmap bytes).
3. Thread B, upon observing the new `LocationInFile`, calls `get(location)` on the `RO` handler, which dereferences `self.memory_ptr` directly via `std::slice::from_raw_parts` with no lock acquired.
4. Under `--cfg miri` or with TSAN-instrumented builds (or simply on weakly-ordered hardware/compiler optimizations), Thread B's raw read races with Thread A's mutex-protected write to the same underlying memory, which is flagged by ThreadSanitizer/Miri as a data race and can manifest as a torn/garbled deserialization of `CasmContractClass` in production without any fault.

impl<V: ValueSerde + Debug> Writer<V> for FileHandler<V, RW> {
    fn append(&mut self, val: &V::Value) -> LocationInFile {
        trace!("Inserting object: {:?}", val);
        let serialized = V::serialize(val).expect("Should be able to serialize");
        let len = serialized.len();
        let offset;
        {
            let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
            offset = mmap_file.offset;
            trace!("Inserting object at offset: {}", offset);
            let mmap_slice = &mut mmap_file.mmap[offset..];
            mmap_slice[..len].copy_from_slice(&serialized);
            mmap_file
                .mmap
                .flush_async_range(offset, len)
                .expect("Failed to asynchronously flush the mmap after inserting");
            mmap_file.offset += len;
            mmap_file.should_flush = true;
        }
        let location = LocationInFile { offset, len };
        self.grow_file_if_needed(location.next_offset());
        location
    }

impl<V: ValueSerde, Mode: TransactionKind> Reader<V> for FileHandler<V, Mode> {
    /// Returns an object from the file.
    fn get(&self, location: LocationInFile) -> MmapFileResult<Option<V::Value>> {
        trace!("Reading object at location: {:?}", location);
        let mut bytes = unsafe {
            std::slice::from_raw_parts(
                self.memory_ptr.offset(location.offset.try_into()?),
                location.len,
            )
        };
        trace!("Deserializing object: {:?}", bytes);
        Ok(V::deserialize(&mut bytes))
    }
}

impl<Mode: TransactionKind> CasmStorageReader for StorageTxn<'_, Mode> {
    fn get_casm(&self, class_hash: &ClassHash) -> StorageResult<Option<CasmContractClass>> {
        let casm_location = self.get_casm_location(class_hash)?;
        casm_location.map(|location| self.get_casm_from_location(location)).transpose()
    }

    fn get_casm_and_sierra(
        &self,
        class_hash: &ClassHash,
    ) -> StorageResult<(Option<CasmContractClass>, Option<SierraContractClass>)> {
        Ok((self.get_casm(class_hash)?, self.get_class(class_hash)?))
    }

    fn get_casm_location(&self, class_hash: &ClassHash) -> StorageResult<Option<LocationInFile>> {
        let casm_table = self.open_table(&self.tables.casms)?;

        Ok(casm_location)
    }
