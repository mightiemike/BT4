### Title
Cross-user JSON-RPC request-ID collision enables griefing DoS on Gateway trigger/capability handlers - (File: `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`, `core/services/gateway/handlers/confidentialrelay/handler.go`, `core/services/gateway/handlers/vault/handler.go`)

### Summary
The Gateway's HTTP trigger, confidential-relay, and vault handlers each track in-flight requests in a map keyed solely by the client-supplied JSON-RPC `id` field, with no per-caller/per-workflow namespacing. Any unprivileged user can pick the same `id` value as another user's pending request; whichever request is processed second is unconditionally rejected as a duplicate, denying service to that legitimate caller. This mirrors the "user-chosen `loanId` collision" bug class from the external report, where an attacker preempts a victim's chosen identifier to force the victim's operation to fail.

### Finding Description
`httpTriggerHandler.setupCallback` stores a pending request keyed by `requestID` (which is simply `req.ID`, chosen entirely by the caller) in the shared map `h.callbacks`: [1](#0-0) 

If a second request arrives with the same `requestID` while the first is still in flight, it is rejected with a user error and an `"in-flight request"` error, regardless of who the caller is: [2](#0-1) 

The only validation performed on the caller-supplied `id` is that it is non-empty and does not contain `/`; there is no requirement that it be unique per-caller, per-workflow, or unpredictable: [3](#0-2) 

The same pattern - a global map keyed purely by `req.ID` with a "request ID already exists" rejection - exists independently in the confidential-relay handler: [4](#0-3) 

and in the vault handler: [5](#0-4) 

This is confirmed as intended/known behavior by the existing "duplicate request ID" tests, which only check that the *second* submitter is rejected - they do not consider the case where the second submitter is an unrelated, malicious party targeting a specific victim's chosen ID: [6](#0-5) [7](#0-6) 

Just as the Folks Finance `loanId` is user-chosen and globally unique across all users (allowing an attacker to squat on a victim's intended `loanId`), the Gateway `requestID`/JSON-RPC `id` is user-chosen and globally unique across all callers to a given handler instance, with no binding to caller identity, workflow ID, or owner. An attacker who learns or predicts a victim's chosen `id` (e.g., sequential counters, timestamp-derived IDs, or values leaked via logs/telemetry/observability, all common client patterns) can submit a request with that same `id` first, causing the victim's subsequent legitimate request to be rejected outright with no possibility of the operation succeeding under that ID.

### Impact Explanation
This is a griefing/DoS impact analogous to the reported issue: a legitimate, unprivileged user's `workflows.execute`/vault/confidential-relay request can be selectively blocked by any other unprivileged user who front-runs with a colliding `id`, without any special privilege, node compromise, or cost beyond issuing an ordinary API call. Unlike the on-chain case, there is no "retry with different loanId" recovery path exposed to the victim's client at the protocol layer - the rejection is immediate and the specific request must be resubmitted with a different ID, which the caller may not know how to select safely if the ID scheme is externally dictated (e.g., idempotency keys expected by an upstream system).

### Likelihood Explanation
Exploitability depends on the attacker being able to learn or predict a victim's `id` before the victim's request completes. This is plausible when: (a) IDs are generated using low-entropy schemes (sequential integers, timestamps) by common client SDKs; (b) IDs are visible in shared infrastructure, logs, or client-side code the attacker can observe; or (c) the ID is a well-known/expected value (e.g., idempotency key derived from a public order ID). Likelihood is moderate - it requires the attacker to have some visibility into or prediction of the victim's ID choice, which is a weaker precondition than the original report's public pending-transaction visibility, but still realistic for externally-facing HTTP trigger endpoints in `httpTriggerHandler`.

### Recommendation
Namespace in-flight request tracking by caller identity in addition to the caller-supplied `id`, e.g., key the `callbacks`/`activeRequests` map by a composite of authenticated caller/workflow owner and `req.ID` (as already partially done for vault's outbound response ID via `owner + vaulttypes.RequestIDSeparator + requestID`, but not for the inbound duplicate-check in `newActiveRequest`/`setupCallback`). This ensures a collision can only occur within a single authenticated caller's own request stream, eliminating the cross-user griefing vector while preserving duplicate-detection for legitimate retries.

### Proof of Concept
1. Victim (or a benign client) prepares an HTTP trigger request to `httpTriggerHandler.HandleUserTriggerRequest` with `req.ID = "victim-order-42"`, targeting `workflowID = W`.
2. Attacker, having learned/predicted `"victim-order-42"` (e.g., a low-entropy or leaked identifier), submits a request with the same `req.ID = "victim-order-42"` (any workflow selector; the collision check happens purely on the `id` before workflow-specific dispatch) slightly ahead of the victim.
3. `setupCallback` (`http_trigger_handler.go` lines 397-404) inserts the attacker's entry into `h.callbacks["victim-order-42"]`.
4. When the victim's genuine request arrives, `setupCallback` finds `h.callbacks["victim-order-42"]` already present and returns a `jsonrpc.ErrConflict` user error ("requestID: victim-order-42 has already been used..."), exactly reproducing the behavior demonstrated by the existing `duplicate request ID` test case: [8](#0-7)  - except in the attack scenario, callback1 belongs to the attacker and callback2 (rejected) belongs to the victim.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
