This confirms the analog exists: TRON's `AccountPermissionUpdateContract` permission check does not restrict which permission (Owner or Active) can modify the account's own Owner permission set, provided the signing key's Active permission includes the `AccountPermissionUpdateContract` bit in its `operations` bitmap. This mirrors the report's root cause: a lower-privileged role (`ROLE_MANAGER_ROLE`-equivalent Active permission holder) is able to invoke the role-assignment function (`AccountPermissionUpdateActuator`) and grant itself/others the highest privilege (Owner permission), without any explicit safeguard preventing an Active-permission signer from rewriting the Owner permission to include arbitrary keys with dominant weight.

### Title
Active-permission signer can self-escalate to Owner-level control via `AccountPermissionUpdateContract` - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator.validate()`/`execute()` allows any transaction whose signer satisfies an account's **Active** permission (not necessarily the **Owner** permission) to rewrite that account's entire permission set — Owner, Witness, and Active permissions — as long as the Active permission's `operations` bitmap includes the `AccountPermissionUpdateContract` type bit. There is no additional check preventing such an Active-permission holder from inserting itself (or a colluding address) into the new Owner permission with sufficient weight to meet the Owner threshold, similar to how the reported `ROLE_MANAGER_ROLE` could assign itself the `ROLE_MANAGER_ROLE`/retain elevated privileges.

### Finding Description
The permission check for which key may sign an `AccountPermissionUpdateContract` transaction is generic and contract-type based: `TransactionCapsule.validateSignature`/`checkPermission` resolves the permission by `permissionId` from the transaction and, for non-zero (i.e., Active) permission IDs, only verifies that the permission type is `Active` and that the operations bitmap has the bit for the contract's type set [1](#0-0) . The `AccountPermissionUpdateActuator.execute()` then unconditionally calls `account.updatePermissions(...)` with the new Owner/Witness/Active permissions supplied in the contract, completely replacing the account's existing permission structure [2](#0-1) . The `validate()`/`checkPermission()` logic only checks structural constraints (key count, threshold ≥ 0 sum, distinct addresses, operations size/validity) — it never checks whether the signer of the transaction (identified via `permissionId`) already holds Owner-level authority before allowing it to overwrite the Owner permission [3](#0-2) . Thus if an account owner ever grants an Active permission key the `AccountPermissionUpdateContract` operation bit (a seemingly limited, delegated administrative capability, analogous to `ROLE_MANAGER_ROLE`), that key holder can unilaterally rewrite the account's Owner permission (analogous to `SUPER_ADMIN_ROLE`) to grant itself full weight/threshold control, permanently locking out or diluting the original owner — mirroring the reported flaw where a `ROLE_MANAGER_ROLE` could assign itself the reserved higher-privilege role.

### Impact Explanation
An account owner who intends to delegate only the "manage permissions" capability to a semi-trusted operational key (e.g., an automated key management/rotation bot) unintentionally grants that key full ability to seize complete ownership of the account (all TRX/TRC balances, resources, voting rights), because the Active-key-driven permission update is not restricted from touching the Owner permission. This is a full account takeover / unauthorized privilege escalation.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires that an account owner has explicitly delegated the `AccountPermissionUpdateContract` type into an Active permission's operations bitmap in the first place — a deliberate configuration decision rather than a default state. However, this is a plausible and even encouraged multisig pattern (delegating "permission management" as a distinct role from "asset transfer"), which is exactly analogous to the original report's `ROLE_MANAGER_ROLE` being trusted for role assignment but not Super Admin assignment.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`, when the signing key's resolved permission (via `contract.getPermissionId()`) is of type `Active` (not `Owner`), reject the update if the new Owner permission differs from the existing Owner permission, or otherwise require that only the `Owner` permission itself may authorize changes to the Owner permission (and to other Active permissions with equal-or-greater privilege scope). This mirrors the report's recommendation to prevent a `ROLE_MANAGER_ROLE`-equivalent signer from assigning itself (or others) the reserved highest-privilege role.

### Proof of Concept
1. Account `A` grants Active permission key `K` (weight/threshold sufficient to meet Active threshold) with `operations` bitmap bit set for `AccountPermissionUpdateContract`, intending `K` to only manage day-to-day active permissions.
2. Holder of `K` crafts and signs an `AccountPermissionUpdateContract` transaction with `permissionId` referencing `K`'s Active permission, setting the `owner` field to a new `Permission` where `K` (or an address controlled by the attacker) has weight ≥ new Owner threshold.
3. `AccountPermissionUpdateActuator.validate()` passes all structural checks (`checkPermission`) since none of them verify that only Owner-permission signers may alter the Owner permission [4](#0-3) .
4. `execute()` calls `account.updatePermissions(...)`, replacing the Owner permission with the attacker-controlled one [5](#0-4) , giving the former Active-key holder full Owner-level control of account `A`, including the ability to lock out the original owner in a subsequent transaction.

  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
