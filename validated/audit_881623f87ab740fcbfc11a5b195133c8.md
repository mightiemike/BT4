### Title
Panic-inducing `unwrap()` on `receiver_shard_id()` failure in `DelayedReceiptQueueWrapper::receipt_filter_fn` can halt chunk production - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
The Linux CVE fixes a null-pointer dereference caused by dereferencing an optional pointer (`aux_mode`) without a fallback/guard when it is absent, crashing the kernel. The structurally analogous pattern in nearcore is an `unwrap()` on a `Result` that can be an `Err` in a reachable, attacker/protocol-influenced scenario, causing a node/validator panic instead of a null pointer crash. This was found in `DelayedReceiptQueueWrapper::receipt_filter_fn`, which is on the receipt-processing path exercised by any contract call that creates a `GlobalContractDistribution` receipt, combined with dynamic resharding.

### Finding Description
`DelayedReceiptQueueWrapper::pop` drains the delayed receipt queue and, for ReshardingV3, calls `receipt_filter_fn` to decide whether a popped receipt still belongs to the current shard: [1](#0-0) 

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

`receiver_shard_id()` for a `GlobalContractDistribution` receipt attempts to resolve a possibly-stale `target_shard` (recorded when the receipt was created, potentially several resharding generations ago) to a shard in the *current* layout via `shard_layout.resolve_to_current_shard(target_shard)`. If that resolution fails (the target shard cannot be mapped forward through the layout's split history), the function returns an `Err(EpochError::ShardingError(...))` rather than a shard id: [2](#0-1) 

`receipt_filter_fn` then unconditionally `.unwrap()`s this `Result`. If it is an `Err` (analogous to the missing/absent pointer in the kernel bug), the call panics rather than gracefully falling back or propagating a typed error, crashing the node process that is applying the chunk.

The repository's own test suite documents this exact scenario as a target for regression testing: [3](#0-2) 

The test comment explicitly states: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations."* The scenario constructs: deploy a global contract (an ordinary, unprivileged `DeployGlobalContract` action any account can submit) whose `GlobalContractDistribution` receipt gets stuck in the delayed queue (via gas saturation) across **two consecutive shard splits**, so that by the time it is popped, `target_shard` is two generations stale.

### Impact Explanation
If `resolve_to_current_shard` cannot map a doubly-stale `target_shard` (i.e., the shard-layout split history retained is insufficient to trace it forward, e.g., due to garbage collection of old layouts, an off-by-one in split-history tracking, or simply enough resharding generations occurring while the receipt is delayed), `receipt_filter_fn`'s `unwrap()` panics inside `Runtime::apply`'s receipt-processing loop. Because this is invoked from the core state-transition function that all validators/chunk producers run identically, a single delayed `GlobalContractDistribution` receipt surviving two reshardings would deterministically panic every honest node applying that chunk — a transaction-triggered chain halt for the affected shard (all validators tracking the shard would crash trying to apply the same chunk, matching the "transaction-triggered halt" acceptance criterion).

### Likelihood Explanation
Triggering requires: (1) deploying a global contract (unprivileged, single transaction any account can send), (2) saturating a shard's chunk compute budget for enough blocks that the resulting `GlobalContractDistribution` receipt is pushed to the delayed queue, and (3) the shard undergoing **two** resharding events while that receipt remains delayed. Dynamic resharding is a protocol-level, automatically-triggered process (not attacker controlled) in this codebase (`DynamicReshardingConfig`), so an attacker cannot directly force two reshardings on demand, but can maximize the chance by saturating compute on a shard slated for repeated splits to keep the receipt delayed as long as possible. This makes exploitation feasible but conditioned on resharding cadence, which lowers likelihood from "trivial" to "situational" — still realistic given dynamic (automatic) resharding is a first-class supported feature in this codebase, and the delay only needs to span two reshardings, which the included test reproduces in a bounded number of epochs.

### Recommendation
Replace the `unwrap()` calls in `receipt_filter_fn` with proper error propagation: change its signature to return `Result<bool, RuntimeError>` (or similar), propagate `EpochError`/`StorageError` up through `pop()` as a typed `RuntimeError`, and ensure the caller (`process_delayed_receipts`) handles that error without panicking — e.g., by treating an unresolvable stale distribution receipt as a `StorageInconsistentState` error that surfaces cleanly instead of crashing the process, consistent with how other "delayed receipt must stay valid" invariants are handled elsewhere in `runtime/runtime/src/lib.rs` (`process_delayed_receipts`'s failed-`validate_receipt` handling maps to `StorageInconsistentState` rather than panicking).

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs` (lines 30–186) is itself a working reproduction harness:
1. Deploys a global contract from `user0` while `user0`'s shard is scheduled to be the first of two force-split shards.
2. Saturates the shard's compute budget every block via repeated `burn_gas_raw` calls so the `GlobalContractDistribution` receipt (targeting `user0`'s original shard) is pushed into the delayed queue and stays there.
3. Lets two sequential dynamic-resharding splits occur (`force_split_shards: vec![first_split_shard, second_split_shard]`) while the receipt is still delayed, making its `target_shard` two generations stale.
4. Stops saturating and drains the delayed queue; the assertion `head_height >= drain_end` is the check that the chain did **not** stall/panic while draining the stale receipt through `receipt_filter_fn`'s `unwrap()` calls.

I was not able to fully verify from the index whether `resolve_to_current_shard` in `core/primitives/src/shard_layout/v3.rs` is guaranteed to always succeed across arbitrarily many resharding generations (which would mean the `Err` branch, and thus the `unwrap()` panic, is currently unreachable in practice) — the file's `resolve_to_current_shard` implementation was not retrievable within the indexed context. This is the residual uncertainty in the finding: the `unwrap()` on a fallible `Result` is a genuine defensive-coding gap that mirrors the reported CVE's bug class, but whether it is reachable in the current shard-layout split-history bookkeeping (versus only historically, before a prior fix) could not be conclusively confirmed here. A full review of `ShardLayoutV3::resolve_to_current_shard` and its split-history retention/GC guarantees is recommended to confirm exploitability with certainty.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }
