### Title
Documentation/Implementation Mismatch: `MsgMigrateUEA` Message Path Is Documented as Removed But Remains Live, Wired, and Gasless - (File: `x/uexecutor/keeper/msg_server.go`, `app/txpolicy/gasless.go`)

### Summary
This is a direct native analog of the `proposeBeneficiary()` report: the module documentation asserts an authorization/architecture invariant ("the Cosmos layer no longer has a dedicated migration message") that the actual code contradicts. `x/uexecutor/keeper/msg_server.go` still implements a fully wired `MigrateUEA` `MsgServer` method backed by `MsgMigrateUEA`, and this message type remains in the gasless whitelist, meaning any unprivileged account can submit it at zero Cosmos-fee cost.

### Finding Description
`x/uexecutor/README.md` states explicitly:

> **UEA migration is now part of payload execution.** There used to be a separate `MsgMigrateUEA` message; that path has been removed. UEAs are upgraded by submitting a normal `MsgExecutePayload`... The Cosmos layer no longer has a dedicated migration message — the UEA contract is the source of truth for who is allowed to migrate it and to what implementation. [1](#0-0) 

However, the actual `MsgServer` implementation still exposes and fully processes `MigrateUEA`: [2](#0-1) 

And `MsgMigrateUEA` is still present in the gasless message allowlist consumed by the ante-handler decorators (`MinGasPriceDecorator`, `DeductFeeDecorator`, `AccountInitDecorator`): [3](#0-2) 

This is structurally identical to the external report's bug class: the documented authorization/architecture model ("this path doesn't exist / can't be used this way") diverges from what the implementation actually permits, exactly as the `proposeBeneficiary()` NatSpec claimed owner-only access while `requiresAuth` permitted broader callers.

Unlike `MsgExecutePayload` — whose README documents in detail *why* `Signer != Owner` is safe (the cryptographic binding lives inside the UEA contract's `executeUniversalTx`, verified via ECDSA/Ed25519 recovery against the immutable stored owner key, with nonce/deadline replay protection) — no equivalent "why this is safe" analysis is documented for the still-live `MigrateUEA` path: [4](#0-3) 

Because the README declares this path "removed," it is very plausible that this handler no longer receives the same security scrutiny, review, or fuzzing as the documented-and-supported `ExecutePayload` path, while remaining fully reachable, unprivileged (any signer), and fee-free (gasless).

### Impact Explanation
If `Keeper.MigrateUEA` does not independently and correctly re-implement the same signature/nonce binding checks that `ExecutePayload`'s underlying UEA contract enforces, an unprivileged attacker could submit `MsgMigrateUEA` for an arbitrary victim's `UniversalAccountId` and trigger unauthorized UEA implementation migration — a module-originated EVM state transition affecting a victim-controlled account without the owner's authorization. This falls squarely into the in-scope impact of "unauthorized UEA or CEA execution... unauthorized state transitions in universal execution flows." Even if the underlying keeper does correctly gate this (mirroring `ExecutePayload`'s safety model), the stale documentation itself is evidence of drift between intended and actual authorization architecture, and is the exact bug class the external report flags: dead/forgotten authorization paths retaining broader-than-intended reachability.

### Likelihood Explanation
Likelihood is difficult to assess with full confidence from index-only visibility — the actual body of `Keeper.MigrateUEA` (which performs the real authorization/signature verification) was not directly inspected in this pass. Given the pattern already established in `MsgExecutePayload` (documented, safety-justified `Signer ≠ Owner` model), the same protection is plausibly re-used inside `Keeper.MigrateUEA`. However, the documentation explicitly claiming the path is "removed" while it remains live, gasless, and MsgServer-registered is itself a code/doc integrity issue that warrants explicit verification — exactly the kind of drift the original report's recommendation ("update comments to reflect actual implementation" / "add explicit checks") targets.

```markdown
#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
```

```go
// MigrateUEA handles UEA Migration.
func (ms msgServer) MigrateUEA(ctx context.Context, msg *types.MsgMigrateUEA) (*types.MsgMigrateUEAResponse, error) {
	_, evmFromAddress, err := utils.GetAddressPair(msg.Signer)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to parse signer address")
	}

	err = ms.k.MigrateUEA(ctx, evmFromAddress, msg.UniversalAccountId, msg.MigrationPayload, msg.Signature)
	if err != nil {
		return nil, err
	}

	return &types.MsgMigrateUEAResponse{}, nil
}
```
