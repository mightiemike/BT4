### Title
Denial of Service via unbounded-recursion JSON parsing of untrusted `params` in the JSON-RPC request body - (File: chain/jsonrpc-primitives/src/message.rs, chain/jsonrpc/src/lib.rs)

### Summary
The nearcore JSON-RPC server deserializes every inbound HTTP POST body into a `Message`/`Request` whose `params` field is a raw, untyped `serde_json::Value` [1](#0-0) , parsed through `serde_json` before any application-level validation runs. `serde_json`'s `Value` deserializer walks nested JSON arrays/objects using normal (non-tail) recursion with no depth counter, so a deeply nested array/object payload drives the parser's native call stack to overflow, exactly the class of bug described in the external report (recursive parser crash via stack overflow, CWE-121/CWE-787).

### Finding Description
`rpc_handler()` (the single POST entry point at `/`) uses the Axum `Json<Message>` extractor to deserialize the whole request body before any method-specific logic executes [2](#0-1) . `Message`/`Request` are ordinary `serde`-derived types where `params: Value` is deserialized generically [1](#0-0) , and the top-level `Message` enum is `#[serde(untagged)]`, which additionally requires probing multiple shapes of the same nested value during deserialization [3](#0-2) .

The only protection applied before parsing is the router-level body byte-size cap ("Middleware: CORS ... and request body size limit (default 10MB)" per the RPC architecture doc) — no *structural* (nesting-depth) limit is enforced. Ten megabytes is more than enough to encode hundreds of thousands of nesting levels (e.g. `[[[[...]]]]`), which is far beyond what a native thread stack can absorb during `serde_json`'s recursive-descent value construction. Compare this to how the network layer explicitly protects Borsh-encoded, peer-supplied blobs from oversized/attacker-controlled structures via `try_from_slice_with_limit` and `MAX_TRANSACTION_SIZE_BYTES`/`MAX_ROUTED_MESSAGE_SIZE_BYTES` [4](#0-3) [5](#0-4)  — no equivalent depth/complexity guard exists for the untrusted JSON body accepted by the RPC server, which is reachable by any unauthenticated RPC caller with a single HTTP request, no signature, no gas, and no account required.

Elsewhere in the codebase, engineers have specifically called out and avoided this exact recursion-based crash pattern for trie traversal ("Non recursive approach to avoid any potential stack overflows." [6](#0-5) ) and have guarded the one legitimately recursive, attacker-influenced structure in the transaction/receipt model — nested `Delegate` actions — by construction, using `NonDelegateAction`'s custom Borsh decoder to reject any nested delegate action at the type level [7](#0-6) [8](#0-7) . No analogous guard exists for the free-form JSON `params` blob accepted at the RPC boundary.

### Impact Explanation
A stack overflow in the process handling the JSON-RPC HTTP listener aborts the entire node process (Rust has no way to recover from a genuine native stack overflow; it triggers a hard process abort/segfault, not a catchable panic). Because `JsonRpcHandler` is wired directly into the same node binary as `ClientActor`/`ViewClientActor`/`RpcHandlerActor` (validator/producer node or RPC node), crashing the HTTP-serving thread/process denies availability of the entire node to all users — for a validator this means missed block production and, if it is reproducible and cheaply repeatable by an outside caller against a specific validator's public RPC endpoint or against a light/RPC node relied on for chunk/tx submission, it is a transaction-triggerable (request-triggerable) halt of that node's service to the network.

### Likelihood Explanation
Likelihood is high in principle (a single unauthenticated HTTP POST, no economic cost, no special privileges, works against the default-enabled `/` route), but I could not fully confirm from static analysis whether the specific `serde_json`/`Value` recursion path used here is guarded by a recursion-limit feature at the version pinned in this repo, or whether an intervening layer (e.g., a WAF, a stack-size increase, or `serde_json`'s "arbitrary_precision"/"unbounded_depth" style hardening in a newer release) already mitigates it. I was not able to inspect the pinned `serde_json` version or Cargo.lock in this pass, and the tool budget was exhausted before I could confirm whether Axum's body-size middleware order guarantees the byte cap is enforced strictly before any parsing begins (some HTTP frameworks stream-parse before the full body limit check completes). These are dependency/version-specific details that affect exploitability and would need to be validated in a running instance.

### Recommendation
- Add an explicit maximum-JSON-nesting-depth check (or use a `serde_json::Deserializer` configured with `disable_recursion_limit()` disabled — i.e., keep/verify the recursion limit is enabled and tightened — or pre-scan the raw bytes for excessive `[`/`{` nesting before invoking `serde_json::from_slice`) in the `rpc_handler()` request path in `chain/jsonrpc/src/lib.rs`, applied before the `Json<Message>` extractor / `near_jsonrpc_primitives::message::from_slice` call in `chain/jsonrpc-primitives/src/message.rs`.
- Apply the same depth cap to the Rosetta RPC server's request parsing, which shares the same untyped-JSON risk pattern.
- Add a regression test that posts a deeply nested JSON payload (e.g., 100k+ levels of `[` nesting) within the existing 10MB body-size budget and asserts the server returns a JSON-RPC parse error rather than crashing.
- Consider running the HTTP JSON parsing on a thread with a bounded, monitored stack, or wrapping parsing in `std::thread::Builder::stack_size` + `catch_unwind`-safe isolation so a worst-case recursion failure degrades to a single connection error rather than a full process crash.

### Proof of Concept
Conceptual PoC (not executed against a live node in this pass):
```
POST / HTTP/1.1
Host: <rpc-node>:3030
Content-Type: application/json
Content-Length: <size just under 10MB>

{"jsonrpc":"2.0","id":1,"method":"status","params":[[[[[[[[[[ ... repeated ~500,000+ times ... ]]]]]]]]]]}
```
This is well under the documented 10MB request body limit for the JSON-RPC HTTP endpoint, while containing enough array nesting to exhaust a typical 8MB thread stack during `serde_json`'s recursive `Value` parsing invoked from `rpc_handler()` [2](#0-1)  via `Request.params: Value` [1](#0-0) .

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}
