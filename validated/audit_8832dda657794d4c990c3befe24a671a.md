Confirmed: `ValidateForExecution` never validates `RevertInstructions.FundRecipient` format at all — it only checks `Amount`, `AssetAddr`, and `Recipient` (Push-Chain EVM side) [1](#0-0) . There is no chain-namespace/length check anywhere on the outbound path for `FundRecipient` before `buildRevertOutbound` copies it verbatim into the refund `OutboundTx.Recipient` [2](#0-1) .

The canonicalization itself also does not enforce that the address actually matches the source chain's expected format/length:

- `CanonicalizeAddressByNamespace` only dispatches on the CAIP-2 namespace prefix (`eip155` vs `solana`) [3](#0-2) .
- For a `solana:*` source chain, `canonicalizeSolanaValue` accepts *any* even-length hex string (with `0x` prefix) as valid, without checking it decodes to a 32-byte Solana pubkey [4](#0-3) . A 20-byte EVM-style hex address (40 hex chars) satisfies "even length hex" and is accepted, lowercased, and passed through unmodified — it is never rejected as chain-mismatched.
- `LenientCanonicalizeAddress` (used in `Inbound.Canonicalize()` on `RevertInstructions.FundRecipient`) only falls back to trimmed input on parse *error*; since the Solana namespace's hex-branch doesn't error on a 20-byte value, it never even hits the lenient fallback — it returns a "canonical" but foreign-format value silently [5](#0-4) [6](#0-5) .

So the described path is real: an attacker submits an inbound with `SourceChain = "solana:..."` and `RevertInstructions.FundRecipient` set to a 20-byte EVM-hex address; `Canonicalize()` accepts it as-is; `ValidateForExecution()` has no check on it; on execution failure, `buildRevertOutbound` copies this foreign-format value directly into the refund `OutboundTx.Recipient` [7](#0-6) , which is what the honest UVs will then sign and broadcast to the Solana chain. That transaction is expected to fail there since the address isn't a valid Solana pubkey. This is the same code path exercised by `RevertStuckInbound`/`admin_revert.go`, and normal inbound-execution-failure reverts inside `VoteInbound` [8](#0-7) , both of which are reachable without any privileged actor — it's an ordinary user-submitted inbound with attacker-controlled `RevertInstructions`.

However, per the scope rules, this requires evaluating whether it results in **material, permanent, unrecoverable fund loss** as opposed to a stuck/pending outbound state that could later be corrected (e.g., via the existing `RESCUE_FUNDS`/admin-revert-retry mechanisms already present in the codebase, such as `AttachRescueOutboundFromReceipt`) — the repo already has dedicated "stuck funds" remediation flows (`rescue_funds_test.go`, `admin_revert.go`) suggesting the protocol has designed-in recovery paths for exactly this class of problem (failed/undeliverable outbound). I was not able to fully trace whether an outbound that fails at the external-chain broadcast stage due to a malformed recipient is automatically retried, permanently marked `OUTBOUND_FAILED`, or has any on-chain recovery mechanism triggered by an unprivileged party — that would determine whether the loss is truly *permanent* or just a delay requiring privileged (admin/UV) intervention (which would fall out of scope per the "malicious/privileged actor" exclusion, but recoverability via *any* honest path, privileged or not, would defeat "permanent freezing").

Given the tool budget is exhausted, I cannot conclusively verify the final recoverability step (whether `OUTBOUND_FAILED` for `INBOUND_REVERT` type has any subsequent recovery path). Based on what is confirmed — a genuine missing validation gap on `RevertInstructions.FundRecipient` chain-format matching that is reachable by an unprivileged attacker and propagates into the actual refund `OutboundTx.Recipient` — this is a legitimate finding.

### Title
Missing chain-format validation on `RevertInstructions.FundRecipient` allows attacker-controlled cross-namespace refund address to reach the revert outbound - (File: `x/uexecutor/types/inbound.go`, `utils/canonical.go`, `x/uexecutor/keeper/build_revert_outbound.go`)

### Summary
`Inbound.Canonicalize()` canonicalizes `RevertInstructions.FundRecipient` using `LenientCanonicalizeAddress(SourceChain, ...)`, but neither this canonicalization nor `ValidateForExecution()` verifies that the resulting address is actually a well-formed address *for that chain's namespace* (e.g., a correctly-sized Solana pubkey vs. a 20-byte EVM address). The unchecked value flows directly into `buildRevertOutbound`'s `Recipient` field.

### Finding Description
`utils.canonicalizeSolanaValue` treats any even-length hex string as a valid Solana value regardless of byte length, so a 20-byte EVM-style hex address passes for a `solana:*` chain without error [4](#0-3) . Because it doesn't error, `LenientCanonicalizeAddress` returns it as the "canonical" value rather than falling back or rejecting [6](#0-5) . `Inbound.Canonicalize()` applies this uncritically to `RevertInstructions.FundRecipient` [5](#0-4) , and `ValidateForExecution()` never checks this field at all [1](#0-0) . On execution failure, `buildRevertOutbound` copies `FundRecipient` verbatim into the refund `OutboundTx.Recipient` [7](#0-6) .

### Impact Explanation
If honest UVs sign and broadcast a refund to a malformed/wrong-format address on the source chain, the outbound will likely fail on that chain, and the refunded amount may become stuck pending some recovery mechanism. Whether this is truly *permanent* loss or a recoverable delayed state could not be fully confirmed within the available exploration.

### Likelihood Explanation
Fully attacker-controlled and reachable via ordinary inbound submission with no privileged action required — the mismatched value survives both `Canonicalize()` and `ValidateForExecution()` unmodified.

### Recommendation
Add namespace-and-length-aware validation to `ValidateForExecution()` (or to `Canonicalize()`/`CanonicalizeAddressByNamespace`) for `RevertInstructions.FundRecipient`, rejecting addresses that don't match the expected byte-length/format for the `SourceChain`'s CAIP-2 namespace (e.g., require Solana values to decode to exactly 32 bytes), rather than accepting any even-length hex string.

### Proof of Concept
1. Submit `VoteInbound` with `SourceChain = "solana:101"`, a valid Solana `Sender`, and `RevertInstructions.FundRecipient = "0x000000000000000000000000000000000000beef"` (a 20-byte EVM-format address).
2. Observe `Canonicalize()` accepts it unmodified/lowercased rather than rejecting or falling back to `Sender`.
3. Trigger an execution failure (e.g., invalid `AssetAddr` or amount) so `handleFailedInboundValidation` → `buildRevertOutbound` runs.
4. Assert `OutboundTx.Recipient` equals the 20-byte EVM-format string, which is not a valid Solana account address that TSS/UVs can deliver funds to on-chain.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}

func canonicalizeSolanaValue(s string) (string, error) {
	s = strings.TrimSpace(s)
	if body, had0x := strip0x(s); had0x && len(body)%2 == 0 && isHexString(body) {
		return "0x" + strings.ToLower(body), nil
	}
	if isBase58String(s) {
		return s, nil
	}
	return "", fmt.Errorf("invalid solana value %q: neither 0x-hex nor base58", s)
}

// CanonicalizeAddressByNamespace canonicalizes an address for the given

func CanonicalizeAddressByNamespace(chain, addr string) (string, error) {
	addr = strings.TrimSpace(addr)
	if addr == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMAddress(addr)
	case namespaceSolana:
		return canonicalizeSolanaValue(addr)
	default:
		return addr, nil
	}
}
