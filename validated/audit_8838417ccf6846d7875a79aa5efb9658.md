`depositPRC20`/`CallPRC20Deposit` ultimately call `k.evmKeeper.DerivedEVMCall(...)` [3](#0-2) , which returns an `*evmtypes.MsgEthereumTxResponse`. In the standard Cosmos EVM module semantics that this codebase relies on, a contract-level revert (e.g. the PRC20 mint function reverting due to a blacklist check, pause state, overflow guard, or any other legitimate contract-level condition) is surfaced through the response's `VmError` field, not necessarily as a non-nil Go `error` — the call itself can "succeed" at the message-execution layer while the state change it attempted is rolled back.

- `pcTx.Status` is recorded as `"SUCCESS"` in the UniversalTx's `PcTx` audit trail even though the PRC20 was never minted, corrupting the on-chain accounting record.

### Title
PcTx status falsely recorded as SUCCESS on EVM-level PRC20 deposit revert, causing accounting corruption and skipped refund path - (File: x/uexecutor/keeper/execute_inbound_funds.go)

### Summary
`ExecuteInboundFunds` determines deposit success solely from the Go-level `error` returned by `depositPRC20`/`CallPRC20Deposit`→`DerivedEVMCall`, without checking the EVM response's `VmError`/revert status, unlike the sibling `create_outbound.go` which does check `VmError`.

### Finding Description
When the `depositPRC20Token` EVM call executes but reverts inside the EVM (contract-level revert), the wrapping Go call can return a non-nil receipt with `err == nil` (revert captured in `VmError`, not as a Go error) per the established Cosmos EVM module convention used elsewhere in this codebase. `ExecuteInboundFunds` treats any `err == nil` outcome as `SUCCESS` and appends that status to `utx.PcTx`, and skips the revert-outbound compensation logic that is gated on `err != nil`.

### Impact Explanation
The UniversalTx's PcTx audit trail can diverge from the true PRC20 balance state, and the honest revert/refund flow for a failed deposit is skipped, meaning the user's inbound funds may become unaccounted for/effectively stuck with no automatic outbound revert issued.

### Likelihood Explanation
Reachable purely through an ordinary user's inbound deposit interacting with a PRC20 contract that can legitimately revert (pause, blacklist, cap/overflow checks, etc.) — no privileged actor is required, only depends on whether `DerivedEVMCall`'s wrapping in this codebase surfaces reverts as `VmError` rather than a Go `error`, which the presence of `VmError` checks in `create_outbound.go` strongly suggests is the case.

### Recommendation
In `ExecuteInboundFunds`, inspect `receipt.VmError` (or equivalent revert indicator) in addition to the Go `error`, and treat a non-empty `VmError` the same as a failed deposit — set `pcTx.Status = "FAILED"` and trigger the revert-outbound path — mirroring the pattern already used in `create_outbound.go`.

### Proof of Concept
Mock `depositPRC20`/`CallPRC20Deposit` (or the underlying `DerivedEVMCall`) to return `(*evmtypes.MsgEthereumTxResponse{VmError: "execution reverted"}, nil)`. Call `ExecuteInboundFunds` and assert that `pcTx.Status` is incorrectly `"SUCCESS"` and no revert-outbound was attached, while the PRC20 balance for the recipient did not change — demonstrating the audit-trail/accounting divergence.

I was not able to directly inspect the external `cosmos/evm` module's `DerivedEVMCall`/`CallEVM` implementation (it lives outside this repo's indexed scope as a dependency), so I could not verify with 100% certainty that reverts are always surfaced with `err == nil`. This is inferred from the codebase's own convention of explicitly checking `VmError` in `create_outbound.go`, which strongly implies this is the expected failure mode for these EVM calls.
