### Title
Missing chain/network-binding in the NEP-366/NEP-461 `DelegateAction` signing payload enables cross-network replay of meta-transactions - (File: `core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

### Summary
Just as the LPTokenFactory bug allowed a signed action to be replayed on a different chain because `chain.id` was absent from the signed data, NEAR's meta-transaction (`DelegateAction`/`DelegateActionV2`) signing payload contains no network-identifying value (no genesis hash, no chain id, no block hash). The signature only binds `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` under a fixed message-type discriminant.

### Finding Description
A `DelegateAction` is signed off-chain by the user and handed to a relayer, who wraps it in a normal `SignedTransaction` and submits it on-chain [1](#0-0) . The hash that is actually signed is computed purely from the `DelegateAction`/`DelegateActionV2` fields plus a fixed `SignableMessageType` discriminant — no genesis hash, chain id, or even a recent block hash is included: [2](#0-1) [3](#0-2) 

Compare this with a normal `SignedTransaction`, whose outer wrapper *does* reference a `block_hash` tied to the specific chain it is submitted to. The inner `DelegateAction`, however, only carries `max_block_height`, a plain integer deadline, not a chain-anchored value [4](#0-3) . Two independent NEAR-protocol networks (e.g. a mainnet fork, or a new network bootstrapped by cloning mainnet/testnet state — a capability nearcore explicitly ships via the `tools/mirror` state-mirroring utility [5](#0-4) ) can share identical account ids, identical access-key public keys, and identical access-key nonces for the same account, at least until state diverges. Replay protection for a `DelegateAction` is enforced only via the sender's on-chain access-key nonce (`DelegateActionInvalidNonce`) and `max_block_height` [6](#0-5)  — both of which are values, not chain-binding identifiers, and both of which are identical across two networks that share genesis/account state.

### Impact Explanation
A `SignedDelegateAction` a user creates and hands to a relayer for execution on network A can be captured (by the relayer, a MITM, or simply because it is broadcast/observed) and replayed verbatim on network B, provided the sender's account+key+nonce state is still in sync between the two networks and the current block height on B is below `max_block_height`. Because the inner actions can be arbitrary (`AddKeyAction`, `TransferAction`, `FunctionCall`, etc.), this allows unauthorized execution of the user's intended action on a network the user never intended to interact with — e.g. adding an attacker-controlled access key, transferring tokens, or invoking a contract call the user never authorized in that context. This is unauthorized value movement/action execution triggered purely by a transaction a legitimate user (meta-transaction sender) already produced.

### Likelihood Explanation
This requires two NEAR-protocol networks that share the same account/key/nonce state (a fork, or a genesis-mirrored/cloned network — both of which the codebase supports and even tooling exists for, `tools/mirror`). This is analogous to the audit finding being disputed on the basis of "single-chain deployment" but the judge upholding it because "chains can and have forked" and node operators/teams change their minds about multi-network deployments. The same reasoning applies directly here: nearcore is designed to be forkable/mirrorable, and the signing scheme provides no defense-in-depth against this scenario.

### Recommendation
Include a chain-identifying value (e.g., the genesis hash / chain id) inside the `DelegateAction`/`DelegateActionV2` payload that gets hashed and signed in `get_nep461_hash`, similar to how EVM's EIP-712 domain separator binds signatures to a specific `chainId`. This ensures a `SignedDelegateAction` produced for one NEAR network cannot be validly replayed on any other network, even one that shares identical account/key/nonce state.

### Proof of Concept
1. Network A and Network B are two independent NEAR-protocol chains that share the same genesis/state (e.g., B is a fork of A, or B was bootstrapped by mirroring A's state, as supported by `tools/mirror`).
2. Alice, an account that exists identically on both A and B with the same access key and nonce, signs a `DelegateAction` (e.g. `AddKeyAction` granting a relayer's key, or a `TransferAction`) intending it to be relayed only on network A.
3. `get_nep461_hash()` produces a hash from `sender_id, receiver_id, actions, nonce, max_block_height, public_key` only — no chain id is present [7](#0-6) .
4. The relayer (or any party who intercepts the `SignedDelegateAction`) wraps it into a transaction on network B and submits it before Alice's `max_block_height` deadline on B.
5. Because Alice's nonce/state matches on B, `SignedDelegateAction::verify()` succeeds and the action executes on B [8](#0-7) , even though Alice never intended to interact with network B.

With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.

/// The struct a user creates and signs to create a meta transaction.
struct DelegateAction {
    /// Signer of the delegated actions
    pub sender_id: AccountId,
    /// Receiver of the delegated actions.
    pub receiver_id: AccountId,
    /// List of actions to be executed.
    ///
    /// With the meta transactions MVP defined in NEP-366, nested
    /// DelegateActions are not allowed. A separate type is used to enforce it.
    pub actions: Vec<NonDelegateAction>,
    /// Nonce to ensure that the same delegate action is not sent twice by a
    /// relayer and should match for given account's `public_key`.
    /// After this action is processed it will increment.
    pub nonce: Nonce,
    /// The maximal height of the block in the blockchain below which the given DelegateAction is valid.
    pub max_block_height: BlockHeight,
    /// Public key used to sign this delegated action.
    pub public_key: PublicKey,
}
