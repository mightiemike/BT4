### Title
Session lifetime is unbounded via sliding `last_used` refresh, bypassing intended absolute session expiry - ([File: core/sessions/localauth/orm.go])

### Summary
`findValidSession` validates a session solely by checking `last_used + sessionDuration >= now()`, and `updateSessionLastUsed` resets `last_used` to `now()` on every authenticated request. Because there is no check against the session's `created_at`, an attacker who obtains a valid `sessionID` once can keep it alive forever simply by issuing a request at least once per `sessionDuration` window, defeating the documented "session lasts X duration before requiring re-login" control.

### Finding Description
`AuthorizedUserWithSession` (`core/sessions/localauth/orm.go:87`) calls `findValidSession` (`core/sessions/localauth/orm.go:69`), whose SQL is:
```
SELECT email FROM sessions WHERE id = $1 AND last_used + $2 >= now() FOR UPDATE
```
This only enforces an idle/inactivity timeout — it never considers the session row's `created_at`. Immediately after, `AuthorizedUserWithSession` calls `updateSessionLastUsed` (`core/sessions/localauth/orm.go:78`), which unconditionally sets `last_used = now()`. The background `sessionReaper.Work`/`deleteStaleSessions` (`core/sessions/localauth/reaper.go:35-47`) has the identical weakness: it computes a stale threshold from `now() - SessionReaperExpiration - SessionTimeout` and deletes rows where `last_used < threshold` — again driven only by `last_used`, not `created_at`.

The config docs explicitly describe the intended semantics: `SessionTimeout` is "the amount of idle time to elapse before session cookies expire" while `SessionReaperExpiration` "represents how long an API session lasts before expiring and requiring a new login" (`docs/CONFIG.md:550-560`, `core/config/docs/core.toml:199-202`). This documented behavior implies an absolute cap on total session lifetime, but the implementation only provides a sliding inactivity window: any periodic request (interval < `sessionDuration`) resets `last_used` and keeps the session valid and un-reaped indefinitely. `AuthenticateBySession` (`core/web/auth/auth.go:55-71`) is the sole entry point feeding session IDs into this logic and performs no additional age check.

By contrast, the OIDC session reaper (`core/sessions/oidcauth/reaper.go:47`) deletes based on `created_at`, showing the intended design elsewhere enforces an absolute cutoff — the local-auth path lacks this.

### Impact Explanation
An attacker who captures a session cookie once (XSS, log leak, shoulder-surf, etc.) can maintain persistent authenticated access to the Chainlink node's Operator UI/API indefinitely, as long as they poll periodically, fully bypassing the intended forced re-authentication control. This is a session-management/authz weakness enabling long-term unauthorized access persistence, matching a "broken session management leading to prolonged unauthorized access" bounty category. It does not by itself grant privilege escalation beyond the compromised user's role, but it removes an intended security boundary (mandatory periodic re-login).

### Likelihood Explanation
Requires only possession of a valid session ID (no privilege escalation needed) and the ability to send periodic HTTP requests with that cookie — a low-effort, highly repeatable precondition typical of session-hijacking scenarios (XSS, shared/log-leaked cookies, unattended browser sessions). No rate limiting or additional check blocks the refresh loop.

### Recommendation
Enforce an absolute session lifetime by checking against `created_at` in addition to `last_used` in `findValidSession` (e.g., `AND created_at + $absoluteMax >= now()`), and update `deleteStaleSessions`/the reaper to also reap sessions whose `created_at` exceeds the configured maximum age, mirroring the OIDC reaper's `created_at`-based cutoff.

### Proof of Concept
Integration test in `core/sessions/localauth/orm_test.go` style:
1. Configure `sessionDuration` small (e.g., 2s) via `NewORM`.
2. `CreateSession` for a test user, capturing `sessionID`.
3. Loop N times (N * sessionDuration > several times a proposed "absolute" max, e.g. 10 iterations of 2s = 20s), sleeping `sessionDuration - epsilon` between iterations and calling `AuthorizedUserWithSession(ctx, sessionID)` each time.
4. Assert every call succeeds (no `ErrUserSessionExpired`), and that after the loop, `orm.Sessions` still lists the session with `last_used` far past any reasonable absolute cutoff based on `created_at` — demonstrating no absolute expiry is ever enforced. func (o *orm) findValidSession(ctx context.Context, sessionID string) (email string, err error) {
	if err := o.ds.GetContext(ctx, &email, "SELECT email FROM sessions WHERE id = $1 AND last_used + $2 >= now() FOR UPDATE", sessionID, o.sessionDuration); err != nil {
		o.lggr.Infof("query result: %v", email)
		return email, pkgerrors.Wrap(err, "no matching user for provided session token")
	}
	return email, nil
}

// updateSessionLastUsed updates a session by its ID and sets the LastUsed field to now().
func (o *orm) updateSessionLastUsed(ctx context.Context, sessionID string) error {
	_, err := o.ds.ExecContext(ctx, "UPDATE sessions SET last_used = now() WHERE id = $1", sessionID)
	return err
}

func (o *orm) AuthorizedUserWithSession(ctx context.Context, sessionID string) (user sessions.User, err error) {
	if len(sessionID) == 0 {
		return sessions.User{}, sessions.ErrEmptySessionID
	}

	email, err := o.findValidSession(ctx, sessionID)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	user, err = o.findUser(ctx, email)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	if err := o.updateSessionLastUsed(ctx, sessionID); err != nil {
		return sessions.User{}, err
	}

	return user, nil
}
