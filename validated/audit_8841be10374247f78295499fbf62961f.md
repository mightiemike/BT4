### Title
Stale zero-cost account entries accumulate unbounded in `cost_by_writable_accounts` via retried/dropped transactions - ([File: cost-model/src/cost_tracker.rs])

### Finding Description
`CostTracker::remove` calls `remove_transaction_cost`, which calls `sub_transaction_execution_cost` for every writable account key of the removed transaction: [1](#0-0) . Unlike the rollback path used inside `try_add` on partial-application failure (`roll_back_applied_costs`, which explicitly checks `if new_account_cost == 0 { entry.remove(); }`, [2](#0-1) ), `sub_transaction_execution_cost` unconditionally does `entry(*account_key).or_insert(0)` followed by `saturating_sub`, and never removes the entry even when the resulting value is zero: [3](#0-2) .

This means any `try_add` followed by a `remove` (e.g., a transaction added to the tracker and later dropped/retried by banking stage before landing in a block) leaves a zero-valued `Pubkey` entry permanently in `cost_by_writable_accounts` for the remainder of the slot. The existing unit test `test_try_add_rollback_removes_zeroed_entries` explicitly demonstrates this behavior and even asserts `Some(&0)` remains in the map after `testee.remove(&tx_cost)`: [4](#0-3) . The map is only fully reset when a new tracker is created via `new_from_parent_limits`, which happens once per new bank/slot: [5](#0-4) .

The `number_of_accounts()` helper already accounts for this discrepancy by filtering for non-zero values, confirming that zero entries are an expected and tolerated artifact of the design: [6](#0-5) .

An unprivileged user can create many distinct single-account transactions using unique (self-created/self-funded) account keys, cause them to be added and then removed within the same slot (e.g., by paying fees to get them scheduled and then hitting a downstream failure, or having them dropped/retried), and repeat with new unique keys. Each cycle leaves one permanent stale entry in the `HashMap<Pubkey, u64>` for the slot, with map growth proportional to churn count rather than to fees paid or actual accounts touched by successfully committed transactions.

### Impact Explanation
This causes disproportionate, attacker-controlled memory growth in `CostTracker::cost_by_writable_accounts` within a single slot, scaling with transaction churn rather than any fee paid or block space consumed. It also inflates the cost of `find_costliest_account` and `find_number_of_contended_accounts`, which iterate the full map (`.iter()` / `.values()`), turning per-slot bookkeeping into O(churn) rather than O(committed transactions). This matches the "disproportionate storage and CPU cost" impact category — it is a resource-accounting/DoS-adjacent efficiency bug, not a consensus, balance, or hash-divergence bug.

### Likelihood Explanation
Highly feasible and repeatable: any transaction that is added via `try_add` and later removed via `remove` (a normal, expected code path for retried/replaced/dropped transactions in banking stage) triggers the leak with each unique account key used only once. No special privileges, staked status, or leader control are required — a normal fee-paying user with control over their own transaction/account keys can create the churn. The bug is bounded to lifetime of a single slot (reset on `new_from_parent_limits`), limiting worst-case impact to per-slot memory/CPU, but it is deterministically reproducible.

### Recommendation
Make `sub_transaction_execution_cost` remove the map entry when its post-subtraction value reaches zero, mirroring the logic already present in `roll_back_applied_costs`:
```rust
fn sub_transaction_execution_cost(&mut self, tx_cost: &TransactionCost<impl TransactionWithMeta>, adjustment: u64) {
    for account_key in tx_cost.writable_accounts() {
        if let Entry::Occupied(mut entry) = self.cost_by_writable_accounts.entry(*account_key) {
            let new_account_cost = entry.get().saturating_sub(adjustment);
            if new_account_cost == 0 {
                entry.remove();
            } else {
                *entry.get_mut() = new_account_cost;
            }
        }
    }
    self.block_cost.fetch_sub(adjustment);
}
```
This also removes the need for `number_of_accounts()` to filter zero-valued entries.

### Proof of Concept
```rust
#[test]
fn test_remove_leaves_stale_zero_entries() {
    let mut cost_tracker = CostTracker::default();
    let cost = 100u64;
    let churn = 1000;

    for _ in 0..churn {
        let key = Pubkey::new_unique();
        let transaction = WritableKeysTransaction::new(vec![key]);
        let tx_cost = simple_transaction_cost(&transaction, cost);
        cost_tracker.try_add(&tx_cost).unwrap();
        cost_tracker.remove(&tx_cost);
    }

    // Non-zero (real) accounts tracked:
    assert_eq!(0, cost_tracker.number_of_accounts());
    // But the underlying map has retained one stale zero entry per churned key:
    assert_eq!(churn, cost_tracker.cost_by_writable_accounts.len());
}
```
This demonstrates that `cost_by_writable_accounts.len()` grows linearly with add/remove churn while `number_of_accounts()` (real non-zero accounted cost) stays at zero, confirming unbounded stale-entry accumulation until the tracker is reset by `new_from_parent_limits` at the next slot.
