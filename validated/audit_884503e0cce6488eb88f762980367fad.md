## Finding

### Title
Native-position writes are silently dropped on WriteSet replay because `WriteSetV0.extensions` is `#[serde(skip)]`, causing position-state divergence between live execution and replay/restart — ([File: types/src/write_set.rs])

### Summary
Position (perp/trading) writes produced by the `native_position` Move natives are stored in a `WriteSet` side-channel (`Extension::NativePosition`) rather than in the normal value write set. This side-channel is only serialized when the `WriteSet` is upgraded to `WriteSetV1`; on the default `WriteSetV0` representation the field is annotated `#[serde(skip)]` and is therefore silently dropped whenever the write set is serialized to bytes and later deserialized (persisted to `write_set_db`, replicated to another node, or replayed at bootstrap). The V0→V1 upgrade is driven exclusively by the `HOTNESS_IN_EPILOGUE` feature flag, while the Move-level natives that actually create position writes are gated only by the independent `TRADING_NATIVE`/`NATIVE_POSITION` flags. If governance enables position-writing without also enabling `HOTNESS_IN_EPILOGUE`, position writes are correctly applied in the executing node's live in-memory pipeline, but are permanently lost from the on-disk/serialized write set, causing the position Jellyfish Merkle tree/KV store to diverge from what execution actually produced as soon as the chunk is replayed (restart, backup/restore, or state sync to a following node).

### Finding Description
- `WriteSetV0` carries `hotness` and `extensions` fields but both are tagged `#[serde(skip)]`, explicitly to keep on-disk bytes and `TransactionInfo` hashes unaffected by these side-channels: [1](#0-0) 
- `WriteSetV1` is the only variant that actually serializes `extensions` (and `hotness`): [2](#0-1) 
- Native position writes are carried exclusively inside `Extension::NativePosition`, consumed via `WriteSet::native_position_iter()`, described explicitly as being "used by the storage commit applier": [3](#0-2) [4](#0-3) 
- The only place that promotes a `WriteSet` from V0 to V1 (thereby making `extensions` survive serialization) is `convert_write_sets_to_v1`, gated solely by `onchain_config.hotness_in_epilogue()`: [5](#0-4) [6](#0-5) 
- `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (the flag that would consensus-verify the position root) is explicitly required to also imply `HOTNESS_IN_EPILOGUE`; the developers' own comment confirms this exact hazard ("V0 drops them, so output-replay would diverge"), but this coupling is only enforced for `compute_trading_native_state_roots`, not for the underlying write path: [7](#0-6) 
- However, the Move natives that actually *create* position writes (`native_set_position` / `native_delete_position`) are gated only by the independent `NATIVE_POSITION` feature flag, with no dependency on `HOTNESS_IN_EPILOGUE`: [8](#0-7) 
- `TRADING_NATIVE`/`NATIVE_POSITION` are documented as an independent "umbrella" pair sufficient to enable writes, with `COMPUTE_TRADING_NATIVE_STATE_ROOTS` described as an *additional*, separately-gated feature that "the actual Move-side writes to those trees are gated by separate flags": [9](#0-8) 
- Downstream, the storage layer commits/replays position writes by reading `output.write_set().native_position_iter()` both from live in-memory `TransactionOutput`s at commit time and from write sets deserialized from persisted storage during bootstrap replay: [10](#0-9) [11](#0-10) 

Because the second read path (`replay_position_after_snapshot`) reconstructs `WriteSet`s from `write_set_db` bytes, if those bytes were written while the write set was still `WriteSetV0` (i.e. `HOTNESS_IN_EPILOGUE` off), the deserialized `WriteSet` will have an empty `extensions` vector and `native_position_iter()` yields nothing — even though the same transaction genuinely staged position writes at execution time and those writes were already applied to the live in-memory `PositionDb`/merkle tree before the process restarted.

### Impact Explanation
This is a durable-ledger-data corruption / commit-divergence bug in a state-commitment pathway:
- A node that restarts, fast-syncs, or is bootstrapped from a backup/chunk executor replay will silently lose all native-position writes recorded while `HOTNESS_IN_EPILOGUE` was off, producing a position Jellyfish Merkle tree and KV store that differs from the tree the same transactions produced on first execution.
- The position tree/KV store is exposed through authenticated, proof-bearing DB APIs (`get_position_state_proof_by_version_ext`, `get_persisted_position_state_summary`, `get_state_value_chunk_with_proof` for `StateKind::Position`), so a node that replayed rather than freshly executed will serve *valid-looking* Merkle proofs for a state that is silently missing entries relative to the transactions that were actually executed — an authenticated-response/proof-binding integrity break. [12](#0-11) [13](#0-12) 
- Because `TRADING_NATIVE`/`NATIVE_POSITION` can, per their own documentation, be turned on independently of `HOTNESS_IN_EPILOGUE`, this is reachable purely through normal governance/feature-flag configuration without needing `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (the flag that would have forced the safe coupling). This meets the bar for "committed state that differs from correct VM result / corrupts durable ledger data" and "authenticated API output bound to the wrong ... proof context."

### Likelihood Explanation
This requires only an on-chain governance/feature-flag configuration where `TRADING_NATIVE` and `NATIVE_POSITION` are enabled while `HOTNESS_IN_EPILOGUE` remains disabled — a combination that is not prevented anywhere in the reviewed code (feature-flag enable/disable paths, native's `check_feature_enabled`, and the position commit code all check only their own local flag). Any full-node restart, state-sync catch-up, or chunk-executor replay under that configuration triggers the divergence deterministically, since it reads through `write_set_db`/persisted write sets rather than the live in-process struct.

### Recommendation
Enforce the coupling between position writes and the V1 write-set format at the point where position writes are permitted to occur, not only for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`:
- Either make the `native_set_position`/`native_delete_position` natives' `check_feature_enabled` also require `HOTNESS_IN_EPILOGUE` (mirroring the `with_features` coupling already used for `compute_trading_native_state_roots`), or
- Stop skipping serialization of `extensions` unconditionally on `WriteSetV0` (e.g., always serialize `Extension::NativePosition` regardless of write-set version), so replay/restart never silently drops these writes irrespective of feature-flag combinations.

### Proof of Concept
1. Enable `TRADING_NATIVE` and `NATIVE_POSITION` feature flags without enabling `HOTNESS_IN_EPILOGUE`.
2. Execute a transaction that calls `native_set_position`, producing a `WriteSet::V0` whose in-memory `extensions` contains `Extension::NativePosition`.
3. Observe `commit_native_position` successfully write the position leaf into `PositionDb`/merkle tree using the live in-memory `TransactionOutput`.
4. Persist the block (write sets serialized into `write_set_db` as `WriteSetV0`, dropping `extensions` per `#[serde(skip)]`).
5. Restart the node (or run `chunk_executor`/backup-restore replay), forcing `replay_position_after_snapshot` to reconstruct write sets from `write_set_db`.
6. Deserialized `WriteSet`s now report `native_position_iter()` as empty for the transaction from step 2; the recomputed position tree omits the leaf that was present before restart — a durable, reproducible state divergence purely from persist/restart, independent of any malicious input.

*Note: I was unable to conclusively locate the exact call site that invokes `WriteSet::add_native_positions` when the VM output is first materialized (only its definition and staging context were found via search), so I cannot state with certainty whether that call path itself is unconditionally gated on `HOTNESS_IN_EPILOGUE`. The core defect — that `WriteSetV0.extensions` is `#[serde(skip)]` while the natives that populate it are gated by an independent flag — is directly confirmed in code and stands regardless of that call site's exact location.*

/// Native-position write produced by a transaction. Type-distinct from [`WriteOp`] so the compiler
/// refuses to mix native-position entries into the main-state bucket.
///
/// Carried inside [`Extension::NativePosition`] on a `WriteSet`. The storage commit applier (in
/// `aptos-db`) consumes it via [`WriteSet::native_position_iter`].
#[derive(Clone, Debug, Eq, PartialEq)]
pub struct NativePositionOp(BaseStateOp);

impl NativePositionOp {
    pub fn from_write_op(op: WriteOp) -> Self {
        Self(op.into_base_op())
    }

    pub fn as_base_op(&self) -> &BaseStateOp {
        &self.0
    }

    /// Borrow as a `WriteOp`. Always succeeds because the only
    /// constructor takes a `WriteOp`.
    pub fn as_write_op(&self) -> &WriteOp {
        self.0
            .as_write_op_opt()
            .expect("NativePositionOp must wrap a WriteOp variant")
    }
}

impl Serialize for NativePositionOp {
    fn serialize<S>(&self, serializer: S) -> std::result::Result<S::Ok, S::Error>
    where
        S: Serializer,
    {
        self.as_write_op().serialize(serializer)
    }
}

impl<'de> Deserialize<'de> for NativePositionOp {
    fn deserialize<D>(deserializer: D) -> std::result::Result<Self, D::Error>
    where
        D: Deserializer<'de>,
    {
        WriteOp::deserialize(deserializer).map(NativePositionOp::from_write_op)
    }
}
