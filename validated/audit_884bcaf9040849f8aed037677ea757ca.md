## Finding Summary

The strongest analog I found is a proof-integrity gap in `TransactionOutput::ensure_match_transaction_info` [1](#0-0) , used by the replay-verify tooling to check that re-executed VM output matches the transaction info recorded in backup/archive storage.

### Title
Replay-verify accepts divergent state checkpoint roots because `ensure_match_transaction_info` never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function that binds a freshly re-executed `TransactionOutput` to an authenticated `TransactionInfo` pulled from backup/archive storage during replay verification. It checks status, gas, write-set hash, and event-root hash, but it never checks any of the state-checkpoint-related hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), even though those fields are part of `TransactionInfo` and are covered by the accumulator/ledger-info signature. This mirrors the seed bug's pattern (a critical field accepted without validation), but here the unvalidated field is a committed state root rather than a constructor parameter.

### Finding Description
`ensure_match_transaction_info` validates:
- execution status [2](#0-1) 
- gas used [3](#0-2) 
- write-set hash [4](#0-3) 
- event-root hash [5](#0-4) 

But it explicitly skips the checkpoint hashes, and the code itself flags this as a known gap: [6](#0-5) 

This function is called from `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and compares the result against the `expected_txn_info` read from backup storage: [7](#0-6) 

Since `state_checkpoint_hash` (the Sparse Merkle Tree root of world state at checkpoints), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are never compared here, a divergence between the locally re-executed state root and the archived/authenticated one at a checkpoint boundary is silently ignored by this verification path.

### Impact Explanation
The state-checkpoint hash is the field that actually authenticates the committed world state (as opposed to just the write-set/events of a single transaction). If a bug in execution, storage-commit, or state-checkpoint hashing produces a different Merkle root than what was originally committed and signed by validators, `replay_on_archive`/replay-verify tooling — whose entire purpose is to catch exactly this class of divergence across historical or hard-fork replay — will report success. This masks state-commitment corruption or non-determinism that should be caught before it propagates, undermining the "hard-fork-only divergence during commit/replay/restore" integrity guarantee this tool exists to protect. The gap is high severity for auditors/operators relying on `replay_on_archive` as a correctness oracle, since it can hide state-root divergence rather than surfacing it.

### Likelihood Explanation
This is not a speculative gap — the omission is present in the shipped comparator and is explicitly called out in the code's own TODO comment as a known limitation that must be fixed before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, confirming the local root cause and the exact fields affected. The affected `ensure_match_transaction_info` is on the primary comparison path of the replay-verify tool.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the recomputed output (once state checkpointing runs for that transaction) and the expected `TransactionInfo`, so replay-verify and similar tooling fail loudly on any state-root divergence rather than only on write-set/event/gas/status mismatches.

### Proof of Concept
1. Construct (or simulate) an archived `TransactionInfo` at a checkpoint boundary with a `state_checkpoint_hash` that differs from what the current VM/execution pipeline would produce for the same inputs (e.g., due to a non-deterministic or buggy state-checkpoint hashing change).
2. Run `replay_on_archive`'s `Verifier::verify` over that version range; `execute_and_verify` calls `ensure_match_transaction_info` [8](#0-7) .
3. Observe that verification succeeds (no error returned) despite `state_checkpoint_hash` mismatching, because the comparator omits that check [9](#0-8) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
