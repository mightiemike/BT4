### Title
Exchange rate manipulation via floating-point Bancor formula in TRC10 `Exchange` AMM allows value extraction from the liquidity pool - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
Java-tron's TRC10 `Exchange` feature implements an on-chain Bancor-relay AMM whose price/exchange rate is derived from `firstTokenBalance`/`secondTokenBalance` and computed with `Math.pow`-based floating-point arithmetic in the default (non-hardened) code path. Any unprivileged account can broadcast `ExchangeTransactionContract` transactions to trade against this pool, moving the exchange rate exactly like the KangarooVault `markPrice`, and the double-precision formula produces results that measurably diverge from the exact BigDecimal-based calculation, giving a well-capitalized, patient actor a repeatable rounding edge that drains value from counterparties/pool over many trades — the same "big positions, long enough time" attack shape as the external report.

### Finding Description
The AMM exchange rate lives in `ExchangeCapsule.transaction()`, which selects a `Processor` and applies it to the pool balances: [1](#0-0) 

The default/legacy `Processor` implementation, `ExchangeProcessor`, computes the bancor "relay-token" issuance and redemption using `double` arithmetic and `Maths.pow`: [2](#0-1) 

A second, "hardened" implementation, `SafeExchangeProcessor`, performs the same math with `BigDecimal` for exactness: [3](#0-2) 

The codebase's own test suite proves the two paths diverge for identical inputs — i.e., the legacy double-precision path is provably imprecise relative to the "ground truth" BigDecimal result: [4](#0-3) 

This divergence is driven entirely by `long buyTokenQuant`/`long anotherTokenQuant`, i.e. every trade's output is truncated from a `double`, and which processor is used is chosen by `dynamicStore.allowStrictMath()` and `allowHarden()` — both are governed by on-chain proposal parameters (`allowStrictMath`, `AllowHardenExchangeCalculation`), meaning nodes/chains that have not activated hardening (the default/legacy state, or any private/forked chain based on this code prior to hardening) use the imprecise double-math path for every trade executed through `ExchangeTransactionActuator`: [5](#0-4) 

Because the pool balances (and thus the effective exchange rate) are mutated in-place after every trade and persisted via `Commons.putExchangeCapsule`, any account can repeatedly submit trades sized to exploit the floating-point rounding behavior of `Maths.pow`/`double` truncation in `exchangeToSupply`/`exchangeFromSupply`. Over many transactions and with large enough `sellTokenQuant` (i.e., "big positions for a long enough time," mirroring the external report's requirement), the systematic bias introduced by IEEE-754 double truncation (as opposed to the BigDecimal `RoundingMode.HALF_UP`/`ROUND_DOWN` semantics used in `SafeExchangeProcessor`) can be leveraged to shift value out of the pool balances relative to what exact bancor math would allow, at the expense of other liquidity participants (injectors/withdrawers, whose payout is computed proportionally to `firstTokenBalance`/`secondTokenBalance` in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`).

### Impact Explanation
This maps to "exchange/market math" and "resource and reward accounting" corruption: the manipulated pool ratio directly determines payouts to `ExchangeWithdrawActuator` and `ExchangeInjectActuator` participants (via `firstTokenBalance`/`secondTokenBalance` proportional calculations), so a systematically-biased trade sequence extracts real TRX/TRC10 asset value from other pool participants — an asset/accounting corruption reachable purely from anonymous broadcast transactions, with no privileged role required.

### Likelihood Explanation
Likelihood is low-to-medium, matching the external report's own "Medium" severity determination: exploiting the double-vs-BigDecimal divergence requires (a) operating on a chain/period where hardening is not yet enabled (`allowStrictMath`/`AllowHardenExchangeCalculation` off), (b) sizeable capital to move the pool meaningfully, and (c) many repeated trades over time to accumulate a profitable bias, since each individual trade's rounding delta is small (the test only shows a deterministic *inequality*, not a large drift, between legacy and hardened results). The presence of `SafeExchangeProcessor` and the `allowHarden()`/`allowStrictMath()` governance flags indicates the java-tron team already recognized and partially mitigated float-precision issues in this exact code path, which supports plausibility of the underlying bug class while reducing its current-day exploitability once hardening is activated.

### Recommendation
- Ensure `allowStrictMath` and `AllowHardenExchangeCalculation` are enabled network-wide (verify default/mainnet proposal state) so `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` always route through `SafeExchangeProcessor`'s BigDecimal path instead of `ExchangeProcessor`'s double path.
- Remove or deprecate the legacy `ExchangeProcessor` double-math path entirely once hardening is universally active, eliminating the divergence surface shown by `ExchangeCapsuleTest`/`ExchangeProcessorTest`.
- Add pool-level invariant checks (e.g., constant-product/bancor invariant must not decrease across a trade beyond fee tolerance) in `ExchangeCapsule.transaction()` to reject trades whose net effect would extract value beyond expected precision-loss tolerance.

### Proof of Concept
Not independently reproducible from the index alone (no on-chain state/harness access), but the repository's own test demonstrates the root-cause divergence deterministically: [4](#0-3)  — for every row in `testData`, the non-strict `ExchangeProcessor` result differs from the strict/BigDecimal (`SafeExchangeProcessor`) result on identical `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` inputs, confirming that repeated trades on the legacy path produce outputs inconsistent with the exact bancor formula — the mechanism by which a patient, well-capitalized trader could bias the pool's effective exchange rate over time, analogous to the `markPrice`/`getTokenPrice` drift in the external `KangarooVault` report.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
