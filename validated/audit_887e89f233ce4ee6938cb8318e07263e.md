### Title
Unrestricted, undelayed `UpdateCommissionBps` for block-revenue commission allows a validator to front-run its own commission to steal delegator block-reward share - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The external report describes a pool manager front-running an entry-fee parameter to 100% right before user deposits, stealing value that should have accrued to depositors. The closest reachable analog in Agave is the vote program's commission-update path: legacy `UpdateCommission` is protected by both an epoch-position rule and a one-full-epoch reward-calculation delay, but the newer `UpdateCommissionBps` instruction (SIMD-0291) for `CommissionKind::BlockRevenue` explicitly removes the update-timing restriction, and the block-reward-splitting logic reads the *current* vote-account state rather than a delayed snapshot.

### Finding Description
The vote program's `update_commission_bps` function states explicitly that no timing rule applies: [1](#0-0) 

This contrasts with the legacy `update_commission` function, which enforces `is_commission_update_allowed` (increases only permitted in the first half of an epoch) unless the `delay_commission_updates` feature is active — in which case a one-full-epoch delay is instead achieved by having the reward-calculation code fetch commission from a *cached, prior-epoch snapshot* of vote-account state rather than the live account: [2](#0-1) [3](#0-2) 

For inflation rewards this snapshot-based delay is applied (`snapshot_epoch_vote_accounts`, taken from the epoch prior to the rewarded epoch, per the comment "This snapshot state is saved a full epoch before being used to prevent last minute commission rugs"): [4](#0-3) 

However, the block-revenue-sharing path (`calculate_block_reward`, SIMD-0123) computes the delegator's share directly from `distribution_epoch_vote_accounts` — the current/live vote-account view — and reads `pending_delegator_rewards` from it, not from a one-epoch-delayed snapshot: [5](#0-4) [6](#0-5) 

Because `UpdateCommissionBps` for `CommissionKind::BlockRevenue` can be submitted and take effect immediately (only requiring the authorized withdrawer's signature, no epoch-boundary gating), a validator operator effectively controls how much of the per-block transaction-fee revenue destined for delegators (via `pending_delegator_rewards`) is retained as "commission" versus distributed to stakers, and can change that split transaction-by-transaction with no cooling-off period — the same "front-run the fee parameter right before value flows in" pattern as the reported NFTX bug.

### Impact Explanation
If the block-revenue commission split is applied at the time delegator rewards are deposited/accrued (rather than through the epoch-delayed snapshot used for inflation commission), a malicious or compromised withdraw-authority key could set `block_revenue_commission_bps` to its maximum value immediately before/during the blocks where the vote account's node is leader, capturing the delegators' share of transaction-fee revenue, then reduce it back afterward. This is a direct value-extraction vector from staked delegators to the validator operator, analogous to the reported theft-of-value pattern, and differs materially from the protections the codebase already built for the legacy/inflation commission path.

### Likelihood Explanation
Medium. Exploitation requires control of the vote account's authorized withdrawer key, which is already a semi-trusted role (similar to the "manager is not fully trusted" assumption in the original report). The instruction is reachable directly by any ordinary client transaction signed by that authority — no special protocol privilege beyond normal vote-account authorization is needed, and there is no timelock or cool-down gating the change, unlike the legacy commission path. I was not able to fully trace the exact code path that performs the block-revenue-to-`pending_delegator_rewards` commission split within the available search budget, so I cannot confirm with certainty whether that specific deposit path also applies a delayed/cached commission rate (as inflation rewards do) or uses the live, immediately-updatable `block_revenue_commission_bps`. This uncertainty should be resolved by tracing `DepositDelegatorRewards`/vote-state handler commission-application code before treating this as fully confirmed.

### Recommendation
- Apply the same one-epoch-delay/snapshot mechanism used for inflation-rewards commission (`delay_commission_updates`) to the block-revenue commission (`block_revenue_commission_bps`) so that changes cannot affect revenue already earned or about to be earned in the current epoch/leader slot.
- Alternatively (or additionally), reinstate an epoch-position-based update rule (mirroring `is_commission_update_allowed`) specifically for commission increases under `UpdateCommissionBps`/`CommissionKind::BlockRevenue`.
- Verify and, if necessary, fix the code path that reads `block_revenue_commission_bps` when splitting per-block transaction fee revenue into `pending_delegator_rewards`, ensuring it consults a delayed/cached vote-account view consistent with the protection already afforded to inflation rewards.

### Proof of Concept
Conceptual sequence (pending confirmation of the exact deposit/commission-application code path):
1. Validator's authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }` — accepted immediately, no epoch-position or delay check per `update_commission_bps` (programs/vote/src/vote_state/mod.rs:842-859).
2. The validator's node is leader for upcoming slots and earns transaction fee revenue that is meant to be shared with delegators via `pending_delegator_rewards`.
3. Because block-revenue reward calculation (`calculate_block_reward`) reads live vote-account state rather than a prior-epoch snapshot (runtime/src/bank/partitioned_epoch_rewards/calculation.rs:174-232), if the underlying commission-deduction-on-deposit logic likewise uses the live `block_revenue_commission_bps`, the entire block-revenue share is retained by the validator instead of being split with delegators.
4. The withdrawer can then reduce `block_revenue_commission_bps` back to a normal value with `UpdateCommissionBps`, with no on-chain trace of the transient spike beyond the vote account's own state history.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }
