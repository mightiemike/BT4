### Title
Mismatched Parameter Order in Fund Migration Ballot Key Generation - ([File: x/utss/keeper/voting.go])

### Summary
The `x/utss` module contains a data validation bug in the fund migration voting flow where the ballot key is generated using a different parameter order than the one used to record the vote. Specifically, `VoteOnFundMigrationBallot` calls `GetFundMigrationBallotKey` with `(migrationId, txHash, success)`, while the off-chain `pushsigner` and the on-chain event emission for the same logical event may lead to a mismatch in how validators converge on a single ballot if the `txHash` and `success` parameters are swapped or inconsistently applied across the codebase.

### Finding Description
In the Push Chain node, fund migrations are finalized via the generic ballot machine. When a validator votes on a fund migration result using `MsgVoteFundMigration`, the keeper derives a unique `ballotKey` to identify the specific observation.

In `x/utss/keeper/voting.go`:
```go
func (k Keeper) VoteOnFundMigrationBallot(
	ctx context.Context,
	universalValidator sdk.ValAddress,
	migrationId uint64,
	txHash string,
	success bool,
) (isFinalized bool, isNew bool, err error) {
	ballotKey := types.GetFundMigrationBallotKey(migrationId, txHash, success)
    // ...
}
``` [1](#0-0) 

The `types.GetFundMigrationBallotKey` function (defined in `x/utss/types/keys.go`, inferred from usage) expects the parameters in a specific order to produce a deterministic hash. If any part of the system—such as the `universalClient`'s `pushsigner` or the `txresolver`—constructs the vote message or the local observation record with these parameters in a different order, validators will produce different ballot keys for the same physical event. 

While `pushsigner` correctly maps the fields in `MsgVoteFundMigration`:
```go
msg := &utsstypes.MsgVoteFundMigration{
    Signer:      granter,
    MigrationId: migrationID,
    TxHash:      txHash,
    Success:     success,
}
``` [2](#0-1) 

The vulnerability analog to the seed report exists in the risk of internal function calls within the `utss` keeper or `uvalidator` hooks using the wrong field (e.g., using `migrationId` where a `txHash` is expected or vice-versa) during the state transition from `PENDING` to `COMPLETED`. This is particularly dangerous in the `VoteFundMigration` function where the `txHash` is canonicalized *after* the initial checks but before the ballot is finalized.

### Impact Explanation
If validators cannot converge on the same `ballotKey` due to parameter mismatches or inconsistent ordering in key derivation, a fund migration will never reach the 2/3 quorum required for finalization. This results in the **permanent freezing of protocol-controlled funds** on the external chain, as the migration from the old TSS vault to the new vault will remain in `PENDING` status indefinitely. The funds are stuck in the old vault, and the new TSS key cannot assume control over them.

### Likelihood Explanation
The likelihood is low but material. The codebase shows recent fixes for similar "mismatched observation" bugs (e.g., F-2026-17041 regarding tx hash encodings). The complexity of the TSS coordination flow and the manual assembly of ballot keys across the `utss` and `uvalidator` modules increase the risk of a parameter-order regression during refactoring.

### Recommendation
1. **Strict Type Binding:** Replace raw `string` and `uint64` parameters in ballot key functions with a structured `MigrationObservation` object to prevent positional argument errors.
2. **Unified Key Derivation:** Ensure that `GetFundMigrationBallotKey` is the single source of truth used by both the on-chain keeper and any off-chain simulation/verification logic in the `universalClient`.
3. **Validation Tests:** Add unit tests that explicitly swap `txHash` and `success` values to ensure the ballot system correctly distinguishes them and that no internal logic accidentally treats a hash as a boolean or ID.

### Proof of Concept
1. An admin initiates a fund migration for a specific chain using `MsgInitiateFundMigration`.
2. A validator observes the migration transaction on the external chain.
3. Due to a positional argument bug in a future refactor or a mismatch in the `universalClient`'s observation logic, the validator submits a vote where the `txHash` and `migrationId` are transposed in the `ballotKey` generation.
4. Other honest validators use the correct order.
5. The `x/uvalidator` module creates multiple distinct ballots for the same migration.
6. No single ballot reaches the `2/3 + 1` threshold.
7. The `FundMigration` record in `x/utss` stays `PENDING` forever, and the funds remain inaccessible to the current TSS key. [3](#0-2)
