## Analog Found: Non-Deterministic Wall-Clock Timestamp Validation Causes Signer Disagreement on Block Proposals

### Title
Non-deterministic wall-clock check in `NakamotoBlockProposal::validate` causes signers to disagree on block validity near the timestamp boundary - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
The external report's root cause is a "creation window" check that is evaluated inconsistently because it mixes a deterministic on-chain reference (`block.timestamp`) with wall-clock reads that vary between callers/moments. The same bug class exists in this repo's Nakamoto block-proposal validation: the "block timestamp is too far into the future" check compares the miner-supplied `block.header.timestamp` against each validating node's own `get_epoch_time_secs()` wall-clock read, taken at an arbitrary point during validation, rather than against any value derived deterministically from the burnchain state being validated.

### Finding Description
In `NakamotoBlockProposal::validate`, the two timestamp checks are: [1](#0-0) 

The first check (`self.block.header.timestamp <= parent_nakamoto_header.timestamp`) is deterministic — both sides come from chain data. The second check, however, is:
```
if self.block.header.timestamp > get_epoch_time_secs() + 15 { ... }
```
`get_epoch_time_secs()` reads the local wall clock of whichever node (signer-attached `stacks-node`) is running validation, at whatever instant that node happens to execute this line — which can be delayed by validation stalls, queueing, or fault injection (`fault_injection_validation_delay()` runs just before `validate()` is entered). [2](#0-1) 

Because each of the (independently-operated, potentially clock-skewed) signer nodes calls this same `/v3/block_proposal` endpoint on its own `stacks-node`, and each evaluates `get_epoch_time_secs()` independently at a different wall-clock instant, a block whose `header.timestamp` sits close to the "+15 seconds" boundary can be accepted by nodes that check slightly earlier and rejected by nodes that check slightly later (or whose clock lags/leads). This mirrors exactly the reported bug class: a time-window check implemented against a live/local timestamp rather than a value all validators are guaranteed to compute identically.

### Impact Explanation
This is a minority-triggerable, unprivileged divergence: any miner (no special access needed) can propose a block with `header.timestamp` set to just under the "current time + 15s" boundary. Depending on per-node clock skew and validation-queue delay (both explicitly acknowledged elsewhere in the codebase, e.g. the `tenure_idle_timeout_buffer_secs` comment "Buffer added ... to account for clock skew between signer and miner nodes"), different signers legitimately reach different `InvalidTimestamp` verdicts for the identical block. This is exactly the "validation verdict two nodes disagree on" case called out as an in-scope High-severity impact: it can split signer votes on a given block, causing a temporarily bounded tip/acceptance disagreement between signer sets that would otherwise unanimously accept or reject deterministically.

### Likelihood Explanation
Any miner can trivially construct a borderline-timestamped block to probe or trigger this divergence; no majority collusion or privileged access is required, only crafting the header field, which is fully under the miner's control. Ordinary network jitter and clock skew (already acknowledged as a real operational concern in signer configuration docs) make hitting the boundary plausible without deliberate contrivance, and a malicious miner can do so deterministically by design.

### Recommendation
Replace the wall-clock-relative future check with a deterministic reference (e.g., the burn view's `burn_header_timestamp`, or the sortition tip's timestamp already fetched during `validate()`), or widen/normalize the skew tolerance using a value computed once per burn view and shared consistently rather than re-sampled per validation call. At minimum, capture `get_epoch_time_secs()` once at the very start of `validate()` (tied to `start`/`Instant::now()`) and document/synchronize the acceptable skew window the same way the tenure-idle-timeout buffer already does.

### Proof of Concept
1. Miner crafts a Nakamoto block whose `header.timestamp` is set to `T = now + 15` (the exact edge) and signs it.
2. Miner sends the proposal to two signers' `stacks-node` `/v3/block_proposal` endpoints at nearly the same instant.
3. Due to network latency, validation queueing (see `fault_injection_validation_delay`), or clock skew between the two nodes, node A evaluates `get_epoch_time_secs()` at `T - 1` (block passes: `T <= T-1+15`) while node B evaluates it at `T + 1` (block fails: `T > T+1+15` is false... adjust epsilon appropriately) — the two nodes reach different `InvalidTimestamp` verdicts for the identical block, splitting the signer set's response.
