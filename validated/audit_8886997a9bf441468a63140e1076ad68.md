## Finding: Unauthorized/Unsolicited CEA Execution via Attacker-Controlled Inbound (`isCEA` Path)

The reported `ERC20Rewarder.claim()` bug class — letting any unprivileged caller trigger a state-changing call "on behalf of" a third-party contract, with no check that the contract consented to receive it — has a direct analog in Push Chain's `x/uexecutor` CEA (Cross-chain External Account) execution path.

### Title
Unauthorized/unsolicited `executeUniversalTx` invocation on arbitrary CEA smart contracts via attacker-controlled inbound `isCEA` flag - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/evm.go`)

### Summary
When an inbound is marked `IsCEA=true`, Push Chain's finalization logic resolves the attacker-supplied `Recipient` field, and if that address is a deployed non-UEA smart contract, the `uexecutor` module mints PRC20 tokens to it and force-calls `executeUniversalTx(sourceChain, ceaAddress, payload, amount, prc20AssetAddr, txId)` on it — with `sourceChain`, `ceaAddress` (=inbound `Sender`), and `payload` all derived from a transaction/event that *any* unprivileged external-chain user can produce. There is no mechanism requiring the target contract to opt in per-call, and no cryptographic authorization comparable to the UEA's signature-verified `executeUniversalTx` path.

### Finding Description
For non-`isCEA` inbounds, execution routes to a UEA, and `x/uexecutor/README.md` explicitly documents why `Signer != Owner` is safe: the UEA contract independently verifies a signature over the payload before acting [1](#0-0) .

The `isCEA` path has no equivalent authorization step. `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload` take the raw `Recipient` from the (validator-observed, but attacker-triggered) inbound, check only whether it has EVM bytecode, and if so call it directly: [2](#0-1) 

The actual EVM call is issued by the module account (no user signature at all) against `types.RecipientContractABI`'s `executeUniversalTx(sourceChain, ceaAddress, payload, amount, prc20AssetAddr, txId)`: [3](#0-2) [4](#0-3) 

`sourceChain` and `ceaAddress` (the source-chain sender) are attacker-chosen simply by having an unprivileged EOA send a transaction to the source-chain gateway; UVs faithfully observe and vote on whatever really happened, so these fields are truthful about the *source-chain* event, but nothing ties them to any expectation or authorization from the destination `Recipient` contract. `payload` (the raw `Data` bytes of the `UniversalPayload`) is entirely attacker-controlled and is passed straight through to the target contract's `executeUniversalTx`: [5](#0-4) 

This exactly mirrors the report's bug class: `ERC20Rewarder.claim()` allowed anyone to trigger a claim "on behalf of" an address; here, any unprivileged source-chain actor can trigger `executeUniversalTx` "on behalf of" any deployed contract address they name as `Recipient`, with attacker-chosen `payload`/`ceaAddress`/`amount`, so long as they send a real (even dust-value) transaction to the source-chain gateway.

### Impact Explanation
If a deployed CEA integration does not itself defensively validate `sourceChain`/`ceaAddress`/`payload` (analogous to `VulnerableClaimReceiver` in the report), an attacker can:
- Force PRC20 tokens to be minted into the CEA contract and force it to execute attacker-chosen `payload` bytes, potentially routing/crediting/forwarding funds according to attacker-controlled parameters if the CEA's `executeUniversalTx` implementation trusts `ceaAddress`/`sourceChain`/`payload` without additional binding.
- Cause funds routed by the forced call to become permanently stuck if the CEA contract has no rescue path for calls it never solicited — the same "frozen funds" outcome the report describes, but at the level of any third-party dApp built to receive Push Chain CEA inbounds rather than a single named contract.

This is unauthorized CEA execution reachable purely from unprivileged, ordinary user/attacker action on a source chain — squarely within the "unauthorized UEA or CEA execution" allowed-impact category.

### Likelihood Explanation
Reachable by any external, unprivileged actor at essentially the cost of one source-chain transaction; no validator collusion, admin, or key compromise is required — the honest UV set will faithfully vote and finalize the attacker's real (but adversarially-crafted) inbound event. The severity is bounded by whatever damage a given CEA contract's own `executeUniversalTx` implementation permits when called with untrusted `sourceChain`/`ceaAddress`/`payload`/`amount`, and by the `DeductGasFeesFromReceipt`/`CacheContext` rollback that requires the CEA contract to have UPC balance to pay for the call or the state change is discarded [6](#0-5) , which somewhat limits free-riding but does not address the lack of caller authorization itself.

### Recommendation
Require CEA contracts to explicitly opt in / bind expected callers similar to the UEA's cryptographic model — e.g., a registry of authorized `(sourceChain, ceaAddress)` pairs per CEA recipient, or a mandatory verification hook the target contract must satisfy before `x/uexecutor` will route funds/payload to it — rather than treating "has bytecode" as sufficient authorization to receive arbitrary attacker-driven `executeUniversalTx` calls.

### Proof of Concept
1. Attacker deploys or targets an arbitrary contract `V` on Push Chain (not registered as a UEA) that implements `executeUniversalTx` per `RecipientContractABI` but doesn't validate `sourceChain`/`ceaAddress`/`payload`.
2. Attacker sends a small transaction on any supported source chain to the gateway contract, setting `Recipient = V`, `IsCEA = true`, `TxType = FUNDS_AND_PAYLOAD`, and arbitrary `Data`/payload bytes.
3. Honest UVs observe this real event and vote `MsgVoteInbound`; quorum reached, `ExecuteInboundFundsAndPayload` runs, detects `V` has code, deposits PRC20 into `V`, and calls `V.executeUniversalTx(sourceChain, attackerSenderBytes, attackerPayload, amount, prc20Addr, txId)` — a call `V`'s operator never solicited or authorized. #### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**

		} else {

			_, isUEA, ueaCheckErr := k.CallFactoryGetOriginForUEA(sdkCtx, ueModuleAccAddress, factoryAddress, ueaAddr)
			if ueaCheckErr != nil {
				execErr = fmt.Errorf("failed to verify UEA: %w", ueaCheckErr)
			} else if isUEA {
				// UEA path: deposit PRC20 into the UEA (if amount > 0), then execute payload via UEA
				if inboundAmount.Sign() > 0 {
					receipt, execErr = k.depositPRC20(
						sdkCtx,
						utx.InboundTx.SourceChain,
						utx.InboundTx.AssetAddr,
						ueaAddr,
						utx.InboundTx.Amount,
					)
					if execErr != nil {
						execErr = fmt.Errorf("depositPRC20 failed: %w", execErr)
					}
				}

				// Non-UEA: check if recipient has code (smart contract) vs EOA

					// Smart contract: will call executeUniversalTx after deposit

				}
				// EOA: just deposit, skip executeUniversalTx (no contract to call)

						utx.InboundTx.SourceChain,
						utx.InboundTx.AssetAddr,
						ueaAddr,
						utx.InboundTx.Amount,
					)

						execErr = fmt.Errorf("depositPRC20 failed: %w", execErr)
					}

// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
}
