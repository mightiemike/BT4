## Title
Protocol treasury reward permanently lost when the treasury account is also a validator (`res.insert` overwrite in `RewardCalculator::calculate_reward`) - ([File: chain/epoch-manager/src/reward_calculator.rs])

### Summary
`RewardCalculator::calculate_reward` records the protocol treasury's epoch reward and each validator's epoch reward in the same `HashMap<AccountId, Balance>`. If the `protocol_treasury_account` is also a current-epoch validator, its treasury-share entry is silently overwritten by its validator-share entry instead of being summed. The runtime later credits only the corrupted (smaller) value to the account's `locked` balance, while the total-supply increase (`minted_amount`) still includes the full treasury share. The treasury's rightful reward is permanently lost every such epoch — analogous to the reported `ProtectionPool` bug where `_claimableUnlockedCapital` was assigned (`=`) instead of accumulated (`+=`), silently discarding previously-owed funds.

### Finding Description
In `calculate_reward`, the treasury reward is inserted first: [1](#0-0) 

Then, for every validator in `validator_block_chunk_stats`, the reward map entry is unconditionally overwritten with `res.insert(account_id, reward)`: [2](#0-1) 

If `account_id == self.protocol_treasury_account` (i.e., the treasury account is itself a current-epoch validator), the `res.insert` at line 142 replaces the treasury's `epoch_protocol_treasury` entry with just that validator's `reward`, losing the treasury share from the returned map — exactly the same class of bug as the reported issue, where a later "unlock" overwrote (instead of adding to) a previously unclaimed amount.

Crucially, the second return value, `epoch_actual_reward`, is *not* affected by the overwrite — it is accumulated independently and starts at `epoch_protocol_treasury` before summing every validator's `reward`: [3](#0-2) [4](#0-3) 

This `epoch_actual_reward` becomes `minted_amount`, which is added to `total_supply` at the epoch boundary: [5](#0-4) 

The corrupted `res` map is passed through as `validator_rewards` in `ValidatorAccountsUpdate` and consumed by `update_validator_accounts`, which credits an account's `locked` balance using exactly the (possibly overwritten) map value: [6](#0-5) 

The separate "protocol treasury didn't stake" fallback path only fires when the treasury account is *not* in `stake_info` — i.e., it explicitly assumes that if the treasury account stakes, its reward "was already distributed above," which is false once the overwrite has occurred: [7](#0-6) 

So: `total_supply` is inflated by `epoch_protocol_treasury + Σ(validator rewards)`, but the sum actually credited to any account only reflects `Σ(validator rewards)` (the treasury account's own validator-share substituting for its treasury-share, not adding to it). The treasury's per-epoch share vanishes — it is minted into the reported supply but never lands in any account's balance, i.e., it is permanently and silently lost/frozen.

### Impact Explanation
This breaks the fundamental token invariant: total minted amount must equal the sum of balance increases across all accounts (the "balance checker" invariant documented for the runtime). Every epoch in which the protocol treasury account is also an elected validator, `epoch_protocol_treasury` yoctoNEAR are counted into `total_supply` but credited nowhere, permanently and irrecoverably lost. This is a protocol-level accounting invariant violation with concrete unauthorized value loss (funds that should reach the treasury account disappear), matching the "permanently frozen funds" / state-transition impact criteria.

### Likelihood Explanation
Reachability requires only a single `Stake` action transaction, signed by whoever holds the `protocol_treasury_account` key, requesting enough stake to be elected as a validator in some future epoch — an ordinary transaction available to any account, no special node/validator/network privilege needed. Once elected, the bug triggers automatically and repeatedly (every epoch the account keeps being both a validator and the treasury account) with no additional interaction required. The condition is not exotic: nothing in the protocol code prevents the treasury account from staking.

### Recommendation
Accumulate rather than overwrite the treasury entry when a validator account coincides with `protocol_treasury_account`:
```rust
res.entry(account_id.clone())
    .and_modify(|r| *r = r.checked_add(reward).unwrap())
    .or_insert(reward);
```
instead of the unconditional `res.insert(account_id, reward);` at reward_calculator.rs:142, so the treasury's share is preserved and added to (not replaced by) its validator earnings.

### Proof of Concept
1. Deploy/observe a chain where `protocol_treasury_account` (e.g., `near`) is a normal, controllable account.
2. From `protocol_treasury_account`, submit `Action::Stake` with sufficient stake to be selected as a chunk/block-producing validator (a routine, unprivileged transaction reachable via RPC).
3. Wait for the epoch boundary: `EpochManager` calls `RewardCalculator::calculate_reward` with `validator_block_chunk_stats` now containing `protocol_treasury_account` as a validator entry.
4. In `calculate_reward`: `res.insert(treasury_account, epoch_protocol_treasury)` happens first (line 84); the subsequent loop iteration for `treasury_account` executes `res.insert(treasury_account, reward)` (line 142), discarding `epoch_protocol_treasury`.
5. `epoch_actual_reward` (returned separately, used as `minted_amount`) still equals `epoch_protocol_treasury + Σ(all validator rewards)` — unaffected by the overwrite.
6. `update_validator_accounts` (runtime/runtime/src/lib.rs:1748-1795) credits `treasury_account.locked` using `res[treasury_account]`, which now equals only its validator-share reward, not `epoch_protocol_treasury + validator-share`.
7. Compare `total_supply` delta (includes full `epoch_protocol_treasury`) against the sum of all account balance deltas for that epoch (missing `epoch_protocol_treasury`) — confirming a permanent, unrecoverable loss of the treasury's reward for that epoch.
