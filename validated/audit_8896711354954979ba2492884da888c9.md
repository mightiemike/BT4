### Title
Unauthenticated, network-reachable component RPC servers allow bypass of Gateway transaction validation via direct Mempool `AddTransaction` calls - (File: crates/apollo_infra/src/component_server/remote_component_server.rs)

### Summary
The `RemoteComponentServer` that backs every distributed/hybrid-deployment inter-component RPC endpoint (Mempool, Gateway, Batcher, Committer, State Sync, Class Manager, Sierra Compiler, Signature Manager, L1 providers) accepts and processes any well-formed serialized request from any TCP peer that can reach its port, with no authentication, mTLS, allow-listing, or peer-identity verification. By default it binds to `0.0.0.0` [1](#0-0) , and production distributed/hybrid deployment manifests explicitly configure `bind_ip: 0.0.0.0` for these internal servers [2](#0-1) .

### Finding Description
`RemoteComponentServer::start` binds a TCP listener on `self.config.bind_ip` (default unspecified/`0.0.0.0`) and forwards any incoming HTTP/2 request directly to `remote_component_server_handler`, which deserializes the body into the component's `Request` enum and immediately calls `local_client.send(request).await` — there is no caller authentication, mTLS, shared secret, or network-origin check anywhere in this path [3](#0-2) [4](#0-3) .

In distributed/hybrid deployments, the Mempool component is deployed as its own service with `remote_server_config.bind_ip: 0.0.0.0`, accepting `MempoolRequest` values directly, including `MempoolRequest::AddTransaction(AddTransactionArgsWrapper)` [5](#0-4) [6](#0-5) . Normally, the only path into the Mempool is via `Gateway::add_tx_inner`, which performs stateless validation (`self.stateless_tx_validator.validate(&tx)`), Sierra compilation/class-hash checks for declares, and stateful validation (nonce, fee escalation, `validate` entry-point execution) before ever constructing an `AddTransactionArgsWrapper` and calling `self.mempool_client.add_tx(add_tx_args)` [7](#0-6) .

Because the Mempool's `RemoteComponentServer` performs no access control, any attacker who can reach the Mempool service's bound port — e.g., anyone on the same "adjacent network" (Kubernetes cluster network/VPC/pod network) as described in the referenced NI advisory — can construct an `AddTransactionArgsWrapper` directly and call `MempoolCommunicationWrapper::add_tx`, which only re-checks pool-level invariants (`Mempool::add_tx_validations`: duplicate/nonce/fee-escalation/capacity) and does **not** re-run Gateway's stateless validation, Sierra/class-hash checks, or the stateful `validate` entry-point execution against real chain state [8](#0-7) [9](#0-8) . The attacker fully controls the `AccountState`/nonce fields embedded in `AddTransactionArgs` since the Mempool trusts whatever the caller supplies rather than deriving it from validated on-chain state, allowing injection of transactions that never passed signature/fee/nonce/account-existence checks straight into the pool used for block building, and further gossiped to the mempool-p2p network to other sequencer nodes' Gateways.

### Impact Explanation
This bypasses the entire Gateway validation pipeline (stateless format/signature checks, Sierra-to-CASM compilation and class-hash checks for declares, and stateful nonce/fee/`__validate__` execution) for any transaction injected directly into the mempool. Consequences include: transactions with forged/absent signature validation or against accounts that never ran `__validate__` being staged for block building, potential block-building/execution failures or wasted `blockifier` execution resources when the Batcher later re-executes these unvalidated transactions, and, since `MempoolCommunicationWrapper::add_tx` also gossips accepted transactions to `apollo_mempool_p2p`, propagation of admission-pipeline-bypassing transactions across the network. This is a concrete honest-node divergence / unauthorized mempool admission risk directly reachable by an unprivileged attacker on the adjacent network, without needing an operator, proposer, or staking key.

### Likelihood Explanation
High in any distributed or hybrid deployment topology (the shipped default in `crates/apollo_deployments/resources/services/{distributed,hybrid}/*.json`), since `bind_ip` defaults to `0.0.0.0` unless a deployment operator manually restricts it at the network layer, and the `RemoteComponentServer` code itself contains zero authentication/authorization logic to fall back on if network isolation is imperfect (shared VPC/cluster, misconfigured NetworkPolicy, compromised co-located pod, etc.) — exactly the scenario the referenced NI advisory (adjacent-network reachability of services assumed to be localhost-only) describes.

### Recommendation
Add authentication/authorization to `RemoteComponentServer` (e.g., mTLS with a private CA between known component pairs, or a shared bearer/HMAC token validated in `remote_component_server_handler`) independent of network-layer isolation, so that only the legitimate calling component (e.g., only the Gateway may call Mempool's `AddTransaction`) can invoke sensitive requests. At minimum, apply strict network policies/firewalls as defense-in-depth, but do not rely on them as the sole control given this is exactly the failure mode of the referenced CVE.

### Proof of Concept
1. Deploy the sequencer with a distributed or hybrid topology (e.g., `crates/apollo_deployments/resources/services/hybrid/mempool.json`), where the Mempool's `remote_server_config.bind_ip` is `0.0.0.0` and its port is reachable from the adjacent network/cluster.
2. From another pod/host on the same network (not the legitimate Gateway), craft an HTTP/2 request whose body is a `SerdeWrapper`-serialized `MempoolRequest::AddTransaction(AddTransactionArgsWrapper { args: AddTransactionArgs { tx, account_state }, p2p_message_metadata: None })`, with a forged `InternalRpcTransaction` (e.g., invalid/never-verified signature) and an attacker-chosen `account_state` (nonce) that will pass `Mempool::validate_incoming_tx`.
3. Send this to the Mempool's bound socket with the required `REQUEST_ID_HEADER`; observe that `RemoteComponentServer::remote_component_server_handler` deserializes and forwards it straight to `MempoolCommunicationWrapper::add_tx` → `Mempool::add_tx`, which accepts it without ever invoking Gateway's stateless/stateful/`__validate__` checks, confirming the transaction is admitted to the pool (and subsequently gossiped via mempool-p2p) despite never passing the Gateway validation pipeline described in `docs/diagrams/02-tx-submission-flow.md`.
