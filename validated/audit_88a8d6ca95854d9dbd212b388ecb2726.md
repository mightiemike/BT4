## Title
Replay/state-sync verification silently ignores the authenticated position/hot-state checkpoint hashes when applying `TransactionOutputByHash` chunks - (`types/src/transaction/mod.rs`, `TransactionOutput::ensure_match_transaction_info`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to verify that a locally-executed (or locally-recomputed) `TransactionOutput` matches the authenticated `TransactionInfo` that was signed by validators / fetched with a proof, before the output is committed via chunk execution, replay, or replay-verify tooling.

## Finding Description
The function checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash against the target `TransactionInfo`, but its own inline comment admits it does not check the checkpoint-hash fields that `TransactionInfoV1` carries: the main state checkpoint hash comparison exists elsewhere, but the hot-state checkpoint hash and, critically, `position_state_checkpoint_hash` (the native-position/trading state root) are explicitly excluded from the comparator: [1](#0-0) 

This function is invoked from the chunk executor's commit/replay path (`execution/executor/src/chunk_executor/mod.rs`), from `storage/db-tool/src/replay_on_archive.rs` (replay-verify tooling), from `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and from `aptos-move/cli/src/commands.rs`. These are exactly the code paths that are supposed to guarantee that a node applying a chunk of transactions (during fast sync, chunk replay, or backup/restore verification) produces the same ledger state as the one attested to by the authenticated `TransactionInfo`/ledger-info-with-signatures.

`position_state_checkpoint_hash` is populated by `DoStateCheckpoint::compute_position_checkpoint` and threaded into `TransactionInfoV1` in `DoLedgerUpdate::assemble_transaction_infos` when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled: [2](#0-1) 

Because that hash is meant to be "consensus-verified" per its own doc comment (`COMPUTE_TRADING_NATIVE_STATE_ROOTS` — "so it is consensus-verified. Requires TRANSACTION_INFO_V1"), any path relying on `ensure_match_transaction_info` to validate re-executed/replayed output against the authenticated `TransactionInfo` will not detect a divergence in the native-position (trading) state root, nor in the hot-state root, even though both are carried inside the cryptographically-committed `TransactionInfo` that the accumulator/ledger-info signs over.

## Impact Explanation
If the local position-state (or hot-state) computation diverges from the authenticated value — due to a bug in `compute_position_checkpoint`, a schema/version mismatch during restore, or a non-determinism in the position Merkle extension logic — replay-verify tooling (`replay_on_archive`) and the chunk executor's own commit-time sanity check would both report success while committing/accepting a `TransactionOutput` whose durable position/trading state actually differs from the validator-attested root. This is precisely the "authenticated proof-bearing output bound to the wrong root" class of bug: the node would persist a ledger that is provably wrong relative to its own signed `TransactionInfo`, yet no local consistency check surfaces it. Under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, an incorrect position state could then be served to clients/queries as if authenticated, and used as the basis for subsequent state transitions (native trading commits build directly off `position_state_summary`), silently corrupting durable ledger data.

## Likelihood Explanation
This is gated by feature flags (`TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that are not yet enabled on mainnet based on the surrounding comments ("this is currently None in testnet and mainnet"). I could not verify from the indexed code whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is active on any live network, nor could I fully trace every call site of `ensure_match_transaction_info` to determine whether an independent/redundant checkpoint-hash comparison exists elsewhere in the chunk-commit pipeline (the tool budget was exhausted before I could inspect `chunk_result_verifier.rs` and the full body of `chunk_executor/mod.rs`). This gap is also self-documented in the code as a known TODO ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), which suggests the maintainers are aware it must be fixed before the feature ships, reducing (but not eliminating) the likelihood of present-day exploitability.

## Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionInfo` variant) against locally computed values, and ensure the check runs before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and `HOT_STATE_ROOT_IN_TXN_INFO`) are enabled on any network, per the existing inline TODO.

## Proof of Concept
Not independently reproducible from the indexed code alone: exploitation requires (1) `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` enabled and (2) an actual local/remote divergence in position or hot-state computation (e.g., from a restore-path bug) to demonstrate the missing check fails to catch it. I was not able to execute code or confirm current mainnet feature-flag state to construct a concrete end-to-end PoC given the available tools; this should be verified by a Devin session with full repo/build access before treating it as confirmed-exploitable.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
