### Title
Malformed/incorrect hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` in the Wallet Contract causes silent, unrefunded loss of caller deposits - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (deployed as the global contract backing every ETH-implicit account on NEAR, per NEP-518) hardcodes the account ID of its "Address Registrar" dependency at compile time via `const ADDRESS_REGISTRAR_ACCOUNT_ID: &str = std::include_str!("ADDRESS_REGISTRAR_ACCOUNT_ID")` [3](#0-2) , exactly analogous to the reported `DAIEthOracle` constant that was pinned to an incorrect on-chain address/interface. If this baked-in constant is wrong, unparseable, or points at an account that does not implement the expected `lookup` method (a class of bug indistinguishable in kind from the reported oracle-address mismatch — a fixed dependency address baked into contract logic that silently diverges from the intended live contract), every cross-contract call it drives will fail, and the code path that handles that failure does not perform the deposit refund that the analogous failure path elsewhere in the same contract performs.

### Finding Description
`inner_rlp_execute` parses `ADDRESS_REGISTRAR_ACCOUNT_ID` and issues a cross-contract call to it whenever an `EOABaseTokenTransfer` carries an `address_check` (i.e., whenever the relayer directs a native-token transfer to a raw ETH address rather than a named account) [4](#0-3) . The `caller_deposit` (tracking the external, non-owner caller's attached deposit, explicitly meant "to refund the caller's deposit if the cross-contract call fails" per its own doc comment) is threaded through to `address_check_callback` [5](#0-4) .

However, in `address_check_callback`, the `PromiseResult::Failed` branch — which is exactly the branch that fires when the hardcoded registrar account is wrong (nonexistent, wrong interface, or panics) — simply returns an error `ExecuteResponse` without ever creating a refund promise for `caller_deposit`: [6](#0-5) 

This is inconsistent with the otherwise-analogous failure branch in `rlp_execute_callback`, which does refund `caller_deposit` on `PromiseResult::Failed`: [2](#0-1) 

Because `rlp_execute` is `#[payable]`, any NEAR deposit attached by an external (non-owner) relayer/caller to the transaction is credited to the Wallet Contract's own account balance the moment the receipt executes, independent of what the function later returns; only an explicit `Promise::transfer` back to the caller returns it. Since `address_check_callback`'s failure path issues no such promise, that deposit is retained by the ETH-implicit account instead of being returned to the caller who supplied it.

### Impact Explanation
If the compiled-in `ADDRESS_REGISTRAR_ACCOUNT_ID` is incorrect for a given network deployment (wrong account, unparseable string, or an account that lacks/changes its `lookup` interface — the same class of defect as the reported `DAIEthOracle` address mismatch), then every `EOABaseTokenTransfer` with a non-null `address_check` will unconditionally hit the `PromiseResult::Failed` branch of `address_check_callback`. Any external, non-owner caller who attaches a NEAR deposit while relaying such a transaction has that deposit unrefunded and effectively appropriated by the Wallet Contract, deviating from the caller-refund invariant the contract documents and implements everywhere else on this same call path. This is a concrete unauthorized value movement: value contributed by one account (the caller/relayer) is retained by another (the eth-implicit wallet account) contrary to the contract's designed and tested behavior (see `test_caller_refunds`, which asserts refunds occur when cross-contract calls fail) [7](#0-6) .

### Likelihood Explanation
This is a global, single-deployment contract used by every ETH-implicit account on the network (compiled once, referenced by hash) [8](#0-7) , so a single incorrect `ADDRESS_REGISTRAR_ACCOUNT_ID` value baked in at build/release time (the exact analog of the reported hardcoded, mismatched oracle address) would deterministically and repeatedly manifest for every relayer forwarding an address-checked base-token transfer, requiring no special privilege beyond acting as an ordinary external caller/relayer with a deposit.

### Recommendation
In `address_check_callback`, mirror the refund logic already present in `rlp_execute_callback`: on `PromiseResult::Failed`, issue a `Promise::transfer` of `caller_deposit` back to its `account_id` before returning the failure `ExecuteResponse`. Additionally, treat a misconfigured/unresolvable `ADDRESS_REGISTRAR_ACCOUNT_ID` as a release-blocking configuration check (e.g., verified in CI against the deployed registrar's interface) rather than only a runtime `env::panic_str` on unparseable strings, since a *parseable-but-wrong* account ID is not otherwise detected.

### Proof of Concept
1. Deploy the Wallet Contract with `ADDRESS_REGISTRAR_ACCOUNT_ID` pointing at an account that either does not exist or does not implement `lookup` (mirroring the reported scenario of a hardcoded address lacking the expected `quoteSpecificPoolsWithTimePeriod` method).
2. An external relayer (not the wallet owner) submits `rlp_execute` with a signed Ethereum transaction that is a base-token transfer to a raw address (`EOABaseTokenTransfer` with `address_check: Some(address)`), attaching a NEAR deposit as `caller_deposit`, per the flow in `inner_rlp_execute` [4](#0-3) .
3. The cross-contract call to the address registrar fails (account doesn't exist / wrong method), triggering `PromiseResult::Failed` in `address_check_callback`.
4. `address_check_callback` returns `ExecuteResponse { success: false, ... }` without creating any refund promise [6](#0-5) .
5. The relayer's attached deposit remains in the eth-implicit account's balance and is never returned, contrary to the documented/tested caller-refund guarantee.

async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;

    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };
