### Title
Unbounded outbound fan-out from a single low-cost payload forces disproportionate TSS-signing and validator-voting cost onto Universal Validators - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
The claimer-fee bug's core pattern is: an attacker cheaply creates many entries in a shared array that a different, honest party is then forced to pay a disproportionate flat cost to process. In Push Chain, `BuildOutboundsFromReceipt` scans **every log** in a single EVM receipt for `UniversalTxOutbound` events emitted by `UNIVERSAL_GATEWAY_PC`, and appends one `OutboundTx` entry per matching log to the same `UniversalTx.OutboundTx` array with no cap on count. [1](#0-0) 

### Finding Description
`MsgExecutePayload` is a gasless, permissionless message — "any account may submit the message," and the payload itself is executed as a real EVM call against the UEA with an attacker-controlled `gasLimit` (up to whatever the payload signer chooses to spend from their own UEA balance). [2](#0-1) 

When the resulting EVM receipt is processed, `BuildOutboundsFromReceipt` iterates all logs and converts every `UniversalTxOutbound` event into a new `OutboundTx`, which is then appended to the UTX's `OutboundTx` slice and separately indexed into `PendingOutbounds` inside `attachOutboundsToUtx`: [3](#0-2) 

There is no limit in this code path on the number of `UniversalTxOutbound` events a single payload's contract call can emit (a contract can loop and call the gateway's withdraw entry point repeatedly within one gas-metered call, each emitting a fresh event with a trivial/zero-value amount). Because gas is a Push-Chain-native (EVM) resource and TSS signing/broadcast is an entirely separate, expensive off-chain resource, the cost asymmetry is severe: cheap Push Chain EVM gas paid once by the attacker translates into N independent outbound records that Universal Validators must each: (a) sign via a full TSS ceremony, (b) broadcast to the destination chain, and (c) vote back via `MsgVoteOutbound`. Every one of those `MsgVoteOutbound` calls does a linear O(n) scan over the same growing `utx.OutboundTx` array to find the matching entry by ID: [4](#0-3) 

This mirrors the claimer-fee bug precisely: the attacker (payload submitter) pays a small, fixed EVM-gas cost, while the party that must "process the array" — here, the Universal Validator set doing TSS signing and per-entry voting, plus every future reader that scans `utx.OutboundTx` (e.g. `computeUniversalStatus`, rescue-outbound duplicate checks) — bears a cost that scales linearly (or worse, given TSS ceremony overhead) with the number of entries the attacker chose to create. [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a denial-of-service / resource-exhaustion vector reachable by an ordinary, unprivileged user through the default `MsgExecutePayload` submission path (no privileged role required), consistent with the in-scope "denial of service...reachable without privileged control" category. A single crafted payload can force the Universal Validator set into an unbounded number of TSS signing ceremonies and gasless votes, and grow a single `UniversalTx.OutboundTx` slice without bound, degrading UV throughput and inflating the cost/latency of finalizing legitimate outbounds sharing validator capacity. It does not directly steal funds, but it materially degrades the crosschain execution layer's liveness/availability, which is explicitly an allowed impact category ("denial of service... reachable without privileged control").

### Likelihood Explanation
Reaching this requires only: (1) funding a UEA cheaply, (2) deploying/using a contract that calls the `UniversalGatewayPC` withdraw entry point in a loop within a single `executeUniversalTx` call, each with a minimal/zero-value amount. No validator or admin cooperation is needed. The main uncertainty (not resolved by the available index) is the exact per-call EVM gas limit ceiling enforced elsewhere (e.g. block gas limit or feemarket params) and whether the `UniversalGatewayPC` Solidity contract enforces any per-call cap on withdraw/outbound events — no such cap was found in `x/uexecutor`, `x/uregistry`, or `x/utss` Go code, but the contract itself lives in a separate `push-chain-core-contracts` repo not indexed here, so a Solidity-side per-call limit cannot be ruled out.

### Recommendation
Enforce a maximum number of outbound events processed/attached per receipt in `BuildOutboundsFromReceipt` (reject or truncate with an error beyond a sane threshold, e.g. matching the report's "minimum purchase amount" remediation, but adapted as a "maximum outbound fan-out per payload execution"). Additionally, replace the O(n) linear scan in `VoteOutbound` (and any other lookups by `outbound.Id` within `UniversalTx.OutboundTx`) with a keyed index rather than iterating the append-only slice, so that per-vote cost does not scale with attacker-controlled fan-out.

### Proof of Concept
Cannot be fully constructed from the indexed Go repository alone because the attacker-facing trigger (looping withdraw calls inside a single `executeUniversalTx`) lives in the `UniversalGatewayPC` Solidity contract in the separate `push-chain-core-contracts` repository, which is out of the indexed scope here. The chain-side mechanics substantiating the vulnerability (no per-receipt cap on outbound creation, unbounded append to `UniversalTx.OutboundTx`, and O(n) lookup cost paid by validators on every vote) are directly shown in the cited `create_outbound.go` and `msg_vote_outbound.go` code above.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

// computeUniversalStatus derives a UniversalTxStatus from the actual state of the
// UTX's components instead of reading a stored field that can go stale.
//
// Priority: outbounds > PC txs > inbound presence.
func computeUniversalStatus(utx *types.UniversalTx) types.UniversalTxStatus {
	if len(utx.OutboundTx) > 0 {
		anyPending := false
		anyReverted := false
		for _, ob := range utx.OutboundTx {
			if ob == nil {
				continue
			}
			switch ob.OutboundStatus {
			case types.Status_PENDING:
				anyPending = true
			case types.Status_REVERTED:
				anyReverted = true
			}
		}
		if anyPending {
			return types.UniversalTxStatus_OUTBOUND_PENDING
		}
		if anyReverted {
			return types.UniversalTxStatus_OUTBOUND_FAILED
		}
		return types.UniversalTxStatus_OUTBOUND_SUCCESS
	}
