## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting corrupted state/hot-state/position state roots pass replay and chunk-execution verification - (File: `types/src/transaction/mod.rs`)

### Summary
The external report's bug class is a validation/binding function that is supposed to tie two values together but silently drops part of the binding, letting mismatched data pass as valid. The Aptos-native analog is `TransactionOutput::ensure_match_transaction_info`, the function used across replay/verification code paths to assert that a locally re-executed `TransactionOutput` matches the chain-authenticated `TransactionInfo` for a version. It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function verifies status, gas used, write-set hash, and event root hash against the `TransactionInfo`, but the code contains a self-documented gap: [2](#0-1) 

The comment states verbatim that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", so tooling built on top of it "can report a successful replay even when the authenticated position state root diverges from local execution." This is exactly the analog of the external report's pattern: a function meant to bind/validate two related values (`TransactionOutput` vs. authenticated `TransactionInfo`) that overwrites/ignores part of the expected binding (the checkpoint-hash fields), so state that should be rejected as inconsistent is instead accepted.

This function is called from state-integrity-relevant call sites: [3](#0-2) 
- `execution/executor/src/chunk_executor/mod.rs` — chunk executor commit/replay path
- `storage/db-tool/src/replay_on_archive.rs` — replay-verify tooling
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` — debugging/CLI replay tools

### Impact Explanation
If the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` computed by local re-execution diverges from the value carried in the chain-authenticated `TransactionInfo`, `ensure_match_transaction_info` will not detect it. Any component relying on this function as its authoritative state-consistency check (chunk executor replay verification, `replay_on_archive`, debugger tooling) would treat a state root divergence as a passing replay, i.e., an authenticated response is accepted while bound to the wrong state root/proof context for that version — directly matching the "authenticated API or state-view output bound to the wrong version/object/proof" and "hard-fork-only divergence during commit/replay/restore" categories in the integrity gate.

### Likelihood Explanation
The gap is currently gated by design: it is documented as a known limitation to be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [4](#0-3) , and that feature flag governs whether position/trading-native state roots are computed at all [5](#0-4) . I was not able to fully confirm within the available tool budget whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is already active on mainnet or whether `chunk_executor`'s call to `ensure_match_transaction_info` is reachable on the primary consensus-commit path versus only in offline replay/debug tooling — this would materially change the severity assessment and should be checked before acting on this finding.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed output and the authenticated `TransactionInfo` (when both sides have these fields populated), matching the pattern already used for `write_set_hash` and `event_root_hash`, before any code path that gates commit/replay success on this comparator is relied upon for the trading-native/position-state feature.

### Proof of Concept
Not applicable as a runnable exploit — this is a self-documented code-review finding: the comment block at [4](#0-3)  is the developers' own acknowledgment that a `TransactionOutput` whose position/hot-state checkpoint hash differs from the authenticated `TransactionInfo` will pass `ensure_match_transaction_info` unmodified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
