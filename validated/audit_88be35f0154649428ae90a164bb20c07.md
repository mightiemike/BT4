### Title
Unimplemented `get_compiled_class_hash` (`todo!()`) in gateway's `SyncStateReader` causes runtime panic on stateful transaction validation - (File: `crates/apollo_gateway/src/sync_state_reader.rs`)

### Summary
`SyncStateReader`, the `StateReader` implementation used by the sequencer's gateway to perform stateful validation of every incoming transaction, has an unimplemented `get_compiled_class_hash` method that panics with `todo!()` instead of returning a value. [1](#0-0) 

### Finding Description
`SyncStateReader` implements the `BlockifierStateReader` trait for the gateway, backing every submitted transaction's stateful validation via `StateReaderFactory::get_blockifier_state_reader_and_gateway_fixed_block_from_latest_block`, which is invoked once per incoming transaction. [2](#0-1) 

All other `StateReader` methods on `SyncStateReader` (`get_storage_at`, `get_nonce_at`, `get_class_hash_at`, `get_compiled_class`) are fully implemented, and delegate to the state-sync/class-manager clients, but `get_compiled_class_hash` is left as `todo!()`:
```rust
fn get_compiled_class_hash(&self, _class_hash: ClassHash) -> StateResult<CompiledClassHash> {
    todo!()
}
``` [1](#0-0) 

This is exposed transitively through the `SyncOrGenesisStateReader` wrapper used by the gateway's public `StateReaderFactory`, which forwards `get_compiled_class_hash` calls straight to the underlying `SyncStateReader`: [3](#0-2) 

`StateReader::get_compiled_class_hash` is a core trait method invoked from `CachedState` (used for buffering reads/writes during a transaction's execution/validation) any time a compiled class hash needs to be read from the underlying state: [4](#0-3) 

Because the gateway relies on this exact state reader chain for every submitted transaction's stateful validation, any transaction path that triggers a compiled-class-hash lookup (e.g., re-declare/duplicate-class checks or class-hash bookkeeping tied to `Declare` transactions) will hit the `todo!()` branch and panic the handling thread — this is directly analogous to the reported `force_unreserve` bug class: an interface reachable by an ordinary, unprivileged transaction sender is left unimplemented (`todo!()`/`unimplemented!()`), and invoking it crashes the node instead of returning a graceful error.

I was not able to fully trace, within the remaining tool budget, the exact call site inside the gateway's stateful validation flow that first triggers `get_compiled_class_hash` for a given transaction (e.g., whether it is unconditionally hit for every `Declare` transaction, or only in a specific sub-path). This should be verified by a background agent by tracing gateway "stateful validation" call graph from `GatewayStateReaderWithCompiledClasses`/`StateReaderFactory` usage down into `blockifier`'s transaction validation/execution code to confirm exactly which submitted transaction type(s) reach `StateReader::get_compiled_class_hash`.

### Impact Explanation
If reachable, an attacker can submit a normal transaction (no special privileges needed — a `Declare`, or any transaction causing a compiled-class-hash state read) that panics the gateway process handling stateful validation. This is a denial-of-service on the transaction-validation path of the sequencer: the affected process/thread crashes, and if this crash propagates to the validation service the sequencer becomes unable to accept/validate new transactions, matching the "network unable to confirm new transactions" impact category.

### Likelihood Explanation
`High`. No adversarial timing or privileged position is required — any user submitting an ordinary transaction that triggers a compiled-class-hash state read exercises the `todo!()` panic. The difficulty is only in identifying the precise transaction shape/type that forces this code path, which requires further tracing.

### Recommendation
- Short term: implement `SyncStateReader::get_compiled_class_hash` to actually query the state-sync/class-manager clients (mirroring the pattern used by `get_class_hash_at`/`get_nonce_at`, which gracefully default to `ClassHash::default()`/`Nonce::default()` on `ContractNotFound`) instead of `todo!()`. At minimum, replace the panic with a proper `StateError` so any caller receives a graceful error instead of crashing the process.
- Long term: audit all `StateReader`/`FetchCompiledClasses` trait implementations reachable from gateway/mempool/block-building code paths for remaining `todo!()`/`unimplemented!()` stubs, and add a lint/CI check (or exhaustive trait-implementation test) to prevent unimplemented methods from being reachable in production code paths triggered by untrusted input.

    fn get_compiled_class_hash(&self, class_hash: ClassHash) -> StateResult<CompiledClassHash> {
        let mut cache = self.cache.borrow_mut();

        if cache.get_compiled_class_hash(class_hash).is_none() {
            let compiled_class_hash = self.state.get_compiled_class_hash(class_hash)?;
            cache.set_compiled_class_hash_initial_value(class_hash, compiled_class_hash);
        }

        let compiled_class_hash = cache
            .get_compiled_class_hash(class_hash)
            .unwrap_or_else(|| panic!("Cannot retrieve '{class_hash:?}' from the cache."));
        Ok(*compiled_class_hash)
    }
