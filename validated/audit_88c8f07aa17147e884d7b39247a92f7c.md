### Title
Hardcoded 7/8 HashMap load-factor assumption in accounts-index threshold sizing diverges from hashbrown's actual capacity formula for small bins - ([File: accounts-db/src/accounts_index/bucket_map_holder.rs])

### Summary
`BucketMapHolder::calculate_target_entries_per_bin` computes the in-memory accounts-index eviction watermarks (`high_water_mark`, `low_water_mark`) for `IndexLimit::Threshold` mode by assuming the backing `HashMap` always reallocates once it is 7/8 full: [1](#0-0) 

This 7/8 constant is then used to derive the memory-bound thresholds that gate flush/eviction from the in-memory index: [2](#0-1) 

### Finding Description
The comment justifying the constant states: "HashMap capacities grow in powers of 2 and typically trigger a reallocation when ~7/8 full," and the code applies `(1usize << entries_per_bin_log2) * 7 / 8` unconditionally to derive `target_entries_per_bin`, from which `high_water_mark` and `low_water_mark` are subtracted using `DEFAULT_NUM_ENTRIES_OVERHEAD`/`DEFAULT_NUM_ENTRIES_TO_EVICT` (or configured values): [3](#0-2) 

This 7/8 figure is only accurate for hashbrown's internal capacity formula when the raw bucket count is ≥ 8; hashbrown special-cases smaller tables to allow full (not 7/8) occupancy before growing. The codebase's own test acknowledges the 7/8 number is an *approximation* tied to a specific table size ("Fill the bin's hashmap exactly to hashbrown's max_load (7/8 of 256 buckets)"): [4](#0-3) 

Because `calculate_target_entries_per_bin` applies this single constant uniformly to whatever `entries_per_bin` a given memory-limit/bin-count configuration produces, the computed target/high/low watermarks are only self-consistent with hashbrown's real behavior in the size regime the test happens to cover; the derived thresholds are not proven correct across the general range of `bins`/`num_bytes` values administrators can pass via `AccountsIndexConfig`/`IndexLimit::Threshold`. This is exactly the "precision/tolerance constant not matching the underlying formal model" bug class from the report (a hardcoded fractional constant used for a threshold calculation, asserted correct without being derived from the actual invariant it's approximating).

### Impact Explanation
`check_flush_trigger` and `max_evictions_for_threshold` rely directly on these watermarks to decide when to evict entries from the in-memory accounts index and how many to evict: [5](#0-4) [6](#0-5) 

If the 7/8 assumption doesn't hold for the actual per-bin table size in use, `high_water_mark`/`low_water_mark` will not line up with when hashbrown truly grows/shrinks capacity. This can cause either: (a) premature/needless eviction and disk write-through cycles well before the in-memory hashmap would actually reallocate (wasted CPU/IO — `reallocate_to_clear_tombstones` triggers a full rehash each time), or (b) allowing the table to grow beyond the intended memory budget before eviction kicks in, silently exceeding the operator-configured `--accounts-index-memory-limit-mb`-style threshold. Both fall into the "disproportionate storage and CPU cost" impact category.

### Likelihood Explanation
This code path only activates for `IndexLimit::Threshold` configurations (memory-bounded accounts index), which is an opt-in, non-default configuration for validators bounding accounts-index memory. The mismatch is deterministic (not attacker-triggered) and depends purely on the chosen `bins`/`num_bytes` combination producing a per-bin `entries_per_bin` size where hashbrown's small-table behavior differs from the assumed 7/8 factor.

### Recommendation
Either derive `target_entries_per_bin` from the actual `HashMap::capacity()` behavior at insertion time (as already done reactively in `reallocate_to_clear_tombstones`/`check_flush_trigger`), rather than pre-computing a fixed 7/8 factor from a bare bit-shift, or clamp/validate that `entries_per_bin` values fall within the range where the 7/8 approximation is accurate, and add an explicit test asserting the formula matches `HashMap::with_capacity(entries_per_bin).capacity()` for the range of `bins`/`num_bytes` combinations supported by `AccountsIndexConfig`.

### Proof of Concept
Not applicable as a runtime exploit — this is a constant/formula-precision defect. It can be demonstrated by computing `calculate_target_entries_per_bin(n)` for small `n` (e.g., `n` such that `entries_per_bin_log2` yields a raw bucket count < 8) and comparing against `std::collections::HashMap::<Pubkey, AccountMapEntry>::with_capacity(n).capacity()`; the two values diverge outside the specific 256-bucket case exercised by the existing unit test at [7](#0-6) .

Note: I could not locate a CLI/whitepaper-level document in this index that states an explicit guaranteed byte/entry precision for `IndexLimit::Threshold`, so I cannot claim this contradicts a formally documented spec value the way the original report contradicts the Allora whitepaper — it is presented as an internal formula/self-consistency defect (hardcoded approximation vs. actual `hashbrown` capacity behavior) rather than a doc-vs-code mismatch.

/// The number of entries below an in-mem index bin's usable capacity at which to begin evicting.
///
/// This number should be *at least* the worst case rate that entries are added to the in-mem
/// index per bin.  This ensures we start evicting early enough so that we do not exceed the
/// configured index threshold limit.
///
/// At the same time, we want this value to be as small as possible.  The smaller this value, the
/// higher the utilization of the in-mem index bins.
///
/// This value is used to compute the high watermark.
pub const DEFAULT_NUM_ENTRIES_OVERHEAD: usize = 5_000;

/// The number of entries to evict, once we've hit the high watermark.
///
/// We want this number to be small, similar to `NUM_ENTRIES_OVERHEAD`, to keep utilization high.
/// It also must be large enough to ensure once an eviction is triggered that scanning + flushing +
/// evicting completes before the high watermark is crossed again.
/// We also want to avoid/ammortize scanning the bins for flush/evict, so a larger number helps
/// with that goal.
///
/// This value is used to compute the low watermark.
pub const DEFAULT_NUM_ENTRIES_TO_EVICT: usize = 10_000;

    pub fn max_evictions_for_threshold(&self, current_entries: usize) -> NonZeroUsize {
        let evictions = match &self.threshold_entries_per_bin {
            None => current_entries,
            Some(threshold_entries_per_bin) => {
                // Low water mark: evict down to specified ratio of the per-bin threshold
                current_entries.saturating_sub(threshold_entries_per_bin.low_water_mark)
            }
        }
        .max(1);
        // SAFETY: evictions is ensured to be non-zero above.
        NonZeroUsize::new(evictions).unwrap()
    }

    fn calculate_target_entries_per_bin(entries_per_bin: usize) -> usize {
        if entries_per_bin == 0 {
            0
        } else {
            // HashMap capacities grow in powers of 2 and typically trigger a reallocation
            // when ~7/8 full. Derive the target as the highest power-of-two capacity that
            // fits within entries_per_bin, then apply the 7/8 factor to stay below the
            // reallocation threshold.
            let entries_per_bin_log2 = entries_per_bin.ilog2();
            (1usize << entries_per_bin_log2) * 7 / 8
        }
    }
