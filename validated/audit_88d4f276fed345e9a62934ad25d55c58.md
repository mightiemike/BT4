### Title
Prometheus Metrics HTTP Server Bound to All Interfaces Exposes Internal Node Diagnostics - (File: common/src/main/java/org/tron/common/prometheus/Metrics.java)

### Summary
When `node.metrics.prometheus.enable` is set to `true`, java-tron starts a `io.prometheus.client.exporter.HTTPServer` bound only by port, with no interface restriction, analogous to the reported Spacemesh `pprof` issue where a diagnostic HTTP server was started on `:6060` (all interfaces) instead of `localhost:6060`.

### Finding Description
`Metrics.init()` starts the exporter with `new HTTPServer.Builder().withPort(port).build()`, never calling `withInetAddress(...)`. The underlying `io.prometheus.client.exporter.HTTPServer` defaults to binding the wildcard address (`0.0.0.0`) when no address is supplied, so the metrics endpoint listens on every network interface of the host, not just `localhost`. [1](#0-0) 

This is the same bug class as the referenced report: a debugging/diagnostics HTTP server (pprof there, Prometheus `/metrics` here) started without restricting the bind address to loopback, making it reachable by any client that can route to the node's IP on that port. The default port is `9527` and is user-configurable via `node.metrics.prometheus.port`, but the enable/port config does not offer a bind-address option at all. [2](#0-1) [3](#0-2) 

Unlike java-tron's HTTP API servlets (e.g., `FullNodeHttpApiService`), which run through Jetty with `HttpInterceptor`/`HttpApiAccessFilter` and are covered by the `rate.limiter` configuration in `reference.conf`, the Prometheus exporter is a separate, independent HTTP server with no rate limiting, authentication, or IP allow-listing. [4](#0-3) [5](#0-4) 

The endpoint exposes JVM/hotspot internals (`jvm_memory_bytes_*`, GC stats, thread info), OS-level data (`system_total_physical_memory_bytes`, CPU/load info), Guava cache statistics, DB size/level metrics, error counters by topic/type, and detailed per-endpoint HTTP/gRPC/JSON-RPC latency and traffic metrics. [6](#0-5) 

### Impact Explanation
Exposing this data publicly leaks operational and performance telemetry about the node — memory/CPU utilization, error rates by API endpoint, DB engine and size, and per-witness/per-miner block production statistics — which an attacker can use for reconnaissance: identifying under-resourced or lagging nodes to target for timing/DoS attacks, correlating error spikes with exploit attempts, or fingerprinting node configuration (storage engine, cache sizes) to plan further attacks. This matches the "Information Leakage" bug class from the external report (BVSS impact C:H/I:H).

### Likelihood Explanation
Any operator who enables `node.metrics.prometheus.enable = true` (a documented, supported feature intended for monitoring integration, e.g. Grafana dashboards referenced in `METRICS_CHANGELOG.md`) will have this port open on all interfaces unless they separately firewall it, because the code offers no way to bind to `localhost` only. This is a straightforward, unprivileged misconfiguration risk reachable by any anonymous network client that can reach the configured port, with no authentication required — directly analogous to the confirmed-and-fixed Spacemesh pprof issue.

### Recommendation
Add a configurable bind address (default `127.0.0.1`) to `MetricsConfig.PrometheusConfig`, and use `HTTPServer.Builder().withInetAddress(InetAddress.getByName(bindAddress)).withPort(port).build()` in `Metrics.init()` so operators must explicitly opt in to exposing the endpoint beyond localhost. Document the security implication in `reference.conf` next to `node.metrics.prometheus`, similar to the existing `allowShieldedTransactionApi` warning about private-key exposure.

### Proof of Concept
1. Set `node.metrics.prometheus.enable = true` in config with default `port = 9527` and start the node. [7](#0-6) 
2. `Metrics.init()` runs `new HTTPServer.Builder().withPort(port).build()` without specifying an address, so the Prometheus client library binds the socket to `0.0.0.0:9527`. [8](#0-7) 
3. From any host that can route to the node's public/external IP, run `curl http://<node-ip>:9527/metrics` — the request succeeds and returns all internal metrics (JVM heap, OS load, error counters by topic, DB sizes, per-witness block stats), with no authentication, IP filtering, or rate limiting applied, unlike the main HTTP API which passes through `HttpApiAccessFilter`/`HttpInterceptor`.
