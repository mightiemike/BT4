### Title
Unauthenticated `/wallet/getshieldtransactionhash` endpoint allows unbounded spend/receive description counts, enabling free CPU-cost hashing DoS - ([File: GetShieldTransactionHashServlet.java])

### Finding Description
`GetShieldTransactionHashServlet.doPost` reads the raw POST body, calls `Util.checkBodySize(input)` (a generic byte-length limiter used by dozens of unrelated servlets), then parses it into a `Transaction` via `Util.packTransaction` and immediately invokes `wallet.getShieldTransactionHash(transaction)` [1](#0-0) . `Util.checkBodySize` only enforces an overall request-payload byte cap; it has no awareness of the semantic structure of a `ShieldedTransferContract`, i.e., it does not bound the number of `spend_description`/`receive_description` entries.

By contrast, `ShieldedTransferActuator.validate()` — the code path exercised only when a transaction is actually broadcast/executed on-chain — contains explicit `checkSender`/`checkReceiver` count-limit checks on the spend/receive description lists [2](#0-1) . `Wallet.getShieldTransactionHash` does not call into `ShieldedTransferActuator.validate()` at all; it directly computes the transaction hash for the caller's convenience without any protocol-level count validation.

Because Base64/text-encoded protobuf allows many small `receive_description`/`spend_description` entries to fit within the generic body-size ceiling, an attacker can craft a `Transaction` with a `ShieldedTransferContract` containing far more descriptions than would ever be accepted by the actuator on-chain, and still pass `checkBodySize`. Each such request forces the server to perform the full Sha256Hash/protobuf-serialization work associated with hashing every description, with no TRX fee, no bandwidth/energy consumption, and no actuator-level rejection — only the generic HTTP rate limiter from `RateLimiterServlet` applies.

### Impact Explanation
This allows a remote, unauthenticated caller to repeatedly trigger CPU-bound hashing/serialization work scaled to a description count that could never be validated or paid for on-chain, since the actuator's count caps are never invoked in this code path. Repeated calls (up to whatever rate limit is configured) can be used to consume node CPU disproportionately to the cost incurred by the attacker, degrading responsiveness of the HTTP JSON-RPC service for legitimate users. This is a resource-exhaustion / underpriced-work issue rather than a consensus or fund-safety issue.

### Likelihood Explanation
Preconditions: the node's HTTP API (including the shielded transaction endpoints) must be enabled, which is common for full/API nodes serving wallet clients; no authentication or on-chain fee is required to reach this servlet. The attack is straightforward to reproduce — craft a `Transaction` protobuf with as many spend/receive descriptions as fit under `Util.checkBodySize`'s limit and POST it repeatedly. Feasibility is high given the endpoint is public by design (for offline transaction preparation before signing), but this specific gap (missing description-count validation before hashing) needs verification against the exact numeric caps in `checkSender`/`checkReceiver` and the byte threshold in `checkBodySize`, which I was not able to fully inspect line-by-line in the available index.

### Recommendation
Add explicit spend/receive description count validation (mirroring `ShieldedTransferActuator`'s `checkSender`/`checkReceiver` limits, or a dedicated conservative cap) inside `Wallet.getShieldTransactionHash` before performing any hashing work, so the free hashing endpoint cannot process transactions with more descriptions than the network would ever accept.

### Proof of Concept
1. Java unit test in `framework/src/test/java/org/tron/core/services/http/` that constructs a `Transaction` with a `ShieldedTransferContract` containing N `receive_description` entries, where N is large enough to exceed the actuator's `checkReceiver` cap but the serialized size still passes `Util.checkBodySize`.
2. Call `wallet.getShieldTransactionHash(transaction)` directly (bypassing HTTP) and assert that it does NOT throw (demonstrating no count check exists), while a call to `ShieldedTransferActuator.validate()` on the same transaction throws a `ContractValidateException` due to the receiver-count limit.
3. Measure and compare CPU time of `getShieldTransactionHash` for N=1 vs N=max-allowed-by-body-size, asserting cost scales roughly linearly/superlinearly with N, demonstrating the servlet enforces no cap proportional to actual protocol-accepted limits.

  protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    try {
      String input = request.getReader().lines()
          .collect(Collectors.joining(System.lineSeparator()));
      Util.checkBodySize(input);
      boolean visible = Util.getVisiblePost(input);
      Transaction transaction = Util.packTransaction(input, visible);

      BytesMessage result = wallet.getShieldTransactionHash(transaction);
      response.getWriter().println(JsonFormat.printToString(result, visible));
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }
