### Title
Transaction-info integrity check skips state/hot-state/position checkpoint hashes, letting replay-verify accept a diverged state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole invariant used by chunk-executor's `verify_execution` and by `db-tool`'s `replay_on_archive` to confirm that a locally re-executed `TransactionOutput` matches the trusted, ledger-committed `TransactionInfo`. It checks status, gas, write-set hash (`state_change_hash`), and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the three fields that bind the transaction to the actual Merkle state root committed to the ledger accumulator.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only 4 of the fields present in `TransactionInfo`. The function's own trailing comment documents the gap explicitly: [2](#0-1) 

Meanwhile `TransactionInfoV1` (and V0's `state_checkpoint_hash`) actually carries the authenticated Merkle roots that are folded into the transaction-info hash and, through the accumulator, into the ledger-info-signed root: `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, as built in `DoLedgerUpdate::assemble_transaction_infos`: [3](#0-2) 

`ensure_match_transaction_info` is invoked in two integrity-relevant call sites that don't independently check these roots:
- Chunk-executor's execution-verification path, used to confirm a locally computed output matches the state-sync-provided `TransactionInfo` when applying transactions by re-executing them: [4](#0-3) 
- `db-tool replay-on-archive`, whose entire purpose is confirming that re-execution against an archived state matches the archived, ledger-committed `TransactionInfo`: [5](#0-4) 

Note that this differs from `TransactionOutputListWithProof::verify` (used by state-sync's untrusted chunk-application path), which likewise omits checkpoint-hash checks in its per-item loop, but relies on `self.proof.verify(ledger_info, ...)` to bind the *whole* `TransactionInfo` (hash and all) against the accumulator/ledger-info signature — so a wrong state root there would fail because the info-hash itself wouldn't match the accumulator. That path is not affected because it uses the complete `TransactionInfo::hash()` for accumulator binding, not `ensure_match_transaction_info`.

The two vulnerable call sites, by contrast, compare a **freshly re-executed** `TransactionOutput` field-by-field against a `TransactionInfo` they already trust (either because it came from an already-consistency-checked chunk in `verify_execution`, or because it was loaded straight from backup/archive `TransactionInfoWithProof` in `replay_on_archive`). In both cases the code's job is precisely to catch a **local computation divergence** from the *trusted* committed root — and for the checkpoint-hash fields, it silently passes even when local execution disagrees.

### Impact Explanation
This is a hard-fork-only / replay-verification integrity gap rather than a live consensus-safety bug: the transaction-info hash and accumulator root are still computed correctly from all fields at commit time (`do_ledger_update.rs`), so a live node's synced ledger is not directly corrupted by this alone. However, per the State-Integrity Gate this qualifies because it is exactly the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... transaction proof ... accepted as valid" category: `db-tool replay-on-archive` and chunk-executor's execution-verify path are the tools operators rely on to detect that re-executed state (including the newly introduced native-position/trading-native state Merkle tree gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) matches the already-committed, signed ledger state. If VM re-execution produces a different state/hot-state/position root than what was actually committed on-chain (e.g. due to a state-computation bug, an unintended non-determinism, or an incompletely-guarded feature-flag interaction), these verification tools will report success (`replay_verify_success`) while a real state divergence exists undetected. This directly weakens the guarantee that "authenticated ... proof context" stays bound to the correct object, since the checkpoint hash is precisely the state-root binding for compacted/committed state at that version.

### Likelihood Explanation
Currently `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and to a lesser extent hot-state root checks) are the fields most likely to silently diverge, since they gate newer, less-battle-tested state-merklization code paths (native-position tree). The gap is unprivileged to trigger — it doesn't require an attacker, only a real bug or non-determinism in the newer state-checkpoint computation, and it fires automatically inside the normal replay/verify tooling.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` against the locally computed roots (threading the locally-computed checkpoint hashes into the function, analogous to how `expected_write_set`/`expected_events` are already threaded in), and do so before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet, as the existing TODO comment already recommends.

### Proof of Concept
1. In `execution/executor/src/chunk_executor/mod.rs::verify_execution` (or `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`), feed a `transaction_infos` entry whose `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are set to arbitrary/incorrect values while status, gas, write-set hash, and event root hash are left correct.
2. Call `TransactionOutput::ensure_match_transaction_info(version, txn_info, ..)` — observe it returns `Ok(())` despite the checkpoint hashes not matching what local execution/state actually computed.
3. This demonstrates that any real divergence in locally-computed state/hot-state/position roots versus the trusted `TransactionInfo` would go undetected by both `replay_on_archive` and chunk-executor's execution-verify path. [1](#0-0)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
