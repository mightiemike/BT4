### Title
Silent `BigInteger`→`long` truncation in `MarketUtils.multiplyAndDivide` can corrupt TRC10 exchange-order matching amounts - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
`MarketUtils.multiplyAndDivide(a, b, c, disableMath)` computes `a*b/c` for TRC10 market-order matching. When `a*b` overflows `long`, it falls back to `BigInteger` arithmetic, but the *final* result is converted back with the unchecked `.longValue()` call instead of `.longValueExact()` or an explicit bounds check. [1](#0-0) 
This mirrors the H-05 pattern in the external report: a computation that can legitimately exceed the destination type's capacity is narrowed via an unchecked cast, producing a silently wrong (truncated/wrapped) numeric result that is then used to move real value.

### Finding Description
`multiplyAndDivide` first tries `multiplyExact`/`floorDiv` on `long` operands and, on `ArithmeticException` (i.e., when `a*b` doesn't fit in a `long`), recomputes using `BigInteger`:
```java
BigInteger aBig = BigInteger.valueOf(a);
BigInteger bBig = BigInteger.valueOf(b);
BigInteger cBig = BigInteger.valueOf(c);
return aBig.multiply(bBig).divide(cBig).longValue();
``` [2](#0-1) 
`BigInteger.longValue()` does **not** throw when the value is out of `long` range — it silently keeps only the low-order 64 bits (two's-complement truncation), exactly the same class of bug as the unchecked `uint256`→`uint128` cast in the Trident report. If `a*b` is astronomically larger than `c` (e.g., `c` is small relative to `a` and `b`), the quotient `a*b/c` itself can still exceed `Long.MAX_VALUE`, and the truncated value returned can be arbitrarily smaller (or even negative, since `long` is signed) than the mathematically correct result.

This function is the core quantity-matching primitive used in `MarketSellAssetActuator.matchSingleOrder`, where it computes how much of the buy/sell token a taker or maker actually receives during TRC10-to-TRC10/TRX order matching: [3](#0-2) [4](#0-3) [5](#0-4) 
These results (`takerBuyTokenQuantityReceive`, `makerBuyTokenQuantityReceive`) directly drive `AccountCapsule` asset/TRX balance debits and credits and remaining-order-quantity bookkeeping later in `matchSingleOrder`, so an incorrect (truncated) value corrupts the actual value transferred between the taker, maker, and their token balances.

`sellTokenQuantity`/`buyTokenQuantity` on `MarketSellAssetContract` are user-controlled `long` fields set directly from the transaction (no additional upper bound beyond `long` range is applied beyond `>0` checks) in `MarketSellAssetActuator.execute`/`doValidate`, so an attacker who creates orders (as both maker and taker, or via a colluding maker) can choose `sellTokenQuantity`/`buyTokenQuantity` pairs on the resting (maker) order and the taker order such that the intermediate product `a*b` is huge and the divisor `c` is small enough that the true quotient still exceeds `Long.MAX_VALUE` (~9.22e18), forcing `longValue()` truncation. [6](#0-5) 

### Impact Explanation
This function sits directly in the fund-movement path of `MarketSellAssetActuator`, which settles real TRX/TRC10 balances between accounts on every matched order. A truncated quantity means either:
- an attacker receives far less than expected while the counter-order's remaining-quantity bookkeeping is likewise corrupted, potentially locking or double-crediting funds in subsequent matches, or
- a crafted pair of orders produces a wrapped negative/very small `longValue()` result that is treated as valid ("`== 0`" checks return the taker's tokens, but any non-zero truncated wrong value proceeds to the actual account-balance mutation and order-quantity subtraction), corrupting on-chain token/TRX accounting for the exchange feature.

Because this is TRC10 exchange settlement logic reachable by any account broadcasting `MarketSellAssetContract` transactions, a successful exploit constitutes asset/accounting corruption in a fund-management-critical path, matching the "asset or accounting corruption" acceptance criterion.

### Likelihood Explanation
Exploitation requires an attacker (or attacker with a colluding counterparty) to construct order pairs with extreme, but individually valid, `sellTokenQuantity`/`buyTokenQuantity` ratios so that the true `a*b/c` quotient exceeds `Long.MAX_VALUE`. This is achievable because `long` fields allow values up to ~9.22e18 and the code applies no additional check preventing the *quotient* itself (only the raw product) from exceeding `long` range before calling `longValue()`. This requires careful selection of prices/quantities (similar in spirit to the disputed-but-confirmed Trident PoC, where the reviewer noted the original PoC parameters were wrong but the unsafe-cast root cause was still confirmed) — so real-world exploitability depends on finding concrete order-quantity combinations that satisfy all of `doValidate()`'s constraints (price consistency, balance sufficiency, `MAX_ACTIVE_ORDER_NUM`, etc.) while still forcing the BigInteger quotient over `Long.MAX_VALUE`. I was not able to fully verify from the code alone whether other order-validation constraints (e.g., implicit price/quantity ratio limits enforced elsewhere) make such an overflow condition unreachable in practice; this should be confirmed with a working PoC transaction.

### Recommendation
In `MarketUtils.multiplyAndDivide`, replace the unchecked `.longValue()` with `.longValueExact()` (throwing `ArithmeticException` on overflow, consistent with how the rest of the method already treats overflow as an exceptional/fallback condition), or explicitly check `aBig.multiply(bBig).divide(cBig)` against `BigInteger.valueOf(Long.MAX_VALUE)`/`Long.MIN_VALUE` before narrowing, and propagate a `ContractValidateException`/abort the match instead of silently continuing with a truncated value. [1](#0-0) 

### Proof of Concept
Conceptual PoC (parameters need to be validated against all of `MarketSellAssetActuator.doValidate()`'s constraints, which I could not fully enumerate from the retrieved code):
1. Attacker (as maker) creates a resting sell order with `sellTokenQuantity = b` and `buyTokenQuantity = c` chosen such that `b` is very large and `c` is very small (extreme price).
2. Attacker (as taker, or a colluding second account) creates a matching taker order with `sellTokenQuantityRemain = a` also large, so that `matchSingleOrder` invokes:
```java
long takerBuyTokenQuantityRemain = MarketUtils
    .multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity, ...);
``` [3](#0-2) 
3. If `a*b` overflows `long` (triggering the `BigInteger` fallback) and the true quotient `a*b/c` still exceeds `Long.MAX_VALUE`, `longValue()` returns a truncated (and potentially small or negative) result instead of throwing.
4. This truncated value is then used unchanged to update `takerOrderCapsule`/`makerOrderCapsule` remaining quantities and, downstream in `execute()`, to credit/debit account asset and TRX balances — settling the trade at an incorrect amount and corrupting exchange accounting.
