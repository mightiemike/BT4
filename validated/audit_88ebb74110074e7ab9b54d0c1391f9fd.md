### Title
Loss of witness voting rewards when a witness's snapshotted vote total is zero for a reward cycle - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` (the old, pre-Vi reward algorithm) silently discards an already-accrued witness reward for a cycle when the per-cycle snapshotted total vote count for that witness is zero, with no fallback path that returns the value to any pool, the blackhole, or transaction-fee pool. This mirrors the Olas `claimStakingIncentives` bug class: an incentive amount that was already computed/allocated for a period is neither distributed to its intended recipients nor refunded when the "total weight" for that period is zero — it is simply lost.

### Finding Description
Block/standby/transaction-fee rewards are accrued per witness per cycle in `MortgageService.payReward`, which stores the amount unconditionally in the delegation store keyed by the *current* cycle number: [1](#0-0) 

The per-witness "total vote" used to later split that reward among voters is a snapshot taken once, at the maintenance transition **preceding** the cycle, using the witness's vote count at that instant: [2](#0-1) 

When a voter later withdraws/queries reward for that cycle, `computeReward` looks up this snapshot value and, if it is zero (or `DelegationStore.REMARK`), skips the whole reward for that cycle instead of falling back or refunding it: [3](#0-2) [4](#0-3) 

Because a witness that is newly promoted to an active/standby set can have zero votes at the exact moment the maintenance-time snapshot for that cycle is taken (its votes arrive only afterward, e.g. via `countVote`/`witnessCapsule.setVoteCount` updates that only take effect for the *next* cycle's snapshot in `doMaintenance`), any block/tx-fee/standby reward it earns during that cycle is stored via `delegationStore.addReward(cycle, address, value)` but can never be attributed to any voter, since `getWitnessVote(cycle, address)` for that cycle remains 0 forever. The stored reward amount is never zeroed, never burned to the blackhole, and never credited back to the transaction fee pool or treasury — it becomes permanently orphaned in the `DelegationStore`.

This is directly analogous to the Olas `Dispenser.calculateStakingIncentives` bug: `availableStakingAmount`/`stakingDiff` is computed for a period, but when `totalWeightSum == 0` the code path that should redirect the unused amount back to `tokenomics.refundFromStaking` is never reached, so the value is lost from the accounted supply.

### Impact Explanation
This causes silent, permanent loss of witness/voter reward funds that were already computed and reserved in on-chain state (`delegationStore` reward records), with no corresponding refund to the blackhole, transaction fee pool, or any other accounted destination. This is a resource/reward-accounting corruption bug: the sum of "reward accrued" vs "reward eventually payable + refunded" diverges, silently reducing effectively distributable TRX without any burn accounting, comparable in class (though not necessarily in magnitude) to the referenced Medium-severity Olas finding.

### Likelihood Explanation
The trigger condition — a witness having zero votes at the exact time its per-cycle vote snapshot is taken by `MaintenanceManager.doMaintenance`, while still earning block/standby/fee rewards during that cycle (e.g., immediately after becoming part of the active/standby witness set, or after all its voters unvote right at a maintenance boundary) — occurs through completely normal, unprivileged voting activity (`VoteWitnessContract`) and consensus block production, not through any privileged action. It is a corner case rather than a routine occurrence, matching the "Context/Medium" characterization in the source report.

### Recommendation
In `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)`, when `totalVote == 0` (or `REMARK`) for a witness that has a nonzero `totalReward` for that cycle, explicitly route the orphaned reward to a recoverable destination (e.g., burn to blackhole via `Commons.adjustBalance`, or credit back to the transaction fee pool / retained-earnings-style account) instead of silently `continue`-ing, and mark the cycle/witness pair as reconciled to prevent double-refunding on repeated calls. The same review should be applied to the new-algorithm path in `DelegationStore.accumulateWitnessVi`, which similarly "just forwards" the previous Vi and drops the current-cycle reward when `voteCount == 0`.

### Proof of Concept
1. Configure the chain with `allowChangeDelegation()` enabled and rely on the old reward path (`beginCycle < newRewardAlgorithmEffectiveCycle`), i.e. `useNewRewardAlgorithm` transition cycle not yet reached.
2. Witness `W` has vote count `0` at the exact moment `MaintenanceManager.doMaintenance()` executes the `nextCycle` snapshot loop (`delegationStore.setWitnessVote(cycle=T, W, 0)`), e.g., `W` was just registered/promoted into the active/standby witness list.
3. During cycle `T`, `W` produces blocks and/or is included in the standby list, so `MortgageService.payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness` call `payReward(W, value)`, which stores a positive `delegationStore.addReward(T, W, value)`.
4. A voter casts a vote for `W` during cycle `T` (its vote is only reflected in `witnessCapsule.getVoteCount()` for the *next* cycle's snapshot, not cycle `T`).
5. At cycle boundary `T→T+1`, the voter's `withdrawReward`/`queryReward` calls `computeReward(T, T+1, accountCapsule)` → `computeReward(T, votes)`, which reads `delegationStore.getWitnessVote(T, W) == 0` and skips distribution (line `if (totalVote == DelegationStore.REMARK || totalVote == 0) { continue; }`).
6. `delegationStore.getReward(T, W)` remains permanently non-zero in storage but is never paid to any voter and never refunded to the blackhole or fee pool — the value is stuck/lost from circulation.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
    BytesCapsule bytesCapsule = get(buildVoteKey(cycle, address));
    if (bytesCapsule == null) {
      return REMARK;
    } else {
```
