## #Vulnerability found for this question.

### Title
Missing sorted/unique validation for constructor entry points in compiled class facts allows selector-search integrity violation - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/contract_class/compiled_class.cairo])

### Summary
The Starknet OS's `validate_compiled_class_facts` function validates that entry point selectors are sorted and unique for `external_functions` and `l1_handlers`, but never performs this validation for `constructors`, even though the constructor lookup path relies on the same sorted-array search primitive used for the other two entry-point kinds. This mirrors the reported bug class: validation checks some parts of an uploaded/declared artifact (here, two of three entry-point tables) while omitting an equally security-relevant part (the third table), letting malformed content that should be rejected slip through to execution.

### Finding Description
`validate_compiled_class_facts` calls `validate_entry_points` only for `external_functions` and `l1_handlers`: [1](#0-0) 

It never calls `validate_entry_points` on `compiled_class.constructors` / `n_constructors`, despite the `CompiledClass` struct explicitly carrying a `constructors`/`n_constructors` table that is hashed into the compiled class hash exactly like the other two tables: [2](#0-1) 

The gap matters because `get_entry_point` — the function used at execution time to resolve which bytecode offset to jump to for a given selector — performs the exact same `search_sorted_optimistic` lookup for constructors as it does for external/L1-handler entry points, and that primitive's correctness depends on the array actually being sorted: [3](#0-2) 

Because `hash` (the compiled class hash) is computed over whatever byte layout is supplied via the `LoadClassesAndBuildBytecodeSegmentStructures` / `LoadClass` hints and only checked for equality against the expected hash — not checked for internal sortedness of the constructor table — a compiled-class-fact whose `constructors` array is unsorted or contains duplicate/colliding selectors passes `validate_compiled_class_facts` unmodified as long as the hash matches: [4](#0-3) 

`search_sorted_optimistic` is an "optimistic" binary-search-style routine (not a linear scan); on unsorted or duplicated-key input it can terminate at the wrong element or fail to find an existing key, unlike `find_element`'s exhaustive semantics. This is analogous to the Chamilo bug class: the check that gates acceptance (`h5p.json` exists / entry-point hash matches) is present, but a structurally-required invariant of a *different* part of the same artifact (`.htaccess` extension-execution control / constructor selector sortedness) is left unchecked, letting a hash-valid-but-structurally-malformed artifact reach an execution primitive that assumes the invariant holds.

### Impact Explanation
If a constructor entry-point table with unsorted/duplicate selectors is admitted as a "valid" compiled-class fact (matching hash) into the OS's exec_scope, `get_entry_point` for `ENTRY_POINT_TYPE_CONSTRUCTOR` can resolve to a different bytecode offset than the honest sequencer's blockifier execution would resolve for the same declared class, or spuriously report `ERROR_ENTRY_POINT_NOT_FOUND`. Since the Starknet OS re-execution is what produces the committed execution trace and, ultimately, the block's state commitment, any divergence between the blockifier's compiled-CASM execution (which always compiles constructors in sorted order via the standard Sierra→CASM pipeline) and an OS-side compiled-class-fact with a manipulated constructor table creates a path to honest-node divergence / wrong committed state for `DeployAccount`/constructor-invoking transactions.

### Likelihood Explanation
Reaching this gap in the normal declare pipeline is hard, because compiled classes for declared contracts are produced deterministically by the sequencer's own Sierra→CASM compiler, which sorts entry points including constructors, and the stateless gateway validator additionally checks constructor-selector sort/uniqueness on the submitted Sierra program: [5](#0-4) 

However, that gateway check operates on the user-submitted `SierraContractClass.entry_points_by_type`, not on the final compiled CASM fact consumed by the OS, and the OS-level check is the last line of defense guarding the invariant `search_sorted_optimistic` needs. The missing constructor check is a concrete, provable gap in that defense-in-depth layer, independent of whether a currently-known path exists to smuggle an unsorted constructor table past compilation.

### Recommendation
Add a call to `validate_entry_points` for `compiled_class.constructors` / `n_constructors` inside `validate_compiled_class_facts`, matching the existing calls for `external_functions` and `l1_handlers`, so all three entry-point tables are proven sorted and unique before being trusted by `get_entry_point`'s `search_sorted_optimistic` lookup.

### Proof of Concept
1. Construct a `CompiledClassFact` whose `compiled_class.constructors` array contains two entries with out-of-order or duplicate selectors (e.g., `[selector=5, ...]` followed by `[selector=3, ...]`), while keeping `external_functions` and `l1_handlers` properly sorted.
2. Compute the compiled class hash over this exact layout via `blake_compiled_class_hash`/`compiled_class_hash` (the hash function only hashes the bytes; it does not enforce sortedness) and set `compiled_class_fact.hash` accordingly.
3. Feed this fact through `guess_compiled_class_facts`/`validate_compiled_class_facts_post_execution`; observe that `validate_compiled_class_facts` accepts it because it only calls `validate_entry_points` on `external_functions` and `l1_handlers`.
4. Trigger a constructor call whose selector should resolve to the second (out-of-order) entry; `search_sorted_optimistic` in `get_entry_point` can then return an incorrect success/failure result or the wrong `CompiledClassEntryPoint`, diverging from the blockifier's own sorted-CASM based resolution for the same class.

// Returns the CompiledClassEntryPoint, based on 'compiled_class' and 'execution_context'.
func get_entry_point{range_check_ptr}(
    compiled_class: CompiledClass*, execution_context: ExecutionContext*
) -> (success: felt, entry_point: CompiledClassEntryPoint*) {
    alloc_locals;
    // Get the entry points corresponding to the transaction's type.
    local entry_points: CompiledClassEntryPoint*;
    local n_entry_points: felt;

    tempvar entry_point_type = execution_context.entry_point_type;
    if (entry_point_type == ENTRY_POINT_TYPE_L1_HANDLER) {
        entry_points = compiled_class.l1_handlers;
        n_entry_points = compiled_class.n_l1_handlers;
    } else {
        if (entry_point_type == ENTRY_POINT_TYPE_EXTERNAL) {
            entry_points = compiled_class.external_functions;
            n_entry_points = compiled_class.n_external_functions;
        } else {
            assert entry_point_type = ENTRY_POINT_TYPE_CONSTRUCTOR;
            entry_points = compiled_class.constructors;
            n_entry_points = compiled_class.n_constructors;

            if (n_entry_points == 0) {
                return (success=1, entry_point=cast(0, CompiledClassEntryPoint*));
            }
        }
    }

    // The key must be at offset 0.
    static_assert CompiledClassEntryPoint.selector == 0;
    // TODO(Yoni, 1/1/2026): make sure the cost of searching missing keys is covered
    //   once reverted entrypoints are supported in the OS (should be fine).
    let (entry_point_desc: CompiledClassEntryPoint*, success) = search_sorted_optimistic(
        array_ptr=cast(entry_points, felt*),
        elm_size=CompiledClassEntryPoint.SIZE,
        n_elms=n_entry_points,
        key=execution_context.execution_info.selector,
    );
    if (success != FALSE) {
        return (success=1, entry_point=entry_point_desc);
    }

    return (success=0, entry_point=cast(0, CompiledClassEntryPoint*));
}

    fn validate_entry_points_sorted_and_unique(
        &self,
        contract_class: &starknet_api::state::SierraContractClass,

        let is_sorted_unique = |entry_points: &[EntryPoint]| {
            entry_points.windows(2).all(|pair| pair[0].selector < pair[1].selector)

        if is_sorted_unique(&contract_class.entry_points_by_type.constructor)

            return Ok(());
        }

    }
