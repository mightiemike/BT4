Based on my investigation, I found the concrete analog. The `handleFailedOutbound` function mirrors the `GClaimManager`/`Divider._collect()` composability pattern: an ordinary, expected-to-succeed downstream call is embedded in the middle of the automated recovery flow, and its failure derails the entire flow into a state requiring privileged manual intervention rather than completing atomically or degrading gracefully.

### Title
Failed re-mint during outbound revert permanently freezes bridged funds requiring admin intervention - (File: x/uexecutor/keeper/outbound.go)

### Summary
When an outbound observation is voted as failed, `handleFailedOutbound` attempts to re-mint the bridged PRC20 back to the revert recipient via `CallPRC20Deposit`. If that EVM call errors for any reason, the code does not retry, does not fall back, and does not preserve the outbound in a retryable `PENDING`/`REVERTED` state — it immediately calls `AbortOutbound`, which is an explicit dead-end requiring "manual intervention" (an admin/governance action outside the automatic protocol flow).

### Finding Description
`handleFailedOutbound` in [1](#0-0)  re-mints bridged tokens by calling `k.CallPRC20Deposit(ctx, prc20, recipient, amount)` where `recipient` is taken from `outbound.RevertInstructions.FundRecipient` (attacker-supplied at inbound time, sourced straight from the external gateway event) with fallback to `outbound.Sender`. If this single downstream EVM call reverts or errors, the function immediately gives up and calls `k.AbortOutbound(...)`: [2](#0-1) 

`AbortOutbound` sets `Status_ABORTED` and explicitly documents that "manual intervention is needed": [3](#0-2) . There is no automatic retry path, no alternate recipient fallback, and no code path that returns the outbound to `PENDING` for another attempt.

This is structurally the same composability failure as the reported `GClaimManager`/`Divider._collect()` issue: a single external/downstream call embedded inside an automated, no-privileged-actor-required recovery flow (the outbound-failure → re-mint → done sequence) is allowed to permanently halt that flow the moment it reverts, converting a fully automatic user-funds-return mechanism into one that depends on an admin. Since `RevertInstructions.FundRecipient` is attacker/user-controlled input from the very same inbound the outbound is reverting, an unprivileged party constructs the exact conditions of the trigger (e.g., a `FundRecipient`/address whose corresponding mint call the PRC20/UniversalCore contract will reject — invalid liquidity-cap-exceeding mint amount, blacklisted/paused-token check, or any other on-chain condition enforced by `depositPRC20Token`).

### Impact Explanation
Funds that were bridged in via the original inbound and are meant to be automatically returned to the user upon outbound failure become stuck in `ABORTED` status indefinitely once the re-mint call errors. Recovery is scoped entirely outside honest-validator/consensus flows and instead depends on privileged admin action, which is a permanent freeze of user funds reachable purely from unprivileged user actions (their own inbound + the outbound-failure path that anyone/any validator can vote on legitimately). This matches the "permanent freezing... of user or protocol-controlled funds" allowed impact.

### Likelihood Explanation
Reaching `Status_OBSERVED`→failed-outbound requires normal honest-validator voting (already in-scope, non-privileged), and the re-mint failure condition depends only on the recipient/amount the original attacker-controlled inbound supplied. Any deterministic on-chain revert condition in the PRC20/UniversalCore deposit path (e.g., liquidity cap, paused token, zero-address edge case) reliably triggers this every time, making it a low-effort, repeatable trigger rather than a rare edge case.

### Recommendation
Do not treat a single re-mint failure as terminal. At minimum: (1) leave the outbound in a retryable state (e.g., keep it `PENDING`/introduce a `REMINT_FAILED` retry status) so it can be reattempted automatically on a later block instead of immediately aborting; (2) fall back to a safe default recipient (e.g., always the original `outbound.Sender`, ignoring an attacker-supplied `FundRecipient` that cannot receive) before giving up; and (3) only escalate to `ABORTED`/admin intervention after repeated automatic retries fail, consistent with how `RevertStuckInbound` provides a genuine escape hatch for a different failure class.

### Proof of Concept
1. An external-chain user submits a gateway deposit (inbound) with `TxType=FUNDS`, setting `RevertInstructions.FundRecipient` to an address/amount combination that the PRC20/UniversalCore's `depositPRC20Token` will predictably reject on mint (e.g., an amount that pushes the token's configured `LiquidityCap` over the limit, per `x/uregistry` `TokenConfig.LiquidityCap`).
2. The inbound is voted through normally by honest Universal Validators; a corresponding outbound is created and later voted as `FAILED` by honest validators observing the real destination-chain result.
3. `FinalizeOutbound` → `handleFailedOutbound` [4](#0-3)  calls `CallPRC20Deposit` to re-mint to the crafted `FundRecipient`; the EVM call errors due to the liquidity-cap (or other) rejection.
4. The outbound is immediately set to `Status_ABORTED` via `AbortOutbound`, with no further automatic remediation — the user's bridged funds are stuck pending admin action, with no code path to recover them without privileged intervention.

func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}

func (k Keeper) handleFailedOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	// Only revert bridged funds for funds-related tx types
	if outbound.TxType == types.TxType_FUNDS || outbound.TxType == types.TxType_GAS_AND_PAYLOAD ||
		outbound.TxType == types.TxType_FUNDS_AND_PAYLOAD {

		// Decide revert recipient safely
		recipient := outbound.Sender
		if outbound.RevertInstructions != nil &&
			outbound.RevertInstructions.FundRecipient != "" {
			recipient = outbound.RevertInstructions.FundRecipient
		}

		amount := new(big.Int)
		amount, ok := amount.SetString(outbound.Amount, 10)
		if !ok {
			return fmt.Errorf("invalid amount: %s", outbound.Amount)
		}
		receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)

		pcTx := types.PCTx{
			Sender:      outbound.Sender,
			BlockHeight: uint64(ctx.BlockHeight()),
		}
		// Capture tx hash from receipt even on EVM revert for debugging.
		if receipt != nil {
			pcTx.TxHash = receipt.Hash
			pcTx.GasUsed = receipt.GasUsed
		}
		if err != nil {
			pcTx.Status = "FAILED"
			pcTx.ErrorMsg = err.Error()
			outbound.PcRevertExecution = &pcTx
			// Re-mint failed — mark as ABORTED for manual intervention
			return k.AbortOutbound(ctx, utxId, outbound,
				fmt.Sprintf("failed to re-mint tokens for revert: %s", err.Error()))
		}
