### Title
Integer truncation of an attacker-controlled 32-bit length field causes a negative buffer position (out-of-bounds panic / parser desync) on 32-bit builds - (File: internal/protolazy/bufferreader.go)

### Summary
`protolazy.BufferReader.Skip` and its callers (`SkipBytes`, `SkipValue`, `SkipGroup`, and the inlined length-skip logic in `buildIndex`) take a wire length that was decoded as a `uint32` and pass it directly to `Skip(int(n))` without checking that it fits in a non-negative `int`. On 32-bit architectures (`GOARCH=386`, `arm`, `mips`, etc.) `int` is 32 bits, so any decoded length with the high bit set (`n >= 0x80000000`) becomes a negative `int`, exactly mirroring the PJSIP WAV chunk-length overflow described in ALPINE-CVE-2022-24792 ("reading … data chunks with length greater than 31-bit integers … does not affect 64-bit apps").

### Finding Description
`BufferReader.DecodeVarint32` (`internal/protolazy/bufferreader.go:144-196`) parses an attacker-supplied varint into a `uint32` and can legitimately return any value up to `0xFFFFFFFF`: [1](#0-0) 

Every consumer of this value for a length-prefixed (`BytesType`) field converts it straight to `int` and calls `Skip`: [2](#0-1) [3](#0-2) [4](#0-3) 

`Skip` itself does not detect a negative `n`: [5](#0-4) 

On a 64-bit build, `int` is 64 bits, so `uint32→int` never produces a negative number and this is harmless. On a 32-bit build, a length such as `0x80000000` converts to `int(-2147483648)`. The check `len(b.Buf) < b.Pos+n` performs signed 32-bit arithmetic that can wrap and evaluate false (bypassing the intended bounds check), after which `b.Pos += n` drives `b.Pos` negative. Any subsequent `b.Buf[i]` access with a negative index panics at runtime (Go disallows negative slice indices), and any partial arithmetic before the panic corrupts the parser's notion of position, causing field boundaries to be misidentified.

This `BufferReader` is exercised by `buildIndex` in `internal/protolazy/lazy.go`, which is invoked from `XXX_lazyUnmarshalInfo.FindFieldInProto` (`internal/protolazy/lazy.go:301-319`) the first time a lazily-decoded field is accessed after `proto.Unmarshal`. Lazy decoding of message-typed fields (`mi.lazyOffset`) is enabled by default (`enableLazy = 1` unless `GOPROTODEBUG=nolazy`), so this is on the default/binary-Unmarshal path for messages containing lazily-eligible fields, not a debug-only or opt-in feature: [6](#0-5) [7](#0-6) 

### Impact Explanation
On a 32-bit target process, an unauthenticated peer can send a single crafted message containing (within a lazily-decoded message region) a length-prefixed field whose varint-encoded length has bit 31 set. When the field is later accessed (any getter/reflection touch triggers `buildIndex`), the truncation described above drives the reader position negative, leading to an unrecovered panic (process crash) — a remote, unauthenticated denial of service, matching the High-severity DoS classification of the reference CVE.

### Likelihood Explanation
Requires: (1) the target is a 32-bit build (`GOARCH=386/arm/mips` etc.), (2) the schema contains at least one message-typed field eligible for lazy decoding (trusted-schema precondition, acceptable per rules), and (3) the attacker can supply the raw bytes decoded via the default binary `proto.Unmarshal`. All are realistic for embedded/IoT or 32-bit ARM services built with this library, and no special resolver, malicious peer identity, or privileged caller is needed — only attacker-controlled bytes on an otherwise ordinary Unmarshal path.

### Recommendation
- In `DecodeVarint32`/its callers, reject lengths greater than `math.MaxInt32` (or better, greater than the remaining buffer length) before converting to `int`.
- In `Skip`, validate `n >= 0` before doing pointer arithmetic, and compute the bounds check using unsigned/`uint64` comparisons to avoid architecture-dependent signed overflow.
- Add regression tests run under `GOARCH=386`/`arm` (or emulate 32-bit `int` semantics in tests) to catch this overflow class going forward.

### Proof of Concept
Pseudocode input (bytes) for a lazily-decoded message region containing one `BytesType` field whose length varint encodes `0x80000000`:
```
tag byte for field N, wire type 2 (LEN)   -> e.g. 0x0A (field 1, LEN)
length varint bytes                       -> 0x80 0x80 0x80 0x80 0x08   // decodes to uint32(0x80000000)
(payload bytes, can be empty/short; buildIndex fails/crashes before validating payload length)
```
On a 32-bit build:
1. `DecodeVarint32` returns `n = 0x80000000`.
2. `int(n)` == `-2147483648`.
3. `Skip(-2147483648)` bypasses the `len(b.Buf) < b.Pos+n` check due to signed overflow and sets `b.Pos` to a large negative value.
4. The next `b.Buf[i]` access in `buildIndex`/`SkipGroup` panics with "index out of range" (negative index), crashing the goroutine/process.

This cannot be reproduced on a 64-bit build since `int` there is 64 bits and no truncation occurs, consistent with the original CVE's "does not affect 64-bit apps" scope note.

// skip skips the specified number of bytes
func (b *BufferReader) Skip(n int) (err error) {
	if len(b.Buf) < b.Pos+n {
		return io.ErrUnexpectedEOF
	}
	b.Pos += n
	return
}
