### Title
Unchecked u64 subtraction in `generate_index()` can underflow `accounts_data_len` during snapshot/startup index rebuild - (File: accounts-db/src/accounts_db.rs)

### Summary
`AccountsDb::generate_index()` computes `accounts_data_len_from_duplicates` by summing the stored data length of every duplicate (older/superseded) version of each pubkey found across storages during startup index generation, then subtracts this from the running total `total_accum.accounts_data_len` using a bare, unchecked `-=` operator, unlike the adjacent capitalization subtraction on the same code path which uses `checked_sub(...).expect(...)`. [1](#0-0) 

### Finding Description
Immediately before the vulnerable line, the capitalization aggregate for the same duplicate-visiting pass is subtracted defensively:
```
total_accum.capitalization = total_accum
    .capitalization
    .checked_sub(capitalization_from_duplicates)
    .expect("capitalization cannot underflow");
total_accum.accounts_data_len -= accounts_data_len_from_duplicates;
``` [2](#0-1) 

The engineer clearly recognized that this subtraction class can underflow (hence the `checked_sub`/`expect` guard on capitalization one line above), but the parallel `accounts_data_len` accumulator right below it uses plain `-=`. This mirrors exactly the bug class in the external report: two values are computed independently (a running total accumulated while scanning all account storages during `generate_index`, and a "duplicates" total accumulated separately via `visit_duplicate_pubkeys_during_startup` across all bins/chunks in parallel via `DuplicatePubkeysVisitedInfo::reduce`) and then combined with a subtraction that assumes, but does not verify, that the subtrahend cannot exceed the minuend. [3](#0-2) 

This code executes during `generate_index()`, which is invoked at validator startup to rebuild the accounts index and associated derived accumulators (capitalization, accounts data length, lt hash) directly from the account storages loaded from a snapshot/ledger — i.e. it is exactly the "snapshot generation and rebuild" class of code called out as in-scope.

### Impact Explanation
In a debug/test build, `u64 -= u64` panics on overflow, causing the validator startup index generation to abort with a panic — a node crash during snapshot load/rebuild. In a release build (the default for production Agave binaries, which do not universally enable overflow checks for all crates), the subtraction silently wraps around to a huge `u64` value, corrupting `accounts_data_len`, which is a value used elsewhere for accounts-data-size budget accounting and reported via `Bank`. A silently wrapped, enormous `accounts_data_len` diverges from what the same accounts would compute during normal (non-startup, incremental) accounting, creating an honest-node startup-vs-normal-operation mismatch in a value that participates in bank state. This satisfies the "concrete ... silent balance change ... honest-node snapshot-vs-replay mismatch, node panic" acceptance criteria class.

### Likelihood Explanation
Triggering this requires the sum of stored data lengths of superseded/duplicate account versions (across all slots being loaded) to exceed the running total accumulated in `total_accum.accounts_data_len` for the same set of storages. Because `total_accum.accounts_data_len` and the duplicates total are accumulated via two different, independently-parallelized reduction paths over overlapping sets of storages/pubkeys, an accounting mismatch (e.g. edge cases in how a pubkey's slot-list duplicates are attributed, or empty/zero-length accounts interacting with `calculate_stored_size`) can plausibly cause the subtrahend to exceed the minuend for certain snapshot content. This is a real, reachable arithmetic path exercised on every validator startup from snapshot, not a theoretical or mocked-only path, though the exact scenario, sufficient to overflow was not fully isolated within the available time.

### Recommendation
Change `total_accum.accounts_data_len -= accounts_data_len_from_duplicates;` to use `checked_sub` with an explicit `.expect("accounts data len cannot underflow")` (or `saturating_sub` with a warning/metric if silent clamping is acceptable), matching the defensive pattern already used one line above for `capitalization`. Add a regression test analogous to `test_calculate_capitalization_overflow_intra_slot`/`test_calculate_capitalization_overflow_inter_slot` that exercises `generate_index()` with duplicate accounts to assert the invariant explicitly rather than relying on undefined wraparound behavior.

### Proof of Concept
A precise PoC requires constructing storages such that `visit_duplicate_pubkeys_during_startup`'s summed `accounts_data_len_from_duplicates` exceeds the concurrently-accumulated `total_accum.accounts_data_len` for the same generate_index() call; this was not fully constructed/verified within the available investigation. Structurally, the flaw is directly analogous to the reported `Escrow.processPayment()` bug: an unguarded subtraction of an independently-computed value (`fee + serverAmount` there; `accounts_data_len_from_duplicates` here) from a total (`transaction.amount` there; `total_accum.accounts_data_len` here), where a sibling computation in the very same function (`capitalization`) was hardened with `checked_sub().expect()` but this one was not.
