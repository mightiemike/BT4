### Title
`sanitizeRedirectUrl`/`isSafe()` fails to enforce same-origin, enabling open redirect via `/auth/exit-iframe?exitIframe=` - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts])

### Summary
`isSafe()` in `validate-redirect-url.ts` only checks that a redirect URL is not a `file://` URI, contains no whitespace, has no `//` in its pathname, and uses `http:`/`https:` as protocol — it never compares `url.origin` (or `url.host`) against the `domain` argument. Because `new URL(redirectUrl, domain)` returns the absolute URL itself whenever `redirectUrl` is already an absolute URL (ignoring `domain` as a base), an attacker-controlled absolute URL such as `https://attacker.example/steal` passes `isSafe()` and is returned unmodified by `sanitizeRedirectUrl`.

### Finding Description
`sanitizeRedirectUrl(domain, redirectUrl, options)` at [1](#0-0)  calls `isSafe(domain, redirectUrl, options.requireSSL)` and, if true, returns `new URL(redirectUrl, domain)`. `isSafe()` itself is defined at [2](#0-1) . It rejects `///` and whitespace, rejects `//` in the resolved pathname, and requires the protocol to be `https:`/`http:` — but it never checks `url.origin === new URL(domain).origin`. When `redirectUrl` is itself absolute (e.g. `https://attacker.example/steal`), the `WHATWG URL` constructor ignores the `domain` base entirely and parses the attacker string as-is, so all checks pass and `sanitizeRedirectUrl` returns a `URL` pointing at `attacker.example`.

This function is consumed by `renderAppBridge` in both the Remix and React Router packages: [3](#0-2) . The rendered response is:
```
<script>window.open("<destination>", "<target>")</script>
```
`redirectTo.url` reaches `renderAppBridge` from the unauthenticated `/auth/exit-iframe` route, whose `exitIframe` query parameter is used verbatim as the redirect destination, as shown by the test at [4](#0-3)  and the file-URI-rejection test at [5](#0-4) , confirming `exitIframe` value flows through to the `window.open(...)` script without any origin check other than `sanitizeRedirectUrl`. The exit-iframe endpoint requires no session token or HMAC — it's reachable by an unauthenticated client sending a crafted link (e.g. via phishing) that a logged-in merchant clicks while embedded (`embedded=1`), causing `window.open(attackerUrl, "_top")` to navigate the top-level admin frame away to attacker infrastructure.

### Impact Explanation
This is an open redirect from an authenticated/embedded admin context. An attacker crafts a link `https://<app-domain>/auth/exit-iframe?shop=<shop>.myshopify.com&embedded=1&host=<base64host>&exitIframe=https://attacker.example/phish`. If a merchant (already having a valid app session/JWT context or simply loading the embedded frame) opens this link, the `_top` target navigation takes over the entire browser tab and redirects it to attacker-controlled content, enabling phishing (e.g., a fake Shopify/App login page) with high believability since the URL bar previously showed the legitimate app domain. This matches Shopify's open-redirect impact class, though its severity is capped because it requires the victim to click a crafted link (not silently exploitable) and does not itself leak tokens or secrets.

### Likelihood Explanation
The exit-iframe route and `exitIframe` query parameter are attacker-reachable without authentication, secrets, or privileged access — an unprivileged party only needs to send/host a link. `sanitizeRedirectUrl` currently performs no origin/host allowlist check, only protocol/pathname pattern checks, so the bypass is deterministic and requires no timing or race conditions. The primary limiting factor is that a target must click the link (typical for open-redirect/phishing chains).

### Recommendation
In `isSafe()`, after parsing the URL, explicitly verify that the resolved URL's origin matches the origin of `domain` (or matches an explicit allowlist such as `admin.shopify.com`/`*.myshopify.com` for shopify-admin routes), rejecting any URL whose `origin` doesn't match rather than only checking protocol and pathname patterns:
```ts
const domainUrl = new URL(domain);
if (url.origin !== domainUrl.origin) {
  return false;
}
```

```typescript
function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
```

```typescript
export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}
```

```typescript
    const destination = sanitizeRedirectUrl(config.appUrl, redirectTo.url);

    const target = redirectTo.target ?? '_top';
```
