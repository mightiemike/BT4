### Title
Unbounded native recursion over attacker-influenced receipt DAG in `get_recursive_transaction_results` allows RPC-triggered stack-overflow crash - (File: chain/chain/src/chain.rs)

### Summary
`Chain::get_recursive_transaction_results` walks the receipt tree produced by a transaction using genuine Rust function-call recursion (one stack frame per receipt in the chain), with no depth limit. It is invoked from `get_partial_transaction_result_option` / `get_final_transaction_result`, which back the public `tx` / `tx_status` JSON-RPC methods reachable by any unprivileged RPC caller who knows a transaction hash (including their own transaction). This is analogous to CVE-2019-17450 (`find_abstract_instance` unbounded recursion over attacker-supplied DWARF data causing stack exhaustion and crash): here the "crafted graph" is the chain of `receipt_ids` an attacker's own contract call can generate, and the recursive walk that follows it has no depth cap, unlike the sibling `receipt_to_tx` RPC path which explicitly enforces `RECEIPT_TO_TX_MAX_DEPTH = 1000`.

### Finding Description
`get_recursive_transaction_results` (`chain/chain/src/chain.rs:3190-3207`) recurses once per outgoing `receipt_ids` entry of every outcome it visits:

```
fn get_recursive_transaction_results(...) -> Result<(), Error> {
    let outcome = ...;
    outcomes.push(...);
    for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
        let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
        self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
    }
    Ok(())
}
``` [1](#0-0) 

This is called from `get_final_transaction_result` [2](#0-1)  and `get_partial_transaction_result_option` [3](#0-2) , both of which are reachable from the `TxStatus` handler in `ViewClientActor::get_tx_status` [4](#0-3) , which serves the public `tx` / `tx_status` JSON-RPC methods [5](#0-4) .

The depth of this recursion is equal to the length of the receipt chain a transaction spawns (each function call/promise callback produces a new receipt whose id becomes the next hop). A contract can chain outgoing calls to itself (a "self-delay" pattern) to build an arbitrarily long linear chain limited only by attached gas, not by any explicit depth cap; the integration test `slow_test_self_delay` demonstrates that hundreds of chained receipts are already achievable within ordinary gas budgets [6](#0-5) . Nothing in `get_recursive_transaction_results` limits chain length, unlike the recently-hardened, functionally similar `receipt_to_tx` RPC lookup, which explicitly caps at `RECEIPT_TO_TX_MAX_DEPTH = 1000` and returns `DepthExceeded` instead of recursing unboundedly [7](#0-6) , exercised in `test_receipt_to_tx_depth_exceeded` [8](#0-7) . That the sibling code path added an explicit depth guard, while `get_recursive_transaction_results` was left unbounded, indicates the latter is the analogous unguarded recursion.

Rust's default behavior on stack overflow is to abort the process (it cannot be caught like a normal panic), so a sufficiently deep receipt chain processed by this recursive walk on the `ViewClientActor` thread will crash that thread/process outright — a hard denial of service triggered purely by an RPC query over a self-submitted transaction.

### Impact Explanation
A crash of the `ViewClientActor` (or the whole validator/RPC node process, depending on how stack overflow is handled at the OS/runtime level) constitutes a transaction/RPC-triggered halt of node availability, satisfying the "transaction-triggered halt" acceptance criterion. Because `ViewClientActor` also serves other RPC and internal chain-query functionality on validator/RPC nodes, repeated triggering could be used to degrandade or take down public RPC endpoints and, if run on validator-adjacent view-client infrastructure, impair chain observability/liveness for affected nodes.

### Likelihood Explanation
Exploitation requires only: (1) submitting a transaction whose contract creates a long chain of self-callback receipts (achievable with an ordinary FunctionCall/promise loop, well within max attached gas, as shown by existing test contracts reaching hundreds of hops), and (2) issuing a normal, unprivileged `tx`/`tx_status` RPC call for that transaction's hash. No special permissions, staking, or validator status are required — this is reachable by any transaction signer / RPC caller. The exact chain length needed to overflow a given thread's stack depends on frame size and configured stack size, which was not verified in this review (see Uncertainty below), but the unguarded nature of the recursion combined with demonstrably achievable chain depths in the hundreds makes this plausible without further engineering effort.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative (worklist/queue) traversal, mirroring the non-recursive rewrite already applied to `get_subtree_size` in `core/store/src/trie/trie_recording.rs` for the same "avoid stack overflow" reason [9](#0-8) , or add an explicit maximum-depth/maximum-outcome-count guard analogous to `RECEIPT_TO_TX_MAX_DEPTH` used in the `receipt_to_tx` RPC path [7](#0-6) .

### Proof of Concept
1. Deploy a contract that, on each call, issues a promise/FunctionCall receipt targeting itself (self-delay pattern), as already demonstrated to reach hundreds of chained receipts within normal gas limits by `slow_test_self_delay` [6](#0-5) ; tune parameters/attached gas to maximize chain length (bounded only by gas, not by any recursion-depth check).
2. Submit the transaction that kicks off this chain from an unprivileged account.
3. Once the chain begins executing, call the public `tx` / `tx_status` JSON-RPC method (or `get_final_transaction_result`/`get_partial_transaction_result_option` internally) for the transaction hash; this drives `get_recursive_transaction_results` to recurse once per receipt in the chain.
4. If the chain is long enough relative to the thread's stack size, the recursive walk overflows the stack, aborting the `ViewClientActor` thread/process — a transaction/RPC-triggered denial of service.

**Uncertainty:** I was not able to determine within this review the exact default stack size of the `ViewClientActor` thread or measure the per-frame stack cost of `get_recursive_transaction_results`, so I cannot confirm the precise chain length required to trigger an actual overflow versus merely a slow/expensive but survivable RPC call. This would need to be empirically verified (e.g., building a very long receipt chain and running the RPC against a debug/release build to observe stack usage) to fully confirm severity.

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }
