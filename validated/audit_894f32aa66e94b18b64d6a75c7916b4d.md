### Title
Attacker-triggerable exception during event-trigger dispatch in `blockTrigger` crashes the entire node - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
The reported CCIP issue is a bug class where unhandled exceptions in message-receipt processing propagate and block all subsequent processing until manual intervention. The closest reachable analog in java-tron is `Manager.blockTrigger()`, which wraps event-subscription/log-trigger dispatch (`postBlockFilter`, `postLogsFilter`, `postSolidityFilter`, `postBlockTrigger`, `postSolidityTrigger`) in a single `try { ... } catch (Exception e)` block that does not recover — it rethrows as a `TronError`, which by design forces `System.exit()` via the JVM's default uncaught-exception handler.

### Finding Description
`blockTrigger` is invoked from `pushBlock` right after a block (self-produced or received from the network/broadcast) has already been applied and persisted [1](#0-0) . Inside it, any `Exception` thrown while posting block/log/solidity/contract triggers to filters or the event-plugin queue is caught and converted into a `TronError` with `ErrCode.EVENT_SUBSCRIBE_ERROR`: [2](#0-1) 

`TronError` is explicitly documented as non-recoverable and intended to trigger `System.exit(int)` via `Thread.setDefaultUncaughtExceptionHandler`: [3](#0-2) 

While the lower-level `postContractTrigger` path defensively catches `Throwable` per individual trigger to avoid propagating exceptions [4](#0-3) , the sibling calls inside `blockTrigger` — `postBlockFilter`, `postLogsFilter`, `postSolidityFilter`, `postBlockTrigger`, `postSolidityTrigger` — are not individually hardened, and any single unexpected exception among them (e.g., an `EventPluginLoader`/`NativeMessageQueue` failure, or a serialization/NPE in `postSolidityTrigger`/`processTransactionTrigger` while handling block/transaction data derived from an incoming block or transaction) causes the whole node process to exit.

This mirrors the CCIP report's root cause: a receiving/processing path for externally-influenced data (`_ccipReceive` in the report; block/transaction application in java-tron) has downstream logic that can revert/throw, and that failure is not handled gracefully — it is escalated to a full halt of the pipeline instead of being isolated or retried.

### Impact Explanation
Because `blockTrigger` runs synchronously in the block-application path for every accepted block (produced locally or received via P2P/sync from any peer, including as a side effect of broadcast transactions being included in blocks), an exception surfaced here is far more severe than the original CCIP finding: instead of temporarily blocking one message lane until manual execution, it terminates the entire node process (`System.exit`), which is a complete denial of service for that node until it is manually restarted. If event subscription/JSON-RPC filters are enabled (a common production configuration for exchanges, wallets, and indexers), a single malformed but chain-valid block/transaction that trips an edge case in the trigger-dispatch code could crash every node with that configuration enabled simultaneously.

### Likelihood Explanation
Likelihood depends on whether an attacker can construct a transaction/block that reaches an untested edge case in `postBlockTrigger`, `postSolidityTrigger`, or `processTransactionTrigger` while `isJsonRpcHttpFullNodeEnable`/event-plugin subscriptions are active — this is plausible but not proven here, since the exact throwing condition (e.g. NPE) inside `postSolidityTrigger`/`processTransactionTrigger` was not confirmed by tracing all call paths (test coverage in `ManagerTest.blockTrigger` shows the crash-on-exception behavior is by design, not merely theoretical) [5](#0-4) . This is a design-level "fail-fast" choice (consistent with other `TronError` usages for unrecoverable infra failures like `DB_FLUSH`, `LEVELDB_INIT`), so it may be intentional rather than an oversight, similar to how the original team "risk accepted" the CCIP issue.

### Recommendation
Scope exception handling narrower inside `blockTrigger`: catch and log/skip failures in individual filter/trigger dispatch calls (as already done for `postContractTrigger`) rather than escalating any exception in the whole trigger-posting sequence to a full-node `System.exit`. Reserve `TronError`/process-exit for genuinely unrecoverable state (e.g., storage corruption), not for best-effort event/log subscription delivery which core consensus does not depend on.

### Proof of Concept
Not independently reproduced. The read-only static analysis confirms the code path exists and is exercised by `ManagerTest.blockTrigger`, which asserts that any exception thrown by `postBlockTrigger` propagates out of `blockTrigger` as a `TronError` with `EVENT_SUBSCRIBE_ERROR` [5](#0-4) , and `TronError`'s Javadoc confirms this results in `System.exit` [3](#0-2) . A concrete attacker-controlled trigger (specific malformed transaction/contract data causing an NPE inside `postSolidityTrigger` or `processTransactionTrigger`) was not identified within the scope of this analysis; further investigation of those two methods and `EventPluginLoader`'s native-queue path would be needed to construct an end-to-end exploit.

```java
  void blockTrigger(final BlockCapsule block, long oldSolid, long newSolid) {
    // post block and logs for jsonrpc
    try {
      if (CommonParameter.getInstance().isJsonRpcHttpFullNodeEnable()) {
        postBlockFilter(block, false);
        postLogsFilter(block, false, false);
      }

      if (CommonParameter.getInstance().isJsonRpcHttpSolidityNodeEnable()) {
        postSolidityFilter(oldSolid, newSolid);
      }

      if (EventPluginLoader.getInstance().getVersion() != 0) {
        lastUsedSolidityNum = newSolid;
        return;
      }

      // if event subscribe is enabled, post block trigger to queue (real-time, not removed)
      postBlockTrigger(block, false);
      // if event subscribe is enabled, post solidity trigger to queue
      // (also emits solidified-mode block/transaction triggers)
      postSolidityTrigger(newSolid);
    } catch (Exception e) {
      logger.error("Block trigger failed. head: {}, oldSolid: {}, newSolid: {}",
          block.getNum(), oldSolid, newSolid, e);
      throw new TronError(e, TronError.ErrCode.EVENT_SUBSCRIBE_ERROR);
    }
  }
```
