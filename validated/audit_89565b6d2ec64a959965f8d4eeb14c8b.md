### Title
Duplicate-address user-burn-support entries cause double coinbase minting in `calculate_miner_reward` - ([File: stackslib/src/chainstate/stacks/db/accounts.rs])

### Summary
`calculate_miner_reward` computes a user-burn-supporter's share of the coinbase by scanning `users` and *overwriting* (not accumulating) `this_user` whenever `user_support.address == participant.address`, while simultaneously excluding **every** entry that matches that address from `total_other`. When two user-burn-support rows for the same tenure share the same `address`, both rows are excluded from the denominator's "other" sum and both are assigned the *same* numerator (the last matching entry's burn), producing a coinbase share for each duplicate that no longer sums with the rest of the tenure's participants to the tenure's total coinbase.

### Finding Description
The invariant that should hold for every tenure is:

`coinbase_reward(miner) + Σ coinbase_reward(user_i) == coinbase` (the schedule's `coinbase` value, paid out exactly once per tenure).

In `calculate_miner_reward` (stackslib/src/chainstate/stacks/db/accounts.rs:804-844), the miner's share is computed correctly by simply summing all `users` burns: [1](#0-0) 

But for a *user* participant, the code does: [2](#0-1) 

`this_user` is **assigned**, not accumulated, on every iteration where `user_support.address == participant.address`; and any entry whose address matches `participant.address` is excluded from `total_other`. If two rows in `users` share the same `address` (call their burns `A1` and `A2`, with `A2` appearing later in the vector), then for **both** rows the loop ends with `this_user = A2` and `total_other` excludes both `A1` and `A2`. Consequently:

- Denominator for both duplicate rows: `burn_total = M + R + A2` (missing `A1`, where `M` = miner burn, `R` = sum of all non-duplicate users' burns).
- Numerator for both duplicate rows: `A2`.

Both duplicate-address participants therefore receive `coinbase * A2 / (M + R + A2)` each — the *same*, non-zero share — while the miner's own denominator (computed independently in the miner-branch) is the *correct* total `M + R + A1 + A2`. The two computations use inconsistent denominators, so the shares across all participants of a tenure no longer sum to 1. In the degenerate case `M = R = 0`, both duplicate entries each receive the *entire* coinbase (`A2/A2 = 1`), so a single tenure mints `2×` the intended coinbase.

`find_mature_miner_rewards` (stackslib/src/chainstate/stacks/db/accounts.rs:1044-1068) never checks the cross-participant invariant; it only asserts `parent_reward.total() == 0` per user, never `Σ coinbase == schedule.coinbase`: [3](#0-2) 

No other validation function (`check_tenure_tx`, `verify_signer_signatures`, `validate_vrf_seed`, MARF hashing, or the maturation-window logic) inspects the *content* of `MinerPaymentSchedule` rows for duplicate `address` values before maturation; the bug is purely an accounting error inside `calculate_miner_reward`, unrelated to VRF/sortition/signature validation.

**Caveat / unresolved point:** I was not able to fully confirm, within the available tool budget, whether the "user burn support" mechanism (the source of the `users`/`MinerPaymentSchedule` rows with `miner == false`) is still an actively creatable code path in the current (Nakamoto-era) chainstate, or whether it is a legacy feature from early epochs whose creation was disabled in later consensus rules. If user-burn-support registration is disabled in the currently active epoch, this bug is not presently exploitable on a live network, though the vulnerable code remains reachable for any chain history/replay that still contains such entries, and would become live again if user-burn-support were ever re-enabled. This should be verified against the burnchain-op validation code (`UserBurnSupportOp` acceptance rules) before final severity assignment.

### Impact Explanation
If reachable, this is a genuine coinbase over-mint / reward-theft bug: an attacker who can register two user-burn-support entries with the same `address` for a single tenure (e.g., two burn ops both naming the same payout address, with different `vtxindex`/burn amounts) can cause the chain to mint up to `2×` the intended coinbase for that tenure, split between the miner and the attacker's duplicated address, at the expense of correct accounting. This matches the "block-reward theft/double-payment" Critical category, since it is a protocol-level reward miscalculation, not merely a fee-bounded mispayment, and it is deterministically reproducible (not requiring majority stake — a single minority participant broadcasting two burn ops suffices).

### Likelihood Explanation
Preconditions: (1) the tenure must have at least one legitimate user-burn-support entry plus the attacker's two duplicate-address entries, or a purely-attacker set with `miner burn = 0`, `other users = 0`, and two duplicate-address entries to reach the 2× extreme; (2) the burnchain-op ingestion path must currently accept user-burn-support ops with attacker-chosen `address` fields and not deduplicate/reject repeated addresses within a tenure. Exploitation cost is bounded by the BTC fee needed to broadcast two burn transactions naming the same reward address — cheap relative to normal mining costs, and repeatable every tenure where user-burn-support is accepted. The severity is contingent on confirming user-burn-support ops are still creatable in the currently active epoch; this must be validated before treating this as an active, exploitable finding on mainnet today.

### Recommendation
Fix `calculate_miner_reward`'s user branch to accumulate rather than overwrite when matching addresses occur, and add an explicit invariant check in `find_mature_miner_rewards` that `miner_reward.coinbase + Σ user_rewards[i].coinbase == miner.coinbase` (using the schedule's un-fractioned coinbase amount, accounting for burn_total==0 shadow-block special case), panicking/erroring if the identity does not hold. Additionally, either reject/deduplicate `MinerPaymentSchedule` rows sharing the same `address` within a tenure at insertion time, or explicitly aggregate all rows for a given address into a single logical participant before running the reward-fraction computation.

### Proof of Concept
Rust integration test plan (to be added near existing tests in `stackslib/src/chainstate/stacks/db/accounts.rs`'s `#[cfg(test)] mod test`):
1. Construct a miner `MinerPaymentSchedule` with `burnchain_commit_burn = 0` and `coinbase = C` (nonzero).
2. Construct two user `MinerPaymentSchedule` entries, `U1` and `U2`, both with the **same** `address`, but with `burnchain_commit_burn = A1` and `A2` respectively (`A1 != A2`, both nonzero), same `coinbase = C`.
3. Call `StacksChainState::find_mature_miner_rewards`-equivalent logic (or directly call `calculate_miner_reward` for miner, `U1`, and `U2` against `users = [U1, U2]`) as done at accounts.rs:1044-1068.
4. Assert (equality that should hold): `miner_reward.coinbase + user_rewards[0].coinbase + user_rewards[1].coinbase == C`.
5. Show the assertion fails: with `A1=100, A2=200`, expect `user_rewards[0].coinbase == user_rewards[1].coinbase == C` (both 100%), and `miner_reward.coinbase == 0`, so the left side equals `2*C`, violating the equality and demonstrating the double-mint.
