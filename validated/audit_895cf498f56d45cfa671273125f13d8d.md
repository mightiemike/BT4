### Title
Inconsistent overflow-hardened arithmetic in `ResourceProcessor.increase()` — safe `BigInteger` math used for the operands but plain `+=` used to combine them - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
`ResourceProcessor` implements a "hardened calculation" mode (`hardenCalculation()` / `disableJavaLangMath()`, gated by `DynamicPropertiesStore.allowHardenResourceCalculation()`) that is meant to make bandwidth/energy usage accounting overflow-safe by replacing raw `long` arithmetic with checked `BigInteger`/`addExact` operations. In `increase(long lastUsage, long usage, long lastTime, long now, long windowSize)`, the two operands `averageLastUsage` and `averageUsage` are computed via the overflow-checked `divideCeilExact(BigInteger, BigInteger)` path when hardening is enabled, but they are then combined with a bare `averageLastUsage += averageUsage;` that never goes through any hardened/checked path, unlike the sibling `getUsage(oldUsage, oldWindowSize, newUsage, newWindowSize)` helper used by the other `increase(...)` overload, which does perform the equivalent addition inside a `hardenCalculation()`-guarded `BigInteger` computation.

### Finding Description
`ResourceProcessor.increase(long lastUsage, long usage, long lastTime, long now, long windowSize)`: [1](#0-0) 

When `hardenCalculation()` is true, `averageLastUsage` and `averageUsage` are each derived through `divideCeilExact`, which converts to `BigInteger` and calls `longValueExact()` — this throws `ArithmeticException` rather than silently wrapping on overflow: [2](#0-1) [3](#0-2) 

But the final combining step that folds the decayed `averageLastUsage` and `averageUsage` together is a plain, unchecked `long` addition regardless of the hardening flag: [4](#0-3) 

This is the same bug class as the GMX finding: intermediate values are protected from overflow by an explicit "safe/exact" arithmetic path, but a later step in the same computation chain reverts to raw arithmetic, defeating the purpose of hardening and producing inconsistent behavior depending on where in the pipeline an overflow occurs. Contrast this with the other overload, `increase(AccountCapsule, ResourceCode, ...)`, where the analogous combination of `averageLastUsage` and `averageUsage` is delegated to `getUsage(oldUsage, oldWindowSize, newUsage, newWindowSize)`, which *does* check `hardenCalculation()` and performs the addition/multiplication in `BigInteger` before converting back with `longValueExact()`: [5](#0-4) 

The 5-argument `increase(...)` overload (containing the unguarded `+=`) is invoked directly by `recovery(AccountCapsule, ResourceCode, long, long, long)`, a public method used in bandwidth/energy usage recovery, itself reachable from ordinary transaction processing via `BandwidthProcessor`: [6](#0-5) 

### Impact Explanation
If `allowHardenResourceCalculation()` is enabled specifically to guarantee that resource-usage accounting either produces a correct value or throws (rather than silently wrapping/corrupting state), the unguarded `+=` at line 76 breaks that guarantee for this particular code path. In the unlikely event `averageLastUsage + averageUsage` overflows a `long` (both are `precision`-scaled usage values, so this requires usage values near `Long.MAX_VALUE`), the result will silently wrap to a negative or incorrect value instead of throwing `ArithmeticException` as the hardening mode is designed to do elsewhere in the same class. This could corrupt bandwidth/energy usage accounting (resource and reward accounting) rather than deterministically failing/cancelling the operation, which is a worse outcome than the GMX case (silent corruption vs. explicit rejection).

### Likelihood Explanation
Low likelihood: reaching an overflow at this specific addition requires usage/`precision`-scaled values to already be extremely close to `Long.MAX_VALUE`, which under normal bandwidth/energy accounting bounds (constrained by chain parameters and account limits) is not attainable through ordinary transaction flows. This mirrors the sponsor's own assessment in the source GMX report that the bricking/overflow scenario, while theoretically possible, has quite small likelihood.

### Recommendation
Make the addition in `increase(long lastUsage, long usage, long lastTime, long now, long windowSize)` honor the same `hardenCalculation()` guard as `getUsage(oldUsage, oldWindowSize, newUsage, newWindowSize)`, e.g. by routing `averageLastUsage += averageUsage` through `StrictMathWrapper.addExact(...)` (or an equivalent `BigInteger`-checked helper) when hardening is enabled, so that overflow handling is consistent across the entire computation chain rather than only at some sub-steps.

### Proof of Concept
Not independently reproducible without controlling account usage state to reach near-`Long.MAX_VALUE` values (which the runtime does not allow through normal transaction flows); the finding is based on direct code-path analysis of `ResourceProcessor.increase(long, long, long, long, long)` at lines 50–78 versus the guarded equivalent at lines 293–300, showing the inconsistency in applying the hardened-arithmetic guarantee.

  protected long increase(long lastUsage, long usage, long lastTime, long now, long windowSize) {
    long averageLastUsage;
    long averageUsage;
    if (hardenCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }

  private long getUsage(long oldUsage, long oldWindowSize, long newUsage, long newWindowSize) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(oldUsage).multiply(BigInteger.valueOf(oldWindowSize))
          .add(BigInteger.valueOf(newUsage).multiply(BigInteger.valueOf(newWindowSize)));
      return bi.divide(BigInteger.valueOf(precision)).longValueExact();
    }
    return (oldUsage * oldWindowSize + newUsage * newWindowSize) / precision;
  }
