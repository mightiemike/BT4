I confirmed `action_delete_key` in `runtime/runtime/src/access_keys.rs` performs no check on the account's staking (`locked`) status — it only verifies the key exists before removing it. This is the reachable analog to the veRWA finding: a single self-inflicted transaction (deleting one's own last access key) can create a state that becomes permanently unrecoverable, mirroring the "undelegate is blocked by an unsatisfiable check" pattern.

### Title
Deleting the last access key while staked permanently locks the account's staked balance - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
An account owner who submits a `DeleteKey` action removing their last access key while the account still has a nonzero `locked` (staked) balance loses all ability to ever unstake or delete the account, permanently freezing the staked funds. This mirrors the veRWA `[H-04]` pattern: an exit path (`withdraw`/`undelegate` there, `Stake(0)`/`DeleteAccount` here) is gated by a condition (delegatee lock not expired / `locked == 0`) that can never be satisfied again once the triggering user action (letting the lock expire / deleting the last key) has occurred, because the same action that could clear the condition is no longer executable.

### Finding Description
`action_delete_key` in `runtime/runtime/src/access_keys.rs` only checks that the target access key exists (`DeleteKeyDoesNotExist`) before removing it via `delete_regular_key`/`delete_gas_key`; it performs no check on the account's `locked` balance or on whether this is the account's last remaining access key. [1](#0-0) 

Separately, `action_delete_account` explicitly forbids deleting an account while it has staked/locked balance, returning `ActionErrorKind::DeleteAccountStaking`: [2](#0-1) [3](#0-2) 

The only way `locked` can return to zero is via a new `Stake` proposal (typically `stake = 0`) submitted and signed by the account, which is authorized through the normal transaction-verification path requiring a matching access key (`get_signer_and_access_key` → `AccessKeyNotFound` if none exists): [4](#0-3) 

Documentation explicitly acknowledges that an account with zero access keys has "no owner who can run transactions from its behalf": [5](#0-4) 

If a signer submits `DeleteKey` for their own last access key while `account.locked() > 0` (e.g., forgetting they are still staked, or believing an unstake transaction already succeeded), the resulting state has: (1) no access key to ever sign a future `Stake` proposal that would zero `locked`, and (2) `DeleteAccountStaking` blocking `DeleteAccount` as long as `locked() > 0`. The account and its staked balance become permanently unreachable — the exact "chicken-and-egg" lock pattern from the veRWA report, where the state needed to exit (`locked == 0`) can never be produced because the only action that could produce it requires the very authorization that was just destroyed.

### Impact Explanation
This results in permanently frozen funds: the account's `locked` balance can never be unstaked or reclaimed by anyone (not the owner, not any relayer, since meta-transactions/`DelegateAction` also require a valid, existing access key to authorize the `Stake` action), and the account itself can never be deleted to recover the `amount` portion either, since `DeleteAccountStaking` blocks it. This is a single, unprivileged, user-initiated transaction on an ordinary account — reachable purely through the standard `DeleteKey` action — that causes concrete, permanent value loss.

### Likelihood Explanation
This requires the account owner to delete their own last access key while their account still has a nonzero locked/staked balance. This is plausible in practice: users delete "unused" keys via wallets, key-rotation tooling, or scripts without checking `locked` first, especially when relying on eventual stake-return timing across the 3-epoch window and not verifying it completed before removing keys. The `RuntimeSpec/Actions.md` DeleteKeyAction documentation lists only `DeleteKeyDoesNotExist` and `StorageError` as possible failures — there is no documented or enforced safeguard against this scenario. [6](#0-5) 

### Recommendation
Add a check in `action_delete_key` (or in a pre-action validation pass) that rejects removing an account's last access key while `account.locked() > 0`, analogous to the existing `DeleteAccountStaking` guard on `DeleteAccountAction`. Alternatively, require that any `Stake(0)` unstake proposal fully settle (i.e., `locked` returns to zero) before the last access key on an account can be deleted, surfaced as a new `ActionErrorKind` (e.g. `DeleteKeyWouldLockStake`).

### Proof of Concept
1. Create an account with a single `FullAccess` key and submit `Stake { stake: N, public_key }` to become/remain a validator; `account.locked()` becomes `N` per `action_stake` in `runtime/runtime/src/actions.rs:58-109`. [7](#0-6) 
2. Before submitting an unstake (`Stake { stake: 0 }`), submit `DeleteKey { public_key }` for that same, only, access key. `action_delete_key` succeeds unconditionally since the key exists and no staking check is performed. [8](#0-7) 
3. Attempt any subsequent transaction from the account (including an unstake `Stake(0)`) — it fails at signature/access-key verification with `AccessKeyNotFound`, since no key remains.
4. Attempt `DeleteAccount` from any other authorized party is not possible (no key exists to sign it either), and even if it were, it would fail with `DeleteAccountStaking` while `locked() > 0`. [2](#0-1) 
5. The account's `locked` balance is now permanently frozen: unreachable by any future transaction and un-deletable.

pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {
        if let Some(gas_key_info) = access_key.gas_key_info() {
            delete_gas_key(
                config,
                state_update,
                account,
                result,
                account_id,
                &delete_key.public_key,
                &access_key,
                gas_key_info,
            )?;
        } else {
            delete_regular_key(
                &config.fees,
                state_update,
                account,
                account_id,
                &delete_key.public_key,
                &access_key,
            );
        }
    } else {
        result.result = Err(ActionErrorKind::DeleteKeyDoesNotExist {
            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),
        }
        .into());
    }
    Ok(())
}

    let increment = stake.stake.saturating_sub(account.locked());

        if account.locked().is_zero() && stake.stake.is_zero() {

                    account_id: account_id.clone(),
                    stake: stake.stake,

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
