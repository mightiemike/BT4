### Title
Unbounded concurrent execution of expensive `GetAssetIssueListByNameServlet` requests due to QPS-only rate limiting (no concurrency cap) - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueListByNameServlet.java])

### Finding Description
`GetAssetIssueListByNameServlet` extends `RateLimiterServlet`, whose `service()` method gates every request behind two token-bucket style checks: a per-endpoint limiter (`DefaultBaseQqsAdapter` by default, or `QpsRateLimiterAdapter`/`IPQPSRateLimiterAdapter` if configured) and the global `GlobalRateLimiter.acquirePermit(...)` [1](#0-0) . These adapters are QPS (rate-over-time) limiters that admit bursts as long as the aggregate rate stays within budget; they do not track or cap the number of requests concurrently in flight. The only adapter in this codebase designed to cap concurrency is `GlobalPreemptibleAdapter`, which is opt-in per servlet via `Args.getInstance().getRateLimiterInitialization().getHttpMap()` and defaults to `DefaultBaseQqsAdapter` when no entry exists for a servlet [2](#0-1) . `GetAssetIssueListByNameServlet` has no such entry configured (only commented-out examples exist in reference config), so it always falls back to the QPS-only `DefaultBaseQqsAdapter`, and `perEndpointAcquired`/`acquireResource` checks impose no bound on simultaneous execution [3](#0-2) . Once `acquireResource` is true, `super.service(req, resp)` runs `doGet`/`doPost`, which calls `wallet.getAssetIssueListByName(...)`, an operation that scans the asset issue store to collect all assets matching a given name (asset names were historically non-unique in TRC10 prior to same-token-name enforcement, requiring a linear scan rather than a single key lookup) [4](#0-3) . Because concurrency is unbounded, an attacker can open C simultaneous connections, each independently satisfying the QPS token bucket (since QPS limiters only throttle rate, not concurrency), and have all C requests execute the expensive store scan at the same time.

### Impact Explanation
Concurrent execution of many simultaneous full-store scans against `AssetIssueStore`/`AssetIssueV2Store` can saturate Jetty's worker thread pool and amplify RocksDB read I/O and CPU well beyond what the steady-state QPS budget was designed to bound, degrading availability of the HTTP API for legitimate users (service-level denial of service) without ever tripping the QPS limiter.

### Likelihood Explanation
This requires no privileges beyond standard public HTTP API access (the `/wallet/getassetissuelistbyname` endpoint is unauthenticated by default). The attacker only needs to open C concurrent long-lived HTTP connections, each within the per-IP/global QPS budget (e.g., one request per connection every few seconds), which is trivial to script. The lack of any `GlobalPreemptibleAdapter` configuration for this servlet in the reference config means this exposure exists in a default/unmodified deployment.

### Recommendation
Configure a `GlobalPreemptibleAdapter` (or an equivalent concurrency-capping strategy) for `GetAssetIssueListByNameServlet` (and other iterator-scan-based list endpoints) in `RateLimiterInitialization`'s http map by default, so that the number of concurrently executing requests is bounded independent of the QPS token bucket. Alternatively, add explicit semaphore-based concurrency limits inside the servlet or cache/paginate the underlying store scan.

### Proof of Concept
Java integration test plan:
1. Populate `AssetIssueStore`/`AssetIssueV2Store` with a large number (e.g., 100k) of asset issue entries sharing overlapping name prefixes so `wallet.getAssetIssueListByName` must scan a large portion of the store.
2. Start the full node HTTP API service with default `reference.conf` (no `GlobalPreemptibleAdapter` entry for `GetAssetIssueListByNameServlet`).
3. Launch C (e.g., 200) concurrent `HttpURLConnection`/`OkHttp` clients each issuing `GET /wallet/getassetissuelistbyname?value=<hex>` at a rate individually within the per-IP QPS limit (e.g., 1 request every 2 seconds per connection, well under any configured QPS threshold).
4. Assert that:
   - All C requests are individually accepted by `RateLimiterServlet.service` (`acquireResource == true`, HTTP 200, not the "lack of computing resources" error).
   - Measured p99 latency and Jetty QueuedThreadPool active-thread count scale non-linearly with C (e.g., latency degrades by >10x when C goes from 10 to 200), demonstrating that QPS accounting did not bound the concurrent cost despite passing every individual rate check.

  static IRateLimiter buildAdapter(String cName, String params, String name) {
    Class<? extends IRateLimiter> c = ALLOWED_ADAPTERS.get(cName);
    if (c == null) {
      throw rateLimiterInitError(cName, params, name,
          new IllegalArgumentException("unknown rate limiter adapter; allowed="
              + ALLOWED_ADAPTERS.keySet()));
    }
    try {
      return c.getConstructor(String.class).newInstance(params);
    } catch (Exception e) {
      throw rateLimiterInitError(cName, params, name, e);
    }
  }
