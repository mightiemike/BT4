### Title
Webhook Shop-Domain and Topic Headers Excluded From HMAC Signature Enable Cross-Tenant Webhook Spoofing - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
Shopify webhook authenticity in `shopify-api` is verified by computing an HMAC over the raw request body only. The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-Api-Version` headers are read and trusted *after* HMAC validation succeeds, but are never included in the HMAC computation itself. Because the HMAC secret (`apiSecretKey`) is shared across every shop that installs the app, any merchant who has installed the app can legitimately obtain a valid `(rawBody, hmac)` pair for their own store's webhook deliveries and then replay that exact body/HMAC pair to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to point at a different shop or a more sensitive topic. This is directly analogous to the reported issue where `encryptedOutputs` was excluded from `callDataHash`: data that determines how a request is subsequently processed/attributed is left outside the integrity check.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` validates the HMAC only against `rawBody`: [1](#0-0) 

The HMAC comparison itself operates purely on `rawBody`: [2](#0-1) 

After the HMAC succeeds, `checkWebhooksHeaders`/`checkEventsHeaders` extract `topic`, `domain`, `apiVersion`, and `webhookId` straight from unauthenticated headers and mark the payload `valid: true` with those values: [3](#0-2) 

Downstream framework adapters (e.g., `shopify-app-remix`, `shopify-app-react-router`) trust `check.domain` to look up/create the offline session for that shop and `check.topic` to route to the merchant's webhook handler, using the attacker-controlled `rawBody` as the payload: [4](#0-3) 

Because the apiSecretKey used to compute the HMAC is the single app-wide client secret (not per-shop), any shop that has installed the app receives genuinely valid `(body, hmac)` pairs from Shopify for its own webhook events. Since `domain`/`topic`/`webhookId` are not bound into the HMAC, an attacker who owns/controls one installed shop can capture such a pair and resend it directly to the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` (pointing at any other shop that has the app installed) and/or a modified `X-Shopify-Topic` (e.g. selecting a topic whose handler performs destructive/sensitive actions, such as `app/uninstalled`, `shop/redact`, `customers/redact`, or `customers/data_request`). The HMAC check still passes because it only ever validated the body content, not the header metadata that determines attribution.

### Impact Explanation
This allows a single malicious merchant (an unprivileged actor with respect to any other tenant) to:
- Inject forged webhook payloads that the app attributes to a **different, victim shop**, causing the app's registered handler to run business logic (data mutation, GDPR deletion routines, uninstall cleanup, billing changes, etc.) against the victim's stored offline session/access token.
- Select an arbitrary webhook `topic` independent of the body content actually delivered, causing topic/payload-schema mismatches that a handler may not defensively validate, potentially leading to data corruption, incorrect state transitions, or abuse of mandatory compliance webhooks (`shop/redact`, `customers/redact`) against shops the attacker does not control.

This is a genuine cross-tenant integrity issue reachable from an anonymous/unauthenticated HTTP POST to the app's webhook endpoint, using only a valid body+HMAC pair the attacker legitimately obtained for their own shop.

### Likelihood Explanation
Likelihood is moderate-to-high in apps that:
1. Expose their webhook endpoint publicly (required for Shopify to deliver webhooks) — this is inherent in all embedded apps.
2. Have registered handlers for multiple topics (particularly GDPR/mandatory compliance topics, which every public app must implement) that perform sensitive actions based solely on `check.domain`/`check.topic` without additional verification (e.g., checking that the payload shape matches the claimed topic).

Any merchant with a paid/free install of the app can generate the required legitimate `(body, hmac)` pair themselves by simply triggering an event in their own store and capturing the webhook delivery, then modifying the `Domain`/`Topic` headers on replay — no cryptographic secret needs to be recovered.

### Recommendation
Bind the security-relevant metadata into the authenticity check instead of trusting bare headers after a body-only HMAC check:
- Include `topic`, `domain` (shop), `webhookId`, and `apiVersion` in the HMAC-covered data (e.g., HMAC over `headers + body` or a canonical string containing these fields plus the body), similar to how Shopify signs OAuth/App Proxy query parameters.
- Alternatively/additionally, cross-check the `domain` header against the shop associated with the actual installed session before acting on the payload, and validate that the payload body is structurally consistent with the claimed `topic` before invoking handlers, especially for mandatory GDPR topics.
- Reject webhook requests whose `domain` does not match an already-established relationship for the delivering shop when replay/tenant-confusion would otherwise be possible.

### Proof of Concept
1. App developer installs their own test shop `attacker-shop.myshopify.com`, which shares the same app `apiSecretKey` as every other shop that installs the app.
2. Trigger any webhook event (e.g., `products/create`) in `attacker-shop`, and capture the resulting HTTP request Shopify sends to the app, including `rawBody` and the `X-Shopify-Hmac-Sha256` header — this is a valid `(rawBody, hmac)` pair validated by: [5](#0-4) 
3. Resend that exact `rawBody` and `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` and/or `X-Shopify-Topic` to a different registered topic (e.g. `app/uninstalled`).
4. `validateFactory` reports `valid: true` (the HMAC check only validates `rawBody`, per `validate.ts` lines 56–61 and `hmac-validator.ts` lines 168–201), and `checkWebhooksHeaders` returns the forged `domain`/`topic` as trusted fields (`validate.ts` lines 99–146).
5. `authenticateWebhookFactory` (remix/react-router) loads/creates the offline session for `victim-shop.myshopify.com` and invokes the app's handler for the forged topic using the attacker-supplied body as payload: [6](#0-5) 

Note: I could not find any additional cross-check in the codebase (within index coverage) that ties the `domain`/`topic` header values back into the signed payload or otherwise verifies they match the actual delivering shop, confirming the gap.

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}
