### Title
`WithdrawFromGasKeyAction` reachable through `Delegate`/`DelegateV2` meta-transactions bypasses its "transactions-only" access-control restriction, allowing unauthorized draining of gas-key balances - ([File: runtime/runtime/src/access_keys.rs])

### Summary
This maps to the same bug class as the Argo report: two components split a privileged operation, where the intended access-control restriction is documented/enforced conceptually at one layer but the underlying state-mutating function is reachable through a second path that does not (or did not) re-check the restriction. In nearcore, `WithdrawFromGasKeyAction` is explicitly documented as "must only be available via transactions, not via contract execution" [1](#0-0)  — analogous to `argo_liquidate`'s wrapper being the only intended caller of the underlying engine primitive. However, the actual state mutation lives in `action_withdraw_from_gas_key`, which is dispatched generically from `apply_action` for any `Action::WithdrawFromGasKey`, including one nested inside an `Action::Delegate`/`DelegateV2` (meta-transaction) receipt [2](#0-1) .

### Finding Description
`action_withdraw_from_gas_key` moves balance from a gas key to the owning account without any check on how the action was delivered (direct transaction vs. delegated/meta-transaction receipt) [3](#0-2) . The restriction that this action is transaction-only is only a documentation-level intent on the action type [1](#0-0) , and the codebase needed a dedicated protocol feature, `RejectWithdrawFromGasKeyInDelegate`, to actually enforce it at validation time in `action_validation.rs` (referenced 4 times) and gated in `core/primitives-core/src/version.rs`. Before this protocol feature activates, a delegate action embedding `WithdrawFromGasKeyAction` is admitted and executed, moving funds out of the gas key exactly like a direct transaction would — this is confirmed by an explicit regression test that documents the pre-upgrade exploit and drains the gas key balance:

```
// Before the upgrade the nested withdrawal is admitted and moves balance out
// of the gas key, which is the hole this rule closes.
``` [4](#0-3) 

This is structurally identical to the Argo pattern: the "wrapper" (direct-transaction-only intent / access-control capability) is bypassed by reaching the same state-mutating primitive (`action_withdraw_from_gas_key`) through an alternate path (`Delegate`/`DelegateV2`) that the underlying function does not itself gate.

### Impact Explanation
If this protocol feature (`RejectWithdrawFromGasKeyInDelegate`) is not yet active on a given protocol version (i.e., on any chain still running below its activation version, or during the exact upgrade boundary), a relayer or any party constructing a `Delegate` action containing `WithdrawFromGasKeyAction` can move NEAR out of a gas key's balance into the owning account via a meta-transaction path that was never intended to allow this — this is unauthorized value movement matching the "concrete unauthorized value movement" acceptance criterion. It also creates state-transition divergence risk across nodes at different upgrade heights if the feature-gate logic is inconsistent, though the primary risk is direct fund movement outside the intended authorization model for gas keys.

### Likelihood Explanation
This requires only a single signer capable of building a `Delegate`/`DelegateV2` action (any account holding a gas key and a relayer willing to submit it) — fully reachable from an unprivileged transaction sender via ordinary meta-transaction submission, with no special node/validator privileges required. The very existence of a dedicated protocol feature and regression test to close this exact hole indicates it was a real, exploitable gap prior to the fix; likelihood is high on any protocol version prior to `RejectWithdrawFromGasKeyInDelegate`'s activation and near the upgrade boundary (the test itself continues submitting across the boundary to check nothing crashes, implying tolerance for receipts created pre-upgrade completing post-upgrade).

### Recommendation
Ensure `RejectWithdrawFromGasKeyInDelegate` is unconditionally enforced at both `validate_actions_with_mode`/`action_validation.rs` (for new receipts) and reject any attempt to reintroduce `WithdrawFromGasKeyAction` inside `Delegate`/`DelegateV2` on all currently supported protocol versions; audit for any other action types whose access model is documented as "transaction-only" (e.g., similar restrictions in `core/primitives/src/action/mod.rs`) to confirm each has an equivalent receipt-level validation gate rather than relying on caller intent/documentation alone, mirroring the general lesson from the Argo advisory that access control must be enforced at the lowest-level state-mutating function, not only at an outer wrapper.

### Proof of Concept
1. On a protocol version below the activation of `RejectWithdrawFromGasKeyInDelegate`, create an account with a gas key and fund it via `TransferToGasKeyAction`.
2. Construct a `Delegate`/`DelegateV2` action whose inner action list contains `WithdrawFromGasKeyAction { public_key: <gas_key>, amount: <balance> }`, signed by the sender and submitted through a relayer.
3. Observe the delegate receipt executes successfully and the gas key balance is drained into the owning account balance — reproduced exactly in the repository's own regression test `test_reject_delegated_gas_key_withdraw_protocol_upgrade`, which asserts `balance_after == balance_before - WITHDRAW_AMOUNT` for the pre-upgrade delegated withdrawal [5](#0-4) .

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
```
