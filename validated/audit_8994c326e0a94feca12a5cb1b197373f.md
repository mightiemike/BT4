### Title
Unbounded recursive receipt-outcome traversal risks stack-overflow crash on transaction-status queries - ([File: chain/chain/src/chain.rs])

### Summary
`Chain::get_recursive_transaction_results` walks the receipt DAG of a transaction by recursing once per receipt id with **no depth limit and no cycle/size guard**, unlike the analogous `ReceiptToTx` lookup path that was hardened with an explicit `MAX_DEPTH = 1000` check. This mirrors the BIND9 CVE-2023-2911 bug class: a resource-consuming lookup that recurses per unit of a caller-influenced chain, with no bound, eventually overflowing the call stack and terminating the process.

### Finding Description
`get_recursive_transaction_results` fetches the outcome for a receipt id, appends it, and then recurses into every one of its `receipt_ids` children: [1](#0-0) 

It is the backing implementation of `get_final_transaction_result`, which builds the `FinalExecutionOutcomeView` returned to RPC/API callers for a given `transaction_hash`: [2](#0-1) 

There is no depth ceiling on this recursion — the traversal depth equals the length of the receipt chain the transaction's execution produced (e.g. a chain of self cross-contract calls / promise callbacks). By contrast, the codebase already has a hardened analog for a structurally identical problem: `GetReceiptToTx` resolution walks a similar parent-chain and explicitly enforces `MAX_DEPTH = 1000`, returning `DepthExceeded` instead of recursing unboundedly: [3](#0-2) [4](#0-3) 

No equivalent bound exists for `get_recursive_transaction_results`/`get_final_transaction_result`. An unprivileged transaction sender can construct arbitrarily long linear receipt chains using self cross-contract-call patterns — the test contract itself ships a helper explicitly designed to "delay completion of the receipt for as long as possible through self cross-contract calls," recursing until gas is nearly exhausted: [5](#0-4) 
and this pattern is exercised/measured in existing tests showing tens to hundreds of chained receipts per transaction is achievable within gas limits: [6](#0-5) 

If a node later serves a transaction-status query for such a transaction hash (via `tx`, `EXPERIMENTAL_tx_status`, or `TxStatusRequest`), it will attempt to assemble the outcome tree, invoking the unbounded recursive walk.

### Impact Explanation
A Rust stack overflow is not a catchable panic — the runtime aborts the process on overflow. If a sufficiently deep/self-referential receipt chain can be produced (via chained self-promise calls, which the contract API and existing test utilities in this codebase already demonstrate), a caller can craft a transaction whose descendant-receipt walk exceeds the calling thread's stack, crashing the RPC/view-client serving process for any node that later processes a `tx_status`-style query for that transaction hash. This is a transaction-triggered halt reachable by an ordinary RPC caller with no special privileges, matching the accepted impact class (transaction-triggered halt).

### Likelihood Explanation
Medium. The recursion depth is gas-bounded per hop (each self-call spends prepaid gas), so a single transaction's promise chain is limited by total attached gas (empirically ~50–220+ hops per the existing `slow_test_self_delay`/`test_evil_deep_recursion` tests). Whether that specific bound is sufficient to overflow a given thread's stack is not something I could fully verify without runtime stack-size configuration data; however, the complete absence of any depth guard here — in a codebase that explicitly added a `MAX_DEPTH` guard for the structurally identical `ReceiptToTx` traversal — indicates this specific function was not covered by that fix and represents a real, uncapped growth vector as receipt DAGs can also fan out (not just chain linearly), increasing total node count that must be visited/recursed over for a single `tx_status` request.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative (worklist/stack-based) traversal, or add an explicit maximum depth/total-outcome-count guard analogous to the `MAX_DEPTH`/`DepthExceeded` pattern already used for `GetReceiptToTx`, returning a bounded error instead of recursing without limit.

### Proof of Concept
1. Deploy the test contract exposing `max_self_recursion_delay` (or any contract emitting a long linear self-promise chain), and submit a transaction that invokes it with maximum prepaid gas, producing a long chain of receipts.
2. Repeat/compose such calls (e.g., across multiple transactions or by maximizing per-hop chain length as in `test_evil_deep_recursion`) to maximize the depth of the resulting receipt DAG.
3. Query `tx_status`/`EXPERIMENTAL_tx_status` (or send `TxStatusRequest`) for the originating transaction hash against a node tracking that shard.
4. The view client invokes `Chain::get_final_transaction_result` → `get_recursive_transaction_results`, recursing once per receipt in the chain with no depth bound; sufficiently deep chains crash the serving process via stack overflow.

Note: I could not fully verify in the time available whether `get_tx_status`'s primary path (`get_partial_transaction_result_option`) also funnels into this same unbounded recursive function or whether it is only reached via a secondary path (e.g. `get_transaction_result_with_receipt`/`fetch_receipt=true`, or the `runtime_user.rs`/test-only call sites). This should be confirmed by tracing all callers of `get_final_transaction_result` before treating exploitability as fully confirmed.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}

/// Test delaying the conclusion of a receipt for as long as possible through the use of self
/// cross-contract calls.
#[test]
fn slow_test_self_delay() {
    let node = setup_test_contract(near_test_contracts::rs_contract());
    let res = node
        .user()
        .function_call(
            "alice.near".parse().unwrap(),
            "test_contract.alice.near".parse().unwrap(),
            "max_self_recursion_delay",
            vec![0; 4],
            MAX_GAS,
            Balance::ZERO,
        )
        .unwrap();

    // The exact expected depth varies depending on the set of enabled features.
    // When test_features are enabled, the test contract becomes larger and the calls to it are more expensive.
    // When nightly is enabled, the gas costs change a bit.
    // The test makes sure that the depth is within the expected range, but it doesn't check an exact value
    // to avoid having separate cases for every possible combination of features.
    let min_expected_depth = 56;
    // The upper limit has been recently bumped to 221 from the previous value of 62 after the
    // adjustment of a function call gas costs.
    let max_expected_depth = 221;
    match res.status {
        FinalExecutionStatus::SuccessValue(depth_bytes) => {
            let depth = u32::from_be_bytes(depth_bytes.try_into().unwrap());
            assert!(
                depth >= min_expected_depth,
                "The function has recursed fewer times than expected: {depth} < {min_expected_depth}",
            );
            assert!(
                depth <= max_expected_depth,
                "The function has recursed more times than expected: {depth} > {max_expected_depth}",
            );
        }
        _ => panic!("Expected success, got: {:?}", res),
    }
}
