### Title
Non-deterministic EIP-7594 sidecar admission window based on wall-clock time causes tx-pool acceptance to diverge from block validity - (File: `crates/transaction-pool/src/validate/eth.rs`)

### Summary
`EthTransactionValidator::allow_7594_sidecars` decides whether an EIP-7594 (v1) blob sidecar is accepted into the pool *before* Osaka activates, using `SystemTime::now()` instead of any chain-state-derived value. Depending on when each individual node happens to poll wall-clock time relative to the last pre-Osaka slot, the same transaction can be accepted by one node's pool and rejected by another's, or accepted/rejected inconsistently on the same node across repeated calls.

### Finding Description
`validate_eip4844` gates EIP-7594 sidecars in the last pre-Osaka slot through `allow_7594_sidecars`: [1](#0-0) 

`allow_7594_sidecars` is implemented as: [2](#0-1) 

The `tip_timestamp` here comes from the actual chain tip and is deterministic, but the second branch's condition — `current_timestamp >= tip_timestamp.saturating_add(4)` — reads `SystemTime::now()`, a value that is not derived from any consensus-agreed input (block, header, or fork schedule). It is purely a function of the wall clock of the machine executing `validate_eip4844` at the moment of call.

This means:
- The exact same pooled transaction, submitted at the exact same tip, can be `Valid` on node A (whose local clock has passed the 4-second mark) and `Invalid` on node B (whose local clock has not), purely due to clock skew, scheduling jitter, or NTP drift — not due to any property of the transaction or the chain state.
- The same node polling this function twice in quick succession around the 4-second boundary can flip the same transaction between accepted and rejected states.

This is the direct analog of the H-5 report's core defect: a state-transition boundary check that denies (or grants) an action based on an incidental, non-authoritative signal (wall-clock "now") rather than the deterministic state that should govern the decision (the block/tip that is actually being built against). In the Carapace case it was `poolStatus` transitioning from `Active` to `LateWithinGracePeriod` one second after expiry causing a wrongful denial; here it's `SystemTime::now()` crossing a 4-second threshold causing a wrongful, non-reproducible admission/rejection of a blob sidecar format.

Contrast this with the deterministic decision that block-building code itself makes for the *same* concern using `is_osaka` computed from the block's own timestamp: [3](#0-2) 

Because the payload builder's decision is deterministic (based on the payload's own timestamp) while the pool's admission gate is not (based on wall clock), it's possible for the pool to admit an EIP-7594-sidecar transaction that the payload builder would then reject when attempting to include it (`UnexpectedEip7594SidecarBeforeOsaka`), or vice versa to reject a transaction in the pool that would have been perfectly fine to include. This is exactly the "pool admission diverging from block validity" impact category.

### Impact Explanation
This falls in the High-severity category of "pool admission diverging from block validity" and non-deterministic execution between otherwise-equivalent code paths (here, pool validation vs. payload building validity, both nominally checking the same Osaka/sidecar-format rule but using two different clocks — one deterministic, one not). Concretely:
- Transactions can be non-deterministically stuck oscillating between pool acceptance/rejection near the fork boundary depending on machine clock behavior, not on any protocol-defined event.
- A transaction accepted into one node's pool near this window may never be propagable/includable by other nodes whose local clocks disagree, or may be rejected later during block building despite having passed pool validation, wasting resources and creating unpredictable UX exactly like the "buyer denied renewal one second after expiry" scenario, except here it's the reverse of "should have been let in but wasn't" as well as "let in when it shouldn't have been."

### Likelihood Explanation
This code path executes deterministically for every EIP-4844 transaction with a v1 sidecar received in the narrow ~24-second window before Osaka activates on any chain configured with EIP-7594 support (which is the standard/default configuration per `set_eip7594(true)` default noted in the builder). No attacker action or malicious peer is required — ordinary transaction submission during this window is sufficient to trigger divergent behavior across nodes, driven only by ambient clock differences (NTP jitter is commonly in the sub-second-to-few-second range across real-world fleets, easily straddling the 4-second threshold).

### Recommendation
Replace the `SystemTime::now()` based check with a rule derived solely from deterministic chain state (e.g., the tip's timestamp, block number, or a schedule anchored to the fork activation timestamp itself) so that every node with the same tip reaches the same admission verdict for the same transaction, matching the deterministic check already used in `crates/ethereum/payload/src/lib.rs`.

    /// Returns whether EIP-7594 sidecars are allowed
    fn allow_7594_sidecars(&self) -> bool {
        let tip_timestamp = self.fork_tracker.tip_timestamp();

        // If next block is Osaka, allow 7594 sidecars
        if self.chain_spec().is_osaka_active_at_timestamp(tip_timestamp.saturating_add(12)) {
            true
        } else if self.chain_spec().is_osaka_active_at_timestamp(tip_timestamp.saturating_add(24)) {
            let current_timestamp =
                SystemTime::now().duration_since(SystemTime::UNIX_EPOCH).unwrap().as_secs();

            // Allow after 4 seconds into last non-Osaka slot
            current_timestamp >= tip_timestamp.saturating_add(4)
        } else {
            false
        }
    }
