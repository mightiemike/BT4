### Title
Architecture-dependent `Math.pow` in `MathWrapper.pow` can cause `ExchangeProcessor.exchange` to diverge between x86 and ARM nodes for un-catalogued inputs - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute `Maths.pow(base, exponent, useStrictMath)` and truncate the double result to `long` via `(long) issuedSupply` / `(long) exchangeBalance`. [1](#0-0) 
`Maths.pow` dispatches to either `StrictMathWrapper.pow` (platform-independent `StrictMath.pow`) or `MathWrapper.pow` depending on `useStrictMath`. [2](#0-1) 

The `MathWrapper.pow` implementation is architecture-specific, built separately under `platform/src/main/java/x86` and `platform/src/main/java/arm`. On x86 it is a thin pass-through to hardware/JIT-intrinsic `Math.pow`: [3](#0-2) 
On ARM, `pow` first checks a **hardcoded lookup table** of historically-observed `(a, b) -> result` pairs (recorded against specific past mainnet block heights where ARM's native `Math.pow` diverged from the canonical x86 result), and only falls back to `StrictMath.pow` when the inputs are not in the table: [4](#0-3) 

This table is retroactive — it only contains inputs from transactions that already caused an observed historical divergence and were patched after the fact (comments reference specific mainnet block numbers). For any **new** `sellTokenQuant`/balance combination not already present in the table, an ARM node computes `StrictMath.pow`, while an x86 node computes native `Math.pow`. `Math.pow` and `StrictMath.pow` are not guaranteed by the JLS to be bit-identical (native `Math.pow` may use hardware FMA/vectorized approximations differing by up to 1 ulp from the software fdlibm-based `StrictMath.pow`), and the existing test suite explicitly demonstrates that `useStrictMath=true` vs `false` can already yield different results for the same input set (`Assert.assertNotEquals(anotherTokenQuant, result)`): [5](#0-4) 

Because the exchange formulas use exponents very close to a truncation cliff (`0.0005` and `2000.0` applied to ratios near `1.0`), a single-ulp difference in the `pow` result can flip the truncated `long` value by ±1, changing `buyTokenQuant`/exchange reserve balances persisted on-chain by `ExchangeCapsule.transaction`. [6](#0-5) 

Whether this is exploitable *today* depends entirely on the chain-wide `allowStrictMath` flag read from `DynamicPropertiesStore`, which is a consensus-controlled parameter applied identically on every node for a given block (not attacker- or operator-selectable per node): [7](#0-6) 
When `allowStrictMath=true` (post-hardfork state), all nodes uniformly use `StrictMathWrapper.pow`, closing this gap. I was **not able to verify** in the available time whether this flag currently defaults to `true` (fully mitigated) or `false` (still exposed) on the target deployment, since I ran out of tool iterations before locating the getter/default initializer for `allowStrictMath()` in `DynamicPropertiesStore`.

### Impact Explanation
If `allowStrictMath` is `false` for the relevant block/period, an attacker (any funded account) can broadcast an ordinary `ExchangeTransactionContract` with a `sellTokenQuant` engineered to sit at a `pow()` rounding boundary not present in the ARM lookup table. x86 and ARM full nodes/witnesses would then compute different `buyTokenQuant`/exchange reserve values for the identical transaction, producing divergent application state roots — a **consensus/state divergence** (chain-split / fork) bug, not a key or secret disclosure. This matches the TRON bounty class "consensus divergence" as the question itself suggests re-classifying it.

The second half of the hypothesis — that resulting fork/error responses can be "mined" to fingerprint a specific validator's JVM/log environment and thereby assist ECDSA signer timing attacks — is **not supported by any code found in this repository**. There is no code path that correlates exchange-divergence behavior with node identity disclosure or with signing-timing side channels; this portion of the claim is speculative and rejected.

### Likelihood Explanation
- Preconditions: a heterogeneous x86/arm validator fleet (a normal, permitted deployment topology, not a "non-default configuration") and `allowStrictMath=false` on the live chain — the latter is unverified from this codebase snapshot.
- Cost to attacker: a single signed `ExchangeTransactionContract`, paying ordinary bandwidth/energy fees; no privileged role required.
- The attack is only reliably reproducible for input pairs not already present in the ARM `powData` table; the table already neutralizes all previously-observed historical divergences, so new divergent inputs would need to be found/fuzzed, which is feasible but non-trivial (searching a large space of `(balance, quant)` pairs for a ulp-level `pow` rounding cliff).
- Because `Maths`/`MathWrapper` are marked `@Deprecated` in favor of `StrictMathWrapper`, and a `SafeExchangeProcessor`/`allowStrictMath` migration path already exists in the codebase, this appears to be a known, actively-being-retired code path rather than an undiscovered defect.

### Recommendation
- Ensure `allowStrictMath` (and equivalently route `ExchangeProcessor`/`ContractStateCapsule` always through `StrictMathWrapper`) is unconditionally enabled and enforced consensus-wide, removing the legacy `MathWrapper`/`Maths.pow` non-strict path entirely rather than gating it behind a toggle that can be `false`.
- Delete or fence off the architecture-specific `MathWrapper` implementations (`platform/src/main/java/{arm,x86}`) so no code path can select a native, non-deterministic `Math.pow` for consensus-critical arithmetic.
- Add a hard-fork gate/ForkController check so any exchange transaction processed while `allowStrictMath=false` is rejected outright rather than falling back to platform-dependent math.

### Proof of Concept
Differential JUnit test demonstrating divergence between `useStrictMath=true` and `useStrictMath=false` (already present in the repo, confirming the underlying non-determinism): [8](#0-7) 

To fully confirm cross-architecture (x86 `Math.pow` vs ARM lookup-table/`StrictMath.pow`) divergence for a *new, un-catalogued* input, an additional test comparing `MathWrapper.pow` output when compiled against the `x86` module vs the `arm` module for a fuzzed set of `(a, b)` pairs near `a=1+ε`, `b=0.0005`/`2000.0` would be needed — this requires running the same JUnit test on both platform variants, which was not verifiable purely from static code review.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
