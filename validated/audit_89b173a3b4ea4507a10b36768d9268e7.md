### Title
Missing origin/capability-allowlist check before granting full MojoJS bindings surface to GEIC PrivilegedWebContents main frame - (File: chrome/browser/geic/geic_pwc_manager.cc)

### Summary
`GeicPwcManager::TabEntry::RenderFrameCreated` and `GeicPwcManager::TabEntry::ReadyToCommitNavigation` unconditionally call `RenderFrameHost::EnableMojoJsBindings(nullptr)` on the primary main frame of a GEIC `PrivilegedWebContents` (PWC) based solely on `IsInPrimaryMainFrame()`, without ever checking the frame's (about-to-be-)committed origin against the PWC's capability allowlist. [1](#0-0)  This mirrors the reported bug class of "lack of access controls": a function that grants a highly sensitive capability lacks any authorization check, relying only on structural position (primary main frame) rather than verifying the caller is the intended, allowlisted principal. The corresponding browser-client hook, `ChromeContentBrowserClient::ShouldAllowMojoJsBindingsForFrame`, has the identical gap, explicitly acknowledged in its own comment. [2](#0-1) 

### Finding Description
`EnableMojoJsBindings` is the same mechanism used to grant WebUI-grade privileges: it enables the `Mojo.bindInterface`/MojoJS JavaScript surface, which lets a document call directly into any Mojo interface exposed via `MojoJsInterfaceProvider`/`content::MojoJsInterfaceProvider` binder maps in the browser process — not just the intended `geic::mojom::GeicApi` interface. In every other GEIC/PWC binder path, capability checks are enforced through `pwc::EnforceCapabilityGate`, which validates the frame against the PWC's `capability_allowlist` before any interface is bound, e.g. in `BindGeicApi` and `BindGeicBrowserHost`. [3](#0-2) [4](#0-3) 

However, the code path that actually flips on the MojoJS bindings — `RenderFrameCreated`/`ReadyToCommitNavigation` — bypasses this gate entirely. It is gated only by `IsInPrimaryMainFrame()`, with an explicit developer TODO stating: "This exposes the entire Mojo surface rather than only GeicApi, and the committed origin is not checked against the capability allowlist here." [5](#0-4)  The same missing check exists in the underlying content-layer authorization hook `ShouldAllowMojoJsBindingsForFrame`, which grants MojoJS to the outermost main frame of *any* `PrivilegedWebContents` purely by checking `!GetParentOrOuterDocument()` and `pwc::PrivilegedWebContents::FromWebContents(web_contents)`, again without validating the frame's committed/pending origin against the PWC's navigation or capability allowlist. [2](#0-1) 

Because `PrivilegedWebContents::Create` is configured with a `FixedPwcPolicyDelegate` whose allowlist is meant to be the sole trust boundary restricting which origin may act as the privileged GEIC surface, [6](#0-5)  any gap between the navigation-allowlist enforcement (elsewhere, e.g. a throttle) and this MojoJS-granting logic means a frame that is merely "the primary main frame of a GEIC PWC" — regardless of which origin it ultimately commits — receives full MojoJS/browser-Mojo access. This is architecturally analogous to the reported issue: sensitive, system-level capability grants (there: contract address/parameter setters; here: enabling the entire browser Mojo IPC surface for a frame) implemented with a TODO/acknowledged-but-unenforced access control gate rather than an actual origin/capability check.

### Impact Explanation
If a GEIC PWC's main frame can be made to commit (via redirect, renderer-initiated navigation, or any allowlist-check ordering race relative to `ReadyToCommitNavigation`) a document whose origin is not the intended GEIC guest origin, that document is granted the entire `MojoJsInterfaceProvider` surface exposed to `IsInPrimaryMainFrame()` privileged frames — effectively WebUI-grade access to browser-process Mojo interfaces from ordinary web content. This is a universal-XSS/sandbox-escape-class outcome: attacker content executing with browser-process IPC capabilities normally reserved for trusted WebUI, going well beyond the narrow `GeicApi` interface the design intends to expose.

### Likelihood Explanation
The gate is a single boolean check (`IsInPrimaryMainFrame()`) with no origin comparison, and the developers themselves flagged it in-code as a "prototype shortcut" that is unsafe (`crbug.com/539909218`), indicating it is a live, acknowledged code path rather than dead code. Exploitability depends on whether an independent navigation-allowlist enforcement mechanism fully closes the gap before `ReadyToCommitNavigation`/`RenderFrameCreated` fire; the comments indicate this is explicitly not guaranteed in the current implementation.

### Recommendation
In `GeicPwcManager::TabEntry::RenderFrameCreated` and `ReadyToCommitNavigation`, and in `ChromeContentBrowserClient::ShouldAllowMojoJsBindingsForFrame`, validate the frame's (pending) committed origin against the owning `PrivilegedWebContents`'s capability allowlist (the same policy used by `pwc::EnforceCapabilityGate`) before calling `EnableMojoJsBindings`, and scope the exposed MojoJS surface to only the intended `GeicApi`/`GeicBrowserHost` interfaces rather than the full binder map, terminating the renderer via `bad_message` on mismatch as is already done in `BindGeicApi`/`BindGeicBrowserHost`.

### Proof of Concept
1. Enable the GEIC feature and configure a GEIC guest URL allowlisted to origin `A`.
2. Cause the GEIC PWC's primary main frame to navigate/commit an attacker-controlled or non-allowlisted origin `B` (e.g., via an open redirect hosted on origin `A`, or by exploiting any timing gap between navigation-allowlist enforcement and `ReadyToCommitNavigation`).
3. Because `ReadyToCommitNavigation`/`RenderFrameCreated` only check `IsInPrimaryMainFrame()`, `EnableMojoJsBindings(nullptr)` is invoked unconditionally for the committing frame regardless of origin `B`. [7](#0-6) 
4. Origin `B`'s script can now call `Mojo.bindInterface`/`chrome.mojoJs` style APIs to reach any interface exposed to MojoJS-enabled frames in the browser process — an unauthorized, non-allowlisted origin obtaining privileged browser-process IPC access, matching the "no access control on a sensitive capability-granting function" bug class from the reference report.

void GeicPwcManager::TabEntry::RenderFrameCreated(

  // TODO(crbug.com/539909218): Prototype shortcut. This exposes the entire
  // Mojo surface rather than only GeicApi, and the committed origin is not

}

void BindGeicApi(content::RenderFrameHost* render_frame_host,
                 mojo::PendingReceiver<mojom::GeicApi> receiver) {
  // The shared gate enforces the full capability policy (and terminates the
  // renderer itself on a renderer-controllable violation); null simply means
  // do not bind.
  pwc::PrivilegedWebContents* privileged =
      pwc::EnforceCapabilityGate(render_frame_host);
  if (!privileged) {
    return;
  }

  // The gate is component-agnostic; GeicApi additionally requires the
  // component to be GEIC. A request from another component's frame is again a
  // compromised renderer.
  if (privileged->component() != pwc::PrivilegedComponent::kGeic) {
    bad_message::ReceivedBadMessage(render_frame_host->GetProcess(),
                                    bad_message::PWC_BRIDGE_UNQUALIFIED_FRAME);
    return;
  }
