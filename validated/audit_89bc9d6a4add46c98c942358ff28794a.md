### Title
`check_microblock_header_signer` fails to verify equivocation (same-sequence conflicting content), allowing slashing of an honest, non-forking miner - (File: `stackslib/src/chainstate/stacks/db/transactions.rs`)

### Summary
`check_microblock_header_signer` only verifies that two microblock headers were signed by the same key; it never checks `mblock_header_1.sequence == mblock_header_2.sequence`, nor that the headers actually conflict (same `prev_block`/`sequence` with differing content). This lets an attacker submit any two genuinely-produced, non-conflicting microblock headers from an honest miner's ordinary (non-forked) stream as a `PoisonMicroblock` transaction, which passes into `handle_poison_microblock` and records a slashing/poison report against that miner.

### Finding Description
The broken equality is: `reported "double-signature" (any two headers signed by the same key)` == `a genuine same-position equivocation (mblock_header_1.sequence == mblock_header_2.sequence, same prev_block, differing hash)`.

`check_microblock_header_signer` [1](#0-0)  only recovers the public key hash from each header and compares `pkh1 != pkh2`. It performs no comparison of `sequence`, `prev_block`, or the header hashes themselves.

`handle_poison_microblock`, the actual consensus-critical execution path invoked from Clarity (`vm::contexts`) when any node processes a `PoisonMicroblock` transaction included in a block, relies solely on this check: [2](#0-1)  `check_microblock_header_signer(mblock_header_1, mblock_header_2)?`. If it returns `Ok`, the code proceeds to look up `mblock_pubk_height`, validate maturity, and then unconditionally record a poison report keyed on `mblock_header_1.sequence` — treating any two same-key headers as proof of a fork: [3](#0-2) .

Notably, a *separate* and stricter check does exist — but only in the mempool-admission path (`MemPoolRejection`), which explicitly requires `sequence`, `prev_block`, and `version` equality before accepting a `PoisonMicroblock` tx into the local mempool: [4](#0-3) . That check uses the `MemPoolRejection` error type and belongs to the local node's mempool-admission policy, not to the consensus-critical transaction-processing path (`Error` type) that all nodes use when validating a block that already contains the transaction. A miner/attacker can bypass local mempool admission entirely by directly embedding a crafted `PoisonMicroblock` transaction (two non-conflicting, correctly-sequenced microblock headers from an honest miner's normal stream) into a block they mine. Every other node that processes that block calls `process_transaction` → `handle_poison_microblock` → `check_microblock_header_signer`, which will accept it since only pubkey-hash equality is checked, causing the honest miner's key to be marked poisoned/slashed even though it never equivocated.

Existing guards checked:
- `check_microblock_header_signer` — insufficient (no sequence/prev_block/hash-conflict check).
- Mempool `PoisonMicroblocksDoNotConflict` check in `blocks.rs` — exists but is scoped to local mempool admission (`MemPoolRejection`), not enforced in the actual consensus transaction-processing path that determines block validity.
- No other equivocation validation is present between `check_microblock_header_signer` and the poison-report bookkeeping in `handle_poison_microblock`.

### Impact Explanation
This allows reward theft/loss against an honest, non-equivocating miner: their microblock public key hash gets marked as poisoned, denying them the maturing block reward/commission and instead paying a "commission" (per the doc comment on `handle_poison_microblock`) to an attacker who never observed a real fork. This is a wrongful, network-visible outcome once the crafted transaction is included in an accepted block — every node applying `process_transaction` reaches the same (wrong) slashing conclusion, so it is not merely a local mempool disagreement but an actual state-changing consensus effect. This matches the Critical category of block-reward theft/loss for an honest miner.

### Likelihood Explanation
Preconditions are minimal: the attacker needs any two headers from an honest miner's ordinary microblock stream (both are public once broadcast) that share the same signing key — trivially true for every honest miner's whole stream, since they use one microblock private key. The attacker does not need majority stake, node-operator privilege, or another party's key; they only need to be able to place a transaction into a block, which is available to any miner with a single valid block-commit (matching the stated unprivileged-attacker model), or to any user if a miner is willing to include a directly-submitted raw transaction bypassing normal mempool relaying. This is repeatable against every honest miner's stream on demand.

### Recommendation
Add an explicit equivocation check inside `check_microblock_header_signer` (or immediately before/after it in `handle_poison_microblock`) mirroring the mempool-side logic in `blocks.rs`: require `mblock_header_1.sequence == mblock_header_2.sequence`, `mblock_header_1.prev_block == mblock_header_2.prev_block`, and that the header hashes differ (i.e., genuinely conflicting content at the same stream position), before treating the pair as proof of miner equivocation.

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/stacks/db/transactions.rs` test module, alongside existing poison-microblock tests such as the one at `stackslib/src/chainstate/stacks/db/transactions.rs:5509-5597`):

1. Generate a single microblock private key `block_privk` for an honest miner.
2. Construct two **honestly-chained, non-conflicting** microblocks using this key at different sequences, e.g. `mblock_seq5` with `sequence = 5` and a correct `prev_block` continuing a legitimate chain, and `mblock_seq900` with `sequence = 900` and its own correct, non-forking `prev_block` — i.e., normal, sequential stream elements, not a fork.
3. Build `TransactionPayload::PoisonMicroblock(mblock_seq5.header.clone(), mblock_seq900.header.clone())`, sign as a reporter transaction, and call `StacksChainState::process_transaction`.
4. Assert on both sides of the claimed equality:
   - Left side (attacker's claim accepted): `check_microblock_header_signer(&mblock_seq5.header, &mblock_seq900.header)` returns `Ok(pkh)` (same signer) — this currently succeeds.
   - Right side (should be required for genuine equivocation): `mblock_seq5.header.sequence == mblock_seq900.header.sequence` — this is `false` (5 != 900).
5. Assert that `process_transaction` should return an `Err` (rejecting the non-equivocating pair) — if instead it returns `Ok` and inserts a poison report via `get_poison_microblock_report`, that confirms the vulnerability: an honest miner is being slashed based on two non-conflicting headers from their own legitimate stream.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
