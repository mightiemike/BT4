### Title
Unbounded duplicate growth of the shop→session-id index in `KVSessionStorage` can DoS `storeSession`/`findSessionsByShop` for a shop - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds` appends session ids to the shop's index array in Cloudflare KV without checking for duplicates, unlike the equivalent Redis implementation. Because the offline session id is deterministic per shop, any normal flow that re-stores the same offline session (token exchange re-runs, expiring offline access tokens, 401 re-auth) appends a fresh duplicate entry every time, causing the index value to grow without bound, analogous to the unbounded `MAX_DELEGATES` array growth described in the source report.

### Finding Description
`storeSession` always calls `addShopIds`, which reads the existing array and blindly concatenates the new id(s) without checking whether they are already present: [1](#0-0) [2](#0-1) 

Compare this with `RedisSessionStorage.addKeyToShopList`, which explicitly guards against duplicates before pushing: [3](#0-2) 

`storeSession` for the offline session (whose `id` is deterministic per shop, not per request) is re-invoked on ordinary, unprivileged flows whenever no valid/active session exists — e.g. every time `TokenExchangeStrategy.authenticate` finds `!session || !session.isActive(...)` and re-exchanges the offline token: [4](#0-3) 

This path runs on normal app loads (expired session, cleared cookies, or the `expiringOfflineAccessTokens` future flag causing periodic re-exchange), each time appending another copy of the same session id to the `shop:<shop>` KV value with no deduplication.

### Impact Explanation
Because Cloudflare KV values have practical size limits (and even before hitting hard limits, JSON parsing/serializing grows linearly), continual duplicate appends over the life of an installation will cause the `shop:<shop>` index value to grow unbounded. This directly degrades and can eventually break:
- `findSessionsByShop` [5](#0-4)  — iterates and loads a session per (duplicated) id, becoming progressively slower and eventually failing/timing out.
- `storeSession`/`removeShopIds` themselves, once the value exceeds the KV per-key size limit, causing writes to fail for that shop, which blocks token exchange/session persistence entirely for that shop — a session-storage DoS analogous to the `MAX_DELEGATES` unbounded-array DoS in the source report.

This is scoped purely to session storage/lookup (an approved category) and requires no privileged actor, leaked secret, or attacker-controlled infrastructure — a single merchant's normal, repeated (re-)authentication traffic is sufficient to trigger it.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment using `shopify-app-session-storage-kv` with token-exchange-based auth (Remix/React Router adapters), especially with the `expiringOfflineAccessTokens` future flag enabled, since offline tokens are then refreshed periodically for the lifetime of the install, guaranteeing the duplicate-append path executes indefinitely without any adversarial input.

### Recommendation
Deduplicate before writing in `KVSessionStorage.addShopIds` (and correspondingly ensure `removeShopIds` removes all occurrences), mirroring the guard already present in `RedisSessionStorage.addKeyToShopList`:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Configure an app with `KVSessionStorage` and `future.expiringOfflineAccessTokens: true` (or simply allow the offline session to expire/be invalidated between requests).
2. Repeatedly load the embedded app such that `TokenExchangeStrategy.authenticate` finds no active offline session (e.g., let the token TTL lapse each cycle) — this is normal, single-merchant behavior, not an attack.
3. Each cycle calls `config.sessionStorage!.storeSession(offlineSession)` with the same deterministic offline `session.id` for the shop.
4. Inspect the KV value at key `shop:<shop>`: it will contain N duplicate copies of the same session id after N cycles, growing without bound and never being deduplicated, until reads/writes to that key become slow or fail outright.

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
