## Title
Replay-verify skips checkpoint-hash validation, allowing a corrupted state/hot-state/position-state root to pass as authentic — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant check used to confirm that a locally re-executed transaction output matches an externally supplied/authenticated `TransactionInfo` (the object committed to the transaction accumulator). It checks status, gas used, write-set hash, and event root hash, but the code explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed local values, even though these fields are part of `TransactionInfo` and are used to build the accumulator leaf that ultimately gets validator-signed.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` validates a `TransactionOutput` against a `TransactionInfo` by checking:
- execution status
- gas used
- `state_change_hash` (write-set hash)
- `event_root_hash`

The trailing comment is explicit about the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

This is exactly the same class of bug as the external report: a value that is supposed to bind/scale the computed result to the actual input (there: `remainingLockDuration`/stake scaling; here: `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) is silently dropped from the check, so the function's "success" result becomes independent of the very state it is supposed to authenticate. This function is used by `replay_on_archive` (`storage/db-tool/src/replay_on_archive.rs`) and by the CLI/debugger paths (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) as the pass/fail criterion for verifying that replayed execution matches the historical, signed ledger record.

Because the checkpoint hashes (Sparse-Merkle/Jellyfish-Merkle state roots) are the fields that actually commit the *state* resulting from a transaction (as opposed to just the write-set of that one transaction), omitting them from the match check means: if an externally-supplied `TransactionInfo`/archive record (or a corrupted/malicious backup or archive-node response) carries a `state_checkpoint_hash` that does not correspond to the true state produced by replaying the referenced transactions, `ensure_match_transaction_info` will still return `Ok(())` as long as gas/status/write-set-hash/events happen to line up. Replay-verify tooling built on this check therefore cannot detect a diverging authenticated state root — the primary purpose of that comparator.

### Impact Explanation
This breaks the proof/commitment invariant that a `TransactionInfo`'s checkpoint hash fields must be verified to reflect the actual post-execution state before being trusted. Tools relying on `ensure_match_transaction_info` (replay-verify, debugger, CLI-based verification flows) can report a **false positive successful replay** even when the state root diverges from what local execution actually produced. This directly matches the "Proof and Storage Pivots" requirement that "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" and that "restore paths must preserve deterministic proof binding" — here, the state root binding is explicitly unchecked. An operator or auditor using replay-on-archive to validate historical or restored data would get a false assurance that the reconstructed ledger state is correct, when in fact the state-tree root (and by extension the authenticated `LedgerInfo`) could be silently wrong.

### Likelihood Explanation
The comment shows this is a currently-known, acknowledged, and still-unpatched gap gated behind future work ("before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), but the omission of the ordinary `state_checkpoint_hash`/`hot_state_checkpoint_hash` comparison (not just the position-state one) is already present today, independent of that feature flag, in the general replay-verify code path. Any caller of `ensure_match_transaction_info` today misses this check regardless of whether the trading-native feature is enabled.

### Recommendation
Add explicit comparisons of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) between the locally-recomputed roots and the `TransactionInfo` under check inside `ensure_match_transaction_info`, before any code path (including `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) relies on this function as a correctness gate.

### Proof of Concept
Not independently reproducible from static analysis alone: exploiting this requires supplying a `TransactionOutput`/`TransactionInfo` pair through one of the replay-verify entry points (`replay_on_archive`, `aptos-debugger`, or CLI commands) where the write-set hash, event root hash, gas, and status match but the checkpoint hash fields do not correspond to the actual resulting state tree. I could not verify from the index alone what runtime guardrails (if any) exist further up each specific call site to compensate for this gap, since I was unable to load the full contents of `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` before running out of tool budget. The code comment itself is direct, first-party confirmation that this gap exists and is understood as a real replay-verify blind spot by the aptos-core maintainers.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
```
