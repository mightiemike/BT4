Confirmed: this is a valid, real analog to the PayoutManager bug — a permanent, unrecoverable fund-lock path in the CEA (Chain-Enabled Abstraction) inbound flow.

### Title
CEA smart-contract inbound: permanent, irrecoverable loss of deposited PRC20 funds when `executeUniversalTx` on the recipient contract fails after a successful deposit - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
For `isCEA` inbounds whose `Recipient` resolves to a deployed smart contract (not a UEA), the flow first mints PRC20 to the recipient (`depositPRC20`/auto-swap), then calls `CallExecuteUniversalTx` exactly once to invoke `executeUniversalTx` on that contract. If that single call fails — for any reason under the recipient contract's control, e.g. an internal eligibility/authorization check that becomes false after the deposit lands — the funds are permanently stuck: no automatic revert is ever created for `isCEA` inbounds, and the manual rescue path explicitly refuses to help once the deposit succeeded.

### Finding Description
In `ExecuteInboundFundsAndPayload` (also mirrored in `ExecuteInboundGasAndPayload`), the `isCEA` + smart-contract branch does:
1. `depositPRC20`/auto-swap into the recipient address (mints PRC20 tokens — funds now live on Push Chain, attributed to the recipient contract). [1](#0-0) 
2. `CallExecuteUniversalTx` is invoked a single time against the recipient contract to actually deliver the payload/funds logic. [2](#0-1) 

The code comment is explicit that `isCEA` failures never trigger an `INBOUND_REVERT` outbound, regardless of where in the pipeline the failure occurs: [3](#0-2) 

The only other escape hatch, `AttachRescueOutboundFromReceipt`, is gated on the deposit itself having failed for CEA inbounds: [4](#0-3) 

and this is directly asserted by the test suite — rescue is rejected once the deposit (first `PCTx`) succeeded, even if the payload execution later fails: [5](#0-4) 

So once the deposit to the CEA smart contract succeeds and `executeUniversalTx` subsequently fails (e.g., because the contract's own internal check — analogous to the AML/eligibility check in the PayoutManager report — now rejects the call), there is no code path left to move the money:
- No automatic revert (`isCEA` is exempt).
- No rescue (deposit already succeeded, so `AttachRescueOutboundFromReceipt` rejects with `"deposit did not fail"`).
- No admin function analogous to `RevokePayout`/`RevertStuckInbound` exists for this specific state — `RevertStuckInbound` in `x/uexecutor/keeper/admin_revert.go` only handles inbounds whose *ballot* is `EXPIRED`, which is a completely different failure mode (never reached quorum) from a UTX that *did* finalize and execute the deposit successfully. [6](#0-5) 
- Because the recipient is a plain contract (not a UEA owned by a private key), the funds' owner cannot resubmit a signed `MsgExecutePayload` to retry — the module is the only entity that ever calls `executeUniversalTx` on that address, and it does so exactly once, synchronously, inside inbound execution.

The failed attempt is only recorded as a `FAILED` `PCTx` entry on the UTX for observability, with no further remediation: [7](#0-6) 

### Impact Explanation
User/protocol funds (PRC20 balance already minted to the CEA recipient address) become permanently frozen with no way for the depositor, the recipient, or the admin/governance to recover them via any documented code path — the direct analog of the PayoutManager bug where an investor's changed eligibility permanently blocks claiming already-deposited principal. This is a "permanent freezing of user-controlled funds" impact, reachable purely from an unprivileged user's own inbound deposit combined with an ordinary (non-malicious) later failure of the recipient contract's own logic (which the protocol has no control over and cannot assume is always succeed-on-retry, since retry isn't even possible).

### Likelihood Explanation
Medium. It requires: (a) a CEA-style inbound targeting a deployed smart contract recipient (a supported, intentional feature), and (b) that contract's `executeUniversalTx` call reverting after the deposit PCTx already succeeded (e.g., a contract-side allow-list, cap, or precondition that becomes false between deposit and payload call, or simply a contract bug/edge-case). This does not require any malicious or privileged actor — it only requires ordinary transaction ordering/timing or a legitimate business-logic revert in the recipient contract, matching the "unprivileged external attacker" / "ordinary user" scope.

### Recommendation
Add a dedicated recovery path for CEA UTXs whose deposit succeeded but whose `executeUniversalTx` call failed — either (a) allow a bounded number of retries of `CallExecuteUniversalTx` (e.g., via a permissionless "retry execution" message once conditions may have changed), or (b) extend the rescue-funds mechanism / a new admin function (mirroring `RevertStuckInbound`) to permit returning the already-deposited PRC20 back to the original sender (via `RevertInstructions.FundRecipient`) when the post-deposit `executeUniversalTx` PCTx is `FAILED`, rather than only when the deposit itself failed.

### Proof of Concept
1. Deploy a "recipient" smart contract implementing `executeUniversalTx` that reverts under some condition it controls (e.g. `require(callCount == 0)` to simulate a one-shot eligibility check, or any check that can flip after deployment).
2. Submit an `isCEA` `FUNDS_AND_PAYLOAD` inbound with `Recipient` = this contract's address and a nonzero `Amount`.
3. Reach validator quorum via `MsgVoteInbound` — `ExecuteInboundFundsAndPayload` runs: `depositPRC20` succeeds (PCTx\[0\] = SUCCESS, PRC20 minted to the contract), then `CallExecuteUniversalTx` reverts because the contract's condition is now false (PCTx\[1\] = FAILED).
4. Observe: `utx.OutboundTx` is empty (no `INBOUND_REVERT` created, consistent with `test/integration/uexecutor/vote_inbound_validation_test.go:243-310`).
5. Attempt `AttachRescueOutboundFromReceipt` for this UTX — it is rejected with `"rescue: UTX %s CEA deposit did not fail"` because `PcTx[0].Status == "SUCCESS"`, exactly as asserted in `test/integration/uexecutor/rescue_funds_test.go:299-325`.
6. No further message (`MsgRecomputeBallotQuorum` + `RevertStuckInbound`) applies either, since the ballot already `PASSED` — that admin tool is scoped to `EXPIRED` ballots only.
7. Result: the deposited PRC20 remains permanently locked in the recipient contract's balance with no on-chain path to release it.

// RevertStuckInbound creates an INBOUND_REVERT outbound for an inbound whose
// ballot has expired without finalizing. The revert outbound enters the normal
// PendingOutbounds flow; UVs sign it via TSS and broadcast it to the source
// chain, refunding the user.
//
// Strict precondition: the ballot for the supplied inbound must be in EXPIRED
// state. Admin must run MsgRecomputeBallotQuorum first to drive a stuck ballot
// to EXPIRED if it isn't already (recompute auto-expires when no eligible
// voters remain).
//
// Returns the new UTX ID and revert outbound ID for telemetry.
func (k Keeper) RevertStuckInbound(ctx context.Context, inbound types.Inbound) (utxId, outboundId string, err error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Same canonical form as the vote path, so the admin-supplied payload
	// derives the same ballot key / UTX key the votes did.
	inbound.Canonicalize()

	if vErr := inbound.ValidateBasic(); vErr != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, vErr.Error())
	}

	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, fmt.Sprintf("failed to derive ballot key: %s", err))
	}

	ballot, err := k.uvalidatorKeeper.GetBallot(ctx, ballotKey)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrNotFound, fmt.Sprintf("ballot for inbound not found (key=%s): %s", ballotKey, err))
	}

	if ballot.Status != uvalidatortypes.BallotStatus_BALLOT_STATUS_EXPIRED {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest,
			fmt.Sprintf("ballot %s status is %s; admin revert requires EXPIRED (use MsgRecomputeBallotQuorum to drive a stuck pending ballot to EXPIRED)",
				ballotKey, ballot.Status.String()))
	}
