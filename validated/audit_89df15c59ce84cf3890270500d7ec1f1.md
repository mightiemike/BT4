## Finding

### Title
Free, unbounded `MsgExecutePayload` submission enables an unprivileged gasless-flood DoS on block/EVM execution capacity - (File: `app/txpolicy/gasless.go`, `x/uexecutor/keeper/msg_execute_payload.go`, `app/ante/account_init_decorator.go`)

### Summary
The external report describes a DoS where an attacker floods a low-fee source chain with cheap message-call requests, forcing the relayer's queue to fill with junk it must still process, delaying legitimate users. Push Chain has a structurally identical exposure on its own chain: `MsgExecutePayload` is whitelisted as gasless for **any** signer, and `AccountInitDecorator` lets a brand-new, unfunded account submit such a transaction and be created on the spot. This lets an attacker generate unlimited fresh keypairs and submit unlimited free transactions that each trigger real EVM computation (UEA factory address resolution, contract calls, signature-recovery/precompile work) before reverting, with zero cost and no built-in account/tx rate limit.

### Finding Description
`IsGaslessTx` in [1](#0-0)  whitelists `/uexecutor.v1.MsgExecutePayload` as a gasless message type for **any** sender — not just bonded Universal Validators. The `x/uexecutor` README confirms this is intentional: "`MsgExecutePayload` | any | yes" [2](#0-1)  and explicitly states "Any account may submit the message" and pays no Cosmos fee [3](#0-2) .

Three ante decorators cooperate to make this fully free:
- `DeductFeeDecorator` skips fee deduction entirely for gasless txs [4](#0-3) .
- `MinGasPriceDecorator` skips the minimum-gas-price check for gasless txs [5](#0-4) .
- `AccountInitDecorator` will create a brand-new on-chain account for a first-time gasless signer, verifying only a self-consistent signature over `account_number=0, sequence=0`, and short-circuits the rest of the ante chain [6](#0-5) .

Because an attacker fully controls key generation, they can mint an unbounded number of fresh signer identities, each producing a valid signature for its own `MsgExecutePayload` at zero cost — no funded account, no minimum fee, no gas price required. Each accepted message then drives real, non-trivial computation in `ExecutePayload`: chain-config lookup, `CallFactoryToGetUEAAddressForOrigin` (an EVM call), and `CallUEAExecutePayload` (another EVM call into the target UEA contract, which performs ECDSA recovery or an Ed25519 precompile call before it can revert on bad `verificationData`) [7](#0-6) . Fee deduction, when it happens, is charged only against the target UEA's own balance (`DeductGasFeesFromReceipt`), never against the attacker's signer account [8](#0-7) , so the attacker bears none of this cost even when the call fails.

This mirrors the external report's core defect precisely: an unprivileged party can generate a theoretically unbounded stream of "message call" requests that the chain's honest block producers and validators must still admit and partially execute (signature checks, account creation, EVM calls) regardless of legitimacy, at effectively zero cost to the attacker, crowding out genuine gasless traffic — including the same-whitelist `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration` messages that Universal Validators depend on to keep the crosschain pipeline moving.

### Impact Explanation
No funds are stolen or state is corrupted, but block gas/computation capacity and mempool space are consumed for free by an unprivileged actor, competing directly with legitimate gasless UV votes and user `MsgExecutePayload` calls. Since block gas is bounded by consensus params but not backed by any fee market for this message class, this is a pure application-level admission-control gap (not network-level flooding), reachable via ordinary transaction submission with no privileged role required — squarely inside the "gasless admission" and unprivileged-DoS pivot named in scope.

### Likelihood Explanation
Trivial to execute: generating keypairs and self-signing `sequence=0` transactions is free and requires no special access. The only cost to the attacker is their own compute to generate and broadcast transactions, not any on-chain resource.

### Recommendation
- **Short term:** Rate-limit or cap the number of free-account-creations and/or gasless `MsgExecutePayload` submissions per block/per IP/per validator mempool slot; consider a minimal anti-spam bond or Cosmos-level fee floor specifically for `MsgExecutePayload` that is refunded/waived only when the payload's signature check actually succeeds (i.e., move cost after cheap pre-validation, or require a tiny non-gasless wrapper fee from the `Signer`, distinct from the UEA's own gas billing).
- **Long term:** Analyze mempool prioritization/admission for the gasless whitelist as a whole (all six message types) under sustained hostile load, and consider per-signer/per-UEA throughput quotas so a burst of illegitimate calls cannot delay the finalization of legitimate Universal Validator votes or user payload executions.

### Proof of Concept
1. Generate N fresh secp256k1 keypairs (free, off-chain).
2. For each key, construct a `MsgExecutePayload` with an arbitrary/garbage `UniversalAccountId` and `VerificationData`, sign it as the sole message in a transaction with `fee=0`, `gas` set to whatever is accepted.
3. Broadcast all N transactions. Each is gasless per `IsGaslessTx` [1](#0-0) ; `AccountInitDecorator` creates the never-before-seen signer account and passes it through [6](#0-5) ; `DeductFeeDecorator`/`MinGasPriceDecorator` impose no cost [4](#0-3) [5](#0-4) .
4. `ExecutePayload` runs chain-config lookup and two EVM calls before rejecting the forged signature [9](#0-8) , consuming validator/node compute and block space for every one of the N transactions at zero cost to the attacker, while legitimate gasless UV votes and user payloads compete for the same block space.
