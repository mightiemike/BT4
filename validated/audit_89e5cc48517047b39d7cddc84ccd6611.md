### Title
`liquidate-multi()` swallows per-position failures, letting a liquidator's already-executed debt repayment be stranded without a corresponding debt/collateral update - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi()` maps over a caller-supplied batch of liquidation positions and does not propagate individual failures — matching exactly the "allowFailure ignore a failed action" pattern from the Tapioca `burst()` report. Because each position is liquidated via a *direct* function call (not `contract-call?`), a failure partway through `liquidate()` does not unwind sub-calls to other contracts (e.g. the vault) that already committed, so value already moved by an earlier step of the same liquidation is not returned when a later step in the same call fails.

### Finding Description
`liquidate-multi` is defined as: [1](#0-0) 

It calls the private helper `call-liquidate`, which invokes `liquidate` directly (same-contract function call, not `contract-call?`): [2](#0-1) 

Inside `liquidate`, the debt repayment is executed first via a cross-contract call to the vault: [3](#0-2) 

and only *after* that repayment succeeds does the function attempt to remove the borrower's scaled debt in `market-vault` and seize collateral. Each of these is its own `contract-call?`, which in Clarity rolls back *only its own* state changes if it returns an error — it does not undo an already-committed prior `contract-call?` in the same execution. Because `liquidate` is invoked directly (not via `contract-call?`) from `call-liquidate`, and `liquidate-multi` never calls `try!`/`unwrap!` on the mapped results (it just wraps the whole list in `(ok ...)`), an `err` returned by `liquidate` for one position in the batch does not abort the transaction and does not undo the vault-level repayment that already committed for that same position.

Concretely: if a liquidator submits the same `{borrower, collateral-ft, debt-ft, ...}` position twice in one `liquidate-multi` call, the first entry succeeds (debt repaid, debt removed, collateral seized). On the second entry, `vault-system-repay` again pulls the liquidator's debt tokens and commits (vault-level `total-borrowed`/`assets` update), but the subsequent `debt-remove-scaled` call now fails with `ERR-INSUFFICIENT-DEBT` (the borrower's remaining scaled debt is `u0`). Because `liquidate`'s error is swallowed by the enclosing `map`, `liquidate-multi` still returns `ok`, but the liquidator's second token transfer is never refunded and no collateral is received for it — the tokens are irrecoverably spent while the borrower's ledger and the vault's global debt accounting go out of sync (vault debt reduced twice while market-vault debt removal only succeeded once).

### Impact Explanation
This lets a caller's transferred funds be permanently consumed by the protocol with no compensating debt reduction or collateral, and simultaneously desynchronizes the vault's `total-borrowed`/`assets` accounting from `market-vault`'s per-user obligation ledger. This is a permanent loss of the caller's funds and a protocol accounting break stemming directly from the batch entry point's failure-swallowing design — the same root cause class as the referenced report (value moved in one step of a multi-step, failure-tolerant entry point is not returned when a later step aborts).

### Likelihood Explanation
Triggering requires only a single liquidator constructing a `liquidate-multi` call containing the same (or an already-fully-liquidated) position more than once, or two positions in the batch that happen to fully clear the same borrower's debt for an asset before a later entry attempts to remove it again. No collusion or second party is required — a single caller in a single transaction can hit this path.

### Recommendation
- Have `liquidate-multi` propagate a hard failure (e.g. via `try!`) whenever a position's `liquidate` call errors instead of silently accepting `(ok err-value)`, or
- Restructure so that `vault-system-repay` (and any other value-moving step) executes only after all preconditions for that specific position are re-validated atomically within the same `contract-call?` boundary as the debt/collateral update, so a failure in one step cannot leave an earlier committed transfer stranded.

### Proof of Concept
1. Liquidator calls `market.liquidate-multi` with a `positions` list containing the same `{borrower, collateral-ft, debt-ft, debt-amount, min-collateral-expected}` entry twice (targeting a borrower whose debt is fully liquidatable by the first entry).
2. First `call-liquidate` → `liquidate` executes fully: `vault-system-repay` succeeds, `debt-remove-scaled` succeeds (borrower's scaled debt becomes `u0`), collateral is seized.
3. Second `call-liquidate` → `liquidate` re-enters: `vault-system-repay` again pulls debt tokens from the liquidator and commits at the vault level.
4. `debt-remove-scaled` then fails with `ERR-INSUFFICIENT-DEBT` since the borrower's scaled debt is already `u0`; `liquidate` returns `err` via `try!`.
5. Because `call-liquidate`/`liquidate-multi` never `try!`s the per-position result, `liquidate-multi` still returns `(ok (list (ok ...) (err ...)))` — the transaction succeeds overall, but the liquidator's second repayment is not refunded and no collateral is received for it.

**Note on assumptions:** This finding relies on the Clarity semantic that a `contract-call?` invocation establishes its own rollback boundary (only that specific call's state changes are undone on error), while directly invoking another public function in the same contract (as `call-liquidate` does with `liquidate`) does not itself create a rollback boundary and lets earlier, already-committed cross-contract calls persist even if a later step in the same local call fails and the enclosing `map`/`liquidate-multi` never escalates that failure into a transaction abort. This is standard, documented Clarity behavior, but I was not able to independently re-confirm it against a Clarity language-semantics reference file within this repository's index, so this should be validated by a background agent against real test execution before relying on it as a confirmed exploit.
