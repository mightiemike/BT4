### Title
Registered `liquidity_cap` on `uregistry.TokenConfig` is never enforced before minting PRC20 tokens, allowing unbounded inbound-driven minting past the configured supply cap - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/evm.go`)

### Summary
This is the Push Chain analog of the `addInvestor()` bug: a per-entity "available supply" field exists in state (`investors_supply` in the C4 report; `liquidity_cap` in `uregistry.TokenConfig`), but the code path that allocates/mints tokens never reads or checks it before minting. `TokenConfig.LiquidityCap` is documented as "max supply cap for this token" and is required to be a non-empty string by `ValidateBasic`, but grepping the entire scoped codebase shows `LiquidityCap` is only ever read in validation/tests — it is never parsed into a `big.Int` or compared against anything in the actual PRC20 minting flow (`depositPRC20` → `CallPRC20Deposit` → `depositPRC20Token`).

### Finding Description
`x/uregistry/types/token_config.go` `ValidateBasic()` only checks that `LiquidityCap` is a non-empty string [1](#0-0)  — it never parses it as a number or validates it's a sane cap value.

The field is documented in `proto/uregistry/v1/types.proto` as the "max supply cap for this token (string big.Int format)" [2](#0-1) .

The actual minting path that an unprivileged, ordinary inbound event drives is `x/uexecutor/keeper/handler.go:depositPRC20`, which looks up the `TokenConfig` only to resolve the `NativeRepresentation.ContractAddress` (the PRC20 address) — it never reads or checks `tokenConfig.LiquidityCap`: [3](#0-2) 

`depositPRC20` calls `k.CallPRC20Deposit`, which builds a `DerivedEVMCall` to `depositPRC20Token` on the `UNIVERSAL_CORE` handler contract with the raw inbound `amount`, again with no supply-cap check anywhere in the Go keeper: [4](#0-3) 

This mint path is reachable from ordinary, unprivileged source-chain deposits: `ExecuteInboundFunds` (funds-only inbound), `ExecuteInboundFundsAndPayload` (UEA/CEA deposits), and `ExecuteInboundGasAndPayload`/auto-swap paths all call `depositPRC20` / `gasAndPayloadDepositAutoSwap` → `CallPRC20DepositAutoSwap`, none of which consult `LiquidityCap`. [5](#0-4) [6](#0-5) 

Even the failed-outbound revert path re-mints tokens via the same uncapped `CallPRC20Deposit` call: [7](#0-6) 

A grep across the entire repository for `LiquidityCap`/`liquidityCap`/`maxSupply`/`totalSupply` confirms the field appears only in generated protobuf code, tests, and the JSON config seed files (as static config values shipped to operators) — never in any keeper logic that gates a mint call.

### Impact Explanation
Because the honest-validator-driven inbound flow mints PRC20 tokens purely off the observed source-chain deposit amount with no reference to the token's configured `liquidity_cap`, an ordinary, unprivileged user can deposit funds on the source chain (a normal, permissionless action, not requiring any privileged role) that get faithfully observed and voted on by honest Universal Validators, and Push Chain will mint PRC20 tokens without ever checking whether the resulting total supply exceeds the admin-configured cap. This corrupts PRC20 accounting semantics that the protocol advertises via `uregistry` (`liquidity_cap` is supposed to bound issuance per bridged asset) and can result in PRC20 supply inflation beyond the intended backing/liquidity limit for that asset — a real accounting-integrity violation matching the "corruption of PRC20 ... accounting" allowed-impact category. This does not require any admin/validator/relayer compromise; it is purely a missing invariant check on the unprivileged, default inbound-deposit path.

### Likelihood Explanation
High. No special conditions or edge-case timing are needed — any inbound deposit of an amount whose cumulative total (across many ordinary users, or a single large deposit) exceeds a token's `liquidity_cap` will be minted regardless. Since `liquidity_cap` is per-token config data that operators configure per bridged asset (as seen in `config/testnet-donut/*/tokens/*.json`), and there is no code anywhere reading it during minting, this is a systemic, always-present gap rather than a rare corner case.

### Recommendation
Before calling `CallPRC20Deposit` / `CallPRC20DepositAutoSwap` in `depositPRC20` (`x/uexecutor/keeper/handler.go`) and in the auto-swap deposit helpers, look up the token's current minted supply (e.g., query `totalSupply()` on the PRC20 contract, or maintain an on-chain running total in `uexecutor`/`uregistry` state) and compare `currentSupply + amount` against `tokenConfig.LiquidityCap` parsed as a `big.Int`. If the cap would be exceeded, fail the deposit (recording a `FAILED` PCTx / triggering the existing `INBOUND_REVERT` path) rather than minting. Apply the same check to the revert re-mint path in `handleFailedOutbound` to avoid double-counting toward the cap when reverting.

### Proof of Concept
1. Admin registers a `TokenConfig` for `chain=eip155:11155111`, `address=<USDC>`, with `liquidity_cap = "1000000"` (i.e., 1 USDC at 6 decimals) — a deliberately small cap for illustration, mirroring the real JSON configs at `config/testnet-donut/*/tokens/usdc.json`. [8](#0-7) 
2. An ordinary user (no admin/validator privilege) makes two separate real deposits on the source chain, each for `amount = "1000000"` (i.e., together `2,000,000`, twice the configured cap), to two different recipients (or the same recipient twice).
3. Honest Universal Validators observe both source-chain events truthfully and submit `MsgVoteInbound` for each; each reaches quorum independently (see `TestInboundSyntheticBridge` for the exact quorum-vote flow that exercises `depositPRC20` end to end). [9](#0-8) 
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` executes for both inbounds; each call succeeds and mints the full requested `amount`, because neither `depositPRC20` (`x/uexecutor/keeper/handler.go`) nor `CallPRC20Deposit` (`x/uexecutor/keeper/evm.go`) ever reads `tokenConfig.LiquidityCap` or checks cumulative minted supply.
5. Query the PRC20 contract's `balanceOf`/`totalSupply` after both inbounds finalize: total minted supply for the token is `2,000,000`, exceeding the configured `liquidity_cap` of `1,000,000`, with no error, revert, or rejection anywhere in the pipeline.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
