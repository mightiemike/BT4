### Title
Unbounded duplicate accumulation in KV session storage's shop-session index list can exhaust storage and break session lookups (analogous to CometBFT mempool list/map duplication) - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage.storeSession` maintains a per-shop index (`shop:{shop}` key) that lists all session ids belonging to that shop, similarly to how CometBFT's mempool keeps a list of transactions indexed by a map. Just like the CometBFT bug, this KV index can accumulate duplicate entries when the same session id is stored more than once, because the append path performs no membership check before writing.

### Finding Description
`storeSession` always calls `addShopIds(session.shop, [session.id])` on every store, even when the id already exists in the shop's session-id list: [1](#0-0) 

`addShopIds` unconditionally concatenates the new id(s) onto the existing array without checking whether the id is already present: [2](#0-1) 

This is the same bug class as the CometBFT report: a list-like data structure (the shop's session-id array) that can contain multiple copies of the same logical entry because the write path does not deduplicate before appending. By contrast, the Redis implementation of the identical mechanism explicitly guards against this: [3](#0-2) 

`storeSession` is called repeatedly for the *same, deterministic* offline session id (`offline_${shop}`) whenever a merchant's session token is exchanged and no valid offline session is currently cached, which happens on every request that lacks (or has an expired) cached session: [4](#0-3) [5](#0-4) 

Because the offline session id is deterministic per shop (not random), any burst of concurrent requests carrying a valid Shopify session token for that shop (e.g., multiple embedded-app iframe requests firing in parallel during install, token refresh races, or a merchant/app repeatedly re-authenticating) will invoke `storeSession(offlineSession)` multiple times for the identical id, each of which appends another duplicate copy of that id to the `shop:{shop}` KV list — unboundedly, since there is no cap or dedup.

### Impact Explanation
- The `shop:{shop}` KV value grows without bound as duplicates accumulate, eventually risking Cloudflare KV per-value size limits and causing `put`/`get` failures for that shop's session index — a denial of service against the session-storage/auth layer for that shop.
- `findSessionsByShop` iterates every id in the (now duplicated) list, causing redundant KV reads and returning duplicate `Session` objects, degrading performance and correctness of any code path relying on it (e.g., `AppInstallations.includes/delete`), which is directly in the authentication/session-lookup path.
- This is a session-storage integrity issue reachable by a single merchant/app-session actor without needing elevated privileges, matching a "DoS of an auth handler" class impact.

### Likelihood Explanation
Reaching this requires only that a merchant/app makes concurrent or repeated authenticated requests to an app using `@shopify/shopify-app-session-storage-kv` while its offline session is missing/expired (common during install, token exchange races, or repeated re-auth). No secret leakage, privileged access, or MITM is required — only normal, valid session-token traffic during a window where the cached offline session is not yet valid.

### Recommendation
Mirror the Redis implementation: check for existing membership before appending in `addShopIds` (and analogously de-duplicate in `removeShopIds`), e.g.:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Configure an app with `KVSessionStorage`.
2. Fire N concurrent requests bearing a valid Shopify session-token for shop `test.myshopify.com` while no valid offline session is stored (e.g., during first install or right after token expiry), each hitting `performTokenExchange`/`TokenExchangeStrategy.authenticate`.
3. Each concurrent request calls `config.sessionStorage.storeSession(offlineSession)` with the same id `offline_test.myshopify.com`, invoking `addShopIds` N times.
4. Inspect the KV key `shop:test.myshopify.com` — it will contain N duplicate copies of `offline_test.myshopify.com` instead of one, and `findSessionsByShop('test.myshopify.com')` will return N identical `Session` entries.
