## Finding: Analog Identified [1](#0-0) 

### Title
Unprivileged accounts can unboundedly bloat another account's `DelegatedResourceAccountIndex` list, forcing costly/DoS-prone migration work on that victim's future delegation transactions - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
`FreezeBalanceActuator.delegateResource()` lets any account freeze-and-delegate resources to an arbitrary `receiverAddress` that has never consented and has no way to block the operation. Every such call appends the delegator's address to the receiver's `DelegatedResourceAccountIndexCapsule.fromAccountsList` (and the delegator's own `toAccountsList`), with **no maximum size check**, analogous to how `HatsSignerGate` allowed unrelated modules to add safe owners without checking `maxSigners`. [2](#0-1)  The `DelegatedResourceAccountIndexCapsule` stores these lists as repeated fields inside a single protobuf value keyed by address. [3](#0-2) 

### Finding Description
When `supportAllowDelegateOptimization()` is enabled, the next delegation touching either the `ownerAddress` or `receiverAddress` triggers a mandatory one-time migration via `DelegatedResourceAccountIndexStore.convert()`, which iterates **every** entry in that account's legacy `toAccountsList`/`fromAccountsList` and rewrites each as an individual V2 key: [4](#0-3) 

```
public void convert(byte[] address) {
  ...
  for (int i = 0; i < toList.size(); i++) { this.delegate(address, toList.get(i)..., i + 1L); }
  for (int i = 0; i < fromList.size(); i++) { this.delegate(fromList.get(i)..., address, i + 1L); }
  this.delete(address);
}
```

Because the pre-optimization append path (`FreezeBalanceActuator.delegateResource`, lines 320-345) never bounds `toAccountsList`/`fromAccountsList` size, and because `calcFee()` for both `FreezeBalanceActuator` and `DelegateResourceActuator` returns `0`, an attacker can cheaply generate many funded accounts that each freeze the minimum 1 TRX and delegate it to a single victim `receiverAddress`, appending one entry per attacker-controlled account to the victim's index with essentially no fee cost beyond minimal bandwidth/energy and the (recoverable) frozen TRX. [5](#0-4) [6](#0-5) 

This mirrors the H-5 bug class precisely: an unrelated/unprivileged actor mutates shared state belonging to a victim, bypassing any limit check that the "owning" logic assumes will always hold, and the first subsequent legitimate operation by (or touching) the victim pays the cost — here, an O(n) `convert()` migration executed synchronously inside a single transaction, for attacker-controlled n.

### Impact Explanation
A victim account can be forced to carry an arbitrarily large `DelegatedResourceAccountIndex`. The first transaction that triggers `convert()` for that address (which could be initiated by the victim itself, or by any third party delegating to/from the victim) must perform O(n) sequential DB read/delegate/delete operations within one transaction's execution budget. For sufficiently large n this creates a DoS/gas-griefing vector against the victim (and against whichever transaction happens to trigger the migration), and represents unbounded, attacker-funded state growth with no cap and no cleanup path — the DelegatedResourceAccountIndexStore never trims stale/spam entries.

### Likelihood Explanation
Reachable entirely via ordinary broadcast transactions (`FreezeBalanceContract`/`DelegateResourceContract`) from any account, requiring no special privileges — only the ability to fund minimal frozen balances across (potentially many) accounts. No consent or check by the receiver is required at any step, matching the "other module can act on shared state" pattern from the source report.

### Recommendation
Cap the size of `fromAccountsList`/`toAccountsList` (or the equivalent V2 per-key index) per account, similar to the `maxFrozenSupplyNumber`/`getTotalSignNum` bounds enforced elsewhere in the actuator layer, and/or perform the V1→V2 `convert()` migration incrementally (e.g., paginated across multiple blocks/transactions) rather than atomically within a single triggering transaction, so that an attacker cannot force unbounded synchronous work onto an unrelated account's transaction.

### Proof of Concept
1. Attacker creates N funded accounts (each holding ≥1 TRX).
2. Each account submits a `FreezeBalanceContract` (or `DelegateResourceContract`) transaction with `receiverAddress` set to the victim's address, delegating the minimum allowed balance.
3. Each call appends one entry to the victim's `DelegatedResourceAccountIndexCapsule.fromAccountsList` via `delegateResource()` with no upper bound. [7](#0-6) 
4. After `supportAllowDelegateOptimization()` becomes active, any transaction that causes `convert(victimAddress)` to run (e.g., the victim performing a new-style delegate, or a third party delegating to/from the victim) must iterate all N legacy entries synchronously inside that single transaction. [4](#0-3)

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
