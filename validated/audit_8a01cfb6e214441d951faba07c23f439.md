## Title
Fixed L1-handler gas cap (`l1_handler_max_amount_bounds` / `L1_HANDLER_L2_GAS_MAX_AMOUNT`) can cause valid L1→L2 messages to revert yet still be irrevocably consumed - ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs], [File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo])

### Summary
Just like the Optimism bug where `MigrateWithdrawalGasLimit()` hard-caps the computed intrinsic gas at 25M even though the real Ethereum block gas limit is 30M — causing genuinely-needed-more-gas withdrawals to be finalizable-but-guaranteed-to-revert and permanently marked done — Starknet's L1-handler execution path grants every L1→L2 message a **fixed** gas budget (`l1_handler_max_amount_bounds` in Rust / `L1_HANDLER_L2_GAS_MAX_AMOUNT` in the Cairo OS) regardless of how much gas the invoked entry point actually needs, while the message-consumption bookkeeping happens independently of whether execution completes successfully.

### Finding Description
In the blockifier, `L1HandlerTransaction::execute_raw` sets the execution gas budget directly from a protocol-wide constant, not from anything the L1 message itself can influence beyond paying "any amount of fee": [1](#0-0) 

If the entry point actually needs more gas/steps than this fixed bound (e.g., because the contract's on-chain state has grown, requiring more computation than when the constant was set), execution reverts (`callWithMinGas`-style out-of-gas or entrypoint failure) and `TransactionReceipt::reverted_l1_handler` is produced instead of a successful receipt: [2](#0-1) 

The equivalent Cairo OS logic consumes the L1→L2 message (the on-chain proof that the message was "used up") *before* the capped, non-reverting execution attempt runs, so consumption is unconditional on whether the fixed budget is sufficient: [3](#0-2) 

Downstream, the batcher explicitly treats any transaction that reached execution (even with a revert) as belonging in `consumed_l1_handler_tx_hashes`, distinct from `rejected_tx_hashes` (which is reserved for hard executor errors, not reverts). This is confirmed by a dedicated regression test: [4](#0-3) [5](#0-4) 

Once `consumed_l1_handler_tx_hashes` is committed to the L1 events provider / transaction manager, the message's record transitions to `Committed` and cannot be re-submitted or retried with more gas — there is no mechanism analogous to "user pays more gas and resubmits": [6](#0-5) 

This is structurally the same root cause as the Optimism finding: a hard, protocol-fixed gas ceiling that is decoupled from the actual (potentially larger) resource need of a specific, otherwise-valid cross-domain message, combined with irreversible "already processed" bookkeeping that occurs regardless of whether the capped execution actually completed the intended work.

### Impact Explanation
An L1→L2 message whose target entry point requires more Sierra gas/steps than the fixed `l1_handler_max_amount_bounds`/`L1_HANDLER_L2_GAS_MAX_AMOUNT` constant will always revert when included, yet is unconditionally marked consumed. Because Starknet does not resend or replay a message once it is consumed, the intended L2 side-effect (e.g., minting/crediting bridged assets, unlocking L2 state tied to the L1 deposit) is permanently lost while the L1 side believes the message was delivered — a form of permanent freezing/loss of funds tied to the L1 message. An adversary who can increase the target contract's state-dependent computation cost (e.g., by making a tracked collection/dictionary large before a victim's L1 message is processed) can deliberately push a legitimate L1 message's required gas above the fixed cap, forcing this outcome for a specific victim.

### Likelihood Explanation
The gas bound is a versioned constant applied identically to *all* L1-handler transactions, so any contract whose L1-handler logic performs state-size-dependent work (loops, dictionary iteration, recursive calls) is a candidate. Triggering it requires only crafting/growing state so that a legitimate L1 message's computation exceeds the fixed cap; no privileged access, and no L1/L2 network-level manipulation is required beyond a normal contract call and a normal L1 message.

### Recommendation
Do not let a fixed protocol-wide gas constant silently determine whether a message's execution outcome is "final." Either (a) size `l1_handler_max_amount_bounds`/`L1_HANDLER_L2_GAS_MAX_AMOUNT` with a wide safety margin above the maximum computation any allowed L1-handler entry point could realistically need (analogous to raising Optimism's cap to the real 30M block limit), and/or (b) decouple "message consumed" from "capped execution reverted due to gas insufficiency" so that a message which reverts purely because of hitting the fixed gas ceiling (as opposed to a genuine business-logic revert) is not treated identically to a completed, successful message — e.g., preserve replayability or route to a distinguishable failure class rather than `consumed_l1_handler_tx_hashes`.

### Proof of Concept
1. Deploy a contract with an `#[l1_handler]` entry point whose gas cost scales with existing on-chain state (e.g., iterating a `Felt252Dict`/array that grows with prior calls), similar to `verify_gas_limits_l1_handler` / `l1_handler_set_value_and_revert` test fixtures. [7](#0-6) 
2. Grow the contract's state (via ordinary `__execute__`/other L1 messages) until the handler's per-call cost approaches `L1_HANDLER_L2_GAS_MAX_AMOUNT`.
3. Send a legitimate L1→L2 message targeting this handler; once state exceeds the threshold, the sequencer executes it with `remaining_gas = l1_handler_bounds.l2_gas.0` (fixed), runs out of gas, and returns `reverted_l1_handler`, per the flow in `L1HandlerTransaction::execute_raw`.
4. Observe via `apollo_batcher::block_builder::collect_execution_results_and_stream_txs` that the transaction hash is nonetheless inserted into `consumed_l1_handler_tx_hashes` and committed, permanently marking the message processed with no possibility of retry.

        self.rollback_staging();
