### Title
`ValidateMultiSign`/`BatchValidateSign` TVM precompiles perform signature checks without consuming or tracking used signatures, enabling replay of authorization proofs - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x0a`, ABI `validatemultisign(address,uint256,bytes32,bytes[])`) and its sibling `BatchValidateSign` recover signer addresses from a caller-supplied hash and return a boolean/weight result, but neither precompile records, marks, or otherwise "consumes" the signatures it validates. This mirrors the exact root cause in the external report: a signature-authorization primitive that only checks *validity of a signature over caller-controlled data* with no nonce, expiry, or used-proof bookkeeping, leaving replay protection entirely to whoever calls it.

### Finding Description
`ValidateMultiSign.execute()` builds the message to verify purely from caller-supplied inputs — `address`, `permissionId`, and an arbitrary `data` blob — with no chain-level nonce, sequence number, or timestamp component: [1](#0-0) 

It then recovers signer addresses and checks accumulated weight against the account's `Permission` threshold, returning `true`/`false` with no side effects that would prevent the identical `(address, permissionId, data, signatures)` tuple from validating successfully again: [2](#0-1) 

`BatchValidateSign.doExecute()` follows the same stateless pattern — it recovers an address from a signature over an arbitrary `hash` and compares it to an expected address, with no tracking of whether that exact signature/hash pair has been "used" before: [3](#0-2) 

Both precompiles are freely callable by any deployed TVM smart contract, from any unprivileged caller, at zero special permission. The design is intentionally analogous to `ecrecover`-style primitives, but — exactly as in the `ResourceLockValidator.validateUserOp()` bug — any downstream contract logic that treats "signature validated by `validatemultisign`" as equivalent to "authorization is single-use" inherits the same replay flaw: nothing in the precompile prevents the identical previously-observed `(address, permissionId, data, signature[])` input from being resubmitted and re-validated an unlimited number of times, in the same or later transactions, by any third party who has seen the tuple on-chain or in the mempool.

### Impact Explanation
If a TVM contract implements an "authorize-once" pattern (e.g., off-chain approved withdrawal, session-key grant, resource lock/bid approval — the same class of pattern the original report flagged) by relying solely on `validatemultisign`/`batchvalidatesign` returning success, an attacker who captures a previously broadcast signature can resubmit the exact same signed proof to force repeated execution of the guarded action, since the precompile provides no anti-replay guarantee. This is a direct parallel to the reported critical-risk impact: attacker-forced re-execution of a privileged action using a reused signature, without any legitimate re-authorization by the signer.

### Likelihood Explanation
High for any contract built on these primitives without independently tracking a nonce/used-proof set, since the precompiles are public, callable by anyone, and the signed payload (`address`, `permissionId`, `data` / `hash`) is visible on-chain or in the mempool once used once. No privileged role or insider access is required — any unprivileged user who can observe a prior valid call can replay it.

### Recommendation
- Document explicitly that `ValidateMultiSign`/`BatchValidateSign` are stateless verification primitives (like `ecrecover`) and that callers MUST embed their own nonce/expiry/used-proof tracking in the signed payload (`data`/`hash`) if the validated signature guards a single-use, state-changing action.
- Consider adding an optional nonce/expiry field convention (and reference implementation) so contract authors are not left to individually re-derive anti-replay handling, reducing the chance that dApps repeat the exact ResourceLockValidator-class bug on top of these precompiles.

### Proof of Concept
1. A dApp built on TVM uses `validatemultisign(address,uint256,bytes32,bytes[])` to gate a withdrawal function: it hashes `(address, permissionId, data)` where `data` encodes a withdrawal amount/recipient, and treats a successful `ValidateMultiSign` result as sufficient authorization to transfer funds.
2. The account owner signs a single authorization for a withdrawal and submits it once.
3. An attacker observes the call (`address`, `permissionId`, `data`, `signatures[]`) on-chain.
4. The attacker resubmits the identical parameters to the dApp's withdrawal function; `ValidateMultiSign.execute()` recomputes the same hash from the same `data`, recovers the same signer, hits the same threshold, and returns `dataOne()` again — exactly as before, because no state was updated in `PrecompiledContracts.java` on the first successful call.
5. The dApp executes the withdrawal a second (and indefinitely repeatable) time using the same original signature, since the underlying precompile never marked it as consumed.
