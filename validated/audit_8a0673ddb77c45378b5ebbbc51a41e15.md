### Title
Attached deposit is silently absorbed and never refunded when an `AddKey`/`DeleteKey` transaction succeeds via the NEAR Wallet Contract - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point is `#[payable]` and accepts an arbitrary `attached_deposit` alongside any parsed Ethereum-style action. For `AddKey`/`DeleteKey` actions, no NEAR value is ever attached to the outgoing promise, yet on successful execution the previously captured `CallerDeposit` is simply discarded instead of being refunded, permanently stranding the caller's funds in the wallet contract.

### Finding Description
`inner_rlp_execute` records the attached deposit into a `CallerDeposit` for any external (non-self) caller: [1](#0-0) 

This `caller_deposit` is threaded through to `rlp_execute_callback`, but is **only used in the failure branch** to issue a refund. On success it is dropped without any use: [2](#0-1) 

The assumption behind this design is that the attached deposit was already forwarded as part of the executed action's `deposit` field (e.g. `FunctionCall`/`Transfer` actions add `additional_value` to their own `yocto_near` field, see `Action::try_into_near_action`): [3](#0-2) 

However, for `AddKey` and `DeleteKey` actions, `Action::value()` always returns zero, and `action_to_promise` never attaches any deposit to the outgoing promise for these two action kinds: [4](#0-3) [5](#0-4) 

There is no validation anywhere in `inner_rlp_execute` that requires `attached_deposit == 0` when the parsed transaction resolves to an `AddKey`/`DeleteKey` action. If a caller (either the account owner themselves calling directly, or a relayer forwarding funds on the owner's behalf) attaches any non-zero deposit to a transaction whose action is `AddKey`/`DeleteKey`, that deposit:
- Is never forwarded to any receiver (since these actions carry no `deposit` field).
- Is never refunded on success, because `rlp_execute_callback`'s `PromiseResult::Successful` branch ignores `caller_deposit` entirely.

The deposit is only refunded when the promise chain *fails* (`PromiseResult::Failed`), which is the opposite of the scenario the report describes — a mismatch between "the check that decides whether the value is used" (action type) and "the actual value transfer" (unconditional `msg.value`/`attached_deposit` acceptance), directly analogous to the `DepositStableCoinToDealer` bug where `asset != weth` skips the deposit-handling path but `msg.value` is still accepted.

### Impact Explanation
Any NEAR attached by an unprivileged caller to a successful `AddKey`/`DeleteKey` transaction through the Wallet Contract becomes permanently stuck in the wallet contract's account balance with no code path to reclaim it — a concrete, transaction-triggered loss/freezing of funds for the depositor. Because `rlp_execute` is a normal payable entry point reachable by any RPC caller or relayer, this is directly reachable by an unprivileged transaction signer, matching the allowed threat model.

### Likelihood Explanation
This can be triggered by any external account (owner or relayer) attaching a non-zero deposit to a wallet-contract transaction that resolves to `AddKey` or `DeleteKey` — for example, a relayer or wallet UI mistakenly including a value/fee field with such a request, or a user assuming the deposit will be applied like it is for `Transfer`/`FunctionCall` actions. No special privileges are required; a single mis-parameterized transaction triggers the loss.

### Recommendation
Reject `AddKey`/`DeleteKey` transactions (or reject the top-level `attached_deposit`) when a non-zero value is attached for action kinds whose `Action::value()` is zero, similar to how the report recommends checking that `msg.value == 0` when the branch that consumes it isn't taken. Alternatively, always refund `caller_deposit` in the `PromiseResult::Successful` branch of `rlp_execute_callback` whenever the executed action did not itself consume that deposit.

### Proof of Concept
1. An external account (not equal to the wallet contract's own account) calls `rlp_execute(target, tx_bytes_b64)` with `attached_deposit = N` yoctoNEAR, where `tx_bytes_b64` decodes to an `AddKey` (or `DeleteKey`) action.
2. `CallerDeposit::new` records `{ account_id: caller, yocto_near: N }`.
3. `action_to_promise` builds a promise for `AddKey`/`DeleteKey` that carries **no deposit**.
4. The promise succeeds; `rlp_execute_callback` hits `PromiseResult::Successful` and returns `ExecuteResponse { success: true, .. }` without ever using `caller_deposit`.
5. The `N` yoctoNEAR attached by the caller remains on the wallet contract's account balance permanently, with no method exposed to reclaim or refund it.

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
}
