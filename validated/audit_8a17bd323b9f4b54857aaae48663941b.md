### Title
Silent asset‑deduction failure lets a market sell order register full quantity without debiting the seller — (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.execute()` creates a market order for `sellTokenQuantity` and later fills it against maker orders, crediting the buyer with `buyTokenId` tokens. [3](#0-2)  Before creating the order it calls `transferBalanceOrToken()` to actually take the sell-side tokens away from the owner's account. For TRC10 assets this method calls `accountCapsule.reduceAssetAmountV2(...)` but ignores its boolean return value. [2](#0-1) 

### Finding Description
This mirrors the Beanstalk "sow more than burned" bug class: an accounting step (order creation / matching, crediting the counter-party) proceeds using the *requested* amount, while the actual debit of the paying asset can silently fail to move the full amount, with the discrepancy never checked.

`reduceAssetAmountV2` only mutates state and returns `true` when `amount > 0 && currentAmount != null && amount <= currentAmount`; otherwise it returns `false` and leaves the account's asset balance untouched. [1](#0-0)  Every other call site that uses this return value treats `false` as a hard failure and throws (e.g., `TransferAssetActuator` throws `ContractExeException("reduceAssetAmount failed !")` when it returns false [4](#0-3) , and `Commons.adjustAssetBalanceV2` throws `BalanceInsufficientException` [5](#0-4) ), confirming that the codebase's own convention is that a `false` return must abort the operation. `MarketSellAssetActuator.transferBalanceOrToken()` breaks this convention — it neither checks the return value nor propagates a failure. [2](#0-1) 

`validate()` does check `ownerAccount.assetBalanceEnoughV2(sellTokenID, sellTokenQuantity, dynamicStore)` beforehand, [6](#0-5)  so a straightforward single-transaction exploit is prevented for that specific check. However, this pre-check only inspects the account state as read at validation time; it does not guarantee that `reduceAssetAmountV2` will succeed at execution time if account asset state has changed between validate and execute (e.g., via the asset-optimization "import" lazy path in `importAsset`, or if the object references diverge due to intervening logic), and it establishes a code pattern where a failure path exists in `execute()` with zero enforcement or error signaling — inconsistent with the strict-accounting invariant enforced everywhere else in the codebase.

### Impact Explanation
If `reduceAssetAmountV2` ever returns `false` in `execute()` (any state divergence between the `validate()` check and `execute()`, e.g. due to future refactors, additional actuators being added to the same transaction, or the account/asset map having been mutated by an earlier assetOptimization import), the seller's order books full `sellTokenQuantity` for matching without ever debiting the tokens, letting a counter-party receive real tokens for tokens that were never actually taken from the seller. This is exactly the accounting-corruption class described in the source report — the "amount used for downstream accounting" (order size / credited match quantity) diverges from the "amount actually moved" (silently-failed reduction), and the discrepancy is unconditionally ignored rather than causing a revert.

### Likelihood Explanation
Reachable directly via an anonymous broadcast `MarketSellAssetContract` transaction — no privileged role required. Under current validate()-then-execute() sequencing on the same account snapshot, this specific return-value swallow is not trivially triggerable in a single isolated transaction, which limits immediate exploitability; the primary risk is architectural fragility (silent failure with no safety net) rather than a proven standalone reachable exploit today.

### Recommendation
Check the return value of `reduceAssetAmountV2` in `MarketSellAssetActuator.transferBalanceOrToken()` and throw `ContractExeException`/abort order creation on `false`, matching the pattern already used in `TransferAssetActuator` and `Commons.adjustAssetBalanceV2`. Add unit tests that force a failure of `reduceAssetAmountV2` inside `execute()` (e.g., via a crafted concurrent asset mutation) to confirm the order is never created/matched in that case.

### Proof of Concept
Not independently reproducible as a standalone single-transaction exploit given the current `validate()` pre-check; the defect is the missing invariant enforcement in `transferBalanceOrToken()` at [2](#0-1) , which would allow order creation/matching to proceed with an unfunded sell leg the moment `reduceAssetAmountV2` returns `false` for any reason.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
