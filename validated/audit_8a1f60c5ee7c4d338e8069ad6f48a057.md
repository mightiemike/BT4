### Title
`BucketStorage::map_open_file` silently swallows all file-open errors when reusing an on-disk accounts-index bucket at restart, masking real corruption/permission failures - (File: bucket_map/src/bucket_storage.rs)

### Summary
`BucketStorage::load_on_restart` calls `map_open_file(path, /*create=*/false, 0, &stats)` to reopen a persisted disk-index bucket file when the validator restarts and tries to reuse its accounts-index bucket map files. `map_open_file` treats *any* `Err` from `OpenOptions::open()` in the non-create path as an unconditional "file doesn't exist, bail without error" case and returns `None`, causing the caller to silently discard the file and fall back to creating a brand-new, empty bucket.

### Finding Description
`map_open_file` is written to only distinguish two outcomes when `create == false`: [1](#0-0) 
This mirrors the audited pattern in the external report: an empty/ambiguous error signal (`Err(err)` from `OpenOptions::open`) is unconditionally mapped to a single assumed benign cause ("file missing, so we can't load it") without inspecting `err.kind()`. In reality, `open()` can fail for many other reasons that are not "the file is absent," e.g. `PermissionDenied`, `EMFILE`/`ENFILE` (too many open files), `EIO` (disk read error), or transient filesystem errors. All of these are silently converted into `None` exactly the same way a legitimately-missing file would be.

The caller, `BucketStorage::load_on_restart`, relies on this `None` to mean "no reusable file, create fresh": [2](#0-1) 
This is invoked from `Bucket::new()`'s restart path, which explicitly deletes the file it could not reuse and creates a new bucket file in its place: [3](#0-2) 

So a transient or permission-related OS error while reopening an existing accounts-index bucket file at startup is treated identically to "there is nothing to reuse," and the pre-existing, valid on-disk bucket file is deleted and silently replaced by an empty one via `restartable_bucket.get()`'s cleanup path: [4](#0-3) 

This is the closest structural analog to the audited bug class: an empty/ambiguous failure signal is used to infer one specific benign root cause (file absence / OOG in the original report) via a catch-all pattern, when the signal can equally originate from unrelated failure modes (disk I/O errors, resource exhaustion, permissions), silently corrupting state instead of surfacing/handling the real error.

### Impact Explanation
The accounts index disk bucket map is part of `AccountsIndex`'s on-disk backing store; losing/recreating an index bucket at restart means the in-memory index built during `generate_index()` will not be able to reuse the previously persisted disk-index contents for that bucket, and the "reused_file_at_startup" fast-path optimization silently degrades to slow-path rebuild for that bucket. Because the failure is swallowed without any log or metric, an operator has no visibility that a bucket restart-reuse silently failed due to (e.g.) a permission or I/O problem rather than genuine absence, which could mask underlying storage degradation. Since `delete_file_on_drop = false`/deletion of the "unreusable" candidate is driven straight off this misclassified `None`, and the file that could not be reopened is unlinked, this can cause loss of disk-index data that was otherwise valid and only failed to open due to a transient condition. This does not affect consensus-critical hashing/capitalization since index rebuild logic recomputes state, but it is a disproportionate storage-management fault: legitimate disk state is destroyed based on an error that doesn't actually indicate corruption or absence.

### Likelihood Explanation
This path only triggers during `load_on_restart` (validator restart with fastboot/bucket-map persistence enabled) when the underlying `OpenOptions::open()` call returns an OS error other than "not found," e.g. due to resource limits (`EMFILE`), permission changes, or storage I/O errors on the accounts-index drive. This is plausible under real-world file-descriptor exhaustion or disk-health issues during restart, matching the same "low but realistic" likelihood profile the judges accepted for the original medium-severity finding (there, an unusual-but-real ERC20 revert; here, a real-but-uncommon OS-level open() failure).

### Recommendation
In `map_open_file`, when `create == false`, inspect `err.kind()`. Only treat `std::io::ErrorKind::NotFound` as the benign "nothing to reuse" case and return `None`; for any other error kind, propagate the error (e.g., log at `warn!`/`error!` with the path and error, and/or return a `Result` instead of `Option`) so the caller can decide whether to delete the file or preserve it and fail loudly instead of silently discarding potentially valid index bucket state.

### Proof of Concept
1. Run a validator with the disk-based `bucket_map` accounts index enabled and a persisted restart file (fastboot) from a previous run.
2. On restart, artificially cause the specific bucket file being reopened via `load_on_restart`'s `map_open_file(&path, false, 0, &stats)` call to fail `OpenOptions::open()` with a non-`NotFound` error, e.g. by revoking read/write permission on that single bucket file, or exhausting the process's open file descriptor limit right before this call.
3. Observe that `map_open_file` returns `None` regardless of the actual `err.kind()`.
4. `load_on_restart` propagates `None`, `Bucket::new()` treats this as "could not reuse," calls `fs::remove_file(path)` on the bucket file and creates a brand-new empty bucket instead.
5. The previously valid on-disk index bucket contents are permanently lost with no error surfaced to the operator, even though the root cause was not "file is absent."

    /// load and mmap the file that is this disk bucket if possible
    pub(crate) fn load_on_restart(
        path: PathBuf,
        elem_size: NonZeroU64,
        max_search: MaxSearch,
        stats: Arc<BucketStats>,
        count: Arc<AtomicU64>,
    ) -> Option<Self> {
        let offset = Self::get_offset_to_first_data();
        let num_elems = std::fs::metadata(&path)
            .ok()
            .map(|metadata| metadata.len().saturating_sub(offset) / elem_size)?;
        if num_elems == 0 {
            return None;
        }
        let mmap = Self::map_open_file(&path, false, 0, &stats)?;
        Some(Self {
            path,
            mmap,
            cell_size: elem_size.into(),
            count,
            stats,
            max_search,
            contents: O::new(Capacity::Actual(num_elems)),
            // since we loaded it, it persisted from last time, so we obviously want to keep it present disk.
            delete_file_on_drop: false,
        })
    }
