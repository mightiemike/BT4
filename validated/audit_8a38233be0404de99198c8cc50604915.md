### Title
Independent per-call truncation in `FreezeBalanceProcessor.execute` combined with aggregate-truncation in `UnfreezeBalanceProcessor.execute` allows attacker-driven drift of `totalNetWeight`/`totalEnergyWeight` - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java])

### Summary
`UnfreezeBalanceProcessor.execute` (lines 190-201) subtracts `unfreezeBalance / TRX_PRECISION` from the global `totalNetWeight`/`totalEnergyWeight` based on the full accumulated frozen balance at unfreeze time, while `FreezeBalanceProcessor.execute` (lines 118-129) adds `frozenBalance / TRX_PRECISION` per individual freeze call, using only that call's own (non-cumulative) amount. Because the legacy freeze model only permits a single Frozen slot per account (merging repeated freezes into one balance) but unfreezes it all at once, an attacker who freezes in several fractional-TRX chunks via the TVM `FREEZE`/`UNFREEZE` opcodes (`Program.freeze`/`Program.unfreeze`) causes the sum of per-call floor-divisions added at freeze time to be systematically smaller than the single floor-division subtracted at unfreeze time, producing a persistent negative drift in the global weight totals with each cycle.

### Finding Description
`FreezeBalanceProcessor.validate` only requires `frozenBalance >= TRX_PRECISION` (1 TRX), not that it be an exact multiple of `TRX_PRECISION` [1](#0-0) , and further requires `frozenCount` to be 0 or 1, meaning repeated freezes on the same account/resource type keep merging into a single `Frozen` entry via `accountCapsule.setFrozenForBandwidth(frozenBalance + accountCapsule.getFrozenBalance(), expireTime)` [2](#0-1) [3](#0-2) .

Critically, the global weight adjustment on each freeze call uses only that call's own `frozenBalance`, not the cumulative total: [4](#0-3) 

Then `UnfreezeBalanceProcessor.execute` reads back the full accumulated `Frozen` balance and unfreezes it in one shot, applying a single floor-division on that true total: [5](#0-4) 

Exploit flow (reachable by any unprivileged contract via the TVM `FREEZE`/`UNFREEZE` opcodes, implemented as `Program.freeze`/`Program.unfreeze` which instantiate `FreezeBalanceProcessor`/`UnfreezeBalanceProcessor` directly): [6](#0-5) [7](#0-6) 

1. Attacker's contract calls `freeze()` with 1.5 TRX (1,500,000 sun) → `frozenBalance/TRX_PRECISION = 1` added to `totalNetWeight`; account now holds 1.5 TRX frozen.
2. Attacker calls `freeze()` again with 1.5 TRX → merges into the single Frozen slot, now 3.0 TRX total, but the weight delta added is again `1,500,000/1,000,000 = 1` (not the cumulative delta), so `totalNetWeight` has only gained `+2` total, even though the true weight for 3.0 TRX frozen should be `3`.
3. Attacker calls `unfreeze()` once the lock period expires → the full 3,000,000 sun is unfrozen in one call, and `totalNetWeight` is decremented by `3,000,000/1,000,000 = 3`.
4. Net effect over the complete freeze→freeze→unfreeze cycle: `totalNetWeight` changes by `+1+1-3 = -1`, even though the account's true frozen balance returned to the original baseline (net zero). This decrement is entirely attacker-controlled by choosing the number and size of fractional-TRX freeze calls before a single aggregate unfreeze.

This differs materially from the newer `FreezeBalanceV2Processor`/`FreezeBalanceV2Actuator`, which correctly compute `oldWeight`/`newWeight` from the account's true cumulative frozen balance and apply the *difference* as the delta, avoiding this drift: [8](#0-7) 

No auth/accounting guard prevents this: `validate()` in both processors only checks positivity, minimum 1 TRX, and balance sufficiency — none enforce that frozen amounts are exact multiples of `TRX_PRECISION`, and nothing reconciles per-call truncation against the aggregate truncation used at unfreeze time.

### Impact Explanation
`totalNetWeight`/`totalEnergyWeight` are globally shared chain state read by `BandwidthProcessor`/`EnergyProcessor` to compute the network-wide bandwidth/energy unit price (price is inversely related to total weight versus total frozen stake). Any unprivileged account can repeatedly execute fractional-TRX freeze/unfreeze cycles through TVM opcodes to drift these totals away from the true aggregate frozen stake, at the cost only of the TRX being temporarily locked (no burn, no fee beyond gas), causing systemic, network-wide mispricing of bandwidth/energy — a public-cost integrity issue affecting all users, not just the attacker.

### Likelihood Explanation
Fully reachable by an unprivileged actor: any contract can call the `FREEZE`/`UNFREEZE` TVM opcodes with arbitrary amounts ≥ 1 TRX, and nothing enforces exact-multiple-of-`TRX_PRECISION` amounts. The only precondition is the standard freeze lock duration (`FROZEN_PERIOD`, controlled via `frozenDuration`, which can be set to 0 via `CommonParameter.getCheckFrozenTime()` test flag or minimally via `getMinFrozenTime()` in production) before unfreezing. Because the drift is proportional to the number of fractional freeze calls performed before a single unfreeze, it is fully repeatable and scales with attacker effort and capital lock-up time, making it a low-cost, highly repeatable griefing vector against network-wide pricing accuracy.

### Recommendation
Change `FreezeBalanceProcessor.execute`'s weight bookkeeping to compute the delta the same way `FreezeBalanceV2Processor` does: derive `oldWeight = existingFrozenBalance / TRX_PRECISION` before merging, `newWeight = (existingFrozenBalance + frozenBalance) / TRX_PRECISION` after merging, and add `newWeight - oldWeight` to `totalNetWeight`/`totalEnergyWeight`, rather than adding `frozenBalance / TRX_PRECISION` independently per call. This keeps the freeze-side and unfreeze-side truncation consistent against the same true cumulative balance, eliminating drift.

### Proof of Concept
```java
// Invariant test sketch, e.g. added to FreezeBalanceActuatorTest / a new test class
@Test
public void testTotalNetWeightDriftOnFractionalFreezeUnfreezeCycles() throws Exception {
  // setup: fresh account with sufficient balance, dynamicStore.addTotalNetWeight starts at 0
  long baselineWeight = dynamicStore.getTotalNetWeight();

  FreezeBalanceProcessor freezeProcessor = new FreezeBalanceProcessor();
  UnfreezeBalanceProcessor unfreezeProcessor = new UnfreezeBalanceProcessor();

  // Two fractional freezes of 1.5 TRX each (not multiples of TRX_PRECISION)
  FreezeBalanceParam p1 = buildFreezeParam(owner, owner, 1_500_000L, BANDWIDTH);
  freezeProcessor.validate(p1, repo);
  freezeProcessor.execute(p1, repo);

  FreezeBalanceParam p2 = buildFreezeParam(owner, owner, 1_500_000L, BANDWIDTH);
  freezeProcessor.validate(p2, repo);
  freezeProcessor.execute(p2, repo);

  // advance block time past expire time
  dynamicStore.saveLatestBlockHeaderTimestamp(now + FROZEN_PERIOD + 1);

  UnfreezeBalanceParam up = buildUnfreezeParam(owner, owner, BANDWIDTH);
  unfreezeProcessor.validate(up, repo);
  long unfrozen = unfreezeProcessor.execute(up, repo);

  Assert.assertEquals(3_000_000L, unfrozen); // full 3 TRX returned, balance correctly restored

  long finalWeight = dynamicStore.getTotalNetWeight();
  // Expected (correct) invariant: finalWeight == baselineWeight (net zero cycle)
  // Actual (buggy) behavior: finalWeight == baselineWeight - 1
  Assert.assertNotEquals("totalNetWeight drifted from true aggregate frozen stake",
      baselineWeight, finalWeight);
}
```
Run this across many randomized N-freeze-then-unfreeze cycles with amounts not evenly divisible by `TRX_PRECISION` (e.g., property-based/fuzz test summing all `addTotalNetWeight` deltas and comparing against `trueAggregateFrozenStake / TRX_PRECISION`) to demonstrate the drift accumulates monotonically and is fully attacker-controlled.

  public boolean unfreeze(DataWord receiverAddress, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver, 0, null,
        "unfreezeFor" + convertResourceToString(resourceType), nonce, null);

    UnfreezeBalanceParam param = new UnfreezeBalanceParam();
    param.setOwnerAddress(owner);
    param.setReceiverAddress(receiver);
    param.setResourceType(parseResourceCode(resourceType));
    try {
      UnfreezeBalanceProcessor processor = new UnfreezeBalanceProcessor();
      processor.validate(param, repository);
      long unfreezeBalance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(unfreezeBalance);
      }
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM Unfreeze: validate failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }
