Confirmed: `ExchangeTransactionActuator` (the swap path) enforces a caller-supplied minimum-output check — `anotherTokenQuant < tokenExpected` throws `ContractValidateException("token required must greater than expected")` [1](#0-0) . But `ExchangeInjectActuator` (the liquidity-add path, TRON's Bancor-style "Exchange" AMM analog to Uniswap's `addLiquidity`) has no such caller-supplied minimum for the second token quantity it computes and pulls from the depositor.

### Title
Exchange (TRON Bancor-style AMM) liquidity injection lacks minimum-output/slippage protection, enabling sandwich attacks - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectContract`/`ExchangeInjectActuator` implements TRON's built-in AMM liquidity-provision function (the analog of `addLiquidity` in the reported Vader bug). It computes the counter-token amount proportionally from the current pool reserves and silently deducts it from the depositor's balance, with no field allowing the caller to bound the amount they are willing to contribute relative to the pool state at submission time.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no "expected"/minimum field [2](#0-1) . In `ExchangeInjectActuator.doValidate()` and `execute()`, the amount of the *other* token the user must contribute (`anotherTokenQuant`) is derived purely from whatever `firstTokenBalance`/`secondTokenBalance` happen to be in the pool at execution time, using a ratio calculation with no user-supplied bound [3](#0-2) . The same unconstrained calculation is repeated in `execute()` [4](#0-3) .

By contrast, the swap path `ExchangeTransactionContract` explicitly includes an `expected` field [5](#0-4)  that is enforced in `ExchangeTransactionActuator.doValidate()`: `if (anotherTokenQuant < tokenExpected) { throw new ContractValidateException("token required must greater than expected"); }` [1](#0-0) . This shows the protocol designers recognized the need for slippage protection on trades, but the same protection was never applied to liquidity injection.

This mirrors the reported Vader issue exactly: `addLiquidity`-style operations that price a second asset off the live pool ratio, executed without a bound, are exploitable by front-running the reserve ratio (e.g., via an `ExchangeTransactionContract` trade) immediately before the victim's `ExchangeInjectContract` is packed into the same block, then reversing the trade afterward to extract the difference — a classic sandwich/MEV attack, here executable by any block-producing witness or MEV searcher able to reorder transactions within a block.

### Impact Explanation
A block producer (witness) or a party colluding with one can reorder transactions to sandwich an `ExchangeInjectContract`: skew the pool ratio with a large opposing trade, force the victim's inject to deposit at the skewed ratio (silently draining more of the victim's counter-token than a fair-price deposit would require), then trade back to restore the ratio and capture the difference. This is a concrete value-extraction/accounting impact against unprivileged liquidity providers using TRON's native Exchange feature, not a theoretical or mocked-only scenario — the actuator logic and lack of bound are present in the current production contract path.

### Likelihood Explanation
Likelihood is elevated by the fact that TRON block producers control transaction ordering within blocks they produce, and this exchange feature is a first-class, unprivileged, on-chain function reachable by any account holding TRX/TRC10 assets. The absence of any user-configurable minimum ratio or maximum slippage bound means every `ExchangeInjectContract` submission is exposed whenever pool liquidity is imbalanced or thin enough for the ratio to be meaningfully moved within a block (this mirrors the "illiquid pool" precondition noted in the original report).

### Recommendation
Add a minimum-received/maximum-slippage-style bound to `ExchangeInjectContract` (e.g., a `min_another_token_quant` field), analogous to the `expected` field already present on `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` by rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller-specified bound.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from a victim in the mempool that will inject `tokenQuant` of `firstTokenID`, expecting the pool to compute `anotherTokenQuant` proportional to current `firstTokenBalance`/`secondTokenBalance` [6](#0-5) .
2. Attacker (or colluding witness) submits an `ExchangeTransactionContract` trade before the victim's transaction that heavily skews `firstTokenBalance`/`secondTokenBalance` in the same exchange.
3. Victim's `ExchangeInjectContract` executes against the skewed reserves, causing the actuator to compute a larger `anotherTokenQuant` than the victim expected, deducting more of their asset via `reduceAssetAmountV2` with no cap [7](#0-6) .
4. Attacker submits a reversing `ExchangeTransactionContract` trade to restore the ratio, extracting the difference as profit, all within the same block due to witness-controlled ordering.

I was unable to independently verify witness-level transaction-ordering guarantees or block-packing behavior in this session (that logic lives outside the files inspected here), so the block-producer-reordering precondition is stated based on general TRON DPoS block-production design rather than direct code confirmation.
