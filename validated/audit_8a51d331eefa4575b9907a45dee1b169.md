### Title
Backslash-prefixed relative URL bypasses `isSafe()` host allowlist, enabling unauthenticated open redirect via `exitIframe`/`redirectTo.url` - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts)

### Summary
`sanitizeRedirectUrl`/`isSafe` in `validate-redirect-url.ts` is meant to guarantee that any URL passed to `renderAppBridge` resolves under `config.appUrl`'s origin. Because the WHATWG `URL` parser treats backslash (`\`) the same as forward slash (`/`) for special schemes (http/https), a value like `/\attacker.com` resolves to a completely different host, and the library's regex checks never catch this since they inspect the wrong properties.

### Finding Description
`isSafe()` runs two structural checks before calling `new URL(redirectUrl, domain)`:
- `FILE_URI_MATCH = /\/\/\//` (looks for three literal forward slashes)
- `WHITESPACE_CHARACTER`

then, only *after* parsing, checks `INVALID_RELATIVE_URL = /[/\\][/\\]/` against `url.pathname` (not the raw input, not `url.host`): [1](#0-0) 

For input `redirectUrl = "/\\attacker.com"` (a `/` followed by a single backslash), neither `FILE_URI_MATCH` nor `WHITESPACE_CHARACTER` match. Per the WHATWG URL Standard, when parsing a relative reference against a special-scheme base (https), a backslash is treated identically to a forward slash in the "relative slash state"/"special authority ignore slashes state". This means `/\attacker.com` is interpreted as a scheme-relative authority reference (equivalent to `//attacker.com`), so `new URL('/\\attacker.com', 'https://app.example.com').host === 'attacker.com'`, while `url.pathname` becomes just `'/'`. Since `INVALID_RELATIVE_URL` is tested against `url.pathname` — which no longer contains any doubled slash/backslash because the host already absorbed it — the check passes, `VALID_PROTOCOLS`/SSL checks pass (protocol is inherited as `https:`), and `isSafe()` returns `true`. `sanitizeRedirectUrl` then returns a `URL` object pointing at `attacker.com` instead of `config.appUrl`.

This is reachable by an unauthenticated attacker through `respondToExitIframeRequest` in `authenticate.ts`, which reads the `exitIframe` query parameter directly from the request URL with no auth/session requirement and passes it straight to `renderAppBridge`: [2](#0-1) 

`renderAppBridge` then calls `sanitizeRedirectUrl(config.appUrl, redirectTo.url)` and embeds the (attacker-controlled) result verbatim into a `window.open(...)` script served to the merchant's browser: [3](#0-2) 

The same bypass affects any other caller of `sanitizeRedirectUrl`/`renderAppBridge` with attacker-influenced `redirectTo.url`, such as `redirectFactory`'s `_parent`/`_top`/bounce-page flows. [4](#0-3) 

### Impact Explanation
This is an unauthenticated open redirect out of an embedded Shopify admin app to an attacker-chosen origin, delivered via a top-level `window.open` triggered by App Bridge's exit-iframe/bounce mechanism. A merchant clicking an attacker-crafted link to `{appUrl}/auth/exit-iframe?exitIframe=/\%5Cattacker.com&shop=...` would have their top-level browsing context redirected to `https://attacker.com`, which can be used for phishing (spoofing a fake Shopify admin/app login) or OAuth-consent phishing. This matches Shopify's "open redirect" bounty impact class.

### Likelihood Explanation
Fully unauthenticated and requires only sending a link/URL to a victim merchant; no secrets, privileged roles, or non-default configuration are needed. The `exitIframe` path is a documented, always-available library route (`config.auth.exitIframePath`), and the bypass string is trivial and deterministic (works for any `domain`/`config.appUrl` with a special scheme).

### Recommendation
Do not rely on regex checks against `url.pathname` post-parse. Instead, after constructing `url = new URL(redirectUrl, domain)`, validate that `url.host === new URL(domain).host` (or `url.origin === new URL(domain).origin`) explicitly, rejecting any redirect whose resolved origin differs from the configured app origin — this closes the backslash-authority trick regardless of how the parser interprets the input.

```ts
import {sanitizeRedirectUrl} from '../validate-redirect-url';

it('BUG: backslash-prefixed relative URL bypasses host allowlist', () => {
  const appUrl = 'https://app.example.com';
  const result = sanitizeRedirectUrl(appUrl, '/\\attacker.com');

  // Expected (per invariant): result.host === new URL(appUrl).host
  // Actual: result.host === 'attacker.com'
  expect(result.host).not.toBe(new URL(appUrl).host);
  expect(result.host).toBe('attacker.com');
});
```

```typescript
const FILE_URI_MATCH = /\/\/\//;
const INVALID_RELATIVE_URL = /[/\\][/\\]/;
const WHITESPACE_CHARACTER = /\s/;
const VALID_PROTOCOLS = ['https:', 'http:'];

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
```
