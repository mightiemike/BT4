### Title
Missing declared-class check in Starknet OS `execute_replace_class` allows OS/Blockifier execution divergence - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The Cairo Starknet OS implementation of the `replace_class` syscall handler, `execute_replace_class`, unconditionally updates a contract's class hash in `contract_state_changes` without verifying that the target `class_hash` corresponds to a declared contract class. This is explicitly marked with a TODO acknowledging the missing check. In contrast, the actual sequencer execution engine (blockifier, Rust) enforces this check before performing the state change.

### Finding Description
`execute_replace_class` in `syscall_impls.cairo` reads the `class_hash` from the syscall request and immediately commits a new `StateEntry` with that class hash to `contract_state_changes`, with only a TODO comment noting the missing validation: [1](#0-0) 

The equivalent syscall handler in the deprecated syscall path (`deprecated_execute_syscalls.cairo`) has the same gap — it commits the new class hash to state without any declared-class check: [2](#0-1) 

This is inconsistent with the actual sequencer execution logic in the Rust `blockifier`, where `replace_class` explicitly requires that the class be declared (by reading the compiled class) and additionally rejects Cairo0 class hashes: [3](#0-2) 

The Rust unit tests confirm this is enforced behavior at the blockifier level — replacing with an undeclared class hash is a documented negative-flow error ("is not declared"): [4](#0-3) 

The Starknet OS is the component that re-executes/verifies the block's transactions (using the block's execution trace and hints) to produce the committed state diff, state root, and block hash that is proven and posted for consensus. Because the OS's own Cairo implementation of `execute_replace_class` does not perform the declared-class check that the block-producing blockifier enforces, any contract that reaches the `ReplaceClass` syscall with an undeclared (or otherwise invalid) class hash may be treated differently by the two components:
- In the actual sequencer execution (blockifier), a call to `replace_class` with an undeclared class hash fails/reverts the call, so the class hash is **not** changed in the state diff that blockifier produces for the block.
- In the OS re-execution of that same trace, `execute_replace_class` blindly trusts the hint-provided `state_entry` and writes the new (undeclared) class hash into `contract_state_changes` with no validation, `dict_update`-ing the state and appending only to the revert log — with no failure path corresponding to the blockifier's rejection.

This means the OS's model of "what syscall calls succeeded/failed and what state changes resulted" can diverge from the blockifier's real execution result for this specific syscall, since the check that gates success/failure in one component is absent in the other.

### Impact Explanation
Any account/contract that is deployed by an ordinary transaction sender can trigger a `ReplaceClass` syscall (a normal, permissionless Starknet operation — a contract is always allowed to replace its own class hash, this is by design). The vulnerability is not that ownership/authorization is bypassed (the `contract_address`/`self` semantics of `replace_class` are correctly scoped to the calling contract in both implementations), but that the **declared-class precondition** enforced in production execution is missing in the OS's re-execution/verification logic. A divergence between what the sequencer actually executed (and committed to state) and what the OS accepts/commits as the trace is validated can result in:
- The OS computing a different state diff / state root / block hash than what was actually produced and applied by the block-building sequencer for the same transaction trace.
- Honest-node divergence between block execution (blockifier) and OS-based proof/verification of that same block, undermining the correctness guarantee that the committed root faithfully represents applied transactions.

This falls squarely under the accepted impact categories: "wrong committed root or block hash" and "honest-node divergence" as required by the validation rules.

### Likelihood Explanation
The class of trigger (a contract calling the `replace_class` syscall with an arbitrary, attacker-chosen class hash, including undeclared ones) is trivially reachable by any unprivileged transaction sender who deploys or calls a simple contract executing `replace_class_syscall(class_hash)`. No special privileges, node compromise, or p2p manipulation are needed — it is a standard syscall available to every deployed contract. The TODO comment in the code itself ("Check that there is a declared contract class with the given hash") confirms this is a known, currently-unimplemented gap rather than a hardened, intentional design decision.

### Recommendation
Add the missing declared-class validation in the OS's Cairo `execute_replace_class` (and the deprecated equivalent) so that it mirrors the blockifier's `replace_class` semantics exactly: verify that `class_hash` corresponds to a declared compiled class (and, if matching blockifier's Cairo1-only restriction, reject Cairo0 class hashes) before committing the `StateEntry` update to `contract_state_changes`. Ensure the failure/success path (and any gas/response semantics) is consistent between the two execution engines so that the OS's accepted state diff can never diverge from what the actual sequencer execution produced for this syscall.

### Proof of Concept
1. Deploy a contract (via a standard `DEPLOY`/`DEPLOY_ACCOUNT` transaction from any unprivileged account) whose code, on invocation, calls `replace_class_syscall(class_hash)` with a `class_hash` that has never been declared on the network (an arbitrary/undeclared felt value), analogous to the `test_forbidden_syscall_in_virtual_mode`/`ReplaceClass` test harness pattern already present in the test contracts: [5](#0-4) 
2. Submit an `INVOKE` transaction from any account calling this contract's replace-class entry point.
3. Observe that blockifier (production execution) rejects the call and does not perform the class hash state change, per the enforced check in `syscall_base.rs::replace_class` and the corresponding unit test `undeclared_class_hash`: [6](#0-5) 
4. Feed the identical execution trace/hints into the Starknet OS's `execute_replace_class` (`syscall_impls.cairo`), and observe that — absent the check flagged by the `TODO(Yoni, 1/1/2026)` comment — the OS commits the undeclared class hash into `contract_state_changes` unconditionally: [7](#0-6) 
5. Compare the two resulting state diffs/roots for the same transaction trace — they diverge, demonstrating the honest-node/committed-root discrepancy between the sequencer's real execution and the OS's validation of that execution.

Note: I was unable to fully trace whether any later commitment-time validation (outside these syscall-handling files, e.g., in the bouncer, aliasing, or Patricia-tree commitment code) independently catches undeclared class hashes before final block hash/state-root computation; this could not be fully verified within the indexed portions of the codebase, and a Devin session with full repository access would be needed to rule out a compensating control elsewhere in the OS pipeline.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
