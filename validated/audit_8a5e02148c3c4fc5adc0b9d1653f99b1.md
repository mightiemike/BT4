### Title
Reward-Per-Vote (Vi) Overflow via Division by Near-Zero Vote Count in `DelegationStore.accumulateWitnessVi` - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
`DelegationStore.accumulateWitnessVi()` computes a per-vote reward index (`deltaVi = reward * 1e18 / voteCount`) with no lower bound on `voteCount`. Because block rewards paid to top-27 witnesses are flat, fixed amounts independent of the witness's actual vote count, a witness with a very small vote count can generate an extremely large `deltaVi`. This value is later multiplied back by a voter's `userVote` in `MortgageService.computeReward()` and converted with `BigInteger.longValue()`, which silently truncates/wraps on overflow instead of throwing — directly mirroring the "amount/near-zero-balance" share-inflation root cause in the Burve report, but worse because Java's `long` arithmetic wraps silently rather than reverting.

### Finding Description
`accumulateWitnessVi` guards only against `voteCount == 0`, not against small nonzero values: [1](#0-0) 

This is invoked every maintenance cycle for *every* witness using the witness's live vote count: [2](#0-1) 

Rewards fed into this computation come from `payBlockReward`/`payTransactionFeeReward`, which credit a **flat amount per block** (e.g. fixed block reward + full tx fees) to whichever witness produced the block, with no relation to that witness's total vote count: [3](#0-2) 

So if a witness's `voteCount` (denominator) is very small while it still receives full block rewards (numerator) — plausible on chains/testnets with few candidates, or after mass unvoting drives a witness's tally near the minimum needed to stay in the active set — `deltaVi` inflates sharply, exactly like `ReserveLib.deposit()`'s `amount * shares / balance` inflating when `balance ≈ 0`.

The inflated `deltaVi` is persisted unbounded as a `BigInteger` per cycle and accumulates cycle over cycle (`preVi.add(deltaVi)`): [4](#0-3) 

When a voter later withdraws, this accumulated Vi delta is multiplied back by the voter's own `userVote` and converted to a `long` via the non-exact `.longValue()` (which wraps silently on overflow rather than throwing, unlike `.longValueExact()` used elsewhere in the codebase for similar operations): [5](#0-4) 

The resulting (possibly wrapped/negative) `reward` is then added directly into the user's on-chain `allowance` with a plain, unchecked `long` addition: [6](#0-5) 

There is no bound check comparable to Solidity's automatic overflow revert (`0x11` panic) — Java `long` addition/`BigInteger.longValue()` truncation degrade gracefully into corrupted state rather than reverting, so the corruption is silent, matching the report's "no reverts occur... silent amplification" impact description.

### Impact Explanation
An inflated `Vi` (or reward variable that wraps to a large/negative `long`) directly corrupts a real economic accounting value — the account's `allowance`, which is later paid out as TRX via `withdrawReward`/`withdrawBalance` flows. This can:
- silently inflate a voter's claimable reward far beyond what the protocol actually earned (fund drain from protocol reserves), or
- wrap the allowance to a large negative number, breaking that account's ability to withdraw rewards (denial of value / accounting divergence) and potentially breaking later `adjustAllowance` sign checks (`amount < 0 && allowance < -amount`) that assume sane, unwrapped values.

Since `Vi` values accumulate across cycles without any cap, a single low-vote-count cycle taints all subsequent reward computations for that witness's voters indefinitely, matching the "irreversible corruption of internal accounting" impact in the source report.

### Likelihood Explanation
Reaching a very small nonzero `voteCount` for an actively rewarded witness (top 27, receiving flat per-block rewards independent of vote share) requires only ordinary, unprivileged voting/unvoting actions plus normal block production — no privileged role is needed. This is more easily triggered on chains with few candidate witnesses (common on non-mainnet/private/consortium deployments running this same codebase) where witnesses can occupy an active slot with minimal votes while still collecting full flat block rewards every cycle they produce blocks.

### Recommendation
Enforce a sane minimum `voteCount` threshold before computing `deltaVi` in `accumulateWitnessVi` (analogous to imposing a minimum deposit/balance in the Burve fix), and replace `BigInteger.longValue()` with `longValueExact()` in `MortgageService.computeReward()` so that any overflow throws instead of silently truncating, and add explicit overflow checks (e.g., `Math.addExact`) in `adjustAllowance`'s `allowance + amount` addition rather than plain `+`.

### Proof of Concept
1. Configure a private/test network with few witness candidates so a witness can be in the active top-27 set with a minimal `voteCount` (e.g., `voteCount = 1`).
2. Let that witness produce several blocks, receiving the flat block reward each time via `payBlockReward` (`MortgageService.java:69`), which is added to `delegationStore.addReward(cycle, ...)` unconditionally of vote share.
3. At maintenance, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` with the tiny `voteCount`, producing a hugely inflated `deltaVi = reward * 1e18 / 1`.
4. Have the (small number of) voters for this witness call `withdrawReward`; `MortgageService.computeReward()` multiplies the inflated `deltaVi` by `userVote` and truncates via `.longValue()`, producing an incorrect (possibly wrapped/negative) `reward` value that is added unchecked to the account's `allowance`.
5. Observe the account's `allowance`/withdrawable TRX diverges from the protocol's actual accumulated reward pool, demonstrating the same "silent amplification through rounding/near-zero-denominator division" root cause described in the Burve report, translated to java-tron's witness reward accounting.

    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }
