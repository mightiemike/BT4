### Title
Ancient-append-vec repacking can move a multi-ref account to a slot *lower* than its source slot, resurrecting stale balances - (File: `accounts-db/src/ancient_append_vecs.rs`)

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` uses a simplistic byte-division formula to estimate how many packed storages will be consumed by "many-ref, newest-alive" accounts, but the actual bin-packer (`PackedAncientStorage::pack`) packs data at whole-slot/whole-account granularity and can silently need more storages than the formula predicts. When this happens, `combine_ancient_slots_packed_internal`/`write_packed_storages` can map an older multi-ref account group to a target slot that is *lower* than the account's original (source) slot, violating the "moved to slot >= current slot" invariant.

### Finding Description
`many_ref_accounts_can_be_moved` (`accounts-db/src/ancient_append_vecs.rs:390-415`) computes:
```
required_ideal_packed = alive_bytes / ideal_storage_size + 1
highest_slot = target_slots_sorted[target_slots_sorted.len() - required_ideal_packed]
return many_refs_newest.iter().all(|many| many.slot <= highest_slot)
```
This assumes the many-ref accounts can be tightly packed into exactly `required_ideal_packed` storages (a pure byte-division estimate). But `PackedAncientStorage::pack` (`accounts-db/src/ancient_append_vecs.rs:1009-1095`) is a next-fit bin packer that operates over whole `AliveAccounts` groups (one per originating slot) and cannot split an individual account across storages; when it can't fit the next group's remaining bytes into the current storage it starts a *new* storage instead (`accounts-db/src/ancient_append_vecs.rs:1041-1068`). For groups whose sizes are just over half of `ideal_storage_size`, this produces one storage *per group* instead of the byte-optimal packing, so the real number of many-ref storages can exceed `required_ideal_packed`.

Concretely: with `ideal_storage_size = 1000` and three many-ref-newest groups from origin slots 450, 400, 300, each with 501 bytes, `alive_bytes = 1503`, so `required_ideal_packed = 1503/1000 + 1 = 2`. If `target_slots_sorted = [50, 450, 600]`, `i_last = 3 - 2 = 1`, `highest_slot = target_slots_sorted[1] = 450`, and all three group slots (`450, 400, 300`) are `<= 450`, so `many_ref_accounts_can_be_moved` returns `true`. But `pack()` actually produces **3** separate storages (one per group, because 501+501 > 1000), which equals `target_slots_sorted.len()` (3), so the overflow guard at `accounts-db/src/ancient_append_vecs.rs:506-509` (`pack.len() > accounts_to_combine.target_slots_sorted.len()`) does not trigger either.

`write_packed_storages` (`accounts-db/src/ancient_append_vecs.rs:646-701`) then zips `target_slots_sorted.iter().rev()` (descending: `600, 450, 50`) with the packed storages in original order (group@450, group@400, group@300):
- group@450 → target slot 600 (OK, 600 ≥ 450)
- group@400 → target slot 450 (OK, 450 ≥ 400)
- group@300 → target slot **50** (VIOLATION: 50 < 300)

The account whose newest slot_list entry was at slot 300 is rewritten into the index at slot 50, which is lower than its actual most-recent slot. If an older, still-alive entry for the same pubkey exists at a slot between 50 and 300 (`many_refs_old_alive`, which is preserved untouched at its own slot per `accounts-db/src/ancient_append_vecs.rs:869-899`), that older entry now becomes the highest-slot entry in the index, causing loads to silently return stale account data — a silent balance/state resurrection with no transaction involved.
