## Title
Unvalidated user-controlled `destinationChain`/PRC20 in `UniversalTxOutbound` events permanently burns PRC20 with no compensating outbound - (File: `x/uexecutor/keeper/create_outbound.go`, `x/uexecutor/keeper/evm_hooks.go`)

### Summary
`x/uexecutor` treats the `UniversalGatewayPC` withdraw event log as the sole source of truth for outbound creation, but the registry validation (`IsChainOutboundEnabled`, `GetTokenConfigByPRC20`) that decides whether an outbound is actually creatable happens *after* the EVM transaction (and the PRC20 burn inside it) has already been committed to state. If the caller-supplied `chainId`/PRC20 in the gateway withdraw call doesn't map to an enabled, registered chain/token, `BuildOutboundsFromReceipt` errors out and no outbound is ever attached — but the burn that already occurred inside the committed EVM call is never reversed. This is structurally the same bug class as the `WinnablesTicketManager::propagateRaffleWinner` finding: unvalidated user-facing routing parameters, checked only after an irreversible state transition, permanently strand user funds.

### Finding Description
`x/uexecutor/keeper/evm_hooks.go` `EVMHooks.PostTxProcessing` (lines 28-67) runs after every EVM transaction is executed and commits, and calls `h.k.CreateUniversalTxFromReceiptIfOutbound(ctx, protoReceipt, pcTx)`.
<cite repo="Thankgoddavid56/push-chain-node--022" path="x/uexecutor/keeper/evm_hooks.go" start="25="/> [1](#0-0) 

`CreateUniversalTxFromReceiptIfOutbound` and `AttachOutboundsToExistingUniversalTx` both call `BuildOutboundsFromReceipt`, which decodes the `UniversalTxOutbound` log emitted by `UniversalGatewayPC` and only *then* checks whether the destination chain is outbound-enabled and whether the withdrawn PRC20 maps to a known external token: [2](#0-1) 

If either check fails, `BuildOutboundsFromReceipt` returns an error. In the direct-EVM-tx path (`CreateUniversalTxFromReceiptIfOutbound`, invoked from the post-tx hook on every ordinary EVM transaction), that error is simply propagated up from `PostTxProcessing`. [3](#0-2) 

Because the EVM state transition (including any PRC20 `burn`/withdraw accounting performed inside the gateway contract call itself) has already been committed by the time this post-processing hook runs, there is no mechanism here to roll back the burn — the hook only decides whether Push Chain's off-chain/validator-facing bookkeeping (`OutboundTx`, `PendingOutbounds`) gets created, not whether the EVM-side value movement happened.

In the `MsgExecutePayload` / UEA-driven path, the same failure mode is present but slightly softened: `AttachOutboundsToExistingUniversalTx` is called *after* `writeCache()` has already committed the successful `CallUEAExecutePayload` result: [4](#0-3) 
If `attachOutboundsToUtx`/`BuildOutboundsFromReceipt` fails here, the code only records a `RevertError` string on the UTX and returns `nil` — it does not create any revert/outbound, and does not un-burn the PRC20 that the gateway contract already moved: [5](#0-4) 

The root cause mirrors the external report precisely: the parameters that decide where/whether funds get released on the destination chain (`chainId`, PRC20→token mapping) are attacker/user-influenced (chosen when constructing the payload/EVM call that hits `UniversalGatewayPC`'s withdraw entry point) and are validated only *after* the irreversible on-chain burn, in a code path (`x/uregistry` lookups) that has no way to undo the EVM-side effect it is validating against.

### Impact Explanation
An unprivileged user who submits a payload/EVM call that triggers the gateway's withdraw logic with a `chainId` that is unregistered or has `IsOutboundEnabled=false`, or a PRC20 address with no `TokenConfig` entry, causes:
- The PRC20 to be burned/withdrawn inside the already-committed EVM call.
- `BuildOutboundsFromReceipt` to fail, so no `OutboundTx` is created and no `PendingOutbounds` entry exists for Universal Validators to sign/broadcast.
- No revert path is triggered (unlike the inbound-side flows, which have `buildRevertOutbound`/`RevertStuckInbound` escape hatches), because this is the outbound-creation path and it has no equivalent recovery mechanism.

This is a permanent, unauthorized loss of user funds reachable purely through the outbound-creation flow's failure-after-commit ordering — falling squarely in the "Allowed Impact Gate" categories of permanent loss / corruption of PRC20 accounting.

### Likelihood Explanation
Reachability requires only that a user construct a payload (or, in the direct-EVM path, a raw transaction) that calls `UniversalGatewayPC`'s withdraw entry point with a `chainId`/token combination not currently enabled in `x/uregistry`. Chain/token configs are admin-curated and can be temporarily disabled, removed, or simply never registered for arbitrary CAIP-2 identifiers a user might supply, so the "invalid parameter" precondition is trivial and fully within an ordinary user's control — no validator or admin misbehavior required.

### Recommendation
Move destination-chain/token validation (`IsChainOutboundEnabled`, `GetTokenConfigByPRC20`) to occur *before* the burn/value-moving effect is committed — i.e., either:
1. Enforce this check inside the `UniversalGatewayPC` EVM contract itself (revert the withdraw call if the destination chain/token isn't recognized as enabled), so a failing check reverts the whole EVM transaction atomically with the burn, or
2. If validation must remain in the Cosmos keeper, wrap the burn-triggering EVM call and the outbound-attachment check in the same `CacheContext`/commit boundary (similar to the `writeCache()` pattern already used for fee deduction) so a failed `BuildOutboundsFromReceipt` also discards the EVM-side burn instead of merely recording a `RevertError` string.

### Proof of Concept
I was unable to directly inspect the `UniversalGatewayPC` Solidity contract source (it lives in a separate `push-chain-core-contracts` repository, not indexed here) to confirm definitively whether its withdraw function performs any on-chain chainId/token validation prior to burning, or whether `PostTxProcessing` hook errors are fatal to the enclosing Cosmos-SDK/EVM transaction in this fork of `cosmos-evm`. Both of these facts materially affect whether this is fully exploitable as described versus only partially (e.g., if the contract independently validates the chain ID, or if hook failures do revert the EVM tx). I recommend a Devin session with full repository/contract access to:
1. Confirm whether `UniversalGatewayPC.withdraw` (or equivalent) validates `chainId`/token against any on-chain allowlist before burning.
2. Confirm whether `EvmHooks.PostTxProcessing` errors cause the surrounding `MsgEthereumTx` to revert in the pinned `github.com/pushchain/evm` fork.
3. If both confirm the unprivileged/permanent-loss path, add or verify a regression test exercising `CreateUniversalTxFromReceiptIfOutbound` with a disabled/unregistered destination chain following a successful burn, and confirm no compensating mint/refund is emitted.

// AttachOutboundsToExistingUniversalTx
// Used when UniversalTx already exists (e.g. inbound execution)
// It attaches outbounds extracted from receipt to the existing utx.
func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}

// CreateUniversalTxFromReceiptIfOutbound
// Creates a UniversalTx ONLY if outbound events exist in the receipt.
// Safe to call from ExecutePayload, EVM hooks
func (k Keeper) CreateUniversalTxFromReceiptIfOutbound(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalTxKey, err := k.BuildPcUniversalTxKey(ctx, pcTx)
	if err != nil {
		return errors.Wrap(err, "failed to create UniversalTx key")
	}

	outbounds, err := k.BuildOutboundsFromReceipt(ctx, universalTxKey, receipt)
	if err != nil {
		return err
	}

	if len(outbounds) == 0 {
		return nil
	}

	utx, err := k.CreateUniversalTxFromPCTx(ctx, pcTx)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
