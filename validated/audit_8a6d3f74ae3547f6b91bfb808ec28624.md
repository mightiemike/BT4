### Title
Unbounded per-cycle `GetTransaction` fan-out in SVM event listener allows unprivileged signature flooding to stall inbound event observation - (File: universalClient/chains/svm/event_listener.go)

### Summary
An unprivileged attacker can submit an arbitrary number of low-cost Solana transactions addressed to the monitored gateway address. Each such signature causes `processSignatureBatch` to issue one sequential `el.rpcClient.GetTransaction` round trip, with no per-cycle cap, no concurrency, and no early-exit besides an informational log warning at `largePollWarnThreshold`. Because `listen()` drives `processNewSlots` synchronously from a single ticker goroutine, an inflated poll cycle directly delays the next scan, stalling detection of legitimate inbound `SendFunds`/`FinalizeUniversalTx`/`RevertUniversalTx`/`FundsRescued` events for that chain.

### Finding Description
`processSlotRange` pages through `GetSignaturesForAddress` results and feeds every page to `processSignatureBatch`, which loops over each in-range signature and performs a blocking `GetTransaction` call before continuing to the next. There is no maximum number of signatures processed per poll, no batching/concurrency limit, and no circuit breaker tied to `largePollWarnThreshold` (it only logs). Since all UniversalClient nodes run identical listener code against the same public gateway address, an attacker sending a large volume of cheap Solana transactions targeting the gateway address inflates every honest node's poll cycle simultaneously.

### Impact Explanation
This is a liveness/DoS impact on cross-chain event observation rather than fund loss or consensus corruption: it delays (but does not corrupt) detection and downstream ballot finalization of legitimate SVM-originated deposits/messages across all UniversalClient nodes running this code, since the poll loop is single-threaded and unbounded.

### Likelihood Explanation
The attack requires only funding ordinary Solana transaction fees to the public gateway address — no privileged access, validator collusion, or protocol-level authorization is needed, making it feasible for any unprivileged actor to sustain, bounded mainly by their own Solana fee budget.

### Recommendation
Enforce a hard per-cycle cap (or time budget) on the number of `GetTransaction` calls / signatures processed per poll, and/or parallelize lookups with bounded concurrency; treat `largePollWarnThreshold` as an actual throttle/backoff signal instead of a purely informational log.

### Proof of Concept
Unit-test `processSignatureBatch` with a batch of `>largePollWarnThreshold` synthetic in-range signatures and a mock `GetTransaction` with artificial latency; assert that the total RPC call count and wall-clock time scale linearly with attacker-controlled batch size with no upper bound, and that `listen()`'s next tick cannot begin until the inflated cycle completes.

func (el *EventListener) processSignatureBatch(
	ctx context.Context,
	batch []*solanarpc.TransactionSignature,
	fromSlot, toSlot uint64,
) (uint64, error) {
	var processed uint64
	for _, sig := range batch {
		if sig.Slot < fromSlot {
			continue
		}
		if sig.Slot > toSlot {
			continue
		}
		processed++

		// Get transaction details
		tx, err := el.rpcClient.GetTransaction(ctx, sig.Signature)
		if err != nil {
			el.logger.Error().
				Err(err).
				Str("signature", sig.Signature.String()).
				Msg("failed to get transaction")
			continue
		}
