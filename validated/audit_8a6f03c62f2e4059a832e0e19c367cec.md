### Title
Per-sender rate limiter uses un-normalized `body.Sender` string while authorization uses checksummed address, allowing rate-limit bypass via address-casing variation - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
In `processTrigger`, the `allowedSenders` authorization check normalizes the sender via `ethCommon.HexToAddress(body.Sender).String()` (checksummed form), but the rate limiter is keyed on the raw, attacker-supplied `body.Sender` string via `trigger.rateLimiter.Allow(body.Sender)`. Because Ethereum hex addresses are case-insensitive but the raw string is not normalized before being used as the rate-limit key, an attacker who controls the casing of the `Sender` field in the gateway message can generate an unbounded number of distinct rate-limit buckets for what is, on-chain, the exact same authorized sender.

### Finding Description
`processTrigger` computes two different representations of the same sender:
- `sender := ethCommon.HexToAddress(body.Sender)` is used for the `allowedSenders[sender.String()]` authorization check, which normalizes the address to its canonical checksummed form regardless of the input's letter casing.
- `trigger.rateLimiter.Allow(body.Sender)` uses the raw `body.Sender` string as the rate-limit key. [1](#0-0) 

Because `ethCommon.HexToAddress` accepts hex addresses in any letter case and always maps them to the same `common.Address` value, `sender.String()` will be identical (checksummed) for `0xABCDEF...` and `0xabcdef...`. The `allowedSenders` map check therefore correctly treats both forms as the same, authorized sender. However, the rate limiter's `Allow` call uses the raw, non-normalized `body.Sender` string as its bucket key. An attacker who is an authorized sender (or who can freely choose the letter casing of the `Sender` field in the gateway `MessageBody`, which is attacker-supplied JSON-RPC input) can therefore send many requests, each varying only the letter casing of otherwise-identical hex characters in the address. Every distinct casing produces a brand-new per-sender rate-limit bucket (a fresh token bucket, since the underlying rate limiter keys its per-sender state by exact string), effectively giving the attacker unlimited request budget instead of the single per-sender budget the `allowedSenders`/`PerSenderRPS` configuration was meant to enforce.

None of the existing checks catch this: `hc.ValidatedMessageFromReq` validates message structure/signature but does not normalize `Sender` casing before it reaches `processTrigger`; the authorization check itself is done via `ethCommon.HexToAddress(...).String()` normalization, but the rate-limit check bypasses that normalization entirely.

### Impact Explanation
This is a rate-limit bypass: a single authorized sender identity can generate effectively unlimited per-sender request throughput toward `processTrigger`, defeating the `PerSenderRPS`/`PerSenderBurst` configuration meant to protect the workflow's trigger channel (`trigger.ch`, buffered at `defaultSendChannelBufferSize = 1000`) and the workflow execution pipeline behind it from abuse/flooding by a single sender. This matches the "rate limit violations with real security impact" bounty category, since it lets one nominally-authorized principal consume disproportionate resources or flood workflow execution triggers beyond the intended per-sender quota.

### Likelihood Explanation
This requires only an unprivileged, but already-`allowedSenders`-listed, gateway client (or any party that can control the `Sender` field string sent through the gateway JSON-RPC path) to vary hex letter casing across repeated requests — no cryptographic secrets, no additional privileges, and no timing race are needed. The bug is deterministic and trivially repeatable: each new casing variant of the same address opens a fresh rate-limit bucket in the `RateLimiter`'s internal per-sender map.

### Recommendation
Normalize the sender identity once and use the same normalized value for both the `allowedSenders` authorization check and the rate-limiter key, e.g. use `sender.String()` (or `sender.Hex()` consistently) as the argument to `trigger.rateLimiter.Allow(...)` instead of the raw `body.Sender` string:
```go
if !trigger.rateLimiter.Allow(sender.String()) {
    ...
}
```
This ensures the rate limiter tracks exactly one bucket per canonical address regardless of input casing.

### Proof of Concept
Unit test plan for `core/capabilities/webapi/trigger/trigger_test.go`:
1. Register a trigger via `RegisterTrigger` with `AllowedSenders` containing one address (e.g. `0xABCDEF1234567890abcdef1234567890ABCDEF12`) and a restrictive `RateLimiter` config (`PerSenderRPS`/`PerSenderBurst` = 1).
2. Call `HandleGatewayMessage` (or directly `processTrigger`) repeatedly with `body.Sender` set to the same address but in different letter casings on each call (e.g., all-lowercase, all-uppercase, mixed-case) while keeping `payload.Topics` matching and `payload.TriggerEventId` varying to avoid execution-ID collisions.
3. Assert: with the current code, all requests succeed (`ACCEPTED`) despite exceeding `PerSenderBurst`, because each casing variant hits a different bucket in the rate limiter's internal map — demonstrating the bypass.
4. After applying the fix (normalizing the rate-limit key to `sender.String()`), assert that only the first `PerSenderBurst` requests succeed and subsequent ones are rejected with `"request rate-limited for sender..."`, regardless of casing.
