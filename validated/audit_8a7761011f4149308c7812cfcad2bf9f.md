### Title
Replay-verify tool (`db-tool replay-on-archive`) never validates the state checkpoint root hash, allowing corrupted archived state to pass verification as "correct" - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single integrity check used by `aptos db-tool replay-on-archive` to confirm that locally re-executing an archived transaction reproduces the authenticated result recorded in the backup's `TransactionInfo`/`TransactionInfoWithProof`. The function checks execution status, gas used, write-set hash, and event root hash, but it never compares the JMT `state_checkpoint_hash` (nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) between the freshly computed checkpoint and the one carried in the proven `TransactionInfo`. This is acknowledged in-code by a `TODO(trading-native)` comment, but the gap is not limited to the trading-native feature — the state checkpoint root is unconditionally skipped for every replay-verify run today.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates only:
- `status()` against `txn_info.status()`
- `gas_used()` against `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` against `txn_info.state_change_hash()`
- the event-accumulator root against `txn_info.event_root_hash()`

It ends with a comment explicitly noting the omission: [2](#0-1) 

Note that `state_change_hash` here is only the hash of the *delta write-set produced by this one transaction* — not the accumulated Jellyfish Merkle state root after the transaction (`state_checkpoint_hash`), which is the strong, versioned commitment to the *entire* account/resource state. The write-set hash check can pass even while the resulting full state tree (as recorded by the backup) has been tampered with or is stale, because the write-set hash only covers the individual op values that this transaction claims to have written, not the pre-existing base state those ops are applied on top of, nor the resulting merged tree.

This function is invoked directly by the archive replay-verification pipeline in `storage/db-tool/src/replay_on_archive.rs`: [3](#0-2) 

Here `expected_txn_infos[idx]` originates from the backup's proven `TransactionInfo` (retrieved via `get_transaction_iter`, which is itself proof-verified against a ledger info elsewhere in the backup pipeline), and `executed_outputs[idx]` is what `AptosVMBlockExecutor` recomputed locally from the same starting state view. Because `ensure_match_transaction_info` never asserts `executed_outputs[idx]`'s locally computed state checkpoint hash equals `expected_txn_infos[idx].state_checkpoint_hash()`, a state checkpoint mismatch is silently accepted as a successful replay.

### Impact Explanation
The purpose of replay-verify tooling is to give operators and auditors cryptographic assurance that an archived/backed-up ledger's state matches what the network actually committed and that mainnet history has not been corrupted (accidentally or maliciously) in storage/backup pipelines. Because the state checkpoint root — the actual proof-bearing commitment to the full account state — is never compared, a divergence between the archive's claimed state and the true state produced by re-execution (e.g., due to storage corruption, a bug in a state-restore/backup path, or deliberate tampering of an archive by a party who controls the backup storage) would go undetected by `replay-on-archive`. This directly matches the required-impact category "Wrong ... state proof accepted as valid" and "Authenticated API or state-view output bound to the wrong version, object, or proof context," since the state-checkpoint proof binding is effectively unchecked in this tool despite explicitly being the aspect being certified. Consumers of `replay-on-archive`'s "success" result (auditors, node operators validating a full-history archive before trusting it) would be misled into believing the state root is correct when it is not.

### Likelihood Explanation
This is not a hypothetical: the gap is explicitly documented in the source as a known, unresolved TODO, and it applies unconditionally today (i.e., independent of whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled), since the comparison for the ordinary `state_checkpoint_hash` field is also entirely absent from the function body — no code path in `ensure_match_transaction_info` ever calls `txn_info.state_checkpoint_hash()`. Any archived backup with a subtly corrupted/mismatched state tree at a checkpoint boundary transaction (while write-set/events/status/gas remain byte-identical, or where the divergence stems from base-state corruption rather than this specific transaction's write set) will pass `replay-on-archive` silently.

### Recommendation
In `ensure_match_transaction_info`, after computing the transaction's resulting state (or at minimum whenever `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` is `Some`), compute the actual JMT/hot-state/position root produced by applying the transaction on top of the running state view and assert it equals the corresponding hash(es) in `txn_info`, returning an error via `ensure!` (consistent with the existing checks) on mismatch. This requires threading the actual computed checkpoint root(s) into `TransactionOutput` (or passing them as an additional parameter from the caller, since `execute_block`/`BlockOutput` already computes state checkpoint hashes as seen in `do_ledger_update.rs`), so `replay_on_archive` (and the CLI's other caller in `aptos-move/cli/src/commands.rs`) can actually verify state-root equivalence, not just the isolated write-set delta hash.

### Proof of Concept
Conceptual, based on directly reading the checked-in code (no local execution environment was used):
1. Take an archived transaction backup where a state checkpoint transaction's `TransactionInfo.state_checkpoint_hash` in the manifest/proof has been altered (or corresponds to a state tree that was subtly corrupted during a backup/restore round-trip) while the write-set bytes, events, gas, and status for that same transaction remain unchanged.
2. Run `aptos db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`, `Verifier::execute_and_verify`) against this backup.
3. `AptosVMBlockExecutor::execute_block` recomputes the transaction outputs from the (potentially different) actual base state.
4. `executed_outputs[idx].ensure_match_transaction_info(...)` is called; since it never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, the call returns `Ok(())` as long as gas/status/write-set-hash/events happen to match, even though the actual resulting state root diverges from the one certified in the backup's ledger-info-signed `TransactionInfo`.
5. The tool reports the range as successfully replayed/verified, even though the state commitment is wrong — an outcome the code's own `TODO(trading-native)` comment (lines 2197–2202) confirms is a real, currently-unmitigated gap: [4](#0-3)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
