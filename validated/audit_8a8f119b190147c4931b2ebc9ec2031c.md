## Title
Local `last_endorsed` freshness comparison in the signer's conflict-guard permits a second signature over a sibling block, enabling equivocation - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The signer's double-sign guard (`handle_block_pre_commit`'s conflict check) decides whether an already-signed sibling block still "blocks" a new signature purely on the local wall-clock comparison `conflict.last_endorsed > freshness_cutoff`, where `freshness_cutoff = get_epoch_time_secs().saturating_sub(tenure_last_block_proposal_timeout)` [1](#0-0) . This is structurally the same bug class as CVE-2021-32923: a locally-computed, clock-based "is this credential/commitment still valid" check that treats a boundary case as expired even though the artifact it protects (the earlier signature) can still be finalized on-chain.

### Finding Description
The guard's purpose is explicit in the code comments: two blocks at the same height in any tenure are siblings, and signing both would be a double-sign, so a signer must never place a signature on a second sibling while its first signature is still "fresh" [2](#0-1) . Once the timestamp of the earlier endorsement (`last_endorsed`) falls behind `freshness_cutoff`, the conflict is treated as stale and, if the node also cannot confirm the sibling reached the target height, the signer proceeds to sign the new, conflicting block [3](#0-2) . The signer test suite documents and asserts exactly this "stale → signs again" transition (`stale_sibling_replaced_when_canonical_tip_below`, `reproposal_signs_replacement_after_conflict_times_out`) [4](#0-3) [5](#0-4) .

The equality being protected is: *for a given (tenure, height), at most one block should ever receive this signer's signature while the earlier one could still be included in the canonical chain.* The freshness check breaks this equality at the boundary: `last_endorsed > freshness_cutoff` uses the signer's own `get_epoch_time_secs()` at evaluation time, not any consensus-derived clock. If block A is signed and its `last_endorsed` timestamp sits exactly at (or fractionally before) the rolling `freshness_cutoff` when a competing sibling B reaches the pre-commit threshold, the signer will treat A's signature as dead and countersign B — even though A's earlier signature (aggregated with other signers who evaluated the same boundary a few hundred milliseconds earlier, with slightly different local clocks/skew) may already be in flight toward the 70% threshold on other signers' views. Because each signer runs this comparison independently against its own local clock (`get_epoch_time_secs()`), and `tenure_last_block_proposal_timeout` is a per-node config default (30s, per `stacks-signer/src/config.rs`), clock skew or scheduling jitter across a minority of signers is sufficient to push some signers past the cutoff while others remain within it — precisely the "boundary treated inconsistently" failure mode of the Vault CVE, transplanted to a consensus-adjacent liveness/safety guard instead of a lease TTL.

### Impact Explanation
If a large-enough minority of signers cross the freshness boundary asynchronously and countersign sibling B while other signers (or the same signers, moments earlier) had already signed sibling A, both A and B can independently accumulate signatures toward the 70% weight threshold. This is the exact "temporary tip disagreement" / minority-triggerable safety-violation category called out in scope: two conflicting blocks at the same height, each carrying a valid multi-signer certificate, is the direct precursor to a chain split (competing Nakamoto blocks both satisfying `verify_signer_signatures`'s threshold check at `stackslib/src/chainstate/nakamoto/mod.rs:1180-1187`). The guard's own documentation acknowledges this is exactly the scenario it exists to prevent ("so a single winning miner cannot obtain two signer certificates for one sortition") [6](#0-5) .

### Likelihood Explanation
This requires no majority collusion and no privileged access: it only requires that block proposals/pre-commits for a legitimate sibling race (which the code comments confirm can occur even in benign operation, due to async validation timing) straddle the local freshness boundary on a subset of signers, e.g. via ordinary network latency or clock drift within the configured `tenure_idle_timeout_buffer_secs` tolerance (default 2s) relative to `tenure_last_block_proposal_timeout` (default 30s). The reliance on each signer's independent, non-consensus wall clock for a safety-critical decision makes this a plausible, minority-triggerable divergence rather than a purely theoretical one, though it is probabilistic/timing-dependent rather than deterministically attacker-controlled, so it is rated High rather than Critical.

### Recommendation
Bound the freshness window with a stricter, consensus-anchored signal (e.g., require the node to also confirm the sibling was superseded, not merely a local timeout) rather than relying solely on `get_epoch_time_secs()` deltas, and/or widen the "not yet globally accepted but not confirmed dead" holding period to absorb worst-case clock skew across the signer set, so no two signers can independently conclude one sibling is fresh and the other stale on the same underlying evidence within the same evaluation window.

### Proof of Concept
1. Two sibling tenure-start blocks A and B (same tenure, parent, height) are proposed within the async-validation window, as already demonstrated by the existing `async_sibling_validation` test harness (`run_sibling_scenario`) [7](#0-6) .
2. A reaches pre-commit threshold slightly before B and is signed by signer set S1 while `last_endorsed` for A is still within the freshness window on S1's clocks.
3. Due to clock skew/jitter, a disjoint signer set S2 (or the same signers a few hundred ms later) evaluates B's pre-commit after their local `freshness_cutoff` has already advanced past A's `last_endorsed`, and the node's tenure-tip query for A's tenure returns "not reached" (A not yet confirmed at the node, per `conflict_still_blocks`'s "never globally accepted" branch) [8](#0-7) , causing S2 to sign B.
4. If |S1| and |S2| each independently reach the 70% weight threshold (possible if S1 ∩ S2 signers double-count across a rolling window, or if the sets overlap sufficiently), both A and B obtain valid multi-signer certificates for the same height, producing a chain split resolvable only by node-side tie-breaking — an outcome the guard was explicitly designed to prevent, per its own inline documentation.

    /// Drive the sibling race: two conflicting tenure-start blocks A and B are both tracked
    /// (as they would be after screening two proposals within the async-validation window),
    /// A's validation returns first and is signed, then B's validation returns. Returns the
    /// resulting `BlockInfo` for A (captured right after its own validation), for B (captured
    /// right after its validation), and for B after an optional re-proposal.
    ///
    /// `tenure_last_block_proposal_timeout` controls whether A's signature is still fresh when
    /// B crosses the pre-commit threshold. `serve_sibling_as_tip` controls whether the mock
    /// node reports A (height 10) or the parent (height 9) as the canonical tenure tip, which
    /// is what the signer consults once the signature has timed out. If `re_propose_b_after` is
    /// set, the miner re-submits B's proposal after that delay (as it does after a signature
    /// timeout) and B's `BlockInfo` is captured again as the third element.
    fn run_sibling_scenario(
        tenure_last_block_proposal_timeout: Duration,
        serve_sibling_as_tip: bool,
        re_propose_b_after: Option<Duration>,
    ) -> (BlockInfo, BlockInfo, Option<BlockInfo>) {
        let miner = StacksPrivateKey::from_seed(&[0, 1]);
        let tenure = ConsensusHash([1; 20]);
        let parent_tenure = ConsensusHash([0; 20]);

        // The parent block of the tenure (height 9); both siblings build on it at height 10.
        let mut parent_header = NakamotoBlockHeader {
            version: 1,
            chain_length: 9,
            burn_spent: 10,
            consensus_hash: parent_tenure.clone(),
            parent_block_id: StacksBlockId([9; 32]),
            tx_merkle_root: Sha512Trunc256Sum([0; 32]),
            state_index_root: TrieHash([0; 32]),
            timestamp: 9,
            miner_signature: MessageSignature::empty(),
            signer_signature: vec![],
            pox_treatment: BitVec::ones(1).unwrap(),
            problematic_txs: vec![],
        };
        parent_header.sign_miner(&miner).unwrap();
        let parent_id = parent_header.block_id();

        // Two conflicting sibling tenure-start blocks: same tenure, parent, and height; the only
        // difference is the timestamp (hence the hash). The timestamps are current so that a
        // re-proposal of B passes the proposal age check.
        let now = get_epoch_time_secs();

        let block_b = tenure_start(&miner, &tenure, &parent_tenure, &parent_id, now + 1);
        let hash_a = block_a.header.signer_signature_hash();
        let hash_b = block_b.header.signer_signature_hash();
        assert_ne!(hash_a, hash_b);

    #[test]
    fn stale_sibling_replaced_when_canonical_tip_below() {
        // A zero timeout makes A's signature stale immediately, and the node's canonical tip
        // is still the parent (height 9): A failed to be confirmed, so the signer must sign
        // the replacement rather than stall the tenure (the reorg-recovery case).
        let (info_a, info_b, _) = run_sibling_scenario(Duration::ZERO, false, None);
        assert_a_signed(&info_a);
        assert_eq!(
            info_b.state,
            BlockState::LocallyAccepted,
            "block B should be signed: the conflicting sibling timed out and is not canonical, got: {}",
            info_b.state
        );
        assert!(
            info_b.signed_self.is_some(),
            "block B should carry our signature after the conflict timed out unconfirmed"
        );
    }
