### Title
Exchange pool permanently "closed" once either token balance hits zero, locking remaining funds with no emergency withdrawal path - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` implement a Bancor-style two-token liquidity pool (`ExchangeCapsule`). Just like Perennial's `BalancedVault`, which pools user funds across multiple markets and permanently locks all funds if any single market breaks, java-tron's exchange pool combines two token balances and treats the whole pool as unusable — including the still-solvent side — the moment either side's balance hits zero.

### Finding Description
`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` all share the same guard in `doValidate()`: [1](#0-0) 

identical checks exist in `ExchangeWithdrawActuator` [2](#0-1) 

and are exercised by the test `SameTokenNameCloseTokenBalanceZero` [3](#0-2) 

Once `firstTokenBalance == 0 || secondTokenBalance == 0`, **every** subsequent operation on that exchange id — inject, withdraw, and transaction — reverts with `"Token balance in exchange is equal with 0, the exchange has been closed"`. This is a single combined check on the pool as a whole, not per-side; the creator cannot withdraw the remaining (non-zero) side of the pool once the other side is drained to zero, exactly mirroring the `BalancedVault` bug class where a single market's failure prevents withdrawal from unaffected markets.

The zero-balance state is reachable through normal trading: `ExchangeCapsule.transaction()` computes `buyTokenQuant` via the Bancor-formula `Processor` (`ExchangeProcessor`, floating-point, or `SafeExchangeProcessor`, `BigDecimal`) and only checks for a negative resulting balance when `hardenedCalc` (`allowHarden()`) is enabled: [4](#0-3) 

Because the "hardened" negative-balance check only guards against balances going negative, not against balances landing at exactly `0`, driving one side of the pool to zero through large legitimate trades is possible even under the hardened path, and once it happens the creator's remaining assets on the other side of the pool become permanently frozen in `ExchangeStore`/`ExchangeV2Store` — there is no partial/emergency-withdraw path, unlike ordinary TRC10/TRX balances which remain independently accessible.

### Impact Explanation
Funds injected by the exchange creator into a token pair are exposed to a "combined market" risk: if trading activity (or the lack of a symmetric negative/zero check in the legacy math path) drives either side of the pool to zero, the entire pool — including the side that still has a nonzero balance — becomes permanently un-withdrawable via `ExchangeWithdrawActuator`, un-injectable via `ExchangeInjectActuator`, and untradeable via `ExchangeTransactionActuator`. This is an accounting/asset-lock issue reachable purely through normal broadcast transactions (`ExchangeTransactionContract`), not requiring any privileged actor, and results in permanent loss of access to on-chain assets for the exchange's creator.

### Likelihood Explanation
This requires no privileged access — any account can call `ExchangeTransactionContract` repeatedly (subject to `getExchangeBalanceLimit()`) to push a heavily imbalanced pool's balance toward zero, particularly for a low-liquidity pool. Reaching an exact zero-balance is aided by integer truncation (`RoundingMode.DOWN` / `(long)` cast in both `ExchangeProcessor` and `SafeExchangeProcessor`), which can zero out a small remaining balance. The scenario does not require oracle failure or any external protocol dependency — it is intrinsic to the exchange's own accounting design, making it more directly reachable than the Perennial analog.

### Recommendation
- Separate the "pool is closed" check from a global revert-all condition: allow the creator to withdraw the non-zero side of the pool even when the other side is at zero.
- Add a floor/minimum-liquidity check to `ExchangeCapsule.transaction()` (in both `ExchangeProcessor` and `SafeExchangeProcessor` paths) to prevent a trade from ever driving either balance to exactly zero, not just negative.
- Document this pool-freeze risk clearly if the design is intentional, and consider an emergency/partial withdrawal path analogous to what Sherlock's judges recommended for `BalancedVault`.

### Proof of Concept
1. Creator calls `ExchangeCreateContract` to create a pool with `firstTokenBalance = X`, `secondTokenBalance = Y` (`ExchangeCreateActuator.execute`). [5](#0-4) 
2. An unprivileged trader repeatedly (or with a single large trade) calls `ExchangeTransactionContract` selling the first token, causing `ExchangeCapsule.transaction()` to compute a `buyTokenQuant` that reduces `secondTokenBalance` to exactly `0` (or to a value that later rounds to `0`). [6](#0-5) 
3. The creator now calls `ExchangeWithdrawContract` to retrieve the remaining `firstTokenBalance`; `doValidate()` rejects it because `secondTokenBalance == 0`: [2](#0-1) 
4. The remaining first-token balance is permanently locked in `ExchangeStore`/`ExchangeV2Store` with no way for the creator to recover it.

*Note: I could not fully verify from the index whether `allowHarden()`/`allowStrictMath()` are enabled by default on current mainnet (their configuration is spread across `DynamicPropertiesStore`, `ProposalUtil`, and `VMConfig`), so I cannot state with certainty which math path (legacy vs. hardened) is active without further investigation of proposal/committee parameters at runtime. A Devin session with full repo/build access would be needed to confirm the exact default state of these feature flags on the target network.*

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
