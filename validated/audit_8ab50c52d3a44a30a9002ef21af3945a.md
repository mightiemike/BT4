### Title
Inconsistent `unDelegateBalance` availability check between `UnDelegateResourceActuator` and `UnDelegateResourceProcessor` allows validation bypass for TVM-triggered undelegation - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
`UnDelegateResourceActuator.validate()` (reached via a broadcast `UnDelegateResourceContract` transaction) sums frozen balance from **both** the unlocked `DelegatedResourceCapsule` and the locked one (only if `lockResourceCapsule.getExpireTimeForBandwidth/Energy() < now`) before allowing an unDelegate. `UnDelegateResourceProcessor.validate()` (reached when a smart contract calls the `unDelegateResource` native/precompiled contract) only checks the single unlocked `DelegatedResourceCapsule` fetched via the non-locked db key, with no equivalent handling of a locked-but-expired resource, and no combination logic at all.

### Finding Description
`UnDelegateResourceActuator.validate()` computes the amount available to unDelegate as: [1](#0-0) 
i.e. `delegateBalance = unlockResourceCapsule.getFrozenBalanceForBandwidth() + (lockResourceCapsule expired ? lockResourceCapsule.getFrozenBalanceForBandwidth() : 0)`, using two DB keys (locked/unlocked) fetched earlier: [2](#0-1) 

The parallel TVM-side implementation, `UnDelegateResourceProcessor.validate()`, which is invoked when the `unDelegateResource` operation is triggered from within a smart contract (TVM native contract path), fetches only the unlocked capsule and checks against it in isolation, never considering a lock-key capsule at all: [3](#0-2) 

This is structurally the same defect class as the Lybra `H-02` report: one code path (`liquidation()`/`UnDelegateResourceActuator`) computes the "true" available/owed amount by aggregating all relevant components (borrowed + fees + shares / unlocked + expired-locked balance), while a second, parallel code path (`rigidRedemption()`/`UnDelegateResourceProcessor`) uses an incomplete subset of the same accounting, creating two different notions of "how much resource is actually available" for the same underlying state.

### Impact Explanation
Because the TVM path's check is stricter/narrower (it ignores expired-locked delegated resource that the actuator path would count as available), a contract that has resource delegated with a lock period that has already expired cannot unDelegate that portion of the resource via the TVM `unDelegateResource` precompile, even though the plain transaction-broadcast path would allow it. This is primarily an availability/consistency issue (inconsistent accounting/logic across two entry points into the same state), rather than a direct fund-draining bug, but it demonstrates the same "duplicated/divergent solvency-style calculation" pattern flagged in the source report and can cause confusing, non-uniform contract behavior depending on entry point (RPC broadcast transaction vs. TVM contract call), which is a legitimate consistency/DoS-of-functionality concern reachable from both an anonymous broadcast transaction and a contract call.

### Likelihood Explanation
Both paths are reachable by any user: `UnDelegateResourceActuator` via a normal broadcast `UnDelegateResourceContract` transaction, and `UnDelegateResourceProcessor` via a smart contract calling the corresponding native contract (exposed to any caller with no privilege). The divergence triggers whenever an account has resource delegated under the "locked" mode with an expired lock period and attempts to unDelegate it through the TVM contract-call path.

### Recommendation
Unify the availability calculation for `unDelegateBalance` between `UnDelegateResourceActuator.validate()`/`execute()` and `UnDelegateResourceProcessor.validate()`/`execute()`: both should aggregate frozen balance from the unlocked capsule and any expired locked capsule identically, sharing the same helper logic instead of maintaining two independently written checks.

### Proof of Concept
1. Delegate `BANDWIDTH` (or `ENERGY`) resource from account A to account B using the locked mode with a lock period, then let the lock period expire (`expireTimeForBandwidth < now`), leaving the balance recorded under the locked `DelegatedResourceCapsule` key.
2. Attempt to call `unDelegateResource` from a smart contract owned by A targeting this now-expired-but-still-"locked"-keyed balance — `UnDelegateResourceProcessor.validate()` at [4](#0-3)  only reads the unlocked-key capsule and rejects/miscalculates because it never inspects the locked-key capsule that `UnDelegateResourceActuator.validate()` explicitly checks at [1](#0-0) .
3. Compare with issuing the same unDelegate request via a plain broadcast `UnDelegateResourceContract` transaction, which succeeds because the actuator path accounts for the expired lock — demonstrating the two entry points disagree on the same underlying resource-availability state.
