### Title
Permanent loss of an account's NEAR balance via `DeleteAccount` action with a non-existent beneficiary - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccount` lets an account owner destroy their account and redirect its remaining balance to a `beneficiary_id` of their choosing. The runtime never verifies that `beneficiary_id` refers to an existing (or creatable) account before the deleting account is removed. If the beneficiary is a syntactically valid but non-existent named account, the balance-refund receipt created for it fails on delivery, and per the runtime's refund-handling rules the failed refund's deposit is burned rather than returned to anyone — permanently destroying the deleted account's funds. This mirrors the reported `destroyEscrow()` issue, where deleting an escrow record without accounting for locked/deposited funds could strand tokens; here, deleting a NEAR account without verifying the beneficiary can exist strands (burns) the account's own balance.

### Finding Description
`action_delete_account` unconditionally builds a `Transfer`-style refund receipt to `delete_account.beneficiary_id` for the full account balance and then deletes the account in the same action: [1](#0-0) 

The only validation performed on `beneficiary_id` anywhere in the action pipeline is a syntax check (`validate_action_account_id`), never an existence check: [2](#0-1) 

`check_actor_permissions` for `Action::DeleteAccount` only verifies that the actor equals the account being deleted and that the account has no locked (staked) balance — it does not look at `beneficiary_id` at all: [3](#0-2) 

`check_account_existence` likewise only validates that the *deleted* account exists/is initialized for `Action::DeleteAccount`; it never checks the beneficiary's account state: [4](#0-3) 

Since the refund receipt to `beneficiary_id` is itself an `Action::Transfer`, when it later executes against a non-existent, non-implicit named account, `check_account_existence`'s `Action::Transfer` branch rejects it with `AccountDoesNotExist` (implicit account creation is not permitted for arbitrary named account ids): [5](#0-4) 

Per the runtime's documented invariant, a failed refund receipt does not bounce the funds back anywhere — it burns the deposit instead of refunding: [6](#0-5) 

Because `action_delete_account` has already set `*account = None` and removed the account from state by the time this refund receipt executes (in fact, the deleting transaction itself commits the deletion before the spawned refund receipt is even attempted), there is no way to recover the funds once the beneficiary turns out not to exist — the NEAR is permanently burned.

### Impact Explanation
An account owner (or anyone holding the account's full-access key) can permanently destroy the entire native NEAR balance of that account by submitting a single `DeleteAccount` action naming a syntactically valid but non-existent account as `beneficiary_id` (e.g., a mistyped account id, or one that has itself already been deleted between transaction construction and execution — a race any user could trigger against themselves or, notably, against another account they don't control if they can predict its deletion). This is a direct, transaction-triggered, permanent loss of funds (native token burn) with no recourse, matching the "value permanently frozen/lost" acceptance criterion. It requires no privileged role — any ordinary transaction signer holding a full-access key on the account being deleted can trigger it.

### Likelihood Explanation
Likelihood is realistic: this is not an edge case requiring adversarial network conditions or validator collusion — it is a plain user error (or attacker-induced error, e.g., a wallet/dApp misconfiguration, a relayer supplying an attacker-controlled `beneficiary_id`, or a race where the beneficiary account is deleted just before the refund receipt executes) reachable purely through the standard transaction/action interface with a single `DeleteAccount` action. No special gas, storage, or protocol-feature gating is needed; the code path exists in the stable protocol version referenced in this tree.

### Recommendation
Before permitting `DeleteAccount` to complete, verify that `beneficiary_id` refers to an existing account (or is a valid implicit account id that can be safely credited), similar in spirit to the report's recommendation to check for locked funds before destroying an escrow. Concretely: in `action_delete_account` (or in `check_account_existence`/`check_actor_permissions` prior to committing the deletion), look up `beneficiary_id`'s account state and reject the action (e.g., with a new `ActionErrorKind::BeneficiaryDoesNotExist`) if it is not a resolvable/creatable account, so that the deleting account's funds cannot be routed into a receipt that is guaranteed to fail and be burned.

### Proof of Concept
1. Create account `alice.near` with a full-access key and a non-zero balance, no staking (`locked == 0`).
2. Submit a transaction from `alice.near` to itself containing a single `DeleteAccountAction { beneficiary_id: "definitely-not-an-existing-account.near" }` (a syntactically valid account id per `validate_action_account_id`, but one that has never been created).
3. The action passes `check_actor_permissions` (actor == account, not staking) and `check_account_existence` (account exists/initialized) — see [3](#0-2)  and [4](#0-3) .
4. `action_delete_account` pushes a `Receipt::new_balance_refund(beneficiary_id, account_balance)` and deletes `alice.near` from state — see [7](#0-6) .
5. The spawned refund receipt later executes against `beneficiary_id`; `check_account_existence`'s `Transfer` branch rejects it with `AccountDoesNotExist` since the account doesn't exist and is not implicit-creatable — see [5](#0-4) .
6. Per the documented failed-refund behavior, the deposit is burned instead of returned — see [6](#0-5) .
7. Result: `alice.near`'s entire NEAR balance is permanently destroyed with no recovery path, triggered by a single ordinary transaction.
