Based on my research, I found a plausible analog to the GiantLP zero-address burn-hook issue in Push Chain's outbound revert/refund path, though full verification of the attacker-facing input validation for `RevertInstructions.FundRecipient` was not completed due to tool-access limits on `x/uexecutor/types/outbound_tx.go` (`ValidateBasic`) and `x/uexecutor/keeper/create_outbound.go`, so this should be treated as a **candidate finding requiring further validation**, not a confirmed vulnerability.

### Title
Attacker-supplied `RevertInstructions.FundRecipient` = zero address can permanently freeze bridged funds via `AbortOutbound` - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`handleFailedOutbound` re-mints bridged PRC20 tokens to a "revert recipient" that is taken directly from user-supplied `RevertInstructions.FundRecipient` (falling back to `outbound.Sender`) with no zero-address validation before calling the EVM mint (`CallPRC20Deposit`). If the mint target is `address(0)`, the underlying PRC20 mint (standard ERC20 semantics disallow minting to the zero address) reverts, and the outbound is moved to `Status_ABORTED`, which per the documented lifecycle "requires manual intervention" — i.e., no automatic path exists to recover the funds. This mirrors the GiantLP class of bug: a `to == address(0)` case that is not filtered before being passed into a state-changing operation with a zero-address guard, causing legitimate funds-recovery flow to permanently fail.

### Finding Description
`handleFailedOutbound` computes the revert recipient as: [1](#0-0) 
with no check that `recipient` (derived from `outbound.RevertInstructions.FundRecipient`, which originates from user-controlled inbound data) is non-zero. It is passed straight into `common.HexToAddress(recipient)` and then into `CallPRC20Deposit`, which mints PRC20 tokens to that address: [2](#0-1) 
If the mint call reverts (as ERC20 `_mint` implementations conventionally do for `address(0)`), the error path calls `AbortOutbound`, marking the outbound `Status_ABORTED` — a terminal state defined as requiring manual intervention: [3](#0-2) [4](#0-3) 

The same unvalidated-recipient pattern also appears in `applyGasRefund`'s excess-gas refund path, which uses the same `RevertInstructions.FundRecipient` fallback logic before calling `CallUniversalCoreRefundUnusedGas`: [5](#0-4) 

### Impact Explanation
If reachable, this results in permanent freezing of bridged/refunded user funds (an in-scope impact under "Registry and accounting path" / "permanent freezing of user or protocol-controlled funds"), since `ABORTED` outbounds have no automatic remint/retry path and are explicitly documented as needing operator/admin intervention rather than protocol-level recovery.

### Likelihood Explanation
Uncertain / not fully confirmed. The severity and reachability depend on two facts I could not verify with available tools:
1. Whether `RevertInstructions.FundRecipient` (or `Inbound.Sender`) is validated to reject the zero address at ingress (`ValidateBasic` in `x/uexecutor/types/outbound_tx.go` / `inbound.go`, and `MsgVoteInbound` handling) — if such validation already exists and rejects zero/invalid addresses before an inbound/outbound is created, this issue does not exist.
2. Whether the PRC20 contract's mint function actually reverts on `to == address(0)` (the Solidity contract source itself is not part of this repository's indexed scope, so this could not be directly confirmed here).
If both hold, the attacker only needs to submit an inbound with `RevertInstructions.FundRecipient = 0x0000000000000000000000000000000000000000` and have honest Universal Validators observe/vote the corresponding outbound as failed (a legitimate destination-chain failure is enough) — no privileged or malicious-validator behavior needed.

### Recommendation
- Reject zero-address `FundRecipient`/`Sender` at `ValidateBasic`/vote-ingress time for `Inbound` and `OutboundTx`.
- In `handleFailedOutbound` and `applyGasRefund`, explicitly check `recipient != common.Address{}` before calling `CallPRC20Deposit` / `CallUniversalCoreRefundUnusedGas`, and fall back to a safe default (e.g., a rescue/treasury address) or a distinct recoverable state instead of `ABORTED`, so funds are never left in a state that only manual admin action can resolve.

### Proof of Concept
Not executable from this environment (no access to the PRC20/UniversalCore Solidity source or a running node to confirm mint-to-zero-address revert behavior, nor to `ValidateBasic` code paths that gate `FundRecipient`). A concrete PoC would require:
1. Confirming `PRC20.mint`/`depositPRC20` reverts on `to == address(0)`.
2. Confirming no validation rejects `RevertInstructions.FundRecipient == address(0)` in `MsgVoteInbound`/inbound processing.
3. Submitting an inbound of `TxType_FUNDS` with `RevertInstructions.FundRecipient` set to the zero address, driving it to a destination-chain failure observed by honest UVs, and observing the resulting outbound transition to `Status_ABORTED` with funds unrecoverable through normal protocol flows.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}
