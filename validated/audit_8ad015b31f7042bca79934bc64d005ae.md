### Title
Non-thread-safe global cursor mutation in `WalletOnCursor.futureGet` allows concurrent PBFT/Solidity/HEAD block-read requests to read each other's snapshot cursor, producing non-deterministic/incorrect finality-tagged responses - ([File: framework/src/main/java/org/tron/core/services/WalletOnCursor.java])

### Summary
`GetBlockOnPBFTServlet` and `GetBlockOnSolidityServlet` wrap `GetBlockServlet.doGet/doPost` by calling `walletOnPBFT.futureGet(...)` / `walletOnSolidity.futureGet(...)`, which mutate a single shared `Manager` (`dbManager`) cursor field, run the callable, then reset it. Because this set/run/reset sequence is not synchronized and not thread-local, concurrent HTTP requests hitting the plain `/wallet/getblock`, `/walletsolidity/getblock`, and `/walletpbft/getblock` endpoints on the same node (each backed by the same singleton `Manager`) can interleave and clobber each other's cursor, causing a request meant to read the PBFT/Solidity (finalized) snapshot to actually be served from the HEAD (unconfirmed) snapshot or vice versa.

### Finding Description
`WalletOnCursor.futureGet` implements the cursor-scoped read as: [1](#0-0) 

`dbManager.setCursor(cursor)` mutates state on the shared `Manager` singleton instance (and, transitively, on the underlying `Chainbase`/revoking-store instances) rather than a `ThreadLocal`. Every servlet variant that needs a non-HEAD view reuses this exact same singleton: [2](#0-1) [3](#0-2) 

`WalletOnSolidity`/`WalletOnPBFT` only differ by which `Cursor` enum value they assign to the shared `Manager` before delegating: [4](#0-3) 

Because the Jetty HTTP server processes each request on its own worker thread from a pool, and `GetBlockServlet`, `GetBlockOnSolidityServlet`, and `GetBlockOnPBFTServlet` are all separate `@Component` servlets mapped to different URLs but backed by the *same* `Manager`/`Wallet` singleton beans, nothing prevents this sequence:

1. Thread A (solidity request) calls `dbManager.setCursor(SOLIDITY)`.
2. Before Thread A calls `wallet.getBlock(...)`, Thread B (a concurrent plain `/wallet/getblock` or PBFT request) runs `futureGet`, which calls `dbManager.resetCursor()` (or `setCursor(PBFT)` / `setCursor(HEAD)`), overwriting the field Thread A is about to rely on.
3. Thread A proceeds to call `wallet.getBlock(...)` using whatever cursor Thread B most recently set, returning a block queried against the wrong revoking-store snapshot (e.g., HEAD instead of SOLIDITY, or SOLIDITY instead of PBFT).
4. Thread B's own `finally` block then calls `resetCursor()` again, potentially clobbering state for yet another interleaved thread.

The whole endpoint family (`GetBlockOnPBFTServlet`, `GetBlockOnSolidityServlet`, and any other `*OnPBFTServlet`/`*OnSolidityServlet` built on `WalletOnCursor.futureGet`) is affected, not just `getblock` — this is a systemic reliance on non-thread-safe shared mutable state to select the read snapshot. No authentication, no accounting, no replay guard exists here because this is a pure read-path API — there is no mechanism in the code that serializes or thread-isolates cursor mutation across concurrent requests.

### Impact Explanation
Consumers of the `/walletsolidity/*` and `/walletpbft/*` APIs explicitly rely on these endpoints returning only **finalized** (solidity/PBFT-confirmed) chain state, which is a documented safety property used by exchanges and downstream integrators to avoid acting on data that could be reorganized. If concurrent traffic causes a solidity/PBFT-cursor request to silently read HEAD (unconfirmed) data instead — or vice versa — this breaks that finality guarantee, producing divergent/non-deterministic answers to identical public queries and potentially causing downstream systems to treat unconfirmed data as final (e.g., premature crediting of a deposit based on `getblock`/`getBlockByNum` results assumed to be solidity-confirmed).

### Likelihood Explanation
This requires no privileges: any two concurrent HTTP clients issuing ordinary `getblock`-family requests to different cursor-tagged endpoints on the same full node (a very common deployment pattern, since PBFT/Solidity/HEAD HTTP ports are typically exposed together) can trigger the race under normal, non-adversarial load. High-traffic nodes with concurrent Jetty threads make this a `likely`, low-effort, remotely triggerable condition, though it is timing-dependent (non-deterministic per request rather than always exploitable). I was not able to fully trace `Manager.setCursor`/`resetCursor` internals (whether it touches a single field or iterates multiple revoking stores) or confirm the exact "num > head" check inside `Wallet.getBlock` referenced in the question, since tool access ran out before I could open `Wallet.java` and `Chainbase.java`/`Manager.java` in full — this should be verified directly in those files before finalizing severity.

### Recommendation
Make cursor selection thread-local (e.g., `ThreadLocal<Chainbase.Cursor>`) inside `Manager`/`Chainbase` instead of a shared instance field, so that concurrent `futureGet` invocations from different servlet threads cannot observe or clobber each other's snapshot selection. Alternatively, serialize all `futureGet` calls per Wallet variant through a dedicated single-threaded executor (queue) so cursor set/read/reset is atomic with respect to other concurrent cursor consumers.

### Proof of Concept
```java
// Integration/concurrency test sketch (JUnit)
// framework/src/test/java/org/tron/core/services/WalletOnCursorConcurrencyTest.java

@Test
public void concurrentCursorRaceCausesWrongSnapshotRead() throws Exception {
  Manager manager = /* shared singleton, as in production Spring context */;
  WalletOnSolidity walletOnSolidity = new WalletOnSolidity(); // cursor = SOLIDITY
  WalletOnPBFT walletOnPBFT = new WalletOnPBFT();             // cursor = PBFT
  // wire both to the same `manager` via reflection/Spring context, as in prod

  int iterations = 10_000;
  AtomicInteger mismatches = new AtomicInteger();
  ExecutorService pool = Executors.newFixedThreadPool(8);

  List<Future<?>> futures = new ArrayList<>();
  for (int i = 0; i < iterations; i++) {
    futures.add(pool.submit(() ->
        walletOnSolidity.futureGet(() -> {
          // simulate work between setCursor and the actual read
          Thread.yield();
          Chainbase.Cursor observed = manager.getCursor(); // hypothetical getter
          if (observed != Chainbase.Cursor.SOLIDITY) {
            mismatches.incrementAndGet();
          }
          return null;
        })));
    futures.add(pool.submit(() ->
        walletOnPBFT.futureGet(() -> {
          Thread.yield();
          Chainbase.Cursor observed = manager.getCursor();
          if (observed != Chainbase.Cursor.PBFT) {
            mismatches.incrementAndGet();
          }
          return null;
        })));
  }
  for (Future<?> f : futures) {
    f.get();
  }
  pool.shutdown();

  // Expected (if thread-safe): mismatches == 0
  // Actual (with shared mutable cursor field): mismatches > 0, proving
  // that concurrent identical-looking requests to solidity/PBFT endpoints
  // can read the wrong chain snapshot.
  assertEquals(0, mismatches.get());
}
```
This test should be adapted once `Manager`'s actual cursor-storage mechanism is confirmed (field name/getter), but it demonstrates the reproducible pattern: concurrent `futureGet` calls from `WalletOnSolidity` and `WalletOnPBFT` racing on the same underlying `Manager` cursor state.
