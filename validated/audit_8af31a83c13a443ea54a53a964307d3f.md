### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule` via legacy (non-optimized) `DelegatedResourceAccountIndexStore` index enables cheap targeted storage-bloat DoS - (File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java)

### Summary
When the `ALLOW_DELEGATE_OPTIMIZATION` chain parameter is not enabled (its default value is `0`), `DelegateResourceActuator` and `FreezeBalanceActuator` maintain a single, unbounded, monolithically-serialized `DelegatedResourceAccountIndex` protobuf object per account, appending a new distinct address every time a new delegation relationship is created. There is no cap on the number of entries. Any unprivileged user can cheaply create many fresh accounts and delegate the minimum allowed amount (1 TRX) from each to a single victim address, causing the victim's index object to grow without bound, analogous to the Solana `liquidity_lockbox` finding where cheap repeated `deposit()` calls filled a fixed-size, unbounded-growth data structure.

### Finding Description
`DelegateResourceActuator.delegateResource()` only converts to the bounded, per-pair keyed V2 index format when `dynamicPropertiesStore.supportAllowDelegateOptimization()` is true. Otherwise it falls back to the legacy path that fetches, mutates, and rewrites a single `DelegatedResourceAccountIndexCapsule` for each of the owner and receiver addresses: [1](#0-0) 

The capsule simply appends to an internal repeated field with no size limit: [2](#0-1) [3](#0-2) 

`DelegateResourceActuator` (the actuator that operates on the new Freeze-V2 balances, independent of whether the old Freeze-V1 contract is disabled) uses the very same guard: [4](#0-3) 

The only validation on the delegated amount is a floor of 1 TRX, with no check on the number of distinct counterparties an account may accumulate: [5](#0-4) 

Whether this "old" non-optimized index format is presently reachable on a given deployment depends entirely on the `ALLOW_DELEGATE_OPTIMIZATION` committee proposal (#69) having been passed; both `common/src/main/resources/reference.conf` and `CommonParameter`/`CommitteeConfig` default this flag to `0`: [6](#0-5) [7](#0-6) 

So unless the network operator/committee has explicitly enabled optimization, the vulnerable unbounded-list code path is the live path for every `DelegateResourceContract`.

### Impact Explanation
Repeatedly delegating the minimum 1 TRX from many freshly created attacker-controlled accounts to a single victim address causes that victim's `DelegatedResourceAccountIndexCapsule.fromAccounts` list (and the corresponding `toAccounts` list on the attacker side) to grow without bound. Since the whole object is read, deserialized, mutated, re-serialized, and written back on every delegate/undelegate operation touching that account (`DelegatedResourceAccountIndexStore.get`/`put`), an attacker can inflate the victim's per-transaction state I/O, storage footprint, and CPU/serialization cost for any future freeze/delegate/undelegate action involving that account. This is an accounting/state-growth DoS vector against a specific account rather than a full-chain halt, but it degrades or can eventually break the delegate/undelegate flow for the targeted account at negligible attacker cost.

### Likelihood Explanation
Exploitability requires (a) `ALLOW_DELEGATE_OPTIMIZATION` not yet enabled by committee vote on the target network, and (b) the attacker being willing to create many throwaway accounts and pay minimal freeze/delegate fees (1 TRX per delegation plus account-activation cost). Both are realistic on TRON given account creation and 1-TRX freezes are cheap, and the flag's default is disabled. This mirrors the original finding's "under $10" cost profile. I could not verify from the indexed code alone whether TRON mainnet has already enabled `ALLOW_DELEGATE_OPTIMIZATION` in practice; this depends on on-chain governance state not visible in the static repository.

### Recommendation
- Always use the bounded, prefix-keyed V2 index format (`delegateV2`/prefix-based storage) regardless of the `ALLOW_DELEGATE_OPTIMIZATION` flag, removing the legacy unbounded-list code path entirely, or
- Enforce a maximum count on `fromAccounts`/`toAccounts` in the legacy `DelegatedResourceAccountIndexCapsule` (mirroring the `MAX_ACTIVE_ORDER_NUM` cap used in `MarketSellAssetActuator` and `UNFREEZE_MAX_TIMES` used in `UnfreezeBalanceV2Actuator`), rejecting further delegations once the limit is reached.

### Proof of Concept
1. Confirm target network has not passed proposal #69 (`ALLOW_DELEGATE_OPTIMIZATION` = 0, the default).
2. Attacker creates N fresh accounts, each activated and holding ≥1 TRX plus a minimally frozen V2 balance for BANDWIDTH/ENERGY.
3. From each of the N accounts, attacker submits a `DelegateResourceContract` with `balance = 1_000_000` (1 TRX) targeting the same victim `receiverAddress`.
4. Each call executes `DelegateResourceActuator.delegateResource()` → legacy branch → `receiverIndexCapsule.addFromAccount(...)`, appending one more 21-byte address to the victim's single `DelegatedResourceAccountIndexCapsule` object, unbounded. [8](#0-7) 
5. Repeating this thousands of times inflates the victim's index object size and the read/deserialize/write cost incurred on every subsequent freeze/delegate/undelegate touching the victim's account, at a total attacker cost of `N × (1 TRX + tx fees + account activation fee)`.
