### Title
Disk-index (bucket map) restart file reuse has no self-describing layout/version tag for `IndexEntry<T>`, allowing stale on-disk bucket files to be silently reinterpreted under a mismatched struct layout after a validator binary upgrade - (File: bucket_map/src/bucket_storage.rs)

### Summary
The Solidity finding is about upgradeable proxy contracts whose parent contracts lack storage gaps, so adding new state variables to a base contract silently shifts/corrupts the derived contract's storage layout on upgrade. The equivalent pattern in Agave's disk-backed accounts index (`bucket_map`) is a persisted, `#[repr(C)]`, mmap-backed struct (`IndexEntry<T>`) whose on-disk files are reused across process restarts (and thus across binary/version upgrades) with no embedded, per-struct compatibility tag verifying that the reading code's layout matches the layout the bytes were written with.

### Finding Description
`IndexEntry<T>` is a `#[repr(C)]` struct persisted directly into memory-mapped bucket files by the accounts-index disk bucket map: [1](#0-0) 

When a `Bucket` is constructed, it computes `elem_size` fresh from the *current build's* `size_of::<IndexEntry<T>>()` and, if a restart file indicates a previous file exists for this bucket index, it calls `BucketStorage::load_on_restart` to reuse that file: [2](#0-1) 

`load_on_restart` derives `num_elems` purely by dividing the on-disk file length by the caller-supplied `elem_size`, then mmaps the file and treats its bytes directly as the current build's `IndexEntry<T>`/header layout — there is no stored magic number, layout hash, or size check against what actually produced the file: [3](#0-2) 

The only versioning mechanism nearby is the separate `Restart` sidecar file's `Header.version` (`HEADER_VERSION`), which is manually bumped and only guards the sidecar `Header`/`OneIndexBucket` records (`file_name`, `random`, `buckets`, `max_search`) — it is not tied to, and does not validate, the actual `IndexEntry<T>` (or `BucketWithHeader`/`DataBucketRefCountOccupiedHeader`) layout stored in the real bucket data files: [4](#0-3) [5](#0-4) 

If a future code change alters the byte layout of `IndexEntry<T>` / `MultipleSlots` / `PackedStorage` / `PackedRefCount` (e.g., re-ordering fields, changing bitfield widths, or adding a field while keeping the same total size) without a coordinated bump of `HEADER_VERSION` — which is entirely decoupled from these structs and not enforced by any static assertion tying the two together — an old bucket data file produced by a prior binary version will pass the sidecar restart-file check unchanged, be reused via `load_on_restart`, and then be reinterpreted byte-for-byte under the new struct's field semantics. This is the direct Rust analogue of missing storage gaps: a persisted layout is extended/modified without a hard compatibility boundary protecting the exact bytes that are memory-mapped and reinterpreted.

### Impact Explanation
Because `IndexEntry<T>` encodes the pubkey, ref count, occupied flag, and slot-list/storage-offset metadata for the disk-backed accounts index, a layout mismatch silently reinterprets these fields: pubkeys could be read from the wrong byte offsets, ref counts and "occupied" bits could flip meaning, and `storage_offset`/`num_slots` in `MultipleSlots` could point at incorrect data-bucket locations. This produces stale or wrong-version account index entries pointing at incorrect account data after a validator restarts on a new build with a changed struct layout — a silent index corruption on an otherwise honest node, without any error or panic to signal the mismatch.

### Likelihood Explanation
This requires a future Agave code change to the `IndexEntry<T>`-family structs' binary layout without a corresponding change to `HEADER_VERSION` in `restart.rs` (both files are guarded by simple compile-time size asserts, not schema comparisons between the two files). Because nothing in the code today mechanically links `HEADER_VERSION` to the layout of `IndexEntry<T>`/`BucketWithHeader`, this is a latent structural gap: it is currently benign only because no such layout change has been made, exactly analogous to the Solidity report where the absence of storage gaps is not (yet) an active bug but is a real and easily triggered risk on the next upgrade to the affected contracts.

### Recommendation
Add a self-describing format tag to the actual bucket data files (not just the `Restart` sidecar), e.g. a small header written at `offset_to_first_data()` containing a layout/version constant derived from (or manually tied to) `IndexEntry<T>`'s field layout, and validate it in `BucketStorage::load_on_restart`, refusing to reuse (falling back to a fresh file) if it doesn't match. Alternatively, add a compile-time/CI check that enforces `HEADER_VERSION` is bumped whenever the byte layout of `IndexEntry<T>`, `MultipleSlots`, `PackedStorage`, `PackedRefCount`, or `BucketWithHeader`/`DataBucketRefCountOccupiedHeader` changes, closing the "storage gap" analogue between the sidecar restart file and the real persisted index entries.

### Proof of Concept
1. On build A, run a validator with the disk index enabled so `bucket_map` writes index bucket files using build A's `IndexEntry<T>` layout (size `S`, field order `F1`).
2. Ship build B that changes the internal layout of `MultipleSlots`/`PackedStorage`/`PackedRefCount` (e.g., reallocates bits between `ref_count` and `occupied`, or reorders fields) while keeping `size_of::<IndexEntry<T>>() == S` unchanged and without bumping `HEADER_VERSION` in `bucket_map/src/restart.rs`.
3. Restart the validator on build B. `Restart::get_restart_file` succeeds because `Header.version`, `buckets`, and `max_search` are unchanged ( [6](#0-5) ), so each `Bucket::new` reuses the old file via `BucketStorage::load_on_restart` ( [7](#0-6) ).
4. The old bytes, written under build A's field semantics, are now read as build B's `IndexEntry<T>`, silently corrupting ref counts / occupied flags / slot-list offsets for entries in the disk-backed accounts index — with no error raised.

    /// load and mmap the file that is this disk bucket if possible
    pub(crate) fn load_on_restart(
        path: PathBuf,
        elem_size: NonZeroU64,
        max_search: MaxSearch,
        stats: Arc<BucketStats>,
        count: Arc<AtomicU64>,
    ) -> Option<Self> {
        let offset = Self::get_offset_to_first_data();
        let num_elems = std::fs::metadata(&path)
            .ok()
            .map(|metadata| metadata.len().saturating_sub(offset) / elem_size)?;
        if num_elems == 0 {
            return None;
        }
        let mmap = Self::map_open_file(&path, false, 0, &stats)?;
        Some(Self {
            path,
            mmap,
            cell_size: elem_size.into(),
            count,
            stats,
            max_search,
            contents: O::new(Capacity::Actual(num_elems)),
            // since we loaded it, it persisted from last time, so we obviously want to keep it present disk.
            delete_file_on_drop: false,
        })
    }

    pub(crate) fn get_restart_file(config: &BucketMapConfig) -> Option<Restart> {
        let path = config.restart_config_file.as_ref()?;
        let metadata = std::fs::metadata(path).ok()?;
        let file_len = metadata.len();

        let expected_len = Self::expected_len(config.max_buckets);
        if expected_len as u64 != file_len {
            // mismatched len, so ignore this file
            return None;
        }

        let file = OpenOptions::new()
            .read(true)
            .write(true)
            .create(false)
            .open(path)
            .ok()?;
        let mmap = unsafe { MmapMut::map_mut(&file).unwrap() };

        let restart = Restart { mmap };
        let header = restart.get_header();
        if header.version != HEADER_VERSION
            || header.buckets != config.max_buckets as u64
            || header.max_search != config.max_search.unwrap_or(MAX_SEARCH_DEFAULT)
        {
            // file doesn't match our current configuration, so we have to restart with fresh buckets
            return None;
        }

        Some(restart)
    }
