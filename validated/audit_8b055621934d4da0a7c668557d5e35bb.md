### Title
Hardened resource-usage overflow checks in `ResourceProcessor` can throw uncaught `ArithmeticException`, breaking bandwidth/energy accounting and unfreeze liveness - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
`ResourceProcessor.increase()`/`increaseV2()` (and the internal helpers `getUsage()`, `divideCeilExact()`, `getNewWindowSize()`) contain a "hardened" arithmetic path, gated by `hardenCalculation()`/`VMConfig.allowHardenResourceCalculation`, that replaces the legacy silently-overflowing `long` multiplication/division with `BigInteger` math and `longValueExact()`. When the hardened path is active and any intermediate value exceeds `Long.MAX_VALUE`, it throws an uncaught `ArithmeticException` instead of gracefully saturating like the legacy path did. These methods are invoked unconditionally on the hot path of ordinary bandwidth/energy consumption and resource delegation/unfreeze bookkeeping, so a value overflow here aborts processing of an operation that is expected to always succeed - the same "fix introduces a liveness-breaking revert" pattern described in the external report about `initVaultCache`.

### Finding Description
`ResourceProcessor.increase(long, long, long, long, long)` computes `averageLastUsage`/`averageUsage` via `divideCeilExact(BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize)` when hardening is enabled: [1](#0-0) 
and `divideCeilExact` throws when the division has a non-BigInteger-exact quotient beyond `long` range via `longValueExact()`: [2](#0-1) 

The same pattern recurs in `increase(AccountCapsule, ...)` and `increaseV2(AccountCapsule, ...)`, which additionally compute a new window size via `BigInteger` and `divideCeilExact` for delegation transfers: [3](#0-2) 

None of `increase()`, `increaseV2()`, `unDelegateIncrease()`, or `unDelegateIncreaseV2()` catch `ArithmeticException` internally: [4](#0-3) 

These methods are the core of bandwidth/energy usage accounting invoked on essentially every transaction (via `BandwidthProcessor`/`EnergyProcessor`, which extend `ResourceProcessor`) and during resource-delegation cancellation/unfreeze flows. Existing test coverage in the repo (`ResourceProcessorHardenTest`, `RepositoryImplHardenTest`, `CalculateGlobalLimitHardenTest`) explicitly documents and asserts this behavior change - i.e. the hardening feature was added specifically to detect overflow that used to be silently tolerated, but as a side effect now surfaces an uncaught `ArithmeticException` where the legacy code path would have simply wrapped/continued: [5](#0-4) [6](#0-5) [7](#0-6) 

This mirrors exactly the bug class in the external report: a function that graceful-degrades some overflow paths (e.g. legacy `usage * windowSize / precision`) but reverts (throws) on others once hardening is enabled, breaking the assumption that basic account-state bookkeeping operations (analogous to `withdraw`/`redeem`/`liquidate` in the report) must always be able to execute.

### Impact Explanation
If an uncaught `ArithmeticException` propagates out of `ResourceProcessor.increase()`/`increaseV2()` during ordinary transaction bandwidth/energy consumption or during `unDelegateIncrease`/`unDelegateIncreaseV2` (used when cancelling delegation or unfreezing v2 balances), the enclosing actuator/processor call would fail unexpectedly instead of returning a normal validation error. Because these paths sit underneath account-level resource bookkeeping that every transaction from an affected account must go through, a triggering account could become permanently unable to have transactions processed (persistent per-account DoS), and if triggered during block-level processing rather than pre-validation, it risks destabilizing node transaction execution/consensus (uncaught runtime exception during block application). This matches the "Medium risk - breaks liveness for operations that should always be executable" severity level of the original report.

### Likelihood Explanation
Reaching the overflow threshold requires `lastUsage`/`usage` values on the order of `Long.MAX_VALUE / precision` (~9.2×10¹² given `precision = 10^6`), or comparably large `windowSize`/`WINDOW_SIZE_PRECISION` products in `increaseV2`. Under normal TRX-supply-bounded bandwidth/energy usage counters this is very unlikely to occur through ordinary network activity, similar to the original Euler finding, which was also rated Medium precisely because it requires an extreme/edge-case accumulator state rather than being trivially triggerable by any transaction. The risk is elevated for `increaseV2`'s window-size computation, which multiplies usage by `windowSize * WINDOW_SIZE_PRECISION` and by receiver-provided `remainReceiverWindowSizeV2`, narrowing (but not eliminating) the safety margin compared to the simple usage/precision case.

### Recommendation
- Catch `ArithmeticException` at the boundaries of `ResourceProcessor.increase()`, `increaseV2()`, `unDelegateIncrease()`, and `unDelegateIncreaseV2()` and fail closed in a controlled way (e.g., clamp to `Long.MAX_VALUE` or reject the specific sub-operation) rather than letting the exception propagate into actuator execution.
- Ensure operations that must always be able to complete for a well-formed account (bandwidth/energy usage updates on every transaction, unfreeze/cancel-delegation bookkeeping) never depend on an unguarded overflow-throwing computation.
- Add explicit upper bounds/validation on `usage`/`windowSize` inputs before they reach the hardened arithmetic, so legitimate accounts cannot be pushed toward the overflow boundary even in adversarial delegation scenarios.

### Proof of Concept
Not independently reproducible from the indexed code alone: reaching the overflow requires driving `lastUsage`/`usage`/`windowSize` fields (persisted in `AccountCapsule`) to magnitudes near `Long.MAX_VALUE / precision` (~9.2×10¹²), which is not achievable through a single ordinary transaction under standard TRX-supply and bandwidth/energy limits. The repository's own hardening tests demonstrate the mechanism directly: [8](#0-7) 
which sets `lastUsage = Long.MAX_VALUE / 10` and shows `processor.increase(...)` throws `ArithmeticException` when hardening (`saveAllowHardenResourceCalculation(1)`) is enabled, versus silently succeeding when disabled - confirming the code path exists and is reachable given a sufficiently corrupted/extreme account state, but a full end-to-end exploit chain from an anonymous transaction to that state was not found in the indexed code.

  public long increaseV2(AccountCapsule accountCapsule, ResourceCode resourceCode,
      long lastUsage, long usage, long lastTime, long now) {
    long oldWindowSizeV2 = accountCapsule.getWindowSizeV2(resourceCode);
    long oldWindowSize = accountCapsule.getWindowSize(resourceCode);
    long averageLastUsage;
    long averageUsage;
    if (hardenCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(this.precision);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision),
          BigInteger.valueOf(oldWindowSize));
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision),
          BigInteger.valueOf(this.windowSize));
    } else {
      averageLastUsage = divideCeil(lastUsage * this.precision, oldWindowSize);
      averageUsage = divideCeil(usage * this.precision, this.windowSize);
    }

    if (lastTime != now) {
      if (lastTime + oldWindowSize > now) {
        long delta = now - lastTime;
        double decay = (oldWindowSize - delta) / (double) oldWindowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }

    long newUsage = getUsage(averageLastUsage, oldWindowSize, averageUsage, this.windowSize);
    long remainUsage = getUsage(averageLastUsage, oldWindowSize);
    if (remainUsage == 0) {
      accountCapsule.setNewWindowSizeV2(resourceCode, this.windowSize * WINDOW_SIZE_PRECISION);
      return newUsage;
    }

    long remainWindowSize = oldWindowSizeV2 - (now - lastTime) * WINDOW_SIZE_PRECISION;
    long newWindowSize;
    if (hardenCalculation()) {
      BigInteger biNewWindowSize = BigInteger.valueOf(remainUsage)
          .multiply(BigInteger.valueOf(remainWindowSize))
          .add(BigInteger.valueOf(usage)
              .multiply(BigInteger.valueOf(this.windowSize))
              .multiply(BigInteger.valueOf(WINDOW_SIZE_PRECISION)));
      newWindowSize = divideCeilExact(biNewWindowSize, BigInteger.valueOf(newUsage));
    } else {
      newWindowSize = divideCeil(
          remainUsage * remainWindowSize + usage * this.windowSize * WINDOW_SIZE_PRECISION,
          newUsage);
    }
    newWindowSize = min(newWindowSize, this.windowSize * WINDOW_SIZE_PRECISION,
        this.disableJavaLangMath());
    accountCapsule.setNewWindowSizeV2(resourceCode, newWindowSize);
    return newUsage;
  }

  public void unDelegateIncrease(AccountCapsule owner, final AccountCapsule receiver,
      long transferUsage, ResourceCode resourceCode, long now) {
    if (dynamicPropertiesStore.supportAllowCancelAllUnfreezeV2()) {
      unDelegateIncreaseV2(owner, receiver, transferUsage, resourceCode, now);
      return;
    }
    long lastOwnerTime = owner.getLastConsumeTime(resourceCode);
    long ownerUsage = owner.getUsage(resourceCode);
    // Update itself first
    ownerUsage = increase(owner, resourceCode, ownerUsage, 0, lastOwnerTime, now);

    long remainOwnerWindowSize = owner.getWindowSize(resourceCode);
    long remainReceiverWindowSize = receiver.getWindowSize(resourceCode);
    remainOwnerWindowSize = remainOwnerWindowSize < 0 ? 0 : remainOwnerWindowSize;
    remainReceiverWindowSize = remainReceiverWindowSize < 0 ? 0 : remainReceiverWindowSize;

    long newOwnerUsage = ownerUsage + transferUsage;
    // mean ownerUsage == 0 and transferUsage == 0
    if (newOwnerUsage == 0) {
      owner.setNewWindowSize(resourceCode, this.windowSize);
      owner.setUsage(resourceCode, 0);
      owner.setLatestTime(resourceCode, now);
      return;
    }
    // calculate new windowSize
    long newOwnerWindowSize = getNewWindowSize(ownerUsage, remainOwnerWindowSize, transferUsage,
        remainReceiverWindowSize, newOwnerUsage);
    owner.setNewWindowSize(resourceCode, newOwnerWindowSize);
    owner.setUsage(resourceCode, newOwnerUsage);
    owner.setLatestTime(resourceCode, now);
  }

  private long divideCeil(long numerator, long denominator) {
    return (numerator / denominator) + ((numerator % denominator) > 0 ? 1 : 0);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }
