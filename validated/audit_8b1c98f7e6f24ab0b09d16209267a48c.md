### Title
Panic-based chunk-processing halt from unvalidated `target_shard` in `GlobalContractDistribution` receipts - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
An unprivileged account can submit a `DeployGlobalContractAction`, which embeds a `target_shard` value into a `GlobalContractDistributionReceipt` at creation time. This value is never re-validated against future shard layouts. When such a receipt sits in the delayed-receipt queue across one or more resharding events and is later drained, the shared, per-chunk draining loop calls `.unwrap()` on `receiver_shard_id()`, which can return `Err` if the shard layout's split history cannot resolve the stale `target_shard`. That `.unwrap()` panics, aborting chunk application deterministically on every honest validator applying that chunk — a transaction-triggered halt, not merely a failure local to the deploying account.

### Finding Description
`DeployGlobalContractAction` is available to any authenticated account (`runtime/runtime/src/global_contracts.rs:23-61`, `action_deploy_global_contract`). It calls `initiate_distribution`, which builds a `GlobalContractDistributionReceipt` with `target_shard = apply_state.shard_id` (the sender's current shard) [1](#0-0) . This receipt then hops shard-by-shard via `forward_distribution_next_shard`, which is itself parameterized on the *current* `shard_layout` at forward time [2](#0-1) , but the already-created receipt's `target_shard`/`already_delivered_shards` fields are frozen values from the shard layout(s) in effect when they were written, and are not re-validated against arbitrarily-far-future layouts.

When such a receipt cannot be applied immediately (e.g. because the destination shard's chunk is saturated), it is pushed into the `DelayedReceiptQueue`, a structure that is shared per shard and can retain items across resharding events, per the module's own documentation: "With ReshardingV3, it's possible for a chunk to have delayed receipts that technically belong to the sibling shard before a resharding event" [3](#0-2) .

The draining loop `DelayedReceiptQueueWrapper::pop`, which runs for **every** popped receipt regardless of which account originated it, filters items via `receipt_filter_fn`:

```
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [4](#0-3) 

`receiver_shard_id` for `GlobalContractDistribution` receipts attempts `shard_layout.resolve_to_current_shard(target_shard)` when the stored `target_shard` is not in the current layout, and returns `Err(EpochError::ShardingError(...))` if it cannot find a descendant shard in the split history:

```
let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard) else {
    return Err(EpochError::ShardingError(format!(
        "Shard {target_shard} does not exist in the shard layout or its split history",
    )));
};
``` [5](#0-4) 

The `.unwrap()` in `receipt_filter_fn` converts that `Err` into an immediate panic. Because `pop`/`peek_iter` are invoked while applying every chunk on the shard that owns the delayed queue (`runtime/runtime/src/lib.rs` receipt-processing path), a receipt whose `target_shard` cannot be resolved (an old, stale value carried from a chunk producer/user action, aged across resharding boundaries beyond what `resolve_to_current_shard`'s split history supports) causes `Runtime::apply` to panic deterministically for every validator applying that chunk — halting that shard's chunk production/validation, not just the receipt's own delivery.

This exactly mirrors the reported bug class: a value supplied via ordinary user action (`target_shard`, set implicitly from the deploying account's shard at the time of the `DeployGlobalContractAction`) is stored without forward-looking validation against future protocol state (future shard layouts), and later consumed inside a *shared* processing loop (`DelayedReceiptQueueWrapper::pop`, run once per chunk for the whole shard) whose failure aborts processing for everyone sharing that queue — analogous to how a bad `alert_minutes` value aborted the shared alert-scan loop for all users in the Open WebUI report.

The repository already contains a regression test (`test_stale_global_contract_distribution_after_double_resharding`) explicitly built to probe this exact failure mode after two sequential resharding events, and it asserts the chain does *not* stall — i.e. the maintainers are aware this `.unwrap()` is a known panic surface and have only validated it for a two-level resharding chain [6](#0-5) . Whether `resolve_to_current_shard`'s split-history walk is unconditionally complete for arbitrarily deep/complex resharding sequences (e.g. more splits, merges, or long-lived delayed receipts spanning many epochs) could not be fully confirmed from the available index; the `resolve_to_current_shard` implementations exist in `core/primitives/src/shard_layout/mod.rs` and `v3.rs`, but their full bodies were not retrieved before this analysis had to conclude.

### Impact Explanation
If any code path can produce a `GlobalContractDistributionReceipt` whose `target_shard` becomes unresolvable under a later shard layout (e.g. deeper resharding chains, unusual split/merge sequences, or long queue residency that outlives the tracked split history), the `.unwrap()` at `congestion_control.rs:876` turns a normal `Result::Err` into a hard panic inside `Runtime::apply`. Because chunk application is deterministic and run by every validator, this is a **transaction-triggered halt**: a single account's `DeployGlobalContractAction`, combined with enough delay/resharding, can stop chunk progress on the affected shard for all participants, not just the deployer — satisfying the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Exploitability depends on the completeness of `resolve_to_current_shard`'s split-history tracking, which was not fully verified here. The maintainers' own targeted regression test for "double resharding" suggests this is a recognized risk surface that required a fix to at least the two-level case; the analog is a genuine architectural weakness (unvalidated forward-looking data with an `.unwrap()` in a shared per-chunk loop) even if the currently tracked history depth mitigates the simplest reproduction. Likelihood should be treated as data-dependent on resharding frequency/complexity and delayed-queue residency time, both realistic in a long-lived deployment with multiple resharding events.

### Recommendation
Replace the `.unwrap()` in `DelayedReceiptQueueWrapper::receipt_filter_fn` (and any other unconditional `.unwrap()` on `receiver_shard_id()` in shared per-chunk paths) with graceful error propagation that surfaces as a `RuntimeError`/logged inconsistency rather than a hard panic, and/or ensure `ShardLayout::resolve_to_current_shard` is proven complete for the full historical split/merge graph regardless of how many resharding generations a `GlobalContractDistributionReceipt` survives in the delayed/outgoing-buffer queues.

### Proof of Concept
1. An unprivileged account submits `DeployGlobalContractAction` on shard `S_A`, creating a `GlobalContractDistributionReceipt` with `target_shard = S_A` (`global_contracts.rs:141-169`).
2. The chunk producer/validators saturate compute on the receiving shard so the receipt is pushed into the shard's `DelayedReceiptQueue` (as demonstrated by `test_stale_global_contract_distribution_after_double_resharding`, `global_contracts_distribution.rs:30-186`).
3. Two (or more, depending on split-history coverage) resharding events occur while the receipt remains queued, aging `target_shard` beyond what `resolve_to_current_shard`'s tracked history can map.
4. When the delayed queue is drained, `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` → `receiver_shard_id()` returns `Err(EpochError::ShardingError(...))`, and the `.unwrap()` panics, aborting `Runtime::apply` for every validator applying that chunk — halting the shard.

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,
    receipt_sink: &mut ReceiptSink,
    receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
) -> Result<(), RuntimeError> {
    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()
    else {
        return Ok(());
    };
    let already_delivered_shards = Vec::from_iter(already_delivered_shards);
    let predecessor_id = receipt.predecessor_id().clone();
    let next_receipt = global_contract_data.forward(next_shard, already_delivered_shards);
    let mut next_receipt = Receipt::new_global_contract_distribution(predecessor_id, next_receipt);
    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);
    if apply_state.save_receipt_to_tx {
        receipt_to_tx.push((
            receipt_id,
            ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: *receipt.receipt_id(),
                    parent_predecessor_id: receipt.predecessor_id().clone(),
                }),
                receiver_account_id: next_receipt.receiver_id().clone(),
                shard_id: apply_state.shard_id,
            }),
        ));
    }
    receipt_sink.forward_or_buffer_receipt(next_receipt, apply_state, state_update)?;
    Ok(())
}

```rust
    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }
