## No vulnerability found for this question.

**Validation of the claimed equality:**

The question asks whether `coinbase_recipient_scheduled == coinbase_recipient_committed_by_tx_merkle_root` can be broken by mutating the coinbase's recipient after signing but keeping the stale `tx_merkle_root`.

Tracing the actual code path: `NakamotoBlock` cannot even come into existence as a validated in-memory struct without recomputing and checking the Merkle root during deserialization. `NakamotoBlock::consensus_deserialize` explicitly recomputes the root from the actual `txs` and rejects any mismatch: [1](#0-0) 

This check happens unconditionally for both the RPC path (`getblock_v3` retrieving stored/deserialized blocks) and the P2P path (`NakamotoBlocksData::consensus_deserialize`, which decodes a `Vec<NakamotoBlock>` and thus invokes the same per-block deserializer): [2](#0-1) 

Because deserialization is a prerequisite for a block to be handled by any later stage (`validate_normal_against_burnchain`, `check_tenure_tx`, `check_normal_coinbase_tx`, or eventual `make_scheduled_miner_reward`), a block whose coinbase recipient was mutated post-signing without recomputing `tx_merkle_root` is rejected as `CodecError::DeserializeError("Invalid block: tx Merkle root mismatch")` before it ever reaches `NakamotoChainState::validate_normal_nakamoto_block_burnchain` or `check_normal_coinbase_tx`. The code comment in `validate_normal_against_burnchain` itself documents that `tx_merkle_root` is checked earlier at deserialization time and is intentionally not re-verified here: [3](#0-2) 

The question's own premise concedes this ("only tx_merkle_root binds it, which was already checked earlier during deserialization"), and the impact is explicitly conditioned on a hypothetical *separate* bug in `blocks.rs` deserialization that doesn't actually exist in this repo — the Merkle root check is present and unconditional at the single canonical deserialization entrypoint. There is no reachable code path in this repository where a `NakamotoBlock` with a `tx_merkle_root` inconsistent with its own `txs` reaches `check_normal_coinbase_tx` or `make_scheduled_miner_reward`. Both sides of the claimed equality remain equal in all cases: the scheduled recipient always equals the recipient in the coinbase tx that the (necessarily correct) `tx_merkle_root` commits to.
