### Title
Unvalidated `RevertInstructions.FundRecipient` allows attacker-supplied non-address value to be used as the refund destination for reverted/rescued cross-chain funds - ([File: x/uexecutor/types/inbound.go])

### Summary
The bug-class from the Celo report is: a user/attacker-influenced identifier is accepted and stored without validating that it is a well-formed, resolvable target, and is later consumed by a fund-critical operation that assumes it is valid. In Push Chain, the direct analog is `Inbound.RevertInstructions.FundRecipient` — a field populated from data emitted by the (attacker-controlled) source-chain deposit/gateway event — which is never validated for address format, yet is used directly as the destination for refunds when an inbound deposit fails, when a stuck ballot is reverted, and when funds are rescued.

### Finding Description
`Inbound.ValidateBasic()` and `Inbound.ValidateForExecution()` in [1](#0-0)  perform address-format validation (`utils.IsValidAddress(p.Recipient, utils.HEX)`) only on `p.Recipient` (the Push Chain destination). `RevertInstructions.FundRecipient` is never checked by either validation pass — it only goes through `Canonicalize()`, which is explicitly "lenient": [2](#0-1)  keeps unparseable values "trimmed, never rejected."

This unvalidated `FundRecipient` is then propagated directly into fund-movement paths as the destination address without any additional format check:
- `buildRevertOutbound` (used for GAS/FUNDS swap failures, failed validation, and admin `RevertStuckInbound`) sets `outbound.Recipient = inbound.RevertInstructions.FundRecipient` verbatim: [3](#0-2) 
- `handleFailedOutbound` re-mints tokens to `recipient := outbound.RevertInstructions.FundRecipient` and calls `common.HexToAddress(recipient)` directly: [4](#0-3) 
- `AttachRescueOutboundFromReceipt` uses the same `FundRecipient` fallback as the rescue outbound recipient: [5](#0-4) 

`OutboundTx.ValidateBasic()` only checks that `Recipient` is non-empty (not that it is well-formed): [6](#0-5) . Because `go-ethereum`'s `common.HexToAddress` silently truncates/pads malformed input rather than erroring, a malformed `FundRecipient` does not cause the deposit-side re-mint (`handleFailedOutbound`) to fail — it silently re-mints PRC20 to a garbage/truncated address on Push Chain. Separately, for outbound flows targeting the external chain, the TSS/tx-builder layer (`universalClient/chains/svm/tx_builder.go`) does perform stricter address decoding for revert recipients on the SVM path, meaning a malformed `FundRecipient` there would fail signing/broadcast (funds permanently stuck as a `PENDING`/`ABORTED` outbound that never completes) rather than lose funds outright — but on the EVM PRC20 re-mint path (`handleFailedOutbound`) the failure mode is silent minting to a wrong address, not a hard revert.

### Impact Explanation
Since `FundRecipient` originates from data the depositor (an unprivileged external-chain actor) controls when initiating a deposit/gateway call, a malicious or buggy depositor can supply a malformed value. Depending on the code path this reaches:
- On EVM PRC20 re-mint (`handleFailedOutbound`/`CallPRC20Deposit`), the malformed address is coerced by `common.HexToAddress` into some 20-byte value with no error — refunded principal is minted to an address the depositor may not control, i.e., unauthorized/unintended mint destination and potential permanent loss of the refunded funds.
- On outbound-to-external-chain paths, an invalid `Recipient`/`FundRecipient` can leave the outbound permanently `PENDING`/unresolvable at the TSS layer, i.e., permanent freezing of the refund.

This matches the in-scope "permanent loss," "permanent freezing," and "unauthorized mint/refund" impact categories, and the trigger is purely from an ordinary/malicious depositor's inbound payload — no privileged actor is required.

### Likelihood Explanation
Medium. The attacker only needs to control the raw event data used to populate `RevertInstructions.FundRecipient` when making a deposit on the source chain (this is exactly the class of "external, attacker-influenced but not oracle-dishonest" input the scope calls in-scope). The condition is only reached when the primary execution path fails (swap failure, missing token config, validation failure, or admin revert of a stuck ballot) or a rescue is needed — these are all reachable states shown to occur even under benign conditions in the test suite (e.g. `execute_inbound_gas_test.go` shows GAS-type deposits routinely fail with a revert outbound in normal operation because there's no AMM liquidity). This raises the practical likelihood that a malformed `FundRecipient` reaches the vulnerable code paths.

### Recommendation
Add strict address-format validation of `RevertInstructions.FundRecipient` at the same validation points that check `Recipient`:
- In `Inbound.ValidateForExecution()`, when `RevertInstructions` is present and non-empty, validate `FundRecipient` against the appropriate namespace format for the outbound destination chain (EVM hex-checksum format for eip155 chains, base58 for SVM, etc.), mirroring the existing `utils.IsValidAddress(p.Recipient, utils.HEX)` checks.
- In `buildRevertOutbound` and `handleFailedOutbound`, reject (fail closed, marking the outbound `ABORTED` for manual intervention) rather than silently proceeding with `common.HexToAddress` on an unvalidated string.
- Extend `OutboundTx.ValidateBasic()` to validate that `Recipient` is a well-formed address for `DestinationChain`'s namespace, not just non-empty.

### Proof of Concept
1. An external-chain user calls the Push Chain gateway to deposit funds with `revertInstructions.fundRecipient` set to a malformed value (e.g., a truncated or non-hex string) rather than a valid EVM address, using a `TxType_GAS` or `TxType_FUNDS` inbound that is likely to fail post-execution (e.g., swap failure due to slippage/no liquidity, as reproduced in `execute_inbound_gas_test.go`'s "GAS inbound swap failure creates INBOUND_REVERT outbound" test at [7](#0-6) ).
2. Universal Validators observe and vote the inbound honestly; `ExecuteInboundGas`/`ExecuteInboundFundsAndPayload` fails as designed and calls `buildRevertOutbound`, which copies `FundRecipient` verbatim into `outbound.Recipient` without format validation ( [8](#0-7) ).
3. When the outbound observation eventually reports failure (or for the PRC20 re-mint branch), `handleFailedOutbound` calls `common.HexToAddress(recipient)` on the malformed string and mints the refunded PRC20 to whatever address that resolves to ( [4](#0-3) ), with no error raised — the depositor's refund is misrouted with no on-chain indication of the mismatch.

// Canonicalize normalizes encoding-variant fields in place (per source-chain
// namespace) so the same event from any observer is byte-identical across
// ballot keys, UTX keys and registry lookups. Lenient (unparseable values are
// kept trimmed, never rejected) because the vote path must always record a
// UTX — execution-level validation rejects malformed inbounds later.
func (p *Inbound) Canonicalize() {
	p.SourceChain = strings.TrimSpace(p.SourceChain)
	p.TxHash = utils.LenientCanonicalizeTxHash(p.SourceChain, p.TxHash)
	p.Sender = utils.LenientCanonicalizeAddress(p.SourceChain, p.Sender)
	p.AssetAddr = utils.LenientCanonicalizeAddress(p.SourceChain, p.AssetAddr)
	// Recipient lives on Push Chain (EVM) regardless of source chain.
	p.Recipient = utils.LenientCanonicalizeEVMAddress(p.Recipient)
	p.LogIndex = strings.TrimSpace(p.LogIndex)
	p.Amount = strings.TrimSpace(p.Amount)
	p.RawPayload = utils.CanonicalizeHexBlob(p.RawPayload)
	p.VerificationData = utils.CanonicalizeHexBlob(p.VerificationData)
	if p.RevertInstructions != nil {
		// Refunds return to the source chain.
		p.RevertInstructions.FundRecipient = utils.LenientCanonicalizeAddress(p.SourceChain, p.RevertInstructions.FundRecipient)
	}
}

// ValidateBasic does minimal sanity checks needed to accept a vote.
// Only fields required to identify the inbound and create a UTX key are validated here.
// Execution-level validation (amount, addresses, payload, recipient) is deferred to
// ValidateForExecution so that invalid inbounds still produce an on-chain UTX record
// (with a failed PCTx / revert) instead of silently dropping the vote and leaving
// user funds stuck in the gateway.
func (p Inbound) ValidateBasic() error {
	// Validate source_chain (must follow CAIP-2 format) — needed for UTX key
	chain := strings.TrimSpace(p.SourceChain)
	if chain == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain cannot be empty")
	}
	if !strings.Contains(chain, ":") {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain must be in CAIP-2 format <namespace>:<reference>")
	}

	// Validate tx_hash — needed for UTX key
	if strings.TrimSpace(p.TxHash) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "tx_hash cannot be empty")
	}

	// Validate sender — needed for revert recipient fallback
	if strings.TrimSpace(p.Sender) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "sender cannot be empty")
	}

	// Validate log_index — needed for UTX key
	if strings.TrimSpace(p.LogIndex) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "log_index cannot be empty")
	}

	// Validate tx_type enum — needed to route execution
	if _, ok := TxType_name[int32(p.TxType)]; !ok || p.TxType == TxType_UNSPECIFIED_TX {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid tx_type: %v", p.TxType)
	}

	return nil
}

// ValidateForExecution checks fields that are required for actual execution of the inbound.
// Called after ballot finalization, before ExecuteInbound. Failures here produce a failed
// PCTx and (for non-isCEA) a revert outbound, rather than dropping the vote.
func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}

func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {

		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}
