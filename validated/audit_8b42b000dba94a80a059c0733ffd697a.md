### Title
Stale zToken liquidity index used from block-scoped `index-cache` after `socialize-debt` write-down, allowing overvalued zToken collateral within the same block - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`accrue-and-cache` in `v0-4-market.clar` memoizes vault accrual results (`index`/`lindex`) keyed only by `{ timestamp: stacks-block-time, aid }`. Any market operation in the same block that has already primed this cache for an asset will cause subsequent operations in that same block to reuse the cached `lindex`, even if the vault's real `lindex` has since been permanently written down by `socialize-debt` following a bad-debt liquidation. Because `resolve-ztoken` prices zToken collateral directly off this cached `lindex`, a user can have their zToken collateral valued using a stale, higher (pre-write-down) `lindex` within the same block that the write-down occurred, producing an inflated collateral valuation.

### Finding Description
`accrue-and-cache` treats a cache hit as authoritative for the entire block: [1](#0-0) 

```
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)
      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

The cache key contains only the block timestamp and asset id — it has no dependency on the actual state version of the vault (e.g. `total-assets`, `lindex` version). It is a persistent `define-map`, so entries survive across separate transactions mined in the same block, not just within one transaction's execution.

`resolve-ztoken` (used to price zToken collateral, e.g. zSTX/zsBTC/etc.) consumes exactly this cached value: [2](#0-1) 

```
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
```

Under normal time-based interest accrual, a cache hit within the same block is harmless because zero elapsed time means the index would not change anyway. However, `socialize-debt` is not a time-based accrual — it is a **discrete, instantaneous write-down** of `lindex` triggered by bad-debt liquidation (`liquidate` → `fold socialize-debt-asset` → vault `socialize-debt`), which permanently reduces `lindex` to reflect a loss in `total-assets`, independent of block time: [3](#0-2) 

```
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        ...
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
    (try! (check-caller-auth))
    ...
```

Sequence within a single block N (same `stacks-block-time`):
1. TX A (any user, e.g. a `collateral-add`/`borrow` call touching zSTX) calls `accrue-and-cache(STX)`, which is a cache MISS, so it calls `vault-accrue`, reads `lindex = L0`, and stores `index-cache[{timestamp: N, aid: STX}] = {index, lindex: L0}`.
2. TX B (a `liquidate` call on an under-collateralized borrower in the STX market) results in `no-collateral-left` bad debt, triggering `socialize-debt` on `vault-stx`, permanently reducing the real vault `lindex` to `L1 < L0`.
3. TX C, still within block N, calls a market function that needs to price zSTX collateral (e.g. another user's `collateral-add`, `borrow`, or a liquidation valuation) and internally calls `accrue-and-cache(STX)` again. Because `stacks-block-time` is unchanged, this is a cache **HIT**, returning the stale `L0` instead of the true `L1`.
4. `resolve-ztoken` computes zSTX price using `L0` instead of `L1`, over-valuing zSTX collateral for the remainder of block N.

This is a "cached value not invalidated when its source moves" pattern: the cache is invalidated only by block-time rollover, not by the specific event (`socialize-debt`) that changes the underlying vault state it is meant to represent.

### Impact Explanation
An over-valued zToken price directly inflates a user's `collateral-value` used in `is-healthy`/`is-healthy-with-mask` checks in `borrow`, `collateral-add`, and `collateral-remove`. This lets a user borrow more than their true collateral backs, or avoid/undervalue a legitimate liquidation, creating under-collateralized debt in the protocol. Since this directly enables extraction of funds beyond what collateral actually secures, it falls under **Critical impact: protocol insolvency / permanent freezing of funds** for other depositors whose withdrawable liquidity is impaired by the resulting bad debt.

### Likelihood Explanation
Requires a bad-debt liquidation event (`socialize-debt`) to occur, and a subsequent market interaction referencing the same zToken/asset within the same block — both realistic on a busy chain with multiple transactions per block, and an attacker (or an opportunistic borrower) can also intentionally trigger this by monitoring pending liquidations and immediately submitting a transaction in the same block to exploit the stale cache before block time advances. Likelihood is Medium: it depends on timing (same-block execution) but does not require any privileged access.

### Recommendation
Invalidate or bypass the `index-cache` entry whenever `socialize-debt` (or any non-time-based state mutation of `lindex`/`assets`) is executed on a vault, e.g., by having `socialize-debt` also update/clear the corresponding `index-cache` entry in the market contract, or by keying the cache on a vault-state version/nonce rather than purely on `stacks-block-time`, so that any out-of-band mutation forces re-accrual on the next read.

### Proof of Concept
1. Block N, TX1: User A calls `collateral-add` (or `borrow`) for zSTX, causing `accrue-and-cache(STX)` cache MISS; `index-cache[{timestamp: N, aid: STX}]` is set with `lindex = L0`.
2. Block N, TX2: A liquidator calls `liquidate` on Borrower B's STX debt position, resulting in `no-collateral-left = true`, triggering `socialize-debt-asset` → vault `socialize-debt`, writing `lindex` down to `L1 < L0` in `vault-stx`'s persistent state.
3. Block N, TX3: User C (or User A again) calls `collateral-add`/`borrow` referencing zSTX collateral; `resolve-ztoken` calls `get-cached-indexes(STX)` → `accrue-and-cache(STX)` → cache HIT returns stale `{lindex: L0}` instead of the current `L1`.
4. User C's zSTX collateral is valued at `p * L0 / INDEX-PRECISION` instead of the correct `p * L1 / INDEX-PRECISION`, an inflated valuation, allowing User C to pass health checks and borrow more than the true collateral value supports.

Note: I was unable to fully trace every call path of `check-caller-auth`/`accrue` inside the vault contracts within the available tool budget to rule out an internal re-sync mechanism between `socialize-debt` and the market's `index-cache`; based on the code reviewed, no such synchronization exists (the market cache is never explicitly cleared on `socialize-debt`).
