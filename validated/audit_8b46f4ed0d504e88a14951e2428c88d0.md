### Title
`WITHDRAWREWARD` TVM opcode returns success with a silent no-op when there is no reward to withdraw - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java])

### Summary
The TVM native contract that implements the `withdrawreward()` builtin (exposed to smart contracts via the `WITHDRAWREWARD` opcode) never reverts when the caller has zero allowance/reward. Instead of failing the call, it silently returns `0` and the enclosing transaction still succeeds. This mirrors the Liquity "redeem without redemptions might still return success" bug class: a state-changing operation that finds "nothing to do" completes successfully instead of reverting, so callers relying on transaction success (rather than inspecting the return value) can be misled into believing a reward was withdrawn.

### Finding Description
`WithdrawRewardProcessor.validate()` only rejects genesis/guard-representative accounts; it performs no check that the account actually has a positive reward/allowance to withdraw: [1](#0-0) 

`execute()` then computes the allowance and, if it is `<= 0`, simply returns `0` without throwing any exception — no state is changed and no revert occurs: [2](#0-1) 

This is invoked from `Program.withdrawReward()`, which is reached from the `WITHDRAWREWARD` TVM opcode handler `OperationActions.withdrawRewardAction()`: [3](#0-2) [4](#0-3) 

The opcode handler always pushes the returned `long allowance` (which can legitimately be `0`) onto the stack and calls `program.step()` to continue execution normally — there is no VM-level exception, no revert, and no distinguishable failure signal other than the numeric return value itself.

This is functionally identical to the reported bug pattern: a redemption/withdrawal-style operation that determines "there is nothing to redeem/withdraw" but completes the call successfully instead of reverting with a descriptive error. Contrast this with the equivalent externally-triggered `WithdrawBalanceActuator`, which explicitly validates and reverts with `"witnessAccount does not have any reward"` when there is no allowance/reward: [5](#0-4) 

The TVM native-contract path (`WITHDRAWREWARD` opcode) lacks this equivalent guard.

### Impact Explanation
Any smart contract on the TRON network can call `withdrawreward()` at any time. If another contract or an off-chain caller invokes this function without carefully checking the returned amount (e.g., assumes success == nonzero reward, similar to patterns seen with ERC20-style return-value checks being skipped), it may proceed with downstream logic (e.g., crediting a user, marking a reward cycle as claimed, emitting a "reward claimed" event) even though zero TRX was actually moved. Because the call always "succeeds" from the EVM/TVM perspective (no revert, no exception propagated to the caller contract), a defensively-written contract that doesn't explicitly check the return value for zero could record incorrect internal accounting. This is a caller-integration/accounting-integrity risk rather than direct fund theft, consistent with the informational/low severity of the original Liquity finding.

### Likelihood Explanation
Likelihood is moderate: reaching this state simply requires deploying/calling a contract that invokes the `withdrawreward()` builtin when the caller's `beginCycle > currentCycle`, when votes are empty, or otherwise has zero computed reward and zero existing allowance — all attainable through ordinary, unprivileged transactions (no special permissions, keys, or node compromise needed), matching the "broadcast transaction / TVM execution" reachable-path requirement.

### Recommendation
Add an explicit check in `WithdrawRewardProcessor.execute()` (or `validate()`) that reverts with a descriptive `ContractExeException`/`ContractValidateException` (e.g., "no reward to withdraw") when the computed allowance is `<= 0`, mirroring the check already present in `WithdrawBalanceActuator.validate()`. Alternatively, if returning `0` is intended as a valid signal for TVM callers (as the code comment "If no allowance, do nothing and just return zero" suggests), document this contract behavior clearly and audit/ensure that no first-party contract logic relies on transaction success alone to infer a non-zero reward was withdrawn.

### Proof of Concept
1. Deploy a contract that calls the `withdrawreward()` builtin (as in `VoteTest`'s `Vote` contract, method `withdrawRewardMethod`). [6](#0-5) 
2. Trigger `withdrawRewardMethod` from an account/contract with no accrued reward and zero allowance (e.g., before any `payRewardAndDoMaintenance` cycle, as exercised by `checkRewardAndWithdraw(contract, true)` in the test suite, which asserts `rewardBySystem == 0` yet still calls `withdrawRewardMethod` with `SUCCESS`). [7](#0-6) 
3. Observe the transaction result status is `SUCCESS`/no revert, and the returned value is `0`, even though no reward existed — matching the "success despite nothing redeemed" pattern from the source report.

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }

  public long withdrawReward() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawReward", nonce, null);

    WithdrawRewardParam param = new WithdrawRewardParam();
    param.setOwnerAddress(owner);
    param.setNowInMs(getTimestamp().longValue() * 1000);
    try {
      WithdrawRewardProcessor processor = new WithdrawRewardProcessor();
      processor.validate(param, repository);
      long allowance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(allowance);
      }
      return allowance;
    } catch (ContractValidateException e) {
      logger.warn("TVM WithdrawReward: validate failure. Reason: {}", e.getMessage());
    } catch (ContractExeException e) {
      logger.warn("TVM WithdrawReward: execute failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
  }
