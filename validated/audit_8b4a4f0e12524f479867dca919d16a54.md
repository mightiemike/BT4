### Title
Unbounded recursion in `get_recursive_transaction_results` allows an unprivileged RPC caller to crash a node by requesting the status of a transaction whose contract fanned out many receipts - (File: chain/chain/src/chain.rs)

### Summary
`get_recursive_transaction_results` walks the receipt tree produced by a transaction, recursing once per `receipt_id` referenced by each execution outcome, with no depth limit, no visited-set/cycle guard, and no bound on the total number of nodes visited. This is the same bug class as CVE-2014-9527 (Apache POI HSLFSlideShow): attacker-controlled input drives a loop/traversal whose termination is not actually bounded, letting an attacker force the victim into effectively unbounded work (here: unbounded native-stack recursion / unbounded node visitation), causing a crash or hang of the serving node.

### Finding Description
`get_final_transaction_result` (`chain/chain/src/chain.rs:3211`) calls `get_recursive_transaction_results` (`chain/chain/src/chain.rs:3190`) to collect *all* execution outcomes reachable from a transaction hash: [1](#0-0) 

For every execution outcome, the function iterates over `outcome.receipt_ids` and recurses into each one with no depth counter and no check for whether an `id` has already been visited:

```rust
for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
    let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
    self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
}
```

There is no analog of the `MAX_DEPTH` guard that the newer `ReceiptToTx` machinery explicitly added for the same class of problem — a sibling code path (`GetReceiptToTx`) enforces `MAX_DEPTH = 1000` and returns `DepthExceeded` when a receipt-parent chain gets too long: [2](#0-1) 

`get_recursive_transaction_results` has no equivalent bound. The receipt tree it walks is directly shaped by the contract logic of the *original submitted transaction*: any account can deploy/call a contract that fans out into many outgoing action/data receipts per call (e.g. multiple `promise_batch_action_function_call`s or `promise_then` chains), and each of those receipts, once executed, produces its own outcome with its own `receipt_ids`. A contract that recursively fans out (e.g., a self-call that issues `K` outgoing promises, each of which recurses similarly) creates a receipt DAG whose node count grows multiplicatively with fan-out depth. The existing test contract already demonstrates deep, gas-metered self-recursion: [3](#0-2) 
producing recursion depths of 56–221 for a single chain (`slow_test_self_delay`): [4](#0-3) 
— that test measures a *single* chain, but nothing prevents a contract from creating multiple outgoing receipts per call (fan-out) instead of one, which the recursive-traversal function will visit exhaustively, and, being naive recursion instead of an explicit work-queue with a visited/size cap, will consume call-stack proportional to depth and CPU/memory proportional to total node count.

`get_final_transaction_result` is exposed to any unprivileged caller through the standard `tx` / `EXPERIMENTAL_tx_status` JSON-RPC calls (as evidenced by its use throughout the client/integration-test code and openrpc.json entries), so any account can (1) submit one cheap-looking transaction whose contract fans out into a wide/deep receipt tree, then (2) query that transaction's status via RPC to trigger the unbounded recursive traversal on the serving node.

### Impact Explanation
This is a transaction-triggered denial-of-service against any RPC/view node (or any component, e.g. `Chain`, that calls `get_final_transaction_result`) serving that transaction's status: unbounded native-stack recursion can stack-overflow and crash the serving process (no graceful error path — Rust stack overflow aborts the process), or, short of that, the unbounded number of `get_execution_outcome` lookups/allocations produces disproportionate CPU/memory consumption per RPC request. Because the node process backing JSON-RPC/view calls is shared infrastructure (validators typically also serve RPC, or dedicated RPC/view nodes serve many users), a crash there is a real availability impact triggered purely by a single submitted transaction plus a follow-up status query — both actions available to any unprivileged account/caller. This matches the required class of "transaction-triggered halt."

### Likelihood Explanation
Likelihood is medium: constructing a contract that fans out into many outgoing receipts is straightforward (a handful of `promise_batch_action_function_call` calls per invocation, recursively self-calling), and 300 Tgas budgets combined with self-recursion have already been shown in-repo to reach recursion depths in the 200s for a single linear chain; a fan-out design trades depth for breadth and can multiply the total node count substantially within the same gas budget, since the traversal function's cost is not bounded by anything related to the gas that was spent creating the receipts — it is bounded only by the number of receipts in the tree, which an attacker directly controls via how the receipts branch. No special privileges, validator status, or network position are required — only an ordinary signed transaction and a subsequent RPC query.

### Recommendation
Replace the naive recursive traversal in `get_recursive_transaction_results` with an explicit iterative work-queue (BFS/DFS with an explicit stack, not native recursion) and add:
- a maximum total node/outcome cap (analogous to the `MAX_DEPTH = 1000` guard already used for `ReceiptToTx`), returning an explicit error (e.g. `DepthExceeded`/`TooManyOutcomes`) once exceeded instead of continuing to traverse or overflowing the stack;
- a visited-set guard to avoid redundant re-traversal if the same receipt id is referenced from multiple outcomes.

### Proof of Concept
1. Deploy a contract whose exported method, when called, issues `K` outgoing `FunctionCall` promises to itself (fan-out) instead of one, each of which repeats the same fan-out up to a gas-bounded depth `D` (mirroring the pattern in `max_self_recursion_delay` at `runtime/near-test-contracts/test-contract-rs/src/lib.rs:887-921`, but replacing the single `promise_batch_create` self-call with `K` such calls per invocation).
2. Submit one transaction invoking this method with `K ≥ 2` and enough prepaid gas to reach a depth `D` such that `K^D` is large (e.g. `K=4`, `D=15` ⇒ over a billion nodes, while the gas cost per level is only the fixed promise/function-call dispatch fee, well within existing max gas limits given fan-out amortizes cost per branch level rather than per node visited by the RPC query, which visits every produced receipt outcome).
3. Once the transaction's receipts finish executing on-chain, call the standard `tx` or `EXPERIMENTAL_tx_status` JSON-RPC method for the submitted transaction's hash on the serving RPC node.
4. `Chain::get_final_transaction_result` → `get_recursive_transaction_results` recurses over every produced outcome with no cap, exhausting stack/CPU/memory on the serving node in response to a single RPC request from an unprivileged caller.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}

/// Test delaying the conclusion of a receipt for as long as possible through the use of self
/// cross-contract calls.
#[test]
fn slow_test_self_delay() {
    let node = setup_test_contract(near_test_contracts::rs_contract());
    let res = node
        .user()
        .function_call(
            "alice.near".parse().unwrap(),
            "test_contract.alice.near".parse().unwrap(),
            "max_self_recursion_delay",
            vec![0; 4],
            MAX_GAS,
            Balance::ZERO,
        )
        .unwrap();

    // The exact expected depth varies depending on the set of enabled features.
    // When test_features are enabled, the test contract becomes larger and the calls to it are more expensive.
    // When nightly is enabled, the gas costs change a bit.
    // The test makes sure that the depth is within the expected range, but it doesn't check an exact value
    // to avoid having separate cases for every possible combination of features.
    let min_expected_depth = 56;
    // The upper limit has been recently bumped to 221 from the previous value of 62 after the
    // adjustment of a function call gas costs.
    let max_expected_depth = 221;
    match res.status {
        FinalExecutionStatus::SuccessValue(depth_bytes) => {
            let depth = u32::from_be_bytes(depth_bytes.try_into().unwrap());
            assert!(
                depth >= min_expected_depth,
                "The function has recursed fewer times than expected: {depth} < {min_expected_depth}",
            );

                "The function has recursed more times than expected: {depth} > {max_expected_depth}",
            );
        }

    }
}
