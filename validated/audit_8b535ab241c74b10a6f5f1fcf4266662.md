### Title
Unrestricted `WithdrawFromGasKey` nested inside a `Delegate` meta-transaction drains gas-key balances before protocol version 87 - ([File: runtime/runtime/src/action_validation.rs])

### Summary
At the current stable protocol version (86), any account holding both a plain access key and a gas key can wrap a `WithdrawFromGasKey` action inside a `DelegateAction` (meta transaction) and have it admitted and executed without restriction, silently draining the gas key's balance. The guard that blocks this (`WithdrawFromGasKeyNotAllowedInDelegate`) only activates at protocol version 87, which is not yet live on the stable chain in this codebase.

### Finding Description
`WithdrawFromGasKeyAction` is documented as an action that "must only be available via transactions, not via contract execution" [1](#0-0) , and is implemented in `action_withdraw_from_gas_key`, which decreases the gas key's stored `balance` and increases the owning account's balance by `action.amount` with no additional caller/authorization constraints beyond signature verification of the outer action [2](#0-1) .

The validation path `validate_delegate_action` only rejects a nested `WithdrawFromGasKey` action when `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is enabled for the current protocol version and the receipt is new (not an in-flight existing receipt): [3](#0-2) 

`ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is gated to activate at protocol version **87**: [4](#0-3) 

The comment documenting the feature explicitly states the root cause: the SPICE pending transaction queue only scans the *top-level* actions of a transaction for `WithdrawFromGasKey`, so a `WithdrawFromGasKey` nested inside a `Delegate`/`DelegateV2` action bypasses that scan and drains the gas key balance outside of the queue's tracked commitments: [5](#0-4) 

The regression/behavior test confirms the pre-upgrade (i.e., current stable) behavior: a `Delegate` action wrapping `WithdrawFromGasKey` is admitted and executes successfully, draining exactly `WITHDRAW_AMOUNT` from the gas key, and is only rejected once the node's protocol version reaches 87: [6](#0-5) 

### Impact Explanation
This is a concrete unauthorized/uncontrolled value movement: `WithdrawFromGasKeyAction` was designed to be restricted to direct transactions specifically because the pending-transaction queue (used e.g. by SPICE-mode nodes to admit gas-key transactions against a committed balance) cannot see nested withdrawals. When nested in a `Delegate` action, the withdrawal executes and mutates account/gas-key balances while evading the balance-tracking invariant the queue relies on, matching the reported bug-class of an unauthorized/unguarded function draining stored balance to a recipient the caller controls (the `sender_id`/gas key owner, in this analog, but achieved via a code path meant to be blocked). This can let a gas key holder circumvent balance/allowance commitments the runtime is supposed to enforce for gas-key transactions in flight, causing double-spend-like admission of transactions or improperly permitted balance transfers relative to committed gas-key balance.

### Likelihood Explanation
High reachability: any account with an existing gas key can construct a `SignedDelegateAction`/`Delegate` action wrapping `WithdrawFromGasKey` and submit it as an ordinary transaction — no special privileges, validator status, or network position needed. The condition is purely protocol-version-gated (activates only at PV 87), so as long as the network runs at or below PV 86 (stable per this codebase, `STABLE_PROTOCOL_VERSION = 86`), the path is live and requires only a single crafted transaction.

### Recommendation
Backport/expedite activation of `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` (or an equivalent runtime-level check independent of protocol-version gating) to the currently deployed stable protocol version, or add an unconditional check in `validate_delegate_action`/`action_withdraw_from_gas_key` rejecting `WithdrawFromGasKey` whenever it appears as a nested action inside any `Delegate`/`DelegateV2` action, regardless of protocol version, until the pending-transaction queue is fixed to observe nested actions.

### Proof of Concept
The existing test demonstrates the exploit path end-to-end (build gas key, fund it via `TransferToGasKey`, then submit a `Delegate` action from the sender's plain key wrapping `WithdrawFromGasKey`, observing successful execution and gas-key balance reduction) prior to protocol version 87: [7](#0-6)

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}

fn validate_delegate_action(
    limit_config: &LimitConfig,
    delegate_action: VersionedDelegateActionRef<'_>,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    // Check the count before `get_actions()` clones the list, so a huge
    // nested-action list can't force the allocation before being rejected.
    // Consensus-neutral: same `TotalNumberOfActionsExceeded` as the check in
    // `validate_actions_with_mode` below.
    let num_actions = delegate_action.actions().len() as u64;
    if num_actions > limit_config.max_actions_per_receipt {
        return Err(ActionsValidationError::TotalNumberOfActionsExceeded {
            total_number_of_actions: num_actions,
            limit: limit_config.max_actions_per_receipt,
        });
    }
    let actions = delegate_action.get_actions();
    // As with the `DelegateV2` removal above, receipts created before this rule
    // are still in flight and must keep executing.
    if mode == ValidateReceiptMode::NewReceipt
        && ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(current_protocol_version)
        && actions.iter().any(|action| matches!(action, Action::WithdrawFromGasKey(_)))
    {
        return Err(ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate);
    }

fn test_reject_delegated_gas_key_withdraw_protocol_upgrade() {
    init_test_logger();

    if !ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(PROTOCOL_VERSION) {
        return;
    }

    let new_protocol = ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.protocol_version();
    let old_protocol = new_protocol - 1;
    assert!(
        old_protocol >= MIN_SUPPORTED_PROTOCOL_VERSION,
        "no supported protocol version still admits a delegated WithdrawFromGasKey, so there is \
         nothing left to test here - remove this test"
    );

    let sender = create_account_id("alice");
    let relayer = create_account_id("relayer");
    let epoch_length = 10;

    // Boundary "mm": "alice" lands on the first shard, "relayer" on the second,
    // so the delegate receipt crosses a shard on its way to the sender.
    let shard_layout = ShardLayout::multi_shard_custom(vec![create_account_id("mm")], 1);

    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .protocol_version(old_protocol)
        .protocol_upgrade_schedule(ProtocolUpgradeVotingSchedule::new_immediate(new_protocol))
        .epoch_length(epoch_length)
        .shard_layout(shard_layout)
        .add_user_account(&sender, Balance::from_near(1_000))
        .add_user_account(&relayer, Balance::from_near(1_000))
        .build();

    let gas_key: Signer =
        InMemorySigner::from_seed(sender.clone(), KeyType::ED25519, "gas_key").into();
    let add_key_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::AddKey(Box::new(AddKeyAction {
            public_key: gas_key.public_key(),
            access_key: AccessKey::gas_key_full_access(1),
        }))],
    );
    env.rpc_runner().run_tx(add_key_tx, Duration::seconds(10));

    let fund_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: gas_key.public_key(),
            deposit: Balance::from_near(10),
        }))],
    );
    env.rpc_runner().run_tx(fund_tx, Duration::seconds(10));

    // Before the upgrade the nested withdrawal is admitted and moves balance out
    // of the gas key, which is the hole this rule closes.
    assert_eq!(
        env.rpc_node().protocol_version_at_head(),
        old_protocol,
        "expected to start pre-upgrade"
    );
    let (_, balance_before) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
    let outcome = env
        .rpc_runner()
        .execute_tx(tx, Duration::seconds(10))
        .expect("delegated withdrawal admitted pre-upgrade");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::SuccessValue(_),
        "pre-upgrade delegated withdrawal should execute",
    );
    let (_, balance_after) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    assert_eq!(
        balance_after,
        balance_before.checked_sub(WITHDRAW_AMOUNT).unwrap(),
        "the nested withdrawal should have drained the gas key",
    );

    // Keep submitting across the upgrade boundary. Nothing should crash:
    // transactions admitted just before the upgrade produce receipts that may
    // only execute after it, and those existing receipts must still be tolerated.
    let mut blocks_after_upgrade = 0;
    let mut iterations = 0;
    while blocks_after_upgrade < 5 {
        iterations += 1;
        assert!(iterations < 20 * epoch_length, "the upgrade never happened");
        let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
        env.rpc_node().submit_tx(tx);
        env.rpc_runner().run_for_number_of_blocks(1);
        if env.rpc_node().protocol_version_at_head() >= new_protocol {
            blocks_after_upgrade += 1;
        }
    }

    // After the upgrade the meta transaction is rejected at admission.
    assert!(
        ProtocolFeature::RejectWithdrawFromGasKeyInDelegate
            .enabled(env.rpc_node().protocol_version_at_head())
    );
    let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
    let err = env
        .rpc_runner()
        .execute_tx(tx, Duration::seconds(10))
        .expect_err("delegated withdrawal should be rejected post-upgrade");
    assert_matches!(
        err,
        InvalidTxError::ActionsValidation(
            ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate
        ),
        "post-upgrade delegated withdrawal should be rejected with the new error, got {err:?}",
    );
