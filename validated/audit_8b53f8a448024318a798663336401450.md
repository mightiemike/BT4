## Finding Confirmed

The code contains a real, self-acknowledged gap matching the described issue.

### Title
Missing checkpoint-hash validation in `TransactionOutput::ensure_match_transaction_info` allows replay-verify tooling to accept a divergent hot-state/position-state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` only validates `status`, `gas_used`, the write-set hash (`state_change_hash`), and `event_root_hash` against a given `TransactionInfo`. It never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — even though `TransactionInfoV1` carries all three, and the executor commit path (`DoLedgerUpdate::assemble_transaction_infos`) binds all of them into the hash that goes into the transaction accumulator.

### Finding Description
`ensure_match_transaction_info` performs four checks — status, gas, write-set hash, event root hash — and then returns `Ok(())`, with an explicit `TODO(trading-native)` comment stating that it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)" and that this allows replay-verify tooling such as `db-tool`'s `replay_on_archive` to report a successful replay "even when the authenticated position state root diverges from local execution." [1](#0-0) 

By contrast, the real commit path correctly threads `position_state_checkpoint_hash` and `hot_state_checkpoint_hash` into `TransactionInfoV1`, which is what gets hashed into the ledger accumulator: [2](#0-1) 

The `compute_trading_native_state_roots` feature flag gates whether `DoStateCheckpoint::run` computes and records the position-state checkpoint hash at all, and is only meaningfully active when `transaction_info_v1` and `hotness_in_epilogue` are also enabled: [3](#0-2) [4](#0-3) 

`ensure_match_transaction_info` is consumed by offline/verification tooling — `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` — which re-execute transactions locally and compare the resulting `TransactionOutput` against a `TransactionInfo` pulled from storage/archive/proof material. [5](#0-4) 

Because the comparator skips the checkpoint-hash fields, any of these tools will report a "match"/successful replay even if the `position_state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`state_checkpoint_hash`) actually differs between the supplied `TransactionInfo` and what local execution would have produced.

Importantly, the primary consensus/commit path (`DoStateCheckpoint` → `DoLedgerUpdate::assemble_transaction_infos` → accumulator) computes these checkpoint hashes deterministically from VM-produced write sets, so an unprivileged transaction cannot itself force a wrong value into the accumulator that live validators commit to — the divergence surfaces specifically in the *verification comparator* used by replay/debugger/CLI tooling when checking a given `TransactionInfo` (e.g. one obtained from an archive node, backup, or other external/less-trusted source) against locally re-executed output.

### Impact Explanation
An attacker or a compromised/buggy archive/backup source can supply a `TransactionInfo` whose `position_state_checkpoint_hash` (or `hot_state_checkpoint_hash`) does not correspond to the actual trading-native/hot-state root produced by honest execution, while keeping `status`, `gas_used`, `write_set_hash`, and `event_root_hash` correct (which is easy since these are unaffected by the corrupted field). Tools relying on `ensure_match_transaction_info` — `db-tool replay_on_archive`, `aptos-debugger`, and the CLI replay command — will incorrectly report the replay as verified/successful, masking a real divergence in the authenticated position/hot-state root. This undermines the integrity guarantee that replay-verify tooling is meant to provide for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`-enabled state.

### Likelihood Explanation
Requires `compute_trading_native_state_roots` (and its prerequisites `transaction_info_v1` and `hotness_in_epilogue`) to be enabled, and requires the verifier to be checking against a `TransactionInfo` obtained from an untrusted or independently-corruptible source (archive/backup) rather than one already accumulator-proven against a trusted `LedgerInfo`. The code's own `TODO` comment confirms this is a known, currently-unaddressed gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), indicating the feature is not yet safe to enable without this fix.

### Recommendation
Extend `ensure_match_transaction_info` to validate `state_checkpoint_hash`, and — when present on `TransactionInfoV1` — `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against the corresponding locally-computed values before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` in production, as the existing TODO comment recommends.

### Proof of Concept
1. Enable `compute_trading_native_state_roots` (with `transaction_info_v1` and `hotness_in_epilogue`).
2. Submit an ordinary trading-native-affecting transaction from an unprivileged account so a real `position_state_checkpoint_hash` is computed by `DoStateCheckpoint::compute_position_checkpoint`.
3. Construct a `TransactionInfoV1` copy with the same `status`, `gas_used`, `state_change_hash`, `event_root_hash`, but a different `position_state_checkpoint_hash`.
4. Call `TransactionOutput::ensure_match_transaction_info` with the locally-executed `TransactionOutput` and the tampered `TransactionInfo`; observe it returns `Ok(())`, demonstrating that `db-tool replay_on_archive`/`aptos-debugger`/CLI replay would falsely report a successful, matching replay.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
