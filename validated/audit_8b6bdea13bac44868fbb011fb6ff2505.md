### Title
Cost model's `allocated_accounts_data_size` accounting is bypassed via CPI to `system_program::CreateAccount`/`Allocate`, allowing uncharged account-data growth against the block data-size budget - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_account_data_size_on_instruction` only classifies a `SystemProgramAccountAllocation` when the **top-level** instruction's `program_id` equals `system_program::id()`, using `transaction.program_instructions_iter()`, which enumerates only the transaction's outer (message-level) instructions. An attacker-deployed BPF program that CPIs into `system_program::CreateAccount`/`Allocate` with a large `space` therefore causes this function to return `SystemProgramAccountAllocation::None`, so the cost model attributes zero `allocated_accounts_data_size` to the transaction even though the account really grows on-chain.

### Finding Description
`CostModel::calculate_account_data_size_on_instruction` (cost-model/src/cost_model.rs:242-261) checks `program_id == &system_program::id()` where `program_id` comes from iterating `instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>` sourced from `transaction.program_instructions_iter()` (used in `calculate_cost` at cost-model/src/cost_model.rs:36-52 and `calculate_cost_for_executed_transaction` at cost-model/src/cost_model.rs:56-77). This iterator only exposes the outer message instructions, not CPI/inner instructions dispatched by a user program via `invoke`/`invoke_signed`.

If the top-level `program_id` is anything other than `system_program::id()` (e.g., the attacker's own BPF program), the function unconditionally returns `SystemProgramAccountAllocation::None` (cost-model/src/cost_model.rs:258-260), regardless of what that program does internally. `calculate_allocated_accounts_data_size` (cost-model/src/cost_model.rs:265-301) sums these per-instruction results and treats `None` as contributing 0 to `tx_attempted_allocation_size`. The resulting `allocated_accounts_data_size` is stored on `TransactionCost` and fed into `CostTracker::try_add` (cost-model/src/cost_tracker.rs:220-225), which is the sole gate enforcing `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (`WouldExceedAccountDataBlockLimit`) per block.

Critically, this static/top-level-only accounting is used both pre-execution (`calculate_cost`) and post-execution (`calculate_cost_for_executed_transaction`, which is used to correct actual execution/loaded-account-size costs but still recomputes `allocated_accounts_data_size` via the same `program_instructions_iter()`-based function, not from actual execution results). Meanwhile, the *real* account data growth is tracked completely separately by the bank via `AccountsDeltas`/`accounts_resize_delta` and `Bank::update_accounts_data_size_delta_on_chain` (runtime/src/bank.rs:4448-4459), and is only bounded per-transaction by `TransactionAccounts::can_data_be_resized`'s `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`/`MAX_ACCOUNT_DATA_LEN` checks (transaction-context/src/transaction_accounts.rs:309-326) - there is no cross-check reconciling actual growth against what `CostTracker::allocated_accounts_data_size` charged for the block budget.

Consequently, a transaction that top-level-invokes only the attacker's own program, which CPIs into System's `CreateAccount`/`Allocate` with large `space`, passes `CostTracker::try_add`'s `WouldExceedAccountDataBlockLimit` check while contributing 0 to `self.allocated_accounts_data_size`, even though the account data genuinely grows and consumes real block/space capacity.

### Impact Explanation
This does not create a compute-unit metering bypass (CU execution cost is still charged via `programs_execution_cost`/CU limit), but it does violate the accounting totality of the `allocated_accounts_data_size` mechanism that backs `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (cost-model/src/block_cost_limits.rs:35-37) and `CostTrackerLimits::allocated_data_size` (cost-model/src/cost_tracker.rs:100-108). An attacker can pack a block with CPI-based allocations that real-world grow account data well beyond the intended per-block data-size budget while the cost tracker's ledger for that budget shows near-zero usage, starving the fee-market throttle designed to bound per-block account-data growth (resource-exhaustion / fee-market category, not funds theft or consensus divergence). This matches the "starving the fee market for `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` capacity" scoped impact in the question.

### Likelihood Explanation
Preconditions: a funded keypair (to pay normal transaction fees/rent) and a deployed CPI-relay BPF program that invokes `system_program::create_account`/`allocate` via CPI - both trivially achievable by any unprivileged user (program deployment is permissionless). Cost to the attacker is only the ordinary transaction fee, rent for the created account (rent is not bypassed - `system_program::CreateAccount` still requires sufficient lamports for rent-exemption, enforced by the System program at execution time, not by the cost model), and the compute units consumed by the CPI, which are charged normally. The bypass is specific to the block-level `allocated_accounts_data_size` bookkeeping, not to CU/fee charging, and is fully repeatable across any number of transactions/blocks.

### Recommendation
Update `CostModel::calculate_allocated_accounts_data_size`/`calculate_account_data_size_on_instruction` to walk inner (CPI) instructions as well as top-level instructions when statically estimating allocation size, or, since static analysis of on-chain program behavior cannot fully predict CPI targets, prefer basing the block-level accounting on the transaction's *actual* executed `AccountsDeltas`/`accounts_resize_delta` (already computed in `TransactionExecutionDetails::accounts_deltas`, runtime/svm) rather than solely on pre-execution static parsing of `program_instructions_iter()`. At minimum, reconcile `CostTracker::allocated_accounts_data_size` bookkeeping with `Bank::accounts_data_size_delta_on_chain` after execution.

### Proof of Concept
1. Deploy an SBF "relay" program `R` that accepts a `space: u64` parameter and CPIs into `system_program::create_account`/`allocate` with that `space`.
2. Build and sanitize a transaction whose only top-level instruction invokes `R` (not `system_program` directly), passing a large `space`.
3. Unit-test (cost-model/src/cost_model.rs style, extending the existing `test_calculate_allocated_accounts_data_size_*` tests): call `CostModel::calculate_allocated_accounts_data_size(sanitized_tx.program_instructions_iter(), &FeatureSet::all_enabled())` and assert it returns `0`.
4. Bank/SVM integration test: process this transaction with a real bank (similar to `test_accounts_data_size_with_good_transaction` in runtime/src/bank/tests.rs), and assert `bank.load_accounts_data_size_delta_on_chain()` increases by `space` while the `CostTracker`'s `allocated_accounts_data_size` (via `bank.read_cost_tracker().unwrap().stats().allocated_accounts_data_size`) remains `0`, demonstrating the mismatch between real growth and the block-level budget bookkeeping.
