### Title
ECDSA signature malleability in Nakamoto block/signer-signature verification allows a single block's semantic content to map to multiple valid `block_id`s - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures` recovers signer public keys via `Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s`, which deliberately skips the canonical low-S check that `PublicKey::verify` (and Clarity's `secp256k1-verify`) enforce elsewhere in the codebase. Because ECDSA signatures are malleable (`(r, s)` and `(r, n-s)` are both valid for the same message, and the second form is derivable by anyone from the first using only public information), any already-signed Nakamoto block can be re-emitted with a bit-different but equally-valid `signer_signature` vector. Since the block's `block_id`/hash covers the serialized header including the signature bytes, this produces a second, distinct valid identifier for an otherwise identical block — breaking the assumption that a block's id is a canonical, content-derived value.

### Finding Description
`verify_signer_signatures` accepts high-S ("malleated") signer signatures by design: [1](#0-0) 

which calls into: [2](#0-1) 

Here `verify_low_s` is explicitly set to `false` for signer-signature validation, unlike the strict path (`verify()`/`recover_to_pubkey`) used for e.g. Clarity's `secp256k1-verify`, which normalizes and rejects high-S signatures: [3](#0-2) 

The repository's own test helper documents and exploits exactly this malleability against Nakamoto blocks: [4](#0-3) 

The comment states plainly: flipping a miner/signer's signature via `s' = n - s` (with the recovery-id parity bit flipped) "recovers to the same public key, so the signature remains valid, but its bytes (and any hash committing to them) change... Used to construct malleablized blocks: flipping the miner signature changes a block's id without changing its execution."

This is the same bug class as the external report: a signature-verification path that fails to enforce the canonical scalar form (`0 ≤ S < order/2`, i.e., low-S) allows multiple distinct signature encodings to satisfy the same public key/message pair. In gnark, this breaks nullifier/anti-replay logic keyed on `(R,S)`. Here it breaks the equality "one block's content ⇒ one block identifier," because the `block_id` incorporates the (malleable) `signer_signature` bytes while the `Secp256k1PublicKey::verify`-equivalent check used for signer signatures (`recover_to_pubkey_without_validating_low_s`) treats both the low-S and high-S encodings as equally valid.

Critically, no private key is needed to produce the second valid signature — malleation is a public-key operation on an existing valid signature. Any observer that sees a signed, gossip-relayed Nakamoto block can therefore mint an alternate, equally-valid encoding of that same block with a different `block_id`.

### Impact Explanation
Because downstream consensus-critical logic (staging-block storage, canonical-chain-tip tracking, and child blocks' `parent_block_id` references) is keyed by `block_id`, having two valid `block_id`s for what is semantically one block means:
- Different nodes that receive/relay different malleated variants of the same block can disagree about which specific `block_id` is "the" tip, even though the executed state is identical.
- Any anti-equivocation, orphan-detection, or "already processed this block" logic that keys strictly on `block_id` (rather than semantic content such as `consensus_hash` + `signer_signature_hash` + txid list) can be defeated by relaying a malleated duplicate, causing temporary tip/identifier disagreement across the network (bounded fork/ambiguity) without requiring a majority of signers or any privileged key.

This matches the "High" impact bucket: a minority-triggerable, unprivileged validation/identity divergence causing temporary tip disagreement, reachable purely through public signature-malleation math with no private key or majority collusion required.

### Likelihood Explanation
High. The exploit requires no cryptographic secret — only observing one validly-signed Nakamoto block on the wire and performing a public scalar-negation on each `MessageSignature` in `signer_signature`. The codebase already contains a ready-made helper (`malleablize_signature`) demonstrating the transform is straightforward and produces a signature that `verify_signer_signatures` still accepts (since it explicitly skips low-S enforcement via `recover_to_pubkey_without_validating_low_s`).

### Recommendation
- Enforce canonical low-S signatures in `verify_signer_signatures` (and everywhere Nakamoto miner/signer signatures are validated), i.e. use `Secp256k1PublicKey::recover_to_pubkey` (which validates low-S) instead of `recover_to_pubkey_without_validating_low_s`, unless there is a hard backwards-compatibility requirement (in which case gate acceptance of high-S forms behind epoch checks and disallow them going forward).
- Ensure any consensus-critical dedup/anti-equivocation logic is keyed on signature-independent content (e.g., `consensus_hash` + `signer_signature_hash`, which is the pre-signing hash and unaffected by malleability) rather than on `block_id`, which embeds the malleable signature bytes.

### Proof of Concept
1. Observe any propagated `NakamotoBlock` with a valid `signer_signature` vector satisfying `verify_signer_signatures`.
2. For each `MessageSignature` in the vector, compute `s' = n - s` (secp256k1 order `n`) and flip the recovery-id parity bit, exactly as implemented in the existing test helper: [5](#0-4) 
3. Replace the original signatures with the malleated ones in a copy of the block; `verify_signer_signatures` still succeeds because it recovers with `verify_low_s = false`.
4. The malleated block's `block_id` differs from the original's (since the header hash covers the modified signature bytes) despite committing to the same transactions/state, producing two valid identifiers for the same semantic block.

/// high-S/low-S complement `s' = n - s`, with the recovery id's parity bit
/// flipped. It recovers to the same public key, so the signature remains valid,
/// but its bytes (and any hash committing to them) change. Used to construct
/// malleablized blocks: flipping the miner signature changes a block's id
/// without changing its execution.
fn malleablize_signature(sig: &MessageSignature) -> MessageSignature {
    // secp256k1 group order `n`, big-endian.
    const SECP256K1_ORDER_BE: [u8; 32] = [
        0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF,
        0xFE, 0xBA, 0xAE, 0xDC, 0xE6, 0xAF, 0x48, 0xA0, 0x3B, 0xBF, 0xD2, 0x5E, 0x8C, 0xD0, 0x36,
        0x41, 0x41,
    ];
    // MessageSignature layout: [recovery_id (1)][r (32)][s (32)].
    let mut bytes = sig.0;
    // s' = n - s, as a 32-byte big-endian subtraction.
    let mut borrow = 0i16;
    for i in (0..32).rev() {
        let diff = SECP256K1_ORDER_BE[i] as i16 - bytes[33 + i] as i16 - borrow;
        let (val, next_borrow) = if diff < 0 { (diff + 256, 1) } else { (diff, 0) };
        bytes[33 + i] = val as u8;
        borrow = next_borrow;
    }
    // Negating s flips the parity of R, so flip the recovery id's low bit.
    bytes[0] ^= 0x01;
    MessageSignature(bytes)
}
