The premise doesn't hold up against the actual code. `last_l2_height` in `crates/sequencer/src/commitment/controller.rs` is a purely local, sequencer-side monotonic counter over L2 block heights, entirely decoupled from Bitcoin L1 state or reorgs.

**Binding actually enforced**: `should_commit` asserts `l2_height.0 == last_l2_height + 1` on every call, meaning L2 heights must be strictly consecutive or the sequencer panics [1](#0-0) . This counter is advanced purely as the sequencer produces/replays its own L2 blocks — there is no read of any Bitcoin block hash, DA height, or reorg-sensitive value anywhere in `CommitmentController`, `should_commit`, `check_state_diff_threshold`, or `check_max_l2_blocks` [2](#0-1) .

**Leaf ordering is height-based, not DA-based, on both sides**:
- Producer side (`service.rs::get_commitment`) builds the merkle tree from `l2_block_hashes` collected in ascending height order over `commitment_range` [3](#0-2) .
- Verifier side (full node `da_block_handler.rs`) fetches `get_l2_block_range(start..=end)` and builds the tree from `stored_l2_blocks` in the same stored (height-ascending) order, then compares roots byte-for-byte [4](#0-3) .
- Batch-prover verification (`prover.rs::get_batch_proof_circuit_input_from_commitments`) and the STF blueprint (`apply_l2_blocks_from_sequencer_commitments`) both independently rebuild the same range from the ledger DB in height order and assert equality against the claimed `merkle_root` [5](#0-4) [6](#0-5) .

None of these paths derive leaf order from Bitcoin transaction ordering, mempool ordering, or L1 confirmation order — they all key strictly off L2 block height, which is assigned sequentially by the sequencer independent of when/if the containing L1 block is reorged. A reorg of the L1 block that carried the commitment inscription can, at most, cause the commitment to be re-included in a different L1 block (handled by the DA layer's inclusion/finality logic), but it cannot alter which L2 blocks (or in what order) constitute the leaves of an already-computed `merkle_root`, since that computation only depends on `commitment_range` (`start`/`end` L2 heights) stored in `sov_db`. There is no adjacency between L1 reorg depth and `last_l2_height`'s value or the leaf ordering used to build/verify a commitment's merkle root.

Since both sides of the claimed equality (leaf order at build time vs. leaf order at verify time) are always derived identically from stored L2 heights regardless of any L1 reorg, the invariant "commitment roots are order-canonical" is not broken by this entrypoint.

    fn check_state_diff_threshold(
        &self,
        l2_height: L2BlockNumber,
    ) -> anyhow::Result<Option<CommitmentRange>> {
        let mut accumulated_diff = self.state_diff.lock();

        let state_diff = self.ledger_db.get_state_diff(l2_height)?;
        *accumulated_diff = merge_state_diffs(mem::take(&mut accumulated_diff), state_diff.clone());

        let uncompressed_state_diff = borsh::to_vec(accumulated_diff.as_slice())
            .expect("State diff serialization can not fail");
        // early return if uncompressed state diff doesn't exceed safe limit
        if uncompressed_state_diff.len() <= SAFE_MAX_UNCOMPRESSED_TXBODY_SIZE {
            return Ok(None);
        }

        let compressed_state_diff = compress_blob(&uncompressed_state_diff).unwrap();
        if compressed_state_diff.len() <= MAX_TX_BODY_SIZE {
            return Ok(None);
        }

        // when state diff threshold is exceeded, the final block is excluded from the commitment,
        // hence, the new state diff becomes the last l2 block's state diff
        *accumulated_diff = state_diff;

        debug!("Enough state diff to submit commitment");

        Ok(Some(
            L2BlockNumber(self.next_commitment_start_height())..=L2BlockNumber(l2_height.0 - 1),
        ))
    }
