### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` (and `txpool_removeTransactionsBySender`) RPC methods let any caller on the sequencer's public RPC port halt commitment production - ([File: crates/sequencer/src/rpc.rs])

### Summary
The sequencer's public JSON-RPC endpoint exposes `citrea_haltCommitments`, `citrea_resumeCommitments`, `txpool_removeTransactionsByHash` and `txpool_removeTransactionsBySender` with no caller authentication, while the same RPC module also serves user-facing methods like `eth_sendRawTransaction` on the identical port. Unlike the `backup_*` methods, which are explicitly gated behind an API key, these privileged control-plane methods are reachable by any unauthenticated client that can reach the sequencer's RPC port.

### Finding Description
The sequencer RPC trait defines administrative methods without any built-in access control: [1](#0-0) 

Their implementations forward directly to the sequencer's control channel with no check on `msg.sender`-equivalent identity/authorization: [2](#0-1) 

The runner (the actual state owner) unconditionally applies these messages as soon as they arrive, forwarding the halt/resume signal straight to the `CommitmentService`: [3](#0-2) 

which then stops (or resumes) all commitment production: [4](#0-3) 

The only access-control layer in the RPC stack is the `Auth` middleware, but it only protects three explicitly-listed methods (`backup_create`, `backup_validate`, `backup_info`); `citrea_haltCommitments`, `citrea_resumeCommitments`, and the `txpool_removeTransactions*` methods are absent from that list, so they fall through the "pass straight through" branch: [5](#0-4) 

All of these methods, along with public user methods such as `eth_sendRawTransaction`, are merged into a single `RpcModule` and served from one port with `start_rpc_server`, so there is no separate "internal-only" listener isolating privileged methods from the public-facing ones: [6](#0-5) [7](#0-6) 

`txpool_removeTransactionsBySender` similarly takes an arbitrary `Address` with no verification the caller controls that address, letting anyone purge another user's pending transactions from the sequencer mempool: [8](#0-7) 

This is the same class of bug as the external report: a state-mutating action that should be restricted to a privileged caller (the sequencer operator) instead accepts calls from anyone able to submit a JSON-RPC request, because the code never checks the identity of the caller (analogous to using an attacker-supplied "on behalf of" parameter instead of verifying the caller itself).

### Impact Explanation
Any anonymous party with network access to the sequencer's standard JSON-RPC endpoint (the same endpoint used for normal `eth_sendRawTransaction` traffic) can call `citrea_haltCommitments` to stop the sequencer from publishing `SequencerCommitment`s to the DA layer indefinitely, with no re-authorization or restart required. Since batch/proof generation and L1 finalization of Citrea's rollup state depend on these commitments being posted, this breaks the invariant that only the sequencer operator can suspend chain progress via commitments and mutates critical node state through an unauthenticated JSON-RPC call - matching the accepted "High" impact class ("an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`"). The `txpool_removeTransactionsBySender` method additionally lets any caller silently drop another user's queued transactions from the mempool by specifying their address, mutating the mempool's state on behalf of a victim without their consent.

### Likelihood Explanation
This requires only a raw JSON-RPC request to the sequencer's already-public RPC port; no key, DA control, or node-operator role is needed to send the request. It is directly reachable and repeatable, so likelihood is high.

### Recommendation
Add `citrea_haltCommitments`, `citrea_resumeCommitments`, `txpool_removeTransactionsByHash`, and `txpool_removeTransactionsBySender` to the `Auth` middleware's `PROTECTED_METHODS` list (or otherwise require the operator API key / bind them to a separate internal-only listener), consistent with how `backup_create`/`backup_validate`/`backup_info` are already protected in `crates/common/src/rpc/auth.rs`.

### Proof of Concept
1. Start a Citrea sequencer node with its RPC server bound as configured (e.g. `resources/configs/mock/sequencer_rollup_config.toml`, port `12345`).
2. As an unauthenticated third party (no API key), send:
```
curl -X POST http://<sequencer-host>:12345 \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}'
```
3. Observe (as shown by the existing test `test_sequencer_halt_resume_commitments` in `bin/citrea/tests/mock/sequencer_behaviour.rs`) that no further `SequencerCommitment`s are published to the DA layer even as new L2 blocks continue to be produced, until `citrea_resumeCommitments` is called - which any unauthenticated party can also invoke.
