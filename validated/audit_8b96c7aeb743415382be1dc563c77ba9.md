Confirmed: `socialize-debt` in the vault contracts (e.g. `mainnet/contracts/vault/v0-vault-stx.clar:944-984`) mutates `lindex` directly via `var-set lindex new-lindex` without going through the `accrue`/`accrue-and-cache` path, and it does not touch `market.clar`'s `index-cache` map. ### Title
Stale liquidity-index cache in `accrue-and-cache` lets socialized bad debt within `liquidate-multi` be ignored for later positions in the same transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s `index-cache` map is keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . Because `stacks-block-time` does not change within a transaction, this cache is never invalidated mid-transaction, even when a different code path (vault `socialize-debt`) mutates the underlying vault index that the cache is supposed to mirror. `liquidate-multi` processes several positions in one atomic call, so a bad-debt socialization triggered by liquidating position N can silently be ignored by the cached zToken price used for position N+1.

### Finding Description
`accrue-and-cache` is the single choke-point market.clar uses to keep zToken price resolution consistent with vault state within a block: on cache miss it calls `vault-accrue`, which returns the fresh `{ index, lindex }` pair and stores it under the timestamp key; on cache hit it just returns the stored value without re-checking the vault [1](#0-0) .

`resolve-ztoken` (used during price resolution for all zToken collateral, including in `liquidate`) reads this cache via `get-cached-indexes` and multiplies the underlying price by the cached `lindex` [2](#0-1) .

Separately, each vault exposes `socialize-debt`, which is called by the market when writing off bad debt after a liquidation (`accrue-debt-asset`/`socialize-debt-asset` flow referenced from `liquidate`). `socialize-debt` writes down `lindex` directly with `var-set lindex new-lindex`, bypassing `accrue` entirely [3](#0-2) . It never touches `index-cache` in market.clar, and it does not update `last-update` to force a fresh accrual pass for later reads within the block.

The `liquidate` function first accrues and populates the cache (`accrue-user-debts` / `accrue-user-collateral` → `accrue-and-cache`) before resolving USD-notional collateral/debt values, explicitly commented "accrue FIRST - populates cache ... NOW safe to resolve prices" [4](#0-3) . `liquidate-multi` runs this flow repeatedly, once per position, inside a single top-level call, explicitly documented as processing multiple positions "atomically" in one transaction [5](#0-4) .

Sequence:
1. `liquidate-multi` processes position A, which is liquidated with bad debt remaining; the debt-socialization path calls the underlying vault's `socialize-debt`, writing a new (lower) `lindex` directly into vault storage without updating market's `index-cache`.
2. Before this, position A's own liquidation flow already called `accrue-and-cache` for the shared vault asset (e.g. the vault backing a zToken used as collateral by both positions), populating `index-cache` at key `{ timestamp: stacks-block-time, aid }` with the pre-socialization `lindex`.
3. `liquidate-multi` proceeds to position B, which holds the same zToken as collateral. Its `accrue-and-cache` call for that `aid` hits the cache (same `stacks-block-time`) and returns the pre-socialization `lindex`, never re-querying the vault's now-updated (written-down) `lindex`.
4. `resolve-ztoken` for position B's collateral therefore uses a stale, inflated `lindex`, overvaluing position B's collateral in USD terms.

### Impact Explanation
An overvalued collateral figure for position B changes the computed `current-ltv`, `liq-params`, and the seizable/repayable amounts in `calc-final-liquidation-amounts`. This can let a liquidator seize less collateral than the true (post-write-down) value entitles the protocol to, or let position B be classified as healthier than it is, temporarily freezing/misallocating the value that should have been recovered from B's collateral — a temporary freezing/misallocation of protocol funds within the batch liquidation, falling under the in-scope "temporary freezing of funds" impact.

### Likelihood Explanation
Requires: (a) `liquidate-multi` (or any transaction that liquidates two positions sharing a common vault-backed zToken collateral) processing a position that triggers bad-debt socialization, followed by another position using the same vault asset, all within one transaction/block. This is a plausible, low-difficulty liquidation-bot scenario, not requiring any privileged access, malicious oracle, or DAO compromise — only ordinary market conditions producing multiple simultaneous liquidatable positions with shared collateral asset and one under-collateralized (bad-debt) position.

### Recommendation
Invalidate or bypass `index-cache` entries for a vault `aid` whenever that vault's state is mutated by any non-`accrue-and-cache` path within the same transaction (e.g., `socialize-debt`, `system-borrow`, `system-repay`, `deposit`, `redeem`). Concretely, either (a) have `socialize-debt` and other vault mutators return the updated indexes so the market can re-populate/evict the cache entry for that `aid`, or (b) key the cache off an explicit per-vault mutation nonce/counter rather than solely on `stacks-block-time`, so any intra-block state change forces re-accrual.

### Proof of Concept
Not independently executed; reasoning is based on static code tracing of `accrue-and-cache`, `resolve-ztoken`, `liquidate`, `liquidate-multi`, and vault `socialize-debt` as cited above. A concrete PoC would require a Clarinet/vitest scenario with two borrowers sharing a zToken collateral vault, one position pushed into bad debt, and a single `liquidate-multi` call liquidating both, then asserting the second position's collateral valuation still reflects the pre-write-down `lindex`.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
