## Title
Front-running/sandwich griefing of TRC10 Exchange trades and withdrawals via unprivileged manipulation of pool balances - (`actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
java-tron's built-in TRC10 `Exchange` (a Bancor-relay-style AMM) computes trade output and withdrawal amounts purely from the exchange's current `firstTokenBalance`/`secondTokenBalance`, which any unprivileged account can shift by submitting an `ExchangeTransactionContract` immediately ahead of another user's `ExchangeTransactionContract` or `ExchangeWithdrawContract`. This mirrors the TrueFi report's core bug class: a value that is supposed to reflect pool state (NAV / liquidity) is trivially manipulable by any ordinary, unprivileged participant right before a victim's transaction executes, degrading the victim's outcome (worse price / smaller withdrawal), with the attacker's own capital recovered immediately afterward at negligible cost.

### Finding Description
`ExchangeCapsule.transaction()` computes `buyTokenQuant` for a sell using only the exchange's current in-memory `firstTokenBalance`/`secondTokenBalance` via a Bancor-relay curve (`ExchangeProcessor`/`SafeExchangeProcessor`): [1](#0-0) 

Any account can call `exchangeTransaction()` through `ExchangeTransactionActuator.execute()`, which pulls the live pool balances and updates them atomically per transaction, with no delay or averaging mechanism: [2](#0-1) 

`ExchangeWithdrawActuator.execute()` (and `doValidate()`) likewise reads the *current* `firstTokenBalance`/`secondTokenBalance` at execution time to compute the pro-rata `anotherTokenQuant` the withdrawer receives: [3](#0-2) [4](#0-3) 

Just as in the TrueFi report — where Alice (an allowed, otherwise-legitimate borrower) front-runs Bob's `redeemNFT()`/`arbRestake()` by borrowing right before the NAV is read, temporarily depressing `liquidValue()` and inflating `liquidExitPenalty()` — here Alice (any account, no whitelist needed) can submit an `exchangeTransaction` immediately before Bob's `exchangeTransaction` or the exchange creator's `exchangeWithdraw`, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for Bob, then reverse the trade right after Bob's transaction lands to recover her capital. The cost to Alice is only the Bancor-curve spread and transaction fees, analogous to Alice's short-term loan interest and gas cost in the TrueFi case.

For `ExchangeTransactionActuator`, the `expected` field in `ExchangeTransactionContract` provides partial slippage protection, but it is set by the trader in advance and, if set loosely (or left as a nominal minimum), the sandwich still degrades the trader's realized output up to that threshold. For `ExchangeWithdrawActuator`, there is no slippage/expected-minimum protection at all — `ExchangeWithdrawContract` only carries `token_id` and `quant`, so any balance shift immediately before execution directly reduces the amount the withdrawer receives, with the actuator only checking that the amount is consistent with the (already-manipulated) live ratio, not that it matches the ratio the user intended to withdraw at.

### Impact Explanation
An unprivileged attacker can degrade the economic outcome of TRC10-exchange traders and, more severely, of the exchange creator during `exchangeWithdraw` (which has zero slippage protection), extracting value from victims repeatedly at low cost. This is a concrete underpriced/manipulable public-accounting-state issue: state that should reflect organic market liquidity is trivially steerable by anyone within a single block/transaction window, and there's no delay or TWAP-like smoothing to blunt it, matching the "no impact mitigations exist" characteristic flagged in the TrueFi report.

### Likelihood Explanation
No privileged role, whitelisting, or special setup is required — any account holding the relevant TRC10/TRX can call `ExchangeTransactionContract` and repeat this indefinitely, in the same fashion Alice repeats her attack across many Sherlock users in the source report. The exchange balances are public on-chain data, making target selection and timing straightforward for automated bots.

### Recommendation
Introduce protections analogous to the report's suggested remediation of adding a delay between action and settlement, e.g.: enforce a minimum-received/expected-ratio check on `ExchangeWithdrawContract` (mirroring the `expected` field already present on `ExchangeTransactionContract`), and/or use a time-weighted or multi-block average of `firstTokenBalance`/`secondTokenBalance` rather than the single most-recent state when computing trade and withdrawal outputs, to reduce the profitability of single-transaction sandwiching.

### Proof of Concept
1. Alice observes Bob's pending `ExchangeTransactionContract` or the exchange creator's pending `ExchangeWithdrawContract` targeting exchange `X` in the mempool.
2. Alice submits her own `ExchangeTransactionContract` selling a large amount of one side of pair `X`, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for the next trader (via `ExchangeCapsule.transaction()` at [1](#0-0) ).
3. Bob's transaction (or the creator's `exchangeWithdraw`) executes against the now-skewed balances, receiving less than expected — for `exchangeWithdraw` there is no `expected` guard at all ( [5](#0-4) ), so the victim's received `anotherTokenQuant` is directly reduced by Alice's balance shift.
4. Alice immediately submits a reverse `ExchangeTransactionContract` to restore her original position, recovering nearly all her capital minus the Bancor-curve spread and fees, and repeats this against future victims.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
