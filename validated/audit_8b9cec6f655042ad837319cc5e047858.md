### Title
Front-runnable, deterministic smart-contract deployment address enables cheap Denial-of-Service on `CreateSmartContract` transactions - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
The Astaria report shows that a deterministically pre-computable deployment address, combined with a hard revert if that address is found to already hold state, lets an attacker grief legitimate deployments for a trivial cost. java-tron's `CreateSmartContract` flow has the same shape: the contract address is derived purely from the sender's `ownerAddress` and the (unsigned) `raw_data` hash of the pending transaction, and deployment unconditionally reverts if any account already exists at that address.

### Finding Description
The contract address for a `CreateSmartContract` transaction is computed as `sha3omit12(txRawDataHash || ownerAddress)`: [1](#0-0) 

`txRawDataHash` is `Sha256Hash.of(raw_data)` — i.e. it depends only on the transaction's raw data (owner address, contract payload, timestamp/expiration, fee limit, etc.) and **not** on the signature. This means the future contract address is fully deducible by anyone who observes the unsigned/pending transaction (e.g. in the node's pending-transaction pool, or if the deployer's tooling reveals the raw transaction before broadcast), well before it is included in a block.

Once the address is known, `VMActuator.create()` performs a hard existence check and reverts if any account already occupies that address: [2](#0-1) 

Any ordinary TRX/TRC10 transfer to a previously non-existent address auto-creates a `Normal` account there in java-tron. Therefore an attacker who can compute the victim's future contract address before it lands on-chain can simply front-run with a cheap transfer (or an `AccountCreateContract`) targeting that address, causing the victim's `CreateSmartContract` transaction to fail with `"Trying to create a contract with existing contract address"` — the exact same "pre-fund the deterministic address to corrupt the deployment precondition" pattern described in the Astaria report (`AstariaRouter.sol` reverting on `LIEN_TOKEN.balanceOf(vaultAddr) > 0`).

The same class of hazard exists at the TVM opcode level for internal `CREATE`/`CREATE2`, where `createContractImpl` also aborts (`contractAlreadyExists`) if the target address is already a contract: [3](#0-2) [4](#0-3) 
Notably, for the *legacy* (non-Constantinople) `CREATE` path the code explicitly acknowledges and partially mitigates hash collisions by preserving pre-existing balance rather than reverting: [5](#0-4) 
— but this mitigation only covers balance-preservation for internal `CREATE`, not the top-level `CreateSmartContract` transaction path, which still hard-fails.

### Impact Explanation
This is a griefing/DoS vector, not a fund-theft bug: an attacker cannot steal funds, but can reliably cause a targeted deployer's `CreateSmartContract` transaction to be included on-chain and revert (burning the deployer's bandwidth/energy fee for a failed transaction) by pre-creating an account at the deterministically computable address. Because the address depends on `raw_data` (timestamp/expiration included), each retry by the victim generates a new address, so the attack is not a permanent block, but it can be repeated cheaply for each retry as long as the attacker can observe the pending transaction before confirmation. Impact severity is bounded because (a) it requires the attacker to observe the specific pending transaction in a short window before block inclusion, and (b) each grief only costs the price of a minimal transfer/account-creation, matching the "cheap, unprivileged, invalid-state/DoS" impact class.

### Likelihood Explanation
Likelihood is limited by the practical difficulty of reliably observing a specific victim's pending `CreateSmartContract` transaction before it is confirmed (requires mempool visibility/latency advantage), similar to standard front-running assumptions. It is not a "trusted role" or "internal-only" issue — any unprivileged network participant with mempool visibility can attempt it, and the on-chain logic that causes the revert is unconditionally reachable production code (`VMActuator.create()`), so this is a concrete, reachable analog rather than a purely theoretical one.

### Recommendation
- Avoid hard-reverting the entire deployment transaction solely because an account already exists at the computed address; instead, for the `Normal` (non-contract) pre-existing account case, upgrade it in place (as already done for CREATE2 in `createContractImpl` via `existingAccount.updateAccountType(...)`), preserving balance/resources rather than aborting.
- Only revert if the pre-existing account is already a genuine contract (code/`ContractCapsule` present), mirroring the `isContractExist` check used in the CREATE2 path, so a bare "pre-funded" address cannot be used to grief deployment.
- Apply the same treatment consistently to both the top-level `CreateSmartContract` actuator path (`VMActuator.create()`) and internal TVM `CREATE`, to remove the asymmetry that currently allows a cheap griefing surface only at the top-level path.

### Proof of Concept
1. Attacker monitors the pending-transaction pool for a `CreateSmartContract` transaction from a target deployer address `D`.
2. From the transaction's `raw_data`, attacker computes `txRawDataHash = Sha256(raw_data)` and then `contractAddress = sha3omit12(txRawDataHash || D)` exactly as done in `WalletUtil.generateContractAddress` [1](#0-0) .
3. Attacker submits a minimal TRX transfer (or `AccountCreateContract`) to `contractAddress`, which is confirmed before the victim's deployment transaction (front-run).
4. When the victim's `CreateSmartContract` transaction executes, `VMActuator.create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")` [2](#0-1) , causing the deployment to fail and consuming the victim's fee.

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
