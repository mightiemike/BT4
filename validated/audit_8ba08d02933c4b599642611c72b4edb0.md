### Title
Missing `host` query parameter on embedded admin document requests causes an uncaught `TypeError` (DoS) instead of the intended login redirect - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-shop-and-host-params.ts`)

### Summary
`validateShopAndHostParams` uses non-null assertions (`url.searchParams.get('host')!`) on query parameters that can legitimately be absent, passing the runtime value `null` into `sanitizeHost`. Because `RegExp.prototype.test()` coerces `null` to the string `"null"`, the base64 validity check unexpectedly passes, `atob("null")` decodes to garbage bytes, and those bytes are then fed into `new URL(https://${decoded})`, which can throw an uncaught `TypeError` instead of the intended "invalid host → redirect to login" behavior.

### Finding Description
In `validate-shop-and-host-params.ts`: [1](#0-0) 

The `shop` param, when missing, is coerced through `sanitizeShop(null)`. `RegExp.test()` stringifies `null` to `"null"`, which does not match the shop domain regex, so this path safely returns `null` and correctly triggers `redirectToLoginPath`.

However, the `host` param is more dangerous. In `sanitizeHost`: [2](#0-1) 

`base64regex.test(null)` stringifies to `base64regex.test("null")`, and `"null"` (all alphabetic characters) **matches** `/^[0-9a-zA-Z+/]+={0,2}$/`. This makes `sanitizedHost = "null"`, so the code proceeds to decode it: [3](#0-2) [4](#0-3) 

`atob("null")` decodes to 3 raw bytes (0x9E, 0xE9, 0x65) that are not valid ASCII/IDNA domain characters. Constructing `new URL("https://" + decodedBytes)` can throw an uncaught `TypeError: Invalid URL` because the WHATWG URL host-parsing/IDNA (ToASCII) algorithm rejects such control/extended characters.

This exception is not caught inside `sanitizeHost`/`validateShopAndHostParams`. It propagates up through `authenticateAdmin`'s try/catch in `authenticate.ts`: [5](#0-4) 

The catch block only special-cases `Response` instances for CORS header injection and rethrows everything else unchanged: [6](#0-5) 

So a plain `TypeError` (not a `Response`) is rethrown as-is, resulting in an unhandled exception in the app's route/loader instead of the intended graceful redirect to the login path — breaking the invariant that missing/invalid auth params should always degrade to a clean redirect.

### Impact Explanation
An anonymous, unprivileged client can force an uncaught exception in an `authenticate.admin()`-guarded route simply by omitting the `host` query parameter (while providing a valid `shop` and no session-token header). This is a Denial-of-Service in an authentication handler: instead of a controlled redirect Response, the framework has to surface/handle a raw `TypeError`, which for apps without a top-level error boundary results in a 500 rather than the intended login flow. This matches the "DoS in an authentication handler" impact class called out in scope.

### Likelihood Explanation
- Requires `isEmbeddedApp: true` (default/common configuration for embedded Shopify apps).
- Requires no session-token header, i.e., a plain document GET request — trivially satisfied by any browser/curl request.
- Requires a syntactically valid `shop` parameter but a missing `host` parameter — a single crafted URL, no secrets, no privileges, fully reproducible.

### Recommendation
Do not use non-null assertions on `URLSearchParams.get()` results. Explicitly check for `null`/empty values and short-circuit to `redirectToLoginPath` before calling `sanitizeShop`/`sanitizeHost`, e.g.:
```ts
const shopParam = url.searchParams.get('shop');
const hostParam = url.searchParams.get('host');
if (!shopParam || !hostParam) {
  throw redirectToLoginPath(request, params);
}
```
Additionally, wrap `sanitizeHost`'s `atob`/`new URL` logic in a `try/catch` so any decode/parse failure safely resolves to `sanitizedHost = null` rather than throwing.

### Proof of Concept
```ts
// validate-shop-and-host-params.test.ts
import {validateShopAndHostParams} from '../validate-shop-and-host-params';

it('gracefully redirects instead of throwing when host param is missing', () => {
  const request = new Request(
    'https://my-app.example.com/some-embedded-route?shop=my-store.myshopify.com',
  );
  const params = {
    api: {utils: {sanitizeShop: realSanitizeShop, sanitizeHost: realSanitizeHost}},
    config: {isEmbeddedApp: true, auth: {loginPath: '/auth/login'}},
    logger: {debug: jest.fn()},
  };

  // Expected: throws a redirect Response to loginPath
  // Actual (bug): throws TypeError: Invalid URL from inside sanitizeHost -> decodeHost -> new URL()
  expect(() => validateShopAndHostParams(params as any, request)).not.toThrow(TypeError);
});
```
Equivalent HTTP PoC: `GET https://my-app.example.com/protected-admin-route?shop=my-store.myshopify.com` (no `host` param, no `Authorization`/session-token header) against an embedded app — observe an unhandled `TypeError` instead of a `302` redirect to the login path.
