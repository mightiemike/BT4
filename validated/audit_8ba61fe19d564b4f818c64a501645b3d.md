### Title
Front-running griefing of `ExchangeInjectActuator`/`ExchangeWithdrawActuator` via public `ExchangeTransactionActuator` trades - (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Any unprivileged account can broadcast an `ExchangeTransactionContract` (a public bancor-style trade) to mutate an exchange pair's `firstTokenBalance`/`secondTokenBalance` immediately before the exchange creator's `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction is processed. Because `doValidate()` in both actuators recomputes ratio-dependent quantities and balance-limit/precision checks against the *current* on-chain pool balances rather than any value pinned by the creator, the front-run trade can deterministically force the creator's inject/withdraw transaction to revert, mirroring the `VaultBooster.setBoost()` front-running griefing pattern in the referenced report.

### Finding Description
`ExchangeInjectActuator.doValidate()` reads `firstTokenBalance`/`secondTokenBalance` from the live `ExchangeCapsule` and uses them to compute `anotherTokenQuant`, `newTokenBalance`, `newAnotherTokenBalance`, and to enforce `balanceLimit` and asset-sufficiency checks: [1](#0-0) 

Similarly, `ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` from the live pool balances and enforces a strict precision check (`"Not precise enough"`) and a minimum-balance check (`"exchange balance is not enough"`): [2](#0-1) 

Any account (not the exchange creator) can call `ExchangeTransactionActuator`, which trades against and mutates the same pool balances via `exchangeCapsule.transaction(...)`: [3](#0-2) 

Because the exchange creator has no way to pin the pool state it expects when submitting `setBoost`-equivalent inject/withdraw transactions, an attacker can front-run with a minimal trade sized to push a ratio calculation into a rejected precision bucket, breach `balanceLimit`, or shrink the pool below what the creator's transaction requires — exactly the same TOCTOU mechanic as the `VaultBooster.setBoost()`/`liquidate()` race in the report, where an unprivileged party alters shared state that a privileged configuration transaction checks against.

### Impact Explanation
A griefing attacker with no special role can repeatedly and cheaply (`calcFee()` returns `0` for both inject and withdraw actuators) block an exchange creator from injecting or withdrawing liquidity, since even a 1-unit trade changes the balance ratio enough to trip the `"Not precise enough"` hardened check or the `balanceLimit`/`"another token balance is not enough"` checks. This can indefinitely deny legitimate liquidity management on TRON's on-chain Bancor-style exchange, causing stuck liquidity and degraded exchange usability — a denial-of-service on a protocol-level accounting feature reachable purely via broadcast transactions.

### Likelihood Explanation
High. `ExchangeTransactionActuator` is callable by any account holding the traded token/TRX with no permission checks beyond normal balance sufficiency, and the fee is `0`, making repeated griefing essentially free and always available to any observer of the exchange creator's pending transactions in mempool/block construction.

### Recommendation
Add a tolerance/slippage parameter or a minimum-quantity guard the creator can specify in `ExchangeInjectContract`/`ExchangeWithdrawContract` (analogous to slippage protection in AMMs), or allow the creator to pause trading on the pair before performing inject/withdraw operations, so front-run trades cannot unconditionally force validation failure.

### Proof of Concept
1. Exchange creator prepares an `ExchangeWithdrawContract` transaction sized precisely against current `firstTokenBalance`/`secondTokenBalance`.
2. Attacker observes the pending transaction and broadcasts an `ExchangeTransactionContract` trade for a small amount of the paired token, altering `firstTokenBalance`/`secondTokenBalance` via `exchangeCapsule.transaction(...)`.
3. Once the attacker's transaction is included first, the creator's withdraw transaction is validated against the new balances; the recomputed `anotherTokenQuant` no longer satisfies the hardened precision check, causing `doValidate()` to throw `"Not precise enough"` (or `"exchange balance is not enough"` if sized to breach the minimum), reverting the creator's transaction.
4. The attacker repeats this for every subsequent retry, indefinitely blocking the creator's inject/withdraw operations.
