### Title
Missing Chain/Domain Separation in `ValidateMultiSign` Precompile Message Hash Allows Cross-Chain Signature Replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract constructs its signature-verification message hash from only the account address, permission id, and caller-supplied `data`, with no chain identifier or genesis/network-specific value included. Since TRON account addresses are derived purely from the public key (chain-agnostic) and permission structures can be mirrored across TRON-compatible networks (mainnet, public testnets such as Nile/Shasta, or private forks/sidechains that copy genesis account state), a signature that authorizes a payload for a given `(address, permissionId, data)` tuple on one chain remains valid and replayable on any other chain running the same precompile logic with matching account/permission state.

### Finding Description
`ValidateMultiSign.execute()` builds the hash to be verified as: [1](#0-0) 

```
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter.getInstance().isECKeyCryptoEngine(), combine);
```

This `hash` is then checked against the recovered signer's weight in the account's on-chain `Permission`: [2](#0-1) 

None of `block.chainid`-equivalent data, a genesis block hash, or the precompile/contract address consuming the authorization is folded into `combine`. This mirrors exactly the Opera-Bridge `_verifySignatures()` bug class described in the report: the signed payload commits only to application-level parameters (there: batchId/deposits; here: address/permissionId/data), not to the chain or contract context that is supposed to make the authorization unique.

By contrast, TRON's core transaction signing path (`TransactionCapsule.validatePubSignature` → `checkWeight`) signs `getTransactionId()`, which is derived from `raw` transaction data that includes TAPOS fields (`ref_block_bytes`/`ref_block_hash`), implicitly binding a transaction to a specific chain's recent block history: [3](#0-2)  That implicit domain separation is absent from `ValidateMultiSign`, which any unprivileged smart contract can invoke via the precompiled-contract dispatch table (`getContractForAddress`), making it reachable by ordinary dApp logic that uses this precompile as an off-chain-authorization/meta-transaction primitive.

### Impact Explanation
dApps built on TRON commonly use `ValidateMultiSign` to verify off-chain-signed authorizations (e.g., permit-like flows, multisig-gated operations) without adding their own domain separator, since the precompile is documented/expected to perform the full signature check. Because the address used is the raw TRON account address (chain-agnostic, derived only from the public key) and permission configurations are frequently replicated identically across mainnet and its testnets/forks for testing or multi-deployment purposes, a valid authorization signature captured on one network can be replayed on another network where the same account/permission state exists, letting an attacker execute unauthorized privileged operations (fund transfers, permission-gated contract calls) gated by that signature. This is a concrete authentication/replay impact, not merely theoretical, and it affects unprivileged, generally reachable TVM contract logic.

### Likelihood Explanation
Exploitation requires that the same `(address, permissionId, data)` triple be meaningful and separately reachable/valid on two TRON-compatible networks — a realistic scenario given TRON's ecosystem of public testnets and private/forked deployments that intentionally mirror mainnet account state, and given that address derivation is independent of the chain. The precompile itself is unprivileged and callable by any contract, so likelihood is driven mainly by real-world dApp usage patterns (which frequently omit their own chain-id binding), matching the original report's threat model of "signatures potentially replayable... if deployed on the same chain [structure] or if the contract is redeployed" / in a fork situation.

### Recommendation
Bind the `ValidateMultiSign` (and equivalently `BatchValidateSign`) message hash to chain-specific and precompile/contract-specific context, e.g., include `block.chainid` (or an equivalent network/genesis identifier already tracked by `DynamicPropertiesStore`) and the calling contract address in the `combine` byte array before hashing, following the same remediation the Opera-Bridge team applied (adding destination chain id and processing contract address to the message hash).

### Proof of Concept
1. Deploy identical contract bytecode that calls `ValidateMultiSign(address, permissionId, hash, sigs)` on TRON mainnet and on a TRON-compatible testnet/fork that mirrors the target account's address and `Permission` configuration (a common setup for staging/QA environments).
2. Obtain a valid multisig authorization signature for `(address, permissionId, data)` intended for use on mainnet (e.g., a permit-style authorization signed by the account's active-permission keys).
3. Replay the identical `data`/signature bytes against the testnet/fork deployment's `ValidateMultiSign` call; since `combine = address || permissionId || data` contains no chain-specific value, `hash` is identical on both networks and the signatures verify successfully there as well, allowing the authorization to be exercised twice across environments.

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
