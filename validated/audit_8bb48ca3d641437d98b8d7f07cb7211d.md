## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant that binds a freshly-computed `TransactionOutput` (write set, events, status, gas) to the authenticated `TransactionInfo` that is proven against the transaction accumulator/ledger info. The function deliberately omits verification of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, per an explicit developer TODO in the code itself.

### Finding Description
`ensure_match_transaction_info` checks status, gas, write-set hash, event root hash, and does not check any of the state/hot-state/position checkpoint hashes carried on `TransactionInfo`: [1](#0-0) [2](#0-1) 

The comment explicitly states the consequence: `db-tool`'s `replay_on_archive` can report a successful replay even when the authenticated position state root diverges from local execution, and that checkpoint hashes must be validated before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled. This is confirmed to be the sole consumer for offline consistency checking: `storage/db-tool/src/replay_on_archive.rs` calls `ensure_match_transaction_info` per replayed transaction as its correctness gate: [3](#0-2) 

The state (and hot-state/position) checkpoint hash is the field that actually authenticates the JMT/state-tree root at a checkpoint version — this is the value verified elsewhere in restore flows, e.g. `state_root_hash == manifest.root_hash` in the backup/restore controller: [4](#0-3) 

Because `ensure_match_transaction_info` never re-derives or compares this hash against what local re-execution produced, a divergence between the locally recomputed state root and the historically committed/authenticated `state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) will not be caught by this check. Any tool or verification path relying solely on this function (currently `replay_on_archive`, `aptos-debugger`, and the `aptos move` CLI's replay/verify commands) will "pass" even though the actual state root differs from the correct VM result.

### Impact Explanation
This does not corrupt the live consensus-committed ledger by itself — the transaction accumulator, `TransactionInfo`, and Merkle proof verification code paths (`AccumulatorProof::verify`, `SparseMerkleProof` verification, `TransactionInfoListWithProof::verify`) are unaffected and remain sound; they correctly bind `TransactionInfo` hashes to the ledger root. The concrete broken invariant is narrower: the *self-check* used to validate that re-executed output matches the previously committed `TransactionInfo` state-checkpoint hash is incomplete. This matters because:
- It is the exact mechanism intended to detect a hard-fork-only state divergence during replay/verification (silent state-root drift across a protocol/VM change would go undetected by `replay_on_archive`).
- It directly gates the safety of enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the code comment states — enabling that feature today, or relying on `replay_on_archive` as a correctness oracle for historical state-root integrity, would give false assurance.

This is a real gap but its severity is bounded: it affects only replay/verification tooling, not the consensus commit path itself (`do_ledger_update.rs`'s `assemble_transaction_infos`, which independently computes state-checkpoint hashes at commit time, is unaffected by this gap). I could not fully trace whether any state-sync/chunk-executor "trust-then-verify" path (`ChunkResultVerifier`/`StateSyncChunkVerifier` in `execution/executor/src/chunk_executor`) also depends on this incomplete comparator to accept externally supplied, proof-carrying chunk data as authoritative during fast sync — that would elevate the impact to a live-node state-corruption bug. I was unable to confirm this within the remaining investigation.

### Likelihood Explanation
The gap is triggered automatically any time `replay_on_archive`, `aptos-debugger`, or the CLI verify/replay commands are used to validate historical execution, without any attacker action required — it's a latent correctness/verification gap, not an actively exploitable vector by an unprivileged network attacker on mainnet consensus. It is self-documented as known and intentionally deferred, which lowers its "vulnerability" severity but confirms it as a genuine, provable local gap.

### Recommendation
Extend `ensure_match_transaction_info` to also compare recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against `txn_info`'s corresponding fields (when the local execution has these values available), matching the TODO already present in the code, before any feature depending on this check for state-root authentication (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled.

### Proof of Concept
Not applicable as a live exploit — this is a code-inspection finding based on the explicit gap in `ensure_match_transaction_info` (lines 2139–2204 of `types/src/transaction/mod.rs`) and its sole verification-tool consumer in `storage/db-tool/src/replay_on_archive.rs` (lines 388–406). Demonstrating it concretely would require constructing a `TransactionOutput` whose write-set/events/status/gas match `TransactionInfo` but whose true post-execution state root differs, and observing that `replay_on_archive` reports success — this requires a running node/harness, which I do not have access to.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
