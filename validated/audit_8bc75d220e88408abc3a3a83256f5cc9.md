### Title
Attached deposit from an external caller is permanently lost when the address-registrar lookup or NEP-141 `storage_balance_of` cross-contract call fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::rlp_execute` allows any unprivileged account to call it, optionally attaching a NEAR deposit (`#[payable]`) which is tracked via `CallerDeposit` so it can be refunded if the emulated transaction ultimately fails. However, this refund is only implemented in the terminal `rlp_execute_callback`. The two intermediate callbacks that are invoked for `EOABaseTokenTransfer { address_check: Some(_), .. }` (`address_check_callback`) and for `ERC20Transfer` (`nep_141_storage_balance_callback`) do not perform the refund when their own preliminary cross-contract call (`address_registrar.lookup` or `token::storage_balance_of`) fails.

### Finding Description
`rlp_execute` is `#[payable]` and reachable by any transaction signer/relayer; `CallerDeposit::new` captures `predecessor_account_id` and `attached_deposit` whenever the caller is not the wallet itself [4](#0-3) . This `caller_deposit` is threaded through the promise chains built in `inner_rlp_execute` for `EOABaseTokenTransfer`/`ERC20Transfer` flows [5](#0-4) .

In `address_check_callback`, if `env::promise_result(0)` is `PromiseResult::Failed` (the registrar `lookup` call failed — e.g., ran out of gas, registrar account issue, or any transient failure), the function immediately returns an error `ExecuteResponse` and never touches `caller_deposit`, so no refund promise is scheduled [6](#0-5) .

The same pattern exists in `nep_141_storage_balance_callback`: if the `storage_balance_of` call to the target NEP-141 token fails, the function returns an error response without refunding `caller_deposit` [7](#0-6) .

By contrast, the only path that correctly refunds the caller is the final `rlp_execute_callback`, which explicitly creates a `promise_batch_action_transfer` back to `caller_deposit.account_id` when the final action promise fails [3](#0-2) . This is precisely the missing-error-handling class from the report: a sub-call's failure path is not propagated to the fund-custody logic, silently dropping value that should have been returned to its rightful owner.

### Impact Explanation
Any external, unprivileged account that calls `rlp_execute` with a NEAR deposit attached (e.g., a user or app compensating a relayer, or simply mis-using the flow) permanently loses that deposit — with no refund — whenever the ERC-20 storage-balance check or the address-registrar lookup fails for any reason (target account/contract issue, gas exhaustion of the lookup sub-call, or a malicious/broken token contract that reverts `storage_balance_of`). The deposit remains stuck in the wallet contract's own balance with no code path that returns or accounts for it. This is a concrete case of unauthorized value loss/freezing for the depositor, reachable purely through a transaction to the Wallet Contract.

### Likelihood Explanation
This is triggerable by any caller attaching a deposit to `rlp_execute` and targeting an ERC-20 emulated transfer (or an eth-implicit target requiring the address-registrar check) where the preliminary lookup call fails — which can happen due to ordinary conditions (gas limits, non-existent/paused token contract, registrar unavailability) without any malicious validator or node behavior, making it likely under normal fault conditions, not just adversarial ones.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`: on `PromiseResult::Failed`, if `caller_deposit` is `Some`, create a `promise_batch_create`/`promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the failed `ExecuteResponse`. Consider factoring this into a shared helper to avoid the duplication/omission recurring in future callbacks.

### Proof of Concept
1. An external account `A` (not the wallet owner) calls `rlp_execute` on a wallet contract with an attached deposit `D > 0`, targeting an ERC-20 (`ERC20Transfer`) emulated transaction for a token contract `T` and receiver `R`.
2. `inner_rlp_execute` builds a promise chain: `T::storage_balance_of(R)` → `nep_141_storage_balance_callback(token_id, receiver_id, action, Some(CallerDeposit{account_id: A, yocto_near: D}))` [8](#0-7) .
3. The `storage_balance_of` call to `T` fails (e.g., `T` is paused, deleted, or runs out of gas).
4. `nep_141_storage_balance_callback` hits the `PromiseResult::Failed` branch and returns `ExecuteResponse{success:false,...}` without ever creating a refund promise to `A` [7](#0-6) .
5. `A`'s deposit `D` remains inside the wallet contract's balance permanently, with no execution path recovering it — unlike the symmetric failure of the main action promise, which is refunded in `rlp_execute_callback`.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers

        })
