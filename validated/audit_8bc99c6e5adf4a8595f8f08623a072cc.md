Based on my investigation, I found a concrete Push Chain analog of the external bug's core theme — an unbounded, attacker-controlled gas parameter that is decoupled from the fee/resource-accounting mechanism meant to bound it.

### Title
Unbounded `UniversalPayload.GasLimit` accepted in gasless `MsgExecutePayload`/`MsgMigrateUEA` allows fee-free, uncapped EVM execution - (File: `x/uexecutor/types/universal_payload.go`, `app/txpolicy/gasless.go`, `x/uexecutor/keeper/evm.go`)

### Summary
The external report's root cause is a dynamic, attacker-influenced gas cost that is not properly bounded by the layer meant to constrain it, breaking an invariant that resource consumption maps predictably to what was paid/authorized. Push Chain's `MsgExecutePayload` (and `MsgMigrateUEA`) exhibit the same structural weakness: the user-supplied `UniversalPayload.GasLimit` field is validated only as "a non-negative uint256 string" and is then forwarded verbatim as the real EVM execution gas limit to `DerivedEVMCall`, while the enclosing Cosmos message is in the **gasless whitelist**, meaning no fee is ever charged for the work performed.

### Finding Description
`UniversalPayload.ValidateBasic()` treats `GasLimit` purely as a numeric-format check: [1](#0-0) 

There is no upper bound tied to the Push Chain EVM's block gas limit, no sanity cap, and no relation enforced between this value and any fee actually paid by the caller.

That same `GasLimit` is parsed and passed straight into a committing (`commit=true`) `DerivedEVMCall`: [2](#0-1) 

`MsgExecutePayload` (the message that triggers this call) and `MsgMigrateUEA` are both members of the gasless whitelist, meaning the standard `DeductFeeDecorator` skips fee collection entirely for these messages: [3](#0-2) [4](#0-3) 

The `DERIVED_TRANSACTIONS.md` documentation itself confirms that `gasLimit` is an "Explicit gas limit (`nil` -> use a sensible default)" with no stated cap, and that `gasless` staying `false` is only about receipt visibility, not fee collection — fee collection is separately controlled (and bypassed) by the ante-level gasless whitelist: [5](#0-4) [6](#0-5) 

Combining these facts: an ordinary, unprivileged UEA user can submit a `MsgExecutePayload` with an arbitrarily large `GasLimit` (e.g., pointing at a contract designed to consume near that entire limit via a loop or expensive opcodes), and the transaction pays **zero fee** while still causing full nodes to perform real, committed EVM computation up to that limit. The outer Cosmos `Fee.GasLimit` on the tx envelope is a distinct value from the payload's internal EVM `GasLimit`; the `DeductFeeDecorator` only requires `feeTx.GetGas() != 0` (any positive placeholder value) when not gasless-exempt, and skips this check path for the actual gas/fee that matters once `IsGaslessTx` returns true.

### Impact Explanation
This is an unprivileged, reachable denial-of-service vector under the allowed impact gate ("denial of service only when it is not network-level and is reachable without privileged control"). Repeated submission of `MsgExecutePayload` transactions with maximal `GasLimit` values against gas-hungry UEA-target contracts lets an attacker impose disproportionate, real computational cost on every validating full node without paying commensurate fees, degrading block production throughput. It does not (from what's confirmed) directly enable fund theft, but it undermines the resource/fee invariant that gas-metering is supposed to guarantee for the gasless-admission path (`app/txpolicy/gasless.go`, `app/ante/fee.go`).

### Likelihood Explanation
High: the trigger is a completely ordinary user-facing entry point (`MsgExecutePayload`, whitelisted specifically to let unfunded UEA users transact), requires no validator/relayer/admin cooperation, and no code path found during this investigation enforces an upper bound on `UniversalPayload.GasLimit` relative to a sane per-tx or per-block cap.

### Recommendation
Enforce a maximum cap on `UniversalPayload.GasLimit` in `ValidateBasic()` (e.g., bounded by a chain param well below the EVM block gas limit), and/or require that gasless `MsgExecutePayload`/`MsgMigrateUEA` messages carry a bounded, protocol-defined default gas limit rather than an attacker-supplied value, closing the gap between "no fee charged" and "unbounded EVM computation permitted."

### Proof of Concept
1. Deploy (via a normal `MsgExecutePayload`) a UEA-reachable contract whose fallback/target function performs an expensive loop (e.g., repeated `SSTORE`/hashing) bounded only by supplied gas.
2. Craft and sign a `UniversalPayload` with `To` = that contract, `Data` = call to the expensive function, and `GasLimit` set to a very large value (e.g., near the chain's per-tx/block EVM gas ceiling).
3. Submit as `MsgExecutePayload`; per `app/txpolicy/gasless.go` this message type is gasless, so `DeductFeeDecorator` skips real fee collection.
4. Observe that `CallUEAExecutePayload`/`DerivedEVMCall` commits and executes up to the full attacker-chosen `GasLimit` with no fee paid, and repeat the transaction to impose sustained computational load on validating nodes for free.

**Uncertainty/limitations:** I was not able to fully inspect the `pushchain/evm` fork's internal EVM-gas-to-SDK-gas metering logic (it's an external replaced dependency, not indexed in this repo), so I cannot confirm whether some additional cap exists deeper in that fork's `DerivedEVMCall` implementation. The finding is based on what's verifiable in the scoped repository: no cap in `ValidateBasic`, gasless whitelist membership, and unbounded pass-through into a committing derived call.

```markdown
## The `gasless` Flag

`gasless=true` tells the fork: "this call is part of internal protocol bookkeeping, don't bill any account for the gas." Right now, every Push Chain call site passes `gasless=false`, with the inline comment:

> `// gasless = false (@dev: we need gas to be emitted in the tx receipt)`

The reason: even though the protocol pays the gas, the tx receipt still needs `gas_used` populated so off-chain services (Universal Validators, explorers, the gas-fee accounting in `x/uexecutor`) can read it back. Setting `gasless=true` would suppress the gas field and break that read path.

The flag exists for future use — protocol housekeeping calls that don't need to be observable via receipts (e.g. genesis-time bytecode patches). For day-to-day inbound/outbound execution, `gasless` stays `false`.
```
