### Title
Deposit removed from `DepositDataMempool` on block finalization even when its `BridgeContract::deposit` system tx failed - ([File: crates/sequencer/src/runner.rs])

### Summary
`remove_deposits` is called with the entire batch fetched by `fetch_deposits` (`deposit_data`), not with the subset of deposits whose system transaction actually succeeded in `process_sys_txs`. Since `process_sys_txs` silently reverts and skips any deposit whose `BridgeContract::deposit` call fails during real block production, that deposit is dropped from the mempool at `runner.rs:638` even though no cBTC was minted and no `Deposit` event was emitted.

### Finding Description
Binding that must hold: `deposit removed from accepted_deposit_txs (via remove_deposits) == deposit whose BridgeContract::deposit call actually succeeded and minted cBTC in the finalized block`.

Trace:
1. `citrea_sendRawDepositTransaction` (`crates/sequencer/src/rpc.rs:330-388`) simulates the deposit with `evm.get_call(dep_tx, Some(BlockId::pending()), ...)` and, on success, calls `deposit_mempool.add_deposit_tx(...)`, which records the deposit keyed by `DepositDataMempool::calc_tx_id` (`crates/sequencer/src/deposit_data_mempool.rs:119-136,146-164`). This is only a simulation against pending state at submission time; it does not reflect what light-client/system state will be at actual block-production time.
2. In `advance_l2_block`-style production (`crates/sequencer/src/runner.rs:506-566`), `deposit_data` is fetched via `fetch_deposits` (line 517-520) and reused unmodified through:
   - `dry_run_transactions(...)` at line 549-557, which internally calls `produce_and_run_system_transactions` → `process_sys_txs` (`runner.rs:1552-1607`, `1617-1706`).
   - `remove_deposits(&deposit_data)` at line 638.
3. `process_sys_txs` builds a `SystemEvent::BridgeDeposit` tx per deposit and applies it via `apply_l2_block_txs`. If the call fails with `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful` and `is_deposit` is true, the working set is reverted and the loop simply `continue`s (`runner.rs:1682-1697`) — the deposit's tx is **not** pushed into `all_txs`, so it is never included in the produced block and no mint / `Deposit` event occurs.
4. Despite that, back in the caller, `deposit_data` (the *original, full* fetch — not filtered by which succeeded) is passed unconditionally to `remove_deposits` at `runner.rs:638`, which removes every one of those deposits from `accepted_deposit_txs`/`pending_deposits` based on `calc_tx_id` recomputed from the raw bytes (`deposit_data_mempool.rs:79-109`).

Because the *fetched* set and the *successfully-applied* set are never reconciled, any deposit that reverts during real execution — for any reason including a light-client/system state mutation that occurred between the `citrea_sendRawDepositTransaction` pending-state simulation and the actual block-production run (`set_block_info_event`s for new L1 blocks are pushed and applied ahead of `deposit_events` in the same `produce_and_run_system_transactions` call, `runner.rs:1585-1598`) — is permanently deleted from the mempool with zero mint. Existing guards (`verify_system_tx`, `EvmSystemTransactionNotSuccessful` handling) correctly prevent the malformed/failed deposit tx from being included in the block or crashing the sequencer, but they do nothing to protect the mempool bookkeeping from this batch-removal bug.

I was not able to fully verify within available context whether `BitcoinLightClientContract`'s stored block info is queryable historically by hash (which would affect how easily an attacker/observer could trigger the specific "height advances mid-cycle" precondition) — this detail is in `BitcoinLightClient.sol`, which I could not fully inspect in this session. However, the core defect — unconditional removal of the whole fetched batch regardless of per-deposit success — is independently confirmed by the code and is sufficient to break the stated binding on its own, without needing the light-client race to be the only trigger; any transient revert of `BridgeContract::deposit` at block time (e.g. a benign state race, contract pause toggling, or any other cause) reproduces the same fund-freezing outcome.

### Impact Explanation
A user whose Bitcoin move-to-vault transaction has already confirmed and whose `citrea_sendRawDepositTransaction` blob passed the pending-state `eth_call` simulation can have their deposit permanently purged from `DepositDataMempool` without any cBTC being credited, because `remove_deposits` is invoked with the full fetched batch rather than the subset that actually succeeded in `process_sys_txs`. This matches the Critical category "funds permanently frozen": the deposit's `calc_tx_id` entry is the only record tracking that this deposit needs replay, and once removed, resubmission requires the raw deposit bytes to pass simulation and execution again — which is not guaranteed and, per the report's threat model, is not something the unprivileged user (who cannot resubmit differently, since the underlying Bitcoin tx and proof are fixed) can reliably force. This is repeatable per-deposit and per-block whenever a deposit succeeds simulation but fails in the real `process_sys_txs` execution.

### Likelihood Explanation
The trigger does not require any privileged role: it only requires that at least one deposit's `BridgeContract::deposit` call, which passed `eth_call` simulation against `BlockId::pending()`, subsequently reverts when actually applied in `process_sys_txs` during the same or later block-production cycle (e.g., due to intervening `set_block_info_event`s changing light-client/system state between simulation and application, or any other legitimate revert condition on real state vs. simulated pending state). This is a timing/state race inherent to the existing two-phase simulate-then-produce design, not an exotic attack, and can occur without any adversarial action — an honest user's deposit can be silently and permanently dropped. The precise frequency depends on light-client contract internals not fully verified in this session, but the removal logic itself is unconditionally buggy regardless of cause.

### Recommendation
Change `process_sys_txs` (or its caller) to return which deposits from `deposit_data` actually succeeded (were included in `all_txs`), and pass only that successful subset to `remove_deposits` in `runner.rs:638`, instead of the full `deposit_data` fetched at the start of block production. Deposits that fail during real application should remain in `DepositDataMempool` (or be moved to a distinct retry/quarantine state) so they can be retried in a subsequent block rather than being unconditionally discarded.
