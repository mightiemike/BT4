### Title
Transaction-Triggered Chunk-Apply Panic via Stale Delayed-Receipt Re-Validation Mismatch - (File: runtime/runtime/src/lib.rs)

### Summary
`process_delayed_receipts` re-validates every receipt popped from the persistent delayed-receipt queue against the **current** `validate_receipt` limit config/protocol version before executing it. If a receipt admitted into the queue under one set of validation constraints later fails re-validation (e.g. because config-dependent limits such as `wasm_config.limit_config` fields, action/receipt size limits, or other protocol-version-gated checks changed, or because of an inconsistency between admission-time and dequeue-time validation logic), the mismatch is converted into `StorageError::StorageInconsistentState` instead of being treated as an ordinary tx/receipt failure.

### Finding Description
When a chunk cannot process all receipts within the gas/compute or storage-proof budget, unprocessed local/incoming receipts are persisted to the on-trie `DelayedReceiptQueue` (`runtime/runtime/src/lib.rs:2517-2521`, `:2707-2711`). On a later chunk, `process_delayed_receipts` pops receipts from this queue FIFO and calls `validate_receipt(&apply_state.config.wasm_config.limit_config, &receipt, protocol_version, ValidateReceiptMode::ExistingReceipt)` before executing them [1](#0-0) . Unlike incoming receipts (which are only ever admitted after passing this exact check in the *same* chunk, `runtime/runtime/src/lib.rs:2697-2703`), a delayed receipt can sit in the queue for an arbitrary number of blocks — and possibly epochs — before being popped, during which `protocol_version` advances and `apply_state.config` (including `wasm_config.limit_config`) can change via a protocol upgrade.

Any divergence between the validation rules in effect when the receipt was queued and the rules in effect when it is dequeued causes `validate_receipt` to fail, and the error path treats this purely as "state corruption" — `StorageError::StorageInconsistentState(...)` — rather than gracefully skipping or otherwise handling the receipt. This propagates up through `RuntimeError::StorageError` to `chain/chain/src/runtime/mod.rs`'s `apply_chunk`, where any `StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue` triggers `panic!("{err}")` [2](#0-1) , aborting the node process handling that shard.

This mirrors the CVE-2025-47229 bug class: two logically related code paths (receipt admission-time validation vs. receipt re-validation-on-dequeue) are expected to stay in lockstep, but nothing enforces that invariant across a protocol-version transition or config change, and the mismatch is escalated to an assertion-style fatal error rather than handled as a normal invalid-input case.

An unprivileged party can influence which receipts sit in the delayed queue by simply congesting a shard (submitting many transactions/receipts that exceed the per-chunk gas/compute limit), causing legitimate receipts they control to be pushed into the persistent delayed queue. If any subsequent protocol upgrade tightens/loosens a `wasm_config.limit_config` bound or a `ValidateReceiptMode`-relevant check in a way that a previously-valid queued receipt no longer satisfies, every validator applying that shard hits the same panic deterministically on the same block, since the delayed-receipt queue and protocol version are both part of consensus state.

### Impact Explanation
This is a transaction/receipt-triggered halt: because the queued receipt and its content are part of validated, persisted state (not attacker-controlled arbitrary corruption), and the panic fires deterministically for **every** validator applying the shard at the block where the receipt is dequeued, this can produce a synchronized chain-wide halt of chunk production for the affected shard rather than a single node crash — satisfying the "transaction-triggered halt" acceptance criterion. It requires a config/protocol-version change to actually trigger the mismatch, so likelihood depends on operational conditions, but the code path itself has no defense against it (no fallback, no `Ok`-with-error-outcome path, straight to `panic!`).

### Likelihood Explanation
Getting a receipt into the delayed queue is trivial and available to any unprivileged transaction sender (send enough traffic to a shard to exceed its per-chunk compute/storage-proof limit). Triggering the actual re-validation mismatch additionally requires a protocol-version bump or runtime-config change that alters the `validate_receipt` outcome for an already-queued receipt — something outside a single attacker's direct control but realistic across routine protocol upgrades, especially given the codebase explicitly acknowledges (in its own doc/spec) that "a delayed receipt that fails `validate_receipt` on dequeue is treated as `StorageInconsistentState`" as a known invariant, implying awareness but no mitigation for cross-version drift.

### Recommendation
- Decouple `process_delayed_receipts`'s re-validation from the panic-inducing `StorageInconsistentState` classification: if a delayed receipt fails re-validation solely due to `ValidateReceiptMode`/limit-config differences introduced by a protocol upgrade, execute it against the config/limits in effect when it was originally admitted, or explicitly define and version-gate the migration semantics.
- Alternatively, make `chain/chain/src/runtime/mod.rs::apply_chunk`'s handling of `StorageError::StorageInconsistentState` originating specifically from delayed-receipt re-validation recoverable (e.g., propagate as `Error::InvalidTransactions`/skip-and-log) instead of `panic!`, since this is reachable from ordinary chunk congestion rather than genuine storage/database corruption.
- Add a protocol-level compatibility test that pushes a receipt into the delayed queue under protocol version N, then re-applies the chunk under N+1 (varying the relevant config knobs) to ensure `validate_receipt` never regresses for previously-admitted receipts.

### Proof of Concept
1. As an unprivileged account, submit a burst of `FunctionCall`/`Transfer` transactions/receipts to a target shard sized so several receipts exceed the shard's per-chunk `compute_limit` or trigger `trie.check_proof_size_limit_exceed()`, forcing the runtime to push at least one crafted receipt into the persistent `DelayedReceiptQueue` via `runtime/runtime/src/lib.rs:2517-2521` / `:2707-2711`.
2. Wait for (or, in a controlled testnet, trigger) a protocol-version upgrade that tightens a `wasm_config.limit_config` bound relevant to `validate_receipt`'s `ValidateReceiptMode::ExistingReceipt` checks (e.g., a max action count/size limit) such that the already-queued receipt would now fail validation.
3. On the chunk where the queue is drained, `process_delayed_receipts` calls `validate_receipt` on the stale receipt, which now fails, producing `StorageError::StorageInconsistentState` (`runtime/runtime/src/lib.rs:2628-2640`).
4. This error surfaces from `Runtime::apply` as `RuntimeError::StorageError`, which `chain/chain/src/runtime/mod.rs`'s `apply_chunk` matches and `panic!`s on (lines 1296-1301), crashing every validator process applying that shard at that block height.
