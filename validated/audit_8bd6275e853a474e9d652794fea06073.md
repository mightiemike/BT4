## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` silently skips state/hot-state/position checkpoint hash validation during transaction replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
The replay/verification comparator that is supposed to confirm a locally re-executed transaction produces the *exact same* result as the authenticated, committed `TransactionInfo` deliberately omits comparing the state checkpoint hashes. This means the chunk-replay verification path used by state-sync chunk replay, backup restore replay, `db-tool replay_on_archive`, and `aptos-debugger` can report a transaction as "verified" even though the locally computed Sparse-Merkle-Tree / position-tree root diverges from the authenticated root recorded on-chain.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the function responsible for asserting that a re-executed `TransactionOutput` matches an authenticated `TransactionInfo` (the leaf value committed into the transaction accumulator and signed via `LedgerInfoWithSignatures`). It checks `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash against `event_root_hash`: [1](#0-0) 

Critically, the function's own comment admits the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is invoked from `ChunkExecutor::verify_execution`, the routine that re-executes a range of transactions through the VM and checks each output against the corresponding trusted `TransactionInfo` before the chunk is accepted for replay/apply: [3](#0-2) 

`verify_execution` is called from `remove_and_replay_epoch`, which drives `TransactionReplayer` chunk replay (used by backup restore's replay path and `db-tool`/`aptos-debugger` verification tooling): [4](#0-3) 

After `verify_execution` passes, `remove_and_apply` builds the `TransactionOutput` to actually commit **from the untrusted/backup-supplied `write_set`, `events`, and `txn_info.status/gas_used`** — not from the freshly re-executed VM output: [5](#0-4) 

That chunk is then run through `ReplayChunkVerifier`, whose `transaction_infos` field is the *same* input `TransactionInfo` list rather than an independently derived one: [6](#0-5) 

So the only place where locally-recomputed state actually gets compared against the authenticated checkpoint hash is the omitted check inside `ensure_match_transaction_info`. Because that specific comparison is skipped, a divergence between the real VM/state-tree execution result and the already-signed `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` will not be detected by this verification pass.

### Impact Explanation
This breaks the "proof/commit binding" invariant required for replay and restore correctness: locally recomputed ledger state must be proven identical to the authenticated committed state before being treated as verified. If a bug, VM/state-tree behavior change, or non-determinism causes local re-execution to produce a different world-state root than what was originally committed and signed by validators, `verify_execution`/`ensure_match_transaction_info` will not flag it — silently allowing execution/replay tooling (and the replay-based restore/verification workflow) to report success while the reconstructed local database's Merkle roots diverge from the canonical, signed ledger state. This falls squarely under "hard-fork-only divergence during commit, replay, restore, or proof verification" and "replay paths ... must not reinterpret committed data into a different ledger state," since it removes the primary local detection mechanism for exactly that class of divergence.

### Likelihood Explanation
The gap is deterministic and always present (not a subtle race): any state-root divergence introduced during replay will pass the `verify_execution` check today, 100% of the time, because the code path structurally never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. The condition for it to matter is a pre-existing divergence in the local execution result (e.g., a determinism/DB bug or a not-yet-caught consensus/VM issue) — the code comment itself acknowledges the gap is real and currently unaddressed, but notes it is currently scoped to when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled for the `position_state_checkpoint_hash` piece; the `state_checkpoint_hash`/`hot_state_checkpoint_hash` omission, however, applies unconditionally today.

### Recommendation
Extend `ensure_match_transaction_info` to also recompute the state checkpoint hash (and hot-state/position checkpoint hashes, when applicable) from the actual post-execution state and compare it against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, erroring out on mismatch exactly like the existing `state_change_hash`/`event_root_hash` checks. This should be done before any dependency on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, since the state/hot-state checkpoint hash gap already exists unconditionally.

### Proof of Concept
Not applicable as a runnable exploit — this is a code-level integrity gap proven directly from the shipped implementation and its own acknowledging comment rather than an externally triggerable attack: `ensure_match_transaction_info` at [1](#0-0)  never reads or compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, and is the sole point in the chunk-replay path (`execution/executor/src/chunk_executor/mod.rs::verify_execution` → `remove_and_apply` → `ReplayChunkVerifier`) where locally re-executed state is checked against the authenticated committed state.

**Note on confidence:** I was unable to fully trace, within the available iterations, whether the state-sync *live-commit* path (`StateSyncChunkVerifier` + `ensure_transaction_infos_match` in `execution/executor-types/src/ledger_update_output.rs`) independently re-derives and validates the checkpoint hash from freshly computed state (which would make this specifically a replay/restore-tooling issue rather than a live-consensus-commit issue). The evidence collected strongly suggests the gap is real and unconditional for the replay/restore path, but I could not verify its full downstream blast radius (e.g., whether `db-tool replay_on_archive` results are later cross-checked by a separate accumulator-proof step) within the iteration budget.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    /// Consume `end_version - begin_version` txns from the mutable input arguments
    /// It's guaranteed that there's no known broken versions or epoch endings in the range.
    fn remove_and_apply(
        &self,
        transactions: &mut Vec<Transaction>,
        persisted_aux_info: &mut Vec<PersistedAuxiliaryInfo>,
        transaction_infos: &mut Vec<TransactionInfo>,
        write_sets: &mut Vec<WriteSet>,
        event_vecs: &mut Vec<Vec<ContractEvent>>,
        begin_version: Version,
        end_version: Version,
    ) -> Result<()> {
        let num_txns = (end_version - begin_version) as usize;
        let txn_infos: Vec<_> = transaction_infos.drain(..num_txns).collect();
        let (transactions, persisted_aux_info, transaction_outputs) = multizip((
            transactions.drain(..num_txns),
            persisted_aux_info.drain(..num_txns),
            txn_infos.iter(),
            write_sets.drain(..num_txns),
            event_vecs.drain(..num_txns),
        ))
        .map(|(txn, persisted_aux_info, txn_info, write_set, events)| {
            (
                txn,
                persisted_aux_info,
                TransactionOutput::new(
                    write_set,
                    events,
                    txn_info.gas_used(),
                    TransactionStatus::Keep(txn_info.status().clone()),
                    TransactionAuxiliaryData::default(), // No auxiliary data if transaction is not executed through VM
                ),
            )
        })
        .multiunzip();
