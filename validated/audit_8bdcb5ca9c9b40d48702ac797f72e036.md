### Title
Unrestricted Bootstrap-Declare Bypass Allows Fee-Free, Validation-Free, Nonce-Free Repeated Declares - (File: `crates/blockifier/src/transaction/account_transaction.rs`)

### Summary
The bootstrap-declare special case in `AccountTransaction::execute_raw` skips validation, fee charging, and nonce enforcement for any `Declare` transaction whose sender address equals a hard-coded constant (`bootstrap_address()`), whose nonce is `0`, and whose `charge_fee` execution flag is `false`. There is no additional guard restricting this path to genesis/bootstrap conditions (e.g. block height, one-time system flag, or gateway-level check), so any unprivileged transaction sender who can construct a `Declare` transaction with `sender_address = BOOTSTRAP`, `nonce = 0`, and resource bounds that make `charge_fee == false` can repeatedly (once per distinct class) declare classes for free, without going through account validation or nonce/fee accounting.

### Finding Description
`DeclareTransaction::is_bootstrap_declare()` defines the bypass condition purely from transaction-supplied fields: [1](#0-0) 

`AccountTransaction::execute_raw` checks this condition and, if true, skips `perform_pre_validation_stage` (nonce check/increment, fee checks) entirely and never invokes account `__validate__`, going straight to `run_execute` of the declare, then returns a default (empty, no fee) `TransactionExecutionInfo`: [2](#0-1) 

The only external checks performed on a declare transaction before it reaches execution are the gateway's `check_declare_permissions`, which only enforces the global `block_declare` toggle and an optional `authorized_declarer_accounts` allow-list — neither of which is bootstrap-aware: [3](#0-2) 

By default `authorized_declarer_accounts` is `None` (no restriction), so any sender address, including the fixed bootstrap constant, passes this check: [4](#0-3) 

Because the nonce is never incremented for the bootstrap declare path (the pre-validation stage that performs `check_and_increment_nonce` is skipped entirely), the "bootstrap account" nonce state remains `0` after every execution. An attacker can therefore submit a new `Declare` transaction with the same `sender_address = BOOTSTRAP`, `nonce = 0`, and a distinct, never-before-declared class hash in every subsequent block, each time bypassing the account's `__validate_declare__`, fee payment, and nonce enforcement. The per-class uniqueness assertion in the Starknet OS Cairo counterpart (`assert_not_zero`/`dict_update` requiring `prev_value=0`) only prevents re-declaring the *same* class hash twice — it does not prevent unlimited free declares of *different* classes via this path: [5](#0-4) 

This mirrors the reported bug class: a special mode meant to be gated/limited to a specific intended state (there: "lock toggled off"; here: "genesis bootstrap only") is instead reachable unconditionally by any caller who satisfies attacker-controlled transaction fields, defeating the intended restriction.

### Impact Explanation
An unprivileged transaction sender can repeatedly submit `Declare` transactions that:
- Bypass account `__validate_declare__` entirely (no signature/authorization check tied to any real account),
- Bypass fee charging (no STRK/ETH is collected for compilation, storage, or execution resources consumed),
- Bypass nonce accounting (the "account" never accrues nonce, so the exploit is repeatable indefinitely, once per distinct class hash).

Each exploitation forces the sequencer to perform Sierra→CASM compilation (a CPU/memory-intensive, rate-limited resource per `GatewayStaticConfig::max_concurrent_declare_compilations`) and to persist a new class in state, all for free. This is an unauthorized (fee-free, validation-free) declare action and a mechanism for uncompensated resource consumption of sequencer/compiler capacity — a concrete violation of the fee/resource-accounting invariant the sequencer is supposed to enforce on every account transaction.

### Likelihood Explanation
The path is reachable directly from the gateway's declare submission entry point with a single crafted transaction; no privileged role, node compromise, or malicious peer is required. The `authorized_declarer_accounts` allow-list is `None` (disabled) by default, and `block_declare` is a global kill-switch unrelated to this specific bypass, so a default-configured deployment is exposed. The main attacker requirement is constructing resource bounds/fee parameters that make `charge_fee == false` for a V3 declare with `nonce == 0` and `sender_address == bootstrap_address()`; both are transaction fields fully controlled by the sender.

### Recommendation
Restrict `is_bootstrap_declare` (or its invocation in `execute_raw`) to a genuinely one-time/genesis condition that cannot be satisfied by ordinary transactions after network bootstrap — e.g., gate it on block number 0 (only the very first block may contain bootstrap declares), or track explicit on-chain/state flag that is cleared after the first bootstrap declare is executed, in addition to the current sender/nonce/charge_fee checks in `crates/starknet_api/src/executable_transaction.rs` and `crates/blockifier/src/transaction/account_transaction.rs`.

### Proof of Concept
1. Craft an RPC `Declare` (V3) transaction with `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`), `nonce = 0`, and resource bounds/tip chosen so that `max_possible_fee == 0` (yielding `charge_fee == false` per `is_bootstrap_declare`), targeting any not-yet-declared class.
2. Submit via the gateway; `check_declare_permissions` passes by default (no `authorized_declarer_accounts` restriction).
3. In `AccountTransaction::execute_raw`, `is_bootstrap_declare` evaluates true, so `perform_pre_validation_stage` (nonce/fee checks) and account `__validate_declare__` are both skipped, and the class is declared at zero cost.
4. Because nonce was never incremented, repeat step 1 with a different, never-declared class hash in subsequent blocks to declare unlimited classes for free. [6](#0-5) [7](#0-6)

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }

        // Note: The absence of any account-related action leads to some unintuitive but expected

        // - After the transaction is executed successfully, the batcher does not notify the mempool

        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
