### Title
Denial of service on `MarketSellAssetContract` matching via maker order-book flooding that forces "Too many matches" reverts - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchOrder` iterates the maker order book for a token pair and hard-reverts the entire taker transaction with `ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM)` if a taker's order needs to consume more than `MAX_MATCH_NUM` (20) maker orders during matching. [1](#0-0)  An unprivileged attacker can broadcast many cheap `MarketSellAssetContract` orders at closely spaced prices for a target pair (only requiring `getMarketSellFee()` and a minimal token balance per order) to permanently pollute that pair's order book. Any subsequent legitimate order that would need to match across more than 20 of these small orders is forced to revert, effectively DoS-ing on-chain exchange settlement for that pair — conceptually analogous to the CowSwap report where a cheap, repeatable action keeps a shared state "active"/unmatchable and blocks legitimate operations that share the same guarded code path.

### Finding Description
`matchOrder` walks price levels and, for each price level, walks the linked list of maker orders (`orderIdListCapsule`), calling `matchSingleOrder` for each one and incrementing `matchOrderCount`. [2](#0-1)  If `matchOrderCount` exceeds the static `MAX_MATCH_NUM = 20` limit, it throws `ContractValidateException`, which is caught in `execute()` and rethrown as `ContractExeException`, failing the whole transaction. [3](#0-2) 

This limit exists to bound gas/energy work per transaction, but it creates an exploitable griefing surface: an attacker can seed the order book for a specific `(sellTokenID, buyTokenID)` pair with more than `MAX_MATCH_NUM` small maker orders (e.g., 21+ orders of minimal quantity at slightly different prices, cheaply affordable since the fee is `dynamicStore.getMarketSellFee()` and asset amounts can be tiny). [4](#0-3)  This is confirmed as an intentional and reachable code path by the existing unit test `exceedMaxMatchNumLimit`, which demonstrates exactly this scenario: adding `MAX_MATCH_NUM + 1` maker orders causes a legitimate taker order to fail with "Too many matches." [5](#0-4) 

Because these maker orders remain in the order book (they are only removed when fully consumed or explicitly canceled via `MarketCancelOrderActuator`, which requires the order owner's signature [6](#0-5) ), any taker whose order size would require matching through more than 20 of them is permanently blocked from trading against that pair until the attacker chooses to cancel — mirroring the report's core bug class: a cheap, repeatable, unprivileged action that keeps guarded state in a condition that forces reverts for all other participants attempting to use the same shared mechanism (here, the on-chain order-matching path for a token pair, rather than a `sync` modifier).

### Impact Explanation
This is a concrete DoS via the protocol's exchange/market actuator reachable from any anonymous broadcast transaction — no privileged role is required. Legitimate takers attempting to sell/buy against a targeted pair repeatedly waste transaction fees/energy on reverted transactions, and the market for that pair becomes practically unusable while the attacker's small orders remain queued. In a market with time-sensitive or price-moving intent (analogous to the Dutch-auction incentive in the original report), an attacker can use this to block competing trades in a specific pair for as long as they maintain the flooding orders, at a cost proportional only to `getMarketSellFee()` times the number of maker orders needed (just over `MAX_MATCH_NUM`).

### Likelihood Explanation
Likelihood is high: the attack requires only standard `MarketSellAssetContract` transactions (unprivileged), a modest amount of TRX/tokens, and knowledge of `MAX_MATCH_NUM` (a public constant, `20`, exposed via `MarketSellAssetActuator.getMAX_MATCH_NUM()`). The behavior is already demonstrated to be deterministic and reproducible by the existing test suite. [7](#0-6) 

### Recommendation
- Do not hard-revert the entire taker transaction when the match-count cap is reached; instead partially fill up to `MAX_MATCH_NUM` and place the remainder back into the order book (similar to how partial fills are already handled elsewhere in `matchSingleOrder`), so an attacker cannot force full transaction failure merely by order-count flooding.
- Consider a minimum order size/price-tick granularity or a fee-per-matched-order model so that flooding the book with many tiny orders becomes economically costly relative to the disruption caused.
- Add rate limits or minimum quantities per new order relative to the existing book depth for a given pair to prevent unbounded queuing of trivial orders.
- Alternatively, allow `MAX_MATCH_NUM` to be configured/increased by chain parameters, and add a "matched-so-far" partial settlement path returned to the caller instead of throwing, converting a hard failure into a partial success.

### Proof of Concept
1. Attacker broadcasts `MAX_MATCH_NUM + 1` (21) `MarketSellAssetContract` transactions selling a minimal quantity of `tokenB` for `tokenA` at slightly increasing prices, each paying `dynamicStore.getMarketSellFee()`. This is exactly what the existing test `exceedMaxMatchNumLimit` sets up. [8](#0-7) 
2. A victim then broadcasts a `MarketSellAssetContract` selling `tokenA` for `tokenB` with a quantity large enough that the matching engine must walk through more than 20 of the attacker's maker orders.
3. `matchOrder`/`matchSingleOrder` increments `matchOrderCount` past `MAX_MATCH_NUM`, and `execute()` throws `ContractExeException` with message `"Too many matches. MAX_MATCH_NUM = 20"`, failing the victim's transaction. [9](#0-8) 
4. As long as the attacker's orders remain unfilled/uncanceled in the book, any similarly sized victim transaction against that pair will continue to fail in the same way, denying service to that market.

Note: I was unable to fully verify from the index whether `ContractExeException` thrown mid-`execute()` (after fee deduction and token transfer already occurred in-memory) results in those partial state changes being rolled back at the `Manager`/session level, or whether fee could be partially consumed on failure; the exact settlement-session behavior for actuator-level exceptions was not confirmed in `TransactionTrace.java` within the indexed content. Confirming this would require inspecting `TransactionTrace.exec()`/`RuntimeImpl` directly in a full checkout, since the index did not return matches for exception-handling code in that file.

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
