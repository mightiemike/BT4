## Title
Postponed/PromiseYield receipt tracking rows for an account are never cleaned up on `DeleteAccount`, allowing stale cross-contract-call state to execute against (or lock funds intended for) a re-created account after deletion - (File: `core/store/src/utils/mod.rs`)

## Summary
`action_delete_account` (`runtime/runtime/src/actions.rs`) lets an account owner (via a `FullAccess` key or a self-issued `Promise::batch` `DeleteAccount` action, i.e. an ordinary unprivileged transaction signer) delete their account at any time, refunding its balance to a beneficiary and calling `remove_account`. `remove_account` only removes the `Account`, `ContractCode`, `AccessKey`/gas-key nonce, and `ContractData` trie entries for that `account_id`; it does not remove `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, or `PromiseYieldStatus` entries keyed by that same `account_id`. If the account had outstanding cross-contract calls (postponed action receipts awaiting `DataReceipt`s, or `promise_yield_create`d promises awaiting `promise_yield_resume`) at the moment of deletion, those entries remain in the trie under the now-deleted account id, ownerless.

## Finding Description
An account accumulates receiver-side bookkeeping any time it issues a cross-contract call whose callback has unmet `input_data_ids`, or calls `promise_yield_create`:
- `process_action_receipt` (`runtime/runtime/src/lib.rs:1647-1712`) stores `PostponedReceiptId{receiver_id, data_id}`, `PendingDataCount{receiver_id, receipt_id}` and the full `PostponedReceipt{receiver_id, receipt_id}` when not all `input_data_ids` are present yet. [1](#0-0) 
- `process_receipt` for `PromiseYield` simply stores the receipt under `PromiseYieldReceipt{receiver_id, data_id}` awaiting `PromiseResume`. [2](#0-1) 

None of these rows are indexed by, or reachable from, the `Account` trie entry — they are independent columns keyed by `(receiver_id, data_id/receipt_id)` (`core/primitives/src/trie_key.rs:203-234`, `PROMISE_YIELD_RECEIPT`/`PROMISE_YIELD_STATUS` in the same file). [3](#0-2) 

`action_delete_account` computes storage usage only from the `Account`'s own `storage_usage` field (contract code, access keys, contract data) and gas-key balances; it never inspects postponed-receipt or promise-yield bookkeeping before allowing deletion: [4](#0-3) 

`remove_account` performs the actual cleanup, but only iterates/removes `Account`, `ContractCode`, access-key/gas-key-nonce entries (via prefix scan) and `ContractData` (via prefix scan). It has no code path for `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, or `PromiseYieldStatus`: [5](#0-4) 

Consequently, an account can delete itself while it still has:
1. A postponed action receipt awaiting a `DataReceipt` from another (still-running) contract call it initiated, or
2. A parked `PromiseYield` receipt awaiting `promise_yield_resume`.

Because `AccountId`s are permissionlessly re-creatable after deletion (subject to the normal `CreateAccount`/implicit-account rules in `action_create_account`, `runtime/runtime/src/actions.rs:166-209`), a completely different party can later create a new account under the same id. When the originally-awaited `Data`/`PromiseResume` receipt eventually arrives, `process_receipt` looks it up purely by `receiver_id` (the account id) — with no check that the account still exists or is still owned by the same logical entity — decrements the still-present `PendingDataCount`, and once it hits zero, fetches and executes the stale `PostponedReceipt`/`PromiseYield` receipt via `apply_action_receipt` against whatever account now sits at that id: [6](#0-5) 

This is structurally the same defect class as the Remora report: a deletion path (`DeleteAccount`/`_removePayoutForwardAddress`) is gated only on a narrow, easily-drained predicate (account balance / `isHolder` in Remora; local `Account.storage_usage`/gas-key balance in nearcore) while ignoring other outstanding shared/aggregated state (`calculatedPayout` in Remora; postponed-receipt/promise-yield bookkeeping in nearcore) that still belongs to, or was funded/authorized by, other parties (other holders in Remora; the original callers of the pending cross-contract call in nearcore). Deleting the object silently orphans that state instead of resolving or refunding it.

## Impact Explanation
- If the account id is never re-created, the pending `DataReceipt`/`PromiseResume` for it eventually arrives and triggers execution of a postponed `ActionReceipt` whose receiver account is `None`. Any deposit/transfer actions in that stale receipt cannot land on an existing account, and the receipt's original attached deposit (already debited from the sending predecessor at receipt-creation time) is essentially orphaned/unresolved bookkeeping tied to a deleted account — a form of stuck/frozen value and permanent trie-row leakage that can never be pruned by normal execution.
- If the account id *is* re-created (a very plausible and cheap action for named sub-accounts or implicit accounts), the stale postponed/yield receipt will later fire against the new, unrelated account owner: actions such as `Transfer`, `FunctionCall` with a deposit, or `AddKey` execute using state/authorization context that belonged to the old, already-deleted owner, producing unauthorized value movement and non-deterministic-looking side effects on an account the original caller no longer controls.
- Either way this is a genuine invalid state transition acceptance / potential permanent fund freeze bug reachable purely by an ordinary unprivileged transaction signer deleting their own account while a cross-contract callback or `promise_yield` is in flight — no validator, network, or operator privilege is required.

## Likelihood Explanation
Reachability requires only: (1) issuing a batched cross-contract call or `promise_yield_create` from account A so that A becomes the receiver of a postponed/yielded callback, and (2) sending a `DeleteAccount` action for A (e.g., via `Promise::batch` self-delete, exactly as exercised by the existing `test_instant_delete_account` test) before the callback resolves. Both are ordinary, permissionless actions available to any signer/contract; no timing races with other validators or special protocol knowledge are needed, only ordinary control over when to issue the delete relative to the pending callback. `action_delete_account`'s checks (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`, gas-key balance) never examine postponed/yield state, so nothing currently blocks this sequence. [7](#0-6) 

## Recommendation
Before permitting `DeleteAccount` to actually remove the account (or as part of `remove_account`), check for and reject deletion (or explicitly resolve/refund) any outstanding `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` and `PromiseYieldReceipt`/`PromiseYieldStatus` entries keyed by that `account_id`. At minimum, `remove_account` should prefix-scan and purge these columns the same way it already does for `ContractData` and access keys, and any pending deposits associated with orphaned postponed receipts should be refunded to their original predecessors rather than silently left to resolve against whatever account subsequently occupies that id.

## Proof of Concept
Conceptual reproduction (matches the pattern already exercised by `test_instant_delete_account` in `test-loop-tests/src/tests/create_delete_account.rs`):
1. Deploy a contract to account `A`. From `A`, issue a cross-contract call chain such that `A` becomes the receiver of a batched action receipt with an unmet `input_data_id` (e.g. `Promise::then` on a call to a slow/never-resolving contract `B`), so `process_action_receipt` stores `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` for `A`.
2. In the same or a subsequent block, have `A` call `Promise::batch_create(A).action_delete_account(beneficiary)` — the same instant-delete path validated by `test_instant_delete_account`.
3. Verify via `state-viewer`/direct trie inspection that `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows for `account_id = A` still exist in the trie after the account is gone.
4. Re-create an account named `A` (owned by a different key) via a normal `CreateAccount` action.
5. Let contract `B`'s deferred `DataReceipt` finally arrive; observe that `process_receipt`/`apply_action_receipt` executes the stale postponed receipt against the new `A`, or (if `A` is never re-created) that the entries remain permanently in state with no execution path to clean them up.

This exact end-to-end flow (steps 3-5) was not directly located in the indexed test files during this scan; existing tests only cover the deletion side (`test_instant_delete_account`) and the promise-yield timeout/resume side (`test-loop-tests/src/tests/yield_timeouts.rs`) separately, not their interaction with `DeleteAccount`. A background Devin session with full repository/test-execution access would be needed to write and run the combined regression test and confirm the exact runtime behavior (panic vs. silent execution vs. `StorageInconsistentState`) when the postponed/yield receipt resolves against a missing or re-created account.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

pub struct RemoveAccountResult {
    pub gas_key_nonce_count: usize,
    pub gas_key_nonce_total_key_bytes: usize, // used to calculate compute cost
}

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
