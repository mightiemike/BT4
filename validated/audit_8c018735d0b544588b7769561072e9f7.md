Based on my investigation, I traced this to a genuine, locally-confirmed gap in Aptos's replay-verification tooling.

### Title
Replay-verify tooling (`VerifyExecutionMode::Verify`) accepts a re-executed chunk whose state-checkpoint (SMT/state root) hash diverges from the trusted backup `TransactionInfo` - (File: `types/src/transaction/mod.rs`, `execution/executor/src/chunk_executor/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function used by the chunk-replayer's independent re-execution check — validates only `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash` against the trusted `TransactionInfo`. It explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as documented by the code's own TODO. This function is the sole correctness gate in `ChunkExecutorInner::verify_execution`, which backs `db-tool`'s `replay-verify`/`replay-on-archive` and `backup-cli`'s `TransactionReplayer` "verify execution" mode — the tools operators use to detect execution/state divergence when replaying historical, execution-authenticated transaction backups.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` checks status, gas, write-set hash, and event root hash against the given `TransactionInfo`, but its own comment states:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is invoked from `ChunkExecutorInner::verify_execution`: [2](#0-1) 

which is reached via `TransactionReplayer::enqueue_chunks` → `remove_and_replay_epoch` → `verify_execution`, invoked when `VerifyExecutionMode::Verify` is used, e.g. from `storage/db-tool/src/replay_verify.rs` and `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`.

Separately, the *actual commit path* (`ChunkExecutorInner::update_ledger`, live execution/state-sync) does properly check the computed state-checkpoint hash against the known `TransactionInfo.state_checkpoint_hash()` via `DoStateCheckpoint::run().maybe_known_state_checkpoints(...)`: [3](#0-2) 

So live consensus/state-sync commits remain protected. The gap is isolated to the **independent re-execution verification path** used by archival/replay-verify tooling, which is designed specifically to catch execution non-determinism, VM bugs, or storage-layer state corruption over historical data by re-deriving state from scratch and comparing to the trusted backup.

### Impact Explanation
The write-set hash (`state_change_hash`) check alone does not guarantee the accumulated state tree (checkpoint) is correct: `state_checkpoint_hash` is derived by merging multiple per-transaction write sets into the SMT/JMT at chunk/block boundaries, including hot-state promotion and (per the second flagged term) native "trading" position-state roots. A bug in state merge logic, hot-state key promotion, or the position-state tree (all called out in the same file as newly added, less-battle-tested `trading-native` machinery) could produce a wrong final state root while each individual per-txn write set still hashes identically. Replay-verify would report success despite committing a divergent ledger state — undermining the primary safety mechanism operators rely on to catch hard-fork-class divergence during backup replay/restore. This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category.

### Likelihood Explanation
Moderate-to-low likelihood of exploitation by an external attacker (this isn't attacker-triggered on live consensus), but it silently degrades a security control that is specifically meant to catch execution/state bugs on archival replay. Given the code explicitly acknowledges the gap as a known TODO (not yet remediated), and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a newer feature path, the risk is realistic once that feature is enabled and any state-merge bug exists in that newer code.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when available/known) between the freshly re-executed output and the trusted `TransactionInfo`, consistent with the already-documented TODO, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in replay-verify tooling.

### Proof of Concept
1. Take a historical transaction chunk plus its trusted `TransactionInfo` backup (with correct `state_checkpoint_hash`).
2. Run `db-tool replay-verify` / `backup-cli` transaction restore with `--verify-execution-mode` verify-all.
3. Have local execution reconstruct write-sets whose per-transaction `state_change_hash`/`event_root_hash`/status/gas all match, but where the SMT merge (state checkpoint) diverges (e.g., a hot-state promotion bug or double-application bug affecting only the aggregated state root, not the individual write op hash).
4. `verify_execution` → `ensure_match_transaction_info` passes because it never inspects `state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash` — the tool reports the replay as verified even though the resulting state root is wrong. [4](#0-3)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
