### Title
Transaction-triggered node-wide chunk-processing halt via `.unwrap()` panic in `receipt_filter_fn` on stale `GlobalContractDistribution` receipts across multiple reshardings - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `Receipt::receiver_shard_id(&shard_layout).unwrap()` while popping receipts from the delayed queue. `receiver_shard_id` returns `Err(EpochError::ShardingError(...))` for a `GlobalContractDistribution` receipt whose `target_shard()` cannot be resolved to any shard in the current layout or its split history. This is deterministically reachable by a normal contract deployer who deploys a global contract right before a shard hosting it is resharded twice in succession while the resulting distribution receipt is kept in the delayed queue (e.g., via compute-budget saturation), causing every honest validator/chunk-producer processing that shard to panic identically when draining the delayed queue.

### Finding Description
`Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) handles `GlobalContractDistribution` receipts specially: if the receipt's stored `target_shard` is not part of the current shard layout, it calls `shard_layout.resolve_to_current_shard(target_shard)`, and if that also fails, it returns an `Err(EpochError::ShardingError(...))` — an explicit, reachable error path, not a defensive-only branch. [1](#0-0) 

However, the only caller inside the delayed-receipt draining path, `receipt_filter_fn`, discards this `Result` with `.unwrap()`: [2](#0-1) 

This function is invoked from `DelayedReceiptQueueWrapper::pop` (used every time a delayed receipt is dequeued during normal chunk processing) and from `peek_iter`: [3](#0-2) 

`resolve_to_current_shard` can only trace a shard's ancestry through its own split history; a `GlobalContractDistribution` receipt that stays parked in the delayed queue across **two or more** consecutive resharding events on the same shard can end up carrying a `target_shard` value that is no longer resolvable in the current layout, triggering the `Err` branch and thus the `.unwrap()` panic. This exact scenario — deploy a global contract, saturate the shard's compute budget every block so the resulting `GlobalContractDistribution` receipt is pushed to (and stays in) the delayed queue, force two sequential shard splits on that shard, then stop saturating so the queue drains — is codified as a regression scenario in the repository's own test suite: [4](#0-3) [5](#0-4) 

The test's own comments state plainly: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations," and the assertion is that the chain does not stall (`head_height >= drain_end`) — i.e., this is precisely testing for the described panic. [6](#0-5) 

This is not a hypothetical dependency bug or malicious-validator scenario: any unprivileged account can submit `DeployGlobalContract` and ordinary `FunctionCall` transactions to a shard; if dynamic resharding is configured (a legitimate, protocol-supported feature) and splits the same shard twice while the distribution receipt is delayed, the panic fires deterministically for every node applying that shard's chunks — an unrecoverable chain halt requiring binary/manual intervention, matching the CVE's "hang / repeatable crash / complete DoS" bug class.

### Impact Explanation
A panic inside `Runtime::apply` on a chunk-producing/validating node is not gracefully handled: the surrounding `chain/chain/src/runtime/mod.rs` apply wrapper only intercepts specific `RuntimeError` variants and even explicitly re-panics on some (`RuntimeError::UnexpectedIntegerOverflow` → `panic!`, `RuntimeError::ReceiptValidationError` → `panic!`), showing the codebase's general posture that "should never happen" runtime paths are allowed to crash the process rather than degrade gracefully. [7](#0-6) 
Because the deterministic delayed-receipt draining logic runs identically on every honest node tracking the affected shard, the panic is not isolated to a single node: all chunk producers/validators for that shard hit it at the same block height, producing a synchronized, network-wide halt of chunk production for that shard until the queue can be manually purged or a protocol fix is deployed. This satisfies the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Exploitation requires: (1) an unprivileged account deploying a global contract (a standard, permissionless action), (2) enough compute-budget saturation to keep the resulting delayed receipt parked (achievable by any account submitting expensive `FunctionCall` transactions each block — also permissionless), and (3) two shard splits occurring on the same shard while the receipt is delayed. Item (3) depends on the network's resharding configuration/cadence (a chain-operator/protocol decision, not attacker-controlled), which lowers immediate likelihood on networks with infrequent or non-consecutive resharding of the same shard, but the underlying code defect (`.unwrap()` on a documented `Err` path) is unconditional and will fire whenever the precondition is met — including via crafted resharding schedules on test/permissioned networks or in future mainnet resharding waves that repeatedly split popular/hot shards.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation: change its signature to return `Result<bool, RuntimeError>` (or equivalent), propagate `EpochError` from `receiver_shard_id`/`shard_layout` lookups as a `RuntimeError`, and update `pop`/`peek_iter` callers to surface this as a normal, recoverable `RuntimeError` (e.g., mapped to `StorageInconsistentState` handling already used elsewhere for similar "should not happen post-resharding" conditions) instead of allowing the underlying panic to propagate into `Runtime::apply`.

### Proof of Concept
The repository's own test provides a concrete, runnable reproduction: [8](#0-7) 
Steps: (1) deploy a test contract and then a global contract from `user0` on shard `S_A` (its `GlobalContractDistribution` receipt targets `S_A`); (2) each block, submit 3 `burn_gas_raw` calls that each burn slightly over half the gas limit so the chunk's compute budget is saturated and the distribution receipt is pushed to / kept in the delayed queue; (3) configure dynamic resharding to force-split `S_A` and then split it again in the following epoch (`force_split_shards: [first_split_shard, second_split_shard]`); (4) once both splits complete, stop saturating and let the delayed queue drain — at this point `receipt_filter_fn` calls `receiver_shard_id` on the now-doubly-stale receipt, which returns `Err(EpochError::ShardingError(...))`, and the `.unwrap()` panics, stalling chain progress (asserted by `head_height >= drain_end` failing if the bug is present).

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
