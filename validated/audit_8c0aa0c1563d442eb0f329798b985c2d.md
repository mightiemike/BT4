### Title
Webhook shop-domain binding is not covered by HMAC signature, allowing cross-shop request forgery in `authenticate.webhook` - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`shopify-app-js`'s webhook validation only authenticates the raw request **body** against the shared secret; the `X-Shopify-Shop-Domain` (and topic/webhook-id) headers that determine *which shop* the webhook context is bound to are never included in the HMAC computation. Because the resulting `domain` is then used, unverified, to load that shop's offline session and construct an authenticated `admin` client, an attacker who can obtain one valid `(body, hmac)` pair for a topic (e.g. by triggering that webhook on their own store, where they fully control the app-installation lifecycle) can replay it with a forged `X-Shopify-Shop-Domain` header pointing at a different, victim shop where the app is also installed. This is the same bug class as the referenced report: an operation intended to be scoped to "your own account" can be triggered by an unrelated party against someone else's account, because the binding between "who is allowed to trigger this" and "whose data it acts on" is missing.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC purely from `rawBody`: [1](#0-0) 

The domain/topic/webhook-id used everywhere downstream come from headers that are read separately in `validateFactory` and are **not part of what gets hashed**: [2](#0-1) 

`checkWebhookHeaders` (called after HMAC succeeds) simply extracts `domain` from the request headers with no cryptographic link to the body that was just validated.

In the app framework layers, `authenticateWebhookFactory` takes `check.domain` — the unauthenticated header value — and uses it directly to look up and construct a session/admin client for that shop: [3](#0-2) [4](#0-3) 

Because the HMAC is a function of `rawBody` alone, **any two requests with the same body produce the same valid signature regardless of which shop domain header accompanies them**. An attacker who controls a shop with the app installed can:
1. Trigger a webhook topic on their own shop (e.g. `APP_UNINSTALLED`) to legitimately receive a `(body, X-Shopify-Hmac-Sha256)` pair signed by Shopify with the app's shared secret.
2. Replay that exact body and HMAC to the app's webhook endpoint, but swap `X-Shopify-Shop-Domain` (and matching `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to a victim shop domain where the same app is also installed.
3. `validateHmacFromRequestFactory` still succeeds (body signature matches), and the app's webhook handler runs with `shop = <victim domain>`, `session = <victim's offline session>`, `admin = <victim's authenticated Admin API client>`.

This lets the attacker force topic-specific side effects (e.g. app-uninstall cleanup, credential/session invalidation, or any app-specific business logic keyed by webhook topic) to execute against the victim shop's session/data — a cross-tenant action the attacker has no legitimate right to trigger, directly analogous to the referenced report where an unpermissioned "claim for others" call let one user force an adverse outcome onto another account.

### Impact Explanation
An attacker who has (or creates) any shop with the target app installed can forge the shop-domain binding of a webhook delivery and cause the app to execute topic-specific logic (session deletion, data resync, uninstall cleanup, or any custom `afterAuth`/webhook handler behavior) against an arbitrary **other** merchant's session, without that merchant's involvement. Depending on what the app's webhook handlers do (many delete/rotate the shop's stored access token or purge shop data on `APP_UNINSTALLED`), this can cause denial of service or data loss for a shop that never sent the request, and the admin/storefront clients returned by `authenticate.webhook` for the victim's session could be used by application code as if the victim legitimately made the request.

### Likelihood Explanation
Exploitability depends on (a) the attacker being able to obtain a valid `(body, hmac)` pair — trivially possible by installing the app on any store they control and triggering a webhook topic whose body is static/predictable (e.g., empty or template-shaped payloads), and (b) knowledge of a victim shop domain where the app is installed, which is often guessable/public (`*.myshopify.com`). No secrets need to be leaked and no privileged access is required — this is reachable from a fully anonymous HTTP POST to the app's public webhook endpoint. This raises the likelihood to moderate-to-high for apps whose webhook bodies are low-entropy or attacker-influenceable.

### Recommendation
Bind the shop identity cryptographically to the signed payload rather than trusting the `X-Shopify-Shop-Domain` header independently of the HMAC:
- Include the shop domain (and ideally topic/webhook-id) in the HMAC input, or
- Cross-check the shop domain embedded in the JSON body (where Shopify includes shop-identifying fields) against the header value and reject mismatches, or
- Require that `check.domain` match a shop that has a pre-existing offline session created via the app's own OAuth/install flow *and* additionally verify the request originated from Shopify's known IP ranges/mTLS if available, as defense in depth.
At minimum, document/flag that consumers of `authenticate.webhook`'s `domain`/`shop` field must not treat it as fully trusted unless the HMAC computation is extended to cover it.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook topic with a static/predictable body, e.g. `APP_UNINSTALLED`, and capture the raw body `B` and the resulting `X-Shopify-Hmac-Sha256: H` sent by Shopify (valid because `H = HMAC_SHA256(secret, B)`).
3. Send a POST to the app's `/webhooks` endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop the app is also installed on), and any required `X-Shopify-Topic`/`X-Shopify-Webhook-Id`/`X-Shopify-Api-Version` headers matching topic `B` corresponds to.
4. `validateHmacFromRequestFactory` returns `valid: true` because only `B` and `H` are checked [5](#0-4) .
5. `authenticate.webhook` resolves `shop = victim.myshopify.com`, loads victim's offline session, and invokes the app's `APP_UNINSTALLED`-topic side effects against the victim shop [6](#0-5) .

**Uncertainty/limitations:** I was not able to fully verify, from the indexed codebase alone, the exact byte-level content of real Shopify webhook payloads for every topic (some topics may embed the shop's own domain/id inside the JSON body, which — if consuming application code cross-checks it — would mitigate this for those specific topics). The core library-level gap (HMAC not covering the domain header) is confirmed directly from source, but end-to-end exploitability for a specific topic depends on that topic's payload shape and on what the consuming app's webhook handler does with `shop`/`session`, which is app-specific and outside this repo's control.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
