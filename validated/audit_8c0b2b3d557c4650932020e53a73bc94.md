### Title
Repeated `socialize-debt` bad-debt write-downs collapse the vault's exchange rate, letting a later `deposit` mint disproportionate shares and drive `total-supply` toward permanent overflow/freeze - ([File: mainnet/contracts/vault/v0-vault-stx.clar] and equivalent per-asset vaults)

### Summary
Each `v0-vault-*.clar` vault prices shares via `convert-to-shares-preview`, which divides a deposit amount by the ratio `total-assets-preview / total-supply-preview` [1](#0-0) . `socialize-debt` reduces the raw `assets` variable (and `total-borrowed`/`principal-scaled`) to absorb protocol bad debt, but it never burns any `zft` shares [2](#0-1) . This is the same "value removed from the backing pool without a corresponding share burn" pattern described in the Carapace M-7 report: the accounting variable that determines the exchange rate is mutated by one operation, and a later, unrelated `deposit` call reuses the resulting collapsed ratio to mint shares, without either operation re-checking that the ratio is still sane.

### Finding Description
`convert-to-shares-preview` computes `shares = amount * total-supply-preview / total-assets-preview` [1](#0-0) . `total-assets-preview` is `assets + max(debt-preview - total-borrowed, 0)` [3](#0-2) .

`socialize-debt` write-downs directly subtract `principal-reduction` from `assets` (and `principal-scaled`/`total-borrowed` in lockstep) to reflect a bad-debt loss, while leaving `total-supply` (the `zft` fungible token supply) completely unchanged [2](#0-1) . This is intentional loss-socialization: existing shareholders' claim per share should shrink. However, if `assets` is driven down close to a dust amount relative to `total-supply` (e.g., repeated bad-debt events across the vault's lifetime, each one leaving a small `assets` remainder), the exchange rate `total-assets-preview / total-supply-preview` collapses toward a very small ratio.

The very next unrelated `deposit` call then computes `inkind = amount * ts / ta` with a near-zero `ta` [4](#0-3) , which can multiply `total-supply` by many orders of magnitude in a single call (analogous to Carapace's "next deposits for 1M USDC multiply totalSupply by 10^12" scenario). Because Clarity's `uint` is a fixed 128-bit type (`MAX-U128` is defined as a constant in the same contract) [5](#0-4) , repeating this socialize-debt → deposit cycle a handful of times can push `(* amount ts)` inside `mul-div-down` past `u128` max, causing every subsequent `deposit`/`redeem` call to abort. There is no mechanism that rebases the token, caps the growth of `total-supply`, or re-derives a sane floor for `total-assets-preview` before it is consumed by the next `deposit`.

This is a single-block-reachable multi-step defect: `socialize-debt` mutates the state that backs the exchange-rate calculation, and the very next transaction's `deposit` call consumes that now-invalid/near-zero ratio without any re-validation, exactly matching the "cached value not invalidated when its source moves" analog class.

### Impact Explanation
Once `total-supply` (or the intermediate `(* amount ts)` product inside `mul-div-down`) approaches `u128` max, every `deposit` (and functions that depend on it, like `initialize`, which itself performs a `deposit`) reverts with an arithmetic overflow, permanently freezing new deposits into the vault. Existing depositors' `redeem` calls remain generally viable while `ta > 0`, but new capital can never enter, and the vault's economic accounting becomes unusable — a temporary/permanent freezing-of-funds condition for the affected vault (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar` all share the identical logic) [6](#0-5) .

### Likelihood Explanation
`socialize-debt` is a privileged call gated by `check-caller-auth`, restricted to authorized contracts (i.e., `market.clar`), so it is not directly attacker-triggerable at will [7](#0-6) . It is invoked by the market during legitimate bad-debt write-downs from under-collateralized liquidations. The likelihood therefore depends on how many independent bad-debt events accumulate over the vault's lifetime and how small `assets` is left relative to `total-supply` after each — this is a slow-building, systemic risk rather than a single-transaction exploit, similar to how the original Carapace report required "enough cycles of locking capital/depositing." I could not fully verify from the indexed contract slices whether `market.clar`'s liquidation-shortfall logic bounds how much of `assets` a single `socialize-debt` call can remove relative to `total-supply`, which would materially affect how many cycles are actually required to reach the freeze condition.

### Recommendation
- Track a normalized exchange-rate floor (e.g., refuse to let `total-assets-preview / total-supply-preview` fall below a minimum precision threshold) or burn/rebase shares proportionally inside `socialize-debt` itself instead of leaving `total-supply` untouched.
- Add a sanity bound to `deposit`/`convert-to-shares-preview` that rejects mints which would multiply `total-supply` beyond a safe threshold, rather than relying on eventual `u128` overflow to halt the vault.
- Consider tracking assets/shares in higher precision internally (rebasing index) so that a single bad-debt write-down cannot arbitrarily compress the per-share value for future depositors.

### Proof of Concept
1. Vault starts with `assets = 1,000,000` and `total-supply = 1,000,000` zft (1:1 rate).
2. `market.clar` calls `system-borrow` then later suffers a large liquidation shortfall and calls `socialize-debt` with a `scaled-amount` large enough that `principal-reduction ≈ 999,999`, leaving `assets = 1` while `total-supply` stays at `1,000,000` [2](#0-1) .
3. A user calls `deposit` with `amount = 1,000,000`. `convert-to-shares-preview` computes `inkind = 1,000,000 * 1,000,000 / 1 = 1e12` shares minted in a single call [4](#0-3) . `total-supply` is now ≈ `1.000001e12`, and `assets` is now `1,000,001`.
4. Repeat steps 2–3 a handful more times (each bad-debt event again leaves a small `assets` remainder relative to the now-much-larger `total-supply`); `total-supply` grows multiplicatively each cycle.
5. After enough cycles, `(* amount ts)` inside `mul-div-down` (called from `convert-to-shares-preview`) exceeds `u128` max, causing every future `deposit` call (including any subsequent `initialize` calls or normal user deposits) to abort with an arithmetic-overflow runtime error, permanently freezing new deposits to the vault.

  (let ((ta (total-assets-preview))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
