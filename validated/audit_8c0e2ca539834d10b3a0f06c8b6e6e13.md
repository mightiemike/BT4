### Title
Replay-verify state-integrity gate silently skips state-root checks - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` — the routine used by replay/verification tooling to confirm a freshly re-executed transaction matches the previously committed `TransactionInfo` — never compares the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields. It only checks status, gas used, write-set hash, and event root hash.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) , and validates only:
- execution status,
- gas used,
- `write_set` hash vs `txn_info.state_change_hash()`,
- event root hash,

as shown at [2](#0-1) .

The function's own trailing comment acknowledges the gap explicitly: [3](#0-2) 
This confirms that the state checkpoint hash (the Jellyfish Merkle / sparse-Merkle state root committed at checkpoint boundaries — the primary authenticated ledger-state commitment), the hot-state checkpoint hash, and the trading-native position-state checkpoint hash are **not** cross-checked against the locally recomputed values, even though `TransactionInfo` carries these fields specifically so replay/restore tooling can detect state divergence.

This function is consumed by:
- `storage/db-tool/src/replay_on_archive.rs` (`execute_and_verify`), which drives archive replay-verification: it executes a block and calls `ensure_match_transaction_info` per transaction to decide whether execution matches the archived, previously-committed `TransactionInfo` — see the call site at [4](#0-3) .
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` (confirmed via grep, not fully read due to iteration limits).

Because these are the tools explicitly designed to catch non-deterministic or incorrect VM/storage behavior before it becomes an irreversible hard-fork-class divergence, omitting the state-root fields means a scenario where the write set, events, gas, and status all match but the *computed state root* differs (e.g., a state-merge/commit bug, a JMT/state-summary computation regression, or a storage schema reinterpretation bug) would be reported as a **successful match**, even though the ledger's authenticated state commitment has silently diverged.

Note that in the primary online sync path (`execution/executor/src/chunk_executor/mod.rs`, `do_state_checkpoint.rs::get_state_checkpoint_hashes`), known state-checkpoint hashes *are* validated against computed ones via `ensure!` at [5](#0-4) . The gap is isolated to the `TransactionOutput::ensure_match_transaction_info` comparator used by the replay/debug/archive-verify tools.

### Impact Explanation
This falls in the explicitly allowed "hard-fork-only divergence during commit, replay, restore, or proof verification" category: the whole purpose of replay-verify/archive-replay tooling is to catch state-commitment divergence before a chain upgrade or before trusting historical archives. A missing state-root comparison in this exact code path means the tool can report a clean replay while a critical portion of the ledger's authenticated commitment (state root) is wrong — defeating the safety net that is supposed to catch exactly this kind of bug. This is a genuine integrity gap in the proof/commitment-verification code, not a cosmetic issue.

### Likelihood Explanation
The comparator is unconditionally used in `replay_on_archive` and by internal debugger/CLI replay flows, so any state root regression that leaves write set/events/gas/status unchanged (e.g., a bug isolated to state-summary root computation, hot-state root computation, or Merkle accumulation) is guaranteed to be missed by this exact check on every affected transaction, on every replay run using these tools. It requires no attacker action — it is a latent correctness gap in verification tooling that the developers themselves flagged with a TODO comment, indicating it is known but currently unaddressed.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to compare the recomputed `state_checkpoint_hash` (and, when applicable/enabled, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the corresponding fields on `txn_info`, mirroring the comparisons already done for `write_set` and event root hashes, and failing loudly on mismatch just as `do_state_checkpoint.rs::get_state_checkpoint_hashes` already does for the online commit path.

### Proof of Concept
Not applicable as an exploit against a live network (this is a gap in offline replay/verification tooling, not an attacker-triggerable state-corruption primitive). Demonstration path: construct a `TransactionOutput` whose `write_set`, `events`, `gas_used`, and `status` match a given `TransactionInfo`, but whose actually-derived state-checkpoint hash (via `DoStateCheckpoint`) differs (e.g., by patching the state-summary/root computation to return a wrong hash while leaving the write set untouched); calling `ensure_match_transaction_info` will return `Ok(())` despite the state-root mismatch, and `replay_on_archive`'s `execute_and_verify` will treat the replay as successful.

**Caveat**: I could not fully view the call sites in `aptos-debugger/src/aptos_debugger.rs` and `cli/src/commands.rs` due to tool errors in the final iteration (only confirmed via grep that they call `ensure_match_transaction_info`), so I cannot state with certainty whether those specific call sites already perform an independent state-root check elsewhere in their surrounding logic that would mitigate this gap. If you need that confirmed, a full read of those two files is recommended.
