## Finding

### Title
Chall-Manager style Slowloris DoS on the Sequencer's HTTP Gateway due to missing header/connection timeouts - (File: `crates/apollo_http_server/src/http_server.rs`)

### Summary
`HttpServer::run` binds a raw `TcpListener` and serves the Axum `Router` directly via `axum::serve(listener, app)`, without any per-connection header-read timeout, request timeout, or idle-connection timeout configured. `HttpServerStaticConfig` only exposes `ip`, `port`, `max_request_body_size`, and `dynamic_config_poll_interval` — there is no timeout knob at all. This is the exact bug class described in the external report (missing header timeout enabling Slowloris DoS), applied to the sequencer's own externally-reachable transaction-submission Gateway HTTP server. [1](#0-0) [2](#0-1) 

### Finding Description
The HTTP server that exposes `/gateway/add_rpc_transaction` and `/gateway/add_transaction` — the sole unauthenticated ingress point through which any external user submits transactions into the sequencer (as depicted in the transaction submission flow diagram) — is started with:

```rust
let listener = TcpListener::bind(&addr).await?;
Ok(serve(listener, app).await?)
``` [3](#0-2) 

`axum::serve` wraps hyper's connection handling with default settings. There is no `tower_http::timeout::TimeoutLayer`, no builder-level `http1_header_read_timeout`, and no idle/keep-alive timeout applied anywhere in `HttpServer::app()`, which only layers body-size limits and decompression: [4](#0-3) 

The only configuration surface for this server, `HttpServerStaticConfig`, has fields for `ip`, `port`, `max_request_body_size`, and `dynamic_config_poll_interval`, with no timeout-related field: [2](#0-1) 

This mirrors the exact root cause of GHSA-ggmv-j932-q89q: the HTTP gateway parses headers with no timeout, so a client that opens a TCP connection and sends header bytes at an arbitrarily slow trickle (e.g., 1 byte every few seconds) keeps the connection — and its associated tokio task/socket resources — occupied indefinitely.

### Impact Explanation
Unlike chall-manager, which the advisory itself notes is normally buried deep in infrastructure, this HTTP server is the sequencer's designated public transaction ingress ("HTTP Server" in the tx submission flow, routed straight into the Gateway component). An attacker opening many slow connections can exhaust the node's available file descriptors / connection-handling capacity, preventing legitimate users from submitting transactions to that sequencer. If this affects a block-building sequencer node in a round-robin/rotation scheme, it can stall transaction intake for the duration the attacker sustains the connections, i.e., a network unable to confirm new transactions during that node's slot — a Medium/High-severity availability impact reachable by any unauthenticated, unprivileged network client with no on-chain action required.

### Likelihood Explanation
Exploitation requires no authentication, no valid transaction, and no special privileges — only the ability to open TCP connections to the node's HTTP port and send data slowly, identical to the original Slowloris exploitation technique. Given the port is meant to receive public transaction traffic (unlike chall-manager, which is recommended to be hidden), the attack surface here is directly exposed by design, making exploitation straightforward for any external actor with network reachability to the node.

### Recommendation
Configure explicit timeouts on the HTTP server: set a header-read timeout at the hyper/axum-serve layer (e.g., using `hyper_util::server::conn::auto::Builder` with `http1().header_read_timeout(...)`, or wrap the listener/connections with a bounded accept+read-header deadline), and add a `tower_http::timeout::TimeoutLayer` for overall request duration. Expose these as configurable fields on `HttpServerStaticConfig` analogous to `max_request_body_size`, and apply sane defaults (e.g., a few seconds) so slow/incomplete connections are dropped automatically.

### Proof of Concept
1. Start the sequencer's HTTP server component (`apollo_http_server`) exposing `/gateway/add_transaction`.
2. From an attacker host, open N TCP connections to the server's port and, on each, send `POST /gateway/add_transaction HTTP/1.1\r\n` followed by a single header byte every 5–10 seconds, never completing the header block (never sending the terminating `\r\n\r\n`).
3. Observe that `axum::serve`/hyper keeps each connection open indefinitely awaiting the rest of the headers, consuming a tokio task and socket per connection with no server-side timeout to reclaim it.
4. Repeat until the process's available sockets/file descriptors or connection-handling capacity is exhausted, causing legitimate `add_transaction`/`add_rpc_transaction` requests to be refused or queued indefinitely — a full DoS on transaction submission.

    pub async fn run(&mut self) -> Result<(), HttpServerRunError> {
        init_metrics();

        // Parses the bind address from HttpServerConfig, returning an error for invalid addresses.
        let (ip, port) = self.config.ip_and_port();
        let addr = SocketAddr::new(ip, port);
        let app = self.app();
        info!("HttpServer running using socket: {}", addr);

        tokio::spawn(dynamic_config_poll(
            self.dynamic_config_tx.clone(),
            self.config_manager_client.clone(),
            self.config.static_config.dynamic_config_poll_interval,
        ));

        // TODO(Tsabary): update the http server struct to hold optional fields of the
        // dynamic_config_tx, config_manager_client, and a JoinHandle for the polling task.
        // Then, use `set` and `take` to move these around as needed.

        // Create a server that runs forever.
        let listener = TcpListener::bind(&addr).await?;
        Ok(serve(listener, app).await?)
    }
