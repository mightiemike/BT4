### Title
Any unprivileged transaction sender can masquerade as the system "BOOTSTRAP" identity to declare classes for free, bypassing signature validation and nonce consumption - ([File: crates/blockifier/src/transaction/account_transaction.rs])

### Summary
The blockifier and the Starknet OS special-case a hardcoded sentinel sender address (the felt encoding of the string `'BOOTSTRAP'`) that is meant only to let the sequencer itself declare the initial genesis classes with no fee, no signature validation and no nonce bump. The gate that decides whether a submitted transaction qualifies for this privileged path checks only transaction-supplied fields (`sender_address == bootstrap_address()`, `nonce == 0`, `version == 3`, `charge_fee == false`/`max_possible_fee == 0`) — nothing that proves the caller is actually the sequencer or that the chain is still at genesis. Any external, unprivileged party can construct and submit a `DECLARE` transaction with `sender_address` set to this literal and the required zero-fee resource bounds, at any point in the chain's life, and have it accepted and executed by that bypass path.

### Finding Description
`DeclareTransaction::bootstrap_address()` returns a hardcoded felt (`0x424f4f545354524150`, the ASCII encoding of `'BOOTSTRAP'`): [1](#0-0) 

`is_bootstrap_declare` determines eligibility for the bypass purely from transaction-controlled data — sender address equal to the sentinel, nonce zero, and the (also caller-controlled) `charge_fee` flag: [2](#0-1) 

In `AccountTransaction::execute_raw`, if `is_bootstrap_declare` is true, the transaction skips `perform_pre_validation_stage` (nonce/fee/resource-bounds checks against real chain state), skips `__validate_declare__` entirely, and just runs `run_execute` to declare the class, returning a default (no fee, no state changes beyond the class declaration) `TransactionExecutionInfo`: [3](#0-2) 

The identical special case exists in the Starknet OS Cairo implementation of `execute_declare_transaction`, which checks only `sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, and `max_possible_fee == 0` before skipping the validate-declare call and fee charge and directly writing the class hash into `contract_class_changes`: [4](#0-3) 

Nothing in this logic ties the bypass to genesis block number, to a specific privileged caller, or to a one-time-use invariant enforced by consensus. Because the bootstrap address is never actually deployed as an account and the "bootstrap declare" path explicitly does not increment its nonce (as documented in the integration test comment: "they do not increment its nonce... they will only be removed after being rejected during a subsequent attempt"), the nonce for this address is permanently zero from the chain's perspective, so the special condition `nonce == 0` is always satisfiable by any sender who crafts such a transaction: [5](#0-4) 

The gateway's `StatelessTransactionValidator` only validates generic contract-address well-formedness and never rejects the reserved bootstrap literal, nor restricts it to callers proven to be the sequencer/genesis process: [6](#0-5) 

The only "cost" imposed on the attacker is that the class can be declared once (`prev_value=0` in the dict update enforces first-declaration-wins), and every subsequent submission of the same bootstrap declare re-executes the free path and fails only at the point of re-declaring an already-declared class hash, remaining in the mempool as a re-triable transaction. This means an attacker who is first to declare a novel class hash via this identity spoof pays zero fee for class declaration and skips all account validation — a genuine identity/permission bypass analogous to the Plone advisory's "masquerade as a group": an unprivileged actor is able to act with a privileged, system-reserved identity because the system fails to bind the privileged identity check to any real authorization proof.

### Impact Explanation
This is a fee-bypass and unauthorized-account-action vulnerability: any unprivileged transaction sender can act with the authority of the reserved bootstrap identity to declare classes without paying fees or signing/validating through any account contract, at any point after genesis (not just during the one-time system bootstrap). While the direct on-chain state effect is limited to declaring a new (previously undeclared) class hash for free — a resource-accounting/fee-evasion bug — the deeper issue is one of missing authorization: the system distinguishes "sequencer-issued bootstrap tx" from "attacker-issued tx claiming to be bootstrap" using only transaction content that any user fully controls, which is precisely the confusion-of-identity pattern in the reported advisory.

### Likelihood Explanation
High reachability: constructing this transaction requires only public knowledge of the sentinel `bootstrap_address()` value (visible in the open-source `starknet_api` crate), a class the attacker wants declared for free, `nonce = 0`, `version = 3`, and resource bounds that yield `max_possible_fee == 0`. No special privileges, keys, or node access are required — this is directly reachable from a normal RPC-submitted `DECLARE` transaction.

### Recommendation
Do not gate the bootstrap/no-fee/no-validation declare path solely on transaction-supplied fields. Restrict the bypass to a proven genesis/bootstrap context (e.g., enforce it only at a well-defined block number such as block 0, or via an explicit sequencer-only submission channel that never routes through the public gateway/mempool for ordinary users), and reject any externally submitted transaction whose `sender_address` equals the reserved bootstrap sentinel in the stateless gateway validator (`StatelessTransactionValidator::validate`) before it ever reaches execution.

### Proof of Concept
1. An attacker crafts a `DECLARE` V3 transaction with:
   - `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`)
   - `nonce = 0`
   - `version = 3`
   - `resource_bounds` chosen so that `ValidResourceBounds::AllResources(resource_bounds).max_possible_fee(tip) == Fee(0)` (as used by `ValidResourceBounds::create_for_testing_no_fee_enforcement()` in tests)
   - `class_hash` / `compiled_class_hash` for a class the attacker wants declared, and a valid Sierra-to-CASM class hash pre-image.
   - `signature = TransactionSignature::default()` (empty — never checked).
2. Submit it via the normal RPC `starknet_addDeclareTransaction` path.
3. `StatelessTransactionValidator::validate` performs only generic field checks and does not reject the bootstrap sentinel address.
4. In execution, `AccountTransaction::execute_raw` detects `tx.is_bootstrap_declare(charge_fee)` is true, skips `perform_pre_validation_stage` and `__validate_declare__`, and calls `try_declare`, which succeeds because the class hash is undeclared, per `crates/blockifier/src/transaction/transactions.rs` `try_declare` logic: [7](#0-6) 
5. The attacker's class is declared with zero fee paid and no account signature verified — the attacker has masqueraded as the privileged "BOOTSTRAP" identity that was intended only for the sequencer's genesis initialization.

/// Attempts to declare a contract class by setting the contract class in the state with the
/// specified class hash.
fn try_declare<S: State>(
    tx: &DeclareTransaction,
    state: &mut S,
    class_hash: ClassHash,
    compiled_class_hash: Option<CompiledClassHash>,
) -> TransactionExecutionResult<()> {
    match state.get_compiled_class(class_hash) {
        Err(StateError::UndeclaredClassHash(_)) => {
            // Class is undeclared; declare it.
            state.set_contract_class(class_hash, tx.contract_class().try_into()?)?;
            if let Some(compiled_class_hash) = compiled_class_hash {
                state.set_compiled_class_hash(class_hash, compiled_class_hash)?;
            }
            Ok(())
        }
        Err(error) => Err(error)?,
        Ok(_) => {
            // Class is already declared, cannot redeclare.
            Err(TransactionExecutionError::DeclareTransactionError { class_hash })
        }
    }
}
