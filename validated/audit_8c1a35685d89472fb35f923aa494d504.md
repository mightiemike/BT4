## Finding: Replay-Verify Silently Accepts State-Root Divergence — `ensure_match_transaction_info` Skips Checkpoint Hash Comparison

### Title
Replay/verify tooling fails to validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, masking state-root divergence — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that locally re-executed transactions match the already-committed, ledger-accumulator-authenticated `TransactionInfo`. The function checks status, gas used, write-set hash, and event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually represent the committed world-state root (and, when `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled, the hot-state and native-position roots too).

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` performs `ensure!` checks on:
- `status`
- `gas_used`
- `write_set_hash == txn_info.state_change_hash()`
- `event_root_hash == txn_info.event_root_hash()`

but then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or the repurposed `position_state_checkpoint_hash()`. This gap is explicitly acknowledged by an in-repo comment on the same lines: "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

This comparator is wired directly into consumer tools that exist specifically to catch state-integrity regressions:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` calls it per-transaction after re-executing an archived chunk, and only reports a mismatch/error based on its `Err` result. [2](#0-1) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches` uses it to print divergences between re-executed outputs and expected `TransactionInfo`s. [3](#0-2) 
- `aptos-move/cli/src/commands.rs` uses it when replaying a system transaction from the CLI. [4](#0-3) 

`state_checkpoint_hash` (the Sparse/Jellyfish Merkle root of world state at a checkpoint) is derived from the full accumulated state tree, not solely from the current transaction's write set. A defect anywhere in the state-checkpoint construction pipeline — e.g., `do_state_checkpoint.rs`'s hot-state or native-position root computation, or the JMT update/priming path — could produce a write set (and therefore `state_change_hash`) that is byte-identical to the expected one, while the resulting checkpoint/state root still diverges. Because `ensure_match_transaction_info` never checks these root fields, such a divergence passes replay-verify undetected.

### Impact Explanation
Replay-verify (`replay_on_archive`) and the debugger/CLI replay paths are the tools operators and auditors rely on to detect exactly this class of bug: a hard-fork-only divergence where a node's local execution stops matching the authenticated, consensus-committed ledger state. Since the comparator omits the checkpoint-hash fields, a real state-root corruption (from a bug in the hot-state, position-state, or main-state checkpoint computation) can silently pass verification, giving false confidence that an archived/replayed chain segment is consistent when the actual committed state view is wrong. This directly falls under "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Committed state that differs from the correct VM result."

### Likelihood Explanation
The gap is unconditional — it applies to every call of `ensure_match_transaction_info`, regardless of which optional features (`TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) are enabled; when those features are off the corresponding hash fields are `None` on both sides so the omission is harmless, but once any of them is enabled (as intended by their own design, e.g. `HOT_STATE_ROOT_IN_TXN_INFO` is already exercised in `testsuite/smoke-test/src/hot_state.rs`), a checkpoint-hash mismatch introduced by any future bug in state-checkpoint construction becomes silently unverifiable by this tooling. The bug requires no attacker privilege — it's a missing-invariant defect in verification logic itself, not a bypass by a malicious actor.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed output/state and the expected `TransactionInfo` whenever those fields are `Some` on the expected side (mirroring the pattern already used for `state_change_hash`/`event_root_hash`), so replay-verify and debugger/CLI tooling fail loudly on any state-root divergence instead of only on write-set/event/gas/status mismatches.

### Proof of Concept
Conceptual repro (no live cluster needed to see the gap):
1. Enable `TRANSACTION_INFO_V1` + `HOT_STATE_ROOT_IN_TXN_INFO` (or `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) on a test chain, producing committed `TransactionInfoV1`s with non-`None` checkpoint hashes.
2. Introduce (or simulate) any local execution/build where the write set for a transaction is identical but the derived checkpoint/state root differs (e.g., a stale/incorrect base used in `DoStateCheckpoint::compute_position_checkpoint` or hot-state root derivation) — see `execution/executor/src/workflow/do_state_checkpoint.rs`. [5](#0-4) 
3. Run `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::verify` against the archived chunk containing this transaction.
4. Observe that `execute_and_verify` reports no error (`Ok(None)`) despite the checkpoint hash mismatch, because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. [6](#0-5)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
