**Analysis (why the described exploit path does not hold):**

Tracing `enqueue_chunks`'s epoch-splitting loop directly, the arithmetic correctly handles the case where the very last transaction in the chunk is epoch-ending: [1](#0-0) 

- `chunk_end` is exclusive: `let chunk_end = chunk_begin + num_txns as Version;` [2](#0-1) 
- The loop iterates `version` from `chunk_begin` to `chunk_end - 1` (inclusive, since the range is exclusive on `chunk_end`). When the transaction at `version == chunk_end - 1` (the last transaction of the chunk) is epoch-ending, the code pushes `(epoch_begin, version + 1)`, which equals `(epoch_begin, chunk_end)`, and then sets `epoch_begin = version + 1 = chunk_end`.
- After the loop, the trailing check `if epoch_begin < chunk_end { epochs.push((epoch_begin, chunk_end)); }` correctly evaluates to `false` because `epoch_begin == chunk_end` in this scenario, so no extra/duplicate entry is appended.

Tracing through a concrete alternating-parity example (epoch-ending events at, say, `version=2` and the final `version=4` with `chunk_end=5`): the loop produces `epochs = [(0,3), (3,5)]`, which is a contiguous, non-overlapping partition covering exactly `[chunk_begin, chunk_end)` with no gap or overlap, regardless of how many epoch-ending events occur or their positions (including the last transaction).

Downstream, `remove_and_replay_epoch` and `remove_and_apply` do not use `begin_version`/`end_version` to index into `write_sets`/`transaction_infos`/`event_vecs` by absolute version — they only use `end_version - begin_version` to compute `num_txns` and then `drain(..num_txns)` from the *front* of the mutable vectors: [3](#0-2) . Because epochs are processed strictly in order and each epoch consumes exactly the number of elements corresponding to its version range, the vectors stay aligned with the current version regardless of the specific epoch-boundary pattern, and `TransactionSliceMetadata::chunk(begin, end)` (used inside `enqueue_chunk`/`remove_and_apply`) is constructed with correctly matching, non-empty `[begin, end)` bounds. The `debug_assert!(begin < end, ...)` in `TransactionSliceMetadata::chunk` [4](#0-3)  would in fact fire if an empty/duplicate range were ever produced — but the trailing-check arithmetic shown above guarantees this never happens even when the last transaction is epoch-ending.

Since the epoch list is proven contiguous and exhaustive for any placement (including alternating parity or a boundary on the final transaction) of `is_new_epoch_event`, there is no divergence between the epoch ranges and the `write_sets`/`transaction_infos` slice bounds, so no double-application or omission of the boundary transaction's write set occurs.
