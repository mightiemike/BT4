### Title
Flat per-request QPS pricing on paginated list servlets allows cheap triggering of full-store scan+sort work regardless of requested offset/limit - ([File: framework/src/main/java/org/tron/core/services/http/GetPaginatedAssetIssueListServlet.java])

### Summary
`GetPaginatedAssetIssueListServlet` and `GetPaginatedNowWitnessListServlet` (and their PBFT/Solidity mirrors) are only gated by `RateLimiterServlet`'s flat QPS/permit adapter, which has no cost-weighting by requested `offset`/`limit`. Both endpoints, regardless of the pagination window requested, internally load and sort the **entire** backing store before slicing the requested page, so the per-call cost is O(N log N) in total store size (N = all asset issues or all witnesses+votes), not O(limit).

### Finding Description
`GetPaginatedAssetIssueListServlet.doGet`/`doPost` reads `offset`/`limit` directly from attacker-controlled request parameters and calls `wallet.getAssetIssueList(offset, limit)` [1](#0-0) , which delegates to `AssetIssueStore.getAssetIssuesPaginated`. That method always calls `getAllAssetIssues()` — a full iteration of the entire asset-issue store — and always sorts the complete resulting list before taking a sublist; the `limit`/`offset` values only affect the final `subList` call, not the amount of scanning/sorting work performed [2](#0-1) .

Similarly, `Wallet.getPaginatedNowWitnessList` always fetches `getAllWitnesses()`, iterates the entire `VotesStore` to compute vote deltas (`countVote`), applies the deltas to every witness, and sorts the full witness list — before finally skipping/limiting to the requested page [3](#0-2) [4](#0-3) .

The only gate in front of these expensive operations is `RateLimiterServlet.service`, which acquires a per-endpoint permit via a QPS/preemptible strategy and a global IP/QPS limiter — both flat, request-count-based, with no accounting for the size of work a given request will trigger [5](#0-4) . Neither `GetPaginatedAssetIssueListServlet` nor `GetPaginatedNowWitnessListServlet` has a per-servlet rate-limit override configured in `config.conf`; the commented-out examples in `reference.conf` are illustrative only, so both fall back to the default adapter (`DefaultBaseQqsAdapter`) using the global default QPS (`rate.limiter.global.qps`, e.g. `qps=1000` in the default) [6](#0-5) .

Because the cost is O(N) regardless of the offset/limit parameters actually requested, an attacker doesn't even need "maximal" offset/limit values to trigger the worst case — any call incurs the full-store scan and sort. This means every call at the endpoint's flat QPS ceiling costs the node O(N log N) CPU/IO work, and that cost scales with the number of registered asset issues / witnesses+votes on the network without any corresponding price differentiation from the rate limiter.

### Impact Explanation
As the network's asset-issue count or witness/votes count grows, an unprivileged, unauthenticated attacker can repeatedly call `/wallet/getpaginatedassetissuelist` or `/wallet/getpaginatednowwitnesslist` at the endpoint's allowed QPS and force the node to repeatedly perform full-store iteration and sort operations, driving up CPU and I/O load on the FullNode/SolidityNode/PBFTNode HTTP-serving tier. This is a resource-exhaustion / availability-degradation concern (public API cost asymmetry) rather than a consensus-safety, fund-theft, or state-divergence bug — it does not permit unauthorized execution, value duplication, or double-settlement.

### Likelihood Explanation
Feasibility is high and repeatable: any unauthenticated caller can send GET/POST requests with arbitrary `offset`/`limit` values (or even the smallest valid values, since cost is independent of them) at the endpoint's configured QPS. No authentication, fee, or per-request cost accounting stands in the way; the flat QPS limiter (default 1000 qps, or whatever `global.qps`/servlet-specific `qps=N` is configured) is the only throttle, and it treats a request that triggers a full-store scan identically to a request that would be cheap.

### Recommendation
- Cap or price these endpoints based on actual work rather than flat request count, e.g., introduce a dedicated lower QPS/permit ceiling for `GetPaginatedAssetIssueListServlet` and `GetPaginatedNowWitnessListServlet` via `rate.limiter.http` config (`GlobalPreemptibleAdapter` with a small concurrent-permit count, or a low `IPQPSRateLimiterAdapter` qps), since the underlying store scan is O(N) irrespective of pagination window.
- Fix the root inefficiency: cache the sorted asset-issue/witness list (invalidated on writes) instead of re-sorting the full store on every paginated request, so cost is closer to O(limit) or amortized O(1) per call.
- Consider bounding `ASSET_ISSUE_COUNT_LIMIT_MAX`/`WITNESS_COUNT_LIMIT_MAX` enforcement earlier, and rejecting or de-prioritizing requests once store size exceeds a safe threshold for on-the-fly full sort.

```java
// Benchmarks that DB scan cost for a "cheap-looking" small offset/limit request
// is NOT smaller than for a maximal offset/limit request, proving cost is
// O(store size), not O(limit), and thus is materially underpriced by the
// endpoint's flat QPS gate.

@Test
public void testPaginationCostIndependentOfLimit() {
  // Populate AssetIssueStore with N (e.g. 50_000) synthetic AssetIssueCapsule entries.
  populateAssetIssueStore(50_000);

  long startSmall = System.nanoTime();
  List<AssetIssueCapsule> small = assetIssueStore.getAssetIssuesPaginated(0, 1);
  long costSmall = System.nanoTime() - startSmall;

  long startMax = System.nanoTime();
  List<AssetIssueCapsule> max = assetIssueStore.getAssetIssuesPaginated(
      0, Commons.ASSET_ISSUE_COUNT_LIMIT_MAX);
  long costMax = System.nanoTime() - startMax;

  // Assert the two costs are roughly the same order of magnitude (both dominated
  // by the full getAllAssetIssues() + sort, not by `limit`), demonstrating that
  // the flat per-request QPS price does not scale with the work actually done,
  // and that work scales with store size N regardless of requested limit.
  assertTrue("cost should not scale with requested limit; both dominated by O(N log N)",
      Math.abs(costMax - costSmall) < costSmall * 2);

  // Separately assert absolute cost grows materially with N by re-running with
  // N=5_000 and N=50_000 and comparing costSmall(N=5_000) vs costSmall(N=50_000),
  // showing the "flat priced" endpoint's true cost scales with store size.
}
```
Expected assertion outcome: cost for `limit=1` and `limit=ASSET_ISSUE_COUNT_LIMIT_MAX` is statistically similar (confirming full-store scan dominates), and cost scales with N (store size) — demonstrating that a flat per-request QPS-based rate limiter charges the same "price" for requests whose true backend cost varies by orders of magnitude with network growth, i.e., materially underpriced state-iteration work is exposed on a public, unauthenticated HTTP path.

```java
  public List<AssetIssueCapsule> getAllAssetIssues() {
    return Streams.stream(iterator())
        .map(Entry::getValue)
        .collect(Collectors.toList());
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
```

```java
  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
```
