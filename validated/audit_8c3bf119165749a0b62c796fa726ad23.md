### Title
`ensure_match_transaction_info` never validates state/hot-state/position-state checkpoint hashes, letting replay-verify and debugger tooling accept a divergent ledger state - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function relied on by replay/debug/verify tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, and the `aptos-move/cli` replay command) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` committed on-chain. It checks status, gas, write-set hash, and event root hash, but explicitly **skips** comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that commit the post-execution state (and native-position) Merkle roots. This mirrors the zkSync `skip_if_legitimate_fat_ptr` pattern: a code path meant to bind an authenticated value is bypassed, so a locally computed (possibly forged/wrong) state root can be accepted as matching the authenticated one even when it diverges.

### Finding Description
`ensure_match_transaction_info` in `types/src/transaction/mod.rs` is the sole comparator used to confirm a `TransactionOutput` is consistent with a `TransactionInfo` stored (and Merkle-proven) in the ledger: [1](#0-0) 

It validates:
- `status` vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` vs. `txn_info.state_change_hash()`
- `event_root_hash` vs. `txn_info.event_root_hash()`

But the function ends with: [2](#0-1) 

The comment itself admits the gap: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." `TransactionInfoV1` explicitly carries these three commitment fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), all of which are hashed into `TransactionInfo`'s own hash and are Merkle-proven against the ledger's `TransactionAccumulatorHash`: [3](#0-2) 

These state roots are populated at commit time from `StateCheckpointOutput`, which carries `state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, and `position_state_checkpoint_hashes` computed by `DoStateCheckpoint`/`DoLedgerUpdate` and then baked into `TransactionInfo` via `assemble_transaction_infos`: [4](#0-3) 

`ensure_match_transaction_info` is used precisely to bind locally-derived transaction outputs to the ledger's authenticated commitment in tooling paths such as `replay_on_archive::execute_and_verify` and `aptos-move/cli`'s replay command: [5](#0-4) [6](#0-5) 

Because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never re-derived and compared in `ensure_match_transaction_info`, none of these tools notice if the locally computed state-checkpoint (Sparse Merkle / hot-state / native-position) root diverges from what is committed in the on-chain `TransactionInfoV1` — even though `TransactionInfo::hash()` includes these fields and they are, in fact, Merkle-proven against consensus. The verification bypasses the exact field it is supposed to bind.

### Impact Explanation
This falls squarely within the "Proof And Storage Pivots" scope: authenticated state-checkpoint roots (state/hot-state/native-position) fail to "survive executor-to-storage handoff" verification unchanged, and a wrong state root can be silently accepted as matching the correct, ledger-committed one. Concretely:
- Replay-verify tooling (`db-tool replay-on-archive`, used to detect state divergence/forks between full-node replay and the authenticated chain) will report success even when the locally computed state root, hot-state root, or native-position root (state_checkpoint_hash/hot_state_checkpoint_hash/position_state_checkpoint_hash) is wrong — defeating the entire purpose of that consistency check.
- `aptos-debugger`/`aptos-move/cli` replay/simulation flows that call `ensure_match_transaction_info` to confirm a re-executed transaction matches the authenticated `TransactionInfo` will likewise not catch a divergent state-checkpoint commitment.
- Since `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` are permanent feature flags that, once enabled, make these fields consensus-verified parts of `TransactionInfoV1` (and thus part of the Merkle-proven ledger state), any bug in state-checkpoint/hot-state/native-position root computation on the executor side is masked by this comparator, silently corrupting the perceived correctness of committed state during audits, forensics, and fork detection.

This is a "hard-fork-only divergence during commit/replay/proof verification" class issue per the gate: it does not itself let an attacker forge a live consensus proof (BFT signatures on `LedgerInfo` still bind `TransactionInfo.hash()`, which does include these fields), but it removes the intended detection/verification safety net for state-root correctness in the tools explicitly built to catch such divergence, i.e., the exact same "if memory/state is not enforced, the value should not be trusted" principle violated in the zkSync bug: the comparator claims match/success without actually enforcing equality on these fields.

### Likelihood Explanation
This is a real, currently-shipped gap: it is not a hypothetical edge case but an admitted TODO in production code (`TODO(trading-native)`), invoked unconditionally by the only two documented consumers (`replay_on_archive.rs`, `aptos-move/cli`, `aptos-debugger`). No attacker action or special conditions are required beyond the existence of a bug or divergence in state-checkpoint root computation on the execution side, and the fields already exist and are populated whenever `TRANSACTION_INFO_V1` (+ the trading-native/hot-state flags) are enabled. The comment explicitly documents "Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," indicating the fix is understood but not yet implemented, so the check is unprivileged and always reachable on any replay/simulation performed via this API once the feature is turned on.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against `txn_info`'s corresponding fields (when the relevant feature flags are enabled / when the `TransactionOutput` carries enough information to know if it is a checkpoint transaction), returning an error on mismatch just as is already done for `write_set_hash` and `event_root_hash`. At minimum, gate enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on this comparator being fixed, as the existing TODO comment recommends.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and/or `HOT_STATE_ROOT_IN_TXN_INFO`) on a network/testnet.
2. Introduce (or naturally hit via a pre-existing bug) any divergence between the locally computed post-execution state-checkpoint root (main state, hot state, or native-position) and the value actually committed in the ledger's `TransactionInfoV1` for a given version — e.g. run `db-tool replay-on-archive` or `aptos-debugger`/`aptos-move-cli` replay on a version where the local Merkle root differs from consensus due to an executor bug.
3. Observe that `TransactionOutput::ensure_match_transaction_info` (called in `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` and `aptos-move/cli/src/commands.rs`) returns `Ok(())` because it never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, even though these fields (part of `TransactionInfo::hash()`) actually differ from the replay's freshly computed state.
4. The replay-verify/debug tooling reports a clean, successful replay despite an authenticated state root divergence, exactly the scenario the code's own TODO comment warns about.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
