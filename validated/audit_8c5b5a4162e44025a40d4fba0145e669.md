### Title
Hard-coded resource-limit calculation can throw uncaught `ArithmeticException` in `EnergyProcessor.updateAdaptiveTotalEnergyLimit()` / `calculateGlobalEnergyLimit()`, DoS-ing block/transaction processing - (File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java)

### Summary
Analogous to the Venus `VToken.accrueInterest()` bug — where a dynamically computed value is checked against a hard-coded bound and the function reverts instead of clamping — java-tron's "hardened" resource/energy calculation path introduces the same class of defect: instead of gracefully saturating or clamping an overflowing intermediate value, it explicitly throws `ArithmeticException` (via `BigInteger.longValueExact()`), and this exception is not caught anywhere in the call chain that reaches consensus-critical code paths (`updateAdaptiveTotalEnergyLimit()`, `calculateGlobalEnergyLimit()`, `scaleByRate()`).

### Finding Description
When the chain parameter `ALLOW_HARDEN_RESOURCE_CALCULATION` is enabled (a governance-controlled flag, see `hardenCalculation()` guards throughout `EnergyProcessor`/`ResourceProcessor`), several energy/bandwidth accounting computations switch from `double`-based (silently lossy but non-throwing) arithmetic to `BigInteger`-based arithmetic that calls `.longValueExact()`. This method throws `ArithmeticException` if the result does not fit in a `long`.

Concretely, in `EnergyProcessor.updateAdaptiveTotalEnergyLimit()`: [1](#0-0) 
the `upperBound` computation multiplies `totalEnergyLimit` by `getAdaptiveResourceLimitMultiplier()` using `BigInteger...longValueExact()` when hardened calculation is active. If the product overflows a `long`, this throws unconditionally — there is no fallback to clamp to `Long.MAX_VALUE` (the "hard-coded max" analog), unlike the Venus recommendation of setting `borrowRateMantissa = borrowRateMaxMantissa`.

Similarly, `scaleByRate()` (used by the same function) and `calculateGlobalEnergyLimit()`/`calculateGlobalLimitV1`/`calculateGlobalLimitV2` (called from `EnergyProcessor.useEnergy()`, which is invoked on essentially every energy-consuming transaction) follow the identical pattern: [2](#0-1) [3](#0-2) 

Test code explicitly documents that these overflow conditions raise `ArithmeticException` under hardened mode where the non-hardened mode would instead silently wrap/truncate: [4](#0-3) [5](#0-4) 

`updateAdaptiveTotalEnergyLimit()` and `useEnergy()`/`calculateGlobalEnergyLimit()` are core parts of transaction execution and per-block adaptive-resource bookkeeping (mirrored in `RepositoryImpl.calculateGlobalEnergyLimit`/`usageToBalance`), which are exercised by essentially every transaction that consumes energy, and by end-of-block adaptive resource adjustment. If any of the involved dynamic-property values (`TotalEnergyLimit`, `AdaptiveResourceLimitMultiplier`, `TotalEnergyCurrentLimit`, `TotalEnergyWeight`, frozen balances) reach a combination where the `BigInteger` product exceeds `Long.MAX_VALUE`, the resulting uncaught `ArithmeticException` propagates out of the accounting code.

### Impact Explanation
This mirrors the Venus root cause exactly: a hard "must fit" check (implicit in `longValueExact()`, analogous to Venus's explicit `require(borrowRate <= borrowRateMaxMantissa)`) causes a revert/throw instead of a safe clamp when the calculated quantity legitimately exceeds representable/expected bounds. Because these methods sit on the transaction-execution and block-finalization hot path (energy accounting is invoked for essentially all TVM-calling transactions, and adaptive limit update runs at block boundaries), an uncaught `ArithmeticException` here can abort transaction processing or block processing, producing a chain-wide DoS or non-deterministic behavior across nodes (some nodes may have different governance-parameter or freeze-state histories causing divergent overflow conditions), which could also manifest as a consensus-divergence risk if only some nodes trip the exception.

### Likelihood Explanation
Triggering requires: (1) the `ALLOW_HARDEN_RESOURCE_CALCULATION` chain parameter to be active (a committee-governed toggle, not something an anonymous attacker controls directly), and (2) `TotalEnergyLimit`, `AdaptiveResourceLimitMultiplier`, `TotalEnergyWeight`, or frozen-energy balances to reach values whose product overflows a 64-bit long. These dynamic properties are normally kept in sane ranges by proposal validation (`ProposalUtil` enforces bounds like `[0, 100000000000000000]` for `TOTAL_ENERGY_LIMIT`, `[1, 10000]` for `ADAPTIVE_RESOURCE_LIMIT_MULTIPLIER`), which substantially reduces (but per the linear author's own overflow-detection unit tests, does not entirely eliminate for pathological combinations) the probability of naturally hitting overflow through legitimate parameter/usage growth over a long-running mainnet. I could not fully verify from the available index whether `hardenCalculation()`/`ALLOW_HARDEN_RESOURCE_CALCULATION` is presently enabled on java-tron mainnet, nor find explicit top-level try/catch handling around `updateAdaptiveTotalEnergyLimit()`'s block-boundary caller (the call site was not found in `Manager.java` via search, so I could not confirm whether it is guarded there).

### Recommendation
Change the hardened overflow paths in `EnergyProcessor` (`updateAdaptiveTotalEnergyLimit`, `scaleByRate`, `calculateGlobalEnergyLimit`, `calculateGlobalEnergyLimitV2`) and the equivalent code in `RepositoryImpl`/`ResourceProcessor` to saturate to `Long.MAX_VALUE` (or another explicit system-defined cap) instead of throwing `ArithmeticException` when `BigInteger` results exceed `long` range, mirroring the Venus fix of clamping to `borrowRateMaxMantissa` rather than reverting. At minimum, wrap these calls at the block-processing and transaction-execution call sites with explicit exception handling that degrades gracefully (e.g., keep prior limit, log, and continue) rather than allowing the exception to propagate uncaught.

### Proof of Concept
Existing test code already demonstrates the exact failure condition (only the governance flag and appropriate parameter magnitudes are required to reach it in production): [4](#0-3) [6](#0-5) 
These tests show `updateAdaptiveTotalEnergyLimit()` and `calculateGlobalEnergyLimit()` throwing `ArithmeticException` under hardened calculation when input dynamic-property values are large enough for the `BigInteger` multiplication to exceed `Long.MAX_VALUE` — the same structural bug pattern as the Venus finding, applied to java-tron's energy-limit/borrow-rate-equivalent accounting.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
