### Title
No underpricing vulnerability found in BN128Pairing energy pricing vs Fp12 cost — computation cost is point-value-invariant

### Summary
The premise that an attacker can select "maximally expensive" non-identity point pairs to force disproportionate CPU cost relative to the flat per-pair energy charge does not hold. The pairing implementation's cost (number of `Fp12.mul`/`squared`/`frobeniusMap` calls) is determined entirely by fixed curve constants, not by the specific point values, so no input can be more expensive than any other valid non-zero pair.

### Finding Description
`BN128Pairing.getEnergyForData` charges `80000L * (data.length / PAIR_SIZE) + 100000` (or `34000L * pairs + 45000` under Istanbul) purely as a function of the number of 192-byte pairs in the input. [1](#0-0) 

The actual per-pair cost is executed in `PairingCheck.millerLoop` / `PairingCheck.Pair.millerLoop`. The number of loop iterations is bounded by `LOOP_COUNT.bitLength()`, a fixed curve constant (`LOOP_COUNT = 29793968203157093288`), and `calcEllCoeffs`/`millerLoop` perform the same fixed sequence of `Fp2`/`Fp12` doublings, additions, `squared()`, and `mulBy024()` operations regardless of which specific valid curve point is supplied: [2](#0-1) 

The only value-dependent branch is an early exit that makes a pair *cheaper*, not more expensive: if either point is the zero (infinity) point, `millerLoop()` returns `Fp12._1` immediately, skipping the Miller loop entirely: [3](#0-2) 

`finalExponentiation`, run once per `run()` call regardless of pair count details, is also a fixed sequence of `Fp12` operations independent of point values: [4](#0-3) 

Because the Miller loop iteration count is tied to a fixed curve parameter and not to attacker-chosen coordinates, there is no "costly vs cheap" non-identity point selection an attacker can exploit — any valid, non-zero pair costs the same fixed number of `Fp2`/`Fp12` operations. The only lever an attacker has (choosing zero/identity points) reduces cost below the worst case, which is already what the flat linear formula is calibrated against. This mirrors Ethereum's EIP-197/EIP-1108 gas schedule, from which these constants (80000/pair+100000, 34000/pair+45000) were derived and benchmarked against the worst-case (non-identity) Miller loop + final exponentiation cost.

### Impact Explanation
None. Since per-pair computational cost is invariant across all valid non-zero point inputs, there is no way to construct input that costs materially more than the worst case already priced into the flat linear formula. No underpriced-work DoS is achievable via point selection.

### Likelihood Explanation
Not applicable — the exploit precondition (existence of a subset of valid points that are computationally more expensive than others) does not exist in this implementation.

### Recommendation
No change required for this specific concern. If broader DoS-resistance auditing is desired, verify wall-clock benchmarks of `PairingCheck.run()` for N=1..64 pairs against the linear formula to confirm the calibration constants remain accurate for the current JVM/hardware baseline, but this is a calibration exercise, not a vulnerability tied to attacker-chosen point values.

### Proof of Concept
Not applicable — no exploitable input differential exists. A benchmark test (per the proof idea) would show `run()` time growing linearly in N (pair count) regardless of which valid non-zero points are used, confirming cost is a function of pair count only, consistent with the charged energy formula.

  private static Fp12 millerLoop(BN128G1 g1, BN128G2 g2) {

    // convert to affine coordinates
    g1 = g1.toAffine();
    g2 = g2.toAffine();

    // calculate Ell coefficients
    List<EllCoeffs> coeffs = calcEllCoeffs(g2);

    Fp12 f = Fp12._1;
    int idx = 0;

    // for each bit except most significant one
    for (int i = LOOP_COUNT.bitLength() - 2; i >= 0; i--) {

      EllCoeffs c = coeffs.get(idx++);
      f = f.squared();
      f = f.mulBy024(c.ell0, g1.y.mul(c.ellVW), g1.x.mul(c.ellVV));

      if (LOOP_COUNT.testBit(i)) {
        c = coeffs.get(idx++);
        f = f.mulBy024(c.ell0, g1.y.mul(c.ellVW), g1.x.mul(c.ellVV));
      }

    }

    EllCoeffs c = coeffs.get(idx++);
    f = f.mulBy024(c.ell0, g1.y.mul(c.ellVW), g1.x.mul(c.ellVV));

    c = coeffs.get(idx);
    f = f.mulBy024(c.ell0, g1.y.mul(c.ellVW), g1.x.mul(c.ellVV));

    return f;
  }

  public static Fp12 finalExponentiation(Fp12 el) {

    // first chunk
    Fp12 w = new Fp12(el.a, el.b.negate()); // el.b = -el.b
    Fp12 x = el.inverse();
    Fp12 y = w.mul(x);
    Fp12 z = y.frobeniusMap(2);
    Fp12 pre = z.mul(y);

    // last chunk
    Fp12 a = pre.negExp(PAIRING_FINAL_EXPONENT_Z);
    Fp12 b = a.cyclotomicSquared();
    Fp12 c = b.cyclotomicSquared();
    Fp12 d = c.mul(b);
    Fp12 e = d.negExp(PAIRING_FINAL_EXPONENT_Z);
    Fp12 f = e.cyclotomicSquared();
    Fp12 g = f.negExp(PAIRING_FINAL_EXPONENT_Z);
    Fp12 h = d.unitaryInverse();
    Fp12 i = g.unitaryInverse();
    Fp12 j = i.mul(e);
    Fp12 k = j.mul(h);
    Fp12 l = k.mul(b);
    Fp12 m = k.mul(e);
    Fp12 n = m.mul(pre);
    Fp12 o = l.frobeniusMap(1);
    Fp12 p = o.mul(n);
    Fp12 q = k.frobeniusMap(2);
    Fp12 r = q.mul(p);
    Fp12 s = pre.unitaryInverse();
    Fp12 t = s.mul(l);
    Fp12 u = t.frobeniusMap(3);
    Fp12 v = u.mul(r);

    return v;
  }
