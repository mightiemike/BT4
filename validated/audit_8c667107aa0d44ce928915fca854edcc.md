### Title
JSON-RPC `getTransactionAmount` omits `CreateSmartContract` case, causing wallets/dApps to display `value = 0x0` for contract-deployment transactions that transfer TRX - (File: framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcApiUtil.java)

### Summary
The external report describes a wallet confirmation dialog that failed to display the amount of native coin sent alongside a smart-contract call, because the transaction-building code omitted the `amount`/`call_value` field for contract-call and contract-creation transactions. The java-tron JSON-RPC compatibility layer has the same class of defect: the helper that computes the Ethereum-style `value` field for a transaction, `JsonRpcApiUtil.getTransactionAmount`, has a `switch` over `contract.getType()` that includes a case for `TriggerSmartContract` but has **no case for `CreateSmartContract`**, so the `default` branch is taken and the resulting amount silently defaults to `0`.

### Finding Description
`getTransactionAmount` is the single source used to populate the `value` field returned to any Ethereum-compatible JSON-RPC client: [1](#0-0) 

It explicitly unpacks `TriggerSmartContract.getCallValue()` for contract calls, but there is no corresponding case for `CreateSmartContract`, even though the protocol clearly models a non-zero `call_value` on contract deployment (`CreateSmartContract.new_contract.call_value`): [2](#0-1) 

The actuator confirms that `callValue` is a real, chain-enforced fund transfer on contract creation, moving TRX from the deployer to the newly created contract address: [3](#0-2) 

`getTransactionAmount` is consumed directly by `TransactionResult`, the JSON-RPC representation returned by `eth_getTransactionByHash` / `eth_getTransactionByBlockNumberAndIndex`-equivalent endpoints: [4](#0-3) [5](#0-4) 

Because `CreateSmartContract` falls into the `default:` branch (no-op, `amount` stays `0`), any deployment transaction that transfers TRX to the new contract (a payable constructor) will be reported with `value = 0x0` through the JSON-RPC API, even though on-chain the funds were actually moved.

### Impact Explanation
This is directly analogous to the original report: a confirmation/inspection surface (there, a wallet dialog; here, the standardized JSON-RPC transaction view relied on by MetaMask-compatible wallets, block explorers, and any tooling built against java-tron's Ethereum-JSON-RPC compatibility layer) fails to surface the real amount of native currency moved by a contract-related transaction. Users or automated tooling inspecting a `CreateSmartContract` transaction via JSON-RPC will see `value: "0x0"` and be misled into believing no TRX was transferred, when in fact `callValue` was debited from the deployer and credited to the new contract account. This can cause under-reporting of fund movement in wallets, accounting/indexing systems, and audit tooling that trust the JSON-RPC `value` field instead of decoding the raw contract parameters — a concrete accounting/divergence impact between on-chain state and the value reported through the public API.

### Likelihood Explanation
Any unprivileged user can trigger this by broadcasting a `CreateSmartContract` transaction with a non-zero `call_value` (deploying a payable-constructor contract), which is a completely normal and common operation. Any client (wallet, explorer, monitoring service) that queries the transaction via the JSON-RPC endpoints backed by `TransactionResult` will consistently observe the incorrect `value = 0x0`, making this a deterministic, always-reproducible discrepancy rather than a theoretical edge case.

### Recommendation
Add a `CreateSmartContract` case to `getTransactionAmount` in `JsonRpcApiUtil.java` mirroring the existing `TriggerSmartContract` case, unpacking `CreateSmartContract.class` and returning `getNewContract().getCallValue()` (the same value already used correctly by `TransactionCapsule.getCallValue`): [6](#0-5) 

### Proof of Concept
1. Deploy a smart contract via `CreateSmartContract` with a payable constructor and `call_value > 0` (e.g., using `wallet/deploycontract` with `call_value` set).
2. Query the resulting transaction through the JSON-RPC API (e.g., `eth_getTransactionByHash`), which is served via `TransactionResult`, which calls `JsonRpcApiUtil.getTransactionAmount`.
3. Observe that the returned `value` field is `0x0`, while `getAccountStore().get(contractAddress).getBalance()` (or the on-chain balance change) shows the `call_value` amount was actually transferred, as executed in `VMActuator.create()`.

  public static long getTransactionAmount(Transaction.Contract contract, String hash,
                                          TransactionInfo transactionInfo, Wallet wallet) {
    long amount = 0;
    try {
      Any contractParameter = contract.getParameter();
      switch (contract.getType()) {
        case TransferContract:
          amount = contractParameter.unpack(TransferContract.class).getAmount();
          break;
        case TransferAssetContract:
          amount = contractParameter.unpack(TransferAssetContract.class).getAmount();
          break;
        case VoteWitnessContract:
          List<Vote> votesList = contractParameter.unpack(VoteWitnessContract.class).getVotesList();
          long voteNumber = 0L;
          for (Vote vote : votesList) {
            voteNumber += vote.getVoteCount();
          }
          amount = voteNumber;
          break;
        case WitnessCreateContract:
          amount = 9999_000_000L;
          break;
        case AssetIssueContract:
        case ExchangeCreateContract:
          amount = 1024_000_000L;
          break;
        case ParticipateAssetIssueContract:
          break;
        case FreezeBalanceContract:
          amount = contractParameter.unpack(FreezeBalanceContract.class).getFrozenBalance();
          break;
        case TriggerSmartContract:
          amount = contractParameter.unpack(TriggerSmartContract.class).getCallValue();
          break;

  public static long getCallValue(Transaction.Contract contract) {
    try {
      Any contractParameter = contract.getParameter();
      switch (contract.getType()) {
        case TriggerSmartContract:
          return contractParameter.unpack(TriggerSmartContract.class).getCallValue();

        case CreateSmartContract:
          return contractParameter.unpack(CreateSmartContract.class).getNewContract()
              .getCallValue();
        default:
          return 0L;
      }
    } catch (Exception ex) {
      logger.error(ex.getMessage());
      return 0L;
    }
  }
