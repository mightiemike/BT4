## Analysis

The reported bug class — withdrawals lacking user-controlled slippage protection, letting an unprivileged attacker sandwich the trade — has a concrete analog in Push Chain's `x/uexecutor` module: the automatic PRC20→WPC swap performed during inbound gas processing. Instead of using a caller-supplied minimum output (as `decr_position` did on Superposition), the protocol derives its slippage bound from a spot-price quote fetched in the *same* execution, which is exactly the value an attacker can move beforehand.

### Title
Auto-swap during inbound GAS execution uses a self-referential spot-price slippage bound, enabling unprivileged sandwich extraction - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
`ExecuteInboundGas`, `gasAndPayloadDepositAutoSwap`, and `applyGasRefund` all compute a `minPCOut` slippage floor by taking a live `QuoterV2.quoteExactInputSingle` spot quote and discounting it by a flat 5%, then immediately execute the swap against that same bound. Because the bound is derived from the *current* pool price rather than a price tied to the user's original off-chain deposit intent, an attacker who moves the pool price immediately beforehand (a classic sandwich front-run) causes the "protected" swap to still pass the 5%-band check while executing at a manipulated price, extracting value from the depositor.

### Finding Description
`ExecuteInboundGas` ( [1](#0-0) ) fetches a quote via `k.GetSwapQuote` and computes `minPCOut = quote * 95 / 100` then immediately calls `k.CallPRC20DepositAutoSwap` with that bound. The identical pattern is used for `GAS_AND_PAYLOAD` inbounds in `gasAndPayloadDepositAutoSwap` ( [2](#0-1) ) and for excess-gas refunds in `applyGasRefund` ( [3](#0-2) ).

`GetSwapQuote` calls `QuoterV2.quoteExactInputSingle`, a static read against the live Uniswap-V3-style pool state — not a TWAP or any externally-anchored reference price: [4](#0-3) 

The swap itself, `CallPRC20DepositAutoSwap`, is executed as a `DerivedEVMCall` from the module account with `commit=true` in the very same keeper call, using the `minPCOut` just computed: [5](#0-4) 

This is functionally the same class of bug as the Superposition finding: the amount the user is entitled to receive was never fixed by the user (it can't be — the deposit originated on an external chain, potentially blocks or minutes earlier); the on-chain code substitutes a bound computed from *the pool state at the moment of execution*. An unprivileged attacker watching the mempool/finalizing vote for a large inbound `GAS`/`GAS_AND_PAYLOAD` transaction can:
1. Front-run with a swap that pushes the PRC20/WPC pool price against the depositor.
2. Let the module's auto-swap execute — it still satisfies the 5% band because that band is measured against the attacker's own manipulated price, not a fair/pre-manipulation price.
3. Back-run to unwind the price move, capturing the difference (up to ~5% of the deposited value, or more depending on pool depth and how tight the attacker keeps the manipulated price to the 5% boundary) at the depositor's expense.

Because these Uniswap-V3-style pools on Push Chain (WPC/PRC20) are ordinary public EVM contracts reachable by any address with funds, no validator or TSS privilege is required — this is a plain user-vs-user MEV sandwich, identical in mechanism to the original report, just moved from a withdrawal-slippage context to a deposit-auto-swap context.

### Impact Explanation
Every `GAS` and `GAS_AND_PAYLOAD` inbound that triggers the auto-swap leg (and every outbound gas refund that uses the swap-refund path) is exposed to value extraction bounded by the 5% slippage tolerance, which is attacker-influenced rather than a true safety margin. This is a direct loss of user/protocol-controlled funds (the depositor receives less PC than the fair-value swap would have produced), matching the "stealing ... funds" allowed-impact category.

### Likelihood Explanation
Likelihood is high for any inbound whose swapped notional is large relative to the WPC/PRC20 pool's available on-chain liquidity: sandwiching AMM spot-quote swaps is a well-understood and automatable MEV pattern, and here the "protection" (5% band from `GetSwapQuote`) does not defend against it because the reference price itself is manipulable in the same window. No validator or TSS misbehavior is needed — a single unprivileged actor with capital and gas can perform the attack.

### Recommendation
Do not derive the slippage floor from a live, manipulable in-execution AMM spot quote. Options:
- Use a TWAP-based reference price with a bounded deviation check against the current spot price (revert if spot deviates too far from TWAP) before allowing the auto-swap to proceed.
- Cap swap notional per block/pool relative to available liquidity, or require multi-block observation before committing large auto-swaps.
- Consider deferring/queuing large auto-swaps or splitting them, and/or making the 5% tolerance configurable/tighter and paired with a maximum price-impact check independent of the same-block quote.

### Proof of Concept
1. Attacker observes a pending `MsgVoteInbound` (or the vote that will cross the 2/3 threshold) for a large `GAS`/`GAS_AND_PAYLOAD` inbound whose asset has a shallow WPC pool.
2. Attacker submits an EVM swap transaction against the PRC20/WPC pool that shifts the spot price unfavorably for the upcoming deposit-swap direction, timed to land just before the finalizing vote's execution in the same or an earlier block.
3. The finalizing vote triggers `ExecuteInboundGas` → `GetSwapQuote` (reads the now-manipulated pool price) → `minPCOut = quote*95/100` → `CallPRC20DepositAutoSwap`, which executes at the manipulated price but still satisfies its own 5% band.
4. Attacker submits a back-run trade restoring the pool price, realizing the price-impact profit that came out of the depositor's swap output. [6](#0-5) [4](#0-3)

func (k Keeper) gasAndPayloadDepositAutoSwap(

	prc20AddressHex common.Address,
	ueaAddr common.Address,
	amount *big.Int,

	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	fee, err := k.GetDefaultFeeTierForToken(sdkCtx, prc20AddressHex)
	if err != nil {
		return nil, err
	}

	quote, err := k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)
	if err != nil {
		return nil, err
	}

	// 5% slippage: minPCOut = quote * 95 / 100
	minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
	minPCOut.Div(minPCOut, big.NewInt(100))

	return k.CallPRC20DepositAutoSwap(sdkCtx, prc20AddressHex, ueaAddr, amount, fee, minPCOut)

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}

// Calls Handler Contract to deposit prc20 tokens with auto-swap.
// fee and minPCOut must be pre-computed by the caller (see GetDefaultFeeTierForToken / GetSwapQuote).
func (k Keeper) CallPRC20DepositAutoSwap(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount, fee, minPCOut *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: depositPRC20WithAutoSwap",
		"prc20", prc20Address.Hex(),
		"recipient", to.Hex(),
		"amount", amount.String(),
		"fee", fee.String(),
		"min_pc_out", minPCOut.String(),
	)
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // who is sending the transaction
		handlerAddr,        // destination: Handler contract
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20WithAutoSwap",
		prc20Address,
		amount,
		to,
		fee,
		minPCOut,
		big.NewInt(0), // deadline = 0 → contract uses its default
	)
}
