### Title
Missing checkpoint-hash validation in `TransactionOutput::ensure_match_transaction_info` allows replay-verify tooling to accept a diverging state/hot-state root - (File: `types/src/transaction/mod.rs`)

### Summary
This is the Aptos-native analog of the C4 "wrong `DOMAIN_SEPARATOR`" bug class: a security-critical binding value is silently excluded from the check that is supposed to validate it, so the invariant the check exists to enforce is not actually enforced. Here, `TransactionOutput::ensure_match_transaction_info` — the function used by replay/restore/debug tooling to confirm that a freshly re-executed transaction still matches the authenticated `TransactionInfo` recorded on-chain — deliberately skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, even though these are exactly the fields that bind a transaction's execution to the correct world-state root.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` validates status, gas, write-set hash, and event-root hash against the target `TransactionInfo`, but explicitly does not validate the state-checkpoint-related hashes, as the code itself documents: [1](#0-0) 

Compare this to the sibling `TransactionInfoV0`/`V1` struct definitions, which show that `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are first-class fields folded into the `TransactionInfo` hash (and thus into the transaction accumulator root that ledger infos commit to): [2](#0-1) 

This function is the sole per-transaction correctness check used by:
- `ChunkExecutor::verify_execution`, invoked from `remove_and_replay_epoch` during backup/chunk replay verification: [3](#0-2) 
- The CLI replay/debug path (`aptos-move/cli/src/commands.rs`), used to sanity-check transaction re-execution against on-chain history.

Critically, in the chunk-replay flow, the data that actually gets persisted to storage (`remove_and_apply`) is the *authenticated* historical `write_sets`/`transaction_infos` supplied by the backup/archive — not the freshly recomputed VM output. `verify_execution`/`ensure_match_transaction_info` is the only mechanism whose job is to confirm that local re-execution reproduces the same result as the historical, already-committed data. Because it omits the checkpoint-hash fields, any divergence between local state/hot-state Merkle root computation and the authenticated root — e.g. a nondeterminism bug or a regression in the state-checkpoint/hot-state or `position_state_checkpoint` hashing logic — is invisible to this check and the tool reports success.

### Impact Explanation
This falls squarely in the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" categories. The entire purpose of replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `storage/db-tool/src/replay_verify.rs`, and the `ChunkExecutor::verify_execution` path used during backup restore) is to catch exactly the class of bug that would cause validators to diverge on mainnet: a state-root (SMT/state-checkpoint or hot-state) mismatch between the VM's local re-execution and the authenticated history. By excluding the checkpoint hashes from the comparison, this class of bug is guaranteed to pass replay-verify undetected, defeating the primary safety net meant to catch a real consensus-breaking divergence before/after it occurs. The code's own TODO comment acknowledges this is a known, live gap tied to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Likelihood Explanation
The gap is unconditionally present in current code — not gated behind any feature flag — for every call to `ensure_match_transaction_info` today, and is triggered automatically any time the local execution produces even one non-matching checkpoint hash while all other checked fields still match (perfectly plausible for state-computation bugs, since those are separate hashing paths from write-set/event hashing). No privileged access or malicious actor is required; a benign VM/state-checkpoint bug is sufficient to be silently swallowed by this tooling, undermining the ability to detect it via the standard mainnet safety mechanism (replay-verify) before it manifests as a hard fork.

### Recommendation
Add `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` comparisons to `ensure_match_transaction_info`, matching the pattern already used for `write_set_hash`/`event_root_hash`, before removing the current TODO/disabling gate, so replay-verify and CLI replay tooling can no longer report success when the authenticated checkpoint root diverges from local re-execution.

### Proof of Concept
1. Take any transaction chunk being replayed via `ChunkExecutor::remove_and_replay_epoch` → `verify_execution` (`execution/executor/src/chunk_executor/mod.rs:648-708`).
2. Assume a bug (or non-determinism) exists purely in state-checkpoint/hot-state SMT root computation such that the locally recomputed `state_checkpoint_hash`/`hot_state_checkpoint_hash` differs from the authenticated `transaction_infos[i]` value, while write-set hash, event hash, gas, and status remain identical (a realistic scenario since checkpoint-hash computation is a distinct code path from write-set/event hashing).
3. `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) performs no comparison on the checkpoint hashes and returns `Ok(())`.
4. `replay_on_archive`/`replay_verify` tooling and the CLI replay path report a successful replay, even though the state root produced by local execution has silently diverged from the authenticated ledger state — exactly the signature of a consensus-breaking bug that this tooling exists to catch.
