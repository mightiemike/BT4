### Title
Failed-call refund in `rlp_execute_callback` can panic on insufficient balance, permanently freezing the wallet contract via a stuck `has_in_flight_tx` flag - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The eth-implicit `WalletContract` gates all new transactions on the in-memory/state flag `has_in_flight_tx`: `rlp_execute` refuses to start a new transaction while it is `true` [1](#0-0) , and every promise-chain callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) is responsible for eventually resetting it to `false` [2](#0-1) [3](#0-2) [4](#0-3) . If the receipt executing a callback fails for any reason (including *after* the flag has been set to `false` in the function body), nearcore rolls back **all** state changes made by that receipt, so the flag reverts to whatever it was on-chain beforehand (`true`), exactly like the reported Solidity bug where a state mutation cached at "intent" time gets invalidated before the finalizing step runs and the finalizing step reverts.

### Finding Description
`rlp_execute_callback` refunds an external caller's attached deposit when the main promised action fails:
```rust
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(
            refund_promise,
            NearToken::from_yoctonear(yocto_near.into()),
        );
    }
    ...
}
``` [5](#0-4) 

This refund is only guaranteed to succeed if the wallet account's own NEAR balance at that moment is `>= yocto_near`. But `inner_rlp_execute` can *unconditionally* pay a relayer `fee` out of the wallet's balance before the main action's outcome is even known, for fee-bearing emulated transfers:
```rust
if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
    env::promise_batch_action_transfer(refund_promise, *fee);
}
``` [6](#0-5) 

If the main action then fails (e.g., a bad receiver, a downstream contract panic, or attached-deposit exhaustion caused by that very `fee` payout), the protocol refunds the main action's own deposit back to the wallet **as a separate, independently-scheduled receipt** (`refund_unspent_gas_and_deposits`, `runtime/runtime/src/lib.rs:1166`) — there is no guarantee this refund receipt lands before `rlp_execute_callback` executes. If it hasn't landed yet, the wallet's live balance can be below `yocto_near`, so `promise_batch_action_transfer` inside the callback fails (insufficient balance) and the whole callback receipt fails.

Per the runtime's action-receipt execution model, a failed receipt causes `state_update.rollback()`, discarding *all* state writes made by that receipt (`runtime/runtime/src/lib.rs:961-970`, documented in `protocol-model/spec/runtime-execution.md:69-70`) [7](#0-6) . This includes the `self.has_in_flight_tx = false;` line executed at the top of `rlp_execute_callback` [8](#0-7) : because it never commits, on-chain `has_in_flight_tx` remains `true` (the value set when `rlp_execute` first accepted the transaction, at line 118).

Once stuck at `true`, every subsequent call to `rlp_execute` is rejected at the entry check [9](#0-8) , and there is no owner/administrative function in this contract to clear the flag — unlike the GMX vault which at least has `emergencyPause`/`emergencyResume`. The wallet account becomes permanently unusable through the eth-emulation interface.

### Impact Explanation
This permanently freezes the affected eth-implicit account's ability to submit any further Ethereum-style transaction through `rlp_execute` — a denial-of-service that requires no privileged access and is triggered purely by the ordinary failure/refund-timing path of a single relayer-submitted transaction. This matches the "permanently frozen funds"/"transaction-triggered halt" acceptance criteria: the account's ability to move its own funds and manage its keys via this interface is bricked with no in-contract recovery path.

### Likelihood Explanation
The trigger conditions are realistic and do not require an adversarial validator/network: any fee-bearing emulated transfer (`EOABaseTokenTransfer`/`ERC20Transfer` with `fee != 0`) whose main action subsequently fails puts the wallet's balance at risk of being insufficient for the caller-deposit refund, since the fee payout and the main action's deposit-refund-on-failure are asynchronous, differently-timed receipts relative to the callback. A relayer (malicious or simply unlucky) can construct or encounter this ordering without any special privileges — it is reachable from a single submitted transaction.

### Recommendation
- Track/reserve the caller-deposit refund amount before spending it elsewhere (e.g., before paying out `fee`), or defer the `fee` payout until after the main action's outcome (and refund) is known, so the wallet never risks lacking balance to refund the caller.
- Avoid letting a failure inside `rlp_execute_callback`'s refund logic roll back the `has_in_flight_tx` reset: e.g., reset `has_in_flight_tx = false` and commit that change independently of (i.e., before attempting) the refund transfer, or wrap the refund transfer so its failure cannot abort the whole callback (only attempt the transfer if the balance is provably sufficient, and otherwise degrade gracefully rather than panicking).
- Add an owner-only "unstick" mechanism as a defense-in-depth safety valve, mirroring the emergency-pause/resume pattern recommended for the analogous Solidity bug.

### Proof of Concept
Conceptual sequence (single relayer-submitted RLP transaction reachable end-to-end):
1. Wallet account holds a balance just above `fee + deposit_attached_to_main_action`.
2. Relayer submits an RLP-encoded `EOABaseTokenTransfer` with a non-zero `fee` and a `target` that will cause the main `Transfer`/`FunctionCall` action to fail (e.g., insufficient remaining balance for the action's own deposit, or a bad receiver).
3. `inner_rlp_execute` immediately creates a `Promise::batch_action_transfer` paying `fee` to the relayer [6](#0-5) , then chains the main action `.then(rlp_execute_callback)`.
4. The main action fails on its receiving shard; its own deposit-refund receipt back to the wallet is scheduled independently and has not necessarily landed by the time `rlp_execute_callback` runs.
5. `rlp_execute_callback` sees `PromiseResult::Failed`, tries to refund the caller's `yocto_near` deposit, but the wallet's current balance (reduced by `fee`, and not yet replenished by the main action's deposit refund) is insufficient; `promise_batch_action_transfer` fails.
6. The callback receipt fails; the runtime rolls back all its state changes (`runtime/runtime/src/lib.rs:961-970`), so `has_in_flight_tx` (set to `false` at the top of the function) never actually gets persisted as `false` — it remains `true` from step 3's `rlp_execute`.
7. Any further call to `rlp_execute` on this wallet account is now rejected forever [9](#0-8) , with no contract-level recovery function available.
