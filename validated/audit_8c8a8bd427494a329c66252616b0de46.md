### Title
`WithdrawFromGasKey` moves real balance but is priced as a zero-deposit action in `total_deposit`/refund accounting - (File: `core/primitives/src/action/mod.rs`)

### Summary
`Action::get_deposit_balance()` is the single source of truth the runtime uses to know how much NEAR value an action actually moves, and it is fed into `total_deposit()` which drives deposit-refund and delegate-action balance accounting. `WithdrawFromGasKeyAction` is not matched in `get_deposit_balance()` and falls into the wildcard `_ => Balance::ZERO` arm, even though `action_withdraw_from_gas_key` performs a real balance-changing transfer of `action.amount` from the gas key to the account.

### Finding Description
`get_deposit_balance()` explicitly enumerates the actions that carry value: `FunctionCall`, `Transfer`, `DeterministicStateInit`, `UniversalStateInit`, `TransferToGasKey`, and defaults everything else — including `WithdrawFromGasKey` — to `Balance::ZERO`: [1](#0-0) 

Yet `action_withdraw_from_gas_key` performs a genuine value transfer: it debits `action.amount` from the gas key's balance and credits the same amount onto the account balance: [2](#0-1) 

`get_deposit_balance()` is aggregated by `total_deposit()`, which nearcore documents as "the total sum of deposits for given actions," used both directly and through delegate-action unwrapping: [3](#0-2) 

This is structurally the same class of bug as the GMX report: an action variant that has a genuine `amount`-like field driving a real balance mutation, while the code path responsible for computing "how much value this action moved" (an `inputAmount`/`deposit`-equivalent) was never updated to account for that field and silently resolves to zero for that variant.

`total_deposit()` is consumed in `refund_unspent_gas_and_deposits` to compute `deposit_refund` on receipt failure (`deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO }`), and in `apply_delegate_action` when relayers sponsor meta-transactions: [4](#0-3) [5](#0-4) 

Because `WithdrawFromGasKey` is priced at zero by `total_deposit`, any accounting path that relies on `total_deposit` to reason about "how much value is at stake in this receipt" undercounts a receipt containing a `WithdrawFromGasKey` action by exactly `action.amount`.

### Impact Explanation
I was not able to fully trace, in the remaining budget, every downstream consumer of `total_deposit()`/`get_deposit_balance()` to confirm a concrete state-root divergence, double-refund, or fund-creation path (e.g., whether `refund_unspent_gas_and_deposits`'s `deposit_refund` on a **failed** receipt containing `WithdrawFromGasKey` would omit refunding the withdrawn amount, effectively burning it, or whether some other component uses `get_deposit_balance` for receipt cost/size estimation in a way that could be exploited). The mismatch between the real balance mutation in `action_withdraw_from_gas_key` and the zero valuation in `get_deposit_balance` is confirmed by direct code inspection, but I could not verify within this session whether it is reachable to cause unauthorized value movement, supply inflation, or state-root divergence versus simply an accounting undercount with no direct consensus-visible consequence (e.g., if `WithdrawFromGasKey` receipts can never legitimately fail after the balance mutation, or if refunds for this action type are handled by a different code path not yet located).

### Likelihood Explanation
`WithdrawFromGasKey` is reachable by any signer who owns a gas key on their own account (a normal, unprivileged transaction/action), so the trigger condition itself is trivially reachable. Whether it is *exploitable* for value gain (vs. a benign accounting quirk) depends on downstream consumers of `total_deposit` that I could not fully confirm in this session.

### Recommendation
Confirm every consumer of `total_deposit()` / `Action::get_deposit_balance()` (deposit-refund computation in `refund_unspent_gas_and_deposits`, delegate-action balance accounting in `apply_delegate_action`, and any congestion-control/receipt-cost estimation) and add an explicit `Action::WithdrawFromGasKey(a) => a.amount` arm to `get_deposit_balance()` if this action's value transfer should participate in those computations, or otherwise document explicitly why the wildcard zero is intentional for this variant.

### Proof of Concept
Not independently reproducible from the index alone in this session — the balance-mutation call site (`action_withdraw_from_gas_key`) and the zero-valuing call site (`get_deposit_balance`) are both confirmed by direct citation above, but I could not confirm a full transaction-triggered PoC (e.g., a failing receipt containing `WithdrawFromGasKey` that demonstrably loses or double-counts funds) within the remaining tool budget. A background Devin session with full repo/test access would be needed to write and run such a PoC test (e.g., forcing `action_withdraw_from_gas_key` to succeed then a later action in the same receipt to fail, and observing whether `deposit_refund` accounts for the withdrawn amount).

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}

/// Get the total sum of deposits for given actions.
pub fn total_deposit(actions: &[Action]) -> Result<Balance, IntegerOverflowError> {
    let mut total_balance = Balance::ZERO;
    for action in actions {
        let action_balance;
        if let Some(delegate_action) = delegate_inner_action(action) {
            // Note, here Relayer pays the deposit but if actions fail, the deposit is
            // refunded to Sender of DelegateAction
            let actions = delegate_action.get_actions();
            action_balance = total_deposit(&actions)?;
        } else {
            action_balance = action.get_deposit_balance();
        }

        total_balance = safe_add_balance(total_balance, action_balance)?;
    }
    Ok(total_balance)
}
