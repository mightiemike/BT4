## Analysis

The Starknet report's core issue is: a transaction whose fee-payer is *not* the party who requested/authorized the action (an escape signed only by the Guardian) can have unbounded `L1_GAS`/`L2_GAS` fee parameters, letting a colluding sequencer drain the account's entire balance because no protocol-level ceiling exists on the fee that can be extracted from that account in a single transaction.

Push Chain has a structurally similar pattern in the isCEA branch of `ExecuteInboundGasAndPayload`.

### Title
Unbounded gas-fee debit from a third-party CEA recipient in isCEA inbound execution - (File: `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/fees.go`)

### Summary
For `isCEA` inbounds, `Recipient` and the entire `UniversalPayload` (including `GasLimit`, `MaxFeePerGas`) are attacker-controlled fields taken directly from a source-chain deposit event observed and voted in by honest Universal Validators [1](#0-0) . When the recipient resolves to a deployed smart contract (not a UEA), the module calls `CallExecuteUniversalTx` on that contract as an arbitrary third party, and then debits the *recipient contract's own* PC balance for the resulting gas cost via `DeductGasFeesFromReceipt`, using `ueaAddr` (the attacker-chosen recipient) as the fee payer [2](#0-1) .

### Finding Description
`DeductGasFeesFromReceipt` computes `gasCost = effectiveGasPrice * gasUsed`, where `effectiveGasPrice` is pinned to the network `baseFee` (not the attacker-supplied `MaxFeePerGas`) [3](#0-2) , and the only bound on `gasUsed` is that it cannot exceed the payload's own `GasLimit` [4](#0-3) . Crucially, `GasLimit` itself is taken from `utx.InboundTx.UniversalPayload`, which is populated from the attacker-controlled source-chain event, not from the recipient contract's consent [5](#0-4) . There is no protocol-level maximum on `GasLimit` or on the total upc that can be extracted from the recipient in a single inbound — no analog of the Starknet fix's `MAX_ESCAPE_MAX_FEE_STRK`/`MAX_ESCAPE_TIP_STRK` caps exists here.

Because the smart-contract isCEA branch invokes `executeUniversalTx` on the recipient with attacker-supplied `Data`/calldata and an attacker-supplied `GasLimit` [6](#0-5) , and no signature or consent from the recipient contract's operator is verified anywhere in this path (contrast with `MsgExecutePayload`'s owner-signed authorization model, which explicitly does not apply here) [7](#0-6) , any unprivileged source-chain actor can name an arbitrary already-deployed contract as `Recipient`, drive it into expensive computation, and have the resulting real gas cost billed against that contract's own PC balance.

### Impact Explanation
An attacker who can emit a qualifying source-chain gateway event (a normal, unprivileged action) can force honest Universal Validators to vote in an inbound naming any deployed contract as `Recipient`, causing that contract's PC balance to be debited for gas consumption chosen by the attacker (via calldata/`GasLimit`), up to the contract's full available balance, with no fee ceiling. This is unauthorized draining of protocol/user-controlled funds from an account that never signed, approved, or rate-limited the fee, mirroring the "malicious Guardian sets excessive fee limit" scenario but replacing "excessive price" with "excessive attacker-chosen gas consumption with no per-inbound cap."

### Likelihood Explanation
Reachable by an ordinary unprivileged user through the default `GAS_AND_PAYLOAD` inbound path with `IsCEA=true`, requiring only a legitimate-looking source-chain deposit event with a victim contract address as `Recipient`; no privileged, validator, or governance role is required — only honest UV quorum voting on an event that genuinely occurred on the source chain.

### Recommendation
Introduce a protocol-level cap (mirroring `MAX_ESCAPE_MAX_FEE`) on the total upc that `DeductGasFeesFromReceipt` may charge a recipient in a single inbound execution, and/or require the CEA recipient contract to explicitly register/opt in to a maximum gas budget it is willing to be billed for, rather than accepting an unbounded, sender-supplied `GasLimit` from `UniversalPayload`.

### Proof of Concept
1. Attacker deploys/uses a source-chain gateway to emit a `GAS_AND_PAYLOAD` deposit event with `IsCEA=true`, `Recipient = <victim contract address>`, and a `UniversalPayload.Data` crafted to trigger maximal computation in the victim contract's `executeUniversalTx`, with `GasLimit` set high.
2. Honest UVs observe and vote `MsgVoteInbound` for this real event; quorum is reached.
3. `ExecuteInboundGasAndPayload` resolves `isSmartContract=true` for the victim, invokes `CallExecuteUniversalTx`, and `DeductGasFeesFromReceipt` burns `baseFee * gasUsed` from the victim contract's own PC balance [2](#0-1) .
4. Repeated inbounds continue draining the victim's balance with no per-transaction or cumulative fee ceiling enforced.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**
