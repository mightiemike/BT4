### Title
Contract-fundable gas-key balances can become permanently unrecoverable because `WithdrawFromGasKey` has no promise-batch host function and `DeleteKey` burns/rejects high balances - ([File: runtime/near-vm-runner/src/imports.rs])

### Summary
`TransferToGasKey` can be executed both via a signed transaction and via the `promise_batch_action_transfer_to_gas_key` host function, so a contract can push NEAR into any account's gas-key balance (including its own) purely through cross-contract calls. `WithdrawFromGasKey`, however, is intentionally excluded from the promise-batch host-function API and can only be executed via a directly-signed transaction. The only other way to remove a gas-key balance is `DeleteKey`, which burns balances `<= 1 NEAR` and outright rejects (`GasKeyBalanceTooHigh`) deletion of keys with balance `> 1 NEAR`, leaving the key (and funds) in place. This mirrors the `OngoingBountyV1.receiveNft` bug class: an asset-accepting entry point exists with no reachable, contract-triggerable payout counterpart, so funds routed in via one path have no path back out except a mechanism (a signed transaction from a specific private key) that may not exist for the account that received them.

### Finding Description
- `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257`, called by the host function `promise_batch_action_transfer_to_gas_key` in `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:3549`) lets a contract, via `promise_batch_create` targeting any account (commonly itself, `sir=true`), add balance to a `GasKeyInfo` on that account. [1](#0-0) 
- `WithdrawFromGasKey`'s only handler is `action_withdraw_from_gas_key` (`runtime/runtime/src/access_keys.rs:290`), reachable solely via the transaction path (`verify_and_charge_gas_key_tx_ephemeral` / regular tx handling), never via a promise batch action. This is intentional and explicitly documented at the host-function import table: [2](#0-1) 
- `check_actor_permissions` requires `actor_id == account_id` for both `AddKey`/`WithdrawFromGasKey`, i.e. only a signer that is authorized on that exact account (a `FullAccess` or self-executing contract receipt) can withdraw — a plain contract call from a third party can never trigger it. [3](#0-2) 
- The only alternative exit for gas-key funds is `delete_gas_key` (`runtime/runtime/src/access_keys.rs:93-134`): if `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), it returns `GasKeyBalanceTooHigh` and leaves the key/balance completely untouched; if `balance <= 1 NEAR` it is unconditionally burned into `tokens_burnt`, not refunded to anyone. [4](#0-3) 

Put together: any account whose only means of authorization is a contract (e.g. a `FunctionCallPermission`-only key, or any account that self-adds a gas key via `promise_batch_action_add_key_with_full_access`/similar and never exposes/holds the corresponding private key) can accumulate NEAR in a gas key balance through ordinary contract-driven cross-contract calls, but that balance can never be moved by any further contract logic, and once above 1 NEAR it can neither be withdrawn (no host function, and no controlling private key exists to sign a `WithdrawFromGasKey` transaction) nor deleted (rejected by `GasKeyBalanceTooHigh`). The funds are then frozen in that gas key permanently — analogous to the reported NFT stuck in `OngoingBountyV1` because the contract exposes a deposit-accepting entry point (`receiveNft`) but no reachable payout path (`ClaimManagerV1._claimOngoingBounty` doesn't handle NFTs).

### Impact Explanation
Any NEAR routed into a gas key balance by a contract call, once the balance exceeds 1 NEAR and the account has no accessible private key to sign a `WithdrawFromGasKey`/`DeleteKey` transaction (e.g. purely contract-managed accounts, or gas keys added and funded entirely through contract logic without ever surfacing the private key to a human), is permanently locked in protocol state with no code path — transaction or receipt — capable of releasing it. This satisfies "permanently frozen funds": value that entered circulation cannot re-enter circulation through any reachable mechanism.

### Likelihood Explanation
Likelihood is moderate: it requires a contract-driven pattern where a gas key is added and funded (both doable purely by contract logic via `promise_batch_action_add_key_with_full_access`/`promise_batch_action_transfer_to_gas_key`) without the corresponding private key ever being retained/exposed to an operator, and the accumulated balance exceeding 1 NEAR. This is a realistic pattern for automated/self-custodial contract accounts building on the new Gas Keys (NEP-611) primitive, since the whole point of the feature is to let contracts manage gas keys programmatically; nothing in the runtime prevents a contract from funding a gas key it (or nobody) can ever sign for.

### Recommendation
Provide a safe, contract-reachable way to recover gas-key balances above the 1 NEAR burn threshold, e.g.: (1) allow `DeleteKey`/`delete_gas_key` to refund balances above `MAX_BALANCE_TO_BURN` to the owning account instead of unconditionally erroring, or (2) add a promise-batch host function for `WithdrawFromGasKey` gated so it cannot bypass the pending-transaction-queue visibility guarantees (e.g., restrict it to self-receiver receipts, mirroring the `actor_id == account_id` check already enforced), or (3) document and enforce (at `AddKey`/`TransferToGasKey` time) that gas keys funded via contract calls must have a known/derivable signing key, preventing unrecoverable accumulation.

### Proof of Concept
1. Deploy a contract at account `X` with only a `FunctionCallPermission` access key (no `FullAccess` key ever exists on `X`).
2. Contract logic on `X`, in a single receipt targeting itself (`promise_batch_create("X")`), calls `promise_batch_action_add_key_with_full_access` to add a fresh, randomly-generated gas key public key whose private key is never retained/exposed (`runtime/near-vm-runner/src/imports.rs:262-267`).
3. In the same or a later self-targeted batch, the contract calls `promise_batch_action_transfer_to_gas_key(promise_idx, gas_key_pub, amount > 1 NEAR)` (`runtime/runtime/src/access_keys.rs:257`, host fn wired at `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:3549`), funding the gas key with e.g. 5 NEAR.
4. No party holds the private key for that gas key, so no `WithdrawFromGasKey` transaction (`runtime/runtime/src/access_keys.rs:290`) can ever be signed, and there is no promise-batch host function for it (`runtime/near-vm-runner/src/imports.rs:311-317`).
5. Attempting to reclaim funds via `DeleteKey` fails: `delete_gas_key` sees `balance (5 NEAR) > MAX_BALANCE_TO_BURN (1 NEAR)` and returns `GasKeyBalanceTooHigh`, leaving the key and its 5 NEAR balance in place (`runtime/runtime/src/access_keys.rs:103-111`).
6. The 5 NEAR is now permanently unreachable by any transaction or contract call — the funds are frozen for the lifetime of the account.
