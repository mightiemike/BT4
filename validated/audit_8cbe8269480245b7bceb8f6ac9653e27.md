**Analysis:**

The `acl` module's `ACL` struct has abilities `store, drop, copy` — notably **not** `key`. [1](#0-0)  This means `ACL` can never be published directly as a top-level resource under an address; it can only exist embedded as a field inside another struct that does have the `key` ability and is stored via `move_to`. To mutate an embedded `ACL`, a caller must first obtain `&mut` access to the containing resource via `borrow_global_mut<T>(addr)`, which is a privilege the *consuming module* controls entirely by how it writes its own entry functions — `acl.move` itself never touches global storage and has no opinion on signer checks, by design (per its doc comment describing it as a generic access-list data structure, analogous to `vector`).

Reviewing the actual consuming module present in the repo, `message_board::acl_based_mb`, its mutating entry functions correctly derive the storage address from the caller's own signer rather than accepting an arbitrary target address: `add_participant` and `remove_participant` call `borrow_global_mut<ACLBasedMB>(signer::address_of(account))`, so an unprivileged caller can only mutate the ACL under *their own* address, never another account's. [2](#0-1) 

No production module in this repository was found that exposes `acl::add`/`acl::remove` on a resource looked up by an attacker-supplied address without a signer/self-address check. The described exploit path requires a hypothetical vulnerable wrapping module that does not exist in the current codebase (`acl_based_mb.move` is also a `move-examples` module, out of the review's production scope). Since `acl.move` operates purely on borrowed references and correctly delegates storage-access gating to the resource owner by Move's type/ability system, and no in-scope consuming module misuses it, there is no reachable path for an unprivileged transaction to commit a write set mutating another account's ACL-bound resource.
