### Title
Static per-payload `MaxFeePerGas` vs. dynamic on-chain `baseFee` permanently strands executed inbound funds without payload execution - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` in `x/uexecutor/keeper/fees.go` hard-fails (`maxFeePerGas.Cmp(baseFeeBig) < 0 → error`) whenever the network's dynamic `baseFee` rises above the `MaxFeePerGas` an ordinary user fixed inside their off-chain-signed `UniversalPayload`. This is structurally the same bug class as the Venus `accrueInterest()` finding: a value calculated dynamically (here, `baseFee`, adjusted every block by the `feemarket` module based on network gas usage) can exceed a value effectively "hard-coded" at signing time (`MaxFeePerGas`), and instead of clamping or gracefully deferring, the code errors out of a function on the critical execution path, causing the surrounding logic to discard already-completed work via `CacheContext` rollback.

### Finding Description
`CalculateGasCost` [1](#0-0)  rejects any `maxFeePerGas` below the current `baseFee`. This function is invoked from `DeductGasFeesFromReceipt` [2](#0-1) , which in turn is called from every payload-execution path: `ExecutePayloadV2` [3](#0-2) , the smart-contract branch of `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` [4](#0-3) , and `ExecutePayload` (direct `MsgExecutePayload`) [5](#0-4) .

For **inbound-vote-triggered execution** (the ballot-finalization path reachable purely by an ordinary user submitting a cross-chain deposit + payload), the PRC20 deposit is committed to the recipient/UEA *before* the `CacheContext` scope, but the actual payload call (`ExecutePayloadV2`/`CallExecuteUniversalTx`) plus its fee deduction are wrapped in a `CacheContext` that is discarded entirely if `DeductGasFeesFromReceipt` returns an error [6](#0-5) . Since `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` run exactly once, at the moment the inbound ballot passes quorum, and any resulting error is simply recorded as a terminal `FAILED` `PCTx` with `return nil` [7](#0-6) , there is no retry mechanism.

An ordinary, unprivileged user (or anyone observing mempool/base-fee trends) can choose a `MaxFeePerGas` that is valid at signing time but becomes stale by the time validators reach quorum and the inbound is finalized (which can span multiple blocks while `baseFee` is adjusted upward by ordinary network congestion — itself triggerable by unprivileged EVM traffic). No malicious validator, relayer, or privileged actor is required.

### Impact Explanation
When this race is hit on the `isCEA`/UEA/smart-contract paths, the deposit (PRC20 mint / funds credit) is already committed and irreversible, but the accompanying payload — the actual intended action (e.g., a swap, a contract call, a UEA-authorized transfer) — never executes and is never retried. This is a genuine, unprivileged, non-network-level denial of service on universal execution: user-initiated cross-chain funds+payload delivery is permanently and silently dropped whenever `baseFee` transiently exceeds the payload's fixed `MaxFeePerGas`, with the only trace being a `FAILED` PCTx and no automatic remediation or refund path (the "rescue"/revert path explicitly does not fire because the deposit PCTx is `SUCCESS`, as confirmed by the repo's own test comments [8](#0-7) ).

### Likelihood Explanation
Base fees are dynamic per-block quantities driven by network gas usage [9](#0-8) , while `MaxFeePerGas` is fixed at the time a user (or SDK) constructs and signs the `UniversalPayload` off-chain. Given normal ballot-finalization latency (multiple validator votes required before quorum) and ordinary fee-market volatility, this condition is plausible without any attacker action, and can be trivially triggered/amplified by unprivileged EVM traffic that pushes `baseFee` up during the voting window.

### Recommendation
Do not hard-error out of the whole execution/fee-deduction pipeline when `maxFeePerGas < baseFee`. Instead: clamp the effective gas price to the network's current minimum acceptable value only if it is still ≤ `maxFeePerGas`; otherwise, treat this as a recoverable condition — e.g., retry the payload execution attempt on a subsequent block/until `baseFee` falls back within bounds, or explicitly emit an outbound/refund path for the deposited funds when payload execution can provably no longer succeed, rather than silently terminating with a `FAILED` PCTx and no remediation.

### Proof of Concept
1. User signs a `UniversalPayload` (e.g., FUNDS_AND_PAYLOAD inbound to a UEA) with `MaxFeePerGas = X`, where `X` is valid against the `baseFee` at signing time.
2. Before validators reach vote quorum for this inbound, ordinary Push Chain traffic (unprivileged EVM transactions) raises `baseFee` above `X`.
3. Quorum is reached; `ExecuteInboundFundsAndPayload` runs: the PRC20 deposit into the UEA succeeds and commits (outside the cache scope).
4. `ExecutePayloadV2` → `DeductGasFeesFromReceipt` → `CalculateGasCost` returns `"maxFeePerGas (X) cannot be less than baseFee (Y)"`.
5. The `CacheContext` for the EVM call + fee deduction is discarded; the payload's effect never lands on-chain.
6. `ExecuteInboundFundsAndPayload` records the payload PCTx as `FAILED` and returns `nil`; no retry, no revert/refund outbound is created (isCEA/deposit-success path is exempt from the rescue path).
