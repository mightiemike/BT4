## Finding: Replay-verification skips ledger commitment fields, allowing silent state divergence to pass as verified

### Title
`TransactionOutput::ensure_match_transaction_info` omits state/hot-state/position checkpoint hash comparison, letting replay/restore verification accept a locally-diverging ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single invariant check used by replay tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) and by the chunk executor's replayer (`execution/executor/src/chunk_executor/mod.rs`) to confirm that a freshly re-executed `TransactionOutput` matches the already-committed, signature-backed `TransactionInfo`. The function explicitly checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but the code contains an acknowledged gap: it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the values recomputed locally. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` validates several fields of a re-executed transaction against the trusted, already-committed `TransactionInfo`:
- transaction status
- gas used
- write-set hash vs. `state_change_hash`
- event root hash [2](#0-1) 

But it explicitly does **not** check the checkpoint/root-hash fields that bind a transaction to the actual ledger state root (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), as stated directly in the code comment:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
``` [3](#0-2) 

These checkpoint hashes are the authenticated proof-binding artifacts: `state_checkpoint_hash` is the Sparse-Merkle root of the ledger state, `hot_state_checkpoint_hash` is the hot-state Merkle root, and `position_state_checkpoint_hash` is the native-position Merkle root, all committed inside `TransactionInfoV1` and therefore covered by the transaction accumulator and ultimately by validator signatures. [4](#0-3) 

This function is used by `replay_on_archive` (archive-node replay auditing) and by the chunk executor's `TransactionReplayer`/db-tool code paths, whose entire purpose is to detect exactly this class of divergence — a mismatch between locally-recomputed state and the historically committed ledger. [5](#0-4) 

Because the comparison of `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` is skipped, any bug elsewhere in state-commit code (state-summary computation, hot-state Merkle commit, or the newly added native-position state root computation reachable via `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` feature flags) that produces an incorrect state root will not be caught by this verification path — replay/restore verification will report success even though the locally materialized ledger state differs from the state actually committed by validators.

### Impact Explanation
This breaks the "Proof and Storage Pivots" invariant that "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state," and the invariant that VM outputs/state roots must survive executor-to-storage handoff and replay unchanged. A silent corruption of the state/hot-state/position root during replay (e.g., from another bug, from a bit flip, from a mis-ordered write-set application, or from any divergence introduced by the native-position/hot-state subsystems that are gated behind the newly introduced feature flags) would go undetected by the tool whose specific job is to catch that divergence. This is a hard-fork/replay-only-detectable class of integrity break: verification tooling (used to certify archive-node/backup correctness and drive replay-based recovery) reports "match" even though the actual, provable ledger state diverges, undermining trust in restore/backup verification and any recovery decision made from it.

### Likelihood Explanation
The gap is triggered any time a full checkpoint-root divergence exists at a version being replay-verified. It requires no privileged access or malicious actor input — any pre-existing state-commit inconsistency (bug elsewhere, corrupted backup data, non-deterministic execution) will simply not be flagged by this specific check. The comment in the code confirms this is a known, currently-live gap rather than dead code, and it is directly reachable through the shipped `replay_on_archive` and debugger tooling, and through the chunk executor's replay path used during restore.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when locally computed and when present in `txn_info`) against the locally recomputed roots before returning `Ok(())`, especially before/when enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO`, exactly as the existing TODO indicates.

### Proof of Concept
Not independently reproduced with a running node in this session (no filesystem/terminal access in ask-only mode); the finding is based on direct code inspection: the check is defined and its call sites are confirmed at `types/src/transaction/mod.rs:2139-2204` (used by `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `execution/executor/src/chunk_executor/mod.rs`). I was not able, within the available tool budget, to trace every call site in `chunk_executor/mod.rs` to confirm whether an additional, independent state-root check exists elsewhere in that specific replay path that might compensate for this gap — that should be verified before treating this as fully unmitigated in the live commit/replay flow, though the code comment strongly suggests it is not currently compensated for.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
