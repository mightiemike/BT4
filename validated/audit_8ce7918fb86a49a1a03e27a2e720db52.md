## Analysis

The Convex report describes a class of bug where a privileged party (`owner`) can mutate a reference that downstream unprivileged calls implicitly trust, and can do so *after* observing a victim's pending transaction but *before* it executes — enabling a front-running attack that changes the effective behavior/target of the victim's call.

The closest reachable analog in nearcore is the **`AccountId`-mode Global Contract** mechanism, where the deploying account acts as an unaccountable "owner" of code that other unprivileged accounts reference by mutable account-id pointer rather than by immutable hash.

### Title
Owner-controlled mutable Global Contract (`GlobalContractDeployMode::AccountId`) enables front-running/rug-pull of dependent accounts - (`runtime/runtime/src/global_contracts.rs`)

### Summary
When a contract is deployed with `GlobalContractDeployMode::AccountId`, any account that later calls `UseGlobalContract` with that identifier binds its executable code to `AccountContract::GlobalByAccount(id)` rather than a fixed hash. The code executed for that account is always whatever the publishing account currently has deployed, resolved fresh at call time.

### Finding Description
`GlobalContractDeployMode` explicitly documents this trust model: [1](#0-0) 

`use_global_contract` binds the identifier by account id, without pinning to a code hash or nonce, so it always resolves to the latest deployed code for that publisher account: [2](#0-1) 

`initiate_distribution` shows that a redeploy under `GlobalContractDeployMode::AccountId` simply reuses the same `GlobalContractIdentifier::AccountId(account_id)` key and bumps an internal nonce purely to resolve distribution-ordering races, not to protect callers from a change of code: [3](#0-2) 

The nonce-freshness check exists only to prevent a stale (older) redistribution receipt from clobbering a newer one — it does not stop the publisher from redeploying malicious code at will, and does not protect a specific pending transaction that targets code the caller has already inspected: [4](#0-3) 

This is analogous to Convex's `setFactories`: an "owner" role (the global-contract-publishing account) can change the referenced implementation at any time, including immediately before a specific unprivileged transaction that depends on that implementation executes, since:
- The identifier callers bind to (`AccountId`) never pins a specific code version.
- No commitment/timelock/versioning gate exists between "user observes/signs against code X" and "user's FunctionCall actually executes against code Y."
- A test explicitly documents that any account referencing the identifier immediately picks up the newest version once distributed: [5](#0-4) 

### Impact Explanation
Any unprivileged user who deposits funds into, or otherwise trusts, an account whose code is `AccountContract::GlobalByAccount(publisher)` is exposed to the publisher unilaterally rewriting that code before the user's own signed `FunctionCall` (potentially carrying a deposit) executes. This allows the publisher to front-run a victim's pending transaction and redirect funds, alter withdrawal logic, or otherwise perform unauthorized value movement against depositors who believed they were interacting with a specific, previously-reviewed implementation — the same asymmetric privileged-front-running pattern flagged in the Convex report.

### Likelihood Explanation
Likelihood is moderate to high wherever `GlobalContractDeployMode::AccountId` is used for anything holding user funds or performing value-sensitive logic (e.g., a shared vault/token pattern), because the publisher needs no special protocol privilege — only a normal `DeployGlobalContract` transaction with `deploy_mode: AccountId` targeting the same account id, timed to land before the victim's dependent transaction.

### Recommendation
For any global contract relied upon for value-sensitive logic, prefer `GlobalContractDeployMode::CodeHash` (immutable) references via `UseGlobalContract`, or if `AccountId` mode must remain mutable, add explicit user-facing guarantees such as: pinning a specific accepted code hash/nonce at the time a value-carrying `FunctionCall` is authorized, or a mandatory delay/commit-reveal between redeploy and effect, mirroring the "construct in Booster + migrations directly in factories" recommendation from the original report (i.e., make the trusted reference immutable, or gate updates by an explicit, delayed migration path rather than instantaneous rebind).

### Proof of Concept
1. `publisher.near` deploys a Global Contract V1 with `GlobalContractDeployMode::AccountId` (a legitimate-looking vault contract).
2. `victim.near` calls `UseGlobalContract` referencing `GlobalContractIdentifier::AccountId(publisher.near)`, then deposits funds via a `FunctionCall` (e.g., `deposit`) to `victim.near`.
3. `publisher.near` observes `victim.near`'s pending deposit transaction and submits a new `DeployGlobalContract` (same `AccountId` mode) with malicious code (e.g., a `deposit` method that instead transfers the attached deposit to `publisher.near`) timed to land in an earlier or same-shard-applied block/chunk before `victim.near`'s deposit transaction executes, per `action_deploy_global_contract` / `use_global_contract` / `initiate_distribution` logic shown above.
4. `victim.near`'s subsequent call executes against the new, malicious code, resulting in unauthorized value movement. [6](#0-5)

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

// Checks if the incoming nonce is fresh and updates the stored nonce. Returns
// true if the nonce is fresh, false if it's stale. The nonce is set
// immediately and the freshness check allows the same nonce (>=).
fn check_and_update_nonce(
    global_contract_data: &GlobalContractDistributionReceipt,
    identifier: &GlobalContractCodeIdentifier,
    state_update: &mut TrieUpdate,
) -> Result<bool, RuntimeError> {
    let nonce_key = TrieKey::GlobalContractNonce { identifier: identifier.clone() };
    let stored_nonce = get_nonce(state_update, &nonce_key)?;
    let incoming_nonce = global_contract_data.nonce();

    // Allow the same nonce since the nonce is updated immediately when
    // initiating distribution to prevent multiple distributions with the same
    // nonce from being initiated.
    if incoming_nonce < stored_nonce {
        return Ok(false);
    }

    set_nonce(state_update, nonce_key, incoming_nonce);
    Ok(true)
}
