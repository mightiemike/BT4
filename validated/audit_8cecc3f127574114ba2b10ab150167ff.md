## Finding

### Title
Replay-verification skips `state_checkpoint_hash` validation, allowing state-root divergence to go undetected - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info()` — the function used by all "replay and verify" tooling (`storage/db-tool/replay_on_archive.rs`, `aptos-move/cli/src/commands.rs` transaction replay, and transitively `storage/backup/backup-cli`'s `VerifyExecutionMode`) to confirm that a freshly re-executed transaction matches the previously committed, accumulator-authenticated `TransactionInfo` — explicitly does not check the `state_checkpoint_hash` (nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`). This is acknowledged in the code itself via a TODO comment. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` checks execution status, gas used, the write-set hash (`state_change_hash`), and the event root hash against the corresponding fields of `TransactionInfo`: [2](#0-1) 

It never compares `self` (the `TransactionOutput`) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The trailing comment makes this explicit:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

`state_checkpoint_hash` is the root of the Jellyfish Merkle Tree (state root) computed in `DoStateCheckpoint::run` by applying all write sets up to and including a checkpoint boundary; it authenticates the *cumulative* ledger state, not just an individual transaction's write set: [4](#0-3) 

The `state_change_hash` check (write-set hash) only proves that this single transaction's write set is byte-identical to what was recorded — it says nothing about whether applying that write set on top of the correct prior state produces the correct new state root. A divergence in state-merklization logic, sharding, hot-state handling, or any bug in `calculate_state_and_put_updates`/JMT commit logic that corrupts the cumulative state root while leaving individual per-transaction write sets and events unaffected, would pass `ensure_match_transaction_info` silently.

This function is the sole verification gate used by:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which is the archive replay-verification path [5](#0-4) 
- `aptos-move/cli/src/commands.rs` transaction replay path [6](#0-5) 

### Impact Explanation
The stated purpose of replay-verify tooling is exactly to catch cases where local re-execution diverges from committed/authenticated ledger state (a core proof/commit-integrity invariant). Because `state_checkpoint_hash` is skipped, this tooling can report "successful replay" even when the authenticated state root (the value the JMT and downstream proofs/API responses trust) does not match what local execution actually produced. This is a genuine break of the "replay paths … must not reinterpret committed data into a different ledger state" and "hard-fork-only divergence during commit, replay … must be caught" invariants named in scope. Any bug that corrupts the state-merklization step without altering write-set bytes (e.g. an issue in the hot-state/position-state or sharded-JMT commit path) would silently pass verification, undermining the primary detection mechanism for state-root corruption.

### Likelihood Explanation
This is not an attacker-triggerable exploit in the traditional sense (it requires an underlying state-computation bug elsewhere to actually produce divergent output); it is a genuine gap in a defense-in-depth verification mechanism, confirmed by the developers' own TODO comment describing precisely this failure mode. Given the comment's mention of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` being gated pending this fix, the team is aware but the fix (validating checkpoint hashes) has not yet been implemented in this snapshot of the code.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s computed state checkpoint hash(es) against `txn_info.state_checkpoint_hash()` (and hot-state/position checkpoint hashes when present), for callers that have access to the state view needed to compute them (or plumb the already-computed hashes from the checkpoint step into this comparison), before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, so that replay-verify tooling actually detects state-root divergence.

### Proof of Concept
Not applicable in the traditional exploit sense — this is a verification-logic gap, not a directly triggerable state corruption. Demonstrating impact requires an independent bug in state-merklization (JMT/hot-state commit) that changes the resulting state root while leaving the transaction's own write set and events unchanged; `ensure_match_transaction_info`'s current implementation (`types/src/transaction/mod.rs:2139-2204`) is the artifact proving such a divergence would not be caught by replay verification.

---
Note: I was unable to fully trace whether `storage/backup/backup-cli`'s `VerifyExecutionMode` path independently validates state roots through a different code path (e.g., via `TransactionRestoreBatchController`) before or after calling into transaction restore, due to iteration limits — the grep results show `state_checkpoint_hash` references in `storage/backup/backup-cli/src/backup_types/transaction/restore.rs` and `coordinators/replay_verify.rs` that I could not read in full. If those paths perform an independent state-root check outside of `ensure_match_transaction_info`, the backup-cli replay-verify flow specifically may be less impacted than the `db-tool`/`cli` replay paths, which do rely solely on this function.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
