## Finding: Wrong-format `RevertRecipient` accepted from user-controlled EVM log, minted to unintended/zero address on outbound revert

### Title
Attacker-supplied `RevertRecipient` from the `UniversalTxOutbound` gateway event is used unvalidated as the Push-Chain PRC20 revert-mint address, allowing bridged funds to be minted to an unintended or invalid address when the outbound later fails - (File: `x/uexecutor/keeper/create_outbound.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
`BuildOutboundsFromReceipt` decodes a `UniversalTxOutbound` event emitted by the `UNIVERSAL_GATEWAY_PC` contract (triggered by arbitrary user payload execution, e.g. a UEA calling `gateway.withdraw`) and copies `event.RevertRecipient` directly into `OutboundTx.RevertInstructions.FundRecipient` with no format or ownership validation. [1](#0-0) 

If that outbound later fails (`ObservedTx.Success == false`), `handleFailedOutbound` re-mints the bridged PRC20 tokens on Push Chain by calling `common.HexToAddress(recipient)` where `recipient` is taken from `outbound.RevertInstructions.FundRecipient` (falling back to `outbound.Sender` only if empty), with no re-validation that the string is a well-formed Push-Chain/EVM address. [2](#0-1) 

The same unchecked value is also used as the fallback refund recipient for excess gas in `applyGasRefund`. [3](#0-2) 

### Finding Description
This is the direct analog of the reported bug class: value that is destined to return to a "sender/owner" on failure is redirected based on a value that was never validated to be a controllable, correctly-formatted destination, causing funds to be minted somewhere the intended party cannot access (or, if `common.HexToAddress` receives a non-hex string, silently truncates/zero-pads it into an arbitrary or zero address rather than erroring, per go-ethereum's `common.FromHex`/`Hex2Bytes` semantics of ignoring decode errors).

Unlike the `Inbound.RevertInstructions.FundRecipient` path, which is explicitly canonicalized per source-chain namespace in `Inbound.Canonicalize()` and is validated against the EOA/UEA/hex rules before execution (as shown by the `execute_inbound_*` tests rejecting non-hex recipients with `FAILED` PCTx), the outbound-created `RevertInstructions.FundRecipient` in `BuildOutboundsFromReceipt` comes straight from `event.RevertRecipient` decoded off an EVM log and is never passed through an equivalent hex/EVM validation step before being consumed later by `common.HexToAddress` in `handleFailedOutbound`/`applyGasRefund`. [4](#0-3) [5](#0-4) 

Since the outbound-creation payload originates from an EVM event emitted as a result of an arbitrary UEA/user-controlled `gateway.withdraw`/payload call (an unprivileged, ordinary user transaction path), the attacker fully controls the `RevertRecipient` bytes encoded in that event. If the format is wrong (e.g. non-0x-prefixed, oversized, or otherwise malformed), the later revert-mint silently sends the re-minted PRC20 to an unintended address rather than failing loudly, because `handleFailedOutbound` does not perform the same defensive checks that the inbound-execution path does.

### Impact Explanation
If an outbound created this way subsequently fails on the destination chain (a routine, expected occurrence - swap failures, insufficient liquidity, external-chain reverts, etc., all reachable without any privileged actor), the bridged/native-mapped tokens intended to be refunded to the original sender are minted to whatever address `common.HexToAddress` derives from the unvalidated `RevertRecipient` string, which may not be a controllable address. This matches the reported bug class exactly: funds meant to return to the rightful owner on a "no-bid"/failure path are sent to an address with no way to reclaim them, resulting in permanent, unauthorized loss of user funds.

### Likelihood Explanation
Likelihood is currently uncertain without runtime tracing of the `UNIVERSAL_GATEWAY_PC` contract's `RevertRecipient` encoding/validation on the Solidity side (the smart-contract source is not indexed here), so it is not fully confirmed whether that contract itself enforces the recipient to be a valid 20-byte EVM address before emitting the event, which would neutralize this path. The Go-level keeper code shown does not re-validate the field, so the invariant relies entirely on an off-repo (Solidity gateway) guarantee that this repository's Go code does not itself check.

### Recommendation
Validate `event.RevertRecipient` (and generically all `RevertInstructions.FundRecipient` values used for Push-Chain-side minting) with the same `strings.HasPrefix("0x")` / `common.IsHexAddress` checks already applied to `Inbound.Recipient` in the inbound execution paths, before it is stored on `OutboundTx.RevertInstructions`, and re-validate before calling `common.HexToAddress` in `handleFailedOutbound` and `applyGasRefund`, failing safe (e.g. falling back to `outbound.Sender`, or aborting the outbound for manual intervention) instead of proceeding with a possibly malformed address.

### Proof of Concept
Not independently executed; based on static code tracing. A concrete PoC would require: (1) confirming the `UniversalTxOutbound` Solidity event/gateway contract does not itself constrain `RevertRecipient` to a valid EVM address, (2) crafting a UEA payload that calls `gateway.withdraw` with a malformed `revertRecipient` argument, (3) causing the resulting outbound to be observed as failed by validators, and (4) verifying via `handleFailedOutbound`/`CallPRC20Deposit` that PRC20 tokens are minted to the derived (possibly zero) address instead of back to the original sender. This last verification step (Solidity-side constraints) could not be completed within the available tooling/index and should be confirmed in a live session before treating this as a fully confirmed, high-confidence finding.

```go
// Canonicalize normalizes encoding-variant fields in place (per source-chain
// namespace) so the same event from any observer is byte-identical across
// ballot keys, UTX keys and registry lookups. Lenient (unparseable values are
// kept trimmed, never rejected) because the vote path must always record a
// UTX — execution-level validation rejects malformed inbounds later.
func (p *Inbound) Canonicalize() {
	p.SourceChain = strings.TrimSpace(p.SourceChain)
	p.TxHash = utils.LenientCanonicalizeTxHash(p.SourceChain, p.TxHash)
	p.Sender = utils.LenientCanonicalizeAddress(p.SourceChain, p.Sender)
	p.AssetAddr = utils.LenientCanonicalizeAddress(p.SourceChain, p.AssetAddr)
	// Recipient lives on Push Chain (EVM) regardless of source chain.
	p.Recipient = utils.LenientCanonicalizeEVMAddress(p.Recipient)
	p.LogIndex = strings.TrimSpace(p.LogIndex)
	p.Amount = strings.TrimSpace(p.Amount)
	p.RawPayload = utils.CanonicalizeHexBlob(p.RawPayload)
	p.VerificationData = utils.CanonicalizeHexBlob(p.VerificationData)
	if p.RevertInstructions != nil {
		// Refunds return to the source chain.
		p.RevertInstructions.FundRecipient = utils.LenientCanonicalizeAddress(p.SourceChain, p.RevertInstructions.FundRecipient)
	}
}
```
