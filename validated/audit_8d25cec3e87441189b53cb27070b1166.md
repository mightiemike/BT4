### Title
Unbounded `Vec::with_capacity(n_items)` when parsing Starknet OS output arrays enables OOM DoS during OS re-execution - ([File: crates/starknet_os/src/io/os_output_types.rs])

### Summary
The blanket `TryFromOutputIter for Vec<T>` implementation reads a felt-encoded item count directly from the OS program's Cairo output and immediately allocates `Vec::with_capacity(n_items)` **before** validating that the remaining iterator actually contains enough felts to justify that count. This is the same bug class as the disclosed `brace-expansion` issue: a length/count field is trusted and used to size an allocation without bounding it against the actual amount of underlying data, allowing a crafted or corrupted output stream to trigger a large, uncontrolled memory allocation and crash the process with an unrecoverable OOM — exactly the failure mode the sequencer's own maintainers had already patched for the analogous `CairoArray::try_from(Retdata)` path in `crates/apollo_cairo_utils/src/lib.rs`.

### Finding Description
`Vec<T>`'s `TryFromOutputIter` implementation: [1](#0-0) 

```rust
impl<T: TryFromOutputIter> TryFromOutputIter for Vec<T> {
    fn try_from_output_iter<It: Iterator<Item = Felt>>(...) -> Result<Self, OsOutputError> {
        let n_items = wrap_missing_as(iter.next(), &format!("n_items of {}", ...))?;
        let mut items = Vec::with_capacity(n_items);   // <-- allocated before bounds check
        for _ in 0..n_items {
            items.push(T::try_from_output_iter(iter, private_keys)?);
        }
        Ok(items)
    }
}
```

`n_items` is derived from a single felt in the OS output stream and cast to `usize` via `wrap_missing_as`, with no validation against the number of felts actually remaining in `iter`. This mirrors exactly the pattern the report describes for `brace-expansion`: a size/count value coming from untrusted/attacker-influenced input is used to drive an allocation whose magnitude is not checked against the true bound of available data before the allocation is performed.

This is the same class of defect the sequencer team already fixed once, in `crates/apollo_cairo_utils/src/lib.rs`'s `CairoArray::try_from(Retdata)`: [2](#0-1) 

There, the code explicitly checks `num_items > num_remaining_felts` and rejects the input *before* calling `Vec::with_capacity(num_items)`, with an explicit comment: "Validate before allocating to prevent a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`." The `Vec<T>` implementation used throughout `starknet_os/src/io/os_output.rs` and `aggregator/utils.rs` (e.g. `FullOsOutputsData::try_from_output_iter`, `parse_messages_to_l1`, state-diff parsing) does not carry the same guard.

This generic `Vec<T>` parser is used pervasively for parsing the Starknet OS's Cairo-produced output (state diffs, message lists, compiled-class facts, aggregator outputs) in `crates/starknet_os/src/io/os_output.rs` and `crates/starknet_os/src/hints/hint_implementation/aggregator/utils.rs`, all of which feed the OS re-execution / proof-generation and validation pipeline that is explicitly in-scope per the analog rules ("Starknet OS re-execution").

### Impact Explanation
If the felt stream being parsed is not a perfectly well-formed, already-verified OS execution output — e.g., it is read from a persisted/serialized artifact, a PIE output produced by a possibly-corrupted or adversarial prover run, or any path where the felt sequence is not the direct trusted in-memory VM output — a single crafted `n_items` value (up to `usize::MAX`) causes an immediate, unguarded `Vec::with_capacity` allocation request. This can exhaust process memory and crash with a fatal, uncatchable OOM, identical in effect to the reported `brace-expansion` CVE: denial of service against the node/service performing the parse, halting its ability to process further work (proving, re-execution, or output-consumption pipelines) until restarted.

### Likelihood Explanation
Likelihood depends on whether any caller in the OS re-execution/proving pipeline treats the output felt stream as attacker-adjacent (e.g., proof-response parsing, replay of stored/transmitted PIE outputs, or aggregator inputs combining multiple sub-outputs). Multiple call sites (`crates/starknet_os/src/io/os_output.rs`, `crates/starknet_os/src/hints/hint_implementation/aggregator/{implementation,utils}.rs`) invoke this generic decoder on felt sequences that originate from Cairo VM execution outputs, which are not immediately re-verified against the STARK proof before this parsing step runs. I could not fully confirm from the available context whether every call site is strictly limited to freshly-computed, self-trusted VM output versus data that has crossed a network/storage boundary (e.g., aggregator combining multiple provers' outputs) — this is the key uncertainty that would determine whether the reachable trust boundary is genuinely attacker-controlled or only self-produced. Given the explicit prior remediation of the identical pattern in `apollo_cairo_utils`, the codebase's own security posture treats this exact pattern as exploitable when the length field is not locally-trusted.

### Recommendation
Before allocating, bound `n_items` against the number of felts actually remaining in the iterator (or another explicit upper bound derived from protocol constants), mirroring the fix already applied in `apollo_cairo_utils::CairoArray::try_from`: reject with an `OsOutputError` if `n_items` exceeds what the remaining stream could possibly supply, and only then call `Vec::with_capacity(n_items)`.

### Proof of Concept
Conceptual reproduction (parsing path, not a live network PoC since the trust boundary of the felt stream at each call site would need to be confirmed):
```rust
// A felt stream where the declared item count vastly exceeds the actual
// number of felts backing it.
let malicious_felts = vec![Felt::from(usize::MAX), /* stream ends here */];
let mut iter = malicious_felts.into_iter();
// Triggers Vec::with_capacity(usize::MAX) before any data-availability check,
// aborting the process with an OOM (same failure class as brace-expansion's
// expand() OOM).
let _ = Vec::<SomeOutputItem>::try_from_output_iter(&mut iter, None);
```
