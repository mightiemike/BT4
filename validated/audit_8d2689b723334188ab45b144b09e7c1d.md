### Title
Unbounded `PendingInbounds.Walk` in ballot-terminal hook lets an unprivileged attacker force O(n) state scans on every `MsgVoteInbound` finalization - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
`x/uexecutor`'s `afterInboundBallotTerminal` hook (`x/uexecutor/keeper/ballot_hooks.go:72-104`) locates the `PendingInboundEntry` owning a just-finalized ballot by walking the **entire** `PendingInbounds` collection, because ballot IDs are one-way digests and cannot be reversed to a key. This is functionally the same anti-pattern as the SKALE `_generateGroup` report: an unbounded scan over a state collection whose size is influenced by ordinary, cheap, unprivileged user activity, executed synchronously inside a hot, gasless message path (`MsgVoteInbound`).

### Finding Description
- `RecordInboundVote` (`x/uexecutor/keeper/inbound.go:27-88`) creates one `PendingInboundEntry` per distinct `utx_key = sha256(source_chain:tx_hash:log_index)` the first time any validator votes on that inbound. Nothing gates how many distinct source-chain events/log-indices can exist — any external-chain user can generate any number of gateway events (including zero-amount ones, confirmed by `TestInboundZeroAmountFundsAndPayload` in `test/integration/uexecutor/inbound_zero_amount_test.go`), each becoming its own tracked entry.
- `VoteInbound` (`x/uexecutor/keeper/msg_vote_inbound.go:18-158`) is invoked via the gasless `MsgVoteInbound` message (`app/txpolicy/gasless.go:20`), so submitting/voting these events costs no Cosmos Chain fee and consumes essentially no metered gas for the caller.
- When a ballot for one of these inbounds reaches a terminal state, `x/uvalidator`'s `MarkBallotFinalized` fires the `BallotHooks.AfterBallotTerminal` callback, which for `INBOUND_TX` ballots calls `afterInboundBallotTerminal`.
- That function does:
```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [1](#0-0) 
This is an O(n) scan of the full `PendingInbounds` map on **every** terminal ballot transition (PASSED, REJECTED, or EXPIRED), where n is the number of currently-outstanding pending inbound entries. The code's own comment assumes "the pending set is small and transient" [2](#0-1) , but nothing enforces that assumption — an unprivileged actor fully controls the growth of this set by generating many distinct, cheap source-chain events faster than validators can finalize them (or by relying on chains/tokens with slow finality windows, causing long pending windows while more entries accumulate).

This directly mirrors the SKALE `_generateGroup` bug class: a linear scan over a state collection whose size an unprivileged party can inflate is executed inline in a normal, frequently-invoked state-transition path, with no pagination, cap, or reverse index from `ballotID` to `utx_key`.

### Impact Explanation
Because the scan runs synchronously inside `VoteInbound` → `CheckIfFinalizingVote` → `MarkBallotFinalized` → `AfterBallotTerminal`, every `MsgVoteInbound` that finalizes a ballot pays for iterating all currently pending inbound entries. As `PendingInbounds` grows (attacker-inflatable, no size cap, gasless submission path), the per-tx CPU/time cost of finalizing *any* ballot grows linearly and unboundedly. In a Cosmos SDK chain this manifests as increased block-processing time rather than a literal EVM "out-of-gas" revert, but the practical effect is the same DoS class described in the SKALE report: validators finalizing routine crosschain votes could see block-time blowup, degrading throughput or, in the worst case, contributing to missed block deadlines — a network-adjacent but state-transition-triggered availability degradation reachable purely from ordinary (even zero-value) user deposits, not from any privileged or malicious-validator behavior.

This is a materiality question the code doesn't foreclose: there is no maximum entry cap, no expiry-driven eviction independent of ballot finalization, and no indexed lookup from `ballotID → utxKey`. Whether this reaches "halts a block" severity depends on how large `PendingInbounds` can realistically grow before validators finalize entries and how the Cosmos SDK/CometBFT block-time budget accommodates it — this is a scaling/DoS concern rather than a fund-loss or state-corruption bug.

### Likelihood Explanation
Medium. Triggering entry growth requires only ordinary, unprivileged use of the gateway on any enabled source chain (sending deposits, including zero-amount ones which are explicitly supported) — no validator or admin compromise is needed. However, meaningfully large `n` requires sustained volume of distinct inbound events outstanding simultaneously (i.e., created faster than the honest-validator quorum finalizes them), which is achievable but requires sustained attacker throughput and possibly disabling/slowing execution paths on some chains to keep entries pending longer.

### Recommendation
- Replace the reverse-lookup-by-scan with a secondary index mapping `ballotID -> utxKey` (set alongside `RecordInboundVote`, removed alongside `PendingInbounds.Remove`), eliminating the need to walk the whole collection in `afterInboundBallotTerminal`.
- Alternatively/also, bound the size of `PendingInbounds` (e.g., a maximum outstanding-entry cap or a stricter expiry/GC policy) so that even without an index, a walk is bounded.
- Add telemetry/metrics on `PendingInbounds` size to detect abnormal growth in production.

### Proof of Concept
Conceptual (state-growth) PoC, not a fund-theft exploit:
1. An unprivileged user submits N distinct zero-amount (or dust) deposit events on an inbound-enabled source chain, each with a unique `tx_hash`/`log_index` (cheap on low-fee L2s), faster than the UV set can vote them to finalization.
2. Honest Universal Validators observe and vote each event via gasless `MsgVoteInbound`, each creating a new `PendingInboundEntry` (`RecordInboundVote`), growing `PendingInbounds` to size N.
3. Once any one ballot finalizes, `afterInboundBallotTerminal` performs a `Walk` over all N entries to find the matching one — this cost is paid on the block that processes that `MsgVoteInbound`, and repeats for each subsequent finalizing vote while N remains large.
4. Repeating step 1 continuously keeps N large, so every future inbound finalization pays the O(N) cost, degrading block-processing time as N scales — the same class of issue as SKALE's unbounded `_generateGroup` iteration.
