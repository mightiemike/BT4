### Title
L1 handler transaction is marked "consumed" even when its execution fails outright, permanently burning the L1→L2 message without applying its effects - ([File: crates/apollo_batcher/src/block_builder.rs])

### Summary
The reported bug class is: a system computes an amount it must transfer/settle (e.g. `totalUnderlying()`), but the actual resources it can draw on don't match, so a *mandatory* action fails unexpectedly — and once it fails there is no retry path, causing funds to be effectively lost. The closest reachable analog in this sequencer is in L1-handler processing: `L1HandlerTransaction::execute_raw` enforces a resource-bound check (`l1_handler_max_amount_bounds`) and a "paid fee" check against the *actual* gas/fee consumed, but the transaction has already been irrevocably consumed on L1 (its nonce was bumped in the StarknetCore contract when the message was sent). If the transaction's *actual* required resources exceed the fixed `l1_handler_max_amount_bounds`, or the (currently placeholder, hardcoded) `paid_fee_on_l1` check fails, execution errors out (`Err`, not merely "reverted"), yet the batcher's block builder still records the transaction hash in `consumed_l1_handler_tx_hashes`, i.e. it is treated as consumed regardless of whether the underlying `TransactionExecutorResult` was `Ok` or `Err`.

### Finding Description
`L1HandlerTransaction::execute_raw` (crates/blockifier/src/transaction/l1_handler_transaction.rs:55-144) runs the L1 handler's `execute` call, computes its `TransactionReceipt`, and checks the receipt's gas usage against `l1_handler_max_amount_bounds` (crates/blockifier/src/transaction/l1_handler_transaction.rs:92-96). If the resource check passes but `paid_fee_on_l1 == Fee(0)`, the code path at lines 98-113 already committed the sub-state (`execution_state.commit()`, line 100) and then returns `Err(TransactionExecutionError::TransactionFeeError(...))` instead of returning a "reverted" `TransactionExecutionInfo` (as is done for the resource-bound failure branch at lines 117-129, or for execution errors at 132-141). This is inconsistent with the reverted-l1-handler path, which explicitly builds a `Fee(0)`-receipt `Ok(...)` result that keeps the transaction "processed" in a well-defined, revertible way.

Critically, `paid_fee_on_l1` is currently a hardcoded placeholder value (see `crates/apollo_transaction_converter/src/transaction_converter.rs:473-485` and `crates/apollo_rpc/src/v0_8/api/mod.rs:415-429`, both marked `// TODO(Gilad): Change this once we put real value in paid_fee_on_l1.`), so in the current build the `Fee(0)` branch is effectively unreachable/inert; but the same "commit-then-error" structural pattern applies to *any* code path in `execute_raw` that returns an outright `Err` (e.g. `StateError`s, as demonstrated in the test `failed_l1_handler_transaction_consumed`, crates/apollo_batcher/src/block_builder_test.rs:1064-1111). In that test, one L1 handler transaction execution result is `Err(TransactionExecutorError::StateError(...))`, yet `result_block_artifacts.execution_data.consumed_l1_handler_tx_hashes` includes *all* of the L1 handler transaction hashes fed to the executor, regardless of whether they succeeded or errored.

Because L1 handler transactions represent messages that are already irrevocably consumed on L1 (their L1 nonce has already advanced, and the L2 sequencer has no mechanism to "resend" or "retry" the message once it decides to mark it as processed on L2), any systematic condition that causes the L1 handler's execution to return an outright `Err` — rather than a well-formed reverted receipt — results in a message being recorded as consumed while none of its intended state effects (and no compensating fee/refund) are applied and while the transaction is excluded from further processing.

### Impact Explanation
If an unprivileged L1 message sender (anyone can call `sendMessageToL2` on the L1 StarknetCore contract) can construct an L1→L2 message whose induced entry-point call, when interpreted by the L2 sequencer, causes `execute_raw` to return `Err` (e.g., by triggering `StateError` conditions, or any other error variant not funneled through the "reverted" branch), the corresponding deposit/bridge message is permanently and silently dropped from L2 state while being marked "consumed" and thus never retriable. This is a concrete freezing-of-funds scenario: L1 assets locked/burned for the L2 message are never credited on L2, and the consumption bookkeeping prevents any future remediation via reprocessing.

### Likelihood Explanation
The trigger requires only sending an L1→L2 message with calldata/target chosen so that the induced call errors deep inside execution in a way that is not captured by the standard "reverted" receipt path (the code demonstrates this is possible — see the `StateError` case exercised directly in the block-builder test). No special privileges are needed: any L1 account can call the bridge/messaging entry point on the StarknetCore contract to originate such a message.

### Recommendation
Ensure `L1HandlerTransaction::execute_raw` never returns a bare `Err` due to a post-execution/fee-accounting condition after `execution_state.commit()` has already been called; instead it should always produce a well-defined `Ok(reverted receipt)` outcome (mirroring the resource-bound-exceeded branch) so downstream consumers uniformly treat "processed but reverted" vs. "not processed" transactions, and audit/gate `consumed_l1_handler_tx_hashes` bookkeeping in `apollo_batcher::block_builder` so that a transaction is only marked consumed when its execution genuinely produced a receipt (successful or reverted), never when the executor itself returned a hard `Err`.

### Proof of Concept
Not independently reproducible from static analysis alone — the existing repository test `failed_l1_handler_transaction_consumed` (crates/apollo_batcher/src/block_builder_test.rs:1064-1111) already demonstrates the core defect: it mocks one L1 handler transaction's execution result as `Err(TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress))` and shows that the block builder still includes that transaction's hash in `execution_data.consumed_l1_handler_tx_hashes`. Confirming a concretely triggerable, unprivileged path to that specific `Err` from real message calldata (as opposed to the mocked test) was not completed within the available tool budget, and should be verified further by a background agent by tracing which `StateReader`/execution errors are reachable from attacker-controlled L1 message calldata during `run_execute` in `l1_handler_transaction.rs`.
