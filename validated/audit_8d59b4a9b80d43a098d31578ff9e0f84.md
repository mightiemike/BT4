Now this makes the picture clear: the "Virtual OS Output" (`VIRTUAL_SNOS0` format) that the proof facts commit to is `[output_version, base_block_number, base_block_hash, starknet_os_config_hash, n_l2_to_l1_messages, message_hash_0, ...]` [1](#0-0) . This output does **not** include the transaction's sender address, nonce, calldata, or transaction hash — it only commits to the base block, the OS config hash, and L2-to-L1 message hashes. The blockifier-side check (`validate_proof_facts`) only validates `program_hash`, `proof_version`, `block_number`/`block_hash`, and `config_hash` — none of which are bound to the specific submitting account [2](#0-1) , and the Cairo-side `check_proof_facts` performs the identical checks [3](#0-2) .

The gateway/consensus proof-reuse guard (`contains_proof`/`set_proof` in `apollo_proof_manager`, invoked from `run_proof_verification`) keys solely on the `proof_facts` hash, again with no binding to sender/nonce/calldata: [4](#0-3) . Once one user's transaction has verified and stored `(proof_facts, proof)`, any other transaction (any `sender_address`, `calldata`, `nonce`) that includes that exact `proof_facts`/`proof` pair passes `contains_proof` and skips re-verification, and then passes `validate_proof_facts` in the blockifier during both gateway validation and OS execution, because none of those checks tie the proof to the transaction that produced it.

This is a structural analog of the report's "signature reuse via front-running": in the NFT contract, the whitelist signature was checked for validity and marked used, but not bound to `msg.sender`, letting anyone front-run and consume someone else's code; here, the proof_facts/proof pair is checked for validity (via `contains_proof`/`verify_proof`) and is implicitly treated as a one-time credential (via `set_proof`), but nothing in the verified data or the pre-validation checks binds the proof to the sender address, nonce, or calldata of the transaction that submits it.

### Title
Client-side proving (`proof_facts`/`proof`) is not bound to the submitting transaction, enabling front-running/theft of another user's proof - (File: `crates/blockifier/src/transaction/account_transaction.rs`)

### Summary
`ProofFacts`/`Proof` pairs generated by the `VirtualSnosProver` for client-side proving are treated by the sequencer as a reusable, transferable credential: once accepted, `contains_proof` short-circuits re-verification for any future transaction presenting the identical `proof_facts` bytes, and `validate_proof_facts` only checks block/config/program-hash validity — never the sender, nonce, or calldata of the transaction carrying it.

### Finding Description
The virtual-OS output format that is proven and hashed into `proof_facts` is fixed as `[output_version, base_block_number, base_block_hash, starknet_os_config_hash, n_l2_to_l1_messages, message_hash_i...]` [1](#0-0) . It contains no field committing to which account address, nonce, or calldata the proof was generated for. Downstream validation in `AccountTransaction::validate_proof_facts` only checks `proof_version`, `program_hash`, `block_number`/`block_hash`, and `virtual_os_config_hash` [2](#0-1) , and the identical set of checks is repeated inside the Starknet OS Cairo program (`check_proof_facts`) [3](#0-2) . Separately, the gateway/consensus flow uses `contains_proof(proof_facts)` keyed purely by the `proof_facts` hash to decide whether re-verification of the (expensive) proof can be skipped, and `set_proof` to persist it once verified [5](#0-4) . Nowhere in this pipeline is the proof cryptographically or structurally tied to a specific `sender_address`, `nonce`, or `calldata`. Since `proof_facts`/`proof` are plain fields on a broadcast `RpcInvokeTransactionV3` visible in the mempool/p2p layer, any observer can lift a valid `(proof_facts, proof)` pair from a pending transaction and attach it to their own transaction (different sender, different calldata, different nonce) submitted through the gateway before the original transaction is included.

### Impact Explanation
An attacker who copies another user's `proof_facts`/`proof` can get their own, unrelated transaction accepted through client-side proving path without incurring the cost of legitimately proving anything, and, more importantly, can front-run the original prover/submitter and consume the proof-manager's stored credential for the observed block/output first. Because the checked fields (block hash/number, OS config hash, program hash) are generic and not user-specific, this effectively strips any per-user authorization or accounting semantics that the proof might have been intended to enforce, and lets an unprivileged transaction sender bypass whatever guarantee client-side proving was meant to provide for a completely different account/calldata. This is analogous to the discounted-NFT signature theft in the report: a credential meant to authorize one party's specific action is reusable by anyone who observes it in-flight.

### Likelihood Explanation
Any transaction with non-empty `proof_facts`/`proof` is publicly visible once broadcast to the gateway/mempool/p2p layer, exactly like the NFT whitelist signature reused from a mempool-visible transaction. No special privileges are required — a single unprivileged transaction sender can observe the pending transaction and race a new invoke transaction to the gateway carrying the same `proof_facts`/`proof`. This requires `allow_client_side_proving` to be enabled in gateway config, which gates the feature but does not change the underlying binding gap once enabled [6](#0-5) .

### Recommendation
Bind the proof to the specific transaction it is meant to authorize by including transaction-identifying data (e.g., sender address, nonce, and/or a commitment to calldata) in the virtual-OS output that gets hashed into `proof_facts`, and verify that binding in `validate_proof_facts` (and the Cairo `check_proof_facts`) against the actual `tx_info` of the transaction carrying it, in addition to the existing block/program/config-hash checks. Alternatively, key the proof-manager's `contains_proof`/`set_proof` cache and the on-chain acceptance check by `(proof_facts, sender_address, nonce)` rather than `proof_facts` alone, so a proof cannot be transplanted onto a different account's transaction.

### Proof of Concept
1. User A submits an `Invoke` V3 transaction with `sender_address = A`, valid `nonce`, `calldata_A`, and a legitimately generated `proof_facts`/`proof` pair (from `VirtualSnosProver`) to the gateway; it passes `validate_client_side_proving_allowed`/`validate_proof_facts_and_proof_consistency` [7](#0-6)  and enters the mempool.
2. Attacker M observes the pending transaction (via mempool p2p broadcast or RPC), extracts the identical `proof_facts` and `proof` byte arrays.
3. M crafts their own `Invoke` V3 transaction with `sender_address = M`, `nonce_M`, arbitrary `calldata_M`, reusing the copied `proof_facts`/`proof`, and submits it to the gateway with higher fee/tip to be prioritized ahead of A's transaction.
4. `run_proof_verification` calls `contains_proof(proof_facts)` [8](#0-7) ; if A's proof hasn't been stored yet, M's tx re-verifies the (valid) proof and `set_proof` stores it under M's request, or if it's already stored, M's tx passes `contains_proof` immediately.
5. `AccountTransaction::validate_proof_facts` and the OS's `check_proof_facts` accept M's transaction because none of the checked fields (`program_hash`, `block_hash`, `config_hash`) differ between A's and M's copied proof, despite M being a completely different sender with different calldata/nonce [9](#0-8) .

    fn validate_proof_facts(
        &self,
        block_context: &BlockContext,
        state: &mut dyn State,
    ) -> TransactionPreValidationResult<()> {
        // Only Invoke V3 transactions can carry proof facts.
        let Transaction::Invoke(invoke_tx) = &self.tx else {
            return Ok(());
        };
        if invoke_tx.version() < TransactionVersion::THREE {
            return Ok(());
        }

        // Parse proof facts.
        let proof_facts = invoke_tx.proof_facts();
        let snos_proof_facts = match ProofFactsVariant::try_from(&proof_facts)
            .map_err(|e| TransactionPreValidationError::InvalidProofFacts(e.to_string()))?
        {
            ProofFactsVariant::Empty => return Ok(()),
            ProofFactsVariant::Snos(snos_proof_facts) => snos_proof_facts,
        };
        let os_constants = &block_context.versioned_constants.os_constants;

        if !os_constants.allowed_proof_versions.contains(&snos_proof_facts.proof_version.as_felt())
        {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Proof version {} is not allowed under this protocol version.",
                snos_proof_facts.proof_version
            )));
        }

        // Validate the program hash.
        let allowed = &os_constants.allowed_virtual_os_program_hashes;
        if !allowed.contains(&snos_proof_facts.program_hash) {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS program hash {} is not allowed",
                snos_proof_facts.program_hash
            )));
        }

        // Validate the block hash and block number.
        let proof_block_hash = snos_proof_facts.block_hash.0;
        let proof_block_number = snos_proof_facts.block_number.0;
        Self::validate_proof_block_number(
            proof_block_number,
            block_context.block_info.block_number,
        )?;
        Self::validate_proof_block_hash(proof_block_hash, proof_block_number, os_constants, state)?;

        // Validate the config hash.
        let virtual_os_config_hash = block_context.virtual_os_config_hash();
        let proof_config_hash = snos_proof_facts.config_hash;
        if virtual_os_config_hash != proof_config_hash {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS config hash mismatch. Computed virtual OS config hash: \
                 {virtual_os_config_hash}, expected virtual OS config hash: {proof_config_hash}."
            )));
        }

        Ok(())

    /// Runs proof verification: checks if the proof already exists, and if not, verifies it.
    /// Returns `true` if verification was performed, `false` if skipped (proof already stored).
    /// This is the shared verification logic used by both gateway and consensus flows.
    async fn run_proof_verification(
        proof_facts: ProofFacts,
        proof: Proof,
        proof_manager_client: SharedProofManagerClient,
    ) -> Result<bool, TransactionConverterError> {
        let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;

        if contains_proof {
            return Ok(false);
        }

        let proof_facts_hash = proof_facts.hash();
        let verify_start = Instant::now();
        tokio::task::spawn_blocking(move || {
            starknet_proof_verifier::verify_proof(proof_facts, proof)
        })
        .await
        .expect("proof verification task panicked")?;
        let verify_duration = verify_start.elapsed();
        PROOF_VERIFICATION_LATENCY.record(verify_duration.as_secs_f64());
        info!(
            "Proof verification took: {verify_duration:?} for proof facts hash: \
             {proof_facts_hash:?}"
        );

        Ok(true)
    }

    fn validate_client_side_proving_allowed(
        &self,
        tx: &RpcInvokeTransaction,

        if self.config.allow_client_side_proving {

        // Reject V3 transactions with proofs when client-side proving is disabled.

        Ok(())
