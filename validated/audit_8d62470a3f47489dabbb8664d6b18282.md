### Title
`socialize-debt` computes bad-debt write-down using stale, un-accrued `index`/`total-assets` - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`socialize-debt` in the Zest vault contracts reads `(var-get index)` and derives `old-total-assets` via `total-assets` directly, without first calling `(accrue)` as every other state-mutating vault entry point does. This means the debt figure used to write down the liquidity index (`lindex`) can be understated by exactly the interest that accrued since `last-update`, causing LP shares to absorb a larger-than-correct loss when bad debt is socialized.

### Finding Description
Every other public, state-mutating function in the vault contracts (`redeem`, `system-borrow`, `system-repay`, `flashloan`) begins its `let` binding list with `(u (try! (accrue)))` before reading `(var-get index)`, guaranteeing the index reflects interest accrued up to the current block: [1](#0-0) 

`accrue` recomputes and persists the updated `index`/`lindex` based on elapsed time since `last-update`: [2](#0-1) 

`socialize-debt`, however, omits this call entirely. It reads `idx` and computes `old-total-assets` straight from the stored (potentially stale) `index` via `total-assets`, which itself uses `(var-get index)` rather than the accrued `next-index`: [3](#0-2) [4](#0-3) 

If real time has elapsed since the last `accrue` call (e.g., no user has borrowed/repaid/deposited/redeemed/flash-loaned in the interim), `var-get index` is a cached value whose source — elapsed time / accrued interest — has moved without the cache being invalidated. `socialize-debt` uses this stale, understated `index` to compute both `debt-reduction` and `old-total-assets`, then writes `new-lindex` proportionally to `(old-total-assets - debt-reduction) / old-total-assets`. Because `old-total-assets` is understated (missing accrued-but-uncrystallized interest), the same `debt-reduction` represents a larger fraction of the (too-small) `old-total-assets`, so `new-lindex` is written down further than the true economics warrant. This directly reduces the redemption value of every zToken holder's shares beyond the actual loss being socialized.

This is a single-transaction analog to the report's underlying bug class: an index/balance value cached from a prior update is used without being re-derived from its true current source (time-elapsed interest) before being consumed in a value-transferring calculation.

### Impact Explanation
LP token holders (zToken holders) suffer an incorrect, excessive write-down of their share value whenever `socialize-debt` is invoked after any period without an intervening `accrue`-triggering action. This is a form of temporary/permanent freezing or theft of unclaimed yield: the interest that had accrued but was not yet crystallized into `index`/`assets` is effectively erased and the loss overstated onto every existing LP, rather than the actual bad debt being socialized correctly. This falls under the in-scope Critical/High impact class of theft or permanent loss of unclaimed yield affecting protocol solvency accounting for LPs.

### Likelihood Explanation
Reachable whenever the market contract calls `socialize-debt` on a vault to write off bad debt (this is a normal liquidation-shortfall code path, not an edge case) and some time has passed since the last accrual-triggering vault interaction. No attacker interference with other users is required — the discrepancy arises purely from the missing `accrue` call inside this one function, satisfying the single-transaction/single-block analog criteria.

### Recommendation
Add `(try! (accrue))` as the first binding in `socialize-debt`, mirroring `system-borrow`/`system-repay`/`redeem`/`flashloan`, and use the accrued `index`/`total-assets` (post-`accrue`) for `debt-reduction` and `old-total-assets` calculations so the write-down reflects the true, up-to-date solvency position across all vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`).

### Proof of Concept
1. At time `T0`, a vault's `last-update` is set and `index = I0` after some borrow/repay activity.
2. No further borrow/repay/redeem/deposit/flashloan occurs for a period `Δt` (interest accrues in principle but `index` is never persisted because `accrue` is never invoked).
3. At time `T0+Δt`, the market contract calls `.vault.socialize-debt(scaled-amount)` to write off a defaulted position's bad debt.
4. `socialize-debt` reads `idx = I0` (stale) and computes `old-total-assets` via `total-assets`, which also uses the stale `I0`, understating the true total assets by the uncrystallized interest accrued over `Δt`.
5. `new-lindex` is computed as `current-lindex * (old-total-assets - debt-reduction) / old-total-assets`, using the understated `old-total-assets`, producing a larger writedown ratio than correct.
6. `lindex` is persisted with this excessively reduced value, permanently reducing the redemption value for all zToken holders beyond the actual bad debt amount, without ever running the compensating `accrue` step to restore the accrued interest that was ignored.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
