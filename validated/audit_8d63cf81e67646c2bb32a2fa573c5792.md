### Title
Unauthenticated `shop` Query Parameter Trusted to Mint Full-Privilege Merchant-Custom-App Session - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`)

### Summary
For merchant custom apps (`AppDistribution.ShopifyAdmin`), the admin authentication path extracts the `shop` value directly from the request URL's query string without any cryptographic verification (no HMAC, no session-token signature, no cookie check tying it to the caller), and hands that untrusted value to `MerchantCustomAuth.authenticate`, which calls `api.session.customAppSession(shop)` to synthesize a session carrying the app's configured `adminApiAccessToken`.

### Finding Description
In `getSessionTokenContext` (`packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`), when `config.distribution === AppDistribution.ShopifyAdmin`, the code takes a shortcut: it never validates a session token for this distribution type. Instead:
```
const url = new URL(request.url);
const shop = url.searchParams.get('shop')!;

const sessionId = await api.session.getCurrentId({
  isOnline: config.useOnlineTokens,
  rawRequest: request,
});

return {shop, sessionId, payload: undefined, sessionToken};
``` [1](#0-0) 

The returned `shop` is entirely attacker-controlled — it is read verbatim from `url.searchParams.get('shop')`, with no `sanitizeShop`, HMAC, or session-token/JWT `dest` cross-check as is done in the non-ShopifyAdmin branch just above it (which derives `shop` from a cryptographically validated JWT `payload.dest`) [3](#0-2) .

This `shop` value flows into `MerchantCustomAuth.authenticate`:
```
public async authenticate(
  _request: Request,
  sessionContext: SessionContext,
): Promise<Session | never> {
  const {shop} = sessionContext;
  const session = this.api.session.customAppSession(shop);
  return session;
}
``` [2](#0-1) 

`customAppSession(shop)` builds a `Session` whose `shop` field is whatever string was supplied (only format-validated by `sanitizeShop`, not authenticated) [4](#0-3) . This session is then used to construct the admin GraphQL/REST client, which authenticates to Shopify using the single statically configured `adminApiAccessToken` for the whole app, targeted at whatever `shop` domain the attacker put in the URL [5](#0-4) .

This is directly analogous to the BaseVault bug class: the code trusts an attacker-supplied identifier (here, `shop` from the query string, analogous to the `_from` parameter in `batchDepositERC20`/`batchDepositERC721`/`batchDepositERC1155`) to select which "account" (tenant/session) a privileged operation acts on, instead of deriving that identity strictly from an authenticated channel (the equivalent of `msg.sender`).

### Impact Explanation
A merchant-custom-app deployment (single-tenant, `distribution: AppDistribution.ShopifyAdmin`) is expected to only ever operate against one shop domain, using its single configured `adminApiAccessToken`. Because the `shop` value used to build the outgoing `Session.shop` is taken unauthenticated from the request query string, any caller who can reach the app's admin routes can supply an arbitrary `?shop=other-shop.myshopify.com` and cause the app to issue Admin API requests to that other shop domain using the app's `adminApiAccessToken`/HMAC secret pairing. Depending on how downstream code uses `context.session.shop` (e.g., logging, webhook registration, billing calls, or any app logic keyed off `session.shop`), this can lead to cross-tenant confusion, SSRF-like requests to attacker-chosen `*.myshopify.com` hosts using the app's credentials, or logic bypasses that assume `session.shop` reflects the actual authenticated store.

### Likelihood Explanation
This code path only affects apps configured with `distribution: AppDistribution.ShopifyAdmin` (merchant custom apps) — a distinct, less common deployment mode compared to standard embedded/public apps that go through the session-token or auth-code/token-exchange strategies (which are properly HMAC/JWT-validated, as observed in `getSessionTokenContext`'s other branch and in `oauth.ts`/`hmac-validator.ts`). Any unauthenticated HTTP request to an `authenticate.admin`-protected route of such an app can trigger this, requiring no privileged actor, no leaked secret, and no MITM — only knowledge that the app uses this distribution mode.

### Recommendation
For the `AppDistribution.ShopifyAdmin` branch in `getSessionTokenContext`, do not trust `url.searchParams.get('shop')` for identifying the tenant used to build the session. Either: (1) use the shop configured/pinned in `config` for the merchant custom app (since this distribution mode is meant for exactly one shop) rather than any request-supplied value, or (2) validate the query-string `shop` against the app's configured shop (or an HMAC-signed value) before using it in `customAppSession`, matching the rigor applied to the JWT-based branch above it in the same function.

### Proof of Concept
1. Deploy a `shopify-app-remix`/`shopify-app-react-router` app with `distribution: AppDistribution.ShopifyAdmin` and a configured `adminApiAccessToken`.
2. Send a GET request to any route wrapped by `authenticate.admin` with `?shop=victim-or-arbitrary-shop.myshopify.com` (no valid session token needed, since this branch skips `validateSessionToken`).
3. Observe that `getSessionTokenContext` returns `{shop: 'victim-or-arbitrary-shop.myshopify.com', ...}` [6](#0-5) , which `MerchantCustomAuth.authenticate` uses to build `customAppSession('victim-or-arbitrary-shop.myshopify.com')` [7](#0-6) , causing subsequent Admin API calls to target that attacker-chosen shop domain using the app's static access token.
