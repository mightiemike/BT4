### Title
Wall-clock-based OUT_OF_TIME determination in TVM execution allows hardware-dependent consensus divergence in `TransactionTrace.check()` - ([File: chainbase/src/main/java/org/tron/core/db/TransactionTrace.java])

### Finding Description
`Program.checkCPUTimeLimit()` computes the CPU deadline from `System.nanoTime()` wall-clock time (`vmStartInUs`/`vmShouldEndInUs`) rather than from a deterministic, hardware-independent metric such as opcode/energy count. [1](#0-0) 
This value feeds `ProgramResult`, which becomes the local node's `receipt.getResult()` via `RuntimeImpl`/`VMActuator`, while the block's `trx.getContractRet()` is fixed once-and-for-all by whichever node produced the block. `TransactionTrace.checkNeedRetry()` only compensates for the specific case where the local run is `OUT_OF_TIME` while the block says otherwise, by re-executing once: [2](#0-1) 
After that single retry, `TransactionTrace.check()` performs a strict equality comparison between the consensus-agreed `trx.getContractRet()` and the locally recomputed `receipt.getResult()`, throwing `ReceiptCheckErrException` on any mismatch, with zero tolerance for timing variance: [3](#0-2) 
This check is invoked from `Manager.processTransaction()` for every block with a witness signature, i.e., during normal block validation by every full node re-executing the block's transactions: [4](#0-3) 
An unprivileged attacker can submit ordinary `TriggerSmartContract`/`CreateSmartContract` transactions whose bytecode is crafted to consume CPU time close to `vmShouldEndInUs` (derived from `getMaxCpuTimeOfOneTx()` and time ratios in `VMActuator.call()`). If node CPU speed (or JIT warm-up state, GC pauses, load) differs across honest validators, some nodes will finish just under the deadline (any non-`OUT_OF_TIME` result) and others just over it (`OUT_OF_TIME`), for the exact same deterministic bytecode/input. The single retry in `checkNeedRetry()` only mitigates transient jitter in one direction (local slow-then-fast); a node that is persistently slower hardware will still fail on retry and hit the strict-equality `check()`, throwing `ReceiptCheckErrException` and failing to process the block that all faster nodes have already accepted.

### Impact Explanation
A `ReceiptCheckErrException` thrown out of `Manager.processTransaction()` propagates through block application, causing that node to fail applying the otherwise-valid, signed block — the scoped impact is invalid state divergence between honest nodes (some accept the block, some can't) and repeated halt on the affected node(s) for every re-application of that block (e.g., on resync/replay), a self-inflicted denial of service / consensus-safety violation triggered purely by a normal, unprivileged transaction with borderline execution timing.

### Likelihood Explanation
This requires: (1) an attacker able to submit ordinary bytecode with a deterministic execution time straddling the CPU-time-limit boundary (fully achievable by looping to consume a target number of opcodes/energy, calibrated near `getMaxCpuTimeOfOneTx()`), and (2) heterogeneous, honest-node hardware/load causing one node's wall-clock elapsed time to cross the threshold while another's does not. This is a realistic and repeatable condition in any real multi-node deployment with differing CPU speeds, JIT states, or transient load (GC pauses), and does not require any privileged access — only a normal transaction submission with a carefully timed contract. The one-shot retry in `checkNeedRetry()` reduces but does not eliminate the risk, particularly for nodes that are consistently, not just transiently, slower.

### Recommendation
Replace or supplement the wall-clock CPU-time check with a deterministic, hardware-independent cost metric (e.g., energy/opcode count with a fixed instruction-time model) so that `receipt.getResult()` for `OUT_OF_TIME` is a function purely of the deterministic execution trace and not of host performance. Alternatively, treat `OUT_OF_TIME` divergence in `check()` as a non-fatal condition that triggers block re-sync from a trusted source instead of throwing a hard exception that halts local block application, and widen/adjust the retry logic to also cover the case where local execution unexpectedly succeeds when the block says `OUT_OF_TIME` (currently only one direction is retried).

### Proof of Concept
Java integration test plan (build on existing `BandWidthRuntimeOutOfTimeWithCheckTest`/`TransactionTrace` test utilities):
1. Deploy a contract whose method executes a tight loop calibrated (via `TimeBenchmarkTest`-style measurement) to consume CPU time equal to `~99%` of `getMaxCpuTimeOfOneTx()` on a "fast" simulated `vmShouldEndInUs` deadline.
2. Using `TvmTestUtils.processTransactionAndReturnTvmTestResult`, execute the transaction twice with two different simulated clock speeds (mock `System.nanoTime` deltas or scale the loop iteration count) to represent a fast producer node (`receipt.getResult()==SUCCESS`) and a slow validator node (`receipt.getResult()==OUT_OF_TIME`).
3. Take the `Transaction` produced by the "fast" run (with `contractRet` baked in as `SUCCESS`), and feed it — with `blockCap.hasWitnessSignature()==true` — into a second `TransactionTrace`/`Manager.processTransaction` execution instrumented to behave like the "slow" node.
4. Assert that `trace.check()` throws `ReceiptCheckErrException` even though `checkNeedRetry()` was exercised, demonstrating that persistent hardware speed differences (not just transient jitter) break the single-retry mitigation and diverge `receipt.getResult()` from `trx.getContractRet()`.

  public boolean checkNeedRetry() {
    if (!needVM()) {
      return false;
    }
    return trx.getContractRet() != contractResult.OUT_OF_TIME && receipt.getResult()
        == contractResult.OUT_OF_TIME;
  }

      throw new ReceiptCheckErrException(
          String.format("null resultCode id: %s", trx.getTransactionId()));

      throw new ReceiptCheckErrException(String.format(
          "different resultCode txId: %s, expect: %s, actual: %s",
