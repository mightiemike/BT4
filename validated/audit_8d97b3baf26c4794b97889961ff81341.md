## Analysis Summary

The DIMO report reduces to one integrity invariant: **when a system checks an untrusted/derived output against an authenticated baseline for equivalence, that check must cover every field that is cryptographically bound in the baseline — an incomplete equivalence check lets divergent state pass as validated.**

I evaluated four candidate Aptos-native analogs (write-set → storage-change-set conversion, `WriteOpConverter::convert`, `TransactionAccumulatorSummary` consistency checks, and `TransactionOutput::ensure_match_transaction_info`) and traced their invariants. The first three enforce complete, symmetric checks (duplicate-key rejection, metadata/op-kind matching, and version+root-hash consistency). The fourth has a documented, provable gap.

### Title
Incomplete equivalence check in `ensure_match_transaction_info` lets replay-verify accept a divergent state-checkpoint root - (File: `types/src/transaction/mod.rs`)

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the function used to assert that a re-executed `TransactionOutput` matches the authenticated `TransactionInfo` (the object hashed into the transaction accumulator and covered by validator signatures on the `LedgerInfo`). It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against anything derived from the locally-replayed state. [1](#0-0) 

The code itself documents this omission: [2](#0-1) 

This function is the sole correctness gate used by the archive replay-verification tool: it feeds the locally re-executed `TransactionOutput` and the archived/authenticated `TransactionInfo` straight into `ensure_match_transaction_info` with no additional state-root comparison. [3](#0-2) 

`state_checkpoint_hash` is populated with the actual state (Sparse-Merkle/JMT) root at checkpoint boundaries and is what gets accumulated and signed as part of the `LedgerInfo`, exactly analogous to production block-building logic: [4](#0-3) 

Because `write_set_hash` only certifies the *content of the write set*, not the *resulting global state root*, a bug in state-tree construction (JMT/SMT update logic, sharded state application, or hot-state promotion) that produces an identical write set but a different resulting state root would be completely invisible to this check.

### Impact Explanation
This maps directly to the allowed "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact class. `ensure_match_transaction_info` is the mechanism by which Aptos verifies historical chain correctness against archived, validator-signed data (used by `db-tool replay-on-archive`, the CLI debugger, and `aptos-debugger`). If a state-root computation bug exists anywhere in the executor/storage stack (independent from write-set materialization), this comparator would report "replay successful" even though the authenticated state-checkpoint root diverges from what was actually committed and signed by validators — masking a genuine consensus/state-integrity fork from the very tooling designed to catch it. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
This is not a hypothetical: the code contains a first-party acknowledgment that the exact scenario ("authenticated position state root diverges from local execution") is currently unguarded and is explicitly deferred pending `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. Any correctness bug in the (independently evolving) state-tree/hot-state code paths that preserves write-set bytes but alters the derived root would trigger this blind spot with certainty, since no code path currently compares checkpoint hashes in `ensure_match_transaction_info`.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute the resulting state-checkpoint root (and hot-state/position checkpoint roots, where applicable) from the replayed output plus the pre-transaction state view, and assert equality against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` whenever those fields are `Some`. This must land before (or as a hard prerequisite of) enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, since only then does the field become load-bearing.

### Proof of Concept
1. Assume any latent defect in the JMT/hot-state update logic that changes the computed root hash for a given (pre-state, write-set) pair without altering the write-set itself (e.g., an ordering or sharding bug in state-value application).
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`, `execute_and_verify`) over the affected version range.
3. `AptosVMBlockExecutor::execute_block` produces a `TransactionOutput` whose `write_set` byte-for-byte matches history (so `state_change_hash` matches), but whose real resulting state root differs from the archived `state_checkpoint_hash`.
4. `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139) returns `Ok(())` because it never inspects `state_checkpoint_hash`, so `execute_and_verify` records no failure — the divergence is silently swallowed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
