This is a genuine analog of the Blend "utilization check present on one side, missing on the sibling side" bug class.

### Title
`IsChainOutboundEnabled` gate is enforced for forward outbound creation but missing for revert outbound creation, letting an unprivileged user bypass an outbound-disable safety control - (File: `x/uexecutor/keeper/build_revert_outbound.go`)

### Summary
`x/uexecutor` enforces `IsChainOutboundEnabled` before creating a *forward* outbound in `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:50-57`), but the sibling code path that creates a *revert* outbound — `buildRevertOutbound` (`x/uexecutor/keeper/build_revert_outbound.go:10-56`) — never checks `IsChainOutboundEnabled` for the destination chain before returning a `PENDING` `OutboundTx`. This mirrors the Blend finding exactly: an invariant check ("outbound must not be created for chains that have outbound disabled") exists on one code path that mutates the protected resource (`PendingOutbounds`) but is missing on a semantically equivalent path that mutates the same resource.

### Finding Description
`x/uregistry` exposes a chain-level toggle, `ChainEnabled.IsOutboundEnabled`, checked via `IsChainOutboundEnabled` [1](#0-0) . This flag is used as an operational safety gate: `x/utss`'s `InitiateFundMigration` explicitly *requires* outbound to be disabled for a chain (`"outbound is still enabled"` error) and requires no pending outbounds exist for that chain before a TSS fund migration away from an old key can start [2](#0-1) , confirmed by the integration test `TestInitiateFundMigration` / `"Fails if outbound is still enabled"` [3](#0-2) .

The forward-outbound creation path correctly enforces this gate: `BuildOutboundsFromReceipt` checks `IsChainOutboundEnabled` and hard-fails (`"outbound is disabled for chain %s"`) before building an `OutboundTx` [4](#0-3) , and this is covered by `TestOutbound_ChainEnabled` [5](#0-4) .

However, `buildRevertOutbound` — invoked from every inbound-execution-failure path (`execute_inbound_funds.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, and `handle_failed_inbound_validation.go`) as well as the admin `RevertStuckInbound` flow — builds and returns a `types.OutboundTx` with `OutboundStatus_PENDING` targeting `inbound.SourceChain` with **no call to `IsChainOutboundEnabled`** at all [6](#0-5) . The resulting outbound is attached via `attachOutboundsToUtx`, which indexes it into `PendingOutbounds` the same way a forward outbound would be (as documented, `PendingOutbounds` is removed "ONLY when validators reach consensus", regardless of the type of outbound) [7](#0-6) .

An unprivileged attacker (any external-chain sender) can trigger inbound-execution failure deterministically and for free, e.g. by submitting a zero-amount `GAS`/`FUNDS` inbound, which `ValidateForExecution` rejects with `"amount must be positive for this tx type"` and which always attaches an `INBOUND_REVERT` outbound for non-CEA inbounds [8](#0-7) ; the reject path is entirely driven by attacker-supplied `Inbound` data validated by honest Universal Validators, requiring no privileged action. This forces a new `PENDING` entry into `PendingOutbounds` for the source chain even while that chain has been intentionally disabled for outbound via `x/uregistry` (e.g., specifically to satisfy the `HasPendingOutboundsForChain` precondition ahead of a `MsgInitiateFundMigration`).

### Impact Explanation
This breaks the operational invariant the `IsOutboundEnabled` flag and `MsgInitiateFundMigration`'s pending-outbound precondition are meant to guarantee. An admin who disables outbound for a chain and confirms `HasPendingOutboundsForChain == false` before starting a TSS fund migration can have a new pending outbound silently reintroduced by any external user triggering an inbound-execution failure during the migration window, because `buildRevertOutbound` ignores the disabled flag. That outbound will still be picked up by Universal Validators, signed via TSS with whatever key is currently active, and broadcast — defeating the purpose of the outbound-disable gate and potentially causing outbound traffic (and associated PRC20-to-external asset value movement / gas-fee accounting) on a chain operators have explicitly frozen for safety. This falls squarely in scope under "corruption of ... revert destination ... chain config use ... must not misroute value" and "unauthorized module-originated EVM execution ... reachable from ordinary user deposits ... alone."

### Likelihood Explanation
High reachability: the trigger (a zero-amount or otherwise execution-invalid inbound) is entirely attacker-controlled and gasless (`MsgVoteInbound` is on the gasless whitelist and voted by honest UVs relaying attacker-observed source-chain events) — no privileged actor, no malicious validator, and no race beyond "chain disabled + attacker sends any rejectable inbound" is required. The only precondition is that operators disable outbound for a chain (a documented, expected operational step ahead of fund migration), which is exactly the moment this gap is exploitable.

### Recommendation
Add the same `IsChainOutboundEnabled` check used in `BuildOutboundsFromReceipt` to `buildRevertOutbound` (and audit `RevertStuckInbound` / rescue-funds outbound creation for the same gap) before returning a `PENDING` `OutboundTx`. If reverts to a disabled chain must still be possible, gate them behind an explicit, differently-named invariant (e.g., "allow revert even when outbound disabled") rather than silently omitting the check, and ensure `HasPendingOutboundsForChain` / fund-migration preconditions account for revert-sourced outbounds.

### Proof of Concept
1. Admin adds `ChainConfig` for `eip155:11155111` with `Enabled.IsOutboundEnabled = false` (or flips it false after having it true), intending to run `MsgInitiateFundMigration` for that chain.
2. Attacker (or any relayed source-chain event) causes a `GAS`-type inbound with `Amount = "0"` to be voted through by honest UVs; `ValidateForExecution` fails with `"amount must be positive for this tx type"`, and the non-CEA revert path fires, calling `buildRevertOutbound(sdkCtx, utx.InboundTx)` and `attachOutboundsToUtx(...)` — as shown by the existing test `TestInboundGas` / `"GAS inbound with zero amount ... FAILED PCTx with revert outbound"` [9](#0-8) .
3. Because `buildRevertOutbound` never calls `IsChainOutboundEnabled`, the `INBOUND_REVERT` `OutboundTx` is created and indexed into `PendingOutbounds` for `eip155:11155111` despite outbound being disabled — contrast this with `TestOutbound_ChainEnabled`'s `"outbound not created when destination chain outbound is disabled"` case, which only covers the forward-outbound path [10](#0-9) .
4. `k.uexecutorKeeper.HasPendingOutboundsForChain(ctx, chain)` checked inside `InitiateFundMigration` [11](#0-10)  would now return `true` if re-evaluated, or — if the migration was already initiated before step 2 — the stray pending outbound persists through the "disabled" window unexpectedly.

Note: I was not able to find any subsequent guard elsewhere in the outbound-processing pipeline (e.g., in `FinalizeOutbound`/`handleFailedOutbound`/`handleSuccessfulOutbound`) that re-checks `IsChainOutboundEnabled` before signing/broadcasting a pending outbound, based on the code reviewed; if such a guard exists outside the files surfaced by search, it would need to be confirmed with a full repository checkout.

```go
// IsChainOutboundEnabled checks if outbound is enabled for a given chain
func (k Keeper) IsChainOutboundEnabled(ctx context.Context, chain string) (bool, error) {
	config, err := k.GetChainConfig(ctx, chain)
	if err != nil {
		if errors.Is(err, collections.ErrNotFound) {
			// chain not found
			return false, nil
		}
		return false, err
	}
	if config.Enabled == nil {
		return false, nil
	}
	return config.Enabled.IsOutboundEnabled, nil
}
```

```go
func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {
	recipient := inbound.Sender
	if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" {
		recipient = inbound.RevertInstructions.FundRecipient
	}

	outbound := &types.OutboundTx{
		DestinationChain:  inbound.SourceChain,
		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}

	// Look up the PRC20 address for this external token
	tokenCfg, err := k.uregistryKeeper.GetTokenConfig(sdkCtx, inbound.SourceChain, inbound.AssetAddr)
	if err != nil || tokenCfg.NativeRepresentation == nil || tokenCfg.NativeRepresentation.ContractAddress == "" {
		k.Logger().Warn("failed to get PRC20 for revert outbound gas lookup, proceeding without gas fields",
			"chain", inbound.SourceChain,
			"asset", inbound.AssetAddr,
			"error", err,
		)
		return outbound
	}

	// Fetch gas fields from UniversalCore.getOutboundTxGasAndFees(prc20, 0)
	// 0 means use the contract's baseLimit for this chain
	gasToken, gasFee, gasPrice, gasLimit, err := k.GetGasFeeInfoForRevertOutbound(sdkCtx, tokenCfg.NativeRepresentation.ContractAddress)
	if err != nil {
		k.Logger().Warn("failed to fetch gas fee info for revert outbound, proceeding without gas fields",
			"chain", inbound.SourceChain,
			"prc20", tokenCfg.NativeRepresentation.ContractAddress,
			"error", err,
		)
		return outbound
	}

	outbound.GasToken = gasToken
	outbound.GasFee = gasFee
	outbound.GasPrice = gasPrice
	outbound.GasLimit = gasLimit

	return outbound
}
```

**File:** x/uexecutor/README.md (L262-283)
```markdown
### `PendingOutbounds`

- **Created** by chain code at outbound creation in `create_outbound.go` —
  BEFORE any validator vote. The chain knows the outbound exists because it
  generated the destination-chain transaction itself; validators are tasked
  with observing whether/how it landed.
- **Keyed** by deterministic chain-derived `outbound_id`.
- **Variant-aware:** validator votes append `OutboundObservationVariant`s as
  they arrive (`RecordOutboundVote` inside `VoteOutbound`). Multiple variants
  per outbound indicate validator divergence on the destination-chain
  observation (different `success`/`tx_hash`/`error_msg`/`gas_fee_used`).
- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.
```
