### Title
Division-by-zero panic in `calc-treasury-lp-preview` / `accrue` reserve-fee calculation halts all vault operations - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
The vault contracts (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) compute a "treasury LP" mint amount by dividing by `(- ta-preview reserve-inc)` without ever checking that this denominator is non-zero (or non-underflowing). This is the same bug class as the reported `NativeTokenToStkXPRT`/`StkXPRTToNativeToken` issue: a share/asset conversion ratio computed with an unguarded denominator that can reach zero in normal operation, causing a runtime abort instead of a graceful error.

### Finding Description
`calc-treasury-lp-preview` computes the accrued protocol reserve fee and converts it into an equivalent amount of vault shares to mint to `.dao-treasury`: [1](#0-0) 

```
(define-private (calc-treasury-lp-preview)
  (let ((scaled-principal (var-get principal-scaled))
        ...
        (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
        (ta-preview (total-assets-preview)))
    (if (> reserve-inc u0)
        (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
        u0)))
```

The only guard present is `(> reserve-inc u0)`. There is **no check** that `ta-preview` is greater than `reserve-inc`. If `ta-preview` equals `reserve-inc` exactly, `(- ta-preview reserve-inc)` evaluates to `u0`, and `mul-div-down` (which internally performs a `/` operation) divides by zero. In Clarity, `/` by zero is a runtime error that aborts the entire transaction, exactly analogous to the Go panic in the reported issue for `NativeTokenToStkXPRT`/`StkXPRTToNativeToken` (which also lacked a zero-denominator check that `MintRate`, i.e. the safe sibling calculation, already implements).

Note that elsewhere in the same file, the analogous conversion helpers `convert-to-shares-preview`/`convert-to-assets-preview` DO correctly guard both `ta == 0` and `ts == 0` before dividing: [2](#0-1) 

This confirms the missing-zero-check pattern is not systemic to every division site, but was specifically omitted for the `calc-treasury-lp-preview` denominator — mirroring the report's remediation note that other functions (`MintRate`) already do the safe thing while the vulnerable ones do not.

The exact same unguarded expression is duplicated inline inside `accrue`: [3](#0-2) 

```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
```

`accrue` is invoked at the start of every state-changing vault entry point (`deposit`, `redeem`, `system-borrow`, `repay`, etc.), and `total-supply-preview` (which calls `calc-treasury-lp-preview`) is also invoked directly by `convert-to-shares-preview`/`convert-to-assets-preview` used in `deposit`/`redeem`: [4](#0-3) 

So any call path into the vault will hit this unguarded division whenever the trigger condition (`total-assets-preview == reserve-inc`) is reached.

### Impact Explanation
When `ta-preview` (current vault assets + accrued interest not yet realized as borrowed) is exactly equal to the newly computed `reserve-inc` fee slice, the division-by-zero aborts the transaction. Since `accrue`/`total-supply-preview` is on the hot path of `deposit`, `redeem`, `system-borrow`, and `repay`, this permanently freezes normal usage of the affected vault (deposits and withdrawals revert every block until the underlying state changes enough to move `ta-preview` away from `reserve-inc`, which itself requires a successful transaction — creating a potential permanent lock). This matches the in-scope impact class: **temporary freezing of funds** (potentially indefinite, since the very state mutation needed to escape the condition is blocked by the same panic).

### Likelihood Explanation
`ta-preview` is a function of accrued interest, and `reserve-inc` is a fee cut of that same accrued interest scaled by `fee-reserve/BPS`. While `reserve-inc` is normally much smaller than `ta-preview`, in low-liquidity vault states (e.g., near `MINIMUM-LIQUIDITY` shortly after `initialize`, or after most assets have been borrowed out so `current-assets` is very small while `debt-delta` from a long-idle `next-index` update is comparatively large) `ta-preview` and `reserve-inc` can converge to equality, especially with high `fee-reserve` settings or long accrual gaps. No malicious cross-user interference or privileged action is required — a single call to any vault entry point after enough elapsed time can trigger it, satisfying the single-transaction analog constraint.

### Recommendation
Guard the denominator explicitly before dividing, mirroring the safe pattern already used in `convert-to-shares-preview`/`convert-to-assets-preview`:
```
(if (and (> reserve-inc u0) (> ta-preview reserve-inc))
    (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
    u0)
```
Apply this fix consistently in both `calc-treasury-lp-preview` and the duplicated inline logic in `accrue`, across all six vault contracts (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Deploy/initialize a vault; `current-assets` is set to `MINIMUM-LIQUIDITY`, `total-borrowed` is `u0`.
2. Drive the vault into a state where nearly all liquidity is borrowed out via `system-borrow`, so `assets` (idle liquidity) is small relative to accrued debt.
3. Let sufficient time elapse (no `accrue` calls) so that on the next triggering call, `next-index` produces a `debt-delta` such that `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)` equals `total-assets-preview()` (`current-assets + interest`) exactly — achievable by tuning `fee-reserve` (a DAO-configurable parameter) and the elapsed time/utilization to land on this exact equality, or by repeatedly calling a harmless read/estimate function to observe when the two values converge and then submitting the triggering transaction at that block.
4. Call any of `deposit`, `redeem`, `system-borrow`, or `repay`. The internal call chain reaches `calc-treasury-lp-preview` (via `total-supply-preview` and/or the duplicated logic in `accrue`), computes `(- ta-preview reserve-inc)` = `u0`, and `mul-div-down` performs a division by zero, aborting the transaction.
5. Because `assets`/`index`/`last-update` are not persisted (the abort rolls back all `var-set` calls in the same transaction), every subsequent call to the vault at the same or later block hits the identical computation and also aborts, freezing all deposit/redeem/borrow/repay operations on that vault until protocol parameters or market conditions shift enough to break the exact equality.
