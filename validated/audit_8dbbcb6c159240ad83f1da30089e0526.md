### Title
Unguarded division by zero in `RepositoryImpl.calculateGlobalEnergyLimit` can panic TVM execution - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
The bug class in the external report is an unchecked division-by-zero in a share/ratio conversion function that is reachable from a public entry point, causing a runtime panic. The strongest analog in java-tron is `RepositoryImpl.calculateGlobalEnergyLimit`, which divides by `totalEnergyWeight` without checking whether it is zero, unlike its sibling implementation in `EnergyProcessor`, which was hardened with an explicit zero-check.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes an account's energy limit by dividing by `totalEnergyWeight`: [1](#0-0) 

The only protection against `totalEnergyWeight == 0` is a Java `assert totalEnergyWeight > 0;` statement at line 976. Java assertions are disabled by default at runtime unless the JVM is launched with `-ea`; no such flag was found configured anywhere in the repository. This means the assertion is effectively dead code in production, and execution falls through directly into a division:

```
return BigInteger.valueOf(energyWeight)
    .multiply(BigInteger.valueOf(totalEnergyLimit))
    .divide(BigInteger.valueOf(totalEnergyWeight))
    .longValueExact();
```

`BigInteger.divide` throws `ArithmeticException: BigInteger divide by zero` when the divisor is zero, which is an unchecked runtime exception.

This is directly comparable to the reported bug: a share-ratio function (`stkXPRTAmount / stkXPRTTotalSupplyAmount`-style division) that assumes the denominator is always positive but never enforces it, and where a sibling/parallel implementation elsewhere in the same codebase was already fixed to guard against the zero case. Here, `EnergyProcessor.calculateGlobalEnergyLimit` (used in the ordinary account-resource accounting path) *does* contain the corresponding guard: [2](#0-1) 

specifically the check `if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) { return 0; }` before falling back to `assert totalEnergyWeight > 0;`. The equivalent duplicate logic in `RepositoryImpl` (which is exercised from the TVM/VM execution context rather than the ordinary actuator resource-accounting path) never received this hardening, leaving an inconsistent, unguarded copy of the same computation.

### Impact Explanation
If `totalEnergyWeight` becomes zero or is queried before any account has frozen balance for energy (e.g., a freshly initialized or otherwise energy-weight-drained network state, or code paths where `getTotalEnergyWeight()` returns 0), any smart-contract execution path in the TVM that flows through `RepositoryImpl.calculateGlobalEnergyLimit` would throw an uncaught `ArithmeticException`. Depending on where the exception surfaces in the VM call stack, this can either abort a specific user's TVM invocation unexpectedly (denial-of-service to that transaction/user) or, if unhandled at a higher level, propagate up through block processing, threatening node stability. This matches the "division by zero leading to panic and DoS" bug class of the source report.

### Likelihood Explanation
Likelihood depends on `totalEnergyWeight` legitimately reaching zero at points where the TVM invokes `RepositoryImpl.calculateGlobalEnergyLimit`. `totalEnergyWeight` is a network-wide dynamic property incremented/decremented as accounts freeze/unfreeze TRX for energy; it is plausible for it to be zero in edge conditions (e.g., early chain state, or after mass unfreeze events), and this is an unprivileged, naturally reachable state rather than something requiring a trusted role. The lack of unit test coverage for the zero-weight case in `RepositoryImpl` (compared to the explicit hardened tests for `EnergyProcessor`, see `CalculateGlobalLimitHardenTest`) further indicates this path was not defensively considered for the VM-side duplicate.

### Recommendation
Add the same zero-denominator guard used in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` to `RepositoryImpl.calculateGlobalEnergyLimit`: return `0` (or otherwise short-circuit) when `totalEnergyWeight <= 0`, instead of relying on a `assert` statement that is inert in production builds.

### Proof of Concept
1. Drive `totalEnergyWeight` (via `DynamicPropertiesStore.saveTotalEnergyWeight`) to `0` — reachable through normal freeze/unfreeze accounting when no account currently has energy weight frozen.
2. Trigger a smart-contract call (any TVM execution) for an account that has `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`, causing `RepositoryImpl.calculateGlobalEnergyLimit` to be invoked with `hardenResourceCalculation()` enabled.
3. Observe `BigInteger.divide(BigInteger.ZERO)` throw `ArithmeticException`, since the `assert totalEnergyWeight > 0;` at line 976 does not execute in a production JVM (no `-ea` flag), aborting the TVM call unexpectedly. [1](#0-0) [2](#0-1)

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
