### Title
Unbounded linear entry-point-selector scan on every CALL_CONTRACT/LIBRARY_CALL enables per-call algorithmic-complexity DoS - (File: crates/blockifier/src/execution/contract_class.rs)

### Summary
The gas cost for `CallContract`/`LibraryCall` syscalls in the sequencer is a fixed constant (`CALL_CONTRACT_GAS_COST`, `LIBRARY_CALL_GAS_COST` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/constants.cairo:104-110`) that does not scale with the number of entry points declared by the callee class, yet the actual off-chain (blockifier) lookup of the target entry point is a full linear scan (`O(n)`) over all entry points of the same type, executed on every single call.

### Finding Description
`EntryPointsByType::get_entry_point` (`crates/blockifier/src/execution/contract_class.rs:788-809`) resolves the entry point to execute by doing: [1](#0-0) 
i.e. `entry_points_of_same_type.iter().filter(|ep| ...).collect()` — a linear scan across the whole vector of entry points of the given type, invoked from `get_entry_point` for Cairo1 classes and analogously in `resolve_entry_point_pc` for deprecated Cairo0 classes: [2](#0-1) 

This is called once per contract invocation (every `CALL_CONTRACT`/`LIBRARY_CALL` syscall, and every top-level entry point dispatch), and the sequencer's own on-chain Cairo (Starknet OS) implementation of the same lookup uses binary search over the *sorted* entry-point array (`search_sorted_optimistic`) instead: [3](#0-2) 

The blockifier (off-chain execution engine that actually runs on the sequencer/full nodes) does not exploit the sortedness and re-scans the full list each time. The syscall's charged gas cost is a fixed constant independent of the number of entry points in the callee class: [4](#0-3) 

The gateway's stateless validator only checks that declared entry points are sorted and unique (`crates/apollo_gateway/src/stateless_transaction_validator_test.rs:571-592`, backed by `EntryPointsNotUniquelySorted`), but places no cap on the total *number* of entry points a class may declare — only an overall bytecode-size limit (`max_bytecode_size`, default 81920 felts) bounds it indirectly. A contract can therefore legitimately declare tens of thousands of trivial entry points (each entry point descriptor is small), and every call into that class pays a fixed metered cost while the actual off-chain Rust execution performs an `O(n)` scan.

### Impact Explanation
Because the charged gas/fee for `CallContract`/`LibraryCall` is a flat constant that does not scale with the number of entry points in the target class, an attacker who declares a class with a very large number of entry points of the same type and then repeatedly invokes it (e.g. via recursive `call_contract`/`library_call` chains within one transaction, or across many transactions) forces the sequencer/full-node blockifier to perform `entry_points × calls` work while paying only for `calls` worth of gas. This creates a resource-accounting mismatch: real CPU cost is under-priced relative to the resource bounds validated in the gateway and blockifier, allowing a bounded-fee transaction (or bounded set of transactions) to consume disproportionate sequencer CPU time — a classic "inefficient algorithmic complexity / allocation without limits" DoS matching the CVE-2026-55968 bug class, reachable purely from a declare + invoke by an ordinary account.

### Likelihood Explanation
Medium. Exploitation requires only a `DECLARE` of a class with many entry points (bounded by `max_bytecode_size`, not by entry-point count) followed by ordinary `INVOKE` transactions that trigger repeated `call_contract`/`library_call` dispatch into that class — both of which are standard, unprivileged operations available to any transaction sender/contract deployer. No special node role or race condition is needed. The severity is capped by the per-tx step/gas limits (`invoke_tx_max_n_steps`, `EXECUTE_MAX_SIERRA_GAS`) and by the fact that filtering thousands of small structs is still relatively fast per call, so a single transaction's marginal overhead may be modest; the risk compounds when calls are repeated many times within the step budget (e.g., recursive library/contract calls) or across many transactions targeting the same bloated class, amplifying aggregate CPU usage per unit of paid fee.

### Recommendation
- Enforce an explicit maximum number of entry points per type (and/or total) at declare-time validation in the gateway (alongside the existing sorted/unique check in `stateless_transaction_validator.rs`), independent of the bytecode-size limit.
- Replace the linear `filter`/`collect` entry-point lookup in `EntryPointsByType::get_entry_point` (`contract_class.rs`) and `resolve_entry_point_pc` (`deprecated_entry_point_execution.rs`) with a binary search (`binary_search_by_key`) over the already-sorted entry-point vector, mirroring the OS's `search_sorted_optimistic` approach, to make lookup `O(log n)`.
- Alternatively/additionally, make `CALL_CONTRACT_GAS_COST`/`LIBRARY_CALL_GAS_COST` (and their Cairo1 native/VM equivalents) scale with `log(n_entry_points)` or the callee's declared entry-point count so the charged fee tracks the real lookup cost.

### Proof of Concept
1. Compile/declare a Sierra class `Bloated` whose `entry_points_by_type.external` (or `.l1_handler`) array contains, e.g., 50,000–80,000 distinct trivial entry points (feasible within `max_bytecode_size = 81920` felts, since each `EntryPointV1` descriptor is small), keeping the array sorted and unique to pass `stateless_transaction_validator`'s `EntryPointsNotUniquelySorted` check.
2. Declare `Bloated` via a standard `DECLARE` transaction (no special privileges required).
3. Deploy an account/caller contract that issues repeated `call_contract`/`library_call` syscalls into `Bloated`'s entry points (e.g., recursively, similar to the pattern in `crates/blockifier/src/test_utils/syscall.rs::build_recurse_calldata`), within the per-tx step/gas budget.
4. Measure sequencer-side wall-clock/CPU time for executing this transaction versus an equivalent transaction calling a class with few entry points but the same number of calls — the bloated-class transaction incurs materially higher off-chain CPU cost per syscall (linear scan over tens of thousands of entries) while being charged the same fixed `CALL_CONTRACT_GAS_COST`/`LIBRARY_CALL_GAS_COST`, demonstrating the fee/CPU-cost mismatch.

(Note: I was not able to directly execute or benchmark this PoC in this environment; the finding is based on static analysis of the linear-scan implementation versus the OS's binary-search implementation and the fixed syscall gas costs. Actual quantified CPU overhead and exact exploitability thresholds would need to be measured with a running sequencer/blockifier instance.)
