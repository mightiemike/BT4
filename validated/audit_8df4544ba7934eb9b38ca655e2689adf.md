## Finding

I traced the external "missing slippage" bug class (accept unauthenticated/unchecked value → silent loss) to its closest Aptos-native analog: **a write-set is accepted into durable ledger storage during backup restore without being authenticated against the cryptographically-verified `TransactionInfo.state_change_hash`**, unlike every other restore/sync path in the codebase.

### Title
Backup transaction restore persists unauthenticated write sets not bound to the verified `state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
`LoadedChunk::load` verifies a downloaded transaction-backup chunk using `TransactionListWithProofV2::verify`, which internally calls `TransactionListWithProof::verify`. That verification confirms transaction hashes and event root hashes against the accumulator-proven `TransactionInfo`s, but it never touches `write_sets` at all — `write_sets` are parsed straight from the backup record bytes and carried alongside, untouched by any proof. [1](#0-0) [2](#0-1) 

`TransactionListWithProof::verify` checks transaction hashes, the accumulator proof, and event root hashes, but has no line comparing `CryptoHash::hash(write_set)` to `txn_info.state_change_hash()`: [3](#0-2) 

By contrast, the sibling struct used for output-based sync, `TransactionOutputListWithProof::verify`, explicitly performs this exact check: [4](#0-3) 

This shows the write-set/`state_change_hash` binding is a recognized, load-bearing invariant elsewhere in the codebase — it is simply missing from the transaction-list backup/restore path.

The unverified `write_sets` are then written directly to the `WriteSetDb` and (when `kv_replay` is enabled) fed into `calculate_state_and_put_updates` to compute the persisted state/JMT updates, with no hash check performed anywhere in the save path: [5](#0-4) [6](#0-5) 

### Finding Description
During transaction-backup restore (`TransactionRestoreController` / `LoadedChunk::load`), the chunk file bundles four things per version: `Transaction`, `TransactionInfo`, `events`, and `WriteSet`. Only `Transaction`, `TransactionInfo`/accumulator-proof, and `events` are threaded through `TransactionListWithProof::verify` before being trusted. The `WriteSet` value is read from the same untrusted backup blob but is *not* included in the `TransactionListWithProof` struct passed to `verify`, so nothing checks that `CryptoHash::hash(write_set) == txn_info.state_change_hash()` — the only field that binds a write set into the Merkle-accumulator-proven ledger history.

For versions below `first_to_replay` (i.e., transactions that are not re-executed, just directly persisted — the common case for older history during a restore/bootstrap), `restore_handler.save_transactions()` writes this unauthenticated `write_set` straight into `WriteSetDb`, and (when kv_replay is on) uses it to derive and persist state values/JMT updates via `calculate_state_and_put_updates`. No other stage of the restore pipeline re-validates that the stored write set matches the proven `state_change_hash` for that version.

### Impact Explanation
If the backup archive is corrupted or tampered with (compromised/misconfigured backup object store, bit-rot, bug in the backup writer, MITM if backup storage transport isn't otherwise authenticated), a node restoring from it will durably commit a write set — and, under `kv_replay`, derived state values — that differs from the one actually committed on-chain for that version, while the transaction/event/accumulator proof still verifies successfully. Any subsequent authenticated read (e.g., `get_transaction_outputs`/write-set-with-proof APIs, replay-verify tooling) built on top of this corrupted `WriteSetDb`/state entry would present wrong data as if bound to a valid version and proof, since the accumulator/ledger-info verification pipeline never actually authenticated the write set.

### Likelihood Explanation
This requires a corrupted or malicious backup archive/storage, which is a real (if non-default) restore input in fullnode/backup tooling and state-sync-driven restore flows. It's not attacker-controlled purely by mainnet participants without also controlling or corrupting backup storage, but the whole point of consensus-driven accumulator proofs is to make restore correctness independent of backup-storage trust — that guarantee silently doesn't extend to write sets here.

### Recommendation
Include `write_sets` in the object verified before restore, e.g., by extending `TransactionListWithProof`/`TransactionListWithProofV2` (or adding a dedicated check in `LoadedChunk::load`) to assert `CryptoHash::hash(write_set) == txn_info.state_change_hash()` for every transaction in the chunk, mirroring the check already done in `TransactionOutputListWithProof::verify`. This should be enforced before `save_transactions`/`save_transactions_impl` is ever called with unverified write sets.

### Proof of Concept
1. Produce a valid transaction backup chunk, then tamper with only the `write_set` bytes for one record in the chunk's raw record stream (leaving `Transaction`, `TransactionInfo`, and `events` untouched, so the accumulator/txn/event verification in `LoadedChunk::load` still passes).
2. Run `TransactionRestoreController`/`db-restore` against this tampered chunk targeting a version before `first_to_replay` (or with kv_replay disabled) so the write set is saved as-is via `restore_handler.save_transactions`.
3. Observe that restore completes successfully (no error from `txn_list_with_proof.verify(...)`), yet `ledger_db.write_set_db().get_write_set(version)` now returns the tampered write set, which no longer matches `txn_info.state_change_hash()` for that version — demonstrating storage now holds ledger data inconsistent with its own proven `TransactionInfo`.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;
