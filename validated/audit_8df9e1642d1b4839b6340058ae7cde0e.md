### Title
Panic-inducing `.unwrap()` on stale `receiver_shard_id()` for delayed `GlobalContractDistribution` receipts after repeated resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()` to decide whether a delayed receipt belongs to the current shard after a resharding event [1](#0-0) . This function is invoked from `pop()` and `peek_iter()`, both of which are exercised on every chunk application while draining the delayed receipt queue [2](#0-1) . If a receipt's recorded target shard cannot be resolved against the *current* shard layout (e.g., because the target shard id was retired across two successive resharding splits), `receiver_shard_id` can return an `Err`, and the unconditional `.unwrap()` converts that into a runtime panic during normal, permissionless chunk processing — a transaction-triggered halt.

### Finding Description
This directly mirrors the Linux kernel bug class in the report: after a "redirect"-like state transition (there: XDP `bpf_redirect_map`; here: a shard resharding split that changes which shard a previously-created receipt logically belongs to), a piece of routing/context metadata (`rxq`/ingress device there; `receiver_shard_id` under the *new* shard layout here) is not correctly re-derived, and the consuming code path blindly dereferences/unwraps it, causing a crash.

The nearcore test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs` is written specifically to reproduce this exact scenario: a `GlobalContractDistribution` receipt is deliberately kept in the delayed queue across two consecutive dynamic-resharding splits so that its `target_shard` becomes "stale" relative to the shard layout in effect when the receipt is finally popped [3](#0-2) . The test comment states explicitly: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations."* [4](#0-3) 

The `receipt_filter_fn` implementation in this tree still contains the unconditional `.unwrap()` rather than graceful error handling [1](#0-0) , and this is the exact code path the regression test targets. I was not able to fully verify from the available index whether the underlying `receiver_shard_id`/shard-layout-remapping logic (in `core/primitives/src/shard_layout/v3.rs`, which the index did not let me inspect in full during this session) has been hardened to always succeed across multiple resharding generations, or whether the panic path is still reachable in production. The existence of a dedicated regression test with this exact title and comment strongly suggests this was a real, previously-triggerable bug in this bug class, and the `.unwrap()` itself remains in the code as the single point of failure if remapping ever fails.

### Impact Explanation
If `receiver_shard_id()` returns `Err` for a delayed receipt whose original target shard no longer exists in the current shard layout (possible after two or more resharding splits within the lifetime of a long-delayed receipt, e.g. `GlobalContractDistribution` receipts which explicitly retain a `target_shard` field), the `.unwrap()` panics inside normal chunk-apply logic. Because delayed-receipt draining happens deterministically for every chunk (via `DelayedReceiptQueueWrapper::pop`/`peek_iter`), a panic here crashes the validator/chunk-producer process applying that chunk — a transaction-triggered chain halt reachable purely by an unprivileged contract deployer submitting a global contract deploy transaction and the network naturally undergoing routine dynamic resharding, with no cooperation from validators or the network layer required.

### Likelihood Explanation
Triggering requires: (1) a delayed receipt (e.g. `GlobalContractDistribution`, whose `target_shard` is set once and not automatically remapped on every layout change) to survive across at least two resharding-boundary transitions while still queued, and (2) the shard-layout remapping logic failing to resolve the stale target to a currently valid shard id. The nearcore team already built a targeted regression test for this precise condition, indicating it was recognized as a real, reachable failure mode under dynamic resharding (a now-supported production feature, not test-only). Likelihood is Medium: it requires specific timing (receipt held in queue across two splits) that an attacker cannot directly force but that congestion/compute saturation (demonstrated feasible in the regression test via `burn_gas_raw` saturation) can induce.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with proper error propagation: return a `Result<bool, RuntimeError>` (updating `pop()`/`peek_iter()` signatures accordingly) so that an unresolvable stale receiver shard is handled as an explicit, recoverable error (e.g., treat as permanently filtered/dropped-and-logged, or route via ancestor-shard lookup) rather than panicking the chunk-apply path. Ensure `receiver_shard_id()`/the shard-layout ancestor-resolution logic correctly walks back through multiple resharding generations for all receipt kinds carrying a fixed target/receiver shard, not just one generation.

### Proof of Concept
Follow the reproduction already encoded in the codebase's own regression test:
1. Deploy a global contract from an account on shard `S_A` — this creates a `GlobalContractDistribution` receipt with `target_shard = S_A`.
2. Saturate compute on `S_A` every block (e.g. repeated `burn_gas_raw` calls) so the distribution receipt is pushed into and stays in the delayed receipt queue.
3. While the receipt sits delayed, trigger two sequential dynamic-resharding splits, the first of which splits `S_A` itself.
4. Stop saturating and let the delayed queue drain; the stale receipt is popped and `receipt_filter_fn` calls `receiver_shard_id(&new_shard_layout).unwrap()` on a `target_shard` that no longer maps cleanly under the twice-split layout.

This is codified in [5](#0-4) , whose assertion `head_height >= drain_end` is designed to fail (chain stall) precisely if the panic in `receipt_filter_fn` occurs.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
