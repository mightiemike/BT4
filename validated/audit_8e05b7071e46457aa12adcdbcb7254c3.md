Based on my analysis, I found the disabled-collateral branch of `collateral-remove` in `v0-4-market.clar`, which contains the exact analog bug class: a health/sufficiency check compares against a value that has already had the withdrawal amount subtracted from it via a *different* accounting path, mirroring the flashloan report's "check against `remaining` instead of the original bound" mistake.

### Title
Incorrect sufficiency check in disabled-collateral `collateral-remove` compares against a double-adjusted total, causing unexpected reverts or wrong health evaluation - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
In the disabled-collateral branch of `collateral-remove`, the code computes `total-collateral-value` by adding the *entire* disabled-asset notional (`disabled-notional`, computed from the pre-withdrawal `user-amount`) to the already price-resolved `collateral-value` (which already excludes the disabled asset), then subtracts a separately-rounded `removal-notional` (rounded up) from that combined total to test solvency and to feed the health check. Because `disabled-notional` and `removal-notional` are computed through different rounding paths from different snapshot points instead of directly checking `amount` against `user-amount`, the check can revert or under/over-estimate the post-withdrawal collateral for reasons unrelated to actual insufficiency.

### Finding Description
`collateral-remove` at [1](#0-0)  handles disabled collateral by resolving `price` fresh, computing `disabled-notional` from `user-amount` (the full disabled balance) and `removal-notional` (rounded up, `true` flag) from the withdrawal `amount`, then asserting `total-collateral-value >= removal-notional` before computing `(- total-collateral-value removal-notional)` as the post-removal value passed into `is-healthy`. This mirrors the flashloan bug precisely: instead of directly checking `amount <= user-amount` (the true bound, analogous to `TSLOT_CB_DATA_VALUE`), the protocol checks the withdrawal notional against a derived/mutated total (`total-collateral-value`, analogous to `remaining` in the Napier report) that mixes independently-rounded quantities. `removal-notional` rounds up (`normalize ... true`) while `disabled-notional` rounds down, so a withdrawal of the user's *entire* disabled balance can have `removal-notional > disabled-notional` purely from rounding, making the combined check fail (or artificially reduce `post-removal-collateral-value` used by `is-healthy`) even though the user is not actually short of collateral.

### Impact Explanation
This breaks core withdrawal functionality for users holding disabled-collateral assets: legitimate `collateral-remove` calls can revert unexpectedly (temporary freezing of funds, analogous to the flashloan swap failing unexpectedly), or in edge cases understate `post-removal-collateral-value` fed into the health check, causing an otherwise-healthy withdrawal to be rejected as `ERR-UNHEALTHY`. This lands in the "temporary freezing of funds" impact category.

### Likelihood Explanation
Likelihood is realistic for any full/near-full withdrawal of a disabled-collateral asset given normal price/decimal rounding — no attacker collusion or flashloan mechanics are required, it can occur in a single transaction under standard evaluation order.

### Recommendation
Check the withdrawal amount directly against the raw disabled-collateral balance (`user-amount`), not against a combined/rounded notional total: `(asserts! (<= amount user-amount) ERR-INSUFFICIENT-COLLATERAL)`, and derive `post-removal-collateral-value` by proportionally reducing `disabled-notional` by the same amount ratio rather than subtracting an independently up-rounded `removal-notional` from the combined total.

### Proof of Concept
1. User has `user-amount` of a disabled collateral asset and also holds enabled collateral, plus outstanding debt (`has-debt` true), so the disabled branch at [1](#0-0)  executes.
2. User calls `collateral-remove` with `amount = user-amount` (withdraw entire disabled balance).
3. `disabled-notional = normalize(user-amount * price, decimals, false)` rounds down; `removal-notional = normalize(amount * price, decimals, true)` rounds up on the same `amount = user-amount` — under certain decimal/price combinations `removal-notional` can exceed `disabled-notional` by the rounding margin.
4. `total-collateral-value = collateral-value + disabled-notional`; the assert `(>= total-collateral-value removal-notional)` can fail purely due to this rounding mismatch even though the user is withdrawing exactly their balance, causing `ERR-INSUFFICIENT-COLLATERAL` to be thrown on a legitimate full withdrawal — the analog of `swapETHForYt` reverting despite the user having sufficient value.
