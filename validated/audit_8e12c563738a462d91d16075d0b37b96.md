### Title
Unauthenticated `GET /wallet/getassetissuelist` performs unbounded O(N) full-table scan and serialization over the entire AssetIssueStore - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueListServlet.java])

### Summary
`GetAssetIssueListServlet.doGet()` calls `wallet.getAssetIssueList()`, which in turn resolves to `AssetIssueStore.getAllAssetIssues()`, an unbounded iterator over the entire on-chain asset-issue key space that materializes every `AssetIssueCapsule` into a `List` before JSON-serializing the full result set back to the caller. There is no pagination, offset/limit, or cost accounting on this specific endpoint, so the cost of a single unauthenticated request scales linearly with the total number of asset issues ever created on chain.

### Finding Description
`GetAssetIssueListServlet.doGet()` invokes `wallet.getAssetIssueList()` with no parameters [1](#0-0) . That path resolves down into `AssetIssueStore.getAllAssetIssues()`, which streams the entire underlying key-value store, maps every entry to an `AssetIssueCapsule`, and collects them into an in-memory `List` with no offset/limit bound [2](#0-1) . The result is then fully JSON-serialized in `GetAssetIssueListServlet` and written to the HTTP response without any size cap [3](#0-2) .

Note: I could not locate a direct call from this path to `BandwidthProcessor.updateUsage()` per asset-issue entry as the question premises — `BandwidthProcessor` is used elsewhere in the codebase for transaction bandwidth accounting, not in this read-only query path. The actual amplification mechanism here is the unbounded database iteration plus JSON serialization of the full asset-issue set, not per-entry bandwidth accounting.

The only guard present is `RateLimiterServlet`, a generic per-endpoint QPS limiter, which throttles request frequency but does not scale with or account for the cost of each individual request (i.e., it does not reject/charge based on the size of `AssetIssueStore`). This is a request-frequency control, not a proportional-cost control, so a single request against a large `AssetIssueStore` still performs full O(N) work and returns an O(N)-sized response regardless of the rate limiter.

Notably, the codebase already contains a paginated alternative, `GetPaginatedAssetIssueListServlet` backed by `AssetIssueStore.getAssetIssuesPaginated(offset, limit)` [4](#0-3) , indicating the unbounded nature of the full-list query is a known class of problem that was mitigated for a different endpoint but not for `GetAssetIssueListServlet`.

### Impact Explanation
Since asset-issue creation is a normal, permissionless on-chain action (`AssetIssueContract`), the total number of stored asset issues can grow arbitrarily over the life of the chain. As that number grows, each call to `GET /wallet/getassetissuelist` requires O(N) store iteration, O(N) object allocation, and O(N) JSON serialization work, with an unbounded response payload. Repeated unauthenticated requests (even within whatever QPS limit `RateLimiterServlet` allows) impose disproportionate CPU, heap, and network I/O cost on the serving full node relative to a normal read-only API call, degrading node responsiveness for legitimate users and potentially exhausting node memory/GC headroom under sustained load.

### Likelihood Explanation
This requires no privileges: any client capable of sending HTTP GET/POST requests to a full node's public JSON-RPC/HTTP API can trigger it. The only precondition is a sufficiently large `AssetIssueStore`, which naturally grows over time as regular users issue TRC10 assets — an unprivileged, ordinary chain activity. The rate limiter does not neutralize the per-request cost, only the request frequency, so the attack is fully repeatable within the allowed rate, and the per-request cost keeps growing as chain history accumulates.

### Recommendation
Deprecate or remove the unbounded `GetAssetIssueListServlet` / `Wallet.getAssetIssueList()` full-scan behavior in favor of the existing paginated `GetPaginatedAssetIssueListServlet` (`AssetIssueStore.getAssetIssuesPaginated`). If backward compatibility is required, enforce a hard cap on the number of asset issues returned/scanned per request (mirroring `ASSET_ISSUE_COUNT_LIMIT_MAX`), and/or apply cost-proportional throttling (e.g., reject or heavily rate-limit the unbounded endpoint once `AssetIssueStore` size exceeds a safe threshold).
