### Title
Access key deletion discards the nonce state, allowing replay of stale signed transactions after key recreation - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
When a `DeleteKey` action removes an access key, its trie entry — including the nonce that tracked which transaction sequence numbers had already been consumed — is deleted entirely rather than being retained or archived. If a key with the same public key is later re-added (`AddKey`), the nonce is reseeded purely from the current block height, with no reference to the nonce the deleted key had reached. This is the on-chain analog of CVE-2017-1000136's "session not invalidated after credential change": deleting/rotating a credential (the access key) does not durably invalidate the sequence state tied to it, so a previously-valid but unsubmitted signed transaction can become replayable again.

### Finding Description
`delete_regular_key` simply removes the access key from the trie and reduces storage usage — it does not persist the nonce anywhere: [1](#0-0) 

When a key with the same public key is later added back, `add_regular_key` reseeds the nonce solely from `initial_nonce_value(block_height)`, with no lookback at what nonce the prior incarnation of that key had reached: [2](#0-1) [3](#0-2) 

`action_add_key` only rejects re-adding a key if one currently *exists* (`AddKeyAlreadyExists`); it performs no check against a previously deleted key's last nonce: [4](#0-3) 

This directly contradicts the documented protocol invariant, which explicitly states the recreated key's nonce **must** equal the old key's nonce to prevent replay: [5](#0-4) 

The runtime itself acknowledges this gap in a test comment: deleting the last key on an account "forgets the nonce," and the TODO explicitly connects this to the anti-replay mechanism being broken: [6](#0-5) 

Nonce validation itself (`verify_nonce`) only ever compares the submitted transaction's nonce against whatever nonce is *currently* stored on the access key in trie state — it has no memory of a nonce range consumed by a previous, now-deleted incarnation of the same public key: [7](#0-6) 

Because `initial_nonce_value` is derived from `(block_height - 1) * 1_000_000` and the upper bound check allows nonces up to `block_height * 1_000_000` (`ACCESS_KEY_NONCE_RANGE_MULTIPLIER`), an old key that had already advanced its nonce close to the current block's upper bound will, upon delete + immediate re-add within the same block-height window, produce a *fresh* nonce that is lower than nonces already consumed under the old key incarnation. Any transaction the account owner had previously signed (using that public key) with a nonce in that now-freed range — but never submitted, or submitted and rejected for unrelated reasons (e.g. insufficient balance at the time) — becomes valid again and can be replayed after the key is deleted and recreated.

### Impact Explanation
This allows an unauthorized/invalid state transition to be accepted by the runtime: a transaction that a user intended to invalidate (by deleting the access key, e.g. after suspecting key compromise or to revoke a delegated function-call key) can be resurrected and executed successfully once the same public key is re-added, as long as its nonce falls in the range freed up by the reset. This can result in unauthorized value movement (e.g. replay of an old `Transfer` or `FunctionCall` action) that the account owner reasonably believed was revoked, and represents acceptance of a transaction that correct nonce-monotonicity semantics should have rejected forever.

### Likelihood Explanation
This is reachable purely through ordinary, unprivileged transaction submission: any account owner (or a user who previously obtained a signed transaction, e.g. via a leaked/rotated access key) can trigger it by (1) having a signed-but-unsubmitted transaction under a key, (2) deleting that key, (3) re-adding a key with the identical public key (which any user with the private key can always do, since deriving/reusing the same keypair is trivial), and (4) submitting the old transaction. No special privileges, validator collusion, or network-level manipulation is required — it is entirely within the reach of a normal transaction signer.

### Recommendation
Persist the maximum nonce ever observed for a given `(account_id, public_key)` pair independent of `AccessKey` existence (e.g., a separate long-lived nonce-watermark trie entry that survives `DeleteKey`), and have `add_regular_key`/`add_gas_key` seed the new key's nonce as `max(initial_nonce_value(block_height), previous_watermark)` rather than unconditionally overwriting it. This restores the documented invariant that recreating a key with the same public key must not lower its effective nonce floor.

### Proof of Concept
1. Account `A` adds access key `K` (public key `pk`). It signs transaction `T1` with `nonce = N` (e.g. `N` close to the current block's `(block_height) * 1_000_000` upper bound) but does not submit it.
2. `A` submits `DeleteKey(pk)` to revoke `K` (e.g., believing the corresponding private key leaked). Per `delete_regular_key`, the trie entry — and its nonce — is removed entirely.
3. Still within roughly the same block-height window, `A` (or the private-key holder) submits `AddKey(pk, ...)` re-adding the identical public key. Per `add_regular_key`, the new nonce is set to `initial_nonce_value(block_height)`, which can be `< N`.
4. `T1` (nonce `N`, signed against the deleted key `K`) is now submitted. `verify_nonce` compares `N` against the freshly-seeded (lower) nonce and accepts it, executing an action the user intended to have revoked. [3](#0-2) [1](#0-0) [2](#0-1)

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.

    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
