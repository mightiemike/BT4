### Title
Positional (block-height, vtxindex) lookup of the leader VRF/signing key lets a burnchain reorg re-point a winning sortition's `miner_pk_hash` to a different key, hijacking the active-miner identity signers rely on - (File: `stackslib/src/chainstate/burn/sortition.rs`, `stackslib/src/chainstate/burn/db/sortdb.rs`)

### Summary
`LeaderBlockCommitOp` does not reference its paired `LeaderKeyRegisterOp` by content (e.g. txid or public key), but purely by its **position** in the burnchain history: `key_block_ptr` (block height) and `key_vtxindex` (index of the op within that block), exactly the class of "index/nonce instead of content" determinism flagged in the external Inverter-Network report. On a burnchain reorg, the set and order of transactions at a given block height can change, so the leader key that resolves at that same `(key_block_ptr, key_vtxindex)` slot after the reorg can be a *different* `LeaderKeyRegisterOp` than the one the original commit was built against.

### Finding Description
A block commit stores only positional pointers to its leader key: [1](#0-0) 

Validation of a commit only checks that *some* key exists at that position — it never checks that the key's content (public key / txid / registering sender) matches anything tied to the commit's sender: [2](#0-1) 

The lookup itself is a pure positional query against the DB, scoped only by `(sortition_id, block_height, vtxindex)` — not by any hash/content of the key: [3](#0-2) 

Crucially, this same positional lookup is used to derive the **winning miner's signing-key hash** that becomes part of the committed `BlockSnapshot`, i.e., the sortition-winner identity that signers use to determine the active miner for the tenure: [4](#0-3) 

`get_consumed_leader_keys` (used elsewhere to resolve which keys were consumed by which commits) performs the identical positional resolution: [5](#0-4) 

Attack scenario (analog of the Inverter finding, replacing CREATE-nonce collisions with burnchain-index collisions):
1. Bob registers VRF/signing key `K_bob` via a `LeaderKeyRegisterOp`; it lands at burn height `H`, `vtxindex = V`.
2. Bob's miner later submits a `LeaderBlockCommitOp` whose `key_block_ptr = H, key_vtxindex = V` and wins the sortition; the resulting `BlockSnapshot.miner_pk_hash` is derived from `K_bob` at `(H, V)`.
3. A burnchain reorg replaces block `H` (Bitcoin reorgs are routine and expected on some deployment targets per the analog report). In the replacement block, Eve gets her own `LeaderKeyRegisterOp` mined at the exact same `vtxindex = V` slot (transaction ordering within a freshly-mined/replacement block is controlled by the block producer, not by the equality the protocol relies on).
4. All commits and snapshots referencing `(H, V)` — including ones for tenures built after the reorg, or a still-pending/re-broadcast commit of Bob's — now resolve to Eve's key `K_eve` instead of `K_bob` when `get_leader_key_at`/`select_winning_block`'s `interpret_nakamoto_signing_key()` path runs.
5. Because nothing ties the resolved key back to the original committing party (no check on key content, txid, or sender), the `miner_pk_hash` recorded in the new canonical `BlockSnapshot` is Eve's, not Bob's, even though the burn fee for the winning commit was Bob's and Bob won the burn-weighted sortition.

### Impact Explanation
`miner_pk_hash` from `BlockSnapshot::make_snapshot` is exactly the value signers compare against to determine the currently active/authorized miner (`current_miner_pkh` checks in the signer state machine seen throughout `stacks-signer`/`check_signer_states_reorg`). If the resolved key diverges from the actual sortition winner's key due to a reorg-induced positional collision, this breaks the core equality "sortition winner == the key used to authorize/verify that winner's tenure," letting a party who did not win the burn-weighted sortition be treated as the authorized miner for that tenure — i.e., a minority-triggerable, reorg-only divergence in the signer/network's view of who is entitled to mine and collect the tenure's rewards. This lands in the same class as "a sortition winner not matching the burn-weight function" / "a signer weight ... from the wrong set" that the task explicitly calls in-scope, and mirrors the root cause of the Inverter report (identity/ownership resolved by position/counter rather than content, unstable across a reorg).

### Likelihood Explanation
This requires: (a) a burnchain reorg to occur at or shortly after the block height holding the relevant `LeaderKeyRegisterOp`, and (b) a second `LeaderKeyRegisterOp` to land at the identical `vtxindex` slot in the replacement block. Reproducing exact `vtxindex` collision requires influence over transaction ordering in the replacement block, which is more readily achievable by whoever produces that replacement block (e.g., the Bitcoin miner of the reorg block) rather than by an ordinary unprivileged actor — this is the main source of uncertainty in likelihood, since I could not find any code in-repo that pins `vtxindex` assignment to something the attacker cannot influence, nor any mitigation binding the resolved key to the commit's `apparent_sender`. Given the report's framing (regular/expected reorgs), and the total absence of a content-based binding in `check_common`, the underlying equality-break condition is real and unpatched even if triggering it needs favorable reorg conditions.

### Recommendation
Bind `LeaderBlockCommitOp` to its paired `LeaderKeyRegisterOp` by content, not purely by position: include a hash/txid of the intended `LeaderKeyRegisterOp` (or the VRF public key itself) in the commit, and require `check_common`/`get_leader_key_at` to verify the resolved key's content matches what the commit's sender registered, in addition to the positional lookup. This removes the reorg-sensitive index collision as a source of miner-identity ambiguity.

### Proof of Concept
No executable PoC was constructed (would require a live regtest/bitcoind reorg harness, similar to the existing `stacks-node/src/tests/signer/v0/reorg.rs` and `epoch_4_0_reorg.rs` test infrastructure already in this repo, driving a bitcoind fork that reorders a `LeaderKeyRegisterOp` into the exact `vtxindex` slot consumed by an existing winning `LeaderBlockCommitOp`). The control-flow path proving the vulnerability (positional-only resolution feeding directly into `BlockSnapshot.miner_pk_hash`) is demonstrated via the cited call chain: `LeaderBlockCommitOp::check_common` → `SortitionHandleTx::get_leader_key_at` (existence-only check) → `BlockSnapshot::make_snapshot`'s `sort_tx.get_leader_key_at(...).and_then(interpret_nakamoto_signing_key)` (identity binding for the winning miner).

    /// Find the VRF public keys consumed by each block candidate in the given list.
    /// The burn DB should have a key for each candidate; otherwise the candidate would not have
    /// been accepted.
    pub fn get_consumed_leader_keys(
        &mut self,
        parent_tip: &BlockSnapshot,
        block_candidates: &[LeaderBlockCommitOp],
    ) -> Result<Vec<LeaderKeyRegisterOp>, db_error> {
        // get the set of VRF keys consumed by these commits
        let mut leader_keys = vec![];
        for candidate in block_candidates.iter() {
            let leader_key_block_height = candidate.key_block_ptr as u64;
            let leader_key_vtxindex = candidate.key_vtxindex as u32;
            let leader_key = self
                .get_leader_key_at(
                    leader_key_block_height,
                    leader_key_vtxindex,
                    &parent_tip.sortition_id,
                )?
                .unwrap_or_else(|| {
                    panic!(
                        "FATAL: no leader key for accepted block commit {} (at {},{})",
                        &candidate.txid, leader_key_block_height, leader_key_vtxindex
                    )
                });

            leader_keys.push(leader_key);
        }

        Ok(leader_keys)
    }

    /// Get a leader key at a specific location in the burn chain's fork history, given the
    /// matching block commit's fork index root (block_height and vtxindex are the leader's
    /// calculated location in this fork).
    /// Returns None if there is no leader key at this location.
    pub fn get_leader_key_at<C: SortitionContext>(
        ic: &IndexDBConn<'_, C, SortitionId>,
        key_block_height: u64,
        key_vtxindex: u32,
        tip: &SortitionId,
    ) -> Result<Option<LeaderKeyRegisterOp>, db_error> {
        if key_block_height >= BLOCK_HEIGHT_MAX {
            return Err(db_error::BlockHeightOutOfRange);
        }
        let ancestor_snapshot = match SortitionDB::get_ancestor_snapshot(ic, key_block_height, tip)?
        {
            Some(sn) => sn,
            None => {
                return Ok(None);
            }
        };

        let qry = "SELECT * FROM leader_keys WHERE sortition_id = ?1 AND block_height = ?2 AND vtxindex = ?3 LIMIT 2";
        let args = params![
            ancestor_snapshot.sortition_id,
            u64_to_sql(key_block_height)?,
            key_vtxindex,
        ];
        query_row_panic(ic, qry, args, || {
            format!(
                "Multiple keys at {},{} in {}",
                key_block_height, key_vtxindex, tip
            )
        })
    }
