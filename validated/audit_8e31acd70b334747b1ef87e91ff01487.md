### Title
Hardcoded per-action gas budget in Wallet Contract can be exhausted by future protocol fee increases, permanently freezing the wallet - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/near_action.rs`)

### Summary
The NEAR Wallet Contract hardcodes a static gas allowance of 2 Tgas for any non-`FunctionCall` action (`Transfer`, `AddKey`, `DeleteKey`), asserting this is "sufficient for any non-function call action" [5](#0-4) . This value is added to a small fixed callback budget to size the static gas passed into multi-step promise chains used for base-token transfers and ERC-20 emulation [6](#0-5) [7](#0-6) . This is directly analogous to Solidity's hardcoded 2300-gas `.transfer()` stipend that was later broken by the Istanbul hardfork's gas repricing (EIP-1884) — a fixed gas budget baked into contract logic that assumes current protocol gas costs will never change.

### Finding Description
`Action::gas()` returns a constant `Gas::from_tgas(2)` for `Transfer`, `AddKey`, and `DeleteKey` actions, with the comment "2 Tgas is sufficient for any non-function call action" [5](#0-4) . This value is used to compute the static gas reserved for the two multi-hop promise chains in `inner_rlp_execute`:
- `callback_gas = ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` for the eth-implicit-account address-check flow [6](#0-5) 
- `callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` for ERC-20 emulated transfers [7](#0-6) 

That reserved gas is what the downstream `address_check_callback` / `nep_141_storage_balance_callback` methods have available to actually schedule the real action (`action_to_promise`) plus its own trailing `.then(ext.rlp_execute_callback(...))` [8](#0-7) . The 2 Tgas constant is not derived from any protocol parameter — it is a fixed assumption baked into the contract binary at compile time, just like Solidity's `.transfer()` 2300-gas stipend was a fixed assumption about the cost of an `SSTORE`.

NEAR's own documentation confirms that action/runtime gas costs are not immutable: `max_gas_burnt` was raised from 200 Tgas to 300 Tgas in protocol version 52, and fee/gas parameters are periodically retuned by governance (e.g. NEP-536's `gas_refund_penalty`) [9](#0-8) [10](#0-9) . If a future protocol upgrade raises the base cost of the `Transfer`/`AddKey`/`DeleteKey` action or the `NEW_ACTION_RECEIPT`/`ACTION_RECEIPT_CREATION` base fee beyond what is currently ~1.7 Tgas combined (see `TRANSFER` ≈ 0.23 Tgas and `NEW_ACTION_RECEIPT` ≈ 1.48 Tgas in the gas profile snapshot) [11](#0-10) , the reserved 2 Tgas budget becomes insufficient. The already-deployed Wallet Contract binary cannot be silently patched network-wide (unlike a dApp updating its own deployed code), so this hardcoded value is a durable, systemic risk once baked into deployed wallet accounts.

When the downstream callback (`address_check_callback` or `nep_141_storage_balance_callback`) runs out of gas while trying to schedule the real action promise, the whole callback function call fails/panics. On NEAR, a panicking function call reverts all state changes made *during that call*, but it does **not** revert state changes already committed by the *previous* receipt. Critically, `has_in_flight_tx` was already set to `true` and committed to storage by the prior successful receipt (`rlp_execute` at [12](#0-11)  or `address_check_callback`/`nep_141_storage_balance_callback` at [13](#0-12) [14](#0-13) ). Since the only code paths that ever reset `has_in_flight_tx` back to `false` are the four callback methods themselves [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) , an out-of-gas panic inside one of these callbacks (before it reaches its own `self.has_in_flight_tx = false` line, which executes first, or in a way that the whole call never even starts, e.g. host aborts before entering the function) leaves the flag permanently `true`. Every subsequent call to `rlp_execute` for that account will then immediately short-circuit with `"Error: transaction already in progress, please try again later."` [15](#0-14) , with no method in the contract able to clear it.

### Impact Explanation
This permanently freezes the affected Wallet Contract account — the user's entire wallet (holding NEAR and any ERC-20/NEP-141-emulated assets and any assets reachable only via `rlp_execute`) becomes unusable, since `rlp_execute` is the sole entry point and it always rejects new transactions once `has_in_flight_tx` is stuck `true`. This matches the "permanently frozen funds" and "transaction-triggered halt" acceptance criteria: it is triggered purely by a legitimate transaction (a native EOA-to-EOA base-token transfer to another not-yet-registered eth-implicit account, or an ERC-20 transfer to an unregistered receiver — both are normal, frequent operations of this contract) once the reserved gas is exhausted by a protocol fee change outside the user's control.

### Likelihood Explanation
The trigger condition — a change to NEAR's action/receipt-creation base fees — is not hypothetical; the codebase's own documentation shows these fees have changed before (`max_gas_burnt` 200→300 Tgas, planned `gas_refund_penalty` rollout) [9](#0-8) [10](#0-9) . Because the Wallet Contract hardcodes the 2 Tgas figure at compile time rather than deriving it from runtime parameters or adding a safety margin, any future fee increase silently narrows or eliminates the safety margin for every wallet contract instance already deployed on-chain, with no way to patch already-deployed instances short of a coordinated re-deploy by every user. The bug requires no attacker action beyond normal usage of the contract's transfer/emulation features; the only additional trigger is a protocol parameter change, which is realistically possible over the contract's lifetime.

### Recommendation
Do not hardcode a fixed Tgas figure for non-`FunctionCall` actions. Either (1) query the current runtime action fee parameters via a host function/view call and compute the required gas dynamically with an explicit safety margin, or (2) use NEP-264 gas-weight based allocation (`promise_batch_action_function_call_weight`) so that any unspent prepaid gas is automatically forwarded to the callback instead of relying on a fixed static-gas budget, or (3) add a generous, explicitly-documented safety margin (e.g. 5-10x current usage) and include a recovery/admin path (e.g. a privileged `force_clear_in_flight` guarded by strict conditions, or a timeout-based self-healing mechanism) so a stuck `has_in_flight_tx` can eventually be cleared even if a callback panics.

### Proof of Concept
1. Deploy a Wallet Contract instance (`WalletContract`) for user A's eth-implicit account.
2. User A signs and submits (via a relayer) an RLP-encoded Ethereum transaction representing a base-token transfer to another not-yet-registered eth-implicit account B, causing `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), .. })` to be selected in `inner_rlp_execute` [16](#0-15) .
3. `rlp_execute` commits `has_in_flight_tx = true` and returns a promise that will call `address_check_callback` with `with_static_gas(ADDRESS_CHECK_CALLBACK_GAS + action.gas())` [12](#0-11) .
4. Assume (post future protocol upgrade) the combined base cost of creating the `Transfer` action receipt plus the `RLP_EXECUTE_CALLBACK_GAS` overhead now exceeds `ADDRESS_CHECK_CALLBACK_GAS.saturating_add(Gas::from_tgas(2))`.
5. When `address_check_callback` executes and attempts `action_to_promise(target, action).then(ext.rlp_execute_callback(caller_deposit))`, host-side gas metering aborts the function call with a gas-exceeded error before it can set `self.has_in_flight_tx = false` (or before that state change is committed).
6. The receipt fails; `has_in_flight_tx` remains `true` in contract storage.
7. Any subsequent call to `rlp_execute` by user A immediately returns `"Error: transaction already in progress, please try again later."` [15](#0-14)  forever, with no contract method available to reset the flag — the wallet is permanently bricked.

```markdown
### Gas Refund Fee

After executing the transaction, there might be unspent gas left. For function
calls, this is the normal case, since attaching exactly the right amount of gas
is tricky. Additionally, in case of receipt failure, some actions that did not
start execution will have the execution gas unspent. This gas is converted back
to NEAR tokens and sent as a refund transfer to the original signer.

Before protocol version 78, the full gas amount would be refunded and the refund
transfer action was executed for free. With [NEP-536](https://github.com/near/NEPs/pull/536)
which was implemented in version 78, the plan was to have the network charge a
fee of 5% of unspent gas or a minimum of 1 Tgas. This often removes the need to
send a refund, which avoids additional load on the network, and it compensates
for the load of the refund receipt when it needs to be issued. This is intended
to discourage users from attaching more gas than needed to their transactions.
In the nearcore code, you will find this fee under the name `gas_refund_penalty`.

However, due to existing projects that need to attach more gas than they
actually use, the introduction of the new fee has been postponed. The code is
still in place but the parameters were set to 0 in PR
[#13579](https://github.com/near/nearcore/pull/13579). Among other problems, in
the reference FT implementation, `ft_transfer_call` requires at least 30 TGas
even if most of the time only a fraction of that is burnt. Once all known
problems are resolved, the plan is to try and introduce the 5% / 1 Tgas parameters.
```
