## Analog Found: Unbounded, Attacker‑Controlled Gas‑Fee Deduction Can Drain an Arbitrary Victim UEA via `isCEA` Inbound Payloads

### Title
Unauthenticated, attacker-crafted `UniversalPayload` in `isCEA` inbounds can drain an arbitrary victim UEA's entire `upc` balance via uncapped gas-fee deduction - (File: `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/fees.go`)

### Summary
The external report's bug class is "an unbounded, attacker-influenced fee formula with no protocol-wide cap can consume up to 100% of a user's funds." The Push Chain analog is in the `isCEA` (Chain-Extension-Account) branch of `GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` inbound execution: the `Recipient` UEA and the `UniversalPayload` (including `GasLimit`, `MaxFeePerGas`, `MaxPriorityFeePerGas`, `Data`) are taken verbatim from attacker-controlled, source-chain event data, are executed against that recipient without owner authorization, and the resulting EVM gas cost is billed directly out of the *recipient's own* `upc` balance with no upper bound or cap check.

### Finding Description
For `isCEA=true` inbounds, the recipient UEA is taken directly from the inbound rather than derived from the sender's own identity: `if !strings.HasPrefix(...Recipient..., "0x") {...} else { ueaAddr = common.HexToAddress(utx.InboundTx.Recipient) }` [1](#0-0) . Any external-chain sender can therefore name any deployed UEA as the target simply by crafting the corresponding bridge/gateway calldata; validators only vote on whether that source-chain event happened, not on whether the named recipient consented.

The payload subsequently executed against that UEA (`ExecutePayloadV2` → `CallUEAExecutePayload`, sender = `ueModuleAddr`) uses `utx.InboundTx.UniversalPayload` and `utx.InboundTx.VerificationData` exactly as observed from the source chain [2](#0-1) . Test fixtures for this exact isCEA path show `VerificationData: ""` (empty) being used and the inbound still executing successfully after quorum, with `PcTx` recorded `SUCCESS` [3](#0-2) , i.e. the payload content is not cryptographically bound to the recipient UEA's owner in this flow.

After execution, `DeductGasFeesFromReceipt` computes `gasCost = effectiveGasPrice * gasUsed` from the attacker-supplied `MaxFeePerGas`/`MaxPriorityFeePerGas`/`GasLimit` fields and the actual EVM gas consumed by the attacker-supplied `Data`, then unconditionally burns that amount from the **recipient's** account: [4](#0-3) . `UniversalPayload.ValidateBasic()` only checks that these fields parse as non-negative uint256 strings - there is no ceiling on `MaxFeePerGas`, `GasLimit`, or the resulting `gasCost` [5](#0-4) . `CalculateGasCost` likewise enforces only `maxFeePerGas >= baseFee`, never an upper bound [6](#0-5) .

Because the attacker fully controls both the gas-price parameters and the calldata (`Data`) that determines actual `gasUsed`, they can craft a payload that consumes a large amount of EVM gas against the victim UEA (e.g., an expensive but harmless call), causing `DeductAndBurnFees` to burn the victim's entire pre-existing `upc` balance - funds the victim may have accumulated from unrelated legitimate gas top-ups - with a trivial, cheap source-chain trigger (even a zero/dust-amount inbound, since `GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` support `amount = 0`) [7](#0-6) .

### Impact Explanation
This allows an unprivileged, external-chain attacker to permanently burn (via `bankKeeper.BurnCoins`) the entire `upc` (native gas) balance of any deployed UEA on Push Chain that they did not authorize and did not consent to, purely by naming that UEA as the recipient of a crafted `isCEA` cross-chain bridge/gateway transaction. This is unauthorized loss of protocol/user-controlled funds reachable through ordinary, unprivileged deposit/bridge submission - matching the in-scope impact category of "stealing, draining, permanent loss ... of user or protocol-controlled funds" and "corruption of ... gas fee accounting."

### Likelihood Explanation
The trigger requires only a normal source-chain transaction crafted with attacker-chosen `Recipient`/`UniversalPayload` fields and does not require compromising any validator, TSS participant, or admin key - honest Universal Validators will faithfully observe and vote in exactly what the attacker submitted, since their job is to attest to the source-chain event, not to validate the payload's authorization. Likelihood is high for any UEA that holds a non-trivial `upc` balance from prior legitimate gas top-ups.

### Recommendation
- Require the same signature-based authorization for `isCEA` `UniversalPayload` execution as is enforced for `MsgExecutePayload` (bind the payload cryptographically to the recipient UEA's owner, or require the recipient to opt-in/allowlist source-chain senders permitted to target it as a CEA).
- Enforce a protocol-wide cap on `MaxFeePerGas`/`GasLimit`/derived `gasCost` relative to a sane maximum (e.g., a fraction of the recipient's balance or an absolute ceiling), rejecting or truncating the deduction instead of burning up to 100% of the recipient's balance.
- Do not let an attacker-controlled, unauthenticated payload be executed with `from = ueModuleAddr` (the trusted module sender) against an arbitrary victim UEA; scope `isCEA` recipient targeting to contracts explicitly designed to receive unauthenticated cross-chain calls, not standard UEAs holding user gas funds.

### Proof of Concept
1. Attacker deploys/identifies Victim's UEA address `V` (already funded with `upc` from prior legitimate gas top-ups).
2. Attacker sends a minimal (or zero-amount) bridge/gateway transaction on a supported source chain, encoding a `GAS_AND_PAYLOAD`, `isCEA=true` inbound with `Recipient = V` and a `UniversalPayload` specifying: high `GasLimit`, `MaxFeePerGas` sufficient to cover current `baseFee`, `Data` calling an expensive-but-otherwise-harmless function/loop, and `VerificationData = ""`.
3. Universal Validators observe this real event and vote it in via `MsgVoteInbound` - see `setupInboundCEAGasAndPayloadTest`/`TestInboundCEAGasAndPayload` for the exact fixture shape confirming this executes to completion with empty `VerificationData` [8](#0-7) .
4. `ExecuteInboundGasAndPayload` resolves `ueaAddr = V`, executes the payload via `ExecutePayloadV2`, and `DeductGasFeesFromReceipt` burns `effectiveGasPrice * gasUsed` from `V`'s `upc` balance [9](#0-8) .
5. Repeat/tune `GasLimit`/calldata to maximize `gasUsed` up to `V`'s full `upc` balance, draining it entirely without `V`'s owner ever signing or consenting to the action.

// DeductGasFeesFromReceipt calculates and deducts gas fees from a recipient address
// based on the EVM receipt and universal payload parameters.
// Returns nil if receipt is nil (Go-level error, no EVM tx was created).
// Returns error with gas details if deduction fails (insufficient balance, etc).
func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}
