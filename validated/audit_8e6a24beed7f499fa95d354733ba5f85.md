### Title
Unbounded gzip decompression of user-submitted declare-transaction program allows memory-exhaustion DoS - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The RPC-facing conversion of a user-submitted `BroadcastedDeclareTransaction::V1` decompresses the attacker-controlled, base64-encoded, gzip-compressed Cairo0 `program` field with no size or time bound, mirroring the CVE-2023-22898 ZIP-bomb bug class (unbounded nested/compressed archive decompression causing DoS).

### Finding Description
`decompress_program` reads a base64-decoded gzip stream via `GzDecoder` and calls `read_to_end` into an unbounded `Vec<u8>`, with an explicit TODO acknowledging the missing limit: [1](#0-0) 

This function is invoked from `user_deprecated_contract_class_to_sn_api`, which is used when converting a user-supplied `BroadcastedDeclareTransaction::V1`'s `contract_class` into the internal `starknet_api::deprecated_contract_class::ContractClass` used for execution/simulation: [2](#0-1) 

Notably, the sequencer already has a hardened, size-limited decompression primitive elsewhere (`starknet_api::compression_utils::decompress_with_size_limit`, used e.g. for Sierra program decoding in `DeprecatedGatewaySierraContractClass::convert_to_sierra_contract_class`): [3](#0-2) [4](#0-3) 

but the Cairo0 declare-v1 program path in `apollo_rpc` bypasses this bound entirely, using a raw `GzDecoder::read_to_end` instead — the same unbounded-decompression pattern that Pandora's `extractor.py` suffered from in CVE-2023-22898.

### Impact Explanation
An attacker can submit a `starknet_estimateFee` / `starknet_simulateTransactions` (or trace) RPC request containing a `BroadcastedDeclareV1Transaction` whose `program` field is a small, highly-compressed gzip blob that expands to gigabytes of data. Because `decompress_program` has no output size cap, this forces the node to allocate unbounded memory (and CPU) per request, potentially exhausting node resources and causing the RPC/execution service to crash or become unresponsive, denying service to legitimate transaction submitters/estimators on that node.

### Likelihood Explanation
The endpoint is reachable by any unprivileged JSON-RPC caller with no on-chain fee payment or transaction confirmation required — a single crafted RPC request triggers the unbounded decompression, making this straightforward and cheap to exploit.

### Recommendation
Replace the raw `GzDecoder::read_to_end` call in `decompress_program` (crates/apollo_rpc/src/v0_8/api/mod.rs) with a bounded decompression routine analogous to `starknet_api::compression_utils::decompress_with_size_limit`, enforcing a maximum decompressed size (and ideally a time budget) before returning an error, consistent with how Sierra program decompression already limits size elsewhere in the codebase.

### Proof of Concept
1. Craft a gzip-compressed payload that decompresses to several GB from a few KB of input (a classic "gzip bomb", e.g. compressing a large run of zero bytes).
2. Base64-encode this payload and place it into the `program` field of a `BroadcastedDeclareV1Transaction`'s `contract_class`.
3. Submit this transaction via `starknet_estimateFee` or `starknet_simulateTransactions` to the node's RPC endpoint.
4. `user_deprecated_contract_class_to_sn_api` → `decompress_program` decompresses the payload with no bound, causing large memory allocation and potential OOM/crash of the node process handling the request.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
