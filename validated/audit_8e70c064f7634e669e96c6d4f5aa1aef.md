### Title
Endowment charged to a precompiled-contract call is not tracked for internal-transaction rejection, allowing TRX/TRC10 to become stuck when the precompiled call or the enclosing frame reverts - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress()` moves the `endowment` (TRX or TRC10) from the caller to the precompiled contract's address *before* the precompiled contract is executed, and the code explicitly documents this transfer as "not reversible by rollback." This mirrors the PostOp report's root cause: a pre-payment/transfer is performed ahead of the actual service completion, and if that service (here, the precompiled contract call, or code higher up the call stack) subsequently fails, there is no symmetric mechanism to redeem or roll back the already-moved funds the way ordinary internal calls are handled.

### Finding Description
In `callToAddress()` (regular CALL to a contract) and in `createContractImpl()`, value transfers performed inside an internal call are wrapped in an `InternalTransaction` object, and on failure the code explicitly calls `internalTx.reject()` / `result.rejectInternalTransactions()` to unwind the transfer bookkeeping together with the rest of the state: [1](#0-0) 

By contrast, `callToPrecompiledAddress()` performs the identical kind of value transfer (`MUtil.transfer` for TRX, `addTokenBalance` for TRC10) directly against a child `Repository deposit`, with a comment stating this is explicitly "not reversible by rollback": [2](#0-1) 

The subsequent execution of the precompiled contract can still fail (`out.getLeft() == false`), in which case only the energy handling and stack are adjusted — there is no corresponding compensating transfer, and no `internalTx.reject()`/rejection bookkeeping analogous to the ordinary-call path is applied to the endowment that was already moved to the precompiled contract's address: [3](#0-2) 

This is structurally the same bug class as the paymaster issue: value is moved out of the payer's balance in anticipation of a service (the precompiled call) completing successfully, but the code path for the "service failed" branch does not fully undo or account for the already-executed transfer, and the comment in the code acknowledges this is a known, deliberate deviation from normal rollback semantics rather than a bug that was caught by tests.

### Impact Explanation
If a precompiled contract call fails after the endowment has been moved (e.g., insufficient energy relative to `requiredEnergy`, or the contract's own `execute()` returning `false`), or if some enclosing internal call/parent frame subsequently reverts, TRX or TRC10 tokens that were transferred to the precompiled contract's address are not consistently tracked/rejected the way ordinary CALL-based transfers are. This can result in TRX/TRC10 being moved to a contract address without the corresponding operation completing, i.e., funds effectively "stuck" or unaccounted-for relative to the semantics the rest of the internal-transaction-reject machinery assumes — an accounting-corruption/asset-loss condition analogous to the paymaster's stuck-fund scenario.

### Likelihood Explanation
This code path is reachable by any contract that performs a `CALL`/`CALLCODE`/`DELEGATECALL` with a nonzero `value` to one of the TVM precompiled contract addresses — an anonymous user can trigger this simply by broadcasting a transaction that invokes a contract making such a call. No privileged access is required, only ordinary smart-contract interaction, which keeps likelihood moderate to high, contingent on further confirmation of how deeply this transfer escapes rollback in nested-revert scenarios (which was not fully traceable without reviewing `RepositoryImpl`'s child-commit propagation and internal-transaction-reject logic across nested frames).

### Recommendation
Wrap the endowment transfer performed in `callToPrecompiledAddress()` in the same `InternalTransaction`/`rejectInternalTransactions()` bookkeeping used by `callToAddress()` and `createContractImpl()`, so that a failed precompiled-contract execution (or a later revert of an enclosing frame) properly unwinds the endowment transfer rather than leaving it "not reversible by rollback." At minimum, add an explicit compensating transfer back to the sender when `out.getLeft()` is `false`, and audit all call sites that rely on the current comment's stated behavior to ensure no path allows tokens to be permanently misallocated.

### Proof of Concept
Not independently exploitable-verified beyond static code reading; a concrete PoC would require constructing a contract that:
1. Calls a precompiled contract address with `value > 0` (TRX) or with a TRC10 token transfer, sized so that `contract.getEnergyForData(data) <= msg.getEnergy()` initially but `contract.execute(data)` returns `false` (failure), and
2. Observes that the sender's balance/token balance was decremented and the precompiled contract's address balance was incremented despite `stackPushZero()` signaling call failure, per [4](#0-3) .
