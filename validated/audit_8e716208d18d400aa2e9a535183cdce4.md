### Title
Unbounded global request-cache admission allows unprivileged sender-flooding DoS of gateway handlers - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces `maxCacheSize` as a single global counter shared by all senders, with no per-sender quota inside the cache itself. Because the check-and-insert is done atomically under `c.mu`, the size limit cannot be transiently exceeded by races with `deleteAndSendOnce`, but the cache can still be legitimately filled to `maxCacheSize` by an attacker who supplies many distinct `(sender, messageId)` pairs, causing `"request cache is full"` for all other legitimate senders.

### Finding Description
`NewRequest` computes `key := globalId{request.Body.Sender, request.Body.MessageId}`, locks `c.mu`, checks `len(c.cache) >= int(c.maxCacheSize)`, and only if not full inserts the entry, all under one critical section: [1](#0-0) 

Since the size check and the map insertion happen under the same `sync.Mutex` (acquired once via `defer c.mu.Unlock()`), and `deleteAndSendOnce` acquires the same mutex exclusively for its own delete operation, `len(c.cache)` can never be observed to exceed `maxCacheSize` at any point—Go's `sync.Mutex` provides mutual exclusion, not just memory visibility, so there is no race window here: [2](#0-1) 
This part of the reported concern is not exploitable.

However, the admission control has no notion of per-sender fairness or quota — any caller that can reach `NewRequest` with a fresh `globalId{sender, messageId}` consumes one of the finite `maxCacheSize` slots until the timeout expires or a response arrives. In `functionsHandler.HandleLegacyUserMessage`/`handleRequest`, the `Sender` and `MessageId` values come directly from the inbound `api.Message` body, and cache admission occurs before/independently of any dedicated global fairness control: [3](#0-2) 

The only controls that could stop a flooding attacker are the optional `OnchainAllowlist` and the `UserRateLimiter`, both of which are per-sender-keyed and explicitly optional ("Not specifying ... config disables ... checks"): [4](#0-3) [5](#0-4) 
Even when a per-sender rate limiter is enabled, it only throttles requests per individual sender address; it does nothing to bound the *number of distinct senders* an attacker can present, and Ethereum-style sender addresses/keys are free to generate. Thus an attacker can rotate through arbitrarily many distinct `sender` values (each issuing one or a few requests, staying under any per-sender rate limit) and distinct `messageId`s to occupy all `maxCacheSize` slots in the shared cache, after which every other user's `NewRequest` call returns `"request cache is full"` until the flooding entries time out (`RequestTimeoutMillis`).

### Impact Explanation
This is an unauthenticated resource-exhaustion / denial-of-service condition against gateway handlers backed by `NewRequestCache` (e.g., `functionsHandler`): legitimate Functions users would be unable to submit `secrets_set`/`secrets_list`/heartbeat requests while the cache is saturated by attacker-controlled entries, matching a "DoS of node/service" class impact rather than fund loss or key compromise.

### Likelihood Explanation
Feasibility depends on deployment configuration: if `OnchainAllowlist` is configured and restrictive, sender diversity is bounded and this attack is mitigated; if it is not configured (it is explicitly optional per `FunctionsHandlerConfig`), or if the allowlist is broad, an attacker only needs the ability to generate arbitrary sender identities and message IDs (cheap) and send `maxCacheSize` distinct requests before existing entries time out — a low-cost, repeatable network-level attack requiring no privileges.

### Recommendation
Add a per-sender quota (or weighted/fair-share admission) inside `requestCache`, independent of the global `maxCacheSize`, so that no single identity (or coordinated set of identities without allowlist/stake) can consume more than a bounded fraction of the shared cache; alternatively, require `OnchainAllowlist`/rate limiting to be mandatory (non-optional) for handlers whose cache capacity is a shared, exhaustible resource, and/or reduce `RequestTimeoutMillis` exposure by evicting/prioritizing based on sender request history.

### Proof of Concept
Unit/concurrency test in `core/services/gateway/handlers/common/requestcache_test.go` style:
1. Create `NewRequestCache[T](timeout, maxCacheSize)` with small `maxCacheSize` (e.g., 100) and a long `timeout`.
2. Spawn `maxCacheSize` goroutines, each calling `NewRequest` with a unique `sender` (simulating free identity generation) and unique `messageId`, all succeeding.
3. Assert `len(c.cache) == maxCacheSize`.
4. Have a "legitimate" additional call to `NewRequest` with a new unique sender/messageId and assert it returns `"request cache is full"`.
5. (Separately, to validate the race claim is false) Spawn `maxCacheSize+K` goroutines calling `NewRequest` concurrently while other goroutines concurrently invoke `deleteAndSendOnce`/timeouts, and assert `len(c.cache)` never exceeds `maxCacheSize` at any sampled point (expected to pass, confirming the mutex-based admission is correctly atomic).

func (c *requestCache[T]) deleteAndSendOnce(key globalId, callbackResponse handlers.UserCallbackPayload) error {
	c.mu.Lock()
	entry, deleted := c.cache[key]
	delete(c.cache, key)
	c.mu.Unlock()
	if deleted {
		entry.timeoutTimer.Stop()
		return entry.SendResponse(callbackResponse)
	}

	return nil
}

func (h *functionsHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	sender := common.HexToAddress(msg.Body.Sender)
	if h.allowlist != nil && !h.allowlist.Allow(sender) {
		h.lggr.Debugw("received a message from a non-allowlisted address", "sender", msg.Body.Sender)
		promHandlerError.WithLabelValues(h.donConfig.DonId, ErrNotAllowlisted.Error()).Inc()
		return ErrNotAllowlisted
	}
	if h.userRateLimiter != nil && !h.userRateLimiter.Allow(msg.Body.Sender) {
		h.lggr.Debugw("rate-limited", "sender", msg.Body.Sender)
		promHandlerError.WithLabelValues(h.donConfig.DonId, ErrRateLimited.Error()).Inc()
		return ErrRateLimited
	}
	if msg.Body.Method == MethodSecretsSet && h.subscriptions != nil && h.minimumBalance != nil {
		balance, err := h.subscriptions.GetMaxUserBalance(sender)
		if err != nil {
			h.lggr.Debugw("error getting max user balance", "sender", msg.Body.Sender, "err", err)
		}
		if balance == nil {
			balance = big.NewInt(0)
		}
		if err != nil || balance.Cmp(h.minimumBalance.ToInt()) < 0 {
			h.lggr.Debugw("received a message from a user having insufficient balance", "sender", msg.Body.Sender, "balance", balance.String())
			return fmt.Errorf("sender has insufficient balance: %v juels", balance.String())
		}
	}
	switch msg.Body.Method {
	case MethodSecretsSet, MethodSecretsList:
		return h.handleRequest(ctx, msg, callback)
	case MethodHeartbeat:
		if _, ok := h.allowedHeartbeatInitiators[msg.Body.Sender]; !ok {
			h.lggr.Debugw("received heartbeat request from a non-allowed sender", "sender", msg.Body.Sender)
			promHandlerError.WithLabelValues(h.donConfig.DonId, ErrNotAllowlisted.Error()).Inc()
			return ErrUnsupportedMethod
		}
		return h.handleRequest(ctx, msg, callback)
	default:
		h.lggr.Debugw("unsupported method", "method", msg.Body.Method)
		promHandlerError.WithLabelValues(h.donConfig.DonId, ErrUnsupportedMethod.Error()).Inc()
		return ErrUnsupportedMethod
	}
}
