### Title
Treating a transient L1EventsProviderClient failure as a hard transaction-invalidity aborts entire block validation - (File: crates/apollo_batcher/src/transaction_provider.rs)

### Summary
`ValidateTransactionProvider::get_txs` treats any internal/communication error from the `l1_events_provider_client` (e.g., the provider being mid-restart, unresponsive, or otherwise temporarily broken) identically to a definitively invalid L1Handler transaction. This single external-dependency failure aborts validation of the *entire* batch of buffered transactions — including unrelated, perfectly valid mempool transactions — causing the validator to reject the whole proposal.

### Finding Description
`ValidateTransactionProvider::get_txs` calls `l1_events_provider_client.validate(...)` for every `L1Handler` transaction found in the buffered batch. Any error from this call (RPC failure, provider not yet bootstrapped, provider mid-restart, etc.) is unconditionally coerced into `L1ValidationStatus::Invalid(L1InvalidValidationStatus::L1EventsProviderError)` via `.unwrap_or(...)`, exactly the same code path used for genuinely invalid transactions (`AlreadyIncludedOnL2`, `ConsumedOnL1`, `NotFound`, etc.): [1](#0-0) 

Once any transaction in the batch is deemed invalid this way, `get_txs` immediately returns `Err(TransactionProviderError::L1HandlerTransactionValidationFailed { .. })` for the whole call, discarding the rest of the already-buffered batch (which may contain many unrelated, valid `RpcTransaction`s): [2](#0-1) 

This error is then explicitly special-cased in the block builder to unconditionally fail block validation when the caller is a validator: [3](#0-2) 

The batcher's own comments acknowledge that the L1 events provider is expected to legitimately be transiently unavailable — e.g. right after `start_block` fails the provider is expected to "restart and bootstrap again" — yet no distinction is made between "provider is temporarily down" and "transaction is truly invalid": [4](#0-3) 

The L1 events scraper tests confirm the provider does legitimately crash/restart during normal operation (e.g. on L1 reorg detection), which is exactly the kind of transient malfunction that would trigger this path: [5](#0-4) 

This is directly analogous to the reported AssetManager bug class: a single downstream "adapter" (here, the local `L1EventsProviderClient`) becoming temporarily broken/paused causes the entire higher-level operation (here, block *validation*, analogous to `deposit()`/`withdraw()`) to fail outright rather than degrading gracefully or isolating the failure to just the affected sub-operation.

### Impact Explanation
Whenever a validator's local L1 events provider is unavailable (restarting after an L1 reorg, RPC hiccup, not-yet-bootstrapped, etc.) and it is asked to validate a proposal containing even one `L1Handler` transaction, the validator will fail validation of the entire block/batch and abort the block build (`FailOnErrorCause::L1HandlerTransactionValidationFailed` → `abort_block`), causing it to send a negative/NIL vote on an otherwise perfectly valid proposal. If this transient condition is correlated across validators (e.g., a shared L1 reorg triggers `NeedsRestart` on multiple nodes' scrapers roughly simultaneously), a quorum of validators could reject valid proposals containing L1Handler transactions in the same round, causing repeated view changes and stalling block finalization — i.e., the network becomes unable to confirm new transactions/blocks that include L1Handler transactions until providers recover.

### Likelihood Explanation
This is triggered purely by an existing infrastructure condition — an unresponsive/restarting local L1 events provider — combined with a proposal containing an L1Handler transaction, which requires no attacker action beyond a normal L1-message-sourced transaction being included in a block by any proposer. L1 reorgs and provider restarts are an expected/normal occurrence per the scraper's own test suite, making this a realistic operational condition rather than a purely theoretical one.

### Recommendation
Distinguish transport/communication failures of the `l1_events_provider_client` from genuine transaction invalidity. On a provider-communication error, the validator should not immediately convert it into a hard `Invalid` verdict that aborts the whole batch; instead it should retry, skip/defer just that transaction (while still processing the rest of the batch), or otherwise degrade gracefully so a single transient adapter outage cannot fail validation of an entire, otherwise-valid proposal.

### Proof of Concept
1. A validator's `l1_events_provider_client` is mid-restart (e.g., following `L1EventsScraperError::NeedsRestart` as shown in `crates/apollo_l1_events/src/l1_scraper_tests.rs`), so any `validate()` call returns an error.
2. Consensus delivers a proposal to this validator containing a mix of valid `RpcTransaction`s and one `L1Handler` transaction (via `apollo_batcher::batcher::validate_block` → `ValidateTransactionProvider`).
3. In `get_txs`, the `L1Handler` tx's `validate()` call errors out and is coerced to `Invalid(L1EventsProviderError)`; `get_txs` returns `Err(L1HandlerTransactionValidationFailed)` for the whole buffered batch.
4. `add_txs_to_executor` in `block_builder.rs` converts this into `FailOnErrorCause::L1HandlerTransactionValidationFailed`, aborting the block build entirely — even though the L1Handler transaction and all other transactions in the batch may in fact be fully valid.
