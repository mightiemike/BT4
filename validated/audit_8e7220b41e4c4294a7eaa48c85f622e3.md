### Title
Finalizing an L1 message cancellation removes the record of an already-committed L1 handler transaction without blocking - ([File: crates/apollo_l1_events/src/transaction_manager.rs])

### Summary
`TransactionManager::finalize_cancellation` deletes a transaction's record from `self.records` unconditionally whenever a `TransactionCanceled` L1 event is scraped for its hash, even if the record's state is `Committed` (i.e., the L1→L2 message was already accepted and included in a committed L2 block). The function only emits a `warn!` when the state isn't `CancellationStartedOnL2` — it never aborts the removal. This mirrors the reported bug class of "no check on accepted/committed action before cancellation."

### Finding Description
`mark_cancellation_request` (in `transaction_record.rs`) correctly guards the *request* phase: if the record is already committed, it refuses to transition the state to `CancellationStartedOnL2`, only warning. [1](#0-0) 

However, when the L1 cancellation is later *finalized* (the L1 sender waited out the timelock and called the L1 contract's finalize-cancellation, producing a `TransactionCanceled` event), `TransactionManager::finalize_cancellation` checks the state only to log a warning, then unconditionally removes the record from `self.records` regardless of whether it is `Committed`: [2](#0-1) 

`commit_txs`, the routine that marks transactions as `Committed`, explicitly documents (and relies on) the invariant that "records are only removed via L1 cancellation/consumption, which can't race a block": [3](#0-2) 

`finalize_cancellation` breaks that documented invariant: it can remove a record whose transaction has already been committed to L2. Downstream, `is_committed()` relies on the record's presence: [4](#0-3) 

Once the record is gone, `is_committed(tx_hash)` returns `false` for a transaction that was in fact already executed on L2. If the same `tx_hash` is later re-observed (e.g. through catch-up/re-sync scraping, a delayed/duplicate L1 event, or a differently-timed L1 event scraper on another node), `add_tx`/`create_record_if_not_exist` will happily recreate it as a fresh `Pending` record, making an already-executed L1 handler message eligible again for `get_txs`/`validate_tx` and proposable for inclusion in a future block. [5](#0-4) 

Because L1 event scraping/timing is not perfectly synchronized across sequencer nodes, different honest nodes can observe the `TransactionCanceled` event relative to the commit at different local times, causing some nodes to prematurely wipe the committed record (state divergence) while others still hold `Committed` — an unauthorized re-execution/replay of an already-included L1→L2 message is possible on the node(s) that lost the record.

### Impact Explanation
An already-committed L1 handler transaction's bookkeeping record can be erased due to a late-arriving finalize-cancellation event, defeating the deduplication/replay protection that the transaction manager is supposed to guarantee ("records are only removed via L1 cancellation/consumption, which can't race a block"). This can lead to double-processing (re-proposal/re-validation) of an L1→L2 message that already mutated L2 state, or to divergence between honest sequencer nodes regarding whether a given `tx_hash` is committed — both directly map to the accepted impact categories (unauthorized action / honest-node divergence).

### Likelihood Explanation
This requires an ordinary, unprivileged L1 message sender to (1) send an L1→L2 message that gets included in an L2 block, and (2) separately request+finalize cancellation of that same message via the standard L1 message-canceler flow. No malicious operator/proposer/node behavior is needed — only the natural race between the L1 cancellation finalize event and the L2 commit, which the code's own comments acknowledge as a scenario the design assumes "can't race a block," yet doesn't actually enforce.

### Recommendation
In `finalize_cancellation`, check `record.committed` (or `record.state == TransactionState::Committed`) before removing the record; if the transaction is already committed, skip the removal entirely (treat the late cancellation event as a no-op, consistent with "commit beats cancellations" semantics already implemented in `update_time_based_state` and `mark_cancellation_request`), rather than merely logging a warning and proceeding to delete it.

### Proof of Concept
1. Scraper adds L1 handler tx `T` (record created as `Pending`).
2. Sequencer proposes/commits a block including `T` → `mark_committed()` sets `record.committed = true`, `state = Committed`.
3. Meanwhile, on L1, `T`'s sender calls the message-cancellation-request function; the resulting `Event::TransactionCancellationRequested` may be scraped before or after step 2 — either way `mark_cancellation_request` correctly refuses to move the state once committed (only warns).
4. After the L1 cancellation timelock passes, the sender finalizes the cancellation on L1, producing `Event::TransactionCanceled`.
5. The scraper delivers this event; `finalize_cancellation(T.tx_hash)` is invoked: `record.state == Committed != CancellationStartedOnL2` → logs a warning but still executes `self.records.remove(&tx_hash)`.
6. `is_committed(T.tx_hash)` now returns `false`; if `T` is re-scraped/re-added (e.g., during catch-up or via a duplicate scrape), it is treated as a brand-new `Pending` transaction eligible for proposal again, despite having already been executed on L2.

    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }

    /// Adds a transaction to the transaction manager, return true if the transaction was
    /// successfully added. If the transaction is occupied or already had its hash stored as
    /// committed, it will not be added, and false will be returned.
    // Note: if only the committed hash was known, the transaction will "fill in the blank" in the
    // committed txs storage, to account for commit-before-add tx scenario.
    pub fn add_tx(
        &mut self,
        tx: L1HandlerTransaction,
        block_timestamp: BlockTimestamp,
        scrape_timestamp: UnixTimestamp,
    ) {
        let tx_hash = tx.tx_hash;
        // If exists, return false and do nothing. If not, create the record as a HashOnly payload.
        let is_new_record = self.create_record_if_not_exist(tx_hash);
        // Replace a HashOnly payload with a Full payload. Do not update a Full payload.
        // A hash only payload can come from catching up from state sync, and then updated by
        // add_events from the scraper. However, if we get the same full tx twice (from the scraper)
        // it could indicate a double-scrape, and may cause the tx to be re-added to the proposable
        // index.
        self.with_record(tx_hash, move |record| match &record.tx {
            TransactionPayload::HashOnly(_) => {
                if !is_new_record {
                    info!(
                        "Transaction {tx_hash} already exists as a HashOnly payload. It was \
                         probably gotten via state sync component, and is now updated with a Full \
                         payload."
                    );
                }
                record.tx.set(tx, block_timestamp, scrape_timestamp);
                // Counts the HashOnly -> Full transition, regardless of whether the HashOnly
                // was just created here or pre-existed from state sync.
                L1_MESSAGE_SCRAPER_L1_HANDLER_TX_COUNT.increment(1);
            }
            TransactionPayload::Full { tx: _, created_at_block_timestamp: _, scrape_timestamp } => {
                warn!(
                    "Transaction {tx_hash} already exists as a Full payload, scraped at \
                     {scrape_timestamp}. This could indicate a double scrape. Ignoring the new \
                     transaction."
                );
            }
        });
    }

    pub fn finalize_cancellation(&mut self, tx_hash: TransactionHash) {
        let Some(record) = self.records.get(&tx_hash) else {
            info!(
                "Attempted to finalize cancellation for non-existent transaction: {tx_hash}. This \
                 can happen if the transaction was too old to be scraped (e.g. it was created \
                 before we started scraping)."
            );
            return;
        };

        // Regardless of the state of the tx in the record, if we get the cancellation event from
        // the L1 contract, we delete this tx from the records and from the proposable index, even
        // if it was Pending and ready to be proposed (which is not supposed to happen, hence the
        // warning).
        if record.state != TransactionState::CancellationStartedOnL2 {
            warn!(
                "Attempted to finalize cancellation for transaction {tx_hash} that is not in the \
                 cancellation started on L2 state, but in the {:?} state.",
                record.state
            );
        }
        // This will also call maintain_indices to remove the tx from the proposable index.
        self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());
        self.records.remove(&tx_hash);
    }
