## Title
Missing chain-binding component in the NEP-461/NEP-366 `DelegateAction` signing domain allows cross-network signature replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The Velodrome finding is a classic "incomplete `EIP712Domain` typehash" bug class: the domain separator used to bind a signature to a particular signing context is missing a component (`version`), so the on-chain verification domain diverges from the one the signature is actually intended for. The nearcore analog is in the `SignableMessage`/NEP-461 tagging scheme used to sign `DelegateAction`/`DelegateActionV2` for meta-transactions (NEP-366/NEP-611): the signed payload is only `{discriminant, delegate_action}` and never includes any network/chain-binding value (no genesis hash, no `chain_id`, no `block_hash`), unlike ordinary `SignedTransaction`s which are chain-bound via `block_hash` and `check_transaction_validity_period`.

### Finding Description
`SignableMessage::sign` / `verify` hash exactly `{discriminant, msg}`: [1](#0-0) 

`DelegateAction::get_nep461_hash` / `SignedDelegateAction::verify` build the signed digest purely from the `DelegateAction` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`) plus the NEP discriminant — nothing chain-specific: [2](#0-1) [3](#0-2) 

The same is true for `VersionedSignedDelegateAction`/`DelegateActionV2` (V2 nonce, no chain binding): [4](#0-3) 

By contrast, a normal `SignedTransaction` is bound to a specific chain/fork through its `block_hash` field, which is validated against the actual chain store (`check_transaction_validity_period`), so a `SignedTransaction` created for chain A cannot be accepted on chain B (the referenced `block_hash` simply won't resolve there): [5](#0-4) [6](#0-5) 

But this replay protection is a property of the *outer* transaction the relayer signs, not of the *inner* `SignedDelegateAction` that the end user (Alice) signs and hands to a relayer off-chain. The relayer fully controls the outer transaction's `block_hash`/nonce, and on-chain validation of the inner delegate only checks `max_block_height`, `sender_id == tx.receiver_id`, and the sender's access-key nonce — never anything tying the signature to a specific network/genesis: [7](#0-6) 

This is architecturally the same root cause as the Velodrome report: the signing/verification "domain" for a delegated authorization is missing a required binding component, so a signature intended for one context (chain/network/fork) is valid and accepted in another. NEAR runs multiple long-lived networks (mainnet, testnet) plus operators can spin up private/forked chains from the same genesis binaries, and it is common practice for users/tools to reuse the same keypair for the same `AccountId` across these networks. Since nothing in the meta-tx signing scheme depends on a network identifier, a `SignedDelegateAction` signed by Alice off-chain (intended for use on one network) is bytewise valid and will pass `SignedDelegateAction::verify()`/`apply_delegate_action` on any other NEAR-protocol chain where `sender_id` exists with the same public key and an access-key nonce below the signed nonce and current height below `max_block_height`.

### Impact Explanation
Any party who obtains a `SignedDelegateAction` (the off-chain artifact users hand to relayers, per NEP-366) can replay it as an action inside a transaction on a different NEAR network/fork sharing the same account/key state, causing the delegated actions (e.g., token transfers, `AddKey`, contract calls) to execute under the victim's identity without the additional confirmation the victim believed was scoped to a specific network. This is an invalid-state-transition-acceptance / unauthorized-value-movement class of vulnerability that maps directly to the required "Accept" criteria: `apply_delegate_action` accepts and executes a signature the signer never intended to authorize in that execution context, because `DelegateAction`/`DelegateActionV2` binds only to the NEP-number/version discriminant, not to any per-network context — the exact same "incomplete domain" root cause as the reported EIP-712 issue, where a signature computed under a subtly different (but overlapping) domain is nonetheless accepted.

### Likelihood Explanation
Reaching this requires only a single relayer-submitted transaction embedding an `Action::Delegate`/`Action::DelegateV2`; no validator or node compromise is needed — a relayer (or anyone who intercepts/receives the off-chain `SignedDelegateAction`) is by design a normal, unprivileged transaction submitter. The likelihood of exploitation hinges on account/key reuse across networks sharing the same nearcore state machine, which is a realistic occurrence for test/mirroring setups (the `tools/mirror` code in this very repo re-signs delegate actions when mapping keys between chains, showing this exact scenario — a delegate action created for one chain being carried to another — is an operationally supported pattern): [8](#0-7) 

### Recommendation
Include a network/chain-binding value in the NEP-461 signable payload for delegate actions, analogous to fixing the domain typehash in the report (adding the missing `version`/`chainId` field to the EIP-712 domain). Concretely:
- Add a chain-identifying field (e.g. genesis hash or a configured `chain_id`) to `SignableMessage`/`DelegateAction`/`DelegateActionV2` so `get_nep461_hash` incorporates it, and reject verification if it doesn't match the executing chain's genesis/chain id.
- Alternatively/additionally, require the inner delegate action to reference a `block_hash` validated the same way `SignedTransaction.block_hash` is validated in `check_transaction_validity_period`, giving delegate actions the same chain-scoping guarantee normal transactions already have.

### Proof of Concept
1. Two NEAR networks/forks N1 and N2 share the same nearcore binary/state format and happen to have account `alice.near` initialized with the same public key (a supported/likely scenario, as evidenced by `tools/mirror`, which explicitly re-signs delegate actions while carrying state between chains — `tools/mirror/src/genesis.rs:44-91`).
2. Alice signs a `SignedDelegateAction` off-chain (per NEP-366 flow in `docs/architecture/how/meta-tx.md`) intending it to be relayed only on N1, e.g. to pay a relayer 0.1 $FT and transfer 10 $FT to John on N1.
3. A relayer (or anyone who obtains the `SignedDelegateAction` bytes, which are explicitly meant to be forwarded off-chain to third parties) instead wraps it in a fresh outer `SignedTransaction` on N2, with a valid `block_hash`/nonce for N2 that the relayer fully controls.
4. On N2, `apply_delegate_action` calls `signed_delegate_action.verify()` (`runtime/runtime/src/actions.rs:474`), which succeeds because the digest computed by `get_nep461_hash` (`core/primitives/src/action/delegate.rs:353-357`) contains no N1/N2-distinguishing data — only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`, and the fixed NEP-366 discriminant.
5. As long as `alice.near`'s access-key nonce on N2 is below the signed `nonce` and the current block height on N2 is below `max_block_height`, the delegate action executes on N2 — moving funds/executing actions Alice authorized for N1 only.

pub fn check_transaction_validity_period(
    chain_store: &ChainStoreAdapter,
    prev_block_header: &BlockHeader,
    base_block_hash: &CryptoHash,
    transaction_validity_period: BlockHeightDelta,
) -> Result<(), InvalidTxError> {
    let base_header =
        chain_store.get_block_header(base_block_hash).map_err(|_| InvalidTxError::Expired)?;

    metrics::CHAIN_VALIDITY_PERIOD_CHECK_DELAY
        .observe(prev_block_header.height().saturating_sub(base_header.height()) as f64);

    // First check the distance between blocks
    if prev_block_header.height() > base_header.height() + transaction_validity_period {
        return Err(InvalidTxError::Expired);
    }

    // Then check if there is a path between the blocks (`base` is an ancestor of `prev`)
    validity_period_validate_is_ancestor(&base_header, prev_block_header, chain_store)
}

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
