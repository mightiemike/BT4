### Title
Unbounded `ActiveBallotIDs` scan on every new-ballot creation causes linear-then-quadratic gas/compute blowup - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
`CreateBallot` unconditionally calls `k.ExpireBallotsBeforeHeight(ctx, blockHeight)` before creating any new ballot. That function does a full iteration over the entire `ActiveBallotIDs` collection, fetching each ballot to check its expiry height, every single time a brand-new ballot is created. Since a new ballot is created for every distinct inbound/outbound observation (keyed by `utx_key`/`outbound_id`, which an attacker fully controls by generating many small, distinct external-chain deposits), the size of `ActiveBallotIDs` can be driven up without bound by ordinary unprivileged deposit activity, and every subsequent vote that creates a new ballot re-pays the cost of scanning all of them — the exact "iterate over an ever-growing collection on a hot path" bug class described in the `revokeVotes` report.

`ExpireBallotsBeforeHeight` itself performs a full, unbounded iteration over `ActiveBallotIDs`, fetching each ballot from the store to check expiry: [3](#0-2) 

`VoteOnBallot` is the shared machine behind `MsgVoteInbound` and `MsgVoteOutbound`, both of which are gasless whitelisted messages voted on by bonded Universal Validators for events that originate from ordinary, unprivileged external-chain deposits: [4](#0-3) 

Each `Inbound`/`Outbound` ballot ID is derived from attacker-controllable fields such as `source_chain:tx_hash:log_index`, so an unprivileged attacker can create arbitrarily many distinct external-chain deposit transactions (no malicious validator or admin action required — honest validators dutifully vote every legitimate observation via `RecordInboundVote`/`RecordOutboundVote`): [5](#0-4) 

Unlike Celo's `Governance.dequeued`, which the Celo team argued is bounded by `concurrentProposals` and `dequeueFrequency`, there is no analogous cap here on the number of concurrently `PENDING`/active ballots that can exist at once. Any number of distinct low-value deposits across any number of connected external chains will each spawn a new ballot, and each such new-ballot creation re-scans the *entire* `ActiveBallotIDs` set.

### Impact Explanation
As `ActiveBallotIDs` grows, the per-vote cost of `ExpireBallotsBeforeHeight` grows linearly, and because it runs on every new-ballot creation, the cumulative cost of processing a burst of N distinct deposits is O(N²). This is a non-network-level, unprivileged-attacker-reachable denial-of-service vector against the core voting path shared by `MsgVoteInbound`, `MsgVoteOutbound` (and transitively the ballot-driven universal execution pipeline), since `VoteOnBallot` cannot finalize any inbound/outbound observation without first passing through `GetOrCreateBallot → CreateBallot → ExpireBallotsBeforeHeight`. In the worst case this can push block processing time/gas for legitimate validator votes to unacceptable levels, stalling ballot finalization and hence universal execution (UTX creation, PRC20 minting, outbound dispatch) chain-wide.

### Likelihood Explanation
Triggering it does not require compromising any validator, admin, or TSS participant — an attacker only needs to generate many cheap, distinct deposit transactions on one or more supported external chains (e.g., dust transfers), which honest validators will faithfully observe and vote on per protocol design. The number of ballots an attacker can force into existence is bounded only by the cost of generating distinct external-chain transactions, which on many chains is very low. The `expiryAfterBlocks` window means ballots do eventually leave `ActiveBallotIDs`, but nothing stops an attacker from sustaining a rate of new-ballot creation that keeps the active set large indefinitely, especially since each `ExpireBallotsBeforeHeight` call itself is the only mechanism that prunes the set (i.e., pruning cost scales with the very quantity being pruned).

### Recommendation
Decouple ballot expiry sweeping from the hot per-vote path. Options:
- Move ballot expiry to a periodic `EndBlock`/`BeginBlock` job that processes a bounded number of stale entries per block (paginated sweep) instead of a full scan on every `CreateBallot`.
- Cap the number of ballots expired per `CreateBallot` invocation, and/or maintain a height-ordered secondary index (e.g., keyed by `BlockHeightExpiry`) so expired ballots can be found and removed in O(k) instead of O(n) where k is the number actually expired.
- Consider bounding the number of concurrently active ballots (mirroring Celo's `concurrentProposals` bound) or rate-limiting new-ballot creation per source chain to cap attacker-driven growth of `ActiveBallotIDs`.

### Proof of Concept
1. An attacker sends a large number (N) of distinct low-value deposit transactions on a connected external chain (or across several connected chains), each with a unique `tx_hash`/`log_index`, well within the ballot's `expiryAfterBlocks` window.
2. Honest Universal Validators observe and submit `MsgVoteInbound` for each distinct deposit, each landing on a brand-new `utx_key`/ballot ID.
3. Each such vote invokes `VoteOnBallot → GetOrCreateBallot → CreateBallot → ExpireBallotsBeforeHeight`, which iterates the full `ActiveBallotIDs` set — now containing up to N-1 prior entries — before the new ballot can even be created.
4. As N grows, the cumulative work done purely by `ExpireBallotsBeforeHeight` scans across the batch grows quadratically (O(N²)), degrading validator vote processing time/gas for the entire voting pipeline without any validator, admin, or TSS compromise — solely from ordinary, attacker-generated external-chain deposit spam.

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
