### Title
DelegateAction (NEP-366 meta-transactions) signatures omit any chain/network identifier, enabling cross-network replay - (File: core/primitives/src/action/delegate.rs)

### Summary
`DelegateAction` and `DelegateActionV2` are signed by the end user off-chain and handed to a relayer, who wraps them in a `SignedTransaction` and submits them to a specific chain. Unlike an ordinary `Transaction`, whose signed payload contains a `block_hash` bound to a specific chain's block history (and is explicitly checked against chain ancestry in `check_transaction_validity_period`), the bytes that the user actually signs for a `DelegateAction` contain no chain-identifying value at all. [2](#0-1) [3](#0-2) [4](#0-3) 

The signed hash is `hash(borsh(MessageDiscriminant{NEP-366 tag} || DelegateAction{sender_id, receiver_id, actions, nonce, max_block_height, public_key}))`. Compare this to a plain transaction, which is explicitly documented as being replay-protected across chains via `block_hash`: [5](#0-4) [6](#0-5) 

No equivalent field exists for `DelegateAction`. Validation of a delegate action on execution (`validate_delegate_action_key`) checks only the access key's nonce state and `max_block_height` against the *local* chain's block height — it never checks that the delegate action was created for *this* chain in particular: [7](#0-6) 

### Finding Description
NEAR intentionally supports many independently operated, protocol-compatible networks that share the same account-id namespace and key format (mainnet, testnet, and additional forked/mirrored networks — nearcore even ships a `tools/mirror` utility whose entire purpose is to replay one chain's traffic onto another forked chain). The `tools/mirror` README itself demonstrates why this matters for regular transactions: a transaction cannot be replayed unmodified onto a different (even a forked/cloned) chain because its signed bytes embed the source chain's `block_hash`, so the tool must remap keys to produce validly-signed transactions for the target chain: [8](#0-7) 

`DelegateAction`, however, has no such protection baked into its signature. If the same `sender_id`/`public_key` pair exists on two different NEAR networks with compatible access-key nonce/`max_block_height` state (e.g., a user reusing the same account name and key across mainnet/testnet, a private enterprise deployment sharing state with mainnet, or a forked/mirrored chain where public keys were not fully remapped), a `SignedDelegateAction` produced for use on one network can be taken — verbatim — by any relayer or third party who has seen it off-chain (relayers are explicitly meant to receive these off-chain, per NEP-366) and wrapped into a fresh outer `SignedTransaction` (which the relayer signs normally, satisfying that network's own `block_hash`/nonce checks) and submitted to the other network. The runtime accepts it because `validate_delegate_action_key` only checks the local access key's nonce/`max_block_height`/permissions — it has no way to detect that the inner delegate action was authorized for a different chain.

### Impact Explanation
Successful replay executes the sender's authorized `actions` (which may include token transfers, `AddKey`, `DeleteKey`, `FunctionCall` with deposits, etc.) against the sender's account on a network the sender never intended, resulting in unauthorized value movement or unauthorized account modification (e.g., an attacker-controlled relayer adding their own key to the victim's account on the second network, or moving funds there). This matches the "unauthorized value movement" / "invalid state transition acceptance" impact categories, and is directly analogous to the reported `createStream()` cross-chain replay because both root causes are the same: a deterministically/off-chain-signed authorization message that omits any chain-binding nonce/identifier that its "primary" counterpart (the outer transaction, or `create2` salt) does include.

### Likelihood Explanation
Exploitation requires the victim's account/key/nonce state to be reachable in a compatible way on a second network — this is plausible for the many legitimate scenarios where NEAR account holders or enterprises reuse account ids and keys across mainnet, testnet, and private/forked NEAR-compatible networks, and the meta-transaction flow already requires the signed payload to be transmitted off-chain to third-party relayers before being included on-chain, widening the exposure window beyond what a normal transaction (submitted directly to a single network) has.

### Recommendation
Bind the NEP-366/NEP-461 signable message for `DelegateAction`/`DelegateActionV2` to the target chain, e.g. by including the genesis hash or a network/chain identifier (analogous to `block_hash` in `Transaction`) inside the hashed payload in `DelegateAction::get_nep461_hash` / `VersionedDelegateActionPayload::get_nep461_hash`, and validate it against the local chain in `validate_delegate_action_key`.

### Proof of Concept
1. Two NEAR-protocol-compatible networks (`N1`, `N2`) exist where account `alice.near` has been created with the same `public_key` and compatible access-key nonce on both (e.g. a private/forked deployment created via `tools/mirror`, or a user who registered the same account/key pair on both networks).
2. Alice signs a `DelegateAction{sender_id: "alice.near", receiver_id: "bob.near", actions: [Transfer], nonce: N, max_block_height: H, public_key}` intended for use by a relayer on `N1`, per the flow in `core/primitives/src/action/delegate.rs` (`SignedDelegateAction::sign`) and hands it to the relayer off-chain.
3. Any party in possession of the `SignedDelegateAction` bytes (the relayer, or anyone who observed it) wraps the identical bytes as `Action::Delegate` inside a new outer `SignedTransaction` addressed to `N2`, signing the outer transaction normally with a relayer key valid on `N2` (satisfying `N2`'s own `block_hash`/nonce checks).
4. `N2`'s runtime processes the receipt; `validate_delegate_action_key` (`runtime/runtime/src/actions.rs`) only checks the local access key nonce/`max_block_height`/permissions for `alice.near` on `N2` — since these match, the transfer action executes on `N2`, moving Alice's funds there even though she only authorized it for `N1`.

fn validate_delegate_action_key(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    delegate_action: VersionedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let sender_id = delegate_action.sender_id();
    let public_key = delegate_action.public_key();
    // 'sender_id' account existence must be checked by a caller
    let mut access_key = match get_access_key(state_update, sender_id, public_key)? {
        Some(access_key) => access_key,
        None => {
            result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                InvalidAccessKeyError::AccessKeyNotFound {
                    account_id: sender_id.clone(),
                    public_key: public_key.clone().into(),
                },
            )
            .into());
            return Ok(());
        }
    };

    // A plain nonce advances the single access_key.nonce and forbids gas keys;
    // a gas key nonce advances one of the gas key's nonces selected by
    // nonce_index.
    let delegate_nonce = delegate_action.nonce();
    let (current_nonce, nonce_update) = match delegate_nonce {
        TransactionNonce::Nonce { .. } => {
            if access_key.gas_key_info().is_some() {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresNonGasKey,
                )
                .into());
                return Ok(());
            }
            (access_key.nonce, DelegateNonceUpdate::AccessKey)
        }
        TransactionNonce::GasKeyNonce { nonce_index, .. } => {
            let Some(gas_key_info) = access_key.gas_key_info() else {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresGasKey,
                )
                .into());
                return Ok(());
            };
            if nonce_index >= gas_key_info.num_nonces {
                result.result = Err(ActionErrorKind::DelegateActionInvalidNonceIndex {
                    nonce_index,
                    num_nonces: gas_key_info.num_nonces,
                }
                .into());
                return Ok(());
            }
            // The index is range-checked above and gas keys initialize every
            // nonce row at creation, so a missing row is inconsistent state.
            let current_nonce =
                get_gas_key_nonce(state_update, sender_id, public_key, nonce_index)?.ok_or_else(
                    || {
                        StorageError::StorageInconsistentState(format!(
                            "gas key nonce row missing for {} {} at in-range index {nonce_index} (num_nonces {})",
                            sender_id, public_key, gas_key_info.num_nonces,
                        ))
                    },
                )?;
            (current_nonce, DelegateNonceUpdate::GasKey { nonce_index })
        }
    };

    if delegate_nonce.nonce() <= current_nonce {
        result.result = Err(ActionErrorKind::DelegateActionInvalidNonce {
            delegate_nonce: delegate_nonce.nonce(),
            ak_nonce: current_nonce,
        }
        .into());
        return Ok(());
    }

    let upper_bound = apply_state.block_height
        * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER;
    if delegate_nonce.nonce() >= upper_bound {
        result.result = Err(ActionErrorKind::DelegateActionNonceTooLarge {
            delegate_nonce: delegate_nonce.nonce(),
            upper_bound,
        }
        .into());
        return Ok(());
    }
