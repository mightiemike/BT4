### Title
Unauthenticated "bootstrap declare" mechanism allows front-running of genesis/system class declarations - (File: crates/starknet_api/src/executable_transaction.rs)

### Summary
Starknet's sequencer implements a special "bootstrap declare" transaction path used to declare classes during genesis, before any account exists on-chain. This path is keyed only on a hard-coded, publicly-known sender address (`'BOOTSTRAP'`), a fixed nonce of `0`, and a zero-fee flag — it has **no signature/ownership check** and explicitly skips `__validate_declare__` and fee charging. Because any unprivileged party who can construct and submit an `RpcTransaction::Declare` with these exact (publicly known) fields reaches this same execution path, they can race the legitimate operator-issued bootstrap declaration. Since a class hash may only be declared once (`prev_value == 0` invariant), an attacker who lands their bootstrap declare first can occupy/consume the once-only declaration slot before the intended system class (e.g. account or fee-token contract class) is declared, blocking or corrupting the sequencer's genesis bootstrap flow. This is the direct sequencer analog of the reported "unprotected initializer, frontrunnable" bug class.

### Finding Description
The bootstrap sender address is a fixed, publicly derivable constant — a felt encoding of the literal string `'BOOTSTRAP'`: [1](#0-0) 

`is_bootstrap_declare` defines the trigger condition purely from transaction fields that any sender can set (sender address, nonce, fee flag) — no signer/ownership requirement: [2](#0-1) 

In the blockifier's execution path, when a `Declare` transaction satisfies `is_bootstrap_declare`, the sequencer **skips the normal nonce/fee pre-validation stage and the account's `__validate_declare__` entry point entirely**, running only the declare's `run_execute` (which records the class): [3](#0-2) 

The same unauthenticated special-case exists independently in the Starknet OS Cairo re-execution code, gated only by `sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, with `max_possible_fee == 0`: [4](#0-3) 

Both paths enforce the "declare once" invariant via `dict_update{... prev_value=0}` / equivalent state checks — i.e., only the *first* transaction to declare a given class hash under this mechanism succeeds; subsequent attempts for the same class hash fail. Nothing in these code paths verifies that the caller is the legitimate node operator/deployer; the only gate that exists is the gateway-level, **optional** `authorized_declarer_accounts` allow-list, exercised in `check_declare_permissions` (called from `add_tx_inner` before stateless validation): [5](#0-4) [6](#0-5) 

I was not able to fully verify (index truncated the exact function body) whether `authorized_declarer_accounts`, when configured, is applied uniformly to the BOOTSTRAP sender address or whether operators are expected/required to include/exclude it specifically. If this allow-list is left unset (`None`, its apparent default) during the genesis/bootstrap window — which is plausible since a brand-new network has no accounts yet to populate such a list against — **any external party who submits a well-formed RPC declare transaction with `sender_address = bootstrap_address()`, `nonce = 0`, and zero resource bounds will be accepted by the gateway and mempool exactly like the operator's intended bootstrap transaction**, since the mechanism was purposely designed to bypass normal fee/nonce/signature checks for exactly this address.

### Impact Explanation
An attacker who front-runs the legitimate bootstrap declare transactions (e.g. the genesis declaration of the standard account class or fee-token class) with their own bootstrap-declare (targeting the *same* class hash with a different/malicious `compiled_class_hash`, or targeting adjacent required system class hashes) can:
- Permanently occupy the one-time "declare" slot for a system class hash before the legitimate declaration lands, causing the operator's intended bootstrap declare to be rejected (since `prev_value` is no longer `0`), and
- Potentially get a malicious CASM/compiled-class-hash pairing bound to a class hash the network needs for genesis, since the bootstrap path performs no code review/ownership check on which class gets declared.

This can prevent a new Starknet instance from ever correctly completing genesis bootstrap (a network unable to confirm/execute the transactions needed to complete initialization), which matches the "network unable to confirm new transactions" / permanent freezing criterion. It is directly analogous to the OpenQ report: an unauthenticated initializer that anyone can call/front-run to seize control of a one-time initialization step.

### Likelihood Explanation
Exploitation requires: (1) knowledge of the constant bootstrap address, its exact encoding, and the exact conditions of `is_bootstrap_declare` — all of which are public in this open-source repository; (2) the ability to submit a normal RPC transaction to the gateway/mempool before the operator's own bootstrap transaction is included in a block; and (3) the `authorized_declarer_accounts` allow-list not being configured to block this address. Since bootstrap declares must occur before ordinary access-list infrastructure or governance exists, and the mechanism is explicitly engineered to accept zero-fee, unsigned transactions from this address, the practical likelihood hinges entirely on deployment-time configuration of `authorized_declarer_accounts`, which I could not fully confirm is mandatory or default-enabled for this special address.

### Recommendation
- Require an explicit, mandatory authorization check (e.g., a required allow-list entry, or a dedicated one-time governance/L1-anchored flag) specifically for the bootstrap sender address, rather than relying on an optional `authorized_declarer_accounts` gateway config.
- Alternatively, disable/invalidate the bootstrap declare path automatically once the genesis window has passed (e.g., once block number > 0, or once a specific "bootstrap complete" flag is set in state), independent of gateway configuration, so it cannot be reached by ordinary transaction submitters after deployment.
- Ensure the OS-level Cairo bootstrap-declare check (`transaction_impls.cairo`) and blockifier-level check are both covered by the same non-optional guard, since either path independently allows the state mutation.

### Proof of Concept
1. Deploy a fresh Starknet-based network (no prior blocks/accounts).
2. Before the operator submits its intended bootstrap declare transaction(s), an attacker crafts and submits an `RpcTransaction::Declare(V3)` with:
   - `sender_address = bootstrap_address()` (felt of `'BOOTSTRAP'`, from [7](#0-6) )
   - `nonce = 0`
   - `resource_bounds` set to zero/no-fee-enforcement bounds
   - `class_hash` set to the class hash the operator intends to declare for genesis (e.g. the well-known account or fee-token class hash), paired with an attacker-chosen `compiled_class_hash`.
3. If the gateway's `authorized_declarer_accounts` is not configured to block this transaction, `check_declare_permissions` passes, stateless/stateful validation succeeds (validation is skipped for bootstrap declares per [8](#0-7) ), and the transaction is accepted into the mempool/block ahead of the operator's transaction.
4. Once included, the `dict_update{... prev_value=0}` invariant means the class hash is now marked declared with the attacker's compiled class hash; the operator's subsequent legitimate bootstrap declare for the same class hash fails, blocking correct network genesis.

    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

        // Do not run validate or perform any account-related actions for declare transactions that
        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),

                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());

#[rstest]
#[tokio::test]
async fn test_unauthorized_declare_config(mut mock_dependencies: MockDependencies) {
    let authorized_address = contract_address!("0x1");
    mock_dependencies.config.static_config.authorized_declarer_accounts =
        Some(vec![authorized_address]);

    let gateway = mock_dependencies.gateway();
    let rpc_declare_tx = declare_tx();

    // Ensure the sender address is different from the authorized address.
    assert_ne!(
        rpc_declare_tx.calculate_sender_address().unwrap(),
        authorized_address,
        "Sender address should not be authorized"
    );

    let gateway_output_code_error = gateway.add_tx(rpc_declare_tx, None).await.unwrap_err().code;
    let expected_code_error =
        StarknetErrorCode::KnownErrorCode(KnownStarknetErrorCode::UnauthorizedDeclare);

    assert_eq!(gateway_output_code_error, expected_code_error);
}
