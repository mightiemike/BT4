## Title
Deleting the protocol treasury account causes `RuntimeError::StorageError(StorageInconsistentState)` at epoch boundaries, converting to `Error::StorageError` and stalling chunk application - (File: `runtime/runtime/src/lib.rs`)

### Summary
This is the same bug class as the Forta `FortaStaking.slash()` finding: a privileged payout path (there, sending slashed funds to `_treasury`; here, crediting the epoch reward to `protocol_treasury_account`) assumes the destination account always exists/accepts funds, with no defensive fallback if it doesn't. In nearcore, the protocol treasury account is a normal named account that can be deleted by its own owner via a standard `DeleteAccount` action reachable from any signer holding the account's key, and once deleted, the mandatory end-of-epoch reward-crediting step fails with a fatal storage-inconsistency error.

### Finding Description
At the start of every epoch, `Runtime::update_validator_accounts` unconditionally attempts to credit the protocol-treasury reward: [1](#0-0) 

```
if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
    if !validator_accounts_update.stake_info.contains_key(account_id) {
        let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Protocol treasury account {} is not found",
                account_id
            ))
        })?;
```

There is no fallback (e.g. skip crediting, or route funds elsewhere) if `get_account` returns `None` — it produces a `StorageError::StorageInconsistentState`, which bubbles up as `RuntimeError::StorageError` from `Runtime::apply`.

The protocol treasury account is an ordinary named account (not specially locked or protected): it is only added to genesis as a normal user account with a given balance [2](#0-1) , and reward crediting reads/writes it exactly like any other account via `get_account`/`set_account`. Any regular `DeleteAccount` action executed by that account's own key (or its designated actor) removes the account entirely via `action_delete_account`, refunding its balance to a `beneficiary_id` chosen by the caller [3](#0-2) . The only actor-permission restriction on `DeleteAccount` is "no locked stake" (`check_actor_permissions`) — the treasury account is not required to stake, so nothing prevents its holder from deleting it once and for all.

Once deleted, at the next epoch boundary `update_validator_accounts` is invoked with `protocol_treasury_account_id` still pointing at the now-nonexistent account (this identifier is a fixed genesis-config value, not derived from current state), causing the `ok_or_else` branch to fire and return `StorageInconsistentState`.

This propagates out of `Runtime::apply` and is handled by the calling code as follows: [4](#0-3) 

```
.map_err(|e| match e {
    RuntimeError::InvalidTxError(err) => { ... Error::InvalidTransactions }
    RuntimeError::UnexpectedIntegerOverflow(reason) => {
        panic!("RuntimeError::UnexpectedIntegerOverflow {reason}")
    }
    RuntimeError::StorageError(e) => Error::StorageError(e),
    RuntimeError::ReceiptValidationError(e) => panic!("{}", e),
    RuntimeError::ValidatorError(e) => e.into(),
})?;
```

`StorageError` becomes `Error::StorageError`, which is nearcore's standard fatal-chunk-application error type — the chunk/block cannot be applied, and this failure recurs deterministically every subsequent epoch, since the identifier remains fixed and the account remains gone forever.

### Impact Explanation
This maps to the "transaction-triggered halt" category: an unprivileged holder of the protocol treasury account's access key can submit a single `DeleteAccount` transaction that permanently and irrecoverably breaks the per-epoch reward-distribution step of `Runtime::apply` for every node in the network, since it is a deterministic state-transition function applied identically by all honest validators. This blocks chunk/block application at every subsequent epoch boundary network-wide, not merely for one node — a protocol-level denial of service triggered by ordinary transaction execution, analogous to the Forta report's "slashing mechanism is permanently broken."

### Likelihood Explanation
Reachability depends entirely on whether the account(s) holding keys to the genesis-configured `protocol_treasury_account` are trusted/foundation-controlled (as on mainnet) or attacker-reachable. On any network (testnet/custom chain, or if treasury key custody is ever compromised or misconfigured) where an ordinary key controls that account, a single `DeleteAccount` action is sufficient — no special privilege beyond holding that one account's access key is required, and the codebase provides no protection (no "treasury cannot be deleted" check) analogous to what the original report recommends adding for `_treasury != address(0)`.

### Recommendation
Add an explicit safeguard so the protocol treasury account cannot be deleted, or make epoch-reward crediting resilient to a missing treasury account: either (a) reject `DeleteAccount` on `protocol_treasury_account_id` at the action-validation layer, similar to how staking accounts are already prevented from self-deleting in `check_actor_permissions`; or (b) in `update_validator_accounts`, if `get_account` returns `None` for the treasury account, log/burn the reward (treating it like the existing "receiver account no longer exists" fallback already used for contract gas rewards) instead of returning a fatal `StorageInconsistentState`.

### Proof of Concept
1. On a network whose `protocol_treasury_account_id` (genesis config) is an ordinary named account controlled by a full-access key (this holds by default unless operators specially harden it).
2. The key holder submits a transaction with a single `DeleteAccount` action from that account, with any `beneficiary_id`, per `action_delete_account` at [5](#0-4) .
3. The account is removed from state (`remove_account`), balance refunded to the beneficiary.
4. At the next epoch boundary, `EpochManager`/`RewardCalculator` still designates the same fixed `protocol_treasury_account_id` for the epoch reward, and `Runtime::apply` calls `update_validator_accounts` with that id in `validator_accounts_update.protocol_treasury_account_id`.
5. `get_account(state_update, account_id)?` returns `None`, `ok_or_else` fires `StorageError::StorageInconsistentState("Protocol treasury account ... is not found")` at [6](#0-5) .
6. `chain/chain/src/runtime/mod.rs` converts this to `Error::StorageError`, failing chunk application deterministically on every node, every epoch, from then on.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
