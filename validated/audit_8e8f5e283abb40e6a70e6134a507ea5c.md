### Title
Byte-count estimate in `many_ref_accounts_can_be_moved` can underestimate bins needed by the actual `PackedAncientStorage::pack` next-fit packer, letting a multi-ref account be repacked to a slot lower than its live referencing slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` decides whether `many_refs_newest` accounts (ref_count > 1, but the account's current slot is the newest alive reference) are safe to move by computing `required_ideal_packed = alive_bytes / ideal_size + 1` and checking that every account's slot is `<= target_slots_sorted[len - required_ideal_packed]`. The actual packing performed afterwards by `PackedAncientStorage::pack` is a sequential "next-fit" bin packer that never splits an individual account across storages, so it can require strictly more output storages than the naive `bytes/ideal_size` estimate whenever accounts don't evenly divide the ideal storage size. Because `many_refs_newest` is packed first (chained ahead of `one_ref` accounts) and the resulting storages are zipped with `target_slots_sorted` in *reverse* (highest slots first) inside `write_packed_storages`, any extra bin consumed by fragmentation pushes later many-ref accounts onto a lower target slot than the one validated by the pre-check.

### Finding Description
The relevant guard is: [1](#0-0) 

It is invoked once, before the real pack is computed: [2](#0-1) 

and the real packing / assignment happens afterward with no re-validation against the actual bin boundaries: [3](#0-2) 

`PackedAncientStorage::pack` walks the chained `many_refs_newest` then `one_ref` account groups and greedily fills each output storage until the *next* account would overflow `ideal_size`, at which point it starts a brand-new storage even though the current one may have substantial unused capacity (it never splits a single account or reorders items): [4](#0-3) 

This is a classic "next-fit" bin-packing strategy, whose worst case can require close to 2× the number of bins that `ceil(total_bytes / ideal_size)` (used by the pre-check as `alive_bytes / ideal_size + 1`) would predict, when item sizes are a large fraction of `ideal_size`. The resulting `Vec<PackedAncientStorage>` is then zipped against the *reverse-sorted* `target_slots_sorted` list, so storage index `0` (which holds the earliest/`many_refs_newest` accounts, since they are chained first) is paired with the *highest* available target slot, index `1` with the next highest, and so on: [5](#0-4) 

The pre-check's safety property depends entirely on the assumption that all `many_refs_newest` bytes fit within the first `required_ideal_packed` entries of the packed output (so they only ever land on slots `>= target_slots_sorted[i_last] == highest_slot`). If the real packer needs more bins than `required_ideal_packed` to hold the same bytes (due to next-fit fragmentation from account-size granularity), the extra `many_refs_newest` accounts spill into storage indices `>= required_ideal_packed`, which map to slots `< highest_slot` — potentially lower than the account's own current slot. The only remaining safety valve, `if pack.len() > accounts_to_combine.target_slots_sorted.len() { return; }`, only bounds the *total* number of output storages against the total number of available target slots; it does not verify that `many_refs_newest` content stayed within the specific high-slot subset that the earlier check validated.

An unprivileged attacker fully controls account data sizes (`data_size`) and can create many small accounts referencing the same pubkey across many ancient slots (to build up `ref_count > 1` entries where the current slot is the "newest alive" one), sized so that they are a large fraction of `ideal_storage_size`, deliberately maximizing next-fit fragmentation waste per bin. Given enough such slots/accounts, the actual number of bins needed to hold `many_refs_newest` bytes exceeds the estimate by enough to overflow the `required_ideal_packed` margin, causing `write_one_packed_storage`/`StorableAccountsBySlot` to write a multi-ref account into a target slot below one of its other live slot-list entries for the same pubkey, breaking the "highest slot # defines the most recent account" invariant relied on throughout `calc_accounts_to_combine`'s comments and the accounts index.

### Impact Explanation
If a many-ref account ends up written at a slot lower than another live slot entry for the same pubkey, a load bounded by ancestors below the true latest slot (or the index's newest-alive-entry logic) can resolve to stale account data — enabling reads/writes against wrong-slot or stale account state. This matches the audit's scoped critical impact: stale/wrong-slot account state fed into execution, potentially letting a transaction observe or act on value/ownership state it should not see, and risking hash/capitalization divergence between honest nodes if the corruption is not identically reproduced everywhere (e.g., due to thread-pool scheduling nondeterminism in which storage a particular byte range lands in during `write_packed_storages`'s parallel `packer.par_iter()`).

### Likelihood Explanation
Exploitability requires: (1) accumulating multiple ref-count > 1 pubkeys across several ancient slots where the attacker's slot is the "newest alive" entry, (2) sizing accounts so each is a large enough fraction of the (validator-fixed) `ideal_storage_size` (128 MiB by default from `get_ancient_append_vec_capacity`) to produce meaningful next-fit fragmentation, and (3) enough total volume that the cumulative wasted space exceeds the `+1` bin safety margin baked into `required_ideal_packed`. Given the default 128 MiB ideal size versus the ~10 MiB practical max account size, each bin wastes at most ~8%, so overflowing the single extra bin margin requires roughly a dozen or more max-sized many-ref ancient slots of this shape — costly in rent/storage but not otherwise gated by any protocol-level check, and entirely achievable by a normal fee-paying account owner over time. This is a real but narrow/low-probability condition rather than a one-transaction exploit; it is also not exercised by the existing unit tests (`test_calc_accounts_to_combine_many_refs`, `test_finish_combine_ancient_slots_packed_internal`), which use small numbers of uniformly-sized synthetic accounts and never construct a next-fit worst case.

### Recommendation
Do not rely on a byte-count estimate to predict packer bin counts. Either (a) run `PackedAncientStorage::pack` for `many_refs_newest` alone first, and only then check that the number of storages it actually produced is `<= required` slots from the top of `target_slots_sorted`, re-deriving `highest_slot` from the true output length; or (b) change `PackedAncientStorage::pack` to guarantee near-optimal bin usage (e.g., first-fit-decreasing or explicit slack accounting) and add an assertion/invariant after packing that every `many_refs_newest` entry's assigned target slot is `>=` its original slot, aborting the repack (falling back to `write_ancient_accounts_to_same_slot_multiple_refs`) if violated instead of proceeding.

    /// return false if `many_refs_newest` accounts cannot be moved into `target_slots_sorted`.
    /// The slot # would be violated.
    /// accounts in `many_refs_newest` must be moved a slot >= each account's current slot.
    /// If that can be done, this fn returns true
    fn many_ref_accounts_can_be_moved(
        many_refs_newest: &[AliveAccounts<'_>],
        target_slots_sorted: &[Slot],
        tuning: &PackedAncientStorageTuning,
    ) -> bool {
        let alive_bytes = many_refs_newest
            .iter()
            .map(|alive| alive.bytes)
            .sum::<usize>();
        let required_ideal_packed = (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;
        if alive_bytes == 0 {
            // nothing required, so no problem moving nothing
            return true;
        }
        if target_slots_sorted.len() < required_ideal_packed {
            return false;
        }
        let i_last = target_slots_sorted
            .len()
            .saturating_sub(required_ideal_packed);

        let highest_slot = target_slots_sorted[i_last];
        many_refs_newest
            .iter()
            .all(|many| many.slot <= highest_slot)
    }
