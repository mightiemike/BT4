### Title
Missing slippage protection (`expected`/`minOut`) in `ExchangeWithdrawActuator` allows sandwich attacks on liquidity withdrawal - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The TRC10 bancor-style exchange module in java-tron implements two related but asymmetric operations: `ExchangeTransactionContract` (a swap) and `ExchangeWithdrawContract` (removing liquidity from the pool). The swap path correctly implements a slippage guard via the `expected` field, but the withdraw path computes the counter-token amount purely from the pool's live reserves at execution time with **no user-supplied minimum-output guard**, mirroring exactly the missing `minOut` bug class described in the external Pendle report.

### Finding Description
`ExchangeTransactionContract` includes an `expected` field ("expected minimum number of tokens") [1](#0-0) , and `ExchangeTransactionActuator.doValidate()` enforces it by rejecting the transaction if the computed `anotherTokenQuant` is less than `tokenExpected` [2](#0-1) .

By contrast, `ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/`minOut` field at all [3](#0-2) . In `ExchangeWithdrawActuator.doValidate()`/`execute()`, the counterpart token amount (`anotherTokenQuant`) the withdrawer receives is derived strictly from the current pool balances at execution time (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`, or the mirrored calculation for the other token) [4](#0-3) . The only checks performed are that reserves are non-zero, quant is positive, and a fixed-precision rounding check — none of which protect against the pool ratio itself shifting between transaction submission and inclusion [5](#0-4) .

Since the pool's `firstTokenBalance`/`secondTokenBalance` ratio can be manipulated by any account via ordinary `ExchangeTransactionContract` swaps executed in an earlier position within the same block (block producers or MEV-style transaction ordering), a withdrawer's actual received amount can be pushed arbitrarily below what they expected when they signed and broadcast the withdraw transaction — exactly the "no slippage" bug class flagged in the Pendle `_onWithdraw` report, where `minOut` was hardcoded to 0.

### Impact Explanation
An attacker (or the block-producing witness itself) can front-run a pending `ExchangeWithdrawContract` transaction with `ExchangeTransactionContract` swaps that skew the pool ratio unfavorably, then let the withdraw execute at the manipulated ratio, extracting value from the withdrawer (who is typically the exchange creator, since `doValidate()` requires `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` [6](#0-5) ). This causes a direct, unrecoverable loss of TRC10/TRX funds for the withdrawer — an accounting/settlement impact consistent with the referenced report's fund-loss classification.

### Likelihood Explanation
The attack requires only ordinary permissionless swap transactions (`ExchangeTransactionContract`) targeting the same exchange pool, timed/ordered ahead of the victim's withdraw in the same block — a standard sandwich pattern achievable by any account or a cooperating block producer, with no privileged access needed. The `expected` field's presence on the sibling swap contract but absence on withdraw indicates this is an inconsistent, unintentional gap rather than a deliberate design decision.

### Recommendation
Add an `expected`/`min_receive` field to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` analogous to the existing check in `ExchangeTransactionActuator` (`if (anotherTokenQuant < tokenExpected) throw new ContractValidateException(...)`), so withdrawers can bound their acceptable minimum counter-token output.

### Proof of Concept
1. Exchange pool has reserves `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Creator broadcasts `ExchangeWithdrawContract` withdrawing `q` of the first token, expecting `≈ B*q/A` of the second token based on current state.
3. Before this transaction is packed, an attacker submits `ExchangeTransactionContract` trades against the same `exchange_id` that shift the ratio (e.g., sell large first-token amount to shrink `secondTokenBalance` relative to `firstTokenBalance`).
4. Once packed in the same block ahead of the withdraw, `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` off the now-skewed reserves [4](#0-3) , delivering the creator far less of the second token than anticipated, with no contract-level check to reject this outcome.
