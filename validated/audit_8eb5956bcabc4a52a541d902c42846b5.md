## Title
`ensure_match_transaction_info` skips state-checkpoint / position-state-checkpoint hash comparison, letting replay-verify accept a divergent authenticated state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay-verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed transaction output matches the transaction info that was actually committed to the chain. As written, the function only checks status, gas used, write-set hash (`state_change_hash`), and event root hash — it explicitly, and by its own inline comment, skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function verifies four fields against the `TransactionInfo` that was fetched from (and proven against) the archived ledger: `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`. It never checks `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against any locally computed equivalent. The comment on lines 2197-2202 states this directly:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

`state_checkpoint_hash` is the root hash of the Sparse Merkle Tree describing the full world state at a version [2](#0-1) . It is the strongest state-commitment invariant carried in `TransactionInfo` — stronger than the per-transaction write-set hash, because it captures the entire accumulated state, not just this transaction's delta. `ensure_match_transaction_info` is called directly by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which is the tool operators use to confirm that replaying transactions from an archive against `AptosVMBlockExecutor` reproduces the exact on-chain result [3](#0-2) .

Because the comparator never checks the checkpoint hash, a bug in the "trading-native" position/state-checkpoint computation path (referenced by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), or any other divergence in world-state materialization that happens to leave per-transaction write sets and events unaffected, will not be caught by replay-verify. `execute_and_verify` will treat the replay as successful even though the locally computed state root differs from the authenticated on-chain root.

### Impact Explanation
Replay-verify is the primary tool used to validate that historical or newly-produced execution matches consensus-committed results, and it is also exercised as part of hard-fork/upgrade validation workflows. If the state-checkpoint root diverges (e.g., due to a bug in state materialization, JMT construction, or the trading-native state root path) but per-transaction write sets/events still match, `ensure_match_transaction_info` will report success. This masks state-commitment divergence that should be caught before it propagates — directly matching the "authenticated state differs from correct VM result" and "hard-fork-only divergence during commit/replay" impact classes. This is a detection gap in the primary safety net for validating full-node state correctness against the authenticated chain, which is high severity if a divergence bug is ever introduced upstream (it becomes silently unnoticed), though the vulnerability itself is a missing-check/omission rather than an activatable corruption in production consensus paths today.

### Likelihood Explanation
The condition is guaranteed to manifest whenever any code path produces a wrong state (or hot-state / position-state) checkpoint hash while write-set/events remain correct — this is plausible for state-materialization bugs that only affect the aggregated tree (e.g., an issue in state checkpoint construction in `do_state_checkpoint.rs`, or the newer "trading-native"/position-state-checkpoint feature) since write_set_hash only covers the current transaction's own deltas, not the resulting global root. The maintainers' own TODO acknowledges this gap is real and unaddressed, and explicitly flags it as unsafe to enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS` before fixing it — i.e., this is a known, currently-latent detection bypass in the replay-verify invariant.

### Recommendation
Extend `ensure_match_transaction_info` to accept and check the state-checkpoint hash(es) (and hot-state / position-state checkpoint hash when relevant) against a value independently computed from the state view after applying the output, failing the comparison (as it does for write-set/event mismatches) if they diverge. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or the position-state checkpoint feature in production, per the existing TODO.

### Proof of Concept
Not applicable as an exploit against a live network (this is a missing-check / verification-bypass bug in offline replay tooling, not an attacker-triggerable state-corruption primitive). The proof is the code path itself:
1. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes transactions and calls `ensure_match_transaction_info(version, &expected_txn_info, Some(&expected_writeset), Some(&expected_events))` [4](#0-3) .
2. `ensure_match_transaction_info` never reads or compares `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` against any recomputed value [5](#0-4) .
3. Therefore any hypothetical bug that corrupts only the aggregated state-checkpoint root (leaving per-txn write set/events intact) passes replay-verify silently — confirmed directly by the maintainers' own TODO comment describing this exact scenario.

**Note on investigation limits:** I was unable to fully trace whether `state_checkpoint_hash` divergence is independently checked anywhere else in the replay-verify pipeline (e.g., a separate root-hash comparison performed by `AptosDB`/`state_store` outside of `ensure_match_transaction_info`), so it is possible there is a redundant check elsewhere that mitigates this gap in practice; I could not conclusively rule this out within the available search budget.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
