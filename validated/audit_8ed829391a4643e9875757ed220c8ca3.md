## Analysis

The report describes an unbounded-iteration DoS pattern: a data structure that grows with (attacker-influenced) user activity is later iterated/searched in full inside a single execution path, without any bound, causing gas/CPU cost that scales with the attacker-controlled input size.

The closest in-scope analog in `agave` is the `SecondaryIndex` reverse-index used by `AccountsIndex`'s SPL-token-mint / SPL-token-owner / program-id secondary indexes.

### Title
Unbounded, linearly-scanned `SecondaryIndex` reverse-index entries cause O(n²) insert cost and an unbounded lock-held drain on removal - (File: `accounts-db/src/accounts_index/secondary.rs`)

### Summary
`SecondaryIndex::reverse_index` maps an account pubkey ("inner key") to the list of secondary-index outer keys (e.g. distinct SPL-token mint/owner values, or program-id owners) it has ever been associated with, stored as a plain `Vec<Pubkey>` rather than a bounded/deduplicated structure. The type comment explicitly assumes this list stays small ("rare... ok to use a Vec here over a HashSet"), but nothing enforces that assumption. Every `insert()` call does a linear `Vec::contains()` scan while holding the entry's write lock, and the eventual removal (`remove_by_inner_key_if`) `drain()`s and processes the entire vector synchronously, still holding that lock. If a pubkey accumulates many distinct outer-key associations before it is fully purged from the primary index, both operations degrade proportionally, mirroring the `distribute()`-over-`_feeReceivers` bug class from the external report: iteration/searching over an unbounded, indirectly attacker-influenced list inside a hot path.

### Finding Description
`SecondaryIndex::insert()` at [1](#0-0)  takes the reverse-index write lock for `inner_key` and does `if !outer_keys.contains(key) { outer_keys.push(*key); }` — an `O(n)` linear scan against the *entire* history of outer keys ever seen for that pubkey, executed on every single secondary-index update for that account (i.e., on every write of a matching token/program account).

The type itself is defined and documented as an unbounded, un-deduplicated `Vec`: [2](#0-1) 

`remove_by_inner_key_if()` later `drain()`s this same vector and, for every entry, calls `remove_index_entries()` (itself doing a `DashMap` lookup + panic-checked removal) — all performed synchronously while holding the reverse-index entry's write lock: [3](#0-2) 

Critically, `update_secondary_indexes()` only ever *inserts* new mappings when an account's indexed field (mint, owner, or program-id/owner) changes; it never removes the stale mapping for the account's previous value. The stale entry is only reclaimed once the pubkey is fully "dead" (removed from all slot lists) via `purge_secondary_indexes_for_dead_keys` / `handle_dead_keys`: [4](#0-3) [5](#0-4) 

Because clean/purge runs on a periodic background interval (`CLEAN_INTERVAL`), an account whose indexed field is legitimately changed across many rooted slots between clean cycles will keep accumulating distinct outer-key entries in its `reverse_index` `Vec` before the entry is ever collapsed, since nothing bounds or deduplicates ahead of that point.

### Impact Explanation
This is a "disproportionate CPU cost" issue matching the Validate criteria:
- Insert cost for a given pubkey becomes `O(n)` per write and `O(n²)` cumulative as `n` grows, all while holding the per-key `DashMap` entry lock, blocking any concurrent secondary-index insert/remove that maps to the same shard entry.
- The final removal walks and removes the entire unbounded list synchronously under lock, which is invoked from `clean_accounts` / cache-flush paths on the accounts-background thread — an unexpectedly large `reverse_index` entry can stall that thread and the lock it holds for a duration proportional to attacker-influenced state, degrading clean/flush throughput.

This only applies to validators/RPC nodes that opt in to secondary indexes (`--account-index spl-token-mint|spl-token-owner|program-id`), which is a common RPC-node configuration for `getProgramAccounts`/`getTokenAccountsByOwner` support, not a validator-role or mock-only scenario.

### Likelihood Explanation
Moderate. It requires:
1. The node operator has enabled the relevant secondary index (common on RPC-serving nodes).
2. An unprivileged user causes an account's indexed field (mint/owner) to take on many distinct values across many rooted slots before a `clean_accounts()` cycle collapses the older entries (`CLEAN_INTERVAL`-bound, background-driven, not attacker-controlled timing).

No special privileges are needed by the account holder beyond normal transaction submission; the growth is driven purely by legitimate-looking account writes, not by exploiting a memory-corruption bug.

### Recommendation
- Replace the reverse-index entry's `Vec<Pubkey>` with a `HashSet<Pubkey>` (or otherwise dedupe/bound insertion) to make `insert()` and `contains()` checks O(1) instead of O(n).
- Alternatively, proactively remove the account's *previous* secondary-index mapping whenever `update_secondary_indexes()` detects the indexed field has changed for a still-alive key, rather than only reclaiming stale mappings when the key fully dies, bounding growth to at most one outer-key per inner-key at any time.
- Consider chunking/yielding the `drain()`-based removal in `remove_by_inner_key_if()` so an unexpectedly large reverse-index entry cannot monopolize the lock for an unbounded duration.

### Proof of Concept
Conceptual reproduction path (no exploit code required per rules):
1. Enable `--account-index spl-token-mint` (or `spl-token-owner`/`program-id`) on a node.
2. Repeatedly, across many rooted slots (spaced so each write lands in a separate root before the next `CLEAN_INTERVAL` fires), update the same SPL-token account's `mint` field to a fresh pubkey value via legitimate program instructions requiring account close/reinit (or any path where `update_secondary_indexes` is invoked with a new mint for the same address before clean has purged the old rooted entries).
3. Each call to `SecondaryIndex::insert()` in [1](#0-0)  performs `outer_keys.contains(key)` over a `reverse_index` `Vec` that now has `n` accumulated entries, making the `n`-th such update take `O(n)` time under the entry's write lock.
4. When the pubkey is finally purged, `remove_by_inner_key_if()` at [3](#0-2)  drains and removes all `n` entries synchronously, holding the lock for the duration — the direct analog of `distribute()` iterating unboundedly over `_feeReceivers`.
