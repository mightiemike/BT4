### Title
Unbounded `PendingInbounds.Walk` in `afterInboundBallotTerminal` creates an attacker-scalable, per-vote computation DoS analogous to the TangleStaking `_unstake` loop - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
The reported bug class is a storage-touching `for` loop over an attacker-growable collection that runs on a hot path, causing unbounded gas/compute cost and a DoS as the collection grows. The Push Chain analog is `BallotHooks.afterInboundBallotTerminal`, which performs a full linear `Walk` over the entire `PendingInbounds` collection every time any inbound ballot reaches a terminal state, in order to find the entry containing a given `ballotID`. `PendingInbounds` size is driven by ordinary, unprivileged user activity (crosschain deposits), so an attacker can inflate this collection and make every subsequent inbound-ballot finalization progressively more expensive.

### Finding Description
`afterInboundBallotTerminal` is invoked from `x/uvalidator`'s generic ballot machine every time an `INBOUND_TX` ballot transitions to a terminal state (`PASSED`/`REJECTED`/`EXPIRED`) — i.e., on essentially every `MsgVoteInbound` that finalizes a ballot: [1](#0-0) 

Because ballot IDs are one-way digests (not reversible to the owning `utx_key`), the handler locates the owning `PendingInboundEntry` by scanning **every** entry in `PendingInbounds` and, for each entry, every `InboundVariant`, comparing `BallotId`: [2](#0-1) 

The code comment explicitly assumes the collection stays small: *"the pending set is small and transient, and this hook only fires on terminal transitions."* That assumption is the broken invariant.

`PendingInbounds` entries are created by `RecordInboundVote` on the **first** validator vote for a given inbound (`utx_key = sha256(sourceChain:txHash:logIndex)`), and are only removed once **all** variants of that inbound's ballot(s) reach a terminal state: [3](#0-2) 

Crucially, the *number* of `PendingInbounds` entries is not gated by any validator/admin privilege — it grows in direct proportion to the number of distinct source-chain inbound events (deposits) that Universal Validators are actively voting on. Any unprivileged external user can generate an arbitrary number of distinct inbound events cheaply (e.g., many small/dust deposits from many source addresses/log indices on any supported external chain), each producing a new `utx_key` and thus a new `PendingInboundEntry` that must sit in the map until UVs finalize its ballot. While those entries are pending, every unrelated inbound ballot finalization elsewhere in the system pays the cost of a full `O(n)` walk over the entire `PendingInbounds` map (plus nested `O(v)` scan of variants) just to locate the one entry relevant to that ballot.

This is structurally identical to the TangleStaking `_unstake` issue: a `for` loop combined with storage reads (`Walk` iterates KV-store entries) whose iteration count is controlled by an attacker-inflatable collection, executed on a routine, non-privileged, per-transaction code path (`MsgVoteInbound` finalization), rather than being bounded/indexed by the exact key needed.

### Impact Explanation
As the number of concurrently in-flight inbound observations grows (attacker-driven, via ordinary deposits), the per-finalization cost of `afterInboundBallotTerminal` grows linearly with `len(PendingInbounds)`. Since `MsgVoteInbound` (and its finalization side-effects) is a **gasless** message type (`app/txpolicy/gasless.go` whitelist includes `MsgVoteInbound`), there is no economic cost mechanism scaling with the CPU/storage-read work this hook performs, meaning validators absorb increasing block-processing time for free while the attacker only pays the (low) cost of generating source-chain deposit events. In the worst case this degrades UV vote-processing throughput chain-wide, delaying finalization of legitimate inbounds/outbounds and increasing block-production latency — a denial-of-service condition reachable purely through unprivileged, ordinary deposit activity, not through malicious validators, peers, or network-level flooding.

### Likelihood Explanation
Moderate. Exploitation requires sustaining a large number of simultaneously-pending inbound observations, which in turn requires either slow/backlogged UV voting (natural under load) or an attacker deliberately timing many deposits to arrive faster than UVs can vote/finalize them. No special privileges or validator collusion are needed — the trigger (submitting many crosschain deposits) is available to any external, unprivileged user. The severity scales with how large the eventual `PendingInbounds` size becomes and how frequently inbound ballots finalize.

### Recommendation
Avoid the full-collection `Walk` on the hot finalization path. Maintain a secondary index keyed directly by `ballotID -> utxKey` (set alongside `RecordInboundVote`, removed when the variant is cleared) so `afterInboundBallotTerminal` can do an O(1) lookup instead of an O(n) scan, mirroring the fix recommended for TangleStaking (use a direct/indexed lookup rather than a linear scan tied to an attacker-growable collection). Additionally, consider bounding the maximum number of concurrently pending inbound variants/entries per source chain or enforcing minimum-deposit/rate-limits to cap `PendingInbounds` growth.

### Proof of Concept
1. Attacker submits many distinct dust-value deposits on one or more supported external chains, each with a unique `(sourceChain, txHash, logIndex)` — cheap and requires no special access.
2. Universal Validators begin voting each one via `MsgVoteInbound`; each first vote creates a new `PendingInboundEntry` in the `PendingInbounds` map (`RecordInboundVote`), growing the collection well beyond the "small and transient" assumption.
3. As UVs continue voting on any inbound (including unrelated ones), each ballot finalization triggers `AfterBallotTerminal` → `afterInboundBallotTerminal`, which performs a full `PendingInbounds.Walk` over the now-large collection, plus a nested scan of each entry's `Variants` slice, to find the matching `ballotID`.
4. Repeat step 1 continuously to keep `PendingInbounds` large; measure increasing per-vote processing latency/gas consumed in finalization as the collection size increases, demonstrating the unbounded, attacker-scalable cost identical in kind to the TangleStaking `_unstake` for-loop DoS.

```go
func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
```
