### Title
Unchecked boolean return value of `AccountCapsule.reduceAssetAmountV2` in Exchange actuators causes silent asset-deduction failure and balance-accounting divergence - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator.execute` and `ExchangeTransactionActuator.execute` call `AccountCapsule.reduceAssetAmountV2(...)` to debit a user's TRC10 asset balance but discard the boolean success/failure result, exactly the same bug class as the Notional `stakingContext.auraBooster.deposit` finding: a state-changing call whose boolean outcome is not checked before the caller proceeds to commit dependent state changes.

### Finding Description
`reduceAssetAmountV2` is a boolean-returning method used elsewhere in the codebase to determine whether an asset debit actually succeeded. `TransferAssetActuator.execute` correctly checks this return value and aborts the transaction if it fails: [1](#0-0) 

However, `ExchangeInjectActuator.execute` calls the same method twice — once for the injected token and once for the paired "another token" — without checking the boolean result at all: [2](#0-1) 

The identical unchecked pattern exists in `ExchangeTransactionActuator.execute`, which calls `reduceAssetAmountV2` (and the analogous `addAssetAmountV2`) without validating success: [3](#0-2) 

In both actuators, the `exchangeCapsule.setBalance(...)` update (crediting the exchange pool with the injected/traded token amounts) is computed and persisted regardless of whether the corresponding user-side debit actually succeeded, mirroring the Notional bug where `bptMinted` accounting proceeded without confirming the external `deposit` call succeeded.

### Impact Explanation
If `reduceAssetAmountV2` returns `false` (e.g., due to insufficient balance not otherwise caught, or any internal validation failure inside the method), the actuator still: (1) updates the `ExchangeCapsule` pool balances via `Commons.putExchangeCapsule`, and (2) marks the transaction `ret.setStatus(fee, code.SUCESS)`. This produces divergence between the exchange pool's recorded token balances and the account's actual asset balances — a settlement/accounting integrity failure in the on-chain Bancor-style exchange market, allowing pool balances to be inflated without a corresponding real asset debit from the user.

### Likelihood Explanation
This code path is reachable by any unprivileged user who is the creator of an exchange, via `ExchangeInjectContract`/`ExchangeTransactionContract` — no special privileges are required. Whether `reduceAssetAmountV2` can actually return `false` under conditions not already excluded by `validate()` (e.g., `assetBalanceEnoughV2` pre-check) is not fully confirmed in this session — I was unable to retrieve the full body of `AccountCapsule.reduceAssetAmountV2` before the tool budget was exhausted, so the exact internal failure conditions of that method (and thus precise exploitability) remain unverified.

### Recommendation
Check the boolean return value of `reduceAssetAmountV2` (and `addAssetAmountV2`) in `ExchangeInjectActuator.execute` and `ExchangeTransactionActuator.execute`, mirroring the pattern already used in `TransferAssetActuator`: throw a `ContractExeException` and abort the transaction (avoiding the pool-balance update and `SUCESS` status) if the debit fails.

### Proof of Concept
Not fully constructible without confirming the internal failure conditions of `AccountCapsule.reduceAssetAmountV2` (unverified due to tool budget exhaustion). The structural PoC is: call `ExchangeInjectContract` (or `ExchangeTransactionContract`) with parameters that pass `validate()` but cause `reduceAssetAmountV2` to internally fail/return `false` (if such a condition exists distinct from the pre-checks in `validate()`); observe that `exchangeCapsule`'s balances are still updated and the transaction reports `SUCESS`, producing an exchange-pool/account-balance divergence. Recommend a Devin session with full repo access to inspect `AccountCapsule.reduceAssetAmountV2`'s implementation to confirm concrete failure conditions and finalize the PoC.
