### Title
MEV/sandwich attack risk in the Bancor-style Exchange bonding curve lacks any anti-sandwich mitigation beyond user-supplied slippage - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`ExchangeTransactionActuator` implements a Bancor-formula bonding-curve AMM (`ExchangeCapsule.transaction()` / `ExchangeProcessor.exchange()`) for TRX↔TRC10 token pairs. The only protection against price manipulation is the caller-supplied `expected` (minimum-output) field, structurally identical to the `minimumPayout`/`msg.value` slippage guards described in the external report. As in the reported bonding-curve issue, this leaves the full "consumer surplus" between a trader's accepted slippage and the true market price exposed to sandwich extraction by whoever controls transaction ordering within a block, with no time/ block-based cooldown to remove the incentive.

### Finding Description
`ExchangeTransactionActuator.doValidate()` computes the resulting `anotherTokenQuant` via the constant-product/Bancor curve in `ExchangeCapsule.transaction()` [1](#0-0) , which internally calls `ExchangeProcessor.exchange()` (or `SafeExchangeProcessor` in hardened mode) implementing the classic Bancor `exchangeToSupply`/`exchangeFromSupply` curve [2](#0-1) . The only slippage protection is the check `anotherTokenQuant < tokenExpected` throwing if the trade result is below the caller's minimum [3](#0-2) . This is the exact analog of the reported `minimumPayout`/`msg.value` guard: it bounds worst-case slippage but does not prevent an entity capable of ordering transactions within a block from inserting a front-run buy immediately before, and a back-run sell immediately after, a victim's `ExchangeTransactionContract`, extracting the price impact as risk-free profit — precisely the sandwich pattern in the external report.

Unlike the referenced fix (a 1-block freeze verified against a stored last-mint/transfer timestamp), there is no analogous cooldown anywhere in the Exchange contract family (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) or in `ExchangeCapsule`/`ExchangeProcessor`/`SafeExchangeProcessor`; no timestamp or per-block restriction fields exist on the exchange state, confirmed by the absence of any freeze/cooldown/last-operation-time fields in these classes. Any account may call `exchangeTransaction()` an unlimited number of times per block, and TRON block producers (witnesses) control final ordering of transactions within the blocks they produce, making the sandwich trivially executable by a witness or by anyone who can bribe/coordinate with one, or observe the pending pool and race with a same-block re-broadcast.

### Impact Explanation
The impact is loss of value for ordinary Exchange users: any trade against the on-chain Bancor AMM (`ExchangeTransactionContract`, reachable via the public `ExchangeTransaction` RPC in `api.proto` [4](#0-3) ) can have its price impact skimmed by a sandwiching party, systematically transferring value from ordinary traders to whoever controls block/transaction ordering. This is a value-extraction/accounting-fairness issue rather than a fund-lock or consensus-break bug, and severity is bounded by exchange pool sizes (subject to `getExchangeBalanceLimit()`).

### Likelihood Explanation
Likelihood is high in principle: block producers already have full control over intra-block transaction ordering, and no code path prevents them (or a party colluding with them) from inserting bracket trades around any pending `ExchangeTransactionContract`. Because slippage protection (`expected`) is user-configurable and users must set it loosely enough to tolerate normal volatility, especially during periods of high price movement, the achievable extraction is bounded only by the buffer users leave in `expected`, exactly mirroring the "consumer surplus" argument in the external report.

### Recommendation
Introduce a per-account (or per-exchange) minimum-block-delay between a buy and a subsequent sell (or vice versa) on the same `exchange_id`, analogous to the 1-block freeze recommended in the report. Concretely, store the block number/timestamp of an account's last `ExchangeTransactionContract` interaction with a given `exchange_id` (e.g., in `AccountCapsule` or a dedicated store) and reject a same-account trade against the same pool within the same block or within N blocks of its prior trade in `ExchangeTransactionActuator.doValidate()`. This removes the atomic bracket-trade profitability without requiring any change to the pricing curve itself.

### Proof of Concept
1. A victim broadcasts `ExchangeTransactionContract{exchange_id=E, token_id=T, quant=Q, expected=E_min}` to buy token via the Bancor curve, with `E_min` set below the ideal price to tolerate normal slippage.
2. A block producer (or a party with tx-ordering influence within that producer's block) observes this pending transaction and, before including it, inserts its own `ExchangeTransactionContract` buying the same side of the pool up to just under the point that would make the victim's trade revert (i.e., `anotherTokenQuant` for the victim would still be ≥ `E_min`).
3. The producer includes the victim's transaction next, which executes at the worse price permitted by `expected`.
4. The producer immediately appends a third `ExchangeTransactionContract` selling back the tokens acquired in step 2, capturing the price movement caused by the victim's trade as profit — all within transactions the producer fully orders in its own block, with the only defense being `anotherTokenQuant < tokenExpected` check in `ExchangeTransactionActuator.java:219` [3](#0-2) , which the attacker's bracket trades are constructed to respect.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
