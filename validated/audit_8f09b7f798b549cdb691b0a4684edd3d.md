### Title
Unauthenticated `MethodPublicKeyGet` fan-out has no per-caller rate limiting, enabling attacker-driven DoS against vault DON nodes - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`HandleJSONRPCUserMessage` explicitly skips authorization for `vaulttypes.MethodPublicKeyGet` and, whenever the cache is empty, calls `newActiveRequest` + `handlePublicKeyGet` → `fanOutToVaultNodes`, which sends the request to every DON member via `h.don.SendToNode`. Neither the HTTP ingress layer (`httpserver.go` `handleRequest`, which only enforces `MaxRequestBytesLimiter`) nor the vault handler itself apply any per-caller/IP rate limit to this unauthenticated path before fan-out occurs.

### Finding Description
In `core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage` (lines 403-429) special-cases `MethodPublicKeyGet`: [1](#0-0) 
It checks `h.getCachedPublicKey()`; if the cache is nil, it creates a fresh `activeRequest` via `newActiveRequest` (keyed only by the caller-supplied, unique `req.ID`, capped at 200 chars) and calls `handlePublicKeyGet`, which itself re-checks the cache and, on miss, calls `fanOutToVaultNodes`: [2](#0-1) 
`fanOutToVaultNodes` iterates all `h.donConfig.Members` and calls `h.don.SendToNode` for each: [3](#0-2) 

Tracing the ingress path, `gateway.ProcessRequest` (`core/services/gateway/gateway.go`) decodes the raw JSON-RPC request and immediately dispatches to `h.HandleJSONRPCUserMessage` without any per-sender rate limiting; the underlying `httpServer.handleRequest` only bounds request body size via `MaxRequestBytesLimiter`, with no IP/session throttle. The handler's only rate limiter, `h.nodeRateLimiter`, is applied solely in `HandleNodeMessage` to throttle inbound *node* responses — it is never consulted on the *outbound* user-request path (`HandleJSONRPCUserMessage`/`fanOutToVaultNodes`). Because `MethodPublicKeyGet` bypasses `h.requestProcessor.ProcessRequest` (the authorization/replay/signature check applied to all other vault methods, e.g. `MethodSecretsCreate`), and because request IDs are attacker-chosen and merely required to be unique and ≤200 chars, an attacker can submit an unbounded stream of distinct-ID `MethodPublicKeyGet` requests. Each one, while the cache is empty/stale, results in a full fan-out write to every DON node and an entry inserted into `h.activeRequests` (bounded only by a 5s-interval cleanup with a default 30s timeout, per `defaultCleanUpPeriod`/`requestTimeout`).

The comment at line 416 ("we cache this value quite aggressively so don't need to worry about DoS") is the stated design rationale, but the cache is populated only after a node quorum successfully responds (`tryCachePublicKeyResponse`/`HandleNodeMessage`), or via the periodic `tickerVaultPublicKeyRefresh` (every minute). During any window where the cache is empty (service startup, cache eviction/restart, or if node overload from the flood itself prevents quorum from being reached) the "cache should stop DoS" assumption fails, and every attacker request triggers a full DON fan-out plus map insertion, unthrottled by any caller-scoped limiter.

### Impact Explanation
This matches a Chainlink DoS/availability-impact bounty category: an unprivileged, unauthenticated actor can flood the gateway with `MethodPublicKeyGet` requests to force repeated fan-out traffic to every vault DON node and grow the in-memory `activeRequests` map, consuming gateway CPU/memory/network and node-connection capacity, and potentially preventing quorum convergence (keeping the cache perpetually stale and sustaining the DoS). This is scoped to gateway/vault DON capacity exhaustion, not secret disclosure or fund loss.

### Likelihood Explanation
Feasibility is high and repeatable: the request requires no authentication, no valid signature, and no special knowledge — only a unique `req.ID` string per call (trivially generated, e.g., UUIDs), which is well within normal, unprivileged web/API access to the gateway's public HTTP endpoint. The only precondition is a cache miss, which is guaranteed at startup and can be sustained by the flood itself if it degrades node responsiveness enough to block quorum.

### Recommendation
Apply a caller-scoped rate limiter (e.g., per source IP or per JSON-RPC `req.ID` prefix/session) to the `MethodPublicKeyGet` fast-path in `HandleJSONRPCUserMessage`/`handlePublicKeyGet` before calling `fanOutToVaultNodes`, independent of `h.nodeRateLimiter` (which only limits node→gateway traffic). Consider deduplicating concurrent in-flight `MethodPublicKeyGet` fan-outs (single-flight pattern) so that concurrent cache-miss requests share one node round trip instead of each triggering an independent fan-out, and bound `h.activeRequests` map growth with an explicit size cap/backpressure in addition to the time-based cleanup.

### Proof of Concept
Unit/integration test plan (Go, using existing `handler_test.go` scaffolding for the vault handler):
1. Construct a `handler` with an empty public key cache (`cachedPublicKeyGetResponse == nil`) and a mocked `gwhandlers.DON` (`don.EXPECT().SendToNode(...)`).
2. In a loop, call `h.HandleJSONRPCUserMessage(ctx, req, callback)` N times (e.g., N=10,000) with `req.Method = vaulttypes.MethodPublicKeyGet` and a unique `req.ID` each time (no `req.Auth` set), without ever letting `HandleNodeMessage` supply a quorum response (simulate stale/never-populated cache).
3. Assert that `don.SendToNode` is invoked `N * len(donConfig.Members)` times — i.e., unbounded fan-out proportional to N with no throttling — and that `len(h.activeRequests)` grows linearly with N (bounded only by the 30s cleanup timer), demonstrating the absence of any per-caller/global rate limiter gating this unauthenticated path.
4. Expected (fixed) behavior after remediation: once a caller-scoped rate limit is added, `SendToNode` call count and `activeRequests` growth should plateau independent of N once the caller's limit is exhausted, and the handler should return `api.LimitExceededError`-style responses for excess requests.

func (h *handler) handlePublicKeyGet(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
	if cachedPublicKey != nil {
		l.Debugw("returning cached public key response")
		return h.sendSuccessResponse(ctx, l, ar, &jsonrpc.Response[json.RawMessage]{
			Version: jsonrpc.JsonRpcVersion,
			ID:      ar.req.ID,
			Method:  ar.req.Method,
			Result:  (*json.RawMessage)(&publicKeyResponseBytes),
		})
	}

	l.Debugw("cache stale: forwarding request to nodes", "now", h.clock.Now())
	return h.fanOutToVaultNodes(ctx, l, ar)
}

func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}
