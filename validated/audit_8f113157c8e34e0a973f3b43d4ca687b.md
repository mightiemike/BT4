## Analysis

The Compound-strategy bug is a **memoized/stale on-chain value used to gate an economically-critical threshold decision, without any invalidation when the underlying ground truth changes**. Searching the in-scope areas (burn sortition/distribution, coordinator, boot signer contracts) for the same pattern turns up a structurally identical case in the signer-weight voting contract, which gates approval of the reward-cycle's aggregate signing key — a decision that determines "signer weight below threshold or from the wrong set."

### The analog

`signers-voting.clar` maintains a memoization map that is populated **once** and never refreshed: [1](#0-0) 

The memoized value is computed lazily on the first vote of a cycle and cached permanently thereafter: [2](#0-1) 

This cached `cycle-total-weight` is what determines the approval threshold for the DKG aggregate public key: [3](#0-2) 

...and is consumed directly inside `vote-for-aggregate-public-key` to decide when a candidate key has crossed 70% support and gets committed as the reward cycle's approved key: [4](#0-3) 

Critically, `.signers` — the contract that is the *source of truth* for the signer list/weights that back this cache — places **no restriction preventing re-writes to the same `reward-cycle`**; its guard only prevents going backwards to an older cycle: [5](#0-4) 

Both `set-signers` and `stackerdb-set-signer-slots` are written together, from the node, via `update_signers`, which is invoked from the reward-set/signer-set calculation routine for a given reward cycle: [6](#0-5) [7](#0-6) 

### The equality broken

`get-threshold-weight` is supposed to equal `70% of the *current* total signer weight for the reward cycle`. Once `get-and-cache-total-weight` has been invoked by any single vote, that equality is permanently frozen to whatever `.signers`' contents were **at that instant**. If `.signers`' `cycle-signer-set` for that same reward cycle is subsequently updated (e.g., because the reward-set/signer-set computation for the cycle is re-run — the write path (`update_signers`) is not gated against being called twice for the same `reward_cycle`, unlike the sortition-DB reward-set cache, which explicitly re-validates and overwrites stale/unknown-anchor-block reward sets in the coordinator once the true data becomes available, per `stackslib/src/chainstate/coordinator/mod.rs:799-847`), `signers-voting`'s cached `total-weight` no longer matches the real signer-set weight. A minority of signers by the *true, current* weight could then reach `>= threshold-weight` computed against the smaller, **stale** cached total, and get an aggregate key approved (`map-insert aggregate-public-keys`) with less than the intended 70% real consensus — mirroring the "cached exchange-rate" leak, but here the leaked value is *voting power*, not token value.

### Uncertainty

I could not fully trace whether the reward-set/signer-set calculation (`pox_4_compute_and_update_signers` / `pox_5_compute_and_update_signers`, gated by `NakamotoSigners::check_and_handle_prepare_phase_start`) is ever actually re-invoked for the *same* `reward_cycle` within a single fork in current mainline logic — the body of `check_and_handle_prepare_phase_start` was not fully read in this pass, so I cannot state with certainty that this write-path is reachable more than once per cycle today. What is confirmed by the code itself is: (1) `signers.clar`'s `set-signers` guard does not prevent a same-cycle re-write, and (2) `signers-voting.clar`'s cache is explicitly designed to never recompute once set, with no invalidation logic tied to changes in `.signers`. This is a structural staleness hazard identical in kind to the report even if the concrete trigger path needs deeper verification (e.g., via a Devin session with full execution tracing) to confirm current-day reachability.

### Title
Signer-weight threshold computed against a permanently-cached `cycle-total-weight` that is never invalidated when `.signers` is rewritten for the same cycle - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
`signers-voting.clar` memoizes the total signer weight for a reward cycle the first time any signer votes, and never recomputes it thereafter, even though the underlying `.signers` contract's `cycle-signer-set` for that same reward cycle can, in principle, be overwritten again by the node (no same-cycle guard exists in `signers.clar`'s `set-signers`). If the signer set legitimately changes for the cycle after the cache was already populated, `get-threshold-weight` continues enforcing 70% of the stale, no-longer-accurate total.

### Finding Description
`get-and-cache-total-weight` (lines 103-109) short-circuits to the cached value from `cycle-total-weight` on every call after the first, regardless of whether `.signers`' `cycle-signer-set` map for that reward cycle has since been updated. `signers.clar`'s `set-signers` (lines 28-33) only asserts that the reward cycle being written matches `last-set-cycle` — it does not prevent the *same* reward cycle from being written to multiple times in succession by `update_signers` in the node. There is no cross-contract invalidation: `signers-voting` never re-reads `.signers` once cached.

### Impact Explanation
The approval threshold (`get-threshold-weight`, line 91-93) and hence the final `>= threshold-weight` check in `vote-for-aggregate-public-key` (line 181) is computed against a value that can diverge from the real, current total signer weight for the cycle. This directly maps to the "signer weight below threshold or from the wrong set" impact category: an aggregate DKG key controlling the reward cycle's threshold signature scheme could be approved with support from signers representing less than 70% of the actual live signer weight, undermining the security assumption of the signer-set threshold-signing model for that cycle.

### Likelihood Explanation
Medium/uncertain. The vulnerable memoization pattern and missing same-cycle write guard are both present in the shipped contracts. What remains unverified is whether the Rust-side reward-set/signer-set computation (`pox_4_compute_and_update_signers`/`pox_5_compute_and_update_signers`, gated by `NakamotoSigners::check_and_handle_prepare_phase_start`) is reachable more than once for the same reward cycle in the current codebase; confirming this requires deeper tracing of `check_and_handle_prepare_phase_start`'s guard logic than could be completed here.

### Recommendation
Either (a) remove the memoization and always recompute `total-weight` by re-summing `.signers get-signers` on every vote, or (b) explicitly invalidate/recompute `cycle-total-weight` any time `.signers`' `set-signers` is called for a reward cycle that already has a cached weight (e.g., have `set-signers` clear or bump a version counter that `signers-voting` checks before trusting its cache).

### Proof of Concept
Not independently reproduced; this is a code-pattern analog derived from static analysis of `signers-voting.clar` and `signers.clar`. Reproducing it concretely would require confirming (via a Devin session with full build/test tooling) a reachable path where the node's `update_signers` is invoked twice for the same `reward_cycle` with differing signer weights before/after a vote has occurred, then demonstrating that a minority (by true weight) of signers can still push an aggregate key past `get-threshold-weight`.
