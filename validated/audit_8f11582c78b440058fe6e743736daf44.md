### Title
Active-permission keys can be granted rights to execute `AccountPermissionUpdateContract`, letting a lower-trust (daily-use) key overwrite the Owner permission - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
The external report describes an authorization design flaw: a single, coarse-grained modifier (`onlyAuthorized`) protects functions of very different sensitivity, including one (`setKeeper()`) that should require a strictly *higher* privilege than the operational "keeper" role it gates. If the lower-trust keeper key is compromised, the attacker can use that same access to reassign the higher-trust role, escalating from operational to full control and enabling fund loss. The java-tron permission model contains an analogous structural weakness in `AccountPermissionUpdateActuator`: an `Active` permission (the "daily operations" role, normally restricted to a specific bitmap of contract types and often protected only by a low signature threshold) can be granted the bit for `AccountPermissionUpdateContract` itself. That grants any holder of that lower-trust Active key the ability to invoke `AccountPermissionUpdateContract` and overwrite the account's `Owner` permission - i.e., escalate from an operational key to full ownership control, exactly mirroring the keeper→setKeeper escalation path in the report.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` validates a submitted `Active` permission's `operations` bitmap only against the chain's globally allowed contract-type bitmap (`dynamicStore.getAvailableContractType()`); it does not exclude the `AccountPermissionUpdateContract` type itself from what an `Active` permission may be authorized to call: [1](#0-0) 

Separately, when an account is first created, the *default* Active permission explicitly omits the `AccountPermissionUpdateContract` bit via `getActiveDefaultOperations()`: [2](#0-1) 

However, nothing in `checkPermission()`/`validate()` prevents an owner from later customizing an `Active` permission and explicitly turning that bit on (this is confirmed by the test asserting that the full `checkAvailableContractType` bitmap - used to validate custom Active permissions - includes `AccountPermissionUpdateContract`, while only the *default* bitmap excludes it): [3](#0-2) [4](#0-3) 

Once such a custom Active permission exists, any broadcast transaction signed with `permission_id` set to that Active permission and reaching its (typically low) weight threshold is accepted by the transaction-level permission check, which only verifies that the referenced permission's operations bit is set for the contract type being executed - it performs no distinction of "this contract type must only be executed under the Owner permission": [5](#0-4) [6](#0-5) 

Consequently, a key holding only Active-tier authority (intended for routine/day-to-day transfers, voting, etc.) can call `AccountPermissionUpdateContract` and, via `AccountPermissionUpdateActuator.execute()`, unconditionally overwrite the account's Owner permission with attacker-controlled keys: [7](#0-6) 

This is structurally the same bug class as the reported issue: a single authorization gate is reused across functions/contract-types of differing sensitivity, so an entity that should only hold a *narrower*, operational privilege (the "keeper"/Active-key analog) ends up able to perform the action that redefines the *higher* privilege (the "setKeeper"/Owner-permission analog), instead of that action being restricted to a strictly stronger check (an `onlyGovernance`/Owner-only analog).

### Impact Explanation
If an Active-permission key that has been granted (deliberately or via misconfiguration/tooling defaults) the `AccountPermissionUpdateContract` bit is compromised, the attacker gains full control of the account: they can rewrite the Owner permission to attacker-only keys, permanently locking out the legitimate owner and enabling theft of all TRX/TRC10/TRC20 balances, delegated resources, and any smart-contract-held funds controlled by that account. This is a full account takeover / asset-loss outcome, more severe than the disclosure of just the Active key's intended (narrow) capabilities.

### Likelihood Explanation
Exploitability depends on an account owner having configured an Active permission that includes the `AccountPermissionUpdateContract` bit (this is not the default state created by `createDefaultActivePermission`, but it passes validation and is not blocked by `checkPermission`/`checkAvailableContractType`). Given that multisig setups in TRON are configured by end users/wallets and the permission-update actuator's validation logic imposes no special restriction preventing this bit from being included in Active permissions, misconfiguration is plausible, especially since tooling/documentation does not clearly flag this as dangerous. The likelihood is therefore contingent on operational key-management practices rather than a universally-reachable flaw, similar to how the original report's issue also depends on the keeper key being compromised.

### Recommendation
Disallow the `AccountPermissionUpdateContract` bit from ever being set in the `operations` bitmap of a non-Owner (`Active`) permission inside `AccountPermissionUpdateActuator.checkPermission()`, enforcing that only the `Owner` permission (`permissionId == 0`) can execute `AccountPermissionUpdateContract`. This mirrors the reported recommendation of introducing a strict `onlyGovernance`-equivalent gate for privilege-redefining operations, separate from the gate used for routine/operational actions.

### Proof of Concept
1. Owner account `A` creates a custom `Active` permission (id=2, threshold=1) whose `operations` bitmap includes the bit for `AccountPermissionUpdateContract` (permitted because `checkPermission()` only checks against `getAvailableContractType()`, which is not restricted to exclude this type - see `checkAvailableContractType` test asserting the bitmap includes it) and assigns this Active permission to a "hot" operational key `K`.
2. `K` is compromised (leaked/stolen, e.g. from a bot/keeper service).
3. Attacker crafts an `AccountPermissionUpdateContract` transaction for account `A`, sets `permission_id = 2`, and signs with `K`.
4. `TransactionCapsule.checkPermission`/`validateSignature` accepts the transaction because `permission.getType() == Active` and the operations bit for `AccountPermissionUpdateContract` is set, and threshold (1) is met by `K`'s signature alone.
5. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, overwriting the Owner permission to attacker-controlled keys, giving the attacker full control of account `A`.

      logger.debug(e.getMessage(), e);

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
