### Title
Reverted Bridge deposits are silently purged from `DepositDataMempool`, permanently freezing depositor funds - (File: crates/sequencer/src/runner.rs)

### Summary
`produce_l2_block_inner` fetches a batch of raw deposit blobs via `fetch_deposits`, and after producing the block, unconditionally calls `remove_deposits(&deposit_data)` with the *entire original fetched list*, regardless of whether each individual deposit's `Bridge.deposit()` system transaction actually succeeded on-chain. `process_sys_txs` explicitly catches `EvmSystemTransactionNotSuccessful` for deposits, reverts the working set, and silently `continue`s without including the failed deposit transaction in `all_txs`/`txs_to_run`. Because the deposit is dropped from the produced block but still removed from the mempool, its raw bytes are permanently lost with no retry path.

### Finding Description
The binding the sequencer relies on is: `deposit removed from DepositDataMempool == deposit whose Bridge.deposit() succeeded and credited L2`. This binding is broken.

Trace:
1. `produce_l2_block_inner` calls `self.deposit_mempool.lock().fetch_deposits(self.config.deposit_mempool_fetch_limit)` [3](#0-2) , which only reads/clones the queue without removing anything [4](#0-3) .
2. `deposit_data` is passed into `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs` [5](#0-4) .
3. Inside `process_sys_txs`, each deposit is applied as a `SYSTEM_SIGNER` system tx via `self.stf.apply_l2_block_txs`. If it fails with `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful` (e.g., the underlying Bitcoin move-tx was already nullified by a colliding/duplicate deposit, or any other on-chain Solidity revert condition), the code reverts the working set, decrements the nonce, and `continue`s — crucially, it does **not** push `sys_tx_rlp` into `all_txs` [6](#0-5) .
4. The resulting `txs_to_run` (which excludes the failed deposit) is what actually gets applied to the real block via `instrumented_apply_l2_block_txs` [2](#0-1) . The failed deposit therefore never appears on-chain at all — not even as a reverted transaction with a receipt.
5. After the block is saved, `produce_l2_block_inner` calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the **original, unfiltered** `deposit_data` list fetched in step 1 — not the filtered `txs_to_run` [7](#0-6) .
6. `remove_deposits` computes `calc_tx_id` for every deposit in the passed slice and removes all matches from both `accepted_deposit_txs` and `pending_deposits` unconditionally [8](#0-7) .

There is no code anywhere that reconciles which deposits from `deposit_data` actually ended up in `txs_to_run`/`all_txs` versus which were dropped by `process_sys_txs`. The `eth_call` simulation performed by `citrea_sendRawDepositTransaction` at acceptance time [9](#0-8)  only guarantees the call succeeds against a *prior* pending state snapshot; it provides no guarantee against state changes (e.g., another deposit consuming/nullifying the same underlying Bitcoin move-tx, or any other state-dependent revert condition) between simulation and actual block-production dry run. No existing guard (`is_system_caller`, `Auth`, `CitreaTransactionValidator`, etc.) checks or restores the mempool entry after such a revert.

### Impact Explanation
For any deposit whose `Bridge.deposit()` call reverts during block production after having passed the initial `eth_call` simulation, the raw deposit bytes are unconditionally purged from `DepositDataMempool` (`accepted_deposit_txs` and `pending_deposits`) even though the deposit was never included and never credited on L2. Since `add_deposit_tx` deduplicates by `calc_tx_id` derived from the Bitcoin move-tx fields [10](#0-9) , and the mempool is purely in-memory with no persistence or retry queue, the depositor has no way to resubmit once the entry is dropped — a `citrea_sendRawDepositTransaction` retry that reuses the exact same bytes would need to pass simulation again, but the underlying condition causing the revert (e.g., nullification) is permanent. This matches the "funds permanently frozen" Critical impact category: the Bitcoin-side BTC is moved to the bridge vault but the corresponding cBTC credit is dropped and can never be replayed through this deposit-mempool path.

### Likelihood Explanation
No special privilege is required — any user calling `citrea_sendRawDepositTransaction` can trigger this if their deposit's execution outcome changes between the `eth_call` simulation time and the actual block-production dry run (e.g., because another deposit affecting shared bridge state, such as a colliding/duplicate underlying transaction, was processed first, or general race conditions in bridge contract state). This requires no coordinated timing attack by a third party — an interleaving of two independently-submitted deposits (or even the depositor's own competing submissions) is sufficient, making this reachable via completely normal use of the public JSON-RPC endpoint.

### Recommendation
Track which entries of `deposit_data` actually succeeded (i.e., were pushed into `all_txs`/`txs_to_run` in `process_sys_txs`) and only call `remove_deposits` with that successful subset. Deposits that fail `apply_l2_block_txs` should remain in `DepositDataMempool` (or be moved to a distinct retry/dead-letter set) so they can be retried or explicitly surfaced to the operator/depositor rather than silently dropped.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }

    fn calc_tx_id(req: &Deposit) -> anyhow::Result<[u8; 32]> {
        let call = BridgeContract::depositCall::abi_decode_raw(req, true)
            .map_err(|e| anyhow::anyhow!("Could not decode DepositCall ABI: {e:?}"))?;

        data.extend_from_slice(&tx.vin.0);
        data.extend_from_slice(&tx.vout.0);
        data.extend_from_slice(&tx.locktime.0);

        let hasher = Sha256::hash(&data);

        let second = Sha256::hash(&hasher);

        Ok(second)
    }
