This confirms `storeSession` is invoked on every offline token refresh, which happens automatically whenever a session nears expiry (within 5 minutes) — a routine, repeatable event triggered by normal merchant/app traffic, not requiring privileged access.

### Title
Unbounded Duplicate Session-ID Accumulation in KV Shop Index Enables Storage-Exhaustion DoS - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds` appends session IDs to the per-shop index array without checking for existing membership, unlike the sibling `RedisSessionStorage.addKeyToShopList` implementation which explicitly guards against duplicates.

### Finding Description
`storeSession` calls `addShopIds(session.shop, [session.id])` on every save [1](#0-0) . `addShopIds` unconditionally concatenates the new id(s) onto the existing `shop:${shop}` array and writes it back, with no dedup check: `JSON.stringify([...shopIds, ...ids])` [2](#0-1) . This is exactly the bug class described in the report: an entry can be re-inserted into a tracking array without removing/deduping the prior occurrence, causing double counting in downstream logic (`findSessionsByShop`, which maps over every id in the array and loads it — duplicate ids cause redundant loads) [3](#0-2) .

By contrast, the Redis implementation explicitly checks `if (!idKeysArray.includes(idKey))` before pushing [4](#0-3) , confirming the KV version is a regression/oversight relative to the intended design.

`storeSession` (and thus `addShopIds`) is invoked automatically — with no attacker interaction beyond normal app usage — whenever an offline token is refreshed near expiry, via `ensureOfflineTokenIsNotExpired`, which calls `config.sessionStorage.storeSession(offlineSession)` with the **same session id** each time it runs [5](#0-4) . Because the offline session id is stable for a shop, every refresh cycle appends another duplicate copy of the same id to the `shop:${shop}` KV value, growing it without bound over the life of an installation.

### Impact Explanation
KV backends (e.g., Cloudflare Workers KV) impose hard limits on value size and per-key write frequency. Continuous duplicate accumulation in the `shop:${shop}` index will eventually cause `namespace.put` writes to fail once the value exceeds the size limit, breaking `findSessionsByShop` and `deleteSession`/`removeShopIds` bookkeping for that shop — i.e., a denial-of-service degradation of the session-storage layer underlying authentication for that shop, achievable purely through the app's normal, unauthenticated-relative-to-attacker token-refresh lifecycle. It also causes `findSessionsByShop` to return duplicate `Session` objects, which any consumer trusting array length/uniqueness (e.g., app-installation checks) could be misled by.

### Likelihood Explanation
No special privileges are required beyond having an installed session that periodically refreshes (which happens automatically per app/merchant usage); the flaw is triggered purely by the passage of time and normal request traffic, making it highly likely to manifest in any long-lived app installation using `KVSessionStorage`.

### Recommendation
Update `addShopIds` in `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts` to dedupe before writing, mirroring the Redis implementation, e.g.:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Configure an app with `KVSessionStorage` and `future.expiringOfflineAccessTokens` enabled.
2. Install the app for a shop, creating an offline session with id `S`.
3. Repeatedly trigger requests to the app after each 5-minute expiry window (or simulate by manipulating `session.expires`) so `ensureOfflineTokenIsNotExpired` refreshes and calls `storeSession` with the same session id `S` each time [6](#0-5) .
4. Observe that `shop:${shop}` in the KV namespace grows by one duplicate entry of `S` per refresh with no bound, eventually approaching the KV value size limit and causing `findSessionsByShop`/`storeSession` writes to fail for that shop.
