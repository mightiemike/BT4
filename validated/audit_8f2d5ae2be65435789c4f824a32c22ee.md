Confirmed vulnerability. `GetSignedSignEvents` is deterministic — `ORDER BY block_height ASC, created_at ASC LIMIT 100` over rows filtered by `status = SIGNED` [1](#0-0) . In `Broadcaster.processSigned`, the inner `for {}` loop repeatedly calls this query and only exits when `len(events) < processSignedBatchSize` [2](#0-1) . If ≥100 SIGNED SVM events exist and every one of them fails to transition out of SIGNED, the same deterministic top-100 rows are returned on every iteration.

`broadcastOutboundSVM` only leaves an event in SIGNED status when the deadline hasn't cluster-confirmed as expired and `BroadcastOutboundSigningRequest` fails and `IsAlreadyExecuted` returns false [3](#0-2) . An attacker fully controls the outbound payload contents via ordinary deposit/withdrawal flows (recipient/program/ixData feed into `signingReq`/`outboundData`), so they can craft SVM outbound instructions/programs that deterministically make the SVM builder's `BroadcastOutboundSigningRequest` fail (e.g., a nonexistent/invalid program ID, malformed instruction data causing local encoding/simulation failure) while never landing on-chain, so `IsAlreadyExecuted` also always returns false. As long as the local clock check (`now > deadline`) with cluster confirmation (`clusterTime > deadline`) also never confirms expiry — e.g., attacker sets the future deadline far out, or triggers cases where `checkErr != nil` (RPC/cluster query error) repeatedly returns early — the event stays SIGNED forever.

With ≥100 such permanently-stuck SIGNED events, `processSigned`'s inner loop never observes `len(events) < 100`, so it spins indefinitely within a single tick invocation. Because `run()` calls `b.processSigned(ctx)` synchronously inside its `select` loop [4](#0-3) , an unbounded `processSigned` call blocks the ticker goroutine from ever reaching the next `select` iteration — no future ticks are processed, and no other pending SIGNED events (including EVM outbounds queued after the malicious batch, due to `ORDER BY block_height, created_at`) ever get broadcast. This is a real, reachable, non-network-level liveness/DoS bug: the broadcaster component halts permanently, and no further UniversalTx reaches BROADCASTED, matching the "in-scope" DoS impact criteria (non-network-level, reachable without privileged control).

Note: `ctx` is passed into `builder.BroadcastOutboundSigningRequest`/`IsAlreadyExecuted`, but the surrounding `for {}` in `processSigned` itself has no `ctx.Done()` check, so even a canceled context does not break the loop — confirmed by reading the loop body [5](#0-4) .

### Title
Attacker-crafted SVM outbound events that permanently fail broadcast can wedge `Broadcaster.processSigned` in an infinite loop, halting all EVM/SVM broadcast liveness - (File: universalClient/tss/txbroadcaster/broadcaster.go, universalClient/tss/txbroadcaster/svm.go)

### Summary
An unprivileged user who causes ≥100 SVM outbound events to be created (via ordinary deposit/withdrawal flows that reach outbound signing) can craft the outbound payload (recipient/program/instruction data) so that `broadcastOutboundSVM` never succeeds and never reaches the deadline/`IsAlreadyExecuted` give-up branch, keeping the events perpetually in `SIGNED` status. Since `Broadcaster.processSigned` re-queries the exact same deterministic top-100 `SIGNED` batch every loop iteration and only exits when the batch shrinks below 100, this stalls the broadcaster forever, since `processSigned` is called synchronously from the ticker's `select` loop in `run()`.

### Finding Description
`processSigned` uses an unbounded `for {}` loop that repeatedly calls `GetSignedSignEvents(100)` [5](#0-4) . `GetSignedSignEvents` performs a deterministic ordered query (`block_height ASC, created_at ASC`) over rows with `status = SIGNED` [1](#0-0) . If the same 100 rows remain SIGNED across iterations, the loop condition `len(events) < processSignedBatchSize` never triggers, so the function never returns.

`broadcastOutboundSVM` leaves an event in `SIGNED` state whenever `BroadcastOutboundSigningRequest` errors and `IsAlreadyExecuted` reports false, and the deadline/cluster check hasn't confirmed expiry [3](#0-2) . Both conditions are attacker-influenceable through the content of the outbound payload derived from the user's original deposit/withdrawal request (destination program, instruction data), letting an attacker manufacture outbound instructions that are locally rejected by the SVM tx builder (e.g. malformed/invalid program invocation) but never land on-chain.

### Impact Explanation
Because `run()` invokes `processSigned` synchronously inside its `select`-based ticker loop [4](#0-3) , an unbounded call to `processSigned` blocks all future ticks. No further SIGNED events of any type (EVM or SVM) are ever broadcast, and legitimate UniversalTx records can never reach `BROADCASTED`. This is a material, non-network-level denial of service triggerable purely by ordinary (if adversarially crafted) user transactions, without any privileged actor.

### Likelihood Explanation
Requires only that an unprivileged user submit ≥100 deposit/withdrawal requests routed to SVM outbound with payload data engineered to fail broadcast deterministically (e.g. invalid target program/account or malformed instruction data) while remaining unconfirmed on-chain. This is achievable purely through normal, user-reachable deposit/withdraw flows without any validator/TSS collusion.

### Recommendation
Bound the `processSigned` inner loop (e.g., cap total iterations per tick, or check `ctx.Done()` each iteration), and/or track per-event retry/backoff so that events which fail broadcast are deprioritized (e.g., not re-selected on every immediate retry) or transitioned to a terminal `FAILED`/`REVERT`-eligible status after N consecutive failures, so a batch of permanently-unbroadcastable events cannot monopolize the deterministic top-N query indefinitely.

### Proof of Concept
1. Attacker submits ≥100 deposit/withdrawal operations that generate SVM outbound events with `ixData`/`program`/`recipient` crafted so that the resulting instruction is well-formed enough to be signed but always rejected by `BroadcastOutboundSigningRequest` (e.g., referencing an invalid/closed program account) and never lands on-chain (`IsAlreadyExecuted` stays false), with `SigningDeadline` far enough in the future (or such that `IsAlreadyExecuted`'s cluster check returns `checkErr != nil` on every attempt after the deadline).
2. These events reach `SIGNED` status via normal TSS signing flow.
3. On the next tick, `run()` calls `processSigned(ctx)` [6](#0-5) , which fetches the 100 events, attempts each via `broadcastOutboundSVM`, all remain SIGNED, and since `len(events) == 100` the loop repeats indefinitely with the identical set.
4. `processSigned` never returns; the ticker goroutine is permanently blocked, and no other SIGNED events (EVM or SVM, including legitimate ones) are ever broadcast again.

func (b *Broadcaster) processSigned(ctx context.Context) {
	if b.chains == nil {
		return
	}
	for {
		events, err := b.eventStore.GetSignedSignEvents(processSignedBatchSize)
		if err != nil {
			b.logger.Warn().Err(err).Msg("failed to get signed events")
			return
		}
		if len(events) == 0 {
			return
		}
		for i := range events {
			b.broadcastEvent(ctx, &events[i])
		}
		if len(events) < processSignedBatchSize {
			return
		}
	}
}
