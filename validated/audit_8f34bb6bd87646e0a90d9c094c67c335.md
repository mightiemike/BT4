Based on the investigation, the strongest unprivileged analog in java-tron to the Lens "namespace squatting breaks future migration" bug is **CREATE2/CREATE address front-running**, where any anonymous, unprivileged caller can deterministically pre-compute and occupy a contract address before its intended legitimate owner deploys there, permanently blocking that deployment — mirroring how an unprivileged handle mint blocked a future migration mint of the same identifier.

### Title
Anonymous CREATE2 address squatting can permanently block a legitimate contract deployment - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.createContractImpl()` computes the new contract's address deterministically (via `CREATE` nonce-hash or `CREATE2` salt+codehash) and unconditionally reverts contract creation if an account/contract already exists at that address and is considered "already existing" per `isContractExist()`. Because both the `CREATE` address (sender+nonce/txid hash) and `CREATE2` address (deployer+salt+codehash) are fully computable off-chain by anyone, an unprivileged, anonymous transaction sender can pre-emptively deploy junk bytecode to an address that a legitimate protocol/dApp intends to deploy to later (e.g., predictable factory + salt schemes), permanently causing the legitimate deployment to revert with "Trying to create a contract with existing contract address."

### Finding Description
`WalletUtil.generateContractAddress()` derives the top-level `CREATE` address purely from the transaction id and owner address [1](#0-0) , and `Program.createContractImpl()` derives the internal `CREATE2` address from sender address, salt, and code hash [2](#0-1) . When `createContractImpl` runs, it checks whether an account already exists at the target address and treats an existing contract as fatal: [3](#0-2) 
If `contractAlreadyExists` is true, the creation attempt is rejected with an exception instead of succeeding [4](#0-3) , and the same check/failure exists for top-level contract creation in `VMActuator.create()` [5](#0-4) . Since any anonymous account can broadcast a `CreateSmartContract`/`TriggerSmartContract` transaction, and salts/factory addresses used by well-known deployment patterns (e.g., CREATE2 factories, deterministic proxy deployers) are public knowledge, an attacker can race to deploy filler bytecode to the predicted address before the legitimate deployer's transaction lands — permanently occupying that identifier, exactly as the Lens whitelisted-creator bug permanently occupied a handle that a later V1-profile migration needed.

### Impact Explanation
This is a griefing/DoS vector against any protocol relying on deterministic `CREATE`/`CREATE2` addresses on java-tron (factories, counterfactual wallet deployment, cross-chain address parity schemes such as the TIP-2935 deployment pattern seen in `HistoryBlockHashUtil` which explicitly documents handling of pre-existing accounts at a canonical address) [6](#0-5) . A successful squat permanently prevents the intended contract from ever being deployed at that address, since address+nonce/salt combinations are typically not retried with different salts by application logic, corrupting expected on-chain deployment/migration flows analogous to the Lens handle case.

### Likelihood Explanation
Reachable by any anonymous account issuing an ordinary `TriggerSmartContract` (to a public factory) or `CreateSmartContract` transaction — no special privilege, key leak, or node compromise is required, only knowledge of the deterministic address formula, which is public by design of `CREATE`/`CREATE2`. This mirrors the "unprivileged actor can pre-claim reachable identifier" root cause of the referenced report, but does not require the "privileged whitelisted creator" role that the original report assumed.

### Recommendation
Applications that rely on deterministic deployment addresses should be aware this is inherent to `CREATE`/`CREATE2` semantics; at the protocol layer, consider exposing a way to query whether an address is already claimed (similar to the Lens fix's `getProfileIdByHandleHash` off-chain check) before a deployer commits to a specific salt/address, and encourage factories to include deployer-specific entropy (e.g., `msg.sender`) in the salt to prevent third-party front-running of predictable slots.

### Proof of Concept
1. Deploy a public CREATE2 factory contract (as in `Create2Test.testCreate2`) [7](#0-6) .
2. An attacker, knowing the salt/deployer/codehash a legitimate dApp plans to use, computes the same address via `generateContractAddress2` and submits their own `deploy()` call first.
3. When the legitimate deployer's transaction later executes `createContractImpl` for the same address, `contractAlreadyExists` is true and the call fails permanently with "Trying to create a contract with existing contract address" [4](#0-3) , blocking the intended deployment indefinitely — the same permanent-blocking effect as the original Lens finding.

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
