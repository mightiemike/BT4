### Title
Unchecked `long` summation of unfreeze amounts allows silent integer overflow in `WithdrawExpireUnfreezeActuator` - ([File: actuator/src/main/java/org/tron/core/actuator/WithdrawExpireUnfreezeActuator.java])

### Summary
`WithdrawExpireUnfreezeActuator` computes the total amount to credit back to an account's balance from its list of expired `UnFreezeV2` entries using an unchecked Java Stream `sum()`, and then adds that total to the account balance with a plain `+` operator instead of the codebase's own overflow-safe helpers (`addExact`/`LongMath.checkedAdd`) that are used consistently elsewhere in this same class and in sibling actuators (`AssetIssueActuator`, `TransferActuator`, `ExchangeInjectActuator`, `VoteWitnessProcessor`, etc.). This mirrors the reported `check_total_coins` bug class: a summation over an attacker/user-influenced list is not checked for overflow before being used in an accounting decision.

### Finding Description
`getTotalWithdrawUnfreeze` sums the `unfreeze_amount` field of all expired `UnFreezeV2` records using `Stream.mapToLong(...).sum()`, which performs plain `long` addition and silently wraps on overflow (unlike `Math.addExact`/`LongMath.checkedAdd`): [1](#0-0) 

The result is used first in `validate()`: [2](#0-1) 

and then in `execute()` it is added to the account balance with plain arithmetic (no `addExact`/`checkedAdd` guard at all, unlike the rest of the class which does check overflow for the *pre-sum* value): [3](#0-2) 

The overflow-check the code does perform (`LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze)`) only protects against overflow of the *final addition*; it does nothing to protect the `sum()` call itself. If the `mapToLong(...).sum()` step already wrapped around (because the individual `UnFreezeV2.unfreeze_amount` entries summed past `Long.MAX_VALUE`), `totalWithdrawUnfreeze` becomes an arbitrary (possibly small or negative) value **before** the checked-add ever runs, so the check validates the wrong number. This is architecturally identical to the reported bug: an unguarded sum over a list of values feeding directly into a balance/accounting decision, while a guarded step exists only downstream of the flawed sum.

The identical unguarded-sum pattern (`AtomicLong.addAndGet(unFreezeV2.getUnfreezeAmount())` in a loop, and `ownerCapsule.setBalance(ownerCapsule.getBalance() + withdrawExpireBalance)`) also exists in the sibling, equally unprivileged `CancelAllUnfreezeV2Actuator`: [4](#0-3) [5](#0-4) 

By contrast, other actuators in the same package (`TransferActuator`, `TransferAssetActuator`, `ParticipateAssetIssueActuator`, `AssetIssueActuator`, `ExchangeInjectActuator`, `VoteWitnessProcessor`) consistently guard every balance addition with `addExact`/`LongMath.checkedAdd`, confirming this is the established secure pattern that `WithdrawExpireUnfreezeActuator`/`CancelAllUnfreezeV2Actuator` deviate from for the *aggregate* sum step.

### Impact Explanation
If an account could ever accumulate a set of `UnFreezeV2` entries whose `unfreeze_amount` values sum past `Long.MAX_VALUE`, the wrap-around would corrupt the balance-crediting logic used by an unprivileged, self-service transaction type (`WithdrawExpireUnfreezeContract` / `CancelAllUnfreezeV2Contract`), leading to an incorrect account balance being written to chain state — a concrete accounting/invalid-state defect matching the report's "incorrect values ... crashing the application" class, here manifesting as silent balance corruption rather than a crash, since Java `long` sum wraps instead of throwing.

### Likelihood Explanation
I could not confirm within the codebase that there is any hard cap on the number of entries an account's `unfrozenV2` list can hold (no `MAX_UNFREEZE_COUNT`-style constant was found), so the number of summed entries is not obviously bounded independent of the account's real, circulating TRX balance. However, each individual `unfreeze_amount` is itself bounded by amounts actually frozen from the account's real balance, which is bounded by TRX's total circulating supply (order of 1e17 sun) — several orders of magnitude below `Long.MAX_VALUE` (~9.2e18). Reaching an overflow purely by accumulating many small unfreeze/refreeze cycles from one account is not clearly demonstrated to be practical, and I was unable to verify whether any additional constraints (e.g., a freeze/unfreeze count limit, or the `MAX_ACTIVE_ORDER_NUM`-style guards seen elsewhere) exist to further bound the list size. Given this uncertainty, likelihood is assessed as low/uncertain rather than clearly practical — this is a defense-in-depth / code-hygiene gap rather than a proven, immediately exploitable overflow.

### Recommendation
Replace the unguarded `Stream.sum()`/`AtomicLong.addAndGet()` aggregation in `getTotalWithdrawUnfreeze` (`WithdrawExpireUnfreezeActuator`) and the equivalent aggregation in `CancelAllUnfreezeV2Actuator.updateAndCalculate` with an overflow-checked accumulation (e.g., `LongMath.checkedAdd` in a reduce/fold, mirroring the pattern already used in `VoteWitnessProcessor`), so that an overflowing sum throws an exception and aborts the transaction instead of silently wrapping, consistent with how every other balance-affecting actuator in this codebase already behaves.

### Proof of Concept
Not independently reproducible from static review alone: exploitation would require constructing an account with `UnFreezeV2` entries whose `unfreeze_amount` values sum past `Long.MAX_VALUE`, which was not confirmed to be reachable given real supply constraints and unclear caps on `unfrozenV2` list length. The vulnerable code path itself is directly demonstrated by the cited lines: `getTotalWithdrawUnfreeze` (lines 122-125) feeds into the balance write at line 57 without any overflow guard on the summation step, differing from the guarded pattern used everywhere else in the file/class hierarchy.
