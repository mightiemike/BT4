### Title
`ensure_match_transaction_info` skips state-checkpoint hash validation, allowing replay-verify tooling to accept a diverged state root as valid - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by replay/verification tooling (chunk executor replay, `aptos-debugger`, and `db-tool`'s `replay_on_archive`) to check that a locally re-executed transaction output matches the transaction info recorded on the authenticated ledger, only compares `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`. It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, which are the fields that actually commit to the resulting Sparse-Merkle/Jellyfish state root. The gap is called out in the code itself with a `TODO(trading-native)` comment admitting that replay-verify tooling can report a successful replay even when the authenticated state root diverges from local execution.

### Finding Description
`TransactionInfo` carries `state_checkpoint_hash` (and, for `TransactionInfoV1`, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) as the binding commitment to the post-execution state root [1](#0-0) . `ensure_match_transaction_info` is the function that is supposed to validate an independently re-computed `TransactionOutput` against this authenticated `TransactionInfo`, but it checks only status, gas, write-set hash, and event root, leaving the state-checkpoint related fields unchecked, with an explicit TODO acknowledging this [2](#0-1) .

This function is invoked from the chunk executor's replay path [3](#0-2) , from `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and from `aptos-move/cli/src/commands.rs`, and the comment specifically names `db-tool`'s `replay_on_archive` tool as being affected. In all of these call sites, this comparator is the mechanism used to assert "my local re-execution produced the same committed result as what was accepted onto the authenticated ledger." Because the state-checkpoint hash comparison is silently skipped, a local re-execution that produces a different state root (e.g., due to a divergent bug in state-checkpoint or hot-state computation, or a discrepancy introduced by the yet-unlanded `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature path) will still pass `ensure_match_transaction_info` as long as the write set and event hashes happen to match.

### Impact Explanation
This breaks the "committed state must match VM/local re-execution result" integrity invariant for the tooling paths that rely on `ensure_match_transaction_info` (replay-verify, debugger-based sanity checks, chunk-executor replay validation). A state-root divergence that would otherwise be a hard-fork-class bug can go undetected by the very tool designed to catch it, because the tool's pass/fail signal does not depend on the state-checkpoint hash at all. This is squarely inside the state-integrity/proof-binding scope (replay and proof-verification paths must preserve deterministic proof binding to the correct root), and a false "replay OK" result on divergent state has high severity implications for catching consensus-breaking bugs before they reach mainnet.

### Likelihood Explanation
Likelihood is Medium: this code path only manifests as a real-world problem when there is already a separate divergence bug in state-checkpoint/hot-state computation (this comparator does not itself corrupt state), but when such a divergence exists, this gap guarantees it is masked rather than caught by the checking tooling, until the feature guarded by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled and depended upon by these verification flows.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` when present) against the locally recomputed checkpoint hash, and update all replay-verify/debugger call sites to pass the recomputed checkpoint hash prior to relying on this function as a correctness gate, as already noted in the existing TODO.

### Proof of Concept
Not directly exploitable as an on-chain transaction; the issue is demonstrated by reading `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2203): the function body only contains `ensure!` checks for `status`, `gas_used`, `write_set_hash`, and `event_root_hash`, with zero references to `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, and the accompanying comment explicitly states that "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
