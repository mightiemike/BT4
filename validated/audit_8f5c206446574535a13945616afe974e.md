## Title
Rounding mismatch between per-freeze accrual and lump-sum unfreeze deduction causes `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` to diverge from the true frozen-balance sum, corrupting bandwidth/energy allocation for all accounts - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java)

### Summary
`FreezeBalanceProcessor.execute` increments the network-wide `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` counters using `frozenBalance / TRX_PRECISION` on each individual freeze call [1](#0-0) , while `UnfreezeBalanceProcessor.execute` decrements the same aggregate using `unfreezeBalance / TRX_PRECISION` computed from the *summed* frozen balance being released in one shot [2](#0-1) . Because integer division does not distribute over addition (`floor(a/p)+floor(b/p) ≤ floor((a+b)/p)`), the aggregate `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` can be reduced by more than what was actually added across multiple separate freeze operations for the same account, driving these globals below the true sum of all live weights (or even negative), similarly to how ZeroLend's `executeMintToTreasury` decremented the pooled `totalSupply.supplyShares` by an amount inconsistent with the underlying per-user accounting.

### Finding Description
`FreezeBalanceProcessor.execute` (used by the legacy `FreezeBalanceContract`, reachable directly by any account and via the TVM native contract path) accrues the resource weight by dividing the *newly frozen* amount by `TRX_PRECISION` on every call and adding it to the store-wide counter:
```java
repo.addTotalNetWeight(frozenBalance / TRX_PRECISION);
``` [1](#0-0) 

If the same account calls `freeze` multiple times with sub-`TRX_PRECISION`-aligned amounts (e.g. two calls of 1,500,000 units with `TRX_PRECISION = 1,000,000`), each call contributes `floor(1,500,000/1,000,000) = 1` to the total, for a cumulative contribution of `2`, even though the true frozen sum is `3,000,000` units (i.e. `3` full weight units).

When the account later unfreezes everything, `UnfreezeBalanceProcessor.execute` computes `unfreezeBalance` as the full accumulated frozen amount removed in that single call and subtracts:
```java
repo.addTotalNetWeight(-unfreezeBalance / TRX_PRECISION);
``` [2](#0-1) 
which in the example above subtracts `floor(3,000,000/1,000,000) = 3`, one unit more than was ever added (`2`). The comment "`// adjust total resource, used to be a bug here`" at that exact line [3](#0-2)  indicates this accounting hazard was already recognized as fragile in this code path.

Unlike the actuator-facing `DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight`, which clamp the result to a minimum of zero when `allowNewReward()` is active [4](#0-3) , the `Repository`/`RepositoryImpl` implementation used by the native-contract (TVM) path performs a raw, unclamped add with no floor at zero:
```java
public void addTotalNetWeight(long amount) {
  long totalNetWeight = getTotalNetWeight();
  totalNetWeight += amount;
  saveTotalNetWeight(totalNetWeight);
}
``` [5](#0-4) 
This means repeated freeze/unfreeze cycles through this path can push `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` to a value lower than the true sum of all accounts' frozen weight, including negative values, with no safety clamp.

`TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` are global denominators used to compute every account's bandwidth/energy limit:
```java
long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
...
return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
``` [6](#0-5) 
A corrupted (too-low or negative) `totalNetWeight`/`totalEnergyWeight` distorts this ratio for every account on the network, not just the one that triggered the drift.

### Impact Explanation
This is an unprivileged-user-triggerable state-corruption bug in a core network-wide accounting value. Any account can call the legacy `FreezeBalanceContract`/`UnfreezeBalanceContract` (or their TVM native-contract equivalents) repeatedly with amounts not aligned to `TRX_PRECISION`, causing the aggregate `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` to diverge downward from the true sum of frozen weights across all accounts. Because these globals are the shared denominator for every account's bandwidth/energy limit calculation, this can inflate (or otherwise miscalculate) resource limits for the entire network, or in extreme repeated-drift scenarios drive the value to zero/negative, causing `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` to return degenerate results (e.g., `0` via the explicit `totalNetWeight == 0` guard, or unintended values if negative) [6](#0-5) . This is a chain-state divergence / underpriced-public-resource-work class impact: the resource-pricing invariant that total weight equals the sum of individually frozen weights is broken by ordinary user transactions, not by a privileged operation.

### Likelihood Explanation
Likelihood is high in principle because both `FreezeBalanceContract` and `UnfreezeBalanceContract` are ordinary, permissionless, frequently-used transactions, and the divergence requires no coordination — just repeated freeze/unfreeze operations with amounts that are not exact multiples of `TRX_PRECISION` (1 TRX = 1,000,000 sun), which is the common case since users can freeze arbitrary sun amounts above 1 TRX. However, the magnitude of drift per cycle is capped at ±1 weight unit (1 TRX) per divergence event, so a single occurrence has negligible measurable effect on the network-wide bandwidth ratio; a large effect requires many repeated cycles or is bounded by how `TRX_PRECISION`-unit accounting error accumulates across the whole `TOTAL_NET_WEIGHT` (which is on the order of billions of TRX). This limits real-world severity relative to the ZeroLend original (where a single treasury mint miscounted the entire accrued share amount, immediately blocking withdrawals).

### Recommendation
Make the unfreeze weight deduction symmetric with the freeze accrual by tracking the weight contribution per freeze record (or by recomputing the account's before/after total-frozen-balance delta, dividing once, as already done correctly in the V2 freeze/unfreeze/delegate processors), rather than dividing the lump-sum unfreeze amount independently. Concretely, `UnfreezeBalanceProcessor` should compute `oldWeight = accountCapsule.getFrozenBalance() / TRX_PRECISION` before removing the expired entries and `newWeight` after, then apply `repo.addTotalNetWeight(newWeight - oldWeight)`, mirroring the pattern already used in `FreezeBalanceV2Processor`/`UnfreezeBalanceV2Processor` [7](#0-6) . Additionally, `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight` should clamp results to a minimum of zero, consistent with `DynamicPropertiesStore`'s implementation [4](#0-3) , to prevent the network-wide weight from going negative under any code path.

### Proof of Concept
1. Account A calls `FreezeBalanceContract` (BANDWIDTH) with `frozenBalance = 1,500,000` sun. `TOTAL_NET_WEIGHT += floor(1,500,000/1,000,000) = 1`.
2. After the frozen period elapses, Account A calls `FreezeBalanceContract` again with `frozenBalance = 1,500,000` sun (accumulating onto the existing frozen entry, since `frozenCount` allows a second freeze). `TOTAL_NET_WEIGHT += floor(3,000,000/1,000,000) - floor(1,500,000/1,000,000) = 3 - 1 = 2`. Cumulative `TOTAL_NET_WEIGHT += 1 + 2 = 3` (this particular delta-based accrual in `FreezeBalanceActuator`/`FreezeBalanceV2Processor` is actually correct because it uses before/after account totals — see step 3 for the mismatched path).
3. Using the legacy `FreezeBalanceProcessor` (native-contract call path) where multiple freezes are, instead, each individually divided (`frozenBalance / TRX_PRECISION`) without delta tracking against the account's running total [1](#0-0) , two calls of 500,000 sun each add `floor(500,000/1,000,000) = 0` twice, i.e., `TOTAL_NET_WEIGHT += 0`, even though a subsequent single unfreeze of the combined `1,000,000` sun subtracts `floor(1,000,000/1,000,000) = 1` via `UnfreezeBalanceProcessor` [2](#0-1) .
4. Net effect: `TOTAL_NET_WEIGHT` decreases by `1` more than it was ever incremented, permanently corrupting the global counter relative to the true sum of all accounts' frozen bandwidth, with no floor-at-zero protection in `RepositoryImpl.addTotalNetWeight` [5](#0-4) .

Note: I was unable to fully trace every call-site permutation (e.g., all combinations of `frozenCount`, `TRON_POWER`, and mixed V1/V2 freeze usage) to determine the maximum achievable cumulative drift within the current index; a Devin session with full repository access and test-execution capability would be needed to construct and run a concrete numeric PoC transaction sequence and confirm the exact magnitude of drift achievable.
