I found a genuine, code-documented integrity gap in `TransactionOutput::ensure_match_transaction_info`, which is the exact function that binds an executor/replay result to the "trusted" `TransactionInfo` used to authenticate state during chunk replay, backup replay, and `db-tool replay-on-archive`.

### Title
`TransactionOutput::ensure_match_transaction_info` never validates the state/hot-state/position checkpoint hashes, letting replay accept a state root divergent from the authenticated ledger - ([File: types/src/transaction/mod.rs])

### Summary
`ensure_match_transaction_info` (used by the chunk executor's replay-verification path and by `db-tool`'s `replay_on_archive`) checks transaction status, gas used, write-set hash, and event-root hash against the trusted `TransactionInfo`, but explicitly skips comparing `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`. The code contains its own acknowledgment of this gap: [1](#0-0) .

### Finding Description
The function is defined at [2](#0-1) . It validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but never touches `txn_info.state_checkpoint_hash()` (or the V1 hot-state/position-state checkpoint hashes), even though `TransactionInfo` carries these fields as the authenticated summary of the post-execution world-state Merkle root [3](#0-2)  and [4](#0-3) .

This function is the sole per-transaction correctness check used by the chunk executor's `verify_execution` step in backup replay-verify and archive replay: [5](#0-4) [6](#0-5) 

The state checkpoint hash is precisely the value that would catch a divergence in the *committed state* itself (e.g., a JMT root miscomputation, a state-value corruption during write-set apply, or a VM regression that doesn't change the write set but changes how state is checkpointed/merklized). By omitting this check, `ensure_match_transaction_info` treats a transaction whose emitted write set/events/status/gas match, but whose resulting state Merkle root differs from the one anchored (via the transaction accumulator) in the signed `LedgerInfo`, as a successful verification.

Notably, `assemble_transaction_infos` (the code that produces "live" `TransactionInfo` during normal block execution) computes `state_checkpoint_hash` from the executor's own live-computed root [7](#0-6) , confirming this field is a first-class part of the authenticated per-transaction commitment that `ensure_match_transaction_info` is supposed to validate against, but doesn't.

### Impact Explanation
This breaks the "committed state must match VM result / accumulator-anchored `TransactionInfo`" invariant during any tooling flow that relies on `ensure_match_transaction_info` as its correctness oracle (`replay-verify`, `replay_on_archive`). A state-root divergence (hard-fork-class bug, storage-layer corruption bug, or a regression in JMT/state-checkpoint computation) would not be flagged by these tools even though write set/events/status/gas all match, because the one field that specifically authenticates the state Merkle root is never checked. This is a real gap in the proof/commitment-integrity chain for state-root auditing tooling — the comment in the code itself flags it as a known risk ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution").

### Likelihood Explanation
This is not attacker-triggerable on its own (no unprivileged remote input directly exploits it), but it is a genuine, code-acknowledged blind spot: any state-corrupting bug elsewhere in the storage/executor stack (write-set apply, JMT commit, restore) that preserves write-set/event/gas/status equality but diverges in the resulting state root will silently pass `replay-verify`/`replay_on_archive`, defeating the primary safety net meant to detect exactly this class of bug before/after a hard fork.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s locally computed state checkpoint hash (and hot-state/position-state checkpoint hashes, where applicable) against `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, consistent with how `assemble_transaction_infos` populates these fields during normal execution. This requires plumbing the locally recomputed checkpoint hash into `TransactionOutput` at the call sites in `execution/executor/src/chunk_executor/mod.rs` and `storage/db-tool/src/replay_on_archive.rs`.

### Proof of Concept
Not independently exploitable by an external attacker; the "proof" is the code path itself:
1. `verify_execution` in the chunk executor (or `execute_and_verify` in `replay_on_archive.rs`) re-executes a transaction and obtains `txn_out` with a write set/events/status/gas identical to the trusted `txn_info` from the backup/archive, but a different resulting state Merkle root (e.g., due to a storage/state-checkpoint bug).
2. `txn_out.ensure_match_transaction_info(version, txn_info, ...)` at [8](#0-7)  returns `Ok(())` because only status/gas/write-set-hash/event-root are compared.
3. The tool reports a successful replay/verification despite the state root diverging from what the signed `LedgerInfo`'s accumulator authenticates — i.e., a "hard-fork-only divergence during replay/verification" that the tool was specifically designed to catch goes undetected.

**Caveat**: This is the strongest candidate I found after evaluating several proof/commitment paths (write-set-to-storage conversion, accumulator/JMT proof verification, restore chunk verification, and state-value-with-proof API binding). Those other paths (`AccumulatorProof::verify`, `SparseMerkleProof::verify_by_hash`, `JellyfishMerkleRestore::verify_chunk`, `TransactionInfoWithProof::verify`, `try_combine_into_storage_change_set`) all correctly enforce root-hash/version binding with no bypass found. I was not able to fully confirm whether this checkpoint-hash gap is intentionally deferred behind a feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, mentioned in the comment) that might be enabled by default in some configurations — that would need direct repository access/build inspection beyond what the index exposes to determine current default behavior with certainty.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
