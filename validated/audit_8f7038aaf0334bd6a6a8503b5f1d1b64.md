Now I have sufficient evidence to write the analysis. This is a strong analog to the reported bug class.

## Finding

The `DelegatedResourceAccountIndexStore.getV2Index()` (and the legacy `getIndex()`) methods perform an unbounded scan over all delegation records for a single address via `prefixQuery`, and this index is populated by cheap, unprivileged, repeatable operations (`DelegateResourceContract` with a 1 TRX minimum, no cap on distinct receivers per owner), directly mirroring the reported "grow-forever store scanned in full on every read" bug class.### Title
Unbounded per-address delegation-index growth via unlimited free `DelegateResourceContract` spam causes unbounded-cost `GetDelegatedResourceAccountIndex` RPC/HTTP scans and unbounded on-chain index rewrite cost - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
The reported bug class is: a state store that is *never pruned/bounded*, is grown by a cheap/free, unprivileged, repeatable user operation, and is later scanned/rebuilt *from scratch* (O(n) with no cap), so that spam of many small entries degrades performance for every node that has to reconstruct that structure. In java-tron, `DelegatedResourceAccountIndexStore` exhibits the same pattern: any account can call the fee-free `DelegateResourceContract` (`calcFee()` returns `0`) with the network minimum of 1 TRX, an unlimited number of times to an unlimited number of distinct receiver addresses, with no cap on the number of index entries per owner/receiver. Reconstructing the delegation index for an address (`getIndex`/`getV2Index`) requires a full prefix scan of *all* entries ever created for that address, unbounded and un-pruned, mirroring the "GetDepositsByIndex(0, ...)" full-history-scan pattern from the report.

### Finding Description
- `DelegateResourceActuator.calcFee()` returns `0` [1](#0-0) , and the only economic floor is `delegateBalance must be greater than or equal to 1 TRX` [2](#0-1) . Like the reported Beacon Kit bug (1 BERA minimum deposit, non-loss to attacker since stake still earns yield), the delegated TRX is not lost by the attacker — it remains frozen/staked and can later be undelegated, so the attacker can perform effectively unlimited delegate operations at near-zero real cost.
- Each `DelegateResourceContract` transaction creates fresh index entries via `delegatedResourceAccountIndexStore.delegateV2(...)`, which writes two new keys per delegation (`V2_FROM_PREFIX+owner+receiver` and `V2_TO_PREFIX+receiver+owner`) with no limit on the number of distinct receivers an owner can delegate to, and no automatic pruning of stale/expired entries [3](#0-2) .
- Reading the delegation index for an address requires a full LevelDB/RocksDB *prefix scan* over every entry ever written for that address, with no `limit`/pagination and no bound on result size, directly analogous to `GetDepositsByIndex(0, depositIndex+MaxDepositsPerBlock)` looping from the beginning of history every time: [4](#0-3) 
- This is exposed to any unprivileged/anonymous caller via public RPC/HTTP endpoints: `RpcApiService` (`GetDelegatedResourceAccountIndex`)  and `GetDelegatedResourceAccountIndexServlet` (HTTP JSON-RPC).
- The legacy (v1) model is worse: it stores the entire `toAccounts`/`fromAccounts` lists inside *one* protobuf capsule value, which is fully read, deserialized, mutated, and rewritten on every single delegate/undelegate/unfreeze operation for that address (`FreezeBalanceActuator.delegateResource`, `UnfreezeBalanceActuator`) — an O(n) read-modify-write on every additional delegation: [5](#0-4) 
This exact "unbounded list inside one value" defect is acknowledged by the codebase itself, which introduced `supportAllowDelegateOptimization()`/`delegateV2` to migrate away from it — but the migration only moves the cost from "on-write" (legacy model) to "on-read prefix scan" (V2 model); it does not bound or prune the number of entries.

### Impact Explanation
An attacker holding a modest amount of TRX can repeatedly call `DelegateResourceContract` with the 1-TRX minimum to a large number of distinct receiver addresses (they control both ends, so funds are never at risk and can be undelegated/unfrozen afterward). This inflates a single owner or receiver's delegation-index entry count without bound. Any subsequent read of that address's delegated-resource index (via public RPC/HTTP `GetDelegatedResourceAccountIndex`) forces the serving node to perform a full unbounded prefix scan, and — in the legacy (non-optimized) code path — every further delegate/undelegate/unfreeze transaction touching that address forces an O(n) read-modify-serialize-write of the entire growing list. This is a realistic vector for degrading a full node's RPC responsiveness or increasing per-transaction execution time for affected accounts, consistent with "DoS via RPC-API or protocol implementation" in the accepted-impact categories. It does not reach full chain halt like the Beacon Kit report (there is no equivalent of `PrepareProposal` looping over the whole growing set every block), so the blast radius is narrower — bounded to nodes answering that specific query/executing transactions against the spammed address(es), not global consensus.

### Likelihood Explanation
High feasibility: the operation is completely unprivileged (any funded account can broadcast `DelegateResourceContract`), inexpensive (1 TRX minimum, fee is 0, capital is not lost), and requires no special network conditions. The only real cost to the attacker is bandwidth-limit consumption for the many transactions themselves, which is far cheaper than the 460,800 BERA/day figure cited in the original report. However, unlike the original report, there is no automatic, unconditional "reconstruct entire history every block" trigger analogous to `PrepareProposal`; the heavy cost is realized only when the bloated index is subsequently *read* (RPC/HTTP call) or, in the legacy model, when further delegate/undelegate operations against that specific address occur. This makes the likelihood of *localized* RPC/API degradation high, but the likelihood of full chain-wide consensus halt low/unproven from the code alone.

### Recommendation
- Cap the number of distinct delegation-index entries (`toAccounts`/`fromAccounts`) that a single address may accumulate, or require the requester to page results with an explicit `limit`/cursor instead of full prefix scans in `getIndex`/`getV2Index`.
- Prune delegation-index entries once the underlying `DelegatedResourceCapsule` balance is fully withdrawn (already done in `unDelegate`/`unDelegateV2`, but not for the legacy list-based model, and not for “re-delegate spam” before withdrawal).
- Eliminate the legacy (`supportAllowDelegateOptimization() == false`) single-value list code path in `FreezeBalanceActuator`/`UnfreezeBalanceActuator`, since it performs unbounded read-modify-write on the entire per-address list for every delegate/undelegate transaction.
- Enforce a maximum distinct-receiver count per owner in `DelegateResourceActuator`/`DelegateResourceProcessor` validation, analogous to `UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES`, to bound the on-chain growth in the first place.

### Proof of Concept
1. Fund an attacker-controlled account with N TRX (N = desired spam factor), plus bandwidth/energy to broadcast transactions.
2. Loop N times: broadcast `DelegateResourceContract` from the owner address to a freshly generated receiver address with `balance = 1 TRX` (the contract minimum) and `resource = BANDWIDTH` or `ENERGY`. Each call succeeds at zero protocol fee (`calcFee() == 0`) and creates two new index entries (`delegateV2`) [6](#0-5) .
3. Query `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` for the owner address via public RPC or HTTP JSON-RPC; observe response time growing linearly (unbounded) with N due to the full prefix scan in `getWithPrefix` [7](#0-6) .
4. On a network still running the legacy (non-optimized) delegation model, repeat step 2 using `FreezeBalanceContract` with a `receiverAddress` set instead, and observe that each subsequent freeze/unfreeze against the same owner address performs a full read/deserialize/mutate/serialize/write of the growing `toAccountsList`/`fromAccountsList`, with cost growing linearly in N [5](#0-4) .

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
