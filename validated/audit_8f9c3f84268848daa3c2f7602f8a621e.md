### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, letting `replay-verify` accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-comparison routine used by `storage/db-tool/src/replay_on_archive.rs` to confirm that locally re-executed transactions match the signed, archived `TransactionInfo` from the ledger. It checks execution status, gas used, write-set hash, and event-root hash, but it never compares the state checkpoint hash / hot-state checkpoint hash / position-state checkpoint hash fields carried by `TransactionInfo` against the locally computed state roots. This gap is explicitly called out in a `TODO` comment inside the function itself.

### Finding Description [1](#0-0) 
`ensure_match_transaction_info` validates status, gas, write-set hash and event root hash against `TransactionInfo`, but the function ends without ever checking `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`: [2](#0-1) 
The comment literally documents the gap: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole verification oracle used by the replay-verify tool: [3](#0-2) 
`execute_and_verify` re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` against the `expected_txn_info` pulled from the signed backup/archive. Because the state checkpoint hash is never compared, a divergence between the locally-computed state root (which would be produced by `DoStateCheckpoint`/`StateCheckpointOutput`, see `state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, `position_state_checkpoint_hashes` in `execution/executor-types/src/state_checkpoint_output.rs`) and the state root that was actually accepted into the accumulator/ledger at that version would not be flagged as a verification failure.

The `state_checkpoint_hash` is precisely the field that gets folded into `TransactionInfo` and hashed into the transaction accumulator (`types/src/transaction/mod.rs` `TransactionInfo::builder_v0`/`builder_v1`, consumed by `DoLedgerUpdate::run` in `execution/executor/src/workflow/do_ledger_update.rs`), i.e., it is the actual state-commitment root for that transaction. Skipping it in the comparator means the one automated tool whose entire purpose is to catch state divergence between execution and the historical/authenticated ledger cannot detect a wrong state root — only wrong write-set/event/gas/status.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result … accepted as valid" and "hard-fork-only divergence during commit, replay … verification" integrity classes from the task's scope. `replay_on_archive` (the `db-tool replay-verify` command) is the concrete mechanism operators/auditors run against mainnet archives to detect execution/consensus bugs that produced an incorrect state root (the canonical way such bugs are caught before or after a network incident). Because the checkpoint-hash fields are never checked, a scenario in which the VM produces a correct write set and events but an incorrect state root (e.g., a subtly wrong state-checkpoint/hot-state/position-state computation bug) would pass `ensure_match_transaction_info` and be reported as a "successful replay," masking the true divergence. This directly undermines confidence in the replay/audit invariant that authenticated state roots must match local re-execution, and could delay or prevent detection of a state-corrupting bug that needs a hard fork to fix.

### Likelihood Explanation
The gap is unconditional whenever `ensure_match_transaction_info` is invoked (currently the only caller path exercising is `replay_on_archive.rs`); it does not depend on any feature flag — the TODO/feature reference (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is about a *different*, not-yet-enabled improvement, not a gate that currently protects this check. Today, `ensure_match_transaction_info` simply never validates any checkpoint hash for any transaction, on any config. Triggering the actual "wrong state root" bug that this omission would fail to catch requires a separate underlying divergence (e.g., in the VM, state-checkpoint hashing, or hot/position state modules), so the severity here is that this is a missing safety net for detecting that class of bug, not itself a way to corrupt state. That nuance should be weighed against a strict "High/Critical" bar, since exploitation requires a *pre-existing* state-computation bug to actually go undetected.

### Recommendation
Extend `ensure_match_transaction_info` to also assert that:
- `self`'s computed state checkpoint hash (when available in the calling context, e.g., via `StateCheckpointOutput`) matches `txn_info.state_checkpoint_hash()`,
- the hot-state checkpoint hash matches `txn_info.hot_state_checkpoint_hash()` (for `TransactionInfoV1`), and
- the position-state checkpoint hash matches `txn_info.position_state_checkpoint_hash()` (for `TransactionInfoV1`),
before allowing `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-driven checks to be relied upon by `replay_on_archive`, and ideally regardless of that flag so `db-tool`'s replay-verify can catch any state-root divergence today, not just write-set/event/gas/status divergence. Since `TransactionOutput` itself doesn't carry the checkpoint hash, this likely requires threading the locally-computed checkpoint hash (from `StateCheckpointOutput`) into the verification call site in `replay_on_archive.rs`/`execute_and_verify`.

### Proof of Concept
Conceptual PoC (no working exploit code, since triggering requires an independent state-root-computation bug):
1. Assume a hypothetical (or intentionally injected in a test) bug where the VM/state-checkpoint pipeline computes a correct write set and events for a transaction but an incorrect state summary/state root (e.g., a stale/incorrectly-updated Merkle summary).
2. Run `db-tool replay-verify` (`replay_on_archive.rs`) over the affected version range, pointed at the archived backup containing the correct/authenticated `TransactionInfo`.
3. `execute_and_verify` re-executes the transaction and calls `ensure_match_transaction_info(version, &expected_txn_info, Some(&expected_writeset), Some(&expected_events))`.
4. Because status/gas/write-set-hash/event-root-hash all still match, `ensure_match_transaction_info` returns `Ok(())` even though the state checkpoint hash recorded in `expected_txn_info` (and thus in the ledger's transaction accumulator) does not match what would have been computed from local execution — the mismatch is silently ignored per the code's own TODO comment at [4](#0-3) .
5. `replay-verify` reports zero failed transactions for this range, giving operators false assurance that historical execution is fully consistent with the signed ledger, when in fact the state root diverges.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
