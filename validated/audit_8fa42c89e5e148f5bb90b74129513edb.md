Based on my investigation, I found a genuine index-integrity divergence in the Move framework's validator-set refresh logic, though I was unable to fully trace the consensus-side consumption of `validator_index` before running out of tool budget — I flag that uncertainty explicitly below.

### Title
Validator index gaps in `refresh_validator_set_in_place` desynchronize `ValidatorConfig.validator_index` from `ValidatorPerformance` positions — (File: `aptos-move/framework/aptos-framework/sources/stake.move`)

### Summary
`refresh_validator_set_in_place` (the "sync"/non-DKG path of `on_new_epoch`) filters out validators that fall below `minimum_stake` by simply skipping them when building `next_epoch_validators`, without reassigning `config.validator_index` to the validator's new contiguous position [1](#0-0) . This contrasts with the parallel DKG-precompute path `next_validator_consensus_infos_v2`/`compute_simulated_validator_info`, which explicitly re-stamps `config.validator_index = validator_index` for every accepted candidate and even carries an explicit prover invariant that the final vector must satisfy `new_active_validators[i].config.validator_index == i` [2](#0-1) [3](#0-2) .

### Finding Description
When `on_new_epoch` takes the synchronous path (no `PrecomputedValidatorSet` cached), it calls `refresh_validator_set_in_place`, which iterates over the previous epoch's active validators and only pushes a validator into `next_epoch_validators` if its recomputed voting power is `>= minimum_stake` [4](#0-3) . The `ValidatorInfo`/`ValidatorConfig` pushed is built via `generate_validator_info`, which copies the validator's *existing* `ValidatorConfig.validator_index` unchanged [5](#0-4) . If any validator earlier in the list is excluded for insufficient stake, every subsequent surviving validator keeps its old, now-non-contiguous `validator_index` (e.g. 0,1,3,4 instead of 0,1,2,3), because the function never re-numbers the indices of the accepted subset.

Immediately afterward, `on_new_epoch` rebuilds `ValidatorPerformance.validators` by pushing one fresh `IndividualValidatorPerformance` entry per surviving validator, in vector *position* order [6](#0-5) . Proposal accounting (`update_performance_statistics`) later indexes into this vector using `proposer_index`/`failed_proposer_indices` supplied from consensus, which are the validators' `validator_index` values as recorded in the on-chain `ValidatorConsensusInfo`/`ValidatorConfig` for the epoch [7](#0-6) . Once these two numbering schemes diverge (position vs. stored `validator_index`), a proposer's successful/failed proposal counters get attributed to the wrong slot in `ValidatorPerformance.validators`, which directly feeds `calculate_rewards_amount` during the next `update_stake_pool` reward computation.

The DKG path's explicit re-stamping and prover-enforced invariant (`new_active_validators[i].config.validator_index == i`) shows the codebase's own expectation that the resulting active-validator vector must always have contiguous, position-matching indices — an invariant `refresh_validator_set_in_place`'s primary filtering branch does not uphold.

### Impact Explanation
If this divergence is triggered, reward minting (`update_stake_pool` → `distribute_rewards` → `calculate_rewards_amount`) attributes successful/failed proposal statistics — and therefore minted `AptosCoin` rewards — to the wrong validator's stake pool. That is committed, durable ledger state (stake pool balances, hence account/coin state and total supply distribution) diverging from the economically correct result implied by actual consensus participation, which fits the "committed state differs from correct VM result" gate. It could also desynchronize `PendingTransactionFee.pending_fee_by_validator`, keyed by `v.config.validator_index` [8](#0-7) , causing transaction-fee aggregators to be attached to the wrong validator.

### Likelihood Explanation
I could not confirm within the available budget whether the synchronous (`refresh_validator_set_in_place`) path is actually reachable on a live mainnet-configured chain, versus always being superseded by the DKG/async precompute path in current production configuration, nor could I trace the exact site in consensus/safety-rules code that binds a proposer's on-wire index to `ValidatorConfig.validator_index` to conclusively confirm the position-vs-index mismatch manifests as mis-attribution rather than being caught/rejected. This limits my confidence that the divergence is exploitable end-to-end on mainnet today, even though the code-level invariant violation (missing index reassignment in the filtering branch) is real and locally verifiable.

### Recommendation
In `refresh_validator_set_in_place`'s primary (non-fallback) branch, reassign `validator_config.validator_index` to the position in `next_epoch_validators` at push time (mirroring what `compute_simulated_validator_info` already does), and add/enforce the same invariant (`new_active_validators[i].config.validator_index == i`) that is already specified for the DKG path.

### Proof of Concept
Conceptual trace (not independently executed, due to tool-call exhaustion):
1. Validator set has 3 active validators with `validator_index` 0, 1, 2, and `ValidatorPerformance.validators` also has 3 entries at positions 0, 1, 2.
2. During an epoch without DKG caching, validator at index 1 drops below `minimum_stake` (e.g., due to unlocks). `refresh_validator_set_in_place` skips it, producing `next_epoch_validators = [validator0 (idx 0), validator2 (idx 2)]` — index 2 is now out of range for a 2-length performance vector once rebuilt.
3. `validator_perf.validators` is rebuilt with only 2 entries (positions 0 and 1) for the 2 surviving validators, per [6](#0-5) .
4. Consensus, still using `validator_index = 2` for the second validator (as recorded in the committed `ValidatorConfig`/`ValidatorSet`), reports proposals with `proposer_index = 2`.
5. `update_performance_statistics` at [9](#0-8)  checks only `cur_proposer_index < validator_len` (here `2 < 2` is false), so the update is silently dropped rather than attributed correctly — the surviving validator's real proposal never counts toward its rewards, an incorrect committed performance/reward state for that epoch.

Given the incomplete verification of reachability and downstream consumption, I present this with the noted caveats rather than full certainty.
