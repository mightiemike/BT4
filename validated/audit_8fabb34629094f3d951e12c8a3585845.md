### Title
Unchecked division result in `MarketSellAssetActuator.matchSingleOrder` "taker == maker" branch allows a maker to lose their entire remaining sell quantity for zero payment - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator` implements TRON's on-chain order-book market (`MarketSellAssetContract`, reachable from any broadcast transaction). When a taker order exactly consumes a maker order's remaining sell quantity, the actuator computes the payment the maker should receive with an integer division (`MarketUtils.multiplyAndDivide`) and, unlike the sibling "taker > maker" branch, never checks whether this computed amount is zero before finalizing the match. This mirrors the reported `AaveUtils._tokenSwapOutAmount` bug class: an unchecked, integer-division-derived output amount can legitimately be `0`, and the code proceeds to settle the trade anyway (100% "slippage").

### Finding Description
In `matchSingleOrder`, three branches handle the relative size of `takerBuyTokenQuantityRemain` vs. `makerOrderCapsule.getSellTokenQuantityRemain()`:

- **taker == maker branch** (no zero-check): [1](#0-0) 

- **taker > maker branch** (has an explicit zero-check and special-cased "return sell token to maker" handling): [2](#0-1) 

In the "taker == maker" branch, `makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` — the same integer-division formula used in the "taker > maker" branch, which the code's own comment acknowledges can legitimately evaluate to `0` for small remainders. However, in this branch the result is used unconditionally:
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` — the maker's order is fully closed, i.e., the maker gives up its *entire* remaining sell-token balance.
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive` — if `makerBuyTokenQuantityReceive == 0`, the taker's remaining balance is left untouched, meaning the taker pays nothing for the tokens it receives.
- `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` at line 490 then credits the maker with `0` tokens.

No `minOut`/`expected` parameter analogous to `ExchangeTransactionContract.expected` exists for `MarketSellAssetContract` orders, and there is no fallback path (like `returnSellTokenRemain`) for this specific branch when the computed amount is zero.

### Impact Explanation
If exploitable, this results in direct asset-accounting corruption on-chain: a maker order can be fully consumed (its remaining sell-token quantity zeroed and removed from the order book) while the maker receives `0` of its buy token, and the taker receives the maker's full remaining sell-token quantity while its own balance debit (`takerSellTokenLeft`) is unaffected. This is a real value transfer with no consideration — the taker effectively receives free tokens and the maker suffers a complete loss on the unmatched fragment, achievable by any account broadcasting `MarketSellAssetContract` transactions (an anonymous, unprivileged operation).

### Likelihood Explanation
Likelihood depends on how easily `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity == 0` can be forced to coincide with `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`. Since order quantities and prices are fully attacker-controlled inputs (`sellTokenQuantity`, `buyTokenQuantity` on `MarketSellAssetContract`, validated only for `> 0`), an attacker can craft a maker order with a very small remaining sell quantity relative to its buy quantity (so the division rounds to zero) and then place a matching taker order sized to exactly equal that remaining quantity, deterministically triggering the branch. This looks readily reproducible rather than probabilistic, though full confirmation would require running the actual on-chain matching logic end-to-end (order-book state transitions, price-key ordering, and `MarketUtils.multiplyAndDivide`'s exact division mode) which I could not fully execute here.

### Recommendation
In the "taker == maker" branch of `matchSingleOrder`, add the same zero-check used in the "taker > maker" branch: if `makerBuyTokenQuantityReceive == 0`, do not close out the maker's order for zero consideration — either reject/skip the match, or return the maker's remaining sell-token quantity via `MarketUtils.returnSellTokenRemain` instead of zeroing it out and crediting `0` tokens. More broadly, add an invariant check ensuring the computed settlement amount for either counterparty is never zero when its counterparty's balance is fully debited.

### Proof of Concept
Not independently executed against a running node; the trigger condition is derived purely from static analysis of the arithmetic:
1. Attacker (or colluding accounts) creates a maker sell order with `sellTokenQuantity`/`buyTokenQuantity` chosen such that, once partially filled, the remaining `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity` rounds down to `0` (e.g., `makerSellRemainQuantity` small and `makerBuyQuantity < makerSellQuantity`).
2. A taker order is placed with `sellTokenQuantityRemain` exactly equal to the maker's `sellTokenQuantityRemain`, forcing the `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch in [1](#0-0) .
3. The maker order is closed (`setSellTokenQuantityRemain(0)`), the taker receives the maker's full remaining sell tokens, and `addTrxOrToken(makerOrderCapsule, 0)` credits the maker nothing, while `takerSellTokenLeft` is unchanged — the taker paid nothing for the tokens received.
