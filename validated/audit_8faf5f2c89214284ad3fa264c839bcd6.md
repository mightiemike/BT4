### Title
Stale cached vault liquidity index used after `socialize-debt` bypasses the cache - (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`market.clar`'s `accrue-and-cache` memoizes each vault's `index`/`lindex` for the duration of a Stacks block, keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . `socialize-debt`, however, writes a new `lindex` directly to vault storage without going through the normal `accrue()` path and without touching the market's cache [2](#0-1) . Any market-side computation that already read/cached the pre-write-down `lindex` earlier in the same block continues to use the stale, higher value for pricing zToken collateral for the rest of that block, even though the real on-chain `lindex` has just been marked down.

### Finding Description
`accrue-and-cache` is a per-block cache: on a cache miss it calls `vault-accrue` and stores `{index, lindex}` under `{timestamp: stacks-block-time, aid}`; on a hit it returns the stored value without re-checking the vault [1](#0-0) . This cache is consumed both for user debt/collateral accrual [3](#0-2)  and for ztoken price resolution, per the protocol's own documentation of this caching layer [4](#0-3) .

`socialize-debt` is the mechanism that writes off bad debt: it computes a new `lindex` proportional to the loss in `total-assets` and stores it via `var-set lindex new-lindex` directly on the vault, bypassing `accrue()`'s normal time-based index recomputation entirely [2](#0-1) . It is routed through the market via `vault-socialize-debt` [5](#0-4) , but nothing in that call path invalidates or updates `index-cache` for the affected `aid`.

The value bound is `index-cache { timestamp, aid } -> { index, lindex }`; the event that invalidates its source is `socialize-debt`'s direct `var-set lindex`; the later use is any subsequent `accrue-and-cache` cache hit for the same `aid` within the same block/timestamp (e.g., in the collateral-pricing path used for health checks or notional valuation, as seen in the collateral capacity check flow) [6](#0-5) . Because Clarity evaluates block time as constant across all transactions in a block, and the cache key includes only `stacks-block-time` (not a monotonically-incrementing version or nonce), a cache entry written before `socialize-debt` runs remains a hit for the remainder of the block, returning the pre-write-down `lindex`.

### Impact Explanation
A stale, inflated `lindex` overstates the redemption value of any zToken collateral priced against it, since ztoken/vault-share value is `shares * lindex`. If this stale value is reused later in the same transaction/block flow (e.g., for a follow-up collateral valuation or capacity check on the same or another position tied to the same underlying vault) it allows the protocol to treat collateral as worth more than it actually is after the loss has been socialized, letting positions escape a health check or letting a user extract/borrow value the vault can no longer back. This lands on protocol insolvency / theft of funds at rest via mispriced collateral, a Critical-tier impact.

### Likelihood Explanation
This requires: (1) a `socialize-debt` event on a vault (triggered when a liquidation leaves bad debt) to occur, and (2) an `accrue-and-cache` read for the same `aid` to have already populated the cache earlier in the same block. Since `stacks-block-time` is shared by all transactions in a block, and the market performs `accrue-and-cache` reads for collateral valuation on essentially every borrow/collateral-add/health-check operation, the pre-condition for a stale cache read is realistic whenever socialization happens mid-block after other market activity on the same asset.

### Recommendation
Invalidate or overwrite `index-cache` for the affected `aid` at the same `stacks-block-time` key whenever `socialize-debt` (or any other function that mutates `index`/`lindex` outside the standard `accrue()` flow) runs, so subsequent cache reads in the same block reflect the post-write-down state.

### Proof of Concept
Not independently verified end-to-end: I confirmed the caching mechanism (`accrue-and-cache` / `index-cache`) and the bypassing mutation (`socialize-debt`'s direct `var-set lindex`), but was unable to trace the exact call ordering inside the market's liquidation entry point (i.e., whether a single liquidation transaction both primes the cache for an asset and then triggers `socialize-debt` on that same asset before reusing the cached value) before running out of tool iterations. This ordering is necessary to confirm a single-transaction (rather than cross-transaction/cross-user) exploit path, so this should be treated as a plausible analog requiring confirmation of the liquidation function's internal sequencing.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

## Index Caching

The market maintains a timestamp-based cache for vault liquidity indexes to optimize ztoken price resolution:

```clarity
;; In market.clar
(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache- cache-key)))
    (match cached?
      existing existing
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
```

**Purpose:** 
- Multiple price resolutions for the same vault within a single block use cached indexes
- Avoids redundant cross-contract calls to vaults
- Significantly reduces gas costs for transactions involving multiple ztoken prices

**Cache Invalidation:** Cache is timestamp-based using `stacks-block-time`, automatically invalidating when a new block is processed.
```
