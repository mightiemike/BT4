### Title
`ValidateMultiSign` precompile double-counts signer weight via ECDSA signature malleability, bypassing multisig threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign.execute()` deduplicates submitted signatures by concatenating `recoveredAddr + rawSignatureBytes` rather than deduplicating by `recoveredAddr` alone. Because ECDSA signatures are malleable (a signature `(r, s, v)` and its counterpart `(r, n-s, 1-v)` both recover to the same address but have different raw bytes), an attacker can submit two distinct byte-encodings of a signature from a single key and have that key's weight counted twice toward `permission.getThreshold()`.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()` (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1088-1106`): [1](#0-0)

The dedup check only `continue`s (skips weight accumulation) when the *exact same* `recoveredAddr+rawSignatureBytes` pair reappears. If the same `recoveredAddr` reappears with **different raw signature bytes** — which is trivially producible by flipping the malleable `s` value/recovery id of a single ECDSA signature — the code falls through the inner `if`, calls `MUtil.checkCPUTime()` (a CPU-time throttle, not a rejection), and then re-adds `TransactionCapsule.getWeight(permission, recoveredAddr)` to `totalWeight` a second time for the same underlying key. This is a genuine logic bug distinct from (and weaker than) the address-based dedup that the `checkWeight` path (used by `TransactionCapsule`/`GetTransactionSignWeightServlet`) is expected to perform on recovered addresses.

Exploit flow:
1. Attacker deploys/uses a smart contract that calls the `validatemultisign` precompile with the address/`permissionId` of a target account (any account, not necessarily one fully controlled by the attacker) whose `Permission` has threshold `2*W` and includes a key the attacker holds with weight `W`.
2. Attacker signs `hash` once with their key, then derives the second malleable encoding of the same signature (`s' = n - s`, flipped recovery bit) — both recover to the same address.
3. Both signatures are passed to the precompile call. The dedup check based on `recoveredAddr+sign` fails to catch the duplicate key because the raw signature bytes differ, so `totalWeight` accumulates `W + W = 2W`, reaching `permission.getThreshold()`.
4. `execute()` returns `dataOne()` (success) even though only one real key authorized the action.

Any TVM contract (e.g., a custom multisig wallet or approval-gated vault) that relies on this precompile's boolean result to gate movement of TRX/TRC-20 funds can be tricked into believing sufficient distinct-signer weight was reached when only one signer actually participated, violating the exact-authorization guarantee of the account's `Permission`/threshold model set via `AccountPermissionUpdateActuator`.

### Impact Explanation
This breaks the on-chain multisig authorization invariant at the TVM precompile layer: a party holding less than the required weight of keys for an account's active/witness permission can make `validatemultisign` falsely report success by supplying malleable duplicates of one signature. Any contract logic built on top of this precompile (custodial multisig wallets, cross-chain bridges, DAO treasuries) that trusts its output to authorize a transfer can have funds moved/drained by a party who does not hold the required distinct-key weight — this maps to the "unauthorized account operation / asset drain via authorization bypass" bounty impact class.

### Likelihood Explanation
- No privileged role required: any account can deploy a contract and call the precompile with attacker-chosen `data`.
- Cost is only the deploy/call TVM energy fee (`ENGERYPERSIGN * signatureCount`), no economic barrier beyond normal gas.
- Producing the second malleable signature is a pure, deterministic elliptic-curve arithmetic operation (`s' = n - s`), requiring no additional secret material or brute force.
- Repeatable for any account/permission combination where the attacker legitimately controls at least one weighted key but less than the full threshold.
- The bug is purely a code-path deficiency in `ValidateMultiSign`; there is no fork gate, canonical low-S signature check, or address-only dedup guarding it in the shown code.

### Recommendation
Change the dedup logic in `ValidateMultiSign.execute()` to key exclusively on `recoveredAddr` (not `recoveredAddr+rawSignature`), mirroring the address-based dedup used by `TransactionCapsule`'s weight-checking path, so that any second signature recovering to an address already counted is always skipped regardless of its raw byte encoding. Additionally, enforce canonical low-S signature form during ECDSA recovery/validation to eliminate malleable duplicate encodings before they reach the weight-accumulation loop.
