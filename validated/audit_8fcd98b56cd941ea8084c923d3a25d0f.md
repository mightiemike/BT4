## Analysis

CVE-2015-2689 describes Tor crashing via an `assert()` failure when pending-connection resolve state bookkeeping is violated under crafted/heavy load. The analogous bug class here is a *reachable Rust `assert_eq!` inside sequencer transaction-admission bookkeeping* that can be violated by an ordinary transaction sender, crashing the mempool/batcher process.

### Title
Reachable assertion failure in `MempoolState::stage` crashes the mempool/batcher when a single account's transactions are staged out of nonce order - (File: `crates/apollo_mempool/src/mempool.rs`)

### Summary
`MempoolState::stage`, invoked from `Mempool::get_txs`, asserts that a newly staged nonce for an address is exactly one more than the previously staged nonce for that same address within the same `get_txs` call: [1](#0-0) 

`get_txs` pops a chunk of `TransactionReference`s from the transaction queue and stages every one of them sequentially, without verifying that multiple entries for the same address in that chunk are nonce-sequential: [2](#0-1) 

In FIFO/Echonet queue mode, all of an account's transactions are inserted into the queue "regardless of nonce," explicitly to preserve source-chain ordering rather than nonce ordering: [3](#0-2) 

If a single account has two (or more) queued transactions whose nonces are not consecutive when they land in the same popped chunk, the second `stage()` call computes a mismatched `next_nonce` against the already-staged nonce, and the `assert_eq!` panics.

### Finding Description
`stage()` maintains a `staged: AddressToNonce` map used to represent "which nonce would be next for this address if the currently-returned batch were committed." Its invariant assumes that when an address appears more than once among the transactions staged in a single `get_txs()` call, the nonces are strictly consecutive (`existing_nonce + 1 == next_nonce - 1`, i.e., back-to-back).

That invariant is guaranteed in fee-priority mode by `enqueue_next_eligible_txs`/`insert_to_tx_queue`, which only enqueue the next eligible (matching-account-nonce) transaction per address (see `add_tx_inner`, lines 605-616: fee mode branch only inserts a tx whose nonce equals current account nonce, and clears any prior queued reference for the address first). However, in FIFO/Echonet mode, the comment at `mempool.rs:605-608` states explicitly that **all** transactions for an address are inserted into the queue "regardless of nonce," to preserve source-chain (L1/L2 replay) ordering. This means the FIFO queue can legitimately contain multiple entries for one address with non-sequential nonces (e.g., nonce 3 and nonce 7, if both were forwarded/scraped and neither has been pruned).

`pop_ready_chunk` (FIFO queue) returns transactions strictly in arrival/timestamp order, not grouped or sorted by nonce, and `get_txs` iterates the whole popped chunk (`eligible_tx_references`) calling `self.state.stage(tx_reference)` for every entry, in queue order, with no gap check between consecutive entries for the same address. If two transactions for the same address end up in the same chunk with non-adjacent nonces, the second `stage()` call violates the assertion and panics the whole process.

Because `get_txs` is invoked by the batcher during proposal/validation of every block, and mempool ingestion (`add_tx`) is reachable from any unprivileged transaction sender or L1 message sender whose transactions get routed into the FIFO/Echonet mempool, an attacker only needs to get two non-sequential-nonce transactions from the same account queued and popped together.

### Impact Explanation
A successful trigger panics the mempool component inside the batcher process. Because `get_txs()` is called on the hot path of block-building/validation, this is a crash-inducing denial of service: the node running the affected mempool aborts, and if this can be reproduced deterministically (e.g., replicated by re-submitting the same tx sequence to other sequencer replicas), it can stall the network's ability to confirm new transactions — consistent with the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Reaching this requires: (a) the deployment to run the mempool in FIFO/Echonet mode (the mode explicitly designed to accept out-of-nonce-order transactions per-address), and (b) an account having ≥2 pooled, queued transactions with non-consecutive nonces that end up co-located within one `pop_ready_chunk` result. Both conditions are plausible for an ordinary account under normal usage patterns of Echonet-style sequencing (e.g., L1-message/L3 replay scenarios where multiple nonces for one contract legitimately queue up while earlier ones are still pending), making this a realistically triggerable — not purely theoretical — panic path, though it depends on the FIFO mode being enabled in the target deployment (this dependency could not be fully confirmed against production config within the available search budget).

### Recommendation
In `Mempool::get_txs`, before calling `self.state.stage(tx_reference)`, validate that, for any address appearing more than once in `eligible_tx_references`, the nonces form a consecutive, strictly increasing sequence, and return a `MempoolError` (rather than staging) if the invariant is not met, mirroring how fee-priority mode already enforces it by construction. Alternatively, harden `MempoolState::stage` to convert the invariant violation into a recoverable `MempoolError` instead of `assert_eq!`, so that a violated invariant degrades gracefully (drop/reject the offending tx) rather than terminating the process.

### Proof of Concept
1. Deploy/configure the sequencer's mempool in FIFO/Echonet mode (`BehaviorMode::Echonet`), as used for L1-message/L3 sequencing (`static_config.behavior_mode`).
2. As a normal transaction submitter/L1 message sender, submit two transactions for the same account address with non-consecutive nonces (e.g., nonce 3 and nonce 7), both of which pass validation and are added via `add_tx`. Per the FIFO branch of `add_tx_inner` (`mempool.rs:605-608`), both get inserted into the FIFO queue "regardless of nonce."
3. Arrange timing/metadata (`update_tx_block_metadata`) so both transactions become eligible in the same `pop_ready_chunk(n_remaining_txs)` result during a subsequent `get_txs()` call (e.g., request a chunk size ≥ 2 while both txs are at the front of the FIFO queue for the same expected timestamp/block).
4. `get_txs` iterates `eligible_tx_references` and calls `self.state.stage()` for each: staging nonce 3 sets `staged[addr] = 4`; staging nonce 7 computes `next_nonce = 8` and hits `assert_eq!(try_increment_nonce(4), 8, "Staged nonce should be an increment of an existing nonce.")`, which fails and panics the batcher/mempool process (`crates/apollo_mempool/src/mempool.rs:119-127`).
