### Title
User can permanently burn their own gas-key NEAR balance by deleting an access key before withdrawing it - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
The Illuminate bug describes a `redeem` function that irreversibly burns a user's tokens when called out of the intended order, with no way to recover the destroyed value. The nearcore analog is `action_delete_key` / `delete_gas_key` in [1](#0-0) , which is reachable from a single signed `DeleteKey` transaction/action issued by the account owner (an unprivileged transaction signer).

### Finding Description
When a `DeleteKey` action targets a gas key, `action_delete_key` dispatches to `delete_gas_key`: [2](#0-1) 

If `gas_key_info.balance` is at or below `GasKeyInfo::MAX_BALANCE_TO_BURN`, the function unconditionally adds the *entire remaining gas-key balance* to `result.tokens_burnt` — i.e., it is permanently destroyed (removed from total supply) rather than refunded to the account — and only then removes the key. There is no check for whether the user intended to withdraw funds first, no confirmation step, and no atomic combination with a withdrawal.

The protocol does provide a dedicated action, `action_withdraw_from_gas_key`, whose correct job is to move gas-key balance back to the account balance safely: [3](#0-2) 

This mirrors the Illuminate bug exactly: there are two logically-ordered operations (withdraw funds, then delete/close), and calling the "closing" operation (`DeleteKey`) without first calling the "extraction" operation (`WithdrawFromGasKey`) silently and irreversibly destroys the user's funds instead of erroring out or auto-refunding. A user (or a wallet/relayer building a `DeleteKey` transaction, or a `DelegateAction`/meta-transaction sender acting on their behalf) who forgets, races, or mis-sequences a withdrawal before deleting the key will have that balance burned with no recourse — exactly analogous to calling the iPT-burning `redeem` before the external-PT `redeem`.

The same unconditional-burn pattern also occurs in `action_delete_account`, which sums and burns all gas-key balances on the account during deletion: [4](#0-3) 

### Impact Explanation
Funds up to `GasKeyInfo::MAX_BALANCE_TO_BURN` (documented as "≤ 1 NEAR" per the protocol spec) held on a gas key are permanently and irreversibly removed from the user's control and from total supply the moment a `DeleteKey` (or `DeleteAccount`) action executes, with no on-chain warning, revert, or refund path. This is a genuine "permanently frozen/destroyed funds" outcome triggered by a single, ordinary, unprivileged transaction — the exact impact class described in the Illuminate report (accidental, unrecoverable burn of user value due to action-ordering).

### Likelihood Explanation
Likelihood is bounded by protocol design: the burn is capped at `GasKeyInfo::MAX_BALANCE_TO_BURN` specifically to limit worst-case loss, and above that cap the action fails with `GasKeyBalanceTooHigh` rather than proceeding (`runtime/runtime/src/access_keys.rs:103-111`). This cap strongly suggests the nearcore team already identified and consciously bounded this exact risk (a deliberate design tradeoff, not an oversight), which lowers confidence that this rises to the level of an unintended vulnerability versus a known, accepted design limitation — similar to how the Sherlock judges ultimately treated the original finding as input-validation/out-of-scope rather than a critical bug.

### Recommendation
Consider one of: (1) requiring `gas_key_info.balance == 0` before allowing `DeleteKey`/`DeleteAccount` to proceed on a gas key, returning an actionable error otherwise (mirroring the Illuminate recommendation to disallow the "burning" call before the "extraction" call has run); or (2) auto-generating a refund receipt for the remaining gas-key balance to the owning account instead of burning it, subject to the same `MAX_BALANCE_TO_BURN` bound for DoS/complexity reasons.

### Proof of Concept
1. Account `A` adds a gas key via `AddKey` with `AccessKeyPermission::GasKey`.
2. `A` funds the key via `TransferToGasKey` with e.g. `0.5 NEAR` (`action_transfer_to_gas_key`, `runtime/runtime/src/access_keys.rs:257-288`).
3. Instead of calling `WithdrawFromGasKey` first, `A` (or a relayer executing a `DelegateAction` on `A`'s behalf) submits a `DeleteKey` action for that public key.
4. `action_delete_key` → `delete_gas_key` runs; since `0.5 NEAR ≤ MAX_BALANCE_TO_BURN`, the full `0.5 NEAR` is added to `result.tokens_burnt` and the key (and its balance) is deleted with no receipt back to `A` (`runtime/runtime/src/access_keys.rs:112-126`).
5. `A`'s `0.5 NEAR` is permanently gone from total supply; no error, no revert, no refund receipt was produced, matching the "accidental burn with no recourse" impact of the original report.

fn delete_gas_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
) -> Result<(), RuntimeError> {
    if gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: Some(Box::new(public_key.clone())),
            balance: gas_key_info.balance,
        }
        .into());
        return Ok(());
    }
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_info.balance).ok_or(IntegerOverflowError)?;
    let num_nonces = gas_key_info.num_nonces as usize;
    for i in 0..gas_key_info.num_nonces {
        remove_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i);
    }
    let nonce_key_len = gas_key_nonce_key_len(account_id, &public_key.into());
    let nonce_remove_compute = storage_removes_compute(
        &config.wasm_config.ext_costs,
        num_nonces,
        nonce_key_len * num_nonces,
        AccessKey::NONCE_VALUE_LEN * num_nonces,
    );
    result.compute_usage = safe_add_compute(result.compute_usage, nonce_remove_compute)?;
    remove_access_key(state_update, account_id.clone(), public_key.clone());
    account.set_storage_usage(account.storage_usage().saturating_sub(gas_key_storage_cost(
        &config.fees,
        public_key,
        access_key,
        gas_key_info.num_nonces,
    )));
    Ok(())
}
