### Title
`accept_new_txs` pause flag is enforced only at the HTTP server, not at the Gateway itself — P2P-propagated transactions bypass it - (File: crates/apollo_http_server/src/http_server.rs)

### Summary
This mirrors the Aave-Lens finding: a governance-style "pause switch" (`whenNotPaused`) is applied to most external entry points but is missing from one reachable entry point (ERC721 `_beforeTokenTransfer`), letting an operation continue even while the system is meant to be halted. In the sequencer, the analogous pause switch is the `accept_new_txs` dynamic-config flag, and the analogous unprotected entry point is the Gateway's direct `add_tx` path used for P2P-propagated transactions.

### Finding Description
The HTTP server enforces a governance-controlled kill switch, `accept_new_txs`, before admitting a transaction: [1](#0-0) 
Both REST and RPC HTTP endpoints call `check_new_transactions_are_allowed(accept_new_txs)` before forwarding to the Gateway.

However, transactions can also enter the Gateway through a completely separate path that does not go through the HTTP server at all: the `MempoolP2pRunner`, which receives transaction batches broadcast by peers and calls the Gateway client's `add_tx` directly: [2](#0-1) 

The Gateway's own `add_tx`/`add_tx_inner` implementation performs stateless/stateful validation, declare-specific permission checks (`check_declare_permissions`, `block_declare`), and compilation-concurrency limits — but at no point checks `accept_new_txs` or any equivalent flag: [3](#0-2) 

Since `accept_new_txs` lives only in `HttpServerDynamicConfig` and is checked only in the two HTTP handlers (`add_rpc_tx`, `add_tx`), it has no effect on transactions arriving via the P2P `MempoolP2pRunner → GatewayClient.add_tx` path. As documented in the tx-submission flow diagram, "Sequencer B" receives P2P-broadcast batches and forwards them straight into its Gateway with "Same validation flow" — but that "same validation flow" does not include the pause check, because the check lives outside the Gateway, in the HTTP server layer.

### Impact Explanation
When operators use `accept_new_txs=false` to halt admission of new transactions (e.g., during an incident, chain halt, or coordinated maintenance), any node still connected to the P2P mempool network continues to admit and gossip transactions received from peers, and continues to forward them into its local mempool/batcher pipeline. This defeats the purpose of the pause: a node operator (or an attacker/peer who can reach the P2P broadcast topic) can still get transactions accepted and included in blocks on nodes whose local HTTP ingestion is paused, exactly analogous to how pausing the Aave-Lens `LensHub` didn't stop profile-NFT transfers because the transfer path bypassed the `whenNotPaused` check. This can result in the network being unable to reliably halt new transaction admission during an incident — a liveness/control-plane guarantee failure with potential for continued fee draining, unwanted state changes, or interference with incident response across the network.

### Likelihood Explanation
This requires no special privilege beyond normal participation in the P2P network: any peer submitting transactions that get gossiped will have them delivered straight to the Gateway of any receiving node, regardless of that node's `accept_new_txs` setting. The path is exercised in normal operation (not a rare edge case) whenever P2P mempool propagation is enabled, which is the default multi-node topology.

### Recommendation
Move the `accept_new_txs` (or an equivalent) check into the Gateway's `add_tx`/`add_tx_inner` itself (or into a shared pre-check invoked by both the HTTP handlers and the `MempoolP2pRunner` before calling `GatewayClient::add_tx`), so that the pause flag is enforced uniformly regardless of transaction origin (HTTP or P2P).

### Proof of Concept
1. Configure `accept_new_txs = false` in the HTTP server dynamic config on Node A; verify `POST /gateway/add_transaction` and `/gateway/add_rpc_transaction` are rejected via `check_new_transactions_are_allowed`. [1](#0-0) 
2. From a peer Node B, broadcast a valid transaction over the mempool P2P topic.
3. Observe that Node A's `MempoolP2pRunner` receives the batch and calls `gateway_client.add_tx(...)` directly, with no `accept_new_txs` gate anywhere in that call chain. [2](#0-1) [3](#0-2) 
4. Confirm the transaction is admitted to Node A's mempool despite `accept_new_txs = false`, demonstrating that the pause is bypassable via the P2P ingestion path.

async fn add_rpc_tx(

    debug!("ADD_TX_START: Http server received a new transaction.");

    check_new_transactions_are_allowed(accept_new_txs)?;

    ADDED_TRANSACTIONS_TOTAL.increment(1);
    set_unix_now_seconds(&LAST_RECEIVED_TRANSACTION_TIMESTAMP_SECONDS);
    add_tx_inner(app_state, headers, tx).await
}

            }
        }
