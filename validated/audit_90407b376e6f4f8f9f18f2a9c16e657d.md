### Title
Unbounded prefix scan in `TronDatabase.prefixQuery` via attacker-seeded `DelegatedResourceAccountIndexStore` keys - (File: `chainbase/src/main/java/org/tron/core/db/TronDatabase.java`)

### Summary
`TronDatabase.prefixQuery` delegates directly to `dbSource.prefixQuery(key)` / `Chainbase.prefixQuery`, which performs a full, unbounded prefix scan over the underlying store with no cap on the number of matched entries. An unprivileged account can grow the number of keys under an attacker-controlled prefix (e.g. its own address prefix in `DelegatedResourceAccountIndexStore`) by repeatedly calling `DelegateResource`, and later any RPC query that resolves through `getIndex`/`getV2Index` → `prefixQuery` will scan and materialize all of them into memory on every call.

### Finding Description
`TronDatabase.prefixQuery(byte[] key)` simply forwards to the data source: [1](#0-0) 

The actual scan happens in `Chainbase.prefixQuery`, which queries the root DB and the in-memory snapshot layer with no `limit` parameter, unlike the sibling methods `getNext`/`getValuesNext`/`getKeysNext` that all accept and enforce a `limit`: [2](#0-1) 

`DelegatedResourceAccountIndexStore.getWithPrefix` (used by `getIndex`/`getV2Index`) builds a key from a prefix byte + the attacker's own address and calls `prefixQuery(key)` twice, with the result fully materialized into `ArrayList`s and sorted: [3](#0-2) 

Each call to `delegate`/`delegateV2` (invoked by `DelegateResourceActuator` / `DelegateResourceProcessor` for every `DelegateResource` transaction) inserts a new key `PREFIX + from + to` and `PREFIX + to + from` into the store: [4](#0-3) 

An attacker fully controls both `from` (their own address) and `to` (any number of distinct, even freshly-generated/unfunded addresses), so they can grow the number of keys sharing the prefix `PREFIX + from` arbitrarily by broadcasting many cheap `DelegateResource` transactions (delegating small amounts of bandwidth/energy resource to many different addresses). Once seeded, any subsequent RPC call that resolves to `getIndex`/`getV2Index` for that address (exposed via `Wallet`/gRPC `GetDelegatedResourceAccountIndex` and `GetDelegatedResourceAccountIndexV2`) triggers `prefixQuery`, which has to enumerate and materialize all N seeded entries with no bound, on every single query — this scan cost grows linearly (or worse, given the sort and multiple map copies) with the attacker-controlled key count N, independent of any query-side limit.

None of the standard defenses apply here: `TransactionCapsule.validateSignature` and actuator `validate()` only check that the delegating account is properly signed and has enough resource to delegate — they impose no cap on the number of distinct delegation records an account can create. There is no rate limiter or result-size cap on `prefixQuery` itself or on the RPC handlers that call `getIndex`/`getV2Index`.

### Impact Explanation
This matches **DoS via RPC-API (Advanced)**: an attacker seeds an unbounded number of prefix-sharing keys via ordinary, low-cost `DelegateResource` transactions, then any client (attacker or victim) querying `GetDelegatedResourceAccountIndex(V2)` for that address forces the queried node to perform an unbounded scan and in-memory materialization/sort on every call, degrading node responsiveness/CPU and potentially causing sustained service degradation or stalls for that RPC endpoint under repeated querying.

### Likelihood Explanation
The attacker needs only an ordinary funded account able to freeze a minimal amount of TRX for resource and issue many `DelegateResource` transactions to distinct addresses — no privileged role, no leaked keys, no peer/node access. Each delegation transaction is cheap (subject only to normal bandwidth/energy fees, not to the volume of index entries created), so seeding a large N is economically feasible and fully repeatable; the resulting query cost scales with attacker-chosen N indefinitely since `prefixQuery` has no bound.

### Recommendation
Add a bounded/limited variant of `prefixQuery` (mirroring `getNext`/`getKeysNext` which already accept a `limit`) and use it in `TronDatabase.prefixQuery` callers such as `DelegatedResourceAccountIndexStore.getWithPrefix` and `AccountAssetStore`, capping the number of scanned/returned entries per request (with pagination if full results are needed), and consider capping the number of distinct delegation records an account can create per prefix or charging fees proportional to the number of existing records.

### Proof of Concept
```java
// JUnit-style PoC (framework/src/test/java/org/tron/core/db/DelegatedResourceAccountIndexStoreTest.java style)
@Test
public void testPrefixQueryScanGrowsWithSeededKeys() {
  byte[] from = randomAddress();
  long start = System.nanoTime();
  int baselineN = 10;
  for (int i = 0; i < baselineN; i++) {
    delegatedResourceAccountIndexStore.delegateV2(from, randomAddress(), i);
  }
  long t1 = System.nanoTime();
  delegatedResourceAccountIndexStore.getV2Index(from); // triggers prefixQuery
  long baselineScanTime = System.nanoTime() - t1;

  int largeN = 100_000;
  for (int i = 0; i < largeN; i++) {
    delegatedResourceAccountIndexStore.delegateV2(from, randomAddress(), i);
  }
  long t2 = System.nanoTime();
  delegatedResourceAccountIndexStore.getV2Index(from); // triggers prefixQuery again
  long largeScanTime = System.nanoTime() - t2;

  // Assert scan time grows roughly linearly with N, demonstrating unbounded cost
  Assert.assertTrue(largeScanTime > baselineScanTime * (largeN / baselineN) / 2);
}
```
Expected: `largeScanTime` scales with the number of attacker-seeded keys, confirming `prefixQuery` (reached via `getV2Index` → `getWithPrefix`) has no bound and its cost is fully attacker-controllable — each `GetDelegatedResourceAccountIndexV2` RPC call for `from` after seeding will incur this same unbounded scan cost on the serving node.

  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    Map<WrappedByteArray, byte[]> result = prefixQueryRoot(key);
    Map<WrappedByteArray, byte[]>  snapshot = prefixQuerySnapshot(key);
    result.putAll(snapshot);
    result.entrySet().removeIf(e -> e.getValue() == null);
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQueryRoot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      result = ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      result = ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    }
    return result;
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
