### Title
Infinite/livelock loop in `ReadOnlyAccountsCache::evict` when cache holds fewer entries than `evict_sample_size` - (File: accounts-db/src/read_only_accounts_cache.rs)

### Summary
`ReadOnlyAccountsCache::evict` contains an inner `while remaining_samples > 0` sampling loop and an outer `while data_size.load(...) > target_data_size` loop that assumes the cache always contains at least `evict_sample_size` live entries whenever eviction is triggered. The code comment itself acknowledges this can loop indefinitely if that assumption is violated, but no bound or fallback exists.

### Finding Description
In the eviction routine, `remaining_samples` is decremented only inside the shard-sampling `for` loop, per key visited via `choose_multiple(rng, remaining_samples)`: [1](#0-0) 
If the total number of entries actually available across all shards (accounting for concurrent removals via `remove`/`remove_assume_not_present`, or a cache that was simply never populated to `evict_sample_size` entries) is smaller than `remaining_samples`, `choose_multiple` returns fewer than `remaining_samples` items each pass. Because `remaining_samples` is only decreased for entries actually visited, and no entries are found in subsequent random shard draws (empty shards or shards already exhausted), `remaining_samples` can stop decreasing — while `key_to_evict` may still be `None`, or the outer `while data_size.load(...) > target_data_size` loop can spin forever trying to evict below a threshold that is never reachable because `cache_len`/`data_size` do not reflect what the sampler can see.

This directly parallels the analog bug class: an inner loop's continuation condition (`remaining_samples > 0` / outer `data_size > target_data_size`) is not provably guaranteed to progress toward termination given concurrent mutation of the underlying `DashMap`, exactly as the Solidity `for (i = 0; ;)` loop assumed `earnedAmount` would eventually change but never advanced its index. The code's own comment confirms awareness of this exact class of failure: [2](#0-1) 

### Impact Explanation
`evict` runs on the dedicated `solAcctReadCache` evictor background thread on every validator (`spawn_evictor`), so a hang here stalls read-only account cache eviction entirely: [3](#0-2) 
If the eviction loop spins/hangs, `data_size` never drops below `max_data_size_hi`, so the process either busy-loops consuming CPU indefinitely (disproportionate CPU cost) or effectively becomes stuck evicting, causing unbounded growth of the read-only accounts cache's memory footprint. This does not corrupt account state or hashes, but it is a concrete, reachable, unprivileged-triggerable resource-exhaustion condition inside AccountsDB's cache management path, matching the "disproportionate storage and CPU cost" acceptance criterion.

### Likelihood Explanation
This is triggerable purely through normal AccountsDB read-cache usage under concurrency: entries are removed via `remove`/`remove_assume_not_present` from arbitrary threads while the evictor concurrently samples via `evict`. The DashMap's sharded, unsynchronized nature between `data_size`/`cache_len` counters and actual shard contents (they are separate atomics, updated non-atomically with respect to the map mutation) makes transient mismatches between `data_size` and the number of physically present entries plausible under load, especially with small `evict_sample_size` configurations or shortly after bulk removals. The comment in the code explicitly documents this as a known, unresolved risk ("This can loop indefinitely if the cache is misconfigured...").

### Recommendation
Bound the inner sampling loop with an explicit fallback (e.g., track how many entries were actually found across all shard passes and break/return once further progress is impossible, rather than relying solely on `remaining_samples` reaching zero), and bound the outer eviction loop with a maximum iteration count or an explicit re-check against `cache_len`/actual shard iteration, so eviction cannot spin when the assumed invariant ("cache contains at least `evict_sample_size` entries when eviction triggers") does not hold.

### Proof of Concept
Conceptual reproduction (background-agent-executable):
1. Configure a `ReadOnlyAccountsCache` with `max_data_size_lo`/`max_data_size_hi` such that eviction triggers, and `evict_sample_size` larger than the number of entries that remain in the cache after concurrent `remove()` calls drain most entries.
2. From one thread, call `store()` to exceed `max_data_size_hi`, triggering evictor wakeup.
3. From another thread, concurrently call `remove()`/`remove_assume_not_present()` on most cached pubkeys so that live entries drop below `evict_sample_size` while `data_size` bookkeeping still exceeds `target_data_size` momentarily.
4. Observe the evictor thread's `evict()` call spin in the `while remaining_samples > 0` / outer `while data_size... > target_data_size` loops without making progress, consuming CPU and failing to converge, per the acknowledged risk in the surrounding comment.
