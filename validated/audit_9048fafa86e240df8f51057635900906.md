### Title
Unbounded recursion in `get_recursive_transaction_results` walking a receipt-outcome chain can exhaust the JSON-RPC node's stack - (File: `chain/chain/src/chain.rs`)

### Summary
`get_recursive_transaction_results` [1](#0-0)  recursively walks the `receipt_ids` chain of execution outcomes with **no depth limit** to build the result for `get_final_transaction_result` [2](#0-1) , which backs the `tx`/`tx_status` JSON-RPC call reachable from any RPC caller via `RpcTransactionStatusRequest` [3](#0-2) . This is structurally analogous to the HAProxy DNS compression-pointer bug: a chain of pointers/ids of attacker-influenceable length is followed with one native stack frame per hop and no bound, risking stack exhaustion.

### Finding Description
`get_recursive_transaction_results` pushes the outcome for `id`, then for every `receipt_id` produced by that outcome it calls itself again — one recursive call per hop in the receipt DAG, with no depth counter or iterative fallback [4](#0-3) . This differs from the sibling `ReceiptToTx` reverse-lookup path, which the codebase explicitly hardens with a `MAX_DEPTH=1000` / `DepthExceeded` error [5](#0-4)  and has a dedicated regression test proving the limit is enforced [6](#0-5) . No equivalent bound exists on `get_recursive_transaction_results`.

The length of the receipt chain that this function walks is influenced by the depositor/contract deployer: a contract can chain many action receipts together via successive self cross-contract calls (each call produces a new receipt referenced as `receipt_ids` of the previous outcome). The test suite itself contains a purpose-built contract, `max_self_recursion_delay`, that self-recurses via `promise_batch_action_function_call_weight` specifically to build a long linear receipt chain, reaching depths in the hundreds within a single call's gas budget [7](#0-6) [8](#0-7) . Because such self-chaining calls can also be issued across multiple transactions/blocks (each new call is its own receipt, not limited to a single chunk's compute budget), the total resulting chain length recorded in execution outcomes is not bounded by a single chunk's gas/compute limit — it can grow unbounded over the life of a long-running self-recursive workflow.

### Impact Explanation
Any unprivileged RPC caller who queries `tx`/`tx_status` for such a transaction triggers `get_final_transaction_result` → `get_recursive_transaction_results`, which recurses once per receipt in the chain. If the chain is long enough, the recursive calls can exhaust the RPC/view-client thread's native stack and crash the process handling the request — a transaction-triggered denial of service on RPC nodes, matching the "transaction-triggered halt" impact class.

### Likelihood Explanation
Likelihood depends on how deep a receipt chain can practically become and whether Rust's default stack size (with each frame here being fairly small — a couple of `Vec`/`CryptoHash` locals) is sufficient to be exhausted. This is uncertain without further measurement: the demonstrated single-call depth (up to ~221 in the existing test) is unlikely by itself to overflow an 8MB stack, so a genuinely stack-exhausting depth in production likely requires an attacker to run a self-perpetuating chain across many blocks over time, which requires sustained gas expenditure and time, lowering immediate exploitability. I was unable to confirm the exact per-frame stack usage or an authoritative maximum achievable chain length across the codebase, so the practical severity of this specific analog is uncertain.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative worklist/queue traversal (as is already done for the `ops/iter.rs` trie iterator and the `ReceiptToTx` depth-limited walker), or add an explicit depth/count cap with a graceful error, mirroring the `DepthExceeded`/`MAX_DEPTH` pattern already used in `chain/jsonrpc-primitives/src/types/receipts.rs`.

### Proof of Concept
Conceptual PoC (not verified end-to-end due to index/tooling limits):
1. Deploy a contract that, like `max_self_recursion_delay`, issues a self cross-contract `FunctionCall` in a loop, chaining new action receipts across many blocks (bounded only by attacker's willingness to keep paying gas/keep the chain alive), to build a `receipt_ids` chain of length N.
2. Submit the initiating transaction.
3. From any RPC endpoint, call `tx`/`tx_status` for the transaction hash with `wait_until: EXECUTED`/`FINAL`.
4. `get_final_transaction_result` invokes `get_recursive_transaction_results`, recursing N times with no depth guard; for sufficiently large N, this crashes the serving node's thread via stack overflow.

Note: I could not fully verify the exact maximum achievable N in production (gas/compute-limit interactions across blocks) or measure actual stack-frame cost within the tool's available context — this would need dynamic testing to confirm real-world exploitability at Medium/High severity versus a purely theoretical bound.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");

        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}

    // to avoid having separate cases for every possible combination of features.
