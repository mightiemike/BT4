### Title
Inconsistent tron power calculation between `VoteWitnessActuator` and `VoteWitnessProcessor`/`TotalVoteCount` allows vote-power divergence between normal transactions and TVM `vote()` calls - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
Similar to the reported `balanceOfNFT` vs `balanceOfNFTAt`/`_balanceOfNFT` inconsistency (where a security-relevant value is computed with different logic in sibling functions), java-tron computes an account's "tron power" (the value that caps how many votes an account may cast) with two different feature-flag conditions depending on whether the vote is cast via a normal `VoteWitnessContract` transaction or via the TVM native `vote()` contract call / `TotalVoteCount` precompile.

### Finding Description
`VoteWitnessActuator.validate()` computes the voter's tron power using only the `supportAllowNewResourceModel()` flag: [1](#0-0) 

By contrast, the TVM-native equivalent `VoteWitnessProcessor.execute()` (invoked when a smart contract calls `vote()`) and the `TotalVoteCount` precompiled contract (used by contracts to query voting power) both gate the same computation on the conjunction of two flags, `supportUnfreezeDelay() && supportAllowNewResourceModel()`: [2](#0-1) [3](#0-2) 

Both paths ultimately choose between `AccountCapsule.getAllTronPower()` (which includes TRON_POWER-typed FrozenV2 balances) and `AccountCapsule.getTronPower()` (which explicitly excludes TRON_POWER-typed FrozenV2 balances): [4](#0-3) 

If `supportAllowNewResourceModel()` is enabled while `supportUnfreezeDelay()` is not (both are independent proposal-gated `DynamicPropertiesStore` flags configured via `ProposalUtil`), the two code paths diverge:
- The ordinary transaction path (`VoteWitnessActuator`) uses `getAllTronPower()`.
- The TVM-native path (`VoteWitnessProcessor`, `TotalVoteCount`) uses `getTronPower()` (a strictly smaller or equal value, since it omits TRON_POWER-typed frozen balance).

I was not able to fully confirm from the indexed code whether the two flags can independently be set to this particular combination (i.e., whether `ProposalUtil` enforces an ordering/dependency preventing `AllowNewResourceModel=1` while `UnfreezeDelay=0`) — this needs to be verified in `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`, which the grep located but which I could not read in full due to iteration limits.

### Impact Explanation
If the flag combination is reachable, an account's TVM-observable voting power (via `TotalVoteCount`) and TVM-native vote validation (`VoteWitnessProcessor`) would silently diverge from the value used for the normal `VoteWitnessContract` path. This creates an accounting inconsistency for a consensus-critical quantity (tron power / vote weight), analogous to the reported `balanceOfNFT` inconsistency, and could let a smart contract observe or enforce a different vote cap than the on-chain, actuator-validated truth — a form of state/consensus divergence for governance accounting. Severity is bounded because the divergence is a strict under-count in the TVM path relative to the actuator path (not an over-count enabling excess voting power), which limits it to functional inconsistency/DoS-style vote rejection rather than direct fund loss.

### Likelihood Explanation
Likelihood depends entirely on whether the specific flag combination (`AllowNewResourceModel=true`, `UnfreezeDelay=false`) is actually reachable through committee proposals, which I could not fully verify. If proposal ordering enforces `UnfreezeDelay` before `AllowNewResourceModel`, this is unreachable and not exploitable in practice.

### Recommendation
Audit `ProposalUtil.java` to confirm whether these two flags can be set independently. If they can, unify the condition used across `VoteWitnessActuator`, `VoteWitnessProcessor`, and `TotalVoteCount` to the same guard (matching whichever is the intended semantics), so that tron-power-based vote validation and TVM tron-power queries are always consistent regardless of feature-flag state.

### Proof of Concept
Not independently verified against a live node; the divergence is demonstrated purely through static code comparison of the three call sites cited above. Confirming exploitability would require setting `AllowNewResourceModel=1` and `UnfreezeDelay=0` via committee proposals (if permitted) and then comparing `TotalVoteCount` precompile output / TVM `vote()` validation against the normal `VoteWitnessContract` validation for the same account state.

  //tp:Tron_Power
  public long getTronPower() {
    long tp = 0;
    for (int i = 0; i < account.getFrozenCount(); ++i) {
      tp += account.getFrozen(i).getFrozenBalance();
    }

    tp += account.getAccountResource().getFrozenBalanceForEnergy().getFrozenBalance();
    tp += account.getDelegatedFrozenBalanceForBandwidth();
    tp += account.getAccountResource().getDelegatedFrozenBalanceForEnergy();

    tp += getFrozenV2List().stream().filter(o -> o.getType() != TRON_POWER)
            .mapToLong(FreezeV2::getAmount).sum();
    tp += account.getDelegatedFrozenV2BalanceForBandwidth();
    tp += account.getAccountResource().getDelegatedFrozenV2BalanceForEnergy();
    return tp;
  }

  public long getAllTronPower() {
    if (account.getOldTronPower() == -1) {
      return getTronPowerFrozenBalance() + getTronPowerFrozenV2Balance();
    } else if (account.getOldTronPower() == 0) {
      return getTronPower() + getTronPowerFrozenBalance() + getTronPowerFrozenV2Balance();
    } else {
      return account.getOldTronPower() + getTronPowerFrozenBalance()
          + getTronPowerFrozenV2Balance();
    }
  }
