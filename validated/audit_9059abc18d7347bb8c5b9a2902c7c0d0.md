### Title
Unbounded shop→session-ID index array in KV/Redis Session Storage adapters enables session-storage DoS - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
The Cloudflare KV and Redis `SessionStorage` adapters index all session IDs for a shop under a single storage value (a JSON-encoded array), read-modify-written on every `storeSession` call. Unlike ink!'s single-storage-cell vector, which has a fixed buffer/decode limit, these adapters have no deduplication and no bound on this array, so it can grow without limit as the token-exchange/auth handler repeatedly persists the (unchanged) offline session id.

### Finding Description
`KVSessionStorage.storeSession` unconditionally calls `addShopIds(session.shop, [session.id])` on every store, and `addShopIds` appends the id to the existing array without checking for duplicates: [2](#0-1) [3](#0-2) 

Offline sessions have a deterministic, stable id (`offline_<shop>`), computed in `getOfflineId` [4](#0-3) , so every re-store of the *same* offline session appends a duplicate entry to the shop's index array rather than replacing it.

This index is read/decoded in its entirety on every subsequent `storeSession` and `findSessionsByShop` call: [5](#0-4) 

The Redis adapter has the analogous pattern (`addKeyToShopList`/`removeKeyFromShopList`/`findSessionsByShop` all `JSON.parse` a single ever-growing value keyed by shop): [6](#0-5) 

The reachable trigger is the auth/token-exchange handler, which re-persists the offline session (and thus re-appends to the shop index) whenever the cached session is missing or nearing expiry: [7](#0-6) . Each call grows the single JSON array value for that shop by one entry, with no cap and no cleanup outside of explicit `deleteSession`/`deleteSessions` calls.

### Impact Explanation
As with the ink! unbounded-vector bug, the entire array must be decoded/re-encoded on every read/write, so cost grows linearly (then super-linearly in aggregate) with the number of stores. Cloudflare KV enforces a 25 MiB per-value limit; once the JSON string exceeds that, `namespace.put` will begin failing, which breaks `storeSession` for that shop going forward — a durable denial of service for the auth/token-exchange handler and `findSessionsByShop` for that tenant. On Redis, unbounded growth increases latency for every `storeSession`/`findSessionsByShop` call and, on shared infrastructure, can exhaust memory affecting other tenants (noisy-neighbor DoS). Because `findSessionsByShop` calls `loadSession` once per entry in the index (including duplicates), the number of KV/Redis reads for that operation scales with total historical stores, not distinct sessions, compounding the cost.

### Likelihood Explanation
High for KV/Redis-backed deployments: the growth path requires no privileged action, just normal session-token expiry/refresh traffic that is part of the standard App Bridge/token-exchange flow, and it can be accelerated by a single merchant/customer simply causing repeated token-exchange calls (e.g., by forcing session-token refreshes). No authentication bypass is needed to trigger it — it happens inside the legitimate, unauthenticated-by-design token-exchange handler itself.

### Recommendation
In both `KVSessionStorage.addShopIds`/`removeShopIds` and `RedisSessionStorage.addKeyToShopList`/`removeKeyFromShopList`, deduplicate before writing (e.g., use a `Set` or check `includes` before appending, as the Redis code already does for a *new* key but not consistently), and/or replace the "single JSON array in one value" indexing pattern with a per-id secondary key (e.g., `shop:<shop>:session:<id>` marker keys plus a KV `list()`/Redis `SMEMBERS` set) so no single value's size is proportional to total historical writes.

### Proof of Concept
1. Configure a non-embedded app or standard embedded app using `KVSessionStorage` (or `RedisSessionStorage`) with the `shopify-app-express`/`shopify-app-remix` token-exchange strategy.
2. As a normal merchant/customer, repeatedly trigger the App Bridge session-token exchange (e.g., reload the embedded app, or force session-token refresh) so that `performTokenExchange` runs its `storeSession(offlineSession)` path at line 101 of `perform-token-exchange.ts` multiple times for the same shop (this happens naturally whenever the cached session is absent/near-expiry, and can be forced more often client-side).
3. Observe that the KV/Redis value at the shop's index key (`shop:<shop>` in KV, `<shop>` in Redis) grows by one entry (`offline_<shop>`) per call, with duplicate entries accumulating indefinitely.
4. Continue until the value approaches the backend's per-value size limit (25 MiB for Cloudflare KV) — subsequent `storeSession` calls for that shop begin failing, and `findSessionsByShop` becomes increasingly slow/expensive due to loading the same session repeatedly for each duplicate entry.

**Caveat:** I could not fully verify from the indexed code how frequently client-side session-token refresh actually re-invokes `performTokenExchange`'s store path in practice (that depends on App Bridge/browser refresh cadence, which lives outside this repo), so the realistic time-to-impact is uncertain; the structural bug (unbounded, undeduplicated single-value array index) is confirmed directly in the cited source.
