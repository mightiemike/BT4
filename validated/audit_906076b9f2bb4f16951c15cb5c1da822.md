### Title
Excess destination-chain gas fee is permanently unrefunded when the funds-revert re-mint fails on a failed outbound - ([File: x/uexecutor/keeper/outbound.go])

### Summary
`FinalizeOutbound` settles a failed outbound in two conceptually separate steps: (1) re-mint the bridged PRC20 back to the revert recipient, and (2) refund the excess gas fee (`gasFee - gasFeeUsed`) via `applyGasRefund`. When step (1) fails, the code short-circuits into `AbortOutbound` and returns immediately, so step (2) (`applyGasRefund`) never runs. This mirrors the reported bug class ("all functions that mutate accounted-for balances must settle the accrual/fee state first") — here the terminal state transition (`ABORTED`, removed from `PendingOutbounds`) is committed before the fee/refund settlement that is supposed to accompany every outbound finalization, and once `ABORTED`, `FinalizeOutbound` never reprocesses that outbound (it only proceeds when `outbound.OutboundStatus == Status_OBSERVED`).

### Finding Description
`FinalizeOutbound` (`x/uexecutor/keeper/outbound.go:71-97`) dispatches to `handleFailedOutbound` when a UV-observed outbound execution failed on the destination chain. [1](#0-0) 

Inside `handleFailedOutbound` (`x/uexecutor/keeper/outbound.go:99-161`), for funds-carrying tx types the code calls `CallPRC20Deposit` to re-mint the bridged amount to the revert recipient. If that EVM call errors, the function calls `k.AbortOutbound(...)` and **returns immediately** — `applyGasRefund` on line 158 is only reached on the success path (falls through after the `if err != nil { return ... }` block): [2](#0-1) 

`AbortOutbound` sets `Status_ABORTED`, removes the outbound from `PendingOutbounds`, and emits a monitoring event — it does not call `applyGasRefund` and there is no other code path that revisits an `ABORTED` outbound: [3](#0-2) 

By contrast, the successful-outbound path (`handleSuccessfulOutbound`) and the "funds-revert succeeded" branch of `handleFailedOutbound` both always call `applyGasRefund` before persisting the final state: [4](#0-3) 

The comment on `applyGasRefund` explicitly states the invariant that is being violated in the abort branch: *"It is called for both successful and failed outbounds — gas is consumed on the external chain regardless of execution outcome."* [5](#0-4) 

Because `PENDING`/`OBSERVED`→`ABORTED` is a one-way transition and `FinalizeOutbound` is gated on `Status_OBSERVED`, once `AbortOutbound` fires there is no automatic mechanism that ever revisits this outbound to run `applyGasRefund` — the excess gas (`gasFee - gasFeeUsed`, already deducted from the user/gateway at outbound-creation time on the `UniversalCore` contract) is stranded and never returned to the sender/fund-recipient. `README.md` documents `ABORTED` as requiring manual, governance-driven intervention with no automated resolution path, confirming there is no built-in recovery for the skipped refund. [6](#0-5) 

### Impact Explanation
This is a permanent loss of protocol/user-controlled funds: the pre-collected excess gas fee for the affected outbound is never refunded to the user once the abort branch is taken, and the outbound can never be re-finalized to retry the refund because it is no longer `OBSERVED`. This falls squarely within the allowed impact "permanent loss ... of user or protocol-controlled funds" reachable through the honest-validator outbound-voting flow (`MsgVoteOutbound` → `FinalizeOutbound`).

### Likelihood Explanation
Triggering requires only that: (a) UVs (honestly) observe and vote that a destination-chain execution failed (`obs.Success == false`) for a `FUNDS`, `GAS_AND_PAYLOAD`, or `FUNDS_AND_PAYLOAD` outbound, and (b) the subsequent `CallPRC20Deposit` re-mint to the revert recipient fails. The revert recipient is derived from `outbound.RevertInstructions.FundRecipient`, which for many inbound tx types is attacker/user-supplied at inbound-creation time (via `RevertInstructions` on the original `Inbound`/`UniversalPayload`). A user can plausibly steer this field toward a value/config that makes the re-mint call revert deterministically (e.g., an address hitting a PRC20-level restriction, or exploiting normal EVM failure conditions such as gas-limit exhaustion on the module-originated call), causing their own outbound to abort and their own excess gas refund to be permanently lost — or, more importantly for third parties, this can happen for any legitimate failed outbound purely due to ordinary EVM failure modes (no attacker needed at all), meaning honest users can lose funds through normal usage. I was not able to fully verify from the available index which specific conditions make `CallPRC20Deposit` revert in production (this depends on `UniversalCore`/`PRC20` Solidity behavior, which is outside the indexed Go/proto code), so likelihood of deliberate exploitation (vs. incidental occurrence) is uncertain.

### Recommendation
In `handleFailedOutbound`, call `k.applyGasRefund(ctx, &outbound, obs)` before (or regardless of) branching into `AbortOutbound` when the re-mint fails, so the excess gas fee is always settled prior to any terminal/abort state transition — mirroring the "mint/burn must settle fee first" invariant from the reported bug class. If `applyGasRefund` itself can fail, its result should be recorded (as already done via `PcRefundExecution`/`RefundSwapError`) independent of whether the abort path is taken, and/or `AbortOutbound` should be extended to guarantee the gas-refund settlement runs (or is retried) even for aborted outbounds.

### Proof of Concept
1. Create a `FUNDS_AND_PAYLOAD` (or `FUNDS`) inbound with `RevertInstructions.FundRecipient` set to an address/PRC20 configuration under attacker influence, and drive it to outbound creation with a non-trivial `GasFee`/`GasToken` (as in `setupOutboundVotingTest` in `test/integration/uexecutor/gas_fee_refund_test.go`).
2. Have UVs vote `MsgVoteOutbound` with `success=false` and `gasFeeUsed < gasFee` (e.g., as in the `"failed outbound performs both revert and gas refund"` test case), but arrange/mock `CallPRC20Deposit` to fail (e.g., insufficient PRC20 mint permission edge case or EVM revert during re-mint).
3. Observe that `handleFailedOutbound` returns via `AbortOutbound` at `x/uexecutor/keeper/outbound.go:135` without ever calling `applyGasRefund`.
4. Query the resulting `OutboundTx`: `OutboundStatus == ABORTED`, `PcRefundExecution == nil`, and no further `MsgVoteOutbound`/`FinalizeOutbound` call will ever process this outbound again (since it is no longer `OBSERVED`), leaving the excess gas fee permanently unrefunded.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}
