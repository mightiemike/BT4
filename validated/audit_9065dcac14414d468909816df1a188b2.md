## Title
`TransactionOutput::ensure_match_transaction_info` never validates the state-checkpoint root hash, so replay/chunk-verify tooling can accept a corrupted state Merkle root - (File: `types/src/transaction/mod.rs`)

### Summary
The single comparator used by every replay-verification code path (`chunk_executor::verify_execution`, the `db-tool replay-on-archive` verifier, `aptos-debugger`, and the `aptos` CLI replay commands) to confirm that locally re-executed transactions match the transaction data recorded on the authenticated ledger is `TransactionOutput::ensure_match_transaction_info`. This function checks status, gas used, write-set hash, and event-root hash, but explicitly (per its own TODO) skips comparing `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` — the fields that actually commit to the global state Merkle root. As a result, a divergence in state-tree computation between the archived/committed `TransactionInfo` and a fresh re-execution is silently accepted as "matching" by every tool that relies on this function.

### Finding Description
`TransactionInfo` carries the ledger's state commitment in `state_checkpoint_hash` (and, for `V1`, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), which is the root of the Sparse/Jellyfish Merkle Tree summarizing world state at that version: [1](#0-0) 

`ensure_match_transaction_info` is documented as the function that confirms a `TransactionOutput` (freshly produced by re-execution) matches the previously committed `TransactionInfo`. It checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash, but its own comment admits the checkpoint hashes are never compared: [2](#0-1) 

This function is the sole verification gate in three consumer paths that exist specifically to catch state divergence:
- `ChunkExecutor::verify_execution`, used during chunk replay / verify-execution flows in state sync and restore: [3](#0-2) 
- The `db-tool replay-on-archive` verifier, whose entire purpose is to replay historical archive data and flag mismatches: [4](#0-3) 

Because `state_change_hash` only hashes the transaction's own write set (a local diff), it cannot detect a state-Merkle-tree construction bug that mis-applies that diff onto the accumulated global state (e.g., a defect in JMT node placement, hot-state merge logic, or the newer position/native-state tree code seen in `storage/aptosdb/src/native_state_committer.rs` and `storage/aptosdb/src/state_store/mod.rs`). Such a bug would produce a wrong `state_checkpoint_hash` while leaving `state_change_hash`, `event_root_hash`, `gas_used`, and `status` unchanged — and `ensure_match_transaction_info` would report success regardless.

### Impact Explanation
The state-checkpoint hash is the authenticated root that all downstream state proofs, restore verification, and light-client trust ultimately rely on (it's cryptographically bound into `TransactionInfo::hash()` which anchors the transaction accumulator). Replay/verify tooling exists precisely to give independent assurance that this root is correctly derived from deterministic execution. Because the comparator silently ignores it, a bug or non-determinism in state-tree computation (executor-to-storage handoff, JMT commit, hot-state, or the newer trading-native position tree) that corrupts the committed state root would not be caught by `replay-on-archive`, `chunk_executor` verify-execution, or the debugger/CLI replay commands — meeting the "hard-fork-only divergence during commit, replay, restore, or proof verification" bucket. Operators/auditors relying on these tools for post-hoc integrity assurance of mainnet history would get false confidence that historical state roots are correct.

### Likelihood Explanation
This is not a hypothetical attacker-controlled path; it's a structural gap in the verification code itself, guaranteed to manifest whenever the state-tree computation path (rather than the write-set) is the source of a divergence — which is exactly the failure mode replay verification is supposed to catch. The comment in the code confirms the authors are aware the gap exists but have not closed it for the non-gated fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`), only reasoning about future gating for `position_state_checkpoint_hash` behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (and `hot_state_checkpoint_hash` where applicable) between `self`/re-execution output and `txn_info`, whenever a checkpoint hash is expected (i.e., `has_state_checkpoint_hash()`), before returning `Ok(())`. Gate `position_state_checkpoint_hash` comparison behind the corresponding feature flag as already planned, but do not leave the core `state_checkpoint_hash` unchecked unconditionally.

### Proof of Concept
1. Instrument/patch the state-Merkle-tree commit path (e.g., in `storage/aptosdb/src/state_store/mod.rs` or `native_state_committer.rs`) so it computes an incorrect root hash for a given version while leaving the write set, events, gas, and status identical to the correct execution (e.g., swap the order of two leaf updates in a way that changes the root but not the individual write ops).
2. Run `db-tool replay-on-archive` (or `ChunkExecutor::verify_execution`) over a range including that version, supplying the archived (correct) `TransactionInfo`.
3. Observe that `ensure_match_transaction_info` returns `Ok(())` because it never compares `state_checkpoint_hash`, even though the freshly computed state root diverges from the one bound into the archived, signature-authenticated `TransactionInfo`/accumulator.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
