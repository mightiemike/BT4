### Title
Unbounded, cost-free account-store growth via gasless `AccountInitDecorator` — DoS by state exhaustion (File: `app/ante/account_init_decorator.go`)

### Summary
The Deriverse bug allocates fixed-size records in a bounded account (`client_infos_acc`/`client_infos2_acc`) on every order but only frees them on specific cleanup paths (`move_spot_avail_funds`, `finalize_spot`), letting an attacker who avoids those paths permanently consume account space and eventually DoS the exchange. Push Chain's `AccountInitDecorator` has the same allocate-without-deallocate shape: any unprivileged actor can force permanent creation of a new base account in the `x/auth` KV-store at effectively zero cost, with no mechanism to ever remove it, by repeatedly submitting gasless transactions signed by throwaway keys.

### Finding Description
`app/ante/account_init_decorator.go`'s `AnteHandle` runs whenever a transaction is classified gasless by `txpolicy.IsGaslessTx` (`app/txpolicy/gasless.go`), which covers `MsgExecutePayload`, `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`, and `MsgMigrateUEA` (also inside `authz.MsgExec`) — several of which ("any" sender for `MsgExecutePayload`) are reachable by an arbitrary unprivileged caller with no bonding/allowlisting. [1](#0-0) 

If the transaction's single signer has no existing account (`aid.ak.HasAccount`), the decorator only verifies a signature against `account_number=0, sequence=0` — something trivially satisfiable by generating a fresh keypair and self-signing — then unconditionally calls `aid.ak.NewAccountWithAddress(...)` and `aid.ak.SetAccount(...)`, permanently persisting a new account record in the `x/auth` store. [2](#0-1) 

Because this state write happens inside the AnteHandler's branched multistore, which is committed to the parent store once the AnteHandler chain succeeds — independent of whether the subsequent message execution (e.g. `MsgExecutePayload`'s EVM call, or `MsgVoteInbound`'s bonded-validator check) later fails — the account persists even when the message itself is guaranteed to be rejected (e.g. an unbonded caller submitting `MsgVoteInbound`, or a `MsgExecutePayload` whose `VerificationData` can never validate against a victim UEA, as the module's own README documents: "the entire Cosmos transaction... rolls back atomically" only refers to *EVM* state, not the account created in the AnteHandler stage). [3](#0-2) 

Unlike the fee-charging `DeductFeeDecorator`, gasless transactions skip fee deduction entirely (`app/ante/fee.go` via `IsGaslessTx`), and the `MinGasPriceDecorator` skips the minimum-fee check. [4](#0-3) 

The result: an attacker can generate an unlimited number of fresh keypairs off-chain (free), craft a minimal self-signed gasless message of an allowed type for each, and broadcast it — each broadcast permanently grows the `x/auth` account store by one entry, with no code path anywhere in the module to detect, expire, or garbage-collect these accounts. There is no analog of Deriverse's `finalize_spot`/`move_spot_avail_funds` deallocation for this allocation.

### Impact Explanation
This is unbounded, unprivileged, essentially cost-free growth of a core consensus-critical store (`x/auth` accounts), which every full node must store and iterate over indefinitely. Sustained abuse increases state size, snapshot/sync time, and iavl tree depth for all nodes, degrading throughput and potentially exhausting disk/memory resources over time — a non-network-level DoS reachable purely through ordinary unprivileged transaction submission, matching the "denial of service only when it is not network-level and is reachable without privileged control" allowed-impact category.

### Likelihood Explanation
High. No bonding, KYC, minimum balance, or fee is required to trigger account creation — only a fresh Ed25519/secp256k1 keypair and a syntactically valid message of one of the seven gasless types. Generating keys and signatures is computationally cheap, so an attacker can automate mass account creation at a rate limited only by mempool/block throughput, with the underlying message failing (and being irrelevant) in all cases.

### Recommendation
- Require the underlying gasless message to pass its own authorization/validity checks (e.g., bonded-validator check for `MsgVote*`, or successful UEA signature verification for `MsgExecutePayload`) *before* committing the new account record, or perform account creation atomically with, and rolled back alongside, message execution rather than in the branched AnteHandler multistore that commits independently.
- Alternatively, impose a minimal anti-spam cost for first-use account creation (e.g., a tiny bonded stake/deposit, rate limiting per IP/session, or requiring proof that the new account is the actual signer of a subsequently-valid gasless message) so that account creation is not free and unconditional.
- Add a lifecycle/cleanup path for zero-activity accounts created this way, mirroring the recommendation of "deallocate as soon as [the reservation's purpose] is executed, or provide a dedicated deallocation mechanism."

### Proof of Concept
1. Generate a new keypair `K` off-chain (free, no on-chain interaction).
2. Derive `addr(K)`, which has no existing account (`HasAccount` returns false).
3. Construct a `MsgExecutePayload` (or `MsgVoteInbound`, etc.) with `Signer = addr(K)`, any (even garbage/invalid) `UniversalAccountId`/payload, signed by `K` with `account_number=0, sequence=0`.
4. Broadcast the transaction. `AccountInitDecorator.AnteHandle` verifies the self-consistent signature, calls `NewAccountWithAddress`/`SetAccount`, and commits — regardless of whether the message handler later rejects the message (e.g., unbonded validator, invalid UEA authorization).
5. Repeat steps 1–4 with a new keypair each time; each iteration adds one permanent, unremovable entry to the `x/auth` account store at zero fee cost.

```markdown
#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
```

```markdown
### Transaction Pipeline — Gasless Support

Push Chain extends the Cosmos AnteHandler with three custom decorators that together enable **gasless transactions** for Universal Validators and UEA users. Without this, every Universal Validator would need to hold and manage gas tokens just to vote — defeating the point of having a permissioned UV set.

**The gasless whitelist** (`app/txpolicy/gasless.go`) — only these message types qualify:

```
/uexecutor.v1.MsgExecutePayload
/uexecutor.v1.MsgVoteInbound
/uexecutor.v1.MsgVoteOutbound
/uexecutor.v1.MsgVoteChainMeta
/utss.v1.MsgVoteTssKeyProcess
/utss.v1.MsgVoteFundMigration
```

A tx is gasless only if **every** message (including those nested inside `authz.MsgExec`) is in the whitelist.

**Custom decorators**

| Decorator | File | Behavior on gasless tx |
|---|---|---|
| `MinGasPriceDecorator` | `app/cosmos/min_gas_price.go` | Skips the FeeMarket minimum-fee check entirely |
| `DeductFeeDecorator` | `app/ante/fee.go` | Skips fee deduction (no balance required) |
| `AccountInitDecorator` | `app/ante/account_init_decorator.go` | If signer has no on-chain account yet, creates it mid-pipeline with `account_number=0, sequence=0`, verifies the signature against those values, and short-circuits the rest of the ante chain |

The third decorator is what lets a freshly-keygen'd Universal Validator hot key vote on its very first tx, without anyone first having to fund it.
```
