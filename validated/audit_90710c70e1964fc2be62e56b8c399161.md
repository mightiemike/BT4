### Title
Replay-verify tooling accepts divergent state roots because `ensure_match_transaction_info` never checks `state_checkpoint_hash` / `hot_state_checkpoint_hash` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness gate used by `db-tool`'s `replay_on_archive` (and by the Aptos debugger / CLI replay paths) to decide whether a locally re-executed transaction matches the transaction info recorded on the archived, authenticated ledger. The function validates status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never compares the resulting state-checkpoint root (`state_checkpoint_hash`) or hot-state checkpoint root (`hot_state_checkpoint_hash`) against the expected values from the archive. A bug in Jellyfish Merkle Tree checkpoint computation, hot-state root computation, or any code path that only affects the persisted state root but not the per-transaction write set would silently pass replay-verify, defeating the purpose of that tool.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and only asserts on transaction status and gas. It then checks the write-set hash against `txn_info.state_change_hash()` [2](#0-1)  and the event root hash against `txn_info.event_root_hash()` [3](#0-2) . There is no comparison anywhere in the function against `txn_info.state_checkpoint_hash()` or the V1 `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` fields. The function's own trailing comment confirms this gap explicitly: [4](#0-3) 

This function is the exact correctness oracle used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which replays archived transactions through `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` as the only pass/fail check per transaction: [5](#0-4) . Since `state_checkpoint_hash`/`hot_state_checkpoint_hash` are never included in this comparison, a divergence between the locally-computed Sparse-Merkle/Jellyfish state root and the archived, ledger-info-authenticated state root at that version is invisible to this tool — it will report the transaction as verified correctly even though the state root differs from the authenticated one.

The `state_checkpoint_hash` is precisely the field that is supposed to bind a `TransactionInfo` (and, through the transaction accumulator, the `LedgerInfo`) to the authenticated world-state root — see its definition and where it's produced by `DoStateCheckpoint::run`/`get_state_checkpoint_hashes` in the executor [6](#0-5) . Skipping it in the verify oracle means the one tool whose job is to independently re-derive and confirm this root against history cannot detect a determinism bug that corrupts only the state root computation while leaving the write set, gas, and events unchanged (e.g., a bug in JMT nibble path construction, hot-state root merging, or the new trading-native `position_state_checkpoint_hash` path added alongside `compute_trading_native_state_roots` in `do_state_checkpoint.rs`).

### Impact Explanation
Replay-verify is a primary safety net used before/after protocol upgrades and by auditors/validators to confirm that re-execution against archived history reproduces the authenticated ledger deterministically. If a bug causes the persisted state root to diverge from the correct VM result at some historical version (a hard-fork-class bug), `replay_on_archive` would report full success, hiding the divergence from operators who rely on this tool to catch exactly this class of bug before it propagates or before it is discovered by other means. This satisfies the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category, since the corrupted value (the state/hot-state/position state root) is never checked by the designated verification code path.

### Likelihood Explanation
This is not a remotely triggerable bug by itself — it requires a separate root-cause bug in state-checkpoint hash computation to exist. However, the missing check is unconditional (present at every version, not gated by any feature flag for the base `state_checkpoint_hash`), so any future or existing determinism bug in checkpoint/root computation would go completely undetected by this verification tool, silently reducing confidence in an otherwise critical safety mechanism. The trading-native position-state root gap is explicitly acknowledged as a known blind spot in the code's own comment, confirming this is a real, currently-existing coverage hole rather than a theoretical one.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`-derived state checkpoint hashes (when the transaction is a checkpoint) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when applicable), returning an error on mismatch just as is done for `state_change_hash` and `event_root_hash`. This requires threading the locally computed checkpoint hashes (produced by `DoStateCheckpoint`) into the comparator, since `TransactionOutput` alone does not carry them.

### Proof of Concept
Not applicable as a live exploit — this is a verification-tooling coverage gap, not a directly triggerable consensus bug. The proof is the code inspection above: `ensure_match_transaction_info` at [7](#0-6)  never reads `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` from `txn_info`, and its only caller that performs execution-based verification, `Verifier::execute_and_verify` in `replay_on_archive.rs` [8](#0-7) , has no additional independent check of the state root, so any hypothetical state-root-only divergence would pass `replay_on_archive` without error.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
