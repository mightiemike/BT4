### Title
Missing Chain/Network Binding in NEP-461 `SignableMessage` Enables Cross-Network Replay of `DelegateAction` / `DelegateActionV2` Signatures - ([File: core/primitives/src/signable_message.rs])

### Summary
The reported bug is that OZ's `EIP712Upgradeable` derives its domain separator from a hardcoded `_TYPE_HASH` that includes `name` and `version`, but `L2ECO` never initializes those fields, so the signed payload silently omits binding data that EIP-712 signers assume is present, weakening the domain separation the signature scheme is supposed to provide. The analogous defect in nearcore is in the NEP-461/NEP-366 `SignableMessage` scheme used to sign `DelegateAction`/`DelegateActionV2` (meta-transactions): the signed payload's "domain" is only a `MessageDiscriminant` (NEP number + on/off-chain tag) plus the action fields themselves — it contains no chain/network identifier (no genesis hash, chain id, or block hash), so the same signature is valid on any NEAR-protocol-compatible network that shares account IDs and block heights.

### Finding Description
`SignableMessage<T>` is the generic wrapper NEAR uses to bind a NEP-tagged discriminant to a message before hashing and signing: [1](#0-0) 

Its only "domain" separation is the 4-byte `MessageDiscriminant`, which just encodes an on-chain/off-chain flag and a NEP number: [2](#0-1) 

`DelegateAction::get_nep461_hash` and `VersionedDelegateActionPayload::get_nep461_hash` build the signed hash purely from this discriminant plus the action's own fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`): [3](#0-2) [4](#0-3) 

Unlike a normal `SignedTransaction`, which is bound to a specific `block_hash` that is unique per chain/fork, `DelegateAction` freshness is bound only to `max_block_height` — a plain integer, not a chain-specific hash: [5](#0-4) 

There is nothing anywhere in the discriminant, the action payload, or the verification logic (`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify`) that ties the signature to a specific network's genesis/chain id: [6](#0-5) [7](#0-6) 

This is the direct structural analog of the EIP-712 report: the report's contract omits `name`/`version` from the EIP-712 domain, breaking the intended per-application/per-contract binding; here NEAR's meta-transaction signing scheme omits any chain/network identifier from its "domain" (the `MessageDiscriminant`), so the same off-chain-signed `DelegateAction`/`DelegateActionV2` bytes hash and verify identically regardless of which NEAR-protocol network (mainnet, testnet, or any other chain instance sharing the same account-ID space and block-height range) they are submitted to.

### Impact Explanation
An account holder (e.g., "alice.near") who signs a `DelegateAction` intended for relaying on one NEAR network can have that exact signed payload replayed by any relayer on a different NEAR-protocol-based network where an account with the same ID and a compatible key/nonce state exists (e.g., a testnet, a private/enterprise NEAR fork, or a future NEAR-based chain sharing the discriminant scheme). Because `nonce`/`max_block_height` provide only intra-chain replay protection and not cross-chain domain separation, a relayer or attacker who obtains the signed bytes can forward the same authorization to unlock unintended actions on another chain instance where the sender did not intend to authorize them — leading to unauthorized value movement (the relayed actions can include `Transfer`, `FunctionCall` with deposits, etc.) executed under the victim's identity. This satisfies "concrete unauthorized value movement" / "invalid state transition acceptance" categories reachable purely from a signed meta-transaction crafted by a normal user/relayer, no privileged access required.

### Likelihood Explanation
Exploitability requires that the same account ID and a compatible nonce/key state exist on a second network sharing the identical `MessageDiscriminant`/NEP-461 signing scheme (which is by design meant to become a cross-ecosystem standard per the NEP-461 reference in the code comments). This is a realistic scenario for NEAR testnet/mainnet pairs (many accounts are mirrored across both) and for any NEAR-protocol fork or app-specific chain that reuses the same crypto/serialization stack — a scenario nearcore explicitly anticipates by making the discriminant a "forward-looking" cross-ecosystem primitive. Likelihood is medium: it depends on cross-network account/key overlap, but is not a contrived or purely theoretical setup given NEAR's own testnet/mainnet account-mirroring conventions and multi-chain deployment model.

### Recommendation
Bind the NEP-461 `SignableMessage` domain to the specific chain instance, analogous to including `chainId` in an EIP-712 domain separator: incorporate the network's genesis hash or a protocol-defined `chain_id` into the `MessageDiscriminant` (or as an additional field hashed alongside it in `SignableMessage`) so that a `DelegateAction`/`DelegateActionV2` signed for one network cannot be verified as valid on another. This should be added before any wider (NEP-461) standardization to avoid baking a domain-separator gap into a scheme intended for cross-ecosystem reuse.

### Proof of Concept
1. Alice signs a `DelegateAction` off-chain via `DelegateAction::get_nep461_hash()` + her key, intending it for a relayer to submit on Network A: [6](#0-5) 
2. The resulting `SignedDelegateAction` bytes (hash = `sign(hash(borsh(discriminant ++ delegate_action)))`) contain no reference to Network A's genesis/chain id — only the NEP-366 on-chain discriminant and the action fields.
3. If Alice's account ID, public key, and nonce state also exist on Network B (e.g., a testnet mirror or a NEAR-protocol fork sharing the same discriminant constants in `signable_message.rs`), the identical signed bytes pass `SignedDelegateAction::verify()` on Network B as well, because verification only checks the ed25519 signature against the hash — no chain-specific value is part of that hash: [8](#0-7) 
4. A relayer on Network B can therefore submit Alice's Network-A-intended `DelegateAction` as a valid meta-transaction on Network B, executing the inner actions (transfers, function calls with deposits) against Alice's Network B state without her consent for that specific network.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

    /// Delegate action hash used for NEP-461 signature scheme which tags
    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateActionV2);
        let bytes = borsh::to_vec(&signable).expect("failed to serialize");
        hash(&bytes)
    }
}
