Confirmed: the documentation itself says rejected L1-handler transactions should be "unstaged, keep as Pending" [1](#0-0) , but the actual code sets a rejected transaction's state to a distinct `TransactionState::Rejected` variant via `mark_rejected()` [2](#0-1) , and `is_validatable()` never excludes the `Rejected` state — it only excludes `Committed`, `Cancelled`, and `Consumed` [3](#0-2) .

### Title
Rejected L1-handler transactions remain validatable and can be re-included in a new proposal after a block that rejected them - (File: `crates/apollo_l1_events/src/transaction_record.rs`)

### Summary
This is the direct analog of the reported Aragon `Voting.vote()` bug: a state-mutating entry point (`vote()` there, `validate_tx()`/`is_validatable()` here) fails to check one of the terminal/negative states (`rejected` there, `TransactionState::Rejected` here) before allowing the action to proceed.

### Finding Description
`TransactionManager::commit_txs` transitions any transaction hash in `rejected_txs` to `TransactionState::Rejected` and sets the `rejected` metadata flag via `TransactionRecord::mark_rejected()` [4](#0-3) . This is called whenever the batcher's execution rejected an L1Handler tx that had been consumed on L1 but not accepted into the block (e.g. it failed execution) [5](#0-4) .

`TransactionManager::validate_tx` (reached from `L1EventsProvider::validate`, which is called by the batcher for every L1Handler tx during block validation of a subsequent proposal) checks `record.is_validatable()` to decide whether the transaction may be accepted into the block being validated [6](#0-5) , and `is_validatable()` is defined as `!self.is_committed() && !self.is_cancelled() && !self.is_consumed()` [3](#0-2) . There is no `!is_rejected()` check, even though `TransactionState::Rejected` is a distinct enum variant separate from `Pending` [7](#0-6) .

The doc comment on `is_validatable` explicitly claims "this includes states like: a rejected transaction" is meant to be excluded, i.e. the documented intent is that rejected transactions should NOT be validatable, but the implementation does not enforce it [3](#0-2) . This contradicts the design in `docs/diagrams/06-l1-handler-flow.md`, which states that after commit, rejected txs should be returned to `Pending` state so they can be retried later through the normal cooldown/proposable-index path [1](#0-0)  — instead the code leaves them permanently in the separate `Rejected` state, which `is_validatable()` still treats as valid.

### Impact Explanation
Because `is_validatable()` doesn't exclude `Rejected`, a rejected L1Handler transaction can still pass `validate_tx` in any later block's validation phase (an unprivileged validator/proposer path reachable by any consensus round for a submitted proposal containing that tx hash) and get staged and included in a block via `try_mark_staged` returning `ValidationStatus::Validated` [8](#0-7) . This can cause an L1Handler message to be re-processed/re-included in a block after it was already rejected once, which is a state-machine violation for L1↔L2 messaging (each L1 message is supposed to be handled exactly according to the consumed/committed/rejected lifecycle) and can lead to unauthorized/duplicate account actions or honest-node divergence if some nodes still hold stale index state.

### Likelihood Explanation
The bug is reachable purely through the normal propose/validate flow that every sequencer node executes for every block, without any privileged access — any block containing a previously rejected L1Handler tx hash triggers `validate_tx` and will incorrectly permit revalidation. However, I could not fully verify (due to index/tooling limits) whether `get_txs` (proposal path, gated on `is_proposable()` which only matches `Pending`) would ever actually re-propose a `Rejected` tx, since `is_proposable` correctly excludes `Rejected` [9](#0-8) . The concrete exploitable path is through `validate()` when a byzantine/malicious proposer proposes a block containing an already-rejected tx hash — such a proposal would incorrectly pass validation on all honest validator nodes instead of being rejected, which could cause the network to accept an invalid block or diverge from nodes that (correctly, per intended design) treat rejected txs as non-revalidatable.

### Recommendation
Update `TransactionRecord::is_validatable()` to also exclude `TransactionState::Rejected`, i.e. `!self.is_committed() && !self.is_cancelled() && !self.is_consumed() && !matches!(self.state, TransactionState::Rejected)`, or, per the documented design, actually transition rejected transactions back to `Pending` (and re-index them in the proposable index) instead of introducing a separate terminal `Rejected` state, so that stale-rejected transactions are excluded during validation until they are legitimately retried in a fresh proposal.

### Proof of Concept
1. Batcher builds/commits a block that includes an L1Handler tx `T` in its `rejected_txs` set (e.g. execution failed) → `commit_txs` calls `mark_rejected()` on `T`, setting `state = TransactionState::Rejected` [10](#0-9) .
2. In a later height, a proposer (malicious or simply replaying) proposes a block whose consensus stream re-includes `T`'s hash.
3. During validation, `TxProv` calls `L1EventsProvider::validate(T, height)` → `TransactionManager::validate_tx(T, unix_now)` [11](#0-10) .
4. `record.is_validatable()` returns `true` because `state == Rejected` is not excluded, so `try_mark_staged` succeeds and `ValidationStatus::Validated` is returned, allowing `T` to be re-included in the new block despite being previously rejected [12](#0-11) .

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();
        }
        for &tx_hash in rejected_txs {
            self.with_record(tx_hash, |r| r.mark_rejected()).expect(

                 committed block were validated as known (validation rejects unknown hashes), \
                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",
            );
        }

    pub fn validate(
        &mut self,
        tx_hash: TransactionHash,
        height: BlockNumber,
    ) -> L1EventsProviderResult<ValidationStatus> {
        if self.state.is_uninitialized() {
            return Err(L1EventsProviderError::Uninitialized);
        }

        self.check_height_with_error(height)?;
        match self.state {
            ProviderState::Validate => {
                Ok(self.tx_manager.validate_tx(tx_hash, self.clock.unix_now()))
            }
            _ => Err(L1EventsProviderError::UnexpectedProviderState {
                expected: ProviderState::Validate,
                found: self.state,
            }),
        }
    }

    /// Commit the given transactions, and increment the current height.
    fn apply_commit_block(
        &mut self,
        consumed_txs: IndexSet<TransactionHash>,
        rejected_txs: IndexSet<TransactionHash>,
    ) {
        debug!("Applying commit_block to height: {}", self.current_height);
        let (rejected_and_consumed, committed_txs): (Vec<_>, Vec<_>) =
            consumed_txs.iter().copied().partition(|tx| rejected_txs.contains(tx));
        self.tx_manager.commit_txs(&committed_txs, &rejected_and_consumed);

        self.current_height = self.current_height.unchecked_next();
    }
