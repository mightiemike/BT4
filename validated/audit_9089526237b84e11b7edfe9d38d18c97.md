## Title
Contract-code identity switch (`DeployContract` / `UseGlobalContract`) does not clear or reset account storage, allowing forged contract state across code changes — (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
Analogous to the ink! upgradable-contract bug where a proxy and its implementation both write to the same default storage cell, nearcore scopes all contract key-value storage per-`AccountId` under a single trie namespace (`TrieKey::ContractData { account_id, key }`), independent of which contract code is currently associated with that account. When an account switches its contract code — via `DeployContractAction` or `UseGlobalContractAction` — the runtime only adjusts the account's `storage_usage` byte counter; it never clears, migrates, or validates the pre-existing `ContractData` entries against the new contract's expected storage layout.

### Finding Description
`TrieKey::ContractData` is keyed only by `account_id` and a caller-chosen byte key, with no dependency on the account's current `AccountContract` (`Local`/`Global`/`GlobalByAccount`) identity. [1](#0-0) 

When an account switches contracts, both `action_deploy_contract` and `use_global_contract` call `clear_account_contract_storage_usage`, which only subtracts the byte cost of the *code identifier* (local code length or global identifier length) from `storage_usage`; it never touches the account's `ContractData` rows: [2](#0-1) [3](#0-2) [4](#0-3) 

An account's owner (whose `actor_id` matches, so they may freely call `DeployContract`/`UseGlobalContract` on their own account) can therefore:
1. Deploy an arbitrary local contract on their own account and use it to write crafted byte sequences into `TrieKey::ContractData` at storage keys that match the layout a target contract (e.g., a widely-used global contract implementing a token/ledger) expects for balances, allowances, or ownership flags.
2. Call `UseGlobalContractAction` to switch the account's code to that shared global contract, without ever executing the target contract's real initialization/mint/transfer logic.
3. The target contract, upon being called, reads its "own" storage layout and finds the attacker's forged values already present, because nothing clears or validates the previous tenant's leftover key-value data.

The runtime authors are aware that stale `ContractData` is a real hazard in this exact code path — the deterministic-account initializer explicitly documents (and only relies on) a precondition that the account must have no contract data yet: [5](#0-4) 
That precondition is enforced only because deterministic accounts start fresh and are locked out of `DeployContract`/`UseGlobalContract` by the actor-id restriction: [6](#0-5) 
However, this protection does not extend to ordinary named/implicit accounts, which can freely call `DeployContract` and `UseGlobalContract` repeatedly and are never subjected to any "must not have contract data" check.

This is the direct protocol-level analog of the ink! issue: storage is not partitioned per contract-code-identity, there is no reserved/standard slot scheme, and there is no validation between "upgrades" (contract-identity switches) that the storage layout is unchanged or compatible — exactly the two mitigations (standard storage slots / upgrade validation) the ink! report calls out as missing.

### Impact Explanation
Any account can, by itself, pre-plant storage entries and then adopt a shared/global contract's code so that the contract's storage-dependent logic (balances, allowances, ownership, initialization flags) observes attacker-chosen values it never actually computed or validated. For global contracts referenced by many accounts (`GlobalByAccount`/`CodeHash`) that assume "on first use, my storage is empty/uninitialized," this allows forging internal ledger state — e.g., fabricating a nonzero balance/allowance entry or bypassing an "already initialized" guard — without going through the contract's real minting/transfer/initialization path. Depending on the specific global contract's assumptions, this can translate into unauthorized value creation or bypass of contract-level invariants that other users and off-chain consumers (via RPC/view calls) implicitly trust.

### Likelihood Explanation
Reachable by a single unprivileged account signer sending ordinary `DeployContract` and `UseGlobalContractAction`/`DeployGlobalContractAction` actions against its own account — no validator, network, or privileged access is required. The precondition comment in `deterministic_account_id.rs` shows the nearcore team is already aware that "must not have contract data" is a real invariant that has to be enforced somewhere; it is currently enforced only for the deterministic-account path and not for regular `DeployContract`/`UseGlobalContract` transitions.

### Recommendation
- When an account's `AccountContract` identity changes (`DeployContract`, `UseGlobalContract`, or `DeployGlobalContract` overwriting a previous local contract), clear all existing `TrieKey::ContractData` entries for that account (mirroring the iterate-and-remove logic already used in `remove_account` in `core/store/src/utils/mod.rs`), or otherwise make clear that the new contract must not trust unwritten storage.
- Alternatively/additionally, document and/or enforce that global contracts must treat all storage as adversarial input on first use, and consider adding a documented "clean adoption" mode (analogous to a `cargo contract upgrade`-style check) that rejects `UseGlobalContractAction`/`DeployContractAction` when the account already has non-empty `ContractData`, unless explicitly opted into by the contract/account.

### Proof of Concept
1. Account `alice.near` calls `DeployContractAction` with a trivial WASM that, on `init`, calls `storage_write` to set key `b"balance"` to a large `u128` value at the exact byte layout a target global fungible-token-like contract `token.near` (deployed via `DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId`) uses for its own balance field.
2. `alice.near` calls this crafted contract's `init` method, populating `TrieKey::ContractData { account_id: alice.near, key: b"balance" }` with the forged value — see write path in `deploy_deterministic_account`/general `storage_write` host function, which uses the same `TrieKey::ContractData` regardless of contract identity, per [1](#0-0) .
3. `alice.near` calls `UseGlobalContractAction { contract_identifier: GlobalContractIdentifier::AccountId("token.near") }`. This only runs `use_global_contract`, which subtracts the old code's storage-usage bytes and sets the new `AccountContract::GlobalByAccount` — it never removes `TrieKey::ContractData { alice.near, b"balance" }`, per [4](#0-3) .
4. `alice.near` then calls a normal method on `token.near` (e.g. `transfer`), which reads its "balance" storage key and finds the forged value from step 2 already present, letting `alice.near` move/spend funds it never legitimately received.

pub(crate) fn action_deploy_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    deploy_contract: &DeployContractAction,
    config: Arc<VmConfig>,
    next_config: Option<Arc<VmConfig>>,
    cache: Option<&dyn ContractRuntimeCache>,
) -> Result<(), StorageError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_contract").entered();
    clear_account_contract_storage_usage(state_update, account_id, account)?;

    let code = ContractCode::new(deploy_contract.code.clone(), None);
    account.set_storage_usage(
        account.storage_usage().checked_add(code.code().len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(AccountContract::Local(*code.hash())).or_inconsistent_state(account_id)?;
    // Legacy: populate the mapping from `AccountId => sha256(code)` thus making contracts part of
    // The State. For the time being we are also relying on the `TrieUpdate` to actually write the
    // contracts into the storage as part of the commit routine, however no code should be relying
    // that the contracts are written to The State.
    state_update.set_code(account_id.clone(), &code);
    // Precompile the contract under the current `wasm_config`. If a protocol upgrade with a
    // different `wasm_config` is scheduled for the next epoch, also schedule a fire-and-forget
    // warming compile under the new config so the on-disk cache is hot at the boundary.
    // Note: contract compilation costs are already accounted in deploy cost using special logic
    // in estimator (see get_runtime_config() function).
    precompile_contract_with_warming(&code, config, next_config, cache);
    // Inform the `store::contract::Storage` about the new deploy (so that the `get` method can
    // return the contract before the contract is written out to the underlying storage as part of
    // the `TrieUpdate` commit.)
    state_update.record_contract_deploy(code);
    Ok(())
}

pub(crate) fn clear_account_contract_storage_usage(
    state_update: &TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
) -> Result<(), StorageError> {
    let contract_storage = get_contract_storage_usage(state_update, account_id, account)?;
    account.set_storage_usage(account.storage_usage().saturating_sub(contract_storage));
    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}
