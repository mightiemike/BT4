## Finding [1](#0-0) 

### Title
Wallet Contract pays relayer fee unconditionally before validating transaction success, enabling unbounded balance drain via nonce-replay of the address-registrar check path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's `inner_rlp_execute` dispatches the relayer's `fee` refund promise as soon as the Ethereum transaction is *parsed*, without checking (or making the transfer contingent on) whether the underlying action ultimately succeeds. For the `EOABaseTokenTransfer{ address_check: Some(address), .. }` case, the nonce is also deliberately *not* incremented at this point, deferring both the nonce bump and the success determination to `address_check_callback`. However, if the address-registrar lookup later reveals that a named account exists for that address (the "faulty relayer" branch), the contract only bans the relayer's access key when `env::signer_account_id() == current_account_id`; it never increments the nonce and never claws back the fee that was already paid out in `inner_rlp_execute`.

### Finding Description
In `inner_rlp_execute`: [1](#0-0) 

- Nonce increment is skipped specifically for `EOABaseTokenTransfer{ address_check: Some(_), .. }` (lines 358-365), with the increment deferred into `address_check_callback`.
- The relayer fee transfer (`env::promise_batch_action_transfer(refund_promise, *fee)`) is dispatched unconditionally for any `EOABaseTokenTransfer`/`ERC20Transfer` with a non-zero fee (lines 374-385) — **before** the address-registrar lookup, and before the actual action (`ft_transfer`/`Transfer`) is even attempted.

In `address_check_callback`: [2](#0-1) 

- If the registrar lookup returns `Some(account_id)` (i.e. a named account is already registered for that address, meaning the relayer/caller should have used it as `target` instead of the raw eth-implicit account), the code either bans the relayer (only if `signer_account_id == current_account_id`, i.e. it holds a wallet-issued access key) or simply returns a failure response — in neither branch is `self.nonce` incremented.
- The nonce is only incremented in the `else` branch (registrar returns `None`), i.e. only on the "honest" success path.

Because `validate_tx_relayer_data` (in `internal.rs`) accepts `target` as long as it hashes to `tx.to` — the raw eth-implicit account name is a *valid* target from the protocol's point of view even when a named account is registered — a caller can deliberately submit `target` as the raw eth-implicit account for a transaction whose address is registered. This deterministically routes into `address_check_callback`'s "faulty relayer" branch, where:
1. The nonce is never advanced, so `validate_tx_relayer_data`'s nonce check (`nonce != expected_nonce`) never rejects a replay of the exact same signed transaction.
2. The `fee` refund transfer to the caller has already executed in `inner_rlp_execute`, unconditionally, for every single invocation — regardless of the eventual "Error: faulty relayer" outcome.

Combining these two facts, the same signed Ethereum transaction (crafted with the wrong-but-hash-valid `target`) can be resubmitted indefinitely by any caller, each time draining `fee` yoctoNEAR from the wallet contract's own balance, with no compensating mechanism to stop it (no ban applies when the caller is not using a wallet-issued access key, as explicitly acknowledged in the code comments in `error.rs` and `inner_rlp_execute`).

### Impact Explanation
This is a concrete unauthorized value movement out of the Wallet Contract's NEAR balance. An attacker who obtains (or is entrusted with relaying) a user's signed Ethereum transaction targeting a registered eth-implicit address can repeatedly resubmit it with the "wrong" (but protocol-valid) target, draining the `fee` amount every time instead of once, with no nonce advancement and no ban for non-access-key callers. Depending on how large a fee the user attached (bounded by `max_fee_per_gas * gas_limit`, capped at `VALUE_MAX`), this can meaningfully drain the wallet's balance over repeated calls, and there is no automatic recovery — this is a real balance-draining exploit reachable by an ordinary transaction/meta-transaction submitter.

### Likelihood Explanation
The attack requires knowledge of a validly-signed Ethereum transaction (which is, by design, meant to be shared with arbitrary relayers/RPC callers to submit on the user's behalf) targeting an eth-implicit address that has since been registered under a named account in the address registrar. Any external caller (no special privileges, no access key needed) can trigger this by simply choosing `target` = the raw eth-implicit account instead of doing the registrar lookup themselves, and then repeat the same call.

### Recommendation
- Do not dispatch the relayer `fee` refund until the underlying action's success (or at least the address-check outcome) is confirmed — chain the fee transfer as part of (or dependent on) the final callback result rather than firing it eagerly in `inner_rlp_execute`.
- Always increment (or otherwise permanently invalidate) the nonce as soon as the "faulty relayer / existing named account" outcome is determined in `address_check_callback`, regardless of whether the caller holds an access key, so the same signed transaction cannot be replayed to repeatedly collect the fee.
- Alternatively, refund/claw back the previously paid fee when the address-check ultimately fails.

### Proof of Concept
1. User signs an Ethereum transaction (via the Wallet Contract's ECDSA key) with `max_fee_per_gas`/`gas_limit` producing a non-zero `fee`, targeting an address `A` that will later be registered in the address registrar under some named account `N`.
2. Attacker (any account, not necessarily holding a wallet access key) calls `rlp_execute(target = "0x{A}{suffix}", tx_bytes_b64 = <signed tx>)`.
3. `parse_rlp_tx_to_action` succeeds with `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer{ address_check: Some(A), fee })`; nonce is NOT incremented (`lib.rs:358-365`); `fee` is transferred to the attacker unconditionally (`lib.rs:374-385`).
4. `address_check_callback` looks up `A` in the registrar, finds `Some(N)`, and since attacker is not the signer, returns `ExecuteResponse{ success: false, error: "Error: faulty relayer" }` without incrementing `self.nonce` (`lib.rs:160-178`).
5. Attacker repeats step 2 with the identical `tx_bytes_b64`/nonce; because `self.nonce` was never advanced, `validate_tx_relayer_data`'s nonce check passes again, and step 3's fee transfer fires again.
6. Steps 2-5 can be repeated indefinitely, draining `fee` from the wallet's balance on each call.
