### Title
Unbounded, uncapped delegatee/delegator index growth in `DelegatedResourceAccountIndexStore` enables read amplification via `getIndex`/`getV2Index` - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore.delegate`/`delegateV2` store one row per distinct `(owner, receiver)` pair, and neither `FreezeBalanceActuator`, `DelegateResourceActuator`, nor the store itself imposes any cap on the number of distinct receivers/delegators an address can accumulate. `getIndex`/`getV2Index` do an unbounded `prefixQuery` + in-memory sort over all rows for an address, and this is exposed unauthenticated via `GetDelegatedResourceAccountIndexServlet`/`GetDelegatedResourceAccountIndexV2Servlet` and gRPC. However, the exploit is materially more expensive than the question assumes: each new row requires a *distinct, already-existing, non-contract* receiver account and locks real, non-reusable stake (minimum 1 TRX per receiver, cumulative), not a single reusable 1 TRX.

### Finding Description
- `DelegatedResourceAccountIndexStore.delegate`/`delegateV2` write keys `FROM_PREFIX|owner|receiver` and `TO_PREFIX|receiver|owner` (or the V2 equivalents) [1](#0-0) . Because the key includes both `owner` and `receiver`, a new row is only created when a **new distinct receiver** is used; repeated delegations to the same receiver just overwrite the existing row.
- `getIndex`/`getV2Index` call `getWithPrefix`, which does a `prefixQuery` over `FROM_PREFIX+address` and `TO_PREFIX+address` (or V2), collects **all** matching rows into lists, and sorts them by timestamp before returning [2](#0-1) . This work is proportional to the number of accumulated rows for the queried address, with no limit, pagination, or cap.
- These reads are reachable through unauthenticated HTTP endpoints (`GetDelegatedResourceAccountIndexServlet`, `GetDelegatedResourceAccountIndexV2Servlet`) and gRPC (`RpcApiService`), so **any RPC caller**, not just the attacker, pays the cost of querying a bloated address [3](#0-2) .
- To grow the row count for one address, `DelegateResourceActuator.execute`/`validate` is reachable by any funded account: it requires a valid, non-contract, **already-existing** receiver account (`accountStore.get(receiverAddress) != null`, `receiverCapsule.getType() != Contract`) and `delegateBalance >= 1 TRX` [4](#0-3) . `FreezeBalanceActuator.delegateResource` (legacy path, gated by `!supportAllowDelegateOptimization()`) similarly grows `toAccountsList`/`fromAccountsList` per distinct receiver [5](#0-4) .
- There is genuinely **no cap** anywhere in the code on the number of distinct delegatees/delegators per address, and `MaxDelegateLockPeriod` only bounds lock *duration*, not delegatee *count* [6](#0-5) .

### Impact Explanation
This maps to a **DoS via RPC-API / protocol implementation** class: a funded attacker can inflate the delegation index for a target address (their own or, since delegation requires no receiver consent, an existing victim address as receiver/from), causing every subsequent `getIndex`/`getV2Index`/`GetDelegatedResourceAccountIndex(V2)` call against that address to do a large unbounded scan+sort, imposing CPU/IO/memory cost on every node serving that query. Because the endpoints are exposed on public HTTP/gRPC APIs, all RPC clients querying the affected address inherit this cost. This is real amplification (cheap-ish write, unbounded read) but bounded in practice by real economic cost (see below) and is not a "critical" primitive - more of a moderate resource-exhaustion/availability degradation vector, and it does not corrupt state, steal funds, or affect consensus.

### Likelihood Explanation
The question's framing ("minimum 1 TRX equivalent," "each individually cheap") understates the real cost:
- Each new distinct row requires a **new, distinct, already-existing, non-contract receiver account** — the attacker cannot fabricate arbitrary receivers; they must either harvest N distinct pre-existing addresses from the live chain, or first create/fund N accounts (extra cost).
- Delegated balance is **not reusable across distinct receivers** — `delegateBalance` is deducted from the owner's `FrozenV2Balance` pool and locked per-receiver in `DelegatedFrozenV2Balance`, so building 50,000 distinct rows requires the attacker to have **cumulatively frozen/staked at least 50,000 TRX**, only recoverable later via `UnDelegateResourceContract`/unfreeze after the unfreeze delay. This is a real (if temporary, non-burned) capital lockup of tens of thousands of TRX, not "individually cheap" 1-TRX transactions in the way implied.
- Each of the 50,000 transactions also consumes real bandwidth/energy or TRX-burn fees at scale, and requires the attacker to identify 50,000 distinct valid receiver addresses.
- No signature/permission checks are bypassed; this is a resource-cost/design gap rather than a logic flaw, and the amplification factor, while real, is throttled by the capital and transaction-count requirements above.

Given these substantial (if not prohibitive) preconditions, the finding is a legitimate but **moderate-severity, cost-gated** DoS/availability concern rather than a "cheap-write/expensive-read" critical primitive as originally framed.

### Recommendation
- Add an explicit per-address cap on the number of distinct `toAccounts`/`fromAccounts` (or V2 from/to prefix rows) an address may accumulate in `DelegatedResourceAccountIndexStore`/`DelegateResourceActuator.validate()` / `FreezeBalanceActuator.validate()`, rejecting further delegations beyond the cap.
- Add pagination/limits to `getIndex`/`getV2Index` and the corresponding HTTP/gRPC endpoints so a single query cannot force an unbounded scan/sort.
- Consider bounding `prefixQuery` result iteration with a hard limit and returning a "results truncated" indicator, defended by cost metering on both write (grows fee with delegatee count) and read paths.

### Proof of Concept
Conceptual JUnit outline (cost accounting must be added; existing tests only prove one row per receiver, not cost/DoS):
```java
// Setup: fund attacker with 50_000 TRX and freeze it as bandwidth V2 balance.
// For i in 0..50_000: pick distinct existing receiver_i (harvested from chain state),
// broadcast DelegateResourceContract(owner=attacker, receiver=receiver_i, balance=1_000_000 (1 TRX)).
// Each call succeeds (DelegateResourceActuator.validate/execute), consuming 1 TRX
// from attacker's available FrozenV2Balance pool each time (cumulative cost = 50_000 TRX locked).
//
// After all 50_000 delegations:
DelegatedResourceAccountIndexCapsule idx =
    delegatedResourceAccountIndexStore.getV2Index(attackerAddress);
assertEquals(50_000, idx.getToAccountsList().size());
// Measure wall-clock time of getV2Index() before/after -> demonstrates read-time growth
// proportional to N, exposed via GetDelegatedResourceAccountIndexV2Servlet/RpcApiService
// to any unauthenticated caller querying `attackerAddress`.
```
Note: This PoC requires 50,000 distinct pre-existing receiver addresses and cumulative 50,000 TRX in frozen stake from the attacker — this capital/account requirement (not verifiable purely from static code without a live chain state) is the key economic gate on feasibility that the original question's "cheap write" premise omits.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
