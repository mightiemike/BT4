### Title
Unbounded linear scan for entry point resolution instead of leveraging sort order - ([File: crates/blockifier/src/execution/contract_class.rs], [File: crates/blockifier/src/execution/deprecated_entry_point_execution.rs])

### Summary
`EntryPointsByType::get_entry_point` and `resolve_entry_point_pc` in the blockifier resolve the entry point to execute for every single call (external invocation, internal `call_contract`/`library_call`, constructor, or L1 handler) by doing a native Rust `O(n)` linear `.iter().filter(...)` scan over the full `entry_points_of_same_type` vector, rather than exploiting the fact that entry points are sorted (as validated at declare time) to do a binary search.

### Finding Description
`EntryPointsByType::get_entry_point` performs a full linear filter over all entry points of the relevant type on every call: [1](#0-0) 

The deprecated (Cairo0) path does the same thing in `resolve_entry_point_pc`: [2](#0-1) 

This is directly analogous to the reported bug class: iterating an array to find a match instead of using an efficient lookup. Notably, the Starknet OS (Cairo) side of the exact same lookup already does this correctly with a binary search, using `search_sorted_optimistic`: [3](#0-2) 

The blockifier (native sequencer execution) code does not mirror this optimization and instead re-scans the entire entry-point list from scratch on every call, even though entry points are guaranteed sorted and unique for declared Sierra classes via `validate_entry_points_sorted_and_unique`: [4](#0-3) 

Because this scan happens in native Rust code before/around Cairo VM step execution, its CPU cost is not represented by Cairo VM step counting the way computation inside the VM is. A transaction sender can declare a contract class with a very large number of entry points of one type (bounded only by `max_contract_class_object_size`/`max_contract_bytecode_size`, which can still admit many thousands of entries), and then trigger many calls into that contract within a single transaction (e.g., via recursive/looped internal calls), forcing the sequencer to repeatedly perform this unmetered `O(n)` scan.

### Impact Explanation
This does not directly cause loss of funds or state corruption, but it is a resource-accounting mismatch: the fee charged to the transaction sender for gas/steps does not proportionally reflect the actual CPU cost consumed by the sequencer's native entry-point resolution loop for large contracts with many entry points, called repeatedly. This can degrade sequencer/validator block-building and re-execution performance disproportionately to the resources actually billed, which is a resource/DoS-class concern rather than a fund-loss or consensus-divergence issue.

### Likelihood Explanation
Likelihood is low-to-moderate: an attacker needs a declared class with a large number of entry points and needs to invoke calls into it many times inside one or few transactions to accumulate meaningful overhead; the number of entry points is still bounded by the class size limits, and per-call resolution overhead is small (microseconds) relative to a single scan, requiring an extreme number of entry points combined with many repeated calls to be materially impactful. No overflow, panic, or freezing of funds results, and existing block/step-count gas bounds and bouncer weight limits (`crates/blockifier/src/bouncer.rs`) still cap overall block execution, limiting the blast radius.

### Recommendation
Since `EntryPointsByType` is validated to be sorted and unique for declared Sierra classes at the gateway (`validate_entry_points_sorted_and_unique`), the blockifier's native `get_entry_point`/`resolve_entry_point_pc` lookups should use a binary search (`binary_search_by_key` on the selector) instead of `.iter().filter(...)`, mirroring the Cairo OS's `search_sorted_optimistic` approach, to bring native-side lookup complexity down to `O(log n)` and make its cost proportional to what is effectively charged.

### Proof of Concept
Not applicable as a fund-loss/freeze exploit; the concern is a resource-accounting/performance gap in `EntryPointsByType::get_entry_point` (crates/blockifier/src/execution/contract_class.rs:788-809) and `resolve_entry_point_pc` (crates/blockifier/src/execution/deprecated_entry_point_execution.rs:120-166), which can be demonstrated by declaring a class with a maximal number of entry points of one type and benchmarking repeated-call latency versus a small-entry-point-count class of similar total size.

    pub fn get_entry_point(
        &self,
        entry_point: &EntryPointTypeAndSelector,
    ) -> Result<EP, PreExecutionError> {
        entry_point.verify_constructor()?;

        let entry_points_of_same_type = &self[entry_point.entry_point_type];
        let filtered_entry_points: Vec<_> = entry_points_of_same_type
            .iter()
            .filter(|ep| *ep.selector() == entry_point.entry_point_selector)
            .collect();

        match filtered_entry_points[..] {
            [] => Err(PreExecutionError::EntryPointNotFound(entry_point.entry_point_selector)),
            [entry_point] => Ok(entry_point.clone()),
            _ => Err(PreExecutionError::DuplicatedEntryPointSelector {
                selector: entry_point.entry_point_selector,
                typ: entry_point.entry_point_type,
            }),
        }
    }

pub fn resolve_entry_point_pc(
    call: &ExecutableCallEntryPoint,
    compiled_class: &CompiledClassV0,
) -> Result<usize, PreExecutionError> {
    if call.entry_point_type == EntryPointType::Constructor
        && call.entry_point_selector != selector_from_name(CONSTRUCTOR_ENTRY_POINT_NAME)
    {
        return Err(PreExecutionError::InvalidConstructorEntryPointName);
    }

    let entry_points_of_same_type = &compiled_class.entry_points_by_type[&call.entry_point_type];
    let filtered_entry_points: Vec<_> = entry_points_of_same_type
        .iter()
        .filter(|ep| ep.selector == call.entry_point_selector)
        .collect();

    // Returns the default entrypoint if the given selector is missing.
    if filtered_entry_points.is_empty() {
        match entry_points_of_same_type.first() {
            Some(entry_point) => {
                if entry_point.selector
                    == EntryPointSelector(StarkHash::from(DEFAULT_ENTRY_POINT_SELECTOR))
                {
                    return Ok(entry_point.offset.0);
                } else {
                    return Err(PreExecutionError::EntryPointNotFound(call.entry_point_selector));
                }
            }
            None => {
                return Err(PreExecutionError::NoEntryPointOfTypeFound(call.entry_point_type));
            }
        }
    }

    if filtered_entry_points.len() > 1 {
        return Err(PreExecutionError::DuplicatedEntryPointSelector {
            selector: call.entry_point_selector,
            typ: call.entry_point_type,
        });
    }

    // Filtered entry points contain exactly one element.
    let entry_point = filtered_entry_points
        .first()
        .expect("The number of entry points with the given selector is exactly one.");
    Ok(entry_point.offset.0)
}

// Returns the CompiledClassEntryPoint, based on 'compiled_class' and 'execution_context'.
func get_entry_point{range_check_ptr}(
    compiled_class: CompiledClass*, execution_context: ExecutionContext*
) -> (success: felt, entry_point: CompiledClassEntryPoint*) {
    alloc_locals;
    // Get the entry points corresponding to the transaction's type.
    local entry_points: CompiledClassEntryPoint*;
    local n_entry_points: felt;

    tempvar entry_point_type = execution_context.entry_point_type;
    if (entry_point_type == ENTRY_POINT_TYPE_L1_HANDLER) {
        entry_points = compiled_class.l1_handlers;
        n_entry_points = compiled_class.n_l1_handlers;
    } else {
        if (entry_point_type == ENTRY_POINT_TYPE_EXTERNAL) {
            entry_points = compiled_class.external_functions;
            n_entry_points = compiled_class.n_external_functions;
        } else {
            assert entry_point_type = ENTRY_POINT_TYPE_CONSTRUCTOR;
            entry_points = compiled_class.constructors;
            n_entry_points = compiled_class.n_constructors;

            if (n_entry_points == 0) {
                return (success=1, entry_point=cast(0, CompiledClassEntryPoint*));
            }
        }
    }

    // The key must be at offset 0.
    static_assert CompiledClassEntryPoint.selector == 0;
    // TODO(Yoni, 1/1/2026): make sure the cost of searching missing keys is covered
    //   once reverted entrypoints are supported in the OS (should be fine).
    let (entry_point_desc: CompiledClassEntryPoint*, success) = search_sorted_optimistic(
        array_ptr=cast(entry_points, felt*),
        elm_size=CompiledClassEntryPoint.SIZE,
        n_elms=n_entry_points,
        key=execution_context.execution_info.selector,
    );
    if (success != FALSE) {
        return (success=1, entry_point=entry_point_desc);
    }

    return (success=0, entry_point=cast(0, CompiledClassEntryPoint*));
}

    fn validate_entry_points_sorted_and_unique(
        &self,
        contract_class: &starknet_api::state::SierraContractClass,
    ) -> StatelessTransactionValidatorResult<()> {
        let is_sorted_unique = |entry_points: &[EntryPoint]| {
            entry_points.windows(2).all(|pair| pair[0].selector < pair[1].selector)
        };

        if is_sorted_unique(&contract_class.entry_points_by_type.constructor)
            && is_sorted_unique(&contract_class.entry_points_by_type.external)
            && is_sorted_unique(&contract_class.entry_points_by_type.l1handler)
        {
            return Ok(());
        }

        Err(StatelessTransactionValidatorError::EntryPointsNotUniquelySorted)
    }
}
