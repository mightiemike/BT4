### Title
Unhandled `NumberFormatException` in `JsonRpcApiUtil.triggerCallContract` on malformed `tokenId` - (File: framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcApiUtil.java)

### Summary
`JsonRpcApiUtil.triggerCallContract` parses a caller-supplied `tokenId` string directly with `Long.parseLong(tokenId)` with no validation or try/catch, mirroring the reported `MustNewDecFromString` bug class (unchecked numeric string parsing on untrusted input that can panic/throw and is not gracefully handled).

### Finding Description
`triggerCallContract` builds a `TriggerSmartContract` for JSON-RPC calls (`eth_call`/`eth_sendTransaction`-style TRC10 token id parameter) and does:
```java
if (StringUtils.isNotEmpty(tokenId)) {
  builder.setCallTokenValue(tokenValue);
  builder.setTokenId(Long.parseLong(tokenId));
}
``` [1](#0-0) 
There is no format validation of `tokenId` before parsing, and no try/catch around `Long.parseLong`, so any non-numeric string will throw an uncaught `NumberFormatException`. This is the same bug class as the reported `MustNewDecFromString` panic on unchecked input.

By contrast, other numeric-string entry points in the same class (`parseQuantityValue`, `parseBlockNumber`, `parseTxIndex`) explicitly wrap parsing in try/catch and convert failures into a `JsonRpcInvalidParamsException` [2](#0-1) [3](#0-2) , showing this is the established defensive pattern that `triggerCallContract` does not follow.

I located the call sites in `TronJsonRpcImpl.java` (3 matches) but was not able to fully confirm within the available context whether the JSON-RPC dispatcher wraps calls to this method in a top-level try/catch that would convert an uncaught `NumberFormatException` into a JSON-RPC error response versus propagating it into a server error / thread disruption. Without confirming that boundary, I cannot assert with certainty that this results in a node crash rather than a caught HTTP/RPC-level 500 error.

### Impact Explanation
If the exception is not caught by a wrapping handler, an unprivileged JSON-RPC client could send a malformed `tokenId` value to cause an uncaught runtime exception in request-handling code, which is analogous to the reported denial-of-service class ("invalid params → panic/crash"). If it is caught by an outer handler (as is common in HTTP/RPC frameworks), the impact is reduced to a benign error response rather than a node crash.

### Likelihood Explanation
The `tokenId` field is fully attacker-controlled from an unprivileged JSON-RPC caller with no upstream format validation, so triggering the parse failure is trivial (any non-numeric string).

### Recommendation
Wrap the `Long.parseLong(tokenId)` call in a try/catch, or validate the string as numeric first, returning a `JsonRpcInvalidParamsException` (consistent with the pattern already used in `parseQuantityValue`/`parseBlockNumber`/`parseTxIndex`) instead of letting `NumberFormatException` propagate unchecked.
