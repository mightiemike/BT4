### Title
Exchange balance overflow bypasses `ExchangeBalanceLimit` check when `allowHardenExchangeCalculation` is disabled - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator.doValidate` and `ExchangeInjectActuator.execute` both call `addExact`/`subtractExact` methods that are overridden by `AbstractExchangeActuator` to conditionally fall back to raw, unchecked `x + y` / `x - y` arithmetic whenever the dynamic chain parameter `allowHardenExchangeCalculation` is not enabled. Because Java resolves the overridden methods at runtime (not the checked `Maths.addExact`/`Maths.subtractExact` from `AbstractActuator`), the "conservation" invariant that the code appears to enforce via `addExact`/`subtractExact` is silently bypassed under that (default-off, proposal-gated) configuration, allowing an attacker to overflow `firstTokenBalance`/`secondTokenBalance` past `getExchangeBalanceLimit()` and corrupt the exchange's stored balances.

### Finding Description
`AbstractActuator` defines checked-math helpers (`addExact`, `subtractExact`, `multiplyExact`, `floorDiv`) that delegate to `Maths.*` and are meant to always detect overflow/underflow: [1](#0-0) 

However, `AbstractExchangeActuator` (the direct superclass of `ExchangeInjectActuator`) overrides `addExact` and `subtractExact` with a version that only performs the checked (`StrictMathWrapper`) arithmetic when `allowHarden()` (i.e. `dynamicStore.allowHardenExchangeCalculation()`) is true; otherwise it silently falls back to plain, unchecked `x - y` / `x + y`: [2](#0-1) 

Because Java virtual dispatch resolves `this.addExact(...)` / `this.subtractExact(...)` calls in `ExchangeInjectActuator` to this overridden version (not the parent's `Maths`-based one), every balance-affecting arithmetic operation in both `doValidate` and `execute` inherits this conditional bypass:
- `doValidate` computes `newTokenBalance`/`newAnotherTokenBalance` via `addExact(firstTokenBalance, tokenQuant)` etc. and then checks them against `dynamicStore.getExchangeBalanceLimit()`: [3](#0-2) 
- `execute` performs the same unchecked `addExact`/`subtractExact` calls to update `exchangeCapsule` balances and the owner's account balance: [4](#0-3) 

If `allowHardenExchangeCalculation` is not activated (a proposal/parameter that must be turned on by the committee; it is not attacker-controlled but its off state is the normal pre-activation default), an unprivileged attacker who is the creator of an exchange can supply a `tokenQuant` close to `Long.MAX_VALUE` (while separately holding a self-issued TRC10 asset with a correspondingly large total supply, or leveraging a very small existing pool balance) so that `firstTokenBalance + tokenQuant` (or the analogous second-token sum) wraps around to a negative `long`. A negative `newTokenBalance` trivially satisfies `newTokenBalance > balanceLimit` as false, bypassing the intended limit check, and the same wrapped value is then persisted into the `ExchangeCapsule` in `execute`, corrupting the exchange's on-chain balance bookkeeping (negative/garbage balances), which in turn corrupts subsequent price/quant computations for `ExchangeTransactionActuator` and other exchange interactions.

### Impact Explanation
This breaks the stated invariant "balances and supply never underflow or exceed issuance," directly causing asset/accounting corruption in the exchange subsystem: exchange pool balances can be forced negative or wrapped, invalidating price calculations and potentially enabling further value extraction through follow-up trades against the corrupted pool. This matches the "Asset/accounting corruption (Critical)" impact class.

### Likelihood Explanation
The attack requires: (1) the attacker to be the creator of the exchange (achievable unprivileged via `ExchangeCreateContract`), (2) an asset/TRX quantity large enough to approach `Long.MAX_VALUE` to trigger overflow (feasible if the attacker self-issues a TRC10 asset with a very large total supply, which is not restricted by an issuance cap beyond overflow checks elsewhere), and (3) critically, the chain-level dynamic parameter `allowHardenExchangeCalculation` must not be active. This last condition is chain-state dependent and not attacker-controlled — I could not verify from the available code/index whether this parameter is currently activated on any specific deployed network (mainnet/testnet/private chain) derived from this repository snapshot. If the parameter has already been activated network-wide, this specific bypass is not exploitable; if it has not (e.g., a private or newly bootstrapped chain, or prior to the corresponding hard fork), the vector is fully exploitable by any funded, unprivileged account.

### Recommendation
Remove the `allowHarden()`/`allowHardenExchangeCalculation` conditional fallback in `AbstractExchangeActuator.addExact`/`subtractExact` (or make the checked path unconditional/always-on), so `ExchangeInjectActuator` (and other exchange actuators inheriting from `AbstractExchangeActuator`) always use overflow-checked arithmetic regardless of chain-parameter activation state, matching the intended behavior of `AbstractActuator`'s `Maths`-based helpers.

### Proof of Concept
```java
// Pseudocode JUnit sketch (requires access to a test ChainBaseManager with
// dynamicStore.allowHardenExchangeCalculation() == false, the default/non-activated state):

// 1. Attacker account creates a TRC10 asset with total supply near Long.MAX_VALUE.
// 2. Attacker creates an Exchange pairing that asset with TRX, with a small firstTokenBalance.
// 3. Attacker broadcasts ExchangeInjectContract with tokenQuant chosen such that
//    firstTokenBalance + tokenQuant overflows a signed long (wraps negative).
ExchangeInjectContract contract = ExchangeInjectContract.newBuilder()
    .setOwnerAddress(attackerAddress)
    .setExchangeId(exchangeId)
    .setTokenId(ByteString.copyFrom(attackerAssetId))
    .setQuant(Long.MAX_VALUE - firstTokenBalance + 1) // engineered overflow
    .build();

ExchangeInjectActuator actuator = new ExchangeInjectActuator();
// ... set any/contract/chainBaseManager ...
actuator.validate();  // Expected (buggy): passes because newTokenBalance wraps negative,
                       // "newTokenBalance > balanceLimit" evaluates false.
actuator.execute(retCapsule);

ExchangeCapsule after = exchangeStore.get(ByteArray.fromLong(exchangeId));
// Assert conservation violation:
assertTrue(after.getFirstTokenBalance() < 0 || after.getFirstTokenBalance() > balanceLimit);
```
Expected result under the flawed configuration: `doValidate` does not throw despite the arithmetic overflow, and `execute` persists a wrapped/negative balance into `ExchangeCapsule`, violating the conservation invariant.
