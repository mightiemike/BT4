### Title
Zero-weight reward set makes `verify_signer_signatures` accept a Nakamoto block with no signer signatures - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures` guards signer authentication with the same "empty-list short-circuit" pattern as the Camel `KeycloakSecurityPolicy` bug: it only rejects a `None` signer set, but never checks that the *effective* (non-`None`) signer set actually carries any weight. When `RewardSet::signers()` returns `Some(&vec![])` (or a set whose total weight sums to `0`), the approval threshold computed from that weight is also `0`, so the loop that verifies signatures is trivially satisfied by zero signatures, and the block is accepted as validly signed.

### Finding Description
`verify_signer_signatures` only bails out when `reward_set.signers()` is `None`: [1](#0-0) 

It never checks whether the returned `Vec<NakamotoSignerEntry>` is non-empty or whether its summed weight is non-zero. The threshold is then derived directly from that (possibly zero) total weight: [2](#0-1) [3](#0-2) 

`compute_voting_weight_threshold(0)` returns `0` (`0 * 7 / 10 = 0`, no remainder), so `total_weight_signed (0) < threshold (0)` is `false`, and the function returns `Ok(0)` — i.e., success — for a block whose `signer_signature` vector is empty.

The `Some(&vec![])` state is reachable through the normal reward-set construction path, not just theoretically: `StacksChainState::make_signer_set` filters signer entries by `weight == 0` after dividing stacked amounts by the per-slot threshold: [4](#0-3) 

If `entries` is non-empty and every entry carries a `signer` key (`expects_signing_keys == true`, so the function does not return `None` at line 1035-1037) but every computed `weight` rounds down to `0` (e.g. very low stacked-amount-to-threshold ratios in a given reward cycle), the function returns `Some(vec![])` — a signer set that is present but empty of weight. This is exactly the "documented basic setup" analog to the CVE: the presence check (`is_none()`/`entries.first()`) passes, but the actual weight-bearing verification path is never exercised because the set is empty.

The equality that should hold — *a Nakamoto block is valid only if signers holding ≥70% of the registered voting weight signed it* — is broken: with an empty/zero-weight effective signer set, **any** block (including one with zero signer signatures) satisfies `total_weight_signed >= threshold` because both sides degenerate to `0`.

### Impact Explanation
This breaks block-acceptance consensus at its root: `verify_signer_signatures` is the sole function (per `stackslib/src/chainstate/nakamoto/mod.rs`) that decides whether a Nakamoto block carries sufficient signer authorization. If any node computes (or is fed) a reward set with `Some(vec![])`/zero total weight for a cycle, that node would accept a block with **no signer signatures at all** as valid, while a node that treats an empty/zero-weight signer set as an error (as several other call sites already do explicitly, e.g. `StackerDBListener::new` at `stacks-node/src/nakamoto_node/stackerdb_listener.rs:208-225`, `get_signers_weights` at `stackslib/src/chainstate/nakamoto/signer_set.rs:1137-1143`) would reject it. This produces divergent verdicts on the same block across nodes — a chain split / non-reproducible acceptance — and if a miner exploits it, an unsigned/unauthorized block would be accepted network-wide by nodes hitting this code path, i.e., an invalid block accepted, satisfying the Critical impact bar (invalid block accepted network-wide / chain split).

### Likelihood Explanation
Triggering requires the active reward cycle's signer set to have total weight `0` while `signers()` is `Some` rather than `None` — this depends on the PoX stacking/threshold arithmetic in `make_signer_set` producing an all-zero-weight, non-empty signer set for a given cycle (e.g., extremely low or fragmented stacking participation for that cycle, well within the range of naturally occurring or attacker-influenced-but-unprivileged PoX activity, since anyone can choose not to stack or stack in a way that rounds their weight to zero). No majority coalition, admin key, or privileged access is required — it depends only on aggregate stacking behavior in a reward cycle, which is influenced by ordinary unprivileged participants/non-participants. This is a lower-probability, configuration-dependent edge case compared to a always-reachable bug, but the underlying code path performs no defensive check, unlike sibling call sites that already do.

### Recommendation
In `verify_signer_signatures` (and in `RewardSet::total_signing_weight`), explicitly reject reward sets whose signer list is empty or whose total weight is `0`, mirroring the defensive checks already present in `StackerDBListener::new` and `NakamotoStacksBlockBuilder::get_signers_weights`. Concretely: after obtaining `signers`, check `signers.is_empty()` and return `ChainstateError::NoRegisteredSigners`/`InvalidStacksBlock` before computing `total_weight`/`threshold`; likewise, `compute_voting_weight_threshold` should treat `total_weight == 0` as an error rather than silently returning `0`.

### Proof of Concept
1. Construct (or naturally encounter) a reward cycle where `RawRewardSetEntry` inputs to `make_reward_set`/`make_signer_set` all carry a `signer` key but each entry's `amount_stacked / threshold` computes to `0` (e.g. many small stackers under a high per-slot threshold). `make_signer_set` returns `Some(vec![])` (not `None`), since the "no signing keys" early return only fires when `entries.first().signer.is_none()`.
2. This `RewardSet` (with `signers = Some(vec![])`) becomes the active reward set used to validate blocks in that cycle.
3. A miner constructs a `NakamotoBlock` whose header has `signer_signature = vec![]` (no signer approvals at all).
4. Call `header.verify_signer_signatures(&reward_set, epoch_id)`:
   - `signers` is `Some(&vec![])` → passes the `None` check.
   - `total_weight = reward_set.total_signing_weight()` → `0`.
   - `compute_voting_weight_threshold(0)` → `0`.
   - Loop over `self.signer_signature` (empty) → `total_weight_signed = 0`.
   - `0 < 0` is `false` → function returns `Ok(0)`.
5. The block is treated as validly signer-approved despite having zero signatures, while any node/tooling that separately checks `signers.is_empty()` (as several other subsystems in this codebase already do) would reject the same block — producing a consensus divergence on this block's validity.

    pub fn make_signer_set(
        threshold: u128,
        entries: &[RawRewardSetEntry],
    ) -> Option<Vec<NakamotoSignerEntry>> {
        let Some(first_entry) = entries.first() else {
            // entries is empty: there's no signer set
            return None;
        };
        // signing keys must be all-or-nothing in the reward set
        let expects_signing_keys = first_entry.signer.is_some();
        for entry in entries.iter() {
            if entry.signer.is_some() != expects_signing_keys {
                panic!("FATAL: stacking-set contains mismatched entries with and without signing keys.");
            }
        }
        if !expects_signing_keys {
            return None;
        }

        let mut signer_set = BTreeMap::new();
        for entry in entries.iter() {
            let signing_key = entry
                .signer
                .expect("BUG: signing keys should all be set in reward-sets with any signing keys");
            if let Some(existing_entry) = signer_set.get_mut(&signing_key) {
                *existing_entry += entry.amount_stacked;
            } else {
                signer_set.insert(signing_key, entry.amount_stacked);
            };
        }

        let mut signer_set: Vec<_> = signer_set
            .into_iter()
            .filter_map(|(signing_key, stacked_amt)| {
                let weight = u32::try_from(stacked_amt / threshold)
                    .expect("CORRUPTION: Stacker claimed > u32::max() reward slots");
                if weight == 0 {
                    return None;
                }
                Some(NakamotoSignerEntry {
                    signing_key,
                    stacked_amt,
                    weight,
                })
            })
            .collect();

        // finally, we must sort the signer set: the signer participation bit vector depends
        //  on a consensus-critical ordering of the signer set.
        signer_set.sort_by_key(|entry| entry.signing_key);

        Some(signer_set)
