### Title
Unbounded DelegatedResourceAccountIndex growth enables reflected read-amplification DoS via `getDelegatedResourceAccountIndexV2` - (`File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
An unprivileged, funded account can grow its own `V2_FROM_PREFIX`/`V2_TO_PREFIX` delegation index without any protocol-enforced cap on the number of distinct delegatees. Because `getV2Index` performs an unbounded `prefixQuery` + in-memory sort with no page/result-size limit, any anonymous third party can then repeatedly hit the read-only `/wallet/getdelegatedresourceaccountindexv2` endpoint (and gRPC/PBFT/Solidity equivalents) to force the node to repeatedly do the expensive O(n log n) scan against that address.

### Finding Description
`DelegatedResourceAccountIndexStore.delegateV2` writes one `V2_FROM_PREFIX`/`V2_TO_PREFIX` key per `(owner, receiver)` pair with no limit on how many distinct receivers an owner can accumulate [1](#0-0) . `DelegateResourceActuator.validate()` only requires `delegateBalance >= 1 TRX` and enough available frozen V2 balance — there is no check on the number of distinct `receiverAddress` values an owner may target [2](#0-1) .

`getV2Index`/`getWithPrefix` then does an unbounded `prefixQuery` over the `V2_FROM_PREFIX`/`V2_TO_PREFIX` namespace, materializes it into a `List`, and sorts it by timestamp — with no `MAX_RESULT_SIZE`, no pagination, and no cap constant anywhere in the method [3](#0-2) . This is reachable from an unauthenticated HTTP client via `GetDelegatedResourceAccountIndexV2Servlet.fillResponse` → `Wallet.getDelegatedResourceAccountIndexV2` → `getV2Index`, with no additional address ownership or auth check beyond address-format validation [4](#0-3) [5](#0-4) . The same call is also exposed via gRPC (`RpcApiService.getDelegatedResourceAccountIndexV2`) and PBFT/Solidity variants [6](#0-5) [7](#0-6) .

The only mitigating control is `RateLimiterServlet`, which applies generic QPS/IP-based rate limiting per endpoint, not a size-based cost accounting for the *content* of a given address's index — so a low, sustained QPS against a victim address whose index has been artificially inflated to tens of thousands of entries still forces repeated expensive `prefixQuery`+sort work per request [8](#0-7) .

### Impact Explanation
This is a DoS-via-RPC-API class issue: an attacker-controlled account can inflate the on-chain index for its own address (or, since indices are also written for the receiver side under `V2_TO_PREFIX`, indirectly for any receiver address it delegates to) to an arbitrary size, then any anonymous caller can repeatedly trigger CPU/IO work proportional to that size on every read. This does not directly corrupt state, steal funds, or break consensus — it is a targeted resource-consumption amplification against full/solidity/PBFT node read paths, which is a legitimate but bounded-severity DoS-via-RPC-API finding.

### Likelihood Explanation
Growing the index has a real, non-trivial economic cost to the attacker: each distinct `receiverAddress` requires (a) a pre-existing, distinct account (`receiverCapsule == null` is rejected) [9](#0-8) , (b) at least 1 TRX of frozen V2 balance delegated per call (locked, though eventually recoverable via undelegate/unfreeze), and (c) normal transaction bandwidth/energy fees per broadcast transaction. Building 10k+ entries therefore requires funding/creating thousands of accounts and broadcasting thousands of transactions — feasible but not free, and it scales linearly with attacker cost. Once built, however, the read-side cost to re-trigger the expensive query is essentially free and repeatable indefinitely by any anonymous party, since there is no cap on `prefixQuery` result size at read time.

### Recommendation
Add a bound to `getWithPrefix` in `DelegatedResourceAccountIndexStore` (e.g., a `MAX_RESULT_SIZE` constant with pagination/limit support, mirroring patterns used elsewhere in the store layer for prefix queries), and/or enforce a maximum number of distinct delegatees per owner/receiver in `DelegateResourceActuator.validate()` (and the corresponding VM native contract path in `DelegateResourceProcessor.validate`) to cap V2 index growth at the write path.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
