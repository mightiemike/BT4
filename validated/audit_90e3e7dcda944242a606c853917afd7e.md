### Title
Unhandled `ExecuteInbound` Hard-Error Path Reverts Ballot-Finalized State Without Recording Failure or Refund - (File: `x/uexecutor/keeper/msg_vote_inbound.go`)

### Summary
`VoteInbound` deliberately treats known execution-prerequisite failures (`inbound.ValidateForExecution()`) as *soft* failures: it records a `FAILED` `PCTx` and schedules a refund via `handleFailedInboundValidation`, then returns `nil` so the ballot/UTX state is preserved. However, the final dispatch step, `k.ExecuteInbound(ctx, utx)`, is not wrapped the same way — any error it returns bubbles straight up as a hard `error` from `VoteInbound`, exactly like the Cairo `assert` in the referenced report causes the whole call to revert instead of returning `false`.

### Finding Description
In `x/uexecutor/keeper/msg_vote_inbound.go`: [1](#0-0) 
the ballot vote is recorded and finalized inside a `CacheContext` and explicitly `commit()`-ed independently of everything that follows (UTX creation, pending-inbound removal, execution dispatch). [2](#0-1) 
Step 7 (`ValidateForExecution`) failures are caught and converted into a recorded `FAILED` `PCTx` plus (for non-CEA inbounds) a scheduled `INBOUND_REVERT` outbound via `handleFailedInboundValidation`, matching the intended fail-safe design described in the file's own doc-comment ("a UniversalTx is always created … instead of having funds silently stuck in the gateway contract"): [3](#0-2) 

But Step 8's call to `ExecuteInbound` is *not* wrapped this way — any non-nil error is returned directly and is not converted to a `FAILED` `PCTx`/revert record: [4](#0-3) 

`ExecuteInbound` itself has at least one hard-error path that is reachable purely from attacker-supplied inbound data: the `default` branch for an unrecognized `TxType` returns a raw `error` instead of recording a failed execution: [5](#0-4) 

Because a Cosmos SDK message handler that returns a non-nil error causes the entire `DeliverTx`/message execution to be rolled back (all writes performed on the passed-in `ctx`, including `CreateUniversalTx` and `RemovePendingInbound` at Steps 5–6), but the **ballot vote itself was already committed** via the independent `commit()` call at line 75, the net effect on the validator whose vote reaches quorum is: the on-chain ballot is left in a `PASSED`/finalized state while the corresponding `UniversalTx` record, PCTx history, and any refund/revert outbound are never persisted.

### Impact Explanation
This reproduces the exact bug class from the external report: a hard revert on an otherwise-recoverable "unsupported/invalid" condition, instead of a graceful `false`/failed-status return, leaves the cross-chain transaction unrecorded and unresolvable. Concretely:
- The user's deposit/inbound event is permanently unaccounted for on-chain (no UTX, no PCTx, no refund outbound), even though the ballot machinery believes the inbound was finalized.
- Because `VoteInbound` rejects re-processing of an inbound whose UTX already exists (`found` check at Step 1), and the ballot for that inbound key is already finalized, subsequent votes for the same inbound may be unable to re-trigger UTX creation, leaving funds effectively stuck with no path to revert/refund — mirroring the "Pending indefinitely" / "difficulty recovering from invalid state" impact called out in the H-09 report.

### Likelihood Explanation
Reaching the `default` branch in `ExecuteInbound` requires an inbound whose `TxType` is outside the four defined enum values (`GAS`, `FUNDS`, `FUNDS_AND_PAYLOAD`, `GAS_AND_PAYLOAD`). I was not able to confirm within the available context whether `MsgVoteInbound.ValidateBasic()` (or an earlier keeper-side check) restricts `TxType` to only these valid enum values before ballot voting proceeds; if it does not, an attacker-influenced/malformed inbound observation (e.g. crafted off-chain event data relayed by a universal validator acting on user-controlled on-chain event content) could carry an invalid `TxType` and trigger this path. This is the main unverified assumption in this analysis — without confirming the absence of an enum-range guard earlier in the pipeline, the exact triggerability of the `default` branch (as opposed to only structurally-similar failure branches elsewhere in `ExecuteInboundFunds`/`ExecuteInboundGas`/etc. that were not fully audited within budget) remains uncertain.

### Recommendation
Wrap the `k.ExecuteInbound(ctx, utx)` call in `VoteInbound` the same way `ValidateForExecution` errors are handled: on any error returned from `ExecuteInbound`, invoke `handleFailedInboundValidation` (or an equivalent path that records a `FAILED` `PCTx` and schedules an `INBOUND_REVERT` outbound where applicable) and return `nil`, rather than propagating the raw error and rolling back the already-finalized ballot's downstream UTX creation. Additionally, add explicit enum-range validation for `Inbound.TxType` in `ValidateBasic`/`ValidateForExecution` so unsupported values are caught as a recorded soft failure long before `ExecuteInbound`'s `default` branch can be reached.

### Proof of Concept
1. A universal validator submits `MsgVoteInbound` for an inbound whose `TxType` is set to a value outside the four defined constants (assuming no earlier enum-range check rejects it in `ValidateBasic`).
2. Quorum is reached on the 2/3+1 vote; `VoteOnInboundBallot` finalizes and `commit()` persists the `PASSED` ballot state (`x/uexecutor/keeper/msg_vote_inbound.go:55-75`).
3. `CreateUniversalTx` and `RemovePendingInbound` are staged on `ctx` (Steps 5–6), then `ExecuteInbound` is dispatched (Step 8).
4. `ExecuteInbound`'s `switch` hits the `default` branch and returns `fmt.Errorf("unsupported inbound tx type: %d", ...)` (`x/uexecutor/keeper/execute_inbound.go:31-33`).
5. `VoteInbound` returns this error unchanged (`x/uexecutor/keeper/msg_vote_inbound.go:153-155`); the SDK message handler fails, rolling back all `ctx`-scoped writes (UTX creation, pending-inbound removal) — but the ballot's `PASSED` status, committed independently in step 2, remains.
6. The inbound now has a finalized ballot but no UniversalTx record and no refund path, and re-submission via `VoteInbound` for the same inbound key is blocked (or ballot re-voting is rejected) since the ballot is already finalized — reproducing the "stuck/inconsistent state, no recovery" impact of the external H-09 report.
