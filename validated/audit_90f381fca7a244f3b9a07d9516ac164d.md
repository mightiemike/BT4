## No vulnerability found for this question.

**Analysis:**

The claimed exploit requires that `get_leader_key_at` resolve a leader key purely by `(key_block_ptr, key_vtxindex)` coordinates in a way that could collide across forks. Tracing the actual implementation shows this is not the case.

`NakamotoChainState::validate_normal_nakamoto_block_burnchain` calls `db_handle.get_leader_key_at(key_block_ptr, key_vtxindex)` [1](#0-0) , which delegates to `SortitionHandleConn::get_leader_key_at`, which passes `self.context.chain_tip` (the fork the handle is opened against — the canonical fork, since `tenure_burn_chain_tip` was already confirmed canonical by `validate_nakamoto_tenure_snapshot`) as the `tip` parameter [2](#0-1) .

The core `SortitionDB::get_leader_key_at` function first resolves `ancestor_snapshot` by walking the MARF fork identified by `tip` back to `key_block_height`, obtaining the *unique, fork-specific* `sortition_id` for that height on that fork. Only then does it query `leader_keys WHERE sortition_id = ancestor_snapshot.sortition_id AND block_height = ?2 AND vtxindex = ?3` [3](#0-2) .

`SortitionId` values are derived from the full burnchain fork history (not just block height/vtxindex), so two leader-key registrations at the same numeric `(block_height, vtxindex)` on two different Bitcoin forks have two different `sortition_id`s. The query is scoped to the single `sortition_id` belonging to the canonical fork's ancestor at that height — a leader key inserted under the orphaned fork's `sortition_id` simply does not match this `WHERE` clause and can never be returned, regardless of numeric coincidence in `(block_height, vtxindex)`.

**Equality check (before/after):**
- Claimed broken equality: `leader_key(key_block_ptr, key_vtxindex)` resolved by the validation code == leader key actually registered on the canonical fork containing `tenure_burn_chain_tip`.
- Actual: because the lookup is always scoped to the ancestor `sortition_id` derived from `db_handle`'s own (canonical) `chain_tip`, the resolved leader key is always the one registered on that same canonical fork at that height/vtxindex — never one from an orphaned fork, even under coordinate collision. The equality holds in all cases; it is not broken.

Additionally, `validate_nakamoto_tenure_snapshot` independently re-verifies that the tenure's sortition itself is canonical via `get_ancestor_sort_id` before any of this leader-key resolution happens [4](#0-3) , further reinforcing that the entire validation path is anchored to the canonical fork.

No exploitable divergence exists through this code path; the attacker's proposed scenario (colliding `block_ptr`/`vtxindex` across forks causing cross-fork leader-key resolution) is prevented by the `sortition_id`-scoped query design.

    /// Get a leader key at a specific location in the burn chain's fork history, given the
    /// matching block commit's fork index root (block_height and vtxindex are the leader's
    /// calculated location in this fork).
    /// Returns None if there is no leader key at this location.
    pub fn get_leader_key_at<C: SortitionContext>(
        ic: &IndexDBConn<'_, C, SortitionId>,
        key_block_height: u64,
        key_vtxindex: u32,
        tip: &SortitionId,
    ) -> Result<Option<LeaderKeyRegisterOp>, db_error> {
        if key_block_height >= BLOCK_HEIGHT_MAX {
            return Err(db_error::BlockHeightOutOfRange);
        }
        let ancestor_snapshot = match SortitionDB::get_ancestor_snapshot(ic, key_block_height, tip)?
        {
            Some(sn) => sn,
            None => {
                return Ok(None);
            }
        };

        let qry = "SELECT * FROM leader_keys WHERE sortition_id = ?1 AND block_height = ?2 AND vtxindex = ?3 LIMIT 2";
        let args = params![
            ancestor_snapshot.sortition_id,
            u64_to_sql(key_block_height)?,
            key_vtxindex,
        ];
        query_row_panic(ic, qry, args, || {
            format!(
                "Multiple keys at {},{} in {}",
                key_block_height, key_vtxindex, tip
            )
        })
    }
