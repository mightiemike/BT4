## Analog Confirmed

### Title
Post-validation mutation of `output_data_receivers` allows receipts to exceed `max_receipt_size` after size validation - ([File: runtime/runtime/src/lib.rs])

### Summary
The bug class in CVE-2024-43897 is: a size/offset invariant is validated against an object's *original* form, but the object is subsequently transformed (GSO segmentation) such that the validated invariant no longer holds, and downstream code that assumes the invariant still holds misbehaves (`WARN_ON_ONCE`/OOB). nearcore has a directly analogous pattern: a new receipt is created and validated against `max_receipt_size` (4 MiB) at creation time, but is **mutated afterward** by appending `output_data_receivers`, growing it past the validated limit. Downstream consensus-critical code (state witness size accounting, congestion/bandwidth forwarding) assumes `max_receipt_size` is an enforced hard bound.

### Finding Description
When an action receipt returns `ReturnData::ReceiptIndex(receipt_index)` (i.e., a promise chain via `promise_return`), the runtime does not wrap the result in a new `Data` receipt; instead it reaches into the *already-created* new receipt and extends its `output_data_receivers` field in place: [1](#0-0) 

This mutation happens **after** the new receipt has already passed through action-execution/receipt-creation size validation (which enforces `max_receipt_size`, raising `ReceiptValidationError::ReceiptSizeExceeded` for receipts that were too large *before* this mutation). Because the check happens on the pre-mutation size and the mutation happens post-check, a receipt that was exactly at (or just under) `max_receipt_size` can be pushed above the limit by this `extend_from_slice` call — mirroring how `csum_start`/`csum_offset` in the kernel bug were validated against the pre-segmentation packet but used against post-segmentation segments.

This is confirmed by the codebase's own test suite and documentation, which explicitly states the resulting receipt is *not* rejected despite exceeding the hard limit, and calls this out as a known bug (nearcore issue #12606): [2](#0-1) 

The consuming code in the congestion-control forwarding path has to special-case this exact scenario to avoid getting stuck, by silently clamping the observed size down to `max_receipt_size` for admission-limit purposes: [3](#0-2) 

The design doc for `ChunkStateWitness` size limits explicitly states `max_receipt_size` is supposed to be a **hard limit** that keeps the total witness size under ~21 MiB, and that chunk validators must independently verify producers respected it — implying an unenforced oversized receipt is a protocol-level correctness assumption violation, not merely a resource nuisance: [4](#0-3) [5](#0-4) 

### Impact Explanation
An oversized receipt that bypasses the `max_receipt_size` hard limit undermines the sizing assumptions that keep `ChunkStateWitness` bounded (~21 MiB total, per the documented budget breakdown). Because the size clamp in `try_forward` is a workaround rather than a fix, the actual oversized receipt is still forwarded/buffered and stored/transmitted at its true (over-limit) size; only the *admission accounting* pretends it is `max_receipt_size`. This can inflate the real size of `outgoing_receipts`/`source_receipt_proofs` and the resulting state witness beyond the limits the protocol is designed to guarantee, and any place downstream that assumes `size <= max_receipt_size` (e.g., other bandwidth/size budget computations built on the same assumption) can be fed data that violates that assumption. This is a single, unprivileged contract call away (any account calling a deployed contract that does a `promise_then`/`promise_return` chain sized close to the limit), and the repository's own test explicitly frames it as "the receipt should be rejected, but currently isn't" — i.e., an already-acknowledged invalid-state-transition-adjacent bug reachable from ordinary transactions.

### Likelihood Explanation
High reachability: any account can deploy or call an existing contract that builds a promise DAG (`promise_then`) where an intermediate receipt is sized close to `max_receipt_size` and then `promise_return`s into it, causing `output_data_receivers` to be appended post-validation. No special privileges, staking, or validator/network position are required — only a signed transaction and a deployed contract, both of which are described in the repository's own `test_max_receipt_size_promise_return`/`test_max_receipt_size_value_return` tests.

### Recommendation
Re-validate (or re-clamp with a hard rejection, not just an admission-size workaround) receipt size **after** `output_data_receivers` are appended in `runtime/runtime/src/lib.rs`, before the receipt is handed to `receipt_sink.forward_or_buffer_receipt`. Remove the size-clamp workaround in `ReceiptSinkV2::try_forward` (`runtime/runtime/src/congestion_control.rs:412-427`) once the root cause is fixed, so that oversized receipts are rejected outright (as `ReceiptSizeExceeded`) rather than silently forwarded with mis-accounted size.

### Proof of Concept
The repository already contains a working PoC for this exact bug, documented as referencing nearcore issue #12606: [6](#0-5) 
1. Deploy `near_test_contracts::rs_contract()`.
2. Call `max_receipt_size_promise_return_method1` with `args_size` computed so the intermediate promise `C`'s receipt is exactly `max_receipt_size` (4,194,304 bytes) at creation/validation time.
3. The promise DAG resolves such that `C`'s receipt gets `output_data_receivers` appended (routing to `B`), pushing its real size to `expected_size` (4,194,504 bytes in the yield/resume analog test), above `max_receipt_size` — yet it is not rejected with `ReceiptSizeExceeded`, confirmed by `assert_oversized_receipt_occurred`.
