### Title
Griefer can front-run `MsgExecutePayload` to permanently strand an inbound's deposited funds and block the paired payload execution - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
`MsgExecutePayload` is a permissionless, gasless message: any address may submit a user's pre-signed `UniversalPayload` + `VerificationData` to a UEA, and the module deliberately does not enforce `Signer == EVM(Owner)` [3](#0-2) . The UEA contract authenticates the call and advances a monotonic per-UEA nonce embedded in the signed payload [4](#0-3) . This is the same signature-observability/nonce-consumption primitive as the `Erc20Votes::delegateBySig` bug in the external report: a griefer who observes the `UniversalPayload`+`VerificationData` (visible in the source-chain event, in pending/unfinalized `MsgVoteInbound` votes, or in the Push Chain mempool for a directly-submitted `MsgExecutePayload`) can front-run it via their own `MsgExecutePayload` submission using the identical payload/signature before the intended execution runs.

### Finding Description
For a `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbound, `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` perform two *separate, independently-committed* EVM calls against the same UEA:
1. Deposit PRC20/gas into the UEA (`depositPRC20` / `gasAndPayloadDepositAutoSwap`), committed unconditionally on success.
2. Execute the user's pre-signed `UniversalPayload` via `ExecutePayloadV2` → `CallUEAExecutePayload`, which is a *distinct* EVM transaction consuming the UEA's on-chain nonce for that exact payload+signature [5](#0-4) .

Because `MsgExecutePayload` is open to any signer and gasless [6](#0-5) , an attacker who copies the same `UniversalAccountId`, `UniversalPayload`, and `VerificationData` — obtainable before Push Chain's own scheduled execution runs (e.g., from the source-chain gateway event, from pending `MsgVoteInbound` votes, or from a user's own directly-broadcast `MsgExecutePayload` in the mempool) — can submit it themselves via `ms.ExecutePayload` → `k.ExecutePayload` → `CallUEAExecutePayload` at `x/uexecutor/keeper/msg_execute_payload.go:87`. This consumes the UEA's nonce for that payload *before the intended flow's deposit step lands*, so:
- If the front-run call succeeds (e.g., balance not required, or attacker pre-funds gas), the UEA's nonce advances and the *inbound-triggered* `ExecutePayloadV2` call at line 290 will fail signature/nonce verification when it later runs.
- If the front-run call instead reverts inside `executeUniversalTx` for a reason unrelated to nonce validation (e.g., the payload's inner call assumes the not-yet-deposited balance), whether the nonce still advances depends on the UEA contract's internal ordering of nonce-consumption vs. call execution, per the design note that nonce-advance happens once "signature verification" succeeds, independent of the downstream call's outcome [4](#0-3) .

Either way, once the payload's nonce is consumed prematurely, the deposit (Step 1, already committed and irreversible per line 188-206) and the payload execution (Step 3) become permanently desynchronized: `ExecuteInboundFundsAndPayload` simply records a `"FAILED"` PcTx entry and returns `nil` — there is no retry, no re-signing mechanism, and no automatic refund/revert path for this failure mode [7](#0-6) .

### Impact Explanation
The user's deposited PRC20/gas funds land in the UEA, but the atomic "deposit + payload" semantics the protocol promises (e.g., "deposit + DEX swap atomically" per the `TxType` docs [8](#0-7) ) are broken: the payload that was supposed to act on those funds silently fails and is never retried, because the pre-signed `VerificationData` has a fixed embedded nonce that cannot be resubmitted without a brand-new signature from the original owner. This is a fund-freezing/DoS griefing vector matching the "unauthorized griefer blocks legitimate action via nonce pre-consumption" bug class, reachable purely by an unprivileged external attacker observing public payload/signature data.

### Likelihood Explanation
`MsgExecutePayload` is intentionally open to any submitter and gasless by design, so the barrier to submitting a front-run copy is zero cost to the attacker. The main precondition is visibility of the `UniversalPayload`+`VerificationData` before the intended execution lands, which is readily available via the public source-chain event, mempool-visible `MsgVoteInbound`/`MsgExecutePayload` transactions, or general chain observability.

### Recommendation
Decouple retry-ability from the fixed nonce for inbound-triggered payload execution, or gate `MsgExecutePayload` so it cannot be front-run ahead of its paired deposit (e.g., require the deposit and payload execution to be a single atomic EVM call/transaction, or bind the accepted nonce/verification window to the specific `UniversalTx`/inbound so a stray direct submission cannot consume it prematurely). Additionally, add a retry/refund path for `"FAILED"` payload PCTx entries so funds are not permanently stranded when the payload never executes.

### Proof of Concept
1. A user submits (or a UV observes and votes on) an inbound of type `FUNDS_AND_PAYLOAD` with `UniversalPayload` P and `VerificationData` S, targeting UEA `U`.
2. Before the 2/3 UV vote threshold finalizes and `ExecuteInboundFundsAndPayload` runs, an attacker copies P and S (visible in the source event / pending votes) and submits `MsgExecutePayload{UniversalAccountId, P, S}` directly.
3. `ms.ExecutePayload` → `k.ExecutePayload` → `CallUEAExecutePayload` executes against `U`, consuming `U`'s nonce for payload P (`x/uexecutor/keeper/msg_execute_payload.go:87`).
4. The inbound later finalizes; `ExecuteInboundFundsAndPayload` deposits the PRC20/gas into `U` (committed, line 144-157), then calls `ExecutePayloadV2` with the same P/S at line 290 — this fails nonce/signature verification since it was already consumed in step 3.
5. Result: funds are deposited into `U`, but the payload never executes as part of the intended atomic flow; a `"FAILED"` PcTx is recorded permanently with no retry mechanism.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**
