### Title
Unbounded Growth of `DelegatedResourceAccountIndex` Lists via O(n) Linear-Scan Deduplication in `FreezeBalanceActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` maintains per-account `toAccountsList`/`fromAccountsList` in `DelegatedResourceAccountIndexCapsule`, deduplicating with an O(n) `List.contains()` scan before an unbounded `addToAccount`/`addFromAccount` append, with no cap on list size — the same anti-pattern as the reported `_checkExists()`/`depositedTokens` bug.

### Finding Description
When the legacy (non-optimized) delegation path is active (`dynamicPropertiesStore.supportAllowDelegateOptimization()` is `false`), every call to `FreezeBalanceActuator.delegateResource()` loads the owner's and receiver's `DelegatedResourceAccountIndexCapsule`, checks membership with `toAccountsList.contains(...)` / `fromAccountsList.contains(...)`, and if absent appends via `addToAccount`/`addFromAccount`, which just does `.addToAccounts(toAccount).build()` on the underlying protobuf list with no size bound. [1](#0-0) 
The capsule's append methods provide no dedup or limit themselves: [2](#0-1) 
Because this list is stored as a single protobuf-encoded value keyed by account address, every subsequent freeze/delegate to a *new* receiver by the same owner re-reads and re-serializes the whole growing list, and the `contains()` check becomes linearly more expensive as the list grows — mirroring the reported `_checkExists()` O(n) loop over `depositedTokens`.
An attacker (owner) can repeatedly submit `FreezeBalanceContract` transactions with a unique, freshly created receiver address each time and the required minimum of 1 TRX (`frozenBalance >= TRX_PRECISION`, enforced in `validate()`), causing `toAccountsList` on the owner's index and `fromAccountsList` on each receiver's index to grow without bound. [3](#0-2) 
This is a consensus-critical actuator executed by every full node while processing every block, unlike a single dApp's storage — so the cost of the growing linear scan and the growing protobuf blob is paid by the entire network, not just the attacker.

### Impact Explanation
Every additional receiver the attacker adds permanently increases the size of the owner's `DelegatedResourceAccountIndex` value and the per-tx cost of the `contains()` scan performed by `delegateResource()`, degrading transaction execution time for that account's future `FreezeBalanceContract` transactions and increasing state size that must be read/written by every node reprocessing the chain. While the fixed 1-TRX minimum per entry throttles the attack compared to the original 1-wei report, an attacker only needs to spend TRX they get back later (frozen, not burned) to indefinitely grow this list, since there is no cap on `toAccountsList`/`fromAccountsList` length. This is a Denial-of-Service risk on a specific account's future delegate/undelegate/freeze operations and adds unbounded chain-state bloat, matching the "storage bloating via unrestricted deposits" bug class.

### Likelihood Explanation
Exploitability depends on the `allowDelegateOptimization` chain parameter (a committee-controlled dynamic property) being disabled; when disabled this legacy list-append path is live for any account owner freely delegating resources to newly created receiver addresses at minimal cost (1 TRX + new account creation fee, refundable via unfreeze). When `allowDelegateOptimization` is enabled, the store uses key-prefixed per-pair entries (`delegate`/`delegateV2`) instead of a single growing list, which avoids this issue — this indicates the java-tron team already recognized and partially mitigated the underlying pattern via the "optimization" path, similar to the external report's "Fixed" resolution, but the vulnerable code path remains present and reachable for accounts/networks that have not enabled that flag. [4](#0-3) 

### Recommendation
Remove or hard-deprecate the legacy list-based `toAccountsList`/`fromAccountsList` code path in `FreezeBalanceActuator.delegateResource()` (lines 320-346) entirely in favor of the already-implemented key-prefixed `delegate()`/`delegateV2()` indexing, or enforce a maximum size on `toAccountsList`/`fromAccountsList` and reject further delegation once the cap is reached, and/or replace the `contains()` linear scan with an O(1) lookup (e.g., a companion existence flag stored under a composite key) as recommended in the source report.

### Proof of Concept
1. Ensure `allowDelegateOptimization` dynamic property is `0` (default/unset, matching `testFreezeDelegatedBalanceForBandwidth` in `FreezeBalanceActuatorTest`).
2. Attacker account `A` repeatedly generates fresh receiver addresses `R1..Rn`, activates each with the minimal account-creation transfer, then submits `FreezeBalanceContract(owner=A, receiver=Ri, frozenBalance=1_TRX, resource=BANDWIDTH)`.
3. Each execution calls `delegateResource`, which loads `A`'s `DelegatedResourceAccountIndexCapsule`, does `toAccountsList.contains(Ri)` (false), and appends `Ri` via `addToAccount`, growing the list by one entry every call.
4. As `n` grows into the thousands, `A`'s index value size and the `contains()` scan cost for `A`'s subsequent freeze/delegate/unfreeze operations grow linearly, degrading performance for `A`'s account and bloating chain state that every full node must store and re-process.

  public void addFromAccount(ByteString fromAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addFromAccounts(fromAccount)
        .build();
  }

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addToAccounts(toAccount)
        .build();
  }
