### Title
External Initiator credentials bypass job-scoping and can trigger a run on an arbitrary job ID via `POST /v2/jobs/:ID/runs` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` sets the same `SessionUserKey` context value used by real logged-in users/API-token holders, so `PipelineRunsController.Create` treats an authenticated External Initiator (EI) exactly as a "user." Because `Create` performs no check that the requested integer job `:ID` is associated with the authenticating EI, any EI credential can trigger a run on any job in the node by ID, not just the job it was registered for.

### Finding Description
`auth.AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) authenticates the EI's access-key/secret against `bridges.ExternalInitiator`, and on success does: [1](#0-0) 
This unconditionally sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}`, indistinguishable (via `auth.GetAuthenticatedUser`) from a genuine user session/token.

`userOrEI` route group wires `AuthenticateExternalInitiator` ahead of token/session auth on `POST /v2/jobs/:ID/runs`: [2](#0-1) 

`PipelineRunsController.Create` then does: [3](#0-2) 
The comment explicitly states "only users are allowed to run jobs using int IDs - EIs not allowed", but `isUser := auth.GetAuthenticatedUser(c)` returns `true` for EI-authenticated requests too (because of the `SessionUserKey` set above). As a result, once `isUser` is true, the code parses `:ID` as an `int32` and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly, with **no check whatsoever** that `jobID` is the job the EI was registered against, nor that the job is even a webhook/EI-triggerable job type. There is no lookup of `bridges.ExternalInitiator` -> job association anywhere in this path (`GetAuthenticatedExternalInitiator` is never consulted in `Create`).

This exceeds the exact scenario in the question: not only can EI(A) trigger job B belonging to a different registered EI, EI(A) can trigger a run on **any** job in the node addressable by an integer ID (OCR, VRF, cron, keeper, etc.), because the intended "EIs not allowed" restriction is silently defeated by the shared `SessionUserKey` mechanism.

### Impact Explanation
An attacker holding valid credentials for a single, narrowly-scoped External Initiator can force execution of arbitrary jobs on the node (unauthorized workflow/job execution), including jobs unrelated to any external initiator, by simply POSTing to `/v2/jobs/<any-int-id>/runs`. This can cause unintended on-chain transactions, resource exhaustion, or manipulation of job state/history — matching the "unauthorized transaction or workflow execution" bounty category.

### Likelihood Explanation
High feasibility: the attacker only needs one legitimately-issued EI access-key/secret pair (a normal, low-privilege credential). No additional exploitation primitives (no injection, no race, no admin access) are required — a single crafted HTTP POST with a different job ID is sufficient and fully repeatable.

### Recommendation
- In `PipelineRunsController.Create`, distinguish real user sessions/tokens from EI-derived pseudo-users. Use `auth.GetAuthenticatedExternalInitiator(c)` to detect EI callers and reject the integer-ID path for them (restoring the documented "EIs not allowed" intent), or explicitly verify that the requested job's `ExternalInitiators`/`externalJobID` bindings include the authenticated EI before invoking `RunJobV2`.
- Stop reusing `SessionUserKey` to represent EI identity; use a distinct marker/role (e.g., a dedicated `RoleExternalInitiator`) so role-based checks like `isUser` cannot silently conflate the two principal types.

### Proof of Concept
Integration test plan (extends existing `TestRunner_WebhookJobRemoved`/`pipeline_runs_controller_test.go` patterns):
1. Start an app instance; insert two jobs: JobA (any runnable job type, e.g., OCR spec as in `setupPipelineRunsControllerTests`) with integer ID `idA`, and JobB with integer ID `idB`.
2. Register External Initiator `EI1` via `cltest.CreateExternalInitiatorViaWeb`, intended only to be referenced by JobA's spec (or with no job association at all).
3. Authenticate as `EI1` using its access key/secret headers (`static.ExternalInitiatorAccessKeyHeader`/`static.ExternalInitiatorSecretHeader`).
4. POST to `/v2/jobs/<idB>/runs` (JobB's ID, unrelated to EI1) using EI1 credentials.
5. Assert expected secure behavior: `401`/`403` Unauthorized, and `pipeline_runs` count unchanged for JobB.
6. Actual observed behavior: response is `200 OK` with a newly created pipeline run for JobB (`prc.App.RunJobV2` invoked), demonstrating the bypass — confirms the vulnerability described.
