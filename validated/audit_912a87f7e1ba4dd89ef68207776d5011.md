### Title
Unbounded recursion in compiled-class-hash computation over attacker-influenced bytecode segment tree causes sequencer stack-overflow DoS - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs:111-132` recursively walks a `NestedIntList`/`HashableNestedIntList` tree (`bytecode_segment_lengths`) with no depth bound, one Rust stack frame per level. This function is invoked from `HashableCompiledClass::hash` (same file, lines 144-149) which is called directly (not inside any resource-limited sandbox/subprocess) by `SierraCompiler::compile` in `crates/apollo_compile_to_casm/src/lib.rs:60-74`, right after the Sierra→CASM compiler subprocess returns. A contract declarer fully controls the Sierra program submitted in a `DECLARE` transaction (via `apollo_gateway`/`ClassManager::add_class`, `crates/apollo_class_manager/src/class_manager.rs:70-113`), and the compiled bytecode segment tree's shape/depth is a function of the program's control-flow/function nesting. A program engineered to produce a sufficiently deep segment tree will overflow the stack of the main sequencer process during the (unsandboxed) hash step. [1](#0-0) [2](#0-1) 

### Finding Description
- `NestedIntList`/`HashableNestedIntList` is a recursive tree type describing how a compiled contract's bytecode is segmented for the purposes of computing the "compiled class hash" (used both for CASM V1 hash and the newer Blake2-based V2 hash). Its construction is documented and tested elsewhere in the repo as recursive with no depth limit (e.g. `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs:277-307`'s `create_bytecode_segment_structure_inner`, and blockifier's `NestedFeltCounts::new_inner`, `crates/blockifier/src/execution/contract_class.rs:163-194`, which even documents `assert!(segmentation_depth <= 1, ...)` — an ad hoc depth check that exists precisely because deeper nesting is possible but only handled for a narrow "at most 1" case elsewhere; it is *not* present in `bytecode_hash_node`). [3](#0-2) 
- `bytecode_hash_node` performs unconditional recursion `node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child))` with **no depth guard, no iterative fallback, and no resource limit**, unlike other recursive paths in the codebase that are explicitly protected (e.g. blockifier's Cairo call-stack recursion guarded by `RecursionDepthGuard`/`max_recursion_depth`, `crates/blockifier/src/execution/entry_point.rs:706-726`, or gas-metered VM recursion in `test_stack_overflow`, `crates/blockifier/src/blockifier/transaction_executor_test.rs:538-579`). [4](#0-3) 
- The compiled `CasmContractClass` (containing `bytecode_segment_lengths`) comes from `SierraToCasmCompiler::compile`, which does run under `ResourceLimits` (CPU/memory) in a subprocess (`crates/apollo_compile_to_casm/src/compiler.rs:30-55`), but the **subsequent hash computation happens back in the parent, unsandboxed process**: `let executable_class_hash = executable_class.hash(&HashVersion::V2);` in `crates/apollo_compile_to_casm/src/lib.rs:69`. `ResourceLimits` bounds CPU time and memory of the child compiler process — it does not, and cannot, bound the native call-stack depth of the hashing step that runs afterward in the gateway/class-manager component itself. [5](#0-4) 
- This is reachable end-to-end from an unprivileged, unauthenticated transaction sender: `add_tx` → `Gateway::add_tx_inner` (`crates/apollo_gateway/src/gateway.rs:214-254`) → `ClassManager::add_class` (`crates/apollo_class_manager/src/class_manager.rs:70-113`) → `SierraCompiler::compile` → `hash()` → `bytecode_hash_node`. It also re-triggers on every node re-validating the same declared class (`check_compile_class_hash_v2_declaration`, `crates/starknet_api/src/executable_transaction.rs:226-244`) and during OS re-execution / block replay, since the hash must be recomputed by every full node processing the block.

### Impact Explanation
A stack overflow in Rust aborts the process (`SIGABRT`) rather than raising a catchable panic — it cannot be caught by `catch_unwind`, `Result`, or any error-handling wrapper. Since the vulnerable code path runs in the gateway/class-manager component that every sequencer node runs to admit and validate `DECLARE` transactions, a single crafted class submitted by any account can crash that component's process on every node that processes it (initial submission, p2p re-validation on peer nodes, and full-node/OS re-execution during block validation). This is a network-wide denial-of-service: nodes are unable to process the poisoned declare transaction (or any block containing it) without crashing, matching the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Likelihood is high for any attacker willing to reverse-engineer how `cairo-lang-sierra-to-casm`'s segmentation algorithm nests `NestedIntList` for deeply nested/recursive Sierra function structures — no privileged role is required, only the ability to submit a `DECLARE` transaction (bounded only by normal fee/resource-bound requirements and `max_bytecode_size`, which does not limit segment-tree *depth*, only overall bytecode size). No special node role, timing, or race condition is needed.

### Recommendation
- Add an explicit maximum recursion/tree-depth check in `bytecode_hash_node` (and its Starknet-OS/blockifier counterparts, `create_bytecode_segment_structure_inner` and `NestedFeltCounts::new_inner`) mirroring the existing `RecursionDepthGuard` pattern used for entry-point call recursion, returning an error instead of recursing unboundedly.
- Alternatively/additionally, rewrite `bytecode_hash_node` iteratively using an explicit heap-allocated stack, eliminating the native-stack dependency altogether.
- Enforce the depth bound at Sierra-to-CASM compilation output validation time (in `SierraToCasmCompiler::compile` or `SierraCompiler::compile`), rejecting any `CasmContractClass` whose `bytecode_segment_lengths` exceeds a safe maximum depth before it is ever hashed outside the sandboxed subprocess.

### Proof of Concept
Conceptual PoC (requires confirming the exact Sierra construct that maximizes segment-tree depth via `cairo-lang-sierra-to-casm`'s segmentation heuristic, which is out of scope for source inspection here since it lives in a pinned external compiler binary):
1. Craft a Sierra program (via `cairo-lang-starknet` compilation of adversarial Cairo source, or hand-built Sierra) containing deeply nested function/branch structure (thousands of levels) that stays within `max_bytecode_size`/`max_contract_class_object_size` limits but forces the CASM compiler's segmentation logic to emit a `NestedIntList::Node` tree nested to a depth on the order of thousands.
2. Submit this class via a normal `DECLARE` (v2/v3) transaction to `starknet_addDeclareTransaction`.
3. `Gateway::add_tx_inner` → `ClassManager::add_class` → `SierraCompiler::compile` succeeds compilation (bounded by CPU/memory limits) but then calls `executable_class.hash(&HashVersion::V2)`, which recurses through `bytecode_hash_node` to the tree's full depth, overflowing the native stack and aborting (`SIGABRT`) the class-manager/gateway process — the sequencer analog of the `lopdf` PDF nesting DoS. fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
