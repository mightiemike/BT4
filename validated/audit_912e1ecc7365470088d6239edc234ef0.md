## Analysis

The reported bug class — unbounded iteration over an attacker-influenced storage array causing gas exhaustion and reliable transaction reverts — has a direct analog in the universal execution voting path: `x/uexecutor/keeper/ballot_hooks.go`'s `afterInboundBallotTerminal`. [1](#0-0) 

Every time an inbound ballot reaches a terminal state (PASSED/REJECTED/EXPIRED), `x/uvalidator`'s `MarkBallotFinalized` fires this hook, which performs a full `h.k.PendingInbounds.Walk(...)` over the *entire* `PendingInbounds` collection to locate the entry owning the finalized ballot ID — because ballot IDs are one-way digests and not reversible back to their `utx_key`. [2](#0-1) 

`PendingInbounds` entries are created on the *first* Universal Validator vote for any observed source-chain inbound, keyed by `sha256(source_chain:tx_hash:log_index)`, with no cap on the number of concurrently-pending distinct entries: [3](#0-2) [4](#0-3) 

Because any unprivileged user can cheaply generate many distinct source-chain gateway transactions (dust deposits) on any inbound-enabled chain, and each becomes its own tracked `PendingInboundEntry` once observed and voted on by honest UVs, the size of `PendingInbounds` is effectively attacker-controlled and unbounded — the docstring's assumption that "the pending set is small and transient" does not hold under adversarial load: [5](#0-4) 

Since the `Walk` cost is paid out of the KV-store gas meter on *every single* ballot finalization (i.e., inside every `MsgVoteInbound` transaction that happens to be the one crossing the voting threshold), inflating `PendingInbounds` sufficiently makes this walk consume enough gas to exceed the transaction's gas limit, causing an out-of-gas abort. Crucially, this hook fires for *every* inbound ballot system-wide, not just the attacker's own — so once the map is large enough, *all* future inbound finalizations (mint/execute paths for legitimate users too) become unable to complete within a reasonable gas budget, stalling the universal execution pipeline.

### Title
Unbounded `PendingInbounds` walk in ballot-terminal hook enables gas-exhaustion DoS of inbound finalization - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
`afterInboundBallotTerminal` performs a full linear `Walk` over the `PendingInbounds` collection on every inbound ballot finalization to reverse-map an opaque ballot ID back to its owning entry. `PendingInbounds` size is effectively attacker-controlled (grown by cheap, unprivileged source-chain deposit transactions that Universal Validators must observe and vote on), with no maximum-entry cap or expiry-based pruning enforced before the walk executes. As the collection grows, the gas cost of this walk grows linearly and is paid inside the same transaction that finalizes any inbound ballot — eventually causing finalization transactions to run out of gas and revert deterministically, stalling the inbound voting → UTX creation pipeline for all users, not just the attacker.

### Finding Description
`x/uvalidator`'s generic ballot machine invokes `BallotHooks.AfterBallotTerminal` synchronously the moment a ballot's vote tally reaches its threshold, inside `MarkBallotFinalized` [6](#0-5) , which is itself invoked from `CheckIfFinalizingVote` during `VoteOnBallot`, called synchronously from `VoteInbound` while handling `MsgVoteInbound` [7](#0-6) .

For `INBOUND_TX` ballots, the hook (`afterInboundBallotTerminal`) cannot directly look up the owning `PendingInboundEntry` because ballot IDs are one-way digests, so it instead performs a full `Walk` over the whole `PendingInbounds` map searching every entry's `Variants` for a matching `BallotId`.

`PendingInbounds` entries are created and grown purely by validator votes on observed inbound events — but the *inbound events themselves* originate from ordinary, unprivileged user actions on any inbound-enabled external chain (e.g. minimal-value gateway deposits). An attacker can cheaply generate a large number of distinct, low-value source-chain transactions; honest Universal Validators, following protocol, will observe and vote on each, causing `RecordInboundVote` to create a fresh `PendingInboundEntry` per unique `utx_key` with no cap on total pending entries and no way to bound or prune the set except natural ballot finalization/expiry (which itself pays the same iteration cost).

Since store iteration is billed to the SDK gas meter, once the collection is large enough, the `Walk` inside the hook consumes gas proportional to `len(PendingInbounds)`. This cost is incurred by *every* future `MsgVoteInbound` transaction that happens to finalize any ballot (the attacker's own or an honest user's), regardless of which entry actually needs to be found — matching the audited "iteration through a storage array... consuming more gas than allowed per transaction" bug class, except here the array size is attacker-inflatable without any privileged action or admin control.

### Impact Explanation
Once `PendingInbounds` grows past the point where the full walk fits within the practical/enforced gas budget for a `MsgVoteInbound` transaction, ballot finalization transactions begin reverting with out-of-gas. Because the hook is invoked unconditionally for every inbound ballot finalization system-wide, this does not just affect the attacker's own spam inbounds — it can prevent *all* pending inbound ballots (including legitimate user deposits) from ever completing their terminal-state bookkeeping, which blocks `UniversalTx` creation, PRC20 minting, and payload execution for those inbounds. This is a denial of service reachable purely through unprivileged, cheap user actions (external-chain dust transactions), causing effectively permanent freezing of in-flight crosschain inbound value for ordinary users, matching the in-scope impact of "permanent freezing of user or protocol-controlled funds" and "denial of service... reachable without privileged control."

### Likelihood Explanation
The trigger requires no validator, admin, or TSS collusion — only an attacker capable of submitting many low-cost transactions to an inbound-enabled external chain (the source-chain fee is the only cost, and Push Chain's own gasless votes mean UVs bear no additional cost either). Honest Universal Validators are expected to observe and vote on all valid inbound events, so the growth of `PendingInbounds` is a natural, unavoidable consequence of honest operation under attacker-driven load; no bug in validator behavior is needed. The severity scales with time/volume of spam and is only bounded by the source chain's own throughput/cost, making this readily achievable over time.

### Recommendation
Avoid the reverse-lookup `Walk` entirely: maintain a secondary index (`ballotID -> utxKey`) populated alongside `RecordInboundVote`, so `afterInboundBallotTerminal` can do an O(1) lookup instead of a full-collection scan. Additionally, bound the maximum number of concurrently-tracked `PendingInboundEntry` records (e.g., per-chain or globally) and/or enforce a minimum inbound value or rate-limit per source address to make the entry set economically infeasible to inflate, mirroring the post-audit fix referenced in the external report (capping the iterable array size).

### Proof of Concept
1. Attacker repeatedly submits many distinct low-value gateway deposit transactions on an inbound-enabled external chain (each with a unique `tx_hash`/`log_index`).
2. Honest Universal Validators observe each and submit `MsgVoteInbound`, causing `RecordInboundVote` to create a new, distinct `PendingInboundEntry` per event via `k.PendingInbounds.Set` [8](#0-7) , unbounded in count.
3. As votes accumulate toward each ballot's threshold, every finalizing `MsgVoteInbound` transaction triggers `MarkBallotFinalized` → `afterInboundBallotTerminal`, which walks the entire (now large) `PendingInbounds` map [9](#0-8) .
4. Once the map is large enough, this walk's gas cost exceeds the practical gas limit for the finalizing transaction, causing it to fail with out-of-gas — for the attacker's own inbound and any other inbound ballot finalizing concurrently, halting further inbound processing.

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
```

func (k Keeper) MarkBallotFinalized(ctx context.Context, id string, status types.BallotStatus) error {
	if status != types.BallotStatus_BALLOT_STATUS_PASSED && status != types.BallotStatus_BALLOT_STATUS_REJECTED {
		return fmt.Errorf("invalid finalization status: %v", status)
	}

	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as finalized",
		"ballot_id", id,
		"final_status", status.String(),
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.FinalizedBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = status
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, status)
	return nil
```
