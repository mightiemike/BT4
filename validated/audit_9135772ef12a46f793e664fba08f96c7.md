Confirmed: `min_compute_unit_price` is initialized to `u64::MAX` as a sentinel for "unset", and `get_min_compute_unit_price` treats `u64::MAX` as the sentinel indicating no data.### Title
`get_min_compute_unit_price` collides with sentinel value when a transaction sets `compute_unit_price == u64::MAX` - (File: `runtime/src/prioritization_fee.rs`)

### Finding Description
`PrioritizationFee::min_compute_unit_price` is initialized to `u64::MAX` as a sentinel meaning "unset" [1](#0-0) . `PrioritizationFee::update` unconditionally overwrites `min_compute_unit_price` whenever `compute_unit_price < self.min_compute_unit_price`, with no special-casing of `u64::MAX` [2](#0-1) . `get_min_compute_unit_price` then reports `None` whenever the stored value equals `u64::MAX`, treating it as "unset" rather than a legitimate observed minimum: `(self.min_compute_unit_price != u64::MAX).then_some(self.min_compute_unit_price)` [3](#0-2) .

If the only (or minimum) `compute_unit_price` observed in a slot is exactly `u64::MAX`, the stored value legitimately equals the sentinel, and `get_min_compute_unit_price()` will report `None`, indistinguishable from a slot with zero prioritized transactions. This is a real logic bug: the fee-cache state is no longer a pure, unambiguous function of the transactions actually committed to the slot — two different real slot histories (an empty slot vs. a slot with a single `u64::MAX`-priced transaction) become indistinguishable at the query API.

An unprivileged user can trigger this by simply calling `ComputeBudgetInstruction::set_compute_unit_price(u64::MAX)` in a transaction and having it land, controlling only compute-budget instruction data, which is legitimate user input requiring no privileged access.

### Impact Explanation
This is a state-consistency/off-by-sentinel bug in the prioritization-fee cache used to answer `getRecentPrioritizationFees`-style RPC queries. Impact is limited to reporting `None` instead of `Some(u64::MAX)` for the affected slot's minimum compute-unit price (an incorrect fee-market signal), not a consensus, hashing, snapshot, or capitalization issue, and not a crash. `PrioritizationFee` is a local, per-node accounting/metrics structure, not part of AccountsDB/index/hash/snapshot state, so there is no divergence in bank hash, capitalization, or replay-vs-snapshot state. This falls into a minor "incorrect non-consensus state/RPC data" category rather than the higher-severity categories (memory corruption, consensus violation, fund loss) targeted by the bounty program.

### Likelihood Explanation
Trivially reachable: any unprivileged user who can land a single transaction with `set_compute_unit_price(u64::MAX)` (and no other transaction in that slot has a lower nonzero price) triggers it deterministically. No special preconditions beyond normal transaction submission are needed, and it's fully reproducible in a unit test as suggested in the question.

### Recommendation
Store the minimum compute-unit price as `Option<u64>` (mirroring `PrioritizationFeeMetrics::min_compute_unit_price`) instead of using `u64::MAX` as a sentinel encoded in the same domain as valid prices, and update via `Option::map_or`/`min` semantics rather than raw integer comparison. Alternatively, explicitly track a separate "has_any_update" boolean.

### Proof of Concept

```rust
// runtime/src/prioritization_fee.rs (test module)
#[test]
fn test_min_compute_unit_price_u64_max_collision() {
    let mut prioritization_fee = PrioritizationFee::default();
    assert!(prioritization_fee.get_min_compute_unit_price().is_none());

    // Attacker's only transaction in the slot uses compute_unit_price = u64::MAX
    prioritization_fee.update(u64::MAX, /*prioritization_fee=*/ 10, vec![]);
    prioritization_fee.mark_block_completed().unwrap();

    // BUG: this incorrectly returns None even though a transaction was committed
    assert_eq!(
        prioritization_fee.get_min_compute_unit_price(),
        Some(u64::MAX),
        "min compute unit price collides with the 'unset' sentinel value"
    );
}
```
Running this against current code fails the assertion because `get_min_compute_unit_price()` returns `None`, confirming the sentinel collision.
