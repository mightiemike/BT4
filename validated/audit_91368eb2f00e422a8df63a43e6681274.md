### Title
Tenure-extend acceptance gated on signer-local wall-clock time causes cross-signer validation-verdict divergence - ([File: stacks-signer/src/signerdb.rs])

### Summary
`SignerDb::calculate_tenure_extend_timestamp` (and its callers `calculate_full_extend_timestamp` / `calculate_read_count_extend_timestamp` in `stacks-signer/src/signerdb.rs`, invoked from `GlobalStateView::check_proposal` in `stacks-signer/src/chainstate/v1.rs` and `stacks-signer/src/chainstate/v2.rs`) decides whether a miner's `TenureExtend`/`ExtendedReadCount` transaction is valid by comparing each signer's own local wall-clock reading (`get_epoch_time_secs()`) against an `extend_timestamp` derived from locally-recorded `proposed_time` values, rather than any value that is canonically agreed upon by all signers (e.g., burn block height or a value embedded/committed in the block itself). This is the same bug class as the Wildcat `FixedTermLoanHook` finding: gating an accept/reject decision on a mutable, node-local clock reading instead of a deterministic "expiry"-like value, causing different signers to reach different verdicts on the identical block.

### Finding Description
`calculate_tenure_extend_timestamp` computes:
```
tenure_extend_timestamp = tenure_start_time + tenure_idle_timeout_secs + tenure_process_time_ms/1000
``` [1](#0-0) 

where `tenure_start_time` and `tenure_process_time_ms` come from `get_tenure_times`, which reads `proposed_time` and `validation_time_ms` values stored per-block in each signer's own local database: [2](#0-1) 

This `extend_timestamp` is then compared against `get_epoch_time_secs()` — the calling signer's own current wall-clock time — at the moment it evaluates a block proposal:
```
let extend_timestamp = signer_db.calculate_full_extend_timestamp(...);
let epoch_time = get_epoch_time_secs();
let enough_time_passed = epoch_time >= extend_timestamp;
...
if !changed_burn_view && !enough_time_passed && !is_in_replay {
    return Err(RejectReason::InvalidTenureExtend);
}
``` [3](#0-2) 

The same pattern occurs in the v1 chainstate evaluator: [4](#0-3) 

The `proposed_time` values feeding `tenure_start_time` are recorded independently by each signer as it locally observes/validates blocks — they are not a consensus-committed field agreed by all signers (unlike burn height, consensus hash, or VRF-derived sortition data used elsewhere in this codebase for equivalent gating decisions). Because `get_epoch_time_secs()` and the locally-stored `proposed_time` history can differ slightly across signer processes (clock skew, differing observation/validation latency, differing local DB state if a signer missed intermediate blocks), the boolean `enough_time_passed` — which directly gates `Ok`/`Err(RejectReason::InvalidTenureExtend)` — can evaluate differently on different signers for the exact same `NakamotoBlock`.

This mirrors the Wildcat root cause precisely: the correct/intended check is "has the deterministic, network-visible term boundary been reached" (an `expiry`-equivalent), but the actual implementation instead asks "does *my* local clock/local history say enough time has passed" (a `block.timestamp`-equivalent). The report's mitigation trade-off discussion — allowing a bit of drift near a boundary — does not eliminate divergence risk here, because unlike the Wildcat market (single contract state, single clock), this Stacks signer logic is evaluated independently by N signers who must reach a common accept/reject verdict to hit the block-signing weight threshold.

### Impact Explanation
When two or more signers disagree on `enough_time_passed` for a proposed `TenureExtend` block near the idle-timeout boundary, some signers will sign/accept the block while others reject it with `RejectReason::InvalidTenureExtend`. If the split prevents the block from reaching the required signing weight threshold on either the tenure-extend path or the "stick with current miner" path, the network experiences a temporary tip disagreement / stall until the boundary is unambiguously passed (or the standard timeout-based fallback logic recovers), consistent with the "High – … temporary tip disagreement" impact category. No majority stake or admin key is required; ordinary local clock skew or scheduling jitter across independently-operated signer nodes is sufficient to trigger divergence at exactly the moment two signers straddle the timestamp boundary.

### Likelihood Explanation
This condition is reachable in normal operation any time a `TenureExtend`/`ExtendedReadCount` block is proposed close to the computed `tenure_extend_timestamp` boundary — a routine, frequent event (idle timeouts default to tens of seconds; see `tenure_idle_timeout_secs` in `sample/conf/signer/mainnet-signer-conf.toml`, and the boundary is deliberately exercised by tests such as `tenure_extend_after_idle_signers_with_buffer` in `stacks-node/src/tests/signer/v0/tenure_extend.rs`). No attacker action is strictly necessary; a miner (a single, non-majority actor) can additionally choose to propose the extend block right at the boundary to maximize the chance of split verdicts, making this at minimum minority-triggerable.

### Recommendation
Replace the wall-clock comparison with a check anchored to a value all signers can agree on deterministically — e.g., gate tenure-extend validity on burn block height / burn view change (which the code already partially does via `changed_burn_view`) rather than combining it with a signer-local timestamp comparison, or have the miner commit a canonical "idle-since" reference (e.g., last globally-accepted block's committed timestamp) that every signer derives identically instead of relying on each signer's own `proposed_time` history and local `get_epoch_time_secs()` reading.

### Proof of Concept
1. Run N signers with `tenure_idle_timeout_secs` configured (default path exercised in `tenure_extend_after_idle_signers_with_buffer`, `stacks-node/src/tests/signer/v0/tenure_extend.rs:296-365`).
2. Introduce clock skew or differing block-observation latency between two signer processes (e.g., pause one signer's validation briefly, or run with slightly different system clocks) so their locally recorded `proposed_time`/`validation_time_ms` history differs, as computed in `get_tenure_times` (`stacks-signer/src/signerdb.rs:2112-2152`).
3. Have the miner propose a `TenureExtend` block right at the computed idle-timeout boundary.
4. Observe that `calculate_full_extend_timestamp` (`stacks-signer/src/signerdb.rs:2186-2203`) yields different `extend_timestamp` values, and `get_epoch_time_secs() >= extend_timestamp` (`stacks-signer/src/chainstate/v2.rs:234-235`, `v1.rs:376-377`) evaluates to different booleans on the two signers, so one signer emits `RejectReason::InvalidTenureExtend` while the other accepts and signs — producing a split verdict on the identical block.

    fn get_tenure_times<F>(
        &self,
        tenure: &ConsensusHash,
        cause_match: F,
    ) -> Result<(u64, u64), DBError>
    where
        F: Fn(TenureChangeCause) -> bool,
    {
        let query = "SELECT tenure_change_cause, proposed_time, validation_time_ms FROM blocks WHERE consensus_hash = ?1 AND state = ?2 ORDER BY stacks_height DESC";
        let args = params![tenure, BlockState::GloballyAccepted.to_string()];
        let mut stmt = self.db.prepare(query)?;
        let rows = stmt.query_map(args, |row| {
            let tenure_change_cause: Option<u8> = row.get(0)?;
            let tenure_change_cause = tenure_change_cause
                .and_then(|cause_byte| TenureChangeCause::try_from(cause_byte).ok());
            let proposed_time: u64 = row.get(1)?;
            let validation_time_ms: Option<u64> = row.get(2)?;
            Ok((tenure_change_cause, proposed_time, validation_time_ms))
        })?;
        let mut tenure_processing_time_ms = 0_u64;
        let mut tenure_start_time = None;
        let mut nmb_rows = 0;
        for (i, row) in rows.enumerate() {
            nmb_rows += 1;
            let (tenure_change_cause, proposed_time, validation_time_ms) = row?;
            tenure_processing_time_ms =
                tenure_processing_time_ms.saturating_add(validation_time_ms.unwrap_or(0));
            tenure_start_time = Some(proposed_time);
            if let Some(tenure_change_cause) = tenure_change_cause {
                if cause_match(tenure_change_cause) {
                    debug!("Found matching tenure change block {i} blocks ago in tenure {tenure}");
                    break;
                }
            }
        }
        debug!("Calculated tenure extend timestamp from {nmb_rows} blocks in tenure {tenure}");
        Ok((
            tenure_start_time.unwrap_or(get_epoch_time_secs()),
            tenure_processing_time_ms,
        ))
    }
