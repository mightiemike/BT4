### Title
No refund of excess/unspent attached deposit to external callers of the NEAR Wallet Contract's `rlp_execute` on success - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract::rlp_execute` entry point is `#[payable]` and accepts an arbitrary NEAR deposit from any caller (not just the eth-implicit account owner) to cover fees for relayed actions (e.g. NEP-141 storage deposits for `ERC20Transfer`). The contract only tracks and refunds this attached deposit (`CallerDeposit`) when the downstream cross-contract call **fails**. If the call **succeeds**, the entire attached amount is consumed and no excess is ever returned to the external caller, mirroring the reported bug class ("if commission/deposit is paid and the user sends more than required, the excess is not returned").

### Finding Description
`rlp_execute` is payable, and any account can call it on behalf of another account's eth-implicit wallet contract: [1](#0-0) 

The attached deposit is captured into an optional `CallerDeposit` only for "external" (non-owner) callers: [2](#0-1) 

This `CallerDeposit` is refunded **only in the `PromiseResult::Failed` branch** of `rlp_execute_callback`; on `PromiseResult::Successful`, the deposit is simply dropped and no refund logic runs: [3](#0-2) 

The amount actually forwarded to the target as the promise's `deposit` is derived independently from the signed Ethereum transaction's `value`/`yocto_near` fields (via `Action::try_into_near_action`), not from the attached NEAR deposit itself: [4](#0-3) 

Because these two amounts are decoupled, an external caller can attach more NEAR to `rlp_execute` than is actually required by the underlying action (e.g., attaching more than the `NEP_141_STORAGE_DEPOSIT_AMOUNT` needed, or simply more than the eth-tx's `value`). If the relayed transaction succeeds, that surplus is absorbed into the target wallet contract account's balance and is never returned to the caller who paid it — the existing test suite confirms this behavior is intentional/expected, not merely an edge case: [5](#0-4) 

### Impact Explanation
Any unprivileged account (e.g. a relayer paying storage/fee deposits on behalf of a wallet-contract owner) that attaches more NEAR than strictly required to a successful `rlp_execute` call permanently loses the excess — it is transferred to the target account/wallet contract with no path to reclaim it. This is a concrete, protocol-level value-loss condition reachable by any transaction signer or contract caller interacting with the NEAR Wallet Contract, matching "concrete unauthorized value movement" / "permanently frozen funds" for the overpaying party.

### Likelihood Explanation
Medium. It requires an external caller (typically a relayer service, per the contract's own design intent of covering NEP-141 storage or fees) to overestimate/over-attach the deposit needed for a successful relayed action — a realistic operational scenario since relayers must guess storage/fee amounts up front and there is no reconciliation/refund path on success.

### Recommendation
Track the actually-consumed deposit (the `action.deposit`/`NEP_141_STORAGE_DEPOSIT_AMOUNT` actually forwarded) versus the `attached_deposit` supplied by the external caller, and refund the difference to the caller in the success branch of `rlp_execute_callback` (and any other success-path callbacks), not only on `PromiseResult::Failed`.

### Proof of Concept
1. Account `R` (a relayer, distinct from the wallet contract owner) calls `rlp_execute` on the target eth-implicit wallet contract, attaching `N` NEAR as deposit for an `ERC20Transfer` intended to cover `NEP_141_STORAGE_DEPOSIT_AMOUNT` (constant, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:33`).
2. Suppose the receiver is already registered with the NEP-141 token, so `nep_141_storage_balance_callback` skips the `storage_deposit` call entirely and only forwards the `ft_transfer` action with its own small deposit (`lib.rs:224-238`).
3. The cross-contract call succeeds (`PromiseResult::Successful`), so `rlp_execute_callback` returns success without any refund logic (`lib.rs:313-316`).
4. The full `N` NEAR attached by `R` was already deposited into the wallet contract's own balance upon calling `rlp_execute` (payable) and is never returned to `R`, even though the relayed action needed none of that N NEAR extra amount.

    pub fn rlp_execute(

                success: false,

                ),
            });

        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
