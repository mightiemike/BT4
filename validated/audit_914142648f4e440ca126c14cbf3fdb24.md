### Title
Unrestricted callers can drain a smart contract's subsidized `origin_energy_limit` energy pool - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
TRON lets a smart-contract creator subsidize callers' gas by freezing TRX for energy and setting `consume_user_resource_percent < 100`, so that part of every call's energy is charged to the creator's frozen-energy allowance instead of the caller. Exactly like the Gelato `commonFunds` in the referenced report, this subsidy pool is consumed by **any address that calls the contract**, with no whitelist, no per-caller cap, and no cost proportional to the drain inflicted, so it can be exhausted by a griefing caller purely to deny the subsidy to legitimate users.

### Finding Description
When a `TriggerSmartContract` transaction is executed, `VMActuator.getTotalEnergyLimitWithFixRatio()` computes how much of the total energy limit comes from the caller versus from the contract creator's frozen energy, based on `ContractCapsule.getConsumeUserResourcePercent()` and `ContractCapsule.getOriginEnergyLimit()`: [1](#0-0) 

The origin (contract creator) share is drawn from `rootRepository.getAccountLeftEnergyFromFreeze(creator)`, i.e., the creator's own frozen-TRX energy allocation - a finite, shared "common fund" set up by the creator to subsidize *any* user of the dApp: [2](#0-1) 

Billing then actually deducts this usage from the creator's account via `ReceiptCapsule.payEnergyBill()`/`getOriginUsage()`, and `TransactionTrace.pay()` resolves `originAccount` purely from `contractCapsule.getOriginAddress()` for any `TRX_CONTRACT_CALL_TYPE` transaction - there is no restriction on which caller address triggers this consumption: [3](#0-2) [4](#0-3) 

There is no actuator-level check on `TriggerSmartContract` that limits who may call, how frequently, or how much of the creator's subsidized allocation a single unrelated address may consume in aggregate - it is fully permissionless, matching the Gelato `requestUpdateOwner()` pattern where "there is no restriction on requesting these callbacks."

### Impact Explanation
A malicious actor who is not a customer of the dApp can repeatedly invoke the target contract's subsidized function(s) at near-zero personal cost (only their own small percentage share, or none if `consume_user_resource_percent` is 0), continuously draining the contract creator's frozen energy allocation. Legitimate users of the dApp then either pay full price out of pocket or fail if they lack sufficient TRX/energy, defeating the purpose of the subsidy. Because the creator's energy comes from real frozen TRX (opportunity cost of staking), this is an accounting/griefing impact directly analogous to draining Drips' `commonFunds`: a shared resource meant to subsidize legitimate flows can be burned by unrelated third parties with no recourse other than un-freezing/adjusting `origin_energy_limit` or `consume_user_resource_percent`, which itself requires an `UpdateEnergyLimitContractActuator` transaction from the contract owner.

### Likelihood Explanation
Likelihood is high: triggering a smart contract is entirely unauthenticated/permissionless by design (any account can send a `TriggerSmartContract` transaction to any deployed contract with `consume_user_resource_percent < 100`), and many dApps configure exactly this subsidization to onboard users with zero TRX. No special privileges or preconditions beyond knowing the contract address and having minimal TRX/bandwidth for the transaction itself are required.

### Recommendation
This is intrinsic to TRON's intended resource-sharing model (analogous to Drips' own "Acknowledged... intended behavior" response), so a full fix conflicts with the trustless/permissionless design. Mitigations that preserve permissionlessness while limiting griefing include: exposing an on-chain, application-enforced allow-list or rate limiter (via the contract itself) for which callers can draw on the creator's subsidized energy; encouraging dApp developers to monitor `origin_energy_limit` consumption and cap `consume_user_resource_percent` conservatively; and/or providing tooling/alerts so creators can react before the frozen-energy pool is exhausted. As with Drips, an on-chain protocol-level restriction (e.g., mandatory whitelist) is not recommended, since it reintroduces trusted-role risk.

### Proof of Concept
1. Deploy a contract with `consume_user_resource_percent` set below 100 (e.g., 0), and freeze TRX for energy as the creator so `originEnergyLimit`/`getAccountLeftEnergyFromFreeze(creator)` is non-zero (subsidizing all callers).
2. From an arbitrary, unrelated address with no relationship to the dApp, repeatedly send `TriggerSmartContract` transactions invoking any state-changing function of the contract.
3. Observe via `Wallet.getAccountResource()`/`EnergyProcessor` that the creator's `EnergyUsage` climbs and `getAccountLeftEnergyFromFreeze(creator)` depletes purely due to calls from the attacker's address, exactly as the caller-vs-origin split logic in `VMActuator.getTotalEnergyLimitWithFixRatio()` allows.
4. Once depleted, legitimate end users calling the same contract are billed the full energy amount themselves (or the call reverts for insufficient energy/TRX), demonstrating the subsidy pool was fully consumed by an unrelated party with no restriction, mirroring the Gelato `commonFunds` drain.   public long getTotalEnergyLimitWithFixRatio(AccountCapsule creator, AccountCapsule caller,
      TriggerSmartContract contract, long feeLimit, long callValue)
      throws ContractValidateException {

    long callerEnergyLimit = getAccountEnergyLimitWithFixRatio(caller, feeLimit, callValue);
    if (Arrays.equals(creator.getAddress().toByteArray(), caller.getAddress().toByteArray())) {
      // when the creator calls his own contract, this logic will be used.
      // so, the creator must use a BIG feeLimit to call his own contract,
      // which will cost the feeLimit TRX when the creator's frozen energy is 0.
      return callerEnergyLimit;
    }

    long creatorEnergyLimit = 0;
    ContractCapsule contractCapsule = rootRepository
        .getContract(contract.getContractAddress().toByteArray());
    long consumeUserResourcePercent = contractCapsule.getConsumeUserResourcePercent(
        VMConfig.disableJavaLangMath());

    long originEnergyLimit = contractCapsule.getOriginEnergyLimit();
    if (originEnergyLimit < 0) {
      throw new ContractValidateException("originEnergyLimit can't be < 0");
    }

    long originEnergyLeft = 0;
    if (consumeUserResourcePercent < VMConstant.ONE_HUNDRED) {
      originEnergyLeft = rootRepository.getAccountLeftEnergyFromFreeze(creator);
      if (VMConfig.allowTvmFreeze() || VMConfig.allowTvmFreezeV2()) {
        receipt.setOriginEnergyLeft(originEnergyLeft);
      }
    }
    if (consumeUserResourcePercent <= 0) {
      creatorEnergyLimit = min(originEnergyLeft, originEnergyLimit,
          VMConfig.disableJavaLangMath());
    } else {
      if (consumeUserResourcePercent < VMConstant.ONE_HUNDRED) {
        // creatorEnergyLimit =
        // min(callerEnergyLimit * (100 - percent) / percent,
        //   creatorLeftFrozenEnergy, originEnergyLimit)

        creatorEnergyLimit = min(
            BigInteger.valueOf(callerEnergyLimit)
                .multiply(BigInteger.valueOf(VMConstant.ONE_HUNDRED - consumeUserResourcePercent))
                .divide(BigInteger.valueOf(consumeUserResourcePercent)).longValueExact(),
            min(originEnergyLeft, originEnergyLimit, VMConfig.disableJavaLangMath()),
            VMConfig.disableJavaLangMath());
      }
    }
    if (VMConfig.allowTvmFreezeV2()) {
      long now = rootRepository.getHeadSlot();
      EnergyProcessor energyProcessor =
          new EnergyProcessor(
              rootRepository.getDynamicPropertiesStore(),
              ChainBaseManager.getInstance().getAccountStore());
      energyProcessor.updateUsage(creator);
      creator.setLatestConsumeTimeForEnergy(now);
      receipt.setOriginEnergyUsage(creator.getEnergyUsage());
      receipt.setOriginEnergyWindowSize(creator.getWindowSize(ENERGY));
      receipt.setOriginEnergyWindowSizeV2(creator.getWindowSizeV2(ENERGY));
      creator.setEnergyUsage(
          energyProcessor.increase(creator, ENERGY,
              creator.getEnergyUsage(), creatorEnergyLimit, now, now));
      receipt.setOriginEnergyMergedUsage(creator.getEnergyUsage());
      receipt.setOriginEnergyMergedWindowSize(creator.getWindowSize(ENERGY));
      rootRepository.updateAccount(creator.createDbKey(), creator);
    }
    return addExact(callerEnergyLimit, creatorEnergyLimit,
        VMConfig.disableJavaLangMath());
  }

  private long getOriginUsage(DynamicPropertiesStore dynamicPropertiesStore, AccountCapsule origin,
      long originEnergyLimit,
      EnergyProcessor energyProcessor, long originUsage) {
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowTvmFreeze() == 1
        || dynamicPropertiesStore.supportUnfreezeDelay()) {
      return min(originUsage, min(originEnergyLeft, originEnergyLimit, disableJavaLangMath),
          disableJavaLangMath);
    }

    if (checkForEnergyLimit(dynamicPropertiesStore)) {
      return min(originUsage,
          min(energyProcessor.getAccountLeftEnergyFromFreeze(origin), originEnergyLimit,
              disableJavaLangMath), disableJavaLangMath);
    }
    return min(originUsage, energyProcessor.getAccountLeftEnergyFromFreeze(origin),
        disableJavaLangMath);
  }
