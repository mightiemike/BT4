## Analysis: Confirmed — the pattern generalizes to `GAS_AND_PAYLOAD` + `IsCEA=true`

The exploit reasoning is valid. Tracing the full path:

**Entry point.** `ExecuteInboundGasAndPayload` handles `IsCEA=true` by using `Inbound.Recipient` *directly* as the target UEA address, with no binding to `Inbound.Sender`'s real identity: [1](#0-0) 

If `Recipient` resolves to an already-deployed UEA (`isUEA==true`, checked via `CallFactoryGetOriginForUEA`), the code proceeds straight to the deposit/autoswap and then falls through to the payload-execution step — no check that `Sender` (or anyone else authenticated) actually owns that UEA.

**Payload execution with module as `evmFrom`.** After the deposit, the UEA branch calls `ExecutePayloadV2` with the **module account** as `evmFrom`, not a value derived from the attacker/sender: [2](#0-1) 

`ExecutePayloadV2` forwards this straight into `CallUEAExecutePayload` → `executeUniversalTx(payload, verificationData)` on the target UEA: [3](#0-2) 

**The trust assumption that breaks.** Per the module's own documentation, the UEA contract's signature check is keyed off `msg.sender`: it is enforced only when the EVM-level caller is *not* the `UNIVERSAL_EXECUTOR_MODULE` address: [4](#0-3) 

For the **non-CEA** inbound paths this is safe, because `ueaAddr` there is derived deterministically from `Inbound.Sender`'s own cross-chain identity (`CallFactoryToGetUEAAddressForOrigin`) — the module always executes against the *sender's own* UEA, so the module-sender signature bypass just reflects "you authorized this by making the real source-chain transaction yourself." That invariant is explicit in the design.

For the **`IsCEA=true` + `GAS_AND_PAYLOAD`** path, that invariant is deliberately broken by design: `Recipient` (and therefore the UEA that gets executed against) is fully decoupled from `Sender`'s identity — it is attacker-supplied data relayed from an arbitrary source-chain "CEA" contract, validated by Universal Validators only for *faithful observation of the source-chain event*, not for *authorization of the target UEA's owner*. Since `evmFrom == UNIVERSAL_EXECUTOR_MODULE` for every inbound-triggered call regardless of `IsCEA`, and the UEA contract skips signature verification for that sender, an attacker can:

1. Trigger a `GAS_AND_PAYLOAD`, `IsCEA=true` inbound whose `Recipient` is any already-deployed victim UEA.
2. Supply an arbitrary `UniversalPayload` (`To`, `Data`, `Value`, `GasLimit`, etc.) and arbitrary/garbage `VerificationData` — it need not recover to the victim's real key, because the contract-side check is bypassed for module-originated calls.
3. Get that payload executed with the victim UEA as `msg.sender`, letting the attacker move any PRC20/native assets held by the UEA to an address they control.
4. Have `DeductGasFeesFromReceipt` burn the resulting EIP-1559 gas cost out of the **victim's** native (`upc`) balance, since `recipient` passed into fee deduction is the victim's UEA: [5](#0-4) 

Unlike a failed-signature case (where `writeCache()` is never invoked and both the EVM state and fee deduction roll back together — a genuine safety net for the *normal* failure path), here `execErr == nil` because there was never a real check to fail, so `writeCache()` commits both the arbitrary call's effects and the fee burn.

This is consistent with the existing test suite explicitly exercising `IsCEA=true`/`GAS_AND_PAYLOAD` where `Recipient` is a UEA belonging to a chain identity that differs from `Sender` (e.g. `differentSender`/`personBSender` cases), confirming the code path is reachable with attacker-controlled sender/recipient mismatch: [6](#0-5) 

### Caveat
The actual signature-bypass-on-module-sender behavior lives in the UEA Solidity contract (`UEA_EVM.sol`/`UEA_SVM.sol`), which is compiled bytecode in this repo (`test/utils/bytecode.go`) sourced from an external `push-chain-core-contracts` repository not indexed here. I could not directly read the Solidity source to confirm the exact `msg.sender == UNIVERSAL_EXECUTOR_MODULE` bypass condition; this analysis relies on the explicit, in-repo documentation of that behavior in `x/uexecutor/README.md`. A background agent with full repo/contract access should verify this against the actual contract bytecode/source before treating this as fully proven.

### Title
Recipient-spoofing in `IsCEA=true` `GAS_AND_PAYLOAD` inbound lets an unprivileged CEA execute arbitrary calldata as any deployed victim UEA and drain its native gas balance — (File: `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
`ExecuteInboundGasAndPayload`'s `IsCEA` branch uses the attacker-controlled `Inbound.Recipient` directly as the UEA to execute against, then calls `ExecutePayloadV2`/`CallUEAExecutePayload` with the trusted module address as `evmFrom`. Per the module's documented UEA authorization model, the UEA contract skips owner-signature verification when the caller is the `UNIVERSAL_EXECUTOR_MODULE` address — an invariant that is safe only when the executed UEA is derived from the same identity that authorized the inbound (the non-CEA path), but is violated by the CEA path where `Recipient` is unrelated to `Sender`.

### Impact Explanation
An attacker (any external contract emitting a gateway event observed by honest UVs) can target any already-deployed UEA on Push Chain and execute an arbitrary `UniversalPayload` as that UEA (moving PRC20/native assets it holds), while also burning the victim UEA's native `upc` balance to cover the attacker's gas cost via `DeductGasFeesFromReceipt`. This is unauthorized cross-user fund theft/drain, reachable purely through the honest-validator-observed inbound flow.

### Likelihood Explanation
Reachable by any unprivileged actor who controls a source-chain contract capable of emitting the gateway event that becomes an `Inbound`; requires only that the chosen `Recipient` corresponds to a real, already-deployed UEA on Push Chain (readily discoverable on-chain) holding exploitable balances.

### Recommendation
For the `IsCEA` branch of `GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD`, do not allow the module to execute payloads against a `Recipient` UEA whose owner identity differs from `Inbound.Sender` without genuine signature verification — either require `VerificationData` to be a real signature validated independently by the keeper before dispatch, or restrict the CEA UEA-execution branch to only deposit funds (never call `executeUniversalTx`) when `Recipient` isn't provably tied to `Sender`'s authorized identity.

### Proof of Concept
1. Deploy/identify a victim UEA on Push Chain holding PRC20 tokens and native `upc`.
2. As an attacker-controlled source-chain contract, emit a gateway event that UVs will observe and vote as `TxType_GAS_AND_PAYLOAD`, `IsCEA=true`, `Recipient=<victim UEA>`, `UniversalPayload={To: <PRC20 token>, Data: transfer(attacker, allBalance)}`, `VerificationData=<garbage>`.
3. Once UV quorum finalizes the inbound, assert: (a) the arbitrary transfer call executed successfully with the victim UEA as `msg.sender`, and (b) the victim UEA's native `upc` balance decreased via `DeductAndBurnFees` to cover gas for a call the victim never authorized — mirroring the existing test pattern in `test/integration/uexecutor/inbound_cea_gas_and_payload_test.go` (lines 210-260) but with `Recipient` set to a genuine third-party's UEA and a state-mutating/value-transferring `Data` payload instead of a benign transfer to a hardcoded address.

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.

func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}
