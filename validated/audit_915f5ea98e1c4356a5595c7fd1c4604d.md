# STATE-INTEGRITY ANALOG SCAN RESULT

### Title
`TransactionOutput::ensure_match_transaction_info` never validates the state (Merkle) checkpoint hash, letting replay-verify silently accept a wrong final state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by the `replay-verify` audit path (and by `aptos-debugger`/CLI tooling) to confirm that VM re-execution reproduces a previously-committed `TransactionInfo`, checks only `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash. It never compares the recomputed state against `txn_info.state_checkpoint_hash()`, nor the `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields, as the function's own TODO admits.

### Finding Description
`ensure_match_transaction_info` is the sole per-transaction correctness gate used when replaying archived/backup transactions against a fresh VM execution: [1](#0-0) 

It asserts equality of `status`, `gas_used`, `write_set_hash` vs `state_change_hash()`, and `event_root_hash` vs `event_root_hash()`. It does **not** assert anything about `txn_info.state_checkpoint_hash()` — the field that actually commits to the resulting global state Merkle root — and the code explicitly documents that checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`) are ignored: [2](#0-1) 

This function is invoked by the `replay_on_archive` tool as the acceptance check for each replayed transaction against the values loaded from backup storage: [3](#0-2) 

Because the write set produced for a version can be identical while the resulting state tree root still diverges (e.g. non-determinism or a bug in JMT/hot-state/position-state root computation, or a base state that already diverged from a prior undetected mismatch), the replay-verify path can report a transaction as "matching" even though the recomputed authenticated state root is wrong. This breaks the invariant that "Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding" and the invariant that proof-bearing/authenticated verification results must be bound to the correct root.

### Impact Explanation
`replay-verify` (`storage/db-tool/src/replay_on_archive.rs`) is the production auditing mechanism used to validate that a full historical replay of backup/archive data reproduces the exact ledger state committed on mainnet. Because the state checkpoint hash is never checked, this tool can report a clean, successful verification of backup data whose ultimate committed state root is corrupted or divergent from what the network actually agreed on — a false assurance of ledger integrity for exactly the invariant (accumulator/state root correctness) this tool exists to police. This is a hard-fork/replay-class integrity gap: a subtly-wrong state root (from a state-computation bug, restore-path corruption, or tampered archive) would pass silently instead of being flagged, undermining the authenticated-verification guarantee that operators and auditors rely on for mainnet data.

### Likelihood Explanation
Medium: the gap requires a genuine state-computation or backup-corruption bug elsewhere (write set correct, but resulting Merkle/hot-state/position root wrong) to actually manifest a divergence. But given this check is the *only* gate for that class of error, and it is explicitly and knowingly incomplete (per the code's own TODO), any latent state-root computation bug — including ones affecting the newer hot-state/position "trading-native" roots — is guaranteed to go undetected by this tool rather than merely "likely" undetected.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the recomputed `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the corresponding fields on the expected `TransactionInfo`, surfacing a mismatch error just as is done for `state_change_hash` and `event_root_hash`. This closes the blind spot for `replay_on_archive`, `aptos-debugger`, and CLI replay-verification flows before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` more broadly, as the TODO itself recommends.

### Proof of Concept
1. Construct a backup/archive `TransactionInfo` whose `state_checkpoint_hash` (or `position_state_checkpoint_hash`) does not match what fresh VM execution of the same transaction (with the same write set, events, gas, and status) will produce — e.g. by patching a single byte of a stored `TransactionInfo`'s checkpoint hash field, or by simulating a state-computation bug that leaves the write set unchanged but shifts the resulting Merkle root.
2. Run `replay_on_archive`'s `Verifier::execute_and_verify` (`storage/db-tool/src/replay_on_archive.rs:349-415`) against this data.
3. Observe that `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) returns `Ok(())` because it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the replay is reported as verified despite the state root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
