## Title
Maker order in `MarketSellAssetActuator` can be fully closed while receiving zero tokens due to unchecked division rounding - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes trade amounts with integer division via `MarketUtils.multiplyAndDivide`, which truncates (floors) the result. In the branch handling an exact quantity match between taker and maker (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`), the maker's receive amount (`makerBuyTokenQuantityReceive`) is used to close out the maker's order and credit the maker's account, but — unlike the other two match branches in the same method — this branch never checks whether the computed value rounded down to `0`. This mirrors the StepVesting `releaseRate` rounding bug: an integer division whose divisor/quantity ratio can floor to zero, silently zeroing out the beneficiary's proceeds while still consuming their full principal/order.

### Finding Description
In `matchSingleOrder` [1](#0-0) , `takerBuyTokenQuantityRemain` is computed via `MarketUtils.multiplyAndDivide`, and there IS an explicit `== 0` guard that returns the taker's sell tokens if the amount rounds to zero.

The last branch (taker > maker) also explicitly guards against `makerBuyTokenQuantityReceive == 0` and returns the maker's remaining sell tokens instead of closing the order for nothing [2](#0-1) .

However, the "taker == maker" branch computes `makerBuyTokenQuantityReceive` the same way, via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, but performs no such zero-check before fully closing the maker's order: [3](#0-2) 

`MarketUtils.multiplyAndDivide` performs a floor division (`a*b/c`), which — exactly like the StepVesting `releaseRate` calculation (`totalAmount / numOfSteps`) — can round down to `0` when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`: [4](#0-3) 

If `makerBuyTokenQuantityReceive` rounds to `0` in this branch, the code still sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` and marks the maker order `INACTIVE` (fully consumed), then calls `addTrxOrToken(makerOrderCapsule, 0)`, crediting the maker with nothing: [5](#0-4) 

There is no validation-time minimum-order-size or "ratio" guard in `validate()` that would prevent such a rounding condition; the only checks are for `sellTokenQuantity`/`buyTokenQuantity` being positive and under `quantityLimit` [6](#0-5) .

### Impact Explanation
When this specific branch is hit (the taker's computed buy amount exactly equals the maker's remaining sell amount) and the maker's price ratio floors the receive amount to zero, the maker's fully-consumed order results in **the maker losing their entire remaining sell-side assets with zero compensation**, while their order is permanently closed (`INACTIVE`) and removed from the order book. This is a direct fund-loss / broken-accounting condition for a market-maker, equivalent in kind to the StepVesting `releaseRate` becoming `0`. It is asymmetric with the rest of the function, which explicitly defends against the same rounding hazard in the other two branches, confirming this is a missed check rather than an accepted design tradeoff.

### Likelihood Explanation
This requires a coincidental exact match between the taker's computed buy quantity and the maker's remaining sell quantity (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`), combined with an extreme price ratio (`makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`) — most realistic with low-decimal TRC10 tokens or highly skewed sell/buy quantities, similar to the low-decimal-token precondition called out in the original report. Likelihood is low-to-medium: it depends on specific order-book conditions but is fully triggerable by any user placing orders with carefully chosen quantities (an attacker could set up a maker order with an extreme ratio, then place a matching taker order, or induce it against another maker), so it's not purely theoretical.

### Recommendation
Add the same zero-check used in the other two branches to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's remaining sell tokens via `MarketUtils.returnSellTokenRemain` (as done in the "taker > maker" branch) instead of closing the order and crediting zero. Consider also enforcing a minimum tradable quantity for each token pair to prevent floor-to-zero conditions in `multiplyAndDivide` calls generally.

### Proof of Concept
1. Create a maker sell order for pair (A, B) where `makerSellQuantity`/`makerBuyQuantity` ratio is such that `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` (e.g., `makerSellQuantity = 1000`, `makerBuyQuantity = 1`, so any partial remaining quantity below 1000 causes a floor-to-zero when recombined with a taker fill leaving `makerSellRemainQuantity` small).
2. Craft a taker `MarketSellAssetContract` order such that `takerBuyTokenQuantityRemain` computed in `matchSingleOrder` exactly equals `makerOrderCapsule.getSellTokenQuantityRemain()`, landing in the "taker == maker" branch.
3. Ensure `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity` (via `MarketUtils.multiplyAndDivide`) computes to `0`.
4. Observe: `makerOrderCapsule.setSellTokenQuantityRemain(0)` executes, the maker order state is set to `INACTIVE` (fully closed/removed from book), and `addTrxOrToken(makerOrderCapsule, 0)` credits the maker with `0` tokens — the maker's assets are consumed with no payout, unlike the explicitly-guarded "taker > maker" branch at [7](#0-6) .

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
