### Title
Integer division truncates slippage protection to zero in inbound gas-abstraction auto-swap - (File: `x/uexecutor/keeper/execute_inbound_gas.go`)

### Summary
`ExecuteInboundGas` computes the minimum acceptable output (`minPCOut`) for the automatic PRC20→WPC gas-abstraction swap using integer division: `quote * 95 / 100`. When the fetched `quote` is small (which happens whenever the attacker-controlled inbound deposit `amount` is small, since `quote` is derived from `amount` via `GetSwapQuote`), the truncating division rounds `minPCOut` down to `0`. This is the exact bug class from the report: a rate/threshold computed via integer division collapses to zero when the numerator is small relative to the divisor, effectively disabling the protection the calculation was meant to provide.

### Finding Description
In `x/uexecutor/keeper/execute_inbound_gas.go`, `ExecuteInboundGas` is invoked for every inbound deposit that requires the "gas abstraction swap" (converting a small amount of the bridged asset into `upc`/WPC to fund the user's gas account). The flow is: [1](#0-0) 

`amount` comes directly from `inbound.Amount`, which is attacker-controlled input parsed earlier in the function: [2](#0-1) 

`quote` is obtained by calling `GetSwapQuote` with this `amount`, and the 5% slippage buffer is then computed with plain integer division:
```go
minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
minPCOut.Div(minPCOut, big.NewInt(100))
```
Because `big.Int.Div` truncates toward zero, any `quote` value between 1 and 20 satisfies `quote*95/100 == 0`. Since `quote` scales with the attacker-controlled `amount`, an attacker can trigger a deposit whose swap quote falls in this dust range, producing `minPCOut = 0`. That zero is then passed as the slippage-protection parameter directly into the on-chain swap call: [3](#0-2) 

With `minPCOut = 0`, the auto-swap accepts any non-negative output, i.e. the slippage guard is completely disabled for that swap.

### Impact Explanation
This falls under "corruption of ... gas fee accounting, refund accounting, ... token mapping" and potentially "unauthorized module-originated EVM execution" impacts, since the module-originated `DerivedEVMCall`-style swap (`CallPRC20DepositAutoSwap`) executes with no effective minimum-output enforcement. An attacker who controls the timing/ordering of inbound processing (or simply front-runs/sandwiches the swap execution within the same or adjacent block via other transactions that move the AMM pool price) can cause the dust-value swap to execute at an arbitrarily bad price with zero protection, extracting value from the pool/liquidity that funds the gas-abstraction swap. Because `ExecuteInboundGas` never returns `execErr` on this path (the swap call itself doesn't fail — it just executes at a bad price), the loss is silent and the `UniversalTx` is marked `SUCCESS`.

### Likelihood Explanation
Triggering `quote*95/100 == 0` only requires the attacker to submit (or cause) an inbound deposit whose value maps to a small `quote` (dust amount, or a low-priced/low-decimal asset), which is fully within reach of an ordinary unprivileged user submitting a deposit on any registered source chain — no privileged role is required.

### Recommendation
Compute the 95% slippage threshold with higher precision before truncating (e.g., scale numerator up before dividing, or use `sdkmath.LegacyDec` for the percentage multiplication) and add an explicit floor/guard so that `minPCOut` is never `0` when `quote > 0`, matching the report's recommendation to avoid divisions that round rate/threshold values to zero.

### Proof of Concept
1. Attacker deposits a bridged asset amount on a registered source chain such that `GetSwapQuote(..., amount)` returns a `quote` value between 1 and 20 (e.g., due to a low-value/low-liquidity token or a dust-sized deposit).
2. `ExecuteInboundGas` computes `minPCOut := quote*95/100 == 0`.
3. `CallPRC20DepositAutoSwap` is invoked with `minPCOut = 0`, so the swap executes with no minimum-output enforcement.
4. Attacker (or a colluding party) manipulates the pool price around the swap execution (e.g., via other same-block transactions) so the swap settles at a much worse rate than the true quote, extracting value from the pool while the depositor/protocol absorbs the loss; the `UniversalTx` is recorded as `SUCCESS` with no error surfaced.
