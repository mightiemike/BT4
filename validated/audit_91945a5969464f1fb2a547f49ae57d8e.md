### Title
Stale rejection weight is never reconciled when a signer flips from Reject to Accept, permanently inflating `total_weight_rejected` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s per-block tallying logic in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` tracks two independent, monotonically-increasing accumulators, `total_weight_approved` and `total_weight_rejected`, inside a shared `BlockStatus` struct. A single signer is guarded against double-counting *within* each branch (`gathered_signatures.contains_key` for accept, `responded_signers.insert` for reject), but the two branches use **different** guard sets, so a signer who first rejects and later reconsiders and accepts the same block has their rejection weight counted into `total_weight_rejected` **and never removed**, while their acceptance weight is separately counted into `total_weight_approved`. This is directly analogous to the reported `BoostController.removeBoostDelegation` bug: an accounting mutation (vote change) is applied without validating/reconciling the complementary state, leaving a permanently inflated total.

### Finding Description
`BlockStatus` (lines 70–82) holds:
```rust
pub responded_signers: HashSet<u32>,
pub gathered_signatures: BTreeMap<u32, MessageSignature>,
pub total_weight_approved: u32,
pub total_weight_rejected: u32,
``` [1](#0-0) 

On `BlockResponse::Accepted`, weight is only added if the signer is not already in `gathered_signatures`:
```rust
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [2](#0-1) 

On `BlockResponse::Rejected`, weight is only added if the signer is newly inserted into `responded_signers`:
```rust
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [3](#0-2) 

Sequence that breaks the intended equality (`each signer's weight should ultimately count toward at most one live bucket that reflects their current vote`):
1. Signer S (slot `k`, weight `w`) sends `Rejected` for block `B`. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
2. Signer S reconsiders (a scenario the code explicitly anticipates — see the comment in `stacks-signer/src/v0/signer.rs` about signers changing votes on reconsideration) and sends `Accepted` for the same `B`.
3. In the accept branch, the guard checked is `gathered_signatures.contains_key(&k)`, which is still `false` (S never accepted before) — so `total_weight_approved += w` executes.
4. `responded_signers.insert(k)` is now a no-op (already present from step 1); there is **no code path that decrements `total_weight_rejected` or otherwise removes S's stale rejection weight**.

Result: `w` is now counted simultaneously in both `total_weight_approved` and `total_weight_rejected` for the same block, and this is permanent for the lifetime of that `BlockStatus` entry — exactly mirroring the reported bug's "delegation gets deleted regardless of subtraction success," where a state-changing action fails to keep the aggregate totals consistent with removed/superseded per-actor state.

### Impact Explanation
`total_weight_rejected` is read directly by the miner's consensus-critical wait loop in `signer_coordinator.rs`:
```rust
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ...
    return Err(NakamotoNodeError::SignersRejected { temporarily_excluded_txids, permanently_excluded_txids });
}
``` [4](#0-3) 

Because stale reject weight from a signer who has already flipped to Accept is never purged, a single signer (or a handful, well below the 70% weight threshold) can:
- Permanently inflate `total_weight_rejected` for a given block hash by rejecting once and then accepting, contributing "phantom" rejection weight even though their true current vote is acceptance.
- Push the miner into believing a "blocking minority" (`> 30%` weight) opposes the block when the *actual* live opposition is smaller, causing the miner to abandon a block that in reality has legitimate majority/threshold support — a false negative verdict.
- Trigger `permanently_excluded_txids`/`temporarily_excluded_txids` based on this stale, inflated rejection tally, again derived from votes that no longer represent the signers' actual position (`info.total_weight`/`info.problematic_weight` accumulation is similarly one-directional, with no decrement path).
- Because this tallying is done independently and locally by every miner/coordinator process observing the StackerDB event stream, differing message arrival timing/ordering across nodes can cause different miners to reach different `total_weight_rejected`/`total_weight_approved` snapshots for the same block, producing a **temporary tip/verdict disagreement** between nodes — a minority-triggerable, unprivileged (any signer using their own key) divergence, matching the "validation verdict two nodes disagree on" impact class.

This does not require majority collusion; a single signer flipping their own vote is sufficient to desynchronize the two counters, and it is entirely reachable by an unprivileged signer using ordinary protocol messages (no admin/operator key needed).

### Likelihood Explanation
The vote-flip scenario (reject → accept) is not a contrived edge case: the codebase itself documents that a signer's earlier decision "does not change... on rejected blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider" (`stacks-signer/src/v0/signer.rs`, `handle_block_pre_commit`), implying vote reconsideration from reject to accept is an expected/legitimate flow. Any signer that legitimately reconsiders after an initial rejection (e.g., due to updated chain state) will trigger this exact code path in the miner's listener, making the divergence realistically triggerable without any adversarial intent — a genuinely malicious signer can trigger it deliberately and repeatedly across many block proposals to maximize disruption of the tally used for miner decision-making.

### Recommendation
Track each signer's most recent vote decision in a single per-signer map (e.g., `HashMap<u32, VoteDecision>`) rather than two independent monotonic counters guarded by disjoint sets. When a signer's vote flips (reject→accept or accept→reject), atomically remove their weight from the stale bucket before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` always reflect only the *current* live vote of each signer, and their sum never exceeds `total_weight`. Apply the same reconciliation to the per-txid `failed_txids` weight accumulators, which have the identical one-directional accumulation issue.

### Proof of Concept
Not independently executable from static review (no test harness for `StackerDBListener` was inspected in this pass), but the exploit sequence is fully reproducible by driving `StackerDBListener`'s event-processing loop with two crafted `SignerMessageV0` messages from the same signer slot for the same block hash, in this order:
1. `SignerMessageV0::BlockResponse(BlockResponse::Rejected(rejected_data))` for block `B`, signer slot `k`, weight `w` → `total_weight_rejected == w`.
2. `SignerMessageV0::BlockResponse(BlockResponse::Accepted(accepted))` for the same block `B`, same slot `k` → `total_weight_approved == w` while `total_weight_rejected` remains `w` (unchanged).

Assert that after step 2, `block.total_weight_approved + block.total_weight_rejected == 2 * w` even though only one signer of weight `w` is involved — i.e., the same signer's weight is present in both buckets simultaneously, which should be impossible if the tally is meant to reflect current, non-overlapping vote state.
