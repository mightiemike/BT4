## Title
DeleteAccount charges a fixed action fee while iterating and removing an unbounded number of access-key and contract-data trie entries with no compute accounting - (File: `runtime/runtime/src/actions.rs`)

### Summary
The External Report describes AuctionDemo's `returnHighestBid`/`claimAuction`/`cancelAllBids` iterating a never-shrinking `auctionInfoData` array inside functions charged with a fixed cost, letting an attacker inflate the array with dust bids until the loop exceeds the block gas limit and permanently DoSes `claimAuction`. The structural analog in nearcore is `action_delete_account`, which triggers `remove_account` to iterate two unbounded, attacker-inflatable trie ranges (an account's access keys and its contract-data entries) while `DeleteAccount`'s send/exec fees are fixed, protocol-configured constants (`action_delete_account` in `parameters_testnet.yaml`) independent of how many keys/data entries exist.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) gates deletion on a single scalar check: `account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` [1](#0-0) , where `account_storage_usage` is the account's tracked `storage_usage` field minus contract-code bytes. If the check passes, it unconditionally calls `remove_account` [2](#0-1) .

`remove_account` (`core/store/src/utils/mod.rs:504-575`) performs two full trie-range iterations under a lock, each fully materialized into a `Vec` before any deletion:
1. Iterates every access-key/gas-key-nonce row under the account's access-key prefix, collecting them into `keys_to_remove` [3](#0-2) .
2. Iterates every contract-data row under the account's contract-data prefix, collecting into `data_keys` [4](#0-3) .

Compute accounting is charged **only** for gas-key nonce rows (`storage_removes_compute`, driven by `remove_result.gas_key_nonce_count`/`gas_key_nonce_total_key_bytes`) [5](#0-4) . There is no compute or gas charge that scales with the number of plain access-key removals or the number of contract-data-key removals performed in the two loops above — those are billed only through the fixed, protocol-config `delete_account` action fee [6](#0-5) .

The only backstop is `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, a byte-size cap on the account's *total* storage usage (access keys + gas key nonces + contract data + code), enforced once at the top of `action_delete_account`. This caps aggregate bytes, but it does not directly cap the *number of trie rows/keys* that must be individually parsed, hashed, and removed — an attacker can pack many small, cheap access keys or many small contract-data entries (each `storage_num_extra_bytes_record` ~40 bytes plus key/value) up to that byte budget, maximizing row *count* rather than byte size, since ordinary access-key removal work is uncompensated.

This is structurally the same class of bug as the AuctionDemo report: a state array/collection that an unprivileged caller can grow (via `AddKey`/contract `storage_write` actions, both of which the same account signs and pays storage rent for) is later walked in full by a different, flat-fee-priced operation (`DeleteAccount`), with no per-item metering for the bulk of the walked collection.

### Impact Explanation
Because `DeleteAccount`'s exec fee is fixed and independent of the number of access keys/contract-data rows removed, an attacker-controlled account that maximizes row count within the storage-usage cap can make a single `DeleteAccount` receipt perform trie work (row-by-row key parsing under `trie_key_parsers`, plus `state_update.remove` calls) whose actual compute cost is not reflected in the gas charged. If the uncompensated work for the access-key and contract-data loops is large enough relative to `compute_limit`/`gas_limit` accounting, this under-charges the chunk's real per-receipt compute budget, which is the same "unbounded work billed at a fixed price" pattern the report flags — a state-transition cost-accounting bug rather than a full network halt, since (a) the byte-cap does bound the worst case somewhat, and (b) `remove_account` operates on the caller's own account, so any node applying the chunk must still do the real work regardless of how it was billed, risking uneven compute/gas accounting between what was charged and what was executed (a potential state-witness/compute-limit divergence source), rather than an attacker permanently freezing a shared queue as in AuctionDemo's `claimAuction`.

### Likelihood Explanation
Reachable by any account holder with attach-only actions (`AddKey` many times, or `storage_write` many small values from within a contract, both unprivileged actions), followed by a single `DeleteAccount` action — no validator, network, or protocol privilege required. However, exploitability depends on how large `MAX_ACCOUNT_DELETION_STORAGE_USAGE` is set and how expensive a single trie-row parse+remove actually is relative to the fixed `delete_account` fee; I could not fully verify the numeric constant for `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` in the available index, nor precisely quantify whether the uncompensated per-row cost of ordinary (non-gas-key) access-key and contract-data removal is large enough at the capped byte budget to meaningfully exceed the fixed exec fee's gas allotment. This materially limits confidence in the severity/likelihood.

### Recommendation
Charge compute/gas for *every* trie row removed in `remove_account` — not only gas-key nonce rows — using the same `storage_removes_compute`-style accounting already applied to gas-key nonces, so the two unbounded loops in `remove_account` (access keys, contract data) are priced proportionally to the number of rows actually walked and removed, independent of the coarse `MAX_ACCOUNT_DELETION_STORAGE_USAGE` byte cap.

### Proof of Concept
1. Attacker creates/owns account `victim.near`.
2. Attacker issues many `AddKey` actions (each cheap, paying only storage rent) and/or contract `storage_write` calls with many small key/value pairs, keeping total `storage_usage` under `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` but maximizing the *count* of access-key/contract-data rows.
3. Attacker submits a single `DeleteAccount` action on `victim.near`.
4. `action_delete_account` passes the byte-size check [7](#0-6)  and calls `remove_account`, which iterates and removes every access-key and contract-data row [8](#0-7)  for a fixed `delete_account` fee [6](#0-5) , with no compute charge attributed to the non-gas-key portion of that work [5](#0-4) .
