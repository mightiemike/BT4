## Analysis Result

Reducing the external report to its core invariant: **a value contributing to committed/authenticated state must be included in the check that certifies "local result == authenticated result."** In Mellow, `tvl()` omitted pending fees from the authenticated value. The Aptos-native analog is in the state-commitment integrity layer: **the replay-verification comparator omits checkpoint state roots from the authenticated-match check.**

### Title
`TransactionOutput::ensure_match_transaction_info()` omits state/hot-state/position checkpoint-hash comparison, letting replay-verify accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/debugging tooling to assert that a locally re-executed transaction output matches the authenticated `TransactionInfo` recorded on-chain (i.e., committed to the transaction accumulator). It compares status, gas, write-set hash, and event root hash against the `TransactionInfo`, but never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` builds the expected write-set hash and event-root hash and checks them, plus status and gas, against the supplied `txn_info`, then returns `Ok(())` — the state checkpoint hash fields are explicitly skipped, as flagged by the code's own TODO: [2](#0-1) 

This function is the sole correctness check used by:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the tool whose entire purpose is to re-execute historical mainnet transactions from a backup archive and confirm the locally computed result matches the authenticated one persisted in `TransactionInfo`. [3](#0-2) 
- `aptos-move/cli/src/commands.rs`, used for CLI-driven transaction replay/verification. [4](#0-3) 

Because `TransactionInfo` (V1) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as authenticated fields committed into the transaction accumulator (and hence into the ledger-info-signed root), these fields are exactly the "pending value" that state-checkpoint stages (`DoStateCheckpoint::run`, `compute_position_checkpoint`) compute deterministically from the state/hot-state/position Merkle trees. [5](#0-4) [6](#0-5) 

If a bug anywhere in the state-checkpoint/state-summary/position-state pipeline (JMT computation, sparse Merkle tree update, position-state SMT extension, etc.) produced a state root that diverges from what was actually authenticated on-chain, `replay_on_archive` would still report success, because its only correctness oracle — `ensure_match_transaction_info` — never inspects the checkpoint-hash fields at all.

### Impact Explanation
Replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`, exercised by `testsuite/replay-verify`) is the primary mechanism by which mainnet execution-determinism regressions and storage-schema divergences are caught before/after upgrades. A silent gap here means a class of state-root corruption bugs (e.g., in JMT restore, position-state SMT, or hot-state root computation) would pass replay-verify undetected, i.e., "wrong accumulator/state root accepted as valid" by the verification tool itself. This directly weakens the state-integrity gate's detection surface for "committed state that differs from the correct VM result."

### Likelihood Explanation
This is not a theoretical gap — it's an explicitly acknowledged, currently-shipped omission (see the TODO in the code itself), gated to matter once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` features are enabled, at which point `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` become load-bearing authenticated commitments that this verifier still won't check. Even today, `state_checkpoint_hash` (the plain state root, unconditionally present in `TransactionInfoV0`/`V1`) is skipped, so any latent state-root computation bug is currently invisible to `replay_on_archive`. [7](#0-6) 

### Recommendation
Add explicit comparisons in `ensure_match_transaction_info` for `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (each `Option<HashValue>`, only checked when both sides have `Some`, or required to match on checkpoint transactions), mirroring how write-set/event root hashes are already validated. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, exactly as the existing TODO already recommends.

### Proof of Concept
1. Take a checkpoint transaction (block epilogue) at version `V` on a corrupted node/backup where the locally re-computed state root differs from the network-authenticated `TransactionInfo.state_checkpoint_hash` at `V` (e.g., due to a hypothetical JMT/position-state bug).
2. Run `storage/db-tool/src/replay_on_archive` (or the CLI replay path) against this backup/version.
3. `execute_and_verify` calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ..)`. [8](#0-7) 
4. Because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`, the call returns `Ok(())` despite the state root mismatch, and the tool reports the transaction as successfully verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
