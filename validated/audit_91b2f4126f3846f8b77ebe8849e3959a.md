## Analysis

Tracing the exact path: `RemoteTxnWrite` explicitly documents that `write_op` is `None` when the producing transaction aborts: [1](#0-0) 

`CrossShardCommitReceiver::start` (driven by `receive_cross_shard_msg`, itself fed by `CoordinatorClient::receive_execute_command` → `ShardedExecutorService::execute_transactions_with_dependencies` → `CrossShardCommitSender`) unconditionally converts this into `None` and pushes it into the dependent shard's cache: [2](#0-1) 

`CrossShardStateView::set_value` writes directly into the pre-registered `cross_shard_data` entry for that key: [3](#0-2) 

Critically, keys that participate in a cross-shard dependency edge are **pre-inserted** into `cross_shard_data` as `RemoteStateValue::waiting()` before execution starts: [4](#0-3) 

The struct's own doc comment states the base view is consulted only "when a cross shard state value is **not available** in the hashmap" — but a dependency key is always present in the map (it was inserted during construction), so once `set_value` writes `Ready(None)` into it, `RemoteStateValue::get_value` will forever return `None` for that key, and the fallback-to-`base_view` path documented at the top of the file is never reached for that key: [5](#0-4) [6](#0-5) 

So when a producing transaction aborts (correct serial-execution semantics: the key's value is unchanged — whatever it was before this transaction ran, e.g. from `base_view` or an earlier committed writer), the dependent shard instead observes a **phantom deletion** (`get_state_value` returns `None`) rather than the pre-transaction value.

## Caveats / what I could not verify

I was unable to locate and inspect `CrossShardCommitSender`'s implementation (the `TransactionCommitHook::on_transaction_committed` callback referenced via the `aptos_block_executor::txn_commit_hook::TransactionCommitHook` import) within the available iterations, so I cannot confirm with certainty whether the sender ever substitutes a fallback/read value instead of `None` for keys a transaction was expected to write but didn't touch due to abort. The `RemoteTxnWrite` doc comment ("write op is None if the transaction is aborted") and the unconditional handling on the receiver side strongly indicate that no such substitution happens, but this is the one link in the chain I could not directly read.

Because sharded block execution is Aptos's mechanism for horizontally scaling execution while still requiring bit-identical results to serial execution (different validators/operators may run different shard counts), a divergence here is a genuine state-root/consensus-divergence risk between a sharded executor and a serial (or differently-sharded) executor processing the identical block — matching the "hard-fork-only divergence" criterion in the prompt.

### Title
Aborted transaction's `write_op: None` is cached as a permanent state deletion in `CrossShardStateView`, causing sharded execution to diverge from serial execution - (File: `aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

### Summary
`CrossShardCommitReceiver::start` converts an aborted producing transaction's `RemoteTxnWrite{write_op: None}` into `cross_shard_state_view.set_value(&state_key, None)`. Because dependency keys are pre-registered in `CrossShardStateView::cross_shard_data`, this permanently overwrites the cached entry with "no value," and the documented base-view fallback (used only for keys absent from the map) never triggers for it.

### Finding Description
On abort, the correct semantics for the dependent transaction's read of the state key is "unchanged from whatever it was before this transaction" (base state or an earlier writer's committed value), not "deleted." The receiver/state-view pipeline has no representation for "unwritten/unchanged" distinct from "deleted," so it always collapses `write_op: None` into a cached `None` value that the state view will serve to any dependent transaction reading that key.

### Impact Explanation
If a validator/operator's sharded executor hits this abort-then-dependent-read pattern, the resulting `TransactionOutput`/write set for the dependent transaction can differ from what serial execution (or a differently-sharded execution) would produce for the identical block — e.g. a resource existence check that should succeed instead observes "resource missing." This produces a different transaction output/state root for the same block depending on execution topology, which is a hard-fork-class divergence.

### Likelihood Explanation
Requires only an ordinary transaction abort (any unprivileged transaction that gets discarded/aborted for any normal reason — gas, sequence number, contract-logic abort) combined with the partitioner assigning a cross-shard dependency edge to a state key that transaction was anticipated to write. This is a normal, frequent occurrence in sharded execution, not a crafted attack requiring special privilege.

### Recommendation
Distinguish "aborted / did not write" from "explicit deletion" in `RemoteTxnWrite`/`CrossShardMsg`, and on the receiver side, when a transaction aborts, do not overwrite the cached cross-shard value; instead resolve the dependent read against the correct predecessor value (the last actual writer in serial order, or `base_view` if none), so `CrossShardStateView` never serves a phantom deletion for keys whose anticipated writer aborted.

### Proof of Concept
Conceptual reproduction (not executed, given ask-only/read-only tooling):
1. Partition a block so shard A's txn `i` is flagged (via `TransactionWithDependencies::cross_shard_dependencies`) as writer of key `K`, and shard B's txn `j` depends on reading `K` after `i`.
2. Craft txn `i` to abort deterministically (e.g., insufficient balance / explicit `abort` in Move) while `K` already holds a value in `base_view` prior to the block.
3. Run via `ShardedExecutorService::execute_transactions_with_dependencies`; observe `CrossShardCommitReceiver` calls `set_value(K, None)` per [2](#0-1) .
4. Shard B's execution of txn `j` reads `K` via `CrossShardStateView`, receiving `None` instead of the pre-existing `base_view` value.
5. Compare against serial execution of the same block (no sharding) — the reader should see the original `base_view` value of `K`, not `None`; the divergence in `j`'s resulting `WriteOp`/output confirms the bug.

    pub fn create_cross_shard_state_view(
        base_view: &'a S,
        transactions: &[TransactionWithDependencies<AnalyzedTransaction>],
    ) -> CrossShardStateView<'a, S> {
        let mut cross_shard_state_key = HashSet::new();
        for txn in transactions {
            for (_, storage_locations) in txn.cross_shard_dependencies.required_edges_iter() {
                for storage_location in storage_locations {
                    cross_shard_state_key.insert(storage_location.clone().into_state_key());
                }
            }
        }
        CrossShardStateView::new(cross_shard_state_key, base_view)
    }

    pub fn get_value(&self) -> Option<StateValue> {
        let (lock, cvar) = &*self.value_condition;
        let mut status = lock.lock().unwrap();
        while let RemoteValueStatus::Waiting = *status {
            status = cvar.wait(status).unwrap();
        }
        match &*status {
            RemoteValueStatus::Ready(value) => value.clone(),
            RemoteValueStatus::Waiting => unreachable!(),
        }
    }

    pub fn is_ready(&self) -> bool {
        let (lock, _cvar) = &*self.value_condition;
        let status = lock.lock().unwrap();
        matches!(&*status, RemoteValueStatus::Ready(_))
    }
