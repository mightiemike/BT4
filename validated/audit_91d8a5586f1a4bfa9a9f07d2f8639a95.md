## Analog Found

### Title
Unbounded Allocation from Attacker-Controlled Array Size in Deprecated Syscall Felt-Array Reader - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The CVE-2023-5371 bug class is "a length/size field taken directly from untrusted input is used to drive a memory allocation before the actual amount of available data is validated," causing a memory-exhaustion denial of service. The `read_felt_array` helper used by Cairo 0 ("deprecated") syscall handling in the blockifier reproduces this pattern: it reads an `array_size` value straight out of Cairo VM memory — content that is fully controlled by the executing contract's code/calldata — and passes it, unvalidated against any application-level bound, into a routine that allocates a buffer sized by that value.

### Finding Description
`read_felt_array` reads the array-size felt from the VM at the current pointer and, without capping it, converts it to a `usize` and forwards it to `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)`: [1](#0-0) 

`felt_range_from_ptr` itself does no bounds checking against a maximum before delegating to the underlying VM memory-range accessor with the attacker-supplied `size`: [2](#0-1) 

`array_size` originates from a `Felt` written into VM memory by the executing (attacker-deployed or attacker-invoked) Cairo 0 contract as part of a deprecated syscall request (e.g. building the payload for `emit_event`, `send_message_to_l1`, or similar array-taking legacy syscalls that funnel through this helper, as referenced in `crates/blockifier/src/execution/deprecated_syscalls/mod.rs`). A `Felt` can encode values up to ~2^251, and `usize::try_from(array_size.to_biguint())` only fails if the value exceeds `usize::MAX` (2^64-1 on 64-bit targets) — it does not reject merely "very large but representable" sizes. Any size up to `usize::MAX` is accepted and handed to the VM range-read/allocation path before any check confirms that the corresponding memory segment actually contains that many populated cells.

This mirrors the Wireshark RTPS dissector bug: a size value taken from attacker-controlled input is used to size an allocation before the real amount of backing data is validated, so a small malicious input can trigger a vastly disproportionate allocation attempt.

### Impact Explanation
A contract deployer/caller reachable through ordinary transaction execution (any Cairo 0 class invoking the affected deprecated syscall) can supply a huge `array_size` felt. This drives an allocation request sized by that attacker-chosen value on every sequencer/full node that re-executes the transaction (including in blockifier execution and Starknet OS re-execution). Because Rust aborts the process on allocation failure (rather than returning a recoverable error), a sufficiently large size can crash the executing node process, resulting in a denial-of-service that stops the network from confirming new transactions if triggered broadly — satisfying the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Likelihood is constrained by two factors I could not fully verify with the available tooling: (1) whether `cairo-vm`'s underlying `get_integer_range` implementation actually pre-allocates a `Vec` of the requested `size` before validating that the memory segment holds that many values, or whether it validates segment bounds first (this implementation lives in the external `cairo-vm` crate, outside this repository, so I cannot confirm the exact allocation-vs-validation order from the indexed code); and (2) which specific deprecated syscalls route through `read_felt_array` and whether any caller-side bound is already enforced upstream before this helper runs. Reaching this code only requires deploying/invoking a legacy (Cairo 0) contract that crafts a malicious syscall request, which is achievable by any unprivileged transaction sender, so if the underlying VM call does allocate eagerly, likelihood is high; if it validates segment size first, likelihood drops to low/none.

### Recommendation
Add an explicit upper bound check on `array_size` in `read_felt_array` (e.g., reject values above a small sane maximum such as the current segment's actual used size, or a protocol-defined max array length) before converting to `usize` and calling into `felt_range_from_ptr`/`vm.get_integer_range`, mirroring the length-vs-available-data checks already used elsewhere in the codebase for similar length-prefixed reads (e.g., `crates/apollo_propeller/src/padding.rs` checks `original_message_length > message.len() - varint_prefix_len` before slicing, and `crates/apollo_network/src/sqmr/messages.rs` enforces `MAX_MESSAGE_SIZE`) [3](#0-2) [4](#0-3) .

### Proof of Concept
1. Deploy or invoke a Cairo 0 (deprecated) class that constructs a syscall request buffer (e.g. for `emit_event`/`send_message_to_l1`) in VM memory, but sets the array-size felt field to a very large value (e.g., `2^63`) while providing little or no actual backing data.
2. Submit the invoking transaction to the sequencer.
3. During blockifier execution, `read_felt_array` reads the oversized `array_size`, converts it to `usize`, and calls `felt_range_from_ptr(vm, array_data_start_ptr, array_size)`, attempting to materialize a `Vec<Felt>` (or equivalent range read) sized to the attacker-chosen value.
4. If the underlying VM range accessor allocates before validating actual segment contents, the node attempting execution/re-execution can exhaust memory or abort, denying further block processing.

**Note:** I could not inspect the internal implementation of `cairo-vm`'s `get_integer_range` (it is an external dependency, not part of this repository's indexed source), so I cannot fully confirm whether it allocates the buffer before validating the segment's real size. This is the key uncertainty for likelihood; further verification would require reading the `cairo-vm` crate source directly (e.g., via a Devin session with full filesystem/dependency access).

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
