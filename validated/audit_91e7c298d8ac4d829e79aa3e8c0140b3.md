### Title
Sign-weight oracle (`GetTransactionSignWeightServlet` → `TransactionUtil.getTransactionSignWeight`) diverges from actual broadcast-time enforcement (`TransactionCapsule.validateSignature`) for not-yet-activated accounts - ([File: actuator/src/main/java/org/tron/core/utils/TransactionUtil.java])

### Summary
`TransactionUtil.getTransactionSignWeight` unconditionally throws `PermissionException("Account does not exist!")` when the owner `AccountCapsule` is `null`, producing a `PERMISSION_ERROR` verdict for the HTTP client. `TransactionCapsule.validateSignature`, which is the function actually exercised during transaction acceptance/broadcast, instead synthesizes a default permission (`AccountCapsule.getDefaultPermission` for `permissionId == 0`, or `AccountCapsule.createDefaultActivePermission` for `permissionId == 2`) when the account is `null`, and can return `true` (pass) for exactly the same transaction. This is a genuine, code-confirmed logical divergence between the two functions.

### Finding Description
In `TransactionUtil.getTransactionSignWeight` (actuator/src/main/java/org/tron/core/utils/TransactionUtil.java:224-244):
```
AccountCapsule account = chainBaseManager.getAccountStore().get(owner);
if (Objects.isNull(account)) {
  throw new PermissionException("Account does not exist!");
}
```
Any `null` account immediately short-circuits to a `PermissionException`, caught further down and mapped to `Result.response_code.PERMISSION_ERROR` (lines 265-267).

In `TransactionCapsule.validateSignature` (chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:468-496):
```
AccountCapsule account = accountStore.get(owner);
Permission permission = null;
if (account == null) {
  if (permissionId == 0) {
    permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
  }
  if (permissionId == 2) {
    permission = AccountCapsule.createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
  }
} else {
  permission = account.getPermissionById(permissionId);
}
```
For a `permissionId` of `0` (owner) or `2` (default active), this path synthesizes a valid `Permission` object for the not-yet-existing account and continues to `checkPermission`/`checkWeight`, potentially returning `true` if the signature satisfies the synthesized threshold. This is exactly the logic used to accept transactions from freshly-generated (not-yet-on-chain) addresses, a normal and expected TRON behavior (an address is "activated" the first time it receives TRX/appears in a transaction).

Both functions are reachable by an unprivileged attacker: the HTTP endpoint `GetTransactionSignWeightServlet.doPost` (framework/src/main/java/org/tron/core/services/http/GetTransactionSignWeightServlet.java:24-37) accepts an arbitrary unsigned/partially-signed `Transaction` from any anonymous caller and forwards it into `transactionUtil.getTransactionSignWeight(transaction)` with no authentication. Meanwhile `validateSignature` is invoked from the real broadcast/acceptance path in `Manager` (chainbase/framework `db.Manager`, confirmed by 12 references) as part of the actual state-changing transaction validation.

Consequence: for a `TransferContract` (or any contract) signed with the correct key for a not-yet-created owner address, using the default owner permission (id 0) or default active permission (id 2), the HTTP sign-weight API will report `PERMISSION_ERROR` ("Account does not exist!") even though the exact same transaction would be accepted (`ENOUGH_PERMISSION`-equivalent, i.e., pass) by `validateSignature` at actual broadcast time.

### Impact Explanation
This is an oracle/decision-consistency bug, not a fund-theft or accounting-corruption bug. The scoped impact is: a downstream automated signer/operator/relay service that queries `wallet/getTransactionSignWeight` to decide "is this transaction properly authorized before I co-sign/relay it?" gets a false negative (`PERMISSION_ERROR`) for legitimate, not-yet-activated multisig/owner-signed transactions, and could reject or fail to co-sign transactions that would actually succeed on-chain. It does not by itself let the attacker steal funds, corrupt state, or create/destroy value — the actual chain-level enforcement (`validateSignature` inside `Manager`) is unaffected and remains the authoritative gate. The bug is a service/API correctness defect (decision-oracle inconsistency) rather than a direct on-chain compromise; matches at most a low-severity "informational/logic inconsistency" bounty class, not an asset-loss or consensus-divergence class, since the actuator-level enforcement used for real state transitions is untouched.

### Likelihood Explanation
Trivial to trigger: an unprivileged client just needs to construct a transaction whose owner address has never appeared on-chain (any freshly generated keypair) and POST it, unsigned or signed, to `/wallet/getTransactionSignWeight`. No fees, no on-chain resources, no special permissions are required, and it is fully repeatable/deterministic. However, it can only be used to feed misleading information to a party that trusts this endpoint as authoritative for authorization decisions; it cannot force the network into an incorrect state directly.

### Recommendation
Make `TransactionUtil.getTransactionSignWeight` mirror `TransactionCapsule.validateSignature`'s handling of `null` accounts: when `account == null`, synthesize the default permission via `AccountCapsule.getDefaultPermission`/`createDefaultActivePermission` for `permissionId` 0/2 instead of unconditionally throwing `PermissionException`, so the sign-weight oracle and actual enforcement agree for not-yet-activated accounts.

// JUnit-style PoC (conceptual, using existing test infra from TransactionUtilTest / TransactionCapsuleTest)

Transaction unsignedTrx = buildTransferContract(ownerAddress, toAddress, amount, permissionId);

TransactionSignWeight tsw = transactionUtil.getTransactionSignWeight(signedTrx);

boolean ok = TransactionCapsule.validateSignature(signedTrx,

assertTrue(ok); // observed: passes
