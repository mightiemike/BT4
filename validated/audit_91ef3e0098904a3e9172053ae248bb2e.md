### Title
Webhook shop-domain header is not covered by HMAC signature, allowing a malicious merchant to redirect their own valid webhook payload to another shop's session context - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
The webhook validation flow only computes and checks the HMAC over the raw request body [1](#0-0) . The `X-Shopify-Shop-Domain` header (and other identifying headers like topic/webhook id) is read and trusted separately, without being part of the signed payload [2](#0-1) . This mirrors the reported bug class: the code validates one thing (the HMAC/bid), but lets the caller freely control a security-relevant field (`recipient` in the original report, `domain` here) that determines who the resulting action is attributed to.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` performs two independent steps:
1. `validateHmacFromRequestFactory` computes an HMAC over `rawBody` only, using the app's static `apiSecretKey`, and compares it to the `X-Shopify-Hmac-Sha256` header [3](#0-2) .
2. `checkWebhookHeaders`/`checkWebhooksHeaders` separately reads `domain`, `topic`, `webhookId`, `apiVersion` straight from request headers with no cryptographic binding to the body or the HMAC [2](#0-1) .

Because the app's `apiSecretKey` is shared across every shop that installs the app, any merchant that has installed the app receives genuine webhook deliveries (valid body + valid HMAC) for their own shop. Since the shop-domain header is not part of the signed content, that merchant can capture one of their own legitimately-signed webhook requests and simply replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to point at a different (victim) shop, keeping the original body and HMAC intact. `validateFactory` returns `valid: true` with `domain` set to the attacker-supplied header value [4](#0-3) .

Downstream, `authenticateWebhookFactory` (in both the Remix and React Router packages) trusts `check.domain` unconditionally to build the webhook context and to look up/mint an offline session via `ensureValidOfflineSession(params, check.domain)` [5](#0-4) . `ensureValidOfflineSession` loads (or creates) the offline session for whatever shop string it's given [6](#0-5) , then the resulting `WebhookContext` is built with `session` and `admin` client scoped to that (attacker-chosen) shop [7](#0-6) . The app's registered webhook handler code then executes business logic believing it is acting on behalf of `check.domain`/the victim shop, while all payload content is fully attacker-controlled data from the attacker's own store.

### Impact Explanation
An attacker who installs the target app on one shop can forge webhook requests that are accepted as valid and attributed to any other shop domain, obtaining that shop's offline session/admin client inside the webhook handler context and feeding it attacker-controlled payload data. This is a cross-tenant confused-deputy condition: a per-shop-domain header, not covered by any signature, decides which merchant's authenticated context (session + admin client) processes the (attacker-controlled) webhook payload. Depending on what an app's webhook handlers do with `payload`/`admin` (e.g., writing data, triggering GraphQL mutations, sending notifications), this can lead to unauthorized cross-tenant actions or data corruption in another merchant's store using that merchant's real access token.

### Likelihood Explanation
Likelihood is moderate to high for a malicious/curious merchant: they only need to (a) install the target app once on a shop they control, (b) capture one webhook delivery (trivial — just log the endpoint's request headers/body once), and (c) replay it with the `Shop-Domain` header modified. No secrets need to be leaked or brute-forced; this exploits the fact that HMAC coverage excludes the domain header entirely, which is directly reachable from an unauthenticated webhook HTTP endpoint.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the HMAC-protected data, or otherwise cryptographically verify that the domain header actually corresponds to the shop that produced the signature. At minimum, cross-check the resolved `domain` against an expected/known set of currently-installed shops before using it to load or mint an offline session, and/or include the domain header in the HMAC computation used by `validateHmacFromRequestFactory` for webhook validation, analogous to how OAuth callback state and HMAC are both verified together in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` (`validQuery`) [8](#0-7) .

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `products/update`) so Shopify delivers a webhook to the app's `/webhooks` endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared `apiSecretKey`.
3. Capture the exact `rawBody` and `X-Shopify-Hmac-Sha256` value from that delivery.
4. Replay an HTTP POST to the same `/webhooks` endpoint with the identical body and HMAC header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. Observe that `shopify.webhooks.validate` / `authenticate.webhook` returns `valid: true` / a `WebhookContext` with `shop: 'victim-shop.myshopify.com'`, and that `ensureValidOfflineSession` is invoked with the victim's domain, producing a session/admin client scoped to the victim shop while the payload content is fully attacker-controlled — as seen in `authenticateWebhookFactory` [9](#0-8) .

Note: I was not able to fully verify at what layer (Shopify's delivery infrastructure vs. this library) domain-header integrity might be enforced outside of this repo's code; my analysis is scoped strictly to the validation logic present in this codebase, where no such binding exists.

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
