### Title
Job proposal spec approval/cancellation lacks atomic status guard, permitting duplicate processing on repeated/concurrent calls - (File: core/services/feeds/service.go, core/services/feeds/orm.go)

### Summary
`InvestmentManager._reviewRedemptionRequest` allowed the same request to be reviewed repeatedly because there was no persisted guard preventing re-processing of an already-handled state. In Chainlink's Feeds Manager, `service.ApproveSpec` performs its "already approved/rejected/revoked" validation (`isApprovable`) as a separate read before starting the DB transaction, but the actual state transition executed by `orm.ApproveSpec` and `orm.CancelSpec` is an unconditional `UPDATE ... WHERE id = $2` with no `WHERE status = 'pending'` (or similar) guard tying the mutation to the previously-observed state.

### Finding Description
`service.ApproveSpec` fetches the spec, checks `isApprovable` against the spec/proposal status, and only after that check passes does it enter `s.transact(...)` to create the job and call `tx.orm.ApproveSpec`, which issues: [1](#0-0) 
This `UPDATE job_proposal_specs SET status = $1 ... WHERE id = $2` has no predicate requiring the current status to be `pending` (or `cancelled`, in the case where cancelled specs are approvable); it will succeed as long as the row exists, regardless of its current status. The same pattern exists in `CancelSpec`: [2](#0-1) 
The status/eligibility check (`isApprovable`) lives entirely in the service layer, outside the transaction that performs the mutation: [3](#0-2) [4](#0-3) 
Because the read (`GetSpec`)/check (`isApprovable`) and the write (`tx.orm.ApproveSpec`) are not part of the same atomic unit guarded by the spec's current status, two overlapping calls to `ApproveSpec` for the same spec ID (e.g., a retried API/UI request, or a race between an operator's double submission) can both pass `isApprovable` before either commits, resulting in `CreateJob` and `orm.ApproveSpec`/FMS `ApprovedJob` notification being executed twice for the same proposal.

### Impact Explanation
A successful race results in duplicate job creation and duplicate "approved" notifications sent to the Feeds Manager Service (FMS) backend via `fmsClient.ApprovedJob`, as seen in the approval flow: [5](#0-4) 
This can desynchronize the node's local job-proposal bookkeeping from the remote FMS's view of approvals, create orphaned/duplicate jobs consuming resources, and produce inconsistent `JobProposalCounts` metrics — an accounting/state-integrity issue analogous to the redemption-request double-processing described in the report, though it requires a race window rather than a simple repeat call.

### Likelihood Explanation
Exploitation requires the feeds-manager admin (or an automated retry client) to issue two approval/cancellation requests for the same spec ID that overlap in time before the first transaction commits — this is a narrow race window and does not constitute an authorization bypass; it is a robustness/idempotency gap in a privileged administrative action, not exploitable by an unprivileged actor.

### Recommendation
Make the status check atomic with the mutation by adding a `WHERE status = $expected_status` predicate to the `UPDATE` statements in `orm.ApproveSpec` and `orm.CancelSpec` (and equivalently `orm.RejectSpec`), returning `sql.ErrNoRows`/a distinct error when zero rows are affected due to a stale status, so that only the first of any concurrent calls can transition the spec.

### Proof of Concept
1. Create a pending job proposal spec.
2. Issue two concurrent `ApproveSpec(ctx, id, force)` calls for the same `id` (e.g., via two goroutines or two rapid API requests) before either transaction commits.
3. Both calls pass `isApprovable` (both observe `SpecStatusPending`) since the check reads outside any lock tied to the eventual write.
4. Both calls proceed to `CreateJob` and `tx.orm.ApproveSpec`, each of which succeeds because the `UPDATE` has no status precondition — resulting in two jobs and two `ApprovedJob` notifications to FMS for a single spec.

func (s *service) isApprovable(ctx context.Context, propStatus JobProposalStatus, proposalID int64, specStatus SpecStatus, specID int64) error {
	if propStatus == JobProposalStatusDeleted {
		return errors.New("cannot approve spec for a deleted job proposal")
	}

	if propStatus == JobProposalStatusRevoked {
		return errors.New("cannot approve spec for a revoked job proposal")
	}

	switch specStatus {
	case SpecStatusApproved:
		return errors.New("cannot approve an approved spec")
	case SpecStatusRejected:
		return errors.New("cannot approve a rejected spec")
	case SpecStatusRevoked:
		return errors.New("cannot approve a revoked spec")
	case SpecStatusCancelled:
		// allow approval of a cancelled job if no other spec is approved
		specs, serr := s.orm.ListSpecsByJobProposalIDs(ctx, []int64{proposalID})
		if serr != nil {
			return errors.Wrap(serr, "failed to get latest spec")
		}

		for _, spec := range specs {
			if spec.Status == SpecStatusApproved {
				return fmt.Errorf("the job spec with version %d is already approved", spec.Version)
			}
		}

		slices.SortFunc(specs, func(a, b JobProposalSpec) int { return int(b.Version - a.Version) })
		cancelledIndex := 0
		for _, spec := range specs {
			if spec.ID == specID {
				if cancelledIndex >= 2 {
					return errors.New("only the last two cancelled spec versions may be approved")
				}
				return nil
			}
			if spec.Status == SpecStatusCancelled {
				cancelledIndex++
			}
		}

		return fmt.Errorf("failed to find spec %d associated with proposal %d", specID, proposalID)
	case SpecStatusPending:
		return nil
	default:
		return errors.New("invalid job spec status")
	}
