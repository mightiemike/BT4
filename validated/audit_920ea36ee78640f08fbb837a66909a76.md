### Title
Unbounded blocking `GlobalRateLimiter.acquire()` on the gRPC executor thread pool causes node-wide RPC-API DoS via thread exhaustion - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/GlobalRateLimiter.java])

### Summary
`RateLimiterInterceptor.interceptCall` runs synchronously on the gRPC server's (bounded) executor thread and, in the default (non-`apiNonBlocking`) configuration, calls `GlobalRateLimiter.acquirePermit` → `GlobalRateLimiter.acquire()`, which calls Guava's `RateLimiter.acquire()` with no timeout on both the per-IP and global limiter instances. Because Guava's `RateLimiter.acquire()` never rejects and instead makes the caller sleep for an ever-growing "debt" as more concurrent callers reserve permits, an attacker who opens enough concurrent gRPC calls can drive every blocked call's wait time up and pin down worker threads indefinitely, exhausting the fixed-size RPC executor pool and stalling unrelated legitimate calls.

### Finding Description
`RateLimiterInterceptor.interceptCall` is invoked for every incoming gRPC call on the server's request-handling thread (a fixed-size pool created in `RpcService.initServerBuilder` via `ExecutorServiceManager.newFixedThreadPool(this.executorName, parameter.getRpcThreadNum())`, or the gRPC default executor if `rpcThreadNum <= 0`): [1](#0-0) 

Inside `interceptCall`, both the per-endpoint and global permit acquisitions happen synchronously before the RPC handler even starts: [2](#0-1) 

`acquirePermit` dispatches to `acquire()` (blocking) unless `rate.limiter.apiNonBlocking` is true (default `false` per `RateLimiterConfig`): [3](#0-2) [4](#0-3) 

`GlobalRateLimiter.acquire()` calls Guava's `RateLimiter.acquire()` with no deadline/timeout, on both the per-IP limiter and the shared global limiter: [5](#0-4) 

Guava's `RateLimiter.acquire()` (SmoothRateLimiter) is documented to never reject a request — it reserves a future slot and blocks the calling thread for however long is needed to "catch up," and this wait time grows unboundedly as more concurrent callers reserve permits ahead of it. This is fundamentally different from the per-component `GlobalPreemptibleStrategy`, which the code comments explicitly note was designed with a bounded 2-second timeout (`sp.tryAcquire(DEFAULT_ACQUIRE_TIMEOUT, TimeUnit.SECONDS)`) specifically to avoid "tying up Netty IO / gRPC executor threads while waiting for a permit": [6](#0-5) 

No such bound exists for `GlobalRateLimiter.acquire()`. Since this call is unconditionally executed for every RPC (regardless of which method/component is being called) and runs on the bounded executor thread that also services all other RPCs, an attacker driving a sufficiently large burst of concurrent gRPC calls (from one or many source IPs — the shared global `rateLimiter` instance is not per-IP) can force many worker threads to block simultaneously for extended, unbounded durations, exhausting the pool and preventing unrelated legitimate calls from being scheduled at all.

No existing mitigation stops this: there is no timeout on the global `RateLimiter.acquire()` call, no separate async/offload path, and the per-endpoint semaphore-based limiter (which does have a timeout) does not protect calls that reach the always-invoked `GlobalRateLimiter` stage.

### Impact Explanation
This is a node-wide RPC-API availability issue (DoS via RPC-API): once the fixed-size gRPC executor pool is saturated with threads blocked inside `RateLimiter.acquire()`, all RPC calls — including from legitimate clients/other DApps/exchanges — stall until the queued reservations drain, which can take an unbounded amount of time proportional to the number of concurrent excess requests the attacker sent. This matches the "DoS via RPC-API" bounty impact class.

### Likelihood Explanation
Preconditions are the default node configuration (`apiNonBlocking=false`, the documented default in `RateLimiterConfig`) and the ability to open many concurrent TCP/gRPC connections/streams, which is available to any unprivileged, anonymous network client — no signed transaction, funded account, or special role is required. The attack is cheap (no on-chain fee, no energy/bandwidth cost) and fully repeatable; it only requires enough concurrent connections/streams to exceed the configured global/IP QPS and the size of the server's executor pool, both of which are achievable from a single well-resourced attacker.

### Recommendation
Bound the blocking wait in `GlobalRateLimiter.acquire()` the same way `GlobalPreemptibleStrategy` does: use `RateLimiter.tryAcquire(timeout, TimeUnit)` with a small, configurable timeout instead of the unbounded `RateLimiter.acquire()`, and treat a timeout as permit-denied (return `false`/close the call with `RESOURCE_EXHAUSTED`) rather than blocking indefinitely. Alternatively, move the blocking-wait logic off the gRPC executor thread (e.g., via a scheduled/async acquire with `CompletableFuture`) so that blocked callers do not consume worker-pool capacity.

  // Non-blocking: immediately rejects if no permit is available. Used when the
  // apiNonBlocking switch is on, to shed overload instead of tying up Netty IO /
  // gRPC executor threads while waiting for a permit.
  public boolean tryAcquire() {
    return sp.tryAcquire();
  }

  public boolean acquire() {
    try {
      return sp.tryAcquire(DEFAULT_ACQUIRE_TIMEOUT, TimeUnit.SECONDS);
    } catch (InterruptedException e) {
      // Restore the interrupt flag and reject — caller must not release a permit
      // it never acquired.
      logger.error("acquire permit with error: {}", e.getMessage());
      Thread.currentThread().interrupt();
      return false;
    }
  }
