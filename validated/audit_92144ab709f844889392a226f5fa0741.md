### Title
`ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting `replay_on_archive` accept a divergent state root as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single correctness check used by the archive replay-verify tool to confirm that locally re-executing a historical transaction produces the same result the chain committed. It checks status, gas, write-set hash, and event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values recomputed by local execution.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only four fields (status, gas, write-set hash, event root hash) and returns `Ok(())` unconditionally afterward, with a code comment acknowledging the gap: [2](#0-1) 

This function is the sole verification predicate used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and compares the freshly computed `TransactionOutput` against the `TransactionInfo` pulled from (untrusted/downloaded) backup archives: [3](#0-2) 

Because the state checkpoint hashes are the fields that actually encode the Merkle root of the world state (main state, hot state, and the newly-added native "position" state whose root is threaded through `TransactionInfoV1.position_state_checkpoint_hash`, see [4](#0-3) ), skipping them means the tool cannot detect the one class of divergence it exists to catch: local execution computing a different state root than what was archived/committed for a given version, whether from a corrupted archive, a storage/restore bug, or an actual state-computation divergence between nodes.

### Impact Explanation
`replay_on_archive` (and the underlying `ensure_match_transaction_info`, also reachable from `aptos-debugger` and the `aptos` CLI per the grep results) is a state-integrity safety net specifically meant to surface committed-state divergence during replay against historical/backup data. With the checkpoint-hash comparisons omitted, a wrong state root (e.g. from a storage bug corrupting durable ledger data, or a hard-fork-style divergence in state computation) is silently accepted as "verified" by this tool, even though the write set, events, gas, and status all matched. This directly matches the gate's "hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated ... output bound to the wrong version/object/proof context" criteria: a proof-bearing replay pipeline reports success while the actual committed state root is wrong.

### Likelihood Explanation
This is not a hypothetical edge case — it is a documented, currently-shipped gap in the only tool designed to check exactly this invariant. It requires no attacker interaction to trigger the false-negative outcome: any legitimate state-root divergence (bug-induced or malicious archive tampering) during a replay-verify run over affected versions will not be flagged as a mismatch.

### Recommendation
In `ensure_match_transaction_info`, add comparisons for `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the recomputed checkpoint output and `txn_info`'s corresponding fields whenever the transaction is a checkpoint (state-checkpoint-hash `Some`), rather than leaving them entirely unchecked as noted in the TODO. This should be done before (or gated behind still validating today) any feature such as `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, since the verification gap already exists for the main `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields today, not just for the position-state addition.

### Proof of Concept
1. Corrupt or construct an archive/backup such that a given version's stored `TransactionInfo.state_checkpoint_hash` (or `position_state_checkpoint_hash`) is incorrect while `write_set`, `events`, `gas_used`, and `status` are left as originally recorded/matching.
2. Run `storage/db-tool/src/replay_on_archive.rs`'s `verify()` over that version range; `execute_and_verify` re-executes and calls `ensure_match_transaction_info` [5](#0-4) .
3. Observe that no error is returned and the version is reported as successfully verified, despite the state root being wrong, because the checkpoint-hash fields are never compared [6](#0-5) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
