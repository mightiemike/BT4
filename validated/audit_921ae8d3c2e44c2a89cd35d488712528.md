### Title
Missing `BlockPreCommit` payload in `signer_message_payload_matches_lane` filters out valid pre-commit chunks from being recognized by other signers - (File: libsigner/src/events.rs)

### Summary
`SignerMessageTypePrefix` was extended with a `BlockPreCommit = 7` variant that is routed to the `MessageSlotID::BlockPreCommit` lane [1](#0-0) , and `msg_id()` correctly maps `BlockPreCommit` to that lane [2](#0-1) . However, the actual gate used when consuming `.signers-X-Y` StackerDB chunks — `signer_message_payload_matches_lane`, invoked from the `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` handler — has an explicit code comment stating "the mapping in `signer_message_payload_matches_lane` is fixed to v0 ... Future signer-message versions must extend that mapping, or their chunks will not be recognized here" [3](#0-2) . This is structurally the same bug class as the reported M-7 issue: a message type was added to the enum/dispatch definitions but is missing from a separate registration/matching table that gates whether the message is actually processed.

### Finding Description
When a signer receives a `StackerDBChunksEvent` for a `.signers-X-Y` boot contract, each chunk's first byte is decoded via `SignerMessageTypePrefix::from_u8`, and then `signer_message_payload_matches_lane(payload_kind, message_id)` is called to decide whether to accept the chunk for that lane; chunks failing this check are silently skipped with only a `warn!` log [4](#0-3) . If this lane-matching table is not kept in sync with `SignerMessageTypePrefix::msg_id()` — the source of truth that determines which `MessageSlotID` a payload type belongs to — a valid message type (like the newly-added `BlockPreCommit`) can be silently dropped by nodes/signers using a stale or divergent copy of the matching function, even though the sender correctly wrote it to the `BlockPreCommit` slot per `msg_id()`.

### Impact Explanation
This is a minority-triggerable divergence: any single signer whose `signer_message_payload_matches_lane` mapping is inconsistent with `msg_id()`/`SignerMessageTypePrefix` will silently drop valid `BlockPreCommit` (or other newly added lane) messages, while other signers accept them. That produces a real signer-set state divergence — the affected signer's view of pre-commit votes or block responses on a given slot disagrees with peers, without any node operator/admin action or majority collusion, matching the report's "message dropped due to missing registration" bug class. The impact is bounded to a temporary tip/vote disagreement among signers rather than a chain split, since the underlying consensus/state-root logic elsewhere is unaffected — this fits the "High: minority-triggerable ... temporary tip disagreement" bucket rather than Critical.

### Likelihood Explanation
Likelihood depends entirely on whether `signer_message_payload_matches_lane`'s internal match table is actually out of sync with `SignerMessageTypePrefix`/`MessageSlotID::msg_id()` at this commit — the source code comment explicitly flags this as a known risk for future signer-message versions ("Future signer-message versions must extend that mapping, or their chunks will not be recognized here") [5](#0-4) . I was not able to retrieve the actual body/definition of `signer_message_payload_matches_lane` within the available tool budget to confirm whether `BlockPreCommit` is currently included or omitted in its match arms — the search results only located line ranges around its call site and the trailing 10 usages, not its full definition. Given the index size limits noted for this environment, this could not be conclusively verified from the index alone.

### Recommendation
Verify `signer_message_payload_matches_lane`'s match arms cover every `SignerMessageTypePrefix` variant returned by `msg_id()` — ideally by deriving the lane mapping directly from `SignerMessageTypePrefix::msg_id()` instead of maintaining a second, separately-written table, eliminating the possibility of drift between the two.

Given the explicit code comment flagging this exact risk and the load-bearing role of this function in the same registration/dispatch style as the M-7 bug class, this is flagged for further verification. A Devin session with full file access would be needed to confirm the current match arms of `signer_message_payload_matches_lane` and definitively determine whether this is exploitable at this commit.

impl SignerMessageTypePrefix {
    /// The signer-message lane (`MessageSlotID`) this payload type is broadcast on, if any.
    ///
    /// Miner-only payloads (`BlockProposal`, `BlockPushed`, `MockProposal`, `MockBlock`) do
    /// not broadcast over a `.signers-X-Y` contract and return `None`.
    pub fn msg_id(self) -> Option<MessageSlotID> {
        match self {
            // Mock signature uses the same slot as block response since it's exclusively for
            // epoch 2.5 testing.
            Self::BlockResponse | Self::MockSignature => Some(MessageSlotID::BlockResponse),
            Self::StateMachineUpdate => Some(MessageSlotID::StateMachineUpdate),
            Self::BlockPreCommit => Some(MessageSlotID::BlockPreCommit),
            Self::BlockProposal | Self::BlockPushed | Self::MockProposal | Self::MockBlock => None,
        }
    }
