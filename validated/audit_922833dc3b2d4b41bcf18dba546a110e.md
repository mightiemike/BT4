### Title
Replay-verify integrity check silently skips state-checkpoint-hash validation, letting state-root divergence pass as "verified" - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the shared correctness gate used by replay/verify tooling to confirm that locally re-executed VM output matches the trusted, previously-committed `TransactionInfo`. It cross-checks status, gas, write-set hash and event-root hash, but it never compares `state_checkpoint_hash` (nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the freshly computed state root. This mirrors the external report's bug class exactly: a value (`_releaseIntervalSecs`) that is logically derived from/coupled to other validated fields is left out of the cross-validation, so an internally-inconsistent record can pass checks that appear thorough.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates transaction status, gas used, the write-set hash against `state_change_hash`, and the event-root hash — but the function's own trailing comment admits the state checkpoint hashes are not compared: [2](#0-1) 

This function is invoked as the authoritative pass/fail check by `db-tool`'s replay-verify utility: [3](#0-2) 

The `Verifier::execute_and_verify` flow re-executes archived transactions with the VM and calls `ensure_match_transaction_info` against the `expected_txn_info` pulled from the backup/archive (via `self.backup_handler.get_transaction_iter`). Because `state_checkpoint_hash` is excluded from the comparison, if VM re-execution against the archived inputs produces a *different* state root than the one originally committed (e.g., due to a nondeterministic gas/state computation, a subtly wrong write-set materialization for some state keys that don't affect the write-set hash of that particular transaction, or a state-tree/hot-state divergence introduced by a bug elsewhere in the checkpoint path), the mismatch is not surfaced. `execute_and_verify` treats the transaction as verified and moves on to the next chunk, clearing its buffers.

The same primitive (`TransactionInfo`/`TransactionOutput` comparison) is also called from `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`, meaning any tool relying on this shared comparator for "does my execution match the ledger" checks inherits the same blind spot.

### Impact Explanation
Replay-verify is explicitly the mechanism operators/auditors use to detect state-commitment divergence between archived, network-accepted data and independently re-executed results — i.e., to catch hard-fork-only or non-deterministic divergence in committed state. Per the Required Impacts, this class of bug ("hard-fork-only divergence during commit, replay, restore, or proof verification" going undetected) is squarely in scope. If the write-set hash and events happen to match (which does not guarantee the resulting Merkle/state root matches, since the write-set hash covers only newly changed values represented in this transaction's write set, not necessarily the full resulting state tree root which also depends on prior tree structure/position), a genuine state-root corruption or divergence can be reported as "verified" by the tool whose entire purpose is state-integrity assurance. This undermines the primary safety net for detecting silent ledger corruption or non-determinism across nodes/versions.

### Likelihood Explanation
The gap is deterministic and always present — it's not a race condition or malicious-input-dependent bug; it is a structural omission in the comparator's checked-field set, acknowledged directly by the in-code TODO. It requires a genuine state-root divergence to actually surface (which is by definition a rare, high-severity event), but when such a divergence exists, this code guarantees it is missed by anyone relying on `ensure_match_transaction_info` for validation. This is analogous to the referenced VTVL finding, which is similarly "will not trigger the class of harm on every call, but silently permits an internally inconsistent value to be accepted with no cross-validation."

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally computed state checkpoint hash (and, where the feature/version applies, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against `txn_info.state_checkpoint_hash()` (and equivalents), returning an error on mismatch just as is done for `state_change_hash` and `event_root_hash`. Since the caller (`replay_on_archive.rs`) currently only has write-set/events per-transaction and doesn't necessarily track the running SMT root, this will likely require plumbing the computed state-checkpoint hash from the chunk executor's checkpoint output into the comparator, gated on whether the transaction is a checkpoint boundary (mirroring how `state_checkpoint_hash` is `Option<HashValue>` and only `Some` at checkpoint transactions).

### Proof of Concept
Conceptual (cannot be exercised without a live divergence bug elsewhere in the code, which is what this check exists to catch):
1. Introduce (or naturally hit) any bug that causes `DoStateCheckpoint`/state-tree materialization to diverge from the originally committed state root, while leaving the affected transaction's own local write-set hash, event hashes, gas, and status all unchanged (e.g., a divergence caused by carry-over from a *different* transaction's state, or a hot-state/position-state materialization bug not reflected in any single transaction's write set).
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) over the affected version range.
3. `execute_and_verify` calls `ensure_match_transaction_info` per transaction; because `state_checkpoint_hash` is never compared, the check returns `Ok(())`.
4. The tool reports the range as fully verified even though the state root computed by local re-execution does not match the archived/authoritative `state_checkpoint_hash`, per the function's own admitted TODO at [2](#0-1) .

Note: I could not fully trace whether `execute_and_verify`/`Verifier` in `replay_on_archive.rs` has access to a running/independently-computed state checkpoint hash it could compare against `expected_txn_info.state_checkpoint_hash()` (this would need to be added as part of the fix), so the exact remediation plumbing needs further design; this is flagged as uncertain pending deeper review of `execution/executor/src/workflow/do_state_checkpoint.rs`'s integration with the replay tool.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
