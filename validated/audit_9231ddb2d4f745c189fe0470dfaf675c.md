### Title
Witness Brokerage Fee Change Applies With Zero Notice at Cycle Boundary, Allowing Reward-Split Manipulation Against Voters - (File: actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java)

### Summary
A Super Representative (witness) can change its `brokerage` (the percentage of block/vote rewards it keeps before sharing the rest with its voters) at any time via `UpdateBrokerageContract`, and this new rate is committed as the effective value for the very next reward cycle at the next maintenance/epoch boundary, with no minimum notice period. This mirrors the reported "Fee Update Delay Bypass" bug class: a value that is documented/expected to only take effect "next epoch" can in practice be changed right up to the epoch boundary and applied instantly at the start of the new epoch, leaving delegators no time to react (e.g., un-vote) before their reward share changes.

### Finding Description
`UpdateBrokerageActuator.execute()` writes the submitted brokerage value unconditionally to a "pending" slot keyed with cycle `-1`: [1](#0-0) 

which maps to `DelegationStore.setBrokerage(byte[] address, int brokerage)`: [2](#0-1) 

At each maintenance cycle boundary, `MaintenanceManager.doMaintenance()` reads that pending `-1` value and commits it as the brokerage that will be *effective for the next cycle*, in the same maintenance pass that advances `currentCycleNumber`: [3](#0-2) 

Reward distribution then reads the brokerage for the *current* cycle to split rewards between the witness and its voters: [4](#0-3) 

There is no check anywhere in `UpdateBrokerageActuator.validate()` limiting how frequently the brokerage can be changed, nor any enforced minimum lead time before a new value takes effect: [5](#0-4) 

As a result, a witness can broadcast an `UpdateBrokerageContract` transaction immediately before a maintenance cycle triggers (maintenance intervals are deterministic and publicly known via `GetNextMaintenanceTime`), and the new cut becomes effective for the entirety of the very next cycle with zero notice to voters who have already delegated votes to that witness in the prior cycle.

### Impact Explanation
Voters delegate votes to a witness based on its current/advertised brokerage rate expecting a stable reward split. Because the new rate is committed atomically at the same maintenance event that begins the new cycle, voters have no window to withdraw/un-vote in response to a rate hike before it silently starts applying to reward accounting for the whole next cycle (`payReward` in `MortgageService`). A witness can therefore repeatedly lower its brokerage to attract votes and then raise it back to the maximum (100%) right before a cycle boundary to capture a much larger share of that cycle's rewards, corrupting the reward-accounting fairness that `DelegationStore`/`MortgageService` are meant to guarantee, at the expense of unwitting voters.

### Likelihood Explanation
Likely to be exploitable by any account that has been elected as a witness (a permission any address can obtain through sufficient votes, not a chain-admin-only privilege). Maintenance cycle timing is deterministic/queryable, so timing the `UpdateBrokerageContract` transaction just before a boundary is trivial and requires no special access beyond broadcasting a standard signed transaction.

### Recommendation
Enforce that a brokerage change only takes effect at least one full cycle after it is submitted (e.g., stage the value and only copy it into `nextCycle+1`'s slot rather than `nextCycle`'s), and/or add a minimum interval (rate limit) between successive `UpdateBrokerageContract` transactions from the same witness, mirroring the fix pattern described in the referenced patch (blocking a fee change for at least one full epoch before it can apply).

### Proof of Concept
1. Witness W is currently set to `brokerage = 0` (attractive to voters); voters delegate votes to W during cycle N.
2. Immediately before the maintenance boundary that ends cycle N (query `GetNextMaintenanceTime` to time this), W broadcasts `UpdateBrokerageContract{brokerage=100}` — `UpdateBrokerageActuator.execute()` stores this at the `-1` pending slot.
3. `MaintenanceManager.doMaintenance()` runs, advances `currentCycleNumber` to N+1, and copies the pending value (100) into cycle N+1's brokerage slot via `delegationStore.setBrokerage(nextCycle, ...)`.
4. During cycle N+1, `MortgageService.payReward()` reads `getBrokerage(N+1, W)` = 100 and routes 100% of block/standby rewards to W's allowance instead of the voters' reward pool (`delegationStore.addReward`), even though voters delegated expecting the previous 0% rate and had no opportunity to react between steps 2 and 3.

  @Override
  public boolean validate() throws ContractValidateException {
    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }
    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    WitnessStore witnessStore = chainBaseManager.getWitnessStore();
    if (!dynamicStore.allowChangeDelegation()) {
      throw new ContractValidateException(
          "contract type error, unexpected type [UpdateBrokerageContract]");
    }

    if (!this.any.is(UpdateBrokerageContract.class)) {
      throw new ContractValidateException(
          "contract type error, expected type [UpdateBrokerageContract], real type[" + any
              .getClass() + "]");
    }
    final UpdateBrokerageContract updateBrokerageContract;
    try {
      updateBrokerageContract = any.unpack(UpdateBrokerageContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = updateBrokerageContract.getOwnerAddress().toByteArray();
    int brokerage = updateBrokerageContract.getBrokerage();

    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid ownerAddress");
    }

    if (brokerage < 0 || brokerage > ActuatorConstant.ONE_HUNDRED) {
      throw new ContractValidateException("Invalid brokerage");
    }

    WitnessCapsule witnessCapsule = witnessStore.get(ownerAddress);
    if (witnessCapsule == null) {
      throw new ContractValidateException("Not existed witness:" + Hex.toHexString(ownerAddress));
    }

    AccountCapsule account = accountStore.get(ownerAddress);
    if (account == null) {
      throw new ContractValidateException("Account does not exist");
    }

    return true;

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
