Based on my investigation, the strongest verified analog is a self-documented integrity gap in `TransactionOutput::ensure_match_transaction_info`.

### Title
`TransactionOutput::ensure_match_transaction_info()` skips checkpoint-hash verification, letting locally-executed output match a `TransactionInfo` whose state/hot-state/position-state roots diverge from the local re-computation - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to confirm that a locally re-executed `TransactionOutput` matches a `TransactionInfo` obtained from a remote/authenticated source (chunk sync, replay-verify, debugger, CLI). It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as stated directly in the code's own TODO comment. [1](#0-0) 

### Finding Description
The function iterates the fields of `TransactionInfo` that should be re-derived and matched against local execution: status, gas, write-set hash, and event root hash are all `ensure!`-checked. [2](#0-1) 

But the state checkpoint / hot-state checkpoint / position-state checkpoint hashes — which are the fields binding a transaction's execution to the actual world-state Merkle root at that version — are never compared. The comment left in the code makes this explicit:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This function is consumed by multiple integrity-sensitive callers: the chunk executor (`execution/executor/src/chunk_executor/mod.rs`), the archive-replay verification tool (`storage/db-tool/src/replay_on_archive.rs`), the transaction debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`), and the CLI (`aptos-move/cli/src/commands.rs`). [4](#0-3) 

Because the checkpoint hashes are precisely the values that bind a transaction's committed output to the actual state Merkle root of the ledger (state checkpoint hash → state Merkle root, hot-state checkpoint hash → hot-state tier root, position-state checkpoint hash → the "trading-native"/position-state root), skipping them means this verification path can accept a `TransactionOutput` as "matching" a `TransactionInfo` even though the two disagree about the resulting world state.

### Impact Explanation
Tools relying on `ensure_match_transaction_info` for state-commitment assurance (chunk-execution acceptance, `replay_on_archive` verification, and the debugger/CLI replay checks) can report successful/valid replay or execution match even when the authenticated state checkpoint root diverges from what local re-execution actually produced. Since this check is one of the load-bearing invariants tying committed VM output to durable ledger state/proof roots, a divergence here means these tools cannot detect a class of hard-fork-only or storage-corruption divergence at the state-checkpoint level. The comment itself flags this as gating the safe enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` — i.e., the feature was intentionally left unsafe pending this fix.

### Likelihood Explanation
This is not a remotely triggerable single-transaction exploit; it is a structural gap in a verification helper reachable whenever the mismatched fields legitimately differ (e.g., bugs elsewhere in checkpoint-hash computation, a corrupted/malicious `TransactionInfo` supplied to replay/debug tooling, or on-chain feature interactions affecting `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`). Its likelihood of being exercised increases directly as `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and the position-state-root feature are enabled, which the code comment says is intentionally pending this fix.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally computed values (when present in the given `TransactionInfo` variant), before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or relying on this function for chunk-execution/replay-verify state-integrity guarantees.

### Proof of Concept
Not applicable as a remote-exploit PoC — the gap is directly visible in source: `ensure_match_transaction_info` never calls the comparable checks for `state_checkpoint_hash()`, and `TransactionInfoV1` carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` fields that are likewise unchecked, as shown in the cited code and confirmed by the code's own TODO annotation. [5](#0-4) 

**Note on completeness:** I was unable to retrieve the body of `execution/executor/src/chunk_executor/mod.rs` (the file returned empty content via the indexed tools), so I could not confirm the exact call-site context (e.g., whether an additional/redundant checkpoint-hash check exists there that would mitigate this gap for the chunk-executor path specifically).     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
