### Title
Off-by-one in poison-microblock maturity boundary allows a report to be accepted in the same block that the reward matures, causing double payment - (File: `stackslib/src/chainstate/stacks/db/transactions.rs`, function `handle_poison_microblock`)

### Summary
`handle_poison_microblock` rejects a report only when `height + MINER_REWARD_MATURITY < current_height`, which means a report is still *accepted* when `height + MINER_REWARD_MATURITY == current_height`. This is exactly the block height at which `find_mature_miner_rewards` (`stackslib/src/chainstate/stacks/db/accounts.rs`) computes `reward_height = tip_stacks_height - MINER_REWARD_MATURITY` and disburses the matured coinbase reward for that same microblock height, so the poison-report acceptance window and the reward-maturation event overlap on one block.

### Finding Description
The intended invariant is: *"a poison report can only be accepted while the corresponding reward has not yet matured/paid; once matured, it is immutable."* Expressed as an equality, this should be:

`report accepted  ⇔  height + MINER_REWARD_MATURITY >= current_height`  must never overlap with  `reward_height == height` being paid in the same block.

The code in `handle_poison_microblock` uses a strict `<` comparison, so at the exact boundary `height + MINER_REWARD_MATURITY == current_height` the report is *not* rejected. Independently, matured-reward processing (`find_mature_miner_rewards` in `accounts.rs`, invoked from block append/setup logic in `stackslib/src/chainstate/stacks/db/blocks.rs` and `stackslib/src/chainstate/nakamoto/tenure.rs`) computes and disburses rewards for `reward_height = tip_stacks_height - MINER_REWARD_MATURITY` as part of block setup, which in the standard chainstate append flow happens before the block's own transactions (including any `PoisonMicroblock` transaction) are processed.

Because both computations use the same arithmetic relation (`height + MATURITY == current_height`), the block that first matures a given height's reward is the same block in which `handle_poison_microblock` will still accept a poison report against that same height. If reward disbursement runs first (block setup) and the poison-triggered payment/forfeiture runs second (transaction processing within the same block), the honest miner's reward has already been credited before the poison logic executes, so accepting the report on this block adds a second payment path (reporter payout / additional `MinerReward` entry) without reversing the already-committed miner reward.

Existing guards (`check_tenure_tx`, VRF/static validators, `common_validate_against_burnchain`) operate on tenure/VRF/burnchain validity and do not inspect microblock-poison maturity timing, so none of them close this specific boundary condition.

### Impact Explanation
This is a block-reward double-payment: the legitimate miner's coinbase for the poisoned height is paid via the matured-reward path, and the poison reporter is additionally compensated for a report that should have been time-barred, inflating total STX emitted for that reward slot. This matches the Critical category ("block-reward theft/double-payment/loss").

### Likelihood Explanation
The attacker needs no privileged role — any participant able to craft and broadcast a valid `PoisonMicroblock` transaction (which requires only knowledge of two conflicting, correctly signed microblocks from the target miner, obtainable from any leader who has ever built a fork of microblocks) can time its submission to land in the specific block where `current_height - height == MINER_REWARD_MATURITY`. This is a single, deterministic block height that can be computed in advance from public chain state, requiring no stake and no cooperation from other parties, making it fully repeatable whenever a poisonable microblock fork exists.

### Recommendation
Change the maturity check in `handle_poison_microblock` to reject at the boundary as well, i.e. use `height + MINER_REWARD_MATURITY <= current_height` (reject) instead of strict `<`, so that the report window closes strictly before the block in which the corresponding reward matures and is disbursed. Alternatively, ensure poison-report processing runs and is finalized before matured-reward disbursement within the same block, and make the two computations reference a single shared boundary constant/function to avoid divergent off-by-one arithmetic.

### Proof of Concept
1. Set up a local two-node/single-chain integration harness (using existing chainstate test scaffolding under `stackslib/src/chainstate/stacks/tests/`).
2. Have a miner produce a microblock fork at height `H` (two conflicting signed microblocks), then build blocks until `current_height == H + MINER_REWARD_MATURITY` (the exact maturation block).
3. In that exact block, include a `PoisonMicroblock` transaction reporting the fork at height `H`, and separately verify via `find_mature_miner_rewards`/block setup that the matured reward for `reward_height == H` was already disbursed in the same block's setup phase.
4. Assert that after processing, only one `MinerReward` entry exists for that coinbase slot/pubkey hash — the test should show two (miner's matured reward + poison-triggered payout), demonstrating the double payment.
5. As a control, repeat at `current_height == H + MINER_REWARD_MATURITY + 1` and confirm the poison report is correctly rejected, showing the bug is isolated to the exact boundary block. [1](#0-0) [2](#0-1)
