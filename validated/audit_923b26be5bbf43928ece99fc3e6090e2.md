Based on the investigation, the java-tron codebase contains an analogous checked-arithmetic issue in its opt-in "hardened calculation" feature, gated by the `AllowHardenResourceCalculation` and `AllowHardenExchangeCalculation` dynamic parameters. These flags replace previously silent/wraparound-tolerant `long` arithmetic with `BigInteger`/`StrictMathWrapper` checked math that throws `ArithmeticException` on overflow — the same tradeoff at the root of the reported Uniswap V3 issue (checked math causing legitimate operations to revert instead of silently wrapping).

### Title
Hardened resource-usage arithmetic (`AllowHardenResourceCalculation`) throws uncaught `ArithmeticException` during transaction resource accounting, causing node-crashing DoS once enabled - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
### Finding Description
`ResourceProcessor.increase()` / `increaseV2()` and `EnergyProcessor.calculateGlobalEnergyLimit()` (and its `RepositoryImpl` VM-side counterpart) implement two code paths for computing bandwidth/energy usage:
- Legacy path: plain `long` arithmetic that silently overflows/wraps (`averageLastUsage * decay`, `usage * windowSize / precision`, etc.)
- "Hardened" path (`hardenCalculation()` / `hardenResourceCalculation()` gated by `VMConfig.allowHardenResourceCalculation()` / the `AllowHardenResourceCalculation` dynamic property): uses `BigInteger` math and `StrictMathWrapper.addExact` and `.longValueExact()`, which throw `ArithmeticException` when a computed usage value cannot be represented as a `long`. [1](#0-0) [2](#0-1) [3](#0-2) 

This is precisely the class of bug described in the report: intentionally replacing silent overflow/underflow with checked arithmetic changes previously-successful operations into ones that throw. The existing test suite explicitly documents this dual behavior — the same inputs succeed silently without hardening but throw `ArithmeticException` with hardening enabled: [4](#0-3) [5](#0-4) 

`increase()`/`calculateGlobalEnergyLimit()` are invoked from `BandwidthProcessor`/`EnergyProcessor` consumption logic, which runs for essentially every broadcast transaction during both transaction validation and block application (a consensus-critical, identically-executed path on every node). Unlike the actuator-level `ArithmeticException`s in the Exchange* actuators (which are explicitly caught and converted into `ContractValidateException`/`ContractExeException` so a single bad transaction just fails gracefully), I could not confirm that `Manager.java`'s bandwidth/energy consumption call sites catch generic `ArithmeticException` — the catch blocks I was able to inspect only handle `BalanceInsufficientException`/`AccountResourceInsufficientException`. If `ArithmeticException` is left uncaught along this path, it would propagate as an unchecked `RuntimeException` out of core block-application code.

### Impact Explanation
If the network committee enables `AllowHardenResourceCalculation` and an account's accumulated resource usage grows large enough to trigger `BigInteger` overflow in `longValueExact()` (or `addExact` in `divideCeilExact`), then every node processing a block containing that account's transaction would throw the same uncaught `ArithmeticException` at the same point during block application — since this is a deterministic, consensus-relevant computation executed identically by every node. That is a full-network halt / DoS (or, if only partially caught somewhere up the call chain, a discrepancy in behavior between nodes with the flag on vs off, i.e., consensus divergence), analogous to how the Uniswap issue caused reverts for previously-successful, fee-growth-dependent operations once wraparound was disallowed.

### Likelihood Explanation
This requires (a) the `AllowHardenResourceCalculation`/`AllowHardenExchangeCalculation` governance flag to be enabled (currently opt-in/default-off based on the tests toggling it via `saveAllowHardenResourceCalculation`), and (b) an account's usage/weight values to reach magnitudes near `Long.MAX_VALUE/10` or similar boundary conditions demonstrated in the tests. I could not fully confirm within the available investigation whether such magnitudes are practically reachable under current network resource limits (`TotalEnergyWeight`, `TotalEnergyLimit`), nor whether `Manager.java` or higher-level transaction-processing code wraps this call path in a catch-all handler that would prevent an actual node crash. This uncertainty should be resolved by tracing the full call chain from `Manager.consumeBandwidth`/`consumeEnergy` through to block application and confirming exception handling and realistic value ranges before treating this as a live network-halting bug.

### Recommendation
- Ensure every code path that can execute the hardened (`BigInteger`/`*Exact`) arithmetic during consensus-critical transaction/block processing (not just per-transaction actuator execution) has an explicit, tested catch for `ArithmeticException` that fails the transaction/block deterministically and identically on all nodes, rather than allowing an uncaught `RuntimeException` to propagate.
- Audit all `hardenCalculation()`/`hardenResourceCalculation()` branches for consensus-critical accounting (`ResourceProcessor`, `EnergyProcessor`, `RepositoryImpl`) and confirm that legitimate, in-range usage/weight/limit values under real network parameters can never reach the overflow boundary; add invariant checks or clamp values before enabling this flag network-wide.
- Where the design intentionally relies on bounded wraparound-safe ranges (similar to Uniswap's fee-growth ring arithmetic), document and enforce those bounds explicitly rather than depending on incidental non-overflow of `long`/`BigInteger` conversions.

### Proof of Concept
Existing unit tests already demonstrate the dual behavior (silent success vs. `ArithmeticException`) for the same inputs, confirming the underlying mechanism: [6](#0-5) [7](#0-6)

  private long increase(long lastUsage, long usage, long lastTime, long now, long windowSize) {
    long averageLastUsage;
    long averageUsage;
    if (hardenResourceCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay, VMConfig.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }

  private long divideCeil(long numerator, long denominator) {
    return (numerator / denominator) + ((numerator % denominator) > 0 ? 1 : 0);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }

  private long getUsage(long usage, long windowSize) {
    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(usage)
          .multiply(BigInteger.valueOf(windowSize))
          .divide(BigInteger.valueOf(precision))
          .longValueExact();
    }
    return usage * windowSize / precision;
  }

  private boolean hardenResourceCalculation() {
    return VMConfig.allowHardenResourceCalculation();
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
