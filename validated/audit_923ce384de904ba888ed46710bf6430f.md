### Title
`AppendVec::scan_stored_accounts_no_data()` Treats a Legitimately-Stored Zero-Lamport, All-Zero-Pubkey Account (System Program Address) as the Unwritten Tail Sentinel, Silently Truncating the Scan - (File: accounts-db/src/append_vec.rs)

### Summary
`AppendVec::scan_stored_accounts_no_data()` uses `account_meta.lamports == 0 && stored_meta.pubkey == Pubkey::default()` as a sentinel meaning "we have reached the unwritten tail of the file, stop scanning." This is the same bug class as the Beebots `TradeValid()` report: a legitimate, real value (`address(0)` / `Pubkey::default()`) is conflated with an "unset/uninitialized" sentinel, allowing a crafted-but-legal record to be silently mistaken for "nothing here."

### Finding Description
`Pubkey::default()` is the all-zero 32-byte value, and it is also the well-known `system_program::id()` (base58 `11111111111111111111111111111111`). In `scan_stored_accounts_no_data()`, the loop reads each stored account's fixed-size header and stops scanning as soon as it sees an entry with `lamports == 0` and `pubkey == Pubkey::default()`: [1](#0-0) 

This heuristic assumes that such an entry can only occur because the region beyond the last real account is zero-filled (never written) memory/disk, i.e., it is treating the all-zero pattern as an "unwritten" sentinel — directly analogous to Solidity's `idToOwner` mapping defaulting to `address(0)` for un-minted token IDs. However, nothing in the on-disk format prevents a *real*, intentionally-stored account record from having `pubkey == Pubkey::default()` (the system program's address) and `lamports == 0`. If such a record exists mid-file (e.g., due to a zero-lamport tombstone/rewrite for that pubkey, or any write path that ends up storing a zero-lamport record for the system-program address), the scan interprets it as "the last useful account" and `break`s immediately — even though additional, legitimate account records exist later in the same `AppendVec` file.

This is the same class of defect as in the Beebots contract: `Beebots.verify()` treats `signer == address(0)` returned by a failed `ecrecover` as valid because `address(0)` is used as both "no signer" and a possible real value; here, `Pubkey::default()` is used as both "not written yet" and a possible real account address (system program), and the code cannot distinguish the two cases from the stored bytes alone.

### Impact Explanation
`scan_stored_accounts_no_data()` is the core account-enumeration primitive for an `AppendVec`, used by `scan_pubkeys()` and other iteration helpers referenced from `accounts_db.rs`, `account_storage_reader.rs`, `account_storage_entry.rs`, and `snapshot_minimizer.rs`. If the scan truncates early:
- Accounts stored after the false "end of file" marker become invisible to any consumer that walks the `AppendVec` via this path (e.g., rebuilding the accounts index from storage, generating/minimizing snapshots, or accounts-hash/lattice-hash recomputation that relies on enumerating all stored accounts).
- This can produce a silent divergence between what is actually on disk and what the index/hash calculation believes is present — a hash/capitalization divergence or a stale/missing account view, without any panic or error being raised.

### Likelihood Explanation
The likelihood of a zero-lamport record with `pubkey == Pubkey::default()` appearing mid-`AppendVec` depends on whether any account-storage code path ever stores an account keyed by the system program's own address with zero lamports at a non-terminal offset (e.g., via zero-lamport tombstone writes used for cleaning, similar to `zero_account` patterns seen elsewhere in the codebase such as `accounts.rs`'s `huge_clean` test and `test_clean_retains_secondary_index_for_still_cached_key`). Because `AppendVec`s are appended-to sequentially and the sentinel check only inspects header bytes without a stronger invariant (e.g., an explicit written-length field, or reliance solely on the buffered reader's EOF signal), the code's correctness rests entirely on the assumption that "no real account is ever stored with `Pubkey::default()` and zero lamports," which is not enforced anywhere visible in this function or its callers.

### Recommendation
Do not use `lamports == 0 && pubkey == Pubkey::default()` as an end-of-data sentinel. Instead, rely on the actual buffered length/EOF signal (as already used via `reader.fill_buf_required`/`Ok([])`) or an explicit tracked "current length" of written data (as used elsewhere, e.g. `self.len()`/`is_dirty` bookkeeping) to determine where valid data ends, and remove the pubkey-equals-default heuristic entirely, or additionally verify that the offset is beyond the known written length before treating it as the end.

### Proof of Concept
Conceptual reproduction (cannot be executed without a live validator/test harness):
1. Append two accounts to an `AppendVec`: account A with a non-default pubkey and non-zero lamports, followed by account B with `pubkey == Pubkey::default()` (system program address) and `lamports == 0`, followed by account C with a legitimate non-default pubkey and non-zero lamports.
2. Call `scan_pubkeys()`/`scan_stored_accounts_no_data()` on the resulting `AppendVec`.
3. Observe that the scan stops at account B and never yields account C, even though account C is validly stored and within the file's actual written length — demonstrating that a legitimate zero-lamport, all-zero-pubkey record causes silent truncation of the enumeration, mirroring the Beebots `address(0)`-as-sentinel defect.
