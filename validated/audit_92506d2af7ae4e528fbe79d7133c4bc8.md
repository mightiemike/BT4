### Title
Comma Injection in Wallet Contract's Method-Names Serialization Allows Function-Call Access-Key Scope Expansion - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR wallet contract (the eth-implicit account emulation contract) accepts an `AddKey` action whose `method_names: Vec<String>` field is fully attacker-controlled ABI-decoded data from an RLP/Ethereum-style transaction. When converting this action into a native NEAR `Promise::add_access_key_allowance_with_nonce` call, the contract joins the list with a comma separator (`access.method_names.join(",")`) without validating that individual entries are free of the `,` delimiter. The resulting single string is later re-split on the same delimiter by the runtime's `split_method_names` when the `AddKey` action is actually processed as a promise action. This mirrors the root cause of CVE-2019-16255: untrusted string data that is supposed to be pure data is passed, unsanitized, into a context where a delimiter character gives it new syntactic meaning ("command injection"-style confusion between data and control values), letting an attacker who crafts one method-name entry containing an embedded comma cause the created access key to be split into multiple method names instead of the single one it appears to authorize.

### Finding Description
The wallet contract ABI-decodes `AddKey` transactions with:
```
ParamType::Array(Box::new(ParamType::String)), // method_names
``` [1](#0-0) 

These raw strings flow unchanged into `near_action::FunctionCallPermission.method_names: Vec<String>` [2](#0-1)  and then `action_to_promise` converts them to the Near SDK's promise API by joining with a comma:
```rust
near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
    .add_access_key_allowance_with_nonce(
        action.public_key,
        access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
        access.receiver_id,
        access.method_names.join(","),
        action.access_key.nonce,
    )),
``` [3](#0-2) 

At no point is any individual entry of `method_names` checked to be free of the `,` character before this join. The resulting comma-joined buffer is exactly the wire format consumed by the VM logic host function that creates the `AddKey` action, which re-splits it on `,`:
```rust
pub(crate) fn split_method_names(method_names: &[u8]) -> Result<Vec<Vec<u8>>, HostError> {
    ...
    method_names.split(|c| *c == b',') ...
}
``` [4](#0-3) 
used in `promise_batch_action_add_key_with_function_call` [5](#0-4) .

Consequently, a caller submitting an `addKey` payload with a single logical method-name string that contains an embedded `,` (e.g. `"safe_method,ft_transfer"`) will have that one entry silently expanded into two independently-authorized method names (`safe_method` and `ft_transfer`) on the resulting `FunctionCallPermission`, once the AddKey action is actually applied on-chain. This is a classic data/control confusion bug: the ABI array boundary (which should be the sole determinant of how many method names exist) is bypassed by a delimiter injected inside a single array element, exactly as in CVE-2019-16255 where the "command" argument crossed from data into command syntax.

### Impact Explanation
The access key created by this path grants `FunctionCall` permission on the wallet-contract-controlled account (an eth-implicit account emulating an EOA). Any party who can influence the content of a single method-name string presented for signing (e.g., a malicious relayer/dApp front-end constructing the RLP payload for the user to sign, or a malicious/compromised co-signer in a multi-party flow) can smuggle in an additional, unintended method name via comma injection. The end user, inspecting or approving what looks like a single restricted method-name string, ends up authorizing a key that can call additional privileged methods (e.g. token-transfer methods) it was never meant to call, enabling unauthorized value movement out of the account once that key is later used maliciously by whoever controls it. This satisfies the "concrete unauthorized value movement" bar because the injected extra method name effectively increases the blast radius of a function-call access key beyond what the signer explicitly consented to.

### Likelihood Explanation
Exploitation requires an attacker to control (or influence) the content of the RLP-encoded `AddKey` calldata that gets presented for a user's signature, and to insert a method name string containing a literal comma. There is no on-chain validation preventing commas inside method names (validation only enforces per-name length and total-bytes limits, not character content) [6](#0-5) . Because the wallet contract is specifically designed for less-trusted relayer/dApp intermediaries to construct transactions on behalf of users, this is a realistic and directly reachable path for any transaction signer using the wallet contract flow.

### Recommendation
In `action_to_promise` (and any other place that joins `method_names` with `,` for the low-level promise API), reject or escape method names that contain the `,` delimiter before joining, e.g. return `Error::User(UserError::InvalidMethodName)` if any entry in `access.method_names` contains a comma. Alternatively, switch the wallet contract's low-level call to use a Vec-based access-key API (if available) rather than a comma-joined string, eliminating the ambiguity entirely.

### Proof of Concept
1. Craft an Ethereum-style `addKey` calldata for the wallet contract using `ADD_KEY_SIGNATURE`, setting `is_full_access = false`, `is_limited_allowance = true`, and `method_names = ["safe_method,ft_transfer"]` (a single array element containing an embedded comma).
2. Have the account owner sign this RLP transaction believing they are authorizing a function-call key restricted to the single method `"safe_method,ft_transfer"` (which does not exist as a callable method, appearing inert/harmless).
3. Submit the transaction to the wallet contract's `rlp_execute` entry point; the contract decodes `method_names` and constructs `Promise::add_access_key_allowance_with_nonce(..., access.method_names.join(","), ...)`, producing `"safe_method,ft_transfer"`.
4. When the promise action executes as an `AddKey` action, the runtime's `promise_batch_action_add_key_with_function_call` calls `split_method_names` on the buffer, splitting it into `["safe_method", "ft_transfer"]`.
5. Verify via `view_access_key` that the resulting on-chain `FunctionCallPermission.method_names` is `["safe_method", "ft_transfer"]` — i.e., the key now grants call permission for `ft_transfer` even though the signer only intended to authorize a single (non-existent) compound-named method, demonstrating unintended privilege/scope expansion.

/// Uses `,` separator to split `method_names` into a vector of method names.
/// Returns an empty vec if the empty slice is given.
/// Throws `HostError::EmptyMethodName` in case there is an empty method name inside.
pub(crate) fn split_method_names(method_names: &[u8]) -> Result<Vec<Vec<u8>>, HostError> {
    if method_names.is_empty() {
        Ok(vec![])
    } else {
        method_names
            .split(|c| *c == b',')
            .map(|v| if v.is_empty() { Err(HostError::EmptyMethodName) } else { Ok(v.to_vec()) })
            .collect()
    }
}
```
