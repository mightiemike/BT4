### Title
Nested `WithdrawFromGasKey` inside a `Delegate` action bypasses the `PendingTransactionQueue` gas-key balance accounting — ([File: runtime/runtime/src/action_validation.rs])

### Summary
`PendingTransactionQueue::check_pending` tracks `WithdrawFromGasKey` amounts to compute how much of a gas key's balance is already "spoken for" by transactions pending inclusion, so it can safely admit new gas-key transactions without overdrawing the key at chunk-production time. This tracking only scans the **top-level actions** of a submitted transaction. A `WithdrawFromGasKey` action nested inside a `Delegate` action (a meta-transaction) is invisible to this scan, so the admission-time balance bookkeeping silently omits it — structurally the same "check present on one entry point, missing on the semantically equivalent one" pattern as the Astaria `PublicVault.deposit`/`mint` bug.

### Finding Description
`PendingTransactionQueue::check_pending` records `WithdrawFromGasKey` amounts from a transaction's actions into `session_gas_key_withdrawals`, which feeds `paid_from_gas_key` used by later admission checks: [1](#0-0) 

This loop only iterates `tx.transaction.actions()` — the transaction's own top-level actions. It never looks inside an `Action::Delegate` payload's inner `actions` list, so a `WithdrawFromGasKey` action wrapped in a `SignedDelegateAction` is never added to `session_gas_key_withdrawals`/`paid_from_gas_key`.

The runtime itself acknowledges this gap explicitly. The `RejectWithdrawFromGasKeyInDelegate` protocol feature's doc comment states the root cause directly: [2](#0-1) 

And the corresponding validation only rejects the nested action when this specific protocol feature is enabled: [3](#0-2) 

Per the protocol-versioning documentation for this tree, `EnforcePerReceiptStorageProofLimit` is the sole feature activated at `STABLE_PROTOCOL_VERSION = 86`, while `RejectWithdrawFromGasKeyInDelegate` activates at **87** — i.e. on the current stable protocol version the bypass is live and unmitigated: [4](#0-3) 

The test suite reproduces the exact exploit path and explicitly documents that, pre-fix, "the nested withdrawal is admitted and moves balance out of the gas key, which is the hole this rule closes": [5](#0-4) 

The actual withdrawal execution logic (`action_withdraw_from_gas_key`) still performs a real `checked_sub` against the on-chain gas-key balance, so no negative balance can occur: [6](#0-5) 

The vulnerability is therefore not in the final balance check but in the **admission-time invariant** the `PendingTransactionQueue` is supposed to enforce: any unprivileged account holder can submit a meta-transaction (relayed by anyone) whose inner action drains their own gas key's balance through a code path the queue's bookkeeping cannot see, while other pending gas-key transactions concurrently admitted by the same chunk producer are validated against a stale, higher `paid_from_gas_key`/available-balance figure.

### Impact Explanation
Because the pending-queue's gas-key balance accounting is bypassed, a chunk producer can admit multiple gas-key transactions in the same production window under the false assumption that the full gas-key balance is still available, when in fact a concurrently-admitted delegate action has already committed to draining it via the untracked nested `WithdrawFromGasKey`. This breaks the fee/gas-payment guarantee the queue exists to provide: gas-key transactions that were admitted on the assumption of sufficient funds can subsequently fail balance checks at execution time inside the same chunk, wasting the relayer's/network's accounting expectations and violating the intended invariant that the pending-transaction admission control accurately reflects committed gas-key liabilities before inclusion. This is exactly the class of bug the Astaria report describes: a fund-affecting operation (draining balance) reachable through an alternate entry point that skips a guard applied to the "normal" entry point.

### Likelihood Explanation
High reachability: any account owner holding a gas key can construct this today with a single signed transaction (no special privileges, no validator/operator access) — wrap `WithdrawFromGasKey` in a `DelegateAction` and have it relayed, exactly as the existing test `test_reject_delegated_gas_key_withdraw_protocol_upgrade` does pre-upgrade. It requires no network-layer or malicious-node behavior, only standard signed-transaction submission via RPC. The bug is confirmed live on `STABLE_PROTOCOL_VERSION = 86`, and only becomes inert once the `RejectWithdrawFromGasKeyInDelegate` feature (v87) activates on-chain.

### Recommendation
Backport/expedite activation of `RejectWithdrawFromGasKeyInDelegate` (or equivalently have `PendingTransactionQueue::check_pending` recursively scan `Action::Delegate` inner actions for `WithdrawFromGasKey`) so the admission-time accounting cannot be bypassed while the protocol version gate is not yet active on mainnet/testnet.

### Proof of Concept
The existing integration test demonstrates the full exploit path end-to-end pre-upgrade (fund a gas key, submit a `Delegate` action nesting `WithdrawFromGasKey`, observe it executes and drains the gas key balance without being tracked by the pending queue): [7](#0-6)

fn test_reject_delegated_gas_key_withdraw_protocol_upgrade() {
    init_test_logger();

    if !ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(PROTOCOL_VERSION) {
        return;
    }

    let new_protocol = ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.protocol_version();
    let old_protocol = new_protocol - 1;
    assert!(
        old_protocol >= MIN_SUPPORTED_PROTOCOL_VERSION,
        "no supported protocol version still admits a delegated WithdrawFromGasKey, so there is \
         nothing left to test here - remove this test"
    );

    let sender = create_account_id("alice");
    let relayer = create_account_id("relayer");
    let epoch_length = 10;

    // Boundary "mm": "alice" lands on the first shard, "relayer" on the second,
    // so the delegate receipt crosses a shard on its way to the sender.
    let shard_layout = ShardLayout::multi_shard_custom(vec![create_account_id("mm")], 1);

    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .protocol_version(old_protocol)
        .protocol_upgrade_schedule(ProtocolUpgradeVotingSchedule::new_immediate(new_protocol))
        .epoch_length(epoch_length)
        .shard_layout(shard_layout)
        .add_user_account(&sender, Balance::from_near(1_000))
        .add_user_account(&relayer, Balance::from_near(1_000))
        .build();

    let gas_key: Signer =
        InMemorySigner::from_seed(sender.clone(), KeyType::ED25519, "gas_key").into();
    let add_key_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::AddKey(Box::new(AddKeyAction {
            public_key: gas_key.public_key(),
            access_key: AccessKey::gas_key_full_access(1),
        }))],
    );
    env.rpc_runner().run_tx(add_key_tx, Duration::seconds(10));

    let fund_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: gas_key.public_key(),
            deposit: Balance::from_near(10),
        }))],
    );
    env.rpc_runner().run_tx(fund_tx, Duration::seconds(10));

    // Before the upgrade the nested withdrawal is admitted and moves balance out
    // of the gas key, which is the hole this rule closes.
    assert_eq!(
        env.rpc_node().protocol_version_at_head(),
        old_protocol,
        "expected to start pre-upgrade"
    );
    let (_, balance_before) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
    let outcome = env
        .rpc_runner()
        .execute_tx(tx, Duration::seconds(10))
        .expect("delegated withdrawal admitted pre-upgrade");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::SuccessValue(_),
        "pre-upgrade delegated withdrawal should execute",
    );
    let (_, balance_after) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    assert_eq!(
        balance_after,
        balance_before.checked_sub(WITHDRAW_AMOUNT).unwrap(),
        "the nested withdrawal should have drained the gas key",
    );

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
