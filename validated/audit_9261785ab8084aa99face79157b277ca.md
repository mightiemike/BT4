### Title
Zero-Duration Freeze via TVM `freeze()` Opcode Bypasses Minimum Lock-Time Enforcement - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The TVM native `freeze()` opcode sets `frozenDuration` to `0` by default because the flag controlling duration enforcement (`getCheckFrozenTime`) is intended only for tests, and `FreezeBalanceProcessor.validate()` never checks bounds on `frozenDuration` at all. This mirrors the referenced Ocean Protocol bug class where a vesting `duration` argument can be zero, letting the user "instantly release all allocated tokens."

### Finding Description
The ordinary user-facing `FreezeBalanceActuator.validate()` enforces bounds on `frozenDuration` against `dynamicStore.getMinFrozenTime()`/`getMaxFrozenTime()`, but this check is explicitly gated behind a test-only flag: [1](#0-0) 

However, when resources are frozen via the TVM `freeze()` opcode (reachable by any smart contract), the duration is computed independently and, unless the test-only flag is enabled, is hardcoded to `0`: [2](#0-1) 

The underlying `FreezeBalanceProcessor.validate()` used by this TVM path performs no validation of `frozenDuration` whatsoever — it only checks `frozenBalance`, `frozenCount`, `resourceType`, and delegation target: [3](#0-2) 

`FreezeBalanceProcessor.execute()` then computes `expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD`, which becomes `expireTime = now` when `frozenDuration` is `0`: [4](#0-3) 

This is directly analogous to the reported issue: an unvalidated duration input that can be zero, defeating the intended lock/vesting period and enabling near-instant unfreezing of resources that should otherwise be locked for `minFrozenTime` days.

### Impact Explanation
An account (including a smart contract acting via the `freeze` opcode) can freeze TRX for BANDWIDTH/ENERGY and have the frozen balance become immediately eligible for unfreeze (`expireTime <= now`), instead of being locked for the minimum period enforced elsewhere in the protocol. This breaks the intended resource/vote-weight economic model — resources can be acquired to gain bandwidth/energy or voting-related weight and then unfrozen within the same or next block, undermining the lock-based security assumptions (e.g., TRON_POWER/voting stability, spam resistance from lock periods) that the actuator-level bound is designed to enforce.

### Likelihood Explanation
`Program.freeze()` is reachable by any deployed smart contract exercising the native freeze precompile/opcode — no privileged role is required. Exploitation depends on `CommonParameter.getCheckFrozenTime()` not being set to `1` in the running node's configuration; the code comment explicitly calls this flag "for test," implying it is `0` (disabled) in normal/production configurations, making the zero-duration path the default behavior for this code.

### Recommendation
Remove the test-only bypass or make `FreezeBalanceProcessor.validate()` independently enforce the same `minFrozenTime`/`maxFrozenTime` bounds that `FreezeBalanceActuator.validate()` enforces, regardless of the `checkFrozenTime` flag, so TVM-triggered freezes cannot use a duration of `0`.

### Proof of Concept
1. Deploy a contract that calls the `freeze` precompile/opcode (`Program.freeze`) with a valid `frozenBalance` and any `resourceType`.
2. On a node where `checkFrozenTime` is not set to `1` (default/production configuration), `needCheckFrozenTime` evaluates to `false`, so `param.setFrozenDuration(0)` is used.
3. `FreezeBalanceProcessor.validate()` accepts this because it never checks `frozenDuration`.
4. `FreezeBalanceProcessor.execute()` sets `expireTime = now + 0 = now`.
5. Immediately (or in the very next block), the account can call `unfreeze`, since `UnfreezeBalanceProcessor.validate()`/`UnfreezeBalanceActuator` checks only require `expireTime <= now`, which is already satisfied — bypassing the intended `minFrozenTime` lock period entirely. [5](#0-4)

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }

    // validate for delegating resource
    byte[] receiverAddress = param.getReceiverAddress();
    if (!FastByteComparisons.isEqual(ownerAddress, receiverAddress)) {
      param.setDelegating(true);

      // check if receiver account exists. if not, then create a new account
      AccountCapsule receiverCapsule = repo.getAccount(receiverAddress);
      if (receiverCapsule == null) {
        receiverCapsule = repo.createNormalAccount(receiverAddress);
      }

      // forbid delegating resource to contract account
      if (receiverCapsule.getType() == Protocol.AccountType.Contract) {
        throw new ContractValidateException(
            "Do not allow delegate resources to contract addresses");
      }
    }
  }
