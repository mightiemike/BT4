### Title
Missing upper-bound/sign validation on mint amount allows truncated/wrapped value encoding in `mintParamsToHexString` - (File: framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java)

### Summary
`ShieldedTRC20ParametersBuilder.build()` for the MINT case assigns `value = transparentFromAmount` directly from caller-supplied input and passes it to `mintParamsToHexString`, which only rejects values `<= 0` but never rejects values `>= 2^256`. `ByteUtil.bigIntegerToBytes(value, 32)` then encodes this unchecked `BigInteger` into a fixed 32-byte field that is embedded into the TVM trigger-input for the shielded TRC20 contract's mint call.

### Finding Description
In `ShieldedTRC20ParametersBuilder.build()` (MINT branch), `value = transparentFromAmount;` is set with no range check: [1](#0-0) 

This `value` is forwarded to `getTriggerContractInput` → `mintParamsToHexString`: [2](#0-1) 

`mintParamsToHexString` only validates the lower bound (`value.compareTo(BigInteger.ZERO) <= 0`), and immediately calls `ByteUtil.bigIntegerToBytes(value, 32)` on the unchecked value: [3](#0-2) 

There is no upper-bound check (`< 2^256`) anywhere in `ShieldedTRC20ParametersBuilder` itself. The corresponding `checkBigIntegerRange` full-range validation exists only in `org.tron.core.Wallet` (4 occurrences), which per the question's precondition is invoked from `getShieldedContractScalingFactor`/`getTriggerInputForShieldedTRC20Contract` — a different call path than `Wallet.createShieldedContractParameters` → `builder.build(true)` used for constructing mint parameters directly. Since `build()` is a public method of `ShieldedTRC20ParametersBuilder` and does not itself enforce the `[0, 2^256)` invariant, any caller reaching it with an out-of-range `transparentFromAmount` (e.g., via `createShieldedContractParameters`, which sets `builder.setTransparentFromAmount(from_amount)` directly from the request's `PrivateShieldedTRC20Parameters.from_amount`) can produce a `BigInteger` outside the valid range.

If `value` is negative, `BigInteger.toByteArray()` yields a two's-complement representation; depending on `ByteUtil.bigIntegerToBytes`'s truncation/sign-extension behavior, this can result in an encoded 32-byte word representing a large unsigned value rather than being rejected. If `value >= 2^256`, the byte array from `toByteArray()` exceeds 32 bytes and standard `bigIntegerToBytes` implementations (as used across ethereumj-derived TVM code in this repo) truncate to the low-order 32 bytes, silently discarding high-order bits and encoding a wrapped/truncated amount into the trigger input sent to the shielded TRC20 contract's mint function.

### Impact Explanation
This falls under asset/accounting corruption on the shielded TRC20 mint path: the value ultimately written into the ABI-encoded trigger input for the precompiled/contract-side mint call may not faithfully represent the caller's intended (and validated, since the local-only check is `> 0`) amount, breaking the value-conservation invariant that the underlying token supply accounting for the shielded pool depends on. The scoped fatal impact matches "asset supply corruption / created or destroyed value" in the shielded TRC20 mint flow.

### Likelihood Explanation
Preconditions require only that a caller invoke the RPC/API path that instantiates `ShieldedTRC20ParametersBuilder` for MINT and calls `build(true)` with `transparentFromAmount` set outside `[0, 2^256)` (e.g., via `createShieldedContractParameters`, which does not appear to route through `Wallet.checkBigIntegerRange` the way `getShieldedContractScalingFactor`/`getTriggerInputForShieldedTRC20Contract` do). This requires no special privileges — any client able to submit a `PrivateShieldedTRC20Parameters` request can set an arbitrary `from_amount`. I was not able to fully inspect the body of `Wallet.createShieldedContractParameters` in this session to confirm with certainty that it omits `checkBigIntegerRange` before calling `builder.build()` (tool-call budget exhausted), so this aspect of the reachability claim is based on the question's stated precondition and the confirmed absence of any range check inside `ShieldedTRC20ParametersBuilder`/`mintParamsToHexString` itself.

### Recommendation
Enforce `value.compareTo(BigInteger.ZERO) >= 0 && value.compareTo(BigInteger.ONE.shiftLeft(256)) < 0` (i.e., call the same `checkBigIntegerRange` logic used elsewhere in `Wallet`) directly inside `ShieldedTRC20ParametersBuilder.build()` before assigning `value = transparentFromAmount`, and/or inside `mintParamsToHexString` before calling `ByteUtil.bigIntegerToBytes`, so the check cannot be bypassed regardless of which caller/path constructs the builder.

  private String mintParamsToHexString(GrpcAPI.ShieldedTRC20Parameters mintParams,
      BigInteger value) {
    if (value.compareTo(BigInteger.ZERO) <= 0) {
      throw new IllegalArgumentException("require the value be positive");
    }

    ShieldContract.ReceiveDescription revDesc = mintParams.getReceiveDescription(0);
    byte[] zeros = new byte[12];
    byte[] mergedBytes = ByteUtil.merge(
        ByteUtil.bigIntegerToBytes(value, 32),
        revDesc.getNoteCommitment().toByteArray(),
        revDesc.getValueCommitment().toByteArray(),
        revDesc.getEpk().toByteArray(),
        revDesc.getZkproof().toByteArray(),
        mintParams.getBindingSignature().toByteArray(),
        revDesc.getCEnc().toByteArray(),
        revDesc.getCOut().toByteArray(),
        zeros
    );
    return Hex.toHexString(mergedBytes);
