## Title
Session-Token / OAuth-Callback Handlers Leak Raw Exception Messages, Providing a Verification-Failure Oracle to Anonymous Requesters - ([File: packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts], [File: packages/apps/shopify-api/lib/session/decode-session-token.ts], [File: packages/apps/shopify-app-express/src/auth/auth-callback.ts])

### Summary
Several unauthenticated-request-facing handlers in `shopify-app-express` echo raw `error.message` values back to the HTTP client instead of returning a generic message, mirroring the reported bug class ("returning raw exceptions in API responses"). The most sensitive instance is in the session-token verification path, where the underlying JWT error (including the raw token and the specific `jose` library failure reason) is embedded in the thrown `InvalidJwtError` and then sent verbatim to the caller in the 401 response body.

### Finding Description
`decodeSessionToken` wraps any JWT verification failure into an `InvalidJwtError` whose message directly interpolates the offending token and the internal `jose` error text: [1](#0-0) 

This error propagates to `validateAuthenticatedSession`'s `handleSessionError`, which sends `error.message` straight to the response for `InvalidJwtError` (401) and for any other error (500, generic `Error`, including session-storage exceptions): [2](#0-1) 

The same pattern of forwarding `error.message` for storage failures exists earlier in the same flow: [3](#0-2) 

And in the OAuth callback handler, the default branch sends the raw `error.message` for any unclassified exception thrown by `api.auth.callback`, `sessionStorage.storeSession`, or `registerWebhooks`: [4](#0-3) 

Both `validateAuthenticatedSession` and `authCallback` are reached by anonymous/unauthenticated HTTP requests — the former is the very middleware that decides whether a request is authenticated (an attacker can call any protected route with an arbitrary/forged `Authorization: Bearer` token or `shop` query param), and the latter is the public `/auth/callback` endpoint hit during OAuth.

### Impact Explanation
Returning the verbatim JWT-verification failure reason (and the submitted token) to the caller gives an anonymous attacker a distinguishing oracle when attempting to forge or manipulate a session token: the response tells them precisely why a candidate token was rejected (signature mismatch vs. malformed structure vs. audience mismatch vs. expiry), which they can use to iteratively refine forged tokens or probe for algorithm-confusion / library-specific edge cases. It also leaks whether the failure stems from the app's session-storage backend (e.g., a database driver exception), which can expose storage implementation details useful for session-storage injection or further recon. This is a lower-severity variant of the reported class because HS256/JWT verification generally does not yield a full padding-oracle, but it does materially assist request forgery attempts against the authentication boundary.

### Likelihood Explanation
Low-to-moderate. Exploitation requires an attacker to have write access to try many crafted `Authorization` headers or `shop` params against a live app instance and observe differing error text; this is straightforward to automate but does not by itself produce immediate compromise — it aids/accelerates a forgery attempt rather than directly succeeding.

### Recommendation
Return generic, constant error messages (e.g., "Invalid session" / "Internal Server Error") for all branches in `handleSessionError` and `handleCallbackError`, and never interpolate the raw token or underlying library error text into `InvalidJwtError`'s message that is surfaced to the client. Log the full error (including `error.message` and the token) server-side only via `config.logger.error`, as is already done in `authCallback` before calling `handleCallbackError`.

### Proof of Concept
1. Send `GET /some-protected-route?shop=my-shop.myshopify.io` with header `Authorization: Bearer <malformed-or-tampered-jwt>`.
2. The request hits `validateWithAuthCodeFlow` → `api.session.getCurrentId` → `decodeSessionToken`, which throws `InvalidJwtError` containing the submitted token and the specific `jose` failure reason.
3. `handleSessionError` sends `res.status(401); res.send(error.message)`, so the attacker directly observes the internal verification failure detail in the HTTP response body, which they can use to iterate on forged/tampered tokens.

```typescript
  switch (true) {

      res.status(500);
```

```typescript
async function handleCallbackError(
  req: Request,
  res: Response,
  api: Shopify,
  config: AppConfigInterface,
  error: Error,
) {
  switch (true) {
    case error instanceof InvalidOAuthError:
      res.status(400);
      res.send(error.message);
      break;
    case error instanceof CookieNotFound:
      await redirectToAuth({req, res, api, config});
      break;
    case error instanceof BotActivityDetected:
      res.status(410);
      res.send(error.message);
      break;
    default:
      res.status(500);
      res.send(error.message);
      break;
  }
```
