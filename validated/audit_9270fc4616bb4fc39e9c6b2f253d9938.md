## Analysis: Jackson deep-nesting DoS analog in Starknet sequencer

The Jackson advisory describes an unbounded-recursion deserialization issue: attacker-controlled nested data causes uncontrolled recursion and a stack-overflow/DoS. The closest reachable analog in this codebase is in **compiled-class bytecode-segment hashing/structuring**, which is recursive with no depth bound and is driven by a Sierra program that an unprivileged account fully controls via a `DECLARE` transaction.

### Title
Unbounded recursion in compiled-class bytecode segment hashing/structuring enables stack-overflow DoS from a single DECLARE transaction - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
`SierraCompiler::compile` computes the executable class hash immediately after Sierra→CASM compilation, before any additional size/shape validation runs. The hash routine recurses over the CASM's `bytecode_segment_lengths` (`NestedIntList`) with no depth limit. The Starknet OS performs an equivalent unbounded recursion when constructing the bytecode segment structure during re-execution.

### Finding Description
`bytecode_hash_node` recurses once per nesting level of `NestedIntList` with no depth cap: [1](#0-0) 

It is invoked from `hash_inner`/`HashableCompiledClass::hash`, which is called right after Sierra-to-CASM compilation in the declare-transaction path: [2](#0-1) 

`ClassManager::add_class` invokes `self.compiler.compile(...)` (which performs this recursive hashing) *before* `validate_class_length`, so no size/shape guard runs ahead of the recursive hash computation: [3](#0-2) 

Only felt-count/byte-size limits are enforced on the declared Sierra program at the stateless-gateway level — there is no bound on the nesting *depth* the compiler may produce for `bytecode_segment_lengths`: [4](#0-3) 

An equivalent unbounded recursive function exists in the Starknet OS hint implementation used during block re-execution/proving, operating on the same `NestedIntList` structure: [5](#0-4) 

Note that a sibling function, `NestedFeltCounts::new_inner`, explicitly asserts a segmentation-depth invariant (`assert!(segmentation_depth <= 1, ...)`), demonstrating that the codebase already recognizes this exact class of hazard but does not apply the same guard to `bytecode_hash_node` or `create_bytecode_segment_structure_inner`: [6](#0-5) 

### Impact Explanation
Both recursive functions are on paths reachable purely from a class-declarer submitting a crafted, otherwise-valid Sierra program:
- `bytecode_hash`/`bytecode_hash_node` runs synchronously inside the sequencer's Sierra-compilation service during ordinary `DECLARE` processing (`SierraCompiler::compile`, `ClassManager::add_class`), ahead of the size checks. A stack overflow there aborts/crashes the compiling process, denying declare-transaction processing (a component the whole node needs to admit new classes and, transitively, blocks depending on newly declared classes).
- `create_bytecode_segment_structure_inner` runs in the Starknet OS hint layer used during OS re-execution — a crash there can prevent block re-execution/proving, i.e., a network unable to confirm new blocks/transactions.

This satisfies the required impact bar (network unable to confirm new transactions / honest-node crash on a reachable path).

### Likelihood Explanation
The nesting depth of `bytecode_segment_lengths` produced by the Sierra→CASM compiler for a given program is a function of the program's own function/branch structure, and there is no explicit depth cap enforced by this repository's validators (only felt-count/byte-size caps of `max_contract_bytecode_size` = 81920 felts / `max_contract_class_object_size` ≈ 4 MB apply): [7](#0-6) . An attacker with a normal account can submit a single `DECLARE` transaction; no special privileges are required. Whether an attacker can actually craft a program that drives thousands of nesting levels within the byte-size cap depends on the external `cairo_lang_starknet_classes` compiler's segmentation heuristics (outside this repo, so exact feasibility could not be fully confirmed from the indexed code) — this is the main source of residual uncertainty and should be validated experimentally.

### Recommendation
Add an explicit maximum recursion/nesting-depth check (mirroring the `segmentation_depth <= 1` assertion already used in `NestedFeltCounts::new_inner`) to `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` and to `create_bytecode_segment_structure_inner` in `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`, rejecting/erroring out classes whose `NestedIntList` exceeds a safe depth, and perform this depth validation before or during compilation rather than only after receiving the compiled result.

### Proof of Concept
Not fully constructible from the indexed code alone, since the exact NestedIntList shape is produced by the external `cairo_lang_starknet_classes` compiler crate (not part of this repository's index). Conceptually: submit a `DECLARE` transaction whose Sierra program is structured (e.g., via deeply nested function/branch layout) so that the compiler's segmentation output is a deeply right/left-nested `NestedIntList::Node(vec![NestedIntList::Node(...)])` chain; when `SierraCompiler::compile` calls `.hash(&HashVersion::V2)`, the resulting recursive call chain in `bytecode_hash_node` should scale with nesting depth and can be pushed toward stack-overflow limits within the existing `max_contract_bytecode_size` bound.

**Note on confidence:** Because `cairo_lang_starknet_classes`'s exact segmentation algorithm is an external dependency not present in this index, I could not fully verify how deep an attacker-achievable nesting can get within the byte-size limits. This should be validated against the real compiler crate before treating this as a confirmed exploit rather than a structural finding (missing depth bound on attacker-influenced recursive structure).

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
