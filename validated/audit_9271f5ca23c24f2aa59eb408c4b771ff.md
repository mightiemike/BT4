### Title
Panic-inducing `.unwrap()` on receipt shard remapping causes transaction-triggered chunk-apply halt - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs` unconditionally unwraps the results of `epoch_info_provider.shard_layout(...)` and `receipt.get_receipt().receiver_shard_id(&shard_layout)` while draining the delayed-receipt queue during `Runtime::apply`. [1](#0-0) 
This mirrors the CVE-2022-47094 bug class (an unguarded pointer/Option dereference reached through externally-influenced, delayed/queued data — GPAC's `m2tsdmx_declare_pid` dereferences a PID structure it assumed was already declared). Here, `receiver_shard_id()` is expected to always resolve a receipt's shard for the *current* epoch's shard layout, but a receipt originating before a resharding event (specifically `GlobalContractDistribution` receipts, which carry a `target_shard` set at creation time rather than being derived from `receiver_id`) can become stale relative to the shard layout after subsequent resharding generations, causing the `unwrap()` to panic instead of returning a recoverable error.

### Finding Description
`pop()` calls `receipt_filter_fn` on every delayed receipt dequeued from state while a chunk is being applied: [2](#0-1) 
`receipt_filter_fn` is documented as existing specifically to handle the ReshardingV3 case where delayed receipts in the queue may belong to a shard that no longer matches the current shard layout after a split: [1](#0-0) 
Both `epoch_info_provider.shard_layout(&self.epoch_id)` and `receipt.get_receipt().receiver_shard_id(&shard_layout)` are `.unwrap()`ed rather than propagated as `RuntimeError`. A `GlobalContractDistribution` receipt is queued as delayed when a shard's compute budget is saturated, and its `target_shard` is fixed at creation time; it is not automatically remapped through arbitrary numbers of subsequent resharding events. The codebase itself contains a dedicated regression test that documents exactly this failure mode: [3](#0-2) 
The test explicitly states: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations," and checks that chain height keeps advancing past the point where the delayed queue is drained. [4](#0-3) 

Reachability from an unprivileged actor: any account can (1) deploy a global contract via a signed transaction — which creates a `GlobalContractDistribution` receipt targeted at the deploying account's shard — and (2) submit ordinary `FunctionCall` transactions that saturate the shard's per-chunk compute budget every block, forcing the distribution receipt into the delayed-receipt queue across two or more resharding epochs (resharding itself is a protocol-scheduled, non-privileged event driven by shard load/config). When the delayed queue is later drained, `pop()`/`receipt_filter_fn` processes the now-stale receipt.

### Impact Explanation
If `receiver_shard_id()` cannot resolve the receipt's original `target_shard` against a shard layout that has changed generation twice, the `.unwrap()` panics inside chunk application (`Runtime::apply` → `process_delayed_receipts` → `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`). A panic during `apply` on a chunk-producing/validating node halts that node's chunk processing for the shard — a transaction-triggered halt condition, matching the accepted impact category (invalid state transition / chunk-apply crash triggered by a benign sequence of ordinary transactions and protocol-scheduled resharding). Because every honest validator/chunk-producer for the shard executes the same deterministic state transition, all of them would panic identically, producing a shard-wide liveness halt rather than a single-node crash.

### Likelihood Explanation
Triggering requires: submitting a global contract deploy transaction, saturating compute on that shard for enough blocks to push the resulting receipt into the delayed queue, and having two dynamic-resharding generations occur while the receipt remains queued. All of these are actions an unprivileged transaction sender can perform (deploy + spam compute-heavy calls); resharding cadence is protocol/config-determined but not attacker-privileged. The existence of a purpose-built regression test for this exact scenario indicates the failure mode is a recognized, realistic hazard.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (`?` returning `RuntimeError`/`StorageError::StorageInconsistentState`) instead of panicking, and ensure `receiver_shard_id()` (and `GlobalContractDistribution`'s `target_shard`) is remapped/validated across every resharding generation the receipt survives, not just a single split, so stale receipts are handled gracefully (e.g., re-derive target shard from `receiver_id` when possible, or forward/re-queue instead of panicking).

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` is itself the proof-of-concept path: [5](#0-4) 
1. Deploy a contract and then a global contract from `user0`, creating a `GlobalContractDistribution` receipt targeted at `user0`'s shard.
2. Every block, submit 3 `burn_gas_raw` calls sized to saturate the shard's compute budget so the distribution receipt is pushed into the delayed queue.
3. Force two sequential dynamic resharding splits (`force_split_shards`) while the receipt sits delayed.
4. Stop saturating and let the delayed queue drain; assert that `head_height` keeps advancing past `drain_end` — if `receiver_shard_id()`/`shard_layout()` unwrap fails on the stale receipt, the chain stalls (panics), and the assertion fails.

Note: I could not fully trace the implementation of `receiver_shard_id()` (across `core/primitives/src/shard_layout/{v0,v1,v2,v3}.rs`) within the available tool iterations to confirm definitively whether the current code already guards against the double-resharding case the test exercises, or whether the `.unwrap()` sites are still exploitable in an untested scenario (e.g., three or more resharding generations, or other receipt kinds with fixed target shards). This should be verified directly against `receiver_shard_id`'s implementation and its test coverage.

    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
