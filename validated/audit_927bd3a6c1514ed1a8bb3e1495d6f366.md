### Title
`EpochHistory::verify_ledger_info` silently skips validator-signature verification for "too new" epochs, allowing forged `LedgerInfo` to be accepted during backup restore - (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
Analogous to the Paladin bug where an "extend" operation skipped the whitelist check that was enforced at creation time, Aptos' backup-restore path re-uses `EpochHistory::verify_ledger_info` as the trust-establishing check for `LedgerInfoWithSignatures` supplied by (attacker-controllable) backup storage, but the function has a bypass branch that returns `Ok(())` — treating the ledger info as verified — whenever its epoch number exceeds the epoch history the restoring node has already validated, instead of rejecting it.

### Finding Description
`EpochHistory::verify_ledger_info` is the only place that establishes cryptographic trust (validator-set signature verification) for a `LedgerInfoWithSignatures` fetched from backup storage during state-snapshot and transaction restore: [1](#0-0) 

The relevant branch is:
```
if epoch > self.epoch_endings.len() as u64 {
    // TODO(aldenhu): fix this from upper level
    warn!(... "Epoch is too new and can't be verified. Previous chunks are verified and node
    won't be able to start if this data is malicious.");
    return Ok(());
}
```
This unconditionally accepts the ledger info as valid — without checking the validator signatures against any known validator set — whenever the epoch number is larger than the length of `epoch_endings`, which the restoring node collected earlier in the run from the same (attacker-controllable) backup storage.

This check is the sole gate at the two call sites that bind restored data to a trusted chain of validator signatures: [2](#0-1) [3](#0-2) 

In both call sites, once `epoch_history.verify_ledger_info(&li)` returns `Ok(())`, the code proceeds to trust `li.ledger_info()` as the root of a genuine `TransactionInfoWithProof`/`TransactionAccumulatorRangeProof`, and then commits the corresponding write sets / state values into local durable storage via `StateSnapshotRestore`/`save_transactions`. The Merkle-proof verification (`txn_info_with_proof.verify(...)`, `txn_list_with_proof.verify(...)`) only proves internal consistency between the proof and the supplied root/`LedgerInfo` — it never independently proves that the `LedgerInfo` itself was signed by the real validator set. That external signature binding is exactly what `EpochHistory::verify_ledger_info` is supposed to supply, and exactly what this branch skips.

### Impact Explanation
An attacker who controls (or can tamper with) the backup storage used during restore/fast-sync/disaster-recovery can:
1. Supply a `StateSnapshotBackup` or transaction chunk whose associated `LedgerInfoWithSignatures` has an epoch number greater than the epoch chain length already validated by the restoring node (trivial — the attacker also controls the earlier epoch-ending manifests feeding `epoch_endings`, or the node simply hasn't caught up in epoch history yet for that call).
2. Provide arbitrary, unsigned/forged state root hashes, write sets, transactions, and proofs that are self-consistent (attacker builds a fake accumulator/JMT root with matching proof).
3. Have `verify_ledger_info` return `Ok(())` unconditionally, bypassing the only validator-signature check, so the restore pipeline commits the attacker's fabricated ledger state into the node's durable `AptosDB`.

This directly corrupts committed durable ledger data and lets a wrong accumulator/state root be treated as authenticated, matching the "Committed state that differs from the correct VM result" and "Wrong accumulator root ... state proof accepted as valid" impact classes.

### Likelihood Explanation
The bypass triggers on an ordinary, always-reachable condition (`epoch > self.epoch_endings.len()`), not a rare edge case; the comment in the code (`TODO(aldenhu): fix this from upper level`) shows the maintainers are aware this path is not intended to hold true trust but currently does. Any operator/tooling restoring from an untrusted or compromised backup bucket, or performing partial/segmented epoch-history restores (`skip_epoch_endings`-adjacent flows, or when `epoch_history` is built incrementally per manifest), can hit this path.

### Recommendation
Change the "epoch too new" branch to return an error (e.g., `bail!("Epoch {} exceeds verified epoch history (len {})", epoch, self.epoch_endings.len())`) instead of `Ok(())`, or refuse to proceed with the restore chunk until the epoch-ending history has advanced far enough to actually verify it. Do not treat "unverifiable" as "verified."

### Proof of Concept
1. Build a malicious backup with an `EpochEndingBackup` and `StateSnapshotBackup` where the `LedgerInfoWithSignatures` bundled with the state-snapshot proof carries an epoch number far beyond the number of `epoch_endings` the restoring node will have validated at that point in the run (e.g., set `epoch = u64::MAX` while keeping `version <= target_version`).
2. Sign nothing real — fabricate accumulator/JMT roots and matching internal proofs so `txn_info_with_proof.verify(li.ledger_info(), manifest.version)` succeeds against the forged `li`.
3. Run `StateSnapshotRestoreController::run_impl` (storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs:113-139) against this manifest with a populated `epoch_history`.
4. Observe `epoch_history.verify_ledger_info(&li)` return `Ok(())` via the "epoch too new" branch, and the forged state values/root get committed to the target `AptosDB`, corrupting the restored ledger state without any validator signature ever being checked.

impl EpochHistory {
    pub fn verify_ledger_info(&self, li_with_sigs: &LedgerInfoWithSignatures) -> Result<()> {
        let epoch = li_with_sigs.ledger_info().epoch();
        ensure!(!self.epoch_endings.is_empty(), "Empty epoch history.",);
        if epoch > self.epoch_endings.len() as u64 {
            // TODO(aldenhu): fix this from upper level
            warn!(
                epoch = epoch,
                epoch_history_until = self.epoch_endings.len(),
                "Epoch is too new and can't be verified. Previous chunks are verified and node \
                won't be able to start if this data is malicious."
            );
            return Ok(());
        }
        if epoch == 0 {
            ensure!(
                li_with_sigs.ledger_info() == &self.epoch_endings[0],
                "Genesis epoch LedgerInfo info doesn't match.",
            );
        } else if let Some(wp_trusted) = self
            .trusted_waypoints
            .get(&li_with_sigs.ledger_info().version())
        {
            let wp_li = Waypoint::new_any(li_with_sigs.ledger_info());
            ensure!(
                *wp_trusted == wp_li,
                "Waypoints don't match. In backup: {}, trusted: {}",
                wp_li,
                wp_trusted,
            );
        } else {
            self.epoch_endings[epoch as usize - 1]
                .next_epoch_state()
                .ok_or_else(|| anyhow!("Shouldn't contain non- epoch bumping LIs."))?
                .verify(li_with_sigs)?;
        };
        Ok(())
    }
