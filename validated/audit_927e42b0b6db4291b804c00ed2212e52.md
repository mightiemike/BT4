## Title
Inconsistent validation between `UnDelegateResourceActuator` and `UnDelegateResourceProcessor` for locked/expired delegated resources - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
The reported bug class in DebtToken is "duplicated logic across two implementations that must be kept in sync, where one path silently diverges from the other's semantics." An analogous pattern exists in java-tron: `UnDelegateResourceContract` handling is implemented twice — once in `UnDelegateResourceActuator` (used for ordinary broadcast transactions) and once in `UnDelegateResourceProcessor` (used by the TVM native-contract/precompile path reachable from a contract `CALL`). These two implementations do not stay in sync with respect to the "locked" delegated-resource record.

### Finding Description
`UnDelegateResourceActuator.execute()` first calls `delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, dynamicStore.getLatestBlockHeaderTimestamp())` before reading the "unlock" key resource, and its `validate()` explicitly checks both the unlock-key `DelegatedResourceCapsule` (`createDbKeyV2(..., false)`) and the lock-key capsule (`createDbKeyV2(..., true)`), including its already-expired balance, as an available source of balance to undelegate: [1](#0-0) [2](#0-1) 

`UnDelegateResourceProcessor` (the TVM/native-contract counterpart, reachable from an on-chain contract call, per the `param`/`repo`-based interface) reimplements the same operation but its `validate()` only fetches and checks the unlock-key capsule, never consulting or migrating the lock-key/expired resource, and its `execute()` never calls `unLockExpireResource`: [3](#0-2) [4](#0-3) 

This mirrors the DebtToken bug class exactly: instead of factoring the "unlock expired resource + subtract balance" logic into one shared routine that both callers invoke, java-tron maintains two independent copies of the state-transition logic for the same protocol contract (`UnDelegateResourceContract`), and the two copies have already drifted apart on a semantically important detail (whether an expired lock record counts as available delegated balance).

### Impact Explanation
Because the two code paths for the same logical operation diverge, a delegator whose only remaining delegated balance sits in an expired "locked" record (`createDbKeyV2(..., true)`) can successfully undelegate via a normal transaction (`UnDelegateResourceActuator`) but will be rejected with "delegated Resource does not exist" when the equivalent operation is attempted through the TVM native-contract path (`UnDelegateResourceProcessor`), or vice versa in edge cases involving partial unlock/lock balances. This is a functional/DoS-class inconsistency rather than a direct fund-theft bug in the code I was able to review, but it demonstrates the exact "duplication of state-mutation logic across two entry points" root cause flagged in the report, and any future maintenance change applied to one path but not the other (e.g., a fix to `unLockExpireResource` handling) risks a much more serious accounting divergence between the two callers of the same contract semantics, since nothing enforces that they stay behaviorally identical.

### Likelihood Explanation
Reachability is straightforward: `UnDelegateResourceProcessor` is invoked from the TVM native-contract dispatch for `UnDelegateResourceParam`, which is driven by an ordinary smart-contract call (any account can trigger it via a contract that issues the corresponding TVM opcode/precompile call), while `UnDelegateResourceActuator` is invoked by any anonymous broadcast transaction of type `UnDelegateResourceContract`. Both are reachable without privileged access, so triggering the divergent behavior requires only crafting a delegated-resource state where the lock record has expired and no unlock record exists, then calling both paths to observe inconsistent results.

### Recommendation
Refactor `UnDelegateResourceActuator` and `UnDelegateResourceProcessor` to share a single implementation (e.g., have the actuator delegate to `UnDelegateResourceProcessor`, or extract a common helper), ensuring both the "migrate expired lock resource into the unlock record" step (`unLockExpireResource`) and the validate-time check of both lock/unlock capsules are performed identically in both code paths. This removes the duplicated logic instead of maintaining two independently-evolving copies, directly matching the recommended fix pattern from the report (intercept/share the state-mutation logic rather than reimplementing it).

### Proof of Concept
1. Delegate resource from account A to account B twice: once as a normal (unlock) delegation, and once as a "locked" delegation (`isLock = true`) with an expiration timestamp in the near future — this creates a `DelegatedResourceCapsule` at `createDbKeyV2(A, B, true)`.
2. Wait until the lock's expiration time passes (or manipulate `dynamicStore.getLatestBlockHeaderTimestamp()` in a private test harness) so the lock is expired, and ensure no unlock-key record exists for (A, B) (delete/never create it).
3. Path 1 (actuator): submit an `UnDelegateResourceContract` transaction for A→B. `validate()` succeeds because `lockResourceCapsule.getExpireTimeForBandwidth() < now` counts its balance; `execute()` calls `unLockExpireResource` to migrate it and completes successfully.
4. Path 2 (TVM native contract): from a deployed contract, invoke the corresponding native precompile equivalent to `UnDelegateResourceContract` for the same A→B pair and amount. `UnDelegateResourceProcessor.validate()` calls `repo.getDelegatedResource(key)` only for the unlock key, finds `null`, and throws `"delegated Resource does not exist"`, rejecting an operation that the actuator path would accept — demonstrating the behavioral divergence between the two duplicated implementations of the same contract logic.

Note: I was unable to fully verify the exact TVM opcode/precompile entry point that constructs `UnDelegateResourceParam` (searches for its construction site in `Program.java` or a dispatcher class did not return results within the available index), so the precise call-site wiring from an arbitrary contract to `UnDelegateResourceProcessor.execute()` should be confirmed directly in the repository before treating this as fully proven; the core divergence in `validate()`/`execute()` logic between the two files is, however, directly confirmed from the source shown above.
