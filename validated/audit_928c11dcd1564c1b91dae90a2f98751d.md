### Title
Vote program `UpdateCommissionBps` accepts unbounded commission values with no upper-bound validation, permitting > 100% commission - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The external report describes a class of bug where a user-supplied numeric field (`customAttributes` for fighter `weight`/`element`) is accepted without any range validation and later consumed by downstream logic that assumes the value is bounded, causing arbitrary/extreme values to corrupt game mechanics. The equivalent defect exists in the Agave vote program's `update_commission_bps` function: the caller-supplied `commission_bps: u16` (range 0–65,535) is stored directly into `VoteStateV4` with no upper-bound check against the natural 100% ceiling (10,000 bps), even though this value is later consumed as a percentage split factor in inflation reward distribution.

### Finding Description
`update_commission_bps` in `programs/vote/src/vote_state/mod.rs` writes the caller-provided `commission_bps` straight into `inflation_rewards_commission_bps` or `block_revenue_commission_bps` with no bound check: [1](#0-0) 

The only validation performed is a signature check (`authorized_withdrawer` must sign) and, for `CommissionKind::BlockRevenue`, a feature-gate check — there is no range/sanity check equivalent to what should restrict a commission rate to `[0, 10_000]` basis points (0%–100%): [2](#0-1) 

This is confirmed directly in the program's own test suite, which explicitly documents that values above 100% are accepted at the program level: [3](#0-2) 

This stored `commission_bps` value is later read out of the vote account and used as `voter_commission_bps` in the epoch inflation-reward redemption path, where it is expected to represent a fraction of rewards to send to the voter versus the staker: [4](#0-3) [5](#0-4) 

This is structurally identical to the AI Arena finding: an unprivileged, non-consensus-critical instruction (`UpdateCommissionBps`, callable by any vote account's `authorized_withdrawer` — not a node/validator-privileged operation) accepts an unbounded numeric attribute and stores it verbatim; the value is later relied upon by a percentage-split calculation elsewhere in the codebase (`redeem_stake_rewards` / `calculate_stake_points_and_credits`) that implicitly assumes the value represents a valid fraction of 100%.

### Impact Explanation
If `voter_commission_bps` exceeds 10,000 (100%), the downstream stake/voter reward split calculation (`points.rs`, invoked from `redeem_stake_rewards`) is no longer guaranteed to be a valid partition of the total reward pool. Depending on how the split arithmetic is implemented (fraction of `commission_bps / 10_000` applied to total rewards, with the remainder assigned to the staker), a commission > 100% can cause the voter's share to exceed the total reward amount, potentially causing an incorrect distribution of lamports between staker and voter (economic value shifted away from the staker, or duplicated/miscalculated total emitted lamports depending on how the subtraction/remainder is computed). This falls under the "lamport inflation or loss" impact category described in the validation rules.

I was not able to fully trace the exact arithmetic in `runtime/src/inflation_rewards/points.rs` within the available tool budget to confirm whether the split is `saturating`/checked in a way that fully neutralizes overcommission, so the precise magnitude of lamport miscalculation (versus a merely "unfair" but bounded split) is not fully verified here.

### Likelihood Explanation
Likelihood is high for the root cause (missing validation) since it is proven directly by the program's own test comment (`programs/vote/src/vote_state/mod.rs:1932-1934`) stating values above 10,000 bps and even 50,000 bps (500%) are accepted "at program level." Any holder of a vote account's withdraw-authority keypair — an ordinary, non-privileged signer, not requiring validator/node privileges — can trigger this by simply calling `UpdateCommissionBps` once `commission_rate_in_basis_points` and `delay_commission_updates` features are active. This requires no special network position, timing, or node compromise.

### Recommendation
Add an explicit upper-bound check in `update_commission_bps` (and any equivalent commission-setting path) rejecting `commission_bps > 10_000`, returning `InstructionError::InvalidInstructionData` for out-of-range values, consistent with how commission was previously bounded implicitly by the `u8` percentage representation (0–100) before SIMD-0291 introduced basis-point precision.

### Proof of Concept
1. Create/own a vote account (`VoteStateV4`, features `commission_rate_in_basis_points` and `delay_commission_updates` enabled).
2. Submit `VoteInstruction::UpdateCommissionBps { commission_bps: 50_000, kind: CommissionKind::InflationRewards }` signed by the account's `authorized_withdrawer`.
3. Observe the instruction succeeds and `inflation_rewards_commission_bps` is set to 50,000 (500%), as directly reproduced by the existing unit test: [6](#0-5) 
4. On the next epoch's inflation reward redemption for stake delegated to this vote account, `voter_commission_bps = 50_000` is passed into `redeem_rewards`/`redeem_stake_rewards`, exceeding the implicit 100% assumption of the reward-split calculation.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
