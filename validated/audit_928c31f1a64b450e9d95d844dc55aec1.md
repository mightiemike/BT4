### Title
Freezing additional TRX resets the unfreeze/lock expiration of already-frozen balance, extending an account's lockup period without consent - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.execute()` and its TVM analog `FreezeBalanceProcessor.execute()` combine a new `frozenBalance` with the account's existing frozen balance and unconditionally overwrite the stored `Frozen.expireTime` with a freshly computed `now + duration`, discarding the original (potentially sooner) expiration. This mirrors the reported `VaderBond.deposit()` bug class: state that tracks a lock/vesting period is blindly overwritten on a repeat "deposit" (here, a repeat freeze), resetting the wait time for funds the user could otherwise have already unlocked.

### Finding Description
When a user calls `FreezeBalanceContract` a second time for the same resource type (BANDWIDTH/ENERGY/TRON_POWER), the actuator computes a brand-new `expireTime = now + duration` and calls `AccountCapsule.setFrozenForBandwidth` / `setFrozenForEnergy` / `setFrozenForTronPower`, which each **replace** the single stored `Frozen` entry (balance + expireTime) rather than tracking the previous freeze's expiration separately: [1](#0-0) 

```
long now = dynamicStore.getLatestBlockHeaderTimestamp();
long duration = freezeBalanceContract.getFrozenDuration() * FROZEN_PERIOD;
...
long expireTime = now + duration;
...
long newFrozenBalanceForBandwidth = frozenBalance + accountCapsule.getFrozenBalance();
accountCapsule.setFrozenForBandwidth(newFrozenBalanceForBandwidth, expireTime);
```

`setFrozenForBandwidth` overwrites the whole `Frozen` field (combined balance + the new, later `expireTime`) instead of preserving the original expiry for the previously frozen portion: [2](#0-1) 

The same overwrite pattern exists for ENERGY (`setFrozenForEnergy`) [3](#0-2)  and TRON_POWER (`setFrozenForTronPower`) [4](#0-3) , and identically in the TVM-callable native processor used by `freezeBalanceV2`/`freezeBalance` opcodes: [5](#0-4) 

`UnfreezeBalanceActuator` (the withdrawal path) only allows unfreezing the whole combined `Frozen` entry once its single `expireTime` has passed — there is no per-freeze-event tracking, so once the entry is overwritten, the entire combined balance (old + new) is locked until the newest, later `expireTime`.

### Impact Explanation
An account owner who freezes TRX a second time (e.g., to top up bandwidth/energy) unintentionally resets the clock on funds that were already close to becoming unfreezable, forcing them to wait the full new `duration` (`minFrozenTime`–`maxFrozenTime` days) again before they can call `UnfreezeBalanceContract` on the entire combined balance. This is a self-inflicted, unrequested lockup extension — the same bug class as the vesting-period reset in the original report (state overwrite discards an existing unlock/vesting clock). It does not grant an attacker access to another account's funds, but it silently and irreversibly extends the caller's own asset lockup with no warning or opt-out, which is a form of accounting/state-integrity corruption directly reachable via a normal broadcast `FreezeBalanceContract` transaction or the `freezeBalanceV2`/related TVM opcode.

### Likelihood Explanation
High likelihood of accidental trigger: any account holder who freezes additional TRX (a very common, everyday operation for gaining bandwidth/energy) while already holding a frozen balance will trigger this behavior every time, with no validation, warning, or protection preventing it. No privileged role or malicious peer is required — a single unprivileged, anonymous broadcast transaction reaches the vulnerable path deterministically.

### Recommendation
Track per-freeze-operation expiration (e.g., a list of `(balance, expireTime)` entries, similar to the `FreezeV2`/`UnFreezeV2` model already used elsewhere in the codebase such as `AccountCapsule.addUnfrozenV2List`) instead of collapsing all frozen balance into one `Frozen` object with a single, overwritable `expireTime`. At minimum, when combining balances, retain the earliest of the old and new expire times for the portion that was already unlockable, or require users to unfreeze/withdraw existing unlockable balance before permitting a new freeze that would otherwise silently extend the lock.

### Proof of Concept
1. Account A calls `FreezeBalanceContract` with `frozenDuration = 3` days for BANDWIDTH. `Frozen{balance: X, expireTime: t0 + 3d}` is stored via `FreezeBalanceActuator.execute()` [6](#0-5) .
2. 2.9 days later (before expiry), Account A calls `FreezeBalanceContract` again with `frozenDuration = 3` days to add balance Y for BANDWIDTH.
3. `setFrozenForBandwidth(X + Y, now + 3d)` overwrites the stored `Frozen` entry [2](#0-1) , so the entire `X + Y` balance is now locked until `now + 3d`, i.e., roughly 5.9 days from the original freeze — even though `X` was only 0.1 day away from being unlockable.
4. Any call to `UnfreezeBalanceContract` for `X` alone fails until the new, later `expireTime` is reached, since `UnfreezeBalanceActuator` only checks the single combined `Frozen.expireTime`.

        .build();

  public void execute(FreezeBalanceParam param,  Repository repo) {
    // calculate expire time
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    long nowInMs = dynamicStore.getLatestBlockHeaderTimestamp();
    long expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD;

    byte[] ownerAddress = param.getOwnerAddress();
    byte[] receiverAddress = param.getReceiverAddress();
    long frozenBalance = param.getFrozenBalance();
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    // acquire or delegate resource
    if (param.isDelegating()) { // delegate resource
      switch (param.getResourceType()) {
        case BANDWIDTH:
          delegateResource(ownerAddress, receiverAddress,
              frozenBalance, expireTime, true, repo);
          accountCapsule.addDelegatedFrozenBalanceForBandwidth(frozenBalance);
          break;
        case ENERGY:
          delegateResource(ownerAddress, receiverAddress,
              frozenBalance, expireTime, false, repo);
          accountCapsule.addDelegatedFrozenBalanceForEnergy(frozenBalance);
          break;
        default:
          logger.debug("Resource Code Error.");
      }
    } else { // acquire resource
      switch (param.getResourceType()) {
        case BANDWIDTH:
          accountCapsule.setFrozenForBandwidth(
              frozenBalance + accountCapsule.getFrozenBalance(),
              expireTime);
          break;
        case ENERGY:
          accountCapsule.setFrozenForEnergy(
              frozenBalance + accountCapsule.getAccountResource()
                  .getFrozenBalanceForEnergy()
                  .getFrozenBalance(),
              expireTime);
          break;
        default:
          logger.debug("Resource Code Error.");
      }
    }
