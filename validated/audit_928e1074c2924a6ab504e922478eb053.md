Found a concrete analog: a reachable `.unwrap()`-induced panic in the delayed-receipt draining path (`receipt_filter_fn`), which is directly attacker-triggerable through a normal transaction (deploying a global contract) combined with shard resharding — matching the CVE-2021-44993 bug class of an assertion/invariant panic reachable through routine, attacker-influenced execution.

### Title
Transaction-triggered node panic via unmapped `receiver_shard_id()` on stale `GlobalContractDistribution` receipts after resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the result of `receiver_shard_id(&shard_layout)` while draining the delayed-receipt queue. If a `GlobalContractDistribution` receipt's `target_shard` can no longer be mapped into the current shard layout (e.g., after the shard it targeted has been split away by resharding), this call returns an `Err`, and the `.unwrap()` panics on every node applying that chunk.

### Finding Description
`receipt_filter_fn` is used by `DelayedReceiptQueueWrapper::pop` and `peek_iter` to skip delayed receipts that no longer belong to the current shard after a `ReshardingV3` split: [1](#0-0) 

Both call sites blindly trust this to succeed: [2](#0-1) 

`receiver_shard_id()` for a `GlobalContractDistribution` receipt is computed from its `target_shard`, which was fixed at receipt-creation time by whatever shard layout existed then. If that target shard is later removed/renumbered by a *second* resharding event (splitting the same lineage twice) while the receipt is still sitting in the delayed queue (e.g., because the destination shard's chunk was kept saturated with unrelated compute-heavy transactions), the shard layout can no longer resolve `target_shard` back to a live shard id, and `receiver_shard_id()` returns an error instead of a shard id. The `.unwrap()` in `receipt_filter_fn` then panics.

A dedicated regression test in the repo demonstrates exactly this scenario end-to-end from an ordinary user account: deploying a contract, deploying a global contract (which creates the `GlobalContractDistribution` receipt), then keeping the target shard saturated with `burn_gas_raw` calls through two consecutive dynamic-resharding splits so the receipt stays delayed across both: [3](#0-2) [4](#0-3) 

The test's own comment states the expected failure mode directly: [5](#0-4) 

This entire sequence — deploying a contract, deploying a global contract, and submitting repeated `FunctionCall` transactions to saturate compute on the target shard — is achievable by any unprivileged account with sufficient balance/gas; no validator, operator, or network-layer privilege is required. The only external factor is that dynamic resharding must be enabled and trigger two splits along the receipt's shard lineage while the receipt is delayed, which is a protocol-level configuration/timing condition, not an attacker-only precondition, and is realistic on any chain running `DynamicResharding`.

### Impact Explanation
A panic inside `Runtime::apply`'s receipt-processing loop is not a per-transaction failure — it aborts the node process while applying a chunk. Because `receipt_filter_fn` runs identically on every validator/node applying the same chunk (deterministic replay), the panic occurs on **all** honest nodes simultaneously, producing a chain-wide halt rather than an isolated node crash. This matches the "transaction-triggered halt" impact class explicitly allowed by the scan rules: an unprivileged account's ordinary transactions (contract deploy + global contract deploy + compute-saturating calls) combined with routine resharding activity lead to universal node panic and liveness loss.

### Likelihood Explanation
The trigger requires only standard user-level actions (deploying a contract, deploying a global contract, and submitting `FunctionCall` transactions to saturate a shard's compute budget) reachable by any signer. The additional requirement — two resharding splits occurring along the same shard lineage while the receipt remains delayed — depends on `DynamicResharding` being enabled and configured, so likelihood is tied to a chain's resharding configuration/timing rather than to gaining any special privilege. Given nearcore ships and actively exercises dynamic resharding, and the repository itself carries a dedicated regression test purpose-built to reproduce this exact panic, the scenario is a recognized, reachable condition rather than a purely theoretical one.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with graceful handling: if `receiver_shard_id()` fails to resolve a delayed receipt's target into the current shard layout, treat the receipt as belonging to neither (or to a special "unroutable" bucket) instead of panicking — e.g., return a `Result`/skip-and-log path from `pop`/`peek_iter`, or track a full split-lineage remapping (not just parent→one child) for `GlobalContractDistribution` receipts so `target_shard` remains resolvable across an arbitrary number of resharding events. Given `receipt_filter_fn`, `pop`, and `peek_iter` are private (non-`pub` or `pub(crate)`) helpers of `DelayedReceiptQueueWrapper`, this can be fixed without changing any public API.

### Proof of Concept
The nearcore test suite already contains a full, working PoC that exercises this exact path via ordinary transactions: [6](#0-5) 

It: (1) deploys a contract and a global contract from a normal user account, (2) forces two sequential dynamic-resharding splits along the shard containing the deploying account, (3) keeps that shard's compute saturated every block with `burn_gas_raw` calls so the `GlobalContractDistribution` receipt is pushed to and stays in the delayed queue across both splits, then (4) stops saturating and asserts the chain continues advancing (i.e., does not panic while draining the stale receipt) — the assertion failing is the documented signature of this vulnerability being present.

    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }

        .build();

        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);

            both_splits_done = true;
            break;
        }
    }
