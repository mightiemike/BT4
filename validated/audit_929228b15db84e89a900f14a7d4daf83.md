## Finding

### Title
Sequencer receives no compensation for mandatory L1Handler execution while only a nominal, cost-unrelated L1 fee is enforced - ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs])

### Summary
The JOJO report describes a design flaw where a permissionless matcher can be forced to accept a negative fee for performing required work, removing its economic incentive to participate. The Starknet sequencer has a structurally analogous flaw for `L1HandlerTransaction` execution: an L1 message sender can trigger sequencer-side execution while paying an amount that bears no relation to the actual computational cost, and — unlike ordinary account transactions — no fee-transfer to the sequencer ever occurs for L1Handler transactions at all.

### Finding Description
When an `L1HandlerTransaction` is executed, the only fee-related check performed is that `paid_fee_on_l1 != Fee(0)`: [1](#0-0) 

The comment on this code explicitly acknowledges the gap: *"For now, assert only that any amount of fee was paid."* There is no check that `paid_fee_on_l1` covers, or is even proportional to, the `receipt.fee` (the actual computed cost of execution) — the `receipt.gas`/`receipt.fee` values are only used to validate against `l1_handler_max_amount_bounds` (a per-tx resource ceiling), not against the amount paid.

Critically, unlike `AccountTransaction`, no ERC20 fee-transfer call is ever executed for L1Handler transactions to compensate the sequencer/proposer: [2](#0-1) 
Compare this with `AccountTransaction::handle_fee`, which performs an actual token transfer crediting the sequencer's balance: [3](#0-2) 

So the sequencer that builds/validates a block containing L1Handler transactions:
1. Is not permitted to reject them for being underpriced (the code only requires `paid_fee_on_l1 != Fee(0)`, e.g. `Fee(1)` is accepted).
2. Receives no on-chain balance credit for the resources spent executing them (proving cost, Sierra gas, storage writes) — there is no `fee_transfer_call_info` for L1Handler, contrary to account transactions where `add_fee_to_sequencer_balance` runs: [4](#0-3) 

Inclusion of L1Handler transactions is mandatory/prioritized ahead of mempool transactions in block building (`ProposeTransactionProvider` fetches L1Handler txs first, up to `max_l1_handler_txs_per_block_proposal`): [5](#0-4) [6](#0-5) 

This is the same bug class as the JOJO finding: an unprivileged, permissionless external actor (here, an L1 message sender rather than an order matcher) can impose real execution cost on the entity that must process the request, while paying a fee that is decoupled from, or entirely absent relative to, that cost — removing/negating the economic incentive for the party doing the work.

### Impact Explanation
An L1 contract caller can send `LogMessageToL2` messages with an arbitrarily small `paid_fee_on_l1` (e.g. `Fee(1)`, as used by `convert_consensus_l1_handler_to_internal_l1_handler`'s current placeholder), forcing the sequencer to execute potentially resource-heavy `L1Handler` calldata every block cycle (up to `max_l1_handler_txs_per_block_proposal`, prioritized ahead of paying mempool transactions) without any compensating fee transfer. Sustained, cheap L1-side spam degrades sequencer economics and crowds out paying transactions from block capacity, since L1Handler slots are consumed first regardless of payment adequacy — a resource-asymmetric cost that can degrade the network's capacity to confirm ordinary (fee-paying) transactions.

### Likelihood Explanation
Triggering this requires only sending a message to the L2 bridge/core contract from L1 (an unprivileged, permissionless action reachable by any L1 account) with a minimal non-zero value. No special privilege on the sequencer/node is required; the flaw is in the protocol-level fee-enforcement logic itself, and the responsible code explicitly flags it as an interim ("For now") behavior rather than a hardened invariant.

### Recommendation
Enforce that `paid_fee_on_l1` covers (or is checked proportionally against) the actual computed `receipt.fee`/`receipt.gas` for the L1Handler transaction, similar to the `InsufficientFee` error already defined for this purpose, and/or implement an explicit compensation mechanism (fee transfer or credit) to the sequencer for L1Handler execution so that resource cost and payment are economically aligned, consistent with the treatment of `AccountTransaction`.

### Proof of Concept
1. An L1 account calls the Starknet core contract's `sendMessageToL2` with `value` set to a minimal non-zero amount (as `send_message_to_l2` does with an arbitrary `PAID_FEE_ON_L1`).
2. This produces an `L1HandlerTransaction` with `paid_fee_on_l1 = Fee(1)` (matching the current codebase default seen in `convert_consensus_l1_handler_to_internal_l1_handler`): [7](#0-6) 
3. During block building, `ProposeTransactionProvider` fetches this transaction ahead of ordinary mempool transactions (up to the per-block L1Handler cap).
4. `L1HandlerTransaction::execute_raw` computes the real `receipt.fee` from actual gas usage, but only checks `paid_fee_on_l1 != Fee(0)` — `Fee(1)` passes regardless of how large `receipt.fee` is (bounded only by `l1_handler_max_amount_bounds`), and no fee-transfer call is ever made to the sequencer: [8](#0-7) 
5. Repeating this from L1 lets the caller force sequencer execution of L1Handler payloads while paying negligible/no real compensation, block after block, up to the configured cap each time.

        state: &mut TransactionalState<'_, S>,
        tx_context: Arc<TransactionContext>,
        actual_fee: Fee,
        charge_fee: bool,
        concurrency_mode: bool,
    ) -> TransactionExecutionResult<Option<CallInfo>> {
        if !charge_fee || actual_fee == Fee(0) {
            // Fee charging is not enforced in some tests.
            // TODO(Yoni): consider setting the actual fee to zero when the flag is off.
            return Ok(None);
        }

        Self::assert_actual_fee_in_bounds(&tx_context, actual_fee);

        let fee_transfer_call_info = if concurrency_mode && !tx_context.is_sequencer_the_sender() {
            Self::concurrency_execute_fee_transfer(state, tx_context, actual_fee)?
        } else {
            Self::execute_fee_transfer(state, tx_context, actual_fee)?
        };

        Ok(Some(fee_transfer_call_info))
    }

        n_txs: usize,

            .get_txs(n_txs, self.height)
            .await
