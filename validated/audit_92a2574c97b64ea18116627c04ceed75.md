### Title
Unconditional TRX/TRC10 transfer to precompiled contract addresses causes permanently locked funds - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The reported bug class ("missing payable") is about a function that receives `msg.value` without being designed/marked to properly receive and use it, leading to fund loss. The strongest analog reachable from an untrusted smart-contract call path (any `CALL`/`CALLTOKEN`/`CALLCODE`/`DELEGATECALL` opcode executed inside the TVM) is `Program.callToPrecompiledAddress`, which unconditionally moves the call's `endowment` (TRX) or token value to the fixed precompiled-contract address before invoking `contract.execute(data)` — even though none of the `PrecompiledContracts.PrecompiledContract` implementations are designed to receive or redistribute that value.

### Finding Description
When a contract executes `CALL`/`CALLTOKEN` with a nonzero value against a precompiled address (resolved via `PrecompiledContracts.getContractForAddress(codeAddress)`), execution goes through `Program.callToPrecompiledAddress`: [1](#0-0) 
The endowment is transferred to `contextAddress` (the precompiled contract's fixed address) via `MUtil.transfer`/`addTokenBalance` unconditionally whenever `endowment > 0`, prior to calling `contract.execute(data)`: [2](#0-1) 
The dispatch that routes value-bearing calls to precompiled addresses happens in `OperationActions.exeCall`, which is reachable from ordinary `CALL`/`CALLTOKEN`/`CALLCODE` opcode handlers triggered by any user-submitted `TriggerSmartContract` transaction: [3](#0-2) 
None of the `PrecompiledContracts.PrecompiledContract` subclasses (e.g. signature/multisig verification, zk-SNARK helpers) implement any logic to spend, forward, or refund a balance credited to their own fixed address — the address has no owning key and no code path exists elsewhere in the codebase to withdraw from a precompile's balance. This is functionally the same root cause as "missing payable": value is accepted into a context (the precompile) whose logic was never written to expect or use `msg.value`, so it is simply absorbed with no accounting for it, rather than being rejected upfront.

### Impact Explanation
Any TRX or TRC10 tokens sent with value to a precompiled contract address via `CALL`/`CALLTOKEN` are permanently locked in that address's balance since precompiled addresses do not correspond to any spendable account/private key, and no actuator or opcode path exists to move balance out of them. This is an unintended, irreversible loss of user funds triggerable by any contract-calling transaction, with no privileged actor required.

### Likelihood Explanation
This is reachable by any user who deploys or calls a contract performing a `CALL`-with-value (e.g. `address(precompileAddr).call.value(x)(...)`) targeting one of the fixed precompiled addresses. Since precompiled addresses are well known/fixed and `PrecompiledContracts.getContractForAddress` resolution happens before the value transfer, triggering the loss requires only a single crafted, unprivileged transaction. Likelihood of accidental occurrence may be considered low (since it requires deliberately or mistakenly calling with value to a known precompile address), but the mechanism itself is unconditionally exploitable/triggerable without any special permission.

### Recommendation
Reject (revert/refund) any `CALL`/`CALLTOKEN` targeting a precompiled contract address that carries nonzero `endowment`/token value before performing the balance transfer in `Program.callToPrecompiledAddress`, mirroring how EVM implementations generally disallow sending value to precompiles that don't explicitly support it. At minimum, add an explicit check immediately before the transfer block at lines 1701-1721 of `Program.java` so that value-bearing calls to `PrecompiledContracts` addresses fail fast (push zero / revert and refund energy) instead of silently locking funds.

### Proof of Concept
1. Deploy or use any contract with a function that performs `someAddr.call.value(N)(data)` where `someAddr` is a known precompiled contract address (any address recognized by `PrecompiledContracts.getContractForAddress`).
2. Submit a `TriggerSmartContract` transaction invoking this function with `N > 0`.
3. `OperationActions.callAction`/`callTokenAction` → `exeCall` resolves the target as a precompiled contract and calls `Program.callToPrecompiledAddress`.
4. The `MUtil.transfer(deposit, senderAddress, contextAddress, endowment)` call at `Program.java:1706` credits `N` TRX to the precompile's fixed address balance.
5. `contract.execute(data)` runs normal precompile logic (e.g., signature validation) with no awareness of or use for the transferred balance.
6. The `N` TRX now sits in the balance of an address with no private key and no withdrawal path anywhere in the codebase — permanently lost to the sender.

  public static void exeCall(Program program, DataWord adjustedCallEnergy,
      DataWord codeAddress, DataWord value, DataWord tokenId, boolean isTokenTransferMsg) {

    DataWord inDataOffs = program.stackPop();
    DataWord inDataSize = program.stackPop();

    DataWord outDataOffs = program.stackPop();
    DataWord outDataSize = program.stackPop();

    program.memoryExpand(outDataOffs, outDataSize);
    int op = program.getCurrentOpIntValue();
    MessageCall msg = new MessageCall(
        op, adjustedCallEnergy, codeAddress, value, inDataOffs, inDataSize,
        outDataOffs, outDataSize, tokenId, isTokenTransferMsg);

    PrecompiledContracts.PrecompiledContract contract =
        PrecompiledContracts.getContractForAddress(codeAddress);
    if (contract != null) {
      if (program.isConstantCall()) {
        contract =  PrecompiledContracts.getOptimizedContractForConstant(contract);
      }
      program.callToPrecompiledAddress(msg, contract);
    } else {
      program.callToAddress(msg);
    }
    program.step();
  }
