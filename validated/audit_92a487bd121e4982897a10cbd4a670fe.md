### Title
Attacker-controlled `action.gas()` can cause `WalletContract` callbacks to abort, permanently stuck `has_in_flight_tx = true` and freezing the account forever - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract`'s single-in-flight-transaction guard (`has_in_flight_tx`) is only cleared inside `#[private]` callback methods (`rlp_execute_callback`, `nep_141_storage_balance_callback`, `address_check_callback`). If a callback execution itself aborts (panics/fails, e.g. from a `FunctionCallError` such as insufficient gas while scheduling its own chained promise actions), NEAR's execution model discards *all* state writes made during that failed receipt — including the `self.has_in_flight_tx = false` write that already executed at the top of the function. Because callbacks are guaranteed to run exactly once and are never retried, this leaves `has_in_flight_tx` permanently `true`, and every subsequent `rlp_execute` call immediately short-circuits with "transaction already in progress" without ever creating a new promise chain that could reset the flag. This mirrors the reported bug class: a downstream/external call path failure (there: RWA `burn` reverting due to pause/blacklist; here: a callback's promise-scheduling reverting due to gas exhaustion) permanently traps the contract in an unrecoverable state, freezing the funds/functionality gated behind that flag.

### Finding Description
- `rlp_execute` refuses to start a new transaction whenever `has_in_flight_tx` is `true`, and this flag is only ever reset to `false` inside the private callbacks: [1](#0-0) 
- The invariant comment states the flag must be `true` when a promise is returned and `false` otherwise — but this invariant depends on the callback's own execution *always* completing successfully: [2](#0-1) 
- `nep_141_storage_balance_callback` sets `has_in_flight_tx = false` first, then — for an unregistered receiver — schedules two chained function calls (`storage_deposit` then the transfer) using gas amounts partly derived from the attacker/user-supplied `action.gas()` from the original RLP-decoded Ethereum transaction, followed by `.then(ext.rlp_execute_callback(...))`: [3](#0-2) 
- The static gas reserved for this same callback receipt is computed as `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`, i.e. it depends on the attacker-controlled `action.gas()` field embedded in the signed transaction: [4](#0-3) 
- If the actual gas consumed inside the callback (parsing, promise creation, batch actions) exceeds what was reserved/remaining — which can be engineered by a relayer/signer crafting a transaction with a gas value that is just barely sufficient for the "happy path" but insufficient once the `storage_deposit` + transfer + `.then()` chain is scheduled — the callback function call fails with a gas-related `FunctionCallError`, and the entire receipt execution (including the already-executed `self.has_in_flight_tx = false` write and the nonce increment) is discarded per NEAR's per-receipt state-commit semantics.
- Because callback receipts are never retried and there is no other public entry point that resets `has_in_flight_tx`, the flag stays permanently `true`. All future `rlp_execute` calls immediately return the "transaction already in progress" error without spending gas or creating any promise, so nothing can ever flip the flag back — the account is permanently locked out of being able to relay any further Ethereum-emulated transaction through this wallet, exactly analogous to the reported "cannot redeem, cannot liquidate" deadlock in `PawnShop`.

### Impact Explanation
Any account using this eth-wallet-contract can be rendered permanently unable to execute further transactions if a single transaction (whether crafted by a malicious relayer, or even an honestly-signed transaction with a marginal gas value racing against an unregistered NEP-141 receiver) trips this gas-exhaustion path inside the callback. Since `rlp_execute` is the sole entry point for moving funds/performing actions through the eth-implicit account, this is a permanent freeze of user funds/functionality controlled by that account — matching the "permanently frozen funds" / "transaction-triggered halt of a specific account's usability" impact category. This does not require any privileged role; it is directly reachable by any transaction signer/relayer submitting a single crafted RLP transaction to `rlp_execute`.

### Likelihood Explanation
This requires the attacker (or an honest submitter under adversarial gas-estimation conditions) to construct an ERC-20-style emulated transfer to an unregistered receiver with an `action.gas()` value engineered so the reserved callback gas budget is exhausted precisely while chaining the `storage_deposit` → transfer → `rlp_execute_callback` promises. This is plausible but requires understanding of NEAR's gas-accounting internals and the specific constants (`NEP_141_STORAGE_DEPOSIT_GAS`, `RLP_EXECUTE_CALLBACK_GAS`) to construct a gas value that passes initial validation yet still causes the later chained-promise scheduling to fail. It is a single-transaction, no-privilege attack, but precision gas-crafting lowers the likelihood relative to a trivially reachable bug; it should be validated by a background engineer with the ability to run gas-accounting simulations against `runtime/near-vm-runner` to confirm exact panic conditions and whether the "invariant" documented in the code is actually protected elsewhere (e.g., a minimum-gas floor check I did not find evidence of in the reviewed code).

### Recommendation
- Reset `has_in_flight_tx` to `false` as part of a resolution that is guaranteed to succeed regardless of the outcome of chained promise scheduling — e.g., perform the flag write in a top-level receipt that cannot itself fail due to insufficient gas for *subsequent* actions (split "is this callback going to attempt more promises" from "commit the reset").
- Enforce a strict, validated minimum gas requirement up front in `inner_rlp_execute`/`nep_141_storage_balance_callback` before committing to the multi-hop promise chain, rejecting the transaction early (before any state mutation) if the attached/prepaid gas is insufficient to cover the worst-case (`storage_deposit` + transfer + final callback) rather than discovering the shortfall mid-execution.
- Consider adding a fallback/deadman-switch mechanism (e.g., a permissionless `force_clear_in_flight` callable only after a timeout with no promise resolution) so a stuck flag cannot brick the wallet forever, mirroring the report's recommendation to "allow redemption until liquidation occurs" instead of leaving state unrecoverable.

### Proof of Concept
1. Attacker (as the eth-wallet's owner, or a relayer with access key) submits an RLP-encoded emulated ERC-20 `transfer` transaction via `rlp_execute`, targeting a real NEP-141 token and a `receiver_id` that is not registered for storage (so the `None` branch of `nep_141_storage_balance_callback` is taken). [4](#0-3) 
2. The `action.gas()` value embedded in the transaction is set to a value that is enough to pass any early sanity checks but leaves insufficient remaining prepaid gas once `NEP_141_STORAGE_DEPOSIT_GAS`, the transfer's own gas, and `RLP_EXECUTE_CALLBACK_GAS` are all scheduled inside `nep_141_storage_balance_callback`. [5](#0-4) 
3. `storage_balance_of` resolves successfully with `None`, entering the branch that schedules `storage_deposit` → transfer → `.then(rlp_execute_callback)`; the underlying gas-accounting causes the callback's own execution to abort with a gas-related `FunctionCallError` before it returns normally.
4. Per NEAR's execution model, all state writes made during this failed receipt (including the earlier `self.has_in_flight_tx = false`) are discarded; the flag remains persisted as `true` from the initial `rlp_execute` call. [6](#0-5) 
5. Any subsequent call to `rlp_execute` immediately returns `"Error: transaction already in progress, please try again later."` and never creates a new promise, so `has_in_flight_tx` can never be reset — the account is permanently unable to transact through this wallet contract. [7](#0-6) 

Note: I was not able to fully verify from the indexed code whether the NEAR runtime enforces some additional gas-preflight check (e.g., in `runtime/runtime/src/actions.rs` or `runtime/near-vm-runner`) that would reject a transaction outright before allowing this specific mid-callback exhaustion scenario, since search results for state-rollback-on-panic mechanics in `runtime/runtime/src/lib.rs` were inconclusive within available context. A background engineer with full repo access should confirm the exact gas-accounting/state-commit behavior for a receipt that panics partway through scheduling chained `promise_batch_action_function_call`s, and should also check whether `WalletContract`'s tests (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`) already cover or gas-fuzz this specific gas-exhaustion path.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
