### Title
Unbounded zk-SNARK proof generation in `ZenTransactionBuilder.build` allows CPU DoS via wallet RPC before actuator size limits apply - (File: framework/src/main/java/org/tron/core/zen/ZenTransactionBuilder.java)

### Summary
`Wallet.createShieldedTransaction`/`createShieldedTransactionWithoutSpendAuthSig` accept a `PrivateParameters`/`PrivateParametersWithoutAsk` request with attacker-controlled `shielded_spends`/`shielded_receives` lists and pass them unbounded into `ZenTransactionBuilder.build`, which loops over every spend and receive calling `librustzcashSaplingSpendProof`/`librustzcashSaplingOutputProof`. The size limits enforced by `ShieldedTransferActuator.checkReceiver`/`checkSender` only run later, when the resulting transaction is actually validated/executed on-chain, meaning the RPC/HTTP transaction-building endpoint itself performs unbounded, uncharged zk-proof computation.

### Finding Description
The RPC/HTTP entry points `RpcApiService.createShieldedTransaction` / `createShieldedTransactionWithoutSpendAuthSig` and `CreateShieldedTransactionServlet`/`CreateShieldedTransactionWithoutSpendAuthSigServlet` call `Wallet.createShieldedTransaction(request)` [1](#0-0)  which only validates presence/non-emptiness of addresses/amounts and calls `checkCmValid`, but never bounds `request.getShieldedSpendsList()`/`getShieldedReceivesList()` size [2](#0-1) . All spends/receives are then fed to `builder.addSpend`/`shieldedOutput` and finally `builder.build()` [3](#0-2) .

Inside `ZenTransactionBuilder.build`, the method iterates unboundedly over `spends` and `receives`, calling `generateSpendProof`/`generateOutputProof` for each element, each of which invokes the expensive native zk-SNARK proof routines `librustzcashSaplingSpendProof`/`librustzcashSaplingOutputProof` [4](#0-3) [5](#0-4) [6](#0-5) . There is no size check anywhere in `ZenTransactionBuilder` or in `Wallet.createShieldedTransaction`/`createShieldedTransactionWithoutSpendAuthSig` limiting the number of spends/receives.

The actuator-level limits (`ShieldedTransferActuator.checkReceiver`/`checkSender`, confirmed present in `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`) only execute during `validate()` of an already-built `ShieldedTransferContract`, i.e., after a transaction has been fully assembled (and possibly broadcast). They do not gate the RPC transaction-construction path at all — `Wallet.createShieldedTransaction` never invokes the actuator's `validate()` before calling `builder.build()`. Thus an attacker can send a single `PrivateParameters` request with, e.g., 1000 `shielded_receives` entries (each requiring a valid but attacker-fabricated `payment_address`/`rcm` — no real funds or valid spend authorization needed for receive notes, since output proofs don't require ownership of funds) and force the node to perform up to 1000 Groth16 proof generations synchronously in the RPC-handling thread, before any fee, energy, or bandwidth is charged (this is a pre-broadcast, pre-signature RPC helper, not a consensus-charged operation).

The only mitigation in place is the generic HTTP `RateLimiterServlet`, which enforces per-IP/global QPS limits [7](#0-6)  — this limits request *frequency*, not request *size/cost*, so a single permitted request can still trigger unbounded CPU work. The gRPC endpoint (`RpcApiService.createShieldedTransaction`) has no equivalent per-request rate limiting shown in the reviewed code, and no request-size cap on the number of spends/receives.

### Impact Explanation
This is a DoS via RPC-API: a single unprivileged, unauthenticated request to `CreateShieldedTransaction`/`CreateShieldedTransactionWithoutSpendAuthSig` (gRPC or HTTP) can consume disproportionate CPU/memory on the node performing zk-SNARK proof generation, with no fee, energy, or bandwidth charged at that stage (since this is a request-response API for building — not broadcasting — a transaction). Repeated requests (each within QPS limits) can degrade node responsiveness or exhaust CPU resources, matching the "DoS via RPC-API" bounty class. This does not lead to consensus divergence, fund theft, or key leakage — it is limited to node-local resource exhaustion for the API-serving node.

### Likelihood Explanation
- Preconditions: the node must have `allowShieldedTransactionApi` enabled (checked via `checkAllowShieldedTransactionApi()`), which is required for any shielded RPC feature and is common on nodes that support shielded transactions.
- Attacker cost: essentially free — no valid spend authorization or real funds are required to submit crafted `shielded_receives`/`shielded_spends` entries; only well-formed byte arrays needed to reach the proof-generation calls before they fail (or which may succeed and simply cost CPU regardless of ultimate zk-validity, since `librustzcashSaplingSpendProof`/`OutputProof` are the expensive step itself).
- Feasibility: no privileged access, no fee, no on-chain transaction needed — an anonymous RPC/HTTP client can send this at will, repeatably.

### Recommendation
Enforce spend/receive count limits in `Wallet.createShieldedTransaction`/`createShieldedTransactionWithoutSpendAuthSig` (mirroring `ShieldedTransferActuator.checkSender`/`checkReceiver` limits) before any proof generation is attempted in `ZenTransactionBuilder.build`, and/or add an explicit size guard at the top of `ZenTransactionBuilder.build` itself so the check cannot be bypassed by any future caller. Additionally, consider adding request-size-aware rate limiting (e.g., counting spends/receives against a request cost budget) for the shielded transaction RPC/HTTP endpoints.

  public SpendDescriptionCapsule generateSpendProof(SpendDescriptionInfo spend,
      long ctx) throws ZksnarkException {

    byte[] cm = spend.note.cm();

    // check if ak exists
    byte[] ak;
    byte[] nf;
    byte[] nsk;
    if (!ArrayUtils.isEmpty(spend.ak)) {
      ak = spend.ak;
      nf = spend.note.nullifier(ak, JLibrustzcash.librustzcashNskToNk(spend.nsk),
          spend.voucher.position());
      nsk = spend.nsk;
    } else {
      ak = spend.expsk.fullViewingKey().getAk();
      nf = spend.note.nullifier(spend.expsk.fullViewingKey(), spend.voucher.position());
      nsk = spend.expsk.getNsk();
    }

    if (ByteArray.isEmpty(cm) || ByteArray.isEmpty(nf)) {
      throw new ZksnarkException("Spend is invalid");
    }

    byte[] voucherPath = spend.voucher.path().encode();

    byte[] cv = new byte[32];
    byte[] rk = new byte[32];
    byte[] zkproof = new byte[192];
    if (!JLibrustzcash.librustzcashSaplingSpendProof(
        new SpendProofParams(ctx,
            ak,
            nsk,
            spend.note.getD().getData(),
            spend.note.getRcm(),
            spend.alpha,
            spend.note.getValue(),
            spend.anchor,
            voucherPath,
            cv,
            rk,
            zkproof))) {
      throw new ZksnarkException("Spend proof failed");
    }
    SpendDescriptionCapsule spendDescriptionCapsule = new SpendDescriptionCapsule();
    spendDescriptionCapsule.setValueCommitment(cv);
    spendDescriptionCapsule.setRk(rk);
    spendDescriptionCapsule.setZkproof(zkproof);
    spendDescriptionCapsule.setAnchor(spend.anchor);
    spendDescriptionCapsule.setNullifier(nf);
    return spendDescriptionCapsule;
  }

  public ReceiveDescriptionCapsule generateOutputProof(ReceiveDescriptionInfo output, long ctx)
      throws ZksnarkException {
    byte[] cm = output.getNote().cm();
    if (ByteArray.isEmpty(cm)) {
      throw new ZksnarkException("Output is invalid");
    }

    Optional<NotePlaintextEncryptionResult> res = output.getNote()
        .encrypt(output.getNote().getPkD());
    if (!res.isPresent()) {
      throw new ZksnarkException("Failed to encrypt note");
    }

    NotePlaintextEncryptionResult enc = res.get();
    NoteEncryption encryptor = enc.getNoteEncryption();

    byte[] cv = new byte[32];
    byte[] zkProof = new byte[192];
    if (!JLibrustzcash.librustzcashSaplingOutputProof(
        new OutputProofParams(ctx,
            encryptor.getEsk(),
            output.getNote().getD().getData(),
            output.getNote().getPkD(),
            output.getNote().getRcm(),
            output.getNote().getValue(),
            cv,
            zkProof))) {
      throw new ZksnarkException("Output proof failed");
    }

    if (ArrayUtils.isEmpty(output.ovk) || output.ovk.length != 32) {
      throw new ZksnarkException("ovk is null or invalid and ovk should be 32 bytes (256 bit)");
    }

    ReceiveDescriptionCapsule receiveDescriptionCapsule = new ReceiveDescriptionCapsule();
    receiveDescriptionCapsule.setValueCommitment(cv);
    receiveDescriptionCapsule.setNoteCommitment(cm);
    receiveDescriptionCapsule.setEpk(encryptor.getEpk());
    receiveDescriptionCapsule.setCEnc(enc.getEncCiphertext());
    receiveDescriptionCapsule.setZkproof(zkProof);

    OutgoingPlaintext outPlaintext =
        new OutgoingPlaintext(output.getNote().getPkD(), encryptor.getEsk());
    receiveDescriptionCapsule.setCOut(outPlaintext
        .encrypt(output.ovk, receiveDescriptionCapsule.getValueCommitment().toByteArray(),
            receiveDescriptionCapsule.getCm().toByteArray(),
            encryptor).getData());
    return receiveDescriptionCapsule;
  }
