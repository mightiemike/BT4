### Title
Deleting the Last Full-Access Key While Stake Is Locked Permanently Freezes Funds — ([File: runtime/runtime/src/access_keys.rs])

### Summary
The reported bug class is that a contract lets a privileged party voluntarily give up the only credential able to perform safety-critical administrative actions (`renounceOwnership()`), silently bricking functions like pausing. The nearcore analog is `DeleteKeyAction`/`action_delete_key`, which lets an account holder delete its own last `FullAccess` key with no check on locked/staked balance — unlike `DeleteAccountAction`, which explicitly guards against exactly this scenario.

### Finding Description
`action_delete_key` in `runtime/runtime/src/access_keys.rs` simply looks up the key and removes it (`delete_regular_key`/`delete_gas_key`), with no check on the account's `locked` (staked) or `amount` balance before removal. [1](#0-0) 

By contrast, `action_delete_account` in `runtime/runtime/src/actions.rs` — the sibling action that also permanently forfeits control of an account — explicitly forbids deletion while the account has locked/staked balance, returning `DeleteAccountStaking`: [2](#0-1) 

`FullAccess` is required to run the native `Stake` action (to unstake, by calling `Stake` with amount 0) or a plain `Transfer`; a `FunctionCall` permission key cannot sign either. [3](#0-2) 

Unstaking itself only proceeds if the account still has a locked stake and the caller can sign a `StakeAction`: [4](#0-3) 

If an account owner deletes their last `FullAccess` key (`test_delete_key_last` exercises exactly this transition) while `locked > 0` or `amount > 0`, the account becomes fully key-less. Documentation explicitly acknowledges an account can end up with zero access keys and thereby "no owner who can run transactions from its behalf": [5](#0-4) [6](#0-5) 

At that point there is no way to ever sign a `Stake(0)` unstake action or a `Transfer` action from that account — the locked and/or liquid balance is permanently unreachable, with no protocol-level "seal"/guard analogous to `DeleteAccountStaking`.

### Impact Explanation
This mirrors the report's core theme: a previously-accepted, user-initiated action (deleting/renouncing the sole controlling credential) silently removes the only path to a critical follow-up action (unstake/withdraw), permanently freezing funds. `action_delete_account` recognizes this exact risk for the staking case and blocks it (`DeleteAccountStaking`), but `action_delete_key` — which produces an equally unrecoverable state for the account's own controlled funds — has no equivalent safeguard. This falls under "permanently frozen funds," one of the accepted impact categories.

### Likelihood Explanation
Reachable with a single signed `DeleteKey` transaction from the account itself (the unprivileged transaction signer for their own account), no special privileges or network conditions required. It can occur accidentally (rotating/misconfiguring keys while staked) or as a side effect of tooling/automation that isn't staking-aware, exactly the kind of "previously valid pattern becomes dangerous" scenario the report describes.

### Recommendation
Add a check in `action_delete_key` (mirroring `action_delete_account`'s `DeleteAccountStaking` check) that rejects deletion of the last remaining `FullAccess` key when `account.locked() > 0` (and optionally when `account.amount() > 0`), forcing the account to unstake/withdraw or retain at least one `FullAccess` key before it can become key-less.

### Proof of Concept
1. Create/fund an account and stake with its only `FullAccess` key (`StakeAction { stake > 0 }`), so `account.locked > 0`.
2. Submit `DeleteKeyAction` for that same key (see `test_delete_key_last` at [6](#0-5)  for the mechanics of removing the last key).
3. The account now has zero access keys while `locked` (and/or `amount`) remains non-zero.
4. No future transaction can ever be signed as this account (no `FullAccess` key exists to sign `Stake(0)` or `Transfer`), so the staked/liquid balance is permanently unreachable — contrast with attempting `DeleteAccountAction` on a staked account, which is explicitly rejected with `DeleteAccountStaking`.

pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {
        if let Some(gas_key_info) = access_key.gas_key_info() {
            delete_gas_key(
                config,
                state_update,
                account,
                result,
                account_id,
                &delete_key.public_key,
                &access_key,
                gas_key_info,
            )?;
        } else {
            delete_regular_key(
                &config.fees,
                state_update,
                account,
                account_id,
                &delete_key.public_key,
                &access_key,
            );
        }
    } else {
        result.result = Err(ActionErrorKind::DeleteKeyDoesNotExist {
            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),
        }
        .into());
    }
    Ok(())
}

pub(crate) fn action_stake(
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    stake: &StakeAction,
    last_block_hash: &CryptoHash,
    epoch_info_provider: &dyn EpochInfoProvider,
) -> Result<(), RuntimeError> {
    let increment = stake.stake.saturating_sub(account.locked());

    if let Some(new_balance) = account.amount().checked_sub(increment) {
        if account.locked().is_zero() && stake.stake.is_zero() {
            // if the account hasn't staked, it cannot unstake
            result.result =
                Err(ActionErrorKind::TriesToUnstake { account_id: account_id.clone() }.into());
            return Ok(());
        }

        if stake.stake > Balance::ZERO {
            let minimum_stake = epoch_info_provider.minimum_stake(last_block_hash)?;
            if stake.stake < minimum_stake {
                result.result = Err(ActionErrorKind::InsufficientStake {
                    account_id: account_id.clone(),
                    stake: stake.stake,
                    minimum_stake,
                }
                .into());
                return Ok(());
            }
        }

        result.validator_proposals.push(ValidatorStake::new(
            account_id.clone(),
            stake.public_key.clone(),
            stake.stake,
        ));
        if stake.stake > account.locked() {
            // We've checked above `account.amount >= increment`
            account.set_amount(new_balance);
            account.set_locked(stake.stake).or_inconsistent_state(account_id)?;

pub fn test_delete_key_last(node: impl Node) {
    let account_id = &node.account_id().unwrap();
    let node_user = node.user();
    let root = node_user.get_state_root();

    assert!(node_user.get_access_key(account_id, &node.signer().public_key()).is_ok());
    let transaction_result = node_user.delete_key(account_id.clone(), node.signer().public_key());

    match transaction_result {
        Ok(transaction_result) => {
            assert_eq!(transaction_result.status, FinalExecutionStatus::SuccessValue(Vec::new()));
            assert_eq!(transaction_result.receipts_outcome.len(), 1 + extra_refund_outcomes());
        }
        Err(err) => {
            // TODO(#6724): This is a wrong error, the transaction actually
            // succeeds. We get an error here when we retry the tx and the second
            // time around it fails. Normally, retries are handled by nonces, but we
            // forget the nonce when we delete a key!
            assert_eq!(
                err,
                CommitError::Server(ServerError::TxExecutionError(
                    TxExecutionError::InvalidTxError(InvalidTxError::InvalidAccessKeyError(
                        InvalidAccessKeyError::AccessKeyNotFound {
                            account_id: account_id.clone(),
                            public_key: node.signer().public_key().into(),
                        },
                    ))
                ))
            )
        }
    }

    let new_root = node_user.get_state_root();
    assert_ne!(new_root, root);

    assert!(node_user.get_access_key(account_id, &node.signer().public_key()).is_err());
}
