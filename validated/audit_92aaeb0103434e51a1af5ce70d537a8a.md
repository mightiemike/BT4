### Title
Unchecked TRC10 exchange balance subtraction can drive AMM pool reserves negative when hardened-math is not enabled - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes the "amount to receive" (`buyTokenQuant`) from a floating-point bancor-style formula and then updates the pool's stored reserves by simple `+`/`-` arithmetic when `hardenedCalc` is `false` (the default path unless the `AllowHardenExchangeCalculation` proposal is enabled). Just like the PoolTogether `captureAwardBalance` bug where a computed `totalInterest` could exceed the actual accumulated balance and underflow the subtraction, here a computed `buyTokenQuant`/`anotherTokenQuant` derived from `double` math can exceed the actual pool reserve, and the non-hardened path performs the subtraction without any check that the result stays non-negative.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  selects a `Processor` based on `hardenedCalc`. When `hardenedCalc` is `false`, it uses `ExchangeProcessor`, which computes the exchanged amount using `double`-precision Bancor-formula math and casts the double result to `long` via `(long) exchangeBalance` [2](#0-1) . The resulting `buyTokenQuant` is then subtracted from the pool's stored reserve using plain, non-checked arithmetic:

```
newSecondTokenBalance = hardenedCalc
    ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
    : secondTokenBalance - buyTokenQuant;
``` [3](#0-2) 

Critically, the negative-balance guard is only applied when `hardenedCalc` is true:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [4](#0-3) 

`hardenedCalc` is controlled by `allowHarden()`, which reads the `AllowHardenExchangeCalculation` dynamic property/proposal [5](#0-4) . Unless that proposal has been activated on the network, every `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` call to `exchangeCapsule.transaction(...)` runs the unguarded, floating-point path. `ExchangeTransactionActuator.doValidate()` calls `exchangeCapsule.transaction(...)` during validation purely to compute `anotherTokenQuant` for the "expected" check [6](#0-5) , but this mutates `exchangeCapsule`'s in-memory state; `execute()` then re-invokes `transaction(...)` again and persists the resulting (potentially negative) `secondTokenBalance`/`firstTokenBalance` via `Commons.putExchangeCapsule` [7](#0-6) . No check anywhere in `ExchangeTransactionActuator`/`ExchangeInjectActuator` verifies that `anotherTokenQuant <= currentBuyTokenBalance` before persisting (unlike `ExchangeWithdrawActuator`, which does check `firstTokenBalance < tokenQuant` for withdrawals) [8](#0-7) .

This is directly analogous to the referenced report: a value computed by an approximate/rounding-prone calculation (`totalInterest` from `balanceOfUnderlying` vs. `buyTokenQuant` from double-precision `pow`) is subtracted from an accumulated on-chain balance (`_currentAwardBalance` vs. `secondTokenBalance`) without verifying the subtrahend does not exceed the minuend, in a code path (`hardenedCalc == false`) that is still reachable by any user broadcasting an `ExchangeTransactionContract`/`ExchangeInjectContract`.

### Impact Explanation
If the double-precision Bancor calculation ever overestimates `buyTokenQuant` relative to the true integer-exact reserve (e.g., due to floating-point rounding near reserve extremes, very large `supply`/`quant` ratios, or repeated small trades accumulating rounding drift), `secondTokenBalance - buyTokenQuant` (or `firstTokenBalance - buyTokenQuant` in the reverse direction) can go negative and get persisted to the `ExchangeStore`/`ExchangeV2Store`. A negative reserve corrupts the AMM's accounting: subsequent trades against that exchange would compute nonsensical exchange rates (division by/near a negative or zero balance), potentially allowing further extraction of tokens beyond what was ever deposited, or causing the exchange to become permanently unusable/stalled — an asset/accounting corruption and DoS analogous to the report's underflow/stall.

### Likelihood Explanation
This is only exploitable while `AllowHardenExchangeCalculation` is not active for the given chain (this is a governance proposal, so mainnet may or may not have it enabled at any point; the "harden" mitigation strongly suggests the maintainers themselves recognized the non-hardened math was unsafe). Because `ExchangeProcessor` relies on IEEE-754 `double` arithmetic for `Math.pow` with fractional exponents (0.0005 and 2000.0) and casts to `long` by truncation, precision loss is a normal, expected occurrence rather than a rare edge case, making the underflow condition realistically reachable by ordinary users performing `ExchangeTransactionContract`/`ExchangeInjectContract` calls without needing any privileged access.

### Recommendation
Apply the same `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard unconditionally (not only when `hardenedCalc` is true) in `ExchangeCapsule.transaction()`, or use `subtractExact`/checked arithmetic for both paths and reject the transaction (throw `ContractValidateException`) if the computed exchanged quantity would exceed the current reserve, mirroring the `captureAwardBalance` fix of validating the computed value against the accumulated balance before subtracting.

### Proof of Concept
Conceptual PoC (cannot be fully executed without live node/test harness, but the code path is deterministic):
1. Create an exchange pair via `ExchangeCreateContract` with reserves chosen to maximize floating point rounding error in `Maths.pow(1 + quant/newBalance, 0.0005)` and `Maths.pow(1 + supplyQuant/supply, 2000.0)` (e.g., extreme balance ratios or very large `sellTokenQuant` near `Long.MAX_VALUE` bounds allowed by `getExchangeBalanceLimit()`).
2. Do not activate the `AllowHardenExchangeCalculation` proposal (default state), so `allowHarden()` returns `false` and `ExchangeCapsule.transaction()` uses `ExchangeProcessor` with plain `-`/`+` arithmetic and no negativity check [9](#0-8) .
3. Broadcast an `ExchangeTransactionContract` (via `ExchangeTransactionActuator`) with a `sellTokenQuant` engineered so the double-precision-computed `buyTokenQuant` exceeds the actual `secondTokenBalance`.
4. Observe that `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` is negative, is persisted via `Commons.putExchangeCapsule`, and no `ContractValidateException`/`ContractExeException` is thrown, corrupting the exchange's on-chain reserve state for future trades.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
