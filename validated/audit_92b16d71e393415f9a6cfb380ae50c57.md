### Title
Unbounded integer overflow of exchange pool balances on the non-hardened (`hardenedCalc=false`) trade path allows corrupted, unbacked pool state to be persisted - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes `newFirstTokenBalance`/`newSecondTokenBalance` using plain `long` addition/subtraction (`firstTokenBalance + sellTokenQuant`, etc.) whenever `hardenedCalc == false`, and the underlying `ExchangeProcessor.exchangeToSupply` also does unchecked `balance + quant` regardless of mode. The only sanity check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is gated behind `if (hardenedCalc && ...)`, so on the non-hardened path an overflow silently wraps to a negative balance and is written back into the `Exchange` protobuf without any exception, then persisted via `Commons.putExchangeCapsule` in `ExchangeTransactionActuator.execute`.

### Finding Description
`ExchangeCapsule.transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath, boolean hardenedCalc)`: [1](#0-0) 
shows that when `hardenedCalc` is `false` (the legacy/default path, selected in `ExchangeTransactionActuator.execute`/`doValidate` via `allowHarden()`), `newFirstTokenBalance`/`newSecondTokenBalance` are computed with raw `+`/`-` and the negative-balance guard is skipped entirely (`if (hardenedCalc && ...)`).

The `ExchangeProcessor` used on that same non-hardened path also performs unchecked arithmetic: [2](#0-1) 

`allowHarden()` is driven by the dynamic property `ALLOW_HARDEN_EXCHANGE_CALCULATION`: [3](#0-2) 
This is a committee-controlled proposal switch, not attacker-controlled, but it is off by default, meaning the vulnerable legacy code path is the one actually exercised unless/until governance activates hardening.

Compounding this, the only other guard against an oversized `tokenQuant` — the `balanceLimit` check in `ExchangeTransactionActuator.doValidate` — reuses the same non-hardened-aware helper: [4](#0-3) 
`addExact` here is `AbstractExchangeActuator.addExact`, which itself only performs a checked add when `allowHarden()` is true; otherwise it falls back to plain `x + y`: [5](#0-4) 
So in the default/non-hardened configuration, a sufficiently large `tokenQuant` can wrap `tokenBalance` to a negative value, which will never satisfy `tokenBalance > balanceLimit`, silently defeating the intended pre-trade sanity check as well.

Once `exchangeCapsule.transaction(...)` returns without throwing, `ExchangeTransactionActuator.execute` persists the (now potentially corrupted) capsule unconditionally: [6](#0-5) 

The reachable attacker entrypoint is a standard, unprivileged `ExchangeTransactionContract` broadcast by any account, with `quant` fully attacker-controlled. The practical constraint is that the attacker must actually own (or have issued) enough of `sellTokenID` to pass the pre-check `accountCapsule.getBalance()`/`assetBalanceEnoughV2` checks in `doValidate` (lines 207–215) — for TRX this is bounded well below `Long.MAX_VALUE`, but for a self-issued TRC10 asset an unprivileged user fully controls the `total_supply` field of `AssetIssueContract` and receives the full issued supply, making near-`Long.MAX_VALUE` quantities achievable for a token the attacker created themselves and later paired into an exchange (via `ExchangeCreateActuator`/`ExchangeInjectActuator`, both of which are also unprivileged actions). I was not able to verify within this session whether `AssetIssueActuator` imposes an independent numeric cap on `total_supply` well below `Long.MAX_VALUE`; this is the main remaining uncertainty for full end-to-end feasibility, though it does not affect the validity of the arithmetic-safety defect itself.

### Impact Explanation
If a wraparound occurs, `firstTokenBalance`/`secondTokenBalance` in the persisted `Exchange` proto becomes negative or otherwise decoupled from real backing assets moved into/out of user accounts (which are updated via separate, unchecked non-hardened arithmetic in `ExchangeTransactionActuator.execute`, lines 77–91). This permanently desynchronizes the exchange's internal accounting from actual token custody, and subsequent trades computed against the corrupted pool (via `ExchangeProcessor.exchange`) can yield economically incorrect `buyTokenQuant` values, enabling extraction of more of the paired asset than the pool is actually backed by.

### Likelihood Explanation
Exploitability depends on (a) the chain running with `ALLOW_HARDEN_EXCHANGE_CALCULATION = 0` (the apparent default, not attacker-controlled but also not requiring any privileged action to remain in that state), and (b) the attacker being able to acquire/issue a `sellTokenQuant` large enough, relative to the pool's existing balance, to overflow a signed 64-bit sum. TRC10 asset issuance is fully unprivileged and issuer-controlled for `total_supply`, which is the most plausible avenue, though the exact numeric ceiling enforced by `AssetIssueActuator` was not confirmed in this session.

### Recommendation
Remove the `hardenedCalc &&` conditional so the negative-balance guard in `ExchangeCapsule.transaction` runs unconditionally (or always use `StrictMathWrapper`/checked arithmetic for `newFirstTokenBalance`/`newSecondTokenBalance` and in `ExchangeProcessor.exchangeToSupply`), and make `AbstractExchangeActuator.addExact`/`subtractExact` always perform checked arithmetic in the `balanceLimit` validation regardless of `allowHarden()`, so the pre-trade sanity check cannot be bypassed via overflow in the default configuration.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/capsule/ExchangeCapsuleTest.java
@Test
public void testNonHardenedOverflowProducesNegativeBalance() throws Exception {
  ExchangeCapsule capsule = new ExchangeCapsule(
      ByteString.copyFromUtf8("owner"), 200L, 0L,
      "abc".getBytes(), "def".getBytes());
  // Small existing pool balance
  capsule.setBalance(1_000_000L, 1_000_000L);

  // Adversarial quant chosen so firstTokenBalance + sellTokenQuant overflows long
  long adversarialQuant = Long.MAX_VALUE - 500_000L;

  // Non-hardened path (hardenedCalc = false): no exception is thrown,
  // and the resulting balance wraps to negative.
  long buyQuant = capsule.transaction("abc".getBytes(), adversarialQuant, true, false);

  Assert.assertTrue("EXPECTED FAILURE: pool balance should never go negative, "
      + "but non-hardened path allows overflow",
      capsule.getFirstTokenBalance() >= 0);
}
```
Expected (buggy) result: the assertion fails because `newFirstTokenBalance` wraps to a negative value with no exception thrown, demonstrating that the non-hardened path in `ExchangeCapsule.transaction` (and the underlying `ExchangeProcessor.exchangeToSupply`) lacks overflow protection, in contrast to the hardened path which correctly throws `ContractValidateException`/`ArithmeticException` (as shown by the existing tests `testHardenedTransactionNegativeBalanceThrows` and `hardenedExecuteOverflowThrowsArithmeticException`).
