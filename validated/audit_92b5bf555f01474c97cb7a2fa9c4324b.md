### Title
Reward Snapshot Manipulation via Freeze-Vote-Unfreeze Timing Around Maintenance Cycle Boundary - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
The bEth report's root cause is that a reward accumulator (`global_index`) is updated using an instantaneous balance snapshot with no protection against a user momentarily inflating their share of that balance right before the update, then withdrawing immediately after. Java-tron's DPoS witness/voter reward system has a structurally similar pattern: vote weight used for a cycle's reward split is a point-in-time snapshot taken at the maintenance boundary, and both the acquisition of vote weight (`FreezeBalanceV2Contract` → grants TRON Power instantly) and its removal (`UnfreezeBalanceV2Contract` → `updateVote()`) take effect immediately, decoupled from the multi-day capital lock-up that only applies to withdrawing the underlying TRX principal.

### Finding Description
In `MaintenanceManager.doMaintenance()`, at each cycle boundary the following sequence executes:
1. `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` computes the cycle's Vi (analogous to the bEth `global_index`) using whatever `witness.getVoteCount()` currently is [1](#0-0) .
2. `countVote(votesStore)` then folds in votes cast up through the very last block before maintenance, updates each `WitnessCapsule.setVoteCount`, and immediately calls `incentiveManager.reward(newWitnessAddressList)`, which pays out `getWitnessStandbyAllowance()` proportionally to that just-updated vote count, all inside the same maintenance transition [2](#0-1) .
3. `IncentiveManager.reward()` distributes `totalPay` strictly proportional to each witness's `getVoteCount()` at that instant, with no consideration of how long that vote weight existed [3](#0-2) .

Critically, vote weight can be acquired and removed with no delay relative to the maintenance boundary: `UnfreezeBalanceV2Actuator.execute()` calls `updateVote()` which deducts the account's vote/TRON-Power immediately, while only the underlying TRX principal is queued behind a multi-day unfreeze delay (`calcUnfreezeExpireTime`) via `addUnfrozenV2List` [4](#0-3) . The long-term voter/SR reward path (`MortgageService.computeReward` / `DelegationStore.accumulateWitnessVi`) similarly uses a discrete per-cycle Vi delta, `reward * DECIMAL_OF_VI_REWARD / voteCount`, based solely on the vote count recorded for that cycle, not on duration held [5](#0-4) .

This mirrors the bEth flaw precisely: the reward-distribution checkpoint reads a mutable weight/balance value without any time-weighting or per-block dampening, so whoever inflates that value right before the checkpoint captures a disproportionate share of the reward pool computed at that checkpoint.

### Impact Explanation
A holder of TRX can freeze a large amount right before a maintenance boundary (vote weight granted instantly), vote for a target/self-owned witness so it is counted in that maintenance's `countVote()`, receive an outsized slice of `payStandbyWitness`'s per-maintenance TRX allowance or an inflated Vi delta for that cycle, and then immediately call `unfreezeBalanceV2` to remove the vote weight going forward — all without holding the position for any meaningful duration relative to normal long-term voters. This dilutes rewards that should accrue to genuine, sustained SR voters and can be repeated by any address at each cycle boundary, corrupting the intended proportional-to-contribution reward accounting. Unlike the bEth report, capital is not instantly recoverable (unfreeze principal is locked for the unfreeze delay), which limits — but does not eliminate — the practicality of the attack for a well-capitalized whale who can tolerate the lock-up while still banking the disproportionate reward for that single cycle.

### Likelihood Explanation
This requires only ordinary, unprivileged broadcast transactions (`FreezeBalanceV2Contract`, `VoteWitnessContract`, `UnfreezeBalanceV2Contract`) timed relative to the publicly known maintenance interval, which is straightforward to predict on-chain. No special privileges, keys, or node access are needed. The main friction is capital requirement (must actually hold/lock large TRX) and the multi-day unfreeze delay before reclaiming principal, which reduces — but does not remove — attacker incentive compared to a true flashloan-style attack.

### Recommendation
- Time-weight or block-weight the vote/reward computation instead of using a single point-in-time vote-count snapshot per cycle (e.g., integrate vote-weight over the cycle rather than sampling it at the maintenance instant).
- Introduce a minimum holding/vesting period before newly frozen or newly voted TRON Power counts toward `countVote()`/Vi accumulation and `payStandbyWitness` distribution for the current cycle (effects should only apply starting the *next* full cycle, consistently, for all reward paths — not just some).
- Cap the marginal influence any single freeze/vote/unfreeze sequence can have on a single maintenance cycle's reward pool.

### Proof of Concept
1. Monitor `getNextMaintenanceTime()` to predict the upcoming maintenance block.
2. In the block(s) immediately preceding maintenance, broadcast `FreezeBalanceV2Contract` for a large TRX amount, then `VoteWitnessContract` directing the resulting TRON Power to a target witness address (potentially self-controlled).
3. Let `doMaintenance()` run: `countVote()` folds in the new votes, `incentiveManager.reward()` pays `payStandbyWitness` allowance proportional to the now-inflated vote count, and/or `accumulateWitnessVi` records an inflated Vi delta for that cycle.
4. Immediately broadcast `UnfreezeBalanceV2Contract`, which calls `updateVote()` to zero out the vote weight going forward (before the next cycle's snapshot), while the TRX principal sits in the unfreeze queue to be reclaimed later via `WithdrawExpireUnfreezeActuator`.
5. The attacker has captured a disproportionate share of that cycle's reward pool relative to the brief instant their vote weight existed, at the expense of genuine long-term voters/SRs, exactly analogous to the bEth `update_global_index()` exploit.

  public void reward(List<ByteString> witnesses) {
    if (consensusDelegate.allowChangeDelegation()) {
      return;
    }
    if (witnesses.size() > WITNESS_STANDBY_LENGTH) {
      witnesses = witnesses.subList(0, WITNESS_STANDBY_LENGTH);
    }
    long voteSum = 0;
    for (ByteString witness : witnesses) {
      voteSum += consensusDelegate.getWitness(witness.toByteArray()).getVoteCount();
    }
    if (voteSum <= 0) {
      return;
    }
    long totalPay = consensusDelegate.getWitnessStandbyAllowance();
    for (ByteString witness : witnesses) {
      byte[] address = witness.toByteArray();
      long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
          / voteSum));
      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);
      consensusDelegate.saveAccount(accountCapsule);
    }
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
