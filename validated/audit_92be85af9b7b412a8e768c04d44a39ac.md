## Analysis Result

### Title
Unbounded growth of `TransactionManager.records` from spam of unconsumed/rejected L1→L2 messages — ([File: crates/apollo_l1_events/src/transaction_manager.rs])

### Summary
`TransactionManager` (the component that tracks every scraped L1→L2 "L1 handler" transaction) stores each transaction in `Records`, an `IndexMap<TransactionHash, TransactionRecord>` with no cap on the number of entries it can hold. [1](#0-0) [2](#0-1) 

### Finding Description
Any L1 message sender can call `sendMessageToL2` on the StarknetCore contract to have `L1HandlerTransaction`s scraped and inserted into `records` via `TransactionManager::add_tx`, which unconditionally creates a new record if none exists — there is no per-account, per-address, or global cap on the number of tracked records. [3](#0-2) 

Records are removed only through two narrow paths: (1) `finalize_cancellation`, triggered by an L1 cancellation event, and (2) `clear_old_tx_from_consumed_queue`, triggered only after the transaction is marked "Consumed" (an event that fires when the message is actually consumed on L1, i.e., successfully processed on L2 and included in a committed block). [4](#0-3) [5](#0-4) 

However, `commit_txs` can also mark a transaction `Rejected` (e.g., when consensus does not include a proposed/validated L1 handler tx in a committed block), and `mark_rejected` only flips `state`/`rejected` fields — it never removes the record from `records`, and no other code path cleans up `Rejected` entries. [6](#0-5) [7](#0-6) 

A transaction that is never included in a block is also never consumed on L1 (consumption is a consequence of L2 execution occurring), so it never enters the `consumed_queue` used for eventual cleanup. Thus, any L1 handler transaction whose target contract/selector is invalid, or whose nonce/order makes it permanently invalid for inclusion, becomes `Rejected` (or stays `Pending` indefinitely if it never clears validation) and its `TransactionRecord` persists in the `IndexMap` forever, unless the original sender happens to also cancel it on L1 (which an attacker has no incentive to do).

Unlike the mempool (`crates/apollo_mempool`), which enforces `capacity_in_bytes` and evicts transactions when full, the `TransactionManager`'s `Records` store has no analogous capacity/size bound in `TransactionManagerConfig`. [8](#0-7) 

### Impact Explanation
Every sequencer node runs an `L1EventsProvider`/`TransactionManager` that ingests all `sendMessageToL2` events for its tracked contracts from L1. Because record insertion is driven purely by L1 log events (no fee, no L2 nonce/account gating, and reachable by anyone willing to pay L1 gas for a cheap `sendMessageToL2` call targeting an invalid selector/contract so it is perpetually rejected/never proposed), an attacker can grow `records` without bound, consuming sequencer memory over time. Since this state is held identically by every node running the L1 events pipeline (not just the proposer), it degrades or eventually crashes multiple/all sequencer nodes, threatening the network's ability to keep processing transactions — a availability/liveness impact consistent with "network unable to confirm new transactions" once nodes run out of memory or GC pressure severely degrades throughput.

### Likelihood Explanation
Likelihood is high: sending L1→L2 messages is a normal, permissionless, low-cost operation (bounded only by L1 gas), and crafting a message that will be rejected/never proposed (e.g., targeting a non-existent contract address or an entry point/selector combination that fails during validation) requires no special access — this is explicitly a reachable "L1 message sender" path per the scope of this review.

### Recommendation
Add a configurable cap on the number of tracked/pending `TransactionManager` records (analogous to Besu's `--rpc-max-active-filters`), rejecting or evicting the oldest/lowest-priority record when the cap is reached, and add an explicit cleanup path for `Rejected` transactions (e.g., a bounded retention window similar to `l1_handler_consumption_timelock_seconds`) so rejected/never-proposed L1 handler transactions are eventually purged from `records` rather than retained indefinitely.

### Proof of Concept
1. Attacker repeatedly calls `sendMessageToL2` on L1 targeting a contract address/selector combination on L2 that always fails validation (e.g., a nonexistent contract, or a valid contract but an invalid `entry_point_selector`).
2. The L1 scraper picks up each event and calls `TransactionManager::add_tx`, inserting a new `TransactionRecord` into `records` for each distinct message/tx hash. [9](#0-8) 

3. Because these transactions repeatedly fail validation, the batcher/consensus never includes them in a committed block; they remain `Pending`, or are marked `Rejected` via `commit_txs`'s `rejected_txs` path if attempted and rejected by consensus.
4. Since they are never consumed on L1 (no L2 execution occurred) and never cancelled, they never populate `consumed_queue`, so `clear_old_tx_from_consumed_queue` never removes them from `records`.
5. Repeating this at scale causes `records` (an `IndexMap`) to grow without bound, since there is no configured capacity limit anywhere in `TransactionManagerConfig`.

    /// Adds a transaction to the transaction manager, return true if the transaction was
    /// successfully added. If the transaction is occupied or already had its hash stored as
    /// committed, it will not be added, and false will be returned.
    // Note: if only the committed hash was known, the transaction will "fill in the blank" in the
    // committed txs storage, to account for commit-before-add tx scenario.
    pub fn add_tx(
        &mut self,
        tx: L1HandlerTransaction,
        block_timestamp: BlockTimestamp,
        scrape_timestamp: UnixTimestamp,
    ) {
        let tx_hash = tx.tx_hash;
        // If exists, return false and do nothing. If not, create the record as a HashOnly payload.
        let is_new_record = self.create_record_if_not_exist(tx_hash);
        // Replace a HashOnly payload with a Full payload. Do not update a Full payload.
        // A hash only payload can come from catching up from state sync, and then updated by
        // add_events from the scraper. However, if we get the same full tx twice (from the scraper)
        // it could indicate a double-scrape, and may cause the tx to be re-added to the proposable
        // index.
        self.with_record(tx_hash, move |record| match &record.tx {
            TransactionPayload::HashOnly(_) => {
                if !is_new_record {
                    info!(
                        "Transaction {tx_hash} already exists as a HashOnly payload. It was \
                         probably gotten via state sync component, and is now updated with a Full \
                         payload."
                    );
                }
                record.tx.set(tx, block_timestamp, scrape_timestamp);
                // Counts the HashOnly -> Full transition, regardless of whether the HashOnly
                // was just created here or pre-existed from state sync.
                L1_MESSAGE_SCRAPER_L1_HANDLER_TX_COUNT.increment(1);
            }
            TransactionPayload::Full { tx: _, created_at_block_timestamp: _, scrape_timestamp } => {
                warn!(
                    "Transaction {tx_hash} already exists as a Full payload, scraped at \
                     {scrape_timestamp}. This could indicate a double scrape. Ignoring the new \
                     transaction."
                );
            }
        });
    }

    pub fn finalize_cancellation(&mut self, tx_hash: TransactionHash) {
        let Some(record) = self.records.get(&tx_hash) else {
            info!(
                "Attempted to finalize cancellation for non-existent transaction: {tx_hash}. This \
                 can happen if the transaction was too old to be scraped (e.g. it was created \
                 before we started scraping)."
            );
            return;
        };

        // Regardless of the state of the tx in the record, if we get the cancellation event from
        // the L1 contract, we delete this tx from the records and from the proposable index, even
        // if it was Pending and ready to be proposed (which is not supposed to happen, hence the
        // warning).
        if record.state != TransactionState::CancellationStartedOnL2 {
            warn!(
                "Attempted to finalize cancellation for transaction {tx_hash} that is not in the \
                 cancellation started on L2 state, but in the {:?} state.",
                record.state
            );
        }
        // This will also call maintain_indices to remove the tx from the proposable index.
        self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());
        self.records.remove(&tx_hash);
    }

    pub fn consume_tx(
        &mut self,
        tx_hash: TransactionHash,
        consumed_at: BlockTimestamp,
        unix_now: u64,
    ) -> Result<(), BlockTimestamp> {
        self.clear_old_tx_from_consumed_queue(unix_now);

        let Some(record) = self.records.get(&tx_hash) else {
            debug!(
                "Attempted to consume an unknown transaction: {tx_hash}. This can happen if the \
                 transaction was too old to be scraped (e.g. it was created before we started \
                 scraping)."
            );
            return Ok(());
        };

        // Double consumption is a bug.
        if let Some(previously_consumed_at) = record.get_consumed_at_timestamp() {
            return Err(previously_consumed_at);
        }

        // Mark the transaction as consumed.
        self.with_record(tx_hash, |record| record.mark_consumed(consumed_at));
        Ok(())
    }

    pub fn clear_old_tx_from_consumed_queue(&mut self, unix_now: u64) {
        let cutoff =
            unix_now.saturating_sub(self.config.l1_handler_consumption_timelock_seconds.as_secs());
        let still_timelocked = self.consumed_queue.split_off(&BlockTimestamp(cutoff));
        let passed_timelock = std::mem::replace(&mut self.consumed_queue, still_timelocked);
        for tx_hashes in passed_timelock.values() {
            for tx_hash in tx_hashes {
                self.records.remove(tx_hash);
            }
        }
    }

#[derive(Clone, Debug, Default, PartialEq, Eq)]
pub struct Records(IndexMap<TransactionHash, TransactionRecord>);

impl Records {
    /// Warning: this is not a safe method to use outside of the transaction managers's
    /// `with_record`.
    pub fn get_mut_unchecked(&mut self, hash: TransactionHash) -> Option<&mut TransactionRecord> {
        self.0.get_mut(&hash)
    }

    pub fn insert(&mut self, hash: TransactionHash, record: TransactionRecord) -> bool {
        match self.0.entry(hash) {
            Entry::Occupied(_) => false,
            Entry::Vacant(entry) => {
                entry.insert(record);
                true
            }
        }
    }

    pub fn remove(&mut self, hash: &TransactionHash) {
        // Insertion order is not required for Records functionality, so we use `swap_remove_entry`
        // for O(1) performance instead of `shift_remove_entry` which is O(n).
        // The only case where the order of records might matter is for snapshot.
        self.0.swap_remove_entry(hash);
    }
}
