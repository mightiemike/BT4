### Title
`ensure_match_transaction_info` skips validating `state_checkpoint_hash` (and hot/position checkpoint hashes), allowing replay/backup verification to silently accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator used by the chunk executor's replay-verification path to confirm that locally re-executed transactions match the `TransactionInfo` recorded in an already-committed/backed-up ledger. It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never checks `state_checkpoint_hash` (the JMT state root committed at checkpoint boundaries), nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` is called from `ChunkExecutorInner::verify_execution`, which drives `--verify-execution-mode` chunk replay (used by db-tool's `replay-on-archive` and the `replay_verify`/`verify` backup-cli coordinators) to confirm that re-executing archived transactions reproduces the ledger data recorded in the backup/db. [2](#0-1) 

Within the comparator, only `status`, `gas_used`, `write_set` hash (against `state_change_hash`), and `event_root_hash` are asserted; there is no `ensure!` comparing a computed state-checkpoint root against `txn_info.state_checkpoint_hash()` (or the hot-state/position analogs). The code contains a TODO acknowledging exactly this gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

Note that the comment frames this only in terms of the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (native-position) feature, but as written the omission also applies to the plain `state_checkpoint_hash` field used by ordinary (non-trading) state checkpoints — the function simply never touches `state_checkpoint_hash()` at all, trading-native or not.

By contrast, the actual state-sync commit path (`ChunkResultVerifier::verify_chunk_result` → `LedgerUpdateOutput::ensure_transaction_infos_match`) is a separate function not affected by this gap — that path verifies transaction infos directly against the recomputed accumulator/ledger state during real commit. The gap is isolated to the offline "verify-execution" / replay-verify tooling that operates against `TransactionInfo`s already recorded in a backup or archive DB. [4](#0-3) 

### Impact Explanation
The whole purpose of `replay-verify`/`replay_on_archive` tooling is to catch state-root divergence bugs (e.g., a subtle non-determinism or logic bug in VM execution, state-checkpoint construction, or a hard fork boundary) by re-executing historical transactions and confirming the recomputed state matches what was actually committed and authenticated by validator signatures. Because `state_checkpoint_hash` is never compared, a real state-root divergence between local re-execution and the authenticated ledger would not cause `verify_execution` to fail — the tool would report a "successful replay" while the ledger's true (validator-signed) state differs from what local execution computes. This directly undermines a proof/commit integrity invariant this task's scope calls out: "Hard-fork-only divergence during commit, replay, restore, or proof verification" going undetected by the dedicated verification tool.

### Likelihood Explanation
This is not attacker-triggered on its own; it is a latent verification gap that would only manifest together with some other (yet-unknown) state-computation bug. The likelihood of the gap itself existing is certain (verified in code) and its practical severity is high because it defeats a safety-net specifically built to catch state-divergence/hard-fork bugs before they cause damage. However, actually exploiting it to cause a real ledger inconsistency still requires a distinct root-cause bug in state-checkpoint/JMT computation — this report is limited to demonstrating that such a bug, if it existed, would not be caught by `verify_execution`, not that a live divergence currently exists.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between a locally computed state-checkpoint hash (main state, and hot-state/position-state when enabled) and `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, at least for checkpoint-boundary transactions, following the same pattern used for `state_change_hash` and `event_root_hash`. This requires passing the checkpoint output (or the state summary at that version) into `verify_execution` so it can be compared, mirroring what `DoStateCheckpoint::run` already computes.

### Proof of Concept
Not applicable as a standalone exploit — this is a verification-gap analysis, not an executable PoC. Concretely, the gap can be demonstrated by observation: `ensure_match_transaction_info` body (types/src/transaction/mod.rs:2139-2204) contains four `ensure!` checks (status, gas_used, write_set_hash, event_root_hash) and zero checks referencing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, while `TransactionInfo` (both V0 and V1) carries these fields as part of its authenticated content [5](#0-4) . Any test harness that forges a `TransactionInfo` with a mismatched `state_checkpoint_hash` but correct `state_change_hash`/`event_root_hash`/`gas_used`/`status` and feeds it through `ChunkExecutorInner::verify_execution` would pass verification undetected.

            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),

            .iter()

            .cloned()

            .collect::<Vec<_>>();

        )?;
        // not `zip_eq`, deliberately
        for (version, txn_out, txn_info, write_set, events) in multizip((

                    error!("(Not quitting right away.) {}", err);
                    verify_execution_mode.mark_seen_error();
                    Ok(version + 1)
                } else {
                    Err(err)
                };
            }
        }
        Ok(end_version)
