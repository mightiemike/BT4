## Finding Confirmed (with a caveat on downstream confirmation)

### Title
Version-5 metadata clearing in `get_metadata_from_compiled_code` is bypassed by `get_metadata`/`get_randomness_annotation_for_entry_function`, letting stale attributes leak into execution - (File: `types/src/vm/module_metadata.rs`)

### Summary
`get_metadata_from_compiled_code` explicitly nulls out `struct_attributes`/`fun_attributes` for modules compiled with `file_format` version `5` (one below `METADATA_V1_MIN_FILE_FORMAT_VERSION = 6`), because such modules "shouldn't have existed" with V1 metadata attached and were meant to be blocked by publish-time validation. [1](#0-0)  However, `get_metadata`, a sibling accessor used elsewhere in the same file for randomness-annotation lookup, takes only `&[Metadata]` and has no notion of the module's `file_format` version at all, so it can never apply this clearing. [2](#0-1) 

### Finding Description
- `CompiledCodeMetadata::version()` is only available through the `CompiledModule`/`CompiledScript` trait impl, which `get_metadata_from_compiled_code` uses to gate the clearing. [3](#0-2) 
- `get_metadata` has no such parameter and is called directly with the raw `&[Metadata]` slice, so any consumer of `get_metadata` sees the attributes exactly as deserialized, without the version==5 suppression. [2](#0-1) 
- `get_randomness_annotation_for_entry_function` is one such consumer: it calls `get_metadata(metadata)` and reads `fun_attributes` directly to decide whether an entry function carries a `Randomness` annotation. [4](#0-3) 
- By contrast, `verify_module_metadata_for_module_publishing` (the intended enforcement point) calls `get_metadata_from_compiled_code`, so a version-5 module's attributes are already cleared before `is_valid_unbiasable_function`/`is_valid_view_function` validation runs — meaning any such legacy module's attributes were never actually validated against those safety constraints. [5](#0-4) 
- The `extract_abort_info`/`extract_abort_info_legacy` methods only read `error_map`, not `struct_attributes`/`fun_attributes`, so they are unaffected by this specific clearing gap; the exploit question's premise about "abort-info... reusing `get_metadata`" does not apply here. [6](#0-5) 

The practical scenario: any legacy version-5 module already on-chain (published before the version-gating fix existed, since publishing new version-5 modules is presumably no longer possible) that carries an unvalidated `Randomness` `fun_attributes` entry on a function that would fail `is_valid_unbiasable_function` (e.g., a public function) would still have that annotation surfaced by `get_randomness_annotation_for_entry_function`, because that path never routes through the version==5 clearing that `get_metadata_from_compiled_code` applies.

### Impact Explanation
Within this file, the impact is limited to `RandomnessAnnotation` computation via `get_randomness_annotation_for_entry_function`; whether this concretely reaches transaction gas metering, randomness API gating, or committed VM output depends on how `aptos-move/aptos-vm/src/aptos_vm.rs` consumes this annotation. I located references to `get_metadata`/`randomness_annotation`/`extract_abort_info` in `aptos_vm.rs` [7](#0-6)  but ran out of tool budget before reading those specific lines to confirm the exact downstream effect on committed transaction output (e.g., whether it changes gas charged, whether it grants access to the per-block randomness seed, or is only used for a diagnostic/logging purpose). This should be verified before treating it as a confirmed committed-state-corruption bug.

### Likelihood Explanation
The precondition — a version-5 module with populated V1 `fun_attributes`/`struct_attributes` already committed to mainnet state — is a historical/legacy condition (the code comment itself states "it shouldn't have existed in the first place ... this should have been gated in the verify module metadata"), implying such modules may already exist from before the gate was added. Since the vulnerability requires already-published legacy bytecode rather than a live unprivileged publish path, exploitability today depends on whether such modules genuinely exist on mainnet and whether their `fun_attributes` are actually consumed for anything security-relevant by the `aptos_vm.rs` call sites, which I was not able to confirm within budget.

### Recommendation
Route `get_randomness_annotation_for_entry_function` (and any other consumer of `get_metadata` that reads `struct_attributes`/`fun_attributes`) through the same version-aware clearing logic as `get_metadata_from_compiled_code`, or centralize the version==5 suppression in a single shared helper that all attribute consumers call, so no code path can observe attributes from a version-5 module that the system considers invalid.

### Proof of Concept
Not fully constructable from static review alone: it requires (1) confirming whether a version-5 module with populated `fun_attributes` actually exists in committed mainnet state (only possible before the gating fix), and (2) tracing the `aptos_vm.rs` call sites of `get_randomness_annotation_for_entry_function`/`get_metadata` to confirm the returned `RandomnessAnnotation` measurably alters gas charged or randomness-API access for a committed transaction. I verified the code-level inconsistency (`get_metadata` vs. `get_metadata_from_compiled_code`) directly in `types/src/vm/module_metadata.rs`, but could not complete the second step confirming committed-state impact due to tool-call budget exhaustion — this should be independently verified (e.g., via a Devin session with terminal/build access) by writing a synthetic version-5 `CompiledModule` with populated V1 metadata and asserting `get_metadata_from_compiled_code` vs. `get_metadata`/`get_randomness_annotation_for_entry_function` return different attribute sets, then tracing whether `aptos_vm.rs` uses the latter's result in a way that affects transaction execution/gas outcome.

pub fn get_metadata_from_compiled_code(
    code: &impl CompiledCodeMetadata,
) -> Option<RuntimeModuleMetadataV1> {
    if let Some(data) = find_metadata(code.metadata(), APTOS_METADATA_KEY_V1) {
        let mut metadata = bcs::from_bytes::<RuntimeModuleMetadataV1>(&data.value).ok();
        // Clear out metadata for v5, since it shouldn't have existed in the first place and isn't
        // being used. Note, this should have been gated in the verify module metadata.
        if code.version() == 5 {
            if let Some(metadata) = metadata.as_mut() {
                metadata.struct_attributes.clear();
                metadata.fun_attributes.clear();
            }
        }
        metadata
    } else if let Some(data) = find_metadata(code.metadata(), APTOS_METADATA_KEY) {
        // Old format available, upgrade to new one on the fly
        let data_v0 = bcs::from_bytes::<RuntimeModuleMetadata>(&data.value).ok()?;
        Some(data_v0.upgrade())
    } else {
        None
    }
}

pub fn verify_module_metadata_for_module_publishing(
    module: &CompiledModule,
    features: &Features,
) -> Result<(), MetaDataValidationError> {
    if features.is_enabled(FeatureFlag::SAFER_METADATA) {
        check_module_complexity(module)?;
    }

    if features.are_resource_groups_enabled() {
        check_metadata_format(module)?;
    }
    let metadata = if let Some(metadata) = get_metadata_from_compiled_code(module) {
        metadata
    } else {
        return Ok(());
    };

    let functions = module
        .function_defs
        .iter()
        .map(|func_def| {
            let func_handle = module.function_handle_at(func_def.function);
            let name = module.identifier_at(func_handle.name);
            (name, (func_handle, func_def))
        })
        .collect::<BTreeMap<_, _>>();

    for (fun, attrs) in &metadata.fun_attributes {
        for attr in attrs {
            if attr.is_view_function() {
                is_valid_view_function(module, &functions, fun)?;
            } else if attr.is_randomness() {
                is_valid_unbiasable_function(&functions, fun)?;
            } else {
                return Err(AttributeValidationError {
                    key: fun.clone(),
                    attribute: attr.kind,
                }
                .into());
            }
        }
    }

    /// Returns the abort info for the given abort code, if any. Tries the full code first, then
    /// falls back to the lower 2 bytes (the reason) if the upper 5 bytes are zero.
    ///
    /// This skips compiler-generated codes such as `UNSPECIFIED_ABORT_CODE`, which have a
    /// non-zero upper 5 bytes and are not associated with any user-defined error.
    pub fn extract_abort_info(&self, code: u64) -> Option<AbortInfo> {
        self.error_map
            .get(&code)
            .or_else(|| {
                // Only extract the reason for canonical std::error codes (upper 5 bytes zero).
                if code >> 24 == 0 {
                    let reason = code & 0xFFFF;
                    self.error_map.get(&reason)
                } else {
                    None
                }
            })
            .map(|descr| AbortInfo {
                reason_name: descr.code_name.clone(),
                description: descr.code_description.clone(),
            })

/// Trait to unify accesses to [CompiledModule] and [CompiledScript] for extracting metadata.
pub trait CompiledCodeMetadata {
    /// Returns the binary version.
    fn version(&self) -> u32;
    /// Returns the [Metadata] stored in this module or script.
    fn metadata(&self) -> &[Metadata];
}

impl CompiledCodeMetadata for CompiledModule {
    fn version(&self) -> u32 {
        self.version
    }

    fn metadata(&self) -> &[Metadata] {
        &self.metadata
    }
}

impl CompiledCodeMetadata for CompiledScript {
    fn version(&self) -> u32 {
        self.version
    }

    fn metadata(&self) -> &[Metadata] {
        &self.metadata
    }
}
