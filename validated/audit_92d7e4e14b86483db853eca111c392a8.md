### Title
Attached deposit permanently locked in `WalletContract` on early Ethereum-transaction parsing failure — ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::rlp_execute` is a `#[payable]` method: any yoctoNEAR an external caller attaches is credited to the wallet contract's balance the moment the call starts, exactly like the `KeeperOracle → KeeperFactory` token transfer in the Sherlock report. The contract is only supposed to hold that deposit transiently while it builds a cross-contract promise that either consumes the deposit (as part of the emitted Near action) or forwards it back to the caller via the tracked `CallerDeposit` refund mechanism. However, several failure paths inside `inner_rlp_execute`/`parse_rlp_tx_to_action` return an `Err` **before** any promise (and therefore before any `CallerDeposit`-based refund) is created. In those paths the attached deposit is neither consumed by an outgoing action nor refunded — it is left sitting in the wallet contract's balance with no method to reclaim it, mirroring the "asyncFee is left in KeeperFactory and not transferred to the keeper" bug class.

### Finding Description
- `rlp_execute` is `#[payable]`, so `env::attached_deposit()` becomes part of the wallet's balance as soon as the call is scheduled: [1](#0-0) 
- The only deposit-forwarding mechanism is `CallerDeposit`, which is constructed inside `inner_rlp_execute` and threaded through to `rlp_execute_callback`, which refunds it **only if a subsequently created promise fails**: [2](#0-1)  and [3](#0-2) 
- `inner_rlp_execute` calls `internal::parse_rlp_tx_to_action`, and on several error branches (e.g. invalid base64 → `Error::Relayer(RelayerError::InvalidBase64)`, or `TargetKind::OtherNearAccount` with unparsable calldata → propagated `Err`) the function returns an `Err` immediately, *before* `CallerDeposit` is ever attached to a promise: [4](#0-3) [5](#0-4) [6](#0-5) 
- Back in `rlp_execute`, these early errors are handled without ever creating a refund transfer: for `Error::Relayer` when `signer == current_account_id` a `ban_relayer` promise is created that does not touch the deposit; for every other `Err(e)` (including `Error::AccountId` and any other `Error::Relayer`/`Error::User` variant reached this way) the method simply returns `PromiseOrValue::Value(e.into())` with no promise, no transfer: [7](#0-6) [8](#0-7) 
- The `ban_relayer` handler itself only clears the `has_in_flight_tx` flag; it never inspects or refunds a caller's deposit: [9](#0-8) 
- This is structurally the same defect as the KeeperFactory report: tokens move into the intermediary (`WalletContract`) as part of a multi-step "settle"-like flow (RLP-tx parsing → promise construction → callback-based refund-on-failure), but a subset of failure exits skip the step that forwards value back to the party who is owed it, permanently stranding funds in the contract.

### Impact Explanation
Any external, unprivileged account (not just a registered relayer, since `predecessor_account_id` need not hold an access key on the wallet — see `test_caller_refunds`, which already demonstrates an external caller attaching a deposit) that calls `rlp_execute` with a payload triggering one of the pre-promise error paths (malformed base64 RLP payload, malformed Ethereum transaction encoding routed to `TargetKind::OtherNearAccount`, or certain `AccountId`-parsing failures) will have its attached deposit permanently retained by the `WalletContract` instance with no code path to return or claim it. This is a concrete, transaction-triggered permanent loss of user funds (frozen funds) reachable by any RPC caller/contract-call sender — no validator or node compromise required.

### Likelihood Explanation
Likelihood is moderate-to-high: this requires only a single `FunctionCall` to `rlp_execute` with `deposit > 0` and a payload crafted (intentionally or accidentally by a buggy relayer/dApp) to fail parsing before a promise is built. An external caller relying on the documented `test_caller_refunds` guarantee ("External caller gets a refund when the cross-contract call fails") could reasonably expect all failures to be refunded, making accidental fund loss plausible, and an attacker could deliberately craft malformed calldata to grief users who send it through a shared/relayed flow, or simply demonstrate the stuck-funds condition trivially by calling `rlp_execute` directly with `deposit=1` and an invalid base64 string.

### Recommendation
Ensure every error branch returned by `inner_rlp_execute`/`parse_rlp_tx_to_action` that occurs after a deposit has been attached is paired with a refund transfer back to `predecessor_account_id` (mirroring the existing `CallerDeposit` refund used in `rlp_execute_callback`), or defer taking ownership of the deposit until an action/promise consuming or explicitly refunding it has been constructed. Concretely: in `rlp_execute`, for the `Err(e)` branch (and the `Error::Relayer` "ban relayer" branch), check `env::attached_deposit()` and predecessor identity and, if a non-self, non-zero deposit was attached, append a `Promise::new(predecessor_account_id).transfer(...)` to the returned promise before returning.

### Proof of Concept
Conceptual reproduction (matches the existing `test_caller_refunds` harness pattern in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`):
1. Deploy a `WalletContract`.
2. From an external account `caller` (not holding the wallet's access key), attach `deposit_amount > 0` NEAR and call `rlp_execute(target, tx_bytes_b64)` where `tx_bytes_b64` is not valid base64 (or otherwise crafted to hit the `Err` branch returned directly by `parse_rlp_tx_to_action` before any promise is created, e.g. malformed calldata routed through `TargetKind::OtherNearAccount`).
3. Observe that `rlp_execute` returns `PromiseOrValue::Value(ExecuteResponse{success:false, ...})` with **no promise/transfer created**.
4. Query the caller's balance before/after: unlike `test_caller_refunds` (where `PromiseResult::Failed` triggers `CallerDeposit` refund and the caller's balance loss is `< deposit_amount`), here the caller's balance loss is the full `deposit_amount` (minus gas), and the wallet contract's balance increased by that amount permanently, with no contract method exposed to withdraw or reclaim it.

I was not able to execute this against a live/test NEAR node within this session (no filesystem/terminal access here), so this PoC is derived purely from static code-path analysis of `lib.rs`/`internal.rs`/`types.rs`; a Devin session with repo + test-runner access would be needed to confirm the exact error variant reachable from external base64/RLP-malformed input and to execute the workspace test suite (`runtime/near-wallet-contract`) to empirically confirm the stuck balance.

        );
