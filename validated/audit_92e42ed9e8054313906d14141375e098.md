Confirmed: there is no admin retry path for a failed gas refund analogous to `AbortOutbound` for failed fund reverts. `applyGasRefund` is the only code path that ever attempts to return the excess prepaid gas fee, and its failure is only logged into `RefundSwapError`/`PcRefundExecution.Status="FAILED"` with no retry mechanism.

### Title
Excess Outbound Gas Fee Permanently Lost When `refundUnusedGas` Call Fails - (File: x/uexecutor/keeper/outbound.go)

### Summary
When a user's outbound transaction consumes less gas than was pre-charged (`gasFee > gasFeeUsed`), Push Chain attempts to return the difference via `applyGasRefund`, calling `UniversalCore.refundUnusedGas` through `CallUniversalCoreRefundUnusedGas`. If both the swap-refund attempt and the no-swap fallback attempt fail (e.g., insufficient liquidity, slippage bound violated, a reverting recipient contract, or a transient EVM error), the function only records `PcRefundExecution.Status = "FAILED"` and `RefundSwapError`, then returns. No retry, no alternate refund route, and no admin-triggered recovery mechanism exists for the gas-refund path (unlike the fund-revert path, which has `AbortOutbound`/manual-intervention handling). The excess gas fee that was already deducted from the user's bridged funds is not returned and there is no code path that revisits it.

### Finding Description
`x/uexecutor/keeper/outbound.go` computes `refundAmount = gasFee - gasFeeUsed` in `applyGasRefund` [1](#0-0) , then tries a swap-refund and, on failure, a no-swap fallback [2](#0-1) . If the final fallback call also errors, the code simply marks the execution record `FAILED` and moves on: [3](#0-2) .

This function is invoked unconditionally from both `handleSuccessfulOutbound` and `handleFailedOutbound`, and in both cases the outbound is finalized (`UpdateOutbound`) regardless of whether the refund succeeded [4](#0-3) . Contrast this with the fund-revert path in the same file, where a failed re-mint explicitly routes to `AbortOutbound` for manual operator intervention [5](#0-4) . No equivalent abort/retry exists for a failed gas refund. Searching the codebase for any retry message (`MsgRetry*`) or admin path referencing `PcRefundExecution`/`RefundSwapError` found only the outbound.go writer and read-only usages in generated pb/pulsar code and tests — no mutation path exists to reattempt the refund once it fails.

The test suite documents but does not remediate this behavior — it explicitly treats a `FAILED` `PcRefundExecution.Status` as an acceptable outcome ("the important invariant is that the execution record is stored regardless of EVM success/failure") [6](#0-5) , and in the "swap fallback" test case, failure is treated as an acceptable terminal state rather than something requiring recovery [7](#0-6) .

### Impact Explanation
This maps to the "unauthorized burn"/"permanent loss of user or protocol-controlled funds" allowed impact: the pre-charged gas-fee excess belonging to the user (or protocol, depending on accounting) is deducted on outbound creation but never returned when the on-chain refund call fails, and there is no compensating control to retry, escalate, or otherwise recover it. This is reachable purely through the ordinary honest-UV outbound-voting flow (any outbound where `gasFeeUsed < gasFee` and the destination-side `refundUnusedGas` call happens to fail for reasons outside the user's control, e.g. swap-quote slippage or liquidity conditions at settlement time) — no privileged actor or malicious validator is required.

### Likelihood Explanation
Medium. This requires the refund call itself to fail (swap slippage exceeding the 5% tolerance in `applyGasRefund`, thin liquidity for the gas token/PC pair, or a transient EVM/contract issue), which is a normal, not attacker-crafted, operating condition rather than something an unprivileged attacker can force deterministically against arbitrary outbounds. It is nonetheless a realistic occurrence for gas tokens with shallow swap pools, matching the "Medium" severity level cited in the reference report.

### Recommendation
Add a durable recovery path for a failed `applyGasRefund`: either (a) persist the failed refund as a retryable item and expose an admin or permissionless retry message (mirroring the `AbortOutbound`/`MsgRevertStuckInbound` pattern already used for fund reverts), or (b) fail the outbound-finalization path (or explicitly flag it) when the refund cannot be completed so operators are alerted and can manually reconcile funds, instead of silently finalizing the outbound with `PcRefundExecution.Status = "FAILED"` as a dead end.

### Proof of Concept
1. Configure a gas token whose Uniswap V3 pool against PC has low liquidity, such that any swap of `refundAmount` (gasFee − gasFeeUsed) exceeds the 5% `minPCOut` slippage tolerance computed in `applyGasRefund` [8](#0-7) .
2. Trigger a normal outbound (`FUNDS`, `GAS_AND_PAYLOAD`, or `FUNDS_AND_PAYLOAD`) where UVs report `gasFeeUsed < gasFee` via `MsgVoteOutbound`, as in the integration test `TestGasFeeRefund` "refund execution recorded when gasFee exceeds gasFeeUsed" [9](#0-8) .
3. Ensure the no-swap fallback deposit (`CallUniversalCoreRefundUnusedGas` with `withSwap=false`) also fails (e.g., recipient contract without a receive path, or the gas token's PRC20 deposit reverting).
4. Observe `outbound.PcRefundExecution.Status == "FAILED"` and `outbound.RefundSwapError` populated, while the outbound is finalized to `OBSERVED`/`REVERTED` with no further action taken — the user's excess gas fee is unrecoverable through any exposed message in the module.

func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {
	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return
	}

	gasFee := new(big.Int)
	if _, ok := gasFee.SetString(outbound.GasFee, 10); !ok {
		return
	}

	gasFeeUsed := new(big.Int)
	if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}

	refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)

	fee, swapErr := k.GetDefaultFeeTierForToken(ctx, gasToken)

		quote, quoteErr := k.getSwapQuoteForRefund(ctx, gasToken, fee, refundAmount)
		if quoteErr == nil {
			minPCOut := new(big.Int).Mul(quote, big.NewInt(95))
			minPCOut.Div(minPCOut, big.NewInt(100))

			resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, true, fee, minPCOut)
			if err == nil {
				refundPcTx.TxHash = resp.Hash
				refundPcTx.GasUsed = resp.GasUsed
				refundPcTx.Status = "SUCCESS"
				outbound.PcRefundExecution = refundPcTx
				return
			}
			swapFallbackReason = fmt.Sprintf("swap refund failed: %s", err.Error())
		} else {
			swapFallbackReason = fmt.Sprintf("quote fetch failed: %s", quoteErr.Error())
		}
	} else {
		swapFallbackReason = fmt.Sprintf("fee tier fetch failed: %s", swapErr.Error())
	}

	// Step 2: fallback — refund without swap (deposit PRC20 directly to recipient)
	ctx.Logger().Error("applyGasRefund: swap refund failed, falling back to no-swap",
		"outbound_id", outbound.Id,
		"reason", swapFallbackReason,
	)

	resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, false, big.NewInt(0), big.NewInt(0))
	if err != nil {
		refundPcTx.Status = "FAILED"
		refundPcTx.ErrorMsg = err.Error()
	} else {
		refundPcTx.TxHash = resp.Hash
		refundPcTx.GasUsed = resp.GasUsed
		refundPcTx.Status = "SUCCESS"
	}

	outbound.PcRefundExecution = refundPcTx
	outbound.RefundSwapError = swapFallbackReason
