### Title
Unprivileged `StakeInstruction::Merge` during reward-distribution window desynchronizes cached `PartitionedStakeReward` from live `StakesCache`, triggering a deterministic `assert_eq!` panic in `Bank::build_updated_stake_reward` - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`Bank::build_updated_stake_reward` compares the current `Stake.delegation.stake` read from the live `StakesCache` against the reward-adjusted value that was baked into `PartitionedStakeReward.inflation.stake` at reward-calculation time, and panics via `assert_eq!` if they disagree when `adjust_delegations_for_rent` is `false`. An attacker who owns two mergeable, same-voter stake accounts can submit an ordinary `StakeInstruction::Merge` transaction between the epoch-boundary reward-calculation block and the specific distribution block that pays out the destination account, changing the destination's live `delegation.stake` and desynchronizing it from the pre-computed snapshot.

### Finding Description
`Bank::build_updated_stake_reward` fetches the *current* stake account from `stakes_cache_accounts` (the live `StakesCache`, not a frozen snapshot) and destructures its `Stake.delegation.stake` into `stake`: [1](#0-0) 

It then compares that live value plus the reward against `new_stake.delegation.stake`, which comes from `partitioned_stake_reward.inflation.stake` — a value computed and cached at the epoch-boundary calculation block, long before the distribution block executes: [2](#0-1) 

Reward distribution spans multiple blocks (`store_stake_accounts_in_partition` is invoked once per partition, one partition per block) via `distribute_partitioned_epoch_rewards`: [3](#0-2) 

Between the calculation block and the specific block that processes account A's partition, ordinary transactions continue to execute. The codebase explicitly documents and tests that regular (non-reward) transactions, including transfers to stake accounts, execute normally during the reward interval (`test_rewards_period_system_transfer`), and no mechanism was found in `Bank` that blocks `StakeInstruction::Merge` execution while `EpochRewardStatus::Active`. An attacker who owns two stake accounts A and B, both delegated to the same voter and in merge-eligible states, can submit `StakeInstruction::Merge(B into A)` in a block that lands after A's calculation snapshot but before A's distribution-partition block. This merges B's stake into A, increasing A's live `delegation.stake` in the `StakesCache` beyond what was recorded in the cached `PartitionedStakeReward` for A.

When A's partition block finally runs, `build_updated_stake_reward` computes `expected_delegation = <live post-merge stake> + inflation.stake_reward`, while `new_stake.delegation.stake` still holds the stale pre-merge snapshot value plus reward. These values differ by the amount merged in from B, causing the `assert_eq!` to panic instead of returning a `DistributionError`. Because every validator that has adopted the reward-calculation snapshot and StakesCache overlay in the same manner will observe the same discrepancy deterministically when replaying the same block, this crashes the bank-processing thread of every node, halting the cluster.

The `recalculate_partitioned_rewards_if_active` function, which recomputes stake rewards from the live `StakesCache`, is only invoked from `initialize_after_snapshot_restore` — i.e., only on snapshot restore, not on every new bank produced during ordinary block-to-block progress within the same fork: [4](#0-3) 
This means the stale-snapshot vs. live-cache desync is never reconciled mid-epoch outside of a snapshot-restore event, so the described sequence (calculation snapshot → Merge → distribution) is exactly the un-mitigated path into the assert.

The existing `adjust_delegations_for_rent` branch shows the intended pattern (recompute delegation via `adjust_delegation_for_rent` instead of asserting equality), but this branch is gated behind the `relax_post_exec_min_balance_check` feature and is bypassed entirely when that feature is inactive, leaving the assert-based path reachable.

### Impact Explanation
A successful trigger causes `assert_eq!` to panic inside bank-replay/processing code that runs identically on every validator processing the same block, producing a deterministic, cluster-wide panic — a liveness-halting bug, matching Solana's "consensus/liveness halting bug" bounty category. No funds are stolen and no state divergence occurs (all correct validators panic identically), but block production and processing halt cluster-wide until a patched build is deployed.

### Likelihood Explanation
Preconditions: the attacker needs to fund and control two ordinary stake accounts A and B, both delegated to the same vote account, with an already-active/merge-eligible state — entirely achievable by an unprivileged staker at minimal cost (stake account rent-exempt reserve plus stake lamports). The only added element of luck/skill is timing the `Merge` transaction to land after the reward-calculation block for the current epoch but before the specific distribution block that processes account A's partition; on multi-partition (large validator-set) epochs, this window can span many blocks, making the timing straightforward to hit deliberately. The path additionally requires the `relax_post_exec_min_balance_check` feature to be inactive (i.e., the `assert_eq!` branch, not the `adjust_delegation_for_rent` branch) — feature-gate status should be checked on the specific target cluster, since this determines whether the assert path is currently live in production.

### Recommendation
Replace the `assert_eq!` in `Bank::build_updated_stake_reward` with a fallible check that returns a `DistributionError` (mirroring the `AccountNotFound`/`ArithmeticOverflow` handling already present) whenever the live `Stake.delegation.stake` no longer matches the assumption baked into the cached `PartitionedStakeReward`. Alternatively/complementarily, either (a) recompute/validate the expected delegation against the live account unconditionally regardless of the `relax_post_exec_min_balance_check` feature flag, or (b) prevent stake-mutating instructions (`Merge`, `Split`, `Withdraw`, `Deactivate`, `Delegate`) from being processed against any stake account that has a pending, un-distributed `PartitionedStakeReward` entry until distribution completes for it.

### Proof of Concept
Unit test plan (adapting existing `test_build_updated_stake_reward` scaffolding in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`):
1. Create a stake account `A` with `Stake.delegation.stake = S` and store it via `bank.store_account`.
2. Construct a `PartitionedStakeReward` for `A` whose `inflation.stake.delegation.stake = S + stake_reward` (the value computed as if no merge had happened), with `adjust_delegations_for_rent = false`.
3. Simulate the "Merge" by directly mutating the stored account's `Stake.delegation.stake` to `S + B_stake` (as if B were merged in) — this represents the live `StakesCache` state at distribution time, diverging from the value baked into the `PartitionedStakeReward`.
4. Call `Bank::build_updated_stake_reward` with the updated `stakes_cache_accounts` map and the stale `PartitionedStakeReward`.
5. Assert that this call panics (via `std::panic::catch_unwind`) with the message "stake reward delegation must be consistent with the updated stake account lamport balance", instead of returning `Err(...)`.
6. (Optional, higher-fidelity integration test) Use `program-test`/`BanksClient` to: warp to an epoch boundary with multiple reward-distribution partitions, submit a real `stake_instruction::merge` transaction between the calculation block and the target distribution block for a staker's account, then advance blocks and observe the panic during `distribute_partitioned_epoch_rewards`.
