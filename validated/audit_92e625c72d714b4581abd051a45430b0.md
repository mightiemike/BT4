## Title
Replay/output-chunk verification ignores state-checkpoint hashes, allowing a committed state root to diverge from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the routine used both by replay-verification (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) and by debugging/replay tooling (`aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches`) to confirm that a re-derived (or supplied) `TransactionOutput` matches an authenticated `TransactionInfo` — checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) 

Separately, `TransactionOutputListWithProof::verify` — the function that validates an output chunk fetched from a peer during state sync's "apply" (fast-sync/output-replay) path before those outputs are applied directly to storage without VM re-execution — likewise checks only event root, write-set hash, gas, status and transaction hash against the proof, again omitting any check of `state_checkpoint_hash`. [2](#0-1) 

### Finding Description
This is the same class of bug as the reported `Rollup.sol` issue: an authenticated "expected root" field exists (there, `prevStateRoot`; here, `TransactionInfo.state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, all committed into the transaction accumulator and provable via `TransactionInfoListWithProof`), but the code paths that accept and apply a batch of transactions/outputs before they are durably folded into the local Merkle/JMT state never cross-check that the state root actually produced locally matches the authenticated one carried in the proof.

Concretely:
- In `enqueue_chunk_by_transaction_outputs` / `apply_chunk`, transaction outputs (write sets) come with a proof that is checked via `TransactionOutputListWithProof::verify`, which cryptographically ties `write_set_hash`, `gas_used`, `status`, and `transaction_hash` to the accumulator-proven `TransactionInfo`, but never ties the resulting **state root** (`state_checkpoint_hash`) to anything. [3](#0-2) [2](#0-1) 
- The same gap exists in `verify_execution` used by `TransactionReplayer::remove_and_replay_epoch`, which re-executes with the VM and then calls `ensure_match_transaction_info` per transaction to confirm the replay matches the archived `TransactionInfo` — again skipping the checkpoint-hash fields. [4](#0-3) 
- The code itself documents this exact gap as a known, unresolved TODO, explicitly calling out that "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," and instructs that checkpoint hashes must be validated "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." [5](#0-4) 

Because `state_checkpoint_hash` (and its hot/position-state counterparts) is the one field in `TransactionInfo` that is supposed to bind the committed state Merkle/JMT root to the authenticated accumulator entry, its omission means these verification routines cannot detect a divergence between the locally materialized state tree and the state root the network agreed on. This is the same root cause pattern as the reported bug: an "invariant" (previous/expected root correctness) that is assumed to be enforced somewhere is in fact enforced only for a subset of the fields (write-set hash) and not the one that actually anchors state commitment (state-checkpoint hash).

### Impact Explanation
If a node's actual computed state tree (main state, hot state, or the newer native "position" state) diverges from the authenticated `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` in the accumulator-proven `TransactionInfo` — whether due to a local storage bug, a bug in write-set replay logic, or non-determinism in JMT construction — this divergence is silently accepted as a valid replay/apply by both the production output-chunk-apply path (`TransactionOutputListWithProof::verify`, used in real fast-sync/output-replay) and the offline replay-verify tooling that is supposed to catch exactly this class of bug. The affected node would then serve state values, state proofs, and authenticated API responses bound to a state root that the rest of the network does not agree matches its own ledger, i.e. exactly the "wrong accumulator root / proof accepted as valid" and "committed state differs from correct VM result" impacts called out in the State-Integrity Gate.

### Likelihood Explanation
This is not attacker-triggerable on demand in the same direct way as the Solidity bug (there is no separate "malicious sequencer" step here — Aptos's proofs are checked against a BFT-signed `LedgerInfo`, so an attacker cannot forge a `TransactionInfo`). The exposure is that this verification code is the last line of defense against latent state-computation/storage bugs (e.g. write-set application bugs, hot-state or position-state tree construction bugs) actually corrupting a node's durable ledger state without detection, and the code comments confirm the aptos-core authors are aware the check is currently insufficient and gated behind a not-yet-enabled feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`). Given the explicit, still-open TODO, likelihood of this defense-in-depth gap mattering in production is moderate rather than a directly attacker-forced state-root divergence.

### Recommendation
Extend `ensure_match_transaction_info` and `TransactionOutputListWithProof::verify` to also assert that the locally computed `state_checkpoint_hash` (and, where applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) matches the value carried in the accumulator-proven `TransactionInfo`, before those checkpoint hashes are relied upon anywhere (in particular before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / native-position state is enabled). This closes the same class of gap as the reported issue: verify the "previous/expected root" invariant at the point where data is accepted/committed, not only in some other, later or entirely separate code path.

### Proof of Concept
No exploit PoC is provided because this candidate is a defense-in-depth/verification gap rather than a directly attacker-triggerable forgery: the missing checks are documented in-repo as a known TODO (`types/src/transaction/mod.rs:2197-2203`), and confirming an end-to-end exploitable divergence would require identifying a separate primary bug in state/write-set application that this check fails to catch — which was not found in the available code during this review.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    /// Verifies the transaction output list with proof using the given `ledger_info`.
    /// This method will ensure:
    /// 1. All transaction infos exist on the given `ledger_info`.
    /// 2. If `first_transaction_output_version` is None, the transaction output list is empty.
    ///    Otherwise, the list starts at `first_transaction_output_version`.
    /// 3. Events, gas, write set, status in each transaction output match the expected event root hashes,
    ///    the gas used and the transaction execution status in the proof, respectively.
    /// 4. The transaction hashes match those of the transaction infos.
    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_output_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction output versions match
        ensure!(
            self.get_first_output_version() == first_transaction_output_version,
            "First transaction and output version ({:?}) doesn't match given version ({:?}).",
            self.get_first_output_version(),
            first_transaction_output_version,
        );

        // Verify the lengths of the transactions and outputs match the transaction infos
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_outputs(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions and outputs ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_outputs(),
        );

        // Verify the events, write set, status, gas used and transaction hashes.
        self.transactions_and_outputs.par_iter().zip_eq(self.proof.transaction_infos.par_iter())
        .map(|((txn, txn_output), txn_info)| {
            // Check the events against the expected events root hash
            verify_events_against_root_hash(&txn_output.events, txn_info)?;

            // Verify the write set matches for both the transaction info and output
            let write_set_hash = CryptoHash::hash(&txn_output.write_set);
            ensure!(
                txn_info.state_change_hash() == write_set_hash,
                "The write set in transaction output does not match the transaction info \
                     in proof. Hash of write set in transaction output: {}. Write set hash in txn_info: {}.",
                write_set_hash,
                txn_info.state_change_hash(),
            );

            // Verify the gas matches for both the transaction info and output
            ensure!(
                txn_output.gas_used() == txn_info.gas_used(),
                "The gas used in transaction output does not match the transaction info \
                     in proof. Gas used in transaction output: {}. Gas used in txn_info: {}.",
                txn_output.gas_used(),
                txn_info.gas_used(),
            );

            // Verify the execution status matches for both the transaction info and output.
            ensure!(
                *txn_output.status() == TransactionStatus::Keep(txn_info.status().clone()),
                "The execution status of transaction output does not match the transaction \
                     info in proof. Status in transaction output: {:?}. Status in txn_info: {:?}.",
                txn_output.status(),
                txn_info.status(),
            );

            // Verify the transaction hashes match those of the transaction infos
            let txn_hash = txn.committed_hash();
            ensure!(
                txn_hash == txn_info.transaction_hash(),
                "The transaction hash does not match the hash in transaction info. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                txn_hash,
                txn_info.transaction_hash(),
            );
            Ok(())
        })
        .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_output_version())?;

        Ok(())
    }
