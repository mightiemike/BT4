### Title
Unbounded numeric-string parsing of external adapter/bridge response values enables verifier-side CPU DoS - (File: `core/services/pipeline/task.bridge.go`)

### Summary
The `BridgeTask.Run` flow validates required JSON fields from external adapter (EA)/bridge HTTP responses via `jsonDecodeValidateRequiredPaths` and `parseRequiredValidValue`, which feed the raw numeric string value directly into `decimal.NewFromString` and `new(big.Int).SetString(strValue, 0)` with no bound on the length of the numeric string before parsing [1](#0-0) . This mirrors the reported gnark `VerifyPlonk`/`VerifyGroth16` bug class: an untrusted numeric string is handed to a big-integer/decimal parser without prior length or canonical-format validation.

### Finding Description
`jsonDecodeValidateRequiredPaths` is invoked from `maybeValidateRequiredJSONPaths` when a bridge task's response is checked against `t.requiredJSONPaths`, which are derived from downstream `jsonparse` tasks in the pipeline spec [2](#0-1) . For each required path, the raw JSON value bytes are extracted via `jsonparser.Get` and passed to `parseRequiredValidValue`, which tries `decimal.NewFromString` and then `big.Int.SetString(strValue, 0)` on the string with no maximum-length or canonicalization check [3](#0-2) . The only prior constraint on the bridge response body size is the pipeline's `DefaultHTTPLimit()` byte-limit enforced in `makeHTTPRequest`/`clhttp.Request.SendRequest` [4](#0-3)  — that limit bounds total body size but does not bound the size of any individual numeric field within the JSON, nor does it prevent an EA from returning a body consisting almost entirely of a single, extremely long decimal/hex digit sequence at a required path (up to the configured HTTP size limit, which can be large).

Since `decimal.NewFromString` and `big.Int.SetString` perform work proportional to input length (and base-10 big-integer parsing/formatting is known to have superlinear cost for very large inputs), a bridge/EA returning a value with a huge digit count forces the chainlink node to spend proportional CPU/memory validating that single field before any further processing occurs.

### Impact Explanation
This is a verifier-side availability issue analogous to the reported bug: a compromised, misbehaving, or attacker-controlled external adapter can force the receiving Chainlink node to burn excessive CPU/memory parsing an oversized numeric string during required-JSON-path validation, potentially delaying or disrupting job pipeline execution (including OCR report generation feeding on that bridge task's output) for the duration of the bridge task, and creating a slow bridge-cache-fallback cycle on repeated attempts. It does not itself corrupt job results, since parsing failures are treated as failures and fall back to the bridge cache, but it maps to the "external-adapter abuse" trust boundary named in the analog rules and is a genuine availability/performance issue rather than a soundness break.

### Likelihood Explanation
Likelihood is moderate: it requires a bridge/EA source (configured by the node operator, but the EA endpoint itself could be third-party, proxying to an untrusted upstream, or compromised) to return a response containing a very long numeric value at a path required by a downstream `jsonparse` task, and this only triggers when `checkRequired`/`cacheTTL` are enabled for that bridge task [5](#0-4) . There's no explicit code path limiting the numeric field's length independent of the overall HTTP body size limit, so any EA capable of returning near-limit-sized responses (which can be configured to be several megabytes) could exploit this. I was not able to fully confirm the exact default value of `DefaultHTTPLimit()` in this index (only usage sites were found, not the config default), so the practical maximum achievable numeric-string length — and thus the real-world severity of the CPU cost — is unconfirmed.

### Recommendation
- In `parseRequiredValidValue`, reject values whose byte length exceeds a small, sane bound (e.g., 128 bytes) before calling `decimal.NewFromString` or `big.Int.SetString`.
- Prefer validating canonical numeric formatting (no redundant leading zeros/whitespace padding) and cap digit counts to what's plausible for real-world price/decimal feed values.
- Consider applying this length check generically wherever pipeline tasks parse untrusted numeric strings from HTTP/bridge responses (e.g., `DecimalParam`/`ToDecimal` in `core/utils/decimal.go`) to close the same class of issue across all such call sites.

### Proof of Concept
1. Configure a bridge task with `checkRequired="true"` and a non-zero `cacheTTL`, with a downstream strict `jsonparse` task reading a specific JSON field.
2. Point the bridge to a malicious/compromised external adapter that returns HTTP 200 with a JSON body where the required field's value is a decimal literal with millions of digits (kept under the pipeline's `DefaultHTTPLimit` byte cap).
3. Observe `jsonDecodeValidateRequiredPaths` → `parseRequiredValidValue` spend disproportionate CPU/memory parsing that single field via `decimal.NewFromString`/`big.Int.SetString` before returning success or failure, on every bridge task execution against that adapter. [6](#0-5)

// maybeValidateRequiredJSONPaths runs jsonDecodeValidateRequiredPaths when the live call succeeded (HTTP 200, no
// transport error), checkRequired is enabled, cache is enabled, and the pipeline registered required paths. A
// failed check sets err so the caller can fall back to the bridge cache when configured.
func (t *BridgeTask) maybeValidateRequiredJSONPaths(err error, liveOK bool, cacheTTL Uint64Param, checkRequired BoolParam, responseBytes []byte) error {
	if err != nil || !liveOK || cacheTTL == 0 || !bool(checkRequired) || len(t.requiredJSONPaths) == 0 {
		return err
	}
	if verr := jsonDecodeValidateRequiredPaths(responseBytes, t.requiredJSONPaths); verr != nil {
		return errors.Wrap(verr, "bridge response failed required JSON path check for downstream jsonparse")
	}
	return err
}

// jsonDecodeValidateRequiredPaths checks each path in the raw JSON body using
// streaming lookup (no full value unmarshal). Missing keys, JSON null, JSON numbers
// that are not valid for shopspring/decimal (including exponent/size limits), and the
// string "NaN" are treated as failure so bridge cache fallback can apply.
//
// For each present value, parseRequiredValidValue must succeed: decimals and floats
// via shopspring/decimal, integer literals (decimal or hex with optional sign) via
// math/big so huge 0x… values validate and scientific notation is not mistaken for
// hexadecimal.
func jsonDecodeValidateRequiredPaths(body []byte, paths [][]string) error {
	if len(paths) == 0 {
		return nil
	}
	for _, path := range paths {
		if len(path) == 0 {
			continue
		}

		value, dataType, _, err := jsonparser.Get(body, path...)
		if err != nil {
			return errors.Wrapf(err, "required path %q", strings.Join(path, ","))
		}

		if dataType == jsonparser.Null {
			return errors.Errorf("required path %q is null", strings.Join(path, ","))
		}

		if err := parseRequiredValidValue(value); err != nil {
			return errors.Wrapf(err, "required path %q", strings.Join(path, ","))
		}
	}
	return nil
}

// parseRequiredValidValue accepts values that can be parsed by shopspring/decimal or math/big.
func parseRequiredValidValue(value []byte) error {
	strValue := string(value)
	if _, err := decimal.NewFromString(strValue); err == nil {
		return nil
	}
	if _, ok := new(big.Int).SetString(strValue, 0); ok {
		return nil
	}
	return errors.Errorf("invalid value: %s", string(value))
}

func makeHTTPRequest(
	ctx context.Context,
	lggr logger.Logger,
	method StringParam,
	url URLParam,
	reqHeaders []string,
	requestData MapParam,
	client *http.Client,
	httpLimit int64,
) (responseBytes []byte, statusCode int, respHeaders http.Header, start, finish time.Time, err error) {
	var bodyReader io.Reader
	if requestData != nil {
		var bodyBytes []byte
		bodyBytes, err = json.Marshal(requestData)
		if err != nil {
			err = errors.Wrap(err, "failed to encode request body as JSON")
			return
		}
		bodyReader = bytes.NewReader(bodyBytes)
	}

	var request *http.Request
	request, err = http.NewRequestWithContext(ctx, string(method), url.String(), bodyReader)
	if err != nil {
		err = errors.Wrap(err, "failed to create http.Request")
		return
	}
	request.Header.Set("Content-Type", "application/json")
	if len(reqHeaders)%2 != 0 {
		panic("headers must have an even number of elements")
	}
	for i := 0; i+1 < len(reqHeaders); i += 2 {
		request.Header.Set(reqHeaders[i], reqHeaders[i+1])
	}

	httpRequest := clhttp.Request{
		Client:  client,
		Request: request,
		Config:  clhttp.RequestConfig{SizeLimit: httpLimit},
		Logger:  logger.Sugared(lggr).Named("HTTPRequest"),
	}

	start = time.Now()
	responseBytes, statusCode, respHeaders, err = httpRequest.SendRequest()
	finish = time.Now()
