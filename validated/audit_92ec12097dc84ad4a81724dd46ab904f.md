### Title
Idempotent promise handler permanently swallows `afterAuth` hook execution after a failure, causing silent auth completion until a 60-second TTL expires - (File: packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts)

### Summary
The token-exchange authorization strategies (`shopify-app-remix`, `shopify-app-react-router`, `shopify-app-express`) wrap the `afterAuth` hook call in an `IdempotentPromiseHandler` keyed by the session token string, to avoid running the hook twice for the same token. The handler marks the identifier as "consumed" *before* it knows whether the wrapped promise succeeds, mirroring the Andromeda vesting bug pattern where state (`batch.last_claimed_release_time`) is advanced optimistically regardless of whether the underlying transfer actually completed. If the `afterAuth` hook throws (e.g. transient error registering webhooks), the identifier remains marked as "already run" in the in-memory map for up to 60 seconds, silently skipping the hook on any retry with the same session token during that window, while the caller still treats the outer flow as complete.

### Finding Description
`IdempotentPromiseHandler.isPromiseRunnable()` inserts the identifier into the `identifiers` map and returns `true` on the *first* call, then immediately proceeds to `await promiseFunction()`: [1](#0-0) 

If `promiseFunction()` throws, the exception propagates out of `handlePromise` (the `finally` only runs `clearStaleIdentifiers`, which does not remove the just-failed identifier because it hasn't exceeded the 60-second TTL yet). This is called from the token-exchange strategy's `handleAfterAuthHook`: [2](#0-1) 

In `authenticate()`, a failure from `handleAfterAuthHook` is caught and converted into a `500 Internal Server Error` response, but the session (offline/online) was already exchanged and stored via `config.sessionStorage!.storeSession(...)` beforehand: [3](#0-2) 

Because the identifier used is the raw `sessionToken` JWT string (not a per-attempt UUID), any retry with the exact same session token — which is realistic since App Bridge/browser fetch retries typically resend the same in-flight token within the JWT's short validity window — will find `isPromiseRunnable(identifier)` returns `false` and skip `afterAuth` entirely, even though it never actually succeeded. The request will then proceed as if authentication/setup fully completed (the stored session is already active), silently dropping the hook's side effects (e.g., webhook registration) for up to 60 seconds.

This is structurally analogous to the Andromeda bug: an optimistic state transition (`identifiers.set(identifier, Date.now())` / `batch.last_claimed_release_time += ...`) is committed *before* verifying the underlying operation actually completed in full, and the affected resource (webhook registration / staked tokens) is effectively locked out from being retried until a time-based condition elapses (`IDENTIFIER_TTL_MS` / re-vesting cycle).

### Impact Explanation
This is a DoS of the authentication/setup handler: on transient `afterAuth` hook failures, retries within 60 seconds by the same client (same session token) will not re-attempt the hook, silently succeeding the auth flow without its side effects (e.g., mandatory webhook registration performed in `afterAuth`). This can leave an app shop in a partially-configured state (missing webhook subscriptions) without any further errors surfaced to the merchant or developer, for the duration of the TTL, and there is no re-registration until the underlying failure is retried outside the TTL window or with a distinct session token.

### Likelihood Explanation
Likelihood is limited: it requires (a) a transient failure in the developer-supplied `afterAuth` hook, and (b) a retry from the client using the identical session token string within 60 seconds — both plausible under normal browser/App Bridge retry behavior but not guaranteed or attacker-controlled. It does not allow an attacker to forge sessions or bypass authentication; it purely affects reliability/DoS of the auth-setup side effects.

### Recommendation
Only mark the identifier as consumed after `promiseFunction()` successfully resolves, and remove/never insert it if the promise throws, e.g.:
```ts
async handlePromise({promiseFunction, identifier}: IdempotentHandlePromiseParams) {
  if (this.identifiers.has(identifier)) return;
  this.identifiers.set(identifier, Date.now());
  try {
    await promiseFunction();
  } catch (error) {
    this.identifiers.delete(identifier);
    throw error;
  } finally {
    this.clearStaleIdentifiers();
  }
}
```
This ensures a failed `afterAuth` invocation can be retried immediately rather than being silently suppressed for up to a minute.

### Proof of Concept
1. Configure `afterAuth` hook to intermittently throw (e.g. network blip registering webhooks).
2. Client authenticates via token exchange; `TokenExchangeStrategy.authenticate` exchanges/stores the offline session, then calls `handleAfterAuthHook` with `identifier = sessionToken`.
3. `IdempotentPromiseHandler.isPromiseRunnable(sessionToken)` returns `true` and inserts the identifier immediately; `afterAuth` throws; `authenticate()` returns a `500`.
4. Client (same session token, still valid) retries the request within 60 seconds.
5. `isPromiseRunnable(sessionToken)` now returns `false` (identifier still present, not stale) — `afterAuth` is skipped entirely, and since the session was already stored as active, the retried request proceeds as authenticated without ever successfully running `afterAuth`, until the 60-second TTL clears the identifier.

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }
