## Analog Found

### Title
Malicious NEP-141 token can permanently lock the NEAR Wallet Contract by triggering a gas-exhaustion panic in its callback before `has_in_flight_tx` is durably reset - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The external report describes a withdraw function that requires an untrusted external call (a reward-token transfer) to succeed before it will release funds, so a malicious token can make the withdrawal permanently revert and freeze user funds. The `WalletContract` in nearcore's eth-wallet implementation has an analogous single-point-of-failure: a single boolean latch, `has_in_flight_tx`, gates every future transaction, and that latch is only durably cleared if a callback that processes attacker-controlled data from an arbitrary NEP-141 token completes without panicking.

### Finding Description
`WalletContract::rlp_execute` refuses to process any transaction while `self.has_in_flight_tx` is `true`: [1](#0-0) 

For an emulated ERC-20 transfer, `inner_rlp_execute` builds a promise chain to an attacker-chosen `token_id` (the "to" address of the user's own signed Ethereum-style transaction, which can be any NEP-141 contract, including one deployed by an unrelated malicious party), calling `storage_balance_of` and chaining to `nep_141_storage_balance_callback` with a fixed gas budget: [2](#0-1) 

The callback gas budget is a small, fixed constant (5 TGas plus the inner action's gas): [3](#0-2) 

Inside the callback, `has_in_flight_tx` is reset to `false` as the very first statement, and then the callback deserializes the **attacker-controlled** return value from `storage_balance_of` with `serde_json::from_slice`: [4](#0-3) 

Because a malicious token contract fully controls the bytes returned from `storage_balance_of`, it can return a payload crafted to consume disproportionate gas during JSON deserialization (e.g., deeply nested/large JSON), driving the callback to exceed its fixed 5 TGas allotment and panic with an out-of-gas error. Per the runtime's action-receipt execution model, any panic inside a receipt causes the **entire receipt to roll back**, discarding all state writes made during that action — including the earlier `self.has_in_flight_tx = false` assignment: [5](#0-4) 

Since the write is rolled back, `has_in_flight_tx` remains `true` (as it was set before the promise was dispatched), and every subsequent call to `rlp_execute` on this wallet permanently returns the "transaction already in progress" error, blocking all further use of the contract.

### Impact Explanation
This directly mirrors the reported bug class: an untrusted, attacker-influenced external contract (the malicious/"gas-griefing" NEP-141 token, analogous to the malicious reward token) is invoked as part of a value-transfer flow, and its adversarial behavior causes a state (a boolean latch requiring a successful callback) that permanently disables all future withdrawals/transactions for the affected account. Every NEAR balance and every NEP-141 token balance custodied by that Wallet Contract instance becomes permanently inaccessible through the contract's normal `rlp_execute` interface, satisfying the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
The attack is triggerable by a single, unprivileged transaction: the user's own signed Ethereum-style transaction targets an ERC-20-shaped account under attacker control (e.g., a dApp lures the user into an ERC-20 transfer with a malicious token, or the target account is later redeployed/controlled maliciously). No relayer collusion, validator power, or protocol-level privilege is required — only that the wallet owner's transaction routes an ERC-20 transfer through a hostile `token_id` contract. The fixed, small callback gas budget (5 TGas, independent of the untrusted payload size) makes the gas-exhaustion condition realistically reachable with a crafted `storage_balance_of` response.

### Recommendation
- Bound the callback's exposure to untrusted payload size before deserializing (e.g., reject or truncate abnormally large `promise_result` payloads prior to `serde_json::from_slice`), and/or perform the state reset of `has_in_flight_tx` in a way that survives a subsequent panic (e.g., split into two receipts, or use a dedicated top-level callback that only clears the flag and cannot itself panic on attacker data).
- Consider using a bounded/streaming JSON parser or `try_from_slice` with an explicit size cap for NEP-141 responses.
- Add a recovery/"emergency unlock" path (analogous to the recommended `emergencyWithdraw`) that lets the wallet owner force-clear `has_in_flight_tx` after a timeout, independent of the callback's outcome.

### Proof of Concept
1. Attacker deploys a NEP-141-shaped contract whose `storage_balance_of` method returns a JSON payload engineered to be maximally expensive to deserialize (e.g., large/deeply nested JSON) while still fitting under receipt data-size limits.
2. Victim signs an Ethereum-style transaction (via their Wallet Contract) that performs what appears to be a normal ERC-20 `transfer` to that malicious token contract, per `inner_rlp_execute`'s `ERC20Transfer` branch [2](#0-1) .
3. `rlp_execute` sets `has_in_flight_tx = true` and dispatches `storage_balance_of` to the malicious contract, chained to `nep_141_storage_balance_callback` with the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget.
4. The malicious contract's crafted response causes `serde_json::from_slice` inside the callback to exceed the allotted gas and panic.
5. Per `apply_action_receipt`, the callback receipt fails and rolls back all its state changes, including the reset of `has_in_flight_tx` [5](#0-4) .
6. All subsequent calls to `rlp_execute` on the victim's Wallet Contract immediately return `"Error: transaction already in progress, please try again later."` [6](#0-5) , permanently freezing the account's funds accessible through this contract.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
