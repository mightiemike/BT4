### Title
`ensure_match_transaction_info` never checks the state/hot-state/position checkpoint hashes, letting replay-verify accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole post-execution correctness check used by `db-tool`'s `replay-verify` and other replay/debug paths to confirm that locally re-executed transactions match previously committed, backed-up `TransactionInfo`s. It validates status, gas used, write-set hash, and event-root hash, but never compares the state checkpoint hash (nor hot-state/position-state checkpoint hashes) against the corresponding fields of the trusted `TransactionInfo`. This mirrors the reported bug pattern: parameters/values that are supposed to gate a specific check are present but excluded from the actual verification logic, so the intended guarantee ("replayed state matches archived committed state") silently never holds for the state root.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (hash of `self.write_set()`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It never touches `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, or `position_state_checkpoint_hash`. The code itself flags this gap with an explicit `TODO(trading-native)` comment stating the comparator "ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," and that this must be fixed before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled. This confirms the maintainers already understand the gap exists but it is still present in the shipped comparator.

This function is invoked as the terminal correctness gate in `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, at [2](#0-1) , where locally re-executed `TransactionOutput`s are checked against `expected_txn_infos` pulled from a backup/archive. `expected_write_set` and `expected_events` are passed into the function but, as shown at lines 2168-2195, are used only inside the `ensure!` error-message formatting — never in the actual boolean check — which is the direct structural analog of the reported bug (arguments present but functionally inert).

Because the state checkpoint hash is entirely unchecked:
- If local re-execution produces a state checkpoint (Merkle root over updated state) that differs from the state root recorded in the archived `TransactionInfo` (e.g. due to a divergent state-computation bug, storage corruption, or a hard-fork/consensus divergence introduced upstream), `ensure_match_transaction_info` still returns `Ok(())` as long as write-set bytes, events, gas, and status match.
- The write-set-hash check (`state_change_hash`) covers only the raw write set produced *by this transaction*, not the resulting Merkle/state-checkpoint root, which is a materially different value (it depends on the entire state tree, hot-state promotions, and — per the TODO — position-native state). A wrong accumulation of prior writes into the JMT, or an unrelated bug in `DoStateCheckpoint`'s tree update, would not surface here.

### Impact Explanation
This breaks the "committed state must match VM result" and "proof/verification-context bound to the right root" invariants required by the gate: a state root divergence at a checkpoint transaction is exactly the kind of hard-fork/consensus-critical bug this tool exists to catch, yet the tool's sole per-transaction success/failure decision cannot detect it. An operator running `replay-verify` (e.g., to confirm a node's historical execution is byte-for-byte consistent with the canonical archive, or to validate a new VM/executor release before deployment) would get a false "all good" result while state actually diverged. This directly matches the required impact category "Committed state that differs from the correct VM result ... Hard-fork-only divergence during commit, replay, restore, or proof verification," because the verification path itself is blind to the state-root field.

### Likelihood Explanation
Likelihood of the underlying state divergence occurring is low to moderate (it requires a genuine executor/state-checkpoint bug elsewhere), but the likelihood that such a divergence would go *undetected* by this specific tool is effectively certain, since the check for the checkpoint hash simply doesn't exist. The maintainers' own TODO acknowledges this as a real gap they intend to close before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, corroborating that it is a genuine, currently-open weakness rather than a false positive.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s resulting state checkpoint hash (when the transaction is a checkpoint) against `txn_info.state_checkpoint_hash()`, and similarly validate the hot-state and position-state checkpoint hashes when those features are enabled, mirroring how `write_set_hash` and `event_root_hash` are already validated. Until that is done, `replay_on_archive`/`replay-verify` should not be treated as proof that historical state roots match, and this should be explicitly called out as a known limitation (or the check should be added before shipping/relying on trading-native state roots).

### Proof of Concept
Conceptual repro (tooling-level, not requiring privileged access):
1. Take an archived backup containing a `TransactionInfo` for a checkpoint transaction with a known-good `state_checkpoint_hash`.
2. Run `replay_on_archive` against a target DB/execution path that (due to any bug, e.g., a faulty state-checkpoint merge) produces a different state root for that version but the identical write set/events/gas/status (e.g., a stale, incorrectly-cached previous checkpoint hash, or a JMT construction bug that doesn't change write-op contents).
3. `execute_and_verify` calls `ensure_match_transaction_info` at [3](#0-2) ; because the check never inspects `state_checkpoint_hash`, verification returns `Ok(())` and the tool reports success despite the state-root divergence.

Note: I was unable to fully trace whether `TransactionInfo` objects fetched via `backup_handler.get_transaction_iter` are cryptographically authenticated (via an accumulator/Merkle proof against a trusted `LedgerInfo`) before being used as "expected" in this comparison — I ran out of iterations to confirm this chain. If they are unauthenticated raw backup reads (as appears likely for a debug/replay tool operating directly on a backup file), then the missing checkpoint-hash check is the only mechanism that could have caught a state divergence in this flow.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
