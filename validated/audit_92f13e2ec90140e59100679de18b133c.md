## Finding: Missing negative-value validation on `observed_tx.gas_fee_used` allows unbounded unauthorized minting via `applyGasRefund`

### Title
Unchecked negative `GasFeeUsed` in outbound-vote gas-refund path leads to unauthorized PRC20/gas-token minting - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
This is the same bug class as the reported `mintLp`/`burnLp` issue: a value that is expected to be a non-negative `uint256`-equivalent is converted from an attacker/validator-supplied string into a signed `*big.Int` without an explicit sign check, and the unchecked value is then used directly in fund-moving arithmetic and minting calls.

### Finding Description
`MsgVoteOutbound.ValidateBasic` only checks that `observed_tx.gas_fee_used` is non-empty; it never validates that the string parses to a non-negative number: [1](#0-0) 

The value flows unchanged into `Keeper.VoteOutbound` → `FinalizeOutbound` → `applyGasRefund`, where it is parsed with `big.Int.SetString`, which silently accepts a leading `-` sign: [2](#0-1) 

If `obs.GasFeeUsed` is a negative decimal string (e.g. `"-1000000"`), the comparison `gasFee.Cmp(gasFeeUsed) <= 0` is false (since `gasFee > gasFeeUsed`), so the "no excess" short-circuit is skipped, and:
```
refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
```
computes `gasFee - (negative) = gasFee + |gasFeeUsed|`, producing an arbitrarily large positive `refundAmount` (bounded only by the string length the attacker supplies). This inflated amount is then passed straight into `CallUniversalCoreRefundUnusedGas`, which performs a `DerivedEVMCall` to `refundUnusedGas` — a module-originated mint/deposit of the gas token to the refund recipient: [3](#0-2) 

Contrast this with `Inbound.ValidateForExecution`, which explicitly guards against exactly this class of bug for the `Amount` field (`bi.Sign() < 0` check) after a documented negative-amount regression: [4](#0-3) 
No equivalent `Sign() < 0` guard exists for `GasFeeUsed` in `msg_vote_outbound.go`, `outbound.go`, or `applyGasRefund`.

### Impact Explanation
This breaks the "unauthorized mint" invariant in the Registry/Accounting path: an attacker-controlled or malformed `gas_fee_used` value can cause the protocol to mint/deposit an arbitrary, attacker-chosen surplus of the gas-token PRC20 to a `refund_recipient` address that the attacker also controls via `RevertInstructions.FundRecipient`. This is a direct, module-originated unauthorized mint of protocol-controlled funds — squarely in scope ("unauthorized mint ... of user or protocol-controlled funds").

### Likelihood Explanation
The report's threat model requires "honest validators and honest nodes." Under that assumption, whether this is reachable by an unprivileged external attacker hinges on where `gas_fee_used` numeric strings ultimately originate for a given tx type/path, and whether any upstream component (universalClient tx builders, `event_processor.go`) always produces non-negative decimal strings from `big.Int.SetUint64`-derived arithmetic. I was not able to fully trace every producer of `OutboundObservation.GasFeeUsed` within the available context/index to confirm whether an honest, non-malicious codepath (rather than a malicious UV deliberately crafting a negative string) can ever emit a negative value — e.g. via a signed subtraction, a chain-specific fee calculation, or a not-fully-audited universalClient formatting function. Given the uncertainty, likelihood should be treated as **medium/uncertain** until that producer-side trace is completed by someone with full repository access (the ask-only index may not contain every relevant file, e.g. `universalClient/chains/*/event_processor.go` fee-computation internals were only partially visible).

### Recommendation
Add an explicit non-negative check when parsing `GasFeeUsed` (and symmetrically `GasFee`) in `applyGasRefund`, mirroring the fix already applied to `Inbound.ValidateForExecution`:
```go
gasFeeUsed := new(big.Int)
if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok || gasFeeUsed.Sign() < 0 {
    return
}
```
and add the same guard to `MsgVoteOutbound.ValidateBasic` so malformed/negative values are rejected at the message level rather than silently producing a huge refund downstream.

### Proof of Concept
Given the ask-only nature of this task, I could not execute code, but the logical PoC is:
1. Set up an outbound with `GasFee = "111"`, `GasToken` set to a valid PRC20 address (as in the existing `gas_fee_refund_test.go` fixtures).
2. Submit `MsgVoteOutbound` with `observed_tx.gas_fee_used = "-1000000000000000000"` from enough validators to finalize the ballot (this passes `ValidateBasic` since it only checks for empty string, not sign).
3. `applyGasRefund` computes `refundAmount = 111 - (-1000000000000000000) = 1000000000000000111`.
4. `CallUniversalCoreRefundUnusedGas` mints/deposits that inflated amount to `refundRecipient` (attacker-controlled via `RevertInstructions.FundRecipient`).

I recommend a Devin agent with full repo/test access confirm exact reachability (whether `gas_fee_used` is UV-vote-controlled string data, or is bound to safe arithmetic before reaching this msg) and add a regression test analogous to `x/uexecutor/types/inbound_test.go`'s `"negative amount"` case, but for `MsgVoteOutbound`/`applyGasRefund`.

```go
func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {
	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return
	}

	gasFee := new(big.Int)
	if _, ok := gasFee.SetString(outbound.GasFee, 10); !ok {
		return
	}

	gasFeeUsed := new(big.Int)
	if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}

	refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
```

```go
func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
```
