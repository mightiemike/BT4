## Title
Cross-transaction stale liquidity/borrow index from `index-cache` map surviving within a single block after a non-time-based index write-down - (File: `mainnet/contracts/market/v0-4-market.clar`)

## Summary
`market.clar`'s index cache is documented as "ephemeral" and invalidated "each block", but it is implemented as a persistent `define-map` keyed only by `{ timestamp: stacks-block-time, aid: uint }` [1](#0-0) . Because `stacks-block-time` is identical for every transaction inside the same Stacks block, this cache is not actually transaction-scoped — a value written by one transaction remains readable, unmodified, by a later transaction in the same block, as long as no code path explicitly overwrites it.

## Finding Description
`accrue-and-cache` only calls into the vault (`vault-accrue`) on a cache **miss**; on a cache **hit** it returns the previously stored `{index, lindex}` without any further validation [2](#0-1) . `borrow`, `repay`, `collateral-add`, `collateral-remove`, and `liquidate` all rely on this cache being fresh for the current position of health/price computation [3](#0-2) [4](#0-3) .

The one place the code explicitly acknowledges the cache can go stale from a *non-time-based* mutation is `socialize-debt-asset`, which writes down `lindex` in the vault (bad-debt write-off) and then manually re-populates `index-cache` with the fresh value, with a comment flagging exactly this risk: *"Refresh cache with new indexes post-write-down (lindex decreased)"* [5](#0-4) . The vault's `socialize-debt` function itself performs this non-time-based `lindex` reduction directly on persistent vault state [6](#0-5) .

This demonstrates the developers understand the cache's *source of truth* (the vault's index/lindex) can move independently of `stacks-block-time`, and that stale cached values are dangerous enough to warrant a manual refresh in that one path. The root cause is architectural: the cache invalidation strategy ("new block → new timestamp → cache miss") documented in `docs/market.md:627-633` is incorrect for any block containing more than one transaction, since the cache key does not include a transaction/nonce discriminator — only `(timestamp, aid)`.

## Impact Explanation
If any vault-index-moving event (a socialized/written-down bad debt, or any other non-time-based index mutation) lands in the same block as a subsequent user transaction that reads `index-cache` on a hit (bypassing a fresh `vault-accrue` call), that later transaction's debt/collateral valuation, health check, and liquidation math would be computed against a stale index instead of the true post-mutation index for the remainder of that block. Depending on the direction of staleness this can let a borrower's position appear healthier than it truly is (under-valuing debt, or over-valuing zToken collateral priced off `lindex`) at the time of a `borrow`/`collateral-remove`, i.e. temporary freezing/mis-accounting of funds tied to the vault's true asset backing, since the discrepancy self-corrects once the block timestamp changes and forces a fresh accrual on a cache miss. This lands in the **High – temporary freezing of funds** class per the impact taxonomy in scope.

## Likelihood Explanation
Exploitability requires: (1) a `socialize-debt` (or other non-time index write-down) event, and (2) a victim/attacker transaction reading the same `aid`'s cached index later in the same block, before the block's `stacks-block-time` advances. Because `socialize-debt` is a privileged/system path (only reachable through liquidation-driven bad-debt handling) and same-block transaction ordering on Stacks is influenced by miners/relative fee ordering, this is not trivially attacker-controlled end-to-end — the attacker cannot unilaterally guarantee both transactions land in the same block in the needed order. This lowers likelihood from "High" to "Medium/Low" in practice, even though the mechanism (cache is not actually per-transaction, contradicting the documented "ephemeral"/"per-timestamp-invalidated" design) is clearly demonstrated by the code's own defensive refresh in `socialize-debt-asset`.

## Recommendation
Key `index-cache` by `(tx sender/nonce or a monotonic per-transaction counter, aid)` in addition to timestamp, or, more simply, make the cache genuinely ephemeral by clearing entries for an `aid` immediately whenever a value-moving event happens in the vault (as already done for `socialize-debt`), and audit all other vault-mutation paths (`vault-system-borrow`, `vault-system-repay`, `vault-deposit`, `vault-redeem`) to confirm none of them can move `index`/`lindex` without a corresponding `index-cache` invalidation reachable by a subsequent transaction in the same block.

## Proof of Concept
Not independently confirmed with a concrete second index-moving code path beyond `socialize-debt`; the vault-level `accrue`/`vault-accrue` definitions that determine exactly how `index`/`lindex` are recomputed from `total-assets`/`total-supply` were not fully retrieved before the tool budget was exhausted, so I could not conclusively prove a second, attacker-triggerable, non-privileged path that moves the index without an accompanying cache refresh. This is a **partial finding**: the architecture flaw (persistent, cross-transaction cache masquerading as "per-block ephemeral") is proven directly from the code and the developers' own mitigating comment, but a fully attacker-controlled two-transaction PoC using only non-privileged, non-DAO paths could not be completed within the available searches.

Given the residual uncertainty on likelihood and full exploitability chain, I present this as a partial/uncertain finding rather than a fully validated one — further investigation into `v0-vault-*.clar`'s `accrue` implementation would be needed to confirm or refute a fully user-triggerable variant.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
