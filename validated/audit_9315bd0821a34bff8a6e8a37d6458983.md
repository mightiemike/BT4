Based on my research, I found a legitimate analog in the sequencer's execution-engine caching layer.

### Title
Stale cached Cairo0 (deprecated) compiled class bypasses the declared-class check after state revert - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
The `AuctionRebalanceModuleV1` bug is a class of "removal doesn't purge derived/cached state" bug: a mapping keyed by an identifier that should be invalidated on removal is left populated, letting stale data be reused later as if it were still valid. The `apollo_node` sequencer has the same bug class in `StateReaderAndContractManager::get_compiled_from_class_manager`, which caches compiled classes keyed by `class_hash` in the process-local `ContractClassManager` (`class_cache`). The code contains an explicit safeguard comment acknowledging that a cached class can persist "from a reverted block", but the safeguard (`is_declared` check) is only applied to Cairo1 (`V1`)/native classes, not to Cairo0 (`V0`, deprecated) classes.

### Finding Description
`get_compiled_from_class_manager` looks up the runnable class from `self.contract_class_manager.get_runnable(...)`. When found, it explicitly re-validates declaration status only for non-V0 classes: [1](#0-0) 

The comment at lines 76-81 states the exact root cause: cache existence does not imply the class is currently declared, "it might contain a declared class from a reverted block, for example" — but the `if !self.state_reader.is_declared(class_hash)?` check is skipped for `RunnableCompiledClass::V0(_)`. This mirrors the reported bug class where `AuctionRebalanceModuleV1.removeModule` leaves `executionInfo` populated so stale settings are reused after the module is later re-added — here, the storage-level "removal" (a `revert_state_diff` that deletes `deprecated_declared_classes`/class definitions) does not invalidate the derived cache the execution layer trusts.

Storage-side reverting does correctly delete the deprecated class declaration entries: [2](#0-1) 

But this only clears the persistent storage tables — it has no interaction with the separate, process-local `ContractClassManager`/`class_cache` that the blockifier execution path consults first. That in-memory cache is only ever cleared wholesale via `clear()`, never selectively invalidated per reverted class hash: [3](#0-2) 

### Impact Explanation
If a block containing a Cairo0 `deploy`/`declare` is reverted (e.g., during a reorg handled by `revert_block`/`revert_state_diff`), and the sequencer process previously cached the Cairo0 compiled class for that `class_hash`, a subsequent transaction that invokes a contract at that (now-undeclared) class hash can still execute successfully in the sequencer's blockifier because the `V0` branch skips the `is_declared` re-check. Since the Starknet OS re-execution and any honest node without the stale cache would reject the call as referencing an undeclared class, this creates a **divergence between the sequencer's local execution result and the canonical/OS-verified state transition**, potentially producing a block whose state diff/committed root cannot be validated by the OS or by other honest nodes — i.e., a wrong committed root / consensus-safety issue, which is High severity per the class of impacts targeted (honest-node divergence, wrong committed root).

### Likelihood Explanation
Requires two conditions: (1) a class-declaring block later being reverted (a legitimate sequencer/state-sync operation, not attacker-controlled) and (2) an ordinary user submitting an invoke transaction calling that class hash afterward — a fully unprivileged, single-transaction trigger. The comment in the code shows the authors were aware of the reverted-cache risk for V1 but the fix was not extended to V0, making this a straightforward oversight rather than a hypothetical corner case.

### Recommendation
Apply the same `is_declared` verification for `RunnableCompiledClass::V0` that is already applied to the `V1`/native branches in `get_compiled_from_class_manager`, or invalidate/evict the corresponding cache entries in `ContractClassManager` whenever `revert_state_diff` deletes a class declaration.

### Proof of Concept
1. Sequencer executes and commits a block declaring/deploying a Cairo0 class `C` at `class_hash H`; the process's `ContractClassManager.class_cache` caches the compiled class for `H` (populated via `set_and_compile` on first execution touching `H`). [4](#0-3) 
2. A revert occurs on that block (`revert_block` → `revert_state_diff`), which deletes `H` from `deprecated_declared_classes`/`deprecated_declared_classes_block` storage tables, making `is_declared(H)` return `false` going forward. [2](#0-1) 
3. A user submits a new invoke transaction that calls a contract with `class_hash == H`. `get_compiled_class` → `get_compiled_from_class_manager` finds `H` still in `class_cache`, matches `RunnableCompiledClass::V0(_)`, skips the `is_declared` check, and returns the stale compiled class, allowing execution to proceed against an undeclared class hash — producing an execution result inconsistent with the canonical (post-revert) state. [5](#0-4)

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
