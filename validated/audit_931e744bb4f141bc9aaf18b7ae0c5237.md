### Title
Unbounded recursion in `bytecode_hash_node` over Cairo-compiler-supplied `NestedIntList` during compiled class hash computation - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
The reported CVE-2022-30633 is a stack-exhaustion bug caused by unbounded recursive descent when unmarshaling/traversing untrusted, arbitrarily nested input. The closest reachable analog in this sequencer is `bytecode_hash_node` in [1](#0-0) , which recurses once per level of a `NestedIntList` tree (`bytecode_segment_lengths`) with **no depth bound**. This tree's shape is derived from the CASM output produced by compiling an attacker-declared Sierra program, and the hash is computed synchronously, in-process, on the class-manager/gateway path for every `declare` transaction, and again by every node re-executing/verifying that declare (Starknet OS re-execution / compiled-class-hash verification).

### Finding Description
`bytecode_hash_node` walks `NestedIntList::Node(children)` recursively via `iter_children().map(|child| bytecode_hash_node(...))`, one Rust stack frame per nesting level: [2](#0-1) . There is no maximum-depth check anywhere in `HashableNestedIntList`/`bytecode_hash`/`hash_inner`: [3](#0-2) .

`bytecode_segment_lengths` originates from the Cairo Sierra→CASM compiler's own segmentation of program bytecode (nested `if`/`match`/function structure produces nested segments). The Sierra program is fully attacker-controlled (an unprivileged declarer submits it), the compilation happens via a resource-limited subprocess for CPU time/memory (`ResourceLimits` in `apollo_compile_to_casm/src/compiler.rs` — [4](#0-3) ), but that sandbox only bounds CPU time and memory of the *compiler* process — it does not bound the recursion depth of the `NestedIntList` structure it emits, nor does it protect the *hash computation* that happens afterward, out-of-process, in `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs`): [5](#0-4) . The hash is computed with `executable_class.hash(&HashVersion::V2)`, invoking `hash_inner` → `bytecode_hash` → `bytecode_hash_node` recursively, with no depth guard, directly on the class-manager/gateway thread — no separate process, no stack-size override (only `native_blockifier`'s `.cargo/config.toml` bumps `RUST_MIN_STACK`, and that only pins the recursion budget for `MAX_ENTRY_POINT_RECURSION_DEPTH` execution calls, not for this hashing path): [6](#0-5) .

By crafting a Sierra program whose control-flow structure forces the compiler to emit a deeply and lopsidedly nested bytecode-segment tree (e.g., long chains of nested branches/functions), an attacker can make `bytecode_segment_lengths` arbitrarily deep, causing `bytecode_hash_node`'s recursion to exhaust the thread stack and crash the process computing the compiled class hash — this is executed by every sequencer/full node that declares, re-executes, or verifies the class (including Starknet OS re-execution).

### Impact Explanation
A crafted `declare` transaction can crash the class-manager/gateway component (or any full node computing/verifying the compiled class hash) via stack overflow, which in Rust is not a catchable panic — the process aborts. This is a denial-of-service reachable by a single unprivileged declarer, and because the hash computation happens identically on every honest node processing/verifying the same class, it can be used to crash the class-hash computation across the network for that class, disrupting confirmation of that and subsequent declare transactions (a network unable to confirm new transactions on the affected path).

### Likelihood Explanation
Likelihood is uncertain without confirming exactly how deeply/lopsidedly the Cairo compiler's segment-length structure can be forced to nest relative to the `max_bytecode_size`/`max_recursion_depth`-style limits already enforced elsewhere (e.g., `max_contract_bytecode_size`, `DEFAULT_MAX_BYTECODE_SIZE`). If the compiler bounds nesting depth roughly logarithmically in program size, an attacker may need an extremely large program (bounded by `max_bytecode_size`/`max_contract_class_object_size`) to reach thousands of nesting levels; if nesting is closer to linear in a particular crafted construct (e.g., deeply chained match arms), a much smaller program could suffice. This detail could not be fully verified from the indexed code alone.

### Recommendation
Bound the recursion in `bytecode_hash_node` (convert to an explicit iterative/worklist algorithm, or track and cap depth and reject/report an error beyond a safe limit) before computing hashes over compiler-supplied `NestedIntList` structures, and apply the same bound wherever `NestedIntList` is traversed recursively elsewhere in the codebase (e.g., `blockifier/src/execution/contract_class.rs`, `starknet_os` hint implementations for compiled classes) since these were also found to reference `NestedIntList` recursively.

### Proof of Concept
Not independently constructed/verified — building the exact Sierra source needed to force pathological `NestedIntList` nesting depth (and confirming the compiler indeed emits recursion proportional to that Sierra structure rather than being flattened/log-bounded) requires running the actual `cairo-lang` Sierra→CASM compiler binary, which was outside the scope of the static code index available here. This should be validated experimentally (compile a deeply nested test contract and observe the resulting `bytecode_segment_lengths` shape and the stack usage of `bytecode_hash_node` on it) before treating this as confirmed exploitable.

pub trait HashableNestedIntList: Clone {
    /// Returns true if this is a leaf node, false if it's a node with children.
    fn is_leaf(&self) -> bool;

    /// Returns the segment length stored in a leaf node. Panics if called on a non-leaf.
    fn get_segment_length(&self) -> usize;

    /// Returns an iterator over child nodes if this is a node, panics if called on a leaf.
    fn iter_children(&self) -> impl Iterator<Item = &Self>;
}

impl HashableNestedIntList for NestedIntList {
    fn is_leaf(&self) -> bool {
        matches!(self, NestedIntList::Leaf(_))
    }

    fn get_segment_length(&self) -> usize {
        match self {
            NestedIntList::Leaf(segment_len) => *segment_len,
            NestedIntList::Node(_) => panic!("Called get_segment_length on a Node"),
        }
    }

    fn iter_children(&self) -> impl Iterator<Item = &Self> {
        match self {
            NestedIntList::Leaf(_) => panic!("Called iter_children on a Leaf"),
            NestedIntList::Node(children) => children.iter(),
        }
    }
}

/// Computes the hash of the bytecode according to the provided segment structure.
/// The function iterates over the bytecode, partitioning it into segments as described
/// by the `HashableNestedIntList`. For each segment, it recursively computes a hash
/// using the provided `StarkHash` implementation. The final result is a hash representing the
/// entire bytecode structure, as required by Starknet's contract class hash computation.
fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
