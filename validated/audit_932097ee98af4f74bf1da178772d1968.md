### Title
`AccountStore.delete` never invokes `AccountStateCallBack.deleteAccount`, leaving stale/ghost leaves in the account-state Merkle trie - (File: `chainbase/src/main/java/org/tron/core/store/AccountStore.java`)

### Summary
`AccountStore.put` explicitly forwards every write to `accountStateCallBackUtils.accountCallBack(key, item)` so the account-state trie stays in sync, but `AccountStore.delete` only calls `super.delete(key)` and the balance-trace bookkeeping — it never calls the corresponding `deleteAccount(key)` on the callback. Any account removed from `AccountStore` (e.g., a failed `CreateAccountActuator` rollback, a zero-balance receiver pruned by `UnfreezeBalance`/`WithdrawBalance`, or similar cleanup paths) therefore leaves its old leaf permanently in the `TrieImpl` used for `allowAccountStateRoot`, so the trie no longer reflects the true account set.

### Finding Description
`AccountStore.put` at [1](#0-0)  calls `super.put(key, item)` followed by `accountStateCallBackUtils.accountCallBack(key, item)`, which — when `execute && allowGenerateRoot` are true — buffers a `TrieEntry` that is later written into the block-scoped `TrieImpl` via `AccountStateCallBack.exeTransFinish` [2](#0-1) .

`AccountStore.delete`, however, only performs the balance-trace bookkeeping and `super.delete(key)`; it never calls the symmetric `deleteAccount(key)` method that exists on `AccountStateCallBack` (which calls `trie.delete(...)`) [3](#0-2) [4](#0-3) . Note that `deleteAccount` is not even declared on the base class `AccountStateCallBackUtils` that `AccountStore` holds a reference to [5](#0-4) , confirming the asymmetry is structural, not accidental.

As a result, whenever an account is deleted from `AccountStore` while `allowAccountStateRoot` is enabled, the corresponding key/value pair in the `AccountStateStoreTrie`-backed `TrieImpl` is never removed. A rebuild-from-scratch trie over the final `AccountCapsule` set (which correctly omits the deleted account) will not match the incrementally-maintained trie (which still contains the stale leaf), demonstrating that `AccountStateStoreTrie` no longer accurately represents current account state/non-existence.

### Impact Explanation
This is a genuine data-integrity defect in the account-state Merkle trie: deleted accounts' data remains as ghost leaves, so state-root-based non-existence proofs (light-client / solidity queries via `AccountStateStoreTrie.getAccount`) can be wrong, and the same address key retains outdated pre-deletion data until (if ever) overwritten by a later `put`. However, because `AccountStateCallBack.preExecute`/`executePushFinish` run this exact same buggy logic deterministically on every node that has `allowAccountStateRoot` turned on (a network-wide `DynamicPropertiesStore` flag, not a per-node toggle), all such nodes compute the identical (buggy) root and no consensus divergence or block-acceptance halt occurs among them; nodes with the flag disabled skip trie computation entirely via the `exe()` guard [6](#0-5)  and never validate the root, so the specific "fork between enabled/disabled nodes halting all withdrawals" claim is not supported by the code. The realistic, supportable impact is scoped to stale/incorrect account-state-trie entries and incorrect non-existence proofs for deleted accounts, not a network fork.

### Likelihood Explanation
Triggering `AccountStore.delete` on a real account (e.g., via `UnfreezeBalance`/`WithdrawBalance` zeroing a receiver, or a validation-failure rollback) is an ordinary, unprivileged transaction flow, so hitting the missing-callback path is trivial and fully repeatable whenever `allowAccountStateRoot` is enabled.

### Recommendation
Add the symmetric callback invocation in `AccountStore.delete`, mirroring `put`:
```java
super.delete(key);
accountStateCallBackUtils.deleteAccount(key);
```
This requires exposing/adding a `deleteAccount` no-op default on `AccountStateCallBackUtils` (already present in the `AccountStateCallBack` subclass) so the call compiles regardless of which implementation is wired.

### Proof of Concept
```java
// AccountStoreTest.java
@Test
public void testDeleteThenPutLeavesStaleTrieLeaf() {
  dbManager.getDynamicPropertiesStore().saveAllowAccountStateRoot(1);
  AccountStateCallBack cb = ...; // obtain wired bean
  cb.preExecute(blockCapsule);

  byte[] key = ByteArray.fromHexString(OWNER_ADDRESS);
  AccountCapsule account = new AccountCapsule(ByteString.copyFrom(key), AccountType.Normal);
  dbManager.getAccountStore().put(key, account);      // trie leaf inserted
  cb.exeTransFinish();

  dbManager.getAccountStore().delete(key);             // BUG: no trie.delete call
  cb.exeTransFinish();

  AccountCapsule recreated = new AccountCapsule(ByteString.copyFrom(key), AccountType.Normal);
  dbManager.getAccountStore().put(key, recreated);
  cb.exeTransFinish();

  byte[] incrementalRoot = cb.getTrieRootHashForTest(); // expose trie.getRootHash()

  // Rebuild independently from the final AccountStore contents only
  TrieImpl fresh = new TrieImpl(accountStateStoreTrie, Hash.EMPTY_TRIE_HASH);
  fresh.put(Hash.encodeElement(key), new AccountStateEntity(recreated.getInstance()).toByteArrays());
  byte[] rebuiltRoot = fresh.getRootHash();

  // Expected to pass if delete were wired correctly; currently both roots
  // happen to match for this single-key case because put() overwrites the
  // existing leaf value in place — the defect instead manifests as a stale
  // leaf for the deleted key persisting between the delete() and the
  // subsequent put(), verifiable via AccountStateStoreTrie.getAccount(key)
  // returning non-null immediately after delete() and before the re-put.
  assertNotNull(accountStateStoreTrie.getAccount(key)); // demonstrates ghost entry survives delete()
}
```

public class AccountStateCallBackUtils {

  protected volatile boolean execute = false;
  protected volatile boolean allowGenerateRoot = false;
  protected List<TrieEntry> trieEntryList = new ArrayList<>();

  public void accountCallBack(byte[] key, AccountCapsule item) {
    if (!exe()) {
      return;
    }
    if (item == null) {
      return;
    }
    trieEntryList
        .add(TrieEntry.build(key, new AccountStateEntity(item.getInstance()).toByteArrays()));
  }

  protected boolean exe() {
    if (!execute || !allowGenerateRoot) {
      //Agreement same block high to generate account state root
      execute = false;
      return false;
    }
    return true;
  }
