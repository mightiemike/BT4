The pattern in `ark_binary_op_internal!` — popping `handle_2` before `handle_1` from the `VecDeque` via `safely_pop_arg!` — is the standard Move-native calling convention used consistently across all binary arithmetic natives in this module, not a bug specific to `sub_internal`. [1](#0-0) 

Move native function arguments arrive as a `VecDeque` in declaration order, and Aptos's convention for natives is to `pop_back`-style pop them in reverse (last parameter first) to restore correct positional order once both pops complete — `handle_1` still ends up holding the first Move parameter and `handle_2` the second. This exact pop order (`handle_2` first, then `handle_1`) is also used in `div_internal`, an inherently non-commutative operation, and it computes `element_1.div(element_2)` (i.e., first argument divided by second), which is the mathematically correct order, confirming the pop pattern correctly preserves argument order rather than reversing it. [2](#0-1) 

Since `sub_internal` follows the identical macro (`ark_binary_op_internal!`) with the same pop order, `element_1.sub(element_2)` correctly computes `a - b` where `a` is the first Move-level argument and `b` is the second — there is no argument-order inversion. [3](#0-2) 

The premise of the exploit question — that the pop order causes `sub_internal` to compute `element_2 - element_1` instead of `element_1 - element_2` — is incorrect. This is standard, correct native-argument handling shared identically across `add.rs`, `mul.rs`, `div.rs`, and `sub.rs`, and does not corrupt any accumulator root, transaction proof, event proof, state proof, or committed write set.
