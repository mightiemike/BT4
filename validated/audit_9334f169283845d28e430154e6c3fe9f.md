### Title
Event API's declared ledger version is not the version used to resolve Move type layouts for the response - (`api/src/events.rs`)

### Summary
`EventsApi::list` reports `latest_ledger_info` (captured earlier via `Account::new`/`get_latest_ledger_info`) as the ledger version bound to the response, and uses `latest_ledger_info.version()` to bound the event query itself. However, when building the JSON response it calls `Context::latest_state_view_poem`, which ignores the `ledger_info` argument for state-view construction and instead reads whatever the DB's *current* latest checkpoint is at the moment of the call.

### Finding Description
In `api/src/events.rs`: [1](#0-0) 

`ledger_version` (`latest_ledger_info.version()`) is correctly passed to `self.context.get_events(...)`, pinning which events are fetched. But the very next call, `self.context.latest_state_view_poem(&latest_ledger_info)`, is used purely to build the state view for `as_converter(...).try_into_versioned_events(&events)` — i.e. to resolve Move struct layouts needed to decode raw event bytes into typed JSON.

Looking at `latest_state_view_poem` in `api/src/context.rs`: [2](#0-1) 

The `ledger_info` parameter is used *only* to format an error if `self.db.latest_state_checkpoint_view()` fails — it is never used to pin the state-view version. `latest_state_checkpoint_view()` (`storage/storage-interface`) always returns the DB's current latest checkpoint at call time, not the checkpoint corresponding to `latest_ledger_info.version()`.

Because `latest_ledger_info` is captured earlier in the request path (inside `Account::new` during `get_events_by_creation_number`/`get_events_by_event_handle`), and `latest_state_view_poem` is invoked later, any commits/state-sync fast-forward that land on the node between those two points cause the state view used for type-layout resolution to be strictly newer than the version declared in the response's `LedgerInfo` header/body. If a module upgrade altering the emitting struct's layout occurred in that window, the raw event bytes (encoded per the old layout, since `get_events` is version-pinned) would be decoded using the new layout in `try_into_versioned_events`, producing corrupted or nonsensically-typed field values in an authenticated response that claims to represent `latest_ledger_info.version()`.

### Impact Explanation
This binds an authenticated API response to the wrong state-view/version for the purpose of Move value deserialization, which can silently corrupt returned event field data (type layout mismatch) while the response still claims correctness for `latest_ledger_info.version()`. This matches the "Authenticated API or state-view output bound to the wrong version, object, or proof context" impact category. The corruption is scoped to response construction (not to committed ledger state itself), but the returned data misrepresents which ledger version it was derived from.

### Likelihood Explanation
Under normal steady-state operation the window between capturing `latest_ledger_info` and calling `latest_state_view_poem` is extremely small (sub-millisecond), making a module-layout change land in that window unlikely. The window widens meaningfully during state-sync fast-forward, restore, or when the request is delayed inside `api_spawn_blocking` under load — matching the scenario described in the exploit question. Triggering an *observable* corruption additionally requires a struct-layout-changing module upgrade to commit in that exact window, which is a low-probability but non-zero race, not attacker-controlled with precision.

### Recommendation
Change `latest_state_view_poem` (and its callers in `events.rs`, `transactions.rs`, `accounts.rs`) to construct the state view at the *same pinned version* as `latest_ledger_info.version()` (e.g. via `state_view_at_version(ledger_info.version())`) rather than calling `latest_state_checkpoint_view()`, so that type-layout resolution is always consistent with the version declared in the response.

### Proof of Concept
1. In `EventsApi::get_events_by_creation_number`, after `Account::new` captures `account.latest_ledger_info` at version `V`, but before `api.list` reaches the `latest_state_view_poem` call, commit a transaction that upgrades the module defining the event's struct type, changing its field layout, advancing the DB's latest checkpoint to version `V+k`.
2. Observe that `get_events` still returns event bytes encoded per the version-`V` layout (correctly pinned via `ledger_version`).
3. Observe that `try_into_versioned_events` decodes those bytes using type layouts resolved from the version-`V+k` state view returned by `latest_state_view_poem`, producing a response whose `LedgerInfo` claims version `V` but whose event data is typed/decoded per version `V+k`'s module layout — an assertion comparing decoded fields against the expected version-`V` layout would fail.
