### Title
Permanent, unremovable `AccountId` binding in `AccountIdIndexStore` allows irreversible identifier squatting - (File: `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`)

### Summary
`SetAccountIdContract`/`SetAccountIdActuator` lets any account bind an arbitrary human-readable `accountId` to its address exactly once. That binding is written into `AccountCapsule.accountId` and indexed in `AccountIdIndexStore` keyed by the (lower-cased) id string, and there is no actuator, admin function, or any other code path anywhere in the codebase that can update or remove either the per-account `accountId` field or the corresponding entry in `AccountIdIndexStore`.

### Finding Description
`SetAccountIdActuator.validate()` explicitly forbids re-setting an id once present: [1](#0-0) 
and `execute()` unconditionally writes the id into both the account record and the global index with no corresponding delete/update path: [2](#0-1) 

The backing store, `AccountIdIndexStore`, only exposes `put`/`get`/`has` — inherited `delete` is never invoked from any actuator, and there is no `RemoveAccountId`/`UpdateAccountId` contract type in the protocol or actuator set: [3](#0-2) 

This mirrors the reported bug class exactly: a value is bound to a derived key (here, the lower-cased `accountId` string acting as the "key", analogous to the canonical-id/domain hash key in the Swap case) with a one-shot, privileged-by-transaction-authorship write, and the codebase provides no function to reverse, update, or clear that binding — regardless of whether the bound account is later compromised, the id was mistakenly chosen, or the id needs to be freed/reassigned.

### Impact Explanation
Once any address claims a given `accountId` string, that string is permanently and irrevocably reserved to that address for the lifetime of the chain. This is directly reachable by any unprivileged account (not a trusted role) via a standard, fee-bearing transaction. Concrete consequences:
- If the address that owns an `accountId` is later compromised (private key leaked) or becomes defunct, nobody can ever reclaim/free that identifier, and no governance or admin mechanism exists to correct it — a permanent state divergence between the intended and actual owner of a well-known identifier that downstream services (wallets/exchanges resolving accounts by `accountId`) may rely on via `Wallet.getAccountId`-style APIs.
- Malicious actors can pre-emptively squat high-value/short/branded `accountId` strings, permanently denying legitimate users or services the ability to use them — an irreversible griefing/DoS on a shared on-chain namespace with no remediation path.
- Unlike the Connext report (privileged admin key), this is worse in one respect: even the "owner" (the address itself) cannot free or change its own binding, so there is no self-service recovery either.

### Likelihood Explanation
High likelihood of being hit in practice: any account can call `SetAccountIdContract` at any time with an arbitrary lower-cased string id (subject only to length/character validation in `TransactionUtil.validAccountId`), so squatting or accidental permanent misconfiguration requires no special privilege or race condition — a single, ordinary transaction suffices, and the resulting immutable state persists forever once committed.

### Recommendation
Add a properly authorized `RemoveAccountId`/`UpdateAccountId` actuator (or extend `SetAccountIdActuator`) that allows the current owning account (via normal signature/permission checks) to clear its `accountId` from both `AccountCapsule` and `AccountIdIndexStore`, and/or to rebind to a new id after clearing the old one, following the same pattern later applied by the Connext `removeSwap()` fix (PR 2354).

### Proof of Concept
1. Account A sends `SetAccountIdContract{accountId: "popularname", ownerAddress: A}`.
2. `SetAccountIdActuator.execute()` stores `"popularname" -> A` in `AccountIdIndexStore` and sets `A.accountId = "popularname"` — see `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java` lines 45-53.
3. Account A's key is later lost/compromised, or A simply abandons the account. Account B, the rightful/intended holder of "popularname", attempts to claim it: `validate()` rejects it with `"This id has existed"` (line 95) forever, since no code path ever deletes the `AccountIdIndexStore` entry or resets `AccountCapsule.accountId`.
4. There is no other actuator, RPC, or HTTP endpoint in the codebase (confirmed via `AccountIdIndexStore` usage search) that clears this state — the binding is permanent for the life of the chain.

    byte[] lowerCaseAccountId = getLowerCaseAccountId(accountCapsule.getAccountId().toByteArray());
    super.put(lowerCaseAccountId, new BytesCapsule(accountCapsule.getAddress().toByteArray()));
  }

  public byte[] get(ByteString name) {
    BytesCapsule bytesCapsule = get(name.toByteArray());
    if (Objects.nonNull(bytesCapsule)) {
      return bytesCapsule.getData();
    }
    return null;
  }

  @Override
  public BytesCapsule get(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    if (ArrayUtils.isEmpty(value)) {
      return null;
    }
    return new BytesCapsule(value);
  }

  @Override
  public boolean has(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    return !ArrayUtils.isEmpty(value);
  }
