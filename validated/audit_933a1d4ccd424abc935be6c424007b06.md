## Finding: Integer truncation in `CalculateGasCost` causes universal gas fees to be silently evaded

### Title
Gas-fee truncation to zero in `CalculateGasCost` allows systemic fee evasion for UEA/CEA payload execution — ([File: x/uexecutor/keeper/fees.go])

### Summary
`x/uexecutor/keeper/fees.go`'s `CalculateGasCost` converts the feemarket's `LegacyDec` base fee to a whole-upc integer via truncating integer division before using it to compute the gas fee. Whenever the effective base fee per gas unit is less than one whole `upc` token (the realistic case for any properly-tuned EIP-1559-style fee market, where per-gas-unit prices are fractions of the native unit, analogous to gwei vs. ETH), the division rounds the base fee down to `0`, producing a `gasCost` of `0` and silently skipping fee deduction for every inbound `GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` execution.

### Finding Description
`CalculateGasCost` unwraps the 18-decimal `LegacyDec` base fee under the comment-stated assumption that "the base fee is always a whole number of upc": [1](#0-0) 

```go
baseFeeBig := baseFee.BigInt()
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
if maxFeePerGas.Cmp(baseFeeBig) < 0 { ... }
```

This assumption does not generally hold: `feemarket` base fee / min-gas-price parameters are ordinarily configured as small fractional amounts of the native denom to yield reasonable per-gas-unit pricing (the same way Ethereum prices gas in gwei rather than whole ETH). Any base fee value strictly less than `1e18` in its raw `LegacyDec` representation (i.e., less than 1 whole `upc` per gas unit) is truncated to `0` by the integer `Div`. `effectiveGasPrice` is then set to this truncated `0`: [2](#0-1) 

resulting in `gasCost = effectiveGasPrice * gasUsed = 0`, regardless of `gasUsed`.

`DeductGasFeesFromReceipt` then treats this as "nothing to charge" and returns without deducting or burning any fee: [3](#0-2) 

```go
gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
...
if gasCost.Sign() <= 0 {
    return nil
}
```

This function is invoked on every CEA/UEA payload execution path (see call sites in `x/uexecutor/keeper/evm.go` / `execute_inbound_gas.go` and covered by `test/integration/uexecutor/inbound_cea_*` tests), meaning any unprivileged user submitting an inbound with a `UniversalPayload` benefits from complete gas-fee evasion whenever the network's real (non-test-harness) base fee is set at realistic sub-1-upc granularity.

### Impact Explanation
This directly corrupts gas fee accounting — one of the explicitly allowed impacts ("corruption of ... gas fee accounting"). The protocol is expected to burn `gasUsed × effectiveGasPrice` from the recipient's account for every payload execution; instead, due to the truncation bug, the fee silently becomes `0` and no coins are transferred/burned, letting every user (not just an adversary) execute arbitrary UEA/CEA payloads gas-fee-free. This is a systemic, protocol-wide fund-accounting defect rather than an isolated edge case, and it is triggered purely by ordinary transaction submission with no privileged action required.

### Likelihood Explanation
High. The bug does not require any adversarial crafting — it is triggered automatically whenever the operative base fee (in whole-`upc` terms) is less than `1`, which is the normal/expected configuration for a functioning fee market (test/dev genesis files in this repo intentionally set unrealistically large base fees like `1000000000` upc, masking the bug in test environments, but any realistic mainnet-style base fee — a small fraction of 1 upc — reproduces it on every single inbound payload execution).

### Recommendation
Do not perform integer truncation on the `LegacyDec` base fee before multiplying. Keep the fee computation in `sdkmath.LegacyDec` (or scale `maxFeePerGas`/`gasUsed` up to the same 1e18 fixed-point precision) and only convert to a whole-token `big.Int` amount via proper rounding (e.g., `Ceil()`/`TruncateInt()` applied to the final `effectiveGasPrice * gasUsed` product, not to the per-unit base fee itself), analogous to how `MulDivGadget` should validate/preserve full precision before checking or applying its quotient rather than truncating an intermediate operand.

### Proof of Concept
1. Configure (or allow the feemarket's dynamic EIP-1559 adjustment to reach) a base fee of, e.g., `0.000000001000000000` upc (a realistic gwei-equivalent price, well below `1e18` in raw `LegacyDec` terms).
2. Submit any inbound with a `UniversalPayload` (`GAS_AND_PAYLOAD` or `FUNDS_AND_PAYLOAD`) with a valid `MaxFeePerGas` ≥ 0 and a payload that consumes non-trivial `gasUsed` on execution.
3. Observe in `CalculateGasCost`: `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` truncates the base fee to `0`; `effectiveGasPrice = 0`; `gasCost = 0`.
4. `DeductGasFeesFromReceipt` hits `gasCost.Sign() <= 0` and returns `nil` without deducting or burning any fee, even though `receipt.GasUsed > 0` — confirmed by the existing test suite's zero-fee-focused assertions never exercising sub-1-upc base fees (all repo genesis/test configs use base fees ≥ `1e9` upc, which happen to avoid the truncation).
