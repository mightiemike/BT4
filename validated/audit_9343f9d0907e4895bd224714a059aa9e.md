The strongest reachable analog to the Biconomy "drain the incentive pool without rebalancing by looping back source==destination, sender==receiver" bug is the documented meta-transaction (NEP-366) balance-refund design flaw in nearcore, where the account that benefits from an intentionally-failed inner action (the sender) is *not* the account that funded it (the relayer), and this is triggerable by a single unprivileged actor with no special access.

### Title
Meta-transaction sender can redirect relayer-funded deposits to itself by forcing inner-action failure - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
In NEAR's meta-transaction (NEP-366) flow, a relayer pays all gas and attached-deposit costs for actions signed by a `sender_id` (Alice) and addressed to a `receiver_id` (Bob). If an inner action carrying an attached deposit fails on the receiver's shard, the protocol refunds the deposit to the receipt's `predecessor_id`, which for `apply_delegate_action`-generated receipts is `sender_id` (Alice) rather than the relayer who actually funded the deposit [1](#0-0) . This mirrors the Biconomy pattern where an attacker chooses parameters (here: an inner action guaranteed to fail on the target) to redirect a payout meant for the actual value-source back to themselves.

### Finding Description
`Receipt::balance_refund_receiver` returns `predecessor_id` unless an explicit `refund_to` override is set on the receipt [2](#0-1) . When a `DelegateAction` is unwrapped in `apply_delegate_action`, the newly generated inner receipt's `predecessor_id` is set to `sender_id` (Alice), even though the relayer supplied all gas and attached balance for the actions [1](#0-0) . If that inner action fails during execution, `refund_unspent_gas_and_deposits` issues a `Receipt::new_balance_refund` to `balance_refund_receiver()`, i.e., to Alice, not the relayer [3](#0-2) . Nearcore's own documentation explicitly flags this as an economic hazard: "there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard" [4](#0-3) . Just as in the Biconomy bug — where specifying `toChainId == fromChainId` and `receiver == msg.sender` let the attacker redirect a rebalancing incentive to themselves without any real state change — here the meta-transaction sender fully controls the inner action (e.g., a function call to a nonexistent method, or one that predictably reverts) so that the "genuine cross-account transfer" the relayer intended never happens, yet the attached deposit is unconditionally routed back to the sender instead of the payer.

### Impact Explanation
A malicious meta-transaction sender can drain relayer-funded deposits: they request an inner action with an arbitrarily large attached deposit and a receiver/method guaranteed to fail, then collect the deposit-refund receipt themselves. This is unauthorized value movement from an honest relayer to an attacker-controlled account, reachable from a single submitted `SignedDelegateAction`/transaction pair with no special privileges — matching the "concrete unauthorized value movement" bar. Relayer services (a common component of the meta-transaction/gasless ecosystem) are the ones directly financially harmed, and any relayer that pre-validates only the "happy path" cost is exposed.

### Likelihood Explanation
Likelihood is high for any permissionless/low-trust relayer: the attacker needs only to control the contents of `delegate_action.actions` (which they always do, being the meta-tx sender) and pick a receiver/method that is not required to succeed. No race condition, validator collusion, or privileged access is needed — it is a deterministic protocol-level consequence of `predecessor_id` being set to `sender_id` on the generated inner receipt.

### Recommendation
Route balance refunds for actions originating from a `DelegateAction` to the relayer (the outer transaction's actual `signer_id`/gas payer) rather than to `sender_id`, mirroring how gas refunds already correctly go to the relayer. This can be implemented using the existing `refund_to` mechanism already present on `ActionReceiptV2`/`ActionReceipt` [2](#0-1)  by having `apply_delegate_action` set `refund_to` to the relayer when constructing the inner receipt, so that a failed action refunds the actual payer, not the meta-tx sender. Alternatively, require relayers to only trust actions structurally guaranteed to succeed, or cap/escrow deposits until execution outcome is known — but a protocol-level fix via `refund_to` closes the gap for all relayers uniformly.

### Proof of Concept
1. Relayer receives a `SignedDelegateAction` from Alice (`sender_id = alice`) targeting `receiver_id = bob`, containing a `FunctionCall` action to `bob::nonexistent_method` with a large attached deposit `D`, and wraps/submits it as the outer transaction (relayer pays gas + `D`).
2. `apply_delegate_action` builds the inner receipt with `predecessor_id = alice`, `receiver_id = bob` [5](#0-4) .
3. On Bob's shard, `bob::nonexistent_method` fails (method doesn't exist), so the deposit `D` is refunded via `Receipt::new_balance_refund(receipt.balance_refund_receiver(), D)` to `predecessor_id = alice` [3](#0-2) .
4. Alice receives `D` back, which the relayer funded and never gets back — net loss to the relayer, net unearned gain to Alice, with zero legitimate cross-account transfer having occurred.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
