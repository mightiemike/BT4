### Title
`clean_accounts()` panics via `unwrap()` on a possibly-missing storage entry during store-count calculation - (File: `accounts-db/src/accounts_db.rs`)

### Summary
The report's bug class is: a code path that is documented as "must never fail" (liquidation) instead calls a function that reverts/panics on an edge-case input (`rate == 0`), turning a benign condition into a hard failure of a critical, always-must-succeed operation. In agave's `AccountsDb::clean_accounts()` — the analogous "must always complete" background maintenance path that keeps the accounts index/storage consistent — the store-count calculation step unconditionally `unwrap()`s the result of looking up a storage entry that the accounts index says should exist, rather than handling a missing entry gracefully.

### Finding Description
In `AccountsDb::clean_accounts()`, after scanning candidate pubkeys, the function computes, for every rooted-but-reclaimable account, how many live references remain in each storage the account was written to: [1](#0-0) 

```rust
let mut key_set = HashSet::new();
key_set.insert(*pubkey);
let count = self
    .storage
    .get_account_storage_entry(*slot, account_info.store_id())
    .map(|store| store.count())
    .unwrap()
    - 1;
```

`get_account_storage_entry(...)` returns `Option<Arc<AccountStorageEntry>>`, and the code `unwrap()`s it directly instead of treating `None` as a recoverable case (e.g., skip this slot, or fall back to treating it as already-dead/zero-count). If the storage entry referenced by the accounts index for `(*slot, account_info.store_id())` is not present in `self.storage` at the moment this runs, the whole `clean_accounts()` call — and thus the calling thread (`AccountsBackgroundService`, or the direct-call path when `is_startup` is true) — panics with `called 'Option::unwrap()' on a 'None' value'`.

The surrounding code base explicitly documents that such races between the storage map and the accounts index are possible. The comment block describing the Shrinker/Cleaner/Purger interplay spells out that the storage map entry for a slot can be removed (S4/C3/P2) while the accounts index may still transiently reference the old `(store_id, offset)` for that slot in some interleavings, and states "it's a race condition ... retrying from R1 is safu" for the read path: [2](#0-1) 

That read path (`do_load`) is written defensively to retry rather than unwrap. The `clean_accounts()` store-count computation, by contrast, does not retry or defer — it hard-panics on the very same class of race between index state and the storage map. Unlike the liquidation revert (which merely blocks one liquidation transaction), a panic here kills `clean_accounts()`, which is scheduled continuously as part of accounts background maintenance and is required to keep the accounts index/storage from growing unboundedly and staying consistent for both replay and snapshot generation.

### Impact Explanation
`clean_accounts()` is core, always-must-succeed accounts-database maintenance: it runs continuously on every validator to reclaim dead accounts, is a prerequisite for snapshot generation correctness (removing already-purged entries so hashing/capitalization calculations are consistent), and directly parallels the "liquidation must never fail" invariant from the source report (a maintenance/consistency operation on a system that must not fail even under adverse or edge-case conditions). A panic in this path crashes the validator process (denial of node availability) and, if triggered under a race window that is more likely to occur during high load (rapid shrink/clean/purge interleavings), can affect many/most nodes running the same code, since it's an unprivileged, protocol-level path with no privileged-role dependency.

### Likelihood Explanation
The codebase's own internal documentation acknowledges that storage-map entries and accounts-index entries for a slot can be transiently out of sync due to concurrent shrink/purge/clean operations. This `unwrap()` sits in exactly that intersection (looking up a storage entry by `(slot, store_id)` obtained from the accounts index) but, unlike the neighboring `do_load()` read path, has no retry or graceful `None` handling. Because `clean_accounts()` runs unconditionally as background maintenance on every validator (not gated behind an optional feature or privileged role), any window where this race is hit turns into a guaranteed node panic rather than a benign retry.

### Recommendation
Mirror the liquidation fix's spirit ("never fail a must-succeed operation because of a transient/edge condition") by not `unwrap()`ing the `Option` returned by `get_account_storage_entry`. Instead:
- If the storage entry for `(*slot, account_info.store_id())` is missing, treat the count conservatively (e.g., skip inserting into `store_counts` for this slot/pubkey, or treat it as already-zero/dead) rather than panicking.
- Alternatively, add the same kind of racy-retry logic used in `do_load()`/`read_index_for_accessor_or_load_slow` so that a transient race between the index and storage map does not crash the cleaner thread.

### Proof of Concept
1. Trigger `AccountsDb::clean_accounts()` concurrently with a shrink/purge operation that removes a storage entry for a slot referenced by candidate pubkeys collected in the same `clean_accounts()` call (the accounts index still lists `(slot, store_id)` for those pubkeys from the just-completed scan phase, while `self.storage` no longer contains that entry due to the concurrent purge/shrink removing it, per the S3/C3/P2 storage-map-removal race documented at `accounts-db/src/accounts_db.rs:3612-3656`).
2. When `clean_accounts()` reaches the store-count computation loop and calls `self.storage.get_account_storage_entry(*slot, account_info.store_id())` for that slot, the lookup returns `None`.
3. The `.unwrap()` at `accounts-db/src/accounts_db.rs:2063` panics, crashing the accounts background service thread (and, depending on panic handling, the validator process), analogous to how the missing revert-fallback for `rate == 0` in the source report crashed the "must never fail" liquidation path.
