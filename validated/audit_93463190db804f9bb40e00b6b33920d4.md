## Analysis

The MonadBFT report describes a mismatch between a chunk's byte budget and its gas budget: a transaction can occupy a large share of the byte-limited resource while burning only a small fraction of the gas budget, letting an attacker fill block space "cheaply." Nearcore has a structurally identical split: `prepare_transactions_extra` in `chain/chain/src/runtime/mod.rs` enforces two independent, unrelated budgets when packing transactions into a chunk — a gas budget (`transactions_gas_limit`, from `chunk_tx_gas_limit`) and a byte budget (`size_limit = combined_transactions_size_limit`), each checked separately with no cross-scaling between them. [1](#0-0) 

The byte counted against that budget is `size_for_limits`, which from `PostQuantumSignatures` onward equals the full wire size of the signed transaction (body + signature, `wire_size()`), because ML-DSA-65 signatures/pubkeys are large (~3.3 KiB signature, ~1952-byte raw pubkey) and were previously invisible to the legacy `get_size()`. [2](#0-1) 

The fix that makes `combined_transactions_size_limit` count wire bytes correctly is only half of the story: the codebase explicitly documents that the *gas* pricing for those extra bytes was deliberately deferred. `AddKey`/`DeleteKey` actions carrying an ML-DSA-65 public key put ~1952 bytes on the wire (and thus into `size_for_limits`), but no per-byte gas fee for the public key itself exists — the only per-byte fee on `AddKey` is for `method_names`, confirmed in `permission_send_fees`/`permission_exec_fees`: [3](#0-2) [4](#0-3) 

and the design doc records this as a known, deferred gap: [5](#0-4) 

Additionally, the storage-stake charge for an access key uses `PublicKey::trie_id_len()`, which is only 33 bytes for an ML-DSA-65 key (the on-trie form stores only a hash), versus the ~1952-byte wire form — so the balance an attacker must lock is also based on the tiny trie footprint, not the wire footprint that consumes the byte-limited chunk resource. [6](#0-5) 

### Title
Gas/fee bypass in chunk transaction packing via byte-heavy, gas-cheap `AddKey`/`AddFullAccessKey` actions using ML-DSA-65 public keys - ([File: chain/chain/src/runtime/mod.rs])

### Summary
`prepare_transactions_extra` bounds chunk transaction packing by two independent budgets, gas (`transactions_gas_limit`) and bytes (`combined_transactions_size_limit`), exactly as in the reported MonadBFT issue. Nearcore's byte accounting (`size_for_limits`/`wire_size`) correctly counts the large ML-DSA-65 public key/signature bytes a transaction puts on the wire, but the gas fee schedule for `AddKey`/`AddFullAccessKey`/`AddFunctionCallKey` actions has no per-byte term for the public key itself, and the storage-stake charge for the same action is computed from the much smaller on-trie hash length (`trie_id_len()`), not the wire length. A signer can therefore submit `AddKey` actions carrying arbitrary (unowned, freshly generated) ML-DSA-65 public keys to consume a disproportionate share of the byte-limited chunk/witness budget while paying gas and locking storage proportional only to the fixed action base fee and the 33-byte trie footprint, not the ~1952-byte wire payload actually occupying the shared, size-limited resource.

### Finding Description
`prepare_transactions_extra` stops packing a chunk when either `total_gas_burnt >= transactions_gas_limit` or `total_size >= size_limit` (`size_limit = runtime_config.witness_config.combined_transactions_size_limit`), and per-transaction it also enforces `total_size.saturating_add(tx_peek.size_for_limits(...)) > size_limit`. These two budgets are unrelated: nothing ties gas burnt to bytes consumed. `size_for_limits` (and `max_transaction_size`) count the transaction's full wire size (`wire_size()` = body + signature) from `PostQuantumSignatures` onward, so a transaction's ML-DSA-65 signature and any ML-DSA-65 public keys it carries in `AddKey` actions count fully against the byte budget. However, the fee functions that price `AddKey`/`AddFullAccessKey`/`AddFunctionCallKey` (`permission_send_fees`, `permission_exec_fees`) only add a per-byte fee for `method_names`; there is no per-byte fee keyed to the size of the public key itself, regardless of key type. The doc for the feature explicitly flags this: "A per-byte component on `AddKey`/`DeleteKey` for the ~1952-byte pubkey they carry on the wire is in the same deferred bucket" as the deferred pricing decision. Separately, the storage stake an account must lock to hold the new key is derived from `PublicKey::trie_id_len()`, which for an ML-DSA-65 key is only 33 bytes (only the SHA3-256 hash is stored on the trie) versus the actual ~1952-byte raw key transmitted on the wire and counted by `size_for_limits`. The result is a transaction whose gas cost and locked-balance cost scale with a small, fixed quantity, while its footprint against the byte-limited chunk/witness resource scales with the (unpriced) public-key size — the same "cheap byte occupancy, disproportionately low resource cost" pattern the MonadBFT report describes for calldata versus the proposal's byte/gas limits.

### Impact Explanation
An attacker can build a transaction with up to `max_actions_per_receipt` `AddKey` actions (each with a distinct, freshly generated, unowned ML-DSA-65 public key requiring no private-key possession to add), each contributing ~1952 bytes of wire size to `size_for_limits`/`combined_transactions_size_limit` while paying only the fixed `action_add_full_access_key`/`action_add_function_call_key` base fee and locking storage stake sized to 33 bytes (trie hash) per key. Submitting several such transactions (optionally from multiple accounts) lets an attacker consume a large fraction of the `combined_transactions_size_limit`/`max_transaction_size` byte budgets for a small gas cost relative to legitimate transactions of comparable wire size, crowding out other users' transactions from being packed into chunks — a fee/gas bypass on the byte-limited chunk-packing resource, directly analogous to the reported EVM calldata block-stuffing bug.

### Likelihood Explanation
Any unprivileged transaction signer can construct such transactions without any special privilege: generating ML-DSA-65 keypairs and issuing `AddKey` against one's own account is a normal, permitted operation, and no per-byte gas or storage charge currently exists to disincentivize using large numbers of ML-DSA-65 keys purely to inflate wire size cheaply. The only cost is the (comparatively small) storage stake for the 33-byte trie hash per key and ordinary base action gas fees.

### Recommendation
Add a per-byte gas fee term (and/or per-byte storage-stake accounting based on wire size rather than `trie_id_len()`) for the public key payload of `AddKey`/`AddFullAccessKey`/`AddFunctionCallKey`/`DeleteKey` actions, mirroring the approach already used for `ml_dsa_65_verification_cost` on the outer signature, so that the gas/stake an attacker pays for a key scales with the bytes it actually occupies in `size_for_limits`/`combined_transactions_size_limit`, closing the gap the design doc already flags as deferred.

### Proof of Concept
1. Generate N (e.g. up to `max_actions_per_receipt`) distinct ML-DSA-65 keypairs; no private key material needs to be controlled by anyone but the attacker.
2. From a single funded account, submit a transaction with N `Action::AddKey` (`AccessKeyPermission::FullAccess`) actions, each using one generated ML-DSA-65 public key.
3. Observe: `SignedTransaction::size_for_limits` for this transaction is dominated by `N * ~1952` bytes of raw public-key wire data (see `test_wire_size_ml_dsa_signature_is_large`, `core/primitives/src/transaction.rs:1238-1252`, which shows a single ML-DSA-65 signature alone adds >3 KiB invisible to `get_size`), while the gas charged is `N * action_add_full_access_key` base fee only (`runtime/runtime/src/config.rs:256-288`), with no per-byte term for the keys, and the storage stake locked is `N * storage_amount_per_byte * 33` (via `trie_id_len()`), not `N * storage_amount_per_byte * ~1952`.
4. Repeat across accounts/transactions until `combined_transactions_size_limit` is consumed by such transactions in `prepare_transactions_extra` (`chain/chain/src/runtime/mod.rs:962-965,1012-1018`), for a small fraction of the gas that an equivalent-byte-footprint, "priced" transaction (e.g. `FunctionCall` with equivalent argument bytes, priced at `action_function_call_per_byte`) would cost.

    ///
    /// [`Self::get_size`] counts only the inner `Transaction` body, omitting
    /// the signature - ~65 B for ed25519 but up to ~3.3 KiB for ML-DSA-65.

### Size axis (accounting done, pricing deferred)

`SignedTransaction::get_size()` counts only the inner `Transaction` body, so it
under-counted every ML-DSA-65 tx by its ~3.3 KiB signature - including inside
`combined_transactions_size_limit`, the bound on transaction bytes carried by
the `ChunkStateWitness`. `SignedTransaction::wire_size()` now returns the full
borsh length (signature included), and `size_for_limits(protocol_version)`
selects it for the `max_transaction_size` and `combined_transactions_size_limit`
gates from `PostQuantumSignatures` onward (version-gated to keep chunk
production deterministic across the boundary). The mempool counts `wire_size()`
unconditionally, since it physically buffers the signature. *Pricing* the extra
size - e.g. a per-wire-byte gas surcharge at conversion time, mirroring the
verify cost - is deferred: the accounting fix closes the witness-honesty gap on
its own, independent of any later pricing decision. A per-byte component on
`AddKey`/`DeleteKey` for the ~1952-byte pubkey they carry on the wire is in the
same deferred bucket.
