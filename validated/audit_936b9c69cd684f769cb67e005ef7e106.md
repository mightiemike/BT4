### Title
`ChainMeta.MedianIndex` is computed against the full (stale-inclusive) vote history, causing `QueryChainMeta` consumers to read a gas price that does not match the value actually applied on-chain - ([File: x/uexecutor/keeper/chain_meta.go])

### Summary
The external report's core defect pattern is: a contract computes a critical accounting value using a naive/unfiltered quantity (`totalSupply`) instead of the semantically-correct, filtered quantity (`getActualSupply`), producing wrong results for downstream consumers. Push Chain's `x/uexecutor` chain-meta oracle has the same class of defect: the value actually applied to the EVM oracle (`CallUniversalCoreSetChainMeta`) is computed from a **staleness-filtered** subset of votes (`fresh`), but the persisted `ChainMeta.MedianIndex` field (and therefore `ChainMeta.Prices[MedianIndex]` as read via the `ChainMeta`/`AllChainMetas` gRPC queries) is computed against the **full, unfiltered** `entry.Prices` slice, which can include stale votes from validators who haven't refreshed.

### Finding Description
In `VoteChainMeta` (`x/uexecutor/keeper/chain_meta.go:62-189`), two different "median" computations exist over the same logical data:

1. The value actually written to the EVM oracle uses only fresh votes: [1](#0-0) 
filtered into `fresh`, then: [2](#0-1) 
`medianPrice`/`medianChainHeight` (computed only from `fresh`) are what get pushed via `CallUniversalCoreSetChainMeta` and become `LastAppliedChainHeight`.

2. But the stored `entry.MedianIndex` — the field returned by the `ChainMeta` and `AllChainMetas` queries — is computed against the **entire unfiltered** `entry.Prices` array, explicitly documented as "best-effort": [3](#0-2) 

The test suite itself confirms this divergence is a known, accepted discrepancy rather than a fixed invariant — a test explicitly demonstrates that `stored.Prices[stored.MedianIndex]` diverges from the actually-applied EVM value and that callers must bypass the stored field and query the EVM contract directly to get the correct number: [4](#0-3) 

Any unprivileged off-chain consumer (relayers, indexers, the `puniversald` binary itself via `Client.GetGasPrice`, wallets, or third-party tooling) that queries `ChainMeta`/`AllChainMetas` and reads `Prices[MedianIndex]` — the natural, documented way to read "the chain's gas price" from this module — receives a value that can differ arbitrarily from the value the protocol has actually committed to the EVM gas-price oracle, because it is polluted by stale votes that should have been excluded.

### Impact Explanation
This does not directly permit theft of funds, unauthorized minting, or forged ballot state — the EVM-applied value (`LastAppliedChainHeight`/on-chain `gasPriceByChainNamespace`) remains correct and is what the protocol's own fee/refund accounting paths use. The impact is limited to **misinformation to external, unprivileged consumers of the query API** (mirroring the Sherlock report's own Medium-severity classification for "wrong price assumptions"): anyone building tooling, gas estimation, or relayer logic that trusts `ChainMeta.Prices[ChainMeta.MedianIndex]` instead of reading the EVM oracle directly can compute an incorrect gas price, which could lead to under/over-priced outbound transactions if that misread value ever gets fed into gas-limit/fee decisions off-chain (e.g. in `puniversald`'s legacy `GetGasPrice` path against the deprecated `GasPrice`/`MedianIndex` fields, which has the identical structural flaw and is defended only by an out-of-bounds fallback, not a staleness filter).

### Likelihood Explanation
Likelihood is low-to-medium: it requires (a) an unprivileged consumer to actually rely on the `MedianIndex` field of the query response rather than reading the applied EVM oracle value, and (b) enough validators to go stale (>300s without voting) while others keep voting, which is a routine, easily-triggerable operational condition (not an attacker-controlled exploit per se — a stale validator just needs to stop voting, which any external observer can induce by watching for it, not manipulate directly). No malicious/privileged assumption is required to trigger the divergence; it happens under entirely honest-validator conditions whenever vote freshness diverges, which is explicitly acknowledged and tested in the repository's own test suite.

### Recommendation
Compute and persist `MedianIndex` (and ideally store the fresh-filtered price/height directly, e.g., add `AppliedPrice`/`AppliedMedianIndex` fields) using the same `fresh` filtered set used for the EVM write, so that `ChainMeta.Prices[ChainMeta.MedianIndex]` always matches `LastAppliedChainHeight`/the actual on-chain applied value. Alternatively, deprecate/remove the misleading `MedianIndex` field from the query response entirely and document that consumers must read the EVM `gasPriceByChainNamespace` view function for the authoritative price, closing the gap between "what the query returns" and "what the protocol actually uses."

### Proof of Concept
1. Set up 3 Universal Validators, `chainMetaMinVotesForFirstWrite = 3`.
2. All 3 vote at time T with prices `[100, 300, 200]`; bootstrap succeeds, `LastAppliedChainHeight` and EVM oracle now reflect median `200` (this is asserted in `test/integration/uexecutor/vote_chain_meta_test.go:221-263`).
3. Advance block time by 301s (past `chainMetaVoteStalenessSeconds`), so all 3 previous votes are now stale.
4. Only validator 0 re-votes with price `900`. The EVM oracle is updated to `900` (only fresh vote), confirmed via `CallEVM(... "gasPriceByChainNamespace" ...)`.
5. Query `ChainMeta`/`AllChainMetas` via gRPC and read `stored.Prices[stored.MedianIndex]`. This still reflects the full unfiltered slice `[100, 300, 200, 900]` median (i.e., not `900`), diverging from the actual applied EVM value — exactly the discrepancy the repository's own test comment calls out at line 253-254: "MedianIndex on the stored entry reflects the full-slice median... not the stale votes."
