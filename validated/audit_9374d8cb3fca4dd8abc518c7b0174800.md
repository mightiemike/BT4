### Title
Unbounded `feeLimit` field on non-contract transactions causes integer overflow in `BlockResult.gasLimit` JSON-RPC field - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/types/BlockResult.java])

### Finding Description
`BlockResult`'s constructor unconditionally sums `transaction.getRawData().getFeeLimit()` for every transaction in a block into a `long gasLimitInBlock`, regardless of the transaction's contract type: [1](#0-0) [2](#0-1) 

The result is then exposed as a JSON-RPC hex `QUANTITY` via `ByteArray.toJsonHex(gasLimitInBlock)` with no overflow guard: [3](#0-2) 

The only place `feeLimit` is bounds-checked against `DynamicPropertiesStore.getMaxFeeLimit()` is inside `VMActuator.create()` and `VMActuator.call()`, which only execute for `CreateSmartContract` and `TriggerSmartContract` transaction types: [4](#0-3) [5](#0-4) 

For every other contract/transaction type (e.g. `TransferContract`), the `feeLimit` field of `Transaction.raw` is never validated by any actuator, so an attacker can set an arbitrary raw protobuf `int64` value (up to `Long.MAX_VALUE`) on a cheap, unrelated transaction (e.g. a 1-sun TRX transfer) and it will pass all validation and be included in a block unmodified, since nothing checks/caps `feeLimit` for non-VM transaction types. Because `BlockResult` sums `feeLimit` for *all* transactions in the block indiscriminately, only two or three such crafted transactions in one block are needed to overflow a signed 64-bit `long` and wrap `gasLimitInBlock` negative, which is then rendered via `ByteArray.toJsonHex` into a bogus (small/negative-looking) hex `QUANTITY` for the public `eth_getBlockByNumber`/`eth_getBlockByHash` JSON-RPC `gasLimit` field.

### Impact Explanation
Downstream JSON-RPC consumers (wallets, explorers, fee-estimation tooling) that read the block's `gasLimit` field to gauge available energy/fee capacity for a block will receive a corrupted, wrapped value (potentially negative when interpreted as a hex `QUANTITY`), causing systematic misaccounting of per-block TRX fee/energy exposure. This is a public-API data-integrity issue rather than consensus corruption, since `gasLimitInBlock` is only used for JSON-RPC response construction and not stored on-chain or used in consensus/fee accounting.

### Likelihood Explanation
Feasible and repeatable by any unprivileged account: crafting a `TransferContract` (or other non-VM contract type) transaction with `rawData.feeLimit` set to `Long.MAX_VALUE / 2 + 1` (or similar) requires no special privileges, balance requirements are unaffected (bandwidth/fee for the transfer itself is normal), and there is no validation path (`TransactionUtil`, `TransactionCapsule`, or any generic actuator) that rejects an out-of-range `feeLimit` for non-VM transaction types based on the code reviewed. An attacker only needs to get two or more such transactions packed into the same block (trivial, since block producers do not special-case `feeLimit` for inclusion ordering).

### Recommendation
- Validate `feeLimit` bounds for all transaction types at broadcast/pre-execution time (not just inside `VMActuator`), e.g. in `TransactionCapsule` or a common pre-validation step, rejecting values outside `[0, getMaxFeeLimit()]` regardless of contract type.
- In `BlockResult`, use an overflow-safe accumulation (e.g. `Math.addExact` inside a try/catch, or clamp/saturate) when computing `gasLimitInBlock`, and only include `feeLimit` from transaction types where it is semantically meaningful (VM contract calls/creations), matching the pattern already used in `JsonRpcApiUtil.calcFeeLimit` which throws on overflow instead of silently wrapping. [6](#0-5) 

### Proof of Concept
```java
// Pseudocode integration test outline for BlockResultTest
@Test
public void gasLimitInBlockOverflowsWithNonContractFeeLimit() {
  // Craft N TransferContract transactions (not TriggerSmartContract/CreateSmartContract)
  // each with rawData.feeLimit = Long.MAX_VALUE / 2 + 1
  Transaction tx1 = buildTransferWithFeeLimit(Long.MAX_VALUE / 2 + 1);
  Transaction tx2 = buildTransferWithFeeLimit(Long.MAX_VALUE / 2 + 1);

  Block block = buildBlockWithTransactions(tx1, tx2);

  BlockResult result = new BlockResult(block, false, wallet);

  long decoded = ByteArray.jsonHexToLong(result.getGasLimit());
  // Expected (bug): decoded is negative due to silent long overflow
  assertTrue("gasLimit must not silently wrap negative", decoded >= 0);
}
```
Expected current behavior: `gasLimitInBlock` wraps to a negative `long`, and `ByteArray.toJsonHex` encodes that negative value as a corrupted hex `QUANTITY`, violating the invariant that public JSON-RPC numeric fields must not silently overflow.

  /**
   * Compute feeLimit = gas * energyFee with overflow protection. A gas value large enough to
   * overflow a signed 64-bit feeLimit is rejected as invalid-params instead of silently wrapping

   */
  public static long calcFeeLimit(long gas, long energyFee) throws JsonRpcInvalidParamsException {
    try {
      return StrictMathWrapper.multiplyExact(gas, energyFee);
    } catch (ArithmeticException e) {
      throw new JsonRpcInvalidParamsException("invalid gas: fee limit overflow");
