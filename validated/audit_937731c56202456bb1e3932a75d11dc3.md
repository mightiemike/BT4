### Title
Missing domain separation in `ValidateMultiSign` precompiled contract signature hash enables cross-contract/cross-context signature replay - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract, which TVM smart contracts on java-tron use to verify off-chain-produced multisig approvals against an account's `Permission`, builds its signature hash from only `(targetAddress, permissionId, data)` and never includes the calling/verifying contract's own address or a chain/network identifier. This is the same root cause described in the external report: a signature proof constructed without a domain separator (chain id + verifier/contract address) can be replayed outside the context it was intended for.

### Finding Description
`ValidateMultiSign.execute()` computes the message hash that recovered signatures are checked against as: [1](#0-0) 

```
DataWord[] words = DataWord.parseArray(rawData);
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter
    .getInstance().isECKeyCryptoEngine(), combine);
```

The `address` field here is the *target account* whose `Permission` is being checked, not the address of the calling contract that invoked the precompile, and no chain/network identifier is mixed in at all. As a result, the same `(address, permissionId, data)` triple — and therefore the identical signature — is valid input regardless of which smart contract on the chain calls `ValidateMultiSign`, and (because there is no chain id) regardless of which java-tron network (Mainnet, Nile, Shasta, or any private/forked network running the same code) the call happens on. This mirrors exactly the bug class in the report: `hashForKYC()`/`purchaseAllowed()` needed `chain.id` and the verifying contract address mixed into the hash to prevent cross-domain reuse; here `recoverAddrBySign()`/`Sha256Hash.hash(combine)` has the equivalent gap. [2](#0-1) 

The sibling precompile `BatchValidateSign` is even more permissive: it takes the message hash directly from caller-supplied `data` with zero internal domain binding, delegating all domain separation responsibility to the calling Solidity contract: [3](#0-2) 

Both precompiles are reachable by any contract invoked via an ordinary broadcast `TriggerSmartContract` transaction, i.e. by any anonymous caller who can trigger a contract that uses these primitives for off-chain-signature-based authorization (KYC gating, multisig approvals, whitelist gating, etc.) — the exact class of contract functionality (`purchaseAllowed()`-style KYC/whitelist checks) the original report was about.

### Impact Explanation
Any DApp deployed on java-tron that relies on `ValidateMultiSign`/`BatchValidateSign` to authorize an action based on an off-chain-signed approval (e.g. KYC sign-off, whitelist proof, meta-transaction authorization) is exposed to signature replay: a signature obtained for use by one contract, or on one java-tron network, can be resubmitted against a different contract, or replayed on a sibling network sharing the same account-address derivation, as long as the `(address, permissionId, data)` triple collides or, for `BatchValidateSign`, as long as the raw hash matches. This can lead to unauthorized account operations or bypass of application-level access control (asset/accounting corruption at the contract layer), consistent with the "unauthorized account operation" / "asset or accounting corruption" impact classes for precompiled-contract analogs.

### Likelihood Explanation
Exploitability depends on application-layer contracts using these primitives without adding their own domain separation (contract address / chain id) into the signed payload — which is exactly the failure mode the original report flagged in `ERC20Distribution`/`ERC20DistributionNative`. Because java-tron's `ValidateMultiSign` precompile itself does not enforce or even expose a chain-id/contract-address binding, any contract author who signs off application data the same way the report's vulnerable contracts did will inherit the identical cross-domain replay weakness, and the attack is executable by any unprivileged actor via a normal broadcast transaction calling the vulnerable contract.

### Recommendation
Extend the internal hash construction in `ValidateMultiSign` (and document/encourage equivalent practice for `BatchValidateSign` callers) to bind the signed payload to a domain separator analogous to EIP-712's, e.g. include the calling contract's address (`msg.sender`/`this` from the VM's perspective) and the network/chain identifier (`chain.id` equivalent, e.g. `CommonParameter.getInstance().getChainId()` if available, or a distinguishing genesis/network constant) alongside `address`, `permissionId`, and `data` before hashing in `PrecompiledContracts.java`'s `ValidateMultiSign.execute()`.

### Proof of Concept
1. Deploy the same or structurally similar contract `C1` on two java-tron networks (or deploy `C1` and `C2` on the same network) that both call `ValidateMultiSign(address, permissionId, data)` to gate a privileged action.
2. Obtain (via off-chain signing, e.g. as part of a legitimate KYC/whitelist flow for `C1`) a valid signature `sig` over `sha256(address || permissionId || data)` for account `address` and `permissionId`.
3. Submit `sig` to `C2` (or to `C1` deployed on the second network) as the approval for its own gated action, using the identical `(address, permissionId, data)` triple.
4. `ValidateMultiSign.execute()` in `PrecompiledContracts.java` recomputes the same hash, `recoverAddrBySign()` recovers the same address, `TransactionCapsule.getWeight()` finds sufficient weight, and the precompile returns `dataOne()` (success) — authorizing the action on `C2`/the second network even though the signature was never intended for that context.
