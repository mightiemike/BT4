## Analysis

The Lido report describes a class of bug: **a caller's deposit gets absorbed into a contract's balance during a multi-step operation, with no code path to reclaim it when an intermediate step fails.** The closest reachable analog in `nearcore` is the `near-wallet-contract` (the NEP-518 Wallet Contract that every ETH-implicit account runs, and which is directly reachable by any relayer/RPC caller submitting `rlp_execute`).

### Root cause

`rlp_execute` is `#[payable]` and tracks the caller's (typically the relayer's) attached deposit via `CallerDeposit::new`, whose whole purpose is documented as: *"This allows us to refund the caller's deposit if the cross-contract call fails."* [1](#0-0) 

The refund is correctly implemented in the **final** callback: [2](#0-1) 

However, for multi-step flows (ERC-20 emulation and eth-implicit-to-eth-implicit address checks), there are **intermediate** callbacks that run *before* `rlp_execute_callback`. If the intermediate cross-contract call itself fails, these callbacks return early **without ever refunding `caller_deposit`**:

- `address_check_callback` (checks the address registrar before transferring to another eth-implicit account) — on `PromiseResult::Failed` it returns immediately, dropping `caller_deposit`: [3](#0-2) 

- `nep_141_storage_balance_callback` (checks `storage_balance_of` before an ERC-20/NEP-141 transfer) — same pattern, on failure it returns immediately without touching `caller_deposit`: [4](#0-3) 

In both cases the attached NEAR deposit was already credited to the Wallet Contract account's balance when the `FunctionCall` receipt for `rlp_execute` was processed by the runtime (this happens automatically, independent of contract logic). Once these callbacks return without scheduling a transfer back to `caller_deposit.account_id`, **there is no other code path in the contract that can move that balance back to the depositor** — only the wallet owner's Secp256k1 key (via further `rlp_execute` calls) can move that NEAR again, and that key belongs to a different party than the relayer who paid the deposit.

### Title
Wallet Contract silently absorbs relayer's `caller_deposit` with no refund path when the intermediate cross-contract call (address-registrar lookup or NEP-141 `storage_balance_of`) fails - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEP-518 Wallet Contract accepts a `payable` deposit from an external caller (typically a relayer) in `rlp_execute`, tracked as `CallerDeposit`, intended to be refundable if the emulated transaction fails. The refund logic exists only in the final `rlp_execute_callback`. The two earlier-stage callbacks, `address_check_callback` and `nep_141_storage_balance_callback`, each perform a preliminary cross-contract call (to the address registrar, or to a NEP-141 token's `storage_balance_of`) before the actual action is dispatched. If that preliminary call fails, both callbacks return an `ExecuteResponse` directly, bypassing the refund logic entirely, and `has_in_flight_tx` is reset to `false` with no promise scheduled to return the deposit.

### Finding Description
`CallerDeposit` is created in `inner_rlp_execute` whenever the predecessor differs from the current (wallet) account and a nonzero deposit is attached [5](#0-4) . It is threaded through `address_check_callback` and `nep_141_storage_balance_callback`, but on the `PromiseResult::Failed` branch of each, the function returns a value immediately without ever creating a `promise_batch_action_transfer` back to `caller_deposit.account_id`, unlike the equivalent branch in `rlp_execute_callback` which does perform this refund [2](#0-1) . Because the deposit NEAR was already credited to the wallet's account balance by the runtime when the `rlp_execute` receipt executed, that value is now indistinguishable from the wallet owner's own balance, and the depositing relayer has no further mechanism in the contract to reclaim it.

### Impact Explanation
Any relayer/RPC caller that attaches a deposit to `rlp_execute` for an ERC-20 transfer to a not-yet-checked target, or a base-token transfer to another eth-implicit account requiring an address-registrar lookup, can lose that deposit permanently to the wallet owner's account if the registrar call or `storage_balance_of` call fails (e.g., the registrar or token contract is temporarily out of gas, paused, or the shard is congested). This is an unauthorized value movement from the depositing caller to the wallet account, triggered by a single external transaction, with no recovery function for the party that funded the deposit.

### Likelihood Explanation
Triggering this only requires an external account (not the wallet owner) to call `rlp_execute` with a nonzero attached deposit targeting either (a) another eth-implicit account (invoking `address_check_callback`) or (b) an ERC-20/NEP-141 transfer (invoking `nep_141_storage_balance_callback`), and having the intermediate cross-contract call fail — a condition a caller could even induce deliberately by pointing `target`/`token_id` at a contract they control that intentionally fails the lookup call.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, on the `PromiseResult::Failed` branch, mirror the refund logic already present in `rlp_execute_callback`: if `caller_deposit` is `Some`, create a `promise_batch_action_transfer` back to `caller_deposit.account_id` before returning the failure `ExecuteResponse`.

### Proof of Concept
1. Relayer R calls `rlp_execute(target, tx_bytes_b64)` on wallet W, attaching `X` yoctoNEAR, where the RLP transaction is an ERC-20 transfer to token contract `T`.
2. `inner_rlp_execute` records `CallerDeposit { account_id: R, yocto_near: X }` and schedules `T::storage_balance_of` followed by `nep_141_storage_balance_callback`.
3. `T::storage_balance_of` fails (e.g., `T` is out of gas, paused, or crafted to always fail).
4. `nep_141_storage_balance_callback` observes `PromiseResult::Failed`, and returns `ExecuteResponse { success: false, ... }` at [6](#0-5)  without refunding `X` to R.
5. `X` yoctoNEAR remains part of W's account balance, spendable only by W's owner, never returned to R.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
