## Title
Loss of witness block/tx-fee rewards when a witness's vote count reaches zero mid-cycle - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
`DelegationStore.accumulateWitnessVi()` silently discards the block/transaction-fee reward accumulated for a witness during a cycle if that witness's total vote count (`voteCount`) is `0` at the time the cycle's `vi` (voter-index) is folded in. This is the same class of bug as the Sherlock M-7 finding in `StakedEXA`: when the "stake" denominator used to distribute rewards is zero, the index (`vi`) is not advanced, but the fact that a reward was already earned/recorded for that period is not rolled forward or refunded anywhere — the reward becomes permanently stuck.

### Finding Description
Every reward paid to a witness for producing a block or collecting transaction fees goes through `MortgageService.payReward()`, which unconditionally stores the (post-brokerage) reward amount for the *current cycle* regardless of the witness's current vote count: [1](#0-0) 

At the next maintenance cycle, `MaintenanceManager.doMaintenance()` folds this per-cycle reward into the witness's cumulative `vi` (voter index) used to compute proportional payouts to voters: [2](#0-1) 

The folding logic in `DelegationStore.accumulateWitnessVi()` is the root cause: if the witness's `voteCount` for that cycle is `0` (analogous to `totalSupply() == 0` in `StakedEXA`), the accumulated `reward` for the cycle is dropped and only the *previous* `vi` is carried forward — the reward value itself is never redistributed or refunded: [3](#0-2) 

Because `vi` for later cycles is only ever derived from deltas of previously stored `vi` values (see `MortgageService.computeReward` / `VoteRewardUtil.computeReward`, which compute `endVi - beginVi`), a reward that was never folded into `vi` for its cycle can never appear in any future delta. It is not credited to the witness (only the `brokerage` portion is credited to the witness's `allowance` via `adjustAllowance`), and it is not credited to any voter (there are none, by definition, when `voteCount == 0`). The `reward-<cycle>-<address>` entry remains in `DelegationStore` but is never read by any other code path, so the TRX equivalent value is effectively burned/stuck in the "witness reward" pool, unreachable via `WithdrawRewardContract`/`WithdrawRewardProcessor` or any RPC/API call.

A witness's `voteCount` can legitimately be `0` for a full cycle while the witness is still active and producing blocks: SR/witness activity and payouts (`payBlockReward`, `payTransactionFeeReward`) happen continuously as blocks are produced, whereas vote-count changes (via ordinary user-broadcast `VoteWitnessContract` transactions) and the active-witness list are only reconciled once per maintenance cycle in `doMaintenance()`. If all voters withdraw their votes from a witness during a cycle (an action any unprivileged user can trigger by broadcasting `VoteWitnessContract`/unvote transactions), the witness can still finish out that cycle as an active SR, earning block and transaction-fee rewards that are permanently lost at the next maintenance boundary once `witness.getVoteCount()` reads `0`.

### Impact Explanation
This causes silent, permanent loss of legitimately earned block/transaction-fee reward funds within the DPoS reward-accounting subsystem. No party — neither the witness nor former voters — can ever claim that portion of the reward, resulting in asset/accounting corruption (funds effectively vanish from the circulating reward pool without being burned through any documented/observable mechanism). This is reachable purely through ordinary, unprivileged voting/unvoting transactions combined with normal witness block production; no privileged actor or malicious peer is required.

### Likelihood Explanation
Likelihood is moderate: it requires that all votes are withdrawn from an active witness within a single voting cycle while that witness continues (or briefly continues) to produce blocks before the next maintenance reconciles the active set and vote counts. This is a plausible, unprivileged and adversary-controllable scenario (e.g., voters intentionally unvoting a witness they control, or coordinated mass unvoting), especially on networks with few witnesses/voters (e.g., private/test/low-participation networks), though less likely on a mature mainnet with many independent voters per top-27 witness.

### Recommendation
In `DelegationStore.accumulateWitnessVi()` (and its duplicate in `RewardViCalService.accumulateWitnessVi`), when `voteCount == 0` but `reward != 0`, do not silently drop the reward. Instead, either (a) roll the un-distributable reward forward into the next cycle's reward bucket for the same witness (`addReward(cycle + 1, address, reward)`) so it can be distributed once votes reappear, or (b) redirect it to a designated sink (e.g., burn it explicitly via `DynamicPropertiesStore` accounting, or credit it back to the witness's own allowance) so the total supply/accounting invariant is preserved and funds are never unaccounted for.

### Proof of Concept
1. Witness `W` is an active SR with non-zero `voteCount` at the start of cycle `N`.
2. During cycle `N`, `W` produces blocks; each block/tx-fee reward is recorded via `MortgageService.payReward()` → `delegationStore.addReward(N, W, value)` (see `MortgageService.java:79-87`).
3. Before the maintenance that ends cycle `N`, all voters call `VoteWitnessContract` (broadcast transactions) to withdraw their votes from `W`, driving `W.getVoteCount()` to `0`. `W` remains in the active set until the next maintenance runs.
4. At maintenance, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)` (`MaintenanceManager.java:96-101`).
5. Inside `accumulateWitnessVi`, since `voteCount == 0`, the branch at `DelegationStore.java:136-139` executes: `vi` for cycle `N` is simply set to the previous `vi` (or left unset), and the `reward` value fetched from `getReward(N, W)` is never used.
6. All subsequent reward computations (`MortgageService.computeReward`, `VoteRewardUtil.computeReward`) only ever look at `endVi - beginVi`; since `vi` was never incremented for cycle `N`, the reward recorded in `getReward(N, W)` can never be paid out to anyone — it is permanently stuck.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
