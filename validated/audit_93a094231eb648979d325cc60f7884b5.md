### Title
Missing existence check on `DeleteAccountAction.beneficiary_id` leads to permanent burning of the deleted account's balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically well-formed `AccountId` — it never checks that the beneficiary account actually exists. If the beneficiary does not exist, the balance-refund receipt created to pay it out is rejected as `AccountDoesNotExist`, and because that receipt is treated as a system refund, the failure causes the entire transferred balance to be permanently burned rather than returned to anyone.

### Finding Description
`validate_delete_action` (the only "validation" performed on `DeleteAccountAction`) checks the beneficiary purely for account-id format: [1](#0-0) 

No check is made that `beneficiary_id` corresponds to an existing account. When the delete action executes, the remaining account balance is unconditionally sent to that id via a `Receipt::new_balance_refund`, with no existence check performed at this point either: [2](#0-1) 

`Receipt::new_balance_refund` sets `predecessor_id = "system"`, marking the receipt as a refund: [3](#0-2) 

When this refund receipt is later processed against a non-existent (and non-implicit-creatable) beneficiary, `check_account_existence` rejects the `Transfer` action because `implicit_creation_allowed` always returns `false` for refund receipts, regardless of account type: [4](#0-3) [5](#0-4) 

A test explicitly documents this exact outcome — a refund to a missing account fails with `AccountDoesNotExist` and never creates the account: [6](#0-5) 

Finally, when a refund receipt (`predecessor_id.is_system()`) fails, the runtime burns the deposit instead of returning it to anyone: [7](#0-6) 

This is also documented behavior: "If the execution of a refund fails, the refund amount is burnt." [8](#0-7) 

Existing tests and comments elsewhere in the codebase confirm this footgun is known to test authors but not prevented by the protocol: "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" — comment that turns out to understate the actual effect, since the "refund" in this case is not returned but burned. [9](#0-8) 

### Impact Explanation
Any account owner (a single transaction signer, requiring no special privileges) who submits a `DeleteAccountAction` with a syntactically valid but non-existent `beneficiary_id` — a typo, a not-yet-registered subaccount, or an account that was deleted in the same block/receipt batch — permanently and irrecoverably burns their account's entire remaining NEAR balance. There is no way to recover the funds; they are removed from `tokens_burnt`/total supply accounting as burnt tokens. This is a direct, protocol-level, concrete loss of funds triggered by a single transaction, matching the "permanently frozen/lost funds" impact class, and mirrors the reported bug class (unvalidated recipient parameter causing loss of funds due to missing address/existence validation).

### Likelihood Explanation
Likelihood is high: `DeleteAccountAction` is a normal, unprivileged action available to any account owner, and NEAR account ids are free-form strings with no registry lookup required at construction time — a wallet, script, or user typo in `beneficiary_id`, or racing account deletion, will trigger this path. Validation exists only for the id's *format*, giving a false sense of safety while the existence gap remains completely unguarded.

### Recommendation
Before (or instead of) issuing the `Receipt::new_balance_refund` in `action_delete_account`, verify that `beneficiary_id` refers to an existing, initialized account (or otherwise route the transfer through a path that is allowed to implicitly create/receive funds, e.g. a non-refund `Transfer` receipt so failure semantics don't burn the deposit). Alternatively, reject `DeleteAccountAction` at validation time when `beneficiary_id` cannot be resolved to an existing account, or explicitly fall back the balance to the deleting account's predecessor if the target account does not exist, so unspent balance is never silently destroyed.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance.
2. Submit a transaction from `alice.near` containing a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "doesnotexist.near" })`, where `doesnotexist.near` is a syntactically valid but never-created account (this passes `validate_delete_action`'s format-only check).
3. `action_delete_account` removes `alice.near` and enqueues `Receipt::new_balance_refund(&"doesnotexist.near", account_balance)` (`runtime/runtime/src/actions.rs:380-386`).
4. When this receipt is applied, `check_account_existence` rejects the inner `Transfer` action with `AccountDoesNotExist` because `implicit_creation_allowed` is `false` for refund receipts (`runtime/runtime/src/actions.rs:928-933`).
5. Because `receipt.predecessor_id().is_system()` is true and the receipt failed, the entire `account_balance` is added to `other_burnt_amount` and permanently destroyed (`runtime/runtime/src/lib.rs:1047-1055`), as validated by the existing test `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6880-6926`), which demonstrates the identical mechanism for a `0u` deterministic account and asserts no account is ever created — confirming the funds are simply lost.

```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
