### Title
Wallet Contract fails to refund attached deposit when the intermediate lookup call fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract` tracks an external caller's attached deposit in `CallerDeposit` so it can be refunded if the underlying cross-contract action fails. This refund is only actually performed in `rlp_execute_callback`. In the two intermediate callback paths — `address_check_callback` and `nep_141_storage_balance_callback` — the `PromiseResult::Failed` case of the *preceding* lookup call (`address_registrar.lookup` / `storage_balance_of`) is matched, but the code simply returns an error `ExecuteResponse` without ever creating the refund promise for `caller_deposit`, silently dropping the value that should be returned to the caller.

### Finding Description
`CallerDeposit` is explicitly documented as existing "to refund the caller's deposit if the cross-contract call fails" [1](#0-0) .

The only place that actually performs this refund is `rlp_execute_callback`, on `PromiseResult::Failed` of the final action: [2](#0-1) 

However, `address_check_callback` — the callback that runs after the address-registrar `lookup` call for an `EOABaseTokenTransfer` with an address check — receives `caller_deposit` as a parameter but, on `PromiseResult::Failed` (i.e. the lookup call itself failing), just returns an error response without using `caller_deposit` at all: [3](#0-2) 

Likewise, `nep_141_storage_balance_callback` — the callback after the `storage_balance_of` lookup for an emulated ERC-20 transfer — receives `caller_deposit` but on `PromiseResult::Failed` of `storage_balance_of` also returns an error without refunding: [4](#0-3) 

In both cases `caller_deposit` is simply dropped when the function returns `PromiseOrValue::Value(...)`; no promise is created and no state change moves the deposit back to the depositor. This is the direct nearcore analog of the Swivel bug: the external call's outcome (`PromiseResult::Failed`) *is* observed, but the code that should react to that failure (returning the user's attached funds) is missing on two of the three cross-contract-call return paths, even though the sibling function (`rlp_execute_callback`) demonstrates that refunding-on-failure was the intended invariant.

### Impact Explanation
Any external, unprivileged caller (a relayer forwarding another user's signed Ethereum-style transaction, or any account calling `rlp_execute` directly with `deposit(...)`) that triggers either the address-check path (`EOABaseTokenTransfer` to another eth-implicit account) or the ERC-20-transfer path can have their attached NEAR deposit permanently stuck in the wallet contract if the intermediate cross-contract call (`address_registrar.lookup` or `storage_balance_of`) fails — e.g., due to an out-of-gas, the registrar/token contract panicking, or the registrar/token account not existing. The deposit is not returned to the caller and is not consumed by any completed action, so it remains locked in the wallet-contract account's balance with no code path to claim it back through this method (frozen funds for the caller who supplied the deposit).

### Likelihood Explanation
This is reachable by any unprivileged account submitting a normal `FunctionCall` transaction/receipt to `rlp_execute` with `deposit(...)` set and `target` chosen to route into either the `EOABaseTokenTransfer{address_check: Some(_)}` branch or the `ERC20Transfer` branch. Causing the intermediate call to fail only requires supplying a `target`/token account that reverts, is unregistered, or is given insufficient attached gas relative to `REGISTRAR_LOOKUP_GAS` / `NEP_141_STORAGE_BALANCE_OF_GAS` — both realistic, low-cost conditions a caller (or even an honest relayer hitting an edge case) can trigger without any special privilege.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, on the `PromiseResult::Failed` branch, construct and return the same refund promise used in `rlp_execute_callback` (using `env::promise_batch_create` + `env::promise_batch_action_transfer` to `caller_deposit.account_id`) before returning the failure `ExecuteResponse`, so the caller's deposit is never silently forfeited regardless of which cross-contract call in the pipeline fails.

### Proof of Concept
1. An external caller (not the wallet's own account) calls `rlp_execute` with `deposit(X)` and a `tx_bytes_b64` that RLP-encodes a base-token transfer whose `to` address matches another eth-implicit account requiring an `address_check` (`EOABaseTokenTransfer{address_check: Some(address)}`).
2. `inner_rlp_execute` builds `caller_deposit = CallerDeposit::new(&context)` from the attached deposit and schedules `address_registrar.lookup(address).then(ext.address_check_callback(target, action, caller_deposit))` [5](#0-4) .
3. The address-registrar contract call fails (e.g., insufficient `REGISTRAR_LOOKUP_GAS`, the registrar account doesn't exist, or it panics).
4. `address_check_callback` executes with `env::promise_result(0) == PromiseResult::Failed`, and returns `ExecuteResponse { success: false, ... }` without ever touching `caller_deposit` [3](#0-2) .
5. The caller's `X` yoctoNEAR deposit remains in the wallet contract's balance permanently; no subsequent promise moves it back to the caller, unlike the `rlp_execute_callback` failure path which does issue a `refund_promise`.
