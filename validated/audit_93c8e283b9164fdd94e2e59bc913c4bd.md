## Finding Confirmed

The `state_change_hash` binding is never checked at restore time — the write set is carried alongside the verified `TransactionInfo` list but is disjoint from the actual signature verification.

### Title
Missing write_set-to-state_change_hash validation during transaction restore allows a corrupted write set to be committed while accumulator/ledger-info proof still verifies - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`, `storage/aptosdb/src/backup/restore_utils.rs`)

### Summary
`LoadedChunk::load` deserializes `(Transaction, TransactionInfo, Vec<ContractEvent>, WriteSet)` records from a backup chunk file, but only assembles the `Transaction`, `TransactionInfo`, and events into a `TransactionListWithProofV2` for cryptographic verification against the `LedgerInfoWithSignatures`. The `WriteSet` values are collected into a parallel `Vec<WriteSet>` that is never included in, or checked against, that proof.

### Finding Description
In `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`: [1](#0-0) 
each record's `write_set` is pushed into `write_sets`, entirely separate from the `TransactionListWithProofV2` built at: [2](#0-1) 
`txn_list_with_proof.verify(...)` cryptographically validates that `txns`, `event_vecs`, and `txn_infos` are consistent with the accumulator proof and the signed `LedgerInfo` — but `write_sets` is not part of `TransactionListWithProofV2` at all, so it is never touched by `verify()`. The `TransactionInfo.state_change_hash` field (the committed hash the write set is supposed to match) is present in `txn_infos`, but nothing computes `CryptoHash::hash(&write_set)` and compares it to `txn_info.state_change_hash()` anywhere in this file, nor downstream.

The unpacked `write_sets` flow straight through `save_before_replay_version`/`replay_kv` into `RestoreHandler::save_transactions` / `save_transactions_and_replay_kv`: [3](#0-2) 
which calls `restore_utils::save_transactions` → `save_transactions_impl`, where each write set is written verbatim via `WriteSetDb::put_write_set` with no hash check: [4](#0-3) 

For comparison, the correct invariant — that a committed write set must hash to `TransactionInfo.state_change_hash()` — is only ever asserted in test code (`execution/executor/tests/db_bootstrapper_test.rs`), never enforced in the restore path: [5](#0-4) 

### Impact Explanation
Backup chunks are attacker-influenceable input in this scope (loaded from a `BackupStorage` backend, e.g. an object store, potentially fetched by a node operator restoring or by a state-sync-v2 flow reusing these utilities). Because `state_change_hash` is not checked against the actual `WriteSet` bytes, an attacker who can supply/tamper a transaction backup chunk (while leaving `Transaction`, `TransactionInfo`, events, and the accumulator/`LedgerInfo` signatures untouched and self-consistent) can substitute an arbitrary `WriteSet` for any transaction. The restore will succeed, `WriteSetDb::put_write_set` will commit the forged write set, and the resulting node's persisted state diverges from what honest validators produced — corrupting the write-set-to-state-change-hash binding invariant while the ledger info/accumulator proof still validates.

### Likelihood Explanation
Requires control over the content of a `transactions` backup chunk file (the `manifest.transactions` blob) that is later fed into a restore/replay process; the `manifest.proof` file (accumulator proof + signed `LedgerInfo`) does not need to be forged at all since it never covers `write_sets`. This is a straightforward file-content substitution attack against the restore data pipeline, not requiring any cryptographic break.

### Recommendation
In `LoadedChunk::load` (or in `save_transactions_impl`), for each `(txn_info, write_set)` pair, compute `CryptoHash::hash(write_set)` and `ensure!` it equals `txn_info.state_change_hash()` before accepting the chunk / before calling `WriteSetDb::put_write_set`. This restores the binding invariant and causes restore to reject the corrupted chunk rather than silently persist mismatched write sets.

### Proof of Concept
1. Take a legitimate transaction backup chunk file and locate a serialized `(Transaction, TransactionInfo, Vec<ContractEvent>, WriteSet)` (or V1 variant) record.
2. Replace the `WriteSet` bytes with an arbitrary different write set (re-encode with `bcs`), keeping `Transaction`, `TransactionInfo`, and `events` byte-identical, so `TransactionListWithProofV2::verify` still succeeds against the untouched `manifest.proof`.
3. Run `TransactionRestoreController` against this tampered chunk.
4. Observe: `LoadedChunk::load` succeeds (`txn_list_with_proof.verify` passes since write sets aren't checked), `save_transactions`/`save_transactions_impl` commits the forged `WriteSet` via `WriteSetDb::put_write_set`, and `CryptoHash::hash(&forged_write_set) != txn_info.state_change_hash()` — confirming the restore path accepts and commits a corrupted write set instead of rejecting it.
