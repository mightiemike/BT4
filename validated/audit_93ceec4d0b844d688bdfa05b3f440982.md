### Title
Client-side "proof facts" (SNOS proof) are not bound to the transaction, allowing any account to replay another user's proof to forge a validated client-side-proving transaction - ([File: crates/blockifier/src/transaction/account_transaction.rs])

### Summary
`ProofFacts`/`Proof` for client-side proving (invoke V3, "private transaction") attest only to `(proof_version, program_hash, base_block_number, base_block_hash, starknet_os_config_hash, l2-to-l1 message hashes)`. Neither the Cairo OS proof-facts check (`check_proof_facts`) nor the Rust-side `validate_proof_facts` in `AccountTransaction` verify that the proof corresponds to *this* transaction's sender, nonce, or calldata. Because `proof_facts`/`proof` are public request fields (visible in the gateway, mempool, p2p broadcast, and the content-addressed `ProofManager`/GCS archive), any account can copy a previously observed valid `(proof_facts, proof)` pair from any other transaction in the same block window and attach it to its own, unrelated `InvokeTransaction`, passing all "client-side proving" checks.

### Finding Description
`ProofFacts::hash()` content-addresses the proof manager cache/store (`crates/apollo_proof_manager/src/proof_manager.rs`), and `TransactionConverter::run_proof_verification` (`crates/apollo_transaction_converter/src/transaction_converter.rs:395-424`) skips re-verifying a proof entirely if `contains_proof(proof_facts)` is already true — i.e. once *any* client submits a valid proof for a given `proof_facts` value, that exact `(proof_facts, proof)` pair is globally reusable without re-verification.

The `SnosProofFacts` structure (`crates/starknet_api/src/transaction/fields.rs:803-813`) and the OS's `VIRTUAL_OS_OUTPUT_VERSION` layout (`crates/apollo_starknet_os_program/.../virtual_os_output.cairo:14-24`) contain only:
```
[output_version, base_block_number, base_block_hash, starknet_os_config_hash, n_l2_to_l1_messages, ...]
```
There is no sender address, nonce, transaction hash, or calldata commitment anywhere in this output.

`AccountTransaction::validate_proof_facts` (`crates/blockifier/src/transaction/account_transaction.rs:291-351`) only checks: proof version allowed, program hash allowed, block number/hash validity against on-chain state, and OS config hash match — it never checks that the proof_facts/proof relate to `self` (the specific invoke transaction being validated). The Cairo-side gate `check_proof_facts` (`crates/apollo_starknet_os_program/.../execution_constraints.cairo:34-81`) performs the identical set of checks and likewise never ties the proof to the transaction hash, sender, or calldata.

Consequently, this "client-side proving" mechanism is a bug class analogous to shared-cookie leakage: a piece of authorization evidence (`proof`) generated for one principal's request is stored/served through a resource keyed only on non-identifying public data, so it is trivially usable by a different, unrelated principal's request.

### Impact Explanation
An attacker who observes any single valid `(proof_facts, proof)` pair (e.g., by watching mempool/p2p gossip, the gateway's public REST endpoint, or their own legitimately-obtained proof from `starknet_transaction_prover`) can attach that exact pair to an arbitrary `InvokeTransaction` of their own choosing (different sender, nonce, calldata) and have it accepted by `StatelessTransactionValidator::validate_proof_facts_and_proof_consistency` and `AccountTransaction::validate_proof_facts`/`check_proof_facts` in the OS, since none of these checks depend on the transaction's identity. Depending on what semantic guarantee "client-side proving" is relied upon for elsewhere in the stack (e.g., skipping fee charging/zero-fee acceptance, as documented in `starknet_transaction_prover/README.md` — "Prices and tip must be zero: since proving is client-side and no fees are charged"), this allows an unauthorized party to submit fee-free/privately-proven transactions under a false claim of having produced a valid client-side proof for their own execution, potentially enabling fee bypass or acceptance of transactions that were never actually proven to be valid for their specific content. This is a state-affecting authorization bypass, not merely metric/logging noise.

### Likelihood Explanation
Reaching this requires only submitting a normal `RpcTransaction::Invoke` with attacker-chosen `proof_facts`/`proof` copied from any other transaction (their own or one observed in the public mempool/gateway) — a single unprivileged transaction sender can trigger it end-to-end through `Gateway::add_tx_inner` (`crates/apollo_gateway/src/gateway.rs:214-298`). No special privileges, timing races, or operator collusion are needed; likelihood is high.

### Recommendation
Bind the proof facts / virtual-OS output to the specific transaction being submitted (e.g., commit to the transaction hash, sender address, and nonce inside the virtual OS output, and enforce that commitment in both `check_proof_facts` (Cairo) and `AccountTransaction::validate_proof_facts` (Rust)) so a proof generated for one transaction cannot be replayed against a different transaction. Additionally, consider scoping the `ProofManager`/GCS proof cache key to include the transaction hash rather than only `proof_facts.hash()`.

### Proof of Concept
1. Attacker (or anyone) observes a valid `(proof_facts, proof)` pair from any submitted `InvokeTransaction` with client-side proving enabled (visible via mempool p2p gossip, gateway response, or by calling the public `starknet_proveTransaction` prover endpoint themselves once).
2. Attacker crafts a new `RpcInvokeTransactionV3` with their own `sender_address`, `nonce`, and `calldata`, but copies the observed `proof_facts` and `proof` verbatim.
3. Submits via the gateway's `add_tx`. `StatelessTransactionValidator::validate_proof_facts_and_proof_consistency` passes (both fields non-empty and consistent); `TransactionConverter::run_proof_verification` finds `contains_proof(proof_facts)` already true (or independently verifies the copied proof successfully, since verification only checks the SNOS proof against its own public output, unrelated to the new tx); `AccountTransaction::validate_proof_facts` and the OS `check_proof_facts` pass since checks are block/program/config-hash only.
4. The forged transaction is accepted as "private"/client-side-proven despite the proof never having attested anything about this transaction's sender, nonce, or calldata.
