## Title
Webhook Shop-Domain Spoofing Enables Cross-Tenant Admin Session Access — ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
The reported Solidity bug lets an attacker deploy a fake contract and pass its address into `DaosLocker::collect()`; the function trusts that address to determine whose fees get paid out, with no binding between the caller-supplied identifier and the authorization check. The equivalent bug class in `shopify-app-js` is present in the webhook authentication pipeline: the app's HMAC validation only signs the **raw body**, never the `X-Shopify-Shop-Domain` header, yet that header value is later used, unverified, to select which shop's stored offline access token gets attached to the webhook handler context.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC purely from `rawBody` and compares it to the `X-Shopify-Hmac-Sha256` header value — the shop domain is never part of the signed data: [1](#0-0) 

After HMAC succeeds, `validateFactory` reads the domain straight out of the (unauthenticated) `X-Shopify-Shop-Domain` header via `checkWebhooksHeaders`, and returns it as `domain` in the "valid" result without any cryptographic tie to the HMAC that was just checked: [2](#0-1) 

Downstream, `authenticateWebhookFactory` (shopify-app-remix) takes that untrusted `check.domain` value and uses it to look up and attach the corresponding shop's offline session/admin client to the webhook context: [3](#0-2) 

The same pattern repeats in the fulfillment-service handler, which reads `shop` from `request.headers.get(ShopifyHeader.Domain)` after a body-only HMAC check and immediately uses it to fetch an offline session and build an authenticated admin client: [4](#0-3) 

This mirrors the Solidity root cause exactly: a caller-supplied identifier (`dao` address / `X-Shopify-Shop-Domain` header) is used to select whose credentials/funds are accessed, but that identifier is never verified to belong to the entity that produced the accepted proof (LP token ownership check / HMAC signature).

### Impact Explanation
Because a single app-wide `apiSecretKey` is used to sign all webhooks for all installs of the app, any merchant/customer who can install the app on their own store (or otherwise obtain one legitimately-signed `(rawBody, hmac)` pair from Shopify) can replay that exact body+HMAC pair to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to name a different (victim) shop that has an offline session stored by the app. Since the domain is not covered by the HMAC, the request still validates, and the webhook/fulfillment-service handler executes with `shop` set to the victim's domain, obtaining an `admin` client authorized with the **victim's stored offline access token**. This is a cross-tenant authorization bypass: an unprivileged actor from their own store can trigger the app to run privileged Admin API operations against another merchant's shop.

### Likelihood Explanation
The attacker only needs the ability to install the target app on any shop they control and capture one webhook delivery (or use a static/predictable body such as an empty-body topic), then send a crafted HTTP POST directly to the app's public webhook/fulfillment-service route with a forged domain header — no secret key or MITM is required. Reachability is a single anonymous/merchant-controlled HTTP request to the app's exposed webhook endpoint.

### Recommendation
Bind the shop domain (and other identity-critical headers such as topic/webhook id) into the HMAC-signed material, or otherwise fetch the shop for a request only via a value that is itself part of the signed payload/registered subscription, rather than trusting the `X-Shopify-Shop-Domain` header independently of the HMAC. At minimum, cross-check the resolved `domain` against the shop associated with the specific webhook subscription/registration before using it to select session storage.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, allowing the app to register webhooks and obtain a stored offline session for that shop.
2. Attacker triggers a webhook delivery (e.g., `app/uninstalled` or any topic with a static/empty body) and captures the raw POST body plus its valid `X-Shopify-Hmac-Sha256` value from Shopify — this HMAC is valid because it's computed only over `rawBody` using the app's shared `apiSecretKey`, per `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-198`).
3. Attacker sends this exact `(rawBody, X-Shopify-Hmac-Sha256)` pair to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `validateFactory`/`checkWebhooksHeaders` accept the request (HMAC matches; all required headers present) and return `domain: 'victim.myshopify.com'` (`packages/apps/shopify-api/lib/webhooks/validate.ts:99-134`).
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim.myshopify.com')` and constructs an `admin` client using the victim's stored offline access token (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:35-96`), giving the attacker's forged request access to run Admin API operations under the victim shop's credentials inside the app's webhook handler logic.

  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs

    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);

    // Use appropriate header based on webhook type

      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );

      return fail(ValidationErrorReason.InvalidHmac, type, config);

): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
