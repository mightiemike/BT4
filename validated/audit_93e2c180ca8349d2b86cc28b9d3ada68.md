### Title
Actuator authorization relies solely on pipeline-level `validateSignature`/`checkWeight`, with no owner-address/signer cross-check in `VoteWitnessActuator`, `ProposalApproveActuator`, `DelegateResourceActuator`, `UnfreezeBalanceV2Actuator` - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
`TransactionCapsule.validateSignature` derives the acting account solely from `TransactionCapsule.getOwner(contract)` (the `owner_address` field embedded in the contract payload) and then checks whether the *set of signatures on the transaction* recovers to addresses whose permission weights meet the threshold for that owner's permission, via `checkWeight` (`chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:468-496`, `233-270`). None of the four actuators re-verify that the signer(s) who satisfied that threshold are actually tied to the specific `owner_address` in their own contract object beyond what `getOwner`/`validateSignature` already established — they trust the pipeline check completely and never reference recovered-signer identity in `validate()`.

### Finding Description
The transaction-processing pipeline (`Manager.pushTransaction` / `Manager.processTransaction`, `framework/src/main/java/org/tron/core/db/Manager.java:905-909`, `1542-1546`) calls `trxCap.validateSignature(...)`, which internally calls `TransactionCapsule.validateSignature` (`chainbase/.../TransactionCapsule.java:468`). That method:
1. Extracts `owner = getOwner(contract)` directly from the contract's `owner_address` field.
2. Loads the `Permission` for that specific owner/account.
3. Calls `checkWeight(permission, transaction.getSignatureList(), hash, null)`, which recovers an address per signature via `SignUtils.signatureToAddress` (itself dependent on `Rsv.fromSignature`, `crypto/.../Rsv.java:17-25`, for parsing `r`, `s`, `v`) and sums the weight of matched permission keys, deduplicating by recovered address/base64 signature.
4. Returns `true` if `weight >= permission.getThreshold()`.

This is the *only* place identity/authorization is asserted for the whole transaction. Each actuator's `validate()` — `VoteWitnessActuator` (`actuator/.../VoteWitnessActuator.java:61-150`), `ProposalApproveActuator` (`actuator/.../ProposalApproveActuator.java:67-148`), `DelegateResourceActuator` (`actuator/.../DelegateResourceActuator.java:101-249`), `UnfreezeBalanceV2Actuator` (`actuator/.../UnfreezeBalanceV2Actuator.java:103-185`) — only checks address format validity (`DecodeUtil.addressValid`), account/witness/proposal existence, and business-logic invariants (vote counts, resource balances, thresholds, expiry). None of them independently re-derive the signer's address from the signature and compare it to `contract.getOwnerAddress()`; they implicitly assume `validateSignature` already bound the signature set to that exact owner. Because `getOwner(contract)` is what selects *whose* permission/threshold is checked, and `checkWeight` only verifies *weight sufficiency* against that permission — not that a specific unique key signed — any defect in signature recovery/dedup logic (e.g., in `Rsv.fromSignature`, `SignUtils.signatureToAddress`, or `checkWeight`'s dedup map) that causes distinct broadcast signatures to be treated as satisfying the weight threshold for an account the attacker does not control would let `validateSignature` return `true` for a transaction impersonating that owner. Since the actuator layer performs zero secondary identity check, `execute()` would then unconditionally mutate victim state: `countVoteAccount` (votes), `proposalCapsule.addApproval/removeApproval`, `delegateResource` (moves frozen balance to receiver), and `accountCapsule.addUnfrozenV2List` (unfreezes victim's frozen balance) — see `VoteWitnessActuator.java:152-191`, `ProposalApproveActuator.java:37-65`, `DelegateResourceActuator.java:44-98`, `UnfreezeBalanceV2Actuator.java:50-101`.

However, this specific PoC requires an actual confirmed signature-malleability/dedup bug in `Rsv.fromSignature`/`checkWeight` to be present and exploitable. I did not find such a bug in the reviewed code: `checkWeight` (`TransactionCapsule.java:233-270`) throws `PermissionException` if `sig.size() < 65`, rejects sig counts exceeding `permission.getKeysCount()`, deduplicates by base64-encoded signature (or by recovered address post `VERSION_4_7_1`), and requires each signature's `weight` to be nonzero for a real key in the permission — meaning a normal multi-sig threshold bypass would require either forging a second distinct-looking signature that recovers to the *same already-counted* key (blocked by the `addMap.containsKey` dedup) or recovering to a *different* key in the same permission's key list that the attacker doesn't actually control (which would require breaking ECDSA, not just signature malleability). `Rsv.fromSignature` (`crypto/.../Rsv.java:17-25`) is a straightforward 65-byte `r/s/v` parser with a `v < 27` correction; it does not itself introduce an identity collision — signature malleability (e.g., `s` -> `n - s` with flipped recovery id) still recovers to the correct signer's address, and `checkWeight`'s dedup is keyed on the exact signature bytes/recovered address, not on `(r,s)` alone, so an s-negation malleated variant would recover to the same legitimate address and be deduped as "signed twice," not attributed to a different victim account. No standalone owner-mismatch bug was found in this codebase.

### Impact Explanation
*If* a genuine malleability/dedup defect existed in the shared `checkWeight`/`Rsv` path that caused an attacker-controlled signature to be misattributed to a victim's key (which is not established here), the architectural gap described (no actuator-level owner/signer cross-check) would indeed let that single bug cascade into: unauthorized `VoteWitnessContract` votes, unauthorized `ProposalApproveContract` approvals/disapprovals, unauthorized `DelegateResourceContract` resource transfers away from a victim, and unauthorized `UnfreezeBalanceV2Contract` early unfreezes of a victim's frozen balance — corresponding to TRON bounty's "unauthorized account operations" / "asset accounting corruption" impact classes. But without a demonstrated concrete defect in `checkWeight`/`Rsv.fromSignature`/`SignUtils.signatureToAddress`, this is a conditional/hypothetical cascading-impact analysis, not a standalone confirmed vulnerability.

### Likelihood Explanation
Not applicable as a standalone finding: exploitation is entirely contingent on a separate, unconfirmed root-cause bug in the shared signature-recovery/dedup code. As reviewed, `checkWeight`'s per-signature dedup (via base64/address) and the requirement that recovered addresses match real permission keys prevent the "distinct signatures collapse to same recovered address" scenario from succeeding against a victim who never signed.

### Recommendation
No code change is warranted based on what was found. If a future audit identifies a concrete signature-malleability or address-recovery collision in `Rsv.fromSignature`/`SignUtils.signatureToAddress`/`checkWeight`, defense-in-depth would still argue for keeping authorization centralized in `validateSignature` (adding redundant address checks per actuator is not the recommended fix — fixing signature canonicalization/recovery is).

### Proof of Concept

      List<ByteString> approveList)

    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(

        throw new SignatureFormatException(

      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

package org.tron.common.crypto;


import java.util.Arrays;
import lombok.AllArgsConstructor;
import lombok.Getter;

@Getter
@AllArgsConstructor
public class Rsv {

  private final byte[] r;
  private final byte[] s;
  private final byte v;


  public static Rsv fromSignature(byte[] sign) {
    byte[] r = Arrays.copyOfRange(sign, 0, 32);
    byte[] s = Arrays.copyOfRange(sign, 32, 64);
    byte v = sign[64];
    if (v < 27) {
      v += 27; //revId -> v
    }
    return new Rsv(r, s, v);
  }
}

    if (!checkUnfreezeBalance(accountCapsule, unfreezeBalanceV2Contract, unfreezeBalanceV2Contract.getResource())) {
      throw new ContractValidateException(
          "Invalid unfreeze_balance, [" + unfreezeBalanceV2Contract.getUnfreezeBalance() + "] is error"
      );
    }

    int unfreezingCount = accountCapsule.getUnfreezingV2Count(now);
    if (UNFREEZE_MAX_TIMES <= unfreezingCount) {
      throw new ContractValidateException("Invalid unfreeze operation, unfreezing times is over limit");
    }

    return true;
  }
