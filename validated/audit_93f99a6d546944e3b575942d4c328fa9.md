### Title
`SourceBuffer::new_checked_with_verified_build_hash` panics on attacker-crafted Buffer account with all trailing data zero and non-zero metadata bytes ("slice index starts after end") - (File: `runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs`)

### Summary
`SourceBuffer::new_checked_with_verified_build_hash` computes `end_offset` from the *last non-zero byte anywhere in the whole account data* rather than only within the program-data tail, then slices `&data[offset..end_offset]`. An attacker who owns an upgradeable-loader Buffer account can pick an `authority_address` whose trailing bytes are zero and leave the ELF/program-data tail entirely zero, causing `end_offset < offset` and panicking the slice operation.

### Finding Description
`new_checked_with_verified_build_hash` (`runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs:52-73`) first calls `Self::new_checked`, which only validates that `data[..buffer_metadata_size]` deserializes as `UpgradeableLoaderState::Buffer { .. }` [1](#0-0) . It does **not** constrain the value of `authority_address`, which is attacker-controlled 32 raw bytes.

It then computes:
```rust
let offset = UpgradeableLoaderState::size_of_buffer_metadata();
let end_offset = data.iter().rposition(|&x| x != 0).map_or(offset, |i| i + 1);
let buffer_program_data = &data[offset..end_offset];
``` [2](#0-1) 

`data.iter().rposition(...)` scans the **entire** account data buffer (metadata included), not just the tail past `offset`. If the last non-zero byte in the whole buffer lies inside the metadata region (index `i < offset - 1`), then `end_offset = i + 1 < offset`, and `&data[offset..end_offset]` panics with "slice index starts at X but ends at Y" because Rust requires `start <= end` for slicing.

The `authority_address: Option<Pubkey>` field is serialized inside the fixed-size metadata region (as confirmed by usages that always use the full `size_of_buffer_metadata()` offset for both `Some`/`None` cases, e.g. `programs/bpf_loader/src/lib.rs` `Write`/`DeployWithMaxDataLen`/`Upgrade` handlers all reference `UpgradeableLoaderState::size_of_buffer_metadata()` as a fixed constant) [3](#0-2) . The pubkey bytes are copied verbatim from an arbitrary instruction account key supplied to `InitializeBuffer`, with **no signature or validity requirement**:
```rust
UpgradeableLoaderInstruction::InitializeBuffer => {
    ...
    let authority_key = Some(*instruction_context.get_key_of_instruction_account(1)?);
    buffer.set_state(&UpgradeableLoaderState::Buffer { authority_address: authority_key })?;
}
``` [4](#0-3) 

An attacker can therefore:
1. Create/assign a buffer account owned by `bpf_loader_upgradeable::id()`.
2. Call `InitializeBuffer` passing, as instruction account 1, an arbitrary 32-byte address whose trailing bytes are all zero (e.g. `[1, 0, 0, ..., 0]`) — no signature on that account is required.
3. Never write ELF bytes (or write only zero bytes) so the tail from `offset` onward stays entirely zero.

This produces account data whose only non-zero byte(s) sit near the start of the metadata region, satisfying `i + 1 < offset`, so when `new_checked_with_verified_build_hash` is later invoked on this buffer (e.g., during a core-BPF migration verification flow), the slice expression panics and crashes the node performing the evaluation.

### Impact Explanation
This is a validator panic ("Bank"-level unwrap/index panic caused entirely by attacker-authored account bytes with no privileged access required), matching the "state-consistency" / node-crash bounty category rather than a load-freshness or capitalization bug. Because `SourceBuffer::new_checked_with_verified_build_hash` is invoked during built-in-to-Core-BPF program migration checks driven by bank/feature logic, a validator that reaches this code path on such a maliciously crafted buffer account will panic and halt.

### Likelihood Explanation
Fully feasible with only normal, unprivileged transactions: creating a system account, assigning it to `bpf_loader_upgradeable::id()`, and invoking `InitializeBuffer` with an attacker-chosen non-signing pubkey as the "authority" account. No special permissions, staking, or leader control are required, and the state is fully reproducible/deterministic.

### Recommendation
Compute `end_offset` by scanning only the tail slice `&data[offset..]` (not the whole `data`), e.g.:
```rust
let offset = UpgradeableLoaderState::size_of_buffer_metadata();
let tail = data.get(offset..).unwrap_or(&[]);
let end_offset = offset + tail.iter().rposition(|&x| x != 0).map_or(0, |i| i + 1);
```
This guarantees `end_offset >= offset` unconditionally, and also guards against `data.len() < offset` (the current code does not check this either, though `new_checked` prior guarantees `data.len() >= offset`).

### Proof of Concept
```rust
#[test]
fn test_source_buffer_zero_tail_nonzero_metadata_panics() {
    let bank = create_simple_test_bank(0);
    let buffer_address = Pubkey::new_unique();

    let buffer_metadata_size = UpgradeableLoaderState::size_of_buffer_metadata();
    // authority_address with only a leading non-zero byte, rest zero.
    let mut pk_bytes = [0u8; 32];
    pk_bytes[0] = 1;
    let authority_address = Some(Pubkey::new_from_array(pk_bytes));

    // data_len == buffer_metadata_size (no tail at all) OR > with all-zero tail.
    let mut data = vec![0u8; buffer_metadata_size + 8];
    bincode::serialize_into(
        &mut data[..buffer_metadata_size],
        &UpgradeableLoaderState::Buffer { authority_address },
    )
    .unwrap();
    // data[buffer_metadata_size..] stays all zero.

    store_account(&bank, &buffer_address, &data, &bpf_loader_upgradeable::id());

    // Expected: should return an error (e.g. empty/zero-length program data hash mismatch),
    // Actual: panics with "slice index starts at X but ends at Y" inside
    // SourceBuffer::new_checked_with_verified_build_hash.
    let _ = SourceBuffer::new_checked_with_verified_build_hash(
        &bank,
        &buffer_address,
        Hash::default(),
    );
}
```
Expected assertion for the fix: the call returns `Err(CoreBpfMigrationError::BuildHashMismatch(..))` (or similar) instead of panicking, and a fuzz/invariant harness over `(metadata_bytes, tail_len)` should assert `end_offset >= offset` always holds.
