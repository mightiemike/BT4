### Title
Stale reverted Cairo 0 class remains servable from the shared global contract-class cache after a block revert - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
The Chrome CVE is a use-after-free where a callback returns success data referencing an object that has already been freed/invalidated. The closest reachable analog in the sequencer is a *logical* use-after-invalidation: the global, shared `ContractClassManager` cache (`GlobalContractCache` / `RawClassCache`) that backs `StateReaderAndContractManager::get_compiled_from_class_manager` never re-validates cached **Cairo 0 (deprecated)** classes against the current declared-class state, so a class that was cached while declared and later un-declared (via a block revert) can still be served as "runnable" to a later transaction.

### Finding Description
`get_compiled_from_class_manager` explicitly skips the declaration-freshness check for `RunnableCompiledClass::V0` entries, only performing it for Cairo 1 classes: [1](#0-0) 

The code comment for the Cairo 1 branch makes the intent explicit — "verify it is declared, since existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)" — but this verification is deliberately not applied to `RunnableCompiledClass::V0(_)`: [2](#0-1) 

A batcher-level test explicitly documents this asymmetry: `is_declared` only reads the Cairo 1 declared-classes table, so Cairo 0 classes "never read storage" for declaration verification and always resolve through the class manager cache alone: [3](#0-2) 

The underlying cache (`GlobalContractCache`/`RawClassCache`) is a process-wide LRU cache shared across block production and view calls (see `StorageViewStateReaderFactory::create`, which explicitly shares the cache between block production and view calls): [4](#0-3) [5](#0-4) 

On-disk storage correctly removes a Cairo 0 class's declaration record on `revert_state_diff` (deleting from `deprecated_declared_classes_table`), so post-revert, the class is genuinely undeclared in persistent state: [6](#0-5) 

However, only the legacy Python-bound `PyBlockExecutor::revert_block` path explicitly clears the in-memory `contract_class_manager` cache on revert: [7](#0-6) 

I was unable to find an equivalent explicit `contract_class_manager.clear()` call in the current `apollo_batcher::Batcher::revert_block` path (`crates/apollo_batcher/src/batcher.rs`); the revert logic there aborts active height work and reverts committer/storage state, but the class-manager cache clearing pattern used by the legacy `native_blockifier::PyBlockExecutor` was not found there: [8](#0-7) 

Because Cairo 0 classes are never checked against `is_declared`, if the class-manager cache is not fully cleared/invalidated on revert in the current batcher flow, a previously-declared-then-reverted deprecated class hash would still resolve to a "runnable" `V0` class via the cache, i.e. execution would treat an undeclared class hash as declared and executable.

### Impact Explanation
If a Cairo 0 class hash is declared, cached in the shared `ContractClassManager`, and the declaring block is subsequently reverted (e.g., via reorg/consensus revert), any later transaction that references the same class hash (via deploy, replace-class, or as a contract's class) would have its class silently treated as declared/executable rather than failing with `StateError::UndeclaredClassHash`. This can cause execution to diverge from what an honest node that started from a cold cache (or after an explicit cache clear) would compute — leading to honest-node state divergence and a wrong committed state root/block hash for Cairo 0 declarations that were reverted and never redeclared with identical content. This maps to "wrong committed root or block hash" / "honest-node divergence" impact categories.

### Likelihood Explanation
Likelihood depends entirely on whether the current `apollo_batcher::Batcher::revert_block` path clears the shared `ContractClassManager`/`GlobalContractCache` the way the legacy `PyBlockExecutor::revert_block` does. I was not able to confirm within the available tool budget whether such a clear call exists elsewhere in the batcher/block-builder wiring (e.g., inside `abort_active_height`, `revert_commitment`, or a component that owns the `ContractClassManager` instance). If no such clear occurs, the bug is reachable purely through a sequence of (1) an attacker or normal actor declaring a Cairo 0 class, (2) a chain revert of that block (a normal, non-adversarial sequencer operation, not requiring a malicious actor), and (3) any subsequent transaction referencing that class hash. This does not require a malicious operator/proposer/peer — it is triggered by the revert mechanism, which is standard sequencer behavior, combined with a transaction from any unprivileged sender referencing the class hash.

### Recommendation
Apply the same freshness check used for Cairo 1 classes to `RunnableCompiledClass::V0` in `get_compiled_from_class_manager`, i.e., call `self.state_reader.is_declared(class_hash)` (extended to also check the deprecated/Cairo-0 declaration table, since the current `is_declared` implementation only checks the Cairo 1 table per the batcher test) before returning a cached V0 class as runnable. Alternatively/additionally, ensure every code path that reverts a block (not just the legacy `PyBlockExecutor`) explicitly calls `contract_class_manager.clear()` (or a more surgical per-class-hash invalidation) so the shared cache cannot outlive the on-disk declaration state it was populated from.

### Proof of Concept
1. Declare a Cairo 0 class `C` at block `N` (deprecated declaration).
2. Execute a transaction that reads/uses class `C` (e.g., deploy a contract with class hash `C`), causing `get_compiled_from_class_manager` to fetch, cache (`contract_class_manager.set_and_compile`), and return `RunnableCompiledClass::V0(C)`.
3. Revert block `N` through the sequencer's normal revert path (`apollo_batcher::Batcher::revert_block` → underlying storage `revert_state_diff`, which deletes the deprecated declaration record as shown in `crates/apollo_storage/src/state/mod.rs:748-760`), without an accompanying `contract_class_manager.clear()` in that path.
4. Submit a new transaction (e.g., another deploy or a `replace_class` syscall) referencing class hash `C`. Because `get_compiled_from_class_manager` skips `is_declared` for `V0`, the stale cached entry is returned as valid/runnable, executing successfully instead of failing with `StateError::UndeclaredClassHash`, causing divergence from a node whose cache was cold or explicitly cleared at that point.

Note: I could not fully verify within the available tool calls whether `apollo_batcher::Batcher::revert_block` (or a component it calls) ultimately does clear the `ContractClassManager` cache elsewhere in the codebase; this should be confirmed by a full-repo search for `contract_class_manager.clear()` call sites and their reachability from the batcher's revert path before treating this as conclusively unpatched.

                requested_height: input.height,
            },
        )?;

        if height != input.height {
            return Err(BatcherError::StorageHeightMarkerMismatch {
                marker_height: height.unchecked_next(),
                requested_height: input.height,
            });
        }

        if let Some(height) = self.active_height {
            info!("Aborting all work on height {} due to a revert request.", height);
            self.abort_active_height().await;
        }

        // Wait for the revert commitment to be completed before reverting the storage.
        self.revert_commitment(height).await;

        self.storage_writer.revert_block(height);
        BUILDING_HEIGHT.decrement(1);
        GLOBAL_ROOT_HEIGHT.decrement(1);
        REVERTED_BLOCKS.increment(1);
        Ok(())
    }

use std::sync::{Arc, Mutex, MutexGuard};

use cached::{Cached, SizedCache};

use crate::core::ClassHash;

type ContractLRUCache<T> = SizedCache<ClassHash, T>;
type LockedClassCache<'a, T> = MutexGuard<'a, ContractLRUCache<T>>;

// TODO(Yoni, 1/2/2025): consider defining CachedStateReader.
/// Thread-safe LRU cache for contract classes (Sierra or compiled Casm/Native), optimized for
/// inter-language sharing when `blockifier` compiles as a shared library.
#[derive(Clone, Debug)]
pub struct GlobalContractCache<T: Clone>(pub Arc<Mutex<ContractLRUCache<T>>>);

impl<T: Clone> GlobalContractCache<T> {
    /// Locks the cache for atomic access. Although conceptually shared, writing to this cache is
    /// only possible for one writer at a time.
    pub fn lock(&self) -> LockedClassCache<'_, T> {
        self.0.lock().expect("Global contract cache is poisoned.")
    }

    pub fn get(&self, class_hash: &ClassHash) -> Option<T> {
        self.lock().cache_get(class_hash).cloned()
    }

    pub fn set(&self, class_hash: ClassHash, contract_class: T) {
        self.lock().cache_set(class_hash, contract_class);
    }

    pub fn clear(&mut self) {
        self.lock().cache_clear();
    }

    pub fn new(cache_size: usize) -> Self {
        Self(Arc::new(Mutex::new(ContractLRUCache::<T>::with_size(cache_size))))
    }
}
