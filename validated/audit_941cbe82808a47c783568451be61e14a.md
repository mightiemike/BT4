### Title
`TransactionOutput::ensure_match_transaction_info` omits checkpoint-hash verification, allowing state-root divergence to pass replay/chunk-execution validation - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` (the same style of "narrow verification window" flaw as the TWAP oracle: only a subset of the committed data is actually checked, so a manipulated/divergent value can slip through) validates only `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash against a given `TransactionInfo`. It never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of `TransactionInfoV1` and are covered by the accumulator leaf hash (`TransactionInfo` implements `BCSCryptoHash` over the whole struct).

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  is explicitly documented by an in-repo `TODO(trading-native)` comment as skipping the checkpoint hashes: [2](#0-1) 

This function is the sole re-execution integrity check used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and compares the freshly computed `TransactionOutput` against the `TransactionInfo` fetched from the backup/archive: [3](#0-2) .

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class fields feeding the accumulator leaf hash: [4](#0-3) . These are exactly the values that authenticate the post-execution state Merkle root (state tree), hot-state root, and native-position state root respectively — the ledger's core state-commitment integrity anchors. `execution/executor/src/workflow/do_state_checkpoint.rs` computes and sets these checkpoint hashes when building `TransactionInfoV1`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`/`TRANSACTION_INFO_V1` feature flags gate whether they're populated: [5](#0-4) , [6](#0-5) .

Because `ensure_match_transaction_info` never re-derives or compares these checkpoint hashes, replay/verification tooling built on it (`replay_on_archive`, and any caller using this comparator, e.g. `aptos-move/aptos-debugger`, `aptos-move/cli`) can report a **successful** replay even when the locally computed state root, hot-state root, or position-state root diverges from the value that was actually authenticated and committed to the ledger accumulator at that version. The corrupted/divergent value is the checkpoint-hash field(s) of `TransactionInfo`, not merely an off-chain price feed as in the original TWAP report — but the underlying bug class is identical: a validation routine window that omits checking one of the values it claims to authenticate, letting a manipulated/incorrect value pass as "verified."

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... accepted as valid" and "Hard-fork-only divergence during commit, replay ... accepted as valid" integrity gates. If a node's execution of the state checkpoint, hot-state promotion, or native-position subsystem diverges from the canonical result (due to a bug, non-determinism, or a malicious archive/backup source feeding a tampered `TransactionInfo` alongside a correctly-shaped write set/events/gas/status), `ensure_match_transaction_info`-based replay verification will not catch it. This is a High-severity integrity gap: it can mask silent ledger state corruption or hide the fact that a validator computed a different accumulator-committed root than the network, exactly the "authenticated... proof context" mismatch called out in the required impacts. The comment itself flags this as a known, currently-open gap that must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," i.e., the code acknowledges this is currently a real, live weakness in the verification path guarding a not-yet-fully-enabled but present subsystem.

### Likelihood Explanation
Likelihood is Medium: the affected checkpoint-hash fields are populated only when `TRANSACTION_INFO_V1` / `HOT_STATE_ROOT_IN_TXN_INFO` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS` features are active, and the primary exploitation surface (replay-verify/db-tool) is an operational/auditing tool, not the consensus-critical commit hot path itself. However, the gap is unprivileged from the perspective of anyone relying on `replay_on_archive`/similar tooling as a correctness oracle, and the root cause (an incomplete comparator) is present in shared production code (`types/src/transaction/mod.rs`), not test-only code.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values recomputed by the local execution/state-checkpoint result, whenever the corresponding `TransactionInfo` variant/fields are present (matching the exact wording of the existing TODO). This should be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled by default, and ideally is gated as a required fix for any caller depending on this function as a correctness oracle (`replay_on_archive`, `aptos-debugger`, `cli`, chunk executor paths that may reuse it).

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` + `HOT_STATE_ROOT_IN_TXN_INFO` (or `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) so `TransactionInfoV1.hot_state_checkpoint_hash` (or `position_state_checkpoint_hash`) is populated and committed to the ledger accumulator.
2. Take a backup/archive whose stored `TransactionInfo` has a checkpoint hash that does not match what correct re-execution of the state checkpoint would produce, but whose `write_set`, `events`, `gas_used`, and `status` are left untouched/correct.
3. Run `storage/db-tool/src/replay_on_archive.rs`'s verifier (`execute_and_verify` → `ensure_match_transaction_info`) against this archive: [7](#0-6) .
4. Observe that verification succeeds (`Ok(())`) despite the checkpoint-hash mismatch, because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, confirming the state-root divergence is silently accepted as valid — exactly analogous to how the original TWAP oracle silently accepted a manipulated single-block price as a valid window average.

Note: I was not able to fully trace every call site of `ensure_match_transaction_info` (e.g., its usage in `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) within the available search budget, so I cannot confirm whether any of those paths perform an additional, separate checkpoint-hash check elsewhere that would mitigate this gap for those specific tools; this should be verified with direct file inspection before treating the impact as universal across all callers.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
