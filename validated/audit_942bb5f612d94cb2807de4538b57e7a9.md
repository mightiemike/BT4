### Title
Unbounded full-store scan in `getAssetIssueListByName` allows unauthenticated CPU/DoS amplification via `/wallet/getassetissuelistbyname` - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueListByNameServlet.java])

### Summary
`GetAssetIssueListByNameServlet.fillResponse` calls `Wallet.getAssetIssueListByName`, which unconditionally fetches the entire asset issue list via `getAssetIssueStoreFinal(...).getAllAssetIssues()` and streams over it, with no offset/limit pagination unlike `Wallet.getAssetIssueList(offset, limit)`/`getPaginatedAssetIssueList`. Any unauthenticated HTTP client can trigger this full scan repeatedly at no cost.

### Finding Description
`GetAssetIssueListByNameServlet.doGet`/`doPost` read the `value` parameter and call `wallet.getAssetIssueListByName(...)` directly [1](#0-0) . `Wallet.getAssetIssueListByName` always retrieves the complete asset-issue collection with `getAssetIssueStoreFinal(...).getAllAssetIssues()` before filtering by name, and only calls `BandwidthProcessor.updateUsage` on the entries that match the requested name [2](#0-1) . There is no offset/limit here, in contrast to the paginated variant `getPaginatedAssetIssueList`/`getAssetIssueList(offset,limit)` that exists elsewhere in `Wallet.java` for the same underlying data. This endpoint is exposed with only a generic `RateLimiterServlet` base class (IP/QPS based rate limiting configured via `RateLimiterInterceptor`) and no authentication, signature, fee, or per-request bandwidth/energy accounting — the request never goes through `TransactionCapsule.validateSignature`, permission checks, or any actuator `validate()`/fee-deduction path, since it is a pure read-only HTTP query, not a broadcast transaction. As the asset-issue store grows, every unauthenticated call still forces an O(N) full scan of `AssetIssueStore`/`AssetIssueV2Store`, independent of whether the name matches zero, one, or many records.

### Impact Explanation
This is a DoS-via-RPC-API class issue: since the query cost (O(N) full-store iteration) is not bounded by pagination, is not charged with any bandwidth/energy fee, and is reachable by any anonymous HTTP caller, concurrent requests can impose disproportionate CPU/disk load on the node relative to the trivial cost of sending the request. This matches the "DoS via RPC-API" bounty category, though the severity is limited (read-only endpoint, does not affect chain state or consensus, and the underlying asset-issue table only grows via fee-gated `AssetIssueActuator` transactions — see below on likelihood).

### Likelihood Explanation
The attack requires only network access to the node's HTTP API port (default, no special config), and can be repeated without cost per request. However, the actual attack impact depends on the size of the `AssetIssueStore`/`AssetIssueV2Store`, which only grows through paid `AssetIssueContract` transactions gated by `calcFee()` = `getAssetIssueFee()` and a "one asset per account" restriction in `AssetIssueActuator.validate()` [3](#0-2) [4](#0-3) , so an attacker cannot cheaply inflate the store size themselves at will; the amplification factor is bounded by however many legitimate assets already exist on the running chain (mainnet has a bounded, not attacker-controlled, number of asset issuances). This significantly limits real-world severity relative to the described "seed 100k assets" proof-of-concept, which is not something an unprivileged attacker can trivially achieve without paying the aggregate issuance fees. Additionally, generic IP/QPS rate limiting (`RateLimiterInterceptor`, `GetAssetIssueListByNameServlet extends RateLimiterServlet`) mitigates unbounded request flooding, though it does not eliminate the per-request cost asymmetry.

### Recommendation
Add pagination (offset/limit) to `Wallet.getAssetIssueListByName` and the corresponding servlet/gRPC methods, mirroring `getPaginatedAssetIssueList`, or index asset issues by name so lookups don't require scanning the entire store. Additionally, consider tightening per-endpoint rate limits for full-table-scan endpoints in `RateLimiterInitialization`/`config.conf`.

public void testGetAssetIssueListByNameScansFullStore() {
  // seed N AssetIssueCapsule entries directly into AssetIssueV2Store (test harness bypass of fee)
  for (int i = 0; i < 100_000; i++) {
    AssetIssueContract c = AssetIssueContract.newBuilder()
        .setId(String.valueOf(i))
        .setName(ByteString.copyFromUtf8("token" + i))
        .build();
    dbManager.getChainBaseManager().getAssetIssueV2Store()
        .put(ByteArray.fromString(String.valueOf(i)), new AssetIssueCapsule(c));
  }

  long start = System.nanoTime();
  AssetIssueList result = wallet.getAssetIssueListByName(ByteString.copyFromUtf8("no-such-name"));
  long elapsed = System.nanoTime() - start;

  // result is empty (no match) but the call still scanned all 100k entries via getAllAssetIssues()
  Assert.assertEquals(0, result.getAssetIssueCount());
  // elapsed time scales with store size (assert against a smaller-N baseline to show linear growth)
}

  public AssetIssueList getAssetIssueListByName(ByteString assetName) {
    if (assetName == null || assetName.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getName().equals(assetName))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }
