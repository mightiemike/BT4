### Title
`RequiresRunRole`-gated job-run trigger lacks per-job/EI ownership binding, allowing EI for Bridge A to trigger runs of arbitrary Job B when not in a `build.IsProd()` build - ([File: core/web/auth/auth.go])

### Summary
`RequiresRunRole` in `core/web/auth/auth.go` only checks `user.Role != UserRoleView`; it performs no binding between the caller's identity (External Initiator or run-scoped token) and the specific job/bridge being acted on. On `POST /v2/jobs/:ID/runs`, `AuthenticateExternalInitiator` injects a synthetic `User{Role: UserRoleRun}` into the same session key used by real users, which defeats the handler's own intended "EIs not allowed" restriction and lets an EI trigger `PipelineRunsController.Create` for any integer job ID, not just the job/bridge it was registered for.

### Finding Description
`RequiresRunRole` (`core/web/auth/auth.go:200-217`) only inspects `user.Role`: [1](#0-0) 

The route is registered on a group that accepts EI, token, or session auth: [2](#0-1) 

`AuthenticateExternalInitiator` authenticates the EI against its own bridge credentials, but then plants a **fake user object** under `SessionUserKey` (the same key real logged-in users use), with role `UserRoleRun`: [3](#0-2) 

`PipelineRunsController.Create` explicitly comments that "only users are allowed to run jobs using int IDs - EIs not allowed", and gates that branch on `auth.GetAuthenticatedUser(c)` returning `ok`: [4](#0-3) 

However, `GetAuthenticatedUser` simply reads `SessionUserKey` from the gin context: [5](#0-4) 

Because `AuthenticateExternalInitiator` sets that same key with a synthetic `User`, `isUser` evaluates to `true` for an EI-authenticated request, defeating the intended "EIs not allowed" guard. The handler then calls `app.RunJobV2(ctx, jobID, nil)` using only the `:ID` path parameter supplied by the caller, with **no check that the EI's own bridge/job is the one being referenced**: [6](#0-5) 

`RunJobV2` looks up the job purely by numeric ID and executes its full pipeline (`ExecuteAndInsertFinishedRun`), which can include ETH transaction tasks or other side-effecting tasks unrelated to the caller's own bridge: [7](#0-6) 

This confirms the audited invariant failure: `RequiresRunRole` is a pure role check, and the one place that was supposed to add ownership binding (the `isUser`/"EIs not allowed" check in `PipelineRunsController.Create`) is silently bypassed by the auth layer's session-key collision between real users and external initiators.

The one mitigating control present is that `RunJobV2` is gated by `build.IsProd()`:
```go
if build.IsProd() {
    return 0, errors.New("manual job runs not supported on secure builds")
}
``` [8](#0-7) 
I was unable to locate the `core/build` package source in the index to confirm under which build configurations `IsProd()` returns `true` (e.g., official release/docker builds vs. custom/dev builds), so I cannot fully confirm whether officially distributed production binaries are protected by this gate or not. This is a real limitation on my confidence in end-to-end production exploitability, though the root-cause RBAC/ownership-binding defect in `auth.go`/`pipeline_runs_controller.go` is confirmed and reproducible in code regardless of that flag. [9](#0-8) 

### Impact Explanation
If reached (i.e., in a build where `build.IsProd()` is false), an EI holding valid credentials for Bridge A can trigger a full pipeline run for any other job by numeric ID, including jobs it has no relationship to — matching "unauthorized transaction/workflow execution" and "cross-tenant" impact, since pipeline tasks can include ETH transaction submission via node keys. This is scoped by the `build.IsProd()` gate whose behavior in official distributions I could not fully verify from the indexed code.

### Likelihood Explanation
Preconditions: attacker only needs valid EI credentials for any single bridge (Bridge A) — no admin/session/token privileges are required, satisfying the "unprivileged attacker" constraint. The flaw is reachable via a normal HTTP request to a routed, exposed endpoint (`POST /v2/jobs/:ID/runs`) using standard EI headers. Exploitability is conditional on the node not being run in a `build.IsProd()`-gated binary, which reduces likelihood for standard production deployments but is not something I could conclusively rule out or confirm from the available source.

### Recommendation
1. Do not reuse `SessionUserKey` for external initiators; store EI identity only under `SessionExternalInitiatorKey` and check EI authorization independently of `GetAuthenticatedUser`.
2. In `PipelineRunsController.Create`, explicitly reject requests authenticated via `SessionExternalInitiatorKey` for int-ID job triggering (matching the existing code comment's intent), rather than relying on the coincidentally-shared user key.
3. Add an explicit ownership/ACL check binding the authenticated EI (or run-scoped token) to a specific job/bridge before invoking `RunJobV2`, rather than trusting `RequiresRunRole` alone.
4. Confirm and document that `build.IsProd()` reliably reflects officially distributed binaries; consider removing/hard-disabling `RunJobV2`'s HTTP-reachable path entirely rather than relying on a build-time flag for a network-facing endpoint.

### Proof of Concept
Integration test plan (Go, using existing `cltest` helpers referenced in `core/web/auth/auth_test.go`):
1. Create two jobs, Job A (owned/associated conceptually with Bridge A) and Job B (unrelated), both runnable via `RunJobV2` (e.g., simple webhook-less pipeline jobs), in a non-prod test build (`build.IsProd() == false`, as used by existing tests).
2. Register `ExternalInitiator` credentials for Bridge A only via `ExternalInitiatorsController.Create`.
3. Using an HTTP client authenticated ONLY with Bridge A's EI headers (`static.ExternalInitiatorAccessKeyHeader` / `SecretHeader`), issue `POST /v2/jobs/<JobB.ID>/runs`.
4. Assert expectation: request should be rejected (`403`/`422`, "EIs not allowed" or ownership mismatch).
5. Actual (vulnerable) behavior: `auth.GetAuthenticatedUser(c)` returns `ok=true` due to the synthetic user set in `AuthenticateExternalInitiator`, `isUser` is `true`, and `RunJobV2` executes Job B's pipeline, returning `201`/pipeline run resource — demonstrating cross-bridge/job run triggering not bound to Bridge A.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
