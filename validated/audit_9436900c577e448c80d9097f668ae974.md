### Title
`ensure_match_transaction_info` silently ignores state-checkpoint hash fields, letting replay/verify tooling accept a divergent authenticated state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function used by replay/verify tooling (`storage/db-tool/src/replay_on_archive.rs`) and the debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to check that a locally re-executed transaction matches the authenticated on-chain `TransactionInfo` — validates status, gas, write-set hash, and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks:
- `status` vs expected
- `gas_used` vs expected
- `write_set_hash` (hash of `self.write_set()`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It never recomputes or compares the state (or hot-state/position-state) checkpoint root against `txn_info.state_checkpoint_hash()` / `.hot_state_checkpoint_hash()` / `.position_state_checkpoint_hash()`. The code contains a self-acknowledged TODO documenting exactly this gap: [2](#0-1) , stating that "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This comparator is the sole correctness check used by `replay_on_archive.rs::execute_and_verify`, which calls it directly on locally re-executed `TransactionOutput`s against the archived/expected `TransactionInfo` list: [3](#0-2) . Since `TransactionInfo`'s overall hash (used for accumulator commitment and consensus signing) is computed over *all* fields including the checkpoint hashes, the ledger's cryptographic commitment is still sound at the consensus/storage layer — but this particular tool's field-by-field comparator is not a full substitute for that hash check, and is being relied on as the pass/fail signal for whether locally-computed VM/state output matches the archived authenticated data.

### Impact Explanation
If `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (native/"position" state root computation) or hot-state checkpoint hashing diverges between the replay tool's local execution and the historical on-chain commitment (e.g., due to a state-view/backend bug, an unintended non-determinism in position-state or hot-state root construction, or an upgrade that changes checkpoint semantics), `replay_on_archive` and related debugger/CLI verification paths will report the replay as successful even though the authenticated state-checkpoint root diverges from the correct VM result. This directly matches the required "Hard-fork-only divergence during commit/replay/restore or proof verification" and "Committed state that differs from the correct VM result... accepted as valid" impact classes, because it defeats the specific tool whose job is to catch exactly this class of divergence before it reaches production replay-verification pipelines (`testsuite/replay-verify`). It does not corrupt the actual ledger (accumulator/root hash checks elsewhere remain sound), so the impact is confined to false-negative detection in the verification/debugging tooling rather than a live consensus fork.

### Likelihood Explanation
The gap is deterministic and always present (no attacker interaction needed) — it triggers only when a real state-checkpoint-root divergence bug exists elsewhere (e.g., in native/position state root computation, which is new/gated behind the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature per the TODO). It is a masking/detection failure rather than an active exploit path, so likelihood of a divergence being masked depends on the presence of a separate root-cause bug in checkpoint hash computation, which the code comments indicate is an active area of development (`position_state_checkpoint_hash`, hot-state roots are relatively new fields on `TransactionInfoV1`).

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute (or accept as parameters) the state checkpoint hash, hot-state checkpoint hash, and position-state checkpoint hash produced by local re-execution, and compare each against the corresponding fields in `txn_info`, failing the check (as the other fields already do) on any mismatch — exactly as the existing TODO comment recommends before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Proof of Concept
Not applicable as an active exploit — this is a static code-review finding. Demonstration path: run `replay_on_archive` (or the debugger's replay-verify command) against a version range where the local VM execution produces a `TransactionOutput` whose recomputed state/hot-state/position-state checkpoint root differs from the archived `TransactionInfo`'s corresponding hash field, but whose write set and events are otherwise identical. `ensure_match_transaction_info` at [4](#0-3)  will return `Ok(())`, and `execute_and_verify` at [3](#0-2)  will record no error for that transaction, despite the position/hot-state root diverging from the authenticated ledger state.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
