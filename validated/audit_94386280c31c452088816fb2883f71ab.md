**Analysis:**

The `TransactionArgument::fmt::Debug` implementation does use `hex::encode` to render `U8Vector`/`Serialized` byte payloads for human-readable formatting [1](#0-0) . However, this `Debug` output is never consumed by any path that produces authenticated/committed state:

1. **`TransactionInfo.vm_status`** (the API-facing field) is produced by `explain_vm_status`, which pattern-matches on `ExecutionStatus` variants (`MoveAbort`, `Success`, `OutOfGas`, `ExecutionFailure`, `MiscellaneousError`) and formats abort codes/messages/locations — it never touches a `TransactionArgument` or its `Debug` impl. [2](#0-1) 

2. **Transaction hashing** (`committed_hash()`, used to build `TransactionInfo.transaction_hash`) is derived from BCS serialization (`Serialize`/`Deserialize` derive with `serde_bytes` for the byte-vector variants), not from the `Debug` formatter. [3](#0-2) 

3. `TransactionInfoV0`/`V1` (the committed, hashed ledger record) only stores hashes (`transaction_hash`, `event_root_hash`, `state_change_hash`, etc.) and `ExecutionStatus`, none of which is derived from any `Debug`-formatted string. [4](#0-3) 

The `Debug` impl exists purely for developer-facing logging/printing (similarly, `Script`'s `Debug` hex-encodes its bytecode for the same reason) [5](#0-4) . There is no code path in this repository where `TransactionArgument`'s `Debug`-formatted hex string feeds into a hash, write-set, `TransactionInfo`, or any other authenticated/committed state field. The premise that Debug-derived text is baked into `vm_status` or transaction hashing does not hold in this codebase, so there is no committed-state divergence, proof corruption, or authenticated-response misbinding to report.
