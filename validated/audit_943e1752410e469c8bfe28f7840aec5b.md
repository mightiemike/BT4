### Title
Edit-role users can spawn arbitrary local subprocesses via GenericPlugin `Command`/`EnvVars` through both REST `/v2/jobs` and GraphQL `createJob`, sharing the same missing-allowlist weakness - (File: `plugins/cmd.go`)

### Summary
Both the REST job-creation endpoint and the GraphQL `createJob` mutation are gated only by the "edit" role, yet both funnel OCR2 `GenericPlugin` specs into the identical `validate.ValidatedOracleSpecToml` → `validateGenericPluginSpec` → `plugins.NewCmdFactory` path, which builds and executes an `os/exec.Cmd` from job-spec-controlled `Command`/`EnvVars` fields with no allowlist. An edit-role (non-admin) session can therefore reach process spawning through either entrypoint identically.

### Finding Description
- REST: `POST /v2/jobs` is wrapped with `auth.RequiresEditRole(jc.Create)` [1](#0-0) , and `JobsController.Create` → `validateJobSpec` calls `validate.ValidatedOracleSpecToml(ctx, config.OCR2(), config.Insecure(), tomlString, jc.App.GetLoopRegistrarConfig())` for `job.OffchainReporting2` [2](#0-1) .
- GraphQL: `Resolver.CreateJob` is gated only by `authenticateUserCanEdit(ctx)` [3](#0-2) , and calls the exact same `validate.ValidatedOracleSpecToml(ctx, r.App.GetConfig().OCR2(), r.App.GetConfig().Insecure(), args.Input.TOML, r.App.GetLoopRegistrarConfig())` for `job.OffchainReporting2` [4](#0-3) .
- `authenticateUserCanEdit` only rejects `UserRoleView` and `UserRoleRun`; any session with role `edit` or higher passes [5](#0-4) . `auth.RequiresEditRole` enforces the identical rule server-side for REST [6](#0-5) .
- For `pluginType = "plugin"` (GenericPlugin), `validateSpec` dispatches to `validateGenericPluginSpec(ctx, spec.OCR2OracleSpec, rc)` [7](#0-6) .
- `validateGenericPluginSpec` reads `Command` and `EnvVars` straight from the attacker-supplied `pluginConfig` JSON in the job TOML, only checks the binary exists via `exec.LookPath`, then calls `rc.RegisterLOOP(plugins.CmdConfig{ID, Cmd: command, Env: envVars})`, which starts the LOOPP process via `plugin.Start(ctx)` [8](#0-7) .
- `RegisterLOOP` calls `plugins.NewCmdFactory`, which builds `exec.Command(lcfg.Cmd)` and appends attacker-controlled `lcfg.Env` with no allowlist or sanitation of `Cmd`/`Env` [9](#0-8) .
- The `Command` field in `pluginConfig` overrides the operator-configured plugin command entirely: `command := p.Command; if command == "" { command = plugEnv.Cmd.Get() }` [10](#0-9) , meaning the job-spec author (not just the node operator) decides what executable and what environment gets launched, subject only to it existing on `PATH`/being an existing absolute path.
- No additional authorization check exists between `authenticateUserCanEdit`/`RequiresEditRole` and the point where the process is spawned — there is no admin-only gate specifically for `GenericPlugin`/`Command`/`EnvVars` fields in either the REST or GraphQL code paths.

### Impact Explanation
An edit-role session (a role intended for managing job specs, not node infrastructure) can trigger execution of any pre-existing local executable on the node's `PATH`/filesystem with fully attacker-chosen environment variables, via either REST or GraphQL. This is a privilege-escalation from edit-role to process-level influence on the node host (environment-variable-driven behavior manipulation of trusted local binaries, e.g. interpreter/env-var-based code loading such as `BASH_ENV`, `LD_PRELOAD` when combined with existing files, `PYTHONPATH`, etc.), which exceeds what an "edit" privilege level should be able to do. The invariant that authorization should scale with the sensitivity of the action performed is violated identically in both entrypoints, so both share the same root cause in `plugins/cmd.go NewCmdFactory` and must be fixed together (e.g., via a single shared allowlist/policy check invoked before `RegisterLOOP`/`NewCmdFactory` regardless of entrypoint).

### Likelihood Explanation
Preconditions are minimal and match the stated threat model: attacker needs only a valid session with `edit` role (not admin) — no leaked keys or social engineering required beyond normal login as an edit-permissioned user, which is a standard, commonly-provisioned role in multi-operator Chainlink deployments. Both REST and GraphQL entrypoints are always compiled in and reachable by any authenticated edit user; OCR2 must be enabled (`config.OCR2().Enabled()`), which is common in production nodes running OCR2 jobs. The exploit is fully repeatable and requires no race conditions.

### Recommendation
Add an admin-only authorization gate (or a dedicated, admin-managed allowlist of permitted `Command` values/paths and permitted `EnvVars` keys) before `validateGenericPluginSpec`/`plugins.NewCmdFactory` is reached from either `Resolver.CreateJob` and `JobsController.Create/Update`. Since the root cause is centralized in `plugins.NewCmdFactory` (`plugins/cmd.go`), enforce the check there (or in `RegistrarConfig.RegisterLOOP`) so both entrypoints are fixed by a single shared change rather than duplicating logic in each web layer.

```go
func validateGenericPluginSpec(ctx context.Context, spec *job.OCR2OracleSpec, rc plugins.RegistrarConfig) error {
	p := OCR2GenericPluginConfig{}
	err := json.Unmarshal(spec.PluginConfig.Bytes(), &p)
	if err != nil {
		return err
	}

	if p.PluginName == "" {
		return errors.New("generic config invalid: must provide plugin name")
	}

	if p.OCRVersion != 2 && p.OCRVersion != 3 {
		return errors.New("generic config invalid: only OCR version 2 and 3 are supported")
	}

	// OnchainSigningStrategy is optional
	if spec.OnchainSigningStrategy != nil && len(spec.OnchainSigningStrategy.Bytes()) > 0 {
		onchainSigningStrategy := OCR2OnchainSigningStrategy{}
		err = json.Unmarshal(spec.OnchainSigningStrategy.Bytes(), &onchainSigningStrategy)
		if err != nil {
			return err
		}
	}

	plugEnv := env.NewPlugin(p.PluginName)

	command := p.Command
	if command == "" {
		command = plugEnv.Cmd.Get()
	}

	if command == "" {
		return errors.New("generic config invalid: no command found")
	}

	_, err = exec.LookPath(command)
	if err != nil {
		return fmt.Errorf("failed to find binary  %q", command)
	}

	envVars, err := plugins.ParseEnvFile(plugEnv.Env.Get())
	if err != nil {
		return fmt.Errorf("failed to parse env file: %w", err)
	}
	if len(p.EnvVars) > 0 {
		for k, v := range p.EnvVars {
			envVars = append(envVars, k+"="+v)
		}
	}

	loopID := fmt.Sprintf("%s-%s-%s", p.PluginName, spec.ContractID, spec.GetID())
	// Starting and stopping a LOOPP isn't efficient; ideally, we'd initiate the LOOPP once and then reference
	// it later to conserve resources. This code will be revisited once BCF-3126 is implemented, and we have
	// the ability to reference the LOOPP for future use.
	cmdFn, grpcOpts, err := rc.RegisterLOOP(plugins.CmdConfig{
		ID:  loopID,
		Cmd: command,
		Env: envVars,
	})
	if err != nil {
		return fmt.Errorf("failed to register loop: %w", err)
	}
	defer rc.UnregisterLOOP(loopID)

	pluginLggr, _ := logger.New()
	plugin := reportingplugins.NewLOOPPServiceValidation(pluginLggr, grpcOpts, cmdFn)

	err = plugin.Start(ctx)
	if err != nil {
		return err
	}
	defer plugin.Close()

	return plugin.ValidateConfig(ctx, spec.PluginConfig)
```

```go
// NewCmdFactory is helper to ensure synchronization between the loop registry and os cmd to exec the LOOP
func NewCmdFactory(register func(id string) (*RegisteredLoop, error), lcfg CmdConfig) (func() *exec.Cmd, error) {
	registeredLoop, err := register(lcfg.ID)
	if err != nil {
		return nil, fmt.Errorf("failed to register %s LOOP plugin: %w", lcfg.ID, err)
	}
	return func() *exec.Cmd {
		cmd := exec.Command(lcfg.Cmd) //#nosec G204 -- we control the value of the cmd so the lint/sec error is a false positive
		cmd.Env = append(cmd.Env, lcfg.Env...)
		cmd.Env = append(cmd.Env, registeredLoop.EnvCfg.AsCmdEnv()...)
		return cmd
	}, nil
```
