### Title
Reference-equality (`==`) comparison of `ByteString` in `useAssetAccountNet` misroutes issuer self-transfers to the public/free asset-net pool - ([File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java])

### Summary
`BandwidthProcessor.useAssetAccountNet` decides whether a `TransferAssetContract` sender is the asset issuer by comparing `assetIssueCapsule.getOwnerAddress() == accountCapsule.getAddress()` with reference equality instead of `.equals()`. [1](#0-0)  Because `getOwnerAddress()` and `getAddress()` return freshly-deserialized `ByteString` instances loaded from two different stores (`AssetIssueStore`/`AssetIssueV2Store` vs `AccountStore`), the two objects are never the same reference even when the underlying bytes are identical, so this check is always `false` for a genuine issuer self-transfer.

### Finding Description
`BandwidthProcessor.consume` routes every `TransferAssetContract` through `useAssetAccountNet` before falling back to `useAccountNet`/`useFreeNet`. [2](#0-1)  Inside `useAssetAccountNet`, the intended fast path is: if the sender of the `TransferAssetContract` is the asset's issuer, use the issuer's normal frozen-bandwidth pool (`useAccountNet`) rather than the shared `publicFreeAssetNetLimit`/`freeAssetNetLimit` pools. [3](#0-2)  That branch is implemented with `assetIssueCapsule.getOwnerAddress() == accountCapsule.getAddress()`, a `ByteString` reference comparison. `assetIssueCapsule` is loaded via `Commons.getAssetIssueStoreFinal(...).get(assetName.toByteArray())` and `accountCapsule` is the `AccountStore` entry looked up by `TransactionCapsule.getOwner(contract)`; these are two independently deserialized protobuf objects, so `getOwnerAddress()` and `getAddress()` return distinct `ByteString` instances even for the exact same on-chain address. Elsewhere in the codebase (`MarketCancelOrderActuator`, `VMActuator`, `Wallet.java`) the same kind of address comparison correctly uses `.equals()`, confirming `==` here is inconsistent with the codebase's own convention and not an intentional identity check. [4](#0-3)  As a result, the `if` branch never triggers for a real issuer self-transfer, and execution falls through into the public/free-asset-net-limit accounting path (`publicFreeAssetNetLimit`, `freeAssetNetUsage`, and the separate "issuer's bandwidth" check further down), consuming `publicFreeAssetNetUsage` and `freeAssetNetUsage` instead of the issuer's own bandwidth via `useAccountNet`. [5](#0-4) 

However, this fall-through path is not "free" for the attacker/issuer — it still requires exhausting `publicFreeAssetNetLimit` and `freeAssetNetLimit` checks and it still consumes bandwidth from the issuer's account (`issuerAccountCapsule`, which for a self-transfer is the same account) via `newIssuerNetUsage`/`issuerAccountCapsule.setNetUsage(...)` at lines 358–396, and it increments `publicFreeAssetNetUsage`/`freeAssetNetUsage`. So the practical effect is: issuer self-transfers consume both the issuer's own net usage AND the shared public/free asset pools, rather than only the issuer's own pool as intended — this is a real accounting divergence from design intent, but it is a self-inflicted/attacker-neutral bug (any unprivileged non-issuer attacker gains nothing extra) rather than a mechanism by which an *unprivileged attacker* can drain another party's resources or gain unauthorized value. The person "penalized" by faster public-pool exhaustion is the issuer's own asset ecosystem (shared by all holders of that asset), and this occurs only when the account performing the self-transfer happens to be the asset issuer itself — not from an arbitrary unprivileged attacker acting on someone else's asset.

### Impact Explanation
Confirmed: `useAssetAccountNet`'s issuer fast-path is dead code due to `ByteString` reference-equality misuse, causing issuer self-transfers to consume the shared `publicFreeAssetNetLimit`/`freeAssetNetLimit` pools rather than only the issuer's own frozen bandwidth. This is a real accounting-invariant violation reachable via ordinary `TransferAssetContract` transactions sent by the legitimate issuer to themselves. The impact is scoped to that asset's shared free-bandwidth pools being exhausted faster than intended by the issuer's own self-transfers — it does not grant an unprivileged, non-issuer attacker any new capability to steal value or exhaust another party's bandwidth beyond what the existing (buggy) accounting already allows for any TransferAssetContract sender.

### Likelihood Explanation
Trivially reachable: any account can be an asset issuer and issue a `TransferAssetContract` from itself to itself (or any recipient), and the bug fires deterministically every time because `==` on independently-deserialized `ByteString` objects is essentially always `false`. No special privilege beyond being the asset's issuer is required, and this is fully reproducible in a unit test.

### Recommendation
Change the comparison in `useAssetAccountNet` from reference equality to value equality:
```java
if (assetIssueCapsule.getOwnerAddress().equals(accountCapsule.getAddress())) {
  return useAccountNet(accountCapsule, bytes, now);
}
```
This matches the `.equals()` convention used for `ByteString` address comparisons elsewhere in the codebase (e.g., `MarketCancelOrderActuator`, `VMActuator`, `Wallet.java`).

### Proof of Concept
```java
// chainbase/src/test/java/org/tron/core/db/BandwidthProcessorAssetIssuerTest.java
@Test
public void testUseAssetAccountNet_issuerSelfTransfer_shouldUseAccountNetPath() {
  byte[] issuerAddress = ...; // some valid address
  AccountCapsule issuerAccount = new AccountCapsule(ByteString.copyFrom(issuerAddress), ...);
  issuerAccount.setFrozenForBandwidth(...); // ensure netLimit > 0
  accountStore.put(issuerAccount.createDbKey(), issuerAccount);

  AssetIssueCapsule assetIssueCapsule = new AssetIssueCapsule(...);
  assetIssueCapsule.setOwnerAddress(ByteString.copyFrom(issuerAddress)); // same bytes, different object
  assetIssueStore.put(assetIssueCapsule.createDbKey(), assetIssueCapsule);

  Contract contract = buildTransferAssetContract(issuerAddress, assetName, toAddress, amount);

  // Reload accountCapsule fresh from store to guarantee distinct ByteString instance,
  // mirroring real BandwidthProcessor.consume() behavior.
  AccountCapsule reloaded = accountStore.get(issuerAddress);

  boolean result = bandwidthProcessor.useAssetAccountNet(contract, reloaded, now, bytes);

  // Expected (after fix): issuer path used, publicFreeAssetNetUsage unchanged.
  AssetIssueCapsule after = assetIssueStore.get(assetIssueCapsule.createDbKey());
  assertEquals(0L, after.getPublicFreeAssetNetUsage()); // should remain untouched
  assertTrue(reloaded.getNetUsage() > 0); // consumed via useAccountNet

  // Current buggy behavior: publicFreeAssetNetUsage increases even though sender == issuer,
  // demonstrating the reference-equality branch never triggers.
}
```
Expected outcome pre-fix: `after.getPublicFreeAssetNetUsage() > 0` (bug reproduced — issuer self-transfer wrongly debits the shared public pool). Expected outcome post-fix (using `.equals()`): `publicFreeAssetNetUsage` stays `0` and only `issuerAccount.getNetUsage()` changes.
