### Title
Undeclared Cairo0 (V0) classes can be served from the process-global compiled-class cache without re-validating declaration status - (File: `crates/blockifier/src/state/state_reader_and_contract_manager.rs`)

### Summary
This is analogous to the reSDL bug class: a piece of state tied to an object's authorization (a "declared" class) is cached and later reused across a state-transition boundary (block execution/abort/re-proposal) without re-validating that the authorization is still (or was ever) actually committed. The reSDL report shows a stale `approval` surviving a bridge-out and later being exploited after ownership changes; here, a stale compiled-class cache entry can survive an aborted/reverted block execution and later be served as if it were validly declared, but only for Cairo0 classes — the Cairo1 path has an explicit re-check that the Cairo0 path is missing.

### Finding Description
`StateReaderAndContractManager::get_compiled_from_class_manager` consults a process-wide, cross-block cache (`ContractClassManager` / `GlobalContractCache`, see `crates/blockifier/src/state/global_cache.rs` and `crates/blockifier/src/state/contract_class_manager.rs`) before falling back to the authoritative state reader: [1](#0-0) 

For non-V0 (Cairo1) classes, the code explicitly re-validates the cache hit against the authoritative on-chain declaration state via `is_declared`, with the comment stating the reason: *"existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)"*. For V0 (Cairo0) classes, this branch is empty — no equivalent re-validation is performed: [2](#0-1) 

The `FetchCompiledClasses::is_declared` contract itself documents that it is meaningless for V0 classes ("Cairo 0 classes always return `false`"), which is presumably *why* the check is skipped for V0 rather than applied incorrectly: [3](#0-2) 

The cache that backs this lookup is populated by `set_and_compile` whenever any state reader resolves a class hash (e.g. during speculative/candidate block execution, transaction validation, or a proposal that is later aborted/reverted): [4](#0-3) 

Because this cache is a long-lived, process-global structure (not scoped to a single block's `CachedState`), an entry inserted while processing a candidate/aborted block persists in memory after that block's state changes are discarded. For Cairo1 classes this is safe because `is_declared` re-derives ground truth from committed storage on every cache hit; for Cairo0 classes no such re-derivation exists, so a stale cache entry for a class hash that was never actually committed as declared can still be returned as a valid, runnable compiled class on a later lookup (e.g. triggered by a `deploy_syscall`/`replace_class` syscall, or a `library_call`, referencing that class hash).

### Impact Explanation
If a Cairo0 class hash is compiled into the shared cache during a block/proposal that is subsequently reverted or not committed (e.g., a discarded speculative execution, an aborted block proposal, or a re-orged/rejected candidate block in the batcher), the sequencer instance holding the polluted cache will treat that class hash as usable for any later transaction that references it (deploy, `replace_class`, library call) even though it was never declared in committed state. Other honest sequencer/validator nodes that never executed the discarded block will not have this cache entry and will correctly reject the same transaction as referencing an `UndeclaredClassHash`. This produces a state-transition/commitment divergence between nodes for the same input transaction — i.e., honest-node divergence and a wrong committed state root/class-hash mapping, which falls squarely in the accepted impact categories (wrong committed root, honest-node divergence, or a block later failing Starknet OS re-execution because the DB-backed reader used there does perform the correct check).

### Likelihood Explanation
The trigger requires: (1) a Cairo0 declare (or a transaction resolving a Cairo0 class hash) being speculatively executed by a block builder/executor and then discarded/reverted without the class ever being committed, and (2) a later transaction from any user referencing that exact, uncommitted class hash. This is reachable from ordinary user-submitted transactions (declare + deploy/replace_class/library_call), without requiring any privileged or malicious-operator behavior — it only depends on normal block-building churn (candidate blocks that are rebuilt, aborted, or excluded transactions) which is expected sequencer behavior, not an attacker-controlled input by itself. Confirming the exact reachability of the "populate-then-discard" pathway (e.g., precisely which batcher/executor code path calls `set_and_compile` for a Cairo0 class during a block that is ultimately not committed) requires deeper investigation of the batcher/executor abort flow than could be completed here; this should be verified in a full-repo session.

### Recommendation
Apply the same re-validation performed for Cairo1 classes to Cairo0 classes on cache hit in `get_compiled_from_class_manager`. Since `is_declared` is documented as always returning `false` for V0 class hashes, either: (a) extend the state-reader's declaration query to support Cairo0 classes (e.g., check the deprecated-class-definition table for a block number ≤ current state, mirroring the Cairo1 path), or (b) scope the `ContractClassManager`/`GlobalContractCache` inserts so they are only committed to the shared cache once the containing block/proposal is actually finalized and persisted, preventing uncommitted (reverted) class compilations from ever entering the long-lived cache.

### Proof of Concept
A concrete end-to-end PoC was not constructed because it requires driving the batcher/executor through a specific "compile a Cairo0 class as part of a candidate block, then abort/revert without committing" sequence, which needs full-repo tooling to reproduce (multi-block proposal/consensus harness). The root-cause code asymmetry is directly demonstrated by comparing the two branches in `get_compiled_from_class_manager` (Cairo1 branch re-validates via `is_declared`; Cairo0 branch performs no equivalent check) shown above.

    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
