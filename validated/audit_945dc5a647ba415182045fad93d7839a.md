### Title
Unbounded attacker-controlled array length in deprecated (Cairo 0) syscall parsing enables memory-allocation DoS - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The Cairo 0 ("deprecated") syscall request parser reads array lengths (`keys_len`, `data_len`, `calldata_len`, `payload_size`, etc.) as raw attacker-controlled felts and passes them, unchecked against any upper bound, straight into a VM memory-range read that allocates/collects that many elements — the same bug class as the SEDA `secp256k1_verify` issue where unchecked length parameters caused ~12 GB memory inflation.

### Finding Description
In the deprecated syscalls path, `read_felt_array` reads the declared array size directly as an integer felt from syscall calldata, with no cap: [1](#0-0) 

`array_size` here is `felt_from_ptr(vm, ptr)` — a value fully controlled by the calling (Cairo 0) contract, converted via `usize::try_from(array_size.to_biguint())` (bounded only by `usize::MAX`, i.e. up to ~2^64-1 on 64-bit hosts, or an error if it doesn't fit — but any value below that succeeds). This size is then forwarded to: [2](#0-1) 

`felt_range_from_ptr` calls `vm.get_integer_range(ptr, size)`, a `cairo-vm` primitive that reads `size` contiguous memory cells. This function is invoked, unbounded, from every syscall that accepts a variable-length array in the legacy syscall ABI: `EmitEvent` (`keys`/`data`), `SendMessageToL1` (`payload`), and (indirectly via `read_calldata`/`read_call_params`) `CallContract`, `Deploy`, `LibraryCall`: [3](#0-2) [4](#0-3) [5](#0-4) 

Notably, the *current* (Cairo 1) syscall path fixed this exact class of issue by deriving array size from the *difference of two pointers already present in a populated segment* rather than trusting a raw length felt: [6](#0-5) 

That approach ties the claimed length to memory the caller actually had to populate (and thus pay Cairo steps for), naturally bounding the size. The deprecated/Cairo-0 path at line 931-949, in contrast, trusts an arbitrary declared integer with no relationship to already-written memory and no comparison against any calldata/array-length limit before it is used to size a read/allocation.

### Impact Explanation
Any transaction that invokes (or deploys and invokes) a Cairo 0 class can supply a crafted `EmitEvent`, `SendMessageToL1`, `CallContract`, `LibraryCall`, or `Deploy` syscall with an extremely large declared array length. Depending on how `cairo-vm`'s `get_integer_range` is implemented internally (external dependency, not indexed in this repo — could not be fully verified), this can trigger a large up-front allocation (e.g., `Vec::with_capacity(size)`-style pattern common to such range-read helpers) before any per-cell existence/validity check occurs, independent of the gas actually charged for the syscall body. If so, every validator executing that transaction attempts the same oversized allocation simultaneously, which can exhaust memory and crash multiple validator nodes, causing a chain halt — directly analogous to the H-16 impact.

### Likelihood Explanation
Reachable from a single ordinary transaction: an attacker needs only to declare (or reuse an already-declared) Cairo 0 class and invoke it with a crafted calldata segment specifying the syscall's array-length field as a huge felt. No privileged role, no proposer/operator collusion, and no network-level access is required — this satisfies the "single submitted transaction" reachability bar. However, without being able to confirm the exact allocation strategy inside the external `cairo-vm` crate's `get_integer_range`, I cannot be fully certain the allocation happens *before* the length is validated against actual populated memory; this is the main source of uncertainty in confirming exploitability versus a bounded/step-tracked read.

### Recommendation
In `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`), validate `array_size` against a sane upper bound (e.g., the maximum calldata/array length already enforced elsewhere in the protocol, or the remaining gas budget converted to a max element count) before calling `felt_range_from_ptr`/`vm.get_integer_range`. Alternatively, align the deprecated syscall path with the current syscall implementation's approach of deriving length from pointer differences over already-populated memory rather than trusting a raw declared length felt.

### Proof of Concept
Conceptual reproduction (cannot fully verify VM-internal allocation behavior from this index):
1. Declare a Cairo 0 class whose `__execute__` invokes `emit_event` (or `send_message_to_l1`) with `data_len` (or `payload_size`) set to a very large integer (e.g., near `usize::MAX`) while providing only a minimal/absent data segment.
2. Deploy the class and submit a transaction invoking it.
3. During execution, `EmitEventRequest::read` → `read_felt_array` reads this attacker-supplied length directly and calls `felt_range_from_ptr(vm, ptr, size)` → `vm.get_integer_range(ptr, size)` with the oversized `size`, potentially forcing a large memory allocation attempt on every executing validator node before the call fails due to missing memory cells.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
