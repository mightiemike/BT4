Found the key issue: `ChunkAccessor::insert` in the light-client prover circuit stores proof chunks keyed **only by `wtxid`**, with no sender/authentication check and no existence check before overwrite.

### Title
Unauthenticated chunk overwrite by `wtxid` collision in light-client-prover circuit corrupts aggregate proof reconstruction - (File: crates/light-client-prover/src/circuit/mod.rs, crates/light-client-prover/src/circuit/accessors.rs)

### Summary
### Finding Description
In `run_l1_block`, the `DataOnDa::Chunk(chunk)` branch is processed with **no sender check** ("No need to check sender for chunk", [1](#0-0) ) and is written via `ChunkAccessor::<S>::insert(blob.wtxid(), chunk, &mut working_set)`, whose implementation unconditionally overwrites the storage slot keyed by `wtxid` without checking if a value already exists at that key [2](#0-1) .

This mirrors the reported bug class exactly: like `Manager.addToken` overwriting `vaults[_token]` for a second registration without checking pre-existing state, `ChunkAccessor::insert` overwrites `chunk[wtxid]` for any DA blob whose `wtxid` collides with (or is intentionally set to) an already-stored chunk's `wtxid`, with zero authentication or existence guard.

Later, when an `Aggregate(_, wtxids)` blob is processed by the honest batch prover, the circuit fetches each chunk purely `by wtxid` via `ChunkAccessor::<S>::get(*wtxid, &mut working_set)` and concatenates them to reconstruct the complete proof [3](#0-2) . Since chunk lookups trust the state keyed solely by `wtxid` and nothing checks that the chunk at that key still matches what the prover originally submitted, any unprivileged party can submit a DA blob decoded as `DataOnDa::Chunk` whose `wtxid` matches (or is engineered to match) a chunk referenced by a pending aggregate, and have their attacker-controlled bytes silently substitute the honest chunk in `ChunkAccessor` state before the aggregate is assembled.

### Impact Explanation
If exploited, this breaks the binding between "the blob set the honest batch prover intended to be proved" and "the blob set actually assembled and decompressed by the light-client circuit" — this directly matches the in-scope Critical impact category: *"the blob set proved versus the blob set in the block"*. A corrupted/substituted chunk would cause `DS::decompress_chunks(&complete_proof)` to either fail (denial, out of scope) or, in the worst case, decompress into a different byte stream than what the batch prover produced, which is then fed into `process_complete_proof` and eventually verified against a ZK method ID — potentially causing the light-client prover's JMT state (sequencer commitment records used to verify batch proofs) to diverge between honest provers processing the same L1 block, i.e., "a light client proof split across honest provers."

### Likelihood Explanation
Exploitability depends on being able to produce a DA blob with a `wtxid` colliding with an already-referenced chunk's `wtxid` while still being decoded by the circuit as `DataOnDa::Chunk`. `wtxid` is the witness transaction ID of the DA (Bitcoin) transaction carrying the blob, so an attacker cannot arbitrarily choose it to match another prover's specific chunk's `wtxid` without a preimage/second-preimage attack on the hash used to compute `wtxid`, which is computationally infeasible for an unprivileged attacker in the general case. Given the requirement is a hash collision on `wtxid` (not simply "no signature check"), the likelihood of a practical exploit is Low despite the code lacking any authentication or overwrite-protection check as a defense-in-depth measure — this is best characterized as a missing safety check rather than a demonstrated fully practical exploit.

### Recommendation
Add a defense-in-depth existence check in `ChunkAccessor::insert` (or at the call site) so that a chunk is never silently overwritten once stored for a given `wtxid` — e.g., panic/skip if `ChunkAccessor::get(wtxid, ..).is_some()` and the new body differs from the existing one, analogous to the recommended `addToken` mitigation of rejecting duplicate/conflicting registrations instead of allowing silent overwrite.

### Proof of Concept
1. Batch prover submits `DataOnDa::Chunk(chunk_A)` in DA tx with `wtxid = W`, stored via `ChunkAccessor::insert(W, chunk_A, ..)`.
2. Batch prover later submits `DataOnDa::Aggregate(_, [W, ...])` referencing `W` among the chunks needed to reconstruct a complete proof.
3. Before the light-client prover processes the block containing the aggregate, an attacker (or a reused/second DA transaction with the same `wtxid`, if the DA layer or relayer permits any such condition) causes a second `DataOnDa::Chunk(chunk_B)` blob with the same `wtxid = W` to be processed, silently overwriting `chunk_A` with `chunk_B` in `ChunkAccessor` state (no check exists in `insert` at [4](#0-3) ).
4. When the aggregate is later processed, `ChunkAccessor::get(W, ..)` returns `chunk_B` instead of `chunk_A`, corrupting `complete_proof` reconstruction at [5](#0-4) , without any error being raised at the `Chunk` insertion step.

    /// Inserts a new chunk into the light client prover state
    ///
    /// # Arguments
    /// * `wtxid` - The wtxid that corresponds to the chunk body
    /// * `body` - The chunk data to store
    /// * `working_set` - Mutable reference to the working set for storage access
    pub fn insert(wtxid: [u8; 32], body: Vec<u8>, working_set: &mut WorkingSet<S>) {
        // use `StorageKey::singleton_owned` as a hack to create no serialization key
        let mut key = [0u8; 33]; // 1 prefix + 32 hash

        key[0] = Self::PREFIX;
        key[1..].copy_from_slice(&wtxid);

        let p = Prefix::from_slice(&key);

        let key = StorageKey::singleton_owned(p);

        let value: StorageValue = body.into();

        working_set.set(&key, value);
    }
