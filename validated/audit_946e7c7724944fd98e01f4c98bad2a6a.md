Based on my investigation, the reachable path described is accurate, but the "unbounded CPU burn up to maxEnergyLimitForConstant" premise is not fully supported by the code — there's an independent wall-clock timeout that bounds actual VM execution time.

### Title
Free unauthenticated CPU consumption via `/wallet/triggerconstantcontract` with zero fee/bandwidth cost - ([File: framework/src/main/java/org/tron/core/services/http/TriggerConstantContractServlet.java])

### Summary
`TriggerConstantContractServlet.doPost` accepts an unsigned `TriggerSmartContract` and forwards it straight to `Wallet.triggerConstantContract` → `Wallet.callConstantContract` → `VMActuator` with `isConstantCall=true`, executing real EVM/TVM opcodes without any signature check, bandwidth consumption, or committed fee. [1](#0-0)  The energy limit for such calls defaults to `CommonParameter.maxEnergyLimitForConstant` when no `feeLimit` is set in the request, and no TRX/bandwidth is debited because `rootRepository.commit()` is skipped for `isConstantCall`. [2](#0-1) [3](#0-2) 

### Finding Description
`triggerConstantContract` builds a `TransactionCapsule` from raw, unsigned JSON input and calls `callConstantContract`, which never calls `processTransaction`/`consumeBandwidth`, and never runs `TransactionCapsule.validateSignature` (constant calls are read-only simulations by design). [4](#0-3)  When `feeLimit` is unset/zero in the JSON body, `VMActuator.validate` does not shrink `maxEnergyLimit`, leaving it at the configured `maxEnergyLimitForConstant` default (100,000,000). [5](#0-4)  In `call()`, for `isConstantCall`, `energyLimit = maxEnergyLimit` directly, bypassing all balance/frozen-energy checks that normal (non-constant) calls go through. [6](#0-5) 

However, execution is also bounded by an independent CPU wall-clock cutoff computed via `calculateCpuLimitInUs`, which for constant calls uses `CommonParameter.getConstantCallTimeoutMs()` (a configured timeout, not derived from energy) to set `vmShouldEndInUs`, and the VM raises `OutOfTimeException` once that time budget is exceeded regardless of how much energy remains. [7](#0-6) [8](#0-7)  This means a single constant call cannot run indefinitely or burn CPU proportional to 100,000,000 energy if that energy amount would take longer than the configured timeout — the wall-clock limit, not the energy limit, is generally the binding constraint for tight-loop attacks. This materially weakens (but does not eliminate) the "up to 100M energy of unmetered CPU work per call" framing in the question. The repeatable-request DoS concern (many concurrent free constant calls, each consuming up to `constantCallTimeoutMs` of CPU with zero TRX/bandwidth cost) remains valid, since `RateLimiterServlet` only applies configurable per-endpoint/per-IP QPS limits — not TVM-specific pricing — and these are disabled/loose by default in many configurations. [9](#0-8) 

### Impact Explanation
Confirmed impact class: RPC-API DoS via CPU exhaustion. Each unauthenticated POST can consume up to `constantCallTimeoutMs` of wall-clock VM execution time (bounded, not literally proportional to 100M energy) with zero TRX and zero bandwidth debited, because `callConstantContract` skips `rootRepository.commit()` and never invokes bandwidth/energy consumption on the caller account. Concurrent requests against loop-heavy view functions can exhaust RPC worker threads, degrading node availability for legitimate `triggerconstantcontract`/`estimateenergy` callers. This does not corrupt state, steal funds, or affect consensus — it is a resource-exhaustion issue scoped to a single node's RPC layer, mitigated by the existing (if not code-enforced) rate limiter and CPU timeout.

### Likelihood Explanation
Preconditions: `vm.supportConstant=true` (non-default, but commonly enabled on public full nodes offering read-only contract calls, e.g., for wallets/explorers). No signed transaction, funded account, or fee is required — attacker cost is essentially zero besides finding/deploying a public contract with an expensive view function. Repeatability is high (only bounded by whatever `RateLimiterServlet` QPS/IP policy is configured for `TriggerConstantContractServlet`); if operators leave default/loose rate limiting, an attacker can fire concurrent requests freely.

### Recommendation
- Enforce a stricter, non-bypassable per-IP concurrency/QPS cap specifically for `TriggerConstantContractServlet` and `estimateenergy`, independent of the generic configurable `RateLimiterServlet`.
- Consider capping `maxEnergyLimitForConstant` and `constantCallTimeoutMs` conservatively by default and documenting the DoS risk of enabling `vm.supportConstant`.
- Consider requiring `feeLimit`-scaled energy limits even for constant calls (rather than defaulting to the max) to give operators finer control over worst-case CPU cost per request.
