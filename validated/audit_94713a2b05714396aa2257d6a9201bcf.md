### Title
Hard-coded NEP-141 storage deposit amount in the Wallet Contract's ERC-20 emulation can permanently lock attached NEAR or brick the wallet - (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-wallet-contract's ERC-20 transfer emulation path (`rlp_execute` → `nep_141_storage_balance_callback`) attaches a hard-coded `NEP_141_STORAGE_DEPOSIT_AMOUNT` (1,250 microNEAR) to a `storage_deposit` call on an arbitrary NEP-141 token contract instead of querying that contract's actual `storage_balance_bounds`, mirroring the ReLP bug pattern of using an approximate/static formula instead of an exact on-chain amount for a value-moving operation. This is reachable by any unprivileged relayer/caller submitting an RLP-encoded Ethereum transaction to the wallet contract.

### Finding Description
`inner_rlp_execute` routes `EthEmulationKind::ERC20Transfer` through a multi-step promise chain: it first checks `storage_balance_of` on the target token, and if the receiver is unregistered, `nep_141_storage_balance_callback` issues a `storage_deposit` call funded with a hard-coded constant, followed by the transfer call, all attached to the wallet contract's own promise/account balance: [1](#0-0) [2](#0-1) 

The comment at lines 28–32 explicitly acknowledges the amount is a guess ("the one used by the standard NEP-141 implementation, which essentially all tokens use") rather than a value derived from the specific token's actual `storage_balance_bounds`. Because the wallet contract commits to a single fixed value instead of computing the precise requirement for the specific receiver/token pair, two failure modes exist, both defeating the intended value transfer without a compensating make-whole mechanism inside the wallet contract itself:
- If a token's real minimum storage balance exceeds the hard-coded constant, the `storage_deposit` call (and/or the chained transfer action in the same batched receipt) fails, and any attached NEAR the caller funded for this operation is consumed by gas/burn rather than completing the intended transfer.
- If a token's real minimum storage balance is lower, the excess NEAR sent as `NEP_141_STORAGE_DEPOSIT_AMOUNT` is retained by the (possibly non-standard or malicious) token contract rather than being returned to the end user, since any NEP-145 refund goes back to the immediate predecessor (the wallet contract account), not to the original signer who funded the attached deposit.

This is directly analogous to the ReLP bug: an approximate/static calculation substituted for an exact on-chain amount, in a path reachable by any unprivileged caller, leading to value loss without a self-correcting refund path.

### Impact Explanation
Funds attached by the wallet-contract's signer to cover NEP-141 registration can be silently lost to a non-refunding or higher-bound token contract, or the emulated transfer can revert while gas/NEAR is still consumed, for every unregistered-receiver ERC-20 transfer relayed through the wallet contract. Because `has_in_flight_tx` gating means only one transaction can be in flight at a time, repeated failures of this specific path degrade usability of the wallet contract as a whole, and any value discrepancy is not recoverable without a follow-up transaction, since the wallet contract has no logic to detect or reclaim an over/under-estimated storage deposit.

### Likelihood Explanation
Any unprivileged relayer or user can trigger this by submitting an RLP-encoded ERC-20 `transfer` call to an unregistered receiver against any NEP-141 token whose `storage_balance_bounds` differs from the hard-coded constant, or that does not refund excess deposits per spec. No special privileges, validator status, or network conditions are required — only a standard `rlp_execute` call.

### Recommendation
Instead of hard-coding `NEP_141_STORAGE_DEPOSIT_AMOUNT`, query the target token's `storage_balance_bounds` on-chain (as the original design comment says was avoided for gas reasons) and attach exactly the required amount, refunding any caller-supplied surplus back to the original signer (not just the wallet's own account) via an explicit follow-up transfer in `rlp_execute_callback`, and treat a mismatched/failed `storage_deposit` as a hard failure of the whole chain (aborting the subsequent transfer action) rather than letting it silently proceed in the same batched receipt.

### Proof of Concept
Not executable from the available context — the mechanism is established purely by reading the fixed-constant logic at [3](#0-2)  in combination with the promise-chain construction in `inner_rlp_execute` (`Promise::new(token_id.clone()).function_call("storage_balance_of", ...)` at lines 445-457 of the same file). Reproducing end-to-end requires deploying a NEP-141 token with `storage_balance_bounds().min` set above 1,250 microNEAR (or a non-refunding implementation) and driving an `ERC20Transfer` through `rlp_execute` to an unregistered receiver.
