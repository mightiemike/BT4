### Title
Market-level per-block index cache is invalidated only by block-time change, not by direct vault state mutation (`socialize-debt`) - (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/vault/v0-vault-*.clar`)

### Summary
`market.clar` maintains a per-block cache of each vault's borrow/liquidity indexes (`index-cache`, keyed by `{timestamp: stacks-block-time, aid}`) so that multiple market operations touching the same asset in the same block avoid re-calling the vault. This cache is only ever refreshed by calling `accrue`/`accrue-and-cache`, which recomputes indexes from `last-update`/time-delta. However, vaults also expose `socialize-debt`, which writes `lindex`/`index` directly via `var-set` to socialize a shortfall, completely bypassing the `accrue` path. Because `market.clar`'s cache invalidation is driven purely by `stacks-block-time`, not by an explicit "the vault's index changed" signal, any market read of `get-cached-indexes` for that asset later in the same block will return the pre-write-down value that no longer matches vault storage.

### Finding Description
`accrue-and-cache` populates `index-cache` for `{timestamp: stacks-block-time, aid}` on a cache MISS, and simply returns the cached entry on a HIT for the rest of that block: [1](#0-0) 

All downstream market logic (borrow, repay, liquidation collateral/debt valuation) reads indexes exclusively through this cache via `get-cached-indexes`, e.g.: [2](#0-1) [3](#0-2) 

Meanwhile, each vault's `socialize-debt` mutates `lindex` (and `principal-scaled`/`total-borrowed`) by direct `var-set`, independent of the `accrue`→`next-index`/`next-liquidity-index` computation that the cache is built from: [4](#0-3) 

`accrue`'s own cache-freshness check only compares the *computed* next index against the currently stored one, and market's cache freshness is keyed purely by `stacks-block-time`: [5](#0-4) 

So the invalidation event ("the vault's index moved") and the cache's invalidation trigger ("the block-time changed") are two different things. A direct-write mutation like `socialize-debt` changes the value that `get-cached-indexes` is supposed to reflect without changing `stacks-block-time`, so any already-warmed cache entry for that asset remains stale for the rest of the block.

Sequence of the analog to the Timeswap `state.y` bug (bound value not invalidated by the event that changes its source, later reused):
1. Any user transaction early in a block touches asset X (e.g., a small `borrow`/`repay`/`collateral-add`), causing `accrue-and-cache` to run a cache MISS and store `{index: I1, lindex: L1}` for `{timestamp: T, aid: X}`.
2. Later in the same block, a liquidation (or other bad-debt path) triggers vault X's `socialize-debt`, which directly `var-set`s `lindex` to a new, lower value `L2` reflecting a shortfall write-down — this is the "event that invalidates the cached value."
3. Still in the same block (`stacks-block-time` unchanged), a subsequent transaction on asset X (e.g., `repay`, `borrow`, or a ztoken redemption/valuation path) calls `get-cached-indexes(X)`, which hits the cache and returns the stale `L1` instead of the updated `L2`.
4. Any accounting that depends on `lindex`/`index` for asset X in that later transaction (share pricing, debt valuation, redemption amount) is computed against the pre-write-down value instead of the true post-write-down state.

### Impact Explanation
Because the ztoken share price (via `lindex`) and debt index are used to compute how much underlying a redemption/repayment/liquidation is entitled to, operating on the stale, pre-write-down index lets a user extract value based on a liquidity index that no longer reflects the vault's true (reduced) backing. This is a temporary-freezing/mispricing condition confined to the remainder of the block in which the write-down occurs, and can result in other users' funds (remaining depositors bearing the socialized loss) being further diluted by anyone who transacts against the stale cached index before the block ends — a single-block, single-transaction-chain interleaving, not two users interfering with each other maliciously but a stale-value bug triggered by the protocol's own write-down mechanism.

### Likelihood Explanation
This requires (a) a `socialize-debt` write-down to occur in the same block as (b) a prior cache-warming operation and (c) a subsequent cache-read operation for the same asset — a specific but realistic sequencing achievable by any actor who can trigger a liquidation/bad-debt socialization and follow it with a normal market call in the same block. No privileged access or DAO action is required; `socialize-debt` firing during a permissionless liquidation is enough to create the divergence.

### Recommendation
Invalidate (or refresh) the market's `index-cache` entry for an asset whenever the underlying vault's `index`/`lindex` is mutated outside of the standard `accrue` path — e.g., have `socialize-debt` return the updated indexes and have market's `accrue-and-cache` overwrite (not skip on hit) the cache immediately after any such call, or key cache validity on a "last-mutated" nonce/height read from the vault rather than solely on `stacks-block-time`.

### Proof of Concept
Not independently executable from the indexed context alone — the exact call sites that route to `socialize-debt` from `market.clar`'s liquidation flow could not be fully confirmed within the available tool budget (grep found 20 references across trait declarations, private wrapper functions, and the public liquidation path, but the surrounding liquidation logic that decides *when* `socialize-debt` fires was not fully retrieved). The core caching/mutation-bypass mechanism above is directly supported by the cited code; confirming the exact reachable trigger condition for `socialize-debt` within `liquidate()` would require a follow-up review of `mainnet/contracts/market/v0-4-market.clar` around its liquidation bad-debt handling and the corresponding `vault-socialize-debt` wrapper.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
