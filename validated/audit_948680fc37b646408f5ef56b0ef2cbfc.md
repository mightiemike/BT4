## Finding

The mechanism described in the question is real and is present exactly as suspected in `x/uvalidator/abci.go`'s `AllocateTokens` function.

### Title
Distribution module decimal-ledger over-crediting via truncated UV boost transfer - (`x/uvalidator/abci.go`)

### Summary
`AllocateTokens` records the *full, untruncated* decimal `reward` for every active UV validator via `k.DistributionKeeper.AllocateTokensToValidator(ctx, validator, reward)`, but only physically transfers the *truncated integer* sum (`extraCoins`) to the distribution module account, while the truncated fractional remainder (`extraChange`) is diverted back to the `FeeCollector` instead of staying inside the distribution module's own decimal state.

### Finding Description [1](#0-0) 

For each active UV validator, `powerFraction := power.QuoTruncate(effectiveTotalPower)` and `reward := feesCollected.MulDecTruncate(powerFraction)` are computed at full decimal precision and immediately committed into the distribution module's own internal decimal ledger via `AllocateTokensToValidator`. This call only mutates distribution's internal `ValidatorCurrentRewards`/`ValidatorOutstandingRewards` decimal state — it performs no bank transfer of its own, so the caller is responsible for ensuring the recorded decimal amount is fully backed by a corresponding physical transfer. [2](#0-1) 

After all UV rewards are recorded, the code aggregates them (`allocated`) and only *then* truncates to an integer (`extraCoins, extraChange := allocated.TruncateDecimal()`). Only `extraCoins` is sent to the distribution module (`SendCoinsFromModuleToModule(..., types.ModuleName, distrtypes.ModuleName, extraCoins)`). The fractional remainder `extraChange` — which was already committed into the UV validators' decimal ledgers via the earlier `AllocateTokensToValidator` calls — is folded into `remainingFinal` and sent to `FeeCollector` instead of remaining backed inside distribution.

This differs from the standard Cosmos SDK `x/distribution` `AllocateTokens` implementation, where the *entire* fee amount is transferred into the module account first, and any fractional remainder is kept as `DecCoins` inside `FeePool.CommunityPool` (in-module decimal state), so the decimal ledger and the bank balance always match exactly. Here, the uvalidator module instead externalizes the fractional dust to a different module account (`FeeCollector`) after having already "spent" it in distribution's ledger, breaking the invariant `sum(distribution decimal ledgers) == distribution module bank balance`.

### Impact Explanation
This is a genuine (if small) per-block over-crediting of distribution's internal decimal reward ledger relative to its actual token holdings, matching the "corruption of ... accounting" impact category. Because it recurs every block that has at least one active UV and nonzero collected fees — which is ordinary, unprivileged network activity, not something requiring a malicious validator or UV — the deficit compounds indefinitely with no corrective mechanism. Given enough blocks, the distribution module's recorded liabilities to validators can exceed its actual bank balance, which could eventually surface as failed/short reward or commission withdrawals for honest validators/delegators.

That said, the magnitude per block is strictly bounded to less than one unit of the smallest fee denomination (typically `upc`), since `TruncateDecimal` is applied once to the aggregate sum, not per validator. This makes it a slow, low-value drain rather than an immediately drainable exploit, and total token supply is still conserved system-wide (the diverted dust is not destroyed, just misrouted away from where it was already promised).

### Likelihood Explanation
Triggers automatically and deterministically on every block with ≥1 active UV and nonzero fees — no attacker action beyond normal fee-paying transactions is needed. This is a systemic design flaw rather than something an unprivileged attacker specifically weaponizes for direct personal gain; the diverted dust benefits the general (non-UV) fee pool rather than an attacker.

### Recommendation
Mirror the standard SDK pattern: transfer the entire `feesCollectedInt` amount destined for the UV boost into the distribution module account and keep any fractional remainder as `DecCoins` inside distribution's own state (e.g. add it into `FeePool.CommunityPool` or otherwise retain it as decimal dust within distribution), rather than truncating first and forwarding the fractional remainder to `FeeCollector`. Alternatively, truncate `reward` to an integer coin *before* calling `AllocateTokensToValidator`, and only ever pass values that are 1:1 backed by an equivalent bank transfer.

### Proof of Concept
Extend the existing tests (e.g. `test/integration/uvalidator/abci_test.go`'s `TestAllocateTokens`) to additionally sum the *decimal* amounts passed into `AllocateTokensToValidator` (via a spy/mock `DistributionKeeper`) across many simulated blocks with varying `feeAmount` and vote powers, and assert that the cumulative decimal-recorded total across all UVs never exceeds the cumulative `extraCoins` physically transferred to the distribution module account. With odd fee amounts (e.g. repeating the `feeAmount = 999` case across N blocks), the cumulative gap grows monotonically, confirming the decimal ledger diverges from the physically transferred balance over time.
