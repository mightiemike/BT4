### Title
Truncated 10-Byte Workflow Name Hash Enables Workflow-Selector Collisions in Gateway HTTP Trigger Routing - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The Gateway's HTTP trigger handler resolves a workflow by `(workflowOwner, workflowName, workflowTag)` when the caller does not supply the full 32-byte `workflowID`. The `workflowName` component is not the raw name but `HashTruncateName(name)` — a SHA‑256 hash truncated to only 10 bytes (80 bits) [1](#0-0) . This mirrors the reported bug class exactly: a cryptographic hash is deliberately truncated to shrink the identifier, reducing the collision resistance of what is used as a unique lookup key in a trust-boundary-relevant routing table.

### Finding Description
`resolveWorkflowID` builds a `workflowReference{workflowOwner, workflowName, workflowTag}` key using `workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)` and looks it up in `h.workflowMetadataHandler.workflowRefToID` [2](#0-1) . The constant `WorkflowNameHashLength = 22` (0x + 20 hex chars = 10 bytes) confirms the identifier space is only 80 bits [3](#0-2) .

`HashTruncateName` is also used to validate incoming workflow-authorization metadata (`WorkflowNameHashLength` check) as the sole discriminator of workflow identity within an owner+tag scope [4](#0-3) . Because workflow *names* are user-chosen strings supplied by workflow owners (unprivileged users who register workflows on the Workflow Registry contract), an attacker can search offline for a name whose 10-byte truncated hash collides with a victim's already-registered workflow name (under the same owner+tag, or exploiting any place where owner is not strictly bound). An 80-bit space is not computationally infeasible to brute-force offline (unlike a full 256-bit hash), especially if any birthday-style multi-target search or targeted preimage search against a known victim's hash is performed.

This is a direct structural analog to the Lombard `calcDestinationId` finding: a hash function's output is truncated to a much smaller number of bytes and then used as if it were a globally unique identifier for dispatching/authorizing an action, with no other entropy or salting added.

### Impact Explanation
If a collision is found, an attacker-controlled workflow name resolves to the `workflowReference` cache entry of a different, legitimate workflow (same owner+tag would normally still gate access, but the collision breaks the guarantee that distinct names cannot be confused — e.g., under `GetWorkflowID`/`GetWorkflowReference` reverse maps keyed only by the truncated hash) [4](#0-3) . This can cause HTTP trigger requests intended for one workflow to be misrouted/misresolved to another workflow's ID, or allow a maliciously named workflow to spoof the identity used for authorized-key lookups tied to `workflowID` derived from the colliding name. This falls under "misreporting/data tampering" / "unauthorized action routing" since Gateway request dispatch and JWT-authorized-key checks depend on this resolved `workflowID`.

### Likelihood Explanation
Exploitation requires an attacker to register a workflow (a permissionless, unprivileged action via the on-chain Workflow Registry) with a chosen name and brute-force it until its 10-byte hash matches a target reference. 80 bits is smaller than typical strong-collision-resistance recommendations for identifiers used in trust decisions, though still requires significant offline compute (not trivial, but meaningfully weaker than the full 256-bit SHA-256 output the code already computes and then discards 22 of 32 bytes of).

### Recommendation
Do not truncate the workflow-name hash for use as a security-relevant lookup key; use the full 32-byte hash (or bind the full `workflowID`, which already combines owner+name+binary+config, instead of a name-only truncated hash) wherever `workflowRefToID`/`workflowIDToRef`/authorization lookups occur. If the 10-byte truncation is required for on-chain gas/storage reasons, ensure it is never treated as collision-resistant for authorization or routing decisions in the Gateway, and always require a match on the full `workflowID` for authorization-sensitive operations.

### Proof of Concept
Not independently verified end-to-end (would require registering two workflow names offline until their `HashTruncateName` outputs collide and then confirming Gateway routes the second name's HTTP trigger request to the first's `workflowID`); this is inferred from the exact code path shown in `resolveWorkflowID` and `HashTruncateName` usage [1](#0-0)  and the workflow-name-hash constant `WorkflowNameHashLength = 22` [3](#0-2) . The `HashTruncateName` function itself is defined in the external `chainlink-common` module, which is outside this repo's index, so I could not directly inspect its exact byte-truncation logic beyond the 10-byte length confirmed by multiple call sites and comments (e.g., `core/services/workflows/types/workflow_meta.go` and `deployment/data-feeds/changeset/utils.go` both confirm "first 10 bytes of sha256(workflow_name)") [5](#0-4) [6](#0-5) .

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
