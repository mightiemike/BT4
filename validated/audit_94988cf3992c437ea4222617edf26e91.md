### Title
Uncontrolled Recursion in `bytecode_hash_node` During Compiled Class Hash Computation - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` recursively walks the `NestedIntList` segment-structure tree of a CASM contract's bytecode to compute the compiled class hash, with no depth bound. The tree's shape is derived from the declared Sierra program's control-flow structure (functions/branches), which is attacker-controlled input via a `DECLARE` transaction. A pathologically deep segment structure can drive the recursion deep enough to overflow the stack, crashing the compiling/hashing process — directly analogous to the reported llama.cpp CVE-2026-52130 (uncontrolled recursion in schema/grammar processing causing DoS).

### Finding Description
`bytecode_hash_node` in [1](#0-0)  recurses once per nested `Node` level of the `HashableNestedIntList` (`NestedIntList`) without any depth check or iterative fallback:
```
} else {
    let inner_nodes = node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child)).collect_vec();
    ...
}
```
This is invoked from `bytecode_hash` → `hash_inner` → `HashableCompiledClass::hash`, which is called right after Sierra→CASM compilation in the class-declaration/compilation pipeline: `SierraCompiler::compile` calls `executable_class.hash(&HashVersion::V2)` in [2](#0-1) , which is itself invoked by `ClassManager::add_class` in [3](#0-2)  whenever a new class is declared.

The `bytecode_segment_lengths` `NestedIntList` is produced by the (trusted) `cairo-lang-starknet-classes` compiler from the Sierra program's structure, but its nesting depth tracks the program's function/branch nesting depth, which the declarer fully controls by crafting deeply nested functions/branches in the submitted Sierra class. `validate_class_length` in [4](#0-3)  only checks the serialized object *size*, not the segmentation tree *depth*, so a large-but-size-bounded class can still encode very deep nesting.

The identical unbounded-recursion pattern also exists in the Starknet OS hint helper `create_bytecode_segment_structure_inner` ( [5](#0-4) ) and `BytecodeSegmentNode::hash` ( [6](#0-5) ), both reachable during OS re-execution of a block containing the malicious declared class.

### Impact Explanation
A stack overflow during class compilation/hashing crashes the class-compilation worker (and, via the OS-side duplicate logic, potentially the OS re-execution / proving pipeline as well). Since class declaration and compilation happen for every node/sequencer processing the block (and again during Starknet OS re-execution for proving), a single crafted `DECLARE` transaction could cause repeated crashes across sequencers/provers processing that class, resulting in denial of service and inability to make progress on blocks referencing that class — matching the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Reachable directly from an unprivileged `DECLARE` transaction: an attacker only needs to craft a Sierra program with deeply nested branch/function structure that compiles successfully and passes the existing size-only validation (`validate_class_length`), then submit it for declaration. No special privileges are required, making likelihood high, though the exact required nesting depth to trigger a stack overflow depends on stack size and per-frame cost, which is unverified without dynamic testing.

### Recommendation
Add an explicit maximum-depth check (or convert the recursive traversal to an iterative, explicit-stack-based algorithm) in `bytecode_hash_node` and its OS-side/hint counterpart `create_bytecode_segment_structure_inner`, rejecting or bounding classes whose segment-structure nesting exceeds a safe limit before hashing/compiling. Alternatively, bound the compiler's own bytecode segmentation depth during Sierra→CASM compilation.

### Proof of Concept
1. Author a Sierra source program with functions containing thousands of levels of nested branches/inline calls, arranged so the CASM compiler's bytecode segmentation (`bytecode_segment_lengths`) produces an equally deep `NestedIntList::Node(vec![NestedIntList::Node(vec![...])])` chain, while keeping overall bytecode/class size under `max_compiled_contract_class_object_size`.
2. Submit this as the `contract_class` in a `DECLARE` transaction to the gateway.
3. When the class manager compiles the class and calls `.hash(&HashVersion::V2)` ( [7](#0-6) ), `bytecode_hash_node` recurses to the crafted depth, exhausting the call stack and crashing the compiling process.

Note: I could not run the compiler to empirically determine the exact nesting depth needed to overflow the stack (no execution environment available), so likelihood/severity here rests on the structural analysis of the unbounded recursion rather than a confirmed crash trace.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

impl BytecodeSegmentNode {
    pub(crate) fn hash<H: HashFunction>(&self) -> StarkHash {
        match self {
            BytecodeSegmentNode::Leaf(leaf) => H::hash_array(&leaf.data),
            BytecodeSegmentNode::InnerNode(inner_node) => {
                let flatten_input: Vec<_> = inner_node
                    .segments
                    .iter()
                    .flat_map(|segment| [Felt::from(segment.length), segment.node.hash::<H>()])
                    .collect();
                H::hash_array(&flatten_input) + Felt::ONE
            }
        }
    }

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
