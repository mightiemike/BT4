### Title
Wallet Contract silently upgrades a user-requested zero/absent allowance into an `Unlimited` spending allowance when adding a FunctionCall access key - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The referenced audit finding describes a case where a contract disables the dangerous surface (`transfer`, `transferFrom`, `approve`) but forgets to disable a related mechanism (`increaseAllowance`/`decreaseAllowance`) that can silently re-grant the very permission the contract was trying to restrict. The NEAR Wallet Contract has an analogous flaw: it explicitly blocks adding a `FullAccess` key via `AddKey`, but the sibling `FunctionCall` branch of the same action collapses a user-specified zero or absent allowance into `Allowance::Unlimited`, effectively re-granting unrestricted spending power through the "restricted" code path.

### Finding Description
The Wallet Contract's `AddKey` handling explicitly forbids granting `FullAccess` keys because that "would be too dangerous": [1](#0-0) 

Immediately below, for the `FunctionCall` permission branch, the contract converts the user-supplied, ABI-decoded `allowance: Option<NearToken>` into a promise action allowance:

```rust
Promise::new(target).add_access_key_allowance_with_nonce(
    action.public_key,
    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
    access.receiver_id,
    access.method_names.join(","),
    action.access_key.nonce,
)
``` [2](#0-1) 

The `near_action::FunctionCallPermission` struct that carries this value across the Ethereum-emulation boundary is user/relayer controlled data parsed from the RLP-encoded transaction: [3](#0-2) 

`near_sdk::Allowance::limited(amount)` is documented and implemented (in the `near-sdk` dependency, not part of this repo's index) to return `None` when the requested amount is zero — this mirrors the low-level protocol convention already documented for `promise_batch_action_add_key_with_function_call`: "If the `allowance` value... is `0`, the allowance is set to `None` (which means unlimited allowance)" [4](#0-3) . Because of this, both `access.allowance == None` (no allowance specified) **and** `access.allowance == Some(0)` (an explicit "no-spend" allowance encoded by the user/relayer) collapse to the same `.unwrap_or(Allowance::Unlimited)` fallback. There is no intermediate check that rejects a zero-but-present allowance or maps it to a bounded/near-zero key; the contract simply issues an **unlimited** allowance key any time the decoded allowance is not a positive number.

This means a user's or relayer's intent to add a strictly bounded FunctionCall access key (e.g., for a specific `receiver_id`/`method_names` pair, meant to spend at most a small, explicitly-declared amount of the account's NEAR balance on gas) can be silently converted into a key with no spending limit at all, exactly analogous to the referenced report's pattern where a value-limiting mechanism intended to be constrained (allowance) is not actually enforced along a specific code path, letting the counter-party operate with far more permission than granted.

### Impact Explanation
The resulting `FunctionCall` access key is capable of spending the *entire* NEAR balance of the ETH-implicit wallet account as gas/fees for any call to the specified `receiver_id`, rather than being capped to the value the account owner explicitly signed for. Any relayer, dApp, or other counterparty who is handed such a key (added via a signed transaction where the allowance field was zero/omitted, whether intentionally as a boundary condition or through client-side encoding defaults) obtains materially greater spending authority over the account's NEAR balance than the owner intended, which constitutes unauthorized value movement capability against the wallet account's funds.

### Likelihood Explanation
Reachable by any unprivileged caller who can submit an RLP-encoded transaction to `rlp_execute` requesting an `AddKey` action with a `FunctionCall` permission whose ABI-encoded allowance field is zero (the default/unset value in most ABI encodings) — this requires no special privilege beyond owning (or being handed a validly-signed) ETH-implicit account transaction, and matches a natural, likely-common encoding mistake (leaving the allowance field at its zero default) rather than a contrived edge case.

### Recommendation
In `action_to_promise` (runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs), do not silently default a zero/absent allowance to `Allowance::Unlimited`. Explicitly distinguish "no allowance specified" (which may legitimately map to unlimited, matching documented Near semantics) from "an explicit zero value was supplied," and reject (or otherwise safely handle, e.g. by using a minimal non-zero allowance) the latter case with a clear `UserError`, so that a user/relayer cannot be silently granted more spending authority than was requested.

### Proof of Concept
1. Deploy a Wallet Contract for an ETH-implicit account with some NEAR balance.
2. Construct and sign an Ethereum-style transaction (via the wallet contract's `addKey` ABI selector, see `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs:28-31`) that encodes an `AddKey` action with `is_full_access = false`, `receiver_id` set to some target contract, `method_names` set to a specific method, and `allowance = 0`.
3. Submit this transaction via `rlp_execute`.
4. Observe (via `view_access_key`) that the resulting on-chain `FunctionCallPermission.allowance` is `None` (i.e. `Allowance::Unlimited`), not a zero/near-zero bounded allowance as the raw ABI value would suggest.
5. Have the holder of that new key send further `FunctionCall` actions to `receiver_id`; the wallet account's NEAR balance can be drained for gas fees far beyond what a "0" allowance value would normally suggest to the signer.

Note: I was unable to directly inspect the `near_sdk::Allowance::limited` implementation because it lives in the external `near-sdk` dependency, which is outside this repository's indexed contents. My conclusion about its zero-allowance-to-`None` behavior is inferred from the wallet contract's `.and_then(...).unwrap_or(Allowance::Unlimited)` pattern (which only makes semantic sense if `limited(0)` returns `None`) and from the documented low-level host-function convention in `docs/RuntimeSpec/Components/BindingsSpec/PromisesAPI.md` that a raw allowance value of `0` means "unlimited." If a Devin session with full dependency access confirms `Allowance::limited`'s exact behavior differs from this documented convention, the severity/validity of this finding should be re-assessed accordingly.
