### Title
Unchecked `storeSession()` result in OAuth callback and token-exchange flows can leave the app in a broken/orphaned auth state - (File: `packages/apps/shopify-app-express/src/auth/auth-callback.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/auth-code-flow.ts`, `packages/apps/shopify-app-react-router/src/server/authenticate/admin/strategies/token-exchange.ts`)

### Summary
`SessionStorage.storeSession()` is documented to return a `boolean` indicating whether the write succeeded or failed, exactly mirroring the semantics that ERC-721 `safeTransferFrom` is meant to enforce (verify the operation was actually accepted before treating the flow as complete). Across the OAuth callback and token-exchange authentication paths, this return value is awaited but never checked, so a storage failure is silently swallowed and the code proceeds as if the session/access token had been durably persisted.

### Finding Description
The `SessionStorage` contract explicitly defines `storeSession(session: Session): Promise<boolean>` as returning `true` if successfully stored, `false` otherwise, and instructs implementers to catch internal errors and return `false` rather than throw [1](#0-0) . Multiple bundled adapters follow exactly this pattern, catching errors and returning `false` instead of propagating an exception, e.g. the CSV example adapter documented for implementers [2](#0-1) .

Despite this documented contract, the core OAuth callback handlers never check the boolean result:

- Express: `await config.sessionStorage.storeSession(callbackResponse.session);` is followed immediately by webhook registration and the `afterAuth` hook, with no check on success [3](#0-2) .
- Remix (auth-code-flow): `await config.sessionStorage!.storeSession(session);` is followed by conditional online-token OAuth continuation and the `afterAuth` hook, again without checking the result [4](#0-3) .
- React Router (token-exchange strategy): both the offline and online `storeSession` calls are unchecked before the `afterAuth` hook fires [5](#0-4) .
- `invalidateAccessToken` helpers (used to clear a stale/invalid access token) in both Express and Remix also fire-and-forget `storeSession` [6](#0-5) [7](#0-6) .

The library's own migration documentation demonstrates the correct pattern (checking the boolean and logging on `false`) [8](#0-7) , which the shipped `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` middlewares do not follow.

### Impact Explanation
If the configured `SessionStorage` implementation returns `false` on a transient write failure (as the documented contract expects) rather than throwing, the OAuth callback will still: set `res.locals.shopify.session`, register webhooks with the freshly-issued access token, run the `afterAuth` hook, and redirect the merchant back into the embedded app as if installation succeeded - even though no session/access token was actually persisted. On the very next request, session lookup will fail because nothing was stored, forcing the merchant into a repeated or broken OAuth loop, and any webhooks already registered will reference a token the app can never retrieve again. This is a self-inflicted denial-of-service of the auth handler for the affected shop, requiring an app reinstall/token-request cycle to recover, directly analogous to the referenced report where an unchecked/unsafe transfer completion caused the asset to become permanently stuck.

### Likelihood Explanation
This does not require attacker privilege beyond the normal single-merchant install/auth flow; any transient storage-layer failure (DB contention, connection drop, custom adapter validation rejecting the row) that a `SessionStorage` implementation surfaces as `false` per the documented interface will trigger this silently-broken state. Because the interface contract itself encourages returning `false` instead of throwing, this is a realistic occurrence rather than a purely theoretical one.

### Recommendation
Check the boolean returned by `storeSession()` (and `deleteSession`/`deleteSessions` where used for token invalidation) in `auth-callback.ts`, `auth-code-flow.ts`, `token-exchange.ts`, and the `invalidateAccessToken` helpers. On `false`, abort the OAuth/token-exchange flow, log/alert, and return an error response (e.g., redirect back to `/auth` or surface a 500) instead of proceeding to register webhooks, set the session in locals, or invoke `afterAuth`.

### Proof of Concept
1. Configure a custom `SessionStorage` (or induce a failure in a bundled adapter) so `storeSession()` returns `false` on write failure, per the documented contract.
2. Complete the OAuth install flow for a shop; the callback handler in `packages/apps/shopify-app-express/src/auth/auth-callback.ts` (or the Remix/React Router equivalents) ignores the `false` result and proceeds to register webhooks, populate `res.locals.shopify.session`/session context, run `afterAuth`, and redirect the merchant into the app.
3. On the merchant's next request, session lookup fails (nothing was ever persisted), demonstrating the app is now stuck in a broken authenticated-looking state that requires a full reinstall to fix.

import {Session} from '@shopify/shopify-api';

import type {BasicParams} from '../../types';

export async function invalidateAccessToken(
  params: BasicParams,
  session: Session,
): Promise<void> {
  const {logger, config} = params;

  logger.debug(`Invalidating access token for session - ${session.id}`, {
    shop: session.shop,
  });

  session.accessToken = undefined;
  await config.sessionStorage!.storeSession(session);
}
