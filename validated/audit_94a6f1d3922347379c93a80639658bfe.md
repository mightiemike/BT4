### Title
Stale block-cached vault index used for ztoken price resolution after vault state mutates mid-transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches vault liquidity indexes in `index-cache` keyed only by `{ timestamp: stacks-block-time, aid: aid }`, and once a cache entry exists for that timestamp/asset pair it is returned verbatim by `accrue-and-cache` without re-querying the vault, for every subsequent read in the same block/transaction [1](#0-0)  . The cache is documented to invalidate only when the block timestamp changes, i.e. "automatically invalidated each block," with "no manual invalidation needed" for intra-block state changes [2](#0-1) .

### Finding Description
`resolve-ztoken` (used to price zToken collateral/debt for health checks and liquidation) fetches the cached `lindex` via `get-cached-indexes` and scales the underlying price by it [1](#0-0) . That cache is populated the first time any operation in a transaction calls `accrue-and-cache aid`, matching on the cache map; if a cache entry already exists for `{stacks-block-time, aid}` it is returned as-is instead of re-invoking `vault-accrue`, per the documented pattern in `market.clar` [3](#0-2) .

Within a single transaction that performs multiple sequential actions on the same asset (e.g. a combined operation that first triggers a price/health-check read for asset `aid`, caching its index, and later — still in the same block/timestamp — performs a mutating vault call such as borrow/repay/deposit/withdraw on that same asset which genuinely advances the vault's real liquidity index), the cache key does not change because `stacks-block-time` is identical for the whole transaction. Any later `resolve-ztoken`/`price-resolve` call in that same transaction will read the now-stale `lindex` captured before the mutating call, rather than the vault's actual post-mutation index. The value bound is the `{index, lindex}` pair written into `index-cache` at the moment of the first `accrue-and-cache` call; the event that should invalidate it is the subsequent vault-state-mutating call on the same asset within the same transaction; the later use is any subsequent `price-resolve`/`resolve-ztoken` call in that transaction that trusts the cache instead of re-accruing.

This is possible under Clarity evaluation order because the cache check (`match cached? existing existing ...`) is a pure map lookup keyed on a value (`stacks-block-time`) that Clarity fixes for the entire transaction, so no re-entrant call within the same transaction can force a cache miss once the entry has been written.

### Impact Explanation
If a multi-step market entry point resolves zToken collateral value using the stale, pre-mutation index while a debt/collateral-changing action has already executed earlier in the same transaction, the health check or liquidation valuation can be computed against an index that no longer reflects the vault's true state. This can allow a user to pass a health check that should have failed with the up-to-date index, or cause a liquidator/user to misprice collateral, resulting in temporary freezing/mispricing of protocol funds tied to that asset (undercollateralized position surviving a check it should have failed).

### Likelihood Explanation
Requires a market entry point that (a) triggers a cached price/index read for an asset and (b) later in the same call/transaction performs a vault-mutating action on that same asset before a final health/liquidation check re-reads the price. This depends on the exact call ordering inside the market's public entry points, which was not fully confirmed for `v0-4-market.clar`'s public functions within the available index; the cache mechanism itself and its block-scoped (not mutation-scoped) invalidation is confirmed.

### Recommendation
Invalidate or bypass `index-cache` whenever a vault-mutating operation is performed on the same `aid` within the same transaction, rather than relying solely on `stacks-block-time` as the cache key, or re-derive the index directly from the vault immediately after any mutating call before using it for pricing/health checks.

### Proof of Concept
1. Within one transaction, call a market entry point that triggers a price resolution for asset `aid` (populating `index-cache` at `{ timestamp: stacks-block-time, aid }` via `accrue-and-cache`).
2. In the same transaction, execute a vault-mutating operation on `aid` (e.g., borrow/repay) that changes the vault's real liquidity index.
3. Still in the same transaction, trigger another price resolution / health check for `aid`; `resolve-ztoken` returns the pre-mutation cached `lindex` instead of the updated value, because `stacks-block-time` has not changed [1](#0-0) .

Note: I could not confirm within the indexed files exactly which public market entry point sequences a caching read and a mutating vault call on the same asset within one transaction before a final health check — this would need direct inspection of the public functions in `mainnet/contracts/market/v0-4-market.clar` (grep confirmed 38 references to `accrue-and-cache`/`index-cache` in that file but line-level content for those call sites was not retrieved).

;; In market.clar
(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache- cache-key)))
    (match cached?
      existing existing
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
```

**Purpose:** 
- Multiple price resolutions for the same vault within a single block use cached indexes
- Avoids redundant cross-contract calls to vaults
- Significantly reduces gas costs for transactions involving multiple ztoken prices

**Cache Invalidation:** Cache is timestamp-based using `stacks-block-time`, automatically invalidating when a new block is processed.
