### Title
Vault `accrue` pause-passthrough lets `stacks-block-time`-frozen indexes understate live debt/collateral during a legitimate accrual pause - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Every vault's `accrue` function, when the `accrue` pause flag is set, returns the *current* (last-accrued) `index`/`lindex` wrapped in `(ok ...)` instead of reverting: `;; PAUSED: Pass-through without reverting`. Because `next-index`/`next-liquidity-index` are computed purely from elapsed time since `last-update` (which is only advanced on a *successful* non-paused accrual), unpausing later causes the vault to retroactively apply the *entire* elapsed interest in one jump. During the pause window itself, `market.clar`'s `accrue-and-cache` caches these stale values for the block and every downstream consumer (health checks, debt valuation, zToken collateral pricing) treats them as authoritative, understating real debt and real zToken collateral value for the duration of the pause.

### Finding Description
`accrue-and-cache` in `mainnet/contracts/market/v0-4-market.clar:245-257` calls `vault-accrue`/vault `accrue` and caches whatever it returns per `{timestamp: stacks-block-time, aid}`: [1](#0-0) 

The vault's `accrue` implementation (identical across all vaults, e.g. `mainnet/contracts/vault/v0-vault-stx.clar`) explicitly bypasses recomputation while paused: [2](#0-1) 

`last-update` is only advanced inside the non-paused branch, when the index actually changed: [3](#0-2) 

`last-update` is initialized from `stacks-block-time` and only mutated in the non-paused branch: [4](#0-3) 

This cached, stale `index`/`lindex` is then consumed by market-level logic that determines a user's real debt and zToken collateral value:
- Debt notional valuation uses `accrue-and-cache` output directly: `(let ((cached (unwrap-panic (accrue-and-cache asset-id))) (ib (get index cached)) ...)` - [5](#0-4) 
- zToken price resolution (`resolve-ztoken`) reads the same cache: [6](#0-5) 
- `borrow()` explicitly primes the cache and then computes health using it: [7](#0-6) 

Because `next-index`/`calc-index-next` compute interest strictly from elapsed wall-clock time relative to `last-update` (not from any pause-aware counter), any interest that *should* have accrued during the pause is never lost — it is simply deferred and applied all at once the next time a non-paused `accrue()` runs. This confirms the "value bound → not invalidated on the event that should invalidate it → later use" chain:
1. **Value bound**: `index`/`lindex` cached in `market.clar`'s `index-cache` map at `accrue-and-cache` time, sourced from the vault's `(var-get index)`/`(var-get lindex)`.
2. **Event that should invalidate it but doesn't**: the DAO/operator sets the vault's `accrue` pause flag true (an ordinary operational lever, not a compromise) mid-lifecycle, e.g. during oracle maintenance. From that point every `accrue()` call returns the frozen index unconditionally without reverting, and `last-update` stops moving.
3. **Later use**: any `borrow`, `collateral-add`, `collateral-remove`, or `liquidate` call executed while paused reads this frozen index/lindex through `accrue-and-cache`/`get-cached-indexes`, and market health checks (`is-healthy`, `is-healthy-with-mask`) are evaluated against debt/collateral values that omit all interest that has genuinely elapsed since `last-update`.

Under normal Clarity single-block evaluation, this is fully "live": within the pause window, a borrower whose true (uncached, real-time) debt has crept above the liquidation threshold appears healthy to `borrow()`/`collateral-remove()`/`liquidate()` because the cached debt index is frozen at the pre-pause value. The borrower can therefore extract additional value (new borrows, collateral withdrawal) that a correctly-accruing index would have blocked. When the vault is later unpaused, the deferred interest is applied in one lump catch-up against the (now larger) principal, but the extracted value/withdrawn collateral is already gone — leaving the vault under-collateralized for that position, i.e., unrecoverable bad debt that lenders absorb.

### Impact Explanation
This is not the deliberate liquidation-of-disabled-collateral carve-out; it is a general debt/collateral valuation staleness bug triggered by the `accrue` pause's pass-through-without-reverting design. It allows a borrower to `borrow()` more or `collateral-remove()` more than their true health would allow while the frozen cache understates debt, and to avoid `liquidate()` while genuinely liquidatable. The resulting shortfall is unrecoverable once the position has been drained — this lands on **Critical (protocol insolvency / permanent freezing of funds)** for the affected vault's lenders, since the deferred interest that should have accrued to suppliers is effectively lost once the borrower's position is drained below what the (correctly caught-up) debt requires.

### Likelihood Explanation
Requires the `accrue` pause flag to be set on a vault (an ordinary, non-compromised operational action available to the DAO/operator for maintenance or incident response) and a borrower to act during that window before it is lifted. This is plausible any time accrual is paused for a live vault with outstanding debt, since pausing accrual is advertised as safe/non-disruptive ("pass-through without reverting") specifically so that other operations continue to work — but that continuation is exactly what exposes stale valuations to exploitation.

### Recommendation
When `accrue` is paused, `accrue()` should either (a) revert (`ERR-PAUSED`) so dependent market operations that need fresh indexes fail closed instead of silently using stale caches, or (b) if pass-through is required for availability, market-level consumers of `accrue-and-cache`/`get-cached-indexes` must be made aware the index is stale (e.g., by also pausing the corresponding market operations — `borrow`, `collateral-remove`, `liquidate` — for assets whose vault has `accrue` paused) rather than treating the frozen value as an authoritative health input.

### Proof of Concept
1. Borrower opens a position with debt near (but below) the liquidation threshold in `v0-4-market.clar`, secured against a vault (e.g. `v0-vault-stx.clar`).
2. DAO pauses `accrue` on that vault (`pause-states.accrue = true`) for an unrelated maintenance reason; `last-update` freezes at that block's `stacks-block-time`.
3. Real time passes (interest genuinely accrues in the sense that `calc-index-next` would produce a higher index if computed), but every `accrue()` call now returns the old `{index, lindex}` per `mainnet/contracts/vault/v0-vault-stx.clar:837-845`, and `market.clar`'s `accrue-and-cache` caches this stale pair per block.
4. While still paused, the borrower calls `market.clar`'s `borrow()` (or `collateral-remove()`); `get-notional-evaluation`/`calculate-asset-notional-value` compute debt using the stale cached index (`mainnet/contracts/market/v0-4-market.clar:563-569`), understating true debt, so `is-healthy-with-mask` passes and the borrow/withdrawal succeeds.
5. DAO unpauses `accrue`; the vault's next `accrue()` call jumps `index`/`lindex` forward to reflect the full elapsed interest since the original `last-update` (per `calc-index-next`/`calc-multiplier-delta`), retroactively revealing the borrower was already past the liquidation threshold — but the extra borrowed funds/withdrawn collateral are already out of the protocol's control, leaving unrecoverable bad debt for suppliers.
