### Title
Non-embedded multi-shop session cookie collision causes cross-tenant session DoS - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
The GTE Perps bug lets an unprivileged actor occupy a shared boundary slot (`tickSize`-aligned best-ask price) so that legitimate future actors can never successfully claim the analogous slot on the other side, permanently freezing that half of the system. The same class of bug — an attacker-influenced shared, unscoped resource key silently colliding with and overwriting a victim's slot — exists in shopify-app-js's non-embedded OAuth session cookie handling: the `shopify_app_session` cookie is written at a single default path (`/`) shared by every shop, so authenticating a second shop in the same browser silently overwrites the first shop's session cookie.

### Finding Description
For non-embedded apps, `callback()` in `oauth.ts` writes the session id into a single cookie named `SESSION_COOKIE_NAME` (`shopify_app_session`) at a path controlled by `config.cookiePath`, which defaults to `'/'` when unset: [1](#0-0) 

Because the cookie path defaults to the root (`/`) for every shop, and the cookie name is not scoped per-shop, any two shops authenticating in the same browser session (two tabs, two custom-app installs, or a merchant switching between stores) share exactly one cookie slot. The second OAuth completion silently clobbers the cookie value that pointed at the first shop's session, exactly as the SELL backstop order at `tickSize` in the audit report permanently occupies the shared "best ask" slot and blocks any future BUY order from landing at a valid price.

The consuming code, `getCurrentSessionId()`, has no per-shop disambiguation for non-embedded apps — it just reads and verifies whichever session id currently sits in that single cookie: [2](#0-1) 

This collision is acknowledged by the project itself in the CHANGELOG, which added an **opt-in** `cookiePath` factory option specifically to fix it, confirming the default configuration remains vulnerable: [3](#0-2) 

### Impact Explanation
Once shop B's cookie overwrites shop A's, `getCurrentSessionId` for shop A's tab will resolve (and get verified) as shop B's session id. Any subsequent authenticated request from shop A's browser context is silently redirected to operate against shop B's session/shop — this is a session-storage/cookie collision that produces either (a) a hard DoS of the auth handler for shop A (its session is unrecoverable until it re-authenticates), or (b) in some app implementations that trust the resolved session id to select tenant data, a cross-tenant session mix-up. Unlike the perps report where the attack is purely griefing, here the blast radius is every merchant running a non-embedded, multi-shop-capable app who does not explicitly set a per-shop `cookiePath` function — which is the default posture of the library.

### Likelihood Explanation
Requires no privileged access: any actor who can get two distinct shop OAuth flows to complete in the same browser (e.g., an app that supports multiple shop installs, or a user simply managing two stores from one browser) triggers the collision. Since `cookiePath` defaults to `/` and adopting the mitigating factory function is opt-in and undocumented in most integration guides, most non-embedded deployments remain exposed by default.

### Recommendation
Make per-shop cookie scoping the default rather than opt-in — e.g., derive a default `cookiePath` (or cookie name suffix) from the shop domain when `config.cookiePath` is not explicitly provided, instead of falling back to `'/'` in `oauth.ts` (`cookiePath ?? '/'`). At minimum, emit a runtime warning when a non-embedded app has multiple shops authenticating without a shop-scoped `cookiePath`, analogous to adding the "one-tick buffer" mitigation in the audit report to prevent shared-slot collisions.

### Proof of Concept
1. Configure a non-embedded shopify-app-js app without setting `cookiePath` (default `'/'`).
2. In Browser Tab 1, complete OAuth for `shop-a.myshopify.com` → `shopify_app_session` cookie set to session id for shop A at path `/`.
3. In Browser Tab 2 (same browser/profile), complete OAuth for `shop-b.myshopify.com` → same-named cookie at same path `/` is overwritten with shop B's session id, per `oauth.ts` lines 219-229.
4. Return to Tab 1 and make an authenticated request; `getCurrentSessionId()` reads the single shared cookie and now resolves to shop B's session id, per `session-utils.ts` lines 76-79, denying/derailing shop A's session — reproducing the "frozen/blocked slot" DoS pattern from the original report.

```markdown
- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```
