### Title
Unbounded native recursion when assembling transaction status over a long receipt chain can stack-overflow the node process - (File: `chain/chain/src/chain.rs`, function `get_recursive_transaction_results`)

### Summary

`Chain::get_recursive_transaction_results` (chain/chain/src/chain.rs:3190-3207) recursively walks the receipt-outcome DAG produced by a transaction, one native Rust stack frame per hop, with no depth counter and no iterative fallback. It is invoked by both `get_final_transaction_result` (used by the "wait until executed" `tx` JSON-RPC path) and `get_partial_transaction_result_option` (used by the "as-far-as-executed" `tx` JSON-RPC path), both of which are directly reachable by any unauthenticated JSON-RPC caller querying transaction status. An attacker who submits ordinary function-call/cross-contract-call transactions that keep re-issuing themselves (the exact pattern already exercised in-repo by `max_self_recursion_delay` / `recurse`, see `runtime/near-test-contracts/test-contract-rs/src/lib.rs:887-921` and `integration-tests/src/tests/runtime/test_evil_contracts.rs:91-156`) can grow a single logical transaction's receipt chain across many blocks, since gas is replenished per-receipt and per-block. When a client later calls the `tx`/`EXPERIMENTAL_tx_status` RPC method against a node that has finalized this transaction, the node's recursive walk depth equals the length of the accumulated receipt chain, which is not bounded by any single-block/single-receipt limit (`max_gas_burnt`, `max_actions_per_receipt`, etc. only bound recursion *within one apply*, not across the lifetime of a logical retry/callback chain).

### Finding Description

This is the direct structural analog of the reported `graphql-php` bug class: a recursive-descent traversal over attacker-influenced nested/linked data with **no recursion-depth counter and no iterative rewrite**, driven purely by native call-stack depth, reachable from an unprivileged, unauthenticated entry point (here: a JSON-RPC `tx` status query instead of an HTTP GraphQL body).

```rust
// chain/chain/src/chain.rs:3190
fn get_recursive_transaction_results(
    &self,
    outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
    id: &CryptoHash,
    require_all_outcomes: bool,
) -> Result<(), Error> {
    let outcome = match self.get_execution_outcome(id) {
        Ok(outcome) => outcome,
        Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
    };
    outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
    let outcome_idx = outcomes.len() - 1;
    for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
        let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
        self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
    }
    Ok(())
}

Both are reached via the JSON-RPC transaction-status pipeline (`tx`, `EXPERIMENTAL_tx_status`) documented in the RPC architecture notes as backed by `ViewClientActor`/`chain/client/src/view_client_actor.rs`, which is a standard, unprivileged, unauthenticated RPC surface. [5](#0-4) 

The recursion depth is set by the *total length of the receipt chain a transaction has spawned over its lifetime*, not by any single-apply limit. The in-repo test contracts and tests demonstrate that a contract can deliberately extend its own receipt chain across many blocks by re-issuing itself with `promise_batch_create`/`promise_batch_action_function_call_weight` every time it is invoked with fresh prepaid gas:

and the corresponding test explicitly documents that this pattern is used to "delay conclusion of a receipt for as long as possible through the use of self cross-contract calls," achieving depths in the hundreds *within a single top-level call already*: [7](#0-6) 

Per-apply/per-block gas limits (`max_gas_burnt`, `max_actions_per_receipt`) bound the depth achievable in a single chunk, but nothing bounds the *cumulative* chain length across successive blocks — an attacker simply keeps refunding gas to the same self-chaining contract call over many blocks (as `max_self_recursion_delay` is explicitly designed to do), building a receipt chain whose outcome graph is thousands to millions of hops deep, entirely off-chain-state-root-affecting and paid for at ordinary gas prices. Because `get_recursive_transaction_results` is tail-like but implemented with real (non-tail-call-optimized, since it appends to `outcomes` after the recursive call return and propagates `?`) recursion, each hop consumes a full stack frame (locals, the `for` loop state, the `?`-propagated `Result`, etc.), and Rust does not protect against native stack overflow the way exceptions do — a real stack overflow aborts the process (`SIGSEGV`/`SIGABRT`), exactly as described for the PHP analog: it is not catchable by any `Result`/`?`-based error handling in the surrounding RPC-actor code.

### Impact Explanation

A single unauthenticated JSON-RPC caller who queries `tx` (or `EXPERIMENTAL_tx_status`) for a transaction hash whose receipt chain the attacker has grown sufficiently deep can crash the node process serving that RPC request (`ViewClientActor`'s thread/task, and potentially the whole node process depending on Rust's stack-overflow handling in that build configuration). Because JSON-RPC is served to arbitrary external callers and `ViewClientActor` typically shares process space with the rest of the node (chunk production, block validation, etc. in validator/RPC-combo nodes), this is a transaction-triggered denial of service against nodes that later serve status queries for the poisoned transaction hash — satisfying the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation

Building the receipt chain requires only ordinary, permitted transaction/contract-call actions (no privileged operations), and the repository's own test helpers (`max_self_recursion_delay`, `recurse`) show this self-chaining pattern is a known, exercised capability of the runtime, already reaching depths in the hundreds within a single top-level call and easily extendable across many blocks by simply re-funding/re-invoking. The attacker only needs enough NEAR to pay gas for enough hops; there is no other permission barrier. The main uncertainty is the exact number of hops needed to exhaust a typical thread's stack given Rust's per-frame size for this function and its call chain (`get_execution_outcome`, view conversions, DB reads) — this could not be precisely measured with the tools available, but the structural bug (no depth bound, no iterative alternative) is confirmed by direct code inspection.

### Recommendation

Rewrite `get_recursive_transaction_results` to use an explicit work-list/queue (BFS or DFS with a `Vec`-based stack) instead of native recursion, exactly as recommended for the graphql-php parser (Option 2 in the source report). As defense in depth, also add a `max_receipt_chain_depth`/`max_outcomes` cap (mirroring the `NonDelegateAction` one-hop anti-recursion pattern already used elsewhere in the codebase) so that `get_final_transaction_result`/`get_partial_transaction_result_option` return a bounded/paginated error instead of attempting to materialize an arbitrarily large outcome chain in one response.

### Proof of Concept

Conceptual (not executed, since this environment has no code-execution access):
1. Deploy the existing test contract exposing `max_self_recursion_delay` (already in-repo).
2. Call `max_self_recursion_delay` once, then repeatedly, across many blocks, always in the context of the same original transaction's receipt-id chain, refilling prepaid gas each time so the self-chain keeps extending (this pattern is already validated by `slow_test_self_delay` to reach depth ~56–221 within a *single* invocation's gas budget).
3. Repeat over enough blocks/epochs to grow the chain to tens/hundreds of thousands of receipts.
4. From an unprivileged JSON-RPC client, call `tx` (with `wait_until` requiring full execution) or `EXPERIMENTAL_tx_status` for the original transaction hash.
5. Observe that `Chain::get_final_transaction_result` → `get_recursive_transaction_results` recurses once per receipt in the chain; at sufficient depth this exhausts the native thread stack and crashes the serving process, exactly mirroring the PHP parser's uncatchable SIGSEGV failure mode.

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}

fn slow_test_self_delay() {
    let node = setup_test_contract(near_test_contracts::rs_contract());
    let res = node
        .user()
        .function_call(
            "alice.near".parse().unwrap(),
            "test_contract.alice.near".parse().unwrap(),
            "max_self_recursion_delay",
            vec![0; 4],
            MAX_GAS,
            Balance::ZERO,
        )
        .unwrap();

    // The exact expected depth varies depending on the set of enabled features.
    // When test_features are enabled, the test contract becomes larger and the calls to it are more expensive.
    // When nightly is enabled, the gas costs change a bit.
    // The test makes sure that the depth is within the expected range, but it doesn't check an exact value
    // to avoid having separate cases for every possible combination of features.
    let min_expected_depth = 56;
    // The upper limit has been recently bumped to 221 from the previous value of 62 after the
    // adjustment of a function call gas costs.
    let max_expected_depth = 221;
    match res.status {
        FinalExecutionStatus::SuccessValue(depth_bytes) => {
            let depth = u32::from_be_bytes(depth_bytes.try_into().unwrap());
            assert!(
                depth >= min_expected_depth,
                "The function has recursed fewer times than expected: {depth} < {min_expected_depth}",
            );
            assert!(
                depth <= max_expected_depth,
                "The function has recursed more times than expected: {depth} > {max_expected_depth}",
            );
        }
        _ => panic!("Expected success, got: {:?}", res),
    }
