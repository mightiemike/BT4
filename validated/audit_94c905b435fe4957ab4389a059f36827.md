### Title
Poison-microblock report accepted with two identical microblock headers, enabling reward theft from a non-equivocating miner - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`handle_poison_microblock` never checks that `mblock_header_1 != mblock_header_2` before calling `check_microblock_header_signer`, which only verifies that the two headers recover to the same public key hash. Submitting the same signed microblock header twice satisfies this check trivially, since a header trivially has the same signer as itself, allowing an attacker to file a "poison" report against a miner who never actually equivocated.

### Finding Description
The broken equality is: **"a valid poison report exists" should imply "the miner produced two distinct, conflicting signed microblocks (equivocation)"**. `check_microblock_header_signer` at `stackslib/src/chainstate/stacks/db/transactions.rs:686-713` only recovers `pkh1` and `pkh2` from `mblock_hdr_1` and `mblock_hdr_2` respectively and errors only if `pkh1 != pkh2`; it never verifies the two headers are structurally distinct (different block hash, different signature, or different sequence with the same parent). [1](#0-0) 

`handle_poison_microblock` then calls this check directly on the attacker-supplied `mblock_header_1`/`mblock_header_2` with no prior equality guard, looks up `get_microblock_pubkey_hash_height(&pubkh)`, verifies maturity, and — if no lower-sequence report already exists — calls `insert_microblock_poison` with `mblock_header_1.sequence` as the reported fork point. [2](#0-1) 

If the attacker submits `mblock_header_1 == mblock_header_2` (a bit-for-bit clone of a single, legitimately-signed microblock header the miner actually produced), `check_recover_pubkey()` on both copies recovers the identical `pkh`, so the equality check trivially passes — there is no forged signature, no second distinct message, and thus no real equivocation. Yet the code path proceeds exactly as if two conflicting microblocks existed, inserting a poison report crediting the sender/reporter.

I was not able to fully verify within the available search budget whether an earlier layer (e.g., static payload validation in `stackslib/src/chainstate/stacks/transaction.rs` or `stackslib/src/chainstate/stacks/db/blocks.rs`, both of which reference `PoisonMicroblock`) enforces `mblock_header_1 != mblock_header_2` or requires differing `sequence`/`block_hash` fields before this function is reached. If such a guard exists elsewhere in the transaction static-validation pipeline, it would neutralize this specific path. Given the explicit lack of any such check inside `check_microblock_header_signer` or `handle_poison_microblock` themselves, and no evidence found of such a guard during this investigation, the finding stands on the code inspected, but this residual uncertainty should be resolved by directly reading `stackslib/src/chainstate/stacks/transaction.rs` (`PoisonMicroblock` payload validation) and `blocks.rs` before merging any fix.

### Impact Explanation
If confirmed unguarded, this allows an attacker to file a slashing report against an honest miner using only a copy of a microblock header the miner already broadcast publicly (no private key access needed, since microblock headers are public once broadcast). This would redirect the punished miner's coinbase reward to the attacker/reporter without any actual equivocation, i.e., block-reward theft from an honest party — matching the "Critical: block-reward theft" category in the rubric, contingent on there being no upstream duplicate-header rejection.

### Likelihood Explanation
The precondition is simply that a miner produced at least one microblock whose pubkey-hash record is still within the `MINER_REWARD_MATURITY` window, which happens continuously in normal operation. The attacker needs no stake, no signing key, and no privileged role — only the ability to observe a broadcast microblock header and resubmit it twice inside a `PoisonMicroblock` transaction, which is well within an unprivileged participant's capability if no earlier check blocks identical headers.

### Recommendation
Add an explicit inequality check at the start of `handle_poison_microblock` (or inside `check_microblock_header_signer`) requiring that `mblock_header_1` and `mblock_header_2` differ in a way that constitutes genuine equivocation — e.g., same `sequence` number but different `block_hash`/signature, or otherwise structurally distinct signed messages — and reject the transaction with `InvalidStacksTransaction` if the two headers are identical.

### Proof of Concept
1. In a chainstate integration test harness, have a miner legitimately sign one `StacksMicroblockHeader` and have its pubkey hash recorded via the normal microblock-processing path that calls `insert_microblock_pubkey_hash`.
2. Clone that header (`mblock_header_2 = mblock_header_1.clone()`), construct a `TransactionPayload::PoisonMicroblock(mblock_header_1, mblock_header_2)`, sign and broadcast it from an unrelated attacker account.
3. Mine the transaction and call `get_poison_microblock_report`/inspect `get_microblock_poison_report(mblock_pubk_height)`, asserting a report now exists crediting the attacker.
4. Assert, at block maturation, that the honest miner's `MaturedMinerRewards.recipient` reward is redirected to the attacker despite `mblock_header_1 == mblock_header_2` and no distinct second signed microblock ever having been produced — i.e., assert the equality "poison report exists" no longer implies "two distinct conflicting signed headers existed."
5. If an earlier static-validation layer already rejects `mblock_header_1 == mblock_header_2`, the test's transaction submission itself should fail before reaching `handle_poison_microblock`; confirming this determines whether the vulnerability is exploitable end-to-end.

    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
