This confirms the mechanism precisely. The `countVote` accumulation in `MaintenanceManager.doMaintenance` [1](#0-0)  computes `witnessVi` for the closing cycle using the witness's vote count *before* the current cycle's new votes are tallied, then tallies new votes into `witnessCapsule.setVoteCount` [2](#0-1)  and immediately persists that inflated vote count as the fixed snapshot for the *next* full cycle via `delegationStore.setWitnessVote(nextCycle, ...)` [3](#0-2) . That fixed `nextCycle` vote-count snapshot is what `MortgageService.computeReward`/`VoteRewardUtil.computeReward` divide the whole cycle's `totalReward` by when paying out rewards [4](#0-3) .

### Title
Last-block vote reallocation lets a voter capture a full cycle's SR reward share while diluting long-term voters - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
TRON's DPoS vote-reward accounting distributes an entire cycle's (default 6 hours) reward pool to whichever voters are registered for a super representative (SR) at the moment the cycle's vote snapshot is taken during maintenance, rather than pro-rating by how long the vote was actually held during that cycle. This is structurally the same flaw as the reported am-AMM issue: rent/reward for an entire epoch is paid out based on an end-of-period snapshot instead of time-weighted accrual, letting a user who "deposits" (votes) only in the last moment of the previous epoch still receive the full epoch's reward.

### Finding Description
In `MaintenanceManager.doMaintenance()`, at the boundary of cycle `curCycle`:
1. `accumulateWitnessVi` is invoked using the witness's *current* `voteCount` (i.e., the count in effect since the start of `curCycle`, before this maintenance's tally) to close out `curCycle`'s reward index (`Vi`) [1](#0-0) .
2. `countVote(votesStore)` then aggregates every vote transaction submitted during `curCycle` — including one submitted in the very last block before maintenance runs — and immediately adds it to `witnessCapsule`'s vote count [5](#0-4) .
3. That updated (now inflated) vote count is persisted as the *fixed* snapshot `delegationStore.setWitnessVote(nextCycle, witness, witness.getVoteCount())`, which will be used to divide up `nextCycle`'s entire reward pool [3](#0-2) .

Later, `MortgageService.computeReward`/`VoteRewardUtil.computeReward` calculate a voter's share of `nextCycle`'s reward strictly as `deltaVi(cycle-1, cycle) * userVote / DECIMAL`, where `deltaVi` derives from `reward / totalVote` computed once per cycle in `accumulateWitnessVi` [6](#0-5) . There is no time-weighting within the cycle: a user whose vote is included in `witnessVote(nextCycle, ...)` receives the *same per-vote reward rate* as a user who has held that vote for the full previous cycle, even though the newcomer's vote was cast mere seconds/blocks before the snapshot was taken.

Because voting simply reallocates already-frozen TRON Power (no new freeze/lock delay is required to change a vote, only to first acquire TRON Power via freezing), an account that already holds frozen balance can shift its vote to a target SR in the last block of a cycle, be included in that SR's `nextCycle` vote-count snapshot at zero cost, and then reallocate away again immediately after the new cycle starts — while still being entitled to claim the full `nextCycle` reward once it accrues, via the settlement/snapshot logic in `VoteRewardUtil.withdrawReward` / `MortgageService.withdrawReward`, which explicitly preserves a stored `accountVote` snapshot so a voter can withdraw and still be paid for "the latest cycle" even after clearing their votes [7](#0-6) .

This dilutes the reward share that should accrue to voters who genuinely supported the SR for the entire cycle, transferring value to the last-second reallocator — the same wealth-transfer pattern described in the am-AMM report, just expressed through TRON's cycle-based vote/reward snapshot instead of an AMM epoch's LP-token rent burn.

### Impact Explanation
Impact is limited to reward-share dilution/redistribution among voters of the same SR; it does not mint new TRX, corrupt total emission, or allow unauthorized account operations. The attacker only captures a proportional (not amplified) share of the existing reward pool at the expense of long-term voters of that SR, and must still hold frozen TRX (TRON Power) to vote at all. This is closer to Medium impact — a value-transfer/reward-fairness issue rather than a critical accounting break, matching the severity classification given to the original am-AMM finding.

### Likelihood Explanation
Likelihood is Medium: the attack requires no special privilege, only an existing frozen balance and the ability to time a `VoteWitnessContract`/TVM `voteWitness` transaction to land in the final block before a maintenance cycle boundary (maintenance timing is deterministic/predictable from `DynamicPropertiesStore` cycle state), and to submit a follow-up reallocation transaction after the new cycle begins. It is straightforward to script but yields only proportional gains bounded by the attacker's own vote weight relative to the SR's total.

### Recommendation
Weight cycle rewards by the fraction of the cycle during which a vote was actually registered for an SR (e.g., accrue `Vi` incrementally per block/time rather than crediting new votes retroactively for the entire following cycle), or require a minimum holding period (measured from when a vote for a given SR was cast) before that vote counts toward the next cycle's `witnessVote` snapshot used in `MaintenanceManager.doMaintenance` and `RewardViCalService`/`DelegationStore.accumulateWitnessVi`.

### Proof of Concept
1. Account `A` already has frozen TRX (TRON Power) from a prior freeze, currently voting for SR `X`.
2. Just before cycle `N`'s maintenance triggers (last block of cycle `N`), `A` submits `VoteWitnessContract` (or TVM `voteWitness`) to reallocate votes to SR `Y`.
3. `MaintenanceManager.doMaintenance()` runs: `accumulateWitnessVi` closes cycle `N` using `Y`'s pre-tally vote count (excluding `A`'s new vote) [1](#0-0) ; then `countVote` adds `A`'s vote into `Y`'s `voteCount`, and `setWitnessVote(N+1, Y, ...)` snapshots that inflated total for cycle `N+1` [8](#0-7) .
4. Immediately at the start of cycle `N+1`, `A` reallocates its vote away from `Y` again (no lock-up required).
5. After cycle `N+1` closes (cycle `N+2` maintenance), `A` calls `withdrawReward`/`queryReward`; because `VoteRewardUtil.withdrawReward` stores an `accountVote` snapshot at settlement time before votes are cleared, `A` is still credited its proportional share of `Y`'s reward for the entire cycle `N+1`, computed via `deltaVi(N, N+1) * A's userVote` [7](#0-6) [9](#0-8)  — despite having supported `Y` for a negligible fraction of that cycle, at the expense of `Y`'s genuine long-term voters.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;

    if (beginCycle < endCycle) {

        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);

        reward += deltaVi.multiply(BigInteger.valueOf(userVote))

  private void accumulateWitnessVi(long cycle, byte[] address) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long voteCount = getWitnessVote(cycle, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
