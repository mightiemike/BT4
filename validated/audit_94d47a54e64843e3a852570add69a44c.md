Based on my investigation, the strongest state-integrity analog I found is a genuinely acknowledged (but exploitable) gap in the transaction-output/transaction-info matching logic used by `db-tool replay-verify`, `aptos-debugger`, and the CLI — the exact "rounded-down value never reconciled against the expected invariant" pattern from the Balancer bug, but manifesting as *checkpoint hash fields that are silently excluded from the equality check*.

### Title
`ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting replay-verify accept a diverged native state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole authenticity check used by `aptos-debugger`, `aptos-move/cli`, and `db-tool replay_on_archive` to confirm that a locally re-executed transaction output matches the historical, ledger-committed `TransactionInfo` (the object that is actually accumulated into the transaction accumulator and signed by validators). The function checks status, gas, write-set hash, and event-root hash, but explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — as the code itself documents. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` validates only four fields — status, gas used, write-set hash, and event root hash: [2](#0-1) 

It never compares the recomputed state checkpoint hash (nor the hot-state or position-state checkpoint hash carried in `TransactionInfoV1`) against the value stored in the authenticated `txn_info` parameter, and the comment right above `Ok(())` explicitly flags this as an unresolved gap: [3](#0-2) 

This function is the terminal correctness check in the mainnet-facing replay-verification tool: [4](#0-3) 

`replay_on_archive` re-executes historical transactions with `AptosVMBlockExecutor` and compares the freshly computed `TransactionOutput` against the `expected_txn_infos` pulled from backup/ledger storage — the *only* place this comparison happens. Since `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are excluded from the check, any local divergence in state-tree root computation (main Sparse-Merkle root, hot-state root, or "trading native" position-state root gated by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature) is invisible to this authenticated-proof workflow, even though these hashes are exactly the fields committed into `TransactionInfo` and hashed into the transaction accumulator that ledger infos are signed over. [5](#0-4) 

### Impact Explanation
`TransactionInfo`/checkpoint hashes are the authenticated binding between VM execution and the committed Merkle state root. A validator or archive node whose state-checkpoint, hot-state, or position-state root computation has diverged from the correct consensus-derived value (e.g. through a local storage bug, a bug in `DoStateCheckpoint`, or a hard-fork-boundary computation error) will pass `replay_on_archive` cleanly, because the tool's only correctness gate ignores exactly the fields that would reveal that divergence. This defeats the purpose of replay-verification as a detector of state-commitment corruption for "trading native"/hot-state features, silently masking a wrong accumulator root / wrong state root being treated as valid in an authenticated verification pipeline — directly matching the "Wrong accumulator root ... accepted as valid" and "Committed state that differs from the correct VM result" impact classes.

### Likelihood Explanation
This is not a hypothetical: the divergence-masking condition triggers deterministically any time `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or hot-state root inclusion) is active and a node's locally computed checkpoint hash differs from the ledger's — no attacker action or privilege is required, only a local implementation bug or storage corruption in the checkpoint-hash computation path. Because the gap is in the verification tool itself, it applies uniformly across any deployment that relies on `replay_on_archive`/`aptos-debugger` to catch state-integrity bugs post-hoc, which is precisely the mainnet operational safety net this tooling is meant to provide.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the recomputed output and the expected `TransactionInfo`, guarded appropriately for cases where the checkpoint is only produced at block boundaries (i.e., compare only when `txn_info` carries `Some` checkpoint hash, matching `DoStateCheckpoint`'s production semantics). This closes the gap explicitly called out in the existing TODO comment before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` more broadly.

### Proof of Concept
1. Enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or hot-state root in txn info) on a test network.
2. Introduce (or naturally hit) a local divergence in `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` computation on a replay node (e.g., a shard-key ordering bug in `truncate_position_merkle_db_shards`/state-tree assembly, or any bug in `DoStateCheckpoint`).
3. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`, `execute_and_verify`) over the affected version range.
4. Observe that `ensure_match_transaction_info` returns `Ok(())` and no failure is reported, despite the recomputed native/hot state root differing from the ledger-committed one — confirming the checkpoint-hash fields are never compared.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
