### Title
Loose Signature-Length Check (`< 65` instead of `== 65`) in `TransactionCapsule.checkWeight` Enables Duplicate-Signature / Weight-Inflation via Padding Bytes - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
The multi-signature weight verification path `TransactionCapsule.checkWeight` accepts any signature whose byte length is `>= 65` (checked as `sig.size() < 65` → reject), rather than requiring an exact length. This mirrors the reported ENS `BytesUtils.equals` bug class: a length check using `>=`/`<` instead of `==` allows extra/trailing bytes to be silently ignored during comparison/decoding, letting semantically distinct byte strings be treated as equivalent for the purposes that matter (address recovery / permission-weight accounting) while the different byte encodings escape identity-based duplicate detection.

### Finding Description
`checkWeight` validates each signature in a transaction: [1](#0-0) 

only checking `sig.size() < 65`, so any signature ≥ 65 bytes passes the format check. The recovered address is then computed via `SignUtils.signatureToAddress`, and the pre-fork de-duplication logic keys the "has this signer already signed" map on the *raw base64 signature string*, not on the recovered address: [2](#0-1) 

`SignUtils.java` explicitly documents this loose check as intentional for backward compatibility with "historical on-chain signatures that carry trailing padding bytes," confirming the length comparison is `>=`-style rather than exact: [3](#0-2) 

Because `ECKey.signatureToKeyBytes`/`ECDSASignature.fromComponents` only read the first 65 bytes (`r=[1,33)`, `s=[33,65)`, `v=header byte`) of the decoded signature and ignore anything beyond byte 65: [4](#0-3) 

an attacker can take one valid 65-byte signature and append arbitrary trailing bytes to produce many distinct byte sequences (and thus distinct base64 strings / `addMap` keys) that all decode to the *same* recovered address and *same* weight — exactly analogous to `equals(0x0102030000, 0, 0x010203) == true`: the "core" content matches, but the surrounding/trailing bytes differ, and the length check (`>=`/`size() < 65`) fails to enforce that the compared/consumed data is exactly as long as what's actually used.

### Impact Explanation
Before fork `VERSION_4_7_1`, the "signed twice" guard in `checkWeight` uses the literal signature bytes (`base64`) as the map key: [5](#0-4) 

An attacker controlling a broadcast transaction with multiple signature slots could submit N distinct padded variants of the *same* single-key signature. Each variant recovers to the same address/weight but is treated as a "new" unique key by the pre-fork dedup logic, so `currentWeight` accumulates the same key's weight N times, potentially crossing `permission.getThreshold()` with only one real private key — a multisig-permission threshold bypass. This is reachable directly from an anonymous broadcast transaction (`Wallet.broadcastTransaction` / `getTransactionApprovedList` / `TransactionUtil.getTransactionSignWeight` all call into `checkWeight`), i.e., unprivileged RPC input.

### Likelihood Explanation
This path is guarded by a fork flag (`ForkController.instance().pass(VERSION_4_7_1)`), which changes the dedup key to `encode58Check(address)` once active, closing the padding-duplication gap on networks where that fork has activated. The vulnerability is therefore only exploitable on chains/forks where `VERSION_4_7_1` has not yet activated, or in any code path that still relies on the pre-fork behavior. I could not fully verify from the available index whether `VERSION_4_7_1` is unconditionally active on all currently supported networks (mainnet already passed it historically), which limits confidence in present-day exploitability but confirms the bug-class analog exists as dead/legacy logic in the code.

### Recommendation
- Change `sig.size() < 65` to `sig.size() != 65` (or the exact expected length for the algorithm in use) so `checkWeight` rejects any签名 with trailing garbage bytes outright, consistent with `SignUtils.isValidLength`'s stricter bound-checked variant.
- Always key the "already signed" map by the recovered address (`encode58Check(address)`) rather than by raw signature bytes, regardless of fork status, to eliminate any byte-level duplication vector.
- Remove/deprecate the documented "historical padding" tolerance once no live network state depends on it, or gate it behind exact validation of the extra bytes (e.g., require padding to be all-zero and of a fixed known length) rather than accepting arbitrary trailing content.

### Proof of Concept
1. Generate one ECKey and sign a transaction hash normally, producing a canonical 65-byte signature `sig`.
2. Construct `sig2 = sig || 0xFF`, `sig3 = sig || 0xAB` (arbitrary trailing bytes), etc. Each has length ≥ 65 and thus passes `sig.size() < 65` in `checkWeight`.
3. Submit a transaction (pre-`VERSION_4_7_1` fork context) with signature list `[sig, sig2, sig3, ...]` for a multisig permission where the single key's weight is less than the threshold but weight × N ≥ threshold.
4. `checkWeight` decodes each signature independently via `ECKey.signatureToKeyBytes`, which only reads bytes `[0,65)`, so all variants recover to the same address/weight; the pre-fork `addMap` dedup check (keyed on the differing base64 strings) does not flag them as duplicates, so `currentWeight` is summed N times, potentially satisfying `permission.getThreshold()` with a single controlled key.

      signatureBase64) throws SignatureException {
    byte[] signatureEncoded;
    try {
      signatureEncoded = Base64.decode(signatureBase64);
    } catch (RuntimeException e) {
      // This is what you getData back from Bouncy Castle if base64 doesn't
      // decode :(
      throw new SignatureException("Could not decode base64", e);
    }
    // Parse the signature bytes into r/s and the selector value.
    if (signatureEncoded.length < 65) {
      throw new SignatureException("Signature truncated, expected 65 " +
          "bytes and got " + signatureEncoded.length);
    }

    return signatureToKeyBytes(
        messageHash,
        ECDSASignature.fromComponents(
            Arrays.copyOfRange(signatureEncoded, 1, 33),
            Arrays.copyOfRange(signatureEncoded, 33, 65),
            (byte) (signatureEncoded[0] & 0xFF)));
  }
