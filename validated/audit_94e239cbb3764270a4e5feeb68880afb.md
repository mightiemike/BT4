## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, allowing chunk-replay verification to accept a locally re-executed state root that diverges from the authenticated ledger - (File: `types/src/transaction/mod.rs`)

### Summary
The bug-class in the LienToken report is "a privileged/trusted binding is checked against the wrong or incomplete reference, letting a corrupted state be accepted as authentic." The Aptos analog is in the replay/restore integrity check `TransactionOutput::ensure_match_transaction_info`, which is the function chunk-replay and restore tooling use to decide whether locally re-executed output matches an authenticated `TransactionInfo` (proven against a signed `LedgerInfo` via the transaction accumulator). This function checks status, gas, write-set hash and event-root hash, but explicitly **does not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually authenticate the resulting world-state (Merkle) root.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` is documented in-code as intentionally incomplete: [2](#0-1) 

It verifies `status`, `gas_used`, `write_set_hash` (via `state_change_hash`) and `event_root_hash`, but the state checkpoint hash — the field that binds a transaction's execution to the actual JMT/Sparse-Merkle world-state root and hot-state/position roots — is never compared.

This comparator is the sole authenticity check used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, called from `remove_and_replay_epoch`/`enqueue_chunks` (the `TransactionReplayer` path used for backup restore-and-replay and replay-verify tooling), [3](#0-2) 
- `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` replay-verification flows.

In all of these, transactions are re-executed locally against the local state view, and the freshly computed `TransactionOutput` is checked against a `TransactionInfo` that was already accumulator-proven to a signed `LedgerInfo` (i.e., it is treated as ground truth for what should have happened). Because `write_set_hash` is only the hash of *this transaction's own* write set (not the resulting global state tree), it can match even when the *application* of that write set onto the JMT/state tree (key hashing, sharding, hot-state promotion, or `position_state_checkpoint_hash` handling) is broken or diverges from the authenticated chain. Since `state_checkpoint_hash` is the only field that actually authenticates the post-transaction global state root, and it is skipped, `verify_execution`/`ensure_match_transaction_info` will report success even when the locally committed state root differs from the correct, chain-authenticated state root.

### Impact Explanation
This falls squarely under "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and "Hard-fork-only divergence during commit, replay, restore, or proof verification must be flagged." A node performing backup-restore-with-replay or replay-verify (e.g. via `db-tool replay-verify`/`replay_on_archive`, or `TransactionReplayer::enqueue_chunks` with `VerifyExecutionMode::verify_all()`) can silently persist a JMT/state-tree/hot-state/position-state root that diverges from the authenticated on-chain state while the tool reports the replay/restore as successful. Any subsequent state proofs, state-value reads, or further execution built on that node's storage would be served from a *wrong* but *unflagged-as-wrong* ledger state — i.e., an authenticated-looking local state that has silently forked from the network's canonical state.

### Likelihood Explanation
The gap is unconditionally present in the code path (not feature-gated), and is self-documented by the author as a known TODO ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), confirming the local team recognizes the check is currently missing. Any divergence between local state-tree computation and the canonical result (e.g., a JMT bug, a hot-state/position-state materialization bug, or a bug specific to a node's execution path that doesn't affect the write-set hash itself) would go undetected by every consumer of `ensure_match_transaction_info`.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) between the locally computed output and the trusted `TransactionInfo`, at least whenever the transaction is a checkpoint boundary (`state_checkpoint_hash` is `Some`). This should be wired in before any feature that relies on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-style checks, per the existing TODO.

### Proof of Concept
1. Take a `TransactionInfo` from an authenticated backup manifest/ledger (accumulator-proven against a signed `LedgerInfo`), containing a correct `state_checkpoint_hash` for version `V`.
2. Run `TransactionReplayer::enqueue_chunks` (or `replay_on_archive`) with `VerifyExecutionMode::verify_all()` against a node whose JMT/state-tree materialization logic has a latent divergence (e.g., a hot-state promotion or position-state bug) that doesn't change the write set contents but changes how it's folded into the state tree.
3. `chunk_executor::verify_execution` calls `txn_out.ensure_match_transaction_info(version, txn_info, ...)`; since `write_set_hash`, `event_root_hash`, `gas_used`, and `status` are unaffected, the check passes.
4. The chunk is committed via `remove_and_apply`/`commit_chunk_impl`, and the node's on-disk state root for version `V` silently differs from the authenticated chain's `state_checkpoint_hash`, while replay-verify reports success.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
