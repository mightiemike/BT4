### Title
Starknet OS `execute_replace_class` accepts undeclared class hashes, diverging from Blockifier's validated syscall - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The Blockifier's Rust `replace_class` syscall handler validates that the target class hash is a declared class before mutating contract state, but the Starknet OS's Cairo re-implementation of the same syscall performs no such check — a gap the code itself flags with an unresolved `TODO`. Since a single unprivileged transaction can invoke `replace_class` with an arbitrary, undeclared class hash, the OS's independent (re-)execution of that transaction can proceed down a different code path than Blockifier's real execution, producing a state/class-hash divergence between the two execution engines that back the sequencer's block building and its STARK proof of correctness.

### Finding Description
In Blockifier, `replace_class` explicitly checks the class is declared before writing the new class hash: [1](#0-0) 
```
fn replace_class(...) -> DeprecatedSyscallResult<ReplaceClassResponse> {
    // Ensure the class is declared (by reading it).
    syscall_handler.state.get_compiled_class(request.class_hash)?;
    syscall_handler.state.set_class_hash_at(syscall_handler.storage_address, request.class_hash)?;
    ...
}
```
If `request.class_hash` was never declared, `get_compiled_class` returns an error and the syscall fails, which — for un-handled `unwrap_syscall()` patterns commonly used in Cairo contracts — panics the current call and reverts the transaction in Blockifier's real execution.

In contrast, the Starknet OS's Cairo implementation of the identical syscall for both the current and deprecated execution paths performs no declaration check at all, and explicitly documents this as an outstanding gap: [2](#0-1) 
```
func execute_replace_class{...}(contract_address: felt) {
    ...
    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address, prev_value=cast(state_entry, felt), new_value=cast(new_state_entry, felt),
    );
    ...
}
```
The deprecated syscall path has the same unconditional behavior: [3](#0-2) 

The OS runs the actual compiled CASM/Sierra of the invoked contract with its own Cairo VM (it is not merely replaying a Blockifier-provided trace — hints like `GetContractAddressStateEntry` only fetch ambient state, while the syscall `request`/`response` values come from genuine VM execution of the transaction's real bytecode). Because the OS's `execute_replace_class` unconditionally succeeds regardless of whether the requested class hash was ever declared (via `contract_class_changes`/`is_declared`), while Blockifier's handler fails on the same input, the two engines can diverge in what happens *after* the syscall for the exact same transaction: Blockifier reverts/aborts at the failing syscall (rolling back any subsequent state writes in that call), while the OS's execution continues past the syscall as if it succeeded, applying the class-hash change and any subsequent contract logic and storage writes that depended on it. Downstream commitment logic (`state_update` / `compute_class_commitment` in `state.cairo` / `commitment.cairo`) commits whatever ends up in `contract_state_changes`/`contract_class_changes` without any independent cross-check that a `StateEntry.class_hash` is backed by an actually-declared class: [4](#0-3) 

### Impact Explanation
This is a validation-logic divergence between the two engines that are both supposed to compute the exact same state transition for a given block: Blockifier (the engine that actually builds/executes the block and is the reference for consensus) and the Starknet OS (the engine whose Cairo execution is proven and whose output commits the new state root). A single transaction crafted by any unprivileged sender that calls `replace_class` with an undeclared class hash can cause the OS's independent re-execution to follow a different control-flow path (continuing execution and committing state) than Blockifier's real execution (which fails/reverts at that point). This can result in a contract ending up with a class hash that was never declared/committed to the class trie, and in a committed state root / block hash that does not correspond to Blockifier's actual (agreed-upon) execution result — i.e., an honest-node/engine divergence and a wrong committed root, which are explicitly in-scope high-impact outcomes.

### Likelihood Explanation
Triggering the divergent code path requires nothing more than a normal contract deployed by any user calling the `replace_class` syscall with a class hash that has not been declared — an operation fully reachable from a single, unprivileged transaction with no special network position, staking, or operator/prover collusion required to *cause the divergence in the OS's independent execution*. The condition is simple (one syscall parameter), and the missing check is explicitly acknowledged by an open `TODO` in the code, indicating the bug is not defense-in-depth but a genuinely un-implemented check in the proving path.

### Recommendation
Add the same "class is declared" validation to the Starknet OS's `execute_replace_class` (both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo`) that Blockifier's `replace_class` performs — i.e., verify the requested `class_hash` exists in `contract_class_changes` (or the already-committed class tree) before writing the new `StateEntry`, and fail the syscall (matching Blockifier's failure/revert semantics) otherwise. Resolve the `TODO(Yoni, 1/1/2026)` before it can be exploited to desynchronize the OS's committed state root from Blockifier's actual execution result.

### Proof of Concept
1. Deploy a contract `A` (via a normal `DEPLOY`/`DECLARE`+deploy transaction) whose `__execute__`/external function does:
   - Call `replace_class_syscall(UNDECLARED_CLASS_HASH)` (a class hash that has never been declared on-chain).
   - Follow with additional state-mutating logic (e.g., additional `storage_write` calls or a nested contract call) that should only execute if the class replacement succeeded.
2. Submit an ordinary invoke transaction from an unprivileged account calling this function.
3. In Blockifier's real execution: `syscall_handler.state.get_compiled_class(UNDECLARED_CLASS_HASH)` in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:795-807` returns an error; the syscall fails, and (assuming standard `unwrap_syscall()` usage) the call panics, the transaction reverts, and none of the subsequent storage writes are committed.
4. When the Starknet OS independently re-executes the identical transaction bytecode to build its state-transition proof, `execute_replace_class` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo:881-920` performs no declaration check, unconditionally writes the new (bogus) class hash into `contract_state_changes`, and returns success — allowing the OS's execution to continue past the point where Blockifier reverted, and to commit the subsequent storage writes and the invalid class hash into the state/class commitment computed in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/state/state.cairo:47-113`.
5. The result: the state root/class-hash data attested by the OS's proof differs from the state actually produced (or not produced, due to revert) by Blockifier for the same transaction — a concrete honest-engine divergence / wrong committed root originating from a single, unprivileged transaction.
