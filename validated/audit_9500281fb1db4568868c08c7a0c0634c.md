## Title
`TransactionOutput::ensure_match_transaction_info` never validates state-checkpoint / hot-state / position-state roots against the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used to verify that a locally re-executed transaction output matches an externally-supplied, authenticated `TransactionInfo` (i.e. a `TransactionInfo` that is bound to a signed `LedgerInfo`/waypoint via the accumulator). It checks status, gas used, write-set hash and event-root hash, but it explicitly and permanently skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the recomputed values. [1](#0-0) 

## Finding Description
`ensure_match_transaction_info` compares locally computed values (`status`, `gas_used`, write-set hash, event-root hash) with the fields of a caller-supplied, already-authenticated `TransactionInfo`, and returns `Ok(())` unconditionally after those checks — it never touches `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`: [2](#0-1) [3](#0-2) 

This is not an oversight limited to a hypothetical future feature: the state-checkpoint hash is a real, always-present field of `TransactionInfo` (`maybe_state_checkpoint_hash`) that is populated for every state-checkpoint transaction during normal `assemble_transaction_infos` construction, and represents the JMT root over resulting global state after a block/chunk of transactions is applied: [4](#0-3) 

The comment left in the code by the Aptos team itself acknowledges the gap explicitly: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [5](#0-4) 

This function is called from at least four places that all treat it as the authoritative "does my recomputed output match the trusted, proof-bound transaction info" check: the chunk executor commit-time verification path, the replay-verify db-tool (`storage/db-tool/src/replay_on_archive.rs`), the debugger, and the CLI: [6](#0-5) 

Because the write-set hash and event-root hash are checked, a re-executed transaction's *direct* outputs are validated. But the state root that actually gets *committed to durable ledger storage* — the `state_checkpoint_hash` at checkpoint boundaries (and the newer `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields used by the trading-native state root work) — is derived from a separate code path (`DoStateCheckpoint`, JMT update, native position tree update) that is not cross-checked here. If that separate root-computation path diverges from the transaction info that was signed into the ledger (e.g. due to a bug in JMT update logic, hot-state bucketing, or the native position tree merge for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), this comparator will still return `Ok(())`, silently accepting a divergent state root as "verified."

## Impact Explanation
This breaks the "committed state must survive executor-to-storage handoff unchanged" and "authenticated API/proof-bearing output must stay bound to the right root" invariants: a replay tool, debugger, or chunk-executor commit path that relies on `ensure_match_transaction_info` as its correctness gate can report a transaction/chunk as verified even though the locally computed state-checkpoint root (and hence the entire subsequent state tree / restore snapshot) has silently diverged from the authenticated, signed ledger state. Since `TransactionInfo::hash()` (which feeds the transaction accumulator, and ultimately the signed `LedgerInfo`) *does* include `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a wrong locally-computed root would fail accumulator-level detection only if some other explicit comparison catches it — and this function, which is the one place explicitly designed to catch output/info mismatches for replay-verify and chunk-executor flows, does not. This can mask hard-fork-class divergence (state committed on disk differs from the canonical/consensus state) during chunk sync verification and offline replay-verify auditing, which is exactly the "hard-fork-only divergence during commit/replay/restore" impact category.

## Likelihood Explanation
Today this is a latent gap rather than an actively triggerable exploit for `state_checkpoint_hash` at ordinary block boundaries, because for the classic (`transaction_info_v1 == false`) path other consistency assertions elsewhere in the state-checkpoint/ledger-update code (`ensure!(known[idx] == Some(computed_last_checkpoint_hash), ...)` in `do_state_checkpoint.rs`) do separately validate the checkpoint hash when `known_state_checkpoints` are supplied by a verifier. However, `ensure_match_transaction_info` is a distinct, lower-level, explicitly-documented safety net that is supposed to also independently detect such a mismatch for tooling paths (replay-verify, debugger, CLI) that operate directly on `TransactionOutput`/`TransactionInfo` pairs without necessarily going through the full state-checkpoint pipeline's own checks. The in-repo TODO confirms the Aptos team considers this a real, currently-unresolved risk that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" — i.e. as soon as the position-state-root (trading-native) feature is turned on for mainnet, this gap becomes directly exploitable for masking position-state divergence undetected by replay-verify tooling.

## Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) between the recomputed checkpoint output and `txn_info`, following the same `ensure!` pattern already used for gas/status/write-set/event-root, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any consumer relying on this function for checkpoint-hash correctness) is enabled.

## Proof of Concept
Conceptual PoC (cannot be executed without full local devnet/replay harness):
1. Construct (or inject via a modified `DoStateCheckpoint`/JMT update in a local branch) a scenario where the locally recomputed state-checkpoint root for a chunk differs from the `state_checkpoint_hash` embedded in the authenticated `TransactionInfo` supplied to `replay_on_archive` / the chunk executor's `update_ledger` verification path, while status/gas/write-set-hash/event-root-hash remain identical (e.g. an extra untracked resource write that does not appear in the write set hash used by the comparator but does affect state-tree membership, or a JMT root-computation bug).
2. Call `TransactionOutput::ensure_match_transaction_info` with this divergent pair.
3. Observe that the call returns `Ok(())` because the function body — as read directly from `types/src/transaction/mod.rs` lines 2159–2203 — never reads `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, confirming the check is bypassed and a wrong state root would pass "verification."

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

        let _timer = CHUNK_OTHER_TIMERS.timer_with(&["chunk_update_ledger_total"]);

        let txn_infos = chunk_verifier.transaction_infos();

                .collect_vec()

            .maybe_parent_position_state_summary(parent_position_state_summary.as_ref())
