Based on my investigation, I found a concrete, code-acknowledged integrity gap in the transaction-info verification routine used by both replay-verify tooling and the storage restore/replay-verification code paths.

### Title
`ensure_match_transaction_info` omits state-checkpoint / hot-state / position-state root comparison, allowing authenticated replay verification to accept a divergent ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single authenticated-state comparator used by `db-tool`'s `replay_on_archive` and by `ChunkExecutor::verify_execution` (used during backup restore/replay-verify) to confirm that locally re-executed transactions match the transaction infos recorded on-chain/in the backup. The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of `TransactionInfo`/`TransactionInfoV1` and are exactly the fields that bind the authenticated ledger state (state tree root, hot-state root, and trading-native "position state" root) to a given version.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates only `status`, `gas_used`, `write_set` hash, and `event_root_hash` against the supplied `TransactionInfo`. The function contains a `TODO(trading-native)` comment stating explicitly:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole verification gate in two proof-relevant call sites:
- `storage/db-tool/src/replay_on_archive.rs`, `execute_and_verify`, which calls it directly to validate re-executed transactions against archived `TransactionInfo`s [2](#0-1) .
- `execution/executor/src/chunk_executor/mod.rs`, `verify_execution`, used by the backup-restore path (`TransactionRestoreBatchController::replay_transactions` → `ChunkExecutor::enqueue_chunks` → `verify_execution`) [3](#0-2) .

Meanwhile, the actual state-root computation machinery (`DoStateCheckpoint::run`, `DoLedgerUpdate::assemble_transaction_infos`) does produce and carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` into freshly-built `TransactionInfo`s [4](#0-3) , and `TransactionInfo`/`TransactionInfoV1` carry these fields as first-class authenticated data [5](#0-4) . So the state/hot-state/position roots are computed and committed, but the one function responsible for cross-checking re-executed results against the historically recorded/backed-up `TransactionInfo` never compares them.

### Impact Explanation
This is a proof/verification-integrity break, not a consensus-level bug: it does not let bad state get committed by the live validator network (the accumulator/root chain is still signed by validators during normal consensus). However, it directly undermines the two authenticated-state-verification tools whose entire purpose is to detect ledger divergence after the fact:
- `db-tool replay_on_archive`, used to audit an archive node's history against independently re-executed transactions, will report success even if the locally computed state tree root, hot-state root, or position-state (trading-native) root differs from what is recorded, silently masking storage corruption, non-determinism bugs, or state-computation regressions.
- Backup restore's `verify_execution` path (`ChunkExecutor::verify_execution`, invoked from `TransactionRestoreBatchController`) has the same blind spot — a restored/replayed archive can end up with a DB whose committed state values are wrong for the given version while all replay-verify checks pass, because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never cross-validated against the write-set/read state actually produced.

This meets the "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "restore paths must not reinterpret committed data into a different ledger state" criteria: a diverging state root is silently accepted as valid during restore/replay-verify.

### Likelihood Explanation
This is not attacker-triggerable on a live validator (the accumulator hash chain there is signed independently), but the gap is unconditionally present in the shipped verification code path — no special configuration is required to hit it, and the code's own comment documents that it is a real, known, unaddressed issue rather than a hypothetical. Any state-root-divergence bug (e.g., non-determinism, a JMT/hot-state merge bug, or storage schema misinterpretation) occurring anywhere upstream will go undetected by these specific verification tools, and operators relying on `replay_on_archive`/backup-restore verification for post-hoc integrity assurance would have false confidence.

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check invoked at both call sites) to additionally compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when present), and `position_state_checkpoint_hash` (when `compute_trading_native_state_roots` is enabled) between the locally-computed checkpoint output and the expected/persisted `TransactionInfo`. This requires threading the locally computed `StateCheckpointOutput` (already produced by `DoStateCheckpoint`) into the comparator at both `replay_on_archive.rs::execute_and_verify` and `chunk_executor::verify_execution`, rather than only comparing `TransactionOutput`-level fields.

### Proof of Concept
No exploit/PoC is provided because this is not a remotely-triggerable attack against consensus; it is a verification-tooling gap. The proof is the code path itself:
1. `DoStateCheckpoint`/`DoLedgerUpdate` compute and embed `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` into `TransactionInfo` [6](#0-5) .
2. `ensure_match_transaction_info` receives a `TransactionInfo` but only reads `status()`, `gas_used()`, and `event_root_hash()`, never `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` [7](#0-6) .
3. Both `replay_on_archive.rs` and `chunk_executor::verify_execution` rely exclusively on this function to decide pass/fail for replayed transactions [2](#0-1) [3](#0-2) , confirming that a state-root divergence introduced anywhere in the storage/state-checkpoint pipeline is not caught by these tools even though the diverging data is available to compare.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
