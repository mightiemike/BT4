### Title
Rejected L1Handler messages become permanently unproposable while their L1 fee remains locked - ([File: crates/apollo_l1_events/src/transaction_record.rs])

### Summary
In `apollo_l1_events`, an L1→L2 message (`L1HandlerTransaction`) that is scraped from L1 pays its fee on L1 (`paid_fee_on_l1`) up front, exactly like a bidder locking WETH into an auction. The referenced report shows the analogous pattern: an action irreversibly consumes the user's asset, but a subsequent state transition (`cancelAuction`) removes the position without any refund path. In this repo, once a `TransactionRecord`'s state becomes `Rejected` (via `TransactionManager::commit_txs` -> `mark_rejected`), `is_proposable()` permanently returns `false` for that record, and there is no code path that ever re-stages, re-proposes, or refunds a `Rejected` L1Handler transaction. The only other exit for the record is the L1-side cancellation/timelock flow, which is gated on `is_committed()`/`is_cancelled()` checks that never apply to `Rejected` records.

### Finding Description
`TransactionRecord::is_proposable()` only returns true for `TransactionState::Pending`: [1](#0-0) 

`mark_rejected()` transitions a record straight to `TransactionState::Rejected` and asserts it wasn't already committed, but performs no other bookkeeping and provides no way back to `Pending`: [2](#0-1) 

`TransactionManager::commit_txs` is the only caller of `mark_rejected`, driven directly by consensus/batcher output (`rejected_txs`) for a committed block: [3](#0-2) 

Once in `Rejected` state, `maintain_indices` will remove/never re-add the hash to `proposable_index` because `is_proposable()` is false, so `TransactionManager::get_txs` (used by the batcher/proposer) can never surface it again: [4](#0-3) 

The only mechanism that removes a record from the manager afterwards is the L1-driven cancellation flow (`request_cancellation` / `finalize_cancellation`), driven purely by L1 message-cancellation events, not by the L2 sequencer noticing the message is stuck: [5](#0-4) 

Because the L1 sender already paid the fee for the message when it called `sendMessageToL2`, and the record's rejection is an L2-internal bookkeeping decision (e.g. block rejected the tx for reasons unrelated to the sender, or a re-org/backlog inconsistency during `commit_txs`), the sender has no way to trigger a retry from the sequencer side. Their only recourse is the multi-day L1 cancellation timelock (`startL1ToL2MessageCancellation` / finalize), which the sequencer code assumes but does not orchestrate or notify about — the transaction's `Rejected` records stay silently inert in `self.records` (never resurfaced, only eventually pruned via cancellation or a consumption/finalize path).

### Impact Explanation
This mirrors the reported bug class ("asset locked, no path to recovery inside the affected system") ported to the sequencer's L1-message lifecycle: an L1 sender's paid fee/message becomes permanently stuck in a dead `Rejected` state from the L2 sequencer's perspective with no automatic retry, silent to users and without any compensating action inside this component. If `rejected_txs` can legitimately occur for reasons that don't reflect a truly invalid/un-executable message (e.g. transient batcher/consensus rejection, backlog/catch-up inconsistency), a valid L1→L2 message and its associated fee are frozen indefinitely absent the sender manually initiating and waiting out the full L1 cancellation timelock — a funds-freezing condition reachable purely from an L1 message sender's transaction.

### Likelihood Explanation
Reaching `Rejected` requires only that the transaction be included in `rejected_txs` passed to `commit_block`/`commit_txs`, which is under consensus/batcher control, not the L1 sender's. Any legitimate cause of rejection (execution failure, resource limits, or a batcher/proposer discrepancy) makes this reachable without requiring a malicious operator — it is a gap in error-recovery bookkeeping for L1Handler transactions, not a deliberate adversarial exploit, so likelihood depends on how often the block-building pipeline classifies L1Handler transactions as "rejected" versus retried.

### Recommendation
Re-examine whether a `Rejected` L1Handler transaction should be allowed to transition back to `Pending`/proposable (mirroring the auction fix of preventing cancellation while an asset is locked, or providing a refund path), and add an explicit state transition or requeue/alerting mechanism in `TransactionManager` so `Rejected` records are not silently stranded until the multi-day L1 cancellation timelock is manually exercised.

### Proof of Concept
1. An L1 sender calls `sendMessageToL2` paying a fee, producing an `L1HandlerTransaction` scraped into `TransactionManager::add_tx` in `Pending` state.
2. The transaction is proposed via `get_txs` and included in a block, but consensus/batcher classifies it in `rejected_txs` when calling `commit_block`.
3. `L1EventsProvider::apply_commit_block` -> `TransactionManager::commit_txs` calls `mark_rejected`, setting state to `TransactionState::Rejected` (`crates/apollo_l1_events/src/transaction_record.rs:63-72`).
4. `is_proposable()` (`crates/apollo_l1_events/src/transaction_record.rs:155-157`) now always returns `false` for this hash; `maintain_indices` never re-adds it to `proposable_index` (`crates/apollo_l1_events/src/transaction_manager.rs:376-408`), so `get_txs` never returns it again.
5. The sender's only recourse is to independently invoke the L1 cancellation flow and wait out `l1_handler_cancellation_timelock_seconds`, a path the sequencer plays no active role in initiating or notifying about.

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();
        }
        for &tx_hash in rejected_txs {
            self.with_record(tx_hash, |r| r.mark_rejected()).expect(
                "Rejected L1 handler tx has no record. Unreachable: all L1 handler txs in a \
                 committed block were validated as known (validation rejects unknown hashes), \
                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",
            );
        }
    }

            return;
        };

        // Regardless of the state of the tx in the record, if we get the cancellation event from
        // the L1 contract, we delete this tx from the records and from the proposable index, even
        // if it was Pending and ready to be proposed (which is not supposed to happen, hence the
        // warning).

                record.state
            );
        }
        // This will also call maintain_indices to remove the tx from the proposable index.
        self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());

    fn maintain_indices(&mut self, hash: TransactionHash) {
        if let Some(record) = self.records.get(&hash) {
            let TransactionPayload::Full { scrape_timestamp, .. } = record.tx else {
                // We haven't scraped this tx yet, so it isn't indexed.
                return;
            };

            let tx_hash = hash;
            // Check if we need to add this tx to the proposable index.
            if record.is_proposable() {
                // Assumption: txs will only be added to the index once, on arrival, so this
                // preserves arrival order.
                let tx_hashes = self.proposable_index.entry(scrape_timestamp).or_default();
                if !tx_hashes.contains(&tx_hash) {
                    tx_hashes.push(tx_hash);
                }
            } else {
                // This tx needs to be removed from the proposable index if it was on it.
                // Remove from the vec for this timestamp, and drop the entry if it becomes empty.
                match self.proposable_index.entry(scrape_timestamp) {
                    Entry::Occupied(mut entry) => {
                        let tx_hashes = entry.get_mut();

                            tx_hashes.remove(index_in_vec);
                            if tx_hashes.is_empty() {
                                entry.remove();
                            }
                        }
                    }

                }
