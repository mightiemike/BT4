## Analysis

The parser itself, `parseOutboundObservationEvent` in `universalClient/chains/svm/event_parser.go`, has no way to verify that the "Program data:" log line it decodes actually originated from a CPI made by the gateway program. [1](#0-0) 

Tracing the caller confirms this is a structural gap, not just a theoretical parser issue:

1. `processSlotRange` fetches transaction signatures via `GetSignaturesForAddress(gatewayAddr, ...)`. Solana's `getSignaturesForAddress` matches **any** transaction that merely references the given address in its account key list — it does not require that the gateway program was actually invoked. [2](#0-1) 

2. `processSignatureBatch` then iterates over **every** log line (`tx.Meta.LogMessages`) of the fetched transaction and calls `determineEventType(log)` on each one independently, with no tracking of which `Program <id> invoke`/`success` frame the line belongs to. [3](#0-2) 

3. `determineEventType` classifies a log purely by whether its first 8 decoded bytes match a known Anchor event discriminator (e.g. `b3409670758c9c25` for `finalize_universal_tx`, from `config/testnet-donut/solana_devnet/chain.json`). These discriminators are **public, deterministic values** (`sha256("event:<Name>")[0:8]`), not secrets. [4](#0-3) 

Consequently, an unprivileged attacker can submit an ordinary Solana transaction that (a) merely lists the gateway address as one of its accounts (so it appears in `GetSignaturesForAddress` results) and (b) invokes an attacker-owned program that emits its own `Program data: <base64>` log line beginning with the known `finalize_universal_tx`/`revert_universal_tx` discriminator, followed by attacker-chosen bytes for `sub_tx_id` (txID) and `universal_tx_id`. Nothing in the listener/parser path verifies the log came from a CPI made *by* the gateway program.

Downstream, this spoofed `store.Event` is treated identically to a genuine gateway-originated observation: `EventProcessor.processOutboundEvent` parses `TxID`/`UniversalTxID`/`GasFeeUsed` from it and calls `VoteOutbound`, which submits `MsgVoteOutbound` on-chain. [5](#0-4) 

The saving grace is in `x/uexecutor/keeper/msg_vote_outbound.go`: the vote is only accepted if `utxId` resolves to an existing `UniversalTx` with a matching `outboundId` still `PENDING`, and finalization only occurs after `votesNeeded` (≥2/3 of universal validators) submit matching votes hashing to the same ballot key (`sha256(utxId:outboundId:observedTx)`). [6](#0-5) [7](#0-6) 

Because every honest validator's universalClient independently fetches and parses the same on-chain transaction deterministically, an attacker who crafts a spoofed log referencing a **real, currently-pending** `utxId`/`outboundId` (these are queryable, non-secret) could cause all honest validators to converge on the same forged `OutboundObservation` — reaching the honest 2/3 quorum needed to finalize an outbound with attacker-chosen `TxID`/`GasFeeUsed`, and (depending on which discriminator, `finalize_universal_tx` vs `revert_universal_tx`, was spoofed) potentially the wrong success/failure outcome for that outbound. `FinalizeOutbound` then acts on this forged observation, e.g. re-minting/refunding via `handleFailedOutbound` for an outbound that may have genuinely succeeded, corrupting `GasFeeUsed`-based refund accounting. [8](#0-7) 

I was not able to fully verify, within the given tool budget, exactly how `EventProcessor.buildOutboundObservation` maps `EventTypeFinalizeUniversalTx` vs `EventTypeRevertUniversalTx` into the `Success`/`TxHash` fields of `OutboundObservation` (this determines whether the false-failure re-mint scenario is fully reachable or whether some field is independently pinned to the real transaction signature and blocks the attack). That code path should be reviewed directly to confirm the full fund-impact chain; the core defect — the SVM listener/parser treating any log line in a gateway-referencing transaction as gateway-originated purely based on a public discriminator match, without verifying program provenance — is confirmed and is a genuine gap in the honest-validator finalization path described in the scope rules.

### Title
Unverified program provenance of SVM "Program data" logs allows spoofed outbound observations to reach honest-validator voting - (File: universalClient/chains/svm/event_listener.go, universalClient/chains/svm/event_parser.go)

### Summary
`determineEventType` and `parseOutboundObservationEvent` classify and parse **any** log line in a gateway-referencing transaction as a gateway event purely by matching a public 8-byte Anchor discriminator, without confirming the log was emitted via a CPI from the gateway program itself.

### Finding Description
`processSignatureBatch` fetches transactions solely because they reference the gateway address (via `GetSignaturesForAddress`, which matches account-key inclusion, not invocation) and then scans every log line in the transaction. Any log line — even one produced by an unrelated, attacker-controlled program invoked in the same transaction — that starts with `Program data: ` and decodes to bytes whose first 8 bytes equal a known event discriminator is accepted and parsed into a `store.Event` as if it were a genuine gateway-originated `finalize_universal_tx`/`revert_universal_tx` event, with attacker-chosen `TxID`, `UniversalTxID`, and `GasFeeUsed`.

### Impact Explanation
Because all honest universalClient instances parse the same deterministic on-chain transaction the same way, a spoofed log referencing a real, still-pending `utxId`/`outboundId` could let honest validators converge on a forged `OutboundObservation` and reach quorum, causing corrupted outbound finalization (wrong success/failure classification and/or wrong `GasFeeUsed`), which feeds directly into `FinalizeOutbound`'s refund/re-mint accounting.

### Likelihood Explanation
Requires only an unprivileged attacker to submit an ordinary Solana transaction referencing the gateway address and invoking their own program to emit a crafted log — no privileged role needed. The main uncertainty is how much of `OutboundObservation` (particularly `Success`) is attacker-influenced by discriminator selection versus independently derived elsewhere; this needs direct code review of `buildOutboundObservation`.

### Recommendation
Bind log parsing to the actual invoking program by tracking the Solana log "Program <id> invoke [depth]" / "Program <id> success" stack and only treating "Program data:" lines emitted while the gateway program is the active frame as gateway events, instead of trusting any line in a gateway-referencing transaction.

### Proof of Concept
A Go test can build a `tx.Meta.LogMessages` slice containing an unrelated "Program <attacker> invoke" frame followed by a `Program data: <base64>` line whose first 8 bytes equal the `finalize_universal_tx` discriminator and whose subsequent 64 bytes are set to a real, pending `utxId`/`outboundId` pair, then assert that `determineEventType`/`ParseEvent` accepts it and produces a `store.EventTypeOutbound` event identical in shape to a genuine gateway event, demonstrating the parser cannot distinguish forged data from genuine gateway CPI output.

// determineEventType determines the event type based on the log discriminator
func (el *EventListener) determineEventType(log string) string {
	if !strings.HasPrefix(log, "Program data: ") {
		return ""
	}

	eventData := strings.TrimPrefix(log, "Program data: ")
	decoded, err := base64.StdEncoding.DecodeString(eventData)
	if err != nil {
		return ""
	}

	if len(decoded) < 8 {
		return ""
	}

	discriminator := strings.ToLower(hex.EncodeToString(decoded[:8]))

	// Look up event type from discriminator map
	eventType, ok := el.discriminatorToEventType[discriminator]
	if !ok {
		return ""
	}

	return eventType
}

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}
