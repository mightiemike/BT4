## Finding: Replay-verify tooling silently accepts divergent state roots

### Title
`replay_on_archive` / debugger replay verification never checks state, hot-state, or position-state checkpoint hashes - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator used by Aptos's authenticated replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger`, and the `aptos` CLI's transaction-replay command) to confirm that locally re-executed transactions match the `TransactionInfo` that was actually committed to the ledger (and thus covered by the transaction accumulator / ledger-info signatures). The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents with a `TODO(trading-native)` comment.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` performs four checks: execution status, gas used, write-set hash vs `state_change_hash`, and event root hash. It returns `Ok(())` without ever inspecting `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (present on `TransactionInfoV1`), or `txn_info.position_state_checkpoint_hash()`. The in-line comment acknowledges this: [2](#0-1) 

These checkpoint hashes are exactly the authenticated commitments of the world state (the Sparse/Jellyfish Merkle root, the hot-state root, and the native-position-state root) that a `StateCheckpoint`/`BlockEpilogue` transaction is supposed to bind, as seen in the fields and builders of `TransactionInfoV0`/`V1`: [3](#0-2) 

This comparator is the sole correctness gate used by:
- `db-tool`'s `replay_on_archive::execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` per transaction: [4](#0-3) 
- `aptos-debugger`'s `print_mismatches`, used to diagnose divergences between local execution and chain history: [5](#0-4) 
- the `aptos move replay`/CLI transaction-replay command: [6](#0-5) 

Because none of these call sites cross-check the state/hot-state/position-state checkpoint hashes, if a bug in state-checkpoint computation (`DoStateCheckpoint::run`, hot-state accumulation, or the native position-state SMT extension in `do_state_checkpoint.rs`) produces a different root than what was originally committed, replay-verify will report "success" even though the reconstructed ledger state diverges from what the network actually committed. [7](#0-6) 

### Impact Explanation
`replay_on_archive` and the debugger/CLI replay path are the primary tools operators and auditors use to confirm that re-executing archived history reproduces the exact ledger state Aptos mainnet committed (this is the "hard-fork-only divergence during commit/replay" category explicitly in scope). A state-checkpoint-root computation bug (e.g. in JMT update logic, hot-state root computation, or the newer native-position-state root path gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) would corrupt the durable committed state root while remaining completely undetected by this verification path, since write-set hash and event root hash can still match even though the resulting Merkle root diverges. This directly undermines the "authenticated API/proof output bound to the right root" invariant for one of the two intended consumers of `ensure_match_transaction_info`.

### Likelihood Explanation
This is not attacker-triggered in the classic sense; it is a latent gap that turns any independent state-root computation bug (from a future feature rollout, e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`) into a silent divergence that replay-verify tooling cannot catch. Given the TODO explicitly ties the risk to the position-state-checkpoint feature ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), the maintainers are aware the gap is currently benign only because that feature is not yet enabled, but the comparator function itself has no guard preventing this replay-verify blind spot from being relied upon prematurely.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when the local `TransactionInfo`/execution output carries them) against the expected `txn_info`, matching the coverage already given to `state_change_hash` and `event_root_hash`, before any of the trading-native or hot-state-in-checkpoint features are enabled on mainnet.

### Proof of Concept
Not directly exploitable by an external actor; the flaw is demonstrated by code inspection: `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) has no `ensure!` clause referencing `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so a constructed `TransactionOutput` with a correct write-set/event hash but originating from a differently-computed state tree would pass `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs:392-397` without error.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
