I found a concrete analog. This maps directly to the "trusts caller-supplied identity without deriving/binding it to the authenticated data" bug class described in the report.

### Title
Fulfillment service webhook authentication trusts unauthenticated `X-Shopify-Shop-Domain` header instead of a value bound to the HMAC signature - (File: packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts)

### Summary
The Shopify PDA analog: instead of "deriving" the identity (PDA) from validated data, the fulfillment-service authentication handler reads the `shop` identity directly from a request header that is not covered by the HMAC signature, then uses that attacker-controlled value to look up and act on a specific shop's offline session.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/fulfillment-service/validate.ts` only calls `validateHmacFromRequestFactory`, which validates the HMAC solely over `rawBody` [1](#0-0) [2](#0-1) . It never checks the `X-Shopify-Shop-Domain` header. Yet the consuming handler, `authenticateFulfillmentServiceFactory`, pulls the shop identity directly from that unauthenticated header after HMAC validation succeeds, and uses it to load an offline session and build an authenticated admin client:

```ts
const payload = JSON.parse(rawBody);
const shop = request.headers.get(ShopifyHeader.Domain) || '';
...
const session = await ensureValidOfflineSession(params, shop);
``` [3](#0-2) 

This is structurally the same flaw as the Solana report: the handler validates that *some* signature is correct (an authentication check exists), but the actual identity value used to select which tenant's account/session gets acted upon is taken from an untrusted, unvalidated input rather than being derived from or bound to the verified data. In the PDA case, the account key should have been derived inside the account-validation constraints instead of trusted as caller input; here, the shop should be derived from data covered by the HMAC (or cross-checked against it) instead of trusted as a raw header value.

The identical pattern exists in the React Router package's fulfillment-service handler. [4](#0-3) 

### Impact Explanation
Because `X-Shopify-Shop-Domain` is not part of the signed payload, any request whose HMAC is valid (i.e., signed by the app's real secret for that raw body) could have its domain header altered to a different shop's domain, causing `ensureValidOfflineSession` to load a session and offline access token belonging to a different, unrelated shop and exposing that shop's authenticated `admin` client to the fulfillment-service processing code. This is a cross-tenant session/account confusion bug, structurally analogous to the "wiping/using another authority's PDA data" issue in the report. However, the practical impact depends on whether Shopify (the sender) can be tricked into sending a mismatched header/body pair, or whether some other MITM/replay position is required to alter headers post-signing — I was not able to fully verify whether Shopify's servers guarantee the header always matches the signed body in transit, since that guarantee lives outside this repository.

### Likelihood Explanation
Exploitation requires an attacker to alter the `X-Shopify-Shop-Domain` header of an otherwise validly-HMAC'd fulfillment-service request while keeping the body (and thus the HMAC) valid. Since the HMAC secret is per-app and not exposed to unprivileged callers, an external attacker cannot forge a fresh valid HMAC; they would need to intercept/replay/tamper with an in-flight legitimate request (a MITM-style precondition), which the task rules ask to treat with caution. I flag this with reduced confidence because the likelihood hinges on an interception capability not evidenced elsewhere in this codebase.

### Recommendation
Do not read the shop identity from the unauthenticated `X-Shopify-Shop-Domain` header. Either:
1. Include the shop domain in the HMAC-covered payload and validate the header against that authenticated value before using it, or
2. Extend `validateFactory`/`validateHmacFromRequestFactory` for `HmacValidationType.FulfillmentService` to bind and verify the `X-Shopify-Shop-Domain` header as part of the HMAC computation, similar to how OAuth callback state is bound in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` (`validQuery` combines HMAC and state comparison) [5](#0-4) .

### Proof of Concept
Conceptual PoC (requires ability to intercept/modify an in-flight, validly-signed fulfillment-service request before it reaches the app, since the HMAC secret itself cannot be forged by an unprivileged party):
1. Capture a legitimate fulfillment-service POST request for `shop-a.myshopify.com`, with a valid `X-Shopify-Hmac-Sha256` computed over the raw body.
2. Modify only the `X-Shopify-Shop-Domain` header to `shop-b.myshopify.com`, leaving the body (and therefore the HMAC) unchanged.
3. Send the modified request to `shopify.authenticate.fulfillmentService`. Because `validateFactory` only checks the HMAC against `rawBody` [1](#0-0) , validation succeeds.
4. `authenticateFulfillmentServiceFactory` then reads `shop-b.myshopify.com` from the header and loads `shop-b`'s offline session/admin client instead of `shop-a`'s [3](#0-2) .

**Note on confidence:** This finding requires an interception/MITM-style precondition to alter the header post-signing, which the task rules instruct to treat skeptically. I present it as the closest structural analog found in the codebase (unauthenticated identity value trusted for session/account lookup instead of being derived from verified data), but flag that its real-world exploitability is less certain than the original PDA report's fully unprivileged trigger.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
```
