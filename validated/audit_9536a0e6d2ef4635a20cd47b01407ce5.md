### Title
Uncaught exception in `sanitizeHost` via crafted base64 `host` param causes unhandled crash before validation completes - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the `host` query parameter with `base64regex` before decoding it and passing the result to `new URL()`, but the regex accepts base64 strings that either fail Node's `atob` decoding or decode into a string that is not a valid URL authority. Both `decodeHost` (`atob`) and `new URL()` can throw synchronously and are not wrapped in a try/catch inside `sanitizeHost`, so a crafted, unauthenticated `host` value propagates an unhandled exception out of the function instead of returning `null`.

### Finding Description
`sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` does: [1](#0-0) 

1. `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/` only validates the *character set* and optional trailing padding, it does not enforce that the base64 length is a multiple of 4. A string like a single character (`"a"`) or any string whose length mod 4 is 1 passes this regex but is not decodable per the WHATWG forgiving-base64 algorithm that Node's `atob` implements, causing `decodeHost` (`packages/apps/shopify-api/lib/auth/decode-host.ts`, `atob(host)`) to throw a `DOMException`/`InvalidCharacterError` [2](#0-1) .
2. Even when `atob` succeeds, the decoded string is interpolated directly into `` `https://${decodeHost(sanitizedHost)}` `` and passed to `new URL(...)`. If the decoded payload is not a syntactically valid URL authority (e.g., a base64 encoding of a string like `"::::"` or one containing disallowed characters), the `URL` constructor throws a `TypeError: Invalid URL`.

Neither exception is caught inside `sanitizeHost`; the function only has explicit handling for the "regex doesn't match" and "hostname doesn't match allowed domains" cases, not for decode/parse failures. Because this is invoked directly on the unauthenticated `host` query parameter in flows such as `validate-shop-and-host-params.ts` (`packages/apps/shopify-app-react-router/.../validate-shop-and-host-params.ts`, `packages/apps/shopify-app-remix/.../validate-shop-and-host-params.ts`) and `redirect-to-auth.ts` / `redirect-to-shopify-or-app-root.ts` in `shopify-app-express`, an anonymous client can trigger this before any shop/session lookup occurs [3](#0-2) [4](#0-3) .

### Impact Explanation
This is a request-level denial-of-service/error-handling defect: a crafted `host` parameter causes an unhandled exception to escape `sanitizeHost` instead of the intended graceful `null` return. In Express-based apps this becomes an uncaught synchronous throw in a route/middleware (or an unhandled promise rejection if invoked in an async context without a wrapping try/catch), and in Remix/React Router it surfaces as an unhandled loader error. The impact is scoped to producing a 500/error response (or, in the worst case, an unhandled exception that isn't converted into a response and can affect the request-handling worker) rather than any session/token compromise, since no authentication data is exposed or bypassed. This matches a DoS class of impact on an unauthenticated route, but it is not a session/auth-forgery bug.

### Likelihood Explanation
This requires no privileges beyond sending an anonymous GET request with a `host` query parameter (e.g., to a login or embedded-app entry route). It is fully attacker-controlled and repeatable, since valid-charset-but-invalid-length or invalid-URL-decoding base64 payloads can be trivially constructed and re-used against any app built on `@shopify/shopify-api` that calls `sanitizeHost` directly on unauthenticated input.

### Recommendation
Wrap the `decodeHost` call and the `new URL(...)` construction inside `sanitizeHost` in a try/catch, returning `null` (or throwing `InvalidHostError` when `throwOnInvalid` is true) on any decode/parse failure, so malformed base64 or malformed decoded host values are treated identically to a regex mismatch instead of throwing an unhandled exception.

```ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost should not throw for malformed base64/decoded host, but currently does', () => {
  const shopify = shopifyApi(testConfig());

  // 1) Regex-valid but non-multiple-of-4 base64 -> atob throws
  expect(() => shopify.utils.sanitizeHost('a')).not.toThrow(); // FAILS today: atob('a') throws

  // 2) Valid base64 that decodes to an invalid URL authority
  const malformedHost = Buffer.from('::::').toString('base64');
  expect(() => shopify.utils.sanitizeHost(malformedHost)).not.toThrow(); // FAILS today: new URL('https://::::') throws TypeError
});
```

Expected (per invariant): request should resolve to a handled "invalid host" response (e.g., render App Bridge / 500 with controlled message). Actual: an unhandled exception is thrown from `sanitizeHost` before that handling occurs.
