Analog found. The `Contract Branch.sol` deposit-cap bug (cap checked using post-deposit state, allowing overshoot) maps onto a stronger, root-cause version of the same invariant break in `x/uregistry`/`x/uexecutor`: the `LiquidityCap` field is defined and required, but is **never read or enforced anywhere in the deposit execution path**, so the cap does nothing at all.

### Title
`LiquidityCap` on `TokenConfig` is validated as mandatory but never enforced during PRC20 minting - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`uregistry.TokenConfig` carries a `LiquidityCap` field described as "max supply cap for this token" and `ValidateBasic` rejects any token config with an empty `LiquidityCap`, implying the protocol intends to bound how much of a given external asset can be represented as PRC20 on Push Chain. However, the deposit/mint path that actually mints PRC20 tokens (`depositPRC20` → `CallPRC20Deposit` / `CallPRC20DepositAutoSwap`) never reads `LiquidityCap`, never tracks cumulative minted amount, and never compares the inbound amount (or resulting total) against it.

### Finding Description
`x/uregistry/types/token_config.go` enforces `LiquidityCap` non-emptiness at config-admission time: [1](#0-0) 

The field itself is documented as a supply cap: [2](#0-1) 

But the deposit path that mints PRC20 into a recipient's UEA/EOA on every honestly-finalized inbound (`x/uexecutor/keeper/handler.go:depositPRC20`) only fetches the `NativeRepresentation.ContractAddress` and the deposit `amount`; it never looks at `tokenConfig.LiquidityCap`: [3](#0-2) 

This function is invoked directly from the inbound-execution flows (`ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`) once a ballot is finalized by honest Universal Validators: [4](#0-3) [5](#0-4) 

The actual EVM mint call, `CallPRC20Deposit`, forwards the raw `amount` straight to the PRC20 contract's `depositPRC20Token` with no pre-check against any cap: [6](#0-5) 

Since the inbound `Amount` and `SourceChain`/`AssetAddr` are attacker-controlled values originating from a real (attacker-initiated) deposit event on the external chain — and honest UVs faithfully observe and vote on whatever amount the attacker actually deposited/locked on the source chain — an attacker can lock/bridge in amounts that cumulatively (or even in a single inbound) exceed the `LiquidityCap` configured for that token, and Push Chain's own module code will mint the corresponding PRC20 without any resistance. Unlike the external report's version of the bug (where the cap check ran but against the wrong, post-update value), here there is no cap check in this repository's code path at all — the invariant expressed by `LiquidityCap` is purely decorative in `x/uexecutor`.

### Impact Explanation
This directly corrupts PRC20/native asset accounting: `LiquidityCap` is meant to bound how much PRC20 supply of a given bridged asset can exist, presumably to bound Push Chain's exposure/liability for that asset. With no enforcement, an unprivileged attacker can mint PRC20 supply unbounded by the configured cap purely through ordinary deposit/bridge transactions, which is an "unauthorized mint" / "corruption of PRC20 ... accounting" impact under the allowed-impact gate, reachable from default user deposit flows with fully honest validators and honest nodes.

### Likelihood Explanation
High likelihood: no privileged action, no malicious validator/relayer assumption, and no protocol failure is needed — a standard user depositing more of an asset than the admin's configured cap, through the normal inbound voting/finalization flow, triggers unrestricted minting. The only precondition is that the attacker actually locks/sends the funds on the source chain (which they control), and the flow is fully honest-path.

### Recommendation
Track cumulative minted PRC20 supply per token (e.g., a keeper-side or on-chain running total, comparable to the reported fix's request to check the "current deposit" against the cap before applying it) and enforce it in `depositPRC20` / `CallPRC20Deposit` / `CallPRC20DepositAutoSwap` before executing the mint, rejecting (or partially executing/reverting with proper accounting) any inbound whose amount would push total minted supply for that `chain:address` above `TokenConfig.LiquidityCap`.

### Proof of Concept
1. Admin registers a token config for `eip155:1`/`USDC` with `LiquidityCap = "1000000000000000000000000"` (1,000,000 USDC-equivalent), per `x/uregistry/types/token_config.go` validation.
2. Attacker deposits/locks 10,000,000 USDC-equivalent on the external chain in a single transaction (or several).
3. Honest Universal Validators observe and vote `MsgVoteInbound` for the real amount; quorum is reached honestly.
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the full 10,000,000 PRC20 to the recipient — `LiquidityCap` is never consulted anywhere in this path, so no error is raised and the cap is silently exceeded.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
