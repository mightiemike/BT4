### Title
Unprivileged Address Pre-Funding Griefing / DoS of `CreateAccount` via the System Program - (File: `programs/system/src/system_processor.rs`)

### Summary
The System Program's `create_account` (and `CreateAccountWithSeed`) path aborts with `SystemError::AccountAlreadyInUse` if the target address already holds any lamports at execution time. Because any unprivileged sender can transfer lamports to an arbitrary, publicly-derivable address without needing to be a signer on that address, an attacker who observes a pending `CreateAccount`/`CreateAccountWithSeed` transaction (or who can predict the target address ahead of time, e.g. via `Pubkey::create_with_seed`) can front-run it with a trivial `Transfer` of dust lamports to the target address. This causes the legitimate account-creation transaction to permanently fail, mirroring the `LeapFactory.createDrop()` front-running DoS pattern where a predictable/derivable target identity lets a third party pre-empt legitimate initialization.

### Finding Description
`create_account()` in `system_processor.rs` explicitly checks that the `to` account has zero lamports before allowing creation, and returns `AccountAlreadyInUse` otherwise: [1](#0-0) 

This check applies to both `SystemInstruction::CreateAccount` and `SystemInstruction::CreateAccountWithSeed`, both of which route through `create_account()`: [2](#0-1) 

The target address for `CreateAccount` is often deterministic/predictable ahead of time (a fresh keypair whose pubkey is visible once the unsigned transaction/instruction is broadcast, or a `create_with_seed` derived address computed from a public `base`, `seed`, and `owner`): [3](#0-2) 

Crucially, sending lamports to that address via a plain `SystemInstruction::Transfer` requires no signature or permission from the recipient — only the sender must sign: [4](#0-3) 

Combining these facts: any unprivileged network participant can watch the mempool (or predict the seed-derived address off-chain) and submit a cheap `Transfer` of 1 lamport to the not-yet-created target address before the legitimate `CreateAccount`/`CreateAccountWithSeed` transaction lands. When the legitimate transaction executes afterward, `to.get_lamports() > 0` is now true, and the transaction fails with `AccountAlreadyInUse`, exactly as demonstrated by the existing regression test: [5](#0-4) 

This is a direct DoS/griefing analog of the reported `LeapFactory.createDrop()` issue: in both cases a target identity/address is predictable from public inputs, and an attacker (with no special privilege) can pre-empt it to make the victim's legitimate creation transaction revert.

Notably, Agave's own developers recognized this griefing vector: `SystemInstruction::CreateAccountAllowPrefund` was added specifically to let callers bypass the "zero lamports" requirement when the target has been legitimately pre-funded ("Intended for use where account has already had rent paid in whole or in part before creation"): [6](#0-5) 

However, this new instruction is opt-in and feature-gated; the original `CreateAccount`/`CreateAccountWithSeed` paths used pervasively across the ecosystem (wallets, CLI, staking/nonce account creation) remain fully exposed to the pre-funding griefing pattern.

### Impact Explanation
This enables a low-cost, unprivileged denial-of-service against any protocol or user flow that creates an account at a predictable or seed-derived address (e.g., nonce accounts, stake accounts, seed-derived program accounts created via `CreateAccountWithSeed`, as seen in `cli/src/nonce.rs` and `cli/src/stake.rs`). An attacker can repeatedly grief such flows by dusting the target address before each retry, forcing failed transactions, wasted fees, and blocked legitimate initialization — the same class of impact (front-run DoS of a creation function) described in the source finding. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
Likelihood is high for any workflow using deterministic/seed-derived addresses (`Pubkey::create_with_seed`) since the derivation inputs (base pubkey, seed string, owner) are public and computable off-chain, and the pre-funding `Transfer` instruction is trivial, cheap, and requires no special privilege — it is reachable directly from an ordinary unprivileged transaction sender.

### Recommendation
Where feasible, callers/programs creating accounts at deterministic addresses should use (or agave should more broadly promote/default to) the `CreateAccountAllowPrefund` instruction path, which does not require the target to hold zero lamports and instead only asserts ownership/data-emptiness invariants, removing the dust-griefing precondition. Documentation/guidance should clearly flag that `CreateAccount`/`CreateAccountWithSeed` targets are griefable via unprivileged pre-funding and that consumers relying on first-time account creation at predictable addresses should design for idempotent/prefund-tolerant creation.

### Proof of Concept
1. Attacker observes (or independently computes via `Pubkey::create_with_seed(base, seed, owner)`) the target address that a victim's forthcoming `CreateAccountWithSeed` transaction will create, per [3](#0-2) .
2. Attacker submits an unprivileged `SystemInstruction::Transfer` of 1 lamport to that address (no signature from the target required), per [4](#0-3) , and it lands first.
3. Victim's `CreateAccount`/`CreateAccountWithSeed` transaction executes afterward and fails with `SystemError::AccountAlreadyInUse` because `to.get_lamports() > 0`, per [1](#0-0)  and confirmed by the existing unit test at [5](#0-4) .

                    address,

                );

            }
            Some(*base)
        } else {
            None
        };

        Ok(Self {
            address: *address,
            base,
        })

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
