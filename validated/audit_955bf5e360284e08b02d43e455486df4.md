Based on my investigation, I found a directly analogous logic flaw in the vault secrets response-signature verification, structurally identical to the reported multisig `threshold == 0` bug: a quorum/threshold value of `0` silently defeats an equality/inequality check meant to enforce a minimum number of valid approvals.

### Title
Zero-value `minRequired` threshold bypasses vault OCR signature validation - (File: core/capabilities/vault/vaulttypes/types.go)

### Summary
`vaulttypes.ValidateSignatures` verifies that a `SignedOCRResponse` carries at least `minRequired` valid signatures from `allowedSigners` before the gateway/vault aggregator accepts a secrets response as authoritative [1](#0-0) . Just like the multisig `threshold <= signers_num` check that permits `threshold == 0` and thereby breaks the intended `approvals_num == threshold` execution gate, this function's early "not enough signatures" guard (`len(resp.Signatures) < minRequired`) and its per-iteration exit condition (`len(validSigners) >= minRequired`) both trivially pass when `minRequired == 0`, regardless of whether any signature actually verifies against an allowed signer.

### Finding Description
The vulnerable logic: [2](#0-1) 

Walking through it with `minRequired = 0`:
1. `len(resp.Signatures) < minRequired` → `len(resp.Signatures) < 0` is always false, so the "not enough signatures" short-circuit never triggers even for zero signatures.
2. If at least one signature is present, the loop recovers the signer's address via `crypto.SigToPub` and only adds it to `validSigners` if it matches `allowedSigners`.
3. Immediately after processing the **first** signature — matched or not — the loop checks `if len(validSigners) >= minRequired`. With `minRequired == 0`, `len(validSigners) >= 0` is unconditionally true, so the function returns `nil` (success) after inspecting just one signature, even if that signature came from a completely untrusted key.

This mirrors the report's root cause exactly: an equality/threshold check (`approvals_num == threshold` in the multisig, `len(validSigners) >= minRequired` here) that was written assuming the threshold is always positive, with no explicit floor validation on the threshold/quorum input itself.

### Impact Explanation
If `minRequired` is ever computed as `0` when calling `ValidateSignatures` — e.g., through misconfiguration of DON fault-tolerance parameters, a DON with zero configured signers, or any code path that derives this value from an on-chain/off-chain config field without an explicit `> 0` floor — an attacker who can get at least one syntactically-valid-looking signature blob into a `SignedOCRResponse` can make the gateway accept it as fully validated, bypassing OCR consensus/signer-authenticity checks. In the vault flow this backs secrets create/update/delete/list operations, so a bypass here would let a signed response with **no legitimate signer approval** be treated as trusted, undermining the multi-node consensus guarantee the check exists to enforce.

### Likelihood Explanation
I was not able to fully trace, within the available tool budget, the exact call site(s) that compute the `minRequired` argument to `ValidateSignatures` to confirm whether `0` is reachable in production (the visible caller in `core/services/gateway/handlers/vault/aggregator.go` calls `a.validateUsingSignatures(...)`, whose body/threshold derivation I did not get to inspect before running out of iterations). The function's related quorum check in the same package, `validateUsingQuorum`, derives its threshold as `2*don.F + 1`, which cannot be zero for `don.F >= 0` [3](#0-2) , suggesting normal DON configs likely keep `minRequired` non-zero as well. This lowers confidence that the zero-threshold state is reachable via a normal/unprivileged flow, but the function itself contains no defensive floor, so any future or edge-case caller (e.g., a DON with an unusually configured signer/threshold field) would silently reintroduce the exact same class of bug as the reported multisig issue.

### Recommendation
- **Short term:** In `ValidateSignatures`, explicitly reject `minRequired <= 0` at the top of the function (`if minRequired <= 0 { return error }`), independent of any caller-side guarantees.
- **Long term:** Audit all callers/derivations of signature/approval thresholds (vault, multisig-analog quorum code, OCR `F`-derived thresholds) to ensure a minimum value of `1` is enforced wherever a threshold is computed or configured, and add adversarial test cases (threshold/`minRequired` = 0) to the test suite, mirroring the audit's long-term recommendation for the original multisig contract.

### Proof of Concept
Call `vaulttypes.ValidateSignatures(resp, allowedSigners, 0)` with a `SignedOCRResponse` containing exactly one syntactically-valid ECDSA signature (65-byte recoverable signature) that does **not** correspond to any address in `allowedSigners`, and a context of at least 64 bytes with a valid-format config digest. The function returns `nil` after the first loop iteration because `len(validSigners) >= 0` is true, despite `validSigners` being empty — i.e., zero genuine approvals are accepted as satisfying the quorum. This is directly reproducible by unit-testing `ValidateSignatures` with `minRequired = 0`, analogous to how the multisig report demonstrates that `threshold = 0` breaks `approvals_num == threshold`. func ValidateSignatures(resp *SignedOCRResponse, allowedSigners []common.Address, minRequired int) error {
	if len(resp.Context) < 64 {
		return fmt.Errorf("context too short: expected min 64 bytes, got %d bytes", len(resp.Context))
	}

	if len(resp.Signatures) < minRequired {
		return fmt.Errorf("not enough signatures: expected min %d, got %d", minRequired, len(resp.Signatures))
	}

	// The context contains:
	// 0:32 -> config digest
	// 32:64 -> epoch + round, namely:
	//   - 0:27 -> zero padding
	//   - 27:31 -> sequence number (big endian uint32)
	//   - 31:32 -> zero round value
	// 64:96 -> extra hash (not used by the vault plugin)
	cd, epochRound := resp.Context[:32], resp.Context[32:64]
	configDigest, err := ocr2types.BytesToConfigDigest(cd)
	if err != nil {
		return fmt.Errorf("invalid config digest in signature: %w", err)
	}

	epoch := binary.BigEndian.Uint32(epochRound[27:31])
	round := epochRound[31]

	fullHash := ocr2key.ReportToSigData(ocr2types.ReportContext{
		ReportTimestamp: ocr2types.ReportTimestamp{
			ConfigDigest: configDigest,
			Epoch:        epoch,
			Round:        round,
		},
	}, []byte(resp.Payload))

	validSigners := map[common.Address]bool{}
	for _, s := range resp.Signatures {
		signerPubkey, err := crypto.SigToPub(fullHash, s)
		if err != nil {
			return fmt.Errorf("invalid signature: %w", err)
		}
		signerAddr := crypto.PubkeyToAddress(*signerPubkey)

		for _, as := range allowedSigners {
			if as.Hex() == signerAddr.Hex() {
				validSigners[signerAddr] = true
				break
			}
		}

		if len(validSigners) >= minRequired {
			return nil
		}
	}

	return fmt.Errorf("only %d valid signatures, need at least %d", len(validSigners), minRequired)
