## Finding: Zero-Burn Block-Commit Wins Sortition For Free During Prepare Phase / Post-Sunset

### Title
Miners can win sortition and collect block rewards with a zero-value burn commit during the prepare phase/post-PoX-sunset — (File: `stackslib/src/chainstate/burn/operations/leader_block_commit.rs`)

### Summary
`LeaderBlockCommitOp::parse_pre_pox_waterfall_commits` accepts a block-commit whose single burn output amount is `0` when parsing occurs in the prepare phase or after the PoX sunset, unlike the parallel reward-phase branch and the newer waterfall-commit parser, both of which explicitly reject a zero burn/transfer amount.

### Finding Description
`parse_pre_pox_waterfall_commits` branches on whether the transaction occurs during the prepare phase / post-sunset window or the reward phase: [1](#0-0) 

In the prepare-phase/sunset branch, `amount` (the value of the single burn output) is used directly as `burn_fee` with **no check that it is nonzero**. Compare this to the reward-phase branch just below it, which explicitly guards against a zero total commitment: [2](#0-1) 

The project is aware this class of bug matters — a sibling parser for the newer "waterfall" (sBTC) commit format has an explicit regression test asserting that a zero-amount output must be rejected "since accepting it would let a miner commit at zero cost": [3](#0-2) 

No equivalent check or test exists for `parse_pre_pox_waterfall_commits`'s prepare-phase/sunset path.

Once such a zero-burn `LeaderBlockCommitOp` is accepted, it flows into `BurnSamplePoint::make_min_median_distribution`. During the prepare phase, the mining commitment window is forced to `1` [4](#0-3) , so the sample point's `burns` value equals the commit's own `burn_fee` directly (median of a window of size 1 is the value itself): [5](#0-4) .

Sortition winner selection contains a bypass for the single-candidate case that ignores burn-weighted ranges entirely: [6](#0-5) 

So if the attacker is the sole block-committer at a given burn height during the prepare phase (or post-sunset), `dist.len() == 1` and `sample_burn_distribution` returns the zero-burn candidate as the winner unconditionally, regardless of the (zero) burn-weighted range. `select_winning_block` then propagates this candidate as the tenure's winning block-commit: [7](#0-6) .

The winning miner then receives the full coinbase reward computed from `calculate_miner_reward`, having contributed zero burn — an equality break analogous to BunniSwap's `computeSwap`, where a swap with `amountSpecified` triggering an `ExactOut`/`ExactIn` path yielded nonzero output despite zero input. Here, a nonzero sortition win (and reward) is granted despite a burn amount of zero, breaking the intended equality "no burn ⇒ no chance of winning."

### Impact Explanation
This is a reward mis-payment: an unprivileged, single actor (any Bitcoin transaction sender who understands the prepare-phase/sunset commit format) can win Stacks sortition and receive the block's coinbase reward without contributing any actual burn, provided they are the sole committer for that specific burn block. All full nodes deterministically compute the same result from the chain data, so this does not cause a state-root divergence or fork by itself, but it is a concrete instance of value (block reward) being extracted for free, mapping to "reward mis-payment bounded to fees/coinbase" in the classification of accepted findings.

### Likelihood Explanation
Prepare-phase and post-sunset blocks routinely have few competing commits, and an attacker only needs to ensure no other commit lands in the same burn block to force `dist.len() == 1`. Crafting a Bitcoin transaction with a single dust/zero-value `OP_RETURN`-adjacent burn output is trivial and requires no special privilege, no majority, and no cooperation from any other party.

### Recommendation
- **Short term**: Add an explicit `burn_fee == 0` (equivalently, `amount == 0`) rejection in the prepare-phase/post-sunset branch of `parse_pre_pox_waterfall_commits`, mirroring the check already present in the reward-phase branch and in `parse_pox_waterfall_commits`.
- **Long term**: Add an invariant/fuzz test (e.g., via Medusa-style property testing or a Rust equivalent) asserting that no `LeaderBlockCommitOp` with `burn_fee == 0` can ever be selected as a sortition winner, across both classic and waterfall commit formats and across all burn-phase configurations (reward phase, prepare phase, post-sunset).

### Proof of Concept
1. During a prepare-phase or post-PoX-sunset burn block, submit a Bitcoin transaction shaped as a `LeaderBlockCommitOp` whose single required output (`output_0`) is a burn address with `amount = 0`.
2. Ensure no other miner submits a competing block-commit in that same burn block (achievable by choosing a low-activity block or simply being first/only).
3. `parse_pre_pox_waterfall_commits` accepts the op with `burn_fee = 0` (no rejection path exists for this branch).
4. `make_min_median_distribution` produces a single `BurnSamplePoint` with `burns = 0`.
5. `sample_burn_distribution` sees `dist.len() == 1` and returns the attacker's op as the winner unconditionally, bypassing the burn-weighted range check.
6. The attacker's block-commit is recorded as the tenure's winning commit, and the attacker earns the full coinbase reward for that Stacks block despite having burned zero sats.

    /// rejected: such an output is dust (non-standard on the Bitcoin network),
    /// and accepting it would let a miner commit at zero cost. A positive-amount
    /// output parses into a commit whose `burn_fee` carries that amount.
    #[test]
    fn test_parse_pox_waterfall_rejects_zero_amount() {
        fn recipient(amount: u64) -> Option<BurnchainRecipient> {
            let addr = StacksAddress::new(1, Hash160([1; 20])).unwrap();
            Some(BurnchainRecipient {
                address: PoxAddress::Standard(addr, None),
                amount,
            })
        }

        // zero-amount first output -> rejected as invalid input
        let output_0 = recipient(0);
        let outputs = vec![output_0.clone()];
        assert!(matches!(
            LeaderBlockCommitOp::parse_pox_waterfall_commits(&outputs, &output_0),
            Err(op_error::InvalidInput)
        ));

        // positive-amount first output -> parsed, burn_fee carries the amount
        let output_0 = recipient(10);
        let outputs = vec![output_0.clone()];
        let calc = LeaderBlockCommitOp::parse_pox_waterfall_commits(&outputs, &output_0)
            .expect("positive-amount waterfall commit should parse");
        assert_eq!(calc.burn_fee, 10);
    }
