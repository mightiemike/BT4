### Title
Silent overflow/underflow in exchange reserve balance update - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction()` updates the two exchange reserve balances (`firstTokenBalance`/`secondTokenBalance`) that drive the bancor-style pricing curve used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`. Unless the `allowHardenExchangeCalculation` proposal is enabled, the reserve update path performs plain `long` arithmetic (`+`/`-`) with no overflow/underflow check and no post-condition validation, mirroring the exact bug class described in the Caviar `PrivatePool.sol` report: values are combined into a fixed-width accumulator without first checking that the result fits, silently corrupting the invariant that backs the price formula.

### Finding Description
`ExchangeCapsule.transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath, boolean hardenedCalc)` computes the new reserve balances as: [1](#0-0) 

When `hardenedCalc` is `false` (the default/legacy path, active whenever `allowHardenExchangeCalculation` proposal has not been activated), the new balances are computed with plain Java `long` addition/subtraction (`firstTokenBalance + sellTokenQuant`, `secondTokenBalance - buyTokenQuant`, etc.) instead of `StrictMathWrapper.addExact`/`subtractExact`. The post-update sanity check that guards against negative balances is also gated behind `hardenedCalc`: [2](#0-1) 

So in the non-hardened (default) mode there is neither an overflow guard on the additions nor an underflow/negative-balance guard on the subtractions before the value is persisted into the `Exchange` protobuf balance fields.

In addition, `ExchangeProcessor` (used for the non-hardened `Processor` implementation) narrows a `double` computation to `long` without any bounds check: [3](#0-2) 

This is the same bug class as the referenced report: a value that can exceed the target's representable range is cast/added into a fixed-width field (`uint128` in Solidity vs. Java `long` here) without first verifying that the result fits, which silently corrupts the reserve invariant that the constant-product/bancor price formula depends on.

The reserve balances updated here are read back by the same function on every subsequent call (`firstTokenBalance = this.exchange.getFirstTokenBalance()`), so once corrupted (wrapped to a negative or wrapped-around value), every future trade against that exchange pool computes an incorrect price via `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`.

This function is reachable from an anonymous broadcast transaction: `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` directly from an `ExchangeTransactionContract`: [4](#0-3) 

`allowHarden()` returns `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()`, i.e. whether the corresponding hardening proposal has been activated on-chain: [5](#0-4) 

### Impact Explanation
If the non-hardened path is used (default unless the hardening proposal is activated), an attacker can drive `secondTokenBalance - buyTokenQuant` or `firstTokenBalance - buyTokenQuant` below zero, or drive an addition past `Long.MAX_VALUE`, without any exception being thrown and without any check preventing the negative/wrapped value from being persisted. This breaks the `xy=k` (bancor) invariant of the exchange pool, corrupting future price quotes for all traders and potentially allowing extraction of tokens/TRX from the pool at manipulated prices — an asset/accounting corruption analogous to the High-severity Caviar finding.

### Likelihood Explanation
Reachable directly via a normal, unprivileged broadcast transaction (`ExchangeTransactionContract`) against any existing exchange pool; no special permissions are required. It only triggers when the `allowHardenExchangeCalculation` proposal has not been activated on the network (i.e., legacy behavior), which is a normal operating state on many java-tron networks/testnets prior to that proposal's activation.

### Recommendation
Make the overflow/underflow-safe (`StrictMathWrapper.addExact`/`subtractExact`) arithmetic and the post-update non-negative balance check unconditional in `ExchangeCapsule.transaction()`, rather than gating them behind the `hardenedCalc` flag, and add an explicit range check after `(long) issuedSupply` / `(long) exchangeBalance` casts in `ExchangeProcessor` before the value is applied to the persisted balances.

### Proof of Concept
1. Create an exchange pool with a small `secondTokenBalance` (e.g. via `ExchangeCreateContract`) while `allowHardenExchangeCalculation` is not yet activated on the network.
2. Submit an `ExchangeTransactionContract` with a `sellTokenQuant` engineered (via repeated small trades or a single large one) such that `buyTokenQuant` computed by `ExchangeProcessor.exchange()` exceeds `secondTokenBalance`.
3. Observe that `ExchangeCapsule.transaction()` computes `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` as plain `long` subtraction, producing a negative value that is written directly into the `Exchange` capsule via `setBalance` with no `ContractValidateException` thrown (the `hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)` check is skipped because `hardenedCalc` is `false`).
4. Subsequent trades against this pool now compute prices off a corrupted/negative reserve, breaking the invariant analogous to the referenced Caviar `virtualBaseTokenReserves`/`virtualNftReserves` silent overflow.
