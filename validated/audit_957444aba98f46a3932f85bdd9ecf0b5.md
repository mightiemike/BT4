### Title
Unbounded recursive `bytecode_hash_node` in compiled-class hash computation runs outside process-resource-limit sandbox, allowing a crafted DECLARE class to crash the Sierra-compiler component - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`SierraCompiler::compile` in `crates/apollo_compile_to_casm/src/lib.rs` compiles a declarer-submitted Sierra program to CASM inside a resource-limited subprocess, but then computes the compiled-class hash **in the parent process, with no resource limits at all**, by calling `executable_class.hash(&HashVersion::V2)` [1](#0-0) . That hash routine recurses over the compiler-produced bytecode segment tree via `bytecode_hash_node`, with recursion depth driven directly by the nesting of the segment structure returned by the (untrusted-input-driven) Sierra→CASM compiler [2](#0-1) . This is structurally analogous to CVE-2021-45258 (unbounded recursive decode routine `gf_bifs_dec_proto_list` causing a stack-overflow crash from crafted input).

### Finding Description
The gateway's declare-transaction flow (`GenericGateway::add_tx_inner` → `convert_rpc_tx_to_internal_and_executable_txs` → `SierraCompiler::compile`) is reachable by any unprivileged account submitting a DECLARE transaction, subject only to stateless checks on Sierra version and total bytecode size (`max_bytecode_size`, default 80*1024 = 81920 felts) [3](#0-2) , with no check on how the resulting bytecode is *structured* into segments.

`SierraCompiler::compile` performs two distinct steps:
1. `self.compiler.compile(class)` – runs the actual `cairo-lang-sierra-to-casm` compiler binary as a subprocess with explicit CPU-time and memory `ResourceLimits` applied via `resource_limits.apply(&mut command)` [4](#0-3) [5](#0-4) . A crash or resource exhaustion here is isolated to that child process and is turned into an `Err(CompilationUtilError)`.
2. `executable_class.hash(&HashVersion::V2)` – executed directly in the calling (Sierra-compiler component) process, **outside** any subprocess or resource sandbox [6](#0-5) .

`hash()` calls `hash_inner`, which calls `bytecode_hash`, which recurses via `bytecode_hash_node` over the `NL: HashableNestedIntList` (`bytecode_segment_lengths`) tree produced by the real `cairo-lang-starknet-classes` compiler for the declared program:
```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where H: StarkHash, NL: HashableNestedIntList,
{
    if node.is_leaf() { ... }
    else {
        let inner_nodes = node.iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        ...
    }
}
``` [7](#0-6) 

The nesting depth of this segment tree is controlled by the *structure* of the compiled bytecode (nested functions/branches), not its total length: a declarer can author a Sierra program that stays under the 80K-felt bytecode-size limit while producing thousands of deeply-nested internal segments (deeply nested function/branch bodies), causing `bytecode_hash_node` to recurse to a depth on the order of the segment count. Because this call happens in-process with no `catch_unwind`, no subprocess isolation, and no depth bound, a sufficiently deep recursion will overflow the native call stack of the Sierra-compiler process (or, since compilation shares the gateway process in some deployments, the gateway process itself), aborting it with SIGSEGV — exactly the crash class described in the referenced gpac issue for `gf_bifs_dec_proto_list`.

Unlike the compile subprocess step (protected by `ResourceLimits`/CPU-time/memory rlimits and error-converted on failure), the hash-computation step has no such protection, so a crash here is not converted into a graceful `Err`; it terminates the whole process.

### Impact Explanation
A crashed Sierra-compiler (or gateway, depending on deployment topology) process halts declare-transaction processing for that node. Since `max_concurrent_declare_compilations` gates concurrency but not the depth/structure of an individual declared class [8](#0-7) , an attacker needs to submit just one maliciously-structured DECLARE transaction (potentially repeatedly, to any/all gateway nodes) to repeatedly crash the compiler component fleet-wide, since the P2P gateway network relays the same DECLARE transaction to peer sequencers, each independently re-running the same vulnerable compile+hash path (per `docs/diagrams/02-tx-submission-flow.md`). Repeated crashes of this shared, load-bearing component degrade or halt the network's ability to admit new declare transactions across the fleet — a network-wide denial-of-service on transaction confirmation, consistent with the "network unable to confirm new transactions" acceptance criterion.

### Likelihood Explanation
Reachability requires only a single unauthenticated DECLARE transaction from any account able to pass stateless size/version checks — no special privileges, no operator/proposer/prover access needed. Constructing a Sierra program whose CASM bytecode segment tree is deeply nested (e.g., via many nested function/branch structures) while staying under the 80K-felt bytecode cap is a compiler/program-structure exercise, not a privileged action. The main uncertainty (which could not be fully verified without executing the actual `cairo-lang-sierra-to-casm` segment-generation logic, which lives in an external dependency crate not indexed here) is the exact achievable nesting depth for a given bytecode size, and thus whether the resulting recursion depth is sufficient to exhaust a typical Rust thread stack (default 8MB) before other resource limits (e.g., total execution time) intervene.

### Recommendation
- Move the compiled-class hash computation (`executable_class.hash(...)`) inside the same resource-isolated subprocess/sandbox used for compilation, or wrap it with `std::panic::catch_unwind` combined with a bounded-depth, iterative (stack-based, not native-recursion) implementation of `bytecode_hash_node`/`bytecode_hash_internal_node`.
- Enforce an explicit maximum nesting depth on the bytecode segment structure returned by the compiler before hashing, rejecting classes whose segment tree exceeds a safe depth bound, independent of total bytecode size.
- Apply an OS-level `RLIMIT_STACK` or run hash computation on a dedicated thread with a bounded stack size and monitor for abnormal termination, converting a stack overflow into a recoverable compilation error rather than a process crash.

### Proof of Concept
1. Author a Cairo1 contract whose compiled Sierra program, when compiled to CASM, produces a deeply right-nested (or left-nested) bytecode-segment tree — e.g., a long chain of nested `if`/function-call blocks — while the total CASM bytecode stays under `max_bytecode_size` (80 * 1024 felts).
2. Submit this class as a DECLARE V3 transaction to a sequencer's gateway (`POST /add_transaction`).
3. The gateway's declare path invokes `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60`), which successfully compiles the class in the sandboxed subprocess, then calls `executable_class.hash(&HashVersion::V2)` in-process (`crates/apollo_compile_to_casm/src/lib.rs:69`), triggering `bytecode_hash_node` recursion (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:111`) at depth proportional to the crafted segment nesting, causing a native stack overflow and crashing the Sierra-compiler/gateway process — verifiable by observing the process exit with SIGSEGV/abort rather than an `Err(SierraCompilerError)`.

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

pub fn compile_with_args(
    compiler_binary_path: &Path,
    contract_class: ContractClass,
    additional_args: &[&str],
    resource_limits: ResourceLimits,
) -> Result<Vec<u8>, CompilationUtilError> {
    // Create a temporary file to store the Sierra contract class.
    let serialized_contract_class = serde_json::to_string(&contract_class)?;

    let mut temp_file = NamedTempFile::new()?;
    temp_file.write_all(serialized_contract_class.as_bytes())?;
    let temp_file_path = temp_file.path().to_str().ok_or(CompilationUtilError::UnexpectedError(
        "Failed to get temporary file path".to_owned(),
    ))?;

    // Set the parameters for the compile process.
    let mut command = Command::new(compiler_binary_path.as_os_str());
    command.arg(temp_file_path).args(additional_args);

    // Apply the resource limits to the command.
    resource_limits.apply(&mut command);

    // Run the compile process.
    let compile_output = command.output()?;

    if !compile_output.status.success() {
        let stderr_output = String::from_utf8(compile_output.stderr)
            .unwrap_or_else(|_| "Failed to decode stderr output".to_string());

        let error_message = format_compiler_error(&stderr_output, &compile_output.status);
        return Err(CompilationUtilError::CompilationError(error_message));
    }
    Ok(compile_output.stdout)
}
