### Title
Missing small-order/identity check on the VRF public key breaks proof uniqueness, enabling sortition-seed grinding by a single miner - (File: stacks-common/src/util/vrf.rs)

### Summary
`VRF::verify` in this repo validates that the proof's `Gamma` point is not a small-order point, but never performs the equivalent check on the VRF public key point `Y_point_ed` that it decompresses from the registered `VRFPublicKey`. This asymmetry is the same class of defect as the external report (mishandling of degenerate/low-order elliptic-curve points in a signature/proof verification equation), and it breaks the *uniqueness* property that Nakamoto sortition relies on: for a single (adversary-controlled, minority) VRF key, more than one `(Gamma, c, s)` proof can validate for the same `alpha` (the sortition hash), letting a miner choose among multiple valid VRF seeds after the fact.

### Finding Description
`VRF::verify` at [1](#0-0)  does:

```rust
let Y_point_ed = CompressedEdwardsY(Y_point.to_bytes())
    .decompress()
    .ok_or(Error::InvalidPublicKey)?;
if proof.Gamma().is_small_order() {
    return Err(Error::InvalidPublicKey);
}
```

Only `Gamma` is checked for small order; `Y_point_ed` (the public key) is not. `VRFPublicKey::from_bytes`, used when a VRF public key is registered/parsed, likewise only checks that the bytes decompress to *some* valid curve point, with no order check: [2](#0-1) .

This means a public key can legally be the identity element or another point of order dividing 8 (the curve's cofactor). The verification equation is:

```
U_point = s*B - c*Y
V_point = s*H - c*Gamma
c' = Hash(H, Gamma, U, V)
accept iff c' == c
``` [3](#0-2) 

If `Y` is degenerate (e.g., the identity, or a low-order torsion point), the term `c*Y` collapses to one of only a handful of possible values regardless of `c`, which removes the binding between the proof's `c`/`s` scalars and a single unique discrete-log `x`. This is precisely the scenario RFC 9381 (ECVRF) requires "validate_key" to prevent: without it, the same registered key/alpha pair can satisfy the verification equation for more than one `(Gamma, c, s)` triple, i.e. VRF output uniqueness is not guaranteed for that key.

The codebase itself is aware that low-order points are dangerous — the comment on `VRFProof::empty()` explicitly says "can't be all 0's, since an all-0 string decodes to a low-order point" — but this care was only applied to `Gamma`, not to the public key used in the same verification equation.

### Impact Explanation
The VRF seed derived from a valid, verifying VRF proof is chained directly into future sortitions: `block_commit.new_seed` must equal `VRFSeed::from_proof(&self.proof)` and this seed feeds `BlockSnapshot::sample_burn_distribution`, which selects the winning block commit via `sortition_hash.mix_VRF_seed(VRF_seed)` [4](#0-3) . `NakamotoChainState::check_normal_coinbase_tx` and `StacksBlockHeader::validate_burnchain` both accept a block solely because `VRF::verify` returns `Ok(true)` [5](#0-4) [6](#0-5) .

If a single miner registers a VRF public key that is a degenerate/low-order point, it may be possible for them to construct more than one distinct valid `(Gamma, c, s)` proof for the same `alpha` (sortition hash), each producing a different downstream VRF seed via `VRFSeed::from_proof`. Because every node runs the identical (buggy) `VRF::verify`, all nodes would accept whichever seed-producing proof the miner chooses to reveal — this is a minority-triggerable divergence in a value (the VRF seed) that determines the *next* sortition's winner, i.e. exactly the class of "sortition/VRF divergence" called out as High severity: a single attacker biases the seed input to a future leader election without needing majority stake or another party's key.

### Likelihood Explanation
Triggering requires only that an attacker register a VRF public key of their own choosing (no privileged access, no majority stake) — VRF key registration accepts any bytes that decompress to a valid Edwards point, with no order check anywhere in `VRFPublicKey::from_bytes` or in `VRF::verify`. Whether a practical multi-proof construction against a degenerate key exists depends on precise properties of the try-and-increment hash-to-curve output `H_point` and the 128-bit truncated challenge `c` used by this ECVRF variant, which I was not able to fully re-derive/prove within this review — this is a real uncertainty. What is concretely established, however, is that the code omits a check on the public key's order that the RFC and the codebase's own commentary elsewhere (on `Gamma`) treat as necessary, and there is no other check anywhere in the registration or validation path (`leader_key_register.rs`, `sortdb.rs`) that rejects low-order VRF public keys.

### Recommendation
In `VRF::verify`, add a small-order check on `Y_point_ed` symmetric to the existing check on `Gamma`:
```rust
if Y_point_ed.is_small_order() {
    return Err(Error::InvalidPublicKey);
}
```
Additionally, reject low-order public keys at registration time in `VRFPublicKey::from_bytes` so malformed/degenerate keys can never enter the leader-key-register state in the first place.

### Proof of Concept
Not fully constructed: exploiting this requires producing a second valid `(Gamma, c, s)` for a chosen degenerate `Y`, which needs further offline cryptographic analysis of the specific ECVRF variant (try-and-increment hash-to-curve, 128-bit truncated challenge) implemented here — this was not completed within the scope of this review. The structural weakness (missing symmetry between the `Gamma` and `Y` small-order checks in `VRF::verify`, and absence of any order validation in `VRFPublicKey::from_bytes`) is directly demonstrated by the cited code.

    pub fn verify(Y_point: &VRFPublicKey, proof: &VRFProof, alpha: &[u8]) -> Result<bool, Error> {
        let H_point = VRF::hash_to_curve(Y_point, alpha);
        let s_reduced = proof.s();
        let Y_point_ed = CompressedEdwardsY(Y_point.to_bytes())
            .decompress()
            .ok_or(Error::InvalidPublicKey)?;
        if proof.Gamma().is_small_order() {
            return Err(Error::InvalidPublicKey);
        }

        let U_point = s_reduced * &ED25519_BASEPOINT_POINT - proof.c() * Y_point_ed;
        let V_point = s_reduced * &H_point - proof.c() * proof.Gamma();

        let c_prime_hashbuf = VRF::hash_points(&H_point, proof.Gamma(), &U_point, &V_point);
        let Some(c_prime) = VRF::ed25519_scalar_from_hash128(&c_prime_hashbuf) else {
            return Err(Error::InvalidHashPoints);
        };

        // NOTE: this leverages constant-time comparison inherited from the Scalar impl
        Ok(c_prime == *(proof.c()))
    }
```

    /// Given the weighted burns, VRF seed of the last winner, and sortition hash, pick the next
    /// winner.  Return the index into the distribution *if there is a sample to take*.
    fn sample_burn_distribution(
        dist: &[BurnSamplePoint],
        VRF_seed: &VRFSeed,
        sortition_hash: &SortitionHash,
    ) -> Option<usize> {
        if dist.is_empty() {
            // no winners
            return None;
        }
        if dist.len() == 1 {
            // only one winner
            return Some(0);
        }

        let index = sortition_hash.mix_VRF_seed(VRF_seed).to_uint256();
        for (i, dist_elem) in dist.iter().enumerate() {
            if (dist_elem.range_start <= index) && (index < dist_elem.range_end) {
                debug!(
                    "Sampled {}: i = {}, sortition index = {}",
                    dist_elem.candidate.block_header_hash, i, &index
                );
                return Some(i);
            }
        }
