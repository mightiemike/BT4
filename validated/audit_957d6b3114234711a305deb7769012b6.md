## Analysis

The `bytecode_hash_node` function in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recurses over an attacker-influenced tree structure (`NestedIntList`, i.e. `bytecode_segment_lengths`) with no depth limit and no dedicated large-stack thread, which is directly analogous to the reported MongoDB bug class (unbounded recursive processing of a user-supplied nested structure causing a native stack overflow / DoS).

### Title
Unbounded native recursion in compiled-class-hash computation over attacker-controlled bytecode segment tree can crash the sequencer/gateway - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` [1](#0-0)  recursively walks the `bytecode_segment_lengths` (`NestedIntList`) tree produced when a Sierra contract is compiled to CASM, with **no depth bound**. This tree's shape is derived from the *declared contract's own control-flow structure*, so a class declarer indirectly controls its nesting depth. The recursion uses real Rust stack frames (not VM-simulated stack), and unlike the transaction-execution paths in `blockifier`, this code path is not run inside a thread configured with an enlarged stack.

### Finding Description
Compiled class hashing is invoked right after Sierra→CASM compilation, in-process, in `SierraCompiler::compile` [2](#0-1) :
```
let executable_class = self.compiler.compile(class)?;
let executable_class_hash = executable_class.hash(&HashVersion::V2);
```
The comment in `blockifier_reexecution/src/compile.rs` confirms the compiler subprocess is resource-isolated, but the hash step happens afterward, outside that isolation [3](#0-2) .

`hash()` → `hash_inner()` → `bytecode_hash()` → `bytecode_hash_node()` walk the `bytecode_segment_lengths` tree recursively per node [4](#0-3) . Each recursive call in `bytecode_hash_node` allocates a stack frame containing iterators, `Vec` collection buffers (`collect_vec()`), and hash-array computation locals [5](#0-4) . There is no `max_recursion_depth`-style guard analogous to the one enforced for Cairo call-stack recursion in `blockifier`'s `RecursionDepthGuard` [6](#0-5) , and no dedicated large-stack thread analogous to the ones used for Cairo Native contract execution [7](#0-6)  or the worker pool [8](#0-7) .

This mirrors the reported CVE-2021-32040 bug class exactly: a specific operator/stage (here, the bytecode-segment tree walker) whose per-frame stack usage, combined with attacker-influenced nesting depth, can exceed the process's native stack and crash the process — with no configurable depth limit as a mitigation (unlike MongoDB's `internalPipelineLengthLimit` workaround).

Only `max_bytecode_size` (default 61440 bytes, i.e. up to ~15360 felts, see `gateway_config...max_contract_bytecode_size`) bounds the total bytecode [9](#0-8) ; nothing bounds the *tree depth* of `bytecode_segment_lengths` independent of total size — a pathologically constructed control-flow structure (e.g. long chains of single-instruction functions/branches) can approach that bound in nesting depth, since the segment tree mirrors the Sierra program's function/branch structure rather than being balanced.

### Impact Explanation
If the recursion depth exceeds the native stack limit of the thread executing `SierraCompiler::compile` (the gateway's declare-transaction handling path, not a hardened worker with an enlarged stack), the process crashes with a stack overflow — this is an unrecoverable process abort in Rust (no panic/catch_unwind can trap a real stack overflow). Because `max_concurrent_declare_compilations` allows up to 40 concurrent declare compilations by default [10](#0-9) , a single or a few malicious declare transactions submitted by any unprivileged account can crash the gateway/sequencer component, resulting in the network being unable to confirm new transactions (denial of service) — matching the "network unable to confirm new transactions" acceptance criterion.

### Likelihood Explanation
Reachable by any account submitting a `DECLARE` transaction with a crafted Sierra contract compiled to a CASM whose compiler-derived `bytecode_segment_lengths` is deeply/pathologically nested. No special privileges are required. The exact depth needed to overflow the default thread stack is unverified in this analysis (would require testing the compiled binary's stack-frame size per recursion level and the gateway thread's actual stack size), which is the main uncertainty in confirming exploitability end-to-end.

### Recommendation
- Add an explicit maximum recursion/nesting-depth check for `bytecode_segment_lengths` before or during `bytecode_hash_node`, rejecting classes whose segment tree exceeds a safe bound (mirroring `max_recursion_depth` used elsewhere in `blockifier`).
- Alternatively, convert `bytecode_hash_node` to an iterative (explicit-stack) algorithm so recursion depth is decoupled from the native call stack.
- Run compiled-class hashing on a thread with an explicit, sized stack (as already done for Cairo Native execution in `transaction_executor.rs` and `worker_pool.rs`), so any residual deep recursion fails safely (e.g., via `RUST_MIN_STACK`-style guarantees) rather than crashing the whole process.

### Proof of Concept
Not independently constructed/verified in this analysis — doing so would require crafting a Sierra program whose compiled CASM segment structure (as emitted by `cairo_lang_starknet_classes`) is deeply nested near the `max_bytecode_size` bound, submitting it as a `DECLARE` transaction, and observing whether `SierraCompiler::compile`'s call to `.hash(&HashVersion::V2)` [11](#0-10)  triggers a stack overflow in the gateway process. This step (measuring actual achievable nesting depth from the cairo-lang compiler and its correlation to available stack) could not be completed with the available static analysis tools.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}

// Implementing the Drop trait to decrement the recursion depth when the guard goes out of scope.
impl Drop for RecursionDepthGuard {
    fn drop(&mut self) {
        *self.current_depth.borrow_mut() -= 1;
    }
}
