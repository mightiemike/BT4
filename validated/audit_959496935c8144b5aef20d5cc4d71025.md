### Title
Missing slippage/minimum-output protection in `ExchangeInjectContract` liquidity-deposit path allows sandwich-attack value extraction - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` (a TRC10 "Bancor-style" exchange liquidity deposit) computes the counter-token amount required to inject liquidity purely from the pool's current on-chain ratio at execution time, with no user-supplied bound (no "expected"/slippage parameter exists in `ExchangeInjectContract` at all). This is a stronger variant of the reported Uniswap v4 `SlippageCheck.validateMaxInNegative` bug class: there, slippage was skipped only when accrued fees exceeded required tokens; here, slippage protection is entirely absent for every liquidity-injection transaction, so any pool-ratio manipulation immediately before the inject transaction is included forces the depositor to inject at an attacker-chosen ratio with no recourse.

### Finding Description
`ExchangeInjectActuator.doValidate()` reads the current pool balances and derives `anotherTokenQuant` from the live ratio: [1](#0-0) 

Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced via `if (anotherTokenQuant < tokenExpected) { throw ... "token required must greater than expected"; }`: [2](#0-1) 

`ExchangeInjectContract` has no equivalent field — its protobuf definition only carries `owner_address`, `exchange_id`, `token_id`, and `quant`, with no minimum/maximum bound on the resulting `anotherTokenQuant`: [3](#0-2) 

The only checks performed in `doValidate()` are that the computed `anotherTokenQuant` is positive, within the global `exchangeBalanceLimit`, and that the depositor holds enough balance — none of these bound the ratio at which the deposit occurs: [4](#0-3) 

`execute()` then recomputes the same ratio-based amount against whatever the pool state is at execution time and applies it unconditionally: [5](#0-4) 

Because `ExchangeTransactionContract` trades (buy/sell) can be broadcast and mined in the same block or immediately before the inject transaction, an attacker can trade against the pool to skew `firstTokenBalance`/`secondTokenBalance` right before the victim's `ExchangeInjectContract` is executed, then trade back afterward, extracting value analogous to a Uniswap v4 liquidity-increase sandwich — except here the victim has *no way at all* to express a slippage bound, since the field simply doesn't exist (the reported bug only concerns a positive-`balanceDelta` edge case; this is the unconditional absence of protection).

### Impact Explanation
Any account that is the creator of a TRC10 exchange pair (the only actor permitted to call `ExchangeInjectContract`, enforced by the `is not creator` check) is exposed to guaranteed value loss when injecting liquidity if an adversary front-runs/back-runs the injection with `ExchangeTransactionContract` trades. This is an asset/accounting corruption risk reachable purely through normal broadcast transactions (a `ExchangeTransactionContract` trade plus an `ExchangeInjectContract` deposit), not requiring any privileged system role — the "creator" restriction is a pool-specific ownership property obtainable by any address that creates the exchange, not a network-privileged actor.

### Likelihood Explanation
Exploitation only requires observing a pending `ExchangeInjectContract` transaction in the mempool/broadcast layer and submitting `ExchangeTransactionContract` trades before and after it in adjacent transactions/blocks — a standard sandwich pattern with no special access needed. The lack of an `expected`/slippage field in the contract itself (not just a validation-logic bug) makes this deterministic and always exploitable whenever an inject transaction is visible before inclusion.

### Recommendation
Add a slippage-bound field to `ExchangeInjectContract` (e.g., `expected` for the minimum acceptable `anotherTokenQuant`, mirroring `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` analogous to the check already present in `ExchangeTransactionActuator`. Since this requires a protobuf field change, it should be considered for a hard-fork proposal (similar to other `Parameter.java`-gated `Allow*` features) rather than a silent behavior change.

### Proof of Concept
1. Exchange pool `E` has `firstTokenBalance=100000000`, `secondTokenBalance=200000000` for tokens A/B.
2. Creator broadcasts `ExchangeInjectContract{exchange_id=E, token_id=A, quant=1000000}`, expecting to receive/pair roughly `anotherTokenQuant ≈ 2000000` of B based on current ratio, per the computation at `ExchangeInjectActuator.java:215-227`.
3. Attacker observes the pending transaction and submits `ExchangeTransactionContract{exchange_id=E, token_id=A, quant=X, expected=1}` immediately before it, shifting the ratio unfavorably (e.g., buying A with B to inflate `secondTokenBalance` relative to `firstTokenBalance`), then submits the reverse trade immediately after the inject transaction is mined.
4. Because `ExchangeInjectContract` has no `expected`/minimum field (confirmed absent in the protobuf definition and in `doValidate()`), the creator's inject transaction executes at the manipulated ratio in `execute()` (`ExchangeInjectActuator.java:71-83`), locking in a worse-than-expected amount of token B contributed, while the attacker profits from the round-trip trades — with no on-chain check available to prevent it.
