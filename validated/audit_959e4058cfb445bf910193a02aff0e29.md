### Title
Unauthenticated `RescueFundsOnSourceChain` event lets any user attach a mismatched-asset `RESCUE_FUNDS` outbound to another user's stuck UTX, corrupting token mapping and blocking legitimate rescue - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
The external report is about `PoolFactory.sol`'s `Sweep` letting anyone withdraw CPOOL that is reserved for user claims, both stealing accrued rewards and permanently blocking the intended claimant. The Push Chain analog is `Keeper.AttachRescueOutboundFromReceipt` in `x/uexecutor/keeper/create_outbound.go`, which reacts to a `RescueFundsOnSourceChain` event that **any unprivileged user can emit** on the source chain, and attaches a `RESCUE_FUNDS` outbound to someone else's stuck `UniversalTx` without verifying that the caller is entitled to it or that the supplied token matches the original locked asset. [1](#0-0) 

### Finding Description
`AttachRescueOutboundFromReceipt` is documented as reacting to a user-initiated event ("emitted by `UniversalGatewayPC` when a user initiates a rescue on the source chain") and decodes `event.Sender`, `event.PRC20`, `event.GasFee`, `event.GasPrice`, `event.GasLimit` straight from attacker-controlled log data. [2](#0-1) 

The function only checks the *state* of the target UTX (CEA deposit failed, or non-CEA inbound-revert reverted) — it never checks that `event.Sender` is the original inbound's `Sender`/`RevertInstructions.FundRecipient`, and never checks that `event.PRC20` corresponds to the PRC20/asset that was originally locked for that UTX: [3](#0-2) 

It then resolves the outbound's external asset purely from the attacker-supplied `event.PRC20`: [4](#0-3) 

and builds the outbound by mixing the attacker-chosen token config (`tokenCfg.Address`, `event.PRC20`) with the **original UTX's stored amount** (`originalUtx.InboundTx.Amount`), while recipient is fixed to the original depositor: [5](#0-4) 

Because `Amount` comes from the original locked deposit but `ExternalAssetAddr`/`Prc20AssetAddr` come from an attacker-chosen (but validly-registered) token for the same source chain, the resulting `RESCUE_FUNDS` outbound carries mismatched token/amount semantics — TSS will ultimately be asked to sign and broadcast an outbound instructing the source-chain gateway to release `Amount` units of a token that was never actually locked in that amount (or at all) for this UTX.

In addition, the duplicate-rescue guard is keyed only on the UTX, not on the caller: [6](#0-5) 
Any unprivileged attacker can therefore front-run the legitimate victim's rescue attempt by emitting the event first with a bogus/mismatched `PRC20`, planting a `PENDING` `RESCUE_FUNDS` outbound on the victim's UTX. Until Universal Validators vote it to `REVERTED` (which likely happens only after the malformed request fails on-chain), the legitimate rescue is blocked — this is the direct analog of the reported "Sweep... block[s] the possibility of claiming by users."

### Impact Explanation
- **Corruption of token mapping / wrong asset semantics**: an unprivileged attacker can force a `RESCUE_FUNDS` outbound whose `ExternalAssetAddr`/`Prc20AssetAddr` do not correspond to the token/amount actually locked for the UTX, corrupting canonical `UniversalTx` state and, if it reaches TSS signing/broadcast, causing the destination-chain gateway to be instructed with incorrect asset/amount data.
- **Permanent freezing / griefing of user funds**: because the pending-rescue guard is per-UTX (not per-caller), an attacker can plant a malformed rescue for any other user's stuck UTX, blocking the legitimate owner's rescue attempt until validators resolve the bogus one — directly analogous to the CPOOL sweep blocking legitimate claims.
- No signature/ownership check ties `event.Sender` to the UTX's original depositor, so this is reachable by any unprivileged actor who can call the gateway's rescue entry point on the source chain, satisfying the "unprivileged external attacker" scope.

### Likelihood Explanation
High reachability: the trigger is a user-callable event on the (external) `UniversalGatewayPC` contract, and the Push Chain keeper code processes any such log without validating sender identity or token/amount consistency against the original locked deposit. Any Push Chain user (or a bot watching for stuck UTXs, which are visible on-chain via `PendingInbounds`/UTX queries) can exploit this without special privileges.

### Recommendation
- Bind `event.Sender` to `originalUtx.InboundTx.Sender` (or `RevertInstructions.FundRecipient`) before accepting a rescue, rejecting mismatches.
- Validate that `event.PRC20` matches the PRC20/native representation actually associated with `originalUtx.InboundTx.AssetAddr` for that source chain, instead of independently resolving any valid token config from `event.PRC20`.
- Consider keying the duplicate-rescue guard (or an additional cooldown/allowlist) so that only the legitimate owner (or protocol admin) can supersede or retry rescue requests for a given UTX.

### Proof of Concept
1. Wait for (or induce) a UTX to become rescue-eligible (CEA deposit failed, or non-CEA inbound-revert `REVERTED`) — this state is publicly observable via UTX queries.
2. As an unrelated unprivileged user, call the source-chain gateway's rescue-funds entry point supplying that UTX's `universalTxId` but an arbitrary `PRC20` address that is registered as some *other* token's PRC20 for the same source chain (`event.PRC20 != original PRC20`).
3. When the corresponding `RescueFundsOnSourceChain` log is processed by `AttachRescueOutboundFromReceipt`, the keeper accepts it (state checks pass), resolves `tokenCfg` from the attacker-chosen `event.PRC20`, and attaches a `PENDING` `RESCUE_FUNDS` outbound to the victim's UTX carrying `ExternalAssetAddr = tokenCfg.Address` (wrong token) but `Amount = originalUtx.InboundTx.Amount` (original amount) — mismatched asset/amount now sit in canonical on-chain state, and the victim's own legitimate rescue is blocked by the "already has an active rescue outbound" guard until validators resolve the bogus one.

// RescueFundsOnSourceChainEvent holds decoded data from the RescueFundsOnSourceChain
// event emitted by UniversalGatewayPC when a user initiates a rescue on the source chain.
type RescueFundsOnSourceChainEvent struct {
	UniversalTxId  string   // 0x-prefixed bytes32 — the original UTX whose funds are stuck
	PRC20          string   // 0x-prefixed address — PRC20 token whose counterpart is locked
	ChainNamespace string   // source chain namespace (e.g. "eip155")
	Sender         string   // 0x-prefixed address — user who initiated the rescue
	TxType         TxType   // always TxType_RESCUE_FUNDS
	GasFee         *big.Int // gas fee charged (in gas-token units)
	GasPrice       *big.Int // gas price on the source chain
	GasLimit       *big.Int // gas limit used for the rescue execution
}
