**Analysis:**

The premise of the exploit question is incorrect. `InMemoryEventAccumulator` (a type alias for `InMemoryAccumulator<EventAccumulatorHasher>`) is an append-only Merkle accumulator, not a set or map — it never deduplicates leaves based on their hash values. Its `from_leaves`/`append`/`append_one` logic tracks leaves purely by **position** in the frozen-subtree structure, using the leaf count (`num_leaves`) to decide how many trailing carries to perform when merging subtree roots: [1](#0-0) [2](#0-1) 

Because the merge logic depends solely on `num_existing_leaves` (an integer counter) and the sequence of pushed hashes — never on hash value equality or a lookup structure — appending N identical leaf hashes produces a structurally different (and thus differently-valued) root than N-1 or N+1 identical leaf hashes. There is no code path anywhere in `append_one` that checks for or collapses duplicate hash values; two leaves with the same `HashValue` are simply pushed twice and participate independently in the pairwise `MerkleTreeInternalNode` hashing based on their position. This is the same design as Bitcoin/GitHub-style Merkle mountain ranges — duplicate leaf *content* is completely orthogonal to the *count-sensitivity* of the root, which is driven by the append-count/position logic, not content uniqueness.

`ContractEventV2` (constructed via `create_event_v2`/`ContractEvent::new_v2`) indeed carries only `type_tag` and `event_data`, with no `key` or `sequence_number`, unlike `ContractEventV1`: [3](#0-2) [4](#0-3) 

This means two identical V2 events emitted in the same transaction will indeed hash to the same `HashValue` (since `CryptoHash::hash` on a `ContractEvent::V2` is derived from BCS-serializing the whole struct via `BCSCryptoHash`). However, this only means the two leaves happen to have equal *values*; it does not cause them to collapse into one leaf in the accumulator. The event root hash computation at the executor/storage boundary (`do_ledger_update.rs`) and the verification path (`ensure_match_transaction_info`, `TransactionOutputListWithProofV2::verify` / `verify_events_against_root_hash`, and `TransactionWithProof::verify`) all recompute the accumulator identically from the ordered event vector, so the number and order of events is always faithfully reflected in `event_root_hash`: [5](#0-4) [6](#0-5) [7](#0-6) 

Since both the committing side (executor) and the verifying side (proof verification, `TransactionWithProof::verify`, `ensure_match_transaction_info`) use the exact same deterministic `from_leaves(events.iter().map(CryptoHash::hash))` construction over the *actual* ordered event vector (not a deduplicated set), duplicate identical V2 events do not corrupt the count or ordering represented by `event_root_hash`, nor do they enable any proof forgery: an attacker emitting N identical events will get a root that differs from N±1 identical events, and any honest node recomputing the root from the correct event list will match the committed `TransactionInfo.event_root_hash`. There is no dedup logic in the accumulator to exploit, and the absence of `key`/`sequence_number` on `ContractEventV2` is an intentional design choice for module events (which do not need per-account/per-handle sequencing) rather than a defect that affects proof binding.

    /// Appends one leaf. This will update `frozen_subtree_roots` to store new frozen root nodes
    /// and remove old nodes if they are now part of a larger frozen subtree.
    fn append_one(
        frozen_subtree_roots: &mut Vec<HashValue>,
        num_existing_leaves: LeafCount,
        leaf: HashValue,
    ) {
        // For example, this accumulator originally had N = 7 leaves. Appending a leaf is like
        // adding one to this number N: 0b0111 + 1 = 0b1000. Every time we carry a bit to the left
        // we merge the rightmost two subtrees and compute their parent.
        // ```text
        //       A
        //     /   \
        //    /     \
        //   o       o       B
        //  / \     / \     / \
        // o   o   o   o   o   o   o
        // ```

        // First just append the leaf.
        frozen_subtree_roots.push(leaf);

        // Next, merge the last two subtrees into one. If `num_existing_leaves` has N trailing
        // ones, the carry will happen N times.
        let num_trailing_ones = (!num_existing_leaves).trailing_zeros();

        for _i in 0..num_trailing_ones {
            let right_hash = frozen_subtree_roots.pop().expect("Invalid accumulator.");
            let left_hash = frozen_subtree_roots.pop().expect("Invalid accumulator.");
            let parent_hash = MerkleTreeInternalNode::<H>::new(left_hash, right_hash).hash();
            frozen_subtree_roots.push(parent_hash);
        }

/// Verifies a list of events against an expected event root hash. This is done
/// by calculating the hash of the events using an event accumulator hasher.
fn verify_events_against_root_hash(
    events: &[ContractEvent],
    transaction_info: &TransactionInfo,
) -> Result<()> {
    let event_hashes: Vec<_> = events.iter().map(CryptoHash::hash).collect();
    let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash();
    ensure!(
        event_root_hash == transaction_info.event_root_hash(),
        "The event root hash calculated doesn't match that carried on the \
                         transaction info! Calculated hash {:?}, transaction info hash {:?}",
        event_root_hash,
        transaction_info.event_root_hash()
    );
    Ok(())
}
