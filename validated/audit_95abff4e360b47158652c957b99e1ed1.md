### Title
Unbounded growth of `DelegatedResourceAccountIndexStore` per-address index enables cheap RPC DoS via `GetDelegatedResourceAccountIndexV2` - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegateResourceActuator.execute` calls `DelegatedResourceAccountIndexStore.delegateV2`, which unconditionally writes a new `(V2_FROM_PREFIX, from, to)` and `(V2_TO_PREFIX, to, from)` key-value pair for every distinct `(owner, receiver)` pair, with no limit on how many distinct pairs an address can accumulate. An attacker who creates many fresh receiver accounts and delegates the minimum 1 TRX of bandwidth/energy to each grows their own and each receiver's index unbounded, and any later call to `getV2Index`/`getWithPrefix` (used by `GetDelegatedResourceAccountIndexV2` RPC/HTTP) must prefix-scan and sort the full list for that address, so latency/response size scale linearly with attacker-created state.

### Finding Description
`DelegateResourceActuator.validate()` only enforces that `delegateBalance >= TRX_PRECISION` (1 TRX) and that the owner has enough frozen V2 balance to cover it; it does not cap the number of distinct receiver addresses an owner may delegate to, nor the number of distinct delegators a receiver may accumulate. [1](#0-0) 

Each successful delegation call reaches `delegateResource`, which calls `DelegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, ...)` for that unique pair. [2](#0-1) 

`delegateV2` always writes new keys `V2_FROM_PREFIX+from+to` and `V2_TO_PREFIX+to+from` — there is no dedup limit, no maximum list size, and no fee scaled to the number of existing entries. [3](#0-2) 

`getV2Index`/`getWithPrefix` performs a `prefixQuery` over all entries for the queried address, sorts them by timestamp, and materializes the full from/to lists — cost grows linearly (or worse) with the number of distinct pairs. [4](#0-3) 

This is exposed to any unauthenticated caller via the `GetDelegatedResourceAccountIndexV2` HTTP servlet, which simply forwards to `wallet.getDelegatedResourceAccountIndexV2(address)` and serializes the (unbounded) result — the servlet only extends `RateLimiterServlet` (a per-request rate limiter), which does not bound the size of data returned per request. [5](#0-4) 

None of the existing protections (`validateSignature`, `DecodeUtil.addressValid`, actuator `validate()`, fork gates, bandwidth/energy accounting) limit the *count* of distinct delegation relationships — they only validate individual transaction fields and the owner's available frozen balance for that single call.

### Impact Explanation
This is a state-growth / RPC-cost amplification issue rather than a critical asset-loss bug. Impact is scoped to degraded performance (increased latency, memory, and response payload size) of `GetDelegatedResourceAccountIndexV2` (gRPC/HTTP/Solidity/PBFT variants) for the targeted address, and to on-disk growth of `DelegatedResourceAccountIndex` store entries, which persists in state (subject to `TronStoreWithRevoking`) and cannot be trivially reversed by the victim. This corresponds to a "DoS via protocol implementation / RPC-API" class finding, but is low severity since it does not crash nodes, corrupt consensus, or steal funds — it only degrades a specific read API's performance proportional to attacker-created entries.

### Likelihood Explanation
Each distinct delegation requires: (1) the attacker to control frozen V2 balance (bandwidth or energy) of at least 1 TRX per unique receiver, permanently locked out of use until unfrozen via `UnDelegateResourceContract`/unfreeze flow; (2) the receiver address to be an existing, non-contract account (`accountStore.get(receiverAddress) != null` and `getType() != AccountType.Contract`), which the actuator's `validate()` checks — meaning the attacker must first create (activate) each receiver account, incurring the standard account-creation cost. This makes the attack economically nontrivial per entry but still linear and cheap for an attacker with moderate capital (e.g., thousands of TRX can create thousands of distinct entries), and fully repeatable since there is no cap or increasing cost per additional entry.

### Recommendation
- Introduce a maximum number of distinct `(from,to)` index entries per address (either enforced in `DelegateResourceActuator.validate()` or in `delegateV2`), rejecting new delegations once the cap is reached, or
- Change the RPC/HTTP layer (`getDelegatedResourceAccountIndexV2` / `getV2Index`) to support pagination instead of returning the full unbounded list in one response, and
- Consider scaling the bandwidth/fee cost of `DelegateResourceContract` with the current size of the owner's/receiver's existing index to disincentivize index-spam.

### Proof of Concept
Extend `DelegatedResourceAccountIndexStoreTest`/`DelegateResourceActuatorTest` pattern:
```java
@Test
public void testUnboundedIndexGrowth() {
  freezeBandwidthForOwner(); // owner freezes enough V2 bandwidth balance
  int N = 5000;
  for (int i = 0; i < N; i++) {
    ECKey ecKey = new ECKey(Utils.getRandom());
    byte[] receiver = ecKey.getAddress();
    // create & activate receiver account (real cost paid by attacker)
    AccountCapsule receiverCapsule = new AccountCapsule(
        ByteString.copyFromUtf8("r" + i), ByteString.copyFrom(receiver),
        AccountType.Normal, 0L);
    dbManager.getAccountStore().put(receiver, receiverCapsule);

    DelegateResourceActuator actuator = new DelegateResourceActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(
        getDelegateContractForBandwidth(OWNER_ADDRESS,
            ByteArray.toHexString(receiver), 1_000_000L)); // 1 TRX min
    TransactionResultCapsule ret = new TransactionResultCapsule();
    actuator.validate();
    actuator.execute(ret);
  }
  long start = System.currentTimeMillis();
  DelegatedResourceAccountIndexCapsule idx = dbManager
      .getDelegatedResourceAccountIndexStore()
      .getV2Index(ByteArray.fromHexString(OWNER_ADDRESS));
  long elapsed = System.currentTimeMillis() - start;
  Assert.assertEquals(N, idx.getToAccountsList().size());
  // measured elapsed time/response size grows with N, demonstrating
  // unbounded cost for GetDelegatedResourceAccountIndexV2 callers
}
```
Expected result: `idx.getToAccountsList().size()` equals `N` with no upper bound enforced, and query latency/response size for `GetDelegatedResourceAccountIndexV2(OWNER_ADDRESS)` grows linearly with `N`, confirming the unbounded-growth DoS vector.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

@Component
@Slf4j(topic = "API")
public class GetDelegatedResourceAccountIndexV2Servlet extends RateLimiterServlet {

  private static final  String VALUE_FIELD_NAME = "value";

  @Autowired
  private Wallet wallet;

  protected void doGet(HttpServletRequest request, HttpServletResponse response) {
    try {
      boolean visible = Util.getVisible(request);
      String address = request.getParameter(VALUE_FIELD_NAME);
      if (visible) {
        address = Util.getHexAddress(address);
      }
      fillResponse(ByteString.copyFrom(ByteArray.fromHexString(address)), visible, response);
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    try {
      PostParams params = PostParams.getPostParams(request);
      boolean visible = params.isVisible();
      String input = params.getParams();
      if (visible) {
        JSONObject jsonObject = JSONObject.parseObject(input);
        String value = jsonObject.getString(VALUE_FIELD_NAME);
        jsonObject.put(VALUE_FIELD_NAME, Util.getHexAddress(value));
        input = jsonObject.toJSONString();
      }

      BytesMessage.Builder build = BytesMessage.newBuilder();
      JsonFormat.merge(input, build, visible);

      fillResponse(build.getValue(), visible, response);
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  private void fillResponse(ByteString address, boolean visible, HttpServletResponse response)
      throws IOException {
    DelegatedResourceAccountIndex reply =
        wallet.getDelegatedResourceAccountIndexV2(address);
    if (reply != null) {
      response.getWriter().println(JsonFormat.printToString(reply, visible));
    } else {
      response.getWriter().println("{}");
    }
  }
