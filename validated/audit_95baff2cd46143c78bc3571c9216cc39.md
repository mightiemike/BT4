## Title
Reorg-permission decision in `check_parent_tenure_choice` depends on each signer's local timestamps, letting the signer set split on whether a reorg is valid - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg a prior tenure's block(s) by comparing `sortition_state_received_time` (this signer's local wall-clock time when it received the new sortition) against `local_block_info.approved_time` (this signer's local wall-clock time when it approved the reorged tenure's first block), then testing the elapsed duration against `first_proposal_burn_block_timing`. Both timestamps are locally observed, not derived from any canonical, network-agreed value, so different signers evaluating the exact same reorg attempt can reach different `Ok(true)`/`Ok(false)` verdicts.

### Finding Description

`sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` — the time *this particular signer's node* observed the burn block — and `local_block_info.approved_time` is the time *this particular signer* locally approved the earlier block. Neither value is part of consensus state; they are per-signer, per-process observations subject to normal network/propagation jitter, clock differences, and node restart/backfill behavior (the comment even says "this value *should* always be some, but try to do the best we can if it isn't", acknowledging that it can be `None` on some signers and present on others).

Because the decision of whether `proposal_to_sortition < first_proposal_burn_block_timing` is evaluated independently per signer using these non-synchronized local values, two honest, non-colluding signers can compute different booleans for the same tenure/sortition pair: one signer's local receive/approve timestamps might land just inside the timing window (reorg permitted, `Ok(true)` → block signable) while another signer's timestamps land just outside it (reorg refused, `Ok(false)` → block rejected). This directly breaks the intended invariant that "is this reorg valid" is a deterministic, network-wide predicate — the equality/threshold check here is over each node's private clock rather than a value all signers agree on.

### Impact Explanation
If enough signer weight disagrees on whether the reorg is permitted, the signer set can split: some signers globally accept the reorging tenure-change block, others reject it. This produces a temporary tip disagreement between signers/miners (some clients see the reorg block as canonical, others do not) until enough weight converges one way, which matches the "temporary tip disagreement" / minority-triggerable static-validation divergence category. It is not attacker-controlled in the classic sense — it can arise from pure network latency/jitter or a signer restarting and losing its `approved_time`/`get_burn_block_receive_time` records — but a miner racing a tenure-change proposal right at the edge of `first_proposal_burn_block_timing` can amplify the effect and make this divergence minority-triggerable without needing majority collusion.

### Likelihood Explanation
Requires: (1) an actual reorg situation (a miner not building on the prior sortition, which happens during flash blocks/late block-founds — not exotic), and (2) the elapsed time between the reorged tenure's first-block approval and the new sortition's receipt landing close to the `first_proposal_burn_block_timing` boundary as measured independently by different signer nodes. This is plausible under ordinary network conditions (propagation delay variance, signer restarts wiping `approved_time`), making it a realistic, low-cost-to-trigger (even accidental) condition rather than a theoretical one. It does not require majority signer collusion — a single miner racing the timing window can cause divergent verdicts among honest signers.

### Recommendation
Base the reorg-timing decision on a value that is derived from canonical/consensus data (e.g., burn-block timestamps recorded in the sortition DB, or block timestamps embedded in the chain) rather than each signer's local wall-clock receipt/approval times. If local timing must be used as a heuristic, add hysteresis/agreement logic (e.g., require the decision to be stable across a window, or fall back to a canonical timestamp source) so that all correctly-functioning signers converge to the same boolean for the same reorg attempt.

### Proof of Concept
1. Set up two signers, A and B, both observing the same burn chain and same miner activity.
2. Arrange for a miner to submit a tenure-change block that reorgs a prior tenure whose first (and only) block was proposed such that the gap to the next sortition is very close to `first_proposal_burn_block_timing` (e.g., within milliseconds of the threshold).
3. Due to normal network jitter, signer A records `local_block_info.approved_time` slightly earlier (so `proposal_to_sortition` computed by A is `< first_proposal_burn_block_timing`, permitting the reorg) while signer B's local timestamps yield `proposal_to_sortition >= first_proposal_burn_block_timing` (refusing the reorg).
4. Signer A signs/accepts the reorging block; signer B rejects it as `ReorgNotAllowed` — producing a split verdict across the signer set for the identical on-chain event, i.e., a temporary tip disagreement.

This could not be more precisely confirmed without running the actual signer test harness (e.g., `stacks-signer/src/chainstate/tests/v2.rs`'s `check_parent_tenure_choice_reorg_timing_*` tests) under controlled clock skew, which was outside the scope of static code review here.
