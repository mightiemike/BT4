## Analysis

The CVE describes a NULL-pointer dereference caused by using a value without validating it first (GPAC's `gf_isom_get_original_format_type` deref'd without a null check). The closest reachable analog in this nearcore codebase is a `.unwrap()` on a `Result` that can legitimately be `Err` for protocol-generated receipts that outlive several resharding events, causing a **chunk-application panic** (a transaction/receipt-triggered node halt) rather than a graceful rejection. ### Title
Unchecked `Result::unwrap()` on `receiver_shard_id()` in `receipt_filter_fn` can panic the runtime when a delayed `GlobalContractDistribution` receipt outlives its resolvable resharding history - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437`) explicitly returns `Err(EpochError::ShardingError(...))` for a `GlobalContractDistribution` receipt whose `target_shard` cannot be resolved to a shard in the current layout or its split history via `resolve_to_current_shard`. The delayed-receipt queue's filter, `receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:874`, discards this `Result` and calls `.unwrap()` directly on it, turning a designed, recoverable error path into an unconditional panic during chunk application.

### Finding Description
`receipt_filter_fn` is invoked from `DelayedReceiptQueueWrapper::pop` (`runtime/runtime/src/congestion_control.rs:880-909`) every time a delayed receipt is popped off the queue while applying a chunk:
```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```
`receiver_shard_id` was written to *tolerate* stale `target_shard` values by walking split history via `shard_layout.resolve_to_current_shard(target_shard)`, but if that lookup fails (e.g., because the receipt has been delayed across more resharding generations, or split-history bookkeeping doesn't stretch back far enough) it returns `Err`, which `receipt_filter_fn` immediately unwraps into a panic.

A user-triggered `DeployGlobalContractAction` produces a `GlobalContractDistribution` receipt targeted at specific shards. If this receipt is congestion-delayed (placed into the delayed-receipt queue) and enough resharding events occur before it is dequeued, popping it during a later chunk application panics the applying node instead of gracefully failing/skipping the receipt.

The test at `test-loop-tests/src/tests/global_contracts_distribution.rs:163-187` documents this exact code path and asserts that chain progress continues past the point the panic would occur — but the underlying `.unwrap()` remains present in `receipt_filter_fn`, so any resharding topology this specific test does not exercise (e.g., a third or later resharding generation, or any other case `resolve_to_current_shard` cannot walk) reaches the same unwrap and halts the node.

### Impact Explanation
A panic inside `receipt_filter_fn`, called from `apply()`'s receipt-processing path, aborts chunk application on every node that processes that shard/chunk (validators and any tracking node), producing a deterministic, receipt-triggered denial of service / chain-halt for the affected shard — analogous in class and severity to the CVE's crash-inducing null dereference, but reachable purely from ordinary user action (deploying a global contract) combined with the network's own resharding schedule, with no attacker privilege required beyond submitting a normal transaction.

### Likelihood Explanation
Exploitability depends on getting a `GlobalContractDistribution` receipt delayed across enough resharding events that `resolve_to_current_shard` cannot trace it back — congestion delay is attacker-influenceable (user can create/aggravate congestion to keep the receipt queued), and resharding cadence is a protocol-level, predictable schedule, so a patient/well-resourced actor deploying global contracts during high congestion around resharding boundaries can increase the odds of hitting this path, though it is not trivially one-shot.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with proper error propagation (return the `Result`/`RuntimeError` from `pop`) so an unresolvable `target_shard` is handled as a `StorageError`/`RuntimeError` (consistent with how other panics-vs-errors decisions are made elsewhere in this file, e.g. `IntegerOverflowError` handling in `pop`), rather than an unconditional panic; additionally, harden `resolve_to_current_shard` / split-history bookkeeping so multi-generation resharding always resolves stale `target_shard` values.

### Proof of Concept
1. Submit a transaction with `DeployGlobalContractAction`, generating an outgoing `GlobalContractDistribution` receipt targeted at a specific shard.
2. Induce congestion (or otherwise ensure the receipt is buffered/delayed) so it sits in the delayed-receipt queue.
3. Trigger multiple resharding events (as exercised in `global_contracts_distribution.rs`, splitting shards repeatedly) such that the receipt's original `target_shard` is no longer resolvable by `resolve_to_current_shard`.
4. Let the delayed queue drain; `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, which calls `receiver_shard_id(&shard_layout).unwrap()`; when resolution fails, this panics and halts chunk application on the shard.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }
