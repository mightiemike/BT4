### Title
Self-trade against own resting order causes maker-side asset/balance credit to be silently lost due to stale in-memory `AccountCapsule` overwrite - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder` credits the taker via the single `AccountCapsule` instance loaded in `execute()`, but credits the maker via a second, independently fetched `AccountCapsule` obtained fresh from `accountStore` inside `addTrxOrToken(MarketOrderCapsule, long)`. When a maker order and the matching taker order share the same owner address (self-trade, which `validate()` never forbids), the maker-side credit written by `addTrxOrToken` is subsequently clobbered by the stale taker copy written at `execute()` line 148, causing the credited token/TRX amount to disappear from on-disk state.

### Finding Description
In `execute()`, a single `AccountCapsule accountCapsule` is loaded once at [1](#0-0) , mutated in place through fee deduction, `transferBalanceOrToken`, and matching, and finally persisted with `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` at [2](#0-1) .

Inside `matchSingleOrder`, the taker credit uses this same shared `takerAccountCapsule` reference, so it is properly reflected in the final write. However the maker credit is applied via the overloaded `addTrxOrToken(MarketOrderCapsule orderCapsule, long num)` which independently loads the maker's account fresh from the store, mutates it, and writes it back immediately: [3](#0-2) .

If the maker order's owner address equals the taker order's owner address (self-trade), both `addTrxOrToken` calls target the same underlying account key, but operate on two different in-memory `AccountCapsule` objects: [4](#0-3) . The maker-side `accountStore.put` inside `addTrxOrToken` happens mid-execution, but the taker's stale in-memory `accountCapsule` (which lacks the maker credit) is written afterward at line 148, overwriting and discarding the maker credit. `validate()` performs no check that the maker's resting order owner differs from the taker's owner address [5](#0-4) , so this collision is fully reachable by any unprivileged account.

### Impact Explanation
This is an accounting/state-corruption bug (`VALUE_CONSERVATION` violation), not a fund-theft vector against third parties: because the sell-side deduction already occurred via `transferBalanceOrToken` (persisted through the shared taker object) while the corresponding maker-side "buy-back" credit for the same token/address is discarded, the net effect is loss/burn of the account owner's own tokens rather than duplication or theft of another party's funds. It matches the "asset/accounting corruption" bounty impact class, though the practical consequence is self-inflicted value destruction for whichever address performs the self-trade, and additional resting-order updates (`orderStore.put` at line 486) proceed as if the credit succeeded, leaving order-book and account state inconsistent.

### Likelihood Explanation
Trivially reachable: any unprivileged account can place a maker sell order, let it rest in the book, then broadcast a second (taker) sell order from the same address that price-matches it. No privileged role, signature bypass, or victim collusion is required — the precondition is simply the same address acting as both maker and taker, which `validate()` does not forbid. The only cost is the two transactions' standard TRC fees (`getMarketSellFee()`), making this fully repeatable at will.

### Recommendation
In `matchSingleOrder`/`addTrxOrToken`, avoid re-fetching the maker's account from the store when its address matches the taker's account already held in memory; instead, detect `Arrays.equals(makerOrderCapsule.getOwnerAddress(), takerAccountCapsule.getAddress().toByteArray())` and apply the maker credit to the same in-memory `AccountCapsule` object used for the taker, or persist/reload consistently (e.g., load once per unique address per transaction and write once at the end) to guarantee no intermediate write is later overwritten by a stale copy.
