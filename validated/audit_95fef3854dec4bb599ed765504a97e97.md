### Title
Vote reward withdrawal via TVM native contract can silently pay zero/incorrect reward if witness Vi accumulator is not yet populated for a cycle - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
`VoteRewardUtil.computeReward()` (used by the TVM `vote`/`withdrawReward`/`queryReward` native contracts) unconditionally reads witness "Vi" reward accumulator values from `DelegationStore.getWitnessVi()` for any `beginCycle`/`endCycle` pair, without ever checking whether the Vi backfill/accumulation for those cycles has actually completed. This is structurally the same defect class as the ZcToken bug: a state variable (here, per-cycle `Vi`) that legitimately defaults to `0`/`BigInteger.ZERO` when unset is consumed directly in a reward-delta calculation, so if it is queried before it has been populated, the multiplication/subtraction silently yields `0` (or an understated value) instead of erroring or falling back to a safe recomputation.

### Finding Description
`DelegationStore.getWitnessVi()` and `RewardViCalService.getWitnessVi()` both return `BigInteger.ZERO` when no value has been stored for a given `(cycle, address)` key: [1](#0-0) 

The account-based reward path in `MortgageService.computeReward()` is aware that Vi data for cycles before `NewRewardAlgorithmEffectiveCycle` may not yet be backfilled, and explicitly routes those cycles through `RewardViCalService.getNewRewardAlgorithmReward()`, which blocks on a `CountDownLatch` (`lock.await()`) until the asynchronous backfill (`startRewardCal()`/`isDone()`) has completed: [2](#0-1) [3](#0-2) 

However, `VoteRewardUtil.computeReward()` — the analog used by the TVM native "vote" precompile/opcode path (`WithdrawRewardProcessor`, `VoteWitnessProcessor`, `Program.withdrawRewardAndCancelVote`) — reads `repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress)` and `getWitnessVi(endCycle - 1, srAddress)` directly, with no equivalent `isDone()`/blocking/fallback check and no branch distinguishing "old" pre-backfill cycles from "new" cycles: [4](#0-3) 

If `deltaVi.signum() <= 0` (which is exactly what happens when Vi for the relevant cycle boundary has not yet been written, since the missing key defaults to `BigInteger.ZERO`), the loop just `continue`s and contributes `0` to `reward` for that SR vote — functionally identical to `ZcToken.previewWithdraw` returning `0` when `maturityRate` is still unset.

Critically, `VoteRewardUtil.withdrawReward()` then commits state that advances the cycle window regardless of whether the computed reward was correct: [5](#0-4) 

This is worse than the original Swivel finding: whereas Bob could retry `ZcToken.withdraw` after `maturityRate` was properly set and get the correct amount, here `repository.updateBeginCycle`/`updateEndCycle`/`updateAccountVote` permanently move the account's reward cursor past the affected cycles, so any reward attributable to a cycle whose Vi was still `0` at query time is **permanently lost** — it can never be recovered on a subsequent call, since `beginCycle` has already been advanced past it.

### Impact Explanation
This affects TVM-vote-enabled smart contracts (any contract using the `vote`/`withdrawReward`/`freeze`-with-vote native opcodes once `allowTvmVote` is active) calling `withdrawReward`/`queryReward` through `WithdrawRewardProcessor`/`VoteRewardUtil`. If the relevant per-cycle Vi accumulator has not yet been written for a cycle boundary the contract is withdrawing across (e.g., right around/after the new reward algorithm's effective cycle while `RewardViCalService`'s background backfill job has not finished, or any other scenario in which `getWitnessVi` is queried for a cycle whose accumulation hasn't landed), the contract's reward is computed as `0` (or understated) and that reward is irrecoverably forfeited because the begin/end cycle cursors are advanced past it. This is an accounting-corruption / value-loss bug reachable from an ordinary contract call, not merely a UX inconvenience.

### Likelihood Explanation
Likelihood depends on the timing window where `VoteRewardUtil`'s Vi reads race ahead of Vi being written for the queried cycle range (analogous to querying `maturityRate` right at/after the deadline before it's set). Because `VoteRewardUtil` has no equivalent of the `isDone()`/lock-await guard that `MortgageService`/`RewardViCalService` use for the same underlying data, and no gating on `NewRewardAlgorithmEffectiveCycle`, any TVM vote-reward withdrawal whose cycle window touches not-yet-populated Vi entries is affected — this can be triggered by an ordinary, unprivileged transaction/contract call with no special permissions, at any time such a window exists.

### Recommendation
Make `VoteRewardUtil.computeReward()` consistent with `MortgageService.computeReward()`/`RewardViCalService`: before consuming `getWitnessVi()` for a cycle range, verify (or block on) the same completeness guarantee used by `RewardViCalService.isDone()`/`lock.await()`, and split the reward computation for cycles before `NewRewardAlgorithmEffectiveCycle` from the newer, always-synchronously-populated cycles the same way `MortgageService` does. Do not advance `beginCycle`/`endCycle` (i.e., do not finalize/forfeit the reward window) for any cycle range whose Vi data cannot yet be proven complete.

### Proof of Concept
1. Enable `allowChangeDelegation`/`useNewRewardAlgorithm` and `allowTvmVote` via governance proposals.
2. Deploy a contract that freezes balance and votes for a witness, then calls the TVM `withdrawReward` opcode (routed to `WithdrawRewardProcessor.execute` → `VoteRewardUtil.withdrawReward`) for a cycle range whose `Vi` value for `endCycle - 1` (or `beginCycle - 1`) has not yet been written to `rewardViStore`/`DelegationStore` (e.g., immediately following an upgrade, before `RewardViCalService.startRewardCal()` finishes, or any cycle for which the synchronous `MaintenanceManager.doMaintenance()` Vi write for that specific cycle has not yet occurred for the queried boundary).
3. Observe `VoteRewardUtil.computeReward()` at [6](#0-5)  compute `deltaVi <= 0` (because the missing key defaults to `BigInteger.ZERO`) and skip the reward contribution, returning `0`/understated reward.
4. Observe that `repository.updateBeginCycle`/`updateEndCycle` at lines 52-54 have already advanced the cursor, so calling `withdrawReward` again afterward (once Vi is correctly populated) does not recover the lost reward for the skipped cycle.

      if (account != null) {

      }

    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;

      beginCycle += 1;

      repository.updateBeginCycle(address, endCycle + 1);
      return;

      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
