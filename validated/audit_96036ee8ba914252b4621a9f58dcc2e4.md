## Analysis

CVE-2019-20631 is a crash caused by a helper function (`gf_list_count`) dereferencing an invalid/stale pointer that no longer accurately reflects the state of the underlying structure, triggered by a malformed but externally supplied input. The closest reachable analog in nearcore is a `.unwrap()`-triggered panic in the delayed-receipt processing path when a `GlobalContractDistribution` receipt's stale `target_shard` cannot be resolved into the current shard layout after the shard structure has changed (resharding) more than once — a stale-reference-resolution failure that panics instead of erroring gracefully, exactly analogous to a stale/invalid reference crashing a counting/lookup routine.

### Title
Transaction-triggered node panic via unresolvable stale `target_shard` in delayed `GlobalContractDistribution` receipts across repeated static resharding - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the result of `Receipt::receiver_shard_id`, which can return `Err` when a `GlobalContractDistribution` receipt's `target_shard` cannot be resolved to any shard in the current layout or its split history.

### Finding Description
Every popped delayed receipt is checked against `receipt_filter_fn`, which computes the receiver's shard id and `.unwrap()`s it: [1](#0-0) 

`receiver_shard_id` for `GlobalContractDistribution` receipts resolves an out-of-layout `target_shard` via `ShardLayout::resolve_to_current_shard`, returning `Err(EpochError::ShardingError(...))` if the shard cannot be found "in the shard layout or its split history": [2](#0-1) 

Whether resolution succeeds depends on how much split history the shard layout carries. `ShardLayoutV3` (used only under dynamic resharding) stores a *cumulative* split map and can walk arbitrarily many generations back: [3](#0-2) 

But `ShardLayout::resolve_to_current_shard` for `V0`/`V1`/`V2` (the layouts used for static/protocol-version-driven resharding) only tracks a **single generation** via `get_children_shards_ids`: [4](#0-3) 

The codebase itself documents that this is a known limitation, explicitly noting the fix depends on the V3 dynamic-resharding split-history mechanism and does not extend to static resharding: [5](#0-4) 

A `GlobalContractDistribution` receipt is created whenever any account submits a `DeployGlobalContract` action — a standard, unprivileged transaction. If that receipt is delayed (e.g. its target shard is congested/compute-saturated) long enough to span **two** static (V0/V1/V2) resharding events, `target_shard` becomes a shard id from two generations back, `resolve_to_current_shard` returns `None` for that older-generation single-hop lookup, `receiver_shard_id` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics.

### Impact Explanation
The panic occurs inside `DelayedReceiptQueueWrapper::pop`, invoked from the runtime's apply loop while draining the delayed receipt queue — a code path every node executes deterministically when applying a chunk. A panic there crashes the node process handling that shard; since every honest node (or every node tracking that shard) performs the identical deterministic computation, they all panic in lockstep, producing a transaction-triggered chain halt for that shard.

### Likelihood Explanation
Likelihood requires: (1) an unprivileged deploy of a global contract (ordinary transaction, no special privilege), (2) the target shard's queue congesting so the resulting `GlobalContractDistribution` receipt sits in the delayed-receipt queue, and (3) two static resharding events occurring while it is delayed. Any account can trigger (1) and (2) (submit a global-contract deploy and flood the target shard with heavy compute to keep the receipt delayed); (3) depends on the shard layout in use being static (non-dynamic-resharding) across two actual reshardings, which occurs on networks that still perform protocol-version-driven resharding rather than dynamic (V3) resharding. This makes it a real but somewhat operationally-timed condition rather than trivially instant, though it is fully reachable from ordinary transaction submission with no validator/operator cooperation required.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with proper error propagation (return a `Result` and bubble up via `?`), and extend `resolve_to_current_shard`/split-history tracking for static (V0/V1/V2) layouts to walk the full protocol-version layout history (similar to `build_shard_split_map`/`ShardLayoutV3` cumulative tracking), so historical `target_shard` values remain resolvable across any number of static reshardings, not just one.

### Proof of Concept
1. Configure a network still using static (non-V3) shard layouts across successive protocol-version reshardings.
2. From an unprivileged account, submit a `DeployGlobalContract` transaction targeting a shard.
3. Flood that shard with compute-heavy transactions (as in the existing regression test) so the resulting `GlobalContractDistribution` receipt is pushed into, and stays in, the delayed receipt queue.
4. Allow two static resharding events (two epoch-boundary shard-layout changes) to occur while the receipt remains delayed.
5. When the delayed queue drains and `DelayedReceiptQueueWrapper::pop` processes the stale receipt, `receipt_filter_fn` calls `receiver_shard_id(...).unwrap()`, which panics because `resolve_to_current_shard` for the (single-generation) static layout cannot resolve the two-generations-old `target_shard`, crashing every node applying that shard's chunk.     /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }
