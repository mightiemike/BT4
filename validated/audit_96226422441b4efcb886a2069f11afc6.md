## Finding: Silent data loss in `/transactions/by_version` and `/transactions/by_hash` write-set changes

### Title
Authenticated transaction API silently drops `WriteSetChange` entries on resource conversion failure - (`api/types/src/convert.rs`)

### Summary
`AptosValueAnnotator`'s `into_transaction_info` builds the `TransactionInfo.changes` field (the write-set changes returned by the REST API for a given committed transaction) by mapping every write op through `try_into_write_set_changes` and silently discarding any entry that fails to convert, via `.ok()` inside a `filter_map`. Unlike the sibling function `try_into_write_set_payload`, which propagates a conversion error with `?` and fails the whole call, `into_transaction_info` swallows the error and returns a response that still carries the correct, verifiable `hash` / `accumulator_root_hash` / `success` fields taken straight from the real, ledger-committed `TransactionInfo`, while quietly omitting one or more actual state changes from `changes`.

### Finding Description [1](#0-0) 

```rust
changes: write_set
    .into_write_op_iter()
    .filter_map(|(sk, wo)| self.try_into_write_set_changes(sk, wo).ok())
    .flatten()
    .collect(),
```

Compare this with the analogous conversion for `WriteSetPayload::Direct` a few lines below, which correctly fails on any error: [2](#0-1) 

`try_into_write_set_changes` (and the paths it calls, `try_access_path_into_write_set_changes` / `try_table_item_into_write_set_change`) can legitimately return `Err` for several reasons that are outside the caller's control and depend on the current annotator/state view context rather than the actual on-chain data:
- `try_into_resource` failing to resolve/deserialize a resource's Move type layout,
- `try_parse_abi()` failing on module bytecode,
- unresolved `Path::ResourceGroup` entries,
- unsupported `StateKeyInner` variants such as `Raw`/`TradingNative`. [3](#0-2) 

Because `into_transaction_info` is called from `try_into_onchain_transaction`, which serves `GET /transactions/by_version/:txn_version` and `GET /transactions/by_hash`, this defect reaches the public, "authenticated" transaction API directly: [4](#0-3) [5](#0-4) 

The `hash`, `accumulator_root_hash`, `state_change_hash`, and `success` fields all still come from the authentic `TransactionInfo` stored/committed by the executor and are correctly bound to `version`/proof context — they are not forged. However, the `changes` array attached to that same authenticated envelope can be silently incomplete: a resource or module write that really happened at that version can be missing from the reported list with no error, no partial-result flag, and no log visible to the client.

### Impact Explanation
Any client, indexer, auditor, bridge, or verifier that trusts the API's `TransactionInfo.changes` as a complete and faithful reflection of what was written at a given (correctly-hashed) version can be misled into believing a particular state mutation did not occur, even though `success: true` and the hashes are all correct and match the real ledger. This breaks the invariant that "authenticated API or state-view output" bound to a version must be a correct account of ledger-committed state; here the binding (hash/root) is faithful but the payload content is corrupted by omission with no indication of failure. This is a state-integrity/proof-binding issue on the API surface, distinct from a hard consensus fork, but it can silently misinform any system that relies on the node's REST API for completeness of write-set data (e.g., custom indexers or compliance/monitoring tooling reconstructing account state from the API rather than raw storage).

### Likelihood Explanation
This is not privileged and requires no adversarial validator behavior — it triggers deterministically whenever `try_into_write_set_changes` legitimately errors for any write in a transaction (e.g., a resource whose type layout cannot currently be resolved by the value annotator, or a resource-group entry that fails BCS decoding). Because the failure is swallowed rather than surfaced, it is very likely to go unnoticed in production; the only symptom is a shorter-than-expected `changes` list with no error.

### Recommendation
`into_transaction_info` should not use `.ok()` to drop failures. It should either propagate the error (making the endpoint return an explicit error status, consistent with `try_into_write_set_payload`), or explicitly track and surface conversion failures (e.g., logging plus an explicit "incomplete" indicator in the response) rather than silently truncating the `changes` list while still reporting `success: true` for the transaction.

### Proof of Concept
1. Commit a transaction that writes a resource/table item whose value fails to convert under `try_into_resource`/`try_write_table_item_into_decoded_table_data` in the currently configured `AptosValueAnnotator` (e.g., a `ResourceGroup` entry that cannot be BCS-decoded into the expected `BTreeMap<StructTag, Vec<u8>>`, or a resource whose struct layout can't be resolved).
2. Query `GET /v1/transactions/by_version/{version}` for that transaction.
3. Observe: the returned `TransactionInfo` has `success: true` and a `hash`/`accumulator_root_hash` matching the real committed values, but `changes` omits the entry that failed to convert — with no error surfaced anywhere in the response.
