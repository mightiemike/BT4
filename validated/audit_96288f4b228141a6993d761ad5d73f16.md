Based on my investigation, I found a strong architectural analog to the Ion Protocol bug pattern: **a "pause" mechanism enforced on one ingress path but silently bypassed on another path leading to the same sensitive operation.**

### Title
`accept_new_txs` Pause Flag Is Only Enforced at the HTTP Ingress and Is Bypassed for P2P-Propagated Transactions - (File: crates/apollo_mempool_p2p/src/runner/mod.rs)

### Summary
The sequencer exposes a dynamic "pause new transactions" control, `accept_new_txs`, which is checked in the HTTP server's `add_rpc_tx`/`add_tx` handlers before forwarding a transaction to the `Gateway`. However, the `MempoolP2pRunner`, which receives transactions gossiped from peers over the P2P network and forwards them directly to the same `Gateway::add_tx` entry point, never checks `accept_new_txs` (or any equivalent gate). This mirrors the Ion Protocol finding: one code path enforces a "paused" invariant while a structurally parallel path to the same sensitive operation returns/executes without that check, defeating the purpose of the pause.

### Finding Description
`check_new_transactions_are_allowed` is only invoked from the HTTP handlers `add_rpc_tx` and `add_tx`: [1](#0-0) [2](#0-1) 

Both handlers ultimately call `Gateway::add_tx` (via `add_tx_inner`/`GatewayClient`). But `Gateway::add_tx` is also reachable directly from the `MempoolP2pRunner`, which forwards every transaction batch received from the gossip network straight to `gateway_client.add_tx(...)`, with no `accept_new_txs`-equivalent gate: [3](#0-2) 

`Gateway::add_tx`/`add_tx_inner` itself performs no pause check — it goes straight into stateless/stateful validation and mempool insertion: [4](#0-3) [5](#0-4) 

The only place the flag lives is `HttpServerDynamicConfig.accept_new_txs`, polled dynamically for the HTTP server component: [6](#0-5) 

Since `MempoolP2pRunner` and the HTTP server are independent components that both hold a `SharedGatewayClient` and both call `Gateway::add_tx` (via the component's RPC handler), the "pause" is not actually a Gateway-level or Mempool-level invariant — it's an HTTP-server-specific UX gate. This is architecturally identical to the Ion Protocol bug: the "primary" path (individual liquidation / HTTP-submitted tx) enforces the pause via a downstream check, while the "secondary" path (protocol liquidation / P2P-propagated tx) reaches the same effective operation through a different code route that never runs that check.

### Impact Explanation
If an operator intentionally sets `accept_new_txs = false` on a node (e.g., during an incident, migration, or governance-directed pause) expecting no new transactions to enter that node's mempool/pipeline, transactions gossiped from peers will still be accepted, validated, and inserted into the mempool via the P2P path, and can still be proposed by that node during consensus rounds if it becomes proposer. This defeats the purpose of the pause control and can let unwanted transactions continue to be processed/ordered by a node that operators believe is inert, potentially undermining coordinated incident response (e.g., during an emergency where operators want a specific node to stop admitting/propagating transactions).

### Likelihood Explanation
Any unprivileged peer/relayer on the P2P network can trigger this path simply by broadcasting a transaction; no special privileges are required to submit via gossip, and this is the normal transaction propagation mechanism between sequencer P2P peers. The gap is structural (missing check in one code path) and always present whenever `accept_new_txs` is toggled to `false`, i.e., 100% reproducible in that operational state.

### Recommendation
Enforce the `accept_new_txs` (or an equivalent pause invariant) at a single choke point shared by all ingress paths — e.g., inside `Gateway::add_tx`/`add_tx_inner` itself (reading from `SharedConfigManagerClient` or an injected dynamic-config), rather than only in the HTTP server handlers. Alternatively, have `MempoolP2pRunner` consult the same dynamic config as the HTTP server before forwarding batches to the gateway client, so both ingress paths honor the pause consistently.

### Proof of Concept
1. Configure a node with `http_server_config.dynamic_config.accept_new_txs = false` (e.g., via the config manager) so that the HTTP server rejects all `add_rpc_tx`/`add_tx` requests with `SERVICE_UNAVAILABLE`, as verified by the existing test `allow_new_txs`: [7](#0-6) 
2. From a peer sequencer, broadcast an `RpcTransactionBatch` over the `MEMPOOL_TOPIC` gossip topic containing a valid transaction.
3. On the paused node, `MempoolP2pRunner::start` receives the batch via `broadcasted_topic_server.next()` and forwards each transaction directly to `gateway_client.add_tx(...)` with no pause check, as demonstrated by the existing test `incoming_p2p_tx_reaches_gateway_client`, which shows the transaction reaching the gateway client unconditionally: [8](#0-7) 
4. The transaction is validated and inserted into the paused node's mempool despite `accept_new_txs = false`, confirming the pause is bypassed via the P2P ingress path.

        &self,
        tx: RpcTransaction,
        p2p_message_metadata: Option<BroadcastedMessageMetadata>,
    ) -> GatewayResult<GatewayOutput> {
        let mut metric_counters = GatewayMetricHandle::new(&tx, &p2p_message_metadata);
        metric_counters.count_transaction_received();
        if let RpcTransaction::Invoke(RpcInvokeTransaction::V3(ref inv)) = tx {
            if !inv.proof_facts.is_empty() {
                metric_counters.count_private_transaction_received();
            }
        }
        let is_p2p = p2p_message_metadata.is_some();

        if let RpcTransaction::Declare(ref declare_tx) = tx {
            if let Err(e) = self.check_declare_permissions(declare_tx) {
                metric_counters.record_add_tx_failure(&e);
                return Err(e);
            }
        }

        // Perform stateless validations.
        self.stateless_tx_validator.validate(&tx)?;
