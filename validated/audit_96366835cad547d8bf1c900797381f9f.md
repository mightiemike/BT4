## Finding

### Title
`ensure_match_transaction_info` never validates the state-checkpoint root hashes, letting replay/verify-execution tooling silently accept a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator used by chunk-executor replay/verify-execution and the CLI transaction-replay tool to confirm that locally re-executed output matches the authenticated `TransactionInfo` pulled from the trusted ledger (accumulator-proven). The function checks status, gas, write-set hash, and event root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually authenticate the post-txn state tree root. A local state-computation bug that produces a correct write set but a wrong Merkle/JMT root at a checkpoint boundary will pass this check.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . It validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (`state_change_hash`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It explicitly does **not** check `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The code itself documents this gap: [2](#0-1) 

This comparator is the sole per-transaction correctness check used by:
- Chunk executor's independent re-execution verification path, `verify_execution`, which loops over `execution_output.to_commit.transaction_outputs` against `transaction_infos` fetched from the backup/ledger and calls `ensure_match_transaction_info` per transaction: [3](#0-2) 
- The Move CLI's on-chain transaction replay tool, which materializes VM output and calls the same comparator to decide whether replay matched the authenticated transaction: [4](#0-3) 

Note this differs from the *fast-sync / chunk-commit* path (`update_ledger`/`DoLedgerUpdate`), where the freshly computed `TransactionInfo` (including state-checkpoint hashes) is re-hashed and folded into the transaction accumulator, then checked against the target ledger info's accumulator root via `chunk_verifier.verify_chunk_result` — that path *does* bind the state root cryptographically. The gap is specifically in the *verify-execution / replay* tooling that re-executes already-committed transactions and compares outputs directly via `ensure_match_transaction_info`, bypassing accumulator-root binding for the state-checkpoint fields.

### Impact Explanation
Verify-execution/replay-verify is the tool operators and auditors rely on to detect state divergence between a local execution and the authenticated mainnet ledger (e.g., after a VM upgrade, a state-merge bug, or corrupted account/resource-group handling that still produces the same raw write set bytes but merges into a different Merkle tree, or where write-set hash coincidentally matches while a downstream state-checkpoint computation diverges). Because `state_checkpoint_hash` (and the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) are never compared, such divergence can pass "verify-execution" as a false positive, giving operators false assurance that replayed/re-executed state matches the authenticated chain. This directly matches the "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "Wrong accumulator root ... accepted as valid" state-integrity categories, since the mismatch would be undetectable through the intended verification surface even though it is exactly the kind of check that surface exists to perform.

### Likelihood Explanation
This isn't a theoretical parsing quirk — it's a currently-shipped, code-acknowledged gap (the TODO comment explicitly states the comparator "ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated ... state root diverges from local execution"). It requires an underlying state-computation divergence to actually trigger (this comparator doesn't create such a divergence by itself), so its practical severity depends on the existence of some other state-root bug; however, as a standalone integrity control it fails to fulfil its purpose today for any divergence that doesn't also change the raw write set bytes.

### Recommendation
Extend `ensure_match_transaction_info` to accept and compare the expected state-checkpoint hash(es) (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) whenever they are `Some` in the trusted `TransactionInfo`, mirroring how `write_set_hash` and `event_root_hash` are already validated. Until that lands, `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and any reliance on `verify_execution`/CLI replay for state-root assurance should be treated as not providing state-checkpoint integrity guarantees.

### Proof of Concept
Not directly exploitable as a standalone PoC (no local state-root bug was found to trigger the divergence); the finding is that the verification function itself has an incomplete comparison, confirmed by direct code reading of [1](#0-0)  and its call sites in [3](#0-2)  and [4](#0-3) , plus the developer-authored TODO acknowledging the exact impact scenario.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
