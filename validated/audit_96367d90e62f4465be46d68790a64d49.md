### Title
Missing beneficiary-account-existence check on `DeleteAccount` lets user-supplied balance refund be permanently burned - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`DeleteAccountAction::beneficiary_id` is only validated for account-id *syntax*, never for whether the account actually exists. If a user submits `DeleteAccount { beneficiary_id }` pointing at a syntactically valid but non-existent (or since-deleted) named account, the resulting balance-refund receipt fails and the account's remaining NEAR balance is permanently burned instead of being returned to anyone — an unrecoverable loss of user funds, directly analogous to the "missing zero-address validation for `receiver`" issue in the reported audit.

### Finding Description
When an account is deleted, `action_delete_account` unconditionally builds a `Receipt::new_balance_refund` to the caller-supplied `beneficiary_id` and forwards the account's whole balance to it: [1](#0-0) 

The only validation performed on `beneficiary_id` before this happens is a syntactic check, not an existence check: [2](#0-1) 

The generated refund receipt is a `Transfer` action with `predecessor_id == "system"`, i.e. a refund receipt: [3](#0-2) 

When this refund receipt is later applied, `check_account_existence` explicitly forbids account creation for refund receipts (`is_refund` short-circuits to `false`), so if `beneficiary_id` does not exist, the transfer fails with `AccountDoesNotExist`: [4](#0-3) [5](#0-4) 

And crucially, once a refund receipt's execution fails, the runtime does not re-refund or return the deposit anywhere — it burns the tokens: [6](#0-5) 

This exact failure mode is already covered by an existing regression test confirming refunds to nonexistent accounts are rejected (proving the "no recovery path" behavior is real, not speculative): [7](#0-6) 

and a similar test for ordinary transfers to nonexistent accounts, showing the deposit is consumed with no way back to the sender: [8](#0-7) 

So the analog of the Sherlock report's "receiver == zero address, funds locked forever" is: `beneficiary_id` is a well-formed but non-existent account (typo, mistakenly deleted account, account that never existed) — an unprivileged transaction signer fully controls this value when submitting `DeleteAccount`, and there is no requirement or check that the target account actually exists before the balance is unconditionally routed to it as a un-recoverable refund receipt.

### Impact Explanation
Funds locked forever (in this case, burned entirely rather than merely stuck) meets the "permanently frozen funds" acceptance criterion. Any account owner who fat-fingers, mistypes, or targets a beneficiary that has since been deleted permanently loses their entire remaining account balance with no possibility of recovery — this is a direct, concrete value-loss event reachable by a single signed transaction from an unprivileged account owner.

### Likelihood Explanation
High likelihood of accidental triggering (typo in beneficiary_id, or a race where the intended beneficiary account is deleted between signing and execution) and always reachable deterministically by any account holder who deletes their own account — no special privileges, validator status, or network conditions are required. This is a normal `DeleteAccount` action available in every transaction/receipt.

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` currently exists in state (e.g., via `get_account`), and if not, fail the `DeleteAccount` action with a clear `ActionErrorKind` (e.g. `AccountDoesNotExist { account_id: beneficiary_id }`) instead of allowing the account deletion to proceed and unconditionally burn the refund. Alternatively, if deletion must still be allowed to proceed for other reasons, at minimum surface an explicit warning/require step during transaction validation (in `validate_delete_action`, `runtime/runtime/src/action_validation.rs:447`) that checks state for beneficiary existence, mirroring the existing `AccountDoesNotExist` semantics used elsewhere for `Transfer`.

### Proof of Concept
1. Account `alice.near` calls `DeleteAccount { beneficiary_id: "nonexistent.near" }` where `nonexistent.near` has never been created (or was deleted earlier in the same chunk).
2. `validate_delete_action` only checks `nonexistent.near` is a syntactically valid `AccountId` — it passes.
3. `action_delete_account` removes `alice.near` and enqueues `Receipt::new_balance_refund(&"nonexistent.near", account_balance)`.
4. When this refund receipt is applied, `check_account_existence` rejects the implicit account creation (`is_refund == true`), the transfer action fails with `AccountDoesNotExist`.
5. Per `runtime/runtime/src/lib.rs:1047-1054`, because the receipt's predecessor is `"system"` (a refund) and the result is an error, `alice`'s entire deleted-account balance is added to `other_burnt_amount` — burned by the protocol, unrecoverable by anyone.
