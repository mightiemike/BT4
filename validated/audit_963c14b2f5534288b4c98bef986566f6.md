### Title
Unvalidated `beneficiary_id` in `DeleteAccount` causes permanent token burn when the recipient account does not exist - (File: runtime/runtime/src/actions.rs)

### Summary
The external report describes `PrimitiveEngine.withdraw()` allowing a user to specify an unvalidated recipient address, so funds sent to a bad/self address get permanently stuck. The structural analog in nearcore is the `DeleteAccountAction.beneficiary_id` field: a transaction signer chooses an arbitrary `beneficiary_id` to receive their remaining account balance when deleting their own account, but the runtime only validates that this is a *syntactically* valid account id — it never checks that the account actually exists. If it doesn't, the resulting refund receipt fails and the funds are burned forever.

### Finding Description
`action_delete_account` unconditionally converts the deleting account's remaining balance into a system-generated balance-refund receipt addressed to `beneficiary_id`, with no existence check on that id: [1](#0-0) 

That receipt is a `Transfer` action with `predecessor_id == "system"` (a refund). `check_account_existence`/`implicit_creation_allowed` explicitly forbid refunds from creating any account, including named ones — which can never be implicitly created by transfer under any circumstance: [2](#0-1) 

Consequently, if `beneficiary_id` refers to an account that does not exist (a typo, an account that was already deleted, or the deleting account's own id after it has just been removed), the `Transfer` action fails with `AccountDoesNotExist`. Because the receipt is a system-refund receipt, a failed refund is unconditionally burned rather than returned to anyone: [3](#0-2) 

This is confirmed by an existing regression test that asserts exactly this behavior for balance-refund receipts sent to a missing account: the transfer fails with `AccountDoesNotExist` and no account is created: [4](#0-3) 

The only validation performed on `beneficiary_id` is a format check (`InvalidAccountId`) documented in the spec — there is no existence check, and no check that `beneficiary_id != account_id` being deleted: [5](#0-4) 

Existing tests only exercise the case where the beneficiary account is pre-created and exists; the code comment even notes "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund [and fail]": [6](#0-5) 

### Impact Explanation
Any unprivileged account holder submitting a single `DeleteAccount` transaction can permanently and irreversibly destroy their entire remaining account balance if `beneficiary_id` does not correspond to a live account — this is exactly analogous to Alice accidentally sending withdrawal funds to the engine and having them stuck: the funds are irrecoverably lost (in this case burned rather than merely stuck, which is an even more severe outcome since it also reduces total protocol supply, `other_burnt_amount`). This satisfies "permanently frozen funds" / unauthorized value destruction from a single transaction signer's own action, with no attacker or privileged actor needed — a routine user mistake (typo'd beneficiary, referencing an already-deleted sub-account, or reusing the same account id) results in silent, unrecoverable fund loss.

### Likelihood Explanation
High likelihood of accidental triggering: `beneficiary_id` is a free-form `AccountId` parameter supplied directly by the transaction signer (or via `promise_batch_action_delete_account` from a contract), with the only validation being basic account-id format checking. There is no UI/runtime safeguard preventing a user from specifying a nonexistent, sub-account that no longer exists, or an id that will be deleted in the same/adjacent chunk (race condition), all of which lead to silent burning of the deleted account's balance.

### Recommendation
- **Short term**: In `action_delete_account` (or upstream in `validate_delete_action`), verify that `beneficiary_id` refers to an existing account (or reject if `beneficiary_id == account_id`) before allowing the delete to proceed, or fail the `DeleteAccount` action outright rather than issuing a refund receipt that is silently burned on failure.
- **Long term**: Add fuzz/property tests (analogous to the Echidna tests in the referenced report) around `DeleteAccount`/refund flows asserting that funds are never burned as a side effect of a valid, well-formed user transaction, and require RPC/wallet-level warnings when the target beneficiary account cannot be resolved before submitting a `DeleteAccount` transaction.

### Proof of Concept
1. Account `alice.near` has a NEAR balance.
2. `alice.near` submits `SignedTransaction` with a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near".parse().unwrap() })` (or accidentally sets `beneficiary_id: alice.near` itself).
3. `action_delete_account` runs, computes `account_balance > 0`, and pushes `Receipt::new_balance_refund(&"nonexistent.near", account_balance)` [1](#0-0) , then removes `alice.near`'s account state.
4. The refund receipt (predecessor `"system"`) executes a `Transfer` to `"nonexistent.near"`; since the account doesn't exist and refunds are never allowed to create accounts [2](#0-1) , the action fails with `AccountDoesNotExist`.
5. Because it's a system/refund receipt and it failed, the deposit amount (Alice's entire remaining balance) is added to `stats.balance.other_burnt_amount` and permanently removed from total supply [3](#0-2) .
6. Alice's funds are unrecoverably gone; this exact scenario (refund to a missing account failing and not creating it) is directly validated by the existing test `refund_may_not_create_universal_account` [4](#0-3) .

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

## DeleteAccountAction

```rust
pub struct DeleteAccountAction {
    /// The remaining account balance will be transferred to the AccountId below
    pub beneficiary_id: AccountId,
}

**Outcomes**:

- The account, as well as all the data stored under the account, is deleted and the tokens are transferred to `beneficiary_id`.

### Errors

**Validation Error**:

- If `beneficiary_id` is not a valid account id, the following error will be returned

```rust
/// Invalid account ID.
InvalidAccountId { account_id: AccountId },
```

- If this action is not the last action in the action list of a receipt, the following error will be returned

```rust
/// The delete action must be a final action in transaction
DeleteActionMustBeFinal
```

- If the account still has locked balance due to staking, the following error will be returned

```rust
/// Account is staking and can not be deleted
DeleteAccountStaking { account_id: AccountId }
