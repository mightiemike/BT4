### Title
Transaction-triggered panic in `receipt_filter_fn` via unhandled `receiver_shard_id` error on stale `GlobalContractDistribution` receipts across resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
The CVE describes a crash caused by a dissector failing to properly handle/initialize a data structure for a specific message type when parsing attacker-supplied network data. The closest reachable analog in nearcore is a crash caused by the runtime's delayed-receipt dequeue path failing to handle an edge case when resolving the shard destination of a `GlobalContractDistribution` receipt that has aged across resharding events — a receipt type any account can trigger via a `DeployGlobalContract` action.

### Finding Description
`ReceiptOrStateStoredReceipt::receiver_shard_id` computes the destination shard for a receipt. For `GlobalContractDistribution` receipts it does: [1](#0-0) 
which returns `Err(EpochError::ShardingError(...))` when `resolve_to_current_shard` cannot map the receipt's `target_shard` (which may be from an arbitrarily old shard layout, since the receipt can sit in the delayed-receipt queue across multiple resharding events) onto a shard in the current layout.

This `Result` is consumed in the delayed-receipt pop path with an unconditional `.unwrap()`: [2](#0-1) 

The comment on this function explicitly documents the risk: "With ReshardingV3, it's possible for a chunk to have delayed receipts that technically belong to the sibling shard before a resharding event," but the `.unwrap()` on `receiver_shard_id(&shard_layout)` turns any unmapped/stale `target_shard` into an unconditional panic during chunk application rather than a handled error. A dedicated regression test in the codebase acknowledges exactly this failure mode: [3](#0-2) 
("If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations.")

`GlobalContractDistribution` receipts are produced whenever any account submits a `DeployGlobalContract` action — an ordinary, unprivileged transaction. If such a receipt is delayed (e.g., due to congestion) across two or more subsequent resharding events before being dequeued, `resolve_to_current_shard` can fail to find a current-layout descendant for the receipt's stale `target_shard`, causing `receiver_shard_id` to return `Err`, which the `.unwrap()` in `receipt_filter_fn` turns into a panic inside `Runtime::apply`'s receipt-processing loop.

### Impact Explanation
A panic inside chunk application (`process_delayed_receipts` → `DelayedReceiptQueue::pop` → `receipt_filter_fn`) crashes every node applying that shard when it processes the offending chunk. Because this triggers deterministically for any node applying the same chunk, it functions as a transaction-triggered halt of that shard (and potentially chains that depend on cross-shard receipts from it), matching the "transaction-triggered halt" / "invalid state transition acceptance" impact class permitted by the scope of this analysis. This is high-severity because it requires no validator or peer misbehavior — only a normal `DeployGlobalContract` transaction combined with congestion and multiple resharding events, both of which are protocol-scheduled, non-adversarial-only conditions.

### Likelihood Explanation
Triggering requires: (1) submitting a `DeployGlobalContract` action to create a `GlobalContractDistribution` receipt, (2) that receipt becoming delayed (e.g. via congestion), and (3) at least two resharding events occurring for the relevant shard before the receipt is dequeued. This is a narrow but realistic sequence achievable by an ordinary transaction signer without any privileged role, especially on a network actively performing dynamic resharding (`ReshardingV3`/`DynamicResharding`). The existence of a purpose-built regression test in the repository indicates this scenario was identified as a real concern by the codebase's own maintainers.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:876`) with proper error propagation (return `Result` and surface a `RuntimeError`/`StorageInconsistentState` rather than panicking), and verify `resolve_to_current_shard` (`core/primitives/src/shard_layout/v3.rs`) correctly walks an arbitrary number of resharding generations rather than only one hop, since delayed receipts can persist across more than a single resharding event.

### Proof of Concept
Conceptual reproduction (already partially codified in-repo):
1. Submit a `DeployGlobalContract` transaction from any account, producing a `GlobalContractDistribution` receipt targeting shard `S`.
2. Induce congestion so this receipt is placed in the delayed-receipt queue rather than processed immediately.
3. Trigger two (or more) resharding events that change the shard layout such that shard `S` no longer has a resolvable descendant via `resolve_to_current_shard`.
4. When the delayed queue drains and the runtime calls `DelayedReceiptQueue::pop` → `receipt_filter_fn` on the stale receipt, `receiver_shard_id` returns `Err`, and the `.unwrap()` panics, halting chunk application for that shard.

This exact scenario is what `test-loop-tests/src/tests/global_contracts_distribution.rs` (lines 163–186) is built to detect, confirming the reachability and root cause described above. I was not able to fully verify within the available tool budget whether the current `resolve_to_current_shard` implementation in `core/primitives/src/shard_layout/v3.rs` already closes this gap for more than one resharding generation — this should be confirmed with a live Devin session that can run the referenced test and inspect `v3.rs` in full.

    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {

        receipt_shard_id == self.shard_id
    }
