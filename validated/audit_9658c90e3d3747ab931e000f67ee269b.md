### Title
`vote-for-aggregate-public-key` never enforces its own voting-window check, allowing signer-weight votes outside the designated prepare-phase window - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
The `signers-voting.clar` contract defines a private helper `is-in-voting-window` that is meant to restrict `vote-for-aggregate-public-key` to the prepare-phase of the reward cycle whose signer set was most recently computed, but this helper is never called anywhere in the contract. The public entry point only checks that a key has not already been approved for the target `reward-cycle`, that the key is well-formed and novel, and that the caller has not already voted in that `(reward-cycle, round)` pair — it does not check that `reward-cycle` is the one currently open for voting. This is structurally the same class of bug as the reported issue: an operation whose effect should only be permitted while a particular state/window is "active" is missing the corresponding activation/deactivation guard, so it can be exercised outside that window.

### Finding Description
`is-in-voting-window` is defined at [1](#0-0)  and is intended to gate voting to the prepare phase for the reward cycle whose signer set was just computed (`get-last-set-cycle`). However, `vote-for-aggregate-public-key` at [2](#0-1)  never invokes `is-in-voting-window`. The only gating checks present are:
- the aggregate key has not already been approved for that `reward-cycle` (`ERR_OUT_OF_VOTING_WINDOW` is actually reused for this, not for an out-of-window time check),
- the key is 33 bytes,
- the key is novel across cycles,
- the caller has not already voted in that `(reward-cycle, round)`,
- the round only increases by at most 1 (`update-last-round`).

None of these enforce that `reward-cycle` corresponds to the currently active voting window (i.e., the next reward cycle during its prepare phase). `get-signer-weight` at [3](#0-2)  pulls the caller's weight for whatever `reward-cycle` argument was supplied, as long as `.signers get-signer-by-index` has an entry there and the entry's `signer` matches `tx-sender`. Because `.signers` retains signer-set data for cycles beyond just the "current" one, a signer who was part of a *future* reward cycle's already-computed set, or a *past* cycle whose key was never finalized, can call `vote-for-aggregate-public-key` for that cycle at any burn height — not only during that cycle's prepare phase.

This breaks the equality that consensus depends on: “a signer’s vote should only count toward finalizing a key during the reward cycle's designated voting window.” Here, a legitimate signer (no majority collusion needed — a single signer can act unilaterally) can push votes for a reward cycle before or after its window, potentially causing:
- Premature approval of an aggregate key for a future cycle before all/any other signers have registered their intended vote, or
- Continued tallying (and possible approval) of a key for a reward cycle whose window has closed but whose key was never finalized, well after the node/network moved on.

Since `vote-for-aggregate-public-key` is invoked deterministically from the burnchain operation processor at [4](#0-3)  for every `VoteForAggregateKeyOp` observed on the burnchain (there is no additional reward-cycle/window filter applied before the call — see the operation's fields at [5](#0-4) ), any out-of-window vote submitted on the burnchain is processed identically by every node, so this is deterministic (not divergent) — but it does allow the aggregate key state to be mutated outside its intended lifecycle, which downstream consumers (`get_aggregate_public_key_pox_4`, [6](#0-5) ) rely on being tied to the correct reward cycle's finalized signer set.

### Impact Explanation
This does not directly cause a chain split by itself (all nodes process the same burn op deterministically), so it does not meet the "Critical" bar on its own. However, it degrades to a reward-cycle/consensus-state integrity issue: it allows the aggregate public key for a reward cycle to be locked in outside the window intended by contract design (before the prepare-phase signer set stabilizes, or long after the cycle nominally closed). If the timing mismatch causes different rounds/weights to be tallied than the protocol designers intended (e.g., a stale signer voting with old weight data for a future cycle whose real signer-set membership later changes), this could produce an aggregate key that does not reflect the actual reward-cycle signer set — a state that no other validation path double-checks. This is best characterized as a High-severity minority-triggerable divergence in the signer/aggregate-key finalization process, since a single signer, using its own key/weight only, can call the function outside the intended window.

### Likelihood Explanation
Likelihood is high: `vote-for-aggregate-public-key` is a public function with no additional access control beyond the signer's own key, and the missing check is a straightforward omission (the helper function exists in the code but is simply never wired in). No special timing collusion, majority stake, or elevated privilege is required — any legitimate signer that already has an entry in `.signers get-signer-by-index` for a given `reward-cycle` can trigger this at will.

### Recommendation
Call `is-in-voting-window burn-block-height reward-cycle` (or equivalent) as an `asserts!` guard at the top of `vote-for-aggregate-public-key`, returning `ERR_OUT_OF_VOTING_WINDOW` if the vote is not for the reward cycle whose signer set was most recently finalized and the transaction is not currently within that cycle's prepare phase — mirroring the recommendation to only allow rate/state changes ("votes") while the corresponding window/pool is in its designated active state.

### Proof of Concept
1. Wait for `.signers` to finalize the signer set for reward cycle `N+1` (via `get-last-set-cycle` returning `N+1`) during cycle `N`'s prepare phase — this is the intended voting window.
2. As a registered signer for reward cycle `N+1`, do not vote during the prepare phase.
3. After the prepare phase for cycle `N+1` ends (i.e., outside the window `is-in-voting-window` would have permitted), call `vote-for-aggregate-public-key signer-index key round (N+1)` directly. Because the function never calls `is-in-voting-window`, and `get-signer-weight` and `get-approved-aggregate-key` checks pass (assuming the key for `N+1` was not already finalized), the vote succeeds and can push the tally past `threshold-weight`, finalizing `aggregate-public-keys` for `N+1` well after the intended window, or a signer can attempt this before the prepare phase even opens if `.signers` has already published the future signer set.

    /// Get the aggregate public key for a given reward cycle from pox 4
    pub fn get_aggregate_public_key_pox_4(
        &mut self,
        sortdb: &SortitionDB,
        block_id: &StacksBlockId,
        reward_cycle: u64,
    ) -> Result<Option<Vec<u8>>, Error> {
        let aggregate_public_key_opt = self
            .eval_boot_code_read_only(
                sortdb,
                block_id,
                SIGNERS_VOTING_NAME,
                &format!("(get-approved-aggregate-key u{reward_cycle})"),
            )?
            .expect_optional()
            .map_err(|_| {
                Error::Expects("get-approved-aggregate-key did not return optional".to_string())
            })?;
        debug!(
            "Aggregate public key for reward cycle {reward_cycle} is {aggregate_public_key_opt:?}"
        );

        let aggregate_public_key = match aggregate_public_key_opt {
            Some(value) => {
                // A point should have 33 bytes exactly.
                Some(value.expect_buff(33).map_err(|_| {
                    Error::Expects(
                        "get-approved-aggregate-key did not return buff of length 33".to_string(),
                    )
                })?)
            }
            None => None,
        };
        Ok(aggregate_public_key)
    }
