### Title
Mutable `GlobalContractDeployMode::AccountId` global-contract code reference permits a single redeploy transaction to permanently brick and freeze funds of dependent (especially deterministic) accounts - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
`GlobalContractDeployMode::AccountId` lets the deploying account overwrite the code backing a global contract at any time, with no restriction on whether other accounts currently depend on that exact code/storage schema. [1](#0-0)  Any account can opt into that mutable code via `UseGlobalContractAction` or `DeterministicStateInitAction`, and the runtime applies a redeploy globally without checking whether dependents are mid-flow or lack any account owner to opt out. [2](#0-1)  This is the direct nearcore analog of `PaymentSettler::setStablecoin`: a single privileged call swaps a shared referenced resource for every dependent at once, and dependents that were relying on the old resource's schema/logic can be left with permanently frozen funds and no recovery path.

### Finding Description
`DeployGlobalContractAction` with `deploy_mode: AccountId` deploys code that "Users will be able to reference ... by that account id. This allows the owner to update the contract for all its users" — i.e., it is intentionally mutable and can be redeployed at any time by the owning account, unconditionally. [3](#0-2)  This exactly mirrors the report's `setStablecoin`, which "can be called at any time" though it should only be called under a narrow precondition.

Two classes of accounts bind themselves to this mutable resource:
1. Ordinary accounts via `UseGlobalContractAction`, which sets `AccountContract::GlobalByAccount(id)` — resolved dynamically to whatever code currently lives under `id` — and can later call `UseGlobalContractAction` again (with a full access key) to switch away. [4](#0-3) 
2. Deterministic accounts (`0s...`, NEP-616) created via `DeterministicStateInitAction`, whose `code: GlobalContractIdentifier::AccountId(...)` is likewise a live reference to that mutable code. [5](#0-4)  Critically, deterministic accounts are created **without** a full access key: `create_deterministic_account` deliberately keeps `actor_id` as the predecessor "to prevent AddKey, DeployContract, or any other actions that only the account owner is permitted to do." [6](#0-5)  This means the *only* way such an account can ever migrate off a given `GlobalByAccount` reference is if its own currently-installed code self-issues a new `UseGlobalContractAction`/state-init against itself.

If the owning account of the `AccountId`-mode global contract redeploys new code (via one more `DeployGlobalContractAction`, no special privilege beyond being the original deployer, and no check on whether existing dependents are mid-lifecycle), the change propagates shard-by-shard and immediately becomes the effective code for every account referencing that `AccountId` — including deterministic accounts holding balances (`amount`) and contract storage laid out for the old code's schema (`test_global_contract_update` demonstrates the exact mechanic: after redeploy, all `GlobalByAccount` users immediately run the new code). [7](#0-6)  If the new code omits whatever "escape hatch" function the old code exposed (e.g. a withdraw/self-migrate method), and given that dependent deterministic accounts have no full access key to fall back on, those accounts' NEAR balance and any state become permanently unreachable — precisely analogous to "old stablecoin being trapped in the contract" and "holders unable to claim funds" in the report, but for the shared code+schema resource instead of an ERC20 address.

### Impact Explanation
Balances (`amount`) held on deterministic/sharded accounts that use a `GlobalByAccount` reference can become permanently frozen: there is no full access key to intervene, and if the owner redeploys incompatible code the only exit path (a self-issued action from the account's own running contract) may no longer exist. This is a concrete, transaction-triggered case of permanently frozen funds reachable by any deployer of an `AccountId`-mode global contract, affecting every account (including those created by unrelated third parties via `DeterministicStateInitAction`/`UseGlobalContractAction`) that opted into referencing that contract.

### Likelihood Explanation
Any account that deployed a global contract in `AccountId` mode can redeploy at any time with a single ordinary transaction — no special state precondition, cooldown, or dependent-balance check is enforced by `use_global_contract`/the deploy path. [2](#0-1)  The likelihood of accidental incompatibility (a legitimate upgrade that forgets to keep the migration/escape-hatch method) is non-trivial given the sharded-contract pattern is explicitly designed around iterative code updates (`test_global_contract_update`), and malicious intent by the deploying account is also possible since dependents have no on-chain guarantee about future code compatibility.

### Recommendation
Options mirroring the report's suggested mitigations for `PaymentSettler`:
- Pin the code reference used by `DeterministicStateInitAction`/`UseGlobalContractAction` to a specific version/nonce at the time of use rather than resolving dynamically to whatever code currently lives under the `AccountId`, so a later redeploy cannot retroactively change already-committed dependents.
- Require an explicit, dependent-account-controlled opt-in/opt-out mechanism (e.g., only follow `AccountId`-mode updates if the account's current code, or an owner-controlled key, affirmatively re-links to the new version) before a redeploy can affect existing accounts.
- Alternatively, restrict `DeterministicStateInitAction`/`UseGlobalContractAction` to only ever bind to immutable `CodeHash`-mode contracts, eliminating the mutable-reference risk entirely for account classes that lack a full access key fallback.

### Proof of Concept
1. Deployer account `alice` deploys a global contract in `AccountId` mode implementing a `withdraw`/self-migrate method, as in `test_global_contract_update`. [8](#0-7) 
2. A third party creates deterministic (`0s...`) accounts via `DeterministicStateInitAction` with `code: GlobalContractIdentifier::AccountId(alice)`, funding them with NEAR balance, per the pattern in `new_deterministic_account_with_data`. [9](#0-8)  These accounts have no full access key (`create_deterministic_account`). [6](#0-5) 
3. `alice` redeploys new code under the same `AccountId` that omits the withdraw/self-migrate method (e.g., a trivial contract, as also shown in the test). [10](#0-9) 
4. Every deterministic account referencing `alice`'s `AccountId` now runs the new code and can never invoke a function to transfer out its balance or re-link its contract reference — the NEAR held on those accounts is permanently frozen, with no key-based recovery available.

```rust
pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
```

```rust
pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}
```

```rust
#[test]
fn test_global_contract_update() {
    let mut env = GlobalContractsTestEnv::setup(Balance::from_near(1000));
    let use_accounts = [env.account_shard_0.clone(), env.account_shard_1.clone()];

    env.deploy_trivial_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        env.use_global_contract(
            account,
            GlobalContractIdentifier::AccountId(env.deploy_account.clone()),
        );

        // Currently deployed trivial contract doesn't have any methods,
        // so we expect any function call to fail with MethodNotFound error
        let call_tx = env.call_global_contract_tx(account.clone(), account.clone());
        let call_outcome = env.execute_tx(call_tx);
        assert_matches!(
            call_outcome.status,
            FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
                kind: ActionErrorKind::FunctionCallError(FunctionCallError::MethodResolveError(
                    MethodResolveError::MethodNotFound
                )),
                index: _
            }))
        );
    }

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        // Function call should be successful after deploying rs contract
        // containing the function we call here
        env.assert_call_global_contract_success(account.clone(), account.clone());
    }
}
```
