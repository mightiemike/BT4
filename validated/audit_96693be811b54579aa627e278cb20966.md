### Title
Divergent total-weight accounting between `UnfreezeBalanceActuator` and `UnfreezeBalanceProcessor` allows `TotalNetWeight`/`TotalEnergyWeight` to be decremented by the nominal request amount instead of the actual (clamped) state change — analogous to the Vault.vy bad-debt double-accounting bug - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java)

### Summary
The Sherlock H-1 report shows that `total_debt_amount` was decremented using the wrong quantity (the swap output) instead of the actual debt write-off amount, so a global aggregate (`total_debt_amount`) diverged from the sum of individual balances (`bad_debt`), permanently locking LP withdrawals. The equivalent pattern in java-tron is the handling of the global resource-weight counters `TotalNetWeight`/`TotalEnergyWeight`, which are supposed to always equal the sum of all accounts' frozen/delegated balances contributing to bandwidth/energy limits.

### Finding Description
Two independent code paths implement "unfreeze delegated resource" and both must keep `TotalNetWeight`/`TotalEnergyWeight` in sync with individual account balances:

1. `UnfreezeBalanceActuator.execute()` (user-facing transaction path) computes the aggregate decrement carefully. When the receiver's `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` is smaller than the amount being unfrozen (a state divergence explicitly anticipated via `getAllowTvmSolidity059()`), it deliberately sets `oldNetWeight = unfreezeBalance / TRX_PRECISION` before zeroing the receiver field, so that the computed `decrease = newNetWeight - oldNetWeight` still equals the correct amount: [1](#0-0) 

2. `UnfreezeBalanceProcessor.execute()` (native-contract path invoked from the TVM precompile, e.g. when a smart contract calls freeze/unfreeze) performs the receiver-side update via a "safe" clamped subtraction: [2](#0-1) 

but then unconditionally subtracts the full nominal `unfreezeBalance` from the global totals, with no equivalent "decrease" reconciliation logic and no check on whether the receiver's actual field was clamped: [3](#0-2) 

The comment directly above this block — `// adjust total resource, used to be a bug here` — confirms this exact spot in the codebase was previously the source of a total-weight accounting bug: [4](#0-3) 

This is the same root-cause shape as the Vault.vy issue: one code path correctly derives the aggregate adjustment from the *actual* per-account state delta (like `_repay(position_debt_amount)` should have done), while the other path (the TVM native-contract path) blindly applies the *nominal requested* amount (like the buggy `_repay(amount_out_received)` combined with the un-decremented `total_debt_amount`). Whenever the receiver-side field has already diverged from the nominal amount (the scenario the Solidity059 clamp was built to handle), `TotalNetWeight`/`TotalEnergyWeight` will drift away from the true sum of per-account delegated/frozen balances.

### Impact Explanation
`TotalNetWeight` and `TotalEnergyWeight` are the denominators used network-wide to compute every account's bandwidth/energy limit from its frozen TRX. A drift here is a global, protocol-level state-divergence: an under-decrement inflates everyone's per-TRX resource limit (free/underpriced resource issuance across the entire network), while an over-decrement can degrade resource availability for all frozen-TRX holders. Because this counter is a single global value (not user-scoped), a divergence introduced through the TVM-driven path persists indefinitely (like the un-decremented `total_debt_amount` in the report) and cannot be self-corrected by any single account's future actions — matching the "material, permanent divergence" severity bar used in the H-1 judgment.

### Likelihood Explanation
This path is only reachable when: (a) a resource delegation was created and then delegated further/consumed such that the receiver's `AcquiredDelegatedFrozenBalance*` field is smaller than the amount later requested to be unfrozen, and (b) the unfreeze is triggered through the TVM native-contract precompile (`UnfreezeBalanceProcessor`) rather than the ordinary transaction actuator. This is a narrower trigger surface than the Vault.vy case (which fires on every losing trade), so likelihood is lower, and I was unable to fully confirm the exact clamping semantics of `safeAddAcquiredDelegatedFrozenBalanceForBandwidth/Energy` (the implementation body was not retrievable in this session), which is needed to prove the divergence is actually reachable in practice rather than merely defensive/redundant code.

### Recommendation
Mirror the `UnfreezeBalanceActuator` approach in `UnfreezeBalanceProcessor`: compute the receiver's old/new acquired-balance weight before and after the safe/clamped update, and use that measured `decrease` (not the raw `unfreezeBalance`) when calling `repo.addTotalNetWeight(...)`/`repo.addTotalEnergyWeight(...)`, ensuring the global aggregate always reflects the actual state change applied to the receiver account.

### Proof of Concept
Not fully constructible without confirming the exact clamp behavior of `safeAddAcquiredDelegatedFrozenBalanceForBandwidth`/`ForEnergy` in `AccountCapsule.java` (source body not available in this session). The conceptual PoC:
1. Delegate resource A→B for bandwidth, amount X.
2. Cause B's `AcquiredDelegatedFrozenBalanceForBandwidth` to be reduced below X through an intervening state transition (e.g., partial `unDelegateResource` or account type change to `Contract`) without a corresponding adjustment to A's stored delegated amount.
3. Trigger `UnfreezeBalanceProcessor.execute()` for the full delegated amount X via a TVM contract call.
4. Observe `repo.getAccount(B).getAcquiredDelegatedFrozenBalanceForBandwidth()` clamped to 0 (a reduction of less than X), while `TotalNetWeight` is decremented by the full `X / TRX_PRECISION`, causing `TotalNetWeight` to be lower than the true sum of all accounts' effective frozen/delegated balances.
