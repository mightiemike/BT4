## Finding

The Aptos analog of the RAAC "computed-but-not-applied" pattern lives in `TransactionOutput::ensure_match_transaction_info`, which is the sole correctness gate used by the mainnet replay-verify tool (`storage/db-tool/src/replay_on_archive.rs`). Just like the RAAC bug computed a value (`taxAmount`) but skipped applying its effect under a condition, this function is supposed to fully validate that a locally-recomputed `TransactionOutput` matches an authenticated `TransactionInfo`, but it silently omits validating the state-root fields.

### Title
`ensure_match_transaction_info` omits state/hot-state/position checkpoint root validation, defeating replay-verify's divergence detection - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` checks `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash` against the trusted `TransactionInfo`, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
The function's doc/inline comment itself concedes the gap: [2](#0-1) 
It validates transaction status, gas, the write-set hash (`state_change_hash`), and event root hash, but stops there — it never compares the state Merkle root recorded in the trusted `TransactionInfo` (`state_checkpoint_hash`, and future `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against anything computed from the replayed execution.

This function is the exact correctness oracle used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, the tool operators run to replay archived transactions against a target DB and confirm the recomputed ledger state matches what was actually committed/authenticated on-chain: [3](#0-2) 
Note it passes `Some(&expected_writesets[idx])` and `Some(&expected_events[idx])`, i.e., it fully expects `ensure_match_transaction_info` to be the complete divergence check — but that check never inspects the checkpoint hash fields at all, even though those fields are present in `expected_txn_infos[idx]` (the trusted `TransactionInfo`) and are part of the accumulator-hashed, authenticated record. [4](#0-3) 

By contrast, the analogous `TransactionOutputListWithProof::verify` used elsewhere does verify `write_set_hash`, `gas_used`, `status`, and `transaction_hash`, and *also* does not check checkpoint hashes directly — but that path additionally verifies the surrounding accumulator proof against a signed `LedgerInfo`, which is where the checkpoint hash ends up bound cryptographically. `ensure_match_transaction_info`/`replay_on_archive`, in contrast, is specifically the standalone replay tool whose entire job is to catch state divergence for versions where such proof verification isn't independently re-derived from consensus — it just trusts the archived `TransactionInfo` and compares against locally recomputed output.

### Impact Explanation
If local VM execution during a full-history replay produces a different state (Merkle) root than what is recorded in the archived, presumed-authentic `TransactionInfo` — e.g., due to a state-computation bug, a non-deterministic Move/storage bug, or a bug in a newer state-root computation path (state checkpoint, hot-state, or the newly wired-in `position_state_checkpoint_hash` for "trading native" state) — `ensure_match_transaction_info` will still report success because it never looks at `state_checkpoint_hash` at all. The replay-verify tool (`db-tool replay-on-archive`), which is Aptos's primary safety net for catching exactly this class of hard-fork-triggering divergence before/after a network upgrade, would falsely report "all good," masking a real ledger-state corruption or hard-fork condition. This matches the explicitly in-scope "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category.

### Likelihood Explanation
The gap is code-guaranteed today (not merely theoretical): the state-root fields are structurally present in `TransactionInfo` and its `V1` variant, and the comparator function has a branch structure that would trivially need one more `ensure!` block per field, but doesn't have it. The comment in the code itself flags this as a known-but-unaddressed problem ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), meaning the codebase already acknowledges the risk is real once that feature (or any other divergence in state-checkpoint computation) is active — but the fix has not been applied, leaving the primary safety-net tool blind to state-root divergence in the interim and for any future state-checkpoint-hash bug that isn't part of the trading-native rollout.

### Recommendation
Extend `ensure_match_transaction_info` to also verify:
- Recompute the state checkpoint hash for the version (if the transaction is a checkpoint boundary) and `ensure!` it equals `txn_info.state_checkpoint_hash()`.
- Do the equivalent for `hot_state_checkpoint_hash()` (on `TransactionInfoV1`) and `position_state_checkpoint_hash()` once/if those roots are locally computable in the replay context.
- At minimum, until those roots can be independently recomputed by this function, callers like `replay_on_archive.rs` should not treat a "no error" result as proof of full-state equivalence, or should perform the missing checks themselves before enabling any feature that depends on state-checkpoint-hash correctness (as the existing TODO comment already recommends).

### Proof of Concept
Conceptually: run `db-tool replay-on-archive` over a range of versions where a (hypothetical or injected) state-root computation bug causes the locally recomputed Sparse-Merkle-Tree root at a checkpoint boundary to differ from the archived `TransactionInfo.state_checkpoint_hash`, while `write_set`, `events`, `gas_used`, and `status` remain identical (bug only affects root hashing/aggregation, not the write set contents). `execute_and_verify` -> `ensure_match_transaction_info` will return `Ok(())` for every affected version because none of its `ensure!` calls reference `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, so the tool reports a clean, fully verified replay despite the ledger state actually having diverged.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
