## Finding

The tBTC report's core bug class — "a fixed protocol resource ceiling can permanently block inclusion of a transaction representing already-committed/irreversible off-chain value" — has a direct structural analog in this sequencer for L1-to-L2 messages (`L1Handler` transactions).

### Title
Oversized L1-to-L2 message can never be included in any block, permanently freezing bridged funds - (File: `crates/blockifier/src/transaction/transaction_execution.rs`)

### Summary
Every `L1Handler` transaction, after execution, is checked against the bouncer's **fixed** `block_max_capacity` via `verify_tx_weights_within_max_capacity`, not against the *remaining* room in the current block. If an `L1Handler` transaction's execution weights (e.g. `sierra_gas`, `state_diff_size`, `message_segment_length`, `proving_gas`) exceed this fixed cap, it deterministically returns `TransactionTooLarge` every single time it is retried, in every future block, since these values depend only on the transaction's own calldata/entry point and the (static) protocol capacity constants — not on the current block state.

### Finding Description
`Transaction::execute_raw` for both account and `L1Handler` transactions unconditionally calls `verify_tx_weights_within_max_capacity` after execution: [1](#0-0) 

This delegates to `BouncerConfig::within_max_capacity_or_err`, which compares the transaction's own weight to the static `block_max_capacity` (not remaining block room): [2](#0-1) 

This is confirmed by the dedicated regression test `test_transaction_too_large_sierra_gas_based`, which shows `TransactionTooLarge` fires purely because the transaction's resource footprint exceeds `block_max_capacity`, independent of the accumulated block state: [3](#0-2) 

Unlike ordinary account transactions — which are pre-filtered before submission by the gateway's `StatelessTransactionValidator` (`max_calldata_length`, `max_signature_length`, `max_contract_bytecode_size`, `max_l2_gas_amount`, etc.): [4](#0-3) 

`L1Handler` transactions never pass through this stateless gateway validation pipeline at all — they are scraped from L1 events and injected directly into block proposals by the batcher's `ProposeTransactionProvider`/`TransactionManager`, with no size/gas pre-check against the bouncer's `block_max_capacity`: [5](#0-4) 

When such a transaction fails execution/verification, the batcher still records it as "consumed" for the purposes of L1 nonce bookkeeping, but marks it rejected so it goes back to `Pending` and is retried indefinitely: [6](#0-5) [7](#0-6) 

Because the transaction's `TransactionTooLarge` failure mode is deterministic (a pure function of the L1Handler's calldata/entry point and the fixed `block_max_capacity`/`BuiltinInstanceLimits`/`versioned_constants`), retrying it in subsequent blocks cannot change the outcome — the message is permanently stuck as `Pending`, forever failing `verify_tx_weights_within_max_capacity`, with no path to inclusion short of a protocol/versioned-constants upgrade raising `block_max_capacity`.

### Impact Explanation
An L1-to-L2 message (e.g., a bridge deposit calling an L2 contract with a payload that triggers heavy `sierra_gas`/storage/state-diff usage on entry) is emitted by sending a transaction on L1 that locks/burns funds on the L1 side, exactly analogous to a Bitcoin deposit transaction in the tBTC report. If the resulting `L1HandlerTransaction`'s bouncer weights exceed the sequencer's fixed `block_max_capacity` (e.g. `sierra_gas`, `proving_gas`, `state_diff_size`, or `message_segment_length` limits configured in `bouncer_config.block_max_capacity`), the message can never be committed to any Starknet block. Since the L1 side of the bridge already considers the message sent/locked, this results in permanent freezing of the bridged funds/state with no recourse for the L1 sender, mirroring the "depositor loses their deposit entirely" impact described in the tBTC finding.

### Likelihood Explanation
This is reachable by any unprivileged L1 sender simply by calling the L1 bridge/message contract with calldata/logic sized so the resulting `L1HandlerTransaction`'s execution footprint (state diff, sierra gas, message segment, builtin usage) exceeds the sequencer's configured `block_max_capacity` (e.g. `l1_gas: 4400000`, `message_segment_length: 3700`, `sierra_gas: 5000000000`, `proving_gas: 5000000000` in the production batcher config): [8](#0-7) 

No malicious sequencer/operator behavior is required — any legitimate but sufficiently large L1 message triggers this deterministically, since `L1Handler` transactions have no gateway-side size pre-check equivalent to the one applied to RPC account transactions.

### Recommendation
Enforce an `L1Handler`-specific size/resource pre-check (analogous to `StatelessTransactionValidator`'s calldata/signature/gas checks for RPC transactions) at the point the L1 message is scraped/registered in `apollo_l1_events`, so oversized L1-to-L2 messages are flagged or rejected close to origination rather than being retried forever inside the batcher. Additionally, consider exposing L1-side tooling/documentation (mirroring the tBTC recommendation for a deposit-checking UI) so integrators calling L1 bridge contracts can verify in advance that their resulting `L1Handler` transaction fits within `block_max_capacity`.

### Proof of Concept
1. Configure/observe the sequencer's static `bouncer_config.block_max_capacity` (e.g. `sierra_gas`, `state_diff_size`, `message_segment_length` from `replacer_batcher_config.json`).
2. From L1, send a message to L2 (via the L1→L2 message bridge) targeting an L2 entry point whose execution predictably produces bouncer weights exceeding one of these fixed caps (e.g. large calldata causing large `state_diff_size`, or heavy computation causing `sierra_gas`/`proving_gas` to exceed the cap) — see `test_l1_handler`/`test_transaction_too_large_sierra_gas_based` for how weights are computed and compared: [9](#0-8) 
3. Observe that the batcher includes the `L1Handler` transaction in every proposal attempt (`ProposeTransactionProvider::get_l1_handler_txs`), `execute_raw` returns `TransactionTooLarge` every time, the transaction is recorded as rejected and its `TransactionRecord` reverts to `Pending`, and this repeats indefinitely across blocks — the message never gets processed while the corresponding L1 side already treats the message as sent/locked.

    pub fn within_max_capacity_or_err(
        &self,
        weights: BouncerWeights,
    ) -> TransactionExecutionResult<()> {
        if self.block_max_capacity.has_room(weights) {
            Ok(())
        } else {
            Err(TransactionExecutionError::TransactionTooLarge {
                max_capacity: Box::new(self.block_max_capacity),
                tx_size: Box::new(weights),
            })
        }
    }

#[rstest]
fn test_transaction_too_large_sierra_gas_based(block_context: BlockContext) {
    let mut state = test_state(&block_context.chain_info, Fee(0), &[]);
    let mut transactional_state = TransactionalState::create_transactional(&mut state);
    let block_max_capacity = BouncerWeights { sierra_gas: GasAmount(20), ..Default::default() };
    let bouncer_config = BouncerConfig { block_max_capacity, ..Default::default() };

    // Use gas amount > block_max_capacity's.
    let exceeding_gas = GasAmount(30);
    let execution_summary = ExecutionSummary::default();
    let builtin_counters = CairoPrimitiveCounterMap::default();
    let tx_resources = TransactionResources {
        computation: ComputationResources { sierra_gas: exceeding_gas, ..Default::default() },
        ..Default::default()
    };
    let tx_state_changes_keys = transactional_state.to_state_diff().unwrap().state_maps.keys();

    let result = verify_tx_weights_within_max_capacity(
        &transactional_state,
        &execution_summary,
        &builtin_counters,
        &tx_resources,
        &tx_state_changes_keys,
        &bouncer_config,
        &block_context.versioned_constants,
        GasAmount::ZERO,
    )
    .map_err(TransactionExecutorError::TransactionExecutionError);

    let expected_weights = BouncerWeights {
        sierra_gas: exceeding_gas,
        n_txs: 1,
        proving_gas: exceeding_gas,
        ..BouncerWeights::empty()
    };

    assert_matches!(result, Err(
        TransactionExecutorError::TransactionExecutionError(
            TransactionExecutionError::TransactionTooLarge { max_capacity, tx_size }
        )
    )  if *max_capacity == bouncer_config.block_max_capacity && *tx_size == expected_weights);
}

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();

                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",

        }
