### Title
Silent `long` overflow in bandwidth/energy usage accounting (`ResourceProcessor.increase`/`increaseV2`) when the `allowHardenResourceCalculation` guard is not enabled — ([File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java])

### Summary
`ResourceProcessor` computes an account's decayed bandwidth/energy "usage" window (analogous to the LiquidityManager's `node.available`/`node.pending`) by multiplying `lastUsage`/`usage` by `precision` and summing weighted usage*windowSize terms. These operations are performed with raw, unchecked `long` arithmetic unless a governance-gated flag (`allowHardenResourceCalculation`) is enabled, in which case the code switches to `BigInteger`-based exact arithmetic. This mirrors exactly the reported bug class: an accounting sum (`available`/`pending`-equivalent) that silently overflows under normal, unprivileged usage instead of reverting, corrupting resource accounting.

### Finding Description
`ResourceProcessor.increase()`, `increaseV2()`, `getUsage()`, and `getNewWindowSize()` all branch on `hardenCalculation()` [1](#0-0) . When the flag is off (its default until activated by a `ALLOW_HARDEN_RESOURCE_CALCULATION` governance proposal, per `ProposalUtil.java`), the fallback path performs plain `long` multiplication with no overflow detection: [2](#0-1) [3](#0-2) [4](#0-3) 

This is structurally the same defect as the reported `LiquidityManager` issue: an "available + pending"-style accumulator (`averageLastUsage += averageUsage`, `oldUsage*oldWindowSize + newUsage*newWindowSize`) computed with wrap-around native integer math instead of a checked/overflow-safe path. The report's remediation (switching to checked math, e.g., Solidity's post-0.8 default or explicit overflow checks) is precisely what the `hardenCalculation()` branch adds via `BigInteger`/`addExact`/`divideCeilExact`, confirming the maintainers themselves treat the unguarded path as the vulnerable one — the test suite explicitly documents this: `testIncreaseOverflowDetectedWithHardening` throws `ArithmeticException` when hardened, while `testIncreaseOverflowSilentWithoutHardening` passes silently on overflow when not hardened [5](#0-4) .

`increase()`/`increaseV2()` are invoked from `BandwidthProcessor` and `EnergyProcessor` on essentially every transaction that consumes bandwidth or energy, and from `DelegateResourceProcessor`/`UnDelegateResourceProcessor` used by `DelegateResourceActuator`/`UnDelegateResourceActuator` — all reachable by any unprivileged account.

### Impact Explanation
Bandwidth/energy usage values scale with an account's frozen/staked TRX weight and the network's `TotalNetLimit`/`TotalEnergyLimit`, which can be very large (TRX has a large total supply denominated in `sun`, i.e., 6-decimal-precision units, so weight-derived `usage` values for large stakers/exchanges can be large). Multiplying such `usage`/`lastUsage` values by `precision` (a large constant) without an overflow check can wrap a `long`, producing an incorrect (potentially negative or drastically wrong) `averageUsage`/`newUsage`/`newWindowSize`. Because this value directly determines how much bandwidth/energy an account is considered to have consumed (and hence how much it can still consume for free before paying TRX fees, and what window size governs decay), a wrapped value could let an account bypass free-resource limits (underpriced public work / resource-accounting divergence) or corrupt the account's `windowSize` bookkeeping used by subsequent `increase()` calls, leading to persistent incorrect resource-limit accounting for that account.

### Likelihood Explanation
Reaching this path requires no special privilege — it is exercised on the default (un-hardened) production path for ordinary transfers, contract calls, freezing, and resource delegation by any account. The precondition is simply that an account's stake-derived usage numbers are large enough to overflow `long` after multiplication by `precision`/`windowSize`, which is realistic for large TRX holders (exchanges, big stakers) rather than requiring an implausible total-supply assumption, and the flag that would prevent it (`allowHardenResourceCalculation`) is off until a super-representative governance vote enables it, so the vulnerable path is the current default behavior.

### Recommendation
Make the `BigInteger`/exact-arithmetic (`hardenCalculation()`) path the unconditional default in `ResourceProcessor.increase()`, `increaseV2()`, `getUsage()`, and `getNewWindowSize()` rather than gating the fix behind an opt-in governance proposal, so silent overflow cannot occur regardless of whether the proposal has been activated. At minimum, until such governance activation is guaranteed network-wide, add explicit bounds checks on `usage`/`lastUsage`/`precision`/`windowSize` products before performing the plain-`long` multiplication.

### Proof of Concept
The existing test `RepositoryImplHardenTest.testIncreaseOverflowSilentWithoutHardening` already demonstrates the silent-overflow behavior on the un-hardened path with `lastUsage = Long.MAX_VALUE/10` and `usage = 1`, invoking `increase()` and completing without exception (contrast with `testIncreaseOverflowDetectedWithHardening`, which throws `ArithmeticException` under the hardened path) [5](#0-4) . To exploit in production, an account with a sufficiently large frozen-TRX-derived `usage`/weight (achievable by large stakers under normal permissionless freeze/delegate flows) would trigger the same wrap-around inside `ResourceProcessor.increase()`/`increaseV2()` during ordinary bandwidth/energy consumption while `allowHardenResourceCalculation` remains disabled network-wide.

  private long getUsage(long usage, long windowSize) {
    if (hardenCalculation()) {
      return BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize))
          .divide(BigInteger.valueOf(precision)).longValueExact();
    }
    return usage * windowSize / precision;
  }

  private long getUsage(long oldUsage, long oldWindowSize, long newUsage, long newWindowSize) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(oldUsage).multiply(BigInteger.valueOf(oldWindowSize))
          .add(BigInteger.valueOf(newUsage).multiply(BigInteger.valueOf(newWindowSize)));
      return bi.divide(BigInteger.valueOf(precision)).longValueExact();
    }
    return (oldUsage * oldWindowSize + newUsage * newWindowSize) / precision;
  }
