## Title
Floor-division truncation in on-chain order-matching (`MarketSellAssetActuator`/`MarketUtils.multiplyAndDivide`) lets a taker underpay makers, leaking value that compounds across repeated matches - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The external report's bug class — an AMM quote function that uses plain integer division (`(quoteReserve * baseAmount) / baseReserveAfter`) and floors the result, letting a buyer systematically underpay and drain the pool over repeated small trades — has a direct analog in java-tron's on-chain order-book market engine. `MarketSellAssetActuator.matchSingleOrder` relies on `MarketUtils.multiplyAndDivide`, which performs `floorDiv(a*b, c)` (truncating toward zero), to compute the counter-amount owed when consuming a maker order. In two of the three match branches, the **taker receives the maker's full remaining sell-token inventory** while **paying only the floor-rounded (truncated-down) counter-amount**, letting the taker keep the truncation remainder that should have gone to the maker.

### Finding Description
`MarketUtils.multiplyAndDivide` performs simple truncating integer division: [1](#0-0) 

In `MarketSellAssetActuator.matchSingleOrder` (reached by any account broadcasting a `MarketSellAssetContract`, no privilege required), the "taker == maker" branch computes `makerBuyTokenQuantityReceive` — the amount the maker is paid — via this floor division, while `takerBuyTokenQuantityReceive` is set to the maker's *full* remaining sell quantity (unrounded): [2](#0-1) 

The leftover `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive` is credited back to the taker's own order instead of being paid to the maker, even though the taker just consumed the maker's entire remaining inventory. The same pattern repeats in the "taker > maker" branch, where the taker again receives the maker's full remaining sell quantity while paying only the floor-rounded amount: [3](#0-2) 

This mirrors the reported `_getQuoteAmount` flaw exactly: the amount owed by the "buyer" (taker) is computed with floor/truncating division, so the buyer always pays less-than-or-equal to the mathematically correct amount, and the remainder is retained by the buyer rather than the counterparty (maker). Only the "taker < maker" branch rounds against the taker, so an attacker can deliberately structure/crackle their sell order sizes (or place small maker orders as a secondary account) to consistently land in the two branches that favor them.

### Impact Explanation
Each match that hits the "taker == maker" or "taker > maker" branch leaks up to `(makerBuyQuantity/makerSellQuantity)`-scale worth of truncation from the maker to the taker, per match. An attacker who repeatedly creates and crosses many small maker/taker orders (e.g., splitting fills, or using multiple self-controlled accounts as counterparties) can accumulate this truncation loss across many trades, systematically extracting value from the TRC10 exchange/order-book market at the expense of makers — an accounting/asset-corruption issue in the exchange math category, analogous to the reported bonding-curve underpricing exploit and its compounding characteristic.

### Likelihood Explanation
The path is reachable by any account via a standard, unprivileged `MarketSellAssetContract` broadcast transaction — no special permission, leaked key, or malicious peer/node behavior is required. An attacker fully controls the sell/buy token quantities of their own orders and can trivially force matches into the favorable rounding branches, and can act as both taker and (via a second account) maker to guarantee the exploitable branch is hit on demand.

### Recommendation
Compute the counter-amount using a rounding rule that never allows the party consuming the full remaining inventory to underpay — e.g., round the payment *up* (ceiling division) when consuming a maker's full remaining balance, or use exact rational arithmetic (`BigInteger`, as already done elsewhere in `ExchangeWithdrawActuator`) with a consistent rounding policy that always favors the resting maker order rather than the taker. Ensure `takerSellTokenLeft`/similar remainders are never silently returned to the party that received the full countervalue.

### Proof of Concept
1. Maker places an order: sell `makerSellQuantity` of token A for `makerBuyQuantity` of token B, where `makerBuyQuantity` does not evenly divide `makerSellQuantity` (e.g., sell 3 A for 2 B).
2. Attacker (taker) places a matching sell order for exactly the amount of B computed to fully consume the maker's inventory, landing in the `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch of `matchSingleOrder` (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:418-439`).
3. `makerBuyTokenQuantityReceive = multiplyAndDivide(3, 2, 3, ...) = floor(6/3) = 2` (exact in this trivial example, but for non-integer ratios the floor drops the fractional remainder).
4. Taker receives all `3` A tokens (`takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()`), but only pays the floor-rounded `makerBuyTokenQuantityReceive`, keeping `takerSellTokenLeft = original sell amount - makerBuyTokenQuantityReceive` in their own order for reuse.
5. Repeating this against many small maker orders accumulates the truncation remainder in the attacker's favor across the order book, compounding losses to makers over time — the same "repeated small buys exploit rounding" mechanic described in the source report.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);

      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger cBig = BigInteger.valueOf(c);
