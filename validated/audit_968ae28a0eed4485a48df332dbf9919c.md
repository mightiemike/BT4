## Analog Found

### Title
Incomplete Account-Deletion Cleanup Leaves Postponed Receipts / Received-Data / PromiseYield State That Executes Against a Reused Account ID - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account`, the routine invoked by `action_delete_account` to erase an account's on-chain footprint, only clears the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries. It leaves behind every trie entry keyed by the same `account_id` under the `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, and `DATA_ID_TO_YIELD_ID` columns. This is the same bug class as CVE-2019-12902: incomplete cleanup on deletion lets a subsequent entity created under the same identifier inherit/interact with the deleted entity's residual data.

### Finding Description
`remove_account` in [1](#0-0)  removes only four trie-key families, then iterates and removes access keys/gas-key nonces [2](#0-1)  and contract data [3](#0-2) . It never touches the receipt-plumbing columns defined in the trie-key column table [4](#0-3)  and [5](#0-4) , all of which are namespaced per-`account_id` (confirmed by `COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, [6](#0-5) ).

`action_delete_account`, [7](#0-6) , only validates storage-usage cap and gas-key burn amount before calling `remove_account` — there is no check that the account has no outstanding `PostponedReceipt`, `ReceivedData`, or `PromiseYield` state, and the documented error conditions confirm this (`InvalidAccountId`, `DeleteActionMustBeFinal`, `DeleteAccountStaking` only) [8](#0-7) .

Consequently, if an account has in-flight cross-contract-call dependencies (a `FunctionCall` receipt awaiting `promise.then`/`promise.and` results, or a `yield`/`resume`) at the moment it is deleted, the corresponding postponed-receipt bookkeeping remains keyed to that `account_id` in the trie. If a new account is subsequently created with the identical `account_id` (always possible for the deleter's own subaccounts, and in principle for any account_id whose namespace becomes available again, e.g. via registrar-controlled top-level names or implicit-account derivation), the runtime's postponed-receipt dispatch logic — which looks up `PostponedReceipt`/`ReceivedData` purely by `account_id`/`receipt_id`, independent of any generation/incarnation counter — will later execute the stale receipt against the *new* account's live state (its current contract code, storage, and balance), since `Account`-level identity has no epoch/incarnation nonce distinguishing "old alice" from "new alice".

### Impact Explanation
An attacker can create an account, initiate a cross-contract promise chain that leaves a `PostponedReceipt`/pending `ReceivedData` dependency in the trie under that account's ID, delete the account (bypassing any pending-receipt check), and immediately recreate an account with the same ID with different contract code/keys. When the originally-awaited data eventually arrives, the runtime dispatches the stale postponed action receipt against the new account's current trie state rather than treating it as orphaned. This can cause the new account's contract/storage to be mutated by actions the new account owner never authorized, execute `FunctionCall`/`Transfer` actions carrying already-committed deposits against unintended contract logic, or — where account-name reuse is possible across distinct owners (e.g. top-level names freed by the registrar) — allow injected receipts to execute against a completely different party's account, resulting in unauthorized state mutation / value movement and a state-transition divergence between nodes that correctly track versus incorrectly assume clean deletion.

### Likelihood Explanation
Reachable entirely from ordinary transaction/receipt submission: any signer can (a) issue a cross-contract call chain that creates a `PostponedReceipt`/pending data dependency on one of its own accounts, (b) submit a `DeleteAccountAction` as the final action (no check blocks deletion while receipts are pending), and (c) submit a `CreateAccountAction` recreating the same `account_id`. No validator, node-operator, or privileged role is required for the self-account case; the cross-owner case is likelihood-gated only by name-reuse availability (registrar-controlled or implicit-account patterns), so this is assessed as Medium likelihood, Medium-High impact once triggered.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to also enumerate and delete all `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie entries for the account being deleted, or alternatively reject `DeleteAccountAction` outright (a new `ActionErrorKind`) if any such pending entries exist for the account, mirroring the existing `DeleteAccountStaking` guard in `action_delete_account` (`runtime/runtime/src/actions.rs`).

### Proof of Concept
1. Deploy a contract on `sub.attacker.near` (subaccount, fully attacker-controlled) that, in method `start`, issues a cross-contract call to a slow/external contract and chains `.then(self::finish)`, creating a `PostponedReceipt` + `ReceivedData` dependency keyed to `sub.attacker.near`.
2. Before the dependency resolves, submit a `DeleteAccountAction` receipt deleting `sub.attacker.near` (beneficiary = attacker.near). Deletion succeeds — no check inspects postponed-receipt state.
3. Immediately submit a `CreateAccountAction` + `DeployContractAction` recreating `sub.attacker.near` with new/different code and full-access keys.
4. Let the originally-awaited data arrive (the external contract responds). The runtime finds the still-present `PostponedReceipt`/`PendingDataCount` under `sub.attacker.near` and executes `finish` against the *new* account's current state/contract, demonstrating execution of stale, unauthorized actions against a reused account identity.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}
