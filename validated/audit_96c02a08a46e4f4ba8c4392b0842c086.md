## Title
`ensure_match_transaction_info` skips verifying `state_checkpoint_hash` (and hot/position-state hashes), letting replay/verify tooling accept a diverged state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling to confirm that a locally re-executed transaction matches the transaction result that was actually committed to the ledger (and authenticated via consensus signatures / accumulator proofs). It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash — but it never checks `txn_info.state_checkpoint_hash()` (the Sparse Merkle Tree root of world state), nor `hot_state_checkpoint_hash`, nor `position_state_checkpoint_hash`. This gap is explicitly acknowledged in a `TODO(trading-native)` comment immediately preceding the `Ok(())` return. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` computes and compares:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash = CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- `event_root_hash` (from `InMemoryEventAccumulator`) vs `txn_info.event_root_hash()` [2](#0-1) 

It then returns `Ok(())` without ever reading `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, or `position_state_checkpoint_hash` — fields that exist precisely to bind a `TransactionInfo` (and, by extension, the accumulator-committed, consensus-signed ledger) to the resulting Sparse Merkle Tree / native-position state root: [3](#0-2) 

This comparator is not a debug-only helper; it's wired into the code paths whose entire purpose is state-integrity verification:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, used during backup-restore replay verification (`storage/backup/backup-cli/.../replay_verify.rs`) and state-sync chunk replay. [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs`, the dedicated tool operators run to detect state divergence when replaying an archived chain against a candidate VM/build.
- `aptos-move/cli/src/commands.rs`, used to sanity-check a single replayed transaction. [5](#0-4) 

Meanwhile `state_checkpoint_hash` is exactly the root that the executor computes deterministically at checkpoint boundaries via `DoStateCheckpoint::run`, and is meant to be the authenticated binding between execution and the persisted Sparse Merkle Tree / Jellyfish Merkle state: [6](#0-5) 

Because `ensure_match_transaction_info` never re-derives and compares this hash (nor the hot-state / native-position checkpoint hashes introduced by `TransactionInfoV1`), any of the following go undetected by this specific check:
- A locally computed world-state root that diverges from the one actually committed/signed on-chain (e.g. due to non-determinism, a state-store bug, or a hard-fork-only execution divergence) will still pass `ensure_match_transaction_info`, because only the write-set hash and event root are checked, not the resulting SMT root.
- Enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (native-position state root) makes this worse: a diverging native-position Merkle root is explicitly called out by the code's own comment as something this comparator will not catch.

### Impact Explanation
This breaks the state-commitment/proof-integrity guarantee that replay and verify-execution tooling is supposed to enforce: that a node's local re-execution of history reproduces the exact ledger state (not just the write set and events, but the resulting authenticated state root) recorded by consensus. A state-root divergence is one of the most severe classes of bug (silent chain-state corruption / hard-fork-causing non-determinism), and the primary automated safety net for catching it during backup-restore replay-verify and archive replay-verify (`replay_on_archive`, `replay_verify` coordinators) is a no-op for this specific field. This matches the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "committed state that differs from the correct VM result" impact categories: divergence would go undetected by the designated verification pathway until much later (e.g., a live consensus fork), rather than being caught by the archive/backup replay-verify process meant to catch exactly this class of bug pre-emptively.

### Likelihood Explanation
The gap is triggered any time `ensure_match_transaction_info` is used as the sole state-integrity oracle — i.e., every invocation of `chunk_executor::verify_execution` (backup-restore verify-execution mode) and `db-tool replay-on-archive`. It requires no attacker action; it is a latent verification blind spot that manifests whenever local execution state legitimately diverges from the recorded ledger state (from any root cause — non-determinism, a storage bug, a native-position/hot-state computation bug), silently reporting success instead of surfacing the divergence.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the corresponding locally-derived roots before returning `Ok(())`, matching the pattern already used for `write_set_hash` and `event_root_hash`. This should be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, per the existing TODO, but the `state_checkpoint_hash` comparison for the base (non-trading-native) SMT root should be added independent of that feature flag, since it is also currently unchecked.

### Proof of Concept
Not applicable as an exploit PoC (no attacker-controlled trigger); this is a code-inspection finding. Demonstration path: run `replay_on_archive`/backup `replay_verify` against a version whose locally re-executed state has a `state_checkpoint_hash` different from the one recorded in the backed-up `TransactionInfo` (e.g., by mutating persisted state at that version, or by injecting a deterministic-execution bug into the write-application path) — `ensure_match_transaction_info` will still return `Ok(())` because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared, at `types/src/transaction/mod.rs:2139-2204`.

**Caveat**: I could not retrieve version-control history (blame/commit log) for this file, so I cannot confirm whether the state_checkpoint_hash comparison ever existed and was removed, or whether this has always been absent. The `TODO(trading-native)` comment indicates the omission is at least partly known to the maintainers as pending work tied to the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature, but the comment itself concedes the check is missing for `state`/`hot-state` roots as well, not only the new native-position root.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
