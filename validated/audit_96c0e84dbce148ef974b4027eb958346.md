### Title
Unbounded full-store scan in `GetAssetIssueListServlet`/`Wallet.getAssetIssueList()` enables cost-asymmetric DoS - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueListServlet.java])

### Summary
`GetAssetIssueListServlet.doGet`/`doPost` calls `Wallet.getAssetIssueList()`, which iterates the entire `AssetIssueStore` via `AssetIssueStore.getAllAssetIssues()` on every single request, with no pagination or size cap. As TRC10 asset count grows, each request's CPU/serialization cost grows linearly while the rate limiter still only throttles by request count (QPS), not by backend cost, creating an amplification vector for an unprivileged HTTP client.

### Finding Description
`GetAssetIssueListServlet` extends `RateLimiterServlet` and forwards both GET and POST to `wallet.getAssetIssueList()` [1](#0-0) . That method ultimately reaches `AssetIssueStore.getAllAssetIssues()`, which performs a full unindexed iteration of the underlying store and collects every capsule into a `List` with no limit or offset applied [2](#0-1) . Unlike the paginated variant (`getAssetIssuesPaginated`, which caps `limit` at `ASSET_ISSUE_COUNT_LIMIT_MAX`) [3](#0-2) , the plain `getAllAssetIssues()` path used by `getAssetIssuelist` has no such cap.

The only gate in front of this handler is the generic rate limiter framework (`RateLimiterServlet.service`), which by default applies `DefaultBaseQqsAdapter`/`QpsStrategy` with a global default of `qps=1000` unless a per-servlet override is configured in `rate.limiter.http` [4](#0-3) [5](#0-4) . No per-servlet override for `GetAssetIssueListServlet` is present in the default config, so this endpoint receives only the generic count-based throttle, which is agnostic to the backend cost of each request.

I could not confirm the specific claim in the question about `BandwidthProcessor.updateUsage()` being invoked per capsule for this read-only query path — I found no evidence in the reachable code that this GET/POST query handler triggers bandwidth accounting (bandwidth/energy accounting applies to broadcast transactions, not simple wallet queries), so that portion of the described mechanism is unsupported by the code I was able to inspect.

### Impact Explanation
This matches a DoS-via-RPC-API class impact: a request that is cheap for the client (bounded only by QPS count) triggers backend work that scales linearly with total TRC10 asset count in the store. On a long-lived network where thousands of TRC10 tokens have accumulated (historically cheap to issue), sustained concurrent calls to `/wallet/getassetissuelist` can consume disproportionate CPU/memory on the RPC-API thread pool relative to the attacker's request rate, degrading availability for other API consumers.

### Likelihood Explanation
Reaching the vulnerable path requires no privilege — any anonymous HTTP client can call `/wallet/getassetissuelist` [1](#0-0) . The precondition of "large AssetIssueStore" is largely outside the attacker's direct control at low cost: growing it substantially via self-issuance requires paying the TRC10 asset-issuance fee for each new asset, which is a real economic cost per entry, so an attacker cannot cheaply inflate the store size on demand — they are limited to whatever asset count already exists organically. This weakens the "cheap input, unbounded cost" characterization somewhat, since the amplification factor is fixed by existing chain state rather than freely attacker-controlled, though it is still a legitimate structural asymmetry once the store is large.

### Recommendation
Apply pagination/limits to the non-paginated `getAssetIssuelist`/`getAllAssetIssues` API path (or deprecate it in favor of `GetPaginatedAssetIssueListServlet`), and/or configure a stricter per-endpoint rate limit (e.g., `IPQPSRateLimiterAdapter` with low QPS) for `GetAssetIssueListServlet` in `rate.limiter.http`, similar to the documented example for `GetAccountServlet`.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
