### Title
Unbounded blocking `RateLimiter.acquire()` in `QpsStrategy` under sustained over-QPS traffic can exhaust the shared Jetty servlet thread pool, halting the HTTP/JSON-RPC API for all other unprivileged callers - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/strategy/QpsStrategy.java])

### Summary
When `rate.limiter.apiNonBlocking = false` (the shipped default value), `IRateLimiter.acquirePermit()` routes to `acquire()` instead of `tryAcquire()`, and for `QpsRateLimiterAdapter`/`DefaultBaseQqsAdapter`-backed endpoints this calls Guava's `RateLimiter.acquire()` with no timeout. Unlike `GlobalPreemptibleStrategy.acquire()`, which bounds its wait to `DEFAULT_ACQUIRE_TIMEOUT` (2 seconds), `QpsStrategy.acquire()` blocks the calling servlet thread indefinitely, and Guava's smooth-bursty algorithm's required sleep time grows without bound as sustained excess demand accumulates queuing debt.

### Finding Description
- `IRateLimiter.acquirePermit()` dispatches to `acquire(data)` when `Args.getInstance().isRateLimiterApiNonBlocking()` is `false`: [1](#0-0) 
- The default value of this switch in the shipped configuration is `false` (blocking mode): [2](#0-1) 
- `QpsRateLimiterAdapter.acquire()` delegates to `QpsStrategy.acquire()`: [3](#0-2) 
- `QpsStrategy.acquire()` calls Guava's `RateLimiter.acquire()` with **no timeout at all**, unconditionally returning `true` once the (possibly very long) wait completes: [4](#0-3) 
- This is inconsistent with the sibling `GlobalPreemptibleStrategy`, whose `acquire()` explicitly bounds the wait to `DEFAULT_ACQUIRE_TIMEOUT` (2 seconds) and fails closed on timeout: [5](#0-4) 
- Every HTTP servlet extending `RateLimiterServlet` invokes `rateLimiter.acquirePermit(runtimeData)` synchronously on the request-handling thread before proceeding to `super.service()`: [6](#0-5) 
- All servlets for a given `HttpService` (e.g. FullNode HTTP API on port 8090) share a single Jetty `Server` instance created via `new Server(this.port)`, which uses Jetty's default bounded `QueuedThreadPool` (no custom pool is configured in `HttpService.initServer()`): [7](#0-6) 
- Any endpoint without an explicit per-endpoint strategy in `rate.limiter.http`/`rate.limiter.rpc` falls back to `QpsRateLimiterAdapter` with `qps=1000` (`global.api.qps`), as documented in the config comments: [8](#0-7) 

Attack flow: an unprivileged remote client sends valid, low-cost requests (e.g., `GET /wallet/getnowblock` or any endpoint using `QpsRateLimiterAdapter`) at a rate sustained just above the configured/default QPS. Each excess request calls `acquirePermit()` → `acquire()` → Guava `RateLimiter.acquire()`, which computes an ever-growing "reserve and sleep" delay because the requests keep arriving faster than tokens are replenished; the calling servlet thread parks in `Thread.sleep()` for that duration. Because the thread pool backing that `Server` instance is shared across all servlets registered on that port/context, once enough concurrent excess requests are in-flight the fixed-size Jetty thread pool is saturated with threads parked in `acquire()`, and legitimate requests to *other* unrelated endpoints on the same `HttpService` instance (same port) cannot be dispatched (Jetty will queue and eventually reject new connections once its accept/thread pool is exhausted). No auth, accounting, or cost guard interrupts this because rate limiting itself is the mechanism causing the blocking, and there is no per-request deadline applied to the blocking wait.

### Impact Explanation
Sustained crafted-but-otherwise-valid low-cost traffic from a single unprivileged attacker can degrade or halt the HTTP/JSON-RPC surface for all other callers sharing the same `HttpService` port (e.g., FullNode `wallet/*` API on 8090, or JSON-RPC on 8545), since Jetty's default thread pool is shared across all servlets registered in that context. This is a production availability impact scoped to a single node's HTTP surface — a resource-exhaustion-induced denial of service against a public API, not against consensus or funds.

### Likelihood Explanation
- Preconditions: `rate.limiter.apiNonBlocking = false`, which is the value shipped in `reference.conf` (default) — no admin misconfiguration is needed to hit this path. [9](#0-8) 
- Any endpoint that relies on `QpsRateLimiterAdapter` (explicitly configured or via the documented default fallback) is affected.
- The attacker needs only unauthenticated HTTP access and the ability to sustain concurrent connections above the configured QPS — a low-cost, easily repeatable condition requiring no special privileges or cryptographic material.
- Feasibility is high: standard load-testing/flooding tools suffice; no race condition or timing precision is required, only sustained volume.

### Recommendation
Bound the blocking wait in `QpsStrategy.acquire()` analogous to `GlobalPreemptibleStrategy` (e.g., use `RateLimiter.tryAcquire(timeout, unit)` with a small, configurable timeout and fail closed / return `false` on expiry so `RateLimiterServlet`/`RateLimiterInterceptor` can reject the request instead of holding the thread indefinitely). Additionally, consider decoupling the blocking wait from the servlet-container's I/O thread (e.g., via Jetty async servlet support or a dedicated bounded executor for rate-limited waits) so that a saturated queue for one endpoint cannot starve the shared thread pool used by unrelated endpoints.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/services/ratelimiter/strategy/QpsStrategyBlockingDosTest.java
package org.tron.core.services.ratelimiter.strategy;

import java.util.concurrent.*;
import org.junit.Assert;
import org.junit.Test;

public class QpsStrategyBlockingDosTest {

  @Test
  public void sustainedOverQpsTrafficParksThreadsIndefinitely() throws Exception {
    // qps=1 -> only one permit per second; GlobalPreemptibleStrategy would bound wait to 2s,
    // QpsStrategy.acquire() has no such bound.
    QpsStrategy strategy = new QpsStrategy("qps=1");

    int threadPoolSize = 8; // simulate a small Jetty QueuedThreadPool
    ExecutorService pool = Executors.newFixedThreadPool(threadPoolSize);
    CountDownLatch started = new CountDownLatch(threadPoolSize);
    CountDownLatch release = new CountDownLatch(1);

    // Saturate the pool with "excess" requests all blocked in acquire()
    for (int i = 0; i < threadPoolSize; i++) {
      pool.submit(() -> {
        started.countDown();
        strategy.acquire(); // blocks - no timeout
      });
    }

    Assert.assertTrue(started.await(1, TimeUnit.SECONDS));

    // Attempt to submit a "legitimate" unrelated task to the same pool;
    // it should be rejected/queued indefinitely because all threads are parked in acquire().
    Future<Boolean> healthCheck = pool.submit(() -> true);
    try {
      healthCheck.get(500, TimeUnit.MILLISECONDS);
      Assert.fail("expected timeout: pool is saturated by blocked acquire() calls");
    } catch (TimeoutException expected) {
      // demonstrates thread-pool exhaustion / halted "other endpoint" processing
    }

    pool.shutdownNow();
  }
}
```
Expected assertion: the health-check/other-endpoint task times out while all pool threads remain parked inside `QpsStrategy.acquire()`, demonstrating that a fixed-size thread pool backing `RateLimiterServlet`/`HttpService` can be exhausted by sustained just-above-QPS traffic when `rate.limiter.apiNonBlocking=false` (the default), confirming the invariant violation that crafted valid input can halt a public production HTTP flow for other unprivileged callers.
