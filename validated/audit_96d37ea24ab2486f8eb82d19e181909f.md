### Title
Unconditional relayer fee payment before verifying underlying wallet-contract transfer succeeds - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract's `inner_rlp_execute` schedules the relayer's fee payment as an independent promise, created and dispatched before (and not chained to) the promise that actually performs the user's intended transfer (base-token transfer or emulated ERC-20 `ft_transfer`). If that later transfer promise fails, only the `caller_deposit` is refunded in `rlp_execute_callback` — the fee already paid to the relayer is never clawed back. This mirrors the reported Solidity bug class: an "effect" (payment/emission) is committed without checking the return value/success of the operation it is supposed to be conditioned on.

### Finding Description
In `inner_rlp_execute`, when the parsed transaction is an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, a transfer promise to the relayer (`context.predecessor_account_id`) is created unconditionally and immediately via `env::promise_batch_create` / `env::promise_batch_action_transfer`: [1](#0-0) 

This fee-payment promise is a *separate, unlinked* promise batch — it is not `.then()`-chained to, nor gated by, the outcome of the promise that performs the actual value transfer, which is constructed afterward in the same function: [2](#0-1) 

The only failure-handling path, `rlp_execute_callback`, checks `env::promise_result(0)` (the result of the *main* transfer promise) and on `PromiseResult::Failed` refunds only the `caller_deposit` (the attached NEAR deposit of the call) — it does not, and cannot, undo the fee promise that already executed as an independent receipt: [3](#0-2) 

The `tx_fee` is computed directly from the user-signed Ethereum transaction's `max_fee_per_gas * gas_limit` in `parse_rlp_tx_to_action`: [4](#0-3) 

This is functionally analogous to the reported pattern of not checking a `transferFrom` return value before performing an action (emitting an event) that implies success: here, the wallet contract pays out value to the relayer without verifying that the corresponding user-intended transfer (the "transferFrom"-equivalent action) actually completed successfully.

### Impact Explanation
A relayer (an unprivileged party that merely needs to submit the signed Ethereum-style transaction wrapped in a NEAR `FunctionCall` to `rlp_execute`) can cause or observe conditions where the underlying `ft_transfer`/base transfer fails (e.g., insufficient NEP-141 balance, receiver storage registration issues, or a cross-contract call gas/panic failure) while still collecting the fee that was meant to compensate them only for successfully relaying a valid transfer. This is an unauthorized value movement / fee bypass: the user's fee-designated funds are paid out even though the service (the delivered transfer) was not rendered, and the loss is not recoverable through the existing refund path (which only restores `caller_deposit`, a distinct value from the relayer fee). Because access to this path only requires an access key scoped to `rlp_execute` (as configured in the existing wallet-contract test flow), a relayer or a compromised/malicious relayer economically extracts value beyond what a strict "pay-on-success" design would allow.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires no privileged access — any relayer holding a `FunctionCallPermission` access key for `rlp_execute` (the intended, documented usage pattern for this contract) can trigger it by submitting transactions expected to fail the underlying transfer (e.g., targeting an unregistered/underfunded token balance or a target that fails post-registrar-check validation), while a non-zero `fee` is present in the signed transaction. The code path is reached directly from a standard NEAR `FunctionCall` action, i.e., a single submitted transaction.

### Recommendation
Chain the relayer fee-payment promise to occur only after (and conditioned on) success of the main transfer/`ft_transfer` promise, e.g., attach it via `.then()` in the callback after checking `PromiseResult::Successful`, or fold the fee transfer into the same `rlp_execute_callback` logic so it is only dispatched when `env::promise_result(0)` is `Successful`. Alternatively, treat the fee like `caller_deposit`: track it explicitly and only release it to the relayer inside `rlp_execute_callback`'s success branch, refunding/withholding it in the `Failed` branch analogous to how `caller_deposit` is already handled.

### Proof of Concept
1. Deploy the Wallet Contract as in the existing test harness (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs`, `test_erc20_emulation`/`test_base_token_transfer_with_relayer_refund`).
2. As a relayer holding an `rlp_execute`-scoped access key, submit a signed Ethereum-style ERC-20 `transfer` (or base-token transfer) with `gas_price`/`gas_limit` computed to produce a non-zero `tx_fee` (per `internal::parse_rlp_tx_to_action`), targeting a token contract where the wallet's NEP-141 balance is insufficient to cover the requested `amount` (guaranteeing `ft_transfer` fails).
3. Observe that `inner_rlp_execute` creates and dispatches the relayer-fee transfer promise unconditionally (lines 374-385) before the `ft_transfer` promise executes and fails.
4. Confirm on-chain that the relayer's balance increased by the fee amount even though `rlp_execute_callback` (lines 296-317) returns `success: false` and only refunds `caller_deposit`, not the fee — demonstrating value was paid out despite the "transferFrom"-equivalent operation failing.

    // Compute the fee based on the user's Ethereum transaction.
    // This is sent as a refund to the relayer in the case of an emulated base token
    // transfer or ERC-20 transfer. The reason for this refund is that it allows a
    // user with $NEAR to use a relayer service from their wallet immediately without
    // additional on-boarding.
    let tx_fee = {
        // Limit the cost by `VALUE_MAX` since we will convert this to a $NEAR amount.
        // The call to `low_u128` is safe because `VALUE_MAX` is the largest accepted value.
        let wei_amount = tx.max_fee_per_gas.saturating_mul(tx.gas_limit).min(VALUE_MAX).low_u128();
        NearToken::from_yoctonear(wei_amount.saturating_mul(MAX_YOCTO_NEAR as u128))
