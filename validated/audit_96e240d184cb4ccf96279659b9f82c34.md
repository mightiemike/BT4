### Title
Cairo0 compiled-class cache trusts stale reverted-block entries without re-validating declaration status - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
The bug class in the external report (FUXA CVE-2026-65984) is a stale-authorization pattern: a privileged decision is re-derived from a cached/decoded value instead of re-checking the current authoritative record, letting a revoked/deleted entity keep acting as if still valid. The sequencer has a structurally identical pattern in `get_compiled_from_class_manager`: cached Cairo1 classes are re-validated against current chain state on every read, but cached Cairo0 (deprecated) classes are explicitly exempted from that re-validation, even though the surrounding comment documents that cache entries can originate from a reverted block.

### Finding Description
`StateReaderAndContractManager::get_compiled_from_class_manager` looks up a class in the process-local `ContractClassManager` cache. If found, it branches on the runnable class variant: [1](#0-0) 

For `RunnableCompiledClass::V0(_)` (deprecated/Cairo0 classes) the code takes the empty match arm and returns the cached class immediately — no call to `self.state_reader.is_declared(class_hash)`. For every other variant (Cairo1), the code explicitly re-checks `is_declared` before trusting the cache, with the comment: "existence in the cache does not guarantee [declaration], since it might contain a declared class from a reverted block". This re-validation logic is the direct analog of FUXA's missing "does the current DB record still show this privilege" check before re-trusting `decoded.groups`. Here, the "current DB record" is `state_reader.is_declared`, and the "decoded/cached claim" is the warm entry in `ContractClassManager`'s process-local `RawClassCache`.

`ContractClassManager` populates its cache during block-building/validation attempts (via `set_and_compile`) whenever a class is compiled, which happens before a proposal is known to reach consensus finality. If a proposal containing a Cairo0 declare is discarded (fails consensus, is a losing/duplicate round, or a validator merely attempted validation without commit), the class is never persisted into committed state, so `is_declared` (backed by durable storage) would correctly return `false`. But the compiled Cairo0 entry remains warm in the node's local cache indefinitely (it's a size-bound LRU, not tied to block finality), because Cairo0 lookups never consult `is_declared` again. [2](#0-1) 

### Impact Explanation
Because only the node(s) that happened to compile/cache that specific Cairo0 class during the reverted round retain the stale entry, a subsequent transaction (e.g. `library_call`, `replace_class`, or any execution path that resolves a Cairo0 class hash through `get_compiled_class`) referencing that class hash will:
- Succeed on a sequencer with the warm cache (returns the stale compiled class, treating it as declared),
- Fail with `StateError::UndeclaredClassHash` on any honest node without that warm cache entry (freshly started node, node that evicted the LRU entry, or one that never attempted the reverted round).

This produces divergent execution results (success vs. rejection, different state diffs) for the same transaction across honest sequencers, which can manifest as inconsistent state commitments / block hashes between nodes — an honest-node divergence condition. It also lets an attacker's transaction execute against a class that was never actually accepted into committed state, an unauthorized state transition analogous to the FUXA report's "continued unauthorized action after the backing record no longer supports it."

### Likelihood Explanation
Reaching this path requires only ordinary, attacker-triggerable actions: submitting a Cairo0 declare transaction (deprecated declares are still accepted by `check_declare_permissions`/stateless validation) inside a proposal, timed so that the proposal round is discarded or loses consensus (a routine, frequent occurrence in Tendermint-style consensus under contention, not requiring a malicious operator), followed by a second transaction from any account referencing the same class hash. No special privilege is required beyond being a normal transaction submitter, and the reverted-cache scenario is explicitly anticipated by the developers' own comment for the Cairo1 branch — it was simply never extended to Cairo0.

### Recommendation
Remove the special-cased exemption for `RunnableCompiledClass::V0` in `get_compiled_from_class_manager`: perform the same `state_reader.is_declared`-equivalent check for Cairo0 classes (or a Cairo0-specific "deprecated declared" existence check) before trusting a cache hit, so that all cached classes — regardless of Cairo version — are re-validated against current, committed chain state rather than a process-local cache that can retain entries from non-finalized/reverted rounds.

### Proof of Concept
1. Node A (proposer) builds a block proposal containing `DeclareTransaction` `D` for a Cairo0 class `C` (class_hash `h`). During block building, `ContractClassManager::set_and_compile(h, ...)` populates Node A's warm cache via `get_compiled_from_class_manager`'s miss path.
2. The proposal is not finalized (e.g., loses the round to a competing proposer, or fails a subsequent consensus step), so `h` is never written to committed storage; `state_reader.is_declared`-backed checks for `h` return false/absent on all nodes, including Node A's durable storage.
3. A later, finalized block includes a transaction `T` (from any account) that resolves class hash `h` via `get_compiled_class` (e.g., a `library_call` to `h`, or a contract whose class was previously validly deployed being replaced to `h` via `replace_class`).
4. On Node A: `get_compiled_from_class_manager` hits the warm cache, matches `RunnableCompiledClass::V0(_)`, skips the `is_declared` check, and returns the cached compiled class — `T` executes successfully using code for a class that was never actually declared in committed state.
5. On Node B (no warm cache for `h`, e.g. it never attempted the losing round or restarted): the cache misses, `state_reader.get_compiled_classes(h)` is invoked against durable storage, which reports `UndeclaredClassHash(h)` — `T` fails.
6. Nodes A and B now disagree on the execution outcome (and resulting state diff/receipts) for the same finalized block, demonstrating the divergence induced by the stale, unrevalidated Cairo0 cache entry.
