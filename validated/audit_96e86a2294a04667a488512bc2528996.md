### Title
`DelegateAction` Signed Payload Omits Chain ID, Enabling Cross-Chain Replay of Meta Transactions — (`File: core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

---

### Summary

`DelegateAction` (NEP-366 meta transactions) signatures are computed over a payload that contains no chain identifier. A `SignedDelegateAction` produced for testnet is cryptographically valid on mainnet (and vice versa) whenever the same account and key exist on both chains with a still-valid nonce. Any observer of a submitted testnet meta transaction can extract the inner `SignedDelegateAction` and replay it on mainnet inside a fresh outer transaction.

---

### Finding Description

`DelegateAction::get_nep461_hash()` constructs the signed payload as:

```
SHA-256( borsh( MessageDiscriminant(NEP-366) || DelegateAction ) )
``` [1](#0-0) 

`DelegateAction` itself carries `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`: [2](#0-1) 

`SignableMessage` — the wrapper that produces the bytes that are hashed — contains only a `discriminant` and the message body. There is no `chain_id` field anywhere in the structure: [3](#0-2) 

The discriminant is a fixed constant derived from the NEP number (366), identical on every NEAR network: [4](#0-3) 

By contrast, a regular `SignedTransaction` includes a `block_hash` field that ties it to a specific chain's block history, making cross-chain replay impossible for ordinary transactions: [5](#0-4) 

`DelegateAction` has no equivalent anchor. The `max_block_height` field provides expiry but block heights on mainnet and testnet are numerically similar, so a testnet action with `max_block_height = 130_000_000` is also valid on mainnet at the same height range.

At execution time, `apply_delegate_action` verifies the signature via `signed_delegate_action.verify()`, checks the nonce, and checks `max_block_height`, but performs no chain-identity check: [6](#0-5) 

`SignedDelegateAction::verify()` only checks the NEP-461 hash, which — as shown above — contains no chain ID: [7](#0-6) 

---

### Impact Explanation

An attacker who observes a `SignedDelegateAction` on testnet (it is public once the outer transaction is included in a block) can:

1. Extract the `SignedDelegateAction` bytes from the testnet transaction.
2. Construct a new mainnet `SignedTransaction` wrapping the same `SignedDelegateAction`.
3. Submit it to mainnet.

If the `sender_id` account exists on mainnet with the same public key and a nonce lower than the one in the delegate action, the runtime will accept and execute the inner actions — transfers, function calls, key additions/deletions — on mainnet, even though the user only authorized them on testnet.

Affected impacts from the allowed gate: **unauthorized transaction**, **stealing or loss of funds** (if the inner actions include a `Transfer` or a contract call that moves tokens), **balance manipulation**.

---

### Likelihood Explanation

NEAR mainnet and testnet share the same account-ID namespace. Many developers and users deliberately use the same named account and the same key pair on both networks. Nonces on a freshly-created mainnet account start at 0, so any testnet `DelegateAction` with a low nonce is immediately replayable. The `SignedDelegateAction` is embedded in a public transaction visible to any RPC observer or indexer, requiring no privileged access to obtain.

---

### Recommendation

Include the `chain_id` string (available from `GenesisConfig::chain_id`, e.g. `"mainnet"` or `"testnet"`) in the signed payload of `DelegateAction` and `DelegateActionV2`. The cleanest approach is to add a `chain_id: String` field to `DelegateAction` (and `DelegateActionV2`) and include it in the borsh-serialized body before hashing, or to incorporate it into `SignableMessage` as a mandatory field alongside the discriminant. Because `DelegateAction` is a protocol-level struct, this requires a protocol version gate. [8](#0-7) [9](#0-8)

### Proof of Concept

```
# Preconditions:
# - alice.near exists on testnet with key K, nonce=4
# - alice.near exists on mainnet with key K, nonce=3

# Step 1 – Alice signs a DelegateAction on testnet:
delegate_action = DelegateAction {
    sender_id:       "alice.near",
    receiver_id:     "bob.near",
    actions:         [Transfer { deposit: 10 NEAR }],
    nonce:           5,          # valid on testnet (> 4) AND on mainnet (> 3)
    max_block_height: 140_000_000,  # valid on both chains simultaneously
    public_key:      K.public,
}
hash = SHA-256( borsh( discriminant(366) || delegate_action ) )
# hash is IDENTICAL on mainnet and testnet — no chain ID in the input
sig  = K.sign(hash)
signed_da = SignedDelegateAction { delegate_action, sig }

# Step 2 – Relayer submits on testnet; action executes, nonce advances to 5.

# Step 3 – Attacker observes signed_da from the public testnet transaction.

# Step 4 – Attacker wraps it in a mainnet transaction:
mainnet_tx = SignedTransaction {
    signer_id:   "attacker.near",
    receiver_id: "alice.near",   # must equal delegate_action.sender_id
    block_hash:  <recent mainnet block hash>,
    actions:     [Delegate(signed_da)],
    ...
}
# signed_da.verify() passes on mainnet: same hash, same key, same sig.
# Nonce 5 > mainnet ak_nonce 3 → accepted.
# Transfer of 10 NEAR from alice.near to bob.near executes on mainnet.
```

The `verify()` call at execution passes because `get_nep461_hash()` produces the same bytes on both chains, and the nonce check passes because mainnet's access-key nonce is independent of testnet's. [1](#0-0) [10](#0-9)

    pub sender_id: AccountId,

    pub max_block_height: BlockHeight,
    /// Public key used to sign this delegated action.

}

pub struct SignedDelegateAction {
    pub delegate_action: DelegateAction,
    pub signature: Signature,
}

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

#[derive(BorshSerialize)]
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
#[non_exhaustive]
pub enum SignableMessageType {
    /// A delegate action, intended for a relayer to included it in an action list of a transaction.
    DelegateAction,
    /// A delegate action with gas key support, intended for a relayer to include it in an action
    /// list of a transaction.
    DelegateActionV2,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum ReadDiscriminantError {
    #[error("does not fit any known categories")]
    UnknownMessageType,
    #[error("NEP {0} does not have a known on-chain use")]
    UnknownOnChainNep(u32),
    #[error("NEP {0} does not have a known off-chain use")]
    UnknownOffChainNep(u32),
    #[error("discriminant is in the range for transactions")]
    TransactionFound,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum CreateDiscriminantError {
    #[error("nep number {0} is too big")]
    NepTooLarge(u32),
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
