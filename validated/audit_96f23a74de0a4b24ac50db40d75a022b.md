### Title
Bitcoin-mempool front-running of unconfirmed `BatchProofMethodId` bodies permanently skips lower, council-authorised activation heights - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`run_l1_block`'s `DataOnDa::BatchProofMethodId` handling accepts a council-signed method-id upgrade body purely based on its signature and its `activation_l2_height` compared against the *last processed* entry, with no restriction on which Bitcoin transaction/sender carries the bytes. Because the signed payload (`BatchProofMethodIdBody::serialize()`) is not bound to any specific transaction, an unprivileged attacker who observes a still-unconfirmed, genuine council body for a later height `Y` in the mempool can copy those exact bytes into a higher-fee transaction of their own and get it mined before a genuine, lower-height `X` body, permanently causing the `X` update to be dropped.

### Finding Description
Binding claimed: for every entry `(h_i, id_i)` recorded by `BatchProofMethodIdAccessor::<S>` after processing, `h_i` should equal an activation height the council actually intended to be applied, and the set of applied heights must equal the full set the council signed — none silently dropped.

Trace:
- `verify_method_id_security_council` (`crates/light-client-prover/src/circuit/method_id_verifier.rs:14-69`) validates 3-of-5 signatures over `body.serialize()` only — `method_id`, `activation_l2_height`, `chain_id`. Nothing ties the signature to a specific Bitcoin transaction, wtxid, or DA sender.
- Unlike the `Aggregate`/`SequencerCommitment` arms, the `BatchProofMethodId` arm in `run_l1_block` performs no `blob.sender()` check [1](#0-0) , so the raw envelope bytes can be re-inscribed by anyone who copies them from the public mempool into a new reveal transaction, paying a higher fee to be mined first.
- Ordering enforcement only compares against the *last* accessor entry: `let last_activation_height = batch_proof_method_ids.last()...0; if batch_proof_method_id.body.activation_l2_height <= last_activation_height { continue; }` [2](#0-1) .
- `BatchProofMethodIdAccessor::<S>::insert` simply appends `(activation_l2_height, method_id)` to the stored `Vec` with no re-sorting or all-time-maximum check [3](#0-2) .

Exploit flow: two genuine council-signed bodies for `X` and `Y` (`X<Y`) are broadcast to the Bitcoin mempool before either confirms. The attacker copies `Y`'s exact envelope bytes into their own transaction and pays a higher fee, so it confirms first. `run_l1_block` processes it: `last_activation_height` becomes `Y`. When the genuine `X` body later confirms and is processed (in this or a subsequent L1 block), `X <= Y` is true, so the arm logs "activation height is not greater than the last one" and `continue`s — `X`'s method id is never inserted, permanently. Existing guards do not stop this: `verify_method_id_security_council` validates `X`'s signatures correctly (they are genuine), but the height-ordering check runs *before* any concept of "was this in the intended sequence" and is only relative to the last-applied entry, not to whether `X` was supposed to precede `Y`.

### Impact Explanation
The `X` upgrade — a true, council-authorised method-id transition — becomes permanently unappliable: no future call can re-insert it because any resubmission with `activation_l2_height = X` will always fail the `<=` check once `Y` is applied. Any batch proof built against the method id that should have been active in `[X, Y)` can never be matched against the accessor's list, since `X` never appears; light-client provers processing subsequent proofs will either reject valid batch proofs or diverge from what the council intended, splitting proof validity for state transitions built against the never-applied `X` method id. This matches "a true [proof] made unprovable" / a council-authorised method-id transition never taking effect as intended, which is Critical severity per the given rubric. The effect is permanent for that specific `(X, id_X)` pair and requires no repeated action once triggered, but the same technique (front-running a lower, still-pending height with a higher one) can be repeated against any future council upgrade broadcast as long as two pending updates are both unconfirmed at once.

### Likelihood Explanation
Preconditions require the security council to have two upgrade bodies for different heights outstanding in the mempool simultaneously — an operational choice by the council, not attacker-controlled, so likelihood is directly tied to how the council manages its release cadence (e.g., issuing `X`, then rushing out `Y` before `X` confirms). Given that precondition, exploitation cost for the attacker is trivial: only Bitcoin transaction fees to get their copy mined ahead of the original, no cryptographic material, no privileged role. This is well within the stated attacker capabilities ("pay Bitcoin fees to inscribe or mine any Bitcoin transaction"). No fork rule, sender check, or nonce currently prevents it.

### Recommendation
Bind the council signature (or an additional protocol rule) to enforce sequential application: e.g., require each `BatchProofMethodIdBody` to reference the previously active method id/height it is replacing (a `previous_activation_l2_height` or `previous_method_id` field covered by the signature), and have `run_l1_block` verify that the referenced previous entry matches the current last entry before applying, buffering/rejecting the update otherwise instead of comparing only current cumulative order. Alternatively, require strictly sequential heights validated against the *entire* history (all entries, not just the last) and allow re-queuing lower, not-yet-applied heights that arrive after a higher one, rather than permanently discarding them.
