### Title
Unbounded permissionless growth of `DelegatedResourceAccountIndex` (V2) enables prefix-scan DoS via `GetDelegatedResourceAccountIndexV2` RPC/HTTP endpoint - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
Any account can permissionlessly create an unbounded number of distinct `DelegateResourceContract` relationships (owner→receiver pairs) that each get persisted as a separate key under a `V2_FROM_PREFIX`/`V2_TO_PREFIX` namespace in `DelegatedResourceAccountIndexStore`. A public, unauthenticated RPC/HTTP API (`GetDelegatedResourceAccountIndexV2`) then performs a full prefix scan and in-memory aggregation over all these entries for a single target address, with no cap on the number of entries returned or scanned. This mirrors the "poolRewards" bug class: a permissionless write path lets an attacker inflate an array/collection that is later iterated in full by privileged/critical logic, causing resource exhaustion.

### Finding Description
`DelegateResourceActuator.delegateResource()` calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, timestamp)` [1](#0-0)  for every `DelegateResourceContract`. `delegateV2()` writes two new keys (`V2_FROM_PREFIX+from+to` and `V2_TO_PREFIX+to+from`) per call [2](#0-1) . The minimum delegated balance required is only `TRX_PRECISION` (1 TRX) [3](#0-2) , and there is no limit on the number of distinct owner→receiver relationships that can be created against a single victim address — an attacker can generate many throwaway accounts, freeze a small amount of TRX v2 (`FreezeBalanceV2Contract`), and delegate 1 TRX worth of resource each to the same victim `receiverAddress`, later reclaiming the frozen TRX via `UnDelegateResourceContract`/unfreeze.

Reading this data back uses `getV2Index()` → `getWithPrefix()`, which performs `this.prefixQuery(key).values()` over ALL keys matching the victim's prefix, loads them fully into an `ArrayList`, sorts by timestamp, and rebuilds a full protobuf list with no size limit [4](#0-3) . `prefixQuery` itself materializes the entire result set into a `Map` before returning [5](#0-4) .

This is exposed to any unauthenticated caller via:
- gRPC `GetDelegatedResourceAccountIndexV2` → `Wallet.getDelegatedResourceAccountIndexV2()` [6](#0-5) , wired in `RpcApiService` [7](#0-6) , and mirrored on Solidity/PBFT read-only nodes [8](#0-7) .
- HTTP servlet `GetDelegatedResourceAccountIndexServlet` (for the non-V2 path, same `getWithPrefix` pattern for legacy keys) [9](#0-8) .

Because the aggregation happens on every call (no caching, no pagination, no cap), each request against a "polluted" victim address costs O(N) DB reads, sorting, and protobuf construction, where N is fully attacker-controlled and grows without bound over time.

### Impact Explanation
An attacker can inflate a single victim address's delegated-resource index to an arbitrarily large size using only inexpensive, repeatable transactions (minimum 1 TRX per relationship, reclaimable via unfreeze/undelegate). Subsequent calls to `GetDelegatedResourceAccountIndexV2`/`GetDelegatedResourceAccountIndex` for that address force full-witness/API nodes to scan and marshal the entire unbounded list on every request, with no pagination — creating a CPU/memory amplification vector that can degrade or DoS the node's RPC/HTTP service for that endpoint (and, since these run in the same node process, can affect overall node responsiveness). This is a resource-accounting/store-iteration class DoS reachable purely from broadcast transactions plus a public unauthenticated read API — consistent with the reported bug class (unbounded array growth via permissionless writes, unbounded iteration/aggregation in a reachable code path).

### Likelihood Explanation
Moderate-to-high. Unlike the ERC-20 report where token addition was entirely free, here each relationship costs a minimum of 1 TRX frozen (recoverable) plus transaction fees for freeze/delegate/undelegate, and creating many "owner" identities requires account activation. This raises the cost floor relative to the original report but does not eliminate the attack — the capital is not consumed (it's returned via undelegate), so the attacker's cost is bounded by transaction fees and time, not permanent capital loss, making sustained large-scale pollution of a single address's index economically feasible for a moderately funded attacker. I could not verify whether any committee-configurable parameter (e.g. `supportMaxDelegateLockPeriod`/lock-period limits) restricts the total count of distinct delegation relationships per address; based on the code reviewed, no explicit count cap exists.

### Recommendation
- Add a maximum-entries cap (or pagination-only access) to `DelegatedResourceAccountIndexStore.getWithPrefix()`/`getV2Index()`, similar to `GetPaginatedNowWitnessList`/`GetPaginatedProposalList`, instead of unconditionally materializing full lists.
- Enforce a per-address limit on the number of distinct delegation relationships (owner→receiver pairs) that can be created, or require a minimum delegated balance per relationship high enough to make large-scale spam economically irrational.
- Rate-limit or size-limit the `GetDelegatedResourceAccountIndex(V2)` RPC/HTTP handlers based on result size, and consider server-side truncation with an indication that pagination is required for large result sets.

### Proof of Concept
1. Attacker creates N throwaway accounts, each activated with minimal TRX.
2. For each account, broadcast `FreezeBalanceV2Contract` freezing 1 TRX for BANDWIDTH/ENERGY, then `DelegateResourceContract` delegating that 1 TRX to a single victim `receiverAddress`.
3. Repeat for large N (e.g., tens of thousands), each call appending two new keys via `delegateV2()` [2](#0-1) .
4. Call `GetDelegatedResourceAccountIndexV2` (gRPC) or the corresponding wallet method for `receiverAddress`; observe the node performing a full prefix scan, sort, and protobuf marshalling of N entries on every call [10](#0-9) , with response time/memory usage scaling linearly with N and no server-side limit.
5. Optionally, attacker can undelegate/unfreeze to recover most of the locked TRX after inflating the index, since balance is only temporarily locked.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
