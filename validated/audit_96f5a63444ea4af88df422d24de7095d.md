### Title
Duplicate `input_data_ids` in an `ActionReceipt` permanently strands a postponed receipt (receipt loss) - (File: `runtime/runtime/src/lib.rs`)

### Summary
`process_action_receipt` counts pending input-data dependencies by iterating `action_receipt.input_data_ids()` and incrementing a `pending_data_count` once per entry, while writing a `PostponedReceiptId` keyed only by `(receiver_id, data_id)` [1](#0-0) . If the same `data_id` appears twice in `input_data_ids`, `pending_data_count` is incremented twice but the `PostponedReceiptId` trie entry is written (and overwritten) only once. When the single matching `Data` receipt later arrives, `process_receipt`'s Data arm decrements `pending_data_count` by exactly one per data delivery event and only executes the postponed receipt when the counter reaches zero [2](#0-1) . With a duplicated id, the counter can never reach zero through normal delivery (only one distinct `data_id` exists to resolve it), so the postponed action receipt and its `PendingDataCount`/`PostponedReceipt` entries remain in state forever.

### Finding Description
I could not find any validation in `verifier.rs`/`validate_receipt` (or in the action-receipt construction path) that rejects duplicate entries in `input_data_ids`, nor could I locate a dedicated check enforcing distinctness of `input_data_ids` within a single `ActionReceipt`. Because `Receipt::from_tx` / callback-registration APIs (`receipt_manager.rs`, exposed to a `FunctionCall` action via the promise/callback host functions) let a contract construct a callback receipt whose `input_data_ids` list is caller-controlled, a malicious/buggy contract could register the same input dependency twice for a single receipt id.

Root cause chain:
- Construction: nothing enforces uniqueness of `input_data_ids` per receipt before it is queued/executed.
- `process_action_receipt` (`runtime/runtime/src/lib.rs:1662-1677`): loops per id, incrementing `pending_data_count` for every occurrence, but the `PostponedReceiptId` key space is `(receiver_id, data_id)` — a duplicate id collapses to one trie write.
- `process_receipt`, Data arm (`runtime/runtime/src/lib.rs:1452-1526`): a `Data` receipt for a given `data_id` triggers exactly one decrement of `pending_data_count` (from the single `PostponedReceiptId` link). A duplicated id needs two decrements to reach zero but can only ever contribute one, since only one `PostponedReceiptId`/`ReceivedData` row exists for that id.

I was **not able to fully verify** whether any earlier validation layer (e.g., a distinctness check in `validate_receipt` in `runtime/runtime/src/verifier.rs`, or in receipt-manager callback registration) rejects duplicate `input_data_ids` before a receipt reaches `process_action_receipt`. My searches of `verifier.rs` for `input_data_ids` found only 3 references and I did not have room in this session to fully inspect `validate_receipt`'s body or the receipt-manager's callback-registration code to confirm or rule out an explicit dedup/reject check. This is the key open question that determines whether this is truly exploitable.

### Impact Explanation
If the duplicate-id path is indeed unguarded, the practical effect is a **receipt loss / permanently frozen postponed receipt**: the affected receiver account accumulates an un-drainable `PostponedReceipt` + `PendingDataCount` entry in its own state forever. Any prepaid gas/deposit attached to that receipt is stuck (never executed, never refunded), and repeated attacks by the same technique could allow an attacker to grief a target account with dead state, though it does not by itself corrupt cross-node consensus (all honest nodes would derive the same stuck state deterministically from the same malformed receipt) and does not directly enable value theft.

### Likelihood Explanation
Likelihood depends entirely on whether validation currently permits duplicate `input_data_ids`, which I could not conclusively confirm or refute in this session due to running out of iterations. If unguarded, likelihood is high — a contract call is sufficient, and duplicating a `data_id` when registering a callback via a promise API is a plausible attacker/careless-developer action.

### Recommendation
Add an explicit uniqueness check on `ActionReceipt.input_data_ids` — either during `validate_receipt`/action-receipt validation (rejecting receipts with duplicate ids before they enter the postponed-receipt bookkeeping) or by making `process_action_receipt` dedupe ids before computing `pending_data_count`, so the counter matches the number of *distinct* dependencies rather than the raw list length.

### Proof of Concept
Not concretely constructable within this session — this requires confirming (1) that no existing validation rejects duplicate `input_data_ids`, and (2) a concrete callback-registration API path (e.g., via `receipt_manager.rs` host functions) that lets a contract emit two output-data promises resolving into the same downstream `input_data_ids` slot twice for one created receipt. **This finding should be treated as unconfirmed** pending that verification — I recommend a Devin session with full file access to `runtime/runtime/src/verifier.rs` (`validate_receipt`), `runtime/runtime/src/receipt_manager.rs`, and the promise/callback host-function implementations to definitively confirm whether duplicate `input_data_ids` are rejected or reach `process_action_receipt` unfiltered.
