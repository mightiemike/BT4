## Analysis

The reported bug class is: an unprivileged actor uses a **shared key/gate that is not scoped to its own state**, letting it delay or block progress that should only affect its own resource, but instead affects **another party's** resource — inflating a "delay" window that the victim didn't create and can't control.

The reachable analog in `agave` is the interaction between `ScanTracker`/`ScanGuard` and `AccountsDb::clean_accounts`'s `max_clean_root` gate.

### Root cause

Any accounts scan (reachable from RPC calls such as `getProgramAccounts`/`getMultipleAccounts`-style secondary-index-free scans, or any code path invoking `AccountsDb::scan_accounts`/`index_scan_accounts`) registers a `ScanGuard`, pinning the scan's `max_root` into a single, **global** map shared by all callers: [1](#0-0) 

The guard is held for the *entire duration* of the scan (until every account has been visited by `scan_func`), and only unpinned on `Drop`: [2](#0-1) [3](#0-2) 

Crucially, `clean_accounts`'s effective cleaning boundary is computed as the **minimum** of any proposed clean root and the lowest root pinned by *any* in-flight scan, regardless of who initiated that scan or which pubkeys it touches: [4](#0-3) 

This value gates both the periodic cache-flush-with-clean path and the candidate-construction path used by the background cleaning/shrink service: [5](#0-4) [6](#0-5) 

So a single unprivileged scan — belonging to one arbitrary account/key — pins a low root that becomes the effective `max_clean_root_inclusive` for **every other account in the entire validator's state**, not just the ones the scanning caller is interested in. This is structurally identical to the reported bug class: a shared "delay gate" that is not scoped per-committer/per-key, so an unrelated party (the scan initiator) inflates the delay experienced by everyone else (all other accounts pending clean/shrink).

### Title
Unprivileged accounts scan globally throttles `clean_accounts`/shrink for unrelated accounts via shared `min_ongoing_scan_root` gate - (File: `accounts-db/src/accounts_db.rs`, `accounts-db/src/accounts_scan.rs`)

### Summary
`AccountsDb::clean_accounts` computes its cleaning boundary (`max_clean_root`) as `min(min_ongoing_scan_root(), proposed_clean_root)` [4](#0-3)  where `min_ongoing_scan_root` is a single global value shared across all concurrent scans [7](#0-6) . Because this pin is not scoped to the pubkeys the scan actually reads, any single scan — triggered by an unprivileged RPC caller scanning even one unrelated account — can hold back cleaning progress for the entire accounts database.

### Finding Description
`ScanGuard::try_new` pins `max_root_inclusive` into `ongoing_scan_roots` for the lifetime of the scan call [8](#0-7) , and this pin is only released when the scan's `Drop` impl runs, i.e. after `scan_func` has been invoked for every visited account [3](#0-2) . `clean_accounts` and the background flush-with-clean path both bound how far cleaning can advance by this pinned root, independent of which pubkeys the scan actually cares about [9](#0-8) , and `construct_candidate_clean_keys` retains dirty stores/newer slots above that bound untouched [6](#0-5) . This mirrors the reported bug: the "delay" resource (`max_clean_root`) is keyed globally rather than per-account/per-caller, so an unprivileged party unrelated to a given account can extend the wait before that account is cleaned/shrunk, purely by keeping an unrelated scan open.

### Impact Explanation
While a scan is pinned at an old root, `clean_accounts` cannot reclaim any account update that occurred above that root anywhere in the ledger state — not just the accounts touched by the scan. This causes unbounded accumulation of stale/dead account versions in storage (dirty stores, uncleaned pubkeys, shrink candidates all pile up), producing disproportionate storage growth and increased CPU cost when the backlog is eventually processed, matching the "disproportionate storage and CPU cost" impact class.

### Likelihood Explanation
Any unprivileged client capable of triggering an accounts scan (e.g., a scan-based RPC call) reaches `scan_accounts`/`index_scan_accounts` and thus `ScanGuard::try_new`, needing only a single call that takes long enough to process (or is deliberately kept slow via callback work) to hold the pin. The `test_scan_flush_accounts_cache_then_clean_drop` test explicitly demonstrates that clean is blocked for an unrelated account while an unrelated scan is in progress [10](#0-9) .

### Recommendation
Scope the clean-blocking pin to the specific pubkeys/slots actually needed by a scan rather than a single global minimum root, or bound the maximum duration/impact a single scan can have on `max_clean_root` (e.g., a timeout after which clean can proceed and the scan is forced to retry/abort), so no single caller's scan can indefinitely gate cleanup progress for accounts it never touches.

### Proof of Concept
1. Start an accounts scan (e.g. via any code path reaching `AccountsDb::scan_accounts`) whose callback is slow or deliberately stalls on one specific account, as in `setup_scan` in the test suite [11](#0-10) .
2. While the scan is pinned at an old root, store and root new versions of a completely unrelated account, then call `clean_accounts`/`flush_accounts_cache(force_flush=true, ...)`.
3. Observe that the unrelated account's superseded version is not reclaimed until the scan finishes, as shown by the assertions in `test_scan_flush_accounts_cache_then_clean_drop` [10](#0-9) .

#[derive(Debug, Default)]
pub struct ScanTracker {
    ongoing_scan_roots: RwLock<BTreeMap<Slot, u64>>,
    // Each scan has some latest slot `S` that is the tip of the fork the scan
    // is iterating over. The unique id of that slot `S` is recorded here (note we don't use
    // `S` as the id because there can be more than one version of a slot `S`). If a fork
    // is abandoned, all of the slots on that fork up to `S` will be removed via
    // `AccountsDb::remove_unrooted_slots()`. When the scan finishes, it'll realize that the
    // results of the scan may have been corrupted by `remove_unrooted_slots` and abort its results.
    //
    // `removed_bank_ids` tracks all the slot ids that were removed via `remove_unrooted_slots()` so any attempted scans
    // on any of these slots fails. This is safe to purge once the associated Bank is dropped and
    // scanning the fork with that Bank at the tip is no longer possible.
    pub removed_bank_ids: Mutex<HashSet<BankId>>,
    /// # scans active currently
    pub active_scans: AtomicUsize,
    /// # of slots between latest max and latest scan
    pub max_distance_to_min_scan_slot: AtomicU64,
}

impl ScanTracker {
    fn min_ongoing_scan_root_from_btree(ongoing_scan_roots: &BTreeMap<Slot, u64>) -> Option<Slot> {
        ongoing_scan_roots.keys().next().cloned()
    }

    pub fn min_ongoing_scan_root(&self) -> Option<Slot> {
        Self::min_ongoing_scan_root_from_btree(&self.ongoing_scan_roots.read().unwrap())
    }

    pub(crate) fn try_new(
        scan_tracker: &'a ScanTracker,
        scan_bank_id: BankId,
        max_root_inclusive_fn: impl FnOnce() -> Slot,
    ) -> Option<Self> {
        {
            let locked_removed_bank_ids = scan_tracker.removed_bank_ids.lock().unwrap();
            if locked_removed_bank_ids.contains(&scan_bank_id) {
                return None;
            }
        }

        let max_root_inclusive = {
            let mut w_ongoing_scan_roots = scan_tracker
                // This lock is also grabbed by clean_accounts(), so clean
                // has at most cleaned up to the current `max_root` (since
                // clean only happens *after* BankForks::set_root() which sets
                // the `max_root`)
                .ongoing_scan_roots
                .write()
                .unwrap();
            // `max_root()` grabs a lock while
            // the `ongoing_scan_roots` lock is held,
            // make sure inverse doesn't happen to avoid
            // deadlock
            let max_root_inclusive = max_root_inclusive_fn();
            if let Some(min_ongoing_scan_root) =
                ScanTracker::min_ongoing_scan_root_from_btree(&w_ongoing_scan_roots)
                && min_ongoing_scan_root < max_root_inclusive
            {
                let current = max_root_inclusive - min_ongoing_scan_root;
                scan_tracker
                    .max_distance_to_min_scan_slot
                    .fetch_max(current, Ordering::Relaxed);
            }
            *w_ongoing_scan_roots.entry(max_root_inclusive).or_default() += 1;
            max_root_inclusive
        };

impl Drop for ScanGuard<'_> {
    fn drop(&mut self) {
        self.scan_tracker
            .active_scans
            .fetch_sub(1, Ordering::Relaxed);
        let mut ongoing_scan_roots = self.scan_tracker.ongoing_scan_roots.write().unwrap();
        let count = ongoing_scan_roots.get_mut(&self.max_root).unwrap();
        *count -= 1;
        if *count == 0 {
            ongoing_scan_roots.remove(&self.max_root);
        }

    fn max_clean_root(&self, proposed_clean_root: Option<Slot>) -> Option<Slot> {
        match (
            self.scan_tracker.min_ongoing_scan_root(),
            proposed_clean_root,
        ) {
            (None, None) => None,

            (Some(min_scan_root), Some(proposed_clean_root)) => {

    /// Flush all rooted slots up to `requested_flush_root` with cleaning. Cleaning stores only
    /// the newest version of any given account when flushing multiple rooted slots. This reduces
    /// storage space and speeds up background account cleaning. If an ongoing scan is occurring,
    /// cleaning can only be done up to the minimum scan root to avoid cleaning accounts that may
    /// be needed by the scan.
    fn flush_rooted_accounts_cache_with_clean(
        &self,
        requested_flush_root: Option<Slot>,
    ) -> (usize, usize, FlushStats) {
        // If there is a long running scan going on, this could prevent any cleaning
        // based on updates from slots > `max_clean_root`.
        let max_clean_root = self.max_clean_root(requested_flush_root);
        self.flush_rooted_accounts_cache(
            requested_flush_root,
            FlushShouldClean::Yes { max_clean_root },
        )
    }

fn setup_scan(
    db: Arc<AccountsDb>,
    scan_ancestors: Arc<Ancestors>,
    bank_id: BankId,
    stall_key: Pubkey,
) -> ScanTracker {
    let exit = Arc::new(AtomicBool::new(false));
    let exit_ = exit.clone();
    let ready = Arc::new(AtomicBool::new(false));
    let ready_ = ready.clone();

    let t_scan = Builder::new()
        .name("scan".to_string())
        .spawn(move || {
            db.scan_accounts(
                &scan_ancestors,
                bank_id,
                |maybe_account| {
                    ready_.store(true, Ordering::Relaxed);
                    if let Some((pubkey, _, _)) = maybe_account
                        && *pubkey == stall_key
                    {
                        loop {
                            if exit_.load(Ordering::Relaxed) {
                                break;
                            } else {
                                sleep(Duration::from_millis(10));
                            }
                        }
                    }
                },
                &ScanConfig::default(),
            )
            .unwrap();
        })
        .unwrap();

    // Wait for scan to start
    while !ready.load(Ordering::Relaxed) {
        sleep(Duration::from_millis(10));
    }

    ScanTracker { t_scan, exit }
}
