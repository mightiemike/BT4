### Title
Unvalidated negative `gas_fee_used` in outbound votes causes unbounded gas-refund inflation - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`applyGasRefund` (`x/uexecutor/keeper/outbound.go:174-257`) computes `refundAmount := gasFee - gasFeeUsed` using `big.Int` values parsed from `outbound.GasFee` (protocol-set) and `obs.GasFeeUsed` (validator-observation-set, ultimately sourced from `MsgVoteOutbound.ObservedTx.GasFeeUsed`). Neither `ValidateBasic` (`x/uexecutor/types/msg_vote_outbound.go:73-76`) nor `applyGasRefund` itself (`outbound.go:188-191`) rejects a negative `GasFeeUsed` string. `big.Int.SetString` happily parses `"-1000000000000"`. If `gasFeeUsed` is negative, `gasFee.Cmp(gasFeeUsed) <= 0` is false (a positive `gasFee` is always greater than a negative number), so the "no excess" guard at line 194 is bypassed, and `refundAmount = gasFee - gasFeeUsed` becomes `gasFee + |gasFeeUsed|` — an arbitrarily inflated refund amount, entirely attacker/observation-controlled.

### Finding Description [1](#0-0) 
computes `gasFee` and `gasFeeUsed` from strings without a sign check, then only skips the refund if `gasFee <= gasFeeUsed`. This is the same bug class as the referenced report's `_calculate_values`: a value derived from subtracting two signed quantities is trusted to be well-formed/bounded without validating the operand signs, and the result feeds directly into a fund-moving call, `CallUniversalCoreRefundUnusedGas` (`x/uexecutor/keeper/evm.go:597-644`), which mints/refunds `refundAmount` of `gasToken`/PC to the recipient.

The originating value is only length/emptiness-checked in [2](#0-1)  — there is no non-negativity check comparable to the one enforced elsewhere for inbound amounts (`x/uexecutor/types/inbound.go:126-134`, which explicitly rejects `bi.Sign() < 0`). That asymmetry indicates the omission on the outbound gas-fee-used path is a genuine gap rather than an intentional design choice.

### Impact Explanation
Per the scope's "honest validator" assumption, this is only exploitable if 2/3+ of Universal Validators converge on a ballot with a negative `gas_fee_used` value for the same outbound — which would require either a shared bug in the UV's own submission logic (e.g., a parsing error producing a negative decimal string) or non-adversarial validator software error, not a malicious validator. Given that constraint, the severity is best framed as a robustness/invariant gap: the module has no on-chain defense-in-depth against this class of malformed vote, unlike the analogous inbound-amount check. If it is ever triggered (buggy UV client, encoding bug, or a future code path that accepts less-trusted gas-fee data), the result is an unbounded, protocol-funded gas refund minted/swapped to an attacker-influenced recipient (`refundRecipient`, taken from `RevertInstructions.FundRecipient` or `outbound.Sender`), i.e., unauthorized fund release from `UniversalCore`.

### Likelihood Explanation
Low under the strict "honest validator" assumption, since the value must clear ballot consensus. However, likelihood is elevated relative to a pure privileged-actor bug because the check that's missing (non-negativity) is trivial to add and is already present for the structurally similar `Inbound.Amount` field, suggesting it was simply missed for `OutboundObservation.GasFeeUsed`.

### Recommendation
Add an explicit non-negativity check for `gas_fee_used` (and ideally for `outbound.GasFee`) at both admission and use points:
1. In `MsgVoteOutbound.ValidateBasic` (`x/uexecutor/types/msg_vote_outbound.go`), parse `obs.GasFeeUsed` as a `big.Int` and reject if it fails to parse or is negative, mirroring `Inbound.ValidateForExecution`'s amount check.
2. Defensively, in `applyGasRefund` (`x/uexecutor/keeper/outbound.go`), reject/clamp when `gasFeeUsed.Sign() < 0` before computing `refundAmount`, so that even a value that slipped past ballot admission cannot produce an inflated refund.

### Proof of Concept
1. A Universal Validator (or buggy client library used by 2/3+ of them) submits `MsgVoteOutbound` with `ObservedTx.GasFeeUsed = "-999999999999999999"` for a pending outbound whose `GasFee = "111"`.
2. `ValidateBasic` accepts it because the field is non-empty.
3. Ballot finalizes; `handleSuccessfulOutbound`/`handleFailedOutbound` calls `applyGasRefund`.
4. `gasFee.Cmp(gasFeeUsed) <= 0` is false (111 > -999999999999999999), so the function proceeds.
5. `refundAmount = 111 - (-999999999999999999) = 1000000000000000110`, and `CallUniversalCoreRefundUnusedGas` mints/swaps that amount to the refund recipient — far exceeding the actual gas consumed on the destination chain. [3](#0-2) [4](#0-3)

func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {

		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}

	refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
