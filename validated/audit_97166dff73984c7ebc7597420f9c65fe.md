### Title
Missing slippage protection in `ExchangeWithdrawActuator` enables sandwich attacks on TRC10 Bancor-exchange liquidity withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
java-tron's built-in Bancor-style TRC10 exchange module lets a liquidity creator withdraw tokens via `ExchangeWithdrawContract`/`ExchangeWithdrawActuator`. Unlike the paired swap operation (`ExchangeTransactionContract`/`ExchangeTransactionActuator`), which enforces a caller-supplied minimum-output (`expected`) parameter, the withdrawal path computes the counter-token amount purely from the exchange's live balances at execution time and provides no minimum-output/slippage parameter at all. This mirrors the Superposition H-03 pattern: a withdrawal primitive lacking slippage control while the corresponding swap primitive has it, enabling a sandwich attack that skews the pool ratio right before the victim's withdrawal executes.

### Finding Description
`ExchangeTransactionContract` explicitly carries an `expected` field used as a minimum-output check: [1](#0-0) 

`ExchangeTransactionActuator.doValidate()` enforces this check against the live pool state before executing the swap: [2](#0-1) 

In contrast, `ExchangeWithdrawContract` has only `owner_address`, `exchange_id`, `token_id`, and `quant` — no minimum/expected amount field for the counter-token the withdrawer receives: [3](#0-2) 

`ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the exchange's current `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with no comparison against any user-supplied floor: [4](#0-3) 

`doValidate()` similarly only checks precision/rounding tolerance ("Not precise enough") and that `anotherTokenQuant > 0` — it never lets the caller bound the minimum amount received: [5](#0-4) 

Because the ratio used for the payout is read live from `exchangeCapsule` at block-execution time, and any unprivileged account can submit `ExchangeTransactionContract` swap transactions that change `firstTokenBalance`/`secondTokenBalance`, an attacker who observes a pending `ExchangeWithdrawContract` in the transaction pool can:
1. Front-run it with a large swap that skews the pool ratio unfavorably for the withdrawer's token.
2. Let the victim's withdraw execute, receiving a much smaller `anotherTokenQuant` than the pool's pre-attack ratio would have implied.
3. Back-run with a reverse swap to restore the ratio and capture the difference, extracted from the victim's withdrawn value.

This is the same root cause as the Superposition report: a state-mutating liquidity-withdrawal function that derives payout from mutable pool state with no user-defined floor, while the sibling swap function does enforce one.

### Impact Explanation
A withdrawing exchange creator can be made to receive an amount of the counter-token far below fair value, with the difference captured by the attacker — a direct fund-loss/settlement-integrity issue affecting real on-chain TRC10 balances (`AccountCapsule.addAssetAmountV2`/`setBalance`), not a theoretical or internal-only condition. Only the exchange creator can withdraw (per `!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check), but that creator is an ordinary unprivileged account, and the attacker executing the sandwich is also an unprivileged account submitting ordinary `ExchangeTransactionContract` swaps. [6](#0-5) 

### Likelihood Explanation
Any account can observe pending transactions in the network's transaction pool and submit competing swap transactions before block packing (subject to normal TRON transaction ordering/fee mechanics), making the sandwich pattern practically reachable without needing witness/SR privilege — an ordinary user submitting the front-run and back-run swaps is sufficient. The exchange's live balances directly determine payout with no protective floor, so any withdrawal of non-trivial size is exposed.

### Recommendation
Add a minimum-output field (e.g., `expected`) to `ExchangeWithdrawContract`, analogous to `ExchangeTransactionContract.expected`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the withdrawal if the computed `anotherTokenQuant` falls below the caller-supplied minimum, mirroring the check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker monitors the mempool and sees a pending `ExchangeWithdrawContract` from the exchange creator withdrawing `tokenQuant` of `firstTokenID`.
2. Attacker submits an `ExchangeTransactionContract` swap that heavily buys `firstTokenID` out of the pool, shifting `firstTokenBalance`/`secondTokenBalance` so the ratio used in `ExchangeWithdrawActuator.execute()` (lines 74-89) yields a much smaller `anotherTokenQuant` for the victim.
3. Victim's withdraw executes with the skewed ratio, receiving far less `secondTokenID` than expected, with no way to have bounded this since `ExchangeWithdrawContract` carries no minimum-output field.
4. Attacker submits a reverse swap to restore the ratio, realizing the captured difference as profit.
