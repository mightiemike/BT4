### Title
Panic-inducing `expect`/indexing on attacker-controlled `proof_facts` during client-side-proving verification - (File: `crates/starknet_proof_verifier/src/proof_verifier.rs`, `crates/blockifier/src/transaction/account_transaction.rs`)

### Summary
Starknet's client-side-proving feature lets an unprivileged sender attach `proof_facts`/`proof` to an `Invoke` V3 transaction. Both the gateway (via `apollo_transaction_converter`) and the blockifier's `validate_proof_facts` parse this attacker-supplied byte blob before/while charging any fee, using indexing and `try_from` conversions on a fixed-size structured felt array. If the array is shorter than expected or malformed in specific ways, this can panic instead of returning a validation error, analogous to the MobileCoin bug where `HashMap::get(...).expect("Child range should already exist.")` panicked on crafted, but well-formed-looking, input during normal transaction validation.

### Finding Description
`AccountTransaction::validate_proof_facts` in [1](#0-0)  parses the caller-supplied `proof_facts` via `ProofFactsVariant::try_from(&proof_facts)` before any fee is verified or charged. Likewise `starknet_proof_verifier::verify_proof` in [2](#0-1)  takes the first felt of `proof_facts.0` and calls `reconstruct_output_preimage(&proof_facts)`, which is expected to slice/index into the felt array according to header-declared sizes (mirrored in the Cairo `check_proof_facts` implementation at [3](#0-2)  which asserts `ProofHeader.SIZE + VirtualOsOutputHeader.SIZE <= proof_facts_size` before indexing further). If the corresponding Rust-side reconstruction (`reconstruct_output_preimage`) does not perform an equivalent bounds check before slicing/indexing, or uses `.expect(...)` on a lookup/conversion that assumes well-formed input, a sender can submit a transaction with a `proof_facts` array that is empty or truncated relative to the declared header sizes, causing a panic in the gateway process (or in the block-building/consensus path) rather than a clean `TransactionPreValidationError`.

This is structurally identical to the reported MobileCoin bug: an untrusted, attacker-controlled data structure is parsed with an implicit assumption ("this key/index must exist because we already validated the header") enforced via `.expect(...)`/indexing rather than a proper fallible check, and the parsing runs during normal transaction admission (`add_tx` in the gateway), reachable by any transaction sender without needing special privileges.

### Impact Explanation
A panic during `validate_proof_facts` or `verify_proof` executes inside the gateway's `add_tx` request path and/or the transaction-converter's spawned verification task [4](#0-3) . Depending on how these panics propagate (e.g., whether they are caught by `spawn_blocking`/`tokio::spawn` and converted to errors, or whether an unwind escapes into a shared worker thread), a single crafted transaction can crash the gateway component or the sequencer's transaction-converter worker, denying transaction admission for that node — a network-wide availability impact if replicated across nodes running the same code and gateway configuration.

### Likelihood Explanation
Likelihood is High: client-side proving is an intentionally externally-reachable feature (`starknet_proveTransaction` / gateway `add_tx` for Invoke V3 with `proof_facts`), requires no special privilege, and the report's underlying bug class (implicit "this field must be present/well-formed" assumptions enforced by panicking primitives instead of `Result`) is exactly the same shape as the MobileCoin `derive_proof_at_index` issue. However, I could not directly inspect the body of `reconstruct_output_preimage` (index not fully available for this function), so I cannot confirm with certainty whether it already performs safe bounds checks; the associated Cairo code performing the equivalent check explicitly enforces `assert_le` bounds first, and the Rust side should mirror that guard.

### Recommendation
- **Short term:** Ensure `reconstruct_output_preimage` and any other `proof_facts` parsing performs explicit length/bounds validation (returning `Result<_, VerifyProofError>`) before any indexing or slicing, mirroring the Cairo `assert_le(ProofHeader.SIZE + VirtualOsOutputHeader.SIZE, proof_facts_size)` check. Replace any `.expect(...)` or unchecked indexing on `proof_facts` fields with fallible `ok_or`/`try_from` patterns that surface as `TransactionPreValidationError::InvalidProofFacts` instead of panicking.
- **Long term:** Add fuzz targets around `ProofFactsVariant::try_from`, `reconstruct_output_preimage`, and `verify_proof` with malformed/truncated `proof_facts` inputs, and audit all other externally-reachable transaction-field parsers (`Invoke`/`Declare`/`DeployAccount`) for similar implicit-precondition panics.

### Proof of Concept
Submit an `Invoke` V3 transaction with `allow_client_side_proving` enabled where `proof_facts` is a non-empty but truncated felt array — e.g., a single felt equal to a valid `ProofVersion` marker but shorter than `ProofHeader::SIZE + VirtualOsOutputHeader::SIZE` — via the gateway's `add_tx`. If `reconstruct_output_preimage`/`ProofFactsVariant::try_from` index into the array without first checking its length against the declared header sizes, the gateway process (or transaction-converter worker) panics while processing an unprivileged, publicly submitted transaction.

**Uncertainty note:** I was not able to view the full implementation of `reconstruct_output_preimage` or `ProofFactsVariant::try_from` within the indexed context, so I cannot definitively confirm the panic occurs versus being already guarded by a length check returning a `Result`. If a Devin session with full file access confirms these functions already validate lengths safely before indexing, this finding should be downgraded/discarded.

/// The first element of `proof_facts` must be V1, verified via `privacy-circuit-verify-v1`.
pub fn verify_proof(proof_facts: ProofFacts, proof: Proof) -> Result<(), VerifyProofError> {
    // Reject empty proof payloads before running the verifier.
    if proof.is_empty() {
        return Err(VerifyProofError::EmptyProof);
    }

    let proof_version_felt = proof_facts.0.first().copied().unwrap_or_default();
    let proof_version = ProofVersion::try_from(proof_version_felt)
        .map_err(|()| VerifyProofError::InvalidProofVersion { actual: proof_version_felt })?;

    let output_preimage = reconstruct_output_preimage(&proof_facts)?;
    // TODO(Avi): Avoid cloning the proof.
    let proof_bytes = proof.0.to_vec();

    match proof_version {
        // V0 proofs are no longer verifiable: the v0 circuit was removed. V0 proof facts are only
        // tolerated by the blockifier (gated per protocol version) for replaying historical blocks.
        ProofVersion::V0 => {
            return Err(VerifyProofError::InvalidProofVersion { actual: proof_version_felt });
        }
        ProofVersion::V1 => {
            let proof_output = privacy_circuit_verify_v1::PrivacyProofOutput {
                proof: proof_bytes,
                output_preimage,
            };
            privacy_circuit_verify_v1::verify_recursive_circuit(&proof_output)
                .map_err(|e| VerifyProofError::Verification(e.to_string()))?;

    /// Runs proof verification: checks if the proof already exists, and if not, verifies it.
    /// Returns `true` if verification was performed, `false` if skipped (proof already stored).
    /// This is the shared verification logic used by both gateway and consensus flows.
    async fn run_proof_verification(
        proof_facts: ProofFacts,
        proof: Proof,
        proof_manager_client: SharedProofManagerClient,
    ) -> Result<bool, TransactionConverterError> {
        let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;

        if contains_proof {
            return Ok(false);
        }

        let proof_facts_hash = proof_facts.hash();
        let verify_start = Instant::now();
        tokio::task::spawn_blocking(move || {
            starknet_proof_verifier::verify_proof(proof_facts, proof)
        })
        .await
        .expect("proof verification task panicked")?;
        let verify_duration = verify_start.elapsed();
        PROOF_VERIFICATION_LATENCY.record(verify_duration.as_secs_f64());
        info!(
            "Proof verification took: {verify_duration:?} for proof facts hash: \
             {proof_facts_hash:?}"
        );

        Ok(true)
    }
