### Title
Stale `last_checkpoint` in native-position ledger state summary when a checkpoint version has no position writes - (`storage/aptosdb/src/db/aptosdb_writer.rs`, `position_summary_at_commit`)

### Summary
`AptosDB::position_summary_at_commit` (used when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is off) advances the `last_checkpoint` component of `PositionLedgerStateWithSummary` **only when the checkpoint-boundary version happens to have pending native-position writes**. If the ledger checkpoint version inside the chunk has zero native-position writes, `last_checkpoint` is silently left pointing at the previous chunk's checkpoint instead of being refreshed to the (unchanged but now-current) `latest` state at the real checkpoint version — an index/condition mistake structurally identical to the reported `_writeCheckpoint` bug (a required "carry forward the current checkpoint marker" step is gated behind a condition that isn't always true).

### Finding Description
```rust
// storage/aptosdb/src/db/aptosdb_writer.rs
let checkpoint_within_chunk = chunk
    .state
    .last_checkpoint()
    .version()
    .filter(|v| (chunk_first..=chunk_last_inclusive).contains(v));
...
for (i, output) in chunk.transaction_outputs.iter().enumerate() {
    let version = chunk_first + i as Version;
    for (key, op) in output.write_set().native_position_iter() {
        ...
        pending.insert(key.hash(), PositionSlot { ... });
    }
    if Some(version) == checkpoint_within_chunk && !pending.is_empty() {
        let updates: Vec<_> = std::mem::take(&mut pending).into_iter().collect();
        latest = extend_on_base(&latest, version, updates)?;
        last_checkpoint = latest.clone();   // <-- only reached if pending is non-empty
    }
}
``` [1](#0-0) 

`last_checkpoint` is only re-synced to `latest` inside the `if Some(version) == checkpoint_within_chunk && !pending.is_empty()` branch. The correctness of `last_checkpoint` should depend solely on *reaching the checkpoint version*, not on whether that specific version happened to contain position writes. When a ledger checkpoint (state-checkpoint / block-epilogue transaction) lands in this chunk but no native-position write occurred exactly at that version — a very common case since position writes are sparse (as noted in `PositionMerkleDb::get_root_hash`'s own doc comment: "Position snapshots are sparse — many ledger versions have no JMT nodes") [2](#0-1)  — the `&& !pending.is_empty()` guard prevents `last_checkpoint` from ever being advanced to that version. It remains stuck at whatever it was carried in from `current.last_checkpoint()` at function entry [3](#0-2) , i.e., an older, in some cases far older, checkpoint.

The resulting `PositionLedgerStateWithSummary::from_latest_and_last_checkpoint(latest, last_checkpoint)` [4](#0-3)  is then fed into `bufstate.update(new_state, ...)` [5](#0-4) , whose `LedgerStateView` impl exposes `last_checkpoint_snapshot()` off exactly this stale field and asserts `latest.is_descendant_of(&last_checkpoint)` via `LedgerWithSummary::new`/`is_descendant_of` [6](#0-5) . The buffered-state committer (shared generic logic used identically by main state, `BufferedStateCore::enqueue`) uses `last_snapshot`/checkpoint bookkeeping to decide when to hand snapshots to the merkle-batch committer for merklization [7](#0-6) . A stale `last_checkpoint` therefore causes the position (JMT) merklization pipeline to keep tracking an outdated checkpoint boundary rather than the true, just-reached checkpoint boundary of the chain.

### Impact Explanation
This falls squarely under the "committed state that differs from the correct VM result / corrupts durable ledger data" and "authenticated API or state-view output bound to the wrong version" categories: the position ledger's `last_checkpoint` snapshot — used as the authoritative base for the position Jellyfish-Merkle-Tree commitment (`merklize_position`, position proofs, `get_persisted_position_state_summary`, `get_pre_committed_position_state_summary`) — can be left bound to an older version than the actual chain checkpoint. Downstream consumers (position-tree merklization scheduling, proof generation via `PositionProofReader`, and any consistency assertions comparing `last_checkpoint` across chunks via `is_descendant_of`) then operate against a checkpoint marker that does not correspond to the version it is supposed to represent, risking either committing/merklizing at the wrong version boundary or corrupting the invariant `latest.is_descendant_of(&last_checkpoint)` tracking across future chunks.

Because this code path (`position_summary_at_commit`) only executes when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is off (the summary is otherwise supplied by execution) [8](#0-7) , this is a config/feature-dependent bug in the native-position (trading) subsystem rather than in the core Aptos ledger transaction/state accumulator — I could not fully verify from the available index whether `ENABLE_TRADING_NATIVE`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet today, so the real-world blast radius is uncertain.

### Likelihood Explanation
Likely to trigger routinely: any chunk boundary where a state-checkpoint/epilogue transaction lands on a version with no native-position write (the normal case per the codebase's own "sparse" comment) will hit this bug deterministically, with no attacker action required — it's a logic bug on the natural commit path, not something requiring adversarial input.

### Recommendation
Advance `last_checkpoint` whenever the checkpoint-boundary version is reached, regardless of whether `pending` is non-empty:
```rust
if Some(version) == checkpoint_within_chunk {
    if !pending.is_empty() {
        let updates: Vec<_> = std::mem::take(&mut pending).into_iter().collect();
        latest = extend_on_base(&latest, version, updates)?;
    }
    last_checkpoint = latest.clone();
}
```

### Proof of Concept
1. Configure a node with `COMPUTE_TRADING_NATIVE_STATE_ROOTS` off and native position enabled.
2. Commit a chunk that contains a ledger checkpoint (state-checkpoint/epilogue transaction) at some version `V`, but no transaction in that chunk writes to the native-position store at exactly version `V` (position writes occurring only at versions `< V` and/or `> V` within the chunk).
3. Observe that `position_summary_at_commit` returns a `PositionLedgerStateWithSummary` whose `last_checkpoint` still reflects the prior chunk's checkpoint (not version `V`), while `latest` correctly reflects the state through `chunk_last_inclusive`.
4. Confirm via `PositionBufferedState`/`BufferedStateCore` bookkeeping (`last_checkpoint_snapshot()`, `should_commit`, `is_descendant_of`) that the checkpoint marker used for merklization scheduling and consistency checks is bound to the wrong (stale) version rather than `V`.

Note: I was not able to fully trace every downstream consumer of `PositionLedgerStateWithSummary::last_checkpoint()` within the available index (e.g., exact merklization trigger conditions in `PositionMerkleBatchCommitter`), so the precise on-disk corruption scenario (vs. a delayed/late merklization) is not fully confirmed from local code alone — a background Devin session with full repo access would be needed to trace `PositionMerkleBatchCommitter::run()` and `BufferedStateCore::should_commit`/`enqueue` end-to-end to confirm whether this can produce an on-disk root-hash mismatch or only a scheduling delay.

impl LedgerStateView for PositionLedgerStateWithSummary {
    type Snapshot = PositionStateWithSummary;

    fn next_version(&self) -> Version {
        self.latest().next_version()
    }

    fn last_checkpoint_snapshot(&self) -> Self::Snapshot {
        self.last_checkpoint().clone()
    }

    fn is_descendant_of(&self, other: &Self) -> bool {
        self.latest().is_descendant_of(other.latest())
            && self
                .last_checkpoint()
                .is_descendant_of(other.last_checkpoint())
    }
}
