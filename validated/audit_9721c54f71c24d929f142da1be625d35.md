Based on my research, I found a concrete analog to the "Untyped data signing" bug class in the S4 (Simple Shared Storage Service) envelope-signing scheme used by the Functions gateway/secrets pipeline.

### Title
Untyped, non-domain-separated signature scheme in S4 secret-storage envelopes enables cross-DON/cross-job signature replay - (File: `core/services/s4/envelope.go`)

### Summary
The `s4.Envelope` struct, used to authorize writes into the Chainlink Functions "DON-hosted secrets" storage via the Gateway, signs a raw, untyped JSON blob (`address`, `slotid`, `payload`, `version`, `expiration`) with no domain separator — no DON ID, no job/service identifier, no chain ID, and no type/purpose tag. Because multiple independent Functions DON job specs on the same node can share the same S4 storage namespace, a validly-signed `secrets_set` payload captured from one DON context can be replayed against a different DON/job context on the same node without any additional authorization from the user.

### Finding Description
`Envelope.Sign`/`Envelope.GetSignerAddress` compute a signature strictly over the fixed JSON serialization of `{address, slotid, payload, version, expiration}` [1](#0-0) . This is exactly the "untyped application data" pattern flagged in the external report: no EIP-712-style domain separator binds the signature to a specific verifying context (DON ID, job/service, or chain).

The `s4.storage.Put` function — the sole authorization gate for writing into S4 storage — validates a request purely by recomputing this envelope and checking the recovered signer against the claimed key address; it performs no check that the signature was intended for this particular storage instance/DON/job [2](#0-1) .

This storage is reached from the unprivileged, user-facing Functions Gateway/connector path: `functionsConnectorHandler.HandleGatewayMessage` → `handleSecretsSet` → `h.storage.Put(ctx, &key, &record, request.Signature)`, gated only by an allowlist and rate limiter, not by any binding to the specific DON that received the request [3](#0-2) [4](#0-3) .

Critically, the S4 ORM namespace used by every Functions job on a node is a fixed, global constant (`FunctionsS4Namespace = "functions"`), not something derived per-DON or per-job: `s4ORM := s4.NewCachedORMWrapper(s4.NewPostgresORM(conf.DS, s4.SharedTableName, FunctionsS4Namespace), conf.Logger)` [5](#0-4) . Since the signed envelope contains no DON/job identifier, and the storage keyspace (`address`, `slotid`, `version`) is shared across every Functions DON job configured on that node, a signature a user created while interacting with DON-A's gateway is byte-for-byte valid and will be accepted by DON-B's `Put` call as well, as long as slot/version/payload/expiration match — there is nothing in the signed payload that scopes it to the DON the user actually intended to authorize.

### Impact Explanation
An unprivileged user's legitimately-signed `secrets_set` request, if observed or retransmitted (e.g., replayed by a party with access to the gateway traffic, or simply resubmitted to a different DON endpoint the node participates in), will be accepted and written into another DON/job's S4 storage namespace without any additional consent check tying the signature to that specific service context. This breaks the intended authorization boundary between independently operated Functions DON services sharing a node, allowing cross-service data tampering of the secrets storage (i.e., "misreporting/data tampering" of DON-hosted secrets state) — the same signature that should only authorize a write under one DON's storage context is accepted under any other DON/job sharing the node's S4 namespace.

### Likelihood Explanation
Exploitation requires only capturing (or being the original sender of) a validly-signed `secrets_set` envelope and resubmitting it to a different Functions DON gateway endpoint served by the same node — no cryptographic break, no privileged node/operator access is required, and the allowlist/rate-limiter checks in `handleSecretsSet` do not defend against this because they only check `Allow(fromAddr)`, not envelope scope [6](#0-5) .

### Recommendation
Bind the S4 envelope signature to an explicit domain separator including at minimum a namespace/DON identifier (ideally following EIP-712 with a proper domain separator: chain ID, verifying contract/service identifier, and a typed struct hash) so that signatures cannot be replayed across different DON/job contexts sharing the same node and storage namespace. At minimum, include the DON ID / S4 namespace as a signed field in `Envelope` and verify it against the receiving service's own namespace in `storage.Put`.

### Proof of Concept
1. User signs an `s4.Envelope{Address, SlotID, Payload, Version, Expiration}` and submits a `secrets_set` message to Gateway/DON-A's Functions connector, which calls `h.storage.Put` successfully (uses the shared `"functions"` S4 namespace) [4](#0-3) .
2. An attacker (or the user themselves, intentionally or not) resubmits the identical `{payload, signature}` pair in a `secrets_set` request to DON-B's Functions connector running on the same node.
3. `storage.Put` for DON-B recomputes the identical envelope JSON and signature check, which succeeds because nothing in the signed data differentiates DON-A from DON-B [7](#0-6) , causing the secret to be written into DON-B's storage context without DON-B ever independently authorizing it.

// Envelope represents a JSON object that is signed for address verification.
// All []byte values are encoded as base64 (default JSON behavior).
// Hex is not used to avoid confusion due to case-sensivity and 0x prefix.
// A signer is responsible for generating a JSON that has no whitespace and
// the keys appear in this exact order:
// {"address":base64,"slotid":int,"payload":base64,"version":int,"expiration":int}
type Envelope struct {
	Address    []byte `json:"address"`
	SlotID     uint   `json:"slotid"`
	Payload    []byte `json:"payload"`
	Version    uint64 `json:"version"`
	Expiration int64  `json:"expiration"`
}

func NewEnvelopeFromRecord(key *Key, record *Record) *Envelope {
	return &Envelope{
		Address:    key.Address.Bytes(),
		SlotID:     key.SlotId,
		Payload:    record.Payload,
		Version:    key.Version,
		Expiration: record.Expiration,
	}
}

// Sign calculates signature for the serialized envelope data.
func (e Envelope) Sign(privateKey *ecdsa.PrivateKey) (signature []byte, err error) {
	if len(e.Address) != common.AddressLength {
		return nil, fmt.Errorf("invalid address length: %d", len(e.Address))
	}
	js, err := e.ToJson()
	if err != nil {
		return nil, err
	}
	return utils.GenerateEthSignature(privateKey, js)
}

// GetSignerAddress verifies the signature and returns the signing address.
func (e Envelope) GetSignerAddress(signature []byte) (address common.Address, err error) {
	if len(e.Address) != common.AddressLength {
		return common.Address{}, fmt.Errorf("invalid address length: %d", len(e.Address))
	}
	js, err := e.ToJson()
	if err != nil {
		return common.Address{}, err
	}
	return utils.GetSignersEthAddress(js, signature)
}

func (s *storage) Put(ctx context.Context, key *Key, record *Record, signature []byte) error {
	if key.SlotId >= s.contraints.MaxSlotsPerUser {
		return ErrSlotIdTooBig
	}
	if len(record.Payload) > int(s.contraints.MaxPayloadSizeBytes) {
		return ErrPayloadTooBig
	}
	now := s.clock.Now().UnixMilli()
	if now > record.Expiration {
		return ErrPastExpiration
	}
	expSecs := s.contraints.MaxExpirationLengthSec * 1000
	if expSecs > math.MaxInt64 {
		return fmt.Errorf("expiration seconds overflows int64: %d", expSecs)
	}
	if record.Expiration-now > int64(expSecs) {
		return ErrExpirationTooLong
	}

	envelope := NewEnvelopeFromRecord(key, record)
	signer, err := envelope.GetSignerAddress(signature)
	if err != nil || signer != key.Address {
		return ErrWrongSignature
	}

func (h *functionsConnectorHandler) handleSecretsSet(ctx context.Context, gatewayId string, body *api.MessageBody, fromAddr ethCommon.Address) {
	var request functions.SecretsSetRequest
	var response functions.SecretsSetResponse
	err := json.Unmarshal(body.Payload, &request)
	if err == nil {
		key := s4.Key{
			Address: fromAddr,
			SlotId:  request.SlotID,
			Version: request.Version,
		}
		record := s4.Record{
			Expiration: request.Expiration,
			Payload:    request.Payload,
		}
		h.lggr.Debugw("handling a secrets_set request", "address", fromAddr, "slotId", request.SlotID, "payloadVersion", request.Version, "expiration", request.Expiration)
		err = h.storage.Put(ctx, &key, &record, request.Signature)
		if err == nil {
			response.Success = true
			promStorageUserUpdatesCount.WithLabelValues().Inc()
		} else {
			response.ErrorMessage = fmt.Sprintf("Failed to set secret: %v", err)
		}
	} else {
		response.ErrorMessage = fmt.Sprintf("Bad request to set secret: %v", err)
	}
	h.sendResponseAndLog(ctx, gatewayId, body, response)
}
