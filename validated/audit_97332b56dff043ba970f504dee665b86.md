## Analog Found

### Title
L1 handler timelock checks use each node's local wall clock instead of a deterministic committed timestamp, causing honest-node divergence on L1Handler transaction validity - (File: crates/apollo_l1_events/src/l1_events_provider.rs, crates/apollo_l1_events/src/transaction_manager.rs, crates/apollo_l1_events/src/transaction_record.rs)

### Summary
The original report's bug class is that two independent timing mechanisms (CvgRewards' block-timestamp-driven cycles and veCVG's fixed week-rounded clock) can drift apart, so a lock is "expired" under one system but not the other, DOS'ing withdrawal. The sequencer's `apollo_l1_events` crate has the same structural flaw: L1Handler transaction lifecycle timelocks (cancellation and consumption) are evaluated against each node's own local wall-clock `unix_now()`, while the state that these timelocks are measured from (`cancellation_requested_at`, `consumed_at`) is a deterministic `BlockTimestamp` sourced from L1 events. Because `unix_now()` is not a consensus-agreed value, different sequencer nodes (or the proposer vs. a validator) can compute different `now` values and thus reach different verdicts on the same transaction at the same logical point in time.

### Finding Description
`L1EventsProvider::get_txs` (called by the proposer) and `L1EventsProvider::validate` (called by every validator) both pass `self.clock.unix_now()` into the transaction manager: [1](#0-0) [2](#0-1) 

`self.clock` defaults to `DefaultClock`, whose `unix_now()` is `chrono::Utc::now()` — the node's own OS wall clock, not a value derived from the block being built/validated: [3](#0-2) 

`TransactionManager::validate_tx` feeds this local `unix_now` into `TransactionRecord::update_time_based_state`, which performs a state transition (`CancellationStartedOnL2` → `CancelledOnL2`) purely based on comparing local wall time against `cancellation_requested_at` (a deterministic `BlockTimestamp` from an L1 event) plus a configured timelock: [4](#0-3) [5](#0-4) 

`TransactionManager::get_txs` likewise gates proposability using `now.saturating_sub(l1_handler_proposal_cooldown_seconds)` against the proposable index: [6](#0-5) 

and `clear_old_tx_from_consumed_queue` purges records from the map entirely based on local `unix_now` versus the deterministic `consumed_at` timestamp: [7](#0-6) 

This is exactly the two-clocks-drift pattern from the report: one deterministic, L1-anchored timestamp (`cancellation_requested_at`/`consumed_at`, analogous to veCVG's fixed week-rounding) versus one free-running, per-node clock (`unix_now()`, analogous to CvgRewards' `block.timestamp`-driven cycle rollover) used to gate the same state transition. Notably, elsewhere in the codebase the project explicitly accounts for exactly this class of clock-skew risk by adding a tolerance window (`block_timestamp_window_seconds`) when comparing a proposed block's timestamp to `clock.unix_now()`: [8](#0-7) 
No equivalent tolerance or "canonical time" plumbing exists for the L1Handler timelock checks in `apollo_l1_events`, so validators lacking clock synchronization can disagree with the proposer (or each other) about whether a given L1Handler transaction is still validatable.

### Impact Explanation
An L1 message sender can trigger `TransactionCancellationStarted`, which any node ingests via `add_events` and records as `cancellation_requested_at` (deterministic): [9](#0-8) 
If a proposer's local clock lags behind a validator's local clock near the cancellation timelock boundary, the proposer will include the L1Handler tx in a proposal (its own `unix_now` says the timelock hasn't passed), while the validator's `validate` call transitions the same record to `CancelledOnL2` and rejects it as `Invalid(CancelledOnL2)`. Since the underlying state transition is monotonic and irreversible (`CancellationStartedOnL2 → CancelledOnL2` only moves forward with time), retries by the same or other proposers around the same boundary can repeatedly hit the same disagreement, causing repeated proposal rejections/round failures for otherwise-honest proposals — a liveness/availability impact on confirming new transactions, and a case of honest-node divergence on transaction validity, matching the impact categories accepted for this type of issue.

### Likelihood Explanation
This requires no adversarial coordination or privileged role: any L1 user can request cancellation of a bridged/L1Handler message near the timelock boundary (which is common in normal operation, e.g. via bridge withdrawals or games with cancellation UX), and ordinary NTP clock skew (seconds to tens of seconds) between sequencer nodes is enough to hit the race window, especially for short-timelock configurations. The bug is a straightforward root-cause: using `Clock::unix_now()` (local wall time) rather than a value tied to the block/round being processed for a consensus-relevant validity decision.

### Recommendation
Do not use raw local wall-clock `unix_now()` to gate consensus-relevant transaction validity decisions. Either (a) derive the "now" used for L1Handler timelock evaluation from a deterministic, gossipped quantity already used elsewhere for this purpose (e.g., the block's own proposed timestamp, analogous to how `is_proposal_init_valid` bounds `init_proposed.timestamp` against `block_timestamp_window_seconds`), or (b) apply an explicit skew tolerance window around the cancellation/consumption timelock boundaries so that proposer and validator decisions agree within the expected clock-skew bound, consistent with the pattern already used for block timestamp validation.

### Proof of Concept
1. Configure `l1_handler_cancellation_timelock_seconds` to a small value (e.g., matching test setups like `crates/apollo_l1_events/tests/timing_flows.rs`). [10](#0-9) 
2. An L1 message sender submits `TransactionCancellationStarted` for a pending L1Handler tx at L1 block timestamp `T`.
3. Suppose node A (proposer) has local clock reading `T + timelock - 1` and node B (validator) has local clock reading `T + timelock + 1` (a 2-second skew, well within normal NTP tolerances).
4. Node A calls `get_txs`, which does not filter on cancellation state at all (only `Pending` records are proposable, but cancellation-started state removal from `proposable_index` is handled via `maintain_indices`/`is_proposable`); assume the tx was already staged/proposed prior to cancellation-request arrival, so A includes it in the proposal built via `get_txs`.
5. Node B calls `validate` for that tx hash; internally `validate_tx` calls `update_time_based_state(unix_now=T+timelock+1, ...)`, which transitions the record to `CancelledOnL2` and returns `Invalid(CancelledOnL2)`: [4](#0-3) 
6. Node B rejects the proposal even though node A's proposal was valid under A's own clock at proposal time, demonstrating honest-node divergence purely due to unsynchronized local wall clocks used for a deterministic-state-derived timelock check.

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

        let cutoff =

        let still_timelocked = self.consumed_queue.split_off(&BlockTimestamp(cutoff));
        let passed_timelock = std::mem::replace(&mut self.consumed_queue, still_timelocked);
        for tx_hashes in passed_timelock.values() {
            for tx_hash in tx_hashes {
                self.records.remove(tx_hash);
            }
        }
    }

    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }
