### Title
Free, gasless `MsgExecutePayload` flooding causes unbounded state growth and EVM computation DoS with no financial penalty for failed submissions - ([File: x/uexecutor/keeper/msg_execute_payload.go], [File: app/ante/account_init_decorator.go], [File: app/ante/fee.go], [File: app/txpolicy/gasless.go])

### Summary
The external report's core pattern — unprivileged users submitting requests that consume protocol resources but incur no cost when they don't follow through — has a native analog in Push Chain's gasless transaction policy. `MsgExecutePayload` is in the gasless allowlist and is callable by **any** account, not just bonded Universal Validators [1](#0-0) . Combined with `AccountInitDecorator`, which creates a brand-new on-chain account for any never-before-seen signer of a gasless tx and then short-circuits fee/gas checks [2](#0-1) , and `DeductFeeDecorator`, which skips fee deduction entirely for gasless messages [3](#0-2) , an attacker can generate unlimited fresh keypairs off-chain for free and submit a stream of self-signed `MsgExecutePayload` transactions that cost nothing on Push Chain while forcing real, permanent state writes and non-trivial EVM computation per submission.

### Finding Description
`IsGaslessTx` whitelists `MsgExecutePayload` unconditionally — there is no bonded/allowlisted-signer requirement for this message the way there is for `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta` (which additionally check `IsBondedUniversalValidator`) [4](#0-3) . This is intentional to allow "any account" to relay a UEA owner's pre-authorized payload without paying a Cosmos fee [5](#0-4) .

For every gasless tx whose `Signer` address has never been seen on-chain, `AccountInitDecorator.AnteHandle` performs its own lightweight signature check (against `account_number=0, sequence=0`) and then calls `ak.NewAccountWithAddress` + `SetAccount`, permanently persisting a new `BaseAccount` — before the rest of the ante chain (min-gas-price, deduct-fee, sig-count, full sig verification) ever runs [6](#0-5) . Because signing a message with a freshly generated key pair is computationally trivial and free, an attacker can produce an unbounded stream of distinct valid `Signer` addresses, each one causing:
1. A new persistent Cosmos account record (unbounded state growth, no rent/eviction mechanism visible), and
2. Full processing of `Keeper.ExecutePayload`, which calls the EVM factory to compute the UEA address (`CallFactoryToGetUEAAddressForOrigin`), checks the UEA balance, and — critically — if the (attacker-controlled) `UniversalAccountId` corresponds to a UEA address that the attacker has pre-funded with even 1 unit of `upc`, the handler will **auto-deploy a brand-new EVM smart contract (the UEA)** via `DeployUEAV2` [7](#0-6) , confirmed by the auto-deploy test path [8](#0-7) .

Fees for the *EVM-side* gas of `CallUEAExecutePayload`/`DeployUEAV2` are deducted from the UEA's own balance via `DeductGasFeesFromReceipt`, not the Cosmos signer [9](#0-8) , but the *Cosmos-layer* transaction itself — mempool admission, ante-chain execution, account creation, and (for pre-funded/self-owned UEAs) contract deployment triggering — costs the submitting `Signer` literally nothing, since `DeductFeeDecorator` and `MinGasPriceDecorator` both skip normal fee/min-gas enforcement for gasless messages [10](#0-9) .

This mirrors the external report's bug class precisely: legitimate protocol machinery (oracle jobs / here, UEA execution + EVM deployment) is invoked by unprivileged requesters who bear none of the true cost, enabling resource exhaustion of validator nodes (EVM execution, mempool/CheckTx cycles) and permanent state bloat (new accounts, new UEA contracts), without any rate-limit, deposit, or slashing mechanism gating the `MsgExecutePayload` gasless path.

### Impact Explanation
This is a denial-of-service vector reachable by any unprivileged external attacker (no validator/admin/TSS compromise required), fitting the in-scope "denial of service only when it is not network-level and is reachable without privileged control" category. The attacker can:
- Force unbounded growth of the account state trie at zero cost (each unique never-used address that signs a gasless `MsgExecutePayload` becomes a permanent `BaseAccount`).
- Force the chain to repeatedly execute EVM factory lookups, and — with minimal self-funding of precomputed UEA addresses with dust amounts — trigger repeated UEA contract deployments, consuming CPU/storage/gas-metering machinery on every validator without paying the network's normal EVM gas market rate through the Cosmos fee path.
- Do all of this in CheckTx/DeliverTx flows that bypass `MinGasPriceDecorator` and `DeductFeeDecorator`, meaning mempool spam-resistance mechanisms that rely on fees are ineffective for this message type.

This does not directly steal or drain funds, but it degrades chain liveness/performance for legitimate users and grows canonical on-chain state indefinitely — a resource-exhaustion/DoS impact under the allowed scope.

### Likelihood Explanation
Likelihood is high for the account-creation/mempool-spam component, since it requires only generating key pairs and crafting well-formed `MsgExecutePayload` envelopes (ValidateBasic only checks structural validity, not actual UEA ownership or verification-data authenticity against a real UEA) [11](#0-10) . The UEA auto-deploy amplification requires the attacker to pre-fund the precomputed UEA address with a small amount of `upc`, which is cheap and attacker-controlled. I was not able to fully verify from the indexed code whether there is a separate mempool-level rate limiter, per-account gasless-tx quota, or state-rent/pruning mechanism elsewhere in the codebase that might mitigate this; the search did not surface any such control in `app/ante/`, `app/txpolicy/`, or `x/uexecutor/`.

### Recommendation
- Introduce a bonded/staked or deposit-based admission gate (or per-signer rate limiting with a bond/slashing mechanism) for gasless `MsgExecutePayload` submissions, especially for the account-creation code path in `AccountInitDecorator`.
- Consider requiring a minimal Cosmos-level fee or refundable deposit for first-time gasless account creation to prevent unbounded free state growth.
- Gate or fee-meter the UEA auto-deploy-on-execute path (`msg_execute_payload.go` lines 57-78) so that deploying a new contract via a gasless message is not effectively free for the Cosmos-layer submitter.
- Add per-block or per-IP/per-signer submission caps for gasless message types in the mempool/ante pipeline.

### Proof of Concept
Conceptual (not independently executed against a live devnet):
1. Generate N fresh keypairs locally (free, no chain interaction).
2. For each keypair, compute the CAIP-2 `UniversalAccountId`/derived UEA address via the factory (`CallFactoryToGetUEAAddressForOrigin`, a read-only call).
3. Send a small amount of `upc` (e.g. 1 unit) to each precomputed UEA address.
4. Submit N `MsgExecutePayload` transactions, each signed by a distinct never-before-used `Signer` key, with `VerificationData` that need not even be valid for execution to succeed (execution failure post-account-creation still leaves the new account and, per the auto-deploy branch, the deployed UEA, persisted; see `DeductGasFeesFromReceipt` is called regardless of `execErr`) [12](#0-11) .
5. Each transaction bypasses `MinGasPriceDecorator` and `DeductFeeDecorator` (gasless), creates a new `BaseAccount`, and can trigger `DeployUEAV2` — at zero Cosmos-fee cost to the attacker, repeated indefinitely.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

// ValidateBasic does a sanity check on the provided data.
func (msg *MsgExecutePayload) ValidateBasic() error {
	// Validate signer
	if _, err := sdk.AccAddressFromBech32(msg.Signer); err != nil {
		return errors.Wrap(err, "invalid signer address")
	}

	// Validate universalAccountId
	if msg.UniversalAccountId == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal account cannot be nil")
	}

	// Validate universal payload
	if msg.UniversalPayload == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal payload cannot be nil")
	}

	// Validate verificationData
	if len(msg.VerificationData) == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "verificationData cannot be empty")
	}
	if _, err := hex.DecodeString(strings.TrimPrefix(msg.VerificationData, "0x")); err != nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "invalid verificationData hex")
	}

	// Validate universalAccountId structure
	if err := msg.UniversalAccountId.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universalAccountId")
	}

	// Validate universal payload structure
	if err := msg.UniversalPayload.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universal payload")
	}

	return nil
}
