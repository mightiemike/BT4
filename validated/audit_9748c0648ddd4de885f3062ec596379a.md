Findings from investigation: The CVE-2017-8834 bug class is an unbounded/unvalidated memory allocation in a C parser where a length value derived from parser state is used to allocate memory without validating it against the actual remaining input size, causing a memory allocation failure (DoS).

In protobuf-go, the equivalent allocation-sensitive paths are guarded against this exact issue:

- `protowire.ConsumeBytes` validates the length-prefixed value against the actual remaining buffer length before returning (`m > uint64(len(b[n:]))` is rejected), so no downstream allocation can ever request more than the bytes actually present in the input. [1](#0-0) 

- The generated/codegen `consume*Slice` functions (e.g., `consumeInt32Slice`, `consumeUint32Slice`, `consumeFixed32Slice`) compute a preallocation `count` derived from the actual bytes present in the already-length-validated buffer (`len(b)` or a scan of `b`), then call `grow*Slice(count)` — this is bounded by real input size, not an attacker-supplied claim. [2](#0-1) 

- `protodelim.UnmarshalFrom`, which parses a varint size-delimited message and does `make([]byte, size)`, explicitly enforces a `MaxSize` (default 4 MiB) check against the parsed size before allocating, specifically to prevent this class of issue. [3](#0-2) 

- `internal/protolazy/bufferreader.go`'s `SkipBytes`/`Skip` also bound-check against the actual buffer length (`len(b.Buf) < b.Pos+n`) before advancing, preventing unbounded skip/allocate operations. [4](#0-3) 

No code path in scoped production protobuf-go allocates memory based on an untrusted length value without first validating it against the actual remaining buffer size, so the libcroco analog (unchecked allocation size causing a memory allocation error) does not reproduce here.
