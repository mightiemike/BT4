### Title
Universal Executor mints PRC20 based on the emitted `bridgeAmount` value with no independent balance verification, allowing fee-on-transfer or rebasing tokens to inflate synthetic supply - (File: x/uexecutor/keeper/handler.go, universalClient/chains/evm/event_parser.go)

### Summary
The RoyaltyVault/Splitter bug class is "accounting trusts a nominal transfer amount instead of the actual balance delta, so fee-on-transfer (FoT) or rebasing tokens cause over/under-accounting." The Push Chain analog is the inbound deposit path: the amount that gets minted as PRC20 on Push Chain is taken verbatim from the source-chain gateway's emitted `bridgeAmount` value, never cross-checked against an actual balance-delta of the vault, and never re-validated against the PRC20's own transfer semantics at deposit time.

### Finding Description
When a `sendFunds` gateway event fires on an external chain, `universalClient/chains/evm/event_parser.go`'s `parseUniversalTxEvent` extracts the amount purely from the ABI-encoded log data: [1](#0-0) 

This value becomes `Inbound.Amount`, is voted on by Universal Validators (each independently reading the same log, so honest-validator consensus is preserved on the *declared* number, not the *actual* number), and then flows unmodified into `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit`, which mints exactly that amount of PRC20 to the recipient with no balance check: [2](#0-1) [3](#0-2) [4](#0-3) 

None of these steps ever compare the reported `bridgeAmount` against an actual balance-before/balance-after measurement of the vault contract holding the underlying asset. If a registered token behaves like a FoT or rebasing token (e.g., it charges a transfer fee, deflates on transfer, or the vault's actual custodied balance ends up lower than the amount recorded in the event), Push Chain will still mint the full nominal amount as PRC20 — exactly the RoyaltyVault pattern of trusting `splitterShare` instead of `balanceAfter - balanceBefore`. The reverse direction (outbound release) has the same defect: `handleFailedOutbound` re-mints `outbound.Amount` verbatim via `CallPRC20Deposit` without checking whether that amount was actually recovered: [5](#0-4) 

### Impact Explanation
Any deposit of a fee-on-transfer or rebasing token whose vault-side received balance is less than the reported/nominal amount results in PRC20 minted on Push Chain that is not fully backed by the corresponding asset held on the source chain. This corrupts PRC20 accounting (an unbacked mint), and because PRC20 is fungible and freely transferable/redeemable via outbound withdrawal, later users attempting to redeem/bridge back can drain the vault, leaving the last redeemer unable to withdraw — the identical "last user cannot claim" failure mode described in the report. This is a real fund-accounting corruption issue reachable purely from an ordinary user's deposit of a registered token that has these properties (no privileged action beyond a chain-admin having listed such a token in the registry, which is a routine listing decision, not an attack).

### Likelihood Explanation
Likelihood is moderate: it requires a registered token (source_chain + assetAddr present in `uregistry`'s token config) to exhibit fee-on-transfer or rebasing behavior. Such tokens exist on all EVM chains Push Chain plans to support (e.g., certain deflationary/rebasing ERC20s), and nothing in the reviewed registry/keeper code path (`GetTokenConfig`, `depositPRC20`, `CallPRC20Deposit`) rejects or accounts for this token class. The vulnerability does not require a malicious validator, relayer, or admin — only that a supported token has this transfer semantics, or that a user deposits an already-listed token that happens to have such behavior (some tokens change transfer-fee parameters after listing).

### Recommendation
- Document explicitly that FoT/rebasing tokens must not be registered as supported assets in `uregistry`, or
- If support is required, have the Universal Validators independently observe the vault's actual balance delta (pre/post the deposit transaction) on the source chain rather than trusting the event's nominal `bridgeAmount`, and only mint the PRC20 amount that corresponds to the verified balance increase. This requires extending the vote/consensus payload to include an attested balance-delta and validating it deterministically across all voting validators to preserve consensus safety.
- Apply the same fix symmetrically to the outbound refund/re-mint path (`handleFailedOutbound`, `applyGasRefund`) so a shortfall on the destination chain is not blindly re-credited as PRC20 on Push Chain.

### Proof of Concept
1. Chain admin registers token `T` (an ERC20 that charges, say, a 2% fee on every `transfer`/`transferFrom`) in `uregistry` with a `NativeRepresentation` PRC20 contract.
2. A user calls the gateway's `sendFunds(T, 1_000_000, ...)`. The gateway/vault contract records (and emits) `bridgeAmount = 1_000_000`, but due to `T`'s fee-on-transfer logic, the vault's actual `T` balance only increases by `980_000`.
3. Universal Validators observe the `sendFunds` log, agree on `Amount = "1000000"` (per `parseUniversalTxEvent`, lines 169–174), and vote `MsgVoteInbound`.
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints `1,000,000` PRC20-T to the recipient (`x/uexecutor/keeper/execute_inbound_funds.go` lines 24–30; `x/uexecutor/keeper/handler.go` lines 12–46), even though only `980,000` of the underlying `T` is actually custodied by the vault.
5. Total PRC20-T supply on Push Chain now exceeds the vault's real `T` reserve by `20,000` per such deposit. Repeated across many users, an eventual outbound redemption request cannot be fully honored by the vault, leaving the last redeemer's outbound stuck/failed — mirroring the original RoyaltyVault "last claimant gets nothing" scenario.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```

```go
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
```
