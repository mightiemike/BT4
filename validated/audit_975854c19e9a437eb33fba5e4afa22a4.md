## Finding: Replay-Verify Silently Accepts State-Root Divergence Because `ensure_match_transaction_info` Skips Checkpoint-Hash Comparison

### Title
State checkpoint / hot-state / position-state root hashes are never compared in `TransactionOutput::ensure_match_transaction_info`, letting replay-verify accept a state root that diverges from the authenticated ledger - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single function used by all "replay and compare against ground truth" flows (chunk-executor's `verify_execution`, `db-tool`'s `replay_on_archive`, and the `aptos-move/cli` debug-replay command) to confirm that locally re-executed transactions match the authenticated `TransactionInfo` recorded on-chain. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — this is documented in-line as a known, intentional gap.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  verifies only:
- transaction status vs `txn_info.status()`
- `gas_used()`
- `write_set` hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

It then contains the following explicit TODO instead of a check: [2](#0-1) 

This comment confirms the state-checkpoint hash, the hot-state checkpoint hash, and the `position_state_checkpoint_hash` — the exact fields that bind a transaction's execution result to the Jellyfish Merkle state root, hot-state root, and position-state root — are never validated against the values re-derived by local re-execution.

These checkpoint hashes are computed independently during normal commit in `assemble_transaction_infos`: [3](#0-2) , which folds them into `TransactionInfo` and ultimately the transaction accumulator that gets signed by validators (`LedgerInfoWithSignatures`). The whole point of "replay-verify" tooling is to catch cases where re-executing archived transactions produces a *different* state root than what was actually committed/signed on mainnet (i.e., to catch state-divergence/hard-fork bugs before or after they occur). But because `ensure_match_transaction_info` never compares these root hashes, that class of divergence is invisible to the tool.

The function is consumed by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, called during `--verify-execution` chunk replay [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify` path, the dedicated mainnet/testnet replay-verify tool [5](#0-4) 
- `aptos-move/cli/src/commands.rs` transaction-replay/debugging command [6](#0-5) 

In all three, a wrong or maliciously-crafted state/hot-state/position-state root emitted by local execution (e.g. due to a state-computation bug, or a corrupted/mismatched archive backup) will pass verification as long as status/gas/write-set/events match, because the comparator never inspects the checkpoint-hash fields carried by `TransactionInfo`.

### Impact Explanation
This falls squarely into the "Hard-fork-only divergence during commit, replay, restore, or proof verification" category. Aptos's replay-verify infrastructure (`testsuite/replay-verify`, `db-tool replay-on-archive`, chunk-executor `--verify-execution`) exists specifically to catch state-root-diverging bugs in the VM/executor before they can cause a chain split or before an operator trusts a corrupted backup/archive. With this check disabled, a systemic state-computation bug that corrupts the Merkle state root (or hot-state root, or the newer position-state/"trading-native" root) — while still producing byte-identical write sets, gas usage, and events — would be silently reported as "verified" instead of failing loudly. This directly undermines the authenticated-state guarantee the tooling is meant to provide and could allow a broken state root to go undetected across a full archive replay/restore/verification cycle.

### Likelihood Explanation
The gap is unconditional and always present whenever `ensure_match_transaction_info` is invoked — it is not behind an unfinished-feature flag it merely warns about, it's already live code executed on every replay/verify call. The TODO explicitly says this must be fixed "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS", implying the check is currently disabled by omission rather than gated. Any bug (not necessarily malicious) that corrupts the state/hot-state/position-state checkpoint hash while leaving write-set/gas/events unchanged is completely undetectable by these tools today.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s locally re-derived `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when computed/available) against the corresponding fields on `txn_info`, mirroring the existing `write_set_hash`/`event_root_hash` checks, before any code path that relies on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or general replay-verify correctness is trusted.

### Proof of Concept
1. Take any transaction/backup pair with correct write set, events, gas, and status but an intentionally corrupted `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) in the persisted `TransactionInfo` (simulating a bug that miscalculates the state root while leaving all other fields byte-correct).
2. Run `db-tool replay-on-archive` or chunk-executor `--verify-execution` against this data.
3. Observe `ensure_match_transaction_info` at [7](#0-6)  returns `Ok(())` despite the state root mismatch, because no comparison against the checkpoint-hash fields is performed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

impl Opt {
    pub async fn run(self) -> Result<()> {
        let verifier = Verifier::new(&self)?;
        let all_errors = verifier.run()?;
        if !all_errors.is_empty() {
            error!("{} failed transactions", all_errors.len());
            for e in all_errors {
                error!("Failed: {}", e);
