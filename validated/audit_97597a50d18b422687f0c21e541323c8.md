### Title
Webhook `domain`/shop header is never covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
`shopify.webhooks.validate()`/`process()` treats a webhook request as authentic for whatever shop is named in the `X-Shopify-Shop-Domain` (or events `domain`) header, but the HMAC signature that "proves" the request came from Shopify only covers the raw body bytes, never the header set.

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  reads the `hmac` header, then calls `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — the signed message is only `rawBody`. `checkWebhooksHeaders`/`checkEventsHeaders` in [2](#0-1)  then separately read `topic`, `domain`, `apiVersion`, `webhookId`, etc. straight from the (unsigned) request headers and merge them into the same `valid: true` result object as the HMAC check, with no cross-check ensuring the `domain` belongs to the shop whose secret actually produced the HMAC. Downstream, `authenticateWebhookFactory` in both `shopify-app-remix` and `shopify-app-react-router` trusts `check.domain` outright to look up the offline session: [3](#0-2) , and `packages/apps/shopify-api/lib/webhooks/process.ts` passes `webhookCheck.domain` straight into the app's callback (`packages/apps/shopify-api/lib/webhooks/process.ts:146-156`). This is analogous to the PoolTogether finding: code assumes that the value proven authentic by one mechanism (HMAC over `rawBody`, i.e. "the operator") is inseparable from a second, merely-asserted value (the `domain` header, i.e. "the user"), when in fact an attacker who legitimately controls one shop can send Shopify-signed payloads for their own store while attaching an arbitrary `domain` header naming a victim shop, since the same `apiSecretKey` is shared across every shop that installs the app.

### Impact Explanation
Because the app's own client secret (`apiSecretKey`) is shared by all shops of a multi-tenant app, an attacker who installs the app on their own shop (or self-triggers webhooks) can produce a body+HMAC pair that is 100% valid per `validateHmacString`, then relay/craft an HTTP POST to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `process()`/`authenticateWebhookFactory` will accept it as `valid: true`, resolve `check.domain` to the victim, load the victim's offline session/access token, and execute the app's webhook handler with attacker-controlled `rawBody` under the victim's identity — causing cross-tenant data corruption/spoofed events for any app whose handler logic branches on `topic`/`domain` from `check`/`webhookCheck` (e.g., processing an "orders/create" payload as if the victim shop generated it).

### Likelihood Explanation
Requires only that the attacker be able to install the app themselves (any public/unlisted app satisfies this) and be able to submit an arbitrary POST with attacker-chosen headers to the app's public webhook endpoint — no privileged access, no secret leakage, and no MITM needed. This is directly reachable by "a single merchant" per the validation criteria.

### Recommendation
Include the security-relevant headers (`domain`/shop, `topic`, `api-version`, `webhook-id`) in the HMAC-signed message, or independently verify that `domain` corresponds to a shop actually authorized/installed for this app instance (e.g., cross-check against a known/expected shop before trusting `check.domain` for session lookup), rather than deriving trust for the header purely from a signature computed over the body alone.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook (e.g. `orders/create`) with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared `apiSecretKey`.
2. Attacker replays this exact `rawBody`+`hmac` pair to the app's webhook endpoint but swaps the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
3. `validateFactory` → `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:189-197`) validates HMAC successfully (it only checked `rawBody`), and `checkWebhooksHeaders` (`packages/apps/shopify-api/lib/webhooks/validate.ts:127-134`) returns `{valid: true, domain: 'victim-shop.myshopify.com', topic: 'ORDERS_CREATE', ...}`.
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:52`), loading the victim's stored offline session/access token, and the app's registered handler runs with attacker-supplied payload data but victim-shop context/credentials.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
