### Title
Unchecked Bancor-curve output in `ExchangeCapsule.transaction()` can drive TRC10 Exchange pool balances negative, corrupting shared pool accounting - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The reported bug is a class of "unchecked subtraction from a shared accounting variable using a user-controlled amount, which can push the value negative and corrupt/brick shared protocol state." The closest reachable analog in java-tron is the TRC10 `Exchange` (Bancor-style AMM) system. `ExchangeCapsule.transaction()` computes an output amount (`buyTokenQuant`) from a floating-point Bancor curve and then subtracts it from the pool's own balance. Unless the governance-gated `ALLOW_HARDEN_EXCHANGE_CALCULATION` parameter is active, this subtraction is performed as a raw `long - long` with **no bound check** before being persisted, so any pool-balance invariant violation (negative balance) is written straight into on-chain state via `ExchangeTransactionActuator`, corrupting the market for all subsequent users — exactly the "unenforced accounting invariant, checked-too-late" pattern from the `ProfitManager.notifyPnL` finding.

### Finding Description
`ExchangeCapsule.transaction()` has two code paths depending on `hardenedCalc`: [1](#0-0) 

In the non-hardened path (the default unless a `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal has been passed by the committee, gated behind `ForkBlockVersionEnum.VERSION_4_8_2`), the new balances are computed as plain `long` subtraction/addition with **no check that the result is non-negative**:
```
newSecondTokenBalance = secondTokenBalance - buyTokenQuant;
...
newFirstTokenBalance = firstTokenBalance - buyTokenQuant;
```
Only the hardened path validates the invariant:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
```
`buyTokenQuant` itself is produced by `ExchangeProcessor.exchangeFromSupply()`, which relies on `double`/`Math.pow` floating point arithmetic: [2](#0-1) 

Floating-point rounding in the Bancor formula (particularly for extreme `sellTokenQuant` values relative to pool balance) can yield an output that is not strictly bounded below the actual pool balance in the way exact rational math would guarantee.

Crucially, `ExchangeTransactionActuator.doValidate()` — unlike `ExchangeWithdrawActuator`, which explicitly checks `if (firstTokenBalance < tokenQuant || secondTokenBalance < anotherTokenQuant) throw new ContractValidateException("exchange balance is not enough")` — performs **no such balance-sufficiency check** for the AMM `transaction()` path. It only checks slippage against `tokenExpected`: [3](#0-2) 

`execute()` then re-invokes `exchangeCapsule.transaction(...)` on a freshly-loaded capsule and unconditionally persists the result: [4](#0-3) 

The `allowHarden()`/`subtractExact` wrappers used elsewhere in the actuator are gated the same way: [5](#0-4) 

So, absent the hardening proposal being active, there is no code path that stops a pool-balance underflow from being committed to `ExchangeStore`/`ExchangeV2Store`.

### Impact Explanation
If a pool balance is driven negative (or a floating-point edge case yields an output larger than the counter-asset's balance), the on-chain `Exchange`/`ExchangeV2` object's invariant is broken:
- Subsequent trades against that exchange operate on a corrupted `firstTokenBalance`/`secondTokenBalance`, producing incorrect exchange rates for every future participant (mirrors the report's "market becomes unusable" impact).
- Depending on the resulting value, later `Math.pow`/BigDecimal computations in `ExchangeProcessor`/`SafeExchangeProcessor` operating on a negative balance can throw unexpected `ArithmeticException`s or produce nonsensical rates, effectively bricking that TRC10 exchange pair for all users — analogous to `notifyPnL` reverting and freezing the credit market.
- No TRX/TRC10 tokens are directly stolen from other accounts by this path alone, but the shared AMM state (used by all traders on that pair) becomes permanently inconsistent, matching the "medium severity — unusable market, no direct fund theft" classification given to the original finding.

### Likelihood Explanation
Reachability is unprivileged: any account can call `ExchangeTransactionContract` against any live TRC10 `Exchange` pool with attacker-chosen `tokenQuant`. The hardened-math protection (`ALLOW_HARDEN_EXCHANGE_CALCULATION`) is not the default; it requires an explicit committee-passed proposal (gated by `ForkBlockVersionEnum.VERSION_4_8_2`), so any network/testnet/private chain that has not yet enabled it remains exposed. The floating-point precision edge case needed to push a Bancor-curve output past the real pool balance requires carefully chosen extreme `tokenQuant` values near the balance limit, which raises the bar somewhat, similar to the "likelihood: medium" rating the sponsor/judge gave the original report for needing an unusual but plausible large-position scenario.

### Recommendation
- Make the balance non-negativity check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) unconditional in `ExchangeCapsule.transaction()`, not only under `hardenedCalc`, mirroring the report's recommendation to clamp/guard the result rather than allow it to violate the invariant.
- Add an explicit `ContractValidateException` in `ExchangeTransactionActuator.doValidate()` verifying `anotherTokenQuant` does not exceed the actual counter-asset pool balance, consistent with the check already present in `ExchangeWithdrawActuator`.
- Consider migrating the default (non-proposal-gated) code path to the `BigDecimal`-based `SafeExchangeProcessor` to eliminate floating-point rounding risk entirely, rather than relying on governance to opt in.

### Proof of Concept
1. Create a TRC10 `Exchange` pool with small counter-asset balance (e.g., `secondTokenBalance = X`) while `ALLOW_HARDEN_EXCHANGE_CALCULATION` is not enabled (default state).
2. Submit an `ExchangeTransactionContract` with a `tokenQuant` chosen so that the Bancor-curve computation in `ExchangeProcessor.exchangeFromSupply()` (double/`Math.pow` math) returns `buyTokenQuant` at or marginally exceeding `secondTokenBalance`.
3. `ExchangeTransactionActuator.doValidate()` performs no check preventing this (only slippage vs. `tokenExpected`), so `execute()` proceeds and calls `exchangeCapsule.transaction(...)`, which (non-hardened) sets `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` without a floor check, and `Commons.putExchangeCapsule(...)` persists the corrupted (negative or invariant-violating) balance to `ExchangeStore`/`ExchangeV2Store`.
4. All subsequent trades against this exchange pair now operate on corrupted state, reproducing the "system enters an unusable/inconsistent state via unchecked accounting subtraction" pattern described in the source report.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
