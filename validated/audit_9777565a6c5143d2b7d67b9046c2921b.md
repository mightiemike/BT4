Confirmed: the global class cache (`GlobalContractCache`, used by `NativeClassManager`/`ContractClassManager`) has no revert-aware invalidation logic [1](#0-0) , and the only place the sequencer re-validates a cached class against current chain state is `get_compiled_from_class_manager`, which explicitly skips this check for `RunnableCompiledClass::V0` while performing it for Cairo1 classes.

### Title
Stale cached Cairo0 (deprecated) class bypasses declaration re-verification after state revert - (File: `crates/blockifier/src/state/state_reader_and_contract_manager.rs`)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from the process-wide `ContractClassManager` cache whenever present, but re-verifies against the current chain state (`is_declared`) only for Cairo1 (`V1`/`V1Native`) classes — Cairo0 (`V0`) cache hits are returned unconditionally.

### Finding Description
`get_compiled_from_class_manager` reads from the shared `ContractClassManager` global cache. For non-V0 classes it explicitly re-checks `self.state_reader.is_declared(class_hash)` before trusting the cache, with a comment stating this exists because "the cache does not guarantee [declaration], it might contain a declared class from a reverted block" [2](#0-1) . The `V0` branch performs no equivalent check and returns the cached class directly. This asymmetry is deliberate, because `FetchCompiledClasses::is_declared` is defined to query only the Cairo1 `declared_classes` block-number table (via `get_class_definition_block_number`) and is documented to always return `false` for Cairo0 classes [3](#0-2) , so no analogous "is Cairo0-declared" primitive is wired into this path.

The global class cache itself (`RawClassCache`/`GlobalContractCache`) has no notion of block height or state revert — entries persist across reverts indefinitely [1](#0-0) . Combined, this means: once a Cairo0 class has been declared and executed at least once (populating the cache via `set_and_compile`), if the block(s) that declared it are later reverted — storage-side deletion is handled by `revert_state_diff`/`delete_deprecated_declared_classes` [4](#0-3)  — the class remains servable from the in-memory cache with no re-verification, exactly mirroring the reported `SwapHelper.getCalldata()` pattern where `routerTypes`/`swapInfos` remained usable after `whitelistedRouters` was flipped to `false` because the dependent caches were never invalidated or re-checked.

### Impact Explanation
After a legitimate revert (e.g., an L1-triggered reorg causing the sequencer to roll back a block that declared a Cairo0 class), any subsequent transaction (deploy/invoke) referencing that class hash will still successfully retrieve and execute the stale bytecode from the sequencer's in-process class cache, instead of failing with `StateError::UndeclaredClassHash` as the persisted state (and any node without a warm cache) would dictate. This can cause: (1) execution of code for a class that is not actually declared in the current committed state, and (2) honest-node divergence between a node whose cache is warm (accepts the tx, executes deprecated bytecode) and a node whose cache is cold or that restarted (rejects the tx as undeclared), leading to a wrong committed state root / block hash for that block.

### Likelihood Explanation
Requires a prior revert of a block that declared a Cairo0 class, which is an operational event (e.g., L1 reorg handling), not attacker-forged; it is not "malicious-operator" abuse. Given that condition has occurred, triggering the divergence needs only an ordinary transaction from any unprivileged sender referencing the previously-declared, now-reverted class hash — no special privileges are required at the trigger step.

### Recommendation
Apply the same re-verification performed for `V1`/`V1Native` classes to the `V0` branch in `get_compiled_from_class_manager`: add a Cairo0-aware "is currently declared" check (e.g., querying the deprecated-classes declaration table/block number) and return `StateError::UndeclaredClassHash` on failure, mirroring how the reported `SwapHelper` fix set `routerTypes` back to `UNSET` on delist instead of leaving stale state reachable.

### Proof of Concept
1. Declare and deploy a Cairo0 (deprecated) class at block N; invoking it populates `ContractClassManager`'s global cache with `CompiledClasses::V0`.
2. Revert block N (e.g., simulate the sequencer's `revert_state_diff` path), which deletes the class's storage-side declaration entries [5](#0-4) , but does not touch `ContractClassManager`'s in-memory cache.
3. Submit an INVOKE/DEPLOY transaction referencing the same (now undeclared) class hash. `get_compiled_from_class_manager` hits the cache, matches `RunnableCompiledClass::V0(_) => {}` (no verification), and returns the stale bytecode [6](#0-5) , executing successfully where a cold-cache/compliant node would raise `StateError::UndeclaredClassHash`.
