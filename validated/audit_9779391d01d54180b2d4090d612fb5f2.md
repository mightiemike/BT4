### Title
Replay-verify `ensure_match_transaction_info` omits checkpoint-hash validation, masking state-root divergence - (types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by db-tool's `replay_on_archive` (and `aptos-debugger`) to confirm that locally re-executed transaction outputs match the authenticated `TransactionInfo` committed to the ledger accumulator. Since `TransactionInfoV1` added `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields, the comparator was never extended to validate them, so a divergence in any of these committed state roots is silently accepted as a "successful" replay.

### Finding Description
`ensure_match_transaction_info` validates transaction status, gas used, write-set hash against `state_change_hash`, and event root hash, but explicitly skips the checkpoint-hash fields as documented in its own trailing `TODO(trading-native)` comment: [5](#0-4)  These checkpoint hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are part of `TransactionInfoV1`, which is hashed and included in the transaction accumulator as the authenticated, consensus-committed record of a transaction's execution result [3](#0-2) . These fields are gated by on-chain feature flags `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` [6](#0-5) , meaning as these features roll out, more of the authenticated per-transaction state is carried in fields that this comparator ignores.

The comparator is directly relied upon by `db-tool`'s `replay_on_archive::Verifier::execute_and_verify`, which re-executes transactions from a backup/archive and treats a non-error return from `ensure_match_transaction_info` as proof the replay reproduced the authenticated ledger state [7](#0-6) .

### Impact Explanation
`replay_on_archive`/replay-verify tooling is the mechanism operators and auditors use to detect hard-fork-only divergence — i.e., cases where re-executing history under a new binary yields a different state root than what was actually committed on mainnet. Because the checkpoint-hash fields (including the position/hot-state roots now bound into `TransactionInfoV1`) are excluded from the comparison, a local execution bug that corrupts hot-state or native-position state roots — while still producing matching write-set/event/gas/status — will pass replay verification undetected. This is exactly the "hard-fork-only divergence during commit, replay, restore, or proof verification" impact category: the tool that is supposed to catch state-commitment divergence is blind to the newest class of committed state roots.

### Likelihood Explanation
No privileged access is required — this triggers whenever replay-verify tooling is run against transactions that use the newer `TransactionInfoV1` checkpoint fields (increasingly likely as `HOTNESS_IN_EPILOGUE`, `HOT_STATE_ROOT_IN_TXN_INFO`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` features are enabled). The gap is unconditional and always present in the current comparator logic, not dependent on attacker-controlled input, so any bug in the new hot-state/position-state root computation would consistently go unflagged by replay-verify until an unrelated invariant check happens to catch it downstream.

### Recommendation
Extend `ensure_match_transaction_info` to validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the recomputed roots whenever these fields are present in the expected `TransactionInfo` (mirroring how `state_change_hash` and `event_root_hash` are already checked), before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` for production use, as the existing TODO comment itself calls for.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` + `HOT_STATE_ROOT_IN_TXN_INFO` (and/or `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) so `TransactionInfoV1.hot_state_checkpoint_hash`/`position_state_checkpoint_hash` carry real committed roots.
2. Introduce (or trigger) a divergence in hot-state/position-state root computation during local re-execution such that write-set hash, event root, gas, and status still match the archived `TransactionInfo`, but the checkpoint hash would differ.
3. Run `db-tool replay-on-archive` (or `aptos-debugger`) over the affected version range; `execute_and_verify` → `ensure_match_transaction_info` returns `Ok(())` because it never compares the checkpoint-hash fields, so the tool reports a clean replay despite the authenticated state root having diverged.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
