### Title
`migrate_builtin_to_core_bpf` under-counts `old_data_size` for prefunded `program_data_address`, corrupting `accounts_data_size_delta_off_chain` - (File: `runtime/src/bank/builtins/core_bpf_migration/mod.rs`)

### Summary
When `allow_prefunded=true`, `TargetBuiltin::new_checked` accepts an attacker-created System-owned account at `program_data_address` and records its lamports in `program_data_account_lamports`, but silently drops its data length. `migrate_builtin_to_core_bpf` then overwrites that account via `store_account` while computing `old_data_size` from only `program_account` and `buffer_account`, omitting the prefunded account's pre-existing data length from the size-delta bookkeeping.

### Finding Description
`TargetBuiltin::new_checked` (`runtime/src/bank/builtins/core_bpf_migration/target_builtin.rs:57-82`) allows a System-program-owned account to already exist at `program_data_address = get_program_data_address(builtin_program_id)` when `allow_prefunded` is set, capturing only `account.lamports()` into `program_data_account_lamports`. The struct never records or returns that account's `data().len()`. [1](#0-0) 

In `migrate_builtin_to_core_bpf`, `old_data_size` is computed as `checked_add(target.program_account.data().len(), source.buffer_account.data().len())`, which never includes any length from `target.program_data_address`'s prior content — even though `program_data_account_lamports` (correctly) accounts for that account's lamports in `lamports_to_burn`. [2](#0-1) [3](#0-2) 

The function then unconditionally overwrites `target.program_data_address` with `new_target_program_data_account` via the raw `store_account` (not `store_account_and_update_capitalization`, which independently tracks data-size deltas), and finally applies the manually computed `old_data_size`/`new_data_size` to `calculate_and_update_accounts_data_size_delta_off_chain`. [4](#0-3) [5](#0-4) 

Because lamports are correctly burned for the prefunded account but its data length is never subtracted from `old_data_size`, `calculate_data_size_delta(old_data_size, new_data_size)` computes an inflated delta whenever the attacker's prefunded account has non-zero data length. This makes `accounts_data_size_delta_off_chain` (and therefore `load_accounts_data_size()`) diverge from the true, independently-computed sum of all committed account sizes — the exact invariant the question targets. The same bug pattern exists identically in `TargetBpfV2::new_checked` / `upgrade_loader_v2_program_with_loader_v3_program` (`runtime/src/bank/builtins/core_bpf_migration/target_bpf_v2.rs:49-74`, `mod.rs:432-439`). [6](#0-5) 

No existing guard rejects this: `new_checked` explicitly permits (rather than rejects) an existing System-owned account with data at that address when `allow_prefunded` is true, and only rejects it if the owner is not the System Program.

### Impact Explanation
This is a deterministic accounting bug, not a consensus-fork/hash bug: every honest validator executing the same feature-activation migration with the same attacker-prefunded account state will compute the same (wrong) `old_data_size`/delta, so it does not by itself cause a bank-hash mismatch between honest nodes. The concrete impact is that `bank.accounts_data_size_delta_off_chain` — and thus `load_accounts_data_size()`, which gates the network-wide accounts-data-size cap used to bound total on-chain storage growth — becomes permanently and silently wrong (overstated growth is actually undercounted removal, i.e., the tracked size ends up smaller than the real on-disk size), by exactly the byte length the attacker chose to prefund with (up to `MAX_PERMITTED_DATA_LENGTH`). This falls under "accounting/state divergence" rather than the stronger "HASH_DETERMINISM" claim in the prompt, since I could not confirm from available context that `accounts_data_size_delta_off_chain` is itself part of the consensus bank hash or of the serialized snapshot fields that must match between snapshot-generation and replay (this would require verifying snapshot (de)serialization code, which was not found in the indexed context).

### Likelihood Explanation
Exploitability only requires an unprivileged attacker who can create/fund an arbitrary System-program-owned account at a deterministic address (`program_data_address`) before a Core BPF migration feature activates for a target builtin with `allow_prefunded=true`. This is achievable with an ordinary `system_instruction::create_account`/`transfer`+allocate at that address, no elevated privileges needed. However, exploitation depends on migration configs actually using `allow_prefunded=true` for a real (non-test) migration and on the attacker being able to predict/front-run which builtin will be migrated and pre-fund its `program_data_address` before the feature-gated migration runs on-chain — a narrow but plausible window tied to migration rollout timing.

### Recommendation
Track the prefunded `program_data_address` account's data length in `TargetBuiltin`/`TargetBpfV2` (alongside `program_data_account_lamports`) and include it as a third term in `old_data_size` in `migrate_builtin_to_core_bpf` and `upgrade_loader_v2_program_with_loader_v3_program`, matching the treatment already given to lamports in `lamports_to_burn`.

### Proof of Concept
```rust
// runtime/src/bank/builtins/core_bpf_migration/mod.rs (tests module)
#[test_case(0)]
#[test_case(1024)]
#[test_case(MAX_PERMITTED_DATA_LENGTH as usize)]
fn test_migrate_builtin_prefunded_data_size_accounting(prefund_data_len: usize) {
    let mut bank = create_simple_test_bank(0);
    let builtin_id = Pubkey::new_unique();
    let source_buffer_address = Pubkey::new_unique();

    // Set up builtin as in test_migrate_builtin.
    let builtin_name = String::from("test_builtin");
    let account = AccountSharedData::new_data(1, &builtin_name, &native_loader::id()).unwrap();
    bank.store_account_and_update_capitalization(&builtin_id, &account);
    bank.add_builtin(builtin_id, builtin_name.as_str(),
        ProgramCacheEntry::new_builtin(0, NoopBuiltin::register));

    // Attacker prefunds program_data_address with System-owned account, non-zero data.
    let program_data_address = get_program_data_address(&builtin_id);
    let prefund_account = AccountSharedData::new(
        1_000_000, prefund_data_len, &solana_sdk_ids::system_program::ID,
    );
    bank.store_account_and_update_capitalization(&program_data_address, &prefund_account);

    let test_context = TestContext::new(&bank, &builtin_id, &source_buffer_address, None);

    // Ground truth: sum of all account sizes removed/added, including the prefunded account.
    let expected_delta_from_ground_truth =
        bank.accounts_data_size_delta_off_chain.load(Relaxed)
        - bank.get_account(&builtin_id).unwrap().data().len() as i64
        - bank.get_account(&source_buffer_address).unwrap().data().len() as i64
        - prefund_data_len as i64 // <-- omitted term
        + /* new program account + programdata account sizes */ 0;

    let config = CoreBpfMigrationConfig {
        source_buffer_address,
        upgrade_authority_address: None,
        feature_id: Pubkey::new_unique(),
        migration_target: CoreBpfMigrationTargetType::Builtin,
        verified_build_hash: None,
        datapoint_name: "test_migrate_builtin_prefunded",
    };

    bank.migrate_builtin_to_core_bpf(&builtin_id, &config, true).unwrap();

    // FAILS when prefund_data_len > 0: actual delta omits prefunded account's data length.
    assert_eq!(
        bank.accounts_data_size_delta_off_chain.load(Relaxed),
        expected_delta_from_ground_truth,
    );
}
```
Expected result: the assertion fails for `prefund_data_len` in `{1024, MAX_PERMITTED_DATA_LENGTH}` (passes only at `0`), confirming `old_data_size` in `migrate_builtin_to_core_bpf` omits the prefunded `program_data_address` account's data length while `store_account` overwrites it and `lamports_to_burn` does account for its lamports.
