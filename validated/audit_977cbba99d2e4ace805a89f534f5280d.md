### Title
Shared per-asset "public free bandwidth" pool can be exhausted by any token holder, denying free-tier transfers to all other holders of that TRC10 token - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
The Axelar report describes a shared, time-windowed capacity (`flowLimit`, refilled every 6-hour epoch) that any single large actor can exhaust at the start of each epoch, denying the resource to everyone else transferring the same token. java-tron's TRC10 free-bandwidth model contains a structurally identical primitive: `AssetIssueContract.public_free_asset_net_limit`, a single shared, time-windowed quota consumed by *any* holder transferring that specific asset via `TransferAssetContract`. An unprivileged account can drain this shared pool early in each window, blocking all other holders from using free bandwidth for that token until the window naturally decays.

### Finding Description
`BandwidthProcessor.useAssetAccountNet()` gates every `TransferAssetContract` (except from the issuer) behind three shared/individual checks, the first of which is a **global, asset-wide** quota: [1](#0-0) 

`publicFreeAssetNetLimit` is a single value set once by the asset issuer (via `AssetIssueActuator`/`UpdateAssetActuator`), and `publicFreeAssetNetUsage`/`publicLatestFreeNetTime` are shared counters stored on the `AssetIssueCapsule` itself — not per-account: [2](#0-1) 

The usage counter decays over a rolling window using the same `increase()`/decay logic used elsewhere for bandwidth/energy (`ResourceProcessor.increase`, default `windowSize = ChainConstant.WINDOW_SIZE_MS / BLOCK_PRODUCED_INTERVAL`, i.e., a 24-hour rolling window analogous to Axelar's 6-hour epoch): [3](#0-2) 

Because the check `bytes > (publicFreeAssetNetLimit - newPublicFreeAssetNetUsage)` is evaluated against a *global* usage counter shared by every account holding that asset, **any single unprivileged holder** issuing enough `TransferAssetContract` transactions (even zero-value/self/minimal transfers, since the check depends on transaction byte size, not amount) can push `newPublicFreeAssetNetUsage` up to `publicFreeAssetNetLimit`. Once exhausted, `useAssetAccountNet` returns `false` for every subsequent transfer of that token by any other account for the remainder of the window, forcing them to either pay the TRX bandwidth fee (if they have TRX balance) or have their transaction rejected as under-resourced.

### Impact Explanation
This directly mirrors the accepted Medium-severity Axelar issue: a shared, per-token, per-time-window capacity that any actor (not just the token issuer) can exhaust cheaply, degrading availability of a legitimate low-cost transfer path for all other unprivileged holders of that TRC10 asset. The attacker only pays their own transaction fee (bandwidth from their own frozen TRX or a small TRX fee), while the damage (loss of free-tier bandwidth) is imposed asset-wide on every other holder attempting to use `TransferAssetContract` for that token during the window. This is a genuine availability/liveness degradation for the "free transfer" path — it does not steal funds but forces other users into paying fees or failing transactions, exactly the "function of protocol/availability impacted" categorization used to justify Medium severity in the original report.

### Likelihood Explanation
Likelihood is high for any actively-used TRC10 asset with `public_free_asset_net_limit` configured (a common convenience feature many issuers enable to subsidize small transfers): the attack requires no special privileges, only holding a nonzero amount of the target token and enough of the attacker's own bandwidth/TRX to broadcast repeated `TransferAssetContract` transactions to self or colluding addresses. There is no cap preventing a single account from being responsible for the entire `publicFreeAssetNetUsage` increment.

### Recommendation
Consider one or more of:
1. Track and cap `publicFreeAssetNetUsage` consumption per-account within the shared pool (e.g., `min(perAccountShare, remainingPublicPool)`), similar to avoiding "whole limit" designs criticized in the original report.
2. Charge a minimal, non-refundable fee-per-consumption against the public pool proportional to bytes, making repeated draining economically costly regardless of the attacker's own free bandwidth.
3. Allow issuers to configure a maximum single-transaction or per-account-per-window share of `public_free_asset_net_limit` to bound the blast radius of one account.

### Proof of Concept
1. Asset issuer creates/updates a TRC10 asset with `free_asset_net_limit` and `public_free_asset_net_limit` set to a modest shared quota (as validated in `UpdateAssetActuator`/`AssetIssueActuator`).
2. An attacker holding a small balance of that asset (any nonzero amount suffices since the check is byte-size based, not amount-based) and sufficient bandwidth (own frozen TRX) repeatedly broadcasts `TransferAssetContract` transactions transferring the asset (even to itself/second address it controls) until `newPublicFreeAssetNetUsage` in `useAssetAccountNet` reaches `publicFreeAssetNetLimit`.
3. Any other unrelated holder of the same asset then submits a `TransferAssetContract`; `useAssetAccountNet` returns `false` at the public-limit check, and the transaction either fails (insufficient resources) or forces the sender to pay the TRX bandwidth fee instead of using the intended free-tier allowance, exactly as described in `BandwidthProcessorTest` cases exercising `publicFreeAssetNetLimit` exhaustion (`framework/src/test/java/org/tron/core/BandwidthProcessorTest.java`, e.g. `getAssetIssueContract()` setting `PublicFreeAssetNetLimit(1000L)`).
4. The attacker repeats this at the start of each ~24h decay window to keep the public pool perpetually exhausted for that asset at low, sustained cost. [4](#0-3)
