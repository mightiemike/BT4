### Title
Unvalidated `RevertInstructions.FundRecipient` allows non-EVM/malformed address to sink re-minted PRC20 funds to a wrong or zero address on outbound revert - (File: `x/uexecutor/keeper/outbound.go`, `x/uexecutor/types/inbound.go`)

### Summary
Push Chain's design already does the *opposite* of what the M-08 report recommends: it lets a user-supplied `RevertInstructions.FundRecipient` field control where bridged funds go on revert/refund/rescue, instead of hardcoding it to the sender. However, unlike `Inbound.Recipient` (which is explicitly validated with `utils.IsValidAddress(p.Recipient, utils.HEX)` in `ValidateForExecution`), `RevertInstructions.FundRecipient` is never validated for EVM-address well-formedness before it is used as an EVM address for PRC20 re-minting on Push Chain.

### Finding Description
`RevertInstructions.FundRecipient` is set by the (attacker-controllable) source-chain event/relayer payload and is only lenient-canonicalized relative to the **source chain's** namespace in `Canonicalize()`: [1](#0-0) 

This canonicalization is explicitly "lenient" — malformed/foreign-format values are simply trimmed and passed through rather than rejected: [2](#0-1) 

`ValidateForExecution()` validates `p.Recipient` strictly as an EVM hex address for `FUNDS`/`GAS` types, but never validates `RevertInstructions.FundRecipient` at all: [3](#0-2) 

Yet `FundRecipient` is used directly as an EVM address on **Push Chain** (not the source chain) in two places that re-mint PRC20 tokens:

1. `handleFailedOutbound`, which re-mints bridged PRC20 tokens back on Push Chain when an outbound to an external chain fails: [4](#0-3) 

2. `applyGasRefund`, which refunds excess gas by depositing PRC20/native tokens on Push Chain to the same recipient field: [5](#0-4) 

In both cases `common.HexToAddress(recipient)` is called on a string that was only validated (if at all) against the **source chain's** address format (e.g. Solana base58), not against EVM hex format. `common.HexToAddress` from go-ethereum does not error on malformed input — it silently truncates/pads to a 20-byte address, which for a base58 Solana address or other garbage string can resolve to an unintended address, including the zero address `0x000...000`.

The ballot digest (`GetInboundBallotKey`) includes `FundRecipient` verbatim, so all honest validators converge on and execute the same (unvalidated) value — this is not a validator-honesty issue, it's a missing input-validation invariant reachable by an ordinary unprivileged user who controls the source-chain event/payload that becomes the `Inbound.RevertInstructions.FundRecipient`.

### Impact Explanation
If an inbound with `FUNDS_AND_PAYLOAD` (or `GAS_AND_PAYLOAD`) creates a subsequent `OutboundTx` to an external (e.g. Solana) chain that later fails, or excess gas needs to be refunded, and the `RevertInstructions.FundRecipient` inherited from the inbound was in the source chain's own address format (non-hex, e.g., Solana base58) or otherwise malformed, the mint-back call on Push Chain will target a garbage/zero address derived by `common.HexToAddress`. This causes **permanent loss/freezing of bridged user funds** — an unprivileged user's own funds could become unrecoverable due to a client/relayer-populated field never being cross-checked against the chain it's actually used on (Push Chain/EVM), and there is no code path to retry with a corrected recipient once `OutboundStatus` is set to `REVERTED`/funds have been "successfully" re-minted to the wrong address.

### Likelihood Explanation
Moderate. It requires an inbound flow whose destination outbound subsequently fails (or has excess gas), and a `FundRecipient` value that parses under the source chain's namespace but is not valid 20-byte hex (most naturally arising from Solana-originated inbounds, since Solana addresses are base58 and not automatically valid EVM hex). Because outbound failure and gas refund logic execute unconditionally based on ballot/validator consensus and do not add any hex-address gate before minting, this can be triggered without any privileged actor, purely through normal cross-chain usage from a non-EVM chain.

### Recommendation
Validate `RevertInstructions.FundRecipient` as a well-formed EVM (Push Chain) hex address wherever it will be used as an EVM mint/refund target — i.e., add an explicit `utils.IsValidAddress(fundRecipient, utils.HEX)` check in `ValidateForExecution()` (or in `handleFailedOutbound`/`applyGasRefund` before calling `common.HexToAddress`). On failure, fall back safely to `outbound.Sender` (already canonicalized/validated) rather than silently minting to a malformed/zero address, and mark the outbound `ABORTED` for manual recovery instead of `REVERTED`/`SUCCESS` if the fallback also fails validation.

### Proof of Concept
1. Attacker (a normal user) submits an inbound of `TxType_FUNDS_AND_PAYLOAD` from a Solana source chain (`solana:...`) with `RevertInstructions.FundRecipient` set to a valid base58 Solana address string.
2. `Canonicalize()` passes it through `canonicalizeSolanaValue`, which accepts it as valid for the Solana namespace, so no error is raised and it is stored verbatim as `FundRecipient`.
3. The payload execution creates a subsequent `OutboundTx` (e.g. a bridge-out to another chain) with `RevertInstructions` copied/derived from the inbound.
4. That outbound is later observed as failed by validators (honest consensus, quorum reached with `success=false`).
5. `handleFailedOutbound` computes `recipient := outbound.RevertInstructions.FundRecipient` (the Solana base58 string) and calls `common.HexToAddress(recipient)`, which does not error but returns an incorrect/truncated 20-byte address (potentially all-zero for many base58 strings).
6. `CallPRC20Deposit` mints the bridged PRC20 amount to that incorrect address on Push Chain; `outbound.PcRevertExecution.Status` is recorded `SUCCESS`, and `OutboundStatus` becomes `REVERTED` — the protocol considers the user "refunded" while the funds are unrecoverable at the wrong/zero address.

**Note on confidence**: I was not able to fully trace how `RevertInstructions` is populated for the intermediate `OutboundTx` created during `FUNDS_AND_PAYLOAD` execution (the assignment site wasn't found via `create_outbound.go`/`execute_inbound_funds_and_payload.go` grep in the available index), so the exact code path that copies `Inbound.RevertInstructions` onto a subsequent `OutboundTx` should be verified in a full checkout before treating this as final. The core gap — that `FundRecipient` is never hex-validated before being consumed via `common.HexToAddress` on Push Chain in `outbound.go` — is confirmed directly from the cited code.

// Lenient variants for the vote-ingress / key-derivation path: canonical form
// when the value parses, trimmed input otherwise (never an error). Used there
// because that path must never drop a vote — a malformed inbound still has to
// produce an on-chain UTX record (with a failed PCTx / revert), and
// execution-level validation, not key derivation, is what rejects it. Honest
// observers of the same value still converge (same trimmed string), and the
// injective hashFields digest keeps even malformed values collision-safe.
// Strict (error-returning) variants are for admin/config paths where bad input
// should be rejected before it is persisted.

// LenientCanonicalizeAddress canonicalizes addr for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeAddress(chain, addr string) string {
	canon, err := CanonicalizeAddressByNamespace(chain, addr)
	if err != nil {
		return strings.TrimSpace(addr)
	}
	return canon
}
