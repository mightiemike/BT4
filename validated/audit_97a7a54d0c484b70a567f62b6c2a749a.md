### Title
Gas fee deduction failure does not roll back UEA EVM state in direct `MsgExecutePayload` path, enabling free/unauthorized UEA execution - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
`Keeper.ExecutePayload` executes the UEA payload via `CallUEAExecutePayload(sdkCtx, ...)` directly on the live `sdkCtx`, then separately attempts `DeductGasFeesFromReceipt`. If fee deduction fails, the function returns an error — but, per the codebase's own documented invariant, `DerivedEVMCall(commit=true)` commits EVM state independently of whether the surrounding Cosmos message ultimately errors. The `execute_payload.go` (`ExecutePayloadV2`), `execute_inbound_gas_and_payload.go`, and `execute_inbound_funds_and_payload.go` paths were all patched (tagged `F-2026-16738` in tests) to wrap the EVM call + fee deduction in an explicit `sdkCtx.CacheContext()` / `writeCache()` pair specifically to close this "free execution" gap. `msg_execute_payload.go`'s `ExecutePayload` was not updated to use this pattern.

### Finding Description
`Keeper.ExecutePayload` [1](#0-0)  calls `CallUEAExecutePayload` directly against `sdkCtx`, then calls `DeductGasFeesFromReceipt` against the same `sdkCtx`, returning an error only if fee deduction fails.

Compare this to the already-patched `ExecutePayloadV2`, which explicitly notes the free-execution risk and wraps both calls in a cache context: [2](#0-1) . The same pattern and reasoning were applied to `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`, and validated with a dedicated regression test explicitly proving that without the cache wrapper, EVM storage mutations survive a failed fee deduction: [3](#0-2) .

`msgServer.ExecutePayload` — the handler actually bound to the user-facing, gasless `MsgExecutePayload` message — calls the unpatched `Keeper.ExecutePayload`, not `ExecutePayloadV2`: [4](#0-3) . `DeductGasFeesFromReceipt` itself only fails when the recipient (the UEA) cannot cover the computed gas cost: [5](#0-4) .

### Impact Explanation
`MsgExecutePayload` is documented as gasless and callable by "any account," and the target UEA's balance (not the submitter's) pays the EVM gas cost: [6](#0-5) . An unprivileged external attacker can submit a validly-signed payload for a UEA that has zero (or insufficient) native `upc` balance. `CallUEAExecutePayload` executes and commits real EVM state changes (any contract calls the payload authorizes, e.g. transferring PRC20/native value the UEA holds) via `DerivedEVMCall(commit=true)`. The subsequent `DeductGasFeesFromReceipt` fails due to insufficient balance, but that failure only returns a Cosmos-level error — the already-committed EVM state (unauthorized module-originated EVM execution / value movement) is not rolled back, per the exact behavior the sibling patches (`F-2026-16738`) were built to prevent. This causes unauthorized/free EVM execution and gas-fee accounting corruption: protocol gas is spent with no fee ever collected, and any value transfers the payload performs are not reverted.

### Likelihood Explanation
High likelihood: no privileged role is required. The attacker only needs a validly-signed `UniversalPayload` for a UEA (which can be their own, self-owned UEA) with low/zero `upc` balance, and to submit `MsgExecutePayload` directly — a message explicitly designed to be gasless and submittable "by any account." No validator collusion, TSS compromise, or admin action is needed.

### Recommendation
Apply the same fix already used in `ExecutePayloadV2` / `execute_inbound_gas_and_payload.go` / `execute_inbound_funds_and_payload.go`: wrap `CallUEAExecutePayload` and `DeductGasFeesFromReceipt` in an `sdkCtx.CacheContext()`, only calling `writeCache()` when both the EVM call succeeds and fee deduction succeeds, so a fee-deduction failure discards the EVM execution atomically. Add a regression test mirroring `inbound_cea_smart_contract_test.go`'s `"fee deduction failure rolls back executeUniversalTx, keeps deposit"` case, but targeting `MsgExecutePayload` directly.

### Proof of Concept
1. Attacker creates/owns a UEA with a validly-signed `UniversalPayload` whose `Data` calls some state-mutating function on a target contract (or moves a PRC20 the UEA holds) — the UEA has zero `upc` balance.
2. Attacker submits `MsgExecutePayload` (gasless, any signer allowed).
3. `msgServer.ExecutePayload` → `Keeper.ExecutePayload` → `CallUEAExecutePayload(sdkCtx, ...)` executes and commits the EVM call (per the fork's `DerivedEVMCall(commit=true)` semantics documented and relied upon by the sibling `CacheContext` patches).
4. `DeductGasFeesFromReceipt` fails with "insufficient gas" since the UEA balance is 0.
5. `Keeper.ExecutePayload` returns an error, and the outer `MsgExecutePayload` transaction reports failure — but the EVM state mutation from step 3 has already been committed and is not rolled back, since it was written directly to `sdkCtx` rather than a discardable cache context.

**Uncertainty note:** I could not directly execute or trace the internal fork implementation of `DerivedEVMCall`/`CallEVM` (it lives in the pinned `github.com/pushchain/evm` fork, not this repo) to independently confirm that `commit=true` writes immediately and irreversibly to the underlying multistore rather than being contained within Cosmos SDK's transaction-level `msCache`. My conclusion rests on the explicit, repeated pattern and dedicated regression test (`F-2026-16738`) in this repository that treat this exact "EVM state survives a failed Cosmos-level error" behavior as a real, previously-fixed bug for `ExecutePayloadV2` and the inbound-payload execution paths — `msg_execute_payload.go`'s `ExecutePayload` is the one remaining reachable entry point missing that fix. I recommend a Devin session with full repo/fork access to confirm the exact commit semantics of `DerivedEVMCall` before treating this as certain.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
