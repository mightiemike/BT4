### Title
Wallet Contract pays relayer fee unconditionally before confirming the emulated action succeeds - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (`near-wallet-contract`), which lets an ETH-implicit account emulate Ethereum transactions via `rlp_execute`, schedules a NEAR-token refund to the relayer as an independent, fire-and-forget promise batch before the actual requested action (base-token transfer or ERC-20 `ft_transfer` emulation) is known to succeed. If the underlying action later fails, the wallet has still irrevocably paid the relayer's fee out of the user's own balance, with no service rendered and no rollback mechanism — a value-accounting mismatch directly analogous to the reported `FeeTaker`/`IntegratorFeeExtension` bug where fees are moved based on an assumption (successful conversion/settlement) that is not actually guaranteed at the time of transfer.

### Finding Description
`inner_rlp_execute` parses the incoming RLP-encoded Ethereum transaction into a Near `Action` and a `TransactionKind`. When the transaction kind is an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero fee, the function immediately creates a **separate** promise batch that transfers `fee` yoctoNEAR from the wallet to the relayer (`context.predecessor_account_id`), unconditionally: [1](#0-0) 

This refund transfer is dispatched via its own `env::promise_batch_create` / `env::promise_batch_action_transfer` call, completely decoupled from the promise chain that performs the user's intended action (`action_to_promise(...).then(ext.rlp_execute_callback(...))`), which is built afterward: [2](#0-1) 

Because the two promises are independent receipts scheduled from the same host call, the relayer-refund receipt executes and finalizes regardless of whether the emulated action (e.g., the NEP-141 `ft_transfer` invoked through `nep_141_storage_balance_callback` / `rlp_execute_callback`) later fails: [3](#0-2) 

If the emulated action fails — e.g. the target NEP-141 contract lacks the required storage balance and its `storage_deposit`/`ft_transfer` calls revert, the token contract itself fails the transfer (insufficient balance changed between signing and inclusion), or gas is exhausted in the second promise chain — `rlp_execute_callback` only refunds the wallet's own **attached deposit** (`caller_deposit`) for the failed inner Near action; it does **not** claw back the relayer fee that was already paid out in the separate, already-settled batch. The code comments acknowledge the relayer is compensated "even if that transaction eventually fails" for gas-refund purposes generally, but the fee-refund logic here pays out before any confirmation that the requested transfer will succeed at all, exactly mirroring the `FeeTaker`/`postInteraction` root cause: value is moved based on an assumed successful state transition that has not actually occurred yet.

### Impact Explanation
A wallet owner (the ETH-implicit account) can lose real NEAR value (the computed `tx_fee`, based on `max_fee_per_gas * gas_limit`) to the relayer even though the intended action (token transfer, base-token transfer) never completes. This is not merely a "gas griefing" concern — it is an unconditional value transfer that is not contingent on the corresponding service being delivered, i.e., value moves out of the user's account with no successful state transition backing it, matching the "unauthorized value movement" acceptance criterion. Because the wallet contract cannot reverse the fee payment after the fact, any legitimate reason for the emulated action to fail after the transaction is broadcast (insufficient token balance at execution time, target contract behavior, network congestion causing gas exhaustion in the follow-up promise) results in permanent loss of the fee funds without recourse.

### Likelihood Explanation
Likelihood is Medium: this requires a relayer to submit a transaction whose emulated action fails downstream (a call that is entirely plausible in practice — token balances can change between signing and execution, receiver accounts can behave unexpectedly, or gas allocation in the follow-up chain can be insufficient). No malicious relayer collusion is even required — an honest relayer submitting an otherwise-valid signed transaction that simply fails at execution time is enough to trigger the loss, since the refund promise has already unconditionally fired by that point.

### Recommendation
Restructure `inner_rlp_execute` so the relayer's fee transfer is contingent on the success of the underlying action — e.g., move the fee-transfer logic into `rlp_execute_callback` (or an equivalent point after `PromiseResult::Successful` is confirmed) rather than dispatching it as an independent promise batch up front. Alternatively, chain the fee-refund promise after the action's promise so it only executes on success, and ensure any failure path in `rlp_execute_callback` restores/does not charge the fee.

### Proof of Concept
1. A user signs an RLP-encoded ERC-20 `transfer` calldata for an amount exceeding what will be available in the underlying NEP-141 contract by the time the transaction is processed (or targets a receiver not properly registered, causing the `storage_deposit` + `ft_transfer` chain to fail for an unrelated reason), with a non-zero implied `max_fee_per_gas * gas_limit` fee.
2. Any relayer (holding a `FunctionCall`-scoped access key restricted to `rlp_execute`) submits this transaction via `rlp_execute`.
3. In `inner_rlp_execute`, at [4](#0-3) 
the relayer-fee promise batch is created and will independently succeed and transfer `fee` yoctoNEAR from the wallet to the relayer.
4. The main action promise chain (`nep_141_storage_balance_callback` → `ft_transfer`) subsequently fails (e.g., `PromiseResult::Failed`), and `rlp_execute_callback` only refunds the wallet's attached deposit for that failed Near action, not the already-paid relayer fee.
5. Net effect: the wallet's NEAR balance is permanently reduced by `fee`, while the user's intended ERC-20 transfer never took place — an uncompensated, unauthorized value movement triggered by ordinary transaction failure.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;

                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
