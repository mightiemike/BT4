I have confirmed the root cause. This is a known, explicitly documented bug in nearcore (tracked as GitHub issue near/nearcore#12606) where a contract call is able to construct a `Data`/action receipt that exceeds `max_receipt_size` after passing the size validation gate, because the size check in `validate_receipt` runs *before* additional fields (like `output_data_receivers`, or the wrapping of a `value_return` payload into a `DataReceipt`) are appended, letting the final receipt exceed the hard cap. This is directly analogous to the Liferay bug class: a documented byte-size ceiling meant to bound an artifact (profile picture / receipt) is not actually enforced at the point where the oversized artifact is finalized, and the oversized artifact then propagates through the system causing degraded processing/slowdown — the runtime has to add work-around code (`try_forward` clamping) specifically because oversized receipts exist in practice.

### Title
Receipt-size limit is bypassed after validation, allowing oversized receipts into the state witness / cross-shard pipeline (DoS via oversized data) - (File: runtime/runtime/src/verifier.rs)

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` enforces `max_receipt_size` only at the moment a new receipt is validated [1](#0-0) . However, receipt content can grow after that check point — e.g. `output_data_receivers` is appended to an already-validated action receipt (as in the promise-return DAG rewiring), or a `value_return` payload up to `max_length_returned_data` is wrapped into a `DataReceipt` whose total borsh size can still exceed `max_receipt_size` [2](#0-1) . This is a known, unresolved bug tracked upstream as `near/nearcore#12606`, acknowledged directly in code comments in both `runtime/runtime/src/verifier.rs` (the `ExistingReceipt` validation mode exists specifically "to handle them gracefully until the receipt size limit bug is fixed") [3](#0-2)  and `runtime/runtime/src/congestion_control.rs`'s `try_forward`, which explicitly clamps oversized receipts to `max_receipt_size` "to avoid receipts getting stuck" [4](#0-3) .

### Finding Description
The size ceiling `max_receipt_size` (4 MiB) exists to bound the maximum size of any single receipt that can be embedded in a `ChunkStateWitness`, analogous to the 300 KB profile-picture cap in the Liferay CVE [5](#0-4) . The enforcement point, `validate_receipt`, runs the check only when `mode == ValidateReceiptMode::NewReceipt`, and only measures the receipt's serialized size *at that point in the pipeline* [6](#0-5) .

Two documented, reachable paths let a single, unprivileged contract call produce a receipt that ends up above this limit *after* the check has passed:
1. A `FunctionCall` action produces a receipt at exactly `max_receipt_size`; a later `promise_return` mutation appends entries to `output_data_receivers`, growing it past the limit without re-validation (`test_max_receipt_size_promise_return`) [7](#0-6) .
2. `value_return` allows a return value up to `max_length_returned_data` (4 MiB) [2](#0-1) ; that value is wrapped into a `DataReceipt` whose total size (data + envelope) can exceed `max_receipt_size`, and the wrapping is not re-validated against the receipt-level limit (`test_max_receipt_size_value_return`) [8](#0-7) .

Both tests assert that oversized receipts *do* end up in the incoming-receipts / chunk pipeline (`assert_oversized_receipt_occurred`) [9](#0-8) , confirming the receipt-size cap is not actually a hard guarantee once execution begins. The runtime's own congestion/forwarding code has to special-case this by clamping the observed size down to `max_receipt_size` purely so oversized receipts don't get permanently stuck rather than being rejected [4](#0-3) .

### Impact Explanation
This breaks a hard invariant that is load-bearing for the `ChunkStateWitness` size budget (~21 MiB total, built from the sum of the individual per-artifact caps including `max_receipt_size`) [10](#0-9) . An oversized receipt inflates the actual witness beyond what chunk validators budgeted for; because the size is clamped (not rejected) during forwarding, the receipt is admitted into the pipeline rather than dropped, degrading validator/RPC processing (increased serialization, storage-proof accounting, and network payload sizes) — matching the "resource consumption / slowdown" class in the reference CVE. It is a resource-consumption/availability issue rather than a fund-theft or consensus-divergence bug, since the workaround in `try_forward` keeps both honest nodes' behavior for now deterministic (they clamp identically) so it does not directly cause a state-root divergence on its own.

### Likelihood Explanation
High reachability: any account that can deploy and call a contract (test contract `near_test_contracts::rs_contract()`, methods `max_receipt_size_value_return_method`/`return_large_value`, or the promise-return DAG in `max_receipt_size_promise_return_method1`) can trigger this deterministically, with no special privileges, using ordinary `FunctionCall` and `promise_return`/`value_return` host calls [11](#0-10) . It is already reproduced by first-party regression tests in-tree, and is explicitly called out as an open, unresolved bug (`near/nearcore#12606`) rather than a hypothetical scenario.

### Recommendation
Re-validate the final serialized receipt size (including `output_data_receivers` and wrapped return-value data) against `max_receipt_size` at the point where the receipt is finalized/persisted — after all mutations (promise-return DAG rewiring, value-return wrapping) are applied — rather than only at the initial `NewReceipt` validation step in `validate_receipt` (`runtime/runtime/src/verifier.rs`). Reject the receipt (charging appropriate gas / erroring out the causing action) rather than silently clamping the observed size in `congestion_control.rs`'s `try_forward`.

### Proof of Concept
1. Deploy `near_test_contracts::rs_contract()` on an account with sufficient balance.
2. Call `max_receipt_size_value_return_method` (or `return_large_value` directly) with `value_size` set to `max_receipt_size` (4_194_304), reproducing `test_max_receipt_size_value_return` [12](#0-11) .
3. Observe that the resulting `DataReceipt` (return value + envelope) exceeds `max_receipt_size`, yet is neither rejected at creation nor at cross-shard forwarding (only clamped in `try_forward`), and shows up as an oversized incoming receipt in the following chunk, as verified by `assert_oversized_receipt_occurred`.
4. Alternatively, call `max_receipt_size_promise_return_method1` with `args_size` sized so the initial receipt is exactly at `max_receipt_size`; the subsequent `promise_return` DAG rewiring appends `output_data_receivers`, pushing the receipt over the limit undetected (`test_max_receipt_size_promise_return`) [13](#0-12) .

**File:** docs/misc/state_witness_size_limits.md (L16-40)
```markdown
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
* `max_receipt_total_input_size - 4 MiB + 640 B`
  * Hard limit on the combined size of a receipt's resolved promise inputs (the `ReceivedData` referenced by its `input_data_ids`). Receipts which exceed it fail with `TotalPromiseInputSizeExceeded` without executing their actions.
  * These inputs are read before `per_receipt_storage_proof_size_limit` starts counting, so without this limit a single receipt could pull `max_number_input_data_dependencies * max_receipt_size` (128 * 4 MiB) into the witness.
  * The limit is `max_length_returned_data` (4 MiB) plus the worst-case per-input framing overhead (128 * 5 bytes), so 4 MiB of input data always fits no matter how it's split across data receipts.
* `combined_transactions_size_limit - 4 MiB`
  * Hard limit on total size of transactions from this and previous chunk. `ChunkStateWitness` contains transactions from two chunks, this limit applies to the sum of their sizes.
* `new_transactions_validation_state_size_soft_limit - 500 KiB`
  * Validating new transactions generates storage proof (recorded trie nodes), which has to be limited. Once transaction validation generates more storage proof than this limit, the chunk producer stops adding new transactions to the chunk.
* `per_receipt_storage_proof_size_limit - 4 MB`
  * Executing a receipt generates storage proof. A single receipt is allowed to generate at most 4MB of storage proof. This is a hard limit, receipts which generate more than that will fail.
* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
  * Due to implementation details it's hard to find the exact amount of storage proof generated by a receipt, so an upper bound estimation is used instead. This upper bound assumes that every removal generates additional 2000 bytes of storage proof, so receipts which perform a lot of trie removals might be limited more than theoretically applicable.
* `outgoing_receipts_usual_size_limit - 100 KiB`
  * Limit on the size of outgoing receipts to another shard. Needed to keep the size of `source_receipt_proofs` small.
  * On most block heights a shard isn't allowed to send receipts larger than 100 KiB to another shard.
* `outgoing_receipts_big_size_limit - 4.5 MiB`
  * On every block height there's one special "allowed shard" which is allowed to send larger receipts, up to 4.5 MiB in total.
  * A receiving shard will receive receipts from `num_shards - 1` shards using the usual limit and one shard using the big limit.

In total that gives 4 MiB + 500 KiB + 8MB + 4 MiB + 5*100 KiB + 4.5 MiB ~= 21 MiB of maximum witness size. Possibly a little more on missing chunks.
```

```rust
/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
```
