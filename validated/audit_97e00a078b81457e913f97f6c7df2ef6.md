### Title
Erroneous extra division by 1e18 in `CalculateGasCost` zeroes out universal-execution gas fees - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`x/uexecutor/keeper/fees.go`'s `CalculateGasCost` unwraps the fee-market `baseFee` (`sdkmath.LegacyDec`) with `baseFee.BigInt()` and then divides the result by `1e18` again before using it as `effectiveGasPrice`. `LegacyDec.BigInt()` in `cosmossdk.io/math` already returns the truncated, human-scale integer value of the decimal (i.e., the real base-fee-per-gas figure, e.g. `1000000000` for a 1 gwei-equivalent base fee), not the internal `value*10^18` fixed-point representation. The extra `.Div(baseFeeBig, big.NewInt(1e18))` therefore divides an already-correct integer by `1e18` a second time, collapsing any realistic base fee to `0`. This is the same class of bug as the CurveTricryptoOracle report: an oracle/unit-conversion value that is already in the target unit gets divided by an extra normalization factor that doesn't apply at that stage, producing a value that is off by the full scaling factor.

### Finding Description [1](#0-0) 

The comment in the code claims that `LegacyDec`'s internal 18-decimal fixed-point encoding needs to be "unwrapped" by dividing by `1e18`, but `.BigInt()` on `cosmossdk.io/math.LegacyDec` already performs that truncation/unwrap internally and returns the plain integer value of the decimal (this is corroborated by how the codebase itself sets and reads base fee values elsewhere as plain integers, e.g. `math.LegacyNewDec(1000000000)` representing "1000000000" directly in [2](#0-1)  and genesis base-fee params such as `"1000000000.000000000000000000"` in [3](#0-2) , both of which are meant to represent the actual per-gas fee, not a value requiring a further `/1e18`).

Because `baseFeeBig` is already the correct integer base fee, the subsequent `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` divides it by `1e18` a second time. For any realistic base fee (far below `1e18` upc/gas), this integer division truncates to `0`, so:
- `effectiveGasPrice` becomes `0`.
- `gasCost := effectiveGasPrice * gasUsed` becomes `0` regardless of `gasUsed`.
- The `maxFeePerGas.Cmp(baseFeeBig) < 0` guard is effectively neutralized since `baseFeeBig` is `0`.

This function feeds `DeductGasFeesFromReceipt`, which is invoked after module-originated EVM execution triggered by universal payload processing: [4](#0-3) . When `gasCost.Sign() <= 0`, the deduction is skipped entirely: [5](#0-4) .

### Impact Explanation
`DeductGasFeesFromReceipt` is the mechanism by which the protocol recoups the real EVM execution cost (gas actually consumed on-chain) from the universal account (UEA) that requested a `GAS_AND_PAYLOAD`/`PAYLOAD` execution via a `DerivedEVMCall`. Because of the double-division bug, `gasCost` always computes to `0` for any realistic base fee, so the burn/deduction step in `DeductAndBurnFees` (`x/uexecutor/keeper/fees.go:21-37`) is skipped for every such transaction. This breaks the gas-fee accounting invariant explicitly listed as in-scope: "corruption of ... gas fee accounting, refund accounting ... must not misroute value." Concretely, ordinary unprivileged users can trigger arbitrary module-originated EVM execution (deploying/using UEAs, calling contracts through their universal account) via the standard inbound execution path without the protocol ever collecting the intended upc fee for the EVM gas consumed, resulting in a systemic, permanent under-collection (loss) of protocol fee revenue on every inbound `GAS_AND_PAYLOAD`/payload execution.

### Likelihood Explanation
Every unprivileged user submitting an inbound universal transaction that results in payload execution (the standard, default execution path, not a privileged one) goes through `ExecuteInboundGasAndPayload` → `DeductGasFeesFromReceipt` → `CalculateGasCost`. There is no special condition needed to trigger the bug — it fires for any nonzero base fee under standard EIP-1559-style values (which are always far smaller than `1e18` upc/gas), making this deterministic and always-triggered rather than a rare edge case. The main uncertainty is the exact semantics of `cosmossdk.io/math.LegacyDec.BigInt()` in the vendored SDK version used here; I could not directly inspect the vendored source in this session to conclusively confirm it returns the truncated real value rather than the raw `i` field. The strong circumstantial evidence (test and genesis values treating `BaseFee` as a plain, non-pre-scaled integer) supports the double-division reading, but a Devin agent with terminal/vendor access should confirm `LegacyDec.BigInt()`'s exact behavior before treating this as fully confirmed.

### Recommendation
Drop the redundant `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` call in `CalculateGasCost` (`x/uexecutor/keeper/fees.go:60`), or replace `baseFee.BigInt()` with the correct SDK accessor that matches the intended unwrap step (e.g., use `baseFee.TruncateInt().BigInt()` once, without any further division), and add a unit test asserting that for a base fee of, e.g., `1000000000` (LegacyDec), `CalculateGasCost` returns `1000000000 * gasUsed`, not `0`.

### Proof of Concept
1. Set `feemarketKeeper` base fee to a realistic value, e.g. `sdkmath.LegacyNewDec(1_000_000_000)` (1 gwei-equivalent upc/gas), as done in `test/integration/uexecutor/execute_payload_test.go:44`.
2. Submit any inbound universal transaction that results in `GAS_AND_PAYLOAD` execution, causing `ExecuteInboundGasAndPayload` to call `DeductGasFeesFromReceipt` with a receipt reporting nonzero `GasUsed` (e.g., 100,000 gas).
3. Trace `CalculateGasCost(baseFee=1e9, ...)`:
   - `baseFeeBig := baseFee.BigInt()` → `1000000000` (assuming `.BigInt()` truncates correctly).
   - `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` → `1000000000 / 1000000000000000000 = 0` (integer division).
   - `effectiveGasPrice = 0`.
   - `gasCost = 0 * 100000 = 0`.
4. Back in `DeductGasFeesFromReceipt`, `gasCost.Sign() <= 0` is true, so the function returns `nil` without calling `DeductAndBurnFees` — no upc is deducted/burned from the recipient's universal account for the EVM execution that was actually performed on their behalf.

```go
func (k Keeper) CalculateGasCost(
	baseFee sdkmath.LegacyDec,
	maxFeePerGas *big.Int,
	maxPriorityFeePerGas *big.Int,
	gasUsed uint64,
) (*big.Int, error) {
	baseFeeBig := baseFee.BigInt()
	// @dev: LegacyDec stores values with 18-decimal precision internally, so 1 upc = 1e18
	// in the LegacyDec representation. Since 1 upc is the smallest denomination (like wei
	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.
	// This division unwraps the LegacyDec encoding back to the actual upc amount.
	// Note: baseFee.BigInt() returns a reference to the internal big.Int; the in-place Div
	// mutates it, which is safe here since baseFee is a local value-type copy.
	baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
```

**File:** x/uexecutor/keeper/fees.go (L97-127)
```go
func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}
```
