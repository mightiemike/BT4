### Title
Deposit Refund in Failed Meta-Transaction Inner Receipt Sent to Delegate Sender (Alice) Instead of Relayer Who Paid — (`runtime/runtime/src/actions.rs`)

---

### Summary

In NEAR's meta-transaction (NEP-366) execution path, when a relayer submits a `DelegateAction` on behalf of a user (Alice) and the inner action receipt fails on the receiver's shard, the attached deposit is refunded to Alice — not to the relayer who actually paid it. An unprivileged user can deliberately craft a `DelegateAction` with a large deposit attached to an action guaranteed to fail, submit it to any relayer, and receive the full deposit refund while the relayer absorbs the loss. This is the direct nearcore analog of the Aave M03 bug: funds paid by the actual payer are refunded to the wrong party.

---

### Finding Description

**Execution flow:**

1. A relayer submits a transaction containing a `SignedDelegateAction`. The relayer's account is debited for all gas costs **and** for any token deposit attached to the inner actions (`docs/architecture/how/meta-tx.md:232-234`).

2. On Alice's shard, `apply_delegate_action` (`runtime/runtime/src/actions.rs:422-491`) unwraps the delegate and constructs a new inner receipt:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // ← Alice, NOT the relayer
    receiver_id: delegate_action.receiver_id().clone(),
    ...
});
``` [1](#0-0) 

The `predecessor_id` of the inner receipt is set to `sender_id` (Alice), because Alice is the logical sender of the inner actions. The relayer's identity is only preserved in `signer_id` of the `ActionReceipt` inside.

3. This inner receipt is forwarded to Bob's shard. If it fails (e.g., the called method does not exist, or the contract panics), `refund_unspent_gas_and_deposits` is invoked:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),
        deposit_refund,
    ));
}
``` [2](#0-1) 

4. `balance_refund_receiver()` resolves to:

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [3](#0-2) 

For a `Receipt::V0` (which is what `apply_delegate_action` always creates), `refund_to()` unconditionally returns `&None`:

```rust
ReceiptEnum::Action(_) | ... => &None,
``` [4](#0-3) 

So `balance_refund_receiver()` falls back to `predecessor_id` = **Alice**.

5. The deposit refund receipt (`new_balance_refund`) is therefore addressed to Alice, not the relayer. The relayer's account was debited for the deposit at transaction submission time and never receives it back.

The code comment in `apply_delegate_action` itself acknowledges this:

> "Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. … Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit." [5](#0-4) 

The architecture documentation makes the financial incentive explicit:

> "there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [6](#0-5) 

---

### Impact Explanation

The relayer pays the deposit. When the inner receipt fails, the deposit is credited to Alice's account, not the relayer's. The relayer suffers a direct, permanent loss of NEAR tokens equal to the deposit amount. Alice gains those tokens without having paid for them. This is a **stealing of funds** impact: an unprivileged user can extract arbitrary amounts of NEAR from any relayer that does not exhaustively simulate every possible execution path of every submitted meta-transaction.

---

### Likelihood Explanation

Any user who can submit a `DelegateAction` to a relayer can trigger this. The attack requires:
- Crafting a `DelegateAction` with a large `deposit` on a `FunctionCall` inner action.
- Ensuring the inner action will fail on the receiver's shard (e.g., calling a non-existent method, calling a method that panics, or targeting a receiver that has no contract deployed).
- Submitting it to any relayer.

No privileged access, no validator control, and no special network position is required. General-purpose relayers that accept arbitrary `DelegateAction`s from users are fully exposed. The attack is repeatable and scales linearly with the deposit size the relayer is willing to forward.

---

### Recommendation

The deposit refund for a failed inner receipt spawned by a `DelegateAction` should be directed to the relayer (the `signer_id` of the outer action receipt), not to Alice (the `predecessor_id` of the inner receipt). Two concrete approaches:

1. **Use `Receipt::V1` / `ActionReceiptV2` with `refund_to` set to the relayer**: In `apply_delegate_action`, construct the inner receipt as a `ReceiptEnum::ActionV2` with `refund_to: Some(action_receipt.signer_id().clone())`. The `balance_refund_receiver()` method already supports this field and will use it in preference to `predecessor_id`.

2. **Protocol-level rule**: Introduce a protocol version gate that, for receipts originating from a `DelegateAction`, overrides the deposit refund destination to be the `signer_id` (relayer) of the enclosing receipt rather than the `predecessor_id` of the inner receipt.

Gas refunds already correctly go to the relayer via `signer_id` (`runtime/runtime/src/lib.rs:1290-1294`). Deposit refunds should follow the same logic. [7](#0-6) 

---

### Proof of Concept

**Actors:**
- `relayer.near` — the relayer account (holds 1000 NEAR)
- `alice.near` — the attacker
- `bob.near` — a receiver with no contract deployed

**Steps:**

1. Alice constructs a `DelegateAction`:
   - `sender_id`: `alice.near`
   - `receiver_id`: `bob.near`
   - `actions`: `[FunctionCall { method_name: "nonexistent", gas: 10 TGas, deposit: 500 NEAR }]`
   - Signs it with her key.

2. Alice submits the `SignedDelegateAction` to `relayer.near`.

3. The relayer wraps it in a transaction (signer = `relayer.near`, receiver = `alice.near`) and submits it.

4. On `alice.near`'s shard, `apply_delegate_action` runs. The inner receipt is created with `predecessor_id = alice.near`, `signer_id = relayer.near`. The relayer's account is debited 500 NEAR for the deposit.

5. The inner receipt is forwarded to `bob.near`'s shard. The function call fails (`AccountDoesNotExist` or `MethodNotFound`).

6. `refund_unspent_gas_and_deposits` fires. `receipt.balance_refund_receiver()` returns `alice.near` (the `predecessor_id`). A `new_balance_refund` receipt for 500 NEAR is sent to `alice.near`.

7. **Result**: `relayer.near` is down 500 NEAR. `alice.near` is up 500 NEAR. The relayer has no recourse at the protocol level.

**Verification**: The `docs/architecture/how/meta-tx.md` section "Balance refunds in meta transactions" explicitly confirms this execution path and the resulting fund transfer to Alice. [8](#0-7)

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
