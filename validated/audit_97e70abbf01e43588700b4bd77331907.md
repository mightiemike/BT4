Based on my investigation, the strongest local candidate is a **self-documented gap in the transaction-output/transaction-info replay verification comparator**, which omits checking of the state checkpoint (state root) hashes.

### Title
Replay-verification comparator `ensure_match_transaction_info()` skips state-checkpoint hash validation, allowing a diverged state root to pass as a successful replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the function used by replay/restore verification tooling (e.g. db-tool's `replay_on_archive`) to confirm that a locally re-executed `TransactionOutput` matches the canonical, previously-committed `TransactionInfo` for a given version. The function validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** validate the state checkpoint hash, the hot-state checkpoint hash, or the position-state checkpoint hash — a gap the code itself documents.

### Finding Description
`ensure_match_transaction_info` checks four fields against `txn_info`: execution status, gas used, `write_set` hash against `txn_info.state_change_hash()`, and event root hash against `txn_info.event_root_hash()`. [1](#0-0) 

It then contains an explicit TODO acknowledging that the state/hot-state/position checkpoint hashes are not compared, and that this allows replay-verify tooling to report success even though the authenticated position (and by the same logic, main/hot) state root has diverged from local execution: [2](#0-1) 

The `state_change_hash` (write-set hash) only proves that the *set of writes issued by the VM* matches what was recorded; it does not prove that applying those writes to the (possibly already-diverged) base state tree produces the same root that was authenticated in the canonical `TransactionInfo.state_checkpoint_hash`. Divergence could originate upstream (e.g., in state-store commit/restore logic, hot-state materialization, or JMT structure) and would silently propagate through checkpoints without this comparator ever flagging it, because it never re-derives or compares the checkpoint root(s) that `TransactionInfo` carries: `state_checkpoint_hash()`, and (per `TransactionInfoV1`) the hot-state and position-state roots.

### Impact Explanation
This falls under the "Hard-fork-only divergence during commit, replay, restore, or proof verification" category. If a node's underlying state tree construction (JMT restore, hot-state materialization, or position-state tree) has a latent defect that produces a different root hash while still yielding an identical write-set, replay-verify and restore-verification tooling relying on `ensure_match_transaction_info` would report success despite the local ledger state being wrong. This undermines the operational safety net (`replay_on_archive`/verification pipelines) that operators depend on to catch consensus/storage bugs before they manifest as a live divergence, effectively masking a state-commitment defect rather than detecting it.

### Likelihood Explanation
The comparator is unconditionally missing checkpoint-hash validation — this is not behind a flag for the checks that are present, only the note references gating `COMPUTE_TRADING_NATIVE_STATE_ROOTS` before position-state roots become authoritative. The bug's exploitability is contingent on some *other* upstream state-commitment defect existing (this function does not itself corrupt state); its role is a broken detection invariant, not a corruption primitive on its own. I was not able to fully verify all call sites of `ensure_match_transaction_info` within the given iterations (index size limits truncated some surrounding files, e.g. `do_ledger_update.rs` body was not fully retrievable), so I cannot confirm whether other layers (e.g. `restore_utils`, `chunk_executor`) independently re-verify the state checkpoint hash elsewhere, which would reduce real-world severity.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()` (and, when present, hot-state/position-state checkpoint hashes) against the checkpoint hash(es) actually produced by local execution/replay, rather than relying solely on the write-set hash as a proxy for state-tree correctness.

### Proof of Concept
Not independently reproducible from static analysis alone — this is a verification-logic gap rather than a directly triggerable state corruption. Concretely: construct a replay scenario where local execution produces a `TransactionOutput` whose `write_set` hashes identically to the canonical `TransactionInfo.state_change_hash()` (i.e., the VM behaves identically), but where the underlying state tree (due to a separate latent commit/restore defect) yields a different `state_checkpoint_hash`. Calling `ensure_match_transaction_info` on this output will return `Ok(())`, i.e., pass verification despite the state root mismatch, as shown by the check list omitting `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` comparisons. [3](#0-2) 

Note: due to indexing limits, I could not fully inspect every caller of this function (e.g., `execution/executor/src/chunk_executor` replay-verification paths) to determine if an independent checkpoint-hash check exists elsewhere that would mitigate this gap; a full-repository session would be needed to trace all call sites exhaustively.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
