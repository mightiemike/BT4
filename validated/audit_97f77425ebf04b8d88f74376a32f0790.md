### Title
Relayer Deposit Stolen via Intentionally-Failing Meta Transaction — (`runtime/runtime/src/actions.rs`)

### Summary

In NEAR's meta transaction (delegate action) flow, the relayer pays all attached deposits on behalf of the inner `DelegateAction` sender (Alice). When the inner receipt fails on the receiver's shard, the deposit refund is sent to the `predecessor_id` of that inner receipt — which is Alice, not the relayer who actually funded it. An unprivileged user can deliberately craft a `DelegateAction` with a large attached deposit targeting a call that will fail, submit it through any relayer, and receive the full deposit refund while the relayer bears the loss.

### Finding Description

`apply_delegate_action` in `runtime/runtime/src/actions.rs` constructs the inner action receipt with `predecessor_id: sender_id.clone()` — i.e., Alice's account ID. [1](#0-0) 

When that inner receipt fails, `refund_unspent_gas_and_deposits` in `runtime/runtime/src/lib.rs` calls `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`. [2](#0-1) 

`balance_refund_receiver()` returns `refund_to` if set, otherwise falls back to `predecessor_id()`. [3](#0-2) 

Because the inner receipt was created with `predecessor_id = Alice` and no `refund_to` override, the deposit refund is unconditionally sent to Alice. The relayer, who deducted the deposit from its own account when the outer transaction was processed, receives nothing back.

The comment in `config.rs` confirms the relayer pays but Alice receives on failure: [4](#0-3) 

The architecture documentation explicitly acknowledges the financial incentive this creates: [5](#0-4) 

### Impact Explanation

The relayer's NEAR account balance is reduced by the full deposit amount. Alice's NEAR account balance increases by the same amount. The broken invariant is: **the account that funds a deposit must receive the refund when the action fails**. In the meta transaction path this invariant is violated — the relayer funds the deposit but Alice receives the refund. For a deposit of D yoctoNEAR, the relayer loses exactly D yoctoNEAR and Alice gains D yoctoNEAR. This is a direct, protocol-enforced transfer of funds from the relayer to Alice with no recourse.

### Likelihood Explanation

Any user who can reach a relayer service can exploit this. The attack requires only:
1. Crafting a `DelegateAction` with a large `deposit` on a function call targeting a contract that will fail (e.g., a non-existent method, a contract that panics, or a receiver with no contract deployed).
2. Submitting the signed `DelegateAction` to any relayer.

No privileged access, validator control, or network-level capability is required. The attack is repeatable and scales linearly with the deposit size the relayer is willing to forward.

### Recommendation

The inner receipt generated by `apply_delegate_action` should carry the relayer's account ID as the effective deposit-refund receiver, not Alice's. The cleanest fix is to set `refund_to` on the generated inner receipt to `action_receipt.signer_id()` (the relayer) at the point of receipt construction in `apply_delegate_action`, so that `balance_refund_receiver()` returns the relayer rather than Alice on failure. This preserves the existing gas-refund path (which already correctly targets the relayer via `signer_id`) and aligns deposit-refund semantics with the "payer receives refund" invariant. [1](#0-0) 

### Proof of Concept

1. Alice creates a `DelegateAction`:
   - `sender_id`: Alice
   - `receiver_id`: `no-contract.near` (account with no deployed contract)
   - `actions`: `[FunctionCall { method_name: "drain", deposit: 100_000_000_000_000_000_000_000_000 /* 100 NEAR */, gas: 30 TGas }]`
   - `nonce`: valid nonce for Alice's key
   - `max_block_height`: far future
   - Signs with Alice's key.

2. Alice sends the `SignedDelegateAction` to a relayer. The relayer wraps it in a transaction, paying 100 NEAR deposit + gas.

3. On Alice's shard, `apply_delegate_action` creates an inner receipt:
   - `predecessor_id = Alice`
   - `receiver_id = no-contract.near`
   - `actions = [FunctionCall { deposit: 100 NEAR }]`

4. On `no-contract.near`'s shard, the function call fails (no contract). `refund_unspent_gas_and_deposits` fires:
   - `deposit_refund = 100 NEAR`
   - `receipt.balance_refund_receiver() = predecessor_id = Alice`
   - A `Receipt::new_balance_refund(&Alice, 100 NEAR)` is emitted.

5. Alice's account receives 100 NEAR. The relayer's account is down 100 NEAR with no recovery path.
