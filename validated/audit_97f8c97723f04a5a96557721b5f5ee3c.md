### Title
`collateral-remove-redeem` redeems using the requested `amount` instead of the actual zTokens removed - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`collateral-remove-redeem` first calls `collateral-remove` to move zTokens from the user's position to the market contract, then calls `vault-redeem` passing the original caller-supplied `amount` again rather than the amount actually transferred by `collateral-remove`.

### Finding Description
The function is: [1](#0-0) 

Step 1 calls `(collateral-remove ft amount (some current-contract) price-feeds)`, whose actual on-chain effect is executed by `.v0-market-vault collateral-remove`, which returns the amount it actually removed/transferred as its `result` (see the pattern used elsewhere in `collateral-remove`, lines 1156-1161 of the same file, where the `result` of `contract-call? .v0-market-vault collateral-remove` — not the input `amount` — is what gets printed as `updated-collateral-amount` and returned). In `collateral-remove-redeem`, the return value of the `try!` in step 1 is discarded (`(try! (collateral-remove ...))`), and step 2 instead reuses the original request variable `amount`:

`(vault-redeem underlying-id amount min-underlying funds-receiver)`

This is structurally the same defect pattern as the Synthetix `sUSD` bug: the code assumes the amount requested equals the amount actually moved in the prior step, and reuses the pre-operation value for the post-operation call instead of binding and using the actual result of that first operation. If `.v0-market-vault collateral-remove` can return/transfer an amount different from the exact `amount` requested (e.g. due to internal capping, rounding, or partial-fill logic inside the vault's collateral-remove path — the same capping style already visible in this codebase's liquidation helpers `process-collateral-asset` / `scale-debt-for-liquidation`, which cap requested amounts at `user-coll-balance` or `curr-scaled`), then `vault-redeem` in step 2 is called with a mismatched `amount`, either attempting to burn/redeem more zTokens than the market contract actually holds (causing the whole transaction to abort, stranding the collateral-remove side effect within the same failed transaction) or redeeming fewer than what was actually pulled, leaving a residual zToken balance stuck in the market contract that is not accounted for and not returned to the user.

### Impact Explanation
If `collateral-remove` can transfer an amount different from the exact requested `amount` (capped/adjusted internally, similar to the capping logic already present in this market contract's liquidation path), `vault-redeem` in step 2 either reverts on a mismatched burn amount (temporary freezing of the user's withdrawal for that transaction) or succeeds while leaving mismatched zToken/underlying-token accounting, permanently stranding a fraction of the withdrawn collateral in the market contract's zToken balance. This lands in the "temporary/permanent freezing of funds" impact category.

### Likelihood Explanation
This triggers on every single call to `collateral-remove-redeem` whenever the effective amount removed by the vault differs from the caller-supplied `amount` — it is not dependent on interleaving by other users, requires no privileged access, and is reachable by any borrower who has zToken collateral to withdraw.

### Recommendation
Bind the actual return value of the `try!` in step 1 (the exact zToken amount transferred to the market by `.v0-market-vault collateral-remove`) to a local variable, and use that bound value — not the original `amount` parameter — as the input to the subsequent `vault-redeem` call in step 2.

### Proof of Concept
1. Caller invokes `collateral-remove-redeem` with `amount = X`.
2. Step 1: `(try! (collateral-remove ft X (some current-contract) price-feeds))` internally calls `.v0-market-vault collateral-remove`, whose actual effect/return may differ from `X` (e.g., capped to the user's real collateral balance or adjusted by internal accounting) — call the truly-moved amount `X'`.
3. Step 2 discards `X'` and calls `(vault-redeem underlying-id X min-underlying funds-receiver)` using the original `X`, not `X'`.
4. If `X' < X`: `vault-redeem` attempts to burn `X` zTokens from the market's balance, which only holds `X'`, causing `ERR-INSUFFICIENT-BALANCE` and reverting the transaction (temporary freeze of withdrawal). If `X' > X`: the redeemed amount is less than what was actually pulled from the user's collateral, leaving `X' - X` zTokens stuck in the market contract, unaccounted for and unrecoverable by the user (temporary/permanent freeze of funds). (define-public (collateral-remove-redeem (ft <ft-trait>) (amount uint) (min-underlying uint) (receiver (optional principal)) (price-feeds (optional (list 3 (buff 8192)))))
  (let ((ft-address (contract-of ft))
        (asset (try! (get-asset ft-address)))
        (ztoken-id (get id asset))
        (underlying-id (if (is-eq ztoken-id zSTX) STX
                       (if (is-eq ztoken-id zsBTC) sBTC
                       (if (is-eq ztoken-id zstSTX) stSTX
                       (if (is-eq ztoken-id zUSDC) USDC
                       (if (is-eq ztoken-id zUSDH) USDH
                       (if (is-eq ztoken-id zstSTXbtc) stSTXbtc
                       u100)))))))  ;; invalid sentinel for non-ztoken
        (funds-receiver (match receiver recv recv contract-caller)))

    (asserts! (<= underlying-id stSTXbtc) ERR-UNKNOWN-VAULT)
    
    ;; Step 1: Remove collateral - sends zTokens to THIS contract (market)
    ;; receiver=current-contract so market holds the zTokens
    (try! (collateral-remove ft amount (some current-contract) price-feeds))
    
    ;; Step 2: Redeem zTokens for underlying
    ;; vault-redeem calls vault.redeem which burns shares from contract-caller (market)
    ;; Since market now holds the zTokens, this succeeds
    ;; Underlying tokens are sent to the specified receiver
    (vault-redeem underlying-id amount min-underlying funds-receiver)))
