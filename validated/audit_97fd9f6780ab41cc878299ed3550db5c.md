### Title
Missing per-sender quota on gateway functions request cache allows single-sender DoS by cache-exhaustion - ([File: core/services/gateway/handlers/functions/api.go])

### Summary
The functions gateway's pending-request cache (`hc.RequestCache`) enforces only a single global `maxCacheSize` bound with no per-sender limit, keyed by `(sender, messageId)`. A single allowlisted (or allowlist-disabled) sender can flood cheap `MethodSecretsList`/`MethodHeartbeat` requests with unique `MessageId` values to saturate the shared cache, causing `request cache is full` errors for all other senders' `secrets_set`/`secrets_list`/`heartbeat` requests until each entry times out.

### Finding Description
`functionsHandler.HandleLegacyUserMessage` routes `MethodSecretsSet`, `MethodSecretsList`, and `MethodHeartbeat` messages to `handleRequest`, which calls `h.pendingRequests.NewRequest`. [1](#0-0) 

`NewRequest` in the shared cache only checks a single global counter `len(c.cache) >= int(c.maxCacheSize)`, with no per-sender accounting — the key includes the sender, but the size limit does not: [2](#0-1) 

Each entry only leaves the cache after `c.timeout` (`RequestTimeoutMillis`) fires or a response is aggregated, as confirmed by `TestRequestCache_MaxSize` and `TestRequestCache_Timeout`: [3](#0-2) 

Preconditions for exploitation: the attacker only needs a sender address permitted by the (optional) on-chain allowlist — or no allowlist configured at all, since `OnchainAllowlist` is optional per `FunctionsHandlerConfig` comment "Not specifying OnchainAllowlist config disables allowlist checks": [4](#0-3) 
The attacker crafts `MethodSecretsList` messages (empty payload — cheap) with unique `MessageId` values and its own `Sender`, self-signing each one (`ValidatedRequestFromMessage`/signature checks only validate that the sender signed its own message — they don't limit volume). The existing `userRateLimiter` (`UserRateLimiter`) is also optional and, even when enabled, bounds request *rate*, not concurrent pending occupancy over the `RequestTimeoutMillis` window; an attacker can still accumulate up to `MaxPendingRequests` entries within one timeout window at an allowed rate. Because the cache size check is global (not per-sender), once the attacker fills the cache to `maxCacheSize`, every other sender's `NewRequest` call — including for `secrets_set`, `secrets_list`, and `heartbeat` — fails with `"request cache is full"`, denying service to all legitimate senders until the attacker's entries expire after `RequestTimeoutMillis`.

### Impact Explanation
This is a denial-of-service against the shared Chainlink Functions gateway request cache: a single low-privilege (or unauthenticated, if allowlist disabled) sender can block all other DON users from getting responses to `secrets_set`, `secrets_list`, and `heartbeat` for the duration of `RequestTimeoutMillis`, repeatable indefinitely by keeping the attack running. This matches a service-disruption / DoS class bounty impact rather than fund loss or key compromise.

### Likelihood Explanation
High feasibility: constructing `MethodSecretsList` requests is cheap (empty payload), unique `MessageId` values are trivial to generate, and the only requirement is that the attacker's own address be allowlisted (or allowlist disabled) and pass the optional rate limiter — which only throttles rate, not sustained occupancy. The attack is fully repeatable and requires no elevated privileges, matching an ordinary attacker profile reachable via `HandleLegacyUserMessage`.

### Recommendation
Enforce a per-sender quota on pending cache entries in addition to the global `maxCacheSize`, e.g., track counts per `sender` in `requestCache[T]` and reject/limit new requests once a sender's own pending-entry count exceeds a configurable per-sender cap, independent of global occupancy. Alternatively/additionally, make `UserRateLimiter` mandatory (not optional) for the functions handler and size it such that per-sender burst allowance times `RequestTimeoutMillis` cannot approach `MaxPendingRequests`.

### Proof of Concept
Integration/load test:
1. Configure `functionsHandler` with `MaxPendingRequests = N` (e.g., 100) and `RequestTimeoutMillis` = e.g. 60000, allowlist disabled (or attacker address allowlisted), no `UserRateLimiter` configured.
2. From a single sender address, issue `N` `HandleLegacyUserMessage` calls with method `MethodSecretsList`, empty payload, unique `MessageId` per call, all signed by that sender.
3. Assert all `N` calls succeed (`NewRequest` returns nil) and cache size reaches `MaxPendingRequests`.
4. From a distinct, legitimate sender, issue a `secrets_list`/`secrets_set`/`heartbeat` request and assert it fails with `"request cache is full"`.
5. Wait for `RequestTimeoutMillis` to elapse and assert the legitimate sender's subsequent request now succeeds, confirming the DoS window is bounded only by attacker-controlled `RequestTimeoutMillis` and cache saturation, not by any per-sender quota.

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
	codec := api.JsonRPCCodec{}
	timer := time.AfterFunc(c.timeout, func() {
		err := c.deleteAndSendOnce(key, handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(request), ErrorCode: api.RequestTimeoutError})
		if err != nil {
			lggr.Errorw("failed to send timeout response", "error", err)
		}
	})
	c.cache[key] = &pendingRequest[T]{Callback: callback, responseData: responseData, timeoutTimer: timer}
	return nil
}
