### Title
Loss of Precision in Universal Validator Reward Boost Allocation Diverts Truncation Dust Away from UVs - (File: x/uvalidator/abci.go)

### Summary
`x/uvalidator/abci.go:AllocateTokens` computes the 14.8% Universal Validator fee boost using `QuoTruncate` and `MulDecTruncate`, which truncate toward zero. The decimal dust (`extraChange`) is returned to `FeeCollector` rather than being retained for UVs, so active UVs receive less than their intended proportional boost while non-UV validators / proposers absorb the residue.

### Finding Description
`BeginBlocker` invokes `AllocateTokens` every block to split the previous block's fees. The boost share for each UV is calculated as:

```go
powerFraction := power.QuoTruncate(effectiveTotalPower)
reward := feesCollected.MulDecTruncate(powerFraction)
``` [1](#0-0) 

Both operations truncate toward zero. After summing all UV rewards, the code separates integer coins from the accumulated decimal dust:

```go
extraCoins, extraChange := allocated.TruncateDecimal()
remainingCoins, hasNeg := feesCollectedInt.SafeSub(extraCoins...)
remainingDec := sdk.NewDecCoinsFromCoins(remainingCoins...)
remainingDec = remainingDec.Add(extraChange...)
remainingFinal, _ := remainingDec.TruncateDecimal()
``` [2](#0-1) 

`extraCoins` is sent to the distribution module to back the `AllocateTokensToValidator` accounting entries, while `remainingFinal` (which now includes `extraChange`) is sent back to `FeeCollector`:

```go
err = k.BankKeeper.SendCoinsFromModuleToModule(ctx, types.ModuleName, distrtypes.ModuleName, extraCoins)
...
err = k.BankKeeper.SendCoinsFromModuleToModule(ctx, types.ModuleName, authtypes.FeeCollectorName, remainingFinal)
``` [3](#0-2) 

Because `AllocateTokensToValidator` records the full `reward` DecCoins as owed to each UV but the distribution module only receives the truncated integer sum, the module is underfunded by `extraChange` relative to its recorded liabilities. The missing dust is instead recycled through `FeeCollector` and distributed by the standard distribution flow, which dilutes the boost among all validators (including non-UVs), proposers, and the community pool.

### Impact Explanation
This corrupts gas-fee accounting and the UV reward invariant. The intended semantics are that active UVs earn an effective ~14.8% additional fee share proportional to their boosted voting power. In practice, every block with non-zero fees and active UVs shaves off the decimal remainder of each UV's reward and redirects it away from UVs. Over many blocks this accumulates into a material divergence from the documented reward schedule, permanently reducing UV payouts below the configured boost. No user funds are stolen outright, but protocol-controlled fee proceeds are misallocated in favor of non-UV participants.

### Likelihood Explanation
High and deterministic. `BeginBlocker` runs on every block with `height > 1` whenever `previousTotalPower != 0` and `FeeCollector` is non-zero:

```go
if height > 1 {
    if err := AllocateTokens(ctx, previousTotalPower, ctx.VoteInfos(), uvalidatorKeeper); err != nil {
        ...
    }
}
``` [4](#0-3) 

Any ordinary user transaction that pays gas contributes to `FeeCollector` and therefore triggers the truncation on the next block. The amount of dust per block depends on the fee total and the exact validator power distribution, but it is guaranteed to occur whenever the product `feesCollected * powerFraction` is non-integral.

### Recommendation
Round the UV boost in favor of the beneficiary (the UVs), analogous to the OpenZeppelin `VestingWallet` behavior referenced in the external report. Options:
1. Use `QuoRoundUp` when computing `powerFraction`, or add the `extraChange` decimal dust to the amount sent to `distrtypes.ModuleName` rather than to `FeeCollector`.
2. Alternatively, accumulate `extraChange` in a per-block reserve inside `x/uvalidator` and distribute it to UVs once it crosses one base denom, preserving the intended effective boost.

### Proof of Concept
Extend the existing integration test in `test/integration/uvalidator/abci_test.go` to assert that the distribution module's recorded UV liabilities equal the coins actually forwarded. For example, with two active UVs and `feeAmount = 999` (the test already uses an odd value to amplify rounding):

1. Fund `FeeCollector` with `999 upc`.
2. Run `uvalidatormodule.AllocateTokens`.
3. Read each UV's distribution rewards (DecCoins) and sum them.
4. Compare the sum to `extraCoins` sent to the distribution module.
5. Observe that the difference is exactly `extraChange`, which was returned to `FeeCollector`.

The existing test only verifies that the `uvalidator` module ends empty and that `distrGain + FeeCollector == feeAmount`; it does not verify that the dust stays with UVs rather than leaking to `FeeCollector`. A new assertion would demonstrate the invariant break.
