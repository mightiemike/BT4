### Title
Underpriced BALANCE/EXTCODESIZE/EXTCODECOPY opcodes enable cheap disk-I/O amplification via cold-address enumeration - ([File: actuator/src/main/java/org/tron/core/vm/EnergyCost.java])

### Summary
`Op.BALANCE`, `Op.EXTCODESIZE`, and `Op.EXTCODECOPY` are charged a flat energy cost (`BALANCE=20`, `EXT_CODE_SIZE=20`, `EXT_CODE_COPY=20` + memory/copy cost) regardless of whether the target account has been accessed before in the transaction. There is no EIP-2929-style warm/cold access-list accounting in the TVM's `OperationRegistry`/`EnergyCost` implementation, so a contract can force many backing-store lookups (account trie / DB reads) for a fixed, cheap energy price per opcode.

### Finding Description
`OperationRegistry.newBaseOperationSet()` registers `Op.BALANCE` with cost function `EnergyCost::getBalanceCost` and action `OperationActions::balanceAction`, and `Op.EXTCODESIZE`/`Op.EXTCODECOPY` with `EnergyCost::getExtCodeSizeCost`/`getExtCodeCopyCost` and `OperationActions::extCodeSizeAction`/`extCodeCopyAction` [1](#0-0) [2](#0-1) .

The cost functions return a fixed constant with no dependency on the target address's prior access state within the transaction: `getExtCodeSizeCost` always returns `EXT_CODE_SIZE` (20) [3](#0-2) , and `getExtCodeCopyCost` returns `EXT_CODE_COPY` (20) plus a memory/copy-size-based surcharge that is unrelated to whether the account/code was previously loaded [4](#0-3) . The `BALANCE` constant is likewise a flat 20 [5](#0-4) .

The corresponding actions perform an actual account/store lookup per invocation: `extCodeSizeAction` and `extCodeCopyAction` call `program.getCodeAt(address)`, which resolves account code from the account/contract store for whatever address is popped off the stack [6](#0-5) . Since `address` is fully attacker-controlled (arbitrary `DataWord` from the stack), a contract can loop over thousands of distinct, never-before-touched addresses in a single transaction, each triggering a fresh account-store/trie lookup, while every iteration is billed the same flat 20-energy tier as if the account state were already warm/cached.

No warm/cold access-list mechanism (comparable to EIP-2929's `SLOAD`/`EXTCODESIZE`/`BALANCE` cold-vs-warm split) exists in this codebase's `EnergyCost`/`OperationRegistry`. The only dynamic-cost/adjustment mechanisms found (`VMConfig.allowEnergyAdjustment()` → `adjustForFairEnergy`, `getCalculateCallCost`'s `DYNAMIC_ENERGY_FACTOR_DECIMAL` penalty) apply to `CALL`-family energy forwarding, not to `BALANCE`/`EXTCODESIZE`/`EXTCODECOPY` access cost [7](#0-6) .

### Impact Explanation
An attacker-deployed contract that loops these opcodes over many distinct addresses forces the node to perform many real backing-store (trie/DB) lookups per transaction while paying energy priced as if each lookup were negligible/cached. This creates a cost-per-real-IO ratio far below other opcodes that are correctly priced for store access (e.g. `SLOAD`=50 energy, `SSTORE` tiers of 5000/20000), enabling disk I/O amplification that can degrade node throughput/latency relative to the energy fee actually collected — a denial-of-service-adjacent resource exhaustion vector reachable by any unprivileged account through ordinary `TriggerSmartContract` execution.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: deploy a contract via `CreateContract`, then call it via `TriggerSmartContract` with a loop over sequential/derived addresses executing `BALANCE`, `EXTCODESIZE`, or `EXTCODECOPY`. No special permissions, no admin/governance action, and no existing guard (access-list, per-tx address-touch cache pricing, or dynamic surcharge) prevents or discourages this pattern. It is trivially repeatable in every block/transaction up to the block energy limit.

### Recommendation
Introduce access-list-style (EIP-2929-equivalent) accounting in `Program`/`EnergyCost`: track per-transaction "touched addresses" the first time `BALANCE`, `EXTCODESIZE`, `EXTCODECOPY`, `EXTCODEHASH`, or `CALL`-family opcodes access an address, charge a higher "cold access" cost on first touch and the current flat cost only on subsequent ("warm") touches to the same address within the same transaction.

  public static void extCodeSizeAction(Program program) {
    DataWord address = program.stackPop();

    int length = program.getCodeAt(address).length;
    DataWord codeLength = new DataWord(length);

    program.stackPush(codeLength);
    program.step();
  }

  public static void extCodeCopyAction(Program program) {
    DataWord address = program.stackPop();
    byte[] fullCode = program.getCodeAt(address);

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
  }
