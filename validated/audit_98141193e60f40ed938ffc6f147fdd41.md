Meanwhile the epoch manager's `compute_stake_return_info` computes `max_of_stakes` purely from `stake_change` maps recorded in `EpochInfo` over the last three epochs, independent of whether the account still exists [3](#0-2) , and this is fed straight into `ValidatorAccountsUpdate.stake_info` [4](#0-3) .

### Title
Deleting and recreating a validator account after unstake desyncs `update_validator_accounts` from the epoch manager's stake-history window, turning a legitimate action sequence into a chunk-fatal `StorageInconsistentState` halt - (File: `runtime/runtime/src/lib.rs`)

### Summary
`update_validator_accounts` assumes that a named account's `locked` balance can never fall below the `max_of_stakes` the epoch manager computed for it over the last three epochs, and treats any violation as an unrecoverable `FATAL: staking invariant does not hold` error [5](#0-4) . This mirrors the Sense-PT bug class: the redemption/accounting code hard-reverts on any deviation from an assumed 1:1 (or here, monotonic non-decreasing) relationship instead of gracefully handling a legitimate scenario where that relationship doesn't hold, and the failure is fatal rather than recoverable.

### Finding Description
`compute_stake_return_info` in the epoch manager derives `max_of_stakes` for an account purely from the `stake_change` maps of the past two/three `EpochInfo` snapshots — a computation entirely decoupled from the account's *current* on-chain existence or state [6](#0-5) . This `stake_info` map is then handed unmodified to `update_validator_accounts` in the runtime at the next epoch boundary [4](#0-3) .

`update_validator_accounts` only special-cases the situation where the on-chain account is *uninitialized* (a specific legacy/implicit-account representation), in which case it verifies nothing is "owed" (`max_of_stakes`, `reward`, `last_proposal` all zero) before skipping it; otherwise it raises the same FATAL error [7](#0-6) . The code comment explicitly says the *only* way an account could reach `stake_info` while uninitialized is "when a validator deletes their account and re-creates in an uninitialized state," and calls the defensive check "so that minted tokens do not leak from the supply if this path ever becomes reachable" [8](#0-7) . But this only covers the *uninitialized*-recreation sub-case. If, instead, an account is deleted and then recreated as a normal *initialized* account (via `Action::CreateAccount` after `Action::DeleteAccount`, both of which are ordinary permission-checked user actions [9](#0-8) [2](#0-1) ), the account passes the `is_initialized()` check and falls into the main branch, where `account.locked() < *max_of_stakes` is checked against the *freshly created* account's `locked` (necessarily `0`, since a brand-new account has no locked stake) while `max_of_stakes` still reflects a stale non-zero value carried over from the account's staking history recorded up to two epochs earlier [5](#0-4) .

`DeleteAccount` only requires `locked() == 0` at the moment of deletion [1](#0-0) , but `locked` only physically drops to zero at an epoch boundary via this very `update_validator_accounts` return-stake logic (`locked` is otherwise monotonically non-decreasing through `Stake` actions per the staking spec [10](#0-9) ). So a validator can unstake, wait for `locked` to hit zero at an epoch boundary, delete the account, and recreate it as a plain account within the same or a subsequent block — all while the epoch manager's `stake_change`/3-epoch lookback (spanning `epoch_id`, `next_epoch_id`, `next_next_epoch_id`) still attributes a non-zero `max_of_stakes` to that `AccountId` for a later epoch boundary, because that lookback is keyed purely by `AccountId` in `EpochInfo` history and is unaware of any intervening delete/recreate [6](#0-5) .

### Impact Explanation
When the delayed epoch-boundary application runs against this recreated, initialized, zero-locked account with a residual positive `max_of_stakes`, `update_validator_accounts` returns `RuntimeError::StorageError(StorageError::StorageInconsistentState(...))` [5](#0-4) . `StorageInconsistentState` is nearcore's designated fatal/unrecoverable class of error used to signal state corruption; it is not a normal transaction/action failure that can be absorbed into an execution outcome — the entire chunk application for that shard fails, halting block/chunk production for the shard until the situation is resolved (matching the "transaction-triggered halt" impact category). This is exactly analogous to the reported bug class: code that hard-assumes an invariant ("no loss"/"no decrease" outside the code's own control path) and turns a legitimate divergence into total service failure instead of a graceful, contained error.

### Likelihood Explanation
Reaching this requires an unprivileged account owner to: (1) unstake (submit a `Stake` action with `stake = 0`), (2) wait until an epoch boundary sets `locked` to `0` for that account, (3) submit `DeleteAccount`, and (4) submit `CreateAccount` (as an initialized account) for the same `AccountId` before the epoch manager's residual 3-epoch stake-history window (spanning up to `next_next_epoch_id`) is fully drained for that account. All of these are ordinary, permission-checked transactions available to any signer — no privileged network role is required. The existing test `test_apply_validator_update_uninitialized_account` explicitly documents and exercises the *uninitialized*-recreation sub-case and asserts the fatal error fires when anything is "owed" [11](#0-10) , confirming the FATAL path is real and reachable in that adjacent scenario; however, I could not find an equivalent test covering the *initialized*-recreation branch, so I cannot fully confirm from the indexed code alone whether some other safeguard (e.g., epoch-manager-side stake_change clearing on account deletion, or some resharding/timing constraint) prevents the exact initialized-recreation timing window from lining up in practice. This uncertainty should be resolved with further protocol-level tracing/testing before treating this as fully proven.

### Recommendation
In `update_validator_accounts` (`runtime/runtime/src/lib.rs`), extend the existing uninitialized-account defensive handling to also cover initialized accounts whose observed `locked()` is legitimately lower than `max_of_stakes` due to an intervening `DeleteAccount`/`CreateAccount` cycle — e.g., by having the epoch manager clear/zero an account's `stake_change` history entries at deletion time so `max_of_stakes` cannot resurrect stale expectations, or by having the runtime treat a zero-`locked`, freshly-(re)created account the same way it already treats the uninitialized case (verify nothing is owed, else fail gracefully as an action/tx error rather than a fatal `StorageInconsistentState` chunk-halting error).

### Proof of Concept
Conceptual sequence (not runnable as-is from the index, but derivable from the cited code paths):
1. Validator account `V` stakes, becomes part of `stake_change` history for epochs T, T+1.
2. `V` submits `Stake{stake: 0}`; at the next epoch boundary `update_validator_accounts` returns `V`'s stake, setting `locked = 0` [12](#0-11) .
3. With `locked() == 0`, `V` submits `DeleteAccount` (passes the `locked().is_zero()` check) [1](#0-0) .
4. `V`'s owner submits `CreateAccount` for the same `AccountId`, succeeding since the account no longer exists [2](#0-1) , producing a fresh, fully-initialized, zero-locked account.
5. At a subsequent epoch boundary still within the 3-epoch `stake_change` lookback window that recorded `V`'s earlier non-zero stake, `compute_stake_return_info` still emits `max_of_stakes > 0` for `V` [13](#0-12) .
6. `update_validator_accounts` loads the recreated, initialized account (`locked() == 0`), skips the uninitialized special-case, hits `account.locked() < *max_of_stakes` and returns the FATAL `StorageInconsistentState` error [14](#0-13) , failing the shard's chunk application.

On a stake action the balance gets locked immediately (but the locked balance can only increase), and the stake proposal is

Unlocking only happens at the start of an epoch.

equal to the maximum of the last three stakes and the highest proposal in the current epoch.
