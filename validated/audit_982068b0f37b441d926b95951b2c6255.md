## Analysis

The report's core bug class — an entity able to mint tokens without any enforced limit — has a direct analog in Push Chain's registry/accounting invariant for PRC20 minting.

`x/uregistry`'s `TokenConfig` defines a `LiquidityCap` field explicitly documented as the "max supply cap for this token" [1](#0-0) , and every configured token in the repo populates a concrete cap value (e.g. `"1000000000000000000000000"`) [2](#0-1) . `TokenConfig.ValidateBasic` even enforces that `LiquidityCap` is non-empty at registration time [3](#0-2) .

However, the actual PRC20 minting path in `x/uexecutor` never reads or checks `LiquidityCap` anywhere. `depositPRC20` only fetches the `NativeRepresentation.ContractAddress` and parses the amount before minting [4](#0-3) , and `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` unconditionally issue the mint via `DerivedEVMCall` with no cap comparison [5](#0-4) . The only validation performed on `Inbound.Amount` is that it's a non-negative `uint256` (and positive for most tx types) — never bounded against any registry-level cap [6](#0-5) . A repo-wide search confirms `LiquidityCap` is referenced only in proto-generated code, `ValidateBasic`, tests, and config JSON — never in any keeper logic that performs minting or accounting in `x/uexecutor` or `x/uregistry`.

### Title
Configured `LiquidityCap` on `TokenConfig` is never enforced during PRC20 minting - (File: x/uexecutor/keeper/handler.go, x/uexecutor/keeper/evm.go)

### Summary
`x/uregistry.TokenConfig` declares a `liquidity_cap` intended to bound the maximum PRC20 supply mintable for a given external token, and the field is mandatory at token registration. The PRC20 mint path in `x/uexecutor` (`depositPRC20` -> `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`) never reads this field or compares it against cumulative minted supply before calling `depositPRC20Token`/`depositPRC20WithAutoSwap` on the Handler contract.

### Finding Description
Every inbound of `TxType_GAS`, `TxType_FUNDS`, `TxType_FUNDS_AND_PAYLOAD`, or `TxType_GAS_AND_PAYLOAD` that reaches UV quorum triggers a PRC20 mint proportional to `Inbound.Amount` (or a swap-derived quote for `GAS`), resolved from `uregistryKeeper.GetTokenConfig` [7](#0-6) . Neither `depositPRC20` nor `ExecuteInboundGas`/`ExecuteInboundFundsAndPayload` load or check `tokenConfig.LiquidityCap` before invoking `CallPRC20Deposit`, and the module tracks no running total of minted supply per token to compare against the cap [8](#0-7) . Because ordinary users legitimately control how much they deposit into the source-chain gateway (an unprivileged action requiring no validator or admin collusion), repeated genuine deposits can accumulate PRC20 mints on Push Chain that exceed the registry's declared `liquidity_cap` for that token indefinitely, with no on-chain guard rejecting or throttling the mint once the configured ceiling is crossed.

### Impact Explanation
This falls under the required impact category "corruption of PRC20 or native asset accounting ... token mapping" and the registry/accounting invariant pivot ("token config ... must not misroute value or attach the wrong asset semantics"). An unenforced supply cap defeats the risk-control purpose of `liquidity_cap` (bounding synthetic-asset exposure per external token/chain), which can silently invalidate assumptions made elsewhere in the protocol (e.g., swap liquidity backing, risk limits per token) once cumulative deposits exceed the intended ceiling — all without any privileged or malicious actor, purely through normal user deposit activity.

### Likelihood Explanation
High reachability and low complexity: it requires only ordinary users repeatedly depositing a registered token through the standard inbound flow — no validator collusion, no admin action, and no cryptographic bypass. Since `LiquidityCap` is a mandatory, non-empty field on every registered `TokenConfig`, the intent to cap supply is clearly present in the data model but structurally unenforced in the execution path.

### Recommendation
Track cumulative minted PRC20 supply (or read `totalSupply()` on the PRC20 contract) per `(chain, token)` pair in `x/uexecutor` or `x/uregistry`, and reject/cap the deposit in `depositPRC20` (and the `GAS`/`GAS_AND_PAYLOAD` swap-deposit paths) whenever `currentSupply + amount > tokenConfig.LiquidityCap`, routing the excess through the existing failed-PCTx/revert-outbound path. Alternatively, if the cap is intentionally advisory/off-chain-only, remove or clearly document that `LiquidityCap` is not enforced on-chain so operators do not rely on it as a security control.

### Proof of Concept
1. Register a `TokenConfig` with `liquidity_cap = "1000000"` (as in the test fixtures, e.g. `x/uexecutor/keeper/execute_inbound_gas_test.go` lines 54-67).
2. Submit repeated genuine `FUNDS` or `GAS` inbounds for the same `(sourceChain, assetAddr)` with `Amount` values that individually pass `ValidateForExecution` (positive `uint256`), and get them to UV quorum via `MsgVoteInbound`.
3. Observe that `depositPRC20` -> `CallPRC20Deposit` mints PRC20 on every quorum-reached inbound with no check against `tokenConfig.LiquidityCap`, and that the cumulative PRC20 `totalSupply()` for that asset can exceed the configured `liquidity_cap` value with no error, revert, or rejection anywhere in the flow.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}

		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
