### Title
Unbounded gzip decompression of user-supplied Cairo0 program in `decompress_program` enables a compression-bomb DoS - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
`decompress_program` in the RPC layer decompresses a base64-encoded, gzip-compressed Cairo0 `program` field with **no size or time limit**, unlike the equivalent gateway declare-transaction path which enforces a strict byte cap via `decompress_with_size_limit`/`.take(max_size + 1)`. An unprivileged caller can submit a broadcasted deprecated (`Cairo0`) declare transaction for simulation/fee-estimation containing a highly-compressed gzip payload ("zip bomb") that expands to gigabytes in memory, exhausting node resources.

### Finding Description
`decompress_program` reads the entire decompressed stream into an in-memory `Vec<u8>` with `decoder.read_to_end(&mut decompressed, ...)` and explicitly carries a `// TODO(dan): add time and size limits.` comment acknowledging the missing guard: [1](#0-0) 

By contrast, the sequencer's own gateway/transaction-conversion path for the same kind of data (compressed Sierra/Cairo programs inside declare transactions) is hardened against exactly this bug class: it caps decompression output via `.take((max_size + 1)...)` and returns `CompressionError::SizeLimitExceeded` if the limit is exceeded, which bounds both the memory used and the number of bytes read (preventing unbounded/looping decompression): [2](#0-1) [3](#0-2) 

`decompress_program` is reached from the RPC layer when converting a `BroadcastedDeclareV1Transaction` (a legacy/Cairo0 declare) submitted by any client for JSON-RPC calls such as `estimate_fee`, `simulate_transactions`, or trace endpoints — these accept fully attacker-controlled `program` bytes before any chain-level admission/fee checks are performed, since the transaction is only being simulated, not necessarily going through the full gateway compression-size-limited path.

This mirrors the reported PHP phar bug class (`CVE-2022-31628`): a decompression routine that lacks a bound on decompressed output size/time, allowing a small malicious compressed input to cause unbounded resource consumption during decompression.

### Impact Explanation
A single unprivileged JSON-RPC caller can submit one Cairo0 `program` payload compressed to a small size (kilobytes) that expands to a very large size (potentially gigabytes) once decompressed, because `decompress_program` reads to completion with no cap. This can exhaust memory/CPU on the RPC-serving node process, causing it to stall or crash while handling that single request, degrading or denying RPC-based transaction submission/estimation service on that node.

### Likelihood Explanation
High likelihood of triggering: the attack requires only a single JSON-RPC call with a crafted base64+gzip payload, no special privileges, no prior on-chain state, and no interaction with other nodes. It is directly reachable by any external caller of the node's read/execution RPC API.

### Recommendation
Apply the same bounded-decompression pattern already used in `starknet_api::compression_utils::decompress_with_size_limit` (via `.take(max_size + 1)` and explicit `SizeLimitExceeded` error) to `decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs`, replacing the unbounded `decoder.read_to_end(&mut decompressed, ...)` call, and resolve the existing `TODO(dan)` comment.

### Proof of Concept
1. Craft a Cairo0 `program` JSON body, gzip-compress it with a highly repetitive/self-referential payload to achieve a large compression ratio, then base64-encode it (a classic "zip bomb", analogous in effect to the PHP quine-gzip case).
2. Submit it as the `contract_class.program` field of a `BroadcastedDeclareV1Transaction` via a JSON-RPC call that triggers class conversion/execution (e.g., `estimate_fee` or `simulate_transactions`).
3. Observe `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) decompress the payload with no size cap, driving unbounded memory allocation on the serving node, in contrast to the bounded behavior enforced elsewhere by `decompress_with_size_limit` (`crates/starknet_api/src/compression_utils.rs:32-46`).

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
