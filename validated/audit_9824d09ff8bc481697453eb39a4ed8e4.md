### Title
Rosetta RPC Reports Logs from Failed Receipts as Successful FT Transfer Operations, Enabling Phantom Balance Manipulation — (`chain/rosetta-rpc/src/adapters/nep141.rs`, `chain/rosetta-rpc/src/adapters/transactions.rs`)

### Summary

The nearcore Rosetta RPC's NEP-141 event pipeline (`extract_events` → `collect_nep141_events` → `convert_fungible_token_balance_change_to_operations`) never checks the execution status of the receipt that produced a log. Because NEAR preserves logs in `ExecutionOutcome` even when a receipt fails and state is rolled back, any `EVENT_JSON:` log emitted by a configured FT contract before a panic is parsed, accepted, and reported to Rosetta consumers as a `Transfer` operation with hardcoded `OperationStatusKind::Success`. An unprivileged user who can trigger any code path in a configured FT contract that emits a NEP-141 log before failing can inject phantom FT transfer operations into the Rosetta `/block` and `/block/transaction` responses, causing exchanges and wallets that rely on Rosetta for balance reconciliation to credit deposits that never occurred.

### Finding Description

**Root cause — logs survive receipt failure in the NEAR runtime**

/// kept — they reflect work already done.

    self.result = Err(err);
    self.new_receipts.clear();

### Impact Explanation

The Rosetta API is explicitly designed for balance reconciliation by exchanges and custodians. Its README states its goal is "exposing balance-changing operations in a consistent way enabling reconciliation through tracking individual blocks and transactions." [9](#0-8) 

A phantom `FtTransfer` operation reported as `Success` in the Rosetta `/block` response causes any Rosetta-based reconciliation system to believe a fungible token transfer occurred and was finalized. An exchange crediting FT deposits based on Rosetta events would credit a deposit that never happened on-chain, constituting direct balance manipulation reachable through the public Rosetta API.

### Likelihood Explanation

**Preconditions (all unprivileged):**
1. The Rosetta node operator has configured at least one FT contract address in the `currencies` list (standard production deployment for any exchange using Rosetta for FT tracking).
2. The attacker can submit a transaction that causes the configured FT contract to emit an `EVENT_JSON:ft_transfer` log before the receipt fails.

**Trigger paths on standard NEP-141 contracts:**
- Call `ft_transfer` with a `receiver_id` that is not registered in the FT contract. Some NEP-141 implementations emit the transfer log before the `assert` that checks receiver registration, causing the receipt to fail after the log is written.
- Call any function on the FT contract that emits a log and then panics due to any condition (e.g., cross-contract call failure, storage exhaustion, explicit panic in a callback).
- The attacker pays gas for the failed transaction; no other privilege is required.

### Recommendation

1. **Filter failed receipts before NEP-141 event extraction.** In `collect_nep141_events` or `extract_events`, skip any `ExecutionOutcomeWithIdView` whose `outcome.status` is `ExecutionStatusView::Failure` or `ExecutionStatusView::Unknown`.

2. **Use the actual status in `convert_fungible_token_balance_change_to_operations`.** Replace the hardcoded `OperationStatusKind::Success` with a value derived from `fungible_token_event.status` (which is already correctly populated by `get_status`).

The minimal fix is in `collect_nep141_events`:

```rust
pub(crate) fn collect_nep141_events(
    receipt_execution_outcomes: &Vec<ExecutionOutcomeWithIdView>,
    ...
) -> crate::errors::Result<Vec<FungibleTokenEvent>> {
    let mut res = Vec::new();
    for outcome in receipt_execution_outcomes {
        // Skip failed or unknown receipts — logs are preserved but state is rolled back
        match outcome.outcome.status {
            ExecutionStatusView::SuccessValue(_)
            | ExecutionStatusView::SuccessReceiptId(_) => {}
            _ => continue,
        }
        let events = extract_events(outcome);
        ...
    }
    Ok(res)
}
```

### Proof of Concept

**Setup:** A Rosetta node configured with `currencies: [{ symbol: "MYFT", contract_address: "myft.near" }]`.

**Attacker steps:**

1. Deploy or use an existing NEP-141 contract at `myft.near` (the configured currency).

2. Submit a `FunctionCall` transaction to `myft.near` calling `ft_transfer` with `receiver_id` set to an unregistered account. If the contract emits the `EVENT_JSON:` log before the registration check panics, the receipt fails with `ActionError` but the log is preserved in the `ExecutionOutcome`.

   Alternatively, call any method on `myft.near` that emits a crafted `EVENT_JSON:{"standard":"nep141","version":"1.0.0","event":"ft_transfer","data":[{"old_owner_id":"victim.near","new_owner_id":"attacker.near","amount":"1000000000000000000000000"}]}` log and then panics.

3. After the block is finalized, query the Rosetta `/block` endpoint for that block.

**Expected (correct) result:** No FT transfer operations appear, because the receipt failed.

**Actual result:** The Rosetta response contains two `Transfer` operations both with `status: "SUCCESS"`:
- `victim.near` debited `1000000000000000000000000` MYFT
- `attacker.near` credited `1000000000000000000000000` MYFT

These operations are derived entirely from the log in the failed receipt. The on-chain FT balances are unchanged. Any exchange reconciling via Rosetta credits `attacker.near` with 1 MYFT that was never transferred.

**Relevant code path:**
`ExecutionToReceipts::for_block` (no status filter) → `collect_nep141_events` (no status filter) → `extract_events` (no status filter) → `compose_rosetta_nep141_events` (executor_id filter only) → `convert_fungible_token_balance_change_to_operations` (hardcoded `Success`) → `/block` response. pub(crate) fn extract_events(
    execution_outcome: &ExecutionOutcomeWithIdView,
) -> Vec<crate::models::Nep141Event> {
    let prefix = "EVENT_JSON:";
    execution_outcome
        .outcome
        .logs
        .iter()
        .filter_map(|untrimmed_log| {
            let log = untrimmed_log.trim();
            if !log.starts_with(prefix) {
                return None;
            }

            match serde_json::from_str::<'_, crate::models::Nep141Event>(log[prefix.len()..].trim())
            {
                Ok(result) => Some(result),
                Err(_err) => None,
            }
        })
        .collect()
}

async fn block_details(
    State(state): State<RosettaAppState>,
    Json(body): Json<models::BlockRequest>,

    let models::BlockRequest { network_identifier, block_identifier } = body;

    check_network_identifier(&state.client_addr, network_identifier).await?;

    let block_id: near_primitives::types::BlockReference = block_identifier.try_into()?;

        // identifier referencing itself:
        block_identifier.clone()

        let parent_block = state
            .view_client_addr

                near_primitives::types::BlockId::Hash(block.header.prev_hash).into(),
