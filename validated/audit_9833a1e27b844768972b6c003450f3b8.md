### Title
Webhook HMAC covers only the request body, not routing headers, allowing cross-tenant webhook replay - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The Merk report describes a Merkle proof implementation where the root-hash computation does not recurse into all nodes that are nonetheless trusted for key/value lookups, letting an attacker splice in unverified data that still "passes" verification. The shopify-app-js webhook authentication pipeline has an analogous structural flaw: the cryptographic proof (`X-Shopify-Hmac-Sha256`) only covers the raw request body, while the values used to decide *which tenant's session and Admin API client to load* (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, etc.) are carried in unauthenticated headers that are merely checked for *presence*, not for cryptographic binding to the signature.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC exclusively over `rawBody` and compares it to the `hmac` header: [1](#0-0) 

The routing/tenant-identifying headers (`domain`, `topic`, `webhookId`, `apiVersion`) are never included in this computation. `validateFactory` only performs a presence/format check on them via `checkWebhookHeaders` after the body HMAC succeeds: [2](#0-1) 

Downstream, the webhook authenticate handlers in both the Remix and React Router packages use `check.domain` — a value that was never part of the signed data — to look up and load the offline session (and thus the merchant-scoped Admin/Storefront API clients) for that shop: [3](#0-2) 

Crucially, the app's HMAC secret (`apiSecretKey`) is the *same shared secret* for the entire app across all installed shops — it is not shop-specific. So a valid `(rawBody, hmac)` pair obtained from one shop's genuine webhook delivery is cryptographically valid for **any** shop, since the signature never binds to `domain`. The `hmac-validator.test.ts`/`validate.test.ts` suite even demonstrates the general class of "signature computed elsewhere gets replayed against forged headers" (the cookie-signature-as-webhook-HMAC test was patched specifically for this reason), but the underlying architecture — headers unauthenticated, body-only HMAC — remains unchanged for the `domain`/`topic`/`webhookId` fields themselves: [4](#0-3) 

This is the direct structural analog of the Merk bug: the "root hash" (HMAC) does not cover data (headers) that is nonetheless used for a security-critical lookup (which tenant's session/credentials to load), so an attacker can present a validly-signed artifact whose unverified fields are freely substitutable.

### Impact Explanation
A malicious merchant (an unprivileged, single-tenant actor who has installed the app on their own shop, as scoped by the analog rules) can:
1. Trigger any subscribed webhook topic on their own shop to obtain a genuine `(rawBody, X-Shopify-Hmac-Sha256)` pair signed with the app's shared secret.
2. Replay that exact body/HMAC pair to the app's webhook endpoint, substituting `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id` as needed) with a victim shop's domain.
3. Because the HMAC check only validates the body, the request is accepted as "valid," and `ensureValidOfflineSession(params, check.domain)` loads the **victim's** offline session/Admin API client, and the attacker-authored body is dispatched to the app's webhook handler under the victim's identity.

Depending on what the app's webhook handler does with the payload (e.g., updating order/fulfillment state, billing, inventory, or other cross-shop side effects using the victim's Admin client), this can result in cross-tenant data corruption or unauthorized actions performed with another merchant's credentials — directly matching the "cross-tenant access" / "accepted forged Shopify request" impact categories.

### Likelihood Explanation
Exploitation only requires the attacker to install the app themselves (a normal, unprivileged onboarding step) and capture one legitimate webhook delivery HTTP request from Shopify to their own endpoint — trivially obtainable by inspecting their own server logs/proxy. No secret leakage, MITM, or privileged access to Shopify's infrastructure is required; the entire construction happens using data the attacker legitimately receives for their own shop.

### Recommendation
Bind the security-critical headers into the HMAC computation (or otherwise cryptographically bind `domain`/`topic`/`webhookId` to the signed payload), rather than only signing the raw body. Short term, apps can defense-in-depth by cross-checking `check.domain` against the shop associated with the loaded session's known identity before dispatching to handlers; long term, the library should document that these headers are unauthenticated and provide (or require) a mechanism that ties them to the signature, consistent with the Merk report's recommendation to make commitments/encodings injective and unambiguous end-to-end.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; subscribe to a webhook topic (e.g., `orders/create`).
2. Capture the resulting POST to the app's webhook endpoint, noting `rawBody` and the `X-Shopify-Hmac-Sha256` header value (valid because `hmac-validator.ts` only hashes `rawBody` with the shared `apiSecretKey`, per lines 189-197 above).
3. Re-send the identical request to the same endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and other routing headers as required) while keeping `rawBody` and `X-Shopify-Hmac-Sha256` unchanged.
4. `validateHmacFromRequestFactory` returns `valid: true` because the body/HMAC pair is untouched; `authenticateWebhookFactory` then loads `victim-shop.myshopify.com`'s offline session via `ensureValidOfflineSession(params, check.domain)` and invokes the app's handler with attacker-controlled body content attributed to the victim shop.
