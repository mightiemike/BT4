### Title
`TransactionOutput::ensure_match_transaction_info` (used by replay-verify tooling) omits checkpoint-hash validation, allowing state divergence to pass as a verified replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the core invariant check used by `db-tool replay-on-archive` and the CLI/debugger "replay and verify" flows to confirm that locally re-executed transactions match the authenticated, on-chain-committed `TransactionInfo`. It checks status, gas, write-set hash, and event root hash, but explicitly skips validation of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — a gap the code itself documents as needing to be closed before the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature is enabled. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` validates transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against the authenticated `TransactionInfo` pulled from the accumulator/backup data: [2](#0-1) 

It then contains a `TODO` comment that acknowledges the check intentionally ignores the state-checkpoint hashes:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This function is the sole correctness gate used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes historical transactions from the backup/archive and calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` to decide whether replay succeeded: [4](#0-3) 

It is also invoked from `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`, both of which are used for state-integrity verification (debugging historical replays / auditing committed state). None of these three call sites perform any additional checkpoint-hash comparison — `ensure_match_transaction_info` is treated as authoritative.

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as distinct, independently-committed fields in the accumulator-hashed `TransactionInfo`: [5](#0-4) 

These checkpoint hashes are meant to bind the transaction's post-execution state root (regular state, hot state, and the native-trading "position" state introduced under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`NATIVE_POSITION`) to the accumulator-committed, consensus-signed ledger. Because `ensure_match_transaction_info` never compares these fields to a locally recomputed value, a local execution divergence that changes only the checkpoint state root (and not the write-set hash, gas, status, or event root) will not be detected by replay-verify tooling — the tool will report a clean, successful replay even though the authenticated state root recorded on-chain diverges from what local execution produces.

### Impact Explanation
Replay-verify (`replay_on_archive`) and the debugger/CLI "verify" paths are the primary tools operators and auditors use to confirm that a local/full node's state matches the authenticated on-chain ledger, and to detect consensus-vs-execution divergence, non-determinism bugs, or storage/restore corruption. Because the comparator silently ignores checkpoint hashes, any bug that corrupts only the checkpoint/state root computation (e.g. in the state-checkpoint materialization path feeding `state_checkpoint_output.hot_state_checkpoint_hashes` / `position_state_checkpoint_hashes` in `do_ledger_update.rs`/`do_state_checkpoint.rs`) would go completely unreported by this tooling, giving false confidence that historical state is correctly reproduced. This is a proof/state-commitment binding gap: an authenticated field of the committed `TransactionInfo` (and therefore of the accumulator root) is excluded from the very tool designed to authenticate it.

The impact is currently latent rather than actively exploitable on mainnet: `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` are not in `FeatureFlag::default_features()`, i.e., not enabled by default, and `TRANSACTION_INFO_V1` (which these depend on) is likewise absent from the default set. [6](#0-5) [7](#0-6)  Once these features are turned on, however, the gap directly undermines the replay-verify invariant the code's own comment describes.

### Likelihood Explanation
The bug requires no attacker action against the network — it's a latent gap in an internal verification tool that will silently pass over a real discrepancy once the gated features (`TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) are enabled and any checkpoint-root computation bug or storage/restore inconsistency occurs. It does not require malicious behavior; it only requires (a) a real divergence in checkpoint-hash computation (from a bug elsewhere, e.g. in hot-state/position-state materialization) and (b) reliance on `replay_on_archive`/debugger tooling to detect it. The Aptos team's own TODO acknowledges this is a known, unresolved gap that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," indicating the maintainers consider it a real, imminent risk rather than a theoretical one.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionInfo` variant and known/computable from the replay context) against the authenticated `txn_info` fields, mirroring the existing write-set/event-root comparisons, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or `HOT_STATE_ROOT_IN_TXN_INFO` are enabled on any network. Until fixed, `replay_on_archive` and related debugger/CLI verification results should not be treated as proof that native-trading/hot-state checkpoint roots match the authenticated ledger.

### Proof of Concept
No exploit is required from an external actor; the gap is demonstrated directly by code inspection:
1. `TransactionInfoV1` stores `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` as independently committed, accumulator-hashed fields [5](#0-4) .
2. `ensure_match_transaction_info` (the only invariant check available to replay-verify tooling) compares status, gas, write-set hash, and event-root hash only [8](#0-7) , and its trailing comment confirms checkpoint hashes are excluded by design pending a fix [3](#0-2) .
3. `replay_on_archive::Verifier::execute_and_verify` calls this exact function as its pass/fail criterion for each replayed transaction [9](#0-8) .

Because I could not execute the full node/replay pipeline in this environment, I was not able to construct an end-to-end reproduction that actually triggers a checkpoint-hash divergence (e.g., a concrete hot-state/position-state computation bug); the finding is limited to demonstrating that the verification gap exists and is reachable through the documented tooling, as acknowledged by the maintainers' own TODO comment.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
