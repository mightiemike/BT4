## Finding: Missing depth bound check in `SparseMerkleRangeProof::verify` causes integer-underflow panic on malformed state-sync/restore proofs

### Summary
`SparseMerkleRangeProof::verify` computes a `skip` count from an attacker/peer-controlled sibling-count field without first bounding it against the fixed 256-bit key depth, unlike its sibling proof types (`AccumulatorProof`, `AccumulatorRangeProof`) which explicitly enforce `MAX_ACCUMULATOR_PROOF_DEPTH` before doing any arithmetic on sibling counts.

### Finding Description
`SparseMerkleRangeProof::verify` in [1](#0-0)  does:

```rust
let num_siblings = left_siblings.len() + self.right_siblings.len();
...
for bit in rightmost_known_leaf.key().iter_bits().rev()
    .skip(HashValue::LENGTH_IN_BITS - num_siblings)
```

`self.right_siblings` is a plain `Vec<HashValue>` [2](#0-1)  deserialized straight off the wire/backup file with **no cap enforced anywhere in `SparseMerkleRangeProof::new` or `verify`**. By contrast, the accumulator proof types explicitly bound sibling counts before doing index/arithmetic work on them: `AccumulatorProof::verify` checks `self.siblings.len() <= MAX_ACCUMULATOR_PROOF_DEPTH` [3](#0-2)  and `AccumulatorRangeProof::verify` checks both `left_siblings.len()` and `right_siblings.len()` against the same bound [4](#0-3) . `SparseMerkleRangeProof` has no analogous guard.

If a peer or backup file supplies a proof whose `right_siblings.len()` (combined with the locally-derived `left_siblings.len()`) exceeds `HashValue::LENGTH_IN_BITS` (256), the subtraction `HashValue::LENGTH_IN_BITS - num_siblings` underflows a `usize`. This is exactly the "untrusted length field trusted before an arithmetic/slice operation" pattern from the seed report (`public_values[0..size]` sliced before a length check).

The call chain that reaches this with untrusted input is:
- `JellyfishMerkleRestore::verify_chunk` → `self.verify(proof)` [5](#0-4) , which is invoked by `StateSnapshotReceiver::add_chunk` [6](#0-5) .
- `add_chunk` is fed directly from network fast-sync state-value payloads via `StorageSynchronizer::save_state_values`/`apply_snapshot_chunk` [7](#0-6) , and from backup restore tooling [8](#0-7) .

In both paths the `SparseMerkleRangeProof` bytes come from an external, unprivileged source (a sync peer or a backup blob), and `add_chunk`/`verify_chunk` is called before any content is durably committed — so the length is trusted before use, exactly mirroring the SP1 `public_values` bug class.

### Impact Explanation
If this underflow panics (Rust's default debug behavior, and also in any release build compiled with `overflow-checks = true`, which `RUST_SECURE_CODING.md` in this repo explicitly calls out as project policy), any node performing fast-sync bootstrapping or backup restore can be crashed by an unprivileged peer/backup source supplying a state-value chunk with an oversized `right_siblings` vector — a remote DoS against the state-sync and restore machinery, which is squarely a proof-verification integrity code path (the same class the Gate calls out: "Merkle proof ... accepted as valid" / crash before verification completes). If overflow-checks are disabled, the subtraction instead wraps to a near-`usize::MAX` skip count, causing the loop to iterate zero times and leave `current_hash` unrecomputed; this reliably fails the final root-hash equality check rather than accepting a forged proof, so in that build configuration the practical impact is limited to DoS via panic risk in debug/overflow-checked builds rather than a silent acceptance of bad state.

I could not confirm from the index whether Aptos's actual release CI build enables `overflow-checks`; the repo's `Cargo.toml` and `RUST_SECURE_CODING.md` reference the setting but I was not able to inspect the exact profile value before running out of tool budget.

### Likelihood Explanation
The `SparseMerkleRangeProof` proof bytes are deserialized directly from state-sync network messages and backup files, both of which are attacker-influenceable (a malicious peer, or a compromised/corrupted backup source). No signature or additional bound check on `right_siblings.len()` exists before it is used in the underflowing subtraction, so triggering the code path only requires sending a state-value chunk whose accompanying range proof carries an oversized sibling vector — no forged cryptographic material is required, matching the "no forged proof required, only a bad length" characteristic of the seed report.

### Recommendation
Add an eager bound check in `SparseMerkleRangeProof::verify` (and/or in `SparseMerkleRangeProof::new`) rejecting proofs where `left_siblings.len() + self.right_siblings.len() > HashValue::LENGTH_IN_BITS`, mirroring the `MAX_ACCUMULATOR_PROOF_DEPTH` checks already present in `AccumulatorProof::verify` and `AccumulatorRangeProof::verify`, before performing the `HashValue::LENGTH_IN_BITS - num_siblings` subtraction.

### Proof of Concept
1. Craft a `StateValueChunkWithProof` (or a backup state-snapshot chunk) whose `proof: SparseMerkleRangeProof` has `right_siblings` containing more than 256 `HashValue` entries (trivial to serialize via BCS since the vector has no length cap).
2. Send it to a syncing node during fast sync (or feed it to a node running `db-restore`).
3. `StateSnapshotReceiver::add_chunk` → `JellyfishMerkleRestore::verify_chunk` → `verify()` computes `num_siblings = left_siblings.len() + right_siblings.len() > 256` and executes `HashValue::LENGTH_IN_BITS - num_siblings`, underflowing the `usize` subtraction and panicking in any build with overflow checks enabled, crashing the syncing/restoring node's process.
