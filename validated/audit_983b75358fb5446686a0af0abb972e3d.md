### Title
Truncating Division in `CalculateGasCost` Zeroes Out Gas Fees When EIP-1559 Base Fee Decays Below 1 upc - (File: x/uexecutor/keeper/fees.go)

### Summary
`CalculateGasCost` unwraps the feemarket's `LegacyDec` base fee back into a whole `upc` integer using `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` before multiplying by `gasUsed`. This is the same class of bug as the reported interest-rounding issue: an integer division that truncates a small numerator to zero, silently zeroing out the resulting fee/interest. Here, if the feemarket's dynamically-adjusted base fee ever decays below `1e18` in its `LegacyDec` representation (i.e., below 1 whole `upc`), the division rounds down to `0`, `effectiveGasPrice` becomes `0`, and `gasCost` becomes `0` regardless of how much gas was actually used.

### Finding Description
`CalculateGasCost` in [1](#0-0)  computes the fee UEA/CEA payload execution owes for the EVM gas it consumed:

```go
baseFeeBig := baseFee.BigInt()
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
...
effectiveGasPrice := new(big.Int).Set(baseFeeBig)
gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig)
``` [2](#0-1) 

The inline comment asserts "the base fee is always a whole number of upc -- no fractional upc exists," but nothing in this code (or the caller) enforces that invariant. `baseFee` is read directly from the standard cosmos-evm feemarket module's dynamically-adjusted EIP-1559 base fee via `k.feemarketKeeper.GetBaseFee(sdkCtx)` in `DeductGasFeesFromReceipt` [3](#0-2) . That base fee is a `LegacyDec` (18-decimal fixed point) value that adjusts up or down every block based on gas utilization relative to target, exactly like Ethereum's EIP-1559 mechanism. Sustained low network utilization causes it to decay multiplicatively block after block, and nothing in the feemarket module or in `CalculateGasCost` floors it at `1e18` (i.e., 1 whole `upc`). Once `baseFee < 1e18` in its Dec representation, `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` truncates to `0`, making `effectiveGasPrice = 0` and thus `gasCost = new(big.Int).Mul(0, gasUsedBig) = 0` no matter how large `gasUsed` is.

Downstream, `DeductGasFeesFromReceipt` treats a non-positive `gasCost` as "nothing to deduct" and returns early without charging any fee: `if gasCost.Sign() <= 0 { return nil }` [4](#0-3) . This is invoked from the universal-execution payload path to charge the UEA/CEA recipient for the EVM gas consumed by their `DerivedEVMCall`.

This mirrors the reported bug precisely: a formula divides a legitimately small (but non-zero) numerator by a large fixed denominator (`1e18`) without a minimum-value floor or added precision, so the result silently rounds to zero and the fee that should have been collected is not collected.

### Impact Explanation
Under sustained low chain utilization (which is realistic — not every block will be full, and Push Chain's own EIP-1559 base fee mechanism is designed to fall toward a floor over idle periods), the base fee can decay below 1 whole `upc`. Once that happens, every payload execution processed through `DeductGasFeesFromReceipt` charges the executing UEA/CEA recipient **zero** gas fee, no matter the actual `gasUsed`, until the base fee climbs back above 1 `upc`. This is a direct, unprivileged loss of protocol fee revenue/gas-fee accounting corruption (in-scope: "corruption of ... gas fee accounting ... or refund accounting") reachable purely from ordinary user payload submission with no privileged actor involved. It also creates a free-execution window that can be exploited to run unlimited unpaid EVM computation via the universal executor, which can be abused for spam/resource exhaustion at effectively no cost to the attacker.

### Likelihood Explanation
No attacker action is required to trigger the root cause — it occurs naturally whenever network activity is low enough for the standard EIP-1559 base-fee decay to push the value under 1 `upc`, which is a normal, expected market condition rather than an edge case requiring privileged access or adversarial validators. An attacker aware of this can also directly encourage/trigger it by avoiding driving up gas utilization and simply waiting for/timing their submissions to periods of low base fee.

### Recommendation
Do not simply floor-divide the `LegacyDec` base fee by `1e18` before multiplying by `gasUsed`. Instead, keep the base fee in its full-precision `LegacyDec`/`big.Rat` form throughout the computation, multiply by `gasUsed` first, and only truncate/round at the very end (analogous to how `min_gas_price.go` computes `fee = ceil(minGasPrice * gasLimit)` using `Dec.Mul(...).Ceil().RoundInt()`) [5](#0-4) . Alternatively, enforce (and validate) a hard floor on the feemarket's base fee of at least `1e18` (1 whole `upc`) so the truncating division can never zero out the result.

### Proof of Concept
1. Let the feemarket base fee decay (or be configured) to a `LegacyDec` value below `1e18`, e.g. `0.5 upc` represented internally as `5 * 10^17`.
2. A user submits a universal payload that results in a `DerivedEVMCall` consuming, say, `500,000` gas.
3. `DeductGasFeesFromReceipt` calls `CalculateGasCost(baseFee=0.5upc, ..., gasUsed=500000)`.
4. Inside, `baseFeeBig = 5*10^17`; `baseFeeBig.Div(baseFeeBig, 1e18)` → `0` (integer truncation).
5. `effectiveGasPrice = 0`, `gasCost = 0 * 500000 = 0`.
6. `gasCost.Sign() <= 0` is true, so `DeductGasFeesFromReceipt` returns `nil` without deducting or burning any fee from the recipient — the payload executes with 500,000 gas consumed and zero fee charged.

func (k Keeper) CalculateGasCost(
	baseFee sdkmath.LegacyDec,
	maxFeePerGas *big.Int,
	maxPriorityFeePerGas *big.Int,
	gasUsed uint64,
) (*big.Int, error) {
	baseFeeBig := baseFee.BigInt()
	// @dev: LegacyDec stores values with 18-decimal precision internally, so 1 upc = 1e18
	// in the LegacyDec representation. Since 1 upc is the smallest denomination (like wei
	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.
	// This division unwraps the LegacyDec encoding back to the actual upc amount.
	// Note: baseFee.BigInt() returns a reference to the internal big.Int; the in-place Div
	// mutates it, which is safe here since baseFee is a local value-type copy.
	baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))

	// Step 1: Validate maxFeePerGas >= baseFee
	if maxFeePerGas.Cmp(baseFeeBig) < 0 {
		return nil, fmt.Errorf("maxFeePerGas (%s) cannot be less than baseFee (%s)", maxFeePerGas, baseFeeBig)
	}

	// Step 2: Calculate baseFee + maxPriorityFeePerGas (potential effective gas price)
	// @dev: Currently, we are not using maxPriorityFeePerGas in the calculation
	// tipPlusBase := new(big.Int).Add(baseFeeBig, maxPriorityFeePerGas)
	// tipPlusBase := maxFeePerGas

	// Step 3: Find effective gas price by taking minimum
	// @dev: Currently, since we are not using maxPriorityFeePerGas, effectiveGasPrice is just baseFee
	effectiveGasPrice := new(big.Int).Set(baseFeeBig)
	// if tipPlusBase.Cmp(maxFeePerGas) == -1 {
	// 	effectiveGasPrice = tipPlusBase
	// }

	// Step 4: Calculate final gas cost: effectiveGasPrice * gasUsed
	gasUsedBig := new(big.Int).SetUint64(gasUsed)
	gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig)

	k.Logger().Debug("gas cost calculated",
		"base_fee", baseFee.String(),
		"effective_gas_price", effectiveGasPrice.String(),
		"gas_used", gasUsed,
		"gas_cost", gasCost.String(),
	)

	return gasCost, nil
}
