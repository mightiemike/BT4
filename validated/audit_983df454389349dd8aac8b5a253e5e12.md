### Title
Unbounded prefix-scan and sort in `DelegatedResourceAccountIndexStore.getWithPrefix` allows algorithmic-complexity DoS via `getdelegatedresourceaccountindex` - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix` (used by both `getIndex` and `getV2Index`) performs an unbounded `prefixQuery` over the DB, materializes all matching entries into a `HashMap`/`ArrayList`, and sorts them with `Comparator.comparing(getTimestamp)` on every call, with no cap on the number of entries processed. An attacker can cheaply seed a very large number of delegation index entries for one owner address and then repeatedly invoke the public, unauthenticated `getdelegatedresourceaccountindex` HTTP/gRPC endpoint to force the node to repeatedly perform this large, unbounded computation.

### Finding Description
`DelegateResourceActuator.execute` calls `delegatedResourceAccountIndexStore.delegateV2(...)` [1](#0-0)  which stores one `V2_FROM_PREFIX`+owner+receiver and one `V2_TO_PREFIX`+receiver+owner row per delegation [2](#0-1) . Reading back the index goes through `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`, which call `getIndex`/`getV2Index` on the store [3](#0-2) . Both delegate to `getWithPrefix`, which does an unfiltered `prefixQuery(key)` into a `HashMap`, copies all values into an `ArrayList`, and sorts the full list by timestamp with no limit, offset, or pagination [4](#0-3) . This is reachable from the unauthenticated HTTP servlet `GetDelegatedResourceAccountIndexServlet.fillResponse` -> `wallet.getDelegatedResourceAccountIndex(address)` [5](#0-4)  and the equivalent gRPC/JSON-RPC/PBFT/Solidity variants. The servlet extends `RateLimiterServlet`, which only throttles request *frequency* (QPS), not the *cost* of an individual request — once entries exist, each subsequent call still performs the full unbounded scan/sort regardless of rate limiting.

To seed entries, an attacker needs a funded owner account with sufficient `FreezeBalanceV2` bandwidth/energy and, for each target receiver, a pre-existing activated account (validated by `receiverCapsule == null` check in `DelegateResourceActuator.validate`) [6](#0-5) , with `delegateBalance >= 1 TRX` per delegation [7](#0-6) . No check anywhere limits the total number of distinct receivers/index rows an owner can accumulate.

### Impact Explanation
This is a DoS-via-RPC-API class issue: once an attacker has built up a large number of delegation index entries for one owner (a one-time cost), any caller (attacker or others) can trigger repeated, unbounded CPU (sort) and heap (materializing full result sets) work per query against that address, degrading node responsiveness for all API consumers sharing that node/thread pool. It does not corrupt consensus state, steal funds, or leak keys — the impact is limited to service-level degradation (stall/slow responses) on nodes exposing this API.

### Likelihood Explanation
Feasibility is gated by real economic cost: the attacker must (a) pre-fund and activate N receiver accounts, and (b) freeze/delegate at least 1 TRX per receiver from the owner account (bounded by the owner's total frozen V2 balance), and (c) pay bandwidth/energy for N broadcast transactions. For N in the tens of thousands this requires meaningful capital and many transactions, but it's entirely within reach of an ordinary funded, unprivileged account — no signature bypass, no permission-weight bypass, and no fork gate blocks it (`supportDR()`/`supportUnfreezeDelay()` are standard mainnet features). Crucially, after the one-time seeding cost, the amplification vector (repeated free/cheap read-only queries, only throttled by QPS not cost) can be replayed indefinitely and cheaply.

### Recommendation
Bound `getWithPrefix` with a hard cap on the number of entries scanned/returned (and/or add pagination parameters to `getIndex`/`getV2Index`/the RPC methods), reject or truncate results beyond a configurable maximum, and/or track and enforce a maximum number of distinct delegation-index entries per owner address in `DelegateResourceActuator.validate`.

### Proof of Concept
```java
// JUnit-style PoC against DelegatedResourceAccountIndexStore
@Test
public void testUnboundedGetIndexScaling() {
  byte[] owner = "owner".getBytes();
  int N = 100_000;
  for (int i = 0; i < N; i++) {
    delegatedResourceAccountIndexStore.delegateV2(
        owner, ("receiver" + i).getBytes(), i);
  }
  long start = System.nanoTime();
  DelegatedResourceAccountIndexCapsule result =
      delegatedResourceAccountIndexStore.getV2Index(owner);
  long elapsed = System.nanoTime() - start;
  // elapsed and heap usage grow ~linearly/O(N log N) with N, with no cutoff
  Assert.assertEquals(N, result.getToAccountsList().size());
}
```

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
