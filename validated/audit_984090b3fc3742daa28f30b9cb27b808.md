### Title
Sierra-to-CASM compilation for declare transactions runs before signature and balance verification, enabling pre-authorization resource exhaustion - ([File: crates/apollo_gateway_config/src/config.rs])

### Summary
The Starknet gateway's declare-transaction ingestion path is documented and configured to compile a submitted Sierra class to CASM — a CPU- and memory-intensive operation — before the transaction's signature and account balance are verified. This mirrors the OpenClaw bug class (GHSA-hhff-fj5f-qg48): expensive preflight work (there, audio transcription; here, Sierra→CASM compilation) is performed prior to the authorization/authentication gate (there, Discord member allowlist; here, signature + fee/balance validation), allowing an unauthenticated or unfunded sender to consume disproportionate node resources per submitted transaction.

### Finding Description
The gateway config explicitly documents this ordering and the compensating mitigation: [1](#0-0) 

This shows that:
1. Compilation happens "during transaction ingestion before the transaction's signature and balance are verified."
2. The only protection is a concurrency cap, `max_concurrent_declare_compilations` (default `DEFAULT_MAX_CONCURRENT_DECLARE_COMPILATIONS = 40`), which bounds *concurrent* compilations but does not require any authentication or fee-sufficiency check before a compilation is dispatched.

The broader transaction submission flow diagram corroborates this ordering: the gateway forwards the Sierra class to the Class Manager/Sierra Compiler for compilation, and only afterward performs stateful validation (nonce, balance, resource bounds) via the blockifier: [2](#0-1) 

The actual compilation work is delegated to a subprocess-isolated compiler with CPU/memory/time limits per single compilation: [3](#0-2) 

and to the `ClassManager::add_class` path which times and logs compilation duration, again prior to any statement here about balance/signature checks: [4](#0-3) 

The stateless validator (`StatelessTransactionValidator::validate`) checks resource bounds, tx size, and DA modes, but does not perform signature verification or account balance checks — those occur in the stateful validator, later: [5](#0-4) 

Stateful (balance/fee) checks occur in `StatefulTransactionValidator::validate_state_preconditions`, which is invoked after class handling in the ingestion pipeline per the sequence diagram: [6](#0-5) 

### Impact Explanation
An attacker with no account balance and no valid signature (or with a signature/nonce that will ultimately be rejected) can submit a flood of declare transactions with distinct, large/complex Sierra programs. Each triggers a CPU- and memory-intensive Sierra→CASM compilation job before any economic or cryptographic gate rejects the transaction. Although a concurrency cap (`max_concurrent_declare_compilations`, default 40) exists, an attacker can still saturate that cap with fee-less, unauthenticated declares, denying legitimate declare transactions timely compilation slots and consuming the shared sierracompiler fleet's capacity ("blast radius" as acknowledged in the code comment). This is a resource-consumption / gateway-availability degradation matching CWE-770/CWE-408 in the referenced advisory, not a fund-loss or consensus-divergence bug — it affects gateway-level availability for declare transaction ingestion.

### Likelihood Explanation
Likelihood is high for triggering: submitting a declare transaction with an arbitrary Sierra class and no valid balance/signature is trivially reachable by any user of the public RPC/gateway endpoint, with no special privilege required. The existing mitigation (concurrency cap) reduces the severity from unbounded resource exhaustion to a bounded denial-of-service against the declare-compilation pipeline, consistent with the "narrow"/"medium" triage given to the analogous OpenClaw advisory.

### Recommendation
Move minimal-cost authorization checks (signature verification and a lightweight balance/fee-sufficiency pre-check) ahead of Sierra→CASM compilation in the declare ingestion path, so that unauthenticated or unfunded declares are rejected before the class manager forwards the class to the compiler. If reordering is infeasible due to needing the compiled class hash for hash-based checks, consider a cheap pre-check (e.g., verifying the sender has a minimum balance or a valid signature over the raw class bytes) prior to invoking `SierraCompiler::compile`/`ClassManager::add_class`. Additionally, consider per-sender/per-IP rate limiting on declare submissions to complement the global `max_concurrent_declare_compilations` bound.

### Proof of Concept
1. Craft a valid-format Sierra class with maximal bytecode size (within `max_bytecode_size`) that requires expensive compilation.
2. Submit a declare transaction referencing this class from a sender account with insufficient balance and/or an invalid signature, via the gateway's `add_tx` entrypoint.
3. Observe (per `crates/apollo_gateway_config/src/config.rs` comment) that the Sierra→CASM compilation is dispatched via the Class Manager/Sierra Compiler before the stateful signature/balance check runs.
4. Repeat concurrently up to `max_concurrent_declare_compilations` (40 by default) with distinct classes; further legitimate declare transactions are rejected/delayed while the compiler fleet processes attacker-submitted, ultimately-invalid transactions.

```rust
// Compiling a declared Sierra class to CASM is CPU- and memory-intensive, and it happens during
// transaction ingestion before the transaction's signature and balance are verified. Bound the
// number of compilations running concurrently to protect the node from resource exhaustion.
//
// Derivation: compilations are served by the sierracompiler instances, so the safe per-gateway
// bound is the sierracompiler fleet's headroom divided across the gateway fleet, i.e.
// `per_instance_capacity * num_sierracompiler_instances / num_gateway_instances`. Observed
// sierracompiler usage per compilation is small (memory spike ~0.75% of an instance), so a single
// instance can absorb many concurrent compilations. 40 stays well within that envelope while still
// capping the blast radius of a declare flood; retune via the formula above if the
// sierracompiler/gateway instance ratio or per-instance capacity changes.
const DEFAULT_MAX_CONCURRENT_DECLARE_COMPILATIONS: usize = 40;
```

```rust
    pub fn compile(
        &self,
        contract_class: ContractClass,
    ) -> Result<CasmContractClass, CompilationUtilError> {
        let compiler_binary_path = &self.path_to_binary;
        let additional_args = &[
            "--add-pythonic-hints",
            "--max-bytecode-size",
            &self.config.max_bytecode_size.to_string(),
            "--allowed-libfuncs-list-name",
            if self.config.audited_libfuncs_only { "audited" } else { "all" },
        ];
        let resource_limits = ResourceLimits::new(
            Some(self.config.max_cpu_time),
            None,
            Some(self.config.max_memory_usage),
        );

        let stdout = compile_with_args(
            compiler_binary_path,
            contract_class,
            additional_args,
            resource_limits,
        )?;
        Ok(serde_json::from_slice::<CasmContractClass>(&stdout)?)
    }
```

```rust
    #[instrument(skip(self, class), ret, err)]
    pub async fn add_class(&mut self, class: RawClass) -> ClassManagerResult<ClassHashes> {
        let sierra_class = SierraContractClass::try_from(&class)?;
        let class_hash = sierra_class.calculate_class_hash();
        if let Ok(Some(executable_class_hash_v2)) =
            self.classes.get_executable_class_hash_v2(class_hash)
        {
            // Class already exists.
            return Ok(ClassHashes { class_hash, executable_class_hash_v2 });
        }

        let compilation_start_time = Instant::now();
        let (raw_executable_class, executable_class_hash_v2) =
            self.compiler.compile(class.clone()).await.map_err(|err| match err {
                SierraCompilerClientError::SierraCompilerError(error) => {
                    ClassManagerError::SierraCompiler { class_hash, error }
                }
                SierraCompilerClientError::ClientError(error) => {
                    ClassManagerError::Client(error.to_string())
                }
            })?;
        debug!(
            %class_hash,
            compiled_class_hash = %executable_class_hash_v2,
            compilation_elapsed_ms = compilation_start_time.elapsed().as_millis(),
            class_size_bytes =
                class.size().map_or("Failed to get class size".to_owned(), |size| size.to_string()),
            casm_size_bytes =
                raw_executable_class.size().map_or("Failed to get casm size".to_owned(), |size| size.to_string()),
            "Finished compiling class."
        );

        self.validate_class_length(&raw_executable_class)?;
```
