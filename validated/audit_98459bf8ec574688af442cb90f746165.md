### Title
Unchecked `u32` subtraction in `calculate_new_difficulty` diverges from Bitcoin consensus difficulty-retarget behaviour on a negative epoch timespan - (File: `crates/bitcoin-da/src/verifier.rs`)

### Summary
`calculate_new_difficulty` computes the actual timespan of a 2016-block Bitcoin difficulty epoch as a plain `u32` subtraction, `last_timestamp - epoch_start_time`, instead of the signed subtraction Bitcoin Core itself uses. If `epoch_start_time` is ever greater than `last_timestamp` (a negative real timespan, which Bitcoin consensus explicitly anticipates and clamps to the lower bound), the `u32` subtraction wraps to a value near `u32::MAX` instead of being negative. This wrapped value is then clamped by the *upper* bound check instead of the *lower* bound check, producing a next-epoch target that diverges from what real Bitcoin consensus (and thus the true chain) would compute.

### Finding Description
`calculate_new_difficulty` in `crates/bitcoin-da/src/verifier.rs` implements Bitcoin's difficulty retarget algorithm used by the DA verifier/light client to independently recompute expected difficulty (`bits`) for a new epoch: [1](#0-0) 

```rust
let mut actual_timespan = last_timestamp - epoch_start_time;
if actual_timespan < expected_epoch_timespan / 4 {
    actual_timespan = expected_epoch_timespan / 4;
} else if actual_timespan > expected_epoch_timespan * 4 {
    actual_timespan = expected_epoch_timespan * 4;
}
```

Bitcoin Core computes this same quantity as a **signed** 64-bit value (`nActualTimespan = pindexLast->GetBlockTime() - nFirstBlockTime`) precisely because block timestamps are not strictly monotonic across an entire 2016-block epoch — a block only needs to exceed the median of the previous 11 blocks' timestamps, so the timestamp at the end of an epoch can legitimately be less than the timestamp at the start of the epoch, yielding a negative timespan that Bitcoin Core clamps to the lower bound `expected/4`.

Here, both `last_timestamp` and `epoch_start_time` are `u32`. If `epoch_start_time > last_timestamp`, the subtraction underflows. In an execution environment without overflow checks enabled (the default `release` behaviour for Rust), this wraps around to a huge value near `u32::MAX` rather than producing a negative result. That huge wrapped value is caught by the *upper*-bound branch (`actual_timespan > expected_epoch_timespan * 4`) and clamped to `expected_epoch_timespan * 4` — the opposite of the correct Bitcoin behaviour, which would clamp the (correctly negative) timespan to `expected_epoch_timespan / 4`.

This means for the same real Bitcoin block timestamps, this Rust reimplementation of Bitcoin's retarget rule can compute a target that is far larger (i.e., an easier target / lower difficulty) than what real Bitcoin consensus computes for that epoch, breaking the equality that must hold between "the difficulty/target computed natively by Bitcoin consensus" and "the difficulty/target recomputed by Citrea's DA verifier for the same header sequence."

### Impact Explanation
This function underlies the DA verifier's independent recomputation of Bitcoin's proof-of-work target for each new difficulty epoch, which is part of validating the Bitcoin header chain that Citrea's light client and DA layer trust. A divergence here means the verifier could accept (or expect) a target/bits value that does not match what real Bitcoin nodes/miners actually use for that epoch, i.e., a forged/incorrect notion of the required proof-of-work for a segment of the header chain — directly touching the DA-integrity binding between "the root/target computed natively" and "the root/target computed in this verifier." Depending on how this feeds into header-chain acceptance, it could let a chain segment with insufficient real-Bitcoin work be treated as satisfying the (wrongly relaxed) difficulty requirement inside Citrea's verifier logic.

### Likelihood Explanation
The triggering condition — the last block of a 2016-block epoch having a timestamp earlier than the first block of that epoch — is rare but not prevented by Bitcoin's timestamp rules, which only enforce a local median-time-past constraint, not epoch-wide monotonicity; Bitcoin Core's own use of signed arithmetic for this exact computation confirms this case is anticipated. The bug requires no privileged role and is purely a consequence of naturally-occurring (if unusual) Bitcoin block timestamp sequences, so it is reachable through ordinary Bitcoin chain data without any special network position.

### Recommendation
Compute `actual_timespan` using signed arithmetic (e.g., `i64`), matching Bitcoin Core's `nActualTimespan` computation, then clamp to `[expected_epoch_timespan/4, expected_epoch_timespan*4]` before converting back to `u32`/`U256`, e.g.:

```rust
let mut actual_timespan = last_timestamp as i64 - epoch_start_time as i64;
if actual_timespan < (expected_epoch_timespan / 4) as i64 {
    actual_timespan = (expected_epoch_timespan / 4) as i64;
} else if actual_timespan > (expected_epoch_timespan * 4) as i64 {
    actual_timespan = (expected_epoch_timespan * 4) as i64;
}
let actual_timespan = actual_timespan as u32;
```

### Proof of Concept
Given `epoch_start_time = T` and `last_timestamp = T - 1` (i.e., the epoch's last block timestamp is one second earlier than its first block's timestamp — permissible since Bitcoin only enforces the median-time-past-of-last-11-blocks rule, not epoch-wide monotonicity):

- Real Bitcoin consensus: `nActualTimespan = -1`, clamped to `expected_epoch_timespan/4` (the epoch is treated as maximally short → difficulty increases toward the max allowed factor).
- This code: `actual_timespan = (T-1) - T` computed in `u32` wraps to `u32::MAX`, which is `> expected_epoch_timespan*4`, so it is clamped to `expected_epoch_timespan*4` (the epoch is treated as maximally long → difficulty decreases toward the min allowed factor) — the opposite clamp direction from real consensus, producing a materially different (and much larger/easier) target than the one Bitcoin's actual consensus rules require for that epoch. ```rust
/// Calculates the new difficulty target for the next epoch.
fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target_bits: u32,
    max_target: U256,
    expected_epoch_timespan: u32,
) -> [u8; 32] {
    // Step 1: Calculate the actual timespan of the epoch
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < expected_epoch_timespan / 4 {
        actual_timespan = expected_epoch_timespan / 4;
    } else if actual_timespan > expected_epoch_timespan * 4 {
        actual_timespan = expected_epoch_timespan * 4;
    }
    // Step 2: Calculate the new target
    let new_target_bytes = bits_to_target(current_target_bits);
    let mut new_target = U256::from_be_bytes(new_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(expected_epoch_timespan));
    // Step 3: Clamp the new target to the maximum target
    if new_target > max_target {
        new_target = max_target;
    }

    new_target.to_be_bytes()
}
