### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash` (or hot/position checkpoint hashes), letting replay-verify tooling accept a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the local-proof-integrity check used by replay/backup-verification tooling to confirm a freshly re-executed transaction matches the authenticated, signed `TransactionInfo` recorded in the ledger. It checks status, gas used, write-set hash, and event root hash, but the function returns `Ok(())` without ever comparing the locally computed state root against the expected `state_checkpoint_hash` (nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`). [1](#0-0) 

### Finding Description
`TransactionInfo` binds four things: `transaction_hash`, `state_change_hash` (write-set hash), `event_root_hash`, and `state_checkpoint_hash` (the SMT/JMT root produced after applying the transaction). This structure is hashed into leaves of the transaction accumulator, whose root is signed by validators inside `LedgerInfo` [2](#0-1) . Any authenticated proof of correctness for historical execution ultimately reduces to confirming that a locally recomputed `TransactionInfo` (and specifically the resulting state root) matches this authenticated record.

`ensure_match_transaction_info` is the exact function meant to perform that comparison during replay/verification. It validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but it never touches `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` at all [3](#0-2) . The code itself documents this exact gap in a TODO comment immediately before the (missing) checks: "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [4](#0-3) .

This function is invoked directly by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes historical transactions from a chunk against a target DB and calls `ensure_match_transaction_info` per-transaction to decide pass/fail for the whole verification run [5](#0-4) . Because the state-checkpoint hash is never checked, any divergence in the *state* produced by re-execution (e.g., from a JMT/SMT computation bug, a state-checkpoint construction bug in `do_state_checkpoint.rs`, or an executor regression that only manifests in the state root and not in the write set/events/gas/status) is invisible to this tool: the write-set hash, event root, gas, and status can all match while the actual materialized state tree diverges, and the check still returns `Ok(())`.

### Impact Explanation
Replay verification (`db-tool replay-on-archive`, `replay-verify`, and equivalent debugger/CLI paths that call this same comparator) is one of the primary tools used to detect state-commitment bugs by replaying historical chain data and comparing to the authenticated backup/archive record. Because the comparator silently skips the state-checkpoint root — the single most important integrity signal for "does re-execution reproduce the correct committed ledger state" — a real state-divergence bug (introduced by a future code change, an executor/VM regression, or corrupted archive backfill) could pass replay verification undetected. This falls squarely under "Hard-fork-only divergence during commit, replay, restore, or proof verification" in the impact criteria: a verification tool that is supposed to catch exactly this class of bug provides a false sense of assurance, allowing corrupted or incorrect state roots to go unnoticed until they cause consensus-level failures or an undetected chain split.

Note the live/mainnet commit path itself (`execution/executor/src/chunk_executor/mod.rs` → `DoStateCheckpoint`/`DoLedgerUpdate`) has its own independent state-checkpoint-hash verification against `known_state_checkpoints` [6](#0-5) , so this gap does not by itself allow an invalid state root to be *committed* to the primary ledger. Its impact is confined to the correctness guarantee of the replay/backup-verification tooling (`replay_on_archive`, and any other caller of `ensure_match_transaction_info`), which is precisely the kind of proof/replay-verification integrity gap called out as in-scope.

### Likelihood Explanation
This is not a speculative or theoretical gap — it is explicitly documented in-code as a known, currently-unaddressed defect via the `TODO(trading-native)` comment, confirming the maintainers are aware the comparator is incomplete. The unprivileged trigger condition is simply "run replay-verify over a backup where local re-execution's state root differs from the archived state root while write-set bytes, events, gas, and status happen to match" — which is realistic for narrow classes of bugs (e.g., an SMT root/serialization bug, or one confined to state-checkpoint hash aggregation logic, position-state or hot-state paths) that don't change the concrete write set contents but do change how the checkpoint root is derived from it.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash` (and, when applicable to the enabled feature set, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the locally computed state-checkpoint root for the transaction, mirroring the existing checks already used in `do_state_checkpoint.rs`'s `get_state_checkpoint_hashes`. This closes the gap before any dependent feature (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled, and ensures `replay_on_archive`/`replay-verify` actually detect state-root divergence rather than only write-set/event/gas/status divergence.

### Proof of Concept
Local static-analysis proof (no live PoC executed, since I do not have execution access):
1. `TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  only asserts on `status`, `gas_used`, `write_set_hash`, and `event_root_hash`.
2. It never reads `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` — confirmed by absence of any such comparison and the explicit TODO comment admitting this [4](#0-3) .
3. `replay_on_archive.rs::execute_and_verify` re-executes a chunk of historical transactions and treats a return of `Ok(())` from this function as full verification success for that transaction [5](#0-4) .
4. Therefore, a transaction whose replayed write set/events/gas/status match the archived `TransactionInfo` but whose derived state-checkpoint root differs (e.g., due to a bug isolated to checkpoint-root aggregation) will be reported as a successful, verified replay, even though the authenticated state root has diverged — exactly as stated in the code's own TODO comment.

I was not able to execute an end-to-end reproduction (requires building a divergent state-checkpoint scenario and running `db-tool replay-on-archive` against an archive/backup), so this finding rests on direct code-path tracing and the maintainers' own acknowledgment in the TODO comment rather than a runtime PoC.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
