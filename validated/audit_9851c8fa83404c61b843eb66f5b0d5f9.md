### Title
L1 handler transactions that error during execution are marked "consumed" while also being rejected, permanently destroying the underlying L1→L2 message and the funds/state it represents - ([File: crates/apollo_batcher/src/block_builder.rs])

### Summary
Starknet's L1→L2 messaging (the analog of Scroll's bridging deposit) works by having the sequencer pull `L1HandlerTransaction`s produced from L1 `sendMessageToL2` events and execute them in a block. The blockifier's `execute_raw` for `L1HandlerTransaction` treats a hard `Err` result (e.g. state/VM errors during `run_execute`) differently from a "soft" revert: on a genuine `Err` from the executor (as opposed to the fee-check triggered revert), the transaction is dropped from the block by the batcher, yet the code that records "consumed" L1 handler hashes unconditionally records the tx as consumed before looking at whether execution succeeded or failed.

### Finding Description
In `collect_execution_results_and_stream_txs` [1](#0-0) , every `InternalConsensusTransaction::L1Handler` is unconditionally inserted into `execution_data.consumed_l1_handler_tx_hashes` *before* the `match result { Ok(...) => ..., Err(...) => ... }` branch is evaluated:

```
if let InternalConsensusTransaction::L1Handler(_) = input_tx {
    let is_new_entry = execution_data.consumed_l1_handler_tx_hashes.insert(tx_hash);
    ...
}
match result {
    Ok(...) => { ... }
    Err(err) => {
        ...
        execution_data.rejected_tx_hashes.insert(tx_hash);
    }
}
``` [2](#0-1) 

This means that if the blockifier's executor returns a hard `Err` for the L1-handler transaction (e.g. a `TransactionExecutorError::StateError`, or `TransactionExecutionError` such as the `InsufficientFee` path in `L1HandlerTransaction::execute_raw`), the transaction hash lands in *both* `consumed_l1_handler_tx_hashes` and `rejected_tx_hashes`. This exact scenario is confirmed by the unit test `failed_l1_handler_transaction_consumed`, which feeds an `Err(TransactionExecutorError::StateError(...))` for one L1 handler tx, and asserts that the resulting `consumed_l1_handler_tx_hashes` set still contains *all* the L1 handler transaction hashes, including the failed one [3](#0-2) .

The consumed/rejected sets are subsequently handed to the L1 provider / transaction manager during block commit; per the documented commit flow, "committed" (consumed) txs transition Pending→Committed while "rejected" txs are unstaged but kept Pending [4](#0-3) . Because the failed transaction is present in the *consumed* set, its underlying L1→L2 message can be marked Committed (i.e., permanently consumed / no longer retryable) even though its state changes were rolled back and it never had any effect on L2 state — the L2-side entry point that was supposed to receive/process the bridged asset or message never executed.

This is the direct structural analog of the reported Scroll issue: a two-phase bridging operation (L1 message send + L2 message consumption) where a failure in the second half (L2 execution) leaves the deposit/effect from the first half (the L1 message, already consumed/finalized) with no path to refund or retry, because the "message consumed" bookkeeping does not distinguish between transactions that succeeded on L2 and transactions that hard-failed on L2.

Separately, `L1HandlerTransaction::execute_raw` [5](#0-4)  also shows there is no mechanism at all to refund the `paid_fee_on_l1` (the fee paid on L1 for L2 execution) when the L1 handler transaction reverts (`fee_check_report` failure path) or hard-errors — the receipt's `fee` is forced to `Fee(0)` on both revert and Err paths [6](#0-5) , meaning any fee overpaid on L1 for that message is simply lost with no on-chain refund path — directly mirroring the "excessive gas is not refunded" complaint in the Scroll report.

### Impact Explanation
If confirmed to persist to the commit stage (I could not fully trace `apply_commit_block`/`commit_txs` inside this iteration budget — see Uncertainty below), an L1→L2 message tied to a hard-erroring `L1HandlerTransaction` would be marked as permanently consumed on the L2 side bookkeeping despite never taking effect, which is a "concrete loss/permanent freezing of funds" scenario for the L1 sender: the deposit/message sent from L1 can never be retried or reprocessed, and there is no compensating mechanism to notify L1 or refund the sender. This matches the required impact bar (permanent freezing/loss of funds reachable from a single L1 message).

### Likelihood Explanation
Reaching an `Err` (not merely a revert) path for `L1HandlerTransaction::execute_raw`/`run_execute` requires conditions such as state errors (e.g., `OutOfRangeContractAddress`, deserialization/DB errors) or the `InsufficientFee` check — these are plausible under adversarial or edge-case L1 message payloads (e.g. malformed contract address, targeting an undeployed/incompatible contract), all of which are fully attacker-controlled since anyone can call `sendMessageToL2` on L1 with arbitrary target/selector/calldata. The unit test `failed_l1_handler_transaction_consumed` demonstrates the exact code path is exercised and behaves this way by design/test-expectation, suggesting it is either intentional (and thus a genuine, confirmed-by-design refund gap) or an untriaged bug.

### Recommendation
Do not unconditionally add L1-handler transaction hashes to `consumed_l1_handler_tx_hashes` before checking the execution result. Only mark an L1 handler transaction hash as consumed when its execution actually succeeded (`Ok`) — including the intentional-revert case if that is by design — but exclude/segregate transactions that hard-errored (`Err`) so they are not committed as "consumed" on the L1 provider/transaction manager side, and instead surface a real mechanism (retry, refund event, or explicit rejection surfaced back toward L1) for the corresponding L1→L2 message. Additionally, consider introducing a fee-refund or event mechanism for `paid_fee_on_l1` when an `L1HandlerTransaction` reverts or hard-fails, analogous to what the Scroll report recommends for cross-chain messaging fee overpayment/failure refunds.

### Proof of Concept
1. Send an L1→L2 message via `sendMessageToL2` targeting a `contract_address` value that is out-of-range or a contract that does not implement the given `entry_point_selector` (causing the resulting `L1HandlerTransaction::run_execute` to return a hard `Err`, e.g. `StateError::OutOfRangeContractAddress`, rather than a controlled revert).
2. Observe (as reproduced by the existing unit test) that the batcher's `collect_execution_results_and_stream_txs` inserts the transaction's hash into `execution_data.consumed_l1_handler_tx_hashes` regardless of the `Err` result [3](#0-2) .
3. The transaction is simultaneously placed into `rejected_tx_hashes`, meaning it produces no state changes / L2 effect, yet is reported to the L1 provider as consumed at commit time.
4. The user who sent the L1 message has no path to reclaim the L1-side fee/deposit associated with that message, and the message can never be reprocessed once marked consumed.

**Uncertainty:** I was not able to fully trace, within this session, the exact behavior of `apply_commit_block`/`commit_txs` in `apollo_l1_events`/`apollo_batcher` when a transaction hash appears in *both* `consumed_l1_handler_tx_hashes` and `rejected_tx_hashes` simultaneously — specifically whether the transaction manager treats "consumed" as authoritative (finalizing/losing the message) or whether "rejected" takes precedence and the message is kept `Pending` for retry (which would negate this finding). This should be verified directly against `crates/apollo_l1_events/src/transaction_manager.rs` and `crates/apollo_batcher/src/batcher.rs`'s `commit_block`-related code before treating this as a confirmed, exploitable vulnerability. I recommend a Devin session with full repository access to trace this precisely.

async fn collect_execution_results_and_stream_txs(
    tx_chunk: &[InternalConsensusTransaction],
    results: Vec<TransactionExecutorResult<TransactionExecutionOutput>>,
    execution_data: &mut BlockTransactionExecutionData,
    pre_confirmed_tx_sender: &mut Option<PreconfirmedTxSender>,
) -> BlockBuilderResult<()> {
    assert!(
        results.len() == tx_chunk.len(),
        "The number of results match the number of transactions."
    );

    for (input_tx, result) in tx_chunk.iter().zip(results) {
        let optional_l1_handler_tx =
            if let InternalConsensusTransaction::L1Handler(l1_handler_tx) = input_tx {
                Some(l1_handler_tx.tx.clone())
            } else {
                None
            };
        let tx_hash = input_tx.tx_hash();

        // Insert the tx_hash into the appropriate collection if it's an L1_Handler transaction.
        if let InternalConsensusTransaction::L1Handler(_) = input_tx {
            let is_new_entry = execution_data.consumed_l1_handler_tx_hashes.insert(tx_hash);
            // Even though this doesn't get past the set insertion, this indicates a major, possibly
            // reorg-producing bug, either in some batcher cache or the l1 provider.
            assert!(is_new_entry, "Duplicate L1 handler transaction hash: {tx_hash}.");
        }

        match result {
            Ok((tx_execution_info, state_maps)) => {
                if let Some(ref revert_error) = tx_execution_info.revert_error {
                    warn!(
                        "Transaction {} is reverted during execution while still accepted. Revert \
                         Error: {}",
                        input_tx.tx_hash(),
                        revert_error,
                    );
                }
                let (tx_index, duplicate_tx_hash) =
                    execution_data.execution_infos_and_signatures.insert_full(
                        tx_hash,
                        (tx_execution_info, input_tx.tx_signature_for_commitment()),
                    );
                assert_eq!(duplicate_tx_hash, None, "Duplicate transaction: {tx_hash}.");

                if let Some(block_number) = proof_facts_block_number(input_tx) {
                    execution_data.proof_facts_block_numbers.insert(tx_hash, block_number);
                }

                // Skip sending the pre confirmed executed transactions, receipts and state diffs
                // during validation flow or if the channel was closed. In validate flow
                // pre_confirmed_tx_sender is None.
                if let Some(pre_confirmed_sender) = pre_confirmed_tx_sender {
                    let tx_receipt = StarknetClientTransactionReceipt::from((
                        tx_hash,
                        TransactionOffsetInBlock(tx_index),
                        // TODO(noamsp): Consider using tx_execution_info and moving the line that
                        // consumes it below this (if it doesn't change functionality).
                        &execution_data.execution_infos_and_signatures[&tx_hash].0,
                        optional_l1_handler_tx,
                    ));

                    let tx_state_diff = StarknetClientStateDiff::from(state_maps).0;

                    let result = pre_confirmed_sender.try_send((
                        input_tx.clone(),
                        tx_receipt,
                        tx_state_diff,
                    ));

                    match result {
                        Ok(_) => {}
                        Err(TrySendError::Closed(_)) => {
                            warn!(
                                "Preconfirmed block writer channel was closed. Skipping to send \
                                 further preconfirmed transactions."
                            );
                            *pre_confirmed_tx_sender = None;
                        }
                        Err(err) => {
                            warn!("Sending data to preconfirmed block writer failed: {:?}", err);
                        }
                    }
                }
            }
            Err(err) => {
                info!(
                    "Transaction {} failed to execute with error: {}.",
                    tx_hash,
                    err.log_compatible_to_string()
                );
                let is_new_entry = execution_data.rejected_tx_hashes.insert(tx_hash);
                assert!(is_new_entry, "Duplicate rejected transaction hash: {tx_hash}.");
            }
        }
    }

    Ok(())
}

impl<U: UpdatableState> ExecutableTransaction<U> for L1HandlerTransaction {
    fn execute_raw(
        &self,
        state: &mut TransactionalState<'_, U>,
        block_context: &BlockContext,
        _concurrency_mode: bool,
    ) -> TransactionExecutionResult<TransactionExecutionInfo> {
        let tx_context = Arc::new(block_context.to_tx_context(self));
        let limit_steps_by_resources = false;
        let l1_handler_bounds =
            block_context.versioned_constants.os_constants.l1_handler_max_amount_bounds;

        let mut remaining_gas = l1_handler_bounds.l2_gas.0;
        let mut context = EntryPointExecutionContext::new_invoke(
            tx_context.clone(),
            limit_steps_by_resources,
            SierraGasRevertTracker::new(GasAmount(remaining_gas)),
        );
        let l1_handler_payload_size = self.payload_size();

        // Create a copy of the state for the execution. It will be rolled back if the execution is
        // reverted or committed upon success.
        let mut execution_state = TransactionalState::create_transactional(state);
        let execution_result =
            self.run_execute(&mut execution_state, &mut context, &mut remaining_gas);
        match execution_result {
            Ok(execute_call_info) => {
                let receipt = TransactionReceipt::from_l1_handler(
                    &tx_context,
                    l1_handler_payload_size,
                    CallInfo::summarize_many(
                        execute_call_info.iter(),
                        &block_context.versioned_constants,
                    ),
                    &execution_state.to_state_diff()?,
                );

                // Enforce resource bounds.
                let fee_check_report = FeeCheckReport::check_all_gas_amounts_within_bounds(
                    &l1_handler_bounds,
                    &receipt.gas,
                );
                match fee_check_report {
                    Ok(()) => {
                        // Post-execution check passed, commit the execution.
                        execution_state.commit();
                        // TODO(Arni): Consider removing this check. It is covered by the starknet
                        // core contract.
                        let paid_fee = self.paid_fee_on_l1;
                        // For now, assert only that any amount of fee was paid.
                        // The error message still indicates the required fee.
                        if paid_fee == Fee(0) {
                            return Err(TransactionExecutionError::TransactionFeeError(Box::new(
                                TransactionFeeError::InsufficientFee {
                                    paid_fee,
                                    actual_fee: receipt.fee,
                                },
                            )));
                        }

                        Ok(l1_handler_tx_execution_info(execute_call_info, receipt, None))
                    }
                    Err(fee_check_error) => {
                        // Post-execution check failed. Revert the execution.
                        execution_state.abort();
                        let receipt = TransactionReceipt::reverted_l1_handler(
                            &tx_context,
                            l1_handler_payload_size,
                        );
                        Ok(l1_handler_tx_execution_info(
                            None,
                            receipt,
                            Some(fee_check_error.into()),
                        ))
                    }
                }
            }
            Err(execution_error) => {
                execution_state.abort();
                let receipt =
                    TransactionReceipt::reverted_l1_handler(&tx_context, l1_handler_payload_size);
                Ok(l1_handler_tx_execution_info(
                    None,
                    receipt,
                    Some(gen_tx_execution_error_trace(&execution_error).into()),
                ))
            }
        }
    }

fn l1_handler_tx_execution_info(
    execute_call_info: Option<CallInfo>,
    mut receipt: TransactionReceipt,
    revert_error: Option<RevertError>,
) -> TransactionExecutionInfo {
    receipt.fee = Fee(0);
    TransactionExecutionInfo {
        validate_call_info: None,
        execute_call_info,
        fee_transfer_call_info: None,
        receipt,
        revert_error,
    }
}
