### Title
`make_signer_set` can produce a non-empty `Some(vec![])` signer field, degrading the Nakamoto block-approval threshold to zero - (File: `stackslib/src/chainstate/stacks/boot/mod.rs`)

### Summary
`StacksChainState::make_signer_set` returns `Some(signer_set)` even when every entry's computed `weight` floors to `0` and is filtered out, leaving `signer_set` empty but still wrapped in `Some(...)` instead of `None`. This is functionally analogous to the reported `sharesToTokenAmount` bug: a denominator/threshold derived from a possibly-empty aggregate is used without checking for the degenerate zero case, and every caller downstream assumes a non-degenerate value.

### Finding Description
`make_signer_set` only returns `None` when the raw `entries` slice is empty at the outset: [1](#0-0) 

But after aggregating by `signing_key`, each entry's weight is `stacked_amt / threshold`, and any entry whose `stacked_amt` is smaller than `threshold` is filtered out via `filter_map`: [2](#0-1) 

If every individual stacker's `amount_stacked` floors to weight `0` against `threshold` (e.g. many small, roughly-equal stackers each below the per-slot threshold), the final `signer_set` is an empty `Vec`, and the function still returns `Some(signer_set)` (i.e. `Some(vec![])`), not `None`.

This `Some(vec![])` propagates into `RewardSet::signers()`, which is `Option<&Vec<NakamotoSignerEntry>>` and only distinguishes "no signers" via `None`: [3](#0-2) 

`RewardSet::total_signing_weight()` only returns an `Err` when `signers()` is `None`; for `Some(vec![])` it happily folds over the empty vector and returns `Ok(0)`: [4](#0-3) 

That `0` total weight then feeds `NakamotoBlockHeader::verify_signer_signatures`, which computes `threshold = compute_voting_weight_threshold(total_weight)`: [5](#0-4) 

and `compute_voting_weight_threshold` computes `ceil(total_weight * 7 / 10)`, which is exactly `0` when `total_weight == 0`: [6](#0-5) 

With `threshold == 0`, the check `if total_weight_signed < threshold` in `verify_signer_signatures` is `0 < 0 == false`, so the function returns `Ok(0)` **without any valid signer signatures at all**. The equality this breaks is: "a Nakamoto block is only accepted with ≥70% of signer weight approving it." When the reward set degenerates to `Some(vec![])`, that invariant becomes "0% of 0 total weight ≥ 0", trivially true.

Note the fix for the newer PoX-5 path (`pox_5_make_signer_set`) explicitly documents this exact degenerate mode and adds a largest-remainder ("Hare") allocation specifically "to avoid degenerate modes of the floor-and-drop scheme... the entire signer set could be dropped": [7](#0-6) 

This confirms the legacy `make_signer_set` (used for pre-PoX-5 reward cycles) was never hardened against the same scenario — it simply returns the possibly-empty `Some(vec![])`.

### Impact Explanation
If a reward cycle's signer set degenerates in this way, `verify_signer_signatures` will accept a Nakamoto block carrying zero signer signatures as fully valid (`Ok(0)` weight signed against a `0` threshold). This lets a miner unilaterally produce and canonicalize blocks for that tenure without any signer participation — a signature-verification equality that every honest node computes identically, but which is trivially satisfiable, i.e. an "invalid" block (one that should require signer consensus) is accepted network-wide. This falls in the Critical/High boundary described in the rules ("an invalid block accepted... network-wide").

### Likelihood Explanation
Triggering this requires the underlying stacking distribution for a reward cycle to make every stacker's `stacked_amt / threshold` floor to `0` — i.e., no single stacker (after aggregation by signing key) reaches the per-slot threshold. This is a property of the PoX-2/3/4 stacking economics/threshold selection (`get_reward_threshold_and_participation`), which I was not able to fully trace before running out of tool budget, so I cannot conclusively confirm whether the threshold-selection logic elsewhere already guarantees at least one non-zero-weight entry. The explicit degenerate-mode comment added for the PoX-5 replacement strongly suggests this was a real, previously-unguarded gap in the legacy path.

### Recommendation
In `make_signer_set`, after filtering, explicitly check if the resulting `signer_set` is empty and return `None` in that case (mirroring the early `entries.is_empty()` check), so that `RewardSet::signers()` faithfully reports "no signers" rather than a fabricated `Some(vec![])`. Additionally, `total_signing_weight()` and `verify_signer_signatures` should treat a `total_weight == 0` (or an empty `signers` vec) as an error condition rather than a `threshold == 0` pass-through, consistent with the recommended fix in the referenced report ("return an error/None instead of silently succeeding on the degenerate zero case").

### Proof of Concept
1. Construct `entries: &[RawRewardSetEntry]` such that after aggregation each unique `signing_key`'s `amount_stacked < threshold` (e.g., many small stackers just under the per-slot cutoff).
2. Call `make_signer_set(threshold, entries)`; observe it returns `Some(vec![])` rather than `None`.
3. Build a `RewardSet` with `signers = Some(vec![])`; call `total_signing_weight()` — observe `Ok(0)`.
4. Feed this `RewardSet` into `NakamotoBlockHeader::verify_signer_signatures` with an empty `signer_signature` vector on the candidate block — observe it returns `Ok(0)` (success) instead of an error, because `compute_voting_weight_threshold(0) == 0` and `0 < 0` is false.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

        // Allocate `reward_slots` weight across signers in proportion to stake using the
        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
        }
