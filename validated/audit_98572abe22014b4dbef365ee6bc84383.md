Confirmed: `GraphqlClient` builds the Admin API client's `storeDomain` directly from `session.shop` [1](#0-0) , while for custom-store apps (`AppDistribution.ShopifyAdmin`) `session.shop` is populated from an unauthenticated `shop` URL query parameter rather than from a verified session token or signed cookie.

### Title
Unauthenticated `shop` query parameter used to select Admin API destination for merchant custom apps, enabling access-token disclosure to attacker-controlled domains - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts)

### Summary
For apps using the `AppDistribution.ShopifyAdmin` (custom/merchant-installed) authentication path, `getSessionTokenContext` reads the `shop` value directly from the request URL's `shop` query parameter with no signature, HMAC, or session-token cross-check, unlike the embedded-app path where `shop` is derived from a validated JWT's `dest` claim.

### Finding Description
In `getSessionTokenContext`, when `config.distribution === AppDistribution.ShopifyAdmin`, the code takes `shop` straight from `url.searchParams.get('shop')` with no cryptographic validation: [2](#0-1)  This is exactly the same class of bug as the reported `repay_stable_from_liquidation` issue: a caller-supplied identifier (`minter` in the report, `shop` here) is trusted and used directly for a privileged operation instead of being derived from an authenticated source.

That untrusted `shop` value flows into `MerchantCustomAuth.authenticate`, which builds the session as `this.api.session.customAppSession(shop)` [3](#0-2) . `customAppSession` only sanitizes the shop string format but performs no ownership check: [4](#0-3) .

That `Session.shop` is then used, together with the app's single static `config.adminApiAccessToken`, to configure the underlying Admin API client's `storeDomain`: [5](#0-4) . Because custom/merchant apps use one fixed `adminApiAccessToken` for their single installed shop (this is precisely why `AppDistribution.ShopifyAdmin` skips OAuth — see `respondToOAuthRequests`), the request/response destination is normally always the real shop domain. Allowing the caller to substitute an arbitrary hostname into `storeDomain` means the library will send the app's static Admin API access token to a domain the requester controls.

### Impact Explanation
If a route built with `authenticate.admin` for a merchant-custom app forwards `admin.graphql(...)` calls using this session, an anonymous or minimally-privileged requester who supplies `?shop=attacker.example.com` (or another value the sanitizer accepts) can cause the library to issue an authenticated Admin GraphQL/REST request whose target host is attacker-controlled, exfiltrating the app's static `adminApiAccessToken` via the `X-Shopify-Access-Token` header (or equivalent) to that attacker endpoint — a secret-disclosure / SSRF outcome analogous to the "no validation of caller-supplied identity" pattern in the reported bug.

### Likelihood Explanation
Likelihood depends on whether app code that uses this authentication strategy passes the `shop` value through to network operations without additional own validation, and whether `sanitizeShop` rejects non-`myshopify.com`-style hosts (this could not be fully confirmed from the available index — `shop-validator.ts` contents were not retrieved in this session). Given custom/merchant apps are typically single-tenant with a fixed shop, most app implementers may not notice or guard against a spoofed `shop` param, since the built-in path never asks for one to be signed in this flow.

### Recommendation
For `AppDistribution.ShopifyAdmin`, derive `shop` from `config.hostName`/the app's configured shop instead of trusting the request query parameter, or strictly validate that the `shop` query parameter equals the shop the app was configured for before constructing a session or Admin client. This mirrors the fix pattern in the original report: authenticate/validate the actor-supplied identity against a trusted source before using it in a privileged operation.

### Proof of Concept
1. Deploy an app configured with `distribution: AppDistribution.ShopifyAdmin` and a static `adminApiAccessToken`.
2. Send a request to an authenticated admin route with `?shop=attacker-controlled.example.com` instead of the real installed shop domain.
3. `getSessionTokenContext` returns `{shop: "attacker-controlled.example.com", ...}` unchecked [6](#0-5) .
4. `MerchantCustomAuth.authenticate` builds `customAppSession("attacker-controlled.example.com")`.
5. Any subsequent `admin.graphql()` call uses this session, causing `GraphqlClient` to target `storeDomain: "attacker-controlled.example.com"` while attaching the app's real `adminApiAccessToken`, exfiltrating the secret to the attacker's server.

Note: I could not verify within the available index whether `sanitizeShop` (in `packages/apps/shopify-api/lib/utils/shop-validator.ts`) restricts values to `*.myshopify.com` domains, which would materially affect exploitability; this file's contents were not retrieved during this session, so confirm that constraint before treating this as fully exploitable.
