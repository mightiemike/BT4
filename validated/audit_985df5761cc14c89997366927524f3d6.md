### Title
`deposit()` mints zero shares without reverting, allowing depositors to pay underlying tokens and receive nothing — (File: `mainnet/contracts/vault/v0-vault-stx.clar` and all sibling vaults)

### Summary
Every Zest v2 vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts) implements a `deposit`/`redeem` pair. `redeem` explicitly guards against a zero-value payout with `ERR-OUTPUT-ZERO`, but `deposit` has no equivalent guard on the shares it mints. This is the same root cause as the FeeAuction report: a value-transfer path takes payment from the caller and produces an output (assets for FeeAuction, shares for Zest) without verifying that output is non-zero, letting the transaction "succeed" while the payer receives nothing.

### Finding Description
`deposit` computes `inkind` (shares to mint) via `convert-to-shares-preview amount` and only asserts:
- `(> amount u0)` — the *input* underlying amount is non-zero,
- `(>= inkind min-out)` — a slippage floor that defaults to `u0` unless the caller explicitly sets it,
- cap/pause/reentrancy checks. [1](#0-0) 

It never checks `(> inkind u0)`. Compare this to `redeem` in the same contract, which explicitly performs `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` before burning shares/sending underlying: [2](#0-1) 

Because `deposit` skips this check, if `convert-to-shares-preview` rounds down to `0` for a given `amount` (which happens whenever the vault's share price has appreciated enough that `amount * total_shares / total_assets` truncates to zero — a routine, non-adversarial state reached purely by interest accrual over time), the function still proceeds to:
1. Pull the full `amount` of underlying tokens from the caller via `receive-underlying`,
2. Mint `0` shares via `ft-mint? zft 0 recipient` (a no-op that does not error),
3. Increase `assets` by `amount`, silently socializing the deposited principal into the vault for existing shareholders,
4. Return `(ok 0)` as a success.

This mirrors the FeeAuction bug class precisely: a caller pays and the contract does not revert even though the caller receives zero output — except here it requires no front-runner, no second transaction, and no other user; it is a self-contained, single-transaction consequence of an unguarded rounding-to-zero condition on the mint side, directly analogous to the unguarded `_transferOutAssets` balance check in the report.

### Impact Explanation
A user calling `deposit` with `min-out` left at (or supplied as) `0` — the natural default for a "best effort" deposit — can have their entire deposited principal absorbed by the vault with zero shares minted in return. This is a permanent loss of the user's principal (their claim on it, `zTokens`, was never created), constituting direct theft/permanent freezing of user funds at rest. This is amplified by every call site that invokes `deposit` on behalf of users, e.g. `supply-collateral-add` in the market contract, where the deposited underlying is expected to be converted into zTokens and then pledged as collateral in the same transaction.

### Likelihood Explanation
This does not require any attacker action, malicious timing, or governance/oracle manipulation — it can occur to any legitimate depositor who submits a small `amount` relative to the vault's share price (which naturally grows over the vault's lifetime as interest accrues), or who deposits an amount whose share conversion rounds to zero due to the specific `total_assets`/`total_supply` ratio at call time. The likelihood scales with vault age/share-price appreciation and with the minimum deposit size allowed by the UI/market wrapper.

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` to `deposit` in every vault contract, mirroring the existing check in `redeem`, so that a deposit reverts rather than silently minting zero shares while taking full payment. Additionally, consider enforcing a non-zero `min-out` default at the market-contract call sites (e.g. `supply-collateral-add`) so wrapped multi-step deposit-then-collateralize flows cannot silently proceed with a worthless mint.

### Proof of Concept
1. Let the vault's `total_assets` grow relative to `total_supply` (via ordinary interest accrual over time) such that `convert-to-shares-preview(amount) = amount * total_supply / total_assets` rounds down to `0` for some small `amount > 0`.
2. Caller invokes `deposit(amount, 0, recipient)` (using the default `min-out = 0`).
3. Checks pass: `amount > 0` ✓, `inkind (0) >= min-out (0)` ✓, cap check ✓.
4. `receive-underlying amount account` transfers `amount` of underlying tokens from the caller into the vault.
5. `ft-mint? zft 0 recipient` mints zero zTokens — no error is raised.
6. `assets` is incremented by `amount`, and the function returns `(ok 0)`.
7. The caller has paid `amount` underlying tokens and received `0` zTokens — permanent loss of principal, exactly analogous to the FeeAuction `buy` losing-bidder scenario but achievable in a single transaction with no other participant.

Note: I could not fully trace the exact rounding formula of `convert-to-shares-preview`/`convert-to-assets-preview` within the available iterations (the file content matched by name but full body wasn't retrieved before the tool budget ran out), so the precise numeric threshold at which `inkind` rounds to zero is not confirmed from source, though the structural absence of the `ERR-OUTPUT-ZERO` guard in `deposit` (versus its presence in `redeem`) is directly confirmed across all six vault contracts in both `mainnet/contracts/vault/` and `local-testing/contracts/vault/`.
