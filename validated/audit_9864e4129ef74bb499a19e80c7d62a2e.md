### Title
Unbounded growth of `zero_lamport_accounts_to_purge_after_full_snapshot` enables disproportionate CPU/memory cost on the validator - (File: `accounts-db/src/accounts_db.rs`)

### Summary
An unprivileged user can force the validator's `AccountsDb` to accumulate an unbounded number of entries in the `zero_lamport_accounts_to_purge_after_full_snapshot` set by repeatedly creating and zeroing accounts between two full snapshots. The set is only drained by a single, serial, un-chunked `retain()` pass that runs once when the next full snapshot advances, so the attacker-controlled growth is paid for, all at once, by the validator's background cleaning thread — the same "grow an array via cheap repeated user actions, then force a single expensive/atomic settlement pass" pattern described in the external report's `proceeds` array bug.

### Finding Description
`AccountsDb` keeps a `DashSet<(Slot, Pubkey)>` field, `zero_lamport_accounts_to_purge_after_full_snapshot`, used to track zero-lamport accounts that cannot yet be purged by `clean_accounts` because they are newer than the latest full snapshot (needed so an incremental snapshot can still propagate the deletion): [1](#0-0) 

Every time `clean_accounts` runs and finds a zero-lamport candidate whose slot is above the latest full snapshot slot, it inserts a new `(slot, pubkey)` tuple into this set instead of purging it: [2](#0-1) 

Because the key is `(slot, pubkey)` rather than just `pubkey`, an attacker who repeatedly creates an account, funds it, and zeroes it out (e.g. `CreateAccount` + `transfer` + `CloseAccount`/withdraw-to-zero, cheaply repeatable using system-owned accounts) generates a fresh, distinct tuple on every occurrence. Each such event is unprivileged, inexpensive (only transaction fees; rent-exempt lamports are refunded), and adds a permanent entry to the set that persists for the entire interval until the next full snapshot.

The set is only drained in one place, guarded by a boolean flag set when the full snapshot slot advances: [3](#0-2) 

This `retain()` call is a single serial pass over the whole `DashSet` (unlike the main clean scan, which is chunked and parallelized across index bins via `candidates.par_iter()`), and it runs synchronously as part of `construct_candidate_clean_keys`, called from `clean_accounts`: [4](#0-3) 

With a default full-snapshot interval on the order of tens of thousands of slots, an attacker submitting many cheap create/zero cycles per slot for that entire window can grow this set to a very large size before it is ever drained. When the full snapshot finally advances, the validator's background cleaning thread must process the entire accumulated set in one shot, and every surviving entry is re-inserted as a clean candidate to be scanned/reclaimed — directly analogous to the `proceeds` array in the report, which was appended to cheaply but paid off/traversed all at once, imposing an unbounded cost on whichever party had to settle it.

### Impact Explanation
This does not corrupt consensus-critical state (hashes/capitalization stay correct), but it lets an unprivileged user impose disproportionate CPU time and heap memory on validator nodes: unbounded growth of an in-memory `DashSet` for the duration between full snapshots, followed by a large serial `retain()` pass and a correspondingly large batch of clean/reclaim work the moment the snapshot boundary is crossed. This can lengthen `clean_accounts` runs, delay the accounts-background service, and increase memory pressure — a disproportionate-cost issue matching the Validate acceptance criteria ("disproportionate storage and CPU cost").

### Likelihood Explanation
The actions required (creating and zeroing accounts) are ordinary, unprivileged operations available to any fee-paying user, and the tuple insertion has no cap or backpressure. The only natural throttle is total transaction throughput and fees over the snapshot interval, which for a well-funded attacker across a multi-hour interval can still accumulate a very large number of entries.

### Recommendation
Bound or throttle `zero_lamport_accounts_to_purge_after_full_snapshot`, e.g., by tracking only per-pubkey (not per-(slot,pubkey)) state, capping its size with eager partial draining, or parallelizing/chunking the drain pass so it can't become a single unbounded serial operation. Consider also processing the drain incrementally across multiple clean cycles rather than all-at-once when the full snapshot boundary advances.

### Proof of Concept
1. Set `latest_full_snapshot_slot` to slot `S0`.
2. In a loop across many subsequent slots, have an unprivileged payer: create a new (or reuse the same) account, give it lamports, then zero its lamports out in that slot (standard system-program operations), and root the slot so `clean_accounts` runs.
3. Each iteration adds a new `(slot, pubkey)` entry to `zero_lamport_accounts_to_purge_after_full_snapshot` via `filter_zero_lamport_clean_for_incremental_snapshots` (`accounts-db/src/accounts_db.rs:2367`), since the slot differs every time and the account is newer than the last full snapshot.
4. Repeat for the full duration of a snapshot interval to accumulate a large number of entries.
5. Once the next full snapshot slot advances, observe that `clean_accounts` performs a single large serial `retain()` over the whole set (`accounts-db/src/accounts_db.rs:1693-1702`) and re-inserts every surviving entry as a new clean candidate, showing the cost is proportional to the attacker's cumulative cheap actions rather than being bounded independently of them.
