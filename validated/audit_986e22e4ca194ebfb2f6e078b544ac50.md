### Title
Fee-transfer return value discarded in `charge_fee` allows fee to be treated as paid without validating ERC20 `transfer` success flag - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo)

### Summary
In the Starknet OS Cairo implementation of `charge_fee`, the fee-token `transfer` entry point is invoked via `non_reverting_select_execute_entry_point_func`, but the function's return value (`retdata_size`, `retdata`) — which carries the ERC20 `success: felt` boolean — is completely discarded. This mirrors the reported pattern of an external call's return value not being stored/checked (`IERC20.approve` case), applied here to the sequencer's own fee-charging logic.

### Finding Description
`charge_fee` builds a `TransferCallData` for the fee token's `transfer` entry point and calls: [1](#0-0) 

```
let remaining_gas = DEFAULT_INITIAL_GAS_COST;
non_reverting_select_execute_entry_point_func{remaining_gas=remaining_gas}(
    block_context=block_context, execution_context=&execution_context
);
return ();
```

`non_reverting_select_execute_entry_point_func` returns `(retdata_size, retdata, is_deprecated)`: [2](#0-1) 

The only property enforced by this helper is `assert is_reverted = 0` (the call did not revert). It never inspects `retdata[0]`, which for an ERC20 `transfer` call is the `success: felt` boolean, as seen in the ERC20 ABI and Cairo0 reference implementation: [3](#0-2)  and the ABI definition returning a `success` felt: [4](#0-3) .

By contrast, the analogous `run_validate` function *does* capture and validate its retdata, asserting `retdata[0] = VALIDATED`: [5](#0-4) 

This asymmetry means `charge_fee` only guards against a reverting fee-token call, not against a fee-token contract that returns without reverting but with `success = FALSE` (e.g., a class declared/used as the fee token whose `transfer` implementation legitimately returns `0` on certain paths instead of reverting, or a corner-case/legacy ERC20 fee-token class where a non-reverting failure path exists). In such a case, the OS would treat the fee as charged and proceed to finalize the block, while the fee token's internal accounting may not have actually decremented the sender's balance / incremented the sequencer's balance as expected.

### Impact Explanation
If a fee-token class's `transfer` can return `success = 0` without reverting on any invocation path, the sequencer (via the Starknet OS re-execution / block-building charge_fee logic) would incorrectly consider the fee paid. This directly risks: (a) mismatched fee accounting between the blockifier's Rust-side `execute_fee_transfer`/CallInfo handling and the OS's Cairo re-execution, which could cause OS re-execution divergence (a "honest-node divergence" or wrong committed state) if the two code paths disagree on whether the fee-transfer's return value matters, and (b) unauthorized state where a transaction is finalized as fee-paid despite the underlying token transfer not truly succeeding logically, undermining the guarantee that all committed transactions have paid their required fee. This satisfies the required impact classes of wrong committed root/state divergence or unauthorized accounting of funds.

### Likelihood Explanation
Reachability requires only that the network's/chain's designated fee token contract (settable via chain config to any class, since `fee_token_address` and its class are read from state at `crates/apollo_starknet_os_program/.../transaction_impls.cairo:138`) implement a `transfer` that can return `0` without reverting on some input — this is a legitimate ERC20 pattern (return false instead of revert) even though the bundled reference `ERC20.cairo` in this repo always reverts via `assert_not_zero` on insufficient balance rather than returning false. Because the OS enforces no assertion on the `success` flag, any transaction sent by a normal unprivileged account against a fee-token implementing this common alternate ERC20 convention would trigger the gap. This is reachable by a plain unprivileged transaction sender without needing special privileges once the fee token in use follows the "return false" ERC20 convention.

### Recommendation
In `charge_fee` (crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo), capture the `retdata_size`/`retdata` returned by `non_reverting_select_execute_entry_point_func` and assert that `retdata_size == 1 && retdata[0] == TRUE` (mirroring the pattern already used in `run_validate` for the `VALIDATED` magic value), ensuring the ERC20 fee transfer's `success` boolean is explicitly checked rather than discarded.

### Proof of Concept
1. Deploy/select a fee-token class whose `transfer(recipient, amount)` implementation returns `(success=0)` when, e.g., `amount` exceeds a per-call cap or some other non-reverting business rule, instead of reverting via `assert`.
2. Submit a normal invoke transaction where `max_fee`/resource bounds trigger `charge_fee` to call this fee token's `transfer`.
3. Because `non_reverting_select_execute_entry_point_func` only asserts `is_reverted = 0` and never checks `retdata[0]`, the OS proceeds as if the fee was successfully charged (`charge_fee` returns normally), even though the token's internal state indicates the transfer failed logically.
4. This can produce a state/output divergence between what the fee-token's storage actually reflects and what the OS/blockifier assume was charged, risking incorrect committed state or root computation for that block.

Note: I was not able to fully confirm within the available time whether the Rust-side `execute_fee_transfer` in `crates/blockifier/src/transaction/account_transaction.rs` (lines 550–591) similarly ignores the `success` return value of the `CallInfo`, which would corroborate whether this gap is consistent (and thus non-divergent) or inconsistent (and thus a genuine cross-path divergence) between the blockifier and the OS. Confirming that would require deeper review of `CallInfo` post-processing for the fee-transfer call in the Rust execution path.
