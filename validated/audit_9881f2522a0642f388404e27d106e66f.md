## Finding

### Title
Wallet Contract's testnet/localnet WASM binaries are built with the mainnet-only `ADDRESS_REGISTRAR_ACCOUNT_ID` hardcoded value, breaking (or allowing hijack of) the anti-fraud relayer check - (File: `runtime/near-wallet-contract/build.rs`, `runtime/near-wallet-contract/implementation/wallet-contract/src/ADDRESS_REGISTRAR_ACCOUNT_ID`)

### Summary
The Wallet Contract's build process parameterizes the EVM `CHAIN_ID` per network (mainnet/testnet/localnet) but never parameterizes the `ADDRESS_REGISTRAR_ACCOUNT_ID`, so the same mainnet address `address-map.near` is baked into every network's compiled WASM. On testnet (and localnet) this account either does not exist or, because account names are permissionlessly claimable, can be registered and controlled by an attacker, defeating the on-chain relayer-fraud check that protects users' funds when transferring to eth-implicit "shadow" accounts.

### Finding Description
The build script builds three separate WASM artifacts for mainnet, testnet, and localnet, but only swaps the `CHAIN_ID` file between builds: [1](#0-0) 

The `ADDRESS_REGISTRAR_ACCOUNT_ID` file, however, is never touched by `build.rs` and is compiled unconditionally into every network's binary via `std::include_str!`: [2](#0-1) [3](#0-2) 

This constant is used at runtime to decide which contract to call for the anti-fraud "address check" that prevents a faulty/malicious relayer from redirecting an EOA base-token transfer meant for a *named* account (previously registered in the registrar) toward a colliding eth-implicit "shadow" account: [4](#0-3) 

The registrar's `lookup` result is trusted completely: if it returns `None`, the transfer to the eth-implicit target proceeds and the nonce is consumed (finalizing the transfer); if it returns `Some`, the relayer is banned and the transfer is rejected: [5](#0-4) 

Because the mainnet-specific account id `address-map.near` is compiled into the testnet/localnet binaries as well (rather than being parameterized like `CHAIN_ID`), on testnet this account either (a) does not exist, causing the cross-contract call to fail and the whole class of address-checked transactions to be unusable, or (b) can be freely registered by an attacker (NEAR account names are permissionless to claim), letting the attacker deploy a fake "always return `None`" registrar. This test explicitly demonstrates the intended protection — registering a target account's address with the registrar is supposed to force a lazy/faulty relayer to be banned instead of letting the transfer through to the wrong (eth-implicit) target: [6](#0-5) 

If an attacker on testnet controls the registrar account referenced by the hardcoded string, they can make `lookup` always return `None`, permanently disabling this protection network-wide for every deployed eth-implicit wallet contract on that network.

### Impact Explanation
With the fraud check neutralized, a relayer (which any unprivileged party can act as when relaying a signed Ethereum-style transaction through `rlp_execute`) can route a transfer that the user intended for a legitimately registered named account into an "orphan" eth-implicit account instead. Since that eth-implicit account's address is merely a coincidental keccak256 preimage collision with the registered account, in the vast majority of cases nobody holds the matching secp256k1 private key, so the transferred funds become permanently inaccessible — a fund loss/freezing impact. In the adversarial case where the attacker deliberately grinds an address collision, the same broken check enables outright redirection of the transfer to an account the attacker does control, i.e., theft of funds. Either way, the ETH-implicit Wallet Contract mechanism (a core, protocol-integrated account model, see `runtime/near-wallet-contract/src/lib.rs`) is compromised on any network other than mainnet.

### Likelihood Explanation
The bug is deterministic and always present as shipped, since `build.rs` demonstrably never updates `ADDRESS_REGISTRAR_ACCOUNT_ID` per network while it does update `CHAIN_ID`: [7](#0-6) 
Exploitation on testnet requires only registering the plain-text account name embedded in the file (`address-map.near`), which is a normal, permissionless NEAR account creation — no privileged access, no validator collusion, and no reliance on any malicious peer/node behavior.

### Recommendation
Parameterize `ADDRESS_REGISTRAR_ACCOUNT_ID` per network exactly as `CHAIN_ID` is parameterized in `build.rs`, writing the correct registrar account id (mainnet registrar for the mainnet build, the actual deployed testnet registrar for the testnet build, and the test/localnet registrar for the localnet build) before invoking `docker_build`, and restoring the file afterward. Add a build/test-time assertion that the registrar account referenced in each network's compiled WASM matches the intended, officially-deployed registrar for that network before shipping the artifact.

### Proof of Concept
1. Run `build.rs`: observe that `chain_id_path` (`.../wallet-contract/src/CHAIN_ID`) is rewritten for each of `MAINNET_CHAIN_ID`, `TESTNET_CHAIN_ID`, `LOCALNET_CHAIN_ID`, but `address_registrar_account_id_path`/`ADDRESS_REGISTRAR_ACCOUNT_ID` is never referenced or rewritten anywhere in `build.rs`.
2. Inspect the compiled `res/wallet_contract_testnet.wasm` / decompile or trace `ADDRESS_REGISTRAR_ACCOUNT_ID` usage in `inner_rlp_execute`; confirm it always resolves to `address-map.near` regardless of target network.
3. On testnet, create the account `address-map.near` (permissionless) and deploy a contract exposing `lookup(address) -> Option<AccountId>` that always returns `null`.
4. Register a NEP-141 (or any) account's address with the *real* mainnet registrar semantics is irrelevant here — since the testnet wallet contract only ever talks to the attacker-controlled `address-map.near`, any address-checked EOA base token transfer through any eth-implicit wallet on testnet will now always be treated as "not registered," letting a colluding relayer redirect the transfer to an eth-implicit shadow account instead of the intended named account, as shown by contrast with the intended-behavior test `test_relayer_invalid_address_target` (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs:175-240`), which expects the relayer to be banned and the transfer rejected when the address IS properly registered — the neutralized/attacker-controlled registrar defeats exactly this protection.

// looked up the named account corresponding to `tx.to`. In this case the relayer
// should be banned for being lazy.
#[tokio::test]
async fn test_relayer_invalid_address_target() -> anyhow::Result<()> {
    let TestContext {
        worker,
        mut wallet_contract,
        wallet_sk,
        wallet_address,
        address_registrar,
        ..
    } = TestContext::new().await?;

    // Deploy a NEP-141 contract and register its address.
    // Registering should prevent a lazy relayer from setting the target incorrectly.
    let token_contract = nep141::Nep141::deploy(&worker).await?;
    let register_output: Option<String> = address_registrar
        .call("register")
        .args_json(serde_json::json!({
            "account_id": token_contract.contract.id().as_str()
        }))
        .max_gas()
        .deposit(NearToken::from_millinear(1))
        .transact()
        .await?
        .json()?;
    let token_address: [u8; 20] =
        hex::decode(register_output.as_ref().unwrap().strip_prefix("0x").unwrap())?
            .try_into()
            .unwrap();
    assert_eq!(
        token_address,
        account_id_to_address(&token_contract.contract.id().as_str().parse().unwrap(),).0
    );

    // Set up a relayer with control to send transactions via the Wallet Contract account.
    let relayer_pk = wallet_contract.register_relayer(&worker).await?;

    // The user submits a transaction to interact with the NEP-141 contract.
    let transaction = aurora_engine_transactions::eip_2930::Transaction2930 {
        nonce: 0.into(),
        gas_price: 0.into(),
        gas_limit: 0.into(),
        to: Some(Address::from_array(token_address)),
        value: Wei::zero(),
        data: [
            crate::eth_emulation::ERC20_BALANCE_OF_SELECTOR.to_vec(),
            ethabi::encode(&[ethabi::Token::Address(wallet_address)]),
        ]
        .concat(),
        chain_id: CHAIN_ID,
        access_list: Vec::new(),
    };
    let signed_transaction = crypto::sign_transaction(transaction, &wallet_sk);

    // Relayer fails to set `target` correctly
    let result =
        wallet_contract.rlp_execute(register_output.unwrap().as_str(), &signed_transaction).await?;

    assert!(!result.success);
    assert_eq!(result.error.as_deref(), Some("Error: faulty relayer"));

    assert_revoked_key(&wallet_contract.inner, &relayer_pk).await;

    Ok(())
}
