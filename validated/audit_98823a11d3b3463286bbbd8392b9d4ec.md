### Title
Unbounded `AssetIssueStore`/`ExchangeStore`/`ProposalStore` growth with no pruning, exposed via unpaginated `getAssetIssueList()` / `getExchangeList()` / `getProposalList()` APIs - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
Mirroring the VTVLVesting `vestingRecipients` finding — an array that any unprivileged user can append to, with no removal mechanism, eventually consumed by an unbounded getter — java-tron has the same pattern for `AssetIssueStore`, `ExchangeStore`, and `ProposalStore`: any account can permanently add entries to these stores, nothing ever deletes an entry, and `Wallet.getAssetIssueList()` / `Wallet.getExchangeList()` / `Wallet.getProposalList()` build a full-list response by iterating every stored entry with no limit.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` and `ExchangeStore.getAllExchanges()` iterate the entire underlying LevelDB/RocksDB column without any bound [1](#0-0) [2](#0-1) . `Wallet.getAssetIssueList()` calls the unbounded `getAllAssetIssues()` directly, wrapping every asset in the response and running `BandwidthProcessor.updateUsage` for each one [3](#0-2) . `Wallet.getExchangeList()` and `Wallet.getProposalList()` similarly call `getAllExchanges()`/`getAllProposals()` with no limit [4](#0-3) [5](#0-4) . These are wired up to public, unauthenticated HTTP/gRPC endpoints — e.g. `GetAssetIssueListServlet.doGet()` calls `wallet.getAssetIssueList()` directly and serializes the full result [6](#0-5) .

Critically, once an asset issue, exchange, or proposal is created, there is no code path that ever deletes it from `AssetIssueStore`/`ExchangeStore`/`ProposalStore` — unlike the analogous `DelegatedResourceAccountIndexStore`, which does properly remove entries from `toAccountsList`/`fromAccountsList` when a delegation balance reaches zero [7](#0-6) , no equivalent pruning exists for asset issues or exchanges. Any account can pay the asset-issuance fee and call `CreateAssetIssueContract` (via `AssetIssueActuator`) repeatedly with different names to grow `AssetIssueStore` indefinitely; likewise any account can create exchange pairs. This is functionally identical to the reported bug class: an ever-growing, un-prunable collection that a public getter iterates in full.

Note that a bounded, paginated alternative already exists for assets and exchanges — `Wallet.getAssetIssueList(long offset, long limit)` and `Wallet.getPaginatedExchangeList(long offset, long limit)` [8](#0-7) [9](#0-8)  — but the unbounded `getAssetIssueList()`, `getExchangeList()`, and `getProposalList()` remain reachable and are still the endpoints wired into `GetAssetIssueListServlet`, `ListAssetIssue` gRPC, etc.

### Impact Explanation
As the store grows over the life of the chain (assets/exchanges/proposals are created continuously and never pruned), calls to the unbounded list endpoints require the full-node to materialize, process (including `BandwidthProcessor.updateUsage` per asset), and serialize an ever-larger response. This is a node-level resource-exhaustion / degraded-availability issue on public API-serving full nodes, consistent with the C4 report's own characterization (severity Medium, "impact hard to determine," judged as valid but non-critical because the affected function was largely used for off-chain/read purposes). It does not directly corrupt on-chain state or accounting.

### Likelihood Explanation
Likelihood is credible but not high: creating assets/exchanges/proposals costs a fee and takes real transactions over time, so the growth is slow compared to a pure storage-write DoS; and mitigations (rate limiting via `RateLimiterServlet`, and the existence of paginated variants) reduce the immediate risk. Still, since java-tron has been running in production for years and asset issuance is unrestricted to any funded unprivileged account, the underlying store size is already large and will keep growing without bound.

### Recommendation
Deprecate/remove or explicitly rate-limit the unbounded `getAssetIssueList()`, `getExchangeList()`, and `getProposalList()` code paths and endpoints in favor of the already-existing paginated equivalents (`getAssetIssueList(offset, limit)`, `getPaginatedExchangeList`, and a paginated proposal list), so that no HTTP/gRPC endpoint can force a full node to enumerate an ever-growing, non-prunable store in a single response.

### Proof of Concept
1. Repeatedly submit `CreateAssetIssueContract` transactions (paying the required fee) from many different funded accounts, each with a unique asset name, to grow `AssetIssueStore` without limit — there is no code path that ever removes an entry from `AssetIssueStore`.
2. Call the public `GetAssetIssueListServlet` HTTP endpoint (`wallet/getassetissuelist`) or the gRPC `ListAssetIssue` call, which invoke `Wallet.getAssetIssueList()` [3](#0-2) , causing the node to iterate and serialize the entire, ever-growing `AssetIssueStore` in one response.
3. As the number of assets grows over time, response latency, memory, and bandwidth cost for this endpoint increase without bound, degrading node availability for other API consumers — the same class of impact identified in the referenced report for `allVestingRecipients()`.

  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestExchangeNum ? latestExchangeNum : end;

    ExchangeList.Builder builder = ExchangeList.newBuilder();
    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ExchangeCapsule::calculateDbKey).map(key -> {
      try {
        return getExchangeStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getExchangeStore(),
            chainBaseManager.getExchangeV2Store()).get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(exchangeCapsule -> builder
            .addExchanges(exchangeCapsule.getInstance()));
    return builder.build();

  }
