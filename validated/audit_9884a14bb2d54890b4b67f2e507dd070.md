This is the key finding: `AttachRescueOutboundFromReceipt` in `x/uexecutor/keeper/create_outbound.go` builds a `RESCUE_FUNDS` outbound for an *arbitrary attacker-supplied PRC20 token* without checking it matches the asset that was actually locked/failed for that `UniversalTx`.

### Title
Rescue-funds path allows PRC20 selection that is never bound to the original UTX's locked asset - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`AttachRescueOutboundFromReceipt` decodes a `RescueFundsOnSourceChain` event and, after checking only the `UniversalTxId` and its eligibility status (CEA-deposit-failed or inbound-revert-reverted), resolves `event.PRC20` (the token an unprivileged user chose when calling `rescueFundsOnSourceChain` on `UniversalGatewayPC`) into a token config via `GetTokenConfigByPRC20(ctx, originalUtx.InboundTx.SourceChain, event.PRC20)` [1](#0-0) . There is no check that `event.PRC20` equals the PRC20 corresponding to `originalUtx.InboundTx.AssetAddr` (the token that was actually deposited/locked for that UTX). This is the same trust pattern as the reported `Freefall.claim()` bug: the code trusts a caller-supplied token identifier instead of binding it to the record's own asset.

### Finding Description
The eligibility gate in `AttachRescueOutboundFromReceipt` only validates:
1. That `originalUtxId` (from `event.UniversalTxId`) resolves to a real UTX [2](#0-1) .
2. That the UTX is in a "stuck" state (CEA deposit failed, or a REVERTED `INBOUND_REVERT` outbound exists) [3](#0-2) .
3. That no active rescue outbound already exists for that UTX [4](#0-3) .

It never checks that `event.PRC20` — the PRC20 address the *caller chose* when invoking the gateway's rescue entry point — is the PRC20 mapped to `originalUtx.InboundTx.AssetAddr` on `originalUtx.InboundTx.SourceChain`. Any registered PRC20/token-config pair on that source chain is accepted as long as `GetTokenConfigByPRC20` resolves it [1](#0-0) . The resulting outbound is built with `ExternalAssetAddr: tokenCfg.Address` and `Prc20AssetAddr: event.PRC20` for `originalUtx.InboundTx.Amount` (the amount from the *original*, unrelated inbound) [5](#0-4) .

Concretely, if a user has a stuck low-value UTX (e.g., small USDC inbound that failed to deposit or whose revert failed on-chain), they can craft a `rescueFundsOnSourceChain` call referencing that UTX's ID but supplying a different, high-value PRC20 address (e.g., WETH's PRC20) that they have no economic claim on for this UTX. The keeper accepts `event.PRC20` at face value as long as it's a registered token on that source chain, builds a `RESCUE_FUNDS` outbound denominated in the *original UTX's `Amount`* but tagged with the attacker-chosen `Prc20AssetAddr`/`ExternalAssetAddr`, and the outbound then proceeds through the normal TSS-signed outbound-execution path to actually deliver that asset off-chain — an unauthorized cross-asset payout, mirroring the `claim()` vulnerability's "attacker controls the token pool" pattern.

### Impact Explanation
If exploitable, an unprivileged attacker can trigger an outbound denominated in a token they never actually deposited or had locked, using nothing but a stuck/failed UTX they control as the trigger condition and an arbitrary registered PRC20 address as the payout asset. This maps to "unauthorized release" / "unauthorized refund" of protocol-controlled funds and cross-linked ballot/outbound state accepted through a user-reachable flow, which is explicitly in scope.

### Likelihood Explanation
Likelihood depends on two facts I could not fully verify from the Go-side code alone, because the enforcement (if any) lives in the `UniversalGatewayPC` Solidity contract, which is **not present in this repository** (only ABI/event decoders are in scope here):
- Whether the on-chain `rescueFundsOnSourceChain` Solidity function itself restricts `prc20` to the token actually associated with `universalTxId` (e.g., by reading stored deposit/lock records) before emitting the event.
- Whether `amount` for the rescue outbound is derived from actual locked state on-chain versus simply reusing `originalUtx.InboundTx.Amount` client-side as this Go code does.

If the Solidity contract enforces `prc20 == token-bound-to-that-utx` before emitting `RescueFundsOnSourceChain`, then this Go-side keeper code is safe because it is simply relaying an event that already encodes a validated (utxId, prc20) pairing. If it does not enforce this (or if the mapping can be manipulated because `universalTxId` on the Push-chain side is attacker-suppliable independent of the actual on-chain rescue state), then the vulnerability is real and directly analogous to the `claim()` bug. **I could not confirm the contract-side check because the Solidity source for `UniversalGatewayPC` is out of this repository's index.**

### Recommendation
In `x/uexecutor/keeper/create_outbound.go`'s `AttachRescueOutboundFromReceipt`, explicitly re-derive the expected PRC20 for `originalUtx.InboundTx.SourceChain` + `originalUtx.InboundTx.AssetAddr` via `k.uregistryKeeper.GetTokenConfig(...)` and assert it equals `event.PRC20` before building the rescue outbound, rather than trusting `event.PRC20` to resolve to *some* valid token config and implicitly binding the original UTX's amount to whatever asset the event names:
```go
expectedTokenCfg, err := k.uregistryKeeper.GetTokenConfig(ctx, originalUtx.InboundTx.SourceChain, originalUtx.InboundTx.AssetAddr)
if err != nil || expectedTokenCfg.NativeRepresentation == nil ||
    !strings.EqualFold(expectedTokenCfg.NativeRepresentation.ContractAddress, event.PRC20) {
    return fmt.Errorf("rescue: PRC20 %s does not match token bound to UTX %s", event.PRC20, originalUtxId)
}
```
This closes the gap even if the Solidity-side check is later found to be missing or bypassable, applying defense-in-depth consistent with the `require(_tokenAddress == game.tokenAddress, ...)` fix pattern from the referenced report.

### Proof of Concept
Not fully constructible from this repository alone, since the trigger point (`rescueFundsOnSourceChain(universalTxId, prc20, ...)`) is a Solidity entry point on `UniversalGatewayPC` whose source is not indexed here. A complete PoC requires:
1. A stuck UTX `U` for token A (small value) reaching the CEA-deposit-failed or inbound-revert-reverted state.
2. A call to `UniversalGatewayPC.rescueFundsOnSourceChain(U.id, prc20_B, ...)` where `prc20_B` is a *different*, high-value registered token.
3. Observing that `AttachRescueOutboundFromReceipt` accepts this, attaches a `RESCUE_FUNDS` outbound with `Prc20AssetAddr = prc20_B` and `Amount = U.InboundTx.Amount`, and that this outbound is subsequently signed and delivered by TSS on the destination chain — paying out token B for a claim that was only ever backed by token A.

**Uncertainty flag:** Because the smart-contract source enforcing (or failing to enforce) the `(universalTxId, prc20)` binding is outside this repo's scope/index, I cannot confirm with certainty that the vulnerability is reachable end-to-end; the Go-side code shown here does not itself perform this binding check, which is the concrete, verifiable gap.
