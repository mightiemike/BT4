### Title
Consensus wires an unconditional `MockStakingContract` into production committee/proposer selection instead of the real on-chain staking contract - (File: crates/apollo_consensus_manager/src/consensus_manager.rs)

### Summary
`create_committee_provider`, which is called unconditionally from the production node bootstrap path (`apollo_node/src/components.rs`), always constructs a `MockStakingContract` and hands it to `StakingManager` as the `StakingContract` implementation, instead of using the real `CairoStakingContract` that queries the deployed on-chain staking contract via `call_contract`. This mirrors the Blueberry `UniswapV3AdapterOracle` bug class: a stub/mock implementation meant only for testing is left wired into the live execution path, so the value that should come from real (on-chain) state is instead synthesized from static, hardcoded config.

### Finding Description
`create_committee_provider` in `crates/apollo_consensus_manager/src/consensus_manager.rs` is the factory that builds the `CommitteeProvider` used by consensus to determine stakers, proposer/committee membership and epoch boundaries: [1](#0-0) 

The comment directly acknowledges the gap: `// TODO(Asmaa/Dafna): Create StakingContract according to config.` — yet the code unconditionally instantiates `MockStakingContract` regardless of any configuration flag, and that instance is what actually gets used to build the `StakingManager` returned to the caller.

This factory is invoked from the real node component wiring, not from test code: [2](#0-1) 

`MockStakingContract` is explicitly documented as a stub: "Mock implementation of the staking contract backed by static in-memory configuration," and its `get_stakers`/`get_stakers_with_config` derive the committee purely from `StakingManagerDynamicConfig.default_committee` / `override_committee` (static config values), not from any on-chain state: [3](#0-2) [4](#0-3) 

By contrast, the intended production implementation, `CairoStakingContract`, calls the real deployed staking contract entry points (`GET_STAKERS_ENTRY_POINT`, `GET_CURRENT_EPOCH_DATA_ENTRY_POINT`, `GET_PREVIOUS_EPOCH_DATA_ENTRY_POINT`) through the batcher's `call_contract`: [5](#0-4) 

This `CairoStakingContract` is fully implemented and exists in the same crate, but `create_committee_provider` never constructs or selects it — it is dead code from the perspective of the production wiring, exactly analogous to the Blueberry report where the real oracle-consulting library existed but was never actually reached because the code path used the mock instead.

The `StakingManager.committee_at_height`/`fetch_and_build_committee` logic that drives proposer selection and committee validation for consensus consumes whatever `StakingContract` implementation it was given: [6](#0-5) [7](#0-6) 

Since the trait abstraction (`StakingContract`) hides the concrete backing implementation from callers, nothing downstream can detect that the "committee" being used for the real chain height is actually derived from static config rather than real staking/delegation state on L1/L2.

### Impact Explanation
Because committee/proposer selection for every height is derived from `MockStakingContract`'s static config rather than the real staking contract, the set of stakers, their weights, and thus the elected committee and proposer for each height is completely decoupled from actual on-chain stake. Any account or actor with the ability to influence the deployed `StakingManagerDynamicConfig` (which is dynamic/updatable via `config_manager_client.get_staking_manager_dynamic_config()`) — or simply the fact that this hardcoded configuration diverges from real stake — results in:
- Wrong parties being granted proposer/validator (committee) privileges that should be earned via real stake, i.e., unauthorized account action within consensus.
- Consensus nodes computing a different, static committee membership than what the real staking contract would produce, causing honest-node divergence between any node that correctly wires the real contract and nodes running this code, or between different deployments with different static configs.
- Since this is the actual mechanism gatekeeping who can build/commit blocks, an incorrect or manipulable committee can allow the network to accept blocks proposed by parties that should not be part of the committee, or conversely fail to include legitimate stakers, threatening the chain's ability to reach consensus/confirm new blocks under the intended stake-weighted rules.

### Likelihood Explanation
This is not a corner case — `create_committee_provider` is called unconditionally during ordinary node startup for every sequencer node (as wired in `apollo_node/src/components.rs`), with no feature flag or config switch to opt into the real `CairoStakingContract`. Every height's committee computation goes through this path, so the divergence between intended (stake-based) and actual (static-config-based) committee selection is present on every produced/validated block, not just under adversarial conditions.

### Recommendation
Implement the TODO: select `CairoStakingContract` (backed by the real deployed contract address from config) as the production `StakingContract` implementation in `create_committee_provider`, reserving `MockStakingContract` strictly for test builds/paths (e.g., behind `#[cfg(test)]` or an explicit test-only config flag), matching the pattern already used elsewhere in the codebase (e.g., `EmptyClassManagerClient` vs the real client). Add a runtime assertion/config validation so production deployments fail fast if no real contract address is configured, rather than silently falling back to static/mock data.

### Proof of Concept
1. Start a sequencer node via the normal bootstrap path (`apollo_node`), which calls `create_committee_provider` as shown in `crates/apollo_node/src/components.rs` lines 11–15.
2. Observe that regardless of `ConsensusManagerConfig`, the returned `CommitteeProvider` is backed by `MockStakingContract::new(...)` (see `consensus_manager.rs` lines 384–388), never `CairoStakingContract`.
3. Deploy/update the real on-chain staking contract with a staker set/weights that differ from `StakingManagerDynamicConfig.default_committee`/`override_committee`.
4. Call `StakingManager::get_committee(height)` (via `committee_at_height` → `fetch_and_build_committee`) and observe the committee returned reflects the static config values, not the real contract's stakers — demonstrating the committee used for consensus (proposer eligibility, block validation) is disconnected from actual stake, as in `crates/apollo_staking/src/mock_staking_contract.rs` lines 71–85 vs. the real contract calls in `crates/apollo_staking/src/cairo_staking_contract.rs` lines 53–94.

#[async_trait]
impl StakingContract for CairoStakingContract {
    async fn get_stakers(&self, epoch: u64) -> StakingContractResult<Vec<Staker>> {
        info!("Calling staking contract {GET_STAKERS_ENTRY_POINT} for epoch={epoch}.");
        let retdata = self.call_view(GET_STAKERS_ENTRY_POINT, vec![Felt::from(epoch)]).await?;

        // Filter out stakers that don't have a public key.
        let contract_stakers = ContractStaker::from_retdata_many(retdata)?;
        let initial_len = contract_stakers.len();
        let stakers: Vec<Staker> = contract_stakers
            .into_iter()
            .filter_map(|contract_staker| {
                contract_staker.public_key.map(|_| Staker::from(&contract_staker))
            })
            .collect();

        info!(
            "Retrieved {} stakers for epoch={}, filtered out {} without public key.",
            stakers.len(),
            epoch,
            initial_len - stakers.len()
        );

        Ok(stakers)
    }

    // Returns the committee data for the given epoch.
    // If the data is not cached, it is fetched from the state and cached.
    async fn committee_at_height(
        &self,
        height: BlockNumber,
    ) -> CommitteeProviderResult<Arc<Committee>> {
        let epoch = self.epoch_at_height(height).await?;

        // Attempt to read from cache.
        {
            let cache = self.committee_cache.lock().await;
            if let Some(committee) = cache.get(epoch) {
                return Ok(committee.clone());
            }
        }

        // Otherwise, build the committee from state, and cache the result.
        info!("Committee cache miss for epoch={epoch}, fetching from state.");
        let committee = Arc::new(self.fetch_and_build_committee(epoch).await?);

        // Cache the result.
        let mut cache = self.committee_cache.lock().await;
        cache.insert(epoch, committee.clone());

        Ok(committee)
    }
