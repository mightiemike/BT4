### Title
Missing upper-bound validation on Declare transaction `l2_gas.max_amount` permanently strands a stuck account (`StatelessTransactionValidator::validate_resource_bounds`) - (File: crates/apollo_gateway/src/stateless_transaction_validator.rs)

### Summary
`StatelessTransactionValidator::validate_resource_bounds` explicitly skips the `max_l2_gas_amount` ceiling check for Declare transactions, while enforcing it for every other transaction type. This mirrors the reported bug class: a numeric user-supplied parameter (here, `resource_bounds.l2_gas.max_amount`) is accepted by the gateway without an upper bound sanity check, and this un-bounded value can never actually be satisfied downstream (block/bouncer capacity), leading to the transaction — and the account's nonce sequence behind it — becoming permanently stuck.

### Finding Description
`validate_resource_bounds` performs three checks on every transaction: non-zero resource bounds, minimum gas price, and a configured maximum `l2_gas.max_amount`. The maximum-amount check is deliberately bypassed for `RpcTransaction::Declare`: [1](#0-0) 

This means a Declare transaction can be submitted to the gateway with an `l2_gas.max_amount` far exceeding any value the sequencer will ever actually be able to fit into a block — the bouncer independently enforces a hard per-block resource ceiling (`BouncerConfig::block_max_capacity`, e.g. `sierra_gas`, `proving_gas`, `receipt_l2_gas`): [2](#0-1) 

A single transaction whose declared resource bounds exceed `block_max_capacity` will always be rejected during block building as `TransactionTooLarge`/`TransactionExecutorError::BlockFull`-adjacent ("Transaction size exceeds the maximum block capacity"), regardless of how many attempts are made: [3](#0-2) 

Because such a transaction stateless-validates successfully (it is accepted into the mempool) but can never be included in any block, it sits at the account's next expected nonce indefinitely. Since the mempool/protocol requires strictly sequential nonces per account, any transaction the same sender later submits with a higher nonce is permanently blocked behind the stuck Declare transaction — the account's ability to transact is frozen until the account owner discovers and replaces the tx (fee-escalation resubmission at the same nonce), which is not guaranteed to succeed if the misconfigured resource bounds were unintentional or fixed. This exactly parallels the referenced report's root cause: a user-input numeric field with no sane upper bound leads to a mechanism that can never complete, permanently freezing what depends on it (there, mint fees; here, the account's transaction pipeline).

### Impact Explanation
Any account whose Declare transaction is admitted with an over-sized `l2_gas.max_amount` becomes unable to progress its nonce, freezing that account's on-chain activity (including funds locked behind pending operations gated by that nonce) until manual remediation. This is a direct, protocol-level consequence of a documented input-validation gap (the code even contains a `TODO(Arni)` acknowledging the missing check), reachable by any unprivileged transaction sender with a single Declare submission.

### Likelihood Explanation
Medium: this requires a user (or a wallet/SDK bug) to set an excessively large `l2_gas.max_amount` specifically on a Declare transaction — easy to trigger accidentally (e.g., copying resource bounds from an Invoke fee-estimation flow without adjusting for the missing cap) since the gateway performs no sanity check for this specific transaction type while doing so for all others.

### Recommendation
Apply the same `max_l2_gas_amount` upper-bound validation to Declare transactions as is applied to Invoke and DeployAccount transactions in `validate_resource_bounds`, removing the special-cased `if let RpcTransaction::Declare(_) = tx {}` bypass, or otherwise cap declare resource bounds against the bouncer's block capacity constants so that no admitted transaction can be structurally guaranteed to never fit in a block.

### Proof of Concept
1. Submit a `Declare` V3 RPC transaction with `resource_bounds.l2_gas.max_amount` set far above `BouncerConfig::block_max_capacity` (e.g., above `sierra_gas`/`proving_gas`/`receipt_l2_gas` defaults), and `nonce = N` (the account's current nonce).
2. `StatelessTransactionValidator::validate` accepts the transaction because the `max_l2_gas_amount` branch is skipped for Declare (`crates/apollo_gateway/src/stateless_transaction_validator.rs:78-85`).
3. The transaction is admitted to the mempool at nonce `N`.
4. During block building, the transaction is always rejected as exceeding block capacity (`crates/blockifier/src/bouncer.rs:125-137`, confirmed by the `TransactionTooLarge`/"Transaction size exceeds the maximum block capacity" test in `crates/blockifier/src/blockifier/transaction_executor_test.rs:263-276`), and is never included in any block.
5. Every subsequent transaction from the same sender at nonce `N+1, N+2, ...` remains inadmissible for inclusion (nonce ordering), so the account's transaction pipeline is permanently frozen at nonce `N`.

Note: I was unable to directly trace how the batcher's block-building loop (`apollo_batcher/src/block_builder.rs`) handles a transaction rejected as `TransactionTooLarge` (e.g., whether it drops the transaction from the mempool or simply skips it and retries indefinitely) within the available exploration; this detail would need to be confirmed by a full read of that file to precisely characterize whether the tx is evicted automatically or truly stuck forever absent user action (e.g., fee-escalation replacement at the same nonce).
