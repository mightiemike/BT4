### Title
`.unwrap()` panic on `Receipt::receiver_shard_id` when a `GlobalContractDistribution` receipt outlives its shard's split history — potential transaction-triggered chunk-processing halt - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receiver_shard_id(&shard_layout).unwrap()` on every delayed receipt popped from the queue [1](#0-0) . For a `ReceiptEnum::GlobalContractDistribution` receipt, `receiver_shard_id` can return `Err(EpochError::ShardingError(...))` if the receipt's stored `target_shard` no longer exists in the current shard layout's split history [2](#0-1) . Any unprivileged account can trigger creation of such a receipt by deploying a global contract via a normal transaction, and the receipt can sit in the delayed-receipt queue across multiple resharding events before being dequeued and hit this `unwrap()`.

### Finding Description
- A `GlobalContractDistribution` receipt is created whenever any account submits a `DeployGlobalContract` action — a fully unprivileged, ordinary transaction.
- `Receipt::receiver_shard_id` resolves the receiver shard for such a receipt by first checking if `target_shard` is present in the *current* shard layout; if not, it calls `shard_layout.resolve_to_current_shard(target_shard)`, which walks the layout's split history to find a descendant shard [3](#0-2) . If no descendant can be found, it returns an `Err(EpochError::ShardingError(...))`.
- `DelayedReceiptQueueWrapper::pop` (used while draining the delayed-receipt backlog during ordinary chunk `apply`) calls `receipt_filter_fn`, which does `receiver_shard_id(&shard_layout).unwrap()` — turning that `Err` into an unconditional Rust panic rather than a handled error [4](#0-3) .
- A regression test, `test_stale_global_contract_distribution_after_double_resharding`, was specifically written to exercise "double resharding" against a queued `GlobalContractDistribution` receipt and asserts the chain does not stall/panic [5](#0-4) . That test comment explicitly states: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations" [6](#0-5) . This confirms the exact bug class exists in the codebase's own risk model — analogous to CVE-2017-12464's NULL-pointer dereference on an externally influenced pointer/variable (`keyfile`) that is unconditionally dereferenced without a null check, except here it's an `unwrap()` on an externally-influenced `Result` that can be `Err`.
- Whether the split-history depth maintained by `ShardLayout::resolve_to_current_shard` (in `core/primitives/src/shard_layout/mod.rs` and `v3.rs`) is bounded or covers only a limited number of resharding generations could not be fully verified in this pass — I was unable to inspect the full body of `resolve_to_current_shard` before the tool budget ran out, so I cannot confirm whether the two-resharding test case is the maximum depth the code claims to support, or whether a third/fourth resharding generation (or an adversarial GC/pruning interaction) could still exhaust the split history and hit the `unwrap()`.

### Impact Explanation
If `receiver_shard_id` returns `Err` for a delayed `GlobalContractDistribution` receipt (e.g., because its split-history ancestry has been fully superseded by enough resharding generations, or the `unwrap()` is reached via some other path not covered by the regression test), the node panics inside `apply()` while processing an ordinary chunk. This is a transaction-triggered halt: since `apply()` runs identically on every validator/RPC node processing that chunk, the panic would occur consistently across honest nodes, producing a chain-wide liveness failure (all validators tracking the shard crash/panic on the same block) rather than merely a local crash. This matches the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Reachability requires: (1) an unprivileged account deploying a global contract (trivial, ordinary transaction) to create the receipt; (2) the receipt remaining in the delayed queue long enough to span the relevant number of resharding events, which are protocol/config-driven and not directly attacker-controlled but can be influenced by congestion (attacker can flood the shard to keep other receipts delayed, prolonging the window) combined with a chain that reshards multiple times (dynamic resharding is a supported, config-enabled feature). Given the explicit existing regression test targeting exactly two reshardings, the immediate two-generation case appears to already be defended against (the test asserts no stall), but the guarantee for additional resharding generations, or for any code path that reaches this `unwrap()` outside the tested scenario, is not verified here. Likelihood is therefore moderate and conditional on resharding cadence, which is largely operator/protocol-controlled rather than purely attacker-controlled from a single transaction.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs`) with proper error propagation (e.g., return a `RuntimeError`/`StorageError` variant, matching the pattern used elsewhere for "delayed receipt fails validation on dequeue is treated as `StorageInconsistentState`" per the runtime-execution spec) rather than panicking. Additionally, verify/extend `ShardLayout::resolve_to_current_shard`'s split-history retention so it is bounded correctly relative to the maximum time a `GlobalContractDistribution` receipt can remain delayed (or ensure GC / expiry semantics guarantee the receipt is drained before the ancestry needed to resolve it is lost).

### Proof of Concept
1. Configure dynamic resharding (as in the existing test) so that a shard containing a deployer account is split.
2. Have any unprivileged account submit `DeployGlobalContract` to create a `GlobalContractDistribution` receipt targeting that shard.
3. Saturate the chunk's compute/gas budget with ordinary transactions so the distribution receipt is pushed into the delayed-receipt queue.
4. Force additional resharding generations (beyond what `test_stale_global_contract_distribution_after_double_resharding` exercises) while the receipt remains delayed, exceeding whatever split-history depth `resolve_to_current_shard` retains.
5. When the delayed queue is drained and `receipt_filter_fn` is invoked on the stale receipt, `receiver_shard_id(&shard_layout)` returns `Err`, and the `.unwrap()` at `runtime/runtime/src/congestion_control.rs:876` panics, halting chunk processing on every node applying that chunk.

*(Note: step 4's exact feasibility — i.e., whether more than two resharding generations can actually outrun `resolve_to_current_shard`'s retained history — was not independently confirmed against the `resolve_to_current_shard` implementation before the tool budget was exhausted; this should be verified by a background agent with full repository access before treating this as fully proven beyond the two-generation case already covered by the existing test.)*

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }
