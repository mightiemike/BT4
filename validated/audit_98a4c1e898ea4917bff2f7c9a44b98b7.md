### Title
Single-step, unverified `DeleteAccountAction.beneficiary_id` permanently destroys the account balance if the beneficiary does not exist - (File: runtime/runtime/src/actions.rs)

### Summary
The C4 finding describes the risk of committing a critical, value-affecting address in a single irreversible step with no verification/claim step, so that a mistaken address permanently bricks the contract. The analogous nearcore construct is `Action::DeleteAccount`, whose `beneficiary_id` is only validated as a syntactically valid account id and is never checked for existence before the account (and its balance) is unconditionally destroyed. The balance transfer to the beneficiary is deferred to a second, separately-processed receipt; if that beneficiary account does not exist, the transfer receipt fails and, because refund receipts cannot generate further refunds, the funds are simply lost.

### Finding Description
`action_delete_account` in `runtime/runtime/src/actions.rs` unconditionally removes the source account and, if it has a nonzero balance, schedules a new "balance-refund" receipt addressed to `delete_account.beneficiary_id`, then sets `*account = None`, permanently deleting the account in the very same (already-committing) receipt: [1](#0-0) [2](#0-1) 

The only validations performed on `beneficiary_id` (per the spec) are that it is a syntactically valid account id, that `DeleteAccount` is the final action, and that the account is not staking — there is no check that the beneficiary account actually exists: [3](#0-2) 

The generated balance-refund receipt is processed later as a normal `Transfer` action, but with `is_refund = true`. When the destination is a plain named account that does not exist, `check_account_existence`/`implicit_creation_allowed` explicitly forbids implicit creation for refund receipts, so the transfer fails with `AccountDoesNotExist`: [4](#0-3) [5](#0-4) 

This is confirmed by the test `refund_may_not_create_universal_account`, whose comment states the invariant explicitly: "a refund to a missing `0u` id must fail with `AccountDoesNotExist`", and the assertion confirms the account is never created: [6](#0-5) 

Because the failed receipt is itself a refund, no further refund/bounce-back receipt is generated for it (refunds do not spawn refunds, to avoid infinite loops), and a failed receipt's execution simply rolls back state changes made during its own (failed) processing, without restoring the funds to the original owner: [7](#0-6) 

The `DeleteAccount` receipt that removed the original account and moved its balance into the pending refund receipt has already been committed by the time the refund receipt is evaluated — that deletion is not undone when the refund later fails, since they are two separate receipts. The net effect: the account, and its entire balance, are permanently gone, and no account anywhere is credited with the funds.

### Impact Explanation
Any account holder (an unprivileged transaction signer, exactly matching the reachable actor set) can trigger this by submitting a single `DeleteAccount` transaction with a mistyped, unregistered, or otherwise nonexistent `beneficiary_id`. Because the deletion happens irreversibly and atomically in one step, with no two-step "propose beneficiary / confirm receipt" pattern and no existence check up front (exactly the missing safeguard called out in the C4 report), any user mistake in specifying the beneficiary results in permanent, protocol-level loss of the entire account balance — a concrete "permanently frozen (destroyed) funds" outcome as required by the validation rules. This is a supply-deflating bug (effectively burns balance) that stems from root-cause insufficient validation before an irreversible action, not user error tolerated by design (contrast with, e.g., access-key deletion which is documented/expected user risk).

### Likelihood Explanation
High: this requires only a single, ordinary `DeleteAccount` transaction from any account owner (no privilege, no governance, no validator involvement) with a beneficiary id that does not correspond to an existing account (e.g., a typo, an account not yet created, or an account that was itself deleted between construction and execution of the transaction). No collusion or special conditions are needed.

### Recommendation
Require the beneficiary account to exist (or be provably creatable, e.g., an implicit account whose only action is the resulting transfer) before allowing `DeleteAccountAction` to remove the source account, or perform the deletion and the beneficiary credit atomically within the same receipt/state transition so that failure to credit the beneficiary rolls back the deletion as well. Alternatively, disallow refund receipts targeting nonexistent named accounts from silently discarding value — instead bounce them back to the original account (or its predecessor) rather than burning the funds.

### Proof of Concept
1. Create/own account `alice.near` with a nonzero balance and no staking.
2. Submit a transaction with a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "typo-account-that-does-not-exist.near".parse().unwrap() })`, signed by `alice.near`.
3. The `DeleteAccount` receipt succeeds: `alice.near` is removed from state (`runtime/runtime/src/actions.rs:387,404`) and a `Receipt::new_balance_refund` carrying `alice.near`'s entire balance is queued to the nonexistent beneficiary.
4. The refund receipt is later processed against the nonexistent account; `check_account_existence`/`implicit_creation_allowed` rejects implicit creation because `is_refund = true`, so the receipt fails with `AccountDoesNotExist` (as shown by `refund_may_not_create_universal_account`, `runtime/runtime/src/tests/apply.rs:6883-6926`).
5. Because it is itself a refund receipt, no further refund is generated to return the balance to `alice.near` or anyone else — the funds are permanently unrecoverable.
