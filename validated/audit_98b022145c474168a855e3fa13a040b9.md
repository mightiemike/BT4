### Title
Liquidation reverts entirely when the oracle price for any asset in the borrower's egroup is stale or invalid, instead of falling back to a stored rate - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()` calls `get-assets(mask)`, which calls `price-multi-resolve` → `price-resolve` for every asset enabled in the borrower's egroup bitmask. `price-resolve` hard-reverts with `ERR-ORACLE-INVARIANT` if the freshly-fetched price fails legality (`> p u0`) or freshness (`oracle-timestamp-fresh`) checks, with no fallback to a previously accepted price. Since liquidation cannot proceed without this call succeeding, a single stale/invalid oracle reading for any asset in the position's egroup — even one unrelated to the collateral/debt asset actually being liquidated — blocks liquidation of an otherwise unhealthy, insolvent position.

### Finding Description
In `mainnet/contracts/market/v0-4-market.clar`:
- `price-resolve` (lines 373-395) computes `final-price` and unconditionally asserts `(oracle-price-legal final-price)` and `(oracle-timestamp-fresh timestamp last-update-time max-staleness)`, reverting the entire transaction with `ERR-ORACLE-INVARIANT` on failure: [1](#0-0) 
- `price-multi-resolve`/`iter-price-multi` fold over every asset enabled by the position's egroup mask, calling `price-resolve` for each and aborting the whole evaluation if any single resolution fails: [2](#0-1) 
- `get-assets` is the entry point used by `liquidate` to build the assets list with prices, and itself calls `unwrap-panic` on `price-multi-resolve`, converting any oracle-legality/freshness failure into an unrecoverable panic: [3](#0-2) 
- `liquidate` unconditionally calls `get-assets(mask)` before it can compute `total-collateral-usd`/`total-debt-usd` and perform the health check that gates whether a position may be liquidated: [4](#0-3) 

Because Clarity evaluates `let`-bindings sequentially and any `asserts!`/`unwrap-panic` failure aborts the entire transaction (there is no salvage path that substitutes a previously accepted, valid price), a single asset in the egroup with a stale or momentarily invalid oracle reading (e.g., a temporary Pyth/DIA feed outage, staleness beyond `max-staleness`, or price collapsing to `u0`) makes `liquidate()` for that borrower's position revert unconditionally — even though the liquidator supplied fresh `price-feeds` for the collateral/debt pair they intend to liquidate. This mirrors the bound-value/invalidation/later-use pattern in the H-37 report: the "current best" price is bound via `price-resolve`, the freshness/legality check invalidates it on failure, and the later mandatory use of that value (to compute the LTV that gates liquidation) has no fallback, so the whole liquidation aborts.

### Impact Explanation
If a borrower's egroup contains multiple assets and any one of them has a temporarily broken oracle (stale feed, decommissioned/paused feed, price temporarily reporting `u0`, or confidence too low), every liquidation of that borrower is blocked for as long as that unrelated asset's price cannot be freshly resolved. An undercollateralized/unhealthy position that should be liquidated cannot be, allowing its debt to continue accruing and its collateral value to keep falling, which can push the specific position — and in aggregate, the protocol — into insolvency (bad debt) once collateral value drops below outstanding debt with no liquidator able to intervene. This lands on the in-scope **protocol insolvency** impact class.

### Likelihood Explanation
This does not require any attacker action beyond normal oracle unavailability/staleness, which is a realistic and previously-acknowledged operational condition (the codebase explicitly implements staleness/confidence checks anticipating oracle imperfection, per `docs/oracle.md`). Any egroup containing more than one enabled asset is exposed; the more assets bundled into an egroup, the higher the probability that at least one has a stale/invalid price at any given time, making this a plausible single-transaction condition rather than a contrived multi-block scenario.

### Recommendation
Do not let a stale/invalid price for an asset unrelated to the liquidation gate the liquidation call. Options:
1. In `price-resolve`, when the freshness/legality check fails, fall back to the last valid cached price (if within an extended-but-bounded staleness tolerance for liquidation purposes) instead of reverting, mirroring the recommended mitigation in the referenced report (return the old rate rather than reverting).
2. Restructure `get-assets`/`get-notional-evaluation` used inside `liquidate` so that a resolution failure for an asset that is not the collateral or debt asset being liquidated does not abort the transaction (e.g., skip/zero-value that asset's contribution instead of propagating the error), while still requiring fresh prices for the two assets actually involved in the liquidation.
3. At minimum, replace `unwrap-panic` in `get-assets` with an explicit error path that liquidation-specific logic can catch and gracefully degrade from, rather than an unconditional panic.

### Proof of Concept
1. Borrower has collateral/debt spanning egroup assets `A` (being liquidated) and `B` (unrelated, e.g. a low-liquidity or currently-paused oracle feed).
2. Position becomes unhealthy (LTV crosses `ltv-liq-partial`), making it eligible for liquidation.
3. Asset `B`'s oracle feed becomes stale beyond its `max-staleness`, or its Pyth/DIA response temporarily reports a price of `u0` / fails confidence checks.
4. Liquidator calls `liquidate(borrower, collateral-ft=A, debt-ft=A-debt, ...)` supplying fresh `price-feeds` only for asset `A`'s market.
5. `liquidate` calls `get-assets(mask)` → `price-multi-resolve` over all egroup assets including `B` → `price-resolve(B)` → `asserts!` fails on `oracle-timestamp-fresh`/`oracle-price-legal` → `ERR-ORACLE-INVARIANT` → `unwrap-panic` in `get-assets` panics.
6. The entire `liquidate` transaction reverts before the health check or any collateral seizure/debt repayment executes, even though asset `A`'s price was fresh and the position was genuinely eligible for liquidation.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
