### Title
Stale per-timestamp index cache in market.clar is not invalidated when a vault's `lindex` is written down by `socialize-debt`, causing stale collateral/debt valuation within the same transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches each vault's `{index, lindex}` per `{timestamp, aid}` in the `index-cache` map so that multiple operations touching the same asset within one transaction avoid repeated cross-contract calls to the vault [1](#0-0) . The cache is populated exclusively through `accrue-and-cache`, which on a cache miss calls the vault's `accrue` and stores the resulting `{index, lindex}` under the current `stacks-block-time` [2](#0-1) . However, the vault's `socialize-debt` entry point — invoked from market.clar via `vault-socialize-debt` — mutates `lindex` directly (writing it down proportionally to the loss) without going through `accrue` and without market.clar refreshing or invalidating the corresponding `index-cache` entry [3](#0-2) .

### Finding Description
Every vault state-changing entry point that is meant to keep the market's cached index valid (`deposit`, `redeem`, `system-borrow`, `system-repay`) begins with `(u (try! (accrue)))`, which recomputes `index`/`lindex` and is the only path market.clar's `accrue-and-cache` uses to populate its cache [4](#0-3) .

`socialize-debt`, by contrast, computes a written-down `new-lindex` from the pre-existing `lindex` and the loss (`debt-reduction`) directly in its own `let`, and its guard/mutation sequence does **not** call `accrue` first: [5](#0-4) 

Because `socialize-debt` bypasses `accrue`, it also bypasses the only mechanism (`accrue-and-cache`) that market.clar uses to keep `index-cache` in sync [2](#0-1) . The cache key is `{timestamp: stacks-block-time, aid}` — i.e. valid for the entire current block/transaction — so if market.clar already cached the vault's `{index, lindex}` for asset `aid` earlier in the same transaction (e.g. while accruing collateral/debt for one debtor position via `accrue-user-collateral`/`accrue-user-debts`, which call `accrue-and-cache` per asset) [6](#0-5) , and later in the same transaction `vault-socialize-debt` writes down the real `lindex` in the vault, any subsequent read of `index-cache` for that `{timestamp, aid}` within the same transaction still returns the old, pre-write-down `lindex` — a cached value not invalidated when its source moved.

### Impact Explanation
The stale cached `lindex` is used by market.clar to value zToken collateral/debt for every position processed afterward in the same transaction (batched liquidations, multi-asset health checks, price resolution for zTokens). A position whose zToken collateral references the socialized vault will be over-valued relative to the vault's actual post-writedown backing, letting an operation (e.g., a borrow/withdraw/liquidation seize sized against the stale higher valuation) extract more value than the vault now holds. Since the vault's `assets`/`lindex` have already been reduced by the loss, honoring withdrawals/borrows priced off the stale cache directly reduces the value backing other depositors' shares — a theft of/permanent shortfall in vault funds. This lands in the Critical impact class (protocol insolvency / theft of funds at rest).

### Likelihood Explanation
This requires no privileged access: it only requires a transaction (or one liquidation call) that (a) triggers `accrue-and-cache` for an asset earlier in the call (via a batched health check across positions or oracle price resolution for a zToken), and (b) also triggers `vault-socialize-debt` for the same asset later in the same transaction, and (c) has a subsequent read for that same asset in the same transaction (a second position, or a second read in the same liquidation flow). Given `index-cache` is keyed to `stacks-block-time` and market.clar routes many multi-asset, multi-position operations (liquidation, multi-collateral health checks) through the same accrual/caching path, this interleaving is realistically reachable within Clarity's evaluation order (sequential execution within one transaction, no reentrancy needed).

### Recommendation
Either (1) make `socialize-debt` call `accrue` first and have market.clar's `vault-socialize-debt` wrapper refresh/overwrite the `index-cache` entry for that `{timestamp, aid}` with the post-writedown `{index, lindex}`, or (2) explicitly invalidate (`map-delete`) the `index-cache` entry for `aid` at the current `stacks-block-time` immediately after any call to `vault-socialize-debt`, forcing a fresh `vault-accrue` read on the next access within the same transaction.

### Proof of Concept
1. In a single transaction, market.clar processes a batched liquidation/health-check flow that calls `accrue-collateral-asset`/`accrue-debt-asset` for vault `aid=STX`, which calls `accrue-and-cache`, which (cache miss) calls `vault-accrue`, caches `{index, lindex}` under `{timestamp: T, aid: STX}` [7](#0-6) .
2. Later in the same transaction, the flow determines the STX vault has bad debt and calls `vault-socialize-debt STX amount`, which calls `.v0-vault-stx socialize-debt`, writing down `lindex` in the vault directly, without calling `accrue` [3](#0-2) [5](#0-4) .
3. A second position (or a second pass over the same asset) in the same transaction triggers `accrue-and-cache STX` again at the same `stacks-block-time T`; the cache HIT branch returns the pre-writedown `{index, lindex}` instead of re-querying the vault [2](#0-1) .
4. This second position's zSTX collateral/debt is valued using the stale, higher `lindex`, allowing it to pass a health check or be liquidated/seized for more than the vault now backs post-socialization, permanently misallocating value away from remaining zSTX holders.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-private (accrue-user-debts (debt-list (list 64 { aid: uint, scaled: uint})))
  (fold accrue-debt-asset debt-list { success: true }))

(define-private (accrue-debt-asset
  (debt-entry { aid: uint, scaled: uint })
  (acc { success: bool }))
  (begin
    ;; this will use cache if available, accrue if not
    (unwrap-panic (accrue-and-cache (get aid debt-entry)))
    acc))

(define-private (accrue-user-collateral (coll-list (list 64 {aid: uint, amount: uint})))

(define-private (accrue-collateral-asset

    (if (is-ztoken aid)
        ;; ZToken: map to underlying vault routing ID and accrue
        ;; zSTX(1)->STX(0), zsBTC(3)->sBTC(2), zstSTX(5)->stSTX(4), zUSDC(7)->USDC(6), zUSDH(9)->USDH(8), zstSTXbtc(11)->stSTXbtc(10)

                        (if (is-eq aid zsBTC) sBTC
                        (if (is-eq aid zstSTX) stSTX
                        (if (is-eq aid zUSDC) USDC
                        (if (is-eq aid zUSDH) USDH
                        (if (is-eq aid zstSTXbtc) stSTXbtc
                        ;; will cause ERR-UNKNOWN-VAULT with any value over 64
                        u100))))))))
          (begin
            (unwrap-panic (accrue-and-cache vault-id))
            acc))
        ;; Non-ztoken: skip accrual (no liquidity index needed)
        acc)))
