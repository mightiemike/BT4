### Title
Blocking minority of signer weight can permanently blacklist a legitimate transaction by falsely self-reporting it as "problematic" - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, `stacks-node/src/nakamoto_node/signer_coordinator.rs`)

### Summary
The `ProblematicTransaction` reject-code/failed-txid accounting mechanism trusts each signer's self-reported classification of a transaction without any independent verification by the miner. A coordinated minority of signer weight (>30%, i.e. a "blocking minority" — well short of the honest-majority/70% threshold) can report any target transaction as `ValidateRejectCode::ProblematicTransaction` in their `BlockRejection` messages. This causes the miner to permanently exclude that transaction from all future block proposals network-wide, even though the transaction is fully valid and would be accepted by the honest majority of signers/nodes.

### Finding Description
When a miner's proposed block is rejected by signers, `StackerDBListener::handle_stackerdb_chunk` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` accumulates the `failed_txid` and `reason_code` fields directly from each signer's self-authored `BlockRejection` message: [1](#0-0) 

This weight tally is later consulted in `signer_coordinator.rs`, where the miner classifies a txid as either "temporarily excluded" or **permanently excluded** based solely on whether the *problematic_weight* (weight of signers claiming `ProblematicTransaction` rather than `BadTransaction`) exceeds the blocking minority (30%): [2](#0-1) 

Nowhere in this path does the miner independently re-validate the transaction or confirm that a majority (or any objective, reproducible check) agrees that the transaction is genuinely problematic — it is pure self-reported classification, weighted only by signer stake. The `ProblematicTransaction` classification a signer emits is itself derived from its own node's local, potentially non-deterministic checks in `postblock_proposal.rs`, such as per-transaction execution/analysis time limits (`block_proposal_max_tx_execution_time_secs`, `block_proposal_max_tx_analysis_time_secs`), which are hardware/load-dependent and not consensus-critical: [3](#0-2) 

This is the direct structural analog of the CrossL2Inbox issue: just as any unprivileged contract with flow control could invoke `validateMessage` with an invalid hash to make the Supervisor mark an unrelated transaction invalid and exclude it, here any coalition controlling just over 30% of signer weight (a **minority**, not the 70% signing majority required to actually accept/reject blocks) can inject a false "problematic" verdict for an arbitrary target transaction. Because the miner treats the self-reported reason code as ground truth rather than deriving it from a verifiable, reproducible rule, this breaks the equality that "a transaction is excluded from the chain only if it is objectively/deterministically invalid to the honest majority" — the classification instead reflects an unverified minority claim.

### Impact Explanation
This matches the High-severity bucket: "a minority-triggerable ... static-validation divergence... or reward mis-payment bounded to fees." A colluding signer minority (>30% weight, i.e., not a majority and not requiring any key/privilege beyond ordinary signer participation) can permanently censor ("poison") a legitimate, fee-paying transaction from a miner's mempool, imposing a permanent denial-of-service / fee loss on the victim without ever needing majority consensus or an on-chain invalid state. Since the classification is not tied to any objectively reproducible rule enforced by protocol consensus, different miners could also end up with divergent permanently-excluded-txid sets depending on which minority coalition of signers they happen to be paired with, causing static-validation/mempool-inclusion divergence across the network.

### Likelihood Explanation
This requires only that the attacker (or attacker-influenced signer operators) control slightly more than 30% of signer stake weight — a threshold explicitly designed into the protocol as the "blocking minority," well below the 70% needed to actually accept or reject blocks. No majority collusion, no private key of another party, and no node-operator/admin access to anyone else's infrastructure is required; the attacker only needs to control their own signer nodes' reported reject reason for a target `failed_txid`. Because the tally logic (`stackerdb_listener.rs`) accepts the self-reported reason code without cross-validation, the attack is directly reachable through the standard signer protocol messages that are already part of consensus operation.

### Recommendation
Do not let the permanent/temporary exclusion decision hinge purely on self-reported reason codes from a signer minority. Either (a) require the miner to independently re-validate/reproduce the "problematic" determination against its own node before excluding a txid (especially before *permanent* blacklisting), (b) tie `ProblematicTransaction` classification only to deterministic, consensus-agreed static checks (e.g., malformed markers, invalid PoX addresses) rather than time-based/hardware-dependent limits, or (c) require a supermajority (matching the actual block-acceptance threshold) rather than a 30% blocking minority before permanently blacklisting a transaction from the mempool.

### Proof of Concept
1. Attacker controls signer nodes representing slightly more than 30% of total signer weight (a blocking minority, not the 70% needed for block acceptance).
2. Victim submits a legitimate transaction `T` that would be accepted by honest miners/nodes.
3. A miner proposes a block including `T`.
4. The attacker's signers respond with `BlockResponse::Rejected` containing `failed_txid = T.txid()` and `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)`, regardless of whether their own node actually deemed it problematic.
5. `StackerDBListener` accumulates `info.problematic_weight` for `T` past the 30% blocking-minority threshold (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:520-546`).
6. Once total rejection weight also crosses the rejection threshold, `signer_coordinator.rs` returns `NakamotoNodeError::SignersRejected` with `T` in `permanently_excluded_txids` (`stacks-node/src/nakamoto_node/signer_coordinator.rs:521-540`).
7. The miner permanently blacklists `T` from its mempool/future proposals, denying the victim's valid transaction inclusion indefinitely, despite the honest majority of signers never having found it invalid.
