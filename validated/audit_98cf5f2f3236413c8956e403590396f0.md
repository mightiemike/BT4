## Finding

### Title
`socialize-debt` computes debt write-down and liquidity-index markdown using the stale accrual index instead of forcing an accrual first - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every state-mutating vault entrypoint that depends on the interest index (`system-borrow`, `system-repay`, `redeem`, `deposit`, and the DAO-only `set-fee-reserve`/`set-points-util`/`set-points-rate`) begins with `(try! (accrue))` before reading `index`/`total-debt`/`total-assets`. `socialize-debt` — the function used to write off unrecoverable debt — is the one exception: it reads `(var-get index)` and derives `total-debt`, `total-assets`, and the resulting `debt-reduction`/`new-lindex` write-down directly from the cached, potentially stale index, without ever invoking `accrue` first. [1](#0-0) 

### Finding Description
The vault's interest index is only refreshed when `accrue` is explicitly called; it lazily compounds interest based on elapsed time since `last-update`: [2](#0-1) 

All liquidity/borrow entrypoints call `accrue` as their first bound value before reading `index`/`total-debt`, e.g. `system-borrow` and `system-repay`: [3](#0-2) [4](#0-3) 

Even the purely-parametric DAO setters defensively call `(try! (accrue))` before mutating state, e.g. `set-fee-reserve` / `set-points-util`: [5](#0-4) 

`socialize-debt`, however, binds `idx` to `(var-get index)` and `old-total-assets` to `(total-assets)` — both computed from the *cached* index — and never calls `accrue`: [1](#0-0) 

`total-debt` and `total-assets` are private helpers that explicitly use `(var-get index)` (the cached value), as opposed to `debt-preview`/`total-assets-preview`, which use `next-index` (the freshly-computed, would-be-accrued value): [6](#0-5) 

This is the same class of bug as the external report on `MSDController._withdrawReserves`: a value bound (`old-total-assets`, `idx`, `debt-reduction`) from stale state, without invalidating it via the update function (`accrue`) that exists specifically for that purpose, is then used in a privileged accounting mutation (`var-set lindex new-lindex`, principal/debt/asset reductions).

**Sequence:**
1. Vault index is last updated at time `T0` (`last-update = T0`), no `accrue` has occurred since.
2. Time elapses without any user interaction on this vault (borrow/repay/deposit/redeem), so real accrued interest since `T0` is not yet reflected in `index`/`assets`.
3. `market.clar` identifies an insolvent position and invokes the vault's `socialize-debt(scaled-amount)` directly (its caller-authorization is checked via `check-caller-auth`, restricting it to the market contract, but the market contract itself does not force an `accrue` beforehand).
4. `socialize-debt` computes `debt-reduction` using the stale `idx`, and `old-total-assets` using stale `total-debt`/`total-borrowed` — omitting the interest that has silently accrued since `T0` but is not yet booked into `assets`/`index`.
5. `new-lindex` is derived from `(old-total-assets - debt-reduction) / old-total-assets` using these understated inputs, and is written directly with `var-set lindex new-lindex`.
6. The write-down applied to `lindex` (the value used to price zToken redemptions for suppliers) is smaller than what a correctly-accrued calculation would have produced, because the true post-accrual total-assets figure (which should include the just-accrued interest) is never computed or subtracted from.

### Impact Explanation
`lindex` (liquidity index) directly determines the redemption value of `zft` shares for suppliers (`convert-to-assets-preview`/`total-assets-preview` chain). An incorrect (insufficiently reduced) `lindex` after `socialize-debt` leaves the vault's book value of supplier shares higher than the vault's actual recoverable backing. Since this discrepancy is baked into the on-chain state permanently (no later correction mechanism re-derives `lindex` from first principles), later redeemers cannot fully redeem at the stated rate once the shortfall is realized — this is a protocol insolvency / permanent value-freezing condition for a subset of suppliers, satisfying the Critical impact bar (protocol insolvency) or at minimum High (permanent freezing of unclaimed yield, since the accrued-but-unbooked interest that should have inflated `total-assets` before the write-down is effectively lost).

### Likelihood Explanation
The trigger condition — time passing since `last-update` without an intervening `accrue` call on that specific vault before `socialize-debt` executes — is entirely plausible in production: bad-debt socialization is an infrequent, admin/market-triggered event, and there is no guarantee that a regular user action (which would call `accrue`) happens in the same block immediately prior. The bug is deterministic given that condition and requires no attacker collusion — it is a straightforward missing-accrual defect identical in shape to the confirmed MSDController analog.

### Recommendation
Add `(try! (accrue))` as the first bound expression in `socialize-debt`, mirroring `system-borrow`/`system-repay`/`redeem`/`deposit`, so that `total-debt`, `total-assets`, and the resulting `lindex` write-down are computed from freshly-accrued state rather than the stale cached `index`/`assets`. Apply this fix uniformly across all vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), since all six duplicate the identical `socialize-debt` implementation.

### Proof of Concept
Conceptual PoC (cannot be executed without a live Clarinet/Clarigen harness, which is out of scope for static analysis):
1. Deploy vault, have a user borrow to create `principal-scaled > 0`, then let a significant amount of time pass (e.g. several days) without any further `deposit`/`redeem`/`borrow`/`repay` call on that vault — `index`/`assets`/`last-update` remain at their old cached values while real accrued interest is not booked.
2. Have `market.clar` (the only authorized caller per `check-caller-auth`) invoke `socialize-debt` on the vault for the insolvent position's `scaled-amount`, without any accrual step in between.
3. Compare the resulting `lindex` against what would result if `accrue` were called immediately before `socialize-debt` (i.e., using `next-index`/`total-assets-preview` instead of `index`/`total-assets`). The two values diverge by the magnitude of interest that accrued during the elapsed time, demonstrating the supplier share value is left overstated relative to actual vault backing.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
