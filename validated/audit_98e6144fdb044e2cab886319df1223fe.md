### Title
Service-provider-style front-running of `UpdateBrokerageContract` lets a Super Representative silently steal an entire voting cycle's rewards from delegators - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
Java-tron's DPoS reward-sharing model mirrors the Audius "deployerCut" pattern: a Super Representative (SR, the analog of Audius's "service provider") sets a `brokerage` percentage that determines how much of the block/vote reward it keeps versus what it shares with its delegators (voters). SRs can change this cut at will via `UpdateBrokerageContract`. The design intends this change to be timelocked — it is only supposed to take effect starting the *next* voting cycle, snapshotted during `MaintenanceManager.doMaintenance()`. However, because transaction execution happens *before* `doMaintenance()` within the same block that triggers the maintenance/cycle transition, an SR can submit the brokerage update transaction inside that exact transition block. The malicious value is picked up by the snapshot logic and immediately locked in for the entire next cycle, giving delegators zero warning and no opportunity to withdraw their votes before the change takes effect.

### Finding Description
`UpdateBrokerageActuator.execute()` writes the new cut into a "pending" slot (`cycle = -1`, i.e. `DelegationStore.REMARK`) with no delay: [1](#0-0) 

`DelegationStore.setBrokerage(byte[] address, int brokerage)` always targets this pending slot: [2](#0-1) 

Actual reward payouts use a per-cycle *fixed* brokerage value read from `DelegationStore.getBrokerage(cycle, address)`: [3](#0-2) 

The per-cycle value is only refreshed once per maintenance cycle, in `MaintenanceManager.doMaintenance()`, which copies whatever is currently in the "pending" slot into the just-started `nextCycle` for every witness: [4](#0-3) 

This snapshot mechanism is the codebase's de-facto "timelock" — a change made mid-cycle should only affect the *following* cycle, giving delegators time to react. The problem is the ordering of operations inside `Manager.processBlock()`: all transactions in a block (including an `UpdateBrokerageContract`) are executed first, and only afterwards is `consensus.applyBlock(block)` invoked, which is what calls `MaintenanceManager.applyBlock()` → `doMaintenance()`: [5](#0-4) 

`MaintenanceManager.applyBlock()` performs the cycle transition (`doMaintenance()`) whenever the current block's timestamp has crossed `nextMaintenanceTime`: [6](#0-5) 

Because the maintenance boundary is a public, predictable, deterministic timestamp (`getNextMaintenanceTime()`), any witness can craft and broadcast an `UpdateBrokerageContract` transaction timed to land in the exact block that will trigger `doMaintenance()`. The transaction is processed in the transaction loop of that block, updating the pending brokerage value; the subsequent `doMaintenance()` call in the very same block then copies that fresh value into the brokerage snapshot for the newly started cycle — with no timelock at all, since it all happens atomically within a single block.

`UpdateBrokerageActuator.validate()` only requires that the caller be a *registered* witness (present in `WitnessStore`), not necessarily an already-elected/top-27 active SR, and permits any value from 0 to 100: [7](#0-6) 

Any account can become a witness (and thus reach this code path) by broadcasting a standard `WitnessCreateContract`, so this is not a privileged administrative action — it is directly reachable by an ordinary broadcast transaction, exactly like Audius's permissionless "service provider" registration.

### Impact Explanation
An SR can silently set `brokerage = 100` (or any high value) timed to the maintenance-boundary block, capturing up to 100% of the reward pool that would otherwise be shared with its delegators for the entire following voting cycle (the interval between two maintenance events). Delegators have no visibility of the change until after it is already locked in for the cycle, and no mechanism to withdraw/redirect their votes in time to avoid the loss, since vote reassignment itself is only reflected starting from a subsequent cycle boundary via the same `doMaintenance()` snapshot mechanism. This is a direct economic/accounting corruption of delegator rewards (asset/accounting corruption via the reward-accounting actuator), reachable purely through normal broadcast transactions — no node compromise or key leakage required.

### Likelihood Explanation
The maintenance timestamp (`getNextMaintenanceTime()`) is a deterministic, publicly-known chain parameter, so any witness can predict precisely which block will trigger `doMaintenance()` and craft/broadcast the `UpdateBrokerageContract` transaction to land in that block. No privileged access, race against other validators, or unusual network conditions are required — only ordinary transaction broadcasting timed against a known, queryable on-chain value. This makes the attack straightforward for any self-interested SR to execute repeatedly, once per cycle.

### Recommendation
Enforce an explicit timelock for brokerage changes analogous to the Audius fix in PR #657: instead of writing new brokerage values into a "pending" slot that is opportunistically snapshotted at whatever moment `doMaintenance()` happens to run, require that `UpdateBrokerageContract` writes take effect only for cycles that start at least one full maintenance interval after submission (e.g., stage the update for `nextCycle + 1`, not `nextCycle`), and/or reorder `Manager.processBlock()` so that `doMaintenance()`'s witness-state snapshot (brokerage, vote counts) is captured *before* processing that block's own transactions, closing the same-block front-running window.

### Proof of Concept
1. Register (or use an existing) witness account `W` and get it elected as an active SR receiving vote-based rewards, with delegators voting for `W`.
2. Monitor `DynamicPropertiesStore.getNextMaintenanceTime()` (queryable via `getNextMaintenanceTime` API) to know precisely which upcoming block will satisfy `nextMaintenanceTime <= blockTime` and thus trigger `MaintenanceManager.doMaintenance()`.
3. Craft an `UpdateBrokerageContract` transaction from `W` setting `brokerage = 100`, and broadcast it so that it is included in that specific maintenance-boundary block (as block producer `W` can trivially include its own transaction in its own produced block, or otherwise time broadcast for inclusion).
4. Within `Manager.processBlock()`, the transaction executes first (`processTransaction`), setting `DelegationStore`'s pending brokerage (`cycle=-1`) to 100 for `W`.
5. `payReward(block)` still uses the *old* cycle's brokerage for this block's own reward (unaffected), but immediately after, `consensus.applyBlock(block)` invokes `doMaintenance()`, which executes `delegationStore.setBrokerage(nextCycle, W, delegationStore.getBrokerage(W))` — i.e., copies the just-set 100 into the new cycle's fixed brokerage for `W`.
6. For the entirety of the new cycle, `MortgageService.payReward()` now computes `brokerageAmount = value` (100%) for every reward paid to `W`, so `value -= brokerageAmount` leaves `0` for delegators (`DelegationStore.addReward(cycle, W, 0)`), while `adjustAllowance(W, brokerageAmount)` credits `W` the full amount — confirmed by the reward-split logic at [3](#0-2) .
7. Delegators only discover the change after the cycle (and their lost rewards) is already final, with no prior opportunity to withdraw their votes to another SR before the cut applied.

    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
