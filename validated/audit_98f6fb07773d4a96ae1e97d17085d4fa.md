## Title
Unchecked array bounds in `MerkleHash` precompiled contract leads to `ArrayIndexOutOfBoundsException`/DoS on TVM execution - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`MerkleHash.execute()` performs `System.arraycopy(data, 32, left, 0, 32)` and `System.arraycopy(data, 64, right, 0, 32)` on attacker-controlled `data` without first validating `data.length >= 96`, unlike its sibling `VerifyBurnProof`, which explicitly checks `data.length != SIZE` before slicing fixed offsets.

### Finding Description
The `MerkleHash` precompiled contract is invoked whenever any TVM smart contract calls its precompile address with attacker-supplied calldata (`data`), exactly analogous to the external report's pattern of unchecked byte-array slicing/indexing before size validation (e.g. `DeserializeG1`/`DeserializeG2` in the referenced report, and the general "Lack Of Array Size Checks Before Slicing Or Referencing Array Elements" bug class).

```java
public Pair<Boolean, byte[]> execute(byte[] data) {
  byte[] left = new byte[32];
  byte[] right = new byte[32];
  byte[] hash = new byte[32];
  boolean res = true;
  try {
    int level = parseInt(data);
    System.arraycopy(data, 32, left, 0, 32);
    System.arraycopy(data, 64, right, 0, 32);
    JLibrustzcash.librustzcashMerkleHash(...)
  } catch (Throwable any) {
    res = false;
    ...
  }
``` [1](#0-0) 

`parseInt(data)` uses the length-safe `parseBytes()` helper (`org.tron.common.utils.ByteUtil.parseBytes`), which right-pads with zeros for short input and never throws: [2](#0-1) 

However, the two direct `System.arraycopy(data, 32, left, 0, 32)` and `System.arraycopy(data, 64, right, 0, 32)` calls do not go through `parseBytes` and instead operate directly on the raw `data` array. If a caller supplies `data` shorter than 96 bytes (e.g., empty calldata, or `data.length` between 1 and 95), `System.arraycopy` throws `ArrayIndexOutOfBoundsException`. Contrast this with `VerifyBurnProof`, in the same file, which validates the *exact* input length up front before doing identical raw `System.arraycopy` calls at fixed offsets:
```java
if (data.length != SIZE) {
  return Pair.of(true, DataWord.ZERO().getData());
}
``` [3](#0-2) 

`MerkleHash` lacks this equivalent length guard, demonstrating the same missing-check pattern flagged in the external report.

### Impact Explanation
Because the whole `execute()` body (aside from the `arraycopy` calls) is wrapped in `try { ... } catch (Throwable any) { res = false; ... }`, the `ArrayIndexOutOfBoundsException` is actually caught here rather than propagating unhandled. [4](#0-3)  This significantly limits real-world impact — unlike the report's Go-based examples (which have no surrounding recover/catch and would crash the whole node), the JVM `catch (Throwable any)` here contains the panic to the single precompiled-contract call, so this does not crash the TVM/node, and the caller simply receives `false`/empty output as if the proof failed. There is no divergence, no accounting/auth bypass, and no consensus-halt risk demonstrated.

### Likelihood Explanation
Any unprivileged account can trigger this path trivially by calling the `MerkleHash` precompile address with calldata shorter than 96 bytes from a smart contract, but given the exception is caught, the practical effect is limited to the precompile returning a failure result rather than an actual crash or exploitable state corruption.

### Recommendation
Add an explicit length check (`data.length < 96` or `!= 96`) at the top of `MerkleHash.execute()`, mirroring the pattern already used in `VerifyBurnProof`, to fail gracefully and consistently rather than relying on the outer `catch (Throwable any)` to absorb the `ArrayIndexOutOfBoundsException`.

### Proof of Concept
1. Deploy/call a contract that issues a `CALL`/`STATICCALL` to the `MerkleHash` precompile address with `data.length` of, e.g., 40 bytes.
2. `parseInt(data)` succeeds (zero-padded), but `System.arraycopy(data, 64, right, 0, 32)` throws `ArrayIndexOutOfBoundsException` since `data.length (40) < 64 + 32`.
3. The exception is caught by `catch (Throwable any)`, `res` is set to `false`, and `Pair.of(false, EMPTY_BYTE_ARRAY)` is returned — confirming the missing check is reachable but currently non-crashing due to exception handling.

Given the exception is caught and does not propagate to crash the node or corrupt state, this is a low-impact code-quality/defense-in-depth issue rather than a high-severity vulnerability comparable to the unrecovered Go panics described in the external report.

    }
