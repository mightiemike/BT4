### Title
Unvalidated `beneficiary_id` in `DeleteAccountAction` permanently destroys funds when the target account does not exist - ([File: runtime/runtime/src/actions.rs])

### Summary
`DeleteAccountAction::beneficiary_id` is the on-chain analog of the "owner" field in the Sherlock report: it is a caller-supplied account identifier that will unconditionally receive a balance payout, but nearcore only checks that it is *syntactically* a valid `AccountId` — it never checks that the account actually exists or is reachable. Just as an unchecked `owner` address in `initialize()` can permanently lock funds if set to the zero address, an unchecked `beneficiary_id` that names a non-existent (but well-formed) account permanently destroys the deleted account's remaining balance.

### Finding Description
`validate_delete_action` only performs a format check on `beneficiary_id`: [1](#0-0) 

`action_delete_account` then unconditionally removes the source account and enqueues an unconditional balance-refund receipt to `beneficiary_id`, with no check that this account exists: [2](#0-1) 

The comment in the test suite makes the hazard explicit — the beneficiary must exist "otherwise the balance transfer the delete sends it would come straight back as a refund": [3](#0-2) 

Crucially, refund receipts (`predecessor_id` = `system`) that target a non-existent account are not silently retried or re-refunded to someone else — they simply fail with `AccountDoesNotExist` and the tokens are not delivered anywhere, as demonstrated for the related `refund_to` mechanism: [4](#0-3) 

This is the same class of bug as `refund_to` (`ActionReceiptV2::refund_to`), which is validated only for well-formedness (`AccountId::validate`) and not for existence: [5](#0-4) [6](#0-5) 

### Impact Explanation
A signer that deletes their own account (or any account they control the deleting key for) and names a syntactically valid but non-existent account as `beneficiary_id` causes the account's remaining balance to be sent as a refund receipt to that non-existent account. Because refund receipts are terminal (there is no "refund of a refund" to avoid infinite loops), the transfer fails with `AccountDoesNotExist` and the funds are neither delivered to the beneficiary nor returned to anyone — they are permanently and irrecoverably lost. This is a concrete, transaction-triggered, unauthorized loss of funds reachable by any ordinary account holder signing a single `DeleteAccount` action, matching the "lock up of funds" impact described in the original report (unchecked owner/beneficiary address → fund loss).

### Likelihood Explanation
High likelihood of accidental triggering (a typo'd beneficiary account, or an account that has since been deleted/never existed, causes silent, permanent loss with no error surfaced to the user beyond the refund receipt failing asynchronously) and it is trivially reproducible by any single unprivileged account holder with no special permissions, cost, or validator collusion required — only a single `DeleteAccount` action in a signed transaction.

### Recommendation
Before enqueuing the balance-refund receipt in `action_delete_account`, verify (or defer the deletion until verified) that `beneficiary_id` refers to an existing account, or fail the `DeleteAccount` action with an explicit error (e.g. reusing/extending `ActionErrorKind::AccountDoesNotExist`) if the beneficiary does not exist, rather than allowing the account and its balance to be destroyed unconditionally. Alternatively, define a well-specified fallback (e.g., refund to the deleting actor) when the named beneficiary cannot be resolved.

### Proof of Concept
1. Create account `victim.near` with balance `B`.
2. Sign and submit `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near" })` from `victim.near`, where `nonexistent.near` is a syntactically valid `AccountId` that has never been created on-chain.
3. `validate_delete_action` passes because `nonexistent.near` is a well-formed account id.
4. `action_delete_account` removes `victim.near` from state and pushes `Receipt::new_balance_refund(&"nonexistent.near", B)`.
5. When that refund receipt is applied, `check_account_existence`/account lookup fails with `AccountDoesNotExist` (as shown in the `refund_may_not_create_universal_account` test pattern for refunds targeting missing accounts) and balance `B` is not credited to any account — it is permanently lost.
