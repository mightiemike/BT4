## Finding

`WalletContract::rlp_execute` in the eth-implicit-account "wallet contract" is a `#[payable]` entry point that lets **any external caller** attach a NEAR deposit when submitting an RLP-encoded Ethereum transaction to relay. This is directly analogous to the reported Solidity issue: a payable function that accepts `msg.value`/attached deposit without validating or unconditionally refunding it on failure paths, leading to permanent loss of the caller's funds. [1](#0-0) 

### Root cause

`rlp_execute` captures `env::attached_deposit()` into an `ExecutionContext`, and wraps it as `CallerDeposit` only for the "happy path" that reaches a promise chain (`inner_rlp_execute` → `action_to_promise(...).then(rlp_execute_callback(caller_deposit))`), which does correctly refund the caller if the downstream cross-contract call fails. [2](#0-1) [3](#0-2) 

However, several error paths never construct or propagate a refund promise at all:

1. In `rlp_execute`, if `inner_rlp_execute` returns `Err(e)` (e.g. malformed RLP bytes, an unsupported action, or any `Error::User`/`Error::AccountId` variant), the function returns `PromiseOrValue::Value(e.into())` immediately — no promise, no refund of the attached deposit that was already credited to the wallet contract's balance by the NEAR runtime before execution began. [4](#0-3) 

2. Inside `address_check_callback`, when the address-registrar lookup indicates the eth address collides with an existing named account (`maybe_account_id.is_some()`), the function either creates a "ban relayer" promise (which only deletes a key and calls `ban_relayer`, attaching zero deposit) or returns an error value directly — in both sub-branches the `caller_deposit` parameter is simply dropped, never refunded. [5](#0-4) [6](#0-5) 

Per the protocol's Economics API, an attached deposit "will be immediately deposited before the contract execution starts" — i.e., it becomes part of the wallet contract's balance the instant `rlp_execute` is invoked, regardless of what the method logic subsequently does. [7](#0-6) 

So any account can call `rlp_execute` with a deliberately malformed `tx_bytes_b64` (or a target/action combination that trips the address-registrar collision check) while attaching NEAR tokens, and that deposit is permanently absorbed into the wallet contract's balance with no code path to reclaim it — exactly the "no `msg.value == 0` check on functions not designed to hold user value" pattern from the report, translated to NEAR's attached-deposit semantics.

### Title
Unrefunded attached deposit permanently lost on `WalletContract::rlp_execute` error paths - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`rlp_execute` is `#[payable]` and accepts an attached NEAR deposit from any caller relaying an Ethereum-style transaction to an eth-implicit account's wallet contract. Only the promise-chain success path threads this deposit through `CallerDeposit` for refund-on-failure. Early error returns in `rlp_execute` (any `Err` from `inner_rlp_execute`) and in `address_check_callback` (both branches when the registrar lookup returns `Some`) never construct a refund transfer, so the attached deposit is silently kept by the contract.

### Finding Description
- `rlp_execute` is marked `#[payable]`, so callers can attach an arbitrary NEAR deposit. [8](#0-7) 
- `inner_rlp_execute` builds an `ExecutionContext` from `env::attached_deposit()` and, only on the success path, wraps it in `CallerDeposit`, which is forwarded to `rlp_execute_callback` for refund on failure of the cross-contract call. [9](#0-8) [10](#0-9) 
- If `inner_rlp_execute` itself returns `Err` (parse errors, unsupported actions, user errors), `rlp_execute` returns a value directly without ever creating the `CallerDeposit`/refund promise. [11](#0-10) 
- In `address_check_callback`, when the registrar reports a name collision (`maybe_account_id.is_some()`), the code either bans the relayer (zero-deposit promise) or returns an error value — in neither case is the previously attached `caller_deposit` refunded, even though it is passed into the function as a parameter. [5](#0-4) 
- Per protocol semantics, attached deposits are credited to the receiving account's balance immediately, before contract logic runs, so failing to schedule an explicit transfer back means the funds are stuck for good. [7](#0-6) 

### Impact Explanation
Any unprivileged account (a relayer or any other predecessor) calling `rlp_execute` with an attached deposit and a payload that triggers one of these unrefunded error paths permanently loses that NEAR balance into the wallet contract, with no code path to recover it (no event, no automatic protocol-level refund — this is a payable-method top-level function call, not a receipt failure, so NEAR's automatic deposit-refund-on-receipt-failure mechanism does not apply). This is a direct, permanent, unauthorized-in-effect loss of user funds.

### Likelihood Explanation
High: triggering the bug requires no privilege beyond being able to submit any transaction — e.g., attaching a deposit to `rlp_execute` while passing a malformed `tx_bytes_b64` is trivially reachable by any caller, and the address-collision branch is reachable by any relayer/user constructing a base-token-transfer to a target whose derived address collides with a registered named account.

### Recommendation
Ensure the attached deposit is tracked and unconditionally refunded (or forwarded) on *every* exit path of `rlp_execute`/`inner_rlp_execute`/`address_check_callback`, not only the success-oriented promise chain. Concretely: construct `CallerDeposit` before any early `Err` return in `rlp_execute`, refund it there directly (e.g., via a `Promise::new(predecessor).transfer(...)`) when returning `PromiseOrValue::Value`, and thread/refund it in both `address_check_callback` branches instead of discarding the parameter. Alternatively, reject calls with non-zero attached deposit on paths that do not need it, mirroring the suggested `require(msg.value == 0)` pattern from the original report.

### Proof of Concept
1. Caller (any account) calls `rlp_execute(target, tx_bytes_b64)` on an eth-implicit account's wallet contract, attaching a non-zero NEAR deposit.
2. Supply a `tx_bytes_b64` that fails RLP parsing/validation inside `internal::parse_rlp_tx_to_action` (e.g., malformed bytes or an unsupported action such as adding a full-access key).
3. `inner_rlp_execute` returns `Err(Error::User(...))`; `rlp_execute` executes `Err(e) => PromiseOrValue::Value(e.into())` at [12](#0-11)  — no promise is created, so the attached deposit (already credited to the wallet's balance) is never returned to the caller.
4. Repeat while observing on-chain balances: the caller's balance decreases by the attached deposit and the wallet contract's balance increases by the same amount, with no subsequent transfer back.

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }
