## Finding

### Title
`TransactionOutput::ensure_match_transaction_info()` never checks state/hot-state/position checkpoint-hash fields, letting a diverged local state root pass replay/output-application validation - ([File: types/src/transaction/mod.rs])

### Summary
Reducing the external report to its underlying invariant: *a value that is supposed to be validated against an authoritative reference must actually be checked before being trusted/acted upon*. In Aptos, the analogous invariant is that when a `TransactionOutput` is applied to storage without full VM re-execution (state-sync fast-forward, chunk output application, replay-verification tooling), the resulting state root must be checked against the trusted, accumulator-proven `TransactionInfo` before the data is treated as consistent. `TransactionOutput::ensure_match_transaction_info()` is the function meant to enforce this, but it self-admittedly skips the checkpoint-hash fields.

### Finding Description
`ensure_match_transaction_info()` validates a `TransactionOutput` against a `TransactionInfo` by checking status, gas used, write-set hash, and event root hash: [1](#0-0) 

It explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, and the code contains a developer-authored acknowledgment of this gap: [2](#0-1) 

This function is invoked from `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs` — i.e., it is the shared gate used when transaction outputs are applied or replayed without a full independent re-derivation-and-comparison of the state root elsewhere in the same call path.

Because the accumulator only proves that a given `TransactionInfo` (as a whole opaque blob) was actually committed by consensus — it does not prove that a *locally recomputed* state tree matches that `TransactionInfo`'s checkpoint hash — the actual state-root comparison has to happen in application code. `ensure_match_transaction_info` is exactly that application-level comparison point, and it omits the three checkpoint-hash fields introduced by the newer `TransactionInfoV1` format (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) as well as the original `state_checkpoint_hash`.

### Impact Explanation
If a node's local state computation diverges from the authenticated ledger (due to a bug in write-set application, hot-state tracking, or the "trading-native" position-state feature gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), code paths relying on `ensure_match_transaction_info` will report success even though the locally persisted state root differs from the one consensus committed. This is precisely the "committed state that differs from correct VM result" and "authenticated ... output bound to the wrong ... root" impact categories, because a silent state-root divergence would go undetected by this specific integrity gate and could be persisted as durable ledger state.

### Likelihood Explanation
I was not able to fully confirm, within available tool calls, whether the specific commit paths that call this function (e.g., `execution/executor/src/chunk_executor/mod.rs`) independently re-verify `state_checkpoint_hash` elsewhere in the same flow (as `DoStateCheckpoint::get_state_checkpoint_hashes` does when `known_state_checkpoints` is supplied during full-execution flows), which would reduce or eliminate the practical exposure for the base `state_checkpoint_hash` field. The `read_file` call against `chunk_executor/mod.rs` returned no content (likely truncated by index limits), so I could not trace the exact call site and its surrounding checks. The comment itself scopes the acknowledged, currently-unmitigated blind spot narrowly to `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` under the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature and to `db-tool`'s offline `replay_on_archive` verification tool rather than the live consensus commit path.

### Recommendation
- Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally recomputed values wherever they are available, failing hard on mismatch, consistent with the TODO already left in the code.
- Audit all call sites (`chunk_executor/mod.rs`, `aptos_debugger.rs`, CLI commands, `replay_on_archive.rs`) to confirm whether any of them separately re-verify these checkpoint hashes; if not, add that verification before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet.
- Have a Devin session with full repository access trace the exact `chunk_executor/mod.rs` call site (unavailable in this indexed view) to determine definitively whether the state-checkpoint-hash gap is independently mitigated for the non-experimental (`state_checkpoint_hash`) field.

### Proof of Concept

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
