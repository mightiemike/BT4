## Analog Identified: Replay-Verification Ignores Checkpoint-Root Hashes, Allowing Divergent State to Pass as "Verified"

### Title
`TransactionOutput::ensure_match_transaction_info` omits state/hot-state/position checkpoint-hash checks, letting replay-verification accept a state root that diverges from the authenticated ledger - (File: `types/src/transaction/mod.rs`)

### Summary
The external report's underlying invariant is "a signature (proof) must be bound to the *exact* context it authenticates (chain id + contract), or it can be replayed in a context where that binding no longer holds." The Aptos-native analog is a proof-comparison routine that authenticates a re-executed `TransactionOutput` against a ledger-committed `TransactionInfo`, but never checks the fields of `TransactionInfo` that actually bind the transaction to the resulting **state root** (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`). This is the exact context-binding gap for this repo's proof model.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` checks status, gas used, write-set hash, and event root hash against a `TransactionInfo`, but explicitly skips the checkpoint hashes, as the code itself documents: [1](#0-0) 

This function is the sole comparator used to validate that a freshly-executed `TransactionOutput` matches an authenticated `TransactionInfo` in two mainnet-relevant verification flows:

1. `ChunkExecutorInner::verify_execution`, invoked when `VerifyExecutionMode::should_verify()` is set during chunk replay/restore: [2](#0-1) 

2. `replay_on_archive`'s `execute_and_verify`, the dedicated tool for auditing historical execution correctness against archived, ledger-proven data: [3](#0-2) 

Separately, `TransactionOutputListWithProofV2::verify` (the check state-sync's "apply chunk" fast path runs on incoming data) also validates write-set hash, event root hash, gas, status, and transaction hash against `TransactionInfo`, but likewise has no assertion tying the locally-committed state tree to the checkpoint hash inside `TransactionInfo`: [4](#0-3) 

The checkpoint hash is only produced correctly during genuine (non-replay) execution because `DoLedgerUpdate::assemble_transaction_infos` derives it directly from `DoStateCheckpoint`'s own freshly computed Merkle root and bakes it into `TransactionInfo` unconditionally: [5](#0-4) 

So on the primary consensus/execution commit path, the checkpoint hash is self-consistent by construction. The gap only manifests when a *second, independent* execution (replay/backup verification) is compared against an already-authenticated `TransactionInfo` — exactly the scenario the state-integrity gate calls out ("Hard-fork-only divergence during commit, replay ... accepted as valid").

### Impact Explanation
If a fullnode's local Jellyfish Merkle / hot-state / position-state subsystem diverges from the network-agreed state (due to a storage bug, a non-deterministic VM/native path, a schema migration bug, or corruption), `ensure_match_transaction_info` will report "match" even though the locally materialized state root differs from the one signed by validators. Because `remove_and_apply` in `ChunkExecutorInner` (state-sync/backup replay) commits the *given* authenticated write set rather than the freshly re-executed one, this specific gap does not directly corrupt what gets written to that node's own storage from replay/backup-restore flows. However, it does defeat the purpose of `--verify-execution` and `replay_on_archive`, the tools operators and Aptos Labs rely on to detect exactly this class of storage/executor consensus-divergence bug before it manifests broadly or requires a hard fork. A silent pass here means a real state-divergence bug could go undetected until it surfaces as a chain-halting fork.

### Likelihood Explanation
Low-to-moderate: this requires an underlying (separate) non-determinism or storage bug to exist in the first place (e.g., in the hot-state/position/"trading-native" checkpoint-hash computation paths referenced by the TODO). The comparator gap itself is not independently exploitable by an unprivileged party to corrupt committed state — its impact is that it removes a safety net rather than being a direct write-path bug. The maintainers have already flagged it with an explicit `TODO(trading-native)` comment tied to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, indicating it is a known, tracked gap rather than a hidden defect.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) between the locally recomputed checkpoint and the `TransactionInfo` under verification, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any hot-state/position feature) is enabled. Consider also asserting checkpoint-hash equality in `TransactionOutputListWithProofV2::verify` wherever the receiving node can independently compute the same checkpoint (e.g., after applying to a known base state), so both online state-sync and offline replay tooling get the same authenticity guarantee the accumulator/Merkle proofs already provide for write sets and events.

### Proof of Concept
Not executable as a standalone PoC without artificially injecting a divergent state-tree computation (e.g., a modified hot-state or position-state commit path). Conceptually:
1. Run `db-tool replay-verify` (`replay_on_archive.rs`) or chunk-executor `--verify-execution` against archived transactions.
2. Patch/introduce a local execution divergence that only affects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` (write set, events, gas, and status remain identical).
3. Observe `ensure_match_transaction_info` returns `Ok(())` despite the state root differing from the ledger-authenticated `TransactionInfo`, i.e., the replay-verification tool reports success on a divergent state.

**Note:** I could not fully trace whether any currently-shipped feature (hot state, native position subsystem, "trading-native") is enabled on mainnet today in a way that would make the underlying checkpoint-hash divergence practically reachable — the TODO's reference to `COMPUTE_TRADING_NATIVE_STATE_ROOTS` suggests this is guarded behind an as-yet-unstable feature. Confirming the mainnet feature-flag status of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and the hot/position-state subsystems would require inspecting `types/src/block_executor/config.rs` and on-chain feature-flag configuration, which I did not have remaining tool budget to complete.
