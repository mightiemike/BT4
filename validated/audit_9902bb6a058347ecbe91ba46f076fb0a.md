### Title
Premature termination of AppendVec account scans on a legitimate zero-lamport account at the System Program address causes silent skipping of subsequent accounts in `clean` candidate collection - (File: accounts-db/src/append_vec.rs)

### Summary
The external report's bug class is "loss of value because a zero/sentinel address is not specially validated, causing subsequent legitimate operations to be silently skipped or misdirected." The closest reachable analog in `agave` is in `AppendVec::scan_stored_accounts_no_data`, which treats any account record whose `lamports == 0` **and** whose stored pubkey equals `Pubkey::default()` (the all-zero pubkey, which is also the on-chain address of the System Program, `11111111111111111111111111111111`) as an end-of-file sentinel and unconditionally stops scanning the storage file. Because `Pubkey::default()` is a real, reachable address that any user can transfer lamports into and out of via ordinary System Program transfers, an honest account legitimately stored at that pubkey with zero lamports — if it lands anywhere but the very last record of an AppendVec — causes the scan to silently stop, hiding every account physically located after it in that file from the caller.

### Finding Description
`AppendVec::scan_stored_accounts_no_data` is the low-level iterator used by both `scan_pubkeys` and `scan_accounts_without_data`: [1](#0-0) 
This break condition was designed to detect the "useless" zeroed-out padding that AppendVec shrink/reuse leaves at the tail of a recycled file, as shown in the accompanying test `test_scan_useless_accounts`, which manually overwrites an account slot with an all-zero `StoredMeta`/`AccountMeta` to simulate "hidden" trailing accounts: [2](#0-1) 

The problem is that the sentinel check (`lamports == 0 && pubkey == Pubkey::default()`) is indistinguishable from a genuine, honestly-stored account. `Pubkey::default()` (32 zero bytes) is the actual base58-encoded System Program address `11111111111111111111111111111111`. Nothing prevents a user from transferring lamports to this address and later draining it back to zero lamports through normal system-program transfers, which would cause AccountsDb to legitimately store a `(lamports=0, pubkey=Pubkey::default())` record in an AppendVec, at any offset — not necessarily the last one, since AppendVec records accounts in write order, not sorted by pubkey.

`scan_accounts_without_data` (built on this same function) is used directly in production code by `construct_candidate_clean_keys`, the routine that builds the set of pubkey candidates AccountsDb considers during `clean_accounts`: [3](#0-2) 
If a dirty store contains such a zero-lamport `Pubkey::default()` account before its logical end, the scan silently halts, and every account physically stored after that offset in the same AppendVec is never inserted into `candidates` via `insert_candidate`, i.e. never considered "dirty" for this clean pass.

### Impact Explanation
Accounts that are skipped by the truncated scan are not added to the cleaning "dirty" candidate set for that pass, so `clean_accounts` will not evaluate them for removing older/dead index and storage entries. This produces stale index/storage entries that persist longer than they should, and — depending on which accounts sit after the sentinel offset in the AppendVec — index or storage state can diverge from what a full/correct scan would produce, leading to slower reclamation, storage bloat (accounts and dead reference bytes not freed), and potential inconsistencies between the affected node's dead/candidate bookkeeping and other honest nodes that populated their AppendVecs in a different write order (and thus did not hit the same sentinel offset). Because the same `scan_stored_accounts_no_data` helper underlies `scan_pubkeys`, other future/optional callers of AppendVec pubkey scanning are exposed to the same silent truncation.

### Likelihood Explanation
Triggering this requires only: (1) a user transaction transferring lamports into the System Program address (`11111111111111111111111111111111`), then draining it back to zero, and (2) that write not being the last record physically appended to its AppendVec (a common situation, since AppendVecs interleave many pubkeys as transactions are processed within a slot and across slots before being ancient-packed/shrunk). No special validator privilege or malicious snapshot crafting is needed — an ordinary user constructs the transactions; the bug then manifests during normal `clean_accounts` background processing on any honest node whose storage layout happens to place such a record before other live records.

### Recommendation
Do not use `lamports == 0 && pubkey == Pubkey::default()` as an end-of-scan sentinel, since it collides with a real, reachable address. Instead, rely solely on the existing bounds/EOF checks (`unaligned_stored_size` overflow, `offset + unaligned_stored_size > self_len`) to detect the true end of valid data, or use an explicit, unambiguous marker (e.g., a dedicated tombstone flag not derivable from ordinary account state) to distinguish "recycled padding" from a legitimate zero-lamport account at the System Program address.

### Proof of Concept
1. Have a user transfer lamports to address `11111111111111111111111111111111` (i.e., `Pubkey::default()`), then transfer them all back out, leaving a zero-lamport account at that pubkey stored in some slot's AppendVec.
2. Ensure at least one other account is appended to the same AppendVec after that write (normal multi-account slot activity).
3. When that store becomes a "dirty store" candidate for `clean_accounts`, `construct_candidate_clean_keys` calls `store.scan_accounts_without_data(...)`, which internally calls `scan_stored_accounts_no_data`: [4](#0-3) 
4. Upon reaching the zero-lamport `Pubkey::default()` record, the scan `break`s, so `insert_candidate` in `accounts_db.rs` never runs for any subsequent account in that file: [5](#0-4) 
5. The unit test `test_scan_useless_accounts` independently confirms this exact truncation behavior (by manually writing a zero-lamport, `Pubkey::default()` record mid-file and observing the scan stops early), demonstrating the mechanism is real and reachable, not merely theoretical: [6](#0-5)
