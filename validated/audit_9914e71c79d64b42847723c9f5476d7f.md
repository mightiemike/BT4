### Title
Unbounded full-table scan in `AssetIssueStore.getAllAssetIssues()` reachable via public `getAssetIssueByName`/`getAssetIssueListByTimestamp` RPC/HTTP endpoints enables low-cost DoS amplification - (File: chainbase/src/main/java/org/tron/core/store/AssetIssueV2Store.java)

### Summary
`AssetIssueV2Store` extends `AssetIssueStore`, whose `getAllAssetIssues()` performs a full RocksDB iterator scan and materializes every stored `AssetIssueCapsule` into memory on every invocation. This method is used to serve the `getAssetIssueByName` / `getAssetIssueListByTimestamp` gRPC and HTTP endpoints, which are unauthenticated and callable by any client, meaning the per-request cost grows linearly with the total number of assets ever issued on-chain.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` is implemented as an unbounded iterator scan over the entire underlying store: [1](#0-0) . `AssetIssueV2Store` inherits this behavior directly with no overrides [2](#0-1) . A separate, bounded `getAssetIssuesPaginated` helper exists that sorts and slices the result of `getAllAssetIssues()` with an enforced `ASSET_ISSUE_COUNT_LIMIT_MAX` cap [3](#0-2) , but this cap is only applied after the full unpaginated list has already been built in memory — i.e., pagination reduces the *returned* payload size, not the underlying I/O/CPU cost of the scan.

Because every element must first be deserialized from RocksDB and collected into a `List` before any name-filter or timestamp-filter or pagination logic runs, the cost of a single call to `getAssetIssueByName`/`getAssetIssueListByTimestamp` is proportional to the total number of assets ever issued on the chain, not to the size of the response. The endpoints that reach this code path (`RpcApiService`, `GetAssetIssueByNameServlet`, `FullNodeHttpApiService`, `SolidityNodeHttpApiService`, PBFT/Solidity interface variants) are exposed without any application-level authentication, so any unprivileged client can invoke them directly and repeatedly.

An attacker can inflate the size of `AssetIssueV2Store`/`AssetIssueStore` cheaply by broadcasting many low-fee `AssetIssueContract` transactions (each paying only the standard TRC10 issuance fee), then flood the query RPC in parallel to force repeated full scans, driving CPU and disk I/O consumption on the node that is disproportionate to the query cost paid by the attacker.

### Impact Explanation
This is a DoS-via-RPC-API class issue: repeated cheap queries force disproportionate CPU/disk work on a full node, potentially degrading or stalling RPC service availability for legitimate users. It does not cause fund loss, key leakage, or consensus divergence — the impact is scoped to node/service availability degradation, not asset or accounting corruption.

### Likelihood Explanation
Feasibility depends heavily on two factors this review could not fully confirm from the available code: (1) the actual size `AssetIssueStore` can realistically reach in a production TRON network (issuance requires paying TRC10 creation fees, which bounds — but does not eliminate — the attacker's ability to bloat the store cheaply), and (2) whether a request-level rate limiter or QPS throttle already sits in front of these gRPC/HTTP handlers at the interceptor/framework level; no such limiter was found in the specific store/service code inspected, but a broader search of `RpcApiService`/`FullNodeHttpApiService` interceptor chains was not completed within the available tool budget, so this cannot be stated with full confidence. Given the currently-confirmed code (unbounded scan pre-pagination) and unauthenticated endpoint exposure, the finding is credible but its real-world severity is contingent on store size limits and any node-level throttling not fully verified here.

### Recommendation
- Modify `AssetIssueStore`/`AssetIssueV2Store` to support scan-time pagination (e.g., using RocksDB iterator seek/limit rather than draining the full iterator into memory) so that per-request cost scales with the requested page size, not total store size.
- Enforce `ASSET_ISSUE_COUNT_LIMIT_MAX` (or an equivalent bound) at the iterator level for `getAssetIssueByName`/`getAssetIssueListByTimestamp`, rather than only in the already-materialized pagination helper.
- Add or confirm an RPC/HTTP-level rate limiter for these specific handlers.

   * get all asset issues.

  public List<AssetIssueCapsule> getAllAssetIssues() {
    return Streams.stream(iterator())
        .map(Entry::getValue)
        .collect(Collectors.toList());
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
