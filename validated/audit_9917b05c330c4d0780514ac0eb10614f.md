I found the closest analog: the `RejectWithdrawFromGasKeyInDelegate` protocol feature comment directly documents the exact bug pattern from the audit report — a per-call check that fails to account for value drained through an alternate batched/nested execution path, permanently or temporarily bypassing a balance-consistency check that should have gated further spending.

### Title
Pending Transaction Queue scans only top-level actions, so a `WithdrawFromGasKey` nested inside a `Delegate` action drains a gas key the queue still counts as funded - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
The Sherlock finding describes `_depositETH`/`depositETHIntoMultipleRounds` bypassing the round's "should draw" limit check because the batched multi-item entrypoint doesn't re-run the same accounting the single-item path does, letting the tracked counter diverge from the real on-chain state and letting further deposits proceed when they should have been blocked. The nearcore analog is `PendingTxSession::check_pending` in `chain/client/src/pending_transaction_queue.rs`, whose `WithdrawFromGasKey` accounting loop only scans `tx.transaction.actions()` at the top level of a transaction [1](#0-0) . A `WithdrawFromGasKey` nested inside a `Delegate`/meta-transaction action is invisible to this accounting, so the pending-queue's `paid_from_gas_key` tracker undercounts real spend, just as the audited contract's round-completion check undercounts real deposits when made through the batched path.

### Finding Description
`check_pending` builds `paid_from_gas_key` from `snapshot.pending_gas_key_cost.saturating_add(session_gas_key_withdrawal)`, where `session_gas_key_withdrawal` is accumulated only by iterating the transaction's direct actions and matching `Action::WithdrawFromGasKey` [2](#0-1) . This mirrors the vulnerable `_depositETH`/`depositETHIntoMultipleRounds` split in the report: one execution path (`WithdrawFromGasKey` as a direct action) is accounted for, while another path that produces the very same balance-draining effect (`WithdrawFromGasKey` nested inside a `Delegate` action's `actions` list) is not walked into by the counting loop.

The codebase itself documents this exact bug class as a fixed/gated defect: `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` states "The SPICE pending transaction queue scans only the top level actions of a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key that the queue still counts as funded." [3](#0-2) . The action-level validator `validate_delegate_action` also gates the underlying action out of delegates behind this same protocol feature, confirming the nested path previously admitted `WithdrawFromGasKey` inside `Delegate` [4](#0-3) , and the runtime execution model shows `WithdrawFromGasKey` is dispatched identically regardless of whether it arrived directly or via a delegate's inner action list [5](#0-4) .

Before the `RejectWithdrawFromGasKeyInDelegate` feature activates (i.e., on any protocol version prior to its gate, which the test suite exercises explicitly), a relayer-signed meta-transaction whose inner `DelegateAction` contains a `WithdrawFromGasKey` executes successfully and drains the gas key balance [6](#0-5) , exactly the "action executes but the tracked counter never learns about it" pattern from the Sherlock report.

### Impact Explanation
Because the SPICE pending transaction queue's admission check (`PendingTxSession::check_pending`, feeding `paid_from_gas_key` into `verify_and_charge_gas_key_tx_ephemeral`) never observes gas-key spend that happened through a nested `Delegate` action, a subsequent gas-key transaction submitted within the same pending window can be admitted against a balance that has already been drained below what the queue believes is available. This is a direct analog of "the round wasn't drawn/finalized when it should have been because the batched path bypassed the counter that gates further action" — here, further gas-key transactions are optimistically admitted (and pre-charged) against stale balance data, risking `NotEnoughGasKeyBalance` failing at actual runtime charge time or, in the window before the fix, an inconsistency between what the pending-queue admission layer assumes is available and the real on-chain gas key balance.

### Likelihood Explanation
Reachable by any account holder with a gas key and access to a relayer/meta-transaction signer under the SPICE pending-transaction-queue path (`chain/client/src/pending_transaction_queue.rs`), requiring only a single `Delegate` action wrapping `WithdrawFromGasKey` — no privileged or validator-only access needed. It is protocol-version gated behind `RejectWithdrawFromGasKeyInDelegate`, and the nearcore test suite (`test_reject_delegated_gas_key_withdraw_protocol_upgrade`) explicitly demonstrates the pre-upgrade admission and drain [7](#0-6) .

### Recommendation
Confirm `RejectWithdrawFromGasKeyInDelegate` is active on all currently supported protocol versions (the test at `test_reject_delegated_gas_key_withdraw_protocol_upgrade` already asserts this is the case for `MIN_SUPPORTED_PROTOCOL_VERSION`) [8](#0-7) . As defense-in-depth, make `PendingTxSession::check_pending`'s accounting loop recurse into nested `Delegate`/`DelegateV2` action lists (mirroring how `validate_delegate_action` recurses for validation) so `session_gas_key_withdrawals` reflects all reachable `WithdrawFromGasKey` effects rather than only top-level ones, removing reliance on the protocol-feature gate as the sole backstop.

### Proof of Concept
On a protocol version before `RejectWithdrawFromGasKeyInDelegate` activates: fund a gas key, then submit a `Delegate` action (signed by the account's plain access key, relayed by any account) whose inner action list contains `WithdrawFromGasKey` for that gas key. The nearcore test `test_reject_delegated_gas_key_withdraw_protocol_upgrade` demonstrates this exact sequence succeeds and drains the balance pre-upgrade [9](#0-8) , while `PendingTxSession::check_pending`'s `WithdrawFromGasKey` scan only ever inspects `tx.transaction.actions()` directly and never unwraps a `Delegate`'s inner list [1](#0-0) , so any pending-queue admission decision made during that window is based on an undercounted `paid_from_gas_key`.

#[test]
fn test_reject_delegated_gas_key_withdraw_protocol_upgrade() {
    init_test_logger();

    if !ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(PROTOCOL_VERSION) {
        return;
    }

    let new_protocol = ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.protocol_version();
    let old_protocol = new_protocol - 1;
    assert!(
        old_protocol >= MIN_SUPPORTED_PROTOCOL_VERSION,
        "no supported protocol version still admits a delegated WithdrawFromGasKey, so there is \
         nothing left to test here - remove this test"
    );

    let sender = create_account_id("alice");
    let relayer = create_account_id("relayer");
    let epoch_length = 10;

    // Boundary "mm": "alice" lands on the first shard, "relayer" on the second,
    // so the delegate receipt crosses a shard on its way to the sender.
    let shard_layout = ShardLayout::multi_shard_custom(vec![create_account_id("mm")], 1);

    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .protocol_version(old_protocol)
        .protocol_upgrade_schedule(ProtocolUpgradeVotingSchedule::new_immediate(new_protocol))
        .epoch_length(epoch_length)
        .shard_layout(shard_layout)
        .add_user_account(&sender, Balance::from_near(1_000))
        .add_user_account(&relayer, Balance::from_near(1_000))
        .build();

    let gas_key: Signer =
        InMemorySigner::from_seed(sender.clone(), KeyType::ED25519, "gas_key").into();
    let add_key_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::AddKey(Box::new(AddKeyAction {
            public_key: gas_key.public_key(),
            access_key: AccessKey::gas_key_full_access(1),
        }))],
    );
    env.rpc_runner().run_tx(add_key_tx, Duration::seconds(10));

    let fund_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: gas_key.public_key(),
            deposit: Balance::from_near(10),
        }))],
    );
    env.rpc_runner().run_tx(fund_tx, Duration::seconds(10));

    // Before the upgrade the nested withdrawal is admitted and moves balance out
    // of the gas key, which is the hole this rule closes.
    assert_eq!(
        env.rpc_node().protocol_version_at_head(),
        old_protocol,
        "expected to start pre-upgrade"
    );
    let (_, balance_before) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
    let outcome = env
        .rpc_runner()
        .execute_tx(tx, Duration::seconds(10))
        .expect("delegated withdrawal admitted pre-upgrade");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::SuccessValue(_),
        "pre-upgrade delegated withdrawal should execute",
    );
    let (_, balance_after) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    assert_eq!(
        balance_after,
        balance_before.checked_sub(WITHDRAW_AMOUNT).unwrap(),
        "the nested withdrawal should have drained the gas key",
    );
