**Reasoning basis:** `NakamotoBlock`'s wire format is handled entirely by this repo's own `StacksMessageCodec` in `stacks-common/src/codec/mod.rs`, not by an external "serde" crate whose version could vary across node builds. `NakamotoBlock::consensus_deserialize` reads the header, then reads `txs: Vec<StacksTransaction>` via the generic `impl<T> StacksMessageCodec for Vec<T>` implementation, which calls `read_next_at_most` → `read_next_vec`. [1](#0-0) [2](#0-1) 

That length-prefix parsing (`read_next_vec`) reads the count as a fixed 4-byte `u32` (not a variable-width/ambiguous encoding), and then loops reading exactly that many items, propagating an `Err` on any short read or malformed item rather than silently truncating the count to zero: [3](#0-2) 

There is only a single implementation of this decoder in the codebase — there's no "lenient" vs. "strict" alternate decode path for `Vec<StacksTransaction>` inside `consensus_deserialize` for `NakamotoBlock`. A malformed length prefix does not get silently interpreted as zero by one build and as N>0 by another build of the *same* unmodified repo code; it produces a hard `CodecError` on both, since the length field is a fixed-size integer read via `u32::consensus_deserialize`, not a permissive/variable-length field with multiple valid interpretations.

Additionally, `consensus_deserialize` for `NakamotoBlock` independently recomputes the Merkle root over `txs` and compares it against `header.tx_merkle_root`, which would catch any accidental divergence in `txs` length/content before `validate_transactions_static` is ever reached: [4](#0-3) 

The premise of the question — "heterogeneous serde/codec versions across the fleet" causing `self.txs.is_empty()` to diverge between two builds for identical wire bytes — does not correspond to any actual alternate/lenient decoder present in this repository. This is a hypothetical supply-chain/dependency-version scenario explicitly excluded by the audit rules ("compromised dependencies" / non-reproducible issue outside this repo's own code), and no code path in `stacks-common`'s `StacksMessageCodec` or `NakamotoBlock::consensus_deserialize`/`validate_transactions_static` supports such divergence for identical input bytes under the actual, single implementation shipped in this repo.

fn read_next_vec<T: StacksMessageCodec + Sized, R: Read>(
    fd: &mut R,
    num_items: u32,
    max_items: u32,
) -> Result<Vec<T>, Error> {
    let len = u32::consensus_deserialize(fd)?;

    if max_items > 0 {
        if len > max_items {
            // too many items
            return Err(Error::DeserializeError(format!(
                "Array has too many items ({len} > {max_items})"
            )));
        }
    } else if len != num_items {
        // inexact item count
        return Err(Error::DeserializeError(format!(
            "Array has incorrect number of items ({len} != {num_items})"
        )));
    }

    if (mem::size_of::<T>() as u128) * (len as u128) > MAX_MESSAGE_LEN as u128 {
        return Err(Error::DeserializeError(format!(
            "Message occupies too many bytes (tried to allocate {}*{}={})",
            mem::size_of::<T>() as u128,
            len,
            (mem::size_of::<T>() as u128) * (len as u128)
        )));
    }

    let mut ret = Vec::with_capacity(len as usize);
    for _i in 0..len {
        let next_item = T::consensus_deserialize(fd)?;
        ret.push(next_item);
    }

    Ok(ret)
}

impl<T> StacksMessageCodec for Vec<T>
where
    T: StacksMessageCodec + Sized,
{
    fn consensus_serialize<W: Write>(&self, fd: &mut W) -> Result<(), Error> {
        let len = self.len() as u32;
        write_next(fd, &len)?;
        for item in self {
            write_next(fd, item)?;
        }
        Ok(())
    }

    fn consensus_deserialize<R: Read>(fd: &mut R) -> Result<Vec<T>, Error> {
        read_next_at_most::<R, T>(fd, u32::MAX)
    }
}
