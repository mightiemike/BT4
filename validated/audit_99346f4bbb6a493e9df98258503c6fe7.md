## Title
`ensure_match_transaction_info` in `TransactionOutput` silently skips checkpoint-hash validation, letting replay/verify tooling accept a divergent committed state root - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) is the integrity gate used by replay-verification tooling to confirm that a freshly re-executed `TransactionOutput` matches the historical, committed `TransactionInfo` before accepting it as correct. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that authenticate the state-tree/root committed at checkpoint boundaries. The code comment itself documents the gap: `"this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's replay_on_archive) can report a successful replay even when the authenticated position state root diverges from local execution."`

### Finding Description
`storage/db-tool/src/replay_on_archive.rs::execute_and_verify` (lines 388-406) re-executes historical transactions with `AptosVMBlockExecutor` and calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` as the sole correctness gate for that transaction. If this returns `Ok(())`, the tool treats the replay as verified and moves on; if it returns `Err`, the transaction is flagged as failed.

Looking at `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`):
- It compares `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`.
- It never reads or compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (V1), or `txn_info.position_state_checkpoint_hash()` (V1) against anything derived from the locally re-computed state tree.

Because `TransactionInfo` is the leaf object hashed into the transaction accumulator (see `execution/executor/src/workflow/do_ledger_update.rs::assemble_transaction_infos`, which builds `TransactionInfo` from `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` alongside `write_set_hash`/`event_root_hash`), the state-checkpoint hash is exactly the field that authenticates the Sparse-Merkle/Jellyfish state root at that version. Skipping it in `ensure_match_transaction_info` means the one function whose entire purpose is "does my local computation match the historically committed value" cannot detect a divergence in the committed state root — only in the write set and events that produced it.

This matters concretely because the executor computes `state_checkpoint_hash` from the persistent Merkle tree/state summary path (`execution/executor/src/workflow/do_state_checkpoint.rs`), which is a materially different and more complex code path than the one producing `write_set_hash` (a straight hash of the `WriteSet`). A bug or non-determinism specific to state-checkpoint hash computation, hot-state root computation, or (per the comment) the new "trading-native" position-state root — introduced anywhere in the checkpoint pipeline (`LedgerStateSummary::update`, `ProvablePositionStateSummary`, JMT restore paths, etc.) — would go completely undetected by the only tool built to catch this class of bug during replay, because the check that should catch it is missing by construction, not by accident of a passing test.

### Impact Explanation
This breaks the core "authenticated-response / proof-binding" invariant: replay-verify tooling is Aptos's mechanism for independently confirming that historically committed `TransactionInfo` — and therefore the transaction accumulator root and every proof built on top of it — actually reflects correct VM execution. By omitting `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` comparisons, a state root that was corrupted (via a bug in checkpoint/root computation, storage bug, or non-determinism) at commit time will pass `replay_on_archive` as "verified" even though the locally recomputed state tree does not match what was committed to the accumulator. This is a hard-fork-class detection failure: it directly undermines the operator/community's ability to catch state divergence via replay, which is one of the few backstops against an undetected chain split or silently corrupted historical state proof. It is scoped to the verification/tooling path rather than a live consensus-time exploit, so it does not itself corrupt state, but it removes the safety net that would otherwise catch such corruption, which is a high-severity gap in the proof-integrity story.

### Likelihood Explanation
The gap is unconditional and always present — `ensure_match_transaction_info` runs on every version replayed by `replay_on_archive` (and by `aptos-move/cli/src/commands.rs`, the other caller), and it always skips the checkpoint-hash fields. It is not gated behind a rare feature flag failure mode by itself; the trigger condition is any future or already-existing discrepancy in the checkpoint-hash computation (state root, hot-state root, or position-state root under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), at which point this verifier would fail to flag it. I could not fully verify from the index whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled on mainnet or the full definition/gating of the position-state path (the search results were truncated for `aptos_features.rs`), so I cannot state with certainty whether the position-root portion of this gap is presently reachable in production; the state/hot-state checkpoint hash omission, however, is unconditional and already active in the current code.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between the locally recomputed state/hot-state/position checkpoint roots (when available to the caller) and `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, following the same `ensure!(..., "{}: version:{}, ...")` pattern used for the other fields. Since `TransactionOutput` alone doesn't carry the state root, this likely requires threading the computed checkpoint hash(es) into `ensure_match_transaction_info` (or adding a companion check invoked by `replay_on_archive`) before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and any hot-state-root feature are relied upon in production, and before removing the `TODO(trading-native)` comment.

### Proof of Concept
No dynamic PoC was run (index-only analysis). The static proof is the code path itself:
1. `execution/executor/src/workflow/do_ledger_update.rs:95-121` builds `TransactionInfo` including `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` from the executor's checkpoint pipeline.
2. `storage/db-tool/src/replay_on_archive.rs:392-397` re-executes and calls `ensure_match_transaction_info` as the only correctness gate.
3. `types/src/transaction/mod.rs:2139-2204` implements that gate and, per its own inline comment (lines 2197-2202), knowingly omits comparing the checkpoint hashes — so any divergence confined to those fields (i.e., a corrupted/incorrect state root that nonetheless produces the same write-set hash or a differing write set not caught because state comparisons are skipped) is not detected, and `verify()` returns `Ok(None)` (success) for that chunk.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
