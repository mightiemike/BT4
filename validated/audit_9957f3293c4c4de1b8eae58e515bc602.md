### Title
Wallet contract `has_in_flight_tx` can be permanently stuck by out-of-gas in `rlp_execute_callback` - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Nouns-Builder bug is that mint() is wrapped in a catch-all `catch {}` that swallows out-of-gas failures (enabled by EIP-150's 63/64 gas-forwarding rule), setting a `paused` flag that can only be cleared by governance — an unprivileged caller can therefore force a permanent halt. The nearcore analog is the deterministic/global `WalletContract`, whose `rlp_execute` / `rlp_execute_callback` state machine relies on a boolean flag, `has_in_flight_tx`, that is only reset to `false` inside the callback. Because NEAR fully reverts all state writes of a failed/aborted receipt (including out-of-gas panics), an out-of-gas failure in the callback leaves `has_in_flight_tx` stuck at `true` forever, with no code path to reset it — permanently freezing the wallet contract for the account holder, analogous to the forced "pause".

### Finding Description
`rlp_execute` refuses to start a new transaction whenever `self.has_in_flight_tx` is `true`: [1](#0-0) 

Every code path that successfully returns a `Promise` from `rlp_execute`/`inner_rlp_execute` sets `self.has_in_flight_tx = true` before scheduling the `.then(ext.rlp_execute_callback(...))` continuation: [2](#0-1) 

The only place that clears the flag is the very first line of `rlp_execute_callback`: [3](#0-2) 

This callback is scheduled with a small, hard-coded static gas budget (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, or slightly larger variants that add a fixed sub-callback gas amount), independent of the size/complexity of the return value produced by the target contract that was called: [4](#0-3) [5](#0-4) 

`target` is a caller-controlled `AccountId` (an arbitrary contract, e.g. via the default `FunctionCall` action branch that calls `action_to_promise(target, action)`), so the predecessor/relayer fully controls which contract is invoked and — if they also control or influence that contract — how large a return value is produced. `rlp_execute_callback` reads `env::promise_result(0)` and, on `PromiseResult::Successful(value)`, copies `value` into `ExecuteResponse.success_value` and serializes/returns it, an operation whose gas cost scales with the size of `value`. If the returned payload is large enough that reading/copying/serializing it exceeds the fixed `RLP_EXECUTE_CALLBACK_GAS` budget, the callback receipt fails with `GasExceeded` (equivalent to EVM out-of-gas). NEAR guarantees no partial state persists for a failed/panicking function call — the `self.has_in_flight_tx = false` write at the top of the function is discarded along with everything else in that outcome.

Because `has_in_flight_tx` was already durably set to `true` by the prior (successful) receipt that created the promise, and the only reset path panics before commit, the flag remains `true` indefinitely. Every subsequent call to `rlp_execute` for that account will be rejected with "transaction already in progress," with no governance/administrative function anywhere in the contract to clear `has_in_flight_tx`. This is a caller-triggered, permanent denial of service against the account's wallet contract, directly analogous to the reported "forceful pause."

### Impact Explanation
This freezes the deterministic/eth-implicit wallet account permanently: the account owner can no longer submit any RLP-encoded transaction through this contract, since `rlp_execute` unconditionally short-circuits while `has_in_flight_tx == true`, and there is no recovery method in the contract to clear the flag. Because the account, target, and the exact size of the return payload are all attacker/relayer-influenced, a malicious relayer (or malicious/uncooperative target contract) can deliberately trigger this by directing the wallet through a target whose returned value is large enough to exceed the fixed callback gas budget, causing irrecoverable state lock — a transaction-triggered halt with no self-healing path.

### Likelihood Explanation
Reachable directly by any unprivileged account that can submit a transaction executing `rlp_execute` on the wallet contract, or by any relayer using the account's access key; requires only choosing a `target`/method whose returned value is large enough to blow the fixed 5 Tgas callback budget, which is well within attacker control since `target` and the invoked method are attacker/relayer-specified in the general `FunctionCall` action path.

### Recommendation
- Reset `has_in_flight_tx` in a way that survives callback failures, e.g. by moving the reset into the scheduling logic itself (clear it at the very start using a separate always-succeeding low-gas receipt or a `#[private]` fallback that fires regardless of the primary callback's success), or use a state model that does not require a follow-up receipt to reset an in-progress flag.
- Bound the gas actually consumed by `rlp_execute_callback` to be independent of the size of the returned payload (e.g., truncate/store return values by reference rather than copying full payload, or ensure gas allocated is proportional to `promise_result` size, similar to `gas_weight` remaining-gas allocation used elsewhere in the codebase, e.g. `promise_batch_action_function_call_weight`).
- Add an escape hatch (callable without requiring `has_in_flight_tx == false`) that lets the account owner manually clear a stuck `has_in_flight_tx` flag after some form of validation (e.g., verifying no genuinely pending promise exists).

### Proof of Concept
1. Attacker/relayer submits an RLP transaction to `rlp_execute` with `target` pointing at a contract (deployed or already existing) whose invoked method returns a very large successful result (e.g., large bytes/string return value close to the max return-value size allowed by the protocol).
2. `inner_rlp_execute` builds `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))` with `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) statically attached to the callback: [6](#0-5) 
3. `rlp_execute` sets `has_in_flight_tx = true` and returns the promise: [7](#0-6) 
4. The target call succeeds and produces the large `PromiseResult::Successful(value)`.
5. `rlp_execute_callback` executes: it sets `self.has_in_flight_tx = false` in-memory, then attempts to copy `value` into `ExecuteResponse.success_value` and return it, exceeding the 5 Tgas budget and aborting with `GasExceeded`.
6. Because the callback receipt failed, none of its state changes (including the `has_in_flight_tx = false` write) are committed; `has_in_flight_tx` remains `true` in persisted contract state.
7. All future calls to `rlp_execute` immediately fail with "transaction already in progress, please try again later," permanently, since no other function ever clears the flag: [8](#0-7) 

Note: I was unable to fully verify from the index the exact maximum size of a promise return value / the precise per-byte gas cost constants that would confirm the minimum payload size needed to exceed 5 Tgas (the config snapshot files listing `max_length_returned_data` and per-byte host costs were only partially retrievable in this session). A Devin session with full repo access would be needed to compute the exact byte threshold and build a concrete numeric PoC/test.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
