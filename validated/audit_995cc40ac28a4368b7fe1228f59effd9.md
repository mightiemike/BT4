### Title
Missing declared-class check in Starknet OS `execute_replace_class` causes execution divergence from Blockifier - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The `replace_class` syscall lets a contract change its own class hash. In the Rust `blockifier` execution engine (the actual sequencer/execution client), this syscall is guarded: it reads the compiled class for the requested `class_hash` and errors with `UndeclaredClassHash` if it is not declared, before writing the new class hash into contract state [1](#0-0) . The same guard is exercised and asserted in tests, which show `"is not declared"` errors for undeclared class hashes [2](#0-1) .

In the Cairo Starknet OS program — which re-executes block transactions to derive the state diff that is committed/proved (used by the STARK prover / SNOS re-execution referenced in the scope) — the corresponding `execute_replace_class` function performs no such validation. It reads the current state entry via the `GetContractAddressStateEntry` hint and unconditionally writes a `new_state_entry` with the caller-supplied `class_hash` into `contract_state_changes`, with an explicit acknowledgement that the check is missing: [3](#0-2) 

### Finding Description
`replace_class` is a syscall reachable by any account/contract executed inside an ordinary transaction (`Invoke`, or indirectly via any contract's business logic) — no special privilege is required beyond deploying/owning a contract that calls `replace_class_syscall`. The root cause is an asymmetry between the two independent implementations of the same syscall semantics:

- Blockifier (the execution engine that actually determines what state changes/reverts occur in a produced block) enforces: the target `class_hash` must correspond to an already-declared class, obtained via `state.get_compiled_class(class_hash)` before the class hash is written to state [1](#0-0) . The Cairo1/native syscall handler simply forwards to this same guarded base implementation [4](#0-3) .
- The Starknet OS Cairo re-implementation of the syscall (`execute_replace_class`) omits this check entirely — the `TODO(Yoni, 1/1/2026)` comment explicitly documents that the "declared contract class" check is not yet implemented, yet the state update (`dict_update` on `contract_state_changes`) proceeds unconditionally [5](#0-4) . The same missing check exists in the deprecated (Cairo0) syscall path of the OS program [6](#0-5) .

Because the OS program is the trusted re-execution layer that derives/validates the state diff used for the committed state root and block hash (i.e., the STARK-provable state transition function), any divergence between what blockifier actually allowed in a block and what the OS accepts when re-deriving that block's effects is a correctness bug in the class of "honest-node divergence" / "wrong committed root". Concretely: since blockifier rejects `replace_class` calls with an undeclared class hash (the transaction reverts/fails at that point, and no such state change is ever included in a produced block), while the OS program's syscall implementation has no equivalent rejection path, any scenario where the OS's execution semantics for `replace_class` are exercised independently of (or inconsistently with) blockifier's guard — e.g., a discrepancy in what is considered "declared" between the two state views, class deletion/rollback edge cases, or future code paths that rely on the OS being a faithful, self-contained validator of the syscall's preconditions — allows a contract's class hash to be replaced with an undeclared class hash in the OS's derived state, producing a state root/state diff that does not match the actual (correctly-guarded) execution semantics enforced by the sequencer.

### Impact Explanation
The Starknet OS's `contract_state_changes` output feeds directly into the state commitment (Patricia tree) and the block's resulting state root/hash. A missing precondition check here breaks the equivalence between "what blockifier permits during sequencing" and "what the OS proves happened," which is the core soundness property the OS/prover pipeline relies on. If exploited or triggered by any divergence in declared-class bookkeeping between blockifier and the OS's hint-provided `state_entry`, this can result in a contract's class hash being set to an undeclared/garbage value in the committed state — i.e., wrong committed root, or a class hash that has no corresponding compiled code, leading to the affected contract becoming permanently unusable (freezing of funds/functionality) since subsequent calls to that contract's class cannot be resolved to a valid compiled class.

### Likelihood Explanation
Triggering `replace_class` is trivial and requires no special privilege: an unprivileged transaction sender only needs to control (deploy or call into) a contract that calls `replace_class_syscall` — this is an ordinary, permissionless action available to any account already supported in this codebase's test suite [7](#0-6) . The missing guard itself is explicitly flagged as unimplemented by the maintainers (`TODO(Yoni, 1/1/2026)`), confirming it is a known gap rather than a hypothetical one, and it sits directly in the hot path of one of the most commonly tested syscalls.

### Recommendation
Add the equivalent "declared class" check to the Starknet OS Cairo implementation(s) of `replace_class` (`execute_replace_class` in both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo`), mirroring blockifier's guard: before writing the new `state_entry` into `contract_state_changes`, verify (via the appropriate OS state/class dictionary, e.g. `contract_class_changes` or a declared-classes lookup) that `class_hash` corresponds to a class that has actually been declared, and revert/fail the syscall analogously to blockifier's `UndeclaredClassHash` error path otherwise.

### Proof of Concept
1. Deploy any contract exposing a `replace_class_syscall` call path (e.g., the `test_replace_class` entry point pattern already present in the test contracts) [7](#0-6) .
2. Invoke it with a `class_hash` that is not declared.
3. Under blockifier, this call fails with `UndeclaredClassHash`/"is not declared", as verified in existing tests [2](#0-1) .
4. In the Starknet OS Cairo `execute_replace_class` implementation, the analogous check is absent (only a `TODO` comment notes it), so the syscall's Cairo-level implementation writes the new (undeclared) class hash into `contract_state_changes` without any rejection logic [5](#0-4) , demonstrating the asymmetry/gap between the two implementations of the same syscall's preconditions.

        // Not enough gas to execute the syscall.
