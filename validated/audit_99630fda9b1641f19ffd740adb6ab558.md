## Analysis

The reported bug class is: **a permissionless function that mutates a shared, limited on-chain value which another pending transaction's fixed/exact amount check depends on, allowing a griefer to front-run and force a legitimate transaction to revert.**

The closest reachable analog in `java-tron` is `ExchangeTransactionActuator`, which lets *any* account trade against a shared bancor-style liquidity pool (`ExchangeCapsule`), where the resulting output is checked against a caller-specified `expected` minimum [1](#0-0) . Because the pool balances (`firstTokenBalance`/`secondTokenBalance`) are a globally shared, mutable resource that anyone can alter via their own `ExchangeTransactionContract`, an attacker who observes a pending victim transaction in the mempool can front-run it with a small trade against the same `exchange_id`, shifting the AMM rate just enough that the victim's fixed `quant`/`expected` combination computed via `exchangeCapsule.transaction(...)` [2](#0-1)  now yields less than `tokenExpected`, causing `ContractValidateException("token required must greater than expected")` [1](#0-0) .

### Title
Permissionless front-running of shared Exchange pool state causes griefing/DoS of pending `ExchangeTransactionContract` broadcasts - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
`ExchangeTransactionActuator` is fully permissionless: any account may submit an `ExchangeTransactionContract` against any `exchange_id`, mutating the shared pool balances used by the bancor-style AMM math in `ExchangeCapsule.transaction()`. A pending transaction that specifies a fixed `quant`/`expected` pair is validated against the *current* pool state at execution time, so a third party can always shift that state first.

### Finding Description
The validate path computes the expected output using the live pool state and reverts if it falls below the caller-supplied minimum: [3](#0-2) 

Because `ExchangeTransactionContract` has no owner/permission restriction beyond `DecodeUtil.addressValid` and sufficient balance [4](#0-3) , and the exchange pool (`ExchangeStore`/`ExchangeV2Store`) is a single shared resource keyed only by `exchange_id`, any address can broadcast a transaction that alters `firstTokenBalance`/`secondTokenBalance` ahead of a victim's already-broadcast transaction. This is analogous to the CSModule case where a permissionless `compensateELRewardsStealingPenalty()` call could reduce a shared "locked" value out from under a legitimate caller's exact-amount check (`CSBondLock` requiring compensation "no more than what was locked"), forcing the legitimate transaction to revert.

### Impact Explanation
A griefer monitoring the mempool/pending-transaction pool can repeatedly front-run any observed `ExchangeTransactionContract` with a minimal counter-trade, deliberately moving the pool ratio so the victim's `expected` check fails and the transaction reverts with `ContractValidateException`. This denies service to legitimate traders using this exchange mechanism, forcing repeated re-submission (each incurring bandwidth/energy cost) and potentially discouraging use of the on-chain exchange feature entirely for the targeted trading pair.

### Likelihood Explanation
Likelihood is moderate: the attacker needs visibility into the pending transaction pool (readily available via any full node) and must be willing to execute their own trade against the pool (which does carry real economic exposure/slippage cost to the attacker, unlike CSModule's trivial "1 share" compensation). This makes it more costly than the original report's griefing vector but still a concretely reachable, permissionless DoS pattern reachable from ordinary broadcast transactions.

### Recommendation
Consider allowing callers to specify additional safeguards (e.g., a maximum acceptable pool-state deviation, or transaction validity tied to a specific expected pool snapshot/nonce) so that a legitimate trade cannot be trivially invalidated by third-party front-running. At minimum, document this front-running/griefing risk for users and tooling that rely on `ExchangeTransactionContract`'s `expected` field as a safety check.

### Proof of Concept
1. Victim broadcasts `ExchangeTransactionContract{exchange_id=X, token_id=A, quant=Q, expected=E}` where `E` is computed against current pool balances `(balA, balB)`.
2. Attacker observes this pending transaction and immediately broadcasts their own `ExchangeTransactionContract{exchange_id=X, token_id=A, quant=q_small}` with a lower/looser `expected`.
3. If the attacker's transaction is included first (e.g., higher fee/priority or same block ordering), `exchangeCapsule.transaction()` updates `balA`/`balB` [5](#0-4) .
4. The victim's transaction is then re-validated against the new pool state; `anotherTokenQuant` computed from the mutated balances is now `< E`, and `doValidate()` throws `"token required must greater than expected"` [1](#0-0) , causing the victim's transaction to fail/revert.
5. The attacker can repeat this against any newly re-submitted victim transaction, griefing the victim indefinitely at the cost of the attacker's own small trades.
