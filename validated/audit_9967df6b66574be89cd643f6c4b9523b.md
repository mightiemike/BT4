### Title
Unbounded per-key prefix scan in `getV2Index`/`getWithPrefix` allows cheap TRX-cost griefing to inflate victim query latency - ([File: framework/src/main/java/org/tron/core/services/http/GetDelegatedResourceAccountIndexV2Servlet.java])

### Summary
An attacker can broadcast many low-cost `DelegateResourceContract` transactions (minimum 1 TRX delegated balance each) naming a single victim as receiver, causing `DelegatedResourceAccountIndexStore.delegateV2` to write one `V2_TO_PREFIX+receiver+owner` key per transaction into the victim's index namespace. Any client can then call `/wallet/getdelegatedresourceaccountindexv2` for that victim, which triggers `DelegatedResourceAccountIndexStore.getWithPrefix` to run a full prefix scan and in-memory sort over all of the victim's index entries, whose cost scales with the number of attacker-controlled entries.

### Finding Description
`DelegateResourceActuator.delegateResource` (actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java:282-325) calls `DelegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, timestamp)` unconditionally for every successful delegate call, writing a `V2_TO_PREFIX+receiver+owner` key [1](#0-0) . `validate()` only checks that `delegateBalance >= TRX_PRECISION` (1 TRX) and that the owner has sufficient frozen V2 balance [2](#0-1)  — there is no limit on the number of distinct receivers a single owner can target, and the receiver never has to sign or consent to being delegated to; `receiverCapsule` merely needs to exist and not be a Contract account [3](#0-2) [4](#0-3) .

The read path `GetDelegatedResourceAccountIndexV2Servlet.fillResponse` → `Wallet.getDelegatedResourceAccountIndexV2` → `DelegatedResourceAccountIndexStore.getV2Index` → `getWithPrefix` performs `this.prefixQuery(key)` over `V2_TO_PREFIX+address` and `V2_FROM_PREFIX+address`, collects all matching entries into an `ArrayList`, and sorts them by timestamp with `Comparator.comparing` [5](#0-4) . There is no limit on the number of entries returned or scanned; the cost of this single GET request is O(N log N) in the number of index entries under that key prefix, where N is fully attacker-controlled.

`getDelegatedResourceAccountIndexV2` accepts any well-formed 20-byte address with no ownership/signature check [6](#0-5) , and `RateLimiterServlet` only applies a generic QPS-based rate limiter, not a request-cost-aware or key-cardinality-aware limiter [7](#0-6) . Thus a fixed, small per-request rate limit does not bound the aggregate CPU/DB work per request once N grows large.

### Impact Explanation
This is a DoS-via-RPC-API concern: repeated GETs against a victim address with an artificially inflated index (tens of thousands of entries) will consume disproportionate CPU/DB iteration and memory (ArrayList + sort) per request compared to the attacker's cost to create those entries. This can degrade full node responsiveness to `getdelegatedresourceaccountindexv2` (and equally `getdelegatedresourceaccountindex`, which shares `getWithPrefix` for V1 keys) for the targeted address, and repeated large queries could contribute to elevated latency/resource pressure on public API nodes. It does not corrupt state, doesn't touch other accounts' funds, and doesn't cause consensus divergence — the actuator logic itself is deterministic and correctly metered on-chain (fee is 0 by design for delegate, gated by real TRX-frozen-balance requirements), so the write side is not "free" (attacker must actually freeze and delegate ≥1 TRX per receiver-touching transaction, and pay bandwidth/energy for each transaction). The primary exploitable effect is asymmetric read-side latency/resource cost, i.e., an RPC-API DoS amplification vector, not an unauthorized state change or asset loss.

### Likelihood Explanation
Preconditions: `dynamicStore.supportDR() == true` (delegate resource feature enabled, which is standard on current mainnet/testnet) and the attacker must hold enough frozen V2 balance to cover 1 TRX per unique receiver (N receivers require N TRX frozen, i.e., linear cost to the attacker, though the underlying principal is not destroyed — it's just locked/delegated and technically recoverable via undelegate). Each `DelegateResourceContract` transaction must still be broadcast and consumes normal bandwidth/energy and is subject to per-transaction TRX-freezing economics, so building 50k unique receiver entries requires funding roughly 50k TRX (recoverable) plus 50k separate transactions' bandwidth cost — a real but bounded cost, not free. The read-side abuse (repeated GETs) is unauthenticated and can be repeated cheaply by anyone once the index is inflated, since `getdelegatedresourceaccountindexv2` takes only an address parameter with no auth. This makes the vulnerability moderately likely to be exploitable primarily as a "pre-poison then repeatedly query" pattern rather than a pure zero-cost attack.

### Recommendation
- Add a configurable cap on the number of index entries returned/scanned by `getWithPrefix`/`getV2Index` (e.g., pagination or a hard maximum with a `“total truncated”` indicator), similar to bounded-pagination patterns used elsewhere in the codebase (e.g., proposal/witness paginated list servlets).
- Consider limiting the number of distinct delegate receivers/owners indexable per account, or moving to a paginated/streaming DB read that avoids loading and sorting the full key set into memory in `getWithPrefix`.
- Alternatively, cache/memoize the sorted result and only recompute incrementally on writes, rather than re-scanning and re-sorting on every read.

### Proof of Concept
```java
// Pseudo-PoC (JUnit) illustrating scaling behavior of getV2Index under attacker-controlled fan-in.
@Test
public void testGetV2IndexScalesWithFanIn() {
  byte[] victim = ByteArray.fromHexString(RECEIVER_ADDRESS);

  // Baseline: victim has 1 index entry
  long t0 = System.nanoTime();
  dbManager.getDelegatedResourceAccountIndexStore().getV2Index(victim);
  long baseline = System.nanoTime() - t0;

  // Simulate N attacker-driven delegateV2 calls with distinct synthetic owner addresses
  DelegatedResourceAccountIndexStore store = dbManager.getDelegatedResourceAccountIndexStore();
  for (int i = 0; i < 50_000; i++) {
    byte[] owner = ByteArray.fromHexString(String.format("41%038x", i)); // distinct 21-byte addr each
    store.delegateV2(owner, victim, i);
  }

  long t1 = System.nanoTime();
  Protocol.DelegatedResourceAccountIndex idx = store.getV2Index(victim).getInstance();
  long inflated = System.nanoTime() - t1;

  Assert.assertEquals(50_000, idx.getFromAccountsCount());
  // Demonstrates superlinear latency growth vs. baseline with no attacker fee compensation
  Assert.assertTrue(inflated > baseline * 1000);
}
```
Note: actual attacker path uses N real `DelegateResourceContract` broadcasts (each with `receiverAddress = victim`, `balance = 1_000_000` sun, distinct funded owner accounts) rather than direct store calls; the direct-store variant above isolates and measures the read-side cost growth in `getWithPrefix`, which is the actual root cause identified in `DelegatedResourceAccountIndexStore.java:118-138`.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndexV2(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule = chainBaseManager
        .getDelegatedResourceAccountIndexStore().getV2Index(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }

  @Override
  protected void service(HttpServletRequest req, HttpServletResponse resp)
      throws ServletException, IOException {

    RuntimeData runtimeData = new RuntimeData(req);
    IRateLimiter rateLimiter = container.get(KEY_PREFIX_HTTP, getClass().getSimpleName());

    // Check per-endpoint first to avoid consuming global IP/QPS quota for requests
    // that would be rejected by the per-endpoint limiter anyway. acquirePermit()
    // chooses blocking or non-blocking semantics based on rate.limiter.apiNonBlocking.
    boolean perEndpointAcquired = rateLimiter == null || rateLimiter.acquirePermit(runtimeData);
    boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);

    String contextPath = req.getContextPath();
    String url = Strings.isNullOrEmpty(req.getServletPath())
        ? MetricLabels.UNDEFINED : contextPath + req.getServletPath();
    // int64_as_string is honored only on GET requests (URL query). POST is intentionally
    // unsupported because reading the body here would consume request.getReader() and
    // break downstream servlets that read it themselves.
    if ("GET".equalsIgnoreCase(req.getMethod())) {
      JsonFormat.setInt64AsString(Util.getInt64AsString(req));
    }
    try {
      resp.setContentType("application/json; charset=utf-8");

      if (acquireResource) {
        Histogram.Timer requestTimer = Metrics.histogramStartTimer(
            MetricKeys.Histogram.HTTP_SERVICE_LATENCY, url);
        super.service(req, resp);
        Metrics.histogramObserve(requestTimer);
      } else {
        resp.getWriter()
            .println(Util.printErrorMsg(new IllegalAccessException("lack of computing resources")));
      }
    } catch (ServletException | IOException | BadMessageException e) {
      throw e;
    } catch (Exception unexpected) {
      logger.error("Http Api {}, Method:{}. Error：", url, req.getMethod(), unexpected);
    } finally {
      // CRITICAL: this clear pairs with the setInt64AsString call above. Removing it
      // will leak int64_as_string state across requests on reused Tomcat threads,
      // producing intermittent quoted/unquoted output that is very hard to debug.
      JsonFormat.clearInt64AsString();
      // Release whenever the per-endpoint permit was acquired (covers both the normal
      // completion path and the case where GlobalRateLimiter rejected the request).
      if (rateLimiter instanceof IPreemptibleRateLimiter && perEndpointAcquired) {
        ((IPreemptibleRateLimiter) rateLimiter).release();
      }
    }
  }
