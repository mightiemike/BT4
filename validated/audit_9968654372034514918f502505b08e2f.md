### Title
Webhook HMAC signature does not cover the shop-domain header, allowing cross-tenant webhook forgery - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The Foundation report shows a class of bug where a value that determines *who receives funds/authority* (the royalty recipient) is taken from data that is not bound to the transaction it is supposed to protect, letting the seller/creator relationship be spoofed. The equivalent pattern in `shopify-app-js` is in the webhook HMAC validation path: the signature only authenticates the raw body, while the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header — which is later used to select *which tenant's* offline session and access token the request acts on — is never included in the signed data.

### Finding Description
`validateHmacFromRequestFactory` computes and checks the HMAC exclusively over `rawBody`: [1](#0-0) 

The domain (and topic, webhook id, etc.) headers are read afterward, completely outside the HMAC computation, in `checkWebhooksHeaders`/`checkEventsHeaders`: [2](#0-1) 

The resulting `domain` field is then trusted downstream to load the offline session/access token for that shop and construct an authenticated Admin client for the webhook handler: [3](#0-2) [4](#0-3) 

Because the app's client secret (`apiSecretKey`) is the same for every shop that has installed the app, any party who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on their own store and receiving a genuine Shopify webhook for that store) can replay that exact `rawBody`/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop that also has the app installed. `validateHmacFromRequestFactory` will still report `valid: true` because it never checks the domain header against anything, and `validate()` will happily report `check.domain = <victim shop>`. This causes `ensureValidOfflineSession` to load the **victim's** offline session/access token and hand it, together with the attacker-crafted payload, to the app's webhook business logic. This is the same root-cause shape as the Foundation bug: a value used to decide "whose funds/session/authority this transaction affects" is taken from unauthenticated, attacker-controllable data instead of being cryptographically bound to the authenticated request.

### Impact Explanation
An attacker who is a legitimate merchant of the app (a normal, unprivileged actor with respect to any other merchant) can forge webhook deliveries that the SDK will accept as coming from a different, victim merchant's shop. Any app webhook handler that trusts `shop`/`domain` from the validated webhook context (which is the documented, intended usage pattern of this SDK) will then execute attacker-controlled business logic using the victim's offline session and Admin API access token — e.g., triggering data mutations, calling `app/uninstalled` cleanup against a live victim shop, or processing crafted order/customer payloads under the victim's session context. This is a cross-tenant authorization bypass.

### Likelihood Explanation
Reachability requires only: (1) the attacker installs the app on a shop they control (or otherwise obtains one valid signed webhook body/HMAC combination for any topic), and (2) a victim shop that also has the app installed and an active offline session in storage. No secrets need to leak and no privileged actor is required — this is reachable from a single, unprivileged merchant via a plain HTTP POST to the app's public webhook endpoint. The main mitigating factor is that many webhook handlers additionally re-fetch data via Admin API using the resolved shop's token rather than fully trusting body contents, which can reduce (but not eliminate) impact depending on the app's own webhook handler implementation.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the authenticated portion of the webhook check instead of treating it as free-form, unauthenticated header data:
- Include the shop domain header (or an equivalent canonicalized value) as part of the HMAC input, or
- After computing a syntactically valid HMAC, cross-check the resolved `domain` against a shop that is known to have produced that specific webhook subscription (e.g., verify webhook id ownership recorded at registration time) before using it to select a session, or
- At minimum, document and enforce that webhook handlers must not assume `domain` uniquely authenticates the sender beyond "some shop using this app secret sent this exact body," and require handlers to independently verify shop-specific state before performing sensitive mutations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify send a legitimate webhook (e.g., `orders/create`) with attacker-controlled order content to the app's webhook endpoint. Shopify computes: `hmac = HMAC-SHA256(apiSecretKey, rawBody)` and sends header `X-Shopify-Hmac-Sha256: <hmac>` along with `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures this exact `rawBody` and `hmac` value.
3. Attacker replays the same POST to the app's webhook endpoint, keeping `rawBody` and `X-Shopify-Hmac-Sha256` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `validateHmacFromRequestFactory` recomputes the HMAC over the (unchanged) `rawBody` and finds it matches — validation succeeds, per [1](#0-0) .
5. `validate()` returns `domain: 'victim-shop.myshopify.com'`, and `authenticate()` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's real offline session/access token and passing attacker-controlled `payload` to the app's webhook handler under that session, per [5](#0-4) .

Note: I was unable to find any additional binding of `domain` to the signature or any webhook-id-to-shop ownership check elsewhere in the indexed code; if such a check exists in a file outside the index, that would mitigate this finding. Given index size limits, a full-repo review via a Devin session would be needed to conclusively rule out such a check elsewhere in the codebase.

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
