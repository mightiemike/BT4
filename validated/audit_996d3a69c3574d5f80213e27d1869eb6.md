### Title
Panic via unconditional `.expect()` on unset Secp EC-point segment in `secp256k1_add`/`secp256r1_add`/`secp256k1_mul`/`secp256r1_mul` syscalls - ([File: crates/blockifier/src/execution/syscalls/syscall_executor.rs])

### Summary
The blockifier's default `SyscallExecutor` implementations for the `secp256k1_add`, `secp256k1_mul`, `secp256r1_add`, and `secp256r1_mul` syscalls unconditionally unwrap the shared `Option<Relocatable>` "secp points segment base" via `.expect("Secp segment must be set.")` **before** validating that the operand EC points actually exist. Because the segment base is only initialized lazily (inside `allocate_point`, called from `secp_new`/`secp_get_point_from_x`), a contract that invokes `secp256k1_add_syscall`/`secp256k1_mul_syscall`/`secp256r1_add_syscall`/`secp256r1_mul_syscall` as its *first* Secp-related syscall — without a prior `secp256k1_new_syscall`/`secp256k1_get_point_from_x_syscall` in the same execution — causes the `Option` to still be `None`, triggering the `.expect()` panic. This mirrors the reported Dhara FTL bug class: an error/optional value that a caller-controlled code path can leave unset is dereferenced/unwrapped unconditionally instead of being routed through a safe/checked path.

The segment base (`secp_points_segment_base` / the field returned by `get_secpk1_hint_processor_and_base`/`get_secpr1_hint_processor_and_base`) is only ever populated inside `allocate_point`, which is reached solely through `secp_new` or `secp_get_point_from_x`: [6](#0-5) 

The field starts as `None` for every new call/transaction execution context (it is a struct field with no non-`None` default), e.g. in `SyscallHintProcessor`: [7](#0-6) 

Because `secp256k1_add_syscall`, `secp256k1_mul_syscall`, `secp256r1_add_syscall`, and `secp256r1_mul_syscall` are ordinary Cairo1 syscalls callable directly by any deployed/declared contract (see feature-contract usage of `secp256k1_add_syscall`/`secp256k1_mul_syscall` without a preceding `_new_syscall` call being architecturally prevented), a contract can invoke `secp256k1_add_syscall(p0, p1)` (with arbitrary, even garbage, `Secp256k1Point` handles) as the very first Secp operation in a call. This reaches `secp256k1_add`'s `.expect("Secp segment must be set.")` while `secp_points_segment_base` is still `None`, causing an unconditional Rust panic during transaction execution — exactly analogous to the Dhara driver writing through a NULL pointer unconditionally instead of using a NULL-safe helper.

### Impact Explanation
A panic raised deep inside the blockifier's syscall execution path (invoked from `execute_syscall`/`execute_next_syscall`, the core per-transaction VM hint dispatch) is not a `Result`-based recoverable error — it unwinds the Rust call stack. Unless every call site up through block building/batching wraps transaction execution in `catch_unwind` (which is not the general convention for this hot path), this crashes the executing sequencer node/thread while processing a single, cheaply-constructed transaction. Because this is reachable from an ordinary invoke transaction (no special privileges required — any account can call an arbitrary contract that issues the syscall, or deploy such a contract itself), this is a network-availability issue: a single malicious transaction can crash the node executing it, and if propagated/replayed by other honest sequencers, can repeatedly crash any node that attempts to execute or re-execute the block/transaction (including in Starknet OS re-execution, since `SnosHintProcessor` shares the identical unguarded pattern via `get_secpk1_hint_processor_and_base`/`get_secpr1_hint_processor_and_base`, per `crates/starknet_os/src/hint_processor/snos_syscall_executor.rs:123-143`). This matches "a network unable to confirm new transactions" impact class.

### Likelihood Explanation
High reachability: no special contract state, no privileged caller, and no rare flash-medium fault condition (unlike the original CVE) is required — merely calling the syscall in the "wrong order" (add/mul before new/get_point_from_x) within a single call context, which is trivially achievable by any user-deployed Cairo1 contract issuing `starknet::secp256k1::secp256k1_add_syscall` directly.

### Recommendation
Route the segment-base access through a safe, self-initializing path instead of an unconditional `.expect()`:
- Change `secp256k1_add`/`secp256k1_mul`/`secp256r1_add`/`secp256r1_mul` to call `secp_processor.secp_add`/`secp_mul` with the raw `&mut Option<Relocatable>` (as `secp_get_point_from_x`/`secp_new` already do), letting `allocate_point` lazily initialize the segment if needed — but only after `get_point_by_ptr` has confirmed the operand points exist, returning a proper `SyscallExecutorBaseError::InvalidSyscallInput` when they don't.
- Alternatively, validate operand point existence first (returning an execution-reverting error) before touching the segment-base option at all, eliminating any code path where `.expect()` is reached with `None`.
- Apply the same fix symmetrically in `crates/starknet_os/src/hint_processor/snos_syscall_executor.rs`.

### Proof of Concept
1. Deploy a Cairo1 contract with an external entry point that calls `starknet::secp256k1::secp256k1_add_syscall(p0, p1)` (or `secp256k1_mul_syscall`) as the *first* operation, using any placeholder `Secp256k1Point` values (obtained e.g. by transmuting/forging a point handle, or by using a point returned from `secp256k1_get_point_from_x_syscall` in a *separate, prior* transaction/call context so the segment-base field is fresh/`None` in the current context).
2. Submit an ordinary `INVOKE` transaction calling this entry point.
3. During blockifier execution, `SyscallExecutor::secp256k1_add` (or `_mul`/`secp256r1_*`) is dispatched; `get_secpk1_hint_processor_and_base` returns `secp_points_segment_base == None` because no `secp_new`/`secp_get_point_from_x` has run in this context; `optional_secp_segment_base.expect("Secp segment must be set.")` panics, crashing the executing node process/thread on a single unprivileged transaction.

```rust
    pub fn secp_add(
        &mut self,
        request: SecpAddRequest,
        vm: &mut VirtualMachine,
        points_segment_base: Relocatable,
        id: usize,
    ) -> SyscallBaseResult<SecpAddResponse> {
        let lhs = self.get_point_by_ptr(request.lhs_ptr)?;
        let rhs = self.get_point_by_ptr(request.rhs_ptr)?;
        let result = *lhs + *rhs;
        let ec_point_ptr =
            self.allocate_point(result.into(), vm, &mut Some(points_segment_base), id)?;
        Ok(SecpOpRespone { ec_point_ptr })
    }
```

```rust
    fn allocate_point(
        &mut self,
        ec_point: short_weierstrass::Affine<Curve>,
        vm: &mut VirtualMachine,
        points_segment_base: &mut Option<Relocatable>,
        id: usize,
    ) -> SyscallBaseResult<Relocatable> {
        if points_segment_base.is_none() {
            *points_segment_base = Some(vm.add_memory_segment());
        }
        let point_address = (points_segment_base.expect("Points segment base must be set.")
            + EC_POINT_SEGMENT_SIZE * id)?;
        self.points.insert(point_address, ec_point);
        Ok(point_address)
    }
```
