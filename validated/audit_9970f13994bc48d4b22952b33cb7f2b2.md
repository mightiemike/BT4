### Title
Stale name mappings in `AccountIndexStore` permanently squat abandoned account names when renaming - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateAccountActuator.java`)

### Summary
`UpdateAccountActuator.execute()` writes the new name into `AccountIndexStore` but never deletes the previous name entry, so every rename leaves a permanent, unreachable mapping from the old name to the renaming account's address. Once `AllowUpdateAccountName` is `0`, that stale entry makes `AccountIndexStore.has(oldName)` return `true` forever, blocking any other account from ever claiming that name even though no live account holds it.

### Finding Description
In `execute()`, the actuator only performs an insert, never a removal: [1](#0-0) 

`AccountIndexStore.put` keys the underlying revoking DB by the account name and stores the address as the value; there is no corresponding `delete`/`remove` method exposed or called anywhere in the rename path: [2](#0-1) 

`validate()` gates renames with two checks: [3](#0-2) 

- The first check only fires if the account's *current* name is non-empty, so the very first rename from the default empty name to `X` succeeds unconditionally.
- The second check (`has(accountName) && flag==0`) only blocks *new* claims when the flag is `0`; when `AllowUpdateAccountName == 1` both checks are bypassed, allowing an account that already owns a name to rename again without ever clearing the old index entry.

Exploit flow:
1. `CreateAccount` → account has empty name.
2. `AccountUpdateContract(name=X)` — allowed regardless of flag (name was empty) → `AccountIndexStore` now has `X -> A`.
3. Flag toggled to `1` (via governance/committee, out of attacker's control but a normal on-chain configuration state, not an admin action performed by the attacker).
4. `AccountUpdateContract(name=Y)` from the same account — both checks bypassed because flag is `1` → `AccountIndexStore` now has both `X -> A` (stale) and `Y -> A` (current); `X` entry is never deleted.
5. Flag toggled back to `0`.
6. Any other unprivileged account attempting `AccountUpdateContract(name=X)` fails validation because `has(X)` is still `true`, even though address `A` no longer holds name `X` and no account holds it.

The root cause is purely in the actuator/store code (missing deletion of the previous index key on rename), not in the flag-toggling mechanism itself — the flag toggle is just the trigger condition that exposes the permanently orphaned index entry.

### Impact Explanation
This permanently freezes a namespace resource (`AccountIndexStore` name key) that no longer corresponds to any live account, violating the intended invariant that abandoned/renamed-away names should become available again once `AllowUpdateAccountName` reverts to enforcing uniqueness. Over time, repeated renames under a temporarily-relaxed flag accumulate permanently unusable names in the shared on-chain namespace, denying legitimate future users a name with no way to reclaim or clean it up, since no code path ever calls a delete on `AccountIndexStore`.

### Likelihood Explanation
Fully reachable via ordinary transactions (`CreateAccount` + two `AccountUpdateContract`s) requiring no special privilege from the attacker's own account — the only external dependency is the network-wide `AllowUpdateAccountName` dynamic parameter being `1` at the time of the second rename and `0` afterward, which is a normal, expected lifecycle of that flag (it has toggled historically on real TRON networks) rather than an attacker-controlled admin action. Any account holder can trigger this during such a window, and the effect is permanent and repeatable for arbitrarily many names.

### Recommendation
In `UpdateAccountActuator.execute()`, before/after writing the new name, remove the old name's entry from `AccountIndexStore` (e.g., add a `delete`/`remove` method to `AccountIndexStore` keyed on the account's previous `accountName`, and call it whenever `account.getAccountName()` was non-empty and differs from the new name) so that abandoned names become available again for future claims.

```java
// framework/src/test/java/org/tron/core/actuator/UpdateAccountActuatorTest.java (extension)
@Test
public void testStaleNameSquatting() throws Exception {
  // 1. Create account with empty name
  AccountCapsule account = new AccountCapsule(ByteString.copyFrom(ownerAddress),
      ByteString.EMPTY, AccountType.Normal);
  accountStore.put(ownerAddress, account);

  // 2. Rename empty -> X (allowed even with flag=0)
  dynamicPropertiesStore.saveAllowUpdateAccountName(0);
  UpdateAccountActuator actuator1 = new UpdateAccountActuator();
  actuator1.setChainBaseManager(chainBaseManager);
  actuator1.setAny(getContract(ownerAddress, ByteString.copyFromUtf8("X")));
  TransactionResultCapsule ret1 = new TransactionResultCapsule();
  actuator1.validate();
  actuator1.execute(ret1);
  Assert.assertTrue(accountIndexStore.has("X".getBytes()));

  // 3. Flip flag to 1, rename X -> Y (old entry not cleaned up)
  dynamicPropertiesStore.saveAllowUpdateAccountName(1);
  UpdateAccountActuator actuator2 = new UpdateAccountActuator();
  actuator2.setChainBaseManager(chainBaseManager);
  actuator2.setAny(getContract(ownerAddress, ByteString.copyFromUtf8("Y")));
  TransactionResultCapsule ret2 = new TransactionResultCapsule();
  actuator2.validate();
  actuator2.execute(ret2);

  // 4. Flip flag back to 0
  dynamicPropertiesStore.saveAllowUpdateAccountName(0);

  // 5. A fresh, unrelated account tries to claim X — should succeed logically
  //    (nobody holds X) but is permanently blocked.
  byte[] otherAddress = ... // new address, fresh empty-named account
  AccountCapsule otherAccount = new AccountCapsule(ByteString.copyFrom(otherAddress),
      ByteString.EMPTY, AccountType.Normal);
  accountStore.put(otherAddress, otherAccount);

  UpdateAccountActuator actuator3 = new UpdateAccountActuator();
  actuator3.setChainBaseManager(chainBaseManager);
  actuator3.setAny(getContract(otherAddress, ByteString.copyFromUtf8("X")));

  // EXPECTED (bug): throws ContractValidateException("This name is existed")
  // even though address `ownerAddress` no longer holds name "X".
  Assert.assertTrue(accountIndexStore.has("X".getBytes()));
  try {
    actuator3.validate();
    Assert.fail("Expected validation to fail due to stale index entry");
  } catch (ContractValidateException e) {
    Assert.assertEquals("This name is existed", e.getMessage());
  }
}
```
