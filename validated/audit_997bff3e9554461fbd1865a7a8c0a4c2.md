### Title
Hardcoded 24-decimal/18-decimal conversion constant in the NEAR Wallet Contract's ETH-emulation fee logic causes fund loss/incorrect refunds if the assumption breaks - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The NEAR Wallet Contract (the ETH-transaction-emulating account contract reachable by any relayer/transaction signer via `rlp_execute`) hardcodes the conversion factor between Ethereum-style 18-decimal `wei` values and NEAR's 24-decimal `yoctoNEAR` balances as the constant `MAX_YOCTO_NEAR = 1_000_000` (i.e., `10^6 = 10^(24-18)`), used both to compute the relayer refund fee and to convert the Ethereum tx's `value` field into a NEAR transfer amount. This is analogous to the reported bug class: a hardcoded decimal-conversion multiplier baked into contract logic instead of being derived/verified from the actual token/account decimals, meaning any place downstream that assumes a different scale (or any mismatch between the assumed 24-decimal NEAR balance and how a value is validated) is a latent source of miscalculated transfers.

### Finding Description
`internal.rs` defines:
```
pub const MAX_YOCTO_NEAR: u32 = 1_000_000;
const VALUE_MAX: U256 = U256([10175519178963368024, 18446744073709, 0, 0]); // == u128::MAX / 1_000_000
``` [1](#0-0) 

These constants encode a fixed assumption that NEAR balances always have 24 decimals and Ethereum-emulated values always have 18 decimals, hardcoding the multiplier rather than deriving it. The multiplier is used in two security-critical unauthorized-value-movement paths:

1. Fee computation, which is paid out as a **refund transfer to the relayer** from the wallet-contract account:
```
let wei_amount = tx.max_fee_per_gas.saturating_mul(tx.gas_limit).min(VALUE_MAX).low_u128();
NearToken::from_yoctonear(wei_amount.saturating_mul(MAX_YOCTO_NEAR as u128))
``` [2](#0-1) 

2. Conversion of the Ethereum transaction's `value` field into the actual `yocto_near` amount transferred by the resulting NEAR `Transfer`/`FunctionCall` action:
```
let near_action = action
    .try_into_near_action(tx.value.raw().low_u128().saturating_mul(MAX_YOCTO_NEAR.into()))?;
``` [3](#0-2) 

with `validate_tx_value` bounding the input using the hardcoded `VALUE_MAX`:
```
fn validate_tx_value(tx: &NormalizedEthTransaction) -> Result<(), Error> {
    if tx.value.raw() > VALUE_MAX {
        return Err(Error::User(UserError::ValueTooLarge));
    }
    Ok(())
}
``` [4](#0-3) 

Both computations use `saturating_mul` by the fixed `1_000_000` factor, and the refund fee is then unconditionally transferred to the caller/relayer whenever `fee.is_zero()` is false:
```
if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
    env::promise_batch_action_transfer(refund_promise, *fee);
}
``` [5](#0-4) 

Because the 24/18-decimal relationship and the `1_000_000` multiplier are baked in as constants (with `VALUE_MAX` itself pre-computed as `u128::MAX / 1_000_000`, verified only by a unit test `test_value_max`), any change to the assumed decimal precision on either side (NEAR native balance decimals or the emulated "wei" convention used by a relayer/tooling) is not detected or adapted to at runtime — the contract will keep applying the stale `10^6` scale factor. This mirrors the ERC20 report's root cause: a hardcoded decimals multiplier instead of deriving it dynamically, creating silent miscalculation risk baked directly into value-transfer and fee-refund arithmetic reachable by every relayer/user transaction through `rlp_execute`.

### Impact Explanation
This constant directly participates in two paths that move funds: (1) the automatic relayer-fee refund paid from the user's wallet-contract account and (2) the amount transferred as the user's intended NEAR transfer derived from the Ethereum `value` field. Any scale mismatch here would cause either overpayment/underpayment of relayer fees or incorrect transfer amounts by orders of magnitude (a factor of `10^6`), directly resulting in unauthorized value movement or frozen/lost funds for wallet-contract accounts, which fits the "concrete unauthorized value movement" impact bar.

### Likelihood Explanation
Today, the constant correctly reflects nearcore's fixed 24-decimal `yoctoNEAR` balance representation, so exploitation would require this documented decimal relationship to actually diverge (e.g., a future accounting change or an emulation client using a different wei/yocto convention) — there is no way to trigger this drift through a single crafted transaction under the current protocol. This significantly limits standalone exploitability under present conditions; the finding is best characterized as a maintainability/hardcoding risk analogous to the reported bug class rather than a directly triggerable exploit today.

### Recommendation
Avoid embedding the 24 vs 18 decimal relationship as bare literal constants (`MAX_YOCTO_NEAR`, `VALUE_MAX`) computed once and reused throughout `internal.rs`. Instead, derive the multiplier from named, single-source-of-truth decimal constants (e.g., `NEAR_DECIMALS = 24`, `WEI_DECIMALS = 18`, `MULTIPLIER = 10u128.pow(NEAR_DECIMALS - WEI_DECIMALS)`), and add explicit runtime/compile-time assertions tying `VALUE_MAX` to that multiplier, so any future change to either decimal assumption is enforced consistently across all fee and transfer-amount computations instead of relying on manually kept-in-sync hardcoded literals.

### Proof of Concept
No transaction-level PoC is available: exploitation is not currently reachable from a single crafted transaction because the 24-decimal NEAR / 18-decimal wei relationship is fixed by the protocol today. The finding is limited to the code-hygiene/hardcoding pattern itself, demonstrated by: [1](#0-0)  and its two usages at [2](#0-1)  and [3](#0-2) .
