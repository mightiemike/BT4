**Analysis:**

The `mint`/`ensure_primary_store_exists` path in [1](#0-0)  derives the primary store address via `object::create_user_derived_object_address(owner, metadata_addr)`, which uses a domain-separated SHA3-256 preimage with a distinct scheme byte `0xFC` (`OBJECT_DERIVED_SCHEME`) as documented and implemented in [2](#0-1) . This is architecturally distinct from `create_object_address` (seed-based, scheme `0xFE`) and `create_guid_object_address` (scheme `0xFD`) — each derivation path appends a unique constant precisely to prevent cross-scheme address collisions, as the code comments explicitly state: "This constant serves as a domain separation tag to prevent existing authentication key and resource account derivation to produce an object address" [3](#0-2) .

Even setting aside domain separation, any object creation — including the derived object created inside `create_primary_store` via `object::create_user_derived_object` — routes through `create_object_internal`, which explicitly asserts the target address does not already hold an `ObjectCore`: `assert!(!exists<ObjectCore>(object), error::already_exists(EOBJECT_EXISTS));` [4](#0-3) . This means that even in the astronomically improbable event of a genuine SHA3-256 collision against an existing object address, the transaction would abort rather than silently overwrite or corrupt the pre-existing resource — there is no code path that skips this existence check for user-derived objects.

The Rust-side mirror implementation confirms the same domain-separated construction and scheme constants (`Scheme::DeriveObjectAddressFromSeed`, `Scheme::DeriveObjectAddressFromObject`) are used consistently between the Move-VM/AptosVM/native implementation and the type system utilities [5](#0-4)  and [6](#0-5) , so there's no divergence in derivation logic that could be exploited by crafting `owner`/`metadata` inputs.

For an actual collision to occur, an attacker would need to find a SHA3-256 preimage collision between two byte strings differing in the appended domain-separation byte (`0xFC` vs `0xFE`/`0xFD`/other resource-account/auth-key schemes) — this reduces to breaking SHA3-256 collision resistance, which is a cryptographic assumption outside the scope of a Move-logic vulnerability and not something fuzzing `owner`/`metadata` inputs at the application layer can find. There is no logic bug, missing bounds check, or reused constant in this code that would allow an unprivileged caller to force such a collision or bypass the `already_exists` guard.

pub fn create_derived_object_address(
    creator: AccountAddress,
    object_address: AccountAddress,
) -> AccountAddress {
    let mut input = bcs::to_bytes(&creator).unwrap();
    input.extend(bcs::to_bytes(&object_address).unwrap());
    input.push(Scheme::DeriveObjectAddressFromObject as u8);
