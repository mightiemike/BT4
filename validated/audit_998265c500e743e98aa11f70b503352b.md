## Confirmed root cause

`handle_block_rejection` (`stacks-signer/src/v0/signer.rs`) authenticates only the *signature* on a `BlockRejection` message and that the signer is in the registered set — it never independently verifies that the `reject_reason` field the sending signer chose actually corresponds to a real violation on the rejected block. The reason is taken verbatim from the peer's message: `(&rejection.response_data.reject_reason).into()` [1](#0-0) .

`store_and_process_block_rejection` then tallies rejection weight by self-reported reason code via `compute_reject_code_signing_weight`, which simply buckets addresses by whatever `RejectReasonPrefix` they reported [2](#0-1) . Once the aggregate `ReorgNotAllowed`-tagged weight exceeds the blocking-minority threshold (`total_weight - min_weight`, i.e. just over 30%), the signer unilaterally flips the miner's status to `SortitionMinerStatus::InvalidatedBeforeFirstBlock`: [3](#0-2) 

This is only gated behind “active protocol version < global-state activation” — legacy/v1-style signer sets still run this path — but for any signer set on that protocol version, a **minority coalition of colluding signers (>~30% weight, well under the 70% block-approval threshold)** can mark a legitimately sortition-elected, honestly-behaving miner as invalid simply by broadcasting `BlockRejection` messages tagged `ReorgNotAllowed` for a block that is not actually attempting an invalid reorg. This is functionally identical to the external report's bug class: an attacker can cheaply "fake a violation report" (here, a fabricated `ReorgNotAllowed` reason code) to trigger a punitive/blocking consequence (here, disabling a valid miner instead of disabling trading), without ever having to prove the underlying claim.

### Title
Minority of signers can fake `ReorgNotAllowed` rejection reasons to invalidate a legitimate miner - (File: stacks-signer/src/v0/signer.rs)

### Summary
`store_and_process_block_rejection` marks the current sortition-winning miner as `InvalidatedBeforeFirstBlock` based solely on the self-reported `RejectReasonPrefix::ReorgNotAllowed` tag attached by peer signers to their `BlockRejection` messages, without any cryptographic or protocol-level proof that the flagged block actually attempted a disallowed reorg.

### Finding Description
When a `BlockRejection` is received, `handle_block_rejection` only checks that the message is validly signed by a registered signer [4](#0-3) ; it does not re-derive or validate the `reject_reason` against the actual block content. That reason is stored and later summed by weight in `compute_reject_code_signing_weight` [2](#0-1) .

In `store_and_process_block_rejection`, once a blocking minority (>30% weight, i.e., `total_weight - min_weight`) of rejections are tagged `ReorgNotAllowed`, the local sortition view is mutated to invalidate the current miner: [3](#0-2) 

Nothing forces the reason code to reflect a genuine detection of an invalid reorg attempt — a signer can send `ReorgNotAllowed` for any block it wants blocked, including one from an honestly elected, non-reorging miner. Because the invalidation threshold (~30%) is far below the block-approval threshold (~70%), an attacker needs to control only a minority of signer weight to trigger this — they do not need to control enough weight to actually reject the block outright at the honest-majority level for other reasons; they simply need enough weight to cross the blocking-minority bar with a specific self-chosen reason tag.

### Impact Explanation
This breaks the equality that "a sortition winner should mine unless it genuinely misbehaves." A minority of colluding/dishonest signers (below the 70% approval threshold) can force `SortitionMinerStatus::InvalidatedBeforeFirstBlock` on the actual, legitimately VRF-elected miner purely by mislabeling their rejections, causing the network to fall back to the prior miner extending tenure or otherwise stalling the legitimate miner's tenure. This is a minority-triggerable divergence in a consensus-relevant state machine (the signer's view of miner validity, which feeds `StateMachineUpdate` and downstream tenure-extend decisions), matching the High-severity category of "minority-triggerable sortition/validation divergence, temporary tip disagreement."

### Likelihood Explanation
Requires collusion among registered signers holding roughly 30%+ of signer weight — a minority, not a majority, and well below the 70% block-approval bar. This is realistically achievable by a modest coalition of malicious or compromised signer operators, and costs them nothing beyond sending a mislabeled rejection message; the report notes this code path is scoped to signer protocol versions predating global-state activation, so exploitability depends on that version still being active in a live network.

### Recommendation
Do not act on self-reported rejection reason codes without independent verification. Either (a) require the invalidating signer coalition to also supply verifiable evidence (e.g., a valid alternate block/tenure fork proof) that substantiates the `ReorgNotAllowed` claim before mutating `SortitionMinerStatus`, or (b) require the same >=70% approval-level threshold (not the 30% blocking-minority threshold) before allowing a reason-specific rejection tally to change consensus-visible miner-validity state.

### Proof of Concept
1. Stand up a signer set running the legacy (`< global state`) protocol version with `total_weight = 100`.
2. A colluding minority controlling `weight > total_weight - min_weight` (i.e., >30, since `min_weight ≈ 70`) all issue `BlockRejection` messages for a block proposed by the current, legitimately-elected miner, each tagging `reject_reason = RejectReasonPrefix::ReorgNotAllowed`, even though the block does not attempt any reorg.
3. Once these are received and processed by `store_and_process_block_rejection`, `total_reorg_reject_weight.saturating_add(min_weight) > total_weight` becomes true [5](#0-4) .
4. `sortition_state.cur_sortition.miner_status` is set to `SortitionMinerStatus::InvalidatedBeforeFirstBlock` [6](#0-5) , causing the legitimate miner to be treated as invalid for the remainder of its tenure despite never having attempted an improper reorg.

    /// Compute the rejection weight for the given reject code, given a list of signatures
    fn compute_reject_code_signing_weight<'a>(
        &self,
        addrs: impl Iterator<Item = &'a (StacksAddress, RejectReasonPrefix)>,
        reject_code: RejectReasonPrefix,
    ) -> u32 {
        addrs.filter(|(_, code)| *code == reject_code).fold(
            0u32,
            |signing_weight, (stacker_address, _)| {
                let stacker_weight = self.signer_weights.get(stacker_address).unwrap_or(&0);
                signing_weight.saturating_add(*stacker_weight)
            },
        )
    }
