### Title
Wildcard CORS bypass via suffix-collision hostnames in `isAllowedOrigin` - ([File: core/services/gateway/network/httpserver.go])

### Summary
`httpServer.isAllowedOrigin` implements wildcard subdomain matching for `CORSAllowedOrigins` entries like `*.remix.com` by stripping the `*.` prefix and calling `strings.HasSuffix(originHost, allowedHost)`, with no dot-boundary check. An attacker-controlled hostname that merely ends with the same characters (e.g. `notremix.com` or `evilremix.com`) satisfies the suffix test and is incorrectly treated as a trusted subdomain.

### Finding Description
In `core/services/gateway/network/httpserver.go`, `isAllowedOrigin` parses the request's `Origin` header and each configured `CORSAllowedOrigins` entry via `splitURL`, then for wildcard entries does: [1](#0-0) 
`allowedHost` after stripping `*.` from `*.remix.com` becomes `remix.com`. `strings.HasSuffix("notremix.com", "remix.com")` returns `true` because there is no requirement that the character preceding the match be a literal `.` (i.e., that `originHost` equals `allowedHost` or ends with `"."+allowedHost`). The same applies to `evilremix.com`.

This function is invoked directly from the request path in `handleRequest`: [2](#0-1) 
When `CORSEnabled` is true and the origin passes the (broken) check, the server echoes the attacker's exact `Origin` value back in `Access-Control-Allow-Origin`, telling the browser it may expose the cross-origin response to attacker JavaScript. There is no other check (no dot-boundary enforcement, no exact suffix-with-separator match) that would stop this.

### Impact Explanation
An attacker who registers/controls a domain such as `evilremix.com` or `notremix.com` (colliding by suffix with an operator-configured wildcard entry like `*.remix.com`) can host a webpage that issues cross-origin `fetch()` requests to the gateway's JSON-RPC endpoint. The gateway will set `Access-Control-Allow-Origin: https://evilremix.com`, letting the browser expose the JSON-RPC response body to attacker script — bypassing the intended origin allow-list for job/vault/CCIP gateway data. This is an unauthorized cross-origin information-disclosure vector matching "unauthorized browser-based reading of gateway JSON-RPC responses" in scope.

### Likelihood Explanation
Exploitability requires only that: (1) `CORSEnabled=true`, and (2) at least one wildcard entry is present in `CORSAllowedOrigins` (a common, documented configuration pattern for allowing subdomains). No privileged access, leaked keys, or social engineering is needed — the attacker simply registers a suffix-colliding domain and hosts a page with a same-site-policy-abusing script. This is deterministic and fully repeatable.

### Recommendation
Fix the wildcard match to require a proper subdomain boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```
This ensures `notremix.com`/`evilremix.com` do not match `*.remix.com`, while `foo.remix.com` still does.

### Proof of Concept
Add a unit test in `core/services/gateway/network/httpserver_test.go`:
```go
func TestIsAllowedOrigin_WildcardSuffixCollision(t *testing.T) {
    s := &httpServer{config: &HTTPServerConfig{
        CORSAllowedOrigins: []string{"https://*.remix.com"},
    }, lggr: logger.Test(t)}

    assert.False(t, s.isAllowedOrigin("https://notremix.com"))
    assert.False(t, s.isAllowedOrigin("https://evilremix.com"))
    assert.True(t, s.isAllowedOrigin("https://foo.remix.com"))
    assert.True(t, s.isAllowedOrigin("https://remix.com"))
}
```
Expected current behavior (bug): the first two assertions fail because `isAllowedOrigin` returns `true`. After applying the recommended fix, all four assertions pass.
