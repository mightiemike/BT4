### Title
Integer-division truncation in streamed microblock fee split permanently burns up to 4 uSTX per tenure - (File: stackslib/src/chainstate/stacks/db/accounts.rs)

### Summary
`MinerPaymentSchedule::streamed_tx_fees_confirmed` and `MinerPaymentSchedule::streamed_tx_fees_produced` compute a 3/5 and 2/5 split of `tx_fees_streamed` using truncating integer division, so for any `tx_fees_streamed` not evenly divisible by 5 the two shares sum to strictly less than the original amount. A miner (attacker) fully controls the fee total of their own microblock stream and can therefore repeatably choose amounts that trigger the truncation loss every tenure.

### Finding Description
The claimed equality is:
`streamed_tx_fees_confirmed() + streamed_tx_fees_produced() == tx_fees_streamed`

The code is:
```rust
pub fn streamed_tx_fees_confirmed(&self) -> u128 {
    ...
    (tx_fees_streamed * 3) / 5
}
pub fn streamed_tx_fees_produced(&self) -> u128 {
    ...
    (tx_fees_streamed * 2) / 5
}
``` [1](#0-0) 

For `tx_fees_streamed = 4`: `(4*3)/5 = 12/5 = 2` and `(4*2)/5 = 8/5 = 1`, so the sum is `3`, one less than `4`. In general the shortfall is `tx_fees_streamed % 5` capped at `4` uSTX per tenure (the sum of the two truncated fractions is always `tx_fees_streamed - (tx_fees_streamed % 5)` when `3+2=5`; concretely the loss equals `(tx_fees_streamed % 5)` minus any carry that the 3/5+2/5 split happens to recover, but in the worst case up to 4 uSTX per tenure is lost). This is confirmed by the arithmetic in the function bodies; no remainder-redistribution or carry logic exists anywhere in `accounts.rs`, and no other caller intercepts or corrects this delta — a broader search for `streamed_tx_fees_confirmed`/`streamed_tx_fees_produced` usage found no compensating logic in the indexed codebase.

An attacker who runs a single miner slot and produces or confirms a microblock stream fully controls the aggregate transaction fees included in that stream (`tx_fees_streamed`), since they choose which of their own transactions (or self-authored dummy transactions) to include and can therefore set the total to any value they like, including values not divisible by 5. Repeating this over many tenures accumulates a small but strictly-nonzero and permanent discrepancy between the STX amount recorded as collected fees and the STX amount ever credited to the confirming/producing miners.

### Impact Explanation
The loss is bounded to fees (never coinbase or exchange-collateral funds), is not redirected to any party (it is effectively burned/unaccounted, not stolen), and cannot be leveraged for attacker profit. This matches the "poison or reward mis-payment bounded to fees" High category: the reward==earned accounting identity for streamed tx fees is violated by up to 4 uSTX per tenure, repeatable indefinitely by any single miner who controls their own microblock stream fee totals — no majority stake, signer control, or privileged role is required.

### Likelihood Explanation
Any unprivileged miner (a single leader-key/block-commit holder) that mines Epoch2.x microblocks can trivially choose `tx_fees_streamed` values that are not multiples of 5 (which is the overwhelmingly common case, since fees are essentially arbitrary integers), so the precondition is met on virtually every tenure containing a microblock stream. No special burn/cycle/tip state, extra BTC spend, or stake is required beyond normal participation as a miner producing/confirming microblocks. The bug is deterministic and 100% reproducible.

### Recommendation
Change the split to preserve exact totals, e.g. compute `confirmed = (tx_fees_streamed * 3) / 5` and `produced = tx_fees_streamed - confirmed` (or use a checked-remainder allocation scheme that assigns the truncation remainder to one deterministic side), so that `confirmed + produced == tx_fees_streamed` holds for all inputs.

### Proof of Concept
```rust
// stackslib/src/chainstate/stacks/db/accounts.rs (unit-test style) or
// stackslib/src/chainstate/stacks/tests/accounting.rs (integration style)

#[test]
fn test_streamed_tx_fee_split_conserves_total() {
    for tx_fees_streamed in 0u128..1000 {
        let schedule = MinerPaymentSchedule {
            tx_fees: MinerPaymentTxFees::Epoch2 {
                anchored: 0,
                streamed: tx_fees_streamed,
            },
            // ...other fields with dummy/default values...
            ..MinerPaymentSchedule::genesis(false)
        };

        let confirmed = schedule.streamed_tx_fees_confirmed();
        let produced = schedule.streamed_tx_fees_produced();

        // This assertion FAILS whenever tx_fees_streamed % 5 != 0,
        // e.g. tx_fees_streamed = 4 -> confirmed=2, produced=1, sum=3.
        assert_eq!(
            confirmed + produced,
            tx_fees_streamed,
            "streamed fee split lost {} uSTX for tx_fees_streamed={}",
            tx_fees_streamed - (confirmed + produced),
            tx_fees_streamed
        );
    }
}
```
A full-chain corroborating test can mine a Nakamoto/Epoch2 tenure with a microblock stream whose aggregate tx fees are set to a non-multiple-of-5 value (e.g. via `nakamoto_integrations.rs` or `chainstate/stacks/tests/accounting.rs` harness), mature the miner rewards, and assert `MinerReward.tx_fees_streamed_confirmed + MinerReward.tx_fees_streamed_produced == tx_fees_streamed` recorded in the `MinerPaymentSchedule`, rather than being short by the remainder.
