## Title
Rounding-induced `makerBuyTokenQuantityReceive == 0` branch in `matchSingleOrder` leaves the maker order's ACTIVE state and dust unpersisted, permanently stranding the order in the order book - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder` (the java-tron analog of `meme::get_amount_in`/`get_amount_out`) computes cross-token trade quantities with a floor-rounding helper, `MarketUtils.multiplyAndDivide`, exactly the "round-down" pattern described in the report. In the "taker > maker" branch, the code assumes `makerBuyTokenQuantityReceive` (the floor-rounded amount) can never be `0`, and when that unproven assumption is violated it returns early without persisting the maker order to `orderStore`, even though it has already mutated the in-memory `makerOrderCapsule`'s state to `INACTIVE` and unlinked it from the account's order index.

### Finding Description
`MarketUtils.multiplyAndDivide` performs `floorDiv(a*b, c)` [1](#0-0) , mirroring the reported `get_amount_in`/`get_amount_out` rounding-down pattern.

In `matchSingleOrder`, the "taker > maker" branch computes `makerBuyTokenQuantityReceive` via this floor-rounding helper and marks the maker order `INACTIVE` in `marketAccountStore` *before* checking whether the rounded result is `0`: [2](#0-1) 

The inline comment explicitly (and incorrectly, as a general claim) asserts this branch "would not happen," basing the argument only on the specific case `sellQuantity < buyQuantity`. When `makerSellQuantity > makerBuyQuantity` (i.e., the maker sells much more of token A per unit of TRX/B) and `makerSellRemainQuantity` is small relative to that ratio, `floor(makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity)` can legitimately be `0`, and the "impossible" branch executes:

- `MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)` has already removed the maker order id from the owner's `MarketAccountOrderCapsule` order list [3](#0-2) .
- `makerOrderCapsule.setSellTokenQuantityReturn()` records the dust remain and `returnSellTokenRemain(makerOrderCapsule)` credits the dust back to the maker's account balance, but the method then `return`s early — **skipping** the subsequent `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule)` call that persists the mutated capsule (state=`INACTIVE`, remain untouched from its original value) [4](#0-3) .

Because `makerOrderCapsule.getSellTokenQuantityRemain()` was never explicitly set to `0` in this branch (only the local in-memory `setSellTokenQuantityReturn()` was set), the caller `matchOrder`'s removal check `if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) { orderIdListCapsule.removeOrder(...) }` [5](#0-4)  also does not fire, since remain is still the original nonzero value. The net effect: the order is removed from the *account's* order index (so the owner can no longer see/cancel it via `MarketAccountOrderCapsule`) but stays in the `orderStore` (persisted on disk) with its original `ACTIVE` state and stale `sellTokenQuantityRemain`/`sellTokenId`/`buyTokenId`, and remains linked in `pairPriceToOrderStore`'s order list for that price level (since it was never removed there either, only the account index was updated). Meanwhile, dust tokens were already credited to the maker's balance via `returnSellTokenRemain`, so the reserved/escrowed sell-token amount conceptually double-counts: it is both credited back to the balance and still "locked" in the persisted, still-referenced order.

### Impact Explanation
This is a state-consistency corruption in the on-chain order book, directly reachable by any account broadcasting a `MarketSellAssetContract` transaction that triggers a match against a maker order whose price ratio and remaining quantity fall into this floor-rounding-to-zero condition. Consequences:
- A "ghost" order remains permanently referenced in `pairPriceToOrderStore`/`MarketOrderIdListCapsule` for that price bucket while being unreachable from the owner's `MarketAccountOrderCapsule` (so `MarketCancelOrderActuator`, which is driven by the account's order list, cannot cancel it), matching the report's "pool remains open" pattern — the analog here is an order that should be closed/inactive but is never actually finalized in the authoritative store.
- Because the price-bucket linked list (`orderIdListCapsule`) never gets its head removed for this order, subsequent matching iterations against the same price level can repeatedly re-select this stale order id, re-invoking `matchSingleOrder` with inconsistent state and potentially re-crediting dust or looping, which is a resource-exhaustion / matching-correctness risk in the exchange matching engine (an in-scope actuator state-transition and market-math component).
- Token accounting drift: the maker's sell-token dust has already been returned to its liquid balance while the persisted order capsule still logically reserves that same amount, creating a latent double-spend/inconsistency surface for that token pair's order book bookkeeping.

### Likelihood Explanation
Triggering requires only crafting maker/taker sell/buy quantities such that the maker's sell:buy ratio is large and the remaining sell quantity is small enough that `floor(remain * buyQty / sellQty) == 0` — entirely controllable by any two unprivileged accounts placing orders via `MarketSellAssetContract`/`MarketCancelOrderActuator`, no special privileges needed. The code comment itself acknowledges the developers believed this could not happen, indicating it was not defended against nor covered generically in tests (existing tests use small/simple ratios like 1:2, 1:3 that don't stress this edge).

### Recommendation
Remove the early `return` in the `makerBuyTokenQuantityReceive == 0` branch, or explicitly call `makerOrderCapsule.setSellTokenQuantityRemain(0)` and `orderStore.put(...)` (and ensure `orderIdListCapsule.removeOrder(...)` is triggered) before returning, so the persisted order store and the price-bucket list stay consistent with the account-order-index removal that already occurred. More robustly, remove the incorrect invariant comment and add an explicit unit test with a maker sell:buy ratio > 1 and a small remain to exercise this path.

### Proof of Concept
1. Attacker (or any two colluding/independent accounts) create a maker sell order via `MarketSellAssetContract` with `sellTokenQuantity = 1_000_000_000`, `buyTokenQuantity = 1` (i.e., extreme sell:buy ratio), leaving `sellTokenQuantityRemain` at some small residual value after prior partial fills (e.g., `remain = 500`).
2. A taker submits an order that matches this maker's price and whose `takerBuyTokenQuantityRemain` exceeds `makerOrderCapsule.getSellTokenQuantityRemain()` (the "taker > maker" branch), driving execution into `matchSingleOrder`'s else-branch at [6](#0-5) .
3. `makerBuyTokenQuantityReceive = floor(500 * 1 / 1_000_000_000) = 0`, entering the buggy branch at line 466; the maker order is unlinked from `MarketAccountOrderCapsule` but never `orderStore.put()`'d nor removed from `pairPriceToOrderStore`'s order list, leaving inconsistent, unreachable-yet-persisted order state — verifiable by querying `MarketOrderStore` directly for the order id after the transaction and observing state=`ACTIVE`/original nonzero remain, versus the owner's `MarketAccountOrderCapsule` no longer listing it.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
