### Title
Wallet Contract's hard-coded NEP-141 storage-deposit amount and unchecked non-compliant NEP-141 token integration can strand relayer/user funds or corrupt ERC-20 emulation state - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's ERC-20 emulation path (mapping Ethereum `transfer(to, value)` calls to NEP-141 `ft_transfer`) assumes any target token contract behaves exactly like the reference NEP-141/NEP-145 implementation: that `storage_balance_of` truthfully reports registration status, that a fixed `NEP_141_STORAGE_DEPOSIT_AMOUNT` is always sufficient for `storage_deposit`, and that `ft_transfer`/`storage_deposit` either succeed cleanly or fail atomically with automatic deposit refund. This mirrors the Balancer/ERC-20 "non-compliant token" bug class: any account can deploy a token that is a valid NEP-141 receiver target but deviates from the standard's guarantees (e.g., different storage bounds, silently keeping excess deposits, or not reverting fully on partial failure), and the wallet contract has no verification step before trusting the response.

### Finding Description
The relevant logic is in `nep_141_storage_balance_callback` [1](#0-0) , which is reached via the `ERC20Transfer` emulation branch of `create_promise` [2](#0-1) .

The contract hard-codes the storage deposit amount instead of querying the actual token's `storage_balance_bounds`, and the code comment itself acknowledges the trust assumption and its associated risk: [3](#0-2) 

When `storage_balance_of` returns `None`, the contract chains `storage_deposit` (with the fixed amount) followed immediately by the user's `ft_transfer` call in the same promise/receipt, with no verification that the deposit was accepted or that the receiver is now actually registered: [4](#0-3) 

The deserialization of `storage_balance_of`'s response is trusted at face value — `Option<StorageBalance>` — with no cross-check of the `total`/`available` fields against the wallet's own hard-coded deposit constant: [5](#0-4) 

Any token contract can be targeted by an ERC-20-style transaction via the wallet, since `target`/`token_id` is simply the relayer-chosen account passed into `rlp_execute` [6](#0-5)  and is not restricted to a known-good/allow-listed set of NEP-141 tokens. The eth-emulation parser in `eth_emulation.rs` blindly builds an `ft_transfer` action for whatever `target` was supplied: [7](#0-6) .

### Impact Explanation
Because the wallet contract assumes standard NEP-141/NEP-145 semantics without verification:
- A token contract whose actual `storage_balance_bounds.min` exceeds the hard-coded `NEP_141_STORAGE_DEPOSIT_AMOUNT` (1250 µNEAR) will cause `storage_deposit` to fail for that receiver every time, permanently preventing that user's ERC-20-emulated transfers to new receivers of that token from ever succeeding through the wallet (denial of value transfer via this integration path), even though NEAR's protocol-level deposit refund mitigates the attached-deposit loss.
- Conversely, a non-compliant/malicious token contract can accept the deposit without refunding any unused portion (unlike the reference NEP-141 implementation, which auto-refunds excess), letting it drain 1250 µNEAR from the wallet on every new-receiver transfer with no way for the wallet contract to detect or prevent this, since the callback treats a `PromiseResult::Successful` from `storage_deposit` purely as "proceed" (implicit continuation of the promise chain) with no return-value validation.
- Because `storage_balance_of`'s `Some`/`None` response is trusted as ground truth for whether `ft_transfer` will succeed, a token that misreports registration status can cause the wallet to skip the storage deposit step and attempt `ft_transfer` directly; if the underlying transfer then fails, the outcome is reported as `success: false` to the relayer/caller, but if it partially succeeds in a way inconsistent with the assumed atomicity (e.g., non-standard tokens with side effects or non-atomic multi-part registration), the wallet's accounting of "did this action actually happen" may diverge from the token's real internal state, since the wallet never independently confirms the transfer.

This falls within reachable production paths — any transaction signer (via `rlp_execute`) or relayer can direct the Wallet Contract to interact with an arbitrary "token" account, exactly matching the reachable-analog criteria (transaction/action validation, cross-contract receipt handling by an unprivileged caller).

### Likelihood Explanation
Medium. Exploitation requires only deploying an ordinary (non-privileged) NEP-141-labeled contract and inducing a wallet-contract user/relayer to interact with it as an ERC-20 token target — something the wallet's emulation layer permits for any account ID, with no allow-list or bounds verification. No validator, network, or privileged-role compromise is needed; a single crafted transaction/target is sufficient.

### Recommendation
- Query the target token's actual `storage_balance_bounds` before computing the deposit to attach, or clamp/verify the amount rather than relying purely on a hard-coded constant; alternatively, refund any excess deposit explicitly rather than trusting the token's implementation to do so.
- Add an explicit check that `storage_deposit`'s own promise result succeeded before proceeding to call `ft_transfer` (currently the chain unconditionally proceeds once inside the `None` branch of `nep_141_storage_balance_callback`).
- Document (and, where feasible, enforce via a curated token registry) that only NEP-141/NEP-145-compliant tokens should be interacted with through the wallet contract's ERC-20 emulation, mirroring the Balancer documentation's warning about non-compliant tokens.

### Proof of Concept
1. Deploy a "token" contract at some `token_id` that implements `ft_on_transfer`/`ft_transfer`/`storage_deposit`/`storage_balance_of` method signatures matching NEP-141/145, but sets `storage_balance_bounds.min` higher than `NEP_141_STORAGE_DEPOSIT_AMOUNT` (1250 µNEAR) and does not refund excess/insufficient deposits.
2. From a Wallet Contract instance, submit an RLP-encoded ERC-20 `transfer(to, value)` call (via `rlp_execute`) targeting this `token_id` for a `to` address that has never interacted with the token before (per `try_emulation` in `eth_emulation.rs`).
3. Observe that `create_promise`'s `ERC20Transfer` branch calls `storage_balance_of`, sees `None`, and proceeds into `nep_141_storage_balance_callback`'s `None` branch, attaching exactly 1250 µNEAR to `storage_deposit` regardless of the token's real bounds — either the deposit is insufficient (transfer permanently fails for this token/receiver pair) or, if the token accepts smaller-than-required deposits without validation while not refunding unused NEAR, repeated calls silently bleed NEAR from the wallet with no on-chain assertion catching the discrepancy.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
