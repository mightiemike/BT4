## Finding [1](#0-0) 

### Title
Sharded block executor substitutes a fixed sentinel (`TOTAL_SUPPLY_AGGR_BASE_VAL = u128::MAX >> 1`) for the real `AptosCoin` total supply during Move execution, letting unprivileged transactions that branch on `coin::supply<AptosCoin>()` diverge between sharded and sequential execution - (File: `aptos-move/aptos-vm/src/sharded_block_executor/aggr_overridden_state_view.rs`)

### Summary
`AggregatorOverriddenStateView::get_state_value` intercepts reads of `TOTAL_SUPPLY_STATE_KEY` and returns a constant `TOTAL_SUPPLY_AGGR_BASE_VAL` (`u128::MAX >> 1 ≈ 1.7×10^38`) instead of the real on-chain APT total supply, for the duration of a shard's transaction execution. [2](#0-1) 
This is deliberately used so each shard can locally apply mint/burn deltas without waiting for cross-shard total-supply synchronization; the true value is only reconstituted afterward, by patching each transaction's *write-set value* for `TOTAL_SUPPLY_STATE_KEY` via delta arithmetic in `aggregate_and_update_total_supply`. [3](#0-2) 

The problem: the legacy Aggregator V1 read path used by `coin::coin_supply`/`coin::supply` for `AptosCoin` reads the raw state value directly through `TAggregatorV1View::get_aggregator_v1_state_value`, which is a thin wrapper over `StateView::get_state_value`. [4](#0-3) 
`coin::supply<CoinType>()` and `coin::coin_supply<CoinType>()` are public `#[view]` functions reachable from Move (any script, module, or transaction that calls them, e.g. a DeFi protocol checking a supply cap), and internally call `optional_aggregator::read`, which for AptosCoin's parallelizable aggregator resolves the raw value from storage. [5](#0-4) 

Because the post-hoc reconciliation in `aggregate_and_update_total_supply` only rewrites the *stored write-set bytes* for `TOTAL_SUPPLY_STATE_KEY` - it does not re-execute or re-derive the transaction's control flow - any transaction whose Move logic branches (e.g., `assert!`/abort) on the *magnitude* of `coin::supply<AptosCoin>()` will make that branching decision against the sentinel `~1.7×10^38` value when run under the sharded executor, versus the true (much smaller, ~10^17-10^18 octas) supply when run sequentially by `AptosVMBlockExecutorWrapper`/normal `AptosVM`. This can flip `ExecutionStatus` (`Success` vs `MoveAbort`) and, consequently, the entire committed write set (aside from the reconciled `TOTAL_SUPPLY_STATE_KEY` entry) for the same transaction against the same ledger state, depending solely on which execution engine processed it.

### Impact Explanation
If the sharded block executor is used by any node (validator or full node performing replay/verification) to compute the canonical ledger state, this divergence is a determinism bug: it can make that node commit a different transaction output (and thus a different state root) than a node using the standard sequential `AptosVM`, for the exact same ordered transaction and pre-state. That is a state-integrity violation - unprivileged transaction input controls whether the divergence is even triggered, and it corrupts the deterministic binding between transaction, VM output, and committed write set that all proof and consensus machinery relies on. This falls squarely in "hard-fork-only divergence" territory: two conforming implementations of "the VM" produce different, non-reconcilable results from the same input.

### Likelihood Explanation
Exploitability is gated on two facts I could confirm from code:
1. `coin::supply`/`coin::coin_supply` are public view functions that resolve the aggregator's live value through the plain `StateView`, which is exactly the interface `AggregatorOverriddenStateView` overrides.
2. The reconciliation logic explicitly only fixes up `write_set().get_total_supply()`/`update_total_supply()` post-execution - it has no mechanism to detect or correct diverging abort/success decisions made mid-execution.

I was not able to fully verify, within the available exploration, the exact call site that plumbs `AggregatorOverriddenStateView` into the state view object handed to `execute_transactions_with_dependencies` inside `ShardedExecutorService` (I confirmed the type is imported there but did not reach the precise wiring line before running out of iterations). The code comment ("after all the txns are executed, the proof checker expects the total_supply to read/written to the tree") strongly implies the override is live during actual transaction execution, not just in a post-processing shadow view, but this should be confirmed by reading the full `execute_transactions_with_dependencies`/`ExecutorShardCommand` handling path to see exactly which `StateView` object shards use for BlockSTM's speculative reads.

### Recommendation
- Route `AptosCoin` supply reads through the delayed-field/aggregator-v2 abstraction (as newer coins already do) so that "read" operations are treated as speculative/delayed and are properly serialized or invalidated cross-shard, rather than exposing a hardcoded sentinel through the plain `StateView` interface reachable by arbitrary Move code.
- Alternatively, disallow/flag any transaction whose execution path performs a control-flow-affecting comparison against `coin::supply<AptosCoin>()` under sharded execution, or force such transactions to be routed through the global (non-sharded) round.
- At minimum, add an execution-equivalence test that runs a Move test module performing `assert!` on `coin::supply<AptosCoin>()` magnitude under both sharded and sequential execution and asserts identical `TransactionStatus`/write sets, to catch this class of divergence in CI before any config enables sharded execution as a consensus-affecting execution path.

### Proof of Concept
1. Deploy (or use an existing) Move module with an entry function:
   ```
   public entry fun supply_gated_action(caller: &signer) {
       let supply = option::destroy_some(coin::supply<AptosCoin>());
       assert!(supply < 1000000000000000000, 1); // real supply is below this; sentinel (~1.7e38) is not
       // ... perform a state-mutating action, e.g. move_to / mint / transfer
   }
   ```
2. Submit a transaction calling `supply_gated_action` from an unprivileged account.
3. Execute the block containing this transaction via the normal sequential `AptosVM`/`AptosVMBlockExecutorWrapper` path: the assert passes (real supply is far below `1e18`), producing `ExecutionStatus::Success` and a non-trivial write set (e.g., a new resource written).
4. Execute the identical block/transaction via the sharded block executor (`LocalExecutorClient::execute_block` → `ShardedExecutorService::execute_sub_block`): if the state view feeding Move execution is `AggregatorOverriddenStateView`, `coin::supply<AptosCoin>()` resolves to `TOTAL_SUPPLY_AGGR_BASE_VAL ≈ 1.7×10^38`, the `assert!` fails, and the output is `ExecutionStatus::MoveAbort`, discarding the intended write set.
5. Compare `TransactionStatus`/`ExecutionStatus` and the presence of the mutated resource in each path's output: they differ for byte-identical input transaction and identical pre-execution ledger state, proving deterministic-execution divergence.

pub const TOTAL_SUPPLY_AGGR_BASE_VAL: u128 = u128::MAX >> 1;
#[derive(Clone)]
pub struct AggregatorOverriddenStateView<'a, S> {
    base_view: &'a S,
    total_supply_aggr_base_val: u128,
}

impl<'a, S: StateView + Sync + Send> AggregatorOverriddenStateView<'a, S> {
    pub fn new(base_view: &'a S, total_supply_aggr_base_val: u128) -> Self {
        Self {
            base_view,
            total_supply_aggr_base_val,
        }
    }

    fn total_supply_base_view_override(&self) -> Result<Option<StateValue>> {
        Ok(Some(StateValue::new_legacy(
            bcs::to_bytes(&self.total_supply_aggr_base_val)
                .unwrap()
                .into(),
        )))
    }
}

impl<S: StateView + Sync + Send> TStateView for AggregatorOverriddenStateView<'_, S> {
    type Key = StateKey;

    fn get_state_value(&self, state_key: &StateKey) -> Result<Option<StateValue>> {
        if *state_key == *TOTAL_SUPPLY_STATE_KEY {
            // TODO: Remove this when we have aggregated total supply implementation for remote
            //       sharding. For now we need this because after all the txns are executed, the
            //       proof checker expects the total_supply to read/written to the tree.
            self.base_view.get_state_value(state_key)?;
            return self.total_supply_base_view_override();
        }
        self.base_view.get_state_value(state_key)
    }
