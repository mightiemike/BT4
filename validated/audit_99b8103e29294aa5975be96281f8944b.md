### Title
Feature-gated WorkflowDonID binding allows any calling DON to spoof another DON's identity when addressing a shared executable capability - ([File: core/capabilities/remote/executable/request/server_request.go])

### Summary
The `executable` capability server exposes a `workflowDONBindingGate` that, when the setting `RemoteExecutableWorkflowDONBindingEnabled` is disabled (the non-default / rollout-gated state), performs no validation that `capabilityRequest.Metadata.WorkflowDonID` actually matches the authenticated `callingDonID` of the DON that transmitted the P2P message. This is directly analogous to the `swapCalculatingRebate` issue: a piece of "intended flexibility" (a caller-supplied identity field) is trusted without cross-checking it against the authenticated caller, letting one caller claim to be acting as a different, unrelated principal (a different Workflow DON) to a shared/multi-tenant service.

### Finding Description
The executable capability server receives P2P messages carrying `msg.CallerDonId` (the DON the message actually came from, resolved from the registered `workflowDONs` map) and a serialized `CapabilityRequest` whose `Metadata.WorkflowDonID` is fully attacker/caller-controlled data embedded in the payload [1](#0-0) .

The actual binding check lives in `executeCapabilityRequest`, gated behind `workflowDONBindingGate.Limit(ctx)`: [2](#0-1) 

When the gate evaluates to disabled, the code skips validating that `capabilityRequest.Metadata.WorkflowDonID != callingDonID`, so the caller-supplied `WorkflowDonID` in the payload is passed straight through to `capability.Execute(ctx, capabilityRequest)` unchecked. Any DON member that is a legitimate, registered member of *some* `callingDon` (verified only via `addRequester`/`slices.Contains(e.callingDon.Members, from)`) can set an arbitrary `Metadata.WorkflowDonID` in its request payload and have the capability treat the request as if it originated from a different workflow DON, entirely analogous to how `swapCalculatingRebate` let a caller assert someone else's `feeController` identity via a weak/loose check (`tx.origin`) instead of verifying real authorization.

The test suite explicitly documents this bypass: [3](#0-2) 

This confirms that with the gate disabled, a `WorkflowDonID` mismatch "still executes" — the request succeeds despite naming a DON that did not actually send it.

Downstream, capabilities that key sensitive behavior off `Metadata.WorkflowDonID` (e.g., confidential-workflow secrets/compute routing) rely on this binding as a genuine authorization signal, as shown by the caller-side code that explicitly sets `WorkflowDonID` to bind requests to the authenticated calling DON specifically to prevent spoofing when the gate is enabled: [4](#0-3) 

### Impact Explanation
If the `RemoteExecutableWorkflowDONBindingEnabled` setting is off (its rollout/gated state) for a deployment, a workflow node belonging to Workflow DON A can address a shared executable capability while asserting `Metadata.WorkflowDonID = B`, i.e., pretend the request originated from Workflow DON B. Any capability-side logic that trusts `Metadata.WorkflowDonID` for authorization, quota, tenant-isolation, or routing decisions (rather than re-deriving identity purely from `CallerDonId`) can be tricked into acting on behalf of, or attributing actions/resources to, a DON that never made the request — a workflow/job-ingestion and capability-routing trust-boundary violation with impact on tenant isolation and misattribution of privileged actions.

### Likelihood Explanation
Exploitation requires being a legitimate member of some registered Workflow DON with access to send `MethodExecute` messages to the capability server (i.e., an "unprivileged" workflow relative to the DON it wants to impersonate, but a privileged DON member overall) and for the deployment to have the binding gate disabled. This matches the report's own risk framing — it is intentionally configurable/rollout-gated rather than a raw unauthenticated bug, so likelihood depends on operational configuration, similar to how the OasisSwap issue depended on operators failing to detect/block the bypass.

### Recommendation
Do not allow `Metadata.WorkflowDonID` to be trusted unless it is verified equal to the authenticated `callingDonID` unconditionally (i.e., default the binding check to always-on, or fail closed rather than default-open), or, if flexibility must be preserved for staged rollout, ensure that no privileged/cross-tenant decision anywhere in the system relies on `Metadata.WorkflowDonID` while the gate is disabled. Add monitoring/alerting for `Metadata.WorkflowDonID != CallerDonId` mismatches to detect misuse the way the OasisSwap team proposed monitoring rebate abuse.

### Proof of Concept
The existing test demonstrates the bypass directly: [5](#0-4) 

With `limits.NewGateLimiter(false)` (gate disabled), a request is built via `buildPayload(callingDonID+99)` — i.e., `Metadata.WorkflowDonID` set to a DON ID that does not match the actual `callingDonID` of the sending peers — and `require.Equal(t, types.Error_OK, d.msgs[0].Error)` confirms the mismatched request is still executed successfully, proving the caller-asserted `WorkflowDonID` is unchecked against the authenticated sender's DON when the binding gate is off.

	// calling DON so it cannot be spoofed. All F+1 aggregated requests share this
	// payload (WorkflowDonID is part of the request hash), so a single check here
	// covers the quorum. The gate is guaranteed non-nil by NewServerRequest.

		lggr.Errorw("failed to evaluate workflow DON binding gate", "err", gerr)
		return nil, errors.New("failed to evaluate workflow DON binding gate")
	}
