## Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, letting replay-verify tooling accept a divergent state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function replay/backup tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) uses to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` stored on-chain. The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents as a known TODO.

The comment is a first-party admission of the exact broken invariant: the function is supposed to bind a replayed `TransactionOutput` to the *entire* authenticated `TransactionInfo`, but it structurally omits the state-checkpoint / hot-state-checkpoint / position-state-checkpoint hash fields that carry the JMT/SMT root commitments (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash` on `TransactionInfoV1`, see the builder at [2](#0-1) ). Those fields are precisely the "proof-bearing"/root-commitment values this task's State-Integrity Gate is scoped to (accumulator/Merkle roots bound to committed state).

This function is invoked from `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` as the sole consistency check between locally re-derived execution results and the ledger's authenticated `TransactionInfo`. If a re-executed transaction produces a state root (main state SMT/JMT root, hot-state root, or the position-state root used by the trading-native feature) that differs from the one recorded on-chain — whether due to a genuine bug in state application, a storage schema bug, or divergent replay logic — this check will not detect it, because the state/hot-state/position checkpoint hashes are simply never compared.

### Impact Explanation
This breaks the "Proof And Storage Pivots" invariant that "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" and "restore paths must preserve deterministic proof binding." Concretely:
- `replay_on_archive` and the debugger's replay-verify path are the tools operators/auditors use to prove that historical execution matches what is committed on Aptos mainnet. With this gap, such verification can report success even when the state root diverges — a false attestation of ledger integrity.
- Once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (position-state root) is enabled, a bug corrupting the position-state root (e.g. in the native position write handling in `execution/executor/src/workflow/do_state_checkpoint.rs`'s `compute_position_checkpoint`, or in `storage/aptosdb/src/db/aptosdb_writer.rs`'s `position_summary_at_commit`) would not be caught by replay verification, since that's the only check gating trust in this feature's correctness before rollout.

This qualifies as a State-Integrity Gate hit under "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "Wrong accumulator root ... transaction proof ... accepted as valid," because the verification tool's job is exactly to bind a proof/root to its correct execution context, and it fails to do so for three of the five commitment fields in `TransactionInfoV1`.

### Likelihood Explanation
The gap is unconditionally present today (not merely theoretical) — every call to `ensure_match_transaction_info` across all three call sites silently skips checkpoint-hash validation. It is a real, standing hole in Aptos's replay-verification safety net. Its practical severity is currently bounded because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is described as not yet enabled and `hot_state_checkpoint_hash` is also not populated on mainnet/testnet per the code comments elsewhere, but the *existing* `state_checkpoint_hash` field is always populated and is also never checked by this function — meaning any divergence in the main state root during replay verification (not just the not-yet-shipped trading-native feature) would already go undetected by this tool today.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (already-active field) and, once respectively enabled, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against the values computed from local replay, failing loudly on any mismatch, as the existing TODO comment itself specifies.

### Proof of Concept
Not applicable/available from static analysis alone — the missing checks are visible directly in the source (`types/src/transaction/mod.rs:2139-2204`); a full PoC would require constructing a divergent local execution (e.g. altering a state write while keeping the write-set hash/event hash the same, which is not straightforward) or, more directly, instrumenting `replay_on_archive` against a chunk with a deliberately wrong `state_checkpoint_hash` in the fed `TransactionInfo` and observing that `ensure_match_transaction_info` returns `Ok(())`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
