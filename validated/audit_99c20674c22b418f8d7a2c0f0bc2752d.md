### Title
`ensure_match_transaction_info` omits checkpoint-hash validation, allowing replay/restore to accept a wrong state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole function used to reconcile a freshly-computed VM execution result against the `TransactionInfo` that was persisted/backed-up for a version. It is called from `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` — i.e. it is the integrity gate used both during chunk-based replay of backup data (part of the restore/replay pipeline that ultimately re-derives and commits ledger state) and stand-alone replay-verify tooling. The function validates `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash`, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed values, as the code comment itself documents.

### Finding Description [1](#0-0) 

The function computes and compares `write_set_hash` and `event_root_hash` against the `txn_info`'s stored hashes, but the state-checkpoint-related fields recorded in `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash` — see the `TransactionInfo`/`TransactionInfoV1` builder fields) are never compared: [2](#0-1) 

These checkpoint hashes are exactly the values that bind a transaction's execution result to the durable JMT/state-merkle root (and, per the comment, to the "trading-native" position state root) that gets committed into the ledger accumulator via `TransactionInfo::hash()` and verified by all downstream proofs (`TransactionInfoWithProof::verify`, state-snapshot restore root checks, etc.). By skipping this comparison, `ensure_match_transaction_info` can return `Ok(())` even when the locally re-executed state root diverges from the state root that was actually committed/backed-up on-chain.

This check is consumed directly in the chunk-replay verify path used by the backup/restore + replay tooling: [3](#0-2) 

Since the state-checkpoint hash is never independently verified here, an operator running `db-tool replay-on-archive` (or the equivalent chunk-executor / aptos-debugger replay paths that call the same function) will get a clean "verify passed" result even if the recomputed state-merkle root, hot-state root, or the new trading-native position-state root differs from what is recorded in the archived `TransactionInfo`. This is precisely the "committed state that differs from the correct VM result... accepted as valid" and "authenticated ... output bound to the wrong ... proof context" class of bug: the invariant that a `TransactionInfo`'s checkpoint hash faithfully represents the resulting ledger state is silently unenforced by the one function whose job is to enforce it.

### Impact Explanation
If storage-level state (state-merkle DB, hot-state, or the newer position-state-checkpoint used by trading-native features) becomes corrupted or diverges from the deterministic VM-recomputed state — whether from a storage bug, a bad restore, or a malicious archive/backup source — this divergence would not be caught by replay-verify, chunk-executor's post-execution/output-match checks that route through this function, or the debugger's analogous checks. This can mask silent state corruption or a non-deterministic/hard-fork divergence, which is otherwise exactly the kind of check replay-verify exists to catch. Impact is High: it defeats a primary integrity safeguard for detecting divergent, hard-fork-only state, and any tooling/pipeline relying on `ensure_match_transaction_info`'s `Ok(())` result as proof of correctness receives a false assurance.

### Likelihood Explanation
Likelihood is Low-to-Medium: this does not by itself let an unprivileged attacker corrupt consensus-committed state (consensus-level commit still uses the full accumulator/root-hash verification elsewhere), but it does mean that any bug or manipulation that produces a wrong state/hot-state/position-state root will go undetected by every one of the 4 call sites of `ensure_match_transaction_info`, which is the codebase's designated “this must match” assertion for replay integrity. The code comment in-repo already flags this exact gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), confirming it is a known, unresolved gap rather than a speculative one.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on the transaction/output) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, erroring out on mismatch just as is done for `write_set_hash` and `event_root_hash`. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` as the existing TODO comment states, and applied uniformly to all 4 callers (`chunk_executor`, `replay_on_archive`, `aptos-debugger`, `cli/commands.rs`).

### Proof of Concept
1. Take an `ExecutedOutput`/`TransactionOutput` whose recomputed state (e.g., via a corrupted state-merkle DB, or a modified/malicious backup archive) produces a different state root than the archived `TransactionInfo.state_checkpoint_hash` (or `position_state_checkpoint_hash` under trading-native), while write_set bytes, gas, status, and events remain identical.
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`, `execute_and_verify` → `ensure_match_transaction_info`) against this archive.
3. Because `ensure_match_transaction_info` never compares checkpoint hashes, the call returns `Ok(())` and the transaction is reported as verified, even though the actual committed state root diverges from the recomputed one — a silent replay-verify false pass on a state-corruption/hard-fork-class divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
