### Title
Wallet Contract `has_in_flight_tx` lock is not resettable after a rolled-back callback, permanently freezing the ETH-implicit account — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` that every ETH-implicit account is deployed with uses a single boolean flag, `has_in_flight_tx`, as a mutual-exclusion lock so that only one Ethereum-style transaction is "in flight" at a time. `rlp_execute` sets the flag to `true` before returning a `Promise` and refuses to accept any new transaction while it is `true` [1](#0-0) . The flag is reset to `false` only inside the various callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), and in every case the reset is the *first* statement of the callback [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) .

Because the runtime's receipt-execution model rolls back **all** state changes of a receipt the instant that receipt's execution errors — including in-memory writes that happened earlier in the same function, such as the `has_in_flight_tx = false` assignment — any failure that occurs inside one of these callback functions (out-of-gas, host-function panic, deserialization panic, etc.) after that first line but before the receipt otherwise completes successfully causes the flag write to be discarded along with everything else. The flag remains stuck at `true` forever. Since `rlp_execute` is the *only* entry point into the account (ETH-implicit accounts cannot have a full access key added nor be deleted), the account becomes permanently unable to execute any future action, freezing any $NEAR (or NEP-141 tokens reachable only through this account) held by it — the same fund-freezing bug class as the reported `claim_revenue`/`withdraw_token` issue, where an unresettable state flag/threshold gate permanently blocks a legitimate balance-moving operation.

### Finding Description
`rlp_execute` is guarded by the lock: if `has_in_flight_tx` is already `true` it rejects the call outright [6](#0-5) . Otherwise it sets the lock and returns a `Promise` chain terminating in one of the callback methods [7](#0-6) .

Every callback resets the lock as its very first action:
- `address_check_callback`: `self.has_in_flight_tx = false;` then processes `env::promise_result(0)`, deserializes JSON, and may build a further outgoing promise (`create_ban_relayer_promise`/`action_to_promise`) [8](#0-7) .
- `nep_141_storage_balance_callback`: same pattern, with additional JSON deserialization and promise construction after the reset [9](#0-8) .
- `rlp_execute_callback`: resets the lock, then inspects `promise_results_count()`, and on `PromiseResult::Failed` creates a refund `Promise::new(...).transfer(...)` [10](#0-9) .

Per the documented atomicity invariant of the runtime, **a receipt whose action result is `Err` triggers a full `state_update.rollback()`**, discarding every state change performed during that receipt, and the receipt outcome records the failure instead of persisting any of the intermediate writes [11](#0-10) . Consequently, if any code path in a callback *after* the `has_in_flight_tx = false` assignment fails — e.g., the callback runs out of the small statically-reserved gas (`RLP_EXECUTE_CALLBACK_GAS` = 5 Tgas, or the slightly larger `ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) while doing JSON parsing, promise construction, or the refund transfer, or the underlying wasm host call panics for any other reason — the callback receipt as a whole fails. The rollback erases the `has_in_flight_tx = false` write together with everything else, so the persisted contract state still has `has_in_flight_tx == true`.

There is no other method on `WalletContract` that can reset this flag; it is not owner-callable, not time-based, and has no cooldown/expiry. The contract's own doc comment acknowledges the invariant is manually maintained ("`has_in_flight_tx` must be `true` when a mutable method... returns a promise and `false` otherwise") [12](#0-11)  but nothing enforces that the reset itself is failure-proof.

This is structurally the same bug class as the reported `claim_revenue`/`withdraw_token` issue: a single mutable guard/threshold that gates the *only* path to move funds can be driven into a state from which the legitimate operation (here, any further `rlp_execute` call) can never succeed again, with no recovery path.

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, `rlp_execute` unconditionally returns the "transaction already in progress" error for every future call, for the lifetime of the account [13](#0-12) . Because ETH-implicit accounts can only be operated through this contract's `rlp_execute` entry point — they cannot have a full access key added and cannot be deleted [14](#0-13)  — this permanently freezes any $NEAR balance held directly by the account and any NEP-141/other token balances that require an outgoing call signed by the account (transfers, ERC-20 emulation, `AddKey`, etc.). This matches the "permanently frozen funds" impact category.

### Likelihood Explanation
Triggering the bug requires only a single crafted `rlp_execute` call whose downstream callback fails after resetting the flag in memory — e.g., a relayer/attacker (or even an honest but gas-constrained relayer) attaching insufficient total prepaid gas so the reserved callback gas is exhausted mid-execution, or supplying inputs that cause any panic inside the callback's JSON/AccountId handling. Because relayers (who are untrusted, permissionless third parties by design of the wallet contract) fully control the gas budget and the encoded action/parameters of each `rlp_execute` call, and because the contract explicitly supports multi-hop callback chains (`address_check_callback`, `nep_141_storage_balance_callback`) with tight, hard-coded gas reservations, this is plausibly reachable without any special privileges — hence Medium likelihood.

### Recommendation
- Do not treat the flag reset as "safe by virtue of being the first statement." Instead, ensure the lock reset is committed independently of the rest of the callback logic (e.g., reset the lock in a separate, prior receipt/state commit, or make every subsequent operation in the callback infallible/panic-free with respect to gas and parsing).
- Add an explicit, permissionless recovery path (e.g., a time-based expiry on `has_in_flight_tx`, or a self-callable "clear stuck lock" method gated on a minimum elapsed block height since the lock was set) so a single failed callback cannot permanently brick the account.
- Audit all `#[private]` callbacks for panics/gas-exhaustion paths that occur after the lock reset and either move that logic earlier (before the reset) or wrap it so a failure cannot cause a full-receipt rollback that reverts the reset.

### Proof of Concept
1. Deploy/derive an ETH-implicit account with the Wallet Contract as its (global) contract, as in `test_wallet_contract_interaction` [15](#0-14) .
2. Have a relayer submit an `rlp_execute` transaction whose encoded action routes through a multi-hop callback (e.g., an ERC-20 transfer emulation, which goes through `nep_141_storage_balance_callback` and then chains a `storage_deposit` + transfer before finally calling `rlp_execute_callback`) [16](#0-15) , while attaching only just enough total prepaid gas to cover the happy path and starving the reserved callback gas (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) so that the callback runs out of gas partway through, after `self.has_in_flight_tx = false;` has executed in WASM but before the receipt finishes successfully.
3. Because the callback receipt fails (out-of-gas), the runtime rolls back all of the callback's state changes (per the atomicity invariant), so persisted state still has `has_in_flight_tx == true`.
4. Submit any subsequent `rlp_execute` call from the legitimate key holder: it is rejected with "transaction already in progress, please try again later," permanently, because no code path exists to clear the flag outside of a (now unreachable) successful callback.

**Uncertainty/limitations:** I was not able to execute this scenario against a live node to empirically confirm that the specific gas budgeting in `inner_rlp_execute`/the callbacks can actually be driven into an out-of-gas panic *after* the flag reset under realistic relayer-supplied gas values (this would require dynamic testing with the actual `near-workspaces` sandbox, which I do not have access to in this ask-only session). The root-cause mechanism (rollback-on-failure erasing the reset, with no alternate recovery path) is directly supported by the cited code and the documented atomicity invariant, but the exact minimal gas/parameter values needed to trigger a mid-callback failure were not derived here.

    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

                {
                    Ok(p) => p,

                    }
                }
            }

                // receiver_id is not registered so we must call `storage_deposit` first.

                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(

                            ),
                        });
                    }
                };

                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
