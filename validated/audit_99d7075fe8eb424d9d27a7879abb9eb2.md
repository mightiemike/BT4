### Title
Transaction-backup restore persists unauthenticated write sets that are never checked against `TransactionInfo::state_change_hash` - ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
The `Vault._transferAndCheckUnderlying()` bug is a class of "the value that gets committed is never checked against the value that was supposed to be authenticated." The Aptos-native analog is in the transaction-chunk backup/restore path: `WriteSet`s read from a backup manifest file are deserialized and carried alongside verified transactions/`TransactionInfo`s, but they are never checked against the `state_change_hash` field of the corresponding `TransactionInfo`, unlike the transaction-output verification path which explicitly performs this check.

### Finding Description
In `LoadedChunk::load` (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs:99-186`), each backup record is deserialized as a 5-tuple `(txn, aux_info, txn_info, events, write_set)`: [1](#0-0) 

The code then builds a `TransactionListWithProofV2` from `txns`, `event_vecs`, and `txn_infos` — note `write_sets` is deliberately kept out of this structure — and calls `.verify(...)`: [2](#0-1) 

`TransactionListWithProof::verify` only checks the transaction hash, event root hash, and the accumulator inclusion proof of `TransactionInfo` against the ledger info; it has no notion of `write_set` at all, because `write_set` is not one of its fields. By contrast, the sibling type `TransactionOutputListWithProof::verify` (used for transaction-output backups) explicitly computes `CryptoHash::hash(&txn_output.write_set)` and checks it equals `txn_info.state_change_hash()`: [3](#0-2) 

This proves that `state_change_hash` in `TransactionInfo` is the intended cryptographic commitment binding a write set to its transaction/version in the accumulator, and that Aptos's own code enforces this binding on one restore path (outputs) but not the other (plain transactions, e.g. full-history/genesis-forward backup).

After `LoadedChunk::load` returns, `write_sets` is later passed unchanged into `restore_handler.save_transactions(...)`: [4](#0-3) 

which forwards straight to `restore_utils::save_transactions_impl`, where the write set is written into `WriteSetDb` and — if `kv_replay` is enabled — fed into `state_store.calculate_state_and_put_updates(&StateUpdateRefs::index_write_sets(...))`, i.e. it is used to compute and persist the actual key-value state of the ledger: [5](#0-4) 

At no point along this call chain (`LoadedChunk::load` → `save_before_replay_version` → `RestoreHandler::save_transactions`/`save_transactions_and_replay_kv` → `restore_utils::save_transactions_impl`) is `CryptoHash::hash(&write_set)` compared against `txn_info.state_change_hash()`. The only authenticated fields are the transaction itself and its `TransactionInfo` (via the accumulator proof); the write set is trusted purely because it was co-located in the same backup file.

### Impact Explanation
A backup file (or the storage backend serving it, e.g. an S3 bucket, a compromised/misconfigured backup archive, or bit-corruption that happens to still bcs-deserialize) can supply an arbitrary `WriteSet` for a given, otherwise validly-proven transaction/version. Because the write set is never checked against the accumulator-protected `state_change_hash`, that attacker/corruption-controlled write set is committed into `WriteSetDb` and, when `kv_replay` is used, directly folded into the live state tree (`calculate_state_and_put_updates`) and marked committed via `LedgerCommitProgress`/`OverallCommitProgress`. This is exactly the "committed state that differs from the correct VM result / corrupts durable ledger data" case in the State-Integrity Gate: a node restoring from such a backup would end up with a state root/state contents that diverge from what every other correctly-restored node has for the same, ledger-info-verified version, while still reporting the version as fully verified and committed.

### Likelihood Explanation
This requires control over, or corruption of, backup artifacts (the storage backend or transmission of the backup manifest/chunk file), which is a real-world operational trust boundary distinct from "malicious validator/consensus" behavior explicitly excluded by scope. Anyone operating backup infrastructure, or an attacker able to tamper with backup blobs before restore (supply-chain/storage compromise on the backup bucket) can trigger this without needing any validator keys or consensus power — the restore code is the only gate, and it is missing the check. This is a genuine local code defect (missing invariant enforcement), not merely a restatement of the original ERC20-fee report.

### Recommendation
In `LoadedChunk::load`, after building and verifying `txn_list_with_proof`, additionally verify for every entry that `CryptoHash::hash(&write_sets[i]) == txn_infos[i].state_change_hash()`, mirroring the check already performed in `TransactionOutputListWithProof::verify`. Reject the chunk (return an error) if any mismatch is found, before any data reaches `restore_handler.save_transactions`/`save_transactions_and_replay_kv`.

### Proof of Concept
1. Take a legitimate transaction backup chunk file whose transactions/`TransactionInfo`s validate against the accumulator/ledger-info proof.
2. Modify only the `write_set` component of one record (the last element of the bcs-encoded tuple) to an arbitrary `WriteSet`, leaving `txn`, `aux_info`, `txn_info`, and `events` untouched.
3. Run `TransactionRestoreController`/`TransactionRestoreBatchController::run_impl` against this tampered chunk.
4. `LoadedChunk::load` succeeds because `txn_list_with_proof.verify(...)` never examines `write_sets`.
5. `restore_handler.save_transactions_and_replay_kv` (or `save_transactions`) persists the tampered `WriteSet` into `WriteSetDb`, and if `kv_replay` is set, it is applied to compute the on-disk state via `calculate_state_and_put_updates`, corrupting the restored ledger's state for that version while `LedgerCommitProgress`/`OverallCommitProgress` mark it as fully committed.
