### Title
Unauthenticated `citrea_haltCommitments` RPC call lets any caller halt sequencer commitment production - ([File: crates/common/src/rpc/auth.rs])

### Summary
The `Auth` RPC middleware only requires an API key for a hard-coded allowlist of "protected" methods (`backup_create`, `backup_validate`, `backup_info`). Every other JSON-RPC method, including the sequencer-only `citrea_haltCommitments` / `citrea_resumeCommitments` methods, is passed straight through to the service without any authentication check.

### Finding Description
The binding that should hold is: *only the sequencer operator can mutate the sequencer's commitment-production state*. Instead, any unauthenticated JSON-RPC caller who can reach the sequencer's RPC endpoint can flip that state.

`Auth::call` short-circuits authentication for any method not in `PROTECTED_METHODS`: [1](#0-0) 

`citrea_haltCommitments` / `citrea_resumeCommitments` are registered as ordinary sequencer RPC methods with no additional authorization check in the handler itself: [2](#0-1) 

The handler simply forwards a `SequencerRpcMessage::HaltCommitments` / `ResumeCommitments` message to the sequencer runner: [3](#0-2) 

The runner's main loop consumes this message and toggles a channel that the `CommitmentService` reads, immediately stopping (or resuming) the periodic check that decides whether to submit a `SequencerCommitment` to the DA layer: [4](#0-3) [5](#0-4) 

The `api_key` in `RpcConfig` is optional and, more importantly, is only consulted by the `Auth` middleware for the three `backup_*` methods; it plays no role in gating `citrea_haltCommitments`/`citrea_resumeCommitments`: [6](#0-5) 

This matches the report-class hint (a privileged control-plane action executed without any authorization/state check), analog-mapped here to an unauthenticated RPC call mutating sequencer node state rather than a Solidity emergency pause.

### Impact Explanation
This falls squarely under the explicitly listed High-impact class: "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`." Halting commitments indefinitely prevents the sequencer from submitting `SequencerCommitment`s to the DA layer, which stalls proof generation and settlement for the rollup's state roots, since downstream consumers (full nodes, provers, batch-prover) rely on these commitments being posted to L1. An attacker with network access to the sequencer's RPC port (no credentials required) can freeze the commitment pipeline at will and later resume it, without ever triggering the `Auth` API-key check.

### Likelihood Explanation
The bypass requires no privileged role, no key, and no special access beyond reaching the RPC endpoint - which is the same network surface exposed for all other unauthenticated methods (e.g., `eth_sendRawTransaction`). Given `PROTECTED_METHODS` is a static, incomplete allowlist rather than a default-deny list, any newly added sensitive RPC method (like these two) is unauthenticated by default unless explicitly added to that list, making this a systemic gap rather than a one-off oversight.

### Recommendation
Change the `Auth` middleware to default-deny (require the API key) for all non-public/state-mutating admin methods, or explicitly add `citrea_haltCommitments` and `citrea_resumeCommitments` to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`.

### Proof of Concept
1. Start a sequencer node with default/no `api_key` (or with an `api_key` set - it is irrelevant since these methods aren't in `PROTECTED_METHODS`).
2. From any unauthenticated client, call:
   ```
   curl -X POST http://<sequencer-rpc>:<port> \
     -H "Content-Type: application/json" \
     -d '{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}'
   ```
3. Observe the `Auth` middleware passes the request through (method not in `PROTECTED_METHODS`), the runner forwards `HaltCommitments`, and `CommitmentService.is_producing_commitments` becomes `false`, matching the existing test scenario at [7](#0-6)  which shows no new L1 commitment blocks are produced after this call - but here performed without any credentials.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }
