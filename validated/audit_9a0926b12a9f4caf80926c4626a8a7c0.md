### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant session confusion via header substitution - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
The reported bug class is a missing authorization/binding check on a function that shares a trust boundary with sibling functions that do enforce it (`fillCloseRequest`/`openPosition` lacking `notSuspended` while `withdraw`/`withdrawTo` enforce it). The closest unprivileged analog in shopify-app-js is in webhook authentication: the HMAC that proves a webhook request came from Shopify is computed strictly over the raw body, while the shop-identifying header (`X-Shopify-Shop-Domain`) that downstream code trusts to select which merchant's offline session/access token to use is never included in that signature.

### Finding Description
`validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` computes the local HMAC solely from `rawBody`: [1](#0-0) 

`validateFactory`/`checkWebhooksHeaders` in `packages/apps/shopify-api/lib/webhooks/validate.ts` then reads the `domain` header only to confirm it's *present*, not that it is cryptographically bound to the already-verified body: [2](#0-1) 

Downstream, `authenticateWebhookFactory` (in shopify-app-remix and shopify-app-react-router) takes `check.domain` directly — with no further sanitation via `sanitizeShop` — and uses it to look up the offline session/access token for that shop: [3](#0-2) 

The fulfillment-service handler exhibits the identical pattern, pulling the shop straight from the header and feeding it to `ensureValidOfflineSession`: [4](#0-3) 

Because the signature check only proves "this body was HMAC'd with our app secret" and never proves "this body came paired with this particular shop domain," any request whose `rawBody` yields a valid HMAC (e.g., a replayed/captured webhook payload) can have its `X-Shopify-Shop-Domain` header freely substituted by a network intermediary or by the delivering party without invalidating the signature — directly analogous to the `fillCloseRequest` situation where a sibling, security-relevant field (PartyB's suspended state) was left unchecked despite a shared trust boundary with the withdraw path.

### Impact Explanation
If a webhook body's HMAC does not vary per-shop in a way an attacker can't reconstruct (e.g., empty or attacker-influenced payload from a merchant-controlled shop, or a payload that is otherwise reusable), swapping the domain header lets a malicious or compromised delivery path get the app to load and act with **shop B's offline access token/session** while it believes it is processing shop A's event — a cross-tenant confusion in the session-lookup path. This maps to the "session-storage injection / cross-tenant access" acceptance criteria: the shop used to select which merchant's session/access token gets attached to the resulting `admin` client is attacker-influenceable independent of the signature check.

### Likelihood Explanation
Exploitation requires the attacker to already possess a validly-signed webhook body (e.g., captured from their own installed shop, since `apiSecretKey` is shared across all shops of a given app) and the ability to alter headers before they reach the app's endpoint (e.g., a malicious/compromised proxy, replay tooling, or an app architecture that fans out webhook delivery through an intermediary they control). This is more constrained than a fully anonymous, zero-precondition attack, but it does not require any secret material or privileged Shopify credentials — only a legitimately-signed payload from any shop that has installed the app, which is available to any merchant/customer able to trigger events on their own installed store.

### Recommendation
Bind the shop domain (and other identity-bearing headers such as topic/webhook-id/api-version) into the HMAC computation, or otherwise cryptographically tie the header used for session lookup to the verified body, mirroring how `notSuspended` needed to be applied uniformly across `withdraw`, `openPosition`, and `fillCloseRequest`. At minimum, run `sanitizeShop` on `check.domain` before using it for session lookup, and document/enforce that webhook delivery endpoints must not sit behind any component that can rewrite headers after Shopify's original delivery.

### Proof of Concept
1. Install the app on Shop A and Shop B (same app, same shared `apiSecretKey`).
2. Capture a legitimately-delivered webhook for Shop A (`rawBody`, valid `X-Shopify-Hmac-Sha256`, headers including `X-Shopify-Shop-Domain: shop-a.myshopify.com`).
3. Replay the same `rawBody` and HMAC header to the same webhook endpoint, but rewrite `X-Shopify-Shop-Domain` to `shop-b.myshopify.com`.
4. `validateHmacFromRequestFactory` recomputes the HMAC purely from `rawBody`/`apiSecretKey` and returns `valid: true`, since domain is not part of the signed material (`packages/apps/shopify-api/lib/utils/hmac-validator.ts` lines 168-199).
5. `authenticateWebhookFactory` proceeds to call `ensureValidOfflineSession(params, check.domain)` with the attacker-supplied `shop-b.myshopify.com`, loading Shop B's offline session/access token to process a webhook whose payload was never actually generated for Shop B (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts` lines 33-52).

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
