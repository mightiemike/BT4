### Title
Open Redirect via Backslash-Based Protocol-Relative URLs Bypassing `isSafe`/`sanitizeRedirectUrl` - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts])

### Summary
`sanitizeRedirectUrl`'s `isSafe` helper only checks the *raw* `redirectUrl` string against `FILE_URI_MATCH` (`/\/\/\//`, three literal forward slashes) and later checks the *parsed* `url.pathname` against `INVALID_RELATIVE_URL` (`/[/\\][/\\]/`). Neither regex is applied to a mixed slash/backslash prefix such as `"/\evil.com"`, but the WHATWG URL parser (used by Node's/browser's `URL`) treats a leading `"/" + "\"` sequence on a special scheme (`http`/`https`) as a network-path (protocol-relative) reference, moving `evil.com` into the parsed `host`, not the `pathname`. The result is that `new URL("/\\evil.com", APP_URL)` resolves to `https://evil.com/`, which passes all subsequent checks (`VALID_PROTOCOLS` includes `https:`, `requireSSL` satisfied) and is returned as a "safe" URL, producing a genuine open redirect out of `APP_URL`'s origin.

### Finding Description
The relevant checks are: [1](#0-0) 

The `FILE_URI_MATCH` and `WHITESPACE_CHARACTER` checks run against the *raw* attacker-supplied `redirectUrl`, before parsing. A payload like `"/\evil.com"` contains only a single `/` followed by a single `\`, so it does not match `/\/\/\//` (needs three consecutive `/`) nor contains whitespace, so it passes through untouched.

The URL is then constructed: [2](#0-1) 

Per the WHATWG URL Standard, when parsing a relative reference against a special-scheme base (`https:`), a backslash `\` is treated identically to a forward slash `/` in the "relative slash state". Consequently `"/\evil.com"` is interpreted as a network-path reference: the parser consumes the leading `/\` as an authority-start marker and assigns `evil.com` to the `host` component rather than the `pathname`. The resulting parsed URL is `https://evil.com/`, with `pathname === "/"`.

Because `INVALID_RELATIVE_URL` is tested against `url.pathname` (which is now just `"/"`), the check never sees the backslash sequence that caused the origin hijack — the malicious characters were already consumed into the `host` during parsing, before this check runs. The subsequent `VALID_PROTOCOLS` (`https:`) and `requireSSL` checks are satisfied because the scheme is still `https:`. `isSafe` therefore returns `true`, and `sanitizeRedirectUrl` returns `new URL("/\\evil.com", APP_URL)` → an object whose `origin` is `https://evil.com`, not `APP_URL`'s origin, silently bypassing the intended `DESTINATION_ALLOWLIST` invariant (redirect confined to the app's own origin).

This is reachable from `renderAppBridge`, which passes an untrusted `redirectTo.url` straight into `sanitizeRedirectUrl` and embeds the resulting (attacker-controlled) origin into a `window.open(...)` script served to the merchant's authenticated admin browser: [3](#0-2) 

The identical vulnerable logic exists in the sibling package: [4](#0-3) 

### Impact Explanation
An unprivileged attacker can craft a URL/query parameter that ends up as `redirectTo.url` in `renderAppBridge` (or any other caller of `sanitizeRedirectUrl`), causing the app to serve a `window.open("https://evil.com/", ...)` script to an authenticated merchant's embedded-admin browser session. This is an open redirect out of the app's trusted origin, which can be leveraged for App Bridge/session-token phishing (tricking the merchant's browser/App Bridge context into interacting with attacker infrastructure while still embedded/trusted), matching Shopify's "open redirect with real consequence" bounty impact class.

### Likelihood Explanation
No special privileges are required — any anonymous or single-merchant-driven request that can set the `redirectTo.url`/redirect query value reaching `sanitizeRedirectUrl` (e.g., via OAuth flow redirect parameters or any endpoint using `renderAppBridge`) can trigger this. The payload is trivial to construct (`"/\evil.com"` or `"\/\/evil.com"` variants) and does not depend on any secret, non-default configuration, or race condition — it is fully deterministic and repeatable.

### Recommendation
Do not rely on regexes matching literal `/` sequences alone. After parsing, verify that the resulting `url.origin` (or `url.host`) exactly equals the trusted `domain`'s origin for any redirect that is supposed to stay same-origin, e.g.:
```ts
const base = new URL(domain);
if (url.origin !== base.origin) return false;
```
Additionally/alternatively, reject raw `redirectUrl` strings containing backslashes (`\`) before parsing, since backslashes have no legitimate purpose in relative app-internal paths and are the mechanism the WHATWG parser uses to normalize protocol-relative bypasses.

### Proof of Concept
```ts
import {sanitizeRedirectUrl} from '../validate-redirect-url';

const APP_URL = 'https://my-app.example.com';

it('BUG: backslash payload escapes to a different origin', () => {
  const result = sanitizeRedirectUrl(APP_URL, '/\\evil.com');
  // Expected (intended invariant): result.origin === new URL(APP_URL).origin
  // Actual: result.origin === 'https://evil.com'
  expect(result.origin).toBe('https://evil.com'); // demonstrates the bypass
});
```
Request-level PoC: `renderAppBridge(config, request, {url: '/\\evil.com'})` produces a response body containing `<script>window.open("https://evil.com/", "_top")</script>`, served with the merchant's authenticated session context.

const FILE_URI_MATCH = /\/\/\//;
const INVALID_RELATIVE_URL = /[/\\][/\\]/;
const WHITESPACE_CHARACTER = /\s/;
const VALID_PROTOCOLS = ['https:', 'http:'];

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }
