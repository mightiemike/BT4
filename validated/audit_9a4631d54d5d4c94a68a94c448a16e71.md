## Analysis Summary

The reported bug class is: **critical accounting logic relies on an instantaneous, single-block on-chain state variable (Uniswap V3 `slot0`) with no deviation/TWAP check, allowing manipulation of amounts computed from it (LP mint amounts).** The closest reachable analog in java-tron is the TRC10 `Exchange` (Bancor-style two-token pool) module, specifically `ExchangeInjectActuator`, which computes the required deposit ratio directly from the pool's live `firstTokenBalance`/`secondTokenBalance` with no deviation bound or user-supplied slippage limit. The pool's spot balances are freely and atomically movable by any unprivileged user via `ExchangeTransactionActuator`, which swaps tokens using the current `sellTokenBalance`/`buyTokenBalance` through the Bancor formula in `ExchangeProcessor`/`SafeExchangeProcessor`: [3](#0-2) [4](#0-3) 

### Title
Unprotected use of instantaneous exchange pool balances for `ExchangeInject` ratio calculation enables sandwich manipulation - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes `anotherTokenQuant` — the amount of the paired token the injector must deposit — purely from the exchange's *current* `firstTokenBalance`/`secondTokenBalance`, exactly as Real Wagmi's `Multipool` computed LP amounts purely from Uniswap V3's instantaneous `slot0`. Both use the freshest, single-block on-chain state with no deviation check against a time-weighted reference.

### Finding Description
`doValidate()` and `execute()` in `ExchangeInjectActuator` derive the counter-token quantity as a straight ratio of the two live pool balances:
```
anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance
``` [5](#0-4) 

These balances are mutated in the same block by any account calling `ExchangeTransactionActuator`, which executes swaps against the same Bancor-relay formula using the live balances with no TWAP or historical reference: [6](#0-5) 

Critically, unlike a Uniswap-V2-style `addLiquidity`, `ExchangeInjectContract` provides no user-supplied minimum/maximum bound (no slippage parameter) on the computed `anotherTokenQuant` — the actuator computes it and unconditionally debits the injector's account for that amount: [7](#0-6) 

Consequently an attacker can, in the same block:
1. Send an `ExchangeTransactionContract` swap that skews `firstTokenBalance`/`secondTokenBalance` far from the pool's fair/weighted price.
2. Let the pending `ExchangeInjectContract` (from the exchange creator, the only account permitted to inject per the `is not creator` check) execute at the skewed ratio.
3. Reverse the swap afterward, extracting value because the injector was forced to deposit an unfavorable ratio determined entirely by the attacker-controlled spot balances.

### Impact Explanation
The injector (exchange creator) is forced into depositing tokens at an attacker-dictated ratio with no ability to bound the counter-token amount, resulting in economic loss/value extraction analogous to the Real Wagmi finding — the accounting variable used to settle a deposit is derived from a trivially-manipulable single data point. This affects on-chain settlement/accounting of the `Exchange`/`ExchangeV2Store` balances that other users rely on for subsequent swaps.

### Likelihood Explanation
`ExchangeTransactionContract` is callable by any unprivileged account with sufficient token/TRX balance and no special permission, so front-running/sandwiching an `ExchangeInject` transaction (which is visible in the mempool prior to inclusion) is fully within reach of an ordinary user. The absence of any slippage/deviation guard on `anotherTokenQuant` makes exploitation straightforward whenever a creator injects liquidity into a low-liquidity exchange pool.

### Recommendation
Add a user-supplied bound (e.g., `expectedAnotherTokenQuant` with a min/max tolerance) to `ExchangeInjectContract`, and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate()`/`execute()`, rejecting the transaction if the live pool ratio has deviated beyond the caller's tolerance — mirroring the `_checkPriceDeviation` fix applied upstream in Real Wagmi's `Multipool`.

### Proof of Concept
1. Exchange pool has `firstTokenBalance = 1000`, `secondTokenBalance = 1000`.
2. Creator broadcasts `ExchangeInjectContract(tokenId=first, quant=100)`, expecting `anotherTokenQuant ≈ 100`.
3. Attacker, seeing this in the mempool, submits `ExchangeTransactionContract` swapping a large amount of `secondToken` for `firstToken`, driving `firstTokenBalance` down and `secondTokenBalance` up sharply (via `ExchangeProcessor.exchange`) [3](#0-2) , ordered before the creator's inject in the same block.
4. The creator's `ExchangeInject` now executes with skewed `firstTokenBalance`/`secondTokenBalance`, computing a much larger `anotherTokenQuant` than intended [5](#0-4) , and unconditionally deducts it from the creator's balance/assets [8](#0-7) .
5. Attacker reverses the swap, recovering the original ratio plus the value extracted from the creator's oversized deposit — with no on-chain check preventing this because no deviation/TWAP or slippage bound exists.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
