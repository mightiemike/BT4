## Title
Hardcoded gas allocated to the external Address Registrar callback can cause a relayer's attached deposit to be permanently lost - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (the eth-implicit account emulation contract) hardcodes gas amounts for calls into external, independently-upgradeable contracts, exactly like the reported Chainlink VRF issue hardcodes `minimumRequestConfirmations`/`callbackGasLimit` for an external oracle whose validation rules can change. In `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`, `REGISTRAR_LOOKUP_GAS` is a fixed `Gas::from_tgas(5)` attached to a cross-contract call into the external `ADDRESS_REGISTRAR_ACCOUNT_ID` contract's `lookup` method [1](#0-0) , invoked here: [2](#0-1) . Because the wallet contract has no control over the registrar contract's implementation or future gas requirements, an increase in the registrar's execution cost (e.g. due to growth of its internal state or an upgrade) can make this hardcoded gas insufficient, causing the cross-contract call to run out of gas and fail.

### Finding Description
When `rlp_execute` handles an `EOABaseTokenTransfer` whose `address_check` is required, it schedules a call to the external Address Registrar and attaches a callback with `ADDRESS_CHECK_CALLBACK_GAS` (derived from the hardcoded `REGISTRAR_LOOKUP_GAS` + `RLP_EXECUTE_CALLBACK_GAS`) [3](#0-2) . If that registrar call fails (e.g., due to `Out of gas` because the hardcoded 5 Tgas is no longer enough for the registrar's `lookup` execution), `address_check_callback` hits the `PromiseResult::Failed` branch: [4](#0-3) 

Unlike the analogous failure handling in `rlp_execute_callback`, which explicitly refunds the tracked `CallerDeposit` on failure [5](#0-4) , the `Failed` arm of `address_check_callback` does **not** refund `caller_deposit` at all — it simply returns an error response and drops the `caller_deposit` parameter [4](#0-3) .

`CallerDeposit` tracks the NEAR attached by an external (non-owner) predecessor to `rlp_execute`, specifically so it can be refunded if the downstream cross-contract call fails [6](#0-5) . That deposit is already credited to the wallet contract's own NEAR balance the moment `rlp_execute` is called (it is a `#[payable]` method) [7](#0-6) . If the registrar lookup fails and no refund path exists, that deposit becomes permanently stuck inside the wallet contract, since it is only ever moved out via a subsequent eth-signature-validated transaction from the account owner, not by the relayer who supplied it.

### Impact Explanation
This is directly analogous to the reported issue: a hardcoded parameter (gas) used against an external, independently-controlled contract (the Address Registrar) can silently become insufficient as that contract's implementation or state evolves, and the wallet contract has no way to adjust it (no setter, no dynamic estimation). Concretely, this leads to permanently frozen funds for a relayer/caller who submits a base-token-transfer relay transaction with an attached deposit whenever the registrar lookup exceeds the hardcoded gas budget — since the failure path for that specific callback omits the refund logic present elsewhere in the same contract.

### Likelihood Explanation
Likelihood depends on the Address Registrar's gas cost drifting above 5 Tgas over time (larger lookup tables, more expensive storage reads, or logic changes), which is plausible for any registry contract as it accumulates entries — exactly the "external validation parameters change over time" risk highlighted in the original report. It requires no privileged access: any relayer/RPC caller invoking `rlp_execute` with an `EOABaseTokenTransfer` targeting another eth-implicit account and a non-zero attached deposit can trigger this path.

### Recommendation
Add the same deposit-refund logic to the `PromiseResult::Failed` branch of `address_check_callback` as exists in `rlp_execute_callback`, and avoid hardcoding gas for calls into externally-controlled contracts — either pass generous/adjustable gas margins, or make the registrar-call gas configurable/upgradeable so it can be corrected without redeploying the whole wallet-contract logic.

### Proof of Concept
1. Deploy (or have the existing) Address Registrar contract's `lookup` method require more than the hardcoded `REGISTRAR_LOOKUP_GAS` (5 Tgas) to execute — this can happen naturally as its internal registry grows, without any malicious actor.
2. A relayer calls `rlp_execute` on a user's eth-implicit wallet contract with an RLP-encoded `EOABaseTokenTransfer` to another eth-implicit account (`address_check: Some(address)`), attaching a NEAR deposit as `CallerDeposit` [8](#0-7) .
3. The scheduled registrar `lookup` call exceeds `REGISTRAR_LOOKUP_GAS` and fails with `GasExceeded`.
4. `address_check_callback` receives `PromiseResult::Failed` and returns an error response without refunding the attached deposit [4](#0-3) .
5. The relayer's deposit remains permanently in the wallet contract's balance with no code path to reclaim it.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
