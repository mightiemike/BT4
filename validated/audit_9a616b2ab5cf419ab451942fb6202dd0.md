### Title
Non-embedded OAuth session-cookie collision causes cross-tenant session fixation - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
For non-embedded apps, `oauth.callback` writes the authenticated session id into a single cookie named `SESSION_COOKIE_NAME`, and by default that cookie is set at `path: '/'` — domain-wide, without any shop-specific scoping. Because the browser only ever stores one cookie per name+path, completing OAuth for a second shop in the same browser silently overwrites the first shop's session cookie, exactly mirroring the Witch `grab` bug where a second `grab()` call overwrote `vaultOwners[vaultId]` and destroyed the record of the original owner.

### Finding Description
`callback()` sets the non-embedded session cookie using `cookies.setAndSign(SESSION_COOKIE_NAME, session.id, {..., path: cookiePath})`, where `cookiePath` defaults to `'/'` unless the integrator explicitly opts into a shop-specific factory function. [2](#0-1) 

The default value and its risk are explicitly documented in the config type: "By default the cookie is written with `path: '/'`, making it domain-wide. This means that when a user authenticates multiple shops in separate tabs, each OAuth callback overwrites the previous cookie, causing all tabs to use the most-recently-authenticated shop." [3](#0-2) 

`getCurrentSessionId()` — the function that resolves "who is the authenticated session" for a non-embedded request — reads and verifies only that single cookie, with no cross-check against the `shop` query/host parameter of the request being served. [1](#0-0) 

Because `begin()` is a public, unauthenticated GET/redirect endpoint (`shop` is attacker-controlled and no CSRF token is required to invoke it), an attacker can force a victim's browser to start and complete an OAuth flow for an attacker-controlled shop (e.g., via a hidden iframe/link to `/auth?shop=attacker-shop.myshopify.com`), which overwrites the victim's existing, legitimate `SESSION_COOKIE_NAME` cookie with the attacker's session id once the flow completes. This is a session-fixation/login-CSRF pattern. [4](#0-3) 

### Impact Explanation
After the overwrite, the victim's browser presents the attacker's session id for all subsequent requests to the non-embedded app. Any data the victim subsequently enters or actions the victim takes (orders viewed, form submissions, saved data, OAuth-authorized actions) are performed against/exposed to the attacker's shop's session context rather than the victim's own, resulting in cross-tenant session confusion analogous to the Witch bug's loss of the original vault owner — the original (correct) session binding is irrecoverably lost with no way to detect or reverse it. This is comparable in class to a login-CSRF/session-fixation vulnerability.

### Likelihood Explanation
Requires (1) the target app be configured as non-embedded and not set the optional `cookiePath` mitigation (the documented default is the vulnerable `'/'` path), and (2) the victim's browser to be induced to complete an OAuth flow for an attacker's shop while it holds an existing valid session cookie. Both are plausible for typical non-embedded multi-tenant deployments that haven't opted into the new `cookiePath` option, since it is off by default and must be manually configured with app-specific URL routing.

### Recommendation
Make shop-specific cookie scoping (or an equivalent per-shop binding, e.g., signing the shop into the cookie value and validating it against the request's `shop`/host on every read in `getCurrentSessionId`) the default behavior instead of an opt-in, since the vulnerable default (`path: '/'`) remains in place unless developers actively discover and configure `cookiePath`.

### Proof of Concept
1. Deploy a non-embedded app with default configuration (`cookiePath` unset, defaults to `'/'`).
2. Victim authenticates normally, receiving `shopify_app_session` cookie bound to `victim-shop.myshopify.com`'s session id at path `/`.
3. Attacker lures victim to load `https://app-host/auth?shop=attacker-shop.myshopify.com` in a hidden iframe/background tab; the attacker has already installed/authorized the app on `attacker-shop`, so the OAuth `begin`→`callback` round trip completes in the victim's browser context, calling `cookies.setAndSign(SESSION_COOKIE_NAME, attackerSession.id, {path: '/'})`. [2](#0-1) 
4. Victim's browser now sends the attacker's session id cookie on every subsequent request; `getCurrentSessionId` resolves it as "current session" with no shop-consistency check, and the app treats the victim as operating under the attacker's tenant. [5](#0-4)
