### Title
Hardcoded 18-decimal shift in workflow metering settlement causes credit miscalculation for non-18-decimal gas tokens - ([File: core/services/workflows/metering/metering.go])

### Summary
The `Report.Settle()` function in the CRE workflow metering system unconditionally assumes that every `GAS.*` spend unit reported by a capability DON is denominated with 18 decimals (wei-style), applying a hardcoded `value.Shift(18)`. This is the same class of bug as the reported issue: an amount denominated in one decimal precision is combined/converted with logic that assumes a different (18-decimal) precision, producing an incorrect credit balance.

In `Settle`, for every gas-type spend unit reported by capability nodes, the code does: [1](#0-0) 

The comment explicitly acknowledges the assumption: "WARNING: 18 is a magic number here and assumes all gas tokens will have the same level of precision." [2](#0-1) 

The resulting shifted value is then converted to universal credits using `balance.ConvertToBalance`, which divides by a per-chain gas rate (`GasTokensPerCredit`, keyed by chain selector) fetched from the billing service: [3](#0-2) 

The `GAS.<chainSelector>` rate-card mechanism is chain-selector keyed and explicitly supports multiple chain families, not just EVM: [4](#0-3) 

However, the codebase supports CRE/CCIP capabilities on non-EVM chains whose native gas/fee tokens do not use 18 decimals (e.g., Solana's SOL uses 9-decimal lamports, referenced in the CCIP Solana gas helpers) [5](#0-4) , and CCIP/Sui integration tests explicitly call out chain-specific decimal differences (Sui LINK is 9 decimals vs EVM's 18) [6](#0-5) , confirming that decimal precision varies by chain within the same overall system that reports metering values.

Because `Settle` always shifts by 18 regardless of the actual chain/token decimals behind a `GAS.<chainSelector>` spend unit, any capability reporting a native-gas spend value for a chain whose gas token is not 18-decimal (e.g., 9-decimal SVM/Sui-family chains) will have its spend value inflated by 9 orders of magnitude before being converted to credits.

### Impact Explanation
This directly corrupts the workflow's local credit balance and the final billing receipt submitted to the billing service via `SubmitWorkflowReceipt` (`CreditsConsumed`) [7](#0-6) . A 10^9 factor error in the shift would cause massive over-deduction of credits (denial of workflow execution / erroneous billing) or, if the gas rate compensates asymmetrically in the rate card population, incorrect refunds via the `step.Deduction.Sub(spentCredits)` refund logic [8](#0-7) . This is a billing/metering data-integrity issue (misreporting), not a fund-transfer exploit, but it directly affects credit accounting integrity for CRE workflow executions on non-18-decimal-gas chains.

### Likelihood Explanation
Likelihood depends entirely on whether/when the CRE engine's metering path is exercised for a capability whose `GAS.*` spend unit corresponds to a chain with non-18-decimal native gas token. As CCIP/CRE capability support expands to SVM (Solana) and other non-EVM chains — which the repository already integrates elsewhere (gas helpers, Sui/Solana integration tests) — this magic-number assumption becomes reachable in normal (non-malicious) workflow executions run by ordinary workflow owners, without any privileged action or malicious actor required.

### Recommendation
Do not hardcode a `Shift(18)` for all `GAS.*` spend units. Instead:
- Track/derive the native decimal precision per chain selector (similar to how CCIP already models per-chain decimals for tokens), and apply the correct shift dynamically in `Settle`.
- Alternatively, require capabilities to report gas spend values in a fixed, chain-agnostic base unit (e.g., always in the smallest unit as a big-int string) rather than a decimal string requiring a shift, eliminating any decimal-precision assumption in the metering settlement path.
- Add explicit tests in `core/services/workflows/metering/metering_test.go` covering a non-18-decimal `GAS.<chainSelector>` scenario to catch regressions.

### Proof of Concept
1. Configure a workflow's rate card to include a `GAS.<solanaChainSelector>` entry (`GasTokensPerCredit`) for a Solana/SVM-family chain selector.
2. Have a capability report `SpendUnit: "GAS.<solanaChainSelector>"` with `SpendValue` expressed in SOL (9-decimal) terms, e.g. `"0.001"` (1,000,000 lamports).
3. In `Settle`, `isGasSpendType` matches the `GAS.` prefix and the code applies `value.Shift(18)` regardless of the fact the true precision is 9 decimals [2](#0-1) , producing a spend value 10^9 times larger than the actual lamport amount before it is divided by the gas rate and deducted from the workflow's credit balance — corrupting the metering report and billing receipt.
