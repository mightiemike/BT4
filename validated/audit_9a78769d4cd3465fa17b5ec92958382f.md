### Title
Uncontrolled recursion DoS via deeply-nested JSON in the HTTP gateway's transaction deserialization (`add_tx`/`add_rpc_tx`) - ([File: crates/apollo_http_server/src/http_server.rs])

### Summary
The gateway's HTTP entry points deserialize an entirely untrusted, attacker-controlled request body directly with `serde_json` (both via the raw-string legacy endpoint and via Axum's `Json<T>` extractor), with only a byte-size limit enforced (`RequestBodyLimitLayer`/`DefaultBodyLimit`) and no bound on JSON structural nesting depth. A small payload consisting of deeply nested JSON arrays/objects (e.g. `[[[[...]]]]` repeated tens of thousands of times) causes `serde_json`'s recursive-descent parser to recurse once per nesting level with no depth cap, which can exhaust the stack and abort the process — the same bug class (CWE-674, uncontrolled recursion via deeply nested input) described in the external `justhtml` report.

### Finding Description
Two HTTP handlers accept fully untrusted transaction bodies and hand them to `serde_json` without any structural-depth validation:

- `add_rpc_tx` uses the Axum `Json<RpcTransaction>` extractor, which internally calls `serde_json::from_slice`/`from_reader` on the raw request body [1](#0-0) .
- `add_tx` (legacy/Pythonic gateway) receives the body as a raw `String` and calls `serde_json::from_str(&tx)` directly on attacker-supplied text [2](#0-1) .
- Even on failure to match the target schema, the fallback metrics path calls `serde_json::from_str(tx)` a second time, this time into a generic `serde_json::Value`, which is unconstrained in shape [3](#0-2) .

The only protection applied before parsing is a byte-size cap:
```
.layer(RequestBodyLimitLayer::new(self.config.static_config.max_request_body_size))
``` [4](#0-3) 

A byte-size limit does not bound structural nesting depth: a payload like `"["` repeated N times followed by `"]"` repeated N times is only ~2N bytes but has nesting depth N. `serde_json`'s value/skip-parsing logic recurses once per nesting level with no built-in depth guard (unlike some other JSON libraries which impose a hard recursion ceiling by default). This mirrors exactly the root cause identified in the external `justhtml` report: an unbounded recursive traversal of attacker-controlled nested input, reachable purely by handing crafted data to a library/parser without a depth bound, with the "host" (here, the gateway's HTTP handlers) doing nothing to constrain nesting before invoking it.

Because Rust aborts (rather than unwinding) on stack overflow, this is not a catchable `Result`/panic from the handler's perspective — it terminates the entire `apollo_http_server` process (and, in co-located/hybrid deployments, potentially the whole node process), unlike an ordinary parse error.

### Impact Explanation
An unauthenticated network client can send a single small HTTP POST to `/gateway/add_transaction` or `/gateway/add_rpc_transaction` with a deeply nested JSON body and crash the sequencer's gateway/HTTP-server process via stack overflow. This is a network-unable-to-confirm-new-transactions condition: while the process is down (or repeatedly crashed/restarted), the node cannot accept new transactions through this ingress path, and in co-located ("hybrid") deployments this can bring down the whole sequencer process, not just the gateway service. This satisfies the "network unable to confirm new transactions" impact bar and is directly reachable from an unprivileged transaction sender (any HTTP client), matching the allowed "gateway validation" reachable-path category.

### Likelihood Explanation
High likelihood: no authentication, no fee, no valid transaction structure, and no special privileges are required — the request never needs to pass any Starknet-specific validation because the crash happens during raw JSON parsing, before the gateway's semantic/stateless/stateful validators ever run. The payload is trivially constructed (a few tens of KB of bracket characters) and easily fits under typical `max_request_body_size` configurations. The attack can be repeated continuously to keep the service down.

### Recommendation
- Before calling `serde_json::from_str`/`from_slice`/`Json<T>` extraction on any untrusted request body in `crates/apollo_http_server/src/http_server.rs` (`add_tx`, `add_rpc_tx`, and `check_supported_resource_bounds_and_increment_metrics`), enforce a hard limit on JSON nesting depth (e.g., pre-scan bracket/brace nesting depth and reject before invoking `serde_json`, or use a `serde_json::Deserializer` configured with a bounded recursion budget / iterative pre-validation).
- Alternatively/additionally, run the untrusted deserialization step in a context with a constrained, monitored stack (as already done elsewhere in this codebase for other untrusted-recursion risks, e.g. the `RecursionDepthGuard` used for Cairo entry-point call depth in `crates/blockifier/src/execution/entry_point.rs`), or move parsing into a bounded worker that can fail safely (timeout/kill) without taking down the whole process.
- Apply the same depth-limiting fix to any other place that deserializes fully untrusted JSON directly from the network without a pre-existing strongly-typed, depth-bounded schema (the fallback `check_supported_resource_bounds_and_increment_metrics` path is the most exposed, since it explicitly parses into an unconstrained `serde_json::Value`).

### Proof of Concept
```bash
python3 - <<'EOF' > payload.txt
n = 200000
print('[' * n + ']' * n, end='')
EOF

curl -X POST "http://<sequencer-host>/gateway/add_transaction" \
     -H "Content-Type: application/text" \
     --data-binary @payload.txt
```
The payload is well under any reasonable `max_request_body_size`, but its nesting depth (200,000) far exceeds the default stack's recursion budget used by `serde_json::from_str` in `add_tx` (`crates/apollo_http_server/src/http_server.rs:198`), leading to stack exhaustion and process abort in the HTTP server component during the very first `serde_json::from_str(&tx)` call, before any Starknet-specific transaction validation occurs.
