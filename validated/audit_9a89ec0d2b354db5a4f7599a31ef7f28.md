### Title
Stale ABI in `AbiStore` after contract address reuse causes routing divergence in `Wallet#triggerContract` - (chainbase/src/main/java/org/tron/core/capsule/AbiCapsule.java, actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl#commitContractCache` only writes a newly created contract's ABI into `AbiStore` when `abiStore.has(key.getData())` is false, while it unconditionally writes the new `SmartContract` (including its ABI) into `ContractStore`. If a contract address already has an `AbiStore` entry from a prior deployment at the same address (e.g. via `CREATE`/`CREATE2` after the prior contract self-destructed), the new deployment's ABI is silently dropped from `AbiStore`, leaving `ContractStore` and `AbiStore` holding two different ABIs for the same address.

### Finding Description
`commitContractCache` in `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java` (lines 1021-1035) does: [1](#0-0) 
which puts `ContractCapsule` into `ContractStore` unconditionally but only puts the ABI into `AbiStore` `if (!abiStore.has(key.getData()))`. There is no code path that clears or updates a stale `AbiStore` entry when the contract at that address is (re)created; `ClearABIContractActuator` only sets an empty ABI and is a separate, unrelated code path requiring its own dedicated `ClearABIContract` transaction.

Two independent consumers of "the ABI for address X" then disagree:
- `Wallet#triggerContract` (`framework/src/main/java/org/tron/core/Wallet.java` lines 2955-2984) reads the ABI from `chainBaseManager.getAbiStore().get(contractAddress)` and uses `WalletUtil.isConstant(abi, selector)` to decide whether to route the call through `callConstantContract` (view-only execution) or return the transaction for normal state-mutating broadcast/execution: [2](#0-1) 
- `TransactionTrace#checkIsConstant` (`chainbase/src/main/java/org/tron/core/db/TransactionTrace.java` lines 133-152), used on the actual execution/validation path, reads the ABI from `ContractStore` via `contract.getInstance().getAbi()`: [3](#0-2) 

If a contract is deployed at address X with ABI A1, and a later transaction redeploys a *different* contract at the same address X with ABI A2 (address reuse is reachable through `CREATE`/`CREATE2` + `SELFDESTRUCT` semantics exercised in `CreateContractSuicideTest.java`), `commitContractCache` writes A2 into `ContractStore` but skips writing A2 into `AbiStore` because `abiStore.has(X)` is already true (holding stale A1). From that point:
- `Wallet#triggerContract`'s selector-based constant/non-constant routing decision is made against stale ABI A1.
- The actual on-chain execution path (`TransactionTrace.checkIsConstant`, and the VM/actuator execution itself) uses the authoritative ABI A2 from `ContractStore`.

If selector S is state-mutating (non-constant) in A2 but happens to match a constant/view entry (or no matching entry, defaulting to non-constant) in stale A1 differently, `Wallet#triggerContract` can make an incorrect routing decision relative to the authoritative ABI, e.g. treating a genuinely state-mutating call as constant and routing it through `callConstantContract`, which performs a dry-run execution that is never persisted/broadcast as a real state-changing transaction.

However, I could not fully verify within the available context (1) the exact top-level address-generation logic used by `CreateSmartContractActuator`/`VMActuator` for a fresh `CreateSmartContract` transaction (whether it is nonce-based, making address collision with an attacker-chosen previous deployment guessable/reachable by an unprivileged actor), and (2) whether any additional guard (e.g. "contract already exists" check) in the create-contract actuator prevents redeployment at an address with an existing `ContractCapsule`/account marked as a contract. Address reuse in TVM is generally only reachable through `CREATE2`+`SELFDESTRUCT` inside a contract's constructor code, which is achievable by an unprivileged attacker deploying arbitrary bytecode, and this repo's own test `CreateContractSuicideTest.java` exercises self-destruct-during-construction scenarios, supporting reachability, but I did not find a definitive test demonstrating a full ABI-divergence exploit end-to-end.

### Impact Explanation
If exploited, a value-transferring call (`TriggerSmartContract` with a `call_value`/`call_token_value`) that `Wallet#triggerContract` misroutes into `callConstantContract` never has its balance transfer or state mutation committed to the real chain state — the client receives a "successful" constant-call-style response for an intended state-mutating call, and the funds/state change is dropped rather than applied, i.e. value sent by the caller is not delivered and the transaction is not what the caller intended, though the caller controls when to trigger this so it constitutes a self-inflicted foot-gun/wallet-layer bug rather than a way to steal funds from a third party.

### Likelihood Explanation
This requires: (1) an ABI-divergence precondition — an `AbiStore` entry becoming stale relative to `ContractStore`, only achievable by contract redeployment at a reused address (via `CREATE2`+`SELFDESTRUCT`, since normal top-level deployment address collision is not verified in the explored context), and (2) a selector that happens to have differing constant/non-constant classification between the old and new ABI. Both preconditions are non-trivial and depend on TVM address-reuse semantics that were not fully confirmed in this review; likelihood is uncertain without further verification of the address-generation and contract-creation validation code.

### Recommendation
Make `commitContractCache` always overwrite (or reconcile) the `AbiStore` entry when a contract is newly created (`value.getType().isCreate()`), rather than gating the ABI write purely on `!abiStore.has(key.getData())`; alternatively, remove the redundant `AbiStore` and have all ABI-dependent code (`Wallet#triggerContract`, `WalletUtil.isConstant`) read the ABI directly from the authoritative `ContractStore`/`ContractCapsule` used by `TransactionTrace#checkIsConstant`, eliminating the possibility of two divergent ABI sources for the same address.

### Proof of Concept
```java
// Pseudocode/plan for actuator/src/test or framework/src/test unit test
@Test
public void testStaleAbiStoreCausesRoutingDivergence() {
  byte[] contractAddress = ...; // fixed test address
  ABI oldAbi = jsonStr2Abi("[{... function foo() nonpayable ...}]");
  ABI newAbi = jsonStr2Abi("[{... function foo() view ...}]"); // same selector, different mutability

  // 1. Pre-seed AbiStore with old ABI (simulating leftover entry from prior deployment at address)
  abiStore.put(contractAddress, new AbiCapsule(oldAbi));

  // 2. Simulate a "create" commit for a new contract at same address with newAbi
  RepositoryImpl repo = RepositoryImpl.createRoot(storeFactory);
  SmartContract newContract = SmartContract.newBuilder().setAbi(newAbi)....build();
  repo.createContract(contractAddress, new ContractCapsule(newContract)); // marks Type.CREATE
  repo.commit(); // triggers commitContractCache -> ContractStore updated, AbiStore skipped due to abiStore.has()==true

  // 3. Assert divergence
  ABI abiFromContractStore = contractStore.get(contractAddress).getInstance().getAbi();
  ABI abiFromAbiStore = abiStore.get(contractAddress).getInstance();
  Assert.assertNotEquals(abiFromContractStore, abiFromAbiStore); // proves stale ABI persists

  // 4. Assert routing divergence
  byte[] selector = WalletUtil.getSelector(functionCallData); // matches "foo()" selector
  boolean routedAsConstant = WalletUtil.isConstant(abiFromAbiStore, selector); // Wallet#triggerContract's decision
  boolean trueMutability = WalletUtil.isConstant(abiFromContractStore, selector); // authoritative decision
  Assert.assertNotEquals(routedAsConstant, trueMutability); // proves Wallet#triggerContract diverges from ground truth
}
```
This test directly demonstrates that `commitContractCache`'s `abiStore.has()` guard causes `AbiStore` and `ContractStore` to hold different ABIs for the same address, and that `Wallet#triggerContract`'s selector-routing decision (driven by `AbiStore`) can diverge from the ABI authoritative for on-chain execution (`ContractStore`), confirming the finding at the store/routing level. Full end-to-end confirmation of reachability via a real `CREATE2`+`SELFDESTRUCT` redeploy transaction sequence should be added as a follow-up integration test using `TvmTestUtils`/`VMActuator` before treating this as a fully proven live exploit.
