### Title
Unrestricted, instantaneous inflation/block-revenue commission increases via `UpdateCommissionBps` allow validators to front-run reward calculation and extract delegator rewards - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The vote program's new basis-points commission instruction, `VoteInstruction::UpdateCommissionBps`, lets a vote account's authorized withdrawer change `inflation_rewards_commission_bps` or `block_revenue_commission_bps` at any slot with no timing restriction whatsoever, unlike the legacy percentage-based `UpdateCommission` path, which enforces an epoch-position check (`is_commission_update_allowed`) when increasing commission. This mirrors the Tortuga finding: a party controlling commission (there, the pool owner; here, the vote account withdraw authority) can spike the rate to the maximum right before it becomes economically binding, while stakers already committed have no fast way to exit.

### Finding Description
`update_commission` (legacy, percentage-based) rejects a commission *increase* unless the current slot is in the first half of the epoch, via `is_commission_update_allowed(clock.slot, epoch_schedule)`, and this rule is only bypassed once the `delay_commission_updates` feature is active — which imposes a full-epoch delay before the new rate takes effect instead: [1](#0-0) 

`update_commission_bps`, added for SIMD-0291/SIMD-0123, explicitly drops all timing enforcement — the code comment states "No commission update rule, per SIMD-0249 and SIMD-0291" — and applies the new `commission_bps` to `inflation_rewards_commission_bps` / `block_revenue_commission_bps` immediately upon a single authorized-withdrawer signature, with no minimum-delay/epoch-lag substitute visible in this code path: [2](#0-1) 

This is dispatched from an ordinary, permissionless transaction via the vote program processor: [3](#0-2) 

Because inflation and block-revenue rewards are computed periodically (per-epoch partitioned rewards / per-block distribution) by reading whatever commission value is currently stored in the vote account at calculation time, a withdraw authority can wait until immediately before a reward-affecting event, jack `commission_bps` up to 10000 (100%), capture the reward for that period, and then lower it back — precisely the "profit from a large commission for a period, then revert" pattern described in the Tortuga report, except here there is no lockup analog at all protecting the delegator even for the brief window before the change is observed, whereas the legacy path at least had the first-half-of-epoch restriction as a mitigant.

### Impact Explanation
Stakers delegating to a vote account have no way to react to a same-slot commission change before the next reward distribution reads it, since stake activation/deactivation carries warmup/cooldown delay and does not let a delegator escape an already-accruing reward period. A malicious/validator-controlled withdraw authority can therefore extract materially more of the inflation or block-revenue reward stream than delegators expect, effectively diverting staker rewards to the operator. This is an economic-theft-of-funds class issue against ordinary delegators, not merely an operator/no-impact concern, since it acts on stake contributed by third-party delegators through the permissionless vote program instruction path.

### Likelihood Explanation
The `UpdateCommissionBps` instruction is reachable by any ordinary transaction signed by the vote account's authorized withdrawer — no special node privilege is required — and is gated only by the `commission_rate_in_basis_points` and `delay_commission_updates` feature flags being active. Once those SIMDs are enabled, exploitation only requires timing the transaction, which is trivial for any validator operator watching for reward-calculation boundaries.

### Recommendation
Apply the same or a stronger delay/anti-front-running rule to `update_commission_bps` as intended by SIMD-0249 (i.e., enforce that commission-bps increases only take effect starting the following epoch, or restrict increases to the first half of the epoch as the legacy path does), rather than applying the change immediately with no rule at all. Confirm that the "delay" implied by SIMD-0249's naming is actually implemented as a lag in when the new commission value is *read* by the reward-calculation code, not just documented in a comment with no code enforcement.

### Proof of Concept
1. Attacker controls a vote account's authorized withdrawer key and has delegated stake (own or delegators').
2. Attacker submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: InflationRewards }` in the slot(s) immediately preceding epoch/reward-distribution processing — allowed unconditionally per `update_commission_bps` (`programs/vote/src/vote_state/mod.rs:827-859`), since no `is_commission_update_allowed`-style check gates it.
3. Reward calculation reads the now-100% commission from vote state and credits nearly the entire inflation reward to the validator instead of delegators.
4. Attacker submits a follow-up `UpdateCommissionBps` transaction to lower the rate back before the next distribution, repeating the cycle each period. [2](#0-1) [1](#0-0) [3](#0-2)

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
