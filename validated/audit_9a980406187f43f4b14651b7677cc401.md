### Title
Division-before-multiplication in witness standby reward payout causes systematic reward truncation - (File: `consensus/src/main/java/org/tron/consensus/dpos/IncentiveManager.java`)

### Summary
The external report flags ABDKMath64x64 for performing division before multiplication, which truncates fractional precision that could have been preserved by multiplying first. The same anti-pattern exists in java-tron's witness standby-vote reward payout logic, where a division is computed first (as a `double`) and only then multiplied by the vote count, rather than multiplying the integer values first and dividing once at the end.

### Finding Description
In `IncentiveManager.reward()`, the per-witness payout is computed as:

```java
long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
    / voteSum));
``` [1](#0-0) 

Here `totalPay / voteSum` is evaluated first, then multiplied by `voteCount`. This is the same order-of-operations problem the report describes: dividing first discards precision that a "multiply-then-divide" ordering would have preserved. The codebase elsewhere explicitly acknowledges and has hardened this exact class of bug — e.g. `EnergyProcessor.calculateGlobalEnergyLimit()` documents the legacy double-based formula `(long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight))` as imprecise, and provides a `BigInteger`-based "hardened" replacement that multiplies first before dividing: [2](#0-1) [3](#0-2) 

However, `IncentiveManager.reward()` has no such hardened path or `allowHardenResourceCalculation()` gate — it always uses the vulnerable double-division-first formula for every maintenance cycle when standby witness rewards are paid out.

### Impact Explanation
This function distributes `getWitnessStandbyAllowance()` TRX among standby witnesses proportional to their vote share, and is invoked every maintenance cycle for all eligible standby witnesses: [4](#0-3) 
Systematic truncation/rounding errors from doing the division first (rather than `voteCount * totalPay / voteSum`) cause witnesses to be underpaid relative to the mathematically correct proportional share, with the truncated remainder effectively vanishing from circulation rather than being accounted for. This is a state-accounting correctness issue affecting on-chain allowance balances credited to witness accounts every cycle, not a privileged-only or purely theoretical code path — it fires unconditionally whenever `allowChangeDelegation()` is false and there are standby witnesses with votes.

### Likelihood Explanation
This code path executes automatically on every maintenance cycle as part of consensus reward distribution — no attacker action, special permissions, or unusual configuration is required to trigger it. The magnitude of the discrepancy depends on `voteSum` size and vote distribution, but the underlying computation order guarantees a (typically small but non-zero) divergence from the mathematically exact proportional payout, consistent in spirit with the referenced ABDK finding.

### Recommendation
Reorder the computation to multiply before dividing, using integer/BigInteger arithmetic to avoid double-precision loss and truncation-before-multiply errors, mirroring the pattern already used in the "hardened" replacements elsewhere in the codebase (e.g. `calculateGlobalLimitV2` in `ResourceProcessor.java`):
```java
long pay = BigInteger.valueOf(voteCount)
    .multiply(BigInteger.valueOf(totalPay))
    .divide(BigInteger.valueOf(voteSum))
    .longValueExact();
```

### Proof of Concept
Given `totalPay = 100`, `voteSum = 3`, and a witness with `voteCount = 1`:
- Current code: `(double) totalPay / voteSum = 33.333...`, then `1 * 33.333... = 33.333...`, cast to `long` → `33`.
- Correct order: `1 * 100 = 100`, `100 / 3 = 33` (integer) — in this example results coincide, but for larger `voteCount`/`totalPay` values that exceed double's 53-bit mantissa precision (well within TRX's `sun` denomination range, e.g. totalPay in the billions of `sun`), `(double) totalPay / voteSum` loses precision before the multiplication is applied, producing a payout that diverges from the exact integer proportional share computed via `voteCount * totalPay / voteSum`. This directly parallels the ABDKMath64x64 root cause: division performed before multiplication discards precision that reordering the operations would have preserved.

      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);

    }
  }
