## Binding

Claimed invariant: `deposit removed from DepositDataMempool` ⇔ `deposit's system tx was successfully applied on-chain and cBTC credited to the depositor`. I traced the code and this invariant does **not** hold.

## Trace

`produce_l2_block_inner` fetches a batch of pending deposits with `fetch_deposits` and stores it in the local `deposit_data` variable: [1](#0-0) 

This same `deposit_data` slice is fed into `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs`, which builds the deposit system transactions and applies them one by one with a per-tx checkpoint/revert: [2](#0-1) 

Critically, when a deposit system tx fails with `EvmSystemTransactionNotSuccessful`, the working set is reverted, the nonce decremented, and the loop `continue`s — the failed deposit is simply **not added to `all_txs`** and thus never included in the resulting block: [3](#0-2) 

After the block (containing only the *successful* subset of system txs) is built and saved, the sequencer calls `remove_deposits` using the **original, unfiltered** `deposit_data` variable — not the subset that actually succeeded: [4](#0-3) 

`remove_deposits` purges every deposit in the passed list from both `accepted_deposit_txs` and `pending_deposits` by `calc_tx_id`, with no distinction between included and skipped deposits: [5](#0-4) 

Once removed, the original raw `Bytes` blob that was consumed by `add_deposit_tx` at RPC-accept time is gone — there is no resubmission path, since `send_raw_deposit_transaction` only re-validates and re-adds a *freshly submitted* blob via `eth_call` against pending state: [6](#0-5) 

The `eth_call` pre-check at submission time uses `BlockId::pending()` against a possibly-stale state snapshot, so a deposit can pass this check yet fail later in `process_sys_txs` if state has diverged by the time the deposit is actually dry-run for real block inclusion (e.g., another deposit already consumed the same underlying UTXO reference on the bridge contract side) — this is exactly the described TOCTOU window between RPC acceptance and `process_sys_txs`.

## Confirmation

Both sides of the equality were checked:
- Before: deposit accepted into mempool because `eth_call` passed at RPC time.
- After: deposit's system tx reverts in `process_sys_txs` (skipped via `continue`), zero state change, zero cBTC minted — yet `remove_deposits` still deletes it because `deposit_data` (the unconditionally-passed full batch) is used rather than a success-filtered list.

No existing guard (`is_system_caller`, `Auth`, `CitreaTransactionValidator`, fork rules) addresses this — this is purely a sequencer-local bookkeeping bug in `runner.rs`/`deposit_data_mempool.rs`, unrelated to signature/authorization checks.

### Title
Sequencer unconditionally purges failed deposit system transactions from `DepositDataMempool`, permanently freezing depositor funds - ([File: crates/sequencer/src/runner.rs])

### Summary
`produce_l2_block_inner` fetches a batch of pending deposits and passes them to `process_sys_txs`, which silently skips (via `continue`) any deposit whose system transaction fails with `EvmSystemTransactionNotSuccessful`. After the block is built, `remove_deposits` is called with the *original, unfiltered* fetched batch rather than only the deposits whose system transactions actually succeeded, permanently deleting the failed deposit's raw blob from the mempool with no cBTC ever minted and no resubmission path.

### Finding Description
The binding `deposit removed from mempool == deposit's cBTC credited on L2` is broken. `deposit_data` fetched in `produce_l2_block_inner` (`crates/sequencer/src/runner.rs:516-520`) is passed unchanged into `process_sys_txs` (`crates/sequencer/src/runner.rs:1617-1706`), where per-deposit failures are caught, reverted, and `continue`d (`crates/sequencer/src/runner.rs:1678-1697`) so the failing deposit never becomes part of the finalized block's transactions. However, `remove_deposits(&deposit_data)` at `crates/sequencer/src/runner.rs:636-643` is invoked with the same original `deposit_data` variable that was fetched before dry-run, not a list restricted to deposits that succeeded. `DepositDataMempool::remove_deposits` (`crates/sequencer/src/deposit_data_mempool.rs:79-109`) purges every matching entry from `accepted_deposit_txs`/`pending_deposits` unconditionally. A deposit blob that passed the `eth_call` pre-check in `send_raw_deposit_transaction` (`crates/sequencer/src/rpc.rs:339-380`, run against `BlockId::pending()`) but subsequently fails for real when actually processed in `process_sys_txs` — e.g., because bridge contract state diverged between the pending-state simulation and actual block-building (competing deposit consuming shared state first) — is discarded forever with the original raw bytes destroyed and no automatic resubmission mechanism.

### Impact Explanation
The depositor whose real Bitcoin move-to-vault output was legitimately presigned by Clementine receives zero cBTC, and their deposit entry is permanently removed from the sequencer's mempool with no path to recovery short of manually re-inscribing/resubmitting the deposit blob (which the depositor may not even know to do, since the failure is silent from their perspective once accepted). This matches the Critical impact category: funds permanently frozen for the affected party. The bug is repeatable across any L2 block and any deposit whose underlying on-chain condition changes between RPC-time simulation and block-build-time processing.

### Likelihood Explanation
No privileged access is required — any deposit going through the standard `citrea_sendRawDepositTransaction` flow is subject to this TOCTOU window between the `eth_call` check (against `BlockId::pending()`) and the actual `process_sys_txs` execution at block-build time. This can occur under normal operational conditions (not necessarily adversarial) whenever two deposits interacting with shared bridge state are pending simultaneously and get reordered or race between the pre-check and final processing, making this readily reproducible in a `cargo test` harness.

### Recommendation
Track which deposits from `deposit_data` were actually included in `all_txs` inside `process_sys_txs` (e.g., return the successfully-applied subset alongside skipped ones), and call `remove_deposits` only with that successful subset in `produce_l2_block_inner`. Deposits that failed should remain in the mempool (or be explicitly re-queued/flagged for resubmission) rather than being silently discarded.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
