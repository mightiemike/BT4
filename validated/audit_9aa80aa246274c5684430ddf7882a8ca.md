### Title
Clamping negative `totalEnergyWeight`/`totalNetWeight` to zero permanently inflates the accounting base used for per-account resource limits - ([File: chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java])

### Summary
`DynamicPropertiesStore.addTotalNetWeight()`, `addTotalEnergyWeight()`, and `addTotalTronPowerWeight()` clamp the running total to `max(0, total)` whenever `allowNewReward()` is enabled, but they discard the amount of negative overflow instead of tracking it as a deficit to be reconciled against future additions. [2](#0-1) 

### Finding Description
This mirrors the external report's bug class: a running counter (`ohmDeployed`) is decremented, and when the decrement would push it negative, it is clamped to a floor (0) and the excess is meant to be recorded (`circulatingOhmBurned`) so a later increment can offset it. In java-tron's `addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight`, the same clamp-to-zero pattern exists, but there is no equivalent of `circulatingOhmBurned` — the negative overflow is silently dropped:

```java
public void addTotalEnergyWeight(long amount) {
    if (amount == 0) { return; }
    long totalEnergyWeight = getTotalEnergyWeight();
    totalEnergyWeight += amount;
    if (allowNewReward()) {
        totalEnergyWeight = max(0, totalEnergyWeight, disableJavaLangMath());
    }
    saveTotalEnergyWeight(totalEnergyWeight);
}
``` [3](#0-2) 

These totals are decremented by unfreeze/undelegate paths (`UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `UnfreezeBalanceProcessor`) using rounding-truncated per-account weight deltas (`/TRX_PRECISION`), and incremented on freeze/delegate. Because integer division truncates on both increments and decrements independently per-account, the aggregate `totalEnergyWeight`/`totalNetWeight` can legitimately drift below the true sum of individual account weights over many freeze/unfreeze cycles across many accounts — analogous to the Silo's interest accrual causing withdrawals to exceed the tracked deployed amount. When that drift makes a decrement push the aggregate negative, the code clamps it to 0 and the “debt” is lost forever, rather than being carried forward the way `circulatingOhmBurned` was intended to be (per the fix in the referenced advisory). [4](#0-3) [5](#0-4) 

The comment `// adjust total resource, used to be a bug here` in `UnfreezeBalanceProcessor` confirms this area has already been a known source of prior accounting bugs, increasing plausibility that the clamp-without-reconciliation pattern is a genuine residual issue rather than a purely theoretical one. [6](#0-5) 

`totalEnergyWeight` (and analogously `totalNetWeight`) is not just a bookkeeping value — it is used directly as the denominator in `EnergyProcessor.calculateGlobalEnergyLimit()` to compute each account's proportional energy limit from its frozen balance:

```java
long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
...
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [1](#0-0) 

If `totalEnergyWeight` is permanently inflated relative to the true sum of frozen-for-energy balances (because a prior negative delta was clamped to 0 and never subtracted back out on subsequent freezes), this denominator becomes too large system-wide, and **every account's computed energy/bandwidth limit becomes systematically smaller than it should be** relative to their actual stake — the mirror image of the original report's problem where `ohmDeployed` being wrong caused the protocol to under-utilize `maximumToDeploy`.

### Impact Explanation
This is a protocol-wide state/accounting divergence: the true aggregate frozen-balance weight and the on-chain `totalEnergyWeight`/`totalNetWeight` values can diverge and never resynchronize, since there is no mechanism analogous to `circulatingOhmBurned` to carry forward and offset the lost deficit on the next freeze operation. The practical effect is silent under-allocation of bandwidth/energy resource limits to all frozen-balance/stake holders once the divergence has occurred, which is a real (if gradual) accounting-correctness bug in a core public-facing resource mechanism, not merely theoretical, since `calculateGlobalEnergyLimit`/`calculateGlobalLimitV1` (and the bandwidth analog) are on the hot path for every transaction's resource check. [7](#0-6) 

### Likelihood Explanation
Triggering requires accumulated rounding/truncation drift (via repeated `/TRX_PRECISION` division on both increment and decrement paths across many unrelated freeze/unfreeze operations) to eventually push the running total negative enough to be clamped. This is a low-probability-per-operation but cumulative/system-wide condition reachable purely through normal unprivileged freeze/unfreeze/delegate/undelegate transactions — no privileged role is required, matching the "unprivileged-user" scope constraint. However, I was not able to fully quantify, within the available tooling, exactly how large or frequent the rounding drift is in practice (i.e., whether real-world usage patterns make the clamp trigger often or only in edge cases), so likelihood should be treated as plausible-but-unconfirmed pending further modeling or fuzzing of the freeze/unfreeze weight arithmetic across many accounts and cycles.

### Recommendation
Introduce an explicit deficit-tracking variable (analogous to `circulatingOhmBurned`) alongside `totalNetWeight`/`totalEnergyWeight`/`totalTronPowerWeight` in `DynamicPropertiesStore`. When a decrement would drive the total negative, clamp to 0 as today but record the negative remainder in the deficit variable; on the next increment (freeze/delegate), first offset the deficit before adding to the total, mirroring the fix applied for `ohmDeployed`/`circulatingOhmBurned` in the referenced advisory.

### Proof of Concept
Conceptual sequence (mirrors the OHM example):
1. Multiple accounts freeze for energy across several cycles such that `totalEnergyWeight` accumulates rounding-truncated increments (`energyWeight = frozenBalance/TRX_PRECISION`, integer division).
2. Those accounts unfreeze in an order/pattern where the sum of decremented `oldEnergyWeight - newEnergyWeight` deltas (also integer-divided) exceeds the currently tracked `totalEnergyWeight` due to truncation differences accumulated over time — see the decrement logic in `UnfreezeBalanceV2Actuator.updateTotalResourceWeight` and `DynamicPropertiesStore.addTotalEnergyWeight`. [8](#0-7) 
3. `addTotalEnergyWeight` clamps the result to 0 via `max(0, totalEnergyWeight, ...)`, losing the negative remainder permanently. [9](#0-8) 
4. A new account freezes energy afterward; `totalEnergyWeight` is incremented from 0 by the new freeze amount only, with no correction for the previously lost deficit — so `totalEnergyWeight` ends up permanently higher than the true aggregate weight would have been without the clamp, which understates every account's `calculateGlobalEnergyLimit()` result going forward.

**Note on verification limits:** I was able to confirm the code paths and the exact clamp-and-discard logic, and confirm that `totalEnergyWeight`/`totalNetWeight` feed directly into per-account resource-limit computation. I was not able to construct or run an actual numeric transaction trace (no execution/test-running tool available in this session) to prove the exact magnitude of drift achievable in practice; a background Devin session with test execution capability would be needed to build a concrete reproducing unit test (e.g., extending `UnfreezeBalanceActuatorTest`/`FreezeV2Test`) demonstrating the clamp firing and the resulting energy-limit skew.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                        long unfreezeBalance) {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    switch (unfreezeBalanceV2Contract.getResource()) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        dynamicStore.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        dynamicStore.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(-unfreezeBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        dynamicStore.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        //this should never happen
        break;
    }
  }
