This confirms the key architectural fact: `RpcApiServiceOnSolidity` and `HttpApiOnSolidityService`/`SolidityNodeHttpApiService` are enabled with `enable = isFullNode() && ...` — i.e., these "solidity-node" HTTP/gRPC surfaces run as additional listener ports **inside the same FullNode JVM process**, not a separate process. [1](#0-0) [2](#0-1) 

Given that, `GlobalRateLimiter` — whose fields are `static` — is a single shared instance within that one JVM process for both the `/wallet/...` and `/walletsolidity/...` HTTP surfaces, so the global QPS/IP-QPS ceiling is enforced jointly, not doubled, for HTTP traffic. [3](#0-2) 

However, the **per-endpoint** rate limiter bucket is keyed by `getClass().getSimpleName()` in `RateLimiterServlet`, and `ScanShieldedTRC20NotesByOvkServlet` (fullnode `/wallet/...`) and `ScanShieldedTRC20NotesByOvkOnSolidityServlet` (solidity `/walletsolidity/...`) are distinct classes, so they get **independent** per-servlet QPS/permit budgets even though they invoke the identical `Wallet.scanShieldedTRC20NotesByOvk` expensive method against the same underlying `Manager`/stores. [4](#0-3) [5](#0-4) 

For gRPC, the same is true independently: `RpcApiService` (fullnode gRPC) and `RpcApiServiceOnSolidity` (solidity gRPC on a separate port, same JVM) each expose `scanShieldedTRC20NotesByOvk`, invoking `Wallet.scanShieldedTRC20NotesByOvk` via `walletOnSolidity.futureGet(...)` delegating back into the same shared `rpcApiService.getWalletSolidityApi()`. [6](#0-5) [7](#0-6) 

The core expensive work — `Wallet.scanShieldedTRC20NotesByOvk` — decrypts every shielded-log note across up to a 1000-block range by iterating blocks, transactions, and `TransactionInfo` logs, and this cost bound (`endNum - startNum <= 1000`) is the only per-call cost guard; it is not tied to any cross-surface accounting. [8](#0-7) 

So both the HTTP per-endpoint QPS and gRPC per-method QPS (if configured) are enforced **per servlet-class / per gRPC-method component name**, independently for the fullnode and solidity surfaces — even though `GlobalRateLimiter`'s node-wide QPS applies jointly to HTTP within the process. This means an attacker flooding both `/wallet/scanshieldedtrc20notesbyovk` and `/walletsolidity/scanshieldedtrc20notesbyovk` concurrently can obtain up to double the "safe" per-endpoint throughput for the same expensive underlying work, bounded only by the shared node-wide `GlobalRateLimiter.QPS`/`IP_QPS` ceiling (default 50000/10000, or as configured) — which is typically set far higher than any single expensive endpoint's specific per-endpoint limit, meaning the per-endpoint limit (the actual "safe" ceiling operators configure for this expensive call) is the one that gets doubled in practice.

### Title
Per-endpoint rate limits for scanShieldedTRC20NotesByOvk are not shared across fullnode `/wallet` and solidity `/walletsolidity` HTTP/gRPC surfaces, allowing effective doubling of throughput for the same expensive scan - (File: framework/src/main/java/org/tron/core/services/http/ScanShieldedTRC20NotesByOvkServlet.java)

### Summary
`ScanShieldedTRC20NotesByOvkServlet` (fullnode `/wallet/scanshieldedtrc20notesbyovk`) and `ScanShieldedTRC20NotesByOvkOnSolidityServlet` (`/walletsolidity/scanshieldedtrc20notesbyovk`) are distinct `RateLimiterServlet` subclasses whose per-endpoint quota bucket is keyed by class simple name, so operators who configure a tight per-endpoint QPS to bound the cost of the up-to-1000-block shielded scan effectively get that budget twice — once per surface — even though both ultimately execute the identical `Wallet.scanShieldedTRC20NotesByOvk` work against the same `Manager`/store data. The same pattern applies to the corresponding gRPC methods on `RpcApiService` and `RpcApiServiceOnSolidity`.

### Finding Description
`RateLimiterServlet.addRateContainer()` registers a per-servlet rate limiter keyed by `getClass().getSimpleName()` [4](#0-3) . Because `ScanShieldedTRC20NotesByOvkOnSolidityServlet extends ScanShieldedTRC20NotesByOvkServlet` but is a separate concrete class registered on `/walletsolidity/scanshieldedtrc20notesbyovk` [9](#0-8) , its rate-limiter key differs from the fullnode servlet's, so any `rate.limiter.http` entry an operator adds to constrain this expensive endpoint (e.g. `component = "ScanShieldedTRC20NotesByOvkServlet"`) does not cover the solidity-surface servlet, and vice versa. Both surfaces run in the same JVM process (`enable = isFullNode() && ...`) [2](#0-1) , calling into the identical `Wallet.scanShieldedTRC20NotesByOvk(startNum, endNum, ovk, contractAddress)` [8](#0-7) , which iterates every block/transaction/log for up to 1000 blocks — the only real cost bound is the range check, not any request-count accounting shared across surfaces. The gRPC path shows the identical structure: `RpcApiService.WalletSolidityApi.scanShieldedTRC20NotesByOvk` and `RpcApiServiceOnSolidity.WalletSolidityApi.scanShieldedTRC20NotesByOvk` are two independently rate-limitable gRPC components delegating to the same `Wallet` method [7](#0-6) [6](#0-5) .

The one mitigating factor is `GlobalRateLimiter`, whose fields are process-static and thus shared across all HTTP servlets in the same JVM regardless of surface [3](#0-2) ; this caps total combined HTTP QPS/IP-QPS node-wide at the configured `global.qps`/`global.ip.qps` (defaults 50000/10000, test defaults 1000/1000) [10](#0-9) . But this global ceiling is generic and much higher than any endpoint-specific tight QPS an operator would set specifically to bound this CPU/disk-heavy shielded scan, so the effective double-budget still exists below the global ceiling.

### Impact Explanation
An operator who deliberately tightens the per-endpoint rate limit for `ScanShieldedTRC20NotesByOvkServlet` (an intentionally expensive, disk/CPU-heavy operation scanning up to 1000 blocks and iterating all their transactions/logs) to mitigate DoS risk does not get that protection extended to the equivalent `/walletsolidity/...` HTTP servlet or the equivalent gRPC method on the solidity-node service, both of which run in the same process against the same `Manager`/store data. An attacker can therefore run parallel max-range floods against both surfaces, each individually under its "safe" configured qps, achieving up to double the sustained CPU/disk load intended by the operator's per-endpoint limit, up to the shared node-wide `GlobalRateLimiter` ceiling.

### Likelihood Explanation
This requires no privilege beyond making public HTTP/gRPC calls; both surfaces are commonly enabled together on a fullnode that also exposes solidity endpoints (`isFullNode() && isSolidityNodeHttpEnable()`/`isRpcSolidityEnable()`). The default `rate.limiter.http`/`rate.limiter.rpc` lists are empty, so by default all such endpoints fall back to the generic `DefaultBaseQqsAdapter` with default qps (1000, per `reference.conf`) rather than a specifically tightened value — meaning this is a real gap only manifesting once an operator has hardened rate limits per-endpoint, which is the intended use case for this configuration (i.e., the vulnerability is realized specifically when the mitigation the config was designed for is applied).

### Recommendation
Normalize the rate-limiter key for logically identical operations across fullnode and solidity/PBFT surfaces (e.g., derive the key from the underlying `Wallet` method name rather than the concrete Servlet/gRPC class), or explicitly document/require that operators configure matching per-endpoint limits on all `ScanShieldedTRC20NotesByOvk*` variants (fullnode, solidity, PBFT) and the corresponding gRPC methods. Alternatively, introduce a shared cross-surface rate limiter instance (analogous to `GlobalRateLimiter` but scoped to specific expensive operation families) so that the total permitted rate for `scanShieldedTRC20NotesByOvk`-class work is capped once, in aggregate, regardless of which listener the request arrives on.
