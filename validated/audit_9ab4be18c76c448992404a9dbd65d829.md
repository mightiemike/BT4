## Finding: Unchecked subtraction in `AccountStorageReader::new` can underflow when obsolete byte accounting is inconsistent

This is an analog of the reported OETHVaultCore `_checkBalance` bug class: a value that should be clamped to zero (or otherwise bounded) when a "reserved/obsolete" amount exceeds the "total" amount, is instead computed with a raw, unchecked subtraction.

### Finding Description
`AccountStorageReader::new` computes the number of bytes to actually stream for an account storage during snapshot generation: [1](#0-0) 

```rust
let num_total_bytes = storage.accounts.len();
let mut num_alive_bytes = num_total_bytes - storage.get_obsolete_bytes(snapshot_slot);
...
if tombstones_filter == TombstonesFilter::Exclude {
    ...
    num_alive_bytes -= tombstone_offsets.len() * tombstone_stored_size;
    ...
}
```

Both subtractions are plain `-` (not `saturating_sub`/`checked_sub`), so they will panic on debug builds (integer overflow check) or silently wrap to a huge `usize` in release builds if the subtrahend ever exceeds `num_total_bytes`/`num_alive_bytes` — exactly the same "should clamp to zero but instead returns a wrong/garbage value" failure mode described in the report.

`get_obsolete_bytes` sums, over every recorded obsolete entry, `calculate_stored_size(data_len).min(accounts.len() - offset)`: [2](#0-1) 

The per-entry `.min()` bounds a single entry's contribution to the remaining tail of the file, but it does **not** prevent the *sum* from exceeding `num_total_bytes` if the `obsolete_accounts` list ever contains duplicate/overlapping entries for the same offset (or stale entries after a storage's length changed). `ObsoleteAccounts::mark_accounts_obsolete` simply appends to a `Vec` with no deduplication or invariant enforcement: [3](#0-2) 

So if any code path marks the same offset obsolete more than once (e.g., due to a race between clean/shrink/ancient-combining paths that independently determine an account is obsolete, or a storage getting reused/reopened with an obsolete list computed for a different length), `get_obsolete_bytes()` can return a value larger than `storage.accounts.len()`, and the subtraction in `AccountStorageReader::new` underflows.

### Impact Explanation
`AccountStorageReader` is the mechanism used to stream account storage bytes while excluding obsolete/tombstone bytes — this is invoked during full/incremental snapshot archive generation and snapshot rebuild paths (out-of-scope-listed "snapshot generation and rebuild" is explicitly allowed per scan rules). An underflow here causes:
- A validator panic on debug/overflow-checked builds while generating a snapshot (denial of availability for that node during snapshot production), or
- On release builds without overflow checks, `num_alive_bytes` wraps to a near-`usize::MAX` value, which is then used as `reader.len()` — this is consumed by `io::copy` bound logic and by callers computing archive/file layout sizes, producing a snapshot with wildly incorrect declared size (disproportionate storage size / corrupted downstream snapshot artifact), i.e., a hash/capitalization or snapshot-vs-replay type divergence risk once that corrupted snapshot is later loaded.

### Likelihood Explanation
This requires the invariant "obsolete bytes recorded for a storage never exceed the storage's current length" to be violated. The `ObsoleteAccounts` structure keeps appending entries with no dedup, and the code offers no assertion that the accumulated total stays within the storage's length. While normal single-threaded bookkeeping likely avoids duplicate entries in the common case, there is no explicit invariant, debug assertion, or defensive `saturating_sub`/`checked_sub` protecting this path, unlike many other similar accounting subtractions elsewhere in the codebase (e.g., `accounts_db.rs` uses `saturating_sub` pervasively for comparable "alive vs. total" byte computations, e.g. [4](#0-3)  and [5](#0-4) ). This inconsistency (some accounting paths use saturating arithmetic, this one does not) is itself evidence that the raw subtraction here was an oversight rather than an intentionally-proven-safe invariant.

### Recommendation
Replace both raw subtractions in `AccountStorageReader::new` with `saturating_sub` (or add a debug assertion/`checked_sub` with a clear error) to match the defensive style used elsewhere in `accounts_db.rs`/`ancient_append_vecs.rs`:
```rust
let mut num_alive_bytes = num_total_bytes.saturating_sub(storage.get_obsolete_bytes(snapshot_slot));
...
num_alive_bytes = num_alive_bytes.saturating_sub(tombstone_offsets.len() * tombstone_stored_size);
```
Additionally, consider hardening `ObsoleteAccounts::mark_accounts_obsolete` to detect/reject duplicate offsets, or clamp `get_obsolete_bytes`'s sum to `self.accounts.len()`.

### Proof of Concept
Conceptual reproduction (would need to be validated in a live Devin session against the actual obsolete-marking call sites):
1. Construct an `AccountStorageEntry` and write accounts to it.
2. Call `mark_accounts_obsolete` twice for the same `(offset, data_len)` pair (simulating a double-mark race between two independent obsolete-detection call sites, e.g. concurrent clean + ancient-combine paths).
3. Call `AccountStorageReader::new(&storage, None, TombstonesFilter::Include, &mut reader)`.
4. Observe that `get_obsolete_bytes(None)` returns roughly `2 * stored_size` for that account, which combined with other obsolete/tombstone accounting can exceed `storage.accounts.len()`, causing the subtraction on `account_storage_reader.rs:101` to underflow (panic in debug, wraparound in release).
