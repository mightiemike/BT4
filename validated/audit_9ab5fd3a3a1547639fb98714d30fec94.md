### Title
Unbounded-recursion stack exhaustion via deeply nested JSON in the JSON-RPC request path - (File: `chain/jsonrpc/src/lib.rs`)

### Summary
The public JSON-RPC endpoint (`/`) deserializes every incoming HTTP body into `near_jsonrpc_primitives::message::Message` via Axum's `Json<Message>` extractor, and `Message`/`Request::params` is typed as `serde_json::Value`. `serde_json`'s `Deserialize` implementation for arbitrarily nested containers (`Value`, nested arrays/objects) is recursive with no depth limit, only a 10MB body-size cap is enforced. An unprivileged, unauthenticated RPC caller can send a deeply nested JSON payload well within the 10MB limit that causes the recursive parser to exhaust the native call stack, crashing the node process. This is the same bug class as CVE-2018-12066 (unbounded recursive parsing of attacker-controlled input causing stack-consumption denial of service), just moved from BIRD's `birdc` mask-expression parser to nearcore's JSON-RPC message parser.

### Finding Description
The RPC entry point deserializes the raw request body using Axum's `Json` extractor: [1](#0-0) 

`Message` is an untagged enum whose `Request`/`Notification`/`Response` variants hold a `params`/`result` field typed as `serde_json::Value`: [2](#0-1) [3](#0-2) 

The equivalent slice/str based entry points used elsewhere in the crate (`from_slice`/`from_str`) call straight into `serde_json::de::from_slice`, with no recursion-depth or nesting-depth guard applied before or during deserialization: [4](#0-3) 

`serde_json`'s deserializer for arbitrarily-nested JSON values (arrays/objects, and the generic `Value` type) recurses once per level of nesting with no built-in depth limit; this is a well-documented property of the crate (tracked upstream, e.g. RUSTSEC/GHSA advisories about unbounded recursion in `serde_json`). The only mitigation present in nearcore's RPC stack is a body-size limit (documented as "request body size limit (default 10MB)" in the architecture notes), which caps payload size but does not cap nesting depth. A payload of the form `[[[[[...]]]]]` (or nested objects `{"a":{"a":{"a":...}}}`) with millions of nesting levels fits comfortably inside 10MB (2 bytes per level of `[`+`]`), and each level adds one or more stack frames during deserialization, exceeding a typical 8MB thread stack and crashing the process (native stack overflow → SIGSEGV/abort), not a WASM-guest trap.

This is fundamentally different from — and outside the scope of — the WASM-guest-stack protections that DO exist in the runtime (`max_stack_height`, `finite_wasm` stack instrumentation, and the `max_blocks_per_function`/`max_blocks_per_contract` limits enforced in `runtime/near-vm-runner/src/prepare/instrument_v3.rs` and `prepare_v3.rs`). Those protections bound the *WASM interpreter's simulated operand stack*, not the *node process's native call stack* used while parsing an RPC request. There is no analogous depth-limiting guard for the JSON-RPC ingestion path.

### Impact Explanation
A successful stack-exhaustion crash of the RPC-serving `neard` process is a transaction/RPC-triggered halt of node availability. Because JSON-RPC nodes are commonly relied upon by wallets, indexers, and other validators/relays for `broadcast_tx_*` and `query` calls, a remote, unauthenticated attacker can repeatedly crash any publicly reachable RPC node with a single HTTP POST, degrading network observability/serviceability and — if the RPC handler shares a process/thread pool with block-production-critical actors — potentially disrupting validator operation. This matches the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
High likelihood: the attack requires only a single unauthenticated HTTP POST to the default RPC port (3030) with a crafted JSON body under 10MB; no signed transaction, staking, or special account permissions are required. `serde_json`'s recursive `Value`/generic deserialization has no depth guard by default, and nearcore's RPC layer applies no additional nesting-depth check before or during deserialization — only an overall byte-size cap.

### Recommendation
- Enforce an explicit JSON nesting-depth limit before/while deserializing untrusted RPC bodies (e.g., pre-scan for bracket/brace depth, or use a depth-limited/iterative JSON parser for the top-level envelope before handing `params` off to per-method typed parsers).
- Consider running request deserialization on a bounded-recursion-safe path (e.g., increasing thread stack size for the RPC-handling threads is a mitigation, not a fix) or reject requests whose nesting exceeds a small, protocol-appropriate limit (e.g., 64–128 levels) at the Axum extractor layer before `serde_json` recursion is invoked.
- Apply the same nesting-depth guard to any other externally reachable `serde_json::Value`/generic-JSON ingestion points (e.g., Rosetta RPC, debug RPC) that share this pattern.

### Proof of Concept
1. Start a `neard` node with the default JSON-RPC server enabled (port 3030).
2. Send an HTTP POST to `/` with `Content-Type: application/json` and a body such as:
   ```
   {"jsonrpc":"2.0","id":1,"method":"query","params": <N million nested arrays, e.g. "[" * 5_000_000 + "]" * 5_000_000> }
   ```
   sized to remain under the 10MB body limit (each nesting level costs 2 bytes, so ~5,000,000 levels fit in ~10MB).
3. Axum's `Json<Message>` extractor (`chain/jsonrpc/src/lib.rs` `rpc_handler`) invokes `serde_json` to deserialize the body into `Message`, which recurses once per nesting level while parsing the `params: Value` field.
4. The recursive descent exhausts the native call stack of the request-handling thread, crashing/aborting the `neard` process — a remotely triggerable denial of service requiring no authentication or on-chain transaction.
