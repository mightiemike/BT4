### Title
Unbounded-recursion JSON parsing of RPC request bodies causes StackOverflow denial of service - ([File: chain/jsonrpc-primitives/src/message.rs])

### Summary
The nearcore JSON-RPC server deserializes every incoming HTTP request body directly into the `Message` enum using axum's `Json<Message>` extractor, which internally relies on `serde_json`'s recursive-descent `Deserialize` implementation for `serde_json::Value`. Neither the `Message`/`Request`/`Notification` types nor the underlying `serde_json::Deserializer` enforce a maximum nesting depth for JSON arrays/objects. A single unauthenticated POST to the RPC endpoint containing a deeply nested `params` value (or nested `id`) will drive the parser into recursion proportional to the nesting depth, exhausting the request-handling thread's stack before any near-specific request validation (`RpcRequest::parse`, method dispatch, etc.) ever runs — mirroring the HAPI FHIR `JsonParser.readArray()/readObject()` unbounded-recursion bug (CVE-2026-62295).

### Finding Description
- The axum route handler `rpc_handler` extracts the body as `Json(request): Json<Message>` [1](#0-0) , meaning deserialization of the whole JSON body into `Message` happens automatically before `handler.process()` is ever invoked.
- `Message` is an untagged enum whose `Request`/`Notification` variants carry a `params: Value` field [2](#0-1) [3](#0-2) .
- `serde_json::Value`'s `Deserialize` implementation recurses once per nested array/object element with no depth cap; the library's own `from_slice`/`from_str` entry points used elsewhere in this same file confirm the direct pass-through to `serde_json::de::from_slice` with no wrapping depth guard [4](#0-3) .
- A search of the RPC crates found no `recursion_limit`, custom depth-limited deserializer, or any other nesting guard configured anywhere under `chain/jsonrpc*` — the only protection at the HTTP layer is a body-size limit (10MB, per `RPC_ARCHITECTURE.md`), which does not bound nesting depth: a 10MB payload of repeated `[` characters (e.g. `[[[[…]]]]`) can nest millions of levels deep while staying well under the size cap.
- Because deserialization happens as part of the axum extractor before `process_request_internal()`/`RpcRequest::parse()` run, none of the per-method validation logic (e.g., `Params::parse`, `validate_view_state_pagination`, method-specific size checks) ever gets a chance to reject the payload — the crash happens purely inside the generic JSON decode step, exactly analogous to the FHIR `JsonParser` case where `readArray()/readObject()` recursed before FHIR structural validation.
- Rust does not allow catching a stack overflow from unbounded recursion; it triggers a guard-page fault that aborts the entire process, not just the offending task/thread. Since the JSON-RPC server is single-process (all four backend actors — `ClientActor`, `ViewClientActor`, `RpcHandlerActor`, `PeerManagerActor` — live in the same `neard` process per `chain/jsonrpc/RPC_ARCHITECTURE.md`), an abort here takes down the entire node process, not merely the HTTP worker.

### Impact Explanation
Any unauthenticated RPC caller can crash the entire `neard` process serving the JSON-RPC API (port 3030) with a single POST request, with no transaction fee, signature, or account required. Because the four backend actors — including `ClientActor` and `RpcHandlerActor`, which participate in chunk/transaction processing and networking — share the same process as the JSON-RPC HTTP server, killing the process halts the node's participation in the network (including validator duties, if colocated), not just the RPC surface. This is a low-cost, repeatable denial-of-service vector against any RPC-serving node.

### Likelihood Explanation
Likelihood is high: the attack requires no authentication, no valid transaction, no gas payment, and no protocol-level state; it is a single crafted HTTP POST body (a few KB of deeply nested brackets is enough to exceed typical thread stack sizes, e.g. 8MB default stacks can be blown with tens of thousands of nesting levels, all fitting comfortably under the 10MB body limit). The endpoint (`/`) is the primary, always-enabled JSON-RPC interface and is typically exposed publicly.

### Recommendation
Enforce an explicit JSON nesting-depth limit before/while deserializing the RPC body into `Message`/`Value`:
- Use a depth-limited deserializer (e.g., wrap the `Deserializer` with a depth-tracking `Visitor`, or use `serde_json`'s `Deserializer::from_slice` combined with a custom recursive-descent guard) instead of relying on axum's default `Json<T>` extractor for untrusted bodies.
- Alternatively, pre-scan the raw bytes for a maximum bracket/brace nesting depth (cheap linear scan) and reject the request with a `400 Bad Request` before invoking `serde_json` deserialization.
- Apply the same guard to any other externally-reachable JSON entry points that deserialize into unconstrained `serde_json::Value` trees (e.g., `debug_handler`, `EXPERIMENTAL_*` params, Rosetta RPC's operation/action JSON models under `chain/rosetta-rpc/src/models.rs`), since these share the same untagged/`Value`-based deserialization pattern.
- Run the axum request-handling task on a spawned thread with a bounded, monitored stack, or use `stacker`/`spawn` with a guarded stack and graceful task cancellation instead of the ambient tokio worker stack, so a future recursion bug degrades to a single failed request rather than aborting the process.

### Proof of Concept
1. Start a `neard` node with the JSON-RPC server enabled on the default port (3030).
2. Send the following POST request (body kept under the 10MB limit, but nested tens of thousands of levels deep):
```
python3 - <<'EOF'
import requests
depth = 200000
body = '{"jsonrpc":"2.0","id":1,"method":"block","params":' + '['*depth + ']'*depth + '}'
requests.post("http://127.0.0.1:3030/", data=body, headers={"Content-Type": "application/json"})
EOF
```
3. Observe that the `neard` process crashes with a stack overflow (SIGSEGV / abort) while axum's `Json<Message>` extractor is still deserializing the body — before `JsonRpcHandler::process()` or any `RpcRequest::parse()` implementation is reached — taking the entire node process down.
