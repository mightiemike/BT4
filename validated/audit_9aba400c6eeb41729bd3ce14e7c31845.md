### Title
Replay-verify (`ensure_match_transaction_info`) silently ignores `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` mismatches - (File: `types/src/transaction/mod.rs`)

### Summary
This is the Aptos-native analog of the Tigris "value changed but not re-validated" bug class: a value (`TransactionOutput`/state root) can diverge from what was authenticated/expected, but the guard function that is supposed to catch such divergence deliberately skips checking it, so the mismatch is committed/accepted as if verified.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the sole invariant-checking function used by replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs::execute_and_verify`) and by the debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`) to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` pulled from backup/archive storage.

It validates `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash`: [1](#0-0) 

But then it explicitly stops, with a code comment admitting the gap: [2](#0-1) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
```

`TransactionInfo` (V1) carries three separate root/state-commitment fields that are all proof-bearing/authenticated data committed to the ledger and covered by the transaction accumulator: [3](#0-2) [4](#0-3) 

These fields are produced by `DoStateCheckpoint` / `DoLedgerUpdate` during normal execution (`state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, `position_state_checkpoint_hashes`) and are exactly what `assemble_transaction_infos` bakes into the `TransactionInfo` that becomes an accumulator leaf: [5](#0-4) [6](#0-5) 

`replay_on_archive.rs` re-executes historical transactions from backup and calls `ensure_match_transaction_info` as the *only* correctness gate before declaring the replayed chunk verified: [7](#0-6) 

Because the comparator never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` against the values recomputed by re-execution, a local execution bug, a storage-schema bug, or a hard-fork/consensus divergence that corrupts only the state-root fields (while leaving the write set, events, gas, and status untouched) would pass replay-verify undetected.

### Impact Explanation
Replay-verify is one of the primary detection mechanisms used to catch state-divergence and non-determinism bugs before/after mainnet upgrades (the state-integrity gate explicitly calls out "hard-fork-only divergence during commit, replay, restore, or proof verification" as in-scope). A silent gap in the verifier's root-hash comparison means:
- A bug that corrupts the Sparse-Merkle state-checkpoint root, the hot-state root, or the native-position state root (all committed, proof-bearing fields embedded in `TransactionInfoV1`) would not be flagged by `replay_on_archive`, even though the local `LedgerUpdateOutput`/state root actually diverges from the authenticated ledger.
- This directly undermines the "authenticated API or state-view output bound to the wrong version/root/object" and "wrong ... transaction proof ... accepted as valid" invariants: replay-verify, which exists specifically to catch such divergence, reports success ("Nothing to verify" / no error) despite the corrupted root.
- The comment itself flags this as a precondition gate for a specific in-development feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`), meaning the gap is known but currently unaddressed in the invariant-checking code path.

### Likelihood Explanation
This is a real, currently-present gap in the shipped `ensure_match_transaction_info` function (not a hypothetical), reachable by any operator running `db-tool replay-on-archive` or the Aptos debugger — no privileged access or malicious peer behavior required. However, the *practical* trigger requires a separate root-cause bug (e.g., in state-checkpoint hashing, hot-state root computation, or the position-state subsystem) to actually produce a divergent checkpoint hash; this finding itself is the "missing detector" rather than a root-cause corruption. The severity/likelihood is bounded by whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state root subsystems are active on mainnet — I was not able to fully confirm the on-chain default/rollout status of these feature flags from the available index excerpts, so the direct mainnet blast radius (vs. testnet-only "trading-native" feature) is uncertain.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, and, when present (`TransactionInfoV1`), `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` against locally recomputed values before declaring a match, as the existing TODO already specifies. Ensure `replay_on_archive` and the debugger surface these mismatches as verification failures, and gate any future enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on this check being implemented.

### Proof of Concept
1. Corrupt (or introduce a bug that corrupts) only the state-checkpoint/hot-state/position-state root computed for a given block in `DoStateCheckpoint`/`DoLedgerUpdate`, while leaving write set, events, gas, and status output identical to the authenticated backup.
2. Run `db-tool replay-on-archive` against a backup range covering that version.
3. `execute_and_verify` calls `ensure_match_transaction_info`, which checks status/gas/write-set-hash/event-root-hash only [8](#0-7)  and returns `Ok(())`, reporting the chunk as successfully replayed even though the checkpoint/state root diverges from the ledger's authenticated `TransactionInfo`.

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
