### Title
Webhook `domain` header is not authenticated by the HMAC, allowing cross-tenant session hijack via header spoofing - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`, `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The Shopify webhook validation flow verifies the HMAC over the raw request body only, using the app's single shared `apiSecretKey`. It never binds that HMAC to the `domain` (shop) header. The `domain` header is trusted "as is" once the body HMAC checks out, and is then used directly to look up and load that shop's persisted offline session/access token. This mirrors the `QuestSystem` bug: a valid, "locked/verified" object (a signed webhook body) is accepted for use against an arbitrary target (any shop domain) without verifying that the signed data actually belongs to/was issued for that target.

### Finding Description
`validateHmacFromRequestFactory` computes and compares the HMAC using only `rawBody` and the app's `apiSecretKey`: [1](#0-0) 

The `domain` header is read and returned separately by `checkWebhooksHeaders`/`checkEventsHeaders` in `validate.ts` after the body-only HMAC has already succeeded, with no cryptographic linkage between the two: [2](#0-1) [3](#0-2) 

Downstream, `authenticateWebhookFactory` (present in both `shopify-app-remix` and `shopify-app-react-router`) takes `check.domain` from this unauthenticated header and uses it as-is to load an offline session and build an authenticated admin client for that shop: [4](#0-3) 

`ensureValidOfflineSession` then loads/creates the session purely by the `shop` string passed in, with no additional check that the request body's HMAC was meant for that specific shop: [5](#0-4) 

Because the app's `apiSecretKey` is shared across every shop that installs the app (it is not per-installation), any merchant who has legitimately received one authentic webhook (a valid `rawBody` + matching HMAC header, e.g. via Shopify's "resend webhook" feature or their own store's traffic) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or equivalent `domain`) header with a different, victim shop's domain. Validation passes because the HMAC never covered the domain, and the handler proceeds to load and use the victim shop's stored offline access token to process the (attacker-controlled) payload — this is the direct analog of "using an NFT without checking who owns it": the signed artifact (webhook body/HMAC) is accepted and applied to a target that never authorized it.

### Impact Explanation
An attacker (any merchant with the app installed) can force the webhook handler to run business logic against another tenant's session/admin API context, potentially triggering unauthorized data mutation, exfiltration via the returned `admin`/`session` objects, or corrupting another shop's app-side state — a cross-tenant confused-deputy attack requiring only a single unprivileged merchant account.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the app on their own shop (or otherwise obtains one valid rawBody+HMAC pair, which Shopify makes trivially available through webhook resend/test tooling), and (2) knowledge that another target shop uses the same app (discoverable if the app is public). No secret leakage, MITM, or privileged access is required — only crafting an HTTP POST with a substituted header.

### Recommendation
Bind the HMAC/signature verification to the claimed shop domain, e.g. by including the `domain`/`shop` header value in the HMAC-covered data, or by cross-checking the domain header against a shop identifier embedded in the payload/topic metadata before trusting it for session lookup. At minimum, after loading the session for `check.domain`, re-validate that the offline session's own stored shop matches an independently-verifiable value (not solely the attacker-controlled header) before using it to authorize any consumer logic.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger any webhook topic (e.g. `products/create`) so Shopify delivers a real webhook with a genuine `rawBody` and matching `X-Shopify-Hmac-Sha256` value, both observable by the attacker.
2. Replay that exact request to the app's public webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`, an unrelated shop that also has the app installed.
3. `validateHmacFromRequestFactory` succeeds because it only checks `rawBody` against the app's shared secret [6](#0-5) .
4. `authenticateWebhookFactory` then loads `victim-shop.myshopify.com`'s offline session and builds an `admin` client scoped to that shop [7](#0-6) , letting attacker-controlled payload data drive logic executed with the victim shop's credentials.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
