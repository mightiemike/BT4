This confirms the critical detail: `DefaultExpiryAfterBlocks = 100_000_000` [1](#0-0)  — ballots essentially never expire in practice ("effectively disable expiry"). This means `ExpireBallotsBeforeHeight`'s active-set pruning will not remove any ballot for ~19 years, so `ActiveBallotIDs` only grows monotonically with every unique inbound/outbound/chain-meta/TSS observation that has not yet finalized.

### Title
Unbounded `ActiveBallotIDs` iteration in `CreateBallot`/`ExpireBallotsBeforeHeight` causes per-vote-tx gas growth and eventual chain-wide inbound/outbound processing DoS - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
Every time a brand-new ballot is created (i.e., on the first `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, or TSS vote for a not-yet-seen observation), `CreateBallot` unconditionally walks the *entire* `ActiveBallotIDs` set via `ExpireBallotsBeforeHeight` before creating the new record [2](#0-1) . This is the same bug class as the reported `clearLoop()`: an O(n) loop over unboundedly-growing state executed synchronously inside a single transaction.

### Finding Description
`ExpireBallotsBeforeHeight` iterates every key in `ActiveBallotIDs` with no pagination and performs a `Ballots.Get` read per key: [3](#0-2) . This function is invoked from `CreateBallot`, which itself runs inline (not in `BeginBlock`/`EndBlock`) on the very first vote for any new observation: `GetOrCreateBallot` → `CreateBallot` → `ExpireBallotsBeforeHeight` [4](#0-3) .

`ActiveBallotIDs` entries are only removed when a ballot expires (`BlockHeightExpiry <= currentHeight`) or finalizes via 2/3 threshold. Since `DefaultExpiryAfterBlocks` is set to 100,000,000 blocks (deliberately "effectively disable expiry") [1](#0-0) , the expiry-based cleanup path in `ExpireBallotsBeforeHeight` essentially never fires. The only other removal path is normal 2/3-threshold finalization via `VoteOnBallot`/`CheckIfFinalizingVote` [5](#0-4) , which requires timely honest-UV consensus.

Inbound observations are created by ordinary, unprivileged, external-chain deposit transactions (any user can submit a gateway deposit on a source chain), each producing a unique ballot key `sha256(sourceChain:txHash:logIndex)` per the README [6](#0-5) . A user flooding the source chain with many distinct low-value deposits (only paying source-chain gas, no Push-Chain privilege required) forces UVs to submit `MsgVoteInbound` for each unique event. Every one of these first-votes triggers a full walk of `ActiveBallotIDs` inside `CreateBallot`. As the count of concurrently-open (not-yet-finalized) ballots grows — bounded only by the rate at which the attacker can generate distinct inbound events versus the rate 2/3 of UVs can vote them to finality within a block — each subsequent `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta` transaction becomes progressively more expensive (O(n) KV reads per new-ballot creation, mirroring the reported `clearLoop()` mechanics exactly: iterating and doing per-iteration storage reads over a large growing set within a single transaction).

### Impact Explanation
Once `ActiveBallotIDs` grows large enough that a single `Ballots.Get` read for every active entry exceeds the block/tx gas limit, `CreateBallot` (and therefore any subsequent first-vote for a new inbound/outbound/chain-meta/TSS observation) fails with out-of-gas. Because `CreateBallot` is the single choke point through which *all* new crosschain observations must pass before they can be voted on, this can durably stall the creation of new ballots platform-wide — new user deposits (inbounds) can no longer be voted through to execution, and pending outbounds can no longer be created/finalized. This constitutes a non-network-level denial of service reachable by an ordinary, unprivileged external user (spamming source-chain deposits costs only source-chain gas) and can manifest as effective freezing of newly-deposited user funds (inbounds stuck unvoted/unminted) — in line with the in-scope "permanent freezing of user or protocol-controlled funds" and "denial of service ... reachable without privileged control" impacts.

### Likelihood Explanation
Likelihood is Medium-Low to Medium: exploitation requires the attacker to sustain a volume of distinct inbound/outbound observations exceeding the chain's UV vote-finalization throughput long enough to grow `ActiveBallotIDs` into the tens/hundreds of thousands of entries. Because expiry is deliberately disabled (100M blocks) as noted in the code comment, there is no natural self-healing mechanism for a backlog once it accumulates from any cause (bursts, temporary UV downtime, or deliberate flooding), making the growth effectively permanent absent operator/governance intervention (a purge upgrade like `app/upgrades/purge-expired-outbounds/upgrade.go` was needed to manually clear a stuck ballot backlog previously, corroborating that this exact growth pattern has already occurred in production) [7](#0-6) .

### Recommendation
Remove the unconditional full-set walk from the hot `CreateBallot` path. Options: (1) move ballot expiry sweeping to `EndBlocker`/`BeginBlocker` processed in small bounded batches per block instead of inline on every new-ballot creation; (2) cap/paginate `ExpireBallotsBeforeHeight` to process at most N stale ballots per call; (3) re-enable a bounded, sane `DefaultExpiryAfterBlocks` combined with a scheduled background pruning job (analogous to the recommendation in the source report: "divide the work between multiple transactions") so `ActiveBallotIDs` cannot grow without bound within a single call path.

### Proof of Concept
1. Deploy/observe on a source chain reachable by `x/uexecutor`'s inbound flow.
2. As an unprivileged user, submit a very large number (tens of thousands) of small, distinct gateway deposit transactions on the source chain in a short window, faster than 2/3 of UVs can finalize each corresponding ballot.
3. Each distinct deposit produces a unique `GetInboundBallotKey` and triggers `VoteOnInboundBallot` → `VoteOnBallot` → `GetOrCreateBallot` → `CreateBallot` → `ExpireBallotsBeforeHeight`, which iterates the full, growing `ActiveBallotIDs` set and does a `Ballots.Get` per entry.
4. As `ActiveBallotIDs` grows (never shrinking meaningfully due to the 100M-block expiry), observe that `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta` transaction gas cost climbs linearly with active-ballot count until it exceeds the block gas limit, at which point new ballot creation (and thus new inbound/outbound processing) fails chain-wide.

Note: I was not able to execute this against a live node/testnet to empirically confirm the exact ballot count needed to trigger OOG, nor to fully verify whether any additional out-of-scope rate limiting (e.g., mempool/ante-level throttling on `MsgVoteInbound` frequency) exists that could reduce practical exploitability; this is based on static code-path analysis of the cited files only.

	return newBallot, true, err
}

func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}

func (k Keeper) VoteOnBallot(
	ctx context.Context,
	id string,
	ballotType types.BallotObservationType,
	voter string,
	voteResult types.VoteResult,
	voters []string,
	votesNeeded int64,
	expiryAfterBlocks int64,
) (
	ballot types.Ballot,
	isFinalized bool,
	isNew bool,
	err error) {

	k.Logger().Debug("vote on ballot",
		"ballot_id", id,
		"ballot_type", ballotType.String(),
		"voter", voter,
		"vote_result", voteResult.String(),
		"votes_needed", votesNeeded,
	)

	ballot, isNew, err = k.GetOrCreateBallot(ctx, id, ballotType, voters, votesNeeded, expiryAfterBlocks)
	if err != nil {
		return ballot, false, false, errors.Wrap(err, "Error while voting on the ballot")
	}

	// reject votes on ballots whose nominal expiry has passed
	currentHeight := sdk.UnwrapSDKContext(ctx).BlockHeight()
	if ballot.IsExpired(currentHeight) {
		// Transition PENDING ballots to EXPIRED so subsequent reads see the
		// canonical status and the secondary indexes stay consistent. Already
		// non-PENDING ballots fall through to the Status check below for the
		// existing "already X" error message.
		if ballot.Status == types.BallotStatus_BALLOT_STATUS_PENDING {
			if mErr := k.MarkBallotExpired(ctx, id); mErr != nil {
				return ballot, false, isNew, errors.Wrap(mErr, "failed to mark ballot expired during late-vote rejection")
			}
			k.Logger().Warn("late vote rejected, ballot marked expired",
				"ballot_id", id,
				"expiry_height", ballot.BlockHeightExpiry,
				"current_height", currentHeight,
				"voter", voter,
			)
			return ballot, false, isNew, fmt.Errorf("ballot %s expired at height %d (current %d)", id, ballot.BlockHeightExpiry, currentHeight)
		}
	}

	if ballot.Status != types.BallotStatus_BALLOT_STATUS_PENDING {
		k.Logger().Warn("ballot is not in pending state, cannot vote",
			"ballot_id", id,
			"ballot_status", ballot.Status.String(),
			"voter", voter,
		)
		return ballot, false, false, fmt.Errorf("ballot %s is already %s", id, ballot.Status.String())
	}

	if isNew {
		k.Logger().Debug("created new ballot", "ballot_id", id, "ballot_type", ballotType.String())
		err := k.ActiveBallotIDs.Set(ctx, id)
		if err != nil {
			return ballot, false, false, errors.Wrap(err, "Error while voting on the ballot")
		}
	}

	ballot, err = k.AddVoteToBallot(ctx, ballot, voter, voteResult)
	if err != nil {
		return ballot, false, isNew, err
	}

	ballot, isFinalizing, err := k.CheckIfFinalizingVote(ctx, ballot)
	if err != nil {
		return ballot, false, false, err
	}

	return ballot, isFinalizing, isNew, nil
}

- **Inbound** — A gateway event observed on an external chain. Universal Validators wait for finality, then vote it via `MsgVoteInbound` on `x/uexecutor`. Once 2/3 vote the same observation, the core validator executes it on Push Chain (mints PRC20s, runs the user's payload through their UEA).
