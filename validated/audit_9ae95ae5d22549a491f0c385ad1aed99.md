### Title
`ark_de` skips subgroup validation (`Validate::No`) allowing non-subgroup points into DKG `Subtranscript` aggregation - ([File: crates/aptos-crypto/src/arkworks/serialization.rs])

### Summary
The `ark_de` helper used to deserialize `Subtranscript<E>`'s `V0`, `Vs`, `Cs`, `Rs` fields (`crates/aptos-dkg/src/pvss/chunky/subtranscript.rs`) calls `A::deserialize_with_mode(..., Compress::Yes, Validate::No)`, explicitly disabling arkworks' post-deserialization validity check.

### Finding Description
`ark_de` is defined as: [1](#0-0) 

`Validate::No` instructs arkworks to skip the `Valid::check()` call that would normally be run after deserialization. For `ark_ec` affine point types, `check()` is what performs subgroup membership verification (via cofactor clearing / subgroup checks), not merely the on-curve check. With compressed serialization, deserialization does reconstruct a point on the curve equation (from the x-coordinate and a sign bit), but curves like BLS12-381 have `G1`/`G2` groups with nontrivial cofactors, so a valid on-curve point is not guaranteed to lie in the prime-order subgroup unless `check()` (subgroup check) is explicitly performed. Since `Validate::No` is passed, this subgroup check is skipped entirely.

`Subtranscript<E>` applies `ark_se`/`ark_de` via serde attributes to `V0`, `Vs`, `Cs`, `Rs`: [2](#0-1) 

and is deserialized directly from untrusted bytes via `TryFrom<&[u8]>` / BCS: [3](#0-2) 

Once deserialized, these fields are lifted straight into projective form for aggregation without any additional subgroup check: [4](#0-3) 

I searched for any subsequent subgroup-membership check (`is_in_correct_subgroup`, `check()`) being called explicitly on these fields elsewhere in the DKG aggregation/verification path but did not find one in the reachable code within the tool budget available — I was unable to fully confirm whether some other layer of the PVSS verification pipeline (e.g., `verify_common.rs`, SCRAPE low-degree test, or sigma-protocol proof verification) implicitly performs a subgroup check before or after aggregation. This is a gap in my investigation that should be verified further (e.g., by checking `crates/aptos-dkg/src/pvss/chunky/verify_common.rs` and the transcript `verify()`/`aggregate_with` call chain, and by testing that a crafted small-subgroup point actually survives into `to_aggregated`/aggregation).

### Impact Explanation
If confirmed that no other subgroup check exists on the deserialize→aggregate path, a party submitting a malicious/crafted DKG transcript (an "unprivileged" dealer contribution, which is proof/consensus input) could inject a curve point that is on-curve but outside the prime-order subgroup into `V0_proj`/`Vs_proj`/`Cs_proj`/`Rs_proj`. Small-subgroup / invalid-curve attacks against pairing/DKG schemes can allow information leakage about decrypted shares, or corruption of the aggregated public key / dealt shares, breaking the invariant that all committed elements are valid group elements of the correct order. This would corrupt DKG-derived state that is committed on-chain/on-chain consensus artifacts.

### Likelihood Explanation
Likelihood depends on whether the crafted point can actually reach `aggregate_with`/`to_aggregated` without being rejected elsewhere in transcript verification (e.g., a SCRAPE low-degree test or an explicit `is_in_correct_subgroup` check performed as part of `verify()` prior to aggregation). I could not verify this within the available tool budget, so I cannot assert with certainty that this is exploitable end-to-end — only that the specific `ark_de` deserializer used for these fields does not itself perform the check, which is the necessary precondition.

### Recommendation
Change `ark_de` (or add a dedicated, stricter variant for consensus/DKG-critical types) to use `Validate::Yes` instead of `Validate::No`, so subgroup membership is enforced at the point of deserialization for all types that rely on `#[serde(deserialize_with = "ark_de")]`, especially `Subtranscript<E>`'s `V0`/`Vs`/`Cs`/`Rs`. Alternatively, explicitly call `.check()` (or `is_in_correct_subgroup_assuming_on_curve()`) on every deserialized group element before it is used in `to_aggregated`/`aggregate_with`.

### Proof of Concept
Not fully constructed — would require: (1) generating a BLS12-381 G1/G2 point of the correct order-p·h form that lies outside the prime-order subgroup (e.g., using arkworks test utilities to construct a cofactor-multiple point not cleared to the subgroup), (2) serializing it with `serialize_with_mode(Compress::Yes)`, (3) embedding those bytes into a BCS-encoded `Subtranscript` payload, and (4) confirming `Subtranscript::try_from` / `bcs::from_bytes` accepts it (since `Validate::No` is used) and that it propagates unchecked into `to_aggregated()`. I verified step 4's code path structurally (no check present in `ark_de` or `to_aggregated`) but did not execute this against the further downstream `verify()`/aggregation call sites to confirm no other check intercepts it.

pub fn ark_de<'de, D, A: CanonicalDeserialize>(data: D) -> Result<A, D::Error>
where
    D: serde::de::Deserializer<'de>,
{
    let s: Bytes = serde::de::Deserialize::deserialize(data)?;
    let a = A::deserialize_with_mode(s.reader(), Compress::Yes, Validate::No);
    a.map_err(serde::de::Error::custom)
}
