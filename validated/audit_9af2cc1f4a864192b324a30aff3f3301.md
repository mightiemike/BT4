### Title
Fork-divergent poison-microblock report causes matured coinbase reward mismatch / FATAL panic on shared-ancestor reward maturation - (File: `stackslib/src/chainstate/stacks/db/accounts.rs`)

### Summary
`StacksChainState::find_mature_miner_rewards` looks up `get_poison_microblock_report(clarity_tx, reward_height)` against the *currently-processing block's* fork-local Clarity/MARF state, then redirects the matured coinbase to the poison reporter instead of the original miner. Because a `PoisonMicroblock` report is just a standalone transaction that can be mined into one sibling fork's blocks and omitted from another sibling fork that shares the same matured ancestor tenure, the two forks compute different `MinerReward` records for the identical `(parent_block_id, child_block_id)` key, which `inner_insert_matured_miner_reward` asserts must be equal.

### Finding Description
The broken equality is: `MinerReward` computed for tenure `T` (matured at `reward_height = tip_height - MINER_REWARD_MATURITY`) on fork A must equal the `MinerReward` computed for the same tenure `T` on sibling fork B, since both forks key their `matured_rewards` insert by the same common-ancestor `parent_block_id`/`child_block_id`: [1](#0-0) 

`find_mature_miner_rewards` computes the reward by consulting `get_poison_microblock_report`, which reads Clarity DB / MARF state scoped to the block currently being processed (i.e., fork-local state): [2](#0-1) [3](#0-2) 

`calculate_miner_reward` then fully redirects the coinbase share to the poison reporter (as `child_address`/`child_recipient`) when a report is present, vs. paying the original miner when none is present: [4](#0-3) 

Exploit flow: an attacker constructs two conflicting, validly-signed microblock headers at the same sequence number for tenure `T` (standard poison-microblock evidence — this evidence is off-chain data, not fork-specific). They submit a `PoisonMicroblock` transaction carrying this evidence so that it is mined into a block on fork A (built on top of `T`), but ensure (simply by not relaying/broadcasting it in time, or by natural network partition during an organic reorg) that the equivalent block on sibling fork B does not include it. When each fork's chain processing reaches `tip_height = T_height + MINER_REWARD_MATURITY`, `find_mature_miner_rewards` is invoked on each fork's own `clarity_tx`. Fork A's Clarity state contains the poison report (visible via the MARF trie built along fork A), so the coinbase is redirected to the reporter. Fork B's Clarity state does not, so the coinbase is paid to the original miner. Both computations target the identical `(parent_block_id, child_block_id)` insert key for tenure `T`'s matured reward, since `T` is a common ancestor of both forks. `inner_insert_matured_miner_reward`'s explicit multi-fork branch then compares the two stored records with `assert_eq!`, which is documented in-code to assume they are always identical for a shared ancestor — an assumption the poison-microblock reachability above breaks.

No existing guard prevents this: poison-microblock evidence validity does not depend on which fork the report transaction is mined in, `get_poison_microblock_report`/Clarity DB lookups are inherently fork-local by MARF design, and there is no cross-fork reconciliation step before the `assert_eq!` fires.

### Impact Explanation
Two outcomes are possible depending on whether both forks are ever locally processed by the same node before one becomes canonical:
- If only the eventually-canonical fork's blocks are processed by a given node, that node simply pays the coinbase according to whichever fork it followed — this alone is a "reward mis-payment" divergence between what different honest nodes would compute if they happened to follow different forks transiently, matching the "reward mis-payment" / "temporary tip disagreement" category.
- If a node processes blocks from *both* sibling forks (which happens naturally for any node that observes a live reorg/fork contention, since Stacks nodes validate/process all valid received blocks, not only the momentarily-heaviest tip), the `assert_eq!` in `inner_insert_matured_miner_reward` fires with a `"FATAL: tried to insert multiple distinct matured parent block reward records"` panic, crashing the node process. Since every honest node in the network eventually observes both sibling blocks during normal gossip/reorg propagation, this is a network-wide, irrecoverable-without-a-patch halt — matching the Critical "permanent freezing" category.

### Likelihood Explanation
Preconditions: two sibling Nakamoto/Stacks forks sharing a common ancestor tenure `T`, with the reorg/fork boundary occurring within `MINER_REWARD_MATURITY` blocks of `T`'s maturation height, and a valid `PoisonMicroblock` transaction (which only requires possession of two conflicting, correctly-signed microblock headers for `T`'s miner — obtainable by any observer of a genuine microblock fork, no special stake or privilege) mined into one fork but not the other. This requires no majority stake, no signer collusion, and no more than the ability to broadcast a single standard transaction and have it picked up by any one miner on one side of an already-existing fork — well within the stated unprivileged attacker model. The main precondition (a live microblock fork existing at all) is itself rare in Nakamoto (microblocks are largely a legacy epoch2x construct), which somewhat limits real-world frequency, but the code path and mismatch are fully reachable given that precondition.

### Recommendation
Make matured coinbase/poison-report resolution fork-independent for a given ancestor tenure, e.g., resolve poison-microblock reports based on state anchored strictly to the *tenure being matured* (its own block/tenure id) rather than height-relative lookups against the block currently being processed; alternatively, before asserting equality in `inner_insert_matured_miner_reward`, detect a legitimate divergence caused by differing poison-report visibility and handle it by recomputing/reconciling rather than panicking (e.g., downgrade to a logged inconsistency and prefer the report-bearing fork's outcome deterministically), or require poison-microblock evidence to be committed/anchored at a fixed, fork-agnostic point (e.g., only accepted in the same tenure as `T` itself) so both forks converge before divergence is possible.

### Proof of Concept
Rust integration test plan (two-fork harness, e.g. in `stackslib/src/chainstate/nakamoto/tests` or `stackslib/src/chainstate/stacks/tests/block_construction.rs`):
1. Build a chain up to tenure `T` at height `H`.
2. Fork the chain into fork A and fork B both extending `T`.
3. On fork A only, include a valid `PoisonMicroblock` transaction reporting conflicting microblock headers for `T`'s miner.
4. Advance both forks to height `H + MINER_REWARD_MATURITY`, invoking block processing (which internally calls `find_mature_miner_rewards`/`inner_insert_matured_miner_reward`) on each fork independently within the same node's chainstate DB.
5. Assert equality broken: `StacksChainState::get_matured_miner_payment(conn, parent_block_id_T, child_block_id_T)` recipient on fork A == poison reporter address, while the in-memory/just-computed `MinerReward` on fork B == original miner address for the same `(parent_block_id_T, child_block_id_T)` key.
6. Additionally assert that processing fork B's maturing block after fork A's (or vice versa) within the same chainstate DB triggers the `assert_eq!` panic in `inner_insert_matured_miner_reward` (catch via `std::panic::catch_unwind` or expect the process/thread panic), confirming the FATAL mismatch path is reachable.
