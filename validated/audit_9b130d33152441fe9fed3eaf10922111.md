### Title
Interest-index checkpoint (`last-update`) is only advanced when the computed index changes, letting a stale time-delta apply the current spot rate retroactively over an arbitrarily long dormant window - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`v0-vault-stx.clar` (and the equivalent `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) accrues interest by comparing `stacks-block-time` against a `last-update` checkpoint. That checkpoint is only advanced inside `accrue()` when the newly computed `index`/`lindex` differ from the stored ones [1](#0-0) . If the market rate is (or rounds to) zero for a period, the index does not change, so `last-update` is never bumped even though real time keeps passing. When the rate later becomes non-zero, `next-index`/`next-liquidity-index` compute `time-delta = stacks-block-time - last-update` and apply the *current* spot rate to that entire stale span [2](#0-1) , retroactively charging/crediting interest for a period during which the true rate was different (typically near zero).

### Finding Description
Each vault tracks a borrow index and liquidity index, updated via `next-index` / `next-liquidity-index`, which multiply the stored index by a rate-and-time-based multiplier computed from `time-delta = stacks-block-time - (var-get last-update)` [2](#0-1) .

`accrue()` writes the freshly computed `next`/`nliq` back to `index`/`lindex`, but only advances `last-update` when at least one of the two values actually changed:
```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [3](#0-2) 

`interest-rate` is a pure function of the current `utilization()` at call time - it has no memory of what utilization was during the elapsed window [4](#0-3) . Sequence of events:
1. Vault utilization drops to (or stays at) a level where `interest-rate()` returns 0 (or a value small enough that `calc-multiplier-delta` rounds `next` to exactly `idx`). `accrue()` runs (e.g. via a deposit/redeem/repay), computes `next == idx`, and therefore skips the `var-set last-update` branch - the checkpoint freezes while real block time keeps advancing.
2. This dormant state can persist for an arbitrary length of real time (weeks/months) since nothing forces `last-update` to move independently of an index change.
3. A single transaction (e.g. `system-borrow`, which calls `accrue()` first) raises utilization sharply, so `interest-rate()` now returns a materially higher rate.
4. Inside that same call, `next-index`/`next-liquidity-index` compute `time-delta` against the still-frozen, stale `last-update`, and apply the *new, higher* rate across the *entire* stale duration via `calc-multiplier-delta`, producing one giant index jump that is written to `index`/`lindex` and used immediately to compute `debt-delta`, `reserve-inc`, and treasury LP minting in the same `accrue()` call [5](#0-4) .

This is the same class of bug as the external report: `nextBudgetUpdatePeriod`/`last-update` is a checkpoint whose invariant ("advances whenever time that should count elapses") is broken by a conditional guard tied to a *different* condition (index change) rather than to elapsed time itself, so a stale window's contribution can later be misattributed to a rate that only became effective afterward - all resolved within one function/transaction (`accrue()`), matching the "clock advanced only on change" analog class.

### Impact Explanation
The mis-attributed interest inflates (or could under-inflate, depending on rate direction) both the borrow index and liquidity index at once. Because reserve/treasury minting (`treasury-lp`) is computed off `debt-delta` derived from this jump [6](#0-5) , a large retroactive multiplier can cause an outsized one-time debt increase for borrowers and/or an outsized one-time yield credit to suppliers/treasury that does not correspond to any actual accrual event during the frozen window - i.e., value is created or misallocated between borrowers, suppliers, and the treasury based on a rate that never applied during most of the elapsed time. This lands on theft/freezing of unclaimed yield (In-scope High impact: interest/yield miscalculated and permanently locked into the index at the wrong rate, benefiting one class of participants at the expense of another).

### Likelihood Explanation
Requires the vault's utilization to sit at/near zero-rate territory long enough for `next == idx` repeatedly (plausible for any vault when demand is low, e.g., a newly-launched or lightly used asset), followed by a legitimate large borrow. No privileged access, oracle manipulation, or DAO action is required - only normal user activity (or lack thereof) plus one borrow transaction. Likelihood is moderate: it depends on the vault experiencing an extended dormant period, which is a plausible but not universal market condition.

### Recommendation
Decouple the `last-update` checkpoint from whether the index visibly changed. Always set `last-update` to `stacks-block-time` at the end of every `accrue()` call regardless of whether `index`/`lindex` moved, so `time-delta` in the next call reflects only the time since the last accrual attempt, not since the last *visible* change. If precision loss from very small deltas is the original motivation for the conditional, accumulate a separate "pending sub-precision" remainder instead of stalling the checkpoint indefinitely.

### Proof of Concept
1. Vault `v0-vault-usdc` starts with utilization such that `interest-rate()` rounds to a multiplier equal to `INDEX-PRECISION` (effectively 0% given current point-curve/utilization) for many consecutive weeks; every call to `accrue()` (via deposits/redeems) computes `next == idx`, `nliq == lindex`, so the `(if (or ...) (var-set last-update ...))` branch never fires - `last-update` stays at its old value while `stacks-block-time` advances by weeks.
2. A borrower calls `borrow`, sharply increasing utilization; `market.clar`'s `borrow()` triggers `vault-system-borrow` → `accrue()` [7](#0-6) .
3. Inside this single `accrue()` call, `interest-rate()` now returns the new, higher post-borrow rate; `time-delta = stacks-block-time - last-update` equals the entire weeks-long stale window.
4. `calc-multiplier-delta(rate, time-delta, true)` compounds the new rate over the full stale window, producing a large one-shot jump in `index`/`lindex`, which immediately inflates `debt-delta`/`reserve-inc`/treasury minting and every user's scaled-debt valuation in that same transaction - all attributable to a rate that only started applying at step 2.

(define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx
        (let (
            (rate (interest-rate))
            (time-delta (- stacks-block-time (var-get last-update)))
            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
                          (calc-multiplier-delta rate time-delta true))))
          (calc-index-next idx multiplier)))))

  (let ((states (var-get pause-states))
        (lidx (var-get lindex)))

        lidx

            (rate (interest-rate))
            (liquidity-rate (calc-liquidity-rate rate (utilization) (var-get fee-reserve)))

            (multiplier (if (is-eq time-delta u0)
                          INDEX-PRECISION
