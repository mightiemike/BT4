### Title
`send-underlying` transfers real SIP-010 tokens with `sender = current-contract` while `tx-sender` remains the external caller, causing every redeem of sBTC/USDC/USDH-backed vaults to revert and permanently strand user funds - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`, `mainnet/contracts/vault/v0-vault-usdc.clar`, `mainnet/contracts/vault/v0-vault-usdh.clar`)

### Summary
In the three vaults that wrap real, externally-deployed SIP-010 tokens (sBTC, usdcx/USDC, usdh-token-v1), the private `send-underlying` helper calls `transfer` on the external token contract with `sender = current-contract` (the vault itself) but is invoked directly from a public function without wrapping the call in `as-contract?`. Because Clarity's `tx-sender`/`contract-caller` are only rebound to the contract's own principal inside an `as-contract?` block, the token's `transfer` call is executed with `tx-sender` = the original external caller (the redeemer), not the vault. Any compliant fungible-token/SIP-010 implementation enforces that the sender parameter of `transfer` must equal the caller's principal (Clarity has no ERC20-style `approve`/`allowance`, so there is no way to authorize a third party). Consequently `sender != tx-sender` and the call unconditionally fails, exactly mirroring the reported `CoreCollection.withdraw` bug where `transferFrom(address(this), msg.sender, amount)` reverts because `allowance[this][this] == 0` — here the analogous mismatch is `sender=current-contract` vs. actual caller identity, with the same "always revert" outcome.

### Finding Description
Compare the correct pattern (used for the internally minted wrapper `wSTX` and for `ststx`/`ststxbtc`) with the broken pattern (used for real external `sbtc-token`, `usdcx`, `usdh-token-v1`):

Correct pattern, e.g. `mainnet/contracts/vault/v0-vault-stx.clar` (local-testing mirror shown, mainnet uses identical structure):
```
(define-private (send-underlying (amt uint) (account principal))
  (begin
    (try! (as-contract? ((with-stx amt))
      (try! (contract-call? .wstx transfer amt tx-sender account none))
      true))
    (ok true)))
``` [1](#0-0) 

Here `as-contract?` rebinds `tx-sender`/`contract-caller` to the vault's own principal for the duration of the inner call, so `sender = tx-sender = current-contract`, which the token's transfer check accepts.

Broken pattern, `mainnet/contracts/vault/v0-vault-sbtc.clar`:
```
(define-private (send-underlying (amount uint) (account principal))
  (begin
    (try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token transfer amount current-contract account none))
    (ok true)))
``` [2](#0-1) 

Identical broken pattern for USDC: [3](#0-2) 

Identical broken pattern for USDH: [4](#0-3) 

`send-underlying` is called from the public `redeem` entry point after burning the user's zTokens and updating internal accounting:
```
(try! (ft-burn? zft amount account))
(try! (send-underlying inkind recipient))
(var-set assets (- current-assets inkind))
``` [5](#0-4) 

Because `send-underlying` is invoked directly (not inside `as-contract?`), when `redeem` executes the inner `contract-call?`, `tx-sender`/`contract-caller` are still the original external redeemer, not `current-contract`. The external token's `transfer` function — like the vault's own `transfer` implementation shown below, which is the canonical enforcement pattern for SIP-010 tokens in this codebase — requires the sender argument to match the caller identity:
```
(asserts! (or (is-eq tx-sender from) (is-eq contract-caller from)) (err u4))
``` [6](#0-5) 

Passing `sender = current-contract` while `tx-sender = <redeemer>` fails this check (assuming the external sBTC/USDC/USDH token enforces the same standard SIP-010 sender-identity rule, which is standard for all Stacks fungible tokens since there is no allowance/approve mechanism in Clarity). The call reverts inside `try!`, and the entire `redeem` transaction aborts.

### Impact Explanation
This lands on the in-scope "permanent freezing of funds" Critical category: since `send-underlying` can never succeed for these three vaults, no user can ever redeem their zsBTC/zUSDC/zUSDH shares for the underlying asset. The underlying tokens deposited into these vaults are permanently locked with no path to withdrawal (there is no alternative redemption function that bypasses `send-underlying`), affecting the principal and yield of all depositors in these vaults, not a self-inflicted or two-party griefing scenario, and it is deterministic and reachable in a single transaction — every call to `redeem` on these vaults will revert.

### Likelihood Explanation
Likelihood is high/certain: this is not a race condition or edge case — it is the deterministic behavior of every single `redeem` call on the sBTC, USDC, and USDH vaults, since `send-underlying` is unconditionally reached and unconditionally fails identity validation on the external token.

### Recommendation
Wrap the external token `transfer` calls in `send-underlying` (and any other outbound transfer from vault balance) with `as-contract?`, matching the pattern already used correctly for `wSTX`, `ststx`, and `ststxbtc`:
```
(define-private (send-underlying (amount uint) (account principal))
  (begin
    (try! (as-contract? ((with-ft 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token "sbtc-token" amount))
      (try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token transfer amount tx-sender account none))
      true))
    (ok true)))
```
Apply the equivalent fix to `mainnet/contracts/vault/v0-vault-usdc.clar` and `mainnet/contracts/vault/v0-vault-usdh.clar`.

### Proof of Concept
1. A user deposits sBTC into `v0-vault-sbtc` via `deposit`, receiving zsBTC shares; `receive-underlying` succeeds because `sender = account = tx-sender` there (correct identity).
2. The user calls the public `redeem` function on `v0-vault-sbtc.clar` with `amount`, `min-out`, `recipient` set to themselves.
3. Inside `redeem`, `(try! (ft-burn? zft amount account))` succeeds, burning the user's zsBTC shares. [7](#0-6) 
4. `(try! (send-underlying inkind recipient))` is called, which executes `(contract-call? sbtc-token transfer amount current-contract account none)` with `tx-sender` still equal to the original external caller (the redeemer), not `current-contract`. [2](#0-1) 
5. The external `sbtc-token` contract's `transfer` enforces `sender == tx-sender` (standard SIP-010/Clarity FT behavior, no allowance mechanism exists); since `sender = current-contract != tx-sender`, the call fails and `try!` propagates the error, reverting the entire `redeem` transaction.
6. The user's zsBTC shares were already burned in step 3 within the same aborted transaction, so the revert rolls that back too — but because `redeem` can never complete for any caller, the sBTC held by the vault (and analogously USDC/USDH in their respective vaults) is permanently unreachable, causing all depositors' locked assets and any accrued yield in these vaults to be frozen forever.
