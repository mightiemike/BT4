### Title
Front-running race condition in `ExchangeTransactionContract`/`ExchangeWithdrawContract` processing allows an attacker to grief/DoS a victim's exchange trade or withdrawal by shifting AMM pool ratios before the victim's transaction executes - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's built-in bancor-style AMM exchange module (`ExchangeTransactionContract` / `ExchangeWithdrawContract`) computes swap/withdrawal outputs from the *current* `ExchangeCapsule` token balances at the moment a transaction is executed inside a block, not at the moment the user signed/broadcast it. Because transaction ordering within a block is controlled by whoever proposes/orders the block (and by relative gas-price/broadcast timing before that), an attacker who observes a pending `ExchangeTransactionContract` or `ExchangeWithdrawContract` in the mempool can submit their own exchange transaction with higher priority to shift the pool ratio just enough that the victim's transaction fails its balance/slippage checks and reverts — the same class of front-running/TOCTOU issue described in the external LendingPool report, where Bob's front-run redemption causes Alice's later redemption to revert.

### Finding Description
`ExchangeTransactionActuator.doValidate()` computes the expected output amount from the exchange's *current* balances via `exchangeCapsule.transaction(...)` and compares it against the caller-supplied `tokenExpected` slippage bound: [1](#0-0) 

The actual pool state (`firstTokenBalance`/`secondTokenBalance`) used for this computation is mutated in-place by `ExchangeCapsule.transaction()`: [2](#0-1) 

Because this state is shared and order-dependent, whichever transaction touching the same exchange ID executes first in a block determines the resulting ratio for every subsequent transaction that references the same exchange. An attacker who sees a victim's pending `ExchangeTransactionContract` (with a given `tokenExpected` slippage bound) can submit a transaction against the same exchange that shifts the ratio just enough that the victim's `anotherTokenQuant < tokenExpected` check fails, forcing a revert.

The `ExchangeWithdrawActuator` has an analogous, even weaker, protection: it only verifies that the current pool balances are sufficient and that the computed ratio is "precise enough" — there is no slippage/expected bound at all: [3](#0-2) 

An attacker can front-run a legitimate `ExchangeWithdrawContract` with their own `ExchangeTransactionContract` (trade) or `ExchangeWithdrawContract` against the same exchange, altering `firstTokenBalance`/`secondTokenBalance` so that when the victim's withdrawal actually executes, it hits `"exchange balance is not enough"` or `"Not precise enough"` and reverts, exactly mirroring the LendingPool `redeem()` race condition in the report, where Bob's front-run consumes shared liquidity/state that Alice's transaction depended on.

### Impact Explanation
A victim's `ExchangeTransactionContract` or `ExchangeWithdrawContract` can be repeatedly griefed/DoS'd by an attacker who front-runs trades against the same exchange ID, forcing reverts (`ContractValidateException`/`ContractExeException`) and wasting the victim's bandwidth/energy on failed transactions, similar to the informational-severity impact described in the original report (failed redemption, no direct fund loss, but denial of expected service and wasted fees).

### Likelihood Explanation
Any account can broadcast `ExchangeTransactionContract`/`ExchangeWithdrawContract` transactions referencing a known `exchangeId`, and pending transactions are visible before block inclusion, so an attacker only needs to react to a target's pending transaction on the same exchange with a higher-priority/earlier-ordered transaction. This requires no privileged access, matching an anonymous broadcast-transaction threat model.

### Recommendation
- For `ExchangeTransactionActuator`, this is already partially mitigated by the `tokenExpected` slippage parameter, but document that large expected-slippage tolerances make users more vulnerable to this griefing pattern, and consider recommending tighter bounds or commit-reveal/order-independent exchange design.
- For `ExchangeWithdrawActuator`, consider adding an equivalent minimum-expected-output/slippage parameter (similar to `tokenExpected` in `ExchangeTransactionContract`) so withdrawals can be bounded against unfavorable ratio shifts, and document the inherent front-running exposure of shared AMM pool state to users, similar to the recommendation in the original report.

### Proof of Concept
1. Attacker monitors the mempool for a pending `ExchangeWithdrawContract` (or `ExchangeTransactionContract`) referencing exchange `X` from victim Alice.
2. Attacker submits their own `ExchangeTransactionContract` against exchange `X` with a higher priority/earlier position, shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()`.
3. When Alice's transaction subsequently executes, `doValidate()` recomputes the ratio from the now-shifted balances; depending on the shift, either `"exchange balance is not enough"`, `"Not precise enough"` (withdraw), or `"token required must greater than expected"` (trade) is thrown, reverting Alice's transaction and wasting her fee, analogous to Bob front-running Alice's `redeem()` in the original LendingPool report.
