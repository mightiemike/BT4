## Finding: `ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify accept a corrupted/divergent state root

The external report's core lesson — a critical authorization/validation check being silently absent from a function whose whole purpose is to gate acceptance — has a direct Aptos-native analog in the transaction-output/replay-verification path, not in write-set conversion itself.

### Title
Replay-verify accepts transaction outputs with a divergent state-checkpoint root because `ensure_match_transaction_info` never checks it - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the gate used by all offline/replay-verify tooling to decide whether a freshly re-executed transaction output matches the transaction info recorded on-chain/in-backups. It checks status, gas, write-set hash, and event-root hash, but explicitly and admittedly does **not** check `state_checkpoint_hash` (or `position_state_checkpoint_hash`), the field that authenticates the resulting state/hot-state Merkle root for that transaction.

### Finding Description [1](#0-0) 

The function performs four checks — status, gas used, write-set hash vs `state_change_hash`, and event-root hash — then returns `Ok(())`. The code contains its own acknowledgement of the gap: [2](#0-1) 

This function is the sole verification primitive used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, invoked during backup restore/replay-verify (`VerifyExecutionMode::Verify`) — [3](#0-2) 
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the archive replay-verification tool — [4](#0-3) 
- `aptos-move/cli/src/commands.rs` transaction-replay comparison — [5](#0-4) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches` — [6](#0-5) 

By contrast, the in-band commit-time check `LedgerUpdateOutput::ensure_transaction_infos_match` compares the *entire* `TransactionInfo` struct (including its checkpoint-hash fields) by equality, so the normal consensus/state-sync commit path is not directly bypassed: [7](#0-6) 

However, the entire purpose of replay-verify/replay-on-archive tooling is to independently re-derive the state root from historical backups and confirm it matches what's committed — this is the analog of "authorizing" that a piece of data is the correct one before accepting it. Because `ensure_match_transaction_info` never re-derives or compares the state/hot-state checkpoint hash, a discrepancy that leaves write-set hash, event hash, gas, and status all matching (e.g. state introduced by a restore-path bug, a non-deterministic native/aggregator materialization bug, or corrupted/malicious backup data affecting only the persisted state-checkpoint hash bookkeeping) would go **undetected** by every one of these tools.

### Impact Explanation
Replay-verify and replay-on-archive are the primary tools operators and the Aptos Foundation use to certify that archived/backed-up ledger history is authentic and that execution is deterministic across versions. If a state-root-affecting bug (in `do_state_checkpoint`, restore utils, or hot-state materialization) diverges from the recorded checkpoint hash while leaving events/gas/status/write-set-hash intact, this verification gate would report success, hiding a genuine state-integrity break. This directly matches the "Proof And Storage Pivots" criterion that "replay paths ... must not reinterpret committed data into a different ledger state" and that authenticated outputs "must stay bound to the right ... root."

### Likelihood Explanation
This is not a hypothetical race — the code contains an explicit TODO acknowledging the exact gap and naming the exact tool (`replay_on_archive`) affected, and states the feature `COMPUTE_TRADING_NATIVE_STATE_ROOTS` must not be enabled until the check is added. This indicates the aptos-core team is already aware the checkpoint-hash comparison is planned to matter for correctness once that feature ships, i.e., the current state is a known-incomplete verification path.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s locally computed state/hot-state checkpoint hash (and `position_state_checkpoint_hash` where applicable) against `txn_info.state_checkpoint_hash()` (and the corresponding position-state field), consistent with how `LedgerUpdateOutput::ensure_transaction_infos_match` already performs a full-struct comparison. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the existing TODO comment already recommends.

### Proof of Concept
1. Run `replay-verify` or `db-tool replay-on-archive` against a backup/archive whose write set, events, gas, and status match the recorded `TransactionInfo`, but whose actual resulting state tree (post-checkpoint) differs from `txn_info.state_checkpoint_hash()` (e.g., simulate via a restore bug that applies write ops but computes/persists an incorrect state root, or through a deliberately corrupted backup that keeps write-set bytes/hash consistent while the DB's derived Merkle root differs).
2. Observe that `ensure_match_transaction_info` at [1](#0-0)  returns `Ok(())` because it never reads or compares `state_checkpoint_hash`.
3. `verify_execution` in `execution/executor/src/chunk_executor/mod.rs` and `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` therefore report the chunk as verified/matching despite the true state divergence.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
```

```rust
    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
    }
```
