### Title
Webhook `X-Shopify-Shop-Domain` header is unauthenticated and forwarded to handlers unchecked, enabling cross-tenant shop-domain spoofing - ([File: packages/apps/shopify-api/lib/webhooks/process.ts])

### Summary
`callWebhookHandlers` passes `webhookCheck.domain` directly into `handler.callback` as the `shop_domain` argument, but this value originates from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the webhook HMAC computation. An attacker who can obtain any single HMAC-valid webhook payload for their own shop can replay it with a forged `X-Shopify-Shop-Domain` header value, and the library will accept it as fully "valid" and pass the forged domain to the app's handler.

### Finding Description
In `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts`), the HMAC is computed and compared only over `rawBody`: [1](#0-0) . No request header, including `X-Shopify-Shop-Domain`, is part of the signed material.

Separately, `checkWebhooksHeaders` in `packages/apps/shopify-api/lib/webhooks/validate.ts` reads the `domain` straight from the (unauthenticated) header and includes it in the `WebhookValidationValid` result without any cross-check: [2](#0-1) .

`process()` then treats `webhookCheck.valid === true` as fully trustworthy and calls `callWebhookHandlers`, which forwards `webhookCheck.domain` verbatim as the `shop_domain` parameter to the app-supplied handler callback: [3](#0-2) .

Because the domain header is not cryptographically bound to the HMAC-signed body, an attacker who legitimately controls one shop (and therefore legitimately receives at least one valid webhook, i.e., a valid `rawBody` + matching `X-Shopify-Hmac-Sha256`) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` value naming a victim shop. `validateHmacFromRequest` only checks `rawBody` against the HMAC and returns valid regardless of the domain header, so `checkWebhooksHeaders` then packages the forged domain into a `valid: true` result, and `process()` calls the app's handler with the forged `shop_domain`.

### Impact Explanation
If an app's webhook handler uses the `shop_domain` argument to key session-storage reads/writes (a common and Shopify-documented integration pattern, since this is literally the field's purpose), a forged domain lets an attacker trigger session-storage side effects scoped to a shop they don't own — corrupting or overwriting another merchant's stored session/access-token record. This maps to Shopify's cross-tenant data/state access impact class.

### Likelihood Explanation
The attacker needs no privileged role: any merchant who has installed the target app on their own store will receive legitimate webhooks with valid HMACs for their own shop, and can freely replay that request with a different `X-Shopify-Shop-Domain` header value (headers are attacker-controlled on any HTTP client, curl, etc.). The only precondition is that the receiving app's handler trusts `shop_domain` for storage keying, which is exactly the parameter's intended use, making this a broadly repeatable condition across apps built on this library.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` (or `topic`, `api-version`, etc.) as authenticated just because the body HMAC is valid. Either include the relevant headers in the HMAC-signed payload construction, or require callers to cross-reference `webhookCheck.domain` against the shop associated with the `webhookId` (e.g., via a registry/session lookup) before invoking handler callbacks, and document clearly that `domain` is unauthenticated header data that must not be used directly to key session storage without an additional authorization check.

### Proof of Concept
```ts
// Pseudocode illustrating the replay:
// 1. Attacker owns shop "attacker.myshopify.com" and installs the app,
//    triggering a legitimate webhook: rawBody=B, X-Shopify-Hmac-Sha256=H (valid for B).
// 2. Attacker resends the identical request to the app's webhook endpoint,
//    but sets header X-Shopify-Shop-Domain: victim.myshopify.com
//    (keeping rawBody=B and X-Shopify-Hmac-Sha256=H unchanged).

// packages/apps/shopify-api/lib/utils/hmac-validator.ts:189-197
// validHmac = HMAC-SHA256(apiSecretKey, B) === H  -> still true, domain not included.

// packages/apps/shopify-api/lib/webhooks/process.ts:148-156
// handler.callback(topic, "victim.myshopify.com", B, webhookId, apiVersion, context)
// -> app's handler writes/overwrites session storage keyed by "victim.myshopify.com".
```
A Jest test would register a fake handler doing `sessionStorage.storeSession(shop_domain, ...)`, call `process()` with a valid HMAC over a fixed body but an arbitrary `X-Shopify-Shop-Domain` header, and assert that `storeSession` was invoked with the forged (non-owning) shop domain.
