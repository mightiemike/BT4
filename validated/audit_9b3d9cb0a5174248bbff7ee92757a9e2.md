### Title
Race condition in shop-to-session-ID index due to non-atomic read-modify-write ("set") pattern - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage` and `RedisSessionStorage` maintain a per-shop index of session IDs (used by `findSessionsByShop`) by reading the current list, mutating it in memory, and then overwriting ("setting") the whole list back to storage. This is the same anti-pattern as the `change_gauge_weight` finding: a shared, incrementally-modified value is updated via a full "read current value, compute new value, `set`" cycle rather than an atomic increment/decrement. Concurrent, unprivileged operations (e.g. two OAuth flows / online-session creations for the same shop happening close together) can interleave and cause a lost update, corrupting the index.

### Finding Description

Both `addShopIds`/`removeShopIds` (KV) and `addKeyToShopList`/`removeKeyFromShopList` (Redis) follow the pattern: `GET key -> mutate array in JS -> PUT/SET key`. This is invoked from `storeSession` and `deleteSession`, both of which are triggered by unprivileged, externally-reachable flows — `storeSession` is called at the end of the OAuth callback (`packages/apps/shopify-api/lib/auth/oauth/oauth.ts`, `callback()`), and `deleteSession` can be triggered by session invalidation/logout logic. There is no locking, optimistic concurrency check (e.g. compare-and-swap/ETag), or atomic list primitive (e.g. Redis `SADD`/`SREM`) used — the entire list is blindly overwritten with whatever was computed from the last read.

If two `storeSession`/`deleteSession` calls for the same shop race (e.g. a merchant opens the app in two tabs, triggering two concurrent OAuth/online-session flows, or a store/delete race during token refresh), the second `PUT`/`SET` silently clobbers the first writer's update:
- Two concurrent `addShopIds` calls can both read the same base list and each `PUT` a list containing only their own new ID, so one of the two valid session IDs is lost from the shop index.
- A `deleteSession` racing with a `storeSession` can cause the deleted ID to be re-written back into the index after removal (because the store's read happened before the delete's write), reintroducing an ID whose underlying session record has already been deleted from the K/V store.

### Impact Explanation
This directly parallels the "set instead of increment/decrement" root cause from the report: shared aggregate state (the shop's session-ID list) is updated non-atomically and can end up in an incorrect state due to ordinary concurrent, unprivileged usage. In `findSessionsByShop`, a stale ID pointing to an already-deleted session causes `loadSession(id)` to return `undefined`, which is force-cast with a non-null assertion (`(await this.loadSession(id))!`) in the KV implementation: [3](#0-2) 
Any app code that iterates the result of `findSessionsByShop` and dereferences session properties (e.g., for billing checks, multi-session cleanup, or webhook/uninstall handling) can throw on the `undefined` entry, causing request failures — a denial-of-service condition in session-storage-backed authentication/session-management logic. Additionally, losing a legitimately stored session ID from the shop index means that operations relying on `findSessionsByShop` (e.g., revoking all sessions for a shop on uninstall/GDPR erasure) can silently miss a still-active session, leaving stale access tokens undetected.

### Likelihood Explanation
Likelihood is low-to-medium: it requires two writes for the same shop's session index to race, which is realistic under normal concurrent usage (multiple staff accounts creating online sessions for the same shop nearly simultaneously, or rapid session refresh/delete cycles) without any need for privileged access, secret leakage, or MITM. No special timing precision is required beyond ordinary request concurrency.

### Recommendation
Replace the read-then-overwrite pattern with an atomic primitive:
- For Redis, use native set operations (`SADD`/`SREM`) on a Redis Set instead of storing a JSON array and rewriting it wholesale.
- For the KV adapter, use optimistic concurrency (conditional `PUT` with a version/ETag check and retry) or move to a data model where each shop/session-id pair is its own key (e.g. `shop:{shop}:{sessionId}`) so add/remove operations don't require read-modify-write of a shared blob.
- Ensure `findSessionsByShop` tolerates/filters out `undefined` results instead of using a non-null assertion.

### Proof of Concept
1. Configure an app to use `KVSessionStorage` (or `RedisSessionStorage`).
2. Trigger two concurrent OAuth completions (or two concurrent `storeSession` calls) for the same shop with different session IDs `A` and `B`, such that both read the shop's current empty session-ID list before either writes back.
3. Observe that the final stored list contains only one of `A`/`B` instead of both — the other session, though present in the primary session store, is now unreachable via `findSessionsByShop`.
4. Alternatively, race a `deleteSession(A)` with a concurrent `storeSession` for a different session `B` of the same shop, and observe that `A` can reappear in the shop's index after being deleted, causing `findSessionsByShop` to later return `undefined` in place of a valid `Session` object.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async removeShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(
      key,
      JSON.stringify(shopIds.filter((id) => !ids.includes(id))),
    );
  }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }

  private async removeKeyFromShopList(shop: string, id: string) {
    const shopKey = shop;
    const idKey = this.client.generateFullKey(id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);
      const index = idKeysArray.indexOf(idKey);

      if (index > -1) {
        idKeysArray.splice(index, 1);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    }
  }
