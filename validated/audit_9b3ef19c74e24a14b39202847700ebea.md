### Title
Spot-price bonding-curve manipulation in TRC10 `Exchange` (Bancor-relay) actuators enables sandwich/whale attacks - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The TRC10 `Exchange` bonding-curve pools (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) price every trade purely from the pool's current on-chain reserve balances at the moment the transaction executes, with no time-weighted average and no protection against reserves being manipulated by a large trade/inject/withdraw immediately before another user's trade in the same block. This mirrors the FlanBackstop finding: a single-point spot price derived from manipulable LP reserves is used to compute the amount a counterparty receives.

### Finding Description
`ExchangeCapsule.transaction()` computes the counter-token amount using the pool's live `firstTokenBalance`/`secondTokenBalance` fields and a Bancor-relay formula (`ExchangeProcessor`/`SafeExchangeProcessor`), with no historical or averaged price reference: [1](#0-0) 

The pricing function itself is a pure function of the two instantaneous reserve balances passed in: [2](#0-1) 

`ExchangeTransactionActuator.doValidate()` only rejects a trade if the *trader's own* `expected` minimum-output slippage guard is violated — it performs no check on how far the pool price has moved from any recent baseline, and no restriction preventing multiple trades against the same pool within one block: [3](#0-2) 

`ExchangeInjectActuator`/`ExchangeWithdrawActuator` similarly allow anyone controlling the exchange owner account (or, for inject, any funded holder per the exchange's design) to instantly rebalance reserves based only on current balances, with no cooldown or TWAP-based limit: [4](#0-3) 

Because java-tron blocks execute transactions sequentially in producer-controlled order, an attacker (or a colluding/bribed super representative producing the block) can place a large `ExchangeTransactionContract` (or `ExchangeInjectContract`) immediately before a victim's trade to skew the reserve ratio, let the victim's trade execute against the skewed price (the victim's own `expected` field only bounds their own worst case, not the fair market price), and then immediately reverse the position afterward to capture the spread — a classic sandwich attack against the bonding curve, requiring no true "flash loan" primitive since java-tron transactions execute atomically and sequentially without requiring cross-contract borrow/repay.

### Impact Explanation
This allows extraction of value from ordinary TRC10 `Exchange` users (asset/accounting corruption) via price manipulation, analogous to the FlanBackstop pyroflan mispricing issue. Because the same reserve-based single-point price also drives `ExchangeInject`/`ExchangeWithdraw` proportional-quantity calculations, a manipulated reserve ratio can also distort withdrawal/injection accounting for other participants of the same pool.

### Likelihood Explanation
Likelihood is bounded by the fact that `Exchange` pools are a legacy/optional TRC10 feature (superseded in practice by the `MarketSellAssetContract` order-book), and successful sandwiching requires either controlling transaction ordering within a block (a super representative or one paying/bribing for favorable ordering) or racing a victim's pending broadcast transaction, similar in spirit to the acknowledged Behodler risk. It does not require a privileged role or key compromise, only capital and the ability to interleave broadcast transactions around a victim's trade, so it is reachable from anonymous, unprivileged accounts.

### Recommendation
Introduce a TWAP-based or delayed price reference for `ExchangeTransactionContract` pricing (e.g., accumulate a cumulative price similar to Uniswap V2 oracles), impose a minimum elapsed-block/time cooldown between successive trades or inject/withdraw operations against the same exchange pool, and/or cap the maximum single-trade price impact allowed per pool per block, in addition to the existing trader-supplied `expected` slippage bound.

### Proof of Concept
1. Attacker observes a pending victim `ExchangeTransactionContract` (selling token A for token B) targeting exchange pool `id`.
2. Attacker submits their own `ExchangeTransactionContract` selling a large amount of token B for token A first in the same block, sharply raising the effective price of A/lowering B reserves relative to A, per `ExchangeCapsule.transaction()`'s pure reserve-ratio math (`chainbase/.../ExchangeCapsule.java:124-158`, `ExchangeProcessor.java:41-45`).
3. Victim's trade executes next against the now-skewed reserves; the victim still receives ≥ their self-specified `expected` (`ExchangeTransactionActuator.java:217-221`), but at a worse rate than the pre-manipulation fair price.
4. Attacker submits a reverse `ExchangeTransactionContract` (or `ExchangeWithdrawContract`) immediately after to restore/exit the position, capturing the spread extracted from the victim, with no on-chain check preventing this sequence.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
