### Title
Global-state consensus threshold uses floor rounding while block-signing threshold uses ceiling rounding, causing signer-set agreement to diverge from the actual block-approval threshold - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
The Nakamoto signer protocol computes the "70% approval threshold" in two different places using two different rounding rules on the same constant `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD`. `NakamotoBlockHeader::compute_voting_weight_threshold` (used to actually validate a block's signatures) rounds **up** (ceiling), whereas `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` (used by the signer set to decide on miner state, burn view, protocol version, and tx-replay-set agreement) rounds **down** (floor, via plain integer division). For total signer weights where `total_weight * 7` is not a multiple of 10, these two thresholds differ by one weight unit, so a coalition whose combined weight sits exactly in that gap can satisfy the "global agreement" threshold used by the signer network's state machine while not satisfying (or vice versa) the real block-approval threshold enforced on-chain.

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` (the authoritative check used when validating that a Nakamoto block has enough signer weight) computes: [1](#0-0) 

```
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
u32::try_from((total_weight * threshold) / 10 + ceil)
```
i.e. `ceil(total_weight * 7 / 10)`.

By contrast, `GlobalStateEvaluator::reached_agreement` and `reached_disagreement`, used by the signer-side global state machine (`GlobalStateEvaluator::determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, `determine_global_state`, and `find_majority_prefix_replay_set`) to decide whether the signer set has reached agreement on the active protocol version, the current burn view, the current miner state, and the transaction-replay set, compute: [2](#0-1) 

```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```
i.e. `vote_weight >= floor(total_weight * 7 / 10)` — no ceiling adjustment.

For any `total_weight` such that `total_weight * 7` is not evenly divisible by 10 (which is the overwhelming majority of possible weight totals), `floor(total_weight*7/10)` is exactly one less than `ceil(total_weight*7/10)`. Example: `total_weight = 12` → `12*7/10 = 8.4` → block-approval threshold (`compute_voting_weight_threshold`) = `9` (ceiling), but `reached_agreement` treats a vote weight of `8` as already having "reached agreement" (`8 >= floor(8.4) = 8`), one unit below the real approval threshold.

This is precisely the report's rounding-error pattern (interest calc rounding to 0 lets a minority avoid a required payment) transplanted onto Stacks' weight-threshold arithmetic: two code paths meant to implement the *same* "70% weight" rule use different rounding directions, and the discrepancy is deterministic and triggerable by any subset of signers whose combined weight lands exactly at the boundary — no majority collusion is required, just weight distribution that happens to fall in the 1-unit gap, which is a routine, unprivileged occurrence for any reward-cycle stacker distribution.

### Impact Explanation
The global state machine drives what the signer set believes is the current miner, the current burn view, the active protocol version, and the transaction-replay set — decisions that gate whether a signer will sign/accept a block or a miner tenure. Because `reached_agreement` is systematically looser (by up to one weight unit) than the real, consensus-relevant `compute_voting_weight_threshold` used when a block's signature set is actually verified (`NakamotoBlockHeader::verify_signer_signatures`), a subset of signers just below the true 70% approval threshold can be treated by the signer network's global-state logic as having reached "global agreement" on a burn view, miner state, or protocol version that a minority-weighted set does not actually have authority to finalize. This can cause different signers (or a signer vs. the chainstate validator) to disagree about which miner/tenure/state is canonical, producing tip disagreement among signers and inconsistent miner selection — a High-severity, minority-triggerable divergence in the signer set's collective state versus the protocol's actual approval rule, bounded to temporary tip/miner-selection disagreement rather than fund loss.

### Likelihood Explanation
This requires no majority collusion and no privileged access: it is simply a consequence of ordinary reward-cycle weight distributions where `total_weight * 7 mod 10 != 0`, which is true for nearly all possible total weights (9 out of 10 residues). Any signer set whose aggregate weight for a given view happens to land in the resulting one-unit gap will trigger the divergence between "signer-network-perceived agreement" and "actual block-approval threshold" purely through normal PoX stacking weight allocation — no attacker action beyond being present in the reward set is needed.

### Recommendation
Unify the threshold computation into a single shared function (e.g. have `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` call `NakamotoBlockHeader::compute_voting_weight_threshold`, or vice versa extract a common `stacks_common` helper) so both the signer-side global state machine and the chainstate block-approval verifier apply identical ceiling-rounded threshold semantics for the same `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` constant.

### Proof of Concept
1. Configure a reward cycle where the aggregate signer weight is `total_weight = 12` (achievable via any PoX-5/`pox_5_make_signer_set` weight apportionment that yields this total — see [3](#0-2) ).
2. The true block-approval threshold from `NakamotoBlockHeader::compute_voting_weight_threshold(12)` is `ceil(12*7/10) = ceil(8.4) = 9` (see [4](#0-3) ).
3. A coalition of signers with combined weight `8` (< 9, i.e. below the real approval threshold) submits matching `StateMachineUpdate`s for e.g. the current burn view.
4. `GlobalStateEvaluator::determine_global_burn_view` accumulates weight `8` and calls `self.reached_agreement(8)`, which evaluates `8 >= floor(12*7/10) = 8` → `true` (see [5](#0-4)  and start="169" end="175" />).
5. The signer network's global state machine now treats this sub-quorum (weight 8/12, below the real 9/12 threshold) as having established global agreement on the burn view/miner state, even though the same weight would be insufficient to actually approve a Nakamoto block per `verify_signer_signatures`, producing a divergence between the signer set's perceived global state and the chain's real approval rule.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    pub(crate) fn pox_5_make_signer_set<I>(
        entries: &mut I,
        pox_constants: &PoxConstants,
    ) -> Result<Pox5SignerSetOutput, ChainstateError>
    where
        I: Iterator<Item = Result<RawPox5Entry, PoxEntryParsingError>>,
    {
        let mut signer_set = HashMap::new();
        let mut total_ustx_locked = 0u128;
        for entry_res in entries {
            let entry = match entry_res {
                Ok(x) => x,
                Err(PoxEntryParsingError::Skip(err_str)) => {
                    warn!(
                        "Error while iterating PoX-5 entries, impacting a single entry. Dropping entry from signer set";
                        "error" => err_str
                    );
                    continue;
                }
                Err(PoxEntryParsingError::Abort(err_str)) => {
                    error!(
                        "Abort-triggering error while iterating PoX-5 entries";
                        "error" => err_str
                    );
                    return Err(ChainstateError::PoxNoRewardCycle);
                }
            };

            total_ustx_locked += entry.amount_ustx;

            signer_set
                .entry(entry.signer_key)
                .and_modify(|existing_entry| *existing_entry += entry.amount_ustx)
                .or_insert_with(|| entry.amount_ustx);
        }

        // Allocate `reward_slots` weight across signers in proportion to stake using the
        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();
