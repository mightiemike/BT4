## Analysis

This maps cleanly onto the Uniswap "stale hardcoded hash" bug class. In `zeroswap`, `UniswapV2Library.pairFor()` hardcodes an init-code-hash constant that must exactly match the actual bytecode hash of `UniswapV2Pair`; when the pair contract code changed, the hardcoded hash went stale and every dependent contract (`Router`, `Oracle`, `SushiRoll`) resolved to a non-existent address, bricking all swaps.

The nearcore analog is `eth_wallet_global_contract_hash()` in [1](#0-0) , which hardcodes literal `CryptoHash` byte arrays for `MAINNET`/`TESTNET` that must exactly match the real hash of the compiled wallet-contract WASM blobs (`res/wallet_contract_mainnet.wasm`, `res/wallet_contract_testnet.wasm`) embedded via `include_bytes!` at [2](#0-1) .

This value is used directly (not re-derived from the actual WASM) in two runtime-critical places reachable from an ordinary `Transfer` transaction or a `FunctionCall`:

1. `action_implicit_account_creation_transfer` sets `AccountContract::Global(global_contract_hash)` on every freshly created ETH-implicit account using this constant: [3](#0-2) .
2. `RuntimeContractIdentifier::resolve` uses the same constant to resolve which global contract code to execute for legacy ETH-implicit accounts: [4](#0-3) .

Contract execution then looks up the global contract by that exact hash in the trie via `GlobalContractAccessExt::hash`/`code`, and fails with `StorageInconsistentState`/no-code-found if nothing in the trie matches that hash: [5](#0-4) .

### Title
Hardcoded ETH-implicit wallet global-contract hash can desynchronize from the actually-deployed contract, bricking all ETH-implicit accounts - (File: runtime/near-wallet-contract/src/lib.rs)

### Summary
`eth_wallet_global_contract_hash()` returns literal, hand-maintained `CryptoHash` constants for mainnet/testnet instead of deriving the hash from the embedded WASM at build time. Every ETH-implicit account created while `EthImplicitGlobalContract` is active is permanently bound to this constant via `AccountContract::Global(hash)`. If the constant and the actually-deployed global contract (the real object the chain resolves by that hash in the trie) ever diverge — exactly the class of bug reported for Uniswap's hardcoded init-code-hash — every such account's contract resolution breaks.

### Finding Description
`action_implicit_account_creation_transfer` derives the account's contract purely from the hardcoded constant, not from any value tied to what is actually deployed on-chain as the global contract: [3](#0-2) . The same constant is reused for legacy-account resolution: [6](#0-5) . At call time, `GlobalContractAccessExt::hash`/`code` look up `TrieKey::GlobalContractCode { identifier: CodeHash(hash) }` and return `StorageInconsistentState`/`None` if no code with exactly that hash exists in the trie: [5](#0-4) . There is no on-chain cross-check that the hardcoded constant equals the hash of whatever code is actually deployed globally on that chain; correctness depends entirely on manual synchronization between the constant in `lib.rs` and the deployment/build process for the real global wallet contract, the same failure mode as the reported Uniswap bug (hardcoded derived value vs. actual bytecode).

### Impact Explanation
Any account whose ID happens to be (or is chosen to be, since anyone can generate a Secp256K1 keypair) an ETH-implicit address is created by a single `Transfer` from an unprivileged sender: [7](#0-6) . If the hardcoded hash is stale relative to the deployed global contract, the account is created with `AccountContract::Global(stale_hash)` and its `rlp_execute` wallet logic can never be resolved/executed — the account can receive funds but never authorize a `Transfer`, `FunctionCall`, or `DeleteAccount` out of it, since ETH-implicit accounts have no access key and rely solely on the wallet contract for authorization (per NEP-518, described at [8](#0-7) ). This permanently freezes any balance sent to such accounts network-wide, and is a transaction-triggered invalid/inconsistent state condition (`StorageInconsistentState`) reachable purely by an RPC caller sending money to an implicit address.

### Likelihood Explanation
The constant is currently only exercised via unit tests pinning specific expected values (`test_eth_wallet_global_contract_hash_values`) rather than being derived from, or checked against, the deployed global contract's real hash: [9](#0-8) . Any future update to the wallet-contract WASM (a bugfix, a protocol upgrade) that is not accompanied by an exactly-matching manual update of this constant reproduces the Uniswap bug class exactly — the mismatch is undetectable at compile time and silent until an account actually needs to execute its wallet logic.

### Recommendation
Derive `eth_wallet_global_contract_hash()` from the actual embedded/deployed contract object rather than literal byte constants (e.g., compute it from the same `WalletContract`/`ContractCode` instance that is registered as the global contract on each chain, analogous to how `magic_bytes()` already derives its hash from `read_contract().hash()`), and add a build-time or startup assertion that the constant matches the hash of the bytes that are actually deployed as the global contract on each chain.

### Proof of Concept
1. Ship a protocol/binary update that changes the WASM in `res/wallet_contract_mainnet.wasm` (e.g. a genuine bugfix) and deploy the corresponding new global contract on-chain, but forget to update the literal byte array in `eth_wallet_global_contract_hash()` for `MAINNET`.
2. An unprivileged user sends a `Transfer` to a fresh ETH-implicit account ID (`0x...`, derived from a Secp256K1 keypair the attacker/user controls) — this is a normal, permissionless action per `action_implicit_account_creation_transfer` [3](#0-2) .
3. The new account gets `AccountContract::Global(old_stale_hash)`. Any subsequent `rlp_execute` call, or the runtime's own `RuntimeContractIdentifier::resolve`/`GlobalContractAccessExt::hash` lookup for that hash [5](#0-4) , fails to find matching code in the trie (the trie now only has the new contract's hash), so the account can never execute its wallet logic — the deposited funds are permanently unreachable, and the account is effectively bricked network-wide until a further protocol fix.

    pub(crate) fn resolve(
        account_id: &AccountId,
        account_contract: AccountContract,
        state_update: &TrieUpdate,
        chain_id: &str,
        access: AccessOptions,
    ) -> Result<Self, StorageError> {
        let local_hash = match GlobalContractIdentifier::try_from(account_contract) {
            Ok(gci) => {
                let code_hash = gci.clone().hash(state_update, access)?;
                return Ok(RuntimeContractIdentifier::Global { code_hash, identifier: gci });
            }
            Err(ContractIsLocalError::NotDeployed) => return Ok(RuntimeContractIdentifier::None),
            Err(ContractIsLocalError::Deployed(local_hash)) => local_hash,
        };

        if account_id.get_account_type() == AccountType::EthImplicitAccount {
            // Accounts that look like eth implicit accounts and have existed prior to the
            // eth-implicit accounts protocol change (these accounts are discussed in the
            // description of #11606) may have something else deployed to them. Only return
            // something here if the accounts have a wallet contract hash. Otherwise use the
            // regular path to grab the deployed contract.
            if LegacyEthWallet::resolve(local_hash).is_some() {
                // ETH implicit wallet accounts use global contracts, including
                // those created in old protocol versions.
                let global_hash = eth_wallet_global_contract_hash(chain_id);
                return Ok(RuntimeContractIdentifier::Global {
                    code_hash: global_hash,
                    identifier: GlobalContractIdentifier::CodeHash(global_hash),
                });
            }
        }

        Ok(RuntimeContractIdentifier::AccountLocal {
            code_hash: local_hash,
            account_id: account_id.clone(),
        })
    }

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }

    fn code(self, store: &TrieUpdate) -> Result<Option<ContractCode>, StorageError> {
        let key = TrieKey::GlobalContractCode { identifier: self.clone().into() };
        let code_hash = match self {
            GlobalContractIdentifier::AccountId(_) => None,
            GlobalContractIdentifier::CodeHash(hash) => Some(hash),
        };
        let code = store.get(&key, AccessOptions::DEFAULT)?;
        Ok(code.map(|code| ContractCode::new(code, code_hash)))
    }

### Implicit account creation

An account with a NEAR-implicit or ETH-implicit account ID can only be created by sending a transaction/receipt with a single `Transfer` action to the implicit account ID receiver ([deterministic accounts](#deterministic-account-creation) have their own rules):

- The account will be created with the account ID.
- The account balance will have a transfer balance deposited to it.
- If this is NEAR-implicit account, it will have a new full access key with the ED25519-curve public key of `decode_hex(account_id)` and nonce `(block_height - 1) * MULTIPLIER` (to address an issues discussed [here](https://gov.near.org/t/issue-with-access-key-nonce/749)).
- If this is ETH-implicit account, it will have the [Wallet Contract](#wallet-contract) deployed, which can only be used by the owner of the Secp256K1 private key where `'0x' + keccak256(public_key)[12:32].hex()` matches the account ID.

Implicit account can not be created using `CreateAccount` action to avoid being able to hijack the account without having the corresponding private key.

Once a NEAR-implicit account is created it acts as a regular account until it's deleted.

An ETH-implicit account can only be used by calling the methods of the [Wallet Contract](#wallet-contract). It cannot be deleted, nor can a full access key be added.
The primary purpose of ETH-implicit accounts is to enable seamless integration of existing Ethereum tools (such as wallets) with the NEAR blockchain.

### Wallet Contract

The Wallet Contract (see [NEP-518](https://github.com/near/NEPs/issues/518) for more details) functions as a user account and is designed to receive, validate, and execute Ethereum-compatible transactions on the NEAR blockchain.

Without going into details, an Ethereum-compatible wallet user sends a transaction to an RPC endpoint, which wraps it and passes it to the Wallet Contract (on the target account) as an `rlp_execute(target: AccountId, tx_bytes_b64: Vec<u8>)` contract call.
Then, the contract parses `tx_bytes_b64` and verifies it is signed with the private key matching the target [ETH-implicit account ID](#eth-implicit-account-id) on which the contract is hosted.

Under the hood, the transaction encodes a NEAR-native action. Currently supported actions are:

- Transfer (from ETH-implicit account).
- Function call (call another contract).
- Add `AccessKey` with `FunctionCallPermission`. This allows adding a relayer's public key to an ETH-implicit account, enabling the relayer to pay the gas fee for transactions from this account. Still, each transaction has to be signed by the owner of the account (corresponding Secp256K1 private key).
- Delete `AccessKey`.
