### Title
Duplicate outbound entries sharing the same `Id` are appended to `UniversalTx.OutboundTx` without a de-duplication check, causing first-match vote/update logic to permanently shadow the real outbound - (File: `x/uexecutor/keeper/create_outbound.go`, `x/uexecutor/keeper/msg_vote_outbound.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
`BuildOutboundsFromReceipt` and `attachOutboundsToUtx` build and append `OutboundTx` entries to a `UniversalTx.OutboundTx` array keyed by `outbound.Id` (derived from the Gateway-emitted `event.TxID`) with no check that an outbound with the same `Id` doesn't already exist in the array. All downstream processing — `VoteOutbound`'s lookup loop and `UpdateOutbound` — locate an outbound by scanning `utx.OutboundTx` and stopping at the **first** matching `Id`. This is structurally identical to the NestedRecords bug: if two entries with the same `Id` end up in the array, the first occurrence is always the one voted on / updated, and any later occurrence with the "real" data is unreachable.

### Finding Description
`BuildOutboundsFromReceipt` sets `outbound.Id = strings.TrimPrefix(event.TxID, "0x")` for every matching `UniversalTxOutbound` log emitted by `UNIVERSAL_GATEWAY_PC` in a receipt [1](#0-0) , and simply appends every decoded outbound to the returned slice without checking whether an `Id` was already produced earlier in the same receipt [2](#0-1) .

`attachOutboundsToUtx` then appends each of these outbounds directly onto `utx.OutboundTx` with no existence/duplicate check against outbounds already recorded on the UTX: [3](#0-2) 

Downstream, `VoteOutbound` resolves an outbound purely by scanning for the first `Id` match and breaking immediately: [4](#0-3) 

`UpdateOutbound` (used to persist the OBSERVED/finalized state back into the UTX) has the exact same first-match-wins semantics: [5](#0-4) 

This mirrors the NestedRecords pattern precisely: a parameter (`outbound.Id`) is pushed into an array without checking whether it already exists, and if a first occurrence exists (potentially a stale/incorrect entry), all subsequent processing (voting, status update, finalization) targets only that first occurrence — the true, later entry becomes permanently unreachable by the vote/finalize machinery even though it remains in state.

### Impact Explanation
If two `OutboundTx` entries with the same `Id` end up appended to the same `UniversalTx.OutboundTx` list, the first entry perpetually absorbs all universal-validator votes and status transitions. The second (real) entry stays `PENDING` forever: it can never receive its own quorum of votes (votes always resolve to entry #1), it is never marked `OBSERVED`, and `FinalizeOutbound`/refund logic never runs for it. This is a permanent freeze of the destination-chain outbound processing for that entry, and because `PendingOutbounds` is keyed by `Id` (not array index), the pending index also silently only tracks one physical entry, compounding the divergence between the pending-outbound index and the UTX's own outbound list.

### Likelihood Explanation
The reachability of this issue as an *unprivileged, attacker-triggerable* condition hinges entirely on whether `event.TxID` (the source of `outbound.Id`) can be made to repeat across two distinct `UniversalTxOutbound` events processed for the same UTX through ordinary, honest-validator execution paths (e.g., a single payload execution triggering the Gateway's withdraw logic twice with an attacker-influenced/reused `txId` argument, or two separate inbound-triggered executions that resolve to the same UTX key and both independently emit outbound events). I was unable to inspect the `UniversalGatewayPC` Solidity contract source (not indexed/available via the tools in this session) to confirm whether `TxID` is generated deterministically and uniquely by the contract per withdrawal, or whether it can be influenced/repeated by a caller-supplied argument through `executeUniversalTx`/`DerivedEVMCall`. Because this precondition could not be verified, likelihood is **uncertain** — the array-append code itself unconditionally lacks a duplicate-`Id` guard (a real, confirmed gap), but whether an unprivileged actor can actually cause a duplicate `Id` to be emitted requires reviewing the Gateway contract logic, which was not available in the indexed codebase.

### Recommendation
- In `attachOutboundsToUtx` (and/or `BuildOutboundsFromReceipt`), reject or dedupe any incoming outbound whose `Id` already exists in `utx.OutboundTx`, returning an explicit error rather than silently appending a colliding entry.
- Change `VoteOutbound` and `UpdateOutbound` to fail loudly (return an error) if more than one entry with the same `Id` is found in `utx.OutboundTx`, instead of silently matching only the first.
- Confirm in the Solidity Gateway contract that `TxID` used in the `UniversalTxOutbound` event is generated internally (e.g., via an incrementing nonce or hash of immutable transaction context) and can never be influenced or replayed by caller-supplied payload data.

### Proof of Concept
Not fully reproducible from the indexed code alone: a concrete PoC requires confirming that the `UniversalGatewayPC` Solidity contract's withdraw path allows an attacker (via `UniversalPayload.Data` executed through `CallExecuteUniversalTx`) to trigger two `UniversalTxOutbound` events carrying the same `TxID` for a single UTX. Given that precondition, the sequence is:
1. Attacker's inbound payload causes the Gateway to emit `UniversalTxOutbound` event A with `TxID = X` and an attacker-favorable amount (e.g., 0 or self-directed).
2. In the same or a later execution attributed to the same UTX, the Gateway emits event B, again with `TxID = X` but with the legitimate withdrawal amount/recipient.
3. `BuildOutboundsFromReceipt`/`attachOutboundsToUtx` append both as separate `OutboundTx` entries sharing `Id = X` with no duplicate check [6](#0-5) .
4. Universal validators call `VoteOutbound(utxId, "X", ...)`; the lookup loop only ever finds/updates entry A [4](#0-3) , so entry B (the real withdrawal) never finalizes and its funds/outbound action are permanently stuck `PENDING`.

	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {

				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
