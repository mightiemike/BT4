### Title
Signer weight can be counted in both `total_weight_approved` and `total_weight_rejected`, breaking the invariant that a signer's weight is exclusive to one side - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run` tracks per-block signer votes in a `BlockStatus` struct with two independent tallies, `total_weight_approved` and `total_weight_rejected`, each intended to be incremented exactly once per distinct signer weight. The guard used to prevent double-crediting is asymmetric between the two code paths, so a signer that sends a `Rejected` message followed by an `Accepted` message (or vice versa is possible depending on ordering) for the same block has its weight added to *both* tallies. This is structurally the same bug class as the `FiveFiftyRule.numCatalyst` issue: an increment that can legitimately happen more than once per underlying identity is not matched by a symmetric, identity-aware guard on the other side of the ledger.

### Finding Description
`BlockStatus` maintains: [1](#0-0) 

In the `Accepted` branch, the weight is only added if the slot is not already present in `gathered_signatures`: [2](#0-1) 

In the `Rejected` branch, the weight is only added if `responded_signers.insert(slot_id)` succeeds (i.e., the slot was not already in `responded_signers`): [3](#0-2) 

The two guards check different sets:
- The reject path correctly protects itself against being counted twice by checking `responded_signers`, which is written to by *both* branches (`Accepted` inserts into `responded_signers` at line 465, `Rejected` inserts into it at line 515).
- The accept path, however, guards only on `gathered_signatures`, which is written to *exclusively* by the `Accepted` branch.

So if a signer's `Rejected` message is processed first (weight added to `total_weight_rejected`, slot id inserted into `responded_signers` only — not into `gathered_signatures`), and that same signer's message later arrives as `Accepted` (out-of-order network delivery, retried publication, or a signer client that emits a rejection and then updates its vote), the accept path finds `gathered_signatures` does **not** contain the slot id, so it happily adds the same signer weight again — this time to `total_weight_approved`. The single unit of signer weight is now counted on both sides of what should be a mutually exclusive ledger (approved vs. rejected), exactly mirroring how the same catalyst individual inflated `group.numCatalyst` beyond what a correct symmetric accounting would allow.

### Impact Explanation
`total_weight_approved` and `total_weight_rejected` directly drive block-acceptance and rejection decisions inside the miner's block-broadcast logic: [4](#0-3) 

Because a single signer's weight can be double counted, the local `total_weight_approved` at this node can cross `self.weight_threshold` (line 467 of `stackerdb_listener.rs`) even though the true set of distinct approving weight is lower than what actual network-wide validation (`NakamotoBlockHeader::verify_signer_signatures`, which de-duplicates by public key via `signers_by_pk.remove`) would recognize as sufficient. This causes the miner to believe it has gathered quorum and broadcast a block that other honest nodes — which correctly deduplicate signatures — will reject for insufficient real signing weight, producing a temporary tip/block disagreement between the broadcasting miner and the rest of the network. The same double counting can also inflate `total_weight_rejected`, triggering premature/incorrect exclusion of transactions (`permanently_excluded_txids`/`temporarily_excluded_txids`) based on weight from a signer whose vote should not have counted against the block.

### Likelihood Explanation
No majority collusion is required — a single, ordinary (even non-malicious) signer whose messages are reordered by the network, or a signer client re-emitting responses, is sufficient to trigger the asymmetric accounting. The condition only requires that the `Rejected` message for a slot be observed by the listener before the `Accepted` message for the same slot, which is plausible under normal network jitter or client retry behavior, making this a minority/single-actor-triggerable divergence.

### Recommendation
Make the guard symmetric and identity-based: have the `Accepted` branch check `responded_signers` (the same set the `Rejected` branch uses) before crediting `total_weight_approved`, so that once a slot id has responded on either side, its weight cannot be added again from the other side. Concretely, change the condition at line 443 from `!block.gathered_signatures.contains_key(&slot_id)` to `!block.responded_signers.contains(&slot_id)` (or equivalent), consistent with how `Rejected` uses `responded_signers.insert(slot_id)` as its single source of truth for "has this signer's weight already been counted."

### Proof of Concept
1. Miner requests signatures for block `B` from a reward set including signer `S` at `slot_id = k` with weight `w`.
2. `StackerDBListener` processes an incoming `BlockResponse::Rejected` from `S` for `B` first: `responded_signers.insert(k)` succeeds, `total_weight_rejected += w` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-518`).
3. A later message batch delivers `S`'s `BlockResponse::Accepted` for the same block `B` (e.g., due to reordering/retry). The check `!block.gathered_signatures.contains_key(&k)` is true because `gathered_signatures` was never touched by the reject path, so `total_weight_approved += w` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-465`).
4. `total_weight_approved + total_weight_rejected` now exceeds `total_weight` by `w` for a single signer's weight counted on both sides, and `total_weight_approved` can reach `self.weight_threshold` (triggering `cvar.notify_all()` at line 467-470) using less genuinely-approving distinct weight than the threshold requires — while network-wide validation via `verify_signer_signatures` (which deduplicates per-signer) would not have granted quorum for the same signature set.
