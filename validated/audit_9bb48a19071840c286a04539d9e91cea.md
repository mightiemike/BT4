## Finding: Non-deterministic RNG (instead of Fiat–Shamir) drives accept/reject decisions in DKG transcript verification, breaking state-machine-replication determinism

### Title
Non-deterministic challenge generation in `weighted_protocol::Transcript::verify` can make identical DKG transcripts verify differently across validator re-executions - ([File: crates/aptos-dkg/src/pvss/das/weighted_protocol.rs])

### Summary
`Transcript::verify` for the DAS weighted PVSS scheme derives all of its verification challenges — the SoK challenge, the `LowDegreeTest` dual-codeword coefficients, and the random linear-combination coefficients (`alphas`, `betas`, `gammas`) used in the final multi-pairing check — from `rand::thread_rng()` rather than from a Fiat-Shamir hash of the transcript itself: [1](#0-0) 

The comment in the code explicitly acknowledges this design choice ("Deriving challenges by flipping coins... Creates bad RNG risks but we deem that acceptable"). This function is reached via `RealDKG::verify_transcript` → `trx.main.verify(...)`: [2](#0-1) 

which is invoked deterministically-expected in `process_dkg_result_inner` inside the AptosVM as part of committing the on-chain DKG result: [3](#0-2) 

The same `verify()` path (via the chunky-DKG analogue, which also seeds `rand::thread_rng()` per call) is used in peer-to-peer transcript aggregation: [4](#0-3) 

### Finding Description
`process_dkg_result_inner` is a validator-transaction execution path inside the VM — its outcome (`VMStatus::Executed` vs. `VMStatus::MoveAbort` with `TranscriptVerificationFailed`) becomes part of the committed transaction output and therefore the state root. For state-machine replication (and later replay/verification by full nodes, archival nodes, or state sync) to be safe, the exact same transcript bytes must produce the exact same `VMStatus`/`VMOutput` every time this transaction is executed, on any node, at any point in time.

Because the challenges consumed by `LowDegreeTest::random` and the SoK/multi-pairing checks are drawn from `rand::thread_rng()` instead of being deterministically derived (e.g., via a hash of the transcript bytes), the accept/reject decision is a function of ambient randomness, not solely of the transcript content. For a transcript that is *not* a valid low-degree-encoding under the SCRAPE dual-code test (i.e., an invalid `V`), whether `low_degree_test_on_g1` returns `Ok(())` or `Err(...)` depends on which random dual-codeword coefficients happen to be sampled during that particular call.

### Impact Explanation
If `verify()` returns different results on different executions of the identical committed transaction, this is precisely the "hard-fork-only divergence during commit/replay/verification" class of bug: two conforming nodes executing the same validator transaction could reach different `VMStatus` outputs and hence different state roots, or a full node's later replay could diverge from the historically-committed result. This corrupts the deterministic binding between committed transaction bytes and the transaction output/state that the review scope calls out.

### Likelihood Explanation
The practical likelihood of triggering actual divergence is extremely low, because the LDT and multi-pairing checks used here are sound against a soundness bound that depends on the size of the BLS12-381 scalar field (~2^255), independent of how `V` is crafted. No adversary can meaningfully raise the failure probability above field-theoretic negligibility, so this is not something exploitable to reliably force a fork with realistic effort. What is real and independent of attacker skill is the design defect itself: consensus-critical verification is not deterministic-by-construction (it should be re-derived via Fiat-Shamir from the transcript, as is standard practice for exactly this reason), and this pattern is repeated across both the `weighted_protocol` and `chunky` DKG verifiers.

### Recommendation
Replace `rand::thread_rng()` in `Transcript::verify` (and the equivalent chunky-DKG verification path) with a deterministic Fiat-Shamir transform — derive all challenge scalars from a cryptographic hash of the transcript bytes/public parameters (and any other data intended to be bound to the challenge), so that `verify()` is a pure function of its inputs and cannot diverge across independent executions.

### Proof of Concept
Conceptually: call `weighted_protocol::Transcript::verify` twice on the same (malformed) transcript with two different seeded RNGs substituted for `rand::thread_rng()` (requires local instrumentation since the function hardcodes `thread_rng()`), producing two different `extra` challenge vectors at line 306 and thus two different `LowDegreeTest::random` dual-codewords at line 320. For a `V` on the boundary of the code's soundness bound, one run's dual-codeword can yield `Ok(())` while the other yields `Err(...)`, demonstrating that `verify()`'s result is not a deterministic function of the transcript alone.
