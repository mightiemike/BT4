### Title
Hardcoded `CLEAN_INTERVAL`/`SHRINK_INTERVAL` wall-clock constants assume legacy 400ms slot time, causing disproportionate storage/CPU cost after slot-time reduction - (File: `runtime/src/accounts_background_service.rs`)

### Summary
`AccountsBackgroundService`'s clean/shrink cadence is governed by hardcoded `Duration` constants (`CLEAN_INTERVAL = 50s`, derived explicitly from an assumed legacy 400ms slot time) rather than the bank's actual, potentially reduced, slot duration. Agave now supports feature-gated slot-time reduction (200ms/250ms/300ms/350ms) via `runtime/src/slot_params.rs`, which already scales other cadence-sensitive constants (e.g., `partitioned_epoch_rewards_stake_account_stores_per_block` in `accounts-db/src/partitioned_rewards.rs`) to the active slot-time regime — but `CLEAN_INTERVAL`/`SHRINK_INTERVAL` were not similarly adapted. This is analogous to the external report's `blocksPerYear` bug: a wall-clock-derived constant baked in for one block/slot-time assumption becomes wrong once the actual cadence changes, and here it cannot self-correct because it's a fixed background-service timer, not a market variable.

### Finding Description
`CLEAN_INTERVAL` and its accompanying comment make the assumption explicit: [1](#0-0) 

```
const MIN_LOOP_INTERVAL: Duration = Duration::from_millis(100);
// Set the clean interval duration to be approximately how long before the next incremental
// snapshot request is received, plus some buffer.  The default incremental snapshot interval is
// 100 slots, which ends up being 40 seconds plus buffer.
const CLEAN_INTERVAL: Duration = Duration::from_secs(50);
const SHRINK_INTERVAL: Duration = Duration::from_secs(1);
```

The 40-second figure is `100 slots * 400ms/slot`, the legacy PoH slot time baked into `LEGACY_SLOT_PARAMS` in `runtime/src/slot_params.rs`: [2](#0-1) 

The codebase, however, now supports runtime slot-time reduction to 350ms/300ms/250ms/200ms via feature gates, each with its own `ns_per_slot`: [3](#0-2) 

When one of these features is active, the default incremental snapshot interval of 100 slots (`DEFAULT_INCREMENTAL_SNAPSHOT_ARCHIVE_INTERVAL_SLOTS`) elapses in as little as 20 seconds of wall-clock time instead of 40 seconds: [4](#0-3) 

Yet `CLEAN_INTERVAL` in the ABS main loop remains fixed at 50 seconds — it is used verbatim to gate `should_clean`/`should_shrink` without any reference to `bank.ns_per_slot_at_slot()` or `SlotParams`: [5](#0-4) 

Notably, other constants in the same feature area were explicitly redesigned to scale with the active slot-time regime — e.g. `partitioned_rewards.rs` documents "shorter slot-time targets scale this value down in `Bank` state": [6](#0-5) 

demonstrating the codebase's own convention that slot-time-sensitive constants must be scaled, a convention `accounts_background_service.rs`'s `CLEAN_INTERVAL`/`SHRINK_INTERVAL` do not follow.

### Impact Explanation
With a reduced slot time active, several incremental-snapshot cycles (and potentially several successive rounds of new dirty stores, zero-lamport-account creation, and reclaimable storage) can accumulate between two `should_clean` triggers, since `previous_clean_time.elapsed() > CLEAN_INTERVAL` fires far less often relative to the pace of new roots/slots than intended. This causes:
- Disproportionate growth of `dirty_stores` and the accounts index working set between clean cycles, since the ABS loop only performs the flush/clean/shrink branch (which is the code path guarded by `should_clean`/`should_shrink`) when no snapshot request is being handled that iteration: [7](#0-6) 
- Disproportionate CPU/I/O cost when clean/shrink eventually does run, having to process a much larger backlog of candidate slots/storages than the interval was designed for at the assumed 400ms cadence.
- Storage bloat (larger `AccountsDb` file-system footprint) that a properly-scaled interval would have kept bounded, closer in spirit to the `disproportionate storage and CPU cost` category called out as in-scope.

This is a resource/availability-class issue, not a hash-divergence or panic; it degrades under the newly-introduced slot-time-reduction features rather than under default legacy operation.

### Likelihood Explanation
Likelihood is tied directly to activation of any `reduce_slot_time_to_{350,300,250,200}ms` feature, which is a first-class, already-implemented mechanism in this codebase (`slot_time_feature_gates()`), not a hypothetical. Any validator running with slot-time reduction active will unconditionally hit the stale 50s/1s intervals, since these constants have no dependency on `SlotParams`/`bank.ns_per_slot`.

### Recommendation
Derive `CLEAN_INTERVAL` (and `SHRINK_INTERVAL`, if similarly intended to track snapshot cadence) from the bank's actual `ns_per_slot`/`SlotParams` for the currently active slot-time regime, analogous to how `partitioned_rewards.rs`'s `stake_account_stores_per_block` is scaled in `Bank` state, e.g. by computing the interval as `incremental_snapshot_archive_interval_slots * bank.ns_per_slot_at_slot(bank.slot())` plus a fixed buffer, rather than hardcoding a value derived from the legacy 400ms assumption.

### Proof of Concept
1. Activate `feature_set::reduce_slot_time_to_200ms` (as in `runtime/src/bank/tests.rs::test_reduce_slot_time_range_duration`, which already demonstrates this feature path is fully wired: [8](#0-7) ).
2. With `ns_per_slot = 200_000_000` active and the default `DEFAULT_INCREMENTAL_SNAPSHOT_ARCHIVE_INTERVAL_SLOTS = 100`, incremental snapshot requests now arrive roughly every 20 seconds of wall-clock time instead of 40.
3. `AccountsBackgroundService`'s `CLEAN_INTERVAL` remains `Duration::from_secs(50)` (`runtime/src/accounts_background_service.rs:46`), so `should_clean` in the loop (`runtime/src/accounts_background_service.rs:541`) only triggers roughly once every 2-3 incremental snapshot cycles instead of once per cycle as the original 400ms-based design intended, allowing dirty/zero-lamport account state and shrink candidates to accumulate beyond the originally intended bound.
