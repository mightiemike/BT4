### Title
`disable_zk_elgamal_proof_program` feature flag blocks `CloseContextState`, permanently locking users' rent lamports in ZK proof context accounts - (File: `programs/zk-elgamal-proof/src/lib.rs`)

### Summary
The zk-elgamal-proof builtin program's entrypoint applies a single global "pause" check that unconditionally rejects *every* instruction — including `CloseContextState`, the only instruction that returns a user's locked rent-exempt lamports back to them — whenever the `disable_zk_elgamal_proof_program` feature is active and `reenable_zk_elgamal_proof_program` is not. This mirrors the reported OmniPool bug class where a global pause blocks the one "escape hatch" instruction (repay) that protects user funds, rather than exempting it.

### Finding Description
The program entrypoint gates all instruction processing behind a feature check before dispatching to any instruction handler: [1](#0-0) 

```rust
declare_process_instruction!(Entrypoint, 0, |invoke_context| {
    if invoke_context
        .get_feature_set()
        .disable_zk_elgamal_proof_program
        && !invoke_context
            .get_feature_set()
            .reenable_zk_elgamal_proof_program
    {
        ic_msg!(invoke_context, "zk-elgamal-proof program is temporarily disabled");
        return Err(InstructionError::InvalidInstructionData);
    }
    ...
    match instruction {
        ProofInstruction::CloseContextState => {
            ...
            process_close_proof_context(invoke_context)
        }
        ...
    }
});
```

Users create `ProofContextState` accounts (paying rent-exempt lamports for them) via `Verify*` instructions and later reclaim those lamports by invoking `CloseContextState`, transferring the account's lamports to a destination and closing it. Because the pause check is applied uniformly at the top of the entrypoint before instruction dispatch, activating `disable_zk_elgamal_proof_program` (without `reenable_zk_elgamal_proof_program`) blocks `CloseContextState` exactly the same way `whenNotPaused` blocked `OmniPool::repay()` in the referenced report — it disables the one instruction that lets users retrieve funds they are owed, rather than only disabling the risky/exploitable verification paths.

This is directly analogous to the report's root cause: "users are not able to [reclaim funds] when paused," which can leave lamports stuck in context-state accounts for as long as the feature remains active with no override, with no way for the account owner to force-close and recover the rent.

### Impact Explanation
Any user (or program, e.g. Confidential Transfer extension flows) that has an open `ProofContextState` account cannot close it and recover its rent-exempt lamports while the program is disabled. Funds are not stolen but are locked/inaccessible for the duration of the pause — a direct parallel to the referenced finding's "users can't repay, funds partially frozen" impact, differing only in that the underlying protocol here is a native/builtin Solana program rather than an application-layer lending pool. If, during the disabled window, the associated confidential-transfer state depends on closing the context account to finalize a balance-affecting operation, users could be prevented from completing intended state transitions until the feature is reversed.

### Likelihood Explanation
This requires activation of the `disable_zk_elgamal_proof_program` feature without `reenable_zk_elgamal_proof_program` — a cluster-wide, feature-gated, non-attacker-controlled event, not something an ordinary unprivileged client can trigger at will. It historically has been activated by validators/cluster operators. While reachable through an ordinary client transaction attempting `CloseContextState` during such a window, the trigger condition (feature activation) is an operator/consensus-level decision rather than an unprivileged transaction-level exploit.

### Recommendation
Exempt `ProofInstruction::CloseContextState` from the global disable check so that, even when the program is otherwise paused, account owners can always reclaim their locked rent-exempt lamports by closing their proof context state accounts — analogous to removing `whenNotPaused` from `repay()` in the original report.

### Proof of Concept
1. Client submits `VerifyPubkeyValidity` (or other verify instruction) creating a `ProofContextState` account funded with rent-exempt lamports, owned by the zk-elgamal-proof program.
2. Cluster activates `disable_zk_elgamal_proof_program` (and `reenable_zk_elgamal_proof_program` is not active).
3. Client submits `CloseContextState` to reclaim the account's lamports.
4. Entrypoint check at [2](#0-1)  short-circuits before dispatch, returning `InstructionError::InvalidInstructionData` regardless of instruction type.
5. The account and its lamports remain locked/inaccessible to the owner until the feature configuration changes.
