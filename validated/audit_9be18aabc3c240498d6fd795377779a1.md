### Title
Backup restore accepts unsigned/forged `LedgerInfoWithSignatures` when its epoch exceeds the verified epoch history — (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
`EpochHistory::verify_ledger_info` silently returns `Ok(())` (only logging a warning) whenever the epoch of the `LedgerInfoWithSignatures` being checked is greater than the number of epoch-ending `LedgerInfo`s the restore process has already collected and verified. No signature or validator-set check is ever performed in this branch, and none of the callers (`transaction/restore.rs`, `state_snapshot/restore.rs`) perform an independent `verify_signatures`/`check_voting_power` check elsewhere in the restore path.

### Finding Description
`EpochHistory::verify_ledger_info` at [1](#0-0)  is the sole gate that is supposed to authenticate a `LedgerInfoWithSignatures` supplied inside a backup archive during restore, by chaining it to a previously-verified epoch-ending `LedgerInfo`'s `next_epoch_state().verify(...)` (which internally calls BLS signature/voting-power verification via `EpochState::verify` → `ValidatorVerifier`).

However, if `epoch > self.epoch_endings.len()`, the function takes an early-return path that performs **no cryptographic verification at all** — it just logs a warning ("Epoch is too new and can't be verified... node won't be able to start if this data is malicious") and returns `Ok(())`.

This function is invoked directly on attacker-suppliable data coming from `BackupStorage` (an untrusted backup medium by design — that's the entire reason restore verifies signatures) in:
- `LoadedChunk::load` for transaction chunks: [2](#0-1) 
- state snapshot restore (`storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs`), similarly gating a `TransactionInfoWithProof`/`LedgerInfoWithSignatures` pair before trusting the snapshot's root hash.

After `verify_ledger_info` "passes" for such a too-new epoch, the code proceeds to verify the transaction list / state root strictly against the *unauthenticated* `ledger_info`'s accumulator/root hash fields (e.g. `txn_list_with_proof.verify(ledger_info.ledger_info(), ...)` at [3](#0-2) ). Merkle-proof verification against a self-consistent but forged root is meaningless — an attacker who controls the backup archive can forge both the `LedgerInfo` (with any accumulator root, any epoch number, and empty/garbage `AggregateSignature`) and the transaction/state data that hashes to that root, and have it accepted as legitimate as long as the claimed `epoch` field is set higher than however many epoch-ending ledger infos the operator's restore session has actually validated.

### Impact Explanation
This breaks the fundamental trust boundary of the backup/restore feature: the entire point of `EpochHistory`/waypoint verification is to ensure that any `LedgerInfoWithSignatures` used to authenticate restored ledger data was actually signed by a quorum of the epoch's validator set. Bypassing it allows an attacker who can supply or tamper with a backup archive (e.g., a compromised or malicious backup storage backend, a supply-chain-compromised snapshot, or a MITM'd download) to have a node restore/replay arbitrary, fully attacker-chosen transactions, write sets, and state roots as if they were legitimately committed ledger state — corrupting the durable ledger the restored node will subsequently serve to clients and participate in consensus with. This is a durable, hard-to-detect state-integrity violation exactly in the class the task calls out ("restore flows... must not reinterpret committed data into a different ledger state").

### Likelihood Explanation
Triggering the bug only requires the attacker-controlled backup archive to set the `epoch` field of a crafted `LedgerInfo` higher than `epoch_endings.len()` — i.e., higher than the number of epoch-ending ledger infos actually verified in the current restore session (which is trivially small/bounded, e.g. just genesis, for anyone restoring from an untrusted or partial backup). No cryptographic material or private keys are required to forge the accepted `LedgerInfoWithSignatures`. The code comment itself ("Epoch is too new and can't be verified... won't be able to start if this data is malicious") acknowledges the gap is a known, deliberate `TODO` rather than a hardened invariant, and it fires silently (a `warn!` log) rather than aborting restoration.

### Recommendation
Do not treat "epoch too new to verify" as a pass. Either:
1. Reject/defer any `LedgerInfoWithSignatures` whose epoch is not yet covered by the verified `epoch_endings` history (fail closed instead of `Ok(())`), forcing the epoch-history restore to complete first for all epochs referenced by transaction/state-snapshot chunks; or
2. If deferred verification is required architecturally, buffer/queue restored data keyed by claimed root and only commit it to durable storage after the corresponding epoch-ending `LedgerInfo` has been retroactively verified against the validator set, aborting the whole restore if verification later fails.

### Proof of Concept
1. Prepare a malicious backup archive containing:
   - An `EpochEndingBackup` manifest with only genesis (epoch 0) `LedgerInfo`, so `EpochHistory.epoch_endings.len() == 1`.
   - A `TransactionBackup` chunk whose accompanying `(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)` proof file has `ledger_info.epoch() = 999` (any value `> 1`), an `AggregateSignature::empty()`, and a `transaction_accumulator_hash` computed locally over attacker-chosen fake transactions/transaction infos.
2. Run backup-cli restore against this archive pointing to a fresh node's storage.
3. In `LoadedChunk::load`, `epoch_history.verify_ledger_info(&ledger_info)` takes the `epoch > epoch_endings.len()` branch, logs a warning, and returns `Ok(())` without checking signatures.
4. `txn_list_with_proof.verify(ledger_info.ledger_info(), ...)` succeeds because the attacker computed the proof consistently with their own forged root.
5. The forged transactions/write sets are accepted and replayed/committed into the restored database as legitimate ledger history, with no validator signature ever having been checked.
