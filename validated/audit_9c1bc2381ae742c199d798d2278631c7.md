The CVE-2019-11921 describes a memory-safety bug in Proxygen's C++ Base64 decoder — a manual buffer-length miscalculation leading to an out-of-bounds **write** into attacker-influenced memory. In protobuf-go, the analogous Base64 parsing path is `unmarshalBytes` in `encoding/protojson/decode.go`, which decodes JSON string bytes fields using Go's standard library `encoding/base64` (`base64.StdEncoding` / `base64.URLEncoding`, with padding adjustment based on string length) [1](#0-0) .

This does not have the same broken invariant as the C++ report for several reasons:
- Go's `base64.Encoding.DecodeString` computes the destination buffer size internally via `DecodedLen` and allocates a Go slice, which is bounds-checked by the runtime — there is no manual pointer arithmetic or attacker-controlled buffer sizing that could cause an out-of-bounds write.
- Any malformed/invalid Base64 input (bad characters, wrong padding) results in an `error` return, which `unmarshalBytes` checks and turns into a normal decode error via `d.newError(...)` in `unmarshalScalar`, not a memory-corruption sink [2](#0-1) .
- Go's memory model (slice bounds checking, no manual buffer management) structurally prevents the out-of-bounds-write bug class described in the Proxygen advisory.

Since there is no reachable code path in protobuf-go where Base64 decoding of untrusted input can lead to an out-of-bounds write or any equivalent unsafe-memory effect, this report does not have a valid analog in this codebase.

func unmarshalBytes(tok json.Token) (protoreflect.Value, bool) {
	if tok.Kind() != json.String {
		return protoreflect.Value{}, false
	}

	s := tok.ParsedString()
	enc := base64.StdEncoding
	if strings.ContainsAny(s, "-_") {
		enc = base64.URLEncoding
	}
	if len(s)%4 != 0 {
		enc = enc.WithPadding(base64.NoPadding)
	}
	b, err := enc.DecodeString(s)
	if err != nil {
		return protoreflect.Value{}, false
	}
	return protoreflect.ValueOfBytes(b), true
}
