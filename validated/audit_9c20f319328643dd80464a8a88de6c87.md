### Title
Hard-coded NEP-141 storage deposit amount in the Wallet Contract can strand ERC-20 transfer funds/fees when a token's real storage cost exceeds the constant - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (NEAR's ETH-implicit account handler, reachable by anyone submitting an RLP-encoded Ethereum-style transaction via `rlp_execute`) hard-codes the NEP-141 `storage_deposit` amount as a compile-time constant `NEP_141_STORAGE_DEPOSIT_AMOUNT = 1_250 * MICRO_NEAR` instead of querying the target token's actual `storage_balance_bounds`. [1](#0-0) 

### Finding Description
When an ETH-implicit account owner submits an emulated ERC-20 `transfer` (`eth_emulation::try_emulation`, selector `ERC20_TRANSFER_SELECTOR`) to an unregistered receiver, `inner_rlp_execute` first calls `storage_balance_of` on the token and, if the receiver has no storage balance, chains a `storage_deposit` call funded with the fixed `NEP_141_STORAGE_DEPOSIT_AMOUNT` followed immediately by the `ft_transfer` call, all inside one promise batch with no intermediate check of the deposit's success: [2](#0-1) 

This constant is explicitly documented as "the one used by the standard NEP-141 implementation" and intentionally *not* derived from the target contract's `storage_balance_bounds`, both to avoid an extra cross-contract call and to defend against malicious tokens with inflated bounds: [3](#0-2) 

Any legitimate, non-malicious NEP-141 token whose actual registration cost is higher than 1250 * 10^18 yoctoNEAR (e.g., due to longer account-id keys stored, additional per-account metadata, or a future change to storage price/`storage_balance_bounds` on that token) will cause the batched `storage_deposit` call to fail with insufficient deposit. Because `storage_deposit` and `ft_transfer` are chained in the same promise batch, if the first fails the whole batch is treated as failed and `rlp_execute_callback` runs the "Failed" branch: [4](#0-3) 

In that failure path, only the caller's *fee* deposit (`CallerDeposit`) is refunded — the `NEP_141_STORAGE_DEPOSIT_AMOUNT` NEAR attached to the failed `storage_deposit` call and any `ft_transfer` deposit (`yocto_near: 1` per `eth_emulation.rs`) are drawn from the wallet-contract account's own balance via `Promise::new(token_id).function_call(...)`, not refunded by this callback, and their fate depends entirely on the token contract's own panic/refund behavior on a failed `storage_deposit` call. If the token contract does not refund unused attached deposit on failure (which NEP-141/145 does not universally guarantee), the attached NEAR is burned/stuck rather than returned to the user, and the intended `ft_transfer` never executes even though the user's nonce is not incremented for a retried transaction — creating either fund loss or a hard block on all future ERC-20 transfers through this wallet to that receiver.

### Impact Explanation
This is a state-transition-affecting bug reachable purely by a transaction/RLP-payload submitted by a normal ETH-implicit account holder (no privileged or validator role needed): value (attached NEAR for storage registration) can be sent and lost to a legitimate but higher-cost NEP-141 contract because the deposit amount is a hard-coded constant that cannot track real-world `storage_balance_bounds` values, matching the "hard-coding of an external protocol constant that may become insufficient/unusable after an update" bug class from the report (EULER address hard-coding). Unlike the low-severity original report, here the consequence is concrete unauthorized loss of user NEAR funds (deposit sent but not refunded on failure) and/or a permanently failing NEP-141 transfer path for that receiver, satisfying "concrete unauthorized value movement" / "permanently frozen funds" criteria.

### Likelihood Explanation
Likelihood depends on the existence of a NEP-141 token whose real registration storage cost exceeds 1250 microNEAR-scaled units (1.25 * 10^21 yoctoNEAR) — this is plausible for tokens with additional storage-heavy account metadata or that increase their bounds over time, since the wallet contract can't adapt to updates in `storage_balance_bounds` for any given token. This is not a hypothetical audit-only concern but an inherent limitation baked into the compiled binary of the wallet contract deployed for all ETH-implicit accounts.

### Recommendation
Do not hard-code `NEP_141_STORAGE_DEPOSIT_AMOUNT`. Either (a) query `storage_balance_bounds` on the target token before constructing the batched promise and use the returned `min` bound (capping it at some maximum to retain the anti-DoS protection the comment describes), or (b) split `storage_deposit` and `ft_transfer` into separate promises with an explicit callback that checks the `storage_deposit` result and refunds the caller/wallet if it fails before attempting the transfer, so failed registrations never silently consume the wallet's balance.

### Proof of Concept
1. Deploy (or use) a NEP-141 token whose `storage_balance_bounds().min` is greater than `1_250 * 10^18` yoctoNEAR (e.g., due to a larger `min_storage_usage` for its account records).
2. From an ETH-implicit account with the Wallet Contract deployed, submit an RLP-encoded ERC-20 `transfer` (selector `0xa9059cbb`) to a receiver_id that is not yet registered with that token.
3. `inner_rlp_execute` → `nep_141_storage_balance_callback` observes `None` storage balance and issues a batched `storage_deposit` (funded with the fixed constant) + `ft_transfer`. [2](#0-1) 
4. Because the attached deposit is insufficient for this token's actual bounds, `storage_deposit` panics/fails; the batch fails; `rlp_execute_callback` only refunds the relayer fee, not the NEAR sent as the storage deposit attempt. [4](#0-3) 
5. The user's intended ERC-20 transfer never completes and the attached NEAR is lost/stuck, depending on the token's refund behavior on failed calls.
