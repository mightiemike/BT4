### Title
Missing Slippage/Minimum-Output Protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` Enables Front-Running of TRC10 Bancor-style Exchange Operations - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
java-tron's built-in Bancor-style "Exchange" market allows anonymous accounts to submit `ExchangeTransactionContract` (swap) transactions that move a pool's `firstTokenBalance`/`secondTokenBalance` ratio. `ExchangeTransactionActuator` correctly guards against unfavorable pricing because the transaction carries an `expected` (minimum-output) field that is validated against the live pool state before execution [1](#0-0) . However, the analogous liquidity-provision/removal operations — `ExchangeInjectContract` (add liquidity) and `ExchangeWithdrawContract` (remove liquidity) — have no such minimum/maximum bound on the counter-token amount received or paid, exactly mirroring the "missing slippage protection" pattern described in the external report for `enter()`/`quit()`.

### Finding Description
`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` purely from the pool balances read at execution time, with no caller-supplied bound: [2](#0-1) 

The corresponding validation (`doValidate()`) only checks that `anotherTokenQuant` is positive and that the account has enough balance — it never lets the caller specify an acceptable minimum/maximum for `anotherTokenQuant`: [3](#0-2) 

`ExchangeWithdrawActuator` has the same shape: `anotherTokenQuant` (the amount of the paired token returned to the withdrawer) is derived purely from the current pool ratio, and the only safeguard is a fixed 0.0001 rounding-precision check ("Not precise enough"), not a user-defined slippage/minimum-output bound: [4](#0-3) [5](#0-4) 

Compare this to `ExchangeTransactionContract`, which explicitly carries an `expected` field used as the slippage floor [6](#0-5)  and is enforced in `ExchangeTransactionActuator.doValidate()` [1](#0-0) . `ExchangeInjectContract`/`ExchangeWithdrawContract` protobuf messages have no equivalent field [7](#0-6) .

Because `ExchangeTransactionContract` is callable by any account holding the relevant asset (broadcast, unprivileged), an attacker can front-run a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction (observed in the public mempool before block inclusion) with a swap that skews the pool ratio, then let the victim's inject/withdraw execute against the manipulated ratio — extracting value from the liquidity provider/withdrawer with no on-chain check to prevent it.

### Impact Explanation
This causes asset/accounting corruption for the liquidity provider or withdrawer: they receive a materially different amount of the counter-token than the ratio implied when they signed and broadcast their transaction, with no protocol-level minimum bound to reject the unfavorable outcome. Because the Exchange contract types manage real TRX/TRC10 asset balances directly in `AccountStore`/`ExchangeStore` state, this is a concrete on-chain value-extraction vector, not merely a theoretical DeFi contract issue.

### Likelihood Explanation
Exploitation only requires the ability to observe a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` in the transaction pool and race a corresponding `ExchangeTransactionContract` swap ahead of it in block ordering — both actions are available to any unprivileged account via the public broadcast API, requiring no special permissions or keys.

### Recommendation
Add a caller-specified bound (e.g., `expected_another_token_min`/`max`, mirroring the `expected` field already used by `ExchangeTransactionContract`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()`, rejecting the transaction with a `ContractValidateException` when the live-computed `anotherTokenQuant` falls outside the caller's tolerance.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) from victim V targeting exchange pool P with favorable current ratio.
2. Attacker broadcasts an `ExchangeTransactionContract` swap against P with a large `quant` and `expected=1` (minimal, so it always passes attacker's own slippage check) to shift `firstTokenBalance`/`secondTokenBalance` unfavorably for V.
3. If the attacker's swap is ordered before V's inject/withdraw within the same block (achievable by fee/priority manipulation or simple mempool racing), `ExchangeInjectActuator`/`ExchangeWithdrawActuator` computes `anotherTokenQuant` off the now-skewed balances (`ExchangeInjectActuator.java` lines 68-83; `ExchangeWithdrawActuator.java` lines 63-89) with no minimum-output check to reject it.
4. V's transaction executes successfully but yields a much worse `anotherTokenQuant` than intended, while the attacker can reverse their swap afterward to realize a profit — no code path in either actuator prevents this.
