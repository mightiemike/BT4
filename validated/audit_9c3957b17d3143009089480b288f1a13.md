### Title
Unbounded duplicate accumulation in shop session-id index causes denial of service for KV-backed session storage - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage.storeSession` appends a session's id to a per-shop index list (`shop:<shop>`) every time a session is stored, without checking whether that id is already present in the list. Because `storeSession` is called repeatedly for the same session id during normal, unprivileged flows (OAuth callback and token-exchange), the per-shop index array grows without bound and accumulates duplicate ids, mirroring the Ribbon `vaultState.totalPending`-only-ever-increases bug class: a tracking value/collection that is incremented on one path but never correctly reconciled/deduplicated, eventually breaking core functionality.

### Finding Description
`storeSession` calls the private `addShopIds` helper unconditionally on every store: [1](#0-0) 

`addShopIds` fetches the existing id array for the shop and simply concatenates the new id(s) onto it with no de-duplication check: [2](#0-1) 

The corresponding cleanup path, `removeShopIds` (invoked from `deleteSession`), does perform a filter, but only removes ids matching the deleted session — it does not fix already-duplicated entries, and is not invoked at all on re-`storeSession` calls for a session that hasn't been deleted: [3](#0-2) [4](#0-3) 

`storeSession` is invoked from normal, unprivileged, repeat-triggerable flows such as the token-exchange strategy used by embedded apps (executed whenever a valid session-token exchange happens, which can occur repeatedly for the same session id) and the OAuth callback path: [5](#0-4) 

Each repeat call to `storeSession` for the *same* `session.id` (e.g. the deterministic offline session id `offline_${shop}`, or a re-used online session id) appends another duplicate entry to `shop:<shop>` rather than updating/deduping the existing entry — exactly analogous to `vaultState.totalPending` only ever increasing across repeated deposit/instant-withdraw cycles.

### Impact Explanation
As the per-shop id array grows unboundedly with duplicate entries:
- `findSessionsByShop` (used by `AppInstallations.includes`/`delete` in `shopify-app-express`) returns the same session duplicated many times, corrupting any code that assumes one entry per stored session and iterates this list to make installation/authorization decisions.
- The `shop:<shop>` KV value itself grows unbounded. Cloudflare KV enforces per-value size limits; once the serialized array exceeds that limit, subsequent `namespace.put` calls in `addShopIds`/`removeShopIds` will fail, which in turn can throw out of `storeSession`/`deleteSession`. This breaks the OAuth callback and token-exchange completion for that shop going forward — a denial of service of the auth/session-storage handler that can only be fixed by manually purging the corrupted KV key, similar to the "vault upgrade" required in the original report.

### Likelihood Explanation
This does not require a malicious actor: any legitimate, repeated OAuth/token-exchange cycle for the same shop (which is completely normal app usage — reinstalls, re-authentications, token refreshes) triggers `storeSession` with the same session id and grows the index. Over the lifetime of an active shop this is a near-certain outcome given enough store/re-auth cycles.

### Recommendation
In `addShopIds`, de-duplicate before writing (e.g. `Array.from(new Set([...shopIds, ...ids]))`), and/or have `storeSession` remove any pre-existing id for the same session before adding it back, mirroring how `vaultState.totalPending` should be decremented before being conditionally re-incremented. Add tests (as recommended in the analogous report) that call `storeSession` multiple times with the same session id and assert `findSessionsByShop` returns exactly one entry.

### Proof of Concept
1. Create a `KVSessionStorage` instance backed by a KV namespace.
2. Call `storage.storeSession(session)` multiple times with a `Session` object using the same `id` and `shop` (this mirrors what happens across repeated OAuth callbacks or token-exchange calls for the same shop/session).
3. Observe that `shop:<shop>` in the namespace accumulates one duplicate entry per call: [2](#0-1) 
4. Call `storage.findSessionsByShop(shop)` and observe the same session object returned N times instead of once: [6](#0-5) 
5. Repeating this over many cycles eventually produces an array large enough to exceed KV value size limits, causing `put` to fail on future `storeSession`/`deleteSession` calls for that shop.

    );
