## Finding

### Title
`handle_poison_microblock` accepts a replayed *identical* `StacksMicroblockHeader` pair as valid equivocation evidence, letting an unprivileged reporter steal an honest miner's coinbase with zero real fork - (`stackslib/src/chainstate/stacks/db/transactions.rs`)

### Summary
`check_microblock_header_signer` and `handle_poison_microblock` only verify that the two supplied microblock headers recover to the *same* `microblock_pubkey_hash`; neither the Clarity-level handler nor the consensus-critical `process_transaction` path for `TransactionPayload::PoisonMicroblock` ever check that the two headers are actually distinct or represent a genuine conflict (same `prev_block`/`sequence` but different `tx_merkle_root`). An attacker who merely observes one legitimately-signed microblock header broadcast by a victim miner can submit it twice as `(mblock_header_1, mblock_header_2)` and have the report accepted as if a real equivocation occurred.

### Finding Description
The claimed equality is: *reward paid to reporter == miner actually signed two distinct microblocks at the same sequence*.

`check_microblock_header_signer` (`stackslib/src/chainstate/stacks/db/transactions.rs:686-713`) only checks `pkh1 != pkh2` and returns the common pubkey hash — trivially true if `mblock_hdr_1` and `mblock_hdr_2` are byte-identical, since recovering a pubkey from the same message+signature twice yields the same key. [1](#0-0) 

`handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs:722-857`) calls only `check_microblock_header_signer`, then checks the pubkey-hash's recorded height and the `MINER_REWARD_MATURITY` window, then unconditionally inserts a poison report keyed by `mblock_header_1.sequence`. There is no check anywhere in this function that `mblock_header_1 != mblock_header_2`, nor that the two headers share `prev_block`+`sequence` with differing content (the actual definition of equivocation used elsewhere, e.g. `validate_parent_microblock_stream` at `stackslib/src/chainstate/stacks/db/blocks.rs:3018-3037`, which explicitly compares `block_hash()` to detect a real fork). [2](#0-1) [3](#0-2) 

The consensus-critical call site, `process_transaction`'s handling of `TransactionPayload::PoisonMicroblock` (`stackslib/src/chainstate/stacks/db/transactions.rs:1389-1413`), only checks that post-conditions are empty before invoking `clarity_tx.run_poison_microblock(...)` → `handle_poison_microblock`. It performs no additional distinctness/conflict check either. [4](#0-3) 

The only other place a similar check exists is the *mempool admission* gate `MemPoolRejection::PoisonMicroblocksDoNotConflict` (`stackslib/src/chainstate/stacks/db/blocks.rs:6844-6868`), which is not part of block validation/consensus — and even that check only requires `sequence`, `prev_block`, and `version` to be *equal* between the two headers, which is trivially satisfied when the headers are literally identical; it never asserts the headers differ. [5](#0-4) 

**Attacker's exact input / exploit flow:**
1. Attacker observes any single legitimately-signed `StacksMicroblockHeader` `H` produced and broadcast by the victim miner during a tenure (microblocks are broadcast in the clear over the p2p network before being confirmed).
2. Attacker (any unprivileged account, no stake, no mined blocks) builds `TransactionPayload::PoisonMicroblock(H.clone(), H.clone())` and signs/broadcasts it as an ordinary Stacks transaction (fee can be 0).
3. Any node processing a block containing this tx runs `process_transaction` → `run_poison_microblock` → `handle_poison_microblock`. `check_microblock_header_signer` succeeds trivially (`pkh1 == pkh2`), the pubkey-hash height lookup succeeds (the miner's anchored block already recorded it via `insert_microblock_pubkey_hash`), and a poison report is stored via `insert_microblock_poison` keyed at that height/sequence.
4. At maturation, `find_mature_miner_rewards` (`stackslib/src/chainstate/stacks/db/accounts.rs:985-1076`) reads `get_poison_microblock_report` and passes the reporter into `calculate_miner_reward` (`stackslib/src/chainstate/stacks/db/accounts.rs:794-905`), which redirects `POISON_MICROBLOCK_COMMISSION_FRACTION` of the coinbase to the attacker/reporter and destroys the remainder — with no real equivocation ever having occurred. [6](#0-5) [7](#0-6) 

Every node in the network reaches the same (deterministic, consensus-valid) conclusion, so there is no chain split — but the honest miner's coinbase is deterministically and irreversibly redirected/burned based on a forged "equivocation" that consists of a single, honestly-produced header replayed twice.

### Impact Explanation
This is block-reward theft/loss: the honest miner's mature coinbase reward is partially paid to an attacker (the `poison_microblock_commission`) and the remainder is destroyed, even though the miner never actually equivocated (never signed two distinct microblocks at the same sequence). This matches the Critical category "block-reward theft/double-payment/loss." The attack is fully repeatable against any miner as soon as any one of their microblock headers becomes observable (which happens by design, since microblocks are broadcast).

### Likelihood Explanation
Preconditions: the attacker needs (a) visibility of one microblock header broadcast by the target miner (public by protocol design), (b) the miner's anchored block/microblock-pubkey-hash to have already been recorded on chain, and (c) the report to land within `MINER_REWARD_MATURITY` blocks of that height. No BTC spend, no stake, no signer/majority role, and no mined block are required — the attacker only needs to pay ordinary tx fees (which can be minimal). This is highly feasible and trivially repeatable against every miner's tenure.

### Recommendation
In `check_microblock_header_signer` / `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs`), require that the two headers represent a genuine conflict before accepting the report: assert `mblock_header_1 != mblock_header_2`, and require `mblock_header_1.prev_block == mblock_header_2.prev_block && mblock_header_1.sequence == mblock_header_2.sequence` (mirroring the real-fork definition already used in `validate_parent_microblock_stream`), rejecting the transaction otherwise. This check must be enforced in the consensus-critical path (`transactions.rs`/`handle_poison_microblock`), not only in the mempool admission gate.

### Proof of Concept
Rust integration test plan (added alongside existing `process_poison_microblock_*` tests in `stackslib/src/chainstate/stacks/db/transactions.rs`):
1. Set up a chainstate/`TestChainstateBuilder` as in `process_poison_microblock` tests; insert a `block_pubkh` at height 1 via `StacksChainState::insert_microblock_pubkey_hash`.
2. Create exactly ONE signed microblock header `H = make_signed_microblock(&block_privk, &privk, BlockHeaderHash([0x11;32]), 123)` — i.e., only one microblock is genuinely produced/signed by the miner.
3. Build `TransactionPayload::PoisonMicroblock(H.header.clone(), H.header.clone())`, sign with an unrelated `reporter_privk`, and call `StacksChainState::process_transaction`.
4. Assert (bug reproduction): `process_transaction` returns `Ok(..)`, `get_poison_microblock_report(&mut conn, 1)` returns `Some((reporter_addr, 123))`.
5. Assert on the broken equality directly: no second distinct header (`H2 != H`) was ever produced/signed by the miner, yet the poison report equals `Some(...)` — i.e., `report_opt.is_some()` while `"only one microblock was signed"` is true, demonstrating that `reward paid to reporter` does not imply `miner signed two distinct microblocks at the same sequence`.
6. (Correct/fixed behavior assertion) After applying the recommended fix requiring `mblock_header_1 != mblock_header_2`, the same test should assert `process_transaction(...).unwrap_err()` with an error indicating the headers do not conflict.

                false,
            )

                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
