### Title
Platform-dependent `Math.pow` truncation divergence in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` causes consensus-splitting state divergence when strict-math hardening is disabled - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute `issuedSupply`/`exchangeBalance` as a `double` via `Maths.pow(...)` and then truncate it with `(long)` casts to derive `out`/`supply`/downstream `buyTokenQuant` [1](#0-0) . Whether the platform-independent `StrictMath.pow` path is used is gated by a `useStrictMath` boolean, and the legacy `MathWrapper.pow` implementations differ materially between architectures: the x86 variant is a thin wrapper over non-strict `Math.pow` [2](#0-1) , while the ARM variant returns hardcoded historical correction values from a lookup table for known-divergent `(a,b)` inputs and otherwise falls back to `StrictMath.pow` [3](#0-2) . The very existence of this hardcoded correction table (tied to specific historical mainnet block numbers, e.g. comments like `// 4137160(block)`) confirms that x86 `Math.pow` and ARM's `StrictMath.pow` fallback have historically produced bit-different results for the same mathematical inputs in this exact exchange-supply computation [4](#0-3) .

### Finding Description
The exchange computation is:
```
issuedSupply = -supply * (1.0 - pow(1.0 + quant/newBalance, 0.0005, useStrictMath));
out = (long) issuedSupply;
``` [5](#0-4) 

When `useStrictMath` is false (default network posture, per the question's precondition that the corresponding dynamic-property hardening flag is `0`), the pow calculation for a given `(quant, newBalance)` pair can, on the boundary between two adjacent binary64 representable results, resolve to a value on one side of an integer boundary on x86 (`Math.pow`, which is permitted by the JLS to differ from `StrictMath.pow` by up to 1 ULP and may use hardware FPU instructions) and to a value on the other side of that boundary on ARM nodes for any `(a,b)` pair not present in the hardcoded `powData` table baked in from *previously observed* mainnet divergences [6](#0-5) . Because the truncating `(long)` cast is not monotonic-safe across a ±1 ULP difference straddling an integer, this yields a different `out` (and therefore different `supply` state and different `buyTokenQuant` from the subsequent `exchangeFromSupply` call) on x86 vs. ARM validators processing the identical transaction and identical prior state [7](#0-6) .

The attack surface is trivially reachable: any funded account can broadcast an `ExchangeTransactionContract` with attacker-chosen `quant`, processed by `AbstractExchangeActuator`/`ExchangeTransactionActuator`, which construct `ExchangeProcessor` and invoke `exchange()` — none of the standard checks (`validateSignature`, permission weights, `DecodeUtil.addressValid`, actuator `validate()`, `ForkController`, bandwidth/energy accounting) address floating-point cross-platform determinism; they only validate account ownership, balances, and basic parameter sanity, not the numerical determinism of the pow computation.

The lookup table itself is retroactive: it hardcodes fixes only for `(a,b)` pairs already observed to diverge on real mainnet blocks (evidenced by block-number comments in the ARM file). Any *new* `quant`/`balance` ratio not already cataloged, deliberately chosen near a rounding boundary, is not protected by this table, and — with hardening flags at their documented default of `0` — the code still exercises this legacy non-strict path.

### Impact Explanation
This directly matches TRON's "state/receipt divergence across nodes" consensus-divergence impact class: a mixed-architecture fleet of full nodes/witnesses would compute different `Exchange` capsule state (`supply`, `balance`, transaction receipt `exchangeReceivedAmount`) for the same block, causing block-hash/state-root mismatches and a chain split without any malicious peer, leaked key, or privileged role — only an ordinary funded account broadcasting one signed transaction with a carefully chosen `quant`.

### Likelihood Explanation
Preconditions are exactly as scoped: `allowHardenExchangeCalculation()==0` and `allowStrictMath()==0` are the documented defaults, and the fleet naturally contains both x86 and ARM nodes (the codebase ships separate `platform/.../arm` and `platform/.../x86` `MathWrapper` implementations specifically because this is a known operational reality). Cost to the attacker is a single ordinary `ExchangeTransactionContract` transaction fee; no elevated access is required. Finding a concrete divergent `quant` requires offline floating-point analysis (bisecting `Math.pow` vs `StrictMath.pow` outputs near an integer boundary for the specific `0.0005`/`2000.0` exponents used here), which is a bounded, repeatable, purely computational search — not reliant on chain state races.

### Recommendation
- Make strict, platform-independent math mandatory for all exchange calculations regardless of dynamic-property state (i.e., always use `StrictMath.pow`/`StrictMathWrapper`, never gate this behind an opt-in hardening flag with a `0` default), removing the legacy `MathWrapper`/`useStrictMath=false` code path entirely from consensus-critical code.
- Delete or fully disable the deprecated `MathWrapper.pow` non-strict path so it cannot be reached from any actuator, rather than relying on a reactive hardcoded correction table for already-observed divergences.
- Add deterministic fixed-point (BigDecimal/BigInteger) arithmetic for exchange-supply math instead of double-precision floating point, eliminating platform-dependent floating-point semantics altogether.

@Test

  long balance = BALANCE_NEAR_BOUNDARY;
  long quant = QUANT_TUNED_TO_ULP_BOUNDARY; // found via offline search

  // x86 path: useStrictMath=false -> legacy Math.pow semantics
  ExchangeProcessor x86Proc = new ExchangeProcessor(supply, false);
  long outX86 = x86Proc.exchange(balance, balance, quant);

  // ARM path simulated: legacy MathWrapper.pow with StrictMath.pow fallback
  // (reflection/JNI stub swap per the question's proof idea)
  ExchangeProcessor armProc = new ExchangeProcessor(supply, false /* but backed by ARM MathWrapper */);

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
```
