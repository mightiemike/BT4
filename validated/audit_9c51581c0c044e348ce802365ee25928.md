### Title
Webhook HMAC does not bind the `X-Shopify-Shop-Domain` header, allowing cross-tenant replay of an attacker's own valid webhook against a victim shop - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
This finding is the closest reachable analog in shopify-app-js to the Connext "Malicious Relayer can Replay Execute Calldata on Different Chains" bug class: a signature verifies the *payload*, but the *routing/destination identifier* that determines which tenant the request is applied to is not itself covered by the signature, so an attacker who can obtain one genuinely-signed message can redirect it to a different destination context.

### Finding Description
Webhook authenticity in `@shopify/shopify-api` is checked by `validateHmacFromRequestFactory` / `validateHmacString`, which computes an HMAC exclusively over `rawBody` using the app's `apiSecretKey`: [1](#0-0) 

The shop identity for the webhook, however, is read straight from the `X-Shopify-Shop-Domain` header (`WEBHOOK_HEADER_NAMES[...].domain`) and is **not** included as HMAC input: [2](#0-1) 

`validateFactory` only checks HMAC validity over the body and then separately checks that required headers (including domain) are *present*, not that they are cryptographically bound to the signed content: [3](#0-2) 

Downstream, `authenticateWebhookFactory` (shared shape across the Remix/React-Router adapters) trusts `check.domain` at face value to look up/create the offline session for that shop, and attaches a live authenticated `admin` API client bound to that shop's access token to the webhook context: [4](#0-3) [5](#0-4) 

Because the same app secret (`apiSecretKey`) is shared across all shops that install the app, and the HMAC input never incorporates the shop domain, **any body+HMAC pair that is valid for one merchant's webhook is also a valid HMAC for the identical body sent with a different `X-Shopify-Shop-Domain` header**. This is directly analogous to the Connext root cause: the signed artifact (`rawBody`/`transferId`) doesn't bind the destination (`domain`/`destinationDomain`), so a party who can control delivery of a genuinely-signed message (here: any user who can trigger a webhook for a shop they install the app on, or any component in the HTTP path able to view/replay traffic since HMAC secrets are shared and there's no per-request nonce/domain binding) can redirect the accepted, "authentic" message to act on a different shop's tenant context.

### Impact Explanation
An attacker who controls a shop with the app installed can trigger webhooks with attacker-chosen payload content (e.g., via `app/uninstalled`, custom app events, or any webhook whose body content the merchant/admin can influence), capture the genuine HMAC Shopify computed over that body, then resend the same body+HMAC to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header set to a victim shop. Since the app validates only body-vs-HMAC, the request passes validation, `check.domain` is taken as the victim shop, `ensureValidOfflineSession` loads the *victim's* real offline session/access token, and the app's webhook handler executes with the victim shop's authenticated `admin` client and shop-scoped business logic — a cross-tenant compromise. The severity depends on what webhook handlers do with `shop`/`payload`, but at minimum it breaks the trust boundary between tenants that the domain header is assumed to establish.

### Likelihood Explanation
Requires only a single merchant that can install the app (to generate a "genuine" HMAC over attacker-influenced body content) — no privileged access or secret leakage needed. It does not require MITM of Shopify's real webhook delivery; the attacker crafts and sends their own POST directly to the app's public webhook endpoint, since that endpoint is a plain HTTP handler reachable by anyone (there's no requirement the request actually come from Shopify's IPs and no destination-domain binding in the signature). This meets the "concrete forged/accepted Shopify request causing cross-tenant access" bar.

### Recommendation
Include the shop domain (and ideally the webhook topic/id) as part of the HMAC-covered material, or otherwise cryptographically bind `X-Shopify-Shop-Domain` to the signed payload before trusting it to select which tenant's session to load. At minimum, apps should not assume `check.domain` is trustworthy purely because `rawBody` HMAC validated; the shopify-api library should either canonicalize domain+body together before hashing, or provide explicit guidance/enforcement that consumers must verify the returned `domain` against an expected/allow-listed value tied to how the webhook was routed (e.g. matching the URL's `shop` param registered at subscription time), analogous to Connext's recommended fix of validating destination domain against `s.domain` inside `_executeSanityChecks`.

### Proof of Concept
1. Install the target app on Shop A (attacker-controlled).
2. Trigger a webhook topic whose body content is attacker-influenced (e.g. a custom/GDPR webhook, or any topic where resource content can be set by the attacker on their own shop) and capture the resulting `rawBody` and `X-Shopify-Hmac-Sha256` value that Shopify computed and sent to the app's webhook endpoint.
3. Replay a POST to the same app webhook endpoint with the identical `rawBody` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and matching topic/webhook-id headers as needed).
4. Because `validateHmacFromRequestFactory` only checks `rawBody` against `X-Shopify-Hmac-Sha256` [6](#0-5) , validation succeeds; `authenticateWebhookFactory` then loads Shop B's real offline session via `ensureValidOfflineSession(params, check.domain)` and executes the handler with Shop B's authenticated `admin` client [7](#0-6) , demonstrating the cross-tenant execution.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
