## Title
Committee proposal quorum is computed against the *current* active-witness set at processing time rather than a snapshot tied to the proposal, letting the electorate silently change mid-vote - (File: `framework/src/main/java/org/tron/core/consensus/ProposalController.java`)

### Summary
The reported Maia bug is a class of governance flaw where the denominator/electorate used to compute a quorum is fetched live rather than snapshotted at proposal creation, so it drifts while the vote is open. Java-tron's on-chain committee-governance mechanism (`ProposalCreateContract` / `ProposalApproveContract`) has the analogous flaw: the set of witnesses whose approvals count toward quorum is re-fetched from `WitnessScheduleStore` at *processing* time, not fixed to the electorate that existed when the proposal was created or when individual approvals were cast.

### Finding Description
A proposal is created via `ProposalCreateActuator`, which only stores the parameters, creator, `createTime` and `expirationTime`; it does **not** snapshot which addresses were active witnesses at creation time [1](#0-0) . `proposalExpireTime` defaults to 3 days (`259200000` ms) while the active witness (SR) set is recomputed every maintenance cycle (`21600000` ms, i.e. every 6 hours) [2](#0-1) , meaning a proposal can outlive up to ~12 SR re-elections before it is finally processed.

Any registered witness (not necessarily a currently *active* top-27 SR) may add an approval to a proposal — `ProposalApproveActuator` only checks `witnessStore.has(ownerAddress)`, not whether the address is currently in the active set [3](#0-2) . Approvals are simply appended to `Proposal.approvals` [4](#0-3) .

At proposal-processing time (triggered deterministically at maintenance boundaries via `ProposalController.processProposals()`), the quorum check re-fetches the **current** active witness list and filters the recorded approvals against it:
```java
List<ByteString> activeWitnesses = this.manager.getWitnessScheduleStore().getActiveWitnesses();
if (proposalCapsule.hasMostApprovals(activeWitnesses)) { ... }
``` [5](#0-4) 

```java

    long count = this.proposal.getApprovalsList().stream()

    ...
    return count >= activeWitnesses.size() * 7 / 10;

``` [6](#0-5) 

The active-witness set itself is rewritten every maintenance cycle by `MaintenanceManager.doMaintenance()` → `DposService.updateWitness()`, which re-sorts all witnesses by vote count and keeps only the top `MAX_ACTIVE_WITNESS_NUM` [7](#0-6) [8](#0-7) .

This is structurally identical to the Maia finding: the code recomputes a governance denominator/electorate from *current* mutable state at evaluation time instead of freezing it relative to the proposal's lifecycle, so the outcome is not a faithful measure of the electorate's will at the time votes were cast.

### Impact Explanation
Because the electorate used for quorum counting is re-evaluated at processing time:
- Approvals legitimately cast by a witness while it was an active SR are silently discarded from the quorum count if that witness is later voted out of the top-27 before the proposal is processed (which can easily happen over a 3-day window with per-6-hour re-elections). This can flip an otherwise-passing governance/parameter proposal to `DISAPPROVED`, denying legitimate protocol/committee governance actions (fee schedules, energy pricing, TVM feature flags, etc. — set via `ProposalService.process`) without any actual malicious behavior.
- Conversely, a witness that was not part of the active set when other witnesses cast their approvals can join the active set later (through vote accumulation) and have its approval counted at processing time toward the 70% quorum, even though it was not part of the electorate that most of the votes were cast against — allowing coordinated SR churn near proposal-expiration boundaries to influence outcomes.

Since committee proposals govern critical, chain-wide economic and protocol parameters, this can cause governance results to diverge from the actual will of the electorate at any single point in time, effectively a form of governance-integrity/DoS issue reachable purely through ordinary broadcast transactions (`ProposalApproveContract`) combined with the deterministic (but non-snapshotted) witness-election process.

### Likelihood Explanation
Every full node executes `ProposalController.processProposal()` identically and deterministically at maintenance boundaries, so there is no consensus divergence between nodes — all nodes reach the same (flawed) outcome. The triggering condition (witness churn across a multi-day proposal window) is a completely ordinary, expected occurrence in DPoS operation (SR sets change routinely due to voting), so the scenario where legitimate approvals are dropped, or new entrants' approvals are unexpectedly counted, is likely to occur incidentally rather than requiring rare or attacker-crafted conditions. Deliberately timing SR vote swings to manipulate a specific proposal's outcome requires more effort but is technically feasible for well-resourced stakeholders.

### Recommendation
Snapshot the electorate relevant to a proposal instead of recomputing it at processing time:
- When a `ProposalCreateContract` is executed, store the active-witness list (or a reference to the witness-schedule epoch) valid at creation time as part of the `Proposal` protobuf.
- In `ProposalCapsule.hasMostApprovals`, use the snapshotted electorate rather than `WitnessScheduleStore.getActiveWitnesses()` fetched fresh in `ProposalController.processProposal`.
- Alternatively, require that a witness be part of the active set both when it casts an approval and re-validate approvals against the active set at each maintenance cycle so an outgoing witness's approval is proactively removed (rather than silently ignored) and stakeholders can react before the proposal is finally processed.

### Proof of Concept
1. Create a committee proposal (`ProposalCreateContract`) with `proposalExpireTime` spanning several maintenance cycles (default 3 days / ~12 cycles).
2. Have witness A (currently in the active top-27) approve via `ProposalApproveContract`; `Proposal.approvals` now includes A, and at that moment `hasMostApprovals` would count A toward quorum.
3. Wait for at least one maintenance cycle (`MaintenanceManager.doMaintenance()`), during which vote redistribution causes witness A to fall out of the top-27 (e.g. another candidate accumulates more votes) — this is normal DPoS churn, see `DposService.updateWitness` [8](#0-7) .
4. When `ProposalController.processProposal` finally runs at expiration, it calls `getActiveWitnesses()` again, which no longer contains A; A's earlier legitimate approval is filtered out of `hasMostApprovals`'s count [6](#0-5) , potentially causing a proposal that had genuine 70% support at the time of voting to be marked `DISAPPROVED`.
