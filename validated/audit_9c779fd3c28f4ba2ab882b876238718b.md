### Title
Greedy first-fit bin-packing in `PackedAncientStorage::pack` can consume more packed slots than `many_ref_accounts_can_be_moved` accounts for, letting a multi-ref account be written below its own live slot - (`accounts-db/src/ancient_append_vecs.rs`)

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` estimates how many packed ancient storages are required to hold the "newest alive" multi-ref (`ref_count > 1`) accounts, using a single `ceil(total_bytes / ideal_size)`-style formula, and only checks that the *lowest* of the top `required_ideal_packed` target slots is `>=` every candidate account's current slot. The actual packer, `PackedAncientStorage::pack`, is a strict first-fit greedy bin packer operating per-slot `AliveAccounts` group, which — for adversarially sized account groups — can require strictly more storages (bins) than the estimate. When that happens, a multi-ref account whose own slot check passed against the *estimated* boundary slot can end up placed in an actual output storage that maps to a target slot lower than its estimate, and potentially lower than its own current slot.

### Finding Description
In `many_ref_accounts_can_be_moved` [1](#0-0) , the required number of packed storages for the multi-ref "newest alive" accounts is computed purely from the *sum* of bytes across all `many_refs_newest` groups:
```
let required_ideal_packed = (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;
```
and only the boundary target slot at index `target_slots_sorted.len() - required_ideal_packed` is checked against every candidate's slot.

The real packer, `PackedAncientStorage::pack` [2](#0-1) , greedily fills one storage at a time using a **first-fit** strategy: it walks `AliveAccounts` groups (one group per originating slot) in order, and stops adding to the current storage as soon as the *next whole account* would exceed `ideal_size` (never splitting an account). This is textbook first-fit bin packing, which is known to sometimes require noticeably more bins than the ideal `ceil(total_bytes/bin_size)` estimate when item/group sizes are adversarially chosen relative to the bin capacity (e.g., items just over half the bin size, one per group, so the leftover capacity of each bin can never be reused for the next group).

Because `combine_ancient_slots_packed_internal` [3](#0-2)  and `write_packed_storages` [4](#0-3)  then zip `packed_contents` (in creation order, i.e. starting with the highest-slot multi-ref data first) against `target_slots_sorted.iter().rev()` (highest target slot first), any *extra* storage beyond what `many_ref_accounts_can_be_moved` assumed gets mapped to a target slot **lower** than the boundary slot that was validated. If that extra storage still contains part of the multi-ref "newest alive" data, the account can be rewritten to a slot below its own current (live) slot — exactly the situation the code comment at lines 879-885 warns must never happen: *"Moving it to a lower slot could move it before an alive or dead entry to this same account… This would fail the invariant that the highest slot # where an account exists defines the most recent account."* Unlike the `many_refs_old_alive` case, which is explicitly kept in place via `accounts_keep_slots`, the `many_refs_this_is_newest_alive` path relies solely on the (non-tight) bound in `many_ref_accounts_can_be_moved`, which does not model the packer's actual first-fit fragmentation behavior.

An unprivileged attacker fully controls the account keys, sizes, and write cadence needed to: (1) create the multiple slot-list entries required for `ref_count > 1` on chosen pubkeys, and (2) size each per-slot alive-account group so that first-fit fragmentation forces one extra storage beyond the estimate, while (3) picking slot values so the "extra" storage's mapped target slot falls below the account's own live slot but still passes the `many.slot <= highest_slot` check.

### Impact Explanation
If the greedy packer emits more storages than accounted for, the account is written to a target slot lower than its live slot. On the AccountsDB slot list, a lower-slot version of the account may then rank behind a stale/dead entry left in an older slot (or ahead of a still-existing entry it should not precede), causing the wrong version of the account to be treated as canonical after ancient packing. This is a silent, transaction-less account-state/hash divergence: capitalization, accounts-hash, or replay-vs-snapshot mismatches, without any privileged action. It falls under the AccountsDB "incorrect account state after clean/shrink/ancient-pack" bounty category.

### Likelihood Explanation
Exploitability requires: (a) the attacker's target accounts to age into "ancient" storages (this happens automatically through normal validator maintenance, not requiring privileged control), and (b) crafting per-slot alive-account byte totals relative to the dynamically-computed `ideal_storage_size` (derived from total ancient alive bytes / `max_ancient_slots`, both largely inferable/predictable from public ledger state) so that first-fit fragmentation forces an extra bin. This is a non-trivial but fully deterministic combinatorial construction reproducible in a unit test (as the existing test suite already directly drives `calc_accounts_to_combine`, `many_ref_accounts_can_be_moved`, and `PackedAncientStorage::pack` without needing a live cluster). In production it would require sustained account resizing/churn across several epochs to get multiple crafted-size ancient slots aligned, making it feasible but not trivial to land on the very first attempt.

### Recommendation
Replace the aggregate-byte estimate in `many_ref_accounts_can_be_moved` with a check that mirrors the actual packer output: run (or a cheap simulation of) `PackedAncientStorage::pack` over `many_refs_newest` first, and then verify — per resulting packed storage — that the target slot it will actually be assigned (by position in `target_slots_sorted.iter().rev()`) is `>=` the maximum slot of any account placed in that storage. Alternatively, make the packer slot-aware: never coalesce multiple `AliveAccounts` groups whose required target-slot assignment could regress below any of their own current slots, i.e., verify post-pack (before `write_packed_storages`) that for every account originating from a `many_refs_newest` group, its computed destination slot is `>=` its original slot, and abort/no-op the whole `combine_ancient_slots_packed_internal` call otherwise (the way it already aborts on `many_ref_accounts_can_be_moved` returning `false`).

### Proof of Concept
Add a property/unit test alongside `test_calc_accounts_to_combine_many_refs` / `test_many_ref_accounts_can_be_moved` in `accounts-db/src/ancient_append_vecs.rs`:

1. Construct `ideal_storage_size = 1000`.
2. Construct three `AliveAccounts` many-refs-newest groups, each containing exactly one account, sized ~600 bytes, at slots `300`, `200`, `100` (descending, matching the sort order used before `many_ref_accounts_can_be_moved`/`pack` are called).
3. Compute `required_ideal_packed = (1800/1000)+1 = 2`.
4. Construct `target_slots_sorted = [10, 250, 260, 270]` (ascending) so that `i_last = 4-2 = 2`, `highest_slot = 260`, and all three accounts' slots (300 fails naturally — use slots `255, 240, 100` instead to make the check pass while still exceeding the storage estimate) satisfy `<= 260`.
5. Assert `AccountsDb::many_ref_accounts_can_be_moved(&many_refs_newest, &target_slots_sorted, &tuning)` returns `true`.
6. Call `PackedAncientStorage::pack(many_refs_newest.iter(), tuning.ideal_storage_size)` and assert `result.len() > required_ideal_packed` (demonstrating the fragmentation).
7. Simulate `write_packed_storages`'s zip logic (`target_slots_sorted.iter().rev().zip(result)`) and assert that the storage holding the account at slot `255` maps to a target slot `< 255`, violating the "must move to slot >= own slot" invariant documented at lines 386-389 and 879-885.

Expected result: step 6/7 assertions succeed today, proving the estimate in `many_ref_accounts_can_be_moved` is not tight against the real packer, and that a multi-ref account can be assigned a destination slot lower than its own live slot despite passing the guard check.

    fn many_ref_accounts_can_be_moved(
        many_refs_newest: &[AliveAccounts<'_>],
        target_slots_sorted: &[Slot],
        tuning: &PackedAncientStorageTuning,
    ) -> bool {
        let alive_bytes = many_refs_newest
            .iter()
            .map(|alive| alive.bytes)
            .sum::<usize>();
        let required_ideal_packed = (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;
        if alive_bytes == 0 {
            // nothing required, so no problem moving nothing
            return true;
        }
        if target_slots_sorted.len() < required_ideal_packed {
            return false;
        }
        let i_last = target_slots_sorted
            .len()
            .saturating_sub(required_ideal_packed);

        let highest_slot = target_slots_sorted[i_last];
        many_refs_newest
            .iter()
            .all(|many| many.slot <= highest_slot)
    }

impl<'a> PackedAncientStorage<'a> {
    /// return a minimal set of 'PackedAncientStorage's to contain all 'accounts_to_combine' with
    /// the new storages having a size guided by 'ideal_size'
    fn pack(
        mut accounts_to_combine: impl Iterator<Item = &'a AliveAccounts<'a>>,
        ideal_size: NonZeroU64,
    ) -> Vec<PackedAncientStorage<'a>> {
        let mut result = Vec::default();
        let ideal_size: u64 = ideal_size.into();
        let ideal_size = ideal_size as usize;
        let mut current_alive_accounts = accounts_to_combine.next();
        // starting at first entry in current_alive_accounts
        let mut partial_inner_index = 0;
        // 0 bytes written so far from the current set of accounts
        let mut partial_bytes_written = Saturating(0);
        // pack a new storage each iteration of this outer loop
        loop {
            let mut bytes_total = 0usize;
            let mut accounts_to_write = Vec::default();

            // walk through each set of alive accounts to pack the current new storage up to ideal_size
            let mut full = false;
            while !full && current_alive_accounts.is_some() {
                let alive_accounts = current_alive_accounts.unwrap();
                if partial_inner_index >= alive_accounts.accounts.len() {
                    // current_alive_accounts have all been written, so advance to next set from accounts_to_combine
                    current_alive_accounts = accounts_to_combine.next();
                    // reset partial progress since we're starting over with a new set of alive accounts
                    partial_inner_index = 0;
                    partial_bytes_written = Saturating(0);
                    continue;
                }
                let bytes_remaining_this_slot =
                    alive_accounts.bytes.saturating_sub(partial_bytes_written.0);
                let bytes_total_with_this_slot =
                    bytes_total.saturating_add(bytes_remaining_this_slot);
                let mut partial_inner_index_max_exclusive;
                if bytes_total_with_this_slot <= ideal_size {
                    partial_inner_index_max_exclusive = alive_accounts.accounts.len();
                    bytes_total = bytes_total_with_this_slot;
                } else {
                    partial_inner_index_max_exclusive = partial_inner_index;
                    // adding all the alive accounts in this storage would exceed the ideal size, so we have to break these accounts up
                    // look at each account and stop when we exceed the ideal size
                    while partial_inner_index_max_exclusive < alive_accounts.accounts.len() {
                        let account = alive_accounts.accounts[partial_inner_index_max_exclusive];
                        let account_size = account.stored_size();
                        let new_size = bytes_total.saturating_add(account_size);
                        if new_size > ideal_size && bytes_total > 0 {
                            full = true;
                            // partial_inner_index_max_exclusive is the index of the first account that puts us over the ideal size
                            // so, save it for next time
                            break;
                        }
                        // this account fits
                        partial_bytes_written += account_size;
                        bytes_total = new_size;
                        partial_inner_index_max_exclusive += 1;
                    }
                }

                if partial_inner_index < partial_inner_index_max_exclusive {
                    // these accounts belong in the current packed storage we're working on
                    accounts_to_write.push((
                        alive_accounts.slot,
                        // maybe all alive accounts from the current or could be partial
                        &alive_accounts.accounts
                            [partial_inner_index..partial_inner_index_max_exclusive],
                    ));
                }
                // start next storage with the account we ended with
                // this could be the end of the current alive accounts or could be anywhere within that vec
                partial_inner_index = partial_inner_index_max_exclusive;
            }
            if accounts_to_write.is_empty() {
                // if we returned without any accounts to write, then we have exhausted source data and have packaged all the storages we need
                break;
            }
            // we know the full contents of this packed storage now
            result.push(PackedAncientStorage {
                bytes: bytes_total as u64,
                accounts: accounts_to_write,
            });
        }
        result
    }
