### Title
Missing chain-domain separation in `ValidateMultiSign`/`BatchValidateSign` precompile digests enables cross-network signature replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `validatemultisign` TVM precompile (address `0x...0a`) computes the digest that off-chain signers must sign as `sha256(address || permissionId || data)`, with no chain identifier, network magic, or contract-instance salt folded in. Any TRON-compatible network that shares the same account address space (mainnet, Nile/Shasta testnets, or any forked/CREATE2-deployed dApp reusing the same bytecode and account permission layout) can have a signature produced for one network's contract replayed verbatim on another, exactly the domain-separation gap described in the external report for `UniswapV4KEMHook`/`PancakeSwapInfinityKEMHook`.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` builds:
```
byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(..., combine);
``` [1](#0-0) 
then recovers each signer address via `recoverAddrBySign(sign, hash)` and checks its weight against the on-chain `Permission` for `address`/`permissionId` before returning success. [2](#0-1) 

This is the exact off-chain-signature verification primitive many TVM smart contracts (meta-transaction relayers, game-move authorizers, oracle feeds, cross-app authorization flows) rely on to accept a signed payload from a user without an on-chain transaction. The digest tuple committed to is only `(address, permissionId, data)` — there is no `chainid`-equivalent, no genesis-block hash, and no contract-instance identifier baked into the hash. `BatchValidateSign` has the identical property: the digest `hash` used for signature recovery is passed in raw by the caller with zero enforced domain binding. [3](#0-2) 

Because a TRON account's address is derived purely from its public key and is identical across every TRON-protocol network (mainnet, testnets, and any private/forked deployment sharing the same genesis parameters), and because contract bytecode calling this precompile can be deployed at the same logical position on multiple networks, any signed payload `(address, permissionId, data)` valid on network A recovers to the same signer and passes the same weight/threshold check on network B, as long as the target account has an equivalent `Permission` configured there.

### Impact Explanation
A dApp built on top of `validatemultisign`/`batchvalidatesign` to accept off-chain-signed authorizations (the intended use case per TIP-854/TVM docs) has no cryptographic way to prevent a valid signature collected on one TRON-compatible network from being replayed on another. This directly enables unauthorized execution of the signed action (fund transfers, order fills, permissioned state changes) on the second network — an "unauthorized account operation" / "asset or accounting corruption" outcome reachable purely by a contract call using a signature obtained from a different deployment, with no privileged access required.

### Likelihood Explanation
Exploitability depends on an application built atop this precompile being deployed to more than one TRON-protocol network (or contract instance) with the same or predictable account permission setup, and reusing off-chain-signed payloads across them — a realistic pattern for dApps deploying identical bytecode to mainnet and testnet, or to multiple TRON-derived chains. The precompile itself performs no chain binding, so the vulnerability is present in the core VM regardless of any specific dApp's mitigations.

### Recommendation
Fold a domain separator into the digest computed by `ValidateMultiSign`/`BatchValidateSign` — e.g. mix in the chain's genesis block hash or a dedicated `chainId`-equivalent constant, and consider binding the calling contract's own address — so that a digest recovered by `recoverAddrBySign` cannot be valid across two different deployments/networks. Alternatively, document explicitly that callers of this precompile are responsible for including their own domain separator inside `data`, and that TVM provides no default protection against cross-chain/cross-instance replay.

### Proof of Concept
1. Deploy an identical TVM contract (e.g., a game or payment relayer) at address `X` on TRON mainnet and on TRON Nile testnet (or any second TRON-protocol network), both using the same account `A` with an `active` `Permission` (id=2) containing signer key `K`.
2. Off-chain, `K` signs a payload for `data = sha256(move_or_order_bytes)` intended for use on mainnet via `validatemultisign(A, 2, data, [sig])`. This produces `sig` over `hash = sha256(A || 2 || data)`. [4](#0-3) 
3. An attacker observes `sig` (e.g. from a mainnet transaction log) and submits it in a call to the identically-deployed contract on Nile testnet with the same `data`.
4. Because `hash` depends only on `(address, permissionId, data)` and account `A`/permission id=2/key `K` are identical on both networks, `recoverAddrBySign` recovers `K`'s address, the weight check passes, and the contract on Nile testnet executes the authorized action without the signer ever intending to authorize it there. [5](#0-4)
