## Finding

### Title
Replay/state-sync verification of `TransactionInfoV1` ignores checkpoint hashes, letting a corrupted state/hot-state/position root pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to check that a transaction output produced by re-execution actually matches an authenticated `TransactionInfo` fetched with a proof (used by the chunk executor during state-sync/replay, the debugger, the CLI, and `replay_on_archive`). Its own doc comment admits it does not check the checkpoint-hash fields of `TransactionInfoV1`.

### Finding Description
`ensure_match_transaction_info` verifies transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against a supplied `TransactionInfo`, but explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`: [1](#0-0) 

This is analogous to the DODO bug: the code is meant to authenticate an "amount received"/"result produced" against an expected reference, but checks the wrong (or an incomplete) subset of fields, so a divergence that should be caught silently passes. Here, the field that actually carries the authenticated Merkle-committed state root for the position/native-trading subsystem and the hot-state subsystem (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash` in `TransactionInfoV1`) is not part of the equality check performed when accepting a chunk's transaction outputs as matching the accumulator-proved `TransactionInfo`.

This function is invoked from the chunk executor path used during state-sync/replay: [2](#0-1) 

as well as `aptos-debugger`, `cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs` — i.e. tooling and state-sync verification that consumes `TransactionOutputListWithProofV2`/`TransactionListWithProofV2` and is supposed to detect divergence between locally re-computed output and the authenticated, accumulator-proved `TransactionInfo`.

The relevant feature flags document that these checkpoint hashes are meant to be committed to the ledger and consensus-verified: [3](#0-2) 

### Impact Explanation
If `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` are enabled and a node's local hot-state or native-position (order book/collateral) state root diverges from what was actually committed (e.g., due to a local bug, non-determinism, or a malicious/corrupted state-sync source), `ensure_match_transaction_info` — the only integrity check gluing re-executed output to the authenticated, Merkle-proved `TransactionInfo` in these paths — would report success even though the state diverges from the correct, consensus-committed value. This means a corrupted hot-state or position-state root can be silently accepted during replay-verification/state-sync/chunk execution, which is a proof-integrity/state-commitment gap directly in scope of "committed state that differs from the correct VM result" and "wrong ... state proof accepted as valid." The code's own comment confirms the exact mechanism and names `db-tool`'s `replay_on_archive` as one affected consumer, but the same `ensure_match_transaction_info` call also gates chunk execution correctness in `execution/executor/src/chunk_executor/mod.rs`.

### Likelihood Explanation
The gap is real and directly acknowledged in the source as an unfinished TODO ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), meaning the guarded features are presumably not yet fully enabled on mainnet. I could not fully confirm within the remaining iterations whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are actually active in production today, nor whether an independent checkpoint-hash comparison exists elsewhere in the live consensus commit path (`do_state_checkpoint.rs`) that would compensate for this gap in the normal (non-replay) commit flow. This uncertainty affects whether the impact is exploitable today versus latent/future-risk once these flags are turned on.

### Recommendation
Extend `ensure_match_transaction_info` (and any equivalent check used by the chunk executor / replay tooling) to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed output and the authenticated `TransactionInfo`, gated appropriately behind the corresponding feature flags, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet.

### Proof of Concept
Not independently reproducible from static analysis alone: the concrete trigger requires the on-chain features `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, and/or `COMPUTE_TRADING_NATIVE_STATE_ROOTS` to be active, plus a scenario where local re-execution's hot-state or native-position root diverges from the proved `TransactionInfoV1` (e.g. during chunk replay/state-sync bootstrapping). Given tool-call limits, I was not able to confirm the current on-chain activation state of these flags or find a compensating check in `do_state_checkpoint.rs`; this should be verified with further investigation (e.g., a Devin session with full repo access) before treating this as confirmed-exploitable versus a documented latent gap.
