### Title
Fulfillment-service `validate()` does not bind the HMAC to `X-Shopify-Shop-Domain`, allowing shop-header spoofing on an otherwise validly-signed request - (File: packages/apps/shopify-api/lib/fulfillment-service/validate.ts)

### Summary
`validate()` in `fulfillment-service/validate.ts` only verifies that the HMAC over the raw request body matches a value computed with the app's secret; it never checks that the `X-Shopify-Shop-Domain` header is consistent with, or covered by, that signature. Downstream, `authenticateFulfillmentServiceFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts` (and the equivalent `shopify-app-react-router` file) trusts this unverified header value directly to look up the offline session used to build the `admin` API client, so the shop identity used for authorization is not bound to the cryptographic signature.

### Finding Description
`validateFactory` calls `validateHmacFromRequestFactory(config)` with `HmacValidationType.FulfillmentService` and the `rawBody`/adapter args. [1](#0-0) 

`validateHmacFromRequestFactory` computes `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` using only the request body and the `X-Shopify-Hmac-Sha256` (or webhook-type-specific) header — it never reads, or factors in, `ShopifyHeader.Domain`. [2](#0-1) 

After `validate()` returns `valid: true`, the caller extracts the shop purely from the unauthenticated header and uses it to fetch a session and build an authenticated admin client: [3](#0-2) 

Because the HMAC only covers the body, an attacker who is able to obtain (or legitimately receive, e.g. to their own installed app instance) one validly-HMAC'd fulfillment/flow request can retransmit it to the shared app endpoint after rewriting `X-Shopify-Shop-Domain` to a different, victim shop. The signature still validates (it never covered the header), `validate()` returns `valid: true`, and `ensureValidOfflineSession(params, shop)` is called with the attacker-chosen shop value, potentially returning the victim's offline session/access token to be used for the `admin` client built from that forged request.

### Impact Explanation
This breaks the intended invariant that shop identity is cryptographically bound to the verified signature. If the app maintaining sessions for multiple shops receives a replayed/rewritten payload, the fulfillment-service handler will act using another tenant's offline session — a cross-tenant webhook/action confusion consistent with the "cross-tenant webhook action" impact class described in the audit.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly-signed fulfillment-service/Flow payload for some shop the app secret was used to sign — practically obtainable only from a shop where the app is legitimately installed (their own tenant), since `apiSecretKey` is never exposed. The attack itself (retransmitting the body with a rewritten `X-Shopify-Shop-Domain` header) is simple and fully repeatable once such a payload is captured, and no other check in `validate()` or the authenticate wrapper cross-validates the header against the signed content.

### Recommendation
Include the shop domain (and/or topic) as part of the data that is HMAC-verified, or independently verify that the `X-Shopify-Shop-Domain` header matches a shop-identifying field carried inside the signed body/payload before using it to resolve a session. At minimum, reject requests where the header-derived shop does not match an expected/allow-listed value tied to the signature.

### Proof of Concept
```ts
// Jest-style PoC illustrating the missing binding
import {validateHmacFromRequestFactory} from '../../utils/hmac-validator';
import {createSHA256HMAC} from '../../../runtime/crypto';
import {HashFormat} from '../../../runtime/crypto/types';

test('valid HMAC accepted regardless of shop header', async () => {
  const rawBody = JSON.stringify({kind: 'fulfillment_order_notification'});
  const hmac = await createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64);

  const request = buildMockRequest({
    method: 'POST',
    body: rawBody,
    headers: {
      'X-Shopify-Hmac-Sha256': hmac,
      'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // attacker-chosen, unsigned
    },
  });

  const result = await validateHmacFromRequestFactory(config)({
    type: HmacValidationType.FulfillmentService,
    rawBody,
    rawRequest: request,
  });

  expect(result.valid).toBe(true); // passes even though shop header is unverified
});
```
Swapping `X-Shopify-Shop-Domain` to any value leaves `result.valid === true`, confirming the shop header is not covered by the HMAC and is trusted downstream by `authenticateFulfillmentServiceFactory` for session lookup. [4](#0-3)

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}
