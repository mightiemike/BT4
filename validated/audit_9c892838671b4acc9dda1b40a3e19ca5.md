### Title
Witness rewards accrued during a zero-vote cycle become permanently unclaimable ("stuck emissions") - (File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
java-tron's DPoS reward-distribution model pays a witness's block/transaction-fee rewards into a per-cycle reward bucket unconditionally, but converts that bucket into per-voter claimable value (`Vi`) only if the witness's recorded vote count for that cycle is non-zero. If a witness produces blocks (and therefore earns rewards) during a cycle in which its total vote count is `0`, the reward recorded for that cycle is silently discarded from the `Vi` accumulation and can never be attributed to, or withdrawn by, any voter — exactly analogous to the Y2K-Finance bug where a vault with `finalTVL == 0` causes allocated emissions to become permanently stuck.

### Finding Description
Witness rewards are accumulated per cycle via `MortgageService.payReward()`: [1](#0-0) 

This unconditionally calls `delegationStore.addReward(cycle, witnessAddress, value)` regardless of the witness's vote count for that cycle — block/tx-fee rewards accrue purely from block production, independent of vote totals.

The reward is later converted into a claimable share via the `Vi` (value-per-vote index) mechanism, computed in `DelegationStore.accumulateWitnessVi` (used by `MaintenanceManager.doMaintenance`) and equivalently in `RewardViCalService.accumulateWitnessVi`: [2](#0-1) 

When `voteCount == 0` for that cycle (the "nullified epoch" analog to zero TVL), the code takes the `reward == 0 || voteCount == 0` branch and simply **forwards the previous `Vi`** — the reward that was already recorded via `addReward` for this cycle is dropped from the delta-Vi computation and never distributed to anyone.

This is driven from `MaintenanceManager.doMaintenance()`: [3](#0-2) 

which calls `accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount())` using the witness's total vote count captured at that time, then only afterward updates `witnessVote` for the next cycle: [4](#0-3) 

Once `Vi` fails to record the delta for a cycle, all downstream claim paths that rely on `Vi` differences — `MortgageService.computeReward()` (new algorithm branch) and `VoteRewardUtil.computeReward()` (TVM precompiled/native contract path) — will compute `deltaVi.signum() <= 0` and simply `continue`, permanently skipping that cycle's reward: [5](#0-4) 

The legacy (pre new-algorithm) reward path has the identical skip-on-zero-vote logic: [6](#0-5) 

In both the old and new reward algorithms, there is no mechanism anywhere in the codebase (no "treasury sweep" / burn / redistribution function) that reclaims or redirects a cycle's reward once it has been recorded under `addReward` for a witness whose vote count is zero for that cycle. The value is simply orphaned in the `delegation` store forever — unlike a legitimate zero-vote witness that never earns block rewards in the first place, this is specifically the case where reward accrual (from block production / tx fees) and vote-count-based distribution become desynchronized within the same cycle.

### Impact Explanation
Any TRX reward minted/allocated to a witness for a cycle in which that witness's recorded vote total is `0` becomes permanently stuck: it can't be withdrawn by any voter (no voter has a positive `deltaVi` contribution) and there is no admin/treasury reclaim path. This is a reward-accounting corruption bug: value is recorded as paid out (via `addReward`) from the emission schedule, but is unspendable and unrecoverable, silently reducing the effective circulating incentive without any account ever being credited — a permanent loss of otherwise-claimable stake rewards.

### Likelihood Explanation
This state is reachable through ordinary, unprivileged user actions: a witness can remain in the active/standby SR set (and thus keep producing blocks and earning rewards) for a cycle immediately after all its voters withdraw votes (via `UnfreezeBalance`/`UnfreezeBalanceV2`/`VoteWitness` changing to another witness), since vote-count updates and reward accrual happen on different schedules (vote counts are only finalized at `doMaintenance()` cycle boundaries while rewards accrue continuously via block production). A witness can also be newly promoted to the active set with `0` recorded votes for its first cycle while still collecting fees from blocks it produces. No attacker privilege is required — only that normal vote/unfreeze transactions from any account temporarily zero out a witness's vote count while it is still producing blocks.

### Recommendation
When accumulating `Vi` in `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`, if `voteCount == 0` but `reward > 0`, do not silently discard the reward. Instead, either (a) route it to a recoverable pool (e.g., treasury/burn address) that can be swept by a defined mechanism, or (b) carry it forward and add it to the next cycle in which the witness has a non-zero vote count, so it eventually becomes distributable, mirroring the recommended fix in the referenced report (explicit handling of the "nullified" zero-denominator case instead of dropping the value).

### Proof of Concept
1. Witness `W` is part of the active/standby set and produces a block in cycle `N`; `MortgageService.payBlockReward`/`payTransactionFeeReward` → `payReward` calls `delegationStore.addReward(N, W, value)` (value > 0) even though the last recorded vote total for `W` in cycle `N` is `0` (e.g., because all voters unfroze/switched votes at the end of cycle `N-1`, right after `doMaintenance()` recorded `witnessVote(N, W) = 0` via `setWitnessVote`).
2. At the next `doMaintenance()` boundary (start of cycle `N+1`), `accumulateWitnessVi(N, W, witness.getVoteCount())` is invoked with `voteCount == 0`; per `DelegationStore.accumulateWitnessVi` (lines 133-146), the `reward == 0 || voteCount == 0` branch is taken and `Vi(N, W)` is simply set to `Vi(N-1, W)` — the reward recorded in step 1 is never reflected in `Vi`.
3. Any voter later computing rewards via `MortgageService.computeReward` (or the TVM `VoteRewardUtil.computeReward`) for a range spanning cycle `N` gets `deltaVi = Vi(N) - Vi(N-1) = 0`, so no reward is attributed to them for that cycle, even though `getReward(N, W)` in the store shows a nonzero recorded reward.
4. No function exists to reclaim `getReward(N, W)` to a treasury/burn account or redistribute it — the value is permanently orphaned.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
