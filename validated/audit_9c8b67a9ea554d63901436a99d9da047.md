### Title
Exchange pool ratio skew can permanently block ExchangeInject/ExchangeWithdraw via a squeezed valid-quantity window - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator` (and analogously `ExchangeWithdrawActuator`) enforces two independent bounds on the computed counter-token amount: it must be `> 0` and the resulting pool balances must not exceed `dynamicStore.getExchangeBalanceLimit()`. When an unprivileged trader skews a Bancor-style TRC10 exchange pool's token ratio to an extreme (via ordinary, permissionless `ExchangeTransactionContract` trades), these two bounds can become mutually exclusive for *every* possible input quantity, permanently blocking the pool's own liquidity-management operations — the same "squeeze" pattern described in the MuteBond report, where `maxDeposit()` collapses below the minimum non-zero-payout threshold.

### Finding Description
`ExchangeInjectActuator.doValidate()` computes the counter-token quantity using integer division and enforces both a lower and upper bound: [1](#0-0) 

- `anotherTokenQuant = bigOtherBalance * bigTokenQuant / bigThisBalance` (floor division) must be `> 0`.
- `newTokenBalance`/`newAnotherTokenBalance` must both be `<= balanceLimit` (`dynamicStore.getExchangeBalanceLimit()`).

The pool ratio (`firstTokenBalance` / `secondTokenBalance`) is fully attacker-controllable through repeated, permissionless calls to `ExchangeTransactionActuator`, which mutates the balances via `ExchangeCapsule.transaction()`: [2](#0-1) 

If an attacker skews the ratio so that one side (say `firstTokenBalance`) is close to `balanceLimit` while the other side (`secondTokenBalance`) is driven down to a very small value (e.g. `1`), then for the pool's own creator (the only account allowed to call `ExchangeInjectContract`, enforced at line `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`) every possible injection becomes invalid:
- Injecting the scarce token (`secondTokenID`) with any `tokenQuant >= 1` makes `anotherTokenQuant = floor(firstTokenBalance * tokenQuant / secondTokenBalance)` explode past `balanceLimit`, failing the upper-bound check.
- Injecting the abundant token (`firstTokenID`) with any `tokenQuant` small enough to stay under `balanceLimit` yields `anotherTokenQuant = floor(secondTokenBalance * tokenQuant / firstTokenBalance) = 0` (since `firstTokenBalance` is already near `balanceLimit`), failing the `> 0` check; and any `tokenQuant` large enough to produce `anotherTokenQuant > 0` necessarily pushes `newTokenBalance` over `balanceLimit`.

This creates an empty valid input range — exactly the MuteBond `maxDeposit() < 52` pattern, where the compounding of a strict lower bound (non-zero payout) and an upper bound (maxDeposit/balanceLimit) traps the contract in a state where no input satisfies both.

### Impact Explanation
The affected pool's creator becomes permanently unable to inject additional liquidity (and, by the same floor-division/precision logic, `ExchangeWithdrawActuator` can suffer analogous lockups) once an attacker skews the ratio near the chain-wide `ExchangeBalanceLimit`. This is a denial-of-service against ordinary, unprivileged exchange creators, triggerable purely through broadcast `ExchangeTransactionContract` transactions with no special permission required. Recovery requires either a network-wide `ExchangeBalanceLimit` parameter change (a committee/proposal action) or abandoning the exchange, mirroring the "admin must manually intervene" mitigation noted in the original MuteBond report. Trading itself (`ExchangeTransactionActuator`) is not blocked, so funds are not frozen, but pool liquidity management is denied — a medium-severity availability issue.

### Likelihood Explanation
Exchange creation and trading are both open, permissionless operations reachable from any account via ordinary broadcast transactions, so no privileged access is required to skew a pool's ratio. Achieving the extreme skew requires the attacker to move enough token supply through the pool (bounded by `ExchangeBalanceLimit` per direction and by the attacker's own token holdings), making this more feasible for lower-liquidity/newly created TRC10 exchange pools than for deep, well-capitalized ones.

### Recommendation
In `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, avoid combining a hard `> 0` floor-division requirement with a hard upper balance cap without ensuring a non-empty valid range exists; e.g., allow injecting via computing the *required* proportional amount with rounding that favors the injector, or expose a way to inject both sides simultaneously in exact ratio, or clamp/adjust `tokenQuant` rather than reject when the computed counter-quantity underflows to zero solely due to precision loss near the balance limit.

### Proof of Concept
1. Attacker creates or targets an existing low-liquidity TRC10 `Exchange` with `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Attacker repeatedly calls `ExchangeTransactionActuator` (`ExchangeTransactionContract`), selling the second token into the pool, driving `secondTokenBalance` down toward `1` while `firstTokenBalance` rises toward `dynamicStore.getExchangeBalanceLimit()` — each call validated only by the checks in [3](#0-2) , which do not prevent extreme ratio skew.
3. The exchange creator then attempts `ExchangeInjectContract` for either token:
   - Injecting `secondTokenID` with `tokenQuant = 1` computes `anotherTokenQuant = firstTokenBalance / secondTokenBalance ≈ balanceLimit`, failing `newAnotherTokenBalance > balanceLimit`.
   - Injecting `firstTokenID` with any `tokenQuant` small enough to respect `balanceLimit` computes `anotherTokenQuant = floor(secondTokenBalance * tokenQuant / firstTokenBalance) = 0`, failing `anotherTokenQuant <= 0` at [4](#0-3) .
4. Both branches revert for every possible `tokenQuant`, permanently blocking the creator's `ExchangeInjectContract` transactions until `ExchangeBalanceLimit` is raised via committee proposal.

    long buyTokenQuant = 0;

    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc

          : secondTokenBalance + sellTokenQuant;

      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
