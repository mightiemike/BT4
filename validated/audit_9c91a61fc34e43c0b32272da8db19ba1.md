### Title
Missing `EXECUTE_ENTRY_POINT_SELECTOR` restriction on `library_call` allows contracts to invoke `__execute__` outside the OS-controlled transaction execute phase - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The reported OptimismPortal bug relies on the fact that a caller-identity check (`msg.sender != tx.origin`) can be bypassed through a delegate-style call path that preserves the original caller's identity while routing through unintended logic. The sequencer OS contains a directly analogous protocol invariant: contracts are prevented from directly invoking another contract's `__execute__` entry point via `call_contract`, but this restriction is not enforced for the delegate-call-equivalent `library_call` syscall, which preserves both `caller_address` and `contract_address` from the calling context [1](#0-0) .

### Finding Description
In `execute_call_contract`, the OS explicitly forbids invoking the `EXECUTE_ENTRY_POINT_SELECTOR` selector through the `call_contract` syscall:
```
if (request.selector == EXECUTE_ENTRY_POINT_SELECTOR) {
    write_failure_response(remaining_gas=remaining_gas, failure_felt=ERROR_INVALID_ARGUMENT);
    return ();
}
``` [2](#0-1) 

This mirrors the identical check in the deprecated syscall path:
```
// It is forbidded to call the `__execute__` function.
assert_not_equal(call_contract_syscall.request.selector, EXECUTE_ENTRY_POINT_SELECTOR);
``` [3](#0-2) 

This invariant exists so that `__execute__` can only run as the top-level entry point invoked directly by the OS during the transaction's dedicated execute phase (with `caller_address = ORIGIN_ADDRESS`/zero and after fee/nonce checks have already run) - it is analogous to a `tx.origin`-style "must be the true top-level caller" guarantee that account contracts additionally self-enforce (e.g. `assert(starknet::get_caller_address().is_zero(), 'INVALID_CALLER')` in test account contracts) [4](#0-3) .

However, the same restriction is absent from `execute_library_call`, which implements the delegate-call-equivalent syscall. `library_call` preserves the caller's own `caller_address`, `contract_address`, and `tx_info`, changing only the `class_hash` used to resolve the code that executes against the caller's own storage:
```
execution_info=new ExecutionInfo(
    block_info=caller_execution_info.block_info,
    tx_info=caller_execution_info.tx_info,
    caller_address=caller_execution_info.caller_address,
    contract_address=caller_execution_info.contract_address,
    selector=request.selector,
),
``` [5](#0-4) 

No check comparable to `request.selector == EXECUTE_ENTRY_POINT_SELECTOR` exists in this function, nor in its dispatch entry `execute_library_call{...}(block_context, caller_execution_context)` [6](#0-5) . The same gap exists in the deprecated `execute_library_call_syscall` function used by Cairo0 contracts, which likewise omits the `EXECUTE_ENTRY_POINT_SELECTOR` block that is present for `CALL_CONTRACT_SELECTOR` handling in the same file [7](#0-6) , [8](#0-7) .

Because `caller_address` is preserved unchanged by `library_call` (unlike `call_contract`, which sets it to the caller's own address), any code path that already has `caller_address == 0` (e.g. `__validate__`, `__validate_declare__`, `__validate_deploy__`, or `__execute__` itself, all invoked by the OS with `caller_address = ORIGIN_ADDRESS`) can issue a `library_call` naming `EXECUTE_ENTRY_POINT_SELECTOR` and still satisfy an `assert(get_caller_address().is_zero())` guard inside the invoked class code, since that check only inspects `caller_address`, which the syscall did not alter. This lets a malicious account contract "impersonate" a legitimate top-level `__execute__` invocation from within a different phase of the same transaction (e.g. from `__validate__`), or invoke arbitrary class bytecode under the `__execute__` selector against its own storage outside of the OS-controlled execute phase that enforces fee charging and nonce increment ordering.

### Impact Explanation
This breaks the sequencer's protocol invariant that `__execute__` may only run as the OS-driven top-level call of a transaction, after validation and nonce/fee accounting have completed. A malicious sender's own account contract could use `library_call` to trigger `__execute__`-labeled logic (of its own or a different declared class) from inside `__validate__`, out of the intended sequencing enforced elsewhere by the explicit `call_contract` selector block. This can lead to unauthorized/duplicated account action execution relative to what the OS/fee-accounting model assumes, potentially resulting in charge/nonce/fee-flow inconsistencies between the "expected" execution the OS models and what the account contract actually performs, i.e., honest-node/re-execution divergence risk for that transaction's outcome. This qualifies as Medium/High under the "unauthorized account action" / "honest-node divergence" categories in scope.

### Likelihood Explanation
The attacker only needs to deploy or declare an account/contract that calls `library_call` with `entry_point_selector = EXECUTE_ENTRY_POINT_SELECTOR` from within `__validate__` (or any other entry point invoked with `caller_address == 0`). This requires no privileged access — any unprivileged sender who declares/deploys such a contract and submits a normal transaction can reach this path, matching the "reachable from a single submitted transaction, declared class" requirement.

### Recommendation
Add the same restriction present in `execute_call_contract` to `execute_library_call` (and to the deprecated Cairo0 `execute_library_call_syscall`): reject/fail syscalls whose `entry_point_selector == EXECUTE_ENTRY_POINT_SELECTOR` (and consider also `VALIDATE`/`VALIDATE_DECLARE`/`VALIDATE_DEPLOY` selectors) uniformly across both the `call_contract` and `library_call` paths, so that the "top-level-only" invariant for these OS-orchestrated entry points cannot be bypassed by any syscall that preserves or forges a zero `caller_address`.

### Proof of Concept
Conceptual PoC (cannot be dynamically executed in this environment, but derivable from code paths cited above):
1. Deploy an account contract `A` whose `__validate__` entry point (invoked by the OS with `caller_address = ORIGIN_ADDRESS`) calls the `library_call` syscall with `class_hash = A`'s own class hash (or another declared class) and `function_selector = EXECUTE_ENTRY_POINT_SELECTOR`.
2. Because `execute_library_call` (`syscall_impls.cairo:240-282`) does not check the selector, and preserves `caller_address` from the calling context (still zero, since `__validate__` was invoked with `caller_address = ORIGIN_ADDRESS`), the inner call into `__execute__`-labeled code executes successfully, satisfying any `assert(get_caller_address().is_zero())` self-guard inside that code, exactly as if it were the OS's legitimate top-level `__execute__` invocation.
3. This lets contract `A` run `__execute__`-labeled logic during the validate phase, before fee/nonce accounting for the transaction has been finalized by the OS's normal execute-phase flow, deviating from the intended OS transaction lifecycle.

        specific_base_gas_cost=LIBRARY_CALL_GAS_COST, request_struct_size=LibraryCallRequest.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    // Prepare execution context.
    tempvar calldata_start = request.calldata_start;
    tempvar caller_execution_info = caller_execution_context.execution_info;

        entry_point_type=ENTRY_POINT_TYPE_EXTERNAL,
        class_hash=request.class_hash,
        calldata_size=request.calldata_end - calldata_start,

            tx_info=caller_execution_info.tx_info,

        deprecated_tx_info=caller_execution_context.deprecated_tx_info,
