I was unable to view the full body of `Context::feature_enabled` in `api/src/context.rs` before running out of iterations (I only confirmed its declaration exists there via `grep_search`), so I flag that specific piece as inferred-but-unverified. ### Title
API returns synthetic stateless-account data for historical ledger versions using the current feature-flag state instead of the version-pinned state - (File: `api/src/accounts.rs`)

### Summary
`Account::account()` in `api/src/accounts.rs` resolves account data for a given, client-specified `ledger_version`. When no `Account` resource exists in the version-pinned state, it falls back to checking whether `FeatureFlag::DEFAULT_ACCOUNT_RESOURCE` is enabled via `self.context.feature_enabled(...)`, and if so synthesizes an `AccountResource::new_stateless(...)`. This feature check is invoked without threading through `self.ledger_version`, the same version used moments earlier to fetch the actual state value, meaning the "is this account stateless" decision is made against a different (apparently latest/current) protocol configuration than the one that was authoritative at the queried, version-pinned ledger state.

### Finding Description
The relevant code path: [1](#0-0) 

`get_account_resource()` correctly retrieves the state value at `self.ledger_version` (the client-requested, version-pinned lookup). But when that lookup returns `None` (no `Account` resource at that historical version), the code asks `self.context.feature_enabled(FeatureFlag::DEFAULT_ACCOUNT_RESOURCE)` — a call that does not pass `self.ledger_version` or any version parameter — to decide whether to synthesize a fake `AccountResource::new_stateless(addr)` with `sequence_number = 0` and a default authentication key.

Compare this to the correctly version-scoped pattern used elsewhere in the same crate, where any state read is bound through `self.context.state_view(Some(self.ledger_version))`: [2](#0-1) 

The Move-VM side of the feature is correctly execution-scoped: `features::is_default_account_resource_enabled()` inside `account.move` and `Features::is_default_account_resource_enabled` in `types/src/on_chain_config/aptos_features.rs` are read from the on-chain `Features` resource as it existed at the executing block's state, so the *committed ledger state* itself is internally consistent per version: [3](#0-2) [4](#0-3) 

The bug is specific to the read-side API reconstruction: since `feature_enabled` is called without the pinned version, once `DEFAULT_ACCOUNT_RESOURCE` is toggled on governance-wide (a normal chain-upgrade event, not an operator mistake), every historical query for an address that had no `Account` resource at an *older* ledger version will incorrectly be answered as if that address existed as a stateless account at that older version — even though the actual, durable, committed state at that version had no such resource and the correct VM-observable answer would have been "account not found."

This affects both response encodings:
- JSON: `account_resource.into()` is built from the fabricated `AccountResource::new_stateless`.
- BCS: `bcs::to_bytes(&account_resource).unwrap()` synthesizes raw bytes that were never actually written to durable storage at that version, and this fabricated payload is returned tagged with `self.latest_ledger_info` headers (`X-APTOS-LEDGER-VERSION`, etc.), i.e. an authenticated response object bound to a specific (historical) ledger version while its content reflects the feature state at a different version. [5](#0-4) 

### Impact Explanation
This is a version-binding integrity defect in an authenticated API response: the response is labeled with a specific ledger version's headers, but its payload does not correspond to what was durably committed at that version. A consumer (indexer, wallet, historical audit tool, light client relying on the REST endpoint) querying an old `ledger_version` for an address that legitimately had no account resource at that time will receive a fabricated `AccountResource` (sequence number 0, synthetic auth key) instead of a `404 account not found`, corrupting the historically-reported account existence/shape relative to the true committed ledger state at that version. This falls under "Authenticated API or state-view output bound to the wrong version, object, or proof context" in the Required Impacts.

It does not, however, corrupt the actual Merkle/Jellyfish state, accumulator roots, or VM execution outputs — the underlying committed ledger data is untouched; only the API's synthetic reconstruction for missing-resource historical queries is affected.

### Likelihood Explanation
Any unprivileged actor can trigger this simply by querying `/accounts/{address}?ledger_version={old_version}` (or the BCS-encoded equivalent) for any address that never had an `Account` resource before `DEFAULT_ACCOUNT_RESOURCE` was enabled by governance. No malicious transaction, privileged access, or special crafting is required beyond normal read-only API usage after the feature flag transitions — which is an expected, planned chain-upgrade event (AIP-related stateless-account rollout), not an "operator mistake."

### Recommendation
Thread the version-pinned lookup through the feature check: obtain the `Features` on-chain config from the same versioned `state_view` used to fetch the `Account` resource (i.e., `self.context.state_view(Some(self.ledger_version))`) rather than calling `self.context.feature_enabled(...)` against the latest/current state. This ensures the "is address treated as a stateless account" decision is made using the same protocol configuration that was authoritative at the requested historical ledger version, keeping the API response consistent with what was actually committed at that version.

### Proof of Concept
1. Note an address `A` that has never submitted a transaction and has no `Account` resource, at a ledger version `V1` where `DEFAULT_ACCOUNT_RESOURCE` is disabled on-chain.
2. Let governance later enable `DEFAULT_ACCOUNT_RESOURCE` at version `V2 > V1`.
3. Query `GET /accounts/A?ledger_version=V1`.
4. Expected (per committed state at `V1`): `404` "account not found," since at `V1` neither an `Account` resource existed nor was the stateless-account feature active.
5. Actual (due to the code path above): the endpoint returns `200` with a synthesized `AccountData` (`sequence_number: 0`, default `authentication_key`) headers tagged with `X-APTOS-LEDGER-VERSION: V1`, because `feature_enabled(DEFAULT_ACCOUNT_RESOURCE)` reflects the *current* (post-`V2`) chain configuration rather than the state at `V1`.
6. This demonstrates the authenticated, version-labeled API response diverging from the true committed ledger state at the pinned version.

**Note on verification gap:** I could not directly inspect the body of `Context::feature_enabled` in `api/src/context.rs` before exhausting my tool budget; my conclusion that it queries current/latest state rather than the pinned `ledger_version` is inferred from the call site in `api/src/accounts.rs:280-284`, which passes no version argument, in contrast to the version-threaded pattern (`self.context.state_view(Some(self.ledger_version))`) used for the actual resource fetch in the same function and in `api/src/state.rs`. Confirming the exact implementation of `feature_enabled` would remove any remaining ambiguity.

    pub fn account(self, accept_type: &AcceptType) -> BasicResultWith404<AccountData> {
        // Retrieve the Account resource and convert it accordingly
        let state_value_opt = self.get_account_resource()?;

        let account_resource = if let Some(state_value) = &state_value_opt {
            let account_resource: AccountResource = bcs::from_bytes(state_value)
                .context("Internal error deserializing response from DB")
                .map_err(|err| {
                    BasicErrorWith404::internal_with_code(
                        err,
                        AptosErrorCode::InternalError,
                        &self.latest_ledger_info,
                    )
                })?;
            account_resource
        } else {
            let stateless_account_enabled = self
                .context
                .feature_enabled(
                    aptos_types::on_chain_config::FeatureFlag::DEFAULT_ACCOUNT_RESOURCE,
                )
                .context("Failed to check if stateless account is enabled")
                .map_err(|_| {
                    BasicErrorWith404::internal_with_code(
                        "Failed to check if stateless account is enabled",
                        AptosErrorCode::InternalError,
                        &self.latest_ledger_info,
                    )
                })?;
            if stateless_account_enabled {
                AccountResource::new_stateless(*self.address.inner())
            } else {
                Err(account_not_found(
                    self.address,
                    self.ledger_version,
                    &self.latest_ledger_info,
                ))?
            }
        };
