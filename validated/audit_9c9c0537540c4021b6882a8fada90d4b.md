### Title
Signature malleability in `ValidateMultiSign` precompile allows duplicate weight counting from a single key - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ECRecover`-equivalent signature-recovery helper used by TVM's `ValidateMultiSign` precompiled contract (address `0x...0a`) does not enforce canonical/low-`s` signatures. Because ECDSA signatures are malleable (a signature `(r, s)` for a given key/message is always accompanied by a second valid signature `(r, n-s)` with the recovery bit flipped, recovering to the **same** address), and the precompile's duplicate-signer detection compares raw signature bytes instead of recovered addresses, an attacker can submit two distinct-but-malleable signatures from the same private key and have that single key's weight counted twice toward a multisig permission's `threshold`.

### Finding Description
`ValidateMultiSign.execute()` iterates over the signature array supplied by the caller, recovers an address per signature, and accumulates `weight`: [1](#0-0) 

The dedup logic is:
```
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;   // exact same (addr, rawSignatureBytes) already seen -> skip
  }
  MUtil.checkCPUTime();   // otherwise: only a CPU-time guard, NOT a skip
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
The inner `continue` only fires when the **raw signature bytes** are byte-for-byte identical to one already processed. It does **not** fire merely because `recoveredAddr` was already counted — it just imposes a CPU throttle (`MUtil.checkCPUTime()`) and then falls through to add the weight again.

The underlying signature parsing performs no malleability/canonical-form check: `Rsv.fromSignature` simply slices `r`, `s`, `v` directly from the raw 65-byte input with no restriction that `s` be in the lower half of the curve order: [2](#0-1) 

`recoverAddrBySign` then only checks `signature.validateComponents()` (range checks), not canonicality, before recovering the address: [3](#0-2) 

This is the same root cause described in the reference report (SWC-117): `ecrecover`/its analog accepts both the "low-s" and "high-s" (`n - s`) forms of a signature as valid, both of which recover to the same signer address. Here, java-tron's dedup logic assumes that "same recovered address" signature reuse is caught by literal-byte comparison, which malleable variants trivially bypass.

### Impact Explanation
`ValidateMultiSign` is a public, permissionless TVM precompiled contract (guarded only by `VMConfig.allowTvmSolidity059()`, a hard-fork feature flag, not an access-control gate) reachable via `STATICCALL`/`CALL` from any smart contract: [4](#0-3) 

It is the on-chain primitive intended to let smart contracts verify TRON account multisig permissions (weight/threshold-based authorization, mirroring `AccountPermissionUpdateContract`). Any Solidity contract built on top of this precompile to gate privileged actions (e.g., a custody/wallet contract requiring `threshold` weight from N distinct keys) can be tricked into believing a smaller set of real signers satisfied the threshold, because a single signer's key can supply two (or more, by combining with `v` selection) malleable variants of a signature over the same hash, each counted as independent weight. This is a concrete authorization/accounting bypass — exactly the "auth bypass / accounting" impact class requested, not merely theoretical, since the vulnerable accumulation and weight-add logic runs unconditionally for any contract that calls this precompile.

### Likelihood Explanation
Exploitation requires only that: (1) the attacker controls a private key with nonzero weight in the multisig permission being checked, and (2) they can compute the standard ECDSA malleable counterpart of their own signature (`s' = n - s`, flip parity bit) — a trivial, well-known, deterministic transformation requiring no cryptographic breakthrough. No special network position or additional privileges are needed; the exploit is fully client-side signature crafting followed by a normal contract call. The only mitigating factor is that this precompile is opt-in for dApp developers (they must choose to build access control on top of `ValidateMultiSign`), so real-world impact depends on adoption of this pattern by TRC-20/wallet-style contracts, which is a documented, intended TRON multisig use case.

### Recommendation
In `ValidateMultiSign.execute()`, deduplicate signers by `recoveredAddr` alone (not by `(addr, signatureBytes)` pairs) — i.e., `continue`/skip weight accumulation whenever `recoveredAddr` has already been counted, regardless of the raw signature bytes supplied. Additionally, enforce canonical (low-`s`) signature form in `ECDSASignature`/`Rsv`/`SignUtils.fromComponents` validation (reject `s > n/2`) across all signature-recovery paths (`ECRecover`, `ValidateMultiSign`, `BatchValidateSign`) to eliminate malleable variants at the source, consistent with OpenZeppelin's `ECDSA` library approach referenced in the report.

### Proof of Concept
1. Deploy/call a contract that uses `ValidateMultiSign` (precompile address `0x...0a`) to check an account permission with `threshold = 2 * weight(keyA)` and only `keyA` actually controlled by the caller (weight `w`, threshold `2w`).
2. Sign `hash = sha256(address || permissionId || data)` once with `keyA`, obtaining `(r, s, v)`.
3. Compute the malleable counterpart: `s' = SECP256K1_N - s`, `v' = v XOR 1` (i.e., flip parity), producing signature `(r, s', v')`.
4. Submit both signatures `[sig1, sig2]` in the `signatures` array to `ValidateMultiSign`.
5. In the loop: iteration 1 recovers `keyA`'s address, adds weight `w`; iteration 2 recovers the **same** address (malleable signature recovers identically), but since raw bytes differ, `matrixContains(executedSignList, sign)` is false, so execution falls through and adds weight `w` again — `totalWeight = 2w ≥ threshold`, returning `true` (`dataOne()`), even though only one real signer participated.   private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
