### Title
Unbounded per-call WASM instantiation cost (globals/data/element segments) not covered by gas metering, reachable from a single `FunctionCall` transaction — ([File: runtime/near-vm-runner/src/prepare/prepare_v3.rs])

### Summary
CVE-2025-30682 describes a MySQL optimizer bug where a cheap, low-privileged, network-reachable request triggers disproportionate server-side work relative to how the planner "costs" it, causing a hang or crash. nearcore's WASM contract-preparation pipeline has the same bug class: a contract can be engineered so that a `FunctionCall` invocation is charged little/no gas by the protocol's cost model, yet forces the executing node's WASM runtime to perform work proportional to attacker-controlled module size (number of globals, active data segments, active element segments) at every instantiation, unmetered.

### Finding Description
Contract preparation (`prepare_contract` / `PrepareContext::run`) enforces per-module limits such as `max_functions_number_per_contract`, `max_locals_per_contract`, `max_tables_per_contract`, and (as of a config bump that first appears at protocol-version 157, see `core/parameters/res/runtime_configs/157.yaml: max_globals_per_contract: { new: 100_000 }`) a cap on globals. In the current tree's `PrepareContext::new` this limit still defaults to unbounded whenever `max_globals_per_contract` is `None`: [1](#0-0) 

The `GlobalSection` handler only rejects the module if the limit (which may be `u64::MAX`) is exceeded: [2](#0-1) 

For `DataSection` and `ElementSection`, there is no segment-count limit at all anywhere in `prepare_v3.rs` — the payload is validated only against the WebAssembly spec (which permits arbitrarily many active data/element segments) and copied straight through: [3](#0-2) 

The only structural bound on a deployed module is the raw byte size (`max_contract_size`), and a global/data-segment/element-segment declaration costs only a handful of bytes each, so hundreds of thousands of them fit comfortably within the contract size limit.

Critically, the *execution-time cost* of these constructs is explicitly documented as unmetered by gas. The runtime-params-estimator has dedicated "adversarial" benchmarks for exactly this: [4](#0-3) [5](#0-4) 

and the regression test for the (partial) globals fix independently confirms that every defined global costs ~16 bytes of Wasmtime's per-instance `VMContext`, re-initialized on every call: [6](#0-5) 

Gas accounting for `FunctionCall` only charges declared WASM opcodes and `ExtCosts` (`GasCounter::burn_gas`/`process_gas_limit`), never per-global/per-segment instantiation cost: [7](#0-6) 

So a caller can construct a contract that (a) declares an enormous number of globals and/or active data/element segments, all within `max_contract_size`, (b) has a trivial (near-zero-instruction) exported function body, and thus (c) is charged only a tiny, near-baseline amount of gas per `FunctionCall`, while the node executing it (any validator/chunk-producer applying that chunk) pays real, attacker-scaled CPU/memory cost on every single invocation during module instantiation/loading. This is exactly the CVE-2025-30682 bug class: cheap-as-costed, expensive-as-executed operations reachable from an unprivileged network request.

### Impact Explanation
An unprivileged account with a valid access key can deploy such a contract (`DeployContractAction`) and then repeatedly invoke it via cheap `FunctionCall` transactions/receipts. Because the declared gas cost is small, many such calls can be packed into a chunk's gas budget while the real wall-clock cost of instantiating/loading the module scales with attacker-chosen counts (globals/data/element segments), independent of gas paid. This can cause chunk application on validators/chunk-producers to take disproportionately long ("hang") or exhaust node resources, matching the CVE's "hang or frequently repeatable crash (complete DOS)" characterization — a transaction-triggered denial of service against honest nodes applying otherwise-valid chunks.

### Likelihood Explanation
The path is directly reachable by any account holder via ordinary, protocol-legal transactions (`DeployContractAction` + `FunctionCall`), no special privilege or malicious peer/validator behavior required. The gap for data/element segments has no limiting parameter at all in this codebase snapshot; the globals gap is only closed starting at protocol version 157, which per `protocol-model/spec/contract-vm.md` (documenting protocol version 86 as the current stable baseline in this tree) has not shipped yet. I could not find a named `ProtocolFeature` gate for this change in `core/primitives-core/src/version.rs` (grep for `max_globals_per_contract`/`FixContractLoadingError` found no hits there), so I cannot fully confirm the exact activation mechanics or whether an equivalent runtime-level backstop (e.g., Wasmtime's pooling-allocator instance-size cap noted in `runtime_errors.rs`) mitigates the globals case in practice on some backends — this is a genuine unknown given available context. The data/element-segment gap, however, has no such backstop evidenced anywhere in the reviewed code.

### Recommendation
- Ship `max_globals_per_contract` (or an earlier/immediate parameter bump) ahead of/independent from PV157 if it has not yet activated on the target network.
- Add analogous hard limits on the number of active data segments and active element segments per module in `PrepareContext::run` (`DataSection`/`ElementSection` handling in `runtime/near-vm-runner/src/prepare/prepare_v3.rs`), mirroring the existing `global_limit`/`table_limit` pattern.
- Alternatively/additionally, charge `DeployContractAction` and/or `FunctionCall`'s loading/instantiation gas fee proportionally to the number of globals/data/element segments (not just byte size), so declared cost tracks real instantiation work.

### Proof of Concept
1. Craft a WASM module (analogous to `near_test_contracts::contract_with_num_globals`, `many_data_segments_contract`, `many_element_segments_contract` in `runtime/near-test-contracts/src/lib.rs`) with hundreds of thousands of zero-initialized globals and/or tens of thousands of active data/element segments, staying under `max_contract_size`, with a trivial exported function body.
2. Submit a `SignedTransaction` with `DeployContractAction` to deploy it — this passes `prepare_contract` because `global_limit`/segment counts are unbounded by default (pre-PV157) or entirely unbounded (data/element segments).
3. Submit repeated cheap `FunctionCall` transactions/receipts invoking the trivial exported function; each is charged only baseline gas but forces full module instantiation (global re-initialization, data/element segment application) on every chunk-producing/validating node, as confirmed by the `AdversarialLoadManyGlobals`/`AdversarialLoadManyDataSegments`/`AdversarialLoadManyElementSegments` estimator benchmarks documenting this exact unmetered cost.
