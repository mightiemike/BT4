### Title
`verifyInclusion` on `BitcoinLightClient.sol` returns `true` for a coinbase wtxid against any unrecorded block hash - (File: `crates/evm/src/evm/system_contracts/src/BitcoinLightClient.sol`)

### Summary
`BitcoinLightClient._verifyInclusion` derives its expected Merkle proof length and witness root purely from mappings keyed by `_blockHash`, both of which default to zero for any block hash that was never submitted via `setBlockInfo`. This mirrors the `MagicLpAggregator` bug class: a getter/verification function silently falls back to a hardcoded/default value (`0`) instead of failing closed, and callers who treat that default as meaningful data are misled, exactly as integrators checking `updatedAt` were misled by hardcoded zeros in the referenced report.

### Finding Description
`setBlockInfo` populates `witnessRoots[_blockHash]` and `coinbaseDepths[_blockHash]` only for block hashes that the system caller has actually relayed: [1](#0-0) 

For any `_blockHash` that was never relayed, both mappings return the Solidity default of zero. `_verifyInclusion` uses these defaults directly to check proof length and compute inclusion: [2](#0-1) 

For an unrecorded `_blockHash`, `coinbaseDepths[_blockHash] == 0`, so the `require` only accepts an empty `_proof` (`_proof.length == 0`). With an empty Merkle proof and index `0`, a standard Merkle-inclusion check (`ValidateSPV.prove`) degenerates to checking whether the leaf itself equals the root, i.e. `_wtxId == _witnessRoot`. Since `_witnessRoot` for this unrecorded block also defaults to `0`, the call `verifyInclusion(unknown_blockHash, 0x00..00, "", 0)` returns `true` for **any** block hash that has never been set by the system caller, because the wtxid of a coinbase transaction is canonically the zero hash under BIP141.

This is the same root cause pattern as the referenced report: a function meant to attest to real, verified on-chain data (`latestRoundData`'s freshness metadata / here, "this wtxid is included in this Bitcoin block") instead returns a placeholder zero value that happens to satisfy the check trivially, breaking the binding: `verifyInclusion(blockHash, wtxId, proof, index) == true` should imply `blockHash` was actually relayed by `setBlockInfo` AND `wtxId` is actually included in that block's witness Merkle tree. Currently the equality can be satisfied for a `blockHash` that was never relayed at all, i.e. `verifyInclusion` accepts an inclusion claim against Bitcoin state the contract has no knowledge of. This is a forged DA-inclusion result completely analogous to the analog rules' explicit Critical category ("a forged DA inclusion or completeness result").

The `docs/system-contracts.md` "Getters" warning only discusses the null/zero ambiguity for callers doing existence checks (`witnessRoot != 0`); it does not address that `verifyInclusion` itself can return `true` for an unrecorded block, so this specific failure mode is not a documented, accepted limitation.

### Impact Explanation
Any downstream contract (a hypothetical integrator on Citrea, or a future protocol feature) that relies on `BitcoinLightClient.verifyInclusion`/`verifyInclusion(uint256,...)` to attest "this specific Bitcoin transaction (by wtxid) really occurred in a block Citrea has recorded" can be fooled into accepting a forged inclusion claim for a block the light client never actually saw, as long as the claimed wtxid is the zero hash (the canonical wtxid value of any coinbase transaction) and the caller supplies an empty proof. Because `BitcoinLightClient` is explicitly documented as the mechanism "other smart contracts on Citrea" and the canonical `Bridge` use to confirm that Bitcoin-side events happened, a false-positive inclusion result strikes at the DA-integrity binding this analog scan targets.

The current `Bridge.sol` deposit path was not fully confirmed in this pass to call `verifyInclusion` directly (it appears to use a separate SPV/merkle proof check tailored to `moveTx`), so it is uncertain whether this specific path is reachable to mint or move cBTC without a matching deposit today. This is a genuine gap in verification: I could not load `Bridge.sol`'s full deposit implementation in the final iteration to confirm or rule out a direct call chain from `deposit()` into `verifyInclusion`.

### Likelihood Explanation
No privileged role, key, or node compromise is required — `verifyInclusion` is a public `view` function callable by anyone, unauthenticated. The only precondition is supplying `wtxId = 0x00..00` (the fixed wtxid of any coinbase transaction) and an empty proof against a `_blockHash` never submitted via `setBlockInfo`. This is trivially reproducible on any deployment of the contract.

### Recommendation
`_verifyInclusion` (and the two `verifyInclusion` overloads, plus `verifyInclusionByTxId`) must first assert that the block hash / block number is actually known to the light client (e.g., `require(coinbaseDepths[_blockHash] != 0 || blockHashes[_blockNumber] != bytes32(0))`, or maintain and check an explicit "known blocks" set) before doing any proof-length or Merkle-root comparison. Do not allow the zero-default of `coinbaseDepths`/`witnessRoots` for unset block hashes to be indistinguishable from a legitimately recorded single-coinbase-transaction block.

### Proof of Concept
1. Do not call `setBlockInfo` for a chosen `fakeBlockHash` (leave it completely unrecorded).
2. Call `bitcoinLightClient.verifyInclusion(fakeBlockHash, bytes32(0), "", 0)`.
3. `coinbaseDepths[fakeBlockHash]` is `0` (default) → `require(_proof.length == 0)` passes with the empty proof.
4. `witnessRoots[fakeBlockHash]` is `0` (default) → `ValidateSPV.prove(0x00..00, 0x00..00, "", 0)` returns `true` because with an empty proof/index 0 the "root" is defined as the leaf itself, and the leaf (`_wtxId`) equals the "root" (`_witnessRoot`), both zero.
5. The call returns `true`, i.e., the contract asserts inclusion of a coinbase transaction in a Bitcoin block it has no record of ever existing.

Note: I was unable to load `Bridge.sol` in the final iteration to determine whether the canonical `Bridge` deposit flow itself calls `verifyInclusion` (it may use its own dedicated `moveTx` proof logic instead), so downstream cBTC-custody impact through the canonical bridge is unconfirmed and should be checked in `crates/evm/src/evm/system_contracts/src/Bridge.sol`.

    function setBlockInfo(bytes32 _blockHash, bytes32 _witnessRoot, uint256 _coinbaseDepth) external onlySystem {
        uint256 _blockNumber = blockNumber;
        require(_blockNumber != 0, "Not initialized");
        blockHashes[_blockNumber] = _blockHash;
        blockNumber = _blockNumber + 1;
        witnessRoots[_blockHash] = _witnessRoot;
        coinbaseDepths[_blockHash] = _coinbaseDepth;
        emit BlockInfoAdded(_blockNumber, _blockHash, _witnessRoot, _coinbaseDepth);
    }

    function _verifyInclusion(bytes32 _blockHash, bytes32 _wtxId, bytes calldata _proof, uint256 _index) internal view returns (bool) {
        require(_proof.length == coinbaseDepths[_blockHash] * HASH_LENGTH, "Invalid proof length");
        bytes32 _witnessRoot = witnessRoots[_blockHash];
        return ValidateSPV.prove(_wtxId, _witnessRoot, _proof, _index);
    }
