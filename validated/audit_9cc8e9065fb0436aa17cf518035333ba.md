## Analysis

The reported bug class ("functions that pay out `_to` without checking it's non-empty/valid, causing accidental burns") maps to `DeleteAccountAction::beneficiary_id` in nearcore's runtime. When an account is deleted, its remaining balance is sent as a **refund receipt** to `beneficiary_id` — but the only validation performed on `beneficiary_id` is that it is a *syntactically* valid `AccountId` string, never that the account actually exists. [1](#0-0) 

The payout itself is unconditional as long as there's a positive balance: [2](#0-1) 

This refund is a system-predecessor ("refund") receipt. If the beneficiary account doesn't exist, its execution fails with `AccountDoesNotExist`, and — per the documented refund semantics — the amount is permanently burnt rather than returned to anyone: [3](#0-2) 

The corresponding runtime logic burns the deposit into `other_burnt_amount` when a system-predecessor (refund) receipt fails: [4](#0-3) 

This is directly reachable by any unprivileged transaction signer submitting a `DeleteAccount` action with a `beneficiary_id` that is a valid-looking but non-existent account (typo, deleted account, or an account that was simply never created) — exactly the "check `_to` is not empty/invalid" bug class from the report, adapted to nearcore's account model where "empty 0x0" becomes "syntactically valid but non-existent `AccountId`". A test in the codebase explicitly acknowledges this risk as a precondition rather than a guarded invariant: "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" (and, per the refund docs, that refund's failure burns the funds). [5](#0-4) 

### Title
Accidental permanent fund burn via `DeleteAccount` to a non-existent `beneficiary_id` - (File: runtime/runtime/src/actions.rs)

### Summary
`action_delete_account` validates `beneficiary_id` only for account-id string format, not for account existence, before routing the deleted account's entire balance to it as a refund receipt.

### Finding Description
`validate_delete_action` only calls `validate_action_account_id`, which checks that `beneficiary_id` parses as a syntactically valid `AccountId` — it never checks that the account exists on-chain. [1](#0-0) 

`action_delete_account` then unconditionally emits `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` for any positive balance. [2](#0-1) 

This generated receipt has `predecessor_id == "system"` (it's a refund receipt). When such a receipt targets a nonexistent account, its execution fails with `AccountDoesNotExist`, and the runtime's refund-failure path burns the deposit instead of returning it anywhere: [4](#0-3) [3](#0-2) 

### Impact Explanation
Any account holder who submits `DeleteAccount` with a mistaken/mistyped/nonexistent `beneficiary_id` (a plausible, easily reachable user error since NEAR account IDs are free-form strings and existence is never checked before the destructive delete) causes their entire remaining account balance to be irrecoverably burnt. This is an unauthorized, permanent loss of user funds triggered by a single ordinary transaction from an unprivileged signer — no attacker/validator/network assumption is required, matching the reachable-analog criteria (a transaction signer's own action).

### Likelihood Explanation
Likelihood is non-trivial: `beneficiary_id` is user-supplied and unchecked for existence; a simple typo, a reused test/staging account id that was never created, or targeting an implicit account that hasn't been funded/created yet, all reproduce the burn deterministically and irreversibly. There is no confirmation step or existence pre-check protecting the user.

### Recommendation
Before deleting the account and issuing the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or explicitly document/gate this behavior with a stronger warning/opt-in), returning an execution error (e.g., a new `ActionErrorKind` such as `BeneficiaryAccountDoesNotExist`) instead of silently burning funds via a failed refund receipt.

### Proof of Concept
1. Create/own account `alice.near` with a positive balance.
2. Submit `SignedTransaction` with a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent123.near".parse().unwrap() })` signed by `alice.near`.
3. `action_delete_account` removes `alice.near` and enqueues `Receipt::new_balance_refund(&"nonexistent123.near", alice_balance)`.
4. That refund receipt executes against a nonexistent receiver, fails with `ActionErrorKind::AccountDoesNotExist`, and per `lib.rs:1047-1054` the amount is added to `stats.balance.other_burnt_amount` — permanently burnt, unrecoverable by `alice.near` or anyone else. [6](#0-5)

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
