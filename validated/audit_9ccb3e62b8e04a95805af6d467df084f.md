## Finding Confirmed [1](#0-0) 

The JSON conversion path in `Account::resources` does exactly what the question describes: it fetches the raw resource bytes at the possibly-historical `self.ledger_version`, but builds the `MoveConverter` used to decode/annotate those bytes from a state view bound to the *latest* ledger version.

### Title
Historical `/accounts/{address}/resources` JSON responses resolve Move type layouts from the latest state instead of the requested `ledger_version` - (File: `api/src/accounts.rs`)

### Summary
`Account::resources` retrieves the raw BCS resource bytes for the account correctly scoped to `self.ledger_version` via `get_resources_by_pagination`, but for `AcceptType::Json` it builds the annotator/converter from `self.context.latest_state_view_poem(&self.latest_ledger_info)` — a state view pinned to the *current* tip of the chain, not to `self.ledger_version`. [2](#0-1) [3](#0-2) 

### Finding Description
The `MoveConverter` resolves struct field names/types by loading module bytecode (ABI/layout) out of the `StateView` it was constructed with, as seen in `try_into_resources` / `view_resource` in `MoveConverter` (`api/types/src/convert.rs`) which internally calls `self.inner.view_module(...)` against whatever `StateView` backs the annotator. Because the annotator here is built from `latest_state_view_poem`, any module bytecode present at the requested historical `ledger_version` is bypassed in favor of the module bytecode as of the very latest committed version. [4](#0-3) 

Contrast this with the two other resource-lookup code paths in the same file and in `api/src/state.rs`, which correctly bind the state view to the requested version before doing type resolution: [5](#0-4) [6](#0-5) 

`find_resource` (used by `get_account_resource` field lookups) and `StateApi::resource` (the single-resource endpoint) both call `self.context.state_view(Some(self.ledger_version))?`, producing a state view pinned to the requested historical version, and then run type resolution against that same pinned view. Only the bulk `resources()` JSON path diverges and substitutes `latest_state_view_poem`.

The BCS accept-type branch of the same function is unaffected because it returns the raw bytes untouched, without any layout resolution. [7](#0-6) 

### Impact Explanation
This is an authenticated API response (bound to `&self.latest_ledger_info` as its ledger context) whose underlying type-layout resolution is bound to the wrong ledger version. If a module owner republishes a module between the historical `ledger_version` and the current tip in a way that changes struct field composition, ordering, generic instantiation, or enum-variant layout for a struct the queried account still holds an old copy of, the JSON annotator will decode the *old* raw bytes using the *new* layout. This can produce a `MoveResource` JSON body with wrong field names/values, or an outright deserialization failure, misrepresenting a resource actually committed at `ledger_version` in the authenticated API response. This falls squarely under the listed impact "authenticated API or state-view output bound to the wrong version, object, or proof context" — the raw bytes returned via BCS accept type and the underlying storage/proof data are untouched, but the JSON-encoded, ledger_info-authenticated view of historical state is misbound.

### Likelihood Explanation
Triggering this requires only unprivileged actions: any account/package owner can republish a module (subject to the standard Move upgrade-compatibility checker enforced by `Compatibility::check`), and any client can then query `/accounts/{address}/resources?ledger_version=<old>` with `Accept: application/json`. Note that Aptos's mandatory module-compatibility checks for `upgrade_policy = compatible` restrict how much struct layouts can diverge across upgrades (they generally preserve storage compatibility), which somewhat limits — but does not eliminate — the practical scope of layout drift that can be observed (e.g., changes affecting resource-group membership, added enum variants, or generic-instantiation resolution differences can still occur without violating the storage-safety compatibility rules).

### Recommendation
In `Account::resources` (and check `Account::modules`'/other similarly-shaped historical endpoints for the same pattern), replace `self.context.latest_state_view_poem(&self.latest_ledger_info)` with a state view pinned to `self.ledger_version`, mirroring the pattern already used in `find_resource` and `StateApi::resource`, i.e. call `self.context.state_view(Some(self.ledger_version))?` (or the poem-specific equivalent) and use that view's `as_converter(...)` for `try_into_resources`.

### Proof of Concept
1. Publish module `M` at account `A` with struct `S { a: u64 }`; execute a transaction that stores `S{a: 5}` under `A`. Record the resulting `ledger_version = V1`.
2. Republish module `M` (compatibility-preserving upgrade) at a later version that changes `S`'s layout in a way visible to annotation (e.g., add an enum variant / reorder generics / change resource-group membership) — record `ledger_version = V2 > V1`.
3. Call `GET /accounts/A/resources?ledger_version=V1` with `Accept: application/json`.
4. Observe that `Account::resources` fetches the byte blob for `S` from state at `V1` (correct), but constructs its `MoveConverter` from `latest_state_view_poem` (bound to the *latest*, `>= V2`, ledger version), so the returned JSON reflects module `M`'s layout as of the latest version rather than as of `V1` — diverging from what `GET /accounts/A/resources?ledger_version=V1&Accept=application/x-bcs` (raw bytes) actually contains.
