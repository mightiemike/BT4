### Title
Uncost-weighted rate limiting allows CPU/energy amplification via EstimateEnergyServlet's binary-search gas estimation - (File: framework/src/main/java/org/tron/core/services/http/EstimateEnergyServlet.java)

### Summary
`EstimateEnergyServlet.doPost` accepts any syntactically valid `TriggerSmartContract` request bounded only by `Util.checkBodySize`, then unconditionally invokes `wallet.estimateEnergy(...)`, which (per TRON's known gas-estimation design) performs a binary search of constant-contract VM executions to converge on a minimal energy value. The inherited `RateLimiterServlet.service` only throttles by request *count* (QPS/IP-based adapters), never by expected VM execution cost, so an attacker can submit crafted payloads that maximize per-request VM work while staying within the same request-count budget as trivial requests.

### Finding Description
`EstimateEnergyServlet.doPost` reads the body, enforces only a size cap via `Util.checkBodySize(contract)`, parses the contract, builds a `TriggerSmartContract`, and calls `wallet.estimateEnergy(build.build(), trxCap, trxExtBuilder, retBuilder, estimateEnergyBuilder)` with no cost- or complexity-based gating beyond that. [1](#0-0) 

The exception handling at lines 63-73 only distinguishes `ContractValidateException` from generic `Exception` for response formatting — it performs no work-cost accounting and does not abort mid-estimation based on elapsed CPU time or VM execution count. [2](#0-1) 

The base class `RateLimiterServlet.service` gates requests solely through `IRateLimiter.acquirePermit` (per-endpoint) and `GlobalRateLimiter.acquirePermit` (global), both of which are QPS/IP/token-based adapters (`DefaultBaseQqsAdapter`, `QpsRateLimiterAdapter`, `IPQPSRateLimiterAdapter`, `GlobalPreemptibleAdapter`) — none of them account for the actual CPU/VM cost that a given accepted request will consume. [3](#0-2) [4](#0-3) 

Because the request-admission decision (`acquireResource`) happens once, before `super.service(req, resp)` executes `EstimateEnergyServlet.doPost`, the rate limiter has no visibility into (and does not scale with) the size of the submitted bytecode/`feeLimit` range that governs how many binary-search iterations `wallet.estimateEnergy` will run internally. Two requests that consume equal "quota" from the rate limiter can therefore differ by an order of magnitude or more in actual VM execution count/CPU time — one contract that reverts immediately vs. one sized near `Util.checkBodySize`'s limit with a `feeLimit` chosen to maximize the number of binary-search midpoint executions.

Note: I was not able to directly re-verify the internal binary-search loop implementation inside `Wallet.estimateEnergy` (or wherever `cleanContextAndTriggerConstantContract` is invoked) within this session due to tool-call budget exhaustion; the presence and general shape of that binary-search-based estimation is inferred from the question's framing and standard TRON `estimateEnergy` design, not from a line-by-line read of that method in this pass. The architecture-level gap — request-count-based rate limiting with no per-request cost normalization in `EstimateEnergyServlet`/`RateLimiterServlet` — is directly confirmed from the code cited above.

### Impact Explanation
If confirmed, an unprivileged attacker can send a stream of `EstimateEnergyServlet` POST requests, each admitted under the same QPS-based budget as trivial requests, but each internally triggering multiple full VM executions via the binary search in gas estimation. This produces a disproportionate CPU/energy amplification factor per accepted request relative to the configured rate-limiter budget, which can be leveraged to degrade node responsiveness (public read-path DoS) without violating any per-request rate limit.

### Likelihood Explanation
The entrypoint (`EstimateEnergyServlet`) is a public, unauthenticated HTTP API requiring no privileges beyond network access. The only admission control is size (`Util.checkBodySize`) and request-count-based QPS/IP limiting; neither constrains the number of internal VM executions a single accepted request can trigger. This makes the amplification pattern reproducible by any external caller capable of crafting a contract/feeLimit combination that maximizes binary-search iterations, subject to confirming the exact iteration-bound behavior of `wallet.estimateEnergy`, which was not independently re-verified in this session.

### Recommendation
Introduce cost-aware throttling for `EstimateEnergyServlet` (and any other endpoint that performs binary-search or iterative VM-based estimation), e.g., bound the maximum number of `triggerConstantContract`/binary-search iterations per request to a small constant, add a wall-clock/CPU-time budget enforced inside `wallet.estimateEnergy` that aborts and returns an error if exceeded, and/or make the rate limiter adapter for this specific servlet weight permits by estimated computational cost (contract size × iteration bound) rather than a flat per-request token.
