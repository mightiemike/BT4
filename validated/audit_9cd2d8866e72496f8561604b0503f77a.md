### Title
Unmetered O(n) `MUtil.transferAllToken` iteration during `SUICIDE`/`SUICIDE2` causes per-opcode CPU-time overshoot in constant-call RPC path - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Summary
`MUtil.transferAllToken`, invoked from `Program.suicide`/`Program.suicide2` (and transitively `transferFrozenV2BalanceToInheritor`), iterates the entire `assetMapV2` of the self-destructing account with no cap and no energy cost tied to its size, while the `SUICIDE` opcode's energy cost is a small fixed constant. Because the VM's CPU-time watchdog (`Program.checkCPUTimeLimit`) is invoked *before* each opcode executes rather than bounding the opcode's own execution duration, a single `SUICIDE` call on an account holding a very large number of distinct TRC10 tokens can run for an unbounded amount of wall-clock time before the next check can abort it, regardless of the fixed energy charged for that opcode.

### Finding Description
`wallet/triggerconstantcontract` routes through `Wallet.callConstantContract` → `VMActuator.validate/execute` → `VM.play`, exactly the same opcode dispatch used for normal execution [1](#0-0) . Inside `VM.play`, energy for the current opcode is spent, then `program.checkCPUTimeLimit(opName)` is called, and only *after that* is `op.execute(program)` invoked [2](#0-1) . This means the CPU deadline is only enforced at opcode *boundaries*; the duration of the opcode currently executing is not itself bounded.

`SUICIDE`'s energy cost is fixed regardless of account state size: `getSuicideCost`/`getSuicideCost2`/`getSuicideCost3` return `0`, or a fixed `NEW_ACCT_CALL` (25000/30000) surcharge only if the recipient is a new account [3](#0-2) . Yet the actual work performed by `Program.suicide`/`suicide2` includes `MUtil.transferAllToken`, which does a full, unbounded `forEach` over `fromAccountCap.getAssetMapV2()` and rebuilds two `Account.Builder` protobuf objects [4](#0-3) , plus `transferFrozenV2BalanceToInheritor`, which streams `FrozenV2List`/`UnfrozenV2List` [5](#0-4) . Neither cost scales with the size of these collections, and `putAssetV2(tokenId, 0L)` never removes a key from the map, so entries persist even after being zeroed out.

Because `triggerconstantcontract` executes with `isConstantCall = true`, energy is capped by `maxEnergyLimitForConstant` (default 100,000,000) or the transaction's `feeLimit`, and CPU time is capped by `thisTxCPULimitInUs` derived from `maxCpuTimeOfOneTx` or `constantCallTimeoutMs` [6](#0-5) . These limits bound the *number* of opcodes/internal calls that can run, but do not bound the *duration* of any single opcode. If an attacker seeds a contract account (via ordinary, previously-broadcast TRC10 transfers) with a very large `assetMapV2` (many distinct TRC10 token IDs), then a single `triggerconstantcontract` call that triggers `SUICIDE`/`SUICIDE2` on that account pays the fixed, size-independent `SUICIDE` energy cost while the interpreter spends time proportional to the number of distinct tokens, exceeding the per-call CPU deadline before the next `checkCPUTimeLimit()` invocation can intervene.

### Impact Explanation
This maps to "DoS via RPC-API": an unprivileged caller can craft a `triggerconstantcontract` (or `eth_call`/`estimateenergy`, which share the same `callConstantContract` path) request that ties up an RPC worker thread for longer than the configured CPU deadline is meant to allow, because the deadline check happens between opcodes, not during one. Repeated concurrent calls against the same pre-seeded contract could be used to exhaust the RPC-serving thread pool. The blast radius is bounded to a single opcode's overshoot per call (not compounding indefinitely across internal-call fan-out, since energy/CPU budgets still cap the number of such expensive operations that can be reached within one call) — so the stronger "worse-than-linear across nested internal calls" hypothesis in the question is not substantiated by the code; the concrete, demonstrable issue is a single fixed-cost opcode whose real cost is O(n) in attacker-influenced state size and is not gated during its own execution.

### Likelihood Explanation
Exploitation requires: (1) a one-time, real on-chain cost to populate a target contract account's `assetMapV2` with many distinct TRC10 token entries (this requires broadcasting actual TRC10 transfers, paying bandwidth/energy, though it does not require creating new tokens — trading for/holding tiny amounts of many pre-existing TRC10 tokens suffices); (2) the target contract must support a reachable `SUICIDE`/`SUICIDE2` opcode with `allowTvmTransferTrc10` and (optionally) `allowTvmFreezeV2` active. `triggerconstantcontract` itself is free/read-only (no real value transfer/commit — `execute()` returns early for `isConstantCall` without `rootRepository.commit()` [7](#0-6) ), so repeated invocation costs the attacker only RPC bandwidth, not fees. This lowers the bar for repeatable probing/DoS once the expensive account state exists.

### Recommendation
- Charge `SUICIDE`/`SUICIDE2` energy proportional to `assetMapV2.size()` (and `FrozenV2List`/`UnfrozenV2List` sizes), similar to how `LOG` costs scale with data size.
- Enforce a hard cap on the number of distinct TRC10 tokens (`assetMapV2` entries) an account may hold, or prune zero-balance entries in `transferAllToken`/`putAssetV2` instead of leaving dead keys.
- Add an intra-opcode CPU-time check (or a periodic check during the `assetMapV2` iteration) inside `MUtil.transferAllToken`/`transferFrozenV2BalanceToInheritor`, mirroring the existing `MUtil.checkCPUTime()`/`checkCPUTimeForCreate2()` pattern used elsewhere, so time is bounded during execution rather than only between opcodes.

### Proof of Concept
Conceptual JUnit outline (cannot be fully executed without the referenced test harness classes, which were not available for inspection):
```java
// 1. Seed accountX.assetMapV2 with N distinct TRC10 token IDs via repeated
//    AccountCapsule.addAssetAmountV2 calls (simulating N real on-chain transfers).
// 2. Deploy a trivial contract whose fallback executes SUICIDE(accountX_as_contract).
// 3. Measure wall-clock time of Program.suicide2(...) directly (or via
//    VMActuator with isConstantCall=true) for N = 10, 1_000, 100_000 distinct
//    token entries.
// 4. Assert time(N) grows roughly linearly with N while
//    EnergyCost.getSuicideCost/2/3(...) remains constant (0 or fixed 25000/30000),
//    demonstrating energy-cost/CPU-cost decoupling for this opcode.
```
Full end-to-end reproduction (populating a real account with many TRC10 tokens and invoking `triggerconstantcontract` via gRPC) requires broadcasting many `TransferAssetContract` transactions beforehand and was not verified end-to-end in this analysis; the unit-level decoupling between fixed `SUICIDE` energy cost and O(n) `MUtil.transferAllToken` work is directly supported by the cited code.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }

  private long transferFrozenV2BalanceToInheritor(byte[] ownerAddr, byte[] inheritorAddr, Repository repo) {
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddr);
    AccountCapsule inheritorCapsule = repo.getAccount(inheritorAddr);
    long now = repo.getHeadSlot();

    // transfer frozen resource
    ownerCapsule.getFrozenV2List().stream()
        .filter(freezeV2 -> freezeV2.getAmount() > 0)
        .forEach(
            freezeV2 -> {
              switch (freezeV2.getType()) {
                case BANDWIDTH:
                  inheritorCapsule.addFrozenBalanceForBandwidthV2(freezeV2.getAmount());
                  break;
                case ENERGY:
                  inheritorCapsule.addFrozenBalanceForEnergyV2(freezeV2.getAmount());
                  break;
                case TRON_POWER:
                  inheritorCapsule.addFrozenForTronPowerV2(freezeV2.getAmount());
                  break;
              }
            });

    // merge usage
    BandwidthProcessor bandwidthProcessor = new BandwidthProcessor(ChainBaseManager.getInstance());
    bandwidthProcessor.updateUsageForDelegated(ownerCapsule);
    ownerCapsule.setLatestConsumeTime(now);
    if (ownerCapsule.getNetUsage() > 0) {
      bandwidthProcessor.unDelegateIncrease(inheritorCapsule, ownerCapsule,
          ownerCapsule.getNetUsage(), BANDWIDTH, now);
    }

    EnergyProcessor energyProcessor =
        new EnergyProcessor(
            repo.getDynamicPropertiesStore(), ChainBaseManager.getInstance().getAccountStore());
    energyProcessor.updateUsage(ownerCapsule);
    ownerCapsule.setLatestConsumeTimeForEnergy(now);
    if (ownerCapsule.getEnergyUsage() > 0) {
      energyProcessor.unDelegateIncrease(inheritorCapsule, ownerCapsule,
          ownerCapsule.getEnergyUsage(), ENERGY, now);
    }

    // withdraw expire unfrozen balance
    long nowTimestamp = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    long expireUnfrozenBalance =
        ownerCapsule.getUnfrozenV2List().stream()
            .filter(
                unFreezeV2 ->
                    unFreezeV2.getUnfreezeAmount() > 0 && unFreezeV2.getUnfreezeExpireTime() <= nowTimestamp)
            .mapToLong(Protocol.Account.UnFreezeV2::getUnfreezeAmount)
            .sum();
    if (expireUnfrozenBalance > 0) {
      inheritorCapsule.setBalance(inheritorCapsule.getBalance() + expireUnfrozenBalance);
      increaseNonce();
      addInternalTx(null, ownerAddr, inheritorAddr, expireUnfrozenBalance, null,
          "withdrawExpireUnfreezeWhileSuiciding", nonce, null);
    }
    clearOwnerFreezeV2(ownerCapsule);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    repo.updateAccount(inheritorCapsule.createDbKey(), inheritorCapsule);
    return expireUnfrozenBalance;
  }
