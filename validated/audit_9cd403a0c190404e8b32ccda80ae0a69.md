### Title
DoS: An attacker can inflate `VotesStore` with a large number of low-cost vote entries, making the mandatory per-epoch `MaintenanceManager.doMaintenance()` vote tally unbounded in cost - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
The reported pattern ("attacker creates a significant number of excess low-value receipts that must be processed one-by-one before a privileged/aggregate operation can complete, driving up gas cost") maps to `MaintenanceManager.doMaintenance()` / `countVote()` in java-tron. Any account can broadcast a `VoteWitnessContract` transaction with a trivial TronPower amount, which is unconditionally persisted as an entry in `VotesStore`. Every maintenance cycle (fixed, permissionless, protocol-driven cadence run by every full node/SR), `countVote()` must iterate over the *entire* `VotesStore` and delete each entry, exactly analogous to the "excess receipts must all be walked/withdrawn" pattern in the original finding — except here the mandatory processing is baked into consensus itself rather than an owner-only call.

### Finding Description
`VoteWitnessActuator.countVoteAccount()` (or `VoteWitnessProcessor.execute()` for the TVM native contract path) creates/updates a `VotesCapsule` entry in `VotesStore` for the voting owner address on every valid vote transaction, with no minimum vote/stake requirement enforced beyond `MAX_VOTE_NUMBER` (max distinct witnesses per vote list), and no restriction on how small the TronPower backing the vote can be: [1](#0-0) 

At the start of every maintenance period, `MaintenanceManager.doMaintenance()` calls `countVote(votesStore)`, which unconditionally iterates the full `VotesStore` via a DB iterator and deletes every entry it visits: [2](#0-1) 

Because a new account can be created cheaply and each account can independently place a vote backed by a minimal amount of frozen TRX (a "receipt" analog to the excess pool deposits in the original report), an attacker can programmatically create a very large number of distinct addresses, each casting a vote with negligible stake, right before a maintenance boundary. Every SR/full node executing `doMaintenance()` (this runs automatically as part of block production for every witness, not gated behind any privileged actor) must fully scan and delete all of these entries in `countVote()` before it can finish updating witness vote counts and proceed with block production. This is functionally identical to the audited bug class: an unbounded amount of low-value "receipts" that a mandatory downstream aggregate operation must process one-by-one, imposing unbounded cost on the party performing that aggregate step.

The same pattern is duplicated (without cleanup) in the read-only path `Wallet.countVote()` used by `getPaginatedNowWitnessList()`, which iterates the same growing `VotesStore` on every RPC call, compounding the cost for any client hitting this API during a bloated-store window: [3](#0-2) 

### Impact Explanation
Unlike the original report where only the pool owner's gas cost increases, here the affected operation (`doMaintenance`) is executed by every Super Representative/witness node as an intrinsic part of block/consensus processing on a fixed schedule. Artificially inflating the number of `VotesStore` entries directly increases the CPU/IO time every node needs to spend in `countVote()` right before it can compute new witness vote totals and produce blocks, creating a network-wide processing delay rather than an isolated financial inconvenience to one owner. It can also degrade `getPaginatedNowWitnessList()`/vote-count RPC responsiveness for all callers during the affected epoch.

### Likelihood Explanation
The attack requires no privileged role, no leaked keys, and no malicious peer/node behavior — any account holder can call `VoteWitnessContract` (or the corresponding TVM/native contract) after freezing a minimal balance. Account creation and minimal freeze amounts are cheap, so scaling to a large number of vote entries is primarily bounded by transaction throughput/bandwidth cost, similar to the original report's low-cost "1 wei deposit" trick.

### Recommendation
Introduce a minimum TronPower/frozen-balance threshold required to cast a vote (mirroring the "minimum deposit" mitigation FactoryDAO adopted), and/or bound or batch the `VotesStore` scan in `countVote()` (e.g., process/delete in capped batches across multiple maintenance cycles) so a single maintenance pass cannot be forced into unbounded work by cheaply created low-stake voter accounts.

### Proof of Concept
1. Attacker programmatically creates N new accounts, funding each with the minimal TRX needed to activate the account and freeze/stake a negligible TronPower amount.
2. Each account broadcasts a `VoteWitnessContract` transaction voting for any witness with the minimal stake — each creates/updates a `VotesCapsule` entry in `VotesStore` (`VoteWitnessActuator.countVoteAccount`, `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java:152-191`).
3. At the next maintenance boundary, every SR/full node's `MaintenanceManager.doMaintenance()` invokes `countVote(votesStore)`, which must iterate and delete all N entries (`consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java:165-195`) before witness vote totals and rewards can be finalized, imposing O(N) unavoidable work on every node for that maintenance cycle.

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }
