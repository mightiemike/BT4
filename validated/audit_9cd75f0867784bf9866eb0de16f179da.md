## Title
Non-embedded app session cookie collision across shops due to shared, non-scoped `SESSION_COOKIE_NAME` cookie path (default `path: '/'`) - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
For non-embedded apps, the OAuth callback writes the authenticated session id into a single, domain-wide cookie (`shopify_app_session`) at `path: '/'` by default. Because the cookie key is not scoped per shop, completing OAuth for a second shop **silently overwrites** the cookie referencing the first shop's session — the same overwrite-by-shared-key pattern as the reported `referrers[edition_]` bug, just applied to session identity instead of referral fee routing.

### Finding Description
`begin`/`callback` in [1](#0-0)  set the session cookie like this:

```
if (!config.isEmbeddedApp) {
  const cookiePath =
    typeof config.cookiePath === 'function'
      ? config.cookiePath(session)
      : (config.cookiePath ?? '/');
  await cookies.setAndSign(SESSION_COOKIE_NAME, session.id, {
    ...
    path: cookiePath,
  });
}
```

`cookiePath` defaults to `'/'` per [2](#0-1) , meaning the cookie is domain-wide and keyed only by name — not by shop. When the same browser (or an app whose non-embedded flow doesn't set a shop-specific path) completes OAuth for shop B after shop A, the browser overwrites the single `shopify_app_session` cookie, replacing shop A's session id with shop B's.

Subsequently, `getCurrentSessionId` for non-embedded apps simply reads and trusts whatever session id is present in that shared cookie without any per-shop disambiguation: [3](#0-2) 

```
} else {
  log.debug('App is not embedded, looking for session id in cookies', {isOnline});
  const cookies = new Cookies(request, {} as NormalizedResponse, {keys: [config.apiSecretKey]});
  return cookies.getAndVerify(SESSION_COOKIE_NAME);
}
```

Because the cookie is HMAC-signed and simply looked up by name, this is not a spoofing/forgery issue — it's a **cross-tenant session-storage-key collision**: exactly analogous to `referrers[edition_]` being overwritten instead of being keyed by `getRouteId(edition_, tokenId_)`. Here, `SESSION_COOKIE_NAME` at a fixed `path` acts as the coarse key that should have been scoped per shop but isn't by default.

The project's own CHANGELOG confirms the root cause and partial remediation: [4](#0-3)  — a `cookiePath` option was added, but it is opt-in; "Static path (default behaviour, unchanged)" remains `path: '/'`.

### Impact Explanation
In a browser used to interact with multiple shops for the same non-embedded app (a supported/documented scenario per the changelog: "Non-embedded apps that need to support multiple shops simultaneously in separate browser tabs"), authenticating shop B overwrites the cookie used to resolve the current session for shop A's tab. This causes the app to resolve the wrong tenant's session for requests that still target shop A's UI, i.e., a cross-tenant session mix-up: a user interacting with what they believe is shop A's admin/session may actually be operating under shop B's `Session` (or vice versa), potentially exposing or acting on the wrong merchant's authenticated context. This is a genuine cross-tenant confusion bug matching the accepted bug classes (session-storage key collision / cross-tenant session confusion), not merely a UX inconvenience, since it silently substitutes one tenant's authenticated session for another's without any error.

### Likelihood Explanation
Requires no attacker action beyond the normal, documented usage pattern (a merchant/staff account interacting with two shops of the same non-embedded app in the same browser, e.g. multiple browser tabs) — this is explicitly called out by the maintainers as a real-world scenario they added `cookiePath` to address. Any consumer of `shopify-app-js` who has not explicitly configured `cookiePath` (the default) remains exposed. It is a default-configuration issue reachable by an ordinary user of a non-embedded app, not requiring privileged access.

### Recommendation
Make per-shop cookie scoping the default rather than opt-in — e.g., default `cookiePath` to a function that folds the shop domain into the path (or otherwise incorporate shop into the cookie name/key) so that non-embedded apps are safe out of the box. At minimum, strongly warn/log when running non-embedded without a shop-scoped `cookiePath`, and update `getCurrentSessionId` to validate that the shop encoded in the resolved session actually matches the shop parameter of the current request before trusting it, closing the “silently use whichever session cookie exists” gap described in [3](#0-2) .

### Proof of Concept
1. Configure a non-embedded app without setting `cookiePath` (default `'/'`).
2. In one browser, complete OAuth for `shop-a.myshopify.com`; `shopify_app_session` cookie is set to `session.id` for shop A at `path: '/'` — see [1](#0-0) .
3. In a second tab of the same browser, complete OAuth for `shop-b.myshopify.com`. Because the cookie shares the same name/path, it now holds shop B's `session.id`, overwriting shop A's.
4. Return to the first tab and reload a page for shop A. `getCurrentSessionId` reads the shared cookie in [5](#0-4)  and resolves shop B's session id, causing the app to load/operate as shop B rather than shop A.
5. This is corroborated by the maintainers' own fix description in [6](#0-5) : "authenticating a new shop would silently overwrite the previous shop's session," and by the accompanying test demonstrating the default `path: '/'` behavior in [7](#0-6) .

  /**
   * The path to use for the OAuth session cookie in non-embedded apps.
   *
   * By default the cookie is written with `path: '/'`, making it domain-wide.
   * This means that when a user authenticates multiple shops in separate tabs,
   * each OAuth callback overwrites the previous cookie, causing all tabs to use
   * the most-recently-authenticated shop.
   *
   * Set this to a string or a function returning a string to scope the cookie to
   * a URL path prefix that is unique per shop. The browser will then maintain
   * one cookie per shop and deliver only the matching one per request.
   *
   * **Requirement:** the configured path must match the actual URL structure of
   * your app — e.g. if each shop lives under `/shops/:shop/`, use that prefix.
   * The library cannot derive this automatically.
   *
   * @example
   * // Static path (single-shop apps or apps with no shop-specific routing)
   * cookiePath: '/'
   *
   * @example
   * // Factory function (multi-shop non-embedded apps)
   * cookiePath: (session) => `/shops/${session.shop}/`
   *
   * @defaultValue `'/'`
   */
  cookiePath?: string | ((session: Session) => string);
```

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
