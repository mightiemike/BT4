### Title
`sanitizeShop` domain allow-list is derived from a heuristic regex extraction that can diverge from the actual `domainTransformations` matcher, allowing non-Shopify shop values to pass validation - (File: `packages/apps/shopify-api/lib/utils/domain-transformer.ts`)

### Summary
`sanitizeShop` validates a `shop` value in two decoupled steps that must agree, but don't: (1) it builds an allow-list regex from `getTransformationDomains(config)`, which heuristically extracts a domain suffix from each configured `domainTransformations[].match` regex source, and (2) it later calls `applyDomainTransformations`, which actually applies the *real* `transformation.match` regex to decide if/how to transform the shop. Just like the GoodEntry `addDust` finding — where the "dust" amount was computed on one basis (oracle price) while the amount actually consumed was determined on a different basis (LP tick price), causing the two calculations to disagree — here the *validation* allow-list is computed on one basis (a naive suffix-only regex heuristic) while the *actual* legitimacy check is a different, stricter regex. When a configured `match` pattern includes anything beyond a simple literal subdomain (e.g. required infix segments, alternations, optional groups — all explicitly called out as "Unsupported" in the function's own doc comment), the heuristic extracts an overly permissive domain suffix. This lets a `shop` value that does not actually satisfy any transformation rule, and is not a genuine Shopify domain, still pass `sanitizeShop` and be returned as sanitized/valid.

### Finding Description
In `packages/apps/shopify-api/lib/utils/shop-validator.ts` (`sanitizeShop`), when `config.domainTransformations` is configured, the validation regex is built as: [1](#0-0) 

`getTransformationDomains` in `domain-transformer.ts` extracts a domain suffix from the `match` regex source using a single generic pattern: [2](#0-1) 

This heuristic only captures the trailing `\.<domain>` segment of the regex source, discarding any required infix subdomain component, alternation, or optional group that the real matcher enforces. The function's own documentation explicitly warns that alternations (`\.(dev|staging)\.example\.com$`), optional groups, and character classes in the domain part are "Unsupported" and "may not extract correctly": [3](#0-2) 

Meanwhile, the actual transform application uses the real, unmodified regex: [4](#0-3) 

Concretely, for a configuration such as:
```ts
domainTransformations: [{
  match: /^([a-zA-Z0-9-_]+)\.(dev|staging)\.example\.com$/,
  transform: '$1.api.example.com',
}]
```
`getTransformationDomains` extracts only `example\.com` (losing the required `.dev.` / `.staging.` segment), which is then merged into `sanitizeShop`'s allow-list regex:
```
^[a-zA-Z0-9][a-zA-Z0-9-_]*\.(myshopify\.com|shopify\.com|myshopify\.io|shop\.dev|example\.com)[/]*$
```
This regex now matches **any** subdomain of `example.com`, not just `<name>.dev.example.com` / `<name>.staging.example.com`. If an attacker (or a malformed request) supplies `shop=attacker.example.com`:
1. `shopUrlRegex.test('attacker.example.com')` → `true` (passes the loose, heuristic-derived allow-list).
2. `sanitizedShop = 'attacker.example.com'`.
3. `applyDomainTransformations('attacker.example.com', config)` is called; it tests the *real* regex `/^([a-zA-Z0-9-_]+)\.(dev|staging)\.example\.com$/`, which does **not** match `attacker.example.com` (no `.dev.`/`.staging.` segment).
4. Since no transformation matches, `applyDomainTransformations` falls through to its final `return shopUrl;`, returning the original, unmodified string: [5](#0-4) 

`sanitizeShop` then returns `'attacker.example.com'` as a validated shop, even though it is neither a genuine Shopify domain nor a value that satisfies the configured transformation rule.

### Impact Explanation
`sanitizeShop` output is treated throughout the library and app packages as a trusted, validated shop domain and is used to build outbound requests and IDs:
- OAuth begin flow constructs the redirect URL directly from the sanitized shop: `https://${cleanShop}/admin/oauth/authorize...` [6](#0-5) 
- It's used to build session IDs (`getJwtSessionId`, `getOfflineId`) which are looked up/stored in session storage: [7](#0-6) 
- Express/React Router/Remix middleware use `sanitizeShop` to gate whether to redirect to auth or continue processing: [8](#0-7) , [9](#0-8) 

Because a value that bypasses the intended domain restriction can flow into the OAuth-begin redirect construction, an app configured with a `domainTransformations` rule that uses an alternation/optional-group pattern (a pattern the code itself documents as unsupported) can be induced to build an authorize/redirect URL pointing at an attacker-chosen host under the falsely-allow-listed suffix domain, and can create/lookup session identifiers keyed off an unintended shop string. This is a validation/allow-list bypass rooted in the same root cause class as `addDust`: two calculations meant to represent the same constraint are computed on different bases and can diverge.

### Likelihood Explanation
This is only reachable in apps that explicitly opt into the `domainTransformations` future/config feature and configure a `match` pattern falling into the documented "Unsupported" category (alternations, optional groups, or character classes in the domain segment). It is not exploitable in the default configuration (no `domainTransformations`) or when transformation patterns use simple literal subdomains, since the extraction heuristic works correctly for the "supported" cases exercised in `domain-transformer.test.ts`. I could not fully verify from static review alone how many downstream call sites accept attacker-controlled `shop` values before this check versus after other independent guards (e.g., HMAC/state validation in the OAuth callback would still separately need to succeed for a full account-takeover-style attack) — a background agent should trace all `sanitizeShop`/`sanitizeHost` call sites to confirm whether any allow an unauthenticated actor to supply the `shop` parameter feeding into this path.

### Recommendation
- Do not derive the shop/host allow-list from a heuristic regex-source extraction. Instead, validate a candidate shop directly by attempting to match it against each configured `transformation.match` regex (and the standard Shopify domain regex), rather than building a separate "extracted domain" allow-list.
- Alternatively, require `domainTransformations[].match` to be restricted to a documented-safe subset (single literal domain suffix, no alternation/optional groups) and validate that constraint at configuration time (throw at startup if unsupported), rather than silently degrading to a looser match at runtime with only a debug log.
- Add regression tests asserting that `sanitizeShop` rejects any shop value that would fail `applyDomainTransformations`'s real match for every entry in `domainTransformations`, for both simple and "unsupported" pattern shapes.

### Proof of Concept
```ts
import {shopifyApi} from '@shopify/shopify-api';
import {testConfig} from '../../__tests__/test-config';

const shopify = shopifyApi(
  testConfig({
    domainTransformations: [
      {
        // Pattern explicitly documented as "Unsupported" for domain extraction
        match: /^([a-zA-Z0-9-_]+)\.(dev|staging)\.example\.com$/,
        transform: '$1.api.example.com',
      },
    ],
  }),
);

// Does NOT match the real transformation regex (missing .dev./.staging. segment)
const result = shopify.utils.sanitizeShop('attacker.example.com');

// Expected: null (should be rejected, not a valid Shopify domain nor a domain
// satisfying the configured transformation rule)
// Actual: 'attacker.example.com' -- passes validation unchanged
console.log(result);
```
Because `getTransformationDomains` extracts only `example\.com` from the alternation regex source, `sanitizeShop`'s allow-list regex accepts any `*.example.com`, while `applyDomainTransformations` (using the real regex) fails to match and returns the value unchanged — producing a "sanitized" shop string that was never actually validated against the intended rule.

```typescript
export function sanitizeShop(config: ConfigInterface) {
  return (shop: string, throwOnInvalid = false): string | null => {
    let shopUrl = shop;
    const domainsRegex = [
      'myshopify\\.com',
      'shopify\\.com',
      'myshopify\\.io',
      'shop\\.dev',
    ];

    // Add domains from transformations (both source and target)
    if (config.domainTransformations) {
      domainsRegex.push(...getTransformationDomains(config));
    }

    const shopUrlRegex = new RegExp(
      `^[a-zA-Z0-9][a-zA-Z0-9-_]*\\.(${domainsRegex.join('|')})[/]*$`,
    );
```
