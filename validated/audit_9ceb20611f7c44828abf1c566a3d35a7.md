### Title
`DeleteAccount` With `beneficiary_id == account_id` Burns the Account Balance Instead of Preserving It — (`File: runtime/runtime/src/actions.rs`)

### Summary

`action_delete_account` enqueues a balance-refund receipt addressed to `beneficiary_id` **before** it removes the account from the trie. When `beneficiary_id == account_id` (self-deletion), the account is gone by the time that refund receipt executes, the transfer fails, and the entire account balance is permanently burned. No validation prevents a user from supplying their own account ID as the beneficiary.

### Finding Description

In `action_delete_account` the execution order is:

1. Read `account_balance = account_ref.amount()`.
2. Push `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` onto `result.new_receipts`.
3. Call `remove_account(state_update, account_id)` — the account is erased from the trie. [1](#0-0) 

The refund receipt is processed in a later chunk. At that point `get_account(state_update, account_id)` returns `None`. `check_account_existence` for a `Transfer` action on a missing account calls `check_transfer_to_nonexisting_account`, which returns `AccountDoesNotExist` because `implicit_account_creation_eligible` is `false` for system-predecessor (refund) receipts. [2](#0-1) 

A failed refund receipt burns its deposit into `other_burnt_amount` rather than generating a further refund. The user's balance is therefore permanently destroyed.

The default `delete_account` helper in the integration layer already sets `beneficiary_id = signer_id`, and the existing test `test_delete_account_ok` exercises exactly this self-deletion path and asserts only that the account is gone — it never checks that the balance reached anyone. [3](#0-2) [4](#0-3) 

### Impact Explanation

Any user who submits a `DeleteAccount` action with `beneficiary_id` equal to their own `account_id` loses their entire liquid balance. The balance is not transferred to any party; it is burned. This satisfies the "loss of funds" impact criterion.

### Likelihood Explanation

The scenario is reachable by any unprivileged user with a single ordinary transaction. The default SDK/integration helper already produces this configuration. A user who intends to "close and cash out" their account by naming themselves as beneficiary will silently lose all funds with no error returned to them (the outer `DeleteAccount` receipt succeeds; only the inner refund receipt fails silently).

### Recommendation

Add a validation check in `action_delete_account` (or in the action-validation layer) that rejects `DeleteAccountAction` when `beneficiary_id == account_id`:

```rust
if &delete_account.beneficiary_id == account_id {
    result.result = Err(ActionErrorKind::DeleteAccountWithSelfAsBeneficiary {
        account_id: account_id.clone(),
    }.into());
    return Ok(());
}
```

Alternatively, handle the self-deletion case by simply zeroing the account balance in-place (no refund receipt) and crediting it nowhere, with a clear protocol-level note that self-deletion burns the balance — but the former option is safer.

### Proof of Concept

```
1. Alice has account "alice.near" with 10 NEAR.
2. Alice submits:
     SignedTransaction {
       signer_id:   "alice.near",
       receiver_id: "alice.near",
       actions: [DeleteAccount { beneficiary_id: "alice.near" }]
     }
3. action_delete_account runs:
   - account_balance = 10 NEAR
   - new_receipts.push(Receipt::new_balance_refund("alice.near", 10 NEAR))
   - remove_account(state_update, "alice.near")   // account gone
4. Outer receipt outcome: SuccessValue([])         // appears successful
5. Refund receipt processed next chunk:
   - get_account("alice.near") -> None
   - check_account_existence -> AccountDoesNotExist
   - Receipt fails; 10 NEAR burned into other_burnt_amount
6. Net result: Alice's 10 NEAR is permanently destroyed.
``` [5](#0-4) [6](#0-5)

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
