### Title
Non-deterministic HashMap Iteration Order in `VoteWitnessProcessor` Causing State-Serialization Divergence - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/VoteWitnessProcessor.java`)

### Summary
`VoteWitnessProcessor.execute()`, the TVM native-contract handler for `VoteWitnessContract`, deduplicates/merges votes for the same witness using a `java.util.HashMap<ByteString, Long>` and then iterates that map's `entrySet()` to append entries to the account's and votes-capsule's repeated protobuf vote fields, in whatever order the `HashMap` happens to yield.

### Finding Description
The relevant code builds `voteMap` and later iterates it to mutate persisted state: [1](#0-0) [2](#0-1) [3](#0-2) 

Each iteration appends a new `Vote` entry to a protobuf repeated field via `AccountCapsule.addVotes()` and `VotesCapsule.addNewVotes()`, and `addNewVotes` simply calls `Votes.Builder.addNewVotes(...)`, which appends in call order to the underlying `Votes` message: [4](#0-3) 

Because `java.util.HashMap` explicitly does not guarantee any particular iteration order (per its Javadoc contract), the order in which `voteMap.entrySet()` yields entries — and therefore the order of `Vote` entries appended into `accountCapsule`'s and `votesCapsule`'s repeated fields — is unspecified and can differ across JVM vendors/versions even for the exact same input transaction. Since these fields are part of the serialized `AccountCapsule`/`VotesCapsule` bytes that get persisted (`repo.updateAccount`, `repo.updateVotes`) and ultimately committed to the account/votes stores that feed the chain state, a differing byte-serialization order for logically identical vote sets can cause account/votes store content — and any hash computed over it (e.g., merkle/state root or store-level hashing) — to diverge between nodes that do not share bit-for-bit identical `HashMap` bucket layout behavior for these keys, mirroring the reported "non-deterministic ranges" bug class in `inference_synthesis` (map iteration order leaking into persisted/consensus-relevant state).

This differs from the ordinary `VoteWitnessActuator.countVoteAccount()` path, which iterates the contract's vote list directly (already deterministic, no intermediate `HashMap` merge step) and therefore is not affected the same way.

### Impact Explanation
If the append order of votes leaks into the persisted `Account`/`Votes` protobuf byte representation and that representation participates in state hashing/consensus verification, different full nodes could compute different serialized bytes for the same block/transaction, leading to state divergence, chain forks, or consensus halts — a legitimate invalid-state/divergence impact class. The severity depends on whether the account/votes store's serialized bytes are included in any cryptographic commitment checked across nodes (this could not be fully confirmed from the available index without deeper inspection of the account-store hashing/merkle logic).

### Likelihood Explanation
Triggering requires a `VoteWitnessContract` executed through the TVM native-contract path (`VoteWitnessProcessor`) where a voter casts multiple votes for the same witness address in one transaction (so the merge/dedup `HashMap` path is exercised) — an unprivileged, ordinary user action reachable through normal contract execution, not a trusted-role action.

### Recommendation
Replace the `HashMap<ByteString, Long>` in `VoteWitnessProcessor.execute()` with an order-preserving structure, e.g., `LinkedHashMap`, or better, iterate/merge votes while preserving the original input order (or sort deterministically, e.g., by witness address bytes) before appending to `accountCapsule`/`votesCapsule`, ensuring the resulting serialized bytes are deterministic across all nodes regardless of JVM/HashMap implementation.

### Proof of Concept
1. Submit a `VoteWitnessContract` (via the TVM native-contract call path that reaches `VoteWitnessProcessor.execute()`) with votes for witnesses `W1` and `W2` where `W1` appears twice (to force the merge branch at lines 82-85).
2. Observe that `voteMap` is populated via `HashMap.put`, and the final `for (Map.Entry<ByteString, Long> entry : voteMap.entrySet())` loop (lines 105-108) appends `W1`/`W2` in `HashMap` iteration order rather than input order.
3. Run identical input on two JVMs with different `HashMap` implementation internals (different vendor/version), and compare the serialized bytes of the resulting `AccountCapsule`/`VotesCapsule` (`accountCapsule.getData()` / `votesCapsule.getData()`) — the byte order of the repeated `votes`/`new_votes` field can differ, demonstrating serialization divergence for logically identical inputs.
