### Title
Silent double-precision division corrupts Exchange (Bancor-style) pool balances when `allowHardenExchangeCalculation` is disabled — legacy `ExchangeProcessor` does not throw on divide-by-zero/overflow - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The reported bug is a Solidity-style integer division-by-zero that permanently DoSes a vault. In java-tron, the analogous defect exists in the legacy (non-hardened) TRX/token Exchange (Bancor relay) math used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`. Unlike Solidity `uint256` division, Java `double` division by zero does **not** throw — it silently yields `Infinity`/`NaN`, which is then narrowed to a `long`. This can corrupt on-chain exchange pool balances instead of reverting, and is only prevented when the chain parameter `allowHardenExchangeCalculation` is enabled (switching to `SafeExchangeProcessor`, which uses `BigDecimal` and does throw `ArithmeticException`).

### Finding Description
`ExchangeCapsule.transaction()` selects between two math engines based on the `hardenedCalc` flag (`allowHarden()`, driven by the `allowHardenExchangeCalculation` dynamic parameter): [1](#0-0) 

When hardening is **not** enabled, `ExchangeProcessor` (plain-`double` Bancor formula) is used: [2](#0-1) 

`exchangeToSupply` divides `quant` by `newBalance` (`balance + quant`); `exchangeFromSupply` divides `supplyQuant` by the running `supply` variable, which is mutated (`supply -= supplyQuant`) across the call. If `newBalance` or the post-subtraction `supply` reaches `0` (or goes negative for `supply`), the division does not throw in Java for primitive `double` — it produces `Infinity`, `-Infinity`, or `NaN`. Casting `(long) issuedSupply`/`(long) exchangeBalance` from these special values yields `Long.MAX_VALUE`/`Long.MIN_VALUE`/`0` deterministically rather than reverting the transaction.

The callers only guard against the *pool* balances being exactly zero before the trade (`firstTokenBalance == 0 || secondTokenBalance == 0`), e.g. in `ExchangeTransactionActuator.doValidate()`: [3](#0-2) 
and in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` similarly. None of these actuators validate the *intermediate* `newBalance` (`balance + quant`, only overflow-checked, not zero-checked) or the internal `supply` state used only within `ExchangeProcessor`, since that state is entirely internal and not exposed for validation. A carefully chosen `sellTokenQuant` value (near the current pool balance, exploiting floating-point precision, or driving the internal relay `supply` down to zero/negative) can push the double math into the `Infinity`/`NaN` regime.

Contrast this with `SafeExchangeProcessor`, the hardened analog, which explicitly throws `ArithmeticException` on such degenerate cases (confirmed by test `testSafeProcessorDivByZeroThrows`): [4](#0-3) 
This proves the root cause is specifically the legacy `ExchangeProcessor`'s use of unchecked primitive `double` arithmetic instead of range-checked math, and that the fix already exists but is optional/behind a governance flag.

The result is written back into consensus state via `ExchangeCapsule.setBalance(...)` inside `transaction()`: [5](#0-4) 
Because `hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)` is the *only* post-hoc sanity check, and it is skipped entirely when `hardenedCalc == false` (legacy mode), corrupted (e.g. absurdly large or negative-looking-as-huge-unsigned) pool balances can be persisted without any exception, silently breaking the exchange's invariants for all future trades against that pool — an on-chain accounting corruption, not merely a revert.

### Impact Explanation
If triggered, the affected `Exchange`/`ExchangeV2` pool's `first_token_balance`/`second_token_balance` fields can be corrupted to extreme values (via `Infinity`→`Long.MAX_VALUE` or `NaN`→`0` casts) that are committed to chain state. This breaks the AMM invariant for that exchange pair, at minimum causing all subsequent trades against the pool to behave incorrectly (asset accounting corruption, an outcome directly comparable in severity to the referenced report's "funds locked/DoS"), and at worst allowing a party to extract disproportionate amounts of the other token from the pool before the corruption is noticed. This affects any TRC10/TRX exchange created via `ExchangeCreateContract` and traded via `ExchangeTransactionContract` — both reachable by any unprivileged account through a broadcast transaction.

### Likelihood Explanation
Exploitability depends on the network parameter `allowHardenExchangeCalculation` being disabled (legacy behavior, which is/was the historical default before the hardening proposal was activated). While the SR-controlled proposal can enable hardened math, any historical or currently-non-hardened deployment (or one where the maintainers have not yet activated the corresponding chain parameter) remains exposed. Precisely engineering the floating point inputs that push the Bancor relay `supply`/`newBalance` into a degenerate (zero/negative) state requires careful crafting of `sellTokenQuant` relative to existing pool reserves, but is fully within reach of an unprivileged account issuing normal `ExchangeInjectContract`/`ExchangeTransactionContract`/`ExchangeWithdrawContract` transactions repeatedly to manipulate reserves toward the edge case, then submitting the triggering trade.

### Recommendation
- Deprecate/remove `ExchangeProcessor` (the plain-`double` legacy path) entirely, or force `SafeExchangeProcessor` unconditionally regardless of the `allowHardenExchangeCalculation`/`allowStrictMath` flags, since the hardened processor already correctly throws on these degenerate states.
- If backward-compatibility requires keeping the legacy path, explicitly check for `Double.isInfinite`/`Double.isNaN` on `issuedSupply`/`exchangeBalance` in `ExchangeProcessor` before casting to `long`, and throw `ArithmeticException` to force the actuator's existing catch-and-fail logic.
- Add a post-condition check in `ExchangeCapsule.transaction()` that validates `newFirstTokenBalance > 0 && newSecondTokenBalance > 0` unconditionally (not just when `hardenedCalc` is true), so any pool corruption fails the transaction instead of being persisted.

### Proof of Concept
Not independently reproduced against a running node (no execution environment available); the vulnerable code path and the demonstrated behavioral gap between `ExchangeProcessor` (silent `Infinity`/`NaN`→`long` cast, no exception) and `SafeExchangeProcessor` (explicit `ArithmeticException`, verified in `testSafeProcessorDivByZeroThrows`) is established purely via static code reading and the existing test asserting the hardened processor's exception-throwing behavior for a directly analogous input (`exchange(-1L, 100L, 1L)` making `newBalance == 0`): [4](#0-3) 
No equivalent test exists asserting that `ExchangeProcessor` (legacy, non-hardened) throws under the same conditions, and by Java semantics for primitive `double` division it does not.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

  }
