### Title
`many_ref_accounts_can_be_moved` byte-sum estimate can under-count actual packed-storage count, letting `combine_ancient_slots_packed_internal` move a multi-ref account's newest entry to a slot lower than its true owning slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` decides whether it is safe to move the "newest alive" copies of multi-reference pubkeys into packed ancient storages by estimating the number of packed storages they will require from a simple byte-sum division (`alive_bytes / ideal_storage_size + 1`). The actual packing performed afterward by `PackedAncientStorage::pack` is a sequential first-fit bin-packer that can require strictly more storages than this estimate when the many-ref chunks (one per origin slot) have sizes that do not tile evenly into `ideal_storage_size`. When that happens, the extra spill-over packed storage is zipped (in `write_packed_storages`) to a target slot lower than the one verified as safe by `many_ref_accounts_can_be_moved`, which can place a pubkey's newest-alive entry at a new slot below its true originating slot.

### Finding Description
`many_ref_accounts_can_be_moved` (`accounts-db/src/ancient_append_vecs.rs:390-415`) computes:
```
let required_ideal_packed = (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;
...
let highest_slot = target_slots_sorted[i_last]; // i_last = len - required_ideal_packed
many_refs_newest.iter().all(|many| many.slot <= highest_slot)
``` [1](#0-0) 

This assumes the many-ref-newest data will occupy at most `required_ideal_packed` packed storages (the top `required_ideal_packed` entries of `target_slots_sorted`), and only checks that the lowest of those top slots is `>=` every many-ref account's current slot. It does not verify that `PackedAncientStorage::pack` will actually fit the data into exactly that many storages.

`PackedAncientStorage::pack` (`accounts-db/src/ancient_append_vecs.rs:1012-1094`) is a strict first-fit sequential packer: for each origin-slot chunk (`AliveAccounts`, tagged with a single `slot`), it appends accounts to the current storage until the next account would exceed `ideal_size`, then starts a new storage. Because chunks from different origin slots are never reordered or split intelligently across boundaries, an attacker who controls account sizes can force each many-ref chunk to occupy its own storage with large amounts of wasted space (e.g., chunks sized just over half of `ideal_storage_size` cannot share a storage), so the *actual* number of storages consumed by many-ref data can exceed `required_ideal_packed`, which is only guaranteed to be `>= ceil(alive_bytes / ideal_storage_size)`.

In `combine_ancient_slots_packed_internal` (`accounts-db/src/ancient_append_vecs.rs:417-518`), after `many_ref_accounts_can_be_moved` returns true, the actual `pack` is built and only checked with:
```
if pack.len() > accounts_to_combine.target_slots_sorted.len() { return; }
``` [2](#0-1) 
This only bounds the *total* number of packed storages against the *total* number of available target slots - it does not re-validate that every many-ref chunk still lands on a target slot `>=` its origin slot. `write_packed_storages` (`accounts-db/src/ancient_append_vecs.rs:646-701`) then zips `packed_contents` (in fill order, i.e., highest-slot many-ref data first) against `target_slots_sorted.iter().rev()` (highest target slot first). If fragmentation caused one extra storage to be consumed by many-ref data beyond what `many_ref_accounts_can_be_moved` verified, that extra storage is assigned to the next-lower, previously *unverified* target slot, which can be below the many-ref account's true originating slot.

An attacker (unprivileged) can engineer this by: creating a pubkey and repeatedly rewriting it across several ancient-eligible slots (making it a multi-ref pubkey), controlling the data size of each write (and thus each origin slot's aggregate `alive.bytes`) so that adjacent many-ref chunks are just over half of `ideal_storage_size`, forcing one chunk per packed storage. When enough such slots are aged past `ancient_append_vec_offset` and `combine_ancient_slots_packed` runs, the byte-sum estimate under-counts the storages actually required, and the invariant documented in the function's own comment - "accounts in `many_refs_newest` must be moved a slot >= each account's current slot" - can be violated for the spill-over chunk.

### Impact Explanation
If a multi-ref pubkey's newest-alive entry is written to a packed storage at a slot number lower than its true originating slot, the accounts index for that pubkey can end up with an entry at a lower slot than another (older) entry of the same pubkey that remains untouched at its original (now numerically higher) slot. Any logic that treats "highest slot in the index slot-list" as "most recent/live" state can then read the stale, older account version as authoritative, causing a silent balance/state divergence and accounts-hash mismatch between nodes that ran ancient packing on different schedules (bank-hash divergence category).

### Likelihood Explanation
This requires: (1) a pubkey with `>1` alive reference spread across several ancient-eligible slots, entirely attacker-controllable via ordinary account writes; (2) careful sizing of each write so that the aggregate many-ref bytes per origin slot straddle the `ideal_storage_size / 2` boundary to force first-fit fragmentation; (3) the periodic ancient-slot combining path (`shrink_ancient_slots` → `combine_ancient_slots_packed`) to run over the affected slot range with a tight `target_slots_sorted` (little slack beyond the byte-estimate). Because `ideal_storage_size` for real ancient packing is `128MB` (`get_ancient_append_vec_capacity`), triggering an off-by-one storage requires substantial account data volume, which raises cost/feasibility but does not require any validator or leader privilege - only account creation, resizing, and rewriting, which is within the stated attacker model.

### Recommendation
Make `many_ref_accounts_can_be_moved`'s estimate match (or exceed) what `PackedAncientStorage::pack` will actually produce, e.g., by running the same first-fit packing algorithm (or a safe over-approximation of it, worst-case accounting for one wasted storage per many-ref chunk boundary) to compute `required_ideal_packed`, or by post-validating after `PackedAncientStorage::pack` that every resulting chunk's origin slot is `<=` the target slot it is actually zipped to in `write_packed_storages`, aborting the pack (as is already done for the total-length case) if any chunk violates the ordering invariant.

### Proof of Concept
Add a unit test in `accounts-db/src/ancient_append_vecs.rs` alongside `test_many_ref_accounts_can_be_moved` that:
1. Builds `many_refs_newest` as multiple `AliveAccounts` entries at descending slots, each with `bytes` set to `ideal_storage_size/2 + 1` (so no two chunks fit in one storage together).
2. Builds `target_slots_sorted` with only `ceil(total_bytes/ideal_storage_size)` slots at/above the required boundary (i.e., exactly matching `many_ref_accounts_can_be_moved`'s estimate), asserting the function returns `true`.
3. Feeds the same `many_refs_newest` (with real `AccountFromStorage` entries) into `PackedAncientStorage::pack(..., ideal_storage_size)` and asserts `pack.len() > required_ideal_packed`, demonstrating the estimate mismatch.
4. End-to-end: construct real storages via `create_storages_and_update_index` reproducing this byte layout, call `combine_ancient_slots_packed_internal`, then assert for every written account that its new slot (target slot it was packed into) is `>=` its slot in the original index entry (`db.accounts_index` lookup before combining), expecting the assertion to fail, proving the invariant violation.
