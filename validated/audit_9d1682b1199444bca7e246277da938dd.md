### Title
Signature-quorum path broadcasts block acceptance without re-checking chainstate/conflict state that the pre-commit path enforces - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit` re-runs `check_block_against_signer_db_state` and the signed-conflict/freshness checks immediately before a signer commits to signing a block, specifically because the local chain/signer-db state may have changed materially since the block passed its original proposal-time checks. `store_and_process_block_signature`, which is the function that decides when a *quorum of signatures* (rather than pre-commits) has been reached and then marks the block `mark_locally_accepted` and broadcasts it, does **not** perform this same re-check before broadcasting.

### Finding Description
`handle_block_pre_commit` explicitly re-verifies state right at the moment the pre-commit weight crosses the threshold, with the comment: "The chain and signer db state may have changed materially since this block passed the proposal-time checks... Re-run the chainstate checks before putting a signature over the block, and respond with a rejection if they no longer pass" [1](#0-0) . It then also re-checks for fresher conflicting signed blocks in ANY tenure before finally signing [2](#0-1) .

By contrast, `store_and_process_block_signature` — the sibling function that decides whether *signature* weight (as opposed to pre-commit weight) has crossed the broadcast threshold — goes straight from computing `total_signature_weight >= min_weight` to `block_info.mark_locally_accepted(true)`, `insert_block`, and `broadcast_signed_block`, with no call to `check_block_against_signer_db_state` or to the conflict/freshness logic that guards the pre-commit path [3](#0-2) . The only "outdated version" fallback treats an unseen signature as a pre-commit and routes it through `handle_block_pre_commit` (which does the recheck), but once `signed_self`/pre-commit bookkeeping already exists for the caller, that guard is skipped and threshold-crossing goes straight to broadcast [4](#0-3) .

This asymmetry means the "final gate" before this signer's node observes and broadcasts a block as accepted is not re-validated against the signer's current local chain view, the way it explicitly is for the pre-commit gate. Between the time the last signature needed to cross threshold arrives and the moment the signer accepts/broadcasts, the local signer may already have signed or locally-accepted a conflicting sibling at the same or higher height (exactly the scenario the pre-commit path's comment describes as motivating its recheck), yet the signature path will still broadcast acceptance for the older/conflicting block.

### Impact Explanation
This is a minority-triggerable, unprivileged path: any signer whose signature arrives last to cross the group threshold can cause this signer to broadcast "accepted" for a block it would otherwise refuse to sign per the pre-commit-path logic. The result is a temporary tip/acceptance disagreement between signers — some signers end up broadcasting acceptance for a stale/conflicting sibling block while their own local chainstate has already moved past it — matching the "temporary tip disagreement" category the rules classify as High.

### Likelihood Explanation
The condition requires only that signatures accumulate slower than pre-commits for the same block (plausible under normal network jitter, since pre-commits are lightweight while it may take longer to gather full BlockAccepted signatures), and that the local signer signs/accepts a conflicting sibling in the interim — a scenario the codebase's own comments acknowledge is expected to happen ("we may have signed a different block at the same height, possibly in another tenure"). No majority collusion or privileged access is needed; it can occur under ordinary reorg/re-proposal timing.

### Recommendation
Call the same re-validation (`check_block_against_signer_db_state`, plus the signed-conflict/freshness check used in `handle_block_pre_commit`) inside `store_and_process_block_signature` immediately before `mark_locally_accepted`/broadcast, mirroring the pattern already used for the pre-commit threshold path, so that both threshold-crossing gates enforce the same up-to-date chainstate check before a signer commits to an acceptance decision.

### Proof of Concept
1. Block B is proposed and validated; several signers pre-commit and sign it, but total signature weight is still below `min_weight`.
2. Time passes; a competing/conflicting sibling block B' at the same height is proposed and this local signer signs/locally-accepts B' (updating its own chainstate/signer-db view).
3. A remaining signature for B arrives from a slow signer, pushing accumulated signature weight for B over `min_weight` in `store_and_process_block_signature`.
4. Because this function does not re-run `check_block_against_signer_db_state`/conflict checks (unlike `handle_block_pre_commit`), it proceeds directly to `mark_locally_accepted(true)` and `broadcast_signed_block` for B, even though the signer's own current chainstate view already favors B'.
5. Other signers now observe this signer asserting acceptance of B while it has itself accepted B' — a temporary disagreement about the accepted tip that the pre-commit path was specifically designed to prevent but which the signature-quorum path does not guard against.

        // A pre-commit may be superseded by a competing proposal at the same height (e.g. a
        // re-proposed tenure-start block after the first failed to reach consensus), but a
        // signature must not be superseded while it's still "fresh". A signed block at the
        // same or higher height in ANY tenure is a conflict: two blocks at the same height are
        // siblings no matter which tenure they belong to (e.g. the next tenure's tenure-start
        // block conflicts with the current tenure's block at the same height). Blocks in
        // tenures whose reorg we sanctioned under the reorg-timing rules are excluded, but
        // only while the sortition the permit was granted to is still canonical
        // (`check_parent_tenure_choice` records the permit, `reorg_permit_stands` re-derives
        // its validity from the node); every other question about whether a conflict is
        // still live is derived from the node in `conflict_still_blocks`.
        //
        // Unlike the chainstate check above, a refusal here is "for now" rather than a
        // broadcast rejection: a later pre-commit re-evaluation may still sign the block once
        // the conflicting signature has gone stale.
        let conflicts = match self
            .signer_db
            .get_signed_conflicts(block_info.block.header.chain_length, &block_hash)
        {
            Ok(conflicts) => conflicts,
            Err(e) => {
                warn!("{self}: Failed to query the signed blocks. Refusing to sign block {block_hash}: {e:?}");
                return;
            }
        };
        let freshness_cutoff = get_epoch_time_secs().saturating_sub(
            self.proposal_config
                .tenure_last_block_proposal_timeout
                .as_secs(),
        );
        // A fresh signature only blocks while the block it covers could still be part of the
        // chain: see `conflict_still_blocks`, which asks the node whether it is. Check
        // freshness first: it is a local timestamp comparison, while `reorg_permit_stands`
        // and `conflict_still_blocks` each query the node, so stale conflicts cost no
        // round-trips.
        if let Some(conflict) = conflicts.iter().find(|conflict| {
            conflict.last_endorsed > freshness_cutoff
                && !self.reorg_permit_stands(stacks_client, conflict)
                && self.conflict_still_blocks(
                    stacks_client,
                    conflict,
                    block_info.block.header.chain_length,
                )
        }) {
            warn!(
                "{self}: Reached the pre-commit threshold for a block, but we have recently signed or accepted a different block at the same or higher height. Refusing to sign.";
                "signer_signature_hash" => %block_hash,
                "block_height" => block_info.block.header.chain_length,
                "conflicting_signer_signature_hash" => %conflict.signer_signature_hash,
                "conflicting_block_height" => conflict.stacks_height,
                "conflicting_consensus_hash" => %conflict.consensus_hash,
            );
            return;
