Based on my investigation, I found a legitimate unsafe-division analog in the Ethereum-VM energy accounting path of java-tron.

### Title
Unguarded division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` relies on a no-op `assert` instead of a runtime check - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` but the only guard against a zero divisor is a Java `assert` statement, which is compiled out and never executes unless the JVM is started with `-ea`. In default node configurations this is a no-op, so the division is effectively unchecked, exactly the "unsafe division without validating the divisor" pattern described in the LibMathEx report (missing zero-check before `/`).

### Finding Description
`calculateGlobalEnergyLimit` computes the amount of energy an account may consume based on its frozen balance relative to the network-wide `totalEnergyWeight`: [1](#0-0) 

```
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

assert totalEnergyWeight > 0;

if (hardenResourceCalculation()) {
  return BigInteger.valueOf(energyWeight)
      .multiply(BigInteger.valueOf(totalEnergyLimit))
      .divide(BigInteger.valueOf(totalEnergyWeight))
      .longValueExact();
}
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```

Unlike its sibling implementations, which perform a real runtime check before dividing:
- `EnergyProcessor.calculateGlobalEnergyLimit` returns `0` when `allowNewReward()` is set and `totalEnergyWeight <= 0` [2](#0-1) 
- `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` explicitly `return 0` `if (totalNetWeight == 0)` [3](#0-2) 

`RepositoryImpl.calculateGlobalEnergyLimit` has no such fallback — it only has the `assert`. Java assertions are disabled by default (`-da`), so in essentially every production deployment this statement does nothing at runtime; if `totalEnergyWeight` is `0` and `hardenResourceCalculation()` is enabled, `BigInteger.divide(BigInteger.ZERO)` throws an unguarded `ArithmeticException`.

`totalEnergyWeight` is a chain-wide dynamic property (`getDynamicPropertiesStore().getTotalEnergyWeight()`) that reflects the sum of all frozen-for-energy balances; it can legitimately reach `0` (e.g., a private/test chain, or a chain state after mass un-freezing/migration before energy weight is repopulated), which is not something an attacker directly controls but is a reachable chain state during normal contract execution / resource delegation flows that call into `RepositoryImpl`.

### Impact Explanation
If this code path is hit while `totalEnergyWeight == 0` and hardened resource calculation is enabled, it throws an uncaught `ArithmeticException` inside TVM/resource-accounting logic. Depending on the caller, this can abort transaction/block processing unexpectedly. More importantly, because the original protection is a Java `assert` (not a real conditional), behavior differs across nodes depending on whether they run with `-ea`: nodes with assertions enabled fail fast with an `AssertionError` at an earlier point (different code path/timing) than nodes without assertions, which instead proceed to the real division and throw `ArithmeticException` at a different point. This inconsistency in error handling across the network is a potential source of divergent behavior and, at minimum, an unhandled-exception DoS vector during block/transaction processing tied to resource/energy accounting — the exact analog to the missing-zero-check division bug in the report, but embedded in TRON's own resource-accounting math instead of a mock protocol's `LibMathEx`.

### Likelihood Explanation
Likelihood is moderate: `totalEnergyWeight` reaching `0` is not attacker-controlled in a single transaction on an established mainnet (broad energy weight from frozen TRX), but is realistically reachable on new/private/test networks, immediately post-genesis, or during specific migration/parameter states, and the guard is silently absent in all standard production builds because Java assertions are off by default. This is a latent robustness/DoS bug rather than an immediately exploitable one on a mature mainnet, but it is a genuine, reachable, unguarded-division defect matching the reported bug class.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` with an actual runtime guard (e.g., `if (totalEnergyWeight <= 0) { return 0; }`), mirroring the checks already present in `EnergyProcessor` and `BandwidthProcessor`, before performing either the `BigInteger` division or the double-based fallback division. Apply the same audit to any other `RepositoryImpl`/resource-accounting method that uses `assert` as its only safeguard against a zero divisor.

### Proof of Concept
1. Configure/observe a chain state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., freshly initialized private chain before any TRX is frozen for energy, or after all energy-frozen balances are unfrozen).
2. Enable hardened resource calculation (`allowHardenResourceCalculation`).
3. Trigger any code path that calls `RepositoryImpl.calculateGlobalEnergyLimit` for an account with `frozeBalance >= TRX_PRECISION` (e.g., via smart contract execution/energy accounting flows reachable from `VMActuator`/`ContractState`).
4. Because assertions are disabled by default, the `assert totalEnergyWeight > 0;` line executes as a no-op, and `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))` throws `java.lang.ArithmeticException: BigInteger divide by zero`, propagating out of the accounting call. [4](#0-3)
