### Title
Unprivileged `TransferToGasKey` Griefing Locks Gas Key and Account Deletion — (`runtime/runtime/src/actions.rs`, `runtime/runtime/src/access_keys.rs`)

---

### Summary

`Action::TransferToGasKey` carries no actor-permission guard in `check_actor_permissions`. Any unprivileged account can therefore fund a victim's gas key on any account, pushing `GasKeyInfo.balance` above `MAX_BALANCE_TO_BURN = 1 NEAR`. Once that threshold is crossed, both `DeleteKey` and `DeleteAccount` revert with `GasKeyBalanceTooHigh`, permanently blocking those operations until the victim drains the key in a separate step — a step the attacker can keep front-running.

---

### Finding Description

`check_actor_permissions` in `runtime/runtime/src/actions.rs` enforces `actor_id == account_id` for sensitive key-management actions (`AddKey`, `DeleteKey`, `WithdrawFromGasKey`, etc.), but explicitly places `TransferToGasKey` in the unrestricted arm alongside `Transfer` and `FunctionCall`:

```rust
Action::CreateAccount(_)
| Action::FunctionCall(_)
| Action::Transfer(_)
| Action::TransferToGasKey(_) => (),   // ← no permission check
``` [1](#0-0) 

`action_transfer_to_gas_key` then unconditionally adds the deposited amount to `GasKeyInfo.balance`:

```rust
gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit)…;
set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
``` [2](#0-1) 

`delete_gas_key` blocks deletion whenever `balance > MAX_BALANCE_TO_BURN`:

```rust
if gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN {
    result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh { … }.into());
    return Ok(());
}
``` [3](#0-2) 

`MAX_BALANCE_TO_BURN` is 1 NEAR: [4](#0-3) 

`action_delete_account` applies the same aggregate check across all gas keys on the account:

```rust
let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
    result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh { … }.into());
    return Ok(());
}
``` [5](#0-4) 

`WithdrawFromGasKey`, by contrast, **is** gated by the actor check:

```rust
Action::WithdrawFromGasKey(_) => {
    if actor_id != account_id {
        return Err(ActionErrorKind::ActorNoPermission { … }.into());
    }
}
``` [6](#0-5) 

The asymmetry is the root cause: anyone can increase a gas key's balance, but only the owner can decrease it.

---

### Impact Explanation

An attacker submits a `TransferToGasKey` action targeting the victim's gas key with a deposit of `1 NEAR + 1 yoctoNEAR`. This single transaction:

1. Pushes `GasKeyInfo.balance` above `MAX_BALANCE_TO_BURN`.
2. Causes any subsequent standalone `DeleteKey` on that key to revert with `GasKeyBalanceTooHigh`.
3. Causes any subsequent `DeleteAccount` to revert with `GasKeyBalanceTooHigh` (aggregate check).

The victim can recover by including `WithdrawFromGasKey` in the same receipt batch as `DeleteKey`/`DeleteAccount`, because actions within a single receipt execute atomically. However, the attacker can persistently front-run any standalone deletion attempt, forcing the victim to always compose multi-action batches and never rely on simple single-action deletion. If the victim submits only `DeleteKey` or `DeleteAccount` (the natural, documented usage), the transaction fails every time the attacker is watching.

The attacker's deposited NEAR is not lost — it is credited to the gas key balance and can be withdrawn by the victim — but the attacker can repeat the attack at low cost (only gas fees) to maintain the DoS. The victim's account balance is not directly stolen, but the victim's ability to manage their own keys and close their account is broken by an unprivileged third party.

---

### Likelihood Explanation

- Trigger requires only a standard signed transaction with `Action::TransferToGasKey`; no special role, validator access, or privileged key is needed.
- The gas key feature (`ProtocolFeature::GasKeys`, protocol version 85) is live on mainnet.
- Cost to the attacker per harassment round: gas fees only (the deposited NEAR is recoverable by the victim, but the attacker must keep spending gas to re-fund after each victim withdrawal).
- The victim has no on-chain way to prevent third parties from funding their gas key.

---

### Recommendation

Add `Action::TransferToGasKey(_)` to the `actor_id == account_id` arm of `check_actor_permissions` in `runtime/runtime/src/actions.rs`, alongside `WithdrawFromGasKey`. This restricts gas key funding to the account owner and its authorized predecessors (contracts acting on behalf of the account via cross-contract calls where `predecessor_id == account_id`).

If the intended design requires third-party relayers to fund gas keys, a separate, bounded mechanism (e.g., a cap on third-party deposits, or a flag on the gas key permitting external funding) should be introduced rather than leaving the balance unbounded and unguarded. [7](#0-6)

### Proof of Concept

```
// Setup: Alice has account "alice.near" with a GasKeyFullAccess key (pk_gas).
// Gas key balance starts at 0.

// Step 1 — Attacker front-runs Alice's DeleteKey:
// Attacker submits (signed by attacker.near, receiver = alice.near):
//   Action::TransferToGasKey { public_key: pk_gas, deposit: 1_000_000_000_000_000_000_000_001 }
//   (= 1 NEAR + 1 yoctoNEAR)
// → action_transfer_to_gas_key executes; no actor check fires.
// → GasKeyInfo { balance: 1_000_000_000_000_000_000_000_001, … } written to trie.

// Step 2 — Alice's DeleteKey arrives in the same or next block:
//   Action::DeleteKey { public_key: pk_gas }
// → delete_gas_key checks: balance (1e24+1) > MAX_BALANCE_TO_BURN (1e24) → true
// → returns Err(GasKeyBalanceTooHigh { balance: 1_000_000_000_000_000_000_000_001 })
// → Alice's DeleteKey FAILS.

// Step 3 — Alice tries DeleteAccount:
//   Action::DeleteAccount { beneficiary_id: "bob.near" }
// → compute_gas_key_balance_sum returns 1e24+1 > MAX_BALANCE_TO_BURN
// → returns Err(GasKeyBalanceTooHigh)
// → Alice's DeleteAccount FAILS.

// Recovery (requires Alice to know the workaround):
// Alice submits a single receipt with:
//   [WithdrawFromGasKey { public_key: pk_gas, amount: 1e24+1 },
//    DeleteKey { public_key: pk_gas },
//    DeleteAccount { beneficiary_id: "bob.near" }]
// → WithdrawFromGasKey drains balance to 0 (actor check passes: alice == alice)
// → DeleteKey succeeds (balance == 0 ≤ MAX_BALANCE_TO_BURN)
// → DeleteAccount succeeds
// But attacker can front-run the DeleteKey step again with another TransferToGasKey,
// forcing Alice to always compose this three-action batch and never use simple deletion.
``` [8](#0-7) [5](#0-4)

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}

fn delete_gas_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
) -> Result<(), RuntimeError> {
    if gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: Some(Box::new(public_key.clone())),
            balance: gas_key_info.balance,
        }
        .into());
        return Ok(());
    }
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_info.balance).ok_or(IntegerOverflowError)?;
    let num_nonces = gas_key_info.num_nonces as usize;
    for i in 0..gas_key_info.num_nonces {
        remove_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i);
    }
    let nonce_key_len = gas_key_nonce_key_len(account_id, &public_key.into());
    let nonce_remove_compute = storage_removes_compute(
        &config.wasm_config.ext_costs,
        num_nonces,
        nonce_key_len * num_nonces,
        AccessKey::NONCE_VALUE_LEN * num_nonces,
    );
    result.compute_usage = safe_add_compute(result.compute_usage, nonce_remove_compute)?;
    remove_access_key(state_update, account_id.clone(), public_key.clone());
    account.set_storage_usage(account.storage_usage().saturating_sub(gas_key_storage_cost(
        &config.fees,
        public_key,
        access_key,
        gas_key_info.num_nonces,
    )));
    Ok(())
