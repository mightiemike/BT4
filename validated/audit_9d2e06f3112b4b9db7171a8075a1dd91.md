### Title
Version-gated CASM-hash-v1 declare block is bypassable via Declare V2 transactions - ([File: crates/blockifier/src/transaction/transactions.rs])

### Summary
The `block_casm_hash_v1_declares` versioned constant is meant to prohibit declaring new classes whose supplied `compiled_class_hash` is the old Poseidon-based (V1) CASM hash, forcing all new declares to use the Blake-based (V2) hash. However, the enforcement is additionally gated on `self.version() >= TransactionVersion::THREE`, so `DeclareTransaction::V2` (transaction version `0x2`) shares the same code branch as `V3` but never triggers the check, since `TransactionVersion::TWO < TransactionVersion::THREE`. This mirrors the Conic Finance analog: a version-classification gate that is applied to the wrong/incomplete subset of the versioned entities, letting an entity that should be covered by the restriction bypass it.

### Finding Description
In `run_execute` for `DeclareTransaction`, `V2` and `V3` declare variants are handled in the same match arm, but the CASM-hash-v1 block is conditioned on both the flag and `self.version() >= TransactionVersion::THREE`: [1](#0-0) 

Because `DeclareTransaction::V2` always returns `TransactionVersion::TWO` from `self.version()` [2](#0-1) , the condition `self.version() >= TransactionVersion::THREE` is always false for V2 declares, regardless of the `block_casm_hash_v1_declares` flag's value. Consequently `check_compile_class_hash_v2_declaration()` — which validates that the supplied `compiled_class_hash` equals the Blake (V2) hash of the CASM and rejects the transaction with `DeclareTransactionCasmHashMissMatch` otherwise — is only ever invoked for `V3` declares: [3](#0-2) 

`verify_tx_version` confirms `TransactionVersion::TWO` is still an accepted/allowed version for `Declare` transactions [4](#0-3) , so this path remains reachable by any external declarer even after `block_casm_hash_v1_declares` is turned on in versioned constants (the flag is present and toggled across versioned-constants files, e.g. `false`/`true` in the 0.13.x/0.14.x JSON resources) [5](#0-4) .

### Impact Explanation
Once `block_casm_hash_v1_declares` is enabled network-wide with the intent of retiring/preventing new Poseidon(V1)-hashed CASM declarations, an attacker can still declare a class via a `DeclareTransaction::V2` with a V1 (Poseidon) `compiled_class_hash`, silently defeating the protocol-level restriction. This directly undermines the intended state invariant that all newly declared classes carry the V2 (Blake) compiled class hash going forward, which the CASM-hash migration/bouncer machinery (`should_migrate`, `CasmHashMigrationData`) and OS-side hash verification assume as network policy once the flag is on. Because different sequencer/full nodes could diverge in how they treat these grandfathered declares (e.g., some client tooling or future protocol changes may assume the invariant strictly holds post-flag), this can lead to inconsistent state assumptions and undermines the guarantee the flag is meant to enforce — a policy/consensus-invariant bypass reachable directly from an ordinary declare transaction sent by any account.

### Likelihood Explanation
High reachability: any account with a funded sender can submit a standard `DeclareTransaction::V2` (a still-permitted, non-deprecated transaction version) with a Poseidon-hash-based `compiled_class_hash`, with zero special privileges required. The bypass requires no race condition or malicious operator behavior — it's a straightforward logic branch reachable by a single, ordinary transaction.

### Recommendation
Change the check to trigger for both `V2` and `V3` declare transactions (i.e., drop the redundant `self.version() >= TransactionVersion::THREE` condition, or explicitly match on `V2 | V3` when `block_casm_hash_v1_declares` is enabled), so that once the flag is set, no declare transaction variant that carries a `compiled_class_hash` can bypass the V2-hash requirement.

### Proof of Concept
1. Network operator enables `block_casm_hash_v1_declares = true` in versioned constants for a given block/version (as done for the 0.14.x lines).
2. An attacker compiles/declares a Cairo1 contract and computes both the V1 (Poseidon) and V2 (Blake) CASM hashes via `HashableCompiledClass::hash` [6](#0-5) .
3. Attacker submits a `DeclareTransaction::V2` (`starknet_api::transaction::DeclareTransactionV2`) with `compiled_class_hash` set to the V1 (Poseidon) hash rather than V2.
4. In `run_execute`, the transaction matches the `V2 | V3` arm; since `self.version() == TransactionVersion::TWO`, the guard `self.version() >= TransactionVersion::THREE` is false, so `check_compile_class_hash_v2_declaration()` is skipped entirely, and `try_declare` proceeds to store the V1 hash in state [7](#0-6) .
5. Result: the class is declared with a V1 (Poseidon) `compiled_class_hash` in state even though `block_casm_hash_v1_declares` is enabled, whereas the identical attempt via `DeclareTransaction::V3` would be rejected with `DeclareTransactionCasmHashMissMatch`.

    /// Verifies that the compiled class hash field in the declare tx,
    /// is compiled_class_hash_v2 of the compiled contract.
    pub fn check_compile_class_hash_v2_declaration(&self) -> Result<(), StarknetApiError> {
        let compiled_class = &self.class_info.contract_class;
        let compiled_class_hash_v2 = match &compiled_class {
            ContractClass::V0(_) => return Ok(()),
            ContractClass::V1((casm, _)) => casm.hash(&HashVersion::V2),
        };
        let compiled_class_hash = self.compiled_class_hash();
        if compiled_class_hash_v2 != compiled_class_hash {
            let err_var = CasmHashMismatch {
                hash: self.class_hash(),
                actual: compiled_class_hash,
                expected: compiled_class_hash_v2,
            };
            return Err(StarknetApiError::DeclareTransactionCasmHashMissMatch(Box::new(err_var)));
        }
        Ok(())
    }
