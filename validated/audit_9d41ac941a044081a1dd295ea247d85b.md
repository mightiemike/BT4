## Finding: Missing native value attachment in derived UEA payload execution

**Analog identified:** The Lido `WETHGateway` bug (native `msg.value` intended for `submit()` never gets attached, causing always-revert) maps to Push Chain's `CallUEAExecutePayload` helper, which hardcodes `value = big.NewInt(0)` on every `DerivedEVMCall` regardless of what the `UniversalPayload` structure carries.

### Title
Native value is never forwarded from `UniversalPayload` to the derived EVM call in `CallUEAExecutePayload` - (`File: x/uexecutor/keeper/evm.go`)

### Summary
`CallUEAExecutePayload` always passes `big.NewInt(0)` as the `value` argument to `k.evmKeeper.DerivedEVMCall(...)`, so any user payload signed with the intent of moving native PC value through the UEA's `executeUniversalTx` call can never actually attach that value on-chain. [1](#0-0) 

### Finding Description
`DerivedEVMCall` explicitly supports an attacker/user-independent `value *big.Int` parameter meant to carry native value with module- or user-derived EVM calls. [2](#0-1) 
Despite this, every call site in `x/uexecutor/keeper/evm.go` — including `CallUEAExecutePayload`, the function that executes a user's cryptographically signed `UniversalPayload` via `MsgExecutePayload` — passes `big.NewInt(0)` unconditionally: [1](#0-0) 
`ExecutePayloadV2`, the caller of `CallUEAExecutePayload`, does not compute or forward any value either; it only validates the payload/verification data and wraps execution in a cache context for gas-fee accounting. [3](#0-2) 
I located a `Value`-related field referenced in `x/uexecutor/types/decode_payload.go` and `x/uexecutor/types/universal_payload.go`, indicating `UniversalPayload` (or its ABI encoding) carries a value-bearing field, but I was not able to fully read those files before running out of tool iterations — I cannot confirm with certainty whether this field is meant to represent `msg.value` for the UEA call, or purely an internal transfer amount unrelated to native currency. This is the one gap in my verification and should be checked directly in the repo (`x/uexecutor/types/decode_payload.go`, `x/uexecutor/types/universal_payload.go`, `x/uexecutor/types/abi.go`) and against the UEA contract's `executeUniversalTx` signature in `push-chain-core-contracts` before treating this as confirmed.

### Impact Explanation
If `UniversalPayload` is designed to let an owner sign a payload that also moves native PC value through their UEA (e.g. a payable call embedded in the payload, or a `value` component of `executeUniversalTx`), then this hardcoded `0` means:
- Any payload requiring native value forwarding will either revert on execution (mirroring the original Lido bug exactly) or — worse — silently execute the call logic without actually moving the signed value, producing a mismatch between what the owner cryptographically authorized and what state change actually occurred on-chain.
- This is reachable by any ordinary, unprivileged account submitting `MsgExecutePayload` (a gasless, permissionless message per the module's authorization model), so it fits the "denial of service … reachable without privileged control" and "unauthorized state transitions in universal execution flows" impact categories.

### Likelihood Explanation
High likelihood *if* `UniversalPayload` truly encodes a native-value transfer intent — this is a straightforward, always-triggered code path (every `MsgExecutePayload` call goes through `CallUEAExecutePayload`), not a rare edge case. However, likelihood of this being a *security* issue rather than a plain functional/completeness bug depends entirely on confirming that a `Value` field exists in `UniversalPayload` and is expected to become `msg.value` on the destination call. That confirmation is the one piece I could not complete in this pass.

### Recommendation
1. Confirm whether `UniversalPayload` has a value field intended to be forwarded as native currency with the UEA call (check `x/uexecutor/types/universal_payload.go`, `decode_payload.go`, and the UEA contract ABI/interface for `executeUniversalTx`).
2. If confirmed, update `CallUEAExecutePayload` in `x/uexecutor/keeper/evm.go` to parse that value out of `universal_payload` and pass it (as `*big.Int`) into `DerivedEVMCall` instead of the hardcoded `big.NewInt(0)`.
3. Add integration tests asserting that a payload with a non-zero value field actually results in the correct `msg.value` being observed by the destination call/receipt.

### Proof of Concept
Not independently reproducible from the indexed code alone — would require constructing a `UniversalPayload` with a non-zero value field, submitting `MsgExecutePayload`, and observing (via `eth_getTransactionByHash` on the resulting `PCTx.tx_hash`) that the EVM transaction's `value` is `0` regardless of what was signed. This should be validated in a Devin session with full repo/tooling access, given the index-based limitation noted above.

```go
func (k Keeper) ExecutePayloadV2(ctx context.Context, evmFrom common.Address, ueaAddr common.Address, universalPayload *types.UniversalPayload, verificationData string) (*vmtypes.MsgEthereumTxResponse, error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Debug("execute payload v2",
		"uea", ueaAddr.Hex(),
		"from", evmFrom.Hex(),
	)

	// Step 1: Validate payload and verificationData early (fast-fail before EVM work)
	if _, err := types.NewAbiUniversalPayload(universalPayload); err != nil {
		return nil, errors.Wrapf(err, "invalid universal payload")
	}

	verificationDataVal, err := utils.HexToBytes(verificationData)
	if err != nil {
		return nil, errors.Wrapf(err, "invalid verificationData format")
	}

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}
```
