## Finding Confirmed

I traced the full path: `GET /v1/transactions/auxiliary_info` → `TransactionsApi::get_transactions_auxiliary_info` → `list_auxiliary_infos` → `DbReader::get_persisted_auxiliary_info_iterator` → `PersistedAuxiliaryInfoDb`'s RocksDB iterator, and compared it against the sibling iterators (`transaction_db`, `transaction_info_db`, `write_set_db`, `transaction_auxiliary_data_db`) used for the same version range.

### Title
Missing pruning-boundary check and continuity validation on `/v1/transactions/auxiliary_info` causes index-to-version misbinding across the prune point - (File: `storage/aptosdb/src/db/aptosdb_reader.rs`, `storage/aptosdb/src/ledger_db/persisted_auxiliary_info_db.rs`)

### Summary
The `get_transactions_auxiliary_info` endpoint accepts an attacker-chosen `start_version`/`limit` and forwards it, unmodified, to `get_persisted_auxiliary_info_iterator`. Unlike every sibling accessor for the same version range (`get_transaction_iterator`, `get_transaction_outputs`), this call path does **not** invoke `error_if_ledger_pruned` before seeking, and `PersistedAuxiliaryInfoDb`'s iterator does not use the `ExpectContinuousVersions` guard that `TransactionDb`, `TransactionInfoDb`, `WriteSetDb`, and `TransactionAuxiliaryDataDb` all apply.

### Finding Description
`get_transactions_auxiliary_info` builds a `Page` from the raw `start_version`/`limit` query parameters and calls `list_auxiliary_infos`: [1](#0-0) 

`list_auxiliary_infos` computes `start_version`/`limit` and passes them straight into `get_persisted_auxiliary_info_iterator` with no pruning check of its own: [2](#0-1) 

In `AptosDbReader`, the auxiliary-info iterator constructor performs no `error_if_ledger_pruned` call at all, in contrast to the adjacent `get_transaction_iterator`, which explicitly guards against a pruned `start_version`: [3](#0-2) 

The doc comment on the endpoint promises "If the version range has been pruned, a 410 will be returned," but no code on this path enforces that: [4](#0-3) 

Additionally, the sibling column-family iterators (`TransactionDb`, `TransactionInfoDb`, `WriteSetDb`, `TransactionAuxiliaryDataDb`) all validate that returned keys form a contiguous version sequence via `ExpectContinuousVersions::expect_continuous_versions`, e.g.: [5](#0-4) 

`PersistedAuxiliaryInfoDb` does not use this guard on its read iterator (confirmed by the absence of `expect_continuous_versions` in that file, unlike its four siblings). Because RocksDB's `seek(&start_version)` lands on the next existing key when the exact key is absent (e.g., because it was pruned), if `start_version` falls before the persisted-auxiliary-info pruner's progress boundary but the ledger still has non-pruned data for higher versions, the iterator silently begins yielding entries starting at the pruner's progress version rather than at `start_version`. Since the JSON/BCS response is a bare `Vec<PersistedAuxiliaryInfo>` with no explicit per-entry version field, the client is forced to infer each entry's version as `start_version + index`. That inferred version no longer matches the entry actually returned — an authenticated response is silently misbound to the wrong ledger version, with no error surfaced.

### Impact Explanation
This is an authenticated-response misbinding: a legitimate 200 response is returned whose auxiliary-info entries do not correspond to the versions the caller (and anything relying on `start_version + index`, e.g. `RestDebuggerInterface::get_persisted_auxiliary_infos` and `get_committed_transactions`) believes they do. Because `PersistedAuxiliaryInfo` carries per-transaction execution metadata (e.g., in-block transaction index used to resolve BlockEpilogue/BlockMetadata linkage), consumers that zip this vector against independently-fetched transactions/transaction-infos by position will silently associate the wrong auxiliary info with the wrong transaction, corrupting downstream interpretation without any indication of pruning having occurred.

### Likelihood Explanation
This requires only unprivileged HTTP access to the public REST API and a `start_version` chosen to fall inside the pruned prefix while `limit`/ledger height pushes the query across the pruning boundary — no privileged access or malicious peer/node behavior is needed, and pruning is a routine operational occurrence on full/pruned nodes.

### Recommendation
Add an `error_if_ledger_pruned("PersistedAuxiliaryInfo", start_version)` check in `get_persisted_auxiliary_info_iterator` (mirroring `get_transaction_iterator`), and apply the same `ExpectContinuousVersions::expect_continuous_versions` guard used by `TransactionDb`/`TransactionInfoDb`/`WriteSetDb`/`TransactionAuxiliaryDataDb` to `PersistedAuxiliaryInfoDb`'s iterator so that a version gap (from pruning or any other cause) surfaces as an explicit error (mapping to the documented 410) instead of silently shifting the returned entries.

### Proof of Concept
1. Run a node configured to prune ledger data with a small `ledger_prune_window`, and let the persisted-auxiliary-info pruner advance progress past version `V_pruned`.
2. Call `GET /v1/transactions/auxiliary_info?start_version=<version_before_V_pruned>&limit=N` where the range `[start_version, start_version+N)` straddles `V_pruned`.
3. Observe a `200 OK` (not the documented `410`) containing `N` entries.
4. Independently fetch transactions/metadata for versions `start_version..start_version+N` via `/v1/transactions?start=<v>` and compare: entry `i` in the auxiliary-info response corresponds to version `V_pruned + i`, not `start_version + i`, proving the misbinding.

Note: I could not directly view the full body of `PersistedAuxiliaryInfoDb::get_persisted_auxiliary_info_iter` (the file content for that range rendered as blank in the tool, likely a formatting artifact), so the exact RocksDB seek behavior is inferred from the analogous, verified sibling implementation in `transaction_auxiliary_data_db.rs` and from the absence of `expect_continuous_versions` for this schema across the codebase. A background Devin session with full file access should verify this exact function body to remove that residual uncertainty before treating this as fully confirmed.
