## Title
Deleting an account with a non-existent `beneficiary_id` silently burns the account's remaining balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
The Spearbit finding flags that `CoverageFundAddress.set`/`River.setCoverageFund` do not validate the new address against `address(0)`, so a downstream fund-pulling routine silently no-ops instead of reverting. The structurally analogous defect in nearcore is in the `DeleteAccount` action: the `beneficiary_id` supplied by the (unprivileged) transaction signer is validated only for well-formedness, never for existence, before the account is deleted and its balance is redirected to that address. If the address turns out to be unusable (a non-existent named account — the "empty/zero" analog here), the resulting refund receipt fails and the funds are irrecoverably burnt rather than reverting the whole operation.

### Finding Description
`action_delete_account` unconditionally deletes the account and queues a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` for any positive balance, with no check that `beneficiary_id` refers to an existing (or creatable) account: [1](#0-0) 

Validation of `DeleteAccountAction` only rejects a malformed `beneficiary_id` string; it never checks that the account exists: [2](#0-1) 

When the deferred refund receipt is later processed, `implicit_creation_allowed` forbids refunds from ever creating an account, and named accounts can never be implicitly created by a transfer either way: [3](#0-2) 

If the target account doesn't exist, the refund receipt fails with `AccountDoesNotExist`, which is confirmed by the codebase's own regression test asserting exactly this outcome for a refund sent to a missing account id: [4](#0-3) 

Per the protocol's own documentation, a refund receipt that fails to execute has its amount burnt rather than returned or retried: [5](#0-4) 

This is the same bug class as the external report: an address parameter supplied by a transaction is never checked for a degenerate/unusable value ("empty" address(0) there, non-existent `AccountId` here) before it is relied upon to move funds, and the code path that would move the funds silently no-ops (there: skips the pull; here: burns the transfer) instead of reverting the state-changing operation.

### Impact Explanation
By the time the refund fails, the account has already been deleted (`*account = None;` and `remove_account` already ran) as part of the same action — this happens before the refund receipt is even generated/processed. The account owner's entire remaining balance is permanently lost (burnt), removed from total supply, with no way to recover it — a concrete "permanently frozen/lost funds" outcome triggered entirely by a value chosen by the unprivileged transaction signer (or by a relayer in a meta-transaction on the signer's behalf, since `beneficiary_id` is attacker/relayer-controlled input in `DelegateAction`).

### Likelihood Explanation
Any account holder issuing a `DeleteAccount` action can trivially typo, misconfigure, or be tricked (e.g., in a meta-transaction crafted by a malicious relayer) into specifying a `beneficiary_id` that does not exist. There is no confirmation step, no existence check at submission time, and the loss is discovered only after the account is already gone — this requires nothing beyond a single ordinary transaction from a normal user.

### Recommendation
Validate that `beneficiary_id` corresponds to an existing account before performing the deletion (or before creating the refund receipt), and reject the action (returning an error such as `AccountDoesNotExist` for the beneficiary) rather than allowing the delete to proceed and burn the balance. Alternatively, route failed delete-account refunds back through a distinct mechanism that avoids fund destruction (e.g., is delayed/retried or is refunded to the deleting account's predecessor rather than being silently burnt).

### Proof of Concept
1. Create account `alice.near` with some balance and a full-access key.
2. Submit a `DeleteAccount { beneficiary_id: "nonexistent.near" }` action signed by `alice.near`, where `nonexistent.near` is a syntactically valid but never-created account id.
3. Observe: `action_delete_account` deletes `alice.near` and queues `Receipt::new_balance_refund("nonexistent.near", balance)`.
4. When that refund receipt executes, `check_account_existence` / `implicit_creation_allowed` reject implicit creation for a named account via a refund, producing `ActionErrorKind::AccountDoesNotExist`, exactly as asserted by the existing test `refund_may_not_create_universal_account` for the analogous "0u" case ( [6](#0-5) ).
5. Per `docs/RuntimeSpec/Refunds.md`, the failed refund's amount is burnt — `alice.near`'s balance is gone from total supply, unrecoverable, with no successful transfer to any account.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);

        // Assert on the reason, not just the absence: without this the test would

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
