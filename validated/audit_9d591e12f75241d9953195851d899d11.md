### Title
Unbounded growth of Cloudflare KV shop-session index enables session-storage DoS - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage.addShopIds` appends session ids to a per-shop index list stored in KV without checking for duplicates, unlike the equivalent Redis implementation. Because the offline OAuth session id is deterministic (`offline_<shop>`), every re-authentication/re-install cycle for the same shop re-appends the same id, growing the KV list unboundedly, mirroring the class of bug in the reported Moloch `_ragequit` issue: an attacker-influenceable unbounded list that is fully scanned/loaded on every subsequent auth/session operation, eventually causing failures or severe slowdowns of authentication flows for that shop.

### Finding Description
`storeSession` calls `addShopIds(session.shop, [session.id])` on every session store: [1](#0-0) 

`addShopIds` simply concatenates the new id(s) onto the existing array with no de-duplication check: [2](#0-1) 

Compare this to the Redis session storage implementation, which explicitly guards against duplicate insertion with `if (!idKeysArray.includes(idKey))` before pushing: [3](#0-2) 

The offline session id used by the OAuth flow is deterministic per shop — `offline_${shop}` — generated via `getOfflineId`: [4](#0-3) 

and consumed by `createSession` on every completed OAuth callback: [5](#0-4) 

Because the id is always the same for a given shop's offline session, every time the app is (re-)installed, re-authorized, or its OAuth flow is otherwise re-triggered for that shop, `storeSession`/`addShopIds` appends another duplicate copy of the same id string to the `shop:<shop>` KV entry — the list never shrinks on its own (only `deleteSession`/`removeShopIds` trims it, and only removes matching values, so duplicates before dedup still cost read/write bandwidth). This is directly analogous to the reported `_ragequit` issue: an unbounded, attacker-growable list that must be fully processed (here: JSON-parsed, iterated in `findSessionsByShop`, and rewritten on every store/delete) on every subsequent operation.

### Impact Explanation
Once the `shop:<shop>` KV value's session-id array grows large enough (either through repeated legitimate re-installs/OAuth refresh cycles or through a merchant/attacker deliberately re-triggering `/auth` for their own shop many times), every future `storeSession`, `deleteSession`, and `findSessionsByShop` call for that shop must read, JSON-parse, and rewrite an ever-larger array. This degrades and can eventually fail (KV value size limits, e.g. Cloudflare KV's 25 MiB value cap, or Worker CPU-time limits when parsing/iterating the array) all authentication-dependent operations for that shop — a denial of service of the auth/session-storage path, consistent in shape with the reported unbounded-loop-over-whitelist DoS.

### Likelihood Explanation
Triggering this requires only the ability to repeatedly complete OAuth for a shop (e.g., a merchant reinstalling/reauthorizing the app, or any flow that re-triggers offline-token OAuth), which is achievable by a single merchant/app-installer without any elevated privileges — no MITM, leaked secret, or privileged Shopify staff access is needed. The severity is moderate because it requires many repeated store operations to accumulate meaningful size, but it is a straightforward, reachable, cost-free-to-trigger loop that has no natural bound, unlike the Redis adapter in the same package which already fixed this exact issue with a de-duplication check.

### Recommendation
Add the same de-duplication guard used in the Redis adapter to `KVSessionStorage.addShopIds`, e.g. only append ids not already present in `shopIds`, and consider imposing an explicit maximum on the number of tracked session ids per shop (pruning or rejecting beyond a bound), mirroring the mitigation described in the reported bug (separate/limited counts to keep per-operation cost bounded).

### Proof of Concept
1. Configure a Shopify app to use `KVSessionStorage` for session persistence (as documented for Cloudflare Workers deployments).
2. As a merchant, repeatedly (re-)install/reauthorize the app on the same shop (or otherwise repeatedly complete the offline OAuth callback for that shop), each time driving `storeSession` → `addShopIds(shop, [offline_<shop>])`.
3. Observe (via KV inspection) that the `shop:<shop>` key's JSON array grows by one duplicate entry per OAuth completion with no bound, since `addShopIds` performs `[...shopIds, ...ids]` unconditionally.
4. As the array grows, subsequent `findSessionsByShop`, `storeSession`, and `deleteSession` calls for that shop incur linearly increasing KV read/parse/write cost, eventually risking KV value-size limits or Worker CPU-time exhaustion, denying authentication operations for that shop.

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
