## Title
Unchecked negative delta on delegated resource accounting can permanently corrupt account resource weights - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java)

### Summary
The Derby finding is a class of bug where deltas are applied to accounting state (protocol/chain allocations) without validating that the resulting value stays non-negative, causing silent, permanent corruption once an unsigned/positive-only invariant is violated. The closest reachable analog in java-tron is in the TVM-native `undelegateresource` accounting path, where `AccountCapsule` fields that back resource-weight and vote-power computations (`DelegatedFrozenV2BalanceForBandwidth`/`Energy`) are decremented with a raw, unguarded `add...` call instead of the "safe" clamp-to-zero helper used elsewhere in the same codebase for the symmetric acquired-side field.

### Finding Description
`UnDelegateResourceProcessor.execute()` decrements the *receiver's* acquired balance using a guarded/clamped path: [1](#0-0) 

But it decrements the **owner's** `DelegatedFrozenV2BalanceForBandwidth`/`Energy` with a plain, unguarded add of a negative amount, with no invariant check that the field cannot go negative: [2](#0-1) 

The setter/adder itself performs no clamping — it is a raw `+=`: [3](#0-2) 

Compare this to the sibling `UnfreezeBalanceProcessor`, which explicitly uses a `safeAdd...` variant that clamps the result to a floor of `0` via `max(0, ...)` for the equivalent acquired-side field: [4](#0-3) [5](#0-4) 

The `validate()` step in `UnDelegateResourceProcessor` only checks that the *per-relationship* `DelegatedResourceCapsule` frozen balance is sufficient to cover `unDelegateBalance`: [6](#0-5) 

It never checks that the owner account's aggregate `DelegatedFrozenV2BalanceForBandwidth`/`Energy` (a separately-tracked accounting total used elsewhere for `getTronPower`/vote-power/weight computations) is at least `unDelegateBalance` before subtracting. If any code path or historical migration edge case (e.g., FreezeV2/DelegateResource/UnDelegateResource/CancelAllUnfreezeV2 interacting across the legacy `Freeze`→`FreezeV2` and `Delegate`→`DelegateV2` migration boundary) ever causes this aggregate to be less than the per-relationship record, the raw subtraction drives the account-level field negative with no revert and no floor — directly mirroring the Derby pattern of "renew allocation via unchecked delta, no clamp, no revert on negative."

This is the same root-cause shape as the Solidity bug: an accounting field that is implicitly assumed non-negative is updated via an additive delta without a guard, and unlike the neighboring `Unfreeze` path (which was hardened with `safeAdd...`/`max(0, ...)`), this `UnDelegateResourceProcessor` path was left using the raw, unguarded adder.

### Impact Explanation
`DelegatedFrozenV2BalanceForBandwidth`/`Energy` feed into TRON-power and delegation/voting weight bookkeeping on the owner account. A negative value here is a corrupted, out-of-invariant chain state that:
- Persists permanently in the account record (no revert path exists to catch it, exactly like the Solidity case where `uint(amountToProtocol)` silently wraps rather than reverting).
- Can propagate to downstream computations (e.g., aggregated `getTotalDelegatedFrozenBalanceForBandwidth()/Energy()` at line 456/468/523-539 of `AccountCapsule.java`) that assume these are non-negative, producing incorrect resource/vote weight, i.e., an invalid-state/divergence condition in accounting.

### Likelihood Explanation
This is only reachable if the owner-level aggregate field and the per-relationship `DelegatedResourceCapsule` field ever diverge (e.g., due to the legacy Delegate/DelegateV2 dual-accounting bridge, partial-migration states, or another already-hardened bug being triggered elsewhere that desyncs the two). Because the guard that exists in `validate()` only checks the per-relationship value, not the aggregate, this is a latent/second-order risk rather than a directly, trivially triggerable one from a completely fresh, correctly-initialized account — it requires an accounting-desync precondition, which cannot be confirmed as currently reachable from this code alone.

### Recommendation
Mirror the `UnfreezeBalanceProcessor` pattern: replace the raw `ownerCapsule.addDelegatedFrozenV2BalanceForBandwidth(-unDelegateBalance)` / `addDelegatedFrozenV2BalanceForEnergy(-unDelegateBalance)` calls in `UnDelegateResourceProcessor.execute()` with a `safeAdd...` variant that clamps the result to `max(0, ...)`, and/or add an explicit `validate()`-time check that `ownerCapsule.getDelegatedFrozenV2BalanceForBandwidth()/Energy() >= unDelegateBalance` before allowing the operation, so any divergence throws a `ContractValidateException` instead of silently corrupting state.

### Proof of Concept
Not concretely demonstrable from static review alone: reaching the negative state requires first inducing a desync between the owner's aggregate `DelegatedFrozenV2BalanceForBandwidth`/`Energy` and the sum of its `DelegatedResourceCapsule` records (both of which are exercised together in tests such as `UnDelegateResourceActuatorTest.java`, which were not fully inspectable within this pass). This finding should be validated with a runtime/Devin-session investigation that exercises `FreezeBalanceV2` → `DelegateResource` → (partial/duplicate) `UnDelegateResource` sequences to confirm whether the two counters can actually be forced out of sync in the current codebase.
