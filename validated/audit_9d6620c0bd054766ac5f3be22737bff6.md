### Title
Vault `accrue` clock only advances when the computed index changes, letting rounded-down interest periods be silently dropped - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
`accrue()` in the vault contracts (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-ststxbtc.clar`) only writes `last-update` to `stacks-block-time` when the freshly computed `index`/`lindex` differ from the stored ones. When a call to `accrue()` occurs after a short elapsed period whose interest rounds down to zero (`next` == `idx` and `nliq` == `lidx`), `last-update` is left untouched even though the transaction is treated as a fully successful accrual (`(ok { index: next, lindex: nliq })`, no revert). This is the "clock advanced only on change" analog pattern.

### Finding Description
`accrue()` binds `next` and `nliq` from `next-index` / `next-liquidity-index`, both of which are computed as a function of elapsed time since `last-update`. The function then does: [1](#0-0) 

```
(if (not (is-eq idx next)) (var-set index next) false)
(if (not (is-eq lidx nliq)) (var-set lindex nliq) false)
...
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
(ok { index: next, lindex: nliq })
```

`last-update` (the clock the interest formula is anchored to) is advanced *only* when at least one of the two indexes actually changed value. If the elapsed time since the previous accrual is small enough that `mul-div-down`/interest-rate math rounds the computed `next`/`nliq` back down to the currently stored `idx`/`lindex` (e.g., very low elapsed seconds combined with modest rates and Clarity's integer truncation), the function still returns `ok` (no revert, no error) but silently leaves `last-update` frozen at the old timestamp. Every downstream caller (`system-borrow`, `system-repay`, `deposit`, `redeem`, `transfer`, and the market's `accrue-and-cache`) treats this `ok` return as proof that state is up to date and consistent, even though the recorded clock did not advance.

Because `stacks-block-time` continues to increase for every subsequent block while `last-update` stays pinned to the old value, the elapsed-time delta used in the *next* `next-index`/`next-liquidity-index` computation is not simply "missed interest deferred" — it is `stacks-block-time (new) - last-update (stale)`, i.e. the accumulated dust from possibly many rounding-suppressed accrual calls gets compounded into a single later jump. This differs from the intended incremental accrual model: interest that should have compounded across several discrete truncation boundaries is instead concentrated, and any economic computation performed *in between* (health checks, borrow capacity, liquidation thresholds) that reads `index`/`lindex` sees a value that has not moved even though real time (and, in principle, real value) has, until the clock catches up in one large step.

### Impact Explanation
This lands as a temporary freezing / value-distortion issue on unclaimed yield: because `index`/`lindex` (and therefore the market's price/notional resolution for zTokens via `accrue-and-cache`, which caches the vault's returned index under the current timestamp) do not advance during rounding-suppressed accrual calls, the vault's own accounting of supplied assets and debt can lag real elapsed time. Legitimate zToken holders' yield accrual can stall for periods, while callers that repeatedly trigger tiny accruals (or rely on the "no revert = state is current" assumption) can carry out borrow/health-check/collateral operations against a clock that has not actually moved, even though `ok` was returned. This falls under the in-scope "temporary freezing of funds" / "theft of unclaimed yield" category since interest normally due for that window is neither reverted-and-retried nor recorded, and the discrepancy compounds rather than resolves cleanly.

### Likelihood Explanation
This requires no privileged access — any caller invoking `deposit`, `redeem`, `system-borrow`, `transfer`, or `accrue()` directly (all public entry points call `accrue()` first) can trigger the rounding-suppressed path simply by calling shortly after a previous accrual when computed deltas round to zero. Given typical block cadence and vault interest-rate curves, this is a realistic occurrence rather than an edge case requiring adversarial setup, making it fairly straightforward to trigger, though the magnitude of value impact per occurrence is small and grows only when interest computations happen to consistently round to zero over a window.

### Recommendation
Decouple the "did the index change" check from the "did the clock advance" decision: always set `last-update` to `stacks-block-time` on any non-paused `accrue()` call (or at minimum whenever elapsed time > 0), regardless of whether the computed index rounds to the same value. This ensures the elapsed-time base for the interest formula is not corrupted by silently-skipped ticks, and prevents compounding truncation dust into unpredictable interest jumps.

### Proof of Concept
1. A vault (e.g. `v0-vault-usdc.clar`) has `index`/`lindex` at some value, `last-update = T0`.
2. Shortly after `T0` (e.g. `T0 + 1` block), a user calls `deposit`, which calls `accrue()`. `next-index()`/`next-liquidity-index()` compute a value that, after `mul-div-down` truncation, equals the existing `idx`/`lindex` (rounding-down produced zero net change for this short interval).
3. `accrue()` executes the `not-paused` branch, computes `next == idx` and `nliq == lidx`; both `var-set index`/`var-set lindex` guards are skipped (harmless, no-op), and critically the `last-update` guard `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))` is `false`, so `last-update` is **not** updated to `stacks-block-time`. The call still returns `(ok {index: next, lindex: nliq})` — success, no error surfaced to the depositor. [2](#0-1) 
4. This repeats over several subsequent blocks/deposits/redeems/borrows within the window where rounding continues to suppress index movement; `last-update` remains at `T0` while `stacks-block-time` has advanced substantially.
5. Eventually a call occurs where elapsed time (now `stacks-block-time - T0`, spanning all the skipped ticks) produces a non-zero `next`/`nliq` delta; `last-update` jumps directly to the new `stacks-block-time`. The intervening truncated ticks were never separately accounted for, and any position valuation, health check, or borrow capacity calculation that ran against the market via `accrue-and-cache` during the frozen window used a stale `index`/`lindex` as if it were current.

Note: the compounding/rounding magnitude depends on the specific `next-index`/`next-liquidity-index` rate-curve implementation, which was not fully readable within the indexed content (index size limits may have truncated some vault internals); a Devin session with full repository access could confirm the exact rounding behavior and quantify the value at risk per occurrence.
