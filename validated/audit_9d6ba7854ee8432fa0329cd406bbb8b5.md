## Title
Wallet Contract pays the relayer's fee unconditionally before the target/relayer is validated, allowing fee draining of the wallet balance - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`inner_rlp_execute` fires an unconditional `Transfer` promise paying the emulated Ethereum transaction's `fee` to the caller (`predecessor_account_id`) *before* it has confirmed that the transaction is actually valid. For the `EOABaseTokenTransfer { address_check: Some(address), .. }` case, validity is only confirmed later, asynchronously, via a cross-contract call to the address registrar in `address_check_callback`. Because the fee-payment promise is created independently of (and prior to) that check, and because the nonce is deliberately *not* incremented for this same case, an unprivileged caller can resubmit an invalid transaction indefinitely and receive the fee every time, draining the wallet's NEAR balance.

### Finding Description
`inner_rlp_execute` parses the RLP transaction and, based on `transaction_kind`, decides whether to bump the nonce and whether to pay a relayer fee: [1](#0-0) 

For `EOABaseTokenTransfer { address_check: Some(_), .. }` the nonce increment is explicitly skipped (comment: "we still do not know if the transaction has a relayer error"), but the very next `if` block pays the fee unconditionally as long as `fee` is non-zero and `predecessor_account_id != current_account_id` — it does **not** exclude the `address_check: Some(_)` case. The fee transfer (`env::promise_batch_action_transfer`) is issued as an independent promise from the contract's own balance to `predecessor_account_id` right away.

The actual validity check for this case only happens afterward, via a separate promise chain: [2](#0-1) 

`address_check_callback` later determines whether the target really is a faulty one (i.e., corresponds to an existing named account) and, in that case, only bans the relayer if the transaction was signed with the wallet's own access key: [3](#0-2) 

If the caller is an ordinary external account (not using the wallet's own access key, i.e., `env::signer_account_id() != current_account_id`), the response is simply an error — no ban, and (per the earlier logic) no nonce increment either. This means the exact same RLP transaction can be resubmitted by the same caller unlimited times, and each submission unconditionally pays out `fee` from the wallet's balance before the (always-failing) validity check resolves.

The `fee` amount is computed straight from attacker-controlled Ethereum transaction fields, bounded only by the prepaid gas the caller attaches and the value-encoding cap: [4](#0-3) [5](#0-4) 

This is the same bug class as the referenced NFTX finding: a function that combines the behavior of two other paths (pay-fee + validate-then-act) omits the check/administration step ("afterRedeemHook"/"allValidNFTs" equivalent — here, "only pay if the address check succeeds") that the individual paths perform, letting value move out before validation completes.

### Impact Explanation
Any unprivileged account can call `rlp_execute` on a victim's eth-implicit wallet contract with a crafted RLP transaction whose `to` address maps (via the address registrar) to an existing named account. Each call:
1. Fails the address-check validation (expected), but only *after* the fee has already been paid.
2. Does not increment the nonce (by design, for this specific case).
3. Does not ban the caller (since the caller is not using the wallet's own access key).

This lets the attacker repeatedly drain the wallet's NEAR balance in `fee`-sized increments with no cost beyond gas, a direct unauthorized value movement out of the wallet contract's account — high severity given the wallet holds user funds and this is the officially-supported meta-transaction execution path for eth-implicit accounts.

### Likelihood Explanation
High. This requires only a single, unprivileged, externally-submitted `FunctionCall` transaction (`rlp_execute`) to a deployed Wallet Contract, with an RLP payload the attacker fully controls (crafted `to`/target so `TargetKind::EthImplicit` resolves and `address_check` triggers, with any non-zero `max_fee_per_gas`/`gas_limit`). No special role, validator, or node compromise is needed, and the exploit can be repeated automatically since neither the nonce nor a ban blocks resubmission for non-owner-keyed callers.

### Recommendation
Do not fire the relayer-fee transfer for the `address_check: Some(_)` branch until the registrar lookup confirms the target is legitimate — i.e., move the fee-payment promise into (or make it contingent on) the `address_check_callback` success path, mirroring how `redeemTo`'s `afterRedeemHook` only runs after the redemption is confirmed valid. Alternatively, chain the fee-refund promise after the registrar-lookup promise so failure short-circuits payment.

### Proof of Concept
1. Attacker deploys/controls no special keys; they simply call `rlp_execute(target, tx_bytes_b64)` on the victim's wallet contract as an ordinary predecessor.
2. `tx_bytes_b64` encodes an RLP transaction whose `to` field is an eth-implicit address which is *not* `current_address`, causing `parse_target` to yield `TargetKind::EthImplicit(address)`, and whose calldata parses as a Near-native action target mismatch so `parse_tx_data` returns `EOABaseTokenTransfer { address_check: Some(address), fee }` with `fee > 0` (see `internal.rs` around lines 107–121).
3. In `inner_rlp_execute` (`lib.rs:358-385`), the nonce is *not* incremented, but the fee-refund promise IS created and sent to `predecessor_account_id` (the attacker) immediately.
4. The address-check promise resolves later in `address_check_callback` and determines the target actually maps to an existing named account (`maybe_account_id.is_some()`), so it returns an `Err`/error response, without banning the attacker (since they didn't sign with the wallet's key) and without having incremented the nonce.
5. Attacker repeats step 1 indefinitely, extracting `fee` yoctoNEAR from the wallet balance on every call.
