### Title
Front-running name squatting DoS on TRC10 asset creation via `AssetIssueActuator` - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
The external report describes front-running attacks against candidate/name-registration functions (`list`, `register`) that key a record by a deterministic identifier (a hash of the proposed value), letting an attacker observe a pending transaction and race it to claim the identifier first, denying the original submitter. The closest unprivileged, reachable analog in java-tron is TRC10 token issuance via `AssetIssueContract`, where the on-chain record is keyed by the token `name` (when `AllowSameTokenName == 0`) and any anonymous account can front-run a pending broadcast transaction with an identical `name` to squat it and cause the victim's transaction to fail.

### Finding Description
`AssetIssueActuator.validate()` rejects an asset-issuance transaction if an asset with the same `name` already exists in `assetIssueStore`, but only when the legacy `AllowSameTokenName` dynamic property equals `0`: [1](#0-0) . The uniqueness check is purely `name`-based and evaluated independently for every transaction at validation time, with no ordering or reservation guarantee tied to when the transaction was first broadcast. `execute()` then persists the asset keyed by this same name via `assetIssueCapsule.createDbKey()` [2](#0-1) .

Because Alice's transaction is visible in the mempool before being packed into a block, an attacker (Bob) can observe the pending `name` value and submit his own `AssetIssueContract` transaction with the identical `name`, offering a higher fee/priority so it lands in an earlier block or earlier position in the same block. When Alice's transaction is subsequently validated, `assetIssueStore.get(name) != null` is true and her transaction is rejected with `"Token exists"` [1](#0-0) , exactly mirroring the reported pattern where Bob front-runs Alice's `list`/`register` call to seize the candidate identifier first.

This is structurally the same bug class as the report: a globally unique, attacker-predictable identifier (name/hash) is claimed on a first-come/first-processed basis with no binding, commit-reveal, or reservation-by-sender mechanism, so transaction ordering (which any observer can influence via fee bidding or peer position) determines who legitimately "owns" the identifier.

### Impact Explanation
A victim who wants to issue a specific token name can be permanently blocked from ever using that name once an attacker preemptively claims it, since the check is a simple existence check with no expiry or dispute mechanism. This is a low-cost, unprivileged denial-of-service/name-squatting griefing vector reachable by any account able to broadcast a transaction. Because validation failure occurs before `adjustBalance`/fee-deduction logic in `execute()` runs, the victim does not lose the `AssetIssueFee`, but is fully denied use of the desired name and must retry with a different value, which is the same "candidate ownership stolen, no recovery unless attacker allows it" outcome described in the report.

### Likelihood Explanation
Likelihood is bounded by real-world relevance: the vulnerable path is only active when the network dynamic parameter `AllowSameTokenName == 0`; TRON governance (via `ProposalCreateActuator`/`ProposalService`) later moved networks toward `AllowSameTokenName == 1`, after which assets are keyed by an auto-incrementing numeric `tokenIdNum` rather than by name [3](#0-2) , which eliminates the name-collision race entirely. On networks/configurations where `AllowSameTokenName` is still `0` (e.g., private/consortium chains built from this codebase, or prior to the mainnet proposal activation), the front-running race remains fully exploitable by any unprivileged actor monitoring the mempool.

### Recommendation
- Do not use a purely name-based existence check tied to arrival order as the sole gatekeeper for a scarce namespace; either fully deprecate/hard-disable `AllowSameTokenName == 0` support, or bind name reservation to the submitter's account/signature with a commit-reveal scheme so a front-runner cannot claim a name they didn't originate.
- If `AllowSameTokenName == 0` support must remain for backward compatibility, consider requiring a stake/fee proportional to name length/desirability and/or a reservation window tied to the original proposer's address to blunt front-running economics, consistent with the report's short-term fee-based mitigation.
- Document clearly that operators running with `AllowSameTokenName == 0` are exposed to name-squatting via transaction-ordering manipulation, and encourage migration to the ID-based (`AllowSameTokenName == 1`) mode.

### Proof of Concept
1. Attacker monitors the P2P/mempool for a pending `AssetIssueContract` transaction from a victim specifying `name = "ALICE"`.
2. Attacker crafts and broadcasts their own valid `AssetIssueContract` transaction with the same `name = "ALICE"`, using a higher fee/energy bid or exploiting peer propagation timing to get it ordered first.
3. Once the attacker's transaction executes, `assetIssueStore` now contains an entry keyed by `"ALICE"` [2](#0-1) .
4. When the victim's original transaction is processed (same block or later), `AssetIssueActuator.validate()` throws `ContractValidateException("Token exists")` [1](#0-0) , permanently denying the victim the ability to issue a token under that name (assuming `AllowSameTokenName` stays `0`).

Note: I was unable to fully confirm the current mainnet default value of `AllowSameTokenName` from the indexed portion of `DynamicPropertiesStore.java` (grep matched but content was not returned within the available tool budget), so the real-world exploitability on the live TRON mainnet (vs. private/legacy-configured networks) could not be conclusively verified in this pass and should be checked directly in a full repository clone.
