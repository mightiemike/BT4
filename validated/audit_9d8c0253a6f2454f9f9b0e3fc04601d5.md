### Title
Double `PromiseResume` receipt emission via repeated `promise_yield_resume_with_yield_id` on the same `user_yield_id` — (`runtime/runtime/src/ext.rs`)

### Summary
`submit_promise_resume_data_with_yield_id` delegates to `submit_promise_resume_data`, whose guard uses `has_promise_yield_status` (a key-existence check). After the first resume call sets the status to `ResumeInitiated`, the key remains in `TrieUpdate`. A second call within the same function execution passes the guard again and emits a second `PromiseResume` receipt for the identical `data_id`.

### Finding Description
In `submit_promise_resume_data` (ext.rs lines 402–426), the guard is:

```rust
if has_yield_receipt_in_state || has_yield_status_in_state {
    self.receipt_manager.create_promise_resume_receipt(data_id, data);
    set_promise_yield_status(..., PromiseYieldStatus::ResumeInitiated);
    return Ok(true);
}
```

`has_promise_yield_status` is implemented as `trie.contains_key(TrieKey::PromiseYieldStatus{...})`. After the first call, `set_promise_yield_status` writes `ResumeInitiated` to the same key — it does **not** remove it. The `YieldIdToDataId` mapping is also never cleared by the resume path. Therefore a second call within the same execution context resolves the same `data_id` again and emits a second `PromiseResume` receipt. [6](#0-5) [7](#0-6) 

### Impact Explanation
Two `PromiseResume` receipts targeting the same `data_id` are routed to the runtime. The first resolves the waiting yield receipt normally. The second arrives for a `data_id` whose yield receipt has already been consumed, leading to either a stale/orphaned data receipt being stored in state (corrupting `ReceivedData` for that slot) or triggering an inconsistent-state error that aborts chunk processing. Either outcome constitutes **contract execution flow breakage** and a **non-network-level DoS** reachable from ordinary user-submitted transactions.

### Likelihood Explanation
Any unprivileged user who can deploy a contract (or call an existing one) can trigger this by calling `promise_yield_resume_with_yield_id` twice on the same `user_yield_id` in a single function call. No privileged access, validator role, or key compromise is required.

### Recommendation
In `submit_promise_resume_data`, replace the existence check with a value check:

```rust
// Instead of has_promise_yield_status (existence only), read the actual value:
let status = get_promise_yield_status(self.trie_update, &self.account_id, data_id)?;
if has_yield_receipt_in_state || matches!(status, Some(PromiseYieldStatus::Yielded)) {
    ...
}
```

Alternatively, remove the `PromiseYieldStatus` key (or the `YieldIdToDataId` mapping) immediately after the first resume so that subsequent calls find no entry and return `Ok(false)`.

### Proof of Concept
Write a contract that:
1. Calls `promise_yield_create_with_id(user_yield_id, ...)` to register a yield.
2. In a subsequent transaction, calls `promise_yield_resume_with_yield_id(user_yield_id, b"data1")` and then immediately `promise_yield_resume_with_yield_id(user_yield_id, b"data2")` in the same function body.
3. Assert that the `ReceiptManager` (or the outgoing receipts list) contains exactly one `PromiseResume` receipt — the test will fail, showing two receipts for the same `data_id`. [8](#0-7) [9](#0-8)
