Confirmed: any account (with sufficient balance) can call `ExchangeCreateContract` to become the "creator" of a TRC10 Bancor-style exchange pair, then later manage it via `ExchangeInjectContract`/`ExchangeWithdrawContract`. This is not a privileged/system role — it is an ordinary unprivileged user acting as a liquidity provider, directly analogous to a liquidity provider in the reported `ClearingHouse.sol`.

### Title
Exchange pool inject/withdraw operations lack a caller-supplied slippage bound, exposing liquidity providers to sandwich attacks - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
java-tron's built-in Bancor-style token exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`) mirrors the swap/liquidity-management pattern described in the external report. The `ExchangeTransactionActuator` (a taker "swap") correctly implements slippage protection via a user-supplied `expected` (minimum-amount-out) field. However, `ExchangeInjectActuator` and `ExchangeWithdrawActuator`, which change a liquidity provider's pool position, compute the paired token amount purely from the pool's current on-chain ratio and accept it unconditionally — there is no analogous caller-supplied minimum/maximum bound. This is the same root cause as the report: swap-adjacent value transfers are executed at whatever price exists at inclusion time, with no protection against price manipulation between submission and execution.

### Finding Description
In `ExchangeTransactionActuator.doValidate()`, a taker explicitly supplies `expected` (minimum tokens to receive), and the actuator reverts if `anotherTokenQuant < tokenExpected`: [1](#0-0) 

By contrast, `ExchangeWithdrawActuator.execute()` computes the paired token amount to return to the LP purely from the live pool ratio (`bigFirstTokenBalance`/`bigSecondTokenBalance`) with no caller-provided minimum bound on `anotherTokenQuant`: [2](#0-1) 

The `ExchangeWithdrawContract` protobuf itself carries only `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/minimum field exists at all: [3](#0-2) 

Similarly, `ExchangeInjectActuator.execute()` computes and unconditionally transfers `anotherTokenQuant` from the live ratio, again with no LP-specified bound: [4](#0-3) 

Both actions are restricted to the exchange's `creatorAddress`, but that "creator" is any ordinary account that previously called the public `ExchangeCreateActuator` — no special network privilege is required: [5](#0-4) [6](#0-5) 

Because `ExchangeTransactionContract` is public and callable by anyone, an attacker can sandwich a creator's withdraw/inject transaction: submit a large swap immediately before the withdraw/inject to skew `firstTokenBalance`/`secondTokenBalance`, let the withdraw/inject execute at the manipulated ratio, then submit a reversing swap immediately after — extracting value from the creator's LP position exactly as described in the report's `_liquidateLp`/AMM sandwich scenario.

### Impact Explanation
An LP (exchange creator) withdrawing or injecting liquidity has no way to bound the amount of the paired token they receive or must supply. A sandwich attacker can manipulate the pool ratio around the LP's transaction, causing the LP to receive materially less value on withdrawal (or overpay on injection) than the pool's fair state would imply. This is a concrete accounting/value-extraction impact on an unprivileged user's real assets on chain, not theoretical — the mechanism (public swap actuator moving the ratio, LP actuator blindly trusting that ratio) is directly reachable in production code.

### Likelihood Explanation
High reachability: `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` are all standard, unprivileged, publicly submittable transaction types. An attacker only needs to observe a pending withdraw/inject transaction in the mempool (or predict one) and front/back-run it with `ExchangeTransactionContract` swaps — the same MEV/sandwich pattern that is well established on TRON given its visible mempool. No special permissions or contract deployment is required.

### Recommendation
Add an optional caller-specified bound field to `ExchangeInjectContract`/`ExchangeWithdrawContract` (e.g., minimum `anotherTokenQuant` for withdraw, maximum `anotherTokenQuant` for inject), and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validation exactly as `ExchangeTransactionActuator` already enforces `expected` for swaps. Document that all exchange-pool operations affecting a pair's ratio are subject to front-running/sandwich risk.

### Proof of Concept
1. Alice creates an exchange pair via `ExchangeCreateContract` and later wants to withdraw liquidity via `ExchangeWithdrawContract` with `quant` of `firstToken`.
2. Alice broadcasts her withdraw transaction; it sits in the mempool with a computed but unenforced `anotherTokenQuant` based on the current ratio.
3. Eve, monitoring the mempool, submits an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for Alice, ordered to execute immediately before Alice's withdraw (block producers order transactions; on TRON same-block ordering by inclusion favors bots submitting with higher energy/priority or via witness collusion).
4. Alice's withdraw executes in `ExchangeWithdrawActuator.execute()` using the now-skewed ratio, producing a smaller `anotherTokenQuant` than expected, with no validation rejecting it: [7](#0-6) 
5. Eve submits a second `ExchangeTransactionContract` to reverse her initial swap, restoring the pool ratio and pocketing the difference extracted from Alice's withdrawal.
