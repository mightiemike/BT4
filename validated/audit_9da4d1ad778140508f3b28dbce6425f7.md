### Title
Bootstrap declare path allows any unprivileged sender to declare arbitrary fee-free classes indefinitely after genesis - ([File: crates/blockifier/src/transaction/account_transaction.rs])

### Summary
Starknet's sequencer implements a special "bootstrap" declare-transaction path intended to let a new chain register its initial classes (fee token, account classes, etc.) before genesis state exists. The path is keyed only on a fixed sentinel `sender_address == bootstrap_address()` ('BOOTSTRAP'), `nonce == 0`, `version == 3`, and `charge_fee == false` / `max_possible_fee == 0`. This is directly analogous to the RocketStorage bug: a "system bootstrap" mode that is *not durably disabled* once bootstrapping is complete, so anyone able to submit transactions can keep exercising the privileged, fee-free, validation-free path indefinitely.

### Finding Description
`DeclareTransaction::is_bootstrap_declare()` [1](#0-0)  defines the bootstrap condition purely from transaction-local fields (fixed sender address, nonce 0, `!charge_fee`) — it does not consult any global "already bootstrapped"/"initialized" state flag comparable to RocketStorage's `contract.storage.initialised`.

In execution, `AccountTransaction::execute_raw` special-cases this: if `tx.is_bootstrap_declare(...)` is true, it skips nonce increment, fee charge, and `__validate_declare__` entirely and just runs the declare, directly writing the class hash into state: [2](#0-1) 

The same bypass exists in the Starknet OS re-execution code, which skips validation and unconditionally writes the class hash into `contract_class_changes` when `sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, `max_possible_fee == 0`: [3](#0-2) 

The only "already declared" guard is `dict_update{...}(key=[class_hash_ptr], prev_value=0, new_value=compiled_class_hash)` — this only protects a given *class hash* from being redeclared, not the bootstrap address/path itself from being reused for a *different* class hash. Because the bootstrap declare never increments the nonce (explicitly documented behavior: "Bootstrap declare txs ... do not increment its nonce" [4](#0-3) ), the special sender's nonce remains permanently `0`, so the bootstrap condition remains permanently satisfiable by anyone, for any new (not-yet-declared) class hash, at any block height after genesis — not just during the initial system-bootstrap window.

Nothing in the gateway's stateless/stateful validators special-cases or blocks the bootstrap sender address once the chain has left genesis: `check_declare_permissions` only enforces `block_declare` and `is_authorized_declarer` allow-lists that must be explicitly configured [5](#0-4) , and `StatefulTransactionValidator` performs no bootstrap-address filtering. The `GenesisStateReader`/`SyncOrGenesisStateReader` is only used when no blocks exist yet [6](#0-5) , but that only affects gateway state lookups for pre-genesis bootstrap; the execution-layer bypass in `account_transaction.rs`/the OS is unconditional and reachable at any block height because it only checks tx-local fields, not "are we still in the bootstrap phase."

### Impact Explanation
Any unprivileged transaction sender can submit a V3 declare transaction with `sender_address = bootstrap_address()`, `nonce = 0`, and zero resource bounds/fee, at any point after genesis (not only during the intended bootstrap window), and have an arbitrary class hash declared into global state — bypassing `__validate_declare__`, nonce checks, and fee charging. This is a state-consistency and resource-accounting integrity issue: a class can be declared without paying fees or going through account validation, which is exactly the "unauthorized account action"/wrong state-write class of bug described in the RocketStorage report (privileged path usable by anyone because there's no durable "initialization complete" gate). Since `authorized_declarer_accounts` is optional (`gateway_config.static_config.authorized_declarer_accounts` defaults to none/empty per config schema) [7](#0-6) , no operator-side allow-list is required to be bypassed to exploit this — the check only restricts *normal* declares' sender if configured, and does not address the bootstrap sentinel special-case at all.

### Likelihood Explanation
High reachability: the condition is purely a function of transaction fields the submitter fully controls (fixed well-known sentinel address, nonce 0, zero fee bounds), requiring no privileged role, and is checked identically both in blockifier execution and in the Starknet OS re-execution path, so any node accepting this transaction and any prover re-executing it will apply the same unauthenticated declare. The only friction is that each class hash can be bootstrap-declared once (`prev_value=0` check), but an attacker can supply a fresh contract/class hash of their choosing on each attempt.

### Recommendation
Gate the bootstrap-declare bypass on a durable, monotonic "bootstrap complete" indicator (e.g., block number > 0, or an explicit one-time flag set at genesis) rather than solely on transaction-local fields (`sender_address`, `nonce == 0`, `charge_fee`). Concretely: in `AccountTransaction::execute_raw` and in the OS's `transaction_impls.cairo` bootstrap branch, additionally require that the current block number equals 0 (or that no prior block/state exists), matching the RocketPool fix pattern of disabling the privileged path once bootstrapping has completed rather than relying on transaction-supplied values that a general user can always reconstruct.

### Proof of Concept
1. Chain has produced blocks beyond genesis (block_number > 0), fee token and account classes are already declared normally.
2. Attacker crafts and submits an RPC V3 declare transaction with: `sender_address = 0x424f4f545354524150` ("BOOTSTRAP" as felt, per `bootstrap_address()`), `nonce = 0`, arbitrary/zero resource bounds so `charge_fee` is computed false, and a new/arbitrary `class_hash`/`compiled_class_hash` pair for a contract of the attacker's choosing.
3. Gateway/mempool accept it (no bootstrap-address-specific rejection exists in `check_declare_permissions` or the stateful validator).
4. During block building, `AccountTransaction::execute_raw` detects `tx.is_bootstrap_declare(charge_fee=false) == true` and, without running `__validate_declare__`, fee charge, or nonce increment, writes the attacker's class hash into state.
5. The same happens during OS re-execution (`sender_address == 'BOOTSTRAP' and tx_info.nonce == 0 and tx_info.version == 3` with `max_possible_fee == 0`), so provers accept the same unauthorized declare, making it part of the committed state.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }
}

        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.

        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
