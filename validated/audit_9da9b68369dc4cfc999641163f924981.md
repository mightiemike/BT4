### Title
Wallet Contract fails to refund `attached_deposit` on multiple error paths, permanently crediting caller's NEAR to the wallet account - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Near Wallet Contract (`rlp_execute` and its callbacks) accepts an `attached_deposit` from an external caller/relayer and wraps it in a `CallerDeposit` so it can be refunded if the underlying cross-contract call fails. However, several error branches inside the callbacks return `ExecuteResponse { success: false, .. }` directly without creating any refund promise, silently dropping the `caller_deposit` value. Because NEAR credits `attached_deposit` to the receiver's account balance at the protocol level *before* contract logic runs, this deposit is never given back — it stays permanently in the eth-implicit wallet account instead of being returned to the caller who attached it, exactly analogous to the reported `NestedFactory::_transferInputTokens` issue where `msg.value` is silently absorbed instead of refunded on a non-matching/failing path.

### Finding Description
`rlp_execute` is `#[payable]`, so any relayer/caller may attach a NEAR deposit to the call [1](#0-0) . `inner_rlp_execute` captures this deposit into `caller_deposit` via `CallerDeposit::new`, which is `Some` whenever the predecessor differs from the current (wallet) account [2](#0-1) [3](#0-2) .

The *only* place this `caller_deposit` is actually refunded is inside `rlp_execute_callback`, in the `PromiseResult::Failed` branch, which explicitly creates a transfer promise back to the caller [4](#0-3) .

However, `caller_deposit` is threaded through two other callbacks — `address_check_callback` and `nep_141_storage_balance_callback` — and in several of their error branches it is simply discarded without any refund:

- `address_check_callback`: on `PromiseResult::Failed` for the registrar lookup, and on `Some(account_id)` (invalid target) when the caller isn't the wallet's own signer, the function returns `ExecuteResponse{success:false,...}` directly, dropping `caller_deposit` [5](#0-4) .
- `nep_141_storage_balance_callback`: on `PromiseResult::Failed` for the `storage_balance_of` call, on a deserialization error, and when the parsed action isn't a `FunctionCall`, the function likewise returns `ExecuteResponse{success:false,...}` directly, dropping `caller_deposit` [6](#0-5) .

In every one of these cases, the deposit that was attached to the original NEAR transaction has already been credited to the wallet contract's account balance by protocol-level accounting (deposits on function calls are applied to the receiver's balance regardless of what the contract logic subsequently does), so unless the contract code explicitly issues a `Transfer` action back to the caller, the funds stay put. These branches never do so, unlike the sibling `PromiseResult::Failed` branch in `rlp_execute_callback`.

### Impact Explanation
Any relayer (or a user relaying their own transaction) that attaches a nonzero NEAR deposit to `rlp_execute` — inadvertently or because a wallet/relayer implementation always forwards `msg.value`-equivalent NEAR alongside the call — will have that deposit permanently absorbed into the wallet account's balance whenever execution takes one of the unrefunded error branches (registrar lookup failure, invalid target from a non-owner caller, NEP-141 `storage_balance_of` failure/malformed response, or malformed action). This is a "funds get stuck instead of refunded" bug matching the report's bug class: the deposit is not returned to its rightful sender even though the operation it was attached to failed. It is inconsistent with the contract's own stated invariant (tracking `CallerDeposit` specifically "to refund the caller's deposit if the cross-contract call fails" [7](#0-6) ), which the code fails to honor on several code paths.

### Likelihood Explanation
Reachable by any predecessor account calling `rlp_execute` on someone else's eth-implicit wallet with `deposit > 0` (an ordinary function call, no special privileges needed). The registrar-failure and NEP-141-failure paths can be triggered by conditions outside the caller's control (e.g., a down/misbehaving registrar or token contract, or a malformed relayer-provided action), so an honest but unlucky caller who attaches a deposit can lose it. Likelihood of accidental triggering is moderate (depends on relayer implementation always/never attaching deposit); severity of loss is direct and permanent once triggered.

### Recommendation
Ensure every early-return `ExecuteResponse{success:false,...}` branch in `address_check_callback` and `nep_141_storage_balance_callback` that currently drops `caller_deposit` instead issues the same refund promise used in `rlp_execute_callback`'s `PromiseResult::Failed` branch (i.e., `env::promise_batch_create` + `env::promise_batch_action_transfer` to `caller_deposit.account_id` for `caller_deposit.yocto_near`) before returning the failure response. Consider factoring this into a shared helper, e.g. `fn refund_and_fail(caller_deposit: Option<CallerDeposit>, error: &str) -> ExecuteResponse`, to avoid future omissions.

### Proof of Concept
1. Deploy the wallet contract as an eth-implicit account `A` per `test_wallet_contract_interaction` setup [8](#0-7) .
2. Have a different account `R` (relayer/other predecessor) call `A.rlp_execute(target, tx_bytes_b64)` attaching a nonzero deposit, with `target` chosen such that `parse_rlp_tx_to_action` returns `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), .. })`, i.e., the eth tx targets another eth-implicit account not yet registered by `R` — routing execution into `address_check_callback`.
3. Cause the address-registrar cross-contract call to fail (e.g., registrar account doesn't exist / panics), triggering `PromiseResult::Failed` in `address_check_callback` [9](#0-8) .
4. Observe: `ExecuteResponse{success:false,...}` is returned, `R`'s attached deposit is never refunded, and `A`'s account balance permanently reflects the deposit that `R` attached — confirmed by comparing `R`'s and `A`'s balances before/after via `view_balance`, analogous to the balance assertions used in `test_wallet_contract_interaction` [10](#0-9) .
