### Title
Native-contract `delegateResource` TVM opcode always creates an unlocked delegation, letting attackers evade the `lock`/`lockPeriod` restriction that the ordinary `DelegateResourceContract` transaction enforces - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java)

### Summary
The external report's bug class is: a state-changing operation that is *supposed* to carry a time-lock flag is reachable through a second, parallel code path that produces the same end state (crediting the recipient) but omits the lock, letting the actor obtain the unlocked equivalent of a locked action. In java-tron, `DelegatedResourceCapsule` state can be reached through two independent code paths — the `DelegateResourceContract` actuator (broadcast transaction) and the `delegateResource` TVM opcode/native processor (callable from any smart-contract execution) — and only one of them implements the `lock`/`lockPeriod` mechanism.

### Finding Description
`DelegateResourceActuator.execute` reads `lock` and `lockPeriod` from the `DelegateResourceContract`, computes an `expireTime`, and stores the delegated resource under the locked key (`createDbKeyV2(... , lock)`), enforcing that a locked delegation cannot be undelegated before `expireTime`: [1](#0-0) [2](#0-1) 

The same underlying resource-delegation state transition is also reachable from inside the TVM via the `delegateResource` opcode, which is wired into `Program.delegateResource` and dispatches to `DelegateResourceProcessor`: [3](#0-2) 

However, `DelegateResourceProcessor.execute`/`delegateResource` unconditionally writes to the **unlocked** key (`createDbKeyV2(ownerAddress, receiverAddress, false)`) with `expireTime = 0`, and there is no `lock`/`lockPeriod` field anywhere in `DelegateResourceParam` or in the processor's `validate`/`execute` logic: [4](#0-3) [5](#0-4) 

The lock feature in `DelegateResourceActuator` exists specifically to enforce a minimum commitment period for delegated bandwidth/energy (validated against `maxDelegateLockPeriod`/remaining lock time via `validRemainTime`): [6](#0-5) 

Because the TVM path is a completely separate code path into the same `DelegatedResourceStore` state and it has no equivalent of the lock check/enforcement, any actor who can execute a smart contract (i.e., anyone submitting a `TriggerSmartContract` transaction, permissionless) can perform delegate-resource operations that structurally cannot be locked, and — more importantly — this parallel path is not "aware of" existing locked delegations from the sibling actuator path (it always targets the unlocked key, bypassing `validRemainTime` checks entirely).

### Impact Explanation
This mirrors the report's root cause exactly: a mandatory/opt-in lock feature applied on one entry point into shared state is entirely absent on another entry point that produces the same economic effect (resource delegation to a receiver). While `lock` in `DelegateResourceContract` is itself optional (a user can choose `lock=false`), the concern is structural: any protocol logic, tooling, or committee-level policy that relies on the lock semantics being uniformly enforceable/inspectable across all delegation paths is broken, since the TVM path can never be locked and does not interact with `validRemainTime` guarding double-locking abuse. This is a Medium-impact resource/accounting-integrity issue rather than a direct fund-theft bug.

### Likelihood Explanation
Likelihood is High for reachability: the `delegateResource` opcode is available to any contract call once `VMConfig.allowTvmFreezeV2()`/DR feature flags are enabled, requiring no privileged access — any account can trigger a smart contract that invokes it. The divergence between the two code paths is deterministic and always occurs, not a race condition.

### Recommendation
Add `lock`/`lockPeriod` parameters to `DelegateResourceParam`, and update `DelegateResourceProcessor.execute`/`delegateResource` to compute and honor `expireTime` and to check against any pre-existing locked delegation, mirroring `DelegateResourceActuator.delegateResource` and its `validRemainTime` validation, so the TVM-triggered delegation path cannot be used to sidestep lock semantics available on the transaction-level actuator.

### Proof of Concept
1. Deploy or use any smart contract, and via `TriggerSmartContract` call an opcode path that invokes `Program.delegateResource(receiver, balance, resourceType)`.
2. Observe that `DelegateResourceProcessor.delegateResource` writes to `DelegatedResourceCapsule.createDbKeyV2(owner, receiver, false)` with `expireTime = 0` unconditionally — see [7](#0-6) .
3. Compare against `DelegateResourceContract` broadcast with `lock=true`, which is validated and persisted with a nonzero `expireTime` under the locked key — see [2](#0-1) .
4. This confirms the TVM path structurally cannot create/respect a locked delegation, diverging from the actuator path that implements and enforces `lock`.

  public void execute(DelegateResourceParam param, Repository repo) {
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(param.getOwnerAddress());
    long delegateBalance = param.getDelegateBalance();
    byte[] receiverAddress = param.getReceiverAddress();

    // delegate resource to receiver
    switch (param.getResourceType()) {
      case BANDWIDTH:
        delegateResource(ownerAddress, receiverAddress, true,
            delegateBalance, repo);

        ownerCapsule.addDelegatedFrozenV2BalanceForBandwidth(delegateBalance);
        ownerCapsule.addFrozenBalanceForBandwidthV2(-delegateBalance);
        break;
      case ENERGY:
        delegateResource(ownerAddress, receiverAddress, false,
            delegateBalance, repo);

        ownerCapsule.addDelegatedFrozenV2BalanceForEnergy(delegateBalance);
        ownerCapsule.addFrozenBalanceForEnergyV2(-delegateBalance);
        break;
      default:
        logger.debug("Resource Code Error.");
    }

    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
  }
