### Title
Unvalidated `RevertInstructions.FundRecipient` can permanently strand refund/revert outbounds — (File: `x/uexecutor/types/inbound.go`, `x/uexecutor/keeper/build_revert_outbound.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
The external report's root cause — a recovery/refund address that is accepted without checking it is usable on the destination chain, permanently locking funds when execution fails — has a structural analog in Push Chain's `uexecutor` revert/refund path. The `Inbound.RevertInstructions.FundRecipient` field, which becomes the recipient of the `INBOUND_REVERT` outbound (and the excess-gas refund) sent back to the *source* chain, is never format-validated against that chain's address namespace before being attached to a `PENDING` outbound and routed into the TSS/UV signing pipeline.

### Finding Description
`Inbound.ValidateForExecution` in [1](#0-0)  validates `p.Recipient` (an EVM-format Push Chain address) for `FUNDS`/`GAS`/payload types, but never validates `p.RevertInstructions.FundRecipient` at all.

`Inbound.Canonicalize`, called at vote-ingress, only lenient-canonicalizes `FundRecipient`: [2](#0-1) 
and the underlying `LenientCanonicalizeAddress`/`CanonicalizeAddressByNamespace` helpers explicitly fall back to the raw, trimmed, unparsed string whenever the value does not parse for the chain's namespace — by design, so votes are never dropped: [3](#0-2) 

That unvalidated string is then used verbatim as the outbound recipient in both revert-construction paths: [4](#0-3) 
and in the gas-refund/failed-outbound path: [5](#0-4) 

The resulting `OutboundTx` is set to `Status_PENDING` and indexed in `PendingOutbounds` for UV/TSS pickup — i.e., it is handed to the universal-validator broadcast pipeline expecting a well-formed destination-chain address (e.g., a Solana `PublicKey` per `buildRevertData` in `universalClient/chains/svm/tx_builder.go`, or a 20-byte hex EVM address for `eip155` destinations). If `FundRecipient` does not parse into a valid address for the destination namespace, the outbound has no defined fallback (unlike the inbound-side fallback to `Sender` when `FundRecipient` is merely *empty* — a malformed but non-empty value bypasses that fallback entirely, since the check is only `RevertInstructions.FundRecipient != ""`).

### Impact Explanation
Once created, the malformed `PENDING` `INBOUND_REVERT`/refund outbound cannot be corrected by the user — there is no user-facing mechanism to resubmit or amend `RevertInstructions` for an already-created UTX, and the code path that builds/broadcasts destination-chain transactions (`universalClient/chains/svm/tx_builder.go`, `universalClient/chains/evm/tx_builder.go`) requires a parseable address to construct the transaction. This mirrors the LiFi finding's exact failure mode: a "recovery" address accepted without verifying it is usable on the destination chain, resulting in funds being effectively locked pending manual/admin intervention (e.g. via `RevertStuckInbound`/rescue flows), rather than automatically recovered. Because `FundRecipient` is supplied by the same user whose funds are at stake (as part of their own inbound event/payload), this is a self-locking griefing/foot-gun vector rather than a direct fund-theft vector, consistent with the original report's **Low Risk** classification.

### Likelihood Explanation
Any unprivileged user submitting a cross-chain deposit can supply an arbitrary `revert_instructions.fund_recipient` string in their source-chain event/payload. No validator or Push Chain check rejects a malformed value before it is persisted into a `PENDING` outbound, so triggering the stuck state requires no privileged access — only a malformed field on an otherwise-ordinary user transaction.

### Recommendation
Validate `RevertInstructions.FundRecipient` format against the source chain's CAIP-2 namespace (using the existing strict `CanonicalizeAddressByNamespace`, not the lenient variant) inside `Inbound.ValidateForExecution`, and reject/fallback-to-`Sender` when it does not parse — mirroring the existing empty-string fallback but extended to "not a valid address for this chain," so a malformed `FundRecipient` cannot silently produce an unbroadcastable, permanently `PENDING` revert/refund outbound.

### Proof of Concept
1. Attacker (or careless integrator) submits a bridge deposit on a Solana (`solana:...`) source chain with `revert_instructions.fund_recipient` set to a syntactically-base58-valid but wrong-length/garbage string (passes `isBase58String` charset check in `canonicalizeSolanaValue`, so `Canonicalize()` does not reject or fall back to `Sender`).
2. UVs vote the inbound to quorum; execution subsequently fails (e.g. token config missing, swap failure), triggering `handleFailedInboundValidation` → `buildRevertOutbound`, which sets `Recipient = FundRecipient` unchanged: [6](#0-5) .
3. The `INBOUND_REVERT` `OutboundTx` is created with `Status_PENDING` and indexed in `PendingOutbounds` for TSS pickup, but the recipient cannot be parsed into a valid Solana `PublicKey` when the UV client attempts to build the actual `revert_universal_tx` instruction (`buildRevertData` expects `solana.PublicKey`, see [7](#0-6) ), leaving the outbound perpetually `PENDING` with no automated recovery.

Note: I was unable to fully trace the exact downstream error-handling behavior of the UV/TSS broadcaster when address parsing fails (e.g., whether it retries indefinitely, drops the outbound, or surfaces an operator alert) due to running out of investigation budget — this should be verified before treating the "permanent" lock as absolute, but the root cause (missing validation of `FundRecipient` at the on-chain acceptance point) is confirmed in the cited code.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}

// CanonicalizeAddressByNamespace canonicalizes an address for the given
// CAIP-2 chain. Empty input passes through (optional fields).
func CanonicalizeAddressByNamespace(chain, addr string) (string, error) {
	addr = strings.TrimSpace(addr)
	if addr == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMAddress(addr)
	case namespaceSolana:
		return canonicalizeSolanaValue(addr)
	default:
		return addr, nil
	}
}

// CanonicalizeTxHashByNamespace canonicalizes a transaction hash/signature
// for the given CAIP-2 chain. Empty input passes through (e.g. failed
// outbound observations carry no hash).
func CanonicalizeTxHashByNamespace(chain, txHash string) (string, error) {
	txHash = strings.TrimSpace(txHash)
	if txHash == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMHash(txHash)
	case namespaceSolana:
		return canonicalizeSolanaTxHash(txHash)
	default:
		return txHash, nil
	}
}

// Lenient variants for the vote-ingress / key-derivation path: canonical form
// when the value parses, trimmed input otherwise (never an error). Used there
// because that path must never drop a vote — a malformed inbound still has to
// produce an on-chain UTX record (with a failed PCTx / revert), and
// execution-level validation, not key derivation, is what rejects it. Honest
// observers of the same value still converge (same trimmed string), and the
// injective hashFields digest keeps even malformed values collision-safe.
// Strict (error-returning) variants are for admin/config paths where bad input
// should be rejected before it is persisted.

// LenientCanonicalizeAddress canonicalizes addr for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeAddress(chain, addr string) string {
	canon, err := CanonicalizeAddressByNamespace(chain, addr)
	if err != nil {
		return strings.TrimSpace(addr)
	}
	return canon
}

		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}
