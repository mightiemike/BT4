### Title
Wallet Contract callbacks use fixed, hard-coded static gas budgets that can run out mid-execution, permanently bricking the in-flight-transaction lock and freezing the wallet - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (`WalletContract`, used to emulate Ethereum EOAs on NEAR) hard-codes small, fixed static-gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_DEPOSIT_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, `REGISTRAR_LOOKUP_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, all 5 TGas or small sums thereof) for the promise callbacks that reset the `has_in_flight_tx` guard flag [1](#0-0) . This is directly analogous to `Swap.sol`'s hard-coded 2300-gas stipend assumption in `transfer()`: a fixed gas amount is assumed to always be "enough" for the follow-up call, and if that assumption is violated (e.g. by rising VM/host-function gas costs across protocol upgrades, exactly the "gas cost changes" scenario called out in the original report), the call aborts out-of-gas instead of completing.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` before returning a promise chain, and rejects any further calls to `rlp_execute` while this flag is `true` [2](#0-1) . The flag is only ever reset back to `false` inside the private callback functions `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, and `ban_relayer`, always as the very first statement of the callback [3](#0-2) [4](#0-3) [5](#0-4) .

Each of these callbacks is scheduled with a fixed static gas allotment via `.with_static_gas(...)` using the hard-coded constants above, e.g. `RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)` for the plain case [6](#0-5) , or `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (5+5+5 TGas) for the ERC-20 transfer path [7](#0-6) .

On NEAR, if a function call receipt runs out of its allotted gas at any point during execution, the entire receipt fails and **all state changes made during that call are rolled back**, including any writes made earlier in the same function body. Because `self.has_in_flight_tx = false` is a state write made inside the callback body itself, an out-of-gas failure partway through (or even at the very start of) one of these callbacks rolls back that reset along with everything else. Since `has_in_flight_tx` was already durably committed to `true` by the prior receipt (`rlp_execute`), and no other code path ever clears it, an out-of-gas failure in any of these fixed-gas callbacks leaves the contract permanently stuck with `has_in_flight_tx == true`. From that point on, `rlp_execute` unconditionally returns the "transaction already in progress" error for every future call [8](#0-7) , and there is no admin/backdoor method in this contract to clear the flag.

This mirrors the `Swap.sol` finding precisely in structure: a fixed gas stipend is baked into the code as "always sufficient," and any drift in the actual gas cost of the operations performed under that budget (protocol-level repricing of WASM execution, host-function costs, or serialization/formatting logic added in a future contract update) can silently turn a previously safe fixed budget into an insufficient one — with no re-entrancy-guard-style recovery, but instead a hard, permanent DoS lock.

### Impact Explanation
Any account controlled by an ETH-implicit `WalletContract` deployment becomes **permanently unable to execute any further NEAR action** (transfers, function calls, key management) once a single callback OOG-fails under a stale fixed-gas budget, because the `has_in_flight_tx` guard can never be cleared again. This satisfies the "permanently frozen funds" / "transaction-triggered halt" impact bar: any $NEAR or NEP-141 tokens held by that account are then unreachable through the wallet contract's `rlp_execute` interface, since every subsequent transaction from that address is immediately rejected before doing any work.

### Likelihood Explanation
The likelihood of exercising this by an ordinary end-user or attacker today is low for the current parameter set, since 5 TGas per callback (or 15 TGas for the ERC-20 chain) is comfortably above current NEAR host-function costs for the small amount of work each callback does (basic promise/result matching, small `format!`, one refund transfer action). However, the bug is a genuine unprivileged-transaction-reachable structural flaw: it takes only ordinary calls to `rlp_execute` (via `EOABaseTokenTransfer` with `address_check`, or `ERC20Transfer`) to route execution through these fixed-gas callbacks, and the safety of that path depends entirely on an assumption external to the contract (current protocol gas-cost parameters) that is explicitly acknowledged elsewhere in the codebase as subject to change (see `docs/architecture/how/gas.md` on gas-cost evolution across protocol versions, and NEP-536 gas-refund-penalty changes referenced in `docs/RuntimeSpec/Refunds.md`) [9](#0-8) . Any future protocol change that raises the cost of the involved host functions (or a small logic addition to these callbacks) can silently cross the fixed 5 TGas threshold and permanently brick every deployed instance of this exact contract version.

### Recommendation
- Avoid hard-coded fixed static-gas constants for the callback functions that clear `has_in_flight_tx`; instead use `promise_batch_action_function_call_weight`/`GasWeight` so the callback receives a generous share of whatever gas is actually attached to the top-level transaction, similar to the pattern already used for `ban_relayer` (`GasWeight(1)`) [10](#0-9) .
- Alternatively, add a generous safety margin to the fixed constants and add contract tests that fail CI if actual measured gas usage of each callback approaches the hard-coded budget, so future protocol-level cost changes are caught before deployment.
- Consider adding an explicit, permissioned (or time-locked, best-effort) recovery path to clear a stuck `has_in_flight_tx` flag, so a single OOG anomaly cannot permanently and irrecoverably freeze the account.

### Proof of Concept
1. Deploy `WalletContract` for an eth-implicit account and call `rlp_execute` with an RLP-encoded transaction that resolves to `EthEmulationKind::ERC20Transfer`, routing through `nep_141_storage_balance_callback` with the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget [11](#0-10) .
2. Assume (or simulate, e.g. in a protocol-version-bumped test environment with increased WASM/host-function gas costs) that the fixed budget becomes insufficient for the callback body to complete.
3. Observe the callback receipt fails with `GasExceeded`; state changes in that receipt roll back, so `has_in_flight_tx` remains `true` (it was already committed `true` by the prior `rlp_execute` receipt).
4. Call `rlp_execute` again on the same account; observe it always returns `ExecuteResponse { success: false, error: Some("Error: transaction already in progress...") }` [8](#0-7)  for every future call, with no way to clear the flag — the account and any funds routed through it are permanently locked out of the wallet contract's execution path.
