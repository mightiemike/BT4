This confirms a clear analog. Issue #12606 in nearcore is structurally identical to the Hats Protocol bug: a size limit (`max_receipt_size`) is enforced at the point a receipt is first validated (`validate_receipt` in `NewReceipt` mode, checking `receipt_size > limit_config.max_receipt_size`), but the receipt content is mutated **after** that check passes — `output_data_receivers` is appended post-validation in `runtime/runtime/src/lib.rs:1152-1190` (extending `new_action_receipt.output_data_receivers` after the receipt already passed size validation), and separately promise return values can inflate a `DataReceipt`. ### Title
Oversized receipts bypass `max_receipt_size` validation via post-check mutation, permanently degrading congestion/bandwidth admission - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/congestion_control.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
`validate_receipt` enforces `max_receipt_size` only when a receipt is first constructed and validated (`ValidateReceiptMode::NewReceipt`), but a function call's `output_data_receivers` are appended to an already-validated new receipt afterward in `apply_action_receipt`, and a promise's returned value can independently inflate a `DataReceipt` beyond the limit. This is the same bug class as the Hats Protocol `H-6` finding: a size/count cap is enforced at one code path (initial validation) but a different code path (post-validation mutation) can push the guarded quantity over the limit with no re-check, so the invariant the rest of the system relies on ("no receipt exceeds `max_receipt_size`") is silently broken.

### Finding Description
`validate_receipt` in [1](#0-0)  checks `receipt_size > limit_config.max_receipt_size` only for `ValidateReceiptMode::NewReceipt`. However, in `apply_action_receipt`, after a function call executes and produces a `ReturnData::ReceiptIndex`, the runtime mutates the *already created and already size-validated* new receipt by extending its `output_data_receivers` with the current receipt's own output data receivers: [2](#0-1)  This extension happens strictly after the receipt passed `validate_receipt`/`NewReceipt` validation (called earlier per new receipt in the same function, at [3](#0-2) ), so a receipt can be pushed above `max_receipt_size` with no subsequent re-validation.

The `ExistingReceipt` validation mode explicitly documents this as a known, unfixed hole: [4](#0-3)  referencing https://github.com/near/nearcore/issues/12606. Because such oversized receipts can now exist in state/queues, multiple downstream systems that assume `size <= max_receipt_size` have had to add defensive clamps rather than reject the receipt:
- `try_forward` in congestion control clamps the size used for admission math down to `max_receipt_size`, explicitly citing the bug: [5](#0-4) 
- Bandwidth request generation applies the same clamp for the same reason: [6](#0-5) 

This is functionally analogous to the Hats Protocol finding: `claimSigner()` enforces `maxSigners`, but `execTransaction()` (a different, generically-reachable path) can add owners without that check, so the invariant "owners <= maxSigners" that `reconcileSignerCount()` relies on is silently violated, later causing every transaction to revert. Here, `validate_receipt` enforces `size <= max_receipt_size` at creation, but the post-validation `output_data_receivers` append path bypasses it, so the invariant that congestion control, bandwidth scheduling, and outgoing-receipt admission rely on is silently violated — and instead of failing safely, those subsystems were patched to *tolerate* the violation via ad hoc clamps rather than the runtime rejecting the oversized receipt.

### Impact Explanation
An oversized receipt can end up persisted in a shard's outgoing buffer, incoming queue, or delayed queue. The system explicitly acknowledges (in the `try_forward` and bandwidth-request comments) that without the clamp workaround, such receipts "getting stuck" is the alternative outcome — i.e., a receipt that can never satisfy `forward_limit.size >= size` under the real (unclamped) size, and can never be forwarded to its destination shard, since bandwidth grants and outgoing size limits are all bounded relative to `max_receipt_size`-scale values (`outgoing_receipts_usual_size_limit`, `max_single_grant`, etc., per [7](#0-6) ). A stuck receipt in a shard's outgoing buffer or delayed queue permanently occupies space counted in `CongestionInfo` (`buffered_receipts_gas`, `receipt_bytes`), keeping that shard's reported congestion elevated and throttling admission of new transactions/receipts into or out of it — a transaction/contract-triggered degradation of chain throughput that the current clamp-based mitigation only partially addresses (it fixes forwarding admission math, not the root cause that the receipt is oversized). Because size validation is skipped for `ExistingReceipt` mode by design, an oversized receipt that reaches this state is never corrected and persists as a policy violation for its entire lifetime in the system.

### Likelihood Explanation
Reaching the vulnerable path only requires a single ordinary contract call: any account can deploy a contract that creates a promise chain ending in `promise_return` (or a large return value used as promise input), exactly as demonstrated by nearcore's own test suite — `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in [8](#0-7) , both of which are explicitly labeled as exercising issue #12606 and asserting (via `assert_oversized_receipt_occurred`) that an oversized receipt does end up incoming into a shard. No validator, network, or privileged access is needed — an unprivileged transaction sender/contract deployer can trigger it deterministically.

### Recommendation
Re-validate (or at least re-check the size of) any receipt after it is mutated post-creation — specifically after `output_data_receivers` is extended in `apply_action_receipt` ( [2](#0-1) ) — and reject the receipt (or the whole action) if the resulting size exceeds `max_receipt_size`, matching the check already done for freshly created receipts. Once the root cause is fixed and the size invariant restored, the compensating clamps in `try_forward` and `generate_bandwidth_request` (which currently paper over already-oversized receipts) can be removed, closing the gap referenced by issue #12606 rather than only mitigating its symptoms.

### Proof of Concept
The existing nearcore integration test already demonstrates the root cause end-to-end:
1. Deploy `near_test_contracts::rs_contract()`.
2. Call `max_receipt_size_promise_return_method1` with `args_size` sized so the base receipt for promise `C` (in the DAG `A -> C -> B`) is exactly `max_receipt_size` — it passes `validate_receipt`'s `NewReceipt` size check.
3. When promise `A` executes and does `promise_return`, `apply_action_receipt` extends `C`'s `output_data_receivers` after the fact ( [2](#0-1) ), pushing `C`'s serialized size above `max_receipt_size` with no re-validation.
4. `assert_oversized_receipt_occurred` confirms an incoming receipt above `max_receipt_size` reaches a shard ( [9](#0-8) ), and the congestion-control code paths that must clamp around it are the ones explicitly citing issue #12606 ( [5](#0-4) ).

fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain

                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)

                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))

        } else {

            })
        };

        if oversized {
            return;
        }

        block = prev_block;
