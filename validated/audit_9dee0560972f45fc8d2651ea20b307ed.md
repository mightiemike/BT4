### Title
Accounts-index disk-bucket restart files are trusted without content integrity verification, enabling stale/corrupt account index entries - (File: `bucket_map/src/restart.rs`, `bucket_map/src/bucket_storage.rs`)

### Summary
The reported Adena issue is a classic "trust input without verifying its origin/integrity" bug class: a `message` event listener accepts and acts on any payload without checking where it came from. The equivalent pattern in Agave's accounts-index disk bucket-map restart path is that `Restart::get_restart_file` and `BucketStorage::load_on_restart` re-open and blindly reuse on-disk index bucket files from a prior run, validating only coarse metadata (header version, bucket count, `max_search`, file length) but never validating that the actual index-entry contents (`IndexEntry<T>` records: pubkeys, slot lists, ref counts) are internally consistent or were written by a clean shutdown of this same process.

### Finding Description
`Restart::get_restart_file` checks only the file length and three header scalar fields before accepting a restart config file as valid: [1](#0-0) 

Likewise, `BucketStorage::load_on_restart` computes `num_elems` purely from file size divided by `elem_size` and mmaps the file directly, with no checksum or content validation of the index-entry payloads: [2](#0-1) 

`Bucket::new` then wires this reused, unverified mmap directly in as the live index storage for that bucket, falling back to a fresh file only if `load_on_restart` returns `None` (which only happens on size mismatch): [3](#0-2) 

There is no CRC/checksum field anywhere in the bucket-map restart format (`Header`, `OneIndexBucket`) to detect a torn write from an unclean shutdown (crash, `kill -9`, OOM, power loss) that leaves an `IndexEntry`'s `key`, `contents` (slot list / ref-count union), or occupied-bit metadata in a partially-written but structurally-plausible state: [4](#0-3) 

Because the only gate is "does the file length and 3 header scalars match the current config," a bucket file that was only partially flushed to disk before a crash will still pass `get_restart_file`/`load_on_restart` checks and be mmapped in as authoritative index data, exactly analogous to the report's listener accepting any `message` payload purely because it superficially matches an expected shape (`event.data?.status === 'request'`) without validating the sender.

### Impact Explanation
If a validator restarts after an unclean shutdown while a disk-based accounts index bucket write was in flight, `load_on_restart` will accept the partially-written bucket file as-is. This can silently resurrect stale `IndexEntry` slot-list/ref-count data for a pubkey (e.g., pointing at a slot that has since been cleaned/purged, or a torn write mixing old and new bytes for the same cell), causing the AccountsIndex to resolve a pubkey to the wrong slot/ref-count on the very next load. This is a concrete stale-account-load / index-corruption vector that can propagate into wrong balances being read by RPC/banking or into accounts-hash divergence between honest nodes that took the unclean-shutdown path versus nodes that rebuilt from a clean snapshot.

### Likelihood Explanation
Requires an unclean shutdown at the moment a bucket-map index file is being written to disk (a normal, not-uncommon operational event: crash, OOM-kill, host power loss) combined with disk index mode being enabled (`--accounts-index-path`), rather than a network-reachable attack. Likelihood is moderate rather than high because it depends on timing of the crash relative to a bucket write, but it requires no special privileges and no malicious peer, matching the report's "no authentication on the trust boundary" theme.

### Recommendation
Add a per-bucket-file or per-index-entry checksum (e.g., a CRC32/xxhash over the occupied-entry bytes, or a monotonically-increasing "clean shutdown" flag written last) that `get_restart_file`/`load_on_restart` must verify before reuse; on mismatch, fall back to discarding the file and rebuilding the bucket fresh (the existing safe path when `load_on_restart` returns `None`), rather than trusting size/header-scalar equality alone as proof of a clean, fully-flushed prior run.

### Proof of Concept
1. Start a validator with disk index enabled and a `restart_config_file` configured (`BucketMapConfig::restart_config_file`, consumed in `Restart::new`/`Restart::get_restart_file`): [5](#0-4) 
2. Force an unclean shutdown (`kill -9`) while accounts index writes are actively flushing to one or more bucket files on disk, such that a bucket file's on-disk `IndexEntry` bytes are only partially updated for the in-flight write.
3. Restart the validator with the same config. `Restart::get_restart_file` passes (file length and header scalars unchanged) and `Bucket::new`/`BucketStorage::load_on_restart` mmaps the torn file directly as the live index bucket, with no verification that the mid-write entries are self-consistent: [3](#0-2) 
4. Subsequent index lookups on the affected pubkey(s) return the stale/torn slot-list or ref-count value baked into the corrupted entry instead of failing closed or rebuilding, propagating a wrong account resolution into the running validator.

    pub(crate) fn new(config: &BucketMapConfig) -> Option<Restart> {
        let expected_len = Self::expected_len(config.max_buckets);

        let path = config.restart_config_file.as_ref();
        let path = path?;
        _ = remove_file(path);

        let mmap = Self::new_map(path, expected_len as u64).ok()?;

        let mut restart = Restart { mmap };
        let header = restart.get_header_mut();
        header.version = HEADER_VERSION;
        header.buckets = config.max_buckets as u64;
        header.max_search = config.max_search.unwrap_or(MAX_SEARCH_DEFAULT);

        (0..config.max_buckets).for_each(|index| {
            let bucket = restart.get_bucket_mut(index);
            bucket.file_name = 0;
            bucket.random = 0;
        });

        Some(restart)
    }

    pub(crate) fn get_restart_file(config: &BucketMapConfig) -> Option<Restart> {
        let path = config.restart_config_file.as_ref()?;
        let metadata = std::fs::metadata(path).ok()?;
        let file_len = metadata.len();

        let expected_len = Self::expected_len(config.max_buckets);
        if expected_len as u64 != file_len {
            // mismatched len, so ignore this file
            return None;
        }

        let file = OpenOptions::new()
            .read(true)
            .write(true)
            .create(false)
            .open(path)
            .ok()?;
        let mmap = unsafe { MmapMut::map_mut(&file).unwrap() };

        let restart = Restart { mmap };
        let header = restart.get_header();
        if header.version != HEADER_VERSION
            || header.buckets != config.max_buckets as u64
            || header.max_search != config.max_search.unwrap_or(MAX_SEARCH_DEFAULT)
        {
            // file doesn't match our current configuration, so we have to restart with fresh buckets
            return None;
        }

        Some(restart)
    }

    /// load and mmap the file that is this disk bucket if possible
    pub(crate) fn load_on_restart(
        path: PathBuf,
        elem_size: NonZeroU64,
        max_search: MaxSearch,
        stats: Arc<BucketStats>,
        count: Arc<AtomicU64>,
    ) -> Option<Self> {
        let offset = Self::get_offset_to_first_data();
        let num_elems = std::fs::metadata(&path)
            .ok()
            .map(|metadata| metadata.len().saturating_sub(offset) / elem_size)?;
        if num_elems == 0 {
            return None;
        }
        let mmap = Self::map_open_file(&path, false, 0, &stats)?;
        Some(Self {
            path,
            mmap,
            cell_size: elem_size.into(),
            count,
            stats,
            max_search,
            contents: O::new(Capacity::Actual(num_elems)),
            // since we loaded it, it persisted from last time, so we obviously want to keep it present disk.
            delete_file_on_drop: false,
        })
    }
