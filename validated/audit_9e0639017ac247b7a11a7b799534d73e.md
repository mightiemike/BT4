Found the key control at deserialization time: `TransactionPayload::consensus_deserialize` in `stacks-codec/src/transaction.rs` explicitly rejects `PoisonMicroblock` payloads whose two headers are equal (`h1 == h2`), requiring them to differ in some field, before the transaction can even be constructed.### Title
Poison-microblock slashing accepts ECDSA-malleated signature pairs over identical content as proof of equivocation - (File: `stackslib/src/chainstate/stacks/db/transactions.rs`)

### Summary
`handle_poison_microblock` and its helper `check_microblock_header_signer` only verify that two `StacksMicroblockHeader`s recover to the same public-key hash; they never check that the headers commit to *different* microblock content (`tx_merkle_root`). Because signature recovery uses `recover_to_pubkey_without_validating_low_s`, which explicitly skips low-S/malleability validation, an attacker can take a single honestly-signed microblock header and derive a second, distinct-byte signature (via ECDSA `s -> n-s` malleation) over the exact same `prev_block`/`tx_merkle_root`/`sequence`, producing a "PoisonMicroblock" pair that passes all consensus checks despite no real equivocation.

### Finding Description
The claimed equality is: *poison reward paid == exactly one valid double-signature where the two headers commit to different microblock content at the same sequence*. The code never enforces the "different content" half of that equality.

- `StacksMicroblockHeader::check_recover_pubkey` (`stacks-codec/src/transaction.rs:2598-2616`) recovers the signer via `StacksPublicKey::recover_to_pubkey_without_validating_low_s`, which by design (`stacks-common/src/util/secp256k1/native.rs:200-228`, and `wasm.rs:118-134`) skips the low-S canonical-signature check. This means both the canonical (`low-s`) signature and its malleated (`high-s`) counterpart over the identical digest recover to the same public key and the same `pkh`.
- The only "must differ" gate is at deserialization time in `TransactionPayload::consensus_deserialize` (`stacks-codec/src/transaction.rs:2905-2924`): it rejects only byte-for-byte identical headers (`h1 == h2`, which includes the `signature` field), and requires `sequence`/`prev_block` to match. It performs **no check that `tx_merkle_root` differs**. A malleated signature makes `h1 != h2` trivially (different signature bytes) while `version`, `sequence`, `prev_block`, and `tx_merkle_root` remain identical.
- `StacksChainState::check_microblock_header_signer` (`stackslib/src/chainstate/stacks/db/transactions.rs:686-713`) only compares `pkh1 == pkh2`; it never compares `mblock_hdr_1.tx_merkle_root` vs `mblock_hdr_2.tx_merkle_root` or the block hashes.
- `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs:722-856`) proceeds straight to recording a poison report and commissioning the reporter based solely on that `pkh` match and sequence bookkeeping — it never re-derives or compares block content between the two headers.

Exploit flow: an attacker observes one honestly-broadcast, honestly-signed microblock header `h` from a miner with recorded `pubkh`. The attacker computes the malleated signature `h'` (same `version`/`sequence`/`prev_block`/`tx_merkle_root`, flipped `s`/adjusted recovery id). They submit `TransactionPayload::PoisonMicroblock(h, h')` as a user transaction. `consensus_deserialize` accepts it (headers differ in signature bytes, same sequence/prev_block). `check_microblock_header_signer` recovers `pkh1 == pkh2` (true, low-S check skipped). `handle_poison_microblock` records the report and the honest miner is slashed for a "double-signed" microblock they never issued — the attacker (as `reporter_principal`) collects the commission though the miner never equivocated on distinct content.

### Impact Explanation
This is a wrongful slash / reward-mispayment: an honest miner's `pubkh` gets its microblock-signing key treated as equivocating and the reporter/attacker collects the associated commission of the punished miner's reward, while no fork or distinct content ever existed. Per the severity rubric this is a poison/reward mis-payment (bounded to the poisoned miner's commission/coinbase share) triggerable by any unprivileged party who observes one broadcast microblock header from a target miner — no majority stake, no signer collusion, and no compromise of the miner's key are required (attacker never needs the private key; only the malleated public signature).

### Likelihood Explanation
Preconditions are minimal and attacker-controllable: the target miner's `pubkh` must be on record (`get_microblock_pubkey_hash_height`), which happens for every anchored block with microblocks, and the attacker needs to observe just one valid signed microblock header from that miner (already broadcast/public). ECDSA signature malleation (computing `n - s` and the complementary recovery id) is a purely local, free computation requiring no chain resources, BTC spend, or elevated privileges. This is directly repeatable against any miner who has produced at least one microblock, for as long as the height is within `MINER_REWARD_MATURITY`.

### Recommendation
Enforce actual content divergence, not just signer identity, when validating a poison-microblock pair:
- In `check_microblock_header_signer` (or `handle_poison_microblock`), additionally require `mblock_hdr_1.block_hash() != mblock_hdr_2.block_hash()` derived from content fields excluding the signature (e.g., compare `tx_merkle_root`), rejecting the transaction if the two headers commit to identical microblock content.
- Alternatively/also, stop using `recover_to_pubkey_without_validating_low_s` for poison-microblock verification and require canonical low-S signatures so that a single valid signature cannot be malleated into a second "distinct" signature at all.
- Update the `consensus_deserialize` guard in `stacks-codec/src/transaction.rs` to check for `tx_merkle_root` divergence explicitly instead of relying on whole-struct inequality (which is trivially satisfied by signature malleation).

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/stacks/db/transactions.rs` test module, alongside `process_poison_microblock_valid_transaction`):
1. Generate `block_privk`, register its `pubkh` via `insert_microblock_pubkey_hash`.
2. Construct one legitimate `StacksMicroblockHeader h` with fixed `version`, `sequence`, `prev_block`, `tx_merkle_root`, signed by `block_privk` (canonical low-S signature).
3. Derive `h'` = clone of `h` with the same `version`/`sequence`/`prev_block`/`tx_merkle_root`, but with `signature` replaced by the ECDSA-malleated form of `h.signature` (flip `s -> n - s`, adjust recovery id byte), so `h.tx_merkle_root == h'.tx_merkle_root` and `h != h'` only due to signature bytes.
4. Assert first equality side: `h.tx_merkle_root == h'.tx_merkle_root && h.block_hash() != h'.block_hash()` is false-equivalence proof that no real fork/content divergence exists (they are the same microblock content).
5. Build `TransactionPayload::PoisonMicroblock(h.clone(), h'.clone())`, sign with an unrelated reporter key, and call `StacksChainState::process_transaction`.
6. Assert on the second equality side: currently the call succeeds and `get_poison_microblock_report` returns `Some((reporter_addr, h.sequence))` — i.e., a poison reward is paid despite `h` and `h'` committing to identical content. The test should assert this **must fail** (`process_transaction` should return an error such as `PoisonMicroblocksDoNotConflict`/`InvalidStacksTransaction`); as written today it succeeds, demonstrating the theft path.
