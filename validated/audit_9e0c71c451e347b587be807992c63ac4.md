### Title
Dynamic-energy penalty integer division rounds down to zero for cheap opcodes, letting contracts bypass the anti-abuse energy surcharge - (File: actuator/src/main/java/org/tron/core/vm/VM.java)

### Summary
The Morpho `SpeedJumpIrm.sol` bug shows a class of issue where a rate/fee is computed as `(scaled_value - base_value)`, and when the scaling factor is only slightly above 1 and the base value is small, `wMulDown`-style integer rounding causes the scaled value to equal the base value, silently collapsing the intended fee/rate to zero even though it should be non-zero. Java-tron's TVM "dynamic energy" anti-abuse pricing mechanism reproduces the same rounding-collapse pattern in its per-opcode penalty computation.

### Finding Description
When `allowDynamicEnergy` is enabled, each opcode's base energy cost is scaled by a per-contract `factor` (which grows above `DYNAMIC_ENERGY_FACTOR_DECIMAL` = 10,000 as a contract repeatedly exceeds `dynamicEnergyThreshold`, via `ContractStateCapsule.catchUpToCycle`, [1](#0-0) ). The penalty added on top of the base energy cost is computed with plain integer division:

```java
penalty = energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energy;
if (penalty < 0) { penalty = 0; }
energy += penalty;
``` [2](#0-1) 

The identical pattern is duplicated for CALL-family opcodes in `getCalculateCallCost`:
```java
long penalty = energyCost * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energyCost;
if (penalty < 0) { penalty = 0; }
``` [3](#0-2) 

Because `energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL` truncates (rounds down) rather than rounding up or preserving remainder, whenever `factor` is only moderately above `DYNAMIC_ENERGY_FACTOR_DECIMAL` relative to the opcode's base cost, `energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL` truncates back down to exactly `energy`, making `penalty == 0` even though `factor > DYNAMIC_ENERGY_FACTOR_DECIMAL` (the very condition that is supposed to trigger a non-zero surcharge, guarded at [4](#0-3) ). Cheap opcodes are especially exposed: `ZERO_TIER = 0`, `BASE_TIER = 2`, `VERY_LOW_TIER = 3` [5](#0-4) . For `energy = 3`, any `factor` below `⌈10000·4/3⌉ = 13334` yields `3*factor/10000 == 3`, i.e. `penalty = 0`, no matter how large the accumulated per-contract factor grows above the base 10,000 (up to `dynamicEnergyMaxFactor`, capped at 100,000 [6](#0-5) ). For `ZERO_TIER = 0` the penalty is always 0 regardless of factor.

This is directly analogous to the reported bug: `borrowRateAfterJump.wMulDown(variationMultiplier)` rounding back down to `borrowRateAfterJump` when the multiplier is only slightly above 1, causing the derived quantity (`avgBorrowRate`) to collapse to 0/base instead of reflecting the intended proportional increase.

### Impact Explanation
The dynamic-energy mechanism exists specifically to make contracts that repeatedly consume energy above `dynamicEnergyThreshold` pay a growing surcharge (`dynamicEnergyIncreaseFactor`/`dynamicEnergyMaxFactor`) proportional to the burden they place on the network — this is a public resource-pricing/anti-abuse control, similar in spirit to gas-price escalation mechanisms. Because the surcharge computation truncates instead of rounding correctly, an attacker can structure a contract to execute large sequences of cheap opcodes (arithmetic ops, PUSH, DUP, etc., costs 0–5) to accumulate energy usage/CPU burden while paying zero dynamic-energy penalty per opcode, regardless of how high the contract's per-cycle usage factor has climbed. This is a concrete underpriced-public-work condition: the actual resource consumption (CPU time, energy accounting across many opcodes) is not billed according to the intended escalating-fee model, undermining the anti-spam/anti-abuse purpose of the feature and allowing sustained underpayment relative to the network burden imposed.

### Likelihood Explanation
`allowDynamicEnergy` and its parameters are chain-governance-controlled (via committee/proposal, e.g. `DYNAMIC_ENERGY_THRESHOLD`, `DYNAMIC_ENERGY_INCREASE_FACTOR`, `DYNAMIC_ENERGY_MAX_FACTOR` [7](#0-6) ) and once enabled apply automatically to any unprivileged contract call — no special privilege is required to trigger or exploit it. The rounding gap is deterministic and occurs for any opcode whose base cost is small relative to the factor's excess over `DYNAMIC_ENERGY_FACTOR_DECIMAL`, which includes the cheapest and most frequently used TVM opcodes, making exploitation trivial for any contract author on a chain where dynamic energy is active.

### Recommendation
Compute the penalty using a rounding-up (ceiling) division, or compute it directly as `energy * (factor - DYNAMIC_ENERGY_FACTOR_DECIMAL)` divided with ceiling semantics, instead of `energy*factor/DECIMAL - energy`, mirroring the recommended Morpho fix of using a closed-form/rounding-safe formula rather than a subtraction-of-two-rounded-down-quantities approach. Apply the same fix consistently in both `VM.java` and `EnergyCost.getCalculateCallCost`.

### Proof of Concept
1. Enable dynamic energy on a test chain (`allowDynamicEnergy=1`, `dynamicEnergyThreshold` small, `dynamicEnergyIncreaseFactor` set so the contract's factor grows to, e.g., 12000 after repeated calls).
2. Deploy a contract whose hot loop consists only of cheap opcodes (e.g., `ADD`/`PUSH`/`DUP`, base cost 3 or 2).
3. Repeatedly invoke the contract to push its per-cycle `energyFactor` above `DYNAMIC_ENERGY_FACTOR_DECIMAL` (via `ContractStateCapsule.catchUpToCycle`).
4. Observe in `VM.play` that for each such opcode, `energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL - energy` evaluates to 0 as long as `factor < ceil(DECIMAL * (energy+1)/energy)`, confirming `penalty == 0` is charged and `spendEnergy` (not `spendEnergyWithPenalty`'s surcharge) effectively applies base cost only, despite the contract exceeding the abuse threshold.
