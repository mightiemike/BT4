### Title
Validator rewards computed by `RewardCalculator::calculate_reward` are silently discarded when epoch-info construction falls back to a cloned epoch info - (File: chain/epoch-manager/src/lib.rs)

### Summary
This is the closest reachable analog to the reported bug class: two different code paths process the same "epoch computation" step, but only one of them actually persists the reward/mint side effect, while the other silently discards it. In the RewardThrottle report, `_fillInEpochGaps` (called from `fillInEpochGaps`) advances the epoch bookkeeping without distributing the already-owed reward, whereas `checkRewardUnderflow` advances the same bookkeeping and additionally requests/distributes the reward — so whichever function runs first determines whether the epoch's reward is ever paid. In `finalize_epoch`, `RewardCalculator::calculate_reward` is unconditionally executed and produces a `validator_reward`/`minted_amount` for the just-finalized epoch, but if the subsequent validator-selection step (`proposals_to_epoch_info`) fails, the code discards that computed reward/mint data and substitutes a cloned copy of the previous `EpochInfo` with only `epoch_height` bumped.

### Finding Description
`finalize_epoch` first computes rewards deterministically via `RewardCalculator::calculate_reward` [1](#0-0) , producing `(validator_reward, minted_amount)` that is meant to be stored as part of the new `EpochInfo` for epoch T+2 [2](#0-1) .

Immediately after, the code calls `proposals_to_epoch_info` with that `validator_reward`/`minted_amount`. If this call fails with `EpochError::ThresholdError` (not enough stake for required seats) or `EpochError::NotEnoughValidators` (not enough validators for required shards) — both of which are reachable purely through submitted `Stake` transactions (e.g., many/most validators unstaking to zero in the same epoch) — the code takes an entirely different path: it clones the *previous* `EpochInfo` and only increments `epoch_height`, never incorporating the just-computed `validator_reward` or `minted_amount`: [3](#0-2) 

This mirrors the RewardThrottle pattern precisely: the reward/mint computation ("profit accounting" in the analog) happens on one path, but the "commit" step that would normally persist it (`proposals_to_epoch_info` building the new `EpochInfo` with `validator_reward`/`minted_amount` fields, as documented in the protocol spec at [4](#0-3) ) is skipped on the fallback branch, silently dropping the reward for that epoch instead of applying it via any equivalent to `checkRewardUnderflow`'s explicit distribution. There is no compensating mechanism (no analog of `checkRewardUnderflow`'s `overflowPool.requestCapital` call) to later credit the lost `minted_amount`/`validator_reward` once selection recovers.

### Impact Explanation
Because `minted_amount` is what drives the per-block total-supply increase (`new_total_supply = prev.total_supply + minted_amount - balance_burnt`, only applied on the first block of an epoch) [5](#0-4) , and `validator_reward` is what feeds validator balance updates at the epoch boundary, taking the fallback branch means validators who earned rewards for epoch T (based on real block/chunk production) receive nothing for that epoch, and the corresponding inflation is silently never minted — a permanent, un-recoverable loss of otherwise-owed validator rewards with no error surfaced to operators beyond a `tracing::warn!` log line. This is a value-loss bug (lost validator rewards / missed issuance) directly caused by a fallback code path that bypasses the normal reward-commit path, structurally identical to the reported RewardThrottle issue where `fillInEpochGaps` bypasses the reward-distribution path taken by `checkRewardUnderflow`.

### Likelihood Explanation
Triggering this requires driving epoch T+2's proposal set into `ThresholdError`/`NotEnoughValidators`, which can occur from `Stake` actions (a normal transaction type any signer can submit) causing widespread unstaking within an epoch — an edge case explicitly anticipated by the code's own comment ("all validators tried to unstake?"). It is not attacker-exclusive but does require coordinating a mass-unstake event, or occurring naturally on a low-validator-count / test/canary network, making likelihood plausible but not trivial to engineer on a large, healthy validator set.

### Recommendation
When `proposals_to_epoch_info` fails and the code falls back to cloning the previous `EpochInfo`, still persist the computed `validator_reward` and `minted_amount` on the fallback `EpochInfo` (or otherwise ensure they are applied/carried forward) rather than silently discarding them, so that a validator-selection failure never causes computed rewards/issuance to vanish.

### Proof of Concept
1. Configure/observe a network state where, within a single epoch, `Stake` transactions drive total remaining stake/validator count below the `proposals_to_epoch_info` seat/threshold requirements for epoch T+2.
2. Let `finalize_epoch` run for epoch T: `RewardCalculator::calculate_reward` computes non-zero `validator_reward`/`minted_amount` for epoch T's active validators [1](#0-0) .
3. `proposals_to_epoch_info` then returns `Err(EpochError::ThresholdError)` / `Err(EpochError::NotEnoughValidators)`.
4. The fallback branch builds the new `EpochInfo` from the *previous* epoch's info plus `epoch_height + 1`, never referencing `validator_reward`/`minted_amount` [3](#0-2) .
5. When this `EpochInfo` becomes active (T+2), no reward is credited to the validators who earned it in epoch T, and no corresponding inflation is minted — the reward is permanently lost.

### 7. Reward computation and protocol treasury

`RewardCalculator::calculate_reward` (`reward_calculator.rs:51`):
1. `epoch_total_reward = max_inflation_rate * total_supply * epoch_duration / (num_seconds_per_year * NUM_NS_IN_SECOND)` (`reward_calculator.rs:69`).
2. `epoch_protocol_treasury = epoch_total_reward * protocol_reward_rate` credited to `protocol_treasury_account` (`reward_calculator.rs:78`, `reward_calculator.rs:84`). If `genesis_protocol_version == PROD_GENESIS_PROTOCOL_VERSION` (29) the rate is hardcoded to `1/10` (`reward_calculator.rs:63`).
3. The remaining `epoch_validator_reward` is split pro-rata by stake, scaled by an online multiplier `min(1, (uptime - online_min)/(online_max - online_min))` (`reward_calculator.rs:119`–`140`); a validator below `online_min_threshold`, or with zero expected blocks/chunks/endorsements, gets 0 (`reward_calculator.rs:109`). The `production_ratio` blends block, chunk and endorsement ratios via `get_validator_online_ratio` (validator_stats), applying the endorsement cutoff.
4. Returns `(rewards_map, actual_minted)`, where `actual_minted` sums treasury + all validator rewards (`reward_calculator.rs:143`) — this is `minted_amount` stored on the next `EpochInfo`.
