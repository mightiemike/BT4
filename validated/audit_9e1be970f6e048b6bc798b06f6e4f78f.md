### Title
Missing `VRF::verify` cryptographic binding check in `validate_vrf_seed` allows forged VRF seeds in Nakamoto blocks - (File: stackslib/src/chainstate/nakamoto/mod.rs)

### Summary
The epoch2x block validator (`StacksBlockHeader` analogue in `block.rs`) enforces two independent checks on a block's VRF material: (1) the block-commit's `new_seed` must equal `hash(proof)`, and (2) `proof` must cryptographically verify under `VRF::verify(leader_key.public_key, proof, sortition_hash)`. The Nakamoto equivalent, `NakamotoBlock::validate_vrf_seed` (`stackslib/src/chainstate/nakamoto/mod.rs:1680-1712`), only performs check (1) via `block_commit.new_seed.is_from_proof(&parent_vrf_proof)` and never calls `VRF::verify`. Repo-wide search confirms no `VRF::verify` invocation exists anywhere in `nakamoto/mod.rs` to compensate for this gap.

### Finding Description
The broken equality is: epoch2x requires both `new_seed == hash(proof)` AND `VRF::verify(pubkey, proof, sortition_hash) == true` (`stackslib/src/chainstate/stacks/block.rs:227-237` and `:253-272`), whereas Nakamoto's `validate_vrf_seed` only requires the first equality:

```
// stackslib/src/chainstate/nakamoto/mod.rs:1689-1710
let parent_vrf_proof = NakamotoChainState::get_parent_vrf_proof(...)?;
if !block_commit.new_seed.is_from_proof(&parent_vrf_proof) {
    ...
    return Err(...);
}
Ok(())
``` [1](#0-0) 

`is_from_proof` is a pure hash-equality check (`hash(proof) == new_seed`); it does not authenticate `proof` against any sortition hash or public key. The parent tenure's proof is fetched via `get_parent_vrf_proof` purely to compute the expected hash for chaining continuity, not to re-verify the VRF signature. The corresponding epoch2x code explicitly performs the second, cryptographic check:
```
// stackslib/src/chainstate/stacks/block.rs:253-272
let valid = match VRF::verify(
    &leader_key.public_key,
    &self.proof,
    sortition_chain_tip.sortition_hash.as_bytes().as_ref(),
) { ... };
if !valid { return Err(...); }
``` [2](#0-1) 

I could not locate any equivalent `VRF::verify` call elsewhere in the Nakamoto validation pipeline (`stackslib/src/chainstate/nakamoto/mod.rs`) that would substitute for this missing check; a repository-wide search for `VRF::verify` returns hits only in `block.rs` (epoch2x), `vrf.rs` (library implementation), `keychain.rs`/`relayer.rs`/`node.rs`/`tenure.rs` (miner-side proof *generation*, not verification), and test files. None of these are on the Nakamoto block-acceptance path.

### Impact Explanation
If confirmed to be the only check performed network-wide, this would let a miner (or any actor able to register a leader key and submit a coinbase VRF proof) supply an arbitrary byte string as `proof` whose hash matches an already-committed `new_seed`, without that proof being a genuine VRF output tied to the winning sortition's `sortition_hash` and the leader's registered public key. This breaks the deterministic, unpredictable, grinding-resistant VRF seed chain that all nodes are expected to reproduce identically, which is a Critical-category outcome (invalid block accepted network-wide / VRF-seed divergence affecting sortition determinism) if two honest nodes could compute or accept different chained seeds as a result.

### Likelihood Explanation
Exploiting this would require an attacker to control a registered leader key and submit a competing block-commit and Nakamoto block — feasible for a single miner slot without majority stake, consistent with the "minority-triggerable" threat model described. Preconditions (dueling commits at the same burn height, VRF key reuse across commits) are attacker-controlled and repeatable each tenure round if the gap is real.

### Recommendation
This should be verified further by a background agent with full-repository access (not limited by the index), because:
- I was not able to fully rule out that the cryptographic VRF proof check against `sortition_hash`/leader public key is performed at a different stage of the Nakamoto pipeline (e.g., during `get_parent_vrf_proof`'s underlying retrieval, during leader-key/commit "intended sortition" checks in `stackslib/src/chainstate/burn/operations/leader_block_commit.rs`, or during coinbase-tx-specific validation not captured by my grep for the literal string `VRF::verify`).
- The index-based search tool has coverage limits, and `get_parent_vrf_proof`'s full implementation, plus any call sites of `check_block_commit_vrf_seed` named in the question, were not fully inspected within the available tool budget.

Given this uncertainty, I recommend the user start a full Devin session with complete filesystem access to (a) read the full body of `get_parent_vrf_proof` and any `check_block_commit_vrf_seed`/`check_intended_sortition` functions in `leader_block_commit.rs`, and (b) confirm definitively whether `VRF::verify(leader_key.public_key, proof, sortition_hash)` is invoked anywhere in the Nakamoto acceptance path before treating this as a confirmed, reportable vulnerability.

### Proof of Concept
Cannot be finalized without confirming the above; a full PoC would need to construct a two-fork harness where a losing commit's VRF proof (valid over the sibling sortition's hash) is spliced into a winning tenure's coinbase, asserting that the winning fork's block is accepted despite `VRF::verify` failing against the actual winning `sortition_hash`/public key pair — contingent on locating (or confirming the absence of) the second check.

            &block_commit.txid,
