Based on the investigation, I found a concrete analog: `remove_account` in nearcore's runtime removes far less state than the set of trie columns that are actually keyed by `account_id`, leaving stale cross-shard-receipt bookkeeping (`ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`) behind when an `AccountId` is deleted and later recreated — mirroring the Palmera pattern where `removeOrg` didn't clear all storage tied to the reused identifier.

### Title
Incomplete Cleanup on `DeleteAccount` Leaves Postponed/Promise-Yield Receipt State That Executes Against a Recreated Account of the Same Name - (File: `core/store/src/utils/mod.rs`)

### Summary
`DeleteAccountAction` only calls `remove_account`, which clears the `Account`, `ContractCode`, `AccessKey`/gas-key-nonce, and `ContractData` trie rows for the account id [1](#0-0) . However, `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` lists twelve columns keyed by `account_id`, including `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, and `PromiseYieldStatus`, none of which are touched by `remove_account` [2](#0-1) . If a receiver account has in-flight cross-contract-call state (a postponed action receipt awaiting `input_data_ids`, or a parked `PromiseYield`) at the moment it is deleted, that bookkeeping is never cleared and remains addressed to the now-vacant `account_id`.

### Finding Description
`action_delete_account` performs a storage-usage cap check and a gas-key-balance check, then unconditionally calls `remove_account` and clears the in-memory `Account` [3](#0-2) . There is no check that the account has no outstanding `PostponedReceipt`/`PromiseYieldReceipt` before allowing deletion, and `remove_account` does not iterate or remove those columns [4](#0-3) .

Because NEAR account ids are freely re-creatable after deletion (`CreateAccountAction`/implicit-creation just requires the id currently has no `Account` row, per `check_account_existence`) [5](#0-4) , a new, unrelated owner can take over the exact same `account_id`. Any pending `Data`/`PromiseResume` receipt that later arrives for the old `data_id` will still find the dangling `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows keyed to that `account_id` and will drive execution of the **stale postponed `ActionReceipt`** once the last input datum lands, exactly as normal completion would [6](#0-5) . Likewise, a late `PromiseResume` will match a residual `PromiseYieldReceipt`/`PromiseYieldStatus` entry and re-execute the old yielded receipt [7](#0-6) , and the promise-yield timeout scanner will also still find and act on the residual `PromiseYieldTimeout` queue entry pointing at the deleted-then-recreated `account_id` [8](#0-7) . In all these paths, `apply_action_receipt` re-reads whatever `Account` currently exists at that id at execution time — it does not know or check that the account was deleted and replaced in the interim [9](#0-8) . This is the direct nearcore analog of the Palmera bug: state indexed by a reusable identifier (`account_id` here, org name there) is not fully purged on "deletion," so a new owner of that identifier inherits foreign state they never authorized.

### Impact Explanation
If the stale postponed/yielded receipt's actions include a `Transfer`, `FunctionCall`, `AddKey`, or other privileged action, they will execute against the *new* account (the new legitimate owner of that `account_id`), using the old predecessor/signer as `predecessor_id`/`actor_id` context baked into the stored `Receipt`. This can move funds out of the new account, invoke its (freshly deployed, different) contract with attacker-controlled residual input, or otherwise mutate state the new owner never consented to — i.e., unauthorized value movement / invalid state transition triggered purely by residual cross-shard bookkeeping surviving an account deletion. It also represents unbounded, unrecoverable state growth (these entries are never cleaned since the consuming account that would normally clear them is gone), which the account-deletion size cap (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`) does not account for, since that cap only inspects `Account::storage_usage()` and not these separate columns [10](#0-9) .

### Likelihood Explanation
Reachability requires only ordinary, permissionless actions available to any transaction signer: (1) cause a receipt to `account_id` that becomes postponed (an incoming `ActionReceipt` with `input_data_ids` not yet satisfied) or a `PromiseYield` that is left unresumed, (2) delete `account_id` via a normal `DeleteAccountAction` before the corresponding `Data`/`PromiseResume` arrives, and (3) have someone (attacker or unrelated party) recreate the same `account_id`. Steps 1–2 are entirely within a single account owner's control and require no cross-account cooperation; an attacker who owns `account_id` can engineer the timing directly (e.g., issue a self-targeted cross-contract call with an unresolved dependency, then immediately self-delete). Step 3 (recreation by someone else) depends on the deleted name being desirable/known, similar to the org-name-squatting premise in the Palmera report, which somewhat limits but does not eliminate the practical likelihood — sub-accounts under an attacker-controlled parent make this fully attacker-controlled without needing any third party at all, since the attacker can also perform step 3.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), also iterate and remove the remaining account-keyed columns — `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` — for the account being deleted, or alternatively reject `DeleteAccountAction` outright when any such residual entry exists for the account (similar in spirit to the existing `DeleteAccountStaking`/`DeleteAccountWithLargeState` guards in `action_delete_account`). Any protocol-visible change here would need to go through the standard `ProtocolFeature` gating used elsewhere in this file (e.g. `FixDeleteAccountGlobalContractStorageUsage`).

### Proof of Concept
1. Attacker controls `parent.near` and creates `victim.parent.near`.
2. From `victim.parent.near`, send a cross-contract call receipt `R1` to itself with an `input_data_ids` entry that will never be satisfied (e.g., target a promise callback keyed to a `data_id` that legitimately won't resolve soon) — `process_action_receipt` stores `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` for `victim.parent.near` [11](#0-10) .
3. Immediately submit `DeleteAccountAction` for `victim.parent.near`; `action_delete_account`/`remove_account` succeed without touching the postponed-receipt columns [3](#0-2) .
4. Attacker (still controlling `parent.near`) recreates `victim.parent.near` and funds it / lets a third party fund it, believing it is a fresh account.
5. Attacker (who controls the original `predecessor_id`/promise chain) triggers the delayed `Data` receipt that satisfies `R1`'s pending `input_data_id`; the runtime finds `pending_data_count == 1`, fetches the stale `PostponedReceipt` and executes it against the *new* `victim.parent.near` account via `apply_action_receipt` [12](#0-11) , running `R1`'s original actions (e.g. `Transfer`/`FunctionCall`) against the new account's balance/contract without the new owner's consent.

Note: I was not able to execute or step through this scenario in a live nearcore node (no sandbox/terminal access in this mode), so the exact conditions under which `DeleteAccountAction` can be issued while a postponed/yield entry is still outstanding (e.g., interaction with `DeleteActionMustBeFinal` and `check_actor_permissions`) should be validated by a Devin session with repo execution access before treating this as fully confirmed.
