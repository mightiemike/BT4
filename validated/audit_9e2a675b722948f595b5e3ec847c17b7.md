### Title
Logs and internal state emitted by failed/exceptional TVM executions are not cleared unless the unreleased `allowTvmOsaka` hard-fork flag is active - (File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java)

### Summary
In `VMActuator.execute` (reached via `RuntimeImpl.execute` from `/wallet/triggersmartcontract` -> sign -> `/wallet/broadcasttransaction`), the code path that discards logs/state deltas for exceptional (non-revert) VM failures — `clearExceptionResult` — only clears `ProgramResult.getLogInfoList()`/`getDeleteAccounts()` when `VMConfig.allowTvmOsaka()` is true. This flag is a committee-activated hard-fork switch, off by default, so on chains/deployments where it hasn't been activated, `JVMStackOverFlowException`, `OutOfTimeException`, and generic `Throwable` failures leave previously-emitted `LOG0-4` entries attached to the transaction's `ProgramResult` even though `rootRepository.commit()` was never called for that execution.

### Finding Description
`VMActuator.execute` runs the VM via `VM.play(program, ...)` and then branches on outcome:
- If `result.getException() != null || result.isRevert()` and the exception was *captured on the result* (not thrown as a Java exception), logs are unconditionally cleared: [1](#0-0) .
- If, instead, execution throws a Java exception up through `VM.play` (stack overflow, out-of-time, or any other `Throwable`), control goes to the `catch` blocks, where `clearExceptionResult(result)` is called, but that method only clears `deleteAccounts`/`logInfoList` when `VMConfig.allowTvmOsaka()` is true: [2](#0-1) .

`allowTvmOsaka` is one of many chain-parameter feature flags gated by committee proposal, off by default and only flips on via governance activation: [3](#0-2) [4](#0-3) .

None of the catch branches call `rootRepository.commit()`, so account/storage state for that failed execution is never persisted, but `result` (with its uncommitted `LogInfoList`) is still assigned into the transaction context and consumed downstream: [5](#0-4) . That `ProgramResult` is what `RuntimeImpl.execute` exposes via `getResult()` [6](#0-5) , and it feeds into `Manager.processTransaction`, which builds `TransactionInfoCapsule` from `trace` and posts contract triggers (event/log subscriptions) from the same trace object: [7](#0-6) .

An attacker who controls contract bytecode can craft a contract that emits one or more `LOG` events and then deliberately triggers a stack overflow (deep recursion), an out-of-time condition, or another unexpected `Throwable` from within a nested call — none of which are the plain `REVERT` opcode path that is explicitly logging-safe. On chains where `allowTvmOsaka` has not been activated, the emitted logs remain attached to `ProgramResult` and propagate into `TransactionInfoCapsule`/event-plugin triggers even though the corresponding state changes were never committed to the `Repository`.

### Impact Explanation
Downstream consumers (event subscribers, off-chain indexers, monitoring/settlement logic relying on `TransactionInfo` logs or on `EventPluginLoader` triggers) would observe log events for a transaction whose state changes were never actually committed. This is a divergence between published execution artifacts (logs/triggers) and the actual committed TVM state — exactly the invariant violation described in the question — and could drive false settlement or monitoring decisions (e.g., an off-chain relay crediting a deposit event that never actually happened on-chain).

### Likelihood Explanation
The precondition is that `allowTvmOsaka` is not yet activated on the target chain (governance-controlled parameter). Given the flag exists specifically to fix this exact class of bug (log/delete-account leakage on exceptional catch paths) but is hard-fork-gated rather than always-on, any deployment that has not yet passed this specific committee proposal is exposed. Triggering deep recursion/stack overflow or CPU-time-limit exceptions from attacker-supplied bytecode via `/wallet/triggersmartcontract` is straightforward and fully within the "attacker controls contract bytecode/calldata/nested-call structure" threat model stated in the question.

### Recommendation
Make `clearExceptionResult`'s log/delete-account clearing unconditional (not gated by `allowTvmOsaka`) for all exceptional/`Throwable` catch branches in `VMActuator.execute`, matching the behavior already applied for the `result.getException() != null || result.isRevert()` branch. Alternatively, backport the fix as a mandatory (non-optional) chain-wide behavior change rather than an opt-in hard fork flag, since it corrects an artifact/state consistency bug rather than adding new semantics.

### Proof of Concept
Java integration test plan (extending `RuntimeImplTest`/`VMActuatorMockTest` patterns already in the repo):
1. Deploy a contract that in one function: emits a `LOG1` event, then recurses deeply enough to trigger `JVMStackOverFlowException` (or busy-loops to trigger `OutOfTimeException`).
2. Ensure `VMConfig`'s snapshot has `allowTvmOsaka = false` (default/pre-hardfork state) via `ConfigLoader`/test snapshot setup.
3. Call `RuntimeImpl.execute(context)` through `TvmTestUtils.triggerContractAndReturnTvmTestResult` or equivalent.
4. Assertions:
   - `result.getException()` is a `JVMStackOverFlowException`/`OutOfTimeException` (execution failed).
   - `RepositoryImpl.createRoot(...)` shows no state change for the contract's storage (confirming no commit occurred).
   - `result.getLogInfoList()` is non-empty (bug: log data survives despite uncommitted state) — expected assertion for a fixed system is that this list is empty; the PoC demonstrates it is not, confirming the divergence.
5. Repeat with `allowTvmOsaka = true` to show the list becomes empty, confirming the flag directly controls this consistency guarantee and that pre-activation deployments are exposed.
