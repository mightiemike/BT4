### Title
Missing Early Return in `validate_delegate_action_key` Allows Nonce Advancement on Rejected `DepositWithFunctionCall` DelegateAction — (`File: runtime/runtime/src/actions.rs`)

---

### Summary

In `validate_delegate_action_key`, when a `DelegateAction` signed with a `FunctionCall` access key carries a nonzero deposit, the runtime correctly sets `result.result = Err(DepositWithFunctionCall)` but — before protocol version 85 — **does not return early**. Execution falls through to the nonce-update block at lines 685–699, which unconditionally writes the new nonce to the trie. `apply_delegate_action` then sees `result.result.is_err()` and suppresses receipt creation, so the intended action never executes, yet the sender's access-key nonce has already been permanently advanced. A malicious relayer holding a user's signed `DelegateAction` can exploit this to burn the user's nonce without executing the delegated action.

---

### Finding Description

`validate_delegate_action_key` enforces three sequential constraints for `FunctionCall`-permission keys:

1. `deposit == 0` (lines 637–649)
2. `receiver_id` matches the key's `receiver_id` (lines 651–659)
3. `method_name` is in the allowed list (lines 661–673)

Each of checks 2 and 3 returns early on failure. Check 1 does **not** return early (pre-v85):

```rust
if function_call.deposit > Balance::ZERO {
    result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
        InvalidAccessKeyError::DepositWithFunctionCall,
    ).into());
    // ← no early return before FixDelegateActionDepositWithFunctionCallError
}
// falls through to receiver_id check, then method check, then:
match nonce_update {
    DelegateNonceUpdate::AccessKey => {
        access_key.nonce = delegate_nonce.nonce();
        set_access_key(state_update, sender_id.clone(), public_key.clone(), &access_key);
    }
    ...
}
```

When `deposit > 0` **and** `receiver_id` matches **and** `method_name` matches (or the allowed list is empty), none of the subsequent checks fire an early return, so the nonce-update block at lines 685–699 executes. The trie is mutated with the new nonce. Control returns to `apply_delegate_action`, which checks `result.result.is_err()` at line 449 and exits without emitting a receipt.

A secondary effect: when `deposit > 0` **and** `receiver_id` does **not** match, the `ReceiverMismatch` error overwrites `DepositWithFunctionCall` in `result.result`, giving the caller a misleading error. In that branch the nonce is not advanced (the `ReceiverMismatch` arm does return early), so the secondary effect is diagnostic-only. [1](#0-0) [2](#0-1) [3](#0-2) 

---

### Impact Explanation

**Broken invariant**: a `DelegateAction` that fails access-key permission validation must not mutate any persistent state. The nonce is persistent state; advancing it without executing the action violates this invariant.

**Concrete effect**: the sender's `FunctionCall` access-key nonce is consumed. The user must sign a new `DelegateAction` with a higher nonce to retry. Because the relayer controls submission timing and can selectively replay or withhold signed `DelegateAction`s, a malicious relayer can repeatedly burn nonces, preventing the user from executing their intended meta-transaction until they rotate their key or generate a fresh nonce.

No NEAR tokens are transferred and no receipt is created, so direct fund theft does not occur. The impact is **transaction manipulation**: the user's authorized action is suppressed and their nonce is consumed without consent. [2](#0-1) 

---

### Likelihood Explanation

Triggering the nonce-advancement path requires:

1. The sender holds a `FunctionCall` access key.
2. The signed `DelegateAction` carries `deposit > 0`.
3. The `DelegateAction`'s `receiver_id` equals the key's `receiver_id`.
4. The `DelegateAction`'s `method_name` is in the key's allowed list (or the list is empty).

Conditions 3 and 4 are the normal case for a legitimately constructed meta-transaction; condition 2 is the user error (attaching a deposit via a key that forbids it). A user who mistakenly attaches a deposit, or a relayer who modifies the deposit field before submission (impossible — the deposit is covered by the signature), would trigger this. Because the `DelegateAction` is user-signed, the relayer cannot forge condition 2; however, a user who signs such an action and hands it to an untrusted relayer is exposed.

---

### Recommendation

Add an unconditional early return immediately after setting the `DepositWithFunctionCall` error, regardless of protocol version. The `FixDelegateActionDepositWithFunctionCallError` feature flag (protocol version 85) already implements this:

```rust
if function_call.deposit > Balance::ZERO {
    result.result = Err(...DepositWithFunctionCall...);
    return Ok(()); // ← must always fire
}
```

The legacy fallthrough path should not be preserved for any protocol version, because it mutates state (nonce) in a way that cannot be rolled back. [4](#0-3) [5](#0-4) 

---

### Proof of Concept

The codebase itself contains a regression test that demonstrates the pre-fix behavior:

```
test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix
```

It constructs a `DelegateAction` with `deposit = 1 yoctoNEAR`, a `FunctionCall` key whose `receiver_id` is `"other.test.near"`, and a `DelegateAction` targeting `"token.test.near"`. On protocol version 84 (pre-fix), the test asserts that the returned error is `ReceiverMismatch` — proving that `DepositWithFunctionCall` was silently overwritten.

For the nonce-advancement variant, set `receiver_id` in the key to match the `DelegateAction`'s `receiver_id` (and leave `method_names` empty). On protocol version ≤ 84, `validate_delegate_action_key` returns `Ok(())` with `result.result = Err(DepositWithFunctionCall)` **and** the trie nonce is advanced. A subsequent call with the same nonce returns `DelegateActionInvalidNonce`, confirming the nonce was consumed. [6](#0-5) [7](#0-6)

    fn deposit_with_function_call_and_receiver_mismatch(
        protocol_version: ProtocolVersion,
    ) -> ActionResult {
        let (_, signed_delegate_action) = create_delegate_action_receipt();
        let sender_id = signed_delegate_action.delegate_action.sender_id.clone();
        let sender_pub_key = signed_delegate_action.delegate_action.public_key.clone();

        let initial_nonce: u64 = 19_000_000;
        let access_key = AccessKey {
            nonce: initial_nonce,
            permission: AccessKeyPermission::FunctionCall(FunctionCallPermission {
                allowance: None,
                // Use a different receiver than the delegate action to trigger
                // ReceiverMismatch after DepositWithFunctionCall.
                receiver_id: "other.test.near".to_string(),
                method_names: Vec::new(),
            }),
        };

        let mut apply_state =
            create_apply_state(signed_delegate_action.delegate_action.max_block_height);
        apply_state.current_protocol_version = protocol_version;
        let mut state_update = setup_account(&sender_id, &sender_pub_key, &access_key);

        let mut delegate_action = signed_delegate_action.delegate_action;
        delegate_action.nonce = initial_nonce + 1;
        delegate_action.actions =

                args: Vec::new(),
                deposit: Balance::from_yoctonear(1),

        validate_delegate_action_key(
            &mut state_update,
            &apply_state,
            (&delegate_action).into(),
            &mut result,
        )
        .expect("validate_delegate_action_key must not return a RuntimeError");

        result
    }
