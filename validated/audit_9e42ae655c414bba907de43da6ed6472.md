### Title
`RepositoryImpl.calculateGlobalEnergyLimit` returns unbounded (near-`Long.MAX_VALUE`) energy instead of zero when `totalEnergyWeight` is zero - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
This is a structural analog of the reported bug class: a proportional-allocation formula (`amount = weight * totalLimit / totalWeight`) that fails to explicitly short-circuit to `0` when the divisor-like state variable (`totalEnergyWeight`, the java-tron analog of `totalLocked`) is zero, relying instead on an `assert` statement that is compiled out in production JVMs (`-ea` is not enabled by default).

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes a caller's global energy limit proportionally to `totalEnergyWeight`: [1](#0-0) 

Unlike the sibling implementations in `EnergyProcessor` and `BandwidthProcessor`, which both explicitly check `totalEnergyWeight == 0` / `totalNetWeight == 0` and return `0` [2](#0-1) , this `RepositoryImpl` variant (used by the TVM/actuator `Repository` layer) has **no unconditional zero-guard** for `totalEnergyWeight`. It only has:
```java
assert totalEnergyWeight > 0;
```
which is a no-op at runtime unless the JVM is started with `-ea` (assertions are disabled by default in production Java deployments, including typical `java -jar FullNode.jar` invocations). If `totalEnergyWeight` is `0` while `hardenResourceCalculation()` is `false` (legacy path), the code executes:
```java
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
`totalEnergyLimit / 0.0` evaluates to `Double.POSITIVE_INFINITY` in IEEE-754 double arithmetic (no `ArithmeticException` is thrown for floating-point division by zero), and `energyWeight * Infinity` remains `Infinity`. Casting `(long) Infinity` in Java yields `Long.MAX_VALUE`, not `0`. This exactly mirrors the reported bug: the function returns a non-zero (in this case, maximal) value precisely when the underlying denominator/base quantity is zero, instead of returning `0` as intended by the analogous guarded code paths elsewhere in the codebase.

### Impact Explanation
This function feeds directly into `EnergyProcessor.useEnergy` -> `calculateGlobalEnergyLimit` gating logic used to decide whether a transaction can consume energy without payment [3](#0-2) , and the `RepositoryImpl` copy is used within TVM contract execution/native contract processors that reference `getTotalEnergyWeight()` (`DelegateResourceProcessor`, `FreezeBalanceProcessor`, `UnDelegateResourceProcessor`, etc.). If `totalEnergyWeight` were ever `0` (e.g., freshly bootstrapped private/consortium chain, or after mass unfreezing under `supportUnfreezeDelay()`-disabled configurations), any account with `>= 1 TRX` frozen for energy would be granted an energy limit of `Long.MAX_VALUE`, allowing unlimited free contract execution — an accounting/resource-underpricing bypass rather than a benign zero-return. This is a state/accounting-divergence class impact matching the "underpriced-public-work" category in scope.

### Likelihood Explanation
The condition requires `totalEnergyWeight == 0` and `hardenResourceCalculation()` disabled (legacy math path) simultaneously. On TRON mainnet today this is unlikely because `totalEnergyWeight` is virtually never zero and `allowHardenResourceCalculation()`/harden flags are expected enabled on production networks. However, on any network where these hardening flags are not yet activated (new private chains, test networks, or during a transitional period before the harden proposal is turned on) this is directly and cheaply reachable by an ordinary unprivileged user simply freezing the minimum TRX for energy — no privileged role required. It is a real, non-mocked code path (not test-only), so likelihood is best classified as low-to-moderate depending on network configuration, but the flaw itself is concrete and directly analogous to the reported issue (missing explicit zero-check, silent reliance on a disabled assertion).

### Recommendation
Add an explicit, unconditional guard in `RepositoryImpl.calculateGlobalEnergyLimit` (mirroring `EnergyProcessor.calculateGlobalEnergyLimitV2` and `BandwidthProcessor.calculateGlobalNetLimit`):
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
placed before both the hardened `BigInteger` path and the legacy double-arithmetic path, removing dependence on the `assert` statement for correctness enforcement in production.

### Proof of Concept
1. Configure/observe a chain state where `DynamicPropertiesStore.getTotalEnergyWeight() == 0` (e.g., a freshly initialized private network before any `FreezeBalanceContract`/`FreezeBalanceV2Contract` for `ENERGY` has been submitted network-wide, with `allowHardenResourceCalculation()` and `supportUnfreezeDelay()` left at defaults/disabled).
2. Submit a `FreezeBalanceContract` (or `FreezeBalanceV2Contract`) freezing `>= 1 TRX_PRECISION` for `ENERGY` from an unprivileged account, which updates that account's `AllFrozenBalanceForEnergy` but the chain-wide `TotalEnergyWeight` snapshot used by other accounts querying limits may still read `0` in the relevant epoch/isolated `Repository` context.
3. Trigger any TVM path that calls `Repository.calculateGlobalEnergyLimit(accountCapsule)` (e.g., via `TransactionTrace`/`VMActuator` energy check) with `hardenResourceCalculation()` disabled.
4. Observe that the returned energy limit is `Long.MAX_VALUE` (or an otherwise wildly incorrect huge number) instead of `0`, due to `(long) (energyWeight * (totalEnergyLimit / 0.0))` evaluating to `(long) Double.POSITIVE_INFINITY`, confirming the divide-by-zero-to-non-zero defect analogous to `EmissionManagerV1._calculateRebaseEmission` returning non-zero when `totalLocked == 0`.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
