### Title
Replay-verify tool silently ignores state-checkpoint hash divergence, defeating archive replay integrity checks - (File: `types/src/transaction/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the routine used by the `db-tool replay-on-archive` state-integrity check to compare freshly re-executed transaction outputs against the historical, backed-up `TransactionInfo` — explicitly skips comparing `state_checkpoint_hash` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`). This is called out in the code itself as a known gap. As a result, a divergence in the locally computed world-state root versus the archived/expected state root will not be flagged as a mismatch by this tool, even though every other field (write-set hash, events, gas, status, transaction hash) matches.

### Finding Description
`ensure_match_transaction_info` validates transaction status, gas used, write-set hash, and event root hash against a supplied `TransactionInfo`, but deliberately does **not** validate the state/hot-state checkpoint hashes: [1](#0-0) 

The comment in the code explicitly documents this gap: [2](#0-1) 

This function is the sole per-transaction correctness check used by `storage/db-tool`'s `replay_on_archive` verification path, which re-executes historical transactions with the VM against a locally computed state view and compares the result to the trusted/backed-up `TransactionInfo`: [3](#0-2) 

Because the comparator never inspects `state_checkpoint_hash`, if VM execution (or a subtly different SMT/JMT-application path) produces a *different* world-state root than what was originally committed on-chain — for example due to a state-computation bug, a non-deterministic write, or an unintended fork in state application logic — `execute_and_verify` will still report success as long as the write set, events, gas, and status happen to match. The divergence in the authenticated commitment (the state checkpoint root that is itself part of the hashed, accumulator-committed `TransactionInfo`) goes completely undetected by this tool.

### Impact Explanation
This breaks the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Committed state that differs from the correct VM result" integrity classes called out as in-scope. The `replay_on_archive` tool exists specifically to let operators/auditors validate that historical mainnet transactions replay deterministically to the exact same ledger state. Silently ignoring the state checkpoint hash means this tool can produce false negatives for the most important class of bug it's meant to catch: **state root divergence** (the same failure mode that would manifest as a hard fork or an unauthenticated state view being served to clients). An attacker or a latent non-determinism bug that alters state without altering the write-set hash (or a case where state application diverges from what was verified) would pass this check undetected, undermining confidence in "verified" replay/audit results and any tooling or alerts built on top of it.

### Likelihood Explanation
Medium: this is not remotely triggerable by an unprivileged network attacker to corrupt consensus state directly; the gap is in an internal auditing/replay tool. However, it is guaranteed to manifest as soon as (a) this tool is relied upon to confirm the absence of state divergence, and (b) any state-root-affecting bug exists elsewhere in execution/commit/JMT application — which the tool is specifically supposed to catch and does not.

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check inside `execute_and_verify`) to compare the locally computed state-checkpoint hash (and hot-state/position checkpoint hashes when applicable) against `expected_txn_info.state_checkpoint_hash()` at state-checkpoint boundaries, as the existing TODO comment already suggests, before this tool's results are treated as an authoritative signal of replay correctness.

### Proof of Concept
Not applicable as an on-chain exploit — this is a verification-tool logic gap. Conceptual reproduction:
1. Construct (or simulate) a transaction whose re-execution produces an identical write set/events/gas/status but a different resulting state root (e.g., due to non-deterministic state application or a JMT commit bug).
2. Run `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` against the archived `TransactionInfo` for that version.
3. Observe that `ensure_match_transaction_info` returns `Ok(())` despite `state_checkpoint_hash` differing, because the comparator never checks that field — confirmed directly by the code at [4](#0-3) .

Note: I was unable to fully trace whether `expected_txn_infos` fed into `execute_and_verify` are cryptographically re-verified against a trusted ledger-info/accumulator proof elsewhere in the `replay_on_archive` pipeline (the backup-handler transaction iterator's authentication was not resolved before running out of search budget), so I cannot confirm whether a corrupted backup archive alone could exploit this gap versus it only masking genuine local computation bugs. This should be verified in follow-up before treating this as a standalone high-severity finding rather than a defense-in-depth gap in an auditing tool.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
