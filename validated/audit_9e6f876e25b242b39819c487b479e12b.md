### Title
Front-running `ExchangeWithdrawContract` via `ExchangeTransactionContract` swaps distorts token ratio received by exchange creator (no minimum-received check) - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` lets an exchange creator withdraw liquidity from a bancor-style TRX10/TRC10 token pair by specifying only the quantity of one token (`quant`); the "other" token amount returned (`anotherTokenQuant`) is derived on-the-fly from the *current* pool balances at execution time. Unlike `ExchangeTransactionContract`, which carries an `expected` field to bound slippage, `ExchangeWithdrawContract` has no caller-supplied minimum for `anotherTokenQuant`. This is the same bug class as the reported Aera `finalize()`/`returnFunds()` issue: a withdrawal that depends on pool ratio at execution time, with no minimum-received guard, can be front-run by a swap that skews the ratio, forcing the withdrawer to accept an unfavorable token distribution.

### Finding Description
`ExchangeWithdrawActuator.execute()`/`doValidate()` compute `anotherTokenQuant` purely from the exchange's live `firstTokenBalance`/`secondTokenBalance` at the moment the withdraw transaction executes: [1](#0-0) 

The only sanity checks in validation are that `anotherTokenQuant > 0` and a rounding "precision" check comparing the computed value against itself — neither is a caller-specified minimum-received bound: [2](#0-1) 

By contrast, `ExchangeTransactionContract` (the swap contract) explicitly supports an `expected` field to protect against slippage: [3](#0-2) 

but the withdraw path provides no equivalent protection, meaning the exchange creator's withdrawal is executed against whatever pool ratio exists at that moment — regardless of who moved it there.

### Impact Explanation
An attacker who observes a pending `ExchangeWithdrawContract` transaction in the mempool can submit an `ExchangeTransactionContract` (swap) beforehand (or have it ordered before, depending on the block producer building the block) that shifts `firstTokenBalance`/`secondTokenBalance` in the exchange. Because `ExchangeWithdrawActuator` recomputes `anotherTokenQuant` from the post-swap balances, the withdrawer receives a token ratio they never agreed to and cannot bound — directly mirroring the Aera `finalize()` scenario where a Treasury unexpectedly received a skewed WETH/DAI split. This constitutes an accounting/market-math manipulation reachable from any broadcast transaction, without any privileged role beyond being the exchange's creator (a normal, permissionless role obtainable by anyone who calls `ExchangeCreateContract`).

### Likelihood Explanation
The attack requires no special privileges — any account can create an exchange, deposit/withdraw, and any account can submit `ExchangeTransactionContract` swaps against it. The only requirement is timing the swap to land before the withdrawal in the same or an adjacent block, which is a standard front-running primitive available to any network participant (including block-producing witnesses who can freely order transactions within their own produced block). The precision check in `doValidate()` does not prevent this because it validates internal self-consistency of the computed ratio, not resistance to balance changes caused by an intervening swap.

### Recommendation
Add a caller-specified minimum-received bound (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeWithdrawContract`/`ExchangeWithdrawActuator`, e.g., an `expected` or `minAnotherTokenQuant` field that the actuator validates against the computed `anotherTokenQuant`, reverting if the withdrawer would receive less than the specified minimum. This closes the front-running window the same way slippage protection does for swaps.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeWithdrawContract` for `exchangeId` with `tokenId=firstTokenID`, `quant=Q`, expecting to receive `anotherTokenQuant` computed from the current `firstTokenBalance`/`secondTokenBalance` ratio.
2. Before this transaction executes, an attacker broadcasts `ExchangeTransactionContract` against the same `exchangeId`, swapping a large amount of `secondTokenID` for `firstTokenID` (or vice versa), which is processed by `ExchangeTransactionActuator` and mutates `exchangeCapsule`'s balances via `Commons.putExchangeCapsule`.
3. When the withdraw transaction executes, `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` from the now-skewed balances at `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java:74-89`, resulting in the creator receiving a token distribution far from what they expected when they signed the transaction, with no way to have prevented it since no minimum-received field exists on the contract.
