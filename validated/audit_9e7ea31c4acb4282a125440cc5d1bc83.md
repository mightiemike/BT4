### Title
Unvalidated zero-address recipient in inbound PRC20 deposit path can permanently mint-and-lose bridged tokens - (File: x/uexecutor/keeper/handler.go, x/uexecutor/types/inbound.go)

### Summary
The reported ExperiPie `LibERC20.mint` bug is that minting to `address(0)` increments `totalSupply` while the tokens become permanently unrecoverable. The Push Chain analog is the inbound funds path: `Keeper.depositPRC20` [1](#0-0)  converts the inbound's `Recipient` string directly to an EVM `common.Address` and calls `CallPRC20Deposit`, which invokes the PRC20 contract's `deposit(to, amount)` (a mint-style call) via `DerivedEVMCall` [2](#0-1) . If `to` resolves to the zero address, tokens are minted to `address(0)` while `totalSupply` increases — mirroring the ExperiPie finding.

### Finding Description
`Inbound.ValidateForExecution` is the only execution-time gate on the `Recipient` field for `TxType_FUNDS`/`TxType_GAS`, requiring it to be non-empty and pass `utils.IsValidAddress(p.Recipient, utils.HEX)` [3](#0-2) . `ExecuteInboundFunds` then calls `common.HexToAddress(inbound.Recipient)` and deposits PRC20 directly to that address with no additional zero-address check [4](#0-3) . The same unguarded pattern repeats for the CEA-recipient branches in `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`, and for revert re-minting in `handleFailedOutbound`, where the revert recipient is taken from attacker-influenced `RevertInstructions.FundRecipient` or `Sender` with only an empty-string check, no zero-address check [5](#0-4)  and [6](#0-5) .

The `Recipient`/`Sender`/`FundRecipient` fields ultimately originate from the external-chain gateway event data that an unprivileged user fully controls when initiating a deposit on the source chain; validators (UVs) simply observe and vote on whatever the gateway contract emits. If `utils.IsValidAddress` only performs a hex-format/length check (e.g. `^0x[0-9a-fA-F]{40}$`) without excluding the all-zero address, an attacker can set the recipient/fund-recipient field to `0x000...0` in their bridge deposit, causing honest validators to converge on and finalize a UTX that deposits (mints) PRC20 tokens to the zero address — permanently burning the bridged value while `PRC20.totalSupply()` is incremented, exactly matching the reported invariant break.

### Impact Explanation
If confirmed, this causes permanent, unrecoverable loss of the user's own bridged funds (self-inflicted, but also potentially reachable via a malformed cross-chain relay/gateway payload) and corrupts PRC20 accounting invariants (`totalSupply` no longer reflects circulating/recoverable supply), which falls under "permanent loss" and "corruption of PRC20 ... accounting" in the allowed impact gate.

### Likelihood Explanation
Likelihood hinges entirely on whether `utils.IsValidAddress` treats the zero address as valid hex, which I could not verify in this session due to tool-call exhaustion. Many simple regex/format-based address validators do not special-case the zero address, making this a plausible, low-effort trigger requiring only a single external-chain deposit transaction with `recipient = 0x000...0`.

### Recommendation
Add an explicit zero-address check (`recipient != common.Address{}`) before every PRC20 mint/deposit call reachable from inbound/revert flows — specifically in `depositPRC20` (x/uexecutor/keeper/handler.go), `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload`, and `handleFailedOutbound`/`buildRevertOutbound` — and/or harden `Inbound.ValidateForExecution` and `utils.IsValidAddress` to reject the zero address for `Recipient` and `RevertInstructions.FundRecipient`.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm `utils.IsValidAddress`'s zero-address handling in this session. Conceptual PoC: an attacker deposits on the source chain via the gateway contract, specifying `recipient = 0x0000000000000000000000000000000000000000` in the bridge event; honest UVs observe and vote the inbound (`TxType_FUNDS`), `ValidateForExecution` passes if `IsValidAddress` doesn't special-case zero, `ExecuteInboundFunds` calls `depositPRC20` → `CallPRC20Deposit` → PRC20 `deposit(0x0, amount)`, minting tokens to the zero address while `totalSupply` increases.

**Note on verification gap:** I was unable to read `utils/address.go`'s `IsValidAddress` implementation before running out of tool-call budget. This is the single determining factor for whether this finding is exploitable or already mitigated — a background Devin session should read that file first to confirm before treating this as a confirmed vulnerability rather than a plausible candidate.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```

```go
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
```
