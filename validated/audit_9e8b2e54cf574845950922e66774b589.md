Found a strong analog in the NEAR Wallet Contract's ERC-20/EOA emulation fee logic. It mirrors the Unitas bug's core flaw — a fee side-effect is executed independently of (and prior to) the success/failure of the primary action, so users can be charged a fee for an action that ultimately fails.

### Title
Wallet Contract pays relayer fee unconditionally before verifying the emulated transfer succeeds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In `inner_rlp_execute`, when a relayed transaction is parsed as an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the Wallet Contract immediately schedules a separate promise to pay that fee to the relayer (`predecessor_account_id`), independent of the promise chain that actually performs the underlying transfer. [1](#0-0) 

### Finding Description
The fee-refund promise to the relayer is created via `env::promise_batch_create`/`promise_batch_action_transfer` in `inner_rlp_execute`, at the same "level" as (but not chained after) the promise that performs the actual action (`ft_transfer` for ERC-20 emulation, or the native transfer for base-token emulation). The main action's outcome is only checked later, in `rlp_execute_callback`, which on `PromiseResult::Failed` refunds only the `caller_deposit` (the yoctoNEAR value attached to the action itself) — not the fee that was already, unconditionally, sent to the relayer. [2](#0-1) 

This is structurally the same root cause as the Unitas report: a fee-related side effect is coupled to an external call/action whose success is assumed rather than verified before value moves. In the Unitas case, the `mint`-signature mismatch on USDT caused the whole swap (including fee logic) to revert. Here, the failure mode is inverted but equally impactful: because the fee transfer is not chained to depend on the outcome of the emulated action (`ft_transfer` via NEP-141, which can fail for many legitimate reasons — unregistered/paused/blacklisted receiver at the token level, insufficient token balance, a non-standard NEP-141 implementation that reverts, etc., mirrored by the ERC-20 emulation path in `eth_emulation.rs`), the relayer is paid regardless of whether the user's intended transfer completes. [3](#0-2) 

The comment in the code even acknowledges the fee is meant to compensate the relayer for successfully relaying, but the implementation does not gate the fee payment on actual success of the relayed action: [4](#0-3) 

### Impact Explanation
Any eth-implicit account owner using a relayer to submit an ERC-20 (NEP-141) or base-token transfer with a non-zero fee will have that fee unconditionally paid to the relayer even if the underlying transfer subsequently fails (e.g., the target NEP-141 contract rejects `ft_transfer`, is paused, or the receiver is blacklisted at the application layer). This is an unauthorized value movement: the relayer profits from failed transactions at the user's expense, and there is no path in `rlp_execute_callback`'s failure branch that reclaims or refunds the already-paid fee. This is a concrete, transaction-reachable fee bypass / incorrect value transfer, not merely a revert/DoS.

### Likelihood Explanation
Reachable by any single relayed Ethereum-style transaction routed through `rlp_execute`/`inner_rlp_execute` for an eth-implicit account using the Wallet Contract, with a nonzero fee and a target NEP-141 token/action that can fail post-fee-payment (a very common, non-adversarial scenario — e.g. any standard NEP-141 contract that can reject a transfer). No privileged role is required; only a normal user relaying a signed transaction through a relayer.

### Recommendation
Chain the fee-payment promise so it only executes after (and conditioned upon) the success of the primary action's promise (e.g., pay the fee inside/after `rlp_execute_callback` based on `PromiseResult::Successful`), or refund the fee to the user alongside the `caller_deposit` refund when the primary promise fails in `rlp_execute_callback`.

### Proof of Concept
1. User signs an Ethereum-style `transfer` (ERC20_TRANSFER_SELECTOR) transaction targeting a NEP-141 token, with `fee > 0`, via their eth-implicit account's Wallet Contract.
2. Relayer submits it through `rlp_execute` → `inner_rlp_execute`. Because `fee` is nonzero and `predecessor_account_id != current_account_id`, the fee-transfer promise to the relayer is created immediately at [5](#0-4) .
3. Separately, the storage-balance-check/`ft_transfer` promise chain is scheduled (`ERC20Transfer` branch) at [6](#0-5) .
4. Suppose the target NEP-141 contract's `ft_transfer` call fails (e.g., receiver blacklisted, contract paused, insufficient balance at execution time due to a race). `rlp_execute_callback` observes `PromiseResult::Failed` and only refunds `caller_deposit`, not the fee already sent to the relayer at step 2.
5. Result: the relayer keeps the fee even though the user's intended transfer never happened — an unauthorized value transfer out of the user's account.

            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
