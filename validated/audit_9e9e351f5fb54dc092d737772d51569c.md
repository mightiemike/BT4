## Analog Found: `ValidateMultiSign` Duplicate-Signer Weight Double-Count

### Title
Signature deduplication in `PrecompiledContracts.ValidateMultiSign` compares full signature bytes instead of signer identity, allowing weight double-counting via ECDSA signature malleability - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The reported bug is that `Consensus.checkSignatures` only checks `signatures.length >= threshold` without deduplicating signers, letting one valid signature be repeated to satisfy a multi-sig threshold. The TVM precompiled contract `ValidateMultiSign` implements the same "weighted multi-signature threshold" pattern used by java-tron smart contracts (e.g. multisig wallets, exchange/escrow authorization logic) and has an analogous flaw: it deduplicates by exact signature bytes rather than by recovered signer address.

### Finding Description
`ValidateMultiSign.execute` iterates over the supplied signature array, recovers the signer address for each, and accumulates `totalWeight` until it meets `permission.getThreshold()`: [1](#0-0) 

The duplicate check only skips an entry when **both** the recovered address **and** the exact merged signature bytes (`merge(recoveredAddr, sign)`) already exist in `executedSignList`:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
```
If the same address appears again but with a **different** signature encoding for the same `(orderHash)` — which is trivially producible via ECDSA signature malleability (`s' = N - s` with adjusted recovery id `v`), both recovering to the identical signer address — the exact-byte check fails to match, the `continue` is skipped, and `totalWeight += weight` is executed again for the same signer.

Unlike `TransactionCapsule.checkWeight` (used for on-chain transaction multi-sig, which dedupes by address/base64 sig string and throws `"has signed twice!"` on collision) — [2](#0-1)  — `ValidateMultiSign` never enforces canonical/low-`s` signatures before deduplication, and its dedup key is the raw signature bytes, not the signer identity. This is the same root-cause pattern as `Consensus.checkSignatures`: a signature-based threshold check that fails to properly deduplicate by signer, allowing one signer to be counted more than once.

### Impact Explanation
`ValidateMultiSign` is a public TVM precompile (address `0x66`-class predefined contract) invoked by any smart contract wanting to verify account-level multi-signature authorization (e.g., custodial/multisig wallets, withdrawal approval contracts, DEX/exchange settlement logic gated by multi-sig). An unprivileged attacker holding only a single valid key can synthesize a second, distinct-byte but validly-recovering signature for the same key/hash via ECDSA malleability, and submit both in the `signatures` array. This inflates `totalWeight` to reach `permission.getThreshold()` without actually obtaining approval from the additional required signer(s), producing an authorization bypass in any contract relying on this precompile for access control or fund release — a concrete accounting/authz-bypass impact matching the reported bug class.

### Likelihood Explanation
Exploitation only requires: (1) one legitimate signature under the account's permission, and (2) trivial arithmetic to derive a malleable counterpart signature (standard, widely-known ECDSA transformation, no private key needed). No privileged role or internal-only access is required — any contract caller can invoke the `ValidateMultiSign` precompile directly with attacker-controlled calldata. This makes the analog readily and cheaply exploitable wherever a contract's security model assumes N distinct signers behind a weighted threshold but only actually requires N valid raw signature encodings.

### Recommendation
In `ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (not by the full signature bytes) before adding `weight` to `totalWeight` — i.e., reject or skip any signature whose recovered address has already contributed weight in the current call, regardless of the signature's raw byte encoding. Additionally, reject non-canonical (`high-s`) signatures at recovery time to eliminate the malleable variant entirely, consistent with the canonicalization already performed by `ECKey.ECDSASignature.toCanonicalised`. [3](#0-2) 

### Proof of Concept
1. Attacker is one of the keys in a `Permission` with `threshold = 2` and two keys each of weight 1 (as in the existing test setup `ValidateMultiSignContractTest.testDifferentCase`) — [4](#0-3) .
2. Attacker signs `toSign` once with `key1` to get `sig = (r, s, v)`.
3. Attacker derives the malleable counterpart `sig' = (r, N - s, v')` (flipping the recovery parity), which recovers to the same address as `key1` but has different raw bytes.
4. Attacker calls `validatemultisign(address, permissionId, hash, [sig, sig'])`.
5. In `ValidateMultiSign.execute`, iteration 1 adds `key1`'s weight (1) and records `(sig, key1_addr)`; iteration 2 finds `key1_addr` already present but `sig'` bytes don't match `sig`, so it does **not** `continue`, and adds `key1`'s weight again (total 2).
6. `totalWeight (2) >= threshold (2)` returns `true`/`ONE`, even though only one real signer (`key1`) actually authorized the order — `key2`'s signature was never provided.
