### Title
Timing-dependent divergence in `validate_shadow_parent_burnchain` allows a malformed shadow-parented block to be accepted on one node and rejected on another - ([File: stackslib/src/chainstate/nakamoto/shadow.rs])

### Summary
`NakamotoChainState::validate_shadow_parent_burnchain` is the only place that checks a normal Nakamoto block's block-commit `parent_vtxindex`/`parent_block_ptr` against a shadow-block parent's sortition, and it is invoked exactly once, at `accept_block` time (before staging), from `validate_normal_nakamoto_block_burnchain`. If the node has not yet staged the shadow-block header for `block.header.parent_block_id`, the function short-circuits to `Ok(())` ( [1](#0-0) ), and this check is never re-run later in `append_block`, which only checks structural `parent_block_id`/`chain_length`/tenure continuity ( [2](#0-1) ). This produces a genuine node-to-node divergence in the accept/reject verdict for the same block, dependent purely on the arrival order of the shadow-block header relative to the child block.

### Finding Description
The claimed equality is: `accept(childBlock)` on Node A `==` `accept(childBlock)` on Node B, for the identical `childBlock` and identical, already-observed Bitcoin block-commit data.

Code path:
- `accept_block` calls `validate_normal_nakamoto_block_burnchain`, which calls `validate_shadow_parent_burnchain` before the block is inserted into the staging DB ( [3](#0-2) [4](#0-3) ).
- `validate_shadow_parent_burnchain` looks up `block.header.parent_block_id` via `staging_db.get_nakamoto_block_header(..)`. If this returns `None` (parent not yet staged), the function returns `Ok(())` immediately, skipping the `parent_vtxindex == 0` and `parent_block_ptr == parent_sn.block_height` checks entirely ( [5](#0-4) ).
- If the header IS present and is a shadow block, the function enforces both invariants and returns `Err(InvalidStacksBlock(..))` on mismatch (same lines).
- This is the *only* call site for `validate_shadow_parent_burnchain` (confirmed via repo-wide search); `append_block`, which performs the actual state transition once the parent is known, re-checks only `parent_block_id` equality, `chain_length` continuity, and `check_tenure_continuity` — none of which re-validate the block-commit's `parent_vtxindex`/`parent_block_ptr` fields against the shadow parent's sortition ( [6](#0-5) ).

Exploit flow: an attacker who wins (or has previously won) a sortition slot crafts a Bitcoin block-commit whose `parent_vtxindex`/`parent_block_ptr` do not correctly reference the shadow-parent tenure's sortition, and broadcasts a Nakamoto block whose `header.parent_block_id` points at that shadow block. On a node (A) that already has the shadow-block header staged, `accept_block` calls the full check, finds the mismatch, and returns `Err`, so the block is never stored in staging. On a node (B) that has not yet received/staged the shadow-block header, the same call trivially returns `Ok(())`; the block passes this gate and — if it also passes `verify_signer_signatures` and other checks — gets stored via `store_block_if_better`. Since `append_block` does not re-check this invariant when the shadow header later becomes available on B, once B eventually processes the shadow parent, the previously-staged malformed child becomes "ready" and gets appended into B's canonical chain, while A never even has it in its staging DB. Node A and Node B thus derive different canonical tips from the same input data, purely due to network-arrival timing of the shadow block.

### Impact Explanation
This is a chain split contingent on shadow-block propagation timing: two honest, non-Byzantine nodes independently and correctly following protocol logic reach different canonical chains for the same set of burnchain and Stacks-block inputs, based only on message arrival order. This matches the Critical category ("a chain split or deep fork ... an invalid block accepted or a valid block rejected network-wide").

### Likelihood Explanation
Preconditions: the attacker needs (a) to win/hold a sortition slot with a block-commit whose parent pointer fields are inconsistent with the shadow-parent tenure, and (b) to broadcast a Nakamoto block with `parent_block_id` set to a shadow block, timed so that some nodes have the shadow header staged and others do not (a normal condition during shadow-block backfill/sync, or achievable by simply broadcasting the child promptly after the block-commit confirms but before the shadow block has fully propagated). This does not require majority stake, a majority of signers, or any privileged role — a single miner slot suffices, matching the attacker model in scope. I was not able to fully verify, within the available search budget, whether the underlying Bitcoin block-commit validation logic in `leader_block_commit.rs` places any additional constraint on `parent_block_ptr`/`parent_vtxindex` correctness as a precondition for the commit itself to win a sortition; the code excerpt found (`descended_from_anchor`/`maybe_shadow_parent` logic) treats these fields as heuristic/self-declared rather than strictly validated against actual chain history, which suggests such a commit could still win, but this should be double-checked.

### Recommendation
Do not treat "parent header not yet staged" as an implicit pass. Either (a) defer acceptance of a normal block whose parent is unknown until the parent is staged and the shadow-parent check can be run, or (b) re-run `validate_shadow_parent_burnchain` (or an equivalent check) inside `append_block`/`process_next_nakamoto_block` at the point where the parent header is guaranteed to be resolvable, before the block is marked processed and folded into the canonical tip.

### Proof of Concept
Rust integration test plan (two-node/staggered-staging harness):
1. Build a chain up to a shadow tenure `S` and construct a valid `LeaderBlockCommitOp` `C` with `parent_vtxindex = 0` and `parent_block_ptr = S.sortition.block_height` (correct case), then derive a corrupted commit `C'` with `parent_vtxindex = 1` (or `parent_block_ptr = S.sortition.block_height + 1`), following the existing test pattern in `stackslib/src/chainstate/nakamoto/tests/node.rs` lines 2364-2407.
2. Have the sortition process `C'` as the winning commit for the child tenure (or otherwise inject it into `db_handle`).
3. Construct `NakamotoBlock` `child` with `header.parent_block_id` pointing to shadow block `S`.
4. Node A: stage `S`'s header first (`staging_db.store_block_if_better(S, ..)` / `accept_block(S, ..)`), then call `NakamotoChainState::accept_block(child, ..)`. Assert it returns `Err(ChainstateError::InvalidStacksBlock(..))` (equality LHS: rejected).
5. Node B: do NOT stage `S` first; call `NakamotoChainState::accept_block(child, ..)` directly. Assert it returns `Ok(true)` (equality RHS: accepted into staging).
6. Assert `accept(child)_A != accept(child)_B` for identical `child` and `C'`, demonstrating the broken equality `accept(childBlock)_A == accept(childBlock)_B`.
7. (Extended) On Node B, subsequently stage/process `S`, call `process_next_nakamoto_block` and confirm `child` is processed and appended to Node B's canonical chain (`NakamotoChainState::get_canonical_block_header` includes `child.block_id()`), while Node A's staging DB never contains `child` at all — demonstrating the resulting persistent fork.
