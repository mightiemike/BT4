## Finding

### Title
`ensure_match_transaction_info` never verifies `state_checkpoint_hash`, letting replay-verify silently accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole authenticity check used by the `replay_on_archive` db-tool to confirm that locally re-executed transactions match the backed-up/expected `TransactionInfo` (and therefore the historical, signed ledger state). The function checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never compares the `state_checkpoint_hash` field of the two `TransactionInfo`s. This means the one proof field that actually commits to the full accumulated Merkle/state root (and, per the code's own comment, the hot-state and trading-native position-state root) is not verified at all, even though the function is explicitly used as the pass/fail gate for a state-integrity replay tool.

### Finding Description
`ensure_match_transaction_info` performs these checks: [1](#0-0) 

It checks `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`, then returns `Ok(())` without ever reading or comparing `txn_info.state_checkpoint_hash()`: [2](#0-1) 

The comment directly above the `Ok(())` return acknowledges the gap: the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function has a single caller, `storage/db-tool/src/replay_on_archive.rs`, which is the tool operators use to detect divergence between locally re-executed transactions and the trusted, backed-up chain history: [3](#0-2) 

Because `write_set_hash` only commits to the *delta* produced by the current transaction (not the cumulative Jellyfish Merkle root), a bug anywhere upstream that corrupts the running state tree (stale index handling, incorrect prior-version lookup, sharded JMT update bug, etc.) — while still producing an identical delta write-set for the transaction under test — will pass this check even though the actual committed/checkpointed state root has diverged from the correct one. The `state_checkpoint_hash` is precisely the field designed to catch this class of divergence, and it is skipped entirely.

### Impact Explanation
This breaks the core guarantee of `replay_on_archive`: that a clean run proves local execution reproduces the authenticated historical ledger state. A state-root divergence (e.g., from an executor or storage commit bug, or corrupted archive data) can go completely undetected by the tool because the one field binding to the true state commitment (`state_checkpoint_hash`) is never checked. This falls squarely under "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Wrong ... state proof accepted as valid" from the impact gate — operators relying on this tool to detect consensus-breaking non-determinism or DB corruption get a false "all clear."

### Likelihood Explanation
This is not a race condition or attacker-triggered exploit — it is a deterministic, always-present gap in the verification logic that fires on every invocation of `replay_on_archive`. Likelihood of the check being bypassed is 100% whenever a state-root divergence exists without a corresponding write-set-hash divergence; the only variable is whether/when such a state-corrupting bug exists elsewhere in the storage/execution pipeline (e.g., the new native-position/trading-native commit path noted in the comment itself, which is under active development in this fork).

### Recommendation
Add an explicit comparison of `self`'s locally computed state-checkpoint hash (including hot-state and, once available, `position_state_checkpoint_hash`) against `txn_info.state_checkpoint_hash()` inside `ensure_match_transaction_info`, gated appropriately for transactions that carry a checkpoint hash, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or otherwise relying on `replay_on_archive` for state-integrity guarantees.

### Proof of Concept
1. Run `replay_on_archive` over a version range where the local executor's state-value/JMT commit path has a latent bug that does not change the transaction's own write-set bytes (e.g. a stale-index/prior-version bug in `commit_native_position`/`NativeStateCommitter::apply`, or any executor bug that mis-derives the cumulative Merkle root while leaving per-txn deltas identical).
2. Observe `execute_and_verify` calling `ensure_match_transaction_info` per transaction: status, gas, write-set hash, and event hash all match, so `Ok(())` is returned. [4](#0-3) 
3. No comparison of `state_checkpoint_hash` occurs anywhere in the check, so the tool reports zero failed transactions even though the real committed state root differs from the archived/expected one.
