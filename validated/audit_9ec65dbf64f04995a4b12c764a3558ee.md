### Title
Unbounded recursive bytecode-segment hashing in `bytecode_hash_node` may crash the class-compilation process on declare - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
The `bytecode_hash_node` function that computes a declared class's compiled-class hash walks the `NestedIntList` bytecode-segment-structure tree with unbounded plain Rust recursion and no depth check, mirroring the bug class in the OpenAPI.NET advisory (recursive structure walk with no depth guard causing native stack overflow / process termination). This tree is produced by the Sierra→CASM compiler from a class supplied via an ordinary `DECLARE` transaction, and the hash is computed **after** the resource-limited compiler subprocess has already exited, in the unconstrained parent process.

### Finding Description
`SierraCompiler::compile` in `crates/apollo_compile_to_casm/src/lib.rs` first invokes the Sierra→CASM compiler binary through `SierraToCasmCompiler::compile` (`crates/apollo_compile_to_casm/src/compiler.rs:30-55`), which applies CPU-time/memory `ResourceLimits` to the *subprocess* via `compile_with_args` (`crates/apollo_compilation_utils/src/compiler_utils.rs:17-50`). Once the CASM bytes come back over stdout, `SierraCompiler::compile` calls `executable_class.hash(&HashVersion::V2)` directly in its own (unconstrained) process: [1](#0-0) 

`hash()` dispatches to `hash_inner`, which calls `bytecode_hash`, which recurses over the compiler-produced `bytecode_segment_lengths` (a `NestedIntList`) with no depth bound: [2](#0-1) 

Every internal node in this recursion pushes a native Rust stack frame (`iter_children().map(...).collect_vec()` plus the recursive `bytecode_hash_node` call). There is no analog of the `max_recursion_depth`/`RecursionDepthGuard` mechanism used elsewhere in the blockifier for VM call recursion (`crates/blockifier/src/execution/entry_point.rs:706-734`) to bound this tree walk. The tree's shape is derived purely from the compiler's segmentation of the declared Sierra program's control-flow (functions/branches), whose only enforced bound is the overall bytecode size cap (`max_contract_bytecode_size` = 81920, see `gateway_config...max_contract_bytecode_size` in `crates/apollo_node/resources/config_schema.json:3137-3141`). A pathologically structured but small/valid Sierra program (e.g., a long linear chain of nested single-branch functions) can be compiled by the legitimate, resource-limited compiler binary into a CASM artifact whose segment tree is extremely deep and narrow, without the CASM compiler itself needing excessive CPU/memory (so it survives the subprocess resource limits), yet whose subsequent hashing recursion in the parent process consumes stack proportional to that depth.

Because this hashing happens in the class-manager/gateway *parent* process — outside the resource-isolated subprocess boundary that the code comments elsewhere explicitly acknowledge exists for compilation (`crates/blockifier_reexecution/src/compile.rs:73-76`: "unlike the sequencer gateway (which compiles user-submitted classes in a resource-limited subprocess), no process isolation is needed") — a stack overflow here directly aborts the class-manager/gateway process rather than just failing a subprocess.

### Impact Explanation
A stack overflow in Rust aborts the process (no catchable panic), analogous to the referenced advisory's "process termination through public reader APIs." If triggered in the class-manager component handling `add_class` (`crates/apollo_class_manager/src/class_manager.rs:70-113`, called for every declared class), this terminates that sequencer component, halting declare-transaction processing (and, depending on deployment topology, potentially the co-located gateway/mempool components), preventing the network from confirming new declare transactions until the process is restarted — a network-availability impact reachable by a single unprivileged class declarer, consistent with the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Medium-High: the attack requires no special privileges — any account can submit a `DECLARE` transaction with an adversarially structured Sierra program within existing size/step limits. Reaching the specific "very deep, narrow segment tree" shape requires understanding of how `cairo_lang_starknet_classes::CasmContractClass::bytecode_segment_lengths` partitions bytecode (function/branch based), which is public compiler behavior, making the crafting of a proof-of-concept feasible without insider knowledge, though the exact depth needed to overflow the default Rust thread stack (typically 2–8MB) would need empirical tuning against the actual per-frame stack cost of `bytecode_hash_node`.

### Recommendation
- Convert `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` to an explicit iterative/worklist traversal (or use a growable-stack technique) instead of native recursion, removing the unbounded-stack-depth dependency entirely.
- Alternatively/additionally, enforce an explicit maximum nesting depth on `NestedIntList`/`bytecode_segment_lengths` (rejecting or flattening classes that exceed it) before hashing, mirroring the `max_recursion_depth` guard pattern already used for VM call recursion.
- Ensure compiled-class hashing (and any other post-compilation processing of untrusted-derived structures) occurs under the same resource-isolated subprocess/sandbox as the Sierra→CASM compilation step, so a crash there does not take down the parent class-manager/gateway process.

### Proof of Concept
1. Author a Cairo 1 contract whose Sierra program is structured to compile into a deeply, narrowly nested bytecode-segment tree (e.g., many sequentially nested conditional branches/functions), while staying under `max_contract_bytecode_size` (81920) and other gateway stateless limits.
2. Submit it as a `DECLARE` transaction to the gateway.
3. The gateway forwards the class to the class manager, which calls `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60-74`); the resource-limited subprocess successfully compiles it (small program, so within CPU/memory limits) and returns the `CasmContractClass` with a deeply nested `bytecode_segment_lengths`.
4. `executable_class.hash(&HashVersion::V2)` is then called in the parent process, driving `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:111-132`) to recurse to the tree's depth; once depth is sufficient to exhaust the thread's stack, the class-manager/gateway process aborts with a stack overflow.

*Note: I was unable to execute the compiler locally to empirically confirm the exact segment-tree depth achievable within the byte-code size cap versus the default thread stack size; this would need to be validated with a live build (e.g., in a Devin session with the actual `cairo_lang_starknet_classes` compiler) to confirm exploitability before treating this as fully proven.*

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
