### Title
Uncaught TypeError from malformed `URL()` construction in `sanitizeHost` crashes auth/embedded-app-url handlers - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` decodes an attacker-supplied base64 `host` parameter and passes the decoded value directly into `new URL(...)` without a try/catch. A crafted base64 value that decodes to a syntactically invalid URL authority (e.g. an unterminated IPv6-style bracket `[`) causes the `URL` constructor to throw a `TypeError`, which propagates out of `sanitizeHost` as an unhandled exception instead of being converted to a `null`/`InvalidHostError` result.

### Finding Description
`sanitizeHost` only checks that the raw base64 string matches `/^[0-9a-zA-Z+/]+={0,2}$/` [1](#0-0) . This regex validates the *encoded* form, not the decoded content. Once decoded via `decodeHost` (a thin wrapper over `atob`) [2](#0-1) , the resulting string is fed straight into `new URL(`https://${decodeHost(sanitizedHost)}`)` with no surrounding `try/catch`. Any decoded value that the WHATWG URL parser rejects (e.g. `[` — an unterminated IPv6 host literal) throws a `TypeError`, which bubbles out of `sanitizeHost` uncaught.

This function is invoked from multiple auth-adjacent code paths that consume unauthenticated, attacker-controlled `host` query parameters:
- `getEmbeddedAppUrl`/`buildEmbeddedAppUrl`, which read `host` straight from the request URL [3](#0-2) .
- `validateShopAndHostParams` in both shopify-app-remix and shopify-app-react-router, called unconditionally on embedded-admin authentication with no try/catch around `api.utils.sanitizeHost(...)` [4](#0-3) .
- `redirectToShopifyOrAppRoot` in shopify-app-express, an **async** Express handler that calls `api.utils.sanitizeHost(req.query.host as string)!` directly with no try/catch [5](#0-4) . This middleware is invoked as the terminal step of the OAuth callback flow, where the `host` query parameter is not covered by Shopify's OAuth HMAC signature — so it remains fully attacker-controlled even in an otherwise-valid OAuth callback request.

Because a synchronous throw inside an `async` Express handler becomes a rejected `Promise`, and Express 4.x does not automatically forward rejected promises from async handlers to its error-handling middleware, this can manifest as an unhandled promise rejection for that request rather than a clean `4xx` response — a real degradation of the auth completion path. Other call sites (`ensureInstalledOnShop`'s `embedAppIntoShopify`) happen to wrap the resulting `getEmbeddedAppUrl` call in `try/catch`, so they mask the crash into a generic 400, but `redirectToShopifyOrAppRoot` and the remix/react-router `validateShopAndHostParams` have no such protection.

None of the existing checks (`base64regex`, `throwOnInvalid`/`InvalidHostError`, the origin regex test) intercept this case, because the failure happens before any of those checks — inside the `URL` constructor call itself.

### Impact Explanation
This is a denial-of-service in an authentication-adjacent handler: an unauthenticated request with a crafted `host` value can throw an unhandled `TypeError` instead of returning `null`, breaking the intended fail-safe contract of `sanitizeHost` and causing an uncaught exception / unhandled promise rejection in the OAuth completion and embedded-URL-building code paths (`redirectToShopifyOrAppRoot`, `validateShopAndHostParams`). This matches Shopify's "denial of service in authentication flow" bounty class. It does not expose secrets or allow session/token forgery — the impact is limited to crashing/erroring the specific request-handling path, and depending on the host application's process-level `unhandledRejection` handling, session cleanup or the server itself.

### Likelihood Explanation
Trivial to trigger: no authentication, secret, or special role is required. An anonymous attacker can send a single HTTP request with a crafted `host` query parameter (e.g. during the OAuth callback, where `host` is not HMAC-protected) or hit `getEmbeddedAppUrl`/`redirectToShopifyOrAppRoot` directly with `host=` set to `Buffer.from('[').toString('base64')`. It is fully repeatable and requires no non-default configuration.

### Recommendation
Wrap the `new URL(...)` construction in `sanitizeHost` in a `try/catch`, treating any thrown error the same as an invalid host (return `null`, or throw `InvalidHostError` if `throwOnInvalid` is set), e.g.:
```ts
let hostname: string;
try {
  ({hostname} = new URL(`https://${decodeHost(sanitizedHost)}`));
} catch {
  sanitizedHost = null;
}
```

```ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost throws instead of returning null for malformed decoded host', () => {
  const shopify = shopifyApi(testConfig());
  const malformedBase64Host = Buffer.from('[').toString('base64'); // decodes to "["

  // Expected (per contract): should return null.
  // Actual: throws an uncaught TypeError from `new URL()`.
  expect(() => shopify.utils.sanitizeHost(malformedBase64Host)).toThrow();
});
```
Request-level equivalent: `GET /auth/callback?shop=test.myshopify.com&host=Ww%3D%3D&hmac=<valid>&timestamp=<valid>&code=<valid>` — after HMAC validation passes (host isn't part of the signed payload), `redirectToShopifyOrAppRoot` calls `sanitizeHost('Ww==')`, which decodes to `[` and throws inside the async handler.
