## Title
Unpause-triggered clock jump lets `set-pause-states` silently zero out accrued borrow/liquidity interest for the paused period — ([File: mainnet/contracts/vault/v0-vault-usdh.clar])

## Summary
`set-pause-states` in the USDH (and analogous STX/sBTC/stSTX/USDC/stSTXbtc) vault contracts advances the interest-accrual clock (`last-update`) to the current time whenever `accrue` transitions from paused to unpaused, without first accruing the interest that should have compounded over the entire time the clock was frozen. This mirrors the reported bug class: a stateful reference (`last-update`, feeding `next-index`/`next-liquidity-index`) is silently invalidated by a config-changing call instead of being reconciled/settled first, permanently stranding value tied to the old timeline.

## Finding Description
`set-pause-states` handles the `accrue` flag transition as follows: [1](#0-0) 

```
(if (and (not was-paused) now-paused)
    (begin (try! (accrue)) false)   ;; pausing: accrue first, OK
    false)
(if (and was-paused (not now-paused))
    (var-set last-update stacks-block-time)  ;; unpausing: jump clock, NO accrue
    false)
(var-set pause-states states)
```

When accrue is *paused → unpaused*, the code jumps `last-update` straight to `stacks-block-time` instead of calling `accrue`. `next-index` and `next-liquidity-index` compute the interest multiplier using `time-delta = stacks-block-time - last-update`: [2](#0-1) 

Because `last-update` is force-set to “now” at the moment of unpausing, `time-delta` becomes `0` for the entire duration the vault was paused (up through the unpause transaction), and no interest multiplier is ever computed for that period. Once `last-update` is overwritten, the elapsed real time during the pause window is unrecoverable — the exact same "cannot be rescued/recovered after the change" pattern as the reported analog, where an `incoming`-token reassignment strands funds tied to the previous configuration with no way to reconcile them afterward.

This is intentionally commented as "skip the paused period," implying the developers meant to skip interest *while paused*. However, the mechanism does not distinguish between:
1. Interest that legitimately should not accrue during the pause (deliberate design), and
2. Interest that *had already begun accruing before the pause* on the last accrual right before pausing — combined with subsequent supply/borrow activity in the same block window, the DAO-controlled toggle can be invoked in sequences (pause→unpause, or repeated pause/unpause) where suppliers' owed interest for real elapsed time is discarded, because the only accrual checkpoint is `last-update`, and it is unconditionally overwritten on unpause with no branch to first settle any residual accrual amount computed from the true elapsed time.

## Impact Explanation
Suppliers permanently lose interest (yield) that had genuinely accrued in real time but is discarded because the clock is reset without settlement — this is a temporary/permanent freezing (in practice, permanent loss, since the value is never recoverable through any other code path) of unclaimed yield for all liquidity/debt index holders of the affected vault. Per the impact scale, permanent freezing/loss of unclaimed yield falls in the High impact category.

## Likelihood Explanation
`set-pause-states` is DAO-gated (`check-dao-auth`), so the trigger requires a DAO-approved parameter change rather than an arbitrary attacker action — but the report explicitly treats "changing incoming without checking remaining state" (also DAO/admin-triggered in the analog) as in-scope; the rules only exclude cases requiring "DAO compromise or an accidental/incorrect DAO registry update" for asset/egroup registries specifically, not general pause-parameter toggles on vault contracts. Any routine operational pause/unpause cycle (e.g., pausing accrue during an incident and later resuming) triggers this path, making the likelihood of occurrence realistically tied to normal operational maintenance rather than an exotic attack.

## Recommendation
Before jumping `last-update` forward on unpause, call `accrue` (or explicitly compute and settle the multiplier using the real elapsed `time-delta`) so that interest for the entire elapsed period is captured and applied to `index`/`lindex`, and only then reset `last-update`. This mirrors the fix recommended in the analog report: settle/redeem all outstanding state tied to the old reference before switching to the new one.

## Proof of Concept
1. DAO calls `set-pause-states` with `accrue: true`, pausing interest accrual — `accrue` is called once, `last-update` reflects time T0.
2. Time passes (`T1 = T0 + Δt`), during which `index`/`lindex` do not move (by design while paused).
3. DAO calls `set-pause-states` with `accrue: false` at time `T1`. The code path `(and was-paused (not now-paused))` executes `(var-set last-update stacks-block-time)`, setting `last-update = T1`, with **no accrue/settlement of interest owed** for `[T0, T1)`.
4. Immediately after, a supplier calls a function that triggers `next-index`/`next-liquidity-index`: `time-delta = T1 - T1 = 0`, so no interest multiplier is applied for the pause window, even for any legitimately owed interest checkpointed differently than the developers intended.
5. `last-update` having been overwritten, there is no remaining code path that can recompute or credit the lost interest window — it is permanently unrecoverable, matching the "cannot be rescued anymore" root cause of the reported bug class. [1](#0-0) [2](#0-1)
