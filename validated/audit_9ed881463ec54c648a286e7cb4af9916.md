### Title
Floating-point division/multiplication truncation in standby-witness and brokerage reward distribution causes systematic reward under-payment - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payStandbyWitness()` and its sibling implementation `IncentiveManager.reward()` compute each standby witness's share of the fixed per-block reward pool by dividing the total pay by the total vote sum and then multiplying by each witness's individual vote count, using Java `double` arithmetic and truncating to `long`. The same truncation pattern is used in `payReward()` for the SR brokerage split. This mirrors the reported `GammaRewarder.createDistribution` bug class: dividing an amount to distribute by a denominator (vote sum / 100) and truncating per-recipient, so the sum of amounts actually paid out is systematically less than the intended total, with the shortfall silently lost every block/cycle.

### Finding Description
In `payStandbyWitness()`: [1](#0-0) 

`eachVotePay = (double) totalPay / voteSum` is computed once, then for each of up to 127 standby witnesses `pay = (long) (w.getVoteCount() * eachVotePay)` truncates the fractional part independently for every witness. The equivalent logic exists in the older code path: [2](#0-1) 

and the brokerage split in `payReward()`: [3](#0-2) 

`brokerageRate = (double) brokerage / 100` followed by `(long)(brokerageRate * value)` truncates the fee split between the SR's own allowance and the reward pool credited to voters — exactly the "divide, then truncate per recipient" pattern described in the report (there, `amountPerEpoch = realAmountToDistribute / numberOfEpochs`, truncated once per epoch).

This is functionally reachable every single block via the block-reward pipeline: [4](#0-3) 

`payReward()` is invoked once per produced block, calling `mortgageService.payBlockReward(...)` and `mortgageService.payStandbyWitness()` unconditionally, so the truncation occurs on every block for up to 127 witnesses simultaneously — no privileged actor, malicious peer, or special transaction is required; it is a structural property of the protocol's block-closing logic.

Note that java-tron's *newer* delta-VI reward algorithm (`RewardViCalService`, `DelegationStore.accumulateWitnessVi`, `VoteRewardUtil.computeReward`) already applies the report's own recommended mitigation — scaling with `DECIMAL_OF_VI_REWARD` via `BigInteger` multiply-then-divide before truncating once at the end: [5](#0-4) 
This confirms the project is aware of, and has already fixed, this exact bug class in one code path (per-voter reward accrual) but the standby-witness payout and brokerage-split paths were never migrated to the same fixed-point approach and remain vulnerable to the identical precision-loss pattern.

### Impact Explanation
Each block, the sum of `pay` values distributed to the up to 127 standby witnesses in `payStandbyWitness()` is strictly ≤ `totalPay` due to per-witness truncation, and the residual (up to ~1 unit per witness, i.e. up to ~127 sun per block) is neither paid nor accounted anywhere — it is simply lost from the intended reward distribution. Over the lifetime of the chain (blocks every 3 seconds), this compounds into a persistent, protocol-wide accounting discrepancy in witness/voter compensation, matching the reported impact of "small amounts unrewarded over time" and "cumulative precision loss" in the source report. The brokerage double-multiplication in `payReward()` similarly causes small, systematic misallocation between an SR's own allowance and the reward pool shared with its voters on every block/transaction-fee reward event.

### Likelihood Explanation
This occurs unconditionally on every produced block as long as `allowChangeDelegation()` is enabled (the standard reward-distribution mode on mainnet), with no attacker action, special transaction, or privileged role needed — it is a deterministic arithmetic side effect of normal consensus operation, giving it very high likelihood of occurring continuously.

### Recommendation
Replace the `double`-based proportional split in `MortgageService.payStandbyWitness()`, `IncentiveManager.reward()`, and the brokerage computation in `MortgageService.payReward()` with integer/`BigInteger` fixed-point arithmetic that multiplies before dividing (as already done for `DECIMAL_OF_VI_REWARD` in `DelegationStore.accumulateWitnessVi`), and explicitly track/redistribute (or burn deterministically) any remainder so the total distributed always equals the intended `totalPay`/`value`, rather than allowing per-recipient truncation to silently shrink the aggregate payout.

### Proof of Concept
Given `voteSum = 2,700,000,001` (127 witnesses each with ~21,259,842 votes plus 1 extra vote) and `totalPay = getWitness127PayPerBlock()` (e.g. 16,000,000 sun):
1. `eachVotePay = (double) 16000000 / 2700000001 ≈ 5.925925925×10⁻³`
2. For each witness, `pay = (long)(voteCount * eachVotePay)` truncates independently; summing all 127 truncated `pay` values yields a total strictly less than `16000000` sun.
3. The shortfall (typically tens to over a hundred sun per block) is never credited to any account and is lost every block, indefinitely — directly analogous to the `amountPerEpoch` truncation loss demonstrated in the original report's Hardhat PoC. [6](#0-5)

    }

      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);
      consensusDelegate.saveAccount(accountCapsule);
    }
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
