### Title
Malicious tip value causes an unhandled arithmetic-overflow panic in `GasVector::cost`, crashing per-transaction fee computation and halting a concurrent block-building worker for all users - (File: crates/starknet_api/src/execution_resources.rs)

### Summary
`GasVector::cost` combines the block's L2 gas price with the transaction-supplied `tip` and then multiplies/sums per-resource costs, explicitly `panic!`-ing on any `checked_add`/`checked_mul` overflow instead of returning an error. `tip` is a value fully controlled by the transaction sender (part of every V3 transaction's resource-bounds fields) and is not bounded to values that are provably safe against overflow before reaching this fee-computation code. Because this function executes as part of per-transaction fee charging inside the blockifier, a single crafted transaction can trigger the panic during block building.

### Finding Description
`GasVector::cost` adds the transaction's `tip` to the block's L2 gas price and then performs `checked_mul`/`checked_add` on gas amounts and prices, calling `.unwrap_or_else(|| panic!(...))` on failure rather than propagating a typed error: [1](#0-0) 

`tip` originates directly from the submitted transaction's resource bounds and is attacker controlled; there is no evidence in the codebase of a hard upper bound on `tip` enforced prior to this computation that would make the `checked_add`/`checked_mul` overflow provably unreachable (my search for `MAX_TIP`/tip-bounding validation logic found no such check).

This fee computation is invoked from the per-transaction execution/fee-charging path in the blockifier (`crates/blockifier/src/fee/fee_utils.rs`), which runs inside the sequencer's block-building flow — either the sequential executor (`execute_txs_sequentially_inner` in `crates/blockifier/src/blockifier/transaction_executor.rs`) or, in production, inside a `WorkerExecutor` running on a dedicated OS thread managed by `WorkerPool`: [2](#0-1) 

If the panic occurs inside a worker thread, `catch_unwind` marks `a_thread_panicked` and calls `panic::resume_unwind`, which re-triggers the panic outside the `catch_unwind` boundary of that same call chain, and any panic detected via `check_panic()` causes `WorkerPool::run_and_wait` to panic again on the calling (block-builder) thread: [3](#0-2) 

Because a single transaction's fee computation can panic, and that panic is deliberately propagated/aborted rather than turned into a rejectable, isolated transaction-execution error, the failure is not contained to the single malicious transaction — it terminates the batching/proposal task (or the whole worker pool) that is processing the entire block of transactions from all users, analogous to how a single malicious reward token's failing transfer call in `MultiRewards.getRewardForUser` DoSes reward claims for every user sharing that vault's reward-token loop.

### Impact Explanation
If reachable, this crashes the proposer's/validator's active block-building session, discarding in-progress execution of every other transaction in that block/chunk and forcing the node to abort and restart block building — a network-unable-to-confirm-new-transactions condition for the affected round, analogous to the "High" impact rated in the reference report (DoS of the shared batch process for all users, not just the attacker).

### Likelihood Explanation
Uncertain/Low-Medium. The concrete overflow requires the sender to select `tip` and/or resource-bound `max_price_per_unit`/`max_amount` values whose combination with the current block's L2 gas price exceeds `u128`/underlying type bounds in `checked_add`/`checked_mul`. I was not able to confirm from the indexed code whether earlier validation (e.g., in the gateway or `TransactionPreValidationError`/resource-bounds checks) already rejects such extreme values before this function is reached, nor could I fully trace every fee-charging call path (pre-execution vs. post-execution `cost()` invocations) within the tool budget available. This is a hint, not a proven exploit chain — dedicated verification of the actual numeric ranges enforced upstream (RPC/gateway resource-bounds validation, `starknet_api` type bit-widths for `Tip`/`GasPrice`) is required to confirm reachability.

### Recommendation
- Replace the `panic!`-on-overflow behavior in `GasVector::cost` (and any similar `unwrap_or_else(|| panic!(...))` fee/gas arithmetic in the codebase) with a typed, recoverable error that causes only the offending transaction to be rejected/excluded from the block, not a process/thread panic.
- Enforce explicit upper bounds on `tip` and resource-bounds `max_price_per_unit`/`max_amount` during transaction validation (gateway/mempool ingestion) sufficient to make the downstream arithmetic overflow-free by construction.
- Audit all `checked_add`/`checked_mul` `.unwrap_or_else(|| panic!(...))` patterns reachable from per-transaction, attacker-supplied fields in the blockifier and `starknet_api` fee/gas modules for the same class of issue.

### Proof of Concept
Not independently constructed/verified — I could not confirm, within available tool calls, the concrete upstream bounds on `Tip`/`GasPrice`/`max_amount` types that would determine whether an attacker can actually supply values producing an overflow before this code path is reached. A full PoC requires: (1) confirming `Tip`'s and `GasPrice`'s underlying integer widths and any pre-execution bounds checks in `starknet_api::transaction::fields`, and (2) submitting/simulating a V3 invoke transaction with `tip` and/or resource bounds chosen so `gas_prices.l2_gas_price.checked_add(tip.into())`, `gas.checked_mul(price.get())`, or the final `sum.checked_add(cost)` in `GasVector::cost` overflows, then observing whether the panic reaches an unguarded block-building path.

    /// Computes the cost (in fee token units) of the gas vector (panicking on overflow).
    pub fn cost(&self, gas_prices: &GasPriceVector, tip: Tip) -> Fee {
        let tipped_l2_gas_price =
            gas_prices.l2_gas_price.checked_add(tip.into()).unwrap_or_else(|| {
                panic!(
                    "Tip overflowed: addition of L2 gas price ({}) and tip ({}) resulted in \
                     overflow.",
                    gas_prices.l2_gas_price, tip
                )
            });

        let mut sum = Fee(0);
        for (gas, price, resource) in [
            (self.l1_gas, gas_prices.l1_gas_price, Resource::L1Gas),
            (self.l1_data_gas, gas_prices.l1_data_gas_price, Resource::L1DataGas),
            (self.l2_gas, tipped_l2_gas_price, Resource::L2Gas),
        ] {
            let cost = gas.checked_mul(price.get()).unwrap_or_else(|| {
                panic!(
                    "{resource} cost overflowed: multiplication of gas amount ({gas}) by price \
                     per unit ({price}) resulted in overflow."
                )
            });
            sum = sum.checked_add(cost).unwrap_or_else(|| {
                panic!(
                    "Total cost overflowed: addition of current sum ({sum}) and cost of \
                     {resource} ({cost}) resulted in overflow."
                )
            });
        }
        sum
    }

    pub fn run_and_wait(&self, worker_executor: Arc<WorkerExecutor<S>>, target_n_txs: TxIndex) {
        self.run(worker_executor.clone());

        worker_executor.scheduler.wait_for_completion(target_n_txs);

        // Halt the scheduler to allow future blocks to start.
        // This is required since `wait_for_completion` can exit before the scheduler is done.
        worker_executor.scheduler.halt();

        self.check_panic();
    }

    pub fn check_panic(&self) {

            panic!("One of the threads panicked.");
        }
    }

    fn _run_executor(&self, worker_executor: &WorkerExecutor<S>) {
        if self.a_thread_panicked.load(Ordering::Acquire) {
            panic!("Another thread panicked. Aborting.");
        }

        // Making sure that the program will abort if a panic occurred while halting
        // the scheduler.
        let abort_guard = AbortIfPanic;
        // If a panic is not handled or the handling logic itself panics, then we
        // abort the program.
        let res = panic::catch_unwind(panic::AssertUnwindSafe(|| {
            worker_executor.run();
        }));
        if let Err(err) = res {
            // First, set the panic flag. This must be done before halting the scheduler.
            self.a_thread_panicked.store(true, Ordering::Release);

            // If the program panics here, the abort guard will exit the program.
            // In this case, no panic message will be logged. Add the cargo flag
            // --nocapture to log the panic message.

            worker_executor.scheduler.halt();
            abort_guard.release();
            panic::resume_unwind(err);
        }

        abort_guard.release();
    }
