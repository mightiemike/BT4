## Finding

### Title
Inbound event parser trusts the raw `amount` word from source-chain gateway logs as 1:1 backing for PRC20 minting, with no verification against tokens actually received by the vault — ([File: universalClient/chains/evm/event_parser.go])

### Summary
Push Chain's PRC20 minting pipeline assumes that the `amount` field emitted in a source-chain gateway/vault deposit event is exactly equal to the quantity of the underlying asset that was actually locked in the vault. This mirrors the VoterProxy bug: the code assumes a rigid 1-1 relationship between an externally reported quantity and the real backing asset held, without ever independently confirming it. For any enabled token whose observed transfer amount can diverge from the amount actually received/held by the vault (fee-on-transfer, deflationary, or otherwise non-standard ERC20 semantics), the PRC20 supply minted on Push Chain will exceed the real collateral backing it.

### Finding Description
`parseUniversalTxEvent` decodes the deposit `amount` directly as the second 32-byte word of the raw log data, with no cross-check against actual balances: [1](#0-0) 

That value flows unchanged into the `Inbound.Amount` field: [2](#0-1) 

Validators vote on this `Inbound` and, once quorum is reached, the amount is used verbatim to mint PRC20 via `depositPRC20` → `CallPRC20Deposit`, again with no check against the real token balance actually escrowed by the vault contract on the source chain: [3](#0-2) [4](#0-3) 

The system's PRC20 accounting model implicitly assumes a strict 1:1 correspondence between "amount transferred out of the depositor" (the value the gateway/vault event reports) and "amount actually retained by the vault as backing" — exactly the assumption the cited report calls out as unsafe. If any token enabled via `TokenConfig` (e.g. a fee-on-transfer, rebasing, or otherwise non-standard ERC20) is deposited, the vault on the source chain may retain less than the reported amount, yet Push Chain will still mint the full reported amount of PRC20 into the recipient's UEA/EOA/contract.

### Impact Explanation
If the reported/deposited amount and the amount actually escrowed diverge, PRC20 total supply becomes under-collateralized relative to the vault's true holdings. This is a protocol-level accounting corruption: later legitimate outbound/redemption flows against that vault can fail or drain remaining collateral disproportionately, resulting in unauthorized mint of PRC20 not backed by real value and eventual fund loss for other holders of that PRC20 — matching the in-scope impact "corruption of PRC20 or native asset accounting" and "unauthorized mint."

### Likelihood Explanation
This is contingent on governance enabling a token via `TokenConfig` whose transfer semantics are non-standard (fee-on-transfer/rebasing/deflationary) — similar to how the original finding was judged Medium severity specifically because it depended on the sponsor integrating with a protocol (Angle) that used rebasing gauge tokens. Any unprivileged user can then trigger the divergence simply by depositing that token through the normal gateway `sendFunds` path; no privileged access is required once such a token is enabled. Likelihood is Medium: it requires only an ordinary token configuration decision plus a normal user deposit, not a compromise of validators or infrastructure.

### Recommendation
Do not trust the gateway/vault event's `amount` word as authoritative for minting. Either:
- Have the vault contract compute and emit the actual balance delta it observed (before/after transfer) rather than the caller-supplied transfer amount, or
- Have `parseUniversalTxEvent` / the executor reconcile the reported amount against an independently observable balance-change signal before minting PRC20 1:1, or
- Restrict `TokenConfig` registration to tokens verified to have standard, non-fee, non-rebasing transfer semantics, and document/enforce this as an invariant checked at registration time.

### Proof of Concept
1. Governance enables a `TokenConfig` for an ERC20 token that charges a transfer fee (or is otherwise non-standard) on the relevant source chain.
2. An unprivileged user calls the gateway's deposit method with amount `X`; the vault contract actually receives `X - fee` due to the token's fee-on-transfer logic, but the emitted deposit event still encodes `X` in the amount word (as read from `log.Data[32:64]` in `parseUniversalTxEvent`).
3. Push Chain validators observe the event, and `constructInbound` sets `Inbound.Amount = X`.
4. After quorum, `depositPRC20`/`CallPRC20Deposit` mints `X` PRC20 to the recipient — exceeding the `X - fee` actually held by the vault.
5. Repeating deposits of this token systematically under-collateralizes the PRC20, letting subsequent redeemers drain the vault and leaving later holders unable to redeem their full balance.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
