### Title
Precision loss in old vote-reward computation causes rounding-down accumulation, underpaying voters - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The `computeReward(long cycle, List<Pair<byte[], Long>> votes)` method in `MortgageService` computes a voter's per-cycle share of a witness's total reward by first performing a floating-point division (`userVote / totalVote`) and then multiplying by `totalReward`, storing the truncated result into an accumulator (`reward += ...`) across potentially many cycles. This mirrors the reported Move `record_redistribution` bug pattern: dividing before multiplying/accumulating causes systematic rounding-down loss that compounds across iterations.

### Finding Description
`computeReward` for the legacy ("old") reward algorithm is: [1](#0-0) 

```
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```

This is invoked once per cycle inside `getOldReward`, which loops over every cycle between `begin` and `end` and sums the results into a single `long reward` accumulator: [2](#0-1) 

Because the division `userVote / totalVote` is computed as a `double` before multiplying by `totalReward`, and the final result is truncated to a `long` on each accumulation step (via `(long)` cast on `reward +=`, since `reward` is declared `long` and the RHS is `double`), any fractional TRX/vote-reward smaller than the rounding threshold is lost every cycle. Over many cycles (`for (long cycle = begin; cycle < end; cycle++)`), these per-cycle rounding losses compound, exactly analogous to the reported bug where `reward_per_unit_stake` accumulates truncated division results instead of using a fixed-point scaling factor.

Note that java-tron's engineers already recognized and partially fixed this exact class of bug: the newer VI-based algorithm (`RewardViCalService.accumulateWitnessVi` / `DelegationStore.accumulateWitnessVi`) multiplies by a `DECIMAL_OF_VI_REWARD` scaling constant (`10^18`) *before* dividing, specifically to avoid precision loss in the accumulator: [3](#0-2) 

However, the legacy `computeReward(cycle, votes)` / `getOldReward` path — which is still reachable for any cycle prior to `newRewardAlgorithmEffectiveCycle`, or whenever `allowOldRewardOpt` is not enabled — retains the unscaled double-division-then-accumulate pattern: [4](#0-3) 

The same unscaled-division pattern also appears in standby-witness payout and DPoS incentive payout, which are single-shot (not accumulated over many cycles) but still exhibit the same underlying rounding-down defect: [5](#0-4) [6](#0-5) 

### Impact Explanation
Voters using the legacy reward path receive systematically underpaid rewards due to floating-point truncation on every cycle's computation, with losses compounding as more cycles are processed. The "lost" fractional reward is not accounted for anywhere (not carried forward, not redistributed) — it is silently dropped from the total reward pool, i.e., the sum of paid-out voter rewards will not equal the total reward recorded per witness (`delegationStore.getReward`). This is a real accounting divergence: reported witness rewards vs. actually claimable voter rewards diverge over time, an underpriced/inaccurate settlement of funds. However, the code path is largely legacy/pre-`allowChangeDelegation`/`allowOldRewardOpt` — on networks where the new VI algorithm is active for all relevant cycles, this old path is not exercised for those cycles. The IncentiveManager/standby-witness cases have marginal impact since losses don't compound across cycles for the same accumulator.

### Likelihood Explanation
This code executes automatically for any account withdrawing/querying rewards accrued during cycles prior to `newRewardAlgorithmEffectiveCycle`, or when `allowOldRewardOpt` is disabled — no special privileges are required; it is triggered by ordinary voters/unprivileged users calling reward withdrawal/query flows (`withdrawReward`/`queryReward` in `MortgageService` and `VoteRewardUtil`). On networks that have long since transitioned to the new algorithm and enabled `allowOldRewardOpt`, exposure is limited to historical cycles already computed. Likelihood is therefore network/configuration-dependent but concretely reachable.

### Recommendation
Replace the double-based division-then-multiply pattern in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` with a fixed-point/`BigInteger` computation that multiplies before dividing (e.g., `BigInteger.valueOf(totalReward).multiply(BigInteger.valueOf(userVote)).divide(BigInteger.valueOf(totalVote))`), consistent with the approach already used in the new VI algorithm, to eliminate rounding-down accumulation. Apply the same multiply-before-divide fix to `MortgageService.payStandbyWitness` and `IncentiveManager.reward`.

### Proof of Concept
Given `totalVote = 3`, `userVote = 1`, `totalReward = 100` repeated across many cycles:
- `voteRate = (double) 1 / 3 = 0.3333...`
- `reward += voteRate * 100 = 33.33...` → truncated to `33` per cycle (since `reward` is `long`).
- The true proportional share is `33.33` per cycle; over 1,000 cycles the voter should receive `33333` but the accumulator only records `33000`, a compounding loss of `333` units purely from repeated floating-point truncation before accumulation — mirroring the reported `record_redistribution` bug where `collateral_amount / total_stake` is added directly to `reward_per_unit_stake` without a scaling factor.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
