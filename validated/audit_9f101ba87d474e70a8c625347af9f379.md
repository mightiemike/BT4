### Title
Deploy syscall `deploy_from_zero` mode allows deterministic contract addresses to be front-run and permanently squatted - (File: `crates/blockifier/src/execution/syscalls/syscall_base.rs`)

### Summary
When a contract invokes the `deploy` syscall with `deploy_from_zero=true`, the resulting contract address is derived solely from `(salt, class_hash, constructor_calldata)` — the caller/deployer identity is excluded from the address computation. Any unprivileged transaction sender who observes a pending deploy call in the mempool can compute the identical target address and submit a competing transaction that reaches the sequencer first, permanently occupying that address with contract state of the attacker's choosing.

### Finding Description
The `deploy` syscall handler sets `deployer_address_for_calculation` to `ContractAddress::default()` (zero) whenever `deploy_from_zero` is `true`, before calling `calculate_contract_address`: [1](#0-0) 

`calculate_contract_address` hashes only the prefix, deployer address, salt, class hash, and constructor calldata hash — with the deployer forced to zero, the resulting address depends purely on publicly-known, attacker-computable values (`salt`, `class_hash`, `constructor_calldata`): [2](#0-1) 

Once a transaction targeting this address is visible (e.g., pending in the mempool/gateway before block inclusion), any other party can construct their own invoke transaction that calls a `deploy` syscall with the same `salt`, `class_hash`, and `constructor_calldata` (all of which are public in the observed pending transaction) but from a different caller contract, computing the exact same target address. Because contract addresses can only be initialized once, `execute_deployment` rejects any deployment to an address whose class hash is already non-default, returning `UnavailableContractAddress`: [3](#0-2) 

Whichever transaction the sequencer executes first "wins" the address permanently; this is confirmed by existing test coverage showing repeated deployment to the same address fails deterministically: [4](#0-3) 

This mirrors the `registerCode` frontrunning pattern in the reported bug class: a resource that should belong to the original submitter (a specific contract address, analogous to a referral code) can instead be permanently claimed by a third party who races ahead of the legitimate transaction, since the underlying identifier (address / code string) does not bind to the original claimant's identity at computation time.

### Impact Explanation
An attacker can permanently deny a target contract address to its intended owner by deploying arbitrary (e.g., empty or malicious) contract code to that address first. The victim's transaction reverts with `UnavailableContractAddress`, the victim loses the fees paid for the failed transaction, and the intended contract can never be deployed to that specific address again (contract addresses are one-time-use). This is a permanent denial-of-service on a specific deployment target and a loss of transaction fees for the victim, particularly damaging for factory/UDC-style deployment patterns that rely on `deploy_from_zero=true` for deterministic, deployer-independent addresses.

### Likelihood Explanation
Exploitation only requires observing a pending transaction containing a `deploy_from_zero=true` call (visible pre-confirmation via mempool/gateway) and racing it with a higher-fee competing transaction — a standard front-running capability available to any unprivileged network participant. No special privileges are required, making this reachable purely from a submitted transaction.

### Recommendation
Discourage or restrict `deploy_from_zero=true` usage for cases where address exclusivity matters, or document clearly that addresses computed this way are inherently squattable (as done for CREATE2-style deployments on other chains). Applications requiring deployer-exclusive addresses should incorporate the deployer's address or another caller-bound secret into the salt (i.e., use `deploy_from_zero=false`), and factory contracts (e.g., UDC-style) should default to unique, deployer-bound salts rather than relying on the raw zero-deployer address scheme.

### Proof of Concept
1. Alice submits an invoke transaction that internally calls the `deploy` syscall with `deploy_from_zero=true`, `class_hash=H`, `salt=S`, `constructor_calldata=C`, intending to deploy her contract to address `A = hash(0, S, H, hash(C))`.
2. Bob observes Alice's pending transaction in the mempool (values `H`, `S`, `C` are all visible in the calldata).
3. Bob submits his own invoke transaction from a different contract, also calling `deploy` with `deploy_from_zero=true` and the identical `S`, `H`, `C`, but with higher fee/tip so it is included first.
4. The sequencer executes Bob's transaction first: `execute_deployment` in [3](#0-2)  sets the class hash at address `A`.
5. Alice's transaction now executes the same `deploy` syscall targeting the already-occupied address `A`; `execute_deployment` returns `StateError::UnavailableContractAddress(A)`, causing Alice's transaction (or the calling contract's execution) to fail permanently for that address, exactly as exercised in the existing test `to_unavailable_address`: [4](#0-3) .

pub fn calculate_contract_address(
    salt: ContractAddressSalt,
    class_hash: ClassHash,
    constructor_calldata: &Calldata,
    deployer_address: ContractAddress,
) -> Result<ContractAddress, StarknetApiError> {
    let constructor_calldata_hash = Pedersen::hash_array(&constructor_calldata.0);
    let contract_address_prefix = format!("0x{}", hex::encode(CONTRACT_ADDRESS_PREFIX));
    let address = Pedersen::hash_array(&[
        Felt::from_hex(contract_address_prefix.as_str()).map_err(|_| {
            StarknetApiError::OutOfRange { string: contract_address_prefix.clone() }
        })?,
        *deployer_address.0.key(),
        salt.0,
        class_hash.0,
        constructor_calldata_hash,
    ]);
    let (_, address) = address.div_rem(&L2_ADDRESS_UPPER_BOUND);

    ContractAddress::try_from(address)
}
