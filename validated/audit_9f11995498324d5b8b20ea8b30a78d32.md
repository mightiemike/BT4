### Title
Bootstrap declare fast-path allows free class declaration if `charge_fee` is ever false for a user-submitted transaction - (File: `crates/blockifier/src/transaction/account_transaction.rs`)

### Summary
`is_bootstrap_declare` gates a "no-validation, no-fee, no-nonce-check" declare fast-path solely on `sender_address == bootstrap_address()` (a hardcoded, publicly-known constant, the felt encoding of `'BOOTSTRAP'`), `nonce == 0`, and the caller-supplied `charge_fee` execution flag — not on any chain-state condition (e.g. "no blocks exist yet" / genesis-only). Any transaction whose `sender_address` field is set to this constant is fully attacker-controlled, since declare-transaction sender addresses are not cryptographically bound to a deployed account the way invoke/deploy-account addresses are.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` [1](#0-0)  returns true whenever `sender_address == bootstrap_address()` and `nonce == 0` and `!charge_fee`. `bootstrap_address()` is a fixed constant known to anyone reading the code (`0x424f4f545354524150`, i.e. `'BOOTSTRAP'`) [2](#0-1) .

This flag is consumed in `AccountTransaction::execute_raw`, which — if `is_bootstrap_declare` is true — skips `perform_pre_validation_stage` (nonce check, fee-bounds check, balance check), skips the `__validate_declare__` entry point call, skips fee charging, and directly writes the declared class into `contract_class_changes`, returning a default `TransactionExecutionInfo` [3](#0-2) . The equivalent Starknet-OS Cairo path performs the identical unconditional bypass keyed only on `sender_address == 'BOOTSTRAP' and tx_info.nonce == 0 and tx_info.version == 3` plus `max_possible_fee == 0` [4](#0-3) .

Critically, the gate is not conditioned on any chain/state predicate such as "block number 0" or "no prior blocks" — it is conditioned purely on the `charge_fee` boolean, which is a property of the *execution context* the caller passes in, not an inherent, unforgeable property of the transaction or of chain state. The gateway-side "genesis-only" state readers (`GenesisStateReader`/`GenesisFixedBlockStateReader`) are explicitly only used "when no blocks exist yet" [5](#0-4) , suggesting the *intended* restriction is "genesis only," but that restriction is not enforced by `is_bootstrap_declare` itself — it is enforced only incidentally, by whatever caller decides to set `charge_fee=false`. This is directly analogous to the CVE-2020-15130 pattern: a consensus-relevant invariant ("only the legitimate genesis bootstrap process may declare via this path") is supposed to be enforced by validating a specific precondition (there, "burn the required NFT1 Group input"; here, "this is truly a genesis-time system bootstrap"), but the actual code checks a much weaker, spoofable/misconfigurable condition (an execution flag) instead of the real invariant, yielding a false-positive validation outcome that lets an unprivileged party mint/declare something they should not be able to.

### Impact Explanation
If any code path in block-building/validation ever executes a normal, attacker-supplied declare transaction with `charge_fee=false` (whether through a batcher/gateway misconfiguration, a future feature reusing the `charge_fee` flag for legitimate reasons such as fee-abstraction or subsidized transactions, or an operational mode where fee-charging is disabled for non-bootstrap reasons), an attacker who simply sets `sender_address = bootstrap_address()` and `nonce = 0` in a declare transaction can:
- Declare an arbitrary class with **no signature verification** (`__validate_declare__` is never called),
- Pay **zero fee** regardless of resource bounds submitted, since fee-bounds/balance checks (`perform_pre_validation_stage`) are entirely skipped,
- Do so **repeatedly without nonce consumption**, since the nonce is never incremented for this path (confirmed by the comment: "the transaction remains in the mempool... will propose the same transaction again" [6](#0-5) ).

This is a permanent, unauthorized state mutation (declaring a class without payment/authorization) that bypasses the fee/resource accounting the whole network relies on for DoS protection, and could be leveraged for spam/DoS if `charge_fee=false` is reachable outside a true one-time genesis bootstrap.

### Likelihood Explanation
Exploitability hinges entirely on whether `charge_fee=false` is reachable for a transaction that is not genuinely part of a one-time system genesis bootstrap. In this snapshot, `charge_fee` appears to be threaded through as an execution flag set by the caller (gateway/batcher), and I could not fully confirm from the indexed code whether production block-building paths ever set `charge_fee=false` for user-submitted RPC transactions outside the documented `allow_bootstrap_txs` test/deployment flow. The design relies on an implicit assumption (asserted only in comments/tests) that this path is only reachable during genesis, but the guard itself (`is_bootstrap_declare`) does not enforce "genesis-only" as an intrinsic, unforgeable property — it is enforced (if at all) by configuration/operational discipline elsewhere in the stack, which I could not fully trace with the available tooling. This weakens confidence that the bug is currently reachable in a default production configuration, but the code's own design is a textbook instance of the "check a proxy condition instead of the real invariant" bug class from the reported CVE.

### Recommendation
Bind the bootstrap-declare bypass to an unforgeable state predicate rather than (or in addition to) the `charge_fee` flag — e.g., require `block_number == 0` / "no blocks committed yet" as read from state, and reject any declare transaction using `sender_address == bootstrap_address()` once the chain has progressed past genesis. Additionally, consider rejecting user-submitted transactions that use the reserved `bootstrap_address()` value at the gateway/stateless-validation layer unconditionally outside of the node's own internal bootstrap-transaction generation, so that the constant address can never be supplied by external callers.

### Proof of Concept
Conceptual (not confirmed executable in this snapshot due to inability to trace every `charge_fee` assignment site):
1. Craft an `RpcDeclareTransaction::V3` with `sender_address = 0x424f4f545354524150` ("BOOTSTRAP"), `nonce = 0`, arbitrary `class_hash`/`compiled_class_hash`, and an empty/default signature.
2. Submit it through any pipeline stage that ultimately constructs an `AccountTransaction` with `execution_flags.charge_fee = false` for this transaction (e.g., an operational/legacy mode, or misuse of `allow_bootstrap_txs`-style tooling against a live, non-genesis chain).
3. Observe in `AccountTransaction::execute_raw` that `is_bootstrap_declare` returns true, `perform_pre_validation_stage` and `__validate_declare__` are skipped entirely, and the class is declared into state with no fee charged and no nonce increment — confirmed by the existing unit test `test_bootstrap_declare`, which demonstrates exactly this state mutation with `TransactionExecutionInfo::default()` and only a `compiled_class_hashes`/`declared_contracts` state diff [7](#0-6) .

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

        // Do not run validate or perform any account-related actions for declare transactions that
        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
            }
        }
