### Title
Uncaught `TypeError` in `sanitizeHost()` from attacker-controlled `host` query parameter can crash the request-authentication flow - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost()` is documented and used as a "validate-then-return-null-or-throw-if-asked" helper, similar in spirit to the NEAR `ValidAccountId` check that the report says should guard against malformed input before it is used to build a system resource. In `shop-validator.ts`, the `host` value is base64-decoded and immediately fed into the WHATWG `URL` constructor without a try/catch, even when `throwOnInvalid` is `false` (the default used by callers that expect a safe `null` return).

### Finding Description
`sanitizeHost` decodes the incoming, attacker-controlled `host` query parameter with `atob` and passes the decoded value straight into `new URL()`: [1](#0-0) 

The base64-charset regex only checks that the *encoded* string is valid base64 — it does not constrain what the *decoded* bytes look like. A decoded value that is not a well-formed URL authority (for example, an unmatched `[` used to open an IPv6 literal, e.g. `https://[`) makes the native `URL` constructor throw a `TypeError: Invalid URL`. That throw happens unconditionally, **before** the `throwOnInvalid` check further down in the function is ever consulted: [2](#0-1) 

Callers that rely on the documented "returns `null` on invalid input" contract call `sanitizeHost` with the default `throwOnInvalid = false` and do not wrap the call in a try/catch, expecting it can only return `string | null`: [3](#0-2) [4](#0-3) 

This helper is invoked directly on unauthenticated request query parameters as part of `shopify.authenticate.admin` request handling (both `shopify-app-remix` and `shopify-app-react-router`), before any session/HMAC validation occurs: [5](#0-4) 

This mirrors the report's root cause: an externally-supplied identifier (`appchain_id` / here, `host`) is used to construct a downstream resource (`sub_account_id` / here, a `URL` object) without first validating that the value is well-formed for that construction, so a malformed-but-technically-passes-the-first-check value causes the underlying primitive (`Promise::new(...).create_account()` / here, `new URL(...)`) to throw/panic instead of being rejected gracefully.

### Impact Explanation
An anonymous request to any embedded-app route protected by `shopify.authenticate.admin` with a crafted `host` query parameter (no signature or session needed to reach `validateShopAndHostParams`) causes an uncaught exception in the shop/host validation step. Since the calling code assumes `sanitizeHost` can only return a value or `null`, the thrown `TypeError` is not converted into the expected 400/redirect response and instead surfaces as an unhandled exception in that request's handling path, defeating the intended graceful "invalid host → redirect to login/App Bridge" behavior for that request.

### Likelihood Explanation
Any unauthenticated caller can send a GET request with `?shop=<valid>&host=<crafted-base64>` to an app route wired through `shopify.authenticate.admin`; no secret, session, or prior installation is required to reach the vulnerable code path, since it runs before HMAC/session validation.

### Recommendation
Wrap the `new URL(...)` construction inside `sanitizeHost` in a try/catch (or pre-validate the decoded string) so that any decode/parse failure is treated the same as "not a valid host" — i.e., set `sanitizedHost = null` and only throw `InvalidHostError` when `throwOnInvalid` is explicitly `true`, consistent with the function's documented contract.

### Proof of Concept
1. Compute `host = Buffer.from('[').toString('base64')` (decodes to the single character `[`).
2. Send `GET {appUrl}?shop=<valid-shop>.myshopify.com&host=<host>` to a route using `shopify.authenticate.admin`.
3. `validateShopAndHostParams` calls `api.utils.sanitizeHost(host)`, which executes `new URL('https://[')` and throws `TypeError: Invalid URL` instead of returning `null`, propagating an unhandled exception out of the intended validation path.

**Note on confidence:** I was not able to execute this against a live instance to confirm the exact runtime behavior of `new URL('https://[')` in every JS engine/version used by this repo's CI, nor whether an upstream framework-level error boundary in `shopify-app-remix`/`shopify-app-react-router` fully absorbs the exception into a generic 500 (limiting the impact to a single failed request rather than a persistent outage). This differs from the NEAR report's "permanently stuck contract" severity, so the practical impact here is best described as a per-request denial of the intended validation/error-handling behavior rather than a lasting service-wide DoS.
