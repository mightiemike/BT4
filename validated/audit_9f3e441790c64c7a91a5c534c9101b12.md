### Title
Unbounded per-request materialization and sort of all delegated-resource index entries for a single address enables node DoS via GetDelegatedResourceAccountIndex - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix` (invoked by `getIndex` and `getV2Index`) performs a `prefixQuery` over all keys sharing an address prefix, materializes every result into a `HashMap`/`ArrayList`, and sorts the full result set with `Comparator.comparing(getTimestamp)` on every call, with no limit on the number of entries returned or processed. Because `delegate`/`delegateV2` write one FROM-prefixed and one TO-prefixed row per unique `(from, to)` pair, an attacker can grow the index for a single owner address to an arbitrarily large size and then repeatedly trigger this unbounded read+sort path via the public `getdelegatedresourceaccountindex` HTTP/gRPC endpoint.

### Finding Description
`GetDelegatedResourceAccountIndexServlet.fillResponse` (framework/src/main/java/org/tron/core/services/http/GetDelegatedResourceAccountIndexServlet.java:58-67) calls `wallet.getDelegatedResourceAccountIndex(address)`, which reaches `DelegatedResourceAccountIndexStore.getIndex`/`getV2Index`, and ultimately `getWithPrefix`: [1](#0-0) 

For each of the two prefix queries (from-list and to-list) this method builds a `List` from `this.prefixQuery(key).values()` — an in-memory `HashMap` of *every* matching key/value in the store — then calls `.sort(Comparator.comparing(...))` over the entire list, and finally streams/maps it into a response object. There is no page size, entry-count cap, or byte-size limit applied anywhere in this path.

The number of entries for a given owner address is attacker-controlled: `delegate`/`delegateV2` write one row per unique `(from, to)` pair keyed as `FROM_PREFIX/V2_FROM_PREFIX + from + to` and `TO_PREFIX/V2_TO_PREFIX + to + from` (lines 63-89). An ordinary funded account can broadcast many `FreezeBalanceContract`/`DelegateResourceContract` transactions from one owner address to many distinct freshly generated receiver addresses, each creating a new, permanent index row (no expiry/eviction of these index entries is applied on unfreeze in this file — `unDelegate`/`unDelegateV2` only remove rows when the attacker itself calls undelegate, which they control and need not do).

The read path (`GetDelegatedResourceAccountIndexServlet`, and equivalently the gRPC `getDelegatedResourceAccountIndex` in `RpcApiService`) is protected only by the generic `RateLimiterServlet` QPS-style rate limiter (framework/src/main/java/org/tron/core/services/http/RateLimiterServlet.java:103-152), which limits requests-per-second/global concurrency but does not limit or scale with the *cost* of an individual request — i.e., it does not protect against a single expensive request whose cost is proportional to attacker-controlled state size. No actuator-side validation, permission check, or fork gate constrains the number of distinct delegation targets a single owner may accumulate over time, and no cap exists in `getWithPrefix` on the number of rows fetched/sorted.

### Impact Explanation
This matches the "DoS via RPC-API" bounty class: a single unprivileged account can, over time, inflate the persistent index for its own address to a very large size (tens/hundreds of thousands of rows), then issue GET/POST requests to `/wallet/getdelegatedresourceaccountindex` (or the equivalent gRPC/Solidity/PBFT endpoints, which share the same store code) that each force the node to allocate large `HashMap`/`ArrayList` structures and perform an O(N log N) sort per request. Repeated/concurrent requests against that address amplify CPU and heap pressure on the full node, degrading service for other API clients (sustained latency/heap growth), consistent with the described scoped impact of a request-cost/heap-DoS.

### Likelihood Explanation
- Preconditions: only an ordinary funded account; no special permissions, no witness/SR/committee role, no non-default config.
- Cost to attacker: each distinct delegation target requires a separate `FreezeBalanceContract` + `DelegateResourceContract` transaction (paid in TRX/frozen balance and bandwidth), so building N=100k entries costs the attacker N transactions' worth of fees and bandwidth — this is a real chain-economics cost, but it is a one-time, bounded, and modest cost relative to potentially causing repeated, ongoing service degradation for all API consumers querying that address (or any address the attacker chooses to bloat). The read side itself (the actual DoS trigger) is essentially free to repeat — bounded only by the generic QPS rate limiter, not by request cost.
- Feasibility/repeatability: fully scriptable; index growth is monotonic and persists on-chain/in the store unless the attacker explicitly undelegates, and the attacker fully controls when/whether to do so.

### Recommendation
- Add a hard cap (with pagination) on the number of entries returned/sorted by `getWithPrefix`, or convert the sort to a bounded/streaming top-K if only recent entries matter to callers.
- Consider limiting or cost-charging (bandwidth/energy) proportional to the number of distinct delegation relationships an owner accumulates, or capping the number of distinct receivers a single owner can delegate to.
- Add a request-cost-aware rate limiter/backpressure keyed on the resulting index size (e.g., reject or heavily throttle prefix queries whose result set exceeds a configurable threshold) rather than relying solely on QPS-based `RateLimiterServlet`.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
