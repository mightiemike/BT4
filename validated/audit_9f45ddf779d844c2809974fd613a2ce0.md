This confirms a concrete, exploitable analog to the Acala storage-bloat report. The L1 handler transaction fee check in `execute_raw` at [1](#0-0)  only requires `paid_fee_on_l1 != Fee(0)` — it never compares `paid_fee` against the actually computed `receipt.fee`. Any L1 message sender can trigger execution of arbitrary L1-handler entry points that write to many distinct, previously-untouched storage cells (new Patricia-tree leaves) while only needing a nominal non-zero `paid_fee_on_l1` (as low as 1 wei), up to the generous `l1_handler_max_amount_bounds` gas ceiling [2](#0-1) . The comment in the code itself acknowledges the weakness: "assert only that any amount of fee was paid... no matter what was the actual fee" [3](#0-2) , and the RPC/converter layers even hardcode `Fee(1)` as the paid fee for fee estimation and for the default converter path [4](#0-3) [5](#0-4) .

### Title
L1-Handler storage-write fee check accepts any nonzero `paid_fee_on_l1` regardless of actual state-growth cost, enabling cheap storage/Patricia-tree bloat - (File: crates/blockifier/src/transaction/l1_handler_transaction.rs)

### Summary
L1-handler transactions (triggered by unprivileged L1 message senders via `sendMessageToL2`) are checked for gas-bound compliance (`l1_handler_max_amount_bounds`), but the fee-sufficiency check only verifies `paid_fee_on_l1 != Fee(0)`, never that it covers `receipt.fee` (the real cost of the storage writes performed). This lets an L1 sender pay a token amount (e.g. 1 wei) while causing many new (zero→nonzero) storage-key allocations on L2, permanently growing sequencer/full-node storage and the global state (Patricia) tree — the same "no minimum cost relative to storage growth" bug class as the referenced Acala finding.

### Finding Description
In `L1HandlerTransaction::execute_raw`, after execution the code computes the real `receipt.fee` (via `TransactionReceipt::from_l1_handler`, which internally counts `n_storage_updates`/`n_allocated_keys` through `StateChanges::count_for_fee_charge`) and performs a resource-bound check (`FeeCheckReport::check_all_gas_amounts_within_bounds`) against the fixed `l1_handler_max_amount_bounds` ceiling. However, the only fee-adequacy check that follows is:
```rust
let paid_fee = self.paid_fee_on_l1;
if paid_fee == Fee(0) {
    return Err(TransactionExecutionError::TransactionFeeError(...));
}
``` [1](#0-0) 
This never compares `paid_fee` to `receipt.fee`. As long as `paid_fee_on_l1 > 0`, the transaction is committed and `l1_handler_tx_execution_info` even zeroes out the receipt's fee afterward (`receipt.fee = Fee(0)`) [6](#0-5) , meaning no on-L2 fee is actually collected for these storage allocations at all — the "fee" for L1 handlers is nominally handled on L1 by the Starknet core contract, but the sequencer itself performs no proportional cost enforcement.

The `l1_handler_max_amount_bounds` values (e.g. `l1_gas`, `l1_data_gas`, `l2_gas` each `10000000000`) act only as an upper bound per transaction, not a lower bound proportional to state growth [7](#0-6) . Each new (zero→nonzero) storage key written inside the L1-handler entry point is tracked as an `AllocatedKeys` entry and contributes to `n_allocated_keys`/`state_diff_size` for the block's bouncer weights [8](#0-7) , and is permanently persisted to storage (`write_storage_diffs`) once the block is committed [9](#0-8) . Since fee sufficiency is not enforced for L1-handlers, the actual proportional per-storage-cell allocation cost (`allocation_cost` gas vector applied per `n_allocated_keys` in `StateResources::to_gas_vector`) never has to be paid by the L1 sender through the sequencer's fee mechanism [10](#0-9) .

### Impact Explanation
An L1 message sender can deploy a contract with an L1-handler entry point that writes to many distinct, previously-zero storage slots (e.g., using message payload data as unique keys), and repeatedly invoke `sendMessageToL2` while paying only a token amount for `paid_fee_on_l1` (as the sequencer accepts any nonzero value, and both the RPC fee-estimation path and the transaction converter hardcode `Fee(1)` in places where the real L1-paid fee isn't tracked). This causes unbounded accumulation of low-value/near-zero storage entries in the global state, growing the on-chain state tree (Patricia commitment) and the node's persistent storage (`apollo_storage`) size, degrading node performance, sync times, and long-term storage/maintenance costs for all honest nodes — matching the "runtime storage bloat via cheap low-liquidity/low-value positions" impact class from the referenced report, but here at the L1-handler / state-tree level of a Starknet-style sequencer.

### Likelihood Explanation
Likelihood is high: any actor who can call `sendMessageToL2` on the L1 core contract (an unprivileged L1 sender) can trigger this path repeatedly. The gas/resource *upper* bound (`l1_handler_max_amount_bounds`) does not prevent this since it merely limits a single transaction's resource ceiling, not the number of transactions or the true per-transaction cost coverage. Nothing in `execute_raw` ties `paid_fee_on_l1` to the actual `receipt.fee`/state growth, so this is systematically and repeatably exploitable, not a one-off edge case.

### Recommendation
Enforce that `paid_fee_on_l1 >= receipt.fee` (or at minimum scale the acceptance threshold with `n_allocated_keys`/`state_diff_size`) instead of merely checking `paid_fee_on_l1 != Fee(0)`. Alternatively, apply a bouncer-level minimum cost per newly allocated storage key specifically for L1-handler transactions (mirroring the `allocation_cost` already computed in `StateResources::to_gas_vector`), and reject/rate-limit L1-handler transactions whose declared/paid fee does not cover the marginal state-growth cost they induce.

### Proof of Concept
1. Deploy an L2 contract with an `#[l1_handler]` function that, given L1 payload data containing an arbitrary/incrementing key, performs a single `storage_write` to a fresh (never-before-written) storage slot with a nonzero value (analogous to the Acala PoC's 1-wei deposits creating new pool positions).
2. From L1, call `sendMessageToL2` targeting this handler, supplying a unique key each time, and pay the minimal fee accepted by the bridge/core contract (in the sequencer's execution model this is represented as `paid_fee_on_l1 = Fee(1)`, matching the hardcoded value used in `crates/apollo_rpc/src/v0_8/api/mod.rs:427` and `crates/apollo_transaction_converter/src/transaction_converter.rs:481`).
3. Observe in `L1HandlerTransaction::execute_raw` that execution succeeds and is committed as long as `paid_fee_on_l1 != Fee(0)` [11](#0-10) , regardless of the real `receipt.fee` computed from the newly allocated storage key.
4. Repeat across many L1 messages/keys; each call permanently adds a new leaf to the global state tree and a new entry in `contract_storage` in `apollo_storage`, at a cost far below the actual state-growth/Patricia-update cost the protocol's own `allocation_cost` gas model assigns to a new storage key.

pub struct AllocatedKeys(HashSet<StorageEntry>);

impl AllocatedKeys {
    pub fn len(&self) -> usize {
        self.0.len()
    }

    pub fn is_empty(&self) -> bool {
        self.0.is_empty()
    }

    /// Collects entries that turn zero -> nonzero.
    pub fn from_storage_diff(
        updated_storage: &HashMap<StorageEntry, Felt>,
        base_storage: &HashMap<StorageEntry, Felt>,

        Self(
            updated_storage
                .iter()
                .filter_map(|(k, v)| {
                    let base_value = base_storage.get(k).unwrap_or(&Felt::ZERO);
                    if *v != Felt::ZERO && *base_value == Felt::ZERO { Some(*k) } else { None }
                })
                .collect(),
        )
    }

    /// Returns the gas cost of the transaction's state changes.
    // The allocation_cost L2 gas component prices the extra Patricia Merkle tree proving
    // overhead for writing to a new (zero → nonzero) state cell. This is computed from
    // the final state diff, not per-syscall. Implications:
    // - A 0→x→0 write avoids the charge (correct: no net state change, no proving cost).
    // - System-side allocations (fee transfers, etc.) are also charged.
    // - This cost flows into receipt.gas.l2_gas (user fees + EIP-1559) and the bouncer's
    //   receipt_l2_gas dimension (block closure), but NOT into bouncer sierra_gas.
    pub fn to_gas_vector(&self, use_kzg_da: bool, allocation_cost: &AllocationCost) -> GasVector {
        let n_allocated_keys: u64 = self
            .state_changes_for_fee
            .n_allocated_keys
            .try_into()
            .expect("n_allocated_keys overflowed");
        let allocation_gas_vector = allocation_cost.get_cost(use_kzg_da);
        let total_allocation_cost =
            allocation_gas_vector.checked_scalar_mul(n_allocated_keys).unwrap_or_else(|| {
                panic!(
                    "State resources to gas vector overflowed: tried to multiply \
                     {allocation_gas_vector:?} by {n_allocated_keys:?}",
                )
            });
        let da_gas_cost = self.da_gas_vector(use_kzg_da);
        total_allocation_cost.checked_add(da_gas_cost).unwrap_or_else(|| {
            panic!(
                "State resources to gas vector overflowed: tried to add {total_allocation_cost:?} \
                 to {da_gas_cost:?}",
            )
        })
    }
