### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash validation, letting `db-tool replay-verify` accept a corrupted or divergent authenticated state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  is the integrity check used by the `replay-on-archive` verification tool to confirm that locally re-executed transaction results match the authenticated `TransactionInfo` pulled from a backup/archive. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly **does not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` on `TransactionInfo`, per the inline `TODO(trading-native)` comment.

### Finding Description
`TransactionInfoV1` (and V0) carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields [2](#0-1) , which represent the authenticated Sparse-Merkle/JMT state roots that are supposed to bind a transaction's execution result to the exact resulting world state. These are exactly the values a validator or auditor must re-derive and compare during replay to catch execution divergence, storage corruption, or a maliciously/accidentally altered backup.

However, `ensure_match_transaction_info` only validates `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash` [3](#0-2) , then returns `Ok(())` unconditionally afterward, with a comment acknowledging the gap: [4](#0-3) 

This function is the sole verification gate used by `storage/db-tool`'s `replay_on_archive.rs`, which re-executes chunks of historical transactions via `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` per transaction to decide pass/fail: [5](#0-4) 

Because the checkpoint hash fields are skipped, a replay where the write set and events match but the resulting state tree root diverges (e.g., due to a state-store/backup bug, a JMT/position-tree computation bug, or corrupted checkpoint data) will be reported as a **successful replay** even though the authenticated state root is wrong. This directly matches the "Proof and Storage Pivots" concern: authenticated proof-bearing responses (here, the replay-verify tool's PASS/FAIL judgment over `TransactionInfo`, which is the object stored in the transaction accumulator and referenced by state/consistency proofs) become detached from the real ledger state.

### Impact Explanation
`TransactionInfo` is the leaf object hashed into the transaction accumulator, and its `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields are the only durable binding between a committed transaction and the resulting authenticated state root [6](#0-5) . Silently skipping their verification in the primary replay-verification tool means state-root corruption or divergence (whether from a storage bug, a bad backup, or backup tampering) would not be detected by `replay_on_archive`, undermining the tool's core purpose of proving that archived/backed-up ledger state matches independently re-executed results. This is a hard-fork/replay-integrity class issue: it doesn't corrupt live consensus state, but it defeats the audit/verification mechanism meant to catch such corruption after the fact, which is the mainnet-relevant proof-integrity concern called out in the task's scope ("Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state").

### Likelihood Explanation
Medium: this triggers only when `state_checkpoint_hash` (or the newer hot-state/position-state hashes) would actually diverge while write-set/event hashes still match — for example, a bug isolated to Sparse Merkle Tree/JMT root computation, hot-state extension logic (per `execution/executor/src/workflow/do_state_checkpoint.rs`), or a corrupted/incompletely restored state snapshot in a backup. The code comment itself confirms this is a known, currently-open gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), i.e., it's an acknowledged incomplete safeguard rather than a hypothetical.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute (or otherwise validate) `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` from the replayed execution output and compare them against the corresponding fields on the expected `TransactionInfo`, failing verification (returning an `Err`) on any mismatch, before this check set is relied upon as a complete replay/backup integrity gate.

### Proof of Concept
Not independently exploitable without a state-root-producing bug elsewhere; the flaw is that `ensure_match_transaction_info` at [7](#0-6)  is missing the comparisons entirely (verifiable by inspection: no reference to `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` accessors appears in the function body), so any hypothetical/latent state-root divergence during replay of `storage/db-tool/src/replay_on_archive.rs` [8](#0-7)  would pass verification undetected.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
