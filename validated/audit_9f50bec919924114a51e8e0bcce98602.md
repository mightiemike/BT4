## Title
`ensure_match_transaction_info` skips state-checkpoint hash comparison, letting replay-verify accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
The chunk-executor's replay/verify path uses `TransactionOutput::ensure_match_transaction_info` to confirm that a freshly re-executed transaction output matches the transaction info recorded on-chain. That comparator checks execution status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but never checks `state_checkpoint_hash` (nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`). This gap is explicitly acknowledged in a code comment in the same function.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates `status`, `gas_used`, and `write_set_hash` against the corresponding fields of the on-chain `TransactionInfo`, and validates the event root hash at [2](#0-1) . It then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()` (the authenticated state root for that version) against anything computed from the re-executed state. The function's own comment documents this: [3](#0-2) .

This comparator is the sole “outputs match info” check used during chunk replay in `verify_execution`, which is exercised by the archive replay-verification tool (`db-tool`’s `replay_on_archive`/`replay_verify`) and by `TransactionReplayer`: [4](#0-3) . Because only status/gas/write-set-hash/event-root are checked, a re-executed transaction whose resulting state (Merkle/JMT state root, hot-state root, or the new "position" state root guarded by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) differs from the historically committed `state_checkpoint_hash` will still pass verification as long as its write set and events happen to hash the same. More importantly, for any state-root divergence caused by a bug in state-checkpoint computation itself (e.g., in `DoStateCheckpoint`, which independently derives `state_summary`/`last_checkpoint().root_hash()`; see [5](#0-4) ), the replay-verify tool has no mechanism in this code path to catch it, since the state root is simply never compared.

### Impact Explanation
Replay-verify (`db-tool replay_on_archive` / `replay_verify`) is one of the primary mainnet safety mechanisms used to confirm that a full historical replay of an archive produces the same ledger state as what was originally committed by validators. If the state-checkpoint hash is silently excluded from this comparison, replay-verify can report success (“exiting with success”, see [6](#0-5) ) even though the locally computed authenticated state root diverges from the state root that was actually committed on-chain at that version. This masks state-root regressions (e.g., in state-checkpoint/state-summary computation, hot-state root computation, or the new position-state root path) that would otherwise be the exact class of bug replay-verify exists to catch, undermining confidence in ledger-state integrity checks used to validate the correctness of historical execution/storage.

### Likelihood Explanation
This is not an attacker-triggered exploit but a self-documented gap in an unprivileged, purely local verification routine that always executes on this code path (no feature flag guards the missing check itself — the comment only mentions gating a compute flag). Any state-root computation defect introduced elsewhere in the executor/storage stack will deterministically go undetected via this function, so the likelihood of the gap mattering rises directly with the likelihood of any other future/latent state-root bug — it removes a critical detection layer for state-commitment integrity regressions rather than requiring adversarial input.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `txn_info.state_checkpoint_hash()` (and, where computed/available, `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`) against the locally computed roots for checkpoint transactions, rather than only checking status/gas/write-set/event hashes. At minimum, replay-verify tooling should fail loudly instead of silently succeeding when a checkpoint version's authenticated state root cannot be confirmed.

### Proof of Concept
Not exploitable via an external transaction; the gap is demonstrated directly by the code: `ensure_match_transaction_info` ( [7](#0-6) ) is the exhaustive set of checks performed in `verify_execution` ( [8](#0-7) ), and it never calls `TransactionInfo::state_checkpoint_hash()`/`ensure_state_checkpoint_hash()` (defined at [9](#0-8) ) for comparison — so any test or fault-injection that alters only the state Merkle root produced during replay (while keeping write set/events/gas/status identical) will still return `Ok(())` from this function and thus report a successful replay-verify.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    pub fn state_checkpoint_hash(&self) -> Option<HashValue> {
        match self {
            Self::V0(v) => v.state_checkpoint_hash,
            Self::V1(v) => v.state_checkpoint_hash,
        }
    }

    pub fn has_state_checkpoint_hash(&self) -> bool {
        self.state_checkpoint_hash().is_some()
    }

    pub fn ensure_state_checkpoint_hash(&self) -> Result<HashValue> {
        self.state_checkpoint_hash()
            .ok_or_else(|| format_err!("State checkpoint hash not present in TransactionInfo"))
    }
