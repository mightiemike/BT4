### Title
Stale cached `InternalTransaction` hash desynchronized from `value` after post-construction `setValue()` - (File: `chainbase/src/main/java/org/tron/common/runtime/InternalTransaction.java`)

### Summary
`InternalTransaction#getHash()` lazily computes and permanently caches `this.hash` from an encoding that includes `this.value`, but `setValue()` never invalidates that cache. In `Program.java`, several TVM opcode handlers (`suicide`, `cancelAllUnfreezeV2Action`) construct a child `InternalTransaction` (which eagerly computes and caches its hash in the constructor) and later call `internalTx.setValue(...)` to adjust the transferred amount, leaving the exported hash bound to the pre-adjustment value.

### Finding Description
The child constructor computes and stores the hash immediately: `this.hash = getHash();` at [1](#0-0) , where `getHash()` derives the hash from `getEncoded()`, which itself encodes `this.value` into `raw` and also memoizes `protoEncoded` [2](#0-1) . Once `this.hash` is non-empty, `getHash()` always returns the cached bytes without recomputation: `if (!isEmpty(hash)) { return Arrays.copyOf(hash, hash.length); }` [3](#0-2) . `setValue()` only mutates the field and performs no cache invalidation: `public void setValue(long value) { this.value= value; }` [4](#0-3) .

In `Program.suicide()`, an `InternalTransaction` is created via `addInternalTx(...)` (which caches the hash at construction), and later, when `VMConfig.allowTvmFreezeV2()` is enabled and there is an expired unfrozen balance to inherit, its value is adjusted post hoc: `internalTx.setValue(internalTx.getValue() + expireUnfrozenBalance);` [5](#0-4) . The hash cached at construction time reflects the balance *before* `expireUnfrozenBalance` was added, but the exported `value` field reflects the total after adjustment.

When the internal transaction is later serialized via `TransactionUtil.buildInternalTransaction`, it calls `it.getHash()` (returns the stale cached hash) and `it.getValue()` (returns the updated value) into the same `Protocol.InternalTransaction` record: `itBuilder.setHash(...)` and `callValueInfoBuilder.setCallValue(it.getValue())` [6](#0-5) . The same divergence is exposed through the event-plugin trigger pipeline, `TransactionLogTriggerCapsule#getInternalTransactionList`, which independently reads `internalTransaction.getHash()` and `internalTransaction.getValue()` [7](#0-6) . Both consumers assume hash and value are mutually consistent, but there is no guard preventing `setValue()` after hash caching, and no re-derivation of the hash from the current field state.

A similar risk pattern exists in `cancelAllUnfreezeV2Action()`, which calls `internalTx.setExtra(...)` after construction/hash-caching [8](#0-7) ; while `extra` is not part of the hash preimage (`getEncoded()` only includes `parentHash`, `receiveAddress`, `data`, `value`), it reinforces that the class's design allows arbitrary post-construction mutation without hash consistency guarantees, and the `value` case in `suicide()` is a genuine mismatch.

### Impact Explanation
The exported `Protocol.InternalTransaction.hash` field for the internal transaction generated during a `SUICIDE` opcode with `allowTvmFreezeV2` enabled and an inheritable expired-unfrozen balance no longer authenticates the exported `callValue`. Any downstream consumer (block explorer, bridge, indexer) that uses the internal-transaction hash as a content-addressed key to validate or deduplicate settlement/transfer records for that value would validate a record whose committed hash was computed for a different (smaller) amount than what is actually recorded and settled on-chain. This is a deterministic accounting/data-integrity divergence between the on-chain effect (`getContractState()` balance updates, which use the correct, real values) and the exported/observable record used by off-chain systems.

### Likelihood Explanation
This is deterministically reachable by any unprivileged account executing a `SUICIDE` opcode inside a smart contract when `VMConfig.allowTvmFreezeV2()` is active and the contract owner has an expired unfrozen (TVM v2 freezing) balance to inherit (`expireUnfrozenBalance > 0`), which is a standard, attacker-controllable TVM feature-flag path requiring no privileged access — just deploying/calling a contract that self-destructs after freezing/unfreezing TRX. It is fully repeatable and always triggers when the balance condition is met.

### Recommendation
Invalidate (null out) `this.hash` and `this.protoEncoded` inside `setValue()` (and any other setter touching fields included in `getEncoded()`), forcing `getHash()` to recompute from the current state on next access; alternatively, remove hash caching entirely and always recompute from current fields, or forbid calling `setValue()`/`setExtra()` after the hash has been read/finalized by throwing an `IllegalStateException`.

### Proof of Concept
```java
// framework or chainbase test module
@Test
public void testStaleHashAfterSetValue() {
  byte[] parentHash = Hash.sha3("parent".getBytes());
  InternalTransaction internalTx = new InternalTransaction(
      parentHash, 1, 0,
      "sender".getBytes(), "receiver".getBytes(),
      1000L, new byte[0], "suicide", 0L, null);

  byte[] hashBeforeUpdate = internalTx.getHash();

  // Simulate Program.suicide() adjusting value after hash was cached
  internalTx.setValue(internalTx.getValue() + 500L); // e.g. expireUnfrozenBalance

  byte[] hashAfterUpdate = internalTx.getHash();

  // BUG: hash is stale — same as before, even though value changed
  assertArrayEquals(hashBeforeUpdate, hashAfterUpdate);

  // Expected (fixed) behavior: hash should change to reflect new value
  // assertFalse(Arrays.equals(hashBeforeUpdate, hashAfterUpdate));

  Protocol.InternalTransaction proto = TransactionUtil.buildInternalTransaction(internalTx);
  assertArrayEquals(hashBeforeUpdate, proto.getHash().toByteArray());
  assertEquals(1500L, proto.getCallValueInfo(0).getCallValue());
  // proto.hash was computed for value=1000, but proto.callValue=1500 -> inconsistent record
}
```
