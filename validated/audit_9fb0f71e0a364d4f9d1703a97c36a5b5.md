## Title
Cross-tenant session deletion via `X-Shopify-Shop-Domain` header not bound to webhook HMAC signature - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
The Bribes.sol bug allowed an attacker to credit power to one key (`ptf`) while debiting a different, unrelated key, because the bookkeeping never verified that the value used to debit was the same value that was used to credit. In `shopify-app-js`, the webhook-processing pipeline has an analogous mismatch: the cryptographic proof (HMAC) covers only the raw request **body**, while the `shop`/`domain` value used to key state-changing bookkeeping operations (deleting all of a shop's stored sessions on `APP_UNINSTALLED`) comes from the `X-Shopify-Shop-Domain` **header**, which is never bound to that signature.

### Finding Description
`validateHmacFromRequestFactory` computes and compares the HMAC only over `rawBody`: [1](#0-0) 

`validateFactory`/`checkWebhooksHeaders` then extracts `domain` (i.e. the shop) straight from the `X-Shopify-Shop-Domain` header, independent of the HMAC check, and returns it as validated once the body HMAC passes: [2](#0-1) 

That `domain`/`shop` value is then used directly as the bookkeeping key for destructive operations. For the built-in `APP_UNINSTALLED` handling in `shopify-app-express`, the handler receives `shop` from the header-derived value and calls `AppInstallations.delete(shop)`, which looks up and deletes **all** sessions for that shop: [3](#0-2) [4](#0-3) 

The same pattern (using the header-derived `check.domain` to key session lookups) appears in the Remix/React Router webhook authenticate helpers: [5](#0-4) 

Because the HMAC signs only the JSON body (which for `APP_UNINSTALLED` is typically `{}` or shop metadata not required to match the header), any attacker who legitimately controls a shop with the app installed can capture one real, validly-signed webhook delivery to their own endpoint, then replay that request to the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` header to point at a victim shop. The body HMAC still validates (it was computed over the untouched body), but the "key" used for the destructive bookkeeping action (which shop's sessions to purge) is taken from the unauthenticated header — exactly the deposit/withdraw key mismatch pattern in the Bribes.sol report: the credential (valid signature) is tied to one identity (attacker's own webhook body), but the state-changing key (shop to act on) is a different, unverified value.

### Impact Explanation
An attacker who has (or creates) a legitimate installation of the target app on any shop can forge the shop-scoped webhook header to trigger `AppInstallations.delete(victimShop)` for an arbitrary victim shop, wiping the victim's stored offline/online sessions (access tokens). This is a denial-of-service against a specific, unrelated tenant: the app treats the victim shop as freshly uninstalled, requiring re-authentication and potentially disrupting billing/webhook-registration state tied to that access token, all without ever compromising the victim's own credentials directly.

### Likelihood Explanation
Reachable by any external actor who can install the app on one shop (including a free/dev store) and capture a single valid webhook delivery — no admin access token, secrets, or privileged role on the victim shop are required. The only friction is that many app-specific webhook topics use a fixed/predictable or empty body, making the replay straightforward once the attacker controls a delivery endpoint for their own shop.

### Recommendation
- Bind the shop identity into the signed material, or at minimum cross-check the header-derived `domain` against context that Shopify does authenticate (e.g., verify the webhook's `X-Shopify-Webhook-Id`/topic subscription was actually registered for that specific shop, or require confirming an active session exists for that exact combination before performing bulk-destructive operations).
- Before calling `AppInstallations.delete`/`deleteSessions`, verify that a session already on file for the claimed `shop` corresponds to a subscription actually created for that shop (e.g., look up webhook registrations per shop) rather than trusting the header value alone.
- Document that `webhooks.validate`'s HMAC only authenticates the body, not headers, so integrators do not assume `domain`/`shop` is tamper-proof.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a legitimately signed `APP_UNINSTALLED` webhook delivery (HMAC computed over body only) via `validateHmacFromRequestFactory`: [6](#0-5) 
2. Attacker replays the same POST body and HMAC header to the app's `/webhooks` endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `validateFactory` still returns `valid: true` and `domain: 'victim-shop.myshopify.com'` because HMAC verification never inspected the header: [7](#0-6) 
4. The `APP_UNINSTALLED` handler runs `deleteAppInstallationHandler` with `shop = 'victim-shop.myshopify.com'`, calling `AppInstallations.delete(shop)`, which purges all of the victim's stored sessions: [4](#0-3) 

**Note on confidence**: I was not able to inspect Shopify's own webhook delivery guarantees (whether Shopify's real infrastructure enforces a body/shop binding via TLS client identity or additional undocumented server-side checks outside this repo), so the practical exploitability depends on whether an attacker can actually get raw control over the HTTP request reaching the app's endpoint (e.g., by proxying/replaying rather than only through Shopify's genuine webhook delivery channel, since Shopify sends these over HTTPS directly to the registered callback URL, not attacker-controlled infrastructure). This should be validated against Shopify's actual webhook delivery mechanics before treating this as a fully confirmed remote exploit.

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
