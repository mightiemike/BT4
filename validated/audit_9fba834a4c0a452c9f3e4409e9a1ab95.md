### Title
Unsafe `BigInteger.longValue()` downcast in DPoS voting-reward accounting can silently truncate reward payouts - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The DPoS voting reward computation converts an unbounded `BigInteger` reward accumulator into a `long` using the non-checked `longValue()` method instead of a bounds-checked cast (e.g. `longValueExact()`). Exactly like the PoolTogether `_getTier` downcast bug (unchecked `uint256 -> uint96`), this narrowing conversion in java-tron discards high-order bits without reverting, so an overflowing intermediate value silently becomes an incorrect (and potentially negative) `long` reward instead of throwing.

### Finding Description
Any voter/witness reward withdrawal path computes reward using a per-vote accumulator `Vi`, scaled by `DECIMAL_OF_VI_REWARD = 10^18`: [1](#0-0) 

`Vi` is accumulated every cycle and never resets/decays as long as a witness has outstanding un-withdrawn votes: [2](#0-1) 

The same unbounded accumulation logic exists in `RewardViCalService.accumulateWitnessVi`: [3](#0-2) 

When a voter finally withdraws (via `WithdrawBalanceActuator` -> `MortgageService.withdrawReward`, or via the TVM `withdrawReward` opcode -> `VoteRewardUtil.withdrawReward`), the delta between the current and last-checkpointed `Vi` is multiplied by the user's vote count and divided back down, then narrowed to `long` with the unchecked `BigInteger.longValue()`: [4](#0-3) [5](#0-4) [6](#0-5) 

`BigInteger.longValue()` (unlike `longValueExact()`) never throws — it silently returns the low 64 bits of the value when the magnitude exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE`, exactly the "downcast without bounds check" pattern flagged in the PoolTogether report. Because `Vi` is a monotonically-growing accumulator with no upper bound enforced anywhere (no cap on cycle count or on how long a voter can defer `withdrawReward`), and the growth rate per cycle is inversely proportional to a witness's total vote count (`reward * 1e18 / voteCount`), a witness with a very small total vote count accumulates `Vi` extremely quickly. An unprivileged voter can vote for such a low-vote-count witness and simply avoid withdrawing rewards for a long period, letting `deltaVi` grow arbitrarily large before finally calling withdrawal.

### Impact Explanation
If `deltaVi * userVote / DECIMAL_OF_VI_REWARD` exceeds `Long.MAX_VALUE`, the silent truncation in `longValue()` produces an arbitrary (including negative) `long` `reward` value that is then added directly to the account's `allowance`/balance: [7](#0-6) 

This breaks the TRX supply accounting invariant — a voter could receive a drastically wrong (larger or smaller, or negative) reward credited to their account instead of the transaction reverting, which is a direct accounting/settlement correctness violation reachable from unprivileged voting/withdrawal actuators and the TVM `withdrawReward`/`voteWitness` opcodes.

### Likelihood Explanation
Reaching a genuine overflow requires the accumulator to grow past `~9.2e18` in scaled units, which needs either an extremely long deferral period, a witness with a very small vote count, or both. This is a low-probability but non-mocked, unprivileged-reachable path (any TRX holder can vote for a low-vote witness and defer withdrawal), matching the "Medium" severity judged for the original PrizePool finding (no immediate proof of practical trigger, but a real code-level flaw in the accounting arithmetic).

### Recommendation
Replace the unchecked `BigInteger.longValue()` calls in `MortgageService.computeReward`, `VoteRewardUtil.computeReward`, and `RewardViCalService.getNewRewardAlgorithmReward` with `longValueExact()` (or an explicit range check against `Long.MAX_VALUE`), and cause the transaction/withdrawal to fail loudly (or clamp/split the reward) rather than silently wrapping when the computed reward exceeds the `long` range.

### Proof of Concept
1. A witness `W` receives block/tx-fee rewards (`payReward` in `MortgageService`) each cycle while having a very small total `voteCount` (e.g., votes from only one small voter).
2. `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi` computes `deltaVi = reward * 1e18 / voteCount` each cycle and adds it to `preVi`; because `voteCount` is small, `Vi` grows very quickly cycle after cycle.
3. The voter never calls `withdrawReward` (neither `WithdrawBalanceActuator` nor the TVM `withdrawReward` opcode), letting cycles accumulate over an extended period so `Vi` (and thus `deltaVi` at withdrawal time) grows past `Long.MAX_VALUE / userVote * 1e18`.
4. When the voter eventually withdraws, `computeReward` calls `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD).longValue()` — because the intermediate exceeds `Long.MAX_VALUE`, `longValue()` truncates instead of throwing, and an incorrect (potentially negative) `reward` is credited to the account's allowance via `adjustAllowance`, corrupting reward accounting instead of reverting.

  private static long computeReward(long beginCycle, long endCycle,

    }

      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);

          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
