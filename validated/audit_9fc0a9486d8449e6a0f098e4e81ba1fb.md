### Title
Unhardened `long` overflow in TVM vote-reward accounting (`computeReward`) - (`actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
`VoteRewardUtil.computeReward` accumulates per-vote reward into a plain `long reward` accumulator using `BigInteger.multiply(...).divide(...).longValue()` instead of `longValueExact()`, and the running total is updated with an un-checked `reward += ...`. This mirrors the reported bug class (unchecked integer arithmetic in a reward/incentive accounting path leading to silent overflow), except here the silent-truncation risk sits directly in the TVM vote-reward withdrawal/query path rather than being caught by any `checkedAdd`/`longValueExact` hardening that the rest of the resource-accounting code in this codebase already applies.

### Finding Description
`computeReward` is:
```java
private static long computeReward(long beginCycle, long endCycle,
                                  AccountCapsule accountCapsule, Repository repository) {
  ...
  long reward = 0;
  for (Protocol.Vote vote : accountCapsule.getVotesList()) {
    ...
    BigInteger deltaVi = endVi.subtract(beginVi);
    if (deltaVi.signum() <= 0) { continue; }
    long userVote = vote.getVoteCount();
    reward += deltaVi.multiply(BigInteger.valueOf(userVote))
        .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
  }
  return reward;
}
``` [1](#0-0) 

Two problems combine here:
1. `.longValue()` (not `.longValueExact()`) is used after the `BigInteger` multiply/divide, so if the per-witness delta-VI times vote count exceeds `Long.MAX_VALUE` after dividing by `DECIMAL_OF_VI_REWARD`, the result silently wraps instead of throwing, unlike the hardened resource-accounting helpers elsewhere in the codebase (e.g. `EnergyProcessor`/`ResourceProcessor`/`RepositoryImpl`) that consistently call `longValueExact()` and are covered by dedicated overflow tests. [2](#0-1) [3](#0-2) 
2. The accumulation `reward += ...` across multiple votes in the loop is a plain `long` addition with no overflow check at all, so even individually-safe per-vote rewards can overflow the running total across many delegated votes.

The identical unhardened pattern is duplicated in `RewardViCalService.getNewRewardAlgorithmReward`, which computes the same style of `BigInteger` reward and also calls `.longValue()` plus `reward += ...` without a check. [4](#0-3) 

This is reachable from an unprivileged account: `computeReward` is invoked from `VoteRewardUtil.withdrawReward` and `VoteRewardUtil.queryReward`, which are called by `WithdrawRewardProcessor.execute` — a TVM native-contract processor invoked whenever any account (including via a smart contract call) triggers the vote-reward withdrawal opcode. [5](#0-4) [6](#0-5) 

Notably, `WithdrawRewardProcessor.execute` itself does use `LongMath.checkedAdd` for `oldBalance + allowance`, showing the team is aware of overflow risk in this exact code path but did not apply the same rigor to the `computeReward` accumulation that produces the `allowance`/reward value in the first place. [7](#0-6) 

### Impact Explanation
If a wrapped/silently-truncated (or negative, due to overflow wraparound) reward value is computed, `adjustAllowance` will credit the account's allowance with an incorrect (potentially far too small, far too large, or negative) amount, which is subsequently paid out as real TRX balance via `WithdrawRewardProcessor.execute`. This corrupts reward/incentive accounting and could allow balance inflation or reward loss, matching the "asset or accounting corruption" acceptance criterion.

### Likelihood Explanation
Triggering the overflow requires an account (or delegate) to accumulate an extremely large `deltaVi * userVote` product across enough cycles/votes to exceed `Long.MAX_VALUE` after division by `DECIMAL_OF_VI_REWARD`. This requires very large accumulated vote counts and/or VI deltas over many voting cycles, which is a high bar under normal network economics but is not bounded by any explicit validation in this code — there is no check preventing `deltaVi.multiply(...)` from exceeding `Long.MAX_VALUE` before calling `.longValue()`. Given TRON's existing vote/freeze mechanics, an attacker would need extraordinary stake and a long time horizon, making exploitation currently impractical but not structurally prevented by the code.

### Recommendation
Replace `.longValue()` with `.longValueExact()` (as already done in `ResourceProcessor`/`EnergyProcessor`/`RepositoryImpl`) in both `VoteRewardUtil.computeReward` and `RewardViCalService.getNewRewardAlgorithmReward`, and replace the `reward += ...` accumulation with `Math.addExact`/`LongMath.checkedAdd` (consistent with the pattern already used in `WithdrawRewardProcessor.execute`) so an overflow throws an explicit `ArithmeticException`/contract-execution error rather than silently wrapping the reward total.

### Proof of Concept
Conceptual (cannot be executed without full node state):
1. An account votes for a witness and accumulates delegation such that the witness's VI (`getWitnessVi`) delta between `beginCycle-1` and `endCycle-1`, multiplied by the account's `voteCount`, divided by `DECIMAL_OF_VI_REWARD`, exceeds `Long.MAX_VALUE`.
2. The account (or any contract) calls the TVM reward-withdrawal opcode, invoking `WithdrawRewardProcessor.execute` → `VoteRewardUtil.withdrawReward` → `computeReward`.
3. `BigInteger.longValue()` silently truncates the oversized `BigInteger` result to a wrapped/incorrect `long`, which is added to the account's `allowance` via `adjustAllowance` and then paid out as TRX balance, corrupting the account's actual reward entitlement.

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);

    return result;
