## Title
Pause of vault interest accrual silently passes through instead of reverting, letting borrow/repay/deposit/redeem proceed on stale indexes - (File: local-testing/contracts/vault/vault-stx.clar)

### Summary
The external report's root issue is that a control the protocol relies on to make a risky state "safe" (a delegate to fix stuck bridge transfers) is optional and not enforced, so downstream logic (`execute`, `forceUpdateSlippage`) silently proceeds without the safety net, risking frozen funds. The same shape of bug exists in Zest's vault contracts: the `accrue` pause flag is supposed to gate index/liquidity-index updates, but when set, `accrue` does **not** revert — it silently returns the stale, pre-pause `index`/`lindex` as an `(ok ...)` success value [1](#0-0) . All hot-path callers (`system-borrow`, `system-repay`, `deposit`, `redeem`, `flashloan`, and `market.clar`'s `accrue-and-cache`) call `accrue` with `try!` and treat its `ok` result as fresh authoritative state, so pausing accrual does not stop those operations — it only silently freezes the interest-index bookkeeping while borrowing/repaying/depositing/redeeming continue on outdated numbers.

### Finding Description
In each vault contract (`vault-stx.clar`, `vault-sbtc.clar`, `vault-ststx.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-ststxbtc.clar`, and their mainnet `v0-vault-*` counterparts), `accrue` is defined as:

```clarity
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          ...
``` [2](#0-1) 

When the DAO sets `accrue: true` in `pause-states`, the function returns `(ok {...})` with the **old** cached index instead of returning an error. Every state-changing entry point in the vault begins by calling `(u (try! (accrue)))` and continues its logic unconditionally on the `ok` branch:

- `system-borrow` reads `(idx (var-get index))` and computes `scaled-amount` from it right after calling `accrue` [3](#0-2) .
- `flashloan` similarly calls `(try! (accrue))` before computing fees and moving funds [4](#0-3) .
- `deposit`/`redeem` (not shown in full above but same pattern) also gate on `accrue` succeeding, not reverting.

At the market layer, `accrue-and-cache` calls `vault-accrue` and unconditionally caches whatever indexes come back — stale or fresh — for the rest of the transaction/block:

```clarity
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [5](#0-4) 

This cached (possibly stale, pause-passed-through) index then feeds directly into debt/collateral notional valuation used for health checks in `borrow`, `repay`, `collateral-remove`, and `liquidate`:

```clarity
(debt-notional (if (> debt-scaled u0)
                   (let ((cached (unwrap-panic (accrue-and-cache asset-id)))
                         (ib (get index cached))
                         (actual (mul-div-up debt-scaled ib INDEX-PRECISION)))
                     (normalize (* actual price) decimals true))
                   u0))
``` [6](#0-5) 

Root cause, mirroring the report's "presence of delegate not enforced": the pause flag is meant to be the safety mechanism for freezing interest state during an emergency, but it is never actually enforced as a hard stop (revert) at any of the call sites that consume its result — every borrow/repay/deposit/redeem/liquidation health-check silently continues using whatever `accrue` handed back, with no distinct code path or documentation making clear that "paused accrue" means "stale index accepted as truth."

### Impact Explanation
This lands in the **temporary freezing of funds** / accounting-integrity impact class. If the DAO pauses `accrue` on a vault (e.g., during an incident requiring the interest curve/index update logic to be halted), all debt is still valued using the last successfully computed `index`/`lindex` instead of correctly-accrued values for the entire pause window, which may span many blocks. Since `index`/`lindex` monotonically increase in normal operation, borrowers' debt and depositors' collateral value are frozen at a stale, artificially favorable (undercounted debt) or unfavorable (undercounted collateral yield) snapshot for as long as the pause lasts — during that window, health checks (`is-healthy`, liquidation LTV) in `market.clar` operate on incorrect economic state, and legitimate withdrawals/liquidations can be blocked or mispriced, i.e., funds effectively frozen relative to their true value until accrual is unpaused and a big index jump is finally applied in one shot. This matches the class of bug flagged in the original report: an optional safety gate that is silently bypassed rather than enforced, producing frozen/misvalued funds rather than an outright revert that would force operators to address the root condition first.

### Likelihood Explanation
Likelihood is **medium**: this requires the DAO to actually set `accrue: true` in `pause-states` for a vault (a deliberate governance action, not attacker-triggered), so it is not exploitable by an ordinary user in isolation. However, once triggered, the silent pass-through is *automatic and unconditional* — every subsequent `borrow`, `repay`, `deposit`, `redeem`, `flashloan`, and `liquidate` call across the whole vault (and market, via `accrue-and-cache`) is affected without any additional preconditions, for the entire duration of the pause. This is analogous to the Connext finding: the vulnerable condition is not attacker-manufactured, but the absence of an enforced hard-stop means the "recovery" mechanism (pausing) does not actually protect the invariant it was designed to protect once relied upon.

### Recommendation
`accrue`, when paused, should either (a) cause `try!`-calling entry points (`system-borrow`, `system-repay`, `deposit`, `redeem`, `flashloan`, and market's `accrue-and-cache`) to revert instead of returning success with stale state, or (b) be documented explicitly and validated so that dependent health/valuation logic in `market.clar` is aware it is operating on a frozen index and applies compensating logic (e.g., blocking new borrows/liquidations while paused). At minimum, add explicit documentation of this pass-through behavior next to `pause-states` and to all call sites that treat `accrue`'s `ok` result as fresh state.

### Proof of Concept
1. DAO calls the vault's pause-setter to set `pause-states.accrue = true` on, e.g., `vault-usdc.clar`.
2. A user calls `market.clar`'s `borrow` for USDC. Internally this calls `accrue-user-debts` → `accrue-and-cache` → `vault-accrue` → `vault-usdc.accrue`, which (per lines 837-845 pattern in `local-testing/contracts/vault/vault-usdc.clar`) returns the **old** `index`/`lindex` in an `(ok ...)` wrapper instead of erroring [7](#0-6) .
3. `market.clar` caches this stale index via `accrue-and-cache` for the current `stacks-block-time` and uses it in `calculate-asset-notional-value` to value the user's existing USDC debt [6](#0-5) , and `borrow`/`system-borrow` computes new `scaled-amount` from the same stale `index` [8](#0-7) .
4. The transaction proceeds and succeeds end-to-end (no revert), even though the vault operator intended `accrue` to be halted — health checks, new debt scaling, and liquidation thresholds are all computed off stale interest-index data for as long as the pause remains active, misrepresenting real debt/collateral value and freezing accurate accounting until accrual is unpaused.
