## Finding

### Title
Value-pruner races ahead of the asynchronous position Merkle committer, deleting `PositionValueSchema` rows still referenced by an un-caught-up but proof-servable Merkle leaf - (File: `storage/aptosdb/src/position_pruner.rs`)

### Summary
The native-position value pruner's target version is driven purely by the ledger's overall committed/synced version inside `post_commit`, completely decoupled from how far the asynchronous position Merkle batch committer has actually persisted JMT checkpoints. There is no gate that keeps the value pruner from deleting a `PositionValueSchema` row until the Merkle side has advanced past the version that row backs. Under attacker-controlled high-throughput overwrites of the same native-position keys, this allows the value pruner to delete a value row that a still-persisted (and still proof-servable) Merkle leaf points to.

### Finding Description
`commit_native_position` synchronously writes every position write-op into `PositionDb` and the `stale_position_value_index` on every version — not just at checkpoint boundaries: [1](#0-0) 

The in-memory tree/tip is only advanced to actual JMT checkpoints, and even then via a separate async pipeline (`merklize_position` / `PositionMerkleCommit`), consumed from a rendezvous channel (`POSITION_BATCH_CHANNEL_SIZE = 0`) fully decoupled from `commit_native_position`: [2](#0-1) 

Immediately after `commit_native_position` returns (as part of the same `calculate_and_commit_ledger_and_state_kv` scope), `post_commit` activates the value pruner using the raw ledger-committed `version`, with no dependency on whether the Merkle batch committer has persisted the corresponding snapshot: [3](#0-2) 

The module-level doc comment in `position_pruner.rs` explicitly documents this split of responsibility with no coordination between the two: "the value pruner is driven from `commit_native_position`; the merkle pruners' from the position merkle batch committer": [4](#0-3) 

The `PositionValuePrunerManager`'s `maybe_set_pruner_target_db_version` only checks its own `prune_window`/`batch_size` against its own `min_readable_version` — it has no reference to the Merkle committer's persisted progress at all: [5](#0-4) 

The value pruner permanently deletes the *superseded* `(state_key_hash, stale_since_version-associated-version)` row from `PositionValueSchema` once its target passes it, as confirmed by the pruner's own tests (`position_pruner_removes_superseded_values_keeps_live`): [6](#0-5) 

Because a superseding write's stale-index entry is created the instant the *raw KV write* happens (in `commit_native_position`), while the Merkle tree only advances at checkpoint boundaries and via the separate async committer, an attacker who drives many rapid overwrites of the same native-position key across successive committed chunks can make the raw KV/stale-index progress (and hence the value-pruner's eligible target) run far ahead of the Merkle committer's actual persisted checkpoint version. If the Merkle committer is still lagging when it finally persists a checkpoint whose leaf backs an older version `V` of the key, but the value pruner has already advanced past `V + prune_window` and deleted `(key_hash, V)` from `PositionValueSchema`, the resulting Merkle root/proof for that checkpoint will validate cryptographically while the underlying value it points to is already gone from storage.

### Impact Explanation
This breaks the binding between an authenticated (Merkle-proof-backed) response and the actual committed value it is supposed to authenticate. A client or validator holding a valid state/Merkle proof for a persisted checkpoint would be unable to retrieve the value the proof claims exists, i.e., an authenticated response becomes unfulfillable/inconsistent with storage — a direct violation of "Authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object." This is a storage/proof integrity defect reachable purely from unprivileged transaction throughput (no operator misconfiguration is required beyond default/normal pruner configs), and it can silently corrupt the guarantees restore/replay and light-client-style proof consumers rely on.

### Likelihood Explanation
Reaching the race requires the attacker to generate a sustained sequence of overwrites to the same native-position key(s) across many committed versions/chunks fast enough that raw KV commit + stale-indexing (synchronous, in the hot commit path) outpaces the asynchronous Merkle snapshot committer, and for the pruner's `prune_window`/`batch_size` to be small enough (or throughput high enough) that the target crosses the still-unprocessed version before the Merkle side catches up. This is plausible under sustained high transaction throughput to a hot native-position key, which is realistic for a trading/exchange-style module (the "native trading position" feature this code implements), and does not require any privileged action — only ordinary transaction submission. Actual triggering, however, depends on runtime pruner configuration (`prune_window`, `batch_size`) and the depth of the Merkle committer's backlog, both of which are difficult to fully characterize from static code alone.

### Recommendation
Gate the value pruner's target version on the minimum of the ledger's synced version and the position Merkle committer's last-persisted version (mirroring how the main-state value pruner is expected to stay behind the state Merkle snapshot progress), rather than driving it solely from `commit_native_position`'s raw KV write progress. Concretely, expose the Merkle committer's persisted version (e.g., from `PositionMerkleCommit`/`position_snapshot_committer`) and clamp `position_pruner.value_pruner.maybe_set_pruner_target_db_version` to never exceed it minus the configured `prune_window`.

### Proof of Concept
Conceptual reproduction (based on the reviewed code paths, not executed):
1. Repeatedly submit transactions that overwrite the same native-position state key `K` across many consecutive committed chunks/versions (`V0 < V1 < ... < Vn`), forcing `commit_native_position` to write a fresh `PositionValueSchema` row and a `stale_position_value_index` entry for each overwrite synchronously in the hot commit path — [1](#0-0) .
2. Because `post_commit` immediately advances `value_pruner`'s target using the raw ledger `version` — [3](#0-2)  — while the separate, asynchronous Merkle snapshot committer is still processing/persisting an older checkpoint (e.g., at `V0`) — [2](#0-1)  — the value pruner deletes `(key_hash(K), V0)` from `PositionValueSchema` once its window is crossed.
3. Once the Merkle committer finally persists the checkpoint at `V0`, request a Merkle proof for `K` at version `V0`; the proof/root validates, but attempting to fetch the underlying value from `PositionValueSchema` at `(key_hash(K), V0)` fails because it was already pruned — reproducing the "proof authenticates a leaf whose underlying value is gone" scenario.

Note: I was unable to fully trace the exact leaf-version-encoding logic (`leaf_entry_to_jmt_update`) inside `aptos_storage_interface::state_store` to directly confirm the leaf's backing-version pointer format from within this repo's index; that crate's internals were not returned by search and would need direct inspection (e.g., via a full Devin session) to make the version-pointer correspondence airtight.

pub(crate) const POSITION_BATCH_CHANNEL_SIZE: usize = 0;

pub(crate) struct PositionSnapshotToCommit {

/// Advances `*last_snapshot` on success.
pub(crate) fn merklize_position(
    merkle_db: &PositionMerkleDb,
    ledger_db: &LedgerDb,
    last_snapshot: &mut PositionStateWithSummary,
    snapshot: PositionSnapshotToCommit,
) -> Result<PositionMerkleCommit> {
    let new_state = snapshot.snapshot;
    let version = new_state
        .version()
        .expect("snapshot enqueued for merklize must have a concrete version");
    let previous_epoch_ending_version = ledger_db
        .metadata_db()
        .get_previous_epoch_ending(version)?
        .map(|(v, _e)| v);
    let base_version = last_snapshot.version();

    let updates = new_state.make_delta(last_snapshot);

    let all_updates = pre_shard_jmt_updates(
        updates
            .iter()
            .map(|(key_hash, slot)| leaf_entry_to_jmt_update(*key_hash, slot)),
    );

    let (root_hash, _leaf_count, top_levels_batch, batches_for_shards) = merkle_db
        .merklize_snapshot(
            base_version,
            version,
            &last_snapshot.summary().global_state_summary,
            &new_state.summary().global_state_summary,
            all_updates,
            previous_epoch_ending_version,
        )
        .map_err(|e| AptosDbError::Other(format!("position JMT merklize_snapshot failed: {e}")))?;

    *last_snapshot = new_state.clone();

    Ok(PositionMerkleCommit {
        version,
        root_hash,
        batch: crate::common::MerkleBatch {
            top_levels_batch,
            batches_for_shards,
        },
        snapshot: new_state,
    })

    /// Sets pruner target version when necessary.
    fn maybe_set_pruner_target_db_version(&self, latest_version: Version) {
        let min_readable_version = self.get_min_readable_version();
        // Only wake up the state kv pruner if there are `ledger_pruner_pruning_batch_size` pending
        if self.is_pruner_enabled()
            && latest_version
                >= min_readable_version + self.pruning_batch_size as u64 + self.prune_window
        {
            self.set_pruner_target_db_version(latest_version);

#[test]
fn position_pruner_removes_superseded_values_keeps_live() {
    let (_tmp, db) = open_position_db();
    let key = position_key(1);
    let hash = key.hash();

    commit_at(&db, 0, vec![(key.clone(), upsert(b"v0"))]);
    commit_at(&db, 5, vec![(key.clone(), upsert(b"v5"))]);
    commit_at(&db, 10, vec![(key.clone(), upsert(b"v10"))]);

    let pruner = StateKvPruner::<PositionValue>::new(Arc::clone(&db)).unwrap();
    pruner.set_target_version(7);
    pruner.prune(100).unwrap();

    assert_eq!(pruner.progress(), 7);
    assert!(!value_exists(&db, hash, 0), "v0 value pruned");
    assert!(value_exists(&db, hash, 5), "v5 value retained");
    assert!(value_exists(&db, hash, 10), "v10 value retained");
    assert_eq!(
        stale_versions(&db, hash),
        vec![10],
        "only past-target row left"
    );
}
