### Title
Stale delayed `GlobalContractDistribution` receipt can panic `receipt_filter_fn` and halt a shard after repeated resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::pop`/`peek_iter` filter delayed receipts that survive a shard split by calling `receiver_shard_id` and `unwrap()`-ing the result, on the assumption that every receipt sitting in the delayed queue can always be remapped to a shard in the *current* shard layout. This is the same bug class as the Sherlock `Auction.sol` report: state left over from a previous "epoch" of the system (the unsettled auction / the pre-split delayed queue) is blindly consumed by later logic without checking whether it is still valid for the new context, and the two symptoms it can produce - permanently stuck value and, in this codebase, a shard-halting panic - map onto exactly the impacts this scan is looking for (frozen funds / transaction-triggered halt).

### Finding Description
`DelayedReceiptQueueWrapper::receipt_filter_fn` computes the receipt's target shard for the *current* `epoch_id`'s shard layout and unwraps the result unconditionally: [1](#0-0) 

This is invoked from `pop` (drains the delayed queue every chunk) and from `peek_iter` (used for contract-preparation lookahead): [2](#0-1) 

The design intentionally tolerates receipts belonging to a sibling shard right after *one* resharding split — the queue is duplicated across both children and receipts are discarded via this filter until they're all drained — as documented in `docs/architecture/how/resharding_v2.md` and the `cross-shard-congestion.md` spec (`receipt_filter_fn`, `congestion_control.rs:874`).

The regression test `test-loop-tests/src/tests/global_contracts_distribution.rs` (`delayed_receipts_repro_missing_trie_value`/global-contract-distribution split test) explicitly documents the failure mode this code guards against: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations"* — i.e. a `GlobalContractDistribution` receipt that is still sitting in the delayed queue can carry a `target_shard` that no longer exists in the shard layout after a *second* resharding event, at which point `receiver_shard_id()` returns an error and the surrounding `.unwrap()` panics, crashing the chunk-producing/validating node applying that chunk.

`GlobalContractDistribution` receipts are created from an ordinary, unprivileged `DeployGlobalContract` action a signer submits in a transaction (see `runtime-execution.md`: `action_deploy_global_contract`), so an attacker can arrange for such a receipt to be admitted into the delayed queue and then remain there across two consecutive resharding epochs by submitting it (or many of them, to saturate congestion and force delay) shortly before a scheduled resharding, without needing any validator or operator privilege.

The parallel to the `Auction.sol` report is structural: in `Auction.sol`, `_createAuction` blindly clears/overwrites the previous unsettled auction's state on `unpause()`, trusting stale state without validating it is still consistent with the new context, permanently losing the bid and token. Here, the delayed-receipt queue similarly carries state across a structural transition (resharding) that changes the meaning of `target_shard`, and the consuming code (`receipt_filter_fn`) trusts that stale entry to still resolve to a valid shard, `unwrap()`-ing instead of handling the mismatch.

### Impact Explanation
If the panic is actually reachable (which the test's docstring states is the specific vulnerability being repro'd), the impact is a transaction-triggered node/shard halt: any node applying the chunk that pops the stale receipt panics, which for chunk producers/validators processing that shard means chunk production/validation stops, i.e. a chain halt for that shard triggered purely by ordinary transaction activity (submitting a `DeployGlobalContract` action) combined with the deterministic resharding schedule. This matches the required "transaction-triggered halt" impact category.

### Likelihood Explanation
Reaching this requires: (1) a `GlobalContractDistribution` receipt getting delayed (achievable via ordinary congestion — an unprivileged signer can submit `DeployGlobalContract` and congest the target shard so the receipt is pushed into the delayed queue), and (2) that receipt surviving across *two* resharding generations without being drained. Resharding cadence and epoch length are protocol parameters outside a single attacker's control, so the practical likelihood depends on network conditions (how often resharding occurs and how fast the delayed queue drains). The existence of a dedicated regression test written specifically to reproduce this scenario indicates the nearcore team identified it as a genuine, previously-unhandled edge case; I could not fully verify from the available index whether the current `receiver_shard_id` implementation still fails to remap two generations back, or whether the current filtering logic was already patched to handle this (the test file's docstring describes what the panic looks like "if the vulnerability exists", suggesting the test is meant to assert it does *not* happen, i.e. this may already be fixed by the current `receipt_filter_fn`/`receiver_shard_id` implementation). I was not able to open `core/primitives/src/receipt.rs`'s `receiver_shard_id` body or the full resharding test file in this session to confirm definitively whether the fix is complete for the double-resharding case.

### Recommendation
- In `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874`), replace the `unwrap()` on `receiver_shard_id` with an explicit fallback: if the receipt's original target shard no longer exists in the current shard layout (i.e., it predates more than one resharding), deterministically remap it to whichever descendant shard now owns the relevant account/target range, or otherwise safely drop/re-route it without panicking.
- Ensure `receiver_shard_id`/`shard_layout` lookups account for shard ancestry across multiple resharding generations, not just the immediate parent-child relationship from a single split.
- Extend the existing `test_flat_storage_resharding`/global-contract-distribution repro tests to run through at least two resharding cycles while receipts remain queued, and assert no panic and correct routing, to close the gap the current test's docstring anticipates.

### Proof of Concept
1. Submit a `DeployGlobalContract` transaction as an ordinary account, causing a `GlobalContractDistribution` receipt with a fixed `target_shard`.
2. Congest the target shard (e.g., flood it with cheap transactions) so the receipt is pushed into the delayed-receipt queue instead of executing immediately.
3. Trigger/await a resharding event that splits the shard once, then trigger a second resharding before the delayed queue has drained the receipt (as exercised by `delayed_receipts_repro_missing_trie_value` and the global-contract-distribution split test in `test-loop-tests/src/tests/global_contracts_distribution.rs`).
4. When `process_delayed_receipts` calls `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` on the stale receipt, `receiver_shard_id()` is called against the shard layout current at the *second* resharding, which no longer has a slot for the receipt's original `target_shard`, and the `.unwrap()` panics, halting the node applying that chunk.     // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }
