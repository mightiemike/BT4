### Title
Unbounded fixed-length array declaration in `function_selector` triggers pre-metering huge memory allocation in `Util.parseMethod` → `AbiUtil.CoderArray.encode` - ([File: framework/src/main/java/org/tron/core/services/http/TriggerConstantContractServlet.java])

### Summary
`TriggerConstantContractServlet.doPost` calls `Util.parseMethod(selector, parameter)` to hex-encode a smart-contract call before any energy/bandwidth accounting or `VMActuator` validation happens. The ABI-encoding helper's `CoderArray.encode` method builds a `List<Coder>` sized to the **attacker-declared** fixed array length parsed straight out of the `function_selector` string (e.g. `foo(uint256[999999999])`), independent of how many actual values are supplied, so a tiny HTTP request can force allocation of hundreds of millions to billions of list entries.

### Finding Description
The request flow is: `TriggerConstantContractServlet.doPost` reads the body, calls `Util.checkBodySize`, `Util.validateParameter`, then extracts `function_selector`/`function_parameter` and calls `Util.parseMethod(selector, parameter)` [1](#0-0) . This happens **before** `wallet.createTransactionCapsule` / `wallet.triggerConstantContract`, i.e. before any VM energy accounting begins.

`Util.parseMethod` delegates to the ABI-encoding logic that parses the type list from the method signature via a regex `paramTypeArray = "^(.*)\\[([0-9]*)]$"` and, for a matched fixed-size array type, constructs a `CoderArray` with the declared `length` taken directly from the regex-captured digits with no upper bound check [2](#0-1) .

When `CoderArray.encode` runs, it first JSON-parses the caller-supplied array value(s), then — regardless of how many actual items were supplied — loops `this.length` times pushing the same `Coder` reference into an `ArrayList`:
```java
if (this.length == -1) {
  for (int i = 0; i < items.size(); i++) { coders.add(coder); }
} else {
  for (int i = 0; i < this.length; i++) { coders.add(coder); }
}
``` [3](#0-2) 

Because `this.length` is fully attacker-controlled (parsed from the type string, e.g. `999999999`), this loop and the underlying `ArrayList` backing-array growth allocate memory and burn CPU proportional to the declared length, not to the actual payload size. Only after this allocation does `pack(coders, items)` run and eventually throw an `IndexOutOfBoundsException` if `items.size() < coders.size()` [4](#0-3) . The damage (huge allocation/CPU stall) has already occurred by the time that exception fires, and it occurs entirely inside plain Java code with no TVM energy/bandwidth metering, no signature check, and no fee applied — all of which occur later, if at all, in `wallet.triggerConstantContract`.

The attacker payload needed is small: a `function_selector` string like `foo(uint256[999999999])` (tens of bytes) plus a minimal matching JSON array parameter such as `[1]`, easily well under whatever body-size limit `Util.checkBodySize` enforces. `RateLimiterServlet` rate limiting does not bound per-request CPU/memory cost, only request rate, so a low but nonzero rate of such requests can still exhaust node memory/CPU repeatedly.

Note: the `AbiUtil` class located during this investigation resides at `framework/src/test/java/.../AbiUtil.java`, a test-source path. I was unable to positively confirm within the available tool budget that the exact same class (or an identical copy in a main sourceset) is what `Util.parseMethod` in `framework/src/main/java/org/tron/core/services/http/Util.java` actually invokes at runtime, since a main-sourceset class normally cannot depend on test-sourceset code in a standard Gradle build. The vulnerable pattern (unbounded loop sized by attacker-declared array length, executed before any metering) is clearly present in the `AbiUtil` implementation found, and the question's call chain (`Util.parseMethod` → `AbiUtil` encoding) matches it exactly, but exact confirmation of the main-source call target would require deeper access than the indexed search provided.

### Impact Explanation
This is a DoS via RPC-API: an anonymous, unauthenticated HTTP client can force a full node to allocate gigabytes of heap and burn CPU cycles per request, with no TRON fee, energy, or bandwidth cost, because the cost is incurred entirely before the TVM/actuator layer that enforces those costs. Repeated requests can crash or freeze the node (OOM / GC thrashing / thread stall), affecting availability of `wallet/triggerconstantcontract` and related HTTP endpoints (`/wallet/estimateenergy`, `/wallet/triggersmartcontract` share the same `Util.parseMethod` call).

### Likelihood Explanation
No preconditions beyond the ability to send an HTTP POST to the node's public JSON-RPC/HTTP API (default configuration, no special account, no signed transaction required for `triggerconstantcontract`/`estimateenergy`). The attacker's cost is a single small HTTP request; the exploit is deterministic and repeatable at will, limited only by whatever generic per-IP rate limiter is applied to the servlet (which throttles request rate, not per-request cost).

### Recommendation
Enforce a strict upper bound (e.g. a small constant such as 1024 or whatever the largest realistic ABI array size is) on any array/tuple length parsed from the type string in `AbiUtil`'s array-type coder before performing any loop or allocation based on it, and reject `function_selector` strings whose declared array/tuple lengths exceed that bound with a clear validation error, before any encoding work is attempted. Additionally, validate that the declared length matches (or bounds) the actual number of supplied values before allocating any length-sized structures.
