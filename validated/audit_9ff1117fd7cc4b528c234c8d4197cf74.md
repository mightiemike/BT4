### Title
Unbounded `PendingInbounds.Walk` in `AfterBallotTerminal` hook allows attacker-inflated pending-inbound set to create unbounded per-vote gas cost - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
`BallotHooks.afterInboundBallotTerminal` performs a full linear scan (`Walk`) over the entire `PendingInbounds` collection every time any single INBOUND_TX ballot reaches a terminal state (EXPIRED, PASSED, REJECTED), in order to locate the entry that owns the terminating ballot ID. This callback fires synchronously and unconditionally from `MarkBallotExpired`/`MarkBallotFinalized` [1](#0-0) [2](#0-1) , which are invoked from ordinary vote processing paths reachable whenever a `MsgVoteInbound` is processed. Because `PendingInbounds` entries are created on the very first validator vote for any distinct `(source_chain, tx_hash, log_index)` triple — driven entirely by external, attacker-controllable source-chain activity — an attacker can inflate the size of `PendingInbounds` without bound simply by generating many distinct low-value/dust inbound events on any enabled source chain. This is directly analogous to the SmartSession `onUninstall()` bug class: a mandatory, non-skippable cleanup/callback whose cost scales linearly with attacker-inflated storage, with no upper bound enforced anywhere in the code.

### Finding Description
`RecordInboundVote` creates a new `PendingInboundEntry` keyed by `utx_key = sha256(source_chain:tx_hash:log_index)` on the first vote for any inbound, with no cap on the number of entries or variants [3](#0-2) . Each entry is created purely in response to external chain activity that an unprivileged user fully controls (any inbound deposit/tx on any enabled source chain, no matter how small), and each entry persists until its ballot(s) reach a terminal state (pass, reject, or the `DefaultExpiryAfterBlocks` timeout) [4](#0-3) .

When any ballot (belonging to any entry, not necessarily the attacker's) becomes terminal, `afterInboundBallotTerminal` is invoked and performs an O(n) `Walk` across **all** `PendingInbounds` entries to find which entry's variant carries the given `ballotID`, because the map is keyed by `utx_key` rather than by `ballot_id`:

```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [5](#0-4) 

The code comment explicitly (and incorrectly, from a threat-model standpoint) assumes the set is "small and transient" [6](#0-5) , but nothing enforces that assumption — an attacker can keep the set large indefinitely by continuously generating new distinct inbound events faster than they expire, or by exploiting the `DefaultExpiryAfterBlocks` window to keep many entries alive simultaneously.

This hook is fired unconditionally from `MarkBallotExpired`/`MarkBallotFinalized` and hook errors are explicitly swallowed rather than aborting the state transition [7](#0-6) , meaning it cannot be skipped, but it also cannot fail — it can only become arbitrarily expensive. Because it executes inside ordinary consensus-critical transaction processing (any `MsgVoteInbound`/`MsgVoteOutbound` submission that causes a ballot to terminate), the cost is paid deterministically by every validator executing that block.

### Impact Explanation
This does not by itself steal or freeze funds, but it maps to the "denial of service ... reachable without privileged control" allowed impact category. An attacker who is a completely unprivileged external user (they only need to trigger cheap/dust deposit events on any enabled source chain observed by honest Universal Validators) can grow `PendingInbounds` without bound. Once the set is large, every terminal ballot transition — which happens continuously as part of ordinary honest-validator operation — pays an O(n) cost. As n grows, this can:
- Significantly inflate per-transaction gas/CPU cost for `MsgVoteInbound` processing across all validators,
- In the worst case exceed block gas/time budgets, causing block-production stalls or making certain blocks impossible to process within expected timing, a network-wide liveness degradation triggered by an unprivileged user rather than a privileged/malicious validator.

This is the direct structural analog of the `onUninstall()` finding: an operation with attacker-controllable, unbounded storage-driven cost embedded in a mandatory execution path.

### Likelihood Explanation
Likelihood is moderate to high in principle: generating many distinct inbound events (different tx hashes / log indices, even of dust value) on a supported source chain is cheap for an attacker, and nothing in `RecordInboundVote` or `VoteInbound` throttles the number of concurrent `PendingInbounds` entries per account/chain. The severity of the resulting DoS depends on how large `n` can practically grow within the ballot expiry window (`DefaultExpiryAfterBlocks`) and how many chains/validators are actively voting, which would require load-testing to fully quantify.

### Recommendation
- Re-key `PendingInbounds` (or add a secondary index) by `ballot_id -> utx_key` so `afterInboundBallotTerminal` can do an O(1) lookup instead of a full-collection scan.
- Alternatively/additionally, enforce a hard cap on the number of concurrently outstanding `PendingInbounds` entries or variants per source chain/sender, rejecting or rate-limiting new inbound votes once the cap is reached.
- Add monitoring/alerting on `PendingInbounds` collection size so operators can detect abnormal growth before it becomes an operational issue.

### Proof of Concept
1. An attacker submits (or causes honest UVs to observe) a large number `N` of distinct dust inbound transactions on an enabled source chain, each with a unique `tx_hash`/`log_index`, so that each vote creates a new distinct `PendingInboundEntry` via `RecordInboundVote` [8](#0-7) .
2. `PendingInbounds` now holds `N` entries, all legitimately created via the normal `MsgVoteInbound` path.
3. Any single one of these ballots (or an unrelated ballot) reaches a terminal state (pass, reject, or expiry) during normal validator voting, invoking `MarkBallotExpired`/`MarkBallotFinalized` → `fireBallotTerminalHook` → `AfterBallotTerminal` → `afterInboundBallotTerminal` [9](#0-8) .
4. `afterInboundBallotTerminal` walks all `N` entries in `PendingInbounds` to find the matching ballot, an O(N) operation executed synchronously as part of that transaction's state transition [10](#0-9) .
5. As `N` is repeatedly grown by the attacker and multiple ballots terminate per block, the aggregate per-block cost of this hook scales with `N × (terminal ballots per block)`, unbounded, mirroring the unbounded-gas structure of the referenced `onUninstall()` finding.

Note: I was unable to fully trace the exact call sites in `x/uvalidator/keeper/voting.go` that invoke `MarkBallotExpired` during ordinary vote processing (vs. only via a background sweep), so the precise per-block amplification factor (how many ballots can terminate in a single block) could not be fully confirmed within the available tool budget; this would need to be verified in `x/uvalidator/keeper/voting.go` and `x/uvalidator/keeper/keeper.go` before finalizing severity.

func (k Keeper) RecordInboundVote(
	ctx context.Context,
	inbound types.Inbound,
	voter string,
	ballotID string,
) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	height := uint64(sdkCtx.BlockHeight())
	utxKey := types.GetInboundUniversalTxKey(inbound)

	entry, err := k.PendingInbounds.Get(ctx, utxKey)
	if err != nil && !errors.Is(err, collections.ErrNotFound) {
		return err
	}
	if errors.Is(err, collections.ErrNotFound) {
		entry = types.PendingInboundEntry{
			UtxKey:          utxKey,
			CreatedAtHeight: height,
		}
	}

	// Find or create the variant for this ballot.
	variantIdx := -1
	for i, v := range entry.Variants {
		if v.BallotId == ballotID {
			variantIdx = i
			break
		}
	}
	if variantIdx < 0 {
		entry.Variants = append(entry.Variants, types.InboundVariant{
			BallotId:           ballotID,
			Inbound:            &inbound,
			Voters:             []string{voter},
			FirstVotedAtHeight: height,
			LastVotedAtHeight:  height,
			TerminalStatus:     uvalidatortypes.BallotStatus_BALLOT_STATUS_PENDING,
		})
	} else {
		v := &entry.Variants[variantIdx]
		// Idempotent voter add.
		already := false
		for _, x := range v.Voters {
			if x == voter {
				already = true
				break
			}
		}
		if !already {
			v.Voters = append(v.Voters, voter)
		}
		v.LastVotedAtHeight = height
	}

	k.Logger().Debug("inbound vote recorded",
		"utx_key", utxKey,
		"ballot_id", ballotID,
		"voter", voter,
		"variant_count", len(entry.Variants),
	)
	return k.PendingInbounds.Set(ctx, utxKey, entry)
}

func (k Keeper) VoteInbound(ctx context.Context, universalValidator sdk.ValAddress, inbound types.Inbound) error {
	// Canonicalize first so every derived key + the stored inbound use one
	// representation per logical event.
	inbound.Canonicalize()

	k.Logger().Info("vote inbound received",
		"validator", universalValidator.String(),
		"source_chain", inbound.SourceChain,
		"tx_hash", inbound.TxHash,
		"tx_type", inbound.TxType.String(),
		"sender", inbound.Sender,
	)

	// Check inbound enabled before any state changes
	enabled, err := k.uregistryKeeper.IsChainInboundEnabled(ctx, inbound.SourceChain)
	if err != nil {
		return errors.Wrap(err, "failed to check inbound enabled")
	}
	if !enabled {
		k.Logger().Warn("vote inbound rejected: chain inbound disabled", "source_chain", inbound.SourceChain)
		return fmt.Errorf("inbound is disabled for chain %s", inbound.SourceChain)
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Step 1: Derive UTX key from the original inbound data (source_chain:tx_hash:log_index)
	universalTxKey := types.GetInboundUniversalTxKey(inbound)
	found, err := k.HasUniversalTx(ctx, universalTxKey)
	if err != nil {
		return errors.Wrap(err, "failed to check UniversalTx")
	}
	if found {
		k.Logger().Warn("vote inbound rejected: utx already exists", "utx_key", universalTxKey)
		return fmt.Errorf("universal tx with key %s already exists", universalTxKey)
	}

	// use a temporary context to not commit any ballot state change in case of error
	tmpCtx, commit := sdkCtx.CacheContext()

	// Step 2: Record this validator's vote in the per-utx PendingInbounds entry
	// (variant-aware audit trail). Each unique Inbound payload becomes its own
	// variant; multiple variants per utx_key indicate validator divergence.
	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return errors.Wrap(err, "failed to derive inbound ballot key")
	}
	if err := k.RecordInboundVote(tmpCtx, inbound, universalValidator.String(), ballotKey); err != nil {
		return err
	}

	// Step 3: Vote on inbound ballot (uses the original inbound data as-is for the ballot key,
	// so UVs that observe different field data will correctly produce different votes)
	isFinalized, _, err := k.VoteOnInboundBallot(tmpCtx, universalValidator, inbound)
	if err != nil {
		return errors.Wrap(err, "failed to vote on inbound ballot")
	}

	commit()

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
