### Title
Rejected L1 handler transactions become permanently un-proposable, causing L1→L2 messages to become stuck without automatic retry - (File: `crates/apollo_l1_events/src/transaction_manager.rs`, `crates/apollo_l1_events/src/transaction_record.rs`)

### Summary
The `L1EventsProvider`/`TransactionManager` tracks each L1→L2 message (`L1HandlerTransaction`) via a `TransactionRecord` state machine. When a proposed block containing an L1 handler transaction fails to execute (an `Err` result from the transaction executor, e.g. a `TransactionExecutorError::StateError`), the transaction hash is placed in `rejected_tx_hashes` and, on commit, `TransactionManager::commit_txs` calls `TransactionRecord::mark_rejected`, which sets the record's state to `TransactionState::Rejected` permanently. `is_proposable()` only returns `true` for `TransactionState::Pending`, and there is no code path that ever transitions a `Rejected` record back to `Pending`. Consequently the transaction is permanently removed from the `proposable_index` and can never be proposed/committed again by any (honest) sequencer, even though the underlying L1 message was never consumed. This is structurally analogous to the reported bridge bug: a receiver-side gate (`whenNotPaused` there, `is_proposable()`/`Rejected` state here) causes messages that fail once to be permanently undeliverable, with no automatic retry — the only path to "recovery" is an out-of-band, manual action on L1 (cancel/resend), exactly like the Wormhole report's "restart the entire process from the source chain."

### Finding Description
- `TransactionRecord::mark_rejected` (`crates/apollo_l1_events/src/transaction_record.rs:63-72`) sets `self.state = TransactionState::Rejected` and `self.rejected = true`, with no code anywhere reverting this back to `Pending`. [1](#0-0) 
- `is_proposable()` (`crates/apollo_l1_events/src/transaction_record.rs:155-157`) is the sole gate used by `maintain_indices` to decide whether a transaction stays in the `proposable_index` (the structure `get_txs` scans to select L1 handler transactions for future blocks). It only matches `TransactionState::Pending`. [2](#0-1) 
- `TransactionManager::maintain_indices` (`crates/apollo_l1_events/src/transaction_manager.rs:377-408`) removes the transaction from `proposable_index` once `record.is_proposable()` is false — this is permanent for `Rejected` transactions, since nothing sets the state back to `Pending`. [3](#0-2) 
- `TransactionManager::commit_txs` (`crates/apollo_l1_events/src/transaction_manager.rs:147-166`) is the call site that marks any transaction hash appearing in `rejected_txs` as rejected, on every block commit. [4](#0-3) 
- The comment in the sequence diagram (`docs/diagrams/06-l1-handler-flow.md:178-181`) explicitly documents the intended behavior as "For rejected txs: Unstage, keep as Pending" — but the actual implementation sets state to `Rejected`, not `Pending`, contradicting the documented design intent and confirming this is a genuine implementation bug rather than intended behavior. [5](#0-4) 
- The origin of a "rejected" hash is any execution `Err` outcome in `collect_execution_results_and_stream_txs` (`crates/apollo_batcher/src/block_builder.rs:708-716`), which is reachable purely from block execution results — this can happen for a legitimate L1 message under transient conditions (e.g., a state error caused by concurrent/adversarial contract state at execution time, not a message defect). [6](#0-5) 

### Impact Explanation
An L1→L2 message (e.g., a token bridge deposit consumed via an L1 handler entry point) that is rejected exactly once (for any transient reason during execution) is permanently excluded from `proposable_index` and can never be automatically retried by the sequencer network — matching the bug class described in the report: no automatic retry, permanent failure state. Since the message's associated L1-side state (its L1→L2 message hash on the core contract) is not resolved by this rejection (the record is neither committed nor consumed), the user's funds/message become stuck on L1 indefinitely unless a separate, manual/off-chain recovery path (canceling the message on L1 after the cancellation timelock and resubmitting) is invoked. This is a freezing-of-funds condition reachable purely by a normal, unprivileged L1 message sender whose L1 handler transaction happens to fail once during sequencer execution (e.g., due to a race with other state-affecting transactions), with no way to force reinstatement of the message through the standard flow.

### Likelihood Explanation
Likelihood is Medium: triggering requires that an L1 handler transaction's *execution* itself returns an `Err` from the executor (not merely a Cairo-level revert, which is handled as `Ok` with `revert_error` and does NOT get rejected/removed). Such executor-level errors are expected to be rare but can occur legitimately (e.g., contract or state issues at execution time, `StateError::OutOfRangeContractAddress`, or other executor-level errors reachable without any privileged actor). No malicious operator/proposer/relayer collusion is required — any legitimate L1 message can hit this if it collides with a transient executor error.

### Recommendation
Change the rejection handling for L1 handler transactions to match the documented design intent (docs/diagrams/06-l1-handler-flow.md): keep rejected L1 handler transactions in `TransactionState::Pending` (or an explicit new "retryable" state that is included in `is_proposable()`), so they remain in the `proposable_index` and get automatically retried in subsequent blocks, instead of transitioning permanently to `TransactionState::Rejected`. If a `Rejected` terminal state is genuinely desired for some class of errors (e.g., unrecoverable state errors), add a bounded automatic retry/backoff mechanism and/or an explicit admin-triggered re-queue path, and ensure telemetry/alerts fire when a message enters the permanently-rejected state so operators can react before funds become unrecoverable.

### Proof of Concept
1. An L1 message is sent, scraped, and becomes a `Pending` `L1HandlerTransaction` record in the `TransactionManager` (`add_tx`).
2. A sequencer proposes a block including this L1 handler transaction (`get_txs` → `try_mark_staged`).
3. During block execution, the transaction execution returns `Err(...)` from the transaction executor (e.g. `TransactionExecutorError::StateError`) — see `collect_execution_results_and_stream_txs`, which inserts the tx hash into `execution_data.rejected_tx_hashes`.
4. On block commit, `TransactionManager::commit_txs` is called with this hash in `rejected_txs`, invoking `TransactionRecord::mark_rejected`, setting `state = TransactionState::Rejected`.
5. `maintain_indices` observes `is_proposable() == false` (state is `Rejected`, not `Pending`) and removes the transaction hash from `proposable_index`.
6. No code path in `transaction_manager.rs` or `transaction_record.rs` ever sets `state` back to `Pending` for a `Rejected` record; `get_txs` can therefore never select this transaction again, and it will never be included/committed in any future block by any honest sequencer.
7. The corresponding L1 message on the core contract remains unconsumed; the only recovery is the separate, manual L1 cancellation process — i.e., "restart the entire process from the source chain," exactly matching the reported bug class.

        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],

        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();

                // We haven't scraped this tx yet, so it isn't indexed.
                return;
            };

            let tx_hash = hash;
            // Check if we need to add this tx to the proposable index.
            if record.is_proposable() {
                // Assumption: txs will only be added to the index once, on arrival, so this
                // preserves arrival order.
                let tx_hashes = self.proposable_index.entry(scrape_timestamp).or_default();
                if !tx_hashes.contains(&tx_hash) {
                    tx_hashes.push(tx_hash);
                }
            } else {
                // This tx needs to be removed from the proposable index if it was on it.
                // Remove from the vec for this timestamp, and drop the entry if it becomes empty.
                match self.proposable_index.entry(scrape_timestamp) {

                            tx_hashes.remove(index_in_vec);
                            if tx_hashes.is_empty() {
                                entry.remove();
                            }
                        }
                    }
