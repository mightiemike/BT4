### Title
Truncating overflow in legacy (default-active) resource usage/energy-limit multiply-before-divide arithmetic - ([File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java], [File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java], [File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
The legacy (default) bandwidth/energy accounting formulas in `ResourceProcessor`, `EnergyProcessor`, and `RepositoryImpl` compute `usage * precision / windowSize`-style ratios using plain Java `long` arithmetic, performing the multiplication before the division exactly like the reported `reward * ACC_TOKEN_PRECISION / lpSupply` pattern in `ComplexRewarder.sol`. Java `long` silently wraps on overflow (no exception), so a sufficiently large intermediate product truncates/wraps instead of throwing, corrupting the resulting usage/limit value. The team has already written a `BigInteger`-based "hardened" replacement for every one of these call sites, but the fix is gated behind the on-chain governance flag `ALLOW_HARDEN_RESOURCE_CALCULATION` (`ProposalType` code 97), which defaults to `0` (disabled) in both `DynamicPropertiesStore.getAllowHardenResourceCalculation()` and `reference.conf`, so the unsafe legacy path remains the actual runtime behavior until a committee proposal activates the flag.

### Finding Description
`RepositoryImpl.increase()` (non-hardened branch) computes: [1](#0-0) 
using `lastUsage * precision` and `usage * precision` as plain `long` multiplications before dividing by `windowSize`, whereas the "hardened" branch right above it explicitly does the same computation in `BigInteger` to avoid overflow: [2](#0-1) 

The same multiply-before-divide pattern with a legacy `long`-only fallback recurs in `ResourceProcessor.increaseV2()`, `unDelegateIncreaseV2()`, and `getUsage()`: [3](#0-2) [4](#0-3) 

and in `EnergyProcessor.calculateGlobalEnergyLimit()`/`scaleByRate()`: [5](#0-4) 

All of these have a `hardenCalculation()`/`hardenResourceCalculation()` guard that switches to the safe `BigInteger` implementation, gated on `dynamicPropertiesStore.allowHardenResourceCalculation()`: [6](#0-5) 

The flag itself defaults to `0` (unactivated) both in code and configuration: [7](#0-6) [8](#0-7) 

It can only be turned on by a super-representative committee proposal via `ProposalUtil.validator` case `ALLOW_HARDEN_RESOURCE_CALCULATION`: [9](#0-8) 

This is a direct structural analog of TRST-M-4: the correct, overflow-safe (`BigInteger`) formula exists in the codebase, but the code path exercised by default for every ordinary user transaction (freeze/unfreeze, resource delegation, TVM contract energy accounting) is the unsafe `long`-multiplication formula that can silently truncate on overflow rather than raising an error, exactly matching the report's root cause ("this calculation is not safe under N-bit math").

### Impact Explanation
If `usage`/`lastUsage` (bandwidth/energy point counters) or `frozeBalance`/`totalLimit`/`totalWeight` combinations produce a product exceeding `Long.MAX_VALUE` before division, the legacy path silently wraps to an incorrect (potentially negative or drastically smaller/larger) value rather than throwing, corrupting a user's or contract's resource usage window, remaining energy/bandwidth limit, or window size. Because these values gate how much bandwidth/energy an account is allowed to consume for free (i.e., how much of the network's shared resource pool it can draw from without paying TRX), a truncation-induced miscalculation can let an account use more resources than it is entitled to (analogous to reward leakage), or conversely under-credit legitimate accounts. The tests already written by the team (`CalculateGlobalLimitHardenTest`, `RepositoryImplHardenTest`) demonstrate concretely that the legacy path produces different (incorrect) results from the correct `BigInteger` computation under adversarial-but-realistic magnitudes, and that the hardened path throws `ArithmeticException` in the same scenarios — proving the legacy default path does not detect the overflow and instead returns a wrong value silently.

### Likelihood Explanation
This code executes on every ordinary, unprivileged user action that touches bandwidth/energy accounting — freezing/unfreezing TRX, delegating/undelegating resources, and any TVM contract call that consumes energy — via `ResourceProcessor`, `EnergyProcessor`, and `RepositoryImpl` (the VM's resource repository). No special privilege is required to trigger the vulnerable arithmetic; only sufficiently large `usage`/`frozeBalance`/weight values are needed, which is governed by chain-wide totals (`totalEnergyWeight`, `totalNetWeight`) that individual large stakers or accumulated network growth can push toward the danger zone over time, and which the project's own hardening tests demonstrate are reachable overflow inputs.

### Recommendation
Activate `ALLOW_HARDEN_RESOURCE_CALCULATION` by committee proposal (or make the `BigInteger`-based safe computation unconditional/default rather than opt-in) so the exact-arithmetic path in `ResourceProcessor`, `EnergyProcessor`, and `RepositoryImpl` is always used, removing reliance on a governance vote to fix an already-identified, already-patched-in-code overflow class.

### Proof of Concept
Reference the project's own regression tests that reproduce divergence/overflow between the legacy and hardened paths for the same code under test: [10](#0-9) [11](#0-10) 
These tests set `totalEnergyLimit`/`totalWeight`/`frozeBalance` (or `usage`/`totalWeight`/`totalLimit`) to adversarial magnitudes (e.g., `Long.MAX_VALUE / 2` and `Long.MAX_VALUE / 4`), toggle `saveAllowHardenResourceCalculation(0)` (the default/legacy path), and show the legacy `long`-multiplication formula produces a silently wrong (non-thrown, non-matching) result versus the `BigInteger` path, while the hardened path correctly throws `ArithmeticException` — confirming the legacy default path is vulnerable to the same truncation-via-overflow root cause described in TRST-M-4.
