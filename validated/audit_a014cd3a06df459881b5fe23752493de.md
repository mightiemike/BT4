### Title
Stack buffer overflow / panic-based DoS in `BytesAsHex` fixed-size array deserialization via unchecked sequence index - (File: `crates/starknet_api/src/serde_utils.rs`)

### Summary
`BytesAsHex<N, PREFIXED>`, the generic fixed-size byte array type used throughout `starknet_api` for hashes, addresses, and other core `felt`/`u256`-like fields (`ClassHash`, `ContractAddress`, `TransactionHash`, `EthAddress`, etc. — see usages in `crates/starknet_api/src/core.rs`, `crates/starknet_api/src/transaction/fields.rs`, `crates/starknet_api/src/block.rs`), deserializes via a custom `Visitor` when the wire format is non-human-readable (e.g. binary formats used for storage/internal serialization).

### Finding Description
The `visit_seq` implementation writes into a fixed-size stack array without ever checking that the write index stays within bounds: [1](#0-0) 

```rust
let mut res = [0u8; N];
let mut i = 0;
while let Some(value) = seq.next_element()? {
    res[i] = value;
    i += 1;
}
```
This loop keeps consuming elements from the deserializer's sequence for as long as the underlying format reports more elements, and unconditionally indexes `res[i]` — there is no `if i >= N { break/error }` guard. This is directly analogous to the reported CVE-2025-52292 bug class: a fixed-size buffer filled from attacker-controlled input length without a bounds check, causing an out-of-bounds write (in Rust, this manifests as an immediate array-index panic rather than silent memory corruption, but the effect — an uncontrolled crash triggered purely by malformed/oversized input — is the same DoS primitive).

The non-human-readable path is selected whenever `deserializer.is_human_readable()` is false: [2](#0-1) 

Any binary (non-JSON) deserialization of a `starknet_api` type containing a `BytesAsHex<N,_>` field — such as `ClassHash`, `ContractAddress`, `EthAddress`, `TransactionHash`, or block/commitment hash fields defined in `crates/starknet_api/src/core.rs` and `crates/starknet_api/src/block.rs` — that is fed a sequence with more than `N` elements will panic inside `res[i] = value`.

### Impact Explanation
A panic triggered while deserializing a value derived from a submitted transaction, declared class, or L1 message on any component that deserializes these types with a binary (non-human-readable) serializer (e.g. internal component-to-component binary channels, storage encodings) would crash that sequencer process. Per the rules of this analog scan, this can constitute a network unable to confirm new transactions if the affected code path is reachable from unprivileged input before/during validation, execution, or storage of a transaction whose fields are decoded through the binary/non-human-readable path.

However, I could not conclusively confirm, within the scope of this investigation, that any attacker-controlled binary (bincode/bytes) deserialization path — as opposed to the JSON/human-readable RPC and gateway ingestion path, which uses `bytes_from_hex_str` and is properly bounds-checked — actually decodes `BytesAsHex` fields directly from raw, unprivileged network bytes without an outer length-checked framing/schema (e.g. MDBX storage records are typically produced by the node itself, not attacker-supplied). The grep results show `BytesAsHex`-typed fields used pervasively in `starknet_api` core types, `apollo_storage/src/serialization/serializers.rs`, and protobuf converters, but I was unable to fully trace, within remaining budget, whether any of those binary encoders/decoders are exercised on attacker-supplied byte sequences with a sequence length attacker controls (as opposed to fixed schemas where the encoder itself always emits exactly `N` bytes).

### Likelihood Explanation
Medium-Low, contingent on verification: the vulnerable code itself is real and unconditionally reachable via any non-human-readable deserialization of these ubiquitous types, but the analog's severity depends on whether an external, unprivileged sender can control the *number* of sequence elements decoded (not just their values) at one of these binary boundaries. If such a boundary exists on the transaction/class/L1-message ingestion path, the likelihood is high, since supplying an oversized encoded sequence for any `ClassHash`/`ContractAddress`/hash field is trivial for an attacker.

### Recommendation
Add a bounds check in `visit_seq` so any element beyond index `N-1` is treated as a deserialization error rather than an out-of-bounds panic, e.g.:
```rust
while let Some(value) = seq.next_element()? {
    if i >= N {
        return Err(serde::de::Error::invalid_length(i + 1, &self));
    }
    res[i] = value;
    i += 1;
}
if i != N {
    return Err(serde::de::Error::invalid_length(i, &self));
}
```

### Proof of Concept
Not independently verified end-to-end due to inability to confirm a fully attacker-reachable binary deserialization entry point within the remaining investigation budget. Conceptually: construct a binary-encoded (non-human-readable) sequence for a `BytesAsHex<32, _>`-backed field (e.g. `ClassHash`) containing more than 32 elements and feed it to any deserializer path that decodes such a type from untrusted bytes; the `visit_seq` loop will index `res[32]` on a `[u8; 32]` array and panic, crashing the process handling that input. Further work is needed to identify and confirm a concrete unprivileged entry point (e.g. a specific p2p/storage binary decode call) that reaches this exact code without an enclosing length-checked envelope, before this can be asserted as more than a plausible-but-unconfirmed reachable bug per the strict validation rules.
