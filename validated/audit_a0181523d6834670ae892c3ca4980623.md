### Title
Wall-clock resource budget in Nakamoto block-proposal validation lets signers non-deterministically diverge on the same block - (File: `stackslib/src/net/api/postblock_proposal.rs`, `clarity/src/vm/resource_limiter.rs`)

### Summary
This is a wall-clock analog of the AnteTest gas-DoS class: instead of an insufficient-gas try/catch producing a false "test failed" verdict, an insufficient wall-clock `ResourceBudget` in Stacks signer block-proposal validation can non-deterministically produce a false "problematic transaction" verdict on an otherwise valid block. Because the timeout is measured in real time rather than a deterministic cost metric, different signers validating the *identical* block proposal can reach different accept/reject verdicts depending on transient machine load, causing a temporary tip/validation-verdict disagreement across the signer set.

### Finding Description
Nakamoto block-proposal validation (used by stacks-signer nodes, not full consensus replay) enforces per-transaction wall-clock limits via `TransactionResourceBudgets`/`ResourceBudget`: [1](#0-0) 

These budgets are backed by `TimeTracker::MaxTime`, which measures real elapsed time (`Instant::elapsed()`) against a configured `max_duration`, explicitly documented as being used only on "non-consensus voting paths: block assembly (mining) and block-proposal validation (signers)": [2](#0-1) [3](#0-2) 

When this deadline elapses mid-execution, the transaction fails with `RejectedRuntimeTxError::ExecutionResourceBudgetExceeded`, which is treated as a "problematic" transaction and propagates up to reject the entire block proposal, blaming that transaction's txid: [4](#0-3) [5](#0-4) 

The equality this breaks is: *"the same block proposal must produce the same validation verdict for every honest signer."* Because `check_not_expired` compares real elapsed time (not a deterministic cost counter), the verdict for a transaction whose true execution time sits near the configured `block_proposal_max_tx_execution_time_secs` boundary depends on each signer's CPU speed, concurrent I/O, and system load at the moment of validation — not on any property of the block itself. A miner (who does not need special privileges beyond normal block proposal) can include a contract call intentionally engineered to execute close to that boundary (e.g., a Clarity loop whose real time is sensitive to allocator/GC/other host noise while its consensus-critical cost-budget usage stays comfortably under the deterministic `ExecutionCost` limit). Signers under heavier concurrent load (which the same call across the network is exposed to non-uniformly, e.g. signers also relaying/verifying other messages) will time out and reject the proposal (`ValidateRejectCode`, txid blamed), while faster/idle signers will accept it, exactly mirroring how a limited-gas call in the reported AnteTest bug produced a false "test failed" outcome for some observers and not others.

### Impact Explanation
This falls under the allowed "temporary tip disagreement" / "validation verdict two nodes disagree on" class. A split verdict among signers around the 70% signing-weight threshold can stall block approval or cause some signers to sign a competing/absent proposal, producing transient chain-tip disagreement and reduced liveness. It does not directly cause loss of funds or a permanent chain split because the resource budget is intentionally out-of-consensus (deterministic `ExecutionCost` limits still gate full-node replay/consensus, per the code's own documentation), which the codebase authors were clearly aware of ("This is NOT related to cost tracking...defense-in-depth"). This bounds the severity below Critical.

### Likelihood Explanation
Any block-proposing miner can unprivileged-ly submit a transaction whose real execution time straddles the configured `block_proposal_max_tx_execution_time_secs`/`block_proposal_max_tx_analysis_time_secs` thresholds; no majority collusion or privileged key is required to trigger divergence — only ordinary variance in signer hardware/load, which is realistic in a decentralized signer set with heterogeneous node specs. The project's own test suite (`test_block_proposal_validation_execution_time_expired_blames_tx`, `test_block_proposal_validation_analysis_time_expired_blames_tx`) confirms this timeout path is reachable and directly rejects block proposals: [6](#0-5) [7](#0-6) 

However, exploiting the *cross-signer divergence* specifically (rather than a single, uniformly-observed timeout) requires timing that lands consistently near the boundary across a heterogeneous fleet, which the analog scan should flag as a design risk but which is harder to guarantee deterministically than the original gas-based AnteTest exploit (which is fully deterministic per EVM semantics). This is why the class is rated High rather than Critical, consistent with the reported bug's own "High" (rather than Critical) rating.

### Recommendation
- Short term: Ensure any transaction/block rejected purely due to `ExecutionResourceBudgetExceeded`/`AnalysisResourceBudgetExceeded` during block-proposal validation is retried with a generous grace margin (or an unlimited budget) before a signer casts a final rejection vote, so that transient local load cannot manufacture a rejection that other signers would not produce for the same block.
- Consider widening the default `block_proposal_max_tx_execution_time_secs`/`block_proposal_max_tx_analysis_time_secs` margins well above worst-case expected execution relative to the deterministic Clarity cost limits, so wall-clock timeouts are only ever a true defense-in-depth backstop and not a routinely reachable boundary.
- Long term: Replace/augment wall-clock gating in the signer voting path with a deterministic proxy (e.g., a stricter, still-non-consensus cost-based pre-check) so that "problematic" classification does not depend on the validating machine's transient performance.

### Proof of Concept
1. A miner crafts a Clarity contract call whose real (wall-clock) execution time is engineered to sit just under/over typical `block_proposal_max_tx_execution_time_secs` values (default settings; see `stackslib/src/config/mod.rs` fields `block_proposal_max_tx_execution_time_secs`/`block_proposal_max_tx_analysis_time_secs`) while remaining well within the deterministic `ExecutionCost` (`BLOCK_LIMIT_MAINNET_*`) budget that governs consensus-critical replay.
2. The miner proposes a Nakamoto block containing this transaction.
3. Each signer independently calls `NakamotoBlockProposal::validate`, which runs the transaction through `TransactionResourceBudgets::from_settings` → `ResourceBudget::start_tracking` → `TimeTracker::check_not_expired` (`clarity/src/vm/resource_limiter.rs` lines 77-101), using each signer's own wall-clock.
4. Signers under momentary load (GC pause, concurrent verification of other proposals/messages, I/O contention) observe elapsed time ≥ `max_duration` and reject the block via `ExecutionResourceBudgetExceeded` → `is_problematic` → block rejection with the offending txid blamed (`stackslib/src/chainstate/stacks/miner.rs` lines 678-694; `stackslib/src/chainstate/stacks/db/transactions.rs` lines 1074-1089).
5. Idle/faster signers accept the identical block. The signer set is left split on the same valid proposal, demonstrating the equality "same input ⇒ same verdict" is broken for a proposal that has not changed at all between observers.

Note: this analysis is based on statically reviewing the reachable code paths (`resource_limiter.rs`, `miner.rs`, `postblock_proposal.rs`, `transactions.rs`) and the project's own tests exercising these timeouts; I was not able to run the signer network end-to-end to empirically measure the real-world variance needed to reliably trigger a *split* vote (as opposed to a uniform timeout observed by all signers), so the likelihood of achieving a genuine cross-signer split (vs. a uniform timeout that just causes a retried/re-proposed block) remains an estimate rather than a directly demonstrated exploit in this review.

```rust
/// Defines limits on computing resources (heap allocation and wallclock time)
/// during processing of contract deploy and call transaction. These are
/// independent of cost tracking and MUST be [`ResourceBudget::unlimited`]
/// during consensus-critical processing, because that must remain deterministic.
///
/// The budgets are limited during the miner's block construction and the
/// signer node's proposal validation to ensure that a smart contract that
/// triggers excessive memory usage or delays is not included in the chain.
/// This is a defense-in-depth measure -- if these budgets are exceeded, that
/// probably means there's an underlying bug in the VM or analysis engine that
/// should be fixed.
pub struct TransactionResourceBudgets {
    /// The budget that applies during clarity evalution, used both during
    /// contract deploy and contract call transactions.
    execution_budget: ResourceBudget,

    /// The budget that applies during contract analysis, only used during
    /// contract deploy transactions.
    analysis_budget: ResourceBudget,
}

impl TransactionResourceBudgets {
    pub fn new() -> Self {
        Self {
            execution_budget: ResourceBudget::unlimited(),
            analysis_budget: ResourceBudget::unlimited(),
        }
    }

    pub fn unlimited() -> Self {
        Self::new()
    }

    pub fn from_settings(settings: &BlockBuilderSettings) -> Self {
        let memory_limit = if settings.max_assembly_mem_bytes > 0 {
            Some(settings.max_assembly_mem_bytes)
        } else {
            None
        };

        Self {
            execution_budget: ResourceBudget::new()
                .with_max_duration(settings.max_execution_time)
                .with_max_memory_use(memory_limit),
            analysis_budget: ResourceBudget::new()
                .with_max_duration(settings.max_analysis_time)
                .with_max_memory_use(memory_limit),
        }
    }
```

```rust
/// Tracks wall-clock time spent in a single execution phase of one transaction
/// (Clarity evaluation *or* contract analysis) and signals when a configured
/// deadline has elapsed.
///
/// [`TimeTracker::NoTracking`] is the deterministic-replay / no-limit case (it must be used on
/// the commit/replay path so consensus stays deterministic).
///
/// [`TimeTracker::MaxTime`] is used only on the non-consensus voting paths:
/// block assembly (mining) and block-proposal validation (signers) to bound the time
/// a single transaction can spend.
#[derive(Clone, Copy)]
enum TimeTracker {
    NoTracking,
    MaxTime {
        start_time: Instant,
        max_duration: Duration,
    },
}
```

```rust
    /// Returns and error if a deadline is configured and has elapsed. Always
    /// Ok(()) for `NoTracking`.
    pub fn check_not_expired(&self) -> Result<(), String> {
        match self {
            Self::NoTracking => Ok(()),
            Self::MaxTime {
                start_time,
                max_duration,
            } => {
                let elapsed = start_time.elapsed();
                // semantically `>` would be more correct than `>=`, but there
                // are a few tests that assume "zero always expires", and since
                // it makes not practical difference otherwise, we use `>=`.
                if elapsed >= *max_duration {
                    Err(format!(
                        "Elapsed time of {} ms exceeds budget of {} ms.",
                        elapsed.as_millis(),
                        max_duration.as_millis()
                    ))
                } else {
                    Ok(())
                }
            }
        }
    }
```
