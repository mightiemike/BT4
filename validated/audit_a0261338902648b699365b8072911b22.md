### Title
Deterministic-account receiver check validated against the wrong account before `FixDelegatedDeterministicStateInit` — protocol versions 83/84 accept a `DeterministicStateInitAction` whose derived id does not match the actual receiver - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
The Solana report describes `stake::process_stake` trusting a caller-supplied `treasury_tokens_info` account without recomputing/comparing it to the strictly-derived associated token account, letting an attacker redirect funds to an account they control. The closest reachable analog in `patrichyt/nearcore--020` is the `DeterministicStateInitAction` receiver check: the protocol requires that the receiver of this action equal the id **derived** from the action's `DeterministicAccountStateInit` payload (`derive_near_deterministic_account_id`), exactly the same "must equal the deterministically-derived account" invariant as an SPL associated-token-account check. Before `ProtocolFeature::FixDelegatedDeterministicStateInit` (activates at protocol version 85), this check compared the derived id against the **outer transaction's `receiver_id`** instead of the **inner `delegate_action.receiver_id`** when the action arrived wrapped in a meta-transaction (`Action::Delegate`). This is the same failure pattern as the report: the code checks a field that is *not* the true target of value/authority, allowing a relayer/attacker to redirect a deterministic-state-init receipt.

### Finding Description
`validate_deterministic_state_init` performs the intended strict check: [1](#0-0) 
It derives `derived_id = derive_near_deterministic_account_id(&action.state_init)` and requires `derived_id == *receiver_id`, returning `InvalidDeterministicStateInitReceiver` on mismatch — this is the correct, "strict equality" pattern the Solana report says is missing for `treasury_tokens_info`.

The bug (pre-fix) was in how `receiver_id` was chosen when the `DeterministicStateInitAction` was wrapped inside a `Delegate` (meta-transaction) action: the initial transaction-admission validation used the **outer** transaction's `receiver_id` (the meta-tx sender/relayer-controlled wrapper) rather than the **inner** `delegate_action.receiver_id` (the actual account the state-init action targets). A test explicitly documents and exercises this: [2](#0-1) 
The exploit setup crafts a delegate action whose outer `receiver_id` is `det_account_b` (which passes the check because it equals `derive(state_init_b)`), while `delegate_action.receiver_id` is actually `det_account_a` — a different account: [3](#0-2) 
Pre-fix, this "passes initial tx validation" and is only caught later by a receipt-level `validate_receipt` check, i.e., the check that should be strict at admission time authenticates the wrong account, mirroring exactly the "no strict equality check on the intended associated account" class from the report.

### Impact Explanation
`DeterministicStateInitAction` carries a `deposit` used to fund the account's storage/backing balance, and the global-contract code plus initial key/value state install into whichever account id is ultimately used to execute the action. If the receiver-authentication check binds to the wrong account field, an attacker (acting as, or colluding with, a relayer submitting a meta-transaction) can cause a `DeterministicStateInitAction` intended for one deterministic account to be admitted/queued against a different derived account than the one whose bytes were actually validated, misdirecting the deposited balance/storage funding and the installed state to an account the submitter does not intend — the same "unauthorized value/authority redirection" impact class as the Solana treasury-token report. Because deterministic accounts are validator/relayer-composable (any account can be targeted this way through a delegate action), this reaches "unauthorized value movement" at the receipt-admission layer, though it is ultimately caught (and the receipt fails) at `validate_receipt` even without the fix, per the test `test_deterministic_state_init_meta_tx_receiver_check_pre_fix`.

### Likelihood Explanation
This is reachable from a single submitted meta-transaction (`Action::Delegate` wrapping a `DeterministicStateInitAction`), i.e., an unprivileged relayer/signer path, matching the required threat model (transaction/RPC caller). The window is protocol-version-gated: the fix is only active once `FixDelegatedDeterministicStateInit` is enabled, at protocol version 85 (`core/primitives-core/src/version.rs`). Since `MIN_SUPPORTED_PROTOCOL_VERSION` in this tree is 83 [4](#0-3) , a chain/binary still operating at protocol version 83 or 84 (pre-v85) remains exposed to the mis-check at initial transaction validation, even though the mismatch is ultimately rejected at receipt validation rather than allowing state corruption. On any chain that has already activated PV 85+ (current mainnet/stable target per this snapshot, `STABLE_PROTOCOL_VERSION = 86`), this specific instance is already remediated, which lowers exploitability to "historical/version-gated" rather than "currently live on stable."

### Recommendation
Confirm (and keep permanently, not merely protocol-gated) that all receiver/account-derivation checks for `DeterministicStateInitAction` (and any structurally similar derived-account actions, e.g. `UniversalStateInitAction`) validate against the innermost action's own `receiver_id`/derived id at every validation layer — both initial transaction admission and receipt validation — rather than any wrapper/meta-transaction field, so no protocol-version window exists where the wrong field is authenticated. Add regression coverage that runs the meta-transaction exploit test unconditionally against the current stable and next protocol versions to prevent regression of this exact "wrong-field" pattern for any future derived-account action type.

### Proof of Concept
The existing exploit reproduction in the repo IS the PoC for the pre-fix behavior: [5](#0-4) 
1. Deploy two deterministic accounts (`det_account_a`, `det_account_b`) from different `state_init` payloads.
2. Deploy `det_account_b` for real and give it a full-access key (so it can be `meta_tx_sender`).
3. Build a `DelegateAction` with `sender_id = det_account_b`, `receiver_id = det_account_a` (the actually-targeted, mismatched account), wrapping an inner `Action::DeterministicStateInit` built from `state_init_b`.
4. Wrap it in an outer `SignedTransaction` whose `receiver_id = det_account_b` (which equals `derive(state_init_b)`, so it passes the buggy check that used the outer receiver).
5. At protocol version `< FixDelegatedDeterministicStateInit`, `try_execute_tx` shows the transaction **passes initial validation** and only fails later with `InvalidDeterministicStateInitReceiver` inside `NewReceiptValidationError` — i.e., the wrong field was authenticated at admission time, confirmed by `test_deterministic_state_init_meta_tx_receiver_check_pre_fix` [6](#0-5) ; at/after the fix version, `test_deterministic_state_init_meta_tx_receiver_check` shows it is now correctly rejected at transaction validation [7](#0-6) .

Note: I could not fully verify from the index whether any other, currently-unpatched action type (e.g. `UniversalStateInitAction`) has the identical outer-vs-inner receiver_id confusion for delegate/meta-transactions, since the index does not show a parallel `validate_delegate_action` fix history for that action type. If a full audit of `validate_actions`/`validate_delegate_action`'s handling of `UniversalStateInitAction` under `Action::Delegate` is desired to rule out a live (non-version-gated) recurrence of this exact bug class, a Devin session with full repository access would be needed to trace it precisely.

fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }

    protocol_version: ProtocolVersion,

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let (state_init_b, det_account_b) = env.new_deterministic_account_with_data(big());
    assert_ne!(det_account_a, det_account_b);

        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,

        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
