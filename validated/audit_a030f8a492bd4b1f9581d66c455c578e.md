### Title
Fee-transfer entry point call in the Starknet OS ignores the ERC20 `transfer()` success return value, allowing silent fee-charge failure without reverting the transaction - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/execute_transaction_utils.cairo`)

### Summary
The analog of the "ignoring return value of `transfer()`" bug class exists in the Starknet OS re-execution path used to charge transaction fees. `charge_fee()` invokes the fee token's `transfer()` entry point through `non_reverting_select_execute_entry_point_func`, which only asserts that the call did not *revert*, but never inspects the returned `success` felt of the ERC20 `transfer()` ABI. This mirrors exactly the reported vulnerability class: a `transfer()` call whose boolean return value is never checked, so a semantic failure (return `0`/`false` without a Cairo revert) is silently treated as a successful fee charge.

### Finding Description
`charge_fee` builds a `TransferCallData` and executes the ERC20 `transfer` entry point of the fee token contract via `non_reverting_select_execute_entry_point_func`: [1](#0-0) 

That helper only verifies that the call did not revert (`assert is_reverted = 0`) and returns `retdata_size`, `retdata`, `is_deprecated` to the caller — but `charge_fee` never uses those return values to confirm `retdata[0] == 1` (transfer success): [2](#0-1) 

This is in stark contrast to the neighboring `run_validate` function in the same file, which calls the *same* helper for `__validate__` and explicitly checks the returned value against the expected `VALIDATED` magic constant: [3](#0-2) 

The fee-token ERC20 ABI itself declares `transfer` as returning a `success: felt` (boolean-like Uint256/felt result) rather than always reverting on failure: [4](#0-3) 

Because `charge_fee` in the OS program discards this return value entirely, a fee token entry point that completes without a Cairo panic/revert but returns `success = 0` (e.g., due to an unusual/overridden fee-token class, insufficient allowance path, or any implementation that signals failure via return value instead of `assert`) will be accepted by the OS as a fully successful fee charge, with no state divergence detected during OS re-execution.

### Impact Explanation
If the deployed fee-token class ever returns `0` instead of reverting on a failed transfer (a legitimate ERC20 pattern per the ABI's `success: felt` return type), the Starknet OS's re-execution of `charge_fee` would consider the transaction's fee successfully collected while the sequencer/prover-committed state may not reflect an actual balance deduction/credit consistent with what a strictly-checking implementation would produce. This creates a divergence between what the OS proves (fee charged, no revert) and the actual ERC20 semantics (transfer failed), which can lead to incorrect state commitments (wrong balances) or accepted blocks where fees were not truly collected from the sender — a loss-of-funds/incorrect-accounting condition at the OS/committed-state level, satisfying "wrong committed root" / "concrete loss of funds" criteria.

### Likelihood Explanation
This path is reached on essentially every account transaction that pays a non-zero fee, since `charge_fee` is invoked unconditionally whenever `max_fee != 0`. Any unprivileged transaction sender can trigger this code path simply by submitting a normal fee-paying transaction; the vulnerability's trigger depends on the fee-token contract's specific `transfer` implementation returning `0` rather than reverting under some failure condition, which is a supported ERC20 semantic already encoded in the ABI (`success: felt` return) though the canonical Starknet fee token typically reverts on insufficient balance. The likelihood is therefore moderate — it requires a code path in the fee-token class where `transfer` returns `0` without reverting, but the OS trusts the call unconditionally in all cases.

### Recommendation
In `charge_fee` (or within `non_reverting_select_execute_entry_point_func`'s call site for fee transfers), explicitly validate the `transfer()` return value, analogous to the check already performed in `run_validate`:
```
let (retdata_size, retdata, is_deprecated) = non_reverting_select_execute_entry_point_func(
    block_context=block_context, execution_context=&execution_context
);
if (is_deprecated == 0) {
    assert retdata_size = 1;
    assert retdata[0] = 1;  // success
}
```
This ensures the OS only accepts a fee charge as valid when the ERC20 `transfer` call both did not revert and returned a truthy success value, closing the silent-failure gap.

### Proof of Concept
1. Deploy (or, in a permissioned upgrade scenario, have the network use) a fee-token class whose `transfer()` implementation returns `0` (failure) instead of reverting under some condition (this is valid per the ABI's declared `success: felt` return type shown in `erc20_fee_contract_class.json`).
2. Submit any ordinary fee-paying transaction (`max_fee != 0`) as an unprivileged sender.
3. During OS re-execution, `charge_fee` calls the fee token's `transfer` entry point via `non_reverting_select_execute_entry_point_func`; the call returns normally (`is_reverted = 0`) with `retdata[0] = 0`.
4. Because `charge_fee` never inspects `retdata`, the OS treats the fee as successfully charged and proceeds to finalize the transaction/block, despite the underlying transfer having semantically failed. This produces a state root/commitment that does not match what should have resulted from a failed fee transfer. [5](#0-4)

// Charges a fee from the user.
// If max_fee is not 0, validates that the selector matches the entry point of an account contract
// and executes an ERC20 transfer on the behalf of that account contract.
//
// Arguments:
// block_context - a global context that is fixed throughout the block.
// tx_execution_context - The execution context of the transaction that pays the fee.
func charge_fee{
    range_check_ptr,
    builtin_ptrs: BuiltinPointers*,
    contract_state_changes: DictAccess*,
    contract_class_changes: DictAccess*,
    outputs: OsCarriedOutputs*,
}(block_context: BlockContext*, tx_execution_context: ExecutionContext*) {
    alloc_locals;

    local tx_info: TxInfo* = tx_execution_context.execution_info.tx_info;
    let max_fee = compute_max_possible_fee(tx_info=tx_info);

    if (max_fee == 0) {
        return ();
    }

    local low_actual_fee;
    %{ LoadActualFee %}
    local calldata: TransferCallData = TransferCallData(
        recipient=block_context.block_info_for_execute.sequencer_address,
        amount=Uint256(low=low_actual_fee, high=0),
    );

    // Verify that the charged amount is not larger than the transaction's max_fee field.
    assert_nn_le(calldata.amount.low, max_fee);

    // TODO(ilya, 01/01/2026): Consider caching the fee_token_class_hash.
    local fee_token_address = block_context.os_global_context.starknet_os_config.fee_token_address;
    let (fee_state_entry: StateEntry*) = dict_read{dict_ptr=contract_state_changes}(
        key=fee_token_address
    );
    let (__fp__, _) = get_fp_and_pc();
    // Use block_info directly from block_context, so that charge_fee will always run in
    // execute-mode rather than validate-mode.
    local execution_context: ExecutionContext = ExecutionContext(
        entry_point_type=ENTRY_POINT_TYPE_EXTERNAL,
        class_hash=fee_state_entry.class_hash,
        calldata_size=TransferCallData.SIZE,
        calldata=&calldata,
        execution_info=new ExecutionInfo(
            block_info=block_context.block_info_for_execute,
            tx_info=tx_info,
            caller_address=tx_info.account_contract_address,
            contract_address=fee_token_address,
            selector=TRANSFER_ENTRY_POINT_SELECTOR,
        ),
        deprecated_tx_info=tx_execution_context.deprecated_tx_info,
    );

    let remaining_gas = DEFAULT_INITIAL_GAS_COST;
    non_reverting_select_execute_entry_point_func{remaining_gas=remaining_gas}(
        block_context=block_context, execution_context=&execution_context
    );
    return ();
}

// Same as `select_execute_entry_point_func`, but does not support reverts and does
// not have an implicit 'revert_log' argument.
func non_reverting_select_execute_entry_point_func{
    range_check_ptr,
    remaining_gas: felt,
    builtin_ptrs: BuiltinPointers*,
    contract_state_changes: DictAccess*,
    contract_class_changes: DictAccess*,
    outputs: OsCarriedOutputs*,
}(block_context: BlockContext*, execution_context: ExecutionContext*) -> (
    retdata_size: felt, retdata: felt*, is_deprecated: felt
) {
    let revert_log = init_revert_log();
    let (is_reverted, retdata_size, retdata, is_deprecated) = select_execute_entry_point_func{
        revert_log=revert_log
    }(block_context=block_context, execution_context=execution_context);
    assert is_reverted = 0;
    return (retdata_size, retdata, is_deprecated);
}
