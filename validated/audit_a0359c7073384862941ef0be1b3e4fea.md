### Title
Fixed, protocol-wide `l1_handler_max_amount_bounds.l2_gas` gives an unretryable execution budget for L1-triggered `l1_handler` entry points, permanently freezing L1→L2 bridged funds/state on out-of-gas - (File: crates/blockifier/src/transaction/l1_handler_transaction.rs)

### Summary
The external report describes `NFTShadow.releaseOnEid()` computing an under-sized `lzReceive` gas limit, causing the target-chain callback to run out of gas; because LayerZero allows retrying with a higher gas limit, the impact is limited to griefing/delay. In this Starknet sequencer codebase, the analogous gas-budget-for-cross-domain-callback pattern is the `L1HandlerTransaction` executor, which runs the `l1_handler` entry point with a **fixed, protocol-constant gas budget** (`l1_handler_max_amount_bounds.l2_gas`) that is entirely outside the control of the L1 message sender, and — unlike LayerZero — an L1→L2 message is consumed on first execution with **no retry mechanism**. If a contract's `l1_handler` logic legitimately needs more gas than this fixed constant, every future message to it will deterministically revert on out-of-gas, permanently freezing any funds/state tied to that message (e.g., bridged deposits), with no way for the sender to raise the limit and no way for the sequencer to retry.

### Finding Description
`L1HandlerTransaction::execute_raw` sets the callee's `remaining_gas` from a single hard-coded protocol constant, not from anything the L1 sender or the contract can adjust per message: [1](#0-0) 

This mirrors the OS (Cairo) side, where `L1_HANDLER_L2_GAS_MAX_AMOUNT` is likewise a single constant applied to every `l1_handler` invocation regardless of payload size, callee complexity, or fee paid on L1: [2](#0-1) 

Crucially, the L1→L2 message is consumed **before** execution completes (`consume_l1_to_l2_message`) and, in the Rust flow, is marked "consumed" on the L1 side once processed regardless of whether execution reverts: [2](#0-1) 

If execution (or the post-execution gas-bounds check) fails, the Rust executor aborts the *state* changes but still returns a normal (non-error) `TransactionExecutionInfo` with a `revert_error`, i.e. the transaction is included/committed in a block as reverted rather than being retried later with more gas: [3](#0-2) 

Unlike an account-abstraction (`Invoke`/`Declare`/`DeployAccount`) transaction, whose sender chooses `resource_bounds`/`max_fee` and can simply resubmit with higher bounds if `InsufficientResourceBounds`/`MaxFeeTooLow` is hit (see the `AccountTransaction::check_fee_bounds` pre-validation flow), the L1Handler path has no equivalent "sender-supplied gas bound" concept — `TxInfo` for L1 handlers is filled with `resource_bounds_start/end = null` and `max_fee = 0`: [4](#0-3) [5](#0-4) 

The only thing the L1 sender does supply, `paid_fee_on_l1` (`Fee`), is checked merely for being non-zero, not for covering any gas amount, and has no bearing on the gas limit used for execution: [6](#0-5) 

So the entire gas budget for arbitrary `l1_handler` logic — which can include loops over calldata, nested calls, storage writes, and (per the external report's own root cause) validator/hook calls — is dictated solely by a chain-wide, version-gated constant `l1_handler_max_amount_bounds` shipped in `blockifier_versioned_constants_*.json`, identical for every contract on the network, and not something either the L1 caller or the target contract can size for the specific message.

### Impact Explanation
Because the L1→L2 message is consumed/finalized on first inclusion and there is no protocol-level retry-with-more-gas path (contrasted with LayerZero's retryable `lzReceive`), any contract whose `l1_handler` entry point genuinely requires more Sierra gas than `l1_handler_max_amount_bounds.l2_gas` allows will have every legitimate L1→L2 message to it permanently reverted. This causes:
- Permanent freezing of funds/state associated with the message (e.g., a bridging contract that credits L2 balances or unlocks assets inside the `l1_handler`, if that logic — including deep nested calls, dispatcher validation hooks, or growing collections — exceeds the fixed budget).
- A network-wide denial of service for any legitimately gas-heavy `l1_handler`, since the constant is a single systemwide value rather than scaling with the message/contract's needs, and the sender/deployer has no lever to raise it for their specific use case.

This satisfies "concrete loss or permanent freezing of funds" from the validation criteria, and the actor reaching it is an ordinary "L1 message sender" plus a normal contract deployer who defines the `l1_handler` — both explicitly permitted actors under the rules.

### Likelihood Explanation
Likelihood is data-dependent: it triggers only for contracts whose `l1_handler` computation exceeds the fixed constant (e.g., due to large calldata-driven loops, deep call chains, or heavy validation logic invoked from the handler). This is analogous to the original report's root cause (validator/transfer-hook calls inflating real cost beyond the estimate), but here the "estimate" is not per-message — it is a single global ceiling, so any handler design that is anywhere near that ceiling is permanently exposed, and there is no per-message adjustment possible even for the deployer.

### Recommendation
- Do not hard-code a single global `l1_handler_max_amount_bounds.l2_gas` for all `l1_handler` executions; make the effective gas ceiling reflect the fee actually paid on L1 (`paid_fee_on_l1`) so that a higher-paying message can be granted a higher execution budget, similar to how account transactions size execution to their `resource_bounds`.
- Provide a mechanism for L1 callers to intentionally overpay in order to raise the effective gas ceiling for a specific message (functionally the OptionsBuilder-style "extra gas" recommendation from the source report), rather than a chain constant that cannot be tuned per-message.
- Ensure `check_all_gas_amounts_within_bounds` failures on `l1_handler` are distinguished from "genuinely permanently un-executable" handlers versus "needs a bigger, still-bounded budget," and consider surfacing this as an explicit, monitorable condition rather than a silent revert baked into a normal block.

### Proof of Concept
Deterministic PoC (conceptual, following the existing regression test pattern in the repo) that demonstrates the fixed budget:
1. Deploy a Cairo contract with an `l1_handler` entry point whose gas consumption (computed from loops/nested calls over its calldata) is deliberately made to exceed `block_context.versioned_constants.os_constants.l1_handler_max_amount_bounds.l2_gas.0`.
2. Send an L1→L2 message (as any unprivileged L1 account) targeting that entry point with a calldata size chosen to blow the fixed gas budget, following the existing test harness for L1Handler transactions: [7](#0-6) 
3. Execute via `tx.execute(state, block_context)`; because `remaining_gas` is capped at the fixed `l1_handler_bounds.l2_gas.0` (line 67 of `l1_handler_transaction.rs`), the callee runs out of gas mid-execution, `run_execute` fails, `execution_state.abort()` rolls back state, and the transaction is committed as reverted: [8](#0-7) 
4. Because the message's `consume_l1_to_l2_message`/`ConsumedMessageToL2` bookkeeping treats the transaction as final once processed (see `l1_events_provider.rs` `consume_tx` and `TxMgr` "committed" flow), the sender has no way to resend the same message with a larger gas allocation — the funds/state tied to that specific L1 message are permanently stuck.

Note: I was not able to execute this PoC in a live environment (no filesystem/terminal access in this ask-only mode) — the trace above is derived directly from reading the cited execution and consumption code paths, not from running the test. If precise numeric confirmation of `l1_handler_max_amount_bounds.l2_gas` per protocol version is needed, a Devin session with repository access should be used to pull the exact value from `blockifier_versioned_constants_0_14_3.json`'s `os_constants` section and construct a contract whose measured gas usage exceeds it.
