### Title
Node panic via out-of-order slice indices in `SourceBuffer::new_checked_with_verified_build_hash` when a Buffer account has an all-zero ELF payload - ([File: runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs])

### Summary
`SourceBuffer::new_checked_with_verified_build_hash` computes `end_offset` by scanning the *entire* buffer account data with `rposition`, not just the ELF region after the metadata prefix. If the attacker funds/writes the buffer account so that every byte from `offset` (the fixed metadata size) to the end of the account is zero, the last non-zero byte found by `rposition` is necessarily inside the metadata prefix itself (because a valid `UpgradeableLoaderState::Buffer` discriminant is non-zero), producing `end_offset < offset`. The subsequent slice `&data[offset..end_offset]` then panics because the start index exceeds the end index.

### Finding Description
In `source_buffer.rs`:
```
let offset = UpgradeableLoaderState::size_of_buffer_metadata();
let end_offset = data.iter().rposition(|&x| x != 0).map_or(offset, |i| i + 1);
let buffer_program_data = &data[offset..end_offset];
``` [1](#0-0) 

`data` is the *whole* buffer account's data (`buffer.buffer_account.data()`), including the metadata prefix that was already validated to deserialize as `UpgradeableLoaderState::Buffer { .. }` by `new_checked` right before this call: [2](#0-1) 

Because `UpgradeableLoaderState::Buffer` is a non-zero enum discriminant (variant index 1), any account that successfully passes the `Buffer`-state check necessarily has at least one non-zero byte inside `data[..offset]` (the discriminant tag), independent of whether `authority_address` is `Some` or `None`. If the attacker fills every byte from `offset` onward with `0x00` (an "ELF" that is entirely zero bytes, e.g. by simply never writing any ELF payload — the account is zero-initialized by default), then:
- `rposition(|&x| x != 0)` scans backward from the end of the array and finds the non-zero discriminant byte located *before* `offset`.
- `end_offset = i + 1` is therefore `<= offset`, and typically much smaller (e.g. `end_offset == 1` when `authority_address == None`, since only the first discriminant byte is non-zero).
- The expression `&data[offset..end_offset]` then panics at runtime with "slice index starts at `offset` but ends at `end_offset`" because `offset > end_offset`.

This panic occurs inside `SourceBuffer::new_checked_with_verified_build_hash`, which is invoked from `Bank::migrate_builtin_to_core_bpf` whenever `config.verified_build_hash` is configured for a migration: [3](#0-2) 

The crash happens before `directly_invoke_loader_v3_deploy` is even reached, but it is on the same feature-activation-triggered call path referenced in the question, and it is fully attacker-reachable: the source buffer account (`config.source_buffer_address`) is a normal, unprivileged account that anyone can create and fill with data ahead of the feature activation that drives the migration. No slot/ancestor, zero-lamport, or reference-count guard exists to prevent an attacker from pre-populating this account with a well-formed `Buffer` metadata prefix followed by all-zero bytes.

### Impact Explanation
Any validator that processes the feature activation for a Core BPF migration configured with `verified_build_hash` will panic and crash while calling `apply_feature_activations` → `migrate_builtin_to_core_bpf` → `SourceBuffer::new_checked_with_verified_build_hash`, if the designated source buffer account contains an all-zero payload after the metadata prefix. This is a validator node panic ("node panic during feature-activation-triggered migration"), matching Agave's node-crash/panic bounty category. Since this fires deterministically for every validator that processes the same feature activation slot, it can crash the majority of validators simultaneously, which is a cluster-wide availability failure, not just a single node's issue.

### Likelihood Explanation
- Preconditions: an unprivileged attacker must be able to write/fund the specific `source_buffer_address` pubkey referenced by the migration's `CoreBpfMigrationConfig` before the corresponding feature is activated, and must ensure that account is owned by `bpf_loader_upgradeable`, has a valid `Buffer`-state metadata prefix (satisfying `new_checked`), and has all-zero bytes after the metadata prefix (e.g., achieved simply by allocating space via the loader's `InitializeBuffer`/`Write` instructions without writing any non-zero ELF bytes, or writing an all-zero payload).
- These buffer addresses used for real core-BPF migrations are typically known in advance (they are hard-coded/publicly documented ahead of the corresponding feature-gate activation), so a race to fund/create the account with malicious content before the legitimate deployer does is plausible, especially if account creation/write access to that address is not otherwise restricted.
- The bug is deterministic once the malicious buffer state exists at feature-activation time — no timing games or repeated attempts are required, only the account content at the moment the feature activates.

### Recommendation
Restrict the `rposition` scan to the ELF sub-slice only (i.e., `data[offset..].iter().rposition(...)`), and always compute `end_offset` relative to `offset` (e.g., `offset + i + 1`), guaranteeing `end_offset >= offset`. Additionally, explicitly bound-check that `end_offset >= offset` before slicing, and return a `CoreBpfMigrationError` instead of allowing an unchecked slice range to panic.

### Proof of Concept
```rust
// runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs (test)
#[test]
fn test_verified_build_hash_all_zero_elf_panics() {
    let bank = create_simple_test_bank(0);
    let buffer_address = Pubkey::new_unique();

    let buffer_metadata_size = UpgradeableLoaderState::size_of_buffer_metadata();
    let elf_len = 64usize;
    let mut data = vec![0u8; buffer_metadata_size + elf_len]; // all-zero ELF region
    bincode::serialize_into(
        &mut data[..buffer_metadata_size],
        &UpgradeableLoaderState::Buffer { authority_address: None },
    )
    .unwrap();
    // data[buffer_metadata_size..] left as all zeros (malicious "ELF").

    let lamports = bank.get_minimum_balance_for_rent_exemption(data.len());
    let mut account = AccountSharedData::new(lamports, data.len(), &bpf_loader_upgradeable::id());
    account.data_as_mut_slice().copy_from_slice(&data);
    bank.store_account_and_update_capitalization(&buffer_address, &account);

    // Expect Err, not a panic.
    let result = SourceBuffer::new_checked_with_verified_build_hash(
        &bank,
        &buffer_address,
        Hash::default(),
    );
    assert!(result.is_err()); // currently panics instead of returning Err
}
```
Expected (fixed) behavior: the function returns `Err(CoreBpfMigrationError::BuildHashMismatch(..))` or similar. Current behavior: the process panics with a slice-index-order error inside `new_checked_with_verified_build_hash` at `&data[offset..end_offset]`.
