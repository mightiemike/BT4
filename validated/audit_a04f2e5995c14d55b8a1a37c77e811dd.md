### Title
Wallet Contract pays the relayer refund fee unconditionally, before the emulated action's success is known - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`inner_rlp_execute` fires the relayer fee-refund transfer as an independent promise batch at parse time, before the actual emulated action (`ft_transfer`/base-token transfer) is created and executed. Because the fee transfer is not chained to (`.then()`) the outcome of the emulated action's promise, the relayer is paid its fee even when the emulated action later fails.

### Finding Description
In `inner_rlp_execute`, once `parse_rlp_tx_to_action` succeeds and the resulting `TransactionKind` is an emulated base-token transfer or ERC-20 transfer with a non-zero `fee`, the contract immediately schedules a standalone promise batch to refund the relayer: [1](#0-0) 

This refund promise (`env::promise_batch_create` + `env::promise_batch_action_transfer`) is a separate, unlinked promise from the one that actually performs the transfer/ERC-20 call, which is constructed afterwards via `action_to_promise(...)`/the ERC-20 branch in the same function: [2](#0-1) 

The actual emulated action's result is only checked later, in `rlp_execute_callback` / `nep_141_storage_balance_callback`, which on `PromiseResult::Failed` only refunds the `caller_deposit` (the attached deposit of the failed action) — it never claws back or cancels the relayer fee that was already sent in a prior, independent batch: [3](#0-2) 

The fee amount itself is derived purely from the *signed* Ethereum transaction's `max_fee_per_gas * gas_limit`, computed during parsing, independent of whether the emulated transfer can actually succeed at execution time: [4](#0-3) 

Because the fee-refund promise is dispatched unconditionally as soon as parsing succeeds, and is not gated on (nor rolled back by) the success of the transfer/ERC-20 promise that follows, any transaction whose emulated action fails at execution time (e.g., insufficient token balance for `ft_transfer`, receiver-registration edge cases, or a target contract that rejects the call) still results in the relayer being paid — the classic "fee paid even though the transaction fails" bug class from the referenced report, just implemented via an un-gated cross-contract promise instead of an unchecked `call()` return value.

### Impact Explanation
This is a direct value-movement/loss bug reachable purely by submitting an RLP-encoded Ethereum-style transaction to the Wallet Contract (`rlp_execute`), which any relayer or even the wallet owner's signer can trigger. The eth-implicit account (the `current_account_id`, i.e., the wallet owner's actual NEAR funds) unconditionally loses the fee amount to the relayer even when the corresponding transfer/ERC-20 action never executes. A relayer (honest or malicious) can repeatedly submit transactions that are guaranteed or likely to fail (e.g., against a token balance that has since changed) purely to collect the fee without ever performing the requested action, draining the wallet's NEAR balance over time without providing the corresponding service. This is unauthorized value movement out of the user's wallet contract account, satisfying the "Accept only concrete unauthorized value movement… fee or gas bypass" validation criterion.

### Likelihood Explanation
Likelihood is moderate to high: no special privileges are needed beyond being a relayer for the Wallet Contract (any account can act as a relayer, since `rlp_execute` is a `#[payable]`, publicly-callable method), and the fee is computed from user-signed transaction data before the underlying action's feasibility is verified. Ordinary conditions that cause an `ft_transfer`/ERC-20 emulation to fail (stale nonce/balance state, non-atomic multi-call sequences noted elsewhere in this codebase for meta-transactions) are enough to trigger the bug; a malicious relayer can amplify this by deliberately choosing to submit transactions likely to fail on the target contract while still collecting the fee.

### Recommendation
Chain the relayer fee-refund transfer to the outcome of the actual emulated action's promise (e.g., using `.then()`/callback-gated logic similar to `rlp_execute_callback`) so the fee is only paid out if `PromiseResult::Successful` is observed for the underlying transfer/ERC-20 call, or issue the refund from within the success branch of the callback rather than eagerly in `inner_rlp_execute`.

### Proof of Concept
1. User signs an Ethereum-style ERC-20 `transfer` transaction targeting a NEP-141 token where the wallet's token balance is (or becomes) insufficient by the time it executes, and sets `max_fee_per_gas * gas_limit` to a non-zero fee for the relayer.
2. Relayer submits this via `rlp_execute` to the Wallet Contract.
3. `inner_rlp_execute` parses the transaction successfully (parsing does not check token balance), computes `tx_fee`, and immediately creates+dispatches the relayer refund promise batch (lines 381-384).
4. The subsequent `ft_transfer` cross-contract call (via the ERC20Transfer / `nep_141_storage_balance_callback` path) fails at execution time due to insufficient token balance.
5. `rlp_execute_callback` observes `PromiseResult::Failed` and only refunds the `caller_deposit` (attached NEAR deposit of the failed call), not the already-paid relayer fee.
6. Net effect: the relayer received the fee in step 3 even though the ERC-20 transfer never happened.

                    .parse()
                    .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
                ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,

        }
        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
        }
        _ => {

            action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))

    // Compute the fee based on the user's Ethereum transaction.
    // This is sent as a refund to the relayer in the case of an emulated base token
    // transfer or ERC-20 transfer. The reason for this refund is that it allows a
    // user with $NEAR to use a relayer service from their wallet immediately without
    // additional on-boarding.
    let tx_fee = {
        // Limit the cost by `VALUE_MAX` since we will convert this to a $NEAR amount.
        // The call to `low_u128` is safe because `VALUE_MAX` is the largest accepted value.
        let wei_amount = tx.max_fee_per_gas.saturating_mul(tx.gas_limit).min(VALUE_MAX).low_u128();
        NearToken::from_yoctonear(wei_amount.saturating_mul(MAX_YOCTO_NEAR as u128))
    };
