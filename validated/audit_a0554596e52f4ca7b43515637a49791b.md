Based on my investigation, I found a concrete, code-confirmed integrity gap that is a legitimate structural analog to the "missing check leads to unprotected state divergence" bug class from the external report (there, `redeemExpiredPT` skipped a slippage check; here, the ledger's own replay-verification skips a root-hash check).

### Title
Replay-Verify Skips State/Hot-State/Position Checkpoint Hash Comparison, Allowing Silent State-Root Divergence to Pass Verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by both the offline `db-tool replay_on_archive` verifier and, more importantly, by any future/likely commit-path caller relying on it as an output/ledger-consistency check. It validates status, gas used, the write-set hash (`state_change_hash`), and the event root hash against the persisted `TransactionInfo`, but explicitly and knowingly omits comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function performs four checks — transaction status, gas used, write-set hash, and event root hash — each guarded by an `ensure!`. After the event-root check, the function simply returns `Ok(())` with a comment stating the state-checkpoint-related hashes are intentionally skipped: [2](#0-1) 

This is a real, currently-shipped state binding gap: `TransactionInfoV1` (the newer version of the committed ledger record) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields that are part of the authenticated, accumulator-hashed record [3](#0-2) , yet the one function whose stated purpose is to assert that a freshly-computed `TransactionOutput` matches a `TransactionInfo` never checks these fields.

This function is invoked directly by the `db-tool replay_on_archive` verifier — the mainnet-facing tool used to independently re-execute historical transactions and confirm the resulting state matches what was actually committed and signed by validators: [4](#0-3) 

Because `ensure_match_transaction_info` never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a replay run that locally computes a *different* state root than what is stored in the archived, ledger-info-signed `TransactionInfo` will still report success. The check only fails on status, gas, write-set-hash, or event-hash mismatches — none of which necessarily change when a state-root computation bug (e.g. in JMT hashing, hot-state promotion, or the newly-added `position_state_checkpoint_hash`/"trading-native" state root path) diverges from the authenticated value.

### Impact Explanation
This falls squarely under "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Authenticated API or state-view output bound to the wrong version, object, or proof context" from the state-integrity gate. The state checkpoint hash is the authenticated root that light clients, backup/restore flows, and state-proof consumers trust as the summary of the entire account/resource state at a version — [5](#0-4)  shows backup/restore explicitly relies on `ensure_state_checkpoint_hash()` matching the manifest root, confirming how load-bearing this hash is elsewhere in the codebase. A verification tool that is supposed to be the safety net for catching exactly this kind of divergence (post-hardfork bugs, non-deterministic execution, native/trading state root bugs) silently omits the one check that would catch a state-root fork, defeating its purpose as an audit/consensus-safety tool.

### Likelihood Explanation
The gap is not hypothetical — it is called out by the developers themselves via the `TODO(trading-native)` comment, indicating it is a known, currently-live omission tied to the incoming `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature and `position_state_checkpoint_hash` field [6](#0-5) . As long as this feature (or any bug in existing state/hot-state checkpoint computation) is active, `replay_on_archive` — the primary tool operators/auditors use to detect state divergence on historical/mainnet data — cannot detect it.

### Recommendation
Add explicit `ensure!` comparisons in `ensure_match_transaction_info` for `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever the corresponding fields are `Some` in `txn_info` (i.e., at checkpoint-carrying versions), computing the local equivalents from the post-execution state view before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, exactly as the existing TODO comment prescribes.

### Proof of Concept
1. Take any historical range in an archive DB where a `TransactionInfo` (V1) carries a `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`).
2. Run `db-tool replay-on-archive` over that range; the tool calls `execute_and_verify`, which calls `ensure_match_transaction_info`.
3. Introduce (or have present) any divergence solely in state root computation (e.g., a bug in hot-state promotion logic, JMT hashing, or the trading-native position-state root) that does not alter `status`, `gas_used`, the write-set bytes/hash, or emitted events.
4. `ensure_match_transaction_info` returns `Ok(())` because none of its four checks cover the checkpoint hashes, so `replay_on_archive` reports a clean, successful replay verification despite the local state root diverging from the authenticated, validator-signed root — matching the exact scenario the code's own TODO warns about.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
