### Title
Unauthenticated-scope privilege escalation: `run`-role users can execute arbitrary registered capabilities via `POST /v2/execute_capability` - ([File: core/web/capability_controller.go])

### Summary
`CapabilityController.ExecuteCapability` accepts an arbitrary `capabilityName`, fetches it directly from the global `CapabilitiesRegistry`, and executes it with attacker-supplied request bytes, gated only by `RequiresRunRole` which permits any non-`View` role user, including sessions/tokens synthesized for external initiators. There is no workflow-ownership, DON-membership, or capability-scope check binding the caller to the specific capability being invoked.

### Finding Description
The route is defined with only run-role authorization: [1](#0-0)  `RequiresRunRole` only rejects `UserRoleView`; any `UserRoleRun`, `UserRoleEdit`, or `UserRoleAdmin` session passes through. Critically, `AuthenticateExternalInitiator` — a normal, non-privileged auth method used for external-initiator-derived requests — unconditionally sets the authenticated user's role to `UserRoleRun`: [2](#0-1) . This means any caller holding valid external-initiator credentials (which are not admin/node-operator credentials) inherits a `run`-role session sufficient to pass `RequiresRunRole`.

Inside `ExecuteCapability`, the handler takes the caller-supplied `CapabilityName` and request bytes, resolves the executable straight from the shared registry, and invokes `Execute` with no additional authorization, ownership, or workflow-binding check: [3](#0-2) . The handler never checks that the caller is the owning workflow, is part of the target DON, or has any relationship to the specific `capabilityName` being invoked — it treats "authenticated with run role" as sufficient authorization to execute *any* capability registered in the node's `CapabilitiesRegistry`, including privileged/internal capabilities (e.g., CCIP/OCR/vault-adjacent) that are otherwise only meant to be reached through the scoped workflow-engine execution path.

### Impact Explanation
This breaks the intended privilege boundary between "can trigger my own job/workflow run" and "can execute arbitrary node capabilities directly." An attacker with only run-role credentials (including those auto-granted via external-initiator authentication, a low-trust integration point) can invoke privileged capability logic outside of any workflow/DON authorization context — potentially causing unauthorized capability side effects, transaction/report execution, or resource exhaustion, depending on what capabilities are registered on the node.

### Likelihood Explanation
The route is only registered when `build.IsDev()` is true, per the file's stated precondition, which limits exposure to dev/staging builds rather than default production builds — this materially lowers real-world likelihood in a production Chainlink node deployment. However, when enabled, the exploit requires nothing beyond ordinary run-role credentials (including externally-derived ones), no additional bypass, and is fully repeatable since `GetExecutable`/`Execute` perform no per-caller scoping.

### Recommendation
Bind capability execution to an authorized workflow/owner context: require the caller to present workflow ownership or DON-membership proof matching the target `capabilityName`, or restrict this endpoint to admin-only internal tooling and remove it from any code path reachable by `run`-role/external-initiator-derived sessions. At minimum, gate it behind `RequiresAdminRole` and add an explicit capability-to-caller authorization check before calling `capability.Execute`.

### Proof of Concept
Integration test: register a privileged mock `ExecutableCapability` (e.g. named `"privileged-ccip-action"`) in a real `CapabilitiesRegistry` attached to `chainlink.Application`. Start the web server with `IsDev()` forced true. Obtain a session via `AuthenticateExternalInitiator` (mocked `bridges.ExternalInitiator` + valid EI token) or a plain `UserRoleRun` API token. POST to `/v2/execute_capability` with `{"capabilityName": "privileged-ccip-action", "capabilityRequest": <marshaled pb.CapabilityRequest>}`. Assert HTTP 200 and that the mock capability's `Execute` method was invoked — demonstrating execution succeeded with no workflow-ownership or DON-scope check despite the caller holding only a run-role credential.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```

```go
func (cc *CapabilityController) ExecuteCapability(c *gin.Context) {
	body := c.Request.Body
	if body == nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("missing request body"))
		return
	}

	capabilityRegistry := cc.App.GetCapabilitiesRegistry()
	if capabilityRegistry == nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("capability registry not initialized"))
		return
	}
	var capabilityRequestOuter CapabilityRequestOuter
	if err := c.BindJSON(&capabilityRequestOuter); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	capability, err := capabilityRegistry.GetExecutable(c.Request.Context(), capabilityRequestOuter.CapabilityName)
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	capabilityRequest, err := pb.UnmarshalCapabilityRequest(capabilityRequestOuter.CapabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	resp, err := capability.Execute(c.Request.Context(), capabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
```
