### Title
Replay-verification of `TransactionOutput` skips checkpoint-hash comparison, allowing a corrupted state/position root to pass as verified once `compute_trading_native_state_roots` is enabled - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the routine used by replay/archive verification tooling to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` recorded on-chain, checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is a direct analog of the reported bug class: a value that is supposed to bind an authenticated/committed artifact to the correct destination/state is silently left unchecked, so a wrong value is accepted as valid.

### Finding Description
`ensure_match_transaction_info` at <cite repo="Oyahkilomeikhide/aptos-core--018" path="types/src/transaction/mod.rs" start="2139-2204" /> validates:
- execution status
- gas used
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

but the function's own comment acknowledges the gap: [1](#0-0) 
> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole verification routine used by the on-disk replay/archive verifier, `storage/db-tool/src/replay_on_archive.rs`, which calls it directly per transaction: [2](#0-1) 

`TransactionInfoV1` carries three distinct checkpoint-root fields that are meant to authenticate different pieces of durable state: the classic Sparse-Merkle `state_checkpoint_hash`, the `hot_state_checkpoint_hash`, and the newly added `position_state_checkpoint_hash` (used by the "trading-native" state root, computed in `do_state_checkpoint.rs`'s `get_position_checkpoint_hashes`): [3](#0-2) [4](#0-3) 

Because `ensure_match_transaction_info` never compares these fields to the recomputed roots, a replay run can locally recompute a *different* state/hot-state/position-state root than what is stored in the archived (authenticated) `TransactionInfo`, and the verifier will still report success — the divergence in committed ledger state is invisible to the tool whose entire purpose is to catch exactly that divergence.

The relevant on-chain feature, `compute_trading_native_state_roots`, is currently gated off by default (`false` in every constructor) and further requires `transaction_info_v1` and `hotness_in_epilogue` to also be enabled: [5](#0-4) 

### Impact Explanation
This is a proof/commit-integrity gap, not a consensus-safety bug by itself: the accumulator, transaction-info hashing, and range-proof verification code (`types/src/proof/definition.rs`, `types/src/proof/mod.rs`) all correctly bind `TransactionInfo` (which *includes* the checkpoint hash fields) into the Merkle accumulator and verify it end-to-end. The vulnerability is that the tool responsible for detecting a *hard-fork-only divergence* between execution and archived/committed history — the explicit "Hard-fork-only divergence during commit, replay, restore" scenario in scope — is blind to exactly the fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) that would reveal such a divergence. Once `compute_trading_native_state_roots` (or hot-state roots) is turned on in production, an execution bug, storage corruption, or malicious archive/backup provider that alters the position/hot state without touching the write-set or events would go completely undetected by `replay_on_archive`/`replay-verify`, defeating the primary safety net used to catch exactly this class of hard-fork or corruption. This matches the required impact class: "Authenticated API or state-view output bound to the wrong version, object, or proof context" — here, the archive replay-verification result is bound to an incomplete comparison and reports success for a wrong committed state.

### Likelihood Explanation
The gap is guaranteed to trigger any time the corresponding checkpoint hash is wrong, since there is no code path comparing it — it is not a probabilistic race, it's an unconditional omission, confirmed by the author's own TODO. Its practical severity today is limited because `compute_trading_native_state_roots` and `hot_state_root_in_txn_info` require `transaction_info_v1` and are off by default; once those flags are enabled (which the code explicitly anticipates — see the "Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS" comment), the gap becomes immediately exploitable for anyone providing archived/backup data or triggering state corruption on a replaying node.

### Recommendation
Extend `ensure_match_transaction_info` to compute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionInfo` variant) against the locally recomputed roots from execution output, before `compute_trading_native_state_roots`/`hot_state_root_in_txn_info` are enabled on any network. This should be treated as a release-blocking prerequisite for enabling those feature flags.

### Proof of Concept
1. Enable (or simulate) `hot_state_root_in_txn_info` / `compute_trading_native_state_roots` so `TransactionInfoV1` carries meaningful `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` values.
2. Construct an archived `TransactionInfo` (or corrupt a backup/db) whose `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` differ from what a correct local re-execution would produce, while keeping `write_set` and `events` identical/matching.
3. Run `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which calls `TransactionOutput::ensure_match_transaction_info` [2](#0-1) .
4. Observe that verification succeeds (`Ok(())`) despite the state/hot-state/position-state root mismatch, because none of those fields are compared in `ensure_match_transaction_info` [6](#0-5) .

**Note on limitations:** I could not fully confirm whether `compute_trading_native_state_roots`/`hot_state_root_in_txn_info` are enabled on any live network in this snapshot, nor trace every caller of `ensure_match_transaction_info` beyond `replay_on_archive.rs` and its own definition (index coverage of this large repo is partial); a Devin session with full repo access could confirm additional call sites (e.g., state-sync bootstrapper paths referencing `position_state_checkpoint_hash`) and current feature-flag rollout status.
