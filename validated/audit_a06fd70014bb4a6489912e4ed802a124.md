Confirmed: `FreezeBalanceV2Contract` (the current TRON freeze model) has no `frozen_duration` field at all [1](#0-0) , and voting via `VoteWitnessActuator` only checks that `tronPower` (derived from any freeze, old or V2) covers the requested vote count [2](#0-1)  — there is no minimum holding time before a freeze counts as full voting power.

### Title
Vote reward Vi accrues to whatever stake is present at maintenance boundary, letting a voter freeze/vote right before the cycle switch and unfreeze right after to capture a full cycle's reward - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
TRON's DPoS voting-reward algorithm distributes each cycle's accumulated block/fee reward to voters using a per-witness reward-per-vote index ("Vi") that is updated once per maintenance cycle using the witness's *current* vote count at that instant, not a time-weighted average of vote count held throughout the cycle. A user can freeze TRX (or use `FreezeBalanceV2Contract`, which imposes no minimum freeze duration) and cast a vote just before a maintenance boundary, receive full Vi-based reward credit for the entire cycle, then withdraw/unvote immediately after, exactly mirroring the Union Finance bug pattern of a "just locked" stake getting a full-duration reward multiplier.

### Finding Description
At each maintenance boundary, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount())` [3](#0-2) . `accumulateWitnessVi` divides the cycle's total accumulated reward for that witness by `voteCount` (the vote count read from `WitnessCapsule` at that single moment) to compute `deltaVi`, which is then added to the running Vi accumulator for the witness [4](#0-3) .

A voter's reward for holding votes from `beginCycle` to `endCycle` is `deltaVi (endVi - beginVi) * userVoteCount`, computed in `MortgageService.computeReward` / `VoteRewardUtil.computeReward` [5](#0-4) [6](#0-5) . Because `deltaVi` for a cycle is fixed by the witness's *end-of-cycle* vote total (not a time-integral of vote-seconds), a voter who casts votes an instant before the maintenance boundary is credited with the same per-vote reward share as someone who voted for the witness the entire cycle. The `updateVote` (unfreeze) logic in `UnfreezeBalanceV2Processor.updateVote` proportionally reduces stored votes only after the fact [7](#0-6)  but does nothing to time-weight the reward already accrued for the cycle just closed.

The `FreezeBalanceV2Contract` execute path shows there is no lock-up delay before the frozen balance grants `TRON_POWER` / vote weight [8](#0-7) , and `VoteWitnessActuator.validate()` only checks current `tronPower` against requested vote sum, with no check on how long that tron power has been held [9](#0-8) .

### Impact Explanation
An attacker can:
1. Freeze TRX via `FreezeBalanceV2Contract` right before a maintenance boundary (or hold pre-existing bandwidth/energy freeze which also grants `TRON_POWER`).
2. Cast `VoteWitnessContract` votes for a colluding/self-owned witness.
3. Let the maintenance/cycle switch occur, at which point `accumulateWitnessVi` divides that cycle's whole reward pool by the (now-inflated) vote count including the attacker's just-added votes, and the attacker is credited the same Vi delta as a long-term voter.
4. Immediately unvote/unfreeze afterward via `UnfreezeBalanceV2Contract`.

This dilutes the rewards long-term voters would have otherwise received (since the reward pool per witness is fixed and divided by total votes, a last-second voter siphons off a share) and can also be used to game witness ranking/vote counts transiently. As in the original report, no funds are stolen outright, but honest long-term voters are shortchanged of proportional Vi-based rewards — a medium-severity accounting-fairness issue, consistent with the "just locked stake gets full reward multiplier" bug class.

### Likelihood Explanation
This is reachable by any account via public, unprivileged transaction types (`FreezeBalanceV2Contract`, `VoteWitnessContract`, `UnfreezeBalanceV2Contract`) broadcast to the network — no special permissions needed. The maintenance cycle boundary time is publicly known (`getNextMaintenanceTime`), making the timing attack straightforward to schedule. The main friction is capital efficiency (must hold TRX briefly) and needing a controlled/witness beneficiary to fully capture value, similar to the original Union Finance PoC needing "control of another member."

### Recommendation
Time-weight the Vi/reward accrual within a cycle (e.g., track vote-weighted-by-blocks-held or vote-seconds instead of a single end-of-cycle snapshot), or require votes/freezes to be held for a minimum number of blocks/cycles before they count toward the current cycle's Vi computation, analogous to introducing lock-duration accounting recommended in the referenced report.

### Proof of Concept
1. Determine `nextMaintenanceTime` via `DynamicPropertiesStore.getNextMaintenanceTime()`.
2. Just before that time, broadcast `FreezeBalanceV2Contract` (BANDWIDTH/ENERGY/TRON_POWER) to obtain `TRON_POWER`, then broadcast `VoteWitnessContract` voting for witness W.
3. Let `MaintenanceManager.doMaintenance()` run; `accumulateWitnessVi` computes `deltaVi = reward(cycle,W) * 10^18 / witness.getVoteCount()` using the vote count that already includes the attacker's fresh vote [4](#0-3) .
4. Call `withdrawReward`/`WithdrawRewardContract` (or `VoteRewardUtil.withdrawReward` via TVM) — the attacker's reward is `deltaVi * userVoteCount`, identical per-vote share as long-term voters for that cycle.
5. Immediately unfreeze via `UnfreezeBalanceV2Contract`, recovering principal (subject to the 14-day unlock delay for principal withdrawal, but the reward and vote-count dilution already occurred) and clearing votes via `UnfreezeBalanceV2Processor.updateVote` [10](#0-9) .

*Note: I was not able to trace the exact block-height granularity of `getNextMaintenanceTime()` transitions or confirm whether any additional TVM-only vote clearing (`allowTvmVote`) path closes this gap for TVM-triggered votes versus wallet-level `VoteWitnessContract` votes; a full confirmation would require tracing `ConsensusDelegate`/`DposService` interactions in a running node, which is outside index-search capability.*

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
