### Title
Meta-transaction sender can drain relayer funds by intentionally failing delegated actions to redirect deposit refunds to themselves - ([File: runtime/runtime/src/actions.rs])

### Summary
In NEAR's meta-transaction (NEP-366) flow, a relayer pays the gas and attached deposit for a `DelegateAction`'s inner actions, but if the inner action fails on the receiver's shard, the deposit refund is sent to the `predecessor_id` of the failed receipt — which is the meta-transaction sender (e.g., "Alice"), not the relayer who actually paid. This mirrors the Gitcoin bug class: the party required to "pay" (relayer) sends value, but the value is refunded to a different, unprivileged party (the sender) who can deliberately trigger the refund path repeatedly at zero cost to themselves and financial loss to the relayer.

### Finding Description
When a relayer submits a `SignedDelegateAction` on behalf of a sender, the relayer's account is charged for gas and any attached deposits of the inner actions (`apply_delegate_action`, [1](#0-0) ). The new receipt is created with `predecessor_id: sender_id.clone()` — the meta-tx sender, not the relayer [2](#0-1) .

When the inner action is processed and fails, `refund_unspent_gas_and_deposits` computes a deposit refund equal to the full attached deposit and routes it via `receipt.balance_refund_receiver()`, which resolves to `predecessor_id` unless `refund_to` is explicitly set [3](#0-2) [4](#0-3) . Because the predecessor of the inner receipt is the sender (Alice), not the relayer, the refunded deposit — which the relayer actually paid — goes back to Alice instead of the relayer.

This is explicitly documented as a known incentive-misalignment: "what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [5](#0-4) 

The sender (an unprivileged meta-transaction signer) fully controls whether the inner action fails (e.g., call a non-existent method, or a method that reverts) and controls the attached deposit amount up to whatever the relayer is willing to prepay. Since the relayer pays the deposit up front and it is refunded to the sender on failure, the sender can repeat this with new nonces indefinitely, extracting relayer funds with no cost to themselves beyond convincing a relayer to process the transaction (which relayers may do automatically for legitimate-looking, low-risk requests).

### Impact Explanation
This constitutes unauthorized value movement: a relayer's attached deposit is transferred to an unprivileged sender through a self-triggered failure path, with no compensating value delivered to the relayer. Because the sender controls the failure condition and can repeat this arbitrarily via new nonces, it enables systematic draining of a relayer's balance — direct financial loss for any party operating a NEAR meta-transaction relayer, a supported first-class protocol feature (NEP-366).

### Likelihood Explanation
Likelihood is high for any relayer that doesn't perform simulation/dry-run validation of the full delegated action chain (including the innermost receiver's method existence and expected outcome) before broadcasting, since the attack requires nothing more than a normal, protocol-legal `SignedDelegateAction` with an attached deposit and an inner action engineered to fail on the receiver shard.

### Recommendation
Route deposit refunds for delegate-action-derived receipts to the relayer (the actual payer) rather than to `predecessor_id`/sender, or require relayers to always set `refund_to` explicitly to their own account when constructing delegated deposit-bearing actions, and document/enforce this as a mandatory relayer safeguard rather than an implicit trust assumption.

### Proof of Concept
1. Alice creates account with a relayer-funded meta-transaction relationship.
2. Alice signs a `DelegateAction` targeting `receiver_id = Bob`, with `actions = [Transfer/FunctionCall { deposit: X }]` where the inner action is crafted to fail (e.g., calling a nonexistent method on Bob, per the exact test pattern used in `test_refund_on_send_money_to_non_existent_account`-style scenarios [6](#0-5) , or `nonexistent_method` as in `test_gas_key_refund` [7](#0-6) ).
3. Relayer wraps and submits the `SignedDelegateAction`, prepaying gas and deposit `X` from its own balance.
4. `apply_delegate_action` builds a receipt with `predecessor_id = Alice`, `receiver_id = Bob` [2](#0-1) .
5. Inner action fails on Bob's shard; `refund_unspent_gas_and_deposits` issues a `new_balance_refund` to `receipt.balance_refund_receiver()` = Alice, for the full deposit `X` [3](#0-2) .
6. Alice's balance increases by `X`; relayer's balance decreases by `X` (plus gas), with nothing delivered to Bob. Repeat with incrementing nonces to drain the relayer.

    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }

## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
