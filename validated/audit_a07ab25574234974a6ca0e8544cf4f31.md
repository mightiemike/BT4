### Title
Open redirect via protocol-relative URL bypasses `sanitizeRedirectUrl` allowlist checks - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts)

### Summary
The `isSafe` function in `sanitizeRedirectUrl` uses regexes `FILE_URI_MATCH = /\/\/\//` and `INVALID_RELATIVE_URL = /[/\\][/\\]/` to reject dangerous redirect targets, but a scheme-relative URL with exactly two leading slashes (e.g. `//evil.example/path`) evades both checks while still resolving to an attacker-controlled origin. `new URL('//evil.example/path', domain)` resolves to `https://evil.example/path`, inheriting the scheme from `domain`, and `url.pathname` becomes `/path`, which contains no doubled slash. As a result `isSafe` returns `true` and `sanitizeRedirectUrl` returns a cross-origin URL instead of throwing.

### Finding Description
`isSafe` first checks the raw `redirectUrl` string against `FILE_URI_MATCH` (requires three consecutive slashes, e.g. `///path`) and whitespace [1](#0-0) . A two-slash scheme-relative input like `//evil.example/path` doesn't match `FILE_URI_MATCH` (only two slashes, not three) and contains no whitespace, so it passes this gate.

The code then constructs `url = new URL(redirectUrl, domain)` [2](#0-1) . Per WHATWG URL parsing semantics, a string beginning with `//` is treated as network-path/protocol-relative, so the resulting `url` takes `evil.example` as its host while inheriting the scheme (`https:`) from `domain`. This is the crux of the smuggling: the "authority" portion of the malicious input is smuggled into the parsed URL's host, not its path.

The subsequent check `INVALID_RELATIVE_URL.test(url.pathname)` only inspects `url.pathname` (`/path`), which contains no doubled slash, so it also passes [3](#0-2) . Finally `url.protocol` is `https:`, satisfying both `VALID_PROTOCOLS.includes(url.protocol)` and the `requireSSL` check (default `true`) [4](#0-3) . `isSafe` returns `true`, and `sanitizeRedirectUrl` returns `new URL('//evil.example/path', domain)` — a fully cross-origin URL to `evil.example` — instead of throwing `ShopifyError` [5](#0-4) .

This function is reachable from `renderAppBridge`, which is used by the admin authentication/redirect flow to build a `window.open(destination, target)` script served in the app's HTML response, using an attacker-controllable `redirectTo.url` value that flows through `sanitizeRedirectUrl(config.appUrl, redirectTo.url)` [6](#0-5) . An identical implementation and the same flaw exist in the `shopify-app-react-router` package.

### Impact Explanation
An attacker who can influence the `redirectTo.url`/redirect-target parameter reaching `sanitizeRedirectUrl` can cause the merchant's authenticated browser session (running inside the embedded Shopify admin iframe/App Bridge context) to be redirected via `window.open` to an attacker-controlled origin (`https://evil.example/path`) instead of staying within the app's own domain. This matches Shopify's "open redirect" bounty impact class — redirecting an authenticated admin session to attacker infrastructure, which could be used for phishing, session/token leakage via referrer, or further post-redirect exploitation.

### Likelihood Explanation
No privileged access or secret is required — this is a pure input-validation bypass reachable by any party able to supply the redirect target string that ends up in `redirectTo.url` (e.g., via a crafted request/callback parameter in the host app's use of `renderAppBridge` or any other caller of `sanitizeRedirectUrl`). The bypass is fully deterministic and repeatable: `//` followed by any host string always parses as a protocol-relative URL under the WHATWG URL spec, so the vulnerability is 100% reproducible with a simple crafted string.

### Recommendation
After parsing `url`, explicitly verify that `url.host`/`url.hostname` matches the expected `domain`'s host (i.e., enforce same-origin, not just same-scheme), or reject any `redirectUrl` string that starts with `//` (or `\\`) prior to parsing, in addition to the current path-based checks. Comparing `url.origin` (or `url.hostname`) against the parsed `domain`'s hostname closes this gap regardless of the path structure.

### Proof of Concept
```javascript
// packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/__tests__/validate-redirect-url.test.ts
import {ShopifyError} from '@shopify/shopify-api';
import {APP_URL} from '../../../../__test-helpers';
import {sanitizeRedirectUrl} from '../validate-redirect-url';

it('should NOT allow protocol-relative URL redirect to a different origin', () => {
  // Currently this does NOT throw, and instead resolves to
  // an attacker-controlled origin -- demonstrating the bypass.
  const result = sanitizeRedirectUrl(APP_URL, '//evil.example/path');
  expect(result.hostname).not.toBe('evil.example'); // fails today
  // Correct behavior would be:
  expect(() => sanitizeRedirectUrl(APP_URL, '//evil.example/path')).toThrow(
    ShopifyError,
  );
});
```
Running this against the current implementation shows `sanitizeRedirectUrl(APP_URL, '//evil.example/path')` returns `URL { href: 'https://evil.example/path', ... }` rather than throwing, confirming the open redirect.

```typescript
export function sanitizeRedirectUrl<OptionsArg extends Options>(
  domain: string,
  redirectUrl: unknown,
  options: OptionsArg = {} as OptionsArg,
): SanitizedRedirectUrl<OptionsArg> {
  if (isSafe(domain, redirectUrl, options.requireSSL)) {
    return new URL(redirectUrl, domain) as SanitizedRedirectUrl<OptionsArg>;
  } else if (options.throwOnInvalid === false) {
    return undefined as SanitizedRedirectUrl<OptionsArg>;
  } else {
    throw new ShopifyError('Invalid URL. Refusing to redirect');
  }
}
```
