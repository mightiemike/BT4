### Title
Integer overflow in `WithdrawBalanceActuator.execute()` bypasses the `checkedAdd` overflow guard performed in `validate()` - (File: `actuator/src/main/java/org/tron/core/actuator/WithdrawBalanceActuator.java`)

### Summary
`WithdrawBalanceActuator.validate()` performs `LongMath.checkedAdd(balance, allowance)` on a stale snapshot of `allowance` taken before the reward-settlement logic runs. `execute()` then calls `mortgageService.withdrawReward()`, which can increase `allowance` via `adjustAllowance`, and afterwards computes the new balance with a plain `oldBalance + allowance` addition instead of `LongMath.checkedAdd`. This makes the overflow check in `validate()` ineffective against the value actually used in `execute()`.

### Finding Description
In `validate()`: [1](#0-0) 
the overflow check uses `accountCapsule.getBalance()` and `accountCapsule.getAllowance()` as read directly from the store, *before* any reward settlement for the current withdrawal is applied.

In `execute()`: [2](#0-1) 
`mortgageService.withdrawReward(...)` is invoked first. Inside it, `adjustAllowance(address, reward)` is called, which increases the account's persisted `allowance` field via `account.setAllowance(allowance + amount)`: [3](#0-2) 
After this, `execute()` re-reads the account (now with the newly increased `allowance`) and computes `oldBalance + allowance` using a plain `+` operator with no `checkedAdd`/overflow guard, then persists this value via `setBalance`.

Because the value checked in `validate()` (pre-`withdrawReward` allowance) can differ from the value actually added in `execute()` (post-`withdrawReward` allowance, which includes any newly-matured vote reward for the current cycle computed by `computeReward`/`adjustAllowance`), the `checkedAdd` safety check does not cover the actual arithmetic performed. If `oldBalance` is close to `Long.MAX_VALUE` and the reward credited by `withdrawReward` is large enough, `oldBalance + allowance` in `execute()` silently wraps to a negative `long`, and this corrupted value is persisted via `accountStore.put(...)`.

### Impact Explanation
The affected account's balance is written as a negative/wrapped `long`, permanently corrupting the account's `AccountCapsule.balance` field. This freezes/destroys the attacker's own funds and could also break any downstream logic that assumes non-negative balances (e.g. further transfers, fee deduction, freeze/unfreeze operations) for that account, since `AccountCapsule.setBalance` and related actuators do not universally re-validate for negative balances afterward.

### Likelihood Explanation
Exploitability requires the attacker to control an account whose `balance` is close to `Long.MAX_VALUE` and which has a large enough pending un-withdrawn vote/witness reward such that `withdrawReward()`'s `adjustAllowance` addition (`reward`) plus the existing `allowance`, when added to `balance`, exceeds `Long.MAX_VALUE`. This is an extreme precondition (near-max-long balance) that is unlikely in real economic conditions on mainnet, but it is programmatically reachable purely through a normal `WithdrawBalanceContract` broadcast — no privileged access, admin action, or off-chain component is required. The root cause (checked value in `validate()` diverging from the actual added value in `execute()`, and the final addition itself being unchecked) is a genuine code-level defect independent of how likely the preconditions are to occur.

### Recommendation
Replace the plain `oldBalance + allowance` addition in `execute()` with `LongMath.checkedAdd(oldBalance, allowance)`, and catch/handle the resulting `ArithmeticException` by failing the transaction (e.g., set `ret.setStatus(fee, code.FAILED)` and throw `ContractExeException`) rather than persisting a corrupted balance. This aligns `execute()`'s guarantees with the invariant `validate()` intends to enforce, and removes the reliance on a stale pre-`withdrawReward` snapshot.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/actuator/WithdrawBalanceActuatorOverflowTest.java
@Test
public void testWithdrawBalanceOverflow() throws Exception {
  byte[] owner = ...; // test address
  long hugeBalance = Long.MAX_VALUE - 100L;

  AccountCapsule account = new AccountCapsule(ByteString.copyFrom(owner), AccountType.Normal);
  account.setBalance(hugeBalance);
  account.setAllowance(0L); // pre-withdrawReward snapshot is small/zero, passes validate()'s checkedAdd
  accountStore.put(account.createDbKey(), account);

  // Configure delegationStore / vote data so that mortgageService.withdrawReward(owner)
  // computes a reward > 100 via adjustAllowance, e.g. reward = 1000L,
  // simulating a matured witness/vote reward larger than the remaining headroom to Long.MAX_VALUE.
  setupPendingReward(owner, 1000L);

  WithdrawBalanceActuator actuator = new WithdrawBalanceActuator();
  actuator.setChainBaseManager(chainBaseManager);
  actuator.setAny(buildWithdrawBalanceContract(owner));

  // validate() passes: checkedAdd(hugeBalance, 0) does not throw
  Assert.assertTrue(actuator.validate());

  TransactionResultCapsule ret = new TransactionResultCapsule();
  actuator.execute(ret);

  AccountCapsule after = accountStore.get(owner);
  // Expected (fixed) behavior: execute() should fail-fast/throw due to checkedAdd overflow,
  // and balance must never become negative.
  Assert.assertTrue("balance must not overflow/wrap negative", after.getBalance() >= 0);
}
```
Running this against the current (unpatched) code demonstrates `after.getBalance()` becoming negative because `execute()`'s plain `+` wraps, while `validate()` had already passed due to checking the stale, pre-`withdrawReward` allowance value.

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
