## Title
Replay-verification comparator silently ignores state/hot-state/position checkpoint root divergence - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated comparator used by replay/verification tooling (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `execution/executor/src/chunk_executor/mod.rs`) to assert that a locally re-executed transaction output matches the `TransactionInfo` committed to the ledger/accumulator. The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally recomputed state roots. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` computes and checks the transaction status, gas usage, write-set hash (`state_change_hash`) and event-root hash against the supplied `TransactionInfo`, and returns `Ok(())` unconditionally after those checks: [2](#0-1) 

The trailing comment in the same function is an explicit admission of the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This comparator is invoked as the authoritative match check by:
- `execution/executor/src/chunk_executor/mod.rs` — used during chunk replay/state-sync verification.
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` — used by the debugger's execution-replay path.
- `aptos-move/cli/src/commands.rs` — used by CLI replay/verify commands (e.g., `replay_on_archive`-style flows).

None of these call sites perform an independent check of `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` elsewhere in the replay path (this could not be fully confirmed for every caller given tool budget, but no such check surfaced in the chunk executor or debugger code paths inspected). The normal (non-replay) commit path does compute and store these checkpoint hashes as part of `TransactionInfoV1`/`do_state_checkpoint.rs`, but the *comparator that decides whether replayed/re-executed output "matches" the authenticated `TransactionInfo`* does not re-verify them.

Because the state-commitment invariant is "committed state that differs from the correct VM result must be detected," a comparator that is documented to accept an output whose state (or hot-state / position-native state, guarded by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature) diverges from the locally recomputed root is a proof/state-integrity gap: replay tooling used to audit historical ledger data (or verify chunk execution during fast/state sync replay verification) can report success even though the state root embedded in the `TransactionInfo` does not correspond to the actual resulting state tree.

### Impact Explanation
This breaks the invariant that "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" and that "replay paths...must not reinterpret committed data into a different ledger state." Concretely:
- `db-tool replay-verify` / `replay_on_archive`, the debugger's execution comparison, and CLI replay commands can all falsely certify a historical chunk as correctly replayed even when the state checkpoint hash (and, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, the position-native state root) diverges from what local execution actually produced.
- This undermines the guarantee that archive/replay verification detects state-corruption or non-determinism bugs, which is exactly the mechanism relied upon to catch consensus-breaking bugs before/after they reach mainnet. A state root divergence that would otherwise be caught by replay-verify tooling can pass silently.
- Because the gap is explicitly gated behind an unshipped feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS` for the position-hash part) but the `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields are already live in `TransactionInfoV1`, the gap for the standard (non-trading-native) checkpoint hash appears to already be present in shipped replay/verify tooling today.

### Likelihood Explanation
This does not require an attacker to control validator execution; it is a code path used by operators and auditors (self-inflicted integrity blind-spot) — it fires whenever the replay/verify tooling is used on chunk or historical data whose real execution produced a different state root than what is recorded, e.g., due to any other independent non-determinism/storage bug. The severity is contingent on there being an underlying state-computation divergence for the comparator to fail to catch; this comparator itself does not corrupt state, but neutralizes a detection safety net that these tools exist specifically to provide. I could not fully verify within the tool budget whether other layers (e.g., accumulator-root comparison elsewhere in `ReplayChunkVerifier`) already catch this independently for all callers, which is a meaningful source of uncertainty affecting the final severity call.

### Recommendation
Extend `ensure_match_transaction_info` (or its callers) to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `TransactionInfoV1`) against the state/hot-state/position summary produced by local re-execution, and fail replay/verification when any of them mismatch, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production, per the code's own TODO.

### Proof of Concept
Not independently reproducible as a runnable exploit within this investigation; the finding is a direct code-level proof from the function definition and its explicit TODO comment, combined with confirming that its known callers (`chunk_executor/mod.rs`, `aptos_debugger.rs`, `cli/commands.rs`) do not perform a supplemental checkpoint-hash comparison: [1](#0-0)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
