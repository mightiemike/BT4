### Title
Stale same-block `index-cache-` entry after `socialize-debt` write-down lets zToken collateral be overvalued for a subsequent borrow/liquidation in the same block - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`market.clar` caches each vault's liquidity/borrow index per `{ timestamp: stacks-block-time, aid }` key to avoid repeated cross-contract `vault-accrue` calls within the same block [1](#0-0) . This cache is populated the first time a given `aid` is touched in a block and is never invalidated again in that block. However, a vault's `lindex` can also be mutated directly and instantly by `socialize-debt`, completely bypassing `accrue-and-cache` [2](#0-1) . If `socialize-debt` runs after the market has already cached the pre-write-down index for that `aid` in the current block, any later operation in the same block that reuses the cache (via `accrue-and-cache`/`get-cached-indexes`) will read the stale, higher index/lindex instead of the corrected one.

### Finding Description
`market.clar` maintains:
```
(define-map index-cache- { timestamp: uint, aid: uint } { index: uint, lindex: uint })
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache- cache-key)))
    (match cached?
      existing existing
      (let ((fresh (vault-accrue aid))) (map-set index-cache- cache-key fresh) fresh))))
``` [1](#0-0) 

`liquidate()` populates this cache early via `accrue-user-debts`/`accrue-user-collateral`, uses it repeatedly for price/notional math throughout the function, and — for positions with no collateral left — calls `socialize-debt-asset`, which invokes the vault's `socialize-debt` [3](#0-2) [4](#0-3) .

`socialize-debt` writes a *new* `lindex` directly to vault storage (`var-set lindex new-lindex`) without going through `accrue()` and without touching or invalidating `market.clar`'s `index-cache-` map [2](#0-1) . This write-down is triggered by an event (bad debt socialization), not by the passage of time, so the market's cache key `{timestamp, aid}` — which is only meant to be safe because index changes are otherwise strictly time-gated — no longer reflects the true vault state for the remainder of that block.

Sequence:
1. Attacker (via a wrapper contract, or simply as the same tx-sender issuing back-to-back transactions in one block) causes a `liquidate()` call that socializes bad debt on vault `aid = X` (e.g., liquidating some borrower whose collateral fully covers the seized amount but leaves remaining unbacked debt). This call has already cached `{timestamp, X}` → old (higher) `lindex` earlier in its own execution, then calls `socialize-debt`, which writes a lower `lindex` directly into vault `X`'s state.
2. In the same block (same `stacks-block-time`), the attacker calls `borrow()` (or `collateral-add`/another `liquidate`) using zToken collateral backed by vault `X`. Price/notional resolution for that zToken calls `accrue-and-cache X`, which is a cache HIT on the stale, pre-write-down `{timestamp, X}` entry, returning the old higher `lindex`.
3. The zToken collateral is valued using the stale, inflated `lindex`, so the health check in `borrow()`/`liquidate()` overstates the attacker's collateral value, letting them borrow more than the vault's true (post-write-down) backing supports, or letting a subsequent liquidator receive an inflated `coll-final` seizure.

### Impact Explanation
Overstating zToken collateral value directly lets an attacker extract more debt tokens than their true collateral backs, or lets a liquidator seize more collateral than warranted — both are direct value extraction beyond what the protocol's actual (post-socialization) reserves support, i.e., theft of funds / protocol insolvency, which maps to the Critical impact class.

### Likelihood Explanation
This requires: (a) a bad-debt liquidation that triggers `socialize-debt` on a vault used as zToken collateral elsewhere, and (b) a same-block follow-up borrow/liquidate on that same `aid`. Both are attacker-controllable — an attacker can engineer their own under-collateralized position to trigger socialization, then immediately (same block) execute the exploiting borrow via a wrapper contract making both calls, or by racing a second transaction into the same block. No third-party cooperation or DAO action is required, making this realistically exploitable by a single actor.

### Recommendation
Invalidate (or actively overwrite) the market's `index-cache-` entry for the affected `aid` whenever `socialize-debt` executes, e.g., have `socialize-debt` return the new `{index, lindex}` and have `market.clar` `map-set` the cache immediately after any call that can mutate vault indexes outside of time-gated `accrue()`. Alternatively, route all index-affecting vault mutations (including `socialize-debt`) through `accrue-and-cache` so the cache is always refreshed synchronously with the true vault state.

### Proof of Concept
Conceptual reproduction within a single Clarity block:
1. Attacker sets up Position B (a small, deliberately bad-debt position with e.g. a tiny non-zToken collateral) such that liquidating it fully removes its collateral and triggers `bad-debt-socialized` on debt asset `aid = X`, invoking `.vault-X socialize-debt`, which drops `lindex` in vault X.
2. Attacker holds a large zToken-X collateral position (Position A) that is exactly borderline on health.
3. In one transaction (via an attacker-deployed helper contract, or as sequential transactions attacker controls within the same block):
   - Call `market.liquidate(...)` on Position B → triggers step 1's socialize-debt write-down of vault X's `lindex`, while `index-cache- {timestamp, X}` still holds the pre-write-down value from earlier in that call.
   - Call `market.borrow(...)` using zToken-X collateral from Position A → `accrue-and-cache X` returns the stale cached (higher) `lindex` (cache HIT), so Position A's collateral is valued higher than the true post-socialization backing, letting the attacker borrow beyond what their real collateral supports.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
