### Title
Unbounded growth of AccountsDb secondary indexes (`program_id`/`spl_token_mint`/`spl_token_owner`) from attacker-controlled account data — ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
The external report describes a peer being able to force unbounded, cost-free growth of a node's peer list by supplying arbitrary, unvalidated data (a self-declared IP) with no cap on list size. The equivalent unprivileged-user-reachable pattern in AccountsDb is the optional secondary-index feature (`--account-index program-id|spl-token-mint|spl-token-owner`): any unprivileged transaction sender can create accounts whose "owner"/"mint" fields (as read from raw account bytes) are attacker-chosen, and every such account is inserted into a `DashMap`-backed `SecondaryIndex` that has **no size limit and is not subject to the `AccountsIndex`'s bounded/threshold eviction machinery** that was recently added to `BucketMapHolder`/`InMemAccountsIndex`.

### Finding Description
`AccountsIndex::update_secondary_indexes` calls `update_spl_token_secondary_indexes`, which, for every stored account owned by a known token program, unpacks the "owner" and "mint" fields straight from the account's raw byte layout and inserts them into `spl_token_owner_index` / `spl_token_mint_index` (and `program_id_index` for every account's actual owner program): [1](#0-0) 

The insertion path is a bare `DashMap<Pubkey, SecondaryIndexEntryType>` plus a `reverse_index: DashMap<Pubkey, RwLock<Vec<Pubkey>>>`, with no capacity check, no memory-threshold eviction, and no age-based expiry: [2](#0-1) 

By contrast, the primary `AccountsIndex` in-memory maps now have an explicit, hardened bound (`IndexLimitThreshold`, high/low water marks, inline eviction, tombstone-clearing reallocation) specifically engineered to prevent unbounded memory growth from a flood of accounts/pubkeys: [3](#0-2) [4](#0-3) 

The secondary indexes have none of that protection. `AccountSecondaryIndexes::include_key` can be used by operators to exclude specific keys, but there is no default rate limit, no upper bound on the number of distinct outer keys (`index.len()`), and no eviction of stale/cheap entries — every account an attacker creates that happens to be owned by the SPL Token / Token-2022 program contributes at least one permanent entry (until the account is closed and cleaned), directly analogous to "no restriction on size of peer list" and "the node accepts whatever [value] the peer declares" in the reported bug.

### Impact Explanation
On any validator/RPC node that enables `--account-index program-id`, `spl-token-mint`, or `spl-token-owner` (a common configuration for RPC nodes), an unprivileged user can pay ordinary account-creation rent to mint large numbers of token-program-owned accounts with distinct fabricated owner/mint pubkeys embedded in the account data. Each contributes new entries to `SecondaryIndex::index` and `SecondaryIndex::reverse_index`, growing two `DashMap`s (plus per-entry `Vec<Pubkey>`/`RwLock`) without bound, unlike the primary index which now enforces a configured memory ceiling. This produces disproportionate memory/CPU cost on the honest node (DashMap resizing, lock contention, and `log_contents()`/stats overhead scale with entry count) relative to the attacker's cost, matching the "disproportionate storage and CPU cost" acceptance criterion.

### Likelihood Explanation
Medium: only nodes with secondary indexes enabled are affected (opt-in, common for RPC infra), and the state-consuming action (creating accounts) is already rent-metered, but the cost of driving unbounded secondary-index growth is far lower than the resulting per-node memory/CPU burden because there is no per-key/per-index cap, no `--account-index-exclude-key`-by-default protection, and the primary index's newly hardened eviction machinery does not apply here at all.

### Recommendation
Apply the same "hard limit + eviction" model recently added to `BucketMapHolder`/`InMemAccountsIndex` to `SecondaryIndex`: cap the number of outer keys and/or total inner-key entries per secondary index, evict least-recently-used or clearly cheap/likely-spam entries once the cap is hit, and expose configuration/metrics parity with the primary index's `IndexLimitThreshold` so operators running secondary indexes are not exposed to unbounded growth from attacker-controlled account data.

### Proof of Concept
1. Start a node with `--account-index spl-token-mint` (or `spl-token-owner`/`program-id`) enabled.
2. Repeatedly submit transactions that create new accounts owned by the SPL Token (or Token-2022) program, each with a distinct fabricated "mint" (or "owner") field crafted directly into the account's raw byte layout so it satisfies `GenericTokenAccount::unpack_account_mint`/`unpack_account_owner` (via `update_spl_token_secondary_indexes`, `accounts-db/src/accounts_index.rs:557-580`).
3. Observe `spl_token_mint_index.index`/`reverse_index` (`accounts-db/src/accounts_index/secondary.rs:113-171`) grow linearly with the number of accounts created, with no eviction or cap, unlike the primary `AccountsIndex` in-memory maps which are now bounded by `IndexLimitThreshold` (`accounts-db/src/accounts_index/bucket_map_holder.rs:121-143`).
4. Continue account creation until the node's memory/CPU overhead from secondary-index maintenance becomes measurably disproportionate to the attacker's rent expenditure.

impl<SecondaryIndexEntryType: SecondaryIndexEntry + Default + Sync + Send>
    SecondaryIndex<SecondaryIndexEntryType>
{
    pub fn new(metrics_name: &'static str) -> Self {
        Self {
            metrics_name,
            ..Self::default()
        }
    }

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }

        // explicitly drop the locks so we don't hold them while reporting metrics
        drop(outer_keys);
        drop(reverse_index_entry);

        if self.stats.last_report.should_update(1000) {
            datapoint_info!(
                self.metrics_name,
                ("num_secondary_keys", self.index.len(), i64),
                (
                    "num_inner_keys",
                    self.stats.num_inner_keys.load(Ordering::Relaxed),
                    i64
                ),
                ("num_reverse_index_keys", self.reverse_index.len(), i64),
            );
        }
    }

        }

    /// Returns true when a bin's HashMap free entries (`capacity - len`) are low
    /// enough that eviction should begin to prevent an imminent capacity doubling.
    /// The threshold is the overhead gap between `target_entries` and `high_water_mark`.
    pub fn should_evict_based_on_free_entries(&self, free_entries: usize) -> bool {
        match &self.threshold_entries_per_bin {
            None => self.is_disk_index_enabled(),
            Some(threshold_entries_per_bin) => {
                let overhead = threshold_entries_per_bin
                    .target_entries
                    .saturating_sub(threshold_entries_per_bin.high_water_mark);
                free_entries < overhead
            }
        }
