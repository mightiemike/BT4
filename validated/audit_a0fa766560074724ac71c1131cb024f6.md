### Title
Unchecked subtraction in `AccountStorageReader::new` can underflow when computing snapshot alive-byte length - (File: accounts-db/src/account_storage_reader.rs)

### Summary
`AccountStorageReader::new`, which is used when writing accounts storage files into snapshot archives, computes the number of "alive" bytes to include for a storage file using plain (non-saturating, non-checked) integer subtraction. This mirrors the reported `ClaggBaseAdapter._handleFee()` bug class: an arithmetic subtraction that assumes an ordering invariant (`total >= amount_being_subtracted`) that is not defensively enforced at the subtraction site, unlike comparable code elsewhere in the same codebase (e.g. `calculate_data_size_delta`, `bytes_removed` in `accounts_db.rs`) which explicitly use `saturating_sub`.

### Finding Description
In `AccountStorageReader::new`: [1](#0-0) 

```rust
let num_total_bytes = storage.accounts.len();
let mut num_alive_bytes = num_total_bytes - storage.get_obsolete_bytes(snapshot_slot);
...
if tombstones_filter == TombstonesFilter::Exclude {
    let tombstone_stored_size = storage.accounts.calculate_stored_size(0);
    let tombstone_offsets = storage.tombstone_offsets_read_lock();
    num_alive_bytes -= tombstone_offsets.len() * tombstone_stored_size;
    ...
}
```

Both subtractions (`num_total_bytes - storage.get_obsolete_bytes(...)` and the subsequent `num_alive_bytes -= tombstone_offsets.len() * tombstone_stored_size`) are plain `usize` subtractions with no `checked_sub`/`saturating_sub` guard and no debug/production assertion that the subtrahend cannot exceed the accumulator. This is structurally identical to the reported bug pattern: `gain = amount - (userInfo.deposited - userInfo.withdrawn)`, which assumed `deposited >= withdrawn` without verifying it, causing an underflow revert.

Here, the code implicitly assumes:
1. `storage.get_obsolete_bytes(snapshot_slot) <= storage.accounts.len()` (i.e., obsolete bytes computed from `filter_obsolete_accounts` plus `calculate_stored_size` never exceed the file's total bytes), and
2. `tombstone_offsets.len() * tombstone_stored_size <= num_alive_bytes` (post first subtraction) even though tombstone accounts are drawn from a *different* bookkeeping structure (`tombstone_offsets`) than the obsolete-accounts structure used to compute `num_alive_bytes` in step 1.

If tombstone accounting and obsolete-accounts accounting can ever double-count the same on-disk bytes (e.g., an account that is both marked obsolete for a given `snapshot_slot` cutoff and also recorded as a tombstone offset — both are separate tracking structures maintained by different code paths, as seen in tests that populate `tombstone_offsets` and `obsolete_accounts` from disjoint index sets but with no runtime invariant enforcing disjointness in production, e.g. `mark_accounts_obsolete` and `batch_insert_tombstone_offsets`), the second subtraction can underflow `usize`, which panics in debug builds and wraps to a very large value in release builds (validator binaries built with `overflow-checks` disabled by default in release profiles wrap silently).

This differs from the analogous, safer capitalization/size-delta code elsewhere in `runtime/src/bank.rs`, which is careful to use `saturating_sub` or explicit `Ordering` comparisons before subtracting lamports/data-size deltas: [2](#0-1) [3](#0-2) 

By contrast, `AccountStorageReader::new` does not apply the same defensive pattern, leaving it vulnerable to the same underflow bug class described in the report.

### Impact Explanation
`AccountStorageReader` is used from `snapshots/src/archive.rs` when packaging account storage files into full/incremental snapshot archives: [4](#0-3) 

If the subtraction underflows:
- In a debug/`overflow-checks`-enabled build, the validator process panics while generating a snapshot, causing a node crash/denial of availability for that node's snapshot-generation path.
- In a release build without overflow checks, `num_alive_bytes` wraps to a huge `usize` value. This value is used both as the externally reported length (`reader.len()`) and internally to bound reads (`self.num_total_bytes - excluded_start` in the `Read` implementation, itself also using non-saturating subtraction at `account_storage_reader.rs:159`), which can produce a corrupted/truncated/oversized account storage file being written into the snapshot archive — i.e., a snapshot whose account data diverges from what replay would produce, matching the "honest-node snapshot-vs-replay mismatch" impact category.

### Likelihood Explanation
This requires the scenario where an account storage file's tombstone/obsolete-account bookkeeping bytes exceed the storage's own total bytes at the point `AccountStorageReader::new` is invoked during snapshot packaging — something that should not happen under the codebase's normal invariants (tombstones and obsolete accounts are intended to reference disjoint, valid offsets within the storage). I was not able to fully trace the invariant proofs (e.g., whether `mark_accounts_obsolete` and `batch_insert_tombstone_offsets` are guaranteed to always be called with disjoint offset sets across all callers, including shrink/clean/flush paths) within the available tool budget, so I cannot confirm with certainty whether this underflow is currently reachable in practice or is fully prevented by upstream invariants not visible in the reviewed snippets. This uncertainty should be treated as a gap requiring further code-path tracing (e.g., a Devin session with full repository access) rather than a confirmed exploitable bug.

### Recommendation
Replace both subtractions in `AccountStorageReader::new` with `saturating_sub` (matching the pattern already used elsewhere in the codebase, e.g. `bytes_removed` in `accounts_db.rs` and `calculate_data_size_delta` in `bank.rs`), or add explicit `debug_assert!`/`checked_sub` guards that fail loudly (and are validated by tests) if `get_obsolete_bytes(...)` or the tombstone byte total would ever exceed the running `num_alive_bytes`/`num_total_bytes`. This converts a potential silent wraparound/panic into either a safe no-op or an explicit, diagnosable failure, and would also protect the `Read` implementation's own non-saturating subtraction at line 159 which relies on the same invariant.

### Proof of Concept
I could not construct a concrete, verified PoC within the available investigation budget because confirming the underflow requires proving that `storage.get_obsolete_bytes(snapshot_slot)` (from `obsolete_accounts.rs`) and `tombstone_offsets` (populated via `batch_insert_tombstone_offsets`) can reference overlapping or otherwise inconsistent byte ranges relative to `storage.accounts.len()` in some reachable production code path (e.g., a specific ordering of shrink/clean/flush operations). The existing unit tests in `account_storage_reader.rs` (`test_account_storage_reader_with_excluded_accounts`, `test_account_storage_reader_filter_by_slot`) exercise disjoint tombstone/obsolete index sets and do not cover an overlapping/adversarial scenario, so they do not rule this out. A background Devin session with full repository access and the ability to run/instrument the accounts-db test suite would be needed to either construct a concrete failing scenario or conclusively prove the invariant holds for all callers.
