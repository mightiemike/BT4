### Title
Uncaught `TypeError` from `new URL()` in `sanitizeHost` on crafted base64 `host` parameter causes unhandled exception instead of `InvalidHostError` - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` calls `new URL(`https://${decodeHost(sanitizedHost)}`)` without any `try/catch`. Because `decodeHost` is a plain `atob()` call, an attacker can base64-encode arbitrary bytes (including forbidden host code points like NUL, control characters, or embedded characters such as `<`, `>`, `^`, `|`, backslash) that decode into a string which the WHATWG `URL` parser rejects outright with a thrown `TypeError`, rather than simply returning an invalid/empty `hostname`. This exception is never converted into the library's `InvalidHostError` and propagates uncaught out of `sanitizeHost`.

### Finding Description
`sanitizeHost` only validates the *encoding* of the input with `base64regex` — it does not restrict what bytes decode to: [1](#0-0) 

`decodeHost` performs a raw `atob()`, mapping the base64 payload to a "binary string" with no filtering of control/forbidden characters: [2](#0-1) 

The result is fed directly into `new URL('https://' + decodedHost)` with no `try/catch`. Per the WHATWG URL Standard, forbidden host code points (NUL, TAB, LF, CR, space, `#`, `%`, `/` outside separator context, `:`, `<`, `>`, `?`, `@`, `[`, `\`, `]`, `^`, `|`) inside the host component of a special scheme (`https`) cause the parser to throw a `TypeError: Invalid URL`, rather than returning a degraded/invalid hostname. Since `sanitizeHost` has no exception handling around this call, the `TypeError` propagates uncaught to every caller.

Reachable, unprivileged attack surface: `sanitizeHost` is called directly on the attacker-controlled `host` query-string parameter in `validateShopAndHostParams` (used by `authenticate.admin()` in both `shopify-app-remix` and `shopify-app-react-router`) with no surrounding `try/catch`: [3](#0-2) 

and in `buildEmbeddedAppUrl`/`getEmbeddedAppUrl`, which also takes an unauthenticated `host` query parameter from the request URL:


Neither the `throwOnInvalid=false` path (`validateShopAndHostParams`) nor the `throwOnInvalid=true` path (`buildEmbeddedAppUrl`) can protect against this — the exception happens *before* the `InvalidHostError` branch is ever reached, because it originates from the `new URL()` call itself, not from the `hostRegex.test()` check.

Note: `packages/apps/shopify-api/lib/flow/validate.ts` (cited in the question header) does **not** call `sanitizeHost`/`sanitizeShop` at all — it only performs Flow HMAC validation via `validateHmacFromRequestFactory`. That file reference appears to be a mismatch/decoy; the actual vulnerable function and its real callers are as documented above.

### Impact Explanation
This is a Denial-of-Service condition in an authentication helper: any embedded-app request that reaches `authenticate.admin()` (remix/react-router) or `getEmbeddedAppUrl` with a crafted `host` query parameter can throw an uncaught `TypeError` instead of the expected graceful `InvalidHostError`/`null` return. Depending on how the surrounding framework (Remix loader/action, Express middleware) handles synchronous throws vs. promise rejections, this can manifest as an unhandled exception bypassing the library's intended fail-closed `InvalidHostError` semantics for the `DESTINATION_ALLOWLIST`/host validation invariant, and in the worst case (unhandled promise rejection with no process-level handler) crash the Node process, taking down the entire app for all merchants — a scoped DoS in an authentication handler.

### Likelihood Explanation
Trivial and fully unauthenticated: an attacker only needs to send a single HTTP GET request to any embedded-app route with a `host` query parameter equal to a base64 string that decodes to a hostname containing a forbidden host code point (e.g., a NUL byte or control character). No secrets, no prior session, no privileged role required. It is deterministically reproducible.

### Recommendation
Wrap the `new URL(...)` call in `sanitizeHost` in a `try/catch`, treating any thrown error as an invalid host (set `sanitizedHost = null`) so the function always falls through to the existing `InvalidHostError`/`null` contract:
```ts
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  try {
    const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
    // ...existing regex checks...
  } catch {
    sanitizedHost = null;
  }
}
```

```ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost should not throw on malformed decoded host', () => {
  const shopify = shopifyApi(testConfig());

  // decodes to "a\x00b.myshopify.com" — NUL is a forbidden host code point
  const maliciousHost = Buffer.from('a\x00b.myshopify.com/admin').toString('base64');

  // Expected: should return null (InvalidHostError semantics), not throw
  expect(() => shopify.utils.sanitizeHost(maliciousHost)).not.toThrow();
  expect(shopify.utils.sanitizeHost(maliciousHost)).toBeNull();
});
```
Running this against the current implementation throws an uncaught `TypeError: Invalid URL` from within `sanitizeHost` instead of returning `null`, confirming the unhandled-exception path.
