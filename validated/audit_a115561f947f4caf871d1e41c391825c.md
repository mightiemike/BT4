### Title
Unbounded recursion in compiled-class-hash computation over attacker-influenced bytecode segment structure causes sequencer stack-overflow crash - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
The reported `smol-toml` bug is a classic CWE-674 uncontrolled-recursion DoS: a deeply nested TOML input causes unbounded recursive descent and a stack overflow. The sequencer contains an analogous unbounded-recursion pattern in `bytecode_hash_node`, which walks a `NestedIntList` (`bytecode_segment_lengths`) with no depth limit while computing a declared class's compiled-class-hash, a step reachable from any unprivileged `declare` transaction.

### Finding Description
`SierraCompiler::compile` (invoked per-declare-transaction in the gateway/compiler component) compiles a user-submitted Sierra class to CASM via a resource-limited subprocess (`compile_with_args` with `ResourceLimits`, see `crates/apollo_compile_to_casm/src/compiler.rs:42-53`), then immediately calls `executable_class.hash(&HashVersion::V2)` **in the calling process itself**, outside any subprocess/resource sandbox: [1](#0-0) 

That `hash()` call dispatches to `hash_inner`, which calls `bytecode_hash`, which recurses through `bytecode_hash_node` over the `bytecode_segment_lengths: Option<NestedIntList>` field of the compiled `CasmContractClass`: [2](#0-1) 

This recursive walk has **no depth limit or iterative fallback**, unlike other recursive structures in the codebase that are explicitly depth-guarded (e.g. `RecursionDepthGuard` for Cairo entry-point recursion in `crates/blockifier/src/execution/entry_point.rs:706-733`, or the depth assertion in `NestedFeltCounts::new_inner`, `crates/blockifier/src/execution/contract_class.rs:168`). The `bytecode_segment_lengths` nesting structure is derived by the trusted Cairo compiler from the *control-flow/segmentation structure* of the submitted Sierra program (functions/branches), not merely from its total byte size; an attacker who controls the Sierra program's structure (e.g., long chains of single-statement nested functions/branches) can drive the compiler to emit a `NestedIntList::Node` chain whose nesting depth scales with the number of segments rather than being capped independently of `max_bytecode_size`. Since only `max_bytecode_size` (a flat size cap) is enforced (`crates/apollo_compile_to_casm/src/compile_test.rs:81-109`), and not a nesting-depth cap, a sufficiently deep/pathological program can drive `bytecode_hash_node` recursion deep enough to overflow the call stack of the **compiler-component process itself** — the same process that also serves subsequent Sierra-compile requests as a `ConcurrentLocalComponentServer` (`crates/apollo_compile_to_casm/src/communication.rs:12-27`).

The identical unbounded pattern also exists in `create_bytecode_segment_structure_inner` (`crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs:277-307`), reachable during Starknet OS re-execution of any block containing a declare of such a class.

### Impact Explanation
A stack overflow in Rust aborts the process (no catchable panic), so a crafted declare transaction can crash the `SierraCompiler` component process that handles class compilation/hashing for the gateway. Because this component is shared/concurrent (`ConcurrentLocalComponentServer`), crashing it denies service to all pending and future declare-transaction processing on that node, i.e. the node becomes unable to confirm new (declare) transactions until restarted — this matches the "network unable to confirm new transactions" impact bar. The same unbounded recursion in the Starknet OS hint utility additionally risks aborting OS re-execution/proving of blocks containing such a class.

### Likelihood Explanation
Reachable by any unprivileged account submitting a single `declare` (v3) transaction with a Sierra program engineered to produce deeply/pathologically segmented bytecode; no special privileges, contract deployment, or race conditions are required. The main uncertainty (which I could not fully verify without running the actual `cairo-lang-starknet-classes` segmentation algorithm) is exactly how deep a nesting the compiler can be coerced to produce within the `max_bytecode_size` limit — this determines whether realistic recursion depth reaches Rust's default stack size before hitting other CASM-generation limits.

### Recommendation
Impose an explicit maximum nesting-depth check (analogous to `RecursionDepthGuard`) when computing/traversing `bytecode_segment_lengths`, or convert `bytecode_hash_node` / `create_bytecode_segment_structure_inner` to explicit iterative (heap-allocated stack) traversal instead of native recursion, and reject/revert declare transactions whose segment structure exceeds the bound before hashing.

### Proof of Concept
Not independently reproduced (would require driving `cairo-lang-starknet-classes`'s bytecode segmentation with a crafted Sierra program and measuring resulting `NestedIntList` depth against `RUST_MIN_STACK`); this is the primary point of uncertainty flagged above.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
