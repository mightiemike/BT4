### Title
Missing Arbitrum Sequencer Uptime Check Before Consuming LINK/Native Price Feed for VRF Fee Estimation - ([File: core/services/vrf/v2/listener_v2_log_processor.go])

### Summary
The VRF v2/v2+ listener estimates the LINK fee owed for a randomness fulfillment by calling `AggregatorV3Interface.LatestRoundData()` directly on the LINK/ETH (or LINK/Native) price feed, with no check of the L2 sequencer uptime feed. On Arbitrum, if the sequencer is down, `LatestRoundData()` can return a stale/incorrect price without any indication of staleness, causing the node to miscompute the LINK amount required to fulfill randomness requests.

### Finding Description
`listenerV2.estimateFee` reads the price feed round data used to convert a gas-denominated fulfillment cost into LINK (Juels) owed by the subscriber: [1](#0-0) 

This calls `lsn.aggregator.LatestRoundData()` with only a 1-second timeout — there is no call to, or awareness of, an L2 sequencer uptime feed (e.g. Chainlink's `SequencerUptimeFeed` on Arbitrum) before trusting the returned answer. The `aggregator` here is bound directly to the LINK/ETH or LINK/Native `AggregatorV3Interface` deployed at the address returned by `coordinatorV2.LINKETHFEED()` / `coordinatorV2Plus.LINKNATIVEFEED()`: [2](#0-1) [3](#0-2) 

VRF is an explicitly supported/deployed coordinator type on Arbitrum, as shown by the `coordinator-type` flags accepting `"arbitrum"` throughout the VRF setup tooling and the dedicated `IsArbitrumChainID` helper: [4](#0-3) [5](#0-4) 

A repo-wide search confirms there is no `SequencerUptimeFeed`/"sequencer" check anywhere in the price-feed consumption paths (VRF, CCIP FeeQuoter feed reading, etc.) — the only occurrences of "sequencer" in the whole codebase are unrelated changelog text and an Arbitrum chain-config comment about block-liveness detection, not price-feed staleness protection.

### Impact Explanation
If the Arbitrum sequencer goes down, `LatestRoundData()` on the LINK/ETH price feed can return the last-known price/timestamp before the outage without any revert or staleness signal at the aggregator level. `estimateFee` will use this potentially stale `roundData.Answer` to compute `EstimateFeeJuels`, which directly determines the LINK amount charged to the subscriber's subscription for VRF fulfillment. Any unprivileged user who submits a `requestRandomWords` call (the standard, permissionless VRF consumer flow) during a sequencer outage can have their randomness fulfilled using a mispriced LINK/ETH rate — resulting in the subscriber being over- or under-charged relative to the true market price, and correspondingly the node operator being under- or over-compensated. This is a misreporting/data-tampering-class issue directly reachable by any external, unprivileged caller of the VRF service, not requiring any malicious node/operator behavior.

### Likelihood Explanation
Likelihood is tied to the (relatively rare but real) occurrence of Arbitrum sequencer downtime windows, which have occurred in production before. During any such window, exploitation requires no special privilege — any account with a funded VRF subscription can submit `requestRandomWords`, and the listener's fee-estimation path in `runPipelines`/`simulateFulfillment` will unconditionally call `estimateFee` on the live-configured price feed.

### Recommendation
Before trusting `LatestRoundData()` from the LINK/ETH or LINK/Native price feed in `estimateFee` (and any other Arbitrum/L2 price-feed consumption path), check the corresponding `SequencerUptimeFeed` (per Chainlink's documented [L2 Sequencer Uptime Feeds](https://docs.chain.link/data-feeds/l2-sequencer-feeds) pattern) and treat the price as stale/unusable if the sequencer is reported down or has been up for less than the configured grace period. If the sequencer status cannot be verified, the node should fall back to a configured `fallbackWeiPerUnitLink`/`fallbackNativePerUnitLink` value rather than trusting a potentially stale on-chain feed answer.

### Proof of Concept
1. Deploy/operate a VRF v2 or v2+ job against an Arbitrum-configured coordinator (`coordinator-type=arbitrum`), with `nativePayment=false` so `estimateFee` takes the LINK path.
2. Simulate/observe an Arbitrum sequencer outage window (sequencer offline, L1 forced-inclusion still allows new blocks/txs eventually, but the L2 price-feed aggregator's `updatedAt`/`answer` is stale relative to true market conditions).
3. During this window, submit `requestRandomWords` from an unprivileged subscriber contract.
4. Observe that `listenerV2.estimateFee` (`core/services/vrf/v2/listener_v2_log_processor.go:1064-1089`) calls `lsn.aggregator.LatestRoundData()` and uses the returned `Answer` directly in `EstimateFeeJuels` with no sequencer-uptime validation, producing a LINK fee calculation based on a stale/incorrect price.

```go
func (lsn *listenerV2) estimateFee(
	ctx context.Context,
	req RandomWordsRequested,
	maxGasPriceWei *assets.Wei,
) (*big.Int, error) {
	// NativePayment() returns true if and only if the version is V2+ and the
	// request was made in ETH.
	if req.NativePayment() {
		return EstimateFeeWei(req.CallbackGasLimit(), maxGasPriceWei.ToInt())
	}

	// In the event we are using LINK we need to estimate the fee in juels
	// Don't use up too much time to get this info, it's not critical for operating vrf.
	callCtx, cancel := context.WithTimeout(ctx, 1*time.Second)
	defer cancel()
	roundData, err := lsn.aggregator.LatestRoundData(&bind.CallOpts{Context: callCtx})
	if err != nil {
		return nil, fmt.Errorf("get aggregator latestAnswer: %w", err)
	}

	return EstimateFeeJuels(
		req.CallbackGasLimit(),
		maxGasPriceWei.ToInt(),
		roundData.Answer,
	)
}
```
