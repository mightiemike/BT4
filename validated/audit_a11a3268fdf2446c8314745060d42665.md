## Title
Deterministic contract address permits front-running griefing that permanently blocks `CreateSmartContract` transactions - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.create()`, invoked from `validate()` for every `CreateSmartContract` transaction, computes the new contract's address deterministically via `WalletUtil.generateContractAddress(trx)` and then rejects the whole transaction with a `ContractValidateException` if any account already exists at that address. Because the address is derived purely from public, pre-broadcast data (owner address + the transaction's raw-data hash), an unprivileged attacker who observes a pending `CreateSmartContract` transaction on the P2P network can pre-empt it by sending a trivial TRX transfer to the not-yet-existing predicted address, causing the legitimate deployment to permanently fail — a direct DoS/griefing analog of the reported `deploySAFE()` issue where a colliding deterministic-address deployment causes an unconditional revert of a legitimate operation.

### Finding Description
The contract address for a top-level contract creation is computed as: [1](#0-0) 

This is `sha3omit12(txRawDataHash || ownerAddress)`, entirely deterministic and computable by anyone who can see the transaction's raw data (owner address + all fields hashed into `raw_data`) *before* it is included in a block — which is exactly the state of any transaction sitting in the mempool/broadcast phase, since TRON transactions are gossipped across the P2P network prior to packing into a block.

`VMActuator.create()`, called from `validate()`, then performs a hard existence check on that address and throws if anything is already there: [2](#0-1) 

There is no fallback path analogous to a "check-if-contract-code-exists-and-reuse" strategy (as recommended in the external report); any existing account object — even a bare TRX-holding EOA created by an unrelated transfer — is sufficient to trip the `ContractValidateException` and abort validation of the deployment. This mirrors the root cause in the external report: a deterministic, front-runnable target address combined with an unconditional-failure path when that address is already occupied.

Unlike the CREATE2-from-inside-a-contract path in `Program.createContractImpl` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:827-833, 907-910`), which fails gracefully only the inner `CREATE`/`CREATE2` opcode (pushes zero on the stack and returns, without reverting the outer transaction) — behavior that already resembles the fix recommended in the report — the **top-level** deployment path in `VMActuator.create()` has no such graceful degradation: it throws directly out of `validate()`, which aborts the entire transaction.

### Impact Explanation
An attacker who observes a pending `CreateSmartContract` transaction (e.g., in the mempool, or via any node that has received but not yet confirmed it) can:
1. Compute the deterministic `contractAddress = sha3omit12(txRawDataHash || ownerAddress)`.
2. Send any transaction that creates an account at that address (e.g., a 1-sun TRX `TransferContract`) before the victim's `CreateSmartContract` transaction is confirmed.
3. Cause the victim's deployment transaction to permanently fail with `ContractValidateException("Trying to create a contract with existing contract address: ...")`, since the address is derived from the already-signed raw data (which cannot be altered without re-signing and producing a new address).

This is a concrete griefing/DoS impact: an unprivileged third party can deny a specific, chosen deployer's contract deployment with negligible cost (a single sun transfer plus bandwidth/energy for one transaction), forcing the victim to re-sign and rebroadcast (yielding a new unpredictable address) — repeatable indefinitely against a targeted deployer, and directly analogous to the cross-chain DAO counterpart-deployment blocking described in the source report.

### Likelihood Explanation
Likelihood is high for a motivated attacker: computing `sha3omit12` over publicly visible transaction bytes is trivial, front-running via simple fee/priority manipulation on a P2P-gossipped, unconfirmed transaction is a well-known and practiced technique, and the attack requires no special privileges, only network visibility into the mempool and the ability to submit an ordinary transfer transaction with higher priority/earlier inclusion.

### Recommendation
Do not unconditionally reject the deployment merely because an account exists at the predicted address. Instead, mirror the graceful handling already implemented for internal `CREATE`/`CREATE2` (`Program.createContractImpl`): only reject/abort if the existing account is already a *contract* (i.e., has code / `ContractCapsule` present), and if it is a plain EOA (e.g., created by an incidental transfer), upgrade it in place (as done for internal CREATE2 collisions and mirrored by `HistoryBlockHashUtil.deploy`), preserving its balance and proceeding with the deployment rather than failing the whole transaction.

### Proof of Concept
1. Alice submits a `CreateSmartContract` transaction `T` with fixed `raw_data` (owner address `A`, bytecode, timestamp, expiration, etc.).
2. `T` propagates via P2P before being packed into a block.
3. Attacker observes `T`, computes `txRawDataHash = sha256(T.raw_data)` and `contractAddress = sha3omit12(txRawDataHash || A)` per `WalletUtil.generateContractAddress` (`chainbase/src/main/java/org/tron/common/utils/WalletUtil.java:39-52`).
4. Attacker submits (and gets confirmed first) a trivial `TransferContract` sending 1 sun to `contractAddress`, creating an `AccountCapsule` there.
5. When `T` is processed, `VMActuator.create()` executes `rootRepository.getAccount(contractAddress) != null` → true, and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")` (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java:357-361`), permanently failing Alice's deployment transaction `T` (any resubmission of the identical signed `T` will fail the same way; Alice must re-sign with different raw data to get a new address).

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
