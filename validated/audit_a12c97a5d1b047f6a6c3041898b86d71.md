### Title
Division-before-multiplication truncates `netWeight`/`energyWeight` in bandwidth/energy limit calculation, allowing global resource limits to be under- or over-computed - ([File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java])

### Summary
The legacy (non-hardened) resource-limit formulas in `BandwidthProcessor.calculateGlobalNetLimit` and `RepositoryImpl.calculateGlobalEnergyLimit` compute an integer "weight" via `frozeBalance / TRX_PRECISION` *before* multiplying it by the limit/weight ratio, exactly mirroring the reported ditto bug pattern `eth * (timeTillMatch / 1 days)`. This causes the fractional portion of frozen balance below `TRX_PRECISION` (1,000,000 sun) to be discarded before the proportional scaling is applied, producing systematically lower bandwidth/energy limits than the mathematically correct value.

### Finding Description
In `BandwidthProcessor.calculateGlobalNetLimit`:
```
long netWeight = frozeBalance / TRX_PRECISION;
return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
``` [1](#0-0) 

and in `RepositoryImpl.calculateGlobalEnergyLimit`:
```
long energyWeight = frozeBalance / TRX_PRECISION;
...
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [2](#0-1) 

The division `frozeBalance / TRX_PRECISION` truncates to a whole-number "weight" before it is multiplied by the ratio `totalLimit/totalWeight`. Any fractional TRX below the `TRX_PRECISION` (1e6 sun) granularity is dropped from `frozeBalance` at this step, and that fractional loss is compounded when the weight is later scaled up by `totalLimit/totalWeight` (which can be large, e.g., tens of billions), unlike the ditto report where the truncation was capped at a small percentage — here the truncation of `frozeBalance` (up to `TRX_PRECISION - 1` sun) gets scaled by the (typically large) ratio `totalLimit/totalWeight`, amplifying the error in the final bandwidth/energy limit rather than shrinking it.

The codebase itself acknowledges this exact bug class: a "hardened" code path (`hardenCalculation()` / `allowHardenResourceCalculation`) was introduced specifically to fix it by multiplying before dividing using `BigInteger`:
```
protected long calculateGlobalLimitV2(long frozeBalance, long totalLimit, long totalWeight) {
  return BigInteger.valueOf(frozeBalance)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(TRX_PRECISION).multiply(BigInteger.valueOf(totalWeight)))
      .longValueExact();
}
``` [3](#0-2) 
with an explicit code comment describing that the legacy formula truncates weight before the multiply and the hardened version "preserves fractional weight ... through the multiplication and only truncated at the final divide." This comment directly documents the bug and confirms the legacy path is the vulnerable one, gated behind the `allowHardenResourceCalculation` dynamic property/hard fork switch. [4](#0-3) 

Both `calculateGlobalNetLimit` and `calculateGlobalEnergyLimit` still contain the un-hardened, truncation-prone branch guarded by `hardenCalculation()`/`hardenResourceCalculation()`; when this dynamic property is not yet enabled on a network, the vulnerable arithmetic path is reachable on every transaction that calls `useAccountNet`, `consumeBandwidthForCreateNewAccount`, and other bandwidth/energy consumption entry points that call `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`. [5](#0-4) [6](#0-5) 

### Impact Explanation
`calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` determine the total free bandwidth/energy an account is entitled to based on its frozen TRX. A truncated `netWeight`/`energyWeight` results in an incorrectly computed global limit for every account whose frozen balance is not an exact multiple of `TRX_PRECISION` (1 TRX), which is validated on every resource-consuming transaction (`useAccountNet`, `consumeBandwidthForCreateNewAccount`, `useAssetAccountNet`, and TVM energy accounting via `RepositoryImpl.calculateGlobalEnergyLimit`). This can cause legitimate transactions to be wrongly rejected for insufficient bandwidth/energy (DoS-like resource-accounting corruption) or, depending on rounding direction versus the hardened formula, allow slightly different resource consumption than intended, producing inconsistent accounting between nodes if the `allowHardenResourceCalculation` flag differs (a potential source of consensus divergence during the migration period between un-hardened and hardened nodes).

### Likelihood Explanation
This code path is reachable from ordinary, unprivileged broadcast transactions and RPC-triggered smart-contract calls — no privileged role is needed. Its impact depends on whether `allowHardenResourceCalculation` is enabled on the network in question; the presence of the hardened path and its explicit doc-comment referencing this exact truncation bug indicates the java-tron team already identified and patched this issue for networks that activate the flag, but the un-patched legacy formula remains present and reachable when the flag is off (e.g., on networks/forks that have not yet activated it, or during any transitional period).

### Recommendation
Ensure `allowHardenResourceCalculation` is activated on all networks and remove (or deprecate) the legacy un-hardened branches in `BandwidthProcessor.calculateGlobalNetLimit` and `RepositoryImpl.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimit`, always computing `frozeBalance * totalLimit / (TRX_PRECISION * totalWeight)` via `BigInteger` (multiply-before-divide), consistent with the already-implemented `calculateGlobalLimitV1`/`calculateGlobalLimitV2` hardened helpers.

### Proof of Concept
Given `frozeBalance = 1_999_999` sun (just under 2 TRX), `TRX_PRECISION = 1_000_000`, `totalNetLimit = 50_000_000_000`, `totalNetWeight = 1_000_000`:
- Legacy (buggy) path: `netWeight = 1_999_999 / 1_000_000 = 1`; result `= 1 * (50_000_000_000/1_000_000) = 50_000` — the correct weight of ~1.999999 is truncated to 1, roughly halving the computed limit versus the intended ~99,999 (`1.999999 * 50000`).
- Hardened path (`calculateGlobalLimitV1`/`V2`): `1_999_999 * 50_000_000_000 / 1_000_000 / 1_000_000 ≈ 99,999`, matching the mathematically correct proportional limit.

This matches the unit test `testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio`, which explicitly asserts the buggy formula `10000L * (totalEnergyLimit / totalEnergyWeight)` differs from the correct hardened result: [7](#0-6)

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
