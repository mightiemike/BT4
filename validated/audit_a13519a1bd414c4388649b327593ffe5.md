### Title
Vote reward is over-minted for votes cast late in a cycle, allowing a "flash-vote" attack analogous to the Sundial yield-token over-mint bug - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
The Sundial bug minted yield tokens proportional to the raw deposited amount instead of the properly "backdated" (start-of-period) principal amount, letting a late depositor claim a share of the whole period's yield. java-tron's DPoS vote-reward accounting has the same class of flaw: the per-witness reward-per-vote index (`Vi`) for a maintenance cycle is computed using the witness's vote total *as it stood before the current cycle's vote changes were applied*, but when an individual voter's reward is later computed, that same cycle's `Vi` delta is multiplied by the voter's **current** (post-change) vote weight instead of the weight that was actually reflected in that cycle's divisor. A voter (or a smart contract calling the TVM vote precompile) can cast a very large vote right before the maintenance boundary and later collect reward for the entire cycle as if they had held that vote weight throughout, diluting honest long-term voters exactly like the attacker in the Sundial PoC.

### Finding Description
Cycle reward accrual is split into two decoupled steps that use inconsistent vote-weight snapshots:

1. At the very start of `MaintenanceManager.doMaintenance()`, the per-witness value-index `Vi` for the cycle that just ended is accumulated using the *stale* `witness.getVoteCount()` — i.e., the vote total as it stood **before** this cycle's vote diffs are folded in: [1](#0-0) 

2. Only afterwards does `countVote(votesStore)` fold the current cycle's vote changes into `witnessCapsule.setVoteCount(...)`, and the updated total is stored only for the **next** cycle via `delegationStore.setWitnessVote(nextCycle, ...)`: [2](#0-1) 

3. `DelegationStore.accumulateWitnessVi` computes the cycle's reward-per-vote as `reward / voteCount`, where `voteCount` is that stale, pre-update total (`witness.getVoteCount()` from step 1): [3](#0-2) 

4. When a user changes their vote mid-cycle, `VoteWitnessProcessor.execute()` / `VoteWitnessActuator.countVoteAccount()` first flush any pending reward (using the *old* vote list), then immediately apply the new vote and set `beginCycle = currentCycle` (the very cycle in which the change occurred): [4](#0-3) [5](#0-4) 

5. Later, when reward is withdrawn, `computeReward` multiplies the *current* vote count (`vote.getValue()` from the live `AccountCapsule`) by `deltaVi` for that same cycle range, without regard for whether that vote weight was actually part of the divisor used in step 3: [6](#0-5) 

Because step 1 (the divisor for cycle N) is computed *before* the current cycle's vote changes are folded in, but step 5 (beginCycle set to N) lets the new vote start earning reward from cycle N itself, a large new vote cast late in cycle N is never included in the divisor for cycle N's `Vi`, yet is fully multiplied against that `Vi` when the voter later withdraws — an unbacked reward mint, structurally identical to the Sundial bug where the minted "yield" quantity used the raw deposit instead of the time-backdated principal.

### Impact Explanation
This allows an anonymous account (or any TVM contract calling `voteWitness`) to extract SR block/transaction-fee reward it did not economically earn, at the expense of long-term voters, purely by voting a large TRX-power position immediately before a maintenance boundary and withdrawing after the next one. This is an accounting/consensus-reward corruption bug: value is created out of thin air (over-minted allowance) or, symmetrically, the honest voters' share is diluted below what the reward pool for that cycle actually supports. This is reachable from a completely unprivileged, ordinary broadcast transaction (`VoteWitnessContract`, or the TVM `vote` precompile invoked by any contract), matching the "unauthorized asset/accounting corruption" criteria.

### Likelihood Explanation
Exploitation requires only: (1) freezing/acquiring TRON power (bandwidth/energy freeze, permissionless), (2) casting a `VoteWitnessContract` (or TVM vote) transaction timed shortly before a maintenance cycle boundary, and (3) withdrawing rewards afterward. No special privileges, leaked keys, or malicious peers are needed — timing relative to the ~6-hour maintenance interval is the only constraint, similar in spirit to the Sundial PoC's "deposit near the end of the period."

### Recommendation
Ensure the vote weight used to compute a cycle's `Vi` (the reward divisor) and the vote weight later used to multiply that same cycle's `deltaVi` for an individual voter are drawn from the same point-in-time snapshot. Concretely, either: (a) only start counting reward for newly added/changed votes from the cycle *after* they have actually been folded into the witness's total vote count (`nextCycle` in `MaintenanceManager.doMaintenance`), i.e., set `beginCycle = currentCycle + 1` rather than `currentCycle` when the change happens mid-cycle; or (b) store and use a per-cycle historical snapshot of each voter's vote weight (not the live `AccountCapsule` vote list) when computing `computeReward` for past cycles.

### Proof of Concept
1. Attacker freezes a small amount of TRX for TRON power at the very start of cycle N (to have a nonzero vote baseline), or has none previously.
2. Just before the maintenance boundary that ends cycle N, attacker broadcasts `VoteWitnessContract` (or calls the TVM vote precompile) casting a very large vote `B` for witness `W`.
   - `VoteRewardUtil.withdrawReward`/`countVoteAccount` flushes any (zero) prior reward, then sets the attacker's vote to `B` and `beginCycle = N`.
3. Maintenance runs: `MaintenanceManager.doMaintenance()` computes `Vi` for cycle N using witness `W`'s pre-update vote total `V_old` (excluding `B`), per `accumulateWitnessVi`; only afterwards does `countVote` fold `B` into `W`'s total for cycle `N+1`.
4. In cycle `N+1`, attacker withdraws reward. `MortgageService.computeReward`/`VoteRewardUtil.computeReward` computes `deltaVi[N] * B`, granting the attacker a reward for the *entire* cycle N as if `B` had been part of `W`'s vote weight throughout, even though `B` was never included in `V_old` used to derive `deltaVi[N]` — an unbacked payout funded by dilution of the other voters' rightful share of that cycle's fixed reward pool.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
