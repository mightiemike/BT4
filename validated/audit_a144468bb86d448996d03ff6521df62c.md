This confirms `sequencer_commitment_hashes` are always constructed in strict order corresponding to `sequencer_commitment_index_range` — e.g. by `apply_l2_blocks_from_sequencer_commitments` (`crates/citrea-stf/src/verifier.rs:65-86`) which sequentially processes commitments and pushes hashes in the same order as the index range, and this same ordering invariant is committed as part of the SNARK's public journal.

### Analysis

**Binding claimed broken:** `sequencer_commitment_hashes[i]` (position `i` in batch-proof journal) `== JMT-stored commitment hash at index (first+i)`.

**Trace:**
1. The journal's `sequencer_commitment_index_range` and `sequencer_commitment_hashes` are produced by the batch-proof circuit itself (`apply_l2_blocks_from_sequencer_commitments`), which processes commitments sequentially by index and pushes `sequencer_commitment_hashes` in the same order, so the invariant holds by construction inside the honest proof. [1](#0-0) 
2. In the light-client circuit, `Z::extract_raw_output` / `Z::deserialize_output` merely parses bytes from the proof blob into `BatchProofCircuitOutput` — this parsing happens before `Z::verify` is called. [2](#0-1) 
3. `Z::verify` is called with the raw proof bytes and the expected `batch_proof_method_id`, and only if this succeeds does `process_complete_proof` proceed to call `verify_batch_proof_seq_comm_relation`. [3](#0-2) 
4. Since the journal bytes are exactly what `Z::verify` checks against the SNARK proof (or in `MockZkvm`/receipt-based test paths, against the `FakeReceipt`/`MockProof` claim), an attacker cannot mutate the `sequencer_commitment_hashes` ordering or the index range independently of the proof body — any mutation of the journal that changes `sequencer_commitment_hashes` order (while keeping `last-first+1 == len`) would make `Z::verify` reject the proof, per the question's own stated precondition.
5. Even hypothetically bypassing that (which the question explicitly excludes as out of scope — "Z::verify... would reject a forged proof body"), the loop at lines 182-186 zips `(first_index..=last_index)` with `batch_proof_output_sequencer_commitment_hashes` **in the order given in the journal**, then for each `i` fetches the actual `SequencerCommitmentAccessor::<S>::get(index)` from JMT state (an independent, attacker-uncontrolled source of truth) and computes `jmt_commitment_hash = jmt_commitment.serialize_and_calculate_sha_256()`, comparing it against `batch_proof_sequencer_commitment_hash` from the (possibly reordered) journal. [4](#0-3) 
6. Reordering the hashes in the journal doesn't help the attacker: for the check to pass at every position `i`, the hash placed at position `i` in the journal must equal the SHA-256 of the actual, distinct `SequencerCommitment` stored at JMT index `first+i`. A "shuffled" hash list can only pass this loop if it happens to be shuffled back into the **correct** order (i.e., not actually shuffled relative to true indices), or if two distinct commitments produce colliding SHA-256 hashes — which is a hash-collision attack, out of scope.

**Both sides of the equality re-evaluated:** Before: journal claims `hashes[i]` for index `first+i`. After the loop: verified `hashes[i] == sha256(JMT_commitment[first+i])` for every `i` in range, which is precisely the binding needed — the check does not "trigger acceptance of reordered indices" as claimed; it independently re-derives the truth from JMT storage and compares position-by-position, so any actual reordering is caught.

The length check at lines 170-180 only guards array-bounds/well-formedness (ensuring the zip is total over the range) — it is not, by itself, the safety property; the per-position hash comparison at lines 215-223 is what enforces the binding, and it does so correctly regardless of what order the attacker claims in the journal, because the comparison target (`jmt_commitment_hash`) is derived independently per index from trusted state, not from the attacker's array.
