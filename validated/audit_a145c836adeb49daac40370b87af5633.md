Confirmed: `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, and this function is the sole correctness gate used by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`. I have enough to write up the finding.

### Title
Replay-verify (`replay_on_archive`) accepts locally re-executed transactions whose position/state checkpoint roots diverge from the archived, ledger-info-authenticated `TransactionInfo` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the only correctness check `db-tool replay-on-archive` runs between locally re-executed output and the trusted, backup-sourced `TransactionInfo` for each transaction. It checks status, gas, write-set hash, and event root, but the code explicitly, deliberately skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the JMT state root, hot-state root, and native-position state root committed on-chain, per [1](#0-0) . Because of this, `replay_on_archive::execute_and_verify` ( [2](#0-1) ) will report a transaction chunk as fully verified even when the locally computed state/position root diverges from what mainnet actually committed.

### Finding Description
`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as authenticated fields bound into the transaction-accumulator leaf hash [3](#0-2) . These fields are what "prove" the correctness of a specific state-commitment (main JMT root, hot-state root, native "trading" position-state root, respectively) for a version, and they're what state-sync's fast-sync path treats as the sole authenticated anchor for position-state sync (`snapshot_kind_applies_to_target`/`expected_snapshot_root` in `state-sync/state-sync-driver/src/bootstrapper.rs` explicitly rely on `position_state_checkpoint_hash` being present and correct: [4](#0-3) , [5](#0-4) ).

However `TransactionOutput::ensure_match_transaction_info` — the function used by `db-tool replay-on-archive` to confirm that re-executing archived transactions against a real, standalone VM reproduces the mainnet-committed result — only verifies `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root. It explicitly and knowingly omits validating `state_checkpoint_hash`, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` against the locally-computed roots, as stated in the code's own comment:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [6](#0-5) 

This is invoked directly, with no additional checkpoint validation layered on top, by the replay-verify tool: [7](#0-6) 

The same gap exists in the debugger's mismatch-printing path, `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches`, which also calls `ensure_match_transaction_info` with no follow-up state-root comparison [8](#0-7) .

Note that separate transport-level verifications, such as `TransactionOutputListWithProof::verify` (used for state-sync fetches over the network) and `fake_aptosdb.rs::verify_txn_outputs`, also do not check the checkpoint hashes, but those methods don't claim to validate state-root correctness — write-set hash suffices there because state-sync recomputes state independently via the DB's own execution/commit pipeline. `ensure_match_transaction_info` is different: it is the dedicated hard-fork/mainnet integrity check whose entire purpose is to detect *execution divergence*, and it is missing exactly the fields that would catch a divergence in the newly introduced native-position/hot-state commitment logic (`compute_trading_native_state_roots`, `hot_state_root_in_txn_info`).

### Impact Explanation
`replay_on_archive` (and the debugger's mismatch tool) is the primary tooling used to certify that a build of the execution/VM pipeline correctly reproduces mainnet history — e.g., before a validator upgrade, or to detect a state-divergence bug in `compute_trading_native_state_roots`/hot-state-root logic. Because `ensure_match_transaction_info` silently ignores `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, a build with a bug that corrupts the JMT root, hot-state root, or native-position state root (while still producing a byte-identical write set and events) would pass replay-verify with a "successful replay" result. This is exactly the state-commitment integrity gate the task calls out: an authenticated, proof-bearing field (`TransactionInfo`, which is what's checked against the transaction accumulator / ledger info) is not actually being checked at the one place designed to catch execution-vs-history divergence, undermining the guarantee that "committed state differs from the correct VM result" gets caught before it's trusted.

### Likelihood Explanation
Likelihood of the check itself firing incorrectly is high given `compute_trading_native_state_roots` and `hot_state_root_in_txn_info` are newly introduced experimental features (as evidenced by extensive TODO comments referencing them throughout `execution/executor` and `storage/aptosdb`), and the code comment itself flags this exact scenario as a known, not-yet-fixed gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"). Since the check is unconditionally skipped regardless of whether the feature is on, any latent bug in the new position/hot-state commit path is undetectable via this tool today.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to independently recompute (or accept as a parameter) the local `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` and assert they match `txn_info`'s corresponding fields whenever those fields are `Some` in the expected `TransactionInfo`, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` on mainnet.

### Proof of Concept
1. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) against a backup range where `TRANSACTION_INFO_V1` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are active on-chain features.
2. Introduce (or trigger, via a genuine bug) a local execution divergence that only affects the native-position state tree or hot-state tree — e.g., a bug that mis-applies a `native_position_iter()` write during `NativeStateCommitter::apply` (`storage/aptosdb/src/native_state_committer.rs`) — while leaving the ordinary write set, events, gas, and status untouched.
3. Observe that `execute_and_verify` calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(...), Some(...))` (`storage/db-tool/src/replay_on_archive.rs:392-397`) and this returns `Ok(())` because it never compares `position_state_checkpoint_hash`.
4. The tool reports zero failed transactions ("successful replay"), even though the locally recomputed native-position/hot-state root diverges from what was actually authenticated on mainnet via the transaction accumulator.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())

    /// The expected snapshot root for the given kind at the target version, read
    /// from the target transaction info: main state's state checkpoint hash, or
    /// the committed position state root (guaranteed present once the position
    /// stage runs, per `snapshot_kind_applies_to_target`). All kinds share the
    /// target version, so this is taken from the target output, not a storage read.
    fn expected_snapshot_root(&mut self, kind: StateKind) -> Result<HashValue, Error> {
        let transaction_output_to_sync = self.get_transaction_output_to_sync()?;
        let target_transaction_info = transaction_output_to_sync
            .get_output_list_with_proof()
            .proof
            .transaction_infos
            .first()
            .ok_or_else(|| {
                Error::UnexpectedError("Target transaction info does not exist!".into())
            })?;
        match kind {
            StateKind::MainState => target_transaction_info
                .ensure_state_checkpoint_hash()
                .map_err(|error| {
                    Error::UnexpectedError(format!(
                        "State checkpoint must exist! Error: {:?}",
                        error
                    ))
                }),
            StateKind::Position => target_transaction_info
                .position_state_checkpoint_hash()
                .ok_or_else(|| Error::UnexpectedError("Missing position state root!".into())),
        }
