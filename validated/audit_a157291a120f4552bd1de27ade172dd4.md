### Title
Gateway's per-address declare authorization can be bypassed via the unauthenticated bootstrap-declare path - (File: crates/starknet_api/src/executable_transaction.rs, crates/blockifier/src/transaction/account_transaction.rs)

### Summary
The gateway enforces per-account declare authorization through `GatewayConfig::is_authorized_declarer` / `Gateway::check_declare_permissions`, which is meant to be the sole access-control gate for who may declare a new class. However, this authorization check is only a sender-address allow-list check, and the execution layer (`blockifier`) contains a special "bootstrap declare" code path keyed purely off a hardcoded, publicly known sender address (`'BOOTSTRAP'`) that skips signature verification, `__validate_declare__` execution, and nonce enforcement entirely. Because `is_authorized_declarer` defaults to "allow all" (`None => true`) when `authorized_declarer_accounts` is not configured, any unauthenticated transaction sender who crafts a declare transaction using this special address can reach a privileged, validation-free class-declaration path that was intended only for genesis bootstrapping.

### Finding Description
`GatewayConfig::is_authorized_declarer` [1](#0-0)  is the only address-based authorization gate applied to declare transactions, invoked from `Gateway::check_declare_permissions` in `add_tx_inner` [2](#0-1) . When `authorized_declarer_accounts` is unset (the default, confirmed by the deployment overlay setting it empty/`is_none: true`) [3](#0-2) , every sender address — including the hardcoded bootstrap sender — is treated as authorized.

Separately, `DeclareTransaction::is_bootstrap_declare` and `DeclareTransaction::bootstrap_address` define a special, publicly-derivable sender address (`0x424f4f545354524150`, the ASCII encoding of `'BOOTSTRAP'`) that is meant to let the sequencer self-initialize a new chain: any V3 declare with `sender_address == bootstrap_address()`, `nonce == 0`, and `!charge_fee` is treated as a fee-free, validation-free class declaration [4](#0-3) . In `AccountTransaction::execute_raw`, when `is_bootstrap_declare` is true, the transaction skips `perform_pre_validation_stage` (nonce/fee checks) and the entire validate/execute pipeline, going straight to declaring the class in state [5](#0-4) . The equivalent Starknet OS Cairo hint applies the same bypass, skipping `__validate_declare__` when `sender_address == 'BOOTSTRAP' and tx_info.nonce == 0 and tx_info.version == 3` and `max_possible_fee == 0` [6](#0-5) .

This mirrors the reported Open WebUI bug class exactly: one entry point (`generate_chat_completion` / normal declare via a regular account) enforces full authorization, while a second, structurally similar entry point (`/responses` / the bootstrap declare code path) is reachable by any caller who merely knows a magic identifier, and skips the authorization/validation checks that the "main" path enforces. Here, the "magic identifier" is the well-known bootstrap contract address, and the skipped checks are signature verification, nonce enforcement, and (implicitly) declarer-authorization intent, since the gateway's declarer allow-list was never designed with this special address in mind.

### Impact Explanation
If a deployment does not explicitly configure `authorized_declarer_accounts` (the shipped default, per the hybrid deployment overlay), any unauthenticated party can submit a declare transaction from the bootstrap address with nonce 0 and zero-fee resource bounds. This transaction:
- Bypasses `__validate_declare__`/signature verification entirely (unauthorized action performed "as" the bootstrap identity).
- Bypasses nonce enforcement, meaning the same "bootstrap" identity can be reused for spam/interference by anyone, not just the legitimate node operator running the real genesis bootstrap sequence.
- Declares arbitrary classes for free, undermining declare fee accounting and the "declarer allow-list" access-control model the gateway is supposed to provide.
- Per the code comments, since no account-related action is performed, the batcher does not notify the mempool of inclusion, so the transaction remains in the mempool and gets re-proposed until it fails on re-declaration — an operator-facing correctness/DoS side-effect distinct from, and compounding, the authorization bypass.

This satisfies "unauthorized account action" and creates a real risk of interfering with legitimate chain bootstrapping/administration, and of a mempool/consensus divergence if honest nodes handle the resulting rejection differently across implementations.

### Likelihood Explanation
The precondition is that the deployment leaves `authorized_declarer_accounts` unset, which is exactly the shipped default in the reviewed hybrid deployment configuration. The attacker needs no privileges beyond the ability to submit any other declare transaction, and the bootstrap address and required nonce/version fields are all public constants derivable from the open-source code. The remaining unverified variable is whether `enforce_fee` (in `crates/blockifier/src/transaction/objects.rs` / `transactions.rs`) can be forced to return `false` for an attacker-supplied, non-query V3 declare purely via resource-bounds selection — I was not able to fully trace this function before running out of investigation budget, so likelihood is stated with that caveat.

### Recommendation
- Gate the bootstrap-declare bypass on more than sender address/nonce/fee — e.g., require it only be honored when the state is genesis/empty (as `GenesisStateReader` already models) or via an explicit node-operator-controlled flag, not solely on values fully controlled by the transaction sender.
- Make `authorized_declarer_accounts` deny bootstrap-style special addresses by default, or reject any declare from `DeclareTransaction::bootstrap_address()` once the chain has left genesis.
- Ensure `is_authorized_declarer`'s default-allow behavior does not inadvertently authorize the bootstrap identity in production deployments.

### Proof of Concept
1. Deploy with default gateway config (`authorized_declarer_accounts` unset, matching `deployments/sequencer/configs/overlays/hybrid/common/services/gateway.yaml`).
2. Craft a V3 `RpcDeclareTransaction` with `sender_address = 0x424f4f545354524150` (`DeclareTransaction::bootstrap_address()`), `nonce = 0`, empty signature, and resource bounds equivalent to `ValidResourceBounds::create_for_testing_no_fee_enforcement()` (as used by `generate_bootstrap_declare` in `crates/mempool_test_utils/src/starknet_api_test_utils.rs:585-595`).
3. Submit via the normal gateway `add_tx` RPC endpoint; `check_declare_permissions` passes because no allow-list is configured.
4. On execution, `AccountTransaction::execute_raw` detects `is_bootstrap_declare == true` and declares the class without executing `__validate_declare__`, without a valid signature, and without charging a fee.

Note: full confirmation that `enforce_fee` allows an attacker to reach `charge_fee == false` outside of the intended genesis/test-only flow was not completed due to tool-call exhaustion; this should be verified against `crates/blockifier/src/transaction/objects.rs::enforce_fee` before treating this as fully proven in a running production network.

    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
            }
        }
