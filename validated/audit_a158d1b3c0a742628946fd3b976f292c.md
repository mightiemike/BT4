### Title
Market maker orders that are completely filled still don't receive the stated target buy-token amount due to floor-division rounding - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` implements a decentralized-exchange order book for TRC10 tokens, reachable by any account via a broadcast `MarketSellAssetContract` transaction. When a taker order matches and fully consumes a maker's resting order, the amount of buy-token credited to the maker is computed using floor (truncating) integer division rather than being rounded up to match the order's stated price ratio, exactly mirroring the audited GroupBuy bug pattern: a fully-filled position still fails to raise/receive the full stated target amount.

### Finding Description
In `matchSingleOrder`, when a maker order is fully consumed, the buy-token amount owed to the maker is derived via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, an integer multiply-then-divide operation: [1](#0-0) 
This is the "taker == maker" branch, where the maker's `sellTokenQuantityRemain` is set to `0` (i.e., the order is completely filled), but `makerBuyTokenQuantityReceive` is derived from a ratio calculation that truncates any remainder rather than rounding up: [2](#0-1) 
The same pattern recurs in the "taker > maker" branch, where the maker order is again driven to zero remaining sell quantity while its buy-token receipt is computed with the same floor-rounding helper: [3](#0-2) 
The order's price ratio is defined by `sellTokenQuantity : buyTokenQuantity` set at order creation: [4](#0-3) 
Because `makerSellRemainQuantity * makerBuyQuantity` is not always evenly divisible by `makerSellQuantity`, floor division causes the buy-token amount credited to a maker whose sell-side has been driven to exactly `0` remaining to be strictly less than the proportional target implied by the order's original `sellTokenQuantity : buyTokenQuantity` ratio — the exact analog of GroupBuy's `minBidPrices[currentId] = _initialPrice / _totalSupply` under-collecting when `_totalSupply` is fully consumed.

Note: I could not locate the exact source file/line defining `MarketUtils.multiplyAndDivide` within the time available (it is imported and called from `org.tron.core.capsule.utils.MarketUtils`, but a targeted grep against that specific file did not surface the method body), so the precise rounding mode (floor vs. some other mode) could not be independently verified beyond inference from the codebase's consistent `floorDiv`/`divide()` (no rounding mode) pattern seen elsewhere, e.g. in `ExchangeInjectActuator`: [5](#0-4) 

### Impact Explanation
A maker who places a sell order via `MarketSellAssetContract` expects that once their order is fully filled (sell quantity remaining reaches zero), they will receive the full proportional buy-token amount implied by their stated `sellTokenQuantity`/`buyTokenQuantity` ratio. Due to floor-division rounding in the fill-crediting logic, the maker systematically receives less than this stated target. Losses are individually small per fill but can recur across every partial match against a given resting order (up to `MAX_MATCH_NUM = 20` matches per taker transaction, and potentially many taker transactions over an order's lifetime), and there is no reconciliation or "catch-up" mechanism once the order is fully consumed and removed from the book. This is a real, if likely low-magnitude-per-trade, value leakage from ordinary DEX users' accounts, reachable purely by broadcasting standard transactions — falling under "asset or accounting corruption" for the exchange feature.

### Likelihood Explanation
Likelihood is moderate: the condition requires only ordinary usage of the TRC10 exchange feature (placing and matching orders with non-evenly-divisible quantity ratios), which is common since users are free to choose arbitrary `sellTokenQuantity`/`buyTokenQuantity` values. No special privileges, malicious peers, or leaked keys are required — any two ordinary accounts broadcasting `MarketSellAssetContract` transactions can trigger it.

### Recommendation
Round the maker's credited buy-token amount up (ceiling) rather than truncating (floor) whenever a fill drives the maker's remaining sell quantity to zero, so that the sum of buy-token amounts credited across all partial fills is never less than the amount implied by the order's original stated ratio. This mirrors the mitigation recommended in the source report: switch from floor rounding to ceiling rounding for the final/exact-consuming leg of the calculation. This should be applied consistently to the analogous branches in `matchSingleOrder`.

### Proof of Concept
1. Maker places a sell order for `sellTokenQuantity = 3`, `buyTokenQuantity = 10` (ratio 3:10) via `MarketSellAssetContract`.
2. Two takers each fill part of the order such that the sell side is driven to `0` remaining across two partial matches, e.g., taker A consumes `1` sell unit, taker B consumes the remaining `2` sell units.
3. Each partial fill computes `makerBuyTokenQuantityReceive` via `multiplyAndDivide(remainQty, 10, 3)`, e.g., for remainQty=1: `10/3 = 3` (floor) instead of `3.33`; for remainQty=2 against the (now smaller) remaining sell base, a similar truncation occurs.
4. Summing the buy-token credited to the maker across both fills yields less than the exact `10` implied by the full order ratio, while the maker's sell side is fully exhausted (`sellTokenQuantityRemain == 0`) and the order is removed from the book with no further recourse — verifying the "fully filled but under target" condition analogous to the GroupBuy report.
