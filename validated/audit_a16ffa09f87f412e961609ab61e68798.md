## Analysis

The EIP‑7251 report reduces to a single invariant: *a validator/authenticated-value binding check must cover every distinguishing field of the value being verified, not a subset.* Missing a variant/field silently lets divergent state pass as valid. I looked for an Aptos analog in commit/replay/restore integrity checks and found one that is self-documented as incomplete in the code itself.

### Title
`TransactionOutput::ensure_match_transaction_info` never verifies the state/hot-state/position-checkpoint root hashes, letting replay-verify and restore flows accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by chunk replay, backup restore, `replay_on_archive`, and the Aptos debugger/CLI to confirm that a locally re-executed `TransactionOutput` matches the trusted, already-committed `TransactionInfo`. It only checks `status`, `gas_used`, `state_change_hash` (the write-set hash) and `event_root_hash`. It does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, all of which are part of `TransactionInfo`/`TransactionInfoV1` and represent the authenticated Sparse-Merkle-Tree/state root commitments. [1](#0-0) [2](#0-1) 

### Finding Description
`TransactionInfoV1`/`TransactionInfoV0` carry multiple root-hash fields binding a transaction to the post-execution ledger state: `state_change_hash` (write-set hash), `event_root_hash`, `state_checkpoint_hash` (SMT/JMT state root), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`. [3](#0-2) [4](#0-3) 

`ensure_match_transaction_info` is the sole function used to cross-check a freshly-computed `TransactionOutput` against a previously-persisted/downloaded `TransactionInfo` in replay and restore contexts (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`, `storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`). It verifies status, gas, write-set hash, and event root, but the code contains its own acknowledgment that the state/hot-state/position checkpoint hashes are skipped: [5](#0-4) 

Because `state_change_hash` only commits to the write set bytes, and not to the resulting Merkle root, two different underlying state trees (e.g. a JMT corrupted by a storage bug, a non-deterministic apply of hot-state records, or a `position_state_checkpoint_hash`/"trading native" state root diverging due to a hard-fork-only VM bug) can produce byte-identical write sets while their actual committed state roots diverge. `ensure_match_transaction_info` will report a match in that case, since it never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` against the trusted `TransactionInfo`.

### Impact Explanation
This breaks the intended integrity guarantee of replay-verify and restore tooling: these flows exist specifically to detect exactly this class of bug — silent state-root divergence, e.g., during a hard fork or storage-layer corruption — by comparing locally computed results with the network-committed `TransactionInfo`. If the check silently ignores the state-root fields, a validator or archive operator using replay-verify (`aptos-move/cli/src/commands.rs`, `storage/db-tool/src/replay_on_archive.rs`, `storage/backup/backup-cli/src/coordinators/replay_verify.rs`) can be told replay succeeded even though the SMT/hot-state/position-checkpoint root diverges from the authenticated value, i.e., "committed state that differs from the correct VM result... accepted as valid" for restore/replay verification purposes.

### Likelihood Explanation
The gap is deterministic and always present, not a race condition — it's a structural omission in the comparison function, confirmed by the in-code TODO comment. Triggering an actual observable failure requires an independent root cause (e.g., a JMT/hot-state computation bug or a hard-fork-only divergence), but once such a divergence exists, this check would silently mask it rather than flag it, defeating the safety net that replay-verify/restore is meant to provide.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/known) between `txn_info` and the locally recomputed checkpoint output, consistent with how `state_change_hash` and `event_root_hash` are already validated, before enabling any feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that relies on `position_state_checkpoint_hash` for correctness. [6](#0-5)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
