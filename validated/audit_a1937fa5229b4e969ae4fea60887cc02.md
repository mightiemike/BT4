### Title
DelegateAction (meta-transaction) signatures lack any chain/network-binding identifier, enabling cross-chain signature replay - (File: `core/primitives/src/action/delegate.rs`)

### Summary
The NEP-366 meta-transaction `DelegateAction`/`DelegateActionV2` payload that a user signs contains only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — no genesis hash, chain identifier, or block hash binding it to a specific network. Unlike regular `Transaction`s, which carry a `block_hash` that is validated against the actual chain history via `check_transaction_validity_period`/`validity_period_validate_is_ancestor`, a `SignedDelegateAction`'s cryptographic validity check (`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify`) is nothing but a signature-over-hash check with no chain-specific salt.

### Finding Description
`SignedDelegateAction::verify` computes the NEP-461 hash purely from the `DelegateAction` fields and checks the signature against it: [1](#0-0) 

The `DelegateAction` struct itself has no chain-identifying field: [2](#0-1) 

The signing scheme (`SignableMessage`/`MessageDiscriminant` from NEP-461) only tags the *message type* (e.g. `DelegateAction` vs `DelegateActionV2`) and NEP number, not any network/chain identity: [3](#0-2) 

At execution time, `apply_delegate_action` validates only the signature, `max_block_height` (a height, not a chain-specific hash), and that `sender_id` matches the tx receiver; then `validate_delegate_action_key` validates only the access key's nonce for that (`sender_id`, `public_key`) pair: [4](#0-3) [5](#0-4) 

By contrast, ordinary transactions bind to the actual live chain via a validated `block_hash`, which is checked to be an ancestor of the current chain (rejecting forks/other chains): [6](#0-5) [7](#0-6) 

This chain-binding is exactly what is documented as a design goal for ordinary transactions ("the `block_hash` … to limit the validity of the transaction … it must be added within `transaction_validity_period` blocks of `block_hash`"), but this protection does **not** extend to the inner `DelegateAction` payload that the end user actually signs: [8](#0-7) 

Because nonce accounting is purely local per (`sender_id`, `public_key`) access key state on whichever chain the relayer submits to, and `max_block_height` is just a height threshold (not tied to any specific chain's actual header), a `SignedDelegateAction` produced by a user is valid and replayable on **any** nearcore-based network where:
- the same `sender_id`/`public_key` access key exists (common since users frequently reuse the same keypair across NEAR mainnet, NEAR testnet, and any other nearcore-derived chain, e.g. app-specific chains, forks after a chain split, or Aurora-style sidechains sharing the account model), and
- the access key's on-chain nonce and current block height on that other chain happen to satisfy the same nonce/height constraints (trivially true immediately after a chain fork/split where state, including nonces, is identical on both sides, or on a freshly-launched chain where nonces start low).

A relayer (an "unprivileged" meta-transaction submitter, exactly the actor named in scope) who captures/receives a `SignedDelegateAction` intended for use on chain A can wrap and submit the identical bytes as the inner action of a transaction on chain B, and the runtime on chain B will accept it as if the user had authorized that action there, because nothing in the signed bytes commits to "chain B is not the intended chain."

### Impact Explanation
This allows unauthorized execution of user-authorized actions (transfers, `AddKey`, function calls with attached deposits, `WithdrawFromGasKey`, etc.) on a chain/network the user never intended to interact with, as long as the user's key/account state happens to be compatible there. This is a direct unauthorized-value-movement vector: a relayer or any party who obtains a signed `DelegateAction` (which by design is handed to third-party relayers) can replay it cross-chain to move funds or grant access on a network the signer did not target — e.g., immediately after a network fork/split where nonces and access keys are still identical on both branches, or on any nearcore-derived chain reusing NEAR's account/key namespace. This matches "concrete unauthorized value movement" / "invalid state transition acceptance" per the accepted impact categories.

### Likelihood Explanation
Medium. Exploitation requires either (a) a hard fork/chain split scenario where two live nearcore-based chains share identical account/key/nonce state at the split point (plausible for any protocol upgrade contentious fork, or when spinning up a new nearcore-based network from an existing chain's state snapshot), or (b) a user/service reusing the same access key across multiple independent nearcore-based networks and relying on relayers that operate across more than one such network. Given that meta-transactions are explicitly designed to be handed off to third-party relayers (untrusted intermediaries by design, per `docs/architecture/how/meta-tx.md`), and that nearcore is a general blockchain framework routinely forked/reused for other networks, this is a realistic occurrence rather than a purely theoretical one.

### Recommendation
Include a chain-binding value (e.g., the network's genesis hash or a configured `chain_id`) as part of the `DelegateAction`/`DelegateActionV2` struct and incorporate it into the NEP-461 `SignableMessage` hash, so that `SignedDelegateAction::verify` fails when the delegate action's embedded chain identifier does not match the executing chain's own genesis hash/chain id. This mirrors the ancestor/`block_hash` binding already enforced for ordinary transactions and would close the cross-chain replay gap without requiring changes to nonce/access-key semantics.

### Proof of Concept
1. Chain A and Chain B are two live nearcore-based chains that share identical genesis/account state (e.g., B is a fresh fork of A taken at height H, or B is an independently launched nearcore chain where the victim happens to have created an account with the same `AccountId` and registered the same `PublicKey` with a compatible nonce).
2. Victim Alice signs a `DelegateAction` (`sender_id: alice`, `receiver_id: alice`, `actions: [AddKey(attacker_pubkey, FullAccess)]`, `nonce: N`, `max_block_height: H+100`) intending it to be relayed only on Chain A, via `SignedDelegateAction::sign` (`core/primitives/src/action/delegate.rs:92-95`).
3. A relayer (or anyone who obtains the `SignedDelegateAction` bytes, since they are handed to third parties by design) wraps the identical bytes into a `Transaction` on Chain B and submits it there.
4. Chain B's runtime calls `apply_delegate_action` → `signed_delegate_action.verify()` (`runtime/runtime/src/actions.rs:474`), which succeeds because the signature check has no chain-specific input; `max_block_height` and `nonce` checks pass because Chain B's height and Alice's access-key nonce there independently satisfy the same numeric constraints.
5. The `AddKey` action executes on Chain B on Alice's account without her authorization for that specific chain, giving the attacker full access to Alice's account there — demonstrating unauthorized value/permission movement via signature replay across chains.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

pub fn check_transaction_validity_period(
    chain_store: &ChainStoreAdapter,
    prev_block_header: &BlockHeader,
    base_block_hash: &CryptoHash,
    transaction_validity_period: BlockHeightDelta,
) -> Result<(), InvalidTxError> {
    let base_header =
        chain_store.get_block_header(base_block_hash).map_err(|_| InvalidTxError::Expired)?;

    metrics::CHAIN_VALIDITY_PERIOD_CHECK_DELAY
        .observe(prev_block_header.height().saturating_sub(base_header.height()) as f64);

    // First check the distance between blocks
    if prev_block_header.height() > base_header.height() + transaction_validity_period {
        return Err(InvalidTxError::Expired);
    }

    // Then check if there is a path between the blocks (`base` is an ancestor of `prev`)
    validity_period_validate_is_ancestor(&base_header, prev_block_header, chain_store)
}

fn validity_period_validate_is_ancestor(
    base_header: &BlockHeader,
    prev_block_header: &BlockHeader,
    chain_store: &ChainStoreAdapter,
) -> Result<(), InvalidTxError> {
    let base_height = base_header.height();
    let prev_height = prev_block_header.height();
    let base_block_hash = base_header.hash();

    // Base can't be an ancestor of prev if its height is bigger
    if base_height > prev_height {
        return Err(InvalidTxError::InvalidChain);
    }

    // if both are on the canonical chain, comparing height is sufficient
    // we special case this because it is expected that this scenario will happen in most cases.
    if let Ok(base_block_hash_by_height) = chain_store.get_block_hash_by_height(base_height) {
        if &base_block_hash_by_height == base_block_hash {
            if let Ok(prev_hash) = chain_store.get_block_hash_by_height(prev_height) {
                if &prev_hash == prev_block_header.hash() {
                    return Ok(());
                }
            }
        }
    }

    // if the base block height is smaller than `last_final_height` we only need to check
    // whether the base block is the same as the one with that height on the canonical fork.
    // Otherwise we walk back the chain to check whether base block is on the same chain.
    let last_final_height = chain_store
        .get_block_height(prev_block_header.last_final_block())
        .map_err(|_| InvalidTxError::InvalidChain)?;

    if last_final_height >= base_height {
        let base_block_hash_by_height = chain_store
            .get_block_hash_by_height(base_height)
            .map_err(|_| InvalidTxError::InvalidChain)?;
        if &base_block_hash_by_height == base_block_hash {
            Ok(())
        } else {
            Err(InvalidTxError::InvalidChain)
        }
    } else {
        let header =
            get_block_header_on_chain_by_height(chain_store, prev_block_header.hash(), base_height)
                .map_err(|_| InvalidTxError::InvalidChain)?;
        if header.hash() == base_block_hash { Ok(()) } else { Err(InvalidTxError::InvalidChain) }
    }
}
