## Title
`TransactionOutput::ensure_match_transaction_info()` does not verify the state-checkpoint (state root), hot-state, or position-state checkpoint hashes, allowing corrupted state roots to pass replay/consensus-execution verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the integrity check used to confirm that a locally (re-)computed `TransactionOutput` matches the authenticated `TransactionInfo` for a given version. It validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but it explicitly and admittedly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the actual state-tree root produced by execution.

### Finding Description [1](#0-0) 

The function iterates through the fields that legitimately need cross-checking (status, gas, write-set hash, event root hash) but the code comment at the end states outright:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is used as a genuine, non-test integrity checkpoint in multiple places:
- `execution/executor/src/chunk_executor/mod.rs` (replay path from local execution against persisted `TransactionInfo`s)
- `storage/db-tool/src/replay_on_archive.rs` (archive replay-verify tool)
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` [3](#0-2) 

Since `state_checkpoint_hash` is precisely the field that commits to the resulting Jellyfish Merkle / state-tree root (and, per the comment, is on a path toward gating `COMPUTE_TRADING_NATIVE_STATE_ROOTS` — i.e., "trading native" position-state roots), skipping it in this comparator means the state root is not actually being cross-checked by this call site. If the locally re-executed state root diverges from the authenticated on-chain `TransactionInfo.state_checkpoint_hash` (e.g., due to a state-computation bug, a schema/versioning bug in the JMT restore/replay path, or divergent hot-state/position-state computation), `ensure_match_transaction_info()` will still report success as long as the write set and events happen to match.

### Impact Explanation
This breaks the intended proof/replay invariant: "VM outputs, transaction infos ... must survive executor-to-storage handoff unchanged" and "replay paths ... must not reinterpret committed data into a different ledger state." A silent state-root divergence during replay verification (used by db-tool's `replay_on_archive`, and by the chunk executor when verifying chunk replay/backup restore integrity) means a corrupted or incorrectly-restored state tree can be accepted as consistent with the authenticated ledger, even though the actual state root diverges. This is exactly the class of "committed state that differs from the correct VM result or corrupts durable ledger data" that the gate calls out, and specifically touches the hot-state / position-state trading-native root work in progress, which is new and less hardened code.

However, the severity is bounded: this comparator does not by itself cause bad data to be *committed* to the primary ledger during normal block execution (the accumulator/`TransactionInfo` hash chain is still what's cryptographically bound to consensus). Its blast radius is specifically the *verification tooling* (replay-verify, debugger, CLI replay) failing to catch state-root corruption that already occurred elsewhere — i.e., it's a detection gap for a corruption that must originate from another root cause (buggy replay, backup/restore, or trading-native state computation). This is why the impact is capped at "the authenticated position state root diverges from local execution" going unnoticed, rather than a directly forged proof accepted at the network/consensus layer.

### Likelihood Explanation
The likelihood of this manifesting is tied to (a) any bug in state-checkpoint/hot-state/position-state hash computation (an area explicitly under active development, per the "trading-native" and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` references), and (b) operators relying on `replay_on_archive`/replay-verify tooling as a correctness guarantee for restored or replayed state. Given the code authors' own comment flags this as a known, intentional gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), it is a real, currently-live gap rather than a hypothetical one, but it requires a *separate* primary bug to actually produce a divergent state root for this gap to hide.

### Recommendation
Extend `ensure_match_transaction_info()` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding values computed from the locally-produced state (when available/expected for the `TransactionInfo` variant in use), failing loudly on mismatch, before any feature (such as `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on position-state root correctness is enabled in production. At minimum, `replay_on_archive` and chunk-executor replay verification should not report success while these fields are silently unchecked.

### Proof of Concept
Not independently reproducible from the index alone: this is a static-analysis finding based on the function body and its own documenting comment at [1](#0-0) , plus verified call sites in `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. Constructing an end-to-end PoC (e.g., artificially diverging the state-checkpoint hash during a chunk replay and showing `ensure_match_transaction_info` still returns `Ok`) requires running the executor/replay test harness, which was not available in this read-only investigation — I could not execute code to confirm runtime behavior beyond what the source and its own comment state.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
