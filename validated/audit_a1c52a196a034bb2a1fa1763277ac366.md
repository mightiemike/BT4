### Title
`estimateEnergy` silently swallows non-timeout VM exceptions, causing binary search to converge on an under-funded feeLimit that diverges from real execution requirements - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.callConstantContract` decides whether to re-throw a VM execution exception using a boolean expression whose operator precedence makes it re-throw only for `Program.OutOfTimeException`, or when *not* estimating. When called from `estimateEnergy`'s binary search (`isEstimating=true`), any other VM exception (e.g. out-of-energy/illegal-opcode failures triggered by insufficient `feeLimit`) is swallowed and the probe is scored as `SUCCESS`, unlike the real `triggerConstantContract`/broadcast execution path which properly surfaces the same exception as a failure. This makes the binary search converge on a `feeLimit`/energy value lower than what execution actually requires.

### Finding Description
`Wallet.estimateEnergy` (`framework/src/main/java/org/tron/core/Wallet.java:2986-3087`) performs a binary search over `feeLimit`, repeatedly calling `cleanContextAndTriggerConstantContract` → `triggerConstantContract(..., isEstimating=true)` → `callConstantContract(trxCap, builder, retBuilder, true)` [1](#0-0) . The search treats a probe as failing only if `transaction.getRet(0).getRet().equals(code.FAILED)` [2](#0-1) .

Inside `callConstantContract`, the exception handling is:
```java
if (!isEstimating && result.getException() != null
    || result.getException() instanceof Program.OutOfTimeException) {
  RuntimeException e = result.getException();
  ...
  throw e;
}
``` [3](#0-2) 

Because `&&` binds tighter than `||`, this condition is evaluated as `(!isEstimating && result.getException() != null) || (result.getException() instanceof Program.OutOfTimeException)`. When `isEstimating == true` and `result.getException()` is any exception *other than* `Program.OutOfTimeException` (e.g. an out-of-energy or illegal-operation failure caused by an insufficient `feeLimit` on that binary-search probe), both disjuncts are `false`, so the exception is **not** re-thrown. Execution falls through to building a `TransactionResultCapsule` that defaults to `code.SUCESS` unless `result.getRuntimeError()` happens to be non-empty or `result.isRevert()` is true [4](#0-3) .

In contrast, the real execution path used for `eth_call`/`triggerConstantContract`/the eventual broadcast (`isEstimating=false`) does re-throw such exceptions and correctly marks the probe as failed. This asymmetry means `estimateEnergy`'s binary search can classify a `feeLimit` that is genuinely insufficient (would cause a real failure) as "succeeded", causing `low`/`high` to converge on a value lower than the energy actually required to execute the same call without error.

An unprivileged attacker who deploys a contract via `CreateSmartContract` whose bytecode is crafted to trigger such a non-timeout VM exception at a specific energy boundary (rather than a clean revert or `OutOfEnergyException` that is consistently classified) can make `eth_estimateGas`/`estimateenergy` return an energy figure lower than what `triggerConstantContract`/the actual broadcast execution needs for the identical call, per `TronJsonRpcImpl.estimateGas` (`framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java:673-752`) and `TronJsonRpcImpl.estimateEnergy`/`callTriggerConstantContract` (`framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java:466-514`) [5](#0-4) .

Note: this is a *self-consistency/accounting* bug in the estimation logic itself (estimateEnergy's reported figure vs. actual execution requirement), not a cross-node non-determinism bug — TVM execution against identical state is deterministic, so all honest nodes with the same chain state will reject/execute the subsequently broadcast under-funded transaction identically. The "diverge across honest nodes" framing in the question is not supported by this code; what is supported is that `estimateEnergy` can deterministically under-report the energy needed relative to `triggerConstantContract`/real execution for the same call.

### Impact Explanation
A caller relying on `eth_estimateGas`/`/wallet/estimateenergy` (when `Args.getInstance().estimateEnergy == true`) can receive an energy/feeLimit figure that is too low for a crafted contract. Broadcasting `TriggerSmartContract` with `feeLimit = calcFeeLimit(estimatedGas, gasPrice())` then deterministically fails (out-of-energy or reverts) on every honest node, wasting the fee actually charged (bandwidth/energy consumed up to the point of failure) and producing a materially wrong public estimation service output. This is scoped to the estimation/accounting-sufficiency guarantee of the estimateEnergy API, not to consensus divergence between nodes.

### Likelihood Explanation
- Precondition: node operator must have enabled `vm.estimateEnergy = true` (default `false` per `reference.conf`) [6](#0-5) . On such nodes, exploitation only requires public HTTP/JSON-RPC access and the ability to deploy an arbitrary contract, both of which are unprivileged operations.
- Triggering a non-`OutOfTimeException` RuntimeException at a chosen feeLimit boundary in the TVM (e.g. specific opcode-level `IllegalOperationException`, `StackTooSmallException`, or similar) is a realistic construction task for a determined attacker crafting bytecode deliberately, though it requires VM-internals knowledge to hit exactly the right condition during the binary search.

### Recommendation
Fix the operator precedence in `Wallet.callConstantContract` so that any VM exception is treated consistently regardless of `isEstimating`, e.g.:
```java
if (result.getException() != null) {
  RuntimeException e = result.getException();
  ...
  throw e;
}
```
or explicitly parenthesize the intended logic if some exceptions genuinely should be tolerated only in estimation mode:
```java
if ((!isEstimating && result.getException() != null)
    || result.getException() instanceof Program.OutOfTimeException) { ... }
```
should instead be written to always propagate execution-failure exceptions during estimation too (or explicitly classify them as `code.FAILED` in the `isEstimating` path) so binary search correctly treats them as insufficient-`feeLimit` outcomes rather than "success".
