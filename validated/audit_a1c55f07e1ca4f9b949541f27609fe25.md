### Title
Uncapped internal-transaction/log accumulation in constant-call execution enables underpriced memory/bandwidth amplification via `TriggerConstantContractServlet` - (File: `framework/src/main/java/org/tron/core/services/http/TriggerConstantContractServlet.java`)

### Summary
`TriggerConstantContractServlet.doPost` invokes `Wallet.triggerConstantContract`, which executes a smart contract and serializes every internal transaction and log entry produced by `ProgramResult` into the `TransactionExtention` response. `ProgramResult.getInternalTransactions()`/`getLogInfoList()` are unbounded `ArrayList`s that grow with every internal `CALL`/`LOG` opcode executed, and nothing in the reviewed code path caps the count or aggregate byte size of these lists before they are serialized and written to the HTTP response.

### Finding Description
The request enters at `TriggerConstantContractServlet.doPost` [1](#0-0) , which builds a `TriggerSmartContract` from unprivileged, unauthenticated JSON POST input and calls `wallet.triggerConstantContract(...)`, passing `trxExtBuilder` by reference to be filled with the execution result. The only entry-level guard is `RateLimiterServlet` (request-count throttling) and `Util.checkBodySize` (input size limit), neither of which bounds the cost of *executing* the submitted bytecode.

Inside contract execution, `ProgramResult` accumulates every internal call and log event without any cap: [2](#0-1) [3](#0-2) 

These lists are only bounded indirectly by the energy consumed during execution (each `CALL`/`LOG` opcode has an energy cost, and execution halts once the energy ceiling is reached), not by an explicit response-size or count limit. For a "constant" (view-only) call, no TRX fee or bandwidth-point deduction is charged to the caller in the same way as a real on-chain transaction — the servlet's cost gate is only the `RateLimiterServlet`'s per-endpoint request-rate limit, not a resource/CPU/memory cost accounting mechanism. If the energy ceiling configured for constant calls is large (this is the `constant call` energy limit configured via `CommonParameter`, referenced from `Wallet.java`, which I could not fully confirm the exact numeric value for in this pass), an attacker can craft a contract with deeply nested `CALL`s and many `LOG` opcodes to maximize the number of `InternalTransaction`/`LogInfo` entries generated per single HTTP request, up to that ceiling. Each of those entries is later converted into protobuf message fields and appended to `trxExtBuilder` (in `Wallet.triggerConstantContract`, downstream of the code shown), producing a large serialized `TransactionExtention` response for a single rate-limiter "slot" — i.e., disproportionate memory allocation, protobuf serialization, and network egress cost relative to the single request unit the rate limiter accounts for.

I was not able to fully verify within this pass (a) the exact numeric energy ceiling applied to constant calls, and (b) whether any additional response-size truncation exists further downstream in `Wallet.triggerConstantContract` or `Util.printTransactionExtention` — these would materially affect the actual achievable amplification factor and should be confirmed with direct inspection of the full `Wallet.java` method body and `CommonParameter` energy-limit fields before treating this as conclusively exploitable at scale.

### Impact Explanation
An attacker who can reach `TriggerConstantContractServlet` (any public HTTP client) can force the server to allocate and serialize a large `TransactionExtention` object (deep `List<InternalTransaction>` / `List<LogInfo>`) per request while paying only the cost of one rate-limited HTTP call, not a fee proportional to the resulting internal-transaction/log volume. Repeated requests can be used to amplify memory pressure and outbound bandwidth usage on full nodes serving this API, a resource-exhaustion / denial-of-service risk against the HTTP API tier.

### Likelihood Explanation
Feasibility depends entirely on the magnitude of the constant-call energy ceiling and whether any additional caps exist in `Wallet.triggerConstantContract`/`Util.printTransactionExtention` that were not fully verified in this review. If the ceiling is large relative to opcode costs (which is plausible given constant calls are typically granted generous energy budgets to support complex view functions), the attack is straightforward to reproduce: deploy a contract with a recursive/looped internal-call or logging pattern and submit repeated `wallet/triggerconstantcontract` POSTs. The rate limiter throttles request *frequency* but not per-request computational/response cost, so this is repeatable within the rate limit's allowance.

### Recommendation
- Impose an explicit cap on the number of `InternalTransaction` and `LogInfo` entries (and/or serialized byte size) included in the `TransactionExtention` response for constant calls, independent of the energy ceiling, and truncate/flag results that exceed it.
- Consider excluding or paginating internal-transaction/log detail in `TriggerConstantContractServlet` responses by default, requiring an explicit opt-in parameter, similar to size-limiting protections elsewhere in the HTTP API.
- Tie the constant-call energy ceiling and/or add a dedicated "response construction cost" accounting so that rate-limiter quota consumption reflects the actual work performed per request rather than a flat per-request count.
