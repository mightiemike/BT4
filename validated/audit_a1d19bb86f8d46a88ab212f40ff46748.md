## Finding: Transaction backup restore accepts an unverified `WriteSet` that is never checked against the proof-covered `TransactionInfo`

### Title
Unverified write set injection during transaction-backup restore (`TransactionListWithProof` path) — ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
The "transaction" backup restore flow deserializes `(txn, aux_info, txn_info, events, write_set)` tuples from an untrusted backup file and verifies them using `TransactionListWithProof::verify()`, which never checks the write set against the accumulator-proven `TransactionInfo`. The `write_set` is then persisted directly into the ledger DB and, in `kv_replay` mode, folded into the committed `LedgerState`, with no invariant ensuring it corresponds to the transaction that was actually proven.

### Finding Description
In `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`, `LoadedChunk::load()` reads five values per record from the backup stream (an untrusted `BackupStorage` source): `txn`, `aux_info`, `txn_info`, `events`, `write_set`. [1](#0-0) 

It then builds a `TransactionListWithProof` — which does **not** include `write_set` as a field — and calls `.verify()` on it: [2](#0-1) 

`TransactionListWithProof::verify()` only checks (a) the transaction hash against `txn_info.transaction_hash()`, (b) the accumulator proof binding `txn_info` to the `LedgerInfo`, and (c) events against `txn_info.event_root_hash()`. It never receives or checks `write_set` at all: [3](#0-2) 

This is in stark contrast to the sibling type `TransactionOutputListWithProof::verify()`, used by the transaction-*output* backup/restore path, which explicitly enforces `txn_info.state_change_hash() == CryptoHash::hash(&txn_output.write_set)`: [4](#0-3) 

Because the "transaction" backup format keeps `write_set` external to the verified `TransactionListWithProof`, the loaded, unauthenticated `write_set` is passed straight through to `RestoreHandler::save_transactions()` → `restore_utils::save_transactions_impl()`, which unconditionally persists it into `WriteSetDb` and, when `kv_replay` is true, uses it to compute and commit the new `LedgerState` via `state_store.calculate_state_and_put_updates(...)`: [5](#0-4) 

At no point in this path — `LoadedChunk::load`, `TransactionRestoreController`, `RestoreHandler::save_transactions`, or `restore_utils::save_transactions_impl` — is `CryptoHash::hash(&write_set)` compared against `txn_info.state_change_hash()`. The only object cryptographically bound to the accumulator-verified `LedgerInfo` is the `TransactionInfo`; a corrupted or malicious backup source (any node/service implementing `BackupStorage`, e.g. a shared S3/GCS bucket) can therefore supply an arbitrary `write_set` for a version whose `txn_info`/proof are otherwise fully valid.

### Impact Explanation
For versions that are saved directly from the backup chunk without VM replay (the `save_before_replay_version` branch, restoring "before-replay" state up to `first_to_replay`), an attacker-controlled backup archive can inject a `write_set` that diverges from the actual VM-computed result for that transaction while its `TransactionInfo`/accumulator proof still verify successfully. This corrupts durable ledger data (state KV DB and `WriteSetDb`) and the resulting `LedgerState`/state root used by the restoring node, producing authenticated API responses (state reads, write-set queries) for a version whose proof context (accumulator, `TransactionInfo`) is valid but whose actual state content is wrong — a direct divergence between committed state and the correct VM result, and a break of the "authenticated API bound to the right ledger version/root" invariant required by the state-integrity gate.

### Likelihood Explanation
This requires control over, or compromise of, the backup storage source consumed during a restore/fast-sync operation (`BackupStorage` implementation such as an S3/GCS bucket or a local file store). This is a plausible threat model for restore workflows, since backup artifacts are often fetched from third-party or less-trusted storage compared to the validated p2p/state-sync path, and the restore code explicitly treats the accumulator/ledger-info proof as the source of truth while silently trusting the paired `write_set` bytes without any additional verification.

### Recommendation
Add an explicit check in the transaction-backup load/verify path (or in `save_transactions_impl`) that `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every record before it is accepted and persisted, mirroring the check already performed by `TransactionOutputListWithProof::verify()`. Ideally, extend `TransactionListWithProof`/`TransactionInfoListWithProof` verification (or add a dedicated verification helper used by the transaction backup restore path) so that any write set traveling alongside a proven `TransactionInfo` is cryptographically bound to it before being written to durable storage.

### Proof of Concept
1. Take (or construct) a valid "transaction" backup chunk (manifest + `.chunk` transactions file + proof file) for some version `v`, with a legitimate `txn`, `txn_info`, and accumulator `range_proof`/`LedgerInfo`.
2. In the transactions record for version `v`, replace the serialized `write_set` bytes with an arbitrary different `WriteSet` (e.g., one that credits an account with additional balance), leaving `txn`, `txn_info`, and the proof/`LedgerInfo` files untouched.
3. Run a fresh-node restore (`aptos-db-tool restore ... --transaction-manifest ...`) pointing at this tampered backup store.
4. `LoadedChunk::load()` deserializes the tampered `write_set` and calls `txn_list_with_proof.verify()`, which succeeds because it never inspects `write_set`.
5. `RestoreHandler::save_transactions()` persists the tampered `write_set` into `WriteSetDb`, and if the version falls in the pre-replay "save" range with `kv_replay` enabled, `calculate_state_and_put_updates` folds it into the committed state, producing a `LedgerState`/state root that diverges from the value an honest VM re-execution (or the real chain) would have produced — with no verification failure raised anywhere in the restore pipeline.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
