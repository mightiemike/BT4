### Title
Sandwichable On-Chain Autoswap Quote Enables Value Extraction from Bridging Users on GAS/GAS_AND_PAYLOAD Inbounds - (File: x/uexecutor/keeper/execute_inbound_gas.go)

### Summary
The Hubble report shows that when execution price is derived from state that can be influenced by transaction ordering within the same block, a party that controls or can predict that ordering can extract value at the expense of the other side of the trade. Push Chain has a structurally analogous pattern: for `GAS` and `GAS_AND_PAYLOAD` inbounds, the `uexecutor` module fetches a live Uniswap V3 `QuoterV2` quote and immediately executes an on-chain swap against that same pool, applying only a fixed 5% slippage tolerance, with no protection against the pool price being moved by other transactions in the same block.

### Finding Description
When a `GAS`/`GAS_AND_PAYLOAD` inbound reaches quorum, `ExecuteInboundGas` / `ExecuteInboundGasAndPayload` compute the swap parameters and execute the autoswap synchronously in this order:
1. `GetDefaultFeeTierForToken` — static read of the pool fee tier.
2. `GetSwapQuote` (`QuoterV2.quoteExactInputSingle`, `commit=false`) — a live read of the current AMM pool state. [1](#0-0) 
3. `minPCOut = quote * 95 / 100` — a flat 5% slippage tolerance is applied to the just-fetched quote. [2](#0-1) 
4. `CallPRC20DepositAutoSwap` — the module immediately executes `depositPRC20WithAutoSwap` against the same pool with that `minPCOut` floor. [3](#0-2) 

This quote-then-swap step happens inside the ordinary `MsgVoteInbound` message handler, in the same block as (and immediately before) the actual swap execution, with no commit-reveal, no TWAP, and no per-swap price-impact cap beyond the static 5% band. The upgrade notes confirm this is an intentional, but narrow, mitigation: "GAS and GAS_AND_PAYLOAD inbound routes now call the Uniswap V3 QuoterV2 contract to obtain an on-chain swap quote and pass minPCOut (quote × 95%)... replacing the previous 0-slippage call." [4](#0-3) 

Because the timing of an inbound's finalizing vote is observable on-chain before it lands (validators' votes toward quorum are visible state, and the inbound amount/asset is known once the inbound is first proposed), an unprivileged EVM user can submit ordinary transactions in the same block as the finalizing vote to move the pool price against the module's swap (a classic sandwich): push the pool price down before the module's `depositPRC20WithAutoSwap` executes (still within the 5% band), let the module swap execute at the worse price, then reverse the trade afterward. The attacker profits from the spread; the bridging user's UEA receives less PC/PRC20 than the pool's undisturbed price would have produced. No malicious validator or TSS participant is required — this only needs an ordinary user submitting normal transactions to the AMM pool that Push Chain's `UniversalCore`/`QuoterV2` addresses reference.

### Impact Explanation
This directly affects "corruption of PRC20 or native asset accounting ... refund accounting" and value theft from "user or protocol-controlled funds" — the bridging user ends up with fewer output tokens than they should for their inbound deposit, while an unprivileged attacker captures the difference via ordinary sandwich transactions against the pool used by `CallPRC20DepositAutoSwap`. Every GAS/GAS_AND_PAYLOAD inbound that autoswaps is exposed; the 5% band bounds the loss per swap but does not prevent it, and repeated inbounds compound the extractable value.

### Likelihood Explanation
Likelihood is moderate-to-high on any chain where inbound votes/quorum progress is publicly observable before the finalizing vote lands (which is a normal, honest-validator condition, not a privileged assumption), and where the referenced Uniswap V3 pool has realistic depth relative to bridge amounts. No validator or relayer collusion is required; the attacker only needs to watch pending inbound votes and submit ordinary EVM transactions in the same block window. This is a standard MEV/sandwich pattern against any protocol-executed swap with a wide, static slippage tolerance and no commit/reveal or TWAP-based pricing.

### Recommendation
- Replace the spot `QuoterV2` quote + static 5% band with a TWAP-based or otherwise time-weighted price reference so a single-block price movement cannot be exploited.
- Tighten the slippage tolerance or make it configurable per-pool based on realistic liquidity depth, and/or cap the swap size relative to pool liquidity.
- Consider routing protocol-initiated swaps through a private/no-sandwich execution path (e.g., committing the swap in the same atomic unit as quorum finalization without a public pre-image of the exact block in which it executes), or use an on-chain price oracle independent of the swapped pool for the floor calculation.
- Alternatively, split the risk to the user: let the bridging user (or their UEA) specify their own acceptable `minPCOut`/deadline rather than always defaulting to a flat 95% quote taken at execution time.

### Proof of Concept
1. Monitor `x/uexecutor` pending inbounds and `MsgVoteInbound` votes for a `GAS`/`GAS_AND_PAYLOAD` inbound approaching quorum (2/3+ of `x/uvalidator` ballot threshold) — this state is public.
2. When the last vote is expected to land in an upcoming block, submit a transaction that swaps a large amount of WPC → PRC20 (or vice versa, depending on the deposit's asset direction) in the referenced Uniswap V3 pool immediately before the finalizing `MsgVoteInbound` transaction in the block, moving the pool price down within tolerable bounds.
3. The finalizing vote triggers `ExecuteInboundGas`, which calls `GetSwapQuote` against the now-moved pool and executes `CallPRC20DepositAutoSwap` with `minPCOut` computed from the manipulated quote (95% of the depressed price) — this still satisfies the floor and does not revert.
4. Submit a reverse transaction immediately after to restore the pool price, capturing the price difference as profit, while the bridging user's UEA receives fewer output tokens than an unperturbed pool would have produced.

Note: I was not able to fully verify the exact liquidity/pool deployment parameters (e.g., whether the referenced Uniswap V3 pools are deployed with meaningful depth in production, which affects real-world exploitability) — that detail lives in deployment/genesis configuration outside what the index surfaced.

```go
// Calls Handler Contract to deposit prc20 tokens with auto-swap.
// fee and minPCOut must be pre-computed by the caller (see GetDefaultFeeTierForToken / GetSwapQuote).
func (k Keeper) CallPRC20DepositAutoSwap(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount, fee, minPCOut *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: depositPRC20WithAutoSwap",
		"prc20", prc20Address.Hex(),
		"recipient", to.Hex(),
		"amount", amount.String(),
		"fee", fee.String(),
		"min_pc_out", minPCOut.String(),
	)
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // who is sending the transaction
		handlerAddr,        // destination: Handler contract
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20WithAutoSwap",
		prc20Address,
		amount,
		to,
		fee,
		minPCOut,
		big.NewInt(0), // deadline = 0 → contract uses its default
	)
```
