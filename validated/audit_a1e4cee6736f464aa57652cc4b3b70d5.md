### Title
Unbounded Crossbeam Channel in `MultithreadRuntimeHandle` Allows Unprivileged OOM via `broadcast_tx_async` Flooding — (`core/async/src/multithread/runtime_handle.rs`)

### Summary

An unprivileged attacker can submit a high volume of `broadcast_tx_async` JSON-RPC requests to exhaust the node's heap by growing the `RpcHandlerActor`'s internal crossbeam channel without bound. The channel is created with `crossbeam_channel::unbounded()` and there is no admission-control, backpressure, or per-client rate limit on the HTTP path that feeds it.

### Finding Description

`spawn_multithread_actor` creates the actor's message channel with `crossbeam_channel::unbounded()`: [1](#0-0) 

`send_message` calls `self.sender.send(message)` with no capacity check: [2](#0-1) 

The `InstrumentedQueue` attached to the handle is purely observability — it increments/decrements Prometheus counters but enforces no size limit and never blocks or rejects a send: [3](#0-2) 

The `broadcast_tx_async` JSON-RPC method calls `send_tx_async`, which performs a fire-and-forget `CanSend::send` directly into this channel: [4](#0-3) 

The Axum HTTP server applies only a 10 MB body-size limit (`RequestBodyLimitLayer`) and no per-IP rate limiting or concurrent-request cap: [5](#0-4) 

The P2P-layer rate limits (`messages_limits.rs`) apply only to peer-to-peer `Transaction` messages, not to HTTP JSON-RPC submissions: [6](#0-5) 

Each queued `MultithreadRuntimeMessage<RpcHandlerActor>` holds a heap-allocated `Box<dyn FnOnce>` closure capturing a full `SignedTransaction`. With a finite number of consumer threads (`transaction_request_handler_threads`) and no back-pressure, an attacker who submits requests faster than the actor can drain them causes unbounded heap growth: [7](#0-6) 

### Impact Explanation

If the channel queue grows to exhaust available heap, the node process is killed by the OS OOM killer. This terminates block processing and consensus participation for the affected node without any fund loss or state corruption, but constitutes a non-network-level denial of service fixable by a code change (bounded channel or HTTP-layer rate limiting) without a hardfork.

### Likelihood Explanation

The attack requires only the ability to send HTTP POST requests to port 3030 (the default public JSON-RPC port). No keys, stake, or privileged role are needed. A single attacker with moderate bandwidth can sustain a submission rate that exceeds the actor's drain rate, since each `broadcast_tx_async` call returns immediately after enqueuing.

### Recommendation

1. Replace `crossbeam_channel::unbounded()` in `spawn_multithread_actor` with a bounded channel (e.g., `crossbeam_channel::bounded(N)`) and return an error or apply backpressure when the channel is full.
2. Alternatively, add per-IP or global rate limiting at the Axum middleware layer for transaction-submission endpoints.
3. The `transaction_pool_size_limit` config guards the pool, not the actor channel queue, and does not mitigate this path.

### Proof of Concept

Spawn a `MultithreadRuntimeHandle<RpcHandlerActor>` with a handler that sleeps for 100 ms per message. Fire N `send_message` calls in a tight loop without waiting. Assert `instrumentation.queue().get_pending_events()` shows a count exceeding a safe threshold before any message completes. In production, replace the sleep with the real `process_tx` workload and drive the HTTP endpoint with a concurrent HTTP client (e.g., `wrk` or a Tokio-based flood loop targeting `broadcast_tx_async`).

```rust
    pub fn enqueue(&self, message_type: &str) {
        {
            // Try just with read lock first, to avoid write lock in the common case.
            let pending = self.pending.read();
            if let Some(counter) = pending.get(message_type) {
                counter.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
                self.pending_messages_gauge.inc();
                return;
            }
        }
        // Use write lock if the message type is not found.
        let mut pending = self.pending.write();
        let counter = pending.entry(message_type.to_string()).or_insert_with(|| AtomicU64::new(0));
        counter.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
        self.pending_messages_gauge.inc();
    }
```
