### Title
Webhook HMAC signature doesn't bind the `X-Shopify-Shop-Domain`/topic headers, enabling cross-tenant webhook replay with a shared app secret - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The Shopify webhook HMAC verification only authenticates the raw request body against the app's single, shop-wide `apiSecretKey`. It never binds the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers into the signed material. Because every shop that installs the same app shares one `apiSecretKey`, a valid `(rawBody, hmac)` pair captured from one tenant's webhook delivery remains a "valid signature" when replayed with a forged domain header claiming to originate from a different shop — directly analogous to the reported `KeystoreAccount.isValidSignature` issue where a hash that omits the "contract/recipient" binding lets a signature produced under a shared signer be replayed against an unintended target.

### Finding Description
`validateHmacFromRequestFactory` computes the expected HMAC purely from `rawBody` and the app's secret, and compares it to the header value: [1](#0-0) 

`validateHmacString`/`createSHA256HMAC` sign only `data` (the raw body) with `config.apiSecretKey` — no shop domain, topic, or webhook id is folded into the signed payload: [2](#0-1) 

The webhook `validateFactory` computes `webhookType` from headers, validates the HMAC solely over the body, and then trusts the `X-Shopify-Shop-Domain`/`X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers as authenticated once the (unrelated) HMAC check passes: [3](#0-2) 

Downstream, `authenticateWebhookFactory` (in both shopify-app-remix and shopify-app-react-router) takes `check.domain` from the request headers — never independently re-verified — to look up and attach the offline session/admin client for that shop: [4](#0-3) 

Because `apiSecretKey` is a single "shared signer" reused for every shop that installs the app (the same trust anchor as multiple KeystoreAccounts sharing one signer in the report), and the signed content (`rawBody` alone) never says which shop/topic/webhook-id the signature was intended for (the missing "contract address" analog), a body+HMAC pair captured for one tenant is indistinguishable, cryptographically, from a legitimate delivery for any other tenant with the same body content.

### Impact Explanation
An attacker who controls or has access to any one shop that has the target app installed can:
1. Trigger a webhook-eligible action in their own shop, capturing a legitimate `(rawBody, X-Shopify-Hmac-Sha256)` pair from Shopify's real delivery (this is not a secret leak — HMAC and body are visible on the wire to the receiving endpoint or via replay of an intercepted delivery/logs).
2. Replay the exact same body and HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to point at a victim shop.
3. Since HMAC validation only checks the body against the shared `apiSecretKey`, the forged request is accepted as valid, and `ensureValidOfflineSession`/`check.domain` cause the app to process the webhook as if it came from the victim's shop, loading the victim's offline session and admin client and running the app's webhook handler logic (e.g., app/uninstalled, shop/redact, GDPR webhooks, order/customer data handlers) with attacker-controlled body content but attributed to the victim tenant.

This is a cross-tenant request-forgery / spoofing primitive against an "authentication handler" (the webhook auth path), matching the class of accepted-forged-Shopify-request impact called out in the validation criteria.

### Likelihood Explanation
Medium. Exploitation requires: (a) the attacker to be a legitimate merchant/installer of the same app on at least one shop (a very low bar — install is self-service), and (b) an app whose webhook handlers perform tenant-sensitive actions purely keyed off the `domain` header/topic without additional idempotency or content cross-checks (common pattern, as shown by the library's own webhook context construction using `check.domain` directly).

### Recommendation
Bind the tenant/context into the authenticated material, analogous to ERC-7739-style defensive rehashing:
- Include `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` (or a canonical concatenation of them) in the HMAC input, or verify them against Shopify by an independent authenticated channel (e.g., re-fetching the webhook subscription by id) before trusting header-derived `domain`/`topic` values.
- Alternatively, deduplicate/reject webhook deliveries whose `webhookId` has been seen before, and enforce a strict mapping between the shop that owns a given `webhookId` (as registered via the Admin API) and the domain header claimed in the request, rejecting mismatches.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. `orders/create`) in their shop and captures the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` from the real delivery to the app's webhook endpoint (`H = HMAC-SHA256(apiSecretKey, B)` per `validateHmacString`, [2](#0-1) ).
3. Attacker resends `POST /webhooks` with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
4. `validateHmacFromRequestFactory` recomputes the HMAC over `B` only and finds it matches `H` (domain/topic aren't part of the signed input) — validation succeeds: [5](#0-4) .
5. `authenticateWebhookFactory` treats `check.domain` (`victim-shop.myshopify.com`) as authenticated, loads the victim's offline session, and dispatches the (attacker-supplied) body to the topic handler as if `victim-shop` sent it: [6](#0-5) .

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
