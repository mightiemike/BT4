## Analog Found

### Title
Promise-yield resumption token (`data_id`) is a deterministic, publicly-derivable value rather than a secret capability, allowing any caller reaching a contract's `promise_yield_resume` path to settle a pending yield it did not legitimately trigger - (File: runtime/runtime/src/ext.rs)

### Summary
The ClearingHouse bug lets anyone who can reach a "settlement" callback with a matching, guessable/public `collateralId` finalize state that should only be finalized by the genuine originator of that ID. The nearcore analog is the `PromiseYield`/`PromiseResume` mechanism: `submit_promise_resume_data` authorizes resumption purely by checking that `(receiver_id, data_id)` matches a pending `PromiseYieldReceipt`/`PromiseYieldStatus` row, but `data_id` is a deterministic hash of public data (the originating action's `action_hash`, `block_height`, and a small sequential counter), not a secret nonce.

### Finding Description
`promise_yield_create` returns a "resumption token" (`data_id`) that the contract is expected to keep and later pass to `promise_yield_resume` / `promise_yield_resume_with_yield_id` to release the yielded promise with attacker-independent data [1](#0-0) .

The runtime generates this token via `generate_data_id`, which calls `create_receipt_id_from_action_hash(action_hash, block_height, data_count)` [2](#0-1) . That helper is a pure hash of the action's `action_hash`, the current `block_height`, and an incrementing counter, with no random or secret component [3](#0-2) . Since `action_hash` is itself derived from the public `receipt_id` and `block_height` [4](#0-3) , and receipt IDs/heights are visible on-chain the moment the yield-create receipt executes, the resulting `data_id` is fully computable by any observer — it is not a secret held only by the legitimate resumer.

The authorization check performed when resuming only verifies that a pending yield exists for `(self.account_id, data_id)` in the account's own trie state — it does not verify that the resume call originates from whoever legitimately initiated (or was meant to resolve) that specific yield: [5](#0-4) 

The doc comment claims "the resumption token is portable across transactions, but only the current account is allowed to resolve this data dependency" [6](#0-5) , but that restriction is only on *which contract account* (i.e., `current_account_id`) can call resume, not on *which transaction/caller*. Any function call that reaches that account and forwards a caller-supplied or derived `data_id` into `promise_yield_resume` succeeds as long as the `(account_id, data_id)` pair matches — exactly the "matching ID is trusted as proof of genuineness" flaw described in the ClearingHouse report, where anyone who can produce a matching identifier can trigger settlement logic meant for a specific, distinct originator.

Once execution reaches `PromiseResume` processing in the runtime, the lookup is again solely by `(account_id, data_id)`, with no further provenance check, and the yield receipt is unconditionally executed with whatever payload was supplied by the resumer: [7](#0-6) 

### Impact Explanation
Contracts that expose the `data_id`/yield-id as part of a public interface (a documented, supported usage pattern — e.g., "portable across transactions" so it can be persisted and later supplied by any caller/relayer) rely on it being unguessable to prevent unauthorized resumption. Because it is deterministically derivable from public receipt/block data rather than a secret, any account with a function-call path into `promise_yield_resume` can potentially resolve a pending yield belonging to a different, legitimate flow (e.g., an escrow, oracle callback, or auction-settlement pattern implemented on top of `promise_yield_create`/`promise_yield_resume`) with attacker-chosen payload data before the intended resumer does — an invalid state transition analogous to Astaria's genuine-auction-settled-by-a-spoofed-caller scenario. This can cause a contract to execute its yielded callback with incorrect/attacker-controlled `PromiseResult` data, leading to unauthorized value movement or state corruption in the affected contract.

### Likelihood Explanation
Reachable from a single unprivileged function call: any account holding (or being granted) a function-call access key to the target contract, or any contract invoked cross-contract by it, can call `promise_yield_resume`/`promise_yield_resume_with_yield_id` with a `data_id`/`yield_id` it computed or obtained from public chain data. No validator or node compromise is required — only knowledge of the target account's pending yield's public inputs (receipt id, block height, and the small sequential counter), which are exposed in receipts/execution outcomes.

### Recommendation
Do not rely on `data_id` (or `yield_id`) alone as an authorization token when its value is deterministically derivable from public chain data. Either (a) mix in a per-yield secret/randomness that only the legitimate resumer possesses, or (b) require that contracts built on top of `promise_yield_create`/`promise_yield_resume` treat the token purely as a routing key and perform their own additional authorization (e.g., checking predecessor account, an explicit allow-list, or a contract-managed nonce) before acting on the resumed payload — and update the documentation to make explicit that the runtime itself provides no caller-authentication beyond "same receiver account," so callers of this API must not expose `data_id`/`yield_id` as an unauthenticated public parameter if doing so would let any caller resolve another party's yield.

### Proof of Concept
1. Contract `C` calls `promise_yield_create(...)` inside a receipt with known `action_hash`/`block_height`; the resulting `data_id = create_receipt_id_from_action_hash(action_hash, block_height, data_count)` is computable by any observer who can read `action_hash`, `block_height`, and the sequence counter from the emitted receipt/outcome.
2. `C` exposes (as many yield/callback integration patterns do) a public method that accepts a caller-supplied `data_id`/`yield_id` and payload and forwards them to `promise_yield_resume`/`promise_yield_resume_with_yield_id`.
3. An attacker, without being the legitimate resumer, computes/derives the pending `data_id` from public receipt data and calls `C`'s public resume method with a forged payload before the genuine resumer does.
4. `submit_promise_resume_data` finds a matching `(C, data_id)` `PromiseYieldReceipt`/`PromiseYieldStatus` row and accepts the resume unconditionally [5](#0-4) ; the runtime later executes the yield receipt with the attacker's payload as `PromiseResult::Successful` [7](#0-6) , resolving `C`'s awaiting logic (e.g., an escrow release or price commit) with attacker-controlled data instead of the genuine input.

    fn submit_promise_resume_data(
        &mut self,
        data_id: CryptoHash,
        data: Vec<u8>,
    ) -> Result<bool, VMLogicError> {
        let has_yield_receipt_in_state =
            has_promise_yield_receipt(self.trie_update, self.account_id.clone(), data_id)
                .map_err(wrap_storage_error)?;
        let has_yield_status_in_state =
            has_promise_yield_status(self.trie_update, &self.account_id, data_id)
                .map_err(wrap_storage_error)?;

        if has_yield_receipt_in_state || has_yield_status_in_state {
            self.receipt_manager.create_promise_resume_receipt(data_id, data);
            set_promise_yield_status(
                &mut self.trie_update,
                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }

        Ok(false)
    }

/// Creates a new action_hash based on original receipt id.
pub fn create_action_hash_from_receipt_id(
    receipt_id: &CryptoHash,
    block_height: BlockHeight,
    action_index: usize,
) -> CryptoHash {
    // Action hash uses the same input as a new receipt ID, so to avoid hash conflicts we use the
    // salt starting from the `u64` going backward.
    let salt = u64::MAX.wrapping_sub(action_index as u64);
    create_hash_index(receipt_id, block_height, salt)
}
