### Title
Deterministic transaction-triggered panics in `Runtime::apply` error handling violate the "always make progress" invariant and can halt the chain - (File: `chain/chain/src/runtime/mod.rs`)

### Summary
The external report flags `totalAssets()` reverting on attacker/oracle-influenced input, breaking the ERC-4626 "MUST NOT revert" invariant that the surrounding vault protocol relies on. The nearcore analog is `Runtime::apply`, the shard state-transition function that chunk producers/validators run on every chunk. Its own documentation states the explicit design invariant that invalid or malicious transaction/receipt content must be skipped so "the protocol can make progress" rather than fail the whole chunk. However, the call site that maps `RuntimeError` variants back into the chain layer explicitly `panic!`s on `RuntimeError::ReceiptValidationError` and `RuntimeError::UnexpectedIntegerOverflow`, both tagged with `// TODO(#2152): process gracefully`, contradicting that invariant.

### Finding Description
`Runtime::apply` (`runtime/runtime/src/lib.rs:1860`) is documented to never fail the whole chunk because of bad input:
> "Invalid transactions should have been filtered out by the chunk producer, but if a chunk containing invalid transactions does make it to here, these transactions are skipped. This does pollute the chain with junk data, but it also allows the protocol to make progress, as the only alternative way to handle these transactions is to make the entire chunk invalid." [1](#0-0) 

Yet the two call sites that consume the `Result<ApplyResult, RuntimeError>` returned by `apply()` explicitly panic instead of returning a graceful error for two of the `RuntimeError` variants:

```
RuntimeError::UnexpectedIntegerOverflow(reason) => {
    panic!("RuntimeError::UnexpectedIntegerOverflow {reason}")
}
...
RuntimeError::ReceiptValidationError(e) => panic!("{}", e),
``` [2](#0-1) 

The identical pattern is duplicated in the test/user harness path: [3](#0-2) 

Both panic sites are annotated `// TODO(#2152): process gracefully`, i.e. the nearcore team itself has flagged that these code paths are known-unfinished and should not panic, exactly analogous to the finding's "MUST NOT revert" ERC-4626 requirement being violated because an underlying helper (`NoyaValueOracle._getValue()`) can still revert.

Internally, `apply_action_receipt` (`runtime/runtime/src/lib.rs:968-979`) does validate newly created receipts with `validate_receipt(..., NewReceipt)` and, when it fails, wraps the error gracefully into `ActionErrorKind::NewReceiptValidationError` rather than propagating a hard `RuntimeError`. Likewise, `process_incoming_receipts`/`process_delayed_receipts` validate incoming/dequeued receipts before execution and treat validation failures on the delayed queue as `StorageInconsistentState` rather than a raw `ReceiptValidationError` bubbling to the top. This shows that the nearcore engineers' intent is that `ReceiptValidationError`/`UnexpectedIntegerOverflow` reaching the top level of `apply()` should be rare/impossible under normal (honest) operation, but the explicit panic arms exist precisely because there remain call paths where a raw `RuntimeError::ReceiptValidationError` or `RuntimeError::UnexpectedIntegerOverflow` can still be returned from `apply()` (otherwise these match arms and the tracked TODO issue would not exist).

### Impact Explanation
If a transaction or receipt content can be crafted (by an unprivileged signer, since transaction/receipt content is fully attacker-influenced within the byte/action limits enforced only at parse time) such that `Runtime::apply` returns `RuntimeError::ReceiptValidationError` or `RuntimeError::UnexpectedIntegerOverflow` instead of a handled `ActionError`, then every node applying that chunk hits the `panic!` in `chain/chain/src/runtime/mod.rs`. Because chunk application is deterministic, every honest validator and RPC/full node tracking that shard panics identically upon replaying the same chunk — this is a transaction-triggered chain halt (loss of liveness across the network) rather than a state-root divergence, satisfying the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
The likelihood is constrained by whether a currently-reachable path exists that returns the raw `RuntimeError` variant (rather than the gracefully-handled `ActionErrorKind` wrapping already present for the known cases). The explicit TODO comment and the dedicated match arms indicate this is a recognized, tracked gap (`#2152`) rather than a purely theoretical concern; the nearcore developers considered it plausible enough to leave a comment and dedicated panic path instead of silently ignoring it. Exploitability requires finding a concrete crafted transaction/receipt that reaches `validate_receipt`/arithmetic accounting outside of the paths that already wrap the error (e.g., through`process_transactions`'s `tx_cost`/`calculate_tx_cost` overflow paths, which the docs say are converted into `CostOverflow` failed outcomes at `runtime/runtime/src/lib.rs:2010` — a possible counter-indication that this particular path is already handled). Without deeper trace of every call path, it cannot be conclusively confirmed that a specific external transaction can trigger the raw error today; this is flagged as uncertain.

### Recommendation
- Resolve tracked issue `#2152`: replace the `panic!` arms for `RuntimeError::ReceiptValidationError` and `RuntimeError::UnexpectedIntegerOverflow` in `chain/chain/src/runtime/mod.rs` (and the duplicated logic in `integration-tests/src/user/runtime_user.rs`) with graceful handling — e.g., treat the offending transaction/receipt as invalid and skip it (as is already done for `InvalidTxError`), consistent with the "always make progress" design invariant documented on `Runtime::apply`.
- Audit all call sites inside `runtime/runtime/src/lib.rs` (`process_local_receipts`, `process_delayed_receipts`, `process_incoming_receipts`, `apply_action_receipt`) to confirm no code path can return a raw `ReceiptValidationError`/`UnexpectedIntegerOverflow` from `apply()` for attacker-supplied receipt/transaction content; all validation failures on attacker-controlled data should be converted into `ActionError`/`InvalidTxError` outcomes scoped to the single transaction/receipt, never propagated as a hard `RuntimeError` that forces the caller to panic.

### Proof of Concept
Not independently reproduced against a live cluster within this analysis. Root cause is demonstrated statically:
1. `Runtime::apply`'s doc-comment establishes the invariant that invalid transaction/receipt content must never fail the whole chunk: [4](#0-3) 
2. The chain-layer caller nonetheless panics on `RuntimeError::ReceiptValidationError` / `RuntimeError::UnexpectedIntegerOverflow`, explicitly marked as an unresolved TODO: [2](#0-1) 
3. The identical panic pattern is duplicated in the test-harness `apply()` caller: [3](#0-2) 
4. `validate_receipt` is the function whose `Err(ReceiptValidationError)` return value feeds this error type: [5](#0-4) 

Confirming a concrete externally-reachable trigger (a specific transaction/receipt payload that reaches these unhandled arms rather than the already-gracefully-wrapped `ActionErrorKind::NewReceiptValidationError`/`CostOverflow` paths) would require deeper tracing of every receipt-processing branch, which was not conclusively completed in this pass — this gap is explicitly noted as unresolved.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-runner/src/wasmtime_runner/logic.rs#fn(read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt)
        | VersionedReceiptEnum::PromiseYield(action_receipt) => validate_action_receipt(
            limit_config,
            action_receipt,
            receipt.receiver_id(),
            current_protocol_version,
            mode,
        ),
        VersionedReceiptEnum::Data(data_receipt)
        | VersionedReceiptEnum::PromiseResume(data_receipt) => {
            validate_data_receipt(limit_config, &data_receipt)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
    }
}
