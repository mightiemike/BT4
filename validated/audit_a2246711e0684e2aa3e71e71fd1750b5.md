### Title
`ensure_match_transaction_info` never validates state-checkpoint / hot-state / position-state-checkpoint hashes, letting replay-verify tooling accept a corrupted state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/verification tools (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a freshly re-executed transaction produces the exact same committed result (`TransactionInfo`) as what is stored/authenticated on an archive or ledger. The function checks status, gas, write-set hash, and event-root hash, but it explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that authenticate the Sparse-Merkle/JMT state root produced by a block/state checkpoint. This is called out in the code's own TODO comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  deliberately omits verifying `TransactionInfo::state_checkpoint_hash()` (and the V1-only `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the recomputed state root. The comment explicitly documents the gap: [2](#0-1) 

This function is the sole state-divergence detector used by `replay_on_archive`'s `execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and compares the freshly computed `TransactionOutput` against the `expected_txn_info` pulled from the backup/archive: [3](#0-2) 

Because the comparator never checks the state checkpoint hash, if VM execution (or an upstream bug in checkpoint/state-root computation such as `do_state_checkpoint.rs`'s `get_state_checkpoint_hashes`) produces a state root that diverges from the one committed/authenticated in the archive, `execute_and_verify` will still report success — the mismatch is silently swallowed. The only fields cross-checked are status, gas, write-set hash and event-root hash; none of these bind to the actual state root recorded in `TransactionInfo::state_checkpoint_hash`.

This mirrors the external report's underlying bug class: a "sentinel/derived" field that is supposed to gate an authenticity check is silently excluded from validation in certain code paths, allowing state that should be rejected to be accepted as if it matched.

### Impact Explanation
Replay-verification is Aptos's primary tool for independently confirming that historical execution results (and thus the state root ultimately signed into `LedgerInfo`) are reproducible and correct from archived transaction/write-set data. If a VM regression, a non-deterministic native, or storage schema bug causes the locally recomputed state root to diverge from the authenticated one, this comparator will not catch it: replay-verify (`storage/db-tool/src/replay_on_archive.rs`, and any caller of `ensure_match_transaction_info`, including `aptos-debugger` and the CLI) reports a false success. This directly undermines the "proof and storage pivot" invariant that committed state must be provably equal to the correct VM result across executor-to-storage handoff and replay — a wrong state root can go undetected by the very tool meant to catch it, which is a proof-integrity/verification-bypass class issue on mainnet-grade tooling.

### Likelihood Explanation
The gap is 100%-reachable any time `ensure_match_transaction_info` is invoked (every replay-verify/replay_on_archive/debugger run), and it requires no attacker action to trigger — it's a structural blind spot in an integrity-checking function, not a rarely-hit edge case. However, actually exploiting it to hide a divergence still requires some other bug in the VM or checkpoint computation to produce the wrong state root in the first place. The comparator's silence means such a bug would go unnoticed until it manifests as a full state-sync/consensus divergence in practice, rather than being caught early by replay-verify.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, and where present, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against the corresponding hashes recomputed from the freshly-produced ledger state at each checkpoint version, before removing the TODO/gating comment. At minimum, callers such as `replay_on_archive` should independently verify the state checkpoint hash whenever available in the archived data, rather than relying solely on this comparator.

### Proof of Concept
1. Take any archived transaction range that includes a state-checkpoint transaction (block epilogue).
2. Execute a modified/buggy `AptosVM` (or corrupt the local backing store in a way that alters only the merklized state root but not the write set/events/gas/status) and run `replay_on_archive` against it.
3. `execute_and_verify` calls `ensure_match_transaction_info` at [4](#0-3)  which returns `Ok(())` because it never compares `state_checkpoint_hash`.
4. The tool reports "ReplayVerify coordinator succeeded" (per `storage/db-tool/src/replay_verify.rs`) despite the reconstructed state root being wrong.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
