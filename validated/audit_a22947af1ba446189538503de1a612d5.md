### Title
Pre-fork multisig weight inflation via signature-encoding malleability bypasses `checkWeight` dedup - (File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java)

### Finding Description
`TransactionCapsule.checkWeight` dedups signers using a `HashMap` keyed by `base64` — the *raw base64-encoded signature bytes* — unless `ForkController.instance().pass(VERSION_4_7_1)` is true, in which case the key switches to `encode58Check(address)` (the recovered signer address) [1](#0-0) . This conditional branch is explicit proof the pre-fork behavior dedups by signature bytes, not by recovered signer identity: `if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) { base64 = encode58Check(address); }` [2](#0-1) .

ECDSA over secp256k1 is malleable: for any valid signature `(r, s, v)` from a private key, `(r, n-s, v')` (with `v` flipped) is also a valid, distinct-byte signature that `ECKey.signatureToAddress` recovers to the *same* address, because both encode the same underlying `k`-based signature up to the curve's canonical/negated-`s` symmetry. `SignUtils.signatureToAddress` performs this recovery for both variants identically [3](#0-2) .

Consequently, before `VERSION_4_7_1` activates, an attacker holding exactly one Active-permission key with weight `w < threshold` can:
1. Sign the transaction hash once normally, obtaining signature `S1 = (r, s, v)`.
2. Derive the malleable counterpart `S2 = (r, n-s, v^1)` from the same private key (pure arithmetic on the already-known `s`, no private key oracle needed).
3. Submit `[S1, S2]` via `checkWeight` (reachable through `Wallet.getTransactionSignWeight` / `getTransactionApprovedList` and, more critically, through actual transaction/permission signature validation in `Manager`).
4. Both signatures pass the `sig.size() < 65` format check, both recover to the same address via `signatureToAddress`, and since `base64` differs byte-for-byte between `S1` and `S2`, `addMap.containsKey(base64)` returns false both times — the "has signed twice" check at line 260-262 never fires.
5. `currentWeight` accumulates `w + w = 2w`, which can exceed `permission.getThreshold()` even though only one distinct key signed.

This directly violates the stated invariant that multisig weight must reflect distinct signing keys, not distinct signature encodings, and defeats the entire purpose of `checkWeight`'s duplicate-signer guard.

### Impact Explanation
If this path is reachable on a live/private network where `VERSION_4_7_1` has not yet been activated (new chains, private/test chains, or the interval between genesis and community activation of that hard fork on mainnet), an attacker with a single low-weight Active-permission key can forge sufficient weight to pass the multisig threshold alone. Since `checkWeight` gates transaction execution for permission-controlled accounts (contract calls, transfers, account permission changes), this allows unauthorized execution of privileged multisig-protected operations — effectively a full bypass of multisig authorization for any account whose real signer holds partial weight, i.e., unauthorized value transfer / privileged action execution without acquiring the additional required keys.

### Likelihood Explanation
- Requires only a single already-owned private key with nonzero weight in the target permission (attacker "owns exactly one key," as stated) — no key leakage or privileged access needed.
- Malleable signature derivation is pure elliptic-curve arithmetic (`s' = n - s`, `v' = v XOR 1`), computable without any oracle.
- Feasibility is gated entirely on whether `VERSION_4_7_1` is active on the target network. On current TRON mainnet this fork is long active, closing this window; however, the code path itself is exercised unconditionally by any deployer/operator of a new/private/test java-tron network, or any chain that has not yet reached the fork's activation height/vote threshold. The comment in `SignUtils.isValidLength` even documents that `checkWeight` "intentionally" keeps the loose `size < 65` check for compatibility reasons, but does not address the malleability dedup gap for the pre-fork branch [4](#0-3) .
- Repeatable deterministically once threshold-weight math is worked out for a target permission.

### Recommendation
Remove the fork-gated behavior and always dedup by the recovered signer address (`encode58Check(address)`), regardless of `ForkController.instance().pass(VERSION_4_7_1)`. If backward chain-state compatibility across the fork boundary is required, keep the version check strictly for consensus determinism but ensure any new/private network's genesis config activates `VERSION_4_7_1` from block 0, and document that pre-fork behavior is known-vulnerable and must not be relied upon in production.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/capsule/TransactionCapsuleMalleabilityTest.java
// Preconditions: ForkController.instance().pass(VERSION_4_7_1) == false (simulate pre-fork state,
// e.g. via test double / no fork activation in test ChainBaseManager).

@Test
public void testMalleableSignatureWeightInflationPreFork() throws Exception {
  ECKey key = new ECKey(); // attacker's single real key, weight = 1 in permission
  Permission permission = Permission.newBuilder()
      .setThreshold(2)
      .addKeys(Key.newBuilder().setAddress(ByteString.copyFrom(key.getAddress())).setWeight(1))
      .build();

  byte[] hash = Sha256Hash.hash(true, "test-tx".getBytes());

  ECKey.ECDSASignature sig1 = key.sign(hash);              // (r, s, v)
  ECKey.ECDSASignature sig2 = sig1.toCanonicalised().negateS(); // (r, n-s, v^1), same key, different bytes
  // sig2 must be constructed such that ECKey.signatureToAddress(hash, sig2) == key.getAddress()

  ByteString bs1 = ByteString.copyFrom(sig1.toByteArray(sig1.v));
  ByteString bs2 = ByteString.copyFrom(sig2.toByteArray(sig2.v));

  List<ByteString> sigs = Arrays.asList(bs1, bs2);
  List<ByteString> approveList = new ArrayList<>();

  long weight = TransactionCapsule.checkWeight(permission, sigs, hash, approveList);

  // Expected (bug): weight == 2, threshold satisfied with 1 real key.
  // Correct behavior: should throw PermissionException("... has signed twice!")
  assertEquals(2L, weight); // demonstrates threshold bypass with a single key pre-fork
  assertTrue(weight >= permission.getThreshold());
}
```
Expected result confirming the bug: the test passes with `weight == 2` and no `PermissionException`, demonstrating that one key's two malleable signature encodings satisfy a threshold of 2. Post-fork (with `VERSION_4_7_1` active), rerunning the same test must throw `PermissionException` because dedup switches to address-based keying.
