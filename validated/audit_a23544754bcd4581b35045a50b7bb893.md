### Title
Type/Payload Confusion in Smart Contract Transaction Routing Causes NullPointerException DoS - (File: `chainbase/src/main/java/org/tron/core/db/TransactionTrace.java`)

### Summary
Analogous to the Scroll `commitBatch` bug where a caller-supplied `_version` tag selects a code path independent of the actual batch data (allowing version/data mismatch), java-tron routes smart-contract transactions using the caller-supplied `Transaction.Contract.type` enum field, while the actual payload is unpacked from the `Any parameter` field based on its embedded `type_url`. These two are validated independently and a mismatch reaches unguarded code before actuator validation occurs, causing a `NullPointerException`.

### Finding Description
`TransactionTrace`'s constructor determines `trxType` purely from the declared `Contract.type` enum field: [1](#0-0) 

Separately, `ContractCapsule.getTriggerContractFromTransaction` unpacks the `Any` parameter based on its internal `type_url`, independent of the declared `type` field, returning `null` on mismatch instead of throwing: [2](#0-1) 

`TransactionTrace.checkIsConstant()` is invoked before any actuator-level `validate()` runs, and it calls this unpack helper and immediately dereferences its result without a null check: [3](#0-2) 

The `Manager.processTransaction` pipeline confirms `checkIsConstant()` runs prior to `exec()` (which is where `VMActuator.validate()` — the code that actually checks `any.is(TriggerSmartContract.class)` and would reject the payload — executes): [4](#0-3) 

Thus, a transaction whose `Contract.type` is declared `TriggerSmartContract` but whose `Any parameter` field is packed with a different message type (or a malformed/mismatched `type_url`) will cause `getTriggerContractFromTransaction` to return `null` (via a caught `InvalidProtocolBufferException`), and `checkIsConstant()` will then perform `triggerContractFromTransaction.getContractAddress()` on a `null` reference, throwing an unhandled `NullPointerException`.

### Impact Explanation
This is directly reachable by any user broadcasting a crafted transaction to the network — there is no privileged-actor requirement, unlike the original Scroll finding (which required a sequencer role). An unhandled `NullPointerException` thrown mid-transaction-processing, if not caught by a top-level handler in `Manager.processTransaction`/block application, can crash transaction processing for that block or transaction, representing a availability/DoS risk against node transaction processing (`pushTransaction`/block validation path).

### Likelihood Explanation
Likelihood is high given the entry point is a standard broadcast transaction (`TriggerSmartContract`) processed by any full node; no special privileges or malicious peer collusion are required. It only requires the dynamic parameter `allowTvmConstantinople` to be unset (i.e., `getAllowTvmConstantinople() != 1`), which is the condition guarding `checkIsConstant()`'s early return — a condition dependent on chain configuration/fork status, not on the attacker's control.

### Recommendation
In `TransactionTrace.checkIsConstant()` and any other call sites of `ContractCapsule.getTriggerContractFromTransaction` / `getSmartContractFromTransaction`, add null checks and throw `ContractValidateException` before dereferencing the returned object, mirroring the check already present in `VMActuator`'s `InternalTransaction` construction path. More fundamentally, unify the "declared type" and "actual Any payload type" verification (e.g., verify `contract.getParameter().is(ExpectedClass.class)` before selecting an execution path) at the earliest transaction-processing entry point, not only inside the actuator's `validate()`.

### Proof of Concept
Not independently executed (index-based analysis only); the described NPE path is derived from static code reading of `TransactionTrace.checkIsConstant()`, `ContractCapsule.getTriggerContractFromTransaction()`, and `Manager.processTransaction()`'s call ordering. A concrete PoC would involve constructing a `Transaction` whose single `Contract` has `type = TriggerSmartContract` but whose `parameter` `Any` is packed with a different protobuf message (e.g., `AccountCreateContract`), then broadcasting it while `allowTvmConstantinople != 1`, and observing whether the node throws an uncaught `NullPointerException` during `checkIsConstant()`. This was not run against a live/test node as part of this analysis; verifying the actual exception propagation and whether any outer `catch` in `Manager.processTransaction`/`pushTransaction` gracefully handles a `NullPointerException` (versus only checked exceptions like `ContractValidateException`) would require dynamic testing, which is out of scope for this static review.

    try {
      Any any = trx.getRawData().getContract(0).getParameter();
