## Finding: `ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify tools to accept a divergent state root

### Title
Replay/backup verification accepts a `TransactionOutput` whose state/hot-state/position checkpoint root diverges from the authenticated `TransactionInfo` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/debug/backup-verification tooling to assert that a locally re-executed transaction output matches the authenticated `TransactionInfo` committed on-chain. It checks status, gas, write-set hash, and event-root hash, but the author's own comment states it does **not** check the state checkpoint hash, hot-state checkpoint hash, or `position_state_checkpoint_hash` fields of `TransactionInfo`: [1](#0-0) 

This is structurally the same defect pattern as the GMX report: a value that is supposed to gate acceptance (the swap's `minOutputAmount` / here, the checkpoint root) is silently skipped in one code path (no swap path / here, checkpoint-hash comparison in the "match" verifier), letting a state divergence pass as "verified."

### Finding Description
`ensure_match_transaction_info` is called from replay/debugger/verification entry points (`aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `storage/db-tool/src/replay_on_archive.rs`) to confirm that a transaction re-executed against archived state produces the same committed result as what is authenticated by the accumulator-backed `TransactionInfo`: [2](#0-1) 

It compares `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event-root hash — but never compares `TransactionInfo::state_checkpoint_hash()`, the hot-state checkpoint hash, or (per the TODO) `position_state_checkpoint_hash` computed during real ledger commit. Those checkpoint hashes are exactly the values validated during live block/chunk commit via `DoStateCheckpoint::get_state_checkpoint_hashes`, which does perform a strict `ensure!` comparison against `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints`: [3](#0-2) 

So the *live* commit path correctly validates checkpoint roots, but the *replay-verify* path (used to independently audit archived history, e.g. `replay_on_archive`) has no equivalent check. If the Move VM's state-checkpoint/JMT-root computation for a given transaction diverges from what is stored on-chain (due to a bug elsewhere in state summary/hot-state/position root computation), `ensure_match_transaction_info` would still report success as long as write-set bytes, events, gas, and status match — it never notices that the resulting Merkle root differs.

### Impact Explanation
Under the State-Integrity Gate this is a "wrong accumulator root/Merkle proof accepted as valid" and "authenticated API/verification output bound to the wrong ... proof context" class issue: the replay-verify tool (used for auditing backups and detecting silent forks/divergence) would incorrectly attest that history is correct even when the resulting state root differs from the one committed and signed by validators. This weakens the last line of defense that is specifically meant to catch state-root divergence bugs (including hard-fork-only divergence), because the one check designed to catch "committed state differs from correct VM result" is missing exactly for the checkpoint-hash class of value.

### Likelihood Explanation
This is not attacker-triggerable directly (it requires either a pre-existing divergence bug in state-checkpoint/hot-state/position-root computation, or a compromised archive/backup being replayed), so likelihood of exploitation without another underlying bug is low. However, its severity as an integrity-verification blind spot is real: the code's own TODO comment explicitly flags it as unsafe to enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS` before fixing this, which is a direct acknowledgment by the maintainers that the current check is insufficient for its stated purpose.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash()` (and, once enabled, hot-state and position-state checkpoint hashes) between the locally-recomputed checkpoint output and `txn_info`, mirroring the `ensure!` logic already used in `DoStateCheckpoint::get_state_checkpoint_hashes`, before this comparator is relied upon for any state root that participates in consensus commitment (in particular before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`).

### Proof of Concept
Not directly exploitable as a standalone PoC — this is a verification-tool gap rather than a state-mutation bug. It can only be demonstrated in combination with a genuine state-checkpoint-root computation bug: run `replay_on_archive`/`aptos-debugger` on a transaction whose write-set/events/gas/status match the archived `TransactionInfo` but whose recomputed state (or hot-state/position) root differs, and observe that `ensure_match_transaction_info` returns `Ok(())` despite the divergence.

**Caveat:** I could not fully trace whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled on mainnet or gated behind an unreleased feature flag within the available iterations, which affects the immediate blast radius of the position-checkpoint portion of this gap; the state/hot-state checkpoint-hash omission, however, applies regardless of that flag.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
