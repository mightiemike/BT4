### Title
NullPointerException in `VMActuator.call()` when a smart contract's `origin_address` (deployer) has self-destructed, permanently DoS'ing all future calls to the contract - (File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java)

### Summary
This is a valid analog to the Aave Lens "referral fee" bug. In the original finding, `FeeCollectModule` called `IERC721(HUB).ownerOf(referrerProfileId)` without handling the case where the referenced profile NFT had been burned, causing an unrelated, otherwise-valid operation (collecting a mirror) to revert. In java-tron, `VMActuator.call()` similarly fetches the account belonging to a *referenced* entity — the contract's deployer/`origin_address` — without checking for `null`, and that account can legitimately cease to exist (via `SUICIDE`/`selfdestruct`), causing every subsequent call to the contract to fail with an unhandled `NullPointerException` instead of degrading gracefully (e.g., treating origin energy contribution as zero).

### Finding Description
When a user calls a deployed smart contract via `TriggerSmartContract`, `VMActuator.call()` looks up the contract's creator/origin account to compute the energy split between caller and origin: [1](#0-0) 

```java
AccountCapsule caller = rootRepository.getAccount(callerAddress);
...
AccountCapsule creator = rootRepository
    .getAccount(deployedContract.getInstance().getOriginAddress().toByteArray());
energyLimit = getTotalEnergyLimit(creator, caller, contract, feeLimit, callValue);
```

There is no null-check on `creator` before it is passed on. `getTotalEnergyLimit` routes to `getTotalEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFloatRatio`, both of which immediately dereference `creator`: [2](#0-1) 

```java
public long getTotalEnergyLimitWithFixRatio(AccountCapsule creator, AccountCapsule caller,
    TriggerSmartContract contract, long feeLimit, long callValue)
    throws ContractValidateException {

  long callerEnergyLimit = getAccountEnergyLimitWithFixRatio(caller, feeLimit, callValue);
  if (Arrays.equals(creator.getAddress().toByteArray(), caller.getAddress().toByteArray())) {
```

`creator.getAddress()` on a `null` reference throws an unhandled `NullPointerException`.

The `origin_address` account referenced here is not guaranteed to exist forever: the TVM's `SUICIDE`/`selfdestruct` opcode explicitly removes an account from the `AccountStore` (confirmed by `getResult().addDeleteAccount(...)` in `Program.suicide()` and by the assertion `Assert.assertNull(dbManager.getAccountStore().get(suicideContract))` in `ProgramResultTest`): [3](#0-2) [4](#0-3) 

Notably, the java-tron team already recognized and patched exactly this failure mode in a sibling code path, `TransactionTrace.pay()` / `ReceiptCapsule.payEnergyBill()`, which explicitly guards against a `null` origin account (an account whose deployer self-destructed) when `AllowTvmConstantinople` is enabled: [5](#0-4) 

```java
if (Objects.isNull(origin) && dynamicPropertiesStore.getAllowTvmConstantinople() == 1) {
  payEnergyBill(dynamicPropertiesStore, accountStore, forkController, caller,
      receipt.getEnergyUsageTotal(), receipt.getResult(), energyProcessor, now);
  return;
}
```

This proves the root cause and the fix pattern are well-understood elsewhere in the codebase, but the fix was not applied to `VMActuator.call()`'s pre-execution energy-limit computation, which runs *before* `payEnergyBill` and unconditionally dereferences `creator`.

### Impact Explanation
Once a contract's deployer account self-destructs (a legitimate and common pattern for factory-deployed clone/proxy contracts, or any contract whose deployer is itself a contract that later self-destructs), `TriggerSmartContract` calls against that deployed contract become permanently unable to execute (non-constant calls hit the null-dereference path unconditionally whenever `caller != creator`). This is a state/availability impact: legitimate, otherwise fully valid transactions that should succeed instead throw an uncaught `NullPointerException`, denying service to all users of that contract going forward — analogous to the "collect from the mirror fails without error" outcome in the original report, but escalated to a permanent full contract-level halt rather than a single feature failure.

### Likelihood Explanation
Reaching this path requires only: (1) a contract `C1` deployed by another contract `C2` (or any address that can self-destruct, i.e., contract-deployed-contract chains, which are common with factories/proxies), (2) `C2` self-destructing (a normal, unprivileged, permissionless operation via `selfdestruct`), and (3) any unprivileged user subsequently calling `C1` with a non-constant `TriggerSmartContract` where caller != origin. All actions are available to ordinary users without special permissions, and no error handling elsewhere in `VMActuator.call()` prevents it.

### Recommendation
Apply the same defensive pattern already used in `ReceiptCapsule.payEnergyBill()` to `VMActuator.call()`/`getTotalEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFloatRatio`: check whether `creator == null` (i.e., the origin account no longer exists) and, in that case, skip creator-side energy computation (treat contributed creator energy as 0) instead of dereferencing a null object. This preserves the ability of unprivileged users to keep calling contracts whose origin account has been destroyed, mirroring the recommended fix from the original report (treat the missing referenced entity as "non-existent" rather than causing failure).

### Proof of Concept
1. Deploy contract `C2` (a simple contract capable of `selfdestruct`).
2. From `C2`'s constructor (or a callable function), deploy contract `C1` (`CREATE`), so `C1.origin_address == C2`'s address.
3. Call `C2.selfdestruct(anyAddress)`; this deletes `C2`'s account from `AccountStore` (per `Program.suicide()`/`getResult().addDeleteAccount`).
4. From any unprivileged EOA (not the same address as `C1`'s deleted origin), send a `TriggerSmartContract` transaction (non-constant call) to `C1`.
5. `VMActuator.call()` executes `rootRepository.getAccount(deployedContract.getInstance().getOriginAddress().toByteArray())`, which returns `null` because the origin account was deleted; `getTotalEnergyLimitWithFixRatio`/`WithFloatRatio` then calls `creator.getAddress()` on the null reference, throwing `NullPointerException`, and the transaction fails unexpectedly instead of executing normally.
