### Title
Missing tenant-isolation check in `tokenExchange` allows a session token for shop A to be exchanged against an attacker-supplied `shop` parameter - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`tokenExchange` decodes the caller-supplied session token only to verify its signature, audience, and expiry, but never verifies that the token's `dest` claim matches the `shop` parameter that is used to build the outbound OAuth request URL. Since `shopify-app-remix`/`shopify-app-react-router` derive `shop` directly from an attacker-controllable request query parameter rather than from the token itself, a caller can submit a mismatched `(shop, sessionToken)` pair and have the library build and send a token-exchange POST to `https://<attacker-chosen-shop>/admin/oauth/access_token` using a session token that was issued for a different shop.

### Finding Description
`tokenExchange` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` does: [1](#0-0) 

`decodeSessionToken` only checks the JWT signature, `exp`/`nbf`, and optionally `aud`; it never inspects or returns/validates `dest` against any expected shop: [2](#0-1) 

The `shop` value used to build the request URL is taken as-is from the caller and only passed through `sanitizeShop`, which just validates hostname format/domain — it does not cross-check it against the token's `dest`: [3](#0-2) 

Critically, in `shopify-app-remix` the `shop` passed into `tokenExchange` originates directly from the request's URL query string, not from the decoded token: [4](#0-3) 

This `shop` is threaded straight through `TokenExchangeStrategy.authenticate` → `exchangeToken` → `api.auth.tokenExchange({shop, sessionToken, ...})` without ever comparing it to the token's `dest`: [5](#0-4) [6](#0-5) 

By contrast, `shopify-app-express`'s `performTokenExchange` derives `shop` from `payload.dest` of the same decoded token, so no mismatch is possible in that flow: [7](#0-6) 

So the root-cause gap is specifically in the shared library function `tokenExchange`, which has no invariant enforcing `payload.dest === shop`, combined with `shopify-app-remix`/`shopify-app-react-router` supplying an independently attacker-influenced `shop` value from the request URL.

### Impact Explanation
If exploited, the library will construct and send an OAuth token-exchange POST to a shop domain of the attacker's choosing, using a subject_token (session token) that was minted for a different shop. This violates the intended TENANT_ISOLATION invariant at the library layer: the library performs no client-side validation preventing a session token from shop A from being presented as proof of identity for shop B's token exchange endpoint. Whether this results in an actual minted access token for the victim shop depends entirely on Shopify's backend OAuth server correctly rejecting the mismatched `dest`/host pair — that enforcement is external to this codebase and not verifiable here. Nonetheless, this is a defense-in-depth failure: the app library should fail closed itself rather than relying solely on the remote server to catch a cross-tenant identity mismatch, and it needlessly transmits a shop-A-scoped identity token toward an arbitrary, attacker-chosen host.

### Likelihood Explanation
The attacker only needs a valid session token for a shop they have legitimate access to (trivial, since they are a merchant/customer of shop A) and the ability to control the `shop` query parameter on a request to a `shopify-app-remix`/`shopify-app-react-router`-based app (also straightforward, since `getShopFromRequest` reads it unauthenticated from the URL). No secrets, privileged roles, or non-default configuration are required.

### Recommendation
In `tokenExchange` (packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts), after decoding the session token, extract `dest` from the decoded payload and require that the sanitized `shop` matches the shop derived from `dest` (case-insensitively, comparing normalized hostnames), throwing `InvalidJwtError`/similar if they diverge instead of silently proceeding with the caller-supplied `shop`.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/auth/oauth/__tests__/token-exchange.test.ts
it('rejects mismatched shop/sessionToken dest', async () => {
  const tokenForShopA = createSessionToken({dest: 'https://shop-a.myshopify.com', aud: config.apiKey});

  let capturedUrl: string | undefined;
  (fetchRequestFactory as jest.Mock).mockReturnValue(() => async (url: string) => {
    capturedUrl = url;
    return {ok: true, json: async () => ({access_token: 'stolen'})};
  });

  await expect(
    shopify.auth.tokenExchange({
      shop: 'victim-shop.myshopify.com',
      sessionToken: tokenForShopA,
      requestedTokenType: RequestedTokenType.OfflineAccessToken,
    }),
  ).rejects.toThrow(InvalidJwtError);

  expect(capturedUrl).toBeUndefined();
});
```
Currently this test fails because `tokenExchange` proceeds and POSTs to `https://victim-shop.myshopify.com/admin/oauth/access_token` with `subject_token` set to shop A's session token, with no rejection at the library level.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
