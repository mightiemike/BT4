### Title
Signature validation bypass for post-`deploy_account` invoke transactions targeting undeployed accounts - ([File: crates/apollo_gateway/src/stateful_transaction_validator.rs])

### Summary
The gateway's "skip validation for UX" optimization for `invoke` transactions immediately following an account's `deploy_account` relies on a mempool check, `account_tx_in_pool_or_recent_block`, that only verifies *some* transaction exists for the sender address — not specifically that a validly-signed `deploy_account` transaction authorized that account. This lets an unauthenticated third party submit an `invoke` transaction (nonce 1, with an invalid/arbitrary signature) against any account address that is currently mid-deployment (nonce 0, tx present in pool), and have the sequencer execute `__execute__` while entirely skipping the `__validate__` signature check.

### Finding Description
When the gateway validates an incoming transaction it calls `run_pre_validation_checks` → `skip_stateful_validations`: [1](#0-0) 

This function returns `true` (skip validation) whenever:
1. the incoming invoke tx has nonce `1`,
2. the account's on-chain nonce is `0` (i.e., the account has not been deployed yet), and
3. `mempool_client.account_tx_in_pool_or_recent_block(sender_address)` returns `true`.

The intent (per the comment) is: "verify that a deploy_account transaction exists for this account… it is sufficient to check if the account exists in the mempool." However, the actual mempool check does not verify that the existing transaction is a `deploy_account` transaction or that it was signed by the account owner — it only checks whether *any* transaction for that address is currently staged/pooled or recently committed: [2](#0-1) 

The `skip_validate` result is passed straight into `run_validate_entry_point`, which maps it directly to the blockifier's `ExecutionFlags::validate` flag: [3](#0-2) 

And in the blockifier, when `execution_flags.validate` is `false`, the `__validate__`/`__validate_deploy__` entry point is never invoked at all — no signature check of any kind is performed: [4](#0-3) 

Because the "presence check" is generic (any tx for the address, not "a deploy_account tx for the address"), any unauthenticated attacker who observes (via RPC/mempool visibility, or simply by submitting their own throwaway tx for that address first) that an address has nonce `0` and *some* transaction pending for it can submit a second, unsigned/garbage-signature `invoke` transaction with `nonce = 1` targeting that same sender address. The sequencer will skip `__validate__` for it and directly run `__execute__` with attacker-controlled calldata, using the victim account's authority (balance, calls, etc.).

### Impact Explanation
This breaks the fundamental invariant that only the account owner (holder of the private key validated in `__validate__`) can authorize state-changing calls from that account. An attacker can:
- Drain any pre-funded balance held by a counterfactual/soon-to-be-deployed account (a common pattern: users fund the deployment address before sending `deploy_account`) by injecting a competing `invoke` transaction with nonce 1 and arbitrary calldata (e.g., `transfer` to the attacker) before the legitimate owner's own invoke.
- Cause unauthorized account actions to be committed to the block, since `__execute__` runs without any signature/authorization check.
- This maps to "unauthorized account action" / concrete loss of funds — satisfying the required Medium/High/Critical impact and reachability criteria (a single submitted transaction from an unprivileged sender).

The severity depends on race/ordering (the malicious invoke and the legitimate one compete for the same nonce slot; whichever the mempool selects executes), but the mere existence of an unauthenticated path to skip `__validate__` for arbitrary calldata is itself an authentication-bypass class bug, directly analogous to the Better-Auth root cause (fallback/heuristic logic substituting for actual verified identity/authorization).

### Likelihood Explanation
Likelihood is Medium-High: the preconditions (an account with nonce 0 that already has a transaction in the mempool/pool) occur naturally and frequently in the "deploy_account + invoke" UX flow that this feature was built to support, and mempool/pending-tx visibility (via p2p propagation or RPC) makes it straightforward for an attacker to detect and race such accounts. No special privileges are required — only the ability to submit a normal `invoke` RPC transaction.

### Recommendation
`skip_stateful_validations`/`account_tx_in_pool_or_recent_block` must be strengthened so that the skip decision is contingent on the *specific*, already-validated `deploy_account` transaction for that address, signed by the account's own key, not merely "any transaction' exists for the address. Concretely:
- Track (address → validated deploy_account tx hash) explicitly in the mempool state instead of a boolean "contains_account" check, and require that a matching record exists before skipping validation of a dependent invoke.
- Alternatively, always run `__validate__` for such invoke transactions but exempt the fee/nonce race problem via other means (e.g., only skip if the exact tx hash referenced by the client as "prerequisite deploy_account" is confirmed to be a validated deploy_account with matching sender_address).

### Proof of Concept
1. Victim precomputes/counterfactually deploys account `A` (via `calculate_contract_address`) and funds it with STRK/ETH before deployment (a common wallet UX pattern).
2. Victim submits `deploy_account` (nonce 0) for `A`; it passes `__validate_deploy__` and enters the mempool (`account_tx_in_pool_or_recent_block(A) == true`).
3. Attacker, observing the pending `deploy_account` (via `starknet_getMempoolContent`/p2p gossip or simply by polling nonce), crafts an `invoke` transaction: `sender_address = A`, `nonce = 1`, arbitrary/garbage `signature`, `calldata` calling `A`'s `__execute__` with a `transfer` call moving `A`'s pre-funded balance to the attacker's address.
4. Attacker submits this invoke to the gateway. `extract_state_nonce_and_run_validations` sees `tx.nonce()==1`, `account_nonce==0`, and `account_tx_in_pool_or_recent_block(A)==true` → returns `skip_validate = true`.
5. `run_validate_entry_point` sets `execution_flags.validate = false`; the blockifier's `validate_tx` short-circuits at `crates/blockifier/src/transaction/account_transaction.rs:999-1001` and never checks the (invalid) signature.
6. Once `deploy_account` commits (nonce becomes 1-eligible), the attacker's unsigned invoke is eligible to execute `__execute__` directly, transferring out the account's funds without ever having satisfied `__validate__`.

/// Check if validation of an invoke transaction should be skipped due to deploy_account not being
/// processed yet. This feature is used to improve UX for users sending deploy_account + invoke at
/// once.
async fn skip_stateful_validations(
    tx: &ExecutableTransaction,
    account_nonce: Nonce,
    mempool_client: SharedMempoolClient,
) -> StatefulTransactionValidatorResult<bool> {
    if let ExecutableTransaction::Invoke(ExecutableInvokeTransaction { tx, .. }) = tx {
        // check if the transaction nonce is 1, meaning it is post deploy_account, and the
        // account nonce is zero, meaning the account was not deployed yet.
        if tx.nonce() == Nonce(Felt::ONE) && account_nonce == Nonce(Felt::ZERO) {
            let account_address = tx.sender_address();
            debug!("Checking if deploy_account transaction exists for account {account_address}.");
            // We verify that a deploy_account transaction exists for this account. It is sufficient
            // to check if the account exists in the mempool since it means that either it has a
            // deploy_account transaction or transactions with future nonces that passed
            // validations.
            return mempool_client
                .account_tx_in_pool_or_recent_block(tx.sender_address())
                .await
                .map_err(|err| mempool_client_err_to_deprecated_gw_err(&tx.signature(), err))
                .inspect(|exists| {
                    if *exists {
                        debug!("Found deploy_account transaction for account {account_address}.");
                    } else {
                        debug!(
                            "No deploy_account transaction found for account {account_address}."
                        );
                    }
                });
        }
    }

    Ok(false)
}
