### Title
Missing deduplication of witness addresses in `VoteWitnessActuator` allows duplicate vote entries in an account's votes list - (`actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
`VoteWitnessActuator`, which processes the broadcast-able `VoteWitnessContract` sent by any unauthenticated account holder, validates each `Vote` entry individually (address validity, per-vote count > 0, total sum ≤ TRON power) but never checks whether the same witness address appears more than once in `votesList`. In `countVoteAccount()`, each vote entry is applied with `accountCapsule.addVotes(...)` inside a plain `forEach`, appending one `Vote` protobuf entry per list item with no merging. This is the same bug class as the reported `ExchangeIssuanceModule.validateSendTokenParams` issue: an array-of-(address, amount) parameter is validated for per-item well-formedness and aggregate bounds, but never checked for duplicate keys, breaking an implicit "one entry per key" invariant relied on elsewhere in the codebase.

### Finding Description
`VoteWitnessActuator.validate()` iterates `contract.getVotesList()` and validates each vote's address/count and accumulates a `sum` used to bound total TRON power usage: [1](#0-0) 

Nothing in this loop rejects or merges duplicate `witnessCandidate` addresses; the sum check only bounds the total, not per-witness uniqueness. The corresponding `countVoteAccount()` then applies votes verbatim without merging: [2](#0-1) 

`AccountCapsule.addVotes()` unconditionally appends a new `Vote` entry to the account's `votes` repeated field — it does not look for an existing entry with the same `voteAddress` to merge into: [3](#0-2) 

This directly contrasts with the TVM-native equivalent, `VoteWitnessProcessor` (used when voting is triggered via a smart contract call), which explicitly deduplicates/merges votes for the same witness into a `HashMap` before applying them, with an inline comment `// merge vote for same witness`: [4](#0-3) 

Because `VoteWitnessActuator` is the direct execution path for the on-chain `VoteWitnessContract` transaction type (broadcastable by any account), a caller can submit a vote list containing the same witness address multiple times (e.g., `[witnessA:1, witnessA:1, ..., up to MAX_VOTE_NUMBER=30 times]`), each with `voteCount > 0`, and pass `validate()` as long as the aggregated sum stays within tron power. `countVoteAccount()` then stores the account's `votes` field with N separate entries for the same witness, rather than one merged entry.

### Impact Explanation
Downstream consumers of `AccountCapsule.getVotesList()` (e.g. `MortgageService.computeReward`/`withdrawReward`, `VoteRewardUtil.computeReward`, `RewardViCalService`) iterate the votes list and, per entry, compute reward contribution by delta-VI multiplied by that entry's vote count, summing across all entries: [5](#0-4) 

Because the reward formula per witness/cycle uses `deltaVi * userVote`, and duplicate entries for the same witness are simply summed independently rather than being treated as one combined vote to that witness, having N entries with vote counts v1..vN for the same witness produces the same total reward as one merged entry `sum(v1..vN)` under the current linear formula — so the strict reward accounting itself does not appear to be exploitable for value creation in the code paths reviewed. However, this violates the implicit invariant (enforced elsewhere, e.g. `AccountPermissionUpdateActuator.checkPermission` explicitly rejects duplicate addresses, and `VoteWitnessProcessor` explicitly merges duplicates) that an account's vote list contains at most one entry per witness address. This inconsistency between the two code paths for functionally identical operations (`VoteWitnessContract` broadcast vs. TVM `vote` precompile/native contract) is itself a correctness/maintainability defect, and any future logic that assumes one-entry-per-witness (e.g., set/map-based lookups, `Votes.getOldVotesList()` merging logic, or serialization size assumptions) could silently misbehave or be a DoS vector by inflating the account's votes payload size up to `MAX_VOTE_NUMBER` duplicate entries with no additional cost beyond the transaction fee.

### Likelihood Explanation
Any account holder that has frozen TRX (i.e. has TRON power) can trigger this by broadcasting a single `VoteWitnessContract` transaction with a crafted `votes` list containing repeated witness addresses (up to `MAX_VOTE_NUMBER` = 30 entries per the check at line 93-97). No special privileges, keys, or peer compromise are required — this is reachable purely via a standard broadcast transaction.

### Recommendation
In `VoteWitnessActuator.validate()`, reject contracts whose `votesList` contains duplicate `voteAddress` values (mirroring the explicit duplicate-address check already used in `AccountPermissionUpdateActuator.checkPermission`), or alternatively merge duplicate witness votes in `countVoteAccount()` the same way `VoteWitnessProcessor.execute()` does via a `Map<ByteString, Long>` accumulator before calling `accountCapsule.addVotes(...)`. This keeps the two vote-processing code paths (regular contract vs. TVM native contract) consistent and preserves the one-entry-per-witness invariant relied upon elsewhere in the codebase.

### Proof of Concept
1. Freeze balance for `OWNER_ADDRESS` to obtain TRON power (e.g. via `FreezeBalanceActuator`, as done in `VoteWitnessActuatorTest`).
2. Build a `VoteWitnessContract` with `votesList` containing the same `WITNESS_ADDRESS` repeated, e.g. 5 entries each with `voteCount = 1`, using a helper similar to the existing test utility `getRepeateContract`: [6](#0-5) 
3. Call `VoteWitnessActuator.validate()` — it passes because each entry individually satisfies address validity, `voteCount > 0`, and the aggregated `sum` (5) stays within tron power.
4. Call `execute()` — `countVoteAccount()` stores 5 separate `Vote` entries for the same witness address in `AccountCapsule.getVotesList()`, instead of one merged entry with `voteCount = 5`, unlike the TVM-triggered vote path (`VoteWitnessProcessor`) which would merge them into a single entry.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
