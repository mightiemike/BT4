### Title
Potential Unbounded Allocation from Attacker-Controlled Array Size in Deprecated Syscall Array Reading - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The deprecated (Cairo0) syscall array-reading helper `read_felt_array` takes an `array_size` felt directly from VM memory that is under a contract's control, converts it to `usize`, and forwards it to `felt_range_from_ptr` without first validating that the declared size is consistent with any bound on remaining/available memory. [1](#0-0) 

### Finding Description
`read_felt_array` reads `array_size` via `felt_from_ptr`, a value that a Cairo0 contract writes into its own execution memory when preparing a syscall request (e.g., calldata length for `call_contract`, `library_call`, deploy syscalls). [2](#0-1)  This size is converted straight to `usize` and passed to `felt_range_from_ptr` in `execution_utils.rs`, which I was not able to inspect in full before this session ended — I could only confirm it exists and is called from three sites (`execution_utils.rs`, `deprecated_syscalls/hint_processor.rs`, `syscalls/hint_processor.rs`), but not its internal implementation regarding whether it validates memory bounds before allocating a `Vec` of `array_size` capacity.

This bug class is explicitly acknowledged elsewhere in the same codebase: `apollo_cairo_utils::CairoArray::try_from` had to add an explicit check — "Validate before allocating to prevent a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`" — comparing the declared length against `iter.len()` (remaining felts) before calling `Vec::with_capacity(num_items)`. [3](#0-2)  The non-deprecated (Cairo1) syscall variant of `read_felt_array` also avoids trusting a raw size felt directly — it derives `array_size` from the difference between two VM pointers (`array_data_end_ptr - array_data_start_ptr`), which is implicitly bounded by segment layout. [4](#0-3)  The deprecated Cairo0 path, by contrast, trusts a raw felt value for size with no equivalent guard visible in the code I reviewed.

### Impact Explanation
If `felt_range_from_ptr` allocates a buffer sized to the declared `array_size` before validating that the memory segment actually contains that many cells (mirroring the exact bug the `CairoArray` fix targeted), a malicious Cairo0 class could request an allocation on the order of `usize::MAX` felts, causing the sequencer process to abort or exhaust memory — a denial-of-service analogous to CVE-2022-22971's uncontrolled buffer allocation in Spring's STOMP handling.

### Likelihood Explanation
Reachability requires only declaring a Cairo0 class that issues a syscall (e.g., `call_contract`) with a maliciously large size felt, then invoking it via a normal transaction — no special privileges needed. However, I could not confirm whether `felt_range_from_ptr` actually lacks bounds checking, since I did not get to read its body.

### Recommendation
Confirm the implementation of `felt_range_from_ptr` in `crates/blockifier/src/execution/execution_utils.rs`. If it allocates using the raw, unvalidated `array_size` before checking available memory, add the same defensive check used in `apollo_cairo_utils::CairoArray::try_from` — reject the size early if it's inconsistent with actual available memory, or use resource-bounded incremental reads instead of `Vec::with_capacity(array_size)`.
