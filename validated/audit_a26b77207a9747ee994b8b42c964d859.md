### Title
Meta-Transaction Deposit Refund Misdirected to Sender Instead of Relayer Who Paid — (`runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

---

### Summary

When a relayer submits a meta transaction (NEP-366 `DelegateAction`) that includes an attached deposit on an inner action, and that inner action fails on the receiver's shard, the deposit refund is sent to the **sender** (`delegate_action.sender_id`, i.e. Alice) rather than the **relayer** who actually paid the deposit. An unprivileged user (Alice) can deliberately craft a `DelegateAction` with a large attached deposit that is guaranteed to fail, causing the relayer to permanently lose those tokens to Alice.

---

### Finding Description

In `apply_delegate_action`, the inner receipt spawned from a `DelegateAction` is constructed with:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // Alice — the DelegateAction sender
    receiver_id: delegate_action.receiver_id().clone(),
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // relayer
        ...
    }),
});
``` [1](#0-0) 

The `predecessor_id` of the inner receipt is set to `sender_id` (Alice), not the relayer. When this inner receipt fails on Bob's shard, `refund_unspent_gas_and_deposits` issues the deposit refund to `receipt.balance_refund_receiver()`:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),
        deposit_refund,
    ));
}
``` [2](#0-1) 

`balance_refund_receiver()` resolves to `predecessor_id()` when no explicit `refund_to` override is set (which is always the case for `ReceiptEnum::Action` — the V1 receipt type used here):

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [3](#0-2) 

Since `predecessor_id` of the inner receipt is Alice, the deposit refund goes to Alice. The relayer, who paid the deposit when the transaction was converted to a receipt, receives nothing back.

The `total_deposit` function in `config.rs` confirms that for `DelegateAction`, the deposit is counted as belonging to the relayer's payment but is refunded to the sender on failure:

```rust
// Note, here Relayer pays the deposit but if actions fail, the deposit is
// refunded to Sender of DelegateAction
``` [4](#0-3) 

The official documentation explicitly acknowledges this broken invariant:

> "At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a **financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard**." [5](#0-4) 

---

### Impact Explanation

An unprivileged user (Alice) can steal NEAR tokens from any relayer by:

1. Crafting a `DelegateAction` with a large `deposit` attached to an inner `FunctionCall` targeting a contract method that is guaranteed to panic or revert (e.g., a non-existent method, or a method Alice controls that always panics).
2. Sending the signed `DelegateAction` to a relayer.
3. The relayer submits the meta transaction, paying the deposit out of its own balance.
4. The inner action fails on the receiver's shard.
5. The deposit refund receipt is issued to Alice (`predecessor_id` of the inner receipt), not the relayer.

The relayer loses the full attached deposit. The maximum deposit per action is bounded only by the relayer's account balance. Alice can repeat this attack with different relayers or different nonces.

This is a direct, unprivileged **theft of funds** from the relayer, triggered entirely by ordinary user-submitted transactions with no privileged access required.

---

### Likelihood Explanation

- Any user who understands the meta transaction protocol can execute this attack with zero on-chain privileges.
- The attack requires only a valid `DelegateAction` signature (which Alice herself produces) and a willing or unsuspecting relayer.
- Relayers are application-layer entities that cannot inspect whether an inner action will fail before submitting; they can only check current state, not future execution outcomes.
- The attack is repeatable and scales linearly with the deposit amount Alice can convince the relayer to forward.
- The nearcore codebase itself documents this as a known financial incentive for abuse, confirming the attack path is real and reachable.

---

### Recommendation

The deposit refund for a failed inner receipt in a meta transaction should be sent to the **relayer** (the `signer_id` of the outer receipt / the account that actually paid), not to the `predecessor_id` of the inner receipt (Alice).

Concretely, `apply_delegate_action` should set `refund_to` on the inner receipt to the relayer's account ID when constructing the `ReceiptEnum::ActionV2` variant (which carries the `refund_to` field in `ActionReceiptV2`):

```rust
pub struct ActionReceiptV2 {
    pub signer_id: AccountId,
    pub refund_to: Option<AccountId>,  // set this to the relayer
    ...
}
``` [6](#0-5) 

Alternatively, the inner receipt's `predecessor_id` could be set to the relayer rather than Alice, but this would break the `predecessor_account_id()` host function semantics visible to the receiving contract.

The cleanest fix is to populate `refund_to` in the inner receipt with `action_receipt.signer_id()` (the relayer) so that `balance_refund_receiver()` returns the relayer instead of Alice.

---

### Proof of Concept

**Actors:**
- `relayer.near` — submits the meta transaction, pays the deposit
- `alice.near` — crafts the `DelegateAction`, receives the stolen deposit
- `bob.near` — receiver of the inner action (has no contract deployed, so any function call fails)

**Steps:**

1. Alice creates and signs a `DelegateAction`:
   - `sender_id = "alice.near"`
   - `receiver_id = "bob.near"`
   - `actions = [FunctionCall { method_name: "nonexistent", deposit: 10 NEAR, gas: 100 TGas }]`

2. Alice sends the signed `DelegateAction` to the relayer off-chain.

3. The relayer wraps it in a transaction:
   - `signer = "relayer.near"`, `receiver = "alice.near"`
   - `actions = [Delegate(signed_delegate_action)]`
   - The relayer's account is charged `10 NEAR` (deposit) + gas fees.

4. On Alice's shard, `apply_delegate_action` creates the inner receipt:
   - `predecessor_id = "alice.near"` ← Alice
   - `signer_id = "relayer.near"` ← relayer
   - `receiver_id = "bob.near"`

5. On Bob's shard, the function call fails (`AccountDoesNotExist` or `MethodNotFound`).

6. `refund_unspent_gas_and_deposits` issues:
   - **Deposit refund** → `Receipt::new_balance_refund("alice.near", 10 NEAR)` ← Alice gets 10 NEAR
   - **Gas refund** → `Receipt::new_gas_refund("relayer.near", ...)` ← relayer gets only unused gas back

**Result:** Alice receives 10 NEAR that the relayer paid. The relayer's net loss is 10 NEAR minus the gas refund. Alice can repeat this attack indefinitely. [7](#0-6) [8](#0-7)
