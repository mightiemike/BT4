Based on my research, I found a concrete analog: `RuntimeFeesConfig::gas_penalty_for_gas_refund` computes the NEP-536 refund penalty using integer division that truncates toward zero (floor), which rounds the penalty *down* — favoring the user's refund at the protocol's expense, exactly the pattern the Ramses report flags as dangerous.

### Title
Gas-refund penalty is rounded down, systematically under-charging users and leaking value from the protocol - (File: `core/parameters/src/cost.rs`)

### Summary
`gas_penalty_for_gas_refund` computes the NEP-536 refund penalty as `gas_refund * numer / denom` using plain integer division, which always truncates toward zero. Since this value is a *penalty subtracted from the user's refund* (i.e., value that should accrue to the protocol/burnt supply, not the user), rounding it down means the protocol systematically collects less than the exact formula specifies, and the user keeps the rounding remainder. This mirrors the Ramses `secondsDebtDeltaX96` bug: a value that benefits the protocol is being rounded in the direction that favors the user instead.

### Finding Description
In `core/parameters/src/cost.rs`:
```rust
pub fn gas_penalty_for_gas_refund(&self, gas_refund: Gas) -> Gas {
    let relative_cost = Gas::from_gas(
        (u128::from(gas_refund.as_gas()) * *self.gas_refund_penalty.numer() as u128
            / *self.gas_refund_penalty.denom() as u128)
            .try_into()
            .unwrap(),
    );
    let penalty = std::cmp::max(relative_cost, self.min_gas_refund_penalty);
    std::cmp::min(penalty, gas_refund)
}
``` [1](#0-0) 
The integer division `gas_refund.as_gas() * numer / denom` truncates any fractional remainder, i.e. it always rounds down. This `penalty` is then subtracted from the user's gas refund in `refund_unspent_gas_and_deposits`:
```rust
let refund_penalty_amount = safe_gas_to_balance(penalty_gas_price, refund_penalty)?;
let unused_gas_balance_refund = safe_gas_to_balance(gas_purchase_price, gross_gas_refund)?
    .saturating_sub(refund_penalty_amount);
``` [2](#0-1) 
The penalty amount is ultimately added to `tx_burnt_amount` (i.e., burnt/removed from supply, benefiting the protocol/network overall):
```rust
tx_burnt_amount = safe_add_balance(tx_burnt_amount, gas_refund_result.refund_penalty)?;
``` [3](#0-2) 
Because the penalty calculation rounds down, and the same rounded-down penalty is both the amount subtracted from the user's refund and the amount burnt, the user always receives at least as much refund as (and sometimes strictly more than) the "exact" `gas_refund_penalty` fraction dictates — the truncated remainder is neither burnt nor charged to the user, it is simply absorbed as extra refund to the user. This is the same class of issue as the Ramses report: a value that should be rounded in favor of the protocol (the amount to be deducted/burnt) is instead rounded in favor of the party paying it (the user receiving the refund).

### Impact Explanation
Per-transaction the truncation error is at most `1` unit of `Gas` (bounded by integer division truncation), so a single transaction leaks a negligible amount. However, this is a systematic, protocol-wide, per-receipt rounding bias reachable by every signer that generates a gas refund (i.e., essentially all `FunctionCall` receipts with unspent gas), executed on every chunk application. Over the life of the chain this causes a deterministic (not random) micro-leakage of value from the "burnt" pool to end users on every refund-generating receipt, which is exactly the kind of small, always-favors-the-caller rounding error that the cited report warns can be amplified (e.g., via a script issuing many small function calls with slightly oversized attached gas designed to maximize the count of penalty roundings) into a non-trivial value transfer, and, more importantly, is a violation of the intended economic invariant that the protocol always rounds fee/penalty calculations in its own favor. There's currently no live economic exploit since `gas_refund_penalty` is set to `0/100` and `min_gas_refund_penalty` to `0` on mainnet (per `protocol-model/spec/economics.md`), meaning the penalty is currently always zero and this bug is dormant. It would become live once NEP-536 penalties are activated with non-zero rates.

### Likelihood Explanation
Reachable by any unprivileged user simply by submitting a normal `FunctionCall` transaction/receipt that leaves unspent gas — this is one of the most common execution paths in the protocol (`refund_unspent_gas_and_deposits`, invoked from `apply_action_receipt` for essentially every non-refund receipt with leftover gas). No special privileges, timing, or adversarial conditions are required. The only reason it's not exploitable **today** is that the relevant economic parameters (`gas_refund_penalty`, `min_gas_refund_penalty`) are currently zero on mainnet; the rounding bug itself is always present in the code and would activate whenever those parameters change to non-zero values, as NEP-536 originally specified.

### Recommendation
Round the penalty calculation up (ceiling division) rather than down, since the penalty is value that should accrue to the protocol (burnt), not to the user:
```rust
let relative_cost = Gas::from_gas(
    (u128::from(gas_refund.as_gas()) * numer + denom - 1) / denom
);
```
Alternatively, use a checked "round up" helper (analogous to `FullMath.mulDivRoundingUp` in the referenced Solidity report) consistently anywhere a value is computed that is subtracted from a user-facing refund and credited to the protocol/burnt-supply side.

### Proof of Concept
1. Set `gas_refund_penalty = 1/3` (a fraction that does not divide evenly) and a receipt with `gross_gas_refund = 10` gas.
2. `gas_penalty_for_gas_refund(10)` computes `10 * 1 / 3 = 3` (floor of `3.33`), so `penalty = 3`.
3. The "fair" penalty rounded in the protocol's favor would be `4` (ceiling of `3.33`).
4. The user's refund is thus `10 - 3 = 7` instead of the protocol-favoring `10 - 4 = 6`; the extra `1` gas-equivalent value is retained by the user instead of being burnt, on every single receipt refund calculation, deterministically and reproducibly by calling `RuntimeFeesConfig::gas_penalty_for_gas_refund` with any `gas_refund` value not evenly divisible by `denom`.
