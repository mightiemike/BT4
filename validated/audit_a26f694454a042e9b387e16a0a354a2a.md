### Title
Camera/Microphone permission grants ignore the embedding (top-level) origin, allowing silent cross-context reuse of persisted permission - (File: chrome/browser/media/webrtc/media_stream_device_permission_context.cc)

### Summary
`MediaStreamDevicePermissionContext::GetContentSettingStatusInternal` explicitly discards the `embedding_origin` parameter and looks up the persisted camera/microphone content setting keyed only by `(requesting_origin, requesting_origin)`, ignoring the actual top-level/embedding context the request came from.

### Finding Description
The permission lookup for `MEDIASTREAM_MIC`/`MEDIASTREAM_CAMERA` is: [1](#0-0) 

The comment directly documents the root cause: `// TODO(raymes): currently mic/camera permission doesn't consider the embedder.` and the base-class lookup is invoked with `requesting_origin` passed twice instead of `(requesting_origin, embedding_origin)`. This means a persisted camera/microphone grant for origin `A` is honored identically whether `A` is loaded as a top-level page or embedded as a third-party (cross-origin) frame inside a completely different top-level site `B`.

For comparison, other permission contexts in the same codebase explicitly handle the third-party case defensively. `NotificationPermissionContext::GetContentSettingStatusInternal` treats cross-origin (`requesting_origin != embedding_origin`) `ASK` results as `BLOCK`: [2](#0-1) , and its `DecidePermission` outright denies any cross-origin request rather than prompting: [3](#0-2) . `MediaStreamDevicePermissionContext` has no equivalent origin-pair check — it neither considers the embedder when looking up an existing grant nor differentiates first-party vs. third-party context when returning `CONTENT_SETTING_ALLOW`.

The reachable path from an untrusted top-level page is: attacker page embeds an `<iframe allow="camera;microphone" src="https://victim.example">`, which the Permissions Policy allows only if the attacker explicitly grants delegation via the `allow` attribute (this is attacker-controlled, not a policy/flag requirement). If the user previously granted camera/mic access to `victim.example` while visiting it directly (first-party), `getUserMedia()` called from within that cross-origin iframe will resolve via `MediaStreamDevicePermissionContext::GetContentSettingStatusInternal`, which returns `CONTENT_SETTING_ALLOW` based solely on `requesting_origin` — silently granting camera/microphone access with no re-prompt, in a third-party embedding context the user never consented to.

This matches the CVE-2019-11748 bug class exactly: WebRTC honoring a persisted, first-party-granted media permission when the origin is subsequently reached in a third-party/embedded context, without re-prompting the user.

### Impact Explanation
This allows cross-origin disclosure of camera/microphone media streams: a malicious top-level page can silently capture audio/video from a victim origin the user previously trusted, without any additional user interaction or notification, as long as the victim site is embeddable (no `X-Frame-Options`/`frame-ancestors` restriction) and the attacker sets the Permissions Policy `allow` attribute. This is a privacy-sensitive information-disclosure bug (matches CVSS vector `C:H` from the referenced CVE).

### Likelihood Explanation
Exploitation requires: (1) the user has previously granted camera/mic permission to some origin `victim.example` in a first-party context, (2) `victim.example` does not block framing, and (3) the attacker embeds it with `allow="camera;microphone"`. All of these are attacker/page-controlled or common defaults (many sites don't set `X-Frame-Options`), so likelihood is moderate — comparable to the original Firefox advisory's real-world impact rating (Medium).

### Recommendation
Update `MediaStreamDevicePermissionContext::GetContentSettingStatusInternal` to pass the actual `embedding_origin` (not `requesting_origin`) into the base class content-setting lookup, and add an explicit first-party/third-party distinction similar to `NotificationPermissionContext` — e.g., treat `ASK`/ambiguous states as `BLOCK` for cross-origin embedding contexts and re-prompt (or deny) rather than silently reusing a first-party grant, per the existing `crbug.com/41014586` tracking bug referenced in the TODO.

### Proof of Concept
1. Visit `https://victim.example` directly and grant camera/microphone permission (persisted as `CONTENT_SETTING_ALLOW` for that origin).
2. Visit an attacker-controlled page `https://attacker.example` that embeds:
   ```html
   <iframe src="https://victim.example/capture.html" allow="camera; microphone"></iframe>
   ```
3. Inside the iframe, script calls `navigator.mediaDevices.getUserMedia({audio:true, video:true})`.
4. Because `MediaStreamDevicePermissionContext::GetContentSettingStatusInternal` looks up the setting using only `requesting_origin` (ignoring the actual embedding origin `attacker.example`), the call resolves to `CONTENT_SETTING_ALLOW` without prompting the user, and the stream is granted silently in the third-party context.

Note: I could not directly trace the full call path from `navigator.mediaDevices.getUserMedia` through `PermissionContextBase::GetPermissionStatus`/`RequestPermission` down to this function (the `components/permissions/content_setting_permission_context_base.cc` file was not resolvable in the index), so the exact call chain from the renderer request to this specific method should be verified in a full checkout before treating this as conclusively proven; the root-cause code and its self-documented limitation (the TODO comment) are confirmed directly from the file.

void NotificationPermissionContext::DecidePermission(
    std::unique_ptr<permissions::PermissionRequestData> request_data,
    permissions::BrowserPermissionCallback callback) {
  DCHECK_CURRENTLY_ON(content::BrowserThread::UI);

  // Permission requests for either Web Notifications and Push Notifications may
  // only happen on top-level frames and same-origin iframes. Usage will
  // continue to be allowed in all iframes: such frames could trivially work
  // around the restriction by posting a message to their Service Worker, where
  // showing a notification is allowed.
  if (request_data->requesting_origin != request_data->embedding_origin) {
    std::move(callback).Run(content::PermissionResult(
        blink::mojom::PermissionStatus::DENIED,
        content::PermissionStatusSource::UNSPECIFIED));
    return;
  }
