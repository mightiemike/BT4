### Title
Unchecked `common.HexToAddress` silently coerces a malformed refund/revert recipient to the zero address, causing minted PRC20 funds to be sent to `0x0` — ([File: x/uexecutor/keeper/outbound.go])

### Summary
Revert/refund fund-routing in `x/uexecutor` derives an EVM recipient address from attacker-influenced string fields (`Inbound.RevertInstructions.FundRecipient`, `OutboundTx.Sender`) via `common.HexToAddress(...)`, then immediately issues a `DerivedEVMCall` (`CallPRC20Deposit` / `CallUniversalCoreRefundUnusedGas`) targeting that address with no check that the resulting address is non-zero. Go-ethereum's `common.HexToAddress` silently returns the zero address for any string that fails hex decoding (odd length, invalid characters, non-hex encodings such as base58/Solana addresses), rather than erroring. This mirrors the reported bug class: "the call still executes even though the target address was never properly set (zero address), and execution does not revert" — except here the impact is direct fund loss (minted PRC20 sent to `address(0)`), not just incorrect behavior.

### Finding Description
`RevertInstructions.FundRecipient` is a free-form string carried on `Inbound` (and propagated to `OutboundTx`), decoded by validators from source-chain event data that the depositing user fully controls [1](#0-0) .

Canonicalization is intentionally lenient and never rejects malformed values — it just trims and passes them through unchanged if they don't parse as a valid address for the chain's namespace [2](#0-1) . `Inbound.Canonicalize()` applies this lenient canonicalization to `RevertInstructions.FundRecipient` [3](#0-2) , and `Inbound.ValidateForExecution()` never validates the format of `RevertInstructions.FundRecipient` at all (only `Recipient` is checked, and only for `isCEA`/`FUNDS`/`GAS` types) [4](#0-3) .

This unchecked value is then used directly as the revert-outbound recipient: `buildRevertOutbound` sets `recipient := inbound.Sender`, overridden by `inbound.RevertInstructions.FundRecipient` if non-empty, with no address-format validation [5](#0-4) .

When a failed outbound is later reverted, the same unchecked value is converted straight to an EVM address and used to mint PRC20 back on-chain:
```go
recipient := outbound.Sender
if outbound.RevertInstructions != nil && outbound.RevertInstructions.FundRecipient != "" {
    recipient = outbound.RevertInstructions.FundRecipient
}
...
receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)
``` [6](#0-5) 

The excess-gas refund path does the identical unchecked conversion before calling `CallUniversalCoreRefundUnusedGas`:
```go
refundRecipient := outbound.Sender
if outbound.RevertInstructions != nil && outbound.RevertInstructions.FundRecipient != "" {
    refundRecipient = outbound.RevertInstructions.FundRecipient
}
recipientAddr := common.HexToAddress(refundRecipient)
...
resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, true, fee, minPCOut)
``` [7](#0-6) 

Both `CallPRC20Deposit` and `CallUniversalCoreRefundUnusedGas` issue a `DerivedEVMCall` unconditionally with whatever `to`/recipient address is supplied — there is no `to != address(0)` guard anywhere in the chain of calls [8](#0-7) . `go-ethereum`'s `common.HexToAddress` (via `FromHex`/`hex.DecodeString`) returns `nil`/zero bytes on any decode failure rather than erroring, so any FundRecipient string that isn't a well-formed 20-byte hex string (e.g., a Solana base58 address supplied for a non-EVM source chain, a truncated/garbled string, or deliberately malformed data crafted by the depositor on the source chain) silently becomes `0x0000000000000000000000000000000000000000`.

### Impact Explanation
This is an unprivileged, attacker-triggerable path to permanent loss of protocol-minted funds: an ordinary depositor who initiates an inbound deposit on any supported external chain controls the raw event payload that becomes `Inbound.RevertInstructions.FundRecipient` (and, on non-EVM source chains, `Inbound.Sender`, which is the fallback). By supplying a value that is not a valid 20-byte hex string, the attacker can force any subsequent revert (deposit failure, gas-and-payload swap failure, RescueFunds/RevertStuckInbound flow, or a failed/observed-failed outbound requiring re-mint) to mint the bridged PRC20 tokens to the EVM zero address instead of reverting or failing safely. Because `DerivedEVMCall` treats this as a normal successful transaction (mint succeeds against `0x0`), the PCTx/OutboundTx will be recorded as `SUCCESS`, masking the fact that funds are unrecoverable. This satisfies the in-scope impact of "permanent loss/permanent freezing of user or protocol-controlled funds" and "corruption of ... refund accounting ... revert destination".

### Likelihood Explanation
Likelihood is high for anyone attempting it deliberately: the trigger requires only a normal cross-chain deposit with a crafted revert-recipient field, no validator or admin collusion, and no privileged access. The lenient canonicalization design explicitly documents that malformed values are "kept trimmed, never rejected" so that honest validators still converge on the same (malformed) value and vote it in without dropping the inbound — which is precisely what makes the value reach the mint call unmodified. The actual trigger condition (a revert/refund actually firing) does require some downstream condition to fail (e.g., missing token config, swap failure, external-chain execution failure, or an admin/expired-ballot revert), but several of those conditions are also attacker-influenceable or simply routine (e.g., outbound execution failing on the destination chain), making this practically reachable.

### Recommendation
Before calling `CallPRC20Deposit` or `CallUniversalCoreRefundUnusedGas` (and any other `DerivedEVMCall`/`CallEVM` site that derives its `to`/recipient from a user-supplied string), validate that:
1. The source string is a well-formed 20-byte hex address (reject/short-circuit if `common.IsHexAddress(...)` is false), and
2. The resulting `common.Address` is not the zero address (`recipientAddr != (common.Address{})`).

When validation fails, do not execute the mint/refund call — instead mark the PCTx/refund as `FAILED` with a clear error, keep the outbound in an `ABORTED`/manual-intervention state (consistent with the existing `AbortOutbound` pattern already used for other re-mint failures), and surface the raw offending value for operator remediation, rather than silently minting to `0x0`.

### Proof of Concept
1. Attacker deposits on a supported external (e.g., non-EVM) source chain via the gateway, embedding an arbitrary/garbled string (not a valid 20-byte hex value, e.g. `"not-a-real-address"` or a Solana base58 string) as the revert-recipient field of the deposit event.
2. Honest Universal Validators decode and vote in this `Inbound`; `ValidateBasic`/`ValidateForExecution` pass because `RevertInstructions.FundRecipient` format is never checked, and `Canonicalize()` leaves the malformed value as-is [3](#0-2) .
3. Any downstream condition triggers a revert for this inbound (e.g., token config temporarily missing, as already exercised by `TestInboundGas` "missing token config records FAILED PCTx and creates revert" [9](#0-8) ), causing `buildRevertOutbound` to set `Recipient = RevertInstructions.FundRecipient` (the garbled string) [5](#0-4) .
4. If/when this revert outbound path re-mints funds (`handleFailedOutbound`), `common.HexToAddress(recipient)` on the garbled string silently returns the zero address, and `CallPRC20Deposit` mints the full bridged amount to `0x000...000` [6](#0-5) , permanently burning the refunded tokens while the PCTx/outbound is recorded as `SUCCESS`.

Note: I was not able to execute this against a live node/test harness to confirm the exact downstream trigger conditions under which `handleFailedOutbound`/`applyGasRefund` fire for a garbled (non-EVM-formatted) `FundRecipient` specifically — this assessment is based on static code tracing of the validation, canonicalization, and call-site logic described above.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
