### Title
Missing Slippage Protection in ExchangeInjectActuator and ExchangeWithdrawActuator - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Both liquidity-pool actuators for TRON's bancor-style `Exchange` feature compute the counterpart token amount dynamically from the exchange's live reserve ratio at execution time, but unlike `ExchangeTransactionActuator` (which added an `expected` slippage-bound field), neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` lets the user bound how much of the other token they are willing to pay or how little they are willing to accept.

### Finding Description
`ExchangeInjectActuator.execute` computes `anotherTokenQuant` from the current `firstTokenBalance`/`secondTokenBalance` ratio at block-processing time and unconditionally deducts it from the caller's account. [2](#0-1)  The validate path recomputes the same ratio just before execution but only checks that `anotherTokenQuant > 0` and within balance/limit bounds — there is no user-supplied ceiling. [3](#0-2) 

`ExchangeWithdrawActuator` has the same pattern: `anotherTokenQuant` (the amount of the other token the withdrawer will *receive*) is derived from the live ratio, and although there is a "Not precise enough" rounding-drift check, there is no user-specified minimum-received guard. [4](#0-3) [5](#0-4) 

By contrast, `ExchangeTransactionActuator` (the actual "buy" path) was designed with exactly the slippage-protection pattern the external report recommends: the contract carries a `getExpected()` field and validation rejects the trade if the computed `anotherTokenQuant` is below it. [6](#0-5)  The proto definitions confirm this asymmetry: `ExchangeTransactionContract` has an `expected` field, `ExchangeInjectContract`/`ExchangeWithdrawContract` do not. [1](#0-0) 

Both `ExchangeInjectContract` and `ExchangeWithdrawContract` transactions are broadcast by anonymous senders via the standard RPC/HTTP transaction-broadcast path and, like all TRON transactions, sit in the mempool for some time before being packed into a block, during which other broadcast `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions from third parties can shift the pool ratio.

### Impact Explanation
A user injecting or withdrawing liquidity from an `Exchange` pool has no way to bound the amount of the counterpart token they will pay (inject) or the minimum amount they will receive (withdraw). If the pool ratio shifts between transaction construction/signing and on-chain execution — whether from ordinary trading activity or from an attacker deliberately front-running the pending inject/withdraw transaction with their own `ExchangeTransactionContract`/`ExchangeInjectContract` transaction (transaction ordering within a block/mempool is not guaranteed to match submission order) — the actuator will still execute using whatever ratio exists at block-processing time. This can cause the injector to pay substantially more of the second token than intended, or the withdrawer to receive substantially less than intended, i.e. direct accounting/value loss for the affected account with no on-chain recourse.

### Likelihood Explanation
Exploitation only requires broadcasting an ordinary, unprivileged transaction (`ExchangeTransactionContract` or another `ExchangeInjectContract`) against the same exchange pool ID before the victim's inject/withdraw transaction is packed — something any network participant can do since exchange IDs and pending pool states are public. No special privileges, leaked keys, or node compromise are required, making this a plausible sandwich/front-running scenario limited only by normal TRON block-time/mempool-ordering constraints.

### Recommendation
Add slippage-bound fields to `ExchangeInjectContract` (e.g., `max_another_token_quant` — a cap the caller is willing to spend of the other token) and `ExchangeWithdrawContract` (e.g., `min_another_token_quant` — a floor for the amount to receive), mirroring the `expected` pattern already implemented in `ExchangeTransactionContract`, and enforce these bounds in `ExchangeInjectActuator.doValidate` / `ExchangeWithdrawActuator.doValidate` before allowing execution.

### Proof of Concept
1. Exchange pool with `firstTokenBalance = A`, `secondTokenBalance = B` at ratio `B/A`.
2. Victim broadcasts `ExchangeInjectContract` intending to inject `q` of the first token, expecting to also spend roughly `q*B/A` of the second token, based on the ratio observed at signing time.
3. Attacker observes the pending transaction (mempool visibility) and broadcasts their own `ExchangeTransactionContract`/`ExchangeInjectContract` against the same `exchange_id` that shifts the ratio unfavorably before the victim's transaction is included.
4. When the victim's `ExchangeInjectActuator.execute` runs, `anotherTokenQuant` is recomputed from the now-shifted ratio at lines 71-83, causing the victim to pay more second-token than anticipated with no reverting check, since there is no `expected`/max-spend field to enforce the original terms.
