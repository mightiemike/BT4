## Title
`AccountPermissionUpdateContract` performs one-step, unconfirmed owner-permission reassignment - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

## Summary
The reported bug is that `Vault.sol` transfers ownership in a single step via `setOwner()`, with no acceptance step from the new owner, risking permanent loss of control if a wrong address is supplied. The same bug class is present in java-tron's `AccountPermissionUpdateActuator`, which lets any account atomically overwrite its own `Owner` (and `Active`/`Witness`) `Permission` in a single transaction, with no two-step "propose then accept" flow that would require the new key-holder to prove control of the target address before the reassignment takes effect.

## Finding Description
`AccountPermissionUpdateActuator.execute()` unpacks the `AccountPermissionUpdateContract` and immediately calls `AccountCapsule.updatePermissions()`, replacing the account's owner permission (and active/witness permissions) in the same step, with the result committed straight to the `AccountStore`: [1](#0-0) 

The corresponding capsule mutation is likewise a direct, one-shot overwrite: [2](#0-1) 

`validate()` only checks structural well-formedness of the new permission — address format validity (`DecodeUtil.addressValid`), key-count bounds, weight/threshold sanity, and duplicate-key rejection via `checkPermission()`. At no point does it (or any other mechanism) require the address(es) being granted the new `Owner` permission to counter-sign, acknowledge, or otherwise prove possession of the corresponding private key before the reassignment is finalized: [3](#0-2) [4](#0-3) 

This is structurally the same defect as the reported `Vault.setOwner()` issue: a privileged/critical role (here, the account's `Owner` permission, which alone can subsequently re-authorize `Active`/`Witness` permissions and control multisig thresholds via further `AccountPermissionUpdateContract` transactions) is reassigned in one irreversible step, with no second-party confirmation that the new key is reachable/controlled.

## Impact Explanation
Because the transition is one-step and final upon block inclusion, any mistake in specifying the new `Owner` key set (mistyped address, wrong key pasted, key generated but never backed up, or a malicious dApp/contract that induces the user to sign a permission-update transaction with attacker-controlled keys embedded) results in immediate and permanent loss of the account owner's ability to control the account — no `Active` permission holder can subsequently correct the `Owner` permission after the fact because `updatePermissions` is only reachable via a correctly-signed `AccountPermissionUpdateContract`, which itself requires the (now-lost) owner authority for `Owner`-permission changes. This is an invalid/irrecoverable-state outcome for the affected account, directly analogous to the `Vault` owner-transfer bug's "permanent loss of `onlyOwner` functionality" impact.

## Likelihood Explanation
The `AccountPermissionUpdateContract` is a standard, publicly reachable transaction type available to any account once multisig is enabled (`AllowMultiSign`), gated only by the fee threshold `getUpdateAccountPermissionFee()`. No special/trusted role is required to trigger the actuator — any account owner can invoke it on their own account, and any tooling/wallet/dApp bug or phishing-crafted transaction that gets signed can trigger it unintentionally.

## Recommendation
Introduce a two-step confirmation flow for `Owner` permission changes analogous to `ProposableOwnable.sol`/`Ownable2Step.sol`: require the new key(s) named in the proposed `Owner` permission to submit a confirming/accepting transaction (or signature) before the pending permission change is committed to the `AccountCapsule`, with the ability to cancel/overwrite the pending proposal using the still-valid current `Owner` permission.

## Proof of Concept
1. Account `A` (owner key `K1`) enables multisign and calls `AccountPermissionUpdateContract` setting `Owner` permission keys to `[K2]` (a typo'd/uncontrolled address) via `AccountPermissionUpdateActuator.execute()`. [1](#0-0) 
2. `validate()` passes because `K2` is a well-formed, valid-format address (`DecodeUtil.addressValid` only checks format, not reachability) and all other structural checks (`checkPermission`) succeed. [5](#0-4) 
3. `updatePermissions` overwrites `OwnerPermission` in the same transaction with no pending/acceptance state. [2](#0-1) 
4. Account `A` no longer has any signer that can satisfy the new `Owner` permission threshold, permanently losing the ability to further modify its own `Owner`/`Active`/`Witness` permissions.

  private boolean checkPermission(Permission permission) throws ContractValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");
      }
      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {
        weightSum = addExact(weightSum, key.getWeight());
      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }
    if (weightSum < permission.getThreshold()) {
      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission
              .getType());
    }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
