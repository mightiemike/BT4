## Title
Hardcoded, non-network-parameterized `ADDRESS_REGISTRAR_ACCOUNT_ID` in the ETH Wallet Contract bypasses the anti-redirection safety check - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The ETH Wallet Contract (deployed to ETH-implicit accounts to emulate Ethereum transactions, NEP-518) hardcodes the address-registrar account it queries to detect malicious relayers. Unlike `CHAIN_ID`, which the build script explicitly re-writes for each target network (mainnet/testnet/localnet), `ADDRESS_REGISTRAR_ACCOUNT_ID` is baked into every build from a single, unversioned file and is never varied per network, exactly analogous to the reported "Hardcoded WETH" bug class (a single-network constant embedded into code meant to run identically across multiple environments).

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is loaded once at compile time from a static file: [1](#0-0) [2](#0-1) 

Contrast this with `CHAIN_ID`, whose `build.rs` deliberately swaps in a different value per network before invoking the Docker build for each of the three released artifacts (mainnet/testnet/localnet): [3](#0-2) 

No equivalent per-network substitution exists for `ADDRESS_REGISTRAR_ACCOUNT_ID` — it is a single value shared by the mainnet, testnet, and localnet WASM builds. This is confirmed by the test harness, which must manually monkey-patch this file before building the contract for a sandbox/local deployment, then restore it afterward: [4](#0-3) 

At runtime, this fixed account is used as the trust anchor for the contract's core anti-relayer-fraud defense. When a relayer routes an emulated base-token transfer to another ETH-implicit account (`TargetKind::EthImplicit(address)`), the contract queries the registrar to check whether that address is actually mapped to a named NEAR account: [5](#0-4) 

The callback then treats a "registered" answer as proof the relayer was faulty (and bans it / rejects the transfer), while an "unregistered" answer lets the transfer through as the presumed genuine intent of the user: [6](#0-5) 

Because the trusted registrar identity is a single hardcoded string baked into the compiled contract rather than something derived/validated per chain (the way `eth_wallet_global_contract_hash` and `wallet_contract_magic_bytes` correctly branch on `chain_id`), any deployment environment where the real, governance-controlled `AddressRegistrar` contract is not present at that exact account — or is temporarily unavailable/misconfigured — either breaks the safety check entirely (promise to a non-existent contract fails, `address_check_callback` unconditionally reports failure) or, if that account can ever be provisioned by someone other than the intended registrar operator on that network, allows a spoofed `lookup()` response (see `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`) that always returns `None`, silently defeating the check the contract relies on to stop a malicious/faulty relayer from misdirecting an EOA-targeted base-token transfer.

### Impact Explanation
This is Medium severity: the wallet contract's fraud-prevention mechanism for base-token transfers is anchored to a constant that is not network-aware, mirroring the hardcoded-WETH root cause (an address correct for one environment silently reused for others). Depending on deployment/environment drift, this either (a) permanently breaks a security check for legitimate EthImplicit-targeted transfers on any network where the real registrar account doesn't match, or (b) if the registrar identity can diverge from the intended contract, enables a relayer to bypass the "existing named account" redirection check and move a user's transfer to an ETH-implicit shadow account instead of the correctly named account the address is actually registered to.

### Likelihood Explanation
Likelihood is moderate: exploitation of the bypass path requires control of, or divergence in, the account at the hardcoded name on a given network, which is somewhat mitigated by top-level account creation restrictions (`registrar_account_id`-gated creation for short names) — but the underlying design flaw (single fixed identity with no per-network parameterization or on-chain verification of the registrar's authenticity) is unconditionally present in every compiled artifact and is directly reachable by any relayer/meta-transaction sender operating a wallet contract's `rlp_execute` flow.

### Recommendation
Parameterize `ADDRESS_REGISTRAR_ACCOUNT_ID` per network the same way `CHAIN_ID` is parameterized in `build.rs` (distinct values baked into `wallet_contract_mainnet.wasm`, `wallet_contract_testnet.wasm`, `wallet_contract_localnet.wasm`), and/or validate the registrar's identity/code hash on-chain (analogous to `eth_wallet_global_contract_hash`) rather than trusting a single string constant to remain correct across all deployment targets indefinitely.

### Proof of Concept
1. Build the wallet contract WASM for a network where the canonical `address-map.near`-equivalent registrar contract has not yet been deployed, or has drifted from the compiled-in identifier.
2. Have a user sign an Ethereum-style transaction whose `to` targets another ETH-implicit account (`TargetKind::EthImplicit`), and submit it via a relayer to `rlp_execute`.
3. `inner_rlp_execute` calls `.lookup()` on the hardcoded registrar account (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:419-425`); because the account either doesn't exist or is controlled by an entity that isn't the intended governance registrar, the promise fails or returns a forged `None`.
4. `address_check_callback` treats this as "address not registered" and lets the transfer proceed to the ETH-implicit account (`lib.rs:161-189`) even though, on the correct/intended registrar, that address maps to a named account — defeating the fraud check the mechanism exists to enforce.

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

fn build_contract(
    dir: &str,
    contract_name: &str,
    output: &str,
    chain_id: u64,
) -> anyhow::Result<()> {
    let wasm_target_path = format!("./res/{}.wasm", output);
    if Path::new(&wasm_target_path).exists() {
        // Skip building if an artifact is already present
        return Ok(());
    }

    let absolute_dir = Path::new(dir).canonicalize()?;

    let chain_id_path = absolute_dir.join("wallet-contract/src/CHAIN_ID");
    let chain_id_content = std::fs::read(&chain_id_path).context("Failed to read CHAIN_ID file")?;

    // Update the chain id before building
    std::fs::write(&chain_id_path, chain_id.to_string().into_bytes())?;
    docker_build(absolute_dir.to_str().expect("path should be valid UTF-8"))?;

    // Restore chain id file to original value after building
    std::fs::write(&chain_id_path, chain_id_content)?;

    let build_artifact_path =
        format!("target/wasm32-unknown-unknown/release/{}.wasm", contract_name);
    let src = absolute_dir.join(build_artifact_path);

    std::fs::copy(&src, &wasm_target_path)
        .with_context(|| format!("Failed to copy `{}` to `{}`", src.display(), wasm_target_path))?;
    Ok(())
