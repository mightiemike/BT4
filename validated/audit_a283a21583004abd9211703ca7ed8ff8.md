### Title
Missing `totalEnergyWeight > 0` runtime guard before division in `RepositoryImpl.calculateGlobalEnergyLimit` - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
The BadgerDAO report flags the absence of a "price > 0" check before a division that determines value flow, so a zero denominator can either revert (DoS) or corrupt the computed ratio. The closest concrete analog in java-tron is `RepositoryImpl.calculateGlobalEnergyLimit`, which divides by `totalEnergyWeight` (a network-wide, mutable "price" of energy per frozen TRX) using only a Java `assert` — a statement that is compiled out at runtime unless the JVM is started with `-ea`, which is not the default for production nodes.

### Finding Description
`calculateGlobalEnergyLimit` reads `totalEnergyWeight` from `DynamicPropertiesStore` and uses it as a divisor without a real conditional check: [1](#0-0) 

Specifically:
```
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
assert totalEnergyWeight > 0;
if (hardenResourceCalculation()) {
  return BigInteger...divide(BigInteger.valueOf(totalEnergyWeight)).longValueExact();
}
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```

Contrast this with the equivalent function in `EnergyProcessor`, which explicitly checks the denominator instead of relying on `assert`: [2](#0-1) 

`EnergyProcessor.calculateGlobalEnergyLimit` and `calculateGlobalEnergyLimitV2` both have real `if (totalEnergyWeight <= 0) return 0;`/`if (totalEnergyWeight == 0) return 0;` guards, but `RepositoryImpl.calculateGlobalEnergyLimit` — used inside TVM contract-call energy accounting via `getAccountEnergyLimitWithFloatRatio` — only has the compiled-out `assert`: [3](#0-2) 

If `totalEnergyWeight` is ever `0` when this path executes:
- With `hardenResourceCalculation()` enabled, `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`, which is uncaught here (no try/catch around this call site in `VMActuator`), causing the transaction/contract call to fail with an unhandled exception rather than a graceful validation error.
- With hardening disabled, `(double) totalEnergyLimit / 0` produces `Infinity` (if `totalEnergyLimit > 0`) or `NaN` (if also `0`). Casting `(long) Infinity` in Java yields `Long.MAX_VALUE`, which would grant an account an effectively unlimited energy limit for the current call — a serious accounting error, not merely a revert.

### Impact Explanation
This differs from the BadgerDAO analog in one important way: I could not conclusively prove within the available context that `totalEnergyWeight` can reach exactly `0` while an account simultaneously has non-zero frozen-for-energy balance in the current production code path (its value is maintained through `FreezeBalanceActuator`/`UnfreezeBalanceActuator`/`FreezeBalanceV2Actuator`/`DelegateResourceActuator` and related processors, and I was not able to fully trace all decrement paths for edge-case underflow to zero within my remaining search budget). Because of this, I can document the missing/soft guard with certainty, but **cannot confirm real-world reachability of the zero-denominator state** with the evidence gathered.

Given this uncertainty, and per the validation rules requiring concrete, provably reachable impact, I am not confident enough to assert a fully proven high-severity finding purely from static reading. The defensive-coding gap (assert vs. explicit check) is real and inconsistent with the sibling `EnergyProcessor` implementation, which is itself evidence the team considers `totalEnergyWeight == 0` a plausible state worth guarding against elsewhere.

### Likelihood Explanation
Low-to-Medium, unconfirmed. The inconsistency between `EnergyProcessor` (explicit guard) and `RepositoryImpl` (assert only) suggests the zero-weight case is anticipated by the team, but I could not verify a live user-triggerable path from the code paths inspected in this session.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check (as already done in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`) that returns `0` (or otherwise safely short-circuits) when `totalEnergyWeight <= 0`, ensuring parity between the two implementations and eliminating reliance on assertions being enabled in production.
